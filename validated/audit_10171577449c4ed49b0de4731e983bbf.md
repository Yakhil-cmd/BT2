### Title
Division-by-Zero Panic in `consolidatedNode.Split()` Crashes Node During Block Reward Finalization When Proposer Has Zero Total Staking Amount — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidatedNode.Split()` divides by `totalAmount = StakingAmount + CLStakingAmount`. Both values are stored in KAIA units (integer-divided by `params.KAIA = 1e18`), so any validator whose staking contract holds less than 1 KAIA **and** whose CL pool also holds less than 1 KAIA will produce `totalAmount = 0`. When such a validator is selected as the block proposer, `specWithProposerAndFunds()` / `specWithProposerAndFundsFlex()` call `cn.Split(proposer)` unconditionally, triggering a Go integer division-by-zero panic that crashes the node during `FinalizeState()`.

---

### Finding Description

`consolidatedNode.Split()` computes the CL-pool share of a reward:

```go
// kaiax/staking/staking_info.go  lines 169-187
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)   // ← panics when totalAmount == 0
    cnAmount := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
``` [1](#0-0) 

Both `StakingAmount` and `CLStakingAmount` are stored in KAIA units after integer division by `params.KAIA`:

```go
// kaiax/staking/impl/getter.go  line 208

Any balance below 1 KAIA (10¹⁸ kei) rounds to 0. A validator whose staking contract holds < 1 KAIA **and** whose CL pool holds < 1 KAIA will have `StakingAmount = 0` and `CLStakingAmount = 0`, making `totalAmount = 0`.

`Split()` is called for the proposer in both `specWithProposerAndFunds()` and `specWithProposerAndFundsFlex()` with **no guard** on `totalAmount`:

```go

    if cn.RewardAddr != config.Rewardbase {
        continue
    }
    if cn.CLStakingInfo == nil {
        break
    }
    cnAmount, clAmount := cn.Split(proposer)   // ← no zero-check before this
    ...
}
``` [3](#0-2) 

The same pattern exists in `specWithProposerAndFundsFlex()`: [4](#0-3) 

By contrast, `assignStakingRewards()` and `assignStakingRewardsFlex()` are safe because they skip nodes with `StakingAmount < minStake` before ever reaching `Split()`: [5](#0-4) 

The proposer path has no equivalent guard.

---

### Impact Explanation

`specWithProposerAndFunds()` / `specWithProposerAndFundsFlex()` are called from `getDeferredRewardFullKore()` / `getDeferredRewardFullFlex()`, which are called from `getDeferredRewardFull()`, which is called from `GetDeferredReward()` during `FinalizeState()` at the end of every block. A Go integer division by zero is an unrecoverable runtime panic. If the panic is not caught by a `recover()` in the call stack, the entire node process crashes.

- **Corrupted value**: the block reward distribution for the proposer is never written; the block is never finalized on this node.
- **Consensus divergence**: the crashing node falls out of the BFT committee while honest peers continue to finalize blocks, splitting the view of the chain.
- **Allowed impact gate**: "Invalid state transition … or consensus divergence on honest nodes."

---

### Likelihood Explanation

**Trigger conditions (all must hold simultaneously):**

1. The Kore/Prague/Osaka hardfork is active (`getDeferredRewardFull` routes to the affected path).
2. The proposer's consolidated `StakingAmount` rounds to 0 (staking contract balance < 1 KAIA after integer division).
3. The proposer has a non-nil `CLStakingInfo` (registered in the CL registry).
4. The proposer's `CLStakingAmount` rounds to 0 (CL pool balance < 1 KAIA after integer division).

Conditions 2 and 4 can arise naturally: a validator that has withdrawn nearly all stake from both its staking contract and its CL pool, but whose removal from the validator set has not yet propagated (staking info is snapshotted at a fixed interval). Condition 3 is a deliberate registration step. No external attacker action is required beyond the validator's own on-chain state.

---

### Recommendation

Add a zero-total guard inside `Split()` before the division:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    cnAmountBig := big.NewInt(int64(c.StakingAmount))
    clAmountBig := big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)

    // Guard: if both amounts are zero, all reward goes to the CN address.
    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0)
    }

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)
    cnAmount := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

This matches the pattern used in the external report's recommended fix (`if (baseAmount == 0) continue;`) — skip the problematic division when the denominator is zero.

### Proof of Concept

```
State setup (Prague hardfork active, deferred-fee mode):
  - Validator V is in the AddressBook with StakingContract balance = 0.5 KAIA
    → StakingAmount = Div(0.5e18, 1e18) = 0
  - V is registered in the CL registry with CLPool balance = 0.3 KAIA
    → CLStakingAmount = Div(0.3e18, 1e18) = 0
  - CLStakingInfo for V is non-nil (registry entry exists)
  - V is selected as proposer for block N

Block N finalization:
  FinalizeState()
    → GetDeferredReward()
      → getDeferredRewardFull()
        → getDeferredRewardFullKore()   (or Flex variant)
          → specWithProposerAndFunds()
            cns = si.ConsolidatedNodes()
            // cn for V: StakingAmount=0, CLStakingInfo≠nil, CLStakingAmount=0
            cn.Split(proposer)
              totalAmount = 0 + 0 = 0
              clAmount.Div(clAmount, totalAmount)  ← integer division by zero → PANIC
```

Node crashes; other validators continue finalizing blocks → consensus divergence.
