### Title
Unscoped `status` webhook lets any repository flip the CI state of an identical-SHA commit belonging to another repository's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit with a bare `Commit.where(sha: params.sha)` lookup, unlike every other handler (`PushHandler`, `CheckSuiteHandler`) which scope commits/stacks through the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)`). Because the webhook's HMAC signature is only bound to an organization (via `repository_owner`), and the commit lookup is never bound to `payload['repository']['full_name']`, a validly signed `status` event from one repository can mutate `Commit` rows sharing the same 40-character SHA in a completely different repository/stack.

### Finding Description
The broken binding: the code implicitly assumes `commit.sha == params.sha` implies `commit.stack.repository == payload['repository']`, i.e. `Commit.where(sha: params.sha).stack.repository.full_name == payload.dig('repository','full_name')`. This equality is never enforced.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-31) verifies the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository','owner','login')`. This only proves the request came from *some* repository under that GitHub organization/App installation - it proves nothing about which specific repository or commit SHA is legitimate.
- The base `Handler` class exposes a properly-scoped helper: `stacks` → `Repository.from_github_repo_name(repository_name)&.stacks` (app/models/shipit/webhooks/handlers/handler.rb:32-38), and `PushHandler#process` uses exactly this scoping (`stacks.not_archived.where(branch:)`) (app/models/shipit/webhooks/handlers/push_handler.rb:12-17).
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - it never calls `stacks`, never reads `repository_name`, and applies the status to every `Commit` row in the database with that SHA, regardless of which stack/repository it belongs to.

Exploit flow: an attacker who owns/controls a repository (with the Shipit GitHub App/webhook installed, e.g. under an org where they have at least one onboarded stack) triggers or fabricates a `status` event with `sha` equal to a victim commit's SHA (identical SHAs commonly occur across forks, cherry-picked/rebased-but-identical commits, or mirrored repos that share history) and `state: failure`. The webhook is signed with the attacker's own organization's valid secret and passes `verify_signature`. `StatusHandler` then updates `Commit#create_status_from_github!` for the matching row in the victim's unrelated stack, flipping `Commit#success?`/`Commit#blocked?`, which changes `Commit#deployable?` (`success? && !blocked?`) for a stack the attacker does not own and never authenticated for.

None of the existing guards stop this: `verify_signature` checks organization-level signing only; `drop_unhandled_event`/`check_if_ping` are unrelated; the `ExplicitParameters` schema only validates types/presence of `sha`/`state`, not ownership; there is no `require_permission!`/`stacks` scoping check in this handler, unlike `PushHandler`.

### Impact Explanation
An attacker can flip CI status (`success`/`failure`) on any commit row that shares its SHA with a commit under a stack they don't control, changing `Commit#deployable?`/`blocked?` for that unrelated stack. This can block a victim's legitimate green commit (denial-of-deploy / blocking a rollback) or, conversely, mark a bad commit as `success` to make it `deployable?` on the victim stack, enabling downstream unauthorized deploy actions gated on `deployable?`. This is a cross-tenant/cross-repository write via an unauthenticated-for-that-repository webhook, matching "a payload for one repository mutating another's stack/commit" — Critical.

### Likelihood Explanation
The attacker needs: (1) control of some repository with Shipit's GitHub App/webhook installed under an organization Shipit recognizes (so `verify_signature` passes with that org's real secret via genuine GitHub delivery, no secret knowledge needed), and (2) a commit SHA collision with the victim's commit. SHA collisions are not exotic here — they occur naturally via forks, mirrors, or shared history before divergence, which is common in real-world GitHub organizations using Shipit across multiple related repos/forks. No Shipit secrets, session, or API token are required; the request path (`POST /webhooks`) is fully unauthenticated for the actual mutation, only the signature-organization binding is checked, which the root cause bypasses.

### Recommendation
Scope `StatusHandler#process` through the same repository binding used elsewhere: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and restrict the `Commit` lookup to `Commit.where(sha: params.sha, stack_id: stacks... )` (or join through `Commit#stack.repository`) so a status event can only affect commits belonging to the repository that actually produced the event.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is under `test/` and out-of-scope for delivery but described for validation):
1. Create `repo_a = Repository.create!(...)`, `stack_a = Stack.create!(repository: repo_a, ...)`, `commit_a = Commit.create!(stack: stack_a, sha: SHARED_SHA, state: 'success')`.
2. Create `repo_b = Repository.create!(...)` (different, "victim") org/repo, `stack_b = Stack.create!(repository: repo_b, ...)`, `commit_b = Commit.create!(stack: stack_b, sha: SHARED_SHA, state: 'success')`.
3. Assert precondition: `commit_b.deployable?` is `true`, `commit_b.reload.state == 'success'`.
4. Build a `status` payload with `repository.full_name = repo_a.full_name`, `sha: SHARED_SHA`, `state: 'failure'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert: `commit_b.reload.state == 'failure'` and `commit_b.deployable? == false` — proving repo A's webhook mutated repo B's commit/stack it never authenticated for, while `commit_a` (the legitimately-owned commit) also changed as expected.
