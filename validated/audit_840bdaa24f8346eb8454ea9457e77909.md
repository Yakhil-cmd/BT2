### Title
Untrusted `.gitmodules` submodule content can permanently block worktree publishing, causing persistent sync denial - (File: main.go)

### Summary
`repoSync.configureWorktree` bundles multiple independent preparation steps — writing the `.git` file, sparse-checkout setup, hard reset, and submodule initialization — into a single all-or-nothing operation before the new worktree is atomically published via the symlink. A failure in any one step, most notably `git submodule update --init --recursive` (driven entirely by attacker-controlled `.gitmodules`/submodule content in the synced repository), aborts the entire publish for that revision. This is structurally the same defect class as the TOKE report: a valid, independently obtainable result (the up-to-date main repository content and, in TOKE's case, the extra reward) is blocked and made permanently unattainable because it is bundled with a sub-operation that reverts/fails.

### Finding Description
`SyncRepo` performs, in order: fetch, `createWorktree` (creates the new worktree on disk), then unconditionally calls `configureWorktree`, and only if that succeeds does it call `syncHooks.beforePublish` and `publishSymlink` to atomically flip the consumer-facing link [1](#0-0) .

`configureWorktree` runs `git submodule update --init [--recursive]` as an unconditional final step of preparing every new worktree whenever `--submodules` is not `off` (the default is `recursive`) [2](#0-1) . If that git invocation fails — e.g., because a submodule in the synced repository points to an unreachable host, a private repository without credentials configured for git-sync, a deleted/rewritten ref, or any other error — `configureWorktree` returns the error immediately, and `SyncRepo` returns without ever calling `publishSymlink` [3](#0-2) .

Because `.gitmodules` and submodule references are ordinary tracked content in the synced repository, an attacker able to introduce a single new commit (via a merged PR, a compromised/synced branch, or any push access to the source repo) can add or alter a submodule entry to guarantee this failure. On the next sync loop iteration, git-sync will fetch the new (otherwise perfectly valid) commit, attempt to build a fresh worktree, fail at the submodule step, and give up on publishing — over and over, indefinitely, since the same broken submodule reference will be fetched and retried every period [4](#0-3) . Unless `--max-failures` is configured to a small bound (causing the whole process to exit), the sidecar is stuck perpetually retrying the same failing sync while consumers keep serving the last-good stale content, since the symlink is never updated to point at the new worktree.

This mirrors the TOKE bug precisely: a legitimately obtainable result (extra DAI rewards / here, the latest valid repo content) is entangled with an unrelated all-or-nothing sub-step (staking below `MIN_STAKE_AMOUNT` / here, submodule initialization) whose failure is fully attacker-controllable and permanently prevents the otherwise-successful operation from completing.

### Impact Explanation
This matches the accepted "persistent sync denial" impact category: once an attacker-influenced commit with a broken/unreachable submodule reference becomes the new upstream ref (branch HEAD or tag target being tracked), `git-sync` can never advance past that point. The publish step never runs, so the symlink permanently references stale content, and every subsequent sync attempt repeats the identical failure. This effectively pins the deployment at an old revision until an operator manually intervenes (e.g., reverts the offending commit, changes `--submodules=off`, or fixes credentials for the submodule host) — a denial of the tool's core function of continuously syncing to the latest commit.

### Likelihood Explanation
Likelihood depends on the threat model of the git-sync deployment: any actor with push/merge access to the tracked repository (or ability to get a PR merged onto the tracked branch) can trigger this deterministically and at will by adding a `.gitmodules` entry referencing an unreachable or credential-gated repository. Submodule support is enabled by default (`--submodules=recursive`), so no special operator misconfiguration is required to be exposed. The rules exclude malicious-operator scenarios, but this scenario is reachable purely from untrusted repository *content* pushed by anyone with write access to the synced ref/branch — consistent with the "untrusted repo content, ref names, submodules" scope explicitly called out.

### Recommendation
- Make worktree preparation resilient to partial-step failure: if submodule initialization fails, do not discard the otherwise-valid top-level checkout; either (a) publish the top-level content without the failing submodule and surface a clear warning/metric, or (b) fall back to the last successfully-configured worktree instead of looping forever on the same broken commit.
- Consider adding a configurable policy (e.g., `--submodule-failure-policy=fail|skip|best-effort`) so operators can choose whether submodule errors should block publishing or only degrade it.
- Emit a distinct, actionable metric/log event (already partially present via `log.Error(err, "error syncing repo, will retry", ...)`) specifically identifying "submodule update failed" so operators can detect this stuck state quickly, and document this failure mode (as is already partially done for `--stale-worktree-timeout`) so operators understand the risk of `--submodules=recursive` on untrusted/externally-writable repositories.

### Proof of Concept
1. Deploy `git-sync` against a repository the attacker can push/merge to, with default settings (`--submodules` unset → `recursive`).
2. Attacker commits a `.gitmodules` entry (or modifies an existing submodule's URL) pointing to a host that will reliably fail, e.g. an unreachable IP, a private repo requiring auth not provisioned to git-sync, or `ext::` transport pointing to a non-existent binary: `git submodule add https://unreachable.invalid/nope.git sub && git commit -am "break submodule"`.
3. git-sync's next sync loop fetches the new commit (`remoteHash` changes), calls `createWorktree` successfully, then `configureWorktree` fails at `git submodule update --init --recursive` [5](#0-4) .
4. `SyncRepo` returns the error before reaching `publishSymlink`; the symlink under `--link` still points at the old worktree/commit [6](#0-5) .
5. Every subsequent period, the identical fetch/create/fail sequence repeats (visible via repeated "error syncing repo, will retry" log lines) [4](#0-3) , and the consumer-visible content under `--link` never advances past the pre-attack commit — a persistent, attacker-triggerable sync denial.
