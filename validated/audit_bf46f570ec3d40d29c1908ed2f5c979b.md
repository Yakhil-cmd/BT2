### Title
Cross-organization webhook forgery via ambiguous `repository_owner` fallback allows an authenticated GitHub org to trigger syncs/deploys on another org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to verify a webhook against using `repository_owner`, which is derived from the *attacker-controlled* JSON body via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Event handlers such as `PushHandler`, however, determine which `Stack`/`Repository` to act on using an entirely different field: `payload.dig('repository', 'full_name')`. Because the attacker fully controls the raw JSON body (only the HMAC over the whole body is checked), these two fields can be made to point at different organizations, breaking the binding "organization whose secret authenticated the request == repository the handler acts on."

Because an attacker only needs to omit `repository.owner.login` (or omit the `repository.owner` object) from the raw body while including a top-level `organization.login` equal to an org whose secret they know, `verify_signature` authenticates the request as "OrgA" while `PushHandler` (or `StatusHandler`/`CheckSuiteHandler`, which use the same `repository_name` helper) acts on `repository.full_name = "OrgB/victim-repo"`. This breaks the equality: `organization that authenticated == repository that is written`.

### Impact Explanation
An attacker who legitimately administers (and therefore knows the `webhook_secret` of) any one GitHub organization configured on a shared, multi-org Shipit instance can forge a `push` webhook that is verified against their own org's secret but is processed as if it originated from a completely different organization's repository. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on that unrelated stack, which triggers a `GithubSyncJob` to sync new commits and can lead to an unauthorized deploy on stacks configured for continuous delivery — a cross-tenant/cross-repository write and potential unauthorized deploy, matching the "Critical: cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires only that the attacker knows the `webhook_secret` of at least one organization already configured on the shared Shipit instance — a credential every legitimate tenant of a multi-org Shipit deployment already possesses for their own org, per the documented multi-org config schema in `docs/setup.md` and `secrets_double_github_app.yml`. Crafting the ambiguous payload (omitting `repository.owner.login`, setting `organization.login` and `repository.full_name` independently) requires no other privilege, since `WebhooksController#create` parses `request.raw_post` directly with no additional structural validation before signature verification.

### Recommendation
Derive the organization used for signature verification from the same trusted field the handlers use to resolve the target repository (i.e., always use `repository.full_name`'s owner segment, never a separate top-level `organization.login` fallback), or otherwise cross-validate that the verified organization matches the owner of `repository.full_name` before dispatching to handlers. At minimum, reject webhooks where `repository.owner.login` is absent while `repository.full_name` is present, and stop treating `organization.login` as an equivalent substitute for `repository.owner.login`.

### Proof of Concept
1. Attacker administers `OrgA` on a shared multi-org Shipit instance and knows `OrgA`'s `webhook_secret` (legitimately configured for their own installation).
2. Attacker crafts a JSON body:
```json
{
  "organization": {"login": "OrgA"},
  "repository": {"full_name": "OrgB/victim-repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and sends `POST /webhooks` with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `nil` for `repository.owner.login` and falls back to `organization.login` = `"OrgA"`; `verify_signature` selects `OrgA`'s `GitHubApp`/secret and the signature verifies successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` from `repository.full_name` = `"OrgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — a repository entirely unrelated to the organization that authenticated the request.
