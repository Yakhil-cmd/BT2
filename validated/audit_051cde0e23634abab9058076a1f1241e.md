### Title
Webhook signature verification is bound to `repository.owner.login`, but handlers act on `repository.full_name` / no repository check at all, allowing cross-organization/cross-repository forged webhook events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the same "same heartbeat for multiple feeds" class of bug: a single verified field is reused to authorize actions on a different, unverified target. `WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, then verifies the signature with that org's secret. Once verification succeeds, the event handlers act on a **different** field of the same attacker-controlled payload — `repository.full_name` — to decide which `Stack`/`Repository` to mutate, and in the case of commit statuses, don't check the repository at all.

### Finding Description
`verify_signature` picks the `GitHubApp` (and its `webhook_secret`) using `repository_owner`: [1](#0-0) [2](#0-1) 

This equality is assumed but never enforced: `verified-org-secret(repository.owner.login) == secret-that-signed(payload)`. Nothing ties `repository.owner.login` to the field the handlers actually use to select the target: `repository.full_name`, read by the shared `Handler` base class: [3](#0-2) 

Because `repository.owner.login` and `repository.full_name` are both attacker-supplied JSON fields inside the *same* HMAC-signed body, an attacker who legitimately controls one organization's webhook secret (e.g., because they installed their own GitHub App on their own org and configured it in Shipit's multi-org `github:` secrets, as shown in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`) can self-sign a payload where:
- `repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` resolves to their own app and their own `webhook_secret`, making `verify_webhook_signature` pass), while
- `repository.full_name` = a victim org/repo string that does not match `repository.owner.login`.

`PushHandler` and `CheckSuiteHandler` then resolve the target stack purely from `repository.full_name` via `Handler#stacks`/`#repository_name`, with no cross-check against the org that actually authenticated: [4](#0-3) [5](#0-4) 

`StatusHandler` is worse: it doesn't use the repository at all, it matches purely on commit SHA across the entire installation: [6](#0-5) 

So an attacker who can pass signature verification for *any* configured organization can inject an arbitrary fake commit status (`state`, `context`, `description`, `target_url`) for any commit SHA belonging to any other stack in the Shipit instance, entirely independent of `repository_owner`.

### Impact Explanation
Commit statuses drive Shipit's merge-queue and continuous-deployment gating (`Stack#deployment_checks_passed?`, `MergeRequest::StatusChecker`). Forging a passing status (e.g., `context: "ci/required-check", state: "success"`) for a victim repository's commit — using credentials that only authenticate the attacker's own, unrelated org/app — can cause Shipit to consider unrelated CI checks satisfied, unblocking automatic merges/deploys of a commit the attacker does not control. This crosses the "authorized organization vs. repository actually written" trust boundary described in the analog: an unprivileged attacker (with control of only their own org's webhook secret) can influence deploy/merge state of a repository/organization they have no access to.

### Likelihood Explanation
Requires the operator to run Shipit in the "Using Multiple GitHub Applications" mode (documented and supported, see `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github_app_config`), where the attacker legitimately owns one of the configured orgs/apps and thus its `webhook_secret`. Given that, forging the payload is trivial (attacker fully controls their own webhook delivery and its raw body/signature). No Shipit session, API token, or GitHub write access to the victim repo is needed.

### Recommendation
Bind the verified organization to the field actually used to route/act on the event: after signature verification, assert that `repository.owner.login` (the org whose secret verified the request) matches the owner encoded in `repository.full_name`, and reject the webhook otherwise. Additionally, `StatusHandler` should filter `Commit.where(sha: ...)` by the verified repository/stack rather than matching globally by SHA.

### Proof of Concept
1. Configure Shipit with two GitHub orgs in `secrets.github`: `attacker-org` (attacker's own installed app, secret known to attacker) and `victim-org` (has a `Stack` tracking `victim-org/victim-repo` with a pending commit `abc123`).
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook JSON body:
   ```json
   {
     "sha": "abc123",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using the attacker's own secret.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")` (no org/repo filter) and creates a forged "success" status on the victim's commit, potentially satisfying merge-queue/CI requirements it never actually met.
