### Title
Webhook signature verification binds trust to `repository.owner.login`, but every event handler acts on unrelated, unverified fields (`repository.full_name`, `commit.sha`) — cross-organization forgery of commit statuses and sync triggers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (falling back to `organization.login`), but none of the `Shipit::Webhooks::Handlers` ever check that this same field matches the repository/commit they actually act upon. This is the same class of bug as the report's `selfdestruct()` issue: a value that is authenticated (`repository_owner`) is not the same value that is acted upon (`repository.full_name`, `sha`), breaking a trust binding that the rest of the code implicitly assumes holds.

### Finding Description
`verify_signature` computes:
```
repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) [2](#0-1) 

This only proves the raw body was signed with the secret configured for *whatever organization `repository.owner.login` claims to be*. Shipit explicitly supports multiple, independently configured GitHub Apps/organizations, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), so an attacker who administers/controls one organization's GitHub App (and thus legitimately knows that org's `webhook_secret`) can freely construct **any** JSON body, set `repository.owner.login` to their own org (so the signature check passes with their own secret), and set every other field to whatever they want.

Downstream, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target repository from a completely different, unverified field:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and `StatusHandler#process` resolves target commits globally by `sha`, with **no repository scoping at all**:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

So the equality the system needs to hold — `repository_owner (authenticated) == owner(repository.full_name / commit’s stack) (acted upon)` — is never checked. An attacker who owns org "AttackerOrg" (and thus its `webhook_secret`) can sign a payload claiming `repository.owner.login = "AttackerOrg"` while setting `sha` to the SHA of a commit belonging to a totally different organization's stack, or claiming `repository.full_name = "VictimOrg/victim-repo"` in `PushHandler`, and the signature check will pass.

### Impact Explanation
Via `StatusHandler`, the attacker can forge an arbitrary commit status (e.g., `state: success`, forged CI context) for any commit `sha` that exists anywhere in the Shipit database — not limited to their own organization's repositories — because `Commit.where(sha: params.sha)` is global and unscoped by repository/organization. `Commit#deployable?` and `Commit#status` are driven directly by these statuses [5](#0-4) , and `Commit#schedule_continuous_delivery` can trigger `ContinuousDeliveryJob` once a forged "success" status lands and the stack is `continuous_deployment?` [6](#0-5) . This can cause an unauthorized deploy by satisfying CI requirements that were never actually met on GitHub, which matches the "unauthorized deploy" Critical impact criterion. Additionally, `PushHandler` can be made to enqueue `GithubSyncJob` for an arbitrary victim stack by lying about `repository.full_name` [7](#0-6) .

### Likelihood Explanation
Requires the attacker to control one legitimate GitHub App/org's `webhook_secret` configured in the same Shipit installation (an "unprivileged" party relative to other tenants' repositories, but a privileged party for their own — realistic in the documented multi-org deployment model shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`). No GitHub write access, Shipit session, or `ApiClient` token to the victim org/repo is needed — only the ability to send an HTTP POST to `/github/webhooks` with a self-crafted, self-signed payload.

### Recommendation
After verifying the signature, cross-check that the organization used to select the `webhook_secret` (`repository_owner`) actually matches the owner implied by every field the handler will act on (`repository.full_name`'s owner segment for `PushHandler`, and constrain `StatusHandler`'s `Commit` lookup to commits belonging to stacks whose repository owner equals the verified `repository_owner`). Reject the webhook if these do not match.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md` / `secrets.yml`) with two orgs, `AttackerOrg` (secret `S_A`) and `VictimOrg` (secret `S_V`), each with their own GitHub App installed, both feeding the same Shipit instance (this is the documented multi-tenant pattern).
2. The attacker is a legitimate admin of `AttackerOrg`'s GitHub App and therefore knows `S_A`.
3. Attacker crafts body:
```json
{
  "sha": "<victim-commit-sha-in-VictimOrg-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` and POSTs to `WebhooksController#create` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and the HMAC check passes because the attacker legitimately knows `S_A`.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — unscoped by organization — and creates a forged "success" status on the victim's commit, potentially satisfying `stack.ignore_ci?`/CI requirements for `VictimOrg`'s stack and enabling deploy/merge actions that never legitimately passed CI.
