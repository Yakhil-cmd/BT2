### Title
`remote_proxy`/`remote_proxy_with_registered_proof` charge a fixed weight independent of proof size, allowing cheap adversarial trie-proof hashing to under-charge PoV/time cost - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`Pallet::do_remote_proxy` accepts an unbounded `RemoteProxyProof::RelayChain { proof: Vec<Vec<u8>>, block }` and feeds it straight into `sp_trie::StorageProof::new(proof).into_memory_db()` / `sp_trie::read_trie_value`, but the declared `#[pallet::weight]` for `remote_proxy` is a fixed constant benchmarked against a tiny realistic proof, not parameterized by `proof` length or total byte size. An attacker can submit a large, syntactically valid but bogus proof (up to the normal extrinsic length limit) that forces the node to hash the entire proof payload while being charged only the small fixed weight.

### Finding Description
`do_remote_proxy` takes the raw, unbounded `proof: Vec<Vec<u8>>` from the extrinsic and immediately does: [1](#0-0) 

`sp_trie::StorageProof::new(proof).into_memory_db::<RemoteHasherOf<T, I>>()` hashes **every** node in the supplied `Vec<Vec<u8>>` to build the lookup table, and this cost is linear in the total byte size of `proof` regardless of whether the proof is a valid Merkle path to `storage_root`. Only after this O(total proof bytes) hashing pass does `read_trie_value` attempt an actual trie walk (which fails fast with `InvalidProof`/`IncompleteDatabase` once the root or a required node is missing). There is no size check, no `BoundedVec` wrapper, and no `MaxEncodedLen`-style cap on `proof` inside the pallet before this hashing occurs.

The declared weight for the extrinsic is: [2](#0-1) 

`WeightInfoOf::<T, I>::remote_proxy()` is a **fixed** constant, generated from a benchmark that uses `T::RemoteProxy::create_remote_proxy_proof`, i.e. a small, realistic proof: [3](#0-2) 

The generated weight confirms this — proof size and execution time are both fixed constants (`Measured: 105`, `Estimated: 1846`), with no size-scaling component: [4](#0-3) 

Because `proof` is not bounded by any pallet-level `MaxEncodedLen`/`BoundedVec` constraint, only the outer extrinsic-length limits (`frame_system::limits::BlockLength`'s "normal" class ratio) constrain its size — which is typically megabytes, far larger than the ~1.8KB the weight formula assumes. `register_remote_proxy_proof` / `remote_proxy_with_registered_proof` have the same structural issue since they consume the same `RemoteProxyProof` type and route through `do_remote_proxy`.

### Impact Explanation
An attacker can submit `remote_proxy` (or `register_remote_proxy_proof` + `remote_proxy_with_registered_proof`) extrinsics with a large, syntactically valid `RemoteProxyProof::RelayChain` whose `proof` field is filled with maximal-length bogus byte vectors targeting a real, known `block` in `BlockToRoot`. Each such extrinsic is charged only the small fixed weight (`~18_259_000` ps + 1846 proof-size units) while the node actually performs hashing work proportional to the full proof payload (potentially megabytes) before returning `Error::InvalidProof`. Because the block-authoring/weight-limiting logic uses the declared (fixed, small) weight to decide how many such extrinsics fit in a block, an attacker can pack many of these calls into a block, causing real CPU/hashing time spent by block builders and importing nodes to be disproportionate to the weight consumed — a block-level resource-accounting mismatch that can crowd out other extrinsics/slow down block production and import.

### Likelihood Explanation
Feasible for any signed account: `remote_proxy` only requires `ensure_signed(origin)` and a `real` account plus a `block` value present in `BlockToRoot` (block/root pairs are public, continuously updated on-chain state). No proxy relationship or privileged access is required to trigger the expensive path — the proof is checked only after the costly hashing. The attack is trivially repeatable across blocks and scales with how much "normal" extrinsic length budget the runtime allows.

### Recommendation
Bound `proof: Vec<Vec<u8>>` (e.g. total node count and/or total byte size) at the pallet level via a `BoundedVec`/explicit `ensure!` size check before constructing the `MemoryDB`, and make the declared `#[pallet::weight]` for `remote_proxy`/`remote_proxy_with_registered_proof`/`register_remote_proxy_proof` scale with the actual/maximum allowed proof size (parameterize the benchmark on proof length, similar to how `frame_support` benchmarks size-dependent extrinsics), so PoV/time weight charged reflects worst-case hashing cost of `into_memory_db`.

### Proof of Concept
Rust benchmark/integration-test plan:
1. In `pallets/remote-proxy/src/benchmarking.rs`, add a worst-case variant of `remote_proxy` benchmark that builds `proof: Vec<Vec<u8>>` filled with the maximum number/size of byte vectors allowed by the runtime's extrinsic length limit, targeting a valid `block` in `BlockToRoot`, but not a valid Merkle path (i.e. random bytes hashing to unrelated values).
2. Assert that `Pallet::do_remote_proxy` returns `Error::InvalidProof` (so no useful work performed) while measuring actual execution time via `frame_benchmarking`.
3. Compare measured worst-case weight/time against `WeightInfoOf::<T,I>::remote_proxy()` (the currently generated fixed constant) — assert `measured_worst_case_weight > declared_weight * tolerance`, proving the fixed weight under-charges the worst-case adversarial proof.
4. Optionally add an integration test that submits N such extrinsics in one block via `pallet_transaction_payment`/`frame_system::Executive` and measures wall-clock import time vs. declared total weight consumed, asserting the ratio exceeds an acceptable bound.
