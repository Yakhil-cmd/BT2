### Title
Webhook signature verification authenticates `repository.owner.login`, but handlers act on the independently-controlled `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or the `organization` sub-object) [1](#0-0) . However, the actual event handlers (`PushHandler`, `StatusHandler`, etc.) resolve the target `Repository`/`Stack` using a *different* field, `payload.dig('repository', 'full_name')` [2](#0-1) . Because these two fields are independent JSON keys in the same attacker-controlled payload, and only `repository.owner.login` is bound to the signature check, an organization that successfully authenticates (owns a valid `webhook_secret` for its own installation) can forge a payload whose `repository.full_name` points at a completely different, victim-owned repository/stack.

### Finding Description
`verify_signature` picks the `github_app` (and thus the `webhook_secret` used for HMAC verification) via:
```ruby
github_app = Shipit.github(organization: repository_owner)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

This proves only that the request was signed by the app installed for `repository.owner.login`'s organization — i.e., it verifies "this org's app sent this payload," not "this payload legitimately concerns a repo owned by this org."

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full, attacker-controlled JSON to handlers [4](#0-3) . Handlers such as `PushHandler` resolve the affected `Stack`s via `stacks`, which calls `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [2](#0-1) , and `Repository.from_github_repo_name` does a straight `find_by(owner:, name:)` lookup with no cross-check against `repository_owner` used for signing [5](#0-4) .

The equality that should hold is:
`verified_signing_organization (repository.owner.login) == repository actually mutated (repository.full_name's owner)`

This is broken because `repository.owner.login` and `repository.full_name` are two separate, attacker-supplied keys in the same JSON body; nothing forces them to agree, and only the former is covered by the HMAC. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack, resynchronizing/re-triggering continuous deployment logic for a repository the attacker's organization does not own [6](#0-5) . `StatusHandler#process` similarly updates commit statuses matched purely by `sha` across the whole `Commit` table, independent of which organization is nominally "authenticated" [7](#0-6) .

### Impact Explanation
This crosses a genuine trust boundary: an entity that controls (or is granted) a legitimate GitHub App installation for *its own* organization/repository can forge webhook events that are treated as authentic for a *different* organization's stacks in the same Shipit instance (a realistic scenario, since Shipit explicitly supports multi-organization configuration per `config/secrets.development.shopify.yml` and `docs/setup.md`). This enables cross-repository writes: forged `push` events cause `sync_github`/continuous-delivery triggers on victim stacks, and forged `status`/`check_suite`/`commit_status` events manipulate CI state (`create_status_from_github!`) that gates deploy eligibility for a repository the attacker does not control. This matches the Critical-tier "cross-repository writes" / "unauthorized deploy" impact class, since forged CI-green statuses or push events can influence whether a victim stack's continuous deployment fires.

### Likelihood Explanation
Likelihood is High in any deployment where Shipit is configured with multiple GitHub organizations (explicitly documented/supported), since the only requirement is that the attacker controls one legitimate, low-privilege GitHub App installation on the same Shipit instance — no elevated GitHub or Shipit privileges on the victim repo are needed. The signature check passes normally because it validates against the attacker's own correctly-configured `webhook_secret`; the mismatch is only exploitable via the free-form JSON fields the handler layer trusts afterward.

### Recommendation
After computing `repository_owner` for signature verification, re-derive it consistently and enforce that the resolved `Repository` used by handlers belongs to that same verified organization/owner — e.g., pass the already-authenticated `repository_owner` (or the whole verified `repository` object) into `Handler.call`, and have `Repository.from_github_repo_name`/`stacks` reject or ignore payloads whose `full_name` owner does not match the organization that produced a valid signature.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (attacker controls the GitHub App/`webhook_secret`) and `victim-org` (has a tracked `Stack` for `victim-org/victim-repo`).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push`, signing the body with `attacker-org`'s `webhook_secret`, but with payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies the HMAC against `attacker-org`'s secret — passes [8](#0-7) .
4. `PushHandler#stacks` resolves via `full_name` = `"victim-org/victim-repo"`, matches the real victim `Stack`, and calls `sync_github(expected_head_sha: <attacker-chosen-sha>)` on it — a cross-organization write triggered purely by an attacker-controlled installation the victim never authorized [2](#0-1) [6](#0-5) .

      verified = github_app.verify_webhook_signature(

      head(422) unless verified
