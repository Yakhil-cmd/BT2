### Title
Pre-publish exec-hook does not gate symlink publication — malicious content is published before/regardless of hook validation result - (File: main.go)

### Summary
The ERC777 issue in the referenced report stems from a "hook" callback that fires during a critical state-changing operation without the calling code waiting for or checking the outcome of that callback, allowing an attacker to slip malicious effects in "for free" while the rest of the code proceeds as if nothing happened. `git-sync` has a directly analogous pattern in its `--pre-publish-exechook-command` feature: the `beforePublish` callback is documented as running *before* the atomic symlink flip so it can act as a gate (e.g. to scan/verify new content before it becomes visible to consumers), but the implementation only *asynchronously enqueues* the hook and unconditionally proceeds to publish the symlink.

### Finding Description
In the sync loop, `syncHooks.beforePublish` is defined as: [1](#0-0) 

Note that `beforePublish` calls `prePubExechookRunner.Send(hash)` — which only pushes the hash onto an internal channel consumed by a separate goroutine — and then immediately `return nil`, regardless of whether the actual hook command has even started, let alone completed or succeeded.

`SyncRepo` calls this callback and, on receiving `nil`, proceeds straight to `publishSymlink` without waiting for or checking any result from the exec hook: [2](#0-1) 

The hook itself executes later, in its own goroutine, against the same worktree path (attacker-controlled repo content) that is about to be (or already has been) published: [3](#0-2) [4](#0-3) 

The only place the hook's actual success/failure is checked is in `--one-time` mode, via `WaitForCompletion()`, and that check happens *after* the entire sync (including the symlink publish) has already completed — it only affects the process's final exit code, not whether the symlink was published: [5](#0-4) 

In steady-state (non `--one-time`) mode there is no wait or result-check at all — `beforePublish` is pure fire-and-forget.

### Impact Explanation
Operators use `--pre-publish-exechook-command` under the reasonable assumption (reinforced by its name and the code comment "we must call the pre-publish hook... before we [publish]") that it acts as a synchronous gate: if the hook fails, the new content should not become visible via the symlink contract. In reality, an attacker who controls commits on the synced ref (the standard threat model for git-sync, analogous to the "attacker-pushed commit" surface in this bug bounty) will have their content published to the consumer-facing symlink regardless of the pre-publish hook's outcome, because `publishSymlink` runs unconditionally right after the hook is merely *queued*. This falls into the "publishing wrong or partial content" impact category: a validation/gating mechanism that operators rely on to prevent unsafe or malicious repo content from reaching consumers can be silently bypassed by a race between the async hook goroutine and the main sync loop.

### Likelihood Explanation
No special privileges beyond normal push access to the synced git ref are required — this is the baseline attacker model for any git-sync deployment. The race is deterministic in the sense that `publishSymlink` is called immediately in the same function without any synchronization primitive tying it to hook completion, so the bypass is not merely theoretical timing luck for the *first* sync after enabling the flag, but happens on essentially every sync of a changed hash. This requires the operator to have configured `--pre-publish-exechook-command` and to be relying on it as a security gate (rather than purely as a notification), which narrows applicability but does not require any other flag or misconfiguration.

### Recommendation
Make `beforePublish` block on the pre-publish exec hook's actual result before calling `publishSymlink`, and propagate hook failure as a sync error (aborting the publish for that hash) instead of only using the result to set the process exit code in `--one-time` mode. Concretely, `HookRunner` should expose a synchronous "run and wait" call usable from `beforePublish`, or `SyncRepo` should call `WaitForCompletion` (or an equivalent per-hash wait) immediately after `Send` and before `publishSymlink`, propagating any error so it is treated the same as other pre-publish failures in `SyncRepo`.

### Proof of Concept
1. Configure `git-sync` with `--pre-publish-exechook-command=/scan.sh` where `/scan.sh` is meant to validate the newly fetched worktree (e.g., scan for malware/secrets) and exit non-zero on failure.
2. As an attacker with push access to the synced ref, push a commit containing malicious content designed to fail the scan.
3. `git-sync` fetches the new hash, creates the worktree, and calls `beforePublish(hash)`, which only enqueues the hash via `prePubExechookRunner.Send(hash)` and returns `nil` immediately: [6](#0-5) .
4. `SyncRepo` proceeds directly to `git.publishSymlink(newWorktree)`, making the malicious content live via the symlink contract before (or regardless of whether) `/scan.sh` has even started executing: [7](#0-6) .
5. In steady-state mode, there is no later check at all of the hook's result relative to the publish decision, so the malicious content remains published even if `/scan.sh` subsequently fails and is retried per `--pre-publish-exechook-backoff`.

// Run waits for trigger events from the channel, and run hook when triggered.
func (r *HookRunner) Run(ctx context.Context) {
	var lastHash string

	// Wait for trigger from hookData.Send
	for range r.data.events() {
		// Retry in case of error
		for {
			// Always get the latest value, in case we fail-and-retry and the
			// value changed in the meantime.  This means that we might not send
			// every single hash.
			hash := r.data.get()
			if hash == lastHash {
				break
			}

			if err := r.hook.Do(ctx, hash); err != nil {
				r.log.Error(err, "hook failed", "hash", hash, "retry", r.backoff)
				updateHookRunCountMetric(r.hook.Name(), "error")
				// don't want to sleep unnecessarily terminating anyways
				r.sendOneTimeResultAndTerminate(false)
				time.Sleep(r.backoff)
			} else {
				updateHookRunCountMetric(r.hook.Name(), "success")
				lastHash = hash
				r.sendOneTimeResultAndTerminate(true)
				break
			}
		}
	}
