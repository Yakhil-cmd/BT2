### Title
`unstake-sbtc` only zeroes the *current* bond's per-cycle shares, letting a rolled-over staker still claim rewards for the old bond's still-open cycle after the backing sBTC has fully left custody - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond`'s roll-over path intentionally leaves the old bond's per-cycle share entries (`staker-shares-staked-for-cycle`/`signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle` keyed by the OLD `bond-index`) untouched, relying on the fact that the physical sBTC is still custodied under the new bond. `unstake-sbtc` then removes that same physical sBTC from the contract but only mutates cycle entries keyed by the CURRENT (new) `bond-index`, never reaching the old bond's still-open cycle, so that cycle's reward claim becomes fully unbacked.

### Finding Description
The equality that must hold is: sum of sBTC rewards paid across all (bond-index, cycle) entries backed by a staker's coin ≤ the physical sBTC actually held by the contract for that staker at any settlement time. `register-for-bond`'s roll-over comment states explicitly: "A roll-over from an ending bond ADDS the new bond's shares but does NOT tear down the old bond's per-cycle shares/delegation" [1](#0-0) . This is by design because a same-amount roll performs "no net transfer" via `roll-sbtc`, so the physical coin is presumed to remain in custody for the old bond's remaining cycle(s) — confirmed by the test asserting `getStakerSharesStakedForCycle(alice, 12n, 0n, signer)` still equals the full amount after rolling bond0→bond6 [2](#0-1) .

However, `unstake-sbtc` derives `bond-index` solely from the staker's *current* `protocol-bond-memberships` entry (the rolled-to bond) and computes `bond-start-cycle`/`bond-end-cycle` from that same new bond, clamping `current-cycle` into that range: [3](#0-2) . It then only mutates per-cycle maps for that new `bond-index`'s cycle range via `unstake-sats-from-bond-cycles`/`unstake-sats-from-bond-cycle`, which key every map write on the passed-in `bond-index` [4](#0-3) . It never touches entries keyed by the OLD bond-index, and physically transfers the full withdrawn sats out via `as-contract?`/`transfer` [5](#0-4) .

Because `verify-bond-rollover-window` only permits rolling during the old bond's last half-cycle (its L1 unlock window), the roll can happen while the old bond's final cycle is still ongoing and un-settled. If the staker immediately calls `unstake-sbtc` on the new bond for a full withdrawal (`amount-to-withdrawal-sats == current-amount-sats`), the real `current-cycle` at that moment is still the old bond's cycle (strictly less than the new bond's start cycle, by the non-overlap gate `bond-overlaps-new-position?`), so the `clamp` in `unstake-sbtc` floors to the new bond's start cycle — leaving the old bond's still-open cycle entry completely unaffected while the backing sBTC leaves the contract. Mining forward to complete that old-bond cycle and calling `calculate-rewards`/`claim-rewards` for the old bond-index then pays out rewards against a share record no longer backed by any custodied sBTC.

### Impact Explanation
This mints an unbacked sBTC reward payout for the old bond's cycle — value paid out of the reward pool (funded by protocol/signer fees) that is not backed by any actually-locked sBTC at settlement time, i.e., theft/unbacked minting of sBTC rewards. This matches the Critical category (unbacked minting of locked STX or sBTC rewards / double-counting a commitment). It is repeatable by any staker who times a full roll-over immediately followed by a full `unstake-sbtc` within the old bond's rollover window, for every roll-over cycle they can arrange.

### Likelihood Explanation
Preconditions: staker must have an active bond nearing its L1 unlock window, must `register-for-bond` into bond N+6 with equal (or any) sats to trigger `roll-sbtc`'s no-teardown path, then immediately call `unstake-sbtc` for a full withdrawal on the new bond while the old bond's last cycle is still open. This requires only ordinary staker actions (no special privilege), is cheap (a few transactions), and is fully reproducible with the existing test harness (`register-for-bond`, `unstake-sbtc`, `calculate-rewards`, `claim-rewards` are all public entry points already exercised in `pox-5.test.ts`).

### Recommendation
When performing a full (or partial) `unstake-sbtc`, `unstake-sbtc` must also settle/zero out any still-open cycles belonging to a *prior* bond-index that the staker rolled over from with unchanged/no-net-transfer sats, or `register-for-bond`'s roll-over path must fully tear down and re-attribute the old bond's remaining per-cycle shares to the new bond (as `update-bond-registration` already does), rather than leaving them independently claimable after the backing coin has left custody.

### Proof of Concept
Rust/TS test plan (extending `pox-5.test.ts` style):
1. `setupBond(0, ...)`, `registerForBond(bondIndex:0, sbtcAmount:S, staker:alice)`.
2. Mine to bond0's L1 rollover window (`getBondL1UnlockHeight(0)`), still within bond0's final cycle.
3. `setupBond(6, ...)`, `registerForBond(bondIndex:6, sbtcAmount:S, staker:alice)` — asserts no net FT transfer (roll-sbtc no-op) and `getStakerSharesStakedForCycle(alice, bond0LastCycle, 0, signer) == S`.
4. Immediately (same/next block, before bond6's first cycle starts) call `unstakeSbtc({signerManager: signer, amountToWithdrawalSats: S})` — full withdrawal; assert `sbtcBalance(alice)` increases by `S` and `getTotalSbtcStaked() == 0`.
5. Mine to complete bond0's original last cycle.
6. `calculateRewards([0])`, then `claimRewards([0])` for `signer`/`alice`.
7. Assert violation: `getEarnedStakerRewards(alice, bond0LastCycle, 0)` (or the equivalent earned/paid value) is **nonzero**, even though `getTotalSbtcStaked() == 0` and no sBTC backs the contract for that staker — violating `sBTC paid for (signer, staker, cycle=bond0) == 0`.
