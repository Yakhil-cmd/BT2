### Title
Cross-organization webhook forgery: signature is verified against the `repository.owner.login` field but the record acted upon is selected by the independent, unverified `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/HMAC secret to validate the inbound webhook against using a value taken directly from the unauthenticated JSON body: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Shipit supports configuring multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, exactly as shown in `test/dummy/config/secrets_double_github_app.yml`. The signature is checked against the secret for whatever organization the payload claims to be from (`repository.owner.login`), and the HMAC is computed only over `request.raw_post`, which contains the whole body including `repository.full_name`.

However, every webhook `Handler` resolves the target `Stack`/`Repository` using a *different* field of the same JSON body: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository_owner` (used to pick the verifying secret) and `repository_name`/`repository.full_name` (used to pick the object that gets mutated) are two independent JSON keys, and nothing cross-checks that `repository.full_name` actually belongs to the org named in `repository.owner.login`/`organization.login`. This is the same class of bug as the audit finding: a request is validated against one field (`token1`/`quoteAsset` in the report; `repository.owner.login` here) while the impactful action is driven by a different, unchecked field (`token0`/`launchAsset` in the report; `repository.full_name` here).

### Impact Explanation
In any multi-organization Shipit deployment (the officially documented configuration, see `test/dummy/config/secrets_double_github_app.yml` and the README's multi-org secrets schema), anyone who can produce a validly-signed webhook for **one** configured organization (e.g. because they administer that org's own GitHub App/webhook, which is not privileged access to Shipit itself) can set `repository.owner.login` to that org while setting `repository.full_name` to an arbitrary **other** organization's repository. Handlers such as `PushHandler` (triggers `GithubSyncJob`), `StatusHandler` (writes commit `Status` rows, which affect `deployable_status`/CI gating), and `CheckSuiteHandler` will act on the victim org's stack even though the request was never legitimately signed by that victim org's GitHub App. This is a cross-repository/cross-organization write achieved purely by crafting the JSON payload — matching the "cross-repository writes" impact category.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with more than one GitHub organization/App (a supported, documented configuration), and (2) the attacker possessing a valid webhook secret for at least one of those configured organizations (e.g., because they control the GitHub App/webhook config for their own org on that shared instance). This is a realistic scenario for any Shipit instance shared across multiple teams/orgs (multi-tenant setup), which is exactly the use case the `secrets_double_github_app.yml`/multi-org config is designed to support.

### Recommendation
After verifying the signature, cross-validate that `repository.full_name`'s owner segment matches the `repository_owner`/`organization.login` value that selected the signing secret (or, more robustly, derive the target Stack lookup and the signature-selection organization from the same trusted field), rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgAttacker` and `OrgVictim`, each with its own GitHub App and `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls `OrgAttacker`'s GitHub App webhook secret (legitimately, since they administer that org's app).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: push`, a valid `X-Hub-Signature` computed with `OrgAttacker`'s secret over the exact raw body, and a JSON body where:
   - `repository.owner.login` = `"OrgAttacker"` (so `Shipit.github(organization: repository_owner)` picks `OrgAttacker`'s app/secret and signature verification passes)
   - `repository.full_name` = `"OrgVictim/private-repo"`
4. `WebhooksController#create` passes params to `Handlers::PushHandler`, which calls `stacks` → `Repository.from_github_repo_name("OrgVictim/private-repo")`, enqueuing `GithubSyncJob` for `OrgVictim`'s stack despite the request never being signed by `OrgVictim`'s GitHub App.
