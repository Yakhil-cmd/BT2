### Title
`StatusHandler` writes commit statuses across every stack, letting one onboarded organization forge CI results on repositories it doesn't own - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
### Finding Description
Every other webhook handler in the engine scopes its writes to the repository named in the payload by calling the shared `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`), e.g. `PushHandler` (`stacks.not_archived.where(branch:)`) and `CheckSuiteHandler` (`stacks.where(branch: ...)`): [1](#0-0) [2](#0-1) [3](#0-2) 

`StatusHandler`, however, never uses `stacks`/`repository_name` at all. It matches purely on commit sha, globally, across the whole `Commit` table: [4](#0-3) 

The controller-level signature check only proves that the request was signed with the webhook secret belonging to *some* organization present in the payload (`repository.owner.login` or `organization.login`); it does not constrain which stack/commit the handler is allowed to mutate: [5](#0-4) [6](#0-5) 

This creates a binding mismatch: the equality that should hold is `organization whose webhook_secret signed the request == organization owning the commit/stack that gets written`. Because `StatusHandler#process` ignores `params.dig('repository', ...)` entirely, an event validly signed for organization A can write a `Status` record onto a `Commit` belonging to any stack/organization B tracked by the same Shipit instance, as long as the attacker supplies a `sha` that matches an existing commit row (git SHAs of public/internal repos are frequently discoverable via GitHub's own API/UI, PR links, badges, etc., and are not secrets).

### Impact Explanation
Commit `Status` objects drive Shipit's CI gating logic used both for deploy eligibility (`Commit#deployable?`) and merge-queue gating (`MergeRequest::StatusChecker`, `MergeRequest#all_status_checks_passed?`/`#any_status_checks_failed?`), as seen in: [7](#0-6) 

An attacker who only controls one organization onboarded into a shared Shipit instance (and therefore only holds a valid webhook secret for that organization) can forge a `success` status on a commit belonging to a *different* organization's stack. This can make an otherwise CI-failing or CI-missing commit appear deployable, or make a pull request in `MergeRequest#all_status_checks_passed?` appear green, which can lead to an unauthorized deploy or an unauthorized merge (via the auto-merge queue in `ProcessMergeRequestsJob`) on a repository the attacker does not control — this squarely matches the "High - escalation ... or an unauthorized deploy, rollback or merge" impact category.

### Likelihood Explanation
The only prerequisite is that the attacker's own organization is one of the (potentially many) GitHub organizations configured in the shared Shipit instance's `Shipit.github` config — a normal, unprivileged tenant, not a privileged Shipit user/API client. They do not need write access to the victim repository, a `github_access_token`, an `ApiClient` token, or any Shipit-side privilege. They only need to know/guess a target commit SHA (commonly discoverable, e.g. via public GitHub commit history/PR links) belonging to another stack in the same instance, then POST a correctly HMAC-signed (with their own org's secret) `status` webhook payload referencing that SHA.

### Recommendation
Make `StatusHandler` scope its lookup through the shared `stacks`/`repository_name` helper the same way `PushHandler` and `CheckSuiteHandler` do, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so that the organization that signed the webhook and the stack/commit being written are provably the same entity.

### Proof of Concept
1. Shipit instance hosts stacks for both `org-attacker/repo` and `org-victim/repo`, each with its own `webhook_secret` configured under `Shipit.github`.
2. Attacker (owner of `org-attacker`, with legitimate access to configure/send webhooks for their own org) discovers a commit SHA `deadbeef...` that exists in `org-victim/repo`'s tracked branch (e.g. from a public PR link) and is currently failing/missing CI.
3. Attacker crafts a `status` event JSON body: `{"sha": "deadbeef...", "state": "success", "context": "ci/whatever", ...}` and signs it with `org-attacker`'s `webhook_secret`, setting `X-Github-Event: status` and `X-Hub-Signature` accordingly (the payload need not even include a `repository` object matching the victim, since `verify_signature` only needs an org it can resolve, and `StatusHandler` never checks `repository` again).
4. `WebhooksController#verify_signature` succeeds because it validates against `org-attacker`'s configured secret and the request body's own HMAC.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (since lookup is global, unscoped by repository), and creates a `success` status record on it.
6. The victim's commit now looks CI-green, potentially unblocking a deploy or auto-merge in `org-victim`'s stack that the attacker never had access to.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
