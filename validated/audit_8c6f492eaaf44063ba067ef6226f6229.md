### Title
Empty cell-batch input causes `VerifyCellKzgProofBatch` to spuriously throw on `calloc(0)`-returns-NULL libcs instead of returning the reference's vacuous `true` - (File: bindings/node.js/src/kzg.cxx)

### Summary
`VerifyCellKzgProofBatch` calls `calloc(commitments_param.Length(), sizeof(Bytes48))` (and similarly for `cell_indices`, `cells`, `proofs`) with a length of `0` when all four attacker-supplied arrays are empty, then treats a `NULL` return from `calloc(0, ...)` as an unconditional allocation failure and throws. The C standard permits `calloc(0, size)` to return either `NULL` or a valid unique pointer, so this binding's observable result for the empty-batch input diverges from the reference specification's vacuous-`true` result depending on the platform libc.

### Finding Description
The broken equality is: **(bytes, count, result) that the binding produces for `num_cells=0`** must equal **the reference `verify_cell_kzg_proof_batch` semantics for an empty batch**, which is `ok == true` (vacuously true, no proofs to check).

Tracing the code in [1](#0-0) :
- `num_cells = cells_param.Length()` is fully attacker-controlled and can be `0`.
- The length-equality check (`commitments_param.Length() != num_cells || ...`) passes trivially when all four arrays are empty (`0 == 0 == 0 == 0`).
- `commitments = (Bytes48 *)calloc(commitments_param.Length(), sizeof(Bytes48))` is then called with a first argument of `0`.
- The very next check, `if (commitments == nullptr) { ...ThrowAsJavaScriptException(); goto out; }`, unconditionally treats a `NULL` return as "Error while allocating memory for commitments" and aborts before ever reaching `verify_cell_kzg_proof_batch` at [2](#0-1) .

Per the C standard, `calloc(0, size)` is implementation-defined: it may return `NULL` or a unique non-NULL pointer that can later be freed but must not be dereferenced. glibc typically returns a non-NULL pointer for `calloc(0, ...)`, while other libc implementations (e.g., some musl configurations, embedded/alternative allocators) are permitted to return `NULL` for a zero-size request even though no real allocation failure occurred. On the latter, this binding throws `"Error while allocating memory for commitments"` for a completely benign, legitimately empty batch, while the reference C implementation (and other language bindings that don't special-case zero-length calloc) would proceed to call `verify_cell_kzg_proof_batch` with `num_cells=0` and return `out == true`.

None of the existing guards prevent this: the array-length equality check passes for all-empty inputs, there is no `num_cells == 0` short-circuit before the `calloc` calls, and the `nullptr` check cannot distinguish "true OOM" from "standards-permitted NULL for zero-size request."

### Impact Explanation
For the exact attacker-supplied input `commitments_param=[]`, `cell_indices_param=[]`, `cells_param=[]`, `proofs_param=[]`, the Node.js binding's result diverges based solely on the host's libc `calloc(0)` behavior: some deployments return `ok=true` (matching the reference spec), others throw and effectively reject/`false`-path the empty data-column-sidecar batch. This is a verdict divergence for identical, attacker-chosen bytes across different honest nodes running the same binding logic, matching the "High" impact category (verdict differs from the reference specification, causing a fork in behavior across a subset of the network depending on runtime libc).

### Likelihood Explanation
The precondition is only that an attacker (or protocol logic driven by attacker-supplied data) invoke `verifyCellKzgProofBatch` via the Node.js binding with all four input arrays empty — a zero-cost, always-reachable public API call requiring no special privileges, trusted-setup manipulation, or complex crafted bytes. The divergence is 100% repeatable on any given host, and cross-host divergence depends only on which libc's `calloc` implementation the Node.js native addon links against.

### Recommendation
Add an explicit `num_cells == 0` short-circuit in `VerifyCellKzgProofBatch` (and any sibling batch-verification bindings with the same `calloc`-then-null-check pattern) that returns `true` immediately without allocating, mirroring the reference specification's vacuous-true semantics for empty batches, instead of relying on `calloc(0, ...)` never returning `NULL`.

### Proof of Concept
Node.js binding test (extending `bindings/node.js/test/kzg.test.ts`):
```ts
test("verifyCellKzgProofBatch: empty batch returns true (reference semantics)", () => {
  const result = kzg.verifyCellKzgProofBatch([], [], [], []);
  expect(result).toBe(true); // must match reference verify_cell_kzg_proof_batch(num_cells=0) == true
  // must NOT throw "Error while allocating memory for commitments"
});
```
Assert both sides of the equality: (1) reference/C implementation invoked directly with `num_cells=0` returns `C_KZG_OK` and `out=true`; (2) the Node.js binding call with all-empty arrays returns `true` and does not throw, on any libc where `calloc(0, sizeof(Bytes48))` returns `NULL` (reproducible by stubbing/mocking `calloc` in a local C harness to return `NULL` for zero-size requests and confirming the current code path throws).
