## #Vulnerability found for this question.

### Title
Unfiltered pull-request label names inject arbitrary environment variable keys (e.g. `GEM_HOME`) into `TaskCommands#install_dependencies` subprocess env - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment-variable **key** into the stack env with no allowlist, unlike every other env-setting path in the codebase (`EnvironmentVariables#permit`). This merged env flows unfiltered through `TaskCommands#env` into `Command#unbundled_env` and `PTY.spawn`, so a PR author who fully controls their own PR labels and PR branch contents can inject loader-sensitive keys such as `GEM_HOME` into the `bundle`/`ruby` dependency-install step.

### Finding Description
The broken binding: every other user-influenced env surface in this engine enforces `keys(env) ⊆ allowlist(variable_definitions)` via `Shipit::EnvironmentVariables#permit` (see `app/controllers/shipit/tasks_controller.rb:81`, `app/controllers/shipit/deploys_controller.rb:67`, `app/controllers/shipit/rollbacks_controller.rb:30`, and `app/models/shipit/deploy_spec.rb:174-180`). `ReviewStack#env` breaks this invariant:

```ruby
def env
  return super unless pull_request.present?
  super.merge(
    pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
  )
end
``` [1](#0-0) 

There is no call to `EnvironmentVariables.with(...).permit(...)` here — any label name becomes a raw environment key. `pull_request.labels` are populated straight from the webhook body by `LabelCapturingHandler#capture_labels`:

```ruby
def capture_labels
  return unless pull_request = stack.pull_request
  pull_request.update!(labels: params.pull_request.labels.map(&:name))
end
``` [2](#0-1) 

This handler runs for `opened`, `labeled`, `unlabeled`, and `reopened` PR events on any non-archived review stack, including stacks provisioned under `prevent_with_label` (an attacker's own PR that stays unlabeled/does not carry the blocking label). This is a normal, authenticated (signed) webhook a PR author's own actions on their own PR naturally generate — no forged signature or secret is required.

The merged `ReviewStack#env` is consumed by `TaskCommands#env`:
```ruby
def env
  super.merge(@stack.env)...
end
``` [3](#0-2) 

and passed unfiltered into every dependency step:
```ruby
def install_dependencies
  deploy_spec.dependencies_steps!.map do |command_line|
    Command.new(command_line, env:, chdir: steps_directory)
  end
end
``` [4](#0-3) 

`Command` performs no key filtering before spawning the process:
```ruby
def unbundled_env
  BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
end
...
@out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
``` [5](#0-4) 

So a PR label literally named `gem_home` becomes `GEM_HOME=true` in the `bundle install` process env for a repo that has a `Gemfile` (auto-detected by `DeploySpec::BundlerDiscovery#bundler?`, see `app/models/shipit/deploy_spec/bundler_discovery.rb:71-73`). Because the value is a fixed string `"true"` (not an attacker-chosen absolute path), `GEM_HOME` resolves relative to `chdir` = the PR's own checked-out working directory (`steps_directory`), which the PR author fully controls. An attacker can commit a directory literally named `true` in their own branch containing a crafted `specifications/*.gemspec`; RubyGems/Bundler evaluates gemspecs as Ruby code when scanning `GEM_HOME`, giving code execution during the dependency-install step on the Shipit host.

Existing guards do not catch this: `verify_signature` only authenticates that the webhook truly came from GitHub for that repo/org — it does not restrict what fields (like label names) are inside a legitimate, attacker-authored PR event. `EnvironmentVariables#permit` is never invoked for `ReviewStack#env`; it's only wired into controller-driven, human-triggered deploy/rollback/task-trigger params, not into the automatic label-derived env merge.

### Impact Explanation
An unprivileged PR author (fork owner) can influence the process environment of `bundle`/`ruby` invocations that run with the Shipit host's git/GitHub credentials and privileges, during automatic review-stack dependency installation. Combined with full control over their own branch's file tree, this is a path to Remote Code Execution on the Shipit deploy host — matching the Critical RCE class in the rules. It is repeatable per PR/label and scoped to repositories that have review stacks enabled (`allow_all`, `allow_with_label`, or `prevent_with_label` without the blocking label) and use Bundler/Ruby dependency steps.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that allows an unlabeled/labeled PR to reach `provisioning` (all three behaviors have a path to provisioning), and the repository's `shipit.yml`/`Gemfile` must trigger the Bundler dependency step. Attacker cost is minimal: open a PR from a fork and add/name a label — no secrets, no privileged role, no forged webhook needed since GitHub itself will emit a validly-signed webhook for the attacker's own label action. This is fully repeatable and requires only normal GitHub PR/label permissions on one's own PR.

### Recommendation
Remove or heavily restrict `ReviewStack#env`'s unrestricted label-to-env-key merge. At minimum:
- Run the label-derived hash through `Shipit::EnvironmentVariables.with(...).permit(...)` against an explicit, repo-configured allowlist of permitted "label flag" variable names, rejecting/dropping any key not on that list (mirroring how `deploy_variables`/task `variables` are enforced elsewhere).
- Additionally deny known loader/toolchain-sensitive variable names (`GEM_HOME`, `GEM_PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, etc.) outright regardless of allowlist configuration.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` style):
```ruby
test "#env does not allow pull request labels to set loader-sensitive keys" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_home"]

  refute stack.env.key?("GEM_HOME"), "PR label should not be able to inject GEM_HOME into task env"
end

test "TaskCommands#install_dependencies process env must not contain fork-controlled GEM_HOME" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["gem_home"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  command = Shipit::TaskCommands.new(task).install_dependencies.first
  assert_nil command.env["GEM_HOME"], "GEM_HOME reached the dependency-install Command env via an unlabeled allowlist"
end
```
Both assertions currently FAIL against `ReviewStack#env`'s current implementation (`stack.env["GEM_HOME"] == "true"`), demonstrating the broken binding: `keys(TaskCommands#env) ⊄ allowlist(variable_definitions)`.
