### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but `StatusHandler` writes commit CI status by SHA alone with no repository/stack scoping, allowing a valid webhook signer for *any* onboarded organization to forge CI status for commits belonging to a *different* organization's stacks and trigger unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`). That verification only proves "this request was signed with *some organization's* configured secret" - it does not bind the verified organization to the data the corresponding handler actually acts upon. `StatusHandler` ignores the `repository` field entirely and looks up target commits globally by SHA (`Commit.where(sha: params.sha)`), then writes an attacker-supplied status onto whatever commit matches, regardless of which organization/stack owns it.

### Finding Description
The webhook signature check: [1](#0-0) 
picks the GitHub App/organization config to verify against using: [2](#0-1) 

This binds *authentication* to whichever organization login appears in the JSON body - a field fully controlled by whoever crafts the payload, constrained only by needing a signature valid for the secret of the org they name.

The generic `Handler` base class defines repository scoping via a different field (`repository.full_name`): [3](#0-2) 

But `StatusHandler` does not use this scoping at all - it looks up commits purely by SHA, with no repository/organization/stack filter whatsoever: [4](#0-3) 

The write path then flips deploy eligibility directly, since `Commit#status`/`Commit#deployable?` are derived from stored `Status` records: [5](#0-4) [6](#0-5) 

and `add_status` (invoked by `create_status_from_github!`) schedules merges when the new status becomes success/pending: [7](#0-6) 

For stacks with `continuous_deployment` enabled, the periodic `ContinuousDeliveryJob` deploys the latest deployable commit once it satisfies `deployable?` (i.e., `success? && !blocked?`): [8](#0-7) 

**The binding that should hold but doesn't:** `organization authenticated by verify_signature` == `organization/repository whose commit status is written by StatusHandler`. Before the attack, these coincide because GitHub only ever sends a status event for the same repository/org whose secret signed it. After the attack, an entity that legitimately administers Organization A's webhook (and thus knows Org A's `webhook_secret`, configured in `Shipit.github`'s per-org config) can sign a `status` event payload naming `repository.owner.login: "org-a"` (making `verify_signature` succeed using Org A's secret) while setting `sha` to a commit SHA that belongs to Organization B's stack. `StatusHandler` performs no cross-check between the verified organization and the commit's actual stack/repository, so the forged status is applied to Org B's commit.

### Impact Explanation
This breaks a cross-tenant/cross-repository trust boundary in a multi-organization Shipit deployment (`Shipit.github` supports multiple orgs, each with its own webhook secret, per `lib/shipit/github_app.rb` and `config/secrets.development.shopify.yml`). An entity who is only entitled to send webhooks for their own organization can:
- Inject a fake passing CI status for an arbitrary commit belonging to a different, unrelated organization's stack.
- Cause `Commit#deployable?` to become true for that commit even though real CI never passed and even though blocking/required statuses defined by the victim stack were never satisfied.
- Trigger `stack.schedule_merges` and, for continuously-deployed stacks, cause `ContinuousDeliveryJob` to automatically deploy the falsely-"green" commit.

This matches the required Critical impact of an unauthorized deploy driven by a forged/bypassed trust check, achieved purely through a credential (webhook secret) the attacker legitimately owns for their *own* organization - not the victim's.

### Likelihood Explanation
Requires the Shipit instance to host more than one organization (a realistic/common multi-tenant setup, as the config format explicitly supports a map of orgs under `github:`). The attacker needs to know the actual sha of a target commit in the victim's repository - typically public knowledge for open-source repos or obtainable from PR/commit metadata. No access to the victim org's GitHub App, private key, or webhook secret is needed at all, and no `ApiClient` token or Shipit user session is required - only the ability to sign a webhook with any org's configured secret.

### Recommendation
`StatusHandler` (and any other handler that doesn't scope by `repository.full_name`) must resolve the commit *through* the same repository/organization that was verified during signature validation, e.g., restrict the `Commit.where(sha: ...)` lookup with `.joins(stack: :repository).where(repositories: { owner: verified_organization })`, or otherwise thread the verified organization from `WebhooksController` into handlers and assert it matches the target stack's repository owner before mutating any commit/status state.

### Proof of Concept
1. Shipit is configured for two organizations, `org-a` (attacker-controlled) and `org-b` (victim), each with distinct `webhook_secret`s under `Shipit.github`.
2. Attacker legitimately knows `org-a`'s `webhook_secret` (they administer `org-a`'s GitHub App/webhook).
3. Attacker identifies a commit SHA `S` belonging to a stack on `org-b/victim-repo` that has `continuous_deployment: true`.
4. Attacker crafts payload:
   ```json
   {
     "sha": "S",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "org-a" } }
   }
   ```
5. Attacker computes `X-Hub-Signature` HMAC over the raw body using `org-a`'s `webhook_secret` and POSTs to `/webhooks` with `X-Github-Event: status`.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"` (`app/controllers/shipit/webhooks_controller.rb:59-62`), looks up `Shipit.github(organization: "org-a")`, and the signature verifies successfully.
7. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) runs `Commit.where(sha: "S")` - matching the victim's commit in `org-b` - and calls `create_status_from_github!`, writing a fabricated `success` status onto it, with no check that the commit belongs to `org-a`.
8. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) now evaluates true for the victim commit; `add_status` schedules merges, and `ContinuousDeliveryJob` (`app/jobs/shipit/continuous_delivery_job.rb`) deploys it on the victim's stack - an unauthorized deploy triggered entirely by an attacker who only ever controlled `org-a`'s webhook secret.

module Shipit
  class ContinuousDeliveryJob < BackgroundJob
    include BackgroundJob::Unique

    queue_as :deploys
    on_duplicate :drop

    def perform(stack)
      return unless stack.continuous_deployment?

      # If there is a schedule defined for this stack, make sure we are within a
      # deployment window before proceeding.
      return if stack.continuous_delivery_schedule && !stack.continuous_delivery_schedule.can_deploy?

      # checks if there are any tasks running, including concurrent tasks
      return if stack.occupied?

      stack.trigger_continuous_delivery
    end
  end
