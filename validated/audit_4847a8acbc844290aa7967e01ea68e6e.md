### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by matching `sha`, with no check that the webhook's `repository.full_name` corresponds to the `Stack`/`Repository` that owns the matched `Commit`. Any validly-signed webhook (i.e., from any repository/organization already integrated with this Shipit instance) that emits a `status` event for a SHA which happens to also exist in an unrelated stack's commit history will write that status onto the victim commit, satisfying `Stack#required_statuses`/clearing `Commit#blocked?` for a repository the sender never authenticated against.

### Finding Description
The claimed binding is:
`context/state pair accepted as satisfying Stack#required_statuses` == `status actually produced by CI running against that Stack's Repository`

This binding is **false** in the code. `StatusHandler#process` is: [1](#0-0) 

It does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no reference to `payload.dig('repository', 'full_name')`, no comparison against `commit.stack.repository.full_name`. This is inconsistent with the base `Handler` class, which defines a `stacks` helper explicitly scoped by `Repository.from_github_repo_name(repository_name)`: [2](#0-1) 

Other handlers (push, pull_request, check_suite) use this `stacks` scoping helper to restrict effects to the repository named in the payload, but `StatusHandler` bypasses it entirely and queries `Commit` globally by `sha`.

`create_status_from_github!` then unconditionally persists the forged status: [3](#0-2) 

That status feeds directly into `Status::Group.compact`'s required-context matching (`missing_contexts = required_statuses - visible_statuses.map(&:context)`), and ultimately into `Commit#blocked?`/`#deployable?`: [4](#0-3) [5](#0-4) 

Exploit flow: the attacker needs a webhook that passes `verify_signature`, i.e., a `status` event whose `repository.owner.login` maps to a GitHub organization/app config already known to `Shipit.github(organization:)` — this is satisfiable using a repo/org the attacker legitimately owns or controls, per the stated threat model ("emit webhooks from a repository they own"): [6](#0-5) 

Given a SHA that is shared between the attacker's repository and the victim stack's repository (e.g., common git history from a fork/shared upstream, a precondition assumed as given by the question — "as above"), the attacker sets a genuine commit status with `context` equal to one of the victim stack's `required_statuses` and `state=success` on their own repository/commit. GitHub delivers a correctly-signed `status` webhook naming the attacker's own repository. `StatusHandler#process` ignores that repository field and matches purely on `sha`, writing the forged, satisfying status onto the victim's `Commit` row, which flips `blocked?` to `false` for the victim stack and can satisfy `deployable?`.

None of the existing guards stop this: `verify_signature` only validates that the payload came from *some* legitimate GitHub org, not that it's the org owning the commit being mutated; `ExplicitParameters` schema for `StatusHandler` only validates types/shape (`sha`, `state`, `context`, etc.), not repository identity; and there is no `drop_unhandled_event` or model-level cross-check tying `Status` rows to the repository asserted in the webhook payload.

### Impact Explanation
A forged, cross-repository commit status write lets an attacker who controls any repository already integrated with the Shipit instance clear a required-status block on a completely unrelated victim stack's commit, enabling an unauthorized deploy on that victim stack — this is "a payload for one repository mutating another's stack, commit, task" (Critical). The write is repeatable against any stack/commit for which a SHA collision can be arranged, and is not confined to repos within the same GitHub organization as the attacker, since nothing in `StatusHandler` checks organization/repository identity of the target commit.

### Likelihood Explanation
Preconditions: (1) attacker must control a repository whose organization is already configured/integrated with this Shipit instance so the webhook signature check passes, (2) the victim stack must have `required_statuses`/blocking statuses configured with a currently pending/failing context, and (3) a SHA collision must exist between a commit in the attacker's repository and the victim's tracked commit history (plausible via shared fork ancestry, common upstream history, or subtree/vendoring scenarios — this collision precondition is given by the question, not re-derived here). Given those, forging the status requires only setting a commit status via the standard GitHub Statuses API on a commit the attacker controls — low cost, fully repeatable, no Shipit secrets needed.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by both `sha` and repository, e.g. restrict to commits whose `stack.repository` matches `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, mirroring the `stacks` helper already used by other handlers, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (new/extended)
test "status webhook from an unrelated repository can clear a required-status block on a victim stack" do
  victim_repo  = shipit_repositories(:shipit)
  victim_stack = shipit_stacks(:shipit)
  # configure a required status context on the victim stack
  victim_stack.update!(...) # ensure deploy_spec / required_statuses includes 'ci/forged-context'

  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, ...)
  # simulate the collision: an unrelated repo/stack also references the same sha
  other_repo  = Repository.create!(owner: 'attacker', name: 'evil-repo')
  other_stack = other_repo.stacks.create!(...)
  other_stack.commits.create!(sha: victim_commit.sha, ...)

  assert victim_commit.blocked? # precondition: currently blocked

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/forged-context',
    'repository' => { 'full_name' => other_repo.full_name, 'owner' => { 'login' => 'attacker' } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  refute victim_commit.blocked?, "forged status from unrelated repository should not clear victim stack's block"
end
```
Both sides of the binding to assert explicitly: `payload.dig('repository','full_name')` (attacker's `other_repo.full_name`) must **not** equal `victim_stack.repository.full_name`, yet the test demonstrates `victim_commit.blocked?` still flips to `false` — proving the code never checks that equality.
