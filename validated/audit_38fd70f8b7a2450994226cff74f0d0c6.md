### Title
KLAY (and ERC20) Permanently Locked in Service-Chain Bridge When Recipient Rejects Transfer — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` makes a bare `.call.value()` to `_to` and hard-reverts the entire transaction if the call fails. Because there is no skip/rescue path, any bridge transfer whose destination address permanently rejects KLAY causes the corresponding nonce to be unresolvable, permanently locking the bridged KLAY in the contract and freezing `lowerHandleNonce` / `recoveryBlockNumber` for that bridge pair.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

1. Nonce guard (`_lowerHandleNonceCheck`) [1](#0-0) 
2. Operator vote (`_voteValueTransfer`) [2](#0-1) 
3. State writes: `handleNoncesToBlockNums[_requestedNonce]` and `_updateHandleNonce` [3](#0-2) 
4. External KLAY transfer with hard revert on failure: [4](#0-3) 

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

If `_to` is a contract that does not have a payable fallback (or deliberately reverts on receipt), the `require` causes the **entire transaction to revert**, rolling back all state changes including the nonce write. The nonce is therefore never marked handled.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`: [5](#0-4) 

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
```

Because the stuck nonce N is never written, `lowerHandleNonce` is permanently frozen at N, and `recoveryBlockNumber` never advances past the block preceding N.

The identical pattern exists in `handleERC20Transfer` (non-mint-burn mode), where `IERC20(_tokenAddress).safeTransfer(_to, _value)` reverts if `_to` is blacklisted by the token contract: [6](#0-5) 

---

### Impact Explanation

- **KLAY / ERC20 permanently locked**: The bridged value deposited on the source chain can never be delivered to `_to` and there is no admin rescue function to redirect or recover it.
- **`lowerHandleNonce` frozen**: The `valueTransferRecovery` subsystem uses `recoveryBlockNumber` (derived from `lowerHandleNonce`) as its scan start point. With it frozen, the recovery loop will perpetually re-submit the same failing nonce without making progress, blocking the entire bridge pair's recovery pipeline. [7](#0-6) 
- There is no owner/operator function to skip a nonce, redirect a stuck transfer, or withdraw locked KLAY from the bridge contract.

---

### Likelihood Explanation

Any user who initiates a KLAY transfer on the source chain specifying a destination `_to` that is a contract without a payable fallback triggers this condition. Common real-world examples include multisig wallets compiled without a payable fallback, proxy contracts, or any contract that deliberately reverts on ETH/KLAY receipt. The user action is entirely valid and unprivileged (calling `requestKLAYTransfer` or the fallback function on the source bridge). [8](#0-7) 

---

### Recommendation

1. **Separate transfer from state finalization**: Mark the nonce as handled unconditionally, then attempt the transfer. If the transfer fails, record the value in a claimable balance mapping (pull-payment pattern) so the recipient can withdraw later, or an admin can redirect it.
2. **Add an admin rescue / nonce-skip function**: Allow the bridge owner to mark a nonce as permanently skipped (with the value credited to a recovery address), unblocking `lowerHandleNonce`.
3. **Apply the same fix to `handleERC20Transfer`**: Replace the direct `safeTransfer` with a pull-payment or try/catch pattern for the non-mint-burn path. [9](#0-8) 

---

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT

// Attacker-controlled destination: rejects all KLAY
contract RejectKLAY {
    // No payable fallback → any .call.value() to this address returns ok=false

// Steps:
// 1. On source chain, user calls:
//    bridge.requestKLAYTransfer{value: 10 ether}(address(rejectKLAY), 10 ether, "");
//    → RequestValueTransfer emitted with nonce N, 10 KLAY locked in source bridge.

// 2. Operators observe the event and call on destination bridge:
//    bridge.handleKLAYTransfer(txHash, from, address(rejectKLAY), 10e18, N, blockNum, "");
//    → _lowerHandleNonceCheck passes (N >= lowerHandleNonce)
//    → _voteValueTransfer reaches threshold
//    → handleNoncesToBlockNums[N] = blockNum  (written)
//    → _updateHandleNonce(N) runs             (lowerHandleNonce advances)
//    → (bool ok,) = rejectKLAY.call.value(10e18)("") → ok = false
//    → require(ok, ...) REVERTS entire tx
//    → ALL state changes rolled back; handleNoncesToBlockNums[N] == 0

// 3. Every subsequent operator retry for nonce N reverts identically.
//    lowerHandleNonce is permanently stuck at N.
//    10 KLAY is permanently locked in the destination bridge contract.
//    recoveryBlockNumber never advances past block N-1.
