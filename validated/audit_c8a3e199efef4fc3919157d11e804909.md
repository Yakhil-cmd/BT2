### Title
Stack-scoped API token can read any other stack's CCMenu status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-lookup helper in a way that drops the tenant/stack scoping that every other API controller enforces for `ApiClient`s restricted to a single stack.

### Finding Description
The base API controller binds an `ApiClient` token to the set of stacks it is allowed to touch: [1](#0-0) 
`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a specific stack, and every other API resource controller (`LocksController`, `ReleaseStatusesController`, `TasksController`, etc.) resolves its target stack through this scoped `stacks.from_param!` helper, so a token restricted to Stack A can never resolve Stack B.

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!` directly, bypassing `stacks` and therefore the `current_api_client.stack_id` restriction entirely: [2](#0-1) 

The only authorization check that remains is `require_permission :read, :stack`, which merely checks that the token's `permissions` array contains `read:stack` — it never checks that `params[:stack_id]` matches `current_api_client.stack_id`: [3](#0-2) 

This breaks the binding `stack authorized by token == stack the token can act on` (a listed analog category): the equality that should hold is `current_api_client.stack_id == stack.id` whenever `stack_id?` is true, but `CCMenuController#stack` never checks it.

Concretely, tokens created via `CCMenuUrlController` are stack-scoped in intent (they are minted per-stack to drive the CCMenu badge for that one stack) and only carry `read:stack` permission: [4](#0-3) 
Any `ApiClient` fixture/record that is scoped to a single stack (e.g. `stack: shipit` in `here_come_the_walrus`) and has `read:stack` permission is equally affected — its token, presented to `GET /stacks/:owner/:repo/:environment/ccmenu.xml?token=...` (or via Basic auth, since `authenticate_api_client` falls back to `super`) with a different `stack_id`, will successfully authenticate (`ApiClient.authenticate`), pass the `read:stack` permission check, and load an arbitrary stack via `Stack.from_param!(params[:stack_id])`.

### Impact Explanation
This is a cross-stack authorization bypass: a token that was only supposed to authorize reading one stack's build/deploy status can be used to read another stack's status (name, latest deploy/rollback outcome, running/success/failure state) via the CCMenu endpoint. This matches the "High - unauthenticated read of stack state" category relative to the token's own scope, since the token was never authorized for that stack.

### Likelihood Explanation
Any holder of a legitimately-scoped, low-privilege `read:stack` token (which by design is meant to be narrowly scoped to a single stack for the CCMenu integration) can trivially escalate by supplying a different `stack_id`/`repo_owner`/`repo_name`/`environment` in the CCMenu route — no additional secrets, sessions, or elevated permissions are needed beyond the token itself.

### Recommendation
Have `CCMenuController#stack` resolve through the same tenant-scoped `stacks` helper used by the base controller (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is enforced consistently across all API controllers.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` token restricted to Stack A with `permissions: ['read:stack']` (this is exactly what `CCMenuUrlController#client` mints, or any similarly configured client such as the `here_come_the_walrus` fixture: `stack: shipit`, `permissions: ['read:stack']`). [5](#0-4) 
2. Send `GET /stacks/<owner>/<stack-b-repo>/<stack-b-env>/ccmenu.xml?token=<stack-A-token>` where Stack B is a different stack the token was never granted access to.
3. `CCMenuController#authenticate_api_client` authenticates the token via `ApiClient.authenticate(params[:token])`. [6](#0-5) 
4. `require_permission :read, :stack` passes because the token has `read:stack` in its `permissions` list, with no stack-identity check.
5. `stack` resolves `Stack.from_param!(params[:stack_id])` for Stack B directly (bypassing `stacks`), and `show` renders Stack B's deploy/rollback status in the response — data the token was never scoped to see. [7](#0-6)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
