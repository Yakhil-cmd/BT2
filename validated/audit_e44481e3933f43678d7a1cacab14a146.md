### Title
Webhook signature is verified against the payload's `repository.owner.login`, but all handlers act on the payload's `repository.full_name` - allowing cross-organization status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an incoming GitHub webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). But every webhook handler resolves the `Stack`/`Repository` to act on using a *different* field from the same untrusted JSON body: `payload.dig('repository', 'full_name')`. Since Shipit supports multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who legitimately controls one organization's GitHub App installation in this Shipit instance can sign a payload with their own known `webhook_secret`, but forge `repository.full_name` to point at a victim organization's repository/stack.

### Finding Description
The signature check binds trust to `repository_owner`: [2](#0-1) [3](#0-2) 

`Shipit.github(organization: repository_owner)` looks up the per-organization `GitHubApp` and its `webhook_secret` via `github_app_config` [1](#0-0) . This proves the request came from *an* organization the attacker controls (their own GitHub App installation), not necessarily the organization whose repository is subsequently mutated.

Every handler, however, resolves which `Stack`s to mutate using a *separate* field, `repository.full_name`, never cross-checked against `repository.owner.login`: [4](#0-3) 

For example, the status handler (exercised by `test/controllers/webhooks_controller_test.rb`, `":state create a Status for the specific commit"`) writes `state`, `target_url`, `description`, and `context` directly from the payload onto a `Commit` matched purely by `sha` within the stacks resolved from `repository_name`: [5](#0-4) 

This breaks the binding: *organization authenticated (via `webhook_secret`) == repository written (via `full_name`)*. Before the attack, a payload's `repository.owner.login` and `repository.full_name` were assumed to always describe the same repository. After the attack, an attacker sets `repository.owner.login = "attacker-org"` (their own onboarded org, satisfying signature verification with a secret they legitimately know) while setting `repository.full_name = "victim-org/victim-repo"` (whose commits/stacks actually get mutated).

### Impact Explanation
By forging a `status` event this way, an attacker with a legitimate GitHub App installed on *any* organization configured in the same multi-tenant Shipit instance can inject a fabricated "success" CI status onto an arbitrary commit belonging to a different organization's stack. Since Shipit's deploy gating relies on such commit statuses (`ci.require`), this can be used to satisfy CI requirements that were never actually met, resulting in an unauthorized deploy of unvetted code. It can similarly be abused with the `push` handler to enqueue sync jobs (`GithubSyncJob`) against a victim stack under attacker-chosen `after` SHA values [6](#0-5) , and with `membership`/`pull_request` handlers to inject or manipulate victim organization data. This satisfies the Critical bar ("an unauthorized deploy... or cross-repository writes"), since it requires only credentials for the attacker's *own* registered organization, not the victim's.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple organizations (a documented, supported configuration in `lib/shipit.rb`'s `github_app_config`/`github_organizations`), and requires the attacker to control (or self-register) at least one such organization's GitHub App on the shared Shipit instance — which is a realistic scenario for any shared/self-serve Shipit deployment onboarding multiple teams or organizations. No victim credentials, sessions, or tokens are needed; the attacker only forges the JSON body and signs it with their own known secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), cross-validate that `repository.owner.login` (the organization whose secret validated the signature) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the webhook with `422` otherwise.

### Proof of Concept
1. Attacker installs their own GitHub App on `attacker-org`, which is configured in this Shipit instance's multi-org `secrets.github[:attacker-org]` with a known `webhook_secret`.
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and succeeds, since the signature matches attacker-org's own secret [7](#0-6) .
5. The status handler resolves `stacks` via `repository_name` = `"victim-org/victim-repo"` [4](#0-3) , and writes the forged `success` status onto the victim's commit, potentially unblocking a deploy gated on that CI context.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
