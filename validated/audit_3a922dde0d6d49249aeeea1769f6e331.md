### Title
Webhook signature verification keys off the attacker-controlled `repository.owner.login`/`organization.login` field, not the `repository.full_name` that handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC against using `repository_owner`, which is read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while the actual event handlers act on `repository.full_name` (a separate, independently attacker-controlled field in the same body). Because these two fields are never checked for consistency, an attacker who legitimately controls (or has been granted) a GitHub App/webhook secret for **their own** organization "A" can forge a webhook whose signature is valid for org A's secret, but whose `repository.full_name` names a stack belonging to a completely different, victim organization "B".

### Finding Description
`verify_signature` computes the signing key based only on the owner login sub-field: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization: ...)` resolves to a per-organization `GithubApp` config (secret, app id, etc.), each configured independently, as shown in the multi-org secrets template: [3](#0-2) 

Once the signature check passes, the request body is dispatched unmodified to the registered handlers: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` from a *different* field of the same payload — `repository.full_name` — with no cross-check against the `repository.owner.login`/`organization.login` value that was used to pick the signing secret: [5](#0-4) [6](#0-5) 

Handlers such as `PushHandler` (triggers `stack.sync_github`), `StatusHandler` (writes CI `Commit::Status` records that gate deploy safety and merge-queue eligibility), and `CheckSuiteHandler` (schedules check-run refreshes) act purely on `repository_name = payload.dig('repository','full_name')`: [7](#0-6) [8](#0-7) [9](#0-8) 

**The equality that is broken:** `verified organization (used to select webhook_secret) == repository whose data the handlers write`. GitHub itself always sends consistent `organization.login`/`repository.owner.login` and `repository.full_name` fields because it generates the payload server-side and signs it with the secret tied to that specific installation/repo. Shipit's controller, however, never asserts this consistency itself — it trusts the attacker-supplied JSON to tell it which secret to validate against, then trusts a different field of the same JSON to tell it which repository to mutate.

### Impact Explanation
If Shipit is configured for more than one GitHub organization (a documented, supported multi-tenant configuration, see `config/secrets.development.shopify.yml`), any actor who possesses (or can obtain) a valid webhook secret for **one** configured org can forge `status`, `push`, and `check_suite` events claiming to originate from a **different** org's repository, by setting `repository.owner.login`/`organization.login` to their own org (so the signature check passes) while setting `repository.full_name` to `victim-org/victim-repo`. This lets the attacker:
- Inject fabricated commit statuses via `StatusHandler#process` → `Commit#create_status_from_github!`, which is used to gate CI-required checks that block/allow deploys and the merge queue.
- Trigger `PushHandler`/`CheckSuiteHandler` side effects (`sync_github`, `schedule_refresh_check_runs!`) against a repository the attacker has no legitimate write access to.

This can lead to an unauthorized deploy or merge decision being taken based on forged CI signal for a repository the attacker does not control, which falls under the Critical "unauthorized deploy, rollback or merge" category.

### Likelihood Explanation
Exploitation requires the attacker to hold a valid webhook secret for at least one org configured in the same Shipit instance (e.g., because they administer that org's GitHub App/webhook settings) — this is not an anonymous, fully unauthenticated attack, but it is a cross-tenant boundary break that the signature-verification code is specifically supposed to prevent. In any Shipit deployment onboarding multiple, mutually-untrusted GitHub organizations (the documented multi-org secrets layout), this is directly reachable with no additional privilege beyond controlling one tenant's webhook secret.

### Recommendation
After verifying the HMAC signature, assert that the owner/organization used to select the secret matches the owner embedded in `repository.full_name` (and any `organization.login` field) before dispatching to handlers, e.g. reject the request if `repository_owner` and `params.dig('repository','full_name').split('/').first` diverge.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml`).
2. Attacker knows `attacker-org`'s webhook secret (e.g., they administer that org's GitHub App).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
   signed with `attacker-org`'s secret via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully.
5. `StatusHandler#process` runs unconditionally against `Commit.where(sha: ...)`, writing a forged `success` status for `victim-org/victim-repo`'s commit — despite the signature having only proven control of `attacker-org`'s secret.

      github_app = Shipit.github(organization: repository_owner)

      ].join(' '))
    end
