### Title
Webhook signature verified against `repository.owner.login`'s org while data lookup uses independently-controlled `repository.full_name`, letting a secretless org's webhook forge writes into a differently-owned repository's `PullRequest` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate against using `repository_owner` (`params.dig('repository','owner','login')`), while `AssignedHandler#repository`/`#pull_request` resolve the record to mutate using the independently attacker-supplied `params.repository.full_name`. Nothing ties these two values together, so a webhook whose `owner.login` names a Shipit-configured org with no `webhook_secret` set passes signature verification trivially, while `full_name` can point at a completely different, secret-protected org's already-onboarded repository/PR.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`repository_owner` (org used in `Shipit.github(organization: repository_owner).verify_webhook_signature`) **should equal** `params.repository.full_name.split('/').first` (org whose `Repository`/`PullRequest` row gets mutated) — but no code path asserts this.

Path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
2. `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) does `return true unless webhook_secret` — if the org configured under `repository_owner` in `secrets.github` has no `webhook_secret` set, any request (even with a bogus/absent `X-Hub-Signature`) is treated as verified.
3. Once through, `Handler.call` (app/models/shipit/webhooks/handlers/handler.rb:15-24) instantiates `AssignedHandler` with the full JSON payload — including a `params.repository.full_name` field that is completely independent of the `owner.login` used in step 1.
4. `AssignedHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:67-69) calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which downcases and does a plain `find_by(owner:, name:)` (app/models/shipit/repository.rb:53-56) — with no check that this owner matches `repository_owner` from step 1.
5. `AssignedHandler#pull_request` (assigned_handler.rb:53-65) finds an existing `Shipit::PullRequest` scoped only by `number` and `repository.id`.
6. `#process` (assigned_handler.rb:41-45) calls `pull_request.update(github_pull_request: params.pull_request)` if found — writing attacker-controlled PR metadata (head sha, ref, labels, assignees, title, etc.) into a record belonging to org B, having authenticated only against org A's (secretless) app config.

Existing guards do not catch this: `ExplicitParameters` only validates field types/presence, not cross-field consistency; `drop_unhandled_event`/`check_if_ping` are unrelated; there is no `require_permission!`/`User#authorized?` check in the webhook path at all (webhooks are unauthenticated by design, secured only by the HMAC signature); and the HMAC check is keyed off attacker-controlled `owner.login`, not off the repository actually being mutated.

### Impact Explanation
An attacker who can trigger a webhook delivery under an org that Shipit has configured without a `webhook_secret` can craft (or replay via any HTTP client, since the org has no secret, the "signature" header content is irrelevant) a `pull_request.assigned`/`unassigned` payload whose `repository.full_name` names a different, secret-protected, already-onboarded repository/PR of org B. This causes Shipit to overwrite that `PullRequest`'s `github_pull_request` field with attacker-controlled JSON for a repository the attacker never authenticated against — a cross-tenant write (one repo's/organization's payload mutating another's PR record), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any PR number/repo combination that already exists in Shipit's database, for as long as the secretless org configuration exists.

### Likelihood Explanation
Exploitation requires: (a) a Shipit deployment to have at least one org configured in `secrets.github` without a `webhook_secret` (a real-world misconfiguration, e.g., an org added for testing/onboarding that never had its secret set) — a precondition explicitly given in the audit — and (b) a target `Repository`/`PullRequest` row for org B already existing in Shipit (i.e., B previously onboarded and had this PR synced). Given those two preconditions, the attack cost is a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body; no secrets, sessions, or GitHub App credentials are needed. It is fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler`/`AssignedHandler`, enforce that the org used to select the webhook secret is the same org that owns the `Repository` being mutated: e.g., derive the target `Repository` first from `full_name`, then verify the signature using that repository's owner (not the payload's own `owner.login`), or explicitly assert `params.repository.full_name.split('/').first.casecmp?(repository_owner)` before dispatching to handlers. Additionally, treat a missing `webhook_secret` for a configured org as a hard misconfiguration error rather than an implicit "always verified" pass-through in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest plan (no live GitHub, uses `test/dummy` secrets fixtures):
1. Configure two orgs in the test secrets: org `A` with `webhook_secret` blank/absent, org `B` with a `webhook_secret` set.
2. Create `Shipit::Repository.create!(owner: 'b', name: 'repo')`, a `Stack` on it, and a `Shipit::PullRequest` with `number: 42`.
3. Build a `pull_request.assigned` payload where `payload['repository']['owner']['login'] = 'a'` and `payload['repository']['full_name'] = 'b/repo'`, `payload['number'] = 42`, with attacker-controlled `pull_request` fields (e.g., a forged `head.sha`).
4. POST to `/webhooks` with `X-Github-Event: pull_request` and an arbitrary/invalid `X-Hub-Signature` header.
5. Assert response is `200`/`204` (not `422`), proving `verify_signature` passed via org `A`'s missing secret — `assert_response :ok` (not `:unprocessable_entity`).
6. Reload the `PullRequest` for org `B` and assert its `github_pull_request['head']['sha']` now equals the attacker-supplied value — `assert_equal forged_sha, pull_request.reload.github_pull_request['head']['sha']` — demonstrating org `A`'s (secretless) signature check authorized a write to org `B`'s PR record.
7. Contrast: repeat with `full_name` pointing at a non-existent repo (current behavior) and assert the PR record is unchanged, showing the divergence is purely due to row existence, not any owner-consistency check.
