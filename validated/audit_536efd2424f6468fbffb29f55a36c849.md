### Title
Reserve-transfer-to-relay deny bypass via nested XCM instructions (missing `DenyRecursively` wrapper) - ([File: system-parachains/people/people-polkadot/src/xcm_config.rs])

### Summary
`people-polkadot`'s `Barrier` wraps `DenyReserveTransferToRelayChain` directly inside `DenyThenTry`, without the `DenyRecursively` wrapper that other system parachains in this same repository use for the identical deny rule. [1](#0-0)  By contrast, `bridge-hub-polkadot` and `bulletin-polkadot` explicitly wrap the same rule as `DenyRecursively<DenyReserveTransferToRelayChain>`. [2](#0-1) [3](#0-2) 

### Finding Description
`xcm-builder`'s `ShouldExecute` deny filters (such as `DenyReserveTransferToRelayChain`) operate on the top-level instruction slice of the message being executed. The dedicated `DenyRecursively<T>` combinator exists in `xcm-builder` precisely because a bare deny filter does not descend into `Xcm<Call>` programs nested inside instructions like `SetAppendix`, `SetErrorHandler`, or execute-with-origin style wrappers — it only pattern-matches the outer instruction sequence. The presence of `DenyRecursively` as a distinct, separately-applied wrapper in this same codebase (used only for `bridge-hub-polkadot` and `bulletin-polkadot`) is itself evidence that the bare filter is not recursive; otherwise the wrapper would serve no purpose.

On `people-polkadot`, the `Barrier` type only applies the bare, non-recursive `DenyReserveTransferToRelayChain` before falling through to `AllowTopLevelPaidExecutionFrom<Everything>` inside `WithComputedOrigin`. [1](#0-0)  An unprivileged, signed user can call `pallet_xcm::execute` because `ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>` and `XcmExecuteFilter = Everything` place no restriction on the instruction content. [4](#0-3)  An attacker can therefore submit a top-level XCM whose outer instructions look benign (e.g., a paid-execution wrapper satisfying `AllowTopLevelPaidExecutionFrom`), but which contains `SetAppendix`/`SetErrorHandler` payloads embedding `InitiateReserveWithdraw` targeting the Relay Chain followed by `DepositReserveAsset`/`DepositAsset` back to the Relay. Because the deny filter never inspects the nested program contents, the top-level scan finds no matching deny pattern and the message proceeds to the `DenyThenTry`'s allow-set, which permits it via `AllowTopLevelPaidExecutionFrom<Everything>`.

### Impact Explanation
If the nested reserve-withdraw/deposit sequence reaches the Relay Chain, it could induce the Relay to release DOT that is not actually reserve-backed by `people-polkadot` (system parachains treat DOT as teleported, not reserve-transferred, precisely because there is no genuine reserve backing on the parachain side). This creates a path toward unbacked DOT issuance / double-accounting between `people-polkadot` and the Relay Chain, matching the scoped impact of "unauthorized reserve-asset path bypass, potential double-accounting of DOT."

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: any signed account with enough DOT to pay execution/delivery fees can call `pallet_xcm::execute` with a hand-crafted `Xcm<RuntimeCall>` containing nested `SetAppendix`/`SetErrorHandler` instructions. No governance, root, or relayer cooperation is required, and the barrier's `WithComputedOrigin` / `AllowTopLevelPaidExecutionFrom<Everything>` step does not scan nested instruction content either. Exact severity ultimately also depends on Relay-side handling of an `InitiateReserveWithdraw` targeting itself (Relay's own barrier/reserve config might independently reject it), which is outside this file's scope and was not verified here.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` with `DenyRecursively` in `people-polkadot`'s `Barrier` (mirroring `bridge-hub-polkadot`/`bulletin-polkadot`):
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```
This should be applied consistently across all system parachains in this repo that currently use the bare filter (`people-kusama`, `asset-hub-polkadot`, `asset-hub-kusama`, `bridge-hub-kusama`, `coretime-polkadot`, `coretime-kusama`, `collectives-polkadot`, `encointer`).

### Proof of Concept
xcm-emulator test plan:
1. On `PeoplePolkadot`, fund a signed test account with DOT.
2. Construct `Xcm<RuntimeCall>` = `[WithdrawAsset(dot), BuyExecution, SetAppendix(Xcm([InitiateReserveWithdraw { reserve: Parent, xcm: Xcm([DepositReserveAsset { dest: Parent, .. }]) }])), DepositAsset(..)]` (or equivalent nesting via `SetErrorHandler`).
3. Call `PolkadotXcm::execute(signed_origin, xcm, weight_limit)`.
4. Assert: `DenyReserveTransferToRelayChain`/`Barrier::should_execute` allows the top-level message (execution does not fail with `Barrier`/`ProcessMessageError`), proving the deny rule was bypassed at the outer level.
5. Assert on the Relay Chain mock/emulated chain: verify whether the nested `InitiateReserveWithdraw`/`DepositReserveAsset` executed and altered DOT balances inconsistent with actual backing, confirming the double-accounting impact end-to-end.
