This confirms the vulnerability. The security binding is fully broken by design: `verify_signature` at `app/controllers/shipit/webhooks_controller.rb:24-30` selects `Shipit.github(organization: repository_owner)` using `repository_owner` from `params.dig('repository', 'owner', 'login')`, while `ClosedHandler#repository` at `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53` resolves the target using `params.repository.full_name` — an entirely separate, independently attacker-controlled field in the same JSON body. There is no cross-check anywhere in the request path (`WebhooksController#create`, `ExplicitParameters` schema in `ClosedHandler`, or `ReviewStackAdapter#archive!`) that `repository.owner.login` is consistent with `repository.full_name`'s owner segment.### Title
Webhook signature owner is decoupled from the repository the handler mutates, letting one org's signed webhook archive another org's review stack - (File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook request against the `GitHubApp` selected by `params.dig('repository','owner','login')`, but `ClosedHandler#repository` resolves the actual `Shipit::Repository` to mutate from the unrelated `params.repository.full_name` field of the same JSON body. Because these two fields are independently attacker-controlled within a single request whose raw bytes only need to match one org's HMAC secret, an operator of a legitimately-configured tenant org can forge a request that authenticates as their own org but targets and archives another tenant's review stack.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `organization_used_for_signature (repository_owner = params.dig('repository','owner','login'))` MUST equal `organization_owning_mutated_repository (params.repository.full_name.split('/').first)`. Nothing enforces this.

Path:
- `WebhooksController#create` parses `request.raw_post` into `params` and dispatches to handlers by `X-Github-Event` [1](#0-0) .
- `verify_signature` runs as a `before_action`, selecting `Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')`, then verifies the raw body bytes against that org's `webhook_secret` [2](#0-1) [3](#0-2) .
- `GitHubApp#verify_webhook_signature` only checks the HMAC-SHA1 of the raw message against `@webhook_secret` for that one organization; it has no notion of which repository the payload claims to be about [4](#0-3) .
- `ClosedHandler` requires `repository.full_name` as a plain string in its `ExplicitParameters` schema, with no format/consistency validation tying it to `repository.owner.login` [5](#0-4) .
- `ClosedHandler#repository` resolves the actual DB repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, entirely independent of the field used for signature verification [6](#0-5) .
- `ClosedHandler#process` then calls `review_stack.archive!`, scoped to `repository.review_stacks` of that resolved repository [7](#0-6) .
- `ReviewStackAdapter#archive!` finds the stack by `environment: "pr#{params.number}"` within that scope and calls `stack.remove_from_provisioning_queue`, `stack.deprovision`, `stack.archive!(user)` [8](#0-7) [9](#0-8) .

Multi-org support is a first-class, documented feature: `Shipit.github_organizations`/`Shipit.github_app_config` shows each org gets its own independent `webhook_secret` under `secrets.github.<org>` [10](#0-9) , exactly as illustrated in `test/dummy/config/secrets_double_github_app.yml` [11](#0-10)  and `docs/setup.md`'s "Using Multiple Github Applications" section. Any org admin who legitimately administers their own tenant's GitHub webhook (and thus knows their own org's `webhook_secret`, which they themselves configured on GitHub's side) satisfies the "unprivileged attacker" bar with respect to other tenants — they hold no secret belonging to the victim org.

Exploit flow:
1. Attacker controls `evil-org`, a legitimate Shipit tenant, and knows `evil-org`'s `webhook_secret`.
2. Attacker crafts a JSON body satisfying `ClosedHandler`'s schema: `action: "closed"`, `number: N`, a full `pull_request` object, `sender.login`, but sets `repository.owner.login = "evil-org"` and `repository.full_name = "victim-org/victim-repo"`.
3. Attacker computes `sha1=HMAC(evil-org_secret, raw_body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: pull_request`.
4. `verify_signature` looks up `Shipit.github(organization: "evil-org")`, verifies successfully — this is the attacker's own valid secret against their own crafted bytes.
5. `ClosedHandler` looks up the repository via `full_name = "victim-org/victim-repo"`, finds the real victim repository/review stack for PR `N`, and archives + deprovisions it.

No existing guard catches this: `verify_signature` never compares `repository_owner` to `repository.full_name`'s owner segment; the `ExplicitParameters` schema in `ClosedHandler` only checks types/presence, not cross-field consistency; `drop_unhandled_event` and `check_if_ping` are irrelevant; there's no `force_github_authentication`/`User#authorized?`/`require_permission!` involved since webhooks bypass session/API-token auth entirely by design.

### Impact Explanation
A tenant with no access to `victim-org` can silently archive and deprovision `victim-org`'s review stack for any PR number they can guess/enumerate, causing loss of a running preview environment and an unauthorized state mutation on a repository/stack that never authenticated the request. This matches the Critical category "a payload for one repository mutating another's stack" — it is a cross-tenant authentication/authorization boundary bypass, repeatable against any PR number and any repository owned by any other tenant, as long as the attacker knows one valid `webhook_secret` for their own tenant.

### Likelihood Explanation
Preconditions: a multi-org Shipit deployment (`Shipit.github_organizations` with 2+ orgs, each with distinct `webhook_secret` — a documented, supported configuration), a review stack existing for `victim-org/victim-repo` PR `N`, and the attacker controlling any one of those orgs as a legitimate tenant. Attacker cost is minimal — a single crafted HTTP POST with a correctly-computed HMAC using a secret they legitimately possess for their own org. This is fully repeatable against arbitrary PR numbers of any co-tenant repository. On single-org deployments (the common case, where `github_default_organization` is used and there's only one webhook secret) this specific cross-org vector doesn't apply, but the underlying flaw — no binding between the verified signature's org and the mutated repository — is architectural to any multi-tenant setup.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler's `repository` resolution), enforce that the organization derived from `params.repository.full_name` (i.e., the owner segment) matches `repository_owner` used to select the signing `GitHubApp`, rejecting the request (422) on mismatch before any handler processes it. Alternatively, scope `Shipit::Repository.from_github_repo_name` lookups (and all similar lookups in `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, etc.) to only repositories belonging to the verified `repository_owner` organization.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure test secrets with two orgs, `evil-org` and `victim-org`, each with a distinct `webhook_secret` (mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. Create `Shipit::Repository` for `victim-org/victim-repo` and a `Shipit::ReviewStack` with `environment: "pr#{N}"`, `archived_since: nil`.
3. Build a JSON body satisfying `ClosedHandler`'s schema with `repository.owner.login = "evil-org"`, `repository.full_name = "victim-org/victim-repo"`, `action: "closed"`, `number: N`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", evil_org_secret, body)`.
5. `post :create, body: body, as: :json` with headers `X-Github-Event: pull_request`, `X-Hub-Signature: signature`.
6. Assert response is `:ok` (signature verified against `evil-org`).
7. Assert `victim_review_stack.reload.archived?` is `true` — proving the equality `organization_used_for_signature == organization_owning_mutated_repository` was violated (`"evil-org" != "victim-org"`) yet the mutation still occurred.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
