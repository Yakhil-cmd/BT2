## Analysis

The Netty advisory describes a case where an externally-supplied packet is only partially validated before being handed to a native (non-JS/non-JVM-memory-safe) component — the native `SSLEngine` — which then crashes because the packet doesn't conform to what the native code assumes.

The closest reachable analog in `ocore--012` is the PEM public-key parsing/validation path in `signature.js`, which is directly reachable from **oscript formula evaluation** (`is_valid_sig` / `vrf_verify`), i.e. from any AA trigger sender who controls a formula argument, and passes attacker-supplied bytes into Node's native OpenSSL bindings (`crypto.createVerify(...).verify()`).

### Root cause

`validateAndFormatPemPubKey()` only performs a shallow structural check on the DER blob before re-wrapping it as a PEM and handing it to native crypto code:

- It checks the outer `SEQUENCE` tag, the length-tag branch (`0x7F`/`0x81`/`0x82`), and an inner algorithm-identifier `SEQUENCE` with one of a fixed set of allowed lengths (13/16/19/20). [1](#0-0) 
- It computes `typeIdentifiersHex` purely from byte offsets/lengths taken directly from attacker-controlled header bytes, with no bound-check against the actual remaining buffer length before slicing. [2](#0-1) 
- For ECDSA it only checks an aggregate length equation, never validating the actual inner BIT STRING/public-key encoding structure byte-by-byte. [3](#0-2) 
- Once these superficial checks pass, the *original*, unvalidated attacker bytes (not a re-derived/sanitized key) are wrapped back into PEM headers and returned. [4](#0-3) 

This formatted key is then fed straight into the native OpenSSL binding via `crypto.createVerify('SHA256').verify({key: pem_key}, ...)`: [5](#0-4) 

The JS-level `try/catch` around this call only protects against JS exceptions thrown by the binding — exactly like a JVM `try/catch` cannot protect against a native SSLEngine crash. If the underlying native ASN.1/key parser in OpenSSL (invoked through Node's `crypto` C++ bindings) mishandles a structurally-passing-but-semantically-malformed DER blob (correct outer tag, correct algorithm OID/length, but corrupted inner key material or length fields, e.g. crafted via the `identifiersLength` bytes), it can crash the process outside of JS exception handling — the same failure class as the Netty advisory (validation performed at a shallow/structural level while the payload is passed on to native code that assumes fully-valid input).

### Reachability

`is_valid_sig`/`vrf_verify` are oscript operators evaluatable inside any AA definition triggered by an untrusted trigger sender, with the PEM key argument fully attacker-controlled: [6](#0-5) [7](#0-6) 

Since AA trigger validation runs on every full node processing the unit, a crafted PEM key that crashes the node's native crypto layer during `validateAndFormatPemPubKey`/`verifyMessageWithPemPubKey` would crash every full node that attempts to validate that AA trigger — a network-wide denial of service preventing confirmation of new units, matching the accepted impact bucket ("a network unable to confirm new units").

### Caveat

I was not able to find a concrete Node/OpenSSL CVE reproduction inside this repository that demonstrates an actual native-level crash from a malformed DER key passed through `crypto.createVerify`. The vulnerability class match is strong (shallow structural validation before handing bytes to native crypto code), but proving actual native-crash exploitability requires testing against the specific Node.js/OpenSSL version this project bundles, which is outside what static code review here can confirm.

### Title
Insufficiently validated PEM/DER public key passed to native crypto binding in `is_valid_sig`/`vrf_verify` - (File: signature.js)

### Summary
`signature.js`'s `validateAndFormatPemPubKey()` performs only shallow, offset-based structural checks on an attacker-supplied DER-encoded public key (outer tag, algorithm-OID length, aggregate length) before repackaging the *original* unvalidated bytes as PEM and handing them to Node's native OpenSSL bindings via `crypto.createVerify().verify({key: pem_key}, ...)`. This mirrors the Netty class of bug: validation is done at a structural/header level while the actual payload passed to native code is not fully sanitized, so malformed-but-header-plausible input can reach native parsing code that assumes well-formed data.

### Finding Description
`validateAndFormatPemPubKey` (`signature.js:117-188`) validates only the outer `SEQUENCE` tag, the algorithm-identifier length field, and an aggregate byte-length equation for ECDSA keys; it never validates the inner key-material encoding (e.g. BIT STRING tag/length/unused-bits byte, actual coordinate encoding) byte by byte. It then reconstructs the PEM from the *original* base64 content and returns it as "safe" to `verifyMessageWithPemPubKey`, which feeds it into `crypto.createVerify('SHA256').verify({key: pem_key}, signature, encoding)` — code that ultimately calls into the native OpenSSL/BoringSSL key-parsing routines bundled with Node.js. A JS `try/catch` around this call cannot protect against a genuine native crash (segfault/abort) in the underlying C library, only against JS-level exceptions.

### Impact Explanation
`is_valid_sig` and `vrf_verify` are oscript operators evaluatable from AA trigger data fully controlled by any trigger sender. AA trigger validation is performed by every full node processing the triggering unit. If a crafted DER/PEM blob that passes the shallow structural checks reaches a native-level parsing bug in the Node/OpenSSL binding, every full node validating that trigger crashes — a network-wide denial of service preventing confirmation of new units.

### Likelihood Explanation
Exploitability depends on the specific OpenSSL/Node.js version's native key-parsing robustness against malformed-but-structurally-plausible DER; this cannot be conclusively proven via static review of the JS repository alone, so likelihood is assessed as uncertain pending native-library-specific testing, though the reachable path (untrusted AA trigger data -> `is_valid_sig`/`vrf_verify` -> native crypto call) is unambiguous and requires no special privileges.

### Recommendation
Fully validate the DER structure of the public key (proper ASN.1 parsing of every nested field, not just outer tag/length heuristics) before handing it to native crypto APIs, or use a dedicated, memory-safe ASN.1 library to normalize/re-encode the key material rather than passing through attacker-controlled bytes unmodified.

### Proof of Concept
Not conclusively demonstrable via static analysis; would require constructing a DER blob whose outer `SEQUENCE` tag, algorithm-identifier OID, and aggregate length match one of the entries in `objSupportedPemTypes` (e.g. `secp256k1`/RSA) while its inner key-material encoding is corrupted, then invoking `is_valid_sig(message, corrupted_pem_key, signature)` inside an AA trigger and observing node behavior when the key reaches `crypto.createVerify().verify()`.
