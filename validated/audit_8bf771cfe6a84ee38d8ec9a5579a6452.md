## Finding

### Title
Unauthenticated `new_shared_address` handler lets any paired correspondent register a spoofed "shared address" for a victim's wallet without genuine multi-party consent - ([File: wallet_defined_by_addresses.js])

### Summary
The device-message handler for `new_shared_address` accepts and permanently stores an address definition supplied entirely by the remote peer, the same class of bug as the Teller `commitCollateral` issue: the function performs a structural/hash validity check on attacker-controlled data but never validates that the caller is a legitimate party who should be allowed to bind the recipient's own address into this new shared/multisig arrangement.

### Finding Description
The wallet message dispatcher forwards any `new_shared_address` message from a paired correspondent straight into `walletDefinedByAddresses.handleNewSharedAddress` without any authorization or provenance check: [1](#0-0) 

`handleNewSharedAddress` only checks that:
1. `body.address` really is the c-hash of `body.definition` (structural integrity), and
2. every `["address", ...]` leaf in the definition has a matching entry in `body.signers`. [2](#0-1) 

It then calls `determineIfIncludesMeAndRewriteDeviceAddress`, which only confirms that *some* address referenced in the attacker-supplied definition happens to belong to the receiving wallet (`my_addresses` or `shared_addresses`) - it does not verify that the sender (`from_address`) is a genuine counterparty who should be co-owning that specific new address, nor that the user ever initiated or approved creation of this shared address: [3](#0-2) 

If that loose check passes, `validateAddressDefinition` performs only a syntactic/complexity validation of the oscript definition (not a semantic "is this actually a safe multisig" check), and the address is unconditionally persisted and even auto-forwarded to the victim's other cosigner devices: [4](#0-3) [5](#0-4) 

Nothing requires that the definition actually enforces joint control. For example, an attacker can construct `["or", [["address", attacker_address], ["address", victim_address]]]`. Because the victim's address is referenced somewhere in the tree, `determineIfIncludesMeAndRewriteDeviceAddress` succeeds, and the whole thing is silently stored as a legitimate-looking "shared address" the victim's wallet now tracks and displays as a wallet the victim participates in - exactly the same "commit-on-behalf-of-victim with only a superficial check" pattern as the Teller report, except here the wallet's own name-space for the victim's identity is what gets hijacked rather than a `_bidId`.

### Impact Explanation
A victim's wallet UI/backend will list an attacker-crafted address as one of the user's own "shared addresses" (multisig wallets) purely because the attacker referenced the victim's real address inside an arbitrary boolean oscript definition. If the definition is (or is disguised to look like) an `and`/`r of set` multisig but actually contains an `or` branch letting the attacker spend unilaterally, funds a victim later sends to that address (believing it to be jointly controlled) can be unilaterally drained by the attacker. This is unauthorized loss of funds triggered purely by an unprivileged paired correspondent sending a crafted device message - no compromise of keys, hub, or node required.

### Likelihood Explanation
Any device that is paired as a correspondent (a routine, low-trust pairing achievable via a shared pairing code, e.g. posted publicly or exchanged casually) can send this message at will; the handler processes it automatically with no user confirmation step and no verification that the sender is a legitimate party to a shared address involving the victim's key. The only real defense is that a careful user must notice the "shared address" definition looks wrong before funding it — a purely social/UI-side mitigation, not an on-chain/backend safeguard.

### Recommendation
`handleNewSharedAddress` should not silently accept and store address definitions pushed by an arbitrary correspondent. At minimum:
- Require that acceptance of a new shared address only proceed through the existing consensual flow (`createNewSharedAddressByTemplate` / `approvePendingSharedAddress`), where the local user explicitly initiated or approved the specific definition template beforehand, rather than accepting a fully-formed, attacker-chosen definition out of band.
- If unsolicited `new_shared_address` messages must be supported, add explicit user confirmation before persisting the definition, and/or reject definitions where the sender's own address does not have full authentifying control matching every path in the tree (so a party cannot construct an `or`-based bypass while referencing the victim's key).

### Proof of Concept
1. Attacker pairs with victim's device as a normal correspondent.
2. Attacker computes `arrDefinition = ["or", [["address", ATTACKER_ADDR], ["address", VICTIM_ADDR]]]` and `address = objectHash.getChash160(arrDefinition)`.
3. Attacker sends a `new_shared_address` message: `{address, definition: arrDefinition, signers: {"r.0": {address: ATTACKER_ADDR, device_address: ATTACKER_DEVICE}, "r.1": {address: VICTIM_ADDR, device_address: VICTIM_DEVICE}}}`.
4. `handleNewSharedAddress` on the victim's node passes all its checks (hash matches, signer paths match, victim's address is referenced) and calls `addNewSharedAddress`, inserting the address into `shared_addresses`/`shared_address_signing_paths` and forwarding it to the victim's other cosigner devices as a legitimate shared address.
5. If the victim later funds this address believing it requires both signatures, the attacker alone can spend the funds via the `or` branch.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");

						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)

	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
