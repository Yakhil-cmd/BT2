## Analysis

This confirms the full attack chain, including the highest-impact variant: `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) trusts the `organization`, `team`, and `member` fields of the webhook payload to create/find a `Team` and add a `User` as a member via `team.add_member(member)`, and `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants application access based on membership in `Shipit.github_teams`. Combined with the signature-selection flaw in `WebhooksController`, this allows privilege escalation into `Shipit.github_teams` authorization.

### Title
Webhook organization used to select the verifying signature secret is decoupled from the organization/repository acted upon, allowing forged webhooks and team-membership escalation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) is used to verify the `X-Hub-Signature` HMAC based on `repository_owner`, a value read directly from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), *before* the body is otherwise validated. The `create` action then dispatches the very same raw, attacker-controlled `params` hash to event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), and those handlers independently trust other fields of the same payload — e.g. `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, and `MembershipHandler` reads `params.organization.login`, `params.team`, and `params.member.login` — to decide which `Stack`/`Repository`/`Team`/`User` record to mutate.

Because Shipit supports multiple GitHub organizations, each configured with its own (optional) `webhook_secret` (`lib/shipit.rb:170-200`, `docs/setup.md:30`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no secret is configured (`lib/shipit/github_app.rb:76-83`: `return true unless webhook_secret`), an attacker can target any organization in the multi-org configuration that has no `webhook_secret` set. By setting `repository.owner.login` (or `organization.login`) to that unsecured organization while setting the actual mutated fields (`repository.full_name`, `team`, `organization.login` inside `membership_params`, `member.login`) to reference a *different*, properly-secured organization/repository/team, the attacker bypasses signature verification entirely for actions targeting the secured organization.

### Finding Description
The equality that should hold is:
`organization whose secret authenticated the request == organization/repository/team that the handler mutates`

Before the fix, the code allows:
`organization whose secret authenticated the request (from repository.owner.login / organization.login, chosen to be a no-secret org) != organization/repository/team actually written (from repository.full_name / organization.login inside the handler-specific payload, referencing a secured org)`

Concretely:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` and calls `Shipit.github(organization: repository_owner)`.
- `Shipit.github` (`lib/shipit.rb:170-181`) looks up `github_app_config(organization)` when the instance is configured with multiple organizations (`TOP_LEVEL_GH_KEYS` check, `lib/shipit.rb:183-188`), meaning each org can have an independent `webhook_secret`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) trivially returns `true` when that org's `webhook_secret` is blank — a documented "optional" setting (`docs/setup.md:30`).
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) forwards the *entire unmodified* `params` (the same JSON body whose `repository.owner.login`/`organization.login` was used only for secret selection) to handlers such as `Handlers::PushHandler`/`Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and `Handlers::MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`), which look up the actual `Repository`/`Team`/`User` records to write using *other* fields in the same body.
- Since nothing enforces that `repository.owner.login`/`organization.login` used for auth matches the `repository.full_name`/`organization.login`/`team` used for the mutation, an attacker who knows only that one configured organization lacks a webhook secret can forge events for an entirely different, secured organization's repositories, stacks, or teams.
- The most severe consequence is via `MembershipHandler`: `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) adds an arbitrary GitHub login (auto-vivified via `User.find_or_create_by_login!`) to any `Team` record, and `User#authorized?` (`app/models/shipit/user.rb:80-82`) grants application-wide access based on membership in `Shipit.github_teams`. This lets an unauthenticated attacker add an attacker-controlled account to an authorized team, achieving authentication/authorization bypass without ever having a Shipit session, ApiClient token, or any organization's `webhook_secret`.

### Impact Explanation
This crosses the "organization authenticated versus the repository/team that is written" boundary explicitly called out as in-scope. The concrete outcome — an unauthenticated actor forging a `membership` webhook to add an arbitrary GitHub login to a `Team` that is a member of `Shipit.github_teams`, thereby making that login `authorized?` and able to log in via the ordinary GitHub OAuth flow with full application access — is an escalation into `Shipit.github_teams` authorization, matching the High-severity impact category. A lesser but still real consequence (forged `push`/`status`/`check_suite` events against a secured repository's `Stack` via `PushHandler`/`StatusHandler`/`CheckSuiteHandler`) constitutes unauthenticated forgery of stack state changes.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment be configured with more than one GitHub organization (a documented, supported configuration, `lib/shipit.rb:190-200`) and that at least one of those organizations has no `webhook_secret` configured — an explicitly "optional" setting per `docs/setup.md:30`, and a plausible operational state for a newly added or low-priority organization. No credentials, sessions, or tokens are required from the attacker; the `/webhooks` endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`, `app/controllers/shipit/webhooks_controller.rb:5`).

### Recommendation
Do not let handlers trust fields (`repository.full_name`, `organization.login`, `team`) independent from the field used to select/verify the signing secret. Either (a) require every organization in a multi-org configuration to have a non-blank `webhook_secret` and refuse to boot/serve requests otherwise, (b) after signature verification, re-derive and cross-check that `repository.owner.login`/`organization.login` used for secret selection matches the organization implied by `repository.full_name` and any nested `organization`/`team` fields before dispatching to handlers, or (c) verify the signature against every configured organization's secret rather than one selected from attacker-controlled payload content, and only accept the event if it matches the org actually referenced by the mutated resource.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `secure-org` (with `webhook_secret: "s3cret"`) and `open-org` (with `webhook_secret` unset).
2. POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature` (or an arbitrary value), and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "secure-org/some-repo" },
  "action": "added",
  "team": { "id": <id of a Team belonging to Shipit.github_teams>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "secure-org" },
  "member": { "login": "attacker-github-login" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`, whose `verify_webhook_signature` returns `true` unconditionally because `open-org` has no `webhook_secret`.
4. `MembershipHandler#process` runs using `organization.login = "secure-org"` and `team`/`member` fields, adding `attacker-github-login` to the `secure-org` team — even though only `open-org`'s (absent) secret was checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
