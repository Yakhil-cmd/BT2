### Title
Webhook signature/organization confusion allows cross-organization stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured for multiple GitHub organizations (per `docs/setup.md`'s "Using Multiple GitHub Applications"), the webhook signature is validated using a `webhook_secret` selected from the *payload body itself*, not from any transport-level identity. Since each organization admin sets up (and therefore knows) their own App's `webhook_secret`, an attacker who administers Org A's GitHub App can forge a webhook payload whose `repository.owner.login`/`organization.login` says "Org A" (so Shipit picks Org A's secret to verify, which the attacker knows), while the payload's `repository.full_name` field—used by every event handler to locate the target `Stack`—points at an entirely different org/repo (Org B) that the attacker has no access to.

### Finding Description
`WebhooksController#verify_signature` derives the org used to select the HMAC secret from attacker-controlled JSON fields in the same request body it is trying to authenticate: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up per-org secrets from `secrets.github`, one entry per organization (`lib/shipit.rb`): [3](#0-2) 

Each organization's `webhook_secret` is a value chosen by that organization's own GitHub App owner at App-creation time (per `docs/setup.md`), not a value controlled or guaranteed unique by Shipit's operators: [4](#0-3) 

Once the signature check passes (using the secret matched to `repository_owner`, the org the attacker actually controls), every downstream `Webhooks::Handlers::Handler` resolves the target `Stack` purely from a **different**, independently-controlled JSON field: `repository.full_name`: [5](#0-4) 

For example the push handler acts directly on whatever stacks match that `full_name`: [6](#0-5) 

and pull-request handlers similarly resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)`: [7](#0-6) 

**The broken binding**: the HMAC verification proves "this request was authorized by whoever controls the App installed for `repository.owner.login`", but `repository.owner.login` and `repository.full_name` are two independently attacker-writable fields inside the very payload the signature covers. Nothing ties the organization whose secret validated the signature to the organization that actually owns the repository being acted upon. An attacker who legitimately owns/administers Org A's GitHub App (and therefore knows Org A's `webhook_secret`, which they chose themselves) can sign a payload declaring `repository.owner.login: "org-a"` (to pick a secret they know) but `repository.full_name: "org-b/some-repo"` (to target an unrelated stack).

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary described in scope. Concretely, with a self-known secret an attacker in Org A can, without ever touching Org B's App or repository:
- Trigger `GithubSyncJob`/`CacheDeploySpecJob` for Org B's stacks (`PushHandler`), forcing Shipit to re-fetch and re-cache `shipit.yml` at an attacker-chosen `expected_head_sha`.
- Forge commit `Status` updates for Org B's commits (`StatusHandler`), which several other subsystems (CI gating, `deployable?`, merge queue) trust to decide whether a commit is safe to deploy.
- Archive/unarchive Org B's review stacks, or manipulate PR label-driven provisioning logic (`PullRequest::LabeledHandler`, `ClosedHandler`, etc.), causing deprovisioning/reprovisioning actions to run against infrastructure the attacker has no right to touch.
- Manipulate GitHub team membership records via `MembershipHandler` if `organization.login` is similarly spoofed relative to `team`/`member` data.

This is a cross-repository/cross-organization write achieved purely by knowing a secret the attacker legitimately possesses for their own, unrelated organization — i.e., an unauthorized write/deploy-adjacent action performed outside the attacker's authorized organization boundary, satisfying the "cross-repository writes" High/Critical impact bar. It does not require any Shipit session, API token, or GitHub App private key — only that the deployment operates ≥2 GitHub organizations (a documented, supported configuration), and that the attacker administers one of them.

### Likelihood Explanation
Medium: requires a multi-organization Shipit deployment (explicitly documented and supported) where the attacker legitimately administers at least one configured GitHub organization/App. This is a realistic scenario for shared/self-service Shipit installations serving multiple teams or business units, each with its own onboarded GitHub organization. No collusion or privileged Shipit credentials are needed — only the attacker's own, self-chosen `webhook_secret`.

### Recommendation
Do not select the verification secret from data inside the unauthenticated payload. Options:
- Verify the signature against every configured organization's secret (not just the one implied by the payload), and only proceed if a match is found; **then** independently re-validate that `repository_owner`/`repository.full_name`'s owner matches the organization whose secret validated the signature before dispatching to handlers.
- Bind the webhook route to a specific organization (e.g. `/webhooks/:organization`) so the secret is selected from trusted routing configuration, not from the request body, and compare that route-bound organization against `repository.full_name`'s owner as a sanity check before handler dispatch.
- At minimum, after selecting `github_app` via `repository_owner`, assert that `params.dig('repository','full_name')&.split('/')&.first == repository_owner` (case-insensitively) and reject (422) on mismatch.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `org-a` and `org-b`, per the documented multi-app `secrets.yml` schema (`docs/setup.md`), each with Shipit stacks for repositories they own.
2. As the administrator of `org-a`'s GitHub App (attacker), craft a JSON payload for the `push` event:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "org-b/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a's webhook_secret, payload)>` — a value the attacker legitimately knows because they configured `org-a`'s App themselves.
4. POST this payload with `X-Github-Event: push` to Shipit's `/webhooks` endpoint.
5. `WebhooksController#verify_signature` resolves `repository_owner => "org-a"`, fetches `org-a`'s `GitHubApp`, and validates the signature successfully (since it was signed with `org-a`'s own known secret).
6. `PushHandler#process` then looks up stacks via `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org B's stack — an organization/repository the attacker never had legitimate access to — confirming the cross-organization write.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
