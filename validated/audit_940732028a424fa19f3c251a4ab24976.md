### Title
Webhook signature is verified against the wrong organization's secret, allowing cross-organization forged webhook events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`. [1](#0-0) [2](#0-1)  However, the actual handlers that act on the payload (e.g. `PushHandler`, PR handlers) resolve the target `Repository`/`Stack` using an entirely different field, `payload.dig('repository', 'full_name')`. [3](#0-2) [4](#0-3) 

In a multi-organization Shipit deployment, each organization has its own `webhook_secret` under `secrets.github.<org>` [5](#0-4) , selected via `Shipit.github(organization: repository_owner)`. This is the exact analog of the `calcDecrease` bug class: the value used to authenticate the request (`repository.owner.login`, which selects the *authenticating* org's secret) is not the same value the code subsequently trusts and acts on (`repository.full_name`, which determines the *repository actually written to*).

### Finding Description
`verify_signature` computes `repository_owner` and asks `Shipit.github(organization: repository_owner)` for a `GitHubApp` instance holding that organization's `webhook_secret`, then verifies the signature against that secret: [1](#0-0) . `Shipit.github` looks up `github_app_config(organization)` and constructs/caches a `GitHubApp` per organization key: [5](#0-4) .

Once signature verification passes, `create` dispatches the raw parsed JSON `params` to handlers without re-checking that the `repository.owner.login` used for authentication matches the `repository.full_name` the handler will act on: [6](#0-5) . Every handler resolves its target repository purely from `payload.dig('repository', 'full_name')`: [3](#0-2) , and `Repository.from_github_repo_name` blindly splits that string on `/` into owner/name with no cross-check against `repository.owner.login`: [7](#0-6) .

Because `repository.owner.login` and `repository.full_name` are two independently-attacker-controlled JSON fields in the same webhook body, an attacker who legitimately controls (or has compromised) the webhook secret for **organization A** can craft a payload where:
- `repository.owner.login` = `"A"` (or `organization.login` = `"A"`) → causes `verify_signature` to fetch organization A's `webhook_secret` and successfully validate the HMAC signed with that secret,
- `repository.full_name` = `"B/some-repo"` → causes the dispatched handler to look up and act on a stack belonging to organization **B**, an org this attacker has no legitimate access to.

This breaks the intended binding: `organization authenticated == organization/repository written`. Concretely this can be exploited via the `push` event/`PushHandler`, which calls `stack.sync_github(expected_head_sha: params.after)` on the resolved (attacker-chosen) stack [4](#0-3) , or via PR-event handlers that create/close review stacks for a repository resolved the same way (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`), e.g. `OpenedHandler#repository`: [8](#0-7) .

### Impact Explanation
This crosses the "organization authenticated versus repository written" boundary called out in scope: an entity that only has webhook-signing authority for its own GitHub organization can trigger sync/deploy-adjacent side effects (`sync_github`, review-stack creation/close, commit-status writes) against stacks belonging to a different organization tracked by the same Shipit instance. In a single-organization deployment this is not exploitable (there is only one webhook secret to choose from), but in the documented multi-org configuration (`docs/setup.md`/`config/secrets.development.example.yml` show `github.<org>.webhook_secret` per org) [9](#0-8)  this is a genuine cross-repository/cross-organization write using another organization's legitimately obtained credential, matching the High-severity category "escalation into `Shipit.github_teams` authorization" adjacent risk / cross-repository writes.

### Likelihood Explanation
Requires the attacker to already control (or have compromised) a `webhook_secret` for at least one organization configured on the Shipit instance — which is a plausible "unprivileged relative to other orgs" attacker in a multi-tenant Shipit deployment (e.g., a compromised or malicious org admin who owns their own GitHub App/webhook secret but not others'). No other privilege (no `ApiClient` token, no session, no GitHub App private key) is needed beyond that one secret, and the mismatch between `repository.owner.login` and `repository.full_name` is a simple crafted HTTP POST, so likelihood is moderate — gated primarily on whether the target deployment uses the multi-organization config.

### Recommendation
In `WebhooksController`, after signature verification succeeds, assert that the organization/owner used to select the signing secret is consistent with the repository the handlers will act on — e.g., derive `repository_owner` and enforce that `params.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to handlers, or have `Repository.from_github_repo_name` (or the `Handler#stacks` base method) require and validate the verified owner explicitly rather than trusting `full_name` alone.

### Proof of Concept
Conceptual PoC (multi-org Shipit configuration with orgs `orga` and `orgb`, each with distinct `webhook_secret`):
1. Attacker controls `orga`'s GitHub App / webhook secret (legitimately, e.g. as an org admin) but not `orgb`'s.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/target-repo"
  }
}
```
3. Attacker signs the raw body with `orga`'s `webhook_secret` and sets `X-Hub-Signature`.
4. `verify_signature` computes `repository_owner = "orga"`, fetches `Shipit.github(organization: "orga")`, and the HMAC check passes because it was signed with `orga`'s real secret. [1](#0-0) 
5. `create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("orgb/target-repo")` — an `orgb`-owned repository the attacker does not control — and calls `stack.sync_github(...)` on it. [3](#0-2) [4](#0-3) 

Note: I could not find any code path that cross-validates `repository.owner.login` against `repository.full_name`'s owner segment before handler dispatch, confirming the gap is unmitigated elsewhere in the reviewed files.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
