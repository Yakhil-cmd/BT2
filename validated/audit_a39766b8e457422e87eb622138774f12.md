### Title
Hookify plugin's PreToolUse/PostToolUse hooks fail open on timeout or error, allowing dangerous tool calls to bypass security gating - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The External Report describes a pattern where an attacker can cause a mandatory multi-step process to skip a critical step (by exhausting the resource budget available to it) while still receiving the outcome that step was supposed to gate. In `claude-code--017`, the `hookify` plugin's `PreToolUse`/`PostToolUse` hooks implement exactly this "fail-open on resource exhaustion" pattern: any exception, timeout, or import failure during rule evaluation results in the tool call being allowed rather than blocked.

### Finding Description
`pretooluse.py` is the gate that is supposed to run before every tool call (`Bash`, `Edit`, `Write`, `MultiEdit`) and can `deny` dangerous operations per user-configured rules loaded via `load_rules()`/`RuleEngine.evaluate_rules()`. [1](#0-0) 

Critically, the script wraps the entire rule-evaluation path in a broad `try/except Exception`, and its `finally` block unconditionally exits 0 regardless of whether the check ran, errored, or was interrupted: [2](#0-1) 

The same fail-open behavior is duplicated in `posttooluse.py`: [3](#0-2) 

This is compounded by the hook's configured `timeout: 10` in `hooks.json` — if rule evaluation (which loads and parses user `.local.md` rule files and runs `RuleEngine.evaluate_rules`) takes longer than 10 seconds for any reason (large/complex rule files, slow filesystem, or a maliciously crafted rule triggering pathological regex/parsing behavior), the process is killed by the harness's timeout enforcement rather than by the script itself: [4](#0-3) 

Just as in the Salty.IO `performUpkeep()` case — where forwarding only enough gas to complete steps 1–10 lets step 11 revert internally (caught by `try/catch`) while the caller still collects the reward — here, forcing `pretooluse.py`'s rule evaluation to exceed its 10s budget or throw an exception (e.g., via malformed/adversarial rule configuration or resource contention) causes the security check to be skipped, but the surrounding hook contract ("ALWAYS exit 0 — never block operations due to hook errors") still results in the tool call being approved and executed.

### Impact Explanation
`hookify`'s stated purpose is to let users configure `deny` rules for dangerous `Bash`/`Write`/`Edit`/`MultiEdit` operations (per the pattern documented in `plugins/plugin-dev/skills/hook-development/references/patterns.md`, Pattern 1: "Security Validation" — blocking writes to sensitive paths, `.env` files, path traversal, etc.). Since the LLM agent is the actor whose actions this hook is meant to constrain, and the PreToolUse hook is the trust boundary between "agent proposes an action" and "action is actually executed," a fail-open bypass here means a prompt-injected or otherwise compromised agent turn could get a would-be-denied dangerous command executed simply by causing (or waiting for) the rule engine to error or exceed 10 seconds — e.g., by crafting inputs that make `RuleEngine.evaluate_rules` slow or by tool_input that trips an unhandled exception path in rule matching. This directly maps to "concrete approval bypass" / "unauthorized shell/file action" per the validation criteria.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the user to have installed/enabled the `hookify` plugin with deny-rules configured, and (b) an attacker (malicious prompt content, adversarial file content, or a crafted `tool_input`) able to make rule evaluation slow enough to exceed the 10s timeout or throw an exception. I was not able to fully inspect `plugins/hookify/core/rule_engine.py` (the grep matched but full content could not be retrieved in this session) to confirm a concrete trigger such as a ReDoS-prone regex or an unhandled parse error — this should be verified directly by reading that file, along with `config_loader.py`, before treating this as fully confirmed. The design comment "ALWAYS exit 0 — never block operations due to hook errors" is an explicit, acknowledged design choice similar to how the Salty.IO team "acknowledged" their finding rather than disputing it, which strengthens confidence that this fail-open behavior is real and intentional rather than a mere hypothesis.

### Recommendation
- Change the default hook behavior for security-relevant PreToolUse hooks (like `hookify`) to fail **closed** (deny or `ask`) on timeout/exception when deny rules exist for the matched event, rather than silently allowing the operation.
- At minimum, surface a `systemMessage`/`ask` decision instead of silent `allow` when rule evaluation errors, so a human is put in the loop rather than the tool call proceeding unchecked.
- Increase robustness/complexity bounds of `RuleEngine.evaluate_rules` (bounded regex evaluation, input size caps) so legitimate rule sets cannot be forced past the 10s budget by adversarial input.
- Document and test the "hook failure = deny for security-classified rules" contract explicitly.

### Proof of Concept
1. Install the `hookify` plugin with a `deny` rule preventing e.g. writes to `.env` or execution of destructive `rm -rf` patterns (per Pattern 1 in `plugins/plugin-dev/skills/hook-development/references/patterns.md`).
2. Craft a tool call (`Write`/`Bash`) whose `tool_input` or accompanying rule-file state causes `RuleEngine.evaluate_rules` in `plugins/hookify/core/rule_engine.py` to either (a) raise an exception, or (b) run for >10 seconds (the hook's configured timeout in `plugins/hookify/hooks/hooks.json`).
3. Observe that `pretooluse.py`'s `except Exception` branch (or the OS-level timeout kill) results in the process still emitting/exiting 0 with no `deny` decision, per the `finally: sys.exit(0)` contract, so the otherwise-blocked dangerous tool call is executed. [2](#0-1) 

Note: I could not retrieve the full contents of `plugins/hookify/core/rule_engine.py` in this session (index/tool limitation) to pin down the exact code path that could be forced to throw or run long; a Devin session with full filesystem access should read that file and `config_loader.py` directly to confirm and refine the concrete trigger for step 3.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
```
