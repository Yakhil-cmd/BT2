### Title
Arbiter contract shared-address spending condition trusts any historical `CONTRACT_<hash>` data-feed posting instead of the arbiter's final/appealed decision, enabling double payout of disputed funds - (File: `arbiter_contract.js`)

### Summary
The peer-to-peer arbiter contract flow builds a shared address whose spending condition allows either party to withdraw the disputed amount once the arbiter posts a `data_feed` message `CONTRACT_<hash>=<winner_address>`. That condition is evaluated with the `"in data feed"` oscript operator, which is implemented as a plain *existence* scan (`dataFeedExists` / `dataFeedByAddressExists`) over all of the arbiter's past postings for that key — it has no concept of "latest" or "final" value, unlike `data_feed[[...]]` (`readDataFeedValue`) which does track "last" vs "several". If the arbiter (or the arbstore appeal process) ever posts more than one value for the same `CONTRACT_<hash>` key — e.g. an initial (possibly mistaken) dispute resolution followed by a corrected resolution after `appeal()` — both values remain permanently in the data feed history and both satisfy their respective `"in data feed"` branches of the `["or", ...]` shared address definition.

### Finding Description
`deriveSharedAddress()` builds an `"or"` definition where branches 4 and 5 allow the offeror or acceptor to spend once `["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, "=", offeror_address]]` (or `acceptor_address`) is true. [3](#0-2) 

`parseWinnerFromUnit()` / the `"arbiter response"` listener records whichever `CONTRACT_<hash>` data-feed unit arrives, setting the contract to `dispute_resolved` and remembering only the latest `resolution_unit` in the wallet DB. [4](#0-3) [5](#0-4) 

However, `appeal()` explicitly allows a contract in `dispute_resolved` status to be re-opened via the arbstore appeal API, implying the original resolution can be overturned by a later ruling. [6](#0-5) 

The problem: the on-chain enforcement (the shared address's `"in data feed"` condition) does not track *which* resolution is final. It only asks "did the arbiter *ever* post a matching value?" — this is independent of order, timing, or subsequent corrections, exactly mirroring the Taiko bug's root cause where "the history of the final verified transition is not taken into account." Concretely:

1. Arbiter posts `CONTRACT_<hash>=addressA` (a hasty/incorrect first ruling).
2. Party A immediately builds a unit satisfying `in data feed(...) = addressA` and spends the shared-address funds.
3. The appeal process runs and the arbiter posts a corrected `CONTRACT_<hash>=addressB`.
4. Because `dataFeedExists` never excludes or supersedes the earlier posting, party B can *also* construct a valid spending unit against the same shared-address output (`in data feed(...) = addressB` now also true), attempting to spend already-spent funds, or — if party A had not yet spent — both branches remain simultaneously valid, meaning whichever party manages to get their spending unit included as the winner of the double-spend race gets the money regardless of the correct/appealed decision.

Even absent an outright double-spend, the more direct and consistently reachable effect is that **the originally "wrong" party can always redeem the funds by using the earlier (later-overturned) data feed posting**, since nothing removes or negates the earlier value once the arbiter corrects it. The final, appeal-based, verified true outcome does not deterministically control fund custody, unlike the design intent of the arbiter/appeal system.

### Impact Explanation
This allows unauthorized/incorrect spending of the arbiter-contract's escrowed private-payment or public-asset funds, and/or a double-spend attempt on a single shared-address output based on a stale oracle statement, contradicting the intended arbitration/appeal outcome. This is a direct fund-loss/fund-misdirection scenario for the counterparty who actually won the appeal — the funds can be taken by the address named in an earlier, overturned `CONTRACT_<hash>` posting. This matches the "unauthorized spending" and "AA/counterparty fund loss" categories called out in scope.

### Likelihood Explanation
Triggering requires the arbiter to post more than one `CONTRACT_<hash>` value for the same contract hash — a scenario the code itself anticipates and supports via `appeal()`/`in_appeal`/`appeal_approved`/`appeal_declined` statuses. Since arbiters are external, semi-trusted humans operating through an arbstore, and Obyte protocol code does nothing to prevent a corrective re-posting (nor advises arbiters to never do so), an appeal that changes the outcome is a foreseeable and directly reachable path for any private-payment counterparty using this feature, not a contrived edge case.

### Recommendation
Change the shared-address spending condition to reference the *final* value only, e.g. use a data feed value comparison anchored to `min_mci` set after the appeal resolution, or better, require the winner condition to reference an explicit "final" flag posted once by the arbiter/arbstore (e.g., `CONTRACT_FINAL_<hash>`) that is only ever written once, instead of allowing any historical posting under the mutable `CONTRACT_<hash>` key to satisfy the condition. Alternatively, use `data_feed[[..., ifseveral='abort']]` semantics (which do track ambiguity/"several" postings and abort) rather than `"in data feed"`'s pure existence check, and reject spending attempts when more than one `CONTRACT_<hash>` value exists until the appeal window has definitively closed.

### Proof of Concept
1. Two parties, Alice (payer) and Bob (payee), create an arbiter contract and fund the shared address per `createSharedAddressAndPostUnit()`. [7](#0-6) 
2. Bob opens a dispute via `openDispute()`. [8](#0-7) 
3. Arbiter mistakenly posts a `data_feed` unit with `CONTRACT_<hash> = Alice's address` (incorrect first ruling).
4. Alice immediately composes and broadcasts a unit spending the shared-address output using the `["in data feed", ..., "=", Alice]` branch of the definition — this succeeds because `dataFeedExists` finds the matching posting. [1](#0-0) 
5. Bob appeals via `appeal()`, and the arbstore corrects the ruling: arbiter posts a second `data_feed` unit `CONTRACT_<hash> = Bob's address`. [6](#0-5) 
6. Bob attempts to spend the same shared-address output via the `["in data feed", ..., "=", Bob]` branch — the definition still evaluates true because the existence check in `dataFeedByAddressExists`/`dataFeedExists` finds Bob's later posting too, regardless of Alice's earlier (overturned) posting and prior spend. Depending on whether the output was already consumed by Alice's unit, this results either in a rejected double-spend attempt (leaving Bob, the appeal winner, unable to recover funds — permanent loss analogous to Bob's unrecoverable bond in the Taiko report) or, if timed before Alice's unit stabilizes, a genuine double-spend race for the same escrowed funds.

Note: I was not able to execute this against a live network/testnet to observe the exact DAG-conflict resolution outcome (which of the two competing spending units would ultimately be marked `good` vs `final-bad`); this assessment is based on static analysis of `arbiter_contract.js`, `definition.js`, and `data_feeds.js`. Since I only have read access to the indexed codebase, I cannot run the scenario live — a Devin session with sandbox/testnet access could run and confirm this PoC end-to-end.

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
