Confirmed: the signature-verification binding and the repository-write binding are two different fields of the same attacker-controlled JSON body.

### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while all event handlers act on the independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  Once the signature is accepted, `create` dispatches the entire raw JSON body to the event handlers, and every handler (`Shipit::Webhooks::Handlers::Handler#stacks`, `PushHandler`, `LabeledHandler`, `ReopenedHandler`, etc.) resolves the target `Repository`/`Stack` using a completely different field: `repository.full_name`. [3](#0-2) [4](#0-3) 

### Finding Description
This mirrors the reported bug class: a trust binding (the value used to authenticate the request) is not the same value used to determine what resource the request acts on. Here, the equality that should hold but doesn't is:

`organization used to select webhook_secret for HMAC verification` == `repository whose Stack/commits/status get mutated by the handler`

In a Shipit installation configured with multiple GitHub Apps/organizations (as documented in `docs/setup.md`), each organization has its own `webhook_secret` in `Shipit.github(organization:)`. [5](#0-4)  An attacker who legitimately administers "their own" onboarded GitHub organization/App in that Shipit instance (and therefore knows or can trigger a validly-signed webhook delivery for that org's secret) can craft/replay a webhook whose `repository.owner.login` (or `organization.login`) is their own org — passing `verify_webhook_signature` — while setting `repository.full_name` to a *different* org/repo already tracked by Shipit as a `Stack`. [6](#0-5)  Because `Handler#stacks` and downstream handlers only look at `repository.full_name` to find the `Repository`/`Stack` to write to, none of them re-validate that this repository actually belongs to the organization whose secret authenticated the request. [3](#0-2) 

This lets a validly-signed webhook from Org A mutate state belonging to Org B's stack, e.g. enqueueing `GithubSyncJob` for Org B's stack via `PushHandler#process` (which calls `stack.sync_github`, triggering `Stack#github_api`/`Stack#github_app` to fetch commits using Org B's own GitHub App token — not attacker-controlled, but the sync is now driven by attacker-forged push events) [7](#0-6) [8](#0-7) , or archiving/unarchiving review stacks via `LabeledHandler`/`ReopenedHandler`, which resolve `repository` via `Repository.from_github_repo_name(params.repository.full_name)` and act on that repo's review stacks regardless of which org's secret signed the request. [9](#0-8) 

### Impact Explanation
This crosses a repository-write boundary: an actor authenticated only as one onboarded GitHub organization can forge webhook-driven state changes (stack archival/unarchival, forced GitHub sync, commit/status ingestion) against a *different* repository/stack tracked by the same Shipit instance, without possessing that organization's webhook secret or any Shipit session/API credential. This matches the "cross-repository writes" Critical-impact category, since the write is driven by data whose authenticity was never actually verified for the specific repository being modified.

### Likelihood Explanation
Exploitability requires the attacker to control (or replay a delivery from) at least one GitHub App/organization configured in the same multi-org Shipit deployment — a scenario explicitly supported and documented (`docs/setup.md` "Using Multiple Github Applications"). [5](#0-4)  Single-organization deployments are not affected the same way (there is only one `webhook_secret`, and `repository_owner` will equal the only organization), but multi-tenant/multi-org Shipit installations are a first-class, documented deployment mode, making this a realistic and low-effort attack path for a party that legitimately manages one of several onboarded orgs.

### Recommendation
After successfully verifying the HMAC signature, revalidate that `repository.full_name`'s owner matches the `repository_owner` (or `organization.login`) that was used to select the `webhook_secret`, and reject the webhook (422) if they diverge. Alternatively, derive `repository_owner` strictly from `repository.full_name`'s owner segment so the same field is used both to pick the verification secret and to resolve the target `Stack`/`Repository`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, `org-a` and `org-b`, each with its own `webhook_secret`, per `docs/setup.md`'s multi-org example.
2. Shipit tracks a `Stack` for `org-b/victim-repo`.
3. Attacker controls `org-a`'s GitHub App (or captures/replays a valid delivery from it) and sends a `push` webhook to `/webhooks` with:
   - `organization.login` / `repository.owner.login` = `"org-a"` (so `Shipit.github(organization: "org-a")`'s `webhook_secret` is used) and `X-Hub-Signature` correctly computed with `org-a`'s secret,
   - `repository.full_name` = `"org-b/victim-repo"`, `ref` = `refs/heads/<victim-branch>`, `after` = arbitrary sha.
4. `WebhooksController#verify_signature` passes because the signature matches `org-a`'s secret and `repository_owner` resolves to `org-a`. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` and enqueues `GithubSyncJob` for `org-b`'s stack, despite the request never having been authenticated for `org-b`. [3](#0-2) [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
