Confirmed: `Shipit::Api::CCMenuController` bypasses the `ApiClient#stack_id` scoping enforced everywhere else in the API.

### Title
CCMenu controller lets a stack-scoped API token read the state of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController` enforces this scope by resolving stacks through `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` before looking up the requested resource [1](#0-0) . `Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stacks` scoping helper [2](#0-1) .

### Finding Description
The binding that should hold is: **the stack a token authorizes == the stack it touches**. For every other stack-scoped resource in the API, the controller resolves the target stack through `current_api_client`-scoped `stacks`, so a token minted with a `stack_id` (e.g., the CCMenu client created for a specific stack, see `CCMenuUrlController#client`) cannot resolve to any other stack [3](#0-2) .

`Api::CCMenuController#authenticate_api_client` authenticates the client from a `token` query-string parameter [4](#0-3) , and `require_permission :read, :stack` only checks that the token's `permissions` array includes `read:stack` — it never checks `stack_id` [5](#0-4) , [6](#0-5) . The `#show` action then calls `stack.deploys_and_rollbacks.last`, where `stack` is resolved via the overridden method that ignores the client's `stack_id` entirely [7](#0-6) .

Because `authentication_token` is merely a signed client id (`SimpleMessageVerifier`) with no embedded stack binding, any valid token whose permissions include `read:stack` — even one minted for stack A via `CCMenuUrlController` — can be replayed with a different `stack_id` in the URL to read stack B's deploy/rollback state [8](#0-7) .

Before vs after (equality that should hold and is broken):
- Expected: `token.stack_id == stack_shown_in_response.id` (when `stack_id` is set)
- Actual: `stack_shown_in_response.id` is taken unconditionally from `params[:stack_id]`, independent of `token.stack_id`.

### Impact Explanation
This allows unauthenticated (i.e., without the intended stack-scoped) read of stack state and deploy/rollback output for arbitrary stacks using a token that was only supposed to be valid for one stack — matching the High-severity criterion "unauthenticated read of stack state, task streams or deploy output" via escalation of the token's authorized scope. It does not by itself grant write, so it stays in the High bucket rather than Critical.

### Likelihood Explanation
Any holder of a CCMenu URL/token (these are handed out somewhat casually, e.g. embedded in CI dashboards, distributed to team members) can trivially exploit this by editing the `stack_id` in the request path while keeping their own `token` query parameter — no privileged access or additional secret is required.

### Recommendation
**Short term:** In `Api::CCMenuController#stack`, resolve the stack the same way `BaseController#stack` does — through `stacks.from_param!(params[:stack_id])` (i.e., respect `current_api_client.stack_id` scoping) instead of calling `Stack.from_param!` directly.

**Long term:** Add a regression test asserting that a `stack_id`-scoped API client cannot fetch CCMenu data for a different stack, and audit all controllers under `app/controllers/shipit/api/` for direct `Stack.from_param!`/`Stack.find` usage that bypasses the `stacks` scoping helper.

### Proof of Concept
1. Have a `walrus`-owned CCMenu token scoped to `stack_id: A` (created via `CCMenuUrlController#client`, which sets `permissions: %w[read:stack]` and a specific `stack`) [3](#0-2) .
2. Request `GET /api/stacks/B/ccmenu.xml?token=<token-for-A>`.
3. `authenticate_api_client` authenticates the token successfully (it is a valid, unexpired signature) [4](#0-3) .
4. `require_permission :read, :stack` passes because the token has `read:stack` in `permissions`, regardless of `stack_id` [6](#0-5) .
5. `stack` resolves to stack B via `Stack.from_param!(params[:stack_id])`, ignoring the token's `stack_id` of A, and the XML response reveals stack B's latest deploy/rollback status [7](#0-6) .
