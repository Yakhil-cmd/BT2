### Title
Membership webhook signed by any configured GitHub organization can add arbitrary users to any pre-existing `Team` regardless of the org that owns it, via `Team.find_or_create_by!(github_id:)` ignoring organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, never validating that the `organization` in the incoming payload matches the `Team#organization` already stored in the database. Because `WebhooksController#verify_signature` authenticates the request only against the organization named in the payload itself (`repository_owner`, which falls back to `params.dig('organization','login')` for `membership` events), an attacker who owns any org configured in `Shipit.github_teams`/`Shipit.github` can sign a `membership` webhook with their own org's secret while naming a victim org's team `github_id`, causing themselves to be added as a member of that team.

### Finding Description
The broken binding: the organization whose `webhook_secret` verified the HMAC on the request bytes (call it `Org_signing`) must equal the organization that owns the `Team` record being mutated (`Team#organization`, call it `Org_owner`). The code never checks `Org_signing == Org_owner`.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` where `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is `params.dig('repository','owner','login') || params.dig('organization','login')`. `membership` events have no `repository` key, so `repository_owner` is taken directly from `params['organization']['login']`, a value fully controlled by the attacker's request body. As long as this matches an org Shipit has configured (the attacker's own org, "OrgA"), `verify_webhook_signature` succeeds using OrgA's own secret, which the attacker legitimately possesses. [1](#0-0) [2](#0-1) 

2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)`. The `do |team| ... end` block (setting `organization`) only runs when a **new** record is created; if a `Team` already exists with that `github_id` (belonging to `OrgB`), it is simply returned unchanged, without any comparison to `params.organization.login`. [3](#0-2) 

3. `team.add_member(User.find_or_create_by_login!(params.member.login))` then persists the attacker's arbitrary GitHub login as a member of `OrgB`'s team. [4](#0-3) 

Attacker request: `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with OrgA's `webhook_secret` (which the attacker owns/administers), body:
```json
{"action":"added","team":{"id":<OrgB_team_github_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"OrgA"},"member":{"login":"attacker-login"}}
```
Since `repository_owner` resolves to `"OrgA"` and the attacker's own secret validates the signature, `verify_signature` passes. `find_or_create_team!` then finds the existing `Team` row for `OrgB` by `github_id` alone and `add_member` inserts the attacker into it.

Existing guards fail to catch this: `verify_signature` only proves "this org's secret signed this org's own webhook," not "this org owns the team referenced inside the payload." `drop_unhandled_event` is irrelevant (membership is a handled event). The `ExplicitParameters` schema on `MembershipHandler` only validates types/presence, not cross-field org ownership. There is no `require_permission!`/`authorized?` check anywhere in this flow — team membership is written unconditionally.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization: `Team` records referenced there gate deploy/merge permission checks (`User#authorized?`/`require_permission!` consult team membership). An attacker who controls any org configured in Shipit (even a throwaway/low-privilege org they added themselves, as long as it's in the Shipit config) can add themselves to any other configured org's authorization team by simply knowing/guessing that team's numeric GitHub `id` and its Shipit-known github_id — no cross-org secret required. The attack is repeatable against any `Team` row already synced into Shipit (teams get created via `github_sync_job`/`fetch_and_create_from_github`), across every stack/repository that relies on that team for permission checks. This matches the "High: escalation into `Shipit.github_teams` authorization" category, potentially escalating to "Critical: unauthorized deploy/merge" if the targeted team gates deploy permissions.

### Likelihood Explanation
Preconditions: attacker must have their own org registered in Shipit's GitHub app configuration (multi-tenant Shipit installs commonly allow self-service onboarding of orgs), and must know/guess the numeric `github_id` of the victim `Team` (obtainable via GitHub's public team API for team info if not private, or by enumerating small integers, or from prior sync). No Shipit session, API token, or victim org secret is needed — only the attacker's own legitimate webhook secret for their own org. This is a straightforward, cheap, and repeatable HTTP request forgeable entirely by an "attacker action" as scoped (any internet user able to POST to `/webhooks`).

### Recommendation
In `MembershipHandler#find_or_create_team!`, look up the `Team` by both `github_id` **and** `organization: params.organization.login`, and reject/ignore the event (or raise) when a `Team` exists with that `github_id` under a different organization. Additionally, `WebhooksController#repository_owner`/`verify_signature` should not trust the `organization.login` field found inside the payload as authoritative proof of a specific team's ownership — the fix must live in the handler's lookup logic, ensuring cross-org team hijacking is impossible regardless of which org's secret signed the request.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook signed by OrgA cannot add members to OrgB's team" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: 'OrgB', name: 'deployers', slug: 'deployers', api_url: 'https://api.github.com/teams/999')

  params = ExplicitParameters::Params.new(
    action: 'added',
    team: { id: 999, name: 'deployers', slug: 'deployers', url: victim_team.api_url },
    organization: { login: 'OrgA' },
    member: { login: 'attacker-login' }
  )

  # Binding under test: Org_signing ("OrgA") == Team#organization ("OrgB")?
  assert_not_equal 'OrgA', victim_team.organization

  Shipit::Webhooks::Handlers::MembershipHandler.new(delivery: SecureRandom.uuid, event: 'membership', params:).call

  attacker = Shipit::User.find_by(login: 'attacker-login')
  assert victim_team.reload.members.include?(attacker), "attacker was added to OrgB's team despite webhook only being signed by OrgA"
end
```
This demonstrates that `find_or_create_team!` returns/mutates a `Team` whose `organization` never matched the organization used to authenticate the request, confirming both the `AUTHORIZATION_TRUTH` and `WEBHOOK_PROVENANCE` failures.
