Based on the code examined, the vault deposit functions across all Zest vaults compute minted shares from the nominal `amount` parameter rather than the actual balance received after `receive-underlying` completes.

### Title
Deposit share minting uses nominal input amount instead of actually-received underlying balance, allowing shortfall to be socialized across all vault depositors - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vault contracts)

### Summary
Each vault's `deposit` function computes `inkind` (shares to mint) via `convert-to-shares-preview amount` using the caller-supplied `amount`, then calls `receive-underlying amount account` to pull the tokens, and unconditionally increments the global `assets` variable by the same nominal `amount` — without ever checking that the vault's actual token balance increased by that amount. [1](#0-0) 

### Finding Description
The shared state at risk is the `assets` data var and the `zft` share supply, both of which back redemption rights for every depositor in the vault, not just the caller. `deposit` never verifies actual tokens received:

```
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
``` [2](#0-1) 

If the underlying SIP-010 token (e.g. the hardcoded `usdcx` contract-of-record) ever charges a transfer fee, is upgraded/proxied to add one, or `receive-underlying` otherwise does not deliver the full `amount` to the vault, the caller still receives shares/credit for the full nominal `amount` and `assets` is incremented by the full nominal `amount`, while the vault's real token balance increased by less. This inflates `assets` (and therefore `convert-to-assets-preview`) relative to the vault's true backing, so every other shareholder's redeemable value per share is diluted — an unprivileged depositor's action degrades the redemption value of all existing/other depositors' shares, and later redeemers can find `send-underlying` unable to fully honor `available-assets` because on-chain balance is less than `assets` implies. This matches the reported bug class (queue deposit not accounting for fee-on-transfer tokens leads to overstated claims), but here the analog operates on the vault's shared `assets`/`zft` accounting instead of a claims queue.

### Impact Explanation
This falls under temporary/permanent freezing of funds for other depositors: because `assets` (and the resulting share-to-asset conversion rate) is inflated beyond the vault's actual underlying balance, honest depositors redeeming later can be blocked or receive less than their pro-rata entitlement once the shortfall is discovered by `available-assets`/`ERR-INSUFFICIENT-LIQUIDITY` checks in `redeem`, and the vault's insolvency (assets accounting exceeding real balance) is socialized across all shareholders, not just the depositor who triggered it.

### Likelihood Explanation
Likelihood depends entirely on whether `UNDERLYING` (or any token integrated in the future) has fee-on-transfer, deflationary, or rebasing-with-loss behavior, or if `receive-underlying`'s pull mechanism (via `contract-call?` transfer, or the `with-ft`/`with-stx` postcondition patterns used in `supply-collateral-add`) can ever deliver less than `amount`. For the currently configured tokens (standard SIP-010 assets) this is not observed today, so likelihood is low under current token configuration but becomes a real risk if any future or upgraded underlying asset introduces a transfer fee, since the vault code has no defense-in-depth balance check.

### Recommendation
In `deposit` (and `supply-collateral-add`'s deposit path), measure the vault's actual underlying balance before and after `receive-underlying`, and use the delta (not the nominal `amount`) both for `ft-mint? zft` share calculation and for the `var-set assets` update, so any transfer-fee or short-delivery is reflected in the shares minted and cannot dilute other holders' claims.

### Proof of Concept
1. Assume `UNDERLYING` is (or is upgraded/replaced to be) a fee-on-transfer SIP-010 token that deducts 1% on `transfer`.
2. Attacker calls `deposit(amount=1000, min-out=0, recipient=attacker)`.
3. `receive-underlying` pulls tokens; vault actually receives only 990, but `inkind` is computed from `convert-to-shares-preview(1000)` and `assets` is incremented by the full `1000`.
4. Attacker is minted shares worth 1000 nominal assets while the vault only holds 990 real tokens; the loss (10) is spread over all existing and future shareholders' claims, and can push `available-assets` checks in later legitimate `redeem` calls (`mainnet/contracts/vault/v0-vault-usdc.clar` lines 799-817) to fail or under-pay other depositors.
