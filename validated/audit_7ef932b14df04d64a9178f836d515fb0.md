## Title
Cross-organization webhook forgery: signature is authenticated against `repository.owner.login`, but the acted-upon repository is selected from the unvalidated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

## Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate a webhook's HMAC against using one field of the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`), while every event `Handler` (via `Shipit::Webhooks::Handlers::Handler#repository_name`) determines *which stack/repository gets acted upon* using a different field of the same body (`repository.full_name`). Nothing ties these two fields together cryptographically or logically beyond "both are inside the HMAC-signed body" - but the HMAC is computed by whoever holds the secret for the org selected in the first field, over content they fully control. This breaks the intended binding: "the organization whose secret authenticated the request" == "the repository the request is allowed to mutate."

## Finding Description
`app/controllers/shipit/webhooks_controller.rb` verifies webhooks like this: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload: [2](#0-1) 

That value selects a `GitHubApp` instance keyed by organization (`Shipit.github(organization: repository_owner)`), each with its own independently configured `webhook_secret` (see `lib/shipit/github_app.rb` `initialize`/`verify_webhook_signature`, and `test/dummy/config/secrets_double_github_app.yml` showing multiple orgs, each with its own `webhook_secret`). This is a legitimate multi-tenant configuration: Shipit supports hosting multiple GitHub organizations, each with its own GitHub App and its own webhook secret.

Once the signature check passes, `WebhooksController#create` hands the *entire* parsed body to the event handler: [3](#0-2) 

Every handler resolves the target repository/stacks from a *different* field of the same body: [4](#0-3) 

`Repository.from_github_repo_name` splits this string on `/` and looks the repo up with no relation to the org used for signature verification: [5](#0-4) 

Because the attacker constructs the raw JSON body themselves and signs it with their own org's `webhook_secret` (which they legitimately know, since it is the secret for a GitHub App they configured for their own org), they can set `repository.owner.login` = their own org (so the signature check picks their own, correctly-known secret and passes) while setting `repository.full_name` = `"victim-org/victim-repo"` (a completely unrelated tenant's repository on the same Shipit instance). The signature only proves "signed by holder of OrgTwo's secret" - it says nothing about which repository the payload is allowed to reference.

This is exploitable by:
- `PushHandler`, which finds stacks by `repository_name` and calls `stack.sync_github(expected_head_sha: ...)` (`app/models/shipit/webhooks/handlers/push_handler.rb`), forcing a `GithubSyncJob` for a stack belonging to another tenant.
- `StatusHandler`, which finds commits purely `Commit.where(sha: params.sha)` globally (not even scoped by repo/stack) and calls `commit.create_status_from_github!(params)` with attacker-supplied `state`, `description`, `target_url`, `context` for **any** commit sha in the system: [6](#0-5) 

Since `StatusHandler` doesn't even use `stacks`/`repository_name` to scope the commit lookup, forging a `state=success` status for an arbitrary commit sha (which an attacker can learn from a target repo's public commit history) can flip CI gating for a target stack that has `continuous_deployment` enabled and matching required status contexts, potentially triggering an **unauthorized automated deploy** of that commit.

## Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. On a multi-tenant Shipit instance (the officially documented configuration, per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), any org onboarded with its own GitHub App can forge webhook events that are attributed to, and acted upon, a completely different org's repositories/stacks — without ever knowing that other org's webhook secret. Depending on the handler exercised, impact ranges from spurious sync jobs against a foreign stack (`PushHandler`) up to forged CI statuses on arbitrary commits (`StatusHandler`), which can silently satisfy `continuous_deployment` gating criteria and result in an **unauthorized deploy** for a repository the attacker has no access rights to — matching the "Critical: unauthorized deploy" bucket in scope.

## Likelihood Explanation
Requires only that the attacker administers (or has compromised) any single GitHub organization/App that is legitimately configured on the shared Shipit instance — no `ApiClient` token, session, or GitHub App private key for the *victim* org is needed. Any tenant on a multi-org Shipit deployment satisfies this precondition, and crafting the forged webhook body requires no special tooling beyond a standard HTTP client and HMAC-SHA1 signing with a secret the attacker already possesses.

## Recommendation
Bind the field used to select the signing secret to the field used to resolve the affected repository/stack:
- Compute `repository_owner` for signature-key selection and `repository_name`/`full_name` for stack resolution from the *same* trusted source, and reject the webhook (422) if `repository.full_name`'s owner segment does not match `repository_owner`.
- For `StatusHandler`, scope the `Commit` lookup through `stacks` (as other handlers do) rather than a global `Commit.where(sha: ...)`, so a status can only be attached to commits belonging to the repository whose organization actually signed the request.
- Consider moving to per-installation webhook secrets validated against the specific `installation_id`/App rather than an attacker-suppliable `organization`/`repository.owner.login` field.

## Proof of Concept
1. Shipit is configured for two GitHub orgs, `OrgTwo` (attacker-controlled) and `OrgOne` (victim), each with distinct GitHub Apps/`webhook_secret`s, per `config/secrets.development.shopify.yml`/`test/dummy/config/secrets_double_github_app.yml` style config.
2. Attacker (legitimate admin of `OrgTwo`, knows `OrgTwo`'s `webhook_secret`) builds a `push`/`status` JSON body where:
   - `repository.owner.login = "OrgTwo"` (or `organization.login = "OrgTwo"`), and
   - `repository.full_name = "OrgOne/victim-repo"` and, for `status`, `sha` set to a known commit on `OrgOne/victim-repo`, `state = "success"`, `context` matching a required status context for a `continuous_deployment`-enabled stack.
3. Attacker signs the raw JSON body with `OrgTwo`'s `webhook_secret` (HMAC-SHA1) and sets `X-Hub-Signature` accordingly, `X-Github-Event: status` (or `push`).
4. POST to `/github/webhooks` (per `config/routes.rb`).
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and successfully verifies the signature (attacker's own secret matches).
6. `StatusHandler#process` (or `PushHandler#process`) runs against `OrgOne`'s commit/stack, creating a forged passing status (or forcing a sync) for a repository the attacker does not own, potentially triggering `OrgOne`'s continuous-deployment pipeline.

Note: I could not fully trace whether `Stack#deployment_checks_passed?`/continuous-deployment auto-trigger logic (outside the in-scope directories examined) would immediately act on a forged status without additional confirmation steps; this final link is asserted based on the documented `continuous_deployment`/required-statuses mechanism referenced in `app/models/shipit/stack.rb` but was not traced end-to-end within the tool-call budget available.
