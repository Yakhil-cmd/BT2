### Title
`record_contract_call` skips just-deployed contracts under `UpdateTrackedShard`, causing missing contract distribution and validator apply-time failure - (File: runtime/runtime/src/function_call.rs)

### Summary
`record_contract_call` (invoked from `action_function_call`) only records a contract access into `contract_accesses` when the code lookup via `state_update.trie.get_optimized_ref(..., KeyLookupMode::MemOrFlatOrTrie, ...)` finds a value whose hash matches `code_hash`, and it explicitly does this lookup against the raw `state_update.trie`, not through `TrieUpdate::get_ref`, which is the only path that consults the in-flight `prospective`/`committed` overlays. Deploying a contract with `DeployContract` writes the code into the tracker's `uncommitted_deploys` (`ContractStorage::record_deploy`) and the code key into `TrieUpdate::prospective` via `set_code`, neither of which is visible to a direct `Trie::get_optimized_ref` call until the trie is actually committed/applied to storage. Consequently, if the same account performs `DeployContract` immediately followed by a `FunctionCall` referencing the newly deployed code within the same chunk apply, `record_contract_call` for that `FunctionCall` will not find the contract in the trie, will not call `state_update.contract_storage().record_call(code_hash)`, and the contract will be silently omitted from `ContractUpdates::contract_accesses`.

### Finding Description
Code path:
- `runtime/runtime/src/function_call.rs::action_function_call` calls `record_contract_call(state_update, contract_id, &apply_state.apply_reason)` before executing the function call: [1](#0-0) 
- `record_contract_call` gates recording on `apply_reason == ApplyChunkReason::UpdateTrackedShard`: [2](#0-1) 
- It then performs the existence check directly against `state_update.trie` using `get_optimized_ref` with `KeyLookupMode::MemOrFlatOrTrie`, and only calls `record_call` if a matching value is found: [3](#0-2) 

Crucially, this bypasses `TrieUpdate::get_ref`, the wrapper that checks `prospective`/`committed` maps before falling back to `self.trie.get_optimized_ref`: [4](#0-3) [5](#0-4) 

A `DeployContract` action stores the new code via `TrieUpdate::set_code`, which only inserts into `self.prospective` (a `BTreeMap`, not the trie itself): [6](#0-5)  and separately via `ContractStorage::record_deploy`, which stores it in `ContractsTracker::uncommitted_deploys`, explicitly documented as a workaround because "the `TrieUpdate` will only write the contract once the whole transaction is committed at the end of the chunk's apply": [7](#0-6) [8](#0-7) 

Because `record_contract_call` queries `state_update.trie` directly rather than through `TrieUpdate::get_ref` (which would check `prospective`) or `ContractStorage::get` (which would check `uncommitted_deploys`/`committed_deploys`), a `FunctionCall` executed against a contract deployed earlier in the same chunk apply will fail the `contract_ref.is_some_and(...)` check and be silently skipped from `record_call`. The in-code comment even documents this as intentional behavior ("This avoids recording contracts that do not exist or are newly-deployed"), but this rationale does not account for the case where the newly-deployed contract *is* actually executed in the same chunk — it is then a real, executed contract dependency that validators tracking the shard need, yet it's excluded from `contract_accesses`.

### Impact Explanation
This falls under node panic / chain stall for the impact category "node panic or unbounded resource use" / "state divergence." If a validator's node relies on `contract_accesses` to know which contracts to fetch/distribute for a chunk it needs to apply (see `docs/misc/contract_distribution.md` and the `ContractUpdates` type), then omitting a deployed-and-called contract from that set means chunk-producing/validating nodes that don't already have that code (e.g., nodes newly tracking the shard) may be unable to resolve the contract when applying the same chunk, leading to failed chunk application, a stall, or a panic on missing contract code for those nodes — a liveness/determinism issue across the affected validator set.

### Likelihood Explanation
The preconditions are fully attacker-controlled and require no privilege: any account holder can submit a receipt/chunk containing a `DeployContract` action immediately followed by a `FunctionCall` action on the same account in the same apply pass, via ordinary RPC-submitted transactions. This is a common, natural usage pattern (deploy-then-initialize), making it highly likely to be triggered even unintentionally, not just by a deliberate attacker. It is fully reproducible deterministically given `ApplyChunkReason::UpdateTrackedShard`, which is exactly the code path used when validators are fetching/tracking a new shard and need to reconstruct contract code, so it directly targets the scenario the recording mechanism was built to serve.

### Recommendation
`record_contract_call` should check pending/uncommitted state before falling back to the trie — e.g., by using `TrieUpdate::get_ref` (which consults `prospective`/`committed`) or, more directly, by querying `state_update.contract_storage().get(code_hash)` (which checks `uncommitted_deploys`/`committed_deploys` in `ContractsTracker`) prior to or in place of the raw `state_update.trie.get_optimized_ref` call, so that a contract deployed earlier in the same chunk apply is correctly recognized as present and gets recorded via `record_call`.

### Proof of Concept
Integration test plan (extending existing `recording_reads_new_recorder`-style test infrastructure in `runtime/runtime/src/tests`):
1. Construct an `ApplyState` with `apply_reason = ApplyChunkReason::UpdateTrackedShard`.
2. Build a single receipt with two actions on the same account: `DeployContract(new_wasm_code)` followed by `FunctionCall { method_name: "some_method", .. }` targeting that same account.
3. Apply the receipt through the normal runtime `apply` path (as in existing apply tests, e.g. `runtime/runtime/src/tests/apply.rs`).
4. Assert that the resulting `TrieUpdateResult::contract_updates.contract_accesses` (or the `ContractUpdates` returned via `ContractStorage::finalize`) contains `CodeHash(new_wasm_code_hash)`.
5. Expected (buggy) result: the hash is absent from `contract_accesses` despite the contract having been successfully executed, demonstrating the gap; a fix should make the assertion pass.

    fn get_ref_from_updates(&self, key: &[u8]) -> Option<Option<TrieUpdateValuePtr<'_>>> {
        if let Some(key_value) = self.prospective.get(key) {
            return Some(key_value.value.as_deref().map(TrieUpdateValuePtr::MemoryRef));
        } else if let Some(changes_with_trie_key) = self.committed.get(key) {
            if let Some(RawStateChange { data, .. }) = changes_with_trie_key.changes.last() {
                return Some(data.as_deref().map(TrieUpdateValuePtr::MemoryRef));
            }
        }
        None
    }
