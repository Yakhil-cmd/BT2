### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login` field while the mutated resource is chosen from a different unverified field, allowing unauthenticated cross-repository webhook forgery when any configured GitHub App lacks a webhook secret - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which webhook secret) to verify a request against by reading `repository.owner.login`/`organization.login` straight out of the *unverified* request body. `GitHubApp#verify_webhook_signature` treats "no secret configured for that org" as automatically verified (`return true unless webhook_secret`). Meanwhile, every webhook handler resolves the actual `Repository`/`Stack` to mutate from a completely different field of the same body: `repository.full_name`. Nothing binds these two fields together, so a request whose "owner" happens to map to an app with no configured secret is accepted as authentic for whatever `repository.full_name` the attacker puts in the body — even if that names a totally different, securely-configured organization's repository.

then `verify_webhook_signature` returns `true` unconditionally — the HMAC is never even inspected. `head(422) unless verified` never fires, and the request proceeds to `create`.

However, every handler determines *which* repository/stack is actually acted upon from a different, unrelated field in the same JSON body: [6](#0-5) [7](#0-6) 

So the "organization that authenticated" (`repository.owner.login`, used only to pick a verifier) and "the repository that is written" (`repository.full_name`, used to look up the real `Stack`) are never checked for consistency. An attacker who sends a body where `owner.login` names a no-secret-configured org, but `repository.full_name` names an entirely different, sensitive tracked repository, gets `verified = true` for free and the handler proceeds to mutate the real target stack.

### Impact Explanation
This allows a fully unauthenticated, credential-less requester to forge arbitrary GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against any repository Shipit tracks, as long as the Shipit installation has at least one configured GitHub App organization without a webhook secret (a state the docs explicitly describe as "optional" and the default template ships with `webhook_secret: # nil`). Consequences include:
- `PushHandler` triggering `stack.sync_github(expected_head_sha:)` with attacker-chosen data for a repository the attacker does not control.
- Forged `status` events injecting fabricated commit statuses that can satisfy `required_statuses`/`StatusChecker`, unblocking deploys or auto-merges.
- Forged `pull_request`/`membership` events manipulating merge queue state or team membership.

This is a cross-repository write reachable with zero credentials, matching the Critical bar for "an unauthorized deploy, rollback or merge" / "cross-repository writes."

### Likelihood Explanation
No session, API token, webhook secret, or repository access is required from the attacker — only that the Shipit deployment (using the documented multi-GitHub-App feature) has one organization configured without a webhook secret while tracking other repositories. This is a supported, documented configuration path, not a deviation from how the engine is meant to be mounted.

### Recommendation
Bind the value used to select the verifying app to the value used to resolve the target repository: verify the webhook using the app associated with the actual owner segment of `repository.full_name` (not a separately-supplied `repository.owner.login`/`organization.login`), and require a non-blank `webhook_secret` for every configured organization (or reject the request instead of returning `true`) rather than treating an absent secret as implicit trust in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Assume Shipit is configured (per `docs/setup.md`'s "Using Multiple Github Applications" section) with two orgs: `OrgA` (webhook secret configured, tracks `OrgA/critical-repo`) and `OrgB` (webhook secret left blank).

1. Attacker sends, with no authentication and no valid signature header at all:
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/critical-repo"
  }
}
```
2. `repository_owner` resolves to `"OrgB"` (`app/controllers/shipit/webhooks_controller.rb:59-62`), `Shipit.github(organization: "OrgB")` loads OrgB's config, whose `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true` (`lib/shipit/github_app.rb:76-77`) regardless of the (absent/invalid) `X-Hub-Signature` header.
3. `create` runs; `PushHandler#process` resolves `repository_name` as `"OrgA/critical-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), finds `OrgA`'s real tracked `Stack`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` — mutating a repository the attacker has no relationship to, using only knowledge of a repo name and no credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
