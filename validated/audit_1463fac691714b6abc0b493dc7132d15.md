The uncontrolled-search-path class maps onto the router resolving the hop `pool`/token addresses from the attacker-supplied payload. Let me confirm the code path in the controller strategy and the router dispatch.### Title
Attacker-controlled hop `pool` address lets rogue contract execute under the victim's authorization tree and drain wallet tokens — (File: contracts/swap-aggregator/src/venues/aquarius/pool.rs)

### Summary
CVE-2024-21784 is an uncontrolled-search-path bug: the loader resolves a module from a location the attacker chooses, so attacker-supplied code runs with the victim's privileges. The analog in XOXNO Lending is the swap router's hop dispatch: each `SwapHop.pool`/`token_in`/`token_out` address is taken verbatim from the caller-supplied `swap_xdr` payload, with no venue, pool, or token allowlist. `dispatch_hop` hands the payload-named pool to the venue adapter, and `invoke_pool_swap` does `env.invoke_contract(pool, "swap", ...)` on that arbitrary address. Arbitrary code therefore executes inside the transaction while the caller's `require_auth` is on the stack, and any `token.transfer(victim, attacker, x)` the rogue pool issues is recorded by simulation as a sub-invocation of the caller's own authorization entry — executing if the caller signs the tree simulation returned.

### Finding Description
The controller's strategy wrapper grants the router one bounded authorization — an exact `token_in.transfer(controller, router, amount_in)` via `authorize_transfer_as_current` — and then checks only measured input/output deltas (`RouterOverspend`, `NoSwapOutput`). Those checks bound the routed amount, but they do not constrain *what code runs* during the route. In `dispatch_hop` the venue adapter is selected by `hop.venue`, and the Aquarius adapter calls `pool_tokens`/`invoke_pool_swap` on `ctx.hop.pool`, an address fully controlled by whoever built the route XDR — `env.invoke_contract(pool, "swap", args)` at contracts/swap-aggregator/src/venues/aquarius/pool.rs:34. A malicious "pool" only needs to satisfy `get_tokens` (returning the two listed tokens) and implement `swap`; inside `swap` it can issue `token::Client::transfer(&victim_caller, &attacker, &amount)` for any Stellar asset the caller holds. The threat model confirms the router "keeps no allowlist" of the pool/token addresses its payload names, and the harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end that (a) recording-mode simulation attaches the rogue `transfer` as a child of the caller's `swap_collateral` entry, and (b) signing that recorded tree moves the victim's entire unrelated wallet balance to the attacker while the swap still settles fairly.

### Impact Explanation
Theft of user funds beyond the routed amount. The controller's measured-delta checks and the router's `total_min_out`/`ExcessiveResidual` policy bound only the swap's own input and output; the rogue child transfer steals any token in the victim's wallet — the test steals `WALLET_BALANCE = 77_770_000_000` of a token the protocol never listed, while the victim still receives a fair `2.5 ETH` output and the position remains solvent. The same exposure applies on the direct `Router::execute_strategy(sender, total_in, swap_xdr)` path for every swap user, not only controller strategies.

### Likelihood Explanation
Requires a malicious route reaching the user (compromised/malicious quote source or phishing route) plus the victim signing the authorization tree that simulation recorded, where the rogue transfer is visible as a child entry. Any client that signs simulation output without decoding the route XDR is exploitable; the threat model explicitly states a client "must decode the route it signs" because the protocol itself provides no on-chain bound. Impact is theft of arbitrary wallet holdings; likelihood is gated by client verification, so Medium-High overall.

### Recommendation
Enforce a governance-managed venue/pool allowlist (or a registry of recognized pool contract addresses per venue) inside `dispatch_hop`/`invoke_pool_swap`, rejecting payload-named pools not on the list, so a route cannot place third-party code beneath the caller's authorization. At minimum, have the router record and expose the set of contract addresses it will invoke so integrators can verify the signed auth tree contains only the expected input transfer and no other children.

### Proof of Concept
Already executable in-repo: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. Outline:

1. Attacker deploys `RogueHopPool` with a stored plan `(victim=Alice, wallet_token, to=attacker, amount=WALLET_BALANCE)`; its `swap()` calls `token.transfer(alice, attacker, WALLET_BALANCE)` on an unlisted token Alice happens to hold.
2. Alice calls `controller.swap_collateral(alice, account_id, USDC, 5_000e7, ETH, route)` where `route.hop_pool` names the rogue pool. The controller authorizes the exact input transfer and calls `router.execute_strategy`, which invokes the rogue pool's `swap`.
3. `simulateTransaction` (recording mode) returns Alice's auth tree with the stolen `transfer` attached as a `sub_invocation` of her `swap_collateral` entry — asserted at lines 206-227.
4. If Alice signs that recorded tree, `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229-269) shows `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the honest-tree control fails with a host `Auth` error and leaves balances untouched.
