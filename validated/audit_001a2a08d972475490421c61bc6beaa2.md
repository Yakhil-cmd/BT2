### Title
Inconsistent equality comparison of data-feed values between unstable (in-AA) lookups and stable on-disk lookups causes divergent `data_feed`/`in_data_feed` results for numerically-equal values - (File: `data_feeds.js`)

### Summary
`readDataFeedValue()` and `dataFeedExists()` implement two different, mutually inconsistent notions of "equality" for oracle (data feed) values depending on whether the referenced data-feed unit is still unstable or already stable. When an AA formula (`data_feed[[...]]` / `in_data_feed[[...]]`) reads a data feed posted by another (or the same) AA that has not yet stabilized, values are compared with loose `toString()` equality. Once the same unit becomes stable, the identical value is looked up via canonical numeric key-encoding (`string_utils.toNumber` + `encodeDoubleInLexicograpicOrder`). These two comparison strategies disagree on numerically-equal-but-differently-formatted values (e.g. `5` vs `"5.0"`), so the exact same underlying data can be judged "match" in one code path and "no match" in the other.

### Finding Description
In `data_feeds.js`, `readDataFeedValue()` handles unstable AA-authored data feeds with a simple, format-sensitive equality test: [1](#0-0) 

```
var feed_value = payload[feed_name];
if (value === null || value === feed_value || value.toString() === feed_value.toString())
```

This is only reached when `unstable_opts` (i.e. `bAA`) is truthy, which is always the case whenever the comparison is being made from inside AA formula evaluation: [2](#0-1) 

The stable-storage path used once the referenced unit is stable, `readDataFeedByAddress()`, normalizes any numeric-looking value/feed_value into a canonical lexicographically-encoded number before comparing via key lookup: [3](#0-2) 

The same canonicalization is applied when the data feed is originally written to storage in `addDataFeeds()`: [4](#0-3) 

The corresponding `dataFeedExists()`/`in_data_feed` path exhibits the same divergence: the unstable-AA branch uses ad hoc, per-relation logic mixing `toString()` comparisons and manual `string_utils.toNumber()` parsing, [5](#0-4) 

while the stable branch (`dataFeedByAddressExists`) again canonicalizes both sides into typed (`'n'`/`'s'`) lexicographic keys before doing a range query: [6](#0-5) 

Because `readDataFeedValue`'s `unstable_opts` parameter is bound to `bAA` in the formula evaluator, **any** `data_feed[[...]]` call made from within an AA formula always takes the loose, unstable-branch comparison first for any not-yet-stable AA-authored feed with a matching author address — this is normal AA-to-AA / self-referential chained-trigger usage, not a privileged or malicious-node scenario.

### Impact Explanation
A data-feed poster (an AA author, or any AA acting as an oracle within a chained-trigger response) can post a numeric value in a non-canonical string form (e.g. `"5.0"`, `"05"`, `" 5"`) instead of a bare number. A downstream AA formula such as `data_feed[[oracles=..., feed_name="price", feed_value=5]]` will then:
- return "not found" while the oracle's unit is still unstable (loose `toString()` mismatch: `"5"` vs `"5.0"`), causing the AA to fall into its `ifnone`/failure branch (funds bounced, held, or misrouted), and
- return "found" once the same unit stabilizes and the lookup switches to canonical numeric-key comparison.

This means the exact same nominal oracle value produces different AA execution outcomes purely as a function of *when* it is read relative to stabilization — a property that AA authors relying on `data_feed`/`in_data_feed` for fund-release or price-threshold logic have no way to defend against, since the formula language gives no visibility into which comparison path is used. This can be leveraged by an oracle/AA author to make conditional payouts unreliable or to intentionally cause chained AAs to bounce/freeze funds depending on formatting of the posted value, and it undermines the assumption that a data feed's meaning is stable and deterministic regardless of when it is consumed within a trigger chain.

### Likelihood Explanation
No privileged access or malicious node/peer behavior is required. Any account (including an ordinary AA or an asset issuer running an oracle AA) can post a data feed value as a string that "looks like" a number but is not in canonical form, which is common (e.g. price feeds formatted with decimals). Any AA author who composes chained AAs that read each other's just-posted (still-unstable) data feeds — an explicitly supported and documented pattern — is exposed to this divergence without any special conditions.

### Recommendation
Unify the equality/relation semantics used for data-feed values across all code paths (unstable in-AA reads, `readDataFeedByAddress`, `dataFeedByAddressExists`, and `dataFeedExists`'s unstable branch). Specifically, `readDataFeedValue`'s unstable-AA equality check and `dataFeedExists`'s unstable-AA relation checks should reuse the same canonicalization logic (`string_utils.toNumber` + numeric comparison, falling back to strict string comparison only when neither side parses as a number) that the stable/on-disk lookup paths already use, so that a value's match/no-match outcome cannot change purely because the referenced unit transitions from unstable to stable.

### Proof of Concept
1. AA₁ (oracle) posts a `data_feed` message with `{"price": "100.0"}` inside a still-unstable unit authored by address `ORACLE_ADDR`.
2. AA₂'s bytecode contains: `data_feed[[oracles="ORACLE_ADDR", feed_name="price", feed_value=100, ifnone="none"]]`.
3. While AA₁'s unit is unstable and AA₂ is triggered within the same batch (chained trigger), `readDataFeedValue` takes the unstable-AA branch at `data_feeds.js:232`, computing `value.toString()` (`"100"`) vs `feed_value.toString()` (`"100.0"`) — these differ, so no candidate is added and AA₂'s formula falls through to `ifnone`, returning `"none"`.
4. After AA₁'s unit stabilizes, the same formula executed again (or evaluated by a getter for verification) falls to `readDataFeedByAddress` at `data_feeds.js:296-306`, where both `100` and `"100.0"` canonicalize to the same encoded numeric key, so the lookup succeeds and returns `100`.
5. The same nominal oracle value ("100.0" = 100) thus yields two different results (`"none"` vs `100`) purely depending on stabilization timing, demonstrating the inconsistency.
