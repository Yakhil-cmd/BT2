Confirmed: `StatusHandler#process` finds commits purely by `sha` (global, not scoped to any repository) and creates a `Status` record directly from webhook params, and `Commit#deployable?` / merge-queue logic trusts that status to gate deploys and merges. Combined with `WebhooksController#verify_signature` selecting the signing org from `repository.owner.login` while the handlers act on a different, independently-attacker-controlled field, this is exploitable in the documented multi-org configuration.

### Title
Webhook signature is verified against an organization chosen from an unverified payload field, letting one tenant's GitHub App forge push/status/membership events for another tenant's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` picks which GitHub App (and thus which `webhook_secret`) to verify a webhook signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body, *before* the signature is checked. The event handlers then resolve the actual `Repository`/`Stack` to act on using a *different* field from the same untrusted body (`repository.full_name`, or a global `sha` lookup for `status` events). Nothing binds the organization used to authenticate the request to the repository the request is allowed to mutate.

### Finding Description
`WebhooksController#verify_signature` computes:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

In a multi-org Shipit deployment (`Shipit.github_organizations`, documented in `docs/setup.md` "Using Multiple Github Applications" and implemented in `lib/shipit.rb#github_app_config`), each organization has its own `webhook_secret`. `Shipit.github(organization:)` looks up the app/secret purely from that attacker-controlled `repository_owner` string: [2](#0-1) 

Once the signature check passes (because the attacker's own org secret was chosen and the attacker signed the raw body with that secret), `create` re-parses the same body and dispatches to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers determine which `Stack`/`Repository` to mutate from a *different* JSON field than the one used for signature routing:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Worse, `StatusHandler` doesn't even use the repository field - it matches by SHA globally across every stack in the installation:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

This breaks the equality that should hold: `organization whose secret authenticated the request == organization owning the repository/commit being written`. An attacker who is a legitimate administrator of their own org "attacker-org" (and therefore legitimately knows `attacker-org`'s `webhook_secret`, configured in Shipit's multi-org `secrets.yml`) can:
1. Sign an arbitrary JSON body with `attacker-org`'s webhook secret.
2. Set `repository.owner.login` (or `organization.login`) to `"attacker-org"` so `verify_signature` picks `attacker-org`'s app and the signature check passes.
3. Set `repository.full_name` to `"victim-org/victim-repo"` (for `push`/`pull_request` events) or simply set `sha` to a real commit SHA belonging to any other tenant's repo (for `status` events, which have no repository binding at all).

### Impact Explanation
`Commit#deployable?` gates deploys/continuous-delivery and the merge queue on `success?` derived from `Status` rows created this way:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [6](#0-5) 

`Status.after_create` schedules continuous delivery directly:
```ruby
after_commit :schedule_continuous_delivery, :broadcast_update, on: :create
``` [7](#0-6) 

and successful status transitions enqueue `ProcessMergeRequestsJob`, feeding the merge queue's auto-merge logic: [8](#0-7) 

So a webhook forged by one tenant using its own legitimately-known secret can inject a fake `"success"` CI status onto an arbitrary commit belonging to a different tenant's repository, satisfying `ci.require`/`merge.require` and triggering an **unauthorized continuous deployment or an unauthorized pull-request merge** for that other tenant - matching the Critical impact category ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires the Shipit instance to be configured with multiple GitHub Apps/organizations sharing one webhooks endpoint (an explicitly documented and supported configuration in `docs/setup.md`), and requires the attacker to legitimately administer one of those tenant orgs (and thus its `webhook_secret`) while targeting another tenant hosted on the same instance. No GitHub App private key, `ApiClient` token, or Shipit session is needed - only the attacker's own webhook secret, which is inherent to being a normal, low-privilege tenant. Likelihood is Medium-High in any multi-tenant deployment of this feature.

### Recommendation
- Bind the verified organization to the object being mutated: after selecting the app by `repository_owner`, re-validate that every downstream write (`Repository.from_github_repo_name`, `Commit.where(sha:)`) resolves to a repository actually owned by that same, already-authenticated organization, and reject/ignore the event otherwise.
- For `StatusHandler`, additionally require and check a `repository`/`full_name` field consistent with the org used for signature verification instead of matching solely by global SHA.
- Consider verifying webhook signatures against every configured org's secret only as a last resort, and always cross-check the authenticated org against the resource being written before any state mutation.

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`) [9](#0-8) , and a Stack belonging to `OrgTwo/victim-repo` with `ci.require: ["ci/circleci"]`:

1. Attacker, who administers `OrgOne` and knows `OrgOne`'s `webhook_secret`, builds body:
```json
{
  "sha": "<victim commit sha in OrgTwo/victim-repo>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
2. Computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, body)`.
3. POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgOne"`, verifies successfully against `OrgOne`'s secret.
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` -- which finds the `OrgTwo` commit regardless of the `repository` object -- and creates a `success` `Status` on it, potentially satisfying `ci.require` and unblocking an unauthorized deploy/merge in `OrgTwo`'s stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
