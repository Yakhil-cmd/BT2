### Title
Cross-organization webhook forgery via unauthenticated `repository.full_name` field — signature verified against a different org than the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from `repository.owner.login` (or `organization.login`), but every webhook `Handler` resolves the actual `Repository`/`Stack` to mutate from the independent `repository.full_name` field of the same attacker-controlled JSON body. Because both fields live inside the same raw POST body that only needs to be *internally consistent enough to pass HMAC verification with a secret the attacker legitimately knows*, an attacker who controls one organization onboarded to a shared, multi-org Shipit deployment can forge a webhook whose `owner.login` matches their own org (so the signature check passes) while `full_name` points at a completely unrelated victim organization's repository, causing that victim's stack/commit state to be mutated.

### Finding Description
`WebhooksController#verify_signature` looks up the signing app via: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This determines which configured `Shipit.github(organization: ...)` webhook secret is used to HMAC-verify `request.raw_post`: [3](#0-2) 

Separately, every concrete handler (`PushHandler`, `StatusHandler`, etc.) resolves the repository/stack to act on from a *different* key in the very same JSON body: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` and `repository.full_name` are two unrelated JSON keys inside the attacker-fully-controlled raw request body. Nothing ties them together — the signature only proves the body was HMAC-signed with *some* configured org's secret, not that the org whose secret was used is the org that owns the repository the handlers subsequently act on.

Shipit explicitly supports serving multiple independent GitHub organizations from a single instance, each with its own `webhook_secret`, as documented and fixture-tested: [5](#0-4) [6](#0-5) 

The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository being mutated`. Before the attack, an attacker's own org ("attackerorg") can only authenticate webhooks for its own repositories. After the attack, by setting `repository.owner.login = "attackerorg"` (satisfies `verify_signature`) and `repository.full_name = "victimorg/victim-repo"` (consumed by `Handler#repository_name`), the attacker authenticates as their own org but writes to a stack/commit belonging to `victimorg`, breaking the equality.

Concretely, `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — a global, org-unscoped query — and calls `commit.create_status_from_github!(params)`: [7](#0-6) 

This lets the attacker inject an arbitrary CI status (e.g. `state: success`) onto any commit tracked by the shared Shipit instance, regardless of which org it belongs to. Likewise `PushHandler#process` triggers `stack.sync_github(expected_head_sha: params.after)` on any stack matching the forged `full_name`, again cross-org: [8](#0-7) 

### Impact Explanation
Forging a passing CI/status check on a victim's commit can satisfy a stack's configured required release-status check, which Shipit's deploy flow otherwise treats as a gate on commit deployability. Being able to inject fabricated "success" statuses for commits the attacker never had write access to is a cross-organization write and can lead to an unauthorized deploy of a commit that never actually passed the organization's real CI — this maps to the "cross-repository writes" / "unauthorized deploy" Critical/High impact categories.

### Likelihood Explanation
This requires the attacker to control (and know the webhook secret of) at least one organization already onboarded to the same shared Shipit instance — a realistic scenario for any multi-tenant/multi-org Shipit deployment as explicitly documented and tested in this engine. No Shipit session, API token, or write access to the victim repository is required; the `/webhooks` endpoint is reachable without authentication other than the HMAC check, and the attacker supplies the entire JSON body including the mismatched `owner.login` / `full_name` pair.

### Recommendation
In `Handler#repository_name` (or a shared pre-check in `WebhooksController`), verify that the repository resolved from `payload.dig('repository', 'full_name')` belongs to the same organization that was used to select and validate the webhook secret in `verify_signature`, rejecting the request (422) if they diverge. Equivalently, scope `Repository.from_github_repo_name` lookups (and the `Commit.where(sha: ...)` lookup in `StatusHandler`) to repositories owned by `repository_owner`, not just by `full_name`.

### Proof of Concept
1. Attacker registers/operates `attackerorg` as one of the organizations configured in this shared Shipit instance's `config/secrets.yml` (multi-org setup as in `test/dummy/config/secrets_double_github_app.yml`), and knows `attackerorg`'s `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attackerorg" }, "full_name": "victimorg/victim-repo" },
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "created_at": "2026-09-02T00:00:00Z"
}
```
3. Attacker computes `sha1=HMAC-SHA1(attackerorg_webhook_secret, body)` and POSTs to `/webhooks` with headers `X-Github-Event: status` and `X-Hub-Signature: sha1=...`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `"attackerorg"`, fetches `attackerorg`'s `GithubApp`, and successfully verifies the signature (it was indeed signed with that secret). [9](#0-8) 
5. `StatusHandler#process` then runs `Commit.where(sha: params.sha)` (unscoped to `attackerorg`), finds the victim's commit under `victimorg/victim-repo`, and calls `create_status_from_github!`, injecting a forged "success" status onto it. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
