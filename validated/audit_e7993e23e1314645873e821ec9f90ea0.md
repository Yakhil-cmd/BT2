### Title
`Api::CCMenuController#stack` bypasses ApiClient stack scoping - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` overrides `Api::BaseController#stack` and resolves the stack via `Stack.from_param!(params[:stack_id])` directly, instead of using the scoped `stacks.from_param!(params[:stack_id])` that `BaseController` provides. This means any `ApiClient` token with `read:stack` permission can read CCMenu status (name, activity, lastBuildStatus, lastBuildLabel) for *any* stack, not just the stack(s) the token is scoped to via `current_api_client.stack_id`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`Api::CCMenuController#show`'s `stack` should equal an element of `BaseController#stacks` (i.e. `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`), but instead:

```ruby
# app/controllers/shipit/api/ccmenu_controller.rb
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [1](#0-0) 

versus the base class's scoped version:

```ruby
# app/controllers/shipit/api/base_controller.rb
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`CCMenuController#stack` never calls `stacks` or consults `current_api_client.stack_id` at all, so for any `ApiClient` whose `stack_id` is set (a stack-restricted token), `Stack.from_param!` will happily resolve and return a stack outside that restriction. `require_permission :read, :stack` only checks the `read:stack` permission bit on the client, not which stack it applies to, so it does not catch this divergence.

The only piece of the write-up that is not fully substantiated by the code is the specific claim that `CCMenuUrlController#fetch`'s minted client is unrestricted — that is true (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, name:)` sets no `stack_id`, so for *that* client `stacks` would return `Stack.all` anyway) [3](#0-2) . However the underlying code defect is general: any `ApiClient` created with a `stack_id` restriction (stack-scoped token) is still not enforced by `CCMenuController`, because it bypasses `stacks` entirely. This is confirmed by `authenticate_api_client` in the controller, which authenticates via `ApiClient.authenticate(params[:token])` and does not otherwise constrain stack access [4](#0-3) .

### Impact Explanation
Any holder of a `read:stack`-scoped `ApiClient` token — even one that is supposed to be restricted to a single stack via `stack_id` — can supply an arbitrary `stack_id` param and read CCMenu build/lock status for any stack in the system, across repositories/organizations. This is a cross-tenant information disclosure of deploy/task/lock state (`name`, `lastBuildStatus`, `lastBuildLabel`, `activity`), matching the "High - unauthenticated/out-of-scope read of stack state" category. It is fully repeatable against every stack in the installation with a single valid token.

### Likelihood Explanation
Preconditions: `Shipit.disable_api_authentication` is `false` (default), and the attacker possesses any valid `ApiClient` token with `read:stack` permission (which can legitimately be obtained today via `CCMenuUrlController#fetch` for a stack they have `read:stack` access to). No GitHub secrets, sessions, or special privileges are needed — just a single legitimately-issued CCMenu token and knowledge/guessing of another stack's `to_param` (owner/repo/branch), which is often public. Attack cost is a single GET request.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped resolver from `BaseController` instead of overriding it, i.e. remove the override entirely (or reimplement it as `stacks.from_param!(params[:stack_id])`) so that stack-restricted `ApiClient` tokens cannot read stacks outside their `stack_id` scope.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` style (`ApiControllerTestCase`):
1. Create `stack_a = Stack.create!(repository: Repository.new(owner: "org-a", name: "repo-a"), branch: "main")` and `stack_b = Stack.create!(repository: Repository.new(owner: "org-b", name: "repo-b"), branch: "main")`.
2. `client = ApiClient.create!(permissions: %w[read:stack], stack_id: stack_a.id)` — a token explicitly scoped to `stack_a`.
3. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
4. Assert `response.status == 200` and the XML payload's `name` equals `stack_b.to_param`, proving the scoped token read a stack outside `client.stack_id`.
5. Contrast with `Api::StacksController#show` (which uses the base `stack` method) to show the same token correctly returns 404/`RecordNotFound` for `stack_b` there, demonstrating the divergence is specific to `CCMenuController`.
