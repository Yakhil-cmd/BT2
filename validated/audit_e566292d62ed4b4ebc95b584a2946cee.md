### Title
`StatusHandler#process` resolves target `Commit`s by `Commit.where(sha: params.sha)` globally instead of via the verified `stacks` scope, letting a validly-signed status webhook for one stack fire `Hook.emit(:deployable_status/:commit_status, stack, ...)` for an unrelated stack that shares a commit sha - ([File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/commit.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` [1](#0-0)  without restricting to the `stacks` scope that other handlers (e.g. `PushHandler`) use to bind the query to the repository that authenticated the webhook [2](#0-1) [3](#0-2) . Every `Commit` row matching that sha across the entire installation — including rows belonging to stacks whose repository never sent this webhook — has `create_status_from_github!` invoked, and `Commit#add_status` derives `stack` purely from `self.stack` [4](#0-3) , then calls `Hook.emit(:deployable_status, stack, ...)` for that foreign stack.

### Finding Description
The intended binding is: `stack whose webhook Hook.emit fires for == stack belonging to the repository that authenticated the incoming payload (verified via Handler#stacks)`. `StatusHandler#process` breaks this by never consulting `stacks` (the repository-scoped association built from the signature-verified `repository.full_name`) [5](#0-4) ; instead it does a bare `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) .

Because `Commit` rows are keyed by `stack_id`, not repository, the same GitHub commit sha can legitimately exist in multiple `Commit` rows belonging to different `Stack`s that track the same underlying repository (e.g. a `staging` stack and a `production` stack sharing a common ancestor commit), or in unrelated stacks if sha reuse otherwise occurs. `create_status_from_github!` calls `add_status`, which reads `stack` from the commit's own `belongs_to :stack` association [6](#0-5) [7](#0-6)  and emits both `:commit_status` and `:deployable_status` hooks scoped to that stack — regardless of whether that stack's repository is the one whose webhook signature was verified for this specific request.

`verify_signature` only confirms the payload was signed for the organization identified by `repository_owner`/`repository.full_name` [8](#0-7) ; it says nothing about which `Stack` rows should be affected. `Handler#stacks` exists specifically to bind processing to the authenticated repository's stacks, and `PushHandler` correctly uses it [2](#0-1) , but `StatusHandler` does not, so the guard that would prevent this divergence is simply absent for this handler.

### Impact Explanation
A validly-signed `status` webhook for one stack causes `Hook.emit(:deployable_status, ...)` / `Hook.emit(:commit_status, ...)` to fire for a different stack's outbound webhook configuration, feeding that other tenant's external hook receiver with fabricated commit/deployable status events it never authenticated. This can also poison the affected stack's internal state (`create_status_from_github!` persists a `Status` row on the foreign stack's commit and can flip `deployable?`/trigger `schedule_continuous_delivery`, potentially auto-deploying that unrelated stack) [9](#0-8) . This is a record/action performed against a stack that did not authenticate this payload, matching the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable for any sha shared across stacks (most naturally, multiple stacks tracking the same repository).

### Likelihood Explanation
Requires: (1) a `status` event that is validly signed for some repository/org known to Shipit (attacker needs an ability to trigger a real GitHub status webhook, e.g. via a CI check on a branch/PR they control in a repo tracked by Shipit), and (2) a commit sha that also exists as a `Commit` row under a different `Stack` (trivially true when one repository is tracked by multiple stacks, e.g. staging/production, sharing common history). No secrets are needed beyond what GitHub itself sends for a legitimately triggered status event. This is a realistic, low-cost, repeatable multi-tenant configuration in Shipit deployments.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository's stacks, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha)).each { ... }` or equivalently filter `commit.stack` against `stacks` before calling `create_status_from_github!`, mirroring the pattern used in `PushHandler`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_cross_stack_test.rb
test "status webhook for repo A must not emit hooks for stack B sharing the same commit sha" do
  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack(repository: create_repository(owner: 'other-org', name: 'other-repo'))

  shared_sha = '1234567890abcdef1234567890abcdef12345678'
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'shared')
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'shared')

  payload = { 'sha' => shared_sha, 'state' => 'success', 'context' => 'ci', 'repository' => { 'full_name' => stack_a.github_repo_name } }

  Shipit::Hook.expects(:emit).with(:deployable_status, stack_a, anything)
  Shipit::Hook.expects(:emit).with(:deployable_status, stack_b, anything).never # currently FAILS: also fires for stack_b

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
This demonstrates that `Hook.emit` is invoked for `stack_b` despite the webhook only being signed/verified for `stack_a`'s repository.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
