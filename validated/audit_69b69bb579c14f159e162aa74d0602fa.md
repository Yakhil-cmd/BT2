### Title
`status` webhook applies commit-status writes across all repositories regardless of the authenticating organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App belonging to the organization named in the payload (`repository.owner.login`/`organization.login`), but `StatusHandler#process` never checks that binding when performing the corresponding write: it looks up commits by SHA alone, across every stack/repository tracked by the Shipit instance.

### Finding Description
The equality the engine is supposed to enforce is: `organization whose webhook secret verified the request == repository/stack the payload is allowed to mutate`.

- Signature verification is scoped per organization: `Shipit.github(organization: repository_owner)` picks the `GithubApp`/secret tied to the owner named in the payload, and `verify_webhook_signature` only proves the raw body was signed by *that* org's secret. [1](#0-0) 

- Every other handler that mutates state is scoped back to the repository named in the same payload via `Handler#stacks`/`#repository_name` (`payload.dig('repository', 'full_name')`), e.g. `PushHandler` only touches stacks belonging to that repository. [2](#0-1) [3](#0-2) 

- `StatusHandler`, however, never references `repository` at all. It only requires `sha` and `state`, and resolves the target via a global, unscoped `Commit.where(sha: params.sha)`, then calls `create_status_from_github!` on every matching commit in the database — irrespective of which stack/repository/organization that commit belongs to. [4](#0-3) 

Because Shipit explicitly supports multiple independently-configured GitHub organizations, each with its own `webhook_secret`/App credentials, in `config/secrets.yml` (see the multi-org schema in the dummy config), a party who legitimately controls (or is validly authenticated for) one configured organization's GitHub App can emit a signed `status` event whose `sha` matches a commit that actually belongs to a *different* organization's stack (e.g., shared history from a fork, mirrored monorepo, or any coincidental SHA collision across tracked repos), and Shipit will apply the status write to that unrelated commit. [5](#0-4) 

The write itself is not inert: `Commit#create_status_from_github!` → `#add_status` drives `deployable_status` webhook emission and enqueues `ProcessMergeRequestsJob`, and status transitions feed the stack's continuous-deployment pipeline. [6](#0-5) [7](#0-6) 

### Impact Explanation
This breaks the "organization authenticated versus repository written" binding: the signature proves authorship for org A, but the mutation lands on a commit/stack that may belong to org B. Since commit status state directly participates in the continuous-deployment/merge-queue gating logic, an attacker controlling org A's GitHub App/webhook credentials could flip a targeted commit in org B's stack from failing/pending to `success`, unblocking CI-gated deploys or merges for a repository they have no legitimate write access to — a cross-repository, cross-organization write with real downstream effect on the deploy pipeline. This aligns with the "cross-repository writes" / "unauthorized deploy or merge" Critical impact criteria.

### Likelihood Explanation
This is only reachable in deployments that configure Shipit with more than one GitHub organization (a documented, supported configuration), and it further requires that the attacker-controlled org's commit SHA collide with a commit tracked under the victim org's stack (realistic for forked/mirrored repositories that share git history, less so for wholly unrelated codebases). Likelihood is therefore conditioned on multi-org deployment and shared-history repositories, but the missing repository scoping is a concrete, unconditional code defect independent of any Shipit session, API token, or privileged account.

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler operating on `Commit`/`Stack` records) to the repository identified in the payload, mirroring the pattern already used by `PushHandler`/`Handler#stacks`: resolve `Repository.from_github_repo_name(repository_name)` first, then restrict the `Commit.where(sha: …)` lookup to commits belonging to that repository's stacks, rejecting the update if the payload's repository doesn't match.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (as supported by `config/secrets.yml`).
2. Attacker controls (or is validly authenticated to send webhooks for) `org-a`'s GitHub App and knows/produces a commit SHA that also exists in a Shipit stack under `org-b` (e.g., a shared upstream commit present in both a fork tracked by `org-a` and the canonical repo tracked by `org-b`).
3. Attacker sends a `status` webhook event signed with `org-a`'s `webhook_secret`, with `sha` set to that shared commit and `state: "success"`, omitting/ignoring `repository`.
4. `WebhooksController#verify_signature` validates the signature against `org-a`'s secret and passes.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on the matching commit that actually belongs to `org-b`'s stack, potentially flipping its deployable status and triggering `org-b`'s continuous-deployment/merge pipeline — despite the attacker never having been authenticated for `org-b`.
