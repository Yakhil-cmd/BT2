### Title
Cross-organization commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the GitHub App/organization it claims to belong to, using the `repository.owner.login` (or `organization.login`) field of the payload to select which organization's `webhook_secret` to check against. [1](#0-0) [2](#0-1)  Once that check passes, the `status` event is dispatched to `StatusHandler#process`, which updates commit status by looking up commits **solely by `sha`**, with no scoping to the repository/organization that was actually authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2)  This breaks the binding between "the organization whose webhook secret validated this request" and "the repository/stack whose commit is being written," unlike `PushHandler` and `CheckSuiteHandler`, which correctly scope their writes through `stacks`, itself derived from `Repository.from_github_repo_name(repository_name)` — the same owner/repo that was used for signature verification. [4](#0-3) [5](#0-4) 

### Finding Description
Shipit documents and supports hosting multiple, independently-trusted GitHub organizations behind a single Shipit instance, each with its own `webhook_secret` configured under `github.<org>.webhook_secret` in `secrets.yml`, all delivered to the same `/webhooks` endpoint. [6](#0-5)  `WebhooksController#verify_signature` picks the correct secret to verify against purely from the attacker-supplied JSON body (`repository.owner.login` / `organization.login`), then, if that organization's secret matches, allows the event through to the handler pipeline for **any** event type. [7](#0-6) 

For `push` and `check_suite` events, the handlers correctly re-derive the target `Repository`/`Stack` set from the same `repository.full_name` field used implicitly to select the org, so the entity being mutated is always scoped to the organization that was authenticated. [4](#0-3) [8](#0-7) 

`StatusHandler`, however, ignores the `repository` field entirely for its write path and instead performs a global, unscoped `Commit.where(sha: params.sha)` lookup across the whole `commits` table, then calls `commit.create_status_from_github!(params)` on every match, regardless of which stack/repository/organization owns that commit. [9](#0-8)  Because git commit SHAs are content-addressed, any two repositories that share history (forks, mirrors, vendored/monorepo splits, or repositories imported from the same upstream) can contain identical commit SHAs. An organization "Org A" that is a legitimately configured (but mutually distrusting) tenant of the same Shipit instance can send a validly-signed `status` webhook — signed with **Org A's own** `webhook_secret` — referencing a SHA that also exists in "Org B's" tracked stack. `verify_signature` will accept it (Org A's secret matches Org A's own claimed identity), but `StatusHandler` will write a commit status onto Org B's commit, because the lookup is not restricted to commits reachable from repositories owned by the authenticated organization.

Equality that is broken: `organization authenticated by verify_signature (payload.repository.owner.login / payload.organization.login)` ≠ `repository/stack whose Commit row is mutated by StatusHandler (Commit.where(sha:))`.

### Impact Explanation
Commit statuses set via this path feed directly into Shipit's CI/deployability gating logic (`Commit#create_status_from_github!`, consumed by stack/commit "deployable status" checks used before allowing a deploy). By forging a "success" status for a commit belonging to a stack it does not own, an attacker-controlled but legitimately-configured tenant organization can make an otherwise-failing or unchecked commit in a *different* organization's stack appear deployable, enabling an **unauthorized deploy** of that commit — one of the listed Critical impacts (cross-repository writes / unauthorized deploy). This requires no `ApiClient` token, no Shipit session, and no privileged GitHub role in the victim organization — only that the attacker's own organization is one of the (possibly several) organizations configured in the shared Shipit instance, and that a matching SHA exists in the victim's history (fork/mirror/shared-upstream scenario, which is common for infra shared across an ecosystem of forks).

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations sharing one instance (an explicitly documented, supported deployment mode), and (2) SHA overlap between the attacker's repository and the victim's repository (realistic for forks/mirrors/shared upstream history, not requiring a hash collision). Given these two realistic preconditions, the exploit needs only a normal, correctly-signed webhook delivery from the attacker's own GitHub App installation — no secret leakage, no session, no elevated privileges. Likelihood is moderate-to-high in the specific multi-tenant configuration this codebase supports and documents.

### Recommendation
Scope the `StatusHandler` commit lookup to the authenticated repository, mirroring `PushHandler`/`CheckSuiteHandler`: resolve the target stacks/commits through `stacks` (i.e., `Repository.from_github_repo_name(repository_name)`) rather than a bare, instance-wide `Commit.where(sha:)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, so a commit status can only be applied to commits belonging to repositories owned by the organization that was cryptographically authenticated for this specific webhook delivery.

### Proof of Concept
1. Shipit instance configured with two orgs in `secrets.yml`: `orgA` (attacker-controlled, legitimately installed GitHub App) and `orgB` (victim), per the documented multi-org setup. [6](#0-5) 
2. Org B tracks `orgB/victim-repo`, which shares commit history with `orgA/attacker-repo` (fork/mirror), so commit `sha=deadbeef...` exists in both.
3. Attacker triggers (or crafts) a `status` event on `orgA/attacker-repo` for `sha=deadbeef...` with `state=success`, correctly signed with Org A's `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner` to `orgA`, fetches Org A's `webhook_secret`, and the signature validates successfully. [10](#0-9) 
5. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, which matches the commit row belonging to `orgB/victim-repo`'s stack, and calls `create_status_from_github!` on it, marking it "success" in Org B's stack despite Org B never authorizing or sending this status. [3](#0-2) 
6. This forged success status can satisfy deploy-gating checks for Org B's stack, enabling deployment of a commit that Org B never approved via its own CI/webhook.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified

      ].join(' '))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
