### Title
Stack-scoped API tokens can read CCMenu status of any stack, bypassing `ApiClient#stack_id` binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to fetch `Stack.from_param!(params[:stack_id])` directly instead of using the inherited, scope-enforcing `stacks`/`stack` helpers from `BaseController`, so a token that is restricted to one stack can be used to fetch build status for every other stack.

### Finding Description
`ApiClient` records can be created with a `stack_id` to restrict them to a single stack: `Shipit::ApiClient belongs_to :stack, optional: true` [1](#0-0) . `Api::BaseController` enforces this binding for every controller that uses its `stacks`/`stack` helpers: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` and `stack = stacks.from_param!(params[:stack_id])` [2](#0-1) . `Api::StacksController` relies on this scoped helper, so a token bound to stack A returns only stack A from `#index`/`#show` [3](#0-2) .

`Api::CCMenuController`, however, redefines `stack` to bypass the scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [4](#0-3) . The controller still declares `require_permission :read, :stack` and authenticates the caller via `ApiClient.authenticate(params[:token])` [5](#0-4) , so the permission check (`read:stack`) passes for any token that has that permission, without checking whether the requested `stack_id` matches the token's bound `stack_id`.

The equality that should hold is: `token.stack_id == requested_stack.id` (when `stack_id` is set). `CCMenuController` breaks this: it checks only `token.permissions.include?('read:stack')`, and separately resolves `stack` from the raw `params[:stack_id]` with no relation to `token.stack_id`.

### Impact Explanation
An attacker holding *any* API token scoped to a single stack (e.g. a CCMenu token generated by `CCMenuUrlController#client`, or any operator-issued token restricted via the "assign to a stack" UI in `ApiClientsController`) can query `GET /api/stacks/:stack_id/ccmenu` for an arbitrary `stack_id` and obtain that other stack's `lastBuildStatus`, `activity` (deploying/sleeping), `lastBuildLabel` (deploy id), `lastBuildTime`, and `webUrl` [6](#0-5) . This is an unauthorized read of stack state across a trust boundary the token issuer explicitly set up (`stack_id` restriction), matching the High-severity "unauthenticated/unauthorized read of stack state" category.

### Likelihood Explanation
Exploitation requires only possession of a single, stack-restricted read-only API token — no privileged account, no webhook secret, and no session is needed. CCMenu tokens are routinely generated and embedded in third-party CI dashboard tools/URLs (via `CCMenuUrlController`), making them likely to leak or be shared more broadly than a general-purpose API credential, increasing the practical likelihood of this cross-stack read.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scope-enforcing helper instead of calling `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a stack-restricted token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Operator creates an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (e.g. via the CCMenu URL flow on stack A, or by assigning a stack to a token in the `ApiClientsController` UI).
2. Attacker (holder of that token, e.g. from a leaked CCMenu URL) sends:
   `GET /api/stacks/B/ccmenu?token=<token-scoped-to-A>`
3. `authenticate_api_client` succeeds (`ApiClient.authenticate` only checks signature validity) [7](#0-6) ; `require_permission :read, :stack` passes because the token has `read:stack` [8](#0-7) .
4. `stack` resolves stack `B` directly via `Stack.from_param!(params[:stack_id])`, ignoring that the token is bound to stack `A` [4](#0-3) .
5. The response discloses stack `B`'s deploy status/activity/build label, which the token was never authorized to access.
