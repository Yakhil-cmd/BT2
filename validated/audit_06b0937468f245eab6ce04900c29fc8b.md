## Analysis

The claimed vulnerability is real and supported directly by the code. I traced the full path:

**`PreStxOp::parse_from_tx`** (`stackslib/src/chainstate/burn/operations/stack_stx.rs`, lines 74-144) derives `output` purely by decoding the *first Bitcoin output address* of the PreStx transaction into a `StacksAddress` via `try_into_stacks_address()`. There is no check binding this output address to the public key(s) that signed the transaction's *inputs* — an attacker funds/signs the tx entirely with their own UTXOs and can put any Stacks address (a victim's) in `output`. [1](#0-0) 

**`StackStxOp::get_sender_txid`** only checks that the spending tx's first input references `vout == 1` of the PreStxOp tx (proving continuity of the two-tx pattern), not that the spender controls the address in `output`. [2](#0-1) 

**`burnchain.rs::classify_transaction`** then binds `sender = pre_stack_stx.output` (the victim-chosen address) directly into the `StackStxOp`, with zero re-validation. [3](#0-2) 

**`process_stacking_ops`** in `blocks.rs` finally calls `pox-4`'s `stack-stx` using `&sender.clone().into()` as the Clarity `tx-sender` — this is a raw programmatic invocation, not a signed Stacks transaction, so there is no signature check at all tying this call to the victim. [4](#0-3) 

Inside `pox-4.clar`'s `stack-stx`, the only checks are that `tx-sender` isn't already stacking/delegating and has sufficient balance, plus a `signer-key`/`signer-sig` check — but that signature authenticates only the **signer key** for reward-slot purposes, not the **stacker's** consent to lock their own STX. [5](#0-4) 

This burnchain-op path is still actively processed post-Nakamoto (epoch 3.0+), confirmed by `get_burnchain_txids_in_ancestor_tenures`/`process_stacking_ops` being invoked unconditionally in `nakamoto/mod.rs`. [6](#0-5) 

### Title
Burnchain `StackStxOp` locks STX of a Stacks address that never signed anything, keyed only by an attacker-chosen `PreStxOp` output field - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` sets the future stacker (`output`) from an unauthenticated Bitcoin output address chosen freely by whoever crafts the transaction, with no cryptographic link to the transaction's own inputs. An unprivileged attacker who funds and signs the `PreStxOp`/`StackStxOp` pair entirely with their own BTC UTXOs can set `output` to a victim's Stacks address, causing the node to invoke `stack-stx` with `tx-sender` set to the victim, locking the victim's STX without any Stacks or Bitcoin signature from the victim.

### Finding Description
The broken equality: **STX locked by an applied `StackStxOp` == STX owned by the Stacks address whose private key authorized the operation**. In this codebase, the `sender`/`tx-sender` bound to a `StackStxOp` is simply `PreStxOp.output`, a value copied from the first Bitcoin *output* address of an arbitrary attacker-controlled transaction — never validated against the identity of whoever signed the transaction's *inputs*.

Exploit flow:
1. Attacker crafts a `PreStxOp` Bitcoin transaction, funding/signing it entirely with their own BTC UTXOs, but sets the first output (`output`) to the victim's Stacks address (`try_into_stacks_address` accepts any legacy-format Bitcoin address).
2. `PreStxOp::parse_from_tx` accepts this with no validation tying `output` to the signer of the inputs.
3. Attacker spends `vout=1` of that same PreStxOp tx in a `StackStxOp` transaction (satisfying `get_sender_txid`'s `vout==1` check), again funded/signed solely by the attacker.
4. `burnchain.rs::classify_transaction` binds `sender = pre_stack_stx.output` (victim) into the resulting `StackStxOp`.
5. `process_stacking_ops` calls `pox-4`'s `stack-stx` with `tx-sender = victim`. The only guards inside `stack-stx` (`check-caller-allowed`, "not already stacking", "not delegating", sufficient balance, `signer-key`/`signer-sig`) authenticate none of the *stacker's* consent — `signer-sig` only proves the signer-key owner approved being used as the PoX signer for that pox-addr/cycle, not that the stacker agreed to lock their own funds.
6. The victim's STX becomes locked in `stacking-state` with zero signature ever produced by the victim.

### Impact Explanation
Critical: permanent freezing of the victim's staked STX for the chosen `num_cycles` lock period, with rewards routed to a `reward_addr` (also attacker-controlled, from the `StackStxOp`'s own recipient output) — an unsigned/unauthorized stacking action against a victim's balance. Repeatable against any Stacks address holding spendable STX and no existing `stacking-state` entry; cost to the attacker is only Bitcoin transaction fees.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: the victim must simply hold spendable STX and not currently be in `stacking-state`/delegating — properties an attacker can observe on-chain for any address. No cooperation, signature, or private key of the victim is required. The attack requires only standard Bitcoin transaction crafting skills and is executable by any unprivileged party at any reward cycle, including post-Nakamoto (epoch 3.0+) since `stacking_burn_ops` continue to be gathered and applied via `process_stacking_ops`.

### Recommendation
Cryptographically bind the `PreStxOp.output` (and therefore `StackStxOp.sender`) to the entity that actually controls the Bitcoin transaction's inputs — e.g., require the output address's hash160 to match the hash160 derived from the input-signing public key(s), or deprecate/disable the burnchain-op stacking path entirely in favor of Stacks-native signed `stack-stx` transactions (which already correctly bind `tx-sender` to a verified Stacks signature).

### Proof of Concept
Rust integration test plan (using existing harness patterns from `stacks-node/src/tests/neon_integrations.rs` / `nakamoto_integrations.rs` `pre_stx_op` tests):
1. Boot a regtest chainstate; create two keychains: `attacker` (funded BTC UTXOs) and `victim` (a Stacks address with a known STX balance and no `stacking-state` entry).
2. Attacker submits a `PreStxOp` with `output = victim_stx_addr`, signed only by the attacker's Bitcoin key (`btc_regtest_controller.submit_operation` as in existing `pre_stx_op` tests).
3. Attacker submits a `StackStxOp` spending `vout=1` of the prior tx, with `sender` implicitly resolved to `victim_stx_addr`, signed only by the attacker.
4. Mine blocks so both ops are processed.
5. Assert: `get_stacking_state_pox_4(peer, block, victim_stx_addr.to_account_principal())` returns `Some(..)` (victim now locked) — i.e., the equality "STX locked == STX whose owner signed" is violated — while asserting the victim's private key was never used to construct any transaction in the test.
