### Title
Webhook signature verification is silently skipped when `webhook_secret` is unset, allowing unauthenticated forged `membership` events to grant `Shipit.github_teams` access - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` derives the GitHub organization from the *unauthenticated* request body and looks up that org's `GitHubApp` to check the `X-Hub-Signature` header [1](#0-0) . The actual comparison is delegated to `GitHubApp#verify_webhook_signature`, which returns `true` unconditionally whenever the organization's `webhook_secret` is blank: `return true unless webhook_secret` [2](#0-1) . This is the exact analog of the report's binding break: "an organization that authenticated versus the repository that is written" — here, an organization whose signing secret is unset is treated as always "authenticated," so the payload's claimed identity (`params.dig('repository','owner','login')` / `params.dig('organization','login')`) is trusted without any cryptographic proof, even though it fully controls which handler logic executes against the datastore.

### Finding Description
The engine's own sample/dev secrets file documents `webhook_secret:` as an optional, nil-able key (`webhook_secret: # nil`) [3](#0-2) , and `GitHubApp#initialize` accepts a blank secret without error: `@webhook_secret = @config[:webhook_secret].presence` [4](#0-3) . When that field is left blank for any configured organization, `verify_webhook_signature` returns `true` for *any* payload claiming to be from that organization, regardless of the actual `X-Hub-Signature` header content [2](#0-1) .

Once `verify_signature` passes, `WebhooksController#create` parses the raw body and dispatches it, unmodified, to all registered handlers for the claimed event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [5](#0-4) . For the `membership` event, this reaches `MembershipHandler#process`, which trusts the attacker-supplied `organization.login`, `team` block, and `member.login` to create a `Team` (if not already known) and unconditionally add or remove that member: `team.add_member(member)` / `team.members.delete(member)` [6](#0-5) .

`Shipit::Team` membership is exactly the authorization gate used by the application: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) , and `Authentication#force_github_authentication` denies access to any logged-in user that is not `authorized?` [8](#0-7) . Therefore an unprivileged attacker who has (a) a valid GitHub login/session with Shipit (any GitHub account can complete OAuth login) and (b) knowledge/guess that a target organization has no `webhook_secret` configured, can POST a forged `membership` "added" event naming their own `member.login` and any `team.id`/`github_id` belonging to one of `Shipit.github_teams`, and thereby self-grant membership in that team — bypassing the real GitHub organization membership check entirely.

### Impact Explanation
This breaks the "GitHub identity versus the `User` bound to the session" / authorization-team trust boundary: `Shipit.github_teams` is meant to reflect actual GitHub org/team membership fetched via the GitHub API (`Team#refresh_members!`), but the webhook path lets an attacker directly manipulate the `Shipit::Membership` join table without any GitHub-verified proof, as long as the org's webhook secret is unset. This is an escalation into `Shipit.github_teams` authorization, which the rules explicitly list as a High-impact outcome.

### Likelihood Explanation
Exploitation requires only an HTTP POST to `/webhooks` with a crafted JSON body and correctly guessed `X-Github-Event: membership` header — no `ApiClient` token, `webhook_secret`, or GitHub App private key is needed. The only precondition is that the targeted organization's `webhook_secret` is blank, a state the codebase's own documented/sample configuration (`config/secrets.development.shopify.yml`) treats as valid and unremarkable, and which `GitHubApp` accepts silently with no warning or hard failure. Any organization operator who has not explicitly set a webhook secret (e.g., during initial setup, before webhooks are configured on the GitHub side, per `docs/setup.md`'s explicit instruction to set `webhook_secret: some-secret-value`) is exposed for as long as that configuration gap exists. This is a plausible, not merely theoretical, misconfiguration state that the code path actively normalizes.

### Recommendation
Fail closed instead of open when `webhook_secret` is blank: reject all webhook deliveries for organizations without a configured secret (or refuse to boot/serve the endpoint for such organizations) rather than treating an absent secret as automatically verified. Additionally, `MembershipHandler` should not be able to grant membership in a `Team` that wasn't already provisioned/known to correspond to that `organization.login`, and any privilege-bearing side effects of webhook processing should be gated on a signature check that cannot be bypassed by configuration omission.

### Proof of Concept
1. Ensure (or wait for) a target organization to be configured in `Shipit.github(organization: 'target-org')` with `webhook_secret` blank (as the shipped sample config demonstrates is a supported state).
2. As an unprivileged attacker with any Shipit session (a normal, unauthorized GitHub login that has completed OAuth but is not yet a member of `Shipit.github_teams`), send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <id_of_authorized_team_github_id>, "name": "Whatever", "slug": "whatever", "url": "https://example.com" },
  "organization": { "login": "target-org" },
  "member": { "login": "<attacker_github_login>" }
}
```
3. `verify_signature` calls `GitHubApp#verify_webhook_signature` for `target-org`, which returns `true` immediately because `webhook_secret` is blank, regardless of the (absent/garbage) `X-Hub-Signature` header [2](#0-1) .
4. `MembershipHandler#process` runs `find_or_create_team!` and `team.add_member(member)`, adding the attacker's `User` record to the authorized `Team` [6](#0-5) .
5. On the attacker's next request, `User#authorized?` now returns `true` because their `teams` includes an id in `Shipit.github_teams`, granting them full access to Shipit despite never having been a real member of the GitHub organization/team [7](#0-6) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
