### Title
Cross-repository forged CI status injection via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a new `Status` to using only `Commit.where(sha: params.sha)`, with no filter on the repository named in the webhook payload. Because the `shipit_commits` table's uniqueness constraint on `sha` is scoped to `(sha, stack_id)` rather than global, any stack whose `Commit` row happens to share a sha with another stack's commit (e.g. a fork sharing history, or a deliberately reconstructed identical commit object) receives a forged `Status`, and that status feeds directly into `Shipit::MergeRequest#all_status_checks_passed?`.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name')` (the repository the webhook claims to be from, and whose signature was verified) `== stack.repository` for every `Commit` the handler mutates. That equality is enforced by the shared `Handler#stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), which resolves `Repository.from_github_repo_name(repository_name)&.stacks` and is correctly used by `PushHandler#process` (`stacks.not_archived.where(branch:)`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`).

`StatusHandler`, however, never reads `payload['repository']` at all: [1](#0-0) 
It does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a database-wide lookup across every stack/repository ever synced into Shipit, using only the attacker-suppliable `sha` field.

`create_status_from_github!` then creates the `Status` using `commit.stack_id`, i.e. whatever stack the matched `Commit` row actually belongs to, not the stack tied to the webhook's own repository: [2](#0-1) 

The DB schema confirms this is exploitable: the unique index on `commits` is `(sha, stack_id)`, not `sha` alone — [3](#0-2) 
— meaning the same sha is expected to legitimately exist across multiple different stacks (e.g. two stacks tracking a fork relationship, or two repositories that briefly shared history), each with its own `Commit` row.

The resulting forged `Status` is then consumed unconditionally by `MergeRequest`: [4](#0-3) 
via `Commit#statuses_and_check_runs` and `Status::Group`: [5](#0-4) [6](#0-5) 

Why existing guards don't stop this: `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed with the webhook secret belonging to whatever `repository_owner`/organization the attacker put in the payload — it authenticates "a known GitHub org sent this," not "this org owns the commit being mutated." `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`) never require or validate a `repository` field, so nothing downstream re-establishes the missing binding. `Repository`/`Stack` model validations don't apply here because the write path never touches `Repository.from_github_repo_name` at all.

### Impact Explanation
An attacker who controls a repository whose GitHub App/org webhook is wired into the same Shipit instance (a realistic setup wherever Shipit serves multiple repositories/orgs off one GitHub App installation, or wherever the attacker's own repo is a legitimately onboarded Shipit stack) can create arbitrary `Status` rows attached to a victim's `Commit`/stack merely by having a commit sha collision with the victim's pending PR head — achievable via forking (forks retain identical shas for shared history) with no interaction with `victim/prod` at all. This flips `MergeRequest#all_status_checks_passed?`/`any_status_checks_failed?`/`any_status_checks_missing?` to reflect fabricated data, which the merge queue (`reject_unless_mergeable!`, `merge!`) uses to decide whether to auto-merge a PR into `victim/prod`. This is a genuine cross-tenant record write (one repository's webhook mutating another repository's stack data) that can enable an unauthorized merge — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any stack/commit sha the attacker can reproduce, and the blast radius spans every stack hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: `merge_queue_enabled?` on the victim stack; the attacker's own repository must be able to deliver a validly-signed `status` webhook to the same Shipit `/webhooks` endpoint (i.e. their repo/org is one Shipit already trusts — a common multi-tenant Shipit deployment scenario); and the attacker must produce a `Commit` row in Shipit whose `sha` matches the victim's PR head — trivially achievable by forking the victim repo (fork commit shas are identical to upstream until divergence) and letting Shipit sync that fork as a stack, or via any other means that gets an identical sha into their own tracked stack. No Shipit session, API token, or Shipit/GitHub secret is required beyond what the attacker already legitimately has for their own repository. This is a moderate-cost but fully unprivileged and repeatable attack against any Shipit instance shared across tenants/orgs.

### Recommendation
Scope `StatusHandler#process` (and any handler that looks up commits/stacks) to the repository named in the webhook payload, mirroring `Handler#stacks`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
so that the `Status` is only ever attached to a `Commit` belonging to a stack whose `Repository` matches `payload['repository']['full_name']`, restoring the repository-of-webhook == repository-of-mutated-record binding.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar under `test/`):
1. Create two `shipit_stacks` fixtures, `victim_stack` (repository `victim/prod`, `merge_queue_enabled: true`) and `attacker_stack` (repository `attacker/evil`).
2. Create two `shipit_commits` fixtures with the **same** `sha` value, one belonging to `victim_stack` (`victim_commit`) and one belonging to `attacker_stack` (`attacker_commit`).
3. Create a `shipit_merge_requests` fixture on `victim_stack` whose `head` resolves to `victim_commit`; assert `victim_commit.statuses_and_check_runs` is empty and `merge_request.all_status_checks_passed?` is `false`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call({ 'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/travis', 'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'attacker' } } })` (bypassing the controller's signature check, as the flaw is in the handler itself, or going through the controller with `GithubApp#verify_webhook_signature` stubbed true for the attacker org).
5. Assert `victim_commit.reload.statuses.count == 1` (a `Status` was created against the **victim's** commit even though the payload named `attacker/evil`).
6. Assert `merge_request.reload.all_status_checks_passed?` is now `true`, proving the equality `repository-of-webhook == repository-of-mutated-record` was violated and cross-tenant merge forgery occurred.
