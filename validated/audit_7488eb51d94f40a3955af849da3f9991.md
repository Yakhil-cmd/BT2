## Analysis

The GHSA-r578-pj6f-r4ff report describes an "auto-merge" flaw: a new, uncontrolled identity is silently bound to an existing account merely because loosely-verified attributes match, without any real proof of joint consent, letting an attacker hijack control. The closest analog in `ocore--002` is in the shared-address negotiation protocol (`wallet_defined_by_addresses.js`), where a message from any already-paired device is auto-accepted and merged into the victim's own address book without verifying that a legitimate multi-party negotiation actually occurred.

### Title
Unauthenticated `new_shared_address` message lets a paired device silently register an attacker-controlled shared address that impersonates joint control of the victim's own address - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress` accepts a fully attacker-defined address/definition/signers payload from any already-paired correspondent and, via `determineIfIncludesMeAndRewriteDeviceAddress`, automatically "merges" the victim's own address into a brand-new shared-address record — without ever checking that this shared address was the product of a genuine multi-step negotiation (`create_new_shared_address` → `approve_new_shared_address`).

### Finding Description
`wallet.js` dispatches the `new_shared_address` subject directly to `walletDefinedByAddresses.handleNewSharedAddress` for any sender already present in `correspondent_devices` (i.e., any paired device, even one paired long ago or via a low-trust bot): [1](#0-0) 

`handleNewSharedAddress` only performs structural checks (definition/c-hash consistency, address format, signer/definition path consistency) — it never verifies that the sender was an expected participant in a prior `pending_shared_addresses` negotiation: [2](#0-1) 

Crucially, `determineIfIncludesMeAndRewriteDeviceAddress` looks up whether any address referenced in the attacker-supplied `signers` map matches one of the victim's own `my_addresses`/`shared_addresses`, and if so, silently claims that address as belonging to "me" (the victim), even though the victim never agreed to be part of this new address: [3](#0-2) 

The record is then permanently written via `addNewSharedAddress`, with no user confirmation gate in between: [4](#0-3) 

The legitimate design intends `new_shared_address` to be sent only "after the initiator collects approvals from all members" via the `create_new_shared_address`/`approve_new_shared_address` handshake, but `wallet.js`'s switch statement never handles `create_new_shared_address` from the network side (only `approve_new_shared_address`/`reject_new_shared_address`/`new_shared_address` are wired), and `handleNewSharedAddress` has no cross-check against any `pending_shared_addresses` record. This means the entire negotiation state machine is not enforced on receipt — an attacker can skip straight to `new_shared_address` with an arbitrary definition.

Once inserted, this bogus shared address is treated identically to a genuinely negotiated one everywhere else in the codebase: it is included in `readMyAddresses`/`readMyPersonalAndSharedAddresses` (treated as one of the user's own receiving addresses): [5](#0-4) 

It also participates in private-payment "received" classification and cosigner resolution: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because `handleNewSharedAddress` cannot distinguish an attacker-crafted definition from a legitimately negotiated one, and because the definition/signers content is entirely attacker-controlled (subject only to generic oscript syntax validation), the attacker can construct an `"or"` definition such as `["or",[["address","$victim_addr"],["address","$attacker_addr"]]]`. After this is merged into the victim's `shared_addresses`, the victim's wallet UI/APIs (contacts, "shared" balance/cosigner views, payment notifications) present this address as a jointly-controlled address that includes the victim, implying dual-signature protection. In reality, the `OR` branch lets the attacker unilaterally spend any funds sent to that address — whether sent by the victim (who mistakenly believes it's protected by their own key) or by any third party who trusts the apparent joint-control relationship with the victim's identity. This is a form of fund loss/theft enabled purely by an unauthenticated "merge" of address ownership, matching the auto-merge/spoofed-identity bug class from the advisory.

### Likelihood Explanation
Any device that has ever been paired with the victim (bots, casual contacts, revoked-trust peers not yet unpaired) can send this single message; no additional privilege, timing, or race condition is required. The whole `pending_shared_addresses` approval mechanism is dead code on the receiving side, so there is no functional barrier preventing an out-of-band `new_shared_address` message from being accepted as final.

### Recommendation
- In `handleNewSharedAddress`, require and verify a matching, in-progress `pending_shared_addresses` record (keyed by `address_definition_template_chash`) with an approval entry from `from_address` before accepting a finalized `new_shared_address`, rather than accepting any well-formed but unsolicited payload.
- In `determineIfIncludesMeAndRewriteDeviceAddress`, do not silently attribute "my" addresses to unsolicited shared-address definitions; require explicit user confirmation (an event requiring UI approval) before writing to `shared_addresses`/`shared_address_signing_paths`, analogous to the wallet-by-keys `create_new_wallet` flow which does emit a confirmation event before persisting anything.
- Reject `OR`-style definitions (or definitions whose consenting signer's branch is bypassable by another party alone) from being classified/exposed as "shared" in `readMyAddresses`, `readSharedAddressCosigners`, and payment-notification address-type resolution unless the user has explicitly reviewed the definition.

### Proof of Concept
1. Attacker device A pairs with victim device V (or was paired previously as a bot/casual contact) so that `correspondent_devices` on V contains A.
2. V has an existing `my_addresses` entry `VICTIM_ADDR` (e.g., its main wallet address).
3. A crafts `arrDefinition = ["or", [["address","VICTIM_ADDR"], ["address","ATTACKER_ADDR"]]]`, computes `address = objectHash.getChash160(arrDefinition)`, and builds `signers = { "r.0": {address: "VICTIM_ADDR"}, "r.1": {address: "ATTACKER_ADDR", device_address: A} }`.
4. A sends device message `{subject: "new_shared_address", body: {address, definition: arrDefinition, signers}}` directly to V, without any prior `create_new_shared_address`/approval exchange — see `wallet.js:236-245` dispatch and `wallet_defined_by_addresses.js:378-415` handling.
5. `determineIfIncludesMeAndRewriteDeviceAddress` (`wallet_defined_by_addresses.js:279-315`) finds `VICTIM_ADDR` in `my_addresses`, rewrites its `device_address` to V, and `addNewSharedAddress` persists the shared address on V with no confirmation prompt.
6. `address` now shows up in V's `readMyAddresses`/shared-address lists as if it were a legitimate multisig address involving V, while A alone can spend any coins sent to it via the `OR` branch, resulting in fund loss for whoever (V or a third party) is misled into treating it as protected joint control.

// Checks if any of my payment addresses is mentioned.
// It is possible that my device address is not mentioned in the definition if I'm a member of multisig address, one of my cosigners is mentioned instead
function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

// returns information about cosigner devices
function readSharedAddressCosigners(shared_address, handleCosigners){
	db.query(
		"SELECT DISTINCT shared_address_signing_paths.device_address, name, "+db.getUnixTimestamp("shared_addresses.creation_date")+" AS creation_ts \n\
		FROM shared_address_signing_paths \n\
		JOIN shared_addresses USING(shared_address) \n\
		LEFT JOIN correspondent_devices USING(device_address) \n\
		WHERE shared_address=? AND device_address!=?",
		[shared_address, device.getMyDeviceAddress()],
		function(rows){
			if (rows.length === 0)
				throw Error("no cosigners found for shared address "+shared_address);
			handleCosigners(rows);
		}
	);
}

	});

function readSharedAddressPeers(shared_address, handlePeers){
	db.query(
		"SELECT DISTINCT address, name FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) \n\
		WHERE shared_address=? AND shared_address_signing_paths.device_address!=?",
		[shared_address, device.getMyDeviceAddress()],
		function(rows){
			// no problem if no peers found: the peer can be part of our multisig address and his device address will be rewritten to ours
		//	if (rows.length === 0)
		//		throw Error("no peers found for shared address "+shared_address);
			var assocNamesByAddress = {};
			rows.forEach(function(row){
				assocNamesByAddress[row.address] = row.name || 'unknown peer';
			});
			handlePeers(assocNamesByAddress);
		}
	);
}
