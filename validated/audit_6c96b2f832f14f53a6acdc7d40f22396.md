### Title
ReDoS heuristic `_has_redos_structure` misses bounded-quantifier and backreference catastrophic-backtracking shapes, allowing a malicious committed `security-patterns.yaml` regex to hang every hook invocation - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_has_redos_structure` only flags two narrow shapes — unbounded `+`/`*`/`?` immediately after a nested-quantifier group, and single-level alternation-under-repetition with a literal-prefix overlap — leaving whole classes of catastrophic-backtracking regexes undetected. Because `_validate_pattern` relies solely on this heuristic before `re.compile`, an attacker who commits a `.claude/security-patterns.yaml` can smuggle a pattern that passes validation and is later `re.search`'d against every edited file's diff content on each `PostToolUse` hook call, causing the hook to hang or run exponentially/polynomially slower.

### Finding Description
`_validate_pattern` (plugins/security-guidance/hooks/extensibility.py:199-244) calls `_has_redos_structure(regex)` and, if it returns `False`, accepts the regex into the rule set with only a `re.compile` syntax check [1](#0-0) . The heuristic itself is very narrow: [2](#0-1) 

1. `_REDOS_SHAPES[0]` (`\([^()]*[+*][^()]*\)[+*?]`) only fires when the quantifier immediately following the closing paren is `+`, `*`, or `?`. Any nested-quantifier group using a *bounded but still unbounded-in-effect* repetition such as `{50,}` (or even large `{n,m}`) is not "+*?", so `(a+){50,}` — which is structurally identical to the classic `(a+)+` catastrophic case — is never matched.
2. There is no handling at all for backreference-driven blowups such as `(a+)\1+` or `(.+)\1{2,}`. The closing `)` is followed by `\1`, not by a quantifier character, so `_REDOS_SHAPES` never matches, and there's no alternation for `_ALT_UNDER_REP` to catch either.
3. `_ALT_UNDER_REP` only inspects alternation *inside a single group immediately followed by a repetition operator*, using `[^()]*` branch matching (so it can't even see across nested parens). It has no concept of multiple adjacent/concatenated quantified groups over overlapping character classes (e.g. `(a*)(a*)(a*)(a*)b`), which is a well-known polynomial/exponential ReDoS shape that doesn't require alternation or nesting at all.

Since `re.compile` only validates syntax, none of these bypasses are caught anywhere else in the pipeline, and the accepted rule (`rule["regex"] = regex`) is stored in `_user_patterns` and returned by `user_patterns()` [3](#0-2)  for use alongside the built-in `SECURITY_PATTERNS` regex rules that are matched against edited file content on every `PostToolUse` invocation, as documented in the module's own trust-model comment [4](#0-3) .

### Impact Explanation
A single malicious but syntactically valid regex committed in `.claude/security-patterns.yaml` — ordinary repo content, no elevated privilege needed — is loaded on every hook session via `_load_user_patterns` → `load_for_session`, and matched against every file touched by every future edit. A carefully crafted catastrophic pattern (bounded-quantifier nesting or backreference blowup) can make a single `re.search` call take super-linear/exponential time on adversarial-looking (or even coincidentally long/ambiguous) file content, hanging or massively slowing the `PostToolUse` security-review hook for every contributor working in that repository — a functional denial-of-service against the security gate itself.

### Likelihood Explanation
Feasible and repeatable: the only precondition is committing a `security-patterns.yaml`/`.json`/`.yml` file under `.claude/`, which is normal, unprivileged repository content (project-level, not requiring admin/maintainer rights on the victim's machine). No social engineering beyond a normal PR/commit is needed since the file is auto-discovered by `_config_paths` at every hook invocation for anyone using the repo with Claude Code.

### Recommendation
Do not rely purely on structural heuristics for ReDoS prevention. At minimum:
- Extend `_REDOS_SHAPES` to also treat bounded quantifiers (`{n,}`, `{n,m}` with large `n`/`m`) after a group containing an inner quantifier the same as `+`/`*`, not just `[+*?]`.
- Add a check for backreferences (`\N` or `(?P=name)`) combined with any repetition inside or around the referenced group.
- Detect concatenated/adjacent quantified groups that share overlapping character classes (not just alternation-in-one-group).
- More robust: enforce a hard execution-time or step-count budget when actually running user-supplied regexes (e.g., via a regex engine with backtracking limits, or by running `re.search` in a subprocess/thread with a timeout and dropping the rule if it times out on a worst-case probe string), rather than trying to statically prove safety.

### Proof of Concept
Unit/fuzz test in `plugins/security-guidance/hooks/` test suite:
```python
import re, time
from extensibility import _has_redos_structure

BYPASS_PATTERNS = [
    r"(a+){50,}",          # bounded-quantifier nested repetition, not "+*?"
    r"(a+)\1+",            # backreference-based blowup
    r"(a*)(a*)(a*)(a*)(a*)(a*)(a*)b",  # concatenated overlapping quantified groups
]

def worst_case_time(pattern, n=28):
    rx = re.compile(pattern)
    start = time.monotonic()
    rx.search("a" * n + "!")
    return time.monotonic() - start

for p in BYPASS_PATTERNS:
    assert _has_redos_structure(p) is False   # demonstrates heuristic bypass
    assert worst_case_time(p) > 2.0           # demonstrates real catastrophic blowup
```
Expected result today: `_has_redos_structure` returns `False` for all three patterns (bypass confirmed) while `worst_case_time` exceeds several seconds on a modest 28-character adversarial input, demonstrating that `_validate_pattern` would accept these into `_user_patterns` and they would later hang `re.search` calls on `PostToolUse`.

```python
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")


def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
```
