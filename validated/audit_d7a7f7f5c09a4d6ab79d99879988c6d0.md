## Confirmed: Cross-org signature verification does not bind to the resolved repository

The equality that must hold is: **organization used to compute the webhook HMAC == organization that owns the repository the handler subsequently mutates**. This binding is broken.

### The broken binding

`WebhooksController#verify_signature` derives the verifying organization exclusively from the payload's `repository.owner.login` (or `organization.login`) field: [1](#0-0) [2](#0-1) 

It then calls `Shipit.github(organization: repository_owner).verify_webhook_signature` — so the HMAC is checked against the secret configured for whatever `owner.login` string the attacker put in the JSON. There is no check that this equals `repository.full_name`.

Downstream, `UnlabeledHandler#repository` resolves the actual `Shipit::Repository` record to mutate using a **separate** field, `params.repository.full_name`: [3](#0-2) 

`Shipit::Repository.from_github_repo_name` splits this string on `/` and does a plain DB lookup with no relation back to whichever org's secret validated the request: [4](#0-3) 

### Exploit flow

An attacker who legitimately owns a Shipit-integrated org ("attacker-org", with a real GitHub App/webhook secret configured for it) can:

1. Craft an arbitrary JSON POST to `/webhooks` (not through GitHub) with:
   - `repository.owner.login` = `"attacker-org"` (so `verify_signature` picks attacker-org's known secret and the attacker can correctly HMAC-sign the raw body)
   - `repository.full_name` = `"victim-org/victim-repo"` (a repository the attacker does not control)
   - `pull_request.labels` = `[]` (label removed), `number` = victim PR number, `action` = `"unlabeled"`
2. Because the signature check only cares about `owner.login` (attacker-org), the forged, self-signed payload passes `verify_signature`.
3. `UnlabeledHandler#repository` loads the **victim** repository via `full_name`, and `stack` resolves the victim's `ReviewStack` for `environment = "pr#{number}"` via `ReviewStackAdapter`.
4. `archive?`/`unarchive?` logic flips based on `pull_request.labels` in the (attacker-authored) payload, so `stack.archive!` or `stack.unarchive!` executes against the victim's review stack, changing its provisioning/eligibility state — e.g., removing a `prevent_with_label` label unlocks `unarchive!`, re-queueing provisioning (`ReviewStackProvisioningQueue.add`) for a stack the attacker never authenticated.

None of the listed guards prevent this: `verify_signature` validates a signature scoped to `owner.login`, not `full_name`; `ExplicitParameters` only validates types/presence, not cross-field consistency; `drop_unhandled_event` and `check_if_ping` are irrelevant; `EnvironmentVariables#permit`, `Stack` environment format validators, and `Repository` format validators only constrain string shape, not ownership binding to the signing org.

### Caveat / what I could not fully verify

This requires the attacker to actually control (or have installed) a legitimate GitHub App/webhook integration for at least one org known to Shipit (`config[:webhook_secret]` configured for `attacker-org`), which is consistent with the threat model ("any GitHub user who can... emit webhooks from a repository they own"). I could not find any code anywhere in the request path that cross-checks `repository.owner.login` against `repository.full_name`'s owner segment — the split is a distinct, independent field, confirmed by reading `WebhooksController`, `UnlabeledHandler`, `ReviewStackAdapter`, and `Repository.from_github_repo_name` in full.

### Title
Cross-org webhook signature verification does not bind to the repository mutated by `UnlabeledHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` validates the webhook HMAC using the organization named in `repository.owner.login`/`organization.login`, while `Shipit::Webhooks::Handlers::PullRequest::UnlabeledHandler` resolves and mutates the target repository/review stack using the independent `repository.full_name` field. An attacker who controls a legitimately-registered org can forge a signed payload naming a victim's repo in `full_name`, flipping the victim review stack's archive/provisioning state.

### Finding Description
Broken binding: `verifying_org (params.repository.owner.login)` == `mutated_repo_org (params.repository.full_name.split('/').first)`. Trace: `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) uses only `repository_owner` (line 59-62) to select the `GitHubApp` whose secret validates `X-Hub-Signature`. `UnlabeledHandler#repository` (lines 59-63) and `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) resolve the record purely from `full_name`, an attacker-supplied string with no enforced relationship to `owner.login`. Root cause: two independently-attacker-controlled JSON fields are used for two different security-relevant purposes (auth vs. authorization target) with no consistency check.

### Impact Explanation
An attacker with a legitimate Shipit-integrated org can flip a victim review stack's archived/provisioning state (`stack.archive!` / `stack.unarchive!`, re-queues `ReviewStackProvisioningQueue`), i.e., "a payload for one repository mutating another's stack" — matching the Critical impact category. This is repeatable against any victim repository/PR number the attacker chooses, as long as a matching `ReviewStack` exists, cross-tenant.

### Likelihood Explanation
Requires the attacker to control one Shipit-registered org (own webhook secret) — a low bar consistent with the stated attacker capability of "any GitHub user who can... emit webhooks from a repository they own." No victim secrets, session, or API token needed; attacker only crafts a raw HTTP POST with a valid HMAC of their own choosing body content.

### Recommendation
In `WebhooksController`, after signature verification, additionally verify that `repository_owner` (used for the signature) matches the owner segment of `params.dig('repository','full_name')` before dispatching to handlers, or have handlers resolve the repository from the same `owner.login`/`organization.login` field that verified the signature rather than trusting `full_name` independently.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/pull_request/unlabeled_handler_test.rb`):
1. Configure two orgs in `Shipit.github_config`-equivalent test secrets: `attacker-org` (with secret `S_A`) and `victim-org` (with secret `S_V`, unknown to attacker/test-simulated-attacker path).
2. Create `victim-org/victim-repo` `Repository` with `provisioning_behavior: :prevent_with_label`, and a `ReviewStack` for `environment: "pr1"` that is currently `archived: false` (unarchived, i.e., provisioned) because the protective label is present.
3. Build payload JSON with `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `action = "unlabeled"`, `number = 1`, `pull_request.labels = []` (label removed).
4. Sign the raw body with `S_A` (attacker-org's secret) and POST to `/webhooks` with header `X-Github-Event: pull_request`.
5. Assert response is `200`/`204` (accepted) and assert `victim_stack.reload.archived?` flips to `true` (or false depending on setup) — proving the victim's review stack state changed from a request whose only valid credential belonged to `attacker-org`, not `victim-org`.
