### Title
Webhook dispatch/handler processing carries no org binding to the org verified by `verify_signature`, enabling cross-tenant `PullRequest` mutation - ([File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`WebhooksController#verify_signature` selects a GitHub App/secret using `repository.owner.login` from the raw JSON body, but `Shipit::Webhooks.for_event(event)` dispatches handlers purely by the `X-Github-Event` header, and `AssignedHandler` independently resolves the target `Repository`/`PullRequest` using `params.repository.full_name` from that same attacker-controlled body. Because `owner.login` and `full_name` are never cross-checked, and because `verify_webhook_signature` trivially returns `true` for any org with no `webhook_secret` configured, a forged payload can pass verification "as" one org while mutating a `PullRequest` that belongs to a completely different, unrelated repository/stack.

### Finding Description
Binding claimed (and broken): `verification_org (params.repository.owner.login used in verify_signature)` **==** `handler_processing_org (params.repository.full_name used inside AssignedHandler#repository)`. In this codebase these two reads are entirely decoupled.

Code path:
1. `WebhooksController#verify_signature` picks the GitHub App/secret by `repository_owner`, which is read as `params.dig('repository', 'owner', 'login')`: [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that org: [3](#0-2) 
3. `Shipit::Webhooks.for_event(event)` dispatches purely by the event string from the `X-Github-Event` header, with zero organization parameter: [4](#0-3)  and the controller calls every returned handler with the same raw `params`: [5](#0-4) 
4. `AssignedHandler` resolves the repository/PR to mutate strictly from `params.repository.full_name`, a field the schema only requires to be a `String` — no format/consistency check tying it to `owner.login`: [6](#0-5) [7](#0-6) 

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: pull_request` and a JSON body where `repository.owner.login` = an org configured in Shipit with no `webhook_secret` set (verification trivially succeeds regardless of `X-Hub-Signature`), while `repository.full_name` = `"victim-org/victim-repo"` — a completely different, tracked repository. `verify_signature` passes because it only inspects `owner.login`'s org config. `for_event('pull_request')` returns the default handler chain, including `AssignedHandler`, with no org awareness at all. `AssignedHandler#process` then looks up `Shipit::PullRequest` by `number` scoped to the repository resolved from `full_name` (the victim org), and calls `pull_request.update(github_pull_request: params.pull_request)`, mutating title, additions/deletions, labels, assignees, and head commit of a PR belonging to a tenant the attacker never authenticated against.

Existing guards fail to prevent this because: `verify_signature` only ever authenticates the org named in `owner.login`; it never re-derives or checks `full_name`'s owner. The `ExplicitParameters` schema (`params do ... end`) only enforces types/presence, not cross-field consistency. `drop_unhandled_event` only checks that handlers exist for the event, not org context.

### Impact Explanation
A successfully forged/misconfigured-org webhook results in mutation of a `PullRequest` record (title, labels, assignees, head commit) for a repository/stack that the attacker never authenticated for — this is a payload for one repository mutating another's records, matching the Critical impact category. It's repeatable for any PR number in any tracked repository, and the same lack-of-binding pattern is shared across the other `PullRequest::*Handler`s (`ClosedHandler`, `EditedHandler`, `LabeledHandler`, etc.), all of which resolve `repository` from `params.repository.full_name` independent of the org used for signature verification, widening blast radius to stack archival/unarchival and provisioning behavior across tenants.

### Likelihood Explanation
Exploitability depends on getting `verify_signature` to pass for an `owner.login` that is a configured org in Shipit — either because that org has no `webhook_secret` set (a real, code-supported degraded state: `return true unless webhook_secret`), or via other means covered by the question's stated precondition ("for any reason"). No Shipit session, API token, or GitHub secret is needed by the attacker in the no-secret case; they only need to know one configured org name with no secret and the target `full_name`/PR `number`, both of which are public GitHub metadata. This is a config-dependent but plausible and repeatable path, and the underlying code defect (no binding between verification org and processing org) is unconditionally present regardless of that precondition.

### Recommendation
Bind the two contexts explicitly: after `verify_signature` succeeds, pass the verified `repository_owner`/org down to handlers, and have each handler (e.g. `AssignedHandler#repository`) verify that `params.repository.full_name`'s owner matches the org that was cryptographically verified, rejecting the webhook otherwise. Additionally, treat an org with no configured `webhook_secret` as unverifiable (fail closed) rather than `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
```ruby
test "cross-org payload can mutate a PullRequest belonging to a different repository" do
  victim_pr = shipit_pull_requests(:review_stack_review) # belongs to org "shopify"/repo tracked in fixtures
  payload = payload_parsed(:pull_request_assigned)
  payload["number"] = victim_pr.number
  payload["pull_request"]["number"] = victim_pr.number
  payload["repository"]["full_name"] = victim_pr.stack.repository.full_name # victim org/repo
  payload["repository"]["owner"] = { "login" => "attacker-org-no-secret" } # org configured w/ no webhook_secret

  @request.headers['X-Github-Event'] = 'pull_request'
  # Simulate the no-secret-org bypass instead of stubbing verify_signature globally:
  Shipit.stubs(:github).with(organization: "attacker-org-no-secret")
        .returns(stub(verify_webhook_signature: true)) # mirrors `return true unless webhook_secret`

  assert_changes -> { victim_pr.reload.title } do
    post :create, body: payload.to_json, as: :json
  end
end
```
Assert both sides of the equality explicitly before/after: `payload["repository"]["owner"]["login"]` (org used by `verify_signature`) != `payload["repository"]["full_name"]`'s owner (org used by `AssignedHandler#repository`), and show `victim_pr.reload.title` still changes — proving the handler processed data scoped to a repository unrelated to the org that passed verification.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
