## Finding: L1 Bitcoin lockup proofs are not tracked persistently, allowing a single BTC lockup to be credited multiple times in `pox-5.clar`

### Title
Replayable L1 lockup proof allows double-crediting of sats never re-locked on Bitcoin - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`verify-l1-lockups`/`validate-l1-lockup` in `pox-5.clar` only deduplicate Bitcoin outpoints *within a single call* (a fresh `seen-outpoints: (list)` is created on every invocation), and there is no persistent, contract-level map recording which outpoints have already been credited. This mirrors the root cause of the Yearn report: state (shares/credit) is derived from an external, replayable input (a token transfer in Yearn; a Bitcoin UTXO proof here) without a durable guard preventing the same input from being consumed more than once.

### Finding Description
`verify-l1-lockups` initializes the dedup accumulator fresh for every call: [1](#0-0) 

`validate-l1-lockup` only checks the outpoint against `seen-outpoints`, a list scoped to the current fold/transaction: [2](#0-1) 

A `grep` for any persistent map that would record consumed outpoints across separate transactions (e.g. `define-map ... outpoint`) returns no results anywhere in `pox-5.clar`, confirming that once a call completes, nothing on-chain prevents the exact same `(tx, output-index)` Bitcoin outpoint from being submitted again in a subsequent transaction (potentially under a different `bond-index`, or even the same one) to have its `amount` summed into `sum` again.

### Impact Explanation
Because `sum` (the credited sats) is only deduplicated per-call and not persisted, a staker can submit the same valid L1 lockup proof multiple times across separate transactions. Each successful call increases the staker's credited/staked amount by the same BTC amount without any new BTC ever being locked. This breaks the equality "sats credited to a staker == sats actually locked (once) on Bitcoin," resulting in double-counting a commitment — unbacked crediting of stake/shares backed by BTC that was counted more than once. This matches the Critical impact category: "double-counting a commitment or reward" / "sats credited by an L1 proof that were never locked on Bitcoin."

### Likelihood Explanation
The attacker only needs to control their own stacker/staker account and re-submit the identical, already-valid proof data (header, merkle proof, tx bytes, output index) that they legitimately obtained once — no admin, bond, or pause key is required, and no cooperation from another user is needed. This is a straightforward unprivileged-account replay.

### Recommendation
Persist consumed outpoints in a durable map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`), and check/set this map inside `validate-l1-lockup` (or in the caller before crediting), rejecting `ERR_DUPLICATE_LOCKUP_OUTPOINT` for outpoints already recorded from any prior transaction, not just within the same call.

### Proof of Concept
1. Staker A locks BTC via the timelock script and constructs a valid lockup proof (header, merkle path, tx, output-index) referencing that UTXO.
2. Staker A calls the registration/staking function that invokes `verify-l1-lockups` with this proof; `sum` is credited to their bond/stake — this is legitimate.
3. Staker A calls the same (or an equivalent) registration function again in a new transaction, submitting the identical proof data. Since `seen-outpoints` is re-initialized to `(list)` for the new call and no persistent map exists, `validate-l1-lockup` passes all assertions again and credits the same sats a second time.
4. Repeat to accumulate unbacked stake/shares credit without ever locking additional BTC.

**Caveat / uncertainty:** I could not locate the top-level public function that calls `verify-l1-lockups` (e.g., a `register-for-bond`/staking entry point) within the available search budget, so I cannot show the exact downstream code path that turns the returned `sum` into a durable stake/share balance. The absence of any persistent outpoint-tracking map in `pox-5.clar` (confirmed via `grep`) is strong evidence of the flaw, but full confirmation would require reviewing the calling function(s) to verify they don't apply their own independent outpoint check.
