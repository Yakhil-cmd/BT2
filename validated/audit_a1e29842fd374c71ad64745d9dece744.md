Based on my research, the closest FRAME analog to the AuraLocker issue is `pallet-conviction-voting`'s `Tally::support()` calculation, which measures `Perbill::from_rational(self.support, Total::get())` where `Total` is typically bound to the chain's total issuance (`TotalIssuanceOf<Balances>` or `ActiveIssuanceOf<Balances>`), while `self.support` only accumulates capital that has actually been cast or delegated into `Voting::Casting`/`Voting::Delegating` records.This is exactly the pattern in the report — but here it is explicit, documented design, not a bug.

In `pallet-conviction-voting`, `Tally::support()` computes `Perbill::from_rational(self.support, Total::get())`, where `Total` (aliased `MaxTurnout`) is bound in production runtimes to the chain's total issuance (`TotalIssuanceOf<Balances>` / `ActiveIssuanceOf<Balances>`), while `self.support` (the numerator) only accumulates capital from accounts that actually cast a vote or delegated it, via `increase_upstream_delegation`/`Tally::increase`.No vulnerability found for this question.

The closest analog in polkadot-sdk to the AuraLocker report is `pallet-conviction-voting`'s support/turnout calculation, where `Tally::support()` divides accumulated cast/delegated capital by `MaxTurnout` (bound to total issuance in production runtimes) [1](#0-0) , and the numerator only grows via `increase_upstream_delegation`/`Tally::increase` when accounts actually cast or delegate votes [2](#0-1) . However, unlike the AuraLocker report, this discrepancy between "votes cast" and "total issuance" is not a bug — it is the intentional, documented design of Polkadot's OpenGov "support" quorum-biasing mechanism, explicitly described in `pallet-referenda`'s own docs as "the number of aye-votes, pre-conviction, as a proportion of the total number of pre-conviction votes able to be cast in the population" [3](#0-2) , and the `MaxTurnout`/`Total` config item is explicitly documented as configurable "may just be `Currency::total_issuance`" [1](#0-0) .

This mirrors exactly the scenario in the original report that Aura Finance disputed as intended behavior ("not delegating is the equivalent to having voting power but not voting"). Any exploitation would require an attacker to hold/control a large fraction of total issuance and deliberately abstain from voting to suppress support thresholds — this is a pure economic/griefing scenario, not a code defect, unauthorized dispatch, or state-integrity violation, and falls under the excluded categories (pure economic attacks, no violated invariant, no privileged bypass). There is no demonstrable Polkadot SDK analog that meets the bounty program's Critical/High criteria or even a genuine Medium/Low accounting bug distinct from intended adaptive quorum biasing design.

	/// Return the number of votes for `who`.
	fn increase_upstream_delegation(
		who: &T::AccountId,
		class: &ClassOf<T, I>,
		amount: Delegations<BalanceOf<T, I>>,
	) -> u32 {
		VotingFor::<T, I>::mutate(who, class, |voting| match voting {
			Voting::Delegating(Delegating { delegations, .. }) => {
				// We don't support second level delegating, so we don't need to do anything more.
				*delegations = delegations.saturating_add(amount);
				1
			},
			Voting::Casting(Casting { votes, delegations, .. }) => {
				*delegations = delegations.saturating_add(amount);
				for &(poll_index, account_vote) in votes.iter() {
					if let AccountVote::Standard { vote, .. } = account_vote {
						T::Polls::access_poll(poll_index, |poll_status| {
							if let PollStatus::Ongoing(tally, _) = poll_status {
								tally.increase(vote.aye, amount);
							}
						});
					}
				}
				votes.len() as u32
			},
		})
	}
