### Title
Delimiter/Field-Boundary Injection in Arbiter Contract Hash Computation Allows Content Forgery - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.js` computes an integrity hash over multiple untrusted, freely-typed text fields (`title`, `text`, `party_name`, etc.) by concatenating them with either no separator (legacy format) or a fixed string delimiter `"[|#|]"` (new format), without ever validating that the field values do not themselves contain the delimiter (or, in the legacy path, without any delimiter at all). This is the same class of bug as the reported `httpsoft/http-message` issue: a boundary marker used to separate structured fields can be spoofed by attacker-controlled content, causing two semantically different inputs to serialize to the identical string and therefore the identical hash/signature target.

### Finding Description
`getHashSrc()` builds the hash source as: [1](#0-0) 

For contracts created after `NEW_HASH_DATE`, fields are joined with `exports.DELIMITER = "[|#|]"`: [2](#0-1) 

None of `contract.title`, `contract.text`, `payer_name`, `payee_name` (all free-text, user/peer-supplied strings sent over `device.sendMessageToDevice`) are checked for the presence of the delimiter substring before being joined. Because string concatenation with a non-escaped, non-length-prefixed separator is used to build the pre-image for `sha256`, an attacker who controls one or more of these fields can insert the literal delimiter sequence `[|#|]` into `title` or `text` to shift the field boundaries. Two different sets of `(title, text, party_name, …)` values can then produce byte-identical `getHashSrc()` output and thus an identical `getHash()` result.

For contracts created on/before `NEW_HASH_DATE`, the legacy branch concatenates fields with **no delimiter at all** (`.join("")`), which is an even stronger version of the same flaw — trivial boundary-shifting between adjacent free-text fields (e.g. `title`+`text`) with no separator needed.

This hash is used as the authoritative integrity check when contract offers/updates are exchanged between wallets over the device-message (private, peer-to-peer contract) channel: [3](#0-2) 
and when validating dispute requests against a previously-agreed contract hash embedded in a signed unit: [4](#0-3) 

Since `title`/`text`/party names are attacker-supplied strings reachable by any paired device / contract counterparty, this is directly analogous to the reported CWE-436 issue: a delimiter that is supposed to terminate/separate fields can be injected by the untrusted party, causing downstream logic (hash verification, "wrong contract hash" checks) to treat two different documents as equivalent.

### Impact Explanation
An attacker acting as one of the two parties (or a device that later relays contract data, e.g., during a dispute with the arbstore) could craft a `title`/`text` pair containing the delimiter such that the resulting hash matches a hash the honest counterparty believes corresponds to different, more favorable contract terms (different amount-bearing text, different party name, etc.). Since the wallet code path in `wallet.js` uses `body.hash !== arbiter_contract.getHash(body)` as the sole authenticity check for contract content, this can be leveraged to substitute contract terms that still pass verification, enabling fraud in the funds-locking arbiter/private-payment flow (mislabelled disputes, forged terms accepted as matching a previously signed hash). This falls into the "private-payment counterparty" and "asset issuer/payment counterparty" reachable-message-handling category in scope, and can result in fund loss/dispute manipulation for one of the contracting parties.

### Likelihood Explanation
Medium. Exploitation requires the attacker to control the `title`/`text`/party-name fields of a contract offer sent to a counterparty (they always do, being one of the two contracting parties) and craft a specific boundary-colliding string containing the literal `[|#|]` sequence (or, for pre-`NEW_HASH_DATE` contracts, no special sequence needed at all). No cryptographic break is needed — only careful text construction — making this practically reachable by any unprivileged wallet user initiating or accepting an arbiter contract.

### Recommendation
- Reject (or escape) any field value that contains the delimiter substring `"[|#|]"` (and, for backward-compat hashing, forbid ambiguous field lengths) before constructing `getHashSrc()`.
- Prefer a length-prefixed or otherwise unambiguous serialization (e.g., hash each field separately and hash the concatenation of the fixed-size sub-hashes, or use a canonical JSON/`getSourceString`-style encoding as already used elsewhere in the codebase, e.g. `string_utils.getSourceString`) instead of joining raw strings with a delimiter that can appear in user-controlled content.
- Apply the same fix/audit to `getContactsHash()`, which also joins untrusted fields with a bare `"|"` delimiter.

### Proof of Concept
1. Party A initiates an arbiter contract with `title = "Refund"`, `text = "Pay $100[|#|]extra"`.
2. Party B (attacker) constructs an alternate contract with `title = "Refund[|#|]Pay $100"`, `text = "extra"`, keeping all other fields identical.
3. Because `getHashSrc()` joins `[title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset]` with the literal delimiter `[|#|]` and does not forbid the delimiter inside `title`/`text`, both contracts produce the same `getHashSrc()` string and therefore the same `getHash()` value.
4. When B sends the altered contract (`arbiter_contract_offer`/`arbiter_contract_shared`) with `body.hash` equal to the one A expects, the check `body.hash !== prosaic_contract.getHash(body)`-style validation in `wallet.js` passes even though the human-readable terms differ, defeating the integrity guarantee relied upon by the dispute/arbitration flow. function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
