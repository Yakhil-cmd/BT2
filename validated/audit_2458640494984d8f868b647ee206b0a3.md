### Title
`pallet-assets::do_transfer_approved` moves more than the approved amount to the destination while decrementing the `Approvals` ledger only by the nominal (requested) amount, breaking the "approval caps spend" invariant - ([File: substrate/frame/assets/src/functions.rs])

### Summary
`Pallet::do_transfer_approved` lets a `delegate` move up to `Approvals::amount` tokens from `owner` to `destination` on `owner`'s behalf. Internally it calls `transfer_and_die` with `TransferFlags { keep_alive: false, best_effort: false, burn_dust: false }`. Because `keep_alive` is `false` and `burn_dust` is `false`, whenever the requested `amount` would leave `owner`'s remaining balance below `min_balance`, the pallet's existential-deposit "dust sweep" logic (`prep_debit`/`prep_credit`) forces the **entire remaining balance** out of `owner` and credits it to `destination` - not just the requested `amount`. The `Approvals` storage entry, however, is decremented by the caller-supplied nominal `amount`, not by the actual `credit`/`debit` that was moved. This is the same root-cause class as the reported ERC-20 "fee-on-transfer" bug: code assumes the *nominal* transferred quantity equals the *actual* quantity moved, and bases downstream approval accounting on the nominal figure.

### Finding Description
`do_transfer_approved` (substrate/frame/assets/src/functions.rs:1012-1056):

```rust
let remaining = approved.amount.checked_sub(&amount).ok_or(Error::<T, I>::Unapproved)?;
let f = TransferFlags { keep_alive: false, best_effort: false, burn_dust: false };
owner_died = Self::transfer_and_die(id.clone(), owner, destination, amount, None, f)?.1;
``` [1](#0-0) 

Only the `.1` (whether the owner account died) of `transfer_and_die`'s return is used; the `.0` (the actual `credit`/amount deposited into `destination`) is discarded. Compare with `transfer_and_die` itself:

```rust
let debit = Self::prep_debit(id.clone(), source, amount, f.into())?;
let (credit, maybe_burn) = Self::prep_credit(id.clone(), dest, amount, debit, f.burn_dust)?;
``` [2](#0-1) 

`prep_debit` explicitly documents that the actual debited amount "will always be at least `amount` unless `best_effort` is true" and can be `amount` plus dust:

```rust
let actual = Self::reducible_balance(id.clone(), target, f.keep_alive)?.min(amount);
ensure!(f.best_effort || actual >= amount, Error::<T, I>::BalanceLow);
let conseq = Self::can_decrease(id, target, actual, f.keep_alive);
let actual = match conseq.into_result(f.keep_alive) {
    Ok(dust) => actual.saturating_add(dust), //< guaranteed by reducible_balance
``` [3](#0-2) 

Since `do_transfer_approved` always uses `burn_dust: false`, `prep_credit` credits `destination` with the full `debit` (i.e., `amount + dust`), not just `amount`:

```rust
pub(super) fn prep_credit(..., debit: T::Balance, burn_dust: bool) -> ... {
    let (credit, maybe_burn) = match (burn_dust, debit.checked_sub(&amount)) {
        (true, Some(dust)) => (amount, Some(dust)),
        _ => (debit, None),
    };
``` [4](#0-3) 

Meanwhile, back in `do_transfer_approved`, `remaining = approved.amount.checked_sub(&amount)` uses the *nominal* `amount` argument the delegate passed to the dispatchable, not the actual `credit` moved. The dispatchable is `Pallet::transfer_approved`, reachable directly by any signed account holding a non-zero approval:

```rust
pub fn transfer_approved(origin, id, owner, destination, #[pallet::compact] amount) -> DispatchResult {
    let delegate = ensure_signed(origin)?;
    ...
    Self::do_transfer_approved(id, &owner, &delegate, &destination, amount)
}
``` [5](#0-4) 

`owner` reaches this state via the ordinary, unprivileged `approve_transfer` extrinsic:

```rust
pub fn approve_transfer(origin, id, delegate, #[pallet::compact] amount) -> DispatchResult {
    let owner = ensure_signed(origin)?;
    ...
    Self::do_approve_transfer(id, &owner, &delegate, amount)
}
``` [6](#0-5) 

Both extrinsics are permissionless, signed-origin calls exercised by ordinary users with no governance/privileged role, matching the report's "no privileged prerequisite" requirement.

### Impact Explanation
An `owner` who approves a `delegate` for a smaller amount than their full balance - intending to keep a residual balance in the account - can have their *entire* balance swept the moment the delegate calls `transfer_approved` with the approved (smaller) `amount`, if the residual would fall below `min_balance`. The `destination` (which can be the delegate's own account, i.e., attacker-controlled) receives more tokens than the approval authorized for that call. Simultaneously, the `Approvals` entry is decremented only by the nominal `amount`, so:
- If `amount == approved.amount`, the approval is fully cleared (deposit unreserved) even though more than `amount` was actually extracted from `owner` - `owner` suffers an uncapped/unexpected loss beyond what they explicitly authorized for the call.
- If `amount < approved.amount` (as in the existing regression test), a non-zero `Approvals` entry with a locked deposit survives even though `owner`'s account was fully drained and reaped, silently retaining spend authority that the `delegate` could exploit if `owner` ever tops the account back up without noticing/cancelling the stale approval.

This is a genuine violation of the "approval caps third-party spend" invariant that `pallet-assets` intends to provide, and it is user-triggerable (owner + a normal delegate, no root/governance/malicious node needed). Impact is bounded by `min_balance - 1` per occurrence (dust ceiling), so it is a Medium-severity accounting/approval-integrity issue rather than unbounded fund theft.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any asset configured with a non-trivial `min_balance` (existential deposit) where a user approves a delegate for an amount close to (but less than) their full balance will trigger this automatically the first time the delegate exercises the approval near the account's remaining balance - no adversarial timing or race condition is required, just ordinary approve/transfer_approved usage.

### Recommendation
In `do_transfer_approved`, capture the actual `credit` (and/or `debit`) returned by `transfer_and_die` and use that value - not the nominal `amount` argument - when computing `remaining = approved.amount.checked_sub(&actual_debit)`. Alternatively, pass `TransferFlags { keep_alive: true, .. }` (or otherwise disallow reaping) for delegated transfers so a delegate can never move more than the exact approved amount, matching the "checks-effects" pattern recommended in the source finding: measure/derive the real amount moved and reconcile the approval ledger against that value rather than the caller-declared value.

### Proof of Concept
An existing unit test already demonstrates the underlying dust-sweep triggering through `transfer_approved`, though it only asserts the `Died` hook and not the balance/approval mismatch:

```rust
// Death by `transfer_approved`.
assert_ok!(Assets::mint(RuntimeOrigin::signed(1), 0, 1, 100));
Balances::make_free_balance_be(&1, 2);
assert_ok!(Assets::approve_transfer(RuntimeOrigin::signed(1), 0, 2, 100));
assert_ok!(Assets::transfer_approved(RuntimeOrigin::signed(2), 0, 1, 3, 91));
``` [7](#0-6) 

Here `owner=1` has balance `100`, `min_balance=10`, approves `delegate=2` for `100`, and `delegate` requests only `91` be moved to `destination=3`. Because `100 - 91 = 9 < min_balance(10)`, the dust-sweep forces the full `100` out of `owner` into `destination`, but `Approvals::amount` is decremented using the nominal `91`, leaving a stale `9`-unit approval (with its deposit still reserved) even though `owner`'s account has just been reaped to zero. A minimal extension of this exact test - adding `assert_eq!(Assets::balance(0, 3), 100)` (destination got 100, not the requested 91) and `assert_eq!(Assets::allowance(0, &1, &2), 9)` (approval not cleared/consistent with the amount actually moved) - would concretely demonstrate the mismatch using only the existing pallet-assets test harness; no mocked authority/proof acceptance is needed since this exercises real `Pallet::approve_transfer` / `Pallet::transfer_approved` dispatch logic. This PoC was reasoned through source-code and existing-test-derived arithmetic; it has not been executed as a standalone new test run in this session, so no output logs are attached - the guard is `Approvals::<T,I>::try_mutate_exists` at functions.rs:1024, which does not fail or reconcile against the actual `credit` returned from `transfer_and_die`, confirmed by direct code inspection of functions.rs:1012-1056, 276-341, and 623-748.
