### Title
Webhook authentication binds to `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` / a global commit `sha` — allowing cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a request against using `repository.owner.login` (or `organization.login`) pulled from the untrusted payload, then verifies the HMAC using that org's `webhook_secret`. The handlers that subsequently act on the same payload (`Handler#repository_name`, `StatusHandler#process`) do **not** use the verified owner — they read `repository.full_name` (a separate JSON field in the same payload) or, in the status case, do a completely unscoped `Commit.where(sha:)` lookup across the whole database. In a multi-org Shipit install (a documented, supported configuration — see `docs/setup.md:181-216` and `test/dummy/config/secrets_double_github_app.yml`), if any configured organization has no `webhook_secret` set (shown as the default in every example config, e.g. `config/secrets.development.example.yml:11`, `template.rb:73`), `GithubApp#verify_webhook_signature` trivially returns `true` for that org's traffic. An attacker can therefore send a POST claiming to be from the unsecured/known-secret org while pointing `repository.full_name` (push) or an arbitrary `sha` (status) at a completely different, protected organization's stack.

### Finding Description
- `verify_signature` derives the authenticating identity purely from the payload: [1](#0-0) [2](#0-1) 

- `verify_webhook_signature` unconditionally passes when the resolved org has no `webhook_secret` configured: [3](#0-2) 

- Every shipped example config leaves `webhook_secret` unset by default (`nil`), and multi-org setups configure a **separate** secret per organization key: [4](#0-3) [5](#0-4) 

- After the signature gate, the actual dispatch to handlers passes the raw, unverified-for-content `params` — no field of `params` is cross-checked against the `repository_owner` used above: [6](#0-5) 

- `Handler#repository_name`/`#stacks` resolve the target stack from `repository.full_name`, a field disjoint from `repository.owner.login`: [7](#0-6) 

- `PushHandler#process` uses that stack lookup to enqueue a sync against whatever stack `full_name` names: [8](#0-7) 

- `StatusHandler#process` is worse: it doesn't even use `repository_name` — it matches **any** commit in the entire database by `sha` and attaches a forged CI status to it, with no repository/owner scoping at all: [9](#0-8) 

**Binding broken:** `repository_owner` (the identity the HMAC signature is checked against) ≠ `repository.full_name` / commit `sha` (the identity the handler actually writes to). Before the attacker's request, these two fields are assumed to describe the same GitHub delivery and therefore the same trust domain; the controller only checks the first, the handlers only trust the second, and nothing enforces that they refer to the same repository/organization.

### Impact Explanation
Because `ci.require`/`ci.blocking` gate deploys on commit statuses (`README.md:446-480`), and `StatusHandler` accepts a forged status for **any** commit sha in the datastore regardless of which org's secret validated the request, an attacker who controls (or can trivially satisfy, i.e. no-secret) one configured GitHub App/org in a multi-org Shipit instance can inject a passing CI status onto a commit belonging to a completely different, protected repository/stack — unblocking `ci.require` gates and enabling an **unauthorized deploy** on a repository the attacker has no legitimate relationship with. This satisfies the Critical bar ("unauthorized deploy") in the rules. The push-event variant additionally lets the attacker trigger `GithubSyncJob`/sync activity against an unrelated stack by forging `repository.full_name`, again using only a webhook credential scoped to a different, unrelated organization.

### Likelihood Explanation
This requires: (1) a Shipit instance configured with multiple GitHub Apps/organizations (an explicitly documented, supported topology), and (2) at least one of those organizations having no `webhook_secret` set — which is the default/example value shown everywhere in the repo's own config templates. Given that operators frequently skip the optional `webhook_secret` for at least one app (it's marked optional in `docs/setup.md:30`), this is a realistic misconfiguration rather than a theoretical one, and requires no privileged credentials, tokens, or repository access — only the ability to send an unauthenticated HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Cross-validate that `repository.owner.login` (the field used to select the verifying GitHub App/secret) matches the `repository.full_name` owner segment (and, for `status` events, the repository embedded in the payload) before dispatching to handlers. `StatusHandler` in particular should scope its `Commit` lookup by the repository identified in the verified payload rather than searching the entire `Commit` table by `sha` alone. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail closed) rather than treating a blank secret as "verification passes."

### Proof of Concept
1. Configure Shipit with two organizations as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (target, protected repo `OrgOne/protected-app`) and `OrgTwo` left with `webhook_secret: nil` (as shown in every default template).
2. Attacker sends, without any valid signature:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/whatever" },
  "sha": "<sha-of-a-blocking-commit-in-OrgOne/protected-app>",
  "state": "success",
  "context": "ci/circleci"
}
```
3. `verify_signature` resolves `repository_owner` = `"OrgTwo"`, loads `OrgTwo`'s `GithubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`) — the request is accepted despite having nothing to do with `OrgOne`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit belonging to `OrgOne/protected-app`, and calls `create_status_from_github!`, marking the required `ci/circleci` context as passing.
5. The forged passing status satisfies `ci.require` on `OrgOne/protected-app`, permitting an unauthorized deploy of that stack — even though the request was never authenticated for `OrgOne`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
