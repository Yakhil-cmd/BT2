### Title
AA asset-definition policy check `issued_by_definer_only` bypass via formula instead of literal boolean allows private/fixed-denomination assets issued only by definer - ([File: aa_validation.js])

### Summary
`validateAADefinition`'s payload validator for the `asset` app enforces the invariant "an asset issued by the AA definer cannot be private or use fixed denominations" only when `issued_by_definer_only` is the *literal* boolean `true`. Because the same field is also allowed to be a formula string (evaluated only at trigger-handling time), an AA author can set `issued_by_definer_only` to a formula that evaluates to `true` at runtime while `is_private`/`fixed_denominations` are literal `true`, completely skipping the static guard — mirroring the Keycloak bug class where a policy check is only enforced "when explicitly provided" and is bypassed by using an alternate encoding.

### Finding Description
In `aa_validation.js`, when an AA definition contains a message with `app: 'asset'`, the code validates the asset payload as follows: [1](#0-0) 

```
if (payload.cosigned_by_definer !== false)
    return cb2("cosigned_by_definer must be false because AA can't cosign");
if (payload.issued_by_definer_only === true && (payload.is_private !== false || payload.fixed_denominations !== false))
    return cb2("asset issued by AA definer cannot be private or fixed denominations");
```

This guard fires only when `payload.issued_by_definer_only === true` (a *literal* JS boolean). Immediately afterward, the code allows each of these same fields — including `issued_by_definer_only`, `is_private` and `fixed_denominations` — to instead be an oscript **formula string**, which is only evaluated later, during trigger handling: [2](#0-1) 

Because a formula string (e.g. `"{1==1}"`) is not the literal boolean `true`, the static `=== true` check is skipped entirely, even though at runtime the formula will evaluate to `true`. An AA author can therefore define an asset payload such as:
```
{
  app: 'asset',
  payload: {
    issued_by_definer_only: "{1==1}",   // formula, not literal true -> bypasses the guard
    is_private: true,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: true,
    denominations: [{denomination: 1, count_coins: 1000}],
    cosigned_by_definer: false,
    spender_attested: false
  }
}
```
This passes `validateAADefinition` because the offending literal-only check at lines 299-300 never triggers, yet at execution time the AA will actually create an asset that is simultaneously `issued_by_definer_only`, `is_private`, and `fixed_denominations` — exactly the combination the check exists to forbid.

By contrast, the equivalent check for asset definitions posted directly in a unit (non-AA) in `validation.js` requires each of these fields to be a strict `typeof ... === "boolean"`, so no formula bypass is possible there: [3](#0-2) 

The AA path is the one that admits formulas for these same fields and therefore is the one vulnerable to the omission/encoding bypass.

### Impact Explanation
Assets that are simultaneously private and issued/controlled solely by the AA definer combine two mutually-exclusive risk properties the codebase explicitly tries to prevent (`objValidationState.bAA` branch in `validation.js` enforces the same rule for the non-formula path). Private assets rely on off-chain spend-proof delivery and blinding that the deterministic, automated AA response flow is not designed to participate in as a spending counterparty; combining this with `fixed_denominations`/`issued_by_definer_only` can produce asset state that the AA itself cannot correctly move or account for once created, leading to funds effectively becoming unspendable/frozen within the AA (since normal AA payment composition and private-chain forwarding logic assume the invariant holds and is validated once at definition time, not re-checked at issuance time). This falls under the accepted impact category of "AA fund loss or freezing."

### Likelihood Explanation
Any address can post a new AA (`app: 'definition'`, `['autonomous agent', {...}]`) whose response messages include an `asset` message using this construction — this requires no special privilege beyond composing and broadcasting a unit, matching the "unprivileged AA author" threat actor allowed by scope. The bypass requires only substituting a trivial always-true formula for the literal `true` value, which is straightforward to construct and passes `validateAADefinition` at AA-registration time.

### Recommendation
In `aa_validation.js`, do not gate the `issued_by_definer_only`/`is_private`/`fixed_denominations` conflict check on `issued_by_definer_only === true` (a literal-only comparison). Instead, either:
- Reject the combination whenever `issued_by_definer_only` is anything other than the literal `false` (mirroring the strict literal requirement already used in `validation.js` for non-AA asset definitions), or
- Defer this specific invariant check to `handleTrigger`/asset-issuance time in `aa_composer.js`, after all formulas (`issued_by_definer_only`, `is_private`, `fixed_denominations`) are evaluated to concrete booleans, and bounce the AA response if the forbidden combination results.

### Proof of Concept
1. Post a unit defining a new AA whose `messages` array contains, in addition to a `state` message, an asset-issuing message:
```
{
  app: 'asset',
  payload: {
    issued_by_definer_only: "{trigger.data.x==trigger.data.x}", // always true, but not literal `true`
    is_private: true,
    is_transferrable: true,
    auto_destroy: false,
    fixed_denominations: true,
    denominations: [{denomination: 1, count_coins: 1}],
    cosigned_by_definer: false,
    spender_attested: false
  }
}
```
2. `validateAADefinition` accepts this because `payload.issued_by_definer_only === true` is `false` for the formula string, so the guard at `aa_validation.js:299` never executes; all other per-field checks in the `async.eachSeries` loop (lines 301-313) accept formula strings.
3. Once the AA is registered and triggered, the formula evaluates to `true` at runtime, and the AA issues an asset that is simultaneously private, fixed-denomination, and definer-only-issued — the exact state the static check was meant to forbid.

Note: I was unable to trace the full downstream runtime handling of the `asset` app inside `aa_composer.js`/`handleTrigger` within the available index (file content for that section was not retrievable), so the precise mechanism by which this invariant violation manifests as fund freezing at runtime could not be fully confirmed from the indexed code; a Devin session with full repository access would be needed to trace `aa_composer.js`'s asset-issuance handling to conclusively verify the runtime consequences.
