### Title
Cross-tenant stack read via unscoped `Stack.from_param!` in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` enforces per-token stack binding by scoping all stack lookups through `stacks.from_param!`, where `stacks` is restricted to `current_api_client.stack_id` when the token is stack-scoped. `Api::CCMenuController` overrides the private `stack` method to call `Stack.from_param!` directly on the unscoped `Stack` model, bypassing this binding and allowing a token scoped to stack A to read CI status/build data for any stack B.

### Finding Description
The binding that should hold is: for any `Api::BaseController` subclass, `token.stack_id == A` implies `stack` resolved in that controller ∈ `{A}` (or all stacks only if `token.stack_id` is nil). This is enforced generically in `app/controllers/shipit/api/base_controller.rb:74-80`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every other `Api::BaseController` subclass (`TasksController`, `DeploysController`, `CommitsController`, `OutputsController`, `MergeRequestsController`, `StacksController`) relies on this inherited `stack`/`stacks` method, so a token with `stack_id = A` resolving `stack_id param = B` raises `ActiveRecord::RecordNotFound` → 404, as demonstrated by the existing test `"an api client scoped to a stack will only see that one stack"` and `"#index returns a list of stacks filtered by repo and api client"` in `test/controllers/api/stacks_controller_test.rb:188-223`. [2](#0-1) 

`Api::CCMenuController`, however, redefines `stack` to bypass the scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`require_permission :read, :stack` (line 6) only calls `current_api_client.check_permissions!(:read, :stack)`, which checks the `permissions` array on the `ApiClient` record and never touches `stack_id`:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3) 

So for a token that has `permissions: ['read:stack']` and `stack_id = A` (a legitimate configuration supported by the `ApiClient` model, `belongs_to :stack, optional: true`, and exercised by the `here_come_the_walrus` fixture used in `test/controllers/api/stacks_controller_test.rb`), `check_permissions!` passes regardless of which stack is requested, and `CCMenuController#stack` resolves any stack B by param with no ownership check. The attacker's request is simply:
```
GET /api/stacks/<owner-B>/<repo-B>/<env-B>/ccmenu?token=<token scoped to stack A>
```
This returns the CCMenu XML (`app/views/shipit/ccmenu/project.*`) containing stack B's name, lock status, and latest deploy/build status — data the token was never authorized to read.

None of the listed guards intervene: `verify_signature`/webhook checks are irrelevant (this is an API GET, not a webhook), `ExplicitParameters` isn't used by this action, and `require_permission!` only checks the flat permission string, not the stack binding. The divergence is unique to `CCMenuController`; `TasksController`, `DeploysController`, etc. all inherit the safe `stack`/`stacks` methods unchanged.

### Impact Explanation
An attacker holding (or obtaining, e.g. via the CCMenu-URL flow or any other legitimately issued `read:stack`-scoped token bound to stack A) can read build/deploy status, lock state, and stack name for any other stack B in the installation by simply changing the `stack_id` route param — an unauthenticated-for-that-tenant read of stack state across tenant boundaries. This matches the "High" impact category: unauthorized read of stack state for a repository/stack the token was never scoped to, repeatable against arbitrary stacks with a single GET request each.

### Likelihood Explanation
Preconditions are minimal and realistic: any stack-scoped `read:stack` `ApiClient` token (a normal, supported configuration — not requiring any secret beyond the token itself, which the attacker already legitimately possesses for stack A) and knowledge/guessability of another stack's `owner/repo/environment` path (which is often predictable or discoverable). No GitHub secrets, session, or elevated role is required — exactly matching the described attacker capabilities. The exploit is a single unauthenticated (relative to stack B) HTTP GET, fully repeatable.

### Recommendation
Remove the `stack` override in `app/controllers/shipit/api/ccmenu_controller.rb` and use the inherited `stacks.from_param!(params[:stack_id])` from `Api::BaseController` so the `current_api_client.stack_id` scoping is applied consistently, matching every other `Api::BaseController` subclass.

### Proof of Concept
Add to `test/controllers/api/ccmenu_controller_test.rb` (and mirror in `tasks_controller_test.rb`/`deploys_controller_test.rb` for contrast):
```ruby
test "a token scoped to stack A cannot read stack B via ccmenu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: "main")
  @client.update!(stack: stack_a, permissions: ['read:stack'])

  get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }

  assert_response :not_found # currently fails: returns 200 with stack_b's data
end
```
Parametrized cross-check confirming the binding holds elsewhere:
```ruby
# Api::TasksControllerTest / Api::DeploysControllerTest
test "a token scoped to stack A cannot access stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar2"), branch: "main")
  @client.update!(stack: stack_a, permissions: @client.permissions)
  get :index, params: { stack_id: stack_b.to_param }
  assert_response :not_found
end
```
Both sides of the equality `token.stack_id == A ⇒ resolved stack ∈ {A}` hold for `TasksController`/`DeploysController` (404 for B) and are violated only for `CCMenuController` (200 for B), confirming the isolated bug.
