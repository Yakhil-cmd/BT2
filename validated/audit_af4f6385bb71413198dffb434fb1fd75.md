### Title

Caller-controlled swap routes can execute attacker contracts under the signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

XOXNO Lending accepts opaque `swap` bytes on `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, then forwards them to the configured router [1](#0-0) . The controller authenticates the caller and account owner/delegate, but does not decode or constrain the pool addresses embedded in the route [2](#0-1) . A route can therefore place attacker-controlled code inside the transaction authorized by the victim.

### Finding Description

`swap_collateral` withdraws collateral and calls `swap_tokens` with the caller-supplied route [3](#0-2) . `swap_tokens` authorizes only the controller-to-router input transfer, but then invokes `execute_strategy` with the unmodified route bytes [4](#0-3) . Its balance checks bound only the controller’s declared input spend and positive declared output receipt; they do not identify or restrict other contracts invoked inside the route [5](#0-4) .

The router venue path invokes the pool address selected by the payload [6](#0-5) . A malicious pool can call `token.transfer(victim, attacker, amount)`. Because the victim signed the top-level controller authorization tree, simulation can attach that transfer as a child authorization; if the victim signs the resulting tree, the malicious transfer is authorized even though it is unrelated to the lending swap.

### Impact Explanation

An attacker can steal arbitrary tokens held by the victim’s wallet, not merely the collateral amount supplied to the strategy. The account can receive a valid output and pass the final risk checks while unrelated wallet assets are transferred to the attacker. This is theft of user funds.

### Likelihood Explanation

The attacker must cause the victim to submit a malicious route and sign the poisoned authorization tree. This is feasible through a malicious quote, phishing interface, compromised route-generation path, or a wallet/client that does not clearly display nested authorization entries. No protocol privilege, leaked key, upgrade, or control of another user’s account is required. Severity is Medium because signing the expanded authorization tree is required.

### Recommendation

Do not allow opaque routes to select arbitrary pool contracts. Add a governance-managed venue/pool registry or otherwise bind routes to approved pool addresses before execution. Wallets and quoting clients should also reject authorization trees containing calls beyond the expected token input transfer, but client-side checking should not be the only defense because the exploitable authorization is rooted in the contract’s unrestricted external route execution.

### Proof of Concept

1. Victim owns a debt-free XOXNO account with USDC collateral and separately holds `VICTIM_TOKEN`.
2. Attacker deploys a contract exposing the expected pool `swap` interface. Its `swap` implementation calls `VICTIM_TOKEN.transfer(victim, attacker, victim_balance)` and sends enough `ETH` to the router to satisfy the route output measurement.
3. Attacker encodes a route for `swap_collateral(victim, account_id, USDC, amount, ETH, route)` whose hop pool is the malicious contract.
4. The victim submits the route and signs the authorization tree produced by simulation. The tree contains the normal `swap_collateral` root plus the malicious token-transfer child.
5. `process_swap_collateral` authorizes the victim and account owner, withdraws the declared USDC collateral, and calls `swap_tokens` [7](#0-6) .
6. `swap_tokens` calls the configured router with the malicious `swap` bytes [8](#0-7) .
7. The malicious pool executes and transfers `VICTIM_TOKEN` from the victim to the attacker under the signed tree. The router then delivers positive `ETH` output, so the controller’s measured output and final account checks pass [5](#0-4) .
