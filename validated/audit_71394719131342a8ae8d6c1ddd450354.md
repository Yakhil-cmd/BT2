### Title
Cross-Repository Commit Status Forgery via Global SHA Lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` GitHub webhook is authenticated per-organization, but the handler that processes it writes to any `Commit` record in the entire database that matches the payload's `sha`, with no check that the commit belongs to the repository/organization whose webhook signature was verified. This breaks the binding: *organization authenticated* (via `verify_webhook_signature` against that org's `webhook_secret`) ≠ *repository whose commit is written* (any stack's commit sharing that SHA).

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/org config from the payload's `repository.owner.login` (or `organization.login`) and verifies the HMAC signature against that org's `webhook_secret`. [1](#0-0) 

Once verified, `create` dispatches the raw payload to the handler for the event type without any further repository check. [2](#0-1) 

`StatusHandler#process` looks up commits purely by `sha`, globally, across all stacks: [3](#0-2) 

Unlike `Handler#stacks`, which scopes lookups by `repository_name` from the payload, `StatusHandler` never calls `stacks` or otherwise filters by repository — it just does `Commit.where(sha: params.sha)`. Any commit row in any stack, belonging to any repository/organization onboarded to this Shipit instance, whose `sha` column matches the attacker-supplied value will get a new `Status` created via `commit.create_status_from_github!(params)`. [4](#0-3) 

Because a git commit SHA-1 is a deterministic hash of fully public metadata (tree hash, parent SHA, author/committer name/email/date, message), an attacker who is themselves a legitimately onboarded, authenticated organization (with their own valid `webhook_secret`) can reconstruct a commit object with an identical SHA to a target commit in a *different* onboarded repository/stack (e.g., a shared/forked history commit, or by locally reproducing the exact metadata of a known public commit), then trigger (or directly forge, since they control their own webhook delivery/signature) a `status` event referencing that SHA. The webhook signature check passes because it is validated against the attacker's own organization's secret — it says nothing about which commit/repository the event content is allowed to affect.

The resulting forged `Status` is then consumed by `Commit#status`/`Status::Group` and by `MergeRequest::StatusChecker`, which is exactly what `MergeRequest#all_status_checks_passed?` and `#reject_unless_mergeable!` rely on before allowing `MergeRequest#merge!` to call `stack.github_api.merge_pull_request`. [5](#0-4) [6](#0-5) 

### Impact Explanation
This lets an attacker who authenticates only as their own onboarded organization (not the victim's) inject a fabricated "success" status onto a commit belonging to a target stack in another repository. If that commit is the head of a pending `MergeRequest`, the forged status can satisfy `all_status_checks_passed?`/`reject_unless_mergeable!`, causing Shipit's `ProcessMergeRequestsJob` to auto-merge a pull request whose real CI status is failing or missing. This is an **unauthorized merge**, one of the explicitly accepted Critical impacts.

### Likelihood Explanation
Exploitation requires: (1) the attacker to control an org/repo that is itself onboarded into the same Shipit instance (so they have a valid `webhook_secret` to sign a `status` payload), and (2) the ability to produce/know a commit SHA that also exists as a tracked commit in the victim stack (e.g., shared fork history, or reproducing a fully-public commit's exact metadata locally to get an identical SHA — feasible since SHA-1 commit inputs are public via the GitHub API, and no cryptographic secret protects them). This mirrors the analog report's theme of a value used for a critical decision (share price / merge-eligibility) not being re-validated against the correct scope at the time it matters — here, the correct *repository* — even though a signature check exists nearby. Likelihood is non-trivial but bounded by requiring shared/reproducible SHA history between attacker and victim repos, making it a realistic but not universally-applicable Medium/High-likelihood path.

### Recommendation
Scope `StatusHandler#process` (and any other handler that trusts payload `sha` alone) to the repository that sent the webhook, mirroring `Handler#stacks`/`repository_name`, e.g. restrict the commit lookup to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`-derived stacks' commits rather than a bare `Commit.where(sha: ...)` across the whole table.

### Proof of Concept
1. Attacker's organization `attacker-org` is legitimately onboarded to the Shipit instance, giving them a valid `webhook_secret` for signing webhook deliveries to `/github_webhook`.
2. Attacker fetches the public GitHub metadata (tree SHA, parent SHA, author/committer, dates, message) of the head commit `C` of a pending PR in victim stack `victim-org/victim-repo`, and reproduces a git commit object with an identical resulting SHA `S` (trivial if `C` is a root/import commit shared via fork, or reconstructible locally with `git commit-tree`).
3. Attacker crafts a `status` webhook JSON payload: `{"sha": "S", "state": "success", "context": "ci/required", "repository": {"owner": {"login": "attacker-org"}, ...}}`, computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret`, and POSTs it to `/github_webhook`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature — the request is accepted.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which executes `Commit.where(sha: "S")` — matching the victim's commit `C` in `victim-org/victim-repo` — and creates a `success` `Status` on it via `create_status_from_github!`, with no check that `attacker-org` has any relationship to `victim-org/victim-repo`.
6. If `C` is the head of a `MergeRequest` still failing/missing real CI, the injected status can flip `all_status_checks_passed?` to true, and `ProcessMergeRequestsJob` merges the PR via `stack.github_api.merge_pull_request` — an unauthorized merge triggered entirely from an unrelated organization's webhook credentials.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
