## Title
Unauthenticated `payment_notification` Device Message Allows Spoofed Payment Confirmation - (File: wallet.js)

### Summary
The external report describes a "Missing Authentication for Critical Function" bug class: a webhook-style trigger (Spring Cloud Config's `/monitor` endpoint) is acted upon without validating that the request actually originated from the claimed/authorized source. The closest reachable analog in ocore is the `payment_notification` subject handled in `handleMessageFromHub` in `wallet.js`, which accepts a bare unit hash from *any* paired device (including newly/permanently-paired ones) and treats it as an authoritative claim that "I sent you a payment," without any cryptographic binding between the sending device and the actual payer of that unit.

### Finding Description
In `wallet.js`, the `payment_notification` case is handled with only a format check on the unit hash, no check that the sender of the device message is actually one of the authors/senders of that on-chain unit: [1](#0-0) 

The code comment explicitly acknowledges the trust gap: "since the payments are public, an evil user might notify us about a payment sent by someone else (we'll be fooled to believe it was sent by the evil user)." [2](#0-1) 

This is analogous to the CVE's root cause: a message that triggers an internal state/consumer action (`eventBus.emit(... new_public_payment_received ...)`) is accepted from an unauthenticated/unauthorized party — here, any device that has paired with the victim's wallet (pairing itself is reachable by anyone who obtains a one-time pairing secret via `handlePairingMessage`, `wallet.js` `device.js:798-848`) — without validating that the claimed payer is the true unit author.

### Impact Explanation
Because `is_valid_sig`/authorship of the referenced unit is never checked against the sending device's identity, an attacker who has paired with a victim's wallet (e.g., posing as a merchant, exchange counterparty, or support contact) can send a `payment_notification` referencing a real, unrelated unit on the DAG (one they did not send funds in) and cause the victim's wallet UI to display and act as if the attacker had paid them. In an economic-transaction workflow (goods/services released against wallet-reported "received payment" events, or automated systems that key off `new_public_payment_received`), this results in the counterparty releasing value without having received the corresponding on-chain payment — i.e., attacker-induced unauthorized loss of funds/goods for the victim, mirroring the "critical action taken on unauthenticated input" class of the CVE.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be a paired correspondent device of the victim (achievable trivially by obtaining any pairing secret/QR code the victim shares, e.g., for legitimate business purposes) and knowledge of a valid, already-broadcast unit hash (units and their authors are public on the DAG, so any historical or observed unit can be reused). No signature forgery or private key compromise is needed—only a paired device and message-delivery via the hub, both of which are within reach of a normal/low-privileged actor as required by the analog scope.

### Recommendation
Before emitting `new_public_payment_received` (or otherwise treating the notification as authoritative), the wallet should independently verify, by reading the joint/unit from storage, that the sending device's associated address (or a known correspondent address) is actually among the payment's authors/outputs to the recipient — i.e., cross-check `from_address` against `unit_authors`/`outputs` for the referenced unit rather than trusting the claim implicit in receiving the message. Alternatively, treat `payment_notification` purely as a "please look up this unit" hint and derive the actual payer from the verified on-chain data rather than attributing the payment to the sending device.

### Proof of Concept
1. Attacker pairs their device with Victim's wallet using a shared pairing code (or an existing chat relationship). [3](#0-2) 
2. Attacker observes or is given any valid, unrelated unit hash `U` on the DAG (public data) that pays into an address the victim's wallet is watching.
3. Attacker sends a device message: `{subject: "payment_notification", body: "U"}` to the victim.
4. `handleMessageFromHub` dispatches to the `payment_notification` case, which only checks `isStringOfLength(unit, HASH_LENGTH)`, then reads the joint and fires `emitNewPublicPaymentReceived(from_address=<attacker>, U, ...)`. [4](#0-3) 
5. Victim's wallet/UI (or any integration listening on `new_public_payment_received`) now attributes unit `U`'s payment to the attacker, even though the attacker never sent it — enabling social-engineering-driven release of goods/funds by the victim under a false belief that payment was received from the attacker.

**Note on confidence:** This analog satisfies the reachability constraints (a paired device, an unprivileged/low-privileged actor) and the root cause maps closely to "acting on an unauthenticated/unvalidated request." However, the concrete "unauthorized spending" impact here is realized off-chain (via the victim's business logic/trust in the notification) rather than directly moving on-chain funds, so the mapping to the required "concrete unauthorized spending" outcome is indirect and depends on how a consumer of `new_public_payment_received` acts on it. I was not able to find a purely on-chain/ledger-state code path (double-spend, AA fund loss, supply inflation, or stability disagreement) that matches this CVE's bug class as closely; this is the strongest available analog found through search.
