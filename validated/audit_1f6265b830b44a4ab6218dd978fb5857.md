### Title
Unvalidated swap-route venues run third-party code inside the caller's authorization tree and can transfer arbitrary tokens from the user's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The LocalBitcoins incident class — a third-party software component in the transaction path able to send unauthorized transactions from user accounts — maps onto XOXNO Lending's route execution. `swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 34-38) forwards caller-supplied `swap` bytes to the configured router, and `dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs` (lines 30-40) invokes the `hop.pool` address named by that payload with no venue or pool allowlist. Code in that pool executes on the call stack *below* the account owner's `require_auth` entry, so any `token.transfer(victim, attacker, amount)` it performs is recorded by Soroban simulation as a child of the caller's signed invocation and executes once that tree is signed. The theft is bounded by the victim's whole wallet, not by the routed amount.

### Finding Description
Controller strategies (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`) accept opaque `StrategySwap` bytes from the caller and invoke `router.execute_strategy` after authorizing only the exact input transfer (`swap.rs:34`). The router decodes venue/pool addresses from the payload (`dispatch_hop`, `venues/mod.rs:30-40`) and calls whatever contract the route names; its measured-delta checks (`received > 0`, `spent == amount_in`) verify only the router's own balances — they do not constrain what the called pool does inside the invocation. Because the account owner's authorization is the active root frame, a rogue pool's `token::Client::transfer(victim, …)` is attributed to a sub-invocation of the victim's auth entry. The repo's own harness proves this: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` shows `swap_collateral` with a route through `RogueHopPool` draining Alice's entire unrelated wallet token (77,770 units) while still delivering fair swap output and passing all controller risk gates. The threat model documents the identical exposure in `docs/explanation/threat-model.md:154-165`: "a route can put third-party code on the call stack below the caller's authorization… the loss is then the caller's wallet, not the routed amount."

### Impact Explanation
Theft of user funds. An attacker who can get a victim to execute a route through an attacker-deployed pool (e.g., via a compromised/malicious quote source, matching the third-party-software vector of the incident) drains any token the victim holds — unrelated wallet balances far exceeding the swap size. The protocol's input-transfer bound, output measurement, slippage minimum, and final health-factor gate all still pass, so none of them bound the loss.

### Likelihood Explanation
Medium. Exploitation needs the victim to sign the auth tree that simulation produces for the poisoned route; standard wallet flows sign exactly the simulated tree, and the malicious transfer is buried as a nested sub-invocation the user is unlikely to inspect. No protocol privilege or upgrade is required — only a route payload, which any unprivileged caller supplies. The repo treats this as a live threat rather than a theoretical one (dedicated enforcing-mode test, explicit threat-model paragraph instructing clients to reject unexpected child invocations).

### Recommendation
Constrain venue dispatch to a governance- or admin-managed allowlist of pool contracts per venue (or pin venue implementations so `hop.pool` can only be one of known-good adapters), so a route cannot place arbitrary contract code inside the user's authorization frame. Additionally, surface and enforce the invariant from `INV-STRAT`-style documentation at the client/SDK layer: reject any simulated authorization tree whose `execute_strategy`/strategy root contains child invocations other than the single input-token transfer.

- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the transfer executes once the simulated (poisoned) tree is signed (lines 230-269).
