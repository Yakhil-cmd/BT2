### Title
Compounded debt valuation overflows `i128` before the borrow-index cap engages, permanently freezing all operations on a whale market - (File: common/src/rates/index.rs)

### Summary
The CVE class is an arithmetic overflow crashing a running process. The XOXNO analog is a real, self-documented cliff in the rate engine: `borrowed * borrow_index` is a RAY-scaled `i128` product that overflows `i128` when a very large market compounds at high utilization. Every pool mutator runs `interest::global_sync` first, which calls `accrue_step` → `calculate_supplier_rewards` → `Ray::mul` (`mul_div_half_up`), which panics with `MathOverflow`. The `MAX_BORROW_INDEX_RAY` cap in `update_borrow_index` never engages because the *value* product overflows while the index is still far below the cap. Once crossed, the market is permanently frozen: no withdraw, repay, liquidate, or `update_indexes` ever succeeds again, and all supplier funds in that market are stuck forever.

### Finding Description
`calculate_supplier_rewards` in `common/src/rates/index.rs:73-89` computes `borrowed.mul(env, new_borrow_index)` via `mul_div_half_up`, which panics with `GenericError::MathOverflow` when the result does not fit `i128` (`common/src/math/fp_core.rs:108-118`). `accrue_chunk` in `contracts/pool/src/interest.rs:39-53` invokes this inside `global_sync`, which every entrypoint runs before mutating (`contracts/pool/README.md:157-168`). The borrow index is capped at `MAX_BORROW_INDEX_RAY` only after multiplication (`common/src/rates/index.rs:13-19`), so a book whose `borrowed` scaled shares are ~1e36 ray (a billion 18-decimal tokens) overflows the value product at an index of roughly x170, far below the cap. The committed test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-360`) demonstrates exactly this: after a few years at 98% utilization on the steep curve, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.

### Impact Explanation
Permanent freezing of funds. Once `borrowed * borrow_index` crosses `i128::MAX` in ray terms, every accrual panics and every verb accrues first, so suppliers can never withdraw and the market can never process repayments, liquidations, or `clean_bad_debt`. There is no admin recovery path because pool mutators are `#[only_owner]`-gated controller calls that still run `global_sync`.

### Likelihood Explanation
Requires a whale-scale book (≈1e9 whole tokens supplied, the borrow side near full utilization) and sustained high utilization over years, since debt compounds while repayment is optional. The attacker supplies the market size and borrows with their own collateral — both unprivileged entrypoints (`supply`, `borrow`) — then simply abstains from repaying; no privileged action, bad parameter, or oracle dishonesty is needed. On the steepest configured curve segment the index grows multiplicatively, so the cliff is reached deterministically given the market size. Capital cost is large, making this Medium rather than High.

### Recommendation
Saturate rather than panic at the value ceiling: use `mul_div_floor_saturating`-style clamping inside `calculate_supplier_rewards`/`scaled_to_original` during accrual, or engage `MAX_BORROW_INDEX_RAY` based on the ray value of `borrowed` (e.g., cap effective index at `i128::MAX / borrowed`) so the market degrades to capped interest instead of freezing. At minimum, document per-market safe supply caps and enforce them at the cap-setting layer so `borrowed` can never grow to where `borrowed * MAX_BORROW_INDEX_RAY` exceeds `i128::MAX`.

### Proof of Concept
From `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-356`: supply `1e9` 18-decimal tokens (`principal = BILLION * 10^18`), borrow 98% of it against oversized collateral, advance time one year per iteration calling `update_indexes`. Within the tested horizon `try_update_indexes_for(&["BIG18"])` returns `MATH_OVERFLOW` with `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequently `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both revert with `MATH_OVERFLOW`, proving the permanent freeze.
