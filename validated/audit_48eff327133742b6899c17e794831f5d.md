### Title
Permanent Device-Pairing Secret Reuse Enables Indefinite Unauthorized Device Pairing - (File: device.js)

### Summary
`device.js`'s `getOrGeneratePermanentPairingInfo()` generates (or reuses) a single long-lived `pairing_secret` with `is_permanent=1` and an expiry of `2038-01-01`, and this exact secret is repeatedly handed out to third parties (e.g. attached to arbiter-dispute/appeal payloads sent to arbstore servers). Unlike one-time pairing secrets, a permanent secret is never invalidated after use, so anyone who obtains it can pair as a trusted correspondent device with the victim's wallet at any time until 2038 — mirroring the Devise flaw of a single unrotated, indefinitely valid "remember me" credential usable from any device.

### Finding Description
`getOrGeneratePermanentPairingInfo` creates (once) or reuses a permanent pairing secret and stores it with an expiry far in the future: [1](#0-0) 

This secret is embedded into `my_pairing_code` and sent out-of-band to counterparties/arbstore servers as part of normal arbiter-contract flows (`openDispute`, `appeal`): [2](#0-1) [3](#0-2) 

On the receiving side, `handlePairingMessage` accepts any `pairing_secret` matching a non-expired row and, crucially, only deletes it if `is_permanent === 0`; permanent secrets are never consumed or rotated: [4](#0-3) 

The `pairing_secrets` table schema confirms the `is_permanent` flag and the effectively indefinite (2038) expiry design: [5](#0-4) 

Once an attacker replays this leaked/observed secret, `handlePairingMessage` inserts them as a fully `is_confirmed=1` correspondent device with no further authentication: [6](#0-5) 

A confirmed correspondent is then treated as a trusted device for numerous sensitive message types processed in `wallet.js`'s `handleMessageFromHub`, including shared-address creation, signing requests, and private payment chains: [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
This is exactly the Devise class of bug: a single, non-rotating "remember me"-style secret reused across all pairing events. Any party that ever received the permanent pairing code (e.g. an arbstore operator, an ex-counterparty in a dispute, or anyone who intercepted the QR/URL/log containing it) can pair with the wallet at any later time — even years later since the secret expires only in 2038 — without the wallet owner's fresh consent. Once paired, the attacker is treated as a legitimate correspondent device and can initiate "sign" requests for multisig/shared addresses, propose `create_new_shared_address` flows, and inject `private_payments`/`payment_notification` messages, which can be leveraged toward unauthorized fund movement, private-chain confusion, or persistent unauthorized access to the victim's device-messaging trust relationship.

### Likelihood Explanation
The permanent pairing code is generated and shared as part of a documented, reachable feature (arbiter-contract dispute/appeal flow, and other permanent-pairing use in the wallet UI), so any counterparty or intermediary the code passes through can capture it. Because the secret is never rotated or consumed after use, no timing constraints apply — the leak-to-exploitation window is unbounded (effectively 2038), maximizing the practical likelihood of exploitation once the secret is exposed to any untrusted party.

### Recommendation
Rotate or single-use pairing secrets: mark permanent secrets consumed/rotated after each new pairing, require an explicit fresh user confirmation prompt (with visible requester name/URL) before a permanent secret can add a new correspondent, and drastically shorten the default expiry of permanent secrets (or make them opt-in/regeneratable), analogous to Devise's post-CVE-2015-8314 fix of tying remember-me tokens to device-specific, rotating series/token pairs instead of one static, indefinitely valid secret.

### Proof of Concept
1. Wallet A generates its permanent pairing code via `getOrGeneratePermanentPairingInfo` and shares it with counterparty B through `arbiter_contract.openDispute`/`appeal`, which forwards `my_pairing_code` to an arbstore HTTP endpoint.
2. Any party with access to that transmitted code (arbstore operator, network observer, or B after the dispute concludes) later sends a `pairing` device message containing that same `pairing_secret` to Wallet A's hub.
3. `handlePairingMessage` finds the still-valid, still-`is_permanent=1` row, adds the sender as a confirmed correspondent device, and does not delete/rotate the secret.
4. The attacker's device is now a trusted correspondent and can send `sign`, `create_new_shared_address`, or `private_payments` messages that `wallet.js` processes as coming from a legitimate paired device.
