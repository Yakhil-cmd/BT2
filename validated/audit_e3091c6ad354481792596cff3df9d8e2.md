### Title
Unvalidated route payload lets an attacker-named "pool" execute arbitrary calls under the swapper's authorization tree, draining wallet tokens - (File: contracts/swap-aggregator/src/venues/soroswap.rs)

### Summary
The `mcp-remote` bug class is "untrusted remote input drives a dangerous invocation in the user's security context." The on-chain analog is the swap router's `StrategyPayload`: the `assets` registry is fully caller-controlled, and every hop `pool` address is invoked with no allowlist. A hop pool can therefore run attacker contract code while the *caller's* `require_auth` entry is on the stack, and any `token.transfer(caller, attacker, amount)` it makes is recorded by simulation as a child of the caller's authorization — the exact injection shape of the advisory.

### Finding Description
`execute_strategy(sender, total_in, swap_xdr)` decodes caller-supplied bytes where `assets` is an arbitrary `Vec<Address>` and each 5-byte instruction names a pool by `u8` index. `dispatch_hop` routes to venue adapters that invoke `hop.pool` directly, e.g. `env.invoke_contract(&ctx.hop.pool, "get_reserves"/"swap", ...)` in `contracts/swap-aggregator/src/venues/soroswap.rs:55-87`. No venue allowlist exists; the threat model confirms "the router calls the pool and token addresses its payload names and keeps no allowlist of them" (`docs/explanation/threat-model.md:155-165`).

The payload also reaches callers through the lending controller's strategy verbs: `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral` all forward the user's `swap: Bytes` into `router.execute_strategy` via `swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38`, after the user authorized `swap_collateral(...)` on their account. The malicious hop contract runs inside that invocation and can call `token::transfer(victim, attacker, x)` on any token the victim holds — unrelated to the swap pair. `simulateTransaction` records that transfer as a sub-invocation under the victim's `swap_collateral`/`execute_strategy` auth entry, so signing the simulated tree authorizes the theft.

This is proven by the harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` transfers Alice's entire unlisted `wallet_token` balance to the attacker; recording mode attaches the transfer to Alice's `swap_collateral` entry (lines 194-227), and enforcing mode executes the theft exactly when the signed tree contains it (lines 229-269), while the swap itself still returns a fair output and passes all controller risk gates.

### Impact Explanation
Theft of user funds unbounded by the swap: the attacker takes the victim's *whole wallet balance* of any token, not just the routed `amount_in`. Neither the router's `min_out` check nor the controller's `RouterOverspend`/`NoSwapOutput` measurements or final health-factor gate bound it, because the stolen transfer never touches the controller's or router's measured balances. Applies to direct `execute_strategy` callers and to every lending strategy entrypoint that takes `swap` bytes.

### Likelihood Explanation
Requires an unprivileged attacker only to get a victim to submit a malicious `swap_xdr` — the same trust model as the advisory (UI:R). The payload is produced off-chain and opaque packed bytes; a victim signing a `simulateTransaction`-produced auth tree (the documented standard flow) signs the poisoned child entry automatically unless their client decodes the route and rejects unexpected sub-invocations. Any attacker can deploy the rogue pool contract and craft the route; no privileged role, leaked key, or oracle manipulation is needed.

### Recommendation
Enforce an owner-managed venue/pool allowlist in the router (`hop.pool` must resolve to a registered pool for the declared venue and token pair), or at minimum bind `assets` entries to venue-verified identities (e.g., Aquarius `share_id`-style checks already done for LP tokens, extended to pools). On the controller side, document/enforce that clients must reject any `swap_collateral`/`multiply`/`execute_strategy` auth tree containing child invocations other than the single expected input `transfer`. Ideally the router should invoke pools via a sub-call pattern that cannot sit beneath the sender's auth entry.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Deploy `RogueHopPool` configured with `(victim=Alice, wallet_token, to=attacker, amount=77_770_000_000)`.
2. Build a route whose `hop_pool` is the rogue contract, `token_in=USDC`, `token_out=ETH`, `min_out=2.5 ETH` (fair output, so all slippage/risk checks pass).
3. Alice calls `controller.swap_collateral(alice, account_id, USDC_key, 5_000 USDC, ETH_key, route)`.
4. During the hop, `RogueHopPool::swap` executes `wallet_token.transfer(alice, attacker, 77_770_000_000)`. Simulation records it as a sub-invocation of Alice's `swap_collateral` auth entry (`simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` asserts `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`).
5. `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` confirms the signed simulated tree executes the theft while the swap still credits Alice `FAIR_OUT_ETH`.
