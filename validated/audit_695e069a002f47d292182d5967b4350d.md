### Title
Cross-repository Status forgery triggers unauthorized deploy via `Stack#trigger_continuous_delivery` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA (`Commit.where(sha: params.sha)`), with no check that the webhook's `repository.full_name` matches the repository owning that commit's stack. Since git commit SHAs are content-addressed and identical across forks, an attacker who controls any repository whose org is configured in Shipit (and can therefore emit a validly-signed webhook, per the threat model) can post a `success` status for a SHA that also exists in a victim stack, making that commit "deployable" and causing `Stack#trigger_continuous_delivery` to run `trigger_deploy` for it.

### Finding Description
The broken binding: `the repository that authenticated/certified the Status via CI == the repository owning the Stack whose deploy pipeline consumes that Status`. In `StatusHandler#process`: [1](#0-0) 

it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no scoping by the payload's `repository.full_name`. Compare this to `PushHandler#process`, which correctly restricts effects to `stacks` scoped by the webhook's own repository: [2](#0-1) 

`WebhooksController#verify_signature` only verifies the HMAC against the webhook secret configured for `repository_owner` taken from the *attacker's own* payload — it never checks that this repository is the one that actually owns the target commit: [3](#0-2) 

`Commit#create_status_from_github!` then creates the `Status` scoped to the commit's own `stack_id` (the victim stack), not the requester's stack: [4](#0-3) 

Once a `success` status lands, `Status#schedule_continuous_delivery` fires (`ContinuousDeliveryJob`), which calls `Stack#trigger_continuous_delivery`. If the commit becomes the head of `next_commit_to_deploy` (`commits.reachable...deployable_commits(...)`) and the victim stack has `continuous_deployment: true`, no active task, and a cached deploy spec, it calls `trigger_deploy(commit, Shipit.user, ...)`: [5](#0-4) 

`Shipit.user` is a legitimate system identity, but the binding fails at the CI-approval layer: the Status certifying "CI passed" was never emitted by (or for) the victim repository — it was forged by an unrelated repository the attacker controls, exploiting SHA collision from forking. Existing guards (`drop_unhandled_event`, `verify_signature`, `ExplicitParameters` schema on `StatusHandler`) check event type and payload shape/signature but never bind the processed commit to the requesting repository, so none of them catch this.

Attacker flow: fork the victim's public repository (preserving identical commit SHAs), ensure the fork/org is one for which Shipit has a configured webhook secret (satisfied per the threat model's "emit webhooks from a repository they own" capability), then set a commit status to `success` on that SHA in the fork via a legitimate, correctly-signed GitHub status webhook. Shipit's `StatusHandler` applies it to every `Commit` row sharing that SHA, including the one belonging to the victim's unrelated `Stack`.

### Impact Explanation
This lets an unrelated party inject a CI-approval signal for a repository they don't own, which — combined with `continuous_deployment: true` — causes the victim `Stack`'s trusted `Command`/`PTY.spawn` pipeline (carrying `GITHUB_TOKEN`) to execute a deploy for a commit whose actual CI status was never certified by that repository's own CI. This is a payload from one repository mutating another's stack/commit/deploy state and triggering an unauthorized deploy — Critical impact per the rubric. It is repeatable against any victim stack whose commits share a SHA reachable by an attacker-controlled repository (trivial via forking public repos), and the blast radius spans all stacks/tenants sharing the same Shipit instance and GitHub org configuration.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, a cached deploy spec, no active task (all realistic default configurations), and the target commit must not yet be otherwise deployable/deployed. The attacker needs to control a repository capable of emitting a correctly-signed webhook to the shared Shipit instance (granted by the stated threat model) and to have a fork/copy of the victim's repository so a target SHA is shared — straightforward for any public repository. No Shipit session, API token, or GitHub secret is required beyond what the attacker already legitimately controls for their own repository.

### Recommendation
Scope `StatusHandler#process` (and `Commit#create_status_from_github!`) to only apply statuses to commits whose owning `stack.repository.full_name` matches the webhook payload's `repository.full_name`/`repository.owner.login`, mirroring the repository-scoping already done in `PushHandler`. Reject or ignore statuses where the reporting repository does not match the commit's own stack repository.

### Proof of Concept
Minitest plan (model-level, no live GitHub, mirroring existing `StackTest`/`WebhooksControllerTest` patterns):
```ruby
test "#trigger_continuous_delivery must not deploy a commit made deployable by a Status from an unrelated repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.tasks.delete_all
  commit = victim_stack.next_commit_to_deploy_before_status_check # or the next undeployed commit

  # Simulate StatusHandler#process handling a webhook whose repository does NOT match commit.stack.repository
  forged_status_payload = OpenStruct.new(
    sha: commit.sha,
    state: 'success',
    description: 'forged',
    context: 'ci/travis',
    created_at: Time.now.to_s
  )

  # Binding under test:
  # LHS: identity certifying CI == commit.stack.repository.full_name ("shopify/shipit-engine")
  # RHS: identity that actually emitted the Status == "attacker/unrelated-repo"
  assert_not_equal commit.stack.repository.full_name, "attacker/unrelated-repo"

  assert_no_difference -> { Deploy.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(
      { 'sha' => commit.sha, 'state' => 'success', 'context' => 'ci/travis',
        'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } } }
    ).call
    victim_stack.trigger_continuous_delivery
  end
end
```
Currently, because `StatusHandler#process` ignores `repository.full_name`, this test fails (`Deploy.count` increments), proving the vulnerability; after the recommended fix it should assert `assert_no_difference` and pass.

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end

    def schedule_merges
      ProcessMergeRequestsJob.perform_later(self)
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
