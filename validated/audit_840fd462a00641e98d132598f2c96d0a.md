### Title
Bridge KLAY Permanently Locked When Recipient Contract Rejects Native Transfer — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` delivers bridged KLAY to the recipient using a low-level call with a hard `require`. If the recipient is a contract that reverts on receiving native KLAY (no payable `receive`/`fallback`), every operator attempt to settle that bridge nonce will revert, and the KLAY is permanently locked in the bridge contract with no recovery path.

### Finding Description

`handleKLAYTransfer` is the on-chain settlement function called by bridge operators to deliver KLAY that was locked or burned on the counterpart chain:

```solidity
// contracts/service_chain/bridge/BridgeTransferKLAY.sol  lines 98-99
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

Because the `require` is placed **after** all state mutations (`_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, `_updateHandleNonce`), a revert rolls back every state change. The vote record for that nonce is also rolled back (inside `_voteValueTransfer`), so operators can re-vote — but they cannot change `_to`, which is fixed by the original cross-chain request. If `_to` is a non-payable contract, every future call for that nonce will revert identically, and the KLAY is irrecoverable.

The `_lowerHandleNonceCheck` only enforces `lowerHandleNonce <= _requestedNonce`, so the stuck nonce does not block other nonces from being processed. However, `lowerHandleNonce` can never advance past the stuck nonce (since `_updateHandleNonce` advances it only through a contiguous filled range), meaning the bridge's recovery-block pointer is also frozen at that point.

### Impact Explanation

Bridged KLAY is permanently locked in the bridge contract. The user's assets on the source chain were already consumed (locked or burned by `requestKLAYTransfer`). There is no admin escape hatch, no pull-payment fallback, and no way for operators to override `_to`. The loss is total and irreversible for the affected amount.

### Likelihood Explanation

Any user who bridges KLAY to a contract address that lacks a payable `receive` or `fallback` function triggers this. Realistic examples include:
- A multisig or DAO contract deployed without a payable fallback
- A smart-contract wallet whose payable handler was removed in an upgrade
- A contract that deliberately reverts on ETH/KLAY receipt (e.g., a token contract)

The user controls `_to` at request time and may not anticipate the restriction. This is the same scenario acknowledged as Medium severity in the Olas audit.

### Recommendation

Replace the hard-require delivery with a pull-payment pattern: if the low-level call fails, credit `_to`'s claimable balance in a mapping and emit an event, rather than reverting. Alternatively, wrap the call in a try/catch (Solidity ≥0.6) and fall back to a claimable escrow. This ensures the nonce is always settled and KLAY is never permanently locked.

```solidity
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
    emit KLAYTransferFailed(_to, _value, _requestedNonce);
}
```

### Proof of Concept

1. On the source chain, a user calls `requestKLAYTransfer(contractAddr, value, extraData)` where `contractAddr` is a deployed contract with no payable fallback. The KLAY is locked/burned and a `RequestValueTransfer` event is emitted with `requestNonce = N`.
2. Bridge operators observe the event and call `handleKLAYTransfer(txHash, from, contractAddr, value, N, blockNum, extraData)` on the destination bridge.
3. Inside `handleKLAYTransfer`, after voting passes and all state is mutated, line 98 executes `contractAddr.call.value(value)("")`. The call returns `ok = false` because `contractAddr` has no payable fallback.
4. Line 99 `require(ok, ...)` reverts the entire transaction, rolling back all state changes including the vote record.
5. Operators retry indefinitely — every attempt reverts for the same reason.
6. The `value` KLAY is permanently locked in the bridge contract. The user's source-chain assets are already consumed. [1](#0-0) [2](#0-1)
