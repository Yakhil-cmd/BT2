### Title
Cross-stack CI status forgery via unscoped SHA lookup in `StatusHandler#process` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` records for an incoming `status` webhook by a bare SQL match on `sha` with no repository or stack scoping. Any organization whose GitHub App webhook secret is registered in Shipit can therefore write a `Status` onto every `Commit` row across every tracked stack that happens to share that SHA, and if the affected stack has `continuous_deployment` enabled, the resulting state flip can trigger `ContinuousDeliveryJob`/`schedule_merges` on a stack the sender never authenticated for.

### Finding Description
The broken binding is: **the equality `Commit.stack.repository == webhook.repository` is assumed by the system but never enforced** — `StatusHandler#process` only checks `commit.sha == params.sha`.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit` is a `belongs_to :stack` record [2](#0-1)  and `sha` is not unique across stacks: every stack independently records commits it has synced from GitHub, including commits shared through common history (forks, shared upstream, cherry-picks, merges). `WebhooksController#verify_signature` only authenticates that the payload body was HMAC-signed by the org derived from the payload's `repository.owner.login` field [3](#0-2) , and `GitHubApp#verify_webhook_signature` merely confirms the raw body matches that organization's configured `webhook_secret` [4](#0-3) . Neither check ties the verified organization to which `Commit`/`Stack` rows may be mutated — `StatusHandler` never re-checks that the commit it is updating belongs to a stack tracking the authenticated repository.

Exploit flow:
1. Attacker controls (or is a legitimate GitHub org member of) a repository whose org's GitHub App webhook secret Shipit trusts — i.e. any repository that already sends real, correctly-signed webhooks to this Shipit instance (this passes `verify_signature` legitimately, no secret is forged).
2. Attacker arranges for a commit with a specific SHA to exist both in their own tracked history and in a victim stack's tracked history (e.g. a shared upstream/base commit, a merge commit, or a cherry-pick that reproduces byte-identical commit metadata) so that both stacks' `Commit` tables contain a row with the same `sha`.
3. Attacker triggers (or spoofs, from their own already-authorized CI integration) a `status` event with `context: ci/kubernetes`, `state: success` (or `failure`) for that SHA.
4. `StatusHandler#process` fans this single, legitimately-authenticated webhook out to **every** `Commit` row sharing that SHA, including the victim stack's row, via `commit.create_status_from_github!(params)`.
5. `Commit#add_status` recomputes `status`, and on a meaningful transition calls `stack.schedule_merges` [5](#0-4) ; separately `schedule_continuous_delivery` (invoked on commit create, and effectively re-evaluated as CI state changes make the commit deployable) enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` and `stack.deployable?` [6](#0-5) .
6. `ContinuousDeliveryJob#perform` calls `stack.trigger_continuous_delivery`, which deploys `next_commit_to_deploy` if it is now deployable [7](#0-6) [8](#0-7) .

None of the documented guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) close this gap: they validate the sender's identity/organization, not the scope of the record being mutated. The `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/`context`, not that the resolved commits belong to the authenticated repository.

### Impact Explanation
A webhook correctly authenticated for repository/org A can flip CI status and, on stacks with `continuous_deployment` enabled, trigger an unauthorized deploy or block on a stack belonging to repository/org B, purely because both stacks happen to record a `Commit` row with the same `sha`. This is a payload for one repository mutating another's commit/stack state and, when `continuous_deployment` is enabled, an unauthorized deploy — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any pair of stacks sharing commit history and is not limited to a single tenant.

### Likelihood Explanation
Preconditions: the attacker must already have (or be able to trigger) a legitimately-signed `status` webhook for some org tracked by Shipit, and there must be a shared SHA between that org's tracked history and a victim stack with `continuous_deployment: true`. Shared SHAs across stacks are a realistic and common occurrence in this engine (forked repos, shared upstream commits, multiple stacks tracking related repositories) since Shipit does not require SHA uniqueness across stacks. No GitHub/Shipit secrets need to be forged — only a legitimate webhook the attacker is already entitled to send. This makes the precondition plausible rather than purely theoretical, though it depends on cross-stack SHA collisions actually existing in a given deployment.

### Recommendation
Scope the `StatusHandler` (and analogous handlers) lookup by the repository that authenticated the webhook, not by bare SHA: filter `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_id: authenticated_repository.id })` (or equivalent), deriving `authenticated_repository` from the verified `repository_owner`/`repository.full_name` used in `verify_signature`, so a status can only affect commits belonging to stacks of the repository that actually sent it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for one repo's SHA does not flip a commit belonging to another stack's identical SHA" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, requires ci/kubernetes
  victim_stack.update!(continuous_deployment: true)
  attacker_stack = shipit_stacks(:cyclimse) # different repository

  shared_sha = 'deadbeefcafedeadbeefcafedeadbeefcafebabe'
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  params = Shipit::Webhooks::Handlers::StatusHandler.new.send(:params_class).new(
    sha: shared_sha, state: 'success', context: 'ci/kubernetes'
  )

  # Binding under test: only attacker_stack authenticated this webhook (attacker's org signed it)
  assert_no_difference -> { victim_commit.reload.statuses.count }, 'victim commit should not receive a status from another repository\'s webhook' do
    Shipit::Webhooks::Handlers::StatusHandler.new.call({
      'sha' => shared_sha, 'state' => 'success', 'context' => 'ci/kubernetes',
      'repository' => { 'owner' => { 'login' => 'attacker-org' } }
    })
  end

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob)
end
```
This currently fails against the existing code (the victim commit does receive the status and, if it becomes deployable, `ContinuousDeliveryJob` is enqueued for `victim_stack`), demonstrating the cross-repository amplification via `continuous_deployment`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
