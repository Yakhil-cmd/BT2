### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the payload actually acted upon is keyed by the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the `X-Hub-Signature` against using `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Once the signature check passes, the event handlers (`PushHandler`, `CheckSuiteHandler`, etc.) resolve which `Repository`/`Stack` to mutate using a *different*, independently-attacker-controlled field: `payload.dig('repository', 'full_name')` [2](#0-1) . Nothing in the code enforces that `repository.owner.login` and `repository.full_name` refer to the same repository/organization.

### Finding Description
In a multi-organization Shipit deployment (supported natively, see `test/dummy/config/secrets_double_github_app.yml` configuring multiple orgs each with their own `webhook_secret` [3](#0-2) ), each organization is issued its own GitHub App and its own `webhook_secret`. The `verify_signature` before_action does:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

This picks the HMAC secret to validate against based solely on `repository.owner.login`. The signature itself (`sha1=...`) is an HMAC over the *entire raw JSON body*, computed with `GithubApp#verify_webhook_signature` [5](#0-4) , so as long as the attacker has the correct secret for *some* organization configured on the instance, they can sign an arbitrary JSON body — including one where `repository.owner.login` says "OrgA" (to pick OrgA's secret) but `repository.full_name` says "OrgB/victim-repo".

Downstream, `Handler#repository_name` and `Handler#stacks` never re-check the owner:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` splits `full_name` into `owner/name` and does a plain `find_by` with no cross-check against `repository_owner` used for signing [6](#0-5) . `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived, branch-matching stack of that repository [7](#0-6) , and `CheckSuiteHandler` schedules check-run refreshes for commits of a stack chosen the same way [8](#0-7) .

This is the same class of bug as the Trail of Bits Morpho finding: an access-control decision (which entity is "authorized" — there, the contract owner; here, the signing organization) is bound to one identifier, while the privileged operation is executed against a *different*, unchecked identifier taken from the same untrusted input (there, `msg.sender` vs. the implementation state; here, `repository.owner.login` vs. `repository.full_name`).

### Impact Explanation
An attacker who legitimately controls one organization's GitHub App/webhook configuration on a shared Shipit instance (i.e., knows that org's `webhook_secret`, which they set when installing their own app — not a Shipit account, not repository write access on the victim repo) can forge a webhook payload that:
- Passes signature verification under their own organization's secret, and
- Targets a *different* organization's/repository's stack via `repository.full_name`.

This lets the attacker trigger unauthorized `GithubSyncJob`s (`stack.sync_github`) and check-run refreshes against a victim organization's stacks that they have no legitimate access to — an unauthorized deploy-adjacent action performed on another repository's Shipit state, crossing a cross-organization/cross-repository trust boundary without any credential belonging to the victim org.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment configured with more than one GitHub organization (explicitly supported and documented via the `Shipit.github(organization:)` lookup and demonstrated in the test fixtures for double-app configs). The attacker only needs control of one tenant's webhook secret (obtained legitimately by installing their own GitHub App against the same Shipit instance) — no Shipit user account, API token, or GITHUB_TOKEN is required.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the HMAC, additionally verify that the organization used to pick the `webhook_secret` matches the owner encoded in `repository.full_name` (and any organization referenced by handlers), rejecting the request otherwise. Alternatively, bind the signing secret lookup and the repository resolution to the same single field, and have `Repository.from_github_repo_name` (or the handler base class) assert `repository_owner == full_name.split('/').first` before acting.

### Proof of Concept
1. Shipit instance is configured with two organizations, `orgA` and `orgB`, each with a distinct GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately controls `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `sha1=HMAC(orgA_webhook_secret, body)` and sends it as `X-Hub-Signature`.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "orgA")`, verifies successfully using `orgA`'s secret [9](#0-8) .
6. `PushHandler` resolves the target stacks via `payload.dig('repository','full_name')` = `"orgB/victim-repo"` [2](#0-1)  and calls `stack.sync_github` on `orgB`'s stacks, an organization the attacker never authenticated against [7](#0-6) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
