### Title
StatusHandler writes GitHub `status` events to any commit sha across all repositories, independent of `ignore_ci?` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository scoping, so any authenticated (to *its own* organization's webhook secret) `status` webhook can write a `Shipit::Status` row onto a same-sha commit belonging to a completely unrelated stack/repository. The write itself (binding: REPOSITORY SCOPE) happens unconditionally; whether it flips `deployable?` (impact magnitude) depends on the target stack's `ignore_ci?` and the injected `state`.

### Finding Description
Broken binding, stated as an equality that should hold but does not:
`StatusHandler#process`'s effective repository scope == `payload.dig('repository','full_name')`'s repository — this is FALSE. The base `Handler` class exposes exactly this scoping helper, `stacks`, defined as: [1](#0-0) 

but `StatusHandler#process` never uses it. Instead it does a global, cross-tenant lookup: [2](#0-1) 

`Commit.where(sha: params.sha)` matches every `Shipit::Commit` row in the database with that sha, across every `Stack`/`Repository`, and for each one calls `commit.create_status_from_github!(params)`, which writes a `Shipit::Status`: [3](#0-2) 

`verify_signature` in `WebhooksController` only checks the HMAC against the org named in the *attacker's own* payload (`repository.owner.login`), which the attacker fully controls and signs correctly since it's their own repo/org's webhook secret: [4](#0-3) 

Nothing after that validates that the `sha` in the payload actually belongs to the `repository.full_name` also in the payload — that field is accepted by `ExplicitParameters` but never consulted by `StatusHandler` for scoping.

Exploit flow: an attacker who owns/controls any repository tracked by Shipit (or any org configured in Shipit with its own webhook secret) learns the sha of a target commit in a victim stack (git commit shas are public for public repos, or knowable via PR activity), then sends `POST /webhooks` with `X-Github-Event: status`, a body `{"sha": "<victim-sha>", "state": "success", "repository": {"owner": {"login": "<attacker-org>"}}}`, signed with the attacker's own webhook secret. `verify_signature` passes because it validates against the attacker's own org. `StatusHandler` then finds the victim's `Commit` row (matched purely by sha, with no repo check) and writes a `Status` row for the victim's stack.

### Impact Explanation
Every such request writes a persisted `Shipit::Status` for a repository/stack the attacker never authenticated against — this is a cross-tenant write satisfying "a payload for one repository mutating another's stack/commit". The write happens **regardless** of the target stack's `ignore_ci?`. Its downstream effect on deployability differs:
- If the victim stack has `ignore_ci? == false`, injecting a `state: "success"` status can flip `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`, see `app/models/shipit/commit.rb:227-229`) from false to true, potentially triggering an unauthorized deploy via continuous delivery (`Status#after_create :enable_ci_on_stack`, `after_commit :schedule_continuous_delivery`, see `app/models/shipit/status.rb:16-19`).
- If `ignore_ci? == true`, `deployable?` is already true by that clause regardless of CI state, so the extra Status row is written (and CI is force-enabled via `enable_ci_on_stack`) but does not change deployability by itself.

This matches Critical severity ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy") specifically when the target stack is CI-gated (`ignore_ci? == false`), which is exactly the scope where this bug defeats the CI gate the operator explicitly relies on. It is repeatable against any commit sha reachable by any tracked stack, and requires only the attacker's own org's webhook secret (something they legitimately possess for their own repo).

### Likelihood Explanation
Preconditions: attacker needs a webhook-signing identity for any org/repo Shipit is configured to receive webhooks from (trivial — they can own that repo/org), and knowledge of a target commit sha in the victim stack (trivial for public repos, or derivable from PR/commit activity). No Shipit session, API token, or GitHub App secret is required. The request is a single unauthenticated `POST /webhooks` call; fully repeatable and scriptable against arbitrary stacks by sha collision.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring the base `Handler#stacks` helper: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, then only update commits/stacks under that repository's stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent join), rejecting/ignoring the status update for any commit not owned by that repository.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or a new `status_handler_test.rb`), parameterized over `ignore_ci?`:

```ruby
[true, false].each do |ignore_ci|
  test "cross-repo status webhook writes Status regardless of ignore_ci=#{ignore_ci}" do
    victim_stack = shipit_stacks(:shipit)
    victim_stack.update!(ignore_ci:)
    victim_commit = shipit_commits(:first) # belongs to victim_stack, state currently pending/failure

    attacker_payload = {
      'sha' => victim_commit.sha,
      'state' => 'success',
      'repository' => { 'owner' => { 'login' => 'attacker-org' } } # attacker's own org, correctly signed
    }.to_json

    request.headers['X-Github-Event'] = 'status'
    GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # simulating attacker's valid signature for their own org

    before_deployable = victim_commit.reload.deployable?

    assert_difference -> { victim_commit.statuses.count }, 1 do
      post :create, body: attacker_payload, as: :json
    end

    victim_commit.reload
    if ignore_ci
      assert_equal before_deployable, victim_commit.deployable? # binding: write happened, deployable? unchanged
    else
      assert victim_commit.deployable? # binding: write happened AND flipped deployable?
      refute_equal before_deployable, victim_commit.deployable?
    end
  end
end
```

Both assertions on "Status row written" hold in both branches (proving the REPOSITORY SCOPE violation is unconditional), while the `deployable?` assertion diverges only based on `ignore_ci?` (proving impact magnitude is conditional).
