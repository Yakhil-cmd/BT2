## Title
Webhook signature verification authenticates only the claimed organization, not the repository actually acted upon, enabling cross-organization/cross-repository event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
`WebhooksController#verify_signature` derives the organization used to select the HMAC secret from a field inside the very payload it is about to verify (`repository.owner.login` / `organization.login`), and only checks that this claimed organization's secret matches the signature. The event handlers that subsequently execute, however, key their side effects off a *different* payload field (`repository.full_name`) that is never cross-checked against the organization used for authentication. An attacker who legitimately controls **any** organization configured in Shipit's multi-tenant GitHub config (and therefore legitimately knows that organization's own `webhook_secret`) can sign a payload as their own org while setting `repository.full_name` to point at a victim organization's repository, causing Shipit to act on the victim's stack.

## Finding Description
`verify_signature` computes the signing organization purely from attacker-controlled payload content and does not tie it to the object the handlers later mutate: [1](#0-0) 

The signature check itself is a straightforward HMAC compare against the secret configured for that organization: [2](#0-1) 

Shipit explicitly supports multiple independently-configured GitHub organizations, each resolved by name and given its own secret bundle: [3](#0-2) 

Once the request is accepted, dispatch to handlers only depends on the `X-Github-Event` header, not on any verified organization/repository binding: [4](#0-3) 

The base `Handler` class resolves the target repository/stack from `repository.full_name` — a field that was never checked against `repository_owner` in `verify_signature`: [5](#0-4) 

`PushHandler` then uses that unscoped `stacks` relation to trigger a GitHub sync against an attacker-supplied SHA for whichever stack matches: [6](#0-5) 

`StatusHandler` is even more permissive: it looks up commits purely by `sha` with **no repository scoping at all**, so any org's valid signature lets it write a commit status on a commit that belongs to a completely unrelated stack: [7](#0-6) 

**Binding broken:** `organization_that_authenticated(signature) == organization_that_owns(repository_written_to)`. Before the attack, GitHub itself guarantees `repository.owner.login` and `repository.full_name` are consistent for genuine webhooks, so the equality holds naturally. After the attacker's forged request — signed with their own legitimately-known secret for `attacker-org`, but with `repository.full_name` rewritten to `victim-org/victim-repo` — the equality is broken: the signature only proves "attacker-org sent this," not "attacker-org owns the repository referenced in this payload."

## Impact Explanation
This is a cross-repository write: an operator of one tenant organization configured in Shipit can forge `push` webhooks that force `Stack#sync_github` to run against another organization's stack with an attacker-chosen `expected_head_sha`, and can forge `status` webhooks to set arbitrary commit statuses (state/description/target_url/context) on any commit in the database regardless of which organization it belongs to. Since commit status typically feeds into deployability checks, this can be used to manipulate deploy gating on stacks the attacker does not own — matching the "cross-repository writes / unauthorized deploy" impact class.

## Likelihood Explanation
Exploitation requires only that the attacker administers one legitimately configured tenant organization in a multi-org Shipit deployment (a normal, documented, unprivileged relationship to the engine) and can send an arbitrary POST to the shared `/webhooks` endpoint with a body they sign themselves. No Shipit session, `ApiClient` token, or victim-organization credentials are needed — only knowledge of the attacker's own organization's webhook secret, which they legitimately possess.

## Recommendation
Bind the authenticated organization to the repository actually acted upon: after determining the organization used to validate the signature, reject the webhook (or strip/ignore repository-identifying fields) unless `repository.full_name`'s owner segment matches the authenticated `repository_owner`. Additionally, `StatusHandler` (and any other handler resolving objects independent of `repository.full_name`) should scope lookups (e.g., `Commit.where(sha:, stack: ...)`) to a repository derived from the verified organization rather than performing a global, unscoped lookup by `sha` alone.

## Proof of Concept
1. Attacker is the legitimate admin of `attacker-org`, a tenant configured in Shipit's `secrets.github` with its own `webhook_secret` known to the attacker.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` with `attacker-org`'s webhook secret over this exact body and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `attacker-org` from the payload, fetches `attacker-org`'s secret, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-38`, `lib/shipit/github_app.rb:76-83`).
5. `PushHandler` resolves `stacks` via `repository.full_name` = `victim-org/victim-repo` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) — a repository the attacker does not own and never proved control over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
