## Finding

Investigating the `OmniXMultisender` refund-address bug reduces to a single admission invariant: **an authenticator must cryptographically bind a signature to the exact context it claims to authorize — the intended address/binding, not just an incidental byte match.** I traced this invariant through Aptos-native authenticator code (fee-payer `TransactionAuthenticator::verify`, `MultiKeyAuthenticator`, multisig `validate_multisig_transaction`) and found the strongest, independently-provable local violation in the WebAuthn signature verification path.

### Title
WebAuthn signature verification omits `type` and `origin`/RP-ID binding, allowing cross-ceremony signature reuse to authenticate Aptos transactions - (File: `types/src/transaction/webauthn.rs`)

### Summary
`PartialAuthenticatorAssertionResponse::verify` (and `verify_arbitrary_msg`) only checks that the WebAuthn `challenge` field equals the SHA3-256 digest of the signed message. It never validates `CollectedClientData.ty` (must be `"webauthn.get"`) or `CollectedClientData.origin`, and it never checks the relying-party-ID hash embedded in `authenticator_data`. These three fields are exactly what the WebAuthn spec (§7.2, verification steps 11–13) requires clients to check to prevent cross-ceremony and cross-origin signature reuse.

### Finding Description
`verify()` in [1](#0-0)  deserializes `client_data_json` into `CollectedClientData`, extracts only the `challenge` field, and calls `verify_expected_challenge_from_message_matches_actual` to compare it against the SHA3-256 hash of the signing message: [2](#0-1) . It then builds `verification_data` from `authenticator_data || SHA256(client_data_json)` and checks the raw ECDSA signature: [3](#0-2) .

No code path checks `collected_client_data.ty` (present in the struct used by tests, e.g. `ClientDataType::Get`, but never inspected in `verify`) and no code checks `collected_client_data.origin`. The `authenticator_data` field is only used as raw bytes for the signature message; its embedded RP-ID hash (which WebAuthn authenticators compute as SHA-256 of the relying-party ID) is never extracted or compared against an expected value. `PartialAuthenticatorAssertionResponse` only stores `signature`, `authenticator_data`, `client_data_json` — there is no `expected_rp_id` or `expected_type` parameter anywhere in the API: [4](#0-3) .

Per the WebAuthn spec, `authenticatorData || SHA-256(clientDataJSON)` is the exact byte string signed both during a `create()` (registration, self-attestation with "none"/"packed" format) ceremony and a `get()` (assertion) ceremony. The only fields that distinguish these ceremonies and bind the signature to the intended relying party are `type` and `origin` (inside `clientDataJSON`) and the RP-ID hash (inside `authenticatorData`). Because Aptos checks none of these, any signature over `authenticatorData || SHA-256(clientDataJSON)` — regardless of ceremony type or RP binding — that happens to encode the correct transaction-hash challenge will pass `verify()`.

### Impact Explanation
This breaks the authenticator-binding invariant called out in the admission pivots: *"Authenticator parsing, public key binding, WebAuthn checks... must bind to the intended account set."* Because `type` is unchecked, a credential-creation (`webauthn.create`) ceremony's self-attestation signature can be substituted for a `webauthn.get` assertion signature, and because `origin`/RP-ID are unchecked, the client-side origin binding that WebAuthn is specifically designed to enforce provides no protection at the Aptos verification layer — verification would accept the material as long as the raw bytes and challenge line up. Combined with client-side compromise (e.g., a malicious script able to trigger a `create()` ceremony with an attacker-chosen challenge, or a misbehaving/relayed client library), this allows a transaction to be authenticated with signing material that was never actually produced as an authorization "get" assertion for that specific relying party, i.e., wrong signing material accepted at the admission boundary — a High impact per the required admission gate.

### Likelihood Explanation
Exploitation requires control over, or ability to trigger, an alternate WebAuthn ceremony (e.g., `create()`) for the same authenticator/credential and to have the resulting signature routed through the Aptos SDK/authenticator construction path — this is not purely remote/network-triggerable and depends on client-side conditions (e.g., a compromised or malicious front-end/library, or a credential-management bug), making likelihood **Low-to-Medium**, but the missing checks are a clear code-level root cause independent of any external system, and no privileged assumption is required to exploit them once a mismatched-ceremony signature is available.

### Recommendation
In `PartialAuthenticatorAssertionResponse::verify` and `verify_arbitrary_msg`, after deserializing `CollectedClientData`:
1. Assert `collected_client_data.ty == ClientDataType::Get` (reject `Create` or any other type).
2. Compare `collected_client_data.origin` against an expected, chain-configured origin/RP set (or otherwise document and enforce the accepted origin(s)).
3. Parse `authenticator_data` and verify its RP-ID hash matches the expected RP ID for Aptos WebAuthn transactions, consistent with WebAuthn spec verification steps.

### Proof of Concept
Conceptual PoC (requires local code changes to construct, since the SDK doesn't expose a "create" ceremony path directly, but demonstrates the missing check):
1. Construct a `CollectedClientData` with `ty: ClientDataType::Create` and `challenge` set to `Base64Url(SHA3-256(signing_message(raw_txn)))`.
2. Sign `authenticatorData || SHA256(clientDataJSON)` with the credential's private key (as would occur during a self-attested `create()` ceremony).
3. Build `PartialAuthenticatorAssertionResponse::new(AssertionSignature::Secp256r1Ecdsa{signature}, authenticator_data, client_data_json)` and wrap it in `SingleKeyAuthenticator`/`AccountAuthenticator::single_key`, then `TransactionAuthenticator::SingleSender`.
4. Call `signed_txn.verify_signature()` — per the code at [1](#0-0) , this succeeds because only `challenge` is checked, confirming `type`/`origin`/RP-ID are not enforced.

fn verify_expected_challenge_from_message_matches_actual<T: Serialize + CryptoHash>(
    message: &T,
    actual_challenge: &[u8],
) -> std::result::Result<(), CryptoMaterialError> {
    // Generate signing_message, which is the BCS encoded bytes of message, prefixed with a hash
    let signing_message_bytes = signing_message(message)?;
    // Expected challenge is SHA3-256 digest of RawTransaction bytes
    let expected_challenge = HashValue::sha3_256_of(signing_message_bytes.as_slice());

    expected_challenge
        .to_vec()
        .as_slice()
        .eq(actual_challenge)
        .then_some(())
        .ok_or(CryptoMaterialError::ValidationError)
}

    pub fn verify<T: Serialize + CryptoHash>(
        &self,
        message: &T,
        public_key: &AnyPublicKey,
    ) -> Result<()> {
        let collected_client_data: CollectedClientData =
            serde_json::from_slice(self.client_data_json.as_slice())?;
        let challenge_bytes = Bytes::try_from(collected_client_data.challenge.as_str())
            .map_err(|e| anyhow!("Failed to decode challenge bytes {:?}", e))?;

        // Check if expected challenge and actual challenge match. If there's no match, throw error
        verify_expected_challenge_from_message_matches_actual(message, challenge_bytes.as_slice())?;

        // Generates binary concatenation of authenticator_data and hash(client_data_json)
        let verification_data = generate_verification_data(
            self.authenticator_data.as_slice(),
            self.client_data_json.as_slice(),
        );

        // Note: We must call verify_arbitrary_msg instead of verify here. We do NOT want to
        // use verify because it BCS serializes and prefixes the message with a hash
        // via the signing_message function invocation
        match (&public_key, &self.signature) {
            (
                AnyPublicKey::Secp256r1Ecdsa { public_key },
                AssertionSignature::Secp256r1Ecdsa { signature },
            ) => signature.verify_arbitrary_msg(&verification_data, public_key),
            _ => Err(anyhow!(
                "WebAuthn verification failure, invalid key, signature pairing"
            )),
        }
    }
