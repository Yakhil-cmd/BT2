### Title
Webhook Signature Verification Is a No-Op When `webhook_secret` Is Unset, Allowing Forged `membership` Events to Escalate into `Shipit.github_teams` Authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever no `webhook_secret` is configured for the organization, and Shipit's own setup documentation marks `webhook_secret` as *optional*. Combined with the `MembershipHandler`, an unauthenticated attacker can POST a forged `membership` webhook payload that grants any (attacker-controlled) `User` record membership in a `Team` whose `github_id` matches one of `Shipit.github_teams`, thereby satisfying `User#authorized?` and gaining access to the application without ever being a real member of the corresponding GitHub team.

### Finding Description
`WebhooksController#verify_signature` delegates trust verification entirely to the configured `GitHubApp` for the organization named in the payload: [1](#0-0) 

That delegate, `GitHubApp#verify_webhook_signature`, short-circuits to `true` when no secret is configured: [2](#0-1) 

The setup guide explicitly documents `webhook_secret` as optional (`Webhook secret (optional): ...`), so this is a supported, expected configuration in this engine, not a mis-deployment: [3](#0-2) 

Once past `verify_signature`, `WebhooksController#create` dispatches the raw, attacker-supplied JSON directly to the handler for the declared `X-Github-Event`: [4](#0-3) 

`MembershipHandler#process` trusts the payload's `team.id`, `organization.login`, and `member.login` fields to create/find a `Team` and add a `User` (created or found purely from the attacker-controlled `member.login`) to that team: [5](#0-4) [6](#0-5) 

`User#authorized?` grants application access solely based on `Team` membership matching `Shipit.github_teams`: [7](#0-6) 

The break: the binding that should hold is *"organization whose webhook signature was verified" == "organization whose membership/authorization data is written."* When `webhook_secret` is blank, the left side of that equality is never actually checked (`verify_webhook_signature` returns `true` for any payload/signature pair), so the right side — team membership that directly feeds the application's authorization decision (`Shipit.github_teams`) — is fully attacker-controlled.

### Impact Explanation
This lets an unprivileged attacker who can reach the public `/webhooks` endpoint (no session, no `ApiClient` token, no GitHub App private key required) forge a `membership` event naming:
- `team.id` equal to the `github_id` of a `Team` created from one of the configured `Shipit.github_teams`,
- `organization.login` equal to that team's org,
- `member.login` equal to their own GitHub login (which they can register as a `Shipit::User` simply by completing the normal OAuth login flow once).

The handler then adds that `User` to the privileged `Team`, and subsequent authentication checks in `Authentication#force_github_authentication` / `User#authorized?` treat the attacker as a legitimate member of `Shipit.github_teams`, granting them full access to the Shipit UI/API — deploys, rollbacks, task triggering, etc. This is exactly the listed High-impact category: "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Likelihood depends on the target instance configuring at least one organization without a `webhook_secret`, which the project's own setup docs present as an acceptable, optional configuration (not a misconfiguration to be flagged), and on the target using `Shipit.github_teams` for authorization (a documented core feature: "If it's missing, the Shipit installation will be public unless you setup another authentication method"). For any deployment following the documented setup while relying on team-based `oauth.teams` authorization and omitting the optional webhook secret, this is a straightforward, no-prerequisite attack — a single crafted HTTP POST.

### Recommendation
Do not treat a missing/blank `webhook_secret` as "verification passed." At minimum, require a `webhook_secret` for any organization whose config is also used for `Shipit.github_teams`-based authorization, or fail closed (reject the webhook) when no secret is configured instead of returning `true` in `GitHubApp#verify_webhook_signature`. Additionally, `MembershipHandler` should not be able to alter authorization-relevant `Team` membership purely from unauthenticated webhook content without this hard signature guarantee.

### Proof of Concept
1. Configure (or find) a Shipit deployment where one configured GitHub organization has `webhook_secret` unset, per the documented "(optional)" setup, while `Shipit.github_teams` includes a team belonging to that same organization (or any org, since `repository_owner`/`organization.login` resolution is attacker-supplied in the payload and only used to select which, possibly secret-less, app config to check).
2. As an attacker, complete the normal GitHub OAuth login flow once to create your own `Shipit::User` record (login `attacker-login`).
3. Send a forged webhook:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <github_id of a Shipit.github_teams team>, "name": "Team", "slug": "team", "url": "https://github.com/x" },
  "organization": { "login": "<org-with-no-webhook-secret>" },
  "member": { "login": "attacker-login" }
}
```
4. `WebhooksController#verify_signature` resolves the `GitHubApp` for `<org-with-no-webhook-secret>`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) regardless of the (absent or garbage) `X-Hub-Signature` header.
5. `MembershipHandler#process` runs, adding `attacker-login`'s `User` to the privileged `Team`.
6. The attacker logs into Shipit; `User#authorized?` now returns `true` via `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, granting full application access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
