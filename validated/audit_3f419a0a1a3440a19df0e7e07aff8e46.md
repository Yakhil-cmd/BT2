### Title
Cross-organization team membership forgery in `MembershipHandler#process` allows unauthorized `Shipit.github_teams` escalation - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` looks up teams solely by `params.team.id` and never verifies that the signing organization (`params.organization.login`, which is what `WebhooksController#verify_signature` uses to pick the webhook secret) actually owns that team. Any attacker who controls one legitimately-configured org in a multi-org Shipit deployment can sign a `membership` webhook with their own org's real webhook secret while pointing `team.id` at a team that belongs to a completely different, more privileged org already present in `Shipit.github_teams`, causing Shipit to record a real `Membership` row without ever consulting GitHub's actual roster for that team.

### Finding Description
The broken binding: `Membership.exists?(team_id: T, user: attacker) == GitHub_reports_membership(T, attacker)` for `T ∈ Shipit.github_teams.map(&:id)`. This is expected to hold because the whole point of the `membership` webhook is to mirror GitHub's team roster, but the code lets it diverge.

Path:
1. `WebhooksController#verify_signature` selects the webhook secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization', 'login')` for membership events: [1](#0-0)  and [2](#0-1) . This only proves the request was signed by *some org's* legitimate GitHub App secret — the org named in the payload — nothing more.
2. `MembershipHandler#process` then resolves the team purely by numeric id, independent of which org signed the request: [3](#0-2) . `Team.find_or_create_by!(github_id: params.team.id)` will **find** (not create) any pre-existing `Team` row — including one that legitimately belongs to a different organization than the one that signed the request — and `team.add_member(member)` unconditionally inserts a `Membership`.
3. `Shipit.github_teams` is a global list of trusted teams (`github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }`) used everywhere authorization is checked, e.g. [4](#0-3)  and [5](#0-4) .

Exploit: attacker owns/administers `attacker-org`, one of several orgs configured under `secrets.github` (multi-org schema, documented in `docs/setup.md`). They know `attacker-org`'s real webhook secret (it's their own app installation) and can compute a valid `X-Hub-Signature`. They send:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<hmac with attacker-org's real secret>
{
  "action": "added",
  "team": { "id": <github_id of a Team already in Shipit.github_teams, belonging to victim-org>, "name": "...", "slug": "...", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker" }
}
```
`verify_signature` succeeds (attacker-org's secret matches). `find_or_create_team!` finds the pre-existing victim team by `github_id` and ignores the fact that it was signed by `attacker-org`, not `victim-org`. `User.find_or_create_by_login!('attacker')` creates/fetches the attacker's `User`. `team.add_member(member)` inserts the `Membership`. `User#authorized?` now returns `true` for the attacker across the whole Shipit instance, with no real GitHub team-membership check ever performed.

Existing guards do not catch this: `verify_signature` only authenticates "a message from org X", not "this specific team belongs to org X"; `find_or_create_team!` has no such organization-match assertion; the `ExplicitParameters` schema in `MembershipHandler.params` validates shape only, not cross-field authorization.

### Impact Explanation
A single crafted request grants the attacker (or any GitHub login they choose to name in `member.login`, e.g. a colleague or bot they control) full `authorized?` status in Shipit — bypassing GitHub team-membership authorization entirely for the whole application (stacks, deploys, rollbacks, task streams, everything gated by `force_github_authentication`). It is fully repeatable and works against any team id already present in `Shipit.github_teams`, i.e., any org onboarded to the multi-org Shipit config, regardless of which org the attacker actually controls. Blast radius spans all tenants/orgs sharing the Shipit instance.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-org `github:` schema (documented feature) where the attacker legitimately administers at least one of the configured orgs, and (2) `Shipit.github_teams` non-empty and containing a team id from another org. Both are realistic, supported deployment configurations. The attacker's cost is trivial — one HTTP POST with a signature computed from a secret they legitimately hold for their own org's GitHub App — no GitHub API calls, no live GitHub interaction, no privileged Shipit credentials needed.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), verify that `params.organization.login.downcase == team.organization.downcase` before creating/mutating the team or adding/removing members; reject (raise/log and no-op) if they diverge. Additionally, consider re-verifying membership changes against the GitHub API (`GET /orgs/:org/teams/:team_id/members/:username`) before trusting `added`/`removed` events, since webhook payloads should not be treated as sole source of truth for privilege-granting state.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "membership webhook cannot grant access to a team owned by a different signed org" do
  victim_team = shipit_teams(:shopify_developers) # already in Shipit.github_teams, organization: 'shopify'
  Shipit.stubs(:github_teams).returns([victim_team])

  # Attacker controls "attacker-org", a distinct configured org.
  GitHubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # simulate valid signature from attacker-org's real secret

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' }, # signed org != victim_team.organization ('shopify')
    member: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'membership'
  post :create, body: payload, as: :json
  assert_response :ok

  attacker = User.find_by(login: 'attacker')
  # Binding check: no real GitHub roster for `shopify/developers` was ever consulted for `attacker`.
  refute victim_team.members.include?(attacker), "attacker should not be added to a team of an org that did not sign the request"
  refute attacker.authorized?, "attacker must not gain Shipit.github_teams authorization via a webhook signed by a different org"
end
```
This test currently fails against the existing code (the `Membership` row is created and `authorized?` returns `true`), demonstrating the vulnerability.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
