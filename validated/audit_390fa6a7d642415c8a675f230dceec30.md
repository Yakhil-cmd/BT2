### Title
Unauthenticated webhook signature bypass when `webhook_secret` is unset enables forged `membership` events that escalate into `Shipit.github_teams` authorization - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever no `webhook_secret` is configured for the organization selected from the incoming payload, turning the entire webhook authentication check into a no-op for any GitHub App entry left without a secret (which is the documented/shipped default). Combined with `MembershipHandler`, which trusts the raw JSON body to create/locate a `Team` by numeric GitHub `team.id` and unconditionally add an attacker-chosen `member` to it, an unauthenticated network attacker can forge a `membership` webhook that grants an arbitrary GitHub login membership in a `Team` matching one of `Shipit.github_teams`, bypassing the OAuth-team access-control gate entirely.

### Finding Description
`WebhooksController#verify_signature` picks a GitHub App configuration based on an unverified field of the raw JSON payload and delegates the actual cryptographic check to it: [1](#0-0) 

The verification itself is a no-op when the resolved app has no `webhook_secret` configured: [2](#0-1) 

`webhook_secret` is explicitly optional/nilable in the shipped configuration templates and docs ("If you've set a webhook secret ... copy it here"), so a Shipit installation (or one specific organization entry in a multi-org config) can legitimately run with no secret configured: [3](#0-2) [4](#0-3) 

When `verify_signature` passes (trivially, because `webhook_secret` is blank/nil), `WebhooksController#create` dispatches the raw, attacker-controlled JSON straight to the registered handlers with no further authentication: [5](#0-4) 

For the `membership` event, `MembershipHandler#process` creates/looks up a `Team` purely from attacker-supplied `team.id`/`team.name`/`team.slug` and adds an attacker-supplied `member.login` (auto-vivified via `User.find_or_create_by_login!`) to it, with no verification against real GitHub team membership: [6](#0-5) 

Application authorization is gated on exactly this `Team` relationship: a `User` is `authorized?` if it belongs to any team whose id is in `Shipit.github_teams`: [7](#0-6) [8](#0-7) 

**Trust binding broken (as an equality):**
`verify_webhook_signature(secret_for(selected_org), raw_body) == true` is supposed to guarantee `raw_body` genuinely originated from GitHub for `selected_org`. When `secret_for(selected_org)` is unset, the left side collapses to `true` unconditionally — i.e. "payload cryptographically attested by GitHub" is decoupled from "payload accepted and acted upon", exactly mirroring the reported bug class where a specific input (`_epoch` too large relative to `_amount`) collapses a computed value (`rate`) to `0`, silently disabling the intended safeguard. Here the "large input relative to small denominator" is the absence of `webhook_secret`, and the safeguard that collapses is the entire signature check.

**Before the attack:** only genuine GitHub-signed events reach the handlers (assuming `webhook_secret` set); `Shipit.github_teams` membership can only be modified by real GitHub org/team membership changes relayed through a verified webhook.

**After the forged request:** an unauthenticated POST to the webhook endpoint with `X-Github-Event: membership`, action `added`, an arbitrary `member.login`, and a `team.id` matching a `Shipit.github_teams` team's `github_id` results in that login being persisted as a member of the authorizing team — with no GitHub signature ever validated for that org.

### Impact Explanation
This directly matches the report's High-severity bucket: "escalation into `Shipit.github_teams` authorization." Once an attacker-chosen GitHub login is added to a team backing `Shipit.github_teams`, any Shipit `User` record for that login (created on first successful GitHub OAuth login) passes `authorized?` and gains full access to the Shipit application (viewing stacks, deploying, rolling back, etc., depending on what other authorization the app exposes to authenticated users) — an authentication/authorization bypass with no credential of any kind required.

### Likelihood Explanation
The precondition — a Shipit GitHub App configuration entry without a `webhook_secret` — is not a misuse of the engine; it is the shipped default (`webhook_secret: # nil` in `config/secrets.development.example.yml`, and the setup docs describe it as something you only add "if you've set" one). Any operator who deploys Shipit for a quick internal setup, or a multi-org configuration where one organization's App was created without a webhook secret, is exposed. The only additional requirement is knowing (or brute-forcing/guessing) a real numeric GitHub team id that is also configured under `github.oauth.teams`; team ids are frequently discoverable via the public GitHub API for organizations with visible teams, and no other secret, token, or session is needed.

### Recommendation
- Make `verify_webhook_signature` fail closed: never return `true` when a signature header is absent or `webhook_secret` is not configured; instead, either reject the request or, if unauthenticated webhooks are intentionally allowed, gate this explicitly with an operator opt-in flag rather than an implicit fallback on blank secret.
- In `MembershipHandler`, do not trust webhook payload alone to determine authorization-relevant team membership; cross-check against `Shipit.github_teams` via an authenticated GitHub API call (using the App's installation token) before persisting membership changes that affect `authorized?`.
- Treat the org-selection field used for signature verification and any field used by handlers to mutate authorization state as the same trust boundary; do not let downstream handlers key off different payload fields than the one that was used to select/verify the signing secret.

### Proof of Concept
Preconditions: Shipit configured with `github.oauth.teams` including a team whose real GitHub `id` is `48`, and the resolved GitHub App config for the request's organization has `webhook_secret` unset (default/shipped config).

```
POST /github/webhooks HTTP/1.1
Host: shipit.example.com
Content-Type: application/json
X-Github-Event: membership
(no X-Hub-Signature header, or any arbitrary value — it is never checked)

{
  "action": "added",
  "team": { "id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker-github-login" }
}
```

Because `webhook_secret` is blank for the resolved org, `verify_webhook_signature` returns `true` ( [9](#0-8) ), `WebhooksController#create` dispatches to `MembershipHandler`, which executes `team.add_member(member)` for `member.login == "attacker-github-login"` ( [10](#0-9) ). After `attacker-github-login` subsequently completes normal GitHub OAuth login to Shipit, `User#authorized?` returns `true` because the user is now a member of team id `48`, which is in `Shipit.github_teams` ( [7](#0-6) ), granting full access to the application without ever having been added to the real GitHub team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
