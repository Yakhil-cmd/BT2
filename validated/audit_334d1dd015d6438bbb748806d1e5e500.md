### Title
Webhook signature verification keyed by `repository.owner.login` is not bound to the `repository.full_name` actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret validates the HMAC signature by reading `repository.owner.login` (or the `organization.login` fallback) out of the untrusted JSON payload, then verifies the *entire raw body* against that org's secret. However, every event handler resolves the repository to act on using a *different* field from the same payload: `repository.full_name` (e.g. `Handler#repository_name`, `Repository.from_github_repo_name`, and `PullRequest::OpenedHandler#repository`). Nothing in the code enforces that `full_name`'s owner segment matches `owner.login`. This mirrors the Fabric crosslinking bug class: the value covered by the trust check (`owner.login`, used to pick the verifying key) is not the same value the downstream logic actually operates on (`full_name`), so an attacker who legitimately controls one organization's webhook secret can make Shipit act on a repository belonging to a different organization.

### Finding Description
- `verify_signature` in [1](#0-0)  resolves `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, where `repository_owner` is defined as: [2](#0-1) 
- `verify_webhook_signature` in `GitHubApp` does a raw HMAC-SHA1 comparison of the whole request body against the secret configured for that organization: [3](#0-2) . It authenticates *that a body was signed by some org's registered secret*, not that any particular field inside the JSON is trustworthy relative to any other field.
- Every downstream handler, however, resolves the target repository independently via `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 
- `PullRequest::OpenedHandler` (and its siblings) resolve the acted-upon repository the same way, from `params.repository.full_name`, completely independent of `owner.login`: [6](#0-5) [7](#0-6) 
- `PushHandler` uses `stacks`, which is likewise derived from `repository_name` (`full_name`) in the shared `Handler` base class: [8](#0-7) 

In a multi-organization Shipit deployment (`docs/setup.md`'s "Using Multiple Github Applications" section, `lib/shipit.rb`'s `github_app_config`/`github_organizations`), each configured GitHub org has its own `webhook_secret`. Since `verify_signature` only checks that *some* valid signature exists for the org named in `repository.owner.login`, and the actual repository resolution ignores that field entirely in favor of `repository.full_name`, the two JSON fields are never checked for consistency with each other. This is the same class of bug as the Fabric report: a verified/authenticated field (`owner.login`, used to pick the signing key) diverges from the field the system actually trusts and acts upon (`full_name`).

### Impact Explanation
An attacker who is a legitimate GitHub App/webhook administrator for **one** onboarded organization (Org A) knows Org A's `webhook_secret` (it is displayed to whoever creates/manages the GitHub App per `docs/setup.md`). Using that secret, they can HMAC-sign an arbitrary JSON body where `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the signature validates) while `repository.full_name = "OrgB/private-repo"` (a completely different, unrelated organization's repository tracked by the same Shipit instance). Because handlers resolve the acted-upon `Stack`/`Repository` solely via `full_name`, this forged, validly-"signed" webhook can trigger `GithubSyncJob` (push events), create review stacks or manipulate PR-based provisioning (`pull_request` events), post fabricated commit statuses (`status` events), or otherwise write to/impact Org B's stacks and deployment state, cross-repository, despite the attacker never having credentials, membership, or GitHub App access to Org B. This crosses the "cross-repository writes / unauthorized deploy or rollback" impact bar defined for High/Critical findings, since it lets an attacker use one org's trust boundary to write into another org's stack state.

### Likelihood Explanation
This requires only a legitimate (even low-privilege) webhook-secret-holder for any *one* organization onboarded to a shared, multi-tenant Shipit deployment — a realistic and unprivileged-relative-to-other-orgs position, matching the "unprivileged attacker" framing in the rules (no Shipit session, `ApiClient` token, or GitHub App private key for the *target* org is needed). The vulnerable code path (`verify_signature` → handler dispatch) is unconditionally exercised for every webhook POST, so exploitation only requires crafting one payload and computing one HMAC, both trivially scriptable.

### Recommendation
Bind the field used to select the verification key to the field used for repository resolution, or better, verify them against each other after signature validation: after computing `repository_owner`, also derive `repository.full_name`'s owner segment and assert equality before dispatching to handlers; alternatively, resolve the target `Repository`/`Stack` using `repository.owner.login` consistently instead of trusting an independently supplied `full_name`. Consider also validating that `full_name.split('/').first.casecmp(owner.login).zero?` inside `WebhooksController#verify_signature` and rejecting mismatches with `head(422)`.

### Proof of Concept
1. Onboard/administer a legitimate GitHub App installation for organization `attacker-org` on the shared Shipit instance, obtaining its `webhook_secret` (a normal, documented part of the app setup).
2. Craft a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org_webhook_secret, raw_body)`.
4. POST to `/webhooks` with `X-Github-Event: push` and the above signature.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature validates successfully.
6. `PushHandler#process` resolves `stacks` via `Handler#repository_name` → `payload.dig('repository','full_name')` = `"victim-org/target-repo"`, and enqueues `GithubSyncJob`/`sync_github` against Org B's stack — an org the attacker never authenticated to or received a webhook secret for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
