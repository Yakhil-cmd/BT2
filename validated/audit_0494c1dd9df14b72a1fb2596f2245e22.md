### Title
API client scoped to one stack can read CCMenu build status of any other stack via `token` param - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's stack-scoping method with an unscoped lookup, allowing an `ApiClient` restricted to a single stack (`stack_id`) to read the CI/deploy status of arbitrary other stacks.

### Finding Description
`Shipit::Api::BaseController` defines a `stacks` accessor that restricts the queryable set of stacks to the one bound to the authenticated `ApiClient` when that client has a `stack_id`, and a `stack` helper that resolves the requested `params[:stack_id]` only within that scoped relation: [1](#0-0) 

This is the intended binding: *the stack a token authorizes == the stack it touches*. Other API endpoints (e.g. `Api::StacksController`) rely on this scoped `stack`/`stacks` helper, and there is an explicit regression test enforcing it ("an api client scoped to a stack will only see that one stack").

However, `Shipit::Api::CCMenuController` — which authenticates via a bare `token` query-string parameter instead of the `Authorization` header — redefines `stack` to bypass the scoping entirely, resolving directly against the global `Stack` relation: [2](#0-1) 

`require_permission :read, :stack` only checks that the client's `permissions` array contains `read:stack`; it does not verify that the target stack matches `current_api_client.stack_id`: [3](#0-2) 

Tokens of this kind are routinely minted scoped to a single stack for exactly this CCMenu feature: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id == stack.id` (when `stack_id` is set) — is broken specifically in this controller: any valid `read:stack` token, even one scoped to stack A via `stack_id`, can substitute `params[:stack_id]` for stack B and successfully render B's CCMenu XML.

### Impact Explanation
This is an authorization escalation of a deliberately narrow-scoped token: a client meant to see only its own stack's build status can enumerate and read the deploy/build state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, etc.) of every other stack in the installation. This matches the in-scope High-impact category of "unauthenticated read of stack state" via a token whose authorized scope is bypassed.

### Likelihood Explanation
High. No special privilege beyond possessing any valid `read:stack`-scoped `ApiClient` token is required (these tokens are created automatically and embedded in CCMenu URLs, e.g. via `CCMenuUrlController#fetch`). The attacker only needs to change the `stack_id` path segment while reusing their own `token` query parameter — no signature, session, or additional secret is needed.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it via the inherited scoped `stacks.from_param!`) so that stack-scoped `ApiClient` tokens cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. Create/obtain a stack-scoped read-only client for stack A, e.g. via `CCMenuUrlController#fetch` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, name:)` bound implicitly to stack A through normal usage), yielding `token`.
2. Request `GET /stacks/:owner/:repoA/:envA/ccmenu.xml?token=<tokenA>` — succeeds as expected.
3. Request `GET /stacks/:owner/:repoB/:envB/ccmenu.xml?token=<tokenA>` for an unrelated stack B — because `CCMenuController#stack` calls `Stack.from_param!` instead of the scoped `stacks.from_param!`, this also returns HTTP 200 with stack B's build status, despite `tokenA` never having been authorized for stack B.
