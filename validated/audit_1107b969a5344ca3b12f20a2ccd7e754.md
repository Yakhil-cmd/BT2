This confirms the vulnerability. `PushHandler` and `StatusHandler` locate `stacks`/`Commit` purely via `payload.dig('repository', 'full_name')` [1](#0-0) , and `StatusHandler#process` directly creates a GitHub status on any commit matching the given SHA across the whole install [2](#0-1) , while `PushHandler#process` triggers `sync_github` for any stack tracking that branch [3](#0-2) . Neither uses `repository.owner`. Meanwhile signature verification in `WebhooksController#verify_signature` selects the secret to check against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [4](#0-3) [5](#0-4) . Multi-organization installs are an explicitly documented, supported configuration, each with its own independent `webhook_secret` [6](#0-5) [7](#0-6) .

### Title
Webhook signature verification keys off `repository.owner` while event processing keys off `repository.full_name`, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
On a multi-organization Shipit deployment, the field used to select which `webhook_secret` verifies the inbound signature (`repository.owner.login`) is not the same field used to determine which repository/stack the event actually mutates (`repository.full_name`). An attacker who controls a GitHub organization that is legitimately installed on the same Shipit instance can forge a webhook payload whose `owner.login` names their own organization (so it is HMAC-verified with a secret they legitimately possess) but whose `repository.full_name` names a victim repository belonging to a different organization on the same install.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/secret to validate the `X-Hub-Signature` against using:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 
This value is taken from the untrusted, attacker-controlled JSON body, and is used only to pick `Shipit.github(organization: repository_owner)` for signature verification [4](#0-3) .

Once the signature check passes, `create` hands the same raw `params` to the event handlers unchanged [8](#0-7) . Handlers resolve the target stack via `Handler#stacks`, which uses a *different* field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [9](#0-8) 

Nothing ties `full_name`'s owner segment back to the `owner.login`/`organization.login` value that determined which secret authenticated the request. On a Shipit instance configured for multiple GitHub organizations (an explicitly documented and supported setup, each org having its own `webhook_secret`) [6](#0-5) [7](#0-6) , this breaks the binding: **the organization whose secret authenticated the request ≠ the repository the handler writes to**.

Concretely: `PushHandler#process` finds every non-archived stack for the repository named in `full_name` matching the pushed branch and calls `stack.sync_github(expected_head_sha: params.after)` on it [3](#0-2) , and `StatusHandler#process` looks up *any* `Commit` by `sha` across the install and calls `commit.create_status_from_github!(params)`, injecting an attacker-chosen `state`/`context`/`description` [2](#0-1) . Both operate on state keyed to `full_name`/`sha`, not to the authenticated `repository_owner`.

### Impact Explanation
An attacker who administers their own GitHub organization/App installation on a shared multi-org Shipit instance (and therefore legitimately knows their own org's `webhook_secret`) can forge signed webhooks whose `owner.login` is their own org but whose `repository.full_name` targets a victim org's repository. This lets them:
- Inject arbitrary forged commit statuses (`StatusHandler`) onto a victim repository's commits, which the deploy-safety pipeline (`Commit#create_status_from_github!`) consults to decide whether a commit is deployable — a forged "success" status can make an otherwise-blocked commit `deployable?`, enabling an unauthorized deploy on a repository the attacker doesn't own.
- Trigger `GithubSyncJob`/`sync_github` for a victim stack via a forged `push` event, causing Shipit to sync from a git ref of the attacker's choosing content-wise (subject to what `sync_github` fetches), affecting a repository the attacker has no legitimate write access to.

This crosses the "unauthorized deploy" bar because it lets an org-scoped attacker manipulate deploy-gating state for a repository outside their authorization scope, using credentials that are only valid for their own organization.

### Likelihood Explanation
Requires the target Shipit instance to be configured with the documented multi-organization `github:` block (multiple orgs' webhook secrets configured on one instance) and the attacker to control (or have compromised) one of those organizations/App installations. This is a realistic, supported deployment topology (see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), but it does require the attacker to be a legitimate webhook sender for *some* org on the shared instance, which is a real but non-trivial precondition — hence Low/Medium likelihood, High impact.

### Recommendation
Bind the field used to select the verification secret to the same field used to resolve the affected resource. Concretely, derive `repository_owner` from `repository.full_name`'s owner segment (the same field `Handler#repository_name` uses) rather than from the separate `owner.login`/`organization.login` fields, or alternatively have handlers re-verify that the resolved `Repository#owner` matches the organization whose secret validated the signature before mutating any state.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org example).
2. Attacker, who administers the GitHub App installed on `attacker-org`, crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` (known to them).
4. `WebhooksController#verify_signature` calls `repository_owner` → `"attacker-org"` → `Shipit.github(organization: "attacker-org")` → verification succeeds because the signature was computed with that org's real secret [4](#0-3) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — which resolves to the victim commit belonging to `victim-org/victim-repo` — and creates a forged status on it [2](#0-1) , despite the attacker having no authorization over `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
