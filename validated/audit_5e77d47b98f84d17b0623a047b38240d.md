### Title
Rounding cascade in liquidation lets liquidator seize a stranger's full remaining collateral for zero repayment, pushing losses onto socialized suppliers - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The `liquidate` function's dust-avoidance branch computes `remaining-debt-to-repay` through a chain of down-rounding divisions and, if that chain rounds to zero, awards the liquidator the borrower's *entire* remaining collateral balance for that asset (`user-coll-balance` instead of the proportional `coll-final-raw`) with no additional debt repaid. This mirrors the Plaza Auction rounding bug: a caller-controlled, integer-division-heavy calculation degrades the effective "price" (debt repaid per collateral seized) below what governance parameters intend, and the shortfall is absorbed by a third party — here, all suppliers via `socialize-debt-asset`/`vault-socialize-debt` — rather than the liquidator.

### Finding Description
In `liquidate`, `coll-remaining` is the leftover collateral after the proportional seizure `coll-final-raw` computed by `scale-debt-for-liquidation`: [1](#0-0) 

The liquidator fully controls `debt-amount` (capped only by `max-debt-usd`), which flows through `process-debt-asset` → `calc-final-liquidation-amounts` → `scale-debt-for-liquidation`, all of which round down (`mul-div-down`) at multiple points: [2](#0-1) 

By choosing `debt-amount` so that `coll-remaining` is small, the "remaining debt" re-derivation performs four chained divisions (`div-bps-down`, then two `mul-div-down`s, then `mul-div-up`) that can round the scaled remaining debt down to `u0`: [3](#0-2) 

When `remaining-debt-to-repay` evaluates to `u0`, the code sets `coll-final` to the *entire* `user-coll-balance` for that asset rather than the smaller `coll-final-raw`, i.e., the liquidator receives collateral for which no corresponding debt token was ever repaid to the vault. If that asset was the borrower's only/last collateral, this triggers `no-collateral-left`, and the position's remaining debt is written off via `socialize-debt-asset`, which calls `vault-socialize-debt` to spread the unrecovered debt across all vault suppliers: [4](#0-3) [5](#0-4) 

The attacker (liquidator, an unprivileged caller) and the victims (borrower whose collateral is under-repaid, and the vault's supplier pool who absorb the socialized bad debt) are distinct principals connected only through the shared position/vault state — exactly the "socialization charged to all suppliers" pattern called out as in-scope.

### Impact Explanation
Each exploitation of the rounding gap lets the liquidator extract collateral without paying its debt-token equivalent. While a single occurrence may be dust-sized, the liquidator chooses `debt-amount` and can repeat the pattern across many positions/liquidations (the batch entrypoint `liquidate-multi` even facilitates iterating this over many borrowers in one transaction), and when it triggers `no-collateral-left`, the shortfall becomes permanent bad debt socialized onto all suppliers of the debt vault — a protocol-wide, uncompensated loss rather than a loss borne by the liquidator. This lands on the in-scope impact class of protocol insolvency / temporary-to-permanent freezing/loss of supplier funds (socialized bad debt with no offsetting repayment).

### Likelihood Explanation
Likelihood is constrained: the attacker needs precise control of `debt-amount`, oracle prices, and decimals such that the four-stage rounding chain collapses to zero while `coll-remaining` (and thus the "free" collateral) is still economically meaningful, and the position must satisfy `no-collateral-left` to reach the socialization path. This requires careful crafting per position (similar to the original Plaza PoC, which required exact bid sizing), making it a real but non-trivial, precondition-dependent path rather than a trivially repeatable griefing vector.

### Recommendation
Do not let the "no-collateral-left" free-seizure branch bypass debt accounting: if `remaining-debt-to-repay` rounds to zero, either (a) leave the true `coll-final-raw` un-seized dust (accept it stays with the position) instead of granting the liquidator the full `user-coll-balance`, or (b) require the socialized debt amount to be capped/adjusted by the value of collateral actually seized so suppliers are never asked to absorb more debt than the (rounded) collateral shortfall justifies. Additionally, consider asserting that total collateral value seized (in USD) never exceeds total debt value repaid plus intended `liq-penalty`, mirroring the "no post-hoc price improvement" check recommended in the original report (verify no favorable delta before/after the rounding adjustment).

### Proof of Concept
Conceptual PoC (Clarity liquidation call sequence), unverifiable without a live/simnet run of `v0-4-market.clar`:
1. Borrower has a position with a single collateral asset near the liquidation threshold, with `user-coll-balance` such that a chosen `debt-amount` yields `coll-final-raw` slightly less than `user-coll-balance`.
2. Liquidator calls `liquidate` with a `debt-amount` engineered (via known oracle price/decimals) so that `coll-remaining`'s USD value, after `div-bps-down` and two `mul-div-down` steps, produces `rem-scaled = u0`.
3. `remaining-debt-to-repay` evaluates to `u0`, so `coll-final` is set to full `user-coll-balance` instead of `coll-final-raw` — liquidator receives extra collateral for zero extra debt repaid.
4. Since this was the borrower's only collateral, `no-collateral-left` is true; `socialize-debt-asset`/`vault-socialize-debt` write off the borrower's remaining debt, which is absorbed by all suppliers of the debt vault.
5. Repeating step 2–4 across multiple qualifying positions (optionally via `liquidate-multi`) compounds the socialized loss to suppliers while the liquidator's collateral gain is always "free."

This PoC could not be executed against contract state in this session; exact numeric parameters (prices, decimals, `INDEX-PRECISION`, `liq-penalty-max`) would need to be confirmed in a Clarinet/simnet environment to demonstrate the rounding chain reaching exactly zero.

;; Scale debt for storage and calculate final execution amounts
;; Converts to scaled units, caps at current debt, calculates final collateral
;; Returns: { scaled-to-remove: uint, debt-to-repay: uint, coll-final: uint }
(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))
