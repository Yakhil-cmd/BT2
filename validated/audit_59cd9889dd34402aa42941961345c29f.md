### Title
Autonomous Agent payments in uncapped assets silently mint new supply instead of failing when the AA's tracked/expected balance is insufficient, hiding accounting shortfalls (bad debt) through unbounded token inflation - (File: `aa_composer.js`)

### Summary
When an Autonomous Agent (AA) tries to pay out more of a custom asset than it currently holds in on-chain UTXOs, `aa_composer.js` does not bounce the response. Instead, for any asset that is not `issued_by_definer_only`-restricted against the AA (or where the AA itself is the definer) and has no fixed `cap`, the engine automatically fabricates a new `issue` input to cover the shortfall. This mirrors the Perennial "bad debt" bug class: rather than reverting the operation or forcing an explicit, accounted-for socialization of the shortfall, the protocol silently manufactures new value to paper over the gap, diluting every other holder of that asset with no bound and no visible failure.

### Finding Description
In `completePaymentPayload` (invoked from `sendUnit`, the code path that actually composes and persists an AA response unit), the AA first tries to satisfy a payment from its own stable and unstable UTXOs via `readStableOutputs`/`readUnstableOutputsSentByAAs`. [1](#0-0) 

If those outputs are insufficient and the asset is a named asset (not base bytes), the code unconditionally calls `issueAsset()` rather than bouncing: [2](#0-1) 

`issueAsset()` mints exactly the missing amount (`target_amount - total_amount`) as a fresh `issue` input, as long as the asset is not restricted to `issued_by_definer_only` for a non-definer AA: [3](#0-2) 

For capped assets, this is safe because a single, one-time issuance up to `cap` is enforced (`"already issued"` check). But for any *uncapped* asset the AA is allowed to issue, this fallback runs every single time the AA's actual reserve of that asset falls short of what an output requires — regardless of *why* the shortfall exists. Any AA-level accounting defect (e.g., a lending/exchange/bank-style AA, such as the pattern seen in `test/samples/a_bank_without_percent.oscript` and `test/samples/order_book_exchange.oscript`, that tracks per-user claims in `var['balance_...']` state variables) that lets internal ledger claims exceed the AA's real asset reserve will not be caught by `aa_composer.js`: the engine does not compare `var[]`-tracked liabilities to real UTXO holdings — it only checks whether it can literally construct the requested output, and if not, it prints new supply to make the numbers work.

This is analogous to the reported Perennial issue: instead of a negative/undercollateralized balance being reverted or explicitly socialized, the shortfall is quietly absorbed — here by inflating total token supply rather than by leaving a dangling negative balance — with no on-chain signal distinguishing a "real" payment from a "mint-to-cover-shortfall" payment.

### Impact Explanation
This directly enables uncontrolled supply inflation of any custom asset an AA is permitted to issue (`issued_by_definer_only: false`, or the AA itself as `definer_address`, and no `cap`). Any bug or edge case in an AA's own internal solvency accounting (interest/liquidation/fee rounding, race between concurrent secondary triggers consuming the same UTXOs, etc.) that causes the AA to attempt to pay out more of such an asset than it holds will not revert — it will succeed by minting new units. Every existing holder of that asset is diluted, silently, with no explicit event flagging that value was manufactured rather than transferred from real reserves. This falls squarely into the "supply inflation" and "AA fund loss" impact categories: honest holders of the asset lose real value while the party who triggered the underpaid AA (or who exploited an accounting edge-case) receives full payment as if the AA were solvent.

### Likelihood Explanation
This requires only a single posted unit that triggers an AA holding/managing an uncapped, definer-issuable custom asset, in a state where the AA is (through any combination of legitimate business logic and an accounting edge case) asked to pay out more of that asset than its UTXOs currently contain. Because AA developers commonly build banking/exchange/lending-style AAs using `var[]` state to track claims separately from actual on-chain balances (as shown in the shipped sample scripts), and because `aa_composer.js` never cross-checks such internal ledgers against real reserves before falling back to `issueAsset()`, any latent bookkeeping bug — not merely a full protocol compromise — is sufficient to trigger unbounded, invisible inflation instead of a safe bounce.

### Recommendation
For assets an AA is capable of issuing on demand (uncapped, definer-controlled), `aa_composer.js` should not treat "insufficient real balance" and "insufficient issuable supply" as interchangeable success paths. At minimum:
- Do not silently fall back to `issueAsset()` inside `completePaymentPayload` for ordinary payment shortfalls; require the AA definition/oscript logic to explicitly request an `asset` issuance message when it intends to mint, rather than having the engine auto-mint as a generic "not enough funds" recovery mechanism.
- If auto-issuance-on-shortfall must remain for backward compatibility (see the `bSelfIssueForSendAll` / `aa3UpgradeMci` guarded behavior), expose or log the fact that a payment was fulfilled via issuance rather than from existing reserves, so downstream monitoring/oscript logic (e.g., `balance[asset]` checks) can distinguish real solvency from inflated solvency.
- Encourage/require AA authors of custodial-style contracts to reconcile `var[]`-tracked liabilities against `balance[asset]` before allowing withdrawals, since `balance[asset]` reads reflect current on-chain UTXO totals and can be checked prior to composing a payment message.

### Proof of Concept
1. An AA `X` defines a custom asset `A` with `cap: null`/absent and `issued_by_definer_only: false`, using `var['balance_' || address]` to track user deposits/credits of asset `A` (as in `test/samples/a_bank_without_percent.oscript`, `order_book_exchange.oscript`).
2. Due to an oscript-level accounting edge case (e.g., two AA triggers processed in the same primary-trigger response chain that both read a stale `var['balance_...']` before either write is applied, or an interest/fee rounding bug), the AA is induced to emit a `payment` message paying out more of asset `A` to some address than `X`'s current UTXOs of `A` actually hold.
3. In `completePaymentPayload`, `readStableOutputs`/`readUnstableOutputsSentByAAs` fail to cover `target_amount`; per [2](#0-1)  the code calls `issueAsset()`.
4. `issueAsset()` (`aa_composer.js:1175-1211`) mints `target_amount - total_amount` new units of `A` as an `issue` input rather than bouncing, since `A.cap` is falsy and `A.issued_by_definer_only` is false.
5. The response unit is produced and accepted as valid — total supply of `A` has silently increased by the shortfall amount, diluting all other holders, with no bounce/error signal indicating the AA was actually insolvent for that payment.
