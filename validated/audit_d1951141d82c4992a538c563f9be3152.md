### Title
Unauthorized read of stack merge/build status bypassing `Shipit.github_teams` authorization - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController` explicitly skips the engine-wide authentication/authorization filter for its `show` action and only re-checks that the user is logged in — not that the user belongs to an authorized `Shipit.github_teams` team. This lets any GitHub account holder who completes OAuth login (but who is not a member of an authorized team) read the merge/deploy status of any stack, something every other controller in the engine prevents via `force_github_authentication`.

### Finding Description
Every controller in this engine that includes `Shipit::Authentication` runs `force_github_authentication` before each action [1](#0-0) . That filter enforces two independent conditions: the user must be logged in, and the user must be `authorized?` (a member of one of `Shipit.github_teams`) — otherwise a 403 is rendered [2](#0-1) .

`MergeStatusController` opts out of this filter for its externally reachable `show` action:

```ruby
class MergeStatusController < ShipitController
  skip_authentication only: %i[check show]
``` [3](#0-2) 

Inside `show`, the only remaining gate is a check for `current_user.logged_in?`; there is no corresponding check for `current_user.authorized?` (team membership):

```ruby
def show
  ...
  if stack
    return render('logged_out') unless current_user.logged_in?
    if stale?(...)
      render(stack_status, layout: !request.xhr?)
    end
  else
    render(html: '')
  end
``` [4](#0-3) 

The stack being rendered can be selected directly by an attacker-controlled `stack_id` parameter, bypassing any repo/branch inference from the referrer:

```ruby
def stack
  @stack ||= if params[:stack_id]
               Stack.from_param!(params[:stack_id])
             else
               ...
``` [5](#0-4) 

This action is routed publicly at `GET /merge_status`: [6](#0-5) 

The binding that is supposed to hold everywhere else in the engine is: **GitHub identity that completes OAuth == a `User` authorized via `Shipit.github_teams` to view stack state**. Here that binding is broken: an unprivileged GitHub identity (logged in, but not on an authorized team) is treated as sufficiently authorized to read `stack.merge_status` (locked/failure/backlogged/success) and the merge-status HTML/partial for any stack, exactly analogous to how the reported bug allows an unprivileged NFT-account holder to be treated as the authorized position owner when one specific instruction omits the ownership check that its sibling instructions enforce.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization — an explicitly listed High-impact category — allowing an authenticated-but-unauthorized GitHub user to read stack state (lock status, branch/build health, merge queue status) for arbitrary stacks, including private/internal deployment pipelines, without being a member of any team permitted to access the Shipit instance.

### Likelihood Explanation
The only prerequisite is completing a normal GitHub OAuth login against the app (any GitHub account can do this — the OAuth flow itself does not filter by team membership; that filtering happens only in `force_github_authentication`, which this controller bypasses). No repository write access, no ApiClient token, and no privileged Shipit account is required, satisfying the "unprivileged attacker" bar. The `stack_id` is a predictable/enumerable `owner/repo/environment` path segment, making arbitrary-stack targeting straightforward.

### Recommendation
Do not fully skip `force_github_authentication` for `MergeStatusController#show`/`#check`. Instead, add back an explicit `current_user.authorized?` check (equivalent to the team-membership check performed by `force_github_authentication`) before rendering `stack_status`, so that only users who are members of `Shipit.github_teams` can view stack merge/build status.

### Proof of Concept
1. As an attacker, complete the standard `/github/auth/github` OAuth flow with any GitHub account (do not need membership in any `Shipit.github_teams` team) to obtain `session[:user_id]`.
2. Send `GET /merge_status?stack_id=<victim_owner>/<victim_repo>/<environment>` (or with a `referrer` pointing at a target PR).
3. Observe that `MergeStatusController#show` renders the target stack's merge status (e.g. "locked", "backlogged", "Ready to ship!") even though `force_github_authentication`'s team-authorization check — enforced on every other route in the engine — was never evaluated, because `skip_authentication only: %i[check show]` removed it and `show` only checks `current_user.logged_in?`.

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
