### Title
Cross-repository forged `Status` accepted for any commit's SHA regardless of authorizing repository, enabling unauthorized merge-queue merges - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming `status` webhook to every `Commit` row matching `params.sha` across the entire Shipit installation, with no check that the webhook's authorizing repository (used in `verify_signature`) matches the repository/stack that owns the matched commit. An attacker who owns any Shipit-registered repository can obtain a legitimately-signed webhook for a commit whose SHA happens to equal a victim's PR head SHA (git SHAs are portable, content-addressed objects that can be pushed into any repo the attacker controls), and that forged `success` status is written against the victim's stack, satisfying `MergeRequest#all_status_checks_passed?` and triggering an unauthorized merge.

### Finding Description
The broken binding, stated as an explicit equality that the code should enforce but does not:

`request.payload.repository.owner.login` (verified in `WebhooksController#verify_signature` via `Shipit.github(organization: repository_owner)`, [1](#0-0) , [2](#0-1) ) **should equal** `matched_commit.stack.repository.full_name` (the repository of the stack that owns the commit whose status is being mutated).

Tracing the code shows this equality is never checked:

1. `WebhooksController#verify_signature` only proves that the request was HMAC-signed by *some* organization named in the payload's own `repository.owner.login` field — it authenticates *who sent this webhook*, not *which stack/commit the payload is permitted to affect*. [3](#0-2) 
2. `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is global — it is not scoped by `stack_id`, by `repository`, or by anything derived from the verified `repository_owner`. [4](#0-3) 
3. `Commit#create_status_from_github!` writes the new `Status` using the commit's *own* `stack_id`, not anything from the webhook payload: `statuses.replicate_from_github!(stack_id, github_status)`. [5](#0-4) [6](#0-5) 
4. `Commit#add_status` (invoked via `create_status_from_github!`) calls `stack.schedule_merges if new_status.pending? || new_status.success?`, enqueuing `ProcessMergeRequestsJob` for the **victim's** stack. [7](#0-6) 
5. `ProcessMergeRequestsJob#perform` calls `merge_request.all_status_checks_passed?`, which reads `head.statuses_and_check_runs` — this includes the forged `Status` row because it is attached to the victim commit via `stack_id`/`commit_id`, with no re-validation of which repository the status "really" came from. [8](#0-7) [9](#0-8) 
6. If checks pass, `merge_request.merge!` calls the GitHub merge API for the victim's PR. [10](#0-9) 

Exploit flow: the attacker fetches the victim's public PR head commit (a portable, content-addressed git object) and pushes that exact commit object into a repository they own and that is already onboarded into Shipit. The attacker then sets a commit status (`success`) on that SHA using GitHub's real API against their own repo. GitHub emits a genuinely HMAC-signed `status` webhook naming the *attacker's* repository/organization. `verify_signature` passes because the signature is valid for that (attacker's) organization's configured `webhook_secret`. `StatusHandler#process` then matches the victim's `Commit` row purely by SHA and writes a `Status` under the victim's stack, satisfying `all_status_checks_passed?` for the victim's queued `MergeRequest`.

Existing guards fail to prevent this because:
- `verify_signature` validates *sender authenticity for an organization*, but the code never checks that this organization corresponds to the stack/commit the payload claims to update.
- `ExplicitParameters` schema on `StatusHandler` only validates types/shape of `sha`, `state`, etc.; it does not include or validate `repository`. [11](#0-10) 
- `drop_unhandled_event`, `force_github_authentication`, `User#authorized?`, and `require_permission!` are irrelevant here since this is an unauthenticated webhook endpoint by design; the missing control is repository/stack scoping inside the handler itself.

### Impact Explanation
A payload authenticated for one repository (the attacker's) is used to mutate the state of an unrelated stack/commit (the victim's), directly matching the rules' Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." Concretely, the attacker can force a `success` `Status` onto any commit in any Shipit-tracked stack for which they can learn/reconstruct the SHA, causing `ProcessMergeRequestsJob` to merge a pending `MergeRequest` that was otherwise blocked purely on CI. This is repeatable against arbitrary stacks/repositories hosted by the same Shipit instance, as long as the attacker can push an identical commit object into some repo they control and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the target stack has `merge_queue_enabled` with an eligible pending `MergeRequest` blocked only on CI (`any_status_checks_failed?`/`any_status_checks_missing?` false), and the attacker needs at least one repository of their own already onboarded into Shipit (a normal, low-privilege prerequisite — any GitHub user able to install/enable the Shipit-connected GitHub App on a repo they own, or an existing low-trust repo already onboarded). No Shipit session, API token, or secrets are required. The main technical requirement — pushing an identical commit object (same tree/parents/author/committer/timestamps/message) into another repository to reuse the SHA — is standard git behavior (commits are content-addressed and portable across remotes), making this feasible without breaking SHA-1 preimage resistance. This is repeatable for any stack/commit whose SHA the attacker can reproduce this way.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to only commits that belong to the stack/repository actually authorized by the verified webhook (e.g., resolve `stack` via `params.dig('repository','full_name')` matched against `Stack#repository`, and restrict `Commit.where(sha: params.sha, stack: authorized_stacks)`), so a status can only be written for commits belonging to the repository whose signature was verified.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "a status payload authorized for repo A must not affect a commit belonging to repo B's stack" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  attacker_stack = shipit_stacks(:other_repo) # repository "attacker/unrelated-repo"

  victim_commit = shipit_commits(:cyclimse_first) # belongs_to victim_stack
  merge_request = shipit_merge_requests(:shipit_mergeable_pending_ci)
  merge_request.update!(head: victim_commit)

  assert_equal victim_stack.id, victim_commit.stack_id
  assert_not_equal victim_stack.repo_name, attacker_stack.repo_name # BEFORE: distinct repos

  # Forged params: sha matches victim commit, but payload asserts attacker's repository
  params = ExplicitParameters::Params.new(
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/forged',
    created_at: Time.now.iso8601
  )

  refute_predicate merge_request, :all_status_checks_passed?

  Shipit::Webhooks::Handlers::StatusHandler.new(params).process

  victim_commit.reload
  # AFTER: the status was written onto the victim's stack despite being authorized only for attacker_stack's repo
  assert_equal victim_stack.id, victim_commit.statuses.last.stack_id
  assert_predicate merge_request.reload, :all_status_checks_passed?

  assert_enqueued_with(job: Shipit::ProcessMergeRequestsJob, args: [victim_stack])
end
```
This demonstrates that a `Status` scoped only by SHA — with no equality check between the authorizing repository and `victim_stack`'s repository — is written to the victim's stack and flips `all_status_checks_passed?` to `true`, scheduling the merge job for the victim's `MergeRequest`.

      end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
