### Title
Cross-repository status webhook triggers unauthorized deploy on victim stack via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table, with no filter on the repository that authenticated the webhook. An attacker who controls a repository whose fork shares a commit SHA with a victim's stack (e.g., via a shared ancestor commit from a fork) can send a validly-signed status webhook for their own repository, and Shipit will attach that status to the victim's `Commit` record, potentially flipping `Commit#deployable?` to true and triggering an unauthorized deploy on the victim's stack.

### Finding Description
The broken binding is: `repository authenticated by webhook_secret (payload['repository']['full_name'] == attacker/repo)` should equal `commit.stack.repository.full_name` for every `Commit` mutated by the webhook — but it does not.

`WebhooksController#verify_signature` only proves that the request signature matches `Shipit.github(organization: repository_owner)`, i.e., that the payload's own `repository.owner.login` is legitimate [2](#0-1) . It does not prove the SHA in the payload belongs to that repository's stacks.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, unscoped lookup by `sha` across **all** stacks/repositories in the Shipit database [1](#0-0) . The base `Handler` class provides a `stacks` method scoped to `Repository.from_github_repo_name(repository_name)` [3](#0-2) , but `StatusHandler` does not use it — it never checks that the matched `Commit#stack` belongs to the repository named in the authenticated payload.

Because commit SHAs are content-addressed and forks/shared history frequently produce identical SHAs across repositories, an attacker owning any repository (fork or otherwise) can push/reference a commit whose SHA also exists as a `Commit` row tied to the victim's stack, then emit a `status` event for their own repo with that SHA and a passing state. Since the webhook signature only authenticates the attacker's own org/repo, this passes `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema in `StatusHandler.params` (which only requires `sha`/`state`, not repository consistency) [4](#0-3) .

`Commit#create_status_from_github!` then creates a `Status` row scoped to `commit.stack_id` (the victim's stack, taken from the matched `Commit`, not from the payload) [5](#0-4) . `Status#schedule_continuous_delivery` calls `commit.schedule_continuous_delivery` on `after_commit` [6](#0-5) , and `Commit#schedule_continuous_delivery` checks `deployable? && stack.continuous_deployment? && stack.deployable?` before enqueuing `ContinuousDeliveryJob` [7](#0-6) . `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, driven purely by the newly-injected `Status` [8](#0-7) . `Stack#trigger_continuous_delivery` then calls `trigger_deploy(commit, Shipit.user, env: ...)` on the victim's stack with no re-check that the status came from the victim's own repository [9](#0-8) .

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` params schema, model validations) check cross-repository binding for `sha`-keyed lookups in `StatusHandler`. This is a genuine authentication/authorization-scope confusion: the entity that is cryptographically authenticated (attacker's repo) is not the entity whose state is mutated (victim's stack).

### Impact Explanation
An attacker can cause an unauthorized deploy to run on a victim's production stack (`Stack#trigger_deploy`) using a status the attacker fabricated on their own repository, for a commit the victim's own CI never validated. This is a record written (a `Status` and subsequently a `Deploy`) for a repository/stack that never authenticated the request — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy" category. The blast radius spans any victim stack with `continuous_deployment: true`, unlocked, and a `Commit` row whose `sha` collides with one accessible/creatable by the attacker (e.g., shared git history via fork, cherry-pick, or rebase preserving SHA).

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, is unlocked, has `cached_deploy_spec` present, and has a `Commit` record (already pushed/synced into Shipit) that currently lacks a passing status only. The attacker needs a repository they control (any GitHub repo, including a fork) whose commit history includes/shares that same SHA, and the ability to send a `status` event for their own repo (achievable by pushing a commit and letting any CI/status-posting integration on their own repo fire, or by directly crafting the webhook payload if they can get GitHub to sign it via their own repo's real event — i.e., no Shipit secret needed). This is feasible and repeatable against any Shipit-managed repository whose commit history intersects with a repository the attacker controls.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks associated with the authenticated `repository.full_name` from the payload — e.g., filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` using the existing `stacks` helper on `Handler`, mirroring the pattern likely used by other handlers, so a status can only be attached to commits under the repository that produced the signed webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from attacker repo cannot deploy victim's commit with colliding SHA" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, cached_deploy_spec present, unlocked
  colliding_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim commit")

  attacker_payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/other-repo', 'owner' => { 'login' => 'attacker' } }
  }

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end

  victim_commit.reload
  assert_not victim_commit.success?, "attacker-authenticated webhook must not create a status on victim's commit"
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `attacker_payload['repository']`, a `Status` is created against `victim_stack`, `ContinuousDeliveryJob` is enqueued, and `Deploy.count` increases — demonstrating the broken binding (`attacker/other-repo` authenticated ≠ `victim_stack`'s repository mutated). After the fix, the handler must scope the lookup by `stacks` derived from `attacker_payload['repository']['full_name']`, so `victim_commit` is never matched and no job/deploy occurs.
