### Title
Cross-organization commit-status forgery via unscoped `sha` lookup in `StatusHandler` bypasses the organization binding used for webhook-signature verification, enabling unauthorized deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an incoming webhook against using `repository_owner`, a field taken directly from the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`). Once the HMAC check passes for that org's secret, the entire payload is treated as trusted and dispatched to handlers. However, `Shipit::Webhooks::Handlers::StatusHandler` never re-validates that the `repository` referenced in the payload — or its owner — actually matches the commit being modified: it looks up commits **globally** by `sha` alone (`Commit.where(sha: params.sha)`), with no `repository`/`stack` scoping in its own `params` block or `process` method. This breaks the intended binding "organization that authenticated == repository that is written": a request that authenticates as Org B can write CI status data belonging to a commit that lives in an entirely different Org A repository/stack, as long as it guesses/knows that commit's `sha` (identical shas exist for cherry-picked/merged commits, and shas are visible from GitHub PR pages, CI logs, etc., which are typically public or knowable to a legitimate but unprivileged multi-tenant customer).

### Finding Description
- `app/controllers/shipit/webhooks_controller.rb` picks the `github_app`/secret via `repository_owner`, which is read straight out of `params.dig('repository','owner','login')` or `params.dig('organization','login')` (lines 24-30, 59-62). In a multi-tenant Shipit install (as shown by `test/dummy/config/secrets_double_github_app.yml`, which configures a distinct `app_id`/`installation_id`/`webhook_secret` per organization, i.e. `OrgOne`, `OrgTwo`), each onboarded organization's administrators legitimately possess/control their own `webhook_secret` (they created that org's GitHub App and gave Shipit its secret). This is the trust boundary: "authenticate as organization X" should only authorize actions on org X's data.
- `verify_signature` HMACs the *whole* raw payload, so technically `repository.owner.login` is covered by the signature; but that only proves "this request came from whoever owns the secret matching the claimed owner field", not that the content of the payload is restricted to that organization's own repositories.
- `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (used by most handlers, e.g. `PushHandler`, all `PullRequest::*Handler`s) scope operations to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. That still does not prevent an authenticated Org B request from naming Org A's `repository.full_name` (no cross-check exists that the authenticating org and the named repository owner match), but the impact is bounded because those handlers only trigger read-driven syncs or PR bookkeeping.
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`, lines 6-25) is the critical case: its `params` block does not even declare/require a `repository` field, and `process` resolves target commits purely via `Commit.where(sha: params.sha)` — with **no repository/org check at all**. Any commit in the entire Shipit datastore sharing that sha is updated via `commit.create_status_from_github!(params)` → `Status.replicate_from_github!`.
- `Commit#add_status` (`app/models/shipit/commit.rb` lines 366-386) reacts to the new status: if it transitions to `success`, it calls `stack.schedule_merges` and, via `Status#schedule_continuous_delivery`/`Commit#deployable?` (`app/models/shipit/commit.rb` line 227-229), can make the commit `deployable?`. If the targeted stack has `continuous_deployment` enabled, `ContinuousDeliveryJob` (`app/jobs/shipit/continuous_delivery_job.rb`) will pick the commit up via `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb` lines 210-229) and start a real deploy (`stack.trigger_deploy`).

**Binding broken:** `organization authenticated (via webhook_secret matched against payload's repository_owner)` ≠ `repository/stack actually written (commit resolved solely by sha, cross-tenant)`.

### Impact Explanation
This is a Critical-tier issue per the impact taxonomy: it can result in an **unauthorized deploy**. An attacker who is a legitimate but unprivileged tenant of a shared/multi-org Shipit instance (they administer their own GitHub App/org — not privileged relative to other tenants' stacks) can:
1. Learn/guess the `sha` of a commit belonging to another organization's stack that has `continuous_deployment` enabled (shas are often exposed publicly via PRs, CI badges, status pages, etc., and are not secrets).
2. Send a signed webhook `status` event to Shipit's shared `WebhooksController`, using their own org's valid `webhook_secret` and their own org's `repository.owner.login` to pass `verify_signature`, but with `sha` set to the victim commit and `state: success`.
3. Because `StatusHandler` does zero repository/org validation, this creates a fabricated `success` Status on the victim's commit, potentially flipping `deployable?` to true and triggering `ContinuousDeliveryJob`, causing Shipit to run a real deploy task on infrastructure the attacker has no access rights to — an unauthorized deploy that also unblocks `stack.schedule_merges` (`ProcessMergeRequestsJob`), affecting merge automation for a repository outside the attacker's authorization scope.

### Likelihood Explanation
Likelihood is High in any deployment where Shipit is configured with more than one GitHub App/organization (a documented, supported configuration per `test/dummy/config/secrets_double_github_app.yml`). No repository write access, GitHub App private key, or victim's `ApiClient` token is required — only knowledge of a target commit sha and possession of a webhook secret for any one of the configured orgs, which is a normal, unprivileged credential each tenant already legitimately holds for their own org.

### Recommendation
- In `StatusHandler` (and any other handler that mutates state), require and validate the `repository` field, resolve the target `Repository`/`Stack` from `payload.dig('repository','full_name')`, and scope the `Commit` lookup to that stack (`stack.commits.where(sha: params.sha)`) instead of a global `Commit.where(sha: ...)`.
- In `WebhooksController#verify_signature`, after selecting the `github_app` by `repository_owner`, additionally assert that the resolved repository's owner (used later by the handler) matches the same `repository_owner`/organization whose secret validated the signature, rejecting the payload otherwise.
- Apply the same repository/org cross-check uniformly to all webhook handlers that resolve targets by fields not covered by an explicit repository-ownership check (e.g., verify `Repository.from_github_repo_name(...).owner == repository_owner` before processing).

### Proof of Concept
Conceptual reproduction (multi-tenant Shipit instance with two configured orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret`):
1. Org A (victim) has a stack `OrgA/app` with `continuous_deployment: true` and a pending commit `abc123` awaiting a passing CI status.
2. Attacker, who legitimately administers `OrgTwo`'s GitHub App and therefore knows `OrgTwo`'s `webhook_secret`, crafts:
```json
{
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/unrelated-repo" },
  "sha": "abc123",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_OrgTwo, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")` and successfully verifies the signature (it is valid for `OrgTwo`).
5. `Shipit::Webhooks.for_event("status")` dispatches to `StatusHandler`, which runs `Commit.where(sha: "abc123")` — finding Org A's commit despite the payload nominally being about `OrgTwo/unrelated-repo` — and calls `create_status_from_github!`, creating a `success` Status on Org A's commit.
6. If `OrgA/app` has `continuous_deployment: true`, `Commit#add_status` triggers `stack.schedule_merges` and enables `ContinuousDeliveryJob`, which can execute an unauthorized deploy on Org A's stack.

*(Note: I was not able to fully verify in the index whether every deployment scenario satisfies all preconditions in `trigger_continuous_delivery`/`should_delay_continuous_delivery?`/`next_commit_to_deploy` gating logic for every stack configuration — a Devin session with full repository access would be needed to trace every guard clause end-to-end and build a runnable integration test.)*
