### Title
Missing zero-initialization of `PoolState.status` combined with a non-canonical, signer-controlled `pool_state` account allows permanent freezing of LP funds - (File: `programs/cp-swap/src/states/pool.rs`, `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
The CVE-2017-7593 bug class is "a buffer/structure field is not explicitly zero-initialized before use, letting stale memory content leak into program state." The direct analog in this program is `PoolState::initialize()`, which populates every field of the `PoolState` zero-copy struct except `status`, combined with a `create_pool()` code path that allows the `pool_state` account to be an attacker-supplied, non-PDA, signer-controlled account rather than the canonical PDA. This lets a pool creator plant a non-zero `status` byte before calling `initialize`, permanently disabling `deposit`/`withdraw` on the pool for every future LP, with no user-facing recovery path (status changes are admin-only).

### Finding Description
`PoolState` stores a `status` byte that gates deposit/withdraw/swap via bitmask checks: [1](#0-0) 

`PoolState::initialize()` explicitly zeroes every other mutable field (`protocol_fees_token_0/1`, `fund_fees_token_0/1`, `padding1`, `creator_fees_token_0/1`, `padding`) but never assigns `self.status`: [2](#0-1) 

Normally this is harmless because the account backing `pool_state` is freshly created and zero-filled by the runtime. However, `create_pool()` does not require `pool_state` to be the canonical PDA — if the supplied address doesn't match the derived PDA, it only requires the account to be a transaction signer: [3](#0-2) 

Because a signer-supplied account can be any system-owned keypair the creator fully controls (they can temporarily assign it to a helper program of their own to write arbitrary bytes, then reassign it back to the System Program before calling `initialize`), the creator can plant a non-zero value at the `status` byte offset. The custom zero-copy loader used here only checks that the 8-byte discriminator is zero before treating the rest of the buffer as the struct — it performs no full-buffer zero check: [4](#0-3) 

Since `initialize()` never overwrites `status`, the attacker-chosen byte survives pool creation. `status` bits are read via `get_status_by_bit` and are relied on by `deposit`, `withdraw`, and both swap instructions to gate those operations, and can afterward only be changed through the admin-only `update_pool_status` instruction (under `instructions/admin/`), not by the pool creator or any LP: [5](#0-4) 

### Impact Explanation
A malicious pool creator can pre-poison the `status` byte (e.g., set the withdraw-disabled bit, bit index 1) at pool creation. Any LP who subsequently deposits into that pool has their liquidity permanently locked: `withdraw` will refuse to execute because the status bit is set, and only the protocol admin (not the creator or LPs) can flip pool status via `update_pool_status`. This is a permanent freezing of LP funds for an attacker-controlled pool that later victims interact with, satisfying the Medium/High bar (unauthorized privileged effect — a non-admin achieving admin-only pool-status control — leading to fund freezing).

### Likelihood Explanation
Reachable entirely from a single transaction sent by an unprivileged pool creator: they supply their own signer keypair as `pool_state` (bypassing the PDA requirement via the `is_signer` escape hatch), pre-load its byte content via ownership reassignment to a helper program they control, reassign back to the System Program, and call `initialize`/`initialize_with_permission`. No special privilege, leaked key, or validator behavior is required — only standard account-ownership/CPI mechanics available to any transaction signer.

### Recommendation
- In `PoolState::initialize()`, explicitly set `self.status = 0;` (or the intended initial status) alongside the other fields, so the field can never retain attacker-supplied bytes.
- More fundamentally, require `pool_state` (and any other zero-copy account created through the custom `AccountLoad`/`create_or_allocate_account` path) to be the canonical PDA, removing the "or is_signer" bypass in `create_pool()`, and/or have `load_init()` verify the entire account buffer is zeroed (not just the 8-byte discriminator) before treating it as freshly initialized.

### Proof of Concept
1. Attacker (as pool creator) generates keypair `K` for `pool_state` (not equal to the canonical `find_program_address` PDA for the pool seeds).
2. In a setup transaction, attacker's own helper program: (a) has the System Program create account `K` with `PoolState::LEN` space and 0 lamports beyond rent, (b) `Assign`s ownership of `K` to the helper program, (c) writes a non-zero byte at the `status` field offset within `K`'s data, (d) `Assign`s ownership of `K` back to the System Program.
3. Attacker calls `initialize`, passing `K` as `pool_state` with `K` as an additional signer. `create_pool()` accepts it because `pool_account_info.is_signer == true` even though `K != expect_pda_address`.
4. `pool_state_loader.load_init()` only validates the discriminator bytes are zero and casts the rest of the buffer as `PoolState`, preserving the pre-planted non-zero `status` byte.
5. `pool_state.initialize(...)` runs but never touches `self.status`, so the poisoned status persists.
6. A separate LP deposits into this pool.
7. That LP calls `withdraw`; the `get_status_by_bit(PoolStatusBitIndex::Withdraw)` check fails because the corresponding bit was set in step 2, permanently blocking withdrawal since only the admin-only `update_pool_status` instruction can alter it — and the admin has no reason to know this specific pool was poisoned.

    pub fn set_status_by_bit(&mut self, bit: PoolStatusBitIndex, flag: PoolStatusBitFlag) {
        let s = u8::from(1) << (bit as u8);
        if flag == PoolStatusBitFlag::Disable {
            self.status = self.status.bitor(s);
        } else {
            let m = u8::from(255).bitxor(s);
            self.status = self.status.bitand(m);
        }
    }

    /// Get status by bit, if it is `noraml` status, return true
    pub fn get_status_by_bit(&self, bit: PoolStatusBitIndex) -> bool {
        let status = u8::from(1) << (bit as u8);
        self.status.bitand(status) == 0
    }

pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }

    token::create_or_allocate_account(
        &crate::id(),
        payer.to_account_info(),
        system_program.to_account_info(),
        pool_account_info.clone(),
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
            &[bump],
        ],
        PoolState::LEN,
    )?;

    pub fn load_init(&self) -> Result<RefMut<'_, T>> {
        // AccountInfo api allows you to borrow mut even if the account isn't
        // writable, so add this check for a better dev experience.
        if !self.acc_info.is_writable {
            return Err(ErrorCode::AccountNotMutable.into());
        }

        let mut data = self.acc_info.try_borrow_mut_data()?;

        // The discriminator should be zero, since we're initializing.
        let mut disc_bytes = [0u8; 8];
        disc_bytes.copy_from_slice(&data[..8]);
        let discriminator = u64::from_le_bytes(disc_bytes);
        if discriminator != 0 {
            return Err(ErrorCode::AccountDiscriminatorAlreadySet.into());
        }

        // write discriminator
        data[..8].copy_from_slice(&T::DISCRIMINATOR);

        Ok(RefMut::map(data, |data| {
            bytemuck::from_bytes_mut(&mut data.deref_mut()[8..mem::size_of::<T>() + 8])
        }))
    }
