### Title
`handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` Bypass `isRunning` and Token-Lock Emergency Stops — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

### Summary

The Kaia service-chain bridge's three asset-disbursement functions — `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — do not check the `isRunning` flag or the per-asset lock flags (`isLockedKLAY` / `lockedTokens`). The bridge owner can call `setRunningStatus(false)`, `lockKLAY()`, or `lockToken()` to attempt an emergency halt, but bridge operators can still invoke the handle functions to drain all KLAY and bridged tokens from the contract.

### Finding Description

`BridgeTransfer.sol` declares `isRunning` as the global emergency stop: [1](#0-0) 

`BridgeTransferKLAY.sol` declares `isLockedKLAY` as a per-asset lock: [2](#0-1) 

The **inbound** request functions correctly enforce both guards. `_requestKLAYTransfer` carries the `unlockedKLAY` modifier and an explicit `require(isRunning)`: [3](#0-2) 

`_requestERC20Transfer` carries `onlyUnlockedToken` and `require(isRunning)`: [4](#0-3) 

`_requestERC721Transfer` carries the same guards: [5](#0-4) 

The **outbound** handle functions that actually disburse assets carry **only** `onlyOperators` (and `nonReentrant` for KLAY). Neither `isRunning` nor any lock flag is checked:

`handleKLAYTransfer` — sends native KLAY: [6](#0-5) 

`handleERC20Transfer` — mints or transfers ERC-20 tokens: [7](#0-6) 

`handleERC721Transfer` — mints or transfers ERC-721 tokens: [8](#0-7) 

### Impact Explanation

When the bridge owner detects an incident (e.g., a compromised operator key or a bug in the counterpart chain's bridge) and calls `setRunningStatus(false)`, `lockKLAY()`, or `lockToken(addr)`, those calls only block new cross-chain requests. Any operator (or attacker holding a compromised operator key) can still call `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` with arbitrary `_to`, `_value`, and a fresh `_requestedNonce` to drain the bridge's entire KLAY balance and all held ERC-20/ERC-721 tokens. The nonce-window check (`_lowerHandleNonceCheck`) only prevents replaying already-handled nonces; it does not prevent new nonces from being submitted. The result is **unauthorized transfer of KLAY and bridged assets** from the bridge contract to an attacker-controlled address.

### Likelihood Explanation

Bridge operators are semi-trusted accounts whose private keys can be compromised. The multi-operator threshold mechanism (`operatorThresholds`) means that if the threshold is 1 (the default after deployment) or if enough operator keys are compromised to meet the threshold, a single transaction suffices to drain the bridge after the owner has attempted to halt it. The owner's only remaining recourse — deregistering operators — requires a separate on-chain transaction that can be front-run.

### Recommendation

Add `require(isRunning, "stopped bridge")` to all three handle functions. For KLAY, also add the `unlockedKLAY` modifier; for ERC-20 and ERC-721, add `onlyUnlockedToken(_tokenAddress)`. This mirrors the guards already present on the request-side functions and gives the bridge owner a meaningful emergency stop that covers both directions of asset flow.

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators unlockedKLAY nonReentrant {
    require(isRunning, "stopped bridge");
    ...
}

// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}

// BridgeTransferERC721.sol
function handleERC721Transfer(...) public onlyOperators onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    ...
}
```

### Proof of Concept

1. Bridge is deployed with `isRunning = true`, `isLockedKLAY = false`, and 1000 KLAY held in the contract.
2. Operator key is compromised. Bridge owner calls `setRunningStatus(false)` and `lockKLAY()`.
3. Attacker (holding the operator key) calls:
   ```solidity
   bridge.handleKLAYTransfer(
       keccak256("fake"),   // _requestTxHash — any unused hash
       attacker,            // _from
       attacker,            // _to
       1000 ether,          // _value — full balance
       999999,              // _requestedNonce — any nonce above lowerHandleNonce
       block.number,
       ""
   );
   ```
4. Because `handleKLAYTransfer` checks only `onlyOperators` and `nonReentrant`, the call succeeds: `isRunning = false` and `isLockedKLAY = true` are never read. The attacker receives 1000 KLAY.
5. The same attack applies to `handleERC20Transfer` and `handleERC721Transfer` for all registered tokens.

    function handleKLAYTransfer(
        bytes32 _requestTxHash,
        address _from,
        address payable _to,
        uint256 _value,
        uint64 _requestedNonce,
        uint64 _requestedBlockNumber,
        bytes memory _extraData
    )
        public
        onlyOperators
        nonReentrant
    {
        _lowerHandleNonceCheck(_requestedNonce);

        if (!_voteValueTransfer(_requestedNonce)) {
            return;
        }

        _setHandledRequestTxHash(_requestTxHash);

        handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
        _updateHandleNonce(_requestedNonce);

            lowerHandleNonce,
            _extraData
        );

    }
