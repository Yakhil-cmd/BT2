### Title
Membership webhook trusts `params.team.id` / `params.member.login` with no organization binding, letting a signed webhook from an attacker's own org attach an arbitrary GitHub login to any pre-existing `Shipit.github_teams` team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the `Team` purely by `github_id` and the `User` purely by `login`, both taken verbatim from the webhook JSON body, and never checks that the signing organization (the one whose `webhook_secret` validated the request) actually owns that team. `WebhooksController#verify_signature` itself picks which organization's `webhook_secret` to verify against from `params.dig('organization','login')` when no `repository` key is present (true for `membership` events), so the "signing organization" is whatever the attacker puts in the JSON body, as long as that org name is one that is configured in this Shipit instance with its own GitHub App/webhook secret.

### Finding Description
Broken binding: the code assumes `Membership row created for team T == a membership GitHub actually reported for T`, but nothing enforces `team.organization == verified_signing_organization` nor `member.login == a real GitHub member of that team`.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and then does `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [2](#0-1) . For a `membership` event payload there is no `repository` key, so `repository_owner` is taken from the attacker-controlled `organization.login` field in the body itself.
2. `Shipit.github(organization:)` looks up a per-organization config keyed by that name; if the attacker names an organization that is configured in the multi-tenant secrets (as in `test/dummy/config/secrets_double_github_app.yml`), it returns that org's own `GitHubApp`/`webhook_secret` [3](#0-2) . Since it's the attacker's own org, they legitimately know that secret and can produce a valid `X-Hub-Signature` for `verify_webhook_signature` [4](#0-3) .
3. Once signature verification passes, `MembershipHandler#process` runs: `team = find_or_create_team!` resolves `Team.find_or_create_by!(github_id: params.team.id)` [5](#0-4) . If `params.team.id` matches the `github_id` of a pre-existing `Team` row (e.g. one already in `Shipit.github_teams`, created earlier from a legitimate org), `find_or_create_by!` returns that **existing** row and the block (which would set `team.organization`) never runs — the attacker's forged `organization.login` is not applied to, or checked against, the existing team.
4. `member = User.find_or_create_by_login!(params.member.login)` resolves/creates a `User` purely from a string login, with no relation to any org or team [6](#0-5) .
5. For `action == 'added'`, `team.add_member(member)` appends the membership [7](#0-6) [8](#0-7) .
6. `User#authorized?` grants access if `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) . Because `add_member` just wrote a `Membership` row tying that `Team` (whose `id` is in `Shipit.github_teams`) to whatever `User` the attacker named, `authorized?` becomes true for that user — whether it's the attacker's own login or a real maintainer's login the attacker chose to target.

Existing guards do not prevent this: `verify_signature` only proves the payload was signed by *some* configured org's secret — it never proves the payload's claims (team, organization, member) belong to that org. `ExplicitParameters` (`params do ... end` in the handler) only validates types/presence, not cross-field/org consistency. `find_or_create_team!`'s lookup key (`github_id`) is controllable by the attacker and, once a `Team` row exists, silently reuses it without re-validating organization.

### Impact Explanation
An attacker who has a GitHub organization configured as its own tenant in this Shipit instance's `secrets.github` (multi-org/App config) can, using only their own legitimate `webhook_secret`, forge a `membership` "added" event that:
- Targets any `Team` whose `github_id` is already known to Shipit and is part of `Shipit.github_teams` (the authorization gate), regardless of which org actually owns that team.
- Names any GitHub login as the `member` — either the attacker's own login (self-escalation to `authorized?` == true) or an existing real maintainer's login (forged membership record attributing team membership to a real Shipit user without their knowledge).

This is an authentication/authorization bypass into `Shipit.github_teams`-gated access, repeatable at will (any number of `added` events) and not scoped to the attacker's own repositories/teams — it can target any team ID observed on the Shipit instance. This is Critical/High per the escalation-into-`Shipit.github_teams` category.

### Likelihood Explanation
The exploit requires the attacker's organization to already be a configured GitHub App tenant of this specific Shipit instance (i.e., Shipit is deployed in a multi-org configuration where the attacker controls one of the trusted orgs but not the org owning the target team/`Shipit.github_teams`). Under the stated attacker model ("attacker who controls a signing organization"), this is exactly the scenario in scope. Given that precondition, the attack cost is a single crafted HTTP POST with a valid HMAC computed from the attacker's own known secret — trivial and fully repeatable, no GitHub API interaction or session needed.

### Recommendation
In `MembershipHandler#process`/`find_or_create_team!`, bind the verified signing organization to the operation: reject or ignore the event unless `params.organization.login` matches the `Team#organization` value already on record (and for newly created teams, require that the verified signing org equals `params.organization.login` used to create it). Do not allow `find_or_create_by!(github_id:)` to silently reuse a team owned by a different organization than the one that produced a valid signature. Additionally, consider passing the verified organization through from `WebhooksController` into the handler instead of trusting the body's `organization.login` for anything beyond convenience.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` patterns), no live GitHub:
```ruby
test "membership webhook from a foreign org cannot attach members to another org's team" do
  # Precondition: two configured orgs, "shopify" (owns shipit_teams(:shopify_developers))
  # and "attacker-org" (its own webhook_secret, unrelated to shopify).
  team = shipit_teams(:shopify_developers) # github_id belongs to Shipit.github_teams
  Shipit.stubs(:github_teams).returns([team])

  attacker_login = "attacker"
  payload = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: attacker_login }
  }.to_json

  @request.headers['X-Github-Event'] = 'membership'
  # Signature computed with attacker-org's OWN webhook_secret (attacker knows this secret)
  @request.headers['X-Hub-Signature'] =
    "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, payload)}"

  post :create, body: payload, as: :json
  assert_response :ok

  attacker_user = Shipit::User.find_by(login: attacker_login)
  # Binding check: team.organization ("shopify") != signing organization ("attacker-org")
  refute_equal team.organization, 'attacker-org'
  # Vulnerability: despite the mismatch, authorized? is granted
  assert attacker_user.authorized?
end
```
This demonstrates that `team.organization == "shopify"` while the verified signing organization is `"attacker-org"` — the two sides of the required binding diverge, yet `Membership` is created and `authorized?` returns `true`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

    end
