### Title
Forged cross-tenant status webhook can flip commit state and trigger `Stack#schedule_merges` on an unrelated stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by SHA with `Commit.where(sha: params.sha)`, without validating that the payload's `repository` matches the commit's actual stack/repository [1](#0-0) . Because the webhook signature check in `WebhooksController#verify_signature` picks the verifying secret using the *attacker-controlled* `repository.owner.login` field of the payload itself, an attacker who legitimately owns one configured GitHub organization/app in a multi-tenant Shipit install can sign an arbitrary payload with their own known `webhook_secret` and set an arbitrary `sha` value that happens to collide with a commit belonging to a different stack/organization.

### Finding Description
The broken binding: a `Status` row created from a webhook payload must belong to a commit whose `stack.repository` equals `payload['repository']['full_name']`. Instead, the code writes `Commit.where(sha: params.sha)` with no join/filter on repository at all [1](#0-0) .

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (attacker-supplied) and fetches the `GitHubApp` for *that* organization via `Shipit.github(organization: repository_owner)`, then verifies HMAC-SHA1 using that organization's own `webhook_secret` [2](#0-1) .
2. In a multi-tenant configuration (documented and tested — `config/secrets.github` keyed by organization, e.g. `test/dummy/config/secrets_double_github_app.yml`), each organization has its own `webhook_secret` [3](#0-2) [4](#0-3) . An attacker who owns one such organization (a real, properly configured GitHub org integrated with this Shipit instance) knows/controls that org's `webhook_secret` (they configured it when installing the GitHub App), so they can compute a valid `X-Hub-Signature` for any JSON body they want, as long as `repository.owner.login` in that body matches their own org (so the correct, attacker-known secret is selected for verification).
3. `verify_webhook_signature` performs a straightforward HMAC-SHA1 compare against the raw POST body [5](#0-4)  — it does not tie the signature to the specific `sha`/commit referenced inside the body, only to the raw bytes and the organization-selected secret.
4. Once past signature verification, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, whose `params` schema only validates `sha`/`state`/etc. shapes, not repository ownership [6](#0-5) .
5. `process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this can match a commit belonging to a *victim* stack under a completely different organization/repository, since SHAs are just strings and are not namespaced to `(stack_id, sha)` in this query [1](#0-0) .
6. `Commit#create_status_from_github!` calls `add_status`, which creates the `Status` row and, if the simple state transitions (e.g., to `success`/`pending`), calls `stack.schedule_merges` on the victim's `stack` [7](#0-6) .

Why existing guards fail: `verify_signature` authenticates *which organization is speaking*, not *which repository/commit the payload content is entitled to affect*. The signature is valid and consistent for the attacker's own org, but the payload body's `sha` field is free-form and unchecked against that org's actual repositories. The `ExplicitParameters` schema in `StatusHandler` validates types only, not repository scope. No code path re-derives the commit's owning repository and compares it to `payload['repository']['full_name']` before running `create_status_from_github!`.

Preconditions: this requires the multi-org config schema (`github: { org1: {...}, org2: {...} }`) to be in use, and requires that the target commit's SHA is known to the attacker (SHAs are generally public/observable on GitHub, so this is easy to satisfy) and that the SHA doesn't collide within the attacker's own stacks (extremely unlikely collision aside — the point is SHA equality across repos is only theoretically improbable but the code makes zero attempt to disambiguate; a targeted attacker with access to the victim's SHA, e.g. via a public commit hash, a shared/forked history, or a stack the attacker was invited to briefly, can exploit this directly). Even in the single-organization config (`Shipit.github` singular), if the attacker's repository shares the same org as a victim repository (a common real-world case — many stacks share one org, differing only by repo name), the exploit still works because signature verification never checks `repository.name`, only `repository.owner.login`.

### Impact Explanation
A successful forged `status` webhook can flip an arbitrary commit's aggregated `state` (via `Status::Group`) and trigger `stack.schedule_merges` on a stack the attacker does not own, enqueuing `ProcessMergeRequestsJob` [8](#0-7) . This is a cross-tenant write: a payload authenticated for one repository/organization ends up mutating another stack's commit/status state and can push it toward continuous-deployment/merge automation it should never trigger, matching the "Critical — a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy/merge" category. The blast radius spans every stack across every organization configured on the same Shipit instance, since the SHA lookup is completely global and unscoped.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit deployment (or single-org deployment hosting multiple repos under one org, which is also common), (b) attacker legitimately owns/administers one configured GitHub organization/App integration with its own `webhook_secret`, (c) attacker knows the target commit SHA (commonly public). No Shipit session, API token, or GitHub App private key is required — only the attacker's own legitimately configured webhook secret, which they possess by design since they are a legitimate tenant admin of their own org. This is fully repeatable per request against any known SHA and is not rate-limited by any check in this path.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other handler using bare SHA lookups, e.g., `refresh_statuses!`/check-run handlers) to the repository named in the payload — e.g., resolve the target `Stack`/`Repository` from `payload['repository']['full_name']` first, then constrain `Commit.where(sha: params.sha, stack_id: matching_stack.id)` (or join through `stacks.repository`) before calling `create_status_from_github!`. Reject or ignore statuses whose payload repository does not match the commit's actual stack repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "status payload naming an unrelated repository still updates a victim stack's commit and schedules merges" do
  victim_commit = shipit_commits(:fixture) # belongs to some stack, e.g. shipit_stacks(:shipit)
  victim_stack = victim_commit.stack

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack.id]) do
    assert_difference -> { victim_commit.statuses.count }, 1 do
      Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)
    end
  end

  # Binding check: payload repository != commit's actual repository, yet the write succeeded
  refute_equal forged_payload['repository']['full_name'], victim_stack.repository.full_name
end
```
This test calls the handler directly (bypassing signature verification, which is a separate, already-demonstrated bypass via the attacker's own org secret) and asserts that `Commit.where(sha:)` matches and mutates `victim_commit`/`victim_stack` despite the payload naming an unrelated repository, and that `ProcessMergeRequestsJob` is enqueued for the victim stack — proving the repository-scope binding is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
