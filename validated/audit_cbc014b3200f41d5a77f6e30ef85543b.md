### Title
Pull request label names (uppercased) become unfiltered environment variable keys injected into `git`/task subprocess env - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) as an environment variable key with value `"true"`, with no allowlist against the deploy spec's declared `VariableDefinition`s. Because `TaskCommands#env`/`StackCommands#env` merge `@stack.env` directly into the hash later passed to `Command#unbundled_env` and `PTY.spawn`, a label such as `RUBYLIB=/tmp/evil` (as key, forced value `"true"`) or any attacker-chosen uppercase key reaches the deploy host's process environment unfiltered.

### Finding Description
The broken invariant: the environment hash passed to `PTY.spawn` should equal `BASE_ENV ∪ PATH ∪ (keys ⊆ declared VariableDefinition names ∪ Shipit.env ∪ hardcoded task keys)`, but in practice it equals `BASE_ENV ∪ PATH ∪ @stack.env` where `@stack.env` contains **arbitrary attacker-chosen keys** derived from PR label names.

Path:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload onto `pull_request.labels`, with no key/character restriction: [1](#0-0) 
2. `ReviewStack#env` merges these label names, uppercased, as environment keys with no allowlist check: [2](#0-1) 
3. `TaskCommands#env` (used by deploys, rollbacks, and custom tasks) merges `@stack.env` in directly, unlike task-supplied user variables which are filtered via `EnvironmentVariables#permit`/`filter_envs` against `VariableDefinition` allowlists: [3](#0-2)  and [4](#0-3) 
4. `StackCommands#fetch`/`#fetch_commit` similarly merge `@stack.env` for the `git` subprocess: [5](#0-4) 
5. `Command#unbundled_env` merges `@env.stringify_keys` over `BASE_ENV` with no key restriction, and `#start` passes this directly to `PTY.spawn`: [6](#0-5) 

Existing tests confirm the merge is intentional and unrestricted: labels `"wip"`/`"bug"` become `env["WIP"]`/`env["BUG"]` for both `ReviewStack#env` and `TaskCommands#env`: [7](#0-6) [8](#0-7) 

Why guards fail: `EnvironmentVariables#permit`/`filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` only sanitize the **user-supplied deploy/task/rollback form variables** (`@task.env`) against declared `VariableDefinition`s — they are never applied to `@stack.env`, which is where the label-derived keys enter. There is no equivalent allowlist call site for `ReviewStack#env`'s label merge.

Regarding label authorship: GitHub restricts adding labels to users with write/triage access on the target repository, not arbitrary fork PR authors — this is a GitHub-side permission, not enforced by this engine. The audit's Rules section explicitly grants the attacker the capability to "label their own PR," so within the given threat model this path is in scope; however, real-world exploitability depends on the attacker (or a compromised/malicious low-privilege collaborator) actually possessing label-write permission on the tracked repository.

### Impact Explanation
Once a label sets an environment variable key like `RUBYLIB`, any `ruby`/`bundle exec` step invoked in the deploy/task/rollback pipeline (or a `git` hook script relying on `require`) that runs on the Shipit deploy host will `require` attacker-controlled code from an attacker-writable path, achieving arbitrary code execution as the Shipit worker user. This is a Critical RCE on the deploy host, matching the target category. Because the label is attached at the `ReviewStack`/`PullRequest` level, the blast radius is scoped to that stack's deploy/task pipeline but is fully repeatable — any future task, deploy, rollback, or fetch on that review stack inherits the poisoned key until the label is removed and `capture_labels` re-syncs.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that creates a `ReviewStack` for the attacker's PR (`allow_all`, or `allow_with_label`/`prevent_with_label` matched appropriately), and the attacker (or a party controlling labels on that PR) must be able to attach an arbitrary-named label. Attacker cost is low if they have label-write access; the mechanism itself requires no Shipit credentials, only a normal GitHub webhook delivery from GitHub itself. The attack is repeatable at will by relabeling.

### Recommendation
Do not allow PR label names to become environment variable **keys**. Either drop this feature, or route label-derived variables through the same `EnvironmentVariables#permit` allowlist mechanism used for task/deploy variables (e.g., require labels to match a `shipit.yml`-declared `VariableDefinition` allowlist before merging), and additionally block any key that collides with dangerous process-env names (`RUBYLIB`, `LD_PRELOAD`, `GIT_*`, `PATH`, `BUNDLE_*`, etc.) regardless of source.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (extend existing test file)
test "#env allows a PR label to inject an arbitrary process env key like RUBYLIB" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["rubylib"]

  env = Shipit::TaskCommands.new(shipit_tasks(:shipit_restart).tap { |t| t.stack = stack }).env
  assert_equal "true", env["RUBYLIB"]

  command = Shipit::Command.new("git status", env: env, chdir: ".")
  assert_includes command.unbundled_env.keys, "RUBYLIB"
  # Binding under test that should NOT hold if fixed:
  # env.keys - Shipit::VariableDefinition allowlist names should be empty
end
```
This demonstrates the equality `Command#unbundled_env.keys ⊇ {"RUBYLIB"}` derived solely from an uppercased PR label name, with no allowlist check against declared `VariableDefinition`s, confirming the divergence from the expected invariant.
