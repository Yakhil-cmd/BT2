### Title
Hookify `action: block` rules silently degrade to warn-only on case/format mismatch — no validation error - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`hookify`'s rule frontmatter parser and `Rule` model treat `action` as a free-form string with no schema validation, and `RuleEngine` only recognizes the exact literal `'block'`. Any deviation from that lowercase literal (a typo, different casing, or a value the naive hand-rolled YAML parser mangles) silently falls through to the "warn" code path instead of raising an error or rejecting the rule, meaning a rule the user believes will block a dangerous Bash/Edit/Write/Stop operation actually only prints a warning and lets the operation proceed.

### Finding Description
`Rule.from_dict` reads the `action` field with an unconstrained default and no enum/format check: [1](#0-0) 

The custom, hand-rolled frontmatter/YAML parser (`extract_frontmatter`) only special-cases the literal strings `"true"`/`"false"`; every other scalar — including `action` — is passed through as-is after stripping whitespace/quotes: [2](#0-1) 

`RuleEngine.evaluate_rules` then does a case-sensitive, exact-string comparison to decide whether a matched rule blocks or merely warns: [3](#0-2) 

There is no rejection path for an unrecognized `action` value anywhere in `config_loader.py` or `rule_engine.py` — unlike the enum in the `frame.go` bug report where an invalid `is_last` byte is *supposed* to invalidate the frame, here an invalid/mistyped `action` value (`Block`, `BLOCK`, `block ` with a stray character the parser fails to strip, `blocked`, etc.) is accepted without error and silently mapped to the same code path as `action: warn`. `load_rules`/`load_rule_file` never surface this as a warning either — the file loads successfully and the rule is registered and shown as "enabled" with no diagnostic that its action semantics didn't take effect: [4](#0-3) 

This is exactly the bug-class from the report: a security-relevant enum field with only two valid values is parsed with an implicit, silent fallback to the less-restrictive value instead of an explicit error when the input doesn't exactly match the expected literal.

### Impact Explanation
Hookify is documented and marketed as a mechanism for the user to configure `PreToolUse`/`Stop` gates that "prevent operation from executing" for dangerous commands (`rm -rf`, `dd`, credential leaks, etc.): [5](#0-4) 

A user (or the `/hookify` slash command itself, which is Claude-authored via an LLM step generating the YAML front-matter, so it is not immune to producing a value like `Block`/`block.`/`BLOCK`) who intends to have Claude Code deny a destructive command will get no diagnostic that the rule silently only warns. The operation is *not blocked*, and the user has a false sense of security that a hard guardrail is in place. This is a local, single-user impact (no cross-tenant/consensus split, since hookify has no analog to "multiple independent nodes/verifiers" — it's a single local enforcement point), so it does not reach the severity of the original consensus-split bug, but it is a genuine, concrete unauthorized-action outcome: a destructive Bash command or a credential-leaking file edit that the user configured to be blocked is instead permitted to execute.

### Likelihood Explanation
Moderate. The `/hookify` command flow explicitly instructs the agent to write `action: {warn|block}` from a natural-language description via an LLM-authored file (`hookify.md`), and the `hookify:configure` interactive tool edits these files by hand as well — both paths are prone to introducing exactly this kind of subtle casing/formatting drift, especially since the parser is a hand-rolled 100-line YAML subset without any schema validation or unit-tested edge cases enforcing the literal `block`.

### Recommendation
- In `Rule.from_dict`, normalize (`.strip().lower()`) and validate `action` against `{"warn", "block"}`; raise/log a clear error (and refuse to silently load the rule as "warn") when the value doesn't match either literal.
- Add a matching warning in `load_rule_file`/`load_rules` (similar to the existing `missing YAML frontmatter` warning) so a misconfigured `action` is surfaced to the user instead of silently disappearing into an unintended enforcement mode.
- Consider making `RuleEngine._rule_matches`/`evaluate_rules` fail closed (treat unrecognized `action` as blocking, or refuse to register the rule) rather than fail open (treat as warn) — mirroring the recommendation from the referenced report to reject rather than default-accept malformed critical enum values.

### Proof of Concept
1. Create `.claude/hookify.block-rm.local.md`:
```markdown
---
name: block-rm
enabled: true
event: bash
pattern: rm\s+-rf
action: Block
---

🛑 Destructive rm blocked.
```
(Note the capitalized `Block`, e.g. produced by an LLM writing the file, or a user copy-pasting from a source that capitalizes it.)

2. `load_rule_file` parses this successfully — `frontmatter['action'] == "Block"` (no case/enum validation), and `Rule.from_dict` sets `rule.action = "Block"` verbatim. [6](#0-5) 

3. Trigger a `Bash` tool call with `command: "rm -rf /tmp/test"`. `_rule_matches` returns `True` (the regex condition matches), but in `evaluate_rules`, `rule.action == 'block'` evaluates to `False` (`"Block" != "block"`), so the rule is appended to `warning_rules` instead of `blocking_rules`: [3](#0-2) 

4. Result: `{"systemMessage": "**[block-rm]**\n🛑 Destructive rm blocked."}` is returned — a warning message only — and the `PreToolUse` hook does **not** emit `permissionDecision: deny`. The `rm -rf /tmp/test` command executes despite the rule author's clear intent (and the rule's own message text) to block it, with no error or log indicating the `action` value was invalid.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
