### Title
Stale in-memory `Account` snapshot written back after the flash-position receiver callback, overwriting concurrent storage mutations to the same account - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`process_flash_position` loads the `Account` into memory once (`account::load_or_create_account`), mutates that copy, invokes an arbitrary attacker-controlled `receiver` contract via `execute_flash_position`, and only afterwards persists the still-stale in-memory `Account` through `process_deposit` → `strategy_finalize` → `persist_account_positions` (`set_supply_positions`/`set_debt_positions` rewrite the whole `SupplyPositions`/`BorrowPositions` maps). This is the Soroban analog of CVE-2021-47533: the kernel kept a pointer to a `drm_crtc_commit` that could be freed while still referenced, and duplicated state carried the stale pointer forward. Here the controller keeps a *copy* of position state taken before the callback and writes it back afterwards, so any position-map change made to that account during the callback window is clobbered — stale (already-seized or already-removed) positions are resurrected exactly as the stale commit pointer was duplicated into new state.

### Finding Description
At `contracts/controller/src/strategies/flash_position.rs:93-101` the account is loaded and `borrow_into_controller` (line 271-279) mutates `account.borrow_positions` **in memory only** — nothing is persisted yet. The code then enters `storage::with_flash_guard` and calls `invoke_receiver` (lines 120-143, 297-323), handing control to an arbitrary `receiver` contract that knows the `account_id` (it is passed as a callback argument, line 313). After the callback returns, `process_deposit` (line 146) merges measured collateral into the same stale `account` object, and `strategy_finalize` (line 153) ultimately calls `persist_account_positions` in `contracts/controller/src/positions/mod.rs:153-170`, which calls `write_side_map` (`contracts/controller/src/storage/account.rs:94-105`) — a wholesale `persistent.set(key, map)` overwrite of the account's position maps.

Concretely: a caller opens `flash_position` on an account that is already liquidatable (or becomes so). During the callback the receiver invokes `liquidate` on that `account_id`. Liquidation operates on the *persisted* position maps (the pre-flash state, since the flash debt is still only in memory), seizes collateral, and writes reduced maps to storage. When the callback returns, the outer flow's stale `account` — still containing the full pre-liquidation `supply_positions` — is written back by `set_supply_positions`. The seized supply shares reappear on storage while the liquidator already received the underlying tokens: the collateral is effectively duplicated. The reverse ordering (position deleted in storage during callback, resurrected by the stale write-back) mirrors the kernel bug where a freed structure's pointer was copied into duplicated state.

### Impact Explanation
Theft of user funds / protocol insolvency: collateral shares are restored to the account after the pool has already paid them out to the liquidator, inflating `supplied` claims against the same physical pool cash. The resurrected position can be withdrawn in a later transaction, paying out tokens that no longer back the shares — the same shares are paid twice. More generally, any same-account storage mutation reachable during the callback window (liquidation legs, `update_account_threshold` restamping, bad-debt cleanup) is silently discarded by the stale wholesale write-back.

### Likelihood Explanation
Reachability requires only that some permissionless controller verb that writes `SupplyPositions`/`BorrowPositions` for `account_id` is not blocked by `is_flash_loan_ongoing` during the callback. The guard is documented as protecting "both forwarding and the callback" (line 119) because "token hooks can reenter first" — i.e., it targets token-callback reentry, not a full reentrancy lock on all entrypoints, and `receiver` is an arbitrary contract (`require_wasm_receiver` only checks it is a WASM contract and not the controller/pool). The trigger condition (an already-liquidatable account) is common and the attack is a single transaction from one unprivileged address. Uncertainty: I was unable to verify exhaustively within available budget whether `liquidate`/`withdraw`/`clean_bad_debt` each independently assert `!is_flash_loan_ongoing`; if every position-writing entrypoint checks the flag, this vector closes and the finding reduces to a design fragility.

### Recommendation
Persist the position maps *before* invoking the receiver (or reload them from storage afterwards), rather than writing a pre-callback snapshot back post-callback. At minimum, re-read `get_supply_positions`/`get_debt_positions` for `account_id` after `invoke_receiver` returns and merge the callback-window deltas, and assert `is_flash_loan_ongoing` (or a dedicated reentrancy flag covering the callback window) in every public entrypoint that writes account position maps — not only in flash-adjacent paths.

### Proof of Concept
1. Attacker creates an account (`account_id`) with supply `S` in asset A and debt `D` in asset B such that HF < 1 (e.g., via price movement or an intentionally thin position).
2. Attacker deploys a receiver contract implementing `execute_flash_position(initiator, account_id, asset, amount, fee, amount_received, controller, data)` which calls `controller.liquidate(account_id, …)` targeting the pre-flash supply position.
3. Attacker calls `controller.flash_position(account_id, spoke_id, Multiply, debt=(hub,B), amount, receiver, data, collaterals=[(hub,A, min)], refund_assets=[])`.
4. Controller loads `account` (supply `S` still in the in-memory map), mints flash debt in memory, forwards tokens, invokes the receiver.
5. Receiver's `liquidate` call runs against persisted state: supply position `S` is seized pro-rata, tokens transferred to the liquidator, `SupplyPositions(account_id)` written with the reduced/removed entry.
6. Callback returns; `process_deposit` merges collateral receipts into the stale in-memory `account` (still containing `S`), and `strategy_finalize` → `set_supply_positions` overwrites `SupplyPositions(account_id)` with the stale map, resurrecting `S`.
7. The account now holds supply shares whose underlying was already paid to the liquidator; the attacker withdraws the resurrected collateral later — double payout.
