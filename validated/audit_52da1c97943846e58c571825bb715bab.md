## Title
Stack-scoped API token can read any stack's build status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` resolves the target `stack` directly from `Stack.from_param!(params[:stack_id])` instead of going through the `ApiClient`-scoped `stacks` relation that every other API controller uses, breaking the binding: `stack a token authorises == stack it touches`.

### Finding Description
Every other API controller derives the acted-upon stack through the scoped relation defined in `Shipit::Api::BaseController`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::StacksController` follows this pattern exactly (`stacks.from_param!(params[:id])`), confirming this is the intended authorization mechanism for stack-scoped `ApiClient`s. [2](#0-1) 

`Api::CCMenuController` instead overrides `stack` to bypass the scoping relation entirely, resolving the stack directly against the unscoped `Stack` model:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

`ApiClient` supports an optional `stack` association, and `check_permissions!` only validates the coarse `operation:scope` string (e.g. `read:stack`) — it never checks which specific stack the client is scoped to:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3) 

The per-stack restriction for scoped clients is enforced solely by the `stacks` relation in `BaseController`, and `CCMenuController` is the only API controller that does not use it. `require_permission :read, :stack` only checks the permission string is present, not the `stack_id` binding. [5](#0-4) 

**Binding broken (equality that should hold but doesn't):**
`stack authorised by ApiClient.stack_id` ≠ `stack touched by CCMenuController#stack` (via `params[:stack_id]`).

Before the pull request/attack: a token created with `stack_id` set to Stack A and permission `read:stack` can only read Stack A's data everywhere else in the API (enforced by `stacks.from_param!`).
After: that same token, sent to `GET /api/:stack_id/ccmenu.xml` with `stack_id` set to Stack B, is accepted by `authenticate_api_client` (which only checks the token is valid, not its stack scope) and then `stack` resolves Stack B directly, unscoped.

### Impact Explanation
This is an unauthenticated-scope-boundary crossing: a credential explicitly restricted to Stack A can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, `activity`, lock state, etc.) of any other stack in the installation, including stacks the token's creator was never granted this specific token for. This matches the report's "High" impact category of unauthenticated read of stack state through an authorization boundary that other endpoints correctly enforce but this one does not — directly analogous to the underlying report's pattern of a check performed on one side of a binding (organization/permission verified) while the actual object acted upon (a different lender/stack) is not covered by that check.

### Likelihood Explanation
Requires only possession of any valid `ApiClient` authentication token that is stack-scoped (a supported, documented feature: `ApiClient belongs_to :stack, optional: true`, and used by `stacks_controller_test.rb`'s "an api client scoped to a stack will only see that one stack" test) plus knowledge/guessing of another stack's `to_param`. No privileged access or session is required beyond having any one legitimately-issued, narrowly-scoped API token — exactly the kind of unprivileged-attacker credential-boundary violation in scope.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped relation, consistent with every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This enforces `current_api_client.stack_id? => Stack.where(id: current_api_client.stack_id)` the same way `Api::StacksController` and `Api::BaseController#stack` do.

### Proof of Concept
1. Admin creates a stack-scoped `ApiClient` for Stack A with `permissions: ['read:stack']` and `stack: StackA` (supported by the `ApiClient` model and exercised by existing test fixtures/tests).
2. Using that client's `authentication_token` as Basic Auth credentials, request:
   `GET /api/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu.xml` with `Authorization: Basic <token_for_stack_A>`.
3. `authenticate_api_client` in `CCMenuController` succeeds because `ApiClient.authenticate(params[:token])` (or the inherited Basic-Auth flow) only validates token integrity, not stack scope.
4. `stack` resolves `Stack.from_param!(params[:stack_id])` directly against Stack B, bypassing the `current_api_client.stack_id` restriction that `Api::BaseController#stacks` would have enforced.
5. Response renders Stack B's CCMenu XML (build status/label/URL), which the token was never authorized to view — contrast with the same token against `GET /api/stacks/:id` (using `Api::StacksController#stack`, i.e. `stacks.from_param!`), which correctly returns 404/`RecordNotFound` for Stack B.
