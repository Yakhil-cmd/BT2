### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every handler acts on the repository derived from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/webhook secret used to verify `X-Hub-Signature` based on `repository_owner`, which is read from the JSON body itself: `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub Apps/organizations, each configured with its own independent `webhook_secret` in `secrets.yml`, selected by `Shipit.github(organization: ...)`. [3](#0-2) [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the *entire raw payload* to every registered handler for that event. [5](#0-4) 

Every handler, however, resolves *which repository/stack to act on* using a **different** field of the same payload: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Repository.from_github_repo_name`. [6](#0-5) [7](#0-6) 

This is used directly by, e.g., `PushHandler`, which triggers `stack.sync_github(expected_head_sha:)` for every non-archived stack of the resolved repository, [8](#0-7) 
and by `PullRequest::ClosedHandler`, which likewise resolves `repository` from `params.repository.full_name` independently of the signature-verifying owner. [9](#0-8) 

**The broken binding:** the signature cryptographically proves `signing_org == repository.owner.login`, but the code executes side effects on `Repository.from_github_repo_name(repository.full_name)`. Nothing ties `repository.owner.login` to `repository.full_name` — they are two independent attacker-supplied JSON fields inside the same signed body. An attacker who controls (or is an admin of) Organization A's GitHub App — and therefore legitimately knows Org A's `webhook_secret` and can produce validly-signed deliveries for Org A — can craft a payload where `repository.owner.login = "orgA"` (so `Shipit.github(organization: "orgA")` is selected and the HMAC verifies successfully) while `repository.full_name = "orgB/some-other-repo"`. The signature check passes (it validates against Org A's secret over the raw body, which is exactly the body the attacker constructed), and the handlers then look up and mutate Org B's `Stack` (sync commits, archive review stacks, process pull-request/merge events, etc.) even though Org B never authenticated this webhook and the request was never covered by an Org B secret.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository that is written." An operator of one onboarded GitHub organization/App can forge webhook deliveries (push, pull_request, status, check_suite, membership) that are processed as if they came from a completely different organization's repository, because only the `owner.login` sub-field is bound to the signature check while all mutation logic keys off the independent `full_name` field. This enables cross-repository/cross-organization writes to Shipit's state (stack sync, review-stack archival, commit status creation, continuous-deployment triggers) originating from an org that has no legitimate relationship with the targeted repository — a cross-repository write, which is a Critical-tier impact under the given rules.

### Likelihood Explanation
Exploitability requires only that the attacker control the webhook secret of *any one* organization/App configured in Shipit's `secrets.yml` (a normal, unprivileged capability for that org's own GitHub App admin) — no `ApiClient` token, `webhook_secret` of the target org, private key, or Shipit account privilege is needed. The multi-org configuration path is explicitly documented and supported. [10](#0-9) 
Because `repository_owner` and `repository_name` are parsed from two unrelated JSON paths with no cross-validation anywhere in `WebhooksController` or `Handler`, likelihood of a working forgery is high once an attacker has any valid organization secret.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, ensure the organization used to select the verifying secret is cryptographically tied to the repository actually acted upon: derive `repository_owner` from the same `full_name` field used by handlers (e.g., split `repository.full_name` rather than trusting `repository.owner.login` independently), or explicitly assert `repository.full_name.split('/').first == repository.owner.login` before dispatching to handlers, rejecting the webhook if they diverge.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s (per the documented multi-org setup). [10](#0-9) 
2. Attacker administers `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/target-repo"`
   - `ref`, `after` set to attacker-chosen values.
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and the HMAC check passes. [1](#0-0) 
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/target-repo")` and invokes `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack — despite the request never being signed by `orgB`. [8](#0-7) [6](#0-5)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
