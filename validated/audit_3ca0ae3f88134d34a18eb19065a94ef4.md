### Title
Release asset `name` from the GitHub API is joined into the download path with no traversal/absolute-path sanitization, allowing writes outside `--destination` - (File: pkg/cmd/release/download/download.go)

### Summary
`downloadRun` builds `downloadTarget{name: a.Name}` directly from `release.Assets[].Name` returned by the GitHub REST API, with no validation beyond a Windows-reserved-filename check. `destinationWriter.makePath` then does `filepath.Join(w.dir, name)`, which `Clean`s the joined path and permits `..` sequences to walk outside `opts.Destination`.

### Finding Description
The asset name flows unsanitized from the server response into the filesystem write path:
- `downloadRun` copies `a.Name` from `release.Assets` into `downloadTarget.name` [1](#0-0) 
- `downloadAsset` calls `dest.Check(fileName)` then `dest.Copy(fileName, resp.Body)` with that same attacker-controlled name [2](#0-1) 
- `makePath` performs a bare `filepath.Join(w.dir, name)` with no traversal, `..`, or absolute-path check [3](#0-2) 
- `Copy` uses that joined path directly for `os.MkdirAll` and `os.OpenFile`, writing attacker-supplied content to it [4](#0-3) 

The only pre-write validation on `a.Name` is the Windows-reserved-filename check, which does nothing for `..`-style traversal or absolute paths [5](#0-4) . There is no analog of `filepath.Base()` sanitization (which is applied only to the Content-Disposition-derived archive filename fallback, not to `a.Name`) [6](#0-5) .

By contrast, the sibling `gh run download` command explicitly guards against this exact class of attack: it uses `safepaths.Absolute` and `internal/zip.ExtractZip`, which the codebase's own test suite documents as erroring with `"would result in path traversal"` for a crafted artifact name of `".."` [7](#0-6) , and `downloadArtifact` routes writes through `safepaths.Absolute` rather than raw `filepath.Join` [8](#0-7) . `pkg/cmd/release/download/download.go` has no equivalent protection.

Existing tests for `gh release download` only cover benign asset names (e.g., `"windows-32bit.zip"`) written into `Destination` [9](#0-8) ; none test a malicious `name` containing `../` or an absolute path.

### Impact Explanation
An attacker who can publish a public/attacker-controlled repository release (no privileges required — anyone can create a public repo and publish a release) can set an asset's `name` field to a traversal payload (e.g., `"../../../../tmp/evil"`) or an absolute path. When the victim runs `gh release download` (with no `--pattern`, or a pattern that still matches the crafted name) against that repo, `gh` will write the asset's contents to the attacker-chosen path outside `--destination`, resulting in arbitrary file write/overwrite on the victim's machine. This matches GitHub's "file write/overwrite outside intended path" bounty impact class and, depending on target path (e.g., shell profile, cron file, SSH authorized_keys), can escalate to code execution.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to control the JSON `name` field of a release asset, which is fully attacker-controlled since GitHub does not appear to restrict special characters like `../` in asset display names returned via the API (the actual test harness constructs raw JSON for `"name"` directly, confirming assets are addressed purely by this field with no server-side path normalization enforced client-side). The victim simply needs to run `gh release download <tag>` (or without pattern restriction/with a matching pattern) against the malicious repo — a common, expected workflow.

### Recommendation
In `makePath` (or before calling `Check`/`Copy`), reject or sanitize asset names that are absolute paths or that, after `filepath.Clean`, contain `..` elements or resolve outside `w.dir`. Reuse the existing `internal/safepaths` package (already used by `gh run download`) to construct the destination path safely, or explicitly validate with something like: compute `filepath.Clean(filepath.Join(w.dir, name))`, verify it has `w.dir` (resolved) as a prefix, and reject/error otherwise (mirroring the "would result in path traversal" behavior used in `pkg/cmd/run/download`).

### Proof of Concept
Add a test analogous to the existing `"download assets matching pattern into destination directory"` case in `pkg/cmd/release/download/download_test.go`, but with a malicious asset name:

```go
{

    isTTY: true,

        TagName:     "v1.2.3",
        Destination: "tmp/assets",
        Concurrency: 1,
    },

            "assets": [
                { "name": "../../../evil.txt", "size": 4,
                  "url": "https://api.github.com/assets/1234" }
            ]
        }`)
        reg.Register(httpmock.REST("GET", "assets/1234"), httpmock.StringResponse(`pwn!`))
    },
    wantErr: "...", // expect an error such as "would result in path traversal"

```

Run this against current `downloadRun`/`destinationWriter.Copy` and observe that no error occurs and a file is written outside `tmp/assets` (e.g., at `tmp/evil.txt` or higher, depending on relative depth) — confirming the escape. After the fix, the same test should assert that `downloadRun` returns a path-traversal error and no file is created outside `opts.Destination`.

func (w destinationWriter) Copy(name string, r io.Reader) (copyErr error) {
	fp := w.makePath(name)
	if fp == "-" {
		if w.allowEscapes {
			_, copyErr = io.Copy(w.stdout, r)
			return
		}
		copyErr = iostreams.CopyGuardedContent(w.stdout, r, w.isTTY)
		if binErr, ok := errors.AsType[iostreams.BinaryTerminalError](copyErr); ok {
			copyErr = fmt.Errorf("%w; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway", binErr)
		} else if errors.Is(copyErr, iostreams.ErrEscapeSequence) {
			copyErr = errors.New("the asset contains terminal escape sequences; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway")
		}
		return
	}
	if copyErr = w.check(fp); copyErr != nil {
		return
	}

	if dir := filepath.Dir(fp); dir != "." {
		if copyErr = os.MkdirAll(dir, 0755); copyErr != nil {
			return
		}
	}

	var f *os.File
	if f, copyErr = os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644); copyErr != nil {
		return
	}
