### Title
Webhook signature verified against attacker's own organization's secret while the acted-upon repository/commit is taken from a different, unverified field of the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) directly out of the *unverified* JSON body. Once the HMAC checks out, the whole raw `params` hash — including other, independent fields such as `repository.full_name` and `sha` — is handed unchanged to the event handlers, which use those other fields to decide which `Stack`/`Repository`/`Commit` to act on. Nothing binds the “organization whose secret authenticated the request” to the “repository/commit that is actually written.” An attacker who legitimately controls one GitHub organization configured in Shipit (and therefore knows that organization's `webhook_secret`) can therefore forge a signature that Shipit accepts, while pointing the payload's `repository.full_name` (or, for `status` events, just a raw `sha`) at a completely different organization's stack/commit.

### Finding Description
`verify_signature` computes the verifying org purely from attacker-controlled JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to the `GitHubApp`/`webhook_secret` configured for that organization in `Shipit`'s multi-org configuration, and `verify_webhook_signature` performs a plain HMAC comparison against that secret and the raw body: [3](#0-2) 

Once verification passes, `create` dispatches the entire parsed body to the registered handlers unchanged: [4](#0-3) 

Handlers resolve the target repository from a *different* field of the same payload — `repository.full_name` — with no cross-check against the organization used to select the signing secret: [5](#0-4) [6](#0-5) 

`PushHandler` uses that repository lookup to trigger a real GitHub sync (`stack.sync_github`) using the app's own GitHub credentials for any stack matching the spoofed `full_name`: [7](#0-6) 

Even more directly, `StatusHandler` does not scope by repository at all — it looks up commits globally by `sha` and writes a forged CI status onto them: [8](#0-7) 

This is exactly the “organization that authenticated versus the repository that is written” binding called out as in-scope: the equality `organization_that_signed == organization_of_repository_acted_on` is never enforced. Before the attacker's request: `repository_owner` (used to pick the secret) and `repository.full_name`/`sha` (used to pick the target) are supposed to refer to the same GitHub repository. After the attacker's crafted request: `repository_owner` = attacker's own org (whose secret they know), while `repository.full_name`/`sha` reference an unrelated victim org's stack/commit — and the code never checks that these agree.

### Impact Explanation
An attacker who is an admin of, or otherwise controls the webhook secret for, any single GitHub organization configured in this Shipit instance can forge signed webhook deliveries that are processed as if they came from a completely different organization's repository:
- Via `PushHandler`, they can force out-of-band `sync_github` calls against another org's stacks.
- Via `StatusHandler`, because commit lookup is entirely unscoped by repository, they can inject a fabricated `success`/`failure` CI status onto any commit sha in the system, including commits belonging to stacks they have no access to. If those stacks use continuous deployment or status-gated merge/deploy checks, this can lead to an unauthorized deploy of a commit whose CI status was forged.

This matches the High/Critical impact bar (“escalation into authorization boundaries” / “unauthorized deploy”), because it lets a party who is authorized only for organization B act on organization A's stacks/commits.

### Likelihood Explanation
Requires the attacker to control (own the `webhook_secret` of) at least one GitHub organization/App integration configured in the target Shipit deployment — a realistic scenario for any Shipit instance shared across multiple organizations (the engine explicitly supports a multi-org `github:` config, as shown in `config/secrets.development.shopify.yml`). No access to the victim organization, its repository, or any Shipit session/API token is required, satisfying the "unprivileged attacker across a trust boundary" requirement.

### Recommendation
After successfully verifying the HMAC signature for `repository_owner`, cross-check that every other repository-identifying field used by handlers (`repository.full_name`, `organization.login`, and the repository implied by any `sha` lookup) belongs to the same organization that authenticated the request. Reject the webhook if these disagree, and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits whose stack's repository matches the authenticated organization.

### Proof of Concept
1. Attacker registers/controls GitHub org `evilcorp`, which is configured in Shipit's `github:` multi-org secrets with its own `webhook_secret_evilcorp` (known to the attacker as the org owner).
2. Attacker crafts a `push` (or `status`) webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "evilcorp" }, "full_name": "victimcorp/prod-stack" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_evilcorp, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `repository_owner` → `"evilcorp"`, fetches `evilcorp`'s app, and the HMAC check succeeds because the attacker knows `evilcorp`'s secret. [1](#0-0) 
5. `create` dispatches the full payload to `PushHandler`, which resolves `stacks` via `payload.dig('repository', 'full_name')` = `"victimcorp/prod-stack"`, not `evilcorp`, and calls `stack.sync_github(...)` on a stack the attacker never owns. [5](#0-4) [7](#0-6) 
6. For the `status` event variant, the same signature bypass lets the attacker call `StatusHandler`, which matches purely on `sha` (no organization/repository check at all) and writes a forged status onto a victim commit. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
