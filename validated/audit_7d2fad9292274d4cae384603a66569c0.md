### Title
`InitializeBuffer` sets an unsigned, front-runnable buffer authority - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The `bpf_loader_upgradeable` program's `InitializeBuffer` instruction sets the `authority_address` of a buffer account from an instruction account that is **not required to sign**, and only checks that the buffer's current state is `Uninitialized`. Because account creation (`system_instruction::create_account`, assigning ownership to `bpf_loader_upgradeable`) and account initialization (`InitializeBuffer`) are two distinct instructions/transactions, any unprivileged transaction sender who observes a freshly-created, still-`Uninitialized` buffer account in the mempool (or simply races an address before the legitimate owner initializes it) can submit their own `InitializeBuffer` instruction first and claim the `authority_address` for themselves — analogous to the reported `PerpOwnable.transferPerpOwner` front-running bug.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

The buffer account (`accounts[0]`) only needs to be writable; it is not required to be a signer. The authority account (`accounts[1]`) is read purely as `get_key_of_instruction_account(1)` — there is **no `is_instruction_account_signer` check at all** for the authority in this branch, unlike every other authority-consuming branch in the same match statement (`Write`, `SetAuthority`, `SetAuthorityChecked`, `Close`/`common_close_account`), which do call `is_instruction_account_signer`: [2](#0-1) [3](#0-2) 

The only guard against re-initialization is the account's on-chain state:
```
if UpgradeableLoaderState::Uninitialized != buffer.get_state()? {
    return Err(InstructionError::AccountAlreadyInitialized);
}
```
This is a state check, not an access-control check — it prevents double-initialization but does not verify who is allowed to perform the first initialization. Since the buffer account becomes `Uninitialized`/owned-by-`bpf_loader_upgradeable` at the moment `system_instruction::create_account` is confirmed (a separate instruction requiring only the buffer keypair's signature for account creation, not for `InitializeBuffer`), there exists a window between "buffer account created and owned by the loader" and "buffer account initialized with the intended authority" during which **any transaction sender** can submit `InitializeBuffer` naming themselves as `authority_address`, exactly the same "unprotected one-time setter" pattern described in the external report for `PerpOwnable.transferPerpOwner`.

Once the attacker becomes the buffer's authority, every subsequent operation that requires the correct authority to sign — `Write` (to populate program bytes), `SetAuthority`/`SetAuthorityChecked`, and `Close` (which redirects the buffer's entire lamport balance to an attacker-chosen recipient) — is now gated on the attacker's key instead of the legitimate deployer's: [4](#0-3) [5](#0-4) 

This effectively denies the deployer control over their own buffer and lets the attacker either grief (permanently locking or bricking the buffer, blocking `DeployWithMaxDataLen`/`Upgrade`) or drain its rent-exempt lamports via `Close` to an address of the attacker's choosing.

### Impact Explanation
An unprivileged attacker who submits a single, ordinary transaction (`InitializeBuffer` on a target buffer account that is still `Uninitialized`) can:
- Hijack the buffer's authority, blocking the legitimate deployer's `Write`/`Upgrade`/`DeployWithMaxDataLen` flow (denial of service on program deployment), and
- Reclaim the buffer's lamports to their own account via `Close`, an unsigned/unauthorized fund movement from the victim's perspective (the deployer paid the rent-exempt reserve for the account but never controls it).

This matches the "concrete unsigned fund movement" and reachable-from-a-single-submitted-transaction bar, since `InitializeBuffer` requires no signature check on the authority account and is directly reachable by any transaction sender against any account they can observe as `Uninitialized` and owned by `bpf_loader_upgradeable`.

### Likelihood Explanation
Exploitation requires only (a) knowledge of a target buffer address before its intended authority initializes it, and (b) submitting a competing `InitializeBuffer` transaction with a higher priority fee/earlier slot placement — a routine front-running technique, identical in spirit to the exploit scenario described in the external report. Buffer addresses are frequently generated deterministically or observable in the mempool as part of program deployment tooling, and the create-then-initialize pattern (two separate instructions) is exactly the pattern the report warns about. I was not able to fully confirm from the indexed code whether the CLI (`cli/src/program.rs`) always bundles `create_account` and `InitializeBuffer` into a single atomic transaction (which would close the front-running window for the CLI's own flow) — the `solana_loader_v3_interface::instruction::create_buffer` helper itself lives outside this repo's indexed sources, so I could not verify its internals here. Regardless, the on-chain instruction handler itself provides no protection independent of client-side bundling, so any caller (custom tooling, other programs via CPI, or a differently-sequenced transaction) that separates account creation from `InitializeBuffer` is exposed.

### Recommendation
Require the buffer account itself (or a designated authority already bound at account-creation time, e.g., via a PDA/seed derivation or a mandatory co-signature) to sign `InitializeBuffer`, consistent with how `Write`, `SetAuthority`, `SetAuthorityChecked`, and `Close` already require signer checks on their authority accounts. At minimum, add an `is_instruction_account_signer` check on the authority account index in the `InitializeBuffer` branch so that only the party who actually controls (or co-signs with) the buffer/authority key can set the initial authority, closing the front-run window described here.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, buffer_pubkey, lamports, size, owner=bpf_loader_upgradeable::id())`, signed by `buffer_keypair`. This transaction lands, leaving `buffer_pubkey` owned by `bpf_loader_upgradeable` in state `Uninitialized`.
2. Before the victim's follow-up `InitializeBuffer(buffer_pubkey, victim_authority)` transaction lands, an attacker observing the mempool/account state submits their own transaction:
   ```
   Instruction::new_with_bincode(
       bpf_loader_upgradeable::id(),
       &UpgradeableLoaderInstruction::InitializeBuffer,
       vec![
           AccountMeta::new(buffer_pubkey, false),
           AccountMeta::new_readonly(attacker_pubkey, false), // no signature required
       ],
   )
   ```
   with a higher fee/earlier landing slot, per the handler at [1](#0-0) .
3. The buffer's state becomes `Buffer { authority_address: Some(attacker_pubkey) }`. The victim's own subsequent `InitializeBuffer` now fails with `AccountAlreadyInitialized` [6](#0-5) .
4. The attacker can now call `Write` to overwrite the buffer contents, or `Close` (signing as `attacker_pubkey`) to redirect all lamports in the buffer account to any recipient they choose [7](#0-6) , denying the victim any control over the account they paid to create.

fn common_close_account(
    authority_address: &Option<Pubkey>,
    instruction_context: &InstructionContext,
    log_collector: &Option<Rc<RefCell<LogCollector>>>,
) -> Result<(), InstructionError> {
    if authority_address.is_none() {
        ic_logger_msg!(log_collector, "Account is immutable");
        return Err(InstructionError::Immutable);
    }
    if *authority_address != Some(*instruction_context.get_key_of_instruction_account(2)?) {
        ic_logger_msg!(log_collector, "Incorrect authority provided");
        return Err(InstructionError::IncorrectAuthority);
    }
    if !instruction_context.is_instruction_account_signer(2)? {
        ic_logger_msg!(log_collector, "Authority did not sign");
        return Err(InstructionError::MissingRequiredSignature);
    }

    let mut close_account = instruction_context.try_borrow_instruction_account(0)?;
    let mut recipient_account = instruction_context.try_borrow_instruction_account(1)?;

    recipient_account.checked_add_lamports(close_account.get_lamports())?;
    close_account.set_lamports(0)?;
    close_account.set_state(&UpgradeableLoaderState::Uninitialized)?;
    Ok(())
