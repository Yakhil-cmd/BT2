### Title
Webhook signature validated against attacker's own organization while stack actions are keyed to a different repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using the organization name found in the payload itself, but nothing binds that same organization to the repository that the subsequently-invoked handlers act upon.

### Finding Description
`verify_signature` derives the signing key via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the untrusted, attacker-suppliable JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)`/`GitHubApp#verify_webhook_signature` then HMACs the raw body with the `webhook_secret` configured for *that organization only*, using `Shipit::SecureCompare.secure_compare`. Shipit explicitly supports multi-tenant configuration where each GitHub organization has its own `webhook_secret`, `app_id`, and `private_key`. [3](#0-2) [4](#0-3) 

Once `verified` is true, `create` parses the same body and dispatches it to all registered handlers for the event type with no re-check that the organization used for verification matches any org/repository the handler will actually touch: [5](#0-4) 

The binding that should hold is: `organization used to select webhook_secret == organization that owns the repository the handler mutates`. Because `repository_owner` (used for verification) and `repository.full_name` (used by handlers such as the push handler to look up/act on a `Stack`) are both attacker-controlled fields inside the same JSON body, an attacker who is a legitimate GitHub org admin/webhook operator for **their own** organization (and therefore knows/controls their own org's `webhook_secret`) can forge a payload where `repository.owner.login` is set to their own org (so the HMAC check passes using their own secret) while `repository.full_name` names a different, victim organization's repository. I was not able to fully verify the exact field used by the push/status/check_suite handlers to resolve the target `Stack` (`app/models/shipit/webhooks/handlers/push_handler.rb` and `handler.rb` contents could not be retrieved before the tool budget ran out), so I cannot confirm with certainty that the handler-side repository lookup is independent of `repository_owner` rather than re-deriving the same value.

### Impact Explanation
If confirmed, this would let an attacker with only "unprivileged" webhook-signing capability for their own tenant organization forge push/status/check_suite events attributed to a repository belonging to a different tenant, causing Shipit to enqueue `GithubSyncJob`, update commit statuses, or otherwise mutate the state of stacks the attacker does not control — a cross-repository write / unauthorized action on someone else's deploy pipeline.

### Likelihood Explanation
This requires the deployment to use the multi-organization `github:` config format (explicitly documented and shipped as a supported configuration) and requires the attacker to already control a legitimate webhook secret for at least one configured organization. This is a real, but narrower, prerequisite than a fully anonymous attacker, and I could not verify the handler-side lookup logic to confirm exploitability, so this should be treated as unconfirmed pending direct inspection of `app/models/shipit/webhooks/handlers/push_handler.rb` and `handler.rb`.

### Recommendation
In `verify_signature`, and in each handler that resolves a `Stack`/`Repository`, re-derive the organization from the same field for both signing and target-selection (e.g., always use `repository.full_name`'s owner segment consistently), and reject events where the organization implied by `repository.full_name` does not match the organization whose secret validated the signature.

### Proof of Concept
Not able to construct a concrete, fully-verified PoC within the available tool budget — `app/models/shipit/webhooks/handlers/push_handler.rb` and `app/models/shipit/webhooks/handlers/handler.rb` (which resolve the `Stack` from webhook payload data) could not be read before the iteration limit was reached, so the exact field used for repository resolution downstream of `verify_signature` is unconfirmed.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
