### Title
Webhook status/push events are authorized by organization but applied by repository full_name, allowing cross-tenant forged commit statuses and unauthorized deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the organization derived from `repository.owner.login` (or `organization.login`) inside the payload, but the handlers that actually act on that same payload (`StatusHandler`, `PushHandler`) select which `Commit`/`Stack` to mutate using unrelated fields (`sha` globally, or `repository.full_name`). Nothing binds the authenticated organization to the repository/commit that is ultimately written to.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This only proves the raw POST body was HMAC-signed with the webhook secret configured for *some organization present as a value inside the JSON body*. It does not prove that the `repository.full_name` field (owner/repo pair actually acted upon) matches that organization, because HMAC verification of the whole body doesn't constrain the *semantic relationship between two independent JSON fields* — an attacker who legitimately controls the webhook secret for one organization (`OrgA`, e.g. because they administer their own Shipit-tracked repo/app) can freely construct a JSON body where `repository.owner.login = "OrgA"` (satisfies signature-org lookup) while `repository.full_name = "OrgB/victim-repo"` (a completely different, unrelated tenant repository tracked by the same Shipit instance).

Downstream, `Handler#repository_name` uses only `full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and `PushHandler#process` triggers a `GithubSyncJob` on whatever stacks match that `full_name`: [4](#0-3) 

Worse, `StatusHandler` doesn't even consult `repository` at all — it matches commits **globally by sha across every stack in the installation**:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`create_status_from_github!` writes a real `Status` record that feeds `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [6](#0-5)  and schedules continuous delivery when the resulting status is successful [7](#0-6) .

The binding that should hold but doesn't: **organization authenticated by `verify_signature` == organization that owns the repository/stack actually written by the handler**. Because `repository_owner` and `repository_name`/`sha` are independent, attacker-controlled fields inside the same signed JSON body, an entity holding a valid webhook secret for *any* organization configured in this multi-tenant Shipit instance can forge a `status` webhook naming an arbitrary commit `sha` belonging to *any other organization's stack*, and have it accepted as a genuine, successful CI status.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly relevant to this engine's trust model. A tenant with only their own organization's webhook secret can:
- Forge a passing `Status` for an arbitrary commit `sha` in a completely different stack/repository they do not administer, satisfying `ci.require`/`deployable?` checks.
- Combined with `schedule_continuous_delivery`, this can trigger an unauthorized deploy of a victim stack that has continuous deployment enabled, since the forged successful status makes the commit `deployable?` and continuous delivery is scheduled automatically.
- For `push`, the same mismatch lets a party with an unrelated org's secret enqueue `GithubSyncJob` for a stack keyed to `repository.full_name` of a different organization.

This satisfies the "unauthorized deploy" criterion in the High/Critical impact bar.

### Likelihood Explanation
Requires the attacker to already hold a legitimate webhook secret for *some* organization/repository configured in the same shared Shipit instance (a realistic scenario in any multi-tenant deployment, e.g. a large company running one Shipit for many teams/orgs). No GitHub App private key, Shipit session, or API token is required — only the ability to send a raw HTTP POST with a validly-HMAC-signed body using a secret they legitimately possess for their own tenant. This is a plausible and moderately likely attack path for shared/multi-org Shipit deployments.

### Recommendation
- Bind the verified organization to the actual repository being acted upon: after signature verification, re-derive the repository/stack strictly from `repository.full_name` and reject/verify that its owner matches the organization used to look up the webhook secret.
- In `StatusHandler`, scope commit lookup by repository (`stacks` from `Handler#repository_name`) rather than a bare global `Commit.where(sha:)` lookup, so status events can only affect commits within the repository whose organization was authenticated.
- Similarly ensure `PushHandler`/other handlers validate that the `repository.owner.login` used for signing matches the `repository.full_name` owner before acting.

### Proof of Concept
1. Attacker administers `OrgA`, a real organization tracked by this shared Shipit instance, and knows `OrgA`'s configured `webhook_secret`.
2. Attacker crafts a JSON body for a `status` event:
   ```json
   {
     "sha": "<victim-commit-sha-in-OrgB-stack>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over the raw JSON body and POSTs it to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `OrgA`'s webhook secret, and the signature verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit belonging to `OrgB`'s stack regardless of `repository.full_name` — and creates a `success` status on it via `create_status_from_github!`.
6. If `OrgB`'s stack has `continuous_deployment: true` and no other blocking statuses, `Commit#deployable?` now returns true and `schedule_continuous_delivery` enqueues a deploy of `OrgB`'s stack, entirely triggered by an attacker who only had `OrgA`'s webhook secret.
