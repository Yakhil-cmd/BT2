## Analysis

The **bug class** in the source report is a rounding/consistency mismatch: one field (`block.timestamp`) drives the calculation, but the mutation afterwards updates state as if the calculation matched a different quantity, silently decoupling "what was authorized" from "what was recorded/acted upon."

The same class of defect exists in `Shipit::WebhooksController` and its handlers: signature verification is anchored to one payload field (`repository.owner.login` / `organization.login`), while the code that actually mutates state operates on a *different, unchecked* field — in one handler, with **no repository scoping at all**.

### Root cause

`verify_signature` selects which organization's `webhook_secret` is used to validate the HMAC based on `repository.owner.login` (or `organization.login` as a fallback): [1](#0-0) [2](#0-1) 

`Shipit::Webhooks::Handlers::StatusHandler#process`, however, never consults `repository` at all — it looks up commits **globally by SHA** across every stack/repository tracked by the Shipit instance: [3](#0-2) 

Compare this to the base `Handler` class, which *does* define a `repository_name`/`stacks` scoping helper — but `StatusHandler` doesn't use it: [4](#0-3) 

Other handlers (push, pull_request family) do scope by `repository.full_name`, but that field is a second, independently-attacker-controlled JSON key never cross-checked against `repository.owner.login`, which is the field actually used to pick the verifying secret: [5](#0-4) [6](#0-5) 

### Binding broken

`organization authenticated (repository.owner.login → webhook_secret used) == repository/commit acted upon (repository.full_name / bare commit.sha)`

This equality is never enforced. Any org/repo onboarded to a multi-tenant Shipit instance can forge events for **any other** org/repo also onboarded to the same instance, as long as the attacker legitimately administers one webhook endpoint (i.e., knows the `webhook_secret` they themselves configured for their own org in GitHub's webhook settings — this is normal repo-owner configuration, not a Shipit credential, ApiClient token, or GitHub App key, and thus not excluded by the ruleset).

The `StatusHandler` case is the most severe: because `Commit.where(sha: params.sha)` has zero repository scoping, an attacker with a valid signature for *their own* organization can forge a `status` webhook for a commit SHA that exists in a *different* tracked repository (SHAs are public GitHub data), setting `state: "success"`. Since commit statuses gate Shipit's merge queue and deployability checks, this can cause an **unauthorized merge/deploy** for a commit the attacker never had CI access to validate.

### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but handlers act on unscoped/mismatched fields (`repository.full_name`, bare commit `sha`) — cross-repository status/state forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC-verifying `webhook_secret` using `repository.owner.login` (falling back to `organization.login`), but the event handlers that subsequently mutate application state key off different, uncross-checked payload fields — `repository.full_name` in most handlers, and nothing at all (a bare `sha`) in `StatusHandler`. The verified identity and the acted-upon resource are never proven to be the same entity.

### Finding Description
`verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the untrusted JSON body [1](#0-0) , and this only proves the byte string was HMAC-signed with *that org's* configured secret. Downstream, `StatusHandler#process` updates `Commit` records purely by `sha`, with no repository filter whatsoever [3](#0-2) , and other handlers resolve the target repository from `repository.full_name`, a completely separate JSON key from `repository.owner.login` that is never validated to be consistent with it [6](#0-5) [5](#0-4) . An attacker who legitimately administers any single org onboarded to the same multi-tenant Shipit instance (and thus knows the secret they typed into GitHub's own webhook settings for that org — not a Shipit-issued credential) can sign a payload with their own secret while setting `repository.full_name`/`sha` to reference a completely different, victim org's stack/commit.

### Impact Explanation
Forging a `status` event with `state: "success"` for a known public commit `sha` belonging to a victim repository lets an attacker mark that commit's CI/status checks as passing in Shipit, without any relationship to the victim repository's real CI, potentially allowing that commit to satisfy Shipit's merge-queue/deployability gating — an unauthorized merge/deploy path, which matches the required Critical-impact category.

### Likelihood Explanation
Requires the attacker to control at least one org/repo already onboarded onto the same Shipit deployment (multi-tenant `github_apps`/organizations config) and knowledge of a target commit's SHA (public on GitHub). No Shipit session, ApiClient token, or GitHub App private key is required — only a legitimate webhook secret the attacker themselves configured for their own org.

### Recommendation
In `WebhooksController#verify_signature` and all `Shipit::Webhooks::Handlers`, require that the org used to select the verifying secret matches the owner segment of `repository.full_name` used by handlers, and have `StatusHandler` (and any other handler) scope its lookup through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching `Commit` records, exactly as the base `Handler#stacks` helper already does.

### Proof of Concept
1. Attacker legitimately owns `org-attacker/some-repo`, configures a GitHub webhook to Shipit's endpoint with secret `S` (matches `Shipit.github(organization: 'org-attacker')`'s `webhook_secret`).
2. Attacker crafts a `status` event JSON body: `{"sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "org-attacker"}, ...}}`, computes `X-Hub-Signature` with secret `S`.
3. POSTs to the webhook endpoint; `verify_signature` resolves `repository_owner = "org-attacker"`, validates HMAC successfully against `S` [7](#0-6) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — since this is unscoped by repository, it matches the victim's commit record in a completely unrelated stack and writes a forged "success" status onto it [3](#0-2) .
