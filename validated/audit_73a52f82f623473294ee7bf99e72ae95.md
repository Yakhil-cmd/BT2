### Title
Unallowlisted route hops can join the caller's authorization tree and drain wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept a caller-supplied opaque route and invoke the configured router while the user's `require_auth` tree is active. The controller narrows only its own token grant to one exact input transfer, but it does not constrain contracts invoked beneath the router. A crafted route can therefore include a venue contract that calls `token.transfer(victim, attacker, amount)` on an unrelated wallet token. Simulation records that transfer as a child of the victim's controller authorization; if the victim signs the recorded tree, the unrelated wallet transfer executes even though the swap's measured output and final account checks pass.

### Finding Description
The controller authorizes only `token_in.transfer(controller, router, amount_in)` for its own input leg, then invokes `router.execute_strategy(&controller, &amount_in, swap)` inside `swap_tokens`. [1](#0-0)  The opaque `StrategySwap` payload is not decoded or venue-allowlisted by the controller, and the threat model explicitly states that the router keeps no allowlist of pool or token addresses it calls. [2](#0-1) 

Soroban authorization is tree-based rather than limited to the router's expected token transfer. A nested venue can request authorization from the original caller, and simulation records that request under the caller's root controller invocation. The regression test demonstrates a router-selected hop calling `transfer(victim, attacker, WALLET_BALANCE)` while still paying a fair output. [3](#0-2)  In enforcing mode, the same malicious transfer succeeds when the signed tree contains that child invocation. [4](#0-3) 

### Impact Explanation
A crafted route can steal arbitrary tokens held by the transaction signer, including assets never supplied to or listed by the lending protocol. The theft is not bounded by `amount_in`, the route's declared minimum output, measured output, collateral checks, or the final account health check. The protocol can still deliver a valid swap output, leaving the account solvent while an unrelated token transfer drains the user's wallet. This is theft of user funds by a remote attacker supplied with a crafted route, analogous to code execution triggered by crafted WebKit content.

### Likelihood Explanation
Exploitation requires the victim to submit and sign a malicious route, but route construction is normally delegated to wallets or frontends. Simulation can make the malicious child authorization look like part of the normal swap authorization tree, and the controller provides no on-chain venue allowlist or payload inspection to distinguish it. Every router-backed strategy path shares this shape because all funnel through the same `swap_tokens` helper.

### Recommendation
Constrain routed execution to an allowlisted venue/interface set or encode routes in a controller-validated type that cannot name arbitrary contracts. At minimum, reject routers capable of making arbitrary nested calls or use a router design that isolates venue callbacks from the caller's authorization context. Client-side defenses should additionally decode the complete simulated authorization tree and reject any child invocation other than the expected controller token transfer.

### Proof of Concept
A malicious route payload names an attacker-controlled pool. During `router.execute_strategy`, the router invokes that pool. The pool executes:

```rust
token::Client::new(&env, &unrelated_wallet_token).transfer(
    &victim,
    &attacker,
    &wallet_balance,
);
```

This is the production-reachable shape demonstrated by `RogueHopPool::swap`; the test stores the victim, token, recipient, and amount and performs that token transfer inside a route hop. [5](#0-4)  Simulation records the transfer beneath the victim's `swap_collateral` authorization and drains the unrelated wallet token. [6](#0-5)  When the victim signs the recorded tree, enforcement accepts the child transfer and the wallet balance moves to the attacker. [4](#0-3)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
