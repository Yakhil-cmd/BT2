### Title
Unbounded private-payment chain length has no size limit, allowing DoS-level validation cost on every recipient/hub - ([File: indivisible_asset.js])

### Summary
Indivisible (blackbytes-style) private assets are transferred as an ever-growing, append-only chain of hidden "private elements," each referencing the previous one back to the original issuance. Unlike public payments (which cap `inputs`/`outputs` per message via `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE`, see `validation.js` `validatePaymentInputsAndOutputs`), there is **no limit anywhere on the length of `arrPrivateElements`** (the private-payment chain). Any holder of a private coin can re-spend it to themselves or anyone else an arbitrary number of times, and every subsequent recipient, cosigner, or hub must revalidate/re-walk the **entire** chain back to issuance, with the cost of validation and chain-reconstruction growing linearly (or worse) without bound.

### Finding Description
The private-payment chain-validation logic in `indivisible_asset.js` and `private_payment.js` processes `arrPrivateElements` — an array supplied by the counterparty — with no upper bound check on its length:

- `parsePrivatePaymentChain` in `indivisible_asset.js` iterates the full array with `async.forEachOfSeries`, calling `validatePrivatePayment` (which itself does DB queries for `spend_proofs` and calls `validation.validatePayment`) for **every element** of the chain: [1](#0-0) 
- `validateAndSavePrivatePaymentChain` then loops again over the entire chain to persist inputs/outputs: [2](#0-1) 
- `buildPrivateElementsChain` reconstructs the whole chain by recursively walking backward from the current output to the original `issue` input via `readPayloadAndGoUp`, with unbounded recursion depth (no depth counter, no cap): [3](#0-2) 
- On the network side, `handleOnlinePrivatePayment` / `handleSavedPrivatePayments` in `network.js` accept an attacker/counterparty-supplied `arrPrivateElements` array and hand it directly to the validator, with only a non-empty-array check — no maximum-length check: [4](#0-3) 
- `wallet.js`'s `handlePrivatePaymentChains` (used when a hub relays chains between devices) likewise validates only the shape of each element (`isNonemptyObject`, has `unit`, `payload.asset`, `inputs`, `outputs`) but never bounds `c.length` (the chain length) before running validation on every chain, once per hub-relayed message: [5](#0-4) 

Because private, fixed-denomination assets are spent by revealing (unblinding) a chain of `spend_proof`s tracing back to issuance, and because nothing prevents a coin holder from transferring the coin to themselves (or through many hops) an unbounded number of times, this is the direct structural analog of the "append only" bug class: the chain of hidden payments can only grow (there is no mechanism to checkpoint, prune, or cap it), and every future recipient/hub/cosigner who needs to accept, forward, or re-validate that coin must pay the full, ever-increasing validation cost — exactly like the reported unbounded `latestProtocolId`/`vaultWhitelist` iteration that has "no way to remove" entries and is walked in a loop on every subsequent operation.

### Impact Explanation
An unprivileged private-payment counterparty (any user who receives a private indivisible-asset coin) can construct an arbitrarily long private-payment chain purely by repeatedly transferring the same coin between addresses they control, then hand the resulting long chain to a victim (a wallet, a hub relaying `wallet.js`'s `handlePrivatePaymentChains`, or a peer via `network.js`'s `handleOnlinePrivatePayment`). Each recipient/hub is then forced to:
1. Walk/validate every element of the chain (`parsePrivatePaymentChain`), each step performing DB lookups (`spend_proofs`) and full payment validation (`validation.validatePayment`), and
2. In light mode, request and validate link proofs for every element of the chain (`checkThatEachChainElementIncludesThePrevious`), leaking that the light vendor is a party to the full history and multiplying network round-trips.

This can degrade hub/node responsiveness and stall private-payment processing for other users (mutex-serialized `handleSavedPrivatePayments`), and in extreme cases (very deep recursive chain rebuilding in `buildPrivateElementsChain`) risks resource exhaustion. This matches the allowed impact category "a network unable to confirm new units" / node/hub inability to keep up with valid traffic due to unbounded per-message computation cost, triggered entirely by unprivileged private-payment counterparties.

### Likelihood Explanation
Likelihood is Medium: constructing a long private chain costs the attacker only their own transaction fees for self-transfers (no special privileges required), and the resulting chain can be sent to any hub or peer that processes private payments. It does not by itself break consensus/double-spend guarantees (each hop is still individually validated correctly), so the primary effect is denial-of-service/resource-consumption on validators rather than fund loss, which is why this is rated Medium rather than High/Critical.

### Recommendation
Introduce and enforce an explicit maximum length for `arrPrivateElements` (the private-payment chain) at the earliest possible validation point in `private_payment.js`'s `validateAndSavePrivatePaymentChain`, `network.js`'s `handleOnlinePrivatePayment`, and `wallet.js`'s `handlePrivatePaymentChains`, similar to the existing `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_OUTPUTS_PER_PAYMENT_MESSAGE` caps used for public payments. Additionally, add an explicit depth/iteration cap inside `buildPrivateElementsChain`'s recursive `readPayloadAndGoUp` to avoid unbounded recursion when a node itself needs to reconstruct a chain from local data.

### Proof of Concept
1. Issue a small amount of a fixed-denomination private (indivisible) asset to address `A` (via `composeIndivisibleAssetPaymentJoint`/definition with `is_private: 1`, `fixed_denominations: true`).
2. From `A`, repeatedly self-transfer the same coin through a long sequence of controlled addresses `A → A1 → A2 → … → An` (n large, e.g. tens of thousands), each hop a normal private payment message, producing `n` private elements in the resulting chain.
3. Send the final coin (and the full `arrPrivateElements` chain of length `n`) to a victim wallet/hub, e.g. via `wallet.js`'s `sendPrivatePayments`/`handlePrivatePaymentChains` path or directly via `network.js`'s `light/post_...`/`handleOnlinePrivatePayment` path.
4. Observe that the victim's `parsePrivatePaymentChain` (indivisible_asset.js:187-236) must sequentially validate all `n` elements — each with its own DB query and `validation.validatePayment` call — and, if light, must also fetch and validate `n` link proofs via `checkThatEachChainElementIncludesThePrevious` (network.js:2666-2691), causing processing time and DB/network load to scale linearly with attacker-chosen `n`, with no enforced upper bound anywhere in the call path.

					throw Error("readPayloadAndGoUp: input address is NULL");

					throw Error("building chain: asset mismatch");
