Based on my investigation, ocore's address-definition op `attested` has an unbounded attestor-list check that lacks the per-element complexity accounting that sibling ops apply, unlike other reference-based ops in the same file.

### Title
Unbounded `arrAttestors` list in `attested` address-definition op bypasses per-element complexity metering, enabling cheap-to-post, expensive-to-verify definitions - (File: definition.js)

### Summary
In `Definition.validateDefinition`, the `attested` op validates an arbitrarily long `arrAttestors` array with only O(n) local string checks and a single flat `complexity++`/`count_ops++` increment for the whole op, whereas the structurally identical `in data feed` and `in merkle` ops explicitly add `complexity += arrAddresses.length-1` for each additional address in their oracle-address arrays. [1](#0-0) [2](#0-1) 

### Finding Description
`validateDefinition`'s `evaluate()` charges a flat `complexity++` and `count_ops++` per op occurrence, and caps totals at `constants.MAX_COMPLEXITY` (100) and `constants.MAX_OPS` (2000). [3](#0-2) 
For `in data feed` and `in merkle`, the array of oracle addresses (`arrAddresses`) is explicitly priced per element via `complexity += arrAddresses.length-1`, so a large oracle-address list consumes proportional complexity budget and is bounded by `MAX_COMPLEXITY`. [4](#0-3) [5](#0-4) 
The `attested` op, however, only validates that `arrAttestors` is a non-empty array and every element is a valid address in a plain `for` loop, without any per-element complexity charge or length cap: [1](#0-0) 
Because complexity is metered per-op rather than per-array-element, an attacker can define an address (or asset condition) whose definition contains `['attested', [addr, [attestor1, attestor2, ..., attestorN]]]` with N unbounded (only limited by `MAX_UNIT_LENGTH`, 5 MB, and `MAX_OPS`=2000 total ops for the whole tree), i.e. effectively tens of thousands of attestor addresses in a single op while still costing only 1 complexity point and 1 op count.

This same array is later used, every time the address is used to sign a unit or the asset condition is evaluated, in `validateAuthentifiers`'s runtime `evaluate()`, which passes the full `arrAttestors` list straight into `storage.filterAttestedAddresses(conn, {arrAttestorAddresses: arrAttestors}, ...)`: [6](#0-5) 
Every node that re-validates a unit signed by such an address (which happens on every full and light node during unit propagation, and again on every re-evaluation when a referenced inner address/asset condition changes) must run this DB-backed check against the oversized attestor list on every incoming unit from that address, repeatedly, for the life of the definition — a single crafted, low-complexity-scoring definition creates outsized, repeated per-unit validation cost network-wide.

### Impact Explanation
This is a reachable-by-anyone DoS vector: any unprivileged unit poster can define (or use as an asset's spend condition) an address whose definition contains an `attested` clause with a very large attestor array, at a one-time authoring cost bounded mainly by unit size (up to 5 MB), while every subsequent signed unit from that address forces all validating full/light nodes to process/query against the oversized array during standard unit validation (`validateAuthentifiers` → `evaluateAssetCondition`/author validation, called from `validateAuthors`/`validateMessage` in `validation.js`). Because the complexity/op-count anti-spam mechanism that is supposed to bound exactly this kind of cost (as it does for `in data feed`/`in merkle`) is not applied here, the attacker's cost-to-impose-cost ratio is disproportionate. This causes a node-wide validation slowdown when processing units from/associated with the crafted address/asset — a form of unbounded-loop/anti-spam-bypass DoS.

### Likelihood Explanation
Medium likelihood: `attested` is a documented address-definition op, requires only creating an address definition and posting one unit using it (or referencing it as an asset spend condition), and the missing complexity-per-attestor accounting is a clear asymmetry versus the two adjacent ops (`in data feed`, `in merkle`) that already implement the correct pattern in the same function, indicating the omission is a genuine gap rather than an intentional design choice.

### Recommendation
In the `attested` case of `Definition.validateDefinition`'s `evaluate()`, add per-element complexity accounting analogous to `in data feed`/`in merkle`, e.g. `complexity += arrAttestors.length - 1;` after validating the array, and/or introduce an explicit `MAX_ATTESTORS_PER_ADDRESS_DEFINITION`-style cap on `arrAttestors.length` (mirroring `constants.MAX_ATTESTORS_PER_ASSET`, already used for `checkAttestorList`) so that the attestor list in address/asset conditions is bounded independent of overall op-count/complexity budget tricks.

### Proof of Concept
1. Craft an address definition: `['attested', ['SOME_ADDRESS', [attestor_addr_1, attestor_addr_2, ..., attestor_addr_N]]]` wrapped in a valid `sig`-containing branch (e.g. `['and', [['sig', {...}], ['attested', [...]]]]`), with N chosen so total unit size stays under `MAX_UNIT_LENGTH` (5 MB) — tens of thousands of valid-looking BASE32 addresses fit easily.
2. Post a unit defining this address (or an asset with this as its spend/transfer condition) — `validateDefinition` accepts it because complexity only increments by 1 for the whole `attested` op regardless of N, and `count_ops` similarly only increments by 1, well under `MAX_OPS` (2000). [1](#0-0) 
3. Post a follow-up unit signed by/spending from that address; every node validating it invokes `validateAuthentifiers` → the runtime `attested` branch, which calls `storage.filterAttestedAddresses` with the full N-element `arrAttestorAddresses` array on every validation pass. [6](#0-5) 
4. Repeat with further units from the same address (or units referencing the asset condition) to repeatedly impose the oversized-list-processing cost on all validating nodes at negligible incremental cost to the attacker.
