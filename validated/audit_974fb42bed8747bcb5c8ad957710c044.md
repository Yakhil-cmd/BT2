### Title
Reachable "impossible-state" assertion (`throw Error`) in payment-input validation crashes the node — Denial of Service on unit confirmation - (File: validation.js)

### Summary
The external report describes an OpenLDAP flaw where a maliciously crafted, but syntactically processed, value triggers a failed internal assertion (`csnNormalize23()`), crashing the ldap server and denying service. The equivalent bug class in `ocore--002` is the pattern of `throw Error(...)` statements embedded inside the untrusted-unit validation pipeline that are meant to guard "impossible" internal invariants, combined with a global `process.on('uncaughtException', …)` handler that deliberately re-throws to kill the whole node process. [1](#0-0) 

### Finding Description
`validation.validate()` is the single entry point that processes every unit received from the network, from a light client, or posted directly (`handlePostedJoint`/`handleOnlineJoint`/`handleSavedJoint` all funnel into `handleJoint()` → `validation.validate()`). [2](#0-1) [3](#0-2) 

Deep inside the payment-input validation path (`validatePaymentInputsAndOutputs`), when a `transfer` input references a previously-seen source output, the code queries the DB for that output and then asserts several conditions that are assumed to be structurally impossible, e.g.:
```
if (rows.length > 1)
    throw Error("more than 1 src output");
...
if (bStableInParents) {
    if (src_output.sequence === 'temp-bad')
        throw Error("spending a stable temp-bad output " + input.unit);
``` [4](#0-3) 

These are `throw`s, not `callback(error)` calls — i.e. they are not treated as ordinary "unit is invalid" outcomes reported back through `ifUnitError`/`ifJointError`. Because `validate()` runs inside `async.series`/`async.eachSeries` callback chains with no enclosing `try/catch` around this specific branch, an uncaught throw here propagates out of the event-loop tick and is caught only by the global handler:
```
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [1](#0-0) 

This mirrors the OpenLDAP bug-class exactly: a value that reaches a "should never happen" assertion inside a hot data-processing path, and instead of being rejected gracefully, forces a hard process crash.

Similar unguarded `throw Error(...)` assertions exist throughout the same payment/witnessing/headers-commission code paths that a unit poster's spends walk through, e.g. `calcWitnessEarnings`/`buildPaidWitnesses` internal consistency checks such as `"stable unit "+_unit+" not found in cache"` and `"arrPaidWitnesses are not equal"`. [5](#0-4) 

### Impact Explanation
If any of these "impossible" conditions can be forced into an unexpectedly-true state by a specially crafted set of units/inputs — via double-spend/sequence-resolution races, stale connection snapshots, or output-index collisions — a single validating full node processing an incoming unit will crash via the process-wide `uncaughtException` handler. Because this handler explicitly re-throws to kill the process, this is a full denial-of-service: the node stops confirming new units until manually restarted, which matches the accepted "network unable to confirm new units" impact class and the CVSS 7.5 (`AC:L/PR:N/UI:N/A:H`) profile of the analog report.

### Likelihood Explanation
Reaching these specific `throw Error(...)` branches requires the attacker to construct a payment input that references a source output whose on-disk state has diverged from the invariant the code assumes (e.g., a source output resolved as `temp-bad` while simultaneously appearing stable in the querying connection's view, or duplicate output rows for the same `(unit, message_index, output_index)`). These are edge cases in the double-spend/sequence resolution and stabilization machinery rather than simple, always-reachable input checks, so likelihood is lower than a straightforward malformed-field bug — comparable to how the OpenLDAP CSN assertion required a specific malformed value rather than any arbitrary packet. I was not able to fully trace the sequence-resolution/stabilization state machine (`main_chain.js`, `writer.js`) within the available exploration to construct a concrete unit sequence that provably drives one of these states to `temp-bad`-while-stable or to duplicate output rows; this remains an open verification gap.

### Recommendation
- Replace the `throw Error(...)` assertions inside `validatePaymentInputsAndOutputs` (and the analogous ones in `paid_witnessing.js`/`headers_commission.js`) with graceful `callback("...")` unit-error returns instead of unhandled throws, so malformed/unexpected states reject only the offending unit rather than crashing the whole node.
- Audit all `throw Error(...)` calls reachable from the unit-validation call graph (`validation.js`, `paid_witnessing.js`, `headers_commission.js`, `mc_outputs.js`) for reachability from attacker-controlled unit content, and convert genuinely-attacker-reachable ones into recoverable validation errors.
- Consider narrowing the scope of the `process.on('uncaughtException', …)` re-throw so that failures originating specifically from per-unit validation of untrusted network data do not necessarily kill the entire process, while still safely aborting the current transaction/connection.

### Proof of Concept
A fully concrete, minimal-unit PoC could not be constructed within the available investigation: it would require reproducing a specific double-spend/stabilization race that leaves a source output's `sequence` as `temp-bad` while it is simultaneously reported `bStableInParents` in the validating connection's view of `units`/`outputs`, at the exact moment a second unit spends that output — a scenario governed by `main_chain.js` stabilization logic that was not further traced here. This is noted as an open item; the analog is offered based on confirmed root-cause code (`validation.js:2443-2461`, `network.js:4530-4543`) rather than a demonstrated end-to-end exploit sequence.
