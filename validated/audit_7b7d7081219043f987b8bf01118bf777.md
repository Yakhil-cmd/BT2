### Title
CCMenu API tokens are not scoped to the requesting stack, granting cross-stack read access - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints a per-stack "CCMenu URL" containing an `ApiClient` authentication token that is intended to authorize read access to a single stack's build status. However, the backing `ApiClient` record is looked up/created using only `creator` and `name` — never `stack` — so it is never actually scoped to the stack the URL was generated for. Because `Shipit::Api::BaseController#stacks` only restricts visibility when `current_api_client.stack_id?` is true, this unscoped client authorizes reads of **every** stack in the instance. Any holder of one stack's CCMenu URL/token can therefore read the build status of all stacks, not just the one they were handed a link for.

### Finding Description
`CCMenuUrlController#fetch` builds the CCMenu URL and generates the token from a client that is only keyed by user identity, not by stack: [1](#0-0) 

The intended binding is: *token authorizes reads of the stack whose CCMenu URL was requested* = *stack the token actually touches*. Because `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` does not set `stack:`, this equality is broken — the same singleton token is (re)used for every stack a given user requests a CCMenu link for, and its underlying `stack_id` column stays `nil`.

`ApiClient` supports per-stack scoping via `belongs_to :stack, optional: true`, and permission/scoping decisions in the general API controller depend on `stack_id?`: [2](#0-1) 

Since the CCMenu-issued client never has `stack_id` set, `stack_id?` is false, so any code path using `stacks`/`stack` from `BaseController` would treat this client as authorized for `Stack.all`. The dedicated `Api::CCMenuController` makes this concrete by fetching the stack directly from the request param, bypassing the (already ineffective) scoping helper entirely, and it only checks the generic `read:stack` permission — never that the token belongs to *this* stack: [3](#0-2) 

`ApiClient#check_permissions!` only validates that the operation/scope pair (`read:stack`) is present in the `permissions` array — it performs no per-record stack comparison: [4](#0-3) 

The route confirms the token is accepted purely via query string and is generic across any `stack_id` path segment: [5](#0-4) 

This is a direct analog of the reported bug class: a credential (the CCMenu token) is presented and distributed as authorizing a specific, narrow scope (one stack), but the code never enforces that binding, so the credential actually authorizes a much broader scope (every stack) — exactly the "verified but never actually checked" trust gap described in the external report (the position-manager contract is trusted to enforce constraints it never actually enforces).

### Impact Explanation
CCMenu URLs are explicitly designed to be handed out to third-party/unauthenticated build-status tools (that is the entire purpose of the CCMenu XML feed). Anyone who obtains one stack's CCMenu URL (e.g., a build badge pasted into a README, a status board, or a shared dashboard) obtains a live, valid API token that can be replayed against `api_stack_ccmenu_url` for **any other stack** in the Shipit instance, disclosing that stack's name, last build status, last build label, last build time and web URL — including for stacks the token holder was never intended to see. This matches the High-severity category of "unauthenticated read of stack state" once the token — meant for narrow, low-trust distribution — leaks outside its intended single-stack context, which is an expected condition given the feature's design purpose.

### Likelihood Explanation
High. No privileged action is required to trigger the flaw — it exists for every user of the "CCMenu URL" feature, and exploitation only requires possession of any single stack's generated CCMenu URL, which by design is meant to be shared with external, less-trusted consumers (CI dashboards, status badges). The bug is deterministic: the very first token issued to a user is reused, unscoped, forever.

### Recommendation
When minting the CCMenu client, scope it to the specific stack being requested, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`, and enforce in `Api::CCMenuController#stack` (and generally in `Api::BaseController#stack`) that `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` before rendering. Consider also invalidating/rotating any previously issued unscoped CCMenu client tokens.

### Proof of Concept
1. User `alice` (a Shipit user) opens Stack A's settings page and requests a CCMenu URL. `CCMenuUrlController#fetch` creates/finds an `ApiClient` named `"CCMenu Client"` for `alice` (no `stack` set) and returns `https://shipit.example.com/api/stacks/*owner/repo/env-a/ccmenu?token=<TOKEN>`.
2. `alice` publishes this URL to a public/external CI status page (typical usage of CCMenu feeds).
3. An attacker who obtains `<TOKEN>` from that public page requests `https://shipit.example.com/api/stacks/*owner/repo/env-b/ccmenu?token=<TOKEN>` — a completely different stack B that `alice` may not even be authorized to view under normal UI access controls.
4. Because `Api::CCMenuController#authenticate_api_client` accepts the token via `params[:token]` and `#stack` resolves directly via `Stack.from_param!(params[:stack_id])` without checking the client's `stack_id`, the request succeeds and returns Stack B's build status/name/URL — data outside the scope the token was ever meant to grant.

    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))

      render(json: { ccmenu_url: uri.to_s })

    def client

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
