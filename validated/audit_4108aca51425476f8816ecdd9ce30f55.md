### Title
Cross-repository commit status forgery via unscoped `StatusHandler` bypasses per-organization webhook trust boundary - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check in `WebhooksController#verify_signature` authenticates a payload only against the GitHub App/secret belonging to the organization named in the payload (`repository_owner`), but the `status` event handler that actually writes data never verifies that the commit it mutates belongs to that same organization/repository. This breaks the binding `organization that authenticated == repository that is written`, analogous to the reported crowdsale bug where mutable parameters (there, funding cap/pricing/deadline) were trusted from a caller without re-validating the caller's authority over the specific object being changed.

### Finding Description
`WebhooksController#verify_signature` selects the signing secret using only the `repository_owner` extracted from the untrusted JSON payload itself: [1](#0-0) [2](#0-1) 

Once the HMAC is valid for *that* organization, `Shipit::Webhooks.for_event(event)` dispatches the whole raw payload to the registered handler with no further repository-ownership check by the controller: [3](#0-2) 

For most events, `Shipit::Webhooks::Handlers::Handler` scopes writes to the repository named in the payload via `repository_name`/`stacks`: [4](#0-3) 

However, `StatusHandler` never uses that scoping. It only requires `sha`/`state` and looks the commit up by SHA across the **entire** database, with no constraint tying the SHA to the organization whose secret authenticated the request: [5](#0-4) 

Any legitimate GitHub App owner of a completely unrelated organization configured on the same Shipit instance (a common self-hosted, multi-tenant deployment) can therefore sign a forged `status` payload with their own known `webhook_secret`, name their own org as `repository.owner.login`/`organization.login` to pass `verify_signature`, but set `sha`/`state` to target a commit that actually belongs to a different organization's stack (SHA obtainable from any public repository/PR). `Commit#create_status_from_github!` then creates a `Status` scoped to the *victim's* `stack_id` (derived from the found `Commit`, not from the payload), which triggers the same production code paths as a genuine CI signal: [6](#0-5) [7](#0-6) [8](#0-7) 

`add_status` calls `stack.schedule_merges` on success/pending, and `Status#schedule_continuous_delivery` fires continuous delivery, so a forged "success" status for a required CI context can unblock automerge/continuous deploy of a commit that never actually passed CI on the victim's repository.

### Impact Explanation
This crosses the exact boundary called out by the rules: "an organization that authenticated versus the repository that is written." An attacker who legitimately controls the webhook secret for Organization A can forge CI status on commits belonging to Organization B's stacks, bypassing required CI checks (`ci.require` in `shipit.yml`) and triggering an unauthorized automerge/continuous deploy for a repository they have no relationship to. This satisfies the Critical bar: "an unauthorized deploy, rollback, or merge."

### Likelihood Explanation
Exploitation requires only: (1) a valid, self-controlled GitHub App/webhook secret for some organization already configured on the shared Shipit instance (achievable by any tenant of a multi-org deployment or anyone able to register a throwaway org/app pointed at the same instance's webhook endpoint), and (2) knowledge of a target commit SHA (trivially public for open-source repos, or observable from PR metadata). No repository write access, session, or `ApiClient` token is needed — only knowledge of one's own legitimately-issued webhook secret, satisfying the "unprivileged attacker" requirement.

### Recommendation
`StatusHandler` (and any other handler that mutates state) must scope its queries to the repository named in the verified payload, mirroring `Handler#repository_name`/`stacks`, e.g. restrict `Commit.where(sha: params.sha)` to `stacks` (or the repository derived from `payload.dig('repository', 'full_name')`) that belong to the same repository owner that was authenticated in `verify_signature`. More generally, `verify_signature` should pass down the authenticated organization/repository context and every handler should assert that the object it writes to actually belongs to that authenticated scope, rather than trusting attacker-supplied identifiers embedded in the JSON body.

### Proof of Concept
1. Attacker registers/owns GitHub App "AttackerOrg" on the target Shipit instance with a known `webhook_secret`.
2. Attacker finds a public commit SHA `S` belonging to `VictimOrg/victim-repo`, which Shipit is also tracking as a stack requiring `ci/required-check`.
3. Attacker crafts:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attackerorg" } }
}
```
4. Attacker computes `sha1=HMAC(webhook_secret_of_attackerorg, body)` and POSTs to `/webhooks` with `X-Github-Event: status` and `X-Hub-Signature` set accordingly.
5. `verify_signature` resolves `repository_owner` = `attackerorg`, verifies against AttackerOrg's own secret → passes.
6. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the commit under `VictimOrg`'s stack (unrelated to `attackerorg`), and creates a `success` `Status` for it, potentially unblocking merge/deploy on `VictimOrg`'s stack.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
