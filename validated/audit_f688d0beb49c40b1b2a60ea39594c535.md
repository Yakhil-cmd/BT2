### Title
Webhook signature is bound to `repository.owner.login`, but the acted-upon repository is resolved from the unverified `repository.full_name` field — enabling cross-organization stack sync/deploy triggering - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against using `repository_owner` (parsed from `repository.owner.login` in the JSON body), but the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`) resolve the target `Stack`/`Repository` from a *different* field in the same body: `repository.full_name`. Nothing ties these two fields together, so a signed payload from one legitimately-configured GitHub organization can name a repository belonging to a different organization hosted on the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/webhook config to check against based on attacker-suppliable JSON: [1](#0-0) [2](#0-1) 

The actual signature check just HMACs the raw body against the secret configured for `repository_owner`: [3](#0-2) 

Once verified, `WebhooksController#create` dispatches the parsed body to handlers such as `PushHandler`: [4](#0-3) 

But the base `Handler` resolves which `Repository`/`Stack` the payload applies to from `repository.full_name`, a completely independent field from `repository.owner.login`: [5](#0-4) 

`PushHandler` then forces the target stack to sync to an attacker-chosen SHA: [6](#0-5) 

`Repository.from_github_repo_name` simply splits `owner/name` from that string and does a DB lookup — it never cross-checks it against `repository.owner.login`: [7](#0-6) 

This mirrors the referenced bug class exactly: the field that is cryptographically bound/verified (`repository.owner.login`, used to choose the signing secret — the "smartWallet owner" check analog) is not the same field that is subsequently *acted on* (`repository.full_name`, used to look up and mutate a `Stack` — the analog of `_smartWallet` in the vulnerable transfer). Just as the report's `withdrawETHForStaking` never confirmed `_smartWallet` matched a verified owner before transferring funds, Shipit never confirms `repository.full_name`'s owner matches the org whose secret validated the signature before dispatching sync/deploy-triggering actions.

Concretely, on a Shipit instance configured to serve multiple GitHub organizations (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml` showing multiple orgs under one Shipit install), an attacker who administers/owns the GitHub App installation for **their own** organization "OrgA" (and therefore legitimately knows OrgA's `webhook_secret`, or benefits from is unset since `verify_webhook_signature` returns `true` when `webhook_secret` is blank) can:
1. Craft an arbitrary JSON push payload with `repository.owner.login = "OrgA"` (so it authenticates against OrgA's secret) but `repository.full_name = "victim-org/victim-repo"`.
2. Sign it with OrgA's webhook secret and POST it to `/webhooks` with `X-Github-Event: push`.
3. `verify_signature` succeeds (valid signature for OrgA).
4. `PushHandler` looks up the stack for `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: <attacker chosen sha>)`, enqueuing `GithubSyncJob` against a stack the attacker has no authorization over.

### Impact Explanation
This crosses the "repository the org authenticated as" vs. "repository the code writes to" trust boundary explicitly called out in the rules. `GithubSyncJob` fetches commits via the *victim's own* GitHub API credentials/installation (`stack.github_api`), appends them to the victim stack's commit history, and can force resynchronization toward an attacker-nominated `expected_head_sha`. Because stacks may be configured for continuous deployment, this can influence what gets deployed on a victim's stack, constituting an unauthorized cross-repository/cross-organization action triggered without any credential belonging to the victim org. This satisfies the "cross-repository writes / unauthorized deploy" High/Critical impact bar.

### Likelihood Explanation
Requires only that the attacker control (own/administer) at least one GitHub organization whose GitHub App is installed on a shared, multi-tenant Shipit instance — a normal, unprivileged-relative-to-Shipit position, and a configuration explicitly supported by the codebase (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml` show multiple orgs keyed under one Shipit deployment). No Shipit session, `ApiClient` token, or victim credentials are needed. The only extra requirement is knowledge of the attacker's *own* org's webhook secret (which they set themselves), or the secret being unset for their org (`verify_webhook_signature` returns `true` when blank).

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, cross-validate that `payload.dig('repository', 'full_name')` starts with `repository_owner` (i.e., the owner segment of `full_name` must equal `owner.login`) before any handler is allowed to act, or better, always derive the acted-upon repository/organization solely from the same field used for signature verification (`repository.owner.login`) rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit to serve two orgs, `OrgA` (attacker-controlled) and `victim-org` (has a stack `victim-org/victim-repo` configured on the same Shipit instance), similar to `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker builds a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` (known to them since it's their own org's secret) and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` validates successfully against `OrgA`'s config (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), enqueuing `GithubSyncJob` against the victim's stack despite the request never being authenticated as `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
