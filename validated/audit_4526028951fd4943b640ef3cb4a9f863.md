Confirmed: `Shipit.github(organization:)` supports a multi-tenant config where each GitHub organization key under `secrets.github` has its own `webhook_secret` [1](#0-0) . This makes the mismatch concrete: signature verification is keyed on `repository.owner.login` (or `organization.login`), while the actual write target (`Repository.from_github_repo_name`) is keyed on `repository.full_name` — a distinct JSON field.

### Title
Webhook signature verified against `repository.owner.login`'s org secret while sync target is selected by unrelated `repository.full_name` field, enabling cross-tenant repository sync forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In multi-tenant configurations, `Shipit.github(organization:)` resolves a distinct `webhook_secret` per GitHub organization key under `secrets.github` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to validate the HMAC against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . However, once the signature check passes, event handlers (e.g. `PushHandler`) resolve which `Repository`/`Stack` to act on using an entirely different JSON field, `repository.full_name` [3](#0-2) [4](#0-3) , via `Repository.from_github_repo_name` which parses owner/name straight out of that string [5](#0-4) .

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the request == the owner of the repository whose stacks get synced*. Because `repository.owner.login` and `repository.full_name` are independent fields inside the same signed JSON body, an attacker who controls (or compromises) the webhook secret for **any one** tenant organization configured in this Shipit instance can craft a payload where `repository.owner.login` (and/or `organization.login`) names their own organization — causing `verify_signature` to select and successfully validate against their own org's secret — while `repository.full_name` names a **different** organization/repository's tracked stack. Since the HMAC only proves "this bytes blob was signed with organization X's secret," not "field owner.login equals field full_name's owner," the signature is technically valid over the full raw body, but the semantic binding the code relies on (secret-owner == acted-upon-repository-owner) is never actually checked anywhere in the request path.

### Impact Explanation
If exploited, this lets a party who legitimately holds webhook credentials for one tenant/organization trigger `GithubSyncJob` (via `stack.sync_github`) against stacks belonging to a completely different tracked repository/organization in the same Shipit instance, forcing the sync/commit-ingestion pipeline for `Shipit::Commit.create_from_github!` to run using attacker-influenced `expected_head_sha`/branch data pointed at an unrelated repo [6](#0-5) . This is a cross-tenant trust boundary violation reachable purely by crafting a webhook payload; however, it requires the attacker to already control a legitimate webhook secret for some organization configured on the instance (i.e., they must be one of the onboarded GitHub App installations), which is a meaningful precondition.

### Likelihood Explanation
Low-to-Medium. This only matters for deployments using the multi-organization `secrets.github` schema (keyed by org) rather than the single-app schema [7](#0-6) , and requires the attacker to already be a legitimate GitHub App owner/installer for at least one org on the instance — an actor who is not fully unprivileged with respect to this Shipit deployment. It does not grant deploy/rollback/merge capability by itself, only forces a resync against another repo's stacks.

### Recommendation
After signature verification succeeds for organization `X`, explicitly assert that `payload.dig('repository','full_name')`'s owner matches `X` (or `repository_owner`) before dispatching to handlers, rejecting the webhook with 422 on mismatch, rather than trusting that `owner.login` and `full_name` are consistent.

### Proof of Concept
Not demonstrable as a full cross-repo write without controlling a second real webhook secret to compare against; the finding is that no code path anywhere cross-checks `repository.owner.login` against `repository.full_name`'s owner segment, which is the structural root cause: [8](#0-7)  only signs/logs `repository_owner`, while [3](#0-2)  derives the acted-upon repository purely from `full_name` with no reference back to `repository_owner`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
