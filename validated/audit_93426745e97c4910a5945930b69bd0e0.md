### Title
Webhook signature verification key selected by `repository.owner.login`, but stack routing keyed by unrelated `repository.full_name` — cross-org stack forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `payload.dig('repository','owner','login')`. `Handler#stacks` then resolves the target `Stack`/`Repository` using a completely different field, `payload.dig('repository','full_name')`, with no check that this field's owner matches the org whose secret verified the request. An attacker who owns org A can therefore submit a webhook whose `repository.owner.login` is `org-A` (so the signature check uses org A's own known secret) while `repository.full_name` is `org-B/protected-repo`, causing `PushHandler#process` to call `stack.sync_github(expected_head_sha: params.after)` on org B's stack with an attacker-chosen SHA.

### Finding Description
The broken binding: `organization whose secret verified the HMAC (derived from payload.repository.owner.login)` == `organization owning the repository/stack acted upon (derived from payload.repository.full_name)`. This does not hold.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` computes `repository_owner` from `params.dig('repository','owner','login')` and fetches the corresponding `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`, then verifies the raw POST body against `X-Hub-Signature` with that secret.
- Nothing in the controller cross-checks `repository.owner.login` against `repository.full_name`; they are independent, attacker-supplied JSON fields in the same POST body.
- `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves the target repository via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, then `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on that repository tracking the given branch.
- Since the attacker owns org A, they can compute a valid HMAC-SHA1 over any raw body of their choosing using org A's own webhook secret (which they legitimately possess as org A's admin). They set `repository.owner.login = 'org-A'` (so the correct/known secret is used for verification) but set `repository.full_name = 'org-B/protected-repo'` (an unrelated, real Shipit-tracked repository belonging to org B).
- `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) does a plain `find_by(owner:, name:)` lookup with no ownership/authentication cross-check back to the verified signer.
- Result: `sync_github` is invoked on org B's production stack with an attacker-controlled `expected_head_sha`, without org B's webhook secret ever being used or known by the attacker.

### Impact Explanation
This is a cross-tenant authentication bypass: a webhook payload "signed" only by org A's secret is used to mutate/reconcile org B's `Stack` state (`sync_github`) via an attacker-chosen `expected_head_sha`. Depending on `Stack#sync_github`'s internal handling of a non-existent/attacker-chosen commit SHA, this can affect commit-ingestion, CI status reconciliation, and downstream deploy eligibility for a repository/organization the attacker never authenticated against. This matches the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any Shipit-tracked repository whose full name the attacker can guess/know, from any organization the attacker legitimately administers on GitHub (needed only to obtain one valid `webhook_secret` for computing a valid signature).

### Likelihood Explanation
Preconditions: attacker must own/administer at least one org (org A) that is configured in Shipit (`Shipit.github(organization:)` must resolve, i.e., org A's webhook config with a secret exists) and knows target org B's repository full name and a stack tracking a specific branch, both of which are typically public information (repo `owner/name`, branch `main`). No access to org B's secret, API tokens, or Shipit session is required. This is fully attacker-controlled and repeatable (attacker directly POSTs to `/webhooks` with a self-crafted body and a signature computed with their own known secret) — no dependency on GitHub's actual webhook delivery infrastructure.

### Recommendation
Bind signature verification and target resolution to the same, single source of truth: derive the organization/repository used both for `Shipit.github(organization:)` (secret lookup) and for `Repository.from_github_repo_name` from the same field, and reject the payload if `repository.owner.login` does not match the owner portion of `repository.full_name`. Concretely, in `WebhooksController#verify_signature` (or in `Handler#initialize`), assert `payload.dig('repository','owner','login').downcase == payload.dig('repository','full_name').split('/').first.downcase` before proceeding, returning 422 on mismatch.

### Proof of Concept
Minitest plan (no live GitHub calls; stub `Stack#sync_github` with Mocha):

```ruby
test "push webhook signed by org A cannot drive sync_github on org B's stack" do
  org_a_secret = 'org-a-secret'
  Shipit.stubs(:github).with(organization: 'org-a').returns(
    Shipit::GitHubApp.new('org-a', webhook_secret: org_a_secret)
  )

  repository_b = create_repository(owner: 'org-b', name: 'protected-repo')
  stack_b = create_stack(repository: repository_b, branch: 'main')

  attacker_sha = 'a' * 40
  payload = {
    'ref' => 'refs/heads/main',
    'after' => attacker_sha,
    'repository' => {
      'owner' => { 'login' => 'org-a' },       # verified against org A's secret
      'full_name' => 'org-b/protected-repo'    # but targets org B's stack
    }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', org_a_secret, payload)

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: attacker_sha).never
  # Assert: sync_github MUST NOT be called on stack_b using a signature that only proves org A's identity.

  post '/webhooks', params: payload, headers: {
    'X-Github-Event' => 'push',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json'
  }

  assert_response :ok # currently succeeds and (without a fix) invokes sync_github on stack_b
end
```

Binding to assert explicitly: `verified_secret_org == target_stack.repository.owner` must be true; with the current code, `verified_secret_org = 'org-a'` while `target_stack.repository.owner = 'org-b'`, proving the divergence.
