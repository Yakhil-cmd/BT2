## Title
Autonomous Agents can be tricked into accepting non-standard assets (`is_transferrable=false`, `cosigned_by_definer=true`, `transfer_condition` restricted) that the AA cannot subsequently move, causing unexpected payment failures and permanent freezing of AA funds - (File: aa_composer.js)

### Summary
Ocore assets are analogous to the "arbitrary tokens" in the external report: any unprivileged user can define a brand-new asset (`app: 'asset'`) with arbitrary special semantics (`is_transferrable`, `cosigned_by_definer`, `transfer_condition`, `spender_attested`) and then send it to any Autonomous Agent as part of a trigger, with zero review by the AA author, exactly like the arbitrary-token registration in the Loopring report. When the AA later tries to build a normal outgoing payment in that asset, `aa_composer.js`'s payment-building code only special-cases `fixed_denominations` and `is_private`; it does not check `is_transferrable`, `cosigned_by_definer`, `issue_condition`/`transfer_condition`, or `cap` before constructing the response payload.

Since an AA is single-authored (its own address only), it can never satisfy `cosigned_by_definer` unless it is itself the definer, and it can never satisfy `is_transferrable=false` restrictions when trying to pay an arbitrary third-party address (only allowed patterns are payments to/from the asset's definer). Any user (the "asset definer") can create such an asset with `validateAssetDefinition` in `validation.js`, which permits any combination of these flags as long as internally consistent: [5](#0-4) 

Because AA authors write generic logic (e.g. exchange/DEX/market-maker AAs seen in `test/samples/uniswap_like_market_maker.oscript` and `test/samples/option_contract.oscript`) that treats `trigger.output[[asset=...]]` uniformly, an attacker can craft a malicious asset with `is_transferrable: false` or a `transfer_condition` that always fails, send it to a target AA as a trigger payment, and the AA — unaware of the restriction, since `aa_composer.js` never checks it — will attempt to construct a normal outgoing payment in that asset (e.g., a refund, dividend or exchange output). This constructed response unit will then fail `validatePaymentInputsAndOutputs`, causing the whole AA response to bounce (wasting the trigger's bounce fee) or, in flows where the AA credits its internal balance/state before actually being able to pay out (e.g., `var['mm_asset_outstanding'] += $issue_amount` pattern in `uniswap_like_market_maker.oscript`), permanently freezing the asset inside the AA because the AA can never successfully move it out again.

### Impact Explanation
This is analogous to the "arbitrary token added without owner review" bug class: the AA author (analog of the exchange owner) cannot practically vet every asset an unprivileged user might send in a trigger, and ocore provides no analog to `setCheckBalance`/`needCheckBalance` to opt an asset in or out of special handling before interacting with it. The result is unexpected transaction failures and, in more advanced AA logic that tracks balances/state across triggers, permanent loss/freezing of AA funds denominated in the malicious asset, matching the "Medium/High, unauthorized loss/freezing of AA funds or inability to confirm transfers" impact bar.

### Likelihood Explanation
Any unprivileged user can define an asset with `is_transferrable: false`, `cosigned_by_definer: true`, or a `transfer_condition` at will (`validateAssetDefinition`, `validation.js:2725`), and can send it to any target AA in a normal payment trigger without any special privilege. No cooperation from the AA operator or any other party is required to trigger the bounce/freeze condition, making this readily reachable by a single posted unit.

### Recommendation
- Short term: In `aa_composer.js`, when building AA-issued payment messages for non-base assets, load and check `is_transferrable`, `cosigned_by_definer`, and `issue_condition`/`transfer_condition` before attempting to construct outputs, and bounce early with an explicit, understandable error rather than allowing the response unit to fail deep validation (or freeze funds silently).
- Long term: Document in the AA/oscript developer guide that AAs must treat any asset they did not themselves define as untrusted with respect to transferability/attestation/condition semantics, and consider providing a helper (e.g. an `asset[...]` getter field) that surfaces these flags to oscript so AA authors can defensively check them (`is_transferrable`, `cosigned_by_definer`, has-conditions) before crediting/spending an unfamiliar asset.

### Proof of Concept
1. Attacker defines Asset X via a normal `asset` message with `is_transferrable: false`, `issued_by_definer_only: true`, `cosigned_by_definer: false`, `spender_attested: false` (attacker is definer) — allowed per `validateAssetDefinition` (`validation.js:2725`).
2. Attacker issues some amount of Asset X to themselves.
3. Attacker sends a trigger to a target exchange/market-maker AA (e.g. modeled on `test/samples/uniswap_like_market_maker.oscript`) including `trigger.output[[asset=X]]`.
4. The AA's oscript logic (unaware Asset X is non-transferrable) attempts to pay Asset X back to the trigger address as part of its normal flow (e.g. a swap/dividend payout).
5. `aa_composer.js` builds the payment without checking `is_transferrable` (`aa_composer.js:1323-1331`), producing a payload where `arrOutputAddresses` doesn't include the asset definer.
6. Final validation in `validatePaymentInputsAndOutputs` rejects the unit with `"the asset is not transferrable"` (`validation.js:2628`), causing the AA response to bounce (wasting bounce fee) or, if internal AA state already accounted for the payout as sent (e.g., decremented an outstanding-shares counter), leaving Asset X funds effectively stuck/inaccessible in the AA.
