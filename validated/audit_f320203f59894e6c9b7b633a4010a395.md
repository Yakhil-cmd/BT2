### Title
Unsafe `transferFrom()` Instead of `safeTransferFrom()` in ERC721 Bridge Withdrawal Permanently Locks Bridged NFTs — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer` uses the bare `IERC721.transferFrom()` to deliver bridged ERC721 tokens to the recipient. Unlike `safeTransferFrom()`, this does not verify that a contract recipient implements `IERC721Receiver`. Because the bridge fully commits its state (nonce consumed, tx-hash marked handled, event emitted) **before** the transfer call, a silent delivery to an incompatible contract address permanently locks the NFT with no retry path.

---

### Finding Description

In `handleERC721Transfer`, when `modeMintBurn == false`, the withdrawal path is:

```solidity
// BridgeTransferERC721.sol lines 49–70
_setHandledRequestTxHash(_requestTxHash);          // nonce consumed
handleNoncesToBlockNums[_requestedNonce] = ...;    // state committed
_updateHandleNonce(_requestedNonce);               // lowerHandleNonce advanced
emit HandleValueTransfer(...);                     // event emitted

if (modeMintBurn) {
    require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...));
} else {
    IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId); // ← unsafe
}
``` [1](#0-0) 

The ERC721 standard's `transferFrom` does **not** call `onERC721Received` on the recipient. If `_to` is a contract that does not implement `IERC721Receiver`, the token is silently transferred into that contract where it is permanently inaccessible. The OpenZeppelin v2 `ERC721.transferFrom` confirms this — it only calls `_transferFrom` with no receiver check: [2](#0-1) 

Whereas `safeTransferFrom` enforces the receiver check: [3](#0-2) 

The ERC20 withdrawal path in the same codebase correctly uses `safeTransfer`: [4](#0-3) 

The asymmetry is the root cause: ERC20 withdrawals are protected; ERC721 withdrawals are not.

The bridge state is irreversibly committed before the transfer executes. `_updateHandleNonce` advances `lowerHandleNonce` and deletes `handleNoncesToBlockNums[_requestedNonce]` and `closedValueTransferVotes[_requestedNonce]`: [5](#0-4) 

Once `lowerHandleNonce` advances past `_requestedNonce`, `_lowerHandleNonceCheck` will reject any re-submission of the same nonce: [6](#0-5) 

There is no recovery mechanism.

---

### Impact Explanation

A bridged ERC721 token is permanently lost when the recipient `_to` is a contract that does not implement `IERC721Receiver` (e.g., a multisig wallet, DAO treasury, or any smart contract wallet without the ERC721 hook). The bridge marks the nonce as handled and the source tx hash as processed, so the transfer cannot be retried. The NFT is stuck in the recipient contract with no on-chain recourse.

**Corrupted value**: the ERC721 token ID specified in `_tokenId` is transferred to an address from which it can never be recovered, while the bridge's `lowerHandleNonce`, `handleNoncesToBlockNums`, and `handledRequestTx` mappings are permanently updated to reflect a "successful" delivery.

---

### Likelihood Explanation

The `_to` address is supplied by the original user on the source chain via `requestERC721Transfer`. Any user who specifies a contract address as the destination — a common pattern for DAOs, protocol treasuries, or smart contract wallets — triggers this path. Operators faithfully relay the user-specified `_to` without any contract-receiver validation. No special privilege is required beyond initiating a standard bridge transfer.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` in the withdrawal path of `handleERC721Transfer`:

```solidity
// Before (unsafe):
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After (safe):
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

`safeTransferFrom` is already declared in `IERC721`: [7](#0-6) 

If `_to` does not implement `IERC721Receiver`, the call reverts before any bridge state is mutated, preserving the nonce for a corrected retry.

---

### Proof of Concept

1. Deploy a bridge in lock/unlock mode (`modeMintBurn = false`) on a service chain.
2. Deploy a contract `Sink` with no `onERC721Received` function.
3. On the source chain, call `requestERC721Transfer(tokenAddr, Sink.address, tokenId, "")`. Operators relay the event.
4. Operators call `handleERC721Transfer(txHash, user, Sink.address, tokenAddr, tokenId, nonce, blockNum, "", "")` on the destination bridge.
5. Observe: `HandleValueTransfer` event is emitted, `lowerHandleNonce` advances, `handledRequestTx[txHash] == true`.
6. Observe: `IERC721(tokenAddr).ownerOf(tokenId) == Sink.address` — the NFT is in `Sink` with no recovery path.
7. Attempt to re-submit the same nonce: `_lowerHandleNonceCheck` reverts with `"removed vote"`.
8. The bridged NFT is permanently lost.
