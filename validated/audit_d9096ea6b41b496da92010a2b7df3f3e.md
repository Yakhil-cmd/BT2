### Title
Cross-tenant CI status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` matches an incoming GitHub `status` webhook to a commit by SHA alone, with no repository/organization scoping, unlike `PushHandler` which scopes lookups through `stacks` (derived from `Repository.from_github_repo_name(repository_name)`). Since `verify_signature` only proves the request was signed by *some* organization's webhook secret and does not restrict which commits that organization's payload may mutate, an attacker who controls a legitimately registered org/repo in Shipit can forge a `success`/`failure` status for a commit belonging to a completely different tenant, as long as that SHA happens to already exist in Shipit's `commits` table.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`repository_owner (verified via HMAC signature) == owner_of(Commit.where(sha: params.sha).first.stack.repository)`

Trace:
1. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the raw `params` hash.
2. `before_action :verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and validates the HMAC signature against that organization's `webhook_secret`. This proves only that *attacker-org* (whatever org the attacker legitimately registered in Shipit and controls the webhook secret for) sent the payload — it says nothing about which `sha` values that org is allowed to reference.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global, unscoped** query across all repositories/stacks in the Shipit instance. It never consults `payload['repository']['full_name']`, never calls the `stacks` helper that `Handler` provides (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and never checks that the matched commit's stack belongs to the verified `repository_owner`.
4. Contrast with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes via `stacks.not_archived.where(branch:)`, where `stacks` is resolved from the webhook's own `repository.full_name` — this is exactly the ownership check that `StatusHandler` omits entirely.

Attacker's exact request: attacker registers/controls `attacker-org/attacker-repo` in Shipit (a normal, unprivileged onboarding action) and thus knows/possesses its `webhook_secret`. They POST to `/webhooks` with header `X-Github-Event: status`, a valid `X-Hub-Signature` computed with attacker-org's secret, and body:
```json
{
  "repository": {"full_name": "attacker-org/attacker-repo", "owner": {"login": "attacker-org"}},
  "sha": "<victim commit sha>",
  "state": "success",
  "target_url": "https://attacker.example/fake-ci",
  "context": "ci/attacker"
}
```
Because `Commit.where(sha: params.sha)` is global, if that SHA exists in the DB (from a legitimate victim-org sync via `PushHandler`/`Stack#sync_github`), the victim's `Commit` row gets `create_status_from_github!` called on it, appending a forged status entirely outside the victim org's control.

No existing guard prevents this: `verify_signature` authenticates the *sender org*, not the *target commit*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape/presence of fields, not ownership; there is no `require_permission!`, `stacks` scoping, or repository-format validator applied inside `StatusHandler`.

### Impact Explanation
A payload authenticated for one tenant (attacker-org) mutates state (`commit.statuses`) belonging to another tenant's commit/stack — this squarely matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." If a victim stack's deploy/merge gates key off CI status (`context`) matching a check the victim expects, this can contribute to unblocking a deploy or merge for a commit the attacker doesn't own. It's repeatable against any known/guessed SHA already present in Shipit's DB and works cross-tenant without any interaction from the victim org.

### Likelihood Explanation
Preconditions: the attacker must control at least one legitimately onboarded Shipit-registered organization/repo (a normal, unprivileged path — creating a stack/repo in Shipit is not a privileged action per the threat model) and must know or guess a SHA that already exists in Shipit's `commits` table for a victim stack (commit SHAs are often discoverable via public GitHub history, PRs, or CI logs). No secrets belonging to the victim are needed. This is inexpensive and repeatable per request.

### Recommendation
Scope `StatusHandler#process` to only match commits within stacks belonging to the webhook's own `repository.full_name`, mirroring `PushHandler`'s use of `stacks`. E.g., restrict the query with `Commit.where(sha: params.sha).joins(:stack).merge(stacks)` (or equivalent), where `stacks` is derived from `Repository.from_github_repo_name(repository_name)` as in `Handler#stacks`, ensuring the verified organization/repository actually owns the commit before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (illustrative, not from `test/` per scope but describing required assertions):
1. Create two fixture `Repository`/`Stack` pairs: `repo_a` (owner "tenant-a") and `repo_b` (owner "tenant-b"), each with their own `webhook_secret`.
2. Create a `Commit` with a fixed `sha` (e.g., `"deadbeef"`) belonging to `repo_b`'s stack.
3. Build a `status` event payload referencing `repository.full_name = "tenant-a/repo_a"`, `repository.owner.login = "tenant-a"`, `sha = "deadbeef"`, `state = "success"`.
4. Sign the payload with `repo_a`'s (tenant-a's) `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status`.
5. Assert response is `200 OK` (signature accepted).
6. Assert `Commit.find_by(sha: "deadbeef")` (belonging to `repo_b`/tenant-b) now has a new `CommitStatus`/entry in `commit.statuses` with `state: "success"`, `context: <attacker context>` — i.e., `commit.stack.repository.owner == "tenant-b"` but the mutation was authorized only via tenant-a's secret, proving the equality `repository_owner == owner_of(matched_commit.stack.repository)` is violated.
