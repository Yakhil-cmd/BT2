### Title
Webhook signature verification is bound to an attacker-controlled `organization`/`repository.owner` field, not to the entity actually mutated by the handler, allowing cross-organization webhook forgery and `Shipit.github_teams` authorization bypass - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against using a value taken directly from the untrusted JSON body (`repository.owner.login` or `organization.login`). None of the webhook handlers are required to act on that same organization: `Handler#repository_name` resolves the target `Repository`/`Stack` from a separate field (`repository.full_name`), and `MembershipHandler` resolves the target `Team` purely by numeric `github_id`. When any configured organization has no `webhook_secret` set (an explicitly documented "optional" setting), `GitHubApp#verify_webhook_signature` short-circuits to `true`, so an unauthenticated caller can post arbitrary payloads for that organization while causing side effects against completely different, unrelated organizations/repositories/teams.

### Finding Description
`WebhooksController#verify_signature` computes the org used for HMAC validation from attacker-supplied JSON, not from any GitHub-verified identifier: [1](#0-0) [2](#0-1) 

The actual signature check in `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly supports a multi-organization configuration schema where `webhook_secret` is optional per-org, as shown in the shipped example configs: [4](#0-3) 

Once the request passes `verify_signature` (because the *chosen* org happens to have a blank secret), `Shipit::Webhooks.for_event(event)` dispatches to handlers that key off a *different, unchecked* field of the same payload:
- Generic handlers (push, pull_request, etc.) resolve target via `repository.full_name`, independent of `repository.owner.login` used for signing: [5](#0-4) 
- `MembershipHandler` resolves/creates a `Team` purely by numeric `github_id`, and adds an attacker-chosen `member.login` to it: [6](#0-5) 

`Shipit.github_teams` (the authorization allow-list) is built from that same `Team` model by organization/slug handle: [7](#0-6) 

and `User#authorized?` grants app access based solely on membership in one of those `Team` rows: [8](#0-7) 

Because `Team.find_or_create_by!(github_id: params.team.id)` matches by `github_id` alone, a forged `membership` webhook — signed only against an unrelated, secret-less organization — can target the numeric `github_id` of a `Team` row that backs one of `Shipit.github_teams`, and add an arbitrary attacker-chosen GitHub `login` to it. The equality that should hold and does not is: `organization authenticated by verify_signature (payload.organization.login / repository.owner.login, checked against that org's webhook_secret)` == `organization/team actually mutated by the handler (payload.team.id / payload.repository.full_name)`. Nothing in `WebhooksController` or the handlers enforces this equality.

### Impact Explanation
This directly matches the High-severity category "escalation into `Shipit.github_teams` authorization": an unauthenticated network attacker can forge a `membership` (or `push`/`pull_request`/`status`/`check_suite`) event, get it accepted because the org named in the payload has no `webhook_secret` configured, and use it to add an arbitrary GitHub login to a `Team` that is part of the `Shipit.github_teams` allow-list, or to trigger sync/status/PR-lifecycle side effects (`GithubSyncJob`, commit `Status` creation, `ReviewStack` archive/unarchive) against repositories/stacks that belong to organizations that have nothing to do with the org whose (missing) secret let the request through. This breaks the "organization that authenticated versus the repository/team that is written" trust binding called out in the rules.

### Likelihood Explanation
Requires only that at least one organization configured in `Shipit.github` (multi-org schema) has an unset `webhook_secret` — explicitly documented and shown as a valid/expected configuration (`webhook_secret: # nil` in the shipped example files and setup docs marking it "optional"). No credentials, tokens, or repository access are needed; the request is a plain unauthenticated `POST /webhooks`. `Team.github_id` values used as the sole lookup key are not secret (visible via GitHub's org/teams API), making the membership-escalation path plausible for a moderately informed attacker.

### Recommendation
- Require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`).
- Do not select the verification org from unauthenticated payload fields; verify the event is scoped to the org/repository the installation is actually authorized for (e.g., cross-check `installation.id`/`app_id` from GitHub's payload against configuration) before dispatching handlers.
- In `MembershipHandler`, scope `Team.find_or_create_by!` by `organization` in addition to `github_id`, and reject membership events whose `organization.login` doesn't match the org that produced a verified signature.

### Proof of Concept
1. Deployment configures multi-org `Shipit.github` with `orgWithNoSecret` having `webhook_secret: nil` (a documented, valid configuration) and `victimOrg` (secret set) having a `Team` row whose `github_id` is `999` and whose handle is listed in `Shipit.github_teams` (via `oauth.teams`).
2. Attacker discovers `999` is `victimOrg`'s authorized team id via GitHub's public teams API.
3. Attacker sends, without any credentials:
```
POST /webhooks
X-Github-Event: membership
{
  "action": "added",
  "team": { "id": 999, "name": "Anything", "slug": "anything", "url": "https://x" },
  "organization": { "login": "orgWithNoSecret" },
  "member": { "login": "attacker-github-login" }
}
```
4. `verify_signature` calls `Shipit.github(organization: "orgWithNoSecret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
5. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 999)` — matches `victimOrg`'s existing authorized `Team` — and adds `User` with login `attacker-github-login` to it via `team.add_member(member)`.
6. Attacker completes GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns true because the user is a member of a `Team` in `Shipit.github_teams`.

Note: step 6's exact linkage between the webhook-created `User` (by login) and the OAuth-authenticated `User` (looked up by `github_id` in `User.find_from_github`) could not be fully traced in the available index within the remaining tool budget; this is flagged as an area needing confirmation in a full code review/session, though the cross-organization signature/handler binding break itself (steps 1–5) is fully supported by the cited code.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
