### Title
Cross-repository commit status forgery via unscoped `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` binds an inbound webhook to a specific GitHub organization/App by looking up `Shipit.github(organization: repository_owner)` and checking the signature against that organization's `webhook_secret` [1](#0-0) . That binding is: *"the organization whose secret authenticated this payload = the repository the payload is allowed to mutate."* `StatusHandler`, unlike `PushHandler`, never re-checks that binding: it updates commit status for **any** commit in the entire Shipit installation that matches the SHA in the payload, without scoping to the repository/organization that was actually authenticated.

### Finding Description
`Handler#stacks` (the base class helper used by `PushHandler` and pull-request handlers) correctly narrows the affected records to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) , and `PushHandler#process` uses that scoping [3](#0-2) .

`StatusHandler#process`, however, ignores `repository_name`/`stacks` entirely and looks up commits globally by SHA:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

The webhook is authenticated per-organization (`repository_owner` derived from `params.dig('repository', 'owner', 'login')`) [1](#0-0) [5](#0-4) , but the *effect* of the `status` event (writing a `Status` row onto a `Commit`) is applied to whatever row happens to share that SHA across the whole database, with no check that the commit belongs to a repository owned by the authenticated organization. This is the same class of bug as the `TimelockController` report: one code path establishes/authenticates a scope (organization ↔ webhook secret), and a second code path that performs the state mutation fails to re-verify that scope before acting, letting the mutation cross the intended boundary (here, cross-repository/cross-organization instead of cross-execution).

### Impact Explanation
Commit `Status` rows are consumed by Shipit's deployability/merge-gating logic (`CommitChecks`, `EphemeralCommitChecks`, `PerformCommitChecksJob`) to decide whether a commit is safe to deploy or merge. If any repository configured on the same Shipit instance (even one belonging to a different, mutually-untrusted GitHub organization with its own webhook secret) produces a `status` webhook whose commit `sha` collides with a SHA tracked by another stack, that other stack's commit gets a legitimate-looking status write it never should have received. This can be used to influence deploy/merge-readiness signals on a stack the attacker does not control, i.e., it breaks the "organization that authenticated" ↔ "repository that is written" binding. Real-world exploitability depends on producing (or naturally having) a SHA that exists identically in a victim stack's commit table (e.g., shared history from a fork, cherry-pick, or a monorepo split across multiple Shipit-tracked repositories) — a legitimate, unprivileged repository owner does not need any secret to trigger this, only push/CI access to their own already-onboarded repository, since the GitHub-signed webhook for their own repo passes verification normally and then gets applied without repository scoping.

### Likelihood Explanation
Medium. The attack does not require knowledge of any other organization's webhook secret or Shipit credentials — only push/CI access to a repository that is already legitimately connected to the same Shipit instance (a common multi-tenant setup, as shown by the multi-org config example in `docs/setup.md` and `config/secrets.development.shopify.yml`) [6](#0-5) . The practical constraint is causing a SHA collision with a targeted victim commit, which is feasible in scenarios like shared upstream history, mirrored/forked repos, or cherry-picked commits tracked by multiple stacks.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository identified by the authenticated webhook payload, mirroring `PushHandler`/`Handler#stacks`:
```diff
 def process
-  Commit.where(sha: params.sha).each do |commit|
+  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
     commit.create_status_from_github!(params)
   end
 end
```
or equivalently join through `Repository.from_github_repo_name(repository_name)` before matching by SHA, so a `status` event can only mutate commits that belong to the repository/organization that was actually authenticated by `verify_signature`.

### Proof of Concept
1. Onboard two independent repositories/stacks to the same Shipit instance, `org-a/repo` (attacker-controlled, legitimately onboarded) and `org-b/repo` (victim), each with a distinct GitHub App/webhook secret per `docs/setup.md`'s multi-org config.
2. Arrange (e.g., via a fork/cherry-pick/shared history) for a commit with SHA `X` to exist in both `org-a/repo`'s and `org-b/repo`'s `Commit` tables in Shipit.
3. As the legitimate owner of `org-a/repo`, trigger a genuine GitHub `status` webhook for SHA `X` (e.g., via their own CI) with `state: success`. This webhook is correctly signed with `org-a`'s webhook secret and passes `WebhooksController#verify_signature`.
4. `StatusHandler#process` runs `Commit.where(sha: X)`, which matches the `Commit` row belonging to `org-b/repo`'s stack as well, and writes the attacker-supplied status onto it via `create_status_from_github!` — despite the webhook never having been authenticated for `org-b`.
