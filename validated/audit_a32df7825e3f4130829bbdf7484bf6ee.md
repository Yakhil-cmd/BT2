### Title
CCMenu API token stack-scoping bypass allows cross-stack deploy status disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the stack-resolution logic from `Api::BaseController` in a way that ignores the `ApiClient#stack_id` scope, letting a token that is authorized to read only one stack's CI status read the deploy/build status of any stack in the installation.

### Finding Description
Shipit's API tokens (`ApiClient` records) can be scoped to a single stack via `stack_id`, and `Api::BaseController` is designed to enforce that binding by scoping the queryable stacks:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
(`app/controllers/shipit/api/base_controller.rb:74-80`)

This is the mechanism relied upon across the API (e.g. `Api::StacksController`, confirmed by the test "an api client scoped to a stack will only see that one stack") to bind a token's authorization to a specific stack.

However, `Api::CCMenuController` redefines `stack` to bypass this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
(`app/controllers/shipit/api/ccmenu_controller.rb:29-31`)

It resolves the `Stack` directly from the client-supplied `params[:stack_id]`, with no reference to `current_api_client.stack_id`. The `require_permission :read, :stack` before_action only checks that the string `"read:stack"` is present in the token's `permissions` array (`ApiClient#check_permissions!`); it does not, and cannot, verify which stack the permission applies to.

The practical route for generating such a scoped, single-stack CCMenu token is `CCMenuUrlController#fetch`, which creates (or reuses) an `ApiClient` scoped only via `permissions: %w[read:stack]` and hands the resulting URL/token to whoever requested it for their specific stack (`app/controllers/shipit/ccmenu_url_controller.rb:14-18`). Nothing in the token itself encodes the `stack_id` — `ApiClient#authenticate` only verifies and looks up the client `id` (`app/models/shipit/api_client.rb:23-31`) — so the effective authorization scope is supposed to come entirely from the server-side `stacks` filter in `BaseController`, which `CCMenuController` does not use.

This is the same class of bug as the reported Merkle issue: a value used to authorize an action (`current_api_client.stack_id`, the "window"/token scope) is disconnected from the value actually acted upon (`params[:stack_id]`, the "token"/target chosen by the caller), because the verification step never binds them together.

### Impact Explanation
Any holder of a CCMenu token that is legitimately scoped to Stack A can supply an arbitrary `stack_id` for Stack B and receive Stack B's build/deploy status (branch, last build result, activity, web URL) via the XML response rendered in `show.rss.builder`/`show.xml`. This is an unauthorized read of stack state that the token was never granted access to — the analog of "escalation into unauthorized read of stack state" for a scoped credential.

### Likelihood Explanation
Exploitation only requires knowledge of one valid CCMenu token (which is a low-privilege, easily distributed URL meant to be embedded in CI status widgets) and substituting a different `stack_id` in the query path. No privileged access, session, or GitHub credentials are required beyond possessing any single scoped CCMenu token.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `Api::BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack.from_param!` directly, so the `current_api_client.stack_id` binding is enforced identically to the rest of the API.

### Proof of Concept
1. Create two stacks, A and B.
2. Via `GET /ccmenu/*stack_id` for Stack A (`CCMenuUrlController#fetch`), obtain a CCMenu URL/token scoped with `permissions: ["read:stack"]` and `stack_id: A.id`.
3. Using that same token, request `GET /api/stacks/*stack_id/ccmenu?token=<token>` but substitute Stack B's `stack_id` in the path.
4. Observe the response returns Stack B's `NoDeploy`/deploy status XML (HTTP 200), even though the token was only ever authorized for Stack A — because `CCMenuController#stack` never checks `current_api_client.stack_id`.
