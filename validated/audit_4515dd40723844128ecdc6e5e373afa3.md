### Title
Permissionless `initialize` can front-run and permanently hijack the `pool_creator` role/fee stream of a pool intended to be created via `initialize_with_permission` - (File: programs/cp-swap/src/instructions/initialize.rs, programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
Both the public, permissionless `initialize` instruction and the permission-gated `initialize_with_permission` instruction derive the pool's PDA using the exact same seeds — `[POOL_SEED, amm_config, token_0_mint, token_1_mint]` — with no distinguishing tag for "permissioned-only" pools. Since Solana account creation is deterministic and first-come-first-served (like the Fraxlend `create2` salt collision), an unprivileged actor can watch the mempool for a pending `initialize_with_permission` call for a given `(amm_config, token_0_mint, token_1_mint)` triple and front-run it with a plain `initialize` call for the same triple, permanently claiming that PDA slot with themselves set as `pool_creator`.

### Finding Description
`Initialize` (public path) and `InitializeWithPermission` (permission-gated path) both compute `pool_state` via the identical seed set: [1](#0-0) [2](#0-1) 

Both instructions funnel into the same `create_pool` helper, which derives the expected PDA from `(amm_config, token_0_mint, token_1_mint)` and fails only if the account is already owned by a non-system program: [3](#0-2) 

Neither `AmmConfig` nor the account constraints distinguish "must be created via the permissioned path" — `AmmConfig` only carries a `disable_create_pool` flag checked identically by both instructions: [4](#0-3) [5](#0-4) 

Anyone (no `Permission` account required) can call `initialize` because its account set has no permission check at all, only a `creator: Signer<'info>` who is free to be anyone and becomes `pool_state.pool_creator`: [6](#0-5) [7](#0-6) 

An attacker who observes an in-flight `initialize_with_permission` transaction for a given `(amm_config, token_0_mint, token_1_mint)` can submit a competing `initialize` transaction for the same triple with a higher priority fee. Because the PDA is fully deterministic, whichever transaction lands first wins the account; the loser's `create_pool` call reverts with `ErrorCode::NotApproved` since the account is no longer system-owned: [8](#0-7) 

If the attacker wins, they become the on-chain `pool_creator` for that deterministic pool address, which is the sole authority permitted to withdraw accrued creator fees via `collect_creator_fee`: [9](#0-8) 

This mirrors the Fraxlend `FraxlendPairDeployer` bug class: a deterministic, front-runnable identifier (`salt`/PDA) shared between a "standard" and a "privileged/custom" deployment path allows an attacker to seize the slot before the intended party, permanently blocking the honest deployment and, in this case, additionally seizing an economically valuable role (fee-collector) tied to that pool.

### Impact Explanation
The legitimate whitelisted party's `initialize_with_permission` transaction permanently fails for that exact `(amm_config, token_0_mint, token_1_mint)` triple once the attacker's `initialize` lands first, since `pool_state` PDAs cannot be recreated. The attacker becomes `pool_creator` of the resulting pool and is the only signer authorized to sweep `creator_fees_token_0`/`creator_fees_token_1` accrued from all future swaps through `collect_creator_fee`, diverting the intended creator's fee revenue to the attacker indefinitely. This is an unauthorized privileged effect (illegitimate acquisition of the `pool_creator` fee-collection role) and a denial of service against the intended permissioned pool creation for that specific token pair/config, forcing the deployer to either use the attacker-controlled pool or acquire a new `AmmConfig` index.

### Likelihood Explanation
Exploitation requires only observing a public mempool transaction and submitting a competing transaction with the same deterministic accounts and higher fee/priority — no special privilege, whitelisting, or account ownership is needed to call `initialize`. This is a standard, low-cost, one-shot front-running attack achievable by any chain observer, making likelihood high whenever `initialize_with_permission` is used for a token pair/config combination that has not yet been claimed via plain `initialize`.

### Recommendation
Distinguish the PDA seed space (or add an explicit uniqueness/ownership check) between permissioned and public pool creation, e.g., include a config-level flag (such as `amm_config.permissioned_only`) that the public `initialize` path checks and rejects, or derive `initialize_with_permission` pools from seeds incorporating the whitelisted creator's key so a public actor cannot preempt the same address. Alternatively, require `initialize` to also validate a `Permission`-style check against `amm_config` before allowing pool creation for configs intended to be permissioned.

### Proof of Concept
1. A whitelisted deployer signs and broadcasts `initialize_with_permission` for `amm_config = C`, `token_0_mint = A`, `token_1_mint = B`.
2. An attacker observes this pending transaction and immediately submits `initialize(C, A, B, ...)` with a higher priority fee, naming themselves as `creator`.
3. The attacker's transaction lands first; `create_pool` succeeds, setting `pool_state.pool_creator = attacker` at the deterministic PDA `[POOL_SEED, C, A, B]`.
4. The original `initialize_with_permission` transaction is processed next, calls `create_pool` on the same PDA, finds `pool_account_info.owner != system_program::ID`, and reverts with `ErrorCode::NotApproved` — the permissioned pool can never be created for this triple.
5. As swaps occur on the attacker's pool, `creator_fees_token_0`/`creator_fees_token_1` accrue in `pool_state`; only the attacker (as `pool_creator`) can call `collect_creator_fee` to withdraw them.

```rust
pub fn create_pool<'info>(
    payer: &AccountInfo<'info>,
    pool_account_info: &AccountInfo<'info>,
    amm_config: &AccountInfo<'info>,
    token_0_mint: &AccountInfo<'info>,
    token_1_mint: &AccountInfo<'info>,
    system_program: &AccountInfo<'info>,
) -> Result<AccountLoad<'info, PoolState>> {
    if pool_account_info.owner != &system_program::ID {
        return err!(ErrorCode::NotApproved);
    }

    let (expect_pda_address, bump) = Pubkey::find_program_address(
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
        ],
        &crate::id(),
    );

    if pool_account_info.key() != expect_pda_address {
        require_eq!(pool_account_info.is_signer, true);
    }

    token::create_or_allocate_account(
        &crate::id(),
        payer.to_account_info(),
        system_program.to_account_info(),
        pool_account_info.clone(),
        &[
            POOL_SEED.as_bytes(),
            amm_config.key().as_ref(),
            token_0_mint.key().as_ref(),
            token_1_mint.key().as_ref(),
            &[bump],
        ],
        PoolState::LEN,
    )?;
```
