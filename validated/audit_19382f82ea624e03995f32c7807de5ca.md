## Analysis

The reported bug class is: a value used to select/verify a cryptographic credential is *not* the same value that is subsequently trusted to determine what real-world resource gets acted upon — allowing the "identity checked" and "identity acted upon" to diverge. In Bluefin's `distributor`, the digest used for the "already claimed" check could diverge from the actual signed payload. In `shipit-engine`, the same class of divergence exists between the field used to pick which GitHub App/`webhook_secret` verifies a webhook, and the field later used to resolve which `Repository`/`Stack` the webhook payload is applied to.

### The binding that should hold but doesn't
`organization authenticated by verify_signature` should equal `organization owning the repository the handlers act on`.

- `WebhooksController#verify_signature` selects the verifying `GitHubApp` using `repository_owner`, itself taken from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and validates `request.raw_post` against that org's HMAC key: [1](#0-0) [2](#0-1) 
- Each organization's `GitHubApp` is looked up and constructed with its **own, independently configured** `webhook_secret` — this is the documented "Using Multiple Github Applications" mode where every org's key is stored separately and `webhook_secret` is explicitly optional (commented as `# nil` in example configs): [3](#0-2) 
- `GitHubApp#verify_webhook_signature` trivially returns `true`, with **no signature check at all**, whenever that specific org's `webhook_secret` is blank: [4](#0-3) 
- Once the request passes `verify_signature`, `WebhooksController#create` dispatches the *entire raw payload* to handlers: [5](#0-4) 
- Every handler resolves the actual `Repository`/`Stack` to act on using a **different** field of the same payload — `payload.dig('repository', 'full_name')` — completely decoupled from `repository.owner.login`/`organization.login` used for signature-org selection: [6](#0-5) 
- e.g. `PushHandler` finds stacks via that same `full_name`-derived lookup and immediately calls `stack.sync_github`: [7](#0-6) ; pull-request handlers do the same for review-stack creation/labels: [8](#0-7) 

### Exploit path (no credentials required from the attacker)
If any single organization configured in a multi-org Shipit deployment is left with `webhook_secret` unset (explicitly supported/documented as optional), an unauthenticated attacker can:
1. POST to `/webhooks` with `X-Github-Event` set to any handled event (e.g. `push`, `pull_request`, `status`).
2. Craft a JSON body where `repository.owner.login` (or `organization.login`) names the secret-less org — this makes `verify_signature` pick that org's `GitHubApp`, whose `verify_webhook_signature` returns `true` unconditionally, with **no signature needed at all**.
3. Set `repository.full_name` in the same body to a completely different, privileged repository actually tracked by Shipit.
4. Handlers resolve the target `Repository`/`Stack` from `full_name`, not from the (secret-less) `owner.login`, and execute real side effects against it — spoofed `push` events queueing `GithubSyncJob`, forged `status`/`commit_status` events writing fake CI results that later gate deploy safety checks, or forged `pull_request` events creating/mutating review stacks — for a repository the attacker has no relationship to and for which they hold no valid secret whatsoever.

This is exactly the "organization that authenticated versus the repository that is written" binding break called out as an in-scope analog category, and it requires no session, token, or secret from the attacker — only that one tenant in a multi-org config lacks a `webhook_secret`, a state the product itself documents as permitted.

### Title
Webhook signature verification is keyed by an attacker-controlled organization field decoupled from the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `GitHubApp`/`webhook_secret` to validate a webhook against using `repository.owner.login`/`organization.login` from the unauthenticated JSON body itself, while every event handler resolves the actual `Repository`/`Stack` to mutate using the unrelated `repository.full_name` field from that same body. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization has no `webhook_secret` configured (an explicitly supported, optional setting), an attacker can name a secret-less organization for verification purposes while pointing `full_name` at any other repository tracked by Shipit, bypassing signature verification entirely for that target repository.

### Finding Description
`repository_owner` (used only to pick the verifying `GitHubApp`) and `repository_name`/`full_name` (used by every `Handler` subclass to resolve the actual `Stack`) are two independent, unauthenticated fields of the same JSON body, with no code enforcing they refer to the same repository/org. [2](#0-1) [6](#0-5) 

`GitHubApp#verify_webhook_signature` short-circuits with `true` when `webhook_secret` is blank for the selected org, meaning no HMAC/signature is checked at all in that case. [4](#0-3) 

Multi-org configuration is a first-class, documented mode (`docs/setup.md`, "Using Multiple Github Applications") where each org has its own independently-set (optionally blank) `webhook_secret`, looked up via `Shipit.github(organization: ...)`. [3](#0-2) 

### Impact Explanation
An attacker with zero credentials can forge webhook deliveries that are dispatched as legitimate for any repository already tracked by Shipit, as long as one configured organization (any tenant, not necessarily the target) has an unset `webhook_secret`. This enables spoofed `push` syncs, forged `status`/`commit_status` payloads that feed deploy-readiness checks, and forged `pull_request` events driving review-stack provisioning/archival — all against a repository unrelated to the org whose (missing) secret was used to pass verification. Spoofable commit statuses can be leveraged to defeat required-status-check gating ahead of a deploy, which lands in the "unauthorized deploy" impact category.

### Likelihood Explanation
Requires only that one tenant among potentially many in a multi-org Shipit install has no `webhook_secret` set — a state the product's own setup documentation presents as optional/acceptable, not a hardening failure the operator is warned about in relation to *other* tenants' security.

### Recommendation
Bind signature verification to the same repository the handlers will act on: derive the verifying organization strictly from `repository.full_name`'s owner segment (or from a trusted, pre-registered `Repository`/`Stack` lookup) rather than from the independent `repository.owner.login`/`organization.login` fields, and/or refuse verification (rather than trivially passing) when a configured org's `webhook_secret` is blank, requiring an explicit "unsigned webhooks accepted" opt-in scoped per-organization.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": {"login": "org-with-no-webhook-secret"},
    "full_name": "victim-org/critical-repo"
  },
  "organization": {"login": "org-with-no-webhook-secret"},
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"
}
```
No `X-Hub-Signature` header is required: `verify_webhook_signature` for `org-with-no-webhook-secret` returns `true` unconditionally, and `PushHandler` resolves and syncs `victim-org/critical-repo` from the `full_name` field. [9](#0-8) [10](#0-9)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
