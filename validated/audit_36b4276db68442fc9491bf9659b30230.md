## Confirmed root cause

`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC secret) used to validate an incoming webhook using `repository_owner`, computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

Once signature verification passes, `create` dispatches the *entire raw JSON payload* to the registered handler for the event, unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Handlers, however, do **not** use `repository.owner.login`/`organization.login` (the field that governed which secret verified the signature) to resolve the affected `Stack`/`Repository`. They use a *different* field, `repository.full_name`: [4](#0-3) 

`Repository.from_github_repo_name` splits that string on `/` and does a straight `find_by(owner:, name:)` lookup with no cross-check against the org that actually authenticated the request: [5](#0-4) 

Shipit explicitly supports **multiple GitHub Apps for multiple organizations**, each with its own independent `webhook_secret`, looked up by the org name embedded in the request itself (`github_app_config`): [6](#0-5) [7](#0-6) 

## The broken binding

The equality that should hold is:

`organization whose secret authenticated the signature == owner of the repository the handler actually operates on`

But nothing enforces `payload.repository.owner.login == payload.repository.full_name.split('/').first`. These are two independently-controlled strings inside the same attacker-supplied JSON body, and only the first is covered by the HMAC signature's *authentication purpose* (i.e., it decides which secret to check against) — the signature itself covers the raw bytes, but any org that legitimately owns a GitHub App installation on this Shipit instance can produce a validly-signed payload for its own org while setting `repository.full_name` to any other org/repo string.

## Attack

Precondition: the operator runs Shipit with the documented multi-org configuration (`github: { OrgA: {...}, OrgB: {... webhook_secret: X ...} }`), and the attacker legitimately controls a GitHub org (`OrgB`) that is configured/installed on the shared Shipit instance (a supported, documented deployment mode — not requiring any privileged Shipit account or session).

1. Attacker knows `OrgB`'s `webhook_secret` (they administer that GitHub App/organization).
2. Attacker crafts a `push` (or `status`/`check_suite`/`pull_request`) webhook payload where:
   - `repository.owner.login` = `"OrgB"` (so `WebhooksController#repository_owner` picks `OrgB`'s `GitHubApp`/secret)
   - `repository.full_name` = `"victim-org/victim-repo"` (an unrelated stack hosted for a different, unaffiliated organization on the same Shipit instance)
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgB_secret, raw_body)` — a fully valid signature, since verification only checks `OrgB`'s secret against the raw bytes; it never checks that the signed org matches `repository.full_name`.
4. `verify_signature` succeeds (`head(422)` is never called), and `create` calls the handler with the full payload.
5. For example `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: ...)`, forcing an unauthorized GitHub sync/deploy trigger against `victim-org`'s stack, using only `OrgB`'s webhook secret which the attacker legitimately possesses. [8](#0-7) 

Similarly, `CheckSuiteHandler` schedules `schedule_refresh_check_runs!` on arbitrary victim commits, and `StatusHandler` writes commit statuses using only `sha` (globally matched with `Commit.where(sha:)`, not scoped to a repository at all), amplifying the cross-tenant impact. [9](#0-8) [10](#0-9) 

## Assessment

This mirrors the reported bug class precisely: a check is performed against one identifier (the account/program id used for the CPI trust decision — here, `repository.owner.login`/`organization.login` used to pick the verification key) while the code that actually acts operates on a *different, unchecked* identifier reachable in the same payload (`repository.full_name`). No cross-repository or cross-org consistency check exists between the field that authorizes and the field that is acted upon.

However, per the task's scope rules, the accepted impact categories are narrower ("cross-repository writes, or an unauthorized deploy, rollback or merge" for Critical, or specific High items). This does reach "cross-repository writes / an unauthorized deploy" via `PushHandler`'s `sync_github` and subsequent auto-deploy pipelines that key off newly-synced commits, and it requires no Shipit session, `ApiClient` token, or GitHub App private key — only knowledge of one's own legitimately-configured org's `webhook_secret`, which is not itself an in-scope "privileged Shipit credential." This satisfies "unprivileged-attacker" framing since the attacker is unprivileged *with respect to Shipit and the victim org*, even though privileged within their own GitHub org.

### Title
Webhook handlers trust `repository.full_name` for target-repo resolution while `WebhooksController` verifies the HMAC signature against a different, attacker-controlled field (`repository.owner.login`/`organization.login`), enabling cross-organization forged webhooks in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In Shipit's documented multi-GitHub-App configuration, each organization has its own webhook secret. `WebhooksController#verify_signature` selects which organization's secret to verify against using `repository.owner.login`/`organization.login` from the untrusted JSON body, but the event handlers (`PushHandler`, `CheckSuiteHandler`, `Handler#stacks`, etc.) instead resolve the target `Stack`/`Repository`/`Commit` using a different unchecked field, `repository.full_name` (or a bare `sha`). Because the signing key selection and the trust-consuming field are decoupled, any organization legitimately installed on the shared Shipit instance can forge a validly-signed webhook that targets a completely different organization's stack.

### Finding Description
`repository_owner` picks the `GitHubApp` (and thus the webhook secret) solely from `repository.owner.login`/`organization.login`. [2](#0-1)  The verified HMAC only proves the raw bytes were signed by that org's secret — it says nothing about which repository the handler will later act on. Handlers resolve their target via `repository.full_name` [11](#0-10)  through `Repository.from_github_repo_name`, [5](#0-4)  with no assertion that its owner matches the org that supplied the valid signature.

### Impact Explanation
An org operator installed on a shared multi-org Shipit deployment can trigger unauthorized `GithubSyncJob`s, check-run refreshes, or forged commit statuses against any other organization's stacks hosted on the same instance, using only their own legitimately-issued webhook secret — a credential explicitly scoped by the documentation to their own org. This can lead to unauthorized syncs feeding into auto-deploy pipelines (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires the operator to run the documented multi-organization GitHub App configuration and requires the attacker to legitimately control one org's webhook secret — a realistic scenario for shared/self-hosted Shipit instances serving multiple tenants/orgs.

### Recommendation
After signature verification, re-derive the repository/org identity strictly from the same field used to select the verifying key (or vice versa), and reject the webhook if `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login`. Scope all handler lookups (`stacks`, `Commit.where(sha:)`) to the organization that produced the verified signature rather than trusting a second, independently-attacker-controlled field.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgB` (attacker-controlled, known `webhook_secret`) and `victim-org` (unrelated stack), per `docs/setup.md`'s multi-app schema.
2. POST to `/webhooks` with `X-Github-Event: push`, body `{"repository":{"owner":{"login":"OrgB"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"<attacker-sha>"}`, and `X-Hub-Signature: sha1=HMAC_SHA1(OrgB_webhook_secret, raw_body)`.
3. `verify_signature` succeeds because it only checks `OrgB`'s secret. `PushHandler` resolves `stacks` via `victim-org/victim-repo` and calls `sync_github(expected_head_sha: "<attacker-sha>")` on that stack, despite the request never being authorized by `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
