### Title
Webhook signature verified for the organization named in `repository.owner.login`, but the repository acted upon is taken from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / HMAC secret to check against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, the actual event-processing code (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves the target `Repository`/`Stack` from a *different* JSON field, `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is defined as: [2](#0-1) 

`Shipit.github(organization:)` looks up a completely separate `GitHubApp` instance (and separate `webhook_secret`) per configured organization key [3](#0-2) . In a multi-organization deployment (as documented in `config/secrets.development.shopify.yml`, which shows two independent orgs each with their own `webhook_secret`) [4](#0-3) , each organization's secret only proves that the sender knows *that organization's* secret — it says nothing about which repository the payload's `repository.full_name` refers to.

After signature verification succeeds, the dispatched handler (e.g. `PushHandler`, `CheckSuiteHandler`, `StatusHandler`) resolves which `Repository`/`Stack` to mutate using `Handler#repository_name`/`#stacks`: [5](#0-4) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

The equality that composability/authentication requires is:
`organization used to select and verify the HMAC secret == owner of the repository whose stacks are mutated`

But the code actually enforces only:
`organization used to select and verify the HMAC secret == payload['repository']['owner']['login']` (attacker-controlled field)

and separately:
`repository acted upon == payload['repository']['full_name']` (also attacker-controlled field)

Nothing binds these two attacker-controlled fields together. An entity that controls (or has been granted) the webhook secret for organization A's GitHub App configuration can craft a raw POST body where `repository.owner.login = "orgA"` (so the correct, real, HMAC-verifiable secret is selected and the signature check passes) while `repository.full_name = "orgB/some-repo"` (an entirely different, unrelated organization/repository configured in the same Shipit instance). Because `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` and `CheckSuiteHandler`/`StatusHandler` mutate commit/status state for whatever `Stack` is resolved from `full_name`, this results in cross-organization/cross-repository state writes (triggering GitHub syncs, check-run refresh jobs, and commit status writes) driven by a payload whose authenticity was only ever established for a *different* organization than the one being written to.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in scope. The concrete effects reachable without any Shipit session or `ApiClient` token — only knowledge of one organization's webhook secret in a multi-org Shipit deployment — include: forcing `GithubSyncJob` to run for another organization's stack (`PushHandler`), forging commit statuses on another organization's commits (`StatusHandler`), and forcing check-run refreshes on another organization's commits (`CheckSuiteHandler`). This does not itself achieve RCE or GITHUB_TOKEN exfiltration, and does not directly cause an unauthorized deploy (deploys still require CI/merge-queue conditions to be independently satisfied via the real GitHub API state), so the concrete, provable impact is "cross-repository writes" of secondary state (sync triggers, statuses, check-run scheduling) rather than a full unauthorized deploy/rollback/merge.

### Likelihood Explanation
Requires: (a) a Shipit instance configured with more than one GitHub organization (the multi-org config schema is explicitly documented and shipped as an example — `config/secrets.development.shopify.yml`), and (b) the attacker possessing the webhook secret for at least one of those configured organizations (e.g., as an admin of that org's GitHub App installation, which is a lesser privilege than access to the target organization/repository). This is a plausible but non-default configuration; single-organization deployments (`github_default_organization` returning `nil`) are unaffected because there is only one secret/one implicit organization scope.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification succeeds, additionally verify that `params.dig('repository', 'full_name')` (or `organization.login` for org-scoped events) belongs to the same organization (`repository_owner`) whose secret was used to validate the signature, and reject (422) otherwise. Alternatively, bind the verified organization into the request context and have `Handler#repository_name`/`#stacks` refuse to resolve repositories outside that organization.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema), and a `Stack`/`Repository` for `orgB/target-repo`.
2. As an entity that knows only `orgA`'s webhook secret, compute `X-Hub-Signature: sha1=HMAC(orgA_secret, body)` over a crafted `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and the above signature.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA").verify_webhook_signature(...)`, which succeeds because the signature was computed with `orgA`'s real secret [1](#0-0) .
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` resolves `Repository.from_github_repo_name("orgB/target-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: params.after)` on `orgB`'s stack [6](#0-5)  — a write against `orgB`'s repository state triggered using only `orgA`'s credential.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
