Found the binding break: the webhook signature is verified against the **organization derived from `repository.owner.login`** (`WebhooksController#repository_owner`), while the actual write target for `status` events is resolved purely by **`sha` lookup with no repository/organization scoping at all**.

### Title
Cross-repository Status forgery via unscoped commit SHA lookup in webhook StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery by resolving the GitHub App/organization from `repository.owner.login` (or `organization.login`) in the payload and checking the HMAC signature with that organization's `webhook_secret` [1](#0-0) . This proves "this payload was legitimately sent by GitHub for org X's app", not "this payload's contents apply only to org X's repositories". `StatusHandler#process`, however, never checks the payload's `repository` field at all — it just does `Commit.where(sha: params.sha)` globally across the whole database and creates a status on every matching commit [2](#0-1) . Compare with `PushHandler`/base `Handler`, which correctly scope by `repository.full_name` via `Repository.from_github_repo_name` before acting [3](#0-2) .

### Finding Description
The equality that should hold is: **organization whose webhook_secret signed the payload == organization/repository whose commit rows are mutated**. `verify_signature` only binds the signature check to the organization owning the repo field, but `StatusHandler` breaks the binding by resolving target rows purely from the attacker-influenced `sha` field with zero repository filtering:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Because Shipit is a multi-tenant application that can host stacks for many unrelated GitHub organizations/repositories (each with its own configured `webhook_secret`), any organization/app that is legitimately configured in Shipit and can send a properly signed `status` event for *its own* repository can, in that same request, set `sha` to any 40-character hex value. If that value happens to collide with (or is deliberately chosen to equal) a commit SHA that already exists in a *different* organization's stack tracked by the same Shipit instance, the handler will create/update a commit status on that unrelated stack's commit — because the lookup is purely `Commit.where(sha:)`, with no `stack_id`/`repository_id` scope.

Practically, the most severe manifestation is a griefing/spoofing primitive: the attacker's own signed webhook (which they can trigger by pushing a `status` event via their own repo/app that they legitimately control, since they only need a valid signature for their own org) writes fabricated CI status (`state`, `context`, `target_url`, `description`) onto a commit belonging to a stack they do not control, as long as they can predict or brute force a shared SHA (feasible in orgs that share history via forks/vendoring, or trivially if any two tracked repositories share a commit due to a common upstream/fork relationship — a very common real-world topology for Shipit's typical mono-repo-descendant deployments). This status is then consumed by `Commit#create_status_from_github!` and by merge-queue/CI-gating logic (`StatusChecker`, `MergeRequest#all_status_checks_passed?`) [4](#0-3) , meaning a forged "success" status from one organization's signed webhook can flip the deployability/mergeability of a commit that actually belongs to a completely different, unrelated stack.

### Impact Explanation
This crosses the "organization authenticated versus repository/commit written" boundary. It allows an entity that is a legitimate webhook sender for **one** organization's repository to influence CI-status-derived deploy/merge gating data belonging to a **different** organization's stack, without ever needing that other organization's `webhook_secret`, GitHub token, or Shipit session/ApiClient token. Depending on how status data feeds `required_statuses`/merge automation, this can lead to an unauthorized/incorrectly-gated deploy or merge on a stack the attacker does not own, which maps to the High/Critical impact categories ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability depends on the attacker being able to make `params.sha` match a commit SHA already known/ingested by Shipit for a target stack. This is straightforward when: (a) the target stack tracks a fork or shares history with the attacker's own repository (common in this kind of deployment tooling), or (b) the attacker can observe the target's public commit history (SHAs are not secret) and simply reference that SHA in their own signed status payload for their own repository — GitHub does not require the `sha` in a `status` webhook to actually correspond to a commit reachable from the sending repository for Shipit to accept it, since Shipit performs no cross-check against `repository.full_name`.

### Recommendation
In `StatusHandler#process` (and any other handler that trusts `params.sha`/`params.number` without repository scoping), constrain the lookup to commits belonging to the `stacks` scoped by `repository_name` (as `Handler#stacks` already computes), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent join, instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Configure/own a legitimate GitHub organization `Attacker-Org` with its own Shipit App installation and `webhook_secret` (a normal, unprivileged setup step any org admin can do for their own org).
2. Identify a target stack tracked by the same Shipit instance for an unrelated `Victim-Org/repo`, and note a commit SHA `S` currently pending/failing CI in that stack (SHAs are public).
3. From `Attacker-Org`'s repository, send (or have GitHub deliver, e.g., by creating a commit with a colliding SHA path, or via a fork sharing history) a `status` webhook event with `sha: S`, `state: "success"`, correctly signed with `Attacker-Org`'s `webhook_secret`.
4. `WebhooksController#verify_signature` validates the signature against `Attacker-Org` (derived from the payload's own `repository.owner.login`) and passes [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: S)`, finds the victim's commit object (because it is unscoped by repository), and calls `create_status_from_github!(params)`, writing a fabricated `success` status onto `Victim-Org`'s commit [2](#0-1) .
6. If that context is part of `required_statuses`/`merge_request_required_statuses` for the victim stack, this can unblock a deploy or merge-queue entry that should have remained blocked.
