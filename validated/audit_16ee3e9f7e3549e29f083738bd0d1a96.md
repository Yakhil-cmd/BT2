### Title
Cross-organization team-membership authorization escalation via `MembershipHandler` team lookup keyed only by `github_id` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using the organization/repository owner claimed inside the payload itself, then dispatches the (now "verified") payload to `Shipit::Webhooks::Handlers::MembershipHandler`. That handler resolves the target `Team` record purely by the GitHub-side `team.id` (`github_id`), never re-checking that the team actually belongs to the organization whose secret validated the request. In a multi-organization Shipit deployment (a documented, supported configuration), this lets a user who controls one configured, less-trusted organization forge a legitimate, signature-valid `membership` webhook that adds themselves as a member of a `Team` belonging to a *different*, more-trusted organization — including a team listed in `Shipit.github_teams`, which gates access to the whole application.

### Finding Description
`WebhooksController#verify_signature` picks which organization's secret to use for HMAC verification from the payload itself: [1](#0-0) 

For `membership` events (no `repository` key), `repository_owner` falls back to `params.dig('organization', 'login')`. So the only invariant a valid signature proves is: *"this payload was signed with the secret configured for the organization named in `organization.login`."* Nothing ties the numeric GitHub team id inside the payload to that same organization.

`MembershipHandler` then processes the payload: [2](#0-1) 

`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)`. Because lookup is by `github_id` only, if a `Team` row already exists for that id (created earlier via `Shipit.github_teams`/`teams:fetch`, or via a legitimate prior membership webhook from the real owning organization), the `organization:` attribute set inside the `do |team| ... end` block is **never re-applied**, and more importantly the code never verifies that `params.organization.login` matches `team.organization` for the found record. The handler then does `team.add_member(member)` using whatever `member.login` was supplied in the (correctly-signed-for-org-A) payload.

This breaks the equality that should hold: *organization whose secret authenticated the request == organization that owns the team being mutated*. Docs explicitly support multiple GitHub organizations each with independent secrets/oauth config: [3](#0-2) 

`authorized?` on `User` checks membership in `Shipit.github_teams` by `Team` id, which is exactly the record `MembershipHandler` can be tricked into mutating: [4](#0-3) 

### Impact Explanation
An attacker who is the legitimate owner/admin of *any* organization configured in this Shipit instance's `github` secrets (organization A) can cause GitHub to deliver a genuinely signed `membership` webhook (add a member to a real team in org A), but craft the `team.id` field to reference the `github_id` of a `Team` belonging to organization B (a trusted org whose team is part of `Shipit.github_teams`). Shipit's `verify_signature` only checks the signature against org A's secret (which is valid, since GitHub really signed it for org A), then `MembershipHandler` blindly updates the `Team` row matching that `github_id` regardless of which organization it actually belongs to, adding the attacker as a member. This directly escalates the attacker into `Shipit.github_teams` authorization, granting them access to the entire protected Shipit application (stacks, deploys, rollbacks, API client management) — matching the High-severity "escalation into `Shipit.github_teams` authorization" impact category.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations with per-org secrets/apps (explicitly documented/supported), (2) attacker being a legitimate member/owner able to trigger `membership` webhooks in at least one configured, less-trusted organization, and (3) attacker knowing/guessing the numeric GitHub `team.id` of the target trusted team (discoverable via GitHub's own team API, which is often not tightly access-controlled, or via prior legitimate observation). No compromise of the target organization's own webhook secret is required — the exploit relies purely on Shipit failing to scope the team lookup/update to the authenticated organization.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (`params.organization.login`), and raise/reject if an existing `Team` with that `github_id` has a different `organization` than the one that authenticated the webhook. More generally, `WebhooksController#verify_signature` should pass the verified organization down to handlers, and every handler that mutates organization-scoped state (teams, memberships) should assert consistency between the verified organization and the entities it is about to modify before acting.

### Proof of Concept
1. Deploy Shipit with two organizations configured under `github` in `secrets.yml`: `trusted-org` (holds a team listed in `Shipit.github_teams`, e.g. `github_id: 999`) and `attacker-org` (attacker is an owner/admin, with its own valid `webhook_secret`).
2. Ensure Shipit already has a `Team` record with `github_id: 999, organization: "trusted-org"` (created via `rake teams:fetch` or a prior legitimate webhook), used to gate `authorized?`.
3. From `attacker-org`, trigger (or directly send, since the secret for `attacker-org` is known to the attacker as its GitHub App owner) a `membership` webhook to `POST /github/webhooks` with `X-Github-Event: membership`, signed with `attacker-org`'s real webhook secret, but with body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Trusted Team", "slug": "trusted-team", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-github-login" }
}
```
4. `verify_signature` validates successfully against `attacker-org`'s secret. `MembershipHandler#process` finds the existing `Team` (github_id 999, actually owned by `trusted-org`) and calls `team.add_member(member)`, adding the attacker's user to it.
5. The attacker logs into Shipit via GitHub OAuth; `current_user.authorized?` now returns true because they belong to a `Team` present in `Shipit.github_teams`, granting full application access.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
