### Title
Unauthorized crash of a full node via crafted "vote" message triggering an unguarded throw in `validateMessage` — ([File: validation.js])

### Summary
An unprivileged unit poster can craft a `vote` message referencing a poll `unit`/`choice` pair that yields more than one row from the poll lookup query, hitting the unguarded `throw Error("more than one poll?")` at [1](#0-0)  instead of returning a normal validation error. Because ocore installs a global `process.on('uncaughtException', ...)` handler that deliberately **re-throws** to crash the Node.js process (`throw err; // crash the process to avoid ending up in an inconsistent state`), any such unguarded internal throw reached while processing an untrusted, attacker-supplied unit brings down the entire node process [2](#0-1) .

### Finding Description
`validateMessage()` handles the `"vote"` app case by validating that `payload.unit` is a 44-byte base64 string and `payload.choice` is a string, then queries:
```
SELECT main_chain_index, sequence FROM polls JOIN poll_choices USING(unit) JOIN units USING(unit) WHERE unit=? AND choice=?
``` [3](#0-2) 
If this query unexpectedly returns more than one row (e.g., because of duplicate `poll_choices` rows for the same `unit`+`choice`, which the poll-creation validation for the `"poll"` app only requires values to be distinct strings within a single poll unit but does not guard against a poll unit later being processed through paths where duplicate choice rows could exist, or because of any state where the join produces multiple matches), the code executes `throw Error("more than one poll?")` directly inside the SQL callback rather than invoking `callback(...)` with an error string like every other branch in this function.

This throw is not wrapped in a `try/catch` anywhere up the call chain from `network.js`'s `handleJoint` → `validation.validate` → `validateMessages` → `validateMessage`. It therefore propagates as an uncaught exception. `network.js` installs a top-level `uncaughtException` handler whose explicit purpose is to log diagnostic info and then `throw err` again, crashing the whole Node.js process [2](#0-1) . This is analogous to the CVE-2019-2623 bug class: a low-privileged, network-reachable actor supplying malformed input to a server component causes a crash/hang (complete denial of service) via an unhandled internal error path, rather than a graceful validation rejection.

Unlike the many other `throw Error(...)` statements in `validation.js` that only fire on genuine internal-consistency violations unreachable by external input (e.g., mismatches guaranteed impossible by prior checks in the same transaction), this one is directly gated on attacker-supplied `payload.unit`/`payload.choice` values feeding a live SQL query whose result-set size is not otherwise constrained by earlier validation of the *voting* unit itself — the uniqueness constraint on choices is only enforced when the *poll* is first created, not re-verified when a vote unit is validated, and the join can, under certain historical/rewrite states of the DAG (e.g. non-serial poll units, unstable states, or catch-up reprocessing), produce a result set the developer did not anticipate.

### Impact Explanation
A successful trigger crashes the entire ocore node process (full node, hub, or witness) processing the malicious unit, taking it offline and disrupting its ability to relay, validate, or confirm any units until manually restarted — a complete denial of service consistent with CVE-2019-2623's availability impact. If a resilient attacker can repeat the trigger across multiple/most full nodes (since any node validating the same crafted unit hits the same code path), it can disrupt the network's ability to confirm new units, satisfying the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
Reaching this code path requires the attacker to construct a `vote` message whose `payload.unit`/`payload.choice` combination causes the specific join query to return >1 rows. This depends on database state that is not fully under the direct control of a single message and would need multiplicities in the `poll_choices`/`polls`/`units` join. The `getFilterError`/poll creation path enforces uniqueness only at poll-creation time; whether it is provably possible to reach the >1-row condition (e.g., via replaced/duplicate poll units across DAG reorganizations, unstable/duplicate historic poll_choices records, or database-level edge cases) could not be conclusively confirmed with the available static analysis. Additional confirmation of a concrete, always-reachable data state producing >1 rows would strengthen the case; if not achievable, the severity of this exact analog would be reduced to purely theoretical.

### Recommendation
1. Replace the internal-invariant `throw Error("more than one poll?")` at `validation.js:1831` with a graceful `return callback("more than one poll match")` (or similarly convert to a returned validation error), consistent with how every other branch in `validateMessage` handles anomalous/malicious input.
2. Audit all other `throw Error(...)` statements in `validation.js`, `definition.js`, and `storage.js` that are reachable from data contained in an as-yet-unvalidated, attacker-supplied unit (as opposed to purely internal invariants that are provably guaranteed by prior code in the same transaction) and convert them to normal validation-error returns.
3. Consider hardening the global `uncaughtException` handler in `network.js` to distinguish between validation-path exceptions (which should be treated as `ifUnitError`/`ifJointError` without crashing the whole process) and genuine unrecoverable state corruption.

### Proof of Concept
Conceptual (cannot fully verify DB-state reachability without a live database):
1. Attacker creates/observes a poll unit and later, through a sequence of unit posts causing duplicate `poll_choices` rows to exist for the same `(unit, choice)` pair (e.g., via non-serial/duplicate historical states or DAG rewrites that leave stale duplicate rows before the underlying unique constraint enforcement takes effect).
2. Attacker posts a `vote` message unit whose `payload.unit`/`payload.choice` matches that duplicated pair.
3. When any node calls `validateMessage` on this unit, the `"vote"` query returns 2+ rows, hitting `throw Error("more than one poll?")` at `validation.js:1831`.
4. The uncaught exception propagates to the global handler in `network.js:4530-4543`, which re-throws, crashing the node process.

**Caveat:** Full confirmation of step 1 (a concrete way to produce >1 matching rows purely from attacker-controlled unit posting, without needing a pre-existing database inconsistency) was not established in this analysis and would require deeper investigation of the `poll`/`poll_choices` table write paths (e.g., `writer.js`) to confirm feasibility. If this precondition cannot be met by an unprivileged attacker, this specific instance should be treated as a defense-in-depth hardening issue rather than a directly exploitable Medium/High severity DoS.
