### Title
Signature reuse across duplicate branches of `r of set`/`and`/`weighted and` allows a single key to satisfy a multi-signature address definition - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` checks structural properties of composite spending conditions (`or`, `and`, `r of set`, `weighted and`) — minimum set length, `required <= set.length`, positive weights — but never checks that the branches of a set are *distinct* (different pubkeys/addresses/conditions). Because the same unit hash (`objValidationState.unit_hash_to_sign`) is what gets signed regardless of authentifier path, one private key can produce a valid `sig` authentifier for *every* path that uses that pubkey. This mirrors the Uniswap report's root cause: a security property ("N independent parties must authorize") is only partially verified, and the check can be defeated by supplying the same underlying value (a pubkey/definition) more than once where distinctness was implicitly assumed.

### Finding Description
When validating an address (or asset-condition) definition, `evaluate()` in `definition.js#L118-L185` handles `r of set` and `weighted and` by iterating the `set` array and counting how many members can be satisfied, then comparing against `required`: [1](#0-0) 
There is no check anywhere in this function (or in `hasFieldsExcept`/type checks) that the members of `args.set` are cryptographically or structurally distinct.

During authentifier verification, `validateAuthentifiers()`'s `sig` handler simply verifies the ECDSA signature found at `assocAuthentifiers[path]` against `objValidationState.unit_hash_to_sign`, which is the same hash for the whole unit regardless of `path`: [2](#0-1) 
The `r of set` authentifier evaluation just counts how many `set` entries evaluate true and compares to `required`: [3](#0-2) 

Because the signed message is path-independent, if two (or more) entries of `set` reference the *same* pubkey (e.g., `["sig",{pubkey:X}]` appearing twice, or nested `["address", A]` definitions that both resolve to the same key), a single signer can copy the *same signature bytes* into both authentifier paths (`r.0` and `r.1`) and satisfy `required: 2` alone. This is structurally identical to the reported bug pattern: a distinctness invariant that downstream logic depends on (here: "2 different signers approved this spend") is never actually enforced, and it is defeated by supplying the same value (pubkey) where two different values were expected.

This is reachable purely from the wallet/shared-address layer, which builds definitions from device-supplied templates without checking uniqueness of members either:
- `createMultisigWallet()` builds `["r of set", {required, set}]` directly from a caller-supplied `arrDeviceAddresses` list without de-duplication beyond none: [4](#0-3) 
- `handleNewSharedAddress()` (processing an untrusted peer device's shared-address proposal) validates that each `signing_path` in the definition has a corresponding signer entry and that the c-hash matches, but never verifies that the distinct signing paths of a "required-N" set correspond to distinct keys/devices: [5](#0-4) 
- `validateAddressDefinitionTemplate()` only ensures `arrDeviceAddresses.length >= 2` (uniqueness of the *overall* device list), not that each `r of set`/`weighted and` branch used for a specific threshold is backed by non-duplicated devices: [6](#0-5) 

A malicious cosigner proposing a shared address (e.g., claiming "2-of-3 multisig") could construct a definition where two of the three `set` branches use the same pubkey/device they control, while the other party believes two *distinct* participants are required to spend. The malicious party alone can then produce a validly-signed unit that spends from the "multisig" address, defeating the security guarantee the honest cosigner believed they had.

### Impact Explanation
This allows unauthorized spending from what is represented and trusted as an N-of-M multisig/shared address: an attacker who controls only one nominal "member" of the set can satisfy a `required >= 2` threshold alone, moving funds without the cooperation of the other legitimate cosigner(s) they believed were necessary. This directly matches the "concrete unauthorized spending" impact bar, since honest funds held in a shared address can be unilaterally withdrawn by a colluding/duplicating cosigner.

### Likelihood Explanation
Exploitation requires the attacker to be one of the parties proposing/agreeing to a shared address definition (e.g., in a group wallet setup flow), and for the honest counterpart to not manually audit the raw `arrDefinition`/pubkeys embedded in the JSON structure for duplicates — a check the GUI/wallet code itself does not perform (`validateAddressDefinitionTemplate` and `handleNewSharedAddress` do not check for duplicate members). Because ordinary users rely on the wallet software's validation rather than manually inspecting embedded pubkeys, and no automatic uniqueness check exists in `definition.js`, this is plausible in real-world shared-address setup scenarios, particularly ones where address definitions/templates are received from other devices (`wallet_defined_by_addresses.js`) rather than generated locally.

### Recommendation
- In `validateDefinition()`'s handling of `r of set` and `weighted and` (and `and`/`or` where relevant to counting), reject sets containing duplicate/structurally-identical branches (e.g., duplicate pubkeys in `sig`, duplicate hash secrets in `hash`, duplicate `address` targets, or identical serialized sub-definitions).
- In `wallet_defined_by_addresses.js#handleNewSharedAddress` and `validateAddressDefinitionTemplate`, explicitly verify that all signing paths belonging to a single `r of set`/`weighted and` node map to distinct device addresses/pubkeys before accepting or approving a proposed shared-address definition.
- Consider requiring `objectHash`-based comparison of `set` members to enforce distinctness at parse time for any composite condition with `required > 1`.

### Proof of Concept
1. Attacker Mallory controls device key `Km`. Honest party Alice controls device key `Ka`.
2. Mallory proposes a shared address to Alice with definition:
   `["r of set", {required: 2, set: [["sig",{pubkey:Ka}], ["sig",{pubkey:Km}], ["sig",{pubkey:Km}]]}]`
   (paths `r.0`→Alice, `r.1`/`r.2`→Mallory, using the same key twice). Alice's client only checks that her own device address is present and that `arrDeviceAddresses.length >= 2` per `validateAddressDefinitionTemplate` (`wallet_defined_by_addresses.js#L481-L516`), which passes since `_.uniq` over `[Ka, Km, Km]` = `[Ka, Km]`, length 2.
3. Alice believes the address needs 2 of {Alice, Mallory-as-one-signer, plus a spare backup slot}, but in reality `required: 2` can be met by two authentifiers both produced by Mallory alone signing at paths `r.1` and `r.2` with the same signature bytes (since `ecdsaSig.verify` in `definition.js#L745` only checks the fixed `unit_hash_to_sign`, independent of path).
4. Mallory constructs a unit spending from the shared address, supplying identical valid signatures for `r.1` and `r.2`, and `evaluate()`'s `r of set` counts `count=2 >= required=2` (`definition.js#L692-L711`), authorizing the spend without any input from Alice.
