### Title
Unallowlisted route venues let an attacker-supplied swap payload smuggle a wallet-draining `token.transfer` into the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's strategy entrypoints (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`) accept a fully caller-supplied `swap` route payload. The payload names the pool and token addresses for every hop, and neither the controller nor the swap-aggregator router filters those addresses against any allowlist of trusted venues — the analog of Webpack copying any file type reachable through `URL()` into the bundle. A route can therefore place attacker-deployed contract code on the call stack beneath the caller's `require_auth` entry. Any `token.transfer(caller, attacker, amount)` that rogue code issues is recorded by `simulateTransaction` as a child of the caller's own authorization entry and executes if the caller signs the simulated tree, stealing wallet tokens the protocol never listed.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` passes the raw `swap` bytes to the configured router inside a flash guard and authorizes exactly one input transfer. The controller checks only measured `token_in`/`token_out` deltas and final account risk; it never inspects which contracts the route invokes.

The router dispatches each hop to `hop.pool` / `hop.token_in` / `hop.token_out` as decoded from the payload, with no venue or pool allowlist (`contracts/swap-aggregator/src/venues/mod.rs:23-59`). The threat model states this explicitly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-165`).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the mechanics end-to-end: a `RogueHopPool` contract whose `swap()` calls `token.transfer(alice, attacker, WALLET_BALANCE)` is named as the hop pool in a `swap_collateral` route. In recording mode the theft appears as a child invocation under Alice's `swap_collateral` auth entry (lines 194-227), and in enforcing mode the same signed tree executes the transfer and drains her wallet (lines 258-268).

### Impact Explanation
Theft of user funds. A victim who signs the simulated authorization tree for a malicious route loses arbitrary balances of any token in their wallet — demonstrated by `WALLET_BALANCE = 77_770_000_000` of an unlisted token moving from Alice to the attacker in the test (lines 224-225, 267-268). The loss is the caller's whole wallet, not just the routed amount: "The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`threat-model.md:159-161`).

### Likelihood Explanation
Any unprivileged address can deploy a rogue "pool" contract and craft the payload; no protocol role is needed. The exploit requires a victim to sign a route containing the attacker's venue — the same trust relationship as the Webpack report (a malicious package's HTML is bundled and delivered to end users). Every route-bearing entrypoint an unprivileged caller can reach is exposed: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`, and direct `execute_strategy` calls. The only mitigation is off-chain client diligence (decoding the signed auth tree), which most wallets do not surface meaningfully. Documented, but the exposure is real and reachable from production entrypoints; severity is bounded to the signing victim rather than the protocol's pooled funds.

### Recommendation
Filter what a route can invoke, mirroring the report's "limit imports to trusted file types":
- Maintain a governance-managed allowlist of venue pool addresses (or venue contracts) and reject any hop whose `pool` is not listed, enforced in `dispatch_hop` or during `Program::validate`.
- Alternatively/ additionally, have the controller reject route payloads whose embedded addresses differ from a vetted set for the specific strategy being executed.
- Until an allowlist exists, clients should refuse to sign any authorization tree containing child invocations beyond the single expected `token_in.transfer(sender, router, total_in)` — but this should not be the only line of defense.

### Proof of Concept
Provided in-repo at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

```rust
// Attacker-deployed "pool" named by the route payload
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = /* plan */;
    if amount > 0 {
        token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
    }
}
```

1. Attacker deploys `RogueHopPool` with plan `(alice, wallet_token, attacker, WALLET_BALANCE)`.
2. Attacker crafts a `swap_collateral` route: `token_in = USDC`, `token_out = ETH`, `hop_pool = rogue_pool`, `min_out = FAIR_OUT_ETH` (router pays fair output so the swap looks legitimate).
3. Alice calls `controller.swap_collateral(alice, account_id, usdc_key, 50_000_000_000, eth_key, route)`.
4. Simulation records the rogue `transfer(alice → attacker, 77_770_000_000)` as a sub-invocation of Alice's `swap_collateral` entry (test asserts the recorded tree at lines 206-222).
5. Alice signs the simulated tree; enforcing mode executes the theft: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the swap itself completes normally and her account passes all risk gates (lines 265-268).
