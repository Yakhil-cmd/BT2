### Title
Delegator rewards pooled in a vote account (`pending_delegator_rewards`) can become permanently un-redeemable and un-withdrawable once the vote account has no active delegated stake - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
Under SIMD-0123 (block revenue sharing), delegator rewards intended for stakers are first deposited into the vote account's `pending_delegator_rewards` balance and only later paid out to individual stake accounts based on their share of the vote account's total active delegated stake, calculated in `calculate_block_reward`. If a vote account's total active stake drops to zero (e.g., all delegators deactivate/withdraw before the reward is distributed), `calculate_block_reward` returns `0` and the pooled reward is never paid to any staker. Because `withdraw()` in the vote program always reserves `rent_exempt_minimum + pending_delegator_rewards` and blocks full account closure while `pending_delegator_rewards > 0`, this leftover balance becomes permanently frozen in the vote account with no code path shown to zero it out. This mirrors the reported analog: funds queued for distribution/redemption become permanently stuck once the entity they were meant to be redeemed against (collateral / delegated stake) no longer exists, and there is no mechanism analogous to "set redemption parameter to 0 on sunset" to release them.

### Finding Description
`deposit_delegator_rewards` accumulates lamports into `pending_delegator_rewards` via `add_pending_delegator_rewards`: [1](#0-0) 

The only mechanism observed that reduces `pending_delegator_rewards` is the per-epoch block-reward calculation, which is gated on the vote account's `total_active_stake` for the rewarded epoch: [2](#0-1) 

When `total_active_stake == 0` (i.e., no delegated stake remains active for that vote account at the rewarded epoch), the function returns `0` regardless of how large `pending_delegator_rewards` is: [3](#0-2) 

Meanwhile, `withdraw()` in the vote program permanently reserves this balance and refuses to close the account while it is non-zero: [4](#0-3) 

This is directly analogous to the reported bug class: a "queued" balance (here, pooled delegator rewards) is meant to be redeemed against a live resource (active delegated stake), but once that resource is fully "sunset" (stake fully deactivated/withdrawn) before distribution occurs, there is no remaining code path to redeem or release the queued balance — it is stuck in the vote account indefinitely, unlike the report's suggested fix of resetting a cooldown/parameter to 0 to allow recovery.

### Impact Explanation
This results in permanently frozen lamports inside the vote account: the authorized withdrawer can never withdraw below `rent_exempt_minimum + pending_delegator_rewards`, and can never close the account while `pending_delegator_rewards > 0`, as enforced in `withdraw()`. More importantly, the stakers who were owed this pooled reward (unprivileged delegators) never receive it, since the only distribution path (`calculate_block_reward`) yields zero once their delegation has fully deactivated. This falls under the accepted "permanently frozen accounts" / "misattributed rewards" impact categories, since delegator-owed funds become both frozen and effectively lost to their intended recipients with no recovery path evidenced in the reward-distribution or vote-withdraw code paths.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) the SIMD-0123/V4 commission features to be active, (b) a deposit to `pending_delegator_rewards` via `deposit_delegator_rewards`, and (c) all delegated stake to that vote account fully deactivating (going to zero effective stake) in the same epoch window before that reward gets distributed. This is a plausible but non-adversarial sequence (e.g., a validator being fully un-delegated from right after a block-revenue deposit, before the epoch boundary), matching the report's "Low likelihood" rating for its analog.

### Recommendation
When `total_active_stake` for a vote account is zero at the time block rewards would be calculated/distributed, either (a) route the un-distributable `pending_delegator_rewards` back to the vote account's block-revenue/inflation collector or the general treasury instead of silently returning `0`, or (b) allow the withdraw authority to reclaim/zero the stranded `pending_delegator_rewards` once it can be proven no active stake exists to redeem it against (analogous to setting the report's `redemptionCooldownPeriod` to 0 on sunset). At minimum, add an explicit accounting/decrement of `pending_delegator_rewards` whenever `calculate_block_reward` determines there is no eligible stake to distribute to, so the pooled balance does not remain permanently reserved and unredeemable.

### Proof of Concept
1. Enable SIMD-0123-related features (`commission_rate_in_basis_points`, `custom_commission_collector`, `block_revenue_sharing`) and use a V4 vote account.
2. Call `DepositDelegatorRewards` to add lamports to `pending_delegator_rewards` (see `deposit_delegator_rewards`, `programs/vote/src/vote_state/mod.rs:936-988`).
3. Fully deactivate/withdraw all stake accounts delegated to this vote account so that, at the next rewarded epoch, `reward_epoch_delegated_stakes.delegated_stakes.get(&vote_pubkey)` is `0` or absent (see `calculate_block_reward`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:206-231`).
4. Let the epoch reward distribution run; `calculate_block_reward` returns `0` for every stake delegation tied to this vote account, so `pending_delegator_rewards` is never reduced.
5. Attempt `Withdraw` on the vote account for the full balance: it fails with `InstructionError::InsufficientFunds` per the `pending_delegator_rewards > 0` check in `withdraw()` (`programs/vote/src/vote_state/mod.rs:1084-1121`), and this condition persists indefinitely since no future distribution round can ever pay it out (no active stake remains to compute a nonzero `calculate_block_reward`).
