### Title
Cross-repository status forgery via unscoped commit lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook by a bare `Commit.where(sha: params.sha)` query with no filter on the repository that emitted the event, unlike every other handler in the same module. Any commit row in the entire Shipit instance that happens to share that sha — regardless of which `Repository`/`Stack` it belongs to — receives the forged status, which can flip `MergeRequest::StatusChecker#success?` to true for a merge request that never received that check from its own repository's CI.

### Finding Description
The broken binding, stated explicitly: `status.stack_id (the repo whose CI produced context X) == merge_request.stack.repository_id (the repo whose required-status gate context X satisfies)`. The code never enforces this equality.

`StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Contrast with `PushHandler#process`, which correctly scopes to the repository that sent the webhook via the `stacks` helper (`Repository.from_github_repo_name(repository_name).stacks`): [2](#0-1)  and the base `Handler#stacks`/`#repository_name` implementation [3](#0-2) .

`StatusHandler` never calls `stacks` or checks `payload.dig('repository', 'full_name')` at all — it queries the global `Commit` table by `sha` only. `create_status_from_github!` then unconditionally persists a `Status` row tied to that commit's own `stack_id`: [4](#0-3) 
and `Status.replicate_from_github!` writes state/context verbatim from the payload with no cross-check against the repository that produced it: [5](#0-4) .

`statuses_and_check_runs` feeds directly into `Status::Group`/status evaluation used by `MergeRequest`'s required-status gate: [6](#0-5) [7](#0-6) 

Exploit flow: if a commit with a given sha is tracked under two different `Stack`s (e.g. shared ancestor commit between a victim repo and an attacker-owned/forked repo registered on the same Shipit instance — forks and shared history preserve identical git SHA-1 object ids), then a properly-signed `status` webhook from the attacker's own repository (verified only against that repository's own GitHub organization secret via `verify_signature`) will be applied to the victim's `Commit` row as well, because `StatusHandler` performs no repository check. If the forged `context` matches a name in the victim stack's `deploy_spec.merge.require`, `MergeRequest#all_status_checks_passed?` (built from `head.statuses_and_check_runs`) can flip to `true` without the victim repository's own CI ever reporting that check.

`verify_signature` only proves the webhook came from *some* GitHub organization known to Shipit (`repository_owner` in the payload) — it does not prove that repository is the one the resulting `Status` row gets attached to, so it does not prevent this divergence. `drop_unhandled_event`, `ExplicitParameters` schema validation (only validates field types/shapes, not repository identity), `force_github_authentication`, and model validations on `Repository`/`Stack` are likewise irrelevant to this code path — none of them re-validate that the commit being updated belongs to the repository in `payload['repository']`.

### Impact Explanation
A successful forgery writes a `Status` row for a repository that did not authenticate that check, which can satisfy a required-status gate that gatekeeps `MergeRequest#merge!`/deploy eligibility for an unrelated victim stack — this is an unauthorized-merge-gate bypass across tenants sharing one Shipit instance. Repeatable per shared-sha commit, and since Shipit is explicitly multi-repo/multi-stack, this is a cross-tenant blast radius issue matching the "Critical: payload for one repository mutating another's stack/commit/task, or an unauthorized deploy/rollback/merge" category.

### Likelihood Explanation
Requires: (1) a single Shipit instance hosting multiple repositories/stacks (the platform's normal use case), (2) the attacker owning or controlling a repository registered on that same instance whose organization is known to `Shipit.github_apps` (so `verify_signature` passes for their own webhook), and (3) a commit sha genuinely shared between the attacker's repo and the victim's tracked commit (realistic via forks/shared git history, cherry-picks preserving identical commit objects, or repos split from a common history) landing in both repos' `commits` tables. This does not require breaking SHA-1 or forging any secret — it only requires the attacker's own legitimately-signed status event for a sha that also exists in the victim's stack. Given the code path is fully unconditional once the sha matches, the attack is trivially repeatable against any stack sharing that sha.

### Recommendation
Scope `StatusHandler#process` to the repository that emitted the webhook, mirroring `PushHandler`/base `Handler#stacks`: resolve `Repository.from_github_repo_name(repository_name)` and restrict the commit lookup to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalent join through `stack.repository`), so a status can only ever be attributed to commits belonging to the repository that generated it.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook does not forge status onto commits of an unrelated stack sharing the sha" do
  victim_stack = shipit_stacks(:shipit) # some repository A
  attacker_stack = shipit_stacks(:other) # a different Repository B on the same instance

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  merge_request = shipit_merge_requests(:some_pending_mr) # belongs to victim_stack, head = victim_commit
  merge_request.stack.update!(cached_deploy_spec: DeploySpec.new('merge' => { 'require' => ['ci/circle'] }))

  refute merge_request.all_status_checks_passed? # baseline: gate not satisfied

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/circle',
    'repository' => { 'full_name' => attacker_stack.repository.github_repo_name } # attacker's own repo
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  merge_request.reload
  assert merge_request.head.reload.statuses.exists?(context: 'ci/circle')
  # Vulnerable if this flips true despite the check never coming from victim_stack's own repository CI:
  assert merge_request.all_status_checks_passed?
end
```
This demonstrates `Commit.where(sha: params.sha)` in `StatusHandler#process` [1](#0-0)  applying an attacker-attributed webhook to a commit belonging to an unrelated stack, satisfying `merge_request_required_statuses` for a repository that never produced the check.
