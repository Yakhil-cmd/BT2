### Title
Webhook signature verification is bound to an attacker-chosen organization while handlers act on unrelated, unverified payload fields (cross-repository/cross-stack forgery) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`'s `webhook_secret` to validate the incoming request against using `repository_owner`, a value read straight out of the untrusted, not-yet-verified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  Once verification passes, `create` dispatches the entire body to every registered handler for the event, and those handlers select the actual target repository/stack/commit using *other* fields of the same body — `repository.full_name` in `Handler#repository_name` [3](#0-2) , or a bare, cross-stack `Commit.where(sha: params.sha)` lookup in `StatusHandler#process` with no owner/repository check at all [4](#0-3) . The HMAC only proves "this request came from whoever holds the secret for the organization named in `repository.owner.login`" — it proves nothing about which repository, stack, or commit the body will actually mutate.

Shipit explicitly supports multiple GitHub organizations, each with its own independent, **optional** `webhook_secret` in `secrets.yml` [5](#0-4) [6](#0-5) . `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no secret is configured for the resolved organization: `return true unless webhook_secret`. [7](#0-6) 

### Finding Description
Binding that should hold: `organization whose secret authenticated the request == organization that owns the repository/commit being mutated`.

Before the attacker's request: for any legitimate delivery, GitHub signs the exact body it sends for the actual repository, so `repository.owner.login` (used for verification) and `repository.full_name` / `sha` (used for mutation) always describe the same real event.

After the attacker's request: the attacker crafts an arbitrary POST body to `/github_hooks` (or the mounted webhooks route) in which:
- `repository.owner.login` (or `organization.login`) is set to any GitHub organization configured in Shipit's multi-org `github:` section that happens to have `webhook_secret` unset/`nil` — a state the config schema explicitly allows as the default [6](#0-5) , and
- `repository.full_name` / commit `sha` / `pull_request` fields reference a completely different, legitimately-tracked repository/stack in the same Shipit instance.

`verify_signature` resolves `Shipit.github(organization: repository_owner)` for the attacker-chosen org, calls `verify_webhook_signature`, which short-circuits to `true` since that org's `webhook_secret` is blank — no HMAC is ever actually checked. [1](#0-0) [7](#0-6)  The request then reaches `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [8](#0-7) , and handlers act on the unrelated `repository.full_name`/`sha` fields to mutate a target the attacker never had to prove any relationship to.

This is the same trust-binding break described in the analog report: the field actually verified (`repository_owner`, used to select the HMAC secret) is never the field that governs which resource is written (`repository.full_name`/`sha`, used by handlers), so satisfying the verification constraint for one identity silently authorizes actions on a different identity's data — exactly like `manualAllocation` trusting `new_debt` while `update_debt`'s real effect is bounded by an unchecked `minimum_idle_amount` constraint.

### Impact Explanation
Concretely reachable, unauthenticated (no Shipit session, no API token, no repository write access) impacts once one org's `webhook_secret` is unset:
- `StatusHandler#process` matches `Commit.where(sha: params.sha)` globally, with **no repository scoping whatsoever** [4](#0-3) , so the attacker can post a forged `success` status for any commit SHA on any tracked stack. `Commit#create_status_from_github!`/`Status` creation feeds directly into `ci.require`-gated deploy eligibility (`Commit#deployable?`) and continuous-deployment/merge-queue automation (`Status#schedule_continuous_delivery`, `ProcessMergeRequestsJob`) [9](#0-8) , letting an attacker mark an unreviewed/failing commit as CI-passing to trigger an **unauthorized deploy or unauthorized merge** — a Critical-impact outcome per the report's rules.
- `PushHandler#process` uses `repository.full_name` to select stacks and enqueues `GithubSyncJob` with an attacker-supplied `expected_head_sha` [10](#0-9) , affecting sync state of any tracked repository whose owner org differs from the one used to bypass verification.

### Likelihood Explanation
Requires only that one org among several configured in a multi-org Shipit deployment has no `webhook_secret` set — an explicitly documented, default-nil configuration value [6](#0-5)  — and that Shipit tracks at least one other repository/stack the attacker wants to target. No credentials, GitHub App access, or prior authentication are needed; the attacker only needs to know the target's tracked repo full name/branch or an in-flight commit SHA (both are public/observable via GitHub itself). This is a design-level binding gap in `WebhooksController`, not a misuse of a single misconfigured field.

### Recommendation
Do not select the verifying organization from unverified payload content that differs from the field the handlers act on. At minimum: (1) require `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`), and (2) verify the signature using the same identity (repository full name, not just owner) that handlers subsequently use to select the mutated resource, or bind each `GithubHook`/organization config to the exact repository set it is allowed to affect and re-check that binding inside every handler before mutating state (especially `StatusHandler`, which currently has no repository check at all).

### Proof of Concept
1. Deploy Shipit with `config/secrets.yml` configured for two organizations, e.g. `OrgA` (attacker-known, `webhook_secret: nil`) and `OrgB` (the real target org already tracked by Shipit, e.g. `Shopify/shipit-engine`), per the documented multi-org schema. [5](#0-4) 
2. POST to the webhooks endpoint with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" },
  "sha": "<sha of a real, unreviewed commit on OrgB/shipit-engine>",
  "state": "success",
  "context": "ci/required-check"
}
```
No valid `X-Hub-Signature` is required because `OrgA`'s `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally. [7](#0-6) 
3. `StatusHandler#process` matches the commit purely by `sha` across all stacks and records a fabricated `success` status [4](#0-3) , making the commit `deployable?` and eligible for continuous deployment/merge on `OrgB`'s stack despite the attacker never proving any relationship to `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
