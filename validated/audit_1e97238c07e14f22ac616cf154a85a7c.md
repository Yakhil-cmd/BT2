### Title
`pull_request` webhook signature verified against `repository.owner.login`'s org while `AssignedHandler` mutates the repo/stack resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates the incoming webhook using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository','owner','login')`. `AssignedHandler#repository`/`#pull_request`, however, resolve the mutated database record using `params.repository.full_name`. These are two independently attacker-controlled fields in the same JSON body, and nothing enforces that `full_name` belongs to `owner.login`.

### Finding Description
The broken binding is the implicit assumption:
`repository_owner (used for HMAC verification) == owner(repository.full_name) (used for DB mutation)`
which is never checked anywhere in the code path.

Path:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` unconditionally when that org's `webhook_secret` is blank/not configured (`return true unless webhook_secret`).
- On success, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` invokes `AssignedHandler.call(params)` with the *entire* raw JSON payload, unfiltered by which org "verified" it.
- `AssignedHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:67-69) resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely separate field from the one used for signature verification.
- `AssignedHandler#pull_request` (lines 53-65) looks up the persisted `Shipit::PullRequest` joined to that resolved repository's stacks, and `#process` (lines 41-45) calls `pull_request.update(github_pull_request: params.pull_request)`.

Exploit: an attacker registers/owns a GitHub org (e.g. `attacker-org`) that is configured in Shipit but has no `webhook_secret` set (or any org for which they know the secret). They send `POST /webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "unassigned",
  "number": <victim PR number>,
  "pull_request": { ... arbitrary attacker-crafted fields ... },
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sender": { "login": "attacker" }
}
```
`verify_signature` computes `repository_owner = "attacker-org"`, fetches that org's (secret-less) `GitHubApp`, and `verify_webhook_signature` short-circuits to `true`. The request is accepted and dispatched. `AssignedHandler` then resolves `victim-org/victim-repo`'s persisted `PullRequest` and overwrites its `github_pull_request` JSON column with attacker-supplied data — data belonging to a repository that never authenticated this webhook.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type; `ExplicitParameters` schema only validates types/presence, not cross-org consistency; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` involved since this is an unauthenticated webhook path; model validations on `Repository`/`Stack` do not constrain webhook dispatch. The `ignore_ci: true` stack condition affects `Commit#deployable?` (short-circuiting CI requirements) but is not itself part of the auth check — it only affects what impact follows from `PullRequest`/commit mutation once the record is written across the authentication boundary; it is not required for the cross-tenant write itself, only amplifies downstream deploy eligibility.

### Impact Explanation
An attacker with no privileges on the victim's org can force a write to `Shipit::PullRequest#github_pull_request` for any repository/stack whose `full_name` they can guess or observe (repo names are public), as long as any Shipit-configured org lacks a webhook secret (or the attacker knows any org's secret). This is a payload for one repository (attacker's) causing a database mutation on another repository/stack's `PullRequest` record that never validated the request — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any `full_name` and any PR number, and combined with `ignore_ci: true` stacks the corrupted PR/commit metadata can influence merge/deploy eligibility decisions that consult that state.

### Likelihood Explanation
Preconditions: at least one Shipit-registered GitHub org configured without `webhook_secret` (common in real deployments — `verify_webhook_signature` explicitly treats a missing secret as "trust everything"), or knowledge of any one org's secret. No Shipit session, API token, or GitHub write access to the victim repo is required. The attacker only needs to craft an HTTP POST with a divergent `owner.login`/`full_name`, which is trivial and free to repeat.

### Recommendation
After successfully verifying the webhook signature using `repository_owner`, re-derive and enforce that the org portion of `params.dig('repository','full_name')` matches `repository_owner` (reject with 422 otherwise), or better, verify the signature using the org extracted from `full_name` itself rather than a separate `owner.login` field, so a single field determines both authentication scope and mutation scope.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in `Shipit.github_configs`: `"attacker-org"` with no `webhook_secret`, and `"victim-org"` with a real `webhook_secret`.
2. Create `victim-org/victim-repo` `Repository`, a `Stack` with `ignore_ci: true`, and a `PullRequest` with `number: 42` and known `github_pull_request` content.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body `{"action":"unassigned","number":42,"pull_request":{...attacker-controlled...},"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (not `422`).
5. Reload the victim `PullRequest` and assert `pull_request.github_pull_request` equals the attacker-supplied payload — proving `repository_owner ("attacker-org") != full_name org ("victim-org")` yet the write succeeded, breaking the claimed invariant.
