### Title
Missing zero-check on the `tps_interval` system variable allows division-by-zero in TPS-fee calculations - (File: storage.js)

### Summary
`tps_interval` is a network-wide, vote-controlled system variable (analogous to `observationFrequency` in the reported Olympus bug) that is used as a **divisor** in every TPS-fee calculation. None of the functions that consume it guard against a value of `0`, so if `tps_interval` is ever set to `0`, the fee computation degenerates to `Infinity`/`NaN`, exactly mirroring the reported pattern of an unchecked configuration parameter causing the dependent core logic to revert/malfunction.

### Finding Description
`tps_interval` is read from the votable `system_vars` table via `getSystemVar('tps_interval', ...)` and is fed directly into `exp(tps / tps_interval)` in three separate fee-calculation functions, with no check that the value is non-zero: [1](#0-0) [2](#0-1) 

`tps_interval` is seeded as a normal system var alongside `threshold_size`, `base_tps_fee`, and `tps_fee_multiplier`, and is updated through the standard numerical-vote governance mechanism (`numerical_votes` / `system_votes` tables), not hard-coded: [3](#0-2) 

Because the divisor comes from a governed variable rather than a compile-time constant, the same class of bug as the reported issue applies: the constructor/initializer path for this "config" value performs no positivity check, so any code path that can drive `tps_interval` to `0` will make `exp(tps / 0)` evaluate to `Infinity` (when `tps > 0`) or `NaN` (when `tps === 0`), which then propagates through `Math.round(...)` into the required/paid TPS fee (`getLocalTpsFee`, `getCurrentTpsFee`, `getCurrentTpsFeeToPay`, `getPaidTpsFee`).

I was not able to fully confirm within the available search budget whether the numerical-vote validation logic in `validation.js` enforces `tps_interval > 0` (only that it references `isNonnegativeInteger`/`isPositiveInteger`-style checks near these subjects); this should be verified directly in `validation.js` before treating the vote-path as fully closed. Regardless of the vote-path outcome, the consuming functions in `storage.js` themselves contain no defensive check against a zero divisor, which is the same root-cause pattern as the reported bug (missing validation of a critical parameter before it is used in dependent arithmetic).

### Impact Explanation
If `tps_interval` becomes `0` (via a successful governance vote, buggy migration, or any other path that writes `system_vars`), TPS-fee amounts computed by `getCurrentTpsFeeToPay`/`getPaidTpsFee` become `NaN`/`Infinity`. Since these values gate whether a posted unit carries a sufficient `tps_fee`, comparisons against `NaN` are always `false`, which can either (a) cause every unit to be treated as underpaying and rejected — a network unable to confirm new units — or (b) cause the fee requirement to be bypassed entirely, letting units through without paying the anti-spam TPS fee, undermining the fee market that protects DAG throughput. Either outcome is a network-wide correctness/availability failure, not a localized one.

### Likelihood Explanation
`tps_interval` is a votable system parameter reachable by ordinary unprivileged addresses posting `system_vote`/numerical-vote units (per the same mechanism used to seed `threshold_size`, `base_tps_fee`, `tps_fee_multiplier`), not an operator-only or hub-only setting. If the vote-aggregation/validation code does not strictly enforce `tps_interval > 0` (unconfirmed here), any coordinated voting bloc could drive the value to `0`, or a rounding/edge-case defect in the vote-tallying logic could produce `0` unintentionally. Even absent a vote-path bug, the complete absence of a defensive check in the consuming arithmetic itself makes this a real risk surface, matching the "missing check in constructor/initializer" bug class from the report.

### Recommendation
Add an explicit guard wherever `tps_interval` is consumed as a divisor, e.g. in `getLocalTpsFee`, `getCurrentTpsFee`, and `getCurrentTpsFeeToPay`:
```js
const tps_interval = getSystemVar('tps_interval', last_ball_mci);
if (!(tps_interval > 0))
    throw Error(`invalid tps_interval ${tps_interval}`);
```
Additionally, confirm and, if necessary, harden the numerical-vote validation path in `validation.js` so that a vote/value of `0` (or negative) for `tps_interval` (and similarly `threshold_size`, `base_tps_fee`, `tps_fee_multiplier` if used as divisors elsewhere) is rejected before it can ever be written to `system_vars`.

### Proof of Concept
1. Through the standard system-variable voting mechanism, cause `system_vars.value` for `subject='tps_interval'` to become `0` (either via a validation gap in the vote-tally path, or by demonstrating the seed/migration path in `initial_votes.js` could not itself prevent such a state going forward).
2. On the next call to `getCurrentTpsFeeToPay(...)` / `getPaidTpsFee(...)` in `storage.js`, `tps / tps_interval` evaluates to `Infinity` or `NaN` (division by `0`), which propagates through `Math.round(...)` into the computed required/paid TPS fee.
3. Because comparisons involving `NaN` are always `false`, any unit's `tps_fee` check against this required amount behaves unpredictably network-wide (either universally rejecting valid units or universally bypassing the fee requirement), demonstrating the DoS/consensus-inconsistency impact.
