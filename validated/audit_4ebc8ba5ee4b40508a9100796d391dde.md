## Title
Unhandled exception when computing AA dry-run trigger addresses crashes full nodes processing a posted unit with a private payment message - (File: network.js)

## Summary
`handleJoint()`'s `ifOk` callback in `network.js` builds a list of payment output addresses to check for new AA triggers before saving a newly accepted unit. It reads `msg.payload.outputs` for every message with `app === 'payment'` without checking that `msg.payload` exists. A valid, protocol-legal unit can contain a `payment` message with `payload_location: "none"` (a private payment, which by design has no inline `payload`, only `spend_proofs`). Such a unit thrown at any node reaches this code inside an `async` callback with no surrounding `try/catch`, producing an unhandled promise rejection that, under default Node.js behavior, terminates the process — a single-message crash of the full node, analogous to the `nord` `/action` panic described in the source report.

## Finding Description
In `network.js`, `handleJoint()`'s `ifOk` handler runs an optional "dry run" of any AA the just-accepted unit might trigger: [1](#0-0) 

```

```

This code filters all `payment` messages of the newly-accepted unit and unconditionally dereferences `msg.payload.outputs`. However, `validation.js` explicitly allows a `payment` message to have **no** inline `payload` when it is a private payment carried via `spend_proofs` (`payload_location: "none"`): [2](#0-1) 

```

    if (objMessage.payload_location !== "inline" && objMessage.payload_location !== "none")
        return callback("payment location must be inline or none");
    if (objMessage.payload_location === "none" && !objMessage.spend_proofs)
        return callback("private payment must come with spend proof(s)");
}
```

Such a message legitimately passes full validation and reaches `writer.saveJoint`, but before that, if the unit also contains any output that is addressed to a known AA (`objValidationState.count_primary_aa_triggers` is non-zero) and the operator has `conf.bDryRunNewTriggers` enabled, the code above executes `msg.payload.outputs` on the private-payment message, where `msg.payload` is `undefined`. This throws `TypeError: Cannot read properties of undefined (reading 'outputs')`.

```

```

The buggy `outputAddresses` computation omits the `&& msg.payload` guard that `getTrigger` uses, making it a straightforward oversight of the same class as the `nord` bug: user-controlled, protocol-valid input reaches an unguarded property access that panics/throws instead of being handled as a validation error.

Because the throw occurs synchronously inside an `async function` used as an event callback (`ifOk`) that nobody `await`s or wraps in `.catch()`, it becomes an unhandled promise rejection. `handleJoint` is invoked from `handleOnlineJoint`/`handleSavedJoint`/`handlePostedJoint`, which are reachable directly from a peer's `joint` justsaying, `post_joint` request, or a locally composed/forwarded unit — i.e., from any single unprivileged unit poster on the network: [4](#0-3) [5](#0-4) 

## Impact Explanation
Any full node running with `conf.bDryRunNewTriggers` enabled can be crashed remotely by a single unit that (a) validates successfully, (b) contains at least one output paying an existing AA address, and (c) also contains a private `payment` message (`payload_location: "none"`) anywhere in the same unit. On modern Node.js runtimes, an unhandled promise rejection by default terminates the process. A node crash stops that node from validating/confirming/relaying new units, directly matching the required impact class of "a network unable to confirm new units" if propagated to multiple full nodes running this feature (e.g., witnesses or hub operators who enabled dry-run trigger checking for early AA-crash detection, which is exactly the purpose the code comment states: "if it would crash, let it crash now, not when we execute the trigger for real" — except it crashes the whole node instead of just bouncing the trigger).

## Likelihood Explanation
The trigger requires no special privileges — an ordinary unit poster can construct a unit with a payment to an AA address plus an unrelated private payment message, sign it normally, and broadcast it. The only external precondition is that the receiving node has `conf.bDryRunNewTriggers` enabled, which is a legitimate, documented safety feature (not malicious operator behavior); nodes that adopt it to guard against exactly this class of AA-related crash are the ones exposed. Given the specific combination of message types required, likelihood is Medium, but the impact of an unauthenticated, single-message full node crash is High.

## Recommendation
Guard the `payload` dereference the same way `aa_composer.getTrigger()` does:

```js
const outputAddresses = objJoint.unit.messages
    .filter(msg => msg.app === 'payment' && msg.payload)
    .reduce((acc, msg) => acc.concat(msg.payload.outputs.map(output => output.address)), []);
```

More broadly, wrap the `bDryRunNewTriggers` block (and ideally the whole `ifOk` async callback) in a `try/catch` that reports the error via `ifUnitError`/logging instead of allowing any exception to propagate as an unhandled rejection, mirroring how `validation.validate()` itself carefully catches hashing/serialization errors and reports them through `ifJointError`/`ifUnitError` rather than throwing.

## Proof of Concept
1. Enable `conf.bDryRunNewTriggers = true` on a full node (as intended for early AA-crash detection).
2. Deploy or use any existing AA address `A`.
3. Compose and broadcast a unit with:
   - message 1: `app: "payment"`, `payload_location: "inline"`, base-asset payment with an output to `A` (any amount ≥ bounce fee), and
   - message 2: `app: "payment"`, `payload_location: "none"`, carrying valid `spend_proofs` for a private asset payment (no inline `payload`).
4. Once the unit passes validation and `objValidationState.count_primary_aa_triggers > 0`, `network.js`'s `ifOk` handler executes `msg.payload.outputs` on message 2, whose `payload` is `undefined`, throwing `TypeError: Cannot read properties of undefined (reading 'outputs')` inside the unguarded `async` callback, crashing the node process via an unhandled promise rejection.
