This confirms the multi-organization design: `Shipit.github(organization:)` maintains a separate `GitHubApp` instance (with its own `webhook_secret`) per organization key in `secrets.github`, as configured in `config/secrets.development.shopify.yml`. This directly confirms the cross-organization vulnerability I found: the webhook signature is verified against the secret belonging to `repository_owner`/`organization.login`, but the actual entity acted upon (`repository.full_name`, used by `Shipit::Webhooks::Handlers::Handler#repository_name` to find the target `Stack`) is an entirely different, unverified field from the same JSON body.

### Title
Webhook signature is verified against `repository.owner.login`'s org secret while handlers act on the unverified `repository.full_name` field, allowing cross-organization forged events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
Shipit supports multi-tenant GitHub configuration where each organization has its own GitHub App and `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository','owner','login')` [2](#0-1) . However, the event handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler`, pull-request handlers, `CheckSuiteHandler`) resolve the target `Stack`/`Repository` using a different field of the same payload, `repository.full_name`, via `Handler#repository_name` and `Handler#stacks` [3](#0-2) .

### Finding Description
The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository being acted upon**. Instead, the code verifies:
```
repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')
verified = Shipit.github(organization: repository_owner).verify_webhook_signature(sig, raw_post)
``` [2](#0-1) 

but then dispatches to handlers that resolve the affected `Stack` purely from `payload.dig('repository', 'full_name')`:
```
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [3](#0-2) 

Because `repository.owner.login` and `repository.full_name` are two independent fields inside the same attacker-controlled JSON body, and the HMAC signature is computed over the raw body using whichever organization's secret the attacker legitimately controls (any organization onboarded into the same multi-tenant Shipit instance, per `secrets.github` in `config/secrets.development.shopify.yml`) [4](#0-3) , an attacker who is a legitimate GitHub App owner/admin for **their own** onboarded organization (and therefore knows that org's `webhook_secret`) can craft a payload where `repository.owner.login` is their own org (so `verify_webhook_signature` succeeds) but `repository.full_name` names a **different** organization's repository. This lets the attacker's own valid signature drive events (`push`, `status`, `pull_request`, `check_suite`) against a victim organization's `Stack`, whose GitHub API calls are made using the stack's own `stack.github_api` (the victim org's installation token) [5](#0-4) .

The impact varies by handler:
- `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` for the victim stack using an attacker-chosen `after` SHA [6](#0-5) .
- `StatusHandler` injects forged commit statuses for the victim's commits by matching on `sha`, which can flip CI/merge-gate state (`commit.create_status_from_github!`) [7](#0-6) .
- If the forged status marks required checks as passing, this can feed into `MergeRequest#merge!`, which uses the victim stack's own `github_api` to merge/close and delete branches on GitHub [5](#0-4) .

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope: the signature check authenticates only that the request came from *some* onboarded organization's GitHub App, but every subsequent lookup and side effect (syncing commits, injecting statuses, potentially merging pull requests) is keyed off an unauthenticated field naming a *different* repository/organization. This can result in unauthorized cross-repository writes and forged CI status leading to unauthorized merges — impacts explicitly listed as Critical/High.

### Likelihood Explanation
This requires the attacker to control (or be an admin of) at least one organization that is legitimately onboarded to the same multi-tenant Shipit instance (i.e., know that org's `webhook_secret`), which is a normal, unprivileged-relative-to-other-orgs position in a shared Shipit deployment. No GitHub App private key, `ApiClient` token, or Shipit session is required — only the ability to send an HTTP POST to `/webhooks` with a validly-signed-for-their-own-org payload whose `repository.full_name` targets a victim stack.

### Recommendation
`WebhooksController#verify_signature` (or the individual `Handler#stacks`/`repository_name` resolution) should cross-check that the organization used to select/verify the webhook secret matches the owner embedded in `repository.full_name` (and reject the event, or additionally verify the resolved `Stack`'s `Repository#owner` matches `repository_owner`) before any handler acts on the payload.

### Proof of Concept
1. Onboard/control organization `attacker-org` in the shared Shipit deployment's `secrets.github`, knowing its `webhook_secret`.
2. Craft a `push` (or `status`) webhook payload where `repository.owner.login == "attacker-org"` but `repository.full_name == "victim-org/victim-repo"`.
3. Compute `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw JSON body, then POST it to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which succeeds.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")`, triggering `sync_github`/status injection against the victim's stack — despite the request never being verified with the victim organization's secret.
