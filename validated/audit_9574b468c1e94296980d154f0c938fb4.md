### Title
Cross-repository status webhook forgery via unscoped `Commit.where(sha:)` lookup causes write and broadcast on unrelated victim stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table, with no constraint tying the match to the repository/organization that the webhook's signature actually authenticated. An attacker who owns a small fork containing an unmodified upstream commit (identical `sha`) can send a validly-signed `status` webhook from their own repo/org and have it applied to every `Commit` record sharing that `sha`, including ones belonging to a victim's unrelated private stack, triggering `Commit#create_status_from_github!` → `add_status` → `Hook.emit(:commit_status, ...)` for that stack.

### Finding Description
The broken binding, stated as an equality, is:

`repository_owner_that_signed_the_webhook == owner_of_every_stack_whose_commit.sha_matches_params.sha`

This should always hold (a webhook should only mutate data belonging to the repository/org that produced and signed it) but does not.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and validates the payload against `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, see [1](#0-0) . This only proves the payload was signed with the webhook secret configured for `repository_owner`'s GitHub App/org — it says nothing about which `sha` values may be referenced inside the payload body, since GitHub statuses payloads are attacker/GitHub-controlled JSON for a repo the attacker owns.
2. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, see [2](#0-1) .
3. `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This query is **global** — it is not scoped to `Repository.from_github_repo_name(payload['repository']['full_name'])` or to any stack owned by `repository_owner`. Note the base `Handler` class does define a `stacks` helper scoped by `repository_name` [4](#0-3) , but `StatusHandler` does not use it.
4. `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }` [5](#0-4) , writing a `Status` row tied to the victim commit's `stack_id`.
5. `Status` creation triggers `after_commit :broadcast_update` (delegated to `commit`) and the test suite confirms `add_status` fires `Hook.emit(:commit_status, ...)`, which is delivered per-stack via `Hook.deliver`/`Hook.emit` [6](#0-5)  and observed in `expect_hook_emit(commit, :commit_status, expected_status_attributes)` in the existing test suite [7](#0-6) .

Because git commit `sha`s are content-addressed and identical across forks that share history (the described scenario: attacker forks upstream, keeps an unmodified commit), the same `sha` can legitimately exist as rows in multiple `Stack`s' `commits` tables — one belonging to the attacker's tracked fork/repo, another belonging to a victim's unrelated private Shipit stack that happens to track the same upstream commit. `verify_signature` only authenticates that the JSON body came from the org owning the webhook secret used (the attacker's own org for their own fork); it does not and cannot restrict which `sha`-matching `Commit` rows across the whole install get updated, since `StatusHandler` never re-checks repository/stack ownership against the payload's `repository.full_name`.

None of the listed guards prevent this: `verify_signature` validates HMAC per-organization only, `drop_unhandled_event` and `ExplicitParameters` schema only validate shape/presence of `sha`/`state`, and there is no `Repository`/`Stack` ownership check inside `StatusHandler#process`.

### Impact Explanation
A single crafted, validly-signed `status` webhook from an attacker-controlled repository writes a `Shipit::Status` record onto a completely unrelated, private/internal victim stack's commit — this is a "payload for one repository mutating another's stack/commit," matching the Critical category defined in scope. It also causes `Hook.emit(:commit_status, {commit:, stack:, status:})` to fire for the victim's stack, which is delivered to that stack's registered hooks (`Hook.deliver`) and, per the existing test helper conventions (`Pubsubstub.publish` on channel `stack.#{stack.id}`), broadcasts an "update" event to that stack's subscribers — revealing the existence of the victim stack and an updated CI state to the attacker's forged input, without the attacker being a subscriber, member, or maintainer of the victim's org/stack. This is repeatable against arbitrary shared-history shas and arbitrary victim stacks the attacker can guess or discover shas for (e.g., well-known open-source base commits tracked by many private forks).

### Likelihood Explanation
Preconditions: attacker needs (a) their own GitHub repository/org with a Shipit-configured webhook (trivial — they control this entirely, since Shipit webhook_secret is per-organization and attacker can simply not configure one, or use their own org's secret which they legitimately know since it's their own installation), and (b) a `sha` value that also exists in a victim's tracked `Stack#commits`. Since the scenario stipulates the attacker forks the victim's upstream repo and keeps an unmodified commit, this is trivially satisfiable — no secret of the victim's is needed. Cost is a single HTTP POST to `/webhooks` with a valid signature computed with the attacker's own known webhook secret. Fully repeatable and scriptable against any victim stack whose tracked shas are shared history.

### Recommendation
Scope `StatusHandler#process` (and ideally other handlers relying on bare `sha`/global lookups) to only commits belonging to stacks under the repository identified in the payload, e.g. use the existing `stacks` helper: `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the webhook's authenticated repository (`Repository.from_github_repo_name(payload['repository']['full_name'])`) is the actual owner of every commit that gets mutated, not merely a `sha`-collision anywhere in the database.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative — not to be placed under `test/` per rules but describing the required assertions):
1. Create `victim_stack` belonging to org `victim-org`/repo `victim-org/private-repo`, with a tracked `Commit` whose `sha == SHARED_SHA`.
2. Create `attacker_stack`/repo `attacker/fork` (or simply configure a webhook secret for `attacker` org) also containing a `Commit` with `sha == SHARED_SHA` (simulating shared upstream history).
3. Stub `Pubsubstub.expects(:publish).with { |channel, _payload, _opts| channel == "stack.#{victim_stack.id}" }` (or assert `Hook.emit` args for `victim_stack`).
4. `request.headers['X-Github-Event'] = 'status'`; POST body `{ sha: SHARED_SHA, state: 'success', ... }.merge(repository: { full_name: 'attacker/fork', owner: { login: 'attacker' } })`, signed with the `attacker` org's webhook secret (which is legitimately known/controllable by the attacker, not the victim's).
5. Assert response `:ok`, assert a new `Status` row was created for `victim_stack`'s commit (`assert_difference 'victim_commit.statuses.count', 1`), and assert the `Pubsubstub.publish`/`Hook.emit` expectation for `victim_stack`'s channel fired — proving `repository_owner_that_signed == 'attacker'` while `owner_of_mutated_stack == 'victim-org'`, i.e. the binding is broken.
