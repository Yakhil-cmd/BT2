### Title
Stale pool snapshot reused after mid-invocation mutation — `Context::cached_pool_sync_data` never invalidated - (File: contracts/controller/src/context.rs)

### Summary
`Context` is the invocation-local cache shared by every leg of a controller call. It caches three kinds of market data with different invalidation semantics: `market_indexes` has an explicit refresh hook (`put_market_index`, called by `positions/supply.rs`, `positions/debt.rs`, and `strategies/flash_position.rs` after each pool mutation), `spoke_usage`/`spoke_config`/`spoke_assets` are cleared by `reset_spoke_context`, but `pool_sync_data` — fetched once per `HubAssetKey` via `cached_pool_sync_data` — has **no invalidation path at all**. Its own doc comment states it "Does not accrue interest or refresh a cached snapshot" (context.rs:92-102). This is the direct analog of CVE-2019-18197: a cached pointer/snapshot that is not reset when the underlying state is freed/replaced, so a later bounds check runs against stale memory.

### Finding Description
`cached_pool_sync_data` populates `self.pool_sync_data` on first read and returns the cached `PoolSyncData` on every subsequent read within the same invocation (context.rs:94-102). `PoolSyncData` carries mutable market state — cash reserves, borrowed totals, and the stored indexes — not immutable parameters. Flows that mutate the pool mid-invocation and then consult sync data therefore evaluate against a pre-mutation snapshot:

- `strategies/flash_position.rs` mints debt into the pool *before* invoking the receiver callback and settles after it. The same `Context` spans the whole operation, and `put_market_index` refreshes only `market_indexes`, never `pool_sync_data`.
- Multi-leg position flows (supply/withdraw/borrow/repay legs and multi-leg liquidation execution) share one `Context`; a leg that commits a pool mutation leaves `pool_sync_data` holding the market's state *before* that commit, and any later leg whose gate reads sync data (reserve/cash checks, utilization or cap checks, min-borrow sizing) uses the stale values.

The reset mechanism demonstrably exists for indexes (`put_market_index`, context.rs:105-107) and for spoke state (`reset_spoke_context`, context.rs:177-181) but was never implemented for `pool_sync_data`, matching the bug class: a reset performed for some cached fields but omitted for one field "under certain circumstances" — exactly when the pool was mutated inside the same invocation.

### Impact Explanation
Any bounds check that consumes `PoolSyncData` after an earlier leg mutated the market is evaluated on stale values: a cash/borrowed figure that excludes the mutation. Depending on the consumer this permits a leg to pass a reserve or cap check it should fail (borrowing or withdrawing against reserves the pool no longer holds), or mis-sizes a min-borrow/collateral requirement. In the worst case this enables an unprivileged account to draw funds beyond the market's enforced limits — theft of user funds or positions pushed into under-collateralization that socialize into protocol insolvency via `apply_bad_debt_to_supply_index`. Severity: Medium–High depending on which gate consumes the stale snapshot.

### Likelihood Explanation
Reachable by any unprivileged caller: any multi-leg batch or `flash_position`/`multiply` strategy where the first leg commits a pool mutation and a later leg reads `cached_pool_sync_data` for the same `HubAssetKey`. The stale window is guaranteed whenever the first `fetch_pool_sync_data` call precedes a mutating leg. Exploitability magnitude depends on which specific gate reads sync data — I was unable to fully trace every `cached_pool_sync_data` consumer (`positions/supply.rs`, `positions/debt.rs`, `strategies/flash_position.rs`, `views.rs`) within the iteration budget, so the exact bound-check being bypassed should be confirmed; the structural defect (mutation with no cache reset) is verified in context.rs.

### Recommendation
Add an invalidation hook symmetric to `put_market_index`: either a `put_pool_sync_data`/`invalidate_pool_sync_data(hub_asset)` that every pool-mutating leg calls alongside `put_market_index`, or make `cached_pool_sync_data` re-fetch after any mutation flagged in the `Context`. Audit all call sites where a pool mutation and a `cached_pool_sync_data` read can coexist in one invocation (notably `flash_position.rs` and batched position legs).

### Proof of Concept
1. Open a `flash_position` (or a batched position call) that first triggers `cached_pool_sync_data(hub_asset)` for market M — e.g., a leg that checks reserves/caps — caching `PoolSyncData` S0.
2. The flow then mints debt / moves cash in M via the pool (the flash debt minted before the callback in `flash_position.rs`, or an earlier mutating leg), changing M's committed state to S1.
3. A subsequent leg or post-callback settlement in the same invocation calls `cached_pool_sync_data(M)` and receives S0 (context.rs:95-97 returns the cached entry), because no reset exists — the guard it feeds evaluates against stale cash/borrowed values and admits an operation the post-mutation state would reject.     /// Returns stored pool parameters and state, fetching once per hub asset.
    /// Does not accrue interest or refresh a cached snapshot.
    pub(crate) fn cached_pool_sync_data(&mut self, hub_asset: &HubAssetKey) -> PoolSyncData {
        if let Some(data) = self.pool_sync_data.get(hub_asset.clone()) {
            return data;
        }
        let pool_addr = self.cached_pool_address();
        let data = fetch_pool_sync_data(&self.env, &pool_addr, hub_asset);
        self.pool_sync_data.set(hub_asset.clone(), data.clone());
        data
    }

    /// Replaces the cached index with a pool mutation's updated index.
