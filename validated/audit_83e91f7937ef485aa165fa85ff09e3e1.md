### Title
Shared/multisig address definitions accepted from a peer without verifying that the local co-signer's branch is actually load-bearing, allowing an "OR-trick" address that a counterparty can drain alone - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` and its helper `validateAddressDefinition()` only check that the proposed multi-party address definition is *syntactically* valid (`Definition.validateDefinition`) and that the local user's address appears *somewhere* in the definition tree (`extractAddressPathsFromDefinition` / `determineIfIncludesMeAndRewriteDeviceAddress`). Neither step verifies that the user's signing branch is actually *necessary* for spending, i.e. that there is no alternate `or` branch that lets the counterparty (or any other listed member) authorize a spend without the user's cooperation. This mirrors the reported bug class: an authority-bearing structure (the market vault / here, the shared spending address) is created and accepted without validating that all co-authorities that are supposed to have joint control genuinely do.

### Finding Description
`wallet_defined_by_addresses.js` builds shared/multisig addresses out of an arbitrary `arrDefinition` boolean tree (`and`/`or`/`r of set`/`weighted and` of `["address", ...]` leaves) supplied by a remote device over the p2p wallet-chat protocol: [1](#0-0) 

The only checks performed are:
1. `objectHash.getChash160(body.definition) === body.address` (definition hashes to the claimed address). [2](#0-1) 
2. Every `signing_path` in `body.signers` matches an `["address", ...]` leaf extracted from the definition tree via `extractAddressPathsFromDefinition`. [3](#0-2) [4](#0-3) 
3. `determineIfIncludesMeAndRewriteDeviceAddress` only requires that *one* of the member addresses resolves to `my_addresses` or `shared_addresses` — i.e. that the local user appears *somewhere* in the tree. [5](#0-4)

None of these checks establishes that the local co-signer's leaf is on every viable spending path. Because `or` is a valid top-level/nested operator in address definitions (as validated generically by `definition.js`'s `evaluate()` for `'or'`/`'and'`), a malicious counterparty can propose a definition such as:

```
["or", [
  ["and", [ ["address", myAddress], ["address", peerAddress] ] ],  // looks like a 2-of-2
  ["address", peerAddress]                                          // but peer alone can also satisfy it
]]
```

`extractAddressPathsFromDefinition` will find `myAddress` at some path and `peerAddress` at two paths, all of `body.signers` will validate, `determineIfIncludesMeAndRewriteDeviceAddress` will succeed (my address is present), and `Definition.validateDefinition` will accept the tree as complexity- and syntax-valid. `addNewSharedAddress` then persists the address and the UI/wallet treats it as a jointly-controlled (e.g. 2-of-2 "safe"/escrow) address, when in fact the counterparty alone satisfies the `or` and can sign and spend unilaterally at any time.

### Impact Explanation
Any funds a user is later induced to send to (or that accumulate at) such a shared address — because they believe it requires their co-signature (e.g. an escrow, joint-savings, or arbiter-style address) — can be spent by the malicious counterparty alone via the independently-satisfiable `or` branch, without the victim's knowledge or consent. This is unauthorized spending / theft of funds, directly matching the accepted-impact class ("concrete unauthorized spending" of funds controlled by what is presented as a jointly-authorized account), analogous to the reported vault-authority bug where an unchecked authority could drain funds meant to be jointly/program-controlled.

### Likelihood Explanation
The entire flow is reachable by any unprivileged correspondent device that can send a `new_shared_address`/`create_new_shared_address` p2p message — this is the standard, unauthenticated wallet-chat message path already used for legitimate co-signer negotiation, so no privileged position is required. Building a definition with a benign-looking `and` branch plus a hidden always-satisfiable `or` branch requires only knowledge of the public wallet protocol and is straightforward to construct; the victim's software performs no analysis of whether the "safe-looking" branch is actually the only branch, so the flaw is not something the victim can detect from the definition's superficial presence checks.

### Recommendation
When accepting a shared-address definition from a remote party, in addition to the current syntactic/hash checks, statically analyze the boolean tree to ensure the local member's address (and any other addresses that are supposed to jointly co-sign) is *conjunctively required on every satisfying assignment* — e.g., reject definitions containing any `or` branch that can be satisfied without the local signing path (or, more generally, without all declared "signers" for a specific role), or explicitly warn/require user confirmation showing the full decoded spending conditions (not just member list) before persisting the shared address and allowing funds to be sent to it.

### Proof of Concept
1. Attacker (device B) initiates a "create shared address" proposal to victim (device A) with:
   - `body.definition = ["or", [ ["and", [["address","$address@A"], ["address","$address@B"]]], ["address","$address@B"] ]]`
   - `body.signers` mapping the two `and` leaves' paths to A's and B's real addresses and the standalone `or` leaf to B's real address again (a distinct signing path, e.g. `r.1`).
2. A's `handleNewSharedAddress` runs:
   - hash check passes (attacker computes the definition and its chash correctly),
   - `extractAddressPathsFromDefinition` finds `myAddress` present at `r.0.0`, satisfying the "signer for every def path" check,
   - `determineIfIncludesMeAndRewriteDeviceAddress` succeeds because `myAddress` is in `my_addresses`,
   - `validateAddressDefinition` accepts the tree as a syntactically valid boolean formula.
3. `addNewSharedAddress` persists the address; A's wallet displays it as a 2-of-2 shared/joint address.
4. Victim A sends funds to this address believing B cannot spend without A's cooperation.
5. B signs a payment unit using only the `r.1` (`["address", B]`) branch of the `or`, satisfying the definition alone, and spends the funds without A's signature — demonstrating unauthorized spend of funds from an address presented as requiring joint authority.

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
