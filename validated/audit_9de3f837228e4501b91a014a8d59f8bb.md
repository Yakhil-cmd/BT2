### Title
Webhook signature verification is keyed on `repository.owner.login`, but write actions are keyed on `repository.full_name` — allowing a cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against using `repository.owner.login` (falling back to `organization.login`) taken from the **unverified** JSON body itself. Every `Handler` subclass, however, resolves the target `Stack`/`Repository` to act on using a *different* field of that same unverified body: `repository.full_name`. Because Shipit supports multiple independently-configured GitHub organizations/apps (each with its own `webhook_secret`), an attacker who knows the secret for *any one* configured organization (e.g. their own org, where they legitimately installed the Shipit GitHub App) can forge a webhook whose `repository.owner.login` names that org (so the correct, attacker-known secret is selected and the HMAC — which the attacker computes themselves — validates), while `repository.full_name` names an arbitrary victim repository/stack tracked by the same Shipit instance. The handler then executes against the victim stack.

### Finding Description
`verify_signature` does: [1](#0-0) [2](#0-1) 

`github_app = Shipit.github(organization: repository_owner)` picks the app config/secret by the attacker-controlled `repository.owner.login`/`organization.login` field, then verifies the raw POST body's HMAC against that org's secret. Shipit is explicitly designed to host multiple orgs, each with its own `webhook_secret`: [3](#0-2) 

Once verification passes, `create` dispatches to handlers using the same raw, unverified body: [4](#0-3) 

All `Handler` subclasses resolve the stack(s) to mutate via `repository.full_name`, a completely different field than the one used for signature-key selection: [5](#0-4) 

For example, `CheckSuiteHandler` writes check-run refresh state directly onto commits of any stack matched by `full_name`/branch/sha taken from the payload: [6](#0-5) 

And the `status` handler creates a `Status` record directly from attacker-supplied fields (`state`, `context`, `target_url`, `description`) for whatever commit/stack `full_name` resolves to, as shown by the existing test asserting the created `Status` fields come straight from the payload: [7](#0-6) 

Because the binding "which organization's secret authenticated this request" is never checked against "which repository/stack the handler subsequently writes to," an attacker with a valid secret for org A can impersonate GitHub for org B's repositories.

The binding broken, as an equality that should hold but doesn't:
`organization selected via repository_owner (used to pick the verifying webhook_secret)` == `repository selected via repository.full_name (used by the Handler to pick the Stack that is written)`

Before the attack: only GitHub, holding the real per-organization `webhook_secret`, can produce a validly-signed webhook for a given `repository.full_name`.
After the attacker's crafted request: any actor holding *any one* configured org's `webhook_secret` can produce a validly-signed webhook whose `owner.login` matches that org (satisfying `verify_signature`) while its `full_name` names an unrelated, victim-owned repository/stack, which the handler then writes to.

### Impact Explanation
Using the `status` webhook handler, an attacker can fabricate a passing CI/status context on a specific commit of a victim's tracked stack (e.g. satisfying `ci.require` contexts configured in `shipit.yml`), which can unlock the "Deploy" button for a commit that never actually passed CI, directly enabling an unauthorized deploy — one of the explicitly listed Critical impacts ("an unauthorized deploy, rollback or merge"). The `check_suite` handler similarly lets an attacker inject fabricated check-run state for a victim stack's commits. This crosses a real authentication boundary (forging authenticated write actions against a repository/organization the attacker does not control) without requiring a Shipit session, API token, or GitHub write access to the victim repo — only knowledge of a `webhook_secret` for some org configured on the same Shipit instance.

### Likelihood Explanation
Exploitability requires the attacker to know one legitimate `webhook_secret` configured in this Shipit instance — realistically satisfiable by an attacker who administers their own GitHub organization/repo and has installed the same shared Shipit deployment's GitHub App on it (a common multi-tenant setup this engine explicitly supports, as shown by `config/secrets.development.shopify.yml` and `docs/setup.md`). No repository push/write access to the victim repository, no Shipit account, and no GitHub App private key are needed — only crafting an HTTP POST with a correctly computed HMAC using the attacker's own known secret and a body where `owner.login` and `full_name` disagree.

### Recommendation
Bind signature verification to the same repository identity the handler subsequently acts on. Specifically: after selecting the `GitHubApp` via `repository_owner`, verify that the resolved organization actually matches the owner segment of `repository.full_name` used by `Handler#stacks`/`#repository_name`, and reject the webhook (422) if they diverge. More robustly, look up the target `Repository`/`Stack` record first (by `full_name`), derive `organization` from the *stored* repository record rather than solely from the untrusted payload, and use that organization's `webhook_secret` for verification — ensuring the same identity is used to both authenticate and authorize the write.

### Proof of Concept
1. Attacker creates/administers GitHub org `attacker-org` and installs the shared Shipit GitHub App on it, obtaining knowledge of the `webhook_secret` configured for `attacker-org` in Shipit's `secrets.yml` (`Shipit.github(organization: 'attacker-org')`).
2. Attacker crafts a `status` (or `check_suite`) webhook JSON body where:
   - `repository.owner.login` = `"attacker-org"` (so `WebhooksController#repository_owner` resolves to `attacker-org`, and `verify_webhook_signature` checks against `attacker-org`'s secret, which the attacker knows).
   - `repository.full_name` = `"victim-org/victim-repo"` (a repository Shipit tracks and that the attacker does not own).
   - `sha`, `state: "success"`, `context: "ci/required-check"` set to match a commit awaiting deploy on the victim's stack.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, raw_body)` and POSTs it to `/github/webhooks`.
4. `verify_signature` passes (correct secret for the claimed `attacker-org`).
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs `StatusHandler`, which resolves `stacks` via `repository.full_name` = `victim-org/victim-repo`, and creates a fabricated `Status` (`success`) on the targeted commit — satisfying `ci.require` and enabling deploy of a commit that never passed real CI, without ever touching `victim-org`'s actual `webhook_secret` or GitHub credentials.
