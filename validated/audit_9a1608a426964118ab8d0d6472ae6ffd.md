This confirms a multi-organization Shipit deployment (`test/dummy/config/secrets_double_github_app.yml`) configures a separate `webhook_secret` per GitHub organization, and `Shipit.github(organization:)` looks up that org's `GitHubApp` config by name to verify signatures. This is exactly the kind of binding mismatch the task targets.

### Title
Webhook signature is verified against `repository.owner.login`, but payload handlers dispatch on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` in the JSON body, but the handlers that actually act on the payload (`Handler#stacks`, used by `PushHandler`, and similar lookups in PR/handler classes) key off `repository.full_name`, a separate, independently-attacker-controlled field in the same unsigned-until-verified JSON body.

### Finding Description
`verify_signature` computes `repository_owner` from the payload and fetches that organization's `GitHubApp` (and its `webhook_secret`) to validate `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the raw, already-parsed body straight to the event handlers without re-deriving or cross-checking the org: [3](#0-2) 

Handlers, however, resolve the target `Stack`/`Repository` using a *different* field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

For example `PushHandler` calls `stacks` (derived from `repository.full_name`) and triggers `stack.sync_github(expected_head_sha: params.after)` for any matching, non-archived stack: [5](#0-4) 

`Shipit.github(organization:)` supports (and the fixtures demonstrate) multi-org deployments where each org has its own independent `webhook_secret`: [6](#0-5) [7](#0-6) 

In such a deployment, the binding the signature check is supposed to enforce is: `signing organization == acted-upon repository owner`. Because `repository.owner.login` (used to select the HMAC key) and `repository.full_name` (used to select the `Stack`/`Repository` acted on) are two independent, attacker-supplied fields in the same JSON body, this equality is never actually checked. An attacker who legitimately controls one onboarded GitHub organization (`OrgOne`) and therefore knows/can produce a valid signature under `OrgOne`'s `webhook_secret` can set `repository.owner.login = "OrgOne"` (so the signature check passes) while setting `repository.full_name = "OrgTwo/victim-repo"` (so the handler acts on a stack belonging to a completely different, unrelated organization/repository).

### Impact Explanation
This breaks the trust boundary between "the org that authenticated the webhook" and "the repository that gets written to." A malicious webhook can force `GithubSyncJob`/`sync_github` to run against another organization's stack (updating heads, syncing commits, driving check-run refreshes, PR label capture, etc. depending on which handler is targeted), i.e. cross-organization/cross-repository state manipulation. Depending on which handler is reached this can escalate to state changes on stacks the attacker does not own, meeting the "cross-repository writes" bar for a High/Critical-class engine finding.

### Likelihood Explanation
Likelihood is High for any Shipit deployment using the multi-organization `github:` config format (explicitly supported and tested, e.g. `secrets_double_github_app.yml`). Any actor who is a legitimate, authenticated user/integrator for one onboarded organization (i.e., can get a webhook delivered/signed for that org, such as by installing the configured GitHub App on a repo they control) can trivially forge the `repository.full_name` field to point at any other tracked repository, since only `repository.owner.login` is used for key selection and no consistency check ties it back to `full_name`.

### Recommendation
After signature verification, re-validate that `repository.full_name`'s owner segment matches the `repository.owner.login` (or `repository_owner`) value used to select the signing organization, and reject the webhook (422) if they diverge. Alternatively, derive the signing organization directly from `repository.full_name` instead of from a separate `repository.owner.login` field, so there is a single source of truth for both signature verification and dispatch.

### Proof of Concept
1. Deploy Shipit with multi-org config, e.g. `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately controls a repo under `OrgOne` and has the GitHub App installed there, so GitHub will sign webhooks for that repo with `OrgOne`'s `webhook_secret` (or the attacker independently learns/derives `OrgOne`'s secret through legitimate means available to an `OrgOne` member).
3. Attacker crafts (or replays with modification, since HMAC does not need to be recomputed if secret is known) a `push` event payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgOne" },
       "full_name": "OrgTwo/victim-repo"
     }
   }
   ```
4. `verify_signature` computes `repository_owner = "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and validates the HMAC using `OrgOne`'s secret - it passes.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks` lookup resolves `Repository.from_github_repo_name("OrgTwo/victim-repo")`, and the handler proceeds to call `stack.sync_github(expected_head_sha: ...)` on a stack the attacker does not own, entirely on `OrgOne`'s validated signature.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
