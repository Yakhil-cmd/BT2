### Title
Webhook signature verification binds only to the payload's claimed organization, while `StatusHandler` applies the status update to any commit matching the SHA — enabling cross-tenant commit-status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using the `repository.owner.login` (or `organization.login`) field taken directly from the *unverified* payload, then only checks that the signature matches that specific organization's secret. It never checks that the entity being mutated by the event handler (a `Commit`/`Stack` belonging to a specific `Repository`) actually belongs to that same organization. `StatusHandler#process` compounds this by resolving the target purely from `params.sha`, scanning the **entire** `Commit` table with no stack/repository scoping at all.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body and used to pick the `GitHubApp` instance whose `webhook_secret` will validate the signature: [3](#0-2) 

The signature only proves the request was signed with the secret configured for **that named organization** — it says nothing about which repository/commit the payload's other fields describe. `StatusHandler`, however, ignores the verified organization entirely and updates every `Commit` row in the database whose `sha` matches the attacker-controlled `params.sha`: [4](#0-3) 

This breaks the binding `verified organization == repository being mutated`. A user with legitimate control of a webhook for Organization A (e.g., an org admin who configured Shipit for their own org/repo and therefore possesses/can generate a valid `X-Hub-Signature` for A's `webhook_secret`) can submit a `status` event whose signature validates against Organization A, but whose `sha` corresponds to a commit belonging to an unrelated Organization B's stack also hosted on the same shared Shipit instance. `Commit.where(sha: params.sha)` will match and update B's commit regardless of which org's secret signed the request.

`CheckSuiteHandler` and `PushHandler` also derive their target purely from `payload.dig('repository', 'full_name')` (via `Handler#repository_name`) rather than from the organization actually verified by the signature check, so the same class of confusion (verified org vs. acted-upon repository) generally applies across handlers, but `StatusHandler` is the most severe because it has *no* repository scoping whatsoever: [5](#0-4) 

### Impact Explanation
Commit statuses in Shipit are used to gate deployability (required/soft/blocking checks per stack). Forging a "success" status on a commit belonging to a different tenant's repository, without ever having credentials, GitHub App access, or webhook secret for that tenant, lets an attacker mark an otherwise unverified/failing commit as deployable in a stack they do not control — a cross-tenant write that can enable an unauthorized deploy, matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy"). The prerequisite is only knowledge of a target commit SHA (commonly public information for any repo whose contents/commits are visible) and control over one legitimate, unrelated organization's webhook signing secret on the same multi-tenant Shipit instance.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator/owner of at least one organization/GitHub App configured on the shared Shipit instance (a low bar in multi-tenant deployments, and the engine's docs explicitly describe per-organization `webhook_secret` configuration), plus knowledge of a target commit SHA in another tenant's repository. No GitHub App private key, `ApiClient` token, or session for the victim org is needed — only the ability to sign a webhook payload with credentials belonging to a *different, unrelated* organization.

### Recommendation
In `WebhooksController#verify_signature` and in each `Handler`, cross-check that the organization used to validate the signature matches the owner of the repository/stack/commit the handler is about to mutate (e.g., resolve `Repository`/`Stack` and assert `stack.repository.owner == repository_owner` before dispatching). For `StatusHandler` specifically, scope the `Commit` lookup to commits whose stack's repository owner matches the verified `repository_owner`, rather than querying `Commit.where(sha:)` globally.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `docs/setup.md` guidance), each hosting a stack Shipit tracks.
2. As an administrator of `org-a` (or anyone who can compute a valid HMAC with `org-a`'s `webhook_secret`), find a target commit SHA that belongs to `org-b`'s tracked repository (e.g., a public commit SHA).
3. Send `POST /webhooks` with header `X-Github-Event: status`, body:
```json
{
  "sha": "<org-b commit sha>",
  "state": "success",
  "context": "required-ci-check",
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/some-repo"}
}
```
signed with `org-a`'s webhook secret in `X-Hub-Signature`.
4. `verify_signature` validates successfully because `repository.owner.login` is `org-a` and the signature matches `org-a`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds and updates the `org-b` commit, creating a forged `success` status via `commit.create_status_from_github!(params)` — even though the request was never signed by anything belonging to `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
