### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler acts on the repository named in `repository.full_name` - allowing a valid signer for one org to forge events for stacks under a different org ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) 
Every downstream handler, however, resolves the target `Repository`/`Stack` from a *different* JSON field: `payload.dig('repository', 'full_name')`. [2](#0-1) [3](#0-2) 

### Finding Description
In multi-tenant configurations, Shipit can be configured with one GitHub App/secret per organization, selected via `Shipit.github(organization:)`, which looks up `github_app_config(organization)` in `secrets.github`: [4](#0-3) 

The webhook signature check binds the *verification key* to `repository.owner.login` (the organization sub-key of the JSON body), not to the repository that will actually be acted upon:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

Once the signature is accepted, the raw JSON is dispatched unchanged to every registered handler for the event (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`): [6](#0-5) 

But those handlers derive the actual target repository/stack from `repository.full_name`, an entirely separate, unrelated field of the same body: [7](#0-6) 

`PushHandler#process` then invokes `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching that `full_name` and branch: [8](#0-7) 

The equality that the engine implicitly relies on but never enforces is:
`organization that authenticated the signature (repository.owner.login)` == `organization/repository that the handler mutates (repository.full_name)`.

Nothing in the code checks that `repository.full_name` starts with (or otherwise matches) `repository.owner.login`. An attacker who administers their own GitHub organization "OrgA" (and therefore knows/controls the `webhook_secret` registered for OrgA in `secrets.github.OrgA`) can craft an arbitrary JSON payload, set `repository.owner.login` to `"OrgA"` so the HMAC is computed/verified with OrgA's secret, but set `repository.full_name` to `"OrgB/private-repo"` — a repository belonging to a completely different, unrelated tenant configured on the same Shipit instance. The signature check passes (it only proves the attacker knows OrgA's secret), yet the handler resolves and mutates stacks belonging to OrgB.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credentials authenticated the request" and "the repository whose stacks are written to," which is explicitly one of the vulnerability classes in scope. Concretely, with the `push` handler an attacker-controlled `after` SHA and `full_name` targeting a victim org's stack can cause `Stack#sync_github` to run against a commit chosen by the attacker for a repository the attacker does not own, potentially advancing `undeployed_commits`, triggering continuous-deployment logic, or corrupting the deploy state of an unrelated tenant — an unauthorized cross-repository/cross-organization action performed without any credential belonging to the victim organization. Other handlers (`status`, `check_suite`, `pull_request/*`) exhibit the same pattern, since they all inherit `repository_name` from `Handler#repository_name`, so CI status can be forged and PR/review-stack lifecycle actions (archive/unarchive, review-stack creation) can be triggered cross-tenant as well.

### Likelihood Explanation
This is only exploitable when the deployment is configured with the documented multi-organization schema (`secrets.github.<org>.webhook_secret` per org), which the engine explicitly supports and documents for hosting multiple GitHub orgs on one Shipit instance: [9](#0-8) 
In that configuration, any tenant organization administrator (who legitimately knows their own org's webhook secret because they configured it) can mount this attack against any other tenant on the same instance without needing that tenant's credentials — a low-effort, unprivileged-relative-to-the-victim escalation.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select the signing secret matches the owner of the repository being acted on — e.g., verify that `params.dig('repository', 'owner', 'login')` (or `organization.login`) equals the owner segment of `params.dig('repository', 'full_name')`, and reject the request (422) if they diverge. Alternatively, resolve the target `Repository` first and derive the verification organization strictly from that same repository record rather than trusting an independent field of the unverified-at-that-point JSON body.

### Proof of Concept
1. Shipit is deployed with `secrets.github` containing both `OrgA` and `OrgB` (multi-org schema), each with tenant stacks tracked (e.g. `OrgB/victim-repo` has a stack with continuous deployment enabled).
2. Attacker is an administrator of `OrgA` and therefore knows `secrets.github.OrgA.webhook_secret` (they configured GitHub App/webhook settings for their own org).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-that-exists-in-OrgB/victim-repo>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: 'OrgA')` and validates the signature successfully (see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `Shipit::Handlers::PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves stacks via `Repository.from_github_repo_name('OrgB/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: <attacker sha>)` on the victim's stack — a cross-organization action performed using only the attacker's own org's webhook secret.

  module Webhooks

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
