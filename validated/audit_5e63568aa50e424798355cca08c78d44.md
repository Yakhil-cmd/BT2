### Title
Webhook signature verifies the `organization`/`repository.owner.login` field while all event handlers act on the unrelated `repository.full_name` (or bare commit `sha`) field — allowing any onboarded organization to forge writes on another organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by looking up the GitHub App configuration for the organization named in `repository.owner.login` (or `organization.login`) and validating the HMAC signature against **that** organization's `webhook_secret`. Every event handler, however, determines *which* `Stack`/`Repository`/commit to mutate using a completely different, unauthenticated field: `repository.full_name` (in `Shipit::Webhooks::Handlers::Handler#repository_name`) or a bare `sha` (for status events). Nothing cross-checks that the authenticated `repository.owner.login` actually matches the repository referenced by `full_name`/`sha`. Any org that is legitimately onboarded to a shared, multi-tenant Shipit instance (and therefore knows its own `webhook_secret`) can sign a payload with its own secret while pointing `repository.full_name` (or `sha`) at a victim org's stack/commit.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb#verify_signature` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from attacker-controlled JSON (`params.dig('repository','owner','login')`), and is used purely to pick *which* org's `webhook_secret` to validate against (`Shipit.github(organization: repository_owner)`), as configured per-org in `config/secrets.development.example.yml`'s multi-org block. This lets a legitimate low-privilege org (already onboarded with its own App/secret) always pass signature verification for payloads it self-signs.

Once verified, `Shipit::Webhooks.for_event(event)` dispatches to a handler that resolves the actual object to mutate from a *different, unauthenticated* field: [3](#0-2) 

`PushHandler` (and other handlers) use this `stacks` helper to find and mutate a `Stack` purely by `repository.full_name`, with no relation to the `repository.owner.login` that was cryptographically verified: [4](#0-3) 

The equality the code implicitly (and incorrectly) assumes is:
`organization authenticated via repository.owner.login (signature check) == organization that owns repository.full_name (object mutated)`.
Nothing enforces this equality — an attacker fully controls both fields in the raw POST body before signing it with their own valid secret.

Status/commit-status webhooks similarly locate and overwrite a `Status` purely by `sha`/`repository` full name, with attacker-controlled `state`, `description`, `target_url`, independent of the org whose secret validated the request, as confirmed in the test suite: [5](#0-4) 

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," per the analog rule set. A malicious org admin who legitimately owns a low-privilege organization onboarded to the same shared Shipit instance can:
- forge `push` events that reference a victim org's `Stack` via `repository.full_name`, forcing `GithubSyncJob`/`sync_github` calls with an attacker-chosen `expected_head_sha` on a stack they do not own [4](#0-3) ;
- forge `status`/`commit_status` events that write an arbitrary `state` (e.g. `success`) onto a specific victim commit's `Status`, which is exactly the kind of check `ci.require` in `shipit.yml` relies on to gate deploys, potentially enabling an unauthorized deploy of unreviewed code on the victim's stack — matching the "unauthorized deploy" and "cross-repository writes" impact tiers.

The attack requires only a credential (the attacker's own onboarded org's `webhook_secret`) that is legitimate and unprivileged with respect to the victim — it grants no access to the victim's repository, GitHub App, or GITHUB_TOKEN, yet lets the attacker mutate victim-owned Shipit state.

### Likelihood Explanation
Any deployment of this engine as a multi-tenant service (the documented `config/secrets.development.example.yml` multi-org configuration is explicitly supported) has multiple orgs each possessing their own valid `webhook_secret`. Constructing a payload with a mismatched `repository.owner.login` vs `repository.full_name`/`sha` requires no special access beyond crafting and signing a raw HTTP POST, which is trivial for any org member who can read their own org's webhook secret from their GitHub App settings.

### Recommendation
In `WebhooksController#verify_signature` (or in the base `Handler`), after signature verification, additionally verify that the repository referenced by `full_name` (or the repository owning the target `sha`/commit) belongs to the same GitHub organization/owner login (`repository_owner`) that was cryptographically authenticated. Reject the webhook if these do not match.

### Proof of Concept
1. Attacker is an admin of `attacker-org`, which is legitimately configured as a separate GitHub App/organization in Shipit's multi-org `secrets.yml`, and therefore knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POSTs to `/github/webhooks`.
4. `verify_signature` reads `repository_owner == "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the signature validates successfully [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `repository.full_name == "victim-org/victim-repo"` [6](#0-5)  and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a stack the attacker has no legitimate access to [4](#0-3) .
6. The equivalent construction against a `status` event lets the attacker forge a `success`/`pending` `Status` on an arbitrary victim commit, independent of `attacker-org`'s actual repositories, potentially satisfying `ci.require` checks used to gate victim deploys.
