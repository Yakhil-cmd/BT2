### Title
Sustained accrual on a large market panics `accrue_step` before the borrow-index cap, permanently freezing all market entrypoints - (File: common/src/rates/simulate.rs)

### Summary
The Redis CVE bug class is "a crafted input triggers a crash that kills the process." The analog in XOXNO Lending is an unprivileged-triggerable arithmetic panic in the interest-accrual step: once scaled debt × borrow index exceeds `i128`, `scaled_to_original` panics with `MathOverflow`. Because every pool verb accrues interest first via `synced_market` → `interest::global_sync`, the panic brick-walls the entire market — no supply, withdraw, repay, liquidate, seize, or `update_indexes` — permanently locking supplier and collateral funds. The protocol's own test asserts this freeze.

### Finding Description
`accrue_step` (common/src/rates/simulate.rs:60-61) begins every compounding step by unscaling positions to original value:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` (common/src/rates/scaling.rs:14-16) is `scaled.mul(env, index)` → `mul_div_half_up` (common/src/math/fp_core.rs:108-118), which panics with `GenericError::MathOverflow` when `borrowed * borrow_index` overflows `i128`/`I256`-to-`i128` conversion. The borrow index is capped at `MAX_BORROW_INDEX_RAY` (10³⁶) by `update_borrow_index`, but a market with very large scaled balances hits the value ceiling — `borrowed × index > i128::MAX` — well before the index cap engages.

Every public market mutation loads the market through `synced_market` (contracts/pool/src/ops/mod.rs:30-34), which calls `interest::global_sync` (contracts/pool/src/interest.rs:20-33) → `accrue_chunk` → `accrue_step`. Once the panic threshold is crossed, `global_sync` reverts before any state is written, so the panic is self-reinforcing: each subsequent call re-attempts the same accrual over an ever-larger `elapsed_ms` and reverts identically.

### Impact Explanation
Permanent freezing of funds. Once the market crosses the RAY-value ceiling, no entrypoint on that market's book can execute: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, `clean_bad_debt`/`recapitalize` cannot run, and `update_indexes` itself reverts. All supplied tokens and collateral positions referencing that market's shares are locked forever. The protocol test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361) explicitly asserts `try_withdraw_raw` and `try_repay` fail with `MATH_OVERFLOW` and that "the market is frozen: no repay, no withdraw, no liquidation."

### Likelihood Explanation
Reachable entirely through unprivileged entrypoints: an attacker supplies a large principal (`supply`), borrows near-maximum (`borrow`), then lets interest compound; `update_indexes` is permissionless, so anyone can advance accrual. The precondition is a market whose `borrowed × borrow_index` product exceeds `i128::MAX` (~1.7×10³⁸), i.e., roughly 170× index growth on a very large 18-decimal market at sustained high utilization (the test reaches it within a bounded number of years at ~98% utilization on a steep rate curve). This requires a whale-scale deposit and, depending on deployed caps, sufficiently high borrow caps — a real but heavyweight condition. Note: this freeze is documented behavior in the repo's own test suite, which weakens novelty but does not change reachability or impact.

### Recommendation
Saturate or clamp the value computation instead of panicking: in `accrue_step`, compute `borrowed_original`/`supplied_original` via a saturating multiply-divide (as `calculate_scaled_cap` already does with `mul_div_floor_saturating`), or early-exit accrual once `borrow_index == MAX_BORROW_INDEX_RAY` so interest stops accruing without computing overflowing values. Alternatively, bound market share supply (`supplied`/`borrowed` scaled caps) at listing/enforcement time so `scaled × index` can never exceed `i128::MAX` before the index cap engages.

### Proof of Concept
The repo's own test demonstrates the sequence (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361):

1. `supply(BOB, "BIG18", principal)` — large 18-decimal market.
2. `supply(ALICE, "COL", ...)` then `borrow(ALICE, "BIG18", ~98% of principal)` — whale-scale debt at high utilization.
3. Advance ledger time in `YEAR_SECS` steps calling permissionless `update_indexes` until accrual crosses the RAY-value ceiling: `try_update_indexes_for(&["BIG18"])` returns `MathOverflow`.
4. Thereafter `withdraw(BOB, "BIG18", 1)` and `repay(ALICE, "BIG18", ...)` both revert with `MathOverflow` inside `global_sync` → `accrue_step` → `scaled_to_original`; the borrow index is still below `MAX_BORROW_INDEX_RAY`, confirming the value ceiling — not the cap — caused the freeze.
