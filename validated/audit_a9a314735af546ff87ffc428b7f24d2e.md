### Title
Cross-repository status webhook forgery triggers unauthorized continuous deployment - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` updates CI status for every `Commit` matching a given sha across the entire database, without scoping to the repository that owns the verified webhook, unlike every other handler in the same directory. Because commit shas are attacker-controlled content of a repository the attacker owns, a `state: success` status webhook from that repository can flip the CI state of an unrelated commit belonging to any other stack that happens to share the same sha, which in turn can trigger an unauthorized deploy via continuous delivery.

### Finding Description
The broken binding: `Repository.from_github_repo_name(payload['repository']['full_name'])` (the repo verified by `verify_signature`/`Shipit.github(organization: repository_owner)`) must equal `commit.stack.repository` for every `Commit` mutated by the handler — it does not.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit` globally by `sha` with no repository/stack filter. Compare to `PushHandler#process`, which scopes via `stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`) before touching any records [2](#0-1) , and `CheckSuiteHandler#process`, which does the same [3](#0-2) . The base `Handler#stacks` helper exists precisely to scope by the verified repository [4](#0-3) , but `StatusHandler` never calls it.

`WebhooksController#verify_signature` only verifies that the payload is authentically signed for `repository_owner`'s GitHub organization/app installation — it does not restrict which `Commit` records the handler is allowed to mutate [5](#0-4) . Signature verification proves "this payload really came from repo A's webhook config," not "this payload may only affect repo A's records." `StatusHandler` conflates these.

Exploit flow:
1. Attacker owns repo A, configured (or auto-configured) as a Shipit repository/stack, with `webhook_secret` correctly set for repo A (this is legitimate — GitHub signs it).
2. Attacker crafts a commit in repo A whose sha collides with (or, more practically, is deliberately chosen to equal) an existing undeployed commit sha C already present in victim stack B — e.g., by rebasing/cherry-picking the exact same tree+parents+author+committer+timestamps combination, which is fully attacker-controlled for their own repo/commits and requires no access to repo B.
3. Attacker POSTs a `status` event (`state: success`) for that sha to `/webhooks`. GitHub signs it validly for repo A.
4. `verify_signature` passes (it's a legitimate signature for repo A).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches commit C in stack B (not just any commit in repo A), and calls `commit.create_status_from_github!(params)` on it — writing a `success` `Status` row against `stack_id: B` [6](#0-5) .
6. `Status#schedule_continuous_delivery` (after_commit) invokes `Commit#schedule_continuous_delivery`, which checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.perform_later(stack)` [7](#0-6) .
7. `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) now returns true for C in stack B, purely from the forged status [8](#0-7) .
8. `ContinuousDeliveryJob#perform` checks `stack.continuous_deployment?` and `stack.occupied?`, then calls `stack.trigger_continuous_delivery` [9](#0-8) .
9. `Stack#trigger_continuous_delivery` calls `next_commit_to_deploy`, which now includes C, and calls `trigger_deploy(commit, Shipit.user, ...)`, creating and enqueuing a real `Deploy` for stack B [10](#0-9) .

No existing guard closes this gap: `verify_signature` is per-organization, not per-commit-record; `drop_unhandled_event` only checks event type; there is no `ExplicitParameters` constraint tying `sha` to `repository`; and `StatusHandler` has no repository/stack scoping at all, unlike its siblings.

### Impact Explanation
An unprivileged attacker who controls only their own repository can cause an unauthorized `Deploy` to be created and run against a completely unrelated tenant's stack (stack B), matching the Critical category "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy." The blast radius spans any stack with `continuous_deployment: true` whose undeployed commit sha the attacker can reproduce in a repository they control, and is repeatable per matching sha/status event.

### Likelihood Explanation
Preconditions: victim stack B has `continuous_deployment: true`, an undeployed commit C, and no blocking statuses; attacker needs a GitHub repo they own (free) and the ability to make a commit whose sha exactly matches C's — feasible since git commit shas are deterministic from tree, parents, author/committer identity and timestamps, all of which the attacker fully controls when constructing their own commit (e.g., by cloning public metadata of C, which is often visible via the target's own public repo/PR, and replaying it into their own repo). No Shipit secrets, sessions, or privileged roles are required — only a standard GitHub status webhook against the attacker's own repo.

### Recommendation
Scope `StatusHandler#process` by the verified webhook repository, matching the pattern used by `PushHandler`/`CheckSuiteHandler`: only update `Status` records for commits belonging to stacks under `stacks` (i.e., `Repository.from_github_repo_name(repository_name)&.stacks`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join through `Stack`/`Repository`, instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not update commits belonging to a different repository's stack" do
  repo_a = shipit_repositories(:shipit) # attacker-controlled repo
  stack_a = repo_a.stacks.first

  repo_b = Shipit::Repository.create!(name: 'victim-repo', owner: 'victim-org')
  stack_b = Shipit::Stack.create!(repository: repo_b, environment: 'production',
                                   branch: 'master', continuous_deployment: true)
  commit_c = stack_b.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:shipit),
                                      committer: shipit_users(:shipit),
                                      committed_at: Time.now, authored_at: Time.now,
                                      message: 'shared sha commit')

  payload = {
    'sha' => commit_c.sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => repo_a.full_name, 'owner' => { 'login' => repo_a.owner } }
  }

  assert_no_difference -> { commit_c.reload.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_no_difference -> { Shipit::Deploy.where(stack: stack_b).count } do
    perform_enqueued_jobs
  end
end
```
This test currently fails against the existing implementation (the status is created on `commit_c` in `stack_b`, and `ContinuousDeliveryJob` is enqueued and, once run, creates a `Deploy` for `stack_b`), demonstrating the cross-tenant mutation and unauthorized deploy trigger via a webhook scoped only to `repo_a`.
