### Title
`StatusHandler#process` writes GitHub status events by bare SHA with no repository/stack scoping, letting a `release/gate` `success` status from one authenticated repository mutate an unrelated stack's commit state - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, which matches every `Commit` row in the entire database sharing that SHA regardless of which `stack`/repository they belong to. Because GitHub Apps are installed and their webhook secret is verified at the **organization** level (`Shipit.github(organization: repository_owner)`), any repository under the same organization installation can produce a validly-signed `status` webhook, and that webhook's `context`/`state` will be applied to `Commit` records of *any* stack in the database that happens to have a matching commit SHA - not just the stack tied to the repository that authenticated the event.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`commit.stack.github_repo_name == payload['repository']['full_name']` for every `commit` mutated by a `status` webhook.

Trace:
1. `Shipit::WebhooksController#create` parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`. [1](#0-0) 
2. `verify_signature` only checks the HMAC against the **organization-level** webhook secret (`Shipit.github(organization: repository_owner)` → `github_app.verify_webhook_signature`); it never checks that the specific `repository.full_name` in the payload matches the stack that will be mutated. [2](#0-1)  GitHub Apps deliver webhooks for every repository in the installation using a single shared secret, so this check is identical for all repos within an org/installation. [3](#0-2) 
3. `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - a bare, unscoped lookup by SHA with **no** filter on stack, repository owner, or repository name. [4](#0-3) 
4. `create_status_from_github!` → `add_status`, and if the new status becomes `success` (i.e. the required `release/gate` context now reports green), `stack.schedule_merges` is invoked, which is the mechanism that advances the merge queue and triggers `merge!`. [5](#0-4) [6](#0-5) 

Root cause: the handler resolves commits purely by SHA across the whole `commits` table, and the SHA itself is not namespaced to a repository - Git commit hashes are content-addressed and do not encode the repository name, so any repository (fork, sibling repo in the same org, etc.) that ends up sharing an identical commit object (e.g. a cherry-picked/forked commit with an unchanged tree/parent/author/committer/message) will have the exact same SHA as the one tracked by a victim stack. The `verify_signature` guard authenticates that "some repository under this org sent this event," not that "this specific repository owns this SHA," so nothing in `drop_unhandled_event`, `verify_signature`, or `StatusHandler`'s `ExplicitParameters` schema enforces the missing invariant.

Exploit flow: an attacker with write access to a repository within the same GitHub App installation/org (their own repo, or a fork under an org member's account) sets a commit status (`context: release/gate`, `state: success`) via the GitHub API on a commit whose SHA is shared with a commit already tracked by a victim stack that has `merge_queue_enabled: true` and requires `release/gate`. GitHub signs and delivers this event with the org-level webhook secret; Shipit's `verify_signature` accepts it because it only checks the org secret, not the specific repository; `StatusHandler#process` then writes the `success` status onto the victim's `Commit` row, and `add_status` triggers `stack.schedule_merges`, forcing the merge queue to advance/merge on the strength of a status the victim repository never authenticated.

### Impact Explanation
A successful exploit lets an attacker cause a required gating status (`release/gate` = `success`) to be recorded against a commit in a stack/repository the attacker does not control, directly driving `Stack#schedule_merges` and the merge queue's `merge!` logic. This is a payload for one repository mutating another repository's stack/commit state, matching the Critical category ("unauthorized deploy, rollback or merge", "a payload for one repository mutating another's stack, commit, task or team"). The blast radius covers every stack whose commits happen to share a SHA with any repository under the same GitHub App installation, which can affect multiple tenants/stacks configured under one organization.

### Likelihood Explanation
Preconditions: (a) the victim stack has `merge_queue_enabled: true` and requires the `release/gate` context, (b) the attacker controls (or has write access to) some repository within the same GitHub App installation/org so that the org-level webhook secret validates their events, and (c) the attacker must produce or obtain a commit SHA identical to one already tracked by the victim stack. Because Git SHAs are content-addressed, (c) is trivially satisfiable for legitimate scenarios like forks/cherry-picks that reproduce an identical commit object (same tree, parent, author, committer, message/timestamp) without needing a cryptographic SHA-1 collision; it is not trivially satisfiable against an arbitrary chosen victim commit content the attacker doesn't already have. This makes the attack highly feasible in shared-org/fork topologies and low-cost once (b) and (c) are met, and it is repeatable against any stack sharing that installation.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other SHA-keyed handlers) to only mutate commits whose `stack.github_repo_name` matches `payload['repository']['full_name']` (or `owner/name` derived from the payload), e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: ..., repository_name: ... })`, and add a request-level assertion that the authenticated `repository_owner`/`repository_name` used in `verify_signature` matches every commit being written before persisting `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar):
```ruby
test "status for a SHA shared with another repository must not mutate an unrelated stack" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, requires 'release/gate'
  victim_commit = victim_stack.commits.create!(sha: "a" * 40)

  # Simulate a different repository's authenticated webhook delivering a status
  # for the SAME sha (as would happen with a shared/forked commit object).
  attacker_repo_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "context" => "release/gate",
    "repository" => { "full_name" => "attacker/unrelated-repo", "owner" => { "login" => "attacker" } }
  }

  before_state = victim_commit.reload.status.state
  assert_not_equal "success", before_state

  Shipit::Webhooks::Handlers::StatusHandler.new.process # with attacker_repo_payload params

  after_state = victim_commit.reload.status.state
  # THE ASSERTION: repository that authenticated (attacker/unrelated-repo)
  # must equal repository owning the mutated commit (victim_stack.github_repo_name).
  # Currently they are NOT equal, yet the write succeeds and schedule_merges fires.
  refute_equal "success", after_state, "status from an unrelated repository must not flip release/gate on victim stack"
end
```
This test currently fails because `StatusHandler#process` has no repository scoping, demonstrating the cross-repository write and the resulting `stack.schedule_merges` trigger. [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
