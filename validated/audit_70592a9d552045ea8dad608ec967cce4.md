## Finding Confirmed

The asymmetry described in the exploit question is real and verifiable in the source.

### Title
Missing `chain_id` domain separation in `SignerCapabilityOfferProofChallengeV2` allows cross-fork replay of signer-capability-offer signatures - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
`offer_signer_capability` verifies a user-supplied signature against `SignerCapabilityOfferProofChallengeV2`, a struct that contains only `sequence_number`, `source_address`, and `recipient_address` — no `chain_id`. Its sibling function `offer_rotation_capability` uses `RotationCapabilityOfferProofChallengeV2`, which explicitly adds `chain_id: chain_id::get()` for the documented purpose of "prevent[ing] replaying the challenge message" across networks.

### Finding Description
`SignerCapabilityOfferProofChallengeV2` is defined without a `chain_id` field: [1](#0-0) 

By contrast, `RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to include `chain_id` with the stated purpose of preventing replay: [2](#0-1) 

`offer_signer_capability` constructs the challenge and verifies the signature purely from `sequence_number`, `source_address`, and `recipient_address`, with no chain binding: [3](#0-2) 

Compare this to `offer_rotation_capability`, which explicitly pulls in `chain_id::get()` into the signed payload before verification: [4](#0-3) 

Because the BCS-serialized `SignerCapabilityOfferProofChallengeV2` message that is Ed25519/MultiEd25519-signed does not encode `chain_id`, a valid signature produced by an account owner authorizing a signer-capability delegation on one chain (e.g., mainnet) is bit-for-bit identical to, and thus valid on, any other chain where the same address, auth key, and sequence number exist (e.g., a devnet/testnet fork sharing genesis state, or a rehearsal/fork network). This breaks the stated invariant in the code comments that all approval-set-changing signatures should be domain-separated to prevent replay, an invariant explicitly implemented for the rotation-capability path but not for the signer-capability path.

### Impact Explanation
An attacker who obtains a `SignerCapabilityOfferProofChallengeV2` signature from a victim (e.g., leaked from a forked/testing environment, a chain split, or any environment where the same account state exists) can replay it via `offer_signer_capability` on a different network sharing the address space, corrupting `Account.signer_capability_offer.for` — the approval set governing who can later call `create_authorized_signer` to impersonate the account. This falls under the "approval validation accepting the wrong signing material or wrong approval set" admission-impact category since the offer mechanism is the approval-set-changing primitive gating delegated signer authority.

### Likelihood Explanation
Exploitation requires the existence of two networks (chains) that share the same account address, authentication key, and sequence-number state — i.e., a fork scenario (testnet/devnet resets from mainnet state, localnet forks, rehearsal networks). This is a narrower precondition than a same-chain replay, but is realistic for Aptos given its practice of periodically forking mainnet state into testnet/devnet or for third-party fork deployments.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2`, mirroring `RotationCapabilityOfferProofChallengeV2`, and populate it with `chain_id::get()` in `offer_signer_capability` before verifying the signature. This will require a new versioned struct (e.g., `SignerCapabilityOfferProofChallengeV3`) plus a migration/compat story if the old struct must remain for backward validation.

### Proof of Concept
1. On chain A (e.g., mainnet), have the victim sign `SignerCapabilityOfferProofChallengeV2 { sequence_number, source_address, recipient_address }` and submit `offer_signer_capability` — capture `signer_capability_sig_bytes`.
2. Fork/replicate the same account state (same `source_address`, `authentication_key`, `sequence_number`) onto chain B (different `chain_id`), e.g., a devnet/testnet reset from the same genesis snapshot.
3. On chain B, submit a transaction calling `offer_signer_capability` with the identical `signer_capability_sig_bytes`, `account_scheme`, `account_public_key_bytes`, and `recipient_address`.
4. Observe that `verify_signed_message` succeeds because the signed payload is chain-agnostic, and `signer_capability_offer.for` is set/overwritten on chain B without the victim having authorized anything on chain B specifically — contrast this with attempting the same replay via `offer_rotation_capability`, which would fail because `RotationCapabilityOfferProofChallengeV2.chain_id` differs.
