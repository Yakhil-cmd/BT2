### Title
`StatusHandler` mutates commits across repositories because it queries `Commit.where(sha:)` without repository scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other webhook `Handler` subclass restricts its mutations to the payload's own repository via `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.repository.full_name)&.stacks`. `StatusHandler#process` instead calls `Commit.where(sha: params.sha)` with no repository filter at all, so a `status` event delivered for repository A can mutate a `Commit` row that actually belongs to a stack tracking repository B, as long as the SHA values match.

### Finding Description
The binding that holds for every other handler is:
`handler mutation target set == Repository.from_github_repo_name(payload.repository.full_name)&.stacks`
as implemented by `Handler#stacks`/`Handler#repository_name` [1](#0-0) , and used e.g. by `CheckSuiteHandler#process`, which scopes to `stacks.where(branch: ...)` before touching any commit [2](#0-1) .

`StatusHandler#process` breaks this binding:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
It never calls `stacks`, never resolves `Repository.from_github_repo_name`, and matches commits purely by `sha` across the entire `commits` table, i.e. across every repository/stack tracked by the Shipit instance.

Exploit path: Git commit objects are content-addressed, so a fork of a public repository shares identical commit SHAs with its upstream for any commit that hasn't been rebased. An attacker who forks a victim repository (or otherwise owns a repository sharing commit history with the victim) and has a legitimately signed webhook on their own fork for the `status` event can send (or trigger via a GitHub Action/API call) a `status` event on a SHA that is also tracked as a `Commit` for the victim's stack. `WebhooksController#verify_signature` only checks that the request was really sent by GitHub for the organization owning the attacker's own repository [4](#0-3) ; it does not verify that `payload.repository.full_name` corresponds to the commit(s) that will end up mutated. `StatusHandler` then finds and updates the victim's `Commit` record with the attacker-supplied `state`/`description`/`target_url`, via `Commit#create_status_from_github!` → `add_status`, which can flip `deployable?`, unblock `blocking_statuses`, and trigger `stack.schedule_merges`/continuous delivery for the victim's stack [5](#0-4) [6](#0-5) .

None of the existing guards prevent this: `verify_signature` authenticates the *sender's own* organization, not the *target* of the mutation; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc., not their relationship to `payload.repository.full_name`.

### Impact Explanation
An attacker who owns/forks any repository can forge a "success" (or any) commit status for a commit belonging to a different, victim-owned stack, provided that commit's SHA is shared (trivial via forking). This can satisfy `required_statuses`/clear `blocking_statuses` on the victim stack, enabling an unauthorized deploy or continuous-delivery trigger for a repository the attacker does not control - matching the Critical category "a payload for one repository mutating another's stack, commit, task ... or an unauthorized deploy". The attack is repeatable against any repository whose commits are reachable (e.g. any public repo that can be forked, or any repo sharing commit ancestry with the attacker's own).

### Likelihood Explanation
Preconditions: attacker needs their own repository with a `status` webhook that Shipit will accept (i.e., a repository under a GitHub org/App installation Shipit already trusts), and a commit SHA shared with the target stack (trivially achieved by forking a public repo). No Shipit session, API token, or secret is required beyond what a normal repository owner already has for their own webhook. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve `stacks` from `payload.repository.full_name` and only update commits belonging to those stacks, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event from repository B cannot mutate a commit belonging to repository A's stack" do
  stack_a = create(:stack) # tracks "owner/repo-a"
  commit  = create(:commit, stack: stack_a, sha: "abc123")

  payload = {
    "repository" => { "full_name" => "attacker/repo-b" }, # unrelated repo
    "sha" => commit.sha,
    "state" => "success"
  }

  assert_no_difference -> { commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  # Currently FAILS: StatusHandler creates a Status on `commit` even though
  # payload.repository.full_name ("attacker/repo-b") != stack_a's repository.
end
```
This demonstrates the equality `Commit.where(sha: params.sha)` (StatusHandler's actual mutation set) diverging from `Repository.from_github_repo_name(payload.repository.full_name)&.stacks` (the expected/required mutation set used by every other handler).
