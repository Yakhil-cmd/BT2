### Title
Webhook organization used for signature verification is not bound to the repository/org the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body, then verifies the raw body against that org's secret. Once verification passes, the event is dispatched to handlers (`PushHandler`, `MembershipHandler`, `PullRequest::*Handler`, `StatusHandler`) which act on a *different* field of the same unverified body (`repository.full_name`, `organization.login` for team membership, or bare `sha` for statuses) to decide which `Stack`/`Team`/`Commit` in the database gets mutated. Nothing enforces that the field used to pick the signing secret and the field used to pick the mutated resource refer to the same repository/org.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) [2](#0-1) [3](#0-2) 

`repository_owner` (used only to pick `Shipit.github(organization: repository_owner)` for the HMAC check) is derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — both read from `request.raw_post` before any authenticity has been established. `verify_webhook_signature` then simply HMACs the whole raw body with that org's `webhook_secret` and compares: [4](#0-3) 

Once the signature is accepted, `create` hands the same raw JSON to `Shipit::Webhooks.for_event(event)` handlers: [1](#0-0) 

But the handlers key their DB lookups off a *different* attribute of the payload:
- `Handler#stacks`/`#repository_name` uses `payload.dig('repository', 'full_name')`, not `owner.login`: [5](#0-4) 
- `PushHandler#process` resolves stacks from that `full_name` and calls `stack.sync_github`: [6](#0-5) 
- `MembershipHandler` stores `team.organization = params.organization.login` and adds/removes members to `Team` records purely from the payload's `organization.login`/`team.id`/`member.login`, independent of the org used for signature verification: [7](#0-6) 
- `PullRequest::*Handler` classes resolve `repository` from `params.repository.full_name` as well: [8](#0-7) 
- `StatusHandler` doesn't even check repository/org at all, matching purely on a global `sha`: [9](#0-8) 

This is exactly the trust-binding break the analog rules describe: "an organization that authenticated versus the repository that is written." A single Shipit deployment can be configured with multiple GitHub Apps/orgs, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`, which configures `OrgOne` and `OrgTwo` with independent secrets). The signature check binds only to whichever org name appears in `repository.owner.login`/`organization.login`; the mutation binds to `repository.full_name` or `organization.login` read from the same untrusted body, with no code path that cross-checks the two are the same repository the App is actually installed for.

### Impact Explanation
An attacker who legitimately controls (or has been given webhook access to) one org/repo configured in this Shipit instance — i.e., who knows a valid `webhook_secret` for OrgA — can craft a payload where the signature-selection field (`repository.owner.login`/`organization.login`) says `"OrgA"` (so the signature check passes using OrgA's known secret) while the handler-consumed field (`repository.full_name`, or for `membership` events a *different* `organization.login`/`team.id`) targets a completely unrelated `Stack`/`Team` belonging to OrgB, which the attacker has no access to. Because the fields aren't required to match, this crosses a repository/organization boundary using credentials scoped to a different org — this is a cross-repository write and, for `MembershipHandler`, a direct escalation into `Team`/`Shipit.github_teams`-based authorization (adding an arbitrary attacker-controlled `User` login to any `Team`, since `find_or_create_by_login!` will create the user if it doesn't exist). This matches the High severity criterion "escalation into `Shipit.github_teams` authorization" and can also drive unauthorized `GithubSyncJob`/deploy-triggering behavior via `PushHandler`.

### Likelihood Explanation
Requires the attacker to already have a valid webhook secret for *some* org/repo hosted on the same Shipit instance (multi-tenant install, as explicitly supported/documented by the fixture `secrets_double_github_app.yml`). Given that, forging the divergent-field payload is trivial (a raw HTTP POST with attacker-chosen JSON and a correctly computed HMAC for their own org). No GitHub write access to the target repo, no Shipit session, and no `api_clients_secret` are needed — only knowledge of one org's `webhook_secret`, which is a materially weaker credential than the ones excluded by scope rules (that scope excludes `webhook_secret` itself as a required precondition only when it is the credential being *stolen*, not when it is legitimately possessed for a different, unrelated org).

### Recommendation
Bind the signature-verification identity to the same identity the handler acts on: after verifying the signature, re-derive `repository_owner`/`organization` from the verified body and assert it matches the App/organization configuration that the resolved `Stack`/`Team`/`Repository` actually belongs to (e.g., compare `repository.full_name`'s owner segment, or the resolved `Repository#owner`, against `repository_owner` used for signature verification) before executing any handler logic. Reject the webhook if they diverge.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with an installed GitHub App and distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately controls a repo under `OrgA` and thus knows `OrgA`'s `webhook_secret`.
3. Attacker sends a `membership` event to `POST /webhooks` with body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://example.com"},
  "organization": {"login": "OrgB"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "OrgA"}}
}
```
and `X-Hub-Signature: sha1=<HMAC-SHA1 of body with OrgA's webhook_secret>`.
4. `WebhooksController#repository_owner` reads `repository.owner.login` = `"OrgA"`, so `verify_signature` checks against OrgA's secret and passes: [2](#0-1) 
5. `MembershipHandler#process` then creates/updates `Team` with `organization = "OrgB"` and adds user `attacker` to it, even though the attacker never authenticated as anything related to `OrgB`: [7](#0-6) 

Note: I could not fully trace `Stack#sync_github`/`ContinuousDeliveryJob` internals in this pass to confirm whether the `PushHandler` path can additionally trigger an unauthorized deploy versus just a metadata sync — this would need further verification in a live/full-context session (`app/models/shipit/stack.rb`, `app/jobs/shipit/continuous_delivery_job.rb`) but the `MembershipHandler` cross-org write is confirmed directly from the cited code.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
