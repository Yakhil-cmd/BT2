### Title
Unbounded in-memory cache of ArbStore address never expires, embedding stale ArbStore payout address into arbiter contract shared-address definitions - (File: arbiters.js)

### Summary
`arbiters.getArbstoreInfo()` fetches the ArbStore's payout `address` and fee `cut` from a remote HTTP endpoint and caches the result forever in the process-lifetime object `arbStoreInfos`, keyed only by `arbiter_address`, with no TTL or invalidation. This cached (and potentially stale) `address` is then compiled directly into the smart-contract definition that `deriveSharedAddress()` builds for every new arbiter contract, determining where the ArbStore's cut of the payment must be sent.

### Finding Description
`getArbstoreInfo` in [1](#0-0)  checks an in-memory map `arbStoreInfos` first and, if present, returns the cached value indefinitely — there is no expiry timestamp, no re-validation, and no way for a running node to pick up a rotated ArbStore address/cut without a full process restart.

This cached info is consumed by `deriveSharedAddress()` in `arbiter_contract.js`, which is invoked whenever a wallet user (an unprivileged counterparty to a private arbiter contract) creates or accepts a contract: [2](#0-1) 

The `arbstoreInfo.address` is embedded directly as the required payout `address` for the ArbStore's cut inside the `"has"` output condition of the generated definition, and `arbstoreInfo.cut` is used to compute the exact split of the contract amount: [3](#0-2) 

Because the cache never expires, once any contract for a given `arbiter_address` has been resolved once on a running node, every subsequent contract for the same arbiter reuses the same address/cut for the lifetime of the process — even if the real ArbStore rotates its payout address (e.g. for a security incident, key rotation, or provider migration) and even if it returns an error on the next call (errors are not cached, but successes are permanently cached, so a compromised/old response is never re-checked once accepted).

### Impact Explanation
If the ArbStore legitimately rotates its payout address (for example after a compromise of its old key), every node that has already cached the old info will keep constructing shared-address definitions that pay the arbitration cut to the stale address. Funds sent as `"has" output` to that address are unrecoverable/misdirected — this is a concrete unauthorized/incorrect-destination spending of contract funds (the cut portion of every future contract with that arbiter), matching the "incorrect deployment parameter → wrong destination address" bug class from the reference report, but reachable here through the normal contract-creation flow available to any unprivileged wallet user or private-payment counterparty, not through a deploy script.

### Likelihood Explanation
Likelihood is moderate: it requires (a) at least one prior successful contract negotiation with a given arbiter on that node process (to populate the cache) and (b) a subsequent address rotation by the ArbStore. Long-running full/hub nodes that mediate many arbiter contracts over time are the most exposed, since the cache is never cleared except by process restart.

### Recommendation
Add a TTL to `arbStoreInfos` entries (re-fetch periodically or on every new contract negotiation), and invalidate/refresh the cache immediately when the ArbStore signals an address rotation (e.g., via a dedicated hub notification or a short cache lifetime such as re-fetching once per contract or once per day). At minimum, do not treat a single successful lookup as valid indefinitely for the life of the process.

### Proof of Concept
1. Node A negotiates an arbiter contract with `arbiter_address = X`; `getArbstoreInfo(X, cb)` is called, fetches `{address: OLD_ADDR, cut: 0.02}` from `http://arbstore-url/api/get_info`, and caches it in `arbStoreInfos[X]` permanently (`arbiters.js` lines 59, 76).
2. The ArbStore operator rotates its payout key/address to `NEW_ADDR` due to a compromise of `OLD_ADDR`, and updates its `/api/get_info` endpoint accordingly.
3. Node A (still running, cache populated) negotiates a second, unrelated arbiter contract with the same `arbiter_address = X`. `deriveSharedAddress()` calls `arbiters.getArbstoreInfo(X, ...)`, which returns the stale cached `OLD_ADDR` (`arbiters.js` line 59) instead of contacting the ArbStore again.
4. The generated shared-address definition requires the contract's cut to be paid to `OLD_ADDR` (`arbiter_contract.js` lines 504-522), a payout address the legitimate ArbStore no longer controls, permanently misdirecting that fund share whenever the contract completes.

			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))

			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
