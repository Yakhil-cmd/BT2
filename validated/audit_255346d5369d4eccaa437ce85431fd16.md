### Title
Asset definer can unilaterally and instantly change the attestor list of a `spender_attested` asset with no delay or opt-out for counterparties - (File: validation.js)

### Summary
Byteball/ocore assets that are `spender_attested` rely on an attestor list to gate who may legally spend or receive the asset. The list is not immutable: the asset definer can post an `asset_attestors` message at any time to add or remove attestors, and this change is enforced against the asset the instant it becomes the latest stable list — with no delay, versioning cutoff, or opt-out mechanism for holders or private-payment counterparties who transacted based on the previous list.

### Finding Description
An asset is created with `spender_attested: true` and an initial `attestors` list in the `asset` message [1](#0-0) . After creation, only the definer can update this list via the `asset_attestors` app, and `validateAttestorListUpdate` performs no check against the previous list, no cooldown, and no requirement that existing holders/counterparties consent to the change: [2](#0-1) 

The check enforced at spend time is simply "is issuer/every author currently on the *latest* attestor list", determined by `storage.readAsset`'s `addAttestorsIfNecessary`, which always picks the most recent stable `asset_attestors` unit for the asset: [3](#0-2) 

That freshly-loaded attestor list is then used to gate every subsequent payment of the asset in `validatePayment`/`loadAssetWithListOfAttestedAuthors`: [4](#0-3) [5](#0-4) 

Unlike `StreamingFeeModule`'s PENDING→INITIALIZED module lifecycle referenced in the external report, there is no analogous "pending" period, timelock, or notice window between the definer publishing an `asset_attestors` change and it taking full effect on the network — the change becomes binding as soon as it stabilizes, which is a matter of network confirmation latency, not a governance delay that gives holders a chance to react (e.g. cash out, finish an in-flight private chain, or refuse the new terms).

### Impact Explanation
Holders and payment counterparties commit to the asset's attestation rules (e.g., KYC/whitelisting) at issuance or when negotiating a trade/private payment. Because the definer can swap the trust set unilaterally and immediately:
- A definer can retroactively revoke an address's ability to spend/receive the asset by dropping its attestor from the list, freezing legitimately-held asset balances for addresses that relied on being attested (`objAsset.arrAttestedAddresses.length === 0` → `"none of the authors is attested"`, `validation.js:2118-2119`).
- A definer can add new attestors to admit parties that should not have been able to transact under the originally agreed compliance model, defeating the purpose that made counterparties trust the asset in the first place.
- Because private payments are built and signed off-chain in a chain of dependent transactions, a mid-chain attestor list change can invalidate a payment a counterparty already received and is relying on, leading to loss/freezing of funds without any recourse for the affected party.

This matches the "Unstable Functionality" class: a privileged actor can retroactively change agreed-upon security parameters with no opportunity for affected users to opt out.

### Likelihood Explanation
Any asset definer of a `spender_attested` asset can trigger this at will by posting a single `asset_attestors` unit; no other permission, cosigning, or delay is required (`objUnit.authors[0].address !== objAsset.definer_address` is the only authorization gate, `validation.js:2841-2842`). This makes the issue trivially and repeatably reachable by a single unprivileged-but-legitimate asset issuer against any of that asset's holders/counterparties.

### Recommendation
Introduce a mandatory delay (measured in MCI or wall-clock time) between an `asset_attestors` update being posted and it taking effect for the purposes of `validatePayment`/`loadAssetWithListOfAttestedAuthors`, so that existing holders and counterparties in flight have a window to react (e.g., finish pending private payment chains or exit positions) before the new attestor list is enforced. Alternatively, allow holders to opt to keep transacting under the attestor list that was in effect when they first acquired/agreed to the asset, similar to how a timelock on module transitions was recommended for `SetToken`.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and `attestors: [X]`.
2. Address `H`, attested by `X`, receives/holds `A`, and enters into a multi-step private payment negotiation with counterparty `C`, relying on continuing to be considered "attested" for the duration of the exchange.
3. Before the exchange completes, `D` posts an `asset_attestors` message removing `X` and/or adding a different attestor `Y` (`validation.js:2829-2848`, `writer.js:244-251`).
4. Once this unit stabilizes, `storage.readAsset` picks it up as the new latest attestor list (`storage.js:1917-1945`), and any subsequent attempt by `H` to spend/transfer `A` fails validation with `"none of the authors is attested"` (`validation.js:2118-2119`), freezing `H`'s in-flight funds/negotiation — all unilaterally triggered by `D` with a single, immediately-effective message.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
