### Title
Webhook signature verification is bound to `repository.owner.login`, not to `repository.full_name`/commit `sha` actually acted upon, allowing cross-repository status/write forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, computed from the JSON payload itself (`params.dig('repository','owner','login')`). Once the signature is accepted, the actual handlers (e.g. `StatusHandler`, `PushHandler`, and all `PullRequest::*Handler`s) never re-check that this same `repository_owner`/organization matches the `repository.full_name` (or bare commit `sha`) they act on. This breaks the intended binding: "organization whose secret authenticated the request" == "repository/commit the handler writes to."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does: [1](#0-0) 
using `repository_owner` derived purely from the untrusted JSON body: [2](#0-1) 

This only proves the sender knows the webhook secret configured for *that* organization (as returned by `Shipit.github(organization: repository_owner)` in `lib/shipit/github_app.rb`). In a multi-tenant Shipit install (`config/secrets.development.example.yml` documents per-organization `github:` blocks each with its own `webhook_secret`), this means: knowing organization A's webhook secret only proves control of a repo/app installation in org A.

However, none of the fields actually consumed downstream to decide *which* record to mutate are cross-checked against `repository_owner`:
- `Handler#repository_name` (base class used by `PushHandler`, all `PullRequest::*Handler`s) reads `payload.dig('repository', 'full_name')` independently: [3](#0-2) 
- `StatusHandler` is worse: it doesn't even use `repository` at all — it looks up commits globally by bare `sha`: [4](#0-3) 

So an attacker who legitimately controls a GitHub App installation/webhook secret for their own organization ("attacker-org", configured in Shipit's multi-org `github:` secrets) can craft a raw JSON body where `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")`'s secret is used and the HMAC is computed correctly by the attacker), while `sha` (for `status` events) or `repository.full_name` (for `push`/`pull_request` events) refers to a **different, victim-owned** repository/commit that is tracked by a Shipit stack the attacker has no access to.

### Impact Explanation
Via a forged `status` event, the attacker can create arbitrary `Commit#create_status_from_github!` records (state `success`/`failure`, `context`, `description`, `target_url`) for any commit `sha` tracked anywhere in the Shipit install, regardless of which organization/repository actually owns that commit. This is a cross-repository write: CI/status gating used by Shipit to decide deploy readiness/merge-queue eligibility for a victim stack can be forged by an unrelated, unprivileged (with respect to the victim repo) GitHub App owner, potentially unlocking or blocking deploys for repositories the attacker does not control. This satisfies the "cross-repository writes" / "unauthorized deploy" impact bucket, since it breaks the equality `organization that authenticated == repository/commit actually written`.

### Likelihood Explanation
Exploitation requires only that the attacker operate their own legitimate, independently-configured GitHub App/organization entry in Shipit's multi-org `github:` webhook_secret configuration (a normal, unprivileged deployment scenario for shared/multi-tenant Shipit instances), and be able to send an arbitrary HTTP POST to the public `/webhooks` endpoint — no session, `ApiClient` token, or repository write access to the victim repository is needed. Likelihood is high in any multi-organization Shipit deployment.

### Recommendation
After computing `repository_owner` and validating the signature, re-validate that every organization-scoped field consumed by handlers (`repository.owner.login`, `repository.full_name`'s owner segment, and any `sha`-only lookups in `StatusHandler`) is consistent with the organization whose secret validated the signature — e.g., have `Handler` reject payloads whose `repository.full_name` owner doesn't match the verified `repository_owner`, and have `StatusHandler` scope its `Commit.where(sha:)` lookup by the stack's repository/organization rather than searching globally by `sha` alone.

### Proof of Concept
1. Configure Shipit with two organizations in `github:` secrets, each with its own `webhook_secret` (as documented in `config/secrets.development.example.yml`).
2. As the legitimate administrator of `attacker-org`'s GitHub App, compute a valid `X-Hub-Signature` HMAC (using `attacker-org`'s known `webhook_secret`) over a hand-crafted JSON body for a `status` event where `repository.owner.login = "attacker-org"` but `sha` is the SHA of a commit that belongs to a stack tracked under a victim organization's repository.
3. POST this body with header `X-Github-Event: status` and the computed `X-Hub-Signature` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves and validates against `attacker-org`'s secret and succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30`), then `StatusHandler#process` creates a status on the victim's commit purely by `sha` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), with no check that the commit belongs to a repository owned by `attacker-org`.
