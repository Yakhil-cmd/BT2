### Title
`ReviewStack#env` label merge silently overwrites the real `GIT_ASKPASS` path with attacker-controlled value - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::Commands#base_env` sets `GIT_ASKPASS` to the trusted `lib/snippets/git-askpass` script path when `Shipit.use_git_askpass?` is true, which the script uses to feed `GITHUB_TOKEN` to git over HTTPS. `TaskCommands#env` merges `@stack.env` (which for a `ReviewStack` injects one `"true"` entry per PR label, uppercased) after `super()`, so any GitHub user who can label their own PR `GIT_ASKPASS` overwrites that path with the literal string `"true"` before the env reaches `Command`/`PTY.spawn`.

### Finding Description
The broken binding: `TaskCommands#env['GIT_ASKPASS']` should equal `Shipit::Engine.root.join('lib','snippets','git-askpass').realpath.to_s` (set in `Shipit::Commands#base_env`, [1](#0-0) ) whenever `Shipit.use_git_askpass?` is true, but it does not hold once a label collides with that key.

Path:
1. `TaskCommands#env` calls `super` (→ `base_env`, sets `GIT_ASKPASS` to the real script path) and then `.merge(@stack.env)`: [2](#0-1) 
2. `ReviewStack#env` merges the PR's `labels`, uppercased, each mapped to the string `"true"`, on top of `super`: [3](#0-2) 
3. `PullRequest#labels` is populated directly from GitHub's payload (`github_pull_request.labels.map(&:name)`) with no filtering/denylist: [4](#0-3) 
4. Any repository owner/PR author can add a label named `GIT_ASKPASS` (or `git_askpass`, since it's uppercased) to their own PR — this requires only GitHub-side label permission on their own repo, not any Shipit privilege. That label is ingested via `labeled`/`opened`/`reopened` webhook handlers under `app/models/shipit/webhooks/handlers/pull_request/`, all of which write straight into `PullRequest#labels` via `github_pull_request=`.
5. Since `.merge(@stack.env)` happens strictly after `super` in `TaskCommands#env`, the label-derived `"true"` value silently wins, overwriting the trusted askpass script path with a value the attacker fully controls (any label name, not just `GIT_ASKPASS`).

None of the existing guards catch this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the payload came from GitHub for that repo — they do not restrict label content. `drop_unhandled_event`, `ExplicitParameters`, `force_github_authentication`, `User#authorized?`, `require_permission!` are unrelated to label content or stack env construction. No model validation exists on `PullRequest#labels` or on the `Stack#env`/`ReviewStack#env` merge to protect reserved env keys like `GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`. `EnvironmentVariables#permit` (used for stack-configured custom env vars) is a separate mechanism from the PR-label-derived env and does not filter this path.

### Impact Explanation
When `Shipit.use_git_askpass?` is enabled, the deploy host runs git commands for the review-stack deploy (`checkout`, `clone`, etc., via `Command`/`PTY.spawn`) with `GIT_ASKPASS` no longer pointing at the trusted helper script that supplies `GITHUB_TOKEN`. This defeats the token-injection mechanism for HTTPS git auth on that stack's deploy, breaking the confidentiality/integrity guarantee that `GITHUB_TOKEN` is only exposed via the controlled askpass script. Any PR author on their own repository can trigger it against their own review stack's deploy environment, repeatably, for every deploy of that stack. It does not cross tenant boundaries into other repositories' stacks (each `ReviewStack` and its `PullRequest` belong to a single repo), so blast radius is scoped to the attacker's own stack — the attacker is degrading/hijacking the git auth mechanism for a deploy they already control via their own PR. This corresponds to the "authentication bypass" / "deploy-time secret handling defeated" category but the scope is confined to the attacker's own resource, limiting severity below a cross-tenant Critical.

### Likelihood Explanation
Preconditions: `Shipit.use_git_askpass?` must be true (an install-wide config flag), and the repo must use `ReviewStack` (PR-based deploys) with a `PullRequest` record. Attacker cost is trivial: label their own PR `GIT_ASKPASS` via the GitHub UI/API, which they already control. No Shipit secrets or elevated roles needed. Feasible and repeatable on every deploy of that stack.

### Recommendation
In `ReviewStack#env`, exclude/reserve environment keys that are security-sensitive (e.g. `GIT_ASKPASS`, `GITHUB_TOKEN`, `GITHUB_DOMAIN`) from the label-derived hash, or merge label-derived env before `super`/`base_env` rather than after, so trusted values set in `Commands#base_env` cannot be overridden by attacker-supplied PR labels. Alternatively, apply an explicit denylist/allowlist filter on label names before merging them into `env`.

### Proof of Concept
```ruby
test "PR label named GIT_ASKPASS overrides the real askpass script path" do
  Shipit.stubs(:use_git_askpass?).returns(true)

  stack = shipit_stacks(:shipit) # or a factory-built ReviewStack
  pull_request = stack.create_pull_request!(...)
  pull_request.update!(labels: ['GIT_ASKPASS'])

  task = stack.tasks.build
  commands = Shipit::TaskCommands.new(task)

  real_path = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s

  assert_equal 'true', commands.env['GIT_ASKPASS']
  refute_equal real_path, commands.env['GIT_ASKPASS']
end
```
