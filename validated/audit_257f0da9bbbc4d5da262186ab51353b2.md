### Title
Webhook signature bypass when `webhook_secret` is unset allows forged `membership` events to escalate into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The reported bug class is a state/threshold-verification gap: a critical decision (liquidation) is gated on a check that can be bypassed or become stale, letting balances the contract "believes" are safe diverge from reality. The closest reachable analog in this engine is a verification binding that can be trivially satisfied by an attacker: `WebhooksController#verify_signature` delegates trust to `GitHubApp#verify_webhook_signature`, which unconditionally returns `true` when no `webhook_secret` is configured for the organization resolved from the (unauthenticated) payload. Because `docs/setup.md` explicitly documents the webhook secret as **optional**, an installation following the documented setup can be fully unauthenticated for webhook delivery, letting any remote attacker forge a GitHub `membership` webhook that grants themselves membership in a `Shipit::Team`, escalating into `Shipit.github_teams` authorization.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/organization from unverified payload fields and then asks that app to verify the signature: [1](#0-0) 

The verification itself is: [2](#0-1) 
`return true unless webhook_secret` means that if no secret is configured for the resolved organization, **any** payload is accepted, with **no signature check at all**, regardless of the value or absence of `X-Hub-Signature`.

The setup documentation explicitly marks the webhook secret as optional: [3](#0-2) 
and the multi-org secrets example likewise leaves `webhook_secret:` blank: [4](#0-3) 

Once past this gate, the `membership` event handler trusts the payload's `organization`, `team`, and `member` fields to create/lookup a `Team` and add a `member` to it: [5](#0-4) 

Team membership is exactly what `authorized?` checks to gate access to the app: [6](#0-5) 
and `force_github_authentication` uses `Shipit.github_teams` / `authorized?` as the sole authorization gate for logged-in users: [7](#0-6) 

So the binding that should hold is: *"authenticated webhook signature" == "authorization to mutate `Shipit::Team`/`Membership` records that drive `Shipit.github_teams` authorization"*. When `webhook_secret` is blank (a documented, supported configuration), that binding collapses: an attacker with no credentials can forge a `membership` "added" event naming themselves (an already-known GitHub login, e.g. their own) as a member of one of the organization's authorized teams. `User.find_or_create_by_login!` will fetch/create the corresponding `Shipit::User` via the app's own GitHub API token, and `Team#add_member` will then link that user to the team, all without the attacker ever needing a Shipit session, an `ApiClient` token, or GitHub OAuth completion for that account.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" bar explicitly called out as High severity. Any GitHub identity (attacker-controlled login) can gain membership in a Shipit-authorized team purely through forged webhook traffic, subsequently authorizing that identity to log in and access all deploy/rollback/merge functionality gated by `force_github_authentication`. This does not require any privileged token, GitHub App private key, or repository write access — the attacker only needs the (documented) absence of a webhook secret and network reachability to `/webhooks`.

### Likelihood Explanation
Likelihood is contingent on operator configuration: this is exploitable when `webhook_secret` is left blank, a state the documentation and sample secrets files present as a normal, supported option rather than a documented misconfiguration. Given the docs literally label it "(optional)" with no security warning about its criticality for authorization, operators following the guide as written may end up in this state. The webhooks endpoint (`/webhooks` per `config/routes.rb` mounting) is unauthenticated by design (it must accept GitHub's calls), so once `webhook_secret` is absent there is no additional barrier.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than optional-fallback-to-`true`; reject/422 any webhook when no secret is configured instead of treating it as automatically verified.
- Update `docs/setup.md` to state that omitting the webhook secret disables signature verification and is unsafe, or remove the "(optional)" framing entirely.
- Consider requiring `X-Hub-Signature-256` (sha256) verification exclusively, and reject events like `membership` from being processed unless the request could be cryptographically tied to the GitHub App installation.

### Proof of Concept
1. Deploy Shipit per `docs/setup.md` without setting `github.webhook_secret` (a documented supported option).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/1" },
  "organization": { "login": "<victim-org>" },
  "member": { "login": "<attacker-github-login>" }
}
```
No `X-Hub-Signature` header is required to be valid; per `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`), verification short-circuits to `true` because `webhook_secret` is blank.
3. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) creates/finds `team` with `github_id: 1` and adds `attacker-github-login` (fetched via `User.find_or_create_by_login!`) as a member.
4. If team `id: 1` (or any team the attacker can guess/target) is included in `Shipit.github_teams`, the attacker's GitHub account is now authorized per `User#authorized?` (`app/models/shipit/user.rb:80-82`), and logging in via GitHub OAuth grants full application access enforced by `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      end
```
