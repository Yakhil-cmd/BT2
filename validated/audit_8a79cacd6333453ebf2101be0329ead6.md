### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the independent `repository.full_name` field, allowing cross-organization/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit's webhook signature verification selects which GitHub App (and thus which HMAC secret) to check the payload against using the payload's own `repository.owner.login` (or `organization.login`) field, while every webhook handler determines which `Stack`/`Repository` to mutate using a different, unrelated payload field: `repository.full_name`. Because the field used to select the *verifying* secret is never checked against the field used to select the *acted-upon* repository, a webhook that is validly signed for one configured GitHub organization can be crafted to target and mutate the state of a Stack belonging to a completely different organization/repository in the same Shipit installation.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to pick the verifying `github_app` purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config (each org can have its own `webhook_secret`, as shown in the multi-org secrets template): [3](#0-2) 

Signature verification (`GithubApp#verify_webhook_signature`) HMACs the *entire raw body* against that one org's secret: [4](#0-3) 

Note also that `webhook_secret` is documented as optional; when unset, `verify_webhook_signature` returns `true` unconditionally, so any organization without a configured secret bypasses verification entirely.

However, once the request passes `verify_signature`, every webhook handler that decides *what to mutate* uses a completely different field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

The binding the engine implicitly relies on is:
`organization_verified (repository.owner.login used to select the secret) == organization_written (owner embedded in repository.full_name used to select the Repository/Stack)`

Nothing in `verify_signature` or in the handlers enforces this equality. An attacker who is a legitimate (unprivileged, non-KYC'd/non-team) administrator of *any* GitHub organization that is configured in Shipit (or of an org with no `webhook_secret` set) can compute (or trivially bypass, if unset) a valid `X-Hub-Signature` for that org, while setting the JSON body's `repository.full_name` (and other repository/stack-identifying fields) to point at a Repository/Stack belonging to an entirely different, unrelated organization that they have no access to. Because the raw body is only checked for byte-integrity against one secret — never cross-checked for internal consistency between `repository.owner.login` and `repository.full_name` — the forged payload is accepted and dispatched to handlers (`push` → `GithubSyncJob`, `status`, `check_suite` → `RefreshCheckRunsJob`, `pull_request` → review-stack provisioning, `membership` → team/user mutation), all scoped to the victim repository: [7](#0-6) 

### Impact Explanation
This breaks the organization-authenticated vs. repository-written trust boundary, letting an attacker who only controls one configured (or unsecured) organization inject synchronization events, fake CI/check-run/status updates, or membership changes against a Stack that they do not own or have permission over. Faked `status`/`check_suite` events can flip commit statuses used as deploy gates, and faked `push` events force `GithubSyncJob` to resync arbitrary target repositories — this can enable an unauthorized deploy/rollback path once combined with the merge-queue/CI-gating logic, satisfying the "unauthorized deploy" High-impact criterion.

### Likelihood Explanation
Requires only that Shipit is configured to serve more than one GitHub organization (a documented, supported configuration) and that the attacker has legitimate access to one such organization's webhook signing (or that org's `webhook_secret` is left unset, which is explicitly documented as optional). No Shipit session, `ApiClient` token, or GitHub App private key is needed — only the ability to produce a validly-HMAC'd body for one org, which is directly reachable from an unprivileged external POST to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature`, after establishing the verifying organization, cross-check that `params.dig('repository','owner','login')` matches the owner embedded in `params.dig('repository','full_name')`, and additionally have every `Handler` subclass validate that the resolved `Repository`'s owner equals the organization whose secret verified the request signature, rejecting (422) any mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `attacker-org` (attacker is an org owner, secret known/controllable, or secret unset) and `victim-org` (tracked Stack `victim-org/app`) — mirroring `config/secrets.development.shopify.yml`.
2. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/app" },
  "after": "<attacker-chosen sha>"
}
```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` (or, if unset, sends any signature).
4. POST to `/webhooks` with `X-Github-Event: push` and the crafted `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, verifies successfully against `attacker-org`'s secret (or bypasses check entirely if unset), per [1](#0-0) .
6. The push handler resolves the target repository via `payload.dig('repository','full_name')` → `victim-org/app`, per [5](#0-4) , and enqueues `GithubSyncJob` for the victim's Stack — despite the request never being signed by `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
