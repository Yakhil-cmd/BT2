## Finding: Analog Confirmed

### Title
Receipt size limit is bypassed when `output_data_receivers` is added after size validation, allowing oversized receipts into the chain - (File: `runtime/runtime/src/verifier.rs`)

### Summary
The external report describes an unbounded/unchecked external-call return-data size in Solidity leading to gas exhaustion and receipts that never get properly finalized/bounded. The direct analog in nearcore is a data-validation gap in receipt size enforcement: `validate_receipt` checks `max_receipt_size` on a newly created receipt, but the `output_data_receivers` field is populated *after* that check for receipts involved in `promise_return`/`value_return` chains, allowing the final on-chain receipt to exceed `max_receipt_size`.

### Finding Description
`validate_receipt` in `ValidateReceiptMode::NewReceipt` computes `borsh::object_length(receipt)` and rejects it if it exceeds `limit_config.max_receipt_size`: [1](#0-0) 

This check happens when a new receipt is created during action processing: [2](#0-1) 

However, `output_data_receivers` — the field analogous to registering the callback recipient for a promise's return value — is attached to a receipt after this validation point when a promise is later resolved via `promise_return` or a large value is set via `value_return`. This lets a receipt that passed size validation at `max_receipt_size` grow beyond the limit once `output_data_receivers` is appended, exactly mirroring the Solidity bug where the check for validity/success happens before the full cost/size implication (huge return data) is realized. The bug is explicitly acknowledged in the codebase itself: [3](#0-2) 

The maintainers even added a dedicated `ValidateReceiptMode::ExistingReceipt` mode specifically to gracefully tolerate these malformed size-exceeding receipts already in state, referencing tracked issue https://github.com/near/nearcore/issues/12606.

Reachable, concrete PoC-style tests exist that reproduce this from ordinary contract calls: [4](#0-3) [5](#0-4) 

Both `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` deploy an ordinary contract, submit an ordinary transaction, and assert (`assert_oversized_receipt_occurred`) that a receipt exceeding `max_receipt_size` is actually produced and propagated on-chain: [6](#0-5) 

### Impact Explanation
This is a **data-validation/resource-accounting gap reachable by any unprivileged account** via a standard `FunctionCall` action (calling `promise_then`/`promise_return`/`value_return`) — no validator or network-layer privilege required. It allows receipts to exceed the protocol-mandated `max_receipt_size` (4 MiB), i.e., unbounded/underpriced resource use relative to what the config intends to bound: larger-than-permitted receipts consume more state-witness/storage-proof and network bandwidth than accounted for by congestion control and bandwidth scheduler limits, which are calibrated assuming `max_receipt_size` is a hard ceiling. This is analogous to the Solidity finding's core concern: return-data (`output_data`) size is not fully bounded at the point where a receipt is judged "valid," enabling downstream resource blow-up.

### Likelihood Explanation
High likelihood of triggering: the bug is deterministically reproducible with a simple contract using `promise_then`/`promise_return` or `value_return` sized close to `max_receipt_size`, as demonstrated by the existing regression tests. No malicious node, validator collusion, or network manipulation is needed — only a standard signed transaction from any account with a deployed contract.

### Recommendation
Move (or duplicate) the `max_receipt_size` validation to occur *after* `output_data_receivers` is finalized for the receipt (i.e., validate the fully-assembled receipt, not an intermediate one), consistent with the short-term Solidity recommendation of fixing/bounding the checked quantity before it can grow further. Until fixed, ensure downstream consumers (congestion control, bandwidth scheduler, state-witness size accounting) can safely handle receipts that exceed `max_receipt_size`, and prioritize closing tracked issue near/nearcore#12606 rather than only tolerating it via `ValidateReceiptMode::ExistingReceipt`.

### Proof of Concept [7](#0-6) 

This test deploys the standard test contract, calls `max_receipt_size_value_return_method` with `value_size` equal to `max_receipt_size`, and confirms via `assert_oversized_receipt_occurred` that a resulting on-chain receipt exceeds `max_receipt_size`, exactly as the analogous Solidity report predicted unbounded/unchecked return data would break size assumptions downstream.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
