### Title
Integer-range overflow in asset denomination validation causes cross-backend storage truncation and node consensus divergence - ([File: validation.js])

### Summary
`CVE-2021-21837` is a class of "unchecked arithmetic on an attacker-controlled numeric field causes the value to exceed the range the field is later used/stored in, corrupting downstream state." The GPAC bug allowed unchecked integer arithmetic during MPEG-4 box parsing to overflow a buffer size computed from attacker input. In `ocore`, the closest reachable analog is in the asset-definition path: an unprivileged asset issuer can post a `unit` containing an `asset` message with `fixed_denominations: true` whose `denominations[].denomination` field is validated against `constants.MAX_CAP` (9e15) in `validation.js`, but that same value is persisted into a SQL column typed as 32-bit `INT` (`asset_denominations.denomination`) in the MySQL/MyRocks schemas used by hubs. This mismatch between the JS-level bound and the SQL storage width is a genuine, unchecked "integer overflow" of the intended value range, root-caused exactly the way the GPAC bug is (a size/limit check exists, but it does not match the true representable range of the value as it flows into a fixed-width store).

### Finding Description
`validateAssetDefinition()` bounds an asset's per-denomination `denomination` value only against `constants.MAX_CAP` (9e15): [1](#0-0) 

`constants.MAX_CAP` is `9e15`: [2](#0-1) 

That value, taken directly from the attacker-supplied unit payload, is written unmodified into `asset_denominations.denomination`: [3](#0-2) 

But in the MySQL/MyRocks schemas (used by hubs and some full nodes), the target column is a 32‑bit signed `INT`, whose maximum value (2147483647, ≈2.1e9) is roughly 4.2 million times smaller than the validated maximum (9e15): [4](#0-3) [5](#0-4) 

The SQLite schema used by other full/light nodes declares the same column name/type (`INT`), but SQLite's dynamic type system does not enforce a 32-bit width — it stores the exact 64-bit value: [6](#0-5) 

Because ocore is explicitly designed to run on either SQLite or MySQL/MyRocks backends interchangeably (hubs typically run MySQL, many full/light nodes run SQLite), a single unit's `denomination` field, once it exceeds `2^31-1`, is stored differently depending on the backend: SQLite preserves the exact value used for consensus/hash computation, while MySQL (unless the connection enforces `STRICT_TRANS_TABLES`) silently truncates/clamps the out-of-range integer on `INSERT`. No explicit `sql_mode`/strict-mode configuration was found being set by the driver connection code, so the default server configuration governs this behavior, which is not something ocore controls or codifies.

Downstream, `denomination` is used as a foreign-key-like lookup value in the exact-match conditions that decide unit validity, e.g. in `validateIndivisibleIssue()`: [7](#0-6) 

and in `pickIndivisibleCoinsForAmount`/issuance selection which matches stored `denomination` rows: [8](#0-7) 

If a node's stored `denomination` value differs from the value embedded in and hashed into the unit (because that node's DB backend silently truncated it on write while another node's backend did not), that node will fail to find a matching `asset_denominations` row (`"invalid denomination"`) or will otherwise disagree on the coin's identity/validity, while a node on the other backend accepts the same unit as valid.

### Impact Explanation
This produces exactly the kind of consensus-critical fault the validate criteria call for: nodes running different, officially supported DB backends (SQLite vs. MySQL/MyRocks) can permanently disagree on whether a given unit/asset-issuance is valid, because the persisted `denomination` differs from the value that was hashed and validated. That is a "node disagreement on validity" and, in a hub-vs-full-node split, could stall confirmation of the affected asset's units on part of the network (network unable to confirm new units for that asset) or allow an issuer to construct issuance sequences that validate on one backend but not another, undermining the divisible/fixed-denomination asset issuance invariant that all denominations must sum exactly to the declared `cap`.

### Likelihood Explanation
The trigger is a single, unprivileged, permissionless action: any user can post a unit defining a new asset (`app: "asset"`) with `fixed_denominations: true` and a `denominations` array containing a `denomination` value between `2^31` and `9e15` — this passes all current JS-side checks (`isPositiveInteger`, `<= MAX_CAP`, sorted, etc.) in `validation.js` lines 2769-2778. No special privilege, hub cooperation, or race condition is required; only mixed-backend deployment (which is the norm — hubs commonly use MySQL/MyRocks, other nodes use SQLite) is needed for the divergence to manifest.

### Recommendation
Bound `denomInfo.denomination` (and any other fields sharing the `asset_denominations`/`outputs`/`inputs`.`denomination` INT columns) to the actual minimum representable range across all supported storage backends — i.e., `2^31 - 1` (or widen the MySQL/MyRocks column to `BIGINT`, matching `count_coins`, `cap`, and `amount`, which are already `BIGINT`). Add an explicit check in `validateAssetDefinition()` such as `denomInfo.denomination > 2147483647 → return callback("denomination too large")`, and audit all other numeric consensus fields for the same class of column-width vs. validation-bound mismatch (e.g., `payload.denomination`, `input.serial_number`, `main_chain_index` fields) to ensure identical behavior across SQLite, MySQL, and MyRocks.

### Proof of Concept
1. As any user, compose and broadcast a unit containing an `asset` message:
```json
{
  "app": "asset",
  "payload": {
    "cap": 4611686022722355200,
    "is_private": false,
    "is_transferrable": true,
    "auto_destroy": false,
    "fixed_denominations": true,
    "issued_by_definer_only": true,
    "cosigned_by_definer": false,
    "spender_attested": false,
    "denominations": [
      { "denomination": 4294967296, "count_coins": 1073741824 }
    ]
  }
}
```
   `denomination = 4294967296` (2^32) passes `isPositiveInteger` and `<= constants.MAX_CAP` (9e15) in `validation.js` (lines 2769-2778), and `cap === total_cap_from_denominations` holds.
2. Broadcast the unit. A full node running SQLite persists `asset_denominations.denomination = 4294967296` exactly (per `writer.js` lines 236-242).
3. A hub or full node running MySQL/MyRocks (schema `INT NOT NULL`, `initial-db/byteball-mysql.sql` lines 254-261) either truncates/clamps the value on insert (non-strict `sql_mode`) or raises an insert error (strict `sql_mode`), producing a stored value/state that differs from the SQLite node's.
4. A subsequent issuance unit referencing `denomination: 4294967296` in its input (as validated in `validation.js` lines 2207-2231) will be accepted by the SQLite-backed node (matching row found) but rejected as `"invalid denomination"` by the MySQL-backed node (no matching row, or a mismatched truncated value) — a concrete, reproducible node disagreement on unit validity stemming directly from unchecked-range arithmetic on attacker-controlled input, mirroring the CVE-2021-21837 root cause.
