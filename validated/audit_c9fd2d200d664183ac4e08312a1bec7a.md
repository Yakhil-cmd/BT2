### Title
Forged `membership` webhook signed by an attacker-owned organization can mutate team membership of an unrelated, privileged `Shipit::Team` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves the target `Team` solely by the numeric `team.id` field of the webhook payload and resolves the target `User` solely by `member.login`, with no check that the signing organization actually owns that team. Because `WebhooksController#verify_signature` validates the HMAC against the webhook secret of whatever organization is named in the *payload* (`params.dig('organization','login')`), an attacker who administers their own GitHub org registered in Shipit can sign a `membership` webhook with their own legitimate `webhook_secret`, but set `team.id` to the GitHub-global id of an unrelated, already-provisioned privileged team and `member.login` to an existing operator's login, causing Shipit to add or remove that operator from the privileged team.

### Finding Description
The broken binding is: `team mutated by the handler == team actually managed by the organization that signed the webhook`. This should hold but doesn't.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) . For a `membership` event there is no `repository` object, so `organization.login` — a value the attacker fully controls in the JSON body — determines *which* org's `webhook_secret` is used to check the signature. If the attacker names their own administered org, the check passes using a secret the attacker legitimately possesses.
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`, keyed only on the attacker-supplied integer `team.id`, and only sets `organization`/`github_team` attributes on *creation* (the `do |team| ... end` block only runs when a new record is built) [3](#0-2) . If a `Team` row with that `github_id` already exists (e.g. a genuine privileged team provisioned earlier from real GitHub webhooks/`teams.rake`), the lookup returns that existing row untouched — the attacker never has to match its real `organization`.
- `User.find_or_create_by_login!(params.member.login)` resolves purely by `login` string, with no proof the named user is actually a member of the signing org [4](#0-3) .
- `process` then does `team.add_member(member)` or `team.members.delete(member)` based on `params.action`, with no cross-check between `team.organization` and the verified signing organization [5](#0-4) .

GitHub team ids are globally unique (not scoped per organization), so an attacker can learn or guess the numeric id of a real privileged team (e.g. by observing a public team URL, or via Shipit's own team API/rake output) and forge a payload where `organization.login` = attacker's own org, `team.id` = victim's real privileged team id, and `member.login` = a real operator's login. `verify_signature` only proves the payload was signed by *some* org's secret matching the org named in the payload — it does not prove that org owns the referenced team, and `Team.find_or_create_by!` never re-validates ownership against the verified organization. This is the exact gap the question describes: the guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) all pass, yet the binding "team member added == member GitHub actually reports for that team's real organization" is broken.

### Impact Explanation
This directly escalates into `Shipit.github_teams` authorization: `User#authorized?` grants privileged access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) . An attacker can (a) add an attacker-controlled login (their own GitHub account) to a `Team` row whose `github_id` matches a team configured in `Shipit.github_teams`, granting themselves operator-level authorization in Shipit without ever being a real member of that trusted team/org, or (b) issue `action=removed` to strip a legitimate operator from that team, revoking their access. Both are repeatable against any `Team` row already present in Shipit's database, regardless of which organization the attacker actually administers. This matches the "High — escalation into `Shipit.github_teams` authorization" category, and combined with the ability to self-grant membership it borders on Critical since it can lead to unauthorized deploys once authorization checks pass.

### Likelihood Explanation
Preconditions: the attacker must administer at least one GitHub organization that is configured in Shipit (has a registered `webhook_secret`) — the prompt states this is given. They must also know or discover the numeric GitHub `team.id` of the target privileged team, which is often discoverable from public team API responses, team URLs, or prior legitimate webhook traffic, and is not treated as a secret by GitHub. No Shipit session, API token, or the victim org's `webhook_secret` is required. The attack is a single crafted POST to `/webhooks` with a valid `X-Hub-Signature` computed from a secret the attacker legitimately owns, making it cheap, deterministic, and repeatable at will.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `organization` already stored on any existing `Team` record found by `github_id`, and reject/raise if they diverge instead of silently reusing the row. More generally, `WebhooksController#verify_signature` should ensure the verified signing organization is authorized to describe the specific team/repository referenced in the payload before any handler runs, and `MembershipHandler` should refuse to mutate a `Team` whose stored `organization` differs from the verified signing organization.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or a new handler test) with no live GitHub:

1. Seed a `Shipit::Team` with `github_id: 999`, `organization: "victim-org"`, and an existing `Shipit::User` operator (`login: "real-operator"`) as a member via `Membership.create!`.
2. Configure Shipit with two orgs in test config: `"victim-org"` and `"attacker-org"`, each with its own `webhook_secret` (`victim_secret`, `attacker_secret`).
3. Build a membership webhook JSON body: `{"action":"removed","team":{"id":999,"name":"Ops","slug":"ops","url":"..."},"organization":{"login":"attacker-org"},"member":{"login":"real-operator"}}`.
4. Compute `X-Hub-Signature` using `attacker_secret` (the attacker's own, legitimately-known secret) via `OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)`.
5. POST to `/webhooks` with header `X-Github-Event: membership` and the computed signature.
6. Assert response is `200`/`:ok` (signature verification succeeded using the attacker's own secret).
7. Assert `Shipit::Membership.exists?(team_id: team.id, user_id: operator.id)` is now `false` — proving the operator was removed from `victim-org`'s privileged team using only `attacker-org`'s webhook secret, i.e. `team.organization` (`"victim-org"`) never equaled the verified signing organization (`"attacker-org"`), yet the mutation was applied.
