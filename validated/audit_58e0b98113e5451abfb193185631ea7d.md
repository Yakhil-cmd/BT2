### Title
Stable Outputs Become Permanently "Spent" (Frozen) When Their Only Spending Unit Turns final-bad - ([File: writer.js])

### Summary
When `writer.js` writes a unit, it unconditionally flags the source output referenced by each `transfer` input as `is_spent=1`, regardless of whether the spending unit ultimately becomes `good` or `final-bad`. The stabilization logic in `main_chain.js` that later downgrades a losing/invalid unit to `sequence='final-bad'` resets the `inputs.is_unique` flag so the input is no longer treated as a competitor, but it never resets `outputs.is_spent` back to `0` on the output that unit tried to spend. If that final-bad unit was the only unit ever to reference the output, the output is left marked as spent forever even though no `good` unit actually claims it, freezing it from the owner's perspective.

### Finding Description
Every inline payment input, at write time, triggers an unconditional output-spend update: [1](#0-0) 
This runs for every unit regardless of its eventual `sequence` (`good`, `temp-bad`, or `final-bad`) — the only conditional logic (`is_unique`) governs the `inputs` row, not the `outputs.is_spent` flag: [2](#0-1) 

Later, during stabilization, `markMcIndexStable()` resolves conflicts among non-serial units on the same MCI and decides the final `sequence` of each. When a unit is confirmed as `final-bad`, its `inputs.is_unique` is cleared so it is treated as a "non-existent competitor" going forward, but no query un-marks the outputs it referenced: [3](#0-2) 
The same pattern repeats in `propagateFinalBad()`, which cascades `final-bad` status to downstream spenders but likewise only clears `inputs.is_unique`, never `outputs.is_spent`: [4](#0-3) 

The maintainers' own diagnostic tool documents this exact defect as a discrepancy between two balance-calculation methods: [5](#0-4) 
The tool's "NEW" (correct) balance query explicitly has to work around the stale flag by using a `NOT EXISTS` check against actually-good stable spenders instead of trusting `outputs.is_spent`: [6](#0-5) 

By contrast, `archiving.js` does correctly reverse `is_spent` when a joint is archived/voided: [7](#0-6) 
but this un-spend path is only exercised for archived/voided joints (e.g., during light-client catch-up pruning), not for the normal full-node stabilization path where a `temp-bad` unit is confirmed `final-bad` in `main_chain.js`.

### Impact Explanation
Any unprivileged unit poster who ends up with two competing spends of the same output (e.g., a wallet double-broadcast, a race between a user's own retransmitted payment, or a multi-authored/shared-address transaction whose sequence flips to `final-bad` for reasons unrelated to this specific input) can leave the referenced output permanently flagged `is_spent=1` in the `outputs` table even though it was never actually spent by any `good` unit. Since balance/spendable-output queries throughout the codebase (as illustrated by `balances.js`/`compare_vote_balances.js`) filter on `is_spent=0`, the coin becomes invisible/unspendable to normal wallet balance and payment-composition logic — a concrete fund-freezing condition reachable purely by posting units, without needing a hub, node operator, or network-level attack.

### Likelihood Explanation
The precondition — a unit with a `transfer` input ending up `final-bad` after being written with `is_spent=1` already applied — is a normal, expected outcome of the existing double-spend/non-serial resolution mechanism (`findConflictingUnits`/`markMcIndexStable`), not an edge case requiring privileged access. It can be triggered unintentionally by ordinary wallet behavior (retries, network races) or deliberately by a user against their own outputs, and the missing reset logic is corroborated by the maintainers' own comparison tool description of "zombie-spent outputs."

### Recommendation
When a unit's `sequence` is confirmed as `final-bad` (both in `markMcIndexStable()`'s `handleNonserialUnits()` and in `propagateFinalBad()`), issue additional queries to reset `outputs.is_spent=0` (and the analogous `headers_commission_outputs`/`witnessing_outputs` `is_spent` flags) for every output referenced by that unit's inputs, unless another `good` unit already claims the same output. Reuse the existing `generateQueriesToUnspendTransferOutputsSpentInArchivedUnit`-style logic from `archiving.js` in this code path.

### Proof of Concept
1. From address A, broadcast unit U1 spending output O (a stable, `good` output) to address B.
2. Before U1 stabilizes, broadcast a conflicting unit U2 from the same address A, spending the same output O to address C (e.g., due to wallet retry after perceived failure, or deliberately).
3. Both U1 and U2 are written; `writer.js` sets `outputs.is_spent=1` on O for both (writer.js:378-383).
4. During stabilization, `findConflictingUnits`/`markMcIndexStable` resolves the conflict: suppose U1 becomes `good` and U2 becomes `final-bad` (main_chain.js:1327-1350), or a third-party cause (e.g., cross-author conflict) makes the *only* spender of O `final-bad`.
5. `inputs.is_unique` for the losing unit is cleared, but `outputs.is_spent` on O is never reset.
6. Query `outputs` for O: `is_spent=1` persists even in the case where no `good` unit actually spent O, permanently excluding O from balance calculations that filter on `is_spent=0`, as demonstrated by the discrepancy check in `tools/compare_vote_balances.js`.

async function balancesNewWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const rows = await db.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)

function generateQueriesToUnspendTransferOutputsSpentInArchivedUnit(conn, unit, arrQueries, cb){
	conn.query(
		"SELECT src_unit, src_message_index, src_output_index \n\
		FROM inputs \n\
		WHERE inputs.unit=? \n\
			AND inputs.type='transfer' \n\
			AND NOT EXISTS ( \n\
				SELECT 1 FROM inputs AS alt_inputs \n\
				WHERE inputs.src_unit=alt_inputs.src_unit \n\
					AND inputs.src_message_index=alt_inputs.src_message_index \n\
					AND inputs.src_output_index=alt_inputs.src_output_index \n\
					AND alt_inputs.type='transfer' \n\
					AND inputs.unit!=alt_inputs.unit \n\
			)",
		[unit],
		function(rows){
			rows.forEach(function(row){
				conn.addQuery(
					arrQueries, 
					"UPDATE outputs SET is_spent=0 WHERE unit=? AND message_index=? AND output_index=?", 
					[row.src_unit, row.src_message_index, row.src_output_index]
				);
			});
			cb();
		}
	);
}
