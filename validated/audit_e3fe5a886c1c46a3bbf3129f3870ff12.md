### Title
Unresolved inner address definitions are unconditionally accepted as signed in `validateDefinition` - ([File: definition.js])

### Summary
`CVE-2021-40690` is a case where a security-relevant flag (`secureValidation`) is silently dropped when a definition is resolved through one extra level of indirection (`KeyInfoReference` → `KeyInfo`), letting an attacker bypass a restriction that would otherwise apply. The closest reachable analog in this codebase is in the `'address'` operator of `validateDefinition()` in `definition.js`, where a restriction flag that used to gate acceptance of an unresolved nested address reference has been hard-coded to always succeed, regardless of the calling context.

### Finding Description
In `definition.js`, `validateDefinition()`'s `'address'` case dereferences another address's spending definition. When the inner definition cannot be found in storage, the code falls back to looking for a matching author-supplied definition in the current unit: [1](#0-0) 

The critical line is:
```
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
var bAllowUnresolvedInnerDefinitions = true;
``` [2](#0-1) 

The original gating check (`objValidationState.bAllowUnresolvedInnerDefinitions`) — which presumably was meant to be `true` only in specific validation contexts (e.g., top-level definition validation without a known unit) — is commented out and replaced with an unconditional `true`. This means that whenever an `'address'` sub-expression references another address whose definition is not resolvable in storage and not supplied by a matching co-author in the current unit, the evaluator now treats that branch as valid and signed (`cb(null, true)`) in **every** validation context, not just the contexts the original flag was designed to permit.

This is directly analogous to the Apache Santuario bug: a security flag that should be forwarded/checked correctly across one level of reference indirection (nested/inner address definition resolution via `'address'`) is instead force-set to the permissive value, so the "unresolved reference" restriction is bypassed unconditionally.

### Impact Explanation
`validateDefinition()` is invoked whenever a new address or asset spending-condition definition is posted (unit author definition, `definition` message, asset issuer/transfer conditions) and it enforces that "each branch must have a signature" as its correctness invariant: [3](#0-2) 

Because the `'address'` branch resolving to an unresolved reference is now always reported as `bHasSig = true`, an attacker (any unprivileged unit poster / address definer) can construct an `or`/`r of set`/`weighted and` definition containing a branch such as `['address', 'SOME_UNRELATED_UNUSED_ADDRESS']` that:
- points to an address with no known/resolvable definition, and
- is not actually supplied by any co-author in the unit,

and have that branch counted as satisfying the "signature present" requirement for the whole definition, even though it provides no real authentication when actually spent. This lets a malicious definition pass validation-time acceptance checks that are meant to guarantee every logical branch of a spending condition is backed by an actual, verifiable authentifier (signature/hash), weakening the guarantee normally provided at definition-creation time. Combined with `or`-style branches, this can be used to register address/asset spending-condition definitions that appear to satisfy the "has a signature somewhere" sanity check while containing branches that are effectively unauthenticated placeholders, undermining a validity invariant that other protocol logic (and downstream tooling) may rely on when accepting such definitions as sound.

### Likelihood Explanation
Any unprivileged unit poster can trigger this path directly by submitting a unit containing an address/asset definition with an `'address'` operator referencing an address that has no resolvable/co-author-supplied definition — this requires no special privileges, no cooperation from other parties, and no network-level trust assumptions. The code path is reached on every definition validation, making the likelihood high for a crafted, low-cost unit.

### Recommendation
Restore the original conditional gate instead of the hard-coded `true`:
```js
if (objValidationState.bAllowUnresolvedInnerDefinitions)
    return cb(null, true);
return cb("definition of inner address " + other_address + " not found");
```
so that unresolved nested address references are only treated as acceptable in the specific validation contexts intended by `objValidationState.bAllowUnresolvedInnerDefinitions`, preserving the "each branch must have a signature" invariant in all other contexts.

### Proof of Concept
1. Post a unit that defines (or redefines, via `definition` message) an address/asset spending condition of the form:
   ```
   ["or", [
     ["address", "SOME_ADDRESS_WITH_NO_KNOWN_DEFINITION_AND_NO_COAUTHOR_DEFINITION"],
     ["sig", {"pubkey": "<attacker_pubkey>"}]
   ]]
   ```
2. `validateDefinition()` evaluates the `'address'` branch; `storage.readDefinitionByAddress` reports `ifDefinitionNotFound`, and since no co-author in the unit supplies a matching definition, `arrDefiningAuthors.length === 0`.
3. Because `bAllowUnresolvedInnerDefinitions` is now unconditionally `true` [4](#0-3) , the callback returns `cb(null, true)`, marking this branch as having a signature — even though it never actually resolved a real authentifier.
4. The overall `'or'` evaluation combines this artificially "signed" branch with the real `'sig'` branch, and the top-level "each branch must have a signature" check passes trivially regardless of whether the unresolved branch is ever meant to be satisfiable.
