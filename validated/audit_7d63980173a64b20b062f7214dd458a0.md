### Title
Cross-repository forged `Status` defeats `Commit#blocked?`/`Commit#blocking?` because status trust has no repository-origin check - (File: `app/models/shipit/commit.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves commits to attach a status to purely `by sha` across the entire `commits` table, with no scoping to the repository that authenticated the webhook, unlike the base `Handler#stacks` helper which does scope by `repository_name`. Because git commit SHAs are stable across forks/mirrors, an attacker who owns any repository sharing history with the victim's repo can post a validly-signed webhook from their own repo that writes a `Status` row onto the victim's commit, and `Commit#blocking?`/`blocked?` consume that status with no way to tell it didn't originate from the victim's authorized CI context.

### Finding Description
Broken binding: the question posits the invariant `status.repository == commit.stack.repository` (the repository that authorized the status equals the repository whose blocking logic consults it). Tracing the code shows this equality is never enforced.

- `Shipit::Webhooks::Handlers::StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This looks up commits by `sha` alone across **all** stacks/repositories, not via the `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) which scopes to `Repository.from_github_repo_name(repository_name)`. Any commit row in any stack that happens to share the SHA gets the forged status attached.

- `verify_signature` in `WebhooksController` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload came from *some* registered GitHub org/repo (the attacker's own repo/org, which the attacker fully controls and can register with Shipit as their own stack) - it says nothing about which commit/stack the status should apply to. `context`, `state`, and `sha` are all attacker-chosen (`accepts :context, String`, `requires :state, String`, `requires :sha, String`).

- `Commit#blocking?` is delegated to `status` (`app/models/shipit/commit.rb:219`, `304-306`), and `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) is:
```ruby
def blocking?
  !success? && commit.blocking_statuses.include?(context)
end
```
There is no field on `Status` distinguishing which repository/webhook produced it - `state` and `context` are trusted identically regardless of origin. If a victim commit was blocked because a required `context` was `Status::Missing` (never reported), a forged `success` status with the matching `context` string, once attached via `create_status_from_github!` → `add_status` → `Status::Group.compact`, replaces the missing/blocking entry with a "success" entry for that context.

- `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) then re-scans `stack.commits.reachable...any?(&:blocking?)` purely within `self.stack`, but since the underlying per-commit `blocking?` has already been flipped to false by the forged cross-repo status, `blocked?` faithfully (and incorrectly) re-derives `false` - it trusts the forged row identically to a legitimate one because nothing in the data model or query distinguishes provenance.

Attacker flow:
1. Attacker forks/owns a repository (`repo X`) that shares a commit SHA with the victim's tracked repository (e.g., because it's a fork sharing history, or the victim cherry-picked/merged a commit also present in repo X).
2. Attacker configures a webhook on repo X (their own repo, using their own valid signing secret) and POSTs a `status` event: `sha: <shared sha>`, `state: 'success'`, `context: '<victim's required CI context string>'`.
3. `verify_signature` passes (signature is valid for repo X, which the attacker legitimately owns).
4. `StatusHandler#process` matches `Commit.where(sha: ...)`, which includes the victim's `Commit` row (same sha, different stack), and calls `create_status_from_github!` on it.
5. The victim commit's `status` recomputes to success for that context; `blocking?` → false; `blocked?` → false; `deployable?` → true.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) validate webhook authenticity and payload shape but not commit/stack ownership, so they do not prevent this divergence.

### Impact Explanation
An unprivileged attacker who controls any repository/webhook can write into an unrelated victim stack's `Status` records and flip that commit's blocking/deployability state, defeating the required-CI-status safety gate and enabling an unauthorized deploy of a commit that never actually passed the victim's CI check. This is a "payload for one repository mutating another's stack/commit" scenario, matching the Critical severity bucket (payload for one repo mutating another's stack/commit/task, or an unauthorized deploy). It is repeatable against any repository/commit SHA the attacker can align with a fork or shared history, and blast radius extends to any Shipit stack tracking a repository whose commit history the attacker can duplicate.

### Likelihood Explanation
Preconditions: the attacker needs (a) a GitHub repository they own/administer whose webhook they can configure and sign legitimately, and (b) a commit SHA shared with the victim's tracked repository (trivially achievable by forking the victim repo, since fork commits retain identical SHAs until rebased). No Shipit credentials, session, API token, or GitHub App secret are required - only the attacker's own repo's webhook secret, which they control. This is low-cost and fully repeatable/scriptable against any target repository they can fork.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers, e.g. check-run handlers) to the repository that authenticated the webhook, mirroring `Handler#stacks`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Stack -> Repository` so only commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')` are updated. Do not allow `Commit.where(sha: ...)` to be resolved globally across repositories.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
  test "a status webhook from an unrelated repository cannot unblock a victim commit" do
    victim_stack = shipit_stacks(:shipit)
    victim_stack.update!(cached_deploy_spec: { blocking_statuses: ['ci/required'] })
    attacker_stack = shipit_stacks(:cyclimse) # a different, unrelated stack/repository

    shared_sha = 'a' * 40
    victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared commit')
    # simulate the same sha existing under an unrelated repo/stack (e.g. via a fork)
    attacker_stack.commits.create!(sha: shared_sha, message: 'shared commit')

    # required context never reported -> Status::Missing -> blocking
    assert victim_commit.reload.blocking?

    payload = {
      'sha' => shared_sha,
      'state' => 'success',
      'context' => 'ci/required',
      'repository' => { 'full_name' => attacker_stack.repository.full_name,
                         'owner' => { 'login' => attacker_stack.repository.owner } },
    }

    Shipit::Webhooks::Handlers::StatusHandler.call(payload)

    # binding under test: status.repository == commit.stack.repository
    assert_not_equal attacker_stack.repository.full_name, victim_stack.repository.full_name

    assert_not victim_commit.reload.blocking?, "forged cross-repo status should not clear victim's blocking status"
    assert_not victim_commit.blocked?
  end
end
