### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a cross-repository/cross-stack status webhook flip `Stack#ignore_ci` via `Status#enable_ci_on_stack` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table, with no filter tying the webhook's `repository` field to the commit's stack, unlike every sibling handler. Because `Status#enable_ci_on_stack` unconditionally calls `commit.stack.enable_ci!` on every `Status` creation, an attacker who can get one validly-signed webhook delivered (from a repository/org they control) for a `sha` that happens to also exist as a `Commit` on an unrelated victim `Stack` can flip that victim stack's `ignore_ci` to `false`, with no ownership check on the stack being mutated.

### Finding Description
The broken binding: the party allowed to change `Stack#ignore_ci` must be `commit.stack`'s own repository/owner (equivalently, `payload.dig('repository','full_name') == commit.stack.repository.full_name`). In `StatusHandler#process` this equality is never checked: [1](#0-0) 

Compare with the sibling handlers, which all restrict work to `stacks` (i.e. `Repository.from_github_repo_name(repository_name)&.stacks`), derived from the webhook's own `repository.full_name`: [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler` is the only handler that bypasses this `stacks` scope entirely and queries `Commit` globally by `sha`. Once a matching `Commit` is found (regardless of which stack/repository it belongs to), `create_status_from_github!` creates a `Status`, whose `after_create` callback runs unconditionally: [5](#0-4) [6](#0-5) 

and `Commit#create_status_from_github!` performs no repository check either: [7](#0-6) 

`WebhooksController#verify_signature` only proves the payload was signed by *some* organization matching `repository.owner.login` in the payload; it never checks that the referenced `sha`'s owning stack belongs to that same repository: [8](#0-7) 

Exploit flow: the attacker needs a `Commit` row with a `sha` matching one already present on the victim stack — either (a) because the same underlying repository is tracked by multiple `Stack`s/environments (demonstrated directly by the fixtures, e.g. `shipit` stack commit `first` and `shipit_canaries` stack commit `canaries_first` share sha `6d9278037b872fd9a6690523e411ecb3aa181355`), or (b) because the attacker forked the victim's repository, which preserves identical commit SHAs for shared history — both explicitly within the stated attacker capabilities ("push to a fork," "emit webhooks from a repository they own"). The attacker triggers (or the underlying CI naturally emits) a `status` event referencing that `sha`; the webhook is validly signed for the attacker's own org/repo. `StatusHandler#process` matches every `Commit` with that `sha` across the whole install, including the victim's, and creates a `Status` on the victim's commit, which fires `enable_ci_on_stack` and flips `stack.ignore_ci` to `false` — a configuration write the attacker never authorized nor administers.

Existing guards do not stop this: `verify_signature` authenticates the sending organization/repo, not the target stack; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not ownership; there is no `require_permission!` or stack-membership check anywhere on this path; `stacks`/`Repository.from_github_repo_name` scoping — used by every other handler — is simply absent here.

### Impact Explanation
Any `Stack` whose `Commit#sha` collides with a commit reachable by an attacker-controlled/attacker-triggered webhook has its `ignore_ci` column mutated to `false` without authorization, altering deployment-gating semantics (`Commit#deployable?` depends on `stack.ignore_ci?`). This is a payload from one repository/webhook context mutating another stack's configuration — matching the Critical category "a payload for one repository mutating another's stack." It is repeatable against any stack sharing a commit sha with an attacker-reachable webhook source, and is not limited to a single victim if the attacker can enumerate/guess shared history (e.g., popular open-source repos with many downstream forks/environments configured in Shipit).

### Likelihood Explanation
Preconditions: (1) attacker can get one validly-signed `status` webhook delivered to the Shipit endpoint (own repo/org with the app/webhook installed, or a real CI status fired on a fork sharing commit history with the victim repo), and (2) a `Commit` with the referenced `sha` exists in the victim stack (guaranteed for same-repo multi-environment setups, as shown by the fixtures; plausible for forks of the tracked repo). No Shipit session, API token, or org membership beyond the attacker's own repo is required. Cost is a single webhook/status event; the effect is deterministic and repeatable.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve commits only through `stacks` (derived from the webhook's `repository.full_name`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, so a status update can only touch commits belonging to stacks of the repository that actually sent the webhook.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Create/reuse two stacks with different `repository` fixtures, e.g. `shipit` (`ignore_ci: false`) and `undeployed_stack` (`repository: foo-bar`, `ignore_ci: true`).
2. Insert a `Commit` on the victim stack (`undeployed_stack`) with a `sha` equal to a `Commit` sha that also exists in a different stack tracking a different repository (mirroring the existing `first`/`canaries_first` sha collision in `test/fixtures/shipit/commits.yml`).
3. Assert precondition: `assert stack.reload.ignore_ci?` (victim's ignore_ci is `true` before the attack).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => <colliding sha>, 'state' => 'success', 'repository' => { 'full_name' => 'attacker/other-repo' })` (or POST to `WebhooksController#create` with signature verification stubbed, as done in `test/controllers/webhooks_controller_test.rb`), using a payload whose `repository` does NOT match the victim stack's repository.
5. Assert post-condition: `refute stack.reload.ignore_ci?` — the victim stack's `ignore_ci` flipped to `false` as a side effect of `Status#enable_ci_on_stack`, despite the webhook payload never referencing that stack's repository.
