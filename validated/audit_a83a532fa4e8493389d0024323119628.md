### Title
Webhook signature is verified against the attacker's own organization while `StatusHandler` writes commit statuses without any repository check, enabling a forged CI status that unlocks unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using the organization named inside the *unverified* request body, then verifies the signature against that same organization's own secret. Any GitHub organization legitimately onboarded to the Shipit instance can therefore produce a validly-signed webhook for itself. The `status` event handler, however, never checks which repository/organization the status belongs to — it looks up the target `Commit` purely by `sha` across the entire database. This breaks the intended binding "organization that authenticated == repository that is written," letting a low-privileged org owner forge a passing CI status on a commit that actually belongs to a different, victim repository, which can satisfy `required_statuses` and unlock an unauthorized deploy.

### Finding Description
`repository_owner` (used to pick the verification secret) is read straight from the untrusted payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the GitHub App/secret config keyed by that organization name, and `verify_webhook_signature` only proves that the raw body was HMAC-signed with *that* organization's secret — not that the body's contents actually pertain to that organization's repositories: [3](#0-2) 

For most handlers, the target repository/stack is re-derived from `payload.dig('repository', 'full_name')` via `Handler#stacks`: [4](#0-3) 

This is already a second, independently-controlled field (nothing enforces `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` used for signature selection), but `StatusHandler` doesn't even use `full_name` — it looks up commits purely by SHA with no repository scoping at all: [5](#0-4) 

Because Git commit SHAs are derived from content and are shared across every fork/mirror of a repository, an attacker who owns (or forks) a public repository whose history overlaps with a victim's tracked repository can trivially produce a `status` payload whose `sha` matches a commit already recorded for the victim's `Stack` (synced earlier via legitimate `push` events). The attacker signs this payload with their own org's `webhook_secret` — which `verify_signature` happily accepts because it only checked that the signature matches the organization named in the payload, not that the acted-upon repository belongs to that organization.

**Binding broken:** organization authenticated by the webhook signature (`repository_owner` picked from payload) ≠ repository/commit actually written to (`Commit.where(sha:)` with no owner/repo filter).

### Impact Explanation
`commit.create_status_from_github!(params)` lets the attacker inject an arbitrary CI status (`state`, `context`, `description`, `target_url`) onto a commit belonging to a repository/stack they do not control. Shipit's deploy gating (`Stack#required_statuses`, `Commit#deployable?`) relies on these stored statuses. By forging a `success` status for the exact `context` a victim stack requires, an attacker can make an otherwise CI-failing or unreviewed commit appear deployable, potentially triggering an automatic/continuous deployment or letting an operator merge/deploy a commit that never actually passed CI. This crosses the "unauthorized deploy" impact bar defined in scope, since it manipulates deploy-gating state cross-repository using only the attacker's own, legitimately-issued webhook credentials.

### Likelihood Explanation
Likelihood is Medium: it requires (1) the attacker to already be an authenticated GitHub organization onboarded to the same multi-tenant Shipit instance (a realistic scenario for self-hosted Shipit deployments serving many orgs/teams), and (2) a SHA collision opportunity, which is trivially achievable by forking/mirroring the victim's public repository (its history and commit SHAs are copied identically) or by knowing a specific target commit SHA in advance. No GitHub App private key, `ApiClient` token, or repository write access is needed — only a webhook secret that the attacker's own org is entitled to.

### Recommendation
`StatusHandler` (and other handlers) should never resolve target records by content alone; every handler must scope commit/stack lookup by the repository derived from `payload.dig('repository', 'full_name')`, and — critically — `WebhooksController#verify_signature` must confirm that the organization used to select the verification secret matches the owner segment of `repository.full_name` actually referenced by the payload before dispatching to handlers, rejecting mismatches with 422.

### Proof of Concept
1. Attacker registers/owns GitHub organization `attacker-org`, which is legitimately configured in Shipit with its own `webhook_secret`.
2. Attacker forks the victim's public repository `victim-org/victim-repo` (or otherwise learns a commit SHA `abc123` already tracked by a `Shipit::Stack` for `victim-org/victim-repo`, e.g. from a public push event).
3. Attacker builds a `status` webhook JSON body:
   ```json
   {
     "sha": "abc123",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker_org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature (attacker knows their own secret) — see `app/controllers/shipit/webhooks_controller.rb:24-30`.
6. `StatusHandler#process` runs `Commit.where(sha: 'abc123').each { |commit| commit.create_status_from_github!(params) }` — see `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — matching and updating the victim's tracked commit regardless of the `attacker-org` repository named in the same payload, forging a passing status that can satisfy `victim-org/victim-repo`'s `required_statuses` gate.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
