### Title
Webhook Signature is Verified Against `repository.owner.login`/`organization.login` But `StatusHandler` and Other Handlers Act on an Unrelated `repository.full_name`/Commit SHA, Enabling Cross-Organization Status/Sync Forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate a webhook against using `repository.owner.login` (or `organization.login`) pulled out of the *same, attacker-authored* JSON body it is about to verify [1](#0-0) . Downstream handlers then act on a *different* field of that body — `repository.full_name` in most handlers, or, worse, no repository scoping at all in `StatusHandler`, which resolves target commits purely by `Commit.where(sha: params.sha)` across the entire installation [2](#0-1) . In a multi-organization Shipit deployment (`Shipit.github_organizations`, each org with its own `webhook_secret` in `secrets.github`) [3](#0-2) , an attacker who legitimately controls the webhook secret for one configured organization can craft a payload whose `repository.owner.login`/`organization.login` names *their own* org (so it passes verification against their own secret) while the `sha`/`repository.full_name` field targets a stack that belongs to a *different* organization.

### Finding Description
The binding that should hold is: **organization whose secret authenticated the request == repository/stack the handler is permitted to mutate**. This binding is violated:

- Verification side: `verify_signature` picks the `GitHubApp` (and thus the HMAC secret) via `repository_owner`, itself derived from the unverified JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) [4](#0-3) , then calls `github_app.verify_webhook_signature(signature, raw_post)` which HMACs the *entire* raw body against that org's secret [5](#0-4) .
- Action side: `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no repository/organization filter whatsoever** [2](#0-1) , and the base `Handler#stacks` helper used by other handlers resolves the target purely from `payload.dig('repository','full_name')` [6](#0-5)  — a field that is never compared to `repository.owner.login`, the field the signature check actually trusted.

Since the attacker authors the entire JSON body and only needs to know *one* configured org's `webhook_secret` to produce a valid HMAC over the whole payload, nothing stops them from putting a trusted org's login in `repository.owner.login`/`organization.login` while pointing `sha` (for `StatusHandler`) or `repository.full_name` (for `PushHandler`/PR handlers) at a completely different organization's stack.

### Impact Explanation
`StatusHandler` writes a `Status` for any matching commit and reruns `add_status`, which schedules `ProcessMergeRequestsJob` and continuous delivery whenever the state transitions to `pending`/`success` [7](#0-6) . By forging a `success` status against a required CI context for a known commit SHA on another organization's stack, an attacker with only their own (unrelated) organization's webhook secret can satisfy `ci.require`/`ci.blocking` and trigger continuous deployment/merge on a stack they have no authorization over — an unauthorized deploy/merge, which meets the Critical bar in the rules. `PushHandler` similarly allows forcing an unscheduled `sync_github` on another org's stack by mismatching `repository.owner.login` vs `repository.full_name` [8](#0-7) .

### Likelihood Explanation
This requires only that the Shipit instance is configured with multiple GitHub organizations (a documented, supported configuration via `secrets.github` per-org keys, not a misconfiguration) and that the attacker holds the `webhook_secret` of any one of them — plausible in any SaaS-style multi-tenant deployment where each customer organization supplies their own GitHub App/webhook secret. No repository write access, session, or `ApiClient` token is needed; the attacker only needs to be able to send an HTTP POST to `/webhooks` and knows a target commit SHA (often public on GitHub).

### Recommendation
Bind verification and action to the same identity: after selecting the `GitHubApp` via `repository_owner`, re-derive the same `repository_owner`/`organization` value the handlers use (`repository.full_name`'s owner segment) and require them to be equal before dispatching, or pass the verified organization into the handler and have every handler (especially `StatusHandler`) filter by `stack.repository.owner`/`full_name` in addition to `sha`, rejecting any event where the verified org does not match the owner of the repository/stack being mutated.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (`secrets.github.orga.webhook_secret`, `secrets.github.orgb.webhook_secret`), each with a stack tracking their own repos.
2. As an operator of `orgA` (holder of `orgA`'s webhook secret only), craft a `status` event body:
```json
{
  "sha": "<known-sha-of-a-commit-on-orgB/some-repo>",
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "orgA" },
  "repository": { "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC(orgA_webhook_secret, body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` resolves `repository_owner == "orgA"`, verifies successfully against `orgA`'s secret [1](#0-0) .
5. `StatusHandler#process` matches `Commit.where(sha: ...)` — since the commit belongs to `orgB`'s stack, not `orgA`'s — and calls `create_status_from_github!`, which can flip the commit's status to `success` and schedule continuous delivery/merge on `orgB`'s stack [2](#0-1) , despite the request never being authenticated against `orgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
