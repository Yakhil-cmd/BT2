### Title
CCMenu API token created via `CCMenuUrlController` is not scoped to the requesting stack, allowing any stack's build/lock status to be read - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
The `set_owner`-style bug class (a privileged field being set/consumed without validating that it actually matches the entity it is presented as authorizing) has an analog here: an `ApiClient` token that is *presented* to the user as being scoped to a single stack is in fact created without any `stack_id` binding, so the token authorizes reads of every stack, not just the one whose CCMenu URL the user requested.

### Finding Description
`CCMenuUrlController#fetch` builds a per-stack "CCMenu URL" containing an API token, intended to let a monitoring widget (CCMenu is typically embedded in shared/public build-status dashboards) read the status of *one specific stack*: [1](#0-0) 

The token is produced by:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```
`find_or_create_by!` only matches/creates on `creator` and `name` — the `stack:` association is never set, and it is not part of the lookup key either. As a result:
1. A single `ApiClient` record named `"CCMenu Client"` is created once per user and reused for every stack for which that user requests a CCMenu URL.
2. Because `ApiClient#stack_id` is nil, `Shipit::Api::BaseController#stacks` treats the token as unscoped: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` returns `Stack.all`. [2](#0-1) 

Making matters worse, `Api::CCMenuController` doesn't even go through that scoped `stacks`/`stack` helper — it overrides `stack` to hit `Stack.from_param!(params[:stack_id])` directly: [3](#0-2) 

So even if the token *were* stack-scoped, this controller's local override would bypass that scoping entirely. Combined with the fact that the token is never actually bound to a stack in the first place, the "stack a token authorises" (the one stack shown in the URL) and "the stack it touches" (any stack, by simply changing `stack_id` in the query string) are not equal.

### Impact Explanation
Anyone who obtains one CCMenu URL/token for a given stack — a scenario the feature explicitly encourages, since CCMenu URLs are meant to be pasted into third-party CI-status monitors/dashboards, some of which are publicly reachable — can enumerate `stack_id` values and read the build/lock/deploy status of every other stack in the Shipit instance (`stack.deploys_and_rollbacks`, lock status, etc. via `app/views/shipit/ccmenu/project.xml.builder`). This is an unauthorized cross-stack read of stack state that the feature's design intends to prevent (the URL is generated per-stack specifically to avoid this). It matches the "High" category: unauthenticated/unauthorized read of stack state via a token that was supposed to be scoped to a single resource.

### Likelihood Explanation
Any authenticated Shipit user can trigger `CCMenuUrlController#fetch` for a stack they can view, obtaining a token; no special privilege is required to exploit the flaw itself — only possession of one valid, previously-issued CCMenu token (their own, or one that leaked because it was embedded in an external monitoring tool as intended by the feature). Guessing/enumerating other `stack_id`s (`owner/name/environment`) is straightforward since they are visible in the Shipit UI.

### Recommendation
- In `CCMenuUrlController#client`, explicitly bind and match on the stack: `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')` (or generate a unique client/token per stack).
- In `Api::CCMenuController`, remove the local `stack` override and instead use the inherited `stacks`/`stack` helpers from `BaseController` so token-to-stack scoping (`current_api_client.stack_id`) is actually enforced.
- Add a regression test asserting that a CCMenu token minted for stack A returns 403/404 (not 200) when used against stack B's `/api/stacks/:stack_id/ccmenu` endpoint.

### Proof of Concept
1. As user `walrus`, request `GET /ccmenu/shopify/shipit/production` (via `CCMenuUrlController#fetch`) → receive `ccmenu_url` containing `token=T`.
2. As the same user, request the CCMenu URL for a *different, private* stack, e.g. `GET /ccmenu/some-org/secret-repo/production` → the controller reuses the same `ApiClient` (`find_or_create_by!(creator: walrus, name: 'CCMenu Client')`), returning the *same token* `T`.
3. Using token `T` (leaked or embedded in a public dashboard for stack A), call `GET /api/stacks/some-org/secret-repo/production/ccmenu?token=T` directly.
4. The request succeeds and returns build/lock/deploy status for `secret-repo`, a stack the token was never explicitly scoped to — confirmed by `Api::BaseController#stacks` returning `Stack.all` for an unscoped `ApiClient`, and by `Api::CCMenuController#stack` bypassing scoping altogether.
