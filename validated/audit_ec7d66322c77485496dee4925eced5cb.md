This confirms the exploit chain: Shipit supports multiple GitHub App configurations keyed by organization name, each with its own `webhook_secret` [1](#0-0) . This is a legitimate multi-tenant setup that Shipit ships and documents. The vulnerability is that the field used to select which secret verifies the HMAC signature (`repository.owner.login`) is different from the field the event handlers use to determine which `Repository`/`Stack` the payload acts upon (`repository.full_name`), and nothing enforces that these two fields are consistent within the same signed payload.

### Title
Webhook signature verified against `repository.owner.login`-selected secret while handlers act on independently-controlled `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `organization.login`) [2](#0-1) [3](#0-2) . Once the signature check passes, the entire raw JSON body is handed unmodified to every registered handler via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . Handlers, however, resolve the target `Repository`/`Stack` using a *different* field: `payload.dig('repository', 'full_name')` [5](#0-4) , and the same pattern (`params.repository.full_name`) repeats across every pull-request handler (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `edited_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`) [6](#0-5) [7](#0-6) .

### Finding Description
Because Shipit explicitly supports one `webhook_secret` per organization (documented and tested via `test/dummy/config/secrets_double_github_app.yml`, keyed `OrgOne`/`OrgTwo`, each with its own `webhook_secret`) [1](#0-0) , a GitHub organization administrator who owns a legitimate GitHub App installation on their own org knows (or can obtain) that org's `webhook_secret`. That secret authenticates *only* "this request came from an app installation belonging to `repository.owner.login`" — an equality of the form `verified_secret_owner == payload['repository']['owner']['login']`. It does **not** and cannot authenticate `payload['repository']['full_name']`, `payload['pull_request']`, `payload['sha']`, or any other field consumed downstream, because those are read from the same JSON blob but never re-checked against the owner used for verification.

An attacker who administers "attacker-org" (with its own webhook secret registered in Shipit) can craft a webhook payload where `repository.owner.login = "attacker-org"` (so `verify_signature` selects and successfully validates against the attacker's own known secret) while `repository.full_name = "victim-org/victim-repo"` (or any other repository name string). The handler layer then looks up `Repository.from_github_repo_name("victim-org/victim-repo")` and acts on that repository's stacks/pull requests regardless of which organization's key actually signed the request [8](#0-7) .

This breaks the intended binding: *the organization whose credentials authenticated the webhook* should equal *the repository the webhook is permitted to mutate*, but the engine only checks the former field for signature routing and blindly trusts the latter field for authorization/target-selection.

### Impact Explanation
Handlers gated by `repository.full_name` perform real writes on arbitrary stacks not owned by the authenticating organization: e.g. `PullRequest::OpenedHandler#process` calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [9](#0-8) , `ClosedHandler#process` calls `review_stack.archive!` [10](#0-9) , and `LabeledHandler`/`UnlabeledHandler` can `stack.archive!` / `stack.unarchive!` [11](#0-10) . An attacker controlling only their own org's app installation can therefore forge signed events that create, archive, or unarchive review stacks belonging to a completely different repository/organization tracked by the same Shipit instance — a cross-repository write achieved purely by crafting a mismatched `owner.login`/`full_name` pair inside a payload they can legitimately sign.

### Likelihood Explanation
Requires the attacker to control (or be granted) a GitHub App installation registered in Shipit's multi-org config, and requires the target Shipit instance to track multiple organizations' repositories — both realistic in a shared/central Shipit deployment as this feature is explicitly built and tested for (`secrets_double_github_app.yml`). No repository write access to the victim repo, no `ApiClient` token, and no session are needed — only knowledge of the attacker's own already-authorized webhook secret and the ability to send an HTTP request to the public webhook endpoint.

### Recommendation
In `Handler#repository_name` (and every duplicate implementation across pull-request handlers), derive the target repository from the *same* field that was cryptographically verified (`repository.owner.login`, or by re-deriving the organization from the verified GitHub App context) instead of trusting `repository.full_name` independently. Alternatively, `WebhooksController#verify_signature` should assert that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers, so the field bound by the signature-selection logic cannot diverge from the field the handlers act on.

### Proof of Concept
1. Attacker registers/controls a GitHub App installation for `attacker-org`, configured in Shipit's `github:` multi-org secrets with its own `webhook_secret` (same shape as `secrets_double_github_app.yml`).
2. Attacker computes `sha1=HMAC(webhook_secret_attacker_org, body)` over a crafted JSON body:
   ```json
   {
     "action": "opened",
     "number": 1,
     "pull_request": { ... },
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
3. POST to `/webhooks` with header `X-Github-Event: pull_request` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against the attacker's own known secret [2](#0-1) .
5. `PullRequest::OpenedHandler` is invoked with the full payload, resolves `Repository.from_github_repo_name("victim-org/victim-repo")` [6](#0-5) , and provisions/archives a review stack under the victim's repository — a write the attacker was never authorized to perform.
