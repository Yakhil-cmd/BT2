Based on my analysis, this is a valid finding but with a significant caveat on the impact mechanism (PYTHONSTARTUP's effect is conditional).

### Title
Unfiltered pull-request label names leak into the `fetch`/`git` subprocess environment via `ReviewStack#env` and `StackCommands#fetch*` — ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and `StackCommands#fetch`/`#fetch_commit`/`#fetch_deployed_revision` pass that unfiltered env straight into `Command`/`PTY.spawn`. An unprivileged fork PR can therefore set an arbitrary environment-variable key (e.g. `PYTHONSTARTUP`) for every process spawned during the fetch phase of its own review stack, bypassing the `EnvironmentVariables#permit` allowlist that protects deploy/rollback/task steps.

### Finding Description
The broken binding: the invariant "the `fetch` step inherits no fork-controllable key" is violated — the equality that should hold is `Command#env (fetch step) == EnvironmentVariables.with(stack.env).permit(<some allowlist>)`, but in fact `Command#env (fetch step) == StackCommands#env == Commands#base_env.merge(@stack.env)` with `@stack.env` unfiltered.

Path:
1. `ReviewStack#env` [1](#0-0)  merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into the base env with no key allowlist.
2. Labels are persisted verbatim from the webhook body by `LabelCapturingHandler#capture_labels`, which does `pull_request.update!(labels: params.pull_request.labels.map(&:name))` with only a `String` type constraint, no name allowlist [2](#0-1) .
3. `StackCommands#env` is `super.merge(@stack.env)` (no `EnvironmentVariables#permit` call) [3](#0-2) , and `fetch`/`fetch_commit`/`fetch_deployed_revision` all pass this unfiltered `env:` directly to `Command.new` [4](#0-3) .
4. `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV` with no key filtering at all before calling `PTY.spawn(unbundled_env, ...)` [5](#0-4) .

By contrast, deploy/rollback/task envs are explicitly filtered through `EnvironmentVariables#permit` against a `variable_definitions` allowlist (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`) [6](#0-5) [7](#0-6) , and `EnvironmentVariables#permit` raises `NotPermitted` for any non-whitelisted key [8](#0-7) . No equivalent filter exists for the `fetch`/git-clone code path, so an attacker's PR label reaches `PTY.spawn`'s environment unchecked.

An attacker can achieve this by: opening/labeling a PR from their own fork on a repository configured with `provisioning_behavior: prevent_with_label` (or `allow_with_label`/`allow_all` — the vulnerable code path is identical regardless of provisioning behavior), naming a label `pythonstartup` (case-insensitive, since it's uppercased), and letting Shipit's webhook (`POST /webhooks`) create/refresh the review stack. `capture_labels` stores the label; `ReviewStack#env` exposes it as `PYTHONSTARTUP=true` to every `git fetch`/`git clone` command run for that stack.

### Impact Explanation
This lets the attacker set arbitrary environment-variable *names* (not just `PYTHONSTARTUP`) into the subprocess environment used for `git fetch`/`git clone` on their own review stack. This is confined to the attacker's own review stack/repository (fork-owned), since review stacks are scoped per pull request and `ReviewStackAdapter` resolves the stack from `repository.review_stacks` tied to that repo — there is no cross-tenant/cross-repository leakage demonstrated. The claimed RCE payload (`PYTHONSTARTUP` naming a malicious file) is not automatically triggered by this path: `PYTHONSTARTUP` is only consulted by CPython when a `python`/`python3` interpreter is launched in **interactive** mode with no script argument; plain `git fetch`/`git clone` invocations do not start an interactive Python REPL. I could not find any code in the `fetch` path that invokes an interactive Python interpreter, so the "python file executed at interpreter start" claim is not substantiated by this codebase — it would require an additional, unproven condition (some tool in the fetch chain dropping into an interactive Python shell) to become genuine code execution. Without that link, the concrete, demonstrable impact is limited to unauthorized/unfiltered environment-variable injection into the fetch subprocess (a control-bypass on `Command#env`/`EnvironmentVariables#permit`'s intended invariant), not verified RCE.

### Likelihood Explanation
Preconditions: `Shipit.review_stacks_enabled` on the target repository (any of the three `provisioning_behavior` values), and the attacker only needs the ability to open a PR from a fork and apply a label to it — both are unprivileged actions. Cost is a single webhook-triggering action (label a PR). The env-injection part is trivially reproducible and repeatable per PR/label. The RCE escalation via `PYTHONSTARTUP` is speculative given the current codebase and would need to be demonstrated against an actual interactive Python invocation somewhere in the fetch chain, which was not found.

### Recommendation
Apply the same `EnvironmentVariables#permit`-style allowlist to `ReviewStack#env`'s label-derived keys (or to the merged env used by `StackCommands#fetch`/`#fetch_commit`/`#fetch_deployed_revision`) before it reaches `Command#env`, rejecting or dropping any key that collides with a reserved/security-sensitive name (`PYTHONSTARTUP`, `LD_PRELOAD`, `BASH_ENV`, `PERL5OPT`, etc.), and/or restrict pull-request label names to a safe character set/prefix before they are allowed to become environment variable names.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (or a new fetch-specific test)
test "fetch step inherits fork-controllable label env keys (unfiltered)" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonstartup"]

  # binding under test: env reaching the fetch Command should equal a filtered set (expected),
  # but actually equals the unfiltered merged stack env (actual)
  actual_env = Shipit::StackCommands.new(stack).env
  assert_equal "true", actual_env["PYTHONSTARTUP"], "attacker-controlled label leaked into fetch env"

  command = stack.stack_commands.fetch # or reflect the Command built by #fetch
  assert_equal "true", command.env["PYTHONSTARTUP"]
end
```
This demonstrates the divergence: `fetch` env contains `PYTHONSTARTUP` sourced purely from an attacker-controlled PR label, with no allowlist rejecting it — confirming the missing invariant. Actual code execution via `PYTHONSTARTUP` was not reproduced against the git-fetch code path in this repository and should be treated as unproven.
