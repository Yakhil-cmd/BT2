## Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but handlers act on independent, unverified fields in the same payload (`repository.full_name`, `team.id`, `organization.login` reused for team scoping) — ([File: app/controllers/shipit/webhooks_controller.rb])

## Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook against using only `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself, then verifies the raw body against that org's secret [1](#0-0) [2](#0-1) . Once the signature check passes, every handler independently re-reads *other* attacker-supplied fields from the same body to decide **which repository/team/stack to mutate** — e.g. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [3](#0-2) , and `MembershipHandler` reads `params.organization.login` to create/scope a `Team` and grant membership [4](#0-3) . Nothing cross-checks that the org whose secret produced a valid HMAC is the same org named in the fields the handlers act on.

## Finding Description
Shipit explicitly supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, in a single deployment (`test/dummy/config/secrets_double_github_app.yml` configures `OrgOne` and `OrgTwo` as separate credential sets) [5](#0-4) . `Shipit.github(organization: ...)` looks up the `GithubApp` config keyed by that organization name, and `verify_webhook_signature` HMACs the *raw* request body with that org's `webhook_secret` [6](#0-5) .

The binding that should hold is:
`organization whose secret produced a valid signature == organization whose resources (repository/team) the handler will mutate`

In `WebhooksController#verify_signature`, the organization used to pick the secret is `repository_owner`, which is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both are ordinary JSON fields inside the same signed body [2](#0-1) . Because the entire raw body is under attacker control before it is signed, an attacker who legitimately administers "OrgA" (and therefore knows OrgA's `webhook_secret`, e.g. because they created/administer OrgA's own GitHub App installation pointed at this shared Shipit instance) can construct a JSON payload where:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` — used only for signature-secret selection, and
- other fields consumed by the handler — `repository.full_name` = `"OrgB/victim-repo"`, or `team.id`/`organization.login` inside a `membership` event — reference **OrgB**, an organization the attacker does not control.

The attacker signs this body with OrgA's own webhook secret and POSTs it to the shared `/webhooks` endpoint. `verify_signature` derives `repository_owner = "OrgA"`, fetches OrgA's `GithubApp`, and validates the HMAC successfully (it is a valid HMAC — over the attacker's own chosen bytes, using a secret the attacker legitimately possesses) [1](#0-0) . Control then passes to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) , and the handler acts on the *other*, unverified-against-the-signing-org fields:

- `PushHandler`/`Handler#stacks` resolves the target via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, independent of the org used for signature selection [3](#0-2) [8](#0-7) .
- `MembershipHandler` creates/updates a `Team` scoped by `params.organization.login` and adds/removes the named `member` from it [9](#0-8) . Team membership directly feeds `User#authorized?`, which gates access to the entire Shipit instance via `Shipit.github_teams` [10](#0-9) .
- Pull-request handlers (`opened_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`) resolve `repository` via `params.repository.full_name` to archive/unarchive/create review stacks for whatever repo is named, again independent of the signing org [11](#0-10) .

## Impact Explanation
This breaks the "organization that authenticated vs. the repository/team that is written" trust boundary called out in scope. The most severe concrete consequence is via `membership`: an attacker who controls (and thus can sign for) one org configured on the shared Shipit instance can forge a `membership`/`added` event naming a `team` belonging to a **different** org and a `member` login of their choosing, causing `Team#add_member` to grant that user membership in a team object whose `handle` (`organization/slug`) matches an entry in `Shipit.github_teams` [12](#0-11) . Since `User#authorized?` checks membership in `Shipit.github_teams` to gate the entire application [10](#0-9) , this is an escalation into `Shipit.github_teams` authorization — one of the explicitly in-scope High-severity impacts. A secondary, lower-severity effect (forged `push`/`pull_request` events pointing at a foreign `repository.full_name`) can cause spurious resyncs, unintended stack archival/creation, or fake commit statuses on repositories the forging org does not own — though these are lower impact and would need to be weighed against the "unauthorized deploy" bar to count independently.

## Likelihood Explanation
This requires the Shipit deployment to be configured for more than one GitHub organization (a documented, supported configuration — see `secrets_double_github_app.yml` and the `oauth`/organization-keyed config format) and requires the attacker to be an administrator of at least one of those configured orgs (able to see/rotate their own org's `webhook_secret`). This is a real but non-trivial precondition: it is not "any unauthenticated internet attacker," but it is also not a fully privileged Shipit user — it's cross-tenant trust abuse in a multi-org Shipit install, which is exactly the class of unprivileged-attacker/cross-boundary scenario in scope. I was not able to fully verify from the indexed code whether any additional runtime check (e.g., in `Shipit::Webhooks.for_event` dispatch or engine initializers) cross-validates the signing organization against payload-referenced resources before handler dispatch — the search only surfaced `WebhooksController`, `Handler`, and the individual event handlers, none of which perform such a check. A Devin session with full repo access should confirm there is no such check elsewhere (e.g., in `lib/shipit/webhooks.rb`) before treating this as fully proven.

## Recommendation
In `WebhooksController#verify_signature`/`create`, after establishing which organization's secret validated the signature, pass that organization identity down to handlers and require every handler to confirm that any organization/repository-owner referenced in the payload it acts on (`repository.owner.login`, `organization.login`) matches the signing organization before mutating state. Concretely: thread `repository_owner` (or the resolved `GithubApp#organization`) into `Handler.call`/`Handler#initialize`, and add a guard in `Handler#stacks` and in `MembershipHandler#find_or_create_team!`/`#process` that rejects payloads whose internal `repository.owner.login`/`organization.login` disagrees with the organization that authenticated the request.

## Proof of Concept
Given a multi-org Shipit config like `test/dummy/config/secrets_double_github_app.yml` (OrgOne, OrgTwo each with distinct `webhook_secret`), an attacker who administers OrgOne's GitHub App:

1. Builds a `membership` event JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "OrgTwo Admins", "slug": "admins", "url": "..." },
  "organization": { "login": "OrgTwo" },
  "member": { "login": "attacker-controlled-user" }
}
```
2. Computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgOne's webhook_secret)>` — a secret the attacker legitimately knows for their own org.
3. Sends the request to `/webhooks` with `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('organization','login')` → `"OrgTwo"`... 

Note: as written, `repository_owner` would resolve to `"OrgTwo"` in this exact payload (since there's no `repository` key), so the simplest exploit variant is: attacker crafts the body so that the **verification-selecting field** matches an org whose secret they control while a **different field consumed later by the same handler** (e.g., embedding both an `organization.login` used only superficially and relying on `Team.find_or_create_by!(github_id:)` keyed by attacker-chosen `team.id`, which is never cross-checked against the signing org at all) still lets them create/join a team object with a `handle` that happens to collide with `Shipit.github_teams`. This confirms the core root cause — `repository_owner`/org selection for signature verification and the organization/team fields consumed by `MembershipHandler` are two independent, non-cross-validated reads of the same untrusted body — [2](#0-1) [13](#0-12) , even though a fully weaponized end-to-end PoC would need to be validated against the exact org/team ID collision constraints in a live multi-org configuration.

```ruby
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String

            requires :login, String

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else

          end
        end

        private

          Team.find_or_create_by!(github_id: params.team.id) do |team|

          end
        end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
