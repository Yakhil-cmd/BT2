### Title
Oracle timestamp monotonicity check allows any caller to DoS another user's in-band price-fed liquidation/borrow/collateral transaction - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` lets any caller attach up to 3 Pyth VAA price updates (`price-feeds` parameter) to `borrow`, `collateral-add`, `collateral-remove`, and `liquidate` for atomic price refresh. Each update is validated in `price-resolve` via `oracle-timestamp-fresh`, which requires the new feed's timestamp to be `>= ` the timestamp already recorded in the shared `last-update` map for that `{type, ident}` key. Because `last-update` is global, shared state, any unrelated user can post a fresher (but still valid) Pyth update immediately before a victim's pending transaction lands, causing the victim's own (slightly older, still-fresh) pre-fetched VAA to fail the `(>= ts prev)` check and revert the entire operation with `ERR-ORACLE-INVARIANT`.

### Finding Description
`price-resolve` enforces freshness on every price feed used by the market: [1](#0-0) 

The freshness predicate requires the new timestamp to be monotonically non-decreasing relative to the value cached in the `last-update` map: [2](#0-1) 

`last-update` is a single shared map keyed only by `{type, ident}` (the asset/oracle identifier), not by caller or transaction: [3](#0-2) 

Any of `borrow`, `collateral-add`, `collateral-remove`, and `liquidate` accept an optional `price-feeds` list and call `write-feeds`/`price-resolve` on the caller's behalf before doing the health/liquidation math: [4](#0-3) [5](#0-4) 

Attack: PartyA (attacker, e.g. the borrower about to be liquidated) fetches the newest available Pyth Hermes VAA for the relevant feed (Pyth updates roughly every ~400ms and Hermes VAAs are freely obtainable by anyone) and submits any cheap operation (even a `borrow`/`collateral-add` with `price-feeds` set) to advance `last-update[{type,ident}]` to a very recent timestamp, right before PartyB's (the liquidator's, victim's) transaction — which was built moments earlier with its own valid (but now relatively "older") VAA — lands in the same block or the next. When PartyB's transaction executes, `oracle-timestamp-fresh` fails the `(>= ts prev)` check since PartyB's `ts` is now less than the attacker-bumped `prev`, so the whole `liquidate` (or `borrow`/`collateral-*`) call reverts with `ERR-ORACLE-INVARIANT`, even though PartyB's price data was well within `max-staleness` and perfectly legitimate. The attacker can repeat this every block by continuously re-fetching and posting the very latest VAA, perpetually starving the victim's pending transaction — structurally identical to the Symm IO `settleUpnl` nonce-DOS: a piece of shared, monotonically-advancing state (there: `partyBNonces`, here: `last-update`) is legitimately advanced by one unprivileged party's own unrelated action, which invalidates another unprivileged party's already-signed/fetched payload and forces a revert.

### Impact Explanation
The primary victim is a liquidator attempting to liquidate an unhealthy position of the borrower who is the attacker (or an accomplice acting on the borrower's behalf). By perpetually reverting `liquidate` calls that carry the borrower's/collateral's price feed, the borrower can stall liquidation of their own unhealthy position while the market continues to move against the collateral, letting bad debt accumulate. This is a temporary freezing of the liquidation mechanism for a specific position and, if sustained through further price deterioration, risks accruing unrecoverable bad debt (protocol insolvency) since Zest v2's liquidation path directly depends on this same freshness check for `liquidate`. It also DoSes ordinary users' `borrow`/`collateral-add`/`collateral-remove` calls that rely on in-band price refresh, causing repeated wasted gas and blocked access to the shared price-update mechanism (temporary freezing of a shared resource) whenever any user's operation depends on their own pre-fetched VAA for a feed another party can grief.

### Likelihood Explanation
The Pyth Hermes VAA for any feed is public and free to fetch by anyone, and any of `borrow`, `collateral-add`, `collateral-remove` can be called by any account with the `price-feeds` param populated at negligible cost (e.g., depositing/withdrawing a minimal amount), so mounting this griefing requires no special privilege — only monitoring the mempool/target liquidation and repeatedly submitting the newest VAA. A borrower with a large unhealthy position has strong economic incentive to do this to delay their own liquidation.

### Recommendation
Do not make oracle freshness validation depend on global, caller-agnostic monotonic state that an unrelated party can advance to invalidate someone else's still-valid data. Either (a) drop the cross-call monotonicity requirement and rely solely on `max-staleness` (absolute freshness) per call, or (b) scope any "must be newer than" comparison to the caller's own prior submissions rather than a globally shared `last-update` entry, or (c) allow the caller to atomically retry with the on-chain freshest price if their own submitted VAA is rejected as stale-relative, rather than reverting the whole transaction.

### Proof of Concept
1. Borrower B has a position nearing the partial-liquidation LTV threshold on asset X.
2. Liquidator L observes this, fetches the latest Pyth VAA for X (timestamp T0) and submits `liquidate(...)` with `price-feeds: [VAA_T0]`.
3. Before L's transaction is included, B (or an accomplice) fetches an even newer VAA for X (timestamp T1 > T0) and submits a cheap `collateral-add`/`borrow` call with `price-feeds: [VAA_T1]`, which updates `last-update[{type: PYTH, ident: X}]` to T1 via `map-set last-update key timestamp` in `price-resolve` (`mainnet/contracts/market/v0-4-market.clar:391-393`).
4. L's `liquidate` transaction then calls `price-resolve` with `VAA_T0`; `oracle-timestamp-fresh` evaluates `(>= T0 T1)` → false, so `ERR-ORACLE-INVARIANT` is asserted and the entire `liquidate` call reverts (`mainnet/contracts/market/v0-4-market.clar:386-388`), despite `VAA_T0` being perfectly fresh relative to `max-staleness`.
5. B repeats step 3 on every subsequent block/attempt, indefinitely delaying liquidation of their own unhealthy position.

```text
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
