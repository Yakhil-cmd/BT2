This confirms the design: the webhook secret is configured **per GitHub organization** (`config/secrets.yml`'s `github.<org>` block, loaded into `GitHubApp` at [1](#0-0) ), and `Shipit::WebhooksController` looks up which organization's secret to verify against using only the `repository.owner.login` (or `organization.login`) field of the *attacker-controlled JSON body*, not any authenticated/trusted source: [2](#0-1) . Meanwhile the event handlers that act on the payload (e.g. `PushHandler`, via `Handler#repository_name`) resolve the target `Stack`/`Repository` using a **different** field, `repository.full_name` [3](#0-2) , and `StatusHandler` doesn't check the repository at all, matching purely by commit `sha` globally: [4](#0-3) .

### Title
Webhook signature verified against `repository.owner.login` while handlers act on unrelated `repository.full_name` / global `sha` fields, allowing cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports hosting multiple GitHub organizations, each with its own independently configured `webhook_secret` (`lib/shipit/github_app.rb`). The `WebhooksController#verify_signature` selects which organization's secret to validate the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the unauthenticated JSON body of the incoming request. Once the HMAC check passes, the *entire* raw JSON body — including fields never covered by that check's selection logic — is handed to the registered handlers, which use a different field (`repository.full_name`) or no repository scoping at all (`StatusHandler`, keyed only by global `sha`) to decide what stack/commit to mutate.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the payload == organization owning the repository that is written to`. Concretely:

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and looks up `Shipit.github(organization: repository_owner)` to get the HMAC secret used for `verify_webhook_signature` [2](#0-1) .
- The HMAC covers the raw POST body (`request.raw_post`), so as long as the signature is valid for *some* value the attacker put in `repository.owner.login`, the whole body — including any other, unrelated `repository.full_name`, `sha`, or `ref` fields — is accepted verbatim.
- `Handler#repository_name` (used by `PushHandler` via `stacks`) resolves the target using `payload.dig('repository', 'full_name')`, a completely separate JSON field from the one used to select the verifying secret [3](#0-2) .
- `StatusHandler#process` does not consult the repository at all — it updates `Commit.where(sha: params.sha)` for any commit in the system matching that SHA, regardless of which repository/organization it belongs to [4](#0-3) .

Because `Shipit.github(organization:)` secrets are scoped per **organization**, not per **repository**, anyone able to produce a validly-signed payload for organization A's webhook (e.g. because they administer a webhook on any single repository within org A, which is normal, low-privilege delegated GitHub access unrelated to any other org A repo or to org B at all) can set `repository.owner.login` to `"A"` (so the correct/known secret is used to sign/verify) while setting `repository.full_name` to `"A/other-repo"` or, for status events, simply supplying any `sha` value with no owner/full_name constraint whatsoever. The handler then mutates state for a stack/commit the forger has no relationship to.

### Impact Explanation
This breaks the equality "the org that authenticated the webhook == the repository the webhook is permitted to affect." For `status` events specifically, an attacker with write access to a webhook on *any* repository configured under a given GitHub App/organization can forge commit statuses (`Commit#create_status_from_github!`) for *any* commit across *any* stack tracked by Shipit, independent of repository — this can flip CI gating used to permit deploys, potentially leading to an unauthorized deploy being triggered off code that never actually passed CI. This aligns with the "unauthorized deploy" high/critical impact class.

### Likelihood Explanation
Exploitability requires only the ability to produce one validly-signed webhook body for the target GitHub App/organization (e.g. control of a webhook trigger on a single repository under that org, or knowledge of the org's shared `webhook_secret`, which by design in `docs/setup.md`/`config/secrets.development.shopify.yml` is shared for *all* repositories of that org, not per-repo) — a lower bar than repository write access on the *specific* repository/commit being forged.

### Recommendation
Cross-check that the repository/organization used to select the verifying webhook secret is the same repository/organization referenced by the payload fields actually consumed by handlers (`repository.full_name`, and any `sha`/`ref` fields), and have `StatusHandler` (and any other handler) scope its `Commit`/`Stack` lookups to the repository named in the verified payload rather than matching purely by `sha` globally.

### Proof of Concept
1. Shipit is configured with two GitHub Apps in `config/secrets.yml`: `OrgA` (whose webhook secret the attacker knows/controls via a webhook they administer on `OrgA/some-repo`) and `OrgB`, which hosts a `production` stack tracking `OrgB/victim-repo`.
2. Attacker crafts a `status` webhook body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<sha of a commit currently in OrgB/victim-repo's stack awaiting CI>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker signs the raw body with `OrgA`'s known `webhook_secret` and sends it with header `X-Hub-Signature: sha1=<hmac>` to `/webhooks`.
4. `verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature [5](#0-4) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and marks the victim's commit status as `success`, even though the attacker never had legitimate access to `OrgB/victim-repo` [4](#0-3) .
