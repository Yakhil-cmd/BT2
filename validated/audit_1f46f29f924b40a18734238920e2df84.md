### Title
`Shipit::GitHubApp#verify_webhook_signature` fails open (returns `true`) when an org's `webhook_secret` is unset - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` starts with `return true unless webhook_secret`, so if a per-organization entry in `Shipit.secrets.github` omits `webhook_secret`, every webhook claimed to belong to that organization is treated as verified without ever inspecting the `X-Hub-Signature` header or hashing the request body. `WebhooksController#verify_signature` relies exclusively on this method, so this single missing config key turns into a full authentication bypass for that org's webhooks.

### Finding Description
The broken binding is: `verified == HMAC(webhook_secret, raw_post) matches X-Hub-Signature` should hold before any handler runs. In practice, when `@config[:webhook_secret]` is blank for an organization, `webhook_secret` (line 166, `attr_reader :webhook_secret`) is `nil`, and: [1](#0-0) 

`return true unless webhook_secret` short-circuits before `signature` or `message` are touched at all — the equality is never evaluated, yet `true` (verified) is returned.

The controller resolves the app per-request from attacker-influenced payload data (`repository.owner.login` / `organization.login`) and trusts the boolean unconditionally: [2](#0-1) [3](#0-2) 

`Shipit.github(organization: repository_owner)` looks up the org's config via `github_app_config`, and `GitHubApp.new` stores `@webhook_secret = @config[:webhook_secret].presence` [4](#0-3) . If that org's block in the multi-org secrets file simply omits `webhook_secret`, `@webhook_secret` is `nil`, and `verify_webhook_signature` becomes a no-op that always returns `true`, regardless of the `X-Hub-Signature` value the attacker sends (any value, or none).

`#create` then dispatches the fully attacker-controlled JSON body straight to real handlers with no other authentication check in between: [5](#0-4) 

None of the other guards mitigate this: `drop_unhandled_event` only checks whether a handler is registered for the event type, not authenticity; `check_if_ping` only special-cases the `ping` event. There is no other signature or provenance check anywhere in the webhook path.

### Impact Explanation
Any unauthenticated internet user can send `POST /webhooks` with `X-Github-Event: push` (or `pull_request`, `status`, `membership`, `check_suite`, etc.) and a JSON body whose `repository.owner.login`/`organization.login` names the misconfigured organization. Every registered `Shipit::Webhooks` handler for that event will execute against attacker-supplied data as if it came from GitHub — this can drive stack/commit/task state changes, membership/team updates, and CI status updates for every repository under that organization, with no possession of the real `webhook_secret`, GitHub App key, or any Shipit credential. This is repeatable indefinitely and scoped to every repository owned by the misconfigured org, matching the "authentication bypass (forged webhook accepted)" Critical category.

### Likelihood Explanation
Requires exactly the precondition the question specifies: an admin using Shipit's multi-org GitHub config, with one organization's entry lacking a `webhook_secret` key (while the top-level/default secret exists and is different, or is simply absent for that entry). This is plausible operator error — nothing in `lib/shipit/github_app.rb` or `lib/shipit.rb`'s `github_app_config`/`github` methods validates that `webhook_secret` is present per-organization, and no warning or fail-closed default exists. Once that misconfiguration exists, exploitation costs the attacker nothing beyond crafting an HTTP POST — no secrets, no session, no GitHub write access required.

### Recommendation
Change `verify_webhook_signature` to fail closed instead of fail open: if `webhook_secret` is blank for a configured (non-legacy) multi-org entry, reject the webhook (return `false`) rather than treating the request as verified. At minimum, log/raise a configuration error at startup or on first use so operators cannot silently ship an org config without `webhook_secret`, and require `webhook_secret` presence for all multi-org entries during `Shipit.github_app_config` resolution.

### Proof of Concept
```ruby
# test/unit/github_app_test.rb (conceptual addition)
test "#verify_webhook_signature returns true (fails open) when webhook_secret is not configured for an org" do
  app = GitHubApp.new('some-org', default_config.except(:webhook_secret))
  assert_equal true, app.verify_webhook_signature('sha1=deadbeef', '{"malicious":"payload"}')
  assert_equal true, app.verify_webhook_signature(nil, '{"malicious":"payload"}')
end
```
This demonstrates that with no `webhook_secret` configured for an org, `verify_webhook_signature` returns `true` for arbitrary or absent signatures, confirming the fail-open bypass reachable through `WebhooksController#verify_signature`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
