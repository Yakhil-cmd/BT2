### Title
Membership webhook processes team actions without verifying webhook signer owns the target team - cross-tenant team membership mutation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#process` resolves the target `Team` purely by `params.team.id` (GitHub's global team id) and never checks that the organization that signed the webhook actually owns that team. An attacker who controls any GitHub organization onboarded to Shipit can sign a `membership` webhook with `action: 'removed'`, set `team.id` to a victim team's `github_id`, and `member.login` to any operator's login, causing that operator's team membership (and therefore `Shipit.authorized?` status) to be revoked.

### Finding Description
The intended binding is: `organization that signed the request (verified via webhook_secret)` == `organization that owns the team whose membership is being mutated`. In code this should mean `repository_owner`/`params.organization.login` used in `WebhooksController#verify_signature` must equal the `organization` field of the `Team` row being modified in `MembershipHandler#process`.

`WebhooksController#verify_signature` derives the signing organization solely from the payload itself: [1](#0-0) 
For a `membership` event there is no `repository` key, so `repository_owner` falls back to `params.organization.login` - a value fully controlled by the attacker's own payload. `Shipit.github(organization: repository_owner)` then loads the attacker's own `GitHubApp` config (their real `webhook_secret`, since they own that org), and `verify_webhook_signature` succeeds because the attacker legitimately signs with their own secret: [2](#0-1) 

Once past signature verification, `MembershipHandler#process` calls `find_or_create_team!`, which looks up `Team` **only by `github_id`**, ignoring which organization is asserted in the current payload: [3](#0-2) 
Because `find_or_create_by!(github_id: params.team.id)` matches an existing row, the block (`team.organization = params.organization.login`) is never invoked, but critically, `process` also never re-validates `team.organization == params.organization.login` before performing the mutation. For `action == 'removed'`, `team.members.delete(member)` is executed unconditionally against whatever `Team` row matches that `github_id`: [4](#0-3) 

The GitHub team `id` (numeric github_id) is not a secret - it's discoverable via the GitHub API/UI - so an attacker only needs to know or guess the victim's team's numeric id and the target operator's GitHub login, both public information.

`User#authorized?` depends directly on team membership: [5](#0-4) 
so deleting the `Membership` row directly flips `authorized?` from `true` to `false` if that was the operator's qualifying team.

No existing guard prevents this: `verify_signature` only proves the payload's *claimed* organization possesses a valid secret - it never proves that claimed organization owns the `team.id` referenced inside the same payload. `find_or_create_team!` has no organization-scoping in its lookup. `drop_unhandled_event` and the `ExplicitParameters` schema only validate structural shape, not tenant ownership.

### Impact Explanation
A payload signed by attacker-controlled Org A mutates a `Team` record and `Membership` row that actually belongs to a completely unrelated Org B, revoking a legitimate operator's authorization state. This is a cross-tenant record mutation (`a payload for one repository/organization mutating another's team`), matching the Critical category. It's repeatable against any operator/team whose `github_id` and login the attacker can learn, and requires no privileges beyond owning any Shipit-onboarded org (a benign, low-bar precondition many multi-tenant Shipit deployments have).

### Likelihood Explanation
Preconditions: attacker must control at least one GitHub organization that has been onboarded to the Shipit instance (has a configured `webhook_secret`/`GitHubApp` entry) so that `Shipit.github(organization: attacker_org)` returns a valid app and `verify_webhook_signature` succeeds. This is explicitly called out as feasible in the audit's stated preconditions. No GitHub App private key, no `secret_key_base`, no victim org's `webhook_secret` is needed. The attacker needs only the victim's team `github_id` (public via GitHub API) and the operator's login (public). Cost is a single crafted HTTP POST to `/webhooks` with a valid HMAC computed from the attacker's own secret - fully repeatable and scriptable.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), validate that the payload's `params.organization.login` matches the `Team#organization` value of the record being looked up (for `find`, not just `create`), and reject/ignore the event if they diverge. Scope the `Team.find_or_create_by!` lookup by both `github_id` and `organization`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and if a team with that `github_id` already exists under a different organization, drop the event (log and no-op) rather than mutating it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, minitest)
test "removed action cannot revoke membership signed by an unrelated organization" do
  victim_team = shipit_teams(:shipit) # organization: 'shopify', github_id: 1, real Shipit.github_teams entry
  operator = shipit_users(:walrus)
  victim_team.add_member(operator)

  assert operator.authorized?  # baseline: true

  # Attacker signs this payload with THEIR OWN org's webhook_secret ('attacker-org'),
  # but names the victim's real team github_id and the operator's real login.
  payload = {
    'action' => 'removed',
    'team' => { 'id' => victim_team.github_id, 'name' => victim_team.name, 'slug' => victim_team.slug, 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => operator.login }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call

  operator.reload
  assert_not operator.authorized?  # BUG: flips to false due to cross-org mutation
end
```
This demonstrates `operator.authorized?` transitioning `true -> false` purely from a payload whose signing organization (`attacker-org`) never matched `victim_team.organization`, confirming the provenance binding is violated in `MembershipHandler#process`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
