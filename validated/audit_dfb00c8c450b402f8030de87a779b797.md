### Title
Cross-tenant status write via `Shipit::Webhooks::Handlers::StatusHandler#process` missing repository/stack scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no scoping by `repository_name`/stack, unlike `CheckSuiteHandler#process` which scopes lookups through `stacks.where(branch: params.check_suite.head_branch)` (itself derived from `Repository.from_github_repo_name(repository_name)` in `Handler#stacks`). Because a git SHA string is attacker-chosen text and not validated as globally unique to one repository within Shipit's schema, an attacker who owns Repo A and knows (or predicts) a SHA that also exists as a commit belonging to victim Stack B can send a `status` webhook for Repo A and have `create_status_from_github!` applied to Repo B's commit.

### Finding Description
The claimed binding is: `repository_name (from verified payload) == Stack#repository for every mutation performed by #process`.

- For `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-16`): `stacks.where(branch: ...)` calls `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which resolves `Repository.from_github_repo_name(repository_name)` from the payload's `repository.full_name`, then restricts to that repository's own stacks. The binding **holds**: every stack touched belongs to the repository named in the payload.
- For `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`): `Commit.where(sha: params.sha)` queries the `Commit` table directly with no call to `stacks`, no reference to `repository_name`, and no `payload.dig('repository', ...)` check at all. The binding **breaks**: any commit row anywhere in the database whose `sha` column matches the attacker-supplied string is mutated via `commit.create_status_from_github!(params)`, regardless of which repository/stack it belongs to.

Root cause: the `params` schema for `StatusHandler` (`requires :sha, :state`, etc.) never binds `repository.full_name` to the query, and `#process` never calls `Handler#stacks`/`Repository.from_github_repo_name` the way `CheckSuiteHandler` does. `Commit#sha` has no uniqueness or format validation enforced in the model that would prevent two different stacks (belonging to two different repositories) from having a `Commit` row with an identical `sha` value — SHAs are attacker-controlled/predictable strings, and nothing in `Commit`/`Stack` model validations (per repo grep, no `validates ... sha` found) prevents collision across stacks.

Attacker exploit flow:
1. Attacker owns Repo A, registered as a Shipit stack (Stack A).
2. Attacker discovers or engineers a commit SHA value that is also present as a `Commit` row for victim Stack B (e.g., by pushing/mirroring the exact same commit content to their own fork, or if Shipit's commit-sync creates rows from git history shared between forks, a common upstream commit SHA will exist identically in both Stack A's and Stack B's `commits` table — this is common practice: forks initially share commit history/SHAs with upstream).
3. Attacker sends a `status` webhook (`POST /webhooks`) with a valid signature for Repo A (attacker's own repo, which they control the GitHub webhook config for) containing `sha = <shared sha>`, `state`, `context`, `target_url`, `description` of their choosing.
4. `StatusHandler#process` finds **all** `Commit` rows with that sha — including Stack B's row — and calls `create_status_from_github!(params)` on each, writing attacker-controlled status/state/description/target_url onto Stack B's commit despite the webhook never being scoped to Stack B's repository.

Why existing guards don't stop this: `verify_signature`/webhook HMAC validation only proves the payload came from the repository whose secret signed it (Repo A, attacker-controlled) — it does not prove or enforce that the `repository.full_name` in the payload matches the commits being mutated. `ExplicitParameters` schema for `StatusHandler` never declares/requires `repository`, so it's simply not part of the enforced contract, and `#process` never consults `payload.dig('repository', 'full_name')`. `drop_unhandled_event`, `force_github_authentication`, `User#authorized?`, `require_permission!` are irrelevant to unauthenticated webhook processing paths — none of these guard the sha-to-repository binding either.

### Impact Explanation
An attacker with control over any single, low-privilege GitHub repository (their own fork) can write arbitrary commit status data (`state`, `context`, `description`, `target_url`) onto commits belonging to unrelated victim stacks/repositories, as long as a shared SHA exists between the two. Since commit statuses drive Shipit's merge/deploy readiness checks (green/red CI gating), this can be used to mark a victim's commit as `"success"` for a check the attacker fabricates, or as `"failure"` to block/deny a victim's deploy — a cross-tenant integrity/availability impact on deploy gating. This matches "a payload for one repository mutating another's stack, commit, task or team" — Critical category. The write is repeatable against any commit sha collision the attacker can arrange, across arbitrarily many target stacks.

### Likelihood Explanation
Preconditions: attacker needs a stack/repository they control that shares a commit SHA with the victim's monitored repository's commit history. This is realistic for forked repositories that share upstream commit ancestry (very common on GitHub, especially before divergence), or for any scenario where Shipit tracks commits by SHA without per-repo namespacing and the attacker can push the exact same tree/commit object to their own repo. No Shipit credentials, session, API token, or GitHub secrets are required — only a normal GitHub webhook signed with the attacker's own repository's webhook secret, which the attacker controls for their own repo. Attacker cost is low: create/own a fork, arrange a shared SHA (trivial for forks not yet diverged, or by cherry-picking the exact victim commit into their own repo history), then POST the crafted `status` webhook.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler#process` does: resolve the repository via `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`) and restrict the `Commit` lookup to commits belonging to that repository's stacks, e.g. `stacks.flat_map(&:commits).each { |c| c.commits.where(sha: params.sha)... }` or equivalent join, rather than an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (no live GitHub, using `Shipit::Webhooks::Handlers::StatusHandler.call` / `CheckSuiteHandler.call` directly):

```ruby
test "StatusHandler mutates a commit belonging to a different repository/stack (cross-tenant write)" do
  stack_a = shipit_stacks(:shipit) # attacker-owned stack, repo "shipit/shipit"
  stack_b = create_stack(repository_owner: 'victim', repository_name: 'secret-app') # victim stack

  shared_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:bob))
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'y', author: shipit_users(:bob))

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'repository' => { 'full_name' => stack_a.repository.full_name }, # attacker's own repo, correctly signed
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_b.reload
  assert commit_b.statuses.exists?(state: 'failure'),
    "victim stack_b's commit was mutated by a status webhook scoped to attacker's repository"
end

test "CheckSuiteHandler does not mutate a stack belonging to a different repository (no cross-tenant write)" do
  stack_a = shipit_stacks(:shipit)
  stack_b = create_stack(repository_owner: 'victim', repository_name: 'secret-app', branch: 'main')

  shared_sha = 'b' * 40
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'y', author: shipit_users(:bob))
  commit_b.expects(:schedule_refresh_check_runs!).never

  payload = {
    'check_suite' => { 'head_sha' => shared_sha, 'head_branch' => 'main' },
    'repository' => { 'full_name' => stack_a.repository.full_name }, # attacker's own repo
  }

  Shipit::Webhooks::Handlers::CheckSuiteHandler.call(payload)
end
```

The first test demonstrates `commit_b` (belonging to victim repo/stack `stack_b`) receiving a status write from a webhook payload naming only the attacker's repository — proving the missing guard in `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). The second test proves `CheckSuiteHandler#process` correctly refuses to touch `stack_b` because `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) scopes by the payload's `repository.full_name`. # frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class Handler
        class << self
          attr_reader :param_parser

          def params(&block)
            @param_parser = ExplicitParameters::Parameters.define(&block)
          end
        end

        def self.call(params)
          new(params).process
        end

        attr_reader :params, :payload

        def initialize(payload)
          @payload = payload
          @params = self.class.param_parser.parse!(payload)
        end

        def process
          raise NotImplementedError
        end

        private

        def stacks
          @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
        end

        def repository_name
          payload.dig('repository', 'full_name')
        end
      end
    end
  end
end
