### Title
Webhook signature check is skipped whenever `webhook_secret` is unset for an organization, letting an unauthenticated caller forge push/status/check_suite events against any repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
### Finding Description
The `[M-06]` report is about a value read from an unsigned/unvalidated context (`timeSinceStart`) being trusted by code that assumes it was constrained, causing the "authorized" computation to diverge from what was actually verified. The structural analog in this engine is the relationship between what `WebhooksController#verify_signature` actually authenticates and what the webhook `Handler` subclasses subsequently act on.

`verify_signature` resolves a `GitHubApp` for the organization named in the payload and calls `verify_webhook_signature`: [1](#0-0) 

The actual comparison lives in `GitHubApp#verify_webhook_signature`: [2](#0-1) 

Line 77, `return true unless webhook_secret`, means that **if the organization's `webhook_secret` is not configured, every payload is accepted as verified, regardless of the `X-Hub-Signature` header or its absence.** The setup documentation explicitly marks the webhook secret as optional: [3](#0-2) 
and the secrets templates ship with it defaulted to `nil`: [4](#0-3) 

Once "verified" (trivially, because no secret exists), `WebhooksController#create` dispatches the raw, attacker-supplied JSON to the registered handlers: [5](#0-4) 

Handlers resolve which `Stack`(s) to act on purely from the payload's own `repository.full_name` field, with no cross-check against the organization that was nominally "authenticated" in `verify_signature` (which itself used `repository.owner.login`): [6](#0-5) 

This is the broken binding: **"organization that authenticated" (`repository.owner.login`, gated by a possibly-absent `webhook_secret`) ≠ "repository that is written"** (`repository.full_name`, used to look up and mutate `Stack` state). Because both fields are read from the same unauthenticated JSON body when no secret is configured, an attacker fully controls both, and can point `full_name` at a stack in an organization that *does* have a strong secret configured, while `owner.login` points at any org (even a nonexistent-but-configured, secret-less one) to sail through `verify_signature`.

Concretely, `StatusHandler` and `CheckSuiteHandler` write directly to `Commit`/`CheckRun` state sourced from the payload without re-fetching from GitHub's API to confirm authenticity, unlike `PushHandler`, which at least triggers a re-sync via `GithubSyncJob` against the real GitHub API. That makes the status/check-suite path the most impactful concrete exploitation: an attacker can inject fabricated CI status / check-run results for a commit, which can flip `ci.require` gating and merge-queue trust decisions in `shipit.yml`-driven flows.

### Impact Explanation
This crosses the "unauthorized deploy or merge" bar in the rules: forged CI-status/check-suite webhooks let an unprivileged network caller manipulate commit status/check state that Shipit's merge queue and deploy safety checks (`ci.require`, `merge_queue_enabled`) rely on, without possessing any of the excluded credentials (no `ApiClient` token, no `api_clients_secret`, no GitHub App private key) - the only requirement is that the target Shipit instance has at least one configured GitHub organization with `webhook_secret` left unset, a state the documentation itself presents as a normal, supported configuration. This can lead to an unauthorized merge/ship decision being made on falsified CI evidence.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: the webhook secret is explicitly optional in the setup docs and defaults to `nil`/blank in the example secrets files, so it is plausible that some configured organizations in a multi-org Shipit instance never had it set. No credential, session, or write access is required to exploit this - just an HTTP POST to the publicly documented `/webhooks` endpoint, which the docs instruct admins to expose (`Webhook URL: <homepage>/webhooks`).

### Recommendation
- Require `webhook_secret` to be present for every configured organization at boot (fail closed instead of `return true unless webhook_secret`).
- Cross-validate that `repository.owner.login`/`organization.login` (used to select the verifying `GitHubApp`) matches the owner embedded in `repository.full_name` (used by `Handler#stacks`) before dispatching to handlers.
- For `StatusHandler`/`CheckSuiteHandler`, consider re-validating status/check state against the GitHub API rather than trusting the webhook payload verbatim, mirroring what `PushHandler` already does via `GithubSyncJob`.

### Proof of Concept
1. Configure Shipit with multi-org support (`config/secrets.yml` → `github: { orgA: {...no webhook_secret...}, orgB: { webhook_secret: "strong-secret" } }`), with a `Stack` under `orgB/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: status` and no (or garbage) `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{ "name": "main" }]
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler` (looked up via `repository.full_name = "orgB/victim-repo"`) writes a fabricated successful `Status` for the victim commit, even though the attacker never possessed `orgB`'s webhook secret. [7](#0-6) [2](#0-1) [6](#0-5)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

      Rails.logger.info([

        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
