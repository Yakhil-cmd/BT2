### Title
Webhook signature verification is keyed by an attacker-controlled `repository.owner.login` field while event processing is keyed by an unrelated `repository.full_name` field, allowing forged webhooks against any stack when any configured GitHub organization has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification from an unauthenticated payload field (`repository.owner.login`), then hands the *entire unauthenticated payload* to handlers that resolve the target stack from a completely different, also-unauthenticated field (`repository.full_name`). If any configured organization has no `webhook_secret` set (an explicitly documented, optional configuration), `verify_webhook_signature` unconditionally returns `true` for a payload claiming that organization, letting an attacker inject a payload whose `full_name` points at an entirely different, secured organization's stack.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the secret) to verify against using `repository_owner`, which is read straight out of the untrusted request body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` deliberately treats an unset secret as "always verified": [3](#0-2) 

This "optional" webhook secret is an explicitly supported configuration, both in the setup docs and in the multi-organization example fixtures (`webhook_secret: # nil`): [4](#0-3) 

After the (possibly no-op) signature check, the controller passes the same raw, unauthenticated JSON body to the event handlers: [5](#0-4) 

Every handler resolves its target `Stack`/`Repository`/`Commit` purely from `payload.dig('repository', 'full_name')` (or `sha`, `branch`, etc.), with no cross-check against `repository_owner`, the field that determined which secret was used to "verify" the request: [6](#0-5) [7](#0-6) [8](#0-7) 

This reproduces the reported bug class exactly: a field the code trusts and acts on (`full_name`, driving which stack/commit is mutated) is never covered by the check that is supposed to gate the request (the signature verified against the secret picked from `owner.login`). The binding that should hold is:

`organization authenticated (repository_owner used to pick the secret) == organization/repository actually written to (repository.full_name used by handlers)`

Before the attacker's request: for a legitimately signed webhook, both fields come from the same GitHub delivery, so they always match and the equality holds trivially.

After the attacker's request: an attacker crafts a payload where `repository.owner.login` = an organization configured in Shipit with no `webhook_secret` (verification trivially passes with no HMAC required), but `repository.full_name` = a fully-secured stack/repository belonging to a different, security-sensitive organization. The equality breaks: the organization that "authenticated" (vacuously, via `return true unless webhook_secret`) is not the organization whose repository is actually acted upon.

### Impact Explanation
With this desynchronization, an unprivileged external attacker (anyone able to POST to `/webhooks` with correct `X-Github-Event` header) can forge events against any tracked stack in a multi-org Shipit deployment as long as at least one configured organization omits `webhook_secret`:
- `push` events can enqueue `GithubSyncJob` with an attacker-chosen `expected_head_sha`, influencing what Shipit believes is the head of a monitored branch.
- `status` events can forge arbitrary commit statuses for real commits via `create_status_from_github!`, which can flip deployability gating used to authorize deploys.
- `membership` events can create/delete `Team`/`Membership` records tied to `Shipit.github_teams`, escalating authorization state used for access control.

These land squarely in the defined High/Critical impact classes ("escalation into `Shipit.github_teams` authorization", "unauthorized deploy" via forged deployable status). I was not able to fully trace, within remaining tool budget, the exact downstream authorization check in `Commit#deployable?`/`Stack` that consumes forged statuses to confirm an end-to-end unauthorized deploy without further verification; this specific chain (status forgery → deploy authorization) should be validated further, though the write primitive itself (forging state for an unrelated org's stack via a no-secret org) is clearly established from the code shown above.

### Likelihood Explanation
This requires no credentials beyond knowledge that a Shipit instance is running in multi-organization mode (documented feature) and that at least one configured organization has no `webhook_secret` — a state the project's own documentation and test fixtures (`test/dummy/config/secrets_double_github_app.yml`, `OrgTwo: webhook_secret: # nil`) present as a normal, supported configuration, not a misconfiguration. No signature knowledge, no repository access, and no session are required; only the public `/webhooks` endpoint (`config/routes.rb`) is used.

### Recommendation
Bind verification to the actual entity being acted upon: either (a) require every configured organization to have a mandatory `webhook_secret` and refuse to boot/serve webhooks otherwise, or (b) after selecting the `GitHubApp` via `repository_owner` and successfully verifying, re-validate that the resolved `Repository`/`Stack` for `repository.full_name` actually belongs to that same `repository_owner` before invoking handlers, rejecting the request otherwise.

### Proof of Concept
1. Configure Shipit with two organizations: `SecureOrg` (has `webhook_secret` set, owns stack `secureorg/prod`) and `OpenOrg` (no `webhook_secret`), as permitted by `docs/setup.md` and demonstrated in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OpenOrg" }, "full_name": "secureorg/prod" },
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>"
}
```
3. `WebhooksController#repository_owner` returns `"OpenOrg"`; `Shipit.github(organization: "OpenOrg").verify_webhook_signature(...)` returns `true` unconditionally because `webhook_secret` is blank (`lib/shipit/github_app.rb` lines 76-83) — no valid `X-Hub-Signature` is required at all.
4. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `stacks` lookup uses only `payload.dig('repository','full_name')` = `"secureorg/prod"` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38), enqueuing `GithubSyncJob` for `SecureOrg`'s stack despite the request never being verified against `SecureOrg`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
