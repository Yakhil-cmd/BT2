### Title
Cross-organization team hijack via unauthenticated `membership` webhook when any configured GitHub organization has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` derives the organization used to look up the HMAC secret from `params.dig('organization', 'login')` when no `repository` key is present, which is exactly the shape of GitHub's `membership` events [1](#0-0) . `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that organization's config has no `webhook_secret` set [2](#0-1) . `MembershipHandler` then mutates `Team` state keyed purely by the numeric `github_id` from the payload, with no re-validation that the "verified" organization actually owns that team [3](#0-2) .

### Finding Description
The binding this code implicitly relies on is: **the organization whose secret (or lack thereof) gated the HMAC check == the organization that owns the `Team` record being mutated.** This binding only holds when `Team.find_or_create_by!(github_id: params.team.id)` actually creates a new row (the `organization` field is only set inside the creation block) [4](#0-3) . Once a `Team` with a given `github_id` already exists (created earlier by its legitimate, secret-protected organization), the binding is silently dropped: any subsequent lookup by that same `github_id` succeeds regardless of which organization's payload triggered it.

Exploit path:
1. Shipit is configured for multiple GitHub organizations (the `github_organizations`/`github_app_config` multi-tenant schema in `lib/shipit.rb` lines 190-200), and at least one configured organization, e.g. `unsecured-org`, has no `webhook_secret` set in its config entry.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: membership` and body:
   ```json
   {"action":"added","organization":{"login":"unsecured-org"},"team":{"id":<privileged_team_github_id>,"name":"x","slug":"x","url":"x"},"member":{"login":"attacker"}}
   ```
3. `repository_owner` resolves to `"unsecured-org"` (no `repository` key in payload) [1](#0-0) .
4. `Shipit.github(organization: "unsecured-org")` loads that org's config, and `verify_webhook_signature` returns `true` because `webhook_secret` is blank — no HMAC is ever checked [5](#0-4) .
5. `MembershipHandler#process` looks up the existing `Team` by `github_id` (which the attacker set to match a real, privileged team originally created under a different, secret-protected organization) and calls `team.add_member(User.find_or_create_by_login!("attacker"))` [6](#0-5) .
6. The attacker's user is now a member of a team that may back `Shipit.github_teams` authorization [7](#0-6) .

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is handled, not the payload's authenticity [8](#0-7) ; `verify_signature` is the only authenticity guard and is vacuous by design when `webhook_secret` is absent; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not organizational ownership [9](#0-8) .

### Impact Explanation
An unprivileged internet attacker can add themselves (or any GitHub login) as a member of an arbitrary `Team` record by `github_id`, including teams belonging to a fully secret-protected organization, as long as any other organization configured on the same Shipit instance omits its `webhook_secret`. Because `Shipit.github_teams` is used for authorization (`lib/shipit.rb` lines 256-258), this is an escalation into that authorization mechanism — matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable: each POST is a fresh, stateless HMAC-bypassed request, and it works against any team whose numeric GitHub team ID the attacker can learn.

### Likelihood Explanation
This requires a specific multi-tenant configuration precondition: the Shipit instance must be configured with more than one GitHub organization (the `github_default_organization` non-nil branch in `lib/shipit.rb`), and at least one of those organizations' config entries must omit `webhook_secret`. If Shipit is run with a single global github config (`secrets.github` without per-org keys) or if every configured organization has a `webhook_secret` set, `repository_owner`/`organization` lookup will either always verify correctly or the unmatched org will 422 via `GithubOrganizationUnknown`, and this path does not open up. The attacker also needs to learn the target team's numeric GitHub `id`, which is not secret but is not trivially public either (visible to org members, or observable from legitimately-received webhook payloads/logs). Given these two preconditions (operator misconfiguration + known team id), attacker cost is low (a single unauthenticated HTTP POST) and the action is fully repeatable.

### Recommendation
- Never treat "no `webhook_secret`" as an implicit trust signal for privileged handlers like `MembershipHandler`, `TeamHandler`, etc. Require a `webhook_secret` to be configured for every organization that can create/modify `Team` records, or reject webhooks entirely for orgs without a secret configured, rather than defaulting to trust in `GitHubApp#verify_webhook_signature`.
- In `MembershipHandler#find_or_create_team!`, verify that an existing `Team#organization` matches `params.organization.login` before allowing membership mutation, rejecting mismatches instead of silently trusting the `github_id` alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test "membership event for an org without webhook_secret can hijack an existing privileged team" do
  # Arrange: privileged team created earlier under a *secured* org
  privileged_team = shipit_teams(:secured_privileged_team) # github_id: 4242, organization: "secured-org"

  # Configure a second org with no webhook_secret
  Shipit.stubs(:github_app_config).with('unsecured-org').returns({app_id: 1, installation_id: 1})

  post shipit.webhooks_path,
    params: {
      action: 'added',
      organization: { login: 'unsecured-org' },
      team: { id: privileged_team.github_id, name: 'x', slug: 'x', url: 'x' },
      member: { login: 'attacker' }
    }.to_json,
    headers: { 'X-Github-Event' => 'membership', 'Content-Type' => 'application/json' }
    # deliberately NO X-Hub-Signature header

  assert_response :ok
  privileged_team.reload
  assert_includes privileged_team.members.map(&:login), 'attacker'
end
```
This test demonstrates that with no valid HMAC signature supplied and no `webhook_secret` configured for the named org, an attacker-controlled login is added as a member of a `Team` originally scoped to a different, secured organization.
