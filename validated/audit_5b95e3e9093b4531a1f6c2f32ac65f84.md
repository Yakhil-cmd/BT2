I found the analog. `BridgeTransferERC721.sol` uses bare `transferFrom` in two places while the ERC20 counterpart correctly uses `safeTransfer`/`safeTransferFrom`. The most impactful instance is in `handleERC721Transfer`.

### Title
ERC721 Bridge Uses `transferFrom` Instead of `safeTransferFrom`, Permanently Locking Bridged NFTs in Non-Receiver Contracts — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer()` delivers bridged ERC721 tokens to the recipient using bare `IERC721.transferFrom()` instead of `safeTransferFrom()`. If the recipient `_to` is a smart contract that does not implement `IERC721Receiver`, the token is silently transferred into an address that can never move it, permanently locking the bridged NFT. The bridge nonce and state are already finalized before the transfer, so the loss is irrecoverable.

---

### Finding Description

`BridgeTransferERC721.sol` line 69 executes:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

The ERC721 standard defines `safeTransferFrom` specifically to prevent this: it calls `onERC721Received` on the recipient if it is a contract, and reverts if the recipient does not return the correct magic value. Plain `transferFrom` skips this check entirely.

By contrast, the ERC20 bridge sibling contract correctly uses `SafeERC20`:

```solidity
using SafeERC20 for IERC20;
...
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [2](#0-1) [3](#0-2) 

The same unsafe pattern also appears on the deposit side:

```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
``` [4](#0-3) 

The OpenZeppelin ERC721 `safeTransferFrom` that is already available in the repo performs the receiver check: [5](#0-4) 

---

### Impact Explanation

When `handleERC721Transfer` is called by operators and `_to` is a contract without `IERC721Receiver`:

1. The bridge nonce is updated and the `HandleValueTransfer` event is emitted — the bridge considers the transfer complete and will never retry it.
2. `transferFrom` succeeds (ERC721 does not revert on non-receiver contracts), moving the token into `_to`.
3. The token is permanently locked: `_to` cannot call `safeTransferFrom` or `transferFrom` on it because it has no such logic.

The result is **permanent, irrecoverable loss of the bridged ERC721 asset**. The user's NFT is gone from the source chain (burned or locked) and the destination token is trapped.

---

### Likelihood Explanation

Any user whose destination address is a multisig wallet, a DeFi vault, a DAO treasury, or any other smart contract that does not explicitly implement `IERC721Receiver` (which is common — many contracts implement ERC20 handling but not ERC721) will trigger this path. No attacker action is required; a normal cross-chain NFT transfer to a contract address is sufficient.

---

### Recommendation

Replace both `transferFrom` calls in `BridgeTransferERC721.sol` with `safeTransferFrom`:

**Line 69** (`handleERC721Transfer`, delivery path):
```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

**Line 129** (`requestERC721Transfer`, deposit path):
```solidity
// Before
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(msg.sender, address(this), _tokenId);
```

The bridge contract must then implement `onERC721Received` (returning the correct selector) to accept the deposit-side `safeTransferFrom`. This is the same pattern used by the ERC20 bridge via `onERC20Received`. [6](#0-5) 

---

### Proof of Concept

1. User holds ERC721 token on the service chain and calls `requestERC721Transfer` (or `onERC721Received` via 1-step) to bridge it to a contract address `_to` on the parent chain.
2. Operators reach quorum and call `handleERC721Transfer(_requestTxHash, _from, _to, _tokenAddress, _tokenId, ...)`.
3. Inside `handleERC721Transfer`, after nonce update and event emission, the call `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` executes.
4. `_to` is a contract (e.g., a Gnosis Safe or a DAO treasury) that does not implement `IERC721Receiver`.
5. `transferFrom` succeeds silently — the token is now owned by `_to` but `_to` has no mechanism to move it.
6. The bridge's `lowerHandleNonce` advances past this nonce; the request is permanently marked handled.
7. The NFT is permanently locked. The source-chain token was already burned or locked in the source bridge. [7](#0-6)
