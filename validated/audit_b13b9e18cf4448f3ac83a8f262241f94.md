## Finding

### Title
Unbounded scan over `storage.assocUnstableMessages` in AA data-feed lookups enables a permissionless, cheap chain-wide DoS - (File: `data_feeds.js`)

### Summary
The reported bug class is an unbounded, per-block iteration over an attacker-growable, permissionlessly-created collection in an execution path that every node must run deterministically and that is not metered proportionally to the collection's size. The direct analog in `ocore` is the in-memory scan of `storage.assocUnstableMessages` performed by `dataFeeds.readDataFeedValue()` and `dataFeeds.dataFeedExists()` whenever an Autonomous Agent evaluates the `data_feed` / `in_data_feed` oscript operators. This scan is triggered on every AA trigger execution (which happens deterministically on every full node during main-chain stabilization, the closest ocore analog to a cosmos `BeginBlock`), and its cost grows linearly with the number of currently-unstable units carrying `data_feed`/`definition`/`system_vote`/`system_vote_count` messages anywhere in the DAG — a quantity any unprivileged unit poster can inflate arbitrarily by posting many low-cost units.

The equivalent `dataFeedExists()` bAA branch performs the identical full scan: [3](#0-2) 

Both loops iterate `for (var unit in storage.assocUnstableMessages)` — i.e. **every unit anywhere in the DAG that is not yet stable and carries a `data_feed`/`definition`/`system_vote`/`system_vote_count` message**, regardless of the oracle address or feed name being queried. `storage.assocUnstableMessages` is populated on every unit write: [4](#0-3) 

and entries are removed only once the corresponding unit's MCI becomes stable, inside `markMcIndexStable` → `saveUnstablePayloads`: [5](#0-4) 

There is no cap on how many such unstable units can accumulate, and the anti-spam formula metering (`MAX_OPS` / `MAX_COMPLEXITY`) charges a **fixed** op/complexity cost for the `data_feed`/`in_data_feed` operator regardless of how many unstable messages exist at evaluation time: [6](#0-5) 

So the static anti-spam budget (`MAX_OPS`, `MAX_COMPLEXITY`, `MAX_RESPONSES_PER_PRIMARY_TRIGGER`) that is supposed to bound AA execution cost does not scale with — and therefore does not protect against — the size of `storage.assocUnstableMessages`, exactly mirroring the audited bug where a fee-gated creation mechanism failed to scale with the size of an unboundedly-iterated collection.

An unprivileged attacker can:
1. Post large numbers of cheap units, each containing a minimal `data_feed` message (any oracle-format address works; the loop doesn't filter by address until deep inside the per-unit body), keeping them from stabilizing (e.g. by controlling their own witnessing/parent structure or simply outpacing stabilization under load).
2. Trigger (or wait for) any AA that reads a data feed via `data_feed[...]` / `in_data_feed[...]` — a very common oscript idiom for oracle price feeds.

Because AA trigger execution runs identically and deterministically on every full node as part of processing stabilized MCIs (`stabilizeMci` → `aa_composer.handleAATriggers`), every node incurs the same O(N) scan cost for every such data-feed read, where N is the attacker-controlled number of outstanding unstable `data_feed`-carrying units. This directly matches the reported bug class: unmetered, unbounded per-unit iteration over an attacker-growable structure in a path executed by every node on every block/MCI transition.

### Impact Explanation
As N grows (attacker floods thousands of cheap units carrying `data_feed` payloads and keeps them unstable), every AA trigger evaluation that touches a data feed becomes proportionally slower on every full node. Because AA execution is part of the deterministic, consensus-critical unit-processing pipeline that must complete for the network to keep confirming new units, sufficiently large N can degrade node throughput to the point that the network becomes unable to confirm new units in a timely manner — the ocore-native form of "chain halt." This satisfies the required impact bar: a network unable to confirm new units, driven purely by a single-class permissionless action (posting ordinary data-feed-bearing units and triggering any oracle-consuming AA), with no privileged access required.

### Likelihood Explanation
Likelihood is high: posting units with a `data_feed` message costs only ordinary base-asset byte fees (there is no special large fee gate comparable to the reported "1 TIA" plan-creation fee), keeping units unstable for extended periods is achievable by a normal, low-cost unit-posting pattern, and triggering an AA that consumes data feeds is a routine, permissionless action available to any wallet or device. The vulnerable code path (`bAA` branch of `readDataFeedValue`/`dataFeedExists`) is exercised by any oracle-consuming AA already deployed on mainnet, so exploitation requires no special AA cooperation beyond simply causing one of these common formulas to execute while the attacker's flood of unstable `data_feed` units is outstanding.

### Recommendation
- Index `storage.assocUnstableMessages` by feed-relevant key (e.g. maintain a secondary map keyed by author address / feed_name) so lookups for a specific `(oracles, feed_name)` pair do not require scanning all unstable units carrying unrelated message types.
- Alternatively (or additionally), impose a hard cap on the number of unstable `data_feed`-bearing units considered per lookup, and/or scale the formula's `count_ops`/`complexity` charge for `data_feed`/`in_data_feed` proportionally to `Object.keys(storage.assocUnstableMessages).length` at validation time, similar to how the audited fix recommended scaling gas cost with the number of existing plans.
- Consider bounding the total size of `storage.assocUnstableMessages` itself (e.g., rejecting/deprioritizing further `data_feed` messages from units whose ancestors are not stabilizing quickly), so the attacker-controlled input to this loop cannot grow unboundedly in the first place.

### Proof of Concept
Conceptual reproduction (matches the reachable, unprivileged-poster path):
1. Deploy (or use an existing) AA that includes a `data_feed[[oracles='SOME_ORACLE_ADDR', feed_name='x']]` or `in_data_feed[...]` read in its `messages`/`state` formula — a standard oracle-consuming AA pattern.
2. From an ordinary wallet, post a large number (e.g. tens of thousands) of minimal-fee units, each containing a `data_feed` message, without waiting for/allowing them to stabilize (e.g., issue them in parallel branches so main-chain advancement lags behind).
3. Send a trigger to the oracle-consuming AA from step 1.
4. Observe that `dataFeeds.readDataFeedValue`'s `bIncludeUnstableAAs` branch (or `dataFeedExists`'s `bAA` branch) iterates the full `storage.assocUnstableMessages` set built in step 2 on every node processing the trigger, with per-node latency scaling linearly with the number of outstanding unstable `data_feed` units — reproducing the same class of unmetered, attacker-amplifiable computation described in the source report, without any privileged or node-level access.
