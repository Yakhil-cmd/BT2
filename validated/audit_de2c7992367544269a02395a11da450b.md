### Title
Reachable assert abort in `recover_cells` via duplicate `cell_indices` bypassing the Rust binding's lack of deduplication check - ([File: src/eip7594/recovery.c])

### Summary
`KZGSettings::recover_cells_and_kzg_proofs` in the Rust binding forwards `cell_indices` to the C function `recover_cells` with **no validation whatsoever** beyond a length-equality check between `cell_indices` and `cells`. If an attacker supplies a `cell_indices` array containing duplicate values with `num_cells >= CELLS_PER_BLOB` but fewer than `CELLS_PER_BLOB` *distinct* indices, and the C-level entry point does not itself deduplicate before checking `num_cells < CELLS_PER_BLOB`, execution reaches `recover_cells` and its `assert(CELLS_PER_EXT_BLOB - len_missing >= CELLS_PER_BLOB)` at src/eip7594/recovery.c:260, aborting the process on every node that processes the crafted sidecar.

### Finding Description
The broken equality is: **`num_cells` (array length, includes duplicates) vs. count of distinct present indices** used to size the "have enough cells" check.

In the Rust binding, `recover_cells_and_kzg_proofs` only checks that `cell_indices.len() == cells.len()` before calling the raw FFI function with `cells.len() as u64` as `num_cells`: [1](#0-0) 

There is no bounds check, no duplicate check, and no ascending-order check on `cell_indices` in this binding — the premise in the question that such a check exists "before the C call" and might be "bypassed" is inaccurate for this Rust binding: **no such check exists at all**, so the raw values are passed through unmodified.

On the C side, `recover_cells` computes `len_missing` not from `num_cells` directly, but by iterating over every possible index `0..CELLS_PER_EXT_BLOB` and calling `is_in_array(cell_indices, num_cells, i)`, which only checks *presence* (true/false), not occurrence count: [2](#0-1) [3](#0-2) 

This presence-based scan means duplicates in `cell_indices` cannot cause `len_missing` to be *under*-counted (i.e., cannot make the assert pass on too few real distinct cells) — is_in_array correctly reports that a truly-missing extended-domain position is missing regardless of how many times some other index is duplicated. So the specific "assert wrongly PASSES" scenario described in the question does not occur; `len_missing` is always computed correctly from the actual set of distinct present indices in `cell_indices[0..num_cells]`.

What *is* a real, reachable problem: if the caller only validates `num_cells >= CELLS_PER_BLOB` (a simple count check) without verifying that `cell_indices` contains `CELLS_PER_BLOB` distinct values, an attacker can supply e.g. `num_cells == CELLS_PER_BLOB` with duplicate entries so that the distinct index count is less than `CELLS_PER_BLOB`. In that case `len_missing` (correctly computed) will be `> CELLS_PER_EXT_BLOB - CELLS_PER_BLOB`, and the `assert` at line 260 will correctly detect insufficient data and **abort the process** rather than returning `C_KZG_BADARGS` gracefully. This is a reachable-assert crash rather than a "wrong verdict."

I was not able to load `src/eip7594/eip7594.c` (the wrapper that calls `recover_cells` and is expected to perform the `num_cells < CELLS_PER_BLOB` / index-range checks) within the available tool budget, so I cannot fully confirm whether that layer performs any deduplication before calling `recover_cells`. This is the key open question: if that layer only checks `num_cells >= CELLS_PER_BLOB` and index range (`< CELLS_PER_EXT_BLOB`) but not distinctness, the assert is attacker-reachable through the Rust binding (and any other binding lacking its own dedup check) with fully attacker-controlled `cell_indices` from a blob/data-column sidecar.

### Impact Explanation
If the assert is reachable, a single crafted cell/cell_indices payload passed to `recover_cells_and_kzg_proofs` causes an `assert` failure, which terminates the process on every node that calls into this function with the same bytes — matching the "High: one blob or sidecar crashes or aborts every node running this library (reachable assert)" category. No proof or commitment forges; the impact is availability (DoS via abort), not a wrong verification verdict.

### Likelihood Explanation
The attacker is an ordinary user submitting a blob/data-column sidecar; they fully control the `cells` and `cell_indices` inputs delivered to `recover_cells_and_kzg_proofs`. The Rust binding performs no validation of `cell_indices` values (only a length-match check), so the crafted duplicate-index array reaches the C layer unmodified. Whether the abort actually triggers depends entirely on the (unverified) validation logic inside `src/eip7594/eip7594.c` — specifically whether it deduplicates cell indices before checking `num_cells >= CELLS_PER_BLOB`. This must be confirmed by inspecting that file directly.

### Recommendation
- In `src/eip7594/eip7594.c`'s `recover_cells_and_kzg_proofs` wrapper, explicitly validate that all entries of `cell_indices` are both `< CELLS_PER_EXT_BLOB` and pairwise distinct (e.g., via a bitmap/seen-array check) before calling `recover_cells`, returning `C_KZG_BADARGS` on failure instead of relying on the downstream `assert`.
- Alternatively/additionally, replace the `assert(CELLS_PER_EXT_BLOB - len_missing >= CELLS_PER_BLOB)` in `src/eip7594/recovery.c` with a proper `C_KZG_RET` error return, so that even if an un-deduplicated `cell_indices` array reaches `recover_cells`, the library fails gracefully instead of aborting the process.
- Add the same distinctness validation in all language bindings (Rust, Python, Node.js, etc.) that call `recover_cells_and_kzg_proofs`, rather than relying solely on the C core.

### Proof of Concept

2. Populate a matching `cells` array of the same length with valid cell bytes for those (duplicated) positions.

Assert: **before fix**, the process aborts (SIGABRT) inside `recover_cells` at the `assert(CELLS_PER_EXT_BLOB - len_missing >= CELLS_PER_BLOB)` line — confirm via a child-process/fork harness catching the abort signal, or via `assert.h`'s `NDEBUG`-off build showing a non-zero-signal exit rather than a `C_KZG_RET` value.
5. **After fix**, the same input should cause the API to return `C_KZG_BADARGS` rather than aborting the process.

static bool is_in_array(const uint64_t *arr, size_t arr_size, uint64_t value) {
