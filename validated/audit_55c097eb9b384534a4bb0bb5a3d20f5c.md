### Title
Cross-Organization Webhook Forgery via Repository Owner/Full-Name Binding Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to authenticate an inbound webhook based on `params.dig('repository', 'owner', 'login')`, while every downstream handler (`Handler#repository_name`, `PushHandler`, `CheckSuiteHandler`, `StatusHandler`) resolves the repository/stack/commit to act on using a *different* field — `payload.dig('repository', 'full_name')` (or, for `StatusHandler`, no repository scoping at all). Because the HMAC signature only proves the payload was signed with a given organization's secret, and that organization is derived from a field the handlers never re-check, a party who legitimately controls one configured GitHub organization's webhook secret can forge events that are executed against a repository belonging to a completely different, unrelated organization on the same multi-tenant Shipit instance.

### Finding Description
`config/secrets.yml` supports multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's app/secret to use for HMAC verification purely from the payload's `repository.owner.login` (falling back to `organization.login`): [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` computes the HMAC over the raw request body using that organization's secret [4](#0-3) . This only proves *which org's secret signed the body*, not that the org named in `repository.owner.login` matches the repository the handler will ultimately mutate.

Once verification passes, `create` dispatches to handlers using the same parsed JSON body [5](#0-4) . The base `Handler` class resolves the target repository from `payload.dig('repository', 'full_name')` — a distinct field from the one used for signature routing: [6](#0-5) 

`PushHandler` and `CheckSuiteHandler` both act on stacks/commits resolved via that `full_name`-derived `stacks` helper [7](#0-6) [8](#0-7) . `StatusHandler` is even less scoped — it updates **any** `Commit` whose `sha` matches, with no repository check at all [9](#0-8) .

Nothing in the request pipeline asserts `repository.owner.login == repository.full_name.split('/').first`. An attacker who is the legitimate operator of "Org A" (and therefore knows Org A's own configured `webhook_secret` — a value they set up themselves when installing their GitHub App, not a privileged Shipit secret) can send a POST to `/webhooks` with:
- `X-Hub-Signature` computed over the payload using Org A's secret,
- `repository.owner.login = "org-a"` (so `verify_signature` picks Org A's app and the signature checks out),
- `repository.full_name = "org-b/victim-repo"` (or an arbitrary `sha`/`ref` for `StatusHandler`/`PushHandler`).

This is the same class of trust binding break as the referenced report: the value checked/authenticated (`repository.owner.login` selecting the signing organization) is not the value later acted upon (`repository.full_name` / commit `sha` selecting the write target), so an attacker with only their own organization's authenticated context can leak effects into another organization/repository's trust domain.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." Concretely:
- Via `PushHandler`, an attacker can force `Stack#sync_github(expected_head_sha:)` on any not-archived stack of any repository name they specify, faking sync events for a stack they do not own [10](#0-9) .
- Via `CheckSuiteHandler`, they can trigger `schedule_refresh_check_runs!` for any commit on any stack matching their forged `head_sha`/`head_branch` [8](#0-7) .
- Via `StatusHandler`, they can inject arbitrary CI status records for **any** commit sha across the entire instance regardless of repository, since it has no repository scoping at all [9](#0-8) . Forged "success" statuses feeding a stack's CI-gating logic can enable an unauthorized deploy/merge for a repository the attacker has no access to — matching the High/Critical impact bar (unauthorized deploy or cross-repository writes) defined in scope.

### Likelihood Explanation
Requires only that the Shipit instance is configured (as documented) with more than one GitHub organization/App and that the attacker legitimately controls one of them (e.g., is an admin of one tenant org on a multi-tenant Shipit deployment). No GitHub App private key, no `api_clients_secret`, no Shipit user session, and no victim-organization secret are needed — only knowledge of the attacker's own org's `webhook_secret`, which they set up themselves. This is a realistic configuration per `docs/setup.md`'s multi-org example, satisfying the "documented deployment" requirement.

### Recommendation
After signature verification, re-derive the organization strictly from the same field(s) used for signature selection and cross-check it against `repository.full_name`'s owner segment (and any repository/organization identifiers used by handlers) before dispatching to handlers; reject the webhook if they diverge. Additionally, scope `StatusHandler` (and any other handler lacking repository scoping) to the verified organization/repository rather than matching commits by `sha` alone across the whole instance.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with distinct `webhook_secret`s, per the documented multi-org config [1](#0-0) .
2. As the legitimate admin of `org-a`, know `org-a`'s `webhook_secret`.
3. Build a JSON payload:
   ```json
   {
     "sha": "<victim-commit-sha-in-org-b-repo>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
   }
   ```
4. Compute `X-Hub-Signature: sha1=HMAC-SHA1(org-a-webhook-secret, raw_body)` and send it to `POST /webhooks` with `X-Github-Event: status`.
5. `verify_signature` selects `Shipit.github(organization: "org-a")` per `repository_owner` [11](#0-10) , verification succeeds because the signature was made with `org-a`'s secret.
6. `StatusHandler#process` then updates the status of the `org-b` commit matching the forged `sha`, even though the attacker never proved control of `org-b` [9](#0-8) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
