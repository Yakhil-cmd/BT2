Confirmed. This is a genuine analog to the reported bug class ("a stack a token authorises versus a stack it touches"): `Shipit::Api::CCMenuController` deliberately overrides the scope-restriction inherited from `BaseController`.

### Title
Scoped API tokens can read the build status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with a `stack_id`, e.g. via `CCMenuUrlController#client`) can only resolve stacks from the set `Stack.where(id: current_api_client.stack_id)` [1](#0-0) . `CCMenuController`, however, overrides `#stack` to bypass this scoping entirely and resolve any stack by its URL parameter, using the global `Stack.from_param!` instead of the client-scoped `stacks.from_param!` [2](#0-1) .

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` whenever a token has a `stack_id` restriction, exactly like `BaseController#stacks` enforces for every other API controller [3](#0-2) .

`CCMenuController` authenticates the caller from a `token` query parameter via `ApiClient.authenticate(params[:token])` [4](#0-3) , then only checks generic permission possession — `require_permission :read, :stack` — which is implemented as `current_api_client.check_permissions!(operation, scope)`, i.e. it only checks whether `"read:stack"` is present in `permissions`, without any awareness of which specific stack is being requested [5](#0-4) .

The actual stack object used to render the response is then fetched with `Stack.from_param!(params[:stack_id])` — unscoped — instead of going through the inherited, client-scoped `stacks` relation [6](#0-5) . As a result, a token deliberately minted with a `stack_id` restriction (the exact pattern used for the "CCMenu Client" itself, created scoped to one stack in `CCMenuUrlController#client`) can be replayed against any other `stack_id` in the deployment and will successfully return that other stack's CI/build status [7](#0-6) .

This is precisely the class of bug in the report: a credential is checked against one binding (generic `read:stack` permission plus the client's authorized `stack_id`), but the resource actually acted upon (`stack` in the `show` action) is resolved through a different, unchecked binding (`params[:stack_id]` against the global `Stack` table).

### Impact Explanation
Any holder of a `here_come_the_walrus`-style scoped token (created for CCMenu integration and deliberately restricted to a single stack, per the pattern demonstrated in `CCMenuUrlController` and the `here_come_the_walrus` fixture) [8](#0-7)  can read the `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` of every stack in the Shipit instance, not just the one they were authorized for. This discloses cross-repository/cross-environment deploy state (including which stacks exist, their branches/environments, and whether recent deploys failed) to a token holder who was only meant to see one specific stack — an authorization-scope bypass qualifying as unauthorized cross-stack read of deploy/build state.

### Likelihood Explanation
Trivial and fully remote: it only requires possession of any valid, stack-scoped CCMenu token (these tokens are routinely embedded in CI dashboard URLs/config, per `CCMenuUrlController#fetch`) [9](#0-8) , and simply changing the `stack_id` route parameter — no additional secret, session, or privileged access is needed.

### Recommendation
Remove the `#stack` override in `CCMenuController` and rely on the inherited, client-scoped `BaseController#stack`/`#stacks` methods so the `stack_id` restriction on the `ApiClient` is always enforced, consistently with every other API controller.

### Proof of Concept
1. Create a stack-scoped API client (as `CCMenuUrlController#client` does) authorized only for `stack_a`, with `permissions: ['read:stack']` and `stack_id: stack_a.id`.
2. Call `GET /api/stacks/:stack_a_id/ccmenu.xml?token=<token>` — succeeds as intended.
3. Call `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` (a different, unauthorized stack) — because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, this also returns `200 OK` with `stack_b`'s build status, even though the token's `stack_id` only authorizes `stack_a`.
