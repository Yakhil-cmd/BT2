This confirms `Api::CommitsController#index` is properly scoped to `stack.commits` (the requesting operator's own stack, authenticated via `require_permission :read, :stack` which enforces `current_api_client.check_permissions!` against that specific stack) [1](#0-0) . There is no separate authorization bug on the read path itself — the controller correctly restricts visibility to the operator's own stack's commits.

The actual issue is entirely upstream, in how the `Status` row gets attached to that commit in the first place. `StatusHandler#process` looks up commits by `sha` alone, with no scoping to the webhook's own repository/stack: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2)  using the **victim commit's own `stack_id`** (not anything from the attacker's payload) [4](#0-3) .

Because of this, once the cross-repo write from "scenario 1" succeeds, the resulting `Status` row is a completely ordinary, correctly-`stack_id`-scoped row on the victim's commit — indistinguishable from a genuine CI report. Every consumer that reads `Commit#status` (`Status::Group.compact(self, statuses_and_check_runs)` [5](#0-4) ), `Commit#deployable?` [6](#0-5) , and `schedule_continuous_delivery` [7](#0-6)  — including the properly-scoped, properly-authenticated `Api::CommitsController#index` and the dashboard UI — will render/act on the forged data exactly as if it were legitimate, because there is no field or flag anywhere in `Status` distinguishing its true origin.

So the read surface (`CommitsController`) itself is not vulnerable — it correctly enforces `require_permission!` and stack scoping — but it faithfully and transparently surfaces the consequence of the write-side flaw already identified in scenario 1. This is not a second, independent vulnerability; it's the same root cause (`StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup) manifesting on the read side. I am not producing a duplicate finding for the same root cause under a different question framing — the file/method-level bug and its Critical impact (falsified data driving `deployable?`/`schedule_continuous_delivery` decisions and any downstream deploy/merge automation or human operator relying on `Commit#status`) were already established for scenario 1's write path.

### Title
Unscoped commit lookup in `StatusHandler#process` lets forged status transparently overwrite/impersonate a victim stack's CI result - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits by `sha` alone across the entire `commits` table, with no check that the webhook's repository matches the commit's owning stack/repository. The resulting `Status` is created with the victim commit's own `stack_id`, making it byte-for-byte indistinguishable from a legitimate CI status once written, so it is rendered as authoritative by every legitimate reader (`Commit#status`, `Commit#deployable?`, `Api::CommitsController`, dashboards) with no marker of its true origin.

### Finding Description
Binding claimed: `Status#stack_id`/commit displayed to a legitimate operator via `Api::CommitsController#index` == a status their own CI reported. Trace: an attacker who owns any repository can emit a signed `status` webhook (valid signature computed from their own repo's `Shipit.github(organization: repository_owner)` secret) with an arbitrary `sha` value. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1)  — this query is global, not scoped by `repository.full_name` or stack. If that `sha` collides with a commit belonging to any other stack (e.g., because the victim's repo was forked/mirrored and shares commit history, or the attacker discovers/predicts an sha already tracked in Shipit), `create_status_from_github!` writes a `Status` using `commit.stack_id` (the victim's real stack) [3](#0-2)  and `Status.replicate_from_github!` persists it with that `stack_id` [4](#0-3) . `verify_signature` only checks that the request was validly signed for *some* organization named in the payload, not that the commit or `sha` belongs to that organization/repository [8](#0-7) . On the read side, `Api::CommitsController#index` is properly permission-scoped (`require_permission :read, :stack`, `stack.commits`) [9](#0-8) , but it faithfully renders whatever `Status` rows exist for the victim's own commits — it has no way to detect the forged row's true origin.

### Impact Explanation
Once written, the forged `success`/`failure` status is used identically to a real one: `Commit#deployable?` [6](#0-5)  and `schedule_continuous_delivery` [7](#0-6)  gate real deploy automation and merges based on it, and any operator or dashboard viewing the victim stack sees it as the victim's own CI result. This is the same Critical-severity write-path bug from scenario 1 (a payload for one repository mutating another's stack/commit state feeding unauthorized deploy/merge decisions) — the read surface does not introduce an independent vulnerability; it is the mechanism by which the write's impact reaches human operators.

### Likelihood Explanation
Same preconditions as scenario 1: attacker needs no privileges beyond owning any GitHub repository capable of emitting a validly-signed webhook to the Shipit host, and needs an `sha` value that collides with a commit already tracked by Shipit under some victim stack (realistic via forked/mirrored repositories sharing commit history, a common real-world pattern). No additional preconditions are introduced by the read side.

### Recommendation
Scope `StatusHandler#process`'s commit lookup to commits whose stack's repository matches the webhook's `repository.full_name`/`repository_owner`, not just `sha`, before calling `create_status_from_github!`.

### Proof of Concept
This restates scenario 1's PoC; no additional test is needed for the read surface since `Api::CommitsController` is not independently vulnerable — see the `commit.statuses.count`/`Status.stack_id` assertions already required for scenario 1 (e.g. in `test/controllers/webhooks_controller_test.rb`'s `":state create a Status for the specific commit"` pattern [10](#0-9) , extended to assert the created `Status.stack_id` equals a *different* stack's id than the one implied by the webhook's `repository` payload, then asserting `commit.reload.deployable?`/`Api::CommitsController#index` for that victim stack reflects the forged state).
