### Title
KLAY Bridge Transfer Permanently Locked When Recipient Contract Reverts — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` delivers KLAY to the user-controlled `_to` address via a low-level call. If `_to` is a contract that reverts on receiving KLAY, the entire transaction reverts, the nonce is never consumed, `lowerHandleNonce` never advances, and the user's KLAY on the source chain is permanently locked in the source bridge with no on-chain recovery path.

---

### Finding Description

`handleKLAYTransfer` performs the following sequence:

```solidity
// BridgeTransferKLAY.sol lines 81–99
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

The `_to` address is fully user-controlled: it is supplied by the user when calling `requestKLAYTransfer` on the source chain and is relayed verbatim to `handleKLAYTransfer` on the destination chain. If `_to` is a contract without a payable fallback (or one that deliberately reverts), the low-level call returns `ok = false`, the `require` reverts the entire transaction, and **all state mutations above are rolled back**. Specifically:

- `handleNoncesToBlockNums[_requestedNonce]` is never set to a non-zero value.
- `_updateHandleNonce` never runs to completion, so `lowerHandleNonce` never advances past nonce N.
- The `HandleValueTransfer` event is never emitted, so `bi.handledEvent` in the Go bridge manager is never updated.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i` starting from `lowerHandleNonce`:

```solidity
// BridgeTransfer.sol lines 149–155
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    delete handleNoncesToBlockNums[i];
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
```

Because nonce N's entry is never set, `lowerHandleNonce` is permanently stuck at N.

The Go-level recovery module (`vt_recovery.go`) uses `lowerHandleNonce` as the `handleNonce` hint. Since `lowerHandleNonce` never advances past N, `retrievePendingEventsFrom` perpetually re-discovers nonce N as unhandled and re-queues it. Each retry submits a new on-chain transaction that reverts, wasting operator gas indefinitely.

There is no `cancelRequest`, `skipNonce`, or `withdraw` function in the bridge contract. The only egress path for KLAY from the source bridge is a successful `handleKLAYTransfer` on the destination chain, which is permanently blocked for nonce N.

---

### Impact Explanation

- **Permanent loss of bridged KAIA**: The user's KLAY deposited into the source bridge on the source chain is irrecoverable. The source bridge holds the funds with no withdrawal mechanism.
- **`lowerHandleNonce` stuck**: The nonce watermark never advances past N. While higher nonces can still be individually handled (the `_lowerHandleNonceCheck` only requires `_requestedNonce >= lowerHandleNonce`), the `recoveryBlockNumber` is frozen, and the recovery loop perpetually re-scans from an earlier block.
- **Operator gas drain**: The recovery mechanism (`vt_recovery.go`) submits failing transactions for nonce N on every recovery cycle, consuming operator gas indefinitely.

---

### Likelihood Explanation

Any user who specifies a contract address as `_to` that lacks a payable fallback — whether accidentally (e.g., a multisig, DAO treasury, or protocol contract that does not accept raw KLAY) or deliberately — triggers this condition. The `requestKLAYTransfer` function imposes no validation on `_to`:

```solidity
// BridgeTransferKLAY.sol line 132–134
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

The scenario is reachable by any unprivileged user with no special access.

---

### Recommendation

1. **Pull-payment pattern**: Instead of pushing KLAY to `_to` in `handleKLAYTransfer`, record the claimable balance and let `_to` withdraw it. This eliminates the external call from the critical path.
2. **Skip-and-escrow**: If the push fails, escrow the KLAY in the bridge and emit a `TransferFailed` event. Allow the bridge owner to redirect escrowed funds to a recovery address.
3. **Pre-flight validation**: Before accepting `requestKLAYTransfer`, verify that `_to` can receive KLAY (e.g., check `_to.code.length == 0` for EOA-only transfers, or require a signed acknowledgement from `_to`).

---

### Proof of Concept

**Step 1 — Deploy a reverting receiver on the destination chain:**
```solidity
contract MaliciousReceiver {
    receive() external payable { revert("no KLAY"); }
}
// deployed at address: 0xDEAD...
```

**Step 2 — Lock KLAY in the source bridge:**
```solidity
// Source chain
bridge.requestKLAYTransfer{value: 10 ether}(
    address(0xDEAD),  // _to = MaliciousReceiver
    10 ether,
    ""
);
// Source bridge now holds 10 KLAY; RequestValueTransfer emitted with nonce N
```

**Step 3 — Operator attempts to handle on destination chain:**
```solidity
// Destination chain — called by bridge operator
bridge.handleKLAYTransfer(txHash, from, 0xDEAD, 10 ether, N, blockNum, "");
// Execution reaches: (bool ok,) = _to.call.value(10 ether)("");
// MaliciousReceiver.receive() reverts → ok = false
// require(ok) reverts entire tx
// handleNoncesToBlockNums[N] remains 0
// lowerHandleNonce stays at N
```

**Step 4 — Recovery loop perpetuates:**
```
vt_recovery.go: lowerHandleNonce = N, requestNonce = N+1
→ retrievePendingEventsFrom finds nonce N unhandled
→ re-queues nonce N
→ operator submits handleKLAYTransfer again → reverts again
→ loop repeats indefinitely
```

**Result**: The user's 10 KLAY is permanently locked in the source bridge. `lowerHandleNonce` is frozen at N. No on-chain path exists to recover the funds. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6)

func retrievePendingEventsFrom(hint *valueTransferHint, from, to *BridgeInfo) ([]IRequestValueTransferEvent, error) {
	if from.bridge == nil {
		return nil, errors.New("from bridge is nil")
	}
	if to.bridge == nil {
		return nil, errors.New("to bridge is nil")
	}
	if hint.requestNonce == hint.handleNonce {
		return nil, nil
	}
	if !checkRecoveryCondition(hint) {
		return nil, nil
	}

	var pendingEvents []IRequestValueTransferEvent

	curBlkNum, err := from.GetCurrentBlockNumber()
	if err != nil {
		return nil, err
	}

	startBlkNum := hint.blockNumber
	endBlkNum := startBlkNum + filterLogsStride

pendingTxLoop:
	for startBlkNum <= curBlkNum {
		if endBlkNum > curBlkNum {
			endBlkNum = curBlkNum
		}
		opts := &bind.FilterOpts{Start: startBlkNum, End: &endBlkNum}
		reqVTevIt, err := from.bridge.FilterRequestValueTransfer(opts, nil, nil, nil)
		if err != nil {
			return nil, err
		}
		reqVTencodedDataIt, err := from.bridge.FilterRequestValueTransferEncoded(opts, nil, nil, nil)
		if err != nil {
			return nil, err
		}

		// TODO: The same logic with two types are verbose and can be neat with Go1.18 which supports generic.
		// For the FilterRequestValueTransfer type
		for reqVTevIt.Next() {
			logger.Trace("pending nonce in the RequestValueTransfer event", "requestNonce", reqVTevIt.Event.RequestNonce)
			if reqVTevIt.Event.RequestNonce >= hint.handleNonce {
				// Check if the event is already handled in target bridge contract
				if isHandledEvent(to, RequestValueTransferEvent{reqVTevIt.Event}) {
					continue
				}
				logger.Trace("filtered pending nonce", "requestNonce", reqVTevIt.Event.RequestNonce, "handledNonce", hint.handleNonce)
				pendingEvents = append(pendingEvents, RequestValueTransferEvent{reqVTevIt.Event})
				if len(pendingEvents) >= maxPendingTxs {
					reqVTevIt.Close()
					break pendingTxLoop
				}
			}
		}
		// For the FilterRequestValueTransferEncoded type
		for reqVTencodedDataIt.Next() {
			logger.Trace("pending nonce in the RequestValueTransferEncoded event", "requestNonce", reqVTencodedDataIt.Event.RequestNonce)
			if reqVTencodedDataIt.Event.RequestNonce >= hint.handleNonce {
				// Check if the event is already handled in target bridge contract
				if isHandledEvent(to, RequestValueTransferEncodedEvent{reqVTencodedDataIt.Event}) {
					continue
				}
				logger.Trace("filtered pending nonce", "requestNonce", reqVTencodedDataIt.Event.RequestNonce, "handledNonce", hint.handleNonce)
				pendingEvents = append(pendingEvents, RequestValueTransferEncodedEvent{reqVTencodedDataIt.Event})
				if len(pendingEvents) >= maxPendingTxs {
					reqVTencodedDataIt.Close()
					break pendingTxLoop
				}
			}
		}
		startBlkNum = endBlkNum + 1
		endBlkNum = startBlkNum + filterLogsStride
		reqVTevIt.Close()
		reqVTencodedDataIt.Close()
	}

	if len(pendingEvents) > 0 {
		logger.Info("retrieved pending events", "bridge", from.address.String(),
			"len(pendingEvents)", len(pendingEvents), "1st nonce", pendingEvents[0].Nonce())
	}
	return pendingEvents, nil
