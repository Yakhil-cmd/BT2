### Title
Unbenchmarked `remove_all_authorized_aliases` weight vs O(n) `AuthorizedAliases` storage/hold removal - (File: `system-parachains/bulletin/bulletin-polkadot/src/xcm_config.rs`)

### Summary
`pallet_xcm::Config::AuthorizedAliasConsideration` on Bulletin Polkadot uses `HoldConsideration<..., LinearStoragePrice<DepositPerItem, DepositPerByte, Balance>>`, and `AuthorizedAliases` storage is per-account, growing without any bound enforced in this runtime's `pallet_xcm::Config`. The autogenerated `WeightInfo` for `pallet_xcm` in this runtime (and in every other system chain checked) benchmarks `add_authorized_alias` and `remove_authorized_alias` individually, but never benchmarks `remove_all_authorized_aliases`, despite the extrinsic being real and callable by any signed account (confirmed via emulated test usage). This means the weight charged for `remove_all_authorized_aliases` does not reflect the per-chain, per-item removal cost of that extrinsic.

### Finding Description
`impl pallet_xcm::Config for Runtime` sets: [1](#0-0) 

`type WeightInfo = crate::weights::pallet_xcm::WeightInfo<Runtime>`, and this file only implements weight functions for `add_authorized_alias` and `remove_authorized_alias`, ending immediately after with `weigh_message`: [2](#0-1) 

No `remove_all_authorized_aliases` function is present in this file, even though the benchmark command used `--extrinsic=*`: [3](#0-2) 

The extrinsic itself is real and reachable by an ordinary signed account, as demonstrated in the emulated integration test which calls it directly with a signed origin: [4](#0-3) 

Because the runtime's generated `WeightInfo` has no override for `remove_all_authorized_aliases`, the call falls back to whatever default/fallback weight the external `pallet_xcm::WeightInfo` trait provides (this repo does not vendor the pallet source, so the exact fallback value cannot be inspected here, but its absence from every per-chain benchmark file across Bulletin, Asset Hub, Bridge Hub, Coretime, People, etc. is consistent). That default weight is necessarily generic and cannot account for the true state-dependent cost of removing N entries from `AuthorizedAliases` and releasing/recomputing the associated `HoldConsideration` (which is priced via `LinearStoragePrice<DepositPerItem, DepositPerByte, Balance>` scaling with stored item/byte count), producing a real mismatch between charged weight and actual execution cost as N grows.

Nothing in this runtime's `pallet_xcm::Config` bounds the number of aliases a single account can register — `MaxLockers: ConstU32<8>` governs `TrustedLockers`/remote lock consumers, an unrelated config item, not `AuthorizedAliases`: [5](#0-4) 

An attacker only needs enough spendable/holdable balance to place N holds (funds are held, not spent, so they are recovered after removal), then can call `add_authorized_alias` N times followed by a single `remove_all_authorized_aliases`, paying only the flat/fallback weight fee for the bulk-removal call while the node performs O(n) actual work.

### Impact Explanation
If the underlying `pallet_xcm::WeightInfo` fallback for `remove_all_authorized_aliases` is fixed/small relative to true O(n) execution cost, an unprivileged signed account can repeatedly grow and bulk-clear its `AuthorizedAliases` set to consume disproportionate block execution time relative to the weight fee charged — a griefing vector against block production capacity, scoped exactly to this extrinsic pair.

### Likelihood Explanation
Feasibility depends on: (1) confirming the actual runtime-linked `pallet_xcm::WeightInfo` fallback weight value for `remove_all_authorized_aliases` (not present in this repo, only inferable from its absence across all generated weight files), and (2) the attacker's ability to afford N simultaneous per-item holds long enough to trigger the bulk removal, which is economically bounded by `DepositPerItem`/`DepositPerByte` but not by any hard `MaxAuthorizedAliases` cap in this runtime's config. Repeatability is high once the deposit cost is affordable, since holds are recovered after removal and the loop can be repeated across blocks.

### Recommendation
Add an explicit, per-runtime benchmark for `remove_all_authorized_aliases` in `system-parachains/bulletin/bulletin-polkadot/src/weights/pallet_xcm.rs` (and all other affected runtimes) that scales with the maximum realistic/bounded number of stored aliases, and enforce a hard bound (e.g., a `MaxAuthorizedAliases` type analogous to other bounded collections) on `AuthorizedAliases` so worst-case weight is provably bounded rather than relying on economic deposits alone.

### Proof of Concept
Rust benchmark-style integration test in the bulletin-polkadot test crate:
1. Fund a signed test account with enough balance to cover N `DepositPerItem`/`DepositPerByte` holds.
2. Loop calling `PolkadotXcm::add_authorized_alias` N times (N = large bound, e.g. 1_000) with distinct alias locations, from the signed origin.
3. Measure actual execution weight/time of a single `PolkadotXcm::remove_all_authorized_aliases` call (e.g. via `frame_benchmarking`-style timing or `System::block_weight()` before/after) for varying N (10, 100, 1000).
4. Compare the measured weight growth curve against the static value returned by `<Runtime as pallet_xcm::Config>::WeightInfo::remove_all_authorized_aliases()`.
5. Assert that declared weight `>=` measured weight for all tested N; a failing assertion at large N demonstrates the underweighted griefing path.
