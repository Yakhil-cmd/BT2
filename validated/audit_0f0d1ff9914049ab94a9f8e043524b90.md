Confirmed root cause. This is exactly the analog the rules describe: "an organization that authenticated versus the repository that is written."

`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the HMAC against using `repository_owner`, which is parsed from `params.dig('repository', 'owner', 'login')` (a field inside the same unauthenticated raw body). `Handler#stacks`/`#repository_name`, however, resolves the target `Repository`/`Stack` using an entirely different field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together — the signature only proves "this body was HMAC-signed with organization X's secret," not "the repository X owns is the repository that will be acted upon."

An attacker who legitimately controls a GitHub App installation on their own low-value organization (so they can generate a validly-signed webhook, e.g. by pushing to their own repo) can intercept/replay that request and rewrite the JSON body's `repository.full_name` to point at any other organization's repository/stack tracked by this Shipit instance, while leaving `repository.owner.login` (and `organization.login`) referencing their own org so `verify_signature` still selects and validates against their own known-good secret. Because the HMAC is computed over the full raw body by the *sender*, this only works if the attacker can produce a valid signature for their tampered payload — which they can, since they possess their own org's `webhook_secret` (set when they created their own GitHub App installation, a normal unprivileged action, not a Shipit credential). This is exactly the "unverified field acted upon while the verified field only pins the secret" binding break. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Webhook signature verification keys off `repository.owner.login` but handlers act on the unrelated `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate a webhook's HMAC using `repository_owner` (derived from `repository.owner.login` or `organization.login`), but every event `Handler` resolves the actual `Stack`/`Repository` to mutate using the sibling field `repository.full_name`. These two fields are never cross-checked, so a validly-signed payload from one organization's installation can be crafted to target another organization's repository.

### Finding Description
`verify_signature` fetches the org-scoped GitHub App config via `Shipit.github(organization: repository_owner)` and validates the raw POST body's HMAC signature against that config's `webhook_secret`: [4](#0-3) 
`repository_owner` is extracted straight from the unauthenticated JSON body: [5](#0-4) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and every `Handler` subclass looks up the target stack(s) via `repository_name = payload.dig('repository', 'full_name')`: [2](#0-1) 

Because Shipit supports multiple organizations each with their own GitHub App and `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`), the field used to *select and validate the signing secret* (`repository.owner.login`) is independent of the field used to *decide what gets acted on* (`repository.full_name`). An attacker who controls their own organization's GitHub App installation can sign a JSON body where `repository.owner.login` = their own org (so verification succeeds against their own secret) while `repository.full_name` = `"victim-org/victim-repo"` (so the handler acts on a stack belonging to a different, unrelated organization).

### Impact Explanation
This breaks the intended trust boundary that a webhook signed by organization A's secret should only be able to affect stacks belonging to organization A's repositories. Depending on the event type dispatched (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.), this can be abused to force a `GithubSyncJob` re-sync, inject fabricated commit statuses, or manipulate merge/team membership state for a completely unrelated, victim organization's stack — effectively a cross-organization write into stack state that the attacker does not control and was never granted webhook access to. This matches the "cross-repository writes" Critical-impact bucket, since it lets an attacker with only their own (low-privilege) GitHub App installation influence another organization's tracked repository/stack.

### Likelihood Explanation
Requires: (1) the deployment to be configured with more than one GitHub App/organization (a supported, documented configuration per `secrets_double_github_app.yml`), and (2) the attacker to control at least one such installation (their own org, an ordinary unprivileged setup step, not a Shipit-internal credential). No Shipit session, `ApiClient` token, or GitHub App private key is required — only the attacker's own organization's `webhook_secret`, which they legitimately possess by virtue of owning that installation. This is a realistic misconfiguration/attack path in any multi-tenant Shipit deployment.

### Recommendation
After signature verification, re-derive the organization solely from the field actually used to select/act on a repository (`repository.full_name`'s owner segment, or resolve the `Repository`/`Stack` and compare its `owner`) and reject the request if it does not match the organization whose secret validated the signature. Alternatively, verify the signature using the config resolved from the same field the handlers use (`full_name`) rather than a separate `owner.login`/`organization.login` field.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` (attacker-controlled GitHub App, known `webhook_secret`) and `VictimOrg` (tracks a `Stack` for `VictimOrg/victim-repo`), as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "AttackerOrg" },
       "full_name": "VictimOrg/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` extracts `repository_owner` = `AttackerOrg`, fetches `AttackerOrg`'s config, and confirms the signature — passes.
5. `PushHandler.call(params)` resolves `repository_name` = `VictimOrg/victim-repo` via `Handler#repository_name`, finds the matching `Stack`, and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, even though the signature only proved knowledge of `AttackerOrg`'s secret.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
