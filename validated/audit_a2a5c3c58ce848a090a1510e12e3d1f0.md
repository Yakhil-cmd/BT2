### Title
`StatusHandler` writes commit statuses without binding them to the organization whose webhook secret authenticated the request - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects a GitHub App configuration (and therefore an HMAC secret) purely from an attacker-supplied payload field (`repository.owner.login` / `organization.login`), and `GithubApp#verify_webhook_signature` unconditionally returns `true` when that App has no `webhook_secret` configured — a state explicitly documented as valid/optional. Once past this check, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks which organization/repository the event belongs to: it updates any `Commit` in the entire database whose `sha` matches the payload, across all stacks and organizations. This breaks the intended binding "the organization that authenticated the webhook == the repository whose data gets written."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the signing secret to validate against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from the JSON body the caller supplies, and is used only to select which `Shipit::GithubApp` instance (and hence which `webhook_secret`) to check the `X-Hub-Signature` header against: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` whenever the selected organization's App has no `webhook_secret` configured at all — a configuration explicitly presented as optional in the setup docs and shown as `webhook_secret: # nil` in the shipped multi-org example: [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature` (either because it was genuinely signed for the org with no secret, or trivially for that org), the actual handler that mutates state does not re-validate that the event pertains to the organization/repository that was authenticated. `StatusHandler#process` looks up commits *only by SHA*, globally, with no scoping by repository/stack/organization: [6](#0-5) 

So the equality that should hold is:
`organization/App used to authenticate the webhook == repository/stack whose Commit rows are written by StatusHandler`

but the code only enforces:
`organization used to pick the HMAC key` (attacker-controlled field, and trivially satisfied for any App configured without a `webhook_secret`)
while
`Commit.where(sha: params.sha)` touches records belonging to **any** stack/organization in the installation, independent of which App authenticated the request.

This is directly analogous to `MainVault.rebalanceXChain` checking `state == SendingFundsXChain` (one binding) but never re-validating `savedTotalUnderlying >= reservedFunds` (the binding that actually matters) before acting — here, Shipit checks "is this signed by *some* configured App" but never re-validates "does this event actually belong to the repository/commit that App is authorized to represent" before writing to `Commit`.

### Impact Explanation
If an installation is configured with multiple GitHub Apps/organizations (a supported, documented setup — see `docs/setup.md` "Using Multiple Github Applications") and at least one of them is left with no `webhook_secret` (also documented as an acceptable/optional configuration), an unauthenticated caller can POST a forged `status` event to `/webhooks` claiming to originate from that unsecured organization, while setting `sha` to the SHA of a commit belonging to a **different**, properly-secured stack/organization. `StatusHandler` will create/overwrite a CI status (e.g. `state: success`) for that commit regardless of which App authenticated the payload. Because commit CI status directly feeds `required_statuses`/`Commit#deployable?` and continuous deployment/merge-queue decisions, this can be used to mark an arbitrary commit as passing CI and trigger an unauthorized deploy or merge on a stack the attacker has no legitimate relationship to — meeting the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
The endpoint `/webhooks` requires no Shipit session, no `ApiClient` token, and no GitHub App private key — it is reachable by any unauthenticated network client. The only prerequisite is an operator having configured at least one GitHub App/org without a `webhook_secret`, which the project's own documentation and shipped test fixtures present as a normal, supported configuration for multi-org installs. Commit SHAs for the target stack are typically public (visible on GitHub or in Shipit's own UI/API), so guessing/obtaining the target `sha` is trivial. This makes the likelihood moderate-to-high in any multi-org deployment that follows the documented "optional" webhook secret guidance for at least one App.

### Recommendation
Do not let the organization used to select the verification secret be decided from unauthenticated payload data. After signature verification (and especially in a multi-org context), re-derive the repository/stack strictly from the *authenticated* organization key and reject or ignore any event whose `repository.full_name`/`repository.owner.login` does not belong to that same organization. Additionally, `StatusHandler#process` (and any other handler that mutates `Commit`/`Stack` state) should scope its lookup by the repository identified in the (now-trusted) payload rather than matching `Commit` rows globally by `sha` alone. Consider also making `webhook_secret` mandatory (or refusing to boot / loudly warning) whenever more than one GitHub App is configured, since the "no secret configured" fallback removes all authentication for that org's events.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (has real `webhook_secret`) and `OrgTwo` (`webhook_secret:` left blank, as shown for `OrgTwo`) — a documented, supported setup.
2. Identify a target `Commit#sha` belonging to a stack owned by `OrgOne` (publicly visible on GitHub or via Shipit's own read-only endpoints).
3. Send, without any authentication and without a valid `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": {"owner": {"login": "OrgTwo"}, "full_name": "OrgTwo/anything"},
  "sha": "<victim commit sha owned by OrgOne>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `verify_signature` resolves `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the request is accepted.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a passing status on the victim commit belonging to `OrgOne`'s stack, even though the request was never authenticated for `OrgOne`. If that status satisfies the stack's `required_statuses`, continuous deployment/merge-queue logic can proceed to deploy or merge that commit without any legitimate authorization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
