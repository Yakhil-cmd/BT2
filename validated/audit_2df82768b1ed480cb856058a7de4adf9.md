### Title
Staker reward baseline is set from a stale per-signer checkpoint, letting a staker claim STX-staking rewards accrued before they staked - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
The pox-5 STX-only-staking reward accounting uses a two-level accumulator: a single pool-wide `rewards-per-token-for-cycle` value (accrued from total STX staked across all signers) and, per signer, a cached checkpoint `signer-rewards-per-token-for-cycle` that is supposed to track that pool-wide value. `settle-rewards` only refreshes a signer's checkpoint when that signer's own shares are currently nonzero [1](#0-0) . When a new staker joins a signer whose shares are currently zero, `settle-staker-rewards` is skipped [2](#0-1)  and the staker's reward baseline is taken directly from that stale, unrefreshed checkpoint [3](#0-2) , instead of the true current pool-wide value. This mirrors the RToken bug class: comparing/seeding one accumulator against an accumulator that has silently drifted out of sync with the value it is supposed to mirror, because the refresh path was skipped under a specific state ("shares == 0" here, "double-scaled index" there).

### Finding Description
`compute-earned-rewards` computes `earned = pending + shares * (rpt_current - rpt_paid) / PRECISION` [4](#0-3) .

For STX-only staking, the pool-wide accumulator `rewards-per-token-for-cycle` grows monotonically based on the total STX staked across *all* signers each time `calculate-rewards` runs [5](#0-4) .

`settle-rewards` is the only place that copies this pool-wide value into a per-signer checkpoint (`signer-rewards-per-token-for-cycle`) that staker-level accounting relies on, and it does this copy *only if the signer's current shares are nonzero*:
```
(if (> shares u0)
    (map-set signer-rewards-per-token-for-cycle {...} rewards-per-token)
    true
)
``` [1](#0-0) 

`get-earned-staker-rewards` uses that per-signer checkpoint as the "current" rpt when computing a staker's earnings [6](#0-5) .

When a staker joins a signer with `prev-staker-shares == 0` (the signer currently has no staked shares - e.g. the signer was just created, or all prior stakers left / dropped below `SIGNER_SET_MIN_USTX`), `settle-rewards` is called first with the signer's shares still at their pre-join value [7](#0-6) . If that value is zero, the checkpoint is *not* refreshed to the current pool-wide rpt, and `settle-staker-rewards` for this staker is skipped entirely [8](#0-7) . The new staker's baseline is then seeded directly from this stale checkpoint:
```
(map-set staker-rewards-per-token-settled-for-cycle {...}
    (get-signer-rewards-per-token-for-cycle signer cycle none)
)
``` [3](#0-2) 

Because the checkpoint can be arbitrarily older than the pool-wide value (it was last refreshed the last time this signer happened to have nonzero shares, which could be many reward-computation calls / a long time ago, or still at its default of `u0` if the signer never had shares before), the staker's baseline (`rpt_paid`) is set lower than the true current pool-wide rpt. On the next settlement for this signer (which will now succeed since the signer's shares are nonzero because of this very staker), the signer's checkpoint jumps straight from the stale value up to the then-current pool-wide value, and the staker's earned amount is computed as `shares * (jumped_value - stale_baseline)` - crediting the staker for the entire pool-wide accrual that happened during the period the signer had zero shares, i.e., a period during which this staker held no stake at all.

### Impact Explanation
This breaks the core stacking-rewards equality: rewards distributed must equal rewards earned by the STX actually staked over time. An unprivileged staker can time joining a signer that currently has zero total staked shares (a state reachable via ordinary `unstake`/threshold-crossing flows) to capture pool-wide reward accrual attributable to *other* signers' stakers during a period before they themselves staked. Since the reward pot (`stx-staker-rewards`) is finite per cycle and shared, this is a double-count/theft of sBTC-denominated STX-staking rewards, potentially starving other honest stakers of rewards they legitimately earned, or causing balance-tracking inconsistencies when the over-credited amount is later claimed against the shared pot.

### Likelihood Explanation
Reaching the vulnerable state requires no privileged role - only ordinary `stake`/`unstake`/delegation actions that any staker can already perform, plus normal timing (waiting for a signer's shares to hit zero, then being first to (re)join). Given `calculate-rewards` runs periodically and signers naturally can drop to/rise from zero shares as members join and leave, this is a realistically reachable path rather than a purely theoretical one.

### Recommendation
Always refresh a signer's `signer-rewards-per-token-for-cycle` checkpoint to the current pool-wide `rewards-per-token-for-cycle` on every `settle-rewards` call, regardless of whether the signer's shares are currently zero, so that a newly joining staker's baseline always reflects the true current pool-wide value rather than a stale, possibly very old, snapshot. Equivalently, seed a new staker's `staker-rewards-per-token-settled-for-cycle` directly from `get-rewards-per-token-for-cycle` (the pool-wide value) instead of from the per-signer cached checkpoint.

### Proof of Concept
1. Signer `S` has stakers with nonzero total shares under the STX-only pool; `calculate-rewards` runs multiple times, growing the pool-wide `rewards-per-token-for-cycle` significantly (e.g., to value `R`), driven mostly by activity from other signers.
2. All stakers under signer `S` unstake, so `signer-shares-staked-for-cycle[S] == 0`. Because `settle-rewards` only refreshes `signer-rewards-per-token-for-cycle[S]` while shares are nonzero, its last recorded value is `r0 << R` (or `0` if `S` never had shares).
3. Attacker (staker `A`) stakes a large amount of STX with signer `S` right after this state, and right before/without further pool activity. `add-staker-to-signer-for-cycle` runs `settle-rewards(S, cycle, none)` with `S`'s pre-join shares still `0`, so the checkpoint stays at `r0`; `settle-staker-rewards` is skipped since `A`'s prior shares are `0`; `A`'s baseline is set to `get-signer-rewards-per-token-for-cycle(S,...) == r0`.
4. Any subsequent action that calls `settle-rewards(S, ...)` (another stake/unstake under `S`, or a claim) now sees `S`'s shares `> 0` and snaps the checkpoint from `r0` straight to the current pool-wide value `R'` (>= `R`).
5. `A` calls `claim-rewards`, and `get-earned-staker-rewards` computes `earned = A_shares * (R' - r0) / PRECISION`, crediting `A` for the entire `R' - r0` accrual window even though `A` had zero stake with `S` for most/all of that window. [9](#0-8) [10](#0-9)

(define-read-only (compute-earned-rewards
        (shares uint)
        (rpt-current uint)
        (rpt-paid uint)
        (pending uint)

(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            rewards-per-token
        )
        (if (> shares u0)
            (map-set signer-rewards-per-token-for-cycle {
                signer: signer,
                reward-cycle: reward-cycle,
                bond-index: bond-index,
            }
                rewards-per-token
            )
            true
        )
        {
            earned: earned,
            rewards-per-token: rewards-per-token,
        }
    )
)
