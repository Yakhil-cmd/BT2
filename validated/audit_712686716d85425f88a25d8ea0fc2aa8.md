### Title
Unauthenticated `body.authors[0]` definition trusted and persisted to `peer_addresses` without being bound to the actually-signed message - ([File: wallet.js])

### Summary
In the `arbiter_contract_response` handler, the code cryptographically verifies a `body.signed_message` blob (`objSignedMessage`) via `signed_message.validateSignedMessage`, but then stores address/definition data taken from a *different, unauthenticated* field of the same peer-supplied message, `body.authors[0]`, instead of from the verified `objSignedMessage.authors[0]`. This mirrors the OpenPGP.js CWE-347 pattern where verified ("hashed") data is silently superseded by unverified ("unhashed") attacker-controlled data that is processed as if it had been authenticated.

### Finding Description
`handleMessageFromHub` in `wallet.js` processes the `arbiter_contract_response` subject as follows: [1](#0-0) 

The signature check is performed only on `objSignedMessage`, parsed from `body.signed_message`: [2](#0-1) 

`validateSignedMessage` verifies that `objSignedMessage.authors[0]` correctly signs `signed_message` and, if a `definition` field is present, that it hashes to the claimed address [3](#0-2) . However, `processResponse` does not use `objSignedMessage.authors[0]` for the definition/address values that get written to storage — it uses `body.authors[0]`, a sibling field of the hub message that is entirely independent from `body.signed_message` and is not covered by any signature check. Only `author.address` is required to equal `objContract.peer_address`, and `author.definition` is only checked for self-consistency (`address === chash160(definition)`), never cross-checked against `objSignedMessage.authors[0].definition`. The resulting record is written into `peer_addresses`: [4](#0-3) 

using `Object.keys(objSignedMessage.authors[0].authentifiers)` (verified) paired with `author.definition` (unverified, from `body`). This mixes verified and unverified sources the same way the OpenPGP advisory describes unhashed subpacket data overwriting hashed data during signature-packet parsing: downstream code (`db.query(... INSERT ... peer_addresses (address, device_address, signing_paths, definition) ...)`) treats the pairing of `signing_paths` and `definition` as trustworthy simply because *part* of the tuple came from a verified structure.

### Impact Explanation
`peer_addresses` records the counterparty address and definition used for later interactions (e.g., private-payment counterparty verification and shared/cosigned address bookkeeping in `wallet_defined_by_addresses.js`/`wallet_defined_by_keys.js`). If the stored `signing_paths`/`definition` pairing does not actually correspond to the real signer of the contract response (only self-consistency of `body.authors[0]` is enforced, not equivalence to `objSignedMessage.authors[0]`), a malicious or compromised peer device can cause a wallet to persist an address definition metadata mismatch that is later relied upon for building or validating shared-address definitions and payment authorization data, creating a foothold for downstream authorization confusion in later private-payment or multisig flows that consume `peer_addresses`.

### Likelihood Explanation
Reachable by any device paired as an arbiter-contract "acceptor" peer sending a single `arbiter_contract_response` hub message — no privileged network/hub position required beyond being the counterparty device in an arbiter contract, matching the allowed "paired device" reach class. The attack requires only crafting the outer message fields (`body.authors`) independently of the inner signed blob (`body.signed_message`), which is trivial since the hub message is a plain JSON object under full sender control.

### Recommendation
Use `objSignedMessage.authors[0].address` and `objSignedMessage.authors[0].definition` (the fields actually covered by `validateSignedMessage`) when populating/updating `peer_addresses`, rather than the unauthenticated `body.authors[0]`. If `body.authors` is intended to convey information not present in the signed message, it must be validated as being equal to the corresponding fields of `objSignedMessage`, not merely self-consistent.

### Proof of Concept
1. Attacker device (peer of an arbiter contract) prepares a valid `body.signed_message` (base64 JSON) that legitimately signs the contract title with `objContract.peer_address`, satisfying `validateSignedMessage`.
2. In the same hub message, attacker sets `body.authors = [{ address: objContract.peer_address, definition: <own chosen definition D2 that still hashes to peer_address if attacker knows an alternate valid definition for that address, e.g. a multisig definition with additional attacker-controlled cosigner paths that were legitimately used to derive the same address at some point>, ... }]`.
3. `handleMessageFromHub` accepts the message because `objSignedMessage` verification succeeds and `body.authors[0]` passes its own self-consistency check (`address === chash160(definition)`), without ever confirming `body.authors[0].definition` equals `objSignedMessage.authors[0].definition`.
4. `peer_addresses` is populated (or updated) using `objSignedMessage.authors[0].authentifiers` paths together with `body.authors[0].definition`, producing a stored `(signing_paths, definition)` pair whose provenance is inconsistent between the signature-verified structure and the raw peer-supplied structure.

Note: full exploitation to concrete fund loss requires further tracing of every downstream consumer of `peer_addresses.definition`/`signing_paths` (in `wallet_defined_by_addresses.js` and `wallet_defined_by_keys.js`) that this ask-only investigation could not exhaustively confirm; the root-cause pattern (mixing verified and unverified fields of the same peer message, per CWE-347) is established with high confidence, but the precise downstream spend/inflation impact should be validated with a live Devin session tracing all reads of the `peer_addresses` table.
