### Title
DelegateAction Signature Hash Lacks Chain/Genesis Binding, Enabling Cross-Chain Replay of Meta-Transactions - ([File: core/primitives/src/action/delegate.rs])

### Summary
The inner signature scheme used for NEP-366 meta-transactions (`DelegateAction`/`DelegateActionV2`, signed and verified via `get_nep461_hash()`) binds only to `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. It contains no chain- or genesis-specific value. Replay protection for this inner signed payload depends entirely on the sender's access-key nonce state stored on whichever chain the outer transaction is submitted to. When that state is shared or duplicated across two NEAR-protocol-based networks (e.g., a state-forked/mirrored chain, or any chain instantiated from a snapshot of another chain's records before nonces diverge), a previously-signed `SignedDelegateAction`/`VersionedSignedDelegateAction` remains fully valid and can be wrapped in a fresh outer transaction (with a valid recent `block_hash` for the second chain) and replayed there, executing the delegated actions a second time on a chain the original signer never intended.

### Finding Description
`SignedDelegateAction::verify` and `VersionedSignedDelegateAction::verify` check the signature against `delegate_action.get_nep461_hash()`, computed purely from the `DelegateAction`/`DelegateActionV2` fields: [1](#0-0) [2](#0-1) 

None of these fields reference the chain the action is meant for — no genesis hash, no chain id, no block hash. Compare this to the *outer* `SignedTransaction`, whose validity is anchored to a specific chain via a recently-produced `block_hash`; this is precisely why nearcore's own `tools/mirror` transaction-mirroring utility must remap account keys and re-sign every mirrored transaction with a freshly-fetched `block_hash` from the target chain rather than replaying transactions byte-for-byte — the outer transaction's `block_hash` binding is what nearcore relies on for cross-chain replay protection: [3](#0-2) 

However, that `block_hash` binding exists only on the *outer* relayer-signed `SignedTransaction`. It provides no protection for the *inner* `SignedDelegateAction`, whose signature (`get_nep461_hash()`) is chain-agnostic by construction. Server-side, replay protection for a `DelegateAction` is enforced solely by comparing `delegate_action.nonce` against the sender's on-chain access-key nonce: [4](#0-3) 

Because this check is purely a function of state local to whichever chain processes the receipt, it offers no protection across two independently-running chains that happen to share (or start from a copy of) the same account/access-key state — for example a state-forked network (as produced by `neard view-state dump-state`, the same workflow `tools/mirror` is built to work around) before any key remapping/nonce-advancing occurs, or any other NEAR-protocol chain instance seeded from the same records. Anyone possessing a `SignedDelegateAction` (which is often carried publicly in a transaction/receipt, e.g. relayed via RPC) can wrap it in a new outer transaction addressed to the same `receiver_id`/`sender_id` pair and submit it to the second chain, and it will validate as long as the sender's access-key nonce there has not yet passed `delegate_action.nonce`.

### Impact Explanation
A successfully replayed `DelegateAction` executes arbitrary actions authorized by the original signer's access key against the second chain's state — this can include `AddKey` (granting the relayer/attacker a new full-access key on the victim's account on the second chain), `Transfer`, `FunctionCall`, or other actions embedded in `actions`. This constitutes unauthorized state/balance changes and unauthorized action execution on a chain the signer never intended to interact with, matching the impact class of "unauthorized state or balance change" via a submitted transaction/RPC path.

### Likelihood Explanation
Exploitation requires a second NEAR-protocol chain sharing account/access-key state with the chain the `DelegateAction` was originally signed for (state-forked networks, chain-snapshot-based test/staging environments, or any deployment reusing production account state) where the specific access key's nonce has not yet advanced past the delegated nonce. This is a realistic and anticipated operational scenario, as evidenced by nearcore itself shipping `tools/mirror` specifically to defend against replaying transactions from a source chain onto a state-forked target chain — but that tool's key-remapping/re-signing mitigation is designed around the *outer* transaction's `block_hash` binding and does not address the chain-agnostic nature of the *inner* `DelegateAction` signature.

### Recommendation
Include a chain-binding value in the NEP-461/NEP-366 signable payload for `DelegateAction`/`DelegateActionV2` — e.g., the genesis hash or a chain identifier — so that `get_nep461_hash()` in `core/primitives/src/action/delegate.rs` produces a distinct hash per chain, and update `SignableMessage` construction in `core/primitives/src/signable_message.rs` accordingly. This mirrors the mitigation recommended in the referenced report (binding the signed hash to `block.chainid`) and would make the inner meta-transaction signature as chain-specific as the outer `SignedTransaction`'s `block_hash` binding.

### Proof of Concept
1. On chain A, a user signs a `DelegateAction` (`sender_id=alice`, actions=[AddKey(attacker_key)], nonce=N, max_block_height=H) via `SignedDelegateAction::sign`, per `core/primitives/src/action/delegate.rs:92-95`.
2. A relayer wraps it in an outer `SignedTransaction` and submits it to chain A; it executes and the access key's nonce advances to N.
3. Chain B is a state-forked/snapshot copy of chain A's state taken before step 2 (or any independently-seeded chain sharing the same account/access-key records), so `alice`'s access-key nonce on chain B is still < N.
4. Anyone who observed the `SignedDelegateAction` bytes (e.g., from chain A's transaction/receipt data) wraps the *same, unmodified* inner payload in a new outer `SignedTransaction` addressed to `alice` on chain B, using a fresh valid `block_hash` from chain B (as `tools/mirror` itself does per `tools/mirror/README.md:31-41`).
5. `validate_delegate_action_key` in `runtime/runtime/src/actions.rs:561-611` finds `delegate_nonce (N) > current_nonce (<N)` and accepts it; `SignedDelegateAction::verify` succeeds because `get_nep461_hash()` never referenced chain A vs. chain B. The `AddKey` action executes on chain B, granting the attacker a key on `alice`'s account there without `alice`'s consent for that chain.

        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
    }
