This confirms the strongest analog: `expandMnemonic()` derives the private key directly from the textcoin mnemonic (`addrInfo.xPrivKey`) [1](#0-0) , and that same mnemonic is treated as the reusable bearer-secret controlling the funds sitting on `addrInfo.address` — whoever holds the plaintext mnemonic can call `receiveTextCoin()` and sweep the coins, as `receiveTextCoin`'s signer literally signs with `addrInfo.xPrivKey.privateKey` [2](#0-1) . `claimBackOldTextcoins()` prints this same bearer secret to the process log in cleartext, both on success and on failure, exactly mirroring the CVE-2017-8761 pattern of a server logging a reusable signed capability (tempurl signature) in operational logs [3](#0-2) .

### Title
Textcoin bearer mnemonic (equivalent to a private key) is written in cleartext to application logs during automatic reclaim - (File: wallet.js)

### Summary
`claimBackOldTextcoins()`, invoked periodically to reclaim unclaimed textcoins after a timeout, logs the full bearer `mnemonic` value via `console.log` both on success and failure paths. This mnemonic is not a public identifier — it deterministically derives the spending private key for the address holding the coin, so leaking it is equivalent to leaking a private key.

### Finding Description
A "textcoin" is a payment sent to a brand-new address whose private key is derived entirely from a 12-word `mnemonic` string, generated in `generateNewMnemonicIfNoAddress()` and persisted in the `sent_mnemonics` table [4](#0-3) . Anyone who possesses the mnemonic can call `expandMnemonic()` to reconstruct the exact same HD private key (`addrInfo.xPrivKey`) and definition (`["sig", {"pubkey": ...}]`) used to fund the coin [1](#0-0) . `receiveTextCoin()` uses this derived key directly to sign a spending transaction with no other authorization check [2](#0-1) , so knowledge of the mnemonic string is functionally identical to knowledge of a raw private key — the "reusable signature/capability" analog to the tempurl signature in the CVE.

`claimBackOldTextcoins(to_address, days)` runs on a schedule to sweep back textcoins that were never claimed. It selects each unclaimed `row.mnemonic` from the DB and, after attempting `receiveTextCoin`, unconditionally writes the mnemonic to stdout/log on both the error and success branches:
```
console.log("failed claiming back old textcoin "+row.mnemonic+": "+err);
...
console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
``` [3](#0-2) 

Any process, log-aggregation pipeline, crash reporter, or third party with read access to these logs (which is a normal, low-privilege access path — operators, monitoring tools, log shipping services, support staff) can extract the mnemonic and derive the spending key, exactly as CVE-2017-8761 allowed log readers to extract reusable tempurl signatures.

Contrast this with `eraseTextcoin()`, which correctly wipes the mnemonic from the DB once spent [5](#0-4)  — showing that the codebase already treats the mnemonic as sensitive material that should not persist, yet it is still permanently written to logs.

### Impact Explanation
Textcoin mnemonics are bearer secrets equivalent to private keys controlling live, funded on-chain addresses (bytes or private/indivisible assets, as handled in `receiveTextCoin`). Logging them in cleartext, especially in the automatic-reclaim sweep that runs specifically on funds that have NOT yet been claimed by the intended recipient, exposes still-spendable balances to unauthorized spending/theft by anyone with log read access — a direct concrete loss of funds, matching the required "unauthorized spending" impact bar.

### Likelihood Explanation
`claimBackOldTextcoins()` runs automatically for every unclaimed textcoin past the configured `days` threshold, requiring no attacker interaction with the chain itself — the exposure occurs purely as a side effect of normal wallet operation. Any deployment that centralizes or ships logs (common operational practice) would passively capture these values over time, making exploitation via log access straightforward whenever any log-reading party is untrusted or logs are inadvertently exposed (e.g., committed, shipped to third-party aggregators, or accessible via misconfigured permissions).

### Recommendation
Remove the mnemonic from both `console.log` statements in `claimBackOldTextcoins()`; log only the `unit`, `asset`, and truncated/opaque identifiers (e.g., a hash of the mnemonic or the derived address) instead of the raw secret. Audit other `console.log` call sites in `wallet.js` that reference `mnemonic` (e.g., in the email-sending and file-storage code paths) to ensure the bearer secret is never persisted to any log stream.

### Proof of Concept
1. Send a textcoin via `sendMultiPayment` to an email/text address without immediate claim; the mnemonic is stored in `sent_mnemonics` [4](#0-3) .
2. Let it remain unclaimed past the configured `days` threshold so the periodic sweep (`claimBackOldTextcoins`) processes it.
3. Observe the application log/stdout: the full mnemonic appears verbatim in the `"claimed back mnemonic "+row.mnemonic...` or `"failed claiming back old textcoin "+row.mnemonic...` line [3](#0-2) .
4. Any party with read access to that log can call `expandMnemonic(mnemonic)` [1](#0-0)  to derive the private key and, before the sweep completes or if it fails/races, spend the coin themselves via the same signing path used in `receiveTextCoin` [2](#0-1) .

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
