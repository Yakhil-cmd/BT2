### Title
Missing uniqueness check on `r of set`/`and`/`or`/`weighted and` members allows one signer to satisfy a multi-party threshold alone, enabling unauthorized spending of shared/multisig funds - (File: definition.js, wallet_defined_by_addresses.js)

### Summary
`Definition.validateDefinition()` and `Definition.validateAuthentifiers()` never check that the elements of an `and`, `or`, `r of set`, or `weighted and` construct are distinct. The same leaf condition (e.g. the same `sig`/`address` entry) can legally appear more than once at different signing paths. When such a definition is used to create a shared/cosigned address (`wallet_defined_by_addresses.js`), a dishonest cosigner can insert a duplicate of their own signing slot into what looks like an "R of N" threshold, so that they alone can satisfy the required count by re-using one signature at two different paths - without any cooperation from the other, honest cosigners. This is the same bug class as the reported "duplicate asset" LTV miscalculation: an unchecked duplicate silently corrupts a count used to decide how much trust/approval is actually required, but here the miscount directly authorizes spending of shared funds.

### Finding Description
In `definition.js`, `evaluate()` handles `and`/`or`/`r of set`/`weighted and` by iterating the `args`/`args.set` array and incrementing a counter (`count_options_with_sig`, `count_options_without_sig`, `weight_of_options_with_sig`) whenever a sub-branch resolves `bHasSig === true`. No code path verifies that the sub-branches are distinct addresses/pubkeys/definitions: [1](#0-0) 

The same absence of a uniqueness check exists in the actual signature-evaluation pass, `validateAuthentifiers()`'s `evaluate()` for `'r of set'`, which just counts how many of `args.set` verify against the supplied per-path authentifiers: [2](#0-1) 

Because each set element is independently addressed by its own path (`path+'.'+index`), a signer who owns the private key referenced by two different leaves can produce a valid signature for both paths using the same key/signature (for `sig`, both paths verify against the same `pubkey`; for a repeated `address` leaf pointing to their own address, they simply supply their own inner-definition signatures twice): [3](#0-2) 

On the wallet layer, `handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts an arbitrary `body.definition` proposed by any correspondent device, validates that declared signer addresses match the paths extracted from the definition, and calls `Definition.validateDefinition` (which, as shown above, does not check for duplicate members) before persisting the shared address and notifying the other cosigners: [4](#0-3) 

`extractAddressPathsFromDefinition()`, used to cross-check signer addresses against the definition, walks `and`/`or`/`r of set`/`weighted and` the same way, with no de-duplication of addresses across paths: [5](#0-4) 

As a result, a malicious proposer of a shared address can construct, e.g., `['r of set', {required: 2, set: [['address', Alice], ['address', Mallory], ['address', Mallory]]}]` (3 apparent members, "2 of 3" threshold) or an equivalent construct using `sig`, and present it to Alice as a normal 2-of-3 multisig. Mallory alone can satisfy `required: 2` by signing at both of his own paths, without ever needing Alice's signature, while Alice believes her cooperation is required to move funds out of the shared address.

### Impact Explanation
This allows a single dishonest cosigner to unilaterally spend funds from what other participants believe is an N-of-M multisig/shared address, resulting in unauthorized spending / theft of funds belonging to honest co-signers who deposited into the shared address trusting the advertised threshold. This is a concrete unauthorized-spending impact reachable purely from a device message / definition proposal exchanged between paired wallet devices, consistent with the required impact class (unauthorized spending, fund loss).

### Likelihood Explanation
The attack requires the attacker to be one of the initiators/cosigners of a new shared address (a normal, unprivileged role reachable by any wallet user who invites others to a shared/multisig wallet) and to craft a definition with a duplicate slot pointing to themselves. Honest cosigners are not expected to manually audit the raw definition tree for duplicate leaves-they rely on the wallet UI, which presents the definition as an "R of N" scheme and on `validateDefinition`/`handleNewSharedAddress` to reject malformed/deceptive definitions, neither of which checks for duplicates. This makes exploitation straightforward for any dishonest party in a shared-address setup.

### Recommendation
In `Definition.validateDefinition()` (definition.js), when validating `and`, `or`, `r of set`, and `weighted and`, reject definitions whose set/args elements are structurally identical (e.g., compare serialized/hashed sub-expressions) so the same leaf key/address cannot be counted more than once toward a threshold. Additionally, in `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`/`extractAddressPathsFromDefinition`, verify that all member addresses/paths declared as independent signers are distinct before accepting and persisting a proposed shared address definition.

### Proof of Concept
1. Mallory (device M) proposes a "shared address" to Alice (device A) via `create_new_shared_address` / `sendOfferToCreateNewSharedAddress`, with definition:
   `['r of set', {required: 2, set: [['address', Alice_addr], ['sig', {pubkey: Mallory_pubkey}], ['sig', {pubkey: Mallory_pubkey}]]}]`
   presented as a "2 of 3" wallet.
2. `validateAddressDefinitionTemplate`/`handleNewSharedAddress` accept it because `Definition.validateDefinition` never checks for duplicate `sig` leaves, and `extractAddressPathsFromDefinition`/signer matching only checks path-to-address consistency, not cross-path uniqueness.
3. Alice deposits funds into the resulting shared address, believing any spend needs at least 2 of {Alice, Mallory, "third slot"} to agree.
4. Mallory signs the spending unit at both of his `sig` paths (`r.1` and `r.2`) using the same private key, satisfying `required: 2` in `evaluate()` inside `validateAuthentifiers` without Alice's signature.
5. The unit passes `validateAuthentifiers`/`validateAuthor` in `validation.js`, and Mallory spends the shared funds unilaterally, defeating the intended multisig protection.

// Returns a map of signing_path -> address for every ["address", ...] leaf in the definition
function extractAddressPathsFromDefinition(arrDefinition) {
	var result = {};
	function traverse(arr, path) {
		if (!Array.isArray(arr) || arr.length < 2) return;
		var op = arr[0];
		var args = arr[1];
		switch (op) {
			case 'or':
			case 'and':
				if (Array.isArray(args))
					for (var i = 0; i < args.length; i++)
						traverse(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (args && Array.isArray(args.set))
					for (var i = 0; i < args.set.length; i++)
						traverse(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				result[path] = args;
				break;
			case 'hash':
				result[path] = 'secret';
				break;
			case 'in merkle':
				result[path] = ''; // empty address
				break;
		}
	}
	traverse(arrDefinition, 'r');
	return result;
}

		});
