### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` lookup in `MembershipHandler#find_or_create_team!` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` solely by `github_id`, without checking that the row's `organization` matches the organization whose webhook secret verified the current request. An attacker who controls a legitimate, independently-onboarded GitHub organization (with its own valid `webhook_secret`) can craft a `membership` webhook naming a `team.id` that collides with an existing `Team` belonging to a different organization (e.g., `shopify`) and add themselves as a member of that team, without ever touching Shopify's webhook secret.

### Finding Description
The broken binding: `Team.find(github_id: 77).organization == organization_that_verified_this_payload` should hold but does not.

Path: `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)`, i.e. `Handlers::MembershipHandler`, after `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` resolves the signing organization via `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. For a `membership` event this organization is `attacker-org` — the attacker's own onboarded org — and the check legitimately passes using attacker-org's own `webhook_secret`.

`MembershipHandler#process` then calls:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [1](#0-0) 

`find_or_create_by!` looks up by `github_id` alone; the block only runs on record creation. Since a `Team` row with `github_id: 77, organization: 'shopify'` already exists (created earlier from a legitimate `shopify` webhook), the lookup returns that row untouched — `team.organization` remains `'shopify'` even though the payload was verified for `attacker-org`. `process` then unconditionally executes `team.add_member(member)` [2](#0-1) , using `member = User.find_or_create_by_login!(params.member.login)` where `member.login` is attacker-controlled.

No guard anywhere (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema) checks that the existing `Team#organization` matches `params.organization.login`; the schema only requires `organization.login` be a `String`, and `verify_signature` only authenticates that *a* configured org's secret matches — it says nothing about which `github_id` team rows that org is entitled to mutate.

Impact chain: `Team#add_member` [3](#0-2)  appends the attacker's `User` to `shopify`'s team's `members`. Authorization is gated by `User#authorized?`:
```ruby
def authorized?
  @authorized ||= Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?
end
``` [4](#0-3) 
and `force_github_authentication` [5](#0-4) . If Shopify's team is one of `Shipit.github_teams` (the configured allow-list restricting access to the whole app, per `docs/setup.md`), the attacker — after simply logging in via GitHub OAuth as themselves — becomes `authorized?` and gains full access to the Shipit instance (stacks, deploys, API client creation) as if they were a genuine `shopify` team member.

### Impact Explanation
This is a cross-tenant authorization escalation: an attacker-verified webhook payload mutates a `Team` record owned by and gating access for a different, unrelated organization (`shopify`). If that team is part of `Shipit.github_teams`, the attacker obtains full authenticated access to the Shipit application (viewing/triggering deploys, creating API clients, etc.), constituting an authentication/authorization bypass into `Shipit.github_teams` — matching the High/Critical impact categories described (escalation into `Shipit.github_teams` authorization; and functionally an unauthorized write onto another organization's Team record). The attack is repeatable against any `team.id` the attacker can guess or observe (GitHub team IDs are sequential integers, often discoverable), and against any number of victim organizations sharing the same Shipit deployment.

### Likelihood Explanation
Preconditions are realistic: multi-tenant Shipit deployments genuinely support multiple organizations each with their own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications"), and the attacker only needs to be a legitimately onboarded tenant of that Shipit instance (no elevated privilege) plus knowledge/guess of a target `team.id`. Cost is a single crafted POST to `/webhooks` signed with the attacker's own valid secret. No live GitHub interaction or secret exfiltration is required, making this both cheap and repeatable.

### Recommendation
In `find_or_create_team!`, verify that `params.organization.login` matches the existing `Team#organization` before mutating; if it doesn't, reject/log the event instead of proceeding, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "Team #{team.github_id} organization mismatch"
  end
  Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```
Alternatively, scope the lookup by both `github_id` and `organization` (`find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), which also prevents silently overwriting the record's team metadata (`github_team=`) if a legitimate collision occurred.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (illustrative)
test "membership event from a different verified organization must not mutate another org's Team" do
  shopify_team = Shipit::Team.create!(github_id: 77, organization: 'shopify', slug: 'developers', name: 'Developers', api_url: 'https://x')

  # Simulate signature verification having passed for 'attacker-org' (its own valid secret)
  payload = {
    'action' => 'added',
    'team' => { 'id' => 77, 'name' => 'Developers', 'slug' => 'developers', 'url' => 'https://x' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'mallory' }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  shopify_team.reload
  assert_equal 'shopify', shopify_team.organization # binding claim: organization unchanged
  refute_includes shopify_team.members.map(&:login), 'mallory' # should fail today: currently INCLUDES mallory
end
```
Currently `shopify_team.members` includes `mallory` despite the payload being verified only for `attacker-org`, demonstrating the cross-org write. Fixing per the recommendation makes this assertion pass by rejecting/ignoring the mismatched-organization event.
