### Title
Cross-repository `Hook.emit` triggering via SHA-only commit lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `sha` string via `Commit.where(sha: params.sha)`, with no check that the authenticated webhook's repository matches the repository owning that commit's stack. Since `Commit#create_status_from_github!` → `add_status` unconditionally calls `Hook.emit(:commit_status, stack, ...)` and `Hook.emit(:deployable_status, stack, ...)` using `commit.stack`, a validly-signed webhook from repository A can trigger hook emission scoped to an unrelated stack B whenever a `Commit` row with the same `sha` exists for both stacks.

### Finding Description
The claimed binding is: `stack` passed to `Hook.emit` must equal the repository authenticated by the request's `webhook_secret`, i.e. `commit.stack.repository == repository_owner_verified_by(request)`.

Tracing the path:
- `WebhooksController#verify_signature` authenticates the *organization* (`repository_owner`, taken from `params.dig('repository','owner','login')`) against the `webhook_secret` configured for that org via `Shipit.github(organization: repository_owner)` and `GitHubApp#verify_webhook_signature`. [1](#0-0) 
- Once verified, `StatusHandler#process` is invoked with the raw JSON `params`, and looks up target commits by **sha alone**, with no repository/stack filter: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [2](#0-1) 
- `create_status_from_github!` calls `add_status`, which unconditionally computes `payload = { commit: self, stack:, status: new_status.state }` and calls `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)`, where `stack` is `commit.stack`, resolved through the model's own `belongs_to :stack` association — completely independent of which organization/repository was authenticated by `verify_signature`. [3](#0-2) [4](#0-3) 

Root cause: the sha-based lookup is global across the entire `commits` table, not scoped to the stack/repository that the webhook's signature verification actually authenticated. `verify_signature` proves that the *org named in the payload* holds the secret, but never re-validates that this org actually matches `commit.stack`'s repository for each row matched by sha.

Exploit precondition: the attacker needs the ability to produce a **genuinely GitHub-signed** `status` webhook for *some* org/repo that Shipit already trusts (i.e., `Shipit.github(organization: repository_owner)` resolves without raising `GithubOrganizationUnknown`). This is satisfiable without any Shipit privilege in a common real-world scenario: forks share commit SHAs with their upstream. If the attacker owns (or has push/CI access to) a repository under a trusted org/namespace that is a fork of, or shares history with, the victim's tracked repository, a real CI status event posted to the attacker's repository for a shared commit produces an authentic signature for the attacker's own repository — yet the `sha` value coincides with a `Commit` row belonging to the victim's stack. Because `StatusHandler` never checks `params['repository']['full_name']` against `commit.stack`, the victim stack's hooks fire.

Existing guards checked and found insufficient: `verify_signature`/`GitHubApp#verify_webhook_signature` only bind the *organization* to the secret, not to the specific `commit`/`stack` records processed; `drop_unhandled_event` only filters unregistered event types; the `ExplicitParameters` schema in `StatusHandler.params` only validates field types/presence, not repository ownership; there is no `stacks`-scope or `Repository`-equality check anywhere in this handler.

### Impact Explanation
An attacker who can get one validly-signed `status` webhook accepted for a trusted org (via their own repository/fork, no Shipit credentials needed) can force `Hook.emit(:commit_status, victim_stack, ...)` and `Hook.emit(:deployable_status, victim_stack, ...)` for a stack/tenant they never authenticated against, as long as a shared-SHA `Commit` row exists for that stack. This directly matches the "payload for one repository mutating another's stack" Critical category: any outbound webhook integrations registered on the victim stack (`Hook`s) receive fabricated status/deployable-status events, and `add_status`'s side effects (`stack.schedule_merges`) can be invoked for the victim stack based on attacker-controlled `state`/`context` values, potentially influencing continuous-delivery/merge scheduling (`schedule_continuous_delivery`) on a stack the attacker doesn't own. This is repeatable per shared SHA and scales to every stack that shares any commit history with a repo the attacker can produce signed events for.

### Likelihood Explanation
Requires: (1) Shipit configured to trust the attacker's org/repository for webhook signature verification (i.e., attacker has legitimate write/CI access to *some* repository under a namespace Shipit already has a GitHub App/secret for — plausible for org members with sandbox/fork repos, or any repo under a shared organization-wide GitHub App installation); (2) a `Commit` row with the same SHA already tracked under the victim's stack, which naturally occurs for forked/mirrored repositories or shared commit ancestry. No Shipit session, API token, or GitHub secret is required beyond what the attacker's own trusted repository already legitimately possesses. This is a moderate-likelihood, environment-dependent bug (not requiring signature forgery, only sha coincidence via fork history), and is repeatable for any shared commit.

### Recommendation
In `StatusHandler#process` (and analogously wherever commits are looked up purely by `sha`, e.g. `refresh_statuses!`/`CheckSuiteHandler` if similarly affected), scope the `Commit` lookup to the stack(s) whose repository matches `params.dig('repository','full_name')` (or `owner/name`), e.g. join through `Stack` and filter `stack.repository.full_name == payload_repository_full_name` before calling `create_status_from_github!`, rather than matching on `sha` alone.

### Proof of Concept
Minitest plan (`test/models/commit_hook_cross_repo_test.rb`, illustrative — actual file must live under `test/` per rules):
```ruby
test "status webhook for repo A must not emit hooks scoped to unrelated stack B sharing a sha" do
  victim_stack = shipit_stacks(:shipit) # repo org/victim
  attacker_repo_commit_sha = "deadbeef" * 5 # shared sha via fork history

  victim_commit = victim_stack.commits.create!(sha: attacker_repo_commit_sha, message: "shared commit")

  Hook.expects(:emit).with(:commit_status, victim_stack, has_entries(commit: victim_commit)).never
  # or, to demonstrate the bug (currently fails/succeeds unexpectedly):
  Hook.expects(:emit).with(:commit_status, victim_stack, anything)

  # Simulate a validly-signed status webhook whose repository is NOT victim_stack's repository
  params = ActionController::Parameters.new(
    sha: attacker_repo_commit_sha,
    state: "success",
    repository: { full_name: "attacker/fork" }
  )
  Shipit::Webhooks::Handlers::StatusHandler.new.call(params)

  # Assert Hook.emit was invoked with victim_stack despite the webhook only authenticating attacker/fork
end
```
Binding assertion: `params['repository']['full_name']` (attacker-authenticated repo) != `victim_commit.stack.repository.full_name`, yet `Hook.emit` receives `victim_stack` — proving the divergence.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
