### Title
`gh skill update` resolves remote skill sources by mutable `owner/repo` name with no repository-identity pinning, enabling repo-name-squatting takeover of trusted skill updates - (File: pkg/cmd/skills/update/update.go)

### Summary
This is the same bug class as the Canto `Turnstile.register`/`assign` finding: a piece of state (`NftData.registered` keyed to a mutable NFT owner) is trusted indefinitely with no re-registration or ownership-change check, so if the underlying "identity" changes hands, stale trust is misapplied. In `gh`, the analog is the skill lockfile / `SKILL.md` frontmatter metadata that records a skill's source as an `owner/repo` **name pair** at install time, with no persisted immutable identifier (e.g., GitHub repository/node ID). `gh skill update` re-resolves and re-downloads skill content purely by that mutable owner/repo string.

### Finding Description
`RecordInstall` stores only human-readable `owner`, `repo`, `SourceURL` (a formatted `owner/repo.git` string) and a `treeSHA` in `.skill-lock.json` — there is no repository ID captured: [1](#0-0) 

Similarly, `parseInstalledSkill` extracts `owner`/`repo` from `SKILL.md` frontmatter (`github-*` metadata) with no immutable ID field: [2](#0-1) 

`updateRun` then re-resolves the skill purely via `discovery.ResolveRef(apiClient, s.repoHost, s.owner, s.repo, "")` and `discovery.DiscoverSkills(...)`, matching remote entries back to the locally installed skill by `sourcePath`/`InstallName` string comparison — never by any stable identifier tied to the original repository: [3](#0-2) 

Because GitHub allows an `owner/repo` name to be freed and reclaimed (the owner renames or deletes the repository, or the account itself is renamed/deleted), an attacker can recreate a repository at the exact same `owner/repo` path once it becomes available. Any subsequent `gh skill update` for a user who previously installed a skill from that path will silently resolve to the attacker's new repository, download its `SKILL.md`/skill files, and overwrite the locally installed skill content, because nothing in the record (owner, repo name, or even `SourceURL`) is bound to the original repository's actual identity — the same "no re-registration/no ownership-change re-validation" gap the report describes, just manifesting as content-trust reuse instead of fee-registration reuse.

### Impact Explanation
A successful takeover of the `owner/repo` path lets an attacker's content flow through `gh skill update` (and initial re-install flows using the same lockfile/metadata) into a victim's `.agents` skill directories, i.e., untrusted file writes to disk under the guise of a trusted update, with no signal to the user that the repository "identity" has changed. This is a supply-chain-style content-injection vector into files that AI agents subsequently read/execute as instructions (`SKILL.md`).

### Likelihood Explanation
Requires the specific precondition that the original `owner/repo` becomes reclaimable (rename/delete/account transfer) and that an attacker notices and re-registers that exact path before the victim runs `gh skill update` again — a real-world scenario (classic "repo-jacking"), but conditional on the name becoming available, so likelihood is moderate rather than trivially exploitable at will.

### Recommendation
Persist and verify an immutable repository identifier (e.g., GraphQL `node_id`/numeric repo ID) alongside `owner`/`repo` in both the lockfile and `SKILL.md` metadata, and have `gh skill update` fetch and compare that ID before trusting/re-resolving a skill's source; warn or refuse the update if the ID has changed for a given `owner/repo`.

### Proof of Concept
Not independently executed against a live GitHub instance; based on static code review of the cited files, the mechanism described (name-only source binding with no repo-ID pinning across install → update) is directly verifiable in `internal/skills/lockfile/lockfile.go` and `pkg/cmd/skills/update/update.go`. Full end-to-end confirmation (actual repo-name reclamation + update run) was not performed in this analysis.

func RecordInstall(host, skillName, owner, repo, skillPath, treeSHA, pinnedRef string) error {
	lockPath, err := lockfilePath()
	if err != nil {
		return err
	}
	if err := os.MkdirAll(filepath.Dir(lockPath), 0o755); err != nil {
		return fmt.Errorf("could not create lock directory: %w", err)
	}

	lockedFile, unlock, err := acquireFLock()
	if err != nil {
		return err
	}
	defer unlock()

	f, err := readFrom(lockedFile)
	if err != nil {
		return err
	}

	now := time.Now().UTC().Format(time.RFC3339)

	existing, exists := f.Skills[skillName]
	installedAt := now
	if exists {
		installedAt = existing.InstalledAt
	}

	f.Skills[skillName] = entry{
		Source:          owner + "/" + repo,
		SourceType:      "github",
		SourceURL:       ghinstance.HostPrefix(host) + owner + "/" + repo + ".git",
		SkillPath:       skillPath,
		SkillFolderHash: treeSHA,
		InstalledAt:     installedAt,
		UpdatedAt:       now,
		PinnedRef:       pinnedRef,
	}

	return writeTo(lockedFile, f)
}
