### Title
`StatusHandler` writes commit status to any stack matching a SHA, without validating that the SHA belongs to the repository whose organization signed the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The Astaria report describes a class of bug where a check is performed against one binding (`L0k`/`A0k` for a single replaced lien) while the system's invariant actually depends on a *different, unchecked* binding (all `L_j`/`o_j` pairs across the whole stack). The generalizable bug class is: **the entity that is cryptographically verified is not the same entity that the subsequent write operation is scoped to.** Shipit's webhook pipeline exhibits the same class of flaw: signature verification is bound to an *organization* (derived from `repository.owner.login`), but the `status` event's mutation is bound only to a `sha` string with no repository/stack scoping at all.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/webhook secret using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or the `organization` sub-object), and verifies the raw payload's HMAC against that organization's secret: [1](#0-0) [2](#0-1) 

This proves only that *some organization configured in Shipit* produced this signature — it says nothing about which specific repository/stack the payload's other fields should be allowed to mutate.

Once verified, `Webhooks.for_event(event)` dispatches the parsed JSON to handlers [3](#0-2) . Most handlers scope their side effects to the repository named in the same payload via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` off `payload.dig('repository', 'full_name')` [4](#0-3) .

`StatusHandler`, however, does **not** use `stacks`/`repository_name` at all. It looks up commits globally by SHA across the entire Shipit instance and writes a status to every matching commit, regardless of which stack/repository it belongs to: [5](#0-4) 

`Commit#create_status_from_github!` unconditionally records the pushed state as an authoritative CI status for that commit's stack: [6](#0-5)  and `Commit#add_status` immediately re-evaluates deployability/merge scheduling based on the new status: [7](#0-6) . `Commit#deployable?` and `Commit#schedule_continuous_delivery` directly gate automatic deploys on this attacker-controlled status: [8](#0-7) [9](#0-8) .

**The broken binding, stated as an equality that should hold but doesn't:**

`organization_that_signed(payload) == repository_owner(sha_being_mutated)`

Signature verification proves the left side. The mutation (`Commit.where(sha: params.sha)`) is performed without checking the right side at all — it is a global, cross-tenant lookup keyed only by `sha`, a value fully under the sender's control and never bound to the verified organization.

### Impact Explanation
In a multi-organization Shipit deployment (`config/secrets.yml` supports configuring `github:` per-organization, each with its own `webhook_secret`, exactly as shown in `config/secrets.development.example.yml` [10](#0-9) ), an attacker who legitimately controls (or can trigger CI/status webhooks for) *Organization A*'s repository can send a validly-signed `status` webhook naming an arbitrary `sha`/`state`/`context`. If that `sha` coincides with a commit tracked under a stack belonging to *Organization B* (a different, unrelated tenant they have no access to — e.g. via a shared upstream commit, mirrored history, or a deliberately crafted commit with matching content pushed independently to both repos), the handler will record a fabricated "success" status for Org B's commit. Because `deployable?` and `schedule_continuous_delivery` react directly to this write, this can trigger an **unauthorized deploy** on Org B's stack if continuous deployment is enabled, or spoof a CI-gate status shown in the UI/merge queue for a repository the attacker has no legitimate write access to. This matches the "unauthorized deploy" and "unauthenticated read/write of stack state" impact bands.

### Likelihood Explanation
The likelihood is bounded by: (a) the deployment must be a multi-organization Shipit instance (a documented, supported configuration, not an undocumented mode) and (b) the attacker must be able to get a genuinely-signed `status` webhook fired for a SHA that also exists in a victim stack. Achieving a colliding SHA across independently-owned repositories generally requires shared commit history (forks, mirrors, vendored/cherry-picked commits) rather than a brute-force hash collision, which limits practical exploitation to related-repository scenarios. This is a real cross-tenant boundary violation in the code, but the practical precondition (attacker-controlled org configured in the same Shipit instance, with a SHA overlap) makes exploitation situational rather than trivial. I could not fully verify additional context (e.g., whether `Repository.from_github_repo_name` enforces any implicit uniqueness that would prevent identical SHAs from residing in two different `Repository`/`Stack` records) within the available index.

### Recommendation
`StatusHandler#process` should scope its `Commit` lookup to the repository asserted in the same payload (`payload.dig('repository', 'full_name')`), mirroring what `Handler#stacks`/`repository_name` already do for other handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent join through `Repository.from_github_repo_name(repository_name)`. This binds the mutated resource to the same repository/organization that was cryptographically verified, closing the gap between "what is checked" and "what is written."

### Proof of Concept
1. Configure Shipit for two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` (as documented in `docs/setup.md`/`config/secrets.development.example.yml`).
2. Attacker controls `org-a/repo-a`, tracked by Shipit, and can trigger a real, correctly-signed `status` webhook for it (e.g., via their own CI reporting a commit status through the GitHub API).
3. Attacker crafts (or already has) a commit whose SHA is identical to a commit that exists in `org-b/repo-b`'s tracked stack (e.g., because `repo-b` is a fork/mirror sharing history with `repo-a`), sets an arbitrary state (`success`) via that status webhook.
4. `WebhooksController#verify_signature` validates the signature using `org-a`'s webhook secret and passes: [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter, finds the matching commit under `org-b/repo-b`'s stack, and calls `create_status_from_github!`, marking it as `success`: [5](#0-4) [6](#0-5) .
6. If `org-b/repo-b`'s stack has `continuous_deployment` enabled, `schedule_continuous_delivery` fires and the commit is auto-deployed based on the forged status: [9](#0-8) .

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
