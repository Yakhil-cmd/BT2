### Title
Block-scoped index cache poisoned by liquidation socialization corrupts other users' borrow-index reads in the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`index-cache` is keyed by `{ timestamp: stacks-block-time, aid: asset-id }`, meaning every transaction within the same block that touches the same asset shares one cache slot for that block [1](#0-0) . During bad-debt socialization inside `liquidate`, `socialize-debt-asset` calls `vault-accrue` and overwrites this shared slot with the post-write-down (reduced) `lindex`/`index` values [2](#0-1) . Any other unrelated user's transaction later in the same block that reads `get-cached-indexes` for that asset id — e.g. via `scale-debt-for-liquidation` or other accrual-dependent logic — will retrieve the value the attacker's liquidation just wrote, not a value it independently computed [3](#0-2) .

### Finding Description
The cache key intentionally uses the block timestamp so all calls within one block reuse the same accrued index (an optimization, avoiding repeated interest accrual math). However, this creates a write-shared/read-shared slot across unrelated principals within a block. `socialize-debt-asset` is invoked as part of `liquidate`'s bad-debt path and force-writes a new (lower, post-socialization) `lindex` into `index-cache` for the affected `asset-id` [4](#0-3) . `scale-debt-for-liquidation`, used by a second, independent liquidator or borrower operation later in the same block, reads that exact slot via `get-cached-indexes` to compute `borrow-index` for repay/liquidation math [5](#0-4) . Because the liquidator who triggers socialization controls the ordering (front-running/back-running within the mempool) and the content written (which position, how much bad debt, when it triggers), a second party's transaction operating on a different position with the same debt asset id can be forced to use an index value that reflects someone else's socialization event rather than the index that would exist absent that first transaction.

### Impact Explanation
This is a shared-cache primed by one caller and consumed by another (in-scope class per the prompt's rules). It affects the correctness of liquidation/repay math (`scale-debt-for-liquidation`, `calc-final-liquidation-amounts`) for a victim's own, unrelated position within the same block, potentially causing incorrect debt-to-repay/collateral-seized calculations - either freezing/misvaluing a victim's position temporarily or enabling seizure amounts inconsistent with the true current index. This lands in the "temporary freezing of funds" / incorrect seizure impact class.

### Likelihood Explanation
Requires an attacker to trigger `liquidate` (bad-debt socialization path) on some position, and a second, unrelated liquidation/repay transaction for the same asset id to land in the same block afterward. On Stacks, block-level ordering can be influenced (fee bidding, or simply natural transaction batching), so this is plausible but requires two transactions on the same asset id landing in one block — a real but non-trivial precondition.

### Recommendation
I was not able to fully trace whether `index-cache` is also refreshed/validated independently at the start of every accrual-dependent call (I could not complete the grep to confirm whether `vault-accrue`/`get-cached-indexes` reads are always paired with a fresh write-then-read in the *same* call, or whether stale cross-transaction reads are actually exploitable in practice). Given this uncertainty, I recommend a Devin engineering session verify: (1) whether every accrual-dependent public function (`borrow`, `repay`, `liquidate`, `collateral-add/remove`) independently calls `vault-accrue`/refresh before consuming `get-cached-indexes`, and (2) whether `socialize-debt-asset`'s write can be observed/relied upon by a second, unrelated transaction's math in the same block. If confirmed exploitable, key the cache by transaction/position rather than sharing across all callers within a block, or re-derive indexes fresh for liquidation-critical calculations instead of trusting the shared per-block cache.

### Proof of Concept
Not independently confirmed with a runnable test; based on static code reading of `mainnet/contracts/market/v0-4-market.clar` lines 879-945 showing the write path (`socialize-debt-asset`) and read path (`get-cached-indexes`, `scale-debt-for-liquidation`) sharing the same `{timestamp, aid}`-keyed map. A concrete PoC would require: Tx1 (attacker) liquidates Position A into bad-debt socialization for asset X, writing a reduced index into `index-cache` for `{block-time, X}`; Tx2 (victim or another liquidator) in the same block acts on Position B with debt in asset X, and its `scale-debt-for-liquidation`/repay math consumes the index written by Tx1 instead of an index that reflects the state before Tx1.

**Note on confidence**: I was unable to complete verification of whether `get-cached-indexes` is populated fresh at the start of *every* top-level accrual-touching call (which would make the shared cache non-exploitable, since each call would overwrite it before reading it back for its own purposes) due to a tool error cutting off my final grep query. This finding should be treated as a lead requiring confirmation, not a fully validated vulnerability.

```text
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
```
