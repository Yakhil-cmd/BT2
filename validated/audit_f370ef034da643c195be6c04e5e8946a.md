### Title
Webhook signature verification uses `repository.owner.login` while all event handlers act on the unverified `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')`). [1](#0-0)  Once verification "passes," the very same raw, attacker-controlled body is handed to every registered handler, all of which resolve their target `Stack`/`Repository` from a *different* JSON field, `repository.full_name`, via `Handler#repository_name`. [2](#0-1)  Because these two fields are independent and both attacker-supplied, the organization whose credentials authenticate the request is not bound to the repository the payload actually mutates.

### Finding Description
`Shipit.github(organization:)` looks up a per-organization GitHub App config (multi-org deployments are explicitly documented and supported) and each org's `webhook_secret` is optional. [3](#0-2)  `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is blank: `return true unless webhook_secret`. [4](#0-3)  Test fixtures/docs confirm `webhook_secret` is commonly left `nil` for some orgs even in multi-org setups. [5](#0-4) 

The controller decides *which* org's app/secret to use purely from `params.dig('repository', 'owner', 'login')` (or `organization.login`), taken from the unauthenticated raw POST body, before the signature is validated: [6](#0-5) 

After that check "passes," the same `params` hash is dispatched to all handlers for the event: [7](#0-6) 

Every default handler (`PushHandler`, `PullRequest::*`, `CheckSuiteHandler`) resolves its target stacks from `repository.full_name` — a field completely independent of `repository.owner.login` used for signature selection: [2](#0-1) [8](#0-7) 

`StatusHandler` is even less scoped: it matches commits purely `Commit.where(sha: params.sha)` with no repository/organization check at all. [9](#0-8) 

**Binding broken (as an equality):**
`organization_used_for_signature (params.repository.owner.login)` ≠ `organization/repository_actually_acted_upon (params.repository.full_name)`.

Before the attacker's request: both fields are expected by GitHub to describe the same repository, so this equality normally holds and the signature genuinely authenticates the payload for that repository.
After the attacker's crafted request: `repository.owner.login` is set to any organization the Shipit instance is configured for that happens to have no `webhook_secret` (or whose secret the attacker can otherwise avoid needing), while `repository.full_name` is set to the victim's tracked repository. The equality no longer holds, yet the code trusts the request as if it did.

### Impact Explanation
An unprivileged external attacker (no GitHub write access, no Shipit account, no `ApiClient` token, no knowledge of the real webhook secret) who only needs to know:
1. the public name of *some* organization configured on the Shipit instance (or one whose secret was never set — the setup docs mark it "optional"), and
2. the public full name of the victim repository/stack they want to target,

can POST directly to `/webhooks` and have their forged payload processed as if it were genuinely signed by GitHub for the victim repository. Depending on event type this allows:
- `push`: forcing `GithubSyncJob` to run for an arbitrary tracked stack with an attacker-chosen `expected_head_sha`, potentially advancing `next_commit_to_deploy` and triggering an unauthorized continuous-deployment run via `trigger_continuous_delivery` [10](#0-9) , i.e. an unauthorized deploy.
- `status`: injecting fabricated commit statuses onto any commit matching a SHA in the datastore (no repository scoping at all in `StatusHandler`), which feeds directly into `Commit#deployable?` (`success? && !blocked?`) [11](#0-10)  and the `required_statuses`/CI-gating logic used to decide whether a commit is safe to deploy — enabling CI-check bypass and an unauthorized deploy.

This matches the report's Critical impact bucket: "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it exists specifically to receive unauthenticated-but-signed GitHub callbacks), so the only gate is `verify_signature`. The prerequisite — at least one configured organization without a `webhook_secret`, or one whose secret has leaked/is weak — is explicitly presented as an optional, low-friction setup choice in the project's own setup documentation, making this a realistic multi-tenant/multi-org misconfiguration rather than a purely theoretical scenario. No privileged credential, session, or GitHub App key is required by the attacker; only public knowledge of organization/repository names.

### Recommendation
Do not select the verification key/organization from unverified webhook body fields. Instead:
- Verify the HMAC signature using every configured organization's secret (or scope the webhook endpoint per-organization, e.g. `/webhooks/:organization`) and only proceed if a match is found.
- After verification succeeds, re-derive the organization/repository actually authorized for that secret and assert it matches `repository.full_name`/`organization.login` used by the handlers before dispatching, rejecting payloads where they diverge.
- For `StatusHandler`, scope commit lookup by the verified repository rather than by `sha` alone.
- Require a non-blank `webhook_secret` for every configured organization (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
Assume a multi-org Shipit deployment: `orgA` (attacker-known, `webhook_secret: nil`) and `victim-org` (secured, tracked stack `victim-org/victim-repo`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/main",
  "after": "<a real commit sha that exists on victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victim-org/victim-repo"
  }
}
```
- `verify_signature` computes `Shipit.github(organization: "orgA")`; since `orgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally. [4](#0-3) 
- `create` parses the body and dispatches it to `PushHandler`, which resolves stacks via `repository.full_name` = `"victim-org/victim-repo"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: ...)` for the victim stack, without ever validating a signature tied to `victim-org`'s actual secret. [12](#0-11) 

I was not able to further verify, within this engine's code alone, exactly how far `trigger_continuous_delivery` propagates into an actual deploy without additional guardrails elsewhere in the stack/deploy state machine (e.g., locking, `deployment_checks_passed?`); a full end-to-end confirmation of "unauthorized deploy actually runs" would need dynamic testing against a configured multi-org instance.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
