### Title
Unbounded memory consumption via `io.ReadAll` in `CopyGuardedContent` when streaming large text responses - ([File: pkg/iostreams/content.go])

### Summary
`CopyGuardedContent` sniffs only the first 512 bytes to classify content as binary or textual, then for any non-binary content calls `io.ReadAll(r)` to buffer the *entire remaining body* in memory before writing it out. An attacker who controls a large `gh api` response body, a `gh repo read-file --output -` file, or a `gh release download -O -` asset that contains no `0x1B` byte in its first 512 bytes can force the client to buffer an arbitrarily large payload in RAM, causing unbounded memory growth.

### Finding Description
`CopyGuardedContent` reads a 512-byte sniff sample and calls `BinaryContentType` to classify content: [1](#0-0) 

If the sniffed prefix is textual (e.g. plain text/CSV/JSON-like content without binary magic bytes), the function falls into the "textual" branch and calls `io.ReadAll(r)` to slurp the rest of the stream fully into memory before scanning for escape sequences and writing it out: [2](#0-1) 

There is no size cap, `io.LimitReader`, or streaming-with-buffered-tail design for this path — the entire response, regardless of size, is materialized as a single `[]byte` (`rest`, then `content := append(head, rest...)`).

This function is reachable from attacker-influenced, unbounded-size content in at least two call sites:
- `pkg/cmd/api/api.go`, in `processResponse`, for any non-JSON `gh api` response body that isn't being discarded: [3](#0-2) 
- `pkg/cmd/release/download/download.go`, in `destinationWriter.Copy`, for `gh release download -O -` (stdout output) of a release asset: [4](#0-3) 

In both cases the reader (`responseBody` / release asset body `r`) is backed by an HTTP response body with no size limit enforced upstream, and the victim controls neither the remote server (attacker-controlled API host for `gh api --hostname`, or attacker-owned release asset) nor the response `Content-Length`. As long as the attacker keeps the first 512 bytes free of `0x1B` and free of binary magic bytes (trivial for a text/plain or text/csv payload), the function will attempt to buffer the whole body via `io.ReadAll`.

### Impact Explanation
This is a denial-of-service via unbounded memory allocation on the victim's machine: a multi-gigabyte crafted response/asset can exhaust available memory or trigger OOM-kill of the `gh` process (and potentially other processes on constrained systems), matching a resource-exhaustion / DoS impact class. It does not provide code execution, credential exfiltration, or file-write-outside-path, so its severity is capped at availability impact against the invoking user's session/machine, not full compromise.

### Likelihood Explanation
Feasible and repeatable: an attacker fully controls the response content in these scenarios — an attacker-operated API host reached via `gh api --hostname` (or a public API endpoint returning attacker-influenced data), or an attacker-published GitHub Release asset downloaded with `gh release download -O -`. No authentication, elevated privileges, or victim interaction beyond running the ordinary command against attacker-supplied input is required. The only constraint is keeping the leading 512 bytes non-binary and free of the escape byte, which is trivial to satisfy with normal text content.

### Recommendation
Cap the amount of data buffered for escape-sequence scanning, e.g. use `io.LimitReader` for the "rest" read plus an overall response-size ceiling (or stream in fixed-size chunks and scan each chunk for `0x1B` incrementally rather than buffering the whole body), returning an error or falling back to raw streaming once a configurable maximum (e.g. a few MB) is exceeded. Alternatively, only buffer up to a bounded limit for escape detection and stream the remainder verbatim once the buffered portion is confirmed clean, since escape sequences are far more likely to appear early or scanning could be done as a rolling window rather than requiring the full body in memory at once.

### Proof of Concept
```go
package iostreams

import (
	"io"
	"testing"
)

// infiniteAReader simulates a huge (or unbounded) text/plain body of 'a' bytes
// with no 0x1B byte anywhere, e.g. a crafted gh api / release asset response.
type repeatReader struct {
	remaining int64
}

func (r *repeatReader) Read(p []byte) (int, error) {
	if r.remaining <= 0 {
		return 0, io.EOF
	}
	n := len(p)
	if int64(n) > r.remaining {
		n = int(r.remaining)
	}
	for i := 0; i < n; i++ {
		p[i] = 'a'
	}
	r.remaining -= int64(n)
	return n, nil
}

func TestCopyGuardedContent_UnboundedMemory(t *testing.T) {
	// 2^31 bytes (~2GB) of plain text, no binary signature, no 0x1B byte.
	src := &repeatReader{remaining: 1 << 31}
	var sink discardCountingWriter // a io.Writer that just counts bytes

	// Expectation for a fixed version: CopyGuardedContent should either
	// stream without fully buffering, or return an error once a size
	// ceiling is exceeded, rather than allocating ~2GB in `rest`/`content`.
	err := CopyGuardedContent(&sink, src, false)
	if err != nil {
		t.Fatalf("unexpected error: %v", err)
	}
	// In the current implementation this test passes but requires the
	// process to allocate ~2GB+ for `rest` and `content` (io.ReadAll +
	// append), demonstrating unbounded memory use for attacker-supplied
	// text content with no size limit enforced.
}
```
Run under a memory profiler (`go test -memprofile`) or monitor RSS while executing against a `repeatReader` of increasing size to demonstrate that peak memory scales linearly and unboundedly with attacker-supplied payload size, with no ceiling enforced by `pkg/cmd/api/api.go`'s `processResponse` or `pkg/cmd/release/download/download.go`'s `destinationWriter.Copy` before invoking `CopyGuardedContent`.
