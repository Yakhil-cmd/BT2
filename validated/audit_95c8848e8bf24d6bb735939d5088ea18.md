### Title
Webhook signature is verified against an organization taken from the untrusted payload while handlers act on a different, unchecked repository/organization field from the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the unauthenticated, attacker-supplied request body. Once verification passes, the individual `Webhooks::Handlers` act on a completely different field of that same body — `repository.full_name` for repository-scoped handlers, or `organization.login` for `MembershipHandler` — without ever re-checking that it belongs to the organization whose secret validated the signature.

### Finding Description
`repository_owner` is derived purely from attacker-controlled JSON: [1](#0-0) 

It is used only to pick the GitHub App config/secret for signature verification: [2](#0-1) 

`Shipit.github` supports a documented multi-organization config schema keyed by organization login, each with its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

Any tenant organization legitimately configured on the instance knows its own `webhook_secret` and can therefore compute a valid `X-Hub-Signature` for an arbitrary raw JSON body it authors itself, since it fully controls both the payload and the signing.

Once `verify_signature` passes, the event is dispatched to handlers, which derive the resource to act on from a *different* field of the same body, with no cross-check against `repository_owner`:
- Generic repository handlers use `repository.full_name`: [5](#0-4) 
- `PushHandler` uses that `stacks` scope to sync arbitrary stacks: [6](#0-5) 
- `MembershipHandler` trusts `params.organization.login` and `params.member.login` outright to mutate `Team` membership: [7](#0-6) 

Nothing binds `repository.owner.login` (verified side) to `repository.full_name` / `organization.login` (acted-upon side) — an attacker can set them to different organizations within one payload.

### Impact Explanation
This breaks the trust equality: `organization used to select webhook_secret for signature verification` == `organization/repository actually mutated by the handler`. Concretely, an org "attacker-org" that is one of the configured tenants on a multi-org Shipit instance can:
- Forge a `push` event with `repository.owner.login = "attacker-org"` (verified with attacker-org's own known secret) but `repository.full_name = "victim-org/victim-repo"`, causing `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` against the victim's stack, forging what Shipit believes is the current branch head for deploy decisions.
- Forge a `membership` event with `organization.login` set to the victim organization/team identifiers matching `Shipit.github_teams` (the mechanism gating application access via `Shipit::Authentication#force_github_authentication`), adding an attacker-controlled GitHub login to a team that authorizes access to the Shipit instance, or removing legitimate members — a direct escalation into `Shipit.github_teams` authorization.

This matches the High-severity category "escalation into `Shipit.github_teams` authorization," and edges toward unauthorized deploy behavior via forged push/sync events, without requiring any session, `ApiClient` token, or the victim's own `webhook_secret`.

### Likelihood Explanation
Requires only that the Shipit instance is configured with the multi-organization GitHub config (documented and supported feature) and that the attacker's own organization is one of the legitimately configured tenants — a realistic scenario for any shared/multi-tenant Shipit deployment. No repository write access, no session, and no knowledge of the victim's secret are needed; the attacker only needs their own org's secret, which they inherently possess.

### Recommendation
After verifying the signature with the organization derived from `repository_owner`, re-validate that every organization/repository-identifying field consumed downstream (`repository.full_name`'s owner, `organization.login`, etc.) matches that same verified organization before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Shipit is configured with two tenants, e.g. `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `config/secrets.development.example.yml` multi-org schema).
2. Attacker crafts a raw JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully using attacker-org's own secret (`app/controllers/shipit/webhooks_controller.rb:24-30`, `:59-62`).
5. `PushHandler#process` looks up stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and triggers `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the signature only proving authenticity for `attacker-org`, never for `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
