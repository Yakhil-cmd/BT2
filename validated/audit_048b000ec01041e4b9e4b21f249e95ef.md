### Title
Unscoped commit lookup in `StatusHandler` lets a webhook authenticated for one GitHub organization forge CI status on commits belonging to a different, unrelated stack/repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by looking up the GitHub App/organization keyed off the payload's `repository.owner.login` (or `organization.login`) field and checking the HMAC signature against that organization's `webhook_secret`. Once verification passes, the *entire* raw JSON payload is handed to the event handler unmodified. `StatusHandler`, unlike `PushHandler` and `CheckSuiteHandler`, never re-derives or checks the `repository` field from the payload — it looks up commits solely by `params.sha` across the whole database and writes a CI status to whatever `Commit` record matches, regardless of which stack/repository it belongs to.

### Finding Description
The verification step binds trust to "the organization owning the pushed `repository` field": [1](#0-0) [2](#0-1) 

But the actual mutation performed by `StatusHandler` is scoped only by commit SHA, with no repository/organization check at all: [3](#0-2) 

Compare this with the base `Handler` class, which does provide a `stacks`/`repository_name` helper that scopes lookups to `payload.dig('repository', 'full_name')`: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` correctly use this `stacks` scope: [5](#0-4) [6](#0-5) 

`StatusHandler` is the outlier: its `params` block doesn't even require a `repository` key, and `process` performs an unscoped `Commit.where(sha: params.sha)` across the entire installation, then calls `create_status_from_github!` on every match.

**The broken equality:** `organization authenticated by HMAC (repository.owner.login of the payload) == repository whose Commit rows are written (sha lookup, unscoped)`. GitHub's Statuses API (`POST /repos/{owner}/{repo}/statuses/{sha}`) lets any user with push/write access to a repository they control set an arbitrary `sha` value — GitHub does not verify that the SHA corresponds to a real commit in that repository before emitting the `status` webhook, and commit SHAs of public repositories/stacks are public information. An attacker who legitimately controls one Shipit-tracked repository/organization (with a correctly configured, real webhook secret) can therefore trigger a properly-signed `status` webhook whose `sha` value is copied from a completely different victim stack tracked by Shipit under a different organization/repository.

### Impact Explanation
Shipit uses commit CI `Status` records to gate whether a commit is deployable (required-context checks, merge-queue gating, etc.). By injecting a forged `success` status onto a victim commit that the attacker does not own or have any push access to, the attacker can make an otherwise CI-failing or unreviewed commit in the victim's stack appear to have passed CI, enabling an unauthorized deploy of that commit through the normal Shipit UI/API by any operator relying on the (now falsified) status. This crosses a repository boundary using only a webhook signature that was legitimately obtained for an unrelated repository, matching the "unauthorized deploy" Critical-impact category.

### Likelihood Explanation
The prerequisites are all attacker-controllable without any Shipit credentials: (1) push/admin access to one's own GitHub repository already registered as a Shipit stack (a legitimate, low-privilege scenario many Shipit deployments support for multiple teams/orgs), (2) knowledge of a target commit SHA in another stack (trivially obtainable for public repositories, or via any other information leak of a SHA), and (3) the ability to call the standard GitHub Statuses API on one's own repo. No `webhook_secret`, `api_clients_secret`, or GitHub App key needs to be known or stolen by the attacker — GitHub computes and sends the valid signature itself for the attacker's own repository event.

### Recommendation
`StatusHandler` should scope its commit lookup to the repository identified in the webhook payload the same way `PushHandler`/`CheckSuiteHandler` do (via the base `Handler#stacks` helper keyed on `repository.full_name`), rejecting or ignoring updates for commits that do not belong to a stack under that repository. More generally, every webhook handler should validate that the payload's `repository`/`organization` field used for the initial signature verification matches the entity referenced when performing the actual mutation, rather than trusting SHA/ID fields in isolation.

### Proof of Concept
1. Attacker registers/owns `attacker-org/attacker-repo` as a Shipit stack with a valid, correctly-configured GitHub App webhook (`webhook_secret` known only to GitHub and Shipit, not to the attacker).
2. Attacker identifies a commit SHA `S` belonging to `victim-org/victim-repo`'s currently pending/undeployed commit (public SHA).
3. Attacker calls `POST https://api.github.com/repos/attacker-org/attacker-repo/statuses/S` with `state: "success"`, `context: "<required-ci-context>"`. GitHub accepts this even though `S` isn't a commit in `attacker-org/attacker-repo`, and delivers a `status` webhook to Shipit signed with `attacker-org`'s real, valid webhook secret.
4. `WebhooksController#verify_signature` verifies the signature successfully against `attacker-org`'s webhook secret (`repository_owner` == `attacker-org`).
5. `StatusHandler#process` executes `Commit.where(sha: S)`, which matches the victim's `Commit` record in `victim-org/victim-repo`'s stack, and calls `create_status_from_github!`, writing a fabricated "success" status onto it — even though the attacker has no access to `victim-org/victim-repo` and its webhook secret was never used.
