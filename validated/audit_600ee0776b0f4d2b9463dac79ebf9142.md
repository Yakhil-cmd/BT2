### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every event handler (`PushHandler`, `StatusHandler`, `Handler#stacks`, etc.) instead resolves the target `Stack`/`Repository` using a *different* JSON field, `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, so the "organization whose secret authenticated the request" and "the repository that is actually written to" are two independently-attacker-controlled strings within the same unsigned/under-verified request.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
selects the signing organization via `repository_owner`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly **bypasses signature verification entirely when no `webhook_secret` is configured for that organization**: [3](#0-2) 
`return true unless webhook_secret` — meaning for any GitHub organization entry in `Shipit.github` that has a blank/unset `webhook_secret` (documented as optional in `docs/setup.md`), signatures are not checked at all, regardless of the value of `X-Hub-Signature`.

Meanwhile, once `create` proceeds, the actual work is dispatched to handlers using an entirely different payload field: [4](#0-3) 
`repository_name = payload.dig('repository', 'full_name')`, used by `Handler#stacks` to look up the `Repository`/`Stack` to act on, and directly by `PushHandler#process`: [5](#0-4) 

Nothing in the controller or in `Handler` validates that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` used for the signature check. An attacker who knows (or can guess) that a particular multi-tenant Shipit installation has at least one configured GitHub organization with no `webhook_secret` set can:
1. Set `repository.owner.login` (and/or top-level `organization.login`) to that unsecured organization's name so `verify_webhook_signature` unconditionally returns `true`.
2. Set `repository.full_name` to `"<victim-org>/<victim-repo>"`, an arbitrary repository tracked under a *different*, secured organization.
3. Send a forged `push` (or `status`, `check_suite`, etc.) event; `WebhooksController#create` accepts it (no valid signature required), and the handler resolves the victim `Stack` purely from `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` — i.e., it can drive GitHub sync / status logic for a stack whose organization DID configure a webhook secret, without ever presenting a valid signature for that organization.

This is directly analogous to the reported Solana bug's pattern: a value that gates/authorizes an operation (`is_closed()`/webhook signature-org) is checked on one binding (the specific `RewardPool`/`repository.owner.login`) while the operation is actually applied against a different, unguarded target (all pools in the loop/`repository.full_name`) — breaking the equality that should hold between "entity verified" and "entity acted upon."

### Impact Explanation
This lets an unprivileged, unauthenticated network attacker forge GitHub webhook events (push, status, check_suite, membership, pull_request, etc.) against any `Stack`/`Repository` tracked by the Shipit instance, as long as one org in the multi-org config has no `webhook_secret`. Consequences include: forcing `GithubSyncJob` to run for arbitrary commits/branches, injecting spoofed commit statuses (`StatusHandler`), or driving review-stack archive/unarchive logic (`labeled_handler.rb`) for a repository that the attacker does not own — enabling unauthorized state changes on that stack's sync/status pipeline. This maps to escalation into deploy/stack-state manipulation without proper cross-repo authorization, matching the "High" bar (unauthenticated manipulation of stack state through the app's own trust boundary).

### Likelihood Explanation
Requires only that the Shipit deployment configures multiple GitHub organizations under `Shipit.github`, at least one of which has no `webhook_secret` set (explicitly documented as optional, and a legitimate low-security/dev configuration). No credentials, tokens, or repository access are needed by the attacker — only knowledge or a guess of an org name lacking a secret and the target `full_name`. Given `webhook_secret` is optional-by-design and organizations are added incrementally, this is a plausible operational state, though it does depend on this specific multi-org/missing-secret configuration.

### Recommendation
Bind signature verification to the same identity that is later used to resolve state changes: derive the authorizing organization strictly from `repository.full_name`'s owner segment (or otherwise cross-validate `repository.owner.login`/`organization.login` against `repository.full_name`) before dispatching to handlers. Additionally, reconsider silently bypassing verification (`return true unless webhook_secret`) — at minimum, require that any organization used to satisfy verification for a request also matches the repository/organization being mutated by the handler.

### Proof of Concept
Assume `Shipit.github` config has two orgs: `secure-org` (webhook_secret set) with tracked repo `secure-org/prod-app`, and `open-org` (no webhook_secret configured).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-invalid

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "secure-org/prod-app"
  }
}
```
- `repository_owner` resolves to `open-org`.
- `Shipit.github(organization: 'open-org').verify_webhook_signature(...)` returns `true` immediately because `open-org` has no `webhook_secret` (`return true unless webhook_secret`).
- `PushHandler#process` (via `Handler#stacks`/`repository_name`) resolves `secure-org/prod-app`'s tracked `Stack` and calls `stack.sync_github(expected_head_sha: 'deadbeef...')`, even though no valid signature for `secure-org` was ever presented. [6](#0-5) [3](#0-2) [4](#0-3) [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
