### Title
Cross-organization webhook confused deputy: an org with no `webhook_secret` can forge a `pull_request.labeled` event naming any victim `repository.full_name`, causing `Shipit::Repository.from_github_repo_name` + `stack.archive!` to run unauthenticated against a victim's ReviewStack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` derives the organization used for signature verification from the attacker-controlled field `params.dig('repository','owner','login')`, while the `LabeledHandler` resolves the repository to mutate from a completely separate attacker-controlled field, `params.repository.full_name`. Because GitHub webhook payloads normally keep these two values consistent, the application never checks that they refer to the same organization, letting an attacker who controls (or names) an org with no configured `webhook_secret` sign for that org (or skip signing entirely) while naming an arbitrary victim repository/organization as the mutation target.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:

`organization_verified_by_signature (params.repository.owner.login)` **should always equal** `organization_of_mutated_repository (params.repository.full_name.split('/').first)`.

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` via `repository_owner` (line 59-62): `params.dig('repository','owner','login') || params.dig('organization','login')`. This is a raw field from the attacker-supplied JSON body — nothing requires it to match anything else in the payload.
2. It calls `Shipit.github(organization: repository_owner)` (lib/shipit.rb:170-181) to fetch that organization's `GitHubApp` config, then `github_app.verify_webhook_signature(...)` (lib/shipit/github_app.rb:76-83): `return true unless webhook_secret`. If the named organization has no `webhook_secret` configured (the Q4 precondition), verification trivially returns `true` — no `X-Hub-Signature` header, or any header value, is required.
3. On success, `WebhooksController#create` (line 10-15) does `params = JSON.parse(request.raw_post)` and dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the **entire** attacker-controlled JSON, not just the portion tied to `repository_owner`.
4. `LabeledHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:65-68) calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. The `ExplicitParameters` schema for this handler (lines 8-39) only `requires :repository { requires :full_name, String }` — it never requires or cross-checks `repository.owner.login` against the value used for signature verification.
5. `Shipit::Repository.from_github_repo_name` (app/models/shipit/repository.rb:53-56) does a raw `find_by(owner:, name:)` lookup with no ownership/consent check tying it back to the organization that was actually verified in step 2.
6. `LabeledHandler#handle` (lines 49-57) then calls `stack.archive!` on the resolved victim `ReviewStack` if `archive?` evaluates true based on the victim repository's own real `provisioning_behavior` and the attacker's crafted `pull_request.labels` — logic entirely under attacker control in the payload.

Because steps 1-2 verify signature against the org identified by `repository.owner.login`, but steps 3-6 mutate whatever repository `repository.full_name` names, an attacker can set `repository.owner.login` to an org with no `webhook_secret` (satisfying/bypassing verification for free) while setting `repository.full_name` to `"victim-org/victim-repo"` — a repository belonging to a completely different, properly-secured organization. No guard in `verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema, or `Repository`/`Stack` validations checks that the two fields agree, because model-level `Repository` validations only constrain the format of `owner`/`name` strings, not their relationship to the verified webhook source.

Attacker's exact request:
```
POST /webhooks
X-Github-Event: pull_request
(no X-Hub-Signature header, or any garbage value)
{
  "action": "labeled",
  "number": 1,
  "pull_request": {
    "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
    "additions": 0, "deletions": 0,
    "head": { "sha": "...", "ref": "..." },
    "user": { "login": "attacker" },
    "assignees": [],
    "labels": [{"name": "<label matching victim repo provisioning_label_name>"}]
  },
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org-with-no-secret" }
  },
  "sender": { "login": "attacker" }
}
```

### Impact Explanation
This lets an attacker whose organization has no `webhook_secret` configured (or who names any such misconfigured org in the request) force a write — `stack.archive!` — against a `ReviewStack` belonging to an entirely unrelated victim organization that does enforce a strict `webhook_secret`. This matches the Critical category "a payload for one repository mutating another's stack/task" and is fully unauthenticated (zero valid signature material for the victim org). It is repeatable against any repository in the Shipit database as long as one org with a missing/blank `webhook_secret` is configured somewhere in the deployment, and other pull_request handlers (`ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `EditedHandler`, `AssignedHandler`) share the identical `Repository.from_github_repo_name(params.repository.full_name)` pattern and are equally exposed.

### Likelihood Explanation
Preconditions: the Shipit deployment must have at least one organization configured in `secrets.github` with a blank/absent `webhook_secret` (the Q4 precondition) — this is a realistic multi-tenant misconfiguration, e.g. a newly onboarded org or a legacy/default entry. The attacker needs no Shipit credentials, no GitHub App secrets, and no relationship to the victim org — they only need to know or guess that such an under-configured org's name exists (organization names/config are often discoverable, e.g. via error messages, existing webhook logs, or trial-and-error since `GithubOrganizationUnknown` responses (422) versus successful bypass (200) leak whether an org is configured with no secret). The victim's `full_name` is either public knowledge or directly enumerable through Shipit's own UI/API. This is a low-cost, fully repeatable attack requiring only crafted HTTP POSTs.

### Recommendation
Enforce that the organization used to verify the webhook signature is the *same* organization that owns the repository being mutated:
- In `WebhooksController#verify_signature`, or in `Handler#initialize`, derive the repository/organization strictly once and validate that `Repository.from_github_repo_name(payload['repository']['full_name'])&.owner` matches the verified `repository_owner`/GitHub App organization before dispatching to any handler.
- Additionally, do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank for organizations that own registered `Repository` rows; treat a missing `webhook_secret` as a hard misconfiguration (raise/alert) rather than an implicit signature bypass.
- Require `repository.owner.login` in every handler's `ExplicitParameters` schema and assert it matches the leading segment of `repository.full_name`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, hypothetical since `test/**` is out of scope for grading but described for reproduction):
```ruby
test "labeled webhook with no-secret attacker org can archive an unrelated victim repository's review stack" do
  # Arrange: victim org has a real, strict webhook_secret
  # Arrange: attacker org is configured in secrets.github with webhook_secret: nil
  victim_repo = shipit_repositories(:victim_org_repo) # owner: 'victim-org', provisioning_behavior_prevent_with_label
  victim_stack = create_review_stack(repository: victim_repo, active: true) # not yet archived

  body = {
    action: "labeled",
    number: 1,
    pull_request: {
      id: 1, number: 1, url: "http://x", title: "t", state: "open",
      additions: 0, deletions: 0,
      head: { sha: victim_stack.sha, ref: victim_stack.branch },
      user: { login: "attacker" },
      assignees: [],
      labels: [{ name: victim_repo.provisioning_label_name }]
    },
    repository: {
      full_name: victim_repo.github_repo_name,          # "victim-org/victim-repo"
      owner: { login: "attacker-org-with-no-secret" }    # forged org, no webhook_secret
    },
    sender: { login: "attacker" }
  }.to_json

  # No X-Hub-Signature header at all
  post shipit.webhooks_path, params: body, headers: { 'X-Github-Event' => 'pull_request', 'CONTENT_TYPE' => 'application/json' }

  assert_response :ok
  assert_predicate victim_stack.reload, :archived? # equality violated: attacker-org's (no-)signature authorized a write to victim-org's stack
end
```
Assertions on both sides of the binding: before the request, `repository_owner_used_for_signature = "attacker-org-with-no-secret"` and `organization_of_mutated_repository = "victim-org"` are unequal, yet the request still succeeds (`200 OK`) and `victim_stack.archived?` becomes `true`, proving the divergence is exploitable end-to-end with zero valid signature material for the victim organization.
