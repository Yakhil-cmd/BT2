### Title
Webhook cross-organization repository confusion: HMAC signature is verified against `repository.owner.login`/`organization.login`, but stack resolution uses the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
Shipit supports hosting multiple GitHub organizations/tenants behind one instance, each with its own configured GitHub App and `webhook_secret` (confirmed by `test/dummy/config/secrets_double_github_app.yml`, which defines distinct `OrgOne`/`OrgTwo` app configs). Incoming webhooks are authenticated per-organization, but the organization used to select the verification secret is read from a different payload field than the one used afterward to resolve which repository/stack the event actually acts on. This breaks the binding: `organization that authenticated == repository that is written`.

### Finding Description
`WebhooksController#verify_signature` selects the `GithubApp` (and therefore the HMAC secret) using: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `repository.owner.login` (or `organization.login`) in the raw JSON body, and `Shipit.github(organization: repository_owner)` picks the tenant-specific `webhook_secret` used to validate `X-Hub-Signature`.

However, every webhook `Handler` (base class used by `PushHandler`, pull-request handlers, etc.) resolves the *target* repository/stack from an entirely separate field, `repository.full_name`, without ever re-checking it against the organization that was used for signature verification: [3](#0-2) 

Because both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same signed JSON body, and the signature only proves the payload was produced with *some* organization's secret, an operator/admin of one tenant organization (`OrgOne`) — who legitimately knows or controls `OrgOne`'s `webhook_secret` because they configured that org's GitHub App integration — can craft a payload where:
- `repository.owner.login = "OrgOne"` (so `verify_signature` selects and validates against `OrgOne`'s secret, which the attacker knows), while
- `repository.full_name = "OrgTwo/victim-repo"` (so the handler resolves and acts on a stack belonging to a completely different tenant, `OrgTwo`).

`Shipit::Repository.from_github_repo_name` is looked up purely from this attacker-controlled `full_name` string, with no cross-check that it belongs to the organization whose secret validated the request.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-org Shipit deployment: signature verification is meant to prove "this event genuinely comes from organization X", but the very fields consumed afterward for repository resolution are not covered by that guarantee. A tenant admin who only controls their own org's webhook secret can forge events (`push`, `status`, pull request open/close/label, `check_suite`, etc.) against a victim organization's stacks, e.g. triggering `stack.sync_github`, forging commit statuses/check runs that feed into merge-queue gating, or manipulating review-stack provisioning/archival for a repository they do not own. Depending on which handler is abused, this can enable unauthorized state changes (sync, archive/unarchive, provisioning) on another organization's stack, satisfying the "cross-repository writes" class of impact described in the assessment criteria.

### Likelihood Explanation
Exploitability requires the attacker to control (or know) the `webhook_secret` for *some* organization configured on the shared Shipit instance — a realistic condition in genuinely multi-tenant deployments where each customer org configures its own GitHub App and secret, as reflected in the repository's own multi-org test fixtures. No Shipit session, `ApiClient` token, or GitHub App private key is required; only knowledge of one's own org's webhook secret, which is inherent to being a legitimate (but otherwise unprivileged w.r.t. other tenants) org owner. This matches the report's core pattern: one authorized party (the org whose signature is checked) can act on/undermine state that should be exclusively controlled by the party the record actually belongs to (the org referenced by `full_name`).

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, derive the organization used for the secret lookup and the organization implied by `repository.full_name` from the same source, and reject the request if they diverge (e.g., assert `repository.full_name.split('/').first == repository.owner.login` before dispatching to handlers). Alternatively, bind `Repository.from_github_repo_name` lookups to only repositories known to belong to the authenticated organization.

### Proof of Concept
1. Shipit instance configured with two tenants, `OrgOne` (webhook_secret `S1`, known to `OrgOne`'s admin) and `OrgTwo` (webhook_secret `S2`, hosting stack for `OrgTwo/victim-repo`), matching the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker (an `OrgOne` admin) crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
3. Computes `X-Hub-Signature: sha1=HMAC-SHA1(S1, body)` using `OrgOne`'s known secret.
4. POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner => "OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and validates the signature successfully against `S1`.
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgTwo/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim org's stack — an action the attacker had no legitimate authorization to trigger.
