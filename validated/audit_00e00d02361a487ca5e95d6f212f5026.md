## Analysis

`Shipit` supports a **multi-organization** configuration (`config/secrets.development.shopify.yml`, `docs/setup.md`), where each GitHub organization has its own GitHub App, its own `webhook_secret`, and its own OAuth credentials [1](#0-0) [2](#0-1) .

`WebhooksController#verify_signature` selects **which** organization's webhook secret to check the HMAC signature against using a value it reads directly out of the untrusted JSON body: [3](#0-2) [4](#0-3) 

`repository_owner` is `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). This is the *only* value used to select the `GitHubApp`/secret used to verify `X-Hub-Signature`.

Once the signature check passes, the raw parsed `params` (the entire attacker-controlled JSON body) is dispatched to handlers such as `PushHandler` and `StatusHandler`. These handlers determine **which repository/stack to mutate** using a *different* field of the same payload: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `verify_signature` checks the signature keyed on `repository.owner.login` (or `organization.login`), while `Handler#repository_name` — used to look up the actual `Repository`/`Stack` to act on — reads `repository.full_name` (a completely independent JSON key), **nothing enforces that `repository.owner.login == full_name.split('/').first`**. This is exactly the "organization that authenticated versus the repository that is written" binding the scan is looking for, and it is broken here.

### Concrete exploitation path
Assume Shipit is configured (as documented) with two organizations, `orgA` and `orgB`, each with its own GitHub App and `webhook_secret`, both installed as legitimate customers on the same Shipit instance [8](#0-7) . Any actor who is an admin/owner of `orgA`'s GitHub App (a normal, unprivileged-with-respect-to-`orgB` customer of the shared Shipit instance — they only administer their own App, not `orgB`'s, Shipit's session, or any `ApiClient`) knows `orgA`'s `webhook_secret` because they configured it themselves when setting up their GitHub App per `docs/setup.md`.

That person can then POST directly to `/webhooks` (no session or `ApiClient` token required — `WebhooksController` is a bare `ActionController::Base` with signature as the only gate) with a forged body:

```json
{
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```

signed with `orgA`'s `webhook_secret`. `verify_signature` resolves `Shipit.github(organization: 'orgA')` and validates the HMAC successfully because it was in fact computed with the correct (attacker-known) `orgA` secret [9](#0-8) . The request then reaches `PushHandler`, which resolves the target purely from `repository.full_name = "orgB/victim-repo"` [5](#0-4) , finds `orgB`'s real `Repository`/`Stack`s, and calls `stack.sync_github(expected_head_sha: params.after)` on them, forcing a `GithubSyncJob` for `orgB`'s stacks using an attacker-supplied SHA that `orgB` never pushed [6](#0-5) . Similarly, `StatusHandler` can inject arbitrary CI status states onto any commit SHA (not scoped to a repository at all) [10](#0-9) , which — combined with `ci.require` gating in `shipit.yml` — can be used to make an otherwise-failing commit appear "deployable" (`Commit#deployable?`) for an org the attacker does not own, undermining the CI-gate check in `Api::DeploysController#create` (`param_error!(:require_ci, ...) if params.require_ci && !commit.deployable?`) [11](#0-10) .

This lets an `orgA` customer forge sync/status events that are attributed to and acted on `orgB`'s stacks — a cross-repository/cross-organization write that breaks the equality `verified_signature_organization == repository_written_organization`, achievable without any Shipit session, `ApiClient` token, or GitHub repository write access to the victim org.

### Title
Webhook signature verification keys off `repository.owner.login`, but event handlers act on the independent `repository.full_name` field, allowing cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to validate `X-Hub-Signature` against using `repository_owner`, sourced from `params.dig('repository','owner','login')` or `params.dig('organization','login')` [12](#0-11) . After the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw attacker-supplied JSON to handlers [13](#0-12) . Those handlers (`Handler#repository_name`, used by `PushHandler`) resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` — a field never checked for consistency with `repository.owner.login` used during signature verification [5](#0-4) . In Shipit's supported multi-organization deployment mode, each org has an independently-configured `webhook_secret` [2](#0-1) [1](#0-0) , so knowledge of one org's secret is sufficient to forge a signed payload naming a different org's repository as the mutation target.

### Impact Explanation
An actor who legitimately administers one organization's GitHub App on a shared multi-org Shipit instance can forge webhook deliveries that trigger `GithubSyncJob` and commit-status writes against a **different organization's stacks**, without holding any Shipit session, `ApiClient` credential, or GitHub write access to the victim organization/repository. This is a cross-repository/cross-organization write and can be leveraged to manipulate `Commit#deployable?` state via forged `status` events feeding into CI-gated deploy checks (`Api::DeploysController#create`) [11](#0-10) .

### Likelihood Explanation
Requires Shipit to be configured in the documented multi-organization mode with more than one org sharing the instance, and requires the attacker to control one org's GitHub App webhook secret (a normal, expected level of access for a customer administering their own integration in such a shared deployment) — not any privileged access to the victim org.

### Recommendation
In `WebhooksController#verify_signature`, after establishing that the signature validated against `repository_owner`'s secret, enforce that every subsequent handler operates strictly on repositories/organizations whose owner matches the same `repository_owner`/`organization` value that authenticated the request (e.g., pass the verified organization through to `Handler` and have `repository_name`/`stacks` reject repositories whose owner does not match it).

### Proof of Concept
1. Configure Shipit with two orgs, `orga` and `orgb`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup).
2. As the administrator of `orga`'s GitHub App (who legitimately knows `orga`'s `webhook_secret`), compute `sha1=HMAC(orga_secret, body)` for the JSON body:
```json
{"ref":"refs/heads/main","after":"<attacker_sha>","repository":{"owner":{"login":"orga"},"full_name":"orgb/victim-repo"}}
```
3. `POST /webhooks` with header `X-Github-Event: push` and the computed `X-Hub-Signature`.
4. `verify_signature` validates successfully against `orga`'s secret; `PushHandler` then looks up `orgb/victim-repo`'s stacks via `full_name` and enqueues a sync using the attacker-chosen `after` SHA, mutating `orgb`'s stack state despite the attacker having no relationship with `orgb`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
