### Title
Integer overflow via unchecked multiplication in asset denomination cap validation - (File: validation.js)

### Summary
`validateAssetDefinition()` accepts asset-issuer supplied `denominations` arrays and accumulates `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` to check it against the declared `cap`, but neither `count_coins` nor the product is bounded to a safe-integer range, allowing the multiplication to silently overflow JavaScript's double-precision arithmetic — the same bug class as CVE-2023-33204's unchecked multiplication overflow in `check_overflow`/`common.c`.

### Finding Description
In `validateAssetDefinition()`, `denomInfo.denomination` is bounded (`isPositiveInteger(denomInfo.denomination) && denomInfo.denomination <= constants.MAX_CAP`), but `denomInfo.count_coins` is only checked with `isPositiveInteger(denomInfo.count_coins)`, which has no upper bound at all: [1](#0-0) [2](#0-1) 

Because `count_coins` can be an arbitrarily large positive integer (up to `Number.MAX_SAFE_INTEGER` or beyond, since `isInteger` only checks `Math.floor(value)===value` on a double, not a safe-integer bound), the expression `denomInfo.count_coins * denomInfo.denomination` can exceed `2^53` and silently lose precision (JS numbers do not throw or wrap on overflow — they just round), directly mirroring the "multiplication integer overflow" root cause described in the CVE. The rounded product is then summed into `total_cap_from_denominations` and compared against the attacker-declared `payload.cap` with a plain `!==`: [3](#0-2) 

Later, at actual issuance time, `validateIndivisibleIssue()` performs the same class of unchecked multiplication for a capped denomination: [4](#0-3) 

Since `input.amount !== denomination * denomInfo.count_coins` is evaluated on doubles, once `count_coins` and `denomination` are chosen so their product straddles the 2^53 precision boundary, distinct mathematically-different `(denomination, count_coins)` pairs can round to the *same* double value, and an attacker-crafted `input.amount` can pass this floating point equality check while not corresponding to the exact intended amount. This lets the definer's own asset "cap" enforcement (which existing code and downstream consumers assume is exact) be satisfied by inconsistent values, defeating the guarantee that total coins issued equals `cap`.

### Impact Explanation
This breaks the fixed-cap invariant of indivisible assets, allowing the asset issuer to define/issue a token whose real circulating supply diverges from its published `cap` due to the overflow — a supply-inflation condition for that asset. This is reachable purely by posting a unit (an `asset` definition message and a subsequent `payment`/issue message) via `validateAssetDefinition()` and `validatePaymentInputsAndOutputs()`, both of which are exercised for any incoming unit during standard `validate()` unit validation, i.e., by an unprivileged issuer with no special node/network access.

### Likelihood Explanation
Exploitation only requires crafting a single asset-definition unit with `denominations` values whose product with `count_coins` is deliberately chosen near/above `2^53`, followed by an issuance unit whose `input.amount` is chosen to match the rounded (imprecise) product — both purely client-side computations requiring no cryptographic material or race condition, making this straightforward for anyone who wants to define such an asset.

### Recommendation
- Bound `count_coins` explicitly (e.g., `count_coins <= constants.MAX_CAP` or similar), and additionally require that `denomInfo.count_coins * denomInfo.denomination <= constants.MAX_CAP` using an overflow-safe check (e.g., verify `denomInfo.count_coins <= Math.floor(constants.MAX_CAP / denomInfo.denomination)` before multiplying) rather than checking the raw product after the fact.
- Apply the same safe-multiplication check in `validateIndivisibleIssue()` before comparing `input.amount` to `denomination * denomInfo.count_coins`.
- Reject any operand or product that would exceed `Number.MAX_SAFE_INTEGER` prior to performing the multiplication.

### Proof of Concept
1. Post an `asset` definition unit with `fixed_denominations: false`/capped denominations, `cap: X`, and a `denominations` entry `{ denomination: D, count_coins: C }` where `D * C` computed as a JS double rounds to exactly `X` even though the true integer product `D*C` (as arbitrary precision) is different — feasible once `D*C > 2^53` (~9.007×10^15), which is reachable because `D` can be as large as `constants.MAX_CAP` and `C` has no upper bound check.
2. `validateAssetDefinition()` accepts the definition since `total_cap_from_denominations === payload.cap` passes on the rounded double.
3. Post an issuance `payment` unit with `input.amount` set to the same rounded double value; `validateIndivisibleIssue()`'s check `input.amount !== denomination * denomInfo.count_coins` passes because both sides are computed/compared as the same imprecise double, even though the exact mathematical amount implied by `denomination` and `count_coins` differs from the declared/intended cap-consistent amount, resulting in an inconsistency between the asset's declared cap and its real accounted supply.
