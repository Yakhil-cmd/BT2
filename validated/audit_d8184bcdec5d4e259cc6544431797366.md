### Title
Stale `Account.owner` lets the previous NFT holder keep spending authority after a position transfer - (File: contracts/controller/src/account.rs)

### Summary
The controller keeps the account owner's `Address` inside the persisted `Account` struct, written once at mint time and never updated afterward. The account-spending guard `is_owner_or_delegate` / `require_owner_or_delegate` trusts this stale `account.owner` field, while the ownership guard `require_account_owner` correctly reads the live NFT owner via `storage::account_owner`. After `position-nft::transfer`, the previous owner still satisfies `caller == account.owner` and their delegate list (keyed under the stale owner) remains active, so the seller retains full control of the position they no longer own.

### Finding Description
`create_account` persists `Account { owner: owner.clone(), .. }` when the NFT is minted (contracts/controller/src/account.rs:62-74). No code path in `contracts/controller/src` ever rewrites `account.owner`. All state-changing position flows (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) reach `require_owner_or_delegate(env, account_id, caller, &account.owner)` (account.rs:99-140), where `is_owner_or_delegate` returns `true` whenever `caller == account.owner` (account.rs:121-123) or when `caller` is in `storage::get_delegates(env, account_id, owner)` — again keyed by the stale `owner` (account.rs:124-127).

In contrast, `require_account_owner` (account.rs:143-148) reads `storage::account_owner(env, account_id)` — the live NFT owner — and `add_delegate`/`remove_delegate`/`renew_account` use that path. So after `position-nft::transfer`/`transfer_from`:

- The new NFT owner is rejected by `require_owner_or_delegate` (they are not `account.owner`, and any delegate they add is stored under the new owner's key, which `is_owner_or_delegate` never looks up because it searches under `account.owner`). They cannot borrow, withdraw, or rescue their own collateral.
- The previous owner still passes `require_owner_or_delegate` as "owner" and keeps all delegates they granted, directly contradicting the documented invariant that "delegate grants from the previous owner go inactive" (scripts/permissionless_entrypoints.txt:111).

This mirrors the advisory class: an action authorized against a stale/weakly-bound identity rather than the current authority, letting a lower-privileged (here: no longer privileged at all) address exercise position-owner powers.

### Impact Explanation
Theft of user funds and permanent freezing of funds. An attacker lists an account NFT (or transfers it to a victim as part of a deal), the victim acquires the position expecting its collateral, and the attacker — still `account.owner` — calls `withdraw`/`borrow`/`multiply` to drain the collateral and maximally leverage the account. The victim cannot withdraw because `require_owner_or_delegate` rejects them, so their funds are frozen until the position is liquidated or emptied by the attacker. Any third-party transfer of a position (sale, gift, contract-held NFT) is exploitable.

### Likelihood Explanation
Reachable by any unprivileged address through `position-nft::transfer` (a documented permissionless path for the token owner) followed by `controller::withdraw`/`controller::borrow` on the same `account_id`. No privileged role, timing constraint, or oracle manipulation is needed; only that an account NFT changes hands, which the NFT contract exists specifically to enable.

### Recommendation
Resolve authority from the live NFT owner everywhere: in `is_owner_or_delegate`/`require_owner_or_delegate`, replace `account.owner` with `storage::account_owner(env, account_id)`, or keep `Account.owner` synchronized on every transfer. Delegate lists should be keyed under the current owner at check time, matching the `add_delegate` path, so grants die with the transfer.

### Proof of Concept
1. Alice calls `controller::supply(caller=alice, account_id=0, ...)` — account 1 is minted; `account.owner = alice`.
2. Alice calls `position-nft::transfer(from=alice, to=victim, token_id=1)`. Stored `account.owner` is still `alice`.
3. Attacker-controlled `alice` calls `controller::borrow(caller=alice, account_id=1, hub_asset=USDC, amount=max_ltv)` — `require_owner_or_delegate` sees `caller == account.owner` and passes; debt accrues on victim's account.
4. `alice` calls `controller::withdraw(caller=alice, account_id=1, hub_asset=collateral_asset, amount=...)` to pull the remaining collateral to herself; post-tx solvency is checked against the account, not the caller, so it succeeds.
5. Victim calls `controller::withdraw(caller=victim, account_id=1, ...)` — rejected with `NotAuthorized` since `victim != account.owner` and no delegate entry exists under `account.owner` for them; likewise `add_delegate` succeeds (live owner) but the new delegate still fails `is_owner_or_delegate` (lookup under stale owner), so the position is unrecoverable.

Caveat: I was unable to read `contracts/controller/src/storage/account.rs` to confirm whether `storage::get_account` rehydrates `Account.owner` from the NFT owner on load; the finding assumes the persisted field is returned as written, consistent with `create_account` (account.rs:62-74) and the absence of any `account.owner` write elsewhere.
