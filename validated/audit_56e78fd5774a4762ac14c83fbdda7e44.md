### Title
Webhook signature verification is scoped to `repository.owner.login`/`organization.login` while push/pull_request handlers act on the unauthenticated `repository.full_name` field, enabling cross-organization stack sync - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to validate the HMAC signature based on `repository_owner`, which is read directly from the untrusted JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`) [1](#0-0) [2](#0-1) . All the downstream handlers that actually act on the payload (e.g. `PushHandler`, the `PullRequest::*` handlers) instead resolve the target `Repository`/`Stack` via a *different* field of the same payload, `repository.full_name`, through `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` [3](#0-2)  and `Repository.from_github_repo_name` [4](#0-3) .

### Finding Description
This is the analog of the M-20 bug class: the value used to satisfy an integrity check (`repository.owner.login`, which selects the secret against which the HMAC signature is verified) is not the same value that is subsequently trusted and acted upon (`repository.full_name`, which is used to locate the `Repository`/`Stack` records that get written to). Mathematically/logically, these two payload fields should always agree for a legitimate GitHub delivery, but nothing in the code enforces that binding — the signature covers the raw JSON bytes, not a specific claim that "`repository.owner.login` == the owner segment of `repository.full_name`".

Binding that should hold: `verified_organization(repository.owner.login) == owner(repository.full_name)`.
What the code actually guarantees: only that the raw body matches *some* HMAC computed with the `GitHubApp` config selected via `repository.owner.login`. The `full_name` field used by `PushHandler#process` (via `Handler#stacks`/`#repository_name`) and by the `PullRequest::*` handlers (`params.repository.full_name`) is never cross-checked against `repository.owner.login`/`organization.login`.

In a multi-tenant Shipit deployment (multiple orgs each configured with their own `github_apps` entry / `webhook_secret`, which the engine explicitly supports via `Shipit.github(organization:)` and `GithubOrganizationUnknown`), an entity that legitimately controls the webhook secret for *its own* organization (e.g., an org admin who configured the GitHub App/webhook for their own org, which is the expected, unprivileged-for-other-orgs trust boundary in this design) can hand-craft an HTTP POST directly to `/github/webhooks` (bypassing GitHub entirely, since this is a public endpoint, not one that authenticates the caller as GitHub) with:
- `repository.owner.login` (or `organization.login`) = their own org → signature verifies successfully with their own secret.
- `repository.full_name` = `"other-org/other-repo"` → handler code resolves and operates on a stack belonging to a different tenant/org entirely.

For the `push` event this reaches `PushHandler#process`, which calls `stack.sync_github(expected_head_sha:)` on stacks belonging to the victim org/repository [5](#0-4) . This enqueues `GithubSyncJob`, which fetches "missing commits" from GitHub for that stack and appends them to the victim's stack, then triggers `CacheDeploySpecJob` [6](#0-5) . Because `sync_github`-driven commit ingestion is precisely the mechanism that (for stacks with `continuous_deployment` enabled) leads to automatic deploy triggering, an attacker who only controls their own tenant's webhook secret can force sync/ingestion activity against a completely different organization's repository/stack that they have no authorization over — a cross-organization write that should have been precluded by webhook signature verification.

### Impact Explanation
This breaks the binding "organization that authenticated versus the repository that is written," matching the Critical category "cross-repository writes, or an unauthorized deploy, rollback or merge." An attacker who is trusted only for their own org's webhook integration can cause sync (and potentially deploy-triggering) activity against another organization's stack, which they have no read/write authorization for through any other engine surface (no `ApiClient` token, no `Shipit.github_teams` membership, no session).

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization/app (each with its own webhook secret) — a supported, non-default-but-documented configuration surfaced by `Shipit.github(organization:)` and `GithubOrganizationUnknown`. The attacker needs only their own legitimately-provisioned webhook secret (not the victim's), and the ability to POST directly to the public `/github/webhooks` endpoint with an arbitrary JSON body of their choosing — no GitHub-side control is required since the controller does not verify the request actually came from GitHub's IP ranges or that the two organization-identifying fields agree.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that the owner segment of `repository.full_name` matches the `repository_owner`/`organization.login` value used to select the verifying secret, and reject the webhook (422) if they differ. Alternatively, verify the signature using a key scoped per-repository/tenant that is derived from (and thus binds) `full_name`, not just the top-level `owner.login`.

### Proof of Concept
1. Configure Shipit with two tenants, `org-a` and `org-b`, each with its own `github_apps[org].webhook_secret`.
2. As the holder of `org-a`'s webhook secret, compute a valid `X-Hub-Signature` for a payload where:
   - `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` is selected and signature verifies).
   - `repository.full_name = "org-b/victim-repo"`, `ref = "refs/heads/main"`, `after = "<attacker-chosen-sha>"`.
3. POST this payload with header `X-Github-Event: push` directly to the webhooks endpoint.
4. `verify_signature` succeeds (secret matches `org-a`). `PushHandler#process` resolves `stacks` via `repository.full_name = "org-b/victim-repo"` [3](#0-2)  and calls `sync_github` on `org-b`'s stack, which the attacker never had any org-b credential for.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
