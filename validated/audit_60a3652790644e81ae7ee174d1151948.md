### Title
Cross-repository status forgery via SHA collision in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb](app/models/shipit/webhooks/handlers/status_handler.rb))

### Summary
`Commit#refresh_statuses!` always re-fetches status data scoped to the owning stack's own `github_repo_name` via `stack.github_api.statuses(github_repo_name, sha, ...)`, guaranteeing that a commit is only ever updated with statuses belonging to its own repository. `StatusHandler#process`, which handles the webhook-driven `status` event, applies an externally-supplied status to every `Commit` matching a bare `sha`, with no check that the webhook's source repository matches the repository owning that commit.

### Finding Description
The binding that should hold is: `commit.stack.github_repo_name == payload["repository"]["full_name"]` for any status applied to `commit`. `Commit#refresh_statuses!` enforces this implicitly because it re-fetches from `stack.github_api.statuses(github_repo_name, sha, ...)` [1](#0-0)  — the repository name is always derived from the owning stack, never from attacker input.

`StatusHandler#process`, by contrast, resolves target commits purely by `sha` and never checks the originating repository at all: [2](#0-1) 
The handler's `params` schema doesn't even capture the GitHub `repository` object present in the real `status` webhook payload, so there is no data available to perform such a check even if the code wanted to.

The controller-level guard, `WebhooksController#verify_signature`, only proves the payload was authentically signed by the GitHub App installation belonging to `repository_owner` (the org of the *sending* repository) — it does not prove anything about which repository's commit should receive the status: [3](#0-2) 

Because git commit SHAs are content-addressed, an attacker who owns/controls any repository (including one they push to or fork) can create a commit with byte-for-byte identical content to a commit that exists in a victim's Shipit-tracked repository/stack (e.g., by fetching and re-pushing the public commit, or replicating the same tree/parents/message/timestamps). This produces an identical SHA. The attacker then sets a commit status on that commit in their own repository (via the GitHub UI/API, which they have full unprivileged control over since it's their own repo). GitHub delivers a legitimately-signed `status` webhook to Shipit for the attacker's own org/repo. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally across all stacks and repositories and calls `commit.create_status_from_github!(params)` on every match — including the victim's commit belonging to an entirely different stack/repository, without ever checking that the webhook's `repository.full_name` equals `commit.stack.github_repo_name`.

`create_status_from_github!` writes a `Status`, and via `add_status` can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` when the new status becomes successful [4](#0-3) [5](#0-4) , which can make a victim's commit appear `deployable?` and unblock automatic merges/deploys on the victim's stack.

None of the existing guards prevent this: `verify_signature` only authenticates the sender's organization, not the payload's semantic relationship to the target commit; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` never captures or validates `repository`; and there is no `stack`/`repository` equality check anywhere in `StatusHandler#process` or `Commit#create_status_from_github!`.

### Impact Explanation
An attacker who controls (or forks) any repository can forge a commit status against any commit in any *other* Shipit-tracked stack whose commit SHA they can reproduce (trivial for public commits, or for any commit content they can otherwise learn/reconstruct). This can flip a victim's commit into a "success"/"deployable" state, potentially triggering `stack.schedule_merges` or unblocking `deployable?` checks that gate automatic deploys — i.e., "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". This matches the Critical impact category (cross-tenant mutation / unauthorized deploy) since it is not confined to the attacker's own repository/stack.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a GitHub repository they control (their own repo or a fork) with the Shipit GitHub App/webhook configured for their own organization — no access to the victim's Shipit stack, session, API token, or webhook secret is required, since the signature is validated per-sender-organization, not per-target-commit. Reproducing an arbitrary target SHA requires the attacker to know/reconstruct the exact commit content (tree, parents, author/committer timestamps, message) of the victim commit, which is straightforward for any commit whose content is public (e.g., open-source PRs) or otherwise known to the attacker. This is repeatable against arbitrary stacks/commits sharing a known SHA.

### Recommendation
In `StatusHandler#process` (and any other webhook handler resolving commits by bare `sha`), capture the `repository.full_name` field from the webhook payload in the `params` schema and filter/validate that `commit.stack.github_repo_name == payload_repository_full_name` before calling `commit.create_status_from_github!(params)`, discarding statuses for commits whose owning stack's repository does not match the webhook's source repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks/commits with the **same** `sha` but different `github_repo_name` — `victim_stack` (`github_repo_name: "victim/repo"`) with `victim_commit`, and `attacker_stack` (`github_repo_name: "attacker/repo"`) with `attacker_commit`, both sharing `sha: "deadbeef..."`.
2. Build a `StatusHandler` payload as would arrive from `attacker/repo`'s webhook: `{ sha: "deadbeef...", state: "success", context: "ci", ... }` (no repository binding enforced).
3. Call `StatusHandler.new(payload).process` (or `.call`).
4. Assert both `victim_commit.reload.statuses` **and** `attacker_commit.reload.statuses` now contain the forged "success" status — demonstrating the cross-repository write.
5. Contrast with `victim_commit.refresh_statuses!` stubbed so `Shipit.github.api.statuses("victim/repo", sha, ...)` returns only victim-specific data; assert it never reads or writes anything derived from `attacker/repo`, proving the divergence is isolated to `StatusHandler#process`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
