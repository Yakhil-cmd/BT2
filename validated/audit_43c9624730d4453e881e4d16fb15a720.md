### Title
Stack-scoped API tokens can read the status of any stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` tokens can be scoped to a single stack via the `stack_id` column, and `Shipit::Api::BaseController` enforces that scope by resolving the requested stack only from the set of stacks the client is allowed to see. `Shipit::Api::CCMenuController` overrides the stack-resolution method and looks the stack up directly from the URL parameter, without checking that it belongs to the authenticated client's authorized scope. This breaks the binding "stack a token authorizes == stack a token touches," letting any valid `read:stack` token read the CI/deploy status of stacks it was never granted access to.

### Finding Description
`ApiClient#authentication_token` signs only the client `id` [1](#0-0) , and `ApiClient.authenticate` verifies the signature and loads the client purely by that `id` [2](#0-1) . Authorization to a *specific* stack is not part of the signed payload; it is enforced out-of-band by each controller consulting `current_api_client.stack_id`.

`Shipit::Api::BaseController` implements this scoping correctly: `stacks` restricts the queryable set to the client's own `stack_id` when present, and `stack` resolves the URL parameter against that restricted set [3](#0-2) .

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this check entirely, resolving the stack directly from all stacks regardless of the authenticated client's scope: [4](#0-3) 

So the equality that should hold — "the stack(s) a token is authorized for" == "the stack the request actually touches" — is violated specifically in this controller. Any client with the `read:stack` permission, no matter which single stack it was scoped to when created, can be pointed at an arbitrary `stack_id` in the CCMenu endpoint and receive that other stack's latest deploy/rollback status, lock state, and build label.

### Impact Explanation
This is an authorization-scope escalation: a token minted for read-only visibility into one stack (e.g. via the “CCMenu URL” self-service flow at `app/controllers/shipit/ccmenu_url_controller.rb:15-18`, or any admin-created `read:stack` client scoped to a specific stack) can be replayed against `/api/<other_stack>/ccmenu.xml` to obtain deploy status, lock status, and last build outcome for stacks it was never authorized to view. This matches the "unauthenticated/unauthorized read of stack state" High-impact bucket, since the token holder does not need any credential or grant for the target stack.

### Likelihood Explanation
Any holder of a valid `read:stack` API token (even one deliberately scoped to a single, less-sensitive stack, e.g. distributed to a CI dashboard) can trivially perform this by editing the `stack_id` segment of the URL — no additional privilege, secret, or session is required beyond the token itself, which the rules already treat as attacker-obtainable via the intended low-privilege distribution path (e.g. CCMenu URLs).

### Recommendation
In `Api::CCMenuController`, resolve the target stack through the same scoped `stacks` helper used by `BaseController` (i.e. remove the private `stack` override, or reimplement it as `stacks.from_param!(params[:stack_id])`) so that clients scoped to a specific `stack_id` cannot query other stacks.

### Proof of Concept
1. Create (or have an admin create) an `ApiClient` with permission `read:stack` scoped to `stack_id = A` (e.g. via the CCMenu self-service flow for stack A, `GET /A/ccmenu_url`), yielding `token_A`.
2. As an unprivileged holder of `token_A`, request:
   `GET /api/B/ccmenu.xml?token=token_A` where `B` is a different, unrelated stack.
3. `Api::CCMenuController#authenticate_api_client` accepts `token_A` because the signature/id check succeeds [5](#0-4) ; `require_permission :read, :stack` passes because the client's `permissions` include `read:stack` [6](#0-5) ; and `stack` resolves `B` directly via `Stack.from_param!` without consulting the client's `stack_id` scope [7](#0-6) .
4. The response returns stack `B`'s deploy status/lock state, even though `token_A` was only ever authorized for stack `A`.
