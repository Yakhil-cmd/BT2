### Title
Uncaught exception in c-hash validation via malformed base64/base32 input causes node crash - (File: chash.js)

### Summary
The CVE describes a heap overflow in NanoMQ's CONNECT packet parser: a length field controls a fixed-size buffer copy without validating that the decoded/parsed length actually matches the expected size, and the mismatch is not safely handled, causing a crash. The analogous bug class in ocore is in the `isChashValid` function in `chash.js`, where a length field derived from decoding attacker-supplied base32/base64 data is *assumed* to match one of two hard-coded bit lengths (160 or 288) without that assumption being fully guarded, causing an uncaught exception when it doesn't.

### Finding Description
`isChashValid` decodes an attacker-supplied string and then processes the decoded buffer assuming its bit-length is exactly 160 or 288 bits: [1](#0-0) 

The `try/catch` in this function only wraps the decode step (`base32.decode`/`Buffer.from(..., 'base64')`), not the subsequent `buffer2bin` / `separateIntoCleanDataAndChecksum` calls. `separateIntoCleanDataAndChecksum` explicitly `throw`s if the resulting bit-length isn't exactly 160 or 288: [2](#0-1) 

`Buffer.from(str, 'base64')` in Node.js is a lenient decoder: characters outside the base64 alphabet are silently skipped rather than causing a decode error, so a 48-character string with a few invalid characters can decode to a buffer that is *not* 36 bytes (288 bits), while the initial `try` around the decode call succeeds. This produces an uncaught `Error("bad length=...")` that propagates out of `isChashValid`, out of `isValidChash` (which has no try/catch of its own), all the way to whatever caller invoked address/definition validation: [3](#0-2) 

The 32-character (160-bit) path is not exploitable this way, because base32's fixed 5-bits-per-character mapping and strict alphabet make the decoded length deterministic for a 32-character input. The 48-character (chash288) path is the vulnerable one, since it uses lenient base64 decoding.

### Impact Explanation
An uncaught exception thrown deep inside a validation helper that has no surrounding try/catch at the call site would propagate up as an uncaught exception in Node.js, which — unless caught by a top-level handler — crashes the process. If this chash-288 validation is reachable from a single posted unit (e.g., via an "address definition template" chash embedded in an oscript/AA address definition, a feature that a growing number of matches for `288`/`chash288` in `wallet_defined_by_addresses.js` and `definition.js` suggest is used for such purposes), then any unprivileged unit poster could craft a unit whose address definition contains a malformed 48-character chash to crash any full node that attempts to validate it — a network-wide denial of service preventing confirmation of new units, which satisfies the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Medium-to-High if the 48-char (chash288) validation path is reachable from ordinary unit/definition content (as strongly suggested by the file-level references, though I was not able to read the exact call site within my remaining tool budget). The specific malformed-base64 input required (mixing valid base64 characters with a few invalid ones to shift the decoded length) is trivial for any attacker to construct.

### Recommendation
- Wrap the entire body of `isChashValid` (not just the decode call) in the existing `try/catch`, so any length-mismatch `Error` from `separateIntoCleanDataAndChecksum`/`mixChecksumIntoCleanData` is caught and causes `isChashValid` to return `false` rather than throwing.
- Additionally, validate that `Buffer.from(encoded, 'base64')` produced exactly 36 bytes (and `base32.decode` produced exactly 20 bytes) before proceeding, rejecting otherwise.
- Audit all callers of `ValidationUtils.isValidChash`/`isChashValid` to ensure none of them execute in a context where an uncaught exception can crash the whole node process during routine unit/definition validation.
