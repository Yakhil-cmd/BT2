The CCMenu XML endpoint issues a per-stack API token but never actually binds that token's authorization to the target stack it was generated for — mirroring the report's core theme of a value that is *nominally* scoped to one entity but is checked without verifying it against the entity actually acted upon.### Title
Cross-stack authorization bypass in CCMenu API — token scoped to one stack grants read access to any stack's deploy/lock state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`CCMenuController#stack` resolves the target stack directly from the URL parameter without ever checking it against the `ApiClient` that authenticated the request, breaking the binding: `stack a token is meant to authorize == stack the request actually touches`.

### Finding Description
The intended, "correct" pattern in this engine is `Api::BaseController#stack`, which resolves the target stack only from the caller's authorized scope: [1](#0-0) 
`current_api_client.stack_id?` gates whether the client is restricted to a single stack; `Api::StacksController` correctly reuses this scoped `stacks`/`stack` helper: [2](#0-1) 

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely and resolve the stack straight from `params[:stack_id]`: [3](#0-2) 
The only check performed is `require_permission :read, :stack`, which only verifies the string `"read:stack"` is present in the client's `permissions` array — it has no notion of *which* stack the token was minted for: [4](#0-3) 

Compounding this, the token handed out by `CCMenuUrlController` for a *specific* stack's CCMenu URL is created without ever setting the `stack:` association on the `ApiClient`: [5](#0-4) 
Even if it had set `stack:`, `CCMenuController#stack` doesn't consult it — so the scoping mechanism is doubly ineffective for this endpoint.

**Before vs after the equality binding:**
- Expected: `token.authorized_stack == stack_being_read` (enforced via `BaseController#stacks`/`stack`, as in `StacksController`).
- Actual in `CCMenuController`: `stack_being_read = params[:stack_id]` (attacker-controlled), completely decoupled from any stack the token was issued for. The equality never holds, and no code path enforces it.

### Impact Explanation
Any holder of a CCMenu token minted for one stack (e.g. shared in a CI status badge, README, or monitoring dashboard for stack A, which is a common, low-sensitivity use case) can substitute any other stack's identifier in the URL path and read that stack's deploy/rollback state, lock status, and last build outcome — data belonging to a stack the token was never meant to expose. This matches the "High — unauthenticated/unauthorized read of stack state" impact category: a credential with a narrow intended scope (one stack's CI status) is honored engine-wide because the controller never checks scope at all.

### Likelihood Explanation
High. No privileged access or credential guessing is required beyond possessing any single valid CCMenu token (which by design is meant to be low-sensitivity and shareable, e.g. embedded in CI dashboard tools) or any other `read:stack`-scoped `ApiClient` token. The attacker only needs to change the `stack_id` path segment; no signature or additional secret needs to be forged since the token itself is unmodified and valid.

### Recommendation
Make `Api::CCMenuController#stack` use the inherited, scoped `Api::BaseController#stack`/`stacks` helper instead of `Stack.from_param!` directly, so lookups are constrained to `current_api_client.stack_id` when the client is stack-scoped. Additionally, have `CCMenuUrlController#client` explicitly set `stack: stack` when creating/finding the `ApiClient`, so tokens minted for a specific stack's CCMenu URL are actually restricted to that stack.

### Proof of Concept
1. User creates (or is given) a CCMenu URL for Stack A via `GET /stacks/:A_owner/:A_name/:A_env/ccmenu_url`, yielding `https://shipit.example.com/api/stacks/A_owner/A_name/A_env/ccmenu.xml?token=T`.
2. Attacker who obtains `T` (e.g., from a status page or CI badge embedding it) sends `GET /api/stacks/B_owner/B_name/B_env/ccmenu.xml?token=T` for an unrelated Stack B they have no access to.
3. `authenticate_api_client` in `CCMenuController` successfully authenticates `T` via `ApiClient.authenticate(params[:token])`.
4. `require_permission :read, :stack` passes because `T`'s permissions include `read:stack` (no stack restriction is checked).
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B directly, and its deploy/lock/build status is rendered — despite `T` never having been intended to authorize access to Stack B. [6](#0-5)
