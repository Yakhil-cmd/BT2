## Analysis

I found a valid analog. The report's bug class is "a check acts on one value, but a different, related value determines the actual effect" — i.e., a broken equality binding between the field used for authorization and the field used for the write. In `Shipit::WebhooksController`, the exact same class of bug exists: the field used to select which secret verifies the signature (`repository.owner.login`) is not bound to the field used to determine which stack/repository is actually written to (`repository.full_name`, used deep in the handlers).

### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while handlers act on the independent `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to check the `X-Hub-Signature` against using `repository_owner`, taken from the attacker-controlled JSON body (`params.dig('repository', 'owner', 'login')` or `organization.login`). Once verification passes, every webhook handler (`PushHandler`, `StatusHandler`, membership/pull-request handlers, etc.) independently determines *which* `Stack`/`Repository` to mutate using a different payload field, `repository.full_name`. These two fields are never cross-validated to be consistent, breaking the equality: `organization that authenticated == organization owning the repository being written`.

### Finding Description
`verify_signature` looks up the GitHub App config for the org named in the payload and verifies the raw body against that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

The signature is computed over the entire raw request body: [3](#0-2) 

However, the actual event handlers ignore `repository.owner.login`/`organization.login` and instead resolve the target `Repository`/`Stack` purely from `repository.full_name`: [4](#0-3) [5](#0-4) 

Shipit supports multiple GitHub Apps/organizations in a single deployment, each with its own `webhook_secret`, as documented in the multi-org secrets format: [6](#0-5) 

Because the field that selects the verification secret (`repository.owner.login`/`organization.login`) is never checked against the field that determines the write target (`repository.full_name`), an attacker who legitimately administers a GitHub App for **OrgA** (and therefore genuinely knows OrgA's `webhook_secret`, since they configured it when creating the App per `docs/setup.md`) can send a request where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` validates the HMAC using OrgA's own known secret — passes)
- `repository.full_name` = `"OrgB/some-repo"` (an entirely different organization's repository that the attacker doesn't own)

The `push` handler will then look up `Repository.from_github_repo_name("OrgB/some-repo")` and, if a matching `Stack` exists, enqueue a `GithubSyncJob`/sync commits for it — using Shipit's own privileged `Shipit.github(organization: "OrgB")` API credentials, not the attacker's. The same applies to `status` (arbitrary CI status injection for any commit sha, which can flip `next_commit_to_deploy` deployability and — combined with `continuous_deployment` — trigger an actual deploy of the target stack), `check_suite`, and `membership`/`pull_request` handlers, which use `full_name` similarly.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely:
- An attacker controlling one org's legitimate webhook secret can forge `status` events for arbitrary commit shas on a stack belonging to a completely different organization/repository configured on the same Shipit instance. If that target stack has `continuous_deployment` enabled, injecting a fabricated `success` status for the next undeployed commit can cause `ContinuousDeliveryJob`/`trigger_continuous_delivery` to trigger a real, unauthorized deploy: [7](#0-6) [8](#0-7) 
- Push events can force out-of-band GitHub syncs of a foreign stack.
This maps to "an unauthorized deploy, rollback or merge" — a Critical-tier impact per the rubric.

### Likelihood Explanation
This requires the deployment to configure more than one GitHub App/organization (`config.github` keyed by org name, exactly as documented and fixture-tested), and the attacker must be an admin of at least one of those configured orgs' GitHub Apps (so they know that org's `webhook_secret`) — this is exactly the kind of "unprivileged w.r.t. Shipit itself, but has some real-world credential" attacker the rules target (no Shipit session, `ApiClient` token, or GitHub App private key needed). Given the documented multi-org support, this is a realistic deployment topology, though single-org deployments are unaffected.

### Recommendation
After locating `repository_owner` for signature verification, also verify that the org segment of `repository.full_name` (and any `organization.login` present) matches `repository_owner` before dispatching to handlers, or better, resolve the webhook secret/app strictly from `repository.full_name`'s owner segment (the field actually used to select the write target) rather than a separately-dug field, so the same value is used both to authenticate and to authorize the target.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml` pattern).
2. As the administrator of `OrgA`'s GitHub App (attacker), craft a `status` webhook payload:
```json
{
  "sha": "<sha of a commit belonging to an OrgB-owned stack>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature` using OrgA's real `webhook_secret` (known to the attacker) over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches OrgA's app, and the signature validates successfully.
6. `StatusHandler#process` finds `Commit.where(sha: ...)` for the OrgB stack (unrelated to OrgA) and creates the forged status, potentially triggering `ContinuousDeliveryJob` for the OrgB stack via `Commit`'s CD callback shown in `test/models/commits_test.rb:233-243`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def trigger_continuous_delivery

        return
      end

        continuous_delivery_delayed!
        return
      end

      begin

      rescue Task::ConcurrentTaskRunning
      end
    end
