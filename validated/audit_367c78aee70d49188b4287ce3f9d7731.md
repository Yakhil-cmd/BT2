### Title
Unbounded, unlimited-input AA payment composition allows dust-flooding an AA's asset balance into a permanently unspendable state - (File: aa_composer.js)

### Summary
The AA response engine's `sendUnit`/`completePaymentPayload` logic in `aa_composer.js` selects unspent outputs to fund an AA-generated payment without any `LIMIT` on the SQL query and without applying `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (that cap is explicitly skipped for AA-authored messages in `validation.js`). Unlike base-asset dust, arbitrary custom-asset outputs sent to an AA are not subject to any minimum-amount filter. An attacker can therefore cheaply flood an AA address with a large number of tiny custom-asset outputs, inflating the set of "unspent outputs of that asset at that address." Whenever the AA subsequently needs to pay out in that asset, every full node must deterministically re-run `iterateUnspentOutputs` over the unbounded result set, mirroring the reported "unbounded loop over an attacker-inflated collection" bug class, and effectively locking the AA's own funds in that asset because payment composition never — or only after excessive, ever-growing work — completes without limit enforcement.

### Finding Description
In `aa_composer.js`, when an AA response contains a `payment` message, `completePaymentPayload` builds up the transaction from database rows: [1](#0-0) 

`readStableOutputs` selects **all** matching unspent outputs for `(address, asset)` with `ORDER BY` but **no `LIMIT`**, and the dust-prevention floor (`amount>=FULL_TRANSFER_INPUT_SIZE`) is applied **only when `asset` is null** (base asset): [2](#0-1) 

The comment explicitly acknowledges the attack pattern for the base asset ("to prevent dust attack: spamming the AA with very small outputs") but the same protection is not applied to custom assets. The result rows are fed into a plain, unbounded `for` loop: [3](#0-2) 

Compounding this, the normal per-message input cap that would otherwise bound how many inputs a payment message can contain is explicitly bypassed for AA-generated messages: [4](#0-3) 

Only the output-count cap remains enforced regardless of author type: [5](#0-4) 

Because a normal user can freely send arbitrary-asset payments to any address, including an AA address, with per-output amounts only constrained to be a positive integer (no minimum, unlike the base-asset case): [6](#0-5) 

an attacker can post many cheap units, each transferring a minuscule (e.g., amount = 1) quantity of a custom asset to the target AA. This is entirely within reach of an unprivileged unit poster / asset-transfer sender: no special permission or private-payment channel is required, only ordinary `payment` messages of an existing asset addressed to the AA.

### Impact Explanation
Once the AA's balance in that asset is comprised of a very large number of dust outputs, any AA trigger that causes the AA to send that asset (a `payment` message in its bounce/response `messages`) forces `completePaymentPayload` to:
1. Fetch an unbounded row set from `outputs`/`units` with no `LIMIT`.
2. Iterate through the entire returned set synchronously in `iterateUnspentOutputs`, growing `payload.inputs` without the `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap that applies to ordinary users (because `objValidationState.bAA` is true).
3. Because every input added increases `size`/`net_target_amount`/`target_amount` (for base asset) and the total output computation, and because tiny-amount inputs contribute negligible `total_amount` per input, the loop can require processing very large numbers of rows before (if ever) satisfying `target_amount`, or it can produce a unit with an enormous number of inputs.

This deterministic re-execution happens on **every full node** each time the trigger fires (AA execution must be reproduced network-wide to reach consensus on the response), turning a single cheap flooding action into a repeated, unbounded computational burden analogous to the reported unbounded-loop DoS. Because AA responses that fail to complete successfully bounce (refunding the trigger but leaving the AA's own stored balance untouched), and because the underlying condition (huge count of tiny same-asset outputs at the AA address) is not itself removed by a failed attempt, the AA's balance in that asset becomes practically unspendable going forward — a permanent freeze of the AA's funds in that asset, matching the "permanent lock of funds" impact class from the report.

### Likelihood Explanation
The attack requires only:
- An existing (or attacker-issued) asset with divisible/arbitrary amounts.
- The ability to send many small, cheap payments of that asset to a known AA address — an unprivileged operation available to any wallet holder.
- No special asset attestation, definer privilege, or private-payment collusion is required for a public divisible asset.

The per-unit cost is the ordinary byte fee for a minimal payment unit, which is very low, making it economical to create thousands of dust outputs. The only necessary precondition is that the target AA (i) accepts/holds the attacker-chosen asset in its logic and (ii) at some point sends that asset out, which is a common pattern for AAs implementing token pools, DEXes, or asset-based accounting.

### Recommendation
- Apply the same dust-prevention floor used for the base asset (`amount >= FULL_TRANSFER_INPUT_SIZE`, or an asset-specific reasonable minimum) to `readStableOutputs`/`readUnstableOutputsSentByAAs` for custom assets, not only when `asset` is null.
- Enforce `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (or an AA-specific cap) even for AA-authored payment messages in `validatePaymentInputsAndOutputs`, removing the `&& !objValidationState.bAA` exemption, and add an explicit `LIMIT` in `readStableOutputs`/`readUnstableOutputsSentByAAs` matching that cap.
- Consider a coin-consolidation/garbage-collection mechanism so AAs (or their owners) can proactively merge dust outputs of a given asset into fewer, larger outputs outside of time-critical trigger processing, bounding worst-case per-trigger work.

### Proof of Concept
1. Attacker issues (or uses an existing) divisible asset `X`.
2. Attacker crafts and posts N (e.g., tens of thousands) of cheap units, each a `payment` message transferring `amount: 1` of asset `X` to the target AA's address. Each unit passes `validatePaymentInputsAndOutputs` because amounts for custom assets only need to be a positive integer — no floor is enforced: [6](#0-5) 
3. Later, a legitimate user triggers the AA in a way that causes it to emit a `payment` message paying out asset `X` (e.g., a withdrawal).
4. `sendUnit` → `completePaymentPayload` → `readStableOutputs` retrieves all N dust outputs (no `LIMIT`, no per-asset minimum): [7](#0-6) 
5. `iterateUnspentOutputs` must loop over the entire dust set to accumulate enough `total_amount`, unconstrained by `MAX_INPUTS_PER_PAYMENT_MESSAGE` because `objValidationState.bAA` disables that check: [4](#0-3) 
6. The AA either times out/bounces repeatedly for every future trigger requiring asset `X` payout, or produces an oversized/expensive unit every full node must reprocess deterministically — freezing the AA's asset-`X` balance indefinitely while degrading node performance on every trigger of that AA.
