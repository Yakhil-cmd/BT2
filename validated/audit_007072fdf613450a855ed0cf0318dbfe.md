### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the acted-upon repository is taken from the unauthenticated `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate a webhook using one field of the JSON payload (`repository.owner.login`, or `organization.login` as fallback), but every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolves which `Stack`/`Repository` to mutate using a *different, independently-controlled* payload field: `repository.full_name`. Because the two fields are never cross-checked, a signature that is cryptographically valid for organization A can carry a payload that claims to originate from organization B's repository, and Shipit will act on organization B's stack.

### Finding Description
The signature check is:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This picks the `webhook_secret` belonging to whatever organization name is embedded in the untrusted JSON body (`repository.owner.login`), and validates the raw body's HMAC against it — this is legitimate for multi-tenant Shipit deployments where several GitHub orgs are each configured with their own `app_id`/`webhook_secret` (see `config/secrets.development.shopify.yml`). [2](#0-1) 

Once the signature is accepted, `WebhooksController#create` dispatches the *same raw payload* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Every handler resolves its target `Stack`s via a base-class helper that reads a *different* payload key:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler`, for example, uses this to trigger `sync_github` on any matching stack:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The binding that is supposed to hold is: `organization authenticated by signature == organization that owns the repository being written to`. The code never enforces `repository.owner.login == repository.full_name.split('/').first`. An attacker who legitimately controls (or has installed the Shipit GitHub App for) *any one* configured organization — call it org A — knows org A's `webhook_secret` (obtainable from their own GitHub App settings, since they administer org A). They can then POST a webhook to Shipit's public `/github/webhooks` endpoint with:
- `X-Hub-Signature` computed with org A's `webhook_secret` over the raw body,
- payload body containing `repository.owner.login = "org-A"` (so `verify_signature` selects and successfully validates against org A's secret),
- payload body containing `repository.full_name = "org-B/victim-repo"` (a stack Shipit manages for an unrelated, victim organization).

`verify_signature` succeeds (it only checks org A's key), but `Handler#repository_name` resolves `org-B/victim-repo`, so the event is processed against the victim's `Stack`.

### Impact Explanation
This breaks the equality "organization authenticated == repository written," letting an attacker who only controls one tenant organization inject forged GitHub events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against a completely different organization's stacks. Depending on handler:
- `PushHandler` can force `GithubSyncJob`/`sync_github` against the victim stack.
- `StatusHandler` can create/forge a `Status` on an arbitrary victim commit sha (as long as the sha exists in the victim repo/stack), which can satisfy `required_statuses`/`blocking_statuses` checks in `DeploySpec` and unblock a deploy that would otherwise be pending CI, i.e., contribute to an **unauthorized deploy**.
- `MembershipHandler`/`PullRequest` handlers can mutate `Team`/`Membership`/review-stack records belonging to the victim org.

This is a cross-tenant/cross-repository write achieved purely by forging one payload field while satisfying signature validation with a different (attacker-controlled) organization's legitimate secret — matching the report's root cause pattern (verification indexed by one field, effect applied using a different, unchecked field).

### Likelihood Explanation
Requires the attacker to be an administrator/owner of at least one GitHub organization that is configured as a tenant in this Shipit instance's `secrets.yml` (a normal, non-privileged position relative to *other* tenants) — no GitHub App private key, no `ApiClient`/API token, no repository write access to the victim repo, and no access to Shipit itself is needed. In any Shipit deployment onboarding multiple GitHub organizations (as the shipped `config/secrets.development.shopify.yml` demonstrates is a supported configuration), this is directly reachable via the public, unauthenticated `/github/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler#stacks`, cross-validate that the organization used to select the webhook secret matches the owner embedded in `repository.full_name` (or better: bind webhook secret validation to the specific installation/repository via GitHub App installation ID rather than an org-name lookup keyed by attacker-supplied payload data), rejecting the event if they diverge.

### Proof of Concept
1. Shipit is configured (per `config/secrets.development.shopify.yml`) with two tenant orgs: `org-A` (attacker-administered, webhook_secret known to attacker) and `org-B` (victim, manages stack `org-B/victim-repo`).
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha existing in org-B/victim-repo>",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-A webhook_secret, raw_body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-A")` and successfully verifies the signature against org A's secret. [6](#0-5) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-B/victim-repo")`, and `process` invokes `stack.sync_github(expected_head_sha: ...)` on the victim's stack — despite the request never being signed by org B's secret. [5](#0-4) [4](#0-3)
