### Title
`repay` refunds the declared overpayment from real custody without measuring inbound tokens — (`File: contracts/pool/src/ops/repay.rs`)

### Summary
The pool's `repay` computes the excess-payment refund from the **declared** `amount` argument, not from the tokens actually received. An attacker can call `repay` with a large declared amount against a market with no outstanding debt, transfer nothing (or dust), and receive the full declared "excess" back out of the pool's real token custody. This is the same bug class as CVE-2017-7272: a caller-supplied value silently overrides the actual constrained quantity the function should operate on.

### Finding Description
`PoolAction` carries a caller-declared `amount` alongside the `hub_asset` market key ( [1](#0-0) ). In `ops::repay`, `resolve_repay` takes the full-close branch whenever the declared amount covers `current_debt_ceil`; when the market has no debt, `current_debt_ceil` is zero, so the entire declared amount becomes refundable "excess". The pinned test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` demonstrates the exact sequence: nothing is transferred in, `credited == 0`, and the refund still drains custody ( [2](#0-1) ). The refund leg neither debits `cash` nor passes `require_reserves`, so the pool's cash book is left claiming funds it no longer holds ( [3](#0-2) ).

The sibling test `test_recapitalize_rejects_a_hub_asset_that_names_no_market` confirms the pool performs no measured-receipt check on the inbound leg either — payouts are bounded only by SAC transfer failure at custody, and the asset-substitution variant is blocked only because the market key derives from `params.asset_id` ( [4](#0-3) ). Nothing constrains `declared amount ≤ actual tokens delivered` for `repay`.

The normal path masks this: the controller pulls `caller → pool` for the exact declared amount before invoking the pool ( [5](#0-4) ), so `declared == received` holds. But `repay` takes `payer` as an argument and is callable directly (the test invokes `t.client().repay(&payer, ...)` on the pool client), so an attacker skips the controller and supplies any `payer` they authorize.

### Impact Explanation
Each call with `declared = custody` on a zero-debt market pays the attacker the market's entire token balance as a "refund". Repeating per market drains the physical pool across all (hub, token) books: direct theft of user funds and protocol insolvency, since the cash/borrowed book is untouched while custody goes to zero — subsequent withdrawals reverts for lack of funds.

### Likelihood Explanation
A single unprivileged address reaches it in one transaction: no collateral, position, oracle dependency, or timing is needed — only a market whose scaled debt is zero (or any market, over-claiming past the debt), and the attacker's own `payer` authorization. The only uncertainty is whether `pool::repay` enforces a controller-only caller check not visible in the indexed snippets; the unit test calls it directly on the pool client, which suggests no such gate, but that could not be fully confirmed within the available iterations.

### Recommendation
Measure inbound funds (`balance_delta_since(pool)` around the operation, or have `repay` pull `transfer(payer → pool, declared)` itself) and bound the refund to the measured receipt — the same pattern `swap_tokens` already uses for router output ( [6](#0-5) ). Additionally, debit `cash` and run `require_reserves` on the refund leg so book and custody cannot desync.

### Proof of Concept
```rust
// Attacker holds zero tokens and transfers nothing.
// Market has no outstanding debt, so current_debt_ceil == 0.
let custody = token.balance(&pool);            // e.g. 1_000_000_000
pool_client.repay(
    &attacker,                               // payer
    &vec![&env, PoolAction {                 // ract(...)
        position: ScaledPositionRaw::default(),
        amount: custody,                     // declared, never delivered
        hub_asset: HubAssetKey { hub_id: 0, asset },
    }],
);
// resolve_repay -> full-close branch -> net_repay == 0
// refund = declared - used = custody, paid from pool balance
// attacker balance: +custody; pool book: cash still claims custody
```
Mirrors `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` ( [7](#0-6) ): `credited == 0` while the full declared amount is refunded to `payer` out of real custody.

#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
