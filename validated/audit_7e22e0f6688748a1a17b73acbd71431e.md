### Title
Router does not verify hop venue/pool identity: an attacker-authored route puts arbitrary contract code inside the signer's authorization tree and drains the signer's wallet - (File: docs/explanation/threat-model.md; contracts/swap-aggregator)

### Summary
CVE-2022-46176 is a missing-authentication-of-the-remote-peer bug: Cargo trusted whatever server answered on the SSH endpoint without pinning its host key. The direct analog in XOXNO Lending is the swap aggregator's route execution: `execute_strategy` invokes whatever pool/token addresses the caller-supplied payload names and keeps no allowlist of venues, so a malicious route places attacker-controlled code on the call stack underneath the sender's authorization. That code can issue `token.transfer(sender, attacker, amount)` calls that appear as legitimate children of the sender's signed auth tree, transferring funds far beyond the routed `total_in`.

### Finding Description
- `Router::execute_strategy(sender, total_in, swap_xdr)` decodes a `StrategyPayload` whose `assets` registry names arbitrary `C…` addresses for pools and tokens. `Program::decode` validates only index bounds and structural rules — never whether a pool address is a genuine Aquarius/Soroswap/etc. deployment.
- `venues::dispatch_hop` calls the payload-named `pool` contract; venue adapters then self-authorize input pulls, but nothing binds the callee to a known DEX contract.
- The threat model states this plainly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller … executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount." [1](#0-0) 
- The test fixture proves the primitive end-to-end: `UnlistedPoolRouter` mirrors the router behavior (pull `total_in`, invoke `route.hop_pool`), and `RogueHopPool::swap` performs `token.transfer(victim, attacker, amount)` from inside the hop call — an unauthorized wallet drain riding the caller's auth. [2](#0-1) 
- The composed path amplifies it: a controller strategy (`swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`) grants the router exactly one input transfer (`authorize_transfer_as_current`), so routed protocol funds are bounded — but a *direct* `execute_strategy` user's wallet is not, since the rogue hop can name any token the victim holds and any victim-signed auth will cover it. [3](#0-2) 

This mirrors the CVE precisely: just as Cargo connected to whatever claimed to be the git host without verifying its key, the router invokes whatever claims to be a swap venue without verifying its identity, and the peer's malicious code runs inside the caller's trust boundary.

### Impact Explanation
Theft of user funds. A victim who signs a crafted route (delivered via a malicious/compromised quote source or phishing UI) authorizes a transaction in which the attacker's pool contract drains arbitrary tokens from the victim's wallet — unbounded by `total_in`, `min_out`, or the residual cap, since the theft executes inside the hop call under the sender's auth entry rather than through vault accounting. This satisfies "theft of user funds" and exceeds mere route-quality slippage.

### Likelihood Explanation
Exploitation needs a victim to submit an attacker-constructed `swap_xdr`/auth tree — the same precondition as the original Cargo CVE (a user cloning from an attacker-in-the-middle endpoint). An unprivileged attacker deploys the rogue pool once and waits for any user to execute a route that names it; no privilege, timing race, or oracle manipulation is needed. Because pools are payload-controlled and the venue adapters invoke them unconditionally, the attack succeeds deterministically once a poisoned route is signed. Simulation tools that blindly attach the simulated auth tree (the documented default flow) make the malicious child transfers invisible to non-decoding users — hence the docs' insistence that clients "decode the route it signs."

### Recommendation
Maintain an on-chain allowlist (or registry hash) of legitimate venue pool contracts, governance-managed, and have `dispatch_hop` reject a `pool` address not present for the claimed venue opcode. Short of that, restrict each venue adapter to contract addresses matching a pinned WASM hash or deployer-verified set, so a route cannot substitute arbitrary code for a DEX pool. At minimum, surface a hard guarantee that honest venues never emit child transfers from `sender`, and enforce it structurally rather than relying on client-side route decoding.

### Proof of Concept
Already pinned in-repo: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` deploys `RogueHopPool` whose `swap()` executes `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` during the hop call; the router double invokes `route.hop_pool` with no identity check. Pointing a real `execute_strategy` payload's `assets[idx_a]` (pool index) at an attacker contract reproduces the same drain against any `sender` that signs the resulting auth tree, on both the direct router path and any token the victim holds.

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
}

/// Attacker-deployed "pool". `amount == 0` is the benign control.
#[contract]
pub struct RogueHopPool;

#[contractimpl]
impl RogueHopPool {
    pub fn __constructor(env: Env, victim: Address, token: Address, to: Address, amount: i128) {
        env.storage()
            .instance()
            .set(&symbol_short!("PLAN"), &(victim, token, to, amount));
    }

    pub fn swap(env: Env) {
        let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = env
            .storage()
            .instance()
            .get(&symbol_short!("PLAN"))
            .expect("plan is set by the constructor");
        if amount > 0 {
            token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
        }
    }
}

## Authorization model

The only signature is the sender's. `execute_strategy` calls `sender.require_auth()`, and the sender's auth entry must cover the nested `token_in.transfer(sender, router, total_in)`; simulation produces that tree (`transaction.simulated = true` envelopes already carry it — `attach_simulated_transaction` copies the simulator's `auth` into the op — and `simulateTransaction` produces it for a locally built one). Do **not** `transfer` or `approve` tokens to the router beforehand: the router pulls the input itself, and tokens sent ahead of time are not credited.

Every venue call is self-authorized by the router with invoker-contract auth (`venues/auth.rs::authorize_as_current` → `env.authorize_as_current_contract`): Phoenix and Sushi (`HopContext::authorize_pool_pull`) and Aquarius (`aquarius/pool.rs::invoke_pool_swap`) register `token_in.transfer(router, pool, amount_in)` before the pool pulls; Comet registers `token_in.approve(router, pool, amount_in, expiry)`, then `swap_exact_amount_in` with a nested entry for the pool's `transfer_from`, then clears the allowance; Soroswap transfers from the router to the pool directly. None of these appear in the sender's auth tree.

A contract calling the router (the lending controller in `contracts/controller/src/strategies/swap.rs`, or your own) is the `sender`: it runs `authorize_transfer_as_current(token_in, self, router, amount_in)` (`common/src/token.rs`) immediately before `execute_strategy(self, amount_in, swap)` and measures its own balance deltas afterward (`RouterOverspend = 501`, `NoSwapOutput = 502` in `common/src/errors.rs`). Details in [composition.md](composition.md).
