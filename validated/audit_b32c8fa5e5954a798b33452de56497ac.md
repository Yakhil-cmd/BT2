## Analysis

Knot DNS's CVE-2017-11104 is a class of bug where a cryptographic authentication check has an **improper time-validity computation**, letting a holder of an otherwise-valid key bypass the intended time-window restriction. The `ocore` analog is in the address-definition **`timestamp`/`mci`** authentifier operators, which are meant to bind a signature's validity to elapsed time/MC-depth, combined with **standalone (non-network-aware) signed messages** used by `is_valid_signed_package` in oscript/AA formulas and by `signed_message.validateSignedMessage()` elsewhere (e.g. arbiter contracts).

### Root cause

`validateDefinition()` explicitly forbids reference-dependent operators (`has`, `has one`, `seen`, `in merkle`, `in data feed`) when `objValidationState.bNoReferences` is set (i.e. the definition is being evaluated for a signed message that has no `last_ball_unit`), but it does **not** apply that same guard to the `mci`/`age`/`timestamp` operators: [1](#0-0) [2](#0-1) [3](#0-2) 

Consequently a definition such as `["timestamp", ["<", EXPIRY]]` (used to grant a key authority only "before EXPIRY") is accepted by `validateDefinition` for messages with `bNoReferences = true`.

When such a message is later authenticated, `signed_message.js` builds `objValidationState` for the non-network-aware branch by hard-coding `last_ball_timestamp` to `0` (and `last_ball_mci` to `-1` before the PEM-curves fix): [4](#0-3) 

That value then feeds directly into the `timestamp`/`mci` relation evaluators in `Definition.validateAuthentifiers`: [5](#0-4) 

Because `last_ball_timestamp` is always `0`, any `["timestamp", ["<", EXPIRY]]` condition is *always true* (0 is always less than any positive expiry) and any `["timestamp", [">", X]]` condition is *always false* — regardless of the real time at which the signature is verified. The check is computed from a stand-in constant rather than an actual, attacker-independent time reference, exactly mirroring the TSIG flaw of an "improper validity period check."

This path is reachable from an unprivileged unit/AA-trigger context: `is_valid_signed_package` in oscript explicitly allows the `last_ball_unit` field to be omitted (only `['signed_message', 'last_ball_unit', 'authors', 'version']` are permitted, none required except `authors`/`signed_message`) and calls `validateSignedMessage` exactly the same way: [6](#0-5) [7](#0-6) 

The same `validateSignedMessage` (with no `last_ball_unit`, hence `bNoReferences`) is also used for wallet-level authorization flows such as arbiter contracts: [8](#0-7) 

### Impact

Any AA or application (e.g. payment channels, arbiter contracts, delegated/time-limited signing authority implemented via `["and", [["sig", ...], ["timestamp", ["<", expiry]]]]`) that relies on the `timestamp` (or, pre-PEM-fix, `mci`) authentifier operator to bound the validity window of an **off-chain signed package** cannot actually enforce that expiry: a party holding a validly-signed package can present/replay it to an AA at any point in the future, and the "expired" check will always evaluate as still-valid. This can let a party retain spending/authorization power over AA funds after the delegation should have lapsed, or let a party dispute/replay stale channel state after the intended cutoff, resulting in unauthorized fund movement or fund freezing/disagreement about validity — matching the required impact bar (AA fund loss, unauthorized spending, or a party being unable to rely on time-limited authorization semantics that the protocol claims to support).

### Title
Improper validity-period check for `timestamp`/`mci` authentifier ops on non-network-aware signed messages allows indefinite replay of "expired" authorizations - (File: `definition.js`, `signed_message.js`)

### Summary
`is_valid_signed_package`/`validateSignedMessage` allow a signed message to omit `last_ball_unit`. In that mode, `signed_message.js` hard-codes `last_ball_timestamp = 0` (and `last_ball_mci = -1` pre-fix) when building `objValidationState` used to evaluate the signer's address definition. `definition.js`'s `validateDefinition` fails to disallow `mci`/`age`/`timestamp` conditions for such "no references" definitions (unlike `has`/`seen`/`in merkle`/`in data feed`, which are explicitly disallowed). The result is that a `timestamp`-bounded authorization embedded in an address definition can never truly expire when authenticated via a detached signed package.

### Finding Description
See root-cause analysis above: `definition.js:480-495` (missing `bNoReferences` guard) combined with `signed_message.js:241-252` (constant `last_ball_timestamp=0`) and the evaluator at `definition.js:1036-1048`.

### Impact Explanation
A time-limited signing authority or off-chain authorization check (`["timestamp", ["<", expiry]]`) embedded in an address definition and verified through `is_valid_signed_package`/`validateSignedMessage` never actually expires, letting a party replay an old, intentionally time-boxed authorization indefinitely — enabling unauthorized AA fund movement or bypass of intended dispute/expiry semantics in contracts relying on this mechanism.

### Likelihood Explanation
Reachable directly from oscript/AA formulas (`is_valid_signed_package`) or from wallet-level flows (`wallet.js` arbiter contract handling) using only a normally-obtained valid signing key — no privileged network position, hub, or node compromise needed, matching the "attacker with a valid key... bypasses authentication" pattern of CVE-2017-11104.

### Recommendation
In `definition.js`, extend the `bNoReferences` guard to the `mci`/`age`/`timestamp` cases so definitions containing these ops are rejected when used for non-network-aware signed messages, or alternatively require `last_ball_unit` (and thus a verifiable, chain-anchored timestamp/mci) whenever a definition being validated contains `mci`/`age`/`timestamp` conditions.

### Proof of Concept
1. Create address `A` with definition `["and", [["sig", {pubkey: P}], ["timestamp", ["<", EXPIRY]]]]`.
2. Sign a `signed_message` package as author `A` **without** a `last_ball_unit` field (satisfies `hasFieldsExcept` in `signed_message.js:132` and the `is_valid_signed_package` field check in `formula/evaluation.js:1672`).
3. Submit this package to an AA trigger (or arbiter-contract flow) via `is_valid_signed_package(package, A)` at any time after `EXPIRY`.
4. `validateSignedMessage` computes `last_ball_timestamp = 0` (`signed_message.js:251`), so `["timestamp", ["<", EXPIRY]]` evaluates `0 < EXPIRY` → `true` regardless of actual time, and the authorization is accepted as still valid.
