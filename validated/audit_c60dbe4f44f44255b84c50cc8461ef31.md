Found a structural analog in `pallet-psm` (Peg Stability Module) that mirrors the Rio LRT cross-asset withdrawal issue: users can mint the internal token by depositing one approved external asset and redeem a *different* approved external asset, with solvency enforced only per-`(internal_asset, external_asset)` debt/reserve slots and no per-account or per-deposit asset binding.

### Title
Cross-asset mint/redeem in `pallet-psm` lets a depositor extract a stronger reserve asset ahead of a predictable peg break, socializing the loss onto remaining holders - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm::mint` credits the caller with the fungible internal asset after depositing any approved `external_asset` into the PSM's shared reserve, and `pallet-psm::redeem` lets the caller burn that same fungible internal asset to withdraw *any other* approved `external_asset`, subject only to that asset's own `PsmDebt`/reserve balance [1](#0-0) [2](#0-1) . Because the internal token is fully fungible and not bound to the asset used to mint it, a user who anticipates a depeg/price-drop in one approved external stablecoin can mint with that asset (while it is still accepted at par) and immediately redeem a stronger external asset from the shared reserve, extracting value that was contributed by holders of the stronger asset and leaving the weakening asset's reserve/debt slot to be unwound later by whoever redeems it — exactly the "deposit asset1 / withdraw asset2" mechanism described in the Rio Network report (Sherlock M-12), generalized from LRT collateral to PSM-approved stablecoins.

### Finding Description
Each PSM instance tracks debt and reserve **per external asset**, not per depositor and not per deposited-asset identity:
- `PsmDebt<T>` is a `StorageDoubleMap<internal_asset, external_asset, Balance>` [3](#0-2) .
- `mint` only checks the aggregate `max_debt` ceiling and the per-`external_asset` ceiling weight before minting the fungible internal asset to the caller [4](#0-3) .
- `redeem` lets the caller choose *any* approved `external_asset` for the instance, checking only that asset's own `PsmDebt` and reserve balance, with no requirement that the caller ever deposited that asset [5](#0-4) .

Attack flow, matching the Rio report's invariant violation (deposit asset A, withdraw a different asset B, sharing A's loss with B's other depositors):
1. Attacker observes/anticipates an imminent depeg or slashing-like price drop of approved external asset `A` (e.g. a stablecoin losing its peg), analogous to the report's monitored slashing/withdrawal signal for cbETH/wstETH.
2. Attacker calls `mint(internal_asset, A, amount, max_fee)` while `A` still redeems/mints at the pallet's assumed 1:1 rate, increasing `PsmDebt[internal, A]` and the reserve of `A` [6](#0-5) .
3. In the same or a following block (no cooldown between mint and redeem exists anywhere in the pallet), attacker calls `redeem(internal_asset, B, amount, max_fee)` for a stronger asset `B`, which only requires `PsmDebt[internal, B]` and `B`'s reserve to be sufficient — both contributed by other users, not the attacker [5](#0-4) .
4. `A` then depegs. Because circuit breakers are governance/emergency-admin actions (`set_asset_status`) that react only after the fact [7](#0-6) , the pallet has no automatic protection between the attacker's mint and redeem. The PSM reserve now holds a disproportionate, devalued amount of `A` while `B`'s reserve is depleted; whoever later tries to redeem via `B` (or the protocol's `max_debt`-based solvency assumption) absorbs the shortfall — the same loss-transfer mechanic Sherlock accepted as valid Medium in the Rio audit.

This is a design-level cross-asset fungibility gap, not a miscalculation: `mint`/`redeem` never binds the caller's redeemable asset to their deposited asset, and the only proposed Rio mitigation ("allow users to withdraw only the type of assets they deposit") is precisely what `pallet-psm` does *not* implement.

### Impact Explanation
Medium: funds cannot be created out of thin air (mint/redeem require real 1:1 external-asset movement per swap, and fees apply), and reserves are always fully backed at the point of any single swap. But an attacker with advance knowledge of a depeg (public information, e.g. observing a stablecoin's reserve run, similar to observing slashing events) can shift which external asset backs their exposure before the loss materializes, extracting value from other depositors of the stronger asset. This matches the Rio report's own "MEDIUM" classification rationale: it requires a foreseeable price-drop condition and capital that cannot be obtained via flash loan (the attacker must already hold or acquire the depegging asset ahead of time to mint with it).

### Likelihood Explanation
Requires only a signed, permissionless call to two already-wired-up public extrinsics (`mint`, `redeem`) on any PSM instance with ≥2 approved externals — no privileged role, governance action, or flash loan is needed. Likelihood is bounded by the difficulty of predicting a depeg early enough (same constraint noted in the source report), and by whether a given PSM instance's admin reacts with `set_asset_status`/ceiling-weight changes before the attacker acts.

### Recommendation
Adopt the same mitigations Sherlock accepted for Rio:
- Track debt/redeemability per depositor+asset (or require redemption in the same external asset that was deposited) rather than allowing any approved external to be freely swapped against a shared fungible internal token.
- Enforce a minimum holding period between `mint` and `redeem` for the same account, or apply per-asset withdrawal rate limits tied to recent deposits.
- Consider tightening `MintingFee`/`RedemptionFee` asymmetrically or adding a global (not just per-asset) automatic freeze trigger keyed on observable price/peg-oracle deviation for external assets, since the current circuit breaker (`CircuitBreakerLevel`) is manual/reactive only.

### Proof of Concept
No local reproduction was executed. The finding is supported by static code inspection of `pallet-psm`'s `mint`/`redeem` dispatchables and storage layout, which confirms the debt/reserve model is keyed per `(internal_asset, external_asset)` with no cross-check binding a caller's redemption target to their prior deposit, and that circuit breakers are the only (reactive, admin-gated) mitigation [7](#0-6) . A concrete PoC would extend `substrate/frame/psm/src/tests.rs` (which already exercises multi-asset mint/redeem cycles, e.g. `mixed_decimal_mint_redeem_cycles_round_trip_to_zero_debt`) to: mint with asset A, redeem with asset B in the same block, then simulate A's external price/peg dropping (outside the pallet's accounting, since PSM has no oracle) to show B's remaining depositors are left with a reserve overweighted in devalued A relative to outstanding internal-asset claims.

			ensure!(external.status.allows_minting(), Error::<T>::MintingStopped);

			let ext_decimals = external.decimals;
			let internal_decimals = info.internal_decimals;

			let internal_equivalent =
				Self::external_to_internal(external_amount, ext_decimals, internal_decimals)?;
			ensure!(!internal_equivalent.is_zero(), Error::<T>::AmountTooSmallAfterConversion);
			ensure!(internal_equivalent >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);

			let effective_external =
				Self::internal_to_external(internal_equivalent, ext_decimals, internal_decimals)?;

			let fee_rate = MintingFee::<T>::get(&internal_asset, &external_asset);
			ensure!(fee_rate <= max_fee, Error::<T>::FeeTooHigh);
			let fee = fee_rate.mul_ceil(internal_equivalent);
			let internal_to_user = internal_equivalent.saturating_sub(fee);

		pub fn redeem(
			origin: OriginFor<T>,
			internal_asset: T::AssetId,
			external_asset: T::AssetId,
			internal_amount: BalanceOf<T>,
			max_fee: Permill,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let info = Psm::<T>::get(&internal_asset).ok_or(Error::<T>::PsmNotFound)?;

			let external = ExternalAssets::<T>::get(&internal_asset, &external_asset)
				.ok_or(Error::<T>::UnsupportedAsset)?;
			ensure!(external.status.allows_redemption(), Error::<T>::AllSwapsStopped);

			let ext_decimals = external.decimals;
			let internal_decimals = info.internal_decimals;

			ensure!(internal_amount >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);

			let fee_rate = RedemptionFee::<T>::get(&internal_asset, &external_asset);
			ensure!(fee_rate <= max_fee, Error::<T>::FeeTooHigh);
			let fee = fee_rate.mul_ceil(internal_amount);
			let internal_net = internal_amount.saturating_sub(fee);

			let external_out =
				Self::internal_to_external(internal_net, ext_decimals, internal_decimals)?;
			ensure!(
				internal_net.is_zero() || !external_out.is_zero(),
				Error::<T>::AmountTooSmallAfterConversion
			);
			// `effective_internal_net` is the internal value that round-trips to `external_out`;
			// it is what we actually burn and what the tracked debt decreases by. Any truncation
			// dust stays in the caller's internal balance, symmetric with `mint`, which takes
			// only the round-tripped share of the external amount.
			let effective_internal_net =
				Self::external_to_internal(external_out, ext_decimals, internal_decimals)?;

			let current_debt = PsmDebt::<T>::get(&internal_asset, &external_asset);
			ensure!(current_debt >= effective_internal_net, Error::<T>::InsufficientReserve);

			let reserve = Self::get_reserve(&internal_asset, &external_asset);
			if reserve < external_out {
				defensive!("PSM reserve is less than expected output amount");
				return Err(Error::<T>::Unexpected.into());
			}

			if !fee.is_zero() {
				T::Fungibles::transfer(
					internal_asset.clone(),
					&who,
					&info.fee_destination,
					fee,
					Preservation::Expendable,
				)?;
			}

			if !effective_internal_net.is_zero() {
				T::Fungibles::burn_from(
					internal_asset.clone(),
					&who,
					effective_internal_net,
					Preservation::Expendable,
					Precision::Exact,
					Fortitude::Polite,
				)?;
			}

			let psm_account = Self::psm_account(&internal_asset);
			if !external_out.is_zero() {
				T::Fungibles::transfer(
					external_asset.clone(),
					&psm_account,
					&who,
					external_out,
					Preservation::Expendable,
				)?;
