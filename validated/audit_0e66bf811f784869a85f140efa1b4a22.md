### Title
CCMenuController#stack bypasses api client stack scoping, allowing cross-stack CCMenu data read - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to `current_api_client.stack_id` via its `stacks`/`stack` helper methods, but `Shipit::Api::CCMenuController` overrides `#stack` to query `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` model. Combined with `ApiClient#check_permissions!` only checking the stack-agnostic string `'read:stack'`, any token holding `read:stack` (even one created for a single stack, e.g. via the CCMenu URL feature) can read CCMenu deploy/task data for any other stack by supplying a different `stack_id` param.

### Finding Description
The intended binding is: `current_api_client.stack_id == stack.id` (or `stack_id` unset, granting global access) must hold before the token's `read:stack` permission is honored for that stack. This is exactly what `BaseController#stacks` enforces: [1](#0-0) 

But `CCMenuController` redefines `#stack` to bypass this scope entirely: [2](#0-1) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which is a pure string-membership check with no stack identity in it at all: [3](#0-2) 

So for a token like the `here_come_the_walrus` fixture — created scoped to a single stack with only `read:stack` — `check_permissions!` returns `true` regardless of which `stack_id` is requested, and `CCMenuController#stack` happily resolves *any* stack from `params[:stack_id]`, not just the token's own stack. This is precisely the pattern the app itself uses to mint single-stack CCMenu tokens (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` scoped via `stack:` association) in `CCMenuUrlController`: [4](#0-3) 
and the `here_come_the_walrus` fixture demonstrating this exact scoped-token shape: [5](#0-4) 

Existing test coverage already inadvertently demonstrates the missing scoping check: the test `"stacks with no deploys render correctly"` authenticates with the fixture client (`@client`, whose `stack` association may differ) and successfully fetches an arbitrary, unrelated, freshly-created stack's CCMenu XML with no permission error: [6](#0-5) 

None of the documented guards intercept this: `verify_signature`/webhook checks are irrelevant to this API path; `ExplicitParameters` is not used here; `User#authorized?`/GitHub team checks never run because this is an API-token-authenticated read, not a web-session request; and `require_permission!` only delegates to the stack-agnostic `check_permissions!`. The only mechanism that could have prevented this — `BaseController#stacks`'s `current_api_client.stack_id?` scoping — is deliberately not used by `CCMenuController` because it overrides `#stack`.

Attacker flow: obtain (or be handed, e.g. via a shared/leaked CCMenu URL for stack A) a `read:stack`-only token scoped to stack A, then issue `GET /api/{stack_id_of_B}/ccmenu.xml?token=<tokenA>` (or via Basic Auth). The response renders stack B's latest deploy/rollback status, build label, activity and web URL — data the token was never meant to access.

### Impact Explanation
An attacker holding any `read:stack`-scoped CCMenu token (which by design in this codebase is handed out per-stack via `CCMenuUrlController` and is a low-privilege, narrowly-scoped credential) can read deploy/task state (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status) for **any stack in the Shipit instance**, not just the one the token was issued for. This matches "High - unauthenticated/unauthorized read of stack state, task streams or deploy output" since the token's authorization for one stack is being escalated to read all stacks. It is fully repeatable against arbitrary stacks by simply varying `stack_id` in the request, with no rate limiting or per-stack check blocking it.

### Likelihood Explanation
Preconditions are modest: the attacker needs possession of *some* valid `read:stack` token — which the app itself generates and distributes for CCMenu integration purposes (embedded in URLs users may configure in CI dashboards, share in tickets, etc.) — but does not need a token specifically for the target stack. No GitHub team membership, no Shipit session, and no secrets are required beyond the one token. Given CCMenu tokens are explicitly designed to be lightweight/shareable (embedded in a plain URL query string), and the exploit is a single GET request with a different `stack_id`, this is highly feasible and trivially repeatable.

### Recommendation
Make `CCMenuController#stack` use the same scoped lookup as the base controller instead of overriding it to query `Stack` directly, e.g. remove the local `#stack` override (or reimplement it as `stacks.from_param!(params[:stack_id])`) so that `current_api_client.stack_id`-scoped clients cannot resolve stacks outside their own scope.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a stack-scoped token cannot read another stack's CCMenu data" do
  scoped_client = shipit_api_clients(:here_come_the_walrus) # permissions: ['read:stack'], stack: shipit
  other_stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  assert_equal shipit_stacks(:shipit).id, scoped_client.stack_id
  refute_equal scoped_client.stack_id, other_stack.id

  request.headers['Authorization'] = nil
  get :show, params: { stack_id: other_stack.to_param, token: scoped_client.authentication_token }

  # Broken binding today: this currently returns :ok instead of :forbidden/:not_found
  assert_response :forbidden
end
```
This asserts the equality `current_api_client.stack_id == stack.id` is enforced (or request rejected when it isn't) — currently it is not, and the request succeeds with `:ok`, proving the vulnerability.
