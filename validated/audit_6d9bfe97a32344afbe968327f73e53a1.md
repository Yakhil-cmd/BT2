### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a stack-scoped token to read any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController#stacks` enforces that scoping for every endpoint that resolves a stack from client-controlled params. `Api::CCMenuController` overrides the `stack` resolution method to bypass this enforcement entirely, so a token that is only authorized for one stack can be used to read the build/deploy status of any other stack in the installation.

### Finding Description
`Api::BaseController` defines the canonical, scope-aware way controllers should resolve a stack from a request: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a specific stack, and `stack` builds on top of that scoped relation. This is the binding the engine relies on: *the stack(s) an `ApiClient` token authorizes* == *the stack(s) that token can touch*.

`Api::CCMenuController` breaks this binding. It authenticates via a raw `token` query-string param (not Basic Auth) and then defines its own `stack` method that ignores the scoped `stacks` relation entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the `ApiClient`'s permission list contains `read:stack` — via `ApiClient#check_permissions!`: [3](#0-2) 

It never checks that `current_api_client.stack_id` matches the requested `params[:stack_id]`. Since `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, any valid token with `read:stack` permission — even one created with a `stack_id` restricting it to a single stack (as in the `here_come_the_walrus` fixture) — can be replayed against `/api/stacks/:stack_id/ccmenu.xml` for a completely different `stack_id` and successfully retrieve that other stack's latest deploy/build status.

Before the request: token T is authorized only for Stack A (`current_api_client.stack_id == A.id`).
After the request: T is used with `params[:stack_id] == B.id`, and `Api::CCMenuController#show` renders Stack B's deploy status because `stack` resolves unscoped.

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" trust binding, letting a token deliberately scoped to a single stack read status/build/deploy information for other stacks in the same Shipit instance — an unauthorized cross-stack information disclosure of deploy state, matching the High-severity class of "unauthenticated/under-scoped read of stack state, task streams or deploy output."

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` `ApiClient` token (e.g., a CI dashboard integration or a limited-purpose credential deliberately restricted to one stack) can trigger this by simply changing the `stack_id` in the request URL — no special privileges, secrets, or session are required beyond the token itself, and the endpoint accepts the token via a simple query parameter.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, matching the behavior of every other `Api::BaseController` subclass, so that stack-scoped tokens cannot be used against stacks outside their authorized scope.

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A only (mirrors the `here_come_the_walrus` fixture): [4](#0-3) 
2. Compute its `authentication_token` (`ApiClient#authentication_token`): [5](#0-4) 
3. Send `GET /api/stacks/<Stack-B-id>/ccmenu.xml?token=<token>` where Stack B is a different, unrelated stack.
4. Observe that `Api::CCMenuController#show` returns Stack B's build/deploy status (name, `lastBuildStatus`, `lastBuildLabel`, etc.) even though the token is only supposed to be authorized for Stack A, because `stack` resolves via `Stack.from_param!` rather than the scoped `stacks.from_param!`: [6](#0-5)
