### Title
CCMenuController#stack bypasses api-client stack scoping, allowing cross-tenant stack read via CCTray XML - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`BaseController#stack` scopes lookups through `stacks.from_param!`, where `stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` whenever the authenticating `ApiClient` is scoped to a single stack. `CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, completely skipping the `current_api_client.stack_id` restriction, so a token scoped to attacker's stack can read any other stack's CCTray status.

### Finding Description
The intended binding is: for every `BaseController` subclass, `stack == stacks.from_param!(params[:stack_id])`, where `stacks` enforces `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) .

`HooksController` relies on the inherited `stack` (via `#stack_id`), so `Hook.where(stack_id:)` is correctly scoped and a token restricted to the attacker's stack raises `RecordNotFound` (404) for any other stack id [2](#0-1) .

`CCMenuController`, however, redefines `stack` locally:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

This calls `Stack.from_param!` on the unscoped `Stack` model class rather than on `stacks` (the request-scoped relation), so the `current_api_client.stack_id` filter defined in `BaseController#stacks` is never applied. The permission check only verifies the client holds `read:stack` in its `permissions` list [4](#0-3) , it does not verify which stack the token is scoped to. Authentication itself only verifies the token's signature, not stack scope [5](#0-4) . As a result, `authenticate_api_client` in `CCMenuController` (custom override supporting `?token=`) succeeds for any valid, unrevoked token regardless of its `stack_id`, and `#show` then resolves and renders any victim stack's CI status/last build info [6](#0-5) .

Attacker flow: attacker holds a token whose `ApiClient#stack_id` is scoped to their own stack and which has `read:stack` permission. They send `GET /api/stacks/:victim_stack/hooks?token=<token>` and correctly receive 404 (confirms `HooksController` scoping works). They then send `GET /api/stacks/:victim_stack/cc.xml?token=<token>` (or whatever route maps to `CCMenuController#show`) and receive `200 OK` with the victim stack's CI project name, last build status, last build label, and last build time — data about a repository/stack the token was never authorized to access.

None of the existing guards prevent this: `require_permission :read, :stack` only checks the permission bit, not stack ownership; `authenticate_api_client` only validates the token signature; and the `stacks` scoping mechanism that would have blocked this is simply never invoked because `CCMenuController` bypasses it by calling `Stack.from_param!` directly instead of `stacks.from_param!`.

### Impact Explanation
This is an unauthenticated-for-that-resource / unauthorized read of stack state: a token scoped to stack A can read stack B's CCTray status (name, last build status/label/time, activity) for any and all stacks in the Shipit installation, not just one victim. It is fully repeatable against arbitrary stacks by iterating `stack_id` and requires only a single valid `read:stack` token. This matches the "High - unauthenticated read of stack state" impact category. It does not by itself achieve write/mutation or secret exfiltration, so it is not Critical.

### Likelihood Explanation
Preconditions: attacker needs any valid `ApiClient` token with `read:stack` permission (even if scoped to a single, attacker-owned stack) — a very low bar, since API clients with `read:stack` are the normal, non-privileged use case for CI status badges. No GitHub secrets, session, or elevated permissions are required. The attack is a single unauthenticated (from the victim's perspective) GET request per target stack. Feasibility is high and cost is trivial.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` relation instead of the raw `Stack` model, matching every other controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This should also be removed entirely if it adds no value over the inherited `BaseController#stack`; there's no clear need to override it.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to one stack cannot read another stack via CCMenu" do
  attacker_stack = shipit_stacks(:shipit)
  victim_stack = Stack.create!(repository: Repository.new(owner: "victim", name: "repo"), branch: "main")

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: "scoped",
    stack_id: attacker_stack.id,
    permissions: ['read:stack', 'read:hook']
  )
  token = scoped_client.authentication_token

  # Control: HooksController correctly scopes and 404s for the victim stack
  get :index, controller: 'shipit/api/hooks', params: { stack_id: victim_stack.to_param, token: }
  assert_response :not_found

  # Vulnerable path: CCMenuController ignores the scope and returns 200
  request.headers['Authorization'] = nil
  get :show, params: { stack_id: victim_stack.to_param, token: }
  assert_response :ok # should be :not_found, proving the divergence
end
```
This paired test asserts both sides of the binding: `HooksController#index` correctly returns 404 (scoped lookup via `stacks.from_param!`), while `CCMenuController#show` returns 200 for the same token/victim-stack pair (unscoped lookup via `Stack.from_param!`), proving the exploitable divergence.
