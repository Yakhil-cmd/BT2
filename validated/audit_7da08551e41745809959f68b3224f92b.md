### Title
`StatusHandler#process` updates commit status by sha alone, unscoped to the webhook's originating repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire database and calls `commit.create_status_from_github!(params)` on every match, with no check that the commit's `stack.github_repo_name` matches the webhook payload's `repository.full_name`. Every other handler (e.g. `PushHandler`) explicitly scopes to `stacks` derived from `Repository.from_github_repo_name(repository_name)`, but `StatusHandler` does not use this scoping at all.

### Finding Description
The binding the question implies - "only statuses fetched via `stack.github_api` (scoped to `github_repo_name`) determine `deployable?`" - is already false today, independent of any timing race with `RefreshStatusesJob`: a *webhook-delivered* status is written straight into `commit.statuses` via `StatusHandler#process`: [1](#0-0) 
without any comparison against `payload.dig('repository', 'full_name')`. Compare with `Handler#stacks`, which every properly-scoped handler (e.g. `PushHandler`) uses to restrict itself to stacks whose repository matches the webhook's repository: [2](#0-1) [3](#0-2) 

`StatusHandler` never calls `stacks`; it queries `Commit` globally by `sha` only: [4](#0-3) 

`create_status_from_github!` then writes the forged state directly and re-evaluates `deployable?`/fires `deployable_status`/schedules merges, all without ever calling `stack.github_api`: [5](#0-4) [6](#0-5) [7](#0-6) 

Signature verification (`WebhooksController#verify_signature`) only proves the request came from GitHub for the organization named in the payload's `repository.owner.login` / `organization.login`; it says nothing about which specific repository within that org, or about any other org's commits sharing the same sha: [8](#0-7) 

Given identical git content (same tree, parents, author/committer, timestamps and message) produces an identical sha regardless of which repository it lives in, any repo that shares a commit with a victim's tracked branch - most commonly a PR head commit that exists both in a contributor's fork and, byte-for-byte, in the upstream repository before/at the moment of push - can trigger a real, correctly-signed `status` webhook from GitHub for the attacker's own fork/repo. `StatusHandler` then finds and mutates every `Commit` row across the whole installation with that sha, including the victim stack's commit, marking it `success` regardless of the victim repo's actual CI outcome. This immediately affects `commit.deployable?`: [7](#0-6) 
and can trigger `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery` → `Stack#trigger_deploy` for the victim stack if `continuous_deployment` is enabled, exactly per the question's scenario, independent of whether `RefreshStatusesJob` runs before or after - the forged write itself, not just a race with the periodic refresh, is what breaks the intended repository-scoping guarantee. `RefreshStatusesJob`/`refresh_statuses!` only fixes this on its next run by re-pulling from `stack.github_api.statuses(github_repo_name, sha, ...)`, which is correctly scoped: [9](#0-8) 
but that is a post-hoc correction, not a guard, and a `ContinuousDeliveryJob` tick that lands between the forged webhook and the next refresh can already have queued/triggered a `Deploy`.

None of `verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema validation, `force_github_authentication`, `require_permission!`, or model validations prevent this, because they all operate at the org/session/parameter layer, not at the "does this commit belong to a stack whose repository matches this webhook's repository" layer, which is the one check that is missing.

### Impact Explanation
An attacker who owns (or forks) any repository that can be onboarded to the target Shipit instance, and who can arrange for a commit sha to be shared with a victim stack's tracked commit (the standard PR-fork-shares-head-sha case, or any repo mirroring/duplicating history), can post a real GitHub commit status of `success` on that sha in their own repo. This is delivered to Shipit as a legitimately-signed webhook, and `StatusHandler` applies it to the victim's `Commit` row, flipping `deployable?` to true and potentially causing `ContinuousDeliveryJob` to trigger an **unauthorized deploy** on the victim stack - a Critical-severity outcome per the category "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." The attack is repeatable against any stack/repository pair that can be made to share a commit sha, and its blast radius spans all stacks/tenants served by the same Shipit installation (or, for the shared-org case, any repo under the same GitHub organization/app installation).

### Likelihood Explanation
Preconditions: Shipit must have `continuous_deployment` enabled on the victim stack for the immediate deploy-triggering path (weaker impact - state corruption/blocking of legitimate deploys - is possible even without CD); the attacker needs a commit sha collision with a tracked commit, which is realistically achievable via the common PR-from-fork pattern (the fork's head commit and the upstream PR head commit share the same sha before any rebase/merge) or by the attacker deliberately reproducing an existing victim commit's exact tree/parents/metadata in their own repo. The attacker's own repo must be reachable by a GitHub App/webhook installation known to this Shipit instance (e.g., same GitHub organization, or Shipit configured to accept the attacker's own org), which is a real but not always trivially satisfied requirement, and can be satisfied simply by opening a PR from a fork against a repo Shipit already tracks. No Shipit credentials, sessions, or secrets are needed.

### Recommendation
Scope `StatusHandler#process` (and any other webhook handler that resolves records purely by sha) to the repository named in the webhook payload, mirroring the pattern used in `Handler#stacks`/`PushHandler`: resolve `stacks` from `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update commits belonging to those stacks, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { ... }` instead of `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "a status webhook from an unrelated repository must not update a commit belonging to another stack" do
          victim_stack = shipit_stacks(:shipit)               # repo: shopify/shipit-engine
          attacker_stack = shipit_stacks(:cyclimse)            # unrelated repo/org

          shared_sha = "deadbeef" * 5
          victim_commit = victim_stack.commits.create!(
            sha: shared_sha, message: "shared content", author: shipit_users(:walrus),
            committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now
          )

          # binding under test: only statuses reachable via victim_stack.github_api
          # (scoped to victim_stack.github_repo_name) should be able to set
          # victim_commit.state == 'success'
          refute_equal 'success', victim_commit.reload.state

          # forged/legitimate webhook payload whose "repository" is the ATTACKER's repo,
          # but whose sha collides with the victim's tracked commit
          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'repository' => { 'full_name' => attacker_stack.github_repo_name,
                               'owner' => { 'login' => attacker_stack.repository.owner } }
          }

          StatusHandler.call(payload)

          # Assert both sides of the equality: the forged, unscoped write must NOT
          # have been able to flip the victim's state/deployable? without going
          # through victim_stack.github_api.
          refute_equal 'success', victim_commit.reload.state,
            "cross-repository forged status must not update a commit belonging to a different stack"
          refute victim_commit.deployable?
        end
      end
    end
  end
end
```

This test is expected to **fail** against the current `StatusHandler#process` implementation (it currently updates `victim_commit` because the lookup is unscoped), demonstrating the break in the claimed binding, and would pass once the handler is scoped by repository as described in the Recommendation.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
