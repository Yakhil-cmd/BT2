## Title
`liquidate-multi` batch liquidations can be entirely aborted by a runtime panic in `process-debt-asset`, defeating its designed front-running protection - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` is explicitly documented as returning one response per position, "Failed liquidations return error codes but don't revert entire batch" [1](#0-0) . However, the per-position helper `call-liquidate` invokes `liquidate` directly, and `liquidate` calls `process-debt-asset`, which does `(unwrap-panic (find-asset debt-aid assets))` [2](#0-1) . If `debt-aid` is not present in the borrower's currently-enabled asset list (`assets`, derived from the borrower's live egroup mask), `find-asset` returns `none` and `unwrap-panic` triggers a hard runtime abort of the *entire* Clarity transaction — not a caught error captured inside the per-position response list. This is functionally identical to the reported Lombard `consortium-node` bug: a single malformed/adversarial input causes an unconditional panic instead of a locally-scoped error, crashing shared batch processing.

### Finding Description
- Shared state: the single Stacks transaction executing `liquidate-multi`, which is supposed to independently process a list of up to 64 unrelated borrower positions [3](#0-2) .
- Attacker: a borrower included in the batch (call them Borrower A) who is about to be liquidated. Before the liquidator's `liquidate-multi` transaction is mined, Borrower A front-runs with a `collateral-remove`/`collateral-add`/`repay` call that changes their egroup mask so that the specific `debt-ft`/`debt-aid` the liquidator computed for them is no longer part of their new `assets` list (e.g., the debt asset becomes disabled/unenabled for the new mask).
- Victim: any other borrower(s), e.g., Borrower B, batched in the *same* `liquidate-multi` call whose positions are genuinely unhealthy and should be liquidated to cap protocol bad debt.
- Root cause: `process-debt-asset` uses `unwrap-panic` on `find-asset debt-aid assets` [4](#0-3)  instead of returning a controlled `(err ...)`. Because `call-liquidate`/`liquidate` are invoked in-contract via direct function calls (not `contract-call?`) inside `(map call-liquidate positions)` [5](#0-4) , a Clarity runtime panic anywhere in that call graph aborts the whole transaction, unwinding every position in the batch — including Borrower B's otherwise-valid liquidation.

### Outcome with vs. without the attacker's transaction
- Without Borrower A's front-run: `liquidate-multi([A, B])` succeeds for B (and either succeeds or cleanly errors-out for A inside its per-position response slot), per the documented "failed liquidations don't revert entire batch" guarantee.
- With Borrower A's front-run: the same call reverts entirely via `unwrap-panic`, so Borrower B's liquidation also fails in that block, even though B's position was unrelated and correctly specified. The liquidator must detect and drop A, then resubmit — delaying B's liquidation.

### Impact Explanation
This directly defeats the batch function's stated purpose — "Prevents front-running attacks that prevent bad debt socialization" [6](#0-5)  — by turning it into a mechanism that lets one borrower's front-run action DoS liquidation of every other borrower bundled in the same transaction. Delayed liquidation of unhealthy positions during volatile price moves increases the risk of the collateral value falling below the debt before liquidation actually executes, i.e. temporary freezing of the liquidation path for victim positions and increased risk of protocol insolvency from unrealized bad debt that keeps growing while keepers retry.

### Likelihood Explanation
Likelihood is moderate: it requires a borrower to notice they're about to be liquidated (mempool visibility) and issue a mask-changing transaction (`collateral-remove`, `repay`, etc.) before the liquidator's `liquidate-multi` transaction confirms, and it requires the liquidator/keeper to have batched that borrower together with others. Given keepers are incentivized to batch multiple due liquidations for gas efficiency, and front-running liquidation to gain time is a standard defensive move by borrowers, this is a realistic griefing vector rather than a purely theoretical one.

### Recommendation
Replace the `unwrap-panic` calls in `process-debt-asset` (and similarly in `process-collateral-asset`'s `unwrap-panic (price-resolve oracle-data)` at line 814, and the other `unwrap-panic (get-cached-indexes ...)` calls) with `unwrap!`/`try!`-based error propagation that produces a normal `(err ...)` response. Since `liquidate-multi` already wraps each call in a response, converting these panics into ordinary errors would let `map call-liquidate` naturally capture the failure for that single position while allowing the other positions in the batch to proceed, restoring the guarantee documented in the code's own comments.

### Proof of Concept
1. Liquidator observes Borrowers A and B are both liquidatable and builds `liquidate-multi([A-entry, B-entry])`, where `A-entry.debt-ft` corresponds to `debt-aid = X`, currently enabled in A's egroup mask.
2. Borrower A submits (and gets mined first, e.g., via higher fee) a `collateral-remove`/`repay` transaction that changes A's active debt/collateral composition such that A's egroup mask no longer includes asset `X` as an enabled debt asset (or disables it).
3. Liquidator's `liquidate-multi` transaction executes: `call-liquidate` for A calls `liquidate` → `process-debt-asset` → `find-asset X assets` returns `none` → `unwrap-panic` fires, aborting the entire transaction.
4. Result: Borrower B's liquidation, which had nothing to do with A's front-run, also fails to execute in that block, even though `liquidate-multi`'s own documentation states failed entries "don't revert entire batch."

```text
(define-private (process-debt-asset
  (debt-amount uint)
  (debt-aid uint)
  (max-debt-usd uint)
  (assets (list 64 {
    id: uint, addr: principal, decimals: uint,
    oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
    collateral: bool, debt: bool, price: uint
  })))
  (let ((debt-asset-info (unwrap-panic (find-asset debt-aid assets)))
        (debt-price (get price debt-asset-info))
        (debt-decimals (get decimals debt-asset-info))
        (debt-usd (normalize (* debt-amount debt-price) debt-decimals false))
        ;; cap debt at maximum liquidatable amount
        (debt-actual-usd (if (> debt-usd max-debt-usd) max-debt-usd debt-usd))
        ;; convert capped USD amount back to token amount
        (debt-actual (mul-div-down debt-actual-usd (pow u10 debt-decimals) debt-price)))
    {
      debt-actual-usd: debt-actual-usd,
      debt-actual: debt-actual,
      debt-price: debt-price,
      debt-decimals: debt-decimals
    }))
```
