Found it: `Api::CCMenuController#stack` in `app/controllers/shipit/api/ccmenu_controller.rb` breaks the "stack a token authorises versus the stack it touches" binding.

### Title
CCMenu API endpoint discloses deploy status of any stack regardless of the authenticating token's stack scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` looks up the target stack directly via `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping method defined in `Api::BaseController` that all other API controllers use to enforce that a stack-scoped `ApiClient` can only touch the stack it was issued for.

### Finding Description
`Api::BaseController#stacks` is the trust boundary that binds an `ApiClient`'s authorization to a single stack when the client was created with a `stack_id`: [1](#0-0) 
Every other stack-scoped controller (`Api::StacksController`, `Api::LocksController`, etc.) resolves the target stack through this `stacks` scope, so `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb`) effectively also constrains *which* stack is affected, not just which operation is allowed.

`Api::CCMenuController`, however, overrides `#stack` to look it up unscoped:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This uses the global `Stack.from_param!` instead of the `stacks` (client-scoped) relation. The controller still declares `require_permission :read, :stack`, which only checks that the token has the `read:stack` *permission string* — it never verifies that `current_api_client.stack_id` (if set) matches the requested `params[:stack_id]`.

So the binding "stack a token authorizes" (equal to `current_api_client.stack_id`) versus "stack a request touches" (`params[:stack_id]` resolved via `Stack.from_param!`) is broken specifically in this controller: any token holding the generic `read:stack` permission — even one that was deliberately scoped by an operator to a single, low-sensitivity stack (e.g. via `ApiClient.create_with(stack: stack_a)`) — can call `GET /api/:any_stack_id/cc_menu.xml` for a completely different stack it was never authorized to see.

### Impact Explanation
This qualifies as the High-severity category "unauthenticated/unauthorized read of stack state, task streams or deploy output" defined in scope. The CCMenu response exposes deploy/rollback state (`stack.deploys_and_rollbacks.last`), which can reveal branch/environment activity, deploy status, and timing across stacks the token holder was never granted access to — an authorization-scope escape enabled purely by the engine's own controller code, requiring nothing beyond possession of any valid `read:stack`-scoped API token (which is explicitly an in-scope credential class, unlike webhook secrets or GitHub App keys).

### Likelihood Explanation
Likelihood is high: any consumer already holding a legitimately-issued, stack-scoped API token (e.g. the "CCMenu Client" token that `CCMenuUrlController` itself generates per-user, scoped with `permissions: %w[read:stack]` and no `stack:` restriction is even the default in `CCMenuUrlController#client` at `app/controllers/shipit/ccmenu_url_controller.rb` lines 15-18) can simply substitute any other stack's `stack_id` in the URL, since `#authenticate_api_client` only checks the bearer token's `read:stack` permission bit and `#stack` never re-validates the resolved `Stack` against `current_api_client.stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped relation, consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the binding `current_api_client.stack_id == stack.id` (when the client is stack-scoped) before serving the CCMenu XML.

### Proof of Concept
1. As a Shipit operator, issue a stack-scoped API client for `stack_a`:
   ```ruby
   client = ApiClient.create!(creator: some_user, name: 'ccmenu', stack: stack_a, permissions: %w[read:stack])
   token = client.authentication_token
   ```
2. Note that `stacks` (the scoped relation used elsewhere) would return only `stack_a`: [2](#0-1) 
3. Request the CCMenu endpoint for an unrelated, sensitive stack `stack_b`:
   ```
   GET /api/stack_b_owner/stack_b_name/stack_b_env/cc_menu.xml?token=<token>
   ```
4. `Api::CCMenuController#authenticate_api_client` succeeds because the token is valid and has `read:stack`: [3](#0-2) 
5. `#stack` resolves `stack_b` directly via `Stack.from_param!`, ignoring `client.stack_id`: [4](#0-3) 
6. `#show` renders `stack_b`'s latest deploy/rollback status, which the token was never authorized to view: [5](#0-4)
