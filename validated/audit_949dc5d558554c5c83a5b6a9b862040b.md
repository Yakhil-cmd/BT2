### Title
`StatusHandler#process` resolves commits by `sha` only, letting a status from any GitHub org fire `Hook.emit(:commit_status/:deployable_status)` for an unrelated victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up affected commits with `Commit.where(sha: params.sha)`, with no repository/stack scoping, unlike every other handler in this codebase (e.g. `PushHandler`, `PullRequest::*Handler`) which all resolve the target via `Handler#stacks`, i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. Because `sha` is not a value scoped to a single repository in Shipit's data model, a `status` webhook whose signature is valid for the *sender's own* GitHub organization/repository can still match `Commit` rows belonging to a completely different stack, causing `Commit#add_status` to call `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)` for that victim stack.

### Finding Description
The binding the question asks about should hold as: `commit.stack.repository == payload.dig('repository', 'full_name')` for every commit that a status webhook is allowed to mutate. Tracing the code:

- `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)`, which for `status` events is `[Handlers::StatusHandler]`. [1](#0-0) 
- `verify_signature` only checks that the payload was signed by the org named in `payload.dig('repository','owner','login')` (or `organization.login`), via `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [2](#0-1) 
This proves authenticity of "this request really came from GitHub for org X," but says nothing about which `Commit`/`Stack` rows the handler is permitted to touch.
- The generic `Handler` base class provides a `stacks` helper that scopes lookups to the payload's own repository: `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name = payload.dig('repository', 'full_name')`. [3](#0-2) 
- `PushHandler` and the `PullRequest::*` handlers all use this `stacks` scoping before doing anything. [4](#0-3) 
- `StatusHandler#process`, however, bypasses `stacks` entirely and queries `Commit` globally by `sha`: [5](#0-4) 
- For every matched `Commit`, regardless of which stack/repository it belongs to, `create_status_from_github!` → `add_status` runs, and on a state transition calls `Hook.emit(:commit_status, stack, payload)` and/or `Hook.emit(:deployable_status, stack, payload)` using `commit.stack` - the *victim's* stack - not anything derived from the incoming payload's repository. [6](#0-5) 

Exploit flow: an attacker who owns/controls any repository whose commit history intersects with a tracked victim stack's commit history (e.g. a public fork of the victim's repo, or any repo sharing a SHA that Shipit happens to have recorded for the victim commit - forks retain identical SHAs for shared history) can, from their own repository, issue a real (or self-created, legitimately-signed-by-their-own-org) `status` event for that shared `sha`. GitHub will sign this webhook validly for the attacker's own organization, which is all `verify_signature` checks. `StatusHandler` then finds the victim's `Commit` row purely by `sha` match and fires the victim stack's hooks - Slack notifications, deploy dashboards, etc. - as if the status came from the victim's own CI/repository.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema in `StatusHandler.params`) validate webhook authenticity and payload shape, but none of them check `payload.dig('repository','full_name')` against the matched commit's `stack.repository`. The two sides of the equality (`commit.stack.repository` vs `payload['repository']['full_name']`) are never compared anywhere in this path, confirming the divergence claimed in the question.

### Impact Explanation
An attacker-controlled repository's status webhook can cause `Hook.emit` to fire for a victim stack's `Hook` rows (Slack/dashboard/etc.), i.e. a payload authenticated for repository A mutates/triggers side effects tied to stack/repository B's hooks - matching the "payload for one repository mutating another's stack" Critical category. The victim stack's `schedule_merges` can also be scheduled (`stack.schedule_merges if new_status.pending? || new_status.success?`), potentially influencing downstream merge automation for the victim, not just notification noise. This is repeatable for any sha shared between attacker- and victim-tracked commits (most straightforwardly, forks of the same upstream repo, which is a common Shipit deployment pattern).

### Likelihood Explanation
Preconditions: the victim stack must have `Hook` rows for `commit_status`/`deployable_status`, and there must exist a `sha` that is recorded as a `Commit` in the victim's stack while the attacker can trigger (or already has) a legitimately-signed `status` webhook referencing that same `sha` from a repository/org they control. The most realistic route is a public fork relationship, which is common (Shipit explicitly supports forks/PR-based workflows). The attacker needs no Shipit credentials, no `webhook_secret`, and no privileged GitHub role - only the ability to create a repository/organization and get GitHub to sign a `status` webhook for it (or, in some GitHub App configurations, send it directly), which is normal unprivileged GitHub usage.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository, mirroring the pattern used by `PushHandler`/`PullRequest` handlers: resolve commits only through `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` (or equivalently filter `Commit.where(sha: params.sha)` by `stack_id: stacks.pluck(:id)`), so `Hook.emit` can never fire for a stack whose `Repository#github_repo_name` differs from `payload.dig('repository', 'full_name')`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook does not fire hooks for a stack whose repository differs from the payload's repository" do
  victim_stack = shipit_stacks(:shipit)                 # tracks "shopify/shipit-engine" (Repository)
  attacker_repo_full_name = "attacker/unrelated-fork"    # different repository entirely

  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared history", author: shipit_users(:shipit))

  # Sanity: binding under test - these must be equal for the emit to be legitimate
  assert_not_equal victim_stack.repository.full_name, attacker_repo_full_name

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Hook.expects(:emit).with(:commit_status, victim_stack, anything).never
  Shipit::Hook.expects(:emit).with(:deployable_status, victim_stack, anything).never

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)
end
```
Running this test against the current `StatusHandler#process` (`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`) fails, because `Hook.emit` is invoked for `victim_stack` despite the payload's `repository.full_name` not matching `victim_stack.repository.full_name` - demonstrating the missing repository-equality check.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      end
