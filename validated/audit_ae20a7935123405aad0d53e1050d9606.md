### Title
Unconditional webhook signature bypass for orgs without `webhook_secret` allows forged `pull_request:assigned` events to corrupt persisted `PullRequest` records - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the org's config has no `webhook_secret`, before any signature/algorithm check is even reached. For such an org, `WebhooksController#verify_signature` therefore accepts *any* payload with *any* (or no) `X-Hub-Signature` header, letting an unauthenticated attacker forge a `pull_request` `assigned`/`unassigned` event that reaches `AssignedHandler#process` and mutates the stored `PullRequest.github_pull_request` for any matching PR under that org's repositories.

### Finding Description
The intended binding is: *a webhook is only trusted if it is HMAC-signed with the secret configured for `repository_owner`'s org* — i.e. `verified == (signature valid for configured webhook_secret)`. The actual code breaks this binding: [1](#0-0) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

When `@webhook_secret` is blank (org configured without one), the method short-circuits to `true` before ever inspecting `signature` or `message`. `WebhooksController#verify_signature` calls this with `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON body: [2](#0-1) [3](#0-2) 

So an attacker simply sets `repository.owner.login` (or `organization.login`) to the name of any org that Shipit has configured without a `webhook_secret`, sends `X-Github-Event: pull_request` with a body `{"action":"assigned","number":N,"pull_request":{...},"repository":{"full_name":"org/repo"},"sender":{"login":"attacker"}}`, and no valid signature (or none at all — the header is never even parsed in this branch) is required. The request passes `verify_signature` unconditionally, `drop_unhandled_event` passes because `pull_request` has registered handlers, and `Shipit::Webhooks.for_event('pull_request')` dispatches to `AssignedHandler`, whose `params` validator only checks payload *shape*, not authenticity: [4](#0-3) [5](#0-4) 

`process` looks up the persisted `Shipit::PullRequest` by `number` and `repository.id` (resolved from the attacker-supplied `full_name`) and calls `.update(github_pull_request: params.pull_request)` with fully attacker-controlled hash contents (title, additions/deletions, labels, assignees, head sha/ref, state) whenever `action` is `assigned` or `unassigned`.

No other guard intervenes: `check_if_ping` only special-cases `event == 'ping'`; `drop_unhandled_event` only checks handler presence, not authenticity; there is no `force_github_authentication`, `User#authorized?`, or team check anywhere on this controller — it is intentionally unauthenticated and relies solely on `verify_signature` for trust, which is exactly the control that fails open.

The "legacy sha1" framing in the question is actually a subset of a broader hole: even with a properly signed `sha1=` header the algorithm restriction (`return false unless algorithm == 'sha1'`) is real, but it's moot for a no-secret org because the `return true unless webhook_secret` guard exits before that check is ever reached — no signature of any kind is required.

### Impact Explanation
For any org configured without `webhook_secret`, an unauthenticated internet requester can inject arbitrary, persisted state changes into `Shipit::PullRequest` records (title, diff stats, head SHA/ref, labels, assignees) for every repository under that org, repeatable at will and for any PR number/repository combination in that org's stacks. This is a full authentication bypass on the webhook trust boundary and a payload-controlled write to persisted application state — matching the Critical category ("forged webhook ... accepted as trusted", record mutation not authenticated by the claimed source).

### Likelihood Explanation
Preconditions: an org entry in Shipit's GitHub app configuration must have no `webhook_secret` set. No GitHub secrets, Shipit session, API token, or team membership is required — the attacker only needs to know/guess a configured org login and repository/PR number, both discoverable via the public Shipit UI or GitHub itself. Cost is a single unauthenticated `POST /webhooks` request; fully repeatable.

### Recommendation
Do not treat a missing `webhook_secret` as "trust everyone." At minimum, `verify_webhook_signature` should reject (return `false`) when `webhook_secret` is blank rather than short-circuiting to `true`, and/or Shipit configuration validation should require a non-empty `webhook_secret` for every configured GitHub org/app before webhooks are accepted for it. Additionally, support/require `X-Hub-Signature-256` (sha256) rather than only legacy `sha1`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "org without webhook_secret accepts forged pull_request:assigned and mutates PullRequest" do
  # Given: org config has no webhook_secret (simulate via GitHubApp.new(org, {}))
  pr = shipit_pull_requests(:some_pr) # existing PullRequest for a stack under repo "org/repo"

  @request.headers['X-Github-Event'] = 'pull_request'
  # deliberately send NO valid signature / garbage signature
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef'

  forged_payload = {
    action: 'assigned',
    number: pr.number,
    pull_request: {
      id: 999999, number: pr.number, url: 'http://x', title: 'PWNED',
      state: 'open', additions: 1, deletions: 1,
      head: { sha: 'deadbeef', ref: 'evil' },
      user: { login: 'attacker' },
      assignees: [{ login: 'attacker' }],
      labels: []
    },
    repository: { full_name: pr.stack.repository.full_name, owner: { login: 'org-without-secret' } },
    sender: { login: 'attacker' }
  }.to_json

  post :create, body: forged_payload, as: :json

  assert_response :ok
  assert_equal 'PWNED', pr.reload.github_pull_request['title']
end
```
Binding checked before/after: `verified == HMAC_valid(webhook_secret, payload)` — before tracing, expected `verified == false` for an unsigned/garbage-signed request; after tracing `lib/shipit/github_app.rb:77`, actual `verified == true` unconditionally whenever `webhook_secret` is blank, so the two sides diverge and the downstream `AssignedHandler` write is reachable without any valid credential.
