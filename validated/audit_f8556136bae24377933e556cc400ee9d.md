### Title
Unvalidated `creator` account in `initialize_with_permission` allows the zero address to be stored as `pool_creator`, permanently freezing all future creator fees for the pool — (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts an arbitrary, unchecked `creator` account and stores it verbatim as `pool_state.pool_creator` with no validation that it is non-zero (or otherwise a controllable address). This is the same class of bug as the CvgSDT report: an externally-supplied address is used later as a token-transfer destination/authority without a zero-address check, and if it is `Pubkey::default()`, the funds sent there become unrecoverable.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as a bare `UncheckedAccount` with no `address`, `signer`, or non-default constraint: [1](#0-0) 

The handler passes `ctx.accounts.creator.key()` directly into `pool_state.initialize(...)`, which stores it as `self.pool_creator`: [2](#0-1) [3](#0-2) 

That `pool_creator` value is later relied upon in `collect_creator_fee_permissionless`, where the creator fee recipient ATAs are derived using `pool_creator` as the ATA's `authority`: [4](#0-3) [5](#0-4) 

If `creator` is `Pubkey::default()` (the zero address, which is off the ed25519 curve and has no corresponding keypair), the ATAs created for `creator_token_0`/`creator_token_1` are owned by an authority nobody can ever sign for. Any trade fee routed to the creator (`creator_fees_token_0`/`creator_fees_token_1`, accumulated during every swap via `swap_base_input`/`swap_base_output`) is permanently locked in that ATA once `collect_creator_fee_permissionless` is invoked — no path exists to move it out, since `token_program` transfers require a signature from the account authority.

Unlike `initialize`, where `pool_creator` is bound to a `Signer` (which cannot practically be the zero address because it must produce a valid signature), `initialize_with_permission`'s `creator` has no such protection, matching exactly the CvgSDT pattern of "external report used a zero-address recipient with no `require(recipient != address(0))` check."

### Impact Explanation
This causes permanent freezing of pool funds: every swap accrues `creator_fee_rate`-based fees credited to `pool_state.creator_fees_token_0/1`, and once collected via `collect_creator_fee_permissionless` into an ATA owned by the zero address, those tokens are irrecoverably lost. Because the fee accrual happens continuously on every swap for the life of the pool, the amount at risk is unbounded and grows over time, qualifying as High severity per the same rationale as the CvgSDT report (loss/freezing of user funds due to a missing zero-address check on a stored, later-used recipient/authority).

### Likelihood Explanation
`initialize_with_permission` can be called by any account holding a `Permission` PDA (gating who can call the instruction), but there is no constraint preventing that legitimate caller from supplying `creator = Pubkey::default()` (or any other address they don't control) for the pool being created — either by mistake or intentionally to grief later fee collection. Anyone can subsequently call the permissionless `collect_creator_fee_permissionless` to trigger the freeze, since it requires no special privilege beyond funding ATA creation.

### Recommendation
Add an explicit check in `initialize_with_permission` (and mirror in `initialize` for defense in depth) that the supplied `creator` is not the default/zero pubkey, e.g.:
```rust
require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default(), ErrorCode::InvalidCreator);
```
before calling `pool_state.initialize(...)`.

### Proof of Concept
1. Attacker (or any account holding a valid `Permission` PDA) calls `initialize_with_permission`, passing `creator = Pubkey::default()` as the `creator` account.
2. `pool_state.initialize(...)` stores `pool_creator = 11111111111111111111111111111111` in the new pool's state.
3. Users swap against the pool; `swap_base_input`/`swap_base_output` accrue `creator_fees_token_0`/`creator_fees_token_1`.
4. Anyone calls `collect_creator_fee_permissionless`; `creator_token_0`/`creator_token_1` ATAs are created with `associated_token::authority = creator` (the zero address), and the accrued fees are transferred there via `transfer_from_pool_vault_to_user`.
5. Because no keypair exists for the zero address, the tokens in these ATAs can never be transferred out — they are permanently frozen.
