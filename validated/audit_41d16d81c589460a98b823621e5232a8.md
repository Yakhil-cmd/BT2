### Title
Cross-organization webhook forgery bypasses `Shipit.github_teams` authorization via `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
In multi-organization Shipit deployments, the signature that authenticates a webhook is verified against the GitHub App belonging to one organization, but the resource that gets mutated by the handler (a `Team`, keyed only by attacker-supplied `github_id`) is never checked against that same organization. An administrator of *any* GitHub App configured on the shared Shipit instance can therefore forge a `membership` webhook, add an arbitrary GitHub login to a `Team` that happens to share a `github_id` with one of the site's `Shipit.github_teams`, and grant that user full authenticated access to the Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate the request against using a field taken straight from the untrusted payload: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting several independent GitHub Apps/organizations behind one instance, each with its own `webhook_secret`: [3](#0-2) 

Once the signature is validated, the controller dispatches the *entire raw payload* to the handler with no notion of "which organization authenticated this request": [4](#0-3) 

`Handlers::Handler` and its subclasses never receive or check the authenticating organization; they act purely on attacker-controlled payload fields: [5](#0-4) 

`MembershipHandler` is the clearest instance of the broken binding: it looks up (or creates) a `Team` solely by the attacker-supplied `params.team.id`, with no cross-check that this team's organization matches the organization whose secret validated the signature, and then adds an attacker-chosen `member.login` to that team: [6](#0-5) 

Authorization in Shipit is entirely team-membership based: [7](#0-6) [8](#0-7) 

`User#authorized?` only checks whether the user belongs to *any* `Team` whose `id` is in `Shipit.github_teams` — it never re-verifies which GitHub organization actually owns that team record. Because `Team.github_id` is a plain attacker-controlled integer in the forged payload, an operator of *any* configured GitHub App on the shared instance can target the `github_id` of a `Team` that Shipit already trusted (created earlier via a legitimate `membership` sync from the victim organization) and inject an arbitrary GitHub login as a member.

Binding broken: **the organization that authenticated the webhook (via `webhook_secret`) ≠ the organization/team resource the handler actually writes to.**

Same-class issue also affects `PushHandler`/`CheckSuiteHandler`, which resolve the target `Stack`/`Repository` from `payload.dig('repository','full_name')` — a field independent of the organization used for signature selection — letting an app administrator on one org trigger `stack.sync_github` for stacks belonging to a different org's repository: [9](#0-8) [10](#0-9) 

### Impact Explanation
This directly matches the "High" impact bucket of escalation into `Shipit.github_teams` authorization: an attacker who controls a GitHub App installed on one organization onboarded to the shared Shipit instance (an "unprivileged" party with respect to every *other* org/repo hosted by that instance) can forge a signed `membership` webhook that adds any GitHub login as a member of a `Team` record matching an authorized team's `github_id`. That user then passes `current_user.authorized?` and gains full authenticated access to Shipit — viewing/triggering deploys, rollbacks and tasks on stacks belonging to organizations they have no legitimate relationship with. The cross-organization `push`/`check_suite` forgery further allows forcing arbitrary stacks to sync against attacker-chosen SHAs, which can influence continuous-deployment behavior on victim stacks.

### Likelihood Explanation
Exploitability requires only that the attacker administers (or has compromised) one GitHub App configured under the multi-organization `github:` block documented in `docs/setup.md`, and that the target `Team`/`Stack` already exists in Shipit's database (created via prior legitimate syncs) — both are realistic for any shared, multi-tenant Shipit deployment, which is an explicitly documented and supported configuration.

### Recommendation
Thread the organization that authenticated the webhook (the `repository_owner`/app key resolved in `WebhooksController#verify_signature`) through to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and have every handler validate that the resource being mutated (`Team#organization`, `Repository`/`Stack` owner) belongs to that same authenticated organization before performing any write. Reject events where the authenticated organization does not match the resource's organization.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations, `attacker-org` (admin-controlled by the attacker) and `victim-org` (hosts stacks the attacker has no access to), per `docs/setup.md:181-209`.
2. Note the `github_id` of a `Team` already synced for `victim-org` that is listed in `Shipit.github_teams` (e.g. discoverable via a prior legitimate `membership` event or team enumeration).
3. Using `attacker-org`'s own known `webhook_secret`, craft and sign (`X-Hub-Signature`) a `membership` event where `organization.login = attacker-org` (so `WebhooksController#verify_signature` selects and validates against `attacker-org`'s secret) but `team.id` equals the victim team's `github_id`, and `member.login` is any GitHub account the attacker controls.
4. POST to `/webhooks`; `MembershipHandler#process` (app/models/shipit/webhooks/handlers/membership_handler.rb:22-34) finds the existing victim `Team` by `github_id` and adds the attacker's account as a member.
5. Log in to Shipit as that account; `User#authorized?` (app/models/shipit/user.rb:80-82) now returns true, granting full access to `victim-org`'s stacks.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
