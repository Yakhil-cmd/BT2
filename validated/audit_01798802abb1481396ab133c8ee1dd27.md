### Title
Review-stack pull request labels are merged into deploy command environment without whitelist filtering, enabling arbitrary env-var injection into `PTY.spawn` - (File: app/models/shipit/review_stack.rb)

### Summary
`Shipit::ReviewStack#env` merges every label on the stack's backing pull request directly into the stack environment hash with no whitelist check, and this hash is unconditionally merged by `TaskCommands#env` / `DeployCommands#env` into the environment passed to `Command.new(...)`, which ultimately reaches `PTY.spawn`. Unlike user-submitted deploy env (`deploy_params`, `trigger_task`, `build_deploy`), which is always passed through `EnvironmentVariables#permit` against `deploy_spec.deploy_variables`, label-derived variables never go through that filter.

### Finding Description
The claimed binding — "keys in `Command#unbundled_env` for a `DeployCommands` invocation == keys permitted by `deploy_spec.deploy_variables`/`machine_env`" — is **false** for review stacks.

Trace:
- `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
```
super.merge(pull_request.labels.each_with_object({}) { |l, h| h[l.upcase] = "true" })
```
with **no** call to `EnvironmentVariables#permit` or any whitelist check. [1](#0-0) 
- `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) unconditionally does `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` — `@stack.env` (the label-poisoned hash for a `ReviewStack`) is merged in directly, with `machine_env`/`@task.env` merged *after* it (so labels can even be overridden by `@task.env`, but any label name not present in `@task.env` survives untouched). [2](#0-1) 
- `DeployCommands#env` only adds `SHA`/`REVISION`/`DIFF_LINK` on top of `super` — it does not filter anything. [3](#0-2) 
- `TaskCommands#perform`/`install_dependencies` build `Command.new(command_line, env:, chdir: steps_directory)` from this unfiltered hash for every deploy step. [4](#0-3) 

Compare this to the two paths that DO enforce the whitelist: `Stack#build_deploy`/`trigger_task` call `filter_deploy_envs`/`definition.filter_envs`, which route through `EnvironmentVariables#permit(deploy_variables)` and raise `NotPermitted` for any key not declared in `deploy.variables` in `shipit.yml`. [5](#0-4) [6](#0-5)  The base `Stack#env` (used by non-review stacks) only exposes fixed keys (`ENVIRONMENT`, `BRANCH`, etc.) and contains no user-influenced content. [7](#0-6)  Only `ReviewStack#env` introduces unfiltered, PR-controlled keys, and none of the two whitelist mechanisms above are ever applied to it.

Root cause: `ReviewStack#env` treats PR labels as trusted, pre-vetted configuration data equivalent to `machine.environment` in `shipit.yml`, but labels are freely settable pull-request metadata, not part of the repository's whitelisted `deploy.variables` contract.

One correction to the scoped-impact claim in the prompt: merging the PR does **not** propagate this to a "real" `Stack`'s `trigger_continuous_delivery`, because `Stack#env` (used by ordinary, non-review stacks) does not read `pull_request.labels` at all — that override exists solely on `Shipit::ReviewStack`. [7](#0-6)  The exploitable path is limited to deploys/tasks run **against the `ReviewStack` itself** (manual deploy click or `continuous_deployment: true` on that review environment), not to the base repository's mainline stack after merge.

### Impact Explanation
Any environment variable name can be injected into the process environment of every shell command Shipit runs for that review stack's deploy (`Command#start` → `PTY.spawn`), e.g. `LD_PRELOAD`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, or `PATH`-prefixing variables consumed by the deploy tooling/shell, independent of whatever the repository's `deploy.variables` whitelist declares. This is Command/PTY.spawn-based RCE on the deploy host, scoped to the review stack's environment (and any resources reachable from the machine performing that deploy) — matching the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" category, but only for the labeled review stack, not for arbitrary other stacks/tenants.

### Likelihood Explanation
Preconditions: (1) the target repository has review apps enabled and a `ReviewStack` exists for the attacker's PR (`stack.pull_request.present?`); (2) the attacker can attach a label to that PR; (3) a deploy of that review stack occurs, either by continuous delivery (`continuous_deployment: true` for the review environment) or by a human triggering a deploy of the review stack.

Precondition (2) is the key caveat: on GitHub, adding a label to a pull request normally requires "triage" (or higher) permission on the target repository — an external fork contributor without write access typically cannot label their own PR against someone else's repository. The prompt's threat model explicitly grants "label their own PR" as an available attacker action, but if the attacker only has this ability on repositories they themselves own/administer, they would also already control that repository's `shipit.yml` and could achieve equivalent code execution directly through `deploy.override`/`deploy.pre`/`deploy.post` commands for their own review stack — the label-injection path adds attack surface only when an attacker without write/triage access can still cause a label to be applied (e.g., via automation/bots with lower privilege, or a maintainer unknowingly applying attacker-suggested labels). This meaningfully reduces but does not eliminate real-world likelihood; it should be evaluated against the specific repository's actual label permissions.

### Recommendation
In `Shipit::ReviewStack#env`, do not merge raw label names as environment variable keys. Either drop this feature, or route label-derived variables through `EnvironmentVariables#permit` against an explicit, opt-in whitelist (e.g., a new `review.label_variables` config in `shipit.yml`), and reject/ignore any label whose name is not on that whitelist, consistent with how `deploy.variables` are enforced elsewhere in `Stack#build_deploy`/`TaskDefinition#filter_envs`.

### Proof of Concept
In a new/updated test under `test/models/shipit/review_stack_test.rb` or `test/lib/shipit/deploy_commands_test.rb`:
1. Build a `ReviewStack` fixture with an associated `pull_request` (`shipit_stacks(:review_stack)` per its pull request association).
2. Set `stack.pull_request.labels = ['ld_preload']` (persist/stub as needed).
3. Instantiate `commands = Shipit::DeployCommands.new(deploy)` for a `Deploy` on that stack.
4. Assert `commands.env['LD_PRELOAD'] == 'true'`.
5. Assert this key is **not** present in `stack.cached_deploy_spec.deploy_variables.map(&:name)` (i.e., it was never whitelisted) — demonstrating `EnvironmentVariables#permit` was never invoked for this key.
6. Call `commands.perform` and assert the returned `Command` objects' `.env` hash contains `LD_PRELOAD => 'true'`, showing it reaches the `Command.new(command_line, env:, chdir:)` call that ultimately feeds `PTY.spawn`. [8](#0-7)
