### Title
Webhook signature verified against attacker-controlled `repository.owner.login` while the handler acts on the independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body, rather than deriving it from any GitHub-authenticated context. Every downstream handler, however, decides *which repository/stack to mutate* using a different field of the same untrusted body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`). Nothing ties these two fields together, so the "organization whose secret authenticated the request" and "the repository that gets written to" are never checked for consistency.

### Finding Description
`verify_signature` computes the verifying organization purely from payload content: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This selects the app/secret via `Shipit.github(organization: repository_owner)` (see `lib/shipit.rb`'s `github` method, which maps organization name to a distinct `webhook_secret` in the multi-org configuration documented in `docs/setup.md` "Using Multiple Github Applications"), then HMAC-verifies the raw body against *that* organization's secret.

Once the signature check passes, `WebhooksController#create` dispatches the same raw payload to handlers: [3](#0-2) 

All handlers derive the target `Stack`/`Repository` from a *different* payload field, independent of `repository_owner`: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

In a genuine GitHub webhook, `repository.owner.login` and `repository.full_name` are always consistent (both come from the same GitHub-computed repository object). But because Shipit's engine only cryptographically authenticates the raw bytes of the JSON body — not any binding between these two specific fields — an attacker who legitimately controls one onboarded GitHub organization's `webhook_secret` (in a multi-org Shipit deployment, e.g. `OrgA` from `config/secrets.yml`) can forge a JSON body where:
- `repository.owner.login` (and thus `repository_owner`) = `"OrgA"` — used only for HMAC selection/verification.
- `repository.full_name` = `"OrgB/other-repo"` — used by the handler to pick the actual `Stack`.

Signing this crafted body with `OrgA`'s webhook secret makes `verify_signature` pass (`Shipit.github(organization: "OrgA")` verifies successfully), while the dispatched handler (`PushHandler`, `StatusHandler`, etc.) resolves and mutates a `Stack` belonging to `OrgB`, whose secret the attacker never had.

This is directly analogous to the reported PriceFeed bug class: the system that validates the "authenticated source" (Chainlink price / here, `repository_owner`'s secret) is not the same one relied upon by the state transition that actually takes effect (Case 4 accepting the raw Chainlink price / here, the handler trusting `repository.full_name` to act).

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. Concrete consequences depend on event type but land in the High/Critical bands:
- `push` events cause `GithubSyncJob` to run against `OrgB`'s stack (`app/models/shipit/webhooks/handlers/push_handler.rb`), which can trigger continuous delivery/deploys on a stack the attacker does not own — an unauthorized deploy / cross-organization write into `OrgB`'s stack state.
- `status`/`check_suite` events can inject fabricated CI status/check-run state for arbitrary commits under `OrgB`'s repository, which (combined with `continuous_deployment`) can trigger an unauthorized deploy on `OrgB`'s stack.
- `pull_request`/`membership` handlers likewise resolve repositories/teams from the same untrusted `full_name`/`organization` fields, enabling cross-tenant provisioning/archival actions.

### Likelihood Explanation
Requires the attacker to control (or know) the `webhook_secret` for at least one organization configured in a multi-organization Shipit deployment — realistic for a legitimate but low-trust tenant onboarded alongside other orgs on the same Shipit instance (a documented, supported configuration in `docs/setup.md`). No Shipit session, `ApiClient` token, or GitHub App private key is required; only crafting a raw HTTP POST with a valid HMAC-SHA1 signature computed from a body they control.

### Recommendation
Bind signature verification to the exact repository being acted upon, not to an independently-controlled field. Concretely: after selecting the GitHub App via a trusted identifier for the request, cross-check that `repository.owner.login` in the payload equals the owner encoded in `repository.full_name`, and further verify that the resolved `Repository`/`Stack` actually belongs to the organization whose secret validated the signature (e.g., compare against `Repository#owner` fetched via `Repository.from_github_repo_name`), rejecting the webhook if they diverge.

### Proof of Concept
Not independently executed against a live instance (no filesystem/terminal access in this session); the exploit path below is derived from static analysis of the cited code:
1. Deploy Shipit with the multi-org config shown in `test/dummy/config/secrets_double_github_app.yml` (`OrgOne`, `OrgTwo`, each with distinct `webhook_secret`), with a `Stack`/`Repository` provisioned for `OrgTwo/target-repo`.
2. As an entity that legitimately knows `OrgOne`'s `webhook_secret` (e.g., an org admin for `OrgOne`, a tenant onboarded on the same Shipit instance), craft a `push` (or `status`) webhook JSON body with `repository.owner.login = "OrgOne"` and `repository.full_name = "OrgTwo/target-repo"`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, raw_body)>` and POST to `/github/auth/.../webhooks` (per `config/routes.rb` webhook endpoint) with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully verifies the signature using `OrgOne`'s secret.
5. `WebhooksController#create` dispatches to `PushHandler`, whose `repository_name` resolves to `"OrgTwo/target-repo"`, causing `GithubSyncJob`/subsequent continuous delivery logic to run against `OrgTwo`'s stack — despite the request never being authenticated by `OrgTwo`.
