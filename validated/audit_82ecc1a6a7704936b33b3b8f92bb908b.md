### Title
CCMenu endpoint ignores the stack scope of an `ApiClient` token, allowing a stack-restricted token to read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via `ApiClient#stack_id`, and `Shipit::Api::BaseController#stacks`/`#stack` is supposed to enforce that scope for every request. `Shipit::Api::CCMenuController` overrides `#stack` and resolves the requested stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the scoping check, so a token limited to one stack can be used to fetch CI/deploy status for any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the authorization binding "the stack(s) a token authorises" == "the stack a request touches": [1](#0-0) 

`current_api_client.check_permissions!` only validates that the permission string (e.g. `read:stack`) is present on the token — it has no knowledge of which specific stack is being requested: [2](#0-1) 

The per-stack restriction is therefore only enforced by the `stacks`/`stack` helper in `BaseController`, which every other API controller (`Api::StacksController`, `Api::CommitsController`, `Api::DeploysController`, `Api::HooksController`, `Api::TasksController`) relies on via inheritance.

`CCMenuController`, however, redefines `stack` to resolve directly against the global `Stack` scope, ignoring `current_api_client.stack_id`: [3](#0-2) 

This breaks the equality the engine otherwise maintains everywhere else: `stack ∈ stacks` (i.e., `Stack.where(id: current_api_client.stack_id)` when the token is scoped) becomes `stack ∈ Stack.all` regardless of the token's `stack_id`.

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (the documented least-privilege pattern, as covered by the `here_come_the_walrus` fixture and the "an api client scoped to a stack will only see that one stack" test) can be handed to a lower-trust consumer such as a CI status badge/dashboard. Via `CCMenuController#show`, that same token — despite only holding `read:stack` for its own stack — can be replayed with a different `stack_id` param to read the CI/build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of any other stack managed by the Shipit instance, including stacks the token was never meant to see. This is an unauthorized cross-stack read of stack/deploy state, matching the High-severity class of "unauthenticated/unauthorized read of stack state ... or deploy output" reachable purely by replaying an already-issued, narrowly-scoped credential outside its intended boundary — no webhook secret, GitHub credentials, or session is required, only the restricted token itself. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
Likelihood is moderate to high: `CCMenuController` is specifically designed for token-in-URL usage (`Shipit::CCMenuUrlController#fetch` embeds the token as a query string), making these tokens more exposure-prone (browser history, CI logs, proxies) than Basic-Auth tokens used elsewhere. The bypass requires only changing the `stack_id` route/query parameter — no additional privilege or secret is needed once a stack-scoped token is obtained.

### Recommendation
Make `CCMenuController#stack` go through the same scoped lookup used elsewhere (`stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a token scoped to `current_api_client.stack_id` cannot resolve a different stack.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to `stack_id: A` with `permissions: ['read:stack']` (e.g., via `CCMenuUrlController#fetch` or an admin-issued token), exactly like the `here_come_the_walrus` fixture.
2. Confirm the scoping works elsewhere: `GET /api/stacks` with this token returns only stack `A` (per the existing "an api client scoped to a stack will only see that one stack" behavior).
3. Send `GET /api/:stack_id_B/ccmenu.xml?token=<token>` (or with the token in the `Authorization: Basic` header) where `B != A`.
4. `CCMenuController#authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` succeeds (token has `read:stack`), and `stack` resolves `Stack.from_param!(params[:stack_id])` to stack `B` — the response discloses `lastBuildStatus`, `lastBuildLabel`, `activity`, and lock state for stack `B`, which the token was never authorized to access.
