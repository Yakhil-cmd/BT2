### Title
Webhook signature verification keys on `repository.owner.login`, allowing a webhook signed by one organization's secret to write to another organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to verify a webhook against based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON payload. Once the HMAC check passes, the same request body is dispatched to `Shipit::Webhooks.for_event(event)` handlers, which independently pick the target `Stack`/`Repository` using a **different** field of the same unverified payload: `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment (`config/secrets.yml` with multiple GitHub Apps, one per org), an attacker who legitimately controls one configured organization's webhook secret can craft a payload where `repository.owner.login` names their own org (so the signature check passes with their own secret) while `repository.full_name` names a **different** organization's repository, whose stack then gets processed as if the push/status/check_suite genuinely came from GitHub for that other org.

### Finding Description
`verify_signature` derives the signing organization from the request body itself, before the signature has been validated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per configured organization key, as demonstrated by the multi-org fixture and test: [3](#0-2) [4](#0-3) 

Once `verify_webhook_signature` returns true for that attacker-chosen organization's secret, the raw payload is handed unmodified to the registered handlers: [5](#0-4) 

Handlers resolve the target stack/repository from a **separate** payload field, `repository.full_name`, which is not tied to the field used for signature verification: [6](#0-5) 

For example, `PushHandler` uses this to enqueue a `GithubSyncJob` for whatever stack matches `repository.full_name`: [7](#0-6) 

This breaks the equality the platform is implicitly relying on: `organization whose secret authenticated the request == organization owning the repository being written to`. Because `repository.owner.login` (used for authentication) and `repository.full_name` (used to select what gets written to) are two independent, attacker-controlled fields in the same unauthenticated JSON body, they can be set inconsistently.

### Impact Explanation
An attacker who is a legitimate GitHub organization admin/owner in a multi-tenant Shipit install (i.e., they know or can generate the webhook signature for their own org's GitHub App, e.g. by controlling the webhook delivery configuration for their own org's app) can forge webhook deliveries claiming to originate from a **different** organization's repository. This can trigger `GithubSyncJob` (push), commit status updates (`status`), check-run refreshes (`check_suite`), or team/membership mutations (`membership`) against stacks that belong to victim organizations they have no legitimate access to — i.e., cross-organization writes to Shipit's data model (commits, statuses, check runs, team memberships) for repositories/organizations the attacker does not control. This matches the "cross-repository writes" Critical-impact category, since a signature that authenticates for org A is treated as authorizing state changes for org B's data.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) the Shipit instance to be configured for multiple GitHub organizations (the "Using Multiple Github Applications" setup documented in `docs/setup.md`), and (b) the attacker to control (or compromise) a legitimate webhook secret for at least one of the configured orgs — which is a normal, expected credential for any org admin using this multi-tenant instance, not a privileged Shipit credential. No Shipit session, API token, or GitHub App private key is required.

### Recommendation
Bind the field used to select the verification secret to the same field used to select the target stack/repository. Concretely, `repository_owner` in `WebhooksController` should be derived from (and cross-checked against) `repository.full_name`'s owner segment, and handlers should reject/ignore payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`. Alternatively, verify the signature against every configured organization's secret and only accept the webhook if the organization it verified against matches the organization that owns the targeted repository/stack.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is an org owner of `OrgA` and knows `OrgA`'s `webhook_secret` (a normal credential for anyone administering that org's GitHub App).
3. Attacker crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over this exact JSON body and POSTs it to `/webhooks`.
5. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which succeeds because the attacker signed with `OrgA`'s real secret.
6. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for `OrgB`'s stack with the attacker-chosen `expected_head_sha`, causing Shipit to sync/deploy state for an organization the attacker does not control.

**Note on verification limits:** I was unable to inspect `app/models/shipit/repository.rb` (the `from_github_repo_name` lookup) or confirm whether any additional validation exists there that cross-checks the owner login against the full_name before the stack is matched — the read attempts for that file did not complete before tool access ended. If `Repository.from_github_repo_name` or an associated model performs such a cross-check, it could mitigate this specific PoC; this should be verified in a full Devin session with complete file access.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
