### Title
`InitializeWithPermission` binds `pool_creator` to an attacker-supplied `creator` account with no ownership/authorization check tied to the permission verification — analogous step-up bypass on privileged fee-collection identity - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The Logto CVE's bug class is: a privileged action (MFA management) is gated on a "verification" record that is checked only for `belongs to current user` + `isVerified === true`, but never checked to be *scoped* to the specific action being authorized (binding a passkey vs. proving existing possession). The analogous pattern in this program is an instruction that performs a permission/gate check on one identity (the transaction `payer`, via the `permission` PDA) but then assigns the privileged, fee-collecting role (`pool_creator`) to a *different*, unchecked identity supplied in the same instruction — i.e., the "verification" and the "privileged binding" are decoupled.

### Finding Description
`InitializeWithPermission` requires a `permission` PDA account derived from `PERMISSION_SEED` + `payer.key()`: [1](#0-0) 

This is the only authorization gate in the instruction — it proves the `payer` was allow-listed via `create_permission_pda` by `admin`/`create_permission_pda_owner`: [2](#0-1) 

However, the `creator` field used to populate `PoolState.pool_creator` (the identity entitled to permissionless-routed and self-service creator-fee collection via `collect_creator_fee` / `collect_creator_fee_permissionless`) is declared as a completely unconstrained `UncheckedAccount`: [3](#0-2) 

There is no `address = payer.key()` (or any relation to `permission.authority`) tying `creator` to the party whose permission was actually checked. `PoolState.initialize` stores whatever `creator` pubkey was passed in as `pool_creator` (per the field's role in `states/pool.rs`) and that pool_creator subsequently has exclusive rights to `collect_creator_fee` (`address = pool_state.load()?.pool_creator` constraint) and is the sole recipient of `collect_creator_fee_permissionless`: [4](#0-3) [5](#0-4) 

I was not able to fully verify, within the available index window, the exact call site inside `initialize_with_permission` (or `create_pool` in `initialize.rs`) that passes `ctx.accounts.creator` into `PoolState::initialize`'s `pool_creator` parameter — the section of the file covering that specific call (between the `create_pool(...)` invocation and `pool_state.initialize(...)`) was not returned by my tool calls before the iteration limit was reached. Given the index size limits noted in my instructions, I recommend starting a full Devin session to inspect the complete body of `initialize_with_permission.rs` (particularly the `pool_state.initialize(...)` call and its arguments) and confirm whether `creator` (unchecked) or `payer` (permission-checked) is the actual source of `pool_creator`.

### Impact Explanation
If `pool_creator` is indeed sourced from the unconstrained `creator` account rather than the permission-verified `payer`, this breaks the intended coupling between "who was authorized to create a permissioned pool" and "who receives the ongoing creator-fee revenue and exclusive collection rights" — allowing an attacker whose own key was never allow-listed to still be named `pool_creator` by having an allow-listed party (or themselves as payer with any `creator` sysvar-unchecked pubkey) initialize the pool on their behalf, or conversely allowing a legitimately-checked payer to disclaim/redirect the privileged role to an arbitrary key without further scrutiny. This is a step-up-bypass-style authorization/identity-binding flaw analogous to the Logto CVE (verification proven for one identity/action, privileged effect applied to another).

### Likelihood Explanation
Low-to-Medium confidence without confirming the exact assignment in `initialize_with_permission`'s body — this claim is **conditional** on `creator` (not `payer`) being written into `pool_creator`. If instead the code hard-binds `pool_creator = payer.key()` and only uses `creator` as a display/reference-only field, this is not exploitable.

### Recommendation
- Add a constraint on the `creator` account in `InitializeWithPermission` tying it explicitly to the checked identity, e.g. `#[account(constraint = creator.key() == permission.authority || creator.key() == payer.key())]`, or remove the separate `creator` account and always use the permission-checked `payer` as `pool_creator`.
- Verify (in a full code review) exactly which field feeds `PoolState.pool_creator` in `initialize_with_permission.rs` and align it with the `permission` PDA's verified identity.

### Proof of Concept
Conceptual (pending confirmation of the `pool_creator` assignment source):
1. Attacker (or any user with a valid `permission` PDA as `payer`) calls `initialize_with_permission`, passing an arbitrary pubkey (their own, non-allow-listed identity) as the `creator` account.
2. If `pool_state.initialize(...)` stores this `creator` value as `pool_creator`, the resulting pool grants that arbitrary, permission-unverified identity exclusive rights to call `collect_creator_fee` (`programs/cp-swap/src/instructions/collect_creator_fee.rs`) and guaranteed fee routing via `collect_creator_fee_permissionless` (`programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs`), decoupling the enforced permission check from the privileged role it was meant to gate.
