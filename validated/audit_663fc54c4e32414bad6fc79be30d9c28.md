### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers dispatch writes using the unrelated `repository.full_name` field from the same unverified-binding payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (falling back to `organization.login`) out of the raw JSON body itself. <cite repo="Jaredbentat/shipit-engine--009" path="app/controllers/shipit/webhooks_controller.rb" start="24="49" /> Once the signature check passes for that organization, `WebhooksController#create` hands the *entire* JSON payload to the registered event handlers unchanged. [1](#0-0)  Every handler (`Handler#stacks`/`#repository_name`, `PushHandler`, `PullRequest::OpenedHandler`, `ReopenedHandler`, `LabeledHandler`, `LabelCapturingHandler`, etc.) independently determines *which repository/stack to mutate* using `payload.dig('repository', 'full_name')`, a completely separate field that is never checked against `repository.owner.login`. [2](#0-1) [3](#0-2)  `Repository.from_github_repo_name` simply splits `owner/name` from that field and loads whatever Repository record matches. [4](#0-3) 

### Finding Description
The binding that should hold is: **organization authenticated == repository written**. Instead the code creates two independent trust anchors inside a single unsigned-content JSON body:

- Anchor A (used for authentication): `repository.owner.login` / `organization.login` → selects `Shipit.github(organization: repository_owner)` → selects the `webhook_secret` used to validate `X-Hub-Signature`. [5](#0-4) [6](#0-5) 
- Anchor B (used for the actual mutation): `repository.full_name` → selects the `Repository`/`Stack` records that get commits appended, pull requests provisioned/archived/unarchived, labels captured, or commit statuses created. [7](#0-6) [8](#0-7) 

Because the HMAC signature covers the raw byte string of the whole request body, an attacker who legitimately controls (and knows the `webhook_secret` for) one on-boarded GitHub organization in this multi-tenant Shipit deployment (the codebase explicitly supports several independently-configured orgs, each with its own `webhook_secret`, see `config/secrets.development.shopify.yml`) can compute a *valid* signature over a payload whose `repository.owner.login`/`organization.login` names their own org (so `verify_signature` succeeds), while setting `repository.full_name` to `victim-org/victim-repo` — a completely different, unrelated stack tracked by the same Shipit instance. Nothing re-derives or cross-checks the acting organization against the full_name's owner before the handler runs. `verify_signature` never inspects `repository.full_name` at all, and the handlers never inspect `repository.owner.login`.

This is functionally the same class of bug as the report: a value that is *acted upon* (here, which repository's stack gets its commits synced / PRs provisioned / archived) is never covered by the same binding that was cryptographically verified (here, the organization whose secret validated the signature).

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly listed as Critical impact. Concretely, using their own org's legitimately-known `webhook_secret`, the attacker can:
- Trigger `PushHandler#process` for `victim-org/victim-repo`'s tracked branches, causing `stack.sync_github(expected_head_sha: ...)` and `GithubSyncJob` to run against the victim stack with an attacker-chosen `after` sha, pulling in `Commit` records via the victim stack's own `github_api` (limited, but state-injection/desync of a stack the attacker doesn't own). [9](#0-8) 
- Trigger `PullRequest::OpenedHandler` / `ReopenedHandler` / `LabeledHandler` to provision, archive, or unarchive review stacks belonging to `victim-org/victim-repo`, and forge `sender.login`/label/PR metadata used in those decisions, since none of that data is bound to the org that authenticated. [10](#0-9) 
- Trigger `MembershipHandler` / `StatusHandler` behavior similarly scoped by attacker-controlled payload fields rather than the authenticated org.

This is a genuine unprivileged cross-tenant boundary break specific to this engine's own dispatch code, not dependent on host misconfiguration, TLS interception, or any privileged credential.

### Likelihood Explanation
Requires only that the attacker administers (or has push/webhook access to) any one GitHub organization that is onboarded to the same multi-tenant Shipit instance, and that the target victim repository/stack is also tracked by that instance — a realistic scenario for any shared/SaaS-style Shipit deployment supporting multiple orgs (as the repo's own multi-org secrets template demonstrates). No session, API token, or GitHub App private key is needed; the attacker only needs the `webhook_secret` value for their own org, which they legitimately possess as that org's admin.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, derive the acting-organization binding once and enforce it consistently: after verifying the signature for `repository_owner`, re-validate that every handler's target repository (`repository.full_name`'s owner segment) matches that same `repository_owner`/`organization.login` before dispatching to handlers, rejecting (422) on mismatch. Alternatively, pass the authenticated `repository_owner` into `Handler.call` and have `Handler#repository_name`/`#stacks` refuse to resolve a `Repository` whose `owner` differs from the authenticated organization.

### Proof of Concept
1. Shipit is configured (per `config/secrets.*.yml`) with two orgs: `attacker-org` (secret `S_A`, known to the attacker as its GitHub App owner) and `victim-org` (secret `S_V`, unknown to attacker), each with stacks tracked in the same Shipit instance.
2. Attacker builds a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, raw_body)`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature using `S_A`. [5](#0-4) [6](#0-5) 
5. `create` dispatches the full payload to `PushHandler.call`, whose `Handler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and syncs/branches for that repo's stacks — a repository the attacker's authenticated organization never owned. [2](#0-1) [9](#0-8)
