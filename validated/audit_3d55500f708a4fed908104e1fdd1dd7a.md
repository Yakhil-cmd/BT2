### Title
Cross-organization forged commit status via webhook signature verified against `repository.owner.login` while `StatusHandler` writes globally by SHA - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-GitHub-App Shipit deployment, `WebhooksController#verify_signature` selects which organization's webhook secret to verify the HMAC signature against by reading `repository.owner.login`/`organization.login` directly out of the **unauthenticated** JSON body [1](#0-0) . Once verification succeeds, the raw `params` are dispatched to event handlers, several of which never re-check that the organization implied by the payload's other fields matches the organization whose secret was used to authenticate the request. `Shipit::Webhooks::Handlers::StatusHandler` is the most severe case: it updates commit status by SHA alone, with **no repository/organization scoping whatsoever** [2](#0-1) .

### Finding Description
The equality the deployment trust model is supposed to enforce is:

```
organization whose webhook_secret authenticated the HMAC == organization whose data the handler is permitted to mutate
```

`verify_signature` picks the `GitHubApp` (and therefore the secret used for HMAC verification) using `repository_owner`, which is read straight from the attacker-supplied JSON body before the signature has been checked:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`verify_webhook_signature` then simply HMACs the *entire raw body* against that organization's secret [4](#0-3) . This is cryptographically sound for confirming "this request was signed with OrgA's secret", but it says nothing about the rest of the JSON body's content being trustworthy for any *other* organization — the whole body, including any `sha`, `check_suite`, or nested fields, is fully attacker-controlled as long as they know OrgA's secret (which they legitimately possess if they administer OrgA's installed GitHub App in this shared, multi-tenant Shipit instance, a configuration explicitly documented in `docs/setup.md`'s "Using Multiple Github Applications" section).

Once verification passes, `WebhooksController#create` unconditionally dispatches the same body to handlers:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [5](#0-4) 

Some handlers (`PushHandler`, `CheckSuiteHandler`) at least scope their side effects through `stacks`, which is derived from `payload.dig('repository', 'full_name')` [6](#0-5)  — but that repository name is, again, just another attacker-controlled field of the same body, independent of `repository.owner.login` used for signature selection; nothing forces them to be consistent.

`StatusHandler` is worse: it doesn't even use `repository_name`/`stacks` scoping. It looks up commits **globally by SHA** and writes a status onto them:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha: params.sha)` is not scoped to any repository/stack at all, so a commit SHA colliding with (or deliberately targeting, since git SHAs are public/known from PRs) a commit tracked by a completely different organization's stack will get its status updated.

### Impact Explanation
An attacker who legitimately administers **any one** GitHub organization/App onboarded onto a shared, multi-org Shipit instance (a supported configuration per `docs/setup.md`) knows that organization's own `webhook_secret`. Using that secret, they can craft an arbitrary `status` (or `check_suite`) webhook payload, sign it with their own org's secret (satisfying `verify_signature` because `repository.owner.login` in the payload is set to their own org), and set `sha` to a commit belonging to a **different, unrelated organization's stack** hosted on the same Shipit instance. Because `StatusHandler` performs no per-repository scoping, this forged "success"/"failure" status is written onto that foreign commit.

If that victim stack's deploy gating, CI checks, `continuous_deployment`, or `merge_queue_enabled` behavior depends on commit statuses to decide whether a commit is deployable/mergeable, the attacker can fabricate a passing CI status for a commit they neither authored nor control, potentially causing an **unauthorized deploy** of that commit — a cross-organization write that crosses a repository/organization trust boundary the attacker was never granted, matching the "cross-repository writes" / "unauthorized deploy" impact category.

### Likelihood Explanation
Likelihood is highest in the documented multi-organization Shipit deployment mode, where distinct customers/teams each have their own GitHub App and webhook secret feeding into one shared Shipit instance and its single `/webhooks` endpoint. Any one of those legitimately onboarded, low-privilege organizations can mount this attack against any other org's stacks on the same instance without needing that other org's secret, an `ApiClient` token, or a Shipit user session — only knowledge of their own org's webhook secret, which they are entitled to have.

### Recommendation
- After signature verification, re-derive and enforce that all identifying fields used by handlers (`repository.full_name`, `sha`'s owning stack, etc.) belong to the same organization whose secret authenticated the request; reject payloads where they diverge.
- Fix `StatusHandler` to scope `Commit` lookups through the same repository-scoping mechanism (`stacks`) used by other handlers, rather than a global, org-agnostic `Commit.where(sha: ...)`.
- Consider binding the webhook_secret selection to a value that is itself verified (e.g., a per-installation secret keyed by a value from the HTTP path/route rather than embedded, attacker-controlled body fields), rather than trusting `repository.owner.login` from the unauthenticated JSON prior to verification.

### Proof of Concept
1. Deploy Shipit in multi-org mode with `OrgA` and `OrgB` both onboarded, each with distinct `webhook_secret`s (per `docs/setup.md`).
2. As an administrator of `OrgA` (attacker-controlled, low privilege relative to `OrgB`), obtain `OrgA`'s `webhook_secret` (already known, since the attacker configured/owns the GitHub App for `OrgA`).
3. Craft a JSON body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" },
  "sha": "<sha of a commit belonging to a stack under OrgB>",
  "state": "success",
  "context": "ci/passed",
  "branches": [{ "name": "main" }]
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
5. POST to `/github_authentication/../webhooks` (the mounted webhooks endpoint) with header `X-Github-Event: status`.
6. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes (attacker knows this secret).
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the `OrgB` commit regardless of the `OrgA` owner used for auth — and writes the forged `"success"` status onto it via `create_status_from_github!`, even though the request was never sent nor authorized by `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
