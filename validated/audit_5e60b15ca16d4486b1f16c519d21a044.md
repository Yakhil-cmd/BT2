### Title
`dataFeedExists()` fast path for AA `in_data_feed` skips the `sequence='good'` filter that the sibling `readDataFeedValue()` enforces - (File: data_feeds.js)

### Summary
The Rolla report describes a state check (`isOracleActive`) that is enforced on one code path (vanilla option minting) but omitted on an economically-equivalent sibling path (spread minting), letting users bypass the intended restriction. The same *"check present on one path, missing on the analogous sibling path"* pattern exists in `data_feeds.js`, where the in-memory fast path used to evaluate the `in_data_feed` oscript operator for Autonomous Agents does not filter out units whose `sequence` is not `'good'`, while the sibling function that reads the actual feed *value* for the same `bAA` case does perform that filter.

### Finding Description
`dataFeedExists()` is the function backing the `in_data_feed` operator, which AAs use to check whether some oracle-posted (or, in AA-to-AA usage, unstable-unit-posted) data feed value satisfies a condition: [1](#0-0) 

When called with `bAA=true` (from AA formula evaluation), it takes a fast, in-memory path over `storage.assocUnstableMessages`, filtering candidate units only by AA-authorship, `latest_included_mc_index` range, and author-address match — it never checks the candidate unit's validity/sequence status: [2](#0-1) 

Compare this with the sibling function `readDataFeedValue()`, which performs the exact same kind of in-memory scan (also gated by `bIncludeUnstableAAs`/`unstable_opts`, used by the `data_feed` operator to read the actual value) but explicitly excludes non-good units: [3](#0-2) 

The line `if (objUnit.sequence !== 'good') continue;` in `readDataFeedValue()` has no counterpart in `dataFeedExists()`. Both functions are invoked from the same call sites in the oscript formula evaluator — `data_feed` and `in_data_feed` are evaluated side by side and are documented/expected to behave consistently: [4](#0-3) [5](#0-4) 

`in_data_feed` is also usable inside address/asset definitions (authentifier evaluation), where a non-AA path is used instead (`bAA=false`), routing to the disk-backed `dataFeedByAddressExists`, which only indexes finalized/committed data (a different, DB-backed code path not affected by this in-memory gap): [6](#0-5) 

The vulnerable path is reachable specifically when an AA evaluates `in_data_feed[[...]]` while looking at *unstable* messages (the very purpose of the `bAA` fast path — to see feeds posted by units not yet on the stable DAG). In that scenario, a unit posting a `data_feed` message that will *eventually be marked non-serial/`final-bad`* (e.g., because it turns out to be on the losing side of a conflict/doublespend, or otherwise loses sequence status before stabilizing) is still counted as a valid data feed source for the boolean existence check, whereas the same unit would correctly be excluded when the AA instead reads the concrete *value* via `data_feed[[...]]`.

### Impact Explanation
An AA whose trigger-response logic uses `in_data_feed[[oracles=..., feed_name=..., feed_value ...]]` to gate a boolean decision (e.g., "has price X been posted by oracle Y — release funds / execute a branch") can be made to take the branch based on a data-feed-bearing unit that is not actually valid (`sequence != 'good'`) and will be excluded once finality is reached. Since AA execution results become part of the DAG once the trigger unit stabilizes, this can cause the AA to commit to a fund-releasing or state-changing branch based on data that should not have counted, causing AA fund loss or incorrect state transitions, and can create disagreement between nodes about the "same" oracle/data-feed logic depending on when/whether they've observed sequence changes for the candidate unit before evaluating the trigger.

### Likelihood Explanation
This requires an AA author to use `in_data_feed` (rather than `data_feed`) against unstable AA-posted data feeds, and requires a candidate data-feed-posting unit to be in a not-yet-`good`/soon-to-be-`final-bad` sequence state at evaluation time — a state that can arise naturally from conflicting/doublespending units in the DAG, not requiring any special privilege from the attacker beyond normal unit posting. It is a logic/consistency gap rather than a trivially-triggerable exploit, but it is reachable by any unprivileged AA trigger sender or unit poster who can influence which units are unstable/conflicting when an AA runs `in_data_feed`.

### Recommendation
Add the same `sequence`-validity filter used in `readDataFeedValue()` to the `bAA` fast path of `dataFeedExists()`, e.g.:
```js
for (var unit in storage.assocUnstableMessages) {
    var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
    if (!objUnit) throw Error("unstable unit " + unit + " not in assoc");
    if (!objUnit.bAA) continue;
    if (objUnit.sequence !== 'good') continue;   // <-- add this, mirroring readDataFeedValue()
    if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci) continue;
    ...
```
This makes `in_data_feed` consistent with `data_feed` for the AA fast path, ensuring both operators agree on which unstable units are eligible sources of feed data.

### Proof of Concept
1. An AA `X` posts (or triggers a message that results in) a `data_feed` message `M` for feed `F=V` in unit `U`, while `U` is still unstable.
2. Another unit conflicting with `U` (double-spending the same author's inputs) is also broadcast, such that `U` will eventually be marked `sequence != 'good'` (non-serial or `final-bad`) once the conflict resolves — but this has not happened yet at the moment AA `Y` is triggered.
3. AA `Y`'s bytecode evaluates `in_data_feed[[oracles=X's address, feed_name='F', feed_value=V, min_mci=...]]` while `U` is still unstable: `dataFeedExists()` is invoked with `bAA=true` per `formula/evaluation.js` lines 701-748, taking the fast path at `data_feeds.js` lines 34-44, which does not check `objUnit.sequence`, so it returns `true` for `U`'s posted feed even though `U` will later be excluded from validity.
4. AA `Y` executes its true-branch logic (e.g., releasing funds) based on this feed existence check.
5. If instead `Y` had used `data_feed[[...]]` to fetch the value, `readDataFeedValue()`'s `objUnit.sequence !== 'good'` check (`data_feeds.js` line 219) would have excluded `U` once its sequence became known as bad — demonstrating the inconsistency between the two sibling operators for the exact same unstable-unit scenario.
