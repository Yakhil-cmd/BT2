Confirmed: `check_permissions!` (app/models/shipit/api_client.rb:38-45) only checks the operation:scope string like `read:stack`; it never checks `stack_id`. The only place stack scoping happens is `Api::BaseController#stacks`/`#stack` (app/controllers/shipit/api/base_controller.rb:74-80), which `Api::CCMenuController` overrides and bypasses.

### Title
Api::CCMenuController#stack bypasses stack_id scoping, allowing cross-stack token replay - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints a `read:stack`-only `ApiClient` bound to a specific `stack_id` and embeds its `authentication_token` in a CCMenu URL for that stack. `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly instead of using the base controller's `stacks`/`#stack` methods that intersect with `current_api_client.stack_id`, so the same token authenticates against any stack simply by changing the `stack_id` path segment.

### Finding Description
The intended binding is: for any request authenticated with an `ApiClient` that has `stack_id` set, `stack.id` resolved by the controller must equal `current_api_client.stack_id`. `Api::BaseController` implements this correctly: [1](#0-0) 

But `Api::CCMenuController` defines its own `#stack` that ignores `current_api_client.stack_id` entirely: [2](#0-1) 

`ApiClient#check_permissions!` only validates the `operation:scope` string (e.g. `read:stack`), never the bound `stack_id`: [3](#0-2) 

`CCMenuUrlController#fetch` creates the token scoped to a stack and embeds it in a URL meant for that stack only: [4](#0-3) 

Exploit flow: an operator generates a CCMenu URL for stack A (e.g. `/api/stacks/owner/repoA/staging/ccmenu.xml?token=T`). An attacker who obtains that URL (browser history, CI badge config, leaked link, shared dashboard) requests `GET /api/stacks/owner/repoB/production/ccmenu.xml?token=T`. `authenticate_api_client` in the controller verifies `T` successfully (token signature is valid, unrelated to path), `require_permission :read, :stack` passes because the client has `read:stack` permission, and `#stack` resolves stack B via `Stack.from_param!` without ever checking that `T`'s `stack_id` matches B. The response renders stack B's latest deploy/rollback state.

### Impact Explanation
An attacker gains unauthenticated (from their perspective) read access to another repository's deploy/task status (latest deploy id, end time, running state) by reusing a token leaked for a different, unrelated stack. This is repeatable against arbitrary stacks since the token check never binds to the requested stack. This matches "High - unauthenticated read of stack state" since the attacker only needs a leaked read-only CCMenu token (not a privileged session or the stack's own token) to read cross-tenant state.

### Likelihood Explanation
Precondition: attacker must obtain a valid CCMenu token minted for any stack (these tokens are long-lived, embedded in plaintext URLs designed for polling by CI status tools, and commonly pasted into CI badges, chat, wikis, or browser history — a realistic and low-cost leak vector). No GitHub secrets, session, or privileged role is required once a token is obtained. Because tokens carry no path/stack restriction check server-side, exploitation is a single HTTP request per target stack.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the base controller's scoped resolution (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the binding `stack.id ∈ {current_api_client.stack_id}` (when the client has a bound `stack_id`) is enforced identically to every other API controller.

### Proof of Concept
Minitest controller test plan (under `test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b` (two distinct `Shipit::Stack` records).
2. Create `client = Shipit::ApiClient.create!(creator: user, name: 'CCMenu Client', stack_id: stack_a.id, permissions: %w[read:stack])`.
3. `token = client.authentication_token`.
4. `get api_stack_ccmenu_url(stack_id: stack_b.to_param), params: { token: token }` (with `stack_b.to_param` composed of `stack_b.repository.owner/name/environment`).
5. Assert binding before fix: `stack_b.id` is NOT in `Stack.where(id: client.stack_id)` (i.e. `client.stack_id == stack_a.id != stack_b.id`), so response should be `403`/`404`.
6. Assert actual (vulnerable) behavior: `response.status == 200` and body contains stack B's deploy data — proving the divergence.
