### Title
Webhook signature is verified against `repository.owner.login`, but every handler acts on the independently-attacker-controlled `repository.full_name` - allows cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In a multi-organization Shipit deployment (`config/secrets.yml` with per-organization `github:` sections, as documented in `docs/setup.md`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to HMAC-verify the raw payload against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Every event handler, however, resolves the target `Repository`/`Stack` from a *different* JSON field in the same payload: `repository.full_name`, via `Handler#repository_name` and `Handler#stacks` [3](#0-2) , or directly via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` in handlers like `PullRequest::LabeledHandler#repository` and `PullRequest::LabelCapturingHandler#repository` [4](#0-3) [5](#0-4) .

Because the HMAC signature covers the entire raw JSON body but the field used to *pick the verification key* (`repository.owner.login`) is not cryptographically tied to the field used to *pick the acted-upon repository* (`repository.full_name`), an attacker who legitimately controls (and thus knows the `webhook_secret` of) one configured organization can forge a payload whose `repository.owner.login` matches their own org (so their known secret verifies) while `repository.full_name` names a Stack belonging to an entirely different organization configured on the same shared Shipit instance.

### Finding Description
This is a direct analog of the audit report's root cause: a value used to establish trust (the honest level-zero edge snapshot / here, the authenticating organization) is not kept consistent with the value later used to make a security-relevant decision (the edge's children / here, the repository actually written to). The binding that should hold as an equality is:

`organization whose webhook_secret authenticated the request == organization that owns the repository/stack acted upon`

Before the attacker's request: for a legitimate GitHub webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always identical, because GitHub itself populates both from the same underlying repository object.

After the attacker's crafted request: `repository.owner.login` = `"OrgB"` (attacker's own onboarded org, whose `webhook_secret` they know from configuring it in `config/secrets.yml`/GitHub App settings), while `repository.full_name` = `"OrgA/some-stack-repo"` (a victim organization hosted on the same Shipit instance). `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` → resolves `OrgB`'s `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker computed the HMAC themselves with the secret they legitimately possess for OrgB [6](#0-5) . The request is accepted, and `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6)  dispatches to handlers that resolve the target `Repository` purely from `repository.full_name` — i.e., `OrgA`'s stack — with no cross-check that it matches the authenticating org.

### Impact Explanation
This lets an attacker who administers only one org onboarded to a shared, multi-tenant Shipit instance forge webhook events against any other org's stacks configured on the same instance:
- `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for a foreign stack [8](#0-7) , forcing unwanted GitHub sync/state changes on a victim's stack.
- `PullRequest::LabeledHandler` can archive/unarchive a victim's review stacks based on forged label events [9](#0-8) .
- `MembershipHandler`/other handlers similarly act on data keyed by the untrusted `full_name`/`organization.login` fields independent of the field used for signature routing.

This crosses an organizational trust boundary without any credential belonging to the victim organization, satisfying the "cross-repository writes" / "unauthorized deploy" criteria for Critical/High impact in scope, since actions land on repositories/stacks the attacker has no legitimate GitHub write access to.

### Likelihood Explanation
This requires the deployment to use the documented multi-organization configuration (`docs/setup.md`, "Using Multiple Github Applications") with more than one org sharing a single Shipit instance, and the attacker to control at least one of those onboarded orgs (a very low bar — they just need to be able to configure their own org's GitHub App/webhook secret, which they inherently possess in a self-service SaaS-like setup). No privileged Shipit account, `ApiClient` token, or victim credentials are required — only knowledge of one's own org's `webhook_secret`, which the attacker sets themselves.

### Recommendation
- **Short term:** In `Handler#stacks`/`Handler#repository_name` (and every handler that independently re-derives `repository` from `params.repository.full_name`), verify that the resolved `Repository#owner` equals the `repository_owner`/organization that was used to authenticate the webhook signature (pass the authenticated organization through from `WebhooksController` into the handler dispatch and assert equality before acting). Reject the event otherwise.
- **Long term:** Bind webhook authentication to a single canonical repository identifier (e.g., always derive both the verification key and the acted-upon repository from `repository.full_name`, or vice versa) so there is only one attacker-influenced field in the trust decision, and add multi-org integration tests that assert cross-organization payloads are rejected.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`, `OrgA` (victim, has a Stack for `OrgA/app`) and `OrgB` (attacker-controlled, webhook secret `S_B` known to attacker), per `docs/setup.md` multi-org instructions.
2. Attacker crafts a raw JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim-relevant-sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/app"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_B, raw_body)>` using their own known `OrgB` secret.
4. POST to `/github/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgB"`, fetches `Shipit.github(organization: "OrgB")`, and verifies successfully with `S_B` [1](#0-0) .
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgA/app")` [3](#0-2)  and calls `stack.sync_github` on `OrgA`'s stack — an action triggered by an attacker with no relationship to `OrgA` at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
