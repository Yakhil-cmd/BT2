### Title
Webhook signature verified against `repository.owner.login` while handlers act on unrelated `repository.full_name`, enabling cross-tenant commit mutation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used for HMAC verification using `params.dig('repository','owner','login')`, but `Handler#repository_name` (used by `CheckSuiteHandler#process`) resolves the target `Repository`/`Stack`/`Commit` using the independently-controlled `payload.dig('repository','full_name')`. Because both fields are attacker-supplied JSON, an attacker who owns `attacker-org` and its own valid `webhook_secret` can sign a payload whose `repository.owner.login` is `attacker-org` (so the signature check passes) but whose `repository.full_name` is `victim-org/victim-repo`, causing the handler to mutate victim-org's commit.

### Finding Description
The broken binding: **organization whose `webhook_secret` verified the request bytes (`repository.owner.login` = `attacker-org`) == organization owning the repository/stack/commit the handler mutates (derived from `repository.full_name` = `victim-org/victim-repo`)**. This equality is false and nothing in the code enforces it.

Code path:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(signature, request.raw_post)`. [1](#0-0) [2](#0-1) 
- `verify_webhook_signature` only checks the HMAC-SHA1 of the raw bytes against that organization's own `webhook_secret` — it has no knowledge of, or binding to, `repository.full_name` inside the payload. [3](#0-2) 
- Once verified, `WebhooksController#create` re-parses the same raw body and dispatches to `CheckSuiteHandler.call(params)`. [4](#0-3) 
- `Handler#repository_name` reads a *different* field, `payload.dig('repository', 'full_name')`, to resolve `stacks` via `Repository.from_github_repo_name`. [5](#0-4) 
- `Repository.from_github_repo_name` does a plain `find_by(owner:, name:)` lookup with no ownership/authorization check tying it back to the org that produced a valid signature. [6](#0-5) 
- `CheckSuiteHandler#process` iterates `stacks.where(branch: ...)` and `stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!)`, all keyed off victim-org's resolved `Repository`, not the org used for signature verification. [7](#0-6) 

Because the attacker controls the entire raw JSON body (they compute the HMAC themselves with their own legitimate `webhook_secret`), they can freely set `repository.owner.login` to their own org (to pick their own secret for signing) while setting `repository.full_name` to any arbitrary `owner/repo` string, including `victim-org/victim-repo`. No existing guard (`drop_unhandled_event`, `ExplicitParameters` schema on `CheckSuiteHandler`, `Repository` validations) checks consistency between these two fields — the `ExplicitParameters` schema only requires `check_suite.head_sha`/`head_branch` are present strings, and `Repository` field validations only constrain characters in `owner`/`name`, not that they match the signing organization.

### Impact Explanation
This lets an attacker who owns any registered GitHub App/org in Shipit forge a `check_suite` webhook that causes Shipit to enqueue `schedule_refresh_check_runs!` against an arbitrary victim organization's commit/stack, entirely bypassing the intended per-organization webhook authentication boundary. This matches the specified Critical category: "a payload for one repository mutating another's stack, commit, task or team." The blast radius spans all repositories/stacks hosted by the Shipit instance, not just the attacker's own — any org with a registered app can target any other org's commits reachable by full_name/branch/sha guesses (branch names and commit SHAs on public GitHub repos are typically discoverable).

### Likelihood Explanation
Preconditions: attacker must run/register their own GitHub App with Shipit for `attacker-org` (this is explicitly stated as available to the attacker in the prompt) and know the victim's `full_name`, `head_branch`, and `head_sha` — all of which are public/discoverable on GitHub for any repo with a public commit history or observable via the victim's own webhook traffic patterns. The attack requires only a single crafted HTTP POST to `/webhooks` with a valid signature computed using the attacker's own secret; it is fully repeatable and scriptable.

### Recommendation
Bind the value used to select the verifying `webhook_secret` to the same value used by handlers to resolve the target repository/stack. Concretely, `WebhooksController#verify_signature` should use `repository.full_name` (or, better, resolve the `Repository`/`Stack` first from `full_name`, then verify against the `webhook_secret` configured for that specific repository/owner), and reject the request if the derived owner from `full_name` does not match `repository.owner.login`/`organization.login`. Alternatively, have `Handler#repository_name` re-derive the repository strictly from the same `repository.owner.login` field used during signature verification instead of trusting `repository.full_name` independently.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub calls — using the existing `Shipit.github` test stub configuration for two orgs, `attacker-org` and `victim-org`, each with their own `webhook_secret`):
1. Seed a `victim-org/victim-repo` `Repository` with a `Stack` on branch `main` and a `Commit` with `sha: 'deadbeef...'`.
2. Build a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "check_suite": {"head_branch": "main", "head_sha": "deadbeef..."}}`.
3. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', attacker_org_webhook_secret, body)`.
4. POST to `/webhooks` with header `X-Github-Event: check_suite` and the above signature/body.
5. Assert response is `200 OK` (signature verified using attacker-org's secret).
6. Assert (via mocking or checking enqueued jobs) that `Commit#schedule_refresh_check_runs!` was called on victim-org's commit — proving `repository.owner.login` (`attacker-org`, the authenticating identity) diverged from the repository actually mutated (`victim-org/victim-repo`).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
