### Title
CCMenu endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` correctly scopes stack lookups to `current_api_client.stack_id` via the `stacks`/`stack` helper methods, but `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely bypassing that scoping. Any token with `read:stack` permission — even one created with a specific `stack_id` — can therefore read deploy status for any stack by changing the URL's `stack_id`.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == params[:stack_id]` (or `current_api_client.stack_id` is nil, i.e. unlimited) whenever a scoped `ApiClient` resolves a stack from a request parameter.

In `Api::BaseController`, this binding is enforced by: [1](#0-0) 
`stacks` restricts the relation to `Stack.where(id: current_api_client.stack_id)` when the client has a scoped `stack_id`, and `stack` resolves `params[:stack_id]` against that restricted relation, so a token scoped to stack A raises `ActiveRecord::RecordNotFound` when `params[:stack_id]` names stack B.

`Api::CCMenuController`, however, defines its own `#stack` that ignores this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model instead of the inherited `stacks.from_param!`, so `current_api_client.stack_id` is never consulted.

`ApiClient.authenticate` and `ApiClient#check_permissions!` only validate the token's signature and the `read:stack` permission string; neither method (nor `require_permission :read, :stack`, applied at [3](#0-2) 
) ever compares `current_api_client.stack_id` to the `stack_id` in the request: [4](#0-3) 

Exploit flow: an attacker who has obtained any leaked but valid CCMenu token for stack A (these tokens are commonly embedded in public CCMenu/CI-badge URLs and Referer headers) sends `GET /api/stacks/<stack-B-id-or-slug>/ccmenu?token=<leaked-token>`. `authenticate_api_client` resolves a real `ApiClient` scoped to stack A: [5](#0-4) 
`require_permission :read, :stack` passes because the client has `read:stack` in its permissions array, regardless of which stack is targeted. `#show` then calls `stack.deploys_and_rollbacks.last`, where `stack` resolves to stack B via the unscoped lookup: [6](#0-5) 
This leaks stack B's latest deploy/rollback state (status, revision) to a party never authorized for stack B.

### Impact Explanation
The attacker obtains unauthenticated (relative to stack B) read access to another stack's deploy/rollback state, including latest deploy id, status, and completion time, by reusing a token that the operator scoped to a different, unrelated stack. This works for any stack in the installation and is repeatable per request with no rate limiting concern relevant here — every request with the leaked token and an arbitrary `stack_id` path succeeds. This matches "unauthorized read of stack state" (High) rather than a full authentication bypass, since the attacker still needs a valid, if narrowly scoped, token; but it breaks the intended stack-scoping guarantee that is otherwise enforced everywhere else in the API.

### Likelihood Explanation
Precondition: the attacker must possess any single valid `read:stack`-permissioned CCMenu token issued for some stack — a low bar, since CCMenu URLs (used for CI status badges/build monitors) are designed to be embedded in third-party tools and are frequently exposed in public dashboards, Referer headers, or public repos/wikis. No GitHub secrets, sessions, or Shipit operator access are required. Once obtained, exploitation is a single unauthenticated GET request with an arbitrary `stack_id`, trivially repeatable against every stack in the instance.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped lookup instead of querying `Stack` directly, e.g. replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])` (removing the local override entirely so it falls back to `Api::BaseController#stack`), ensuring `current_api_client.stack_id` is enforced consistently with all other API endpoints.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B's ccmenu status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse)

  client_a = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-a',
    stack: stack_a,
    permissions: %w[read:stack]
  )

  # binding under test: client_a.stack_id (== stack_a.id) must equal params[:stack_id] (stack_b.id) for access to be granted
  assert_not_equal client_a.stack_id, stack_b.id

  get "/api/stacks/#{stack_b.to_param}/ccmenu", params: { token: client_a.authentication_token }

  # Expected (secure) behavior: request is rejected (404/403) because client_a is not scoped to stack_b
  assert_response :not_found
  # Currently (vulnerable) behavior observed: request succeeds and returns stack_b's deploy data
end
```
