This confirms the vulnerability: `Shipit.github(organization: repository_owner)` in `Shipit::WebhooksController#verify_signature` looks up the app config (and thus the `webhook_secret` used for HMAC verification) keyed strictly by `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`.### Title
Webhook signature verification org and repository resolution org diverge, allowing cross-tenant ReviewStack creation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret using `repository_owner`, which is parsed from `params.dig('repository', 'owner', 'login')` [1](#0-0) , then looks up `Shipit.github(organization: repository_owner)` [2](#0-1) . Downstream, `OpenedHandler#repository` and `ReviewStackAdapter#create!` resolve and mutate a `Repository`/`ReviewStack` using `params.repository.full_name` [3](#0-2) [4](#0-3) . Nothing enforces that `repository.owner.login` (the field used to pick the verifying secret) matches the owner segment embedded in `repository.full_name` (the field used to select which tenant's data is mutated).

### Finding Description
The intended binding is: **`repository_owner` (used to select `webhook_secret`) == owner segment of `repository.full_name` (used to select the `Repository`/`Stack` mutated)**.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and fetches `github_app = Shipit.github(organization: repository_owner)`, verifying `X-Hub-Signature` against that org's `webhook_secret` [2](#0-1) .
2. `Shipit.github(organization:)` looks up per-organization config via `github_app_config(organization)` when multi-org config is used [5](#0-4) , meaning each org (e.g., `attacker-org`) can have its own distinct, attacker-known `webhook_secret`.
3. `OpenedHandler` requires only `repository.full_name` in its schema (not `repository.owner.login`) [6](#0-5) , and resolves the target `Repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , which splits on `/` and does a plain `find_by(owner:, name:)` [7](#0-6) .
4. `ReviewStackAdapter#create!` then creates a `ReviewStack` scoped to that resolved repository and builds a `PullRequest` from attacker-controlled `pull_request` data [4](#0-3) .

Exploit: an attacker who legitimately owns `attacker-org` (configured in Shipit's multi-org `github:` secrets with its own real `webhook_secret`) crafts an arbitrary JSON body — not a real GitHub-delivered webhook — with `repository.owner.login = "attacker-org"` and `repository.full_name = "victim-org/victim-repo"`, and `action = "opened"`. Since HMAC-SHA1 verification (`GitHubApp#verify_webhook_signature`) is computed purely over the raw request body with the shared secret [8](#0-7) , the attacker — who knows `attacker-org`'s own `webhook_secret` — can self-sign this crafted body directly against `POST /webhooks`, with no real GitHub involvement. `verify_signature` picks `attacker-org`'s config (matching `repository.owner.login`) and successfully verifies. Then `OpenedHandler` uses `full_name` to resolve and mutate `victim-org/victim-repo`'s `Repository`, creating a `ReviewStack`, a `PullRequest` record, and enqueuing a provisioning job under that victim repository — entirely cross-tenant.

None of the existing guards catch this: `verify_signature` only checks the signature against the org derived from `owner.login`, never cross-checking it against `full_name`; the `ExplicitParameters` schema in `OpenedHandler` validates only presence/type of `full_name`, not its owner segment against `repository_owner` [6](#0-5) ; `Repository.from_github_repo_name` performs no ownership cross-check [7](#0-6) ; `drop_unhandled_event` and `check_if_ping` are unrelated to this check.

### Impact Explanation
A payload signed with `attacker-org`'s legitimately-possessed `webhook_secret` can create/mutate a `ReviewStack`, `PullRequest`, and trigger `ReviewStackProvisioningQueue`/`GithubSyncJob` enqueuing for a completely unrelated `victim-org/victim-repo`. This is a cross-tenant write triggered by a payload that authenticated as a different organization, matching the Critical category ("a payload for one repository mutating another's stack"). The attack is repeatable against any repository with `review_stacks_enabled` and any `provisioning_behavior` (labels are attacker-supplied fields in the same forged payload, so `allow_with_label`/`prevent_with_label` gates are trivially satisfiable). Blast radius spans every tenant configured on the same Shipit instance under the multi-org `github:` secrets schema.

### Likelihood Explanation
Requires: (1) Shipit configured with the multi-organization `github:` secrets schema (each org with its own GitHub App/`webhook_secret`), and (2) attacker legitimately controls at least one configured organization (`attacker-org`) with a real webhook secret, and (3) the victim repository has `review_stacks_enabled` (a repository-level setting the victim controls independently of the attacker). Given these, the attacker's cost is a single crafted HTTP POST with a computable HMAC signature — no GitHub interaction, no privileged Shipit credentials, fully repeatable and scriptable against any victim repository/PR number.

### Recommendation
In `WebhooksController` or in `Shipit::Webhooks::Handlers::Handler`, derive and enforce that the owner segment of `repository.full_name` matches `repository_owner` (the value used to select the verifying `webhook_secret`) before dispatching to handlers — reject the request (e.g. `head(422)`) on mismatch. Alternatively, resolve `Repository` in handlers using both `owner` and `name` independently validated against the org that authenticated the request, rather than trusting the combined `full_name` string.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "cross-tenant repository confusion in pull_request webhook" do
  victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")

  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", { webhook_secret: "attacker-secret" })
  )

  payload = {
    action: "opened",
    number: 99,
    pull_request: {
      id: 1, number: 99, url: "https://x", title: "x", state: "open",
      additions: 1, deletions: 1,
      head: { sha: "abc123", ref: "feature" },
      user: { login: "attacker" },
      assignees: [], labels: []
    },
    repository: { full_name: "victim-org/victim-repo", owner: { login: "attacker-org" } },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", payload)

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { victim_repo.review_stacks.count }, 1 do
    post :create, body: payload, as: :json
  end
  # Equality broken: repository_owner ("attacker-org") != full_name owner segment ("victim-org"),
  # yet a ReviewStack was created under victim_repo.
end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
