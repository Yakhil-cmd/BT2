### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while state-mutating handlers act on the independently attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App/organization (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` or, as a fallback, `params.dig('organization', 'login')` [4](#0-3) . Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire raw JSON payload to the handlers [5](#0-4) . Every handler resolves the `Repository`/`Stack` to act on from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks` [2](#0-1) . Nothing ties `repository.full_name` to the `repository.owner.login`/`organization.login` used to select the signing secret — they are two independently attacker-supplied JSON fields in the same unsigned-until-verified body.

### Finding Description
This is a direct analog of the RocketRewardPool class of bug: a decision (which value is "trusted") is made based on one piece of state (`RPL` staked "just before" `claim()`), while the actual payout is computed over a different scope (the aggregate reward pool/shares) that the attacker can skew independently. Here, the binding that should hold is:

```
organization/app whose webhook_secret authenticated the request == organization/repository that Shipit actually writes to
```

but the code implements two independent lookups:
- Signing/verification key selection: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [6](#0-5) .
- Actual mutation target: `Repository.from_github_repo_name(payload.dig('repository','full_name'))` inside every handler [2](#0-1) .

In a single-organization deployment this is not exploitable because there is only one webhook secret. However, Shipit explicitly supports multi-organization configuration where each org has its own `app_id`/`webhook_secret` (documented and exercised in `test/dummy/config/secrets_double_github_app.yml`) [7](#0-6) , and `Shipit.github_organizations`/`Shipit.github_app_config` look up the correct app purely by the organization key present in the payload [8](#0-7) . In that configuration, an external, unauthenticated attacker who is a legitimate (even low-privilege) GitHub user/collaborator of "OrgA" — or who otherwise learns/computes a valid signature under OrgA's `webhook_secret` (e.g. by triggering real webhook deliveries from an OrgA repo they control) — can send a forged HTTP request to the shared `/webhooks` endpoint with:
- `X-Hub-Signature` computed with OrgA's `webhook_secret`,
- `repository.owner.login` = `"OrgA"` (so `verify_signature` picks OrgA's app/secret and passes),
- `repository.full_name` = `"OrgB/some-other-repo"` (a repository the attacker does not control and belongs to a different, unrelated organization/app installation).

Because `verify_signature` and the handler dispatch never cross-check that `full_name`'s owner equals `repository_owner`, the forged payload is accepted and processed as if it legitimately originated from OrgB's repository, e.g. triggering `PushHandler` to call `stack.sync_github(expected_head_sha: ...)` for every stack tracking `OrgB/some-other-repo` [3](#0-2) , which enqueues `GithubSyncJob` to fetch commits from GitHub using the Shipit-side (OrgB) GitHub API credentials and can advance `undeployed_commits`/status state, or drive other handlers (`status`, `check_suite`, `membership`, `pull_request`) for a repository/stack the attacker never authenticated against.

### Impact Explanation
This breaks the authentication-to-write binding: an entity that authenticated as OrgA is able to cause writes/state changes scoped to OrgB's repositories and stacks — i.e., a cross-repository/cross-organization write performed without ever being authorized for the target repository. This matches the "cross-repository writes" Critical impact category. Concretely, an attacker can spoof `push`/`status`/`check_suite`/`membership` events for a stack they do not own, influencing sync state, check-run refresh, team/membership records (`MembershipHandler` creates/deletes `Membership`/`Team`/`User` records tied to `organization.login`, itself one of the two independently-controlled fields) and downstream deploy eligibility, without ever possessing the target organization's `webhook_secret`.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations/apps (a documented, supported configuration), and (2) the attacker being able to produce, or replay, a validly-signed payload for at least one configured organization (their own repo's legitimate webhook delivery, which they can trigger themselves without any Shipit credential — this is exactly the "no Shipit session/token" attacker model). No Shipit login, `ApiClient` token, or repository write access to the *target* repository is required — only ordinary GitHub webhook delivery capability for a repository the attacker controls under a different configured organization. Likelihood is moderate: it depends on multi-org deployment, but the feature and test fixtures for it exist explicitly in this engine.

### Recommendation
Bind webhook signature verification to the same fully-qualified repository (not just organization) that the handlers act on: validate that the organization used to select the `webhook_secret`/App matches `payload.dig('repository', 'owner', 'login')` and that this equals the owner segment of `payload.dig('repository', 'full_name')`, rejecting the request otherwise. Alternatively, verify the signature per-installation using the GitHub App installation ID resolved from the payload's `installation.id`, and re-derive `repository_owner` strictly from `repository.full_name` (never from the separate, spoofable `organization.login` fallback) so the value used for secret selection and the value used for the write target are provably the same field.

### Proof of Concept
1. Configure Shipit with two organizations (as in `secrets_double_github_app.yml`): OrgA with `webhook_secret: sA`, OrgB with `webhook_secret: sB`.
2. As an attacker who owns/administers a repo under OrgA (or otherwise knows `sA`), compute `X-Hub-Signature = sha1=HMAC-SHA1(sA, body)` for a crafted `push` payload where:
   - `body.repository.owner.login = "OrgA"`
   - `body.repository.full_name = "OrgB/target-repo"`
   - `body.ref = "refs/heads/main"`, `body.after = "<some sha>"`
3. POST this body with header `X-Github-Event: push` and the computed signature to the shared `/webhooks` endpoint.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `sA` [6](#0-5) .
5. `PushHandler#process` looks up stacks via `Repository.from_github_repo_name("OrgB/target-repo")` and invokes `stack.sync_github(expected_head_sha: ...)` for OrgB's stack [2](#0-1) [3](#0-2) , despite the request never being signed by OrgB's secret.

**Note on uncertainty:** I could not fully verify, within the available index, how `Shipit.github(organization:)` behaves when `github_default_organization` is `nil` (single-org mode) — in that mode `repository_owner` may be unused for secret selection, which would make this specific cross-org path inapplicable to single-organization deployments. I also could not inspect `Repository.from_github_repo_name` or `MembershipHandler`/`Team`/`Membership` creation code in full to confirm the exact downstream blast radius for non-push events. If deeper verification of these paths is needed, a full Devin session with complete repository access would be required.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
