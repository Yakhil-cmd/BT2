### Title
Non-recursive `DenyReserveTransferToRelayChain` barrier bypassable via nested `SetAppendix`/`SetErrorHandler` XCM instructions - (`system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs`, and equivalently `asset-hub-polkadot`, `bridge-hub-kusama`, `collectives-polkadot`, `coretime-kusama`, `coretime-polkadot`, `people-kusama`, `people-polkadot`)

### Summary
`DenyReserveTransferToRelayChain` only scans the top-level instruction list of an incoming XCM program for `InitiateReserveWithdraw`/`DepositReserveAsset`/`TransferReserveAsset` targeting the Relay Chain; it does not recurse into nested XCM programs embedded inside instructions like `SetAppendix`, `SetErrorHandler`, or `ExecuteWithOrigin`. The codebase itself demonstrates the fix (`DenyRecursively<DenyReserveTransferToRelayChain>`) applied to `bridge-hub-polkadot` and `bulletin-polkadot`, but this wrapper is missing on `asset-hub-kusama`, `asset-hub-polkadot`, `bridge-hub-kusama`, `collectives-polkadot`, `coretime-kusama`, `coretime-polkadot`, `people-kusama`, and `people-polkadot`, leaving those chains' barriers bypassable.

### Finding Description
The vulnerable chains configure their `Barrier` as: [1](#0-0) 
i.e. `DenyThenTry<DenyReserveTransferToRelayChain, (...)>` with no `DenyRecursively` wrapper, whereas `bridge-hub-polkadot` and `bulletin-polkadot` use `DenyThenTry<DenyRecursively<DenyReserveTransferToRelayChain>, (...)>`: [2](#0-1) [3](#0-2) 

`DenyReserveTransferToRelayChain::should_execute` (upstream `xcm-builder`) inspects only the top-level `message` slice via `message.iter().any(|inst| matches!(inst, InitiateReserveWithdraw{..}|DepositReserveAsset{..}|TransferReserveAsset{..}))`. Instructions such as `SetAppendix(Xcm<Call>)` and `SetErrorHandler(Xcm<Call>)` carry a *nested* `Xcm` program as a field value; the outer iterator sees only the `SetAppendix`/`SetErrorHandler` variant itself, never unwrapping and matching the inner instructions. Consequently, an attacker can craft a top-level program consisting only of benign instructions (e.g. `WithdrawAsset`, `BuyExecution`) plus a `SetAppendix([InitiateReserveWithdraw { reserve: Parent, .. }])`, and the `DenyReserveTransferToRelayChain` scan will find no matching pattern at the top level and allow execution to proceed to the `Try` branch of `DenyThenTry`. Once permitted (e.g. via `AllowTopLevelPaidExecutionFrom<Everything>` after paying execution fees), the XCM executor runs the main instructions and then executes the appendix/error-handler instructions in the *same* execution context — without re-invoking the `Barrier`/`ShouldExecute` check — so the deny rule never sees the hidden reserve-withdraw instruction.

The attack is reachable by any unprivileged signed account: `pallet_xcm::Config::ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>` and `XcmExecuteFilter = Everything` allow any signed origin to call `pallet_xcm::execute` with an arbitrary attacker-crafted XCM program. [4](#0-3) 

### Impact Explanation
The barrier's explicit purpose is to prevent reserve-based asset transfers to the Relay Chain, forcing all such transfers through the audited teleport path. By nesting the denied instruction inside `SetAppendix`/`SetErrorHandler`, a normal user bypasses this policy control entirely, executing a reserve-transfer/withdraw pattern to the Relay Chain that the runtime's design explicitly disallows. Depending on `IsReserve`/`IsTeleporter` config for the specific asset and chain, this can result in incorrect reserve/teleport accounting semantics between the parachain and Relay Chain, undermining the "Filters, barriers ... must not be bypassable by normal users" invariant, even where actual funds are backed by the user's own withdrawn assets.

### Likelihood Explanation
This requires no privileged access, no proxy, and no special preconditions beyond holding a small balance to pay for a `pallet_xcm::execute` call and constructing a valid nested XCM program — both fully within reach of any ordinary signed account. The bug is deterministic and repeatable for every affected chain and does not depend on race conditions or external state.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` with `DenyRecursively` in the `Barrier` type for `asset-hub-kusama`, `asset-hub-polkadot`, `bridge-hub-kusama`, `collectives-polkadot`, `coretime-kusama`, `coretime-polkadot`, `people-kusama`, and `people-polkadot`, matching the pattern already used in `bridge-hub-polkadot` and `bulletin-polkadot`: [5](#0-4) 

### Proof of Concept
Rust unit test against the affected chain's `Barrier` type (e.g. `asset-hub-kusama::xcm_config::Barrier`):
```rust
#[test]
fn deny_reserve_transfer_to_relay_via_nested_appendix_is_blocked() {
    use xcm::latest::prelude::*;
    use xcm_executor::traits::{ShouldExecute, Properties};

    let relay = Location::parent();
    let mut inner_appendix = Xcm(vec![
        InitiateReserveWithdraw {
            assets: All.into(),
            reserve: relay.clone(),
            xcm: Xcm(vec![]),
        },
    ]);
    let mut message: Xcm<()> = Xcm(vec![
        WithdrawAsset((Here, 1_000_000_000u128).into()),
        BuyExecution { fees: (Here, 1_000_000_000u128).into(), weight_limit: Unlimited },
        SetAppendix(inner_appendix.clone()),
    ]);

    let origin = Location::new(0, [AccountId32 { network: None, id: [1u8; 32] }]);
    let mut properties = Properties { weight_credit: Weight::zero(), message_id: None };

    // EXPECTATION (currently fails without DenyRecursively): should be denied.
    let result = Barrier::should_execute(&origin, &mut message.0, Weight::from_parts(1_000_000_000, 0), &mut properties);
    assert!(result.is_err(), "reserve-withdraw-to-relay hidden in SetAppendix must be denied");
}
```
