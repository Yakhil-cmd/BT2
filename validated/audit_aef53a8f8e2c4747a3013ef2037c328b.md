### Title
Cross-organization `Team` membership tampering via unscoped `github_id` lookup in `MembershipHandler` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound `membership` webhook against the GitHub App configured for *one* organization (derived from the payload itself, since `membership` events carry no `repository` key), while `MembershipHandler` writes membership changes to whatever local `Team` row matches the payload's numeric `team.id` — without checking that the team actually belongs to the organization whose secret signed the request. This breaks the binding "organization that authenticated the webhook == organization whose `Team`/`Membership` rows may be mutated," and can be used to add an attacker-controlled GitHub login to a `Team` that is used by `Shipit.github_teams` for authorization.

### Finding Description
`WebhooksController#verify_signature` selects which configured GitHub App/secret to verify against using `repository_owner`, which for events lacking a `repository` key falls back to `params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

This means a `membership` event is verified solely with the secret configured for the organization named in the payload's own `organization.login` field — i.e. whichever org the sender claims to represent, as long as that org has a configured `Shipit.github(organization:)` entry (a Shipit instance can track/host multiple organizations, each with its own App/webhook secret, per `lib/shipit/github_app.rb`).

`MembershipHandler#process` then resolves the target `Team` purely by the payload's `team.id`, with no check that `params.organization.login` matches the team's stored `organization`: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` only sets `team.organization = params.organization.login` inside the creation block, which does **not** run if a `Team` row with that `github_id` already exists (e.g. created earlier for a different, legitimately-tracked organization). In that case the handler silently operates on the pre-existing `Team` and calls `team.add_member(member)` / `team.members.delete(member)` using the *attacker-signed* `member.login`, even though the request was authenticated for a different organization than the one that owns the team.

The database schema confirms `github_id` is not scoped to `organization` (only `["organization", "slug"]` is a unique index), so this collision is a straightforward primary-key lookup, not merely a hypothetical corner case: [4](#0-3) 

The resulting `Team.members` list is exactly what gates application access: `User#authorized?` checks membership in the teams configured in `Shipit.github_teams`: [5](#0-4) 

### Impact Explanation
If any `Shipit.github_teams`-designated authorization team (belonging to organization B) has already been synced into the local `teams` table (its `github_id` is known/discoverable, since GitHub team IDs are ordinary API-visible integers), an operator who administers a *different* organization (A) that is also tracked by the same multi-tenant Shipit instance — and therefore legitimately possesses org A's webhook secret — can send a forged `membership` webhook, correctly signed for org A, whose payload names org B's team `github_id` and an arbitrary GitHub login as `member.login`. `MembershipHandler` will add that login to the existing (org B) `Team` row, granting it de-facto Shipit application access via `User#authorized?`. This is an escalation into `Shipit.github_teams` authorization, matching the High-impact category for this exercise.

### Likelihood Explanation
Medium. It requires: (a) the target Shipit deployment to track more than one GitHub organization (documented as supported via `Shipit.github(organization:)`), (b) the attacker to legitimately control a webhook secret for at least one tracked organization (i.e., be an admin of some org integrated with the instance, not a privileged Shipit user), and (c) knowledge of the numeric `github_id` of the target authorization team (discoverable through GitHub's team APIs or already recorded from prior sync jobs). These are non-trivial but realistic preconditions for a multi-tenant deployment, and no Shipit session, API token, or GitHub App private key is needed — only a self-controlled, already-configured organization's webhook secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and the authenticated organization (`params.organization.login`), and reject (or no-op) if an existing `Team` with that `github_id` belongs to a different `organization` than the one that signed the webhook:

```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  raise ArgumentError, "Team organization mismatch" if team && team.organization != params.organization.login

  Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```

More generally, `WebhooksController#verify_signature` should also assert that the organization used to select the verification secret matches the organization referenced by whatever record the corresponding handler intends to mutate, rather than trusting the payload's self-declared organization in isolation.

### Proof of Concept
1. Shipit is configured to track two organizations, `org-a` and `org-b` (each with its own GitHub App/webhook secret), via `Shipit.github(organization:)`.
2. `org-b/admins` is listed in `Shipit.github_teams` and has already been synced, creating a local `Team` row with `github_id: 555, organization: "org-b"`.
3. Attacker administers `org-a` and legitimately knows `org-a`'s webhook secret.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, correctly HMAC-signed with `org-a`'s secret, and body:
```json
{
  "action": "added",
  "team": { "id": 555, "name": "Admins", "slug": "admins", "url": "https://github.com/orgs/org-b/teams/admins" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-controlled-login" }
}
```
5. `verify_signature` authenticates the request using `org-a`'s secret (since `repository_owner` resolves to `params.organization.login == "org-a"`) — the signature check passes.
6. `MembershipHandler#find_or_create_team!` finds the existing `Team` (`github_id: 555`, `organization: "org-b"`) and `team.add_member(User.find_or_create_by_login!("attacker-controlled-login"))` adds the attacker's account to `org-b/admins`.
7. That user now passes `User#authorized?` and gains authenticated access to the Shipit UI/API as a member of an authorization team it was never legitimately added to.
