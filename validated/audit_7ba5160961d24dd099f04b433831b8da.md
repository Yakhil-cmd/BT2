### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while write actions act on the independently-controlled `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Every event handler, however, resolves the actual `Repository`/`Stack` that gets mutated using a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` in `Handlers::Handler#repository_name`. Because both fields live in the same raw POST body that the attacker fully controls, and the HMAC only proves "this exact byte string was signed with the secret belonging to whatever org `repository.owner.login` claims to be," an attacker who legitimately owns/administers a *different* organization onboarded into the same multi-tenant Shipit instance (and therefore genuinely knows that org's `webhook_secret`) can forge a signed payload that authenticates as their own org while acting on a victim organization's repository/stack.

### Finding Description
- Trust selection: `Shipit.github(organization: repository_owner)` in `app/controllers/shipit/webhooks_controller.rb:25` and `repository_owner` in lines 59-62 uses `repository.owner.login` (or `organization.login` as fallback). [1](#0-0) [2](#0-1) 
- Write target selection: every handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`, etc.) inherits `Handler#stacks`/`#repository_name`, which resolves the target repository from `payload.dig('repository', 'full_name')` — a field never used in the signature-key-selection step. [3](#0-2) 
- `PushHandler#process` then acts on stacks resolved from that field, calling `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` sha. [4](#0-3) 
- The HMAC check itself (`GithubApp#verify_webhook_signature`) only proves that the raw body was signed with the secret of the organization *named inside that very same body*; it does not tie `repository.owner.login` to `repository.full_name`. [5](#0-4) 

Because a Shipit instance can host multiple GitHub organizations, each with its own `webhook_secret` (as documented in `config/secrets.development.example.yml`), an attacker who administers Organization A (and thus legitimately knows A's `webhook_secret`) can POST to `/webhooks` a JSON body where `repository.owner.login` = `"org-a"` (so `verify_signature` selects and validates against A's known secret) but `repository.full_name` = `"org-b/victim-repo"` (a stack belonging to a completely different, victim organization B that the attacker has no access to). The signature will verify successfully because the attacker controls the entire raw body and knows the secret used to sign it; the handler will nonetheless operate on organization B's stack.

The binding being broken, expressed as an equality: `organization authenticated by verify_signature (repository.owner.login / organization.login)` **should equal but does not equal** `repository whose Stack/Repository record is mutated (repository.full_name)`.

### Impact Explanation
Depending on which event is forged, this crosses the "unauthorized deploy" bar the rules call out:
- A forged `push` event triggers `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, forcing out-of-band syncs against a repository the attacker doesn't control. [6](#0-5) 
- More critically, a forged `status` event lets the attacker inject a fabricated commit status (e.g. mark a required CI context as `success`) for a commit in the victim's stack (as confirmed by the existing `status_master` fixture flow that writes `sha`/`state`/`context` straight onto `commit.statuses`). If that flips the commit to "deployable" and the victim stack has `continuous_deployment` enabled, this triggers `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery`, causing an unauthorized automatic deploy of the victim's stack — matching the documented behavior in `commits_test.rb` ("updating state to success triggers new deploy when stack has continuous deployment"). [7](#0-6) [8](#0-7) 

This satisfies "an unauthorized deploy" impact without requiring any Shipit session, API token, or the victim organization's own webhook secret — only knowledge of a secret the attacker legitimately possesses for their own onboarded organization.

### Likelihood Explanation
Exploitability requires only that the Shipit instance is multi-tenant (hosts more than one GitHub organization/app config, as explicitly supported and documented in `config/secrets.development.example.yml`), and that the attacker legitimately administers one of those organizations (a normal, unprivileged position for a self-service CI platform). No GitHub App private key, `api_clients_secret`, or victim credentials are needed — only the attacker's own, legitimately-known `webhook_secret`.

### Recommendation
Bind signature-key selection to the same field(s) used for all downstream mutations, and reject requests where they diverge. Concretely:
1. In `verify_signature`, additionally verify that `repository_owner` matches the owner segment of `repository.full_name` before proceeding.
2. Alternatively, resolve the target `Stack`/`Repository` using the already-authenticated organization, or require handlers to assert `repository.full_name.split('/').first == verified_organization` before performing any write.

### Proof of Concept
1. Attacker legitimately administers `org-attacker` in a multi-tenant Shipit deployment and knows `org-attacker`'s `webhook_secret` (they configured the GitHub App themselves).
2. Attacker crafts a `status` (or `push`) webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": {
       "full_name": "org-victim/victim-repo",
       "owner": { "login": "org-attacker" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker's webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "org-attacker"`, fetches `org-attacker`'s `webhook_secret` via `Shipit.github(organization: "org-attacker")`, and the HMAC check passes (attacker signed the body with the correct, known secret). [1](#0-0) 
5. `StatusHandler` (subclass of `Handler`) resolves stacks via `payload.dig('repository', 'full_name')` = `"org-victim/victim-repo"`, and creates/updates a `Status` on the victim's commit. [9](#0-8) 
6. If `org-victim`'s stack has `continuous_deployment: true` and this status completes its required checks, `Commit#statuses.create!` transitively triggers `ContinuousDeliveryJob`, causing an unauthorized deploy of `org-victim/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!

      end

                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?

      CacheDeploySpecJob.perform_later(stack)
    end
```
