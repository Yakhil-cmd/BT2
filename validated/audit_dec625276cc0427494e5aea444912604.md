### Title
Webhook signature-selection uses an unverified `repository.owner.login` field, allowing bypass of HMAC verification for multi-organization deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly out of the **unauthenticated** JSON body, before the signature has been checked. `GitHubApp#verify_webhook_signature` then unconditionally returns `true` whenever the selected organization has no `webhook_secret` configured. Because the value used to pick the verification context (`repository.owner.login` / `organization.login`) is never itself covered by any signature, and the value used by the actual event handlers to select the target stack (`stacks`/`branch`/`params.after`, matched against `Repository`/`Stack` records) is derived independently from the rest of the same unauthenticated payload, an attacker can forge a request whose "owner" field points at any org lacking a `webhook_secret`, sail through verification, and then have the handler act on data describing a different, victim repository/stack.

### Finding Description
The binding that should hold is:
`organization used to authenticate the request == organization the acted-upon repository belongs to`.

In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read straight from `request.raw_post` (parsed as `params`) — a field with no cryptographic protection at this point, since the whole point of `verify_signature` is to establish trust in the request body. This value is used to look up a per-organization `GitHubApp` instance:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  ...
end
``` [2](#0-1) 

And `verify_webhook_signature` trivially passes when that organization has no secret configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Shipit explicitly supports running multiple GitHub App configs for different organizations, each with its own `webhook_secret`, as documented in `config/secrets.development.example.yml` [4](#0-3)  and `lib/shipit.rb#github_organizations`/`#github_app_config` [5](#0-4) . Nothing prevents one organization in this multi-tenant config from being deployed without a `webhook_secret` (the same schema documents `webhook_secret: # nil` as an explicitly supported case) [6](#0-5) .

Once `verify_signature` passes (because the attacker-controlled `repository.owner.login` matched the un-keyed org), execution reaches `create`, which dispatches the entire, still-attacker-controlled JSON body to the registered event handler:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

Handlers such as `PushHandler` resolve the target `Stack`/`Repository` from other, independent fields of that same body (`ref`, `after`, and the `repository` scoping done in the base `Handler`), not from `repository_owner`:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [8](#0-7) 

So the field consulted to decide "is this request authentic" (`repository.owner.login`, resolved against a possibly-unsecured org) is disjoint from the field consulted to decide "what repository/stack does this request act on." An attacker who knows (or guesses) that at least one configured organization has no `webhook_secret` can set `repository.owner.login` to that organization's name while filling in `repository.full_name`, `ref`, `after`, etc. with data describing a *different*, secured organization's stack, and the forged webhook will be accepted and processed as if it were legitimately signed for that target repository.

### Impact Explanation
This breaks the authentication boundary the whole `X-Hub-Signature` check exists to enforce: forged, unsigned GitHub events (`push`, `status`, `pull_request`, `merge`, `deployable_status`, etc., listed in `Shipit::Webhooks`/`Hook::EVENTS`) can be injected against any stack in the installation, from any org, as long as one org in the multi-org config lacks a `webhook_secret`. Depending on the handler this can trigger `GithubSyncJob` on arbitrary refs, spoof commit/check statuses that gate deploy eligibility, or manipulate merge/PR state used by Shipit's merge queue — i.e., an unauthorized deploy or merge decision driven entirely by attacker-supplied, unauthenticated data. This qualifies as Critical under the program's "unauthorized deploy, rollback or merge" category.

### Likelihood Explanation
Exploitability depends entirely on operational configuration: the multi-organization github config schema must be in use, and at least one configured organization must have `webhook_secret` unset/blank — a state the shipped example configs explicitly show as valid (`webhook_secret: # nil`) [6](#0-5) . Given that Shipit's own documented example configuration allows `webhook_secret: nil` per organization, and the code path is reachable from any unauthenticated POST to `/webhooks`, the code-level flaw is real; whether a given deployment is affected depends on whether the operator configured every organization with a secret.

### Recommendation
Do not let unverified request-body fields select the verification context. Either:
1. Require every organization entry in a multi-org config to have a non-blank `webhook_secret` (fail closed instead of `return true unless webhook_secret`), or
2. Verify the signature against *all* configured secrets (or a global secret) before trusting any body-derived routing field, and only use `repository_owner`/`organization` for logging/dispatch after the signature has been validated against the correct, independently-established secret.
3. Additionally, cross-check that the organization used for `Shipit.github(organization: ...)` matches the actual owner of the repository/stack that the handler will act upon, so the authenticating org and the acted-upon repository can never diverge.

### Proof of Concept
Given a multi-org secrets config where `secured-org` has a `webhook_secret` and `unsecured-org` does not:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   (no valid secret needed)

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "secured-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
1. `WebhooksController#verify_signature` computes `repository_owner == "unsecured-org"` from the raw, unverified body [9](#0-8) .
2. `Shipit.github(organization: "unsecured-org")` loads that org's config, whose `webhook_secret` is blank [2](#0-1) .
3. `verify_webhook_signature` returns `true` immediately because `webhook_secret` is nil, regardless of the bogus `X-Hub-Signature` [3](#0-2) .
4. `create` dispatches the full body — including the real target `repository.full_name`/`ref`/`after` for `secured-org/victim-repo` — to `PushHandler`, which enqueues `GithubSyncJob` against that stack using attacker-chosen `expected_head_sha` [8](#0-7) , with no valid signature ever having been produced for `secured-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
