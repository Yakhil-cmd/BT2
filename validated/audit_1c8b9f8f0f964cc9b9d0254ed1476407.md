### Title
Cross-organization Team/Membership mutation via `membership` webhook bypasses org-scoping, enabling `Shipit.github_teams` authorization escalation - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` by `github_id` alone, without scoping to the organization whose `webhook_secret` authenticated the request. In a multi-org Shipit deployment, an attacker administering their own registered GitHub org can forge a validly-signed `membership` webhook whose `team.id` equals an *existing* Team row belonging to a different org, causing the handler to add/remove `Membership` rows on that victim `Team` — which can feed directly into `Shipit.github_teams`-based login authorization.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`[organization whose webhook_secret verified the "membership" event] == [organization owning the Team row that gets mutated]`.

Path: `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` where `repository_owner` falls back to `params.dig('organization','login')` for events without a `repository` key [1](#0-0) . In a multi-app config (`docs/setup.md` "Using Multiple Github Applications"), `Shipit.github(organization:)` looks up a per-org `webhook_secret` keyed by that org name [2](#0-1) , so an attacker who legitimately administers `attackerorg` can compute a valid `X-Hub-Signature` for a payload with `"organization":{"login":"attackerorg"}` using `attackerorg`'s own secret — no victim secret is needed.

Once verified, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler#process`, which calls:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 

`find_or_create_by!` looks up solely by `github_id`. The block (which would set `organization` to the attacker's org) only runs on *creation*; if a `Team` with that `github_id` already exists — e.g., a victim org's team created earlier via `Team.find_or_create_by_handle` or a prior legitimate `membership` webhook — the existing record is returned untouched, and `process` then does `team.add_member(member)` or `team.members.delete(member)` [4](#0-3) , mutating `Membership` rows on the victim's `Team` despite the request only ever having been authenticated against `attackerorg`'s secret. `Team` rows are not namespaced/scoped by the org whose app verified the webhook — `Team.find_or_create_by!` has no `organization:` clause [5](#0-4) .

`params.member.login` is fully attacker-controlled and is resolved via `User.find_or_create_by_login!`, which calls `Shipit.github.api.user(login)` — a public GitHub user lookup requiring no special access [6](#0-5) , so the attacker can name any real GitHub login (including their own).

Why existing guards don't stop this:
- `verify_signature` only proves the request was signed by *some* org's app; it never re-checks that the `team.id`/`organization.login` in the payload actually belongs to that same org before mutating rows [7](#0-6) .
- The `ExplicitParameters` schema in `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, `member.login` — it does not correlate `team.id`'s owning org with `organization.login` or with the org that authenticated the request [8](#0-7) .
- `Team` has no unique/foreign-key constraint tying `github_id` to `organization` for lookup purposes.

Downstream impact via `Shipit.github_teams`: this is a global authorization list built once from the *default* org's `oauth.teams` config: `github.oauth_teams.map { |t| Team.find_or_create_by_handle(t) }` [9](#0-8) . `User#authorized?` checks membership against this fixed team-id set: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [10](#0-9) , and `force_github_authentication` gates all app access on `current_user.authorized?` [11](#0-10) . If one of these authorization-gating `Team` rows happens to share a `github_id` targeted by the attacker's forged `membership` webhook, the attacker can insert a `Membership` row linking any GitHub login (including a login they control) to that team, then complete a normal GitHub OAuth login as that account via `GithubAuthenticationController#callback` [12](#0-11)  and pass `authorized?`, gaining full access to the Shipit instance.

### Impact Explanation
An attacker who only administers their own GitHub org (`attackerorg`) can, without any victim secret, write/delete `Membership` rows on a `Team` belonging to a completely different org, provided they can guess/know that team's numeric GitHub team `id` (globally unique, not secret-derived). If that `Team` is one of the org's `Shipit.github_teams` authorization teams, this becomes an authentication/authorization-bypass primitive: an unprivileged GitHub user gains `authorized?` status and thus full access to deploy/rollback/manage stacks in the victim's Shipit instance — matching the High severity category "escalation into `Shipit.github_teams` authorization." Repeatable per team id and per member login, and it works against any Team row already present in the database, cross-tenant.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub Apps/orgs (the documented multi-org setup) so the attacker has valid credentials for at least one org's webhook secret; (2) the attacker knowing/guessing a numeric `team.id` (GitHub team IDs) belonging to a different, victim org whose corresponding `Team` row already exists in Shipit's DB; (3) that Team being one of `Shipit.github_teams` for the escalation path (otherwise impact is limited to spurious Membership rows on an unrelated Team, which is lower severity but still a cross-org write with no authentication proving the mutator owns that org). Attacker cost is low once a multi-org deployment and a target team id are known — no GitHub App private key, no victim webhook secret needed.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and the verified organization (the org resolved by `WebhooksController#verify_signature`, e.g. passed down as `repository_owner`), rejecting/logging (not mutating) if an existing `Team` with that `github_id` belongs to a different `organization`. Additionally, add a DB-level uniqueness/ownership check so `Team#github_id` mutations can only affect rows whose `organization` column matches the payload's `organization.login`, and that `organization.login` matches the org used for signature verification.

### Proof of Concept
```ruby
test ":membership from AttackerOrg cannot mutate a victim org's Team" do
  # Victim team already exists, belongs to shopify
  victim_team = shipit_teams(:shopify_developers)

  # Simulate multi-org setup: attackerorg has its own configured webhook secret
  Shipit.stubs(:github_app_config).with('attackerorg').returns(webhook_secret: 'attacker-secret')
  Shipit.github(organization: 'attackerorg') # memoized GitHubApp with attacker-secret

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attackerorg' },
    member: { login: 'attacker_login' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', payload)

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  Shipit.github.api.expects(:user).with('attacker_login').returns(stub(id: 999, login: 'attacker_login', name: 'A', email: 'a@a.com', avatar_url: '', url: ''))

  assert_difference -> { victim_team.reload.members.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  # Equality check: the org that signed the request ("attackerorg")
  # must equal the org owning the mutated Team ("shopify") -- it does not.
  refute_equal 'attackerorg', victim_team.organization
end
```
Note: exact stubbing of `Shipit.github_app_config`/multi-org secrets depends on `test/dummy` credentials fixtures (e.g. `test/dummy/config/secrets_double_github_app.yml`) which provide a real multi-org config to drive this without stubbing private methods — a background engineer should adapt the PoC to use that fixture file for an end-to-end signature computed against a genuine second org's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
