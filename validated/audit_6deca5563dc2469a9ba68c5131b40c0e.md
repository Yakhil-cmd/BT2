### Title
Webhook signature verification is scoped to an attacker-chosen organization while the payload's target repository/team is a separate, unverified field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to HMAC-verify a request against using an attacker-supplied JSON field (`repository.owner.login`/`organization.login`), while the handlers that actually mutate state (`Shipit::Webhooks::Handlers::Handler#stacks`, `MembershipHandler#process`) act on a *different*, independently-controlled field (`repository.full_name`, `team.id`, `member.login`) taken from the same attacker-authored body. In a multi-organization Shipit deployment (the `github:` config keyed by org, as documented in `docs/setup.md`), this breaks the binding "organization whose signature authenticated the request == repository/team the request is allowed to write to."

### Finding Description
`verify_signature` derives the organization used to look up the verification secret directly from the untrusted body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` maps that string to a distinct `GitHubApp` instance holding its own `webhook_secret` when multiple orgs are configured: [3](#0-2) 

Each org's `webhook_secret` is independent, per `docs/setup.md`'s example config and `github_app_config`. `verify_webhook_signature` HMACs the entire raw body with that org's secret: [4](#0-3) 

The signature therefore proves only "this body was signed with organization X's secret" — it never asserts that the *content* of the body (which repository/team it claims to modify) actually belongs to organization X. Once verification passes, every handler reads the target repository from a separate field, `repository.full_name`, entirely decoupled from `repository.owner.login`: [5](#0-4) 

`PushHandler` uses that repository to run `stack.sync_github`: [6](#0-5) 

`MembershipHandler` similarly trusts attacker-supplied `team.id`/`organization.login`/`member.login` to add or remove team members without any cross-check against the org that passed signature verification: [7](#0-6) 

Because `Team.find_or_create_by!(github_id:)` matches on `github_id` alone, if the attacker knows or can enumerate the numeric GitHub team ID of a team referenced in `Shipit.github_teams` (used for the authorization gate in `User#authorized?`), they can forge a `membership` event — signed with their own org's known secret — claiming `action: "added"`, `team.id: <victim team id>`, `member.login: <attacker's github login>`, and get added as a member of that team: [8](#0-7) 

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary in a multi-org Shipit instance. Concretely:
- An attacker who administers their own organization's GitHub App/webhook integration (and thus legitimately knows their own `webhook_secret`) can forge `push`/`status`/`check_suite` events that are verified against their own org's secret but whose `repository.full_name` targets a stack belonging to a different, unrelated organization tracked by the same Shipit instance, triggering unwanted `GithubSyncJob`/status writes for that victim stack.
- Worse, a forged `membership` event can add the attacker to any `Team` record matched purely by numeric `github_id`, which — if that team is included in `Shipit.github_teams` — grants the attacker `User#authorized?` status, escalating into the deploy/rollback authorization gate used across the app.

This matches the "High" impact bucket: escalation into `Shipit.github_teams` authorization via a forged, org-mismatched webhook.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with multiple GitHub organizations (the supported `github: {org1: {...}, org2: {...}}` schema), and (2) the attacker controlling at least one such configured organization's GitHub App/webhook (i.e., they are a legitimate, but unprivileged-relative-to-the-victim-org, tenant of the shared instance). Given that, forging the body is trivial (it's just JSON with a valid HMAC using a secret the attacker legitimately possesses); no GitHub-side webhook delivery is needed since the endpoint accepts any POST with a matching signature header. Guessing/enumerating a target `team.id` (a small integer, often discoverable via GitHub's public API for the victim org's team) is the main extra step for the team-membership escalation path.

### Recommendation
Bind the verification organization to the actual content being processed rather than trusting the payload's declared owner independently of the handler-consumed repository/team fields:
- After selecting `github_app` in `verify_signature`, re-derive the repository/organization actually referenced by the handler-relevant fields (`repository.full_name`, `organization.login` in membership events) and reject the request if it doesn't match `repository_owner`.
- In `Handler#repository_name` and `MembershipHandler#find_or_create_team!`, cross-check that the resolved `Repository`/`Team`'s organization equals the organization whose secret verified the request, rejecting/ignoring events where they diverge.
- Consider verifying against every configured org's secret only for events whose declared owner matches an org that is entitled to reference the resolved repository/team, rather than a single attacker-chosen lookup key.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (secret known to the attacker, who administers that GitHub App) and `victim-org` (tracks a stack `victim-org/prod-repo` and a `Team` with `github_id: 555` included in `Shipit.github_teams`).
2. POST to `/github/webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": {"id": 555, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/555"},
  "organization": {"login": "attacker-org"},
  "member": {"login": "attacker-handle"}
}
```
signed with `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>`.
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
4. `MembershipHandler#process` runs unchecked, matching `Team.find_or_create_by!(github_id: 555)` — the victim's team — and appends `attacker-handle` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
5. If that team is part of `Shipit.github_teams`, the attacker's Shipit `User` now returns `true` from `authorized?`, escalating their privileges within the app despite never being verified by `victim-org`'s webhook secret.

```ruby
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
