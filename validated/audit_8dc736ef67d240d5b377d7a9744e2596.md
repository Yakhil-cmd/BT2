### Title
`pallet-revive`'s `fungibles::Mutate` impl panics via `.expect()` when an ERC20 contract's `transfer` call succeeds but does not return ABI-encoded `bool` - ([File: substrate/frame/revive/src/impl_fungibles.rs])

### Summary
The reported ERC20 issue is that `Vault_Base_ERC20._decreaseLoan` unconditionally treats the return of `collateral.transfer()` as a `bool` and reverts when a non-standard ERC20 token doesn't return a bool. The Polkadot SDK analog is in `pallet-revive`'s `fungibles::Mutate` implementation for arbitrary ERC20 contracts used as XCM-fungible assets: after a successful (non-reverted) contract call, the code unconditionally decodes the return data as `bool` with `.expect("Failed to ABI decode")` instead of gracefully handling malformed/absent return data — turning a foreign contract's non-standard behavior into a Rust panic instead of a typed error.

### Finding Description
`pallet_revive::Pallet<T>` implements `fungibles::Mutate<AccountId>` so that any ERC20 smart-contract address can be treated as an XCM fungible asset id (`Self::AssetId = H160`). In `burn_from` and `mint_into`, after calling `IERC20::transferCall` via `Self::bare_call`, the code checks whether the call reverted, and if it did not, it does: [1](#0-0) 

```
if let Ok(return_value) = result {
    if return_value.did_revert() {
        Err("Contract reverted".into())
    } else {
        let is_success =
            bool::abi_decode_validate(&return_value.data).expect("Failed to ABI decode");
        ...
```

and the identical pattern in `mint_into`: [2](#0-1) 

Both call sites use `.expect(...)` on `bool::abi_decode_validate(&return_value.data)`. Any contract whose `transfer` function does not revert but returns data that isn't a valid ABI-encoded `bool` — e.g., it returns nothing (many older/simplified ERC20 implementations, similar to the tokens described in the source report), returns a `uint256`/other type, or returns fewer/garbled bytes — causes `abi_decode_validate` to return `Err`, and the `.expect()` panics.

This is the same root-cause class as the reported bug (blind assumption that an arbitrary ERC20's `transfer` returns a well-formed `bool`), but the consequence in a FRAME runtime is more severe than a Solidity-level `revert`: a Rust panic inside pallet logic executed during dispatch is not a typed `DispatchError`, it is a genuine panic. The codebase elsewhere demonstrates the *correct*, non-panicking pattern for exactly this same problem: `assets_common::ERC20Transactor::deposit_asset_with_surplus` decodes the same return type with `abi_decode_returns_validate` and turns a decode failure into a typed `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`: [3](#0-2) 

and the test suite explicitly exercises the "contract does not return bool" scenario for that transactor and expects a graceful XCM execution failure rather than a panic: [4](#0-3) 

`impl_fungibles.rs`, however, has no such safeguard on the exact same decode operation.

### Impact Explanation
A Rust `panic!`/`.expect()` failure triggered from inside pallet logic during dispatch is a defensive-programming violation FRAME explicitly warns against, because unlike a `DispatchError` it is not a recoverable, typed failure — it can abort execution of the extrinsic/block in ways not modeled by the runtime's error-handling and weight-refund machinery, which is a far more serious consequence than the original report's "transaction reverts." Any deployer of an ERC20-shaped contract that omits or non-standardizes its `transfer` return value can make any counterparty (or the chain's own asset-transacting logic, if this `Mutate` impl is wired into an asset transactor/adapter) panic during a call to `burn_from`/`mint_into`, rather than fail cleanly.

### Likelihood Explanation
Deploying a contract on `pallet-revive` that implements a `transfer(address,uint256)` selector without emitting a spec-compliant `bool` return is trivial and requires no privileged role — this mirrors exactly the class of "doesn't return bool on transfer" tokens called out in the source report, and the repository's own tests prove such contracts are anticipated in this codebase (`MyTokenFake`, "returns a number but because it can be cast to true it still succeeds" tests in `tests.rs`). The remaining uncertainty is which live XCM asset-transactor/adapter configuration invokes `pallet_revive::Pallet<T>`'s `fungibles::Mutate` (`burn_from`/`mint_into`) specifically, as opposed to `assets_common::ERC20Transactor`, which was confirmed to be the one wired into `AssetTransactors` in `asset-hub-westend`'s `xcm_config.rs`; I was not able to finish tracing the exact call site(s) that invoke `impl_fungibles.rs`'s `Mutate` methods before running out of tool iterations. That reachability gap must be resolved to confirm real-network exploitability, but the unsafe `.expect()` pattern itself is a demonstrable defect in production pallet code, independent of which caller currently exercises it.

### Recommendation
Replace `.expect("Failed to ABI decode")` in both `burn_from` and `mint_into` in `substrate/frame/revive/src/impl_fungibles.rs` with the same graceful-error pattern already used in `assets_common::ERC20Transactor` (`abi_decode_returns_validate(...).map_err(...)` returning a typed `DispatchError` instead of panicking), so a non-compliant ERC20 contract's return data produces a recoverable error rather than a runtime panic.

#[test]
fn smart_contract_does_not_return_bool_fails() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		// This contract implements the ERC20 interface for `transfer` except it returns a uint256.
		let code = compile_module_with_type("MyTokenFake", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);

		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 220_000),
		)
		.is_err());
	});
}
