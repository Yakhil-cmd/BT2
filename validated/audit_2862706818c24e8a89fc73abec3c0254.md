### Title
Unfiltered ANSI/control-sequence injection via device pairing name propagated to console/log output - (File: device.js)

### Summary
`handlePairingMessage()` in `device.js` accepts a `device_name` from an untrusted, not-yet-confirmed remote peer during the pairing handshake and only strips HTML-like tags before persisting and later displaying/logging it, mirroring the CUPS bug class where a remote-supplied "printer name" is never filtered for ANSI/terminal escape sequences before being emitted to a terminal.

### Finding Description
When a remote device initiates pairing, `handlePairingMessage(json, device_pubkey, callbacks)` validates only length and non-emptiness of `body.device_name`: [1](#0-0) 
It then "sanitizes" the name with a regex that removes only HTML tag-like sequences, not ANSI escape codes, control characters, or terminal escape sequences: [2](#0-1) 
This `safe_device_name` is stored as `correspondent_devices.name`, a field with no additional escaping applied at the SQL layer (`VARCHAR(100)`), and is subsequently retrieved and consumed elsewhere in the codebase, e.g. by `readCosigners`, `readCorrespondents`, `readSharedAddressPeers`, all of which pass the raw `name` field through to callers/UI without further sanitization: [3](#0-2) [4](#0-3) [5](#0-4) 

Separately, `wallet_defined_by_keys.js`'s `handleOfferToCreateNewWallet` performs the exact same insufficient sanitization pattern (`replace(/[<>]/g, '')`) on `wallet_name` and each `cosigner.name`, again stripping only angle brackets and not escape sequences, before these values are emitted via `eventBus.emit("create_new_wallet", ...)` to any listener (including console-based headless wallets or CLI wallets) that will display or log them: [6](#0-5) 

Because neither sanitizer strips ASCII control characters (`\x1B[...]` ANSI CSI sequences, OSC sequences, etc.), a malicious pairing peer or cosigner can embed terminal escape sequences in `device_name`/cosigner `name`. Any downstream code path that writes this value to a terminal (`console.log`, debug/log utilities, or a wallet's own console-based UI for listing correspondents/cosigners) will have those escape sequences interpreted by the terminal emulator, exactly as in the CUPS advisory where crafted printer names containing ANSI sequences could manipulate or exploit a terminal session (including certain terminal emulators capable of triggering title-bar/clipboard writes or, in vulnerable emulators, command execution).

### Impact Explanation
An attacker who merely knows (or brute-forces/guesses within throttling limits) a pairing secret, or who is invited as a wallet cosigner, can supply an arbitrary `device_name`/cosigner `name` containing ANSI/terminal escape sequences. This name is persisted in the operator's/user's local wallet database and re-displayed every time correspondents or cosigners are listed (console-based clients, debug logging, or scripts built on this library). Depending on the terminal emulator used to run the wallet/hub node, this can range from cosmetic terminal corruption to more severe terminal-emulator vulnerabilities (e.g., writing to the terminal's title, triggering clipboard operations, or in some emulators executing further escape-driven attacks). While this is not itself a direct fund-loss vector, it is a genuine unfiltered-injection defect that mirrors CVE-2014-8166's root cause: attacker-controlled remote metadata (printer name / device name) is stored and rendered without stripping terminal control sequences.

### Likelihood Explanation
Reaching this code path only requires initiating a normal pairing handshake (`pairing` subject) or being added as a cosigner in a `create_new_wallet` offer — both are standard, unauthenticated-until-confirmed peer-to-peer wallet interactions that any correspondent device can trigger, matching the "paired device" / "wallet message handling" reachability criteria. No special privileges beyond knowing a pairing secret or being invited to co-sign are required.

### Recommendation
Extend the sanitization applied to `device_name` in `handlePairingMessage()` (device.js) and to `wallet_name`/`cosigner.name` in `handleOfferToCreateNewWallet()` (wallet_defined_by_keys.js) to strip all ASCII control characters and ANSI/VT100 escape sequences (e.g., `/[\x00-\x1F\x7F]/g` and CSI/OSC escape patterns), not just angle-bracket/HTML-like substrings, before persisting or emitting these values for display/logging.

### Proof of Concept
1. Attacker obtains/guesses a valid pairing secret for a target wallet (e.g., a `*` wildcard permanent pairing secret or a shared one).
2. Attacker sends a `pairing` device message with `body.device_name` set to a string containing an ANSI escape sequence, e.g. `"\x1B]0;pwned\x07Attacker"` (or a more elaborate escape payload), staying under the 100-character length check.
3. `handlePairingMessage()` only strips HTML-like tags via `body.device_name.replace(/<[^>]*>?/g, '')`, leaving the ANSI escape sequence intact, and stores it as `correspondent_devices.name`.
4. Any subsequent console-based listing/logging of this correspondent (e.g., a CLI/headless wallet built on `readCorrespondents`/`readCosigners`) prints the raw name to the terminal, causing the terminal emulator to interpret the injected escape sequence.
