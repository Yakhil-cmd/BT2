### Title
Cross-organization webhook forgery via signature verification bound to `repository.owner.login`/`organization.login` but handlers acting on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), each organization configured under `secrets.github` has its own independent `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects *which* secret to verify the inbound HMAC against by reading `repository_owner`, itself parsed straight out of the untrusted JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`), and passes that name into `Shipit.github(organization: repository_owner)` to fetch the matching `GitHubApp` and its `webhook_secret` [2](#0-1) . The event handlers, however, act on a *different* field of the very same payload — `repository.full_name` — to resolve the actual `Repository`/`Stack` to operate on [3](#0-2) , and `Repository.from_github_repo_name` derives owner/name purely from that string [4](#0-3) .

### Finding Description
The binding that should hold is: **the organization whose secret authenticated the signature == the organization that owns the repository actually acted upon**. This binding is not enforced.

`verify_signature` computes the org used to pick the secret from `repository.owner.login` (or `organization.login` as a fallback) [5](#0-4) , then verifies the raw body HMAC using that org's `webhook_secret` via `GitHubApp#verify_webhook_signature` [6](#0-5) . Nothing ties the *value* of `repository.owner.login` to the *value* of `repository.full_name` used later by handlers such as `PushHandler`, `StatusHandler`, or `CheckSuiteHandler`, which call `stacks`/`Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [7](#0-6) .

An attacker who administers (or otherwise possesses the `webhook_secret` for) any one org configured in the same multi-tenant Shipit instance — call it `OrgA` — can craft an arbitrary JSON body where `repository.owner.login = "OrgA"` (so `verify_signature` selects `OrgA`'s secret and the HMAC computed with the known `OrgA` secret validates) while setting `repository.full_name = "OrgB/some-tracked-repo"` for an entirely different organization's repository tracked by the same Shipit deployment. Because the HMAC covers the raw POST body as a whole, and the attacker legitimately knows `OrgA`'s secret, they can sign *any* payload content they like, including one whose `full_name` field points at `OrgB`. `verify_signature` only proves "sender knows some configured org's secret" — it never proves that org owns the repository named elsewhere in the same payload.

This lets the attacker forge, e.g.:
- A `push` event causing `PushHandler` to call `stack.sync_github(expected_head_sha: params.after)` for `OrgB`'s stacks [8](#0-7) .
- A `status`/`check_suite` event injecting forged commit statuses/check results for `OrgB` commits, which downstream gating logic (CI checks, deploy readiness) relies on.

Before the attacker's forged request: `OrgA`'s webhook_secret authenticates only events genuinely originating from `OrgA`'s GitHub App/repos. After: `OrgA`'s webhook_secret can be used to authenticate arbitrary events claimed to be about `OrgB`'s repositories, because the equality "authenticated org == acted-upon repo owner" is never checked.

### Impact Explanation
This crosses an organization/repository trust boundary that the multi-app configuration is explicitly designed to keep separate (`docs/setup.md`, "A Github application can only authenticate to the Github organization it's installed in") [9](#0-8) . Forged `push` events can trigger `GithubSyncJob`/deploy sync flows against another tenant's stacks, and forged `status`/`check_suite` events can manipulate commit check state that gates deploys — this is a cross-repository-write class issue reachable by anyone who legitimately controls one tenant's webhook secret but not another's.

### Likelihood Explanation
Requires the attacker to already know a `webhook_secret` for at least one org configured in the same Shipit instance — plausible in shared/multi-tenant Shipit deployments where different teams/orgs each administer their own GitHub App but share one Shipit installation, since GitHub App webhook secrets are typically visible to org/app admins, not just Shipit operators. No Shipit account, session, or `ApiClient` token is needed — only knowledge of one tenant's webhook secret, which this engine's own signature-selection logic (not any GitHub credential of the target org) fails to bind to the acted-upon repository.

### Recommendation
After selecting the `GitHubApp` via `repository_owner` and verifying the signature, re-verify that `repository_owner` actually matches the owner segment parsed out of `repository.full_name` (and, for organization-level events, that it matches the `Repository`/`Stack` records' recorded owner) before dispatching to handlers, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` (secret `SECRET_A`) and `OrgB` (secret `SECRET_B`), each with tracked repositories/stacks, per `docs/setup.md`'s multi-app configuration.
2. As an attacker who knows only `SECRET_A` (e.g., an `OrgA` admin), craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `SECRET_A` [10](#0-9) .
6. `PushHandler` resolves stacks via `repository.full_name = "OrgB/target-repo"` [3](#0-2)  and triggers `sync_github` for `OrgB`'s stack, even though the request was never signed by `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
