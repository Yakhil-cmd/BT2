### Title
Webhook signature-authenticated organization is not bound to the target repository acted upon, allowing cross-repository forgery of GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook using the organization derived from `repository.owner.login` (or `organization.login`), but every event `Handler` resolves the *actual* target repository/stack from a different, independently-controlled payload field: `repository.full_name`. Because these two fields are never checked for consistency, an attacker who controls the webhook secret for *any one* organization/tenant configured in Shipit can forge a payload whose signature validates against that tenant's secret while `repository.full_name` names a completely different, unrelated repository/stack, causing Shipit to act on it.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config to use for HMAC verification purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')` for events without a `repository` key, e.g. `membership`). The webhook secret used to verify the HMAC is looked up per-organization via `Shipit.github(organization: repository_owner)`, and each configured GitHub App/org has its own `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature is verified against that single field, `params` (the full, attacker-controlled JSON body) is dispatched unchanged to the event handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Every handler resolves the target repository/stack from a **separate** field, `repository.full_name`, not from `repository.owner.login`: [5](#0-4) 

This is used, e.g., by `PushHandler#process` to select stacks and force a resync to an attacker-chosen SHA: [6](#0-5) 

and by `CheckSuiteHandler#process` to schedule check-run refreshes on arbitrary stacks: [7](#0-6) 

and by the pull-request handlers (`ClosedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, etc.) which independently re-derive the repository from `params.repository.full_name` to archive/unarchive review stacks: [8](#0-7) [9](#0-8) 

**Binding that should hold:** `organization_that_authenticated (repository.owner.login used for HMAC lookup) == organization_of_repository_written (owner of repository.full_name used by handlers)`.

**Binding that actually holds:** these are two independently-settable JSON fields in the same unsigned-structure-but-signed-bytes payload; the signature covers the raw bytes, but the *authorization decision* (which secret validates them) is keyed off one field while the *effect* is keyed off another. Any tenant admin who legitimately knows their own org's `webhook_secret` (they configure/receive it when Shipit's operator sets up their GitHub App/organization entry) can set `repository.owner.login` to their own org (to pass `verify_signature`) while setting `repository.full_name` to `"other-org/other-repo"` — a stack belonging to a completely different tenant on the same shared Shipit instance.

### Impact Explanation
This breaks the multi-tenant repository boundary: a low-privileged actor who is only entitled to send webhooks for their own onboarded organization can spoof events that read as if they came from GitHub for a repository/organization they do not own. Concretely reachable effects include forcing `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha` (`PushHandler`), archiving/unarchiving review stacks belonging to unrelated repositories (`ClosedHandler`/`ReopenedHandler`/`UnlabeledHandler`), and mutating stored `PullRequest`/check-run state (`AssignedHandler`, `EditedHandler`, `CheckSuiteHandler`) for repositories outside the attacker's tenant. This is a cross-repository write into another organization's Shipit state driven by a forged, cross-tenant webhook — the class of issue the review scope calls "organization that authenticated versus the repository that is written."

### Likelihood Explanation
Exploitability requires the attacker to legitimately hold a `webhook_secret` for at least one organization configured in the same multi-tenant Shipit deployment (a realistic scenario for any Shipit instance that onboards more than one team/organization, since the org owner sets up/receives that secret when wiring their GitHub App into Shipit). No GitHub push access, Shipit session, or API token is required — only a raw HTTP POST to `/webhooks` with a validly-signed-for-their-own-org body whose `repository.full_name` names a different tenant's repository.

### Recommendation
In `Handler#stacks`/`repository_name` (and in every handler that independently derives `repository.full_name`), cross-check that the resolved repository's owner matches the organization that authenticated the request (i.e., pass `repository_owner` from the controller through to handlers and assert `repository.full_name.split('/').first == repository_owner`), rejecting the webhook otherwise. Alternatively, verify the signature using the actual target-repository's owner (derived consistently from `repository.full_name`) rather than a separately-read `repository.owner.login`/`organization.login` field, so a single canonical field drives both authentication and dispatch.

### Proof of Concept
1. Shipit is configured (via `secrets.yml`) with two tenants, `attacker-org` (webhook secret known to the attacker, who administers that org's GitHub App inside Shipit) and `victim-org/victim-repo` (a stack tracked by Shipit, unrelated to attacker-org).
2. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature (see `app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves stacks via `Handler#stacks`/`repository_name` which reads `payload.dig('repository', 'full_name')` == `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim stack with the attacker-supplied `expected_head_sha` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), even though the attacker never held any credential for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
