### Title
Webhook signature check is keyed on `repository.owner.login`/`organization.login` while the actual write target is keyed on `repository.full_name` — allows cross-org webhook forgery when any configured GitHub org has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook against using `repository_owner`, taken from the untrusted, unverified JSON body (`repository.owner.login`, falling back to `organization.login`). Every downstream `Handler` (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `pull_request/*` handlers) instead resolves the `Repository`/`Stack` to act on using a *different* field from the same untrusted body: `repository.full_name` via `Handler#repository_name` / `Repository.from_github_repo_name`. Because these two fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization named in `repository.owner.login`, an attacker can pick any configured organization that has a blank `webhook_secret` to bypass signature verification, then set `repository.full_name` to point at a *different* organization/repository (one that is actually tracked by Shipit, possibly with its own signed webhook_secret) to have Shipit act on that other org's stacks.

The binding that should hold is: `organization used to select/verify the webhook_secret == organization actually written to via repository.full_name`. Before the attack, both fields normally match because GitHub itself populates them consistently for a genuine webhook. After the attack, an attacker submits a crafted raw POST body where `repository.owner.login` (or `organization.login`) names an org configured with `webhook_secret: nil` — a valid config per the docs — while `repository.full_name` names an entirely different, tracked org/repo. `verify_signature` passes trivially (secret-less org, `verify_webhook_signature` returns `true`), yet the handler dispatched by `Shipit::Webhooks.for_event(event)` in `app/controllers/shipit/webhooks_controller.rb:10-15` operates on `Repository.from_github_repo_name(repository.full_name)`, which resolves to the victim org's stacks.

Downstream handlers that become reachable without any valid GitHub signature for the targeted org include: `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which calls `stack.sync_github(expected_head_sha:)`; `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), which calls `commit.create_status_from_github!(params)` and can forge a commit's CI status; and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`). ### Impact Explanation
Forged, unsigned `status` events let an attacker mark arbitrary commits on a victim org's tracked stack as CI-`success` via `Commit#create_status_from_github!`, which feeds directly into Shipit's deployability computation and the merge queue's auto-merge/auto-deploy gating. This is an unauthorized manipulation of deploy/merge eligibility state achieved purely by crafting an HTTP body — no `ApiClient` token, GitHub App private key, or repository write access is required — satisfying the "unauthorized deploy, rollback or merge" Critical bar, provided at least one configured GitHub org in the deployment omits `webhook_secret` (an explicitly supported and documented configuration).

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (documented, supported feature) where at least one configured org has no `webhook_secret` set — shown as a valid example in `config/secrets.development.example.yml` — and (2) the attacker knows or guesses that org's name plus the victim's `owner/name`. Both are readily discoverable (org list is often public; target repo names are typically public GitHub repos). No credentials, tokens, or session are required, matching the unprivileged-attacker requirement.

### Recommendation
After resolving the target `Repository`/`Stack` in each handler, cross-check that `payload.dig('repository','owner','login')` (the field used to select the verifying `GitHubApp`) matches the owner of the resolved `Repository`, and reject the webhook otherwise. Alternatively, verify the signature using the `GitHubApp` associated with the *resolved* repository's owner (post `Repository.from_github_repo_name` lookup) rather than the raw, unverified payload field, and require a `webhook_secret` to be present for every configured organization (fail closed instead of allowing `verify_webhook_signature` to default to `true`).

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs, e.g. `AttackerOrg` (`webhook_secret: nil`) and `VictimOrg` (`webhook_secret` set, tracked stack `VictimOrg/app`), as in `test/dummy/config/secrets_double_github_app.yml`. [10](#0-9) 
2. POST to `/github/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/app" }
   }
   ```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — commits belong to `VictimOrg/app` stacks resolved independently of the org used for verification — and calls `commit.create_status_from_github!(params)`, forging a `success` status on a victim commit without ever presenting a valid signature for `VictimOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
