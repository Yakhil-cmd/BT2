### Title
Signature verification bound to `repository.owner.login`/`organization.login` while write target is resolved from `repository.full_name` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp` (and thus which `webhook_secret`) validates the HMAC signature using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. However, the actual entity that webhook handlers act on is computed independently by `Shipit::Webhooks::Handlers::Handler#repository_name`, which reads `payload.dig('repository','full_name')`. Nothing ties these two fields together, so the org whose secret authenticates the request is not necessarily the org whose repository/stack is mutated.

### Finding Description
`verify_signature` in [1](#0-0)  picks the `Shipit.github(organization: repository_owner)` app config to check `X-Hub-Signature`, where `repository_owner` is derived at [2](#0-1) .

Every concrete handler, however, resolves the target repository/stack independently via `repository_name`, which reads a *different* JSON key (`repository.full_name`) from the same attacker-supplied payload: [3](#0-2) .

In a legitimate GitHub webhook, `repository.owner.login` and `repository.full_name`'s org segment are always consistent because GitHub generates both. But Shipit's multi-org support (`config/secrets.yml` supports multiple orgs, each with its own independently-configured `webhook_secret`, e.g. [4](#0-3) ) means the *secret owner* picks their own `webhook_secret` value when they create their GitHub App. Any organization admin who has legitimately registered their own org+App in Shipit knows their own `webhook_secret`. That knowledge is enough to author a raw HTTP POST to `/github/webhooks` with:
- `repository.owner.login` (or `organization.login`) = their own org (so `verify_signature` authenticates against their known secret), and
- `repository.full_name` = a *different*, victim organization's `owner/repo` (so the handler dispatches against the victim's Stack/Commit records).

`StatusHandler` demonstrates concrete impact: it looks up `Commit.where(sha: params.sha)` globally (not scoped to the authenticated org) and writes a status [5](#0-4) , and `Commit#create_status_from_github!` feeds directly into `deployable?`/status-gate logic used to decide whether a commit can be shipped [6](#0-5) [7](#0-6) . `PushHandler` similarly resolves `stacks` purely from `repository.full_name` and enqueues a resync job for any matching stack, regardless of which org authenticated the request [8](#0-7) .

This breaks the binding: `organization authenticated by signature == organization/repository the handler writes to`.

### Impact Explanation
An attacker who legitimately controls one organization onboarded to a shared Shipit instance can forge webhook events (signed with their own known secret) that appear, to the handler layer, to originate from a different organization's repository. This can be used to inject a fabricated "success" CI status onto a specific commit SHA in a victim stack they don't own, potentially satisfying `deployable?`/status-based deploy gating and enabling continuous-delivery auto-merge/deploy logic (`schedule_continuous_delivery`) to fire for a commit that never actually passed CI in the victim's real pipeline — an unauthorized deploy vector. This qualifies under High: "escalation ... or an unauthorized deploy" territory, contingent on continuous deployment being enabled for the targeted stack.

### Likelihood Explanation
Requires the attacker to be a legitimate, onboarded org/app owner on the same multi-tenant Shipit instance (they must know their own `webhook_secret`), and requires the victim stack to exist on the same instance with a matching commit SHA already known to the attacker (e.g., a public commit). This is a real but narrower trust boundary than an anonymous attacker; it does not require compromising the victim's or Shipit's own GitHub App credentials.

### Recommendation
Cross-validate that `repository.owner.login` (used for signature-key selection) matches the organization segment of `repository.full_name` before dispatching to any handler, or better, derive both the authentication key and the dispatch target from the same single field (`repository.full_name`'s owner segment), rejecting the request if they diverge. Additionally, scope `StatusHandler`'s `Commit.where(sha:)` lookup by the authenticated repository/stack rather than a global SHA search.

### Proof of Concept
1. Attacker legitimately registers `attacker-org` on the shared Shipit instance with `webhook_secret = S`.
2. Attacker knows a commit `sha` belonging to `victim-org/victim-repo`, a stack hosted on the same Shipit instance.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` over a crafted `status` event body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully (attacker used their own real secret) — see [9](#0-8) .
5. `StatusHandler#process` then looks up `Commit.where(sha: params.sha)` (not filtered by `attacker-org`) — [5](#0-4)  — and writes a forged "success" status to the victim's commit, potentially unblocking deploy gating for `victim-org/victim-repo`.
