### Title
`AsPerson` transaction extension permits replay of a superseded personal-alias/identity proof within the mortality tolerance window - ([File: substrate/frame/people/src/extension.rs])

### Summary
`pallet-people`'s `AsPerson` transaction extension authenticates unsigned (`RawOrigin::None`) extrinsics that link an account to a personal alias (`set_alias_account`) or personal identity (`set_personal_id_account`) using a one-time cryptographic proof/signature plus a `call_valid_at` block number and a fixed `account_setup_time_tolerance` window. The extension's own doc comments admit: *"Replay is only protected against resetting the same account during the tolerance period... If 2 transactions that set 2 different accounts are sent for an overlapping validity period, then those 2 transactions can be replayed indefinitely for the duration of the overlapping period."* This mirrors the Filament MFA flaw exactly: a previously accepted one-time authentication artifact (there: a TOTP code; here: a signed proof binding `account` to an alias/identity) remains fully replayable and can override state set by a *newer*, already-accepted proof, for as long as the acceptance window is open.

### Finding Description
In `substrate/frame/people/src/extension.rs`, `AsPersonInfo::AsPersonalAliasWithProof` and `AsPersonInfo::AsPersonalIdentityWithProof` are validated in `AsPerson::validate` (lines 191-292): [1](#0-0) 

The only anti-replay check is:
```
if AccountToAlias::<T>::get(account).is_some_and(|stored_rev_ca| stored_rev_ca == rev_ca) {
    return Err(InvalidTransaction::Stale.into());
}
```
i.e. the transaction is rejected *only* if the mapping for `account` already equals exactly the value this proof would set. It does **not** check whether the on-chain state has since been advanced to a *different* value by a more recent transaction. The same pattern (checking `record.account == *account`) exists for `AsPersonalIdentityWithProof`: [2](#0-1) 

Both checks are bounded only by the `call_valid_at` + `account_setup_time_tolerance` window: [3](#0-2) 

Because the tolerance window is symmetric and shared across any two transactions whose `call_valid_at` values overlap, a proof for account `A` issued at block `N` and a distinct proof for account `B` issued at block `N+1` are *both* valid (not stale) for the entire overlap of their windows. The pallet's own test suite explicitly demonstrates this as intended/known behavior, not merely a hypothetical: [4](#0-3) [5](#0-4) 

These tests show: user sets account to `10` (tx1), then to `11` (tx2, the "newer code"), and then **tx1 (the older, superseded proof) is successfully replayed**, resetting the mapping back to `10` — exactly the "older code accepted after a newer code" bug class from the Filament advisory.

The comment in `AsPersonInfo` at lines 48-52/58-62 is a self-acknowledged design limitation of the pallet: [6](#0-5) 

### Impact Explanation
`set_alias_account` / `set_personal_id_account` bind an on-chain `AccountId` to a privacy-preserving personal alias or personal identity, which other pallets use to authorize actions "as a person" (see pallet doc at lines 49-56 of `lib.rs`). Both signed extrinsics (containing the proof/signature) are broadcast in cleartext and become permanently visible on-chain history and in the transaction pool/gossip. Any observer (no privileged role, no stolen keys — the "attacker" only needs to have seen a previously broadcast, otherwise-expired-looking transaction) can resubmit that old, superseded extrinsic verbatim as long as its `call_valid_at + account_setup_time_tolerance` window has not fully elapsed and as long as it doesn't happen to equal the *current* stored value. This lets a third party revert the account binding to a stale value chosen by an earlier (still-in-window) transaction, effectively hijacking which `AccountId` is currently authorized to act as that personal alias/identity for the remainder of the overlapping window — undermining the integrity guarantee that only the most-recently-authorized account is bound. Because these mappings gate authorization for downstream calls (`AsPersonalAliasWithAccount`/`AsPersonalIdentityWithAccount`, which just use a nonce once the account link is set), the practical impact is unauthorized account substitution for personhood-gated dispatch, matching CWE-294 (authentication bypass by capture-replay). Severity is bounded by the short, configurable tolerance window (analogous to the ~4-minute TOTP window in the report), so this is a Medium-severity integrity issue, not unbacked issuance or fund theft.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the personhood-key holder to legitimately rotate their bound account twice within the tolerance window (a supported, presumably common operation for key/account migration), and (b) an observer capturing the earlier broadcast extrinsic. Since extrinsics are gossiped/publicly included in blocks, capturing an "old" proof requires no privileged access — only network/chain observation, which is explicitly permitted under the attacker model (no stolen keys, no privileged role required). The tolerance window is a runtime-configurable constant (`account_setup_time_tolerance`), so the exposure window size depends on chain configuration, but the vulnerability exists for any nonzero tolerance greater than the time needed to observe and resubmit a transaction.

### Recommendation
Replace the "does the target account already equal this proof's account" staleness check with a check that binds acceptance to a monotonically increasing value (e.g., require `call_valid_at` to be strictly greater than the `call_valid_at` of whatever proof most recently set the current mapping, and persist that value on-chain), so that once a *newer* proof (by `call_valid_at`) has been accepted, all older proofs for the same signer/proof-subject become permanently stale regardless of the tolerance window overlap — mirroring how `CheckNonce` prevents replay of superseded nonces (`substrate/frame/system/src/extensions/check_nonce.rs`) rather than relying purely on a sliding time window.

### Proof of Concept
The existing pallet test suite already constitutes a working, unmocked reproduction of the flaw through the real `AsPerson` extension boundary (not a mock of authority/proof acceptance — it uses the real `Simple` VRF/ring-proof and real `exec_tx` extrinsic dispatch path):
- `substrate/frame/people/src/tests.rs::replay_protection_for_identity` (lines 2833-2904): tx1 sets account `10`, tx2 sets account `11`, then tx1 is replayed and `assert_ok!` succeeds, reverting the mapping to `10`, only becoming `Stale` after the tolerance window fully elapses.
- `substrate/frame/people/src/tests.rs::replay_protection_for_alias` (lines 2905-2991): identical pattern for `set_alias_account`. [7](#0-6) [8](#0-7) 

These tests demonstrably pass today (they are asserting the vulnerable behavior with `assert_ok!`, not asserting rejection), confirming the flaw is real and reachable via the production `AsPerson`/`CheckNonce`-adjacent extension pipeline with no privileged prerequisites — the same class of "newer accepted code doesn't invalidate an older, still-in-window code" flaw described in the Filament advisory. I was not able to execute a live node/integration-test run in this environment; the evidence above is the existing first-party unit test in the repository showing `assert_ok!` on the replayed, superseded transaction, which is the closest available confirmation without live execution.
