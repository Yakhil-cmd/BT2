## Title
Non-constant-time string comparison in `hash` authentifier validation enables timing side-channel on secret preimage - (File: definition.js)

### Summary
The `hash` authentifier type in `Definition.validateAuthentifiers` verifies a secret preimage posted in a unit's authentifiers against the SHA-256 digest committed in the address definition using JavaScript's `===` operator on strings, which short-circuits on the first mismatched byte. This is the same bug class as CVE-2021-38153 (Apache Kafka using `Arrays.equals` instead of a constant-time compare to validate a password/key), applied here to a secret value that gates spending authority from an ocore address.

### Finding Description
An oscript/AA-capable address can be defined with a `['hash', {algo:'sha256', hash:'<base64 digest>'}]` component, requiring whoever spends from that address to reveal a preimage matching the committed digest as an authentifier. When a unit is validated, `Definition.validateAuthentifiers` evaluates this component with: [1](#0-0) 

The comparison `args.hash === crypto.createHash("sha256")...digest("base64")` is a plain JavaScript strict-equality check on strings. V8's string comparison is not constant-time — for unequal-length or byte-differing strings it can return as soon as a difference is found, creating a timing side channel proportional to the number of matching leading bytes/characters of the base64-encoded digest.

Because this authentifier check gates control over funds/AA-triggering rights tied to the address (this is exactly the class of "address definitions and authentifiers, hashing" logic called out as in-scope), an attacker who can repeatedly submit candidate units/messages containing guessed preimages and measure validation response latency (e.g., through a node they control, or by observing propagation/response timing from a full node or light-wallet endpoint) could incrementally narrow down bytes of the digest-matching computation. This mirrors the Kafka CVE where password/key equality checks leaked timing information usable to accelerate brute-force recovery of a secret credential.

Note that unlike `sig`, which uses `ecdsaSig.verify` (a well-defined cryptographic verification routine), the `hash` case in `definition.js` line 763 is the only authentifier path using a raw, non-constant-time equality operator to validate secret material.

### Impact Explanation
If exploitable, an attacker could use timing information leaked during unit/authentifier validation to reduce the effective search space for the secret preimage protecting a hash-locked address (e.g., addresses using `['hash', ...]` conditions, common in hash-time-locked or atomic-swap-style contracts, or AA definitions that gate execution/fund release on knowledge of a secret). Recovering the preimage would let the attacker construct a valid authentifier and spend funds or trigger AA logic without authorization — i.e., concrete unauthorized spending / fund loss, which is an accepted impact category for this scan.

### Likelihood Explanation
Exploitation requires an attacker to have a way to repeatedly submit validation attempts and measure timing with enough precision to distinguish the byte-count of an early-exit `===` comparison over network jitter — a real-world constraint (this is CWE-203 / "Observable Discrepancy", the same class explicitly rated Medium severity for the analogous Kafka CVE). It does not require a malicious peer/hub/node — a single unprivileged unit-poster interacting with any node that validates the unit and returns fast rejection/acceptance signals is sufficient in principle to begin collecting timing samples. This matches the CVSS vector of the original advisory (network, high attack complexity, no privileges, no user interaction).

### Recommendation
Replace the direct `===` comparison in the `hash` authentifier branch with a constant-time comparison, e.g. using `crypto.timingSafeEqual` on fixed-length buffers (decoding both the committed `args.hash` and the freshly computed digest to buffers of equal length before comparing, and rejecting up front if lengths differ without leaking that fact via early return timing differences).

### Proof of Concept
1. Define an address using `['hash', {algo:'sha256', hash: H}]` where `H = sha256(secret)`.
2. An attacker without knowledge of `secret` submits many units/authentifier validation attempts with different guessed preimages as `assocAuthentifiers[path]`.
3. For each attempt, the attacker measures the time taken by `crypto.createHash("sha256").update(guess).digest("base64") === args.hash` inside `definition.js`'s `hash` case.
4. Because `===` compares byte-by-byte and can exit early on mismatch, statistically averaging many timing samples per guessed prefix allows an attacker to infer which prefixes of the base64 digest match, progressively refining guesses far faster than brute-forcing the full digest space — eventually recovering (or narrowing down) `secret` to forge a valid authentifier and spend from the address.
