Based on the code traced, this is a valid, confirmed vulnerability.

### Title
Cross-repository CI-enable via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely `Commit.where(sha: params.sha)` with no repository/stack scoping, even though the base `Handler` class exposes a `stacks` helper precisely for this purpose. Any commit row on any tenant's stack sharing the sha named in an attacker-controlled, self-signed webhook gets a new `Status` created, whose `after_create` callback unconditionally calls `commit.stack.enable_ci!` — mutating a victim stack's CI configuration without ever checking that the requesting webhook's repository owns that stack.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: `payload.dig('repository', 'full_name') == commit.stack.repository.full_name` for every `commit` touched by the handler. This should always hold but does not.

Trace:
- `Shipit::Webhooks::Handlers::Handler#initialize` parses and validates `params` via `ExplicitParameters` and provides a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, intended to bind webhook processing to the repository that signed the request.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) ignores this scoping entirely: [1](#0-0) . It queries `Commit.where(sha: params.sha)` globally, across every stack/repository in the installation.
- For each matching `Commit`, it calls `commit.create_status_from_github!(params)` (`app/models/shipit/commit.rb:165-169`), which calls `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/status.rb:24-33`), creating a `Status` row tied to `commit`'s actual `stack_id` — the victim stack's id, not the attacker's.
- `Status` has `after_create :enable_ci_on_stack` (`app/models/shipit/status.rb:18,38-40`): [2](#0-1) . This calls `commit.stack.enable_ci!` on whatever stack owns the colliding commit, regardless of which repository's webhook secret/signature validated the request.

Existing guards do not prevent this: the webhook controller's signature verification only proves the payload was sent by the repository named in `payload['repository']['full_name']` — it says nothing about which `Commit`/`Stack` rows in the database happen to share that sha. `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not its binding to a repository. The `stacks` scoping helper exists in the base `Handler` class specifically to prevent this class of bug, but `StatusHandler` never calls it, unlike (implicitly) other handlers that scope through `stacks`.

Attacker exploit flow: attacker owns/controls a GitHub repository (or any repo they can push to) and can send a legitimately-signed `status` webhook for it. If a `Commit` row with the same sha exists under a victim stack (a realistic scenario for forked repositories, shared upstream history, monorepo forks, or any git history the victim stack has ingested that overlaps with the attacker's repository — SHA is git content-addressed and identical across clones/forks), the attacker's signed status webhook creates a `Status` on the victim's `Commit`, flipping `commit.stack.enable_ci!` on the victim stack.

### Impact Explanation
The attacker forces a write (`ignore_ci` becoming enabled, i.e., `Stack#enable_ci!`) on a victim's stack configuration, using a webhook payload that authenticated only for the attacker's own repository. This is a cross-tenant stack configuration mutation triggered by a payload that did not authenticate for the victim's repository — matching the Critical category "a payload for one repository mutating another's stack." It is repeatable against any stack that has ingested a commit with a sha also reachable/known to the attacker (e.g., via forks of the same upstream), and requires no privileges beyond sending an unauthenticated `POST /webhooks` request signed with the attacker's own repo webhook secret (which the attacker controls for their own GitHub repo).

### Likelihood Explanation
Preconditions: the victim `Stack` must already have a `Commit` row with a sha the attacker can name in a webhook they can validly sign (i.e., a commit that exists both in the attacker's own repository and has been synced into the victim's stack's commit history — realistic for forks/shared history scenarios, and Shipit routinely imports commits by sha from GitHub pushes/PRs). No Shipit session, API token, or GitHub App secret is needed; the attacker only needs control of a GitHub repository to emit a validly-signed status webhook for it. This is a low-cost, repeatable attack limited only by sha collision availability, which is a normal circumstance (forks, cherry-picks, shared base commits) rather than requiring a cryptographic SHA-1 collision.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the base `Handler#stacks` helper, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures only commits belonging to stacks tied to the repository named (and cryptographically verified) in the webhook payload can have statuses created against them.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, pattern already used by existing handler tests, no live GitHub calls required):
1. Create `attacker_repo` (`Shipit::Repository`, owner/name `attacker/attacker-repo`) with no associated stack, or a stack unrelated to the victim.
2. Create `victim_stack` (`Shipit::Stack`) with `ignore_ci: false` and a `Commit` with `sha: 'deadbeef...'` belonging to `victim_stack`.
3. Build a `payload` hash mimicking a GitHub status webhook: `{ 'repository' => { 'full_name' => 'attacker/attacker-repo' }, 'sha' => 'deadbeef...', 'state' => 'success', 'context' => 'ci', ... }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the binding was violated:
   - Before: `victim_stack.ignore_ci` == `false`, and `payload['repository']['full_name']` (`'attacker/attacker-repo'`) != `victim_stack.repository.full_name`.
   - After: `assert victim_stack.reload.ignore_ci` is now `true` (or the CI-enabled flag flips), despite the payload naming and being signed for `attacker/attacker-repo`, proving `commit.stack.enable_ci!` fired on a stack the webhook never authenticated for.
