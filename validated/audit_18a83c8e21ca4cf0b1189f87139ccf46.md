### Title
Attacker-controlled `aa` field in a submitted joint lets an unprivileged unit poster force the internal-only AA-validation path and crash the node via an uncaught `throw Error` - (File: validation.js)

### Summary
`validation.validate(objJoint, callbacks)` decides whether to treat a unit as an internally-generated Autonomous-Agent (AA) response unit purely by checking `objJoint.aa` on the *input* object, before that object is otherwise sanitized. Any unit-posting peer can include an `aa: true` (and `aa_mci`) property in a joint sent over the wire, forcing `validate()` down the `bAA` code path that is meant to be used exclusively by `aa_composer.js` for internally composed AA trigger/response units. That path performs far weaker checks and contains unconditional `throw Error(...)` statements reachable with attacker-controlled data, causing an uncaught exception that (per `network.js`'s global `uncaughtException` handler) deliberately crashes the whole node process — a Denial-of-Service analogous to the "malformed packet crashes the process" fastify/websocket bug.

### Finding Description
`validate()` sets the internal flag `bAA` directly from the untrusted `objJoint.aa` property before any of the joint's fields are otherwise checked for legitimacy: [1](#0-0) 

Because the `aa`/`aa_mci` properties are deleted right after being read (`delete objJoint.aa; delete objJoint.aa_mci;`), the subsequent `hasFieldsExcept(objJoint, [...])` checks used to reject "unknown fields in unit-joint" never see them, so a crafted joint of the form:

```json
{ "unit": { ... }, "aa": true, "aa_mci": 123456 }
```
passes the joint-shape checks unchanged. Nothing in `onWebsocketMessage`/`handleJustsaying`/`handleRequest` in `network.js` strips the `aa` property from an incoming joint before it reaches `validation.validate()` — the joint object received directly off the wire (`JSON.parse(message)` in `onWebsocketMessage`) is forwarded essentially unchanged to `handleJoint` → `validation.validate`: [2](#0-1) 

Once `bAA` is true, `validateAuthor()` takes an entirely different branch intended only for internally generated AA response units, which:
* skips the ordinary authentifier/signature checks (`if (!objValidationState.bAA) { ... }`)
* unconditionally throws if the author object has any field other than `address`: [3](#0-2) 

An attacker fully controls `objAuthor` in the posted unit's `authors` array (e.g. `{"address": "...", "authentifiers": {...}}`), so `hasFieldsExcept(objAuthor, ["address"])` on this attacker payload is trivially true, causing `throw Error("unknown fields in AA author")`. This throw happens synchronously inside an `async.eachSeries`/`async.series` callback chain invoked from `validate()`, which is *not* wrapped in a try/catch anywhere in the call chain from `onWebsocketMessage` down through `handleJoint`. The exception therefore propagates all the way to Node's `uncaughtException` handler, which by design re-throws to crash the process: [4](#0-3) 

This mirrors the fastify/websocket advisory pattern exactly: an untrusted, attacker-supplied "packet" (here, a joint/unit) reaches a code path with an unguarded `throw`, and the lack of a catching boundary converts a single bad input from one peer into a full process crash.

### Impact Explanation
Any node (full node or hub) that accepts unit submissions over its WebSocket interface (e.g. from a wallet posting a new unit, or a peer relaying a joint) can be crashed by a single crafted joint containing `aa: true` and a mismatched author object. Because `ocore`'s own crash policy intentionally kills the process on any uncaught exception (`throw err; // crash the process to avoid ending up in an inconsistent state`), this turns an application-level validation bug into guaranteed process termination. For a hub or witness/full node, a repeatedly-crashing node cannot validate/relay/confirm new units, matching the "network unable to confirm new units" impact class — a High severity availability issue reachable from a completely unprivileged unit poster, no special network position or credentials required.

### Likelihood Explanation
Likelihood is high: constructing the payload requires no cryptographic material, no valid signatures, and no privileged network position — merely adding two extra top-level fields (`aa`, `aa_mci`) to an otherwise-arbitrary unit JSON and submitting it as a normal `joint`/`request` message. The vulnerable code path is reached very early in `validate()` before any authentication of the author is performed, so no valid address ownership or private key is needed to trigger the crash.

### Recommendation
- Never trust `objJoint.aa` / `objJoint.aa_mci` when they originate from the network. Require validation entry points that accept external joints (`network.js` message handlers, `light.js`, etc.) to explicitly strip/reject an `aa` field on any inbound joint before calling `validation.validate`, or better, pass the "is this an internal AA joint" flag as a separate trusted parameter to `validate()` rather than reading it off the attacker-controlled object.
- Convert the unconditional `throw Error(...)` invariant checks inside `bAA`-specific code (e.g. `validateAuthor`'s "unknown fields in AA author", and the various `throw Error(...)` calls in `aa_composer.js`'s `validateAndSaveUnit`) into calls to `callback(err)`/`ifUnitError`, or wrap the whole `validate()` call chain in a try/catch that funnels unexpected internal errors to `ifTransientError`/`ifUnitError` instead of letting them become uncaught exceptions.
- As defense in depth, wrap `onWebsocketMessage`'s dispatch to `handleJustsaying`/`handleRequest` (and ultimately `validate()`) with a try/catch that logs and drops the offending message instead of relying solely on the global `uncaughtException` handler to crash the process.

### Proof of Concept
1. Connect to a target node as a normal peer/wallet and construct a unit with a syntactically valid but otherwise arbitrary payload, e.g. a single-author unit with `authors: [{ address: "<VALID_ADDRESS>", authentifiers: { "r": "sig" } }]` (no valid definition/signature needed since the bAA path skips signature checking before hitting the throw).
2. Wrap it in a joint object with the extra fields:
   ```json
   ["justsaying", {"subject":"joint","body":{"unit": { ...as above... }, "aa": true, "aa_mci": 1}}]
   ```
   (or via the `post_joint` request handler used for submitted units, whichever inbound joint entry point is exposed).
3. Send this over the WebSocket connection to the target node.
4. `validation.validate()` sets `bAA = true` from `objJoint.aa`, deletes the `aa`/`aa_mci` markers so joint-shape checks pass, and later calls `validateAuthor()`, which executes `if (objValidationState.bAA && hasFieldsExcept(objAuthor, ["address"])) throw Error("unknown fields in AA author");`. Since the crafted author object contains `authentifiers`, the throw fires.
5. The exception is uncaught anywhere in the call chain and reaches `process.on('uncaughtException', ...)` in `network.js`, which logs it and re-throws, terminating the node process — a one-shot remote crash from an unauthenticated unit submission.

Note: I could not fully trace every inbound joint-handling entry point (e.g., `light.js`'s `light/get_history`/post-joint variants) within the available context to confirm whether some of them pre-sanitize the `aa` field before calling `validation.validate`; the primary `network.js` `onWebsocketMessage` → `handleJustsaying`/`handleRequest` → `handleJoint` → `validation.validate` path shown above does not perform such sanitization based on the code reviewed.
