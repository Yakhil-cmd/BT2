### Title
Missing webhook secret configuration for an organization allows unauthenticated forged `membership` events to grant Team membership - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`GitHubApp#verify_webhook_signature` returns `true unless webhook_secret`, meaning any organization configured in `secrets.github` without a `webhook_secret` accepts webhooks with no HMAC validation at all. Combined with `WebhooksController#verify_signature` looking up the `GitHubApp` purely from the attacker-controlled `repository_owner`/`organization.login` field in the JSON body, an unauthenticated internet attacker can POST a forged `membership` event naming any such organization and cause `MembershipHandler#process` to create/find a `Team` and add an arbitrary user as a member.

### Finding Description
The binding that should hold is: `verified == (signature was produced with HMAC-SHA1 over request.raw_post using the organization's github_app.webhook_secret)`. Instead, in [1](#0-0)  when `@webhook_secret` is nil/blank (`@config[:webhook_secret].presence` at [2](#0-1) ), `verify_webhook_signature` unconditionally returns `true`, breaking the equality for any org with no configured secret — `verified` becomes `true` regardless of the `X-Hub-Signature` header content.

The controller resolves which `GitHubApp` (and thus which secret) to use straight from the untrusted payload: `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` at [3](#0-2) , then `Shipit.github(organization: repository_owner)` is used to verify at [4](#0-3) . If any organization entry in `secrets.github` (e.g., a legacy/misconfigured/newly added org) has no `webhook_secret`, an attacker just needs to name that organization in the payload to sail through `verify_signature` with a bogus `X-Hub-Signature`.

Once past verification, `create` dispatches to registered handlers for `X-Github-Event: membership` at [5](#0-4) , invoking `MembershipHandler#process`, which does `Team.find_or_create_by!(github_id: params.team.id)` and `team.add_member(member)` at [6](#0-5) , entirely driven by attacker-supplied JSON fields (`team.id`, `team.name`, `team.slug`, `team.url`, `organization.login`, `member.login`, `action`). No other guard (no `force_github_authentication`, no `User#authorized?`, no signature re-check) exists in this path.

The attacker's request: `POST /webhooks` with headers `X-Github-Event: membership`, `X-Hub-Signature: sha1=deadbeef` (arbitrary), and JSON body `{"action":"added","team":{"id":<guessed_or_known_id>,"name":"x","slug":"x","url":"x"},"organization":{"login":"<org-without-secret>"},"member":{"login":"attacker"}}`.

### Impact Explanation
This is an authentication bypass into Shipit's authorization model: `Team` records gate access via `Shipit.github_teams` and related authorization checks elsewhere in the app, so being able to silently add an arbitrary GitHub login as a member of any guessed `Team.github_id` is a direct escalation vector. It is repeatable against any team ID for any organization lacking a `webhook_secret`, and since `secrets.github` can define multiple orgs, a single misconfigured/no-secret entry compromises team-membership integrity engine-wide, not just for one repository. This matches the Critical category: authentication bypass (forged webhook accepted).

### Likelihood Explanation
The only precondition is that at least one organization in `secrets.github` has `webhook_secret` unset — a plausible misconfiguration (e.g., a newly onboarded org, an internal/test org, or an app upgraded from a config style that didn't set this key). No Shipit credentials, GitHub App keys, or repository relationship are required by the attacker; the request is a single unauthenticated HTTP POST. Given this, exploitation cost is trivial and fully repeatable.

### Recommendation
Do not treat a missing `webhook_secret` as "verification passes"; instead treat it as a fatal configuration error (raise/log and reject the webhook with 422, or refuse to boot without a configured secret for any org with webhook handling enabled) in `GitHubApp#verify_webhook_signature`. Additionally, consider deriving the target `GitHubApp` from a source not solely controlled by the payload body, or require signature validation success unconditionally regardless of `webhook_secret` presence.

### Proof of Concept
```ruby
test "membership webhook is accepted and creates membership when org has no webhook_secret" do
  Shipit.github(organization: 'no-secret-org').stubs(:webhook_secret).returns(nil)

  payload = {
    action: 'added',
    team: { id: 4242, name: 'Test', slug: 'test', url: 'https://api.github.com/teams/4242' },
    organization: { login: 'no-secret-org' },
    member: { login: 'attacker' }
  }.to_json

  assert_difference -> { Shipit::Membership.count }, 1 do
    post shipit.github_webhooks_path,
      params: payload,
      headers: {
        'X-Github-Event' => 'membership',
        'X-Hub-Signature' => 'sha1=totally_bogus_signature',
        'Content-Type' => 'application/json'
      }
  end

  assert_response :ok
  team = Shipit::Team.find_by(github_id: 4242)
  assert team.members.exists?(login: 'attacker')
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
