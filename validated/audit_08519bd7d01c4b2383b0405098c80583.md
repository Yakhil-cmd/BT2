### Title
Cross-organization webhook forgery via signature/target binding mismatch in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read straight out of the untrusted JSON body (`repository.owner.login` or `organization.login`). Every webhook handler, however, resolves the repository/stack to act on from a *different* field of that same untrusted body: `repository.full_name` (via `Shipit::Webhooks::Handlers::Handler#repository_name`). The signature check therefore authenticates "the organization named in one field of the payload," while the mutation performed by the handler operates on "the repository named in another field of the same payload." Nothing ties these two values together.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is only used to pick *which organization's configured secret* validates the signature, using `Shipit.github(organization: ...)` → `GithubApp#verify_webhook_signature` [3](#0-2) .

Once verification passes, `create` hands the entire raw `params` (the whole untrusted JSON body) to every registered handler for the event: [4](#0-3) 

Every handler resolves the target repository/stack from a *different* key in the same body — `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

For example `PushHandler` acts on whatever stacks match `repository.full_name` and triggers a GitHub sync: [6](#0-5) 

The binding that should hold is: **organization that authenticated the signature == organization that owns the repository acted upon**. Nothing enforces `repository.owner.login == repository.full_name.split('/').first`. An attacker who legitimately administers a GitHub organization/repo that Shipit already tracks (call it Org A — this can be any low-value org with its own Shipit stack, requiring no privilege inside Shipit itself) knows Org A's `webhook_secret` (they configured it themselves when wiring up the GitHub webhook, per the standard Shipit setup flow documented in README's "Registering webhooks" section [7](#0-6) ). That attacker can POST directly to Shipit's public `/webhooks` endpoint (unauthenticated, only signature-gated) with a forged raw body where:
- `repository.owner.login` = `"OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the attacker signs the body correctly with the secret they legitimately know), and
- `repository.full_name` = `"OrgB/high-value-repo"` (a completely unrelated organization/repo they have no rights to, but which is registered as a Shipit stack).

The signature check passes (it is a genuine HMAC over the attacker's own crafted body, using Org A's real secret), yet every handler dispatches against Org B's repository/stack because they only look at `repository.full_name`.

### Impact Explanation
This breaks the trust boundary between organizations onboarded to a shared Shipit instance. Concretely, using the built-in handlers:
- `PushHandler` can force `stack.sync_github(expected_head_sha: ...)` on a victim org's stack whenever the attacker controls the branch name, potentially disrupting deploy state tracking for a repository the attacker doesn't own.
- The `status`/`check_suite` family of handlers write commit `Status`/check-run records (as shown in `test/controllers/webhooks_controller_test.rb` `:state create a Status for the specific commit`), letting the attacker inject fake green CI statuses onto a victim's commits — this is exactly the kind of CI-gate bypass that can lead to an **unauthorized deploy**, since Shipit's deploy safety gates (`required_statuses`, `blocking_statuses`) rely on these `Status` records being trustworthy.
- `MembershipHandler` creates/removes `Team`/`Membership` records tied to whatever `team`/`organization` fields the attacker supplies in the forged body, which can affect `Shipit.github_teams` authorization used by `User#authorized?` — a direct escalation vector.

Both of these map to the in-scope High/Critical impacts: "escalation into `Shipit.github_teams` authorization" and "an unauthorized deploy."

### Likelihood Explanation
Likelihood is high for any Shipit deployment onboarding more than one GitHub organization (a documented, supported configuration — multiple `github` configs keyed by organization, as reflected in `Shipit.github(organization:)`). Any legitimate admin of *any one* onboarded organization can mount this attack against *every other* onboarded organization, without needing any Shipit-side privilege, GitHub App private key, or session — only knowledge of a secret they set themselves for their own org's webhook.

### Recommendation
In `WebhooksController#verify_signature`/`create`, and in `Shipit::Webhooks::Handlers::Handler`, require that the organization used to select/verify the webhook secret matches the owner of the repository the handler is about to act on (e.g., derive `repository_name`'s owner and assert it equals `repository_owner` before dispatching, rejecting mismatched payloads with 422). Alternatively, verify the signature using a secret bound to the specific `repository.full_name` rather than a loosely related `repository_owner`/`organization.login` field.

### Proof of Concept
1. Attacker legitimately administers `OrgA` on GitHub and has configured (or knows) the Shipit `webhook_secret` for `OrgA` (set during normal onboarding).
2. Attacker crafts a raw JSON body for a `push` event with `"repository": {"full_name": "OrgB/high-value-repo", "owner": {"login": "OrgA"}}`, and other required push fields (`ref`, `after`).
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the attacker's own valid signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/high-value-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on Org B's stack — despite the attacker having no access to Org B whatsoever.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
