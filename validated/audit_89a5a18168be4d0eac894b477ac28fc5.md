### Title
Unauthenticated `sender` in `StackStxOp`/`TransferStxOp`/`DelegateStxOp` allows attacker to lock, transfer, or delegate any principal's STX without their signature - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp.output` (renamed `sender` for the follow-up op) is populated purely from the address of the first Bitcoin output of the `PreStx` transaction, which the transaction's creator can set to *any* address, including a victim's. The follow-up `StackStxOp`/`TransferStxOp`/`DelegateStxOp` is only required to spend `vout(1)` of that same `PreStx` tx — a UTXO the attacker fully controls since they created it — with no requirement that the signer of that input controls the key behind the declared `sender` address.

### Finding Description
The broken equality: `sender_used_for_STX_mutation == principal_who_cryptographically_authorized_the_mutation` is violated. In practice `sender_used_for_STX_mutation = pre_stx.output`, an arbitrary Bitcoin-output address chosen by whoever built the `PreStx` transaction [1](#0-0) , while `principal_who_cryptographically_authorized_the_mutation` is nothing — no code path checks the input signer of the follow-up transaction against `sender`.

The dispatch logic simply looks up the `PreStxOp` referenced by the follow-up transaction's first input (which must spend `vout=1`) and passes `pre_stx.output` straight through as `sender` to `StackStxOp::from_tx`, `TransferStxOp::from_tx`, and `DelegateStxOp::from_tx`: [2](#0-1) .

None of `StackStxOp::parse_from_tx` [3](#0-2) , `TransferStxOp::parse_from_tx` [4](#0-3) , or `DelegateStxOp::parse_from_tx` compare the passed-in `sender` to any public key recovered from the transaction's own inputs (unlike `VoteForAggregateKeyOp::get_sender_pubkey`, which does recover and use a signer pubkey [5](#0-4) , but that pubkey is never cross-checked against `pre_stx.output` for the stacking/transfer/delegate ops either).

Downstream, `sender` is used directly as the acting Stacks principal with no Stacks-native signature/nonce check:
- `process_stacking_ops` calls `tx.run_contract_call(&sender.clone().into(), None, ..., "stack-stx", &args, ...)`, i.e. it invokes the PoX contract's `stack-stx` as if `sender` (the victim) were `tx-sender` [6](#0-5) .
- `process_transfer_ops` calls `tx.run_stx_transfer(&sender.clone().into(), &recipient.clone().into(), transfered_ustx, ...)`, directly moving STX out of `sender`'s account to an attacker-chosen `recipient` [7](#0-6) .

From there, `handle_lockup_pox_v5`/`pox_lock_v5` in `pox-locking` only validate balance sufficiency and lock-state invariants on whatever principal is handed to them — they never re-derive or verify who actually authorized the call [8](#0-7) . There is no independent Stacks-chain-native signature reconciliation anywhere in this path.

Attacker's exact call: craft a `PreStx` Bitcoin transaction from the attacker's own UTXOs with `output[0].address = victim_addr` and `output[1]` paid to an address the attacker controls (e.g., a fresh change key). Then craft a second Bitcoin transaction spending `vout(1)` (signed with the attacker's own key) encoding a `TransferStxOp`/`StackStxOp`/`DelegateStxOp` payload. Once both transactions are mined and processed, `sender = victim_addr` is fed straight into `run_stx_transfer`/`stack-stx`/`delegate-stx`, moving or locking the victim's real STX balance with zero input from the victim.

Existing guards do not prevent this: `verify-not-prepare-phase`, `validate-no-reentrancy`/`signer-manager-call-active`, `check-pox-lock-period`, `verify-signer-key-grant`, and the `<=` guards inside `pox-locking` all operate on the *result* of a contract call whose `tx-sender` is already the spoofed victim address — none of them re-authenticate the caller.

### Impact Explanation
- `TransferStxOp`: direct theft of the victim's unlocked STX to an attacker-chosen recipient (Critical — theft of funds never authorized by their owner).
- `StackStxOp`: forced, unauthorized locking of the victim's STX for up to `POX_MAX_NUM_CYCLES` reward cycles, with PoX BTC rewards routed to an attacker-chosen `reward_addr` (Critical — unbacked yield diversion + freezing of victim funds for the lock duration).
- `DelegateStxOp`: forced delegation of the victim's future stacking rights/PoX rewards to an attacker-controlled `delegate_to` principal (High/Critical depending on subsequent commit).
- Repeatable: an attacker can repeat this against any address with a nonzero STX balance, at the cost of only Bitcoin transaction fees plus dust, for as many victims as they choose.

### Likelihood Explanation
No privileged role is required: the attacker only needs their own BTC UTXOs and the ability to broadcast two ordinary Bitcoin transactions with `OP_RETURN` payloads, which stacks-core parses without validating that `sender`/`output` is tied to any signature in the transaction chain. The only "cost" is the dust amount paid to the fabricated `output[0]` (paid to the victim, not requiring the victim's cooperation) and standard BTC fees. This is feasible today with existing tooling (`bitcoin_regtest_controller.rs` shows the exact wire format used by legitimate wallets, which an attacker can replicate) [9](#0-8) .

### Recommendation
Require that the address recovered from `PreStxOp.output` be cryptographically tied to the entity that signs the follow-up transaction's input spending `vout(1)` — e.g., recover the pubkey/script that signs the follow-up transaction's input and require it hashes to the same value as `pre_stx.output`/`sender` before accepting `StackStxOp`, `TransferStxOp`, or `DelegateStxOp`. Alternatively, require that the `PreStxOp`'s own funding input(s) be signed by the same key as `output[0]`, closing the gap where an attacker can name an arbitrary victim as `output` while retaining full control of both transactions in the chain.

### Proof of Concept
Rust integration test plan (using the harness patterns in `stacks-node/src/tests/epoch_21.rs` and `neon_integrations.rs`):
1. Fund only `victim_addr` on Stacks with STX (e.g., via genesis allocation), and ensure `attacker` has BTC UTXOs but no relationship to `victim_addr`'s keys.
2. Attacker (not victim) submits `BlockstackOperationType::PreStx(PreStxOp { output: victim_addr, ... })` using `attacker`'s own `BurnchainOpSigner` and BTC funds, as in `submit_manual`.
3. Attacker submits a `TransferStxOp { sender: victim_addr, recipient: attacker_addr, transfered_ustx: N, .. }` spending `vout(1)` of the prior tx, signed only with attacker's key (`BurnchainOpSigner::new(attacker_sk)`), mirroring `epoch_21.rs` lines 933–972 but with sender/recipient swapped to a non-consenting victim.
4. Mine blocks until the op is processed; assert `get_balance(http_origin, &victim_addr) == original_victim_balance - N` and `get_balance(http_origin, &attacker_addr) == original_attacker_balance + N`, with the applied `StacksTransactionReceipt` containing `TransactionOrigin::Burn(BlockstackOperationType::TransferStx(..))` and no signature field from `victim_addr` anywhere in the receipt or the underlying Bitcoin transactions.
5. Repeat steps 2–4 substituting `StackStxOp`/`DelegateStxOp`, asserting `(stx-account victim_addr)` shows `locked > 0`/`unlock-height > 0` (via `pox_lock_v5` in `pox-locking/src/pox_5.rs`) despite no Stacks transaction ever being signed by `victim_addr`.

        block_height: u64,
        block_hash: &BurnchainHeaderHash,
        epoch_id: StacksEpochId,
        tx: &BurnchainTransaction,
        sender: &StacksAddress,
        pox_sunset_ht: u64,
    ) -> Result<StackStxOp, op_error> {
        // can't be too careful...
        let num_outputs = tx.num_recipients();

        if tx.num_signers() == 0 {
            warn!(
                "Invalid tx: inputs: {}, outputs: {}",
                tx.num_signers(),
                num_outputs
            );
            return Err(op_error::InvalidInput);
        }

        if num_outputs == 0 {
            warn!(
                "Invalid tx: inputs: {}, outputs: {}",
                tx.num_signers(),
                num_outputs,
            );
            return Err(op_error::InvalidInput);
        }

        if tx.opcode() != Opcodes::StackStx as u8 {
            warn!("Invalid tx: invalid opcode {}", tx.opcode());
            return Err(op_error::InvalidInput);
        };

        let data = StackStxOp::parse_data(&tx.data()).ok_or_else(|| {
            warn!("Invalid tx data");
            op_error::ParseError
        })?;

        let outputs = tx.get_recipients();
        assert!(!outputs.is_empty());

        let first_output = outputs
            .get(0)
            .ok_or_else(|| {
                warn!("Invalid tx: no first output");
                op_error::InvalidInput
            })?
            .as_ref()
            .ok_or_else(|| {
                warn!("Invalid tx: failed to decode first output");
                op_error::InvalidInput
            })?;

        // coerce a hash mode for this address if need be, since we'll need it when we feed this
        // address into the .pox contract
        let reward_addr = first_output.address.clone().coerce_hash_mode();

        // check if we've reached PoX disable
        if PoxConstants::has_pox_sunset(epoch_id) && block_height >= pox_sunset_ht {
            debug!(
                "StackStxOp broadcasted after sunset. Ignoring. txid={}",
                tx.txid()
            );
            return Err(op_error::InvalidInput);
        }

        Ok(StackStxOp {
            sender: sender.clone(),
            reward_addr,
            stacked_ustx: data.stacked_ustx,
            num_cycles: data.num_cycles,
            signer_key: data.signer_key,
            max_amount: data.max_amount,
            auth_id: data.auth_id,
            txid: tx.txid(),
            vtxindex: tx.vtxindex(),
            block_height,
            burn_header_hash: block_hash.clone(),
        })
    }

    pub fn get_sender_pubkey(tx: &BurnchainTransaction) -> Result<Secp256k1PublicKey, op_error> {
        match tx {
            BurnchainTransaction::Bitcoin(ref btc) => match btc.inputs.first() {
                Some(BitcoinTxInput::Raw(input)) => {
                    let script_sig = Builder::from(input.scriptSig.clone()).into_script();
                    let structured_input = BitcoinTxInputStructured::from_bitcoin_p2pkh_script_sig(
                        &parse_script(&script_sig),
                        input.tx_ref.clone(),
                    )
                    .ok_or(op_error::InvalidInput)?;
                    structured_input
                        .keys
                        .first()
                        .cloned()
                        .ok_or(op_error::InvalidInput)
                }
                Some(BitcoinTxInput::Structured(input)) => {
                    input.keys.first().cloned().ok_or(op_error::InvalidInput)
                }
                _ => Err(op_error::InvalidInput),
            },
        }
    }

pub fn pox_lock_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    lock_amount: u128,
    unlock_burn_height: u64,
) -> Result<(), LockingError> {
    if unlock_burn_height == 0 {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }
    if lock_amount == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxAlreadyLocked);
    }
    if !snapshot.can_transfer(lock_amount)? {
        return Err(LockingError::PoxInsufficientBalance);
    }
    snapshot.lock_tokens_v5(lock_amount, unlock_burn_height)?;

    debug!(
        "PoX v5 lock applied";
        "pox_locked_ustx" => snapshot.balance().amount_locked(),
        "available_ustx" => snapshot.balance().amount_unlocked(),
        "unlock_burn_height" => unlock_burn_height,
        "account" => %principal,
    );

    snapshot.save()?;
    Ok(())
}
