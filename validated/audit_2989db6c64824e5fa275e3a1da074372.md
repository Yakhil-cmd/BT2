### Title
`WebhooksController#verify_signature` authenticates the sending organization but handlers (especially `StatusHandler`) write to commits/stacks with no matching repository check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The organization whose HMAC secret is used to authenticate an inbound GitHub webhook is not cryptographically or logically bound to the repository/commit the handler subsequently mutates. This is the same class of bug as the KeeperOracle report: a value that gates/keys one operation (which org's secret authorizes the request) is not carried through consistently to the operation that actually performs the write (which repository/commit gets updated), so the second target can diverge from what was "approved" by the first check.

### Finding Description
`WebhooksController#verify_signature` picks *which* GitHub App/organization config to validate the signature against using attacker-supplied JSON fields from the payload itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This only proves "the sender knows organization `repository_owner`'s webhook secret." It does not prove anything about the rest of the payload, in particular the `repository.full_name` field (owner/repo) that handlers use to identify *which* commit/stack to mutate: [2](#0-1) 

Most handlers at least re-derive the target repository from `repository.full_name` via `Repository.from_github_repo_name`, so a same-secret cross-org forgery would only let an attacker pick an arbitrary `full_name` at will (already a violation of "organization authenticated == repository written"). But `StatusHandler`, which is reachable from the same `create` action, goes further and doesn't scope by repository or stack at all: [3](#0-2) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

It matches purely by commit `sha` across the entire Shipit installation (all repositories/stacks), regardless of which organization/repository the payload claims to be from. `create_status_from_github!` writes a new `Status` and can flip a commit into `success?`, which feeds directly into deploy gating: [4](#0-3) [5](#0-4) 

### Impact Explanation
Anyone who legitimately controls a `webhook_secret` for one GitHub organization configured on a multi-org Shipit instance (e.g. an org admin able to view/rotate that org's webhook secret in GitHub's UI — an "unprivileged attacker" with respect to any *other* org/repo hosted on the same Shipit instance) can forge a signed `status` webhook whose signature is validated against their own org, while the payload's `sha` targets a commit belonging to a completely unrelated stack/repository. Because `StatusHandler` has zero repository scoping, this lets the attacker inject a fake `success` CI status onto any known commit SHA anywhere on the instance, satisfying `Commit#deployable?` and enabling an unauthorized deploy of that commit — a cross-repository write / unauthorized-deploy outcome, matching the Critical impact bar ("cross-repository writes ... an unauthorized deploy").

### Likelihood Explanation
Requires only knowledge of one org's `webhook_secret` (obtainable by anyone with admin rights to a webhook on that org's GitHub side — not a Shipit credential, not GITHUB_TOKEN, not repo write access to the *target* repo) plus the target commit's public SHA (visible on GitHub). No Shipit session, API token, or GitHub App private key is needed. This is realistic on any Shipit deployment that hosts multiple organizations (the documented/supported multi-org `secrets.yml` layout).

### Recommendation
Bind the authenticated organization to the object being mutated: after `verify_signature` succeeds, pass along (or re-derive and compare) the verified organization and require that `repository.full_name`'s owner matches it before dispatching to handlers. Additionally, `StatusHandler#process` (and any other handler using raw `sha`/`Commit.where` lookups without an owning-repository filter) should scope its query through `stacks`/`Repository.from_github_repo_name(repository_name)` exactly like `Handler#stacks` does, rather than searching `Commit` globally by `sha` alone.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` (attacker-controlled/known secret) and `orgB` (victim, hosts stack `orgB/victim-repo` with commit `deadbeef...` pending CI).
2. Attacker builds a `status` webhook JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgA_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `GithubApp`, and successfully verifies the signature (correct secret for `orgA`).
5. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` — finds the commit belonging to `orgB/victim-repo` (unrelated to `orgA`) — and calls `create_status_from_github!`, creating a fake `success` status for that commit, potentially unblocking an unauthorized deploy of `orgB`'s stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
