### Title
`StatusHandler#process` looks up `Commit` globally by `sha` with no repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` exist precisely to scope webhook effects to the repository that sent them, and `CheckSuiteHandler` correctly uses this scoping (`stacks.where(branch: ...).stack.commits.where(sha: ...)`), but `StatusHandler#process` never calls `repository_name` or `stacks` at all and instead runs `Commit.where(sha: params.sha)` across the entire `commits` table. Its param schema also never requires `repository`, so `Handler#initialize` succeeds regardless of whether a repository is present, absent, or unrelated to the sha, and `commit.create_status_from_github!` will mutate any `Commit`/`Status` row anywhere in the install that happens to share that sha.

### Finding Description
The claimed binding is: `params.repository.full_name == the repository that owns the commit being mutated`. Tracing the code shows this equality is never even checked.

- `Handler#initialize` calls `self.class.param_parser.parse!(payload)` [1](#0-0)  against `StatusHandler`'s schema, which only requires `sha` and `state` — no `repository` key at all [2](#0-1) .
- `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , with no reference to `repository_name` or `stacks` anywhere in the class.
- By contrast, `CheckSuiteHandler#process` uses `stacks.where(branch: params.check_suite.head_branch)` before touching any commit [4](#0-3) , and `stacks` is defined on the base `Handler` specifically to resolve `Repository.from_github_repo_name(repository_name)&.stacks` [5](#0-4) . `StatusHandler` simply omits this step.
- `Commit#create_status_from_github!` unconditionally writes a new `Status` row and re-evaluates deployability/merges for whatever `stack` that `Commit` belongs to [6](#0-5) , [7](#0-6) .

Reaching `process()` still requires passing `WebhooksController#verify_signature`, which selects the GitHub App/secret via `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) [8](#0-7) , [9](#0-8) . This means an attacker cannot simply hand-craft an arbitrary body with `repository` blanked out and pass signature verification without possessing the webhook secret — that specific "omit the field in a forged POST" vector is blocked by `verify_signature` for any organization Shipit doesn't recognize, and any byte change to a genuinely GitHub-signed payload invalidates the HMAC. Forging/mutating the raw signed body is out of scope (requires the secret or MITM).

However, the underlying structural bug does not require omitting or forging anything: because `StatusHandler` never reads `repository_name`/`stacks` at all, the exploit works with a fully truthful, legitimately-signed `status` webhook from a repository the attacker genuinely owns/controls (e.g., their own public fork of, or a repo that shares commit history with, a repository tracked by Shipit). If the attacker's own repository shares a commit SHA with a Shipit-tracked repository (common with forks, cherry-picks, or rebases that preserve SHAs), a genuine GitHub-signed status event from the attacker's own repo will match `Commit.where(sha: ...)` for the *other* tenant's `Commit` row and mutate its `Status`/deploy-gating state, because the query is never filtered by `repository_name`. This is exactly the "payload for one repository mutating another's stack/commit" Critical impact category.

### Impact Explanation
An attacker who legitimately owns any repository whose commit history intersects (even partially, via fork/cherry-pick) with a repository tracked as a Shipit `Stack` can push CI status updates (`success`/`failure`/`pending`) that get applied to the victim stack's `Commit`, altering `deployable?`, unblocking merges (`stack.schedule_merges`), and firing `commit_status`/`deployable_status` hooks for a repository/stack the attacker never authenticated against. This is repeatable for every shared/matching SHA and is not limited to a single stack — any Shipit-tracked repository whose git history overlaps with an attacker-controlled repo is affected, which matches the Critical "payload for one repository mutating another's stack, commit, task" category.

### Likelihood Explanation
No Shipit or GitHub secret is required. The attacker only needs a real repository with a legitimate webhook delivering `status` events to the Shipit host (satisfied automatically if Shipit's GitHub App/webhook is installed broadly, e.g. org-wide) and a commit whose SHA also exists in a Shipit-tracked stack (achievable via forking or cherry-picking a public commit). This is fully attacker-controlled and repeatable, requiring no privileged role, session, or token — matching the stated unprivileged threat model. The literal "omit `repository.full_name` in a forged, validly-signed body" variant described in the question is not achievable without the webhook secret (blocked by `verify_signature`), but the equivalent structural weakness (no repo scoping at all in `StatusHandler`) is fully exploitable with a truthful, legitimately-signed payload.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve `stacks` via `repository_name` first, then only update `Commit` rows belonging to those stacks, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`. Also add `requires :repository { requires :full_name, String }` to `StatusHandler`'s `params` block so a repository-less payload is rejected by `ExplicitParameters` rather than silently accepted.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, minitest)
test "status handler mutates commits belonging to a different stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_repo_full_name = "attacker/unrelated-repo"

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared commit")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    # repository intentionally unrelated to victim_stack's repository
    "repository" => { "full_name" => attacker_repo_full_name }
  }

  assert_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  # Binding under test: params.repository.full_name (attacker_repo_full_name)
  #   should NOT equal victim_stack.repository.full_name, yet the commit was mutated anyway.
  refute_equal victim_stack.repository.full_name, payload["repository"]["full_name"]
  assert victim_commit.reload.statuses.exists?(state: "success")
end
```
This demonstrates that `StatusHandler` mutates `Commit`/`Status` rows for a stack whose repository does not match `payload['repository']['full_name']`, confirming the unscoped, structural nature of the bug.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
