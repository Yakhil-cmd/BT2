### Title
Webhook signature verification keys on an attacker-controlled `repository.owner.login`/`organization.login` field that is decoupled from the `repository.full_name` the handlers act on, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a request against using `repository_owner`, a value read straight out of the unauthenticated, attacker-supplied JSON body, before the signature has been checked. The event handlers, however, resolve the target `Stack`/`Repository` using a *different* field from the same untrusted body, `repository.full_name`. Because these two fields are never cross-checked, an attacker can pick which org's secret gates the request while directing the resulting webhook action at any repository configured on the instance.

### Finding Description
`verify_signature` computes the verifying app from the payload before verification occurs: [1](#0-0) 
`repository_owner` is taken from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, i.e. directly from the raw POST body, which is not yet signature-verified: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an org with no configured `webhook_secret` as trivially satisfied (`return true unless webhook_secret`): [3](#0-2) 

Once verification passes (or is bypassed because the selected org has no `webhook_secret`), the actual event handler resolves the stack to act on using an entirely independent field from the same request body — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [4](#0-3) 
and `Repository.from_github_repo_name`: [5](#0-4) 

The binding that should hold is: `organization used to select/verify webhook_secret == organization that owns the repository the event is applied to`. Because `repository.owner.login` (used only for verification-key selection) and `repository.full_name` (used only for routing to a `Stack`) are two independent, attacker-controlled JSON keys with no cross-validation, that equality is never enforced. This mirrors the sDai bug class: a value used to satisfy a check (`feesPending` vs. deposited balance / here, "verified org" vs. "acted-upon org") is not the same value that the downstream action actually operates on, so a boundary that looks enforced is not.

This is exploitable in the documented multi-organization configuration, where each org gets its own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications" section), and any org onboarded without a `webhook_secret` set silently short-circuits `verify_webhook_signature`. Multi-org support and per-org `github_app_config` lookups are implemented in `Shipit.github`: [6](#0-5) 

### Impact Explanation
An attacker who can identify (or control) one organization on the instance whose GitHub App entry has no `webhook_secret` configured — or who otherwise has any org's secret — can send a raw HTTP POST directly to the public `/webhooks` endpoint with `repository.owner.login` set to that org (to pass/bypass `verify_signature`) while setting `repository.full_name` to any other repository/stack hosted on the same Shipit install. This lets them forge events (`push`, `status`, `check_suite`, `merge`, `deployable_status`, `membership`, etc.) against a stack they do not own, potentially: creating/altering `CheckRun`/commit status state used to gate deploy eligibility, manipulating merge-queue state, or adding/removing team memberships that feed into `Shipit.github_teams` authorization — an escalation into stack/deploy authorization state, without holding a Shipit session or valid credentials for the targeted repository's organization.

### Likelihood Explanation
Requires an unprivileged, unauthenticated network attacker able to reach the public `/webhooks` endpoint (no session, no `ApiClient` token needed) and requires the instance to have at least one configured organization lacking `webhook_secret`, or knowledge of one org's secret (e.g., because the attacker legitimately administers a GitHub App installed for their own org on the shared instance). This is a realistic deployment pattern per the documented multi-org configuration, but depends on operator configuration (an org missing `webhook_secret`), so likelihood is moderate rather than guaranteed in every deployment.

### Recommendation
Do not let the payload itself pick which secret verifies it independently of what it will be used to act on. Either: (1) require `repository.full_name`'s owner to match `repository_owner` before dispatching to handlers, rejecting mismatches; or (2) verify the signature against every configured org's secret and only accept if exactly one matches, then use that matched org (not the payload-declared one) to resolve `repository_name`; and (3) disallow/warn on any configured GitHub App entry with a blank `webhook_secret` in multi-org mode, since it defeats the purpose of per-org signing keys.

### Proof of Concept
1. Configure (or observe) a multi-org Shipit instance where org `attacker-org` has no `webhook_secret` set (per `docs/setup.md` multi-org example), while target org `victim-org` has `webhook_secret` configured and hosts a tracked `Stack`.
2. POST directly to `/webhooks` with header `X-Github-Event: status` (or `push`/`membership`) and body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success"
}
```
3. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and `verify_webhook_signature` returns `true` unconditionally because that org's `webhook_secret` is blank, per `lib/shipit/github_app.rb` lines 76-83.
4. The `status` handler then resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` (`app/models/shipit/repository.rb` lines 53-56) and applies the forged status to `victim-org`'s stack, despite the request never being signed by `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
