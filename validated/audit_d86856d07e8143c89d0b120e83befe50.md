### Title
Bridge KLAY Handle Nonce Permanently Stuck When Recipient Reverts or Bridge Has Insufficient Balance - (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` updates all nonce-tracking state (`_setHandledRequestTxHash`, `handleNoncesToBlockNums`, `_updateHandleNonce`) and emits `HandleValueTransfer` **before** executing the KLAY transfer. If the low-level call `_to.call.value(_value)("")` returns `false` (bridge has insufficient KLAY balance, or `_to` is a contract that reverts on receipt), the `require(ok, ...)` causes the entire transaction to revert, rolling back every state change. The nonce is never marked as handled, `lowerHandleNonce` never advances, and the bridge is permanently stuck on that nonce.

### Finding Description

In `BridgeTransferKLAY.sol` lines 81–99, the execution order is:

1. `_setHandledRequestTxHash(_requestTxHash)` — marks the request tx hash as consumed
2. `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber` — records the nonce
3. `_updateHandleNonce(_requestedNonce)` — advances `lowerHandleNonce` / `upperHandleNonce`
4. `emit HandleValueTransfer(...)` — emits the event
5. `(bool ok, ) = _to.call.value(_value)("")` — sends KLAY
6. `require(ok, "handleKLAYTransfer: transfer failed")` — **reverts everything above if transfer fails** [1](#0-0) 

Because Solidity reverts all state changes on `require` failure, steps 1–4 are rolled back. The nonce is never recorded in `handleNoncesToBlockNums`, so `_updateHandleNonce`'s loop condition `handleNoncesToBlockNums[i] > 0` is never satisfied for that nonce, and `lowerHandleNonce` never advances past it. [2](#0-1) 

The off-chain bridge manager in `processingPendingRequestEvents` skips events with nonces below `lowerHandleNonce` but will keep retrying the stuck nonce indefinitely: [3](#0-2) 

### Impact Explanation

- **Unauthorized asset lock / permanent transfer failure**: Any KLAY transfer request whose `_to` address is a contract that reverts on receiving KLAY, or any request whose `_value` exceeds the bridge's current KLAY balance, permanently blocks the bridge's nonce sequence. No subsequent KLAY transfer for that bridge pair can ever have `lowerHandleNonce` advance past the stuck nonce.
- The `recoveryBlockNumber` is never updated for the stuck nonce, so the off-chain recovery mechanism keeps re-scanning from the same block, repeatedly attempting the failing handle call.
- This is a direct analog of the RocketPool bug: a "handle" action is blocked by an asset-transfer failure, preventing the protected state (bridge nonce) from advancing.

### Likelihood Explanation

Two realistic triggers exist:

1. **Recipient-controlled revert (unprivileged)**: Any user can call `requestKLAYTransfer` with `_to` set to a contract address whose fallback function reverts. Once bridge operators reach the vote threshold and the handle tx executes, the transfer fails and the nonce is stuck. No operator privilege is required to initiate this.

2. **Bridge underfunding**: If the bridge contract's KLAY balance drops below a pending transfer's `_value` (e.g., due to a separate bug, fee drain, or operator error), every `handleKLAYTransfer` attempt for that nonce reverts.

### Recommendation

Decouple the nonce-advancement from the asset transfer. Two options:

1. **Commit-then-transfer**: Mark the nonce as handled unconditionally (as currently written), but move the `require(ok, ...)` to a separate step or emit a failure event instead of reverting, so `lowerHandleNonce` always advances.

2. **Separate redemption step**: If the transfer fails, record the pending payout in a mapping and allow `_to` to claim it separately, analogous to the RocketPool fix of allowing the bond to be redeemed in a separate step.

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
