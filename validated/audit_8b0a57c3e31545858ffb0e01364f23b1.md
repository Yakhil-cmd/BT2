**Analysis:** The claim misreads the boundary check. In `MultiEd25519Signature::verify_arbitrary_msg`, the match arm is: [1](#0-0) 

```rust
match bitmap_last_set_bit(self.bitmap) {
    Some(last_bit) if (last_bit as usize) < public_key.public_keys.len() => (),
    _ => {
        return Err(anyhow!(...))
    },
};
```

When `last_bit as usize == public_key.public_keys.len()` (the exact boundary the question describes), the guard `(last_bit as usize) < public_key.public_keys.len()` evaluates to `false`, so the match falls through to the wildcard `_` arm and the function returns `Err(...)` immediately — it does not silently skip the check, and it does not proceed to the `.get()` call later in the function [2](#0-1) . Since `bitmap_last_set_bit` returns the *maximum* set index in the bitmap, requiring that maximum to be strictly less than `public_keys.len()` guarantees every other set bit index is also `< public_keys.len()`, so the subsequent `public_key.public_keys.get(bitmap_index)` at line 552 can never go out of bounds for any signature that passes this initial check [3](#0-2) .

There's also an existing unit test (`test_key_boundaries`) exercising a related corrupted-bitmap scenario and asserting `verify_arbitrary_msg` returns an error rather than panicking [4](#0-3) .

The native wrapper `native_signature_verify_strict` in the Move framework natives simply forwards to `verify_arbitrary_msg` and converts the result to a boolean, so no additional bypass is introduced at the native boundary [5](#0-4) .

Since the strict `<` comparison at the boundary correctly rejects the case described (last-set-bit index equal to `public_keys.len()`), there is no off-by-one, no panic path, and no way for an unprivileged attacker to get a corrupted approval set admitted via this code path.
