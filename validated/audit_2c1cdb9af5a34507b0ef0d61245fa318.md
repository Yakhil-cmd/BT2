### Title
Cross-repository Status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the `repository_owner` extracted from the payload, proving the request originated from that owner's repository. `StatusHandler#process` then looks up commits by `Commit.where(sha: params.sha)` globally, with no filter tying the matched `Commit` back to the authenticated repository, so a correctly-signed webhook from repository R1 can write a `Status` onto a `Commit` belonging to an unrelated repository R2 whenever a commit with the same SHA exists in both (e.g., shared history via a fork).

### Finding Description
The claimed broken binding, stated as an equality: `repository_owner` (used in `WebhooksController#verify_signature`, `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`, to pick `Shipit.github(organization: repository_owner).verify_webhook_signature`) should equal `commit.stack.repository.owner` for every `Commit` row mutated by the event dispatched from that request.

Tracing the code:
- `verify_signature` derives `repository_owner` from `params.dig('repository','owner','login')` and validates the HMAC signature using `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) [2](#0-1) . This only proves the payload was HMAC-signed by GitHub for the org named in `repository.owner.login` (which can be the attacker's own org/repo).
- After this, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers with the raw parsed payload [3](#0-2) .
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This query is **global across all `Commit` rows in the database**, irrespective of which stack/repository the row belongs to.
- Contrast with sibling handlers that correctly scope by repository first: `PushHandler#process` filters via `stacks.not_archived.where(branch:)` [5](#0-4) , and `CheckSuiteHandler#process` filters via `stacks.where(branch: ...)` before touching commits [6](#0-5) , where `stacks` resolves through `Repository.from_github_repo_name(repository_name)` — i.e., scoped strictly to the repository named in the authenticated payload [7](#0-6) . `StatusHandler` never calls `stacks` or filters by `repository_name`/`stack_id` at all.

Root cause: `StatusHandler` matches commits purely by `sha`, a value that is not unique per repository — the `commits` table has no uniqueness constraint tying `sha` to a `stack`/repository, and Git SHAs are frequently shared across forks of the same upstream history. An attacker who owns/forks a repository can create a GitHub commit status (via the Statuses API) on any commit SHA present in their own repository, including ancestor commits inherited from the fork's upstream (which may equal a `Commit` row already tracked by a *different*, unrelated Shipit stack for the same upstream project). GitHub will then send a genuine, correctly-signed "status" webhook for the attacker's own repository/org, satisfying `verify_signature` for the attacker's own org, while `params.sha` collides with a `Commit` belonging to the victim's stack.

`verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema for `StatusHandler` (`requires :sha, String; requires :state, String; ...`) do not prevent this — none of them re-check that the matched `Commit`'s owning repository equals the authenticated `repository_owner`.

### Impact Explanation
A successful request causes `Shipit::Status.create!`/`find_or_create_by!` (via `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`) to write a `Status` row against a `Commit` belonging to a repository/stack the attacker never authenticated for [8](#0-7) [9](#0-8) . Writing statuses can flip a commit's CI state, and `add_status` can trigger `stack.schedule_merges`, `deployable_status`/`commit_status` hooks, and continuous-delivery scheduling for the victim's stack [10](#0-9) . This is a payload from one repository/tenant mutating another repository's `Commit`/`Status` state, which can influence whether the victim's continuous-delivery pipeline treats a commit as deployable — matching the "Critical: payload for one repository mutating another's ... commit ... or an unauthorized deploy" category. Repeatable against any target repository whose Shipit-tracked commit SHA is shared with a repository the attacker controls (most commonly via forking a public open-source project also deployed via Shipit).

### Likelihood Explanation
Preconditions: the target project must be open to forking (public repo), tracked by Shipit as a `Stack`, and the attacker must be able to configure/trigger a GitHub webhook for a repository they own that is registered under a `repository_owner`/org known to `Shipit.github(organization:)` (otherwise `GithubOrganizationUnknown` short-circuits with 422). Given that, the attacker's cost is: fork the target repo, use GitHub's Statuses API to post an arbitrary status on any shared ancestor SHA. No Shipit secret, session, or token is required at any point — only ordinary GitHub actions on a repo the attacker owns. This is realistic for any Shipit deployment that whitelists more than one organization/owner (multi-tenant `Shipit.github` config) — a single-tenant deployment (one org only) would not expose external attacker-controlled orgs, which is a mitigating deployment-dependent factor not fixable in code alone.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the authenticated repository, mirroring `PushHandler`/`CheckSuiteHandler`: use `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently iterate `stacks` (derived from `Repository.from_github_repo_name(repository_name)`) and only update commits belonging to those stacks, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ties the mutated `Commit` back to the repository that was actually authenticated by `verify_signature`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":state does not create a Status for a commit belonging to a different repository" do
  request.headers['X-Github-Event'] = 'status'

  # R2 = victim repository/stack, already has a Commit with a known sha
  victim_commit = shipit_commits(:first)
  shared_sha = victim_commit.sha

  # R1 = attacker-owned repository, distinct from R2's owner
  attacker_repository_params = { repository: { owner: { login: 'attacker-org' } } }

  body = {
    'sha' => shared_sha,
    'state' => 'failure',
    'branches' => [{ 'name' => 'master' }]
  }.merge(attacker_repository_params).to_json

  # verify_signature stubbed to succeed for 'attacker-org' (simulating a genuine,
  # correctly-signed GitHub webhook from the attacker's own repo)
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: body, as: :json
  end
end
```
Currently this assertion fails (`StatusHandler#process` writes the Status regardless of `repository_owner`), demonstrating the cross-tenant mutation; after applying the recommended fix scoping the lookup via `stacks`, the assertion passes.
