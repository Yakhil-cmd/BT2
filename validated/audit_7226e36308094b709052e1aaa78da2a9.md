### Title
Operator-precedence bug in `OpenedHandler#provision?` bypasses `repository.review_stacks_enabled == false` for `allow_with_label`/`prevent_with_label` repos - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled == true` as a universal precondition for provisioning a `ReviewStack` from a pull request, regardless of `provisioning_behavior`. Because of Ruby `&&`/`||` precedence, the `review_stacks_enabled` check is only applied to the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches evaluate independently of it, so a repository with review stacks disabled but `provisioning_behavior = prevent_with_label` still creates a `ReviewStack` with an attacker-controlled `branch` from a plain PR-open event.

### Finding Description
Broken binding: intended `repository.review_stacks_enabled == true` for every provisioning path; actual behavior lets `(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` or `(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?)` short-circuit to `true` even when `review_stacks_enabled == false`.

Code: [1](#0-0) 

Due to Ruby operator precedence (`&&` binds tighter than `||`), this parses as:
```
(review_stacks_enabled && allow_all?) ||
(allow_with_label? && has_label?) ||
(prevent_with_label? && !has_label?)
```
Only the first disjunct is gated by `review_stacks_enabled`. `provisioning_behavior_prevent_with_label?` combined with the *default* state of a freshly opened PR (`pull_request_has_provisioning_label?` false, since a fork PR has no labels unless a maintainer adds one) makes the third disjunct `true` unconditionally of `review_stacks_enabled`.

`process` then calls `ReviewStackAdapter#find_or_create!` unconditionally once `provision?` is true: [2](#0-1) 

`find_or_create!` -> `create!` persists `stack_attributes`, which sets `branch: params.pull_request.head.ref` directly from the webhook payload, scoped to `repository.review_stacks`: [3](#0-2) 

Exploit flow: an unprivileged GitHub user opens a real pull request from their fork against a target repository whose admin has configured `provisioning_behavior = prevent_with_label` and `review_stacks_enabled = false` (e.g., to disable auto-provisioning while still using labels to gate a subset). GitHub delivers a legitimately signed `pull_request` "opened" webhook (attacker needs no webhook secret — GitHub sends it). The PR has no labels by default, so `pull_request_has_provisioning_label?` is false, making `prevent_with_label? && !has_label?` true, and `provision?` returns true despite `review_stacks_enabled == false`. `create!` then persists a `ReviewStack` with `branch` equal to the attacker's fork head ref and queues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`.

None of the standard guards catch this: signature verification only authenticates that GitHub sent the webhook (attacker doesn't need to forge it — they trigger it by opening a real PR), `ExplicitParameters` only validates payload shape, and there is no additional `review_stacks_enabled` check inside `ReviewStackAdapter` itself — it trusts the caller's `provision?`/`unarchive?` predicate.

### Impact Explanation
An attacker who can merely open a pull request against a target repository can force creation of a `ReviewStack` scoped to that repository even though the repository owner explicitly disabled review-stack auto-provisioning (`review_stacks_enabled = false`). The stack's `branch` is fully attacker-controlled (their fork's head ref), and the stack is immediately queued for provisioning (`ReviewStackProvisioningQueue.add`), which in Shipit's review-stack model drives subsequent Git checkout/build/deploy tasks against that attacker branch — i.e., commands run against attacker-controlled code/config for a repository whose administrator opted out of this behavior. This is an unauthorized environment created and queued for deployment, which aligns with the Critical category ("an unauthorized deploy... of ... a stack").

### Likelihood Explanation
Preconditions: the target repository must be configured with `provisioning_behavior: prevent_with_label` (or `allow_with_label` if a maintainer has already applied the provisioning label) AND `review_stacks_enabled: false`. This is a plausible, legitimate admin configuration (e.g., an org that wants label-gated provisioning but wants the "disabled" toggle to act as a full kill switch — which it does not). Attacker cost is trivial: open a pull request from a fork with no special labels. No secrets, sessions, or elevated GitHub permissions are required. The attack is repeatable against every repository configured this way.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the equivalent fix to the matching `unarchive?`/`archive?` predicates in `reopened_handler.rb`, `labeled_handler.rb`, and `unlabeled_handler.rb`, which have the same precedence pattern.

### Proof of Concept
minitest plan (extends existing `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` patterns):
```ruby
test "does NOT create a review stack when review_stacks_enabled is false, even with prevent_with_label behavior and no label" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :prevent_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # default state of a freshly opened PR

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Given the current buggy code, this assertion fails: a `ReviewStack` is created with `branch == payload["pull_request"]["head"]["ref"]` despite `review_stacks_enabled == false`, demonstrating the binding violation (`ReviewStack#branch` should never be set from an unapproved head ref when review stacks are disabled for the repository).
