### Title
Cross-repository status forgery via `StatusHandler#process` unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to using a global `Commit.where(sha: params.sha)` query, with no join against the webhook payload's `repository.full_name`. Because commit SHAs are not required to be globally unique across stacks (only unique per `stack_id`), a `status` webhook that is legitimately signed for repository A can be used to write a `Status` row onto a commit belonging to an entirely unrelated stack/repository B whose commit history happens to share that SHA.

### Finding Description
Binding claimed to hold: `repository_of(status_written) == repository_named_in(verified_payload)`.

Trace:
- `WebhooksController#verify_signature` only validates the HMAC signature against the webhook secret configured for `Shipit.github(organization: repository_owner)` [1](#0-0) . It never checks that the specific `repository.full_name` in the payload maps to the stack whose commit is ultimately mutated.
- `StatusHandler#process` does: [2](#0-1) . This is a completely unscoped `Commit.where(sha:)` across the whole `commits` table — it never calls the base class's `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) the way `PushHandler` [3](#0-2)  and `CheckSuiteHandler` [4](#0-3)  both do to scope lookups to the repository named in the payload.
- The `Handler` base class does expose `stacks`/`repository_name` precisely for this purpose [5](#0-4) , but `StatusHandler` is the outlier that doesn't use it.
- `Commit#create_status_from_github!` then unconditionally creates the `Status` on whatever commit was matched, keyed to that commit's own `stack_id` [6](#0-5) , with no re-validation against the incoming payload's repository.
- SHA uniqueness is only enforced per-stack, not globally: the index is `stack_id_and_sha`, so two different stacks/repos (e.g., cherry-picked commits, monorepo splits, vendored code, or forks) can legitimately contain a `Commit` row with an identical `sha` in different `Stack`/`Repository` records.

Exploit flow: attacker owns/has push+status access to repository A, which is onboarded under a GitHub organization/App-installation that Shipit trusts. Attacker pushes (or otherwise causes to exist) a commit in A whose SHA matches a commit already tracked by Shipit in tenant B's stack (via cherry-pick, subtree merge, or any repo sharing history/blobs). Attacker (or their own CI acting on repo A, which they control) sets a `status` on that SHA in repo A. GitHub computes and sends a genuinely signed `status` webhook to Shipit for repository A. `verify_signature` passes because the signature is valid for A's owning organization/secret — it has nothing to do with which commit gets mutated. `StatusHandler#process` then finds and updates the commit row belonging to stack B (a different repository/tenant, possibly a different organization) and creates a `Status`, which can flip `Commit#state` to `success`, satisfy `deployable?`, and even trigger `ProcessMergeRequestsJob` / continuous deployment logic in tenant B's stack, as shown by existing tests that call `create_status_from_github!` and observe state transitions and job enqueuing [7](#0-6) .

No existing guard catches this: `verify_signature` is org-secret-scoped, not repository/commit scoped; `ExplicitParameters` schema for `StatusHandler` only validates types, not repository ownership [8](#0-7) ; and no model validation ties `Status#stack_id`/`Commit#stack_id` back to the webhook's `repository.full_name`.

### Impact Explanation
A webhook correctly authenticated for repository A can write a fabricated CI status onto a `Commit` belonging to a different `Stack`/`Repository` (tenant B), potentially flipping that commit's `state` to `success`/`failure`, unblocking `deployable?` checks, and triggering downstream automation (`ProcessMergeRequestsJob`, continuous deployment via `ContinuousDeliveryJob`) for tenant B without any authorization on repository B. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team," and can lead to an unauthorized deploy being triggered on tenant B's stack if continuous deployment is enabled. The attack is repeatable against any SHA collision the attacker can arrange, across any repositories tracked by the same Shipit instance, including across different GitHub organizations if their App installations share the same Shipit deployment.

### Likelihood Explanation
Preconditions: attacker needs push/status-setting rights on some repository A that is either tracked by Shipit or merely covered by an installed GitHub App/webhook integration pointing at this Shipit instance, plus a SHA collision with a commit tracked in tenant B's stack (achievable via cherry-pick, subtree/vendoring, or fork history — well within an unprivileged GitHub user's control since they choose their own commit content and can reuse an existing public commit's tree/parent to reproduce an identical SHA). No Shipit secrets, sessions, or team membership are required; the webhook signature is real and computed by GitHub itself. This is feasible and repeatable but requires the attacker to engineer or find a SHA collision with a commit already present in Shipit's commit history, which is a real but non-trivial precondition (it is not a hash-collision problem — commits with identical SHAs share full identical content/tree/parent, so this is most practical when repository B's code was actually derived from or shares commits with A, e.g. mirrors, forks, monorepo splits).

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks under the repository that GitHub actually reported (`payload.dig('repository','full_name')`) can have statuses attached, closing the cross-tenant write path.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":state from repository A must not create a Status on a commit belonging to a different stack/repository" do
  attacker_repo_full_name = "attacker-org/attacker-repo"
  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit), repo shopify/shipit-engine (per fixtures)

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end

  # Binding check: repository_of(status_written) must equal repository_named_in(verified_payload)
  assert_not_equal attacker_repo_full_name, victim_commit.stack.repository.full_name
end
```
With `GithubHook#verify_signature`/`verify_webhook_signature` stubbed to `true` (as in the existing `setup` block), the current code fails this test because `StatusHandler#process`'s unscoped `Commit.where(sha:)` matches `victim_commit` regardless of `attacker_repo_full_name`, incrementing `victim_commit.statuses.count` even though `victim_commit.stack.repository.full_name != attacker_repo_full_name`.
