### Title
Unfiltered pull request labels become raw process environment variables in shell-interpreted `shipit.yml` steps, enabling env-injection RCE (e.g. `DYLD_INSERT_LIBRARIES`/`LD_PRELOAD`) - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name, uppercased, directly into the stack's environment hash with no allowlist. This hash flows unfiltered through `TaskCommands#env` / `Command#unbundled_env` into `PTY.spawn`, meaning any GitHub user who can label their own PR on a repository with review apps enabled (`provisioning_behavior=allow_all`, i.e. review stacks auto-provisioned without a gating label) can set arbitrary process environment variables — including `DYLD_INSERT_LIBRARIES`, `LD_PRELOAD`, `PATH`, `BASH_ENV`, `RUBYOPT`, etc. — for the shell that executes the `shipit.yml` steps.

### Finding Description
The broken binding: the set of environment variable keys that reach `PTY.spawn` should equal `{keys explicitly whitelisted by shipit.yml (deploy_variables/rollback_variables/task variables via EnvironmentVariables#permit)} ∪ {Shipit/system-controlled keys}`. In reality it equals that set **∪ {uppercase(label_name) : label_name ∈ pull_request.labels}**, with no allowlist applied to the label-derived keys.

Code path:
- `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` straight from the unauthenticated webhook body onto `pull_request.labels` with no character/name filtering: [1](#0-0) 
- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into the stack's env with no key allowlist: [2](#0-1) 
- `TaskCommands#env` merges `@stack.env` (which includes the label-derived keys) unfiltered, alongside `@task.env` (which *is* filtered elsewhere via `EnvironmentVariables#permit`, but that filtering is never applied to `@stack.env`): [3](#0-2) 
- `Command#unbundled_env` merges `@env.stringify_keys` (containing the attacker-controlled key) into the hash passed to `PTY.spawn`: [4](#0-3) 
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, spawning the shell-interpreted `shipit.yml` step with that environment: [5](#0-4) 

This is confirmed by an existing test that intentionally documents the label-to-env behavior: [6](#0-5) 

Root cause: `EnvironmentVariables#permit` (the allowlist mechanism used for `deploy_variables`/`rollback_variables`/task `variables`) is applied to *user-supplied task env* (`filter_deploy_envs`, `filter_rollback_envs`, `TaskDefinition#filter_envs`) but is never applied to `Stack#env`/`ReviewStack#env`, so nothing gates which keys a PR label can set. [7](#0-6) [8](#0-7) [9](#0-8) 

Exploit flow:
1. Attacker opens a PR on a repository with `review_stacks_enabled` and `provisioning_behavior=allow_all` (no gating label required for provisioning). Repository settings for provisioning behavior are exposed via `Repository#provisioning_behavior_allow_with_label?`/related methods (referenced from `LabeledHandler`), but under `allow_all` no label is even required to trigger provisioning. [10](#0-9) 
2. Attacker (owns the fork/PR, needs no Shipit session or token) adds a label named `dyld_insert_libraries` (or `ld_preload`, `bash_env`, `path`) to their own PR via the GitHub UI/API on their own repo.
3. GitHub emits the `labeled`/webhook event; `LabelCapturingHandler` persists the label name verbatim.
4. Next deploy/task run on the review stack calls `TaskCommands#env`, which includes `DYLD_INSERT_LIBRARIES => "true"` (or any other key) unfiltered, and it becomes a literal process environment variable for the spawned shell running the `shipit.yml` step.
5. On macOS deploy hosts, `DYLD_INSERT_LIBRARIES` preloads an attacker-supplied dylib into any non-restricted (non-SIP, non-hardened-runtime) dynamically linked binary invoked by the step (e.g. `cap`, `bundle`, custom deploy scripts) — RCE. On Linux hosts, equivalent primitives like `LD_PRELOAD`, `PATH`, `BASH_ENV`, or `GIT_SSH` achieve the same effect.

Why existing guards fail: `verify_signature`/webhook signature checks only validate that the request came from GitHub — they do not constrain the label *content*, which is attacker-chosen text on a repo the attacker owns. `EnvironmentVariables#permit` exists but is architecturally never invoked on `Stack#env`/`ReviewStack#env`.

### Impact Explanation
Critical — arbitrary environment variable injection into the shell process that executes `shipit.yml` steps constitutes Remote Code Execution on the Shipit deploy host, matching the "Command running that should not" and RCE-via-`Command`/`PTY.spawn` category. The blast radius is scoped to repositories that have review apps enabled with a permissive provisioning behavior, but it is fully repeatable (any number of PRs/labels) and requires no privileged role — any user able to open a PR and add a label on their own fork/repo.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and a provisioning behavior that provisions the review stack without requiring approval (`allow_all`), which is a documented, supported configuration. Attacker cost is trivial — creating a label with an arbitrary name is a normal, unprivileged GitHub action. The behavior is deterministic and already demonstrated by the existing test suite (labels become uppercased env vars), so likelihood of exploitation, given the configuration precondition, is high. The specific `DYLD_INSERT_LIBRARIES` dylib-preload technique further requires a macOS deploy host and a non-hardened dynamically-linked target binary invoked in the step, narrowing but not eliminating exploitability; the broader arbitrary-env-injection issue (e.g. `PATH`, `BASH_ENV`, `LD_PRELOAD`) is platform-agnostic and equally severe.

### Recommendation
Restrict `ReviewStack#env`'s label-derived keys to an explicit allowlist (e.g. only permit keys declared by the repository/`shipit.yml`, or prefix them, e.g. `LABEL_<NAME>`, so they cannot collide with sensitive dynamic-linker/shell environment variable names), and/or run `EnvironmentVariables#permit` against a fixed denylist/allowlist before merging into `TaskCommands#env`. At minimum, block known-dangerous keys (`LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `DYLD_LIBRARY_PATH`, `PATH`, `BASH_ENV`, `ENV`, `IFS`, `GIT_SSH`, `RUBYOPT`, `PERL5OPT`, etc.) from ever being set via `ReviewStack#env`.

### Proof of Concept
```ruby
# test/lib/shipit/review_stack_env_injection_test.rb
require "test_helper"

class ReviewStackEnvInjectionTest < ActiveSupport::TestCase
  test "PR label name reaches the shell-interpreted shipit.yml step process env unfiltered" do
    stack = shipit_stacks(:review_stack)
    deploy = stack.trigger_continuous_delivery
    stack.pull_request.labels = ["dyld_insert_libraries"]

    env = Shipit::DeployCommands.new(deploy).env

    # Binding claimed broken: the set of keys reaching PTY.spawn should equal
    # only allow-listed keys (deploy_spec.deploy_variables names), but it
    # includes the attacker's uppercased label name unfiltered.
    assert_equal "true", env["DYLD_INSERT_LIBRARIES"]

    command = Shipit::Command.new("id", env:, chdir: ".")
    assert_equal "true", command.unbundled_env["DYLD_INSERT_LIBRARIES"]
  end
end
```
