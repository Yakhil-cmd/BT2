## Title
Cross-repository commit-status forgery via webhook `sha`-only lookup bypasses per-organization signature scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

## Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the specific GitHub organization/app derived from the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) , then falls back to the same field to select which app's secret to verify against [2](#0-1) . However, `StatusHandler#process` — the code that actually writes state — looks up the target `Commit` purely by `sha`, with no scoping back to the repository/organization that was authenticated: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This breaks the equality "organization that authenticated == repository that is written," since `sha` is global across every `Stack`/`Repository` tracked by the Shipit instance, not scoped to the authenticated repository.

## Finding Description
Every other handler resolves its target through `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` and scopes lookups to that specific repository via `Repository.from_github_repo_name` [4](#0-3) . `StatusHandler` is the exception: it declares no `repository` requirement in its `params` block and never consults `repository_name`/`stacks` at all [5](#0-4) .

Meanwhile, `Shipit` supports multiple independently-authenticated GitHub organizations, each installed with its own GitHub App / webhook secret (`Using Multiple Github Applications` deployment mode) [6](#0-5) . `verify_signature` correctly validates the signature is valid *for the org named in this payload* [1](#0-0) , meaning it is a sound guarantee only that "some legitimate, unprivileged actor able to trigger a real GitHub event in Organization A sent this." It carries no guarantee about which commit/repository the payload's `sha` will end up touching.

Because git commit SHAs are content-addressed, identical commits legitimately exist across independent repositories the moment code is forked, mirrored, cherry-picked, or the same upstream commit is merged into two different downstream repos owned by two different organizations — a routine occurrence, not a hash-collision attack. An actor who can trigger a real, validly-signed `status` webhook in Organization A's tracked repo (e.g., because Organization A's repo has any status-reporting integration, or because the actor has ordinary push/CI access there) can set `sha` to a commit hash that also exists in a `Stack` owned by Organization B — and `StatusHandler` will happily write that status onto Organization B's commit, regardless of the fact that the signature was only proven valid for Organization A.

Before the fix, the invariant the codebase implicitly (and incorrectly) assumes is:
`signature verified for organization(repository.owner.login)` ⟹ `state mutated belongs to repository.owner.login`

`StatusHandler` breaks this because the mutated `Commit` is selected by `sha` alone, independent of `repository.owner.login`/`repository.full_name`.

## Impact Explanation
`Commit#create_status_from_github!` persists a `Status` (e.g., `state: "success"`) that other Shipit subsystems treat as an authoritative CI signal for that commit — required-status checks used to gate `MergeMergeRequests`/continuous delivery and to unblock manual deploys. Forging a `success` status on a commit belonging to a `Stack` in a different, untrusted-by-that-org repository can cause Shipit to treat unreviewed/unvetted code as CI-green, contributing to an unauthorized merge or deploy decision in that other organization's stack — this falls in the "unauthorized deploy, rollback or merge" Critical impact bucket, since it is achieved purely by a correctly-signed webhook belonging to a *different* organization than the one whose state is mutated.

## Likelihood Explanation
This does not require compromising any webhook secret, GitHub App private key, or Shipit session — only the ability to cause any legitimate `status` event to be delivered from an organization that already has Shipit's GitHub App installed, with a `sha` value that coincides with a commit tracked under a different organization's `Stack`. Given the routine nature of shared/cherry-picked commits between multi-org GitHub estates that all forward webhooks to the same Shipit instance, this is a realistic, low-effort vector, and the code path (`StatusHandler`) has zero scoping logic to prevent it, unlike every sibling handler.

## Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring the pattern used by every other handler: require and parse the `repository.full_name` from the payload, resolve it via `Repository.from_github_repo_name`, and restrict the `Commit` lookup to `stacks`/commits that belong to that resolved repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`.

## Proof of Concept
1. Shipit is configured in multi-org mode: `OrgA` and `OrgB` each install their own instance of the Shipit GitHub App, each with a distinct `webhook_secret`, as documented in `docs/setup.md` [7](#0-6) .
2. Shipit tracks a `Stack` for `OrgB/critical-repo`. A commit with `sha = X` (e.g., a widely-shared upstream commit, or a cherry-pick/merge from a shared history) exists in both `OrgA/attacker-repo` and `OrgB/critical-repo`.
3. A `status` webhook fires for `OrgA/attacker-repo` for commit `X` (e.g., triggered by any status-reporting bot/CI legitimately connected to `OrgA`'s repo) and is delivered correctly signed with `OrgA`'s webhook secret.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"` from the payload and validates the signature against `OrgA`'s app config — verification succeeds `` [1](#0-0)  ``.
5. `StatusHandler#process` runs `Commit.where(sha: X)`, which matches the `Commit` belonging to `OrgB/critical-repo`'s `Stack`, and writes a forged `success` status onto it — despite the request never having been authenticated for `OrgB` `` [3](#0-2)  ``.
6. Downstream Shipit automation (merge queue / continuous delivery) treats `OrgB/critical-repo`'s commit `X` as CI-green, potentially advancing merge/deploy decisions it should not have.
