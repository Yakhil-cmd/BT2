### Title
Webhook signature verification is scoped to the wrong organization, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook against based on `repository_owner`, an unauthenticated value read straight out of the JSON body. The handlers that actually act on the webhook (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) look up the target `Stack`/`Repository` using a *different* field from the same body — `repository.full_name` — that is never covered by the signature-selection logic. In a multi-organization Shipit deployment (the config format explicitly supports per-organization `github:` blocks with distinct `webhook_secret`s), an attacker who legitimately controls one configured organization (and thus knows/can obtain that organization's valid webhook secret from their own GitHub App settings) can sign a payload whose `repository.owner.login` matches their own org (so signature verification passes using their own secret) while `repository.full_name` names a repository/stack belonging to a completely different, unrelated organization tracked by the same Shipit instance. This breaks the binding: `organization that authenticated == repository that is acted upon`.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

This picks a per-organization `GitHubApp` instance and HMAC-verifies the raw body against *that org's* `webhook_secret`. But once verified, `create` dispatches the whole raw payload to handlers unconditionally:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

Handlers resolve the target repository/stack from a separate field, `repository.full_name`, with no cross-check against `repository.owner.login` (the field the signature was verified against):
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process`, for example, triggers `stack.sync_github(...)` for whichever stacks match `repository_name`: [5](#0-4) 

`Shipit.github(organization:)` config is explicitly per-organization, each with its own `webhook_secret`: [6](#0-5) 

Because `owner.login` and `full_name`'s owner segment are independently attacker-controlled fields inside the same unauthenticated JSON body, and only the former is bound to signature selection, an attacker who is a legitimate GitHub App/org admin for *any* one organization configured in this Shipit instance can forge a signature that verifies (using their own org's secret) while setting `full_name` to `victim-org/victim-repo` for a *different* organization also tracked by the same instance. The `verify_signature` before_action never re-validates that the org whose secret was used actually owns the repository being acted on.

### Impact Explanation
This lets an authenticated-for-one-org attacker forge `push`, `status`, `check_suite`, and other webhook events attributed to a repository owned by a different organization served by the same Shipit deployment. Depending on handler, this can:
- Force `GithubSyncJob`/`sync_github` on a victim stack with an attacker-chosen `expected_head_sha`, potentially triggering continuous deployment of an attacker-influenced commit if that SHA exists in the victim repo history [5](#0-4) .
- Inject forged commit statuses on a victim's commits via `StatusHandler`, which can flip CI gating used to allow deploys/merges [7](#0-6) .

This matches the "unauthorized deploy/rollback" and cross-repository-write class of impact defined in scope.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate administrator of at least one organization/GitHub App configured in a *multi-organization* Shipit deployment (a supported and documented configuration) — i.e., they hold a valid webhook secret for their own org but not for the victim org. This is a narrower attacker model than a fully anonymous outsider, but it is still an "unprivileged attacker" relative to the victim organization/repository, matching the rule's cross-repository-write / organization-vs-repository trust-binding class.

### Recommendation
Bind the verified organization to the repository being acted upon: after signature verification succeeds, `create`/handlers should confirm that `repository.full_name`'s owner matches the same `repository_owner` (or organization) whose secret validated the signature, and reject the webhook otherwise. Alternatively, look up the `Repository`/`Stack` first, derive the organization from the stored repository record, and verify the signature against that same organization's secret exclusively — never trusting an attacker-supplied owner field for secret selection when a different attacker-supplied field is later used for target resolution.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and distinct `webhook_secret` (per `config/secrets.development.example.yml` multi-org format).
2. Attacker controls `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-existing-in-victim-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s secret and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret [1](#0-0) .
6. `PushHandler` resolves stacks via `full_name` = `"victim-org/victim-repo"` [4](#0-3)  and triggers `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack [5](#0-4)  — despite the request never being signed by `victim-org`'s secret.
