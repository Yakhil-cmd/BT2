### Title
Global `last-update` price-feed timestamp ratchet lets one caller DoS another caller's same-block price resolution - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve` in the market contract enforces price freshness against a **global, feed-scoped** `last-update` map rather than a per-caller value. Any account can advance this shared timestamp for a given `{type, ident}` price feed by simply submitting a valid oracle payload with a newer `publish-time`, at essentially no cost. Any other account whose own (still valid, unexpired) price-feed payload has an older `publish-time` than the value just written by the first caller will have their transaction revert with `ERR-ORACLE-INVARIANT`, purely because of the ordering of transactions within the same block — not because their data is stale by the protocol's own `max-staleness` rule.

### Finding Description
`oracle-timestamp-fresh` requires that the new price timestamp `ts` be `>= prev`, where `prev` comes from a shared map keyed only by the price feed identity: [1](#0-0) 

`price-resolve` reads `oracle-last-update key` (the shared `last-update` map, keyed by `{type, ident}`, not by `tx-sender`/account) and calls `map-set last-update key timestamp` whenever a newer timestamp is submitted: [2](#0-1) 

Because this map is a single global slot per feed, shared across every account calling `borrow`, `repay`, `liquidate`, `collateral-add`, etc. in the same block, the following ordering dependence exists between two unprivileged users in one block:

1. Attacker (Alice) submits an operation (e.g. `borrow`) carrying an optional `price-feeds` payload for asset X with a very recent `publish-time` T2, causing `last-update[{type,ident}] = T2`.
2. Victim (Bob), whose transaction was already broadcast/signed using an oracle payload with `publish-time` T1 < T2 (T1 is still within `max-staleness` of `stacks-block-time`, i.e. perfectly valid on its own), gets included later in the same block. `oracle-timestamp-fresh(T1, T2, max-staleness)` fails the `>= ts prev` check, so Bob's call reverts with `ERR-ORACLE-INVARIANT` even though Bob's data satisfies the protocol's own staleness bound.

Alice pays only her own normal gas/transaction cost for a call she wanted to make anyway; Bob's legitimate transaction — which touches only Bob's own position — is forced to fail solely because of Alice's unrelated, earlier-ordered transaction writing into the shared feed-timestamp slot. This is a "position made unevaluable by a third party" pattern: the shared oracle-freshness cache is primed by one caller and silently poisons the evaluability of another caller's transaction in the same block, with no privileged access required by either party.

### Impact Explanation
This does not steal funds, but it can be used to temporarily freeze a victim's ability to `borrow`, `repay`, `collateral-add/remove`, or be liquidated (or, conversely, to force a would-be liquidator's `liquidate` transaction to revert) for the remainder of the block, by trivially/incidentally (or deliberately) submitting a fresher, otherwise-unremarkable price update ahead of the victim in the same block. Repeated or targeted use turns this into deliberate temporary freezing of a specific victim's operations, which falls under the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires two unprivileged users to submit price-augmented operations touching the same asset feed within the same block, with the attacker's payload timestamp ordered ahead of the victim's. Because Stacks transactions can be ordered by fee/nonce and both callers routinely pass fresh price-feed payloads with each operation (the pattern is used throughout `borrow`/`repay`/`liquidate`), an attacker monitoring the mempool can reliably front-run with a marginally-fresher, cheap price submission to grief a specific victim's pending transaction, or simply cause collateral collisions/failed liquidations under contention (e.g., during a liquidation race).

### Recommendation
Do not gate transaction success on a globally shared, cross-account monotonic timestamp. Either (a) validate freshness purely against `stacks-block-time - publish-time <= max-staleness` without comparing to a shared `last-update` ratchet, or (b) scope the "last accepted timestamp" state per-transaction/per-caller instead of a single map slot shared by all accounts, so that one user's fresher price submission cannot invalidate another concurrently valid submission for the same feed.

### Proof of Concept
```
Block N:
1. Bob signs tx: repay(debt-ft, amount, price-feeds=[VAA with publish-time=T1]) 
   -- T1 satisfies (stacks-block-time - T1) <= max-staleness, i.e. legitimately fresh.
2. Alice (attacker) submits: borrow(other-ft, small-amount, price-feeds=[VAA for asset X with publish-time=T2]), T2 > T1,
   ordered before Bob's tx in the block (e.g. higher fee).
   -> price-resolve sets last-update[{type,ident-X}] = T2.
3. Bob's repay executes: price-resolve for the same feed key checks (>= T1 T2) -> false
   -> ERR-ORACLE-INVARIANT, Bob's repay reverts.
Alice pays normal gas for a borrow she wanted anyway; Bob's unrelated, independently-valid transaction is forced to fail this block solely due to ordering against Alice's unrelated tx.
```

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
