### Title
Webhook signature is verified against the organization/secret selected from `repository.owner.login`, but events are dispatched to stacks selected from a different, unverified field `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports configuring multiple GitHub Apps, one per organization, each with its own `webhook_secret` [1](#0-0) . When a webhook is received, `WebhooksController#verify_signature` picks which app/secret to verify the HMAC signature with, based on `repository_owner`, which is read straight out of the untrusted, not-yet-verified JSON body [2](#0-1) [3](#0-2) . Once the signature check passes, the event handlers determine *which stacks to act on* using a completely different payload field: `repository.full_name` [4](#0-3) . The HMAC signature is computed over the *entire* raw body, but because the secret used to check it is selected using `repository.owner.login`, an attacker who legitimately knows the webhook secret for Organization A's GitHub App can sign a payload whose `repository.owner.login` is `"OrgA"` (to select the correct/known secret) while `repository.full_name` is set to `"OrgB/some-repo"` (to target a stack belonging to a completely different, unauthorized organization/repository).

### Finding Description
- `Shipit.github(organization:)` supports a per-organization configuration schema, where each org has its own `webhook_secret` [1](#0-0) .
- `WebhooksController#verify_signature` resolves `repository_owner` from the payload (`repository.owner.login`, falling back to `organization.login`) *before* the signature has been verified, and uses it purely to decide which app's secret to check the signature against: `Shipit.github(organization: repository_owner)` [2](#0-1) [3](#0-2) .
- The signature comparison itself is a normal HMAC-SHA1 comparison of the whole raw body against that selected secret [5](#0-4) . This part is sound in isolation: it does prove the body wasn't tampered with by someone who doesn't know that particular secret.
- The problem is that **downstream event handlers never re-check `repository.owner.login`/organization** - they resolve the target repository/stacks purely from `repository.full_name`, via `Handler#repository_name` and `Handler#stacks` [4](#0-3) , and via similar code in the pull-request handlers (`Repository.from_github_repo_name(params.repository.full_name)`) [6](#0-5) .
- So the equality the code implicitly assumes is: `organization used to select/verify webhook_secret == organization that owns the repository acted upon`. That equality is never enforced. An attacker only needs to control `repository.owner.login` independently of `repository.full_name` within the same signed body, which is trivial since they compute the HMAC themselves knowing OrgA's secret.

Concretely, someone who is a legitimate GitHub App/organization admin for one organization configured in Shipit (OrgA) - and thus knows OrgA's `webhook_secret` - is an "unprivileged attacker" with respect to any other organization (OrgB) configured in the same Shipit instance. They can:
1. Craft a `push` (or `status`, `check_suite`, `pull_request`, etc.) webhook JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/some-repo"`.
2. Sign it with OrgA's known `webhook_secret` and set the `X-Hub-Signature` header accordingly.
3. POST it to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature.
4. `PushHandler#process` (or other handlers) resolve stacks via `repository.full_name` = `"OrgB/some-repo"` and dispatch `GithubSyncJob`/deploy-triggering side effects against OrgB's stacks [7](#0-6) .

This is a cross-organization write into another organization's Shipit stack state, bypassing the authentication binding that the per-organization webhook secret is meant to enforce.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," matching the required cross-repository-write class of impact. Concretely it allows an entity that is only authorized for OrgA's webhooks to trigger `GithubSyncJob` and other webhook-driven behaviors (push-triggered continuous delivery scheduling, status/check-run driven CI updates, `membership`/`team` mutations if `organization.login` is similarly spoofable, PR-driven review-stack provisioning) against stacks belonging to OrgB. Depending on which handler is targeted and how continuous deployment is configured on the victim stack, this can lead to unauthorized deploy triggering on OrgB's stacks - satisfying the "unauthorized deploy" impact bucket.

### Likelihood Explanation
This requires the deployment to be configured with the multi-organization GitHub App schema (multiple orgs, each with a distinct `webhook_secret`) - a supported and documented configuration [8](#0-7) . In that configuration, any organization admin who legitimately has one org's webhook secret is, by definition, in-scope as an "unprivileged attacker" relative to any other org sharing the same Shipit instance. No GitHub App private key, session, or `ApiClient` token is required - only knowledge of one org's own webhook secret, which that org's admins necessarily have to configure it in the first place.

### Recommendation
After signature verification succeeds, re-derive the acting organization strictly from the same field/source used to select the verification secret (`repository.owner.login` / `organization.login`), and cross-check it against the organization implied by `repository.full_name` before dispatching to handlers. Alternatively, restructure handlers so `stacks`/`repository_name` resolution is scoped by the already-verified `repository_owner`, rejecting any event where `repository.full_name`'s owner segment does not match `repository_owner`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret`, per the multi-org schema shown in `config/secrets.development.example.yml`.
2. As an entity that only knows `OrgA`'s `webhook_secret` (e.g., an OrgA GitHub App admin), construct a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
4. `POST /webhooks` with header `X-Github-Event: push` and the above signature.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, calls `Shipit.github(organization: "OrgA")`, and successfully verifies the signature using the attacker-known `OrgA` secret [9](#0-8) .
6. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"OrgB/victim-repo"` [4](#0-3) [10](#0-9) , enqueuing `GithubSyncJob` (and, on subsequent deploy triggers, potentially deploys) against OrgB's stack, despite the attacker never having presented any credential valid for OrgB.

**Uncertainty**: I was not able to fully trace how `organization.login` (used for `membership`/`team` events) interacts with per-organization secret selection versus this `repository.owner.login` path, nor confirm end-to-end whether `sync_github`/`GithubSyncJob` can be coerced into an actual unauthorized deploy versus only metadata sync, since that depends on stack-level continuous-deployment configuration outside the reviewed files. A full audit of `GithubSyncJob` and `Stack#sync_github` would be needed to precisely quantify the deploy-trigger impact.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
