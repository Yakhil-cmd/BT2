### Title
Cross-organization team hijack via unicity of `github_id` in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the HMAC signature matches the webhook secret configured for `repository_owner` (derived from `params['organization']['login']` for `membership` events), it never proves that the numeric `params.team.id` in the payload actually belongs to that same organization. `MembershipHandler#find_or_create_team!` looks up teams solely by `github_id`, and only assigns `organization`/`github_team` inside the `find_or_create_by!` creation block, so when a `Team` with that `github_id` already exists (e.g. owned by `shopify`), the handler silently reuses it and lets the attacker's payload mutate its membership.

### Finding Description
Binding claimed safe: `repository_owner` (the org whose secret validated the HMAC in `verify_signature`) == `Team.find_by(github_id: params.team.id).organization` (the true GitHub org owning that team). Tracing the code shows this binding is never enforced.

- `WebhooksController#repository_owner` falls back to `params.dig('organization', 'login')` when there is no `repository` key, which is exactly the shape of a `membership` event: [1](#0-0) 
- `verify_signature` resolves `Shipit.github(organization: repository_owner)` and only checks that the request HMAC matches that organization's own `webhook_secret`: [2](#0-1) [3](#0-2) . This proves only that the request was signed by whichever organization's secret was used - i.e. it proves `repository_owner` authored the request, not that `params.team.id` belongs to `repository_owner`.
- `MembershipHandler#find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id)`, and only sets `team.organization = params.organization.login` in the block that runs **only when a new record is created**: [4](#0-3) . If a `Team` row with that `github_id` already exists (belonging to a different, legitimate organization such as `shopify`), the existing row is returned untouched and its `organization` field is never compared against `params.organization.login`.
- `process` then calls `team.add_member(member)` / `team.members.delete(member)` on whatever team object was returned, using the `member.login` from the attacker-controlled payload: [5](#0-4)  and `Team#add_member` unconditionally appends the member: [6](#0-5) .

Exploit flow: an attacker who legitimately administers a GitHub organization "attacker-org" that has been onboarded onto this multi-tenant Shipit instance (and therefore knows/controls that org's own `webhook_secret`, since org admins configure the webhook URL+secret on GitHub's side) sends a correctly-signed `membership` webhook with `organization.login = "attacker-org"` but `team.id` set to the `github_id` of an existing `shopify`-owned `Team`, and `member.login` set to their own GitHub handle. `verify_signature` passes because it only checks the attacker-org secret. `find_or_create_team!` finds the pre-existing `shopify` team by `github_id` and returns it unchanged. `process` then adds the attacker as a member of that `shopify` team.

Existing guards do not catch this: `verify_signature` never cross-checks `team.id` against `repository_owner`; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not organization ownership: [7](#0-6) ; and `Team#organization` is a plain string column with no uniqueness constraint tying it to `github_id` at lookup time.

### Impact Explanation
An attacker can add themselves (or any arbitrary GitHub login) to a `Team` record that belongs to a different, victim organization, purely by forging a webhook signed with their own org's secret. If that victim team is one of the teams referenced by `Shipit.github_teams` (used for authorization, e.g. `User#authorized?`), this is a cross-tenant authorization escalation: the attacker's account gains membership in a privileged team without ever being a real GitHub member of the victim org or team. This matches the "escalation into `Shipit.github_teams` authorization" / "a payload for one repository (organization) mutating another's ... team" impact category. The attack is repeatable against any team whose numeric `github_id` the attacker can discover or guess, and is not limited to a single victim org - any onboarded org's members can target any other onboarded org's teams this way.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-tenant, i.e. configured with more than one GitHub organization in `secrets.github` (`Shipit.github_organizations`), each with its own `webhook_secret`; the attacker must administer (or have webhook-secret access to) at least one such onboarded organization - a realistic scenario for a shared/hosted Shipit deployment serving multiple orgs. The attacker also needs to know or brute-force the numeric `github_id` of the victim team (these are sequential, small GitHub team IDs, and often discoverable via GitHub's public API or UI). No Shipit session, API token, or victim-org secret is required. Cost is a single crafted HTTP POST with a valid HMAC computed from the attacker's own known secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after finding (or creating) the `Team`, verify that `team.organization.casecmp?(params.organization.login)` (and ideally that `repository_owner`/`params.organization.login` matches the team's actual organization) before allowing any membership mutation; reject/no-op the event with a 422 or drop it silently if the organization does not match the team's recorded organization. More generally, `verify_signature` should ensure the organization asserted in the payload used to authorize the write matches every entity the payload subsequently mutates.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative, no live GitHub)
test ":membership from a different org cannot hijack another org's team" do
  # Precondition: two onboarded orgs each with their own webhook_secret,
  # e.g. "shopify" (owns shipit_teams(:shopify_developers)) and "attacker-org".
  attacker_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret)
  victim_team = shipit_teams(:shopify_developers)

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'mallory' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  post :create, body: payload, as: :json

  assert_response :ok
  # Binding check: repository_owner ('attacker-org') != victim_team.organization ('shopify')
  assert_not_equal 'attacker-org', victim_team.reload.organization
  # Yet the shopify-owned team was mutated by an attacker-org-signed request:
  assert_includes victim_team.members.map(&:login), 'mallory'
end
```
This demonstrates the request returns 200 and mutates the `shopify`-owned `Team`'s membership despite the signature only proving `attacker-org`'s authenticity, confirming the binding `repository_owner == team.organization` is not enforced.

      return true unless webhook_secret
