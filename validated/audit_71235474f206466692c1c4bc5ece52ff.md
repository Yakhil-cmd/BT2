### Title
Unguarded `throw Error()` on attacker-controllable private-payment fields crashes the node instead of rejecting the payment - (File: `validation.js`)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` treats several conditions on the private, fixed-denomination transfer path as "should never happen" invariants and enforces them with `throw Error(...)` instead of returning a normal validation error through `callback()`. These fields are populated from `objValidationState.src_coin`, which is built in `indivisible_asset.js` `validatePrivatePayment()` directly from attacker-suppliable private-payment-chain data (`objPrevPrivateElement.output`, `prev_hidden_output.amount`) without first confirming the value types match what the throwing code assumes. This mirrors the CVE-2023-53683 bug class: a `WARN_ON()`/assert used on values that come from crafted, untrusted input, producing a kernel/process crash instead of a controlled rejection.

### Finding Description
`validatePaymentInputsAndOutputs()` handles private fixed-denomination asset transfers specially because the source output cannot be looked up in the database (the whole chain is validated before anything is saved): [1](#0-0) 

```
if (objAsset && objAsset.is_private && objAsset.fixed_denominations){
    if (!objValidationState.src_coin)
        throw Error("no src_coin");
    var src_coin = objValidationState.src_coin;
    if (!src_coin.src_output)
        throw Error("no src_output");
    if (!isPositiveInteger(src_coin.denomination))
        throw Error("no denomination in src coin");
    if (!isPositiveInteger(src_coin.amount))
        throw Error("no src coin amount");
```

`objValidationState.src_coin` is populated earlier, in the private-payment-chain validator, straight from the private element supplied over the wire by the sending peer: [2](#0-1) 

```
var src_output = objPrevPrivateElement.output;
var prev_hidden_output = objPrevPrivateElement.payload.outputs[input.output_index];
if (!prev_hidden_output)
    return callbacks.ifError("no prev hidden output");
input_address = src_output.address;
try {
    spend_proof = objectHash.getBase64Hash({
        asset: payload.asset,
        unit: input.unit,
        message_index: input.message_index,
        output_index: input.output_index,
        address: src_output.address,
        amount: prev_hidden_output.amount,
        blinding: src_output.blinding
    });
}
...
objValidationState.src_coin = {
    src_output: src_output,
    denomination: payload.denomination,
    amount: prev_hidden_output.amount
};
```

Prior to this assignment there is no check that `prev_hidden_output.amount` is a positive integer, nor that `src_output`/`payload.denomination` conform to the shapes later assumed by the `throw` guards in `validatePaymentInputsAndOutputs`. `objPrivateElement`/`objPrevPrivateElement` originate from a private payment chain received via a device message (`private_payments`) and dispatched by `wallet.js`'s `handlePrivatePaymentChains`, i.e. content fully controlled by the sending peer (a "private-payment counterparty" — explicitly an in-scope actor per the analog rules).

Whenever any of these guard conditions is violated (e.g. `prev_hidden_output.amount` is `0`, negative, a non-integer, `null`, or otherwise malformed while other constraints such as spend-proof/address matching are satisfiable, or the code path is reached with a shape the author did not anticipate), the code raises an uncaught JavaScript exception rather than calling `callback(...)`. Because this happens inside asynchronous callback chains (`async.forEachOfSeries`), the exception is not caught by any local `try/catch` and propagates to the top of the event loop, triggering the process-wide `uncaughtException` handler, which explicitly **re-throws to crash the process**: [3](#0-2) 

```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	console.error('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

This is the direct analog of the hfsplus `WARN_ON()` bug: a defensive assertion meant for "impossible" internal states is placed on a path reachable with attacker-crafted data, and its failure mode is a full crash instead of a graceful, per-unit rejection.

### Impact Explanation
A malicious private-payment counterparty (or a malicious device peer initiating `private_payments`) can send a hand-crafted private-payment chain that reaches the private fixed-denomination transfer branch with a bogus `amount`/`denomination`/`src_output` shape, causing the receiving node's process to crash via the unguarded `throw`. Because `handleMessageFromHub`/`handlePrivatePaymentChains` runs inside the node process handling wallet/hub messages, this results in denial of service to the targeted node (wallet or hub), which can disrupt validation and confirmation of new units for that node — matching the "network unable to confirm new units" impact category. Repeatable crashes on every reconnect/resend of the malicious payload amount to a persistent DoS against the targeted node.

### Likelihood Explanation
The attack requires no special privileges beyond being a paired/correspondent device capable of sending a `private_payments` message (a normal wallet interaction) or being a hop in a private, fixed-denomination-asset payment chain. Constructing a payload with an out-of-range `amount` value is straightforward; the harder part is passing `validateSpendProof` (which checks a hash of the sent fields against a stored value), which constrains what the attacker can freely forge for transfers already reflected in earlier public units. This reduces certainty about the easiest concrete trigger, and full confirmation would require tracing every call path that populates `src_coin.amount`/`denomination` to determine whether any of them can supply a non-positive-integer or missing value while still passing `validateSpendProof` and other upstream checks. This uncertainty is noted explicitly, since a live analysis session (not available here) would be needed to construct or rule out a working PoC end-to-end.

### Recommendation
- Replace all `throw Error(...)` invariant checks in the private-asset transfer branch of `validatePaymentInputsAndOutputs()` (`validation.js:2416-2424`, and similarly `2299`, `2451`, `2458`) with calls to `cb(...)`/`callback(...)` that report a normal validation error, so malformed/unexpected data results in unit/payment rejection rather than a process crash.
- In `indivisible_asset.js` `validatePrivatePayment()`, explicitly validate `prev_hidden_output.amount` (positive integer), `payload.denomination` (positive integer), and the shape of `src_output` (valid address, valid blinding) before assigning them into `objValidationState.src_coin`, returning `callbacks.ifError(...)` on failure.
- Audit the `uncaughtException` handler in `network.js` to ensure crash-on-invariant-violation is never triggerable purely from untrusted peer input; internal invariant failures should be logged and the offending unit/message rejected without terminating the process.

### Proof of Concept
Conceptual (full working PoC not verified in this analysis, flagged as uncertain):
1. Attacker acts as a paired device/correspondent and initiates a private payment for a fixed-denomination private asset, or is an intermediate holder resending a private-payment chain via a `private_payments` device message (`wallet.js` → `handlePrivatePaymentChains`).
2. Attacker crafts one `objPrivateElement` in the chain whose `payload.outputs[output_index].amount` is `0`, negative, or a non-integer value (or otherwise causes `objValidationState.src_coin.amount`/`denomination`/`src_output` to fail the `isPositiveInteger`/truthiness checks), while keeping other fields consistent enough to pass `validateSpendProof`/`validateSourceOutput`.
3. The targeted node processes the chain through `parsePrivatePaymentChain` → `validatePrivatePayment` → `validation.validatePayment` → `validatePaymentInputsAndOutputs`, hits the `throw Error("no src coin amount")` (or a sibling `throw`) inside an `async.forEachOfSeries` callback.
4. The exception is uncaught, bubbles to `process.on('uncaughtException')` in `network.js`, which re-throws and terminates the node process — denial of service.
