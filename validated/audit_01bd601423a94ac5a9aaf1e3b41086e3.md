### Title
Hardcoded attestor addresses inside asset `issue_condition`/`transfer_condition` cannot be updated after asset creation, risking permanent freezing of asset issuance/transfers - (File: `validation.js`, `definition.js`)

### Summary
When an asset is defined, its `issue_condition` and `transfer_condition` oscript expressions may embed an `attested` operator that hardcodes a fixed list of trusted attestor addresses directly in the condition. Unlike the asset-level `attestors`/`spender_attested` mechanism, which has a dedicated `asset_attestors` message that lets the definer update the trusted attestor list after the fact, conditions embedded in `issue_condition`/`transfer_condition` are set once at asset definition time and have no corresponding update message. If the party controlling the hardcoded attestor address needs to migrate to a new address (key rotation, compromise, organizational change — analogous to a third-party contract "upgrading" its address), the asset's issue/transfer condition becomes permanently unsatisfiable by the legitimate current attestor.

### Finding Description
Asset definitions are validated once in `validateAssetDefinition`, where `issue_condition`/`transfer_condition` are validated as address-definition-style oscript via `Definition.validateDefinition(conn, payload.issue_condition/transfer_condition, ..., bAssetCondition=true, cb)`. [1](#0-0) 

Inside such conditions, the `attested` operator can hardcode a specific array of attestor addresses that must have attested the relevant address for the condition to pass: [2](#0-1) 

At evaluation time (during every payment carrying this asset), the condition is checked strictly against those hardcoded attestor addresses via `filterAttestedAddresses`, with no notion of "current" vs "historical" attestor identity beyond the addresses baked into the condition: [3](#0-2) [4](#0-3) 

By contrast, the separate `spender_attested`/`attestors` field on an asset is explicitly designed to be updatable after asset creation: the definer can publish an `asset_attestors` message to change the trusted attestor list without redefining the asset. [5](#0-4) 

There is no equivalent update path for `issue_condition` or `transfer_condition` — these fields are part of the immutable `assets` table row created once by the `asset` message and are never mutated afterward. [6](#0-5) 

Thus a definer who embeds `['attested', [address, [attestorAddr1, ...]]]` in `issue_condition`/`transfer_condition` (rather than relying on the mutable `attestors` list) permanently commits the asset's spendability to those exact addresses, exactly mirroring the External Report's pattern of an allowance/permission being fixed once at creation with no subsequent update mechanism for the underlying trusted party's address.

### Impact Explanation
If the entity behind the hardcoded attestor address in `issue_condition`/`transfer_condition` needs to change its address (compromised key requiring migration to a fresh address, internal reorganization, or any other reason it can no longer operate from that specific address), no future issuance or transfer that depends on satisfying that condition can ever succeed again, because:
- The condition is baked into the immutable `assets` table row and re-validated on every relevant payment via `evaluateAssetCondition`.
- There is no `asset`-definition-update message analogous to `asset_attestors` for `issue_condition`/`transfer_condition`.

This permanently freezes the affected asset's issuance/transfer path for all legitimate holders, since the only way to "fix" it is to issue an entirely new asset (equivalent to redeploying the `Marketplace` contract in the original report), which does not carry over existing balances or asset identity.

### Likelihood Explanation
This requires the asset definer to have chosen to embed attestor addresses directly inside `issue_condition`/`transfer_condition` rather than using the dedicated `attestors`/`spender_attested` mechanism — a legitimate and reachable configuration choice available to any unprivileged asset issuer via the standard `asset` message. No special privileges beyond posting a normal asset-definition unit are required to create this situation, and any real-world need for the attestor to rotate its address (a routine security practice) triggers the freeze.

### Recommendation
- Discourage or disallow embedding raw attestor addresses via `attested` inside `issue_condition`/`transfer_condition`; instead, document and encourage use of the asset-level `spender_attested`/`attestors` mechanism, which already supports updates via `asset_attestors`.
- Alternatively, extend `checkAttestorList`/`validateAttestorListUpdate`-style update capability to conditions referencing attestors, or provide a way to reference "attestors" indirectly (e.g., an alias resolved at evaluation time) so that address rotation does not require asset redefinition.

### Proof of Concept
1. Definer creates an asset with `transfer_condition: ['attested', ['this address', ['ATTESTOR_ADDR_A']]]` via the `asset` message; this passes validation in `validateAssetDefinition` and is stored immutably in the `assets` table. [1](#0-0) 
2. `ATTESTOR_ADDR_A`'s controlling party rotates to a new address `ATTESTOR_ADDR_B` (e.g., after a key compromise) and continues issuing attestations from `ATTESTOR_ADDR_B`.
3. Any subsequent transfer of this asset is validated against the hardcoded condition, which still requires attestation from `ATTESTOR_ADDR_A`: [3](#0-2) 
4. Since `ATTESTOR_ADDR_A` no longer attests, `filterAttestedAddresses` returns no matches, `evaluateAssetCondition` fails, and the transfer is permanently rejected with "transfer or issue condition not satisfied" — with no message type available to update `transfer_condition` on the existing asset. [4](#0-3)
