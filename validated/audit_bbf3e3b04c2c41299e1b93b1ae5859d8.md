### Title
Any co-signer of a shared (multi-address) definition can permanently freeze all funds held at that address by unilaterally poisoning their own `address_definition_change` - ([File: definition.js])

### Summary
Ocore's `address` operator inside a definition (`["address", "OTHER_ADDRESS"]`) is evaluated dynamically: at every spend, the engine looks up the *current* active definition of the referenced address via `storage.readDefinitionByAddress`/`readDefinitionChashByAddress` rather than fixing it at the shared address's creation time. Any address can unilaterally replace its own active definition at any time using an `address_definition_change` message, which requires only that address's own signature. Because a composite/shared address's spending condition (e.g. `["and", [["address", A], ["address", B]]]`) is re-evaluated against whatever definition each member address currently has, a single co-signer can post a self-authored `address_definition_change` that sets their address's own definition to something intentionally unsatisfiable (e.g. a `sig` referencing a public key whose private key is unknown to anyone), permanently breaking the "and" branch and locking all funds at the shared address forever, with no possible remediation by the other honest co-signers.

### Finding Description
`["address", other_address]` conditions are resolved by looking up the referenced address's *live* definition rather than a definition frozen at composition time: [1](#0-0) 
The same dynamic-lookup pattern is repeated in authentifier validation: [2](#0-1) 

The current definition of an address is looked up as "the last stable, good-sequence `address_definition_change`, otherwise the address itself": [3](#0-2) 

Any address can change its own definition unilaterally with a single-authored `address_definition_change` message; the only requirement is that the new definition hashes to the declared `definition_chash`, and there is no complexity/feasibility check that the new definition can ever actually be satisfied by anyone: [4](#0-3) 

Definition validation (`case 'sig':` and friends in `definition.js`) only checks structural/syntactic validity of a `sig`/`hash` authentifier (that the pubkey/hash field is well formed) — it never verifies that the referenced key is one the address owner (or anyone) actually controls, so posting `["sig", {pubkey: <some valid but uncontrolled base64 key>}]` as a new definition is fully legal and unconditionally unsatisfiable going forward.

Consequence: if two or more parties pool funds into a shared/vault address whose definition is `["and", [["address", A], ["address", B], ...]]` (a common multisig pattern used for wallets and vault-like shared addresses), any single member (A or B) — acting entirely within their own unilateral rights over their own address — can post a self-signed `address_definition_change` that makes their branch permanently unsatisfiable. Because the shared address's spending condition is re-derived from each member's live definition at every future spend attempt, this single action permanently and irrecoverably locks the pooled funds for every other co-signer, exactly mirroring the "1 malicious/compromised operator permanently breaks functionality, with no possible remediation" bug class from the reference report (there the operator bricked a single-role privileged mapping; here a single member of an inherently multi-party financial structure bricks the group's shared address).

### Impact Explanation
This causes permanent, irreversible loss of access ("holding funds hostage") to any funds held in a shared/composite address that includes an `["address", X]` (or nested via `definition template`) branch, whenever one referenced member unilaterally redefines their address to an unsatisfiable condition. Unlike a normal N-of-M multisig where a lost key merely removes one signer's ability to co-sign (but the definition itself, once fixed, doesn't silently mutate), here the live-lookup semantics mean the *definition itself* can be weaponized post hoc by one party, without any cooperation from or override capability by the honest co-owners — matching the "DoS / holding users' funds hostage" impact and "no possible remediation" characteristic called out in the reference report.

### Likelihood Explanation
Likelihood is High for any shared/vault address that includes at least one nested `["address", X]` reference to a party that is not fully trusted (this is the standard way to build 2-of-2 or N-of-M composite wallets/vaults on top of `wallet_defined_by_addresses.js`). The attack requires only a single self-authored transaction (`address_definition_change`) from any one participant — no special privileges, no cooperation, no race condition, and it is indistinguishable from a legitimate benign key-rotation until it's fatally poisoned (funds simply become permanently unspendable through that branch).

### Recommendation
- When composing a shared/multi-party address whose security model assumes all named members remain able to sign (e.g. `and`-combined `["address", X]` branches), consider freezing/pinning the referenced definition at composition time (or offering an explicit opt-in "pinned" vs "dynamic" address reference) rather than always resolving to the live definition.
- Alternatively, require that any `address_definition_change` for an address that is referenced by outstanding shared addresses cannot reduce the address to a provably infeasible condition, or add a protocol-level "conservative" definition-change mode for members of shared addresses that requires cooperation of the other shared-address parties before taking effect.
- At minimum, document this dynamic-resolution behavior prominently for wallet integrators building multisig/vault products, since it is a foot-gun that lets a single co-signer permanently deny access to pooled funds.

### Proof of Concept
1. Address A and Address B jointly create a shared address `S` with definition `["and", [["address", A], ["address", B]]]` via `wallet_defined_by_addresses.js` (`createNewSharedAddress`), and both deposit funds into `S`.
2. B (malicious/compromised) posts a single-authored unit containing an `address_definition_change` message for its own address B, setting `definition_chash` to the hash of `["sig", {pubkey: <base64 of a valid-format but uncontrolled EC point>}]`. This passes validation per `validation.js` lines 1719-1746 because only structural correctness (`isValidAddress(payload.definition_chash)`) is checked.
3. Once this unit is stable, any future attempt to spend from `S` re-evaluates `["address", B]` by calling `storage.readDefinitionByAddress`/`readDefinitionChashByAddress`, which now returns B's new, unsatisfiable definition (`definition.js` lines 269-304, `storage.js` lines 754-768).
4. Because `S`'s definition requires `and` of both branches, and B's branch can never again produce a valid signature, `S` becomes permanently unspendable — A's honest funds are locked forever with no remediation path.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
