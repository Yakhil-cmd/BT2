### Title
API token scoped to a single stack can read CCMenu status for any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` authenticates an `ApiClient` and requires only the generic `read:stack` permission, but it resolves the target `Stack` with an unscoped lookup instead of the client's authorized stack scope, breaking the binding between "the stack(s) a token authorizes" and "the stack the endpoint actually touches."

### Finding Description
`ApiClient` tokens can be scoped to a single stack via the `stack_id` column [1](#0-0) . The intended enforcement of that scope lives in `Api::BaseController#stacks`, which restricts the queryable stacks to `current_api_client.stack_id` when the token is scoped: [2](#0-1) 

`Api::StacksController#stack` correctly reuses this scope (`stacks.from_param!(params[:id])`) [3](#0-2) .

However, `Api::CCMenuController` overrides `stack` to look up the record directly from the global `Stack` model, bypassing the client-scoped `stacks` collection entirely: [4](#0-3) 

The only authorization check performed for this endpoint is the generic permission string check `require_permission :read, :stack` [5](#0-4) , implemented by `ApiClient#check_permissions!`, which only verifies the `operation:scope` string is present in the client's `permissions` array and has no notion of which specific stack it applies to [6](#0-5) .

The binding that should hold is:
`stacks the token authorizes (current_api_client.stack_id-scoped set)` == `stack the CCMenu endpoint operates on (params[:stack_id])`

Before the (missing) fix, `Api::CCMenuController#stack` breaks this equality by resolving `params[:stack_id]` against the unscoped `Stack` model rather than against `stacks` (the client-scoped collection used everywhere else in the API), so any stack ID satisfies the lookup regardless of the token's `stack_id` restriction.

### Impact Explanation
Any holder of a valid, low-privilege `ApiClient` token that was deliberately scoped to a single stack (e.g. a CCMenu integration token created via `CCMenuUrlController`, which creates exactly this kind of scoped `read:stack` client [7](#0-6) ) can query `Api::CCMenuController#show` for an arbitrary `stack_id` and obtain that other stack's deploy/rollback status, including timestamps and running state, an unauthenticated read of stack state/deploy output that the token was never meant to access. This matches the "unauthenticated read of stack state, task streams or deploy output" High-impact category.

### Likelihood Explanation
Likelihood is high for anyone already holding a scoped API token (a routine, low-privilege artifact many integrations create, e.g. CCMenu URLs handed to CI dashboards): exploitation requires only changing the `stack_id` path parameter on a request that is otherwise fully authenticated with their own legitimate token—no additional secrets, GitHub credentials, or elevated access are needed.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the record through the client-scoped collection, consistent with `Api::StacksController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create a stack-scoped `ApiClient` restricted to `stack_id: A` with `permissions: ['read:stack']` (e.g. via `CCMenuUrlController#fetch` for stack A).
2. Using that client's `authentication_token`, call `GET /api/stacks/:stack_id/ccmenu.xml` with `stack_id` set to a different stack `B`'s id/param instead of `A`.
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes (client has `read:stack`), but `stack` resolves `Stack.from_param!(B)` directly, returning stack `B`'s CCMenu status even though the token is scoped to stack `A` only.
