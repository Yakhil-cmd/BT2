### Title
Bash-only committed changes bypass Stop-hook security review after an interrupted turn re-baselines past them - (File: `plugins/security-guidance/hooks/diffstate.py`)

### Summary
The Stop-hook review set is derived from `load_baseline_sha`/`compute_v2_review_set`, which only protects unreviewed edits from being "baselined away" when `touched_paths` is non-empty at the next `UserPromptSubmit`. Changes introduced purely through a Bash `git commit` (no `Edit`/`Write` tool call, which is what populates `touched_paths`) leave `touched_paths` empty even though a dangerous commit now sits on `HEAD`. If that turn ends without the Stop hook completing (interrupt, crash, or any of the several conditions the code already documents as unreachable-by-Stop), the following `UserPromptSubmit` re-captures a fresh `baseline_sha` at the *current* `HEAD`, silently absorbing the dangerous commit into the new baseline so it is never diffed or reviewed again.

### Finding Description
`handle_user_prompt_submit` in `security_reminder_hook.py` decides whether to overwrite `baseline_sha` by checking only `touched_paths` and the existing `baseline_sha`: [1](#0-0) 
`touched_paths` is populated by `record_touched_path`, called from the `PostToolUse[Edit/Write]` path — not from Bash. `compute_v2_review_set`'s own docstring acknowledges the gap explicitly: [2](#0-1) 

Exploit flow, using only ordinary git commands inside a cloned repo:
1. Model (or attacker-influenced content driving the model) makes a dangerous change and commits it purely via `Bash` (`git commit -am "..."`), never touching `Edit`/`Write` on that file in the same turn — this is a completely normal automation flow.
2. The turn ends before the asyncRewake Stop hook finishes (user interrupt, session end, crash, or exceeding `MAX_STOP_HOOK_FIRINGS` after other unrelated fires) — none of these require elevated privilege.
3. Because `touched_paths` is empty, the preservation guard in `handle_user_prompt_submit` does not fire on the next `UserPromptSubmit`; `capture_git_baseline` (`git stash create`/`HEAD`) captures a *new* `baseline_sha` that already includes the dangerous commit.
4. From then on, `compute_v2_review_set`'s `changed_since = _git_name_only(repo, baseline_sha)` no longer contains the dangerous file (it's part of the new baseline), and `tracked_dirty` from `git status --porcelain` is also empty (the file is committed, not dirty) — the intersection permanently excludes it, so the Stop-hook LLM review skips it.

This defeats the module's own stated invariant ("review set must stay bound to the right repo, baseline, and touched paths") because the binding relies entirely on `touched_paths`, which has a known blind spot for Bash-only commits combined with an interrupted Stop.

### Impact Explanation
A dangerous, already-committed change can permanently escape the Stop-hook's LLM security review without any special privilege — just ordinary Bash git usage plus a turn that ends before Stop completes (easily triggered by a user interrupt or normal session churn). This is a security-control bypass: the review pipeline is the mechanism meant to catch injected vulnerabilities, secrets, and unsafe patterns, and this path silently disables it for the specific commit, matching the "dangerous change treated as old and skipped" impact class.

### Likelihood Explanation
No attacker privilege beyond normal repository/tool use is required: a Bash-only `git commit` and an interrupted/incomplete turn are both ordinary occurrences (the code's own comments describe them as expected, not edge-case, behavior — "Telemetry showed a meaningful share of would-be reviews lost..."). This makes the bypass readily and repeatably reachable, not merely theoretical.

### Recommendation
Extend the preservation guard beyond `touched_paths`: also detect and preserve the baseline when `HEAD` at `UserPromptSubmit` differs from the last-consumed `head_at_capture`/reviewed SHA set (e.g., check `_load_reviewed_shas`/reflog for unreviewed commits reachable from current `HEAD`) before overwriting `baseline_sha`, so Bash-only commits are treated the same as Edit/Write-tracked changes for baseline-advance purposes.

### Proof of Concept
Integration test outline (pytest, using existing test git-repo fixtures in the plugin's test suite):
1. Init a repo with one commit; call `handle_user_prompt_submit` (turn 1) to capture `baseline_sha`.
2. Simulate a Bash-only turn: run `git commit -am "add dangerous eval()"` directly via subprocess (no `record_touched_path` call), then simulate the turn ending without `consume_stop_state`/Stop ever running (i.e., don't call the Stop handler).
3. Call `handle_user_prompt_submit` again (turn 2) and assert `preserved["value"]` is `False` and `baseline_sha` in state has moved to a SHA that already contains the dangerous commit.
4. Call `compute_v2_review_set(cwd, new_baseline_sha, ...)` and assert the dangerous file path is **absent** from the returned review set — demonstrating the invariant "the dangerous file stays reviewable" is violated.
