### Title
CCMenu API endpoint reads any stack's deploy status regardless of the requesting `ApiClient`'s stack scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` bypasses the stack-scoping enforced everywhere else in the API, letting a token that is authorized only for one stack read the deploy status of every other stack.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s authorization: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a stack, or `Stack.all` otherwise, and `stack` resolves via `stacks.from_param!(params[:stack_id])` [1](#0-0) . This is the binding that every other API controller relies on: "the stack a token authorizes" (`current_api_client.stack_id`) must equal "the stack it touches" (the record loaded by `stack`).

`CCMenuController` breaks that binding. It overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, without going through the client-scoped `stacks` collection [2](#0-1) . It still runs `require_permission :read, :stack`, which only checks that the token has the `read:stack` permission bit via `ApiClient#check_permissions!` [3](#0-2)  — that check never verifies the `stack_id` association, only the permission list. Because `require_permission` and `check_permissions!` are scope-name checks (`"read:stack"`), not object-identity checks, a per-stack-scoped client (e.g. the `here_come_the_walrus` fixture, which is bound to a single stack and carries `read:stack` [4](#0-3) ) passes the permission check for any `stack_id` param value, and `stack` then loads whatever stack ID is requested instead of being confined to `current_api_client.stack_id`.

Compare this to `StacksController`, `TasksController`, `DeploysController`, etc., which all rely on the inherited `stack`/`stacks` methods from `BaseController` and are therefore correctly scoped — this is confirmed by the test "an api client scoped to a stack will only see that one stack" [5](#0-4) . `CCMenuController` is the only controller that reimplements `stack` and drops the scoping.

### Impact Explanation
Before the bug: a stack-scoped `ApiClient` (`stack_id` set) can only read/act on that one stack via the API, matching "the stack a token authorises" = "the stack it touches".
After exploiting via the CCMenu endpoint: `GET /stacks/:any_stack_id/ccmenu.xml` with that same token returns the deploy status (last deploy/rollback id, success/failure, timestamps) of an arbitrary stack the token was never granted access to, breaking that equality. This is an unauthenticated-for-that-resource read of stack state/deploy output using credentials that were only meant to authorize a different, single stack — matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" via a stack-scope authorization bypass.

### Likelihood Explanation
Any holder of a stack-scoped API token (a common, lower-privilege credential type explicitly supported by `ApiClient.stack_id`) can trigger this by simply changing the `stack_id` route/query parameter on the CCMenu endpoint — no special access, injection, or race condition is required, only knowledge of another stack's identifier (which is often guessable/sequential or discoverable).

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped collection like every other API controller, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, reusing `BaseController#stacks`, so the `current_api_client.stack_id` restriction is enforced consistently across all API endpoints, including CCMenu.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (e.g., analogous to fixture `here_come_the_walrus`) [4](#0-3) .
2. Obtain its `authentication_token` (generated via `ApiClient#authentication_token`) [6](#0-5) .
3. Call `GET /stacks/B/ccmenu.xml?token=<token>` where `B` is a different stack the client is not scoped to.
4. `authenticate_api_client` authenticates the token successfully [7](#0-6) ; `require_permission :read, :stack` passes because the permission list contains `read:stack` regardless of `stack_id` [3](#0-2) ; `stack` then loads stack `B` unrestricted [8](#0-7) , and `show` renders `B`'s latest deploy/rollback status [9](#0-8) .
