### Title
CCMenu Controller Bypasses API Client Stack Scoping, Allowing Cross-Stack Deploy State Disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method inherited from `Shipit::Api::BaseController` and resolves the target stack directly from the unauthenticated `params[:stack_id]`, bypassing the scoping that restricts a stack-bound `ApiClient` token to only the stack it was issued for. This breaks the binding "the stack a token authorizes == the stack it touches," the exact analog of the `kick_token`/lock bug where a state guard (the listing lock / here, the `ApiClient#stack_id` scope) is enforced in one code path but silently skipped in another.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting stack lookup: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a specific stack, and `stack` resolves `params[:stack_id]` only within that restricted set. Every other API controller (`StacksController`, `DeploysController`, `TasksController`, `HooksController`, `LocksController`, etc.) inherits this method unmodified, so a stack-scoped `ApiClient` can only ever act on its own stack — this is explicitly asserted by the test "an api client scoped to a stack will only see that one stack" in `test/controllers/api/stacks_controller_test.rb`.

`CCMenuController`, however, redefines `stack` to skip the scoping entirely: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` resolves against the entire `Stack` table, ignoring `current_api_client.stack_id`. The `require_permission :read, :stack` guard only checks that the `ApiClient#permissions` array contains the literal string `read:stack`: [3](#0-2) 

It does not, and cannot, check *which* stack that permission applies to — that check only happens via the `stacks` scoping in the base controller, which `CCMenuController` does not use.

This is structurally identical to the reported bug class: a state/scope constraint (`kick_token` skipping `token.locked`; here, `CCMenuController#stack` skipping `current_api_client.stack_id`) that is enforced by the "normal" code path but forgotten in a special-cased one, letting an action operate on an object it was never authorized to touch.

### Impact Explanation
A holder of any `ApiClient` token with `read:stack` permission that is scoped to Stack A (`ApiClient#stack_id == A.id`) can call `GET /api/stacks/:stack_id/ccmenu` with `stack_id` set to any other stack B in the installation and receive B's deploy/build status (`lastBuildStatus`, `lastBuildLabel`, activity, etc.) — data the token was never authorized to read. This is an authorization-scope escalation: unauthenticated-relative-to-that-stack read of stack build/deploy state, matching the "High" impact category ("escalation ... unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
Exploitation requires only possession of any valid `read:stack`-permissioned `ApiClient` token that is bound to a specific stack (`ApiClient#stack_id` set) — a legitimate, low-privilege credential by design, not a privileged account or webhook secret. Model support for stack-scoped clients (`belongs_to :stack, optional: true`) and the existing test suite (`test/controllers/api/stacks_controller_test.rb`) confirm this scoping is a real, relied-upon security boundary elsewhere in the API; `CCMenuController` is simply the one endpoint that fails to honor it. No timing/race conditions are needed (unlike the original NEAR receipt-delay scenario), making this deterministically triggerable on every request.

### Recommendation
Remove the `stack` override in `CCMenuController` and use the inherited, scope-respecting `stack`/`stacks` methods from `BaseController` (i.e., resolve `params[:stack_id]` via `stacks.from_param!(params[:stack_id])`), so the CCMenu status is only ever returned for stacks the authenticated `ApiClient` is actually scoped to.

### Proof of Concept
1. Create/obtain an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (e.g. `ApiClient.create!(name: 'x', creator: user, permissions: ['read:stack'], stack: stack_a)`), and derive its `authentication_token`.
2. Request `GET /api/stacks/<stack_B_owner>/<stack_B_name>/<stack_B_env>/ccmenu?token=<token>` (or via HTTP Basic auth) where Stack B ≠ Stack A.
3. Observe the response returns Stack B's `lastBuildStatus`/`lastBuildLabel`/activity, even though the token is scoped to Stack A only — contrast with the same token being correctly rejected/filtered when hitting `GET /api/stacks/<stack_B_param>` (handled by `StacksController`, which uses the properly scoped `stacks` method).
