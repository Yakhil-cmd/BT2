### Title
Unbounded array allocation in oscript `split()` without a limit argument bypasses object-size checks - ([File: formula/evaluation.js])

### Summary
The `split` operator in the oscript formula evaluator, reachable by any AA trigger sender or AA author whose formula executes on trigger, converts a string into an array with `res.split(separator)` when no `limit` argument is supplied, and returns it directly as a `wrappedObject` without ever calling `isTooBigObj()`/`isTooDeeplyNestedOrHasTooManyNodes()` on the result, unlike every other place in the same evaluator that builds arrays (`array` literal case, `dictionary` literal case, `map`/`filter`/`reduce`) which explicitly call `isTooBigObj()` before returning.

### Finding Description
In `formula/evaluation.js`, the `case 'split':`/`case 'join':` branch is: [1](#0-0) 

When `limit_expr` is not provided, the code does:
```
if (!limit_expr)
    return cb(new wrappedObject(res.split(separator)));
```
with **no size/length check on the resulting array** before wrapping it and handing it back into the evaluator's data flow. Compare this to the sibling `array` literal case a few hundred lines earlier, which explicitly checks `isTooBigObj(arrItems)` both during construction and after the loop finishes: [2](#0-1) 

and to `map`/`filter`, which likewise call `isTooBigObj(retValue)` before returning the result: [3](#0-2) 

The `res` string that is split can be of length up to `MAX_AA_STRING_LENGTH` (produced e.g. via `concat`, `replace`, `join`, or directly from `trigger.data`, which is itself limited only by the unit-size limits, not `MAX_AA_STRING_LENGTH`). If an attacker crafts a string consisting largely of the separator character (e.g. thousands of commas) and calls `split(str, ",")` with no limit, the resulting JS array can have as many elements as `MAX_AA_STRING_LENGTH` allows (potentially tens of thousands of elements), all without triggering the `isTooBigObj` check that gates every other array-construction path in the evaluator.

This is structurally the same bug class as the reported vLLM issue: an unbounded `split(",")` on attacker-controlled data builds an array whose size scales with input length, bypassing the size-limiting mechanism ("`num_frames`" in vLLM, "`isTooBigObj`" in ocore) that is enforced on the equivalent "safe" code path elsewhere in the same module.

### Impact Explanation
Assigning this unbounded array to a local variable, passing it to further operations (`concat`, `map`, `join`, `foreach`), or assigning it to a state variable forces subsequent size checks (`isTooBigObj`, `MAX_STATE_VAR_VALUE_LENGTH`) to process/traverse the entire array, and any further `string_utils.cloneDeep` calls (used pervasively throughout `evaluation.js` whenever a `wrappedObject` is stored, e.g. in `local_var_assignment` and object copying) duplicate this large structure. This inflates the memory and CPU cost of processing a single AA trigger unit far beyond what the complexity/ops counters (`MAX_COMPLEXITY`, `MAX_OPS`) are designed to bound, since those counters count formula operations, not the size of data structures produced by a single operation. Because AA execution is performed by every full node when validating/executing the triggering unit, a single crafted trigger could impose disproportionate CPU/memory cost on all nodes evaluating that AA, which is a denial-of-service risk against node execution of AA responses — though it stops short of the direct fund-loss/double-spend impact categories called for by validation rules, and no other AA execution path was confirmed unaffected in the time available.

### Likelihood Explanation
Any user who can post a unit that triggers an AA using `split()` without a `limit` argument on attacker-influenced data (e.g. `trigger.data` fields concatenated into a string, then split on a common separator) can reach this code path directly — no special privileges required, matching the "AA trigger sender" actor allowed by scope rules. The AA author would need to include a `split(...)` call without limit in the AA formula for this to be exploitable per-AA, but such formulas are common and legitimate (e.g., parsing CSV-like data submitted by users), and the missing bound was clearly an oversight given the closely-analogous, correctly-guarded `array`/`map`/`filter` cases in the same file.

### Recommendation
Add an `isTooBigObj()` check (mirroring the `array` literal and `map`/`filter` cases) on the result of `res.split(separator)` in the `split` branch before wrapping it in `new wrappedObject(...)`, returning a fatal error (e.g. "split result is too big") when the check fails, regardless of whether a `limit` argument is present.

### Proof of Concept
1. Deploy an AA whose formula includes a data-feed/response step such as:
   `$parts = split(trigger.data.s, ",");`
   where `trigger.data.s` is a string field taken directly from the trigger unit's `data` payload (no re-validation of length beyond unit size limits).
2. Post a trigger unit whose `data.s` field is a string consisting of tens of thousands of comma characters (bounded only by unit size/oversize-fee limits, not by `MAX_AA_STRING_LENGTH`).
3. When the AA executes, `evaluate()` reaches the `split` case with no `limit_expr`, and calls `res.split(",")`, producing a huge array that is wrapped and returned without any `isTooBigObj` check — unlike the equivalent `array` literal / `map`/`filter` code paths that would reject an equally large object.
4. Subsequent use of `$parts` (e.g. `foreach`, `length($parts)`, assignment to a state var, or further `concat`) forces the oversized structure to be traversed/cloned by every node evaluating this AA response, imposing disproportionate per-trigger CPU/memory cost. [1](#0-0) [2](#0-1) [3](#0-2)
