### Title
Headers-commission distribution via independently-rounded percentage shares allows minting bytes above the actual commission (supply inflation) - (File: headers_commission.js)

### Summary
When a multi-authored unit specifies `earned_headers_commission_recipients`, the headers commission earned by that unit is split among the listed addresses by percentage share. Each recipient's share of the commission is rounded independently with `Math.round(full_amount * share / 100.0)` (in the JS/RAM path) and `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` (in the MySQL path), with no correction for the accumulated rounding error. Validation only guarantees that the percentage shares themselves sum to exactly 100 — it never checks that the resulting rounded byte amounts sum to the original commission amount. Because rounding is applied per-recipient rather than once with a remainder carried to a designated recipient, the total credited to `headers_commission_contributions` can exceed the actual `headers_commission` fee that was paid by the parent unit, in the same way the crowdfund's `_calculateRefundAmount()` could return more than the original contribution.

### Finding Description
`validateHeadersCommissionRecipients()` only enforces that the sum of `earned_headers_commission_share` values equals 100: [1](#0-0) 

The actual distribution then rounds each recipient's cut independently, with no reconciliation against the total commission amount, both in the RAM computation and in the MySQL/SQLite query paths: [2](#0-1) [3](#0-2) [4](#0-3) 

Because `Math.round`/`ROUND(...)` is applied to each `(full_amount * share / 100)` term separately, the sum of the rounded outputs is not guaranteed to equal `full_amount`. For example, with `full_amount = 99` and two recipients each holding a 50% share, `round(99*50/100) = round(49.5) = 50` for each recipient, yielding a total of `100` credited into `headers_commission_contributions` versus only `99` bytes actually collected as `headers_commission` on the parent unit. This is structurally identical to the reported bug class: a value split by percentage with fee/amount rounded independently in two different places, producing a reconstructed total that exceeds the original pool.

The amounts written to `headers_commission_contributions` subsequently become spendable `type: "headers_commission"` inputs, which are treated as legitimate byte inputs during unit validation and consensus (see `validatePaymentInputsAndOutputs`'s issue/transfer/hc handling and `pickDivisibleCoinsForAmount`'s treatment of `headers_commission` inputs).

### Impact Explanation
This allows an attacker who authors a multi-authored unit (an ordinary, unprivileged unit poster) to choose `earned_headers_commission_recipients` shares that deterministically bias the independent roundings upward (e.g. splitting the commission of an odd-valued or otherwise unfavorably-divisible commission across recipients with shares like 50/50 or shares that produce `.5` fractions). Every time that unit wins a headers commission award from any parent unit, the network credits more bytes in `headers_commission_contributions` than were actually paid as commission by the paying unit. Because this can be repeated unit after unit, it results in gradual, permissionless inflation of the total byte supply — a violation of the network's fixed total-supply invariant, which is a form of fund/asset accounting corruption analogous to the reported unauthorized-value bug.

### Likelihood Explanation
The bias is fully attacker-controlled: the attacker just needs to construct a multi-author unit with a chosen recipient/share list (validated only for share-sum=100, not for rounding safety) and receive headers commission from parent units with a commission size that doesn't divide evenly by the chosen shares. Headers commissions are awarded routinely as part of normal DAG operation, so the attacker can repeat this indefinitely to accumulate inflated byte balances over time.

### Recommendation
Do not round each recipient's share independently. Instead, compute all-but-the-last recipient's shares via floor/round and assign the last recipient (in sorted address order) the remainder: `amount_last = full_amount - sum(previous rounded amounts)`, guaranteeing `sum(amounts) === full_amount` exactly. Apply this consistently in both the in-memory JS path and the SQL (MySQL/SQLite) queries in `headers_commission.js`, and add a runtime consistency check enforcing that the total distributed for each payer/child pair equals `full_amount` before insertion into `headers_commission_contributions`.

### Proof of Concept
1. Construct unit `A` (multi-authored, e.g. by addresses `X` and `Y`) with `earned_headers_commission_recipients = [{address:X, earned_headers_commission_share:50}, {address:Y, earned_headers_commission_share:50}]`, satisfying `validateHeadersCommissionRecipients` (sum = 100).
2. Arrange (via normal DAG parenting, which is attacker-influenceable for units they author) for unit `A` to be the winning best child of a parent unit `P` whose `headers_commission` is an odd number, e.g. `99` bytes.
3. When `calcHeadersCommissions()` runs, both `X` and `Y` are credited `Math.round(99*50/100) = 50` bytes each in `headers_commission_contributions`, totaling `100` bytes.
4. `X` and `Y` can each later spend their `50`-byte `headers_commission` input, for a combined `100` bytes spent although `P` only paid `99` bytes of commission — one byte has been minted from nothing, and this can be repeated across many units to accumulate significant unbacked supply.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
