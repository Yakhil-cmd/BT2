## Analysis

I confirmed the code path end-to-end:

1. `PreStxOp::parse_from_tx` sets `output` purely from the **first Bitcoin output's destination address** of the pre-stx tx, with no relationship checked to the inputs that signed that same transaction: [1](#0-0) 

2. `StackStxOp::get_sender_txid` only requires that the StackStxOp's first input spends `vout == 1` of the referenced pre-stx tx — a check on which UTXO is spent, not on who the beneficiary address is: [2](#0-1) 

3. In `burnchain.rs`, the resolved `sender` fed into `StackStxOp::from_tx` is taken directly from `pre_stack_stx.output` (the attacker-chosen vout0 address), with no check that it equals any address derived from the actual signer of either transaction: [3](#0-2) 

4. `StacksChainState::process_stacking_ops` then executes the pox contract's `stack-stx` function using that `sender` as the Clarity `tx-sender` directly, with **no signature check binding this principal to any private key**: [4](#0-3) 

The `signer_key`/`max_amount`/`auth_id` arguments passed into `stack-stx` for pox-4 (via `collect_pox_4_stacking_args`) authenticate the **signer**, not the **stacker/STX owner** — `verify-signer-key-sig` in pox-4/pox-5 proves the signer authorized this specific stacker for this cycle/PoX reward slot, but does nothing to prove that `sender` (the account whose STX gets locked) ever authorized the operation with their own private key.

### The broken equality

`StackStxOp.sender` (used as `tx-sender` inside the Clarity `stack-stx` call that locks STX) is asserted to equal "the Stacks address whose private key authorized this stacking action" (AUTHORITY). In fact `sender` only equals "whatever address string the crafter of the PreStxOp Bitcoin transaction wrote into its first output," which requires **no signature or private-key proof from that address at all** — only a valid Bitcoin signature over inputs the attacker themselves controls, and a valid spend of `vout=1` (also using only the attacker's own key). Nothing in `PreStxOp::parse_from_tx`, `StackStxOp::get_sender_txid`, or `process_stacking_ops` ever requires proof that the party broadcasting these Bitcoin transactions controls the private key corresponding to the `output` address.

This matches your proposed exploit flow exactly: attacker funds and signs a `PreStxOp` tx with `output` = victim's Stacks address (attacker owns neither this address's key nor consents from the victim), spends `vout=1` of that tx (using attacker's own key) in a `StackStxOp` carrying `stacked_ustx`/`signer_key`/etc, and the chain applies `stack-stx` with `tx-sender == victim`, locking the victim's actual STX balance and directing PoX rewards to an address the attacker controls via `reward_addr` (also attacker-chosen, unrelated to the victim).

Given the audit's explicit inclusion of "craft burnchain stacking ops from their own Bitcoin inputs" as an in-scope attacker capability, and that none of `verify-not-prepare-phase`, `signer-manager-call-active`, `check-pox-lock-period`, or `verify-signer-key-grant` address *this* particular gap (they all operate on data the node already trusts as `sender`), this is a valid critical finding.

### Title
Unauthenticated `sender` in burnchain `StackStxOp` allows locking a victim's STX without their private key - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` derives the future `StackStxOp.sender` solely from the first Bitcoin output address of the pre-stx transaction, an address chosen entirely by whoever crafts that transaction and never proven to be controlled by that party's private key. `StacksChainState::process_stacking_ops` then executes the PoX contract's `stack-stx` using this unauthenticated `sender` as `tx-sender`, locking that principal's STX with no signature from the STX owner.

### Finding Description
Broken equality: `StackStxOp.sender` (used as `tx-sender` when locking STX) ≠ "Stacks address whose private key authorized the stacking action." `PreStxOp::parse_from_tx` (stack_stx.rs:106-126) sets `output` from `outputs.get(0)` with no tie to the tx's signing inputs. `StackStxOp::get_sender_txid` (stack_stx.rs:232-247) validates only that vout=1 of the pre-stx tx is spent, not who the beneficiary of vout0 is. `burnchain.rs:929-943` resolves `sender = pre_stack_stx.output` and feeds it into `StackStxOp::from_tx`. `StacksChainState::process_stacking_ops` (blocks.rs:4120-4130) runs the pox contract's `stack-stx` with `tx-sender = sender`, and `handle_stack_lockup_pox_v4`/`pox_lock_v4` (pox_4.rs) lock the corresponding account's real STX balance. The `signer_key`/`auth_id` signature check in pox-4/pox-5 authenticates the signer's grant to a stacker principal, but never requires that principal to have signed anything themselves. Attacker exploit: broadcast a self-funded `PreStxOp` with vout0 = victim address, vout1 = attacker-controlled address; then broadcast a `StackStxOp` spending vout1 (signed only with the attacker's own key) carrying `stacked_ustx`, `signer_key` (attacker's own signer), `reward_addr` (attacker-controlled). The node applies `stack-stx` with `tx-sender == victim`, locking the victim's real STX with no Stacks-level or Bitcoin-level signature from the victim.

### Impact Explanation
Any account with an unlocked STX balance can have that balance forcibly locked by an unrelated party, with PoX/BTC rewards for the cycle directed to an address the attacker (or attacker-designated signer) controls, and the account frozen for `num_cycles` reward cycles. This is theft of staking rewards plus permanent/temporary freezing of a victim's STX they never authorized to stack — Critical impact category (unauthorized locking/freezing of staked STX, rewards accruing to a party who didn't own the locked funds). Repeatable against any victim address with unlocked STX, each requiring only one Bitcoin PreStxOp + one StackStxOp pair funded by the attacker.

### Likelihood Explanation
Preconditions: victim must have an unlocked STX balance and no existing pox lock (checked by `pox_lock_v4`, not an authorization check). Attacker needs only enough BTC to fund two small burnchain-op transactions and knowledge of the victim's public Stacks address (trivially public). No special role, no signer/bond-admin/miner privilege required — fully consistent with "unprivileged attacker crafting burnchain stacking ops from their own inputs." Feasible on any epoch supporting pox-4/pox-5 burnchain-triggered `StackStxOp` processing.

### Recommendation
Require the `PreStxOp` `output` address (and therefore the derived `StackStxOp.sender`) to be cryptographically tied to the party who signs the burnchain transactions — e.g., derive `sender` from the public key(s)/`BurnchainSigner` of the transaction's own inputs rather than trusting an arbitrary output address, or require an explicit Stacks-level signed authorization (e.g., a Clarity-level allowance/consent record) before a burnchain `StackStxOp` is permitted to lock a given principal's STX.

### Proof of Concept
Rust integration test in `stack_stx.rs`/burnchain integration harness:
1. Boot a chainstate; fund attacker's BTC wallet only. Create `victim` Stacks/BTC keypair but never use victim's key to sign anything.
2. Craft and broadcast a `PreStxOp` Bitcoin tx signed only by attacker's key, with `vout0.address = victim_btc_address` (maps to `victim` Stacks address), `vout1.address = attacker_btc_address`.
3. Craft and broadcast a `StackStxOp` Bitcoin tx spending `vout1` (signed only by attacker's key) with `stacked_ustx`, `signer_key = attacker_signer_key`, `reward_addr = attacker_reward_addr`.
4. Mine blocks; process via `StacksChainState::process_stacking_ops`.
5. Assert: `victim`'s `STXBalance` (queried via `ClarityDatabase`/`get_stx_balance_snapshot`) shows `amount_locked() == stacked_ustx` and `unlock_height() > 0`, despite `victim`'s private key never signing any Stacks or Bitcoin transaction — i.e., LHS (`sender` == `victim`) diverges from RHS (party whose key authorized it == `attacker`), proving the equality is broken.
