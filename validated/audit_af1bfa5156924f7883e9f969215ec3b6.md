### Title
Cross-organization webhook forgery: `X-Hub-Signature` binds `repository.owner.login`, but every handler acts on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner` — derived solely from `params.dig('repository', 'owner', 'login')` (or `organization.login` as fallback) — while every `Shipit::Webhooks::Handlers::Handler` subclass subsequently resolves the target `Repository`/`Stack` using an entirely different, unverified field: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, so a valid HMAC computed with organization A's `webhook_secret` can carry a `repository.full_name` pointing at organization B's repository.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is read directly from the untrusted JSON body [2](#0-1) . The HMAC (`OpenSSL::HMAC.hexdigest`) only proves the raw payload bytes were signed with *that org's* secret — it says nothing about which specific fields inside that payload are "trustworthy" relative to that org.

Every event handler, however, resolves the affected `Stack`/`Repository` using `payload.dig('repository', 'full_name')`, a completely separate key from the one used to select the signing org:
- `Handler#repository_name` / `#stacks` [3](#0-2) 
- `PushHandler#process`, which calls `stack.sync_github` for any stack matching that repo/branch [4](#0-3) 
- All the pull-request handlers (`ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, etc.) which look up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/deprovision review stacks [5](#0-4) 

If Shipit is configured with multiple GitHub Apps/organizations (as the test fixtures for `secrets_double_github_app.yml` show is a supported deployment shape) [6](#0-5) , an attacker who controls a webhook delivery for organization A (e.g., they administer any repository/webhook under org A and thus know org A's `webhook_secret`) can craft a raw JSON body with `repository.owner.login = "orgA"` (satisfying the signature check) but `repository.full_name = "orgB/private-repo"` (a completely different, victim organization's stack). The signature is computed over the raw bytes with org A's secret and will validate, yet the handler acts against org B's stack.

### Impact Explanation
This breaks the trust binding "organization that authenticated" == "repository that is written." Concretely:
- `PushHandler` will enqueue `stack.sync_github(expected_head_sha: ...)` for org B's stack based on attacker-chosen `after`/`ref` values, letting an outsider (who only controls a webhook in an unrelated org) drive Github sync state for a victim org's stack.
- Pull-request handlers allow archiving/unarchiving/deprovisioning review stacks (`stack.archive!`, `stack.unarchive!`, `stack.deprovision`) belonging to org B by forging `pull_request`/`labels`/`action` payload content signed only with org A's secret.

This is a cross-repository/cross-organization write triggered purely by possessing a webhook secret for a different, lower-trust org, i.e., "cross-repository writes" as defined in the impact taxonomy.

### Likelihood Explanation
Requires the attacker to already have `webhook_secret` knowledge for at least one organization configured on the shared Shipit instance (e.g., by being a member/admin of one onboarded org, or observing a webhook payload from that org). No compromise of the victim organization's credentials is required. In single-tenant/single-org deployments this issue does not apply, but the codebase and its own test fixtures (`secrets_double_github_app.yml`) demonstrate multi-org support is an intended configuration.

### Recommendation
Bind the field used for org/secret selection to the field used for repository resolution: verify that `repository.owner.login` (used to select `webhook_secret`) matches the owner segment of `repository.full_name` before dispatching to handlers, or better, look up the `Repository`/`Stack` first and confirm its owning organization's `webhook_secret` is the one that validated the signature, rejecting the webhook otherwise.

### Proof of Concept
1. Attacker has (or creates) a webhook subscription under `orgA` (any repo they administer) and thus knows `orgA`'s `webhook_secret`.
2. Attacker crafts payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "orgA")`, validates the signature successfully against `orgA`'s secret.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github(expected_head_sha: attacker_sha)` on org B's stack, entirely bypassing org B's own webhook secret.
