### Title
AA `in_data_feed()` trusts unstable data-feed messages from units without checking `sequence==='good'` - ([File: data_feeds.js])

### Summary
`dataFeeds.dataFeedExists()` has an in-memory fast path for Autonomous Agents (`bAA===true`) that scans `storage.assocUnstableMessages` for a matching `data_feed` message and reports the condition as satisfied. Unlike its sibling function `readDataFeedValue()` (used by `data_feed()`), which explicitly filters out units whose `sequence !== 'good'`, the `dataFeedExists()` AA fast path performs no such check. This is the same bug class as CVE-2020-12244 (PowerDNS): a response/record is accepted as authoritative without validating an accompanying integrity/validity attribute that the rest of the same subsystem does check elsewhere.

### Finding Description
`dataFeedExists()` in `data_feeds.js` is reached from the oscript/AA formula evaluator via the `in_data_feed(...)` operator (`formula/evaluation.js`, case `'in_data_feed'`), which is available inside AA triggers/formulas (`bAA` flag threaded through evaluation). [1](#0-0) 

In the `bAA` branch, the function iterates `storage.assocUnstableMessages`, and for every unit checks only:
- `objUnit.bAA` (author is an AA)
- `latest_included_mc_index` bounds
- author-address intersection

It never checks `objUnit.sequence`. Compare this to the near-identical logic in `readDataFeedValue()`: [2](#0-1) 

which explicitly excludes units where `objUnit.sequence !== 'good'` before treating their `data_feed` payload as valid. The `dataFeedExists()` AA path omits this exact guard, so a unit that is unstable and whose serial/non-serial status has not yet been (or will never be) resolved to `'good'` can still cause `in_data_feed(...)` to evaluate `true`. [3](#0-2) 

### Impact Explanation
`in_data_feed()` is a primitive used inside AA formulas/triggers to gate execution paths (e.g., "only pay out if the oracle posted value X"). Because the AA fast-path in `dataFeedExists()` does not filter on `sequence==='good'`, a data-feed message originating from a unit whose final serial/non-serial status is not yet settled (or which is destined to become `final-bad`, e.g., a losing side of a double-spend/oracle-address fork) can still satisfy the condition. Since AA execution must be fully deterministic across all full nodes (the same trigger at the same mci must produce the same response everywhere), any discrepancy in how/when a given unit's `sequence` is resolved relative to the moment `dataFeedExists()` is evaluated can cause different nodes to compute different results for the same AA trigger — i.e., disagreement on AA response / state, potentially leading to fund loss or freezing at the AA, or a fork in what nodes consider the correct DAG state (nodes cannot re-converge because AA responses, once written, are part of consensus). This satisfies the "Medium/High/Critical" bar for AA fund loss/freezing or node disagreement on validity/stability required by the rules.

### Likelihood Explanation
Exploitation only requires an attacker who controls (or colludes with) an address acting as an "oracle" referenced by an AA's `in_data_feed(oracles=...)` condition, or who can arrange for two conflicting units from the same address to be posted (creating an unresolved/soon-to-be-`final-bad` unit) around the time an AA trigger executes and needs to evaluate that oracle condition. This is a normal, unprivileged unit-posting action (posting a `data_feed` message, and/or a conflicting double-spend from the oracle address) — well within the reach of an ordinary AA-trigger sender or a data-feed-posting address, no special network/hub privileges required.

### Recommendation
Add the same `objUnit.sequence !== 'good'` guard used in `readDataFeedValue()` to the `bAA` branch of `dataFeedExists()` in `data_feeds.js`, so that only units with a settled `'good'` sequence are eligible to satisfy `in_data_feed()`/`dataFeedExists()` for AA formula evaluation. Add a regression test mirroring the existing `data_feed()` tests but exercising `in_data_feed()` against an unstable, eventually-`final-bad` unit to confirm the condition now correctly evaluates to `false`.

### Proof of Concept
1. Address `ORACLE` posts unit `U1` at MCI `m` containing message `{app: 'data_feed', payload: {price: 100}}`.
2. Before `U1` stabilizes, `ORACLE` (or an accomplice) posts a conflicting/double-spending unit `U2` at the same level that will make `U1` resolve to `sequence='final-bad'` once the fork is settled.
3. An AA trigger executes at an mci where `U1` is still in `storage.assocUnstableMessages` (i.e., `latest_included_mc_index` within `[min_mci, max_mci]`) and its `sequence` is not yet `'good'`/is going to become `final-bad`.
4. The AA formula calls `in_data_feed(oracles=ORACLE, feed_name="price", feed_value>=100)`, which is routed to `dataFeeds.dataFeedExists(..., bAA=true, ...)`.
5. Because the `bAA` loop in `dataFeedExists()` never checks `objUnit.sequence`, it reports `bFound=true` from `U1`'s data even though `U1` is not (or will not remain) a valid/serial unit — allowing the AA to branch/pay out based on data that should have been rejected, and creating a scenario where other nodes evaluating the same trigger slightly later (after `U1`'s sequence is finalized as `final-bad`) would compute a different result, breaking deterministic consensus on the AA response.
