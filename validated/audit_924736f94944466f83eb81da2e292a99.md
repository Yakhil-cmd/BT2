### Title
Cross-repository CI status injection bypasses per-organization webhook trust boundary - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `WebhooksController` selects which GitHub organization's `webhook_secret` to verify a webhook against using a repository-owner field taken from the request body itself, then hands the *entire* raw JSON body to the registered event handler with no re-validation that the handler acts on the same repository whose organization was authenticated. `Shipit::Webhooks::Handlers::StatusHandler`, in particular, resolves the target `Commit` purely by SHA, with no scoping to the repository/organization that was cryptographically verified, breaking the binding "organization whose secret authenticated the request == repository being written."

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from attacker-controlled JSON, not from any fixed configuration: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) — fields inside the same untrusted body used later by handlers. Once the HMAC check passes for *that* organization's `webhook_secret`, the controller does no further validation and dispatches the raw body to the handler: [3](#0-2) 

`Shipit::Webhooks::Handlers::StatusHandler#process` then looks up commits **solely by `sha`**, with no repository/stack scoping at all: [4](#0-3) 

This differs from other handlers (`PushHandler`, `PullRequest::*`, `CheckSuiteHandler`) which at least scope lookups through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [5](#0-4) 

But even that scoping is not cross-checked against the `owner.login`/`organization.login` field used for signature-organization selection — `full_name` and `owner.login` are independent, attacker-controlled sub-fields of the same JSON object, and the code never asserts that `full_name` belongs to the organization whose secret verified the signature.

The `status` handler's outcome is directly consequential: `Commit#create_status_from_github!` creates a `Status`, which can flip `Commit#deployable?` to true and triggers continuous delivery: [6](#0-5) [7](#0-6) 

**Binding broken:** `organization authenticated by webhook_secret` ≠ `repository/commit actually written to`.
- Before the attack: only GitHub (holding a given organization's `webhook_secret`) can produce statuses/state for that organization's repositories.
- After a single crafted request: an entity that knows/controls **any one** organization's `webhook_secret` configured in this multi-tenant Shipit instance (see `docs/setup.md` "Using Multiple Github Applications", and `lib/shipit.rb#github`) can post a `status` (or forge cross-repo `push`/`check_suite` events using a mismatched `repository.full_name` vs `repository.owner.login`) payload whose `sha` matches a commit belonging to a *completely different* repository/stack, and have Shipit accept it as a legitimate CI signal for that unrelated stack.

### Impact Explanation
This is a cross-repository/cross-tenant write: an attacker who is only trusted for organization A's webhook traffic can inject a fabricated `success` CI status onto a commit that belongs to organization B's stack. If that stack has `continuous_deployment` enabled and the injected status satisfies `deployable?`/blocking-status rules, this results in Shipit automatically triggering an **unauthorized deploy** of organization B's code — matching the "Critical: unauthorized deploy" impact category. At minimum it allows tampering with another repository's CI/commit-status state and history, which the merge queue and deployability logic rely on.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control (or already legitimately possess) the `webhook_secret` of at least one GitHub organization/app that is configured on the same multi-tenant Shipit instance (a documented, supported configuration per `docs/setup.md`), and to know or guess a target commit SHA tracked by Shipit for a different stack (SHAs are visible in Shipit's UI/API and GitHub commit history, so they are not secret). No Shipit session, `ApiClient` token, or GitHub App private key is needed — only knowledge of one org's webhook secret, which is inherently a much lower trust bar than the credentials this bug class is meant to gate.

### Recommendation
- Scope every webhook handler's writes to the specific `Repository`/`Stack` resolved from the payload's `repository.full_name`, and additionally require that `full_name`'s owner segment matches the `repository_owner` value used to select the signing `webhook_secret` in `WebhooksController#verify_signature`.
- Fix `StatusHandler#process` (and any other handler that queries by bare attributes like `sha`) to filter through the authenticated repository's stacks (e.g., `stacks.joins(:commits).where(commits: { sha: params.sha })`) instead of a global `Commit.where(sha: ...)`.
- Reject webhooks where `repository.full_name`'s owner does not match `repository.owner.login`/`organization.login`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications"), each with a Stack/Repository and tracked commits.
2. Identify a commit `sha` belonging to `OrgB`'s stack (visible via Shipit's public commit history/API for that stack).
3. As an entity holding only `OrgA`'s `webhook_secret`, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<OrgB_commit_sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "full_name": "OrgA/some-repo", "owner": { "login": "OrgA" } }
}
```
signed with `HMAC-SHA1(OrgA_webhook_secret, body)` in `X-Hub-Signature`.
4. `WebhooksController#verify_signature` selects `OrgA`'s `GitHubApp` (via `repository_owner` = "OrgA") and the signature validates.
5. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches the `OrgB` commit regardless of the `OrgA` context used for authentication — and calls `create_status_from_github!`, creating an unauthorized `success` status on `OrgB`'s commit, potentially triggering continuous delivery for `OrgB`'s stack.

        def process

          end
        end
      end
