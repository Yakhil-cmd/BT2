### Title
Cross-tenant webhook forgery: organization used to verify the HMAC signature is not bound to the repository the payload mutates, allowing status/push spoofing on any other tenant's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization config (and thus the HMAC secret) used to authenticate an inbound webhook based on `repository.owner.login` (with a fallback to `organization.login`) in the JSON body, but every event handler resolves the *target* repository/stack from a completely separate payload field, `repository.full_name`. Because nothing binds these two fields together, a party who legitimately controls one organization's webhook secret can sign a payload whose `repository.owner.login` matches their own org (so the signature check passes) while `repository.full_name`/`sha` point at a different tenant's stack or commit, causing the engine to act on data it never actually authenticated for that tenant.

### Finding Description
`verify_signature` computes the verifying GitHub App using an owner/org field read straight out of the untrusted, not-yet-verified body: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up a per-organization config (secret, app id, etc.) keyed by that string, and `verify_webhook_signature` only proves that *some* configured organization's secret matches the request - it says nothing about which repository the payload is allowed to touch: [3](#0-2) [4](#0-3) 

Once the signature passes, every handler in `Shipit::Webhooks::Handlers` resolves the actual repository/stack to mutate from a *different* field, `repository.full_name`, which is never checked against `repository.owner.login`: [5](#0-4) 

`StatusHandler` is the sharpest example: it writes a CI status directly from attacker-supplied fields onto **any** commit in the database matching `params.sha`, with no scoping to the organization/repository that was actually authenticated: [6](#0-5) 

`PushHandler` similarly resolves stacks purely via `repository_name` (i.e. `repository.full_name`) and triggers a resync using an attacker-chosen `expected_head_sha`: [7](#0-6) 

This is the same bug class as the referenced report: a value used to authorize an action (`maxEarning` computed from stale `_sharedA`, here the organization whose secret authenticated the request) is not the value actually acted upon (the real, current commission/earning; here the repository/commit that gets mutated). The binding that should hold - `organization used to verify signature == organization owning the repository being written` - is never enforced.

### Impact Explanation
On a multi-tenant Shipit deployment (one process serving multiple GitHub organizations via `secrets.github` keyed by org, exactly as `Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS` supports), any organization admin who legitimately configured their own org's webhook (and therefore legitimately knows their own `webhook_secret`) can forge signed webhook deliveries that spoof CI/commit statuses (`StatusHandler`) or push events (`PushHandler`) for a completely different organization's stacks/commits, without ever obtaining that other organization's secret. Forged "success" statuses can satisfy deploy-readiness checks that gate `git.shipit.yml`-driven deploys, and forged push/resync events can desynchronize or trigger resync flows for a victim stack - this crosses the "cross-repository writes / unauthorized deploy" bar, since the write is attributed to and executed against a repository the attacker's credential was never actually verified against.

### Likelihood Explanation
Requires only a legitimately-configured, low-privilege organization's own webhook secret (something the attacker already has by design in a shared-instance/multi-org Shipit deployment) and knowledge of a target commit SHA / repository full name (both are public GitHub information, and the report's own repo listing plus Shipit's public stack pages expose full names and SHAs). No repository write access, no GITHUB_TOKEN, no Shipit session or ApiClient token is needed - only the ability to send an HTTP POST with a correctly-HMAC'd body using a secret the attacker is entitled to know for their own org.

### Recommendation
Bind the field used to select/verify the signing organization to the field used to resolve the mutated repository: after selecting `github_app` via `repository_owner`, re-derive `repository_owner` from `repository.full_name`'s owner segment (or, better, require that `repository.full_name.split('/').first == repository.owner.login`) before dispatching to handlers, and reject the request (422) on mismatch. Equivalently, thread the already-verified `repository_owner`/organization into each `Handler` and have `stacks`/`repository_name` resolution assert the found `Repository#owner` matches the verified organization, rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Attacker legitimately installs/administers Shipit for `attacker-org` and thus knows `webhook_secret_A` (the secret they configured on GitHub's webhook settings page for their own org).
2. Attacker crafts a `status` event body:
   ```json
   {
     "sha": "<victim-commit-sha>",
     "state": "success",
     "context": "ci/build",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Attacker signs the raw body with `webhook_secret_A` and sends it with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature verifies successfully against `webhook_secret_A`.
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` - writing a forged `success` status onto the victim's commit, even though the signature was only ever validated against `attacker-org`'s secret, never against `victim-org`'s.     # Backward compatibility

```ruby
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end

    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
