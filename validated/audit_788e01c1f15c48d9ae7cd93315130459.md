### Title
Webhook signature verification authenticates the payload's declared organization, not the repository the event handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to check the HMAC against by reading `repository.owner.login` (or `organization.login`) out of the still-unverified JSON body, then verifies the signature using that organization's `webhook_secret`. Once verified, `create` re-parses the same raw body and hands it to `Shipit::Webhooks.for_event(event)` handlers, which resolve the target `Stack`/`Repository` using a *different* field of the same body: `repository.full_name` (`Handler#repository_name`). Nothing ties the "owner" used to pick the verifying secret to the "full_name" used to pick the repository that is mutated.

### Finding Description [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`create` then does `params = JSON.parse(request.raw_post)` and dispatches to handlers with that same body. Handlers resolve the affected repository independently: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

The equality the app implicitly relies on is:
`organization authenticated by HMAC (repository.owner.login)` == `organization/repository actually written to (repository.full_name)`

Both values come from the same attacker-controlled JSON body, and only the first one is covered by any cryptographic check (`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb` lines 76-83). Nothing forces `repository.full_name` to belong to the org named in `repository.owner.login`. This mirrors the reported bug class exactly: one index/field (`voucherIndex`/organization used for the signature check) is validated, but a *different* index/field (`vouchees[staker][0]`/`repository.full_name` used for the actual write) is the one acted upon, with no cross-check that they refer to the same entity.

In a Shipit deployment using the documented multi-organization configuration (`config/secrets.yml` with several `github:` orgs, each with its own `webhook_secret`, as described in `docs/setup.md` "Using Multiple Github Applications"), any one of those organizations' legitimately configured GitHub Apps can produce a validly-signed webhook (signed with that org's own `webhook_secret`, which the org's admins control/know since they configured it in the GitHub App settings). That signature only proves "this body was HMAC'd with OrgA's secret" - it says nothing about which repository the body's `repository.full_name` field names. An attacker controlling OrgA's webhook secret can therefore submit a payload where `repository.owner.login = "OrgA"` (to pass `verify_signature`) but `repository.full_name = "OrgB/some-other-tracked-repo"`.

### Impact Explanation
Because handlers key off `repository.full_name` rather than the authenticated organization, this crosses a repository boundary that the per-organization webhook-secret scheme is supposed to enforce:
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) will call `stack.sync_github(expected_head_sha: params.after)` for stacks belonging to OrgB's repository, using an attacker-chosen `after` sha - a cross-organization trigger of the sync pipeline for a repository the attacker doesn't own.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb`) creates a `Status` on any `Commit` matching `params.sha` regardless of which org's secret validated the request, letting an attacker forge a passing/failing CI status on commits belonging to OrgB's stacks. If OrgB's `shipit.yml` gates deploys on `ci.require` statuses, this can be used to fabricate the CI signal that gates an otherwise-legitimate deploy - an unauthorized-deploy-adjacent primitive.
- `MembershipHandler`/`PullRequest` handlers similarly act on data (`team`, `member`, PR fields) taken from the same unauthenticated-with-respect-to-repository body.

This satisfies the "cross-repository writes" / "unauthorized deploy" bar because the org-level signature is being relied upon as a repository-level authorization boundary that it does not actually provide.

### Likelihood Explanation
Requires an unprivileged-attacker-controllable webhook secret for *some* organization already configured in the same multi-tenant Shipit instance (a documented, supported configuration - `docs/setup.md` "Using Multiple Github Applications"), not privileged access to the target org/repository being attacked. This is a plausible operating model for Shipit installations that onboard many independent teams/orgs behind one instance, each with a delegated GitHub App and their own webhook secret. The exploit is a single crafted HTTP POST to `/github/webhooks` with mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature` / `Handler#repository_name`, ensure the organization whose secret validated the signature actually owns the repository the handler is about to act on - e.g. re-derive `repository_owner` from `repository.full_name`'s owner segment (not `repository.owner.login`) for the signature check, or explicitly assert `repository.owner.login == repository.full_name.split('/').first` before dispatching, rejecting the webhook otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org example), both with tracked repositories/stacks.
2. As an attacker who knows `OrgA`'s `webhook_secret` (e.g., because they control OrgA's GitHub App settings), craft a JSON push payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker chosen sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/target-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `OrgA`'s `webhook_secret`.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` selects `Shipit.github(organization: "OrgA")` and the signature verifies successfully (per `lib/shipit/github_app.rb#verify_webhook_signature`).
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb`) and triggers `sync_github` for `OrgB`'s stack, with the attacker fully controlling `expected_head_sha` - despite never having any credential tied to `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
