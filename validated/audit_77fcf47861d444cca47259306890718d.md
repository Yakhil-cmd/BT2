### Title
API-scoped clients can bypass stack scoping via `Api::CCMenuController` to read arbitrary stacks' build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController#stack` enforces this scope by resolving stacks through `stacks.from_param!`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the client is scoped. [1](#0-0)  `Api::CCMenuController`, however, overrides `stack` to resolve the target stack directly with `Stack.from_param!(params[:stack_id])`, completely bypassing the `stacks` scoping helper. [2](#0-1) 

### Finding Description
The binding that should hold is: *the stack a token authorizes* (`current_api_client.stack_id`) *== the stack the request actually touches* (`stack` resolved in the controller). `Api::BaseController` establishes this binding for every other API resource (`StacksController`, `HooksController`, etc.) by always looking up the target stack through the `stacks` relation, which is pre-filtered to the client's `stack_id` when one is set. [1](#0-0) 

`Api::CCMenuController` requires only the generic `read:stack` permission (not scoped to any particular stack) via `require_permission :read, :stack`, and then defines its own private `stack` method that loads the stack unconditionally from `params[:stack_id]`, ignoring `current_api_client.stack_id` entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

Authentication for this endpoint accepts the same Basic-Auth API-client tokens as the rest of the API (it only adds a `params[:token]` query-string fallback before delegating to `super`, which performs the standard Basic-Auth `ApiClient.authenticate` flow). [4](#0-3)  Nothing in `require_permission` checks whether the resolved `stack` matches the authenticated client's `stack_id`; `check_permissions!` only checks the string `"read:stack"` against the client's `permissions` array. [5](#0-4) 

Route: `GET /api/stacks/*stack_id/ccmenu` maps `stack_id` from the URL directly into `params[:stack_id]`, which any authenticated caller controls. [6](#0-5) 

Before vs after the equality:
- Intended invariant (held everywhere else in `Api::BaseController`): `client.stack_id == stack.id` whenever `client.stack_id?` is true. [1](#0-0) 
- Actual behavior in `CCMenuController#show`: `stack.id` is taken from attacker-controlled `params[:stack_id]` with no comparison to `client.stack_id` at all. [7](#0-6) 

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (e.g. the `here_come_the_walrus` fixture, scoped to `stack: shipit` with only `read:stack` permission) is intended to only ever see that one stack, as enforced and tested for the rest of the API (`"an api client scoped to a stack will only see that one stack"`). [8](#0-7)  Because `CCMenuController` bypasses this scoping, the holder of such a restricted token can supply any other stack's `stack_id` in the URL and receive that stack's build/deploy status (name, last build status/label/time, web URL) rendered from `shipit/ccmenu/project`. [9](#0-8)  This is an unauthorized cross-stack read of stack state through a token that was explicitly restricted to a different repository/stack — the exact "stack a token authorizes vs. stack it touches" binding break called out in scope, qualifying as High under "unauthenticated read of stack state" analog (here: read of stack state outside the token's authorized scope).

### Likelihood Explanation
Any legitimate holder of a stack-scoped API token (a common, low-privilege credential type explicitly supported by this engine to restrict a client's blast radius) can trigger this with a single GET request, no special conditions or races required. The only prerequisite is possessing one valid, deliberately-restricted token — which is the exact class of credential this scoping mechanism exists to constrain.

### Recommendation
Have `Api::CCMenuController#stack` resolve the stack through the same scoped `stacks` helper used by `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that clients scoped to a specific stack cannot request CCMenu data for any other stack.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A: `permissions: ['read:stack']`, `stack_id: <Stack A id>` (mirrors the `here_come_the_walrus` fixture). [10](#0-9) 
2. Authenticate with this client's token via Basic Auth against `GET /api/stacks/<Stack B owner>/<Stack B name>/<Stack B env>/ccmenu` (Stack B being unrelated to Stack A).
3. `authenticate_api_client` succeeds (valid Basic-Auth token), `require_permission :read, :stack` passes because the client has the `read:stack` permission string regardless of which stack. [11](#0-10) 
4. `stack` resolves to Stack B via `Stack.from_param!(params[:stack_id])`, bypassing the `stack_id`-based restriction that would apply everywhere else in the API. [12](#0-11) 
5. Response renders Stack B's name, last build status/label/time and web URL — data the token was never authorized to access. [9](#0-8)

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end
