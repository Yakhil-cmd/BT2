### Title
Unauthenticated Race Condition on Shared Global `lightBatch` Buffer in AA Dry-Run Execution - ([File: aa_composer.js])

### Summary
`aa_composer.dryRunPrimaryAATrigger()` is exposed to any connected light client via the unauthenticated `light/dry_run_aa` network command [1](#0-0) . When the node is running in light mode (`conf.bLight`), the function does **not** allocate a fresh kvstore batch per invocation as it does for full nodes; instead it reuses a single module-level `lightBatch` object shared across all concurrent calls: [2](#0-1) 

```js
function dryRunPrimaryAATrigger(trigger, address, arrDefinition, onDone) {
	...
	var batch = conf.bLight ? lightBatch : kvstore.batch();
	...
	handleTrigger({
		bDryRun: true, ...
		onDone: function () {
			revertResponsesInCaches(arrResponses);
			batch.clear();
			conn.query("ROLLBACK", function () {
				conn.release();
				onDone(arrResponses);
			});
		},
	});
}
```

Unlike `handleAATriggers()`, which serializes execution behind `mutex.lock(['aa_triggers'], ...)` [3](#0-2) , `dryRunPrimaryAATrigger()` acquires no mutex whatsoever. Nothing prevents two `light/dry_run_aa` requests (or a `light/dry_run_aa` request racing with `conf.bDryRunNewTriggers` dry-runs triggered from `handleJoint`'s `ifOk` callback, see `network.js` lines 1271-1281) from executing concurrently and interleaving writes to and `clear()` calls on the very same `lightBatch` instance.

### Finding Description
`handleTrigger()` performs its kvstore-side effects (AA state-var writes, storage-size bookkeeping, etc.) against the `batch` object passed in via `trigger_opts.batch` [4](#0-3) . For light clients this is always the same singleton `lightBatch`, never a per-call batch. Because Node's event loop interleaves the asynchronous `db.query`/`conn.query` callbacks used throughout `handleTrigger`, `readLastStableMcUnit`, `insertFakeOutputsIntoMcUnit`, and the formula evaluator, two concurrently in-flight `dryRunPrimaryAATrigger()` calls (e.g., triggered by two different unprivileged peers/light clients sending `light/dry_run_aa`, or one peer sending it twice back-to-back) will accumulate their pending kvstore ops into the *same* buffer.

The race manifests exactly like the CVE-2026-44693 analog: a shared, unsynchronized global buffer that is read/written/cleared from multiple concurrent "sessions" (here, AA dry-run evaluation contexts) without any locking. Concretely:
- Call A begins a dry run for AA `X` and starts writing pending batch ops (state var puts) for `X` into `lightBatch`.
- Before A finishes, call B begins a dry run for AA `Y` and also writes into the same `lightBatch`.
- Whichever call's `onDone` fires first executes `batch.clear()`, wiping out the *other* call's still-pending, unflushed batch operations.
- Because `revertResponsesInCaches(arrResponses)` (which walks `storage.assocUnstableUnits` to undo speculative unit insertions from *that* call's `arrResponses`) is called by each dry run independently but they all share process-wide caches and the same batch, this also risks removing responses/units that belong to a different concurrent dry-run session, corrupting the accounting one call reports back to its own caller.

### Impact Explanation
This does not directly move real funds, since `dryRunPrimaryAATrigger` always performs `conn.query("ROLLBACK", ...)` and the underlying SQL side-effects for each call are contained in the SQL transaction of that call's own `conn`. However, the impact analogous to session hijacking is on the **kvstore batch buffer and cross-call state bleed**:
- One caller's dry-run response can be computed against a `lightBatch` state that has been mutated (or wiped) by a concurrent, unrelated dry-run request from a different peer — producing incorrect `arrResponses` (wrong balances/state var values/bounced flags) returned to the requester, i.e., cross-contamination between unrelated, unprivileged sessions.
- If `handleTrigger`'s kvstore reads (via `storage.readAAStateVar`, which is expected to reflect pending batch writes for correctness within a single dry run) observe operations queued by a *different* concurrent dry run, an attacker could manipulate the outcome of a victim's dry-run estimate, or crash the node via unexpected/inconsistent batch state (`throw Error` paths exist throughout `handleTrigger` on invariant violations, e.g., "balance overflow" or storage assertions), leading to a node-wide denial of service.
- Because `light/dry_run_aa` is available with no authentication and no rate/serialization control, any unprivileged light client (or the AA-trigger dry-run path fired automatically from `handleJoint`) can trigger this race repeatedly and reliably by issuing rapid concurrent requests referencing different AAs.

### Likelihood Explanation
High for triggering the race (trivial — send two or more concurrent `light/dry_run_aa` requests referencing different AA addresses; no special privileges, keys, or timing precision beyond normal network jitter are required), but the exact reliably-reproducible corruption/crash outcome depends on the specific interleaving of async callbacks inside `handleTrigger`, `readLastStableMcUnit`, and the formula evaluator, so the severity of the visible symptom (wrong dry-run numbers vs. thrown assertion/DoS) will vary run to run.

### Recommendation
Allocate a fresh kvstore batch per call to `dryRunPrimaryAATrigger()` regardless of `conf.bLight`, i.e., replace `var batch = conf.bLight ? lightBatch : kvstore.batch();` with an unconditional `var batch = kvstore.batch();`, or otherwise serialize all `dryRunPrimaryAATrigger()`/`estimatePrimaryAATrigger()` invocations behind a dedicated `mutex.lock([...])` the same way `handleAATriggers()` is serialized via `mutex.lock(['aa_triggers'], ...)`.

### Proof of Concept
1. Run an ocore light node with the `light/dry_run_aa` command enabled (default for light-vendor-serving nodes).
2. From an unauthenticated client connection, rapidly send two (or more) concurrent `light/dry_run_aa` requests for two different AA addresses `X` and `Y` that each perform several async state-var reads/writes (to widen the race window), e.g., AAs with multiple `state` blocks and remote AA reads.
3. Observe that responses for `X` and/or `Y` intermittently contain incorrect `updatedStateVars`/`balances`, or that the node throws an unexpected error (e.g., "AA not found?", balance/storage assertion failures) sourced from `handleTrigger`, demonstrating that the shared `lightBatch` state from one dry-run session bled into or was cleared by the other's concurrent execution.

function handleTrigger(conn, batch, trigger, params, stateVars, arrDefinition, address, mci, objMcUnit, bSecondary, arrResponses, onDone) {
	var trigger_opts;
	if (arguments.length === 1) {
		trigger_opts = conn;
		conn = trigger_opts.conn;
		batch = trigger_opts.batch;
		trigger = trigger_opts.trigger;
		params = trigger_opts.params;
		stateVars = trigger_opts.stateVars;
		arrDefinition = trigger_opts.arrDefinition;
		address = trigger_opts.address;
		mci = trigger_opts.mci;
		objMcUnit = trigger_opts.objMcUnit;
		bSecondary = trigger_opts.bSecondary;
		arrResponses = trigger_opts.arrResponses;
		onDone = trigger_opts.onDone;
		// extra options:
		// trigger_opts.bAir
		// trigger_opts.assocBalances
		if (!!trigger_opts.bAir !== !!trigger_opts.assocBalances)
			throw Error("assocBalances and bAir do not match");
