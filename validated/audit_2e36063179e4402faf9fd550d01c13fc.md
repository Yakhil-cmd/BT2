### Title
Non-network-aware signed message validation checks only the genesis definition, not the current one — stale/rotated keys remain valid forever - ([File: signed_message.js])

### Summary
`validateSignedMessage()` in `signed_message.js` supports two verification modes: a *network-aware* mode that binds the signature to the address's definition as of a specific `last_ball_unit` (i.e., a specific, provable chain state), and a *non-network-aware* mode used when `last_ball_unit` is absent from the signed package. In the non-network-aware branch, the code never consults the current (or any historical) on-chain definition state at all — it only checks that the caller-supplied `definition` self-hashes to the address [1](#0-0) . Because an address equals `chash160` of its **original** (genesis) definition, this check only succeeds for the original definition, and it says nothing about whether that definition is still the address's active/authoritative one. If the address owner ever rotates keys via an `address_definition_change`, a message signed with the old, now-revoked key together with the original definition will still validate successfully through this code path — exactly analogous to the reported bug where attestation user-data was bound to an identity (the TPM/issuer) but not to its current state (PCR), permitting an old/impersonated state to be accepted as valid.

### Finding Description
`validateSignedMessage(conn, objSignedMessage, address, mci, handleResult)` determines whether the message is network-aware via `var bNetworkAware = ("last_ball_unit" in objSignedMessage);` [2](#0-1) .

When `bNetworkAware` is true, the definition used for verification is read from storage at `last_ball_mci` — i.e., the actual on-chain state at a specific, attested point — via `storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, ...)` [3](#0-2) .

When `bNetworkAware` is false, `validateOrReadDefinition` takes a completely different, state-blind path:
```
else {
    if (!bHasDefinition)
        return handleResult("no definition");
    try {
        if (objectHash.getChash160(objAuthor.definition) !== objAuthor.address)
            return handleResult("wrong definition: " ...);
    } ...
    cb(objAuthor.definition, (mci >= constants.pemCurvesFixMci) ? mci : -1, 0);
}
``` [1](#0-0) 

This never queries `address_definition_changes` or `storage.readDefinitionByAddress`; it simply demands that the supplied definition hashes to the address itself, which is only possible for the address's original genesis definition. It then feeds this (potentially stale) definition straight into `Definition.validateAuthentifiers(...)` to check the signature [4](#0-3) .

Consequently, if a user rotates their address definition/keys (e.g. because the old key was compromised or is being retired) by posting an `address_definition_change`, an attacker who still holds the old private key can produce a signed message using the old (genesis) definition and omit `last_ball_unit`. The verifier has no way to know the address's key material has since changed, because it never looks at the address's current state — only at self-consistency between the supplied definition and the address. This mirrors the reported bug class: proof of identity (address, "TPM") is checked, but the required binding to current authoritative state ("PCR") is skipped when the network-aware, state-referencing field is simply omitted.

`validateSignedMessage` is invoked from `formula/evaluation.js` (implementing the oscript `is_valid_signed_package` check reachable from AA formulas) and from `wallet.js`/`validation.js` for contract/message authentication, so it is reachable by any unprivileged unit poster or AA trigger sender supplying an unsigned, non-network-aware signed package as formula input.

### Impact Explanation
Any AA or oscript logic that trusts `is_valid_signed_package`/`validateSignedMessage` to authenticate an address's authorization (e.g., gating a payout, releasing funds from an escrow AA, or authorizing a data-feed/oracle-style attestation) can be fooled by a signature produced with a **revoked** key, as long as that key belonged to the address's original (never-changed-since-genesis) definition and the caller omits `last_ball_unit`. This can lead to unauthorized approval of AA logic that was supposed to depend on the address's current signing authority (e.g., an address that revoked a compromised key still being treated as a valid signer), potentially causing AA fund loss/misdirection when the AA logic relies on `is_valid_signed_package` to gate payments.

### Likelihood Explanation
Exploitability requires: (1) an address that once had a key/definition change (a realistic, supported operation via `address_definition_change`), (2) the attacker retaining the pre-rotation private key, and (3) an AA or verifying party invoking `is_valid_signed_package`/`validateSignedMessage` without the caller enforcing `last_ball_unit` presence. Since omission of `last_ball_unit` is a normal, allowed input shape for `validateSignedMessage` (it's an optional field, not something the callee can force the signer to include), and the vulnerable code path performs no state lookup at all, the likelihood of triggering the flawed logic is straightforward for any user or AA-integration that accepts non-network-aware signed packages from third parties.

### Recommendation
In the non-network-aware branch of `validateOrReadDefinition`, do not treat "definition hashes to address" as sufficient. Additionally query the current authoritative definition_chash for the address (analogous to the network-aware path, but anchored to the verifier's/AA's own last stable state rather than none) and reject if the address has since changed its definition, or require `last_ball_unit` to always be present for any address that has ever changed its definition. At minimum, document/enforce that `is_valid_signed_package` callers relying on identity assurance should reject signed packages lacking `last_ball_unit` (i.e., disallow the state-blind verification mode for any address that is not provably still on its genesis definition).

### Proof of Concept
1. Address `A` is created with definition `D0` (so `chash160(D0) == A`), and the owner signs and shares an `is_valid_signed_package`-style authorization built with `signMessage(..., bNetworkAware=false)` at some point, or more simply: an attacker who compromised the original key of `A` retains it.
2. Owner of `A` legitimately rotates keys by posting a stable `address_definition_change` unit changing `A`'s definition to `D1`.
3. Attacker crafts `objSignedMessage = { signed_message: <payload>, authors: [{ address: A, definition: D0, authentifiers: {...signed with old key...} }] }` — critically, **without** a `last_ball_unit` field.
4. `validateSignedMessage`/`is_valid_signed_package` is called on this package by an AA or contract handler. Because `bNetworkAware` is false, the code checks only `getChash160(D0) === A` (true, since `A` was originally defined by `D0`), and never consults the fact that `A`'s active definition is now `D1`; the stale signature verifies successfully [1](#0-0) .
5. Any AA logic gating an action on this verification treats the message as validly authorized by `A`'s current signer, despite the corresponding key having been revoked.
