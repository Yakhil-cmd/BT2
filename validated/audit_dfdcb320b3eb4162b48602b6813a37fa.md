### Title
Signature verified against `repository.owner.login` but handlers act on `repository.full_name` — organization authenticated ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body, then verifies the raw request body against that org's secret [1](#0-0) . Once the signature check passes, `create` dispatches the *entire* raw payload to the event handlers [2](#0-1) , and handlers resolve the target `Repository`/`Stack` using a *different* field of the same payload, `repository.full_name`, via `Handler#repository_name`/`#stacks` [3](#0-2) . Nothing enforces that `repository.owner.login` (the field the signature is checked against) matches the owner encoded in `repository.full_name` (the field actually used to locate and act on a stack).

### Finding Description
Shipit explicitly supports hosting multiple independent GitHub Apps/organizations from one instance, each with its own `webhook_secret`, keyed by organization name [4](#0-3) , as documented for multi-org setups [5](#0-4) . `Shipit.github(organization: repository_owner)` looks up the app config for whatever org name appears in the inbound payload before any authenticity check has occurred [6](#0-5) , and `verify_webhook_signature` then HMACs the raw body against that org's secret [7](#0-6) .

The binding that should hold is:
`organization whose webhook_secret validated the signature == organization owning the repository the handler subsequently writes to`

Because both values are read from the same attacker-supplied JSON body, and only the first one is covered by the signature check semantics that matter (the raw body is what's HMAC'd, but the *interpretation* of "which secret to use" and "which repo to act on" are two independent, uncorrelated payload reads), an operator running Shipit for multiple organizations creates the following gap:

- Before the attacker's request: signature verification and repository resolution both implicitly assume `repository.owner.login` and the owner segment of `repository.full_name` refer to the same org.
- After the attacker's request: an attacker who legitimately controls (or has installed the Shipit GitHub App on) Organization A knows Org A's `webhook_secret`. They can sign a payload with that secret where `repository.owner.login = "orgA"` (so `verify_signature` picks Org A's secret and passes) but `repository.full_name = "orgB/victim-repo"` (a repo/stack tracked under a completely different, unrelated organization) [8](#0-7) [9](#0-8) .

This is the same bug class as the report: a value used for authorization/verification (`info.tokenId`/`info.shares`, here "which org's secret authenticated this request") is decoupled from the value actually acted upon (the zeroed `info.tokenId`, here `repository.full_name` driving which stack/repository is mutated).

### Impact Explanation
Handlers dispatched from `create` operate on the `Stack`/`Repository` resolved from the forged `repository.full_name`, independent of which org's secret validated the request signature: e.g. `push` handling enqueues sync/deploy jobs scoped to the target stack, `status`/`check_suite` handlers create commit statuses and check runs, and `membership`/`pull_request` handlers can create teams, users, and provision or archive review stacks — all keyed off attacker-controlled `full_name`/`repository` fields in the payload rather than the org whose secret was actually verified. This lets an attacker who only controls one org onboarded to a shared, multi-org Shipit deployment inject spoofed webhook events against stacks belonging to a different organization, potentially triggering unauthorized deploys, status/check tampering, or review-stack provisioning outside their authorization boundary.

### Likelihood Explanation
This requires a Shipit instance configured with the documented multi-organization `github:` block (each org with its own `webhook_secret`) and an attacker who has legitimate access to one of those orgs (e.g., installs/administers the Shipit GitHub App there) — a realistic operational configuration explicitly supported and documented by the engine. No additional secrets, tokens, or host access are required beyond knowledge of one org's own webhook secret, which that org's own administrators legitimately hold.

### Recommendation
Cross-check that the organization used to select/verify the webhook secret is the same organization referenced by the payload fields the handlers use to resolve the target repository/stack (e.g., derive `repository_owner` and the handler's repository lookup from the same canonical field, and reject the webhook if they diverge) before dispatching to `Shipit::Webhooks.for_event`.

### Proof of Concept
1. Configure Shipit with two orgs in `config/secrets.yml`: `orgA` (attacker-controlled) and `orgB` (victim), each with a distinct `webhook_secret`, per the multi-org setup in `docs/setup.md`.
2. Attacker crafts a `push` payload body with `repository.owner.login = "orgA"` and `repository.full_name = "orgB/victim-repo"`.
3. Attacker signs the raw body with Org A's known `webhook_secret` and sets `X-Hub-Signature` accordingly.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")` and the signature check passes [8](#0-7) .
5. `create` calls `PushHandler.call(params)`; the handler resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` [3](#0-2) , acting on Org B's stack despite the signature having been verified only against Org A's secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
