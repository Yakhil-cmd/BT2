### Title
Cross-organization webhook forgery: signature verified against the wrong GitHub App secret while the acted-upon repository is taken from an untrusted, uncorrelated payload field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects *which* GitHub App's `webhook_secret` to HMAC-verify against by reading `repository.owner.login` (falling back to `organization.login`) directly out of the attacker-supplied JSON body. Separately, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler`, `StatusHandler`, etc.) resolves the actual `Repository`/`Stack` to mutate from a *different* field of the same body: `repository.full_name`. Nothing ties these two fields together, so in a multi-tenant Shipit deployment (multiple GitHub organizations, each with its own `webhook_secret`, as documented in `docs/setup.md` "Using Multiple Github Applications") an attacker who controls one onboarded organization's webhook secret can forge a signed event that is verified as belonging to their own org but acts on a completely different org's stack.

### Finding Description
`verify_signature` picks the GitHub App config for verification purely from payload data: [1](#0-0) [2](#0-1) 

Meanwhile, `Handler#repository_name`/`#stacks` resolves the target `Stack` from an independent payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` simply splits `owner/name` out of that string and looks up the matching `Repository`/`Stack` row, regardless of which organization's secret was used to authenticate the request: [4](#0-3) 

`PushHandler` then directly syncs the resolved stacks using attacker-supplied `after` (target SHA): [5](#0-4) 

Multi-organization support with per-org `webhook_secret` is an explicit, supported configuration: [6](#0-5) [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization that authenticated the request` (derived from `repository.owner.login`/`organization.login`, used to pick the HMAC secret) **≠** `organization/repository whose Stack is actually written` (derived from `repository.full_name`, used by `Repository.from_github_repo_name`).

Before the attack: for a legitimate webhook, GitHub itself sets `repository.owner.login`/`full_name` consistently and signs with the secret belonging to that same organization's installed app, so the two always agree.

After the attacker's forged POST: the attacker sets `repository.owner.login` = "OrgA" (their own onboarded org, whose secret they know because they configured/created that GitHub App) while setting `repository.full_name` = "OrgB/victim-repo" (any other repository/stack hosted on the same Shipit instance). `verify_signature` computes the HMAC using OrgA's secret and validates it (the attacker signs with the same secret), but `PushHandler`/`Handler#stacks` acts on OrgB's stack.

### Impact Explanation
This allows a cross-organization write into another organization's `Stack` state on a shared Shipit instance: an attacker who only controls one onboarded organization's webhook secret can drive `stack.sync_github(expected_head_sha: ...)` for a victim organization's stack (`PushHandler`), or forge commit CI status via `StatusHandler`, for repositories they have no legitimate write access to. On stacks with `continuous_deployment: true` (a supported and common `shipit.yml` setting), this class of forged event can lead to an unauthorized deploy of an attacker-chosen commit SHA being triggered for a repository/organization the attacker does not control — matching the "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Exploitable by any actor who is an owner/administrator of one legitimately onboarded GitHub organization on a shared, multi-tenant Shipit instance (a configuration the engine documents and explicitly supports). No `ApiClient` token, no GitHub write access to the victim repository, and no compromise of the victim org's secret is required — only knowledge of the attacker's own org's `webhook_secret`, which the attacker chooses when creating their own GitHub App.

### Recommendation
`verify_signature` should not be the sole authority selecting which secret to trust; after selecting the app config from `repository_owner`, the controller (or `Handler`) must additionally assert that `repository.full_name`'s owner segment equals the `repository_owner`/`organization.login` used for signature selection, rejecting the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same authenticated organization value used for signature verification rather than trusting the payload's `full_name` field independently.

### Proof of Concept
Given a multi-org Shipit deployment with `secrets.yml` containing `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim, hosting `victim-repo`), the attacker POSTs directly to `/webhooks`:

```
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>

body = {
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },      // used by verify_signature to pick OrgA's secret
    "full_name": "OrgB/victim-repo"    // used by PushHandler to resolve the target Stack
  }
}
```

`WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and validates the HMAC successfully with the attacker's own known secret [1](#0-0) . `PushHandler#process` then resolves and mutates `OrgB/victim-repo`'s stacks using `params.after` [5](#0-4) , despite the request never having been authenticated by anything under `OrgB`'s control.
