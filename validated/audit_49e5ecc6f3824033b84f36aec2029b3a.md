### Title
Stack-scoped `ApiClient` tokens can read the CI status of any stack via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts a stack-scoped `ApiClient` to only the stack it was created for by routing every stack lookup through the `stacks` scope, but `Shipit::Api::CCMenuController` overrides `#stack` to bypass that scope entirely, letting any valid token read the CI/deploy status of any stack in the installation.

### Finding Description
The binding the engine intends to enforce is: **stack a token authorizes == stack it touches**.

`ApiClient` records can be created with an optional `stack_id`, and `BaseController#stacks` is the single choke point meant to enforce that scope: [1](#0-0) 

Every other controller that needs a stack (e.g. `StacksController#stack`) calls `stacks.from_param!(...)`, inheriting this scoping: [2](#0-1) 

`CCMenuController`, however, defines its own private `#stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, never going through `current_api_client`'s `stacks` scope: [3](#0-2) 

The only authorization check performed before `#show` runs is `require_permission :read, :stack`, which validates that the token has the `read:stack` *permission string* in its list — it never checks *which* `stack_id` the token is bound to: [4](#0-3) [5](#0-4) 

So the equality before the request: `token.stack_id == stack_id_used_for_lookup` holds for every other API controller (via `stacks.from_param!`), but for `CCMenuController` it degenerates to `stack_id_used_for_lookup == params[:stack_id]` (attacker controlled), independent of `token.stack_id`.

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (e.g. `here_come_the_walrus` fixture: `permissions: [read:stack], stack: shipit`) is meant to only ever see that one stack's state, per the exact fixtures/tests shown in `test/controllers/api/stacks_controller_test.rb` ("`#index` returns a list of stacks filtered by repo and api client"). `CCMenuController#show` breaks this containment: any holder of a `read:stack` token — however narrowly scoped — can enumerate `stack_id` params for every other stack in the Shipit instance and read its lock state, last deploy status/label, and last build time via the rendered `shipit/ccmenu/project.xml`: [6](#0-5) 

This is an authorization escalation: a credential authorized for one repository's state is used to read another repository's deploy/build state, matching the High-severity class "escalation into authorization... unauthenticated read of stack state."

### Likelihood Explanation
Exploitation requires only a valid `read:stack` `ApiClient` token (no repository write access, no GitHub credentials, no session) — the same minimal capability an unprivileged integration (e.g. the auto-created "CCMenu Client" from `CCMenuUrlController`) already holds. Any application embedding this engine and issuing scoped `ApiClient` tokens for CI dashboards is exposed by default; no misconfiguration is required beyond normal use of stack-scoped tokens.

### Recommendation
Make `CCMenuController#stack` resolve through the authorization-scoped `stacks` method (as `BaseController#stack` and `StacksController#stack` do) instead of calling `Stack.from_param!` directly, so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (e.g. fixture `here_come_the_walrus`).
2. `GET /api/stacks/B/ccmenu?token=<that client's authentication_token>` where `B` is a different stack the client was never authorized for.
3. `CCMenuController#stack` resolves `B` via `Stack.from_param!(params[:stack_id])` (bypassing the `stacks` scope), `require_permission :read, :stack` only checks the permission string and passes, and the response renders `B`'s lock/deploy status — despite the token being scoped only to `A`.
