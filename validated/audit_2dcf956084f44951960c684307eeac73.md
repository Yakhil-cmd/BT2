This confirms the vulnerability chain. The `PushHandler` (and all other handlers via `Handler#stacks`/`#repository_name`) resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, with zero relation to the organization used earlier to select the HMAC secret for signature verification. That organization is derived from `params.dig('repository', 'owner', 'login')` in `WebhooksController#repository_owner`, which is read from the same attacker-supplied, still-unverified JSON body.

### Title
Webhook signature verification keys off an attacker-controlled organization field decoupled from the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the request against using `repository_owner`, a value read out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, the handler dispatch in `create` re-parses the same raw body and hands it to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, whose base `Handler#repository_name` resolves the target `Repository` via a *different* field: `payload.dig('repository', 'full_name')`. Nothing ties these two lookups together.

### Finding Description
In a multi-org Shipit deployment (`docs/setup.md` "Using Multiple GitHub Applications"), each configured GitHub organization has its own `webhook_secret`, known to whoever administers that organization's GitHub App. [1](#0-0) 

The controller picks the secret to verify against solely from the `repository.owner.login`/`organization.login` field inside the same JSON body being verified: [2](#0-1) [3](#0-2) 

But every event handler resolves the affected `Repository`/`Stack` using `repository.full_name`, an independent field of the same body: [4](#0-3) [5](#0-4) 

Since HMAC-SHA1 covers the raw body as a whole (both fields), a valid signature only proves the sender knows *one* org's secret — it says nothing about which `full_name` appears inside. An administrator of a legitimate, low-trust organization "OrgA" configured on the Shipit instance knows OrgA's `webhook_secret` (they created the GitHub App and copied the secret into both GitHub's settings and Shipit's `secrets.yml`). That admin can craft a JSON body where `repository.owner.login` (or `organization.login`) is `"OrgA"` — so `verify_signature` authenticates with OrgA's known secret and passes — while `repository.full_name` is set to `"OrgB/some-other-repo"`, an entirely different, unrelated repository/stack hosted on the same Shipit instance. `PushHandler` (and `StatusHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) then act on `OrgB/some-other-repo` using attacker-supplied data such as `after` (target SHA) or PR/label state, `sha`/`state` for statuses, etc. [6](#0-5) 

This breaks the intended binding: `organization authenticated (via webhook_secret lookup) == repository written (via full_name lookup)`. Before the report, this equality was assumed to always hold because in a legitimate GitHub-originated webhook both fields describe the same repo; the vulnerability is that no code enforces it — an attacker fully controls both independently in the same signed body.

### Impact Explanation
Depending on the handler reached, an attacker who legitimately administers *any one* onboarded GitHub organization on a shared/multi-tenant Shipit instance can inject events attributed to a *different* organization's repository/stack:
- `PushHandler` can trigger `stack.sync_github(expected_head_sha:)` on someone else's stack with an attacker-chosen `after` SHA — influencing what commit is considered "head" for another team's deploy pipeline. [7](#0-6) 
- `StatusHandler`/`CheckSuiteHandler` can forge CI status/check-run state for commits belonging to another organization's stack, which downstream can gate whether a deploy/merge is considered safe.

This does not itself grant `GITHUB_TOKEN` exfiltration or RCE, but it is a cross-repository/cross-organization write of pipeline state achieved purely by forging a webhook body signed with a *different, unrelated* organization's secret than the one whose data is mutated — a cross-tenant integrity violation matching the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (documented as a supported configuration) and requires the attacker to control/administer one such onboarded organization's GitHub App (thus knowing its `webhook_secret`) while targeting a different organization's stack on the same instance. This is a realistic scenario for shared/multi-tenant Shipit deployments serving several orgs (e.g., subsidiaries, partner orgs, or any org onboarded with lower trust than others).

### Recommendation
After signature verification, re-validate that the organization/owner used to select the verifying secret matches the `owner` embedded in `repository.full_name` (and `organization.login` where present) before dispatching to handlers. Reject the webhook if these two identifiers diverge, e.g. compare `repository_owner` against `payload.dig('repository', 'full_name')&.split('/')&.first` and `head(422)` on mismatch in `WebhooksController#verify_signature`.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup). Attacker administers `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "attacker_chosen_sha",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `repository_owner` → `"OrgA"` → `Shipit.github(organization: "OrgA")` → verifies signature successfully using the known `OrgA` secret. [2](#0-1) 
5. `create` re-parses the body and dispatches to `PushHandler.call(params)`, whose `repository_name` reads `"OrgB/victim-repo"` and looks up/acts on `OrgB`'s stack, entirely bypassing any relation to `OrgA`. [4](#0-3)
