### Title
Cross-repo status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no repository/stack scoping, so a `status` webhook that is validly signed for the attacker's own GitHub organization/repository can write a `Status` record onto a `Commit` belonging to an entirely different (`victim`) stack whenever the two repositories happen to share a commit SHA (e.g., a fork of `victim`'s repo). This flips `Shipit::UndeployedCommit#deploy_state` from `'pending'`/`'missing'` to `'allowed'` for `victim`'s commit without the attacker ever authenticating against `victim`'s repository.

### Finding Description
The broken binding: the webhook's authorizing repository/organization (`repository_owner` used in `verify_signature`) must equal the repository whose `Commit`/`Status` records are mutated by `StatusHandler#process`. This equality is violated.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository', 'owner', 'login')`). This only proves the request came from GitHub for *some* org/repo that owns a valid webhook secret — it says nothing about which `Commit`/`Stack` records may be touched. [1](#0-0) [2](#0-1) 
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global lookup by `sha` alone across **all stacks/repositories** in the Shipit instance — there is no `stack_id`/`repository` filter tying the matched commits back to the org/repo that was authenticated in `verify_signature`. [3](#0-2) 
- Because Git commit SHAs are content-addressed, an attacker who forks `victim`'s repository (or otherwise obtains a repo sharing a commit with `victim`, e.g., via a shared merge base or cherry-pick) has, in their own fork, a commit with the exact same SHA as the one sitting in `victim`'s stack as `next_expected_commit_to_deploy`. The attacker sets a commit status (e.g., via the GitHub Status API on their own fork, which they fully control) to `success`. GitHub sends a `status` webhook, correctly signed for the attacker's own org, to Shipit.
- `verify_signature` passes (it's a legitimate signature for the attacker's own org). `StatusHandler#process` then matches `Commit.where(sha: <shared-sha>)`, which includes `victim`'s `Commit` row (same sha, different stack_id), and calls `commit.create_status_from_github!(params)` on it, creating a `Status` scoped to `victim`'s `stack_id`/`commit_id`.
- This flips `victim`'s commit's `status.state` to `success`. `Commit#deployable?` (app/models/shipit/commit.rb:227-229) becomes true if not locked/blocked, and `UndeployedCommit#deploy_state` (app/models/shipit/undeployed_commit.rb:18-31) computes `deployable? ? 'allowed' : status.state`, transitioning from `'pending'`/`status.state` (e.g. missing/unknown) to `'allowed'`. Since `continuous_deployment: true` on `victim`'s stack, `Stack#next_expected_commit_to_deploy`/`Stack#trigger_continuous_delivery` (app/models/shipit/stack.rb:210-229, 331-342) can then pick up this commit and actually deploy it — an unauthorized deploy triggered entirely from a cross-repo forged status, without the attacker ever holding `victim`'s webhook secret, session, or API token.
- None of the existing guards catch this: `verify_signature` only binds the signature to *an* org, not to the specific `Commit`/`Stack` being mutated; `drop_unhandled_event` only checks the event type; the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, etc.) has no repository field to validate against; there is no `Repository`/`Stack` equality check performed anywhere in `Commit.where(sha: ...)` or `create_status_from_github!`.

### Impact Explanation
An unprivileged attacker who controls any repository sharing a commit SHA with a victim's tracked repository (trivially achievable via a public fork) can write arbitrary CI status records onto the victim's commit, causing it to become `deployable?` / `deploy_state == 'allowed'` and, under `continuous_deployment: true`, be automatically deployed. This is "a payload for one repository mutating another's stack/commit" and can result in "an unauthorized deploy" — matching the Critical impact category. It is repeatable against any Shipit-tracked stack whose repository has, or ever will have, a fork (or any independent repo sharing a commit) — i.e., broadly exploitable across public/forkable repositories.

### Likelihood Explanation
Preconditions are attacker-cheap: fork (or otherwise obtain) a repository that shares at least one commit SHA with a Shipit-tracked repo, ensure that commit is the pending/CI-less `next_expected_commit_to_deploy` on the victim stack (`continuous_deployment: true`), then set a commit status to `success` on the attacker-owned fork via the standard GitHub Status API — no Shipit credentials, secrets, or team membership required, and GitHub sends the correctly-signed webhook on the attacker's behalf. This is realistically and repeatably exploitable.

### Recommendation
Scope commit lookup in `StatusHandler#process` (and in `verify_signature`/handler dispatch generally) to the specific repository that the webhook payload authenticated for. Concretely, resolve the `Repository`/`Stack` from `params.dig('repository', 'full_name')` (or equivalent) and filter `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` rather than matching on `sha` alone. Reject the webhook (or skip processing) if no stack for that specific repository exists.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook for one repo's sha mutates another stack's commit with the same sha" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment: true
  attacker_stack = shipit_stacks(:cyclimse) # unrelated repo/org, attacker-controlled in practice

  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'x', authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'x', authored_at: Time.now, committed_at: Time.now)

  undeployed = Shipit::UndeployedCommit.new(victim_commit, index: 0)
  refute_equal 'allowed', undeployed.deploy_state # precondition: pending/missing due to no CI

  # Simulate a validly-signed webhook for the attacker's own org/repo
  Shipit::Webhooks::Handlers::StatusHandler.new(
    OpenStruct.new(sha: shared_sha, state: 'success', context: 'ci/attacker')
  ).process

  assert_equal 'success', victim_commit.reload.status.state
  assert_equal 'allowed', Shipit::UndeployedCommit.new(victim_commit, index: 0).deploy_state
end
```
This demonstrates `deploy_state` transitioning from non-`'allowed'` to `'allowed'` on `victim`'s commit purely via a status write keyed by `sha`, without any authentication against `victim`'s repository. [3](#0-2) [4](#0-3)
