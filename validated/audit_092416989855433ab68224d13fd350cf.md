### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on unrelated, unverified `repository.full_name` / global commit-`sha` fields, enabling cross-repository/cross-organization webhook forgery in multi-GitHub-App deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the request HMAC against using only `repository.owner.login` (or `organization.login`) from the JSON body. [1](#0-0) [2](#0-1)  But the actual event handlers that mutate state select what to act on using a *different* field of the same attacker-supplied payload — `repository.full_name` in the generic `Handler#repository_name`, or, worse, an entirely global lookup by commit `sha` in `StatusHandler` with no repository scoping at all. [3](#0-2) [4](#0-3) 

This is the same bug class as the reported ERC20 issue: a value ("did this transfer succeed" / "is this signature valid for this org") is checked, but a *different*, unchecked value (the actual transfer amount/recipient / the actual repository being mutated) is what state-changing logic actually consumes.

### Finding Description
Shipit explicitly supports hosting multiple independent GitHub App installations for different organizations from a single instance (documented and tested via `test/dummy/config/secrets_double_github_app.yml`, each org with its own `webhook_secret`). [5](#0-4) 

For an incoming webhook, `Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and thus the `webhook_secret`) purely from `repository.owner.login`/`organization.login` in the untrusted JSON body: [6](#0-5) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once verified, `Webhooks.for_event(event)` handlers are invoked with the raw parsed payload — the *same* JSON object whose `repository.owner.login` was used for org selection. The generic handler base class resolves the target `Stack`s using a **separate** field, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing ties `repository.full_name` to `repository.owner.login`/the org whose secret validated the signature. Even more directly, `StatusHandler` doesn't use `repository_name`/`stacks` at all — it looks up commits **globally by SHA**, with no organization or repository scoping whatsoever: [4](#0-3) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Because the HMAC (`X-Hub-Signature`) is computed over the whole raw body and only proves "this exact JSON was signed by *some* org's secret," it proves nothing about which repository the JSON's other fields describe. An attacker who legitimately controls (or can install their own GitHub App/webhook against) **one** organization configured in this Shipit instance knows that organization's `webhook_secret`. They can craft and correctly sign a payload where:
- `repository.owner.login` = their own controlled org (so `verify_webhook_signature` succeeds using their known secret), and
- `sha` (for `status` events) or `repository.full_name` (for `push`/`check_suite` events) = data belonging to a **completely different**, victim organization/repository also hosted on the same Shipit instance.

This breaks the binding "organization that authenticated == repository that is written," analogous to the ERC20 report's unchecked-value class: the code checks one value (signature validity for org A) but acts on an unrelated, unchecked value (repo/commit belonging to org B).

### Impact Explanation
- `StatusHandler` lets the attacker forge arbitrary GitHub commit-status updates (`state`, `context`, `target_url`) on any commit hosted anywhere in the Shipit instance, purely by knowing the SHA (public information) and the webhook secret of any org they control. Forged "success" statuses can satisfy `ci.require`/`merge` gating checks for a victim's stack, contributing to an **unauthorized deploy** or unauthorized merge-queue advancement for a repository the attacker does not control — matching the report's High-impact category ("escalation into authorization... unauthorized deploy, rollback or merge").
- `PushHandler`/`CheckSuiteHandler` let the attacker trigger `sync_github`/check-run refresh actions against a victim stack's branch by supplying a forged `repository.full_name`, again a cross-repository write outside the org that actually authenticated the request.

This requires the deployment to configure more than one GitHub App/org (the multi-org schema Shipit explicitly documents and supports); it does not require any Shipit session, API token, or GitHub write access to the victim repository — only knowledge of one org's `webhook_secret` from an org the attacker legitimately administers.

### Likelihood Explanation
Any Shipit operator using the documented multi-organization GitHub App configuration is affected. An attacker needs only administrative control of one of the configured organizations (to read its `webhook_secret` from their own App/webhook settings) and knowledge of a target SHA or repository full name (both public/discoverable on GitHub). No credential theft, session, or victim-org access is required — only crafting a raw HTTP POST with a valid `X-Hub-Signature` for the attacker's own org.

### Recommendation
Do not select the verifying `webhook_secret` from the same untrusted field used later for authorization. Instead:
1. After selecting the org/app and verifying the signature, re-derive/require that the org used for verification match the org embedded in `repository.full_name` (or reject payloads where they diverge) before dispatching to handlers.
2. In `StatusHandler`, scope the `Commit` lookup by the verified repository/org (join through `Stack`/`Repository`) instead of a global `Commit.where(sha:)`.
3. More generally, ensure every handler that mutates state derives its target repository from a value that has been cross-checked against the organization whose secret validated the signature, not merely "some field in a payload that was correctly signed by someone."

### Proof of Concept
Given a Shipit instance configured with two orgs, `OrgA` (attacker-administered) and `OrgB` (victim), both known to the same instance:

1. Attacker obtains `OrgA`'s `webhook_secret` (they administer `OrgA`'s GitHub App/webhook settings).
2. Attacker finds a real commit SHA belonging to a stack tracked for `OrgB/victim-repo` (public GitHub data).
3. Attacker builds a `status` event payload:
```json
{
  "repository": { "owner": { "login": "OrgA" } },
  "sha": "<OrgB-victim-commit-sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature using `OrgA`'s secret. [6](#0-5) 
6. `StatusHandler#process` finds the commit purely by `sha` (no org check) and creates a forged status on the victim's commit. [4](#0-3) 

Note: I could not fully trace `Commit#create_status_from_github!` and `Stack#sync_github` implementation details (only found via grep, not opened in full) to confirm every downstream consequence (e.g., exact merge-queue gating logic); this should be verified with a full Devin session for complete confirmation of merge/deploy-gating impact.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
