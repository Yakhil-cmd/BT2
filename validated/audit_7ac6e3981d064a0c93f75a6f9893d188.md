### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login` while stack-mutating handlers act on `repository.full_name` — cross-organization/cross-repository webhook forgery in multi-tenant GitHub App configs - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature with, based on `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

However, the field actually used by handlers to decide *which repository/stack is mutated* is `repository.full_name`, read independently in `Handler#repository_name` / `Handler#stacks`: [3](#0-2) 

Nothing in the engine enforces that `repository.owner.login` (used to pick the verification secret) is consistent with `repository.full_name` (used to select the target `Stack`/`Repository`). Since Shipit supports one `webhook_secret` per configured GitHub organization (`Shipit.github(organization: ...)` / `github_app_config`), the signature only proves "this payload was signed by organization X's secret" — it does not prove "this payload legitimately concerns organization X's repository."

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository being acted upon`

Before the attack: an org admin/repo admin who configures a webhook for a repository in Organization A knows (or can trigger) Organization A's `webhook_secret`, because GitHub lets repository/org webhook configurators send arbitrary payloads signed with that secret to any subscribed URL, including custom `full_name`/other payload fields (many webhook UIs, and certainly a compromised/rogue app installed in Org A, allow full control of the outgoing payload). `verify_signature` only checks that the payload is signed with *some* organization's configured secret; it never checks that the `repository.full_name` inside the payload actually belongs to that organization.

After the attack: an attacker who only controls Organization A's webhook secret crafts a raw payload where `repository.owner.login` = `"orgA"` (so `verify_signature` picks Org A's key and passes) but `repository.full_name` = `"orgB/some-other-repo"` (or any repository name known to be tracked by Shipit). `Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)` using that spoofed `full_name`, and the handler acts on Org B's stack instead of Org A's. [4](#0-3) 

Concretely with `PushHandler`, an attacker in Org A can forge a `push` event whose `ref`/`after` (the target commit SHA to sync to) apply to a stack that actually belongs to Org B's repository, invoking `stack.sync_github(expected_head_sha: params.after)` on the wrong stack: [5](#0-4) 

Any other handler that only trusts `repository.full_name` (status handler, check_suite handler, pull_request handlers, label capturing) is equally exposed, since they all inherit `stacks`/`repository_name` from the same base `Handler` class.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. In a multi-organization Shipit deployment (multiple entries under `secrets.github`), a party that is trusted only for Organization A's webhooks can forge events that are processed as if they came from Organization B, causing Shipit to record/sync arbitrary commit SHAs, trigger CI-driven merge/deploy state changes, or otherwise mutate `Stack`/`Commit`/`PullRequest` records for repositories the attacker does not control — a cross-repository/cross-organization write achieved purely by manipulating unauthenticated payload content that sits outside the enforced identity check.

### Likelihood Explanation
Requires the attacker to already be a legitimate webhook configurator/administrator for at least one organization/repository onboarded into the same Shipit instance (i.e., they know or can produce a valid signature for one org's secret) — this is a real but non-trivial precondition, consistent with the "unprivileged attacker breaking a deployment-trust binding" framing rather than a fully anonymous exploit. Given that Shipit is explicitly designed to host multiple organizations behind one set of `secrets.github` webhook configs (see `Shipit.github_app_config`), the multi-tenant scenario is a supported and realistic deployment configuration, making this reachable rather than purely theoretical.

### Recommendation
After picking the organization's webhook secret and verifying the signature, re-validate that the `repository.owner.login` (or `organization.login`) actually matches the owner segment of `repository.full_name` before dispatching to handlers; reject the webhook (422) on mismatch. This closes the gap between the field used to select/verify the signing secret and the field used to select the mutated resource.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `orgA` (attacker-controlled webhook secret) and `orgB` (has a tracked repository/stack, e.g. `orgB/app`).
2. As a legitimate webhook admin for `orgA`, compute `signature = HMAC-SHA1(orgA_webhook_secret, raw_body)` for a crafted `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/app"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<signature>`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully against `orgA`'s secret. [1](#0-0) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgB/app")` (unrelated to `orgA`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `orgB`'s stack. [5](#0-4)
