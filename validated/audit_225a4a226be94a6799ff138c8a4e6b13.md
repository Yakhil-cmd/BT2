### Title
Private assets sent to an AA address become permanently stuck - ([File: aa_composer.js])

### Summary
An Autonomous Agent's on-chain balance accounting (`aa_balances`) and its trigger mechanism (`trigger.outputs`) explicitly exclude private assets. At the same time, the AA-composer refuses to let an AA construct an outgoing private-asset payment. The combination means any private asset (e.g. blackbytes) sent to an AA address can never be observed by the AA's oscript logic and can never be released back by the AA, resulting in permanently frozen funds — the same "stuck on L2 with no accounting path" pattern described in the external report, where value reaches a contract's address but is not reflected in the internal state that governs releasability.

### Finding Description
When a unit triggers an AA, `getTrigger()` builds `trigger.outputs` strictly from `message.payload.outputs` of `payment` messages that are visible in the unit: [1](#0-0) 
For private assets, however, the actual payload (amounts, recipient address, blinding) is never carried inline in the unit — it has `payload_location: 'none'` and is exchanged off-chain via private chains (see `divisible_asset.js`/`indivisible_asset.js` composition, `payload_location: objAsset.is_private ? "none" : "inline"`), so `message.payload` is not populated at validation/trigger time for a private-asset message. This means a private-asset transfer to an AA address is invisible to `getTrigger()`/`trigger.outputs`.

Separately, when an AA's balance is initialized/tracked, private assets are explicitly excluded from the persistent `aa_balances` table: [2](#0-1) 
and the same private-asset filter is embedded in the live balance update path used during trigger handling (`updateInitialAABalances`), which only inserts non-private assets into `objValidationState.assocBalances`: [3](#0-2) 

Even in the hypothetical case where an AA's oscript logic somehow learned about a private-asset balance (e.g., manually via `trigger.data` supplied by the depositor) and tried to send it back, the AA composer explicitly forbids it: [4](#0-3) 
This is because sending a private asset requires a `spend_proof` that only a device holding the private chain (blinding factors, addresses) can produce; AAs have no device/wallet counterpart to receive or possess this chain data, so they can never construct a valid outgoing private payment.

The root cause therefore mirrors the reported bug class exactly: value (private-asset tokens) can land at a contract-like address (the AA) without being reflected in the accounting structure (`aa_balances`/`trigger.outputs`) that the AA's release logic depends on, and there is no protocol-level path to ever move that value back out, because the AA composer categorically blocks outgoing private-asset payments from AAs.

### Impact Explanation
Any user (an "unprivileged unit poster" / "private-payment counterparty") who sends a private asset to an AA address — whether by mistake, by a misconfigured wallet UI, or by a malicious third party tricking a user into doing so — permanently loses those funds. The AA can never see the deposit (it's excluded from `trigger.outputs` and `aa_balances`), so no oscript logic path, however carefully written, can trigger a refund. And even a manually-informed release attempt (e.g., an auditor manually authorizing a refund via `trigger.data`) is blocked at the protocol level since AAs cannot originate private-asset payment messages. This is a direct, irreversible "AA fund loss/freezing" impact as required by the validation criteria.

### Likelihood Explanation
Likelihood is driven by user/wallet error or third-party social engineering rather than active exploitation: nothing in validation prevents a private-asset payment's hidden output address from being set to a valid AA address, and there's no explicit warning or protocol-level rejection of "private payment to AA address" the way there is for base/public payments (`checkAddressIsNotAA` in `validateAATriggerObject`, used only for dry-run/manual trigger construction, does not gate real private-payment validation flows). Given how blackbytes/private assets are used in practice (peer-to-peer, off-chain-negotiated recipients), this is a plausible, easy-to-hit failure mode, especially since AAs are ordinary-looking addresses indistinguishable from wallet addresses to a casual sender.

### Recommendation
- Add an explicit validation check that rejects any private-asset payment (public or private message.app === 'payment' with `objAsset.is_private`) whose (hidden) output address resolves to a known AA address, mirroring the existing `checkNotAAs`/`checkAddressIsNotAA` guard used for AA trigger objects, so such transfers are rejected before becoming stable and unrecoverable.
- Alternatively/additionally, surface a clear, user-facing warning in wallet software when composing a private-asset payment to an address that is registered as an AA (`aa_addresses` table), informing the user that private assets sent to AAs are non-recoverable.
- Document this limitation prominently in the AA/oscript developer documentation, similar to the "warning added" remediation in the referenced report, so AA authors and asset issuers are aware private assets sent to AAs cannot be refunded by any oscript logic.

### Proof of Concept
1. Publish an AA (any oscript logic, e.g. `sell_asset_for_bytes.oscript`), obtaining its AA address `AA_ADDR`.
2. Issue or acquire a private (indivisible or divisible, `is_private: true`) asset in a wallet, e.g. blackbytes.
3. Using the private-asset payment composer (`divisible_asset.js`/`indivisible_asset.js`), construct and post a private-asset payment whose hidden output address is `AA_ADDR` (this only requires knowing the AA's address; no special privilege is needed), and separately relay/forward the private elements chain only to yourself (or not at all — the DAG-level unit still stabilizes with a valid, hidden output assigned to `AA_ADDR`).
4. Observe that:
   - `getTrigger()`/`aa_balances` never register this deposit (per `storage.js:954-961` and `aa_composer.js:491-524`), so no oscript case in the AA can ever match on it or refund it.
   - Even if the depositor separately messages the AA operator/author with the private chain proof and asks for a manual protocol-level workaround, the AA composer's `sendUnit()` path unconditionally returns `"sending private asset from AA"` for any attempt to construct an outgoing private-asset payment (`aa_composer.js:1329-1330`), so the funds cannot be released by the AA under any circumstances.
5. The private-asset tokens are permanently and irrecoverably locked at `AA_ADDR`.
