## Analysis

The relevant bug class from the EOSLuck report — attacker exploiting predictable/manipulable on-chain "randomness" — maps directly to the `number_from_seed()` oscript function used by Autonomous Agents (AAs) to produce pseudo-random numbers from a seed.

### Root cause

`number_from_seed()` is implemented as a deterministic SHA-256 of the seed value, with no external unpredictable entropy source: [1](#0-0) 

The oscript documentation/keyword list exposes `trigger.unit`, `mc_unit`, `response_unit`, `timestamp`, and `mci` as available formula variables that AA authors commonly use as "randomness" seeds (e.g. `number_from_seed(trigger.unit, 1, 100)`), analogous to using `block.blockhash`/current timestamp for on-chain gambling contracts: [2](#0-1) 

Critically, the *trigger unit's hash is fully computed locally by the trigger sender before the unit is ever broadcast to the network*. In `composer.js`, `objUnit.unit = objectHash.getUnitHash(objUnit)` is calculated client-side, prior to the call that actually sends the joint out (`callbacks.ifOk`): [3](#0-2) 

`getUnitHash()` is a pure, deterministic function of the unit's own content (messages, timestamp, parents, authors, etc.) — nothing the network or other honest parties contribute non-deterministically: [4](#0-3) 

### Exploitation path

Because the trigger sender fully controls and can locally recompute `trigger.unit` (and other seed candidates like `timestamp`) before ever exposing the unit to the network, and because the `number_from_seed` algorithm (SHA-256 truncation to a decimal fraction) is public and simple to replicate off-chain, an attacker can:
1. Compose a candidate trigger unit for a "lottery"/gambling AA that uses `number_from_seed(trigger.unit, ...)` (or any of `mc_unit`, `timestamp`, `response_unit`) as its randomness seed.
2. Locally compute the resulting "random" outcome using the same SHA-256-based formula before broadcasting.
3. If the outcome is unfavorable, discard the unit and regenerate a new candidate (e.g., alter a message field, use a different set of parent units, add/remove a harmless data field, or wait a tick to change `timestamp`) — each variation changes the unit hash and thus the derived "random" number — repeating until a winning outcome is found, then only broadcast that specific unit.

This "seed grinding" is exactly the same bug class EOSLuck attackers exploited: an on-chain PRNG whose seed is knowable/controllable by the party who benefits from the outcome before the outcome is committed, allowing them to bias their win rate far above the intended odds — draining AA-held funds (e.g., a lottery/dice AA balance) over time.

### Title
Predictable/Grindable AA Randomness via `number_from_seed()` with Attacker-Controlled Seeds (e.g. `trigger.unit`) - (File: formula/evaluation.js)

### Summary
`number_from_seed()` derives pseudo-random numbers via a plain SHA-256 hash of a seed value. Common seed choices exposed to oscript (`trigger.unit`, `mc_unit`, `response_unit`, `timestamp`) are fully known/computable by the trigger sender before broadcasting, because the trigger unit's hash is calculated client-side in `composer.js` prior to network submission. This lets an attacker precompute the outcome of any gambling/lottery AA using such seeds and selectively broadcast only winning triggers (regenerating the unit content to "re-roll" the seed), exactly mirroring the EOSLuck predictable-RNG exploit.

### Finding Description
`evaluation.js`'s `number_from_seed` case (lines 1872-1918) hashes the seed with SHA-256 and maps the digest to a number/range — a deterministic, publicly-known transformation with no hidden entropy. Any AA that seeds this function with unit-scoped values controllable by the trigger sender (`trigger.unit`) or environment values knowable in advance (`timestamp`, `mc_unit`) effectively lets the caller pre-audit and choose the RNG result before commitment, since `objectHash.getUnitHash()` (object_hash.js:60-65) is computed locally by the composer before the unit leaves the sender's machine (composer.js:589).

### Impact Explanation
An attacker can win AA-run lotteries/games far more often than intended odds allow, draining the AA's fund balance — directly analogous to the EOSLuck loss pattern, and matching "AA fund loss" impact.

### Likelihood Explanation
Any unprivileged AA trigger sender can perform this: it requires only composing and discarding many local unit variants (cheap, local computation) before choosing which to broadcast; no special privilege, node access, or hub/peer collusion is needed. Likelihood is High for any deployed AA that follows the natural/documented pattern of seeding `number_from_seed` with trigger- or unit-derived values.

### Recommendation
Discourage/deprecate use of trigger-sender-controllable or pre-computable values (`trigger.unit`, `timestamp`, `mc_unit`, `response_unit`) as sole seeds for `number_from_seed`; document and/or enforce that secure AA randomness must combine values unknown to the trigger sender at composition time (e.g., a future stable MC unit hash not yet known at trigger-send time, or commit-reveal schemes across multiple AA responses), and add oscript-level guidance/lint warnings against seeding with attacker-predictable data.

### Proof of Concept
1. Deploy an AA whose payout logic is `if (number_from_seed(trigger.unit, 1, 100) <= 50) bounce(...) else pay_out()` (a typical dice/lottery pattern).
2. Attacker composes a trigger unit locally via `composer.js` (without broadcasting), which computes `objUnit.unit = objectHash.getUnitHash(objUnit)` client-side.
3. Attacker runs the identical SHA-256-based `number_from_seed` algorithm locally on this candidate `trigger.unit` value to predict the AA's decision.
4. If unfavorable, attacker perturbs the unit (e.g., changes an included data field or waits for `timestamp` to tick), recomputes the hash, and re-checks — repeating until a favorable result is found.
5. Attacker broadcasts only the winning unit, achieving a win rate far above the AA's intended probability.
