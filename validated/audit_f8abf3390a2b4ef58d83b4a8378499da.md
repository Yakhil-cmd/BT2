### Title
Market decimals are taken from the oracle declaration instead of the token's on-chain decimals, so a listed market can scale and value every position by a wrong power of ten - (File: contracts/governance/src/validate/asset.rs)

### Summary
The analog of the `_sharedDecimals` bug is that XOXNO Lending does not anchor a market's `asset_decimals` to the token's actual `decimals()` value when a price-aggregator oracle exists. `listed_token_decimals` prefers `oracle.asset_decimals` over the live `token_decimals`, and `validate_market_creation` then accepts `params.asset_decimals` only if it equals that oracle-declared value. The pool and controller then use `params.asset_decimals`/`feed.asset_decimals` for every token-unit ↔ RAY ↔ WAD conversion, so a mismatch systematically mis-scales transfers and mis-prices collateral and debt by a power of ten.

### Finding Description
`validate_and_fetch_token_decimals` correctly queries the token's `decimals()` at `contracts/governance/src/validate/asset.rs:15-26`. However, `listed_token_decimals` at `contracts/governance/src/validate/asset.rs:43-50` discards that value whenever a price aggregator is configured and an oracle exists for `PriceKey::Token(token)`, returning `oracle.asset_decimals` instead. `validate_market_creation` at `contracts/governance/src/validate/asset.rs:57-77` then requires `params.asset_decimals == token_decimals` — where `token_decimals` is the oracle-declared figure — and stores it in the market.

Nothing in the aggregator ties `asset_decimals` for a `Token` key to the token contract's real decimals: `asset_decimals` validation at `contracts/price-aggregator/src/validation.rs:177-185` only checks the range `MIN_ASSET_DECIMALS..=MAX_ASSET_DECIMALS`. So a token with true decimals `d` can be listed with `asset_decimals = d'` where `d' != d` and both checks pass.

All downstream arithmetic trusts the stored value:

- `contracts/pool/src/cache/scale.rs:30-47` scales deposits/borrows via `Ray::from_asset(amount, params.asset_decimals)` and `contracts/pool/src/cache/scale.rs:50-77` unscales withdrawals/debt with the same decimals.
- `contracts/controller/src/positions/liquidation/math.rs:132-137` and `:149` value repayments with `feed.asset_decimals` (`usd_value_wad` → `Wad::from_token`), and seizure legs at `:398-416` and `:460-490` convert between RAY and token units via `to_asset*`/`from_token` at `feed.asset_decimals`.

If `d' > d` (e.g., a 7-decimal token listed with `d' = 18` because the oracle declared it), every token unit is treated as `10^(d' - d)` times smaller, inflating USD valuation by that factor on deposit and debt minted at `calculate_scaled_borrow`, while `unscale_supply_floor`/`resolve_withdrawal` pay out raw units that are mis-valued in the opposite direction — an unprivileged account can borrow or liquidate against wildly mispriced collateral. If `d' < d`, valuation is deflated, which can freeze borrowing (positions instantly undercollateralized) or let `liquidate` seize collateral at a bonus calculated against an understated USD value.

### Impact Explanation
High: a mismatched decimal on a live market corrupts every valuation primitive (`usd_value_wad`, `position_value`, health factor, `min_borrow_collateral_usd`) by orders of magnitude, enabling theft of pool funds via overvalued collateral borrows or unfair liquidation seizures, or permanently breaking the market's accounting. A single unprivileged `borrow`, `withdraw`, or `liquidate` call against the affected hub asset realizes the loss.

### Likelihood Explanation
Low-to-medium: it requires a governance-executed listing where the registered oracle's `asset_decimals` for the token differs from `token.decimals()` — possible for tokens whose pricing unit is declared differently (e.g., LP-adjacent registrations, wrapped/ref-keyed listings, or oracle re-registration after a market exists), and no on-chain check enforces equality. Impact fully satisfies the theft/insolvency criteria.

### Recommendation
Enforce the actual token decimals, not the oracle-declared ones: in `validate_market_creation`, require `params.asset_decimals == validate_and_fetch_token_decimals(env, asset)` and drop the `listed_token_decimals` override for `Token` markets (or add an explicit equality check between `oracle.asset_decimals` and `token.decimals()` for `PriceKey::Token` registrations in the aggregator's `asset_decimals` validation).

### Proof of Concept
1. Governance registers an oracle for `PriceKey::Token(T)` where the token's `decimals()` returns `7`, but the oracle's stored `asset_decimals` is `18` (accepted by `asset_decimals` range check at `contracts/price-aggregator/src/validation.rs:177-185`).
2. Governance executes a market-creation op for `T` with `params.asset_decimals = 18`. `validate_market_creation` compares against `listed_token_decimals` → `18` → passes (`asset.rs:43-77`).
3. Attacker supplies `X` units of `T`; `calculate_scaled_supply` scales them as if each unit were `10^-18` whole tokens (`cache/scale.rs:30-37`), and `usd_value_wad` values the position `10^11` times higher than reality.
4. Attacker borrows another listed asset up to the inflated collateral value and withdraws; the pool is drained relative to the true collateral.
Conversely, `asset_decimals = 0` against a 7-decimal token deflates collateral value by `10^7`, letting the attacker liquidate honest suppliers' positions at a fraction of fair repayment via `liquidate`.
