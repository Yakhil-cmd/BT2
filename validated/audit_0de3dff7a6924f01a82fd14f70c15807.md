### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` in `MembershipHandler#find_or_create_team!` bypasses `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Shipit::Team` solely by `github_id`, and the block that assigns `team.organization = params.organization.login` only executes when a new record is created, never when an existing row is found. An attacker who controls their own GitHub organization webhook (and thus its signing secret) can send a `membership` event whose `team.id` collides with the `github_id` of a `Team` belonging to a completely different, unrelated organization, causing their own GitHub login to be added as a member of that foreign team without ever re-validating `team.organization == params.organization.login`.

### Finding Description
Broken binding (stated as equality): the persisted `Team#organization` column for the row being mutated must equal `params.organization.login` from the *same, signature-verified* payload — i.e. `team.organization == payload.organization.login`. This does not hold after the attack.

Code path:
1. `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , and validates the request signature against `Shipit.github(organization: repository_owner)`'s secret [2](#0-1) . Real GitHub `membership` webhooks carry no `repository` key, only `organization.login`, so the signature is verified per-organization using **the attacker's own organization's** secret, which the attacker legitimately knows since they configured that org's own Shipit webhook.
2. `MembershipHandler#find_or_create_team!` then does:
```ruby
Team.find_or_create_by!(github_id: params.team.id) do |team|
  team.github_team = params.team
  team.organization = params.organization.login
end
``` [3](#0-2) 
Because `find_or_create_by!` first performs a plain `find_by(github_id:)`, if a `Team` row already exists with that `github_id` (belonging to a different organization, e.g. `"shopify"`), the block is skipped entirely — `team.organization` is never re-checked against `params.organization.login` (e.g. `"attacker-org"`).
3. `process` then calls `team.add_member(member)` [4](#0-3) , persisting a `Membership` row linking the attacker-controlled GitHub login to the victim organization's `Team`, via `Team#add_member` [5](#0-4) .

Why existing guards don't catch it: `verify_signature` only proves the payload was signed by *some* organization Shipit trusts (the attacker's own), not that the referenced `team.id` belongs to that organization [6](#0-5) . The `ExplicitParameters` schema only enforces types (`Integer` for `team.id`, `String` for `organization.login`) [7](#0-6) , not cross-field consistency. There is no unique index or validation tying `github_id` to `organization` at the model layer — the only unique index is on `[organization, slug]` [8](#0-7) , and `github_id` has no such constraint.

### Impact Explanation
`Team` membership in this engine is the backing store for GitHub-team-based authorization: `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [9](#0-8) , and `Shipit.github_teams` is resolved from configured team handles like `"Shopify/developers"` into `Team` rows via `find_or_create_by_handle` [10](#0-9) . If the attacker can identify a `Team.github_id` that matches one of those configured authorization teams (team IDs are enumerable, sequential GitHub integers with no secrecy), they can silently insert a `Membership` row linking their own GitHub login to that team, satisfying `authorized?` and gaining access to the Shipit application (repositories/stacks/deploys) that is gated behind that team, despite never being a real member of the victim's GitHub organization or team. This matches the explicitly listed High-severity category: "escalation into `Shipit.github_teams` authorization." Because the write is keyed only on a guessable integer `github_id`, it is repeatable against any tenant/organization known or guessed by the attacker, and the blast radius spans every organization sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control (or have configured) at least one GitHub organization/webhook registered with this Shipit instance so a signature-verified `membership` webhook can be sent — this is the baseline "repository/org owner" capability granted to unprivileged attackers per the threat model, requiring no Shipit session, API token, or victim secrets. The attacker must also know or guess a target `Team.github_id` that maps to a `Shipit.github_teams`-listed org/team; GitHub team IDs are small sequential integers and are not secret, making enumeration low-cost. No GitHub-side secrets, no privileged Shipit role, and no live GitHub calls are required to exploit or to reproduce in tests — `find_or_create_by!` behaves identically against a local fixture DB.

### Recommendation
In `MembershipHandler#find_or_create_team!`, do not trust an existing row purely on `github_id`; scope the lookup (and re-validate) by both `github_id` and `organization`, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, or explicitly raise/reject when a found team's `organization` differs from `params.organization.login` instead of silently reusing it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership event cannot hijack a team belonging to another organization" do
  victim_team = Shipit::Team.create!(github_id: 999, organization: "shopify", slug: "developers", name: "Developers")
  attacker_login = "evil-attacker"

  payload = {
    "action" => "added",
    "team" => { "id" => victim_team.github_id, "name" => "Evil", "slug" => "evil", "url" => "https://example.com" },
    "organization" => { "login" => "attacker-org" }, # verified org for the signed request
    "member" => { "login" => attacker_login }
  }

  Shipit::User.expects(:find_or_create_by_login!).with(attacker_login).returns(Shipit::User.new(login: attacker_login).tap(&:save!))

  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  victim_team.reload
  # Broken binding assertion: the row mutated does NOT belong to the verified payload's organization
  refute_equal payload["organization"]["login"], victim_team.organization
  # Yet the write happened anyway:
  assert victim_team.members.exists?(login: attacker_login)
end
```
This demonstrates that `find_or_create_by!(github_id:)` matched and mutated `victim_team` (organization `"shopify"`) from a payload whose verified organization was `"attacker-org"`, confirming the cross-tenant scope violation.
