### Title
Webhook signature verification checks `repository.owner.login` but handlers dispatch on `repository.full_name`, letting any onboarded GitHub org's signed webhook mutate another org's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` used to check the HMAC signature from `payload.dig('repository','owner','login')`, while `Handler#repository_name` (used by every handler, including `PushHandler`) resolves the target `Repository`/`Stack` from a *different* field, `payload.dig('repository','full_name')`. Because both fields are attacker-controlled JSON in the same request body, an attacker who controls any org onboarded to the Shipit instance (their own valid `GithubApp` + `webhook_secret`) can sign a payload whose `repository.owner.login` is their own org (passing signature verification) while `repository.full_name` names a victim repository owned by a different org, causing `PushHandler#process` to enqueue `GithubSyncJob` against the victim's `Stack`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks: `payload['repository']['owner']['login'] == owner(payload['repository']['full_name'])`.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) and uses it to pick the verifying `GithubApp`: `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
- `Handler#repository_name` and `Handler#stacks` instead resolve the target repository from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, with no reference to `repository_owner` at all. [3](#0-2) 
- `PushHandler#process` uses that mis-scoped `stacks` collection directly to enqueue `GithubSyncJob` with an attacker-supplied `expected_head_sha`: `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }`. [4](#0-3) 
- `Stack#sync_github` simply enqueues `GithubSyncJob.perform_later(stack_id: id, expected_head_sha:)`. [5](#0-4) 

Attacker request: a POST to `/webhooks` with `X-Github-Event: push`, HMAC-signed with attacker-org's own `webhook_secret`, and body:
```json
{
  "repository": { "full_name": "shopify/shipit-engine", "owner": { "login": "attacker-org" } },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
`verify_signature` calls `Shipit.github(organization: 'attacker-org')`, which succeeds because attacker signed with their own valid secret. `PushHandler` then looks up `Repository.from_github_repo_name('shopify/shipit-engine')` — the real victim repository — and enqueues `GithubSyncJob(stack_id: <shopify stack id>, expected_head_sha: <attacker sha>)`.

None of the existing guards catch this: `verify_signature` only checks that the signature is valid for *some* configured org matching `repository.owner.login`, never that this org matches the repository/stack actually being mutated; `drop_unhandled_event` and `ExplicitParameters` only validate shape, not provenance; `Repository.from_github_repo_name` performs no ownership cross-check against the authenticated org.

### Impact Explanation
The victim's `Stack` record for `shopify/shipit-engine` is mutated as a side effect of a payload authenticated for a completely different, attacker-controlled organization: `GithubSyncJob` writes to the victim `Stack` (`mark_as_accessible!`/`mark_as_inaccessible!`, `cached_deploy_spec` via `CacheDeploySpecJob`) purely in response to a forged cross-org webhook. [6](#0-5)  This is repeatable against any stack/branch combination in the installation as long as the attacker knows (or can guess/enumerate) the target `full_name`, and it applies uniformly to any multi-tenant Shipit deployment with more than one onboarded GitHub org (e.g. as illustrated by `test/dummy/config/secrets_double_github_app.yml`'s `OrgOne`/`OrgTwo` setup). The same broken binding (`repository_owner` vs `repository.full_name`) affects every other webhook handler built on `Handler#repository_name` (status, pull_request, check_suite handlers), broadening the blast radius beyond `PushHandler` alone, though this analysis is scoped to the push path as asked.

### Likelihood Explanation
Precondition: Shipit must be configured with more than one GitHub organization (each with its own `GithubApp`/`webhook_secret`), which the engine explicitly supports (`Shipit.github(organization:)`, multi-org secrets files). The attacker only needs administrative control of their *own* onboarded org's GitHub App to obtain a valid `webhook_secret` and be able to sign arbitrary webhook bodies — no access to the victim org, no Shipit session, and no knowledge of the victim's secret is required. The attack is a single unauthenticated HTTP POST, trivially repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after signature verification succeeds, cross-check that `repository_owner` (the org whose secret verified the signature) matches the owner encoded in `payload['repository']['full_name']` (or `repository['owner']['login']` used consistently everywhere) before dispatching to handlers; reject the event (422) on mismatch. Apply the same authenticated-organization check inside `Handler#stacks`/`Handler#repository_name` so every handler enforces it, not just the controller.

### Proof of Concept
minitest in `test/controllers/webhooks_controller_test.rb` (for reference only, illustrating the intended assertions):
```ruby
test "push webhook signed by attacker-org cannot enqueue GithubSyncJob for shopify's stack" do
  request.headers['X-Github-Event'] = 'push'
  payload = JSON.parse(payload_fixture(:push_master))
  payload['repository']['full_name'] = 'shopify/shipit-engine' # victim
  payload['repository']['owner'] = { 'login' => 'attacker-org' } # attacker's own org

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  shopify_stack = shipit_stacks(:shipit) # owned by 'shopify'

  # BROKEN BINDING under test:
  # payload['repository']['owner']['login'] ('attacker-org') == owner_of(payload['repository']['full_name']) ('shopify')
  # This must be false, i.e. the request must be rejected.
  assert_no_enqueued_jobs(only: GithubSyncJob) do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :unprocessable_entity
end
```
Before the fix, this test fails: `GithubSyncJob` is enqueued with `stack_id: shopify_stack.id` and the attacker-chosen `after` sha, despite the signature having been verified only against `attacker-org`'s secret.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
