### Title
Unconditional `throw` in `definition template` authentifier evaluation crashes every validating node — ([File: definition.js])

### Summary
`Definition.validateAuthentifiers` in `definition.js` evaluates an address (or asset) spending-condition tree while checking signatures for a unit's author. Unlike its sibling function `validateDefinition` (used only for structural pre-validation and which reports errors via callback), the `definition template` branch of `validateAuthentifiers`'s `evaluate()` throws a synchronous `Error` inside an asynchronous `conn.query` callback whenever the referenced template unit is not found — with no upstream `try/catch` to intercept it. This is directly analogous to CVE-2019-12111 (MiniUPnPd `copyIPv6IfDifferent`): an externally supplied, insufficiently-validated field reaches a code path that dereferences/asserts on it and crashes the process instead of failing gracefully.

### Finding Description
`validateAuthentifiers` is invoked from `validation.js` (`validateAuthor` → `validateAuthentifiers(arrAddressDefinition)`) for **any freshly-used address definition** supplied directly in `objAuthor.definition` of a newly posted unit, i.e. before `Definition.validateDefinition` has structurally vetted the whole tree for well-formedness (`validateDefinition` is only invoked later, via `checkSerialAddressUse` → `next()`, *after* the signature-verification pass in `validateAuthentifiers` has already executed): [1](#0-0) [2](#0-1) 

Inside `evaluate()`, both `or` and `and` combinators recursively descend into **every branch of the tree regardless of the signing path**, with no gating on `pathIncludesOneOfAuthentifiers`: [3](#0-2) 

Unlike the `address` case, which is gated by `pathIncludesOneOfAuthentifiers` before doing any DB work, the `definition template` case has **no such gate** and unconditionally executes a DB query, and if the query does not return exactly one row it performs an unguarded `throw`: [4](#0-3) 

Because this `throw` happens inside the `conn.query(...)` callback (an asynchronous continuation), it cannot be caught by any surrounding `try/catch` in the call stack. It propagates to the top of the event loop and is only caught by the global handler in `network.js`, which explicitly re-throws to crash the process: [5](#0-4) 

By contrast, the structurally-similar `definition template` case inside `validateDefinition` (used only to validate that a definition is *well-formed*, not to check signatures) correctly reports the same condition via callback instead of throwing: [6](#0-5) 

### Impact Explanation
Any single unit poster can define a brand-new address whose definition contains, e.g., `['or', [['sig', {...valid sig branch...}], ['definition template', ['<any 44-byte base64 string that is not a real definition_template unit>', {}]]]]`, and post one payment/transaction from that address. Every full node in the network that validates this unit (which is mandatory for it to reach consensus) will invoke `validateAuthentifiers`, which — regardless of which branch actually holds the valid signature — will also evaluate the sibling `definition template` branch, find zero matching rows, and `throw Error("not 1 template")` inside the async DB callback. This crashes every validating node process deterministically and simultaneously, since the crash condition is unit-content-derived and not node-specific. This satisfies the "network unable to confirm new units" impact bar: a single crafted unit can take down the validating full-node fleet.

### Likelihood Explanation
High. The trigger requires only:
- Defining a new address (any unprivileged unit poster can do this trivially — no special privileges, no prior state).
- Including an `or`/`and` node with a `definition template` branch pointing to a non-existent (or not-yet-stable) unit.
- Broadcasting one ordinary unit signed with that new address.

No race condition, no privileged network position, and no dependency on light client/hub/peer trust is required — this is reachable purely through standard unit posting and address-definition semantics that ocore already supports (`definition template` is a documented op).

### Recommendation
Replace the unguarded `throw Error("not 1 template")` in the `definition template` case of `validateAuthentifiers` (definition.js, ~line 811) with a graceful failure path consistent with the rest of `evaluate()`, e.g. `cb2(false)` (treat as "not satisfied") or route the error through `fatal_error`/`cb` similar to how `sig`/`hash` handle failure, mirroring the safe pattern already used in `validateDefinition`'s equivalent branch (`return cb("template not found or too many")`). Additionally, gate the `definition template` branch with `pathIncludesOneOfAuthentifiers` (as done for `address`) to avoid needlessly evaluating branches unrelated to the actual signing path, and audit other `throw` statements inside `conn.query` callbacks throughout `definition.js`/`validation.js` for the same unguarded-async-throw pattern.

### Proof of Concept
1. Attacker generates a new (unused) address `A` with definition:
   ```json
   ["or", [
     ["sig", {"pubkey": "<attacker pubkey>"}],
     ["definition template", ["AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=", {}]]
   ]]
   ```
   (the second element being any syntactically valid 44-byte base64 string that is not the id of a stable `definition_template` unit).
2. Attacker posts a normal payment unit from address `A`, providing `objAuthor.definition` = the above array and a valid `sig` authentifier at path `r.0`.
3. Every node calling `validation.validate()` reaches `validateAuthor` → `validateAuthentifiers(arrAddressDefinition)` → `Definition.validateAuthentifiers`, whose `evaluate()` walks the `or` node and, in parallel with checking the valid `sig` branch, evaluates the `definition template` branch, issues the DB query, gets 0 rows, and executes `throw Error("not 1 template")` inside the query callback.
4. This uncaught exception is not caught anywhere in the async chain and reaches `process.on('uncaughtException', ...)` in `network.js`, which re-throws and crashes the node process — reproducible on every full node that processes this unit.
