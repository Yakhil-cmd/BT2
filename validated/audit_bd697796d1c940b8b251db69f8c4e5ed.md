### Title
CCMenu API endpoint bypasses per-stack authorization scoping, allowing a stack-scoped `ApiClient` token to read any stack's status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` implements a two-part authorization model for `ApiClient` tokens: a coarse-grained permission check (`read:stack`, `write:stack`, etc. via `check_permissions!`) and a fine-grained scoping check that restricts a stack-bound token to only the single `Stack` it was issued for, implemented in `stacks`/`stack`: [1](#0-0) 

`Api::CCMenuController` overrides `stack` and drops the scoping half of that model while keeping only the coarse permission check: [2](#0-1) 

### Finding Description
The intended binding is: *the set of stacks an `ApiClient` token is authorized to touch == `Stack.where(id: current_api_client.stack_id)` when `stack_id` is set on the token*. This is enforced generically for every other API controller (`TasksController`, `DeploysController`, etc.) because they all rely on `BaseController#stack`, which calls `stacks.from_param!(params[:stack_id])`, and `stacks` filters by `current_api_client.stack_id` when the token has one: [1](#0-0) 

`CCMenuController`, however, defines its own `stack` method that resolves the stack directly from the URL param with no scoping to `current_api_client.stack_id`: [3](#0-2) 

The only check that remains is `require_permission :read, :stack`, which merely verifies the token's `permissions` array contains `"read:stack"` — it never checks which stack the token belongs to: [4](#0-3) 

So for a token created with a `stack_id` (a narrowly-scoped token, e.g. `here_come_the_walrus` in the fixtures, which is limited to the `shipit` stack and only has `read:stack`), the `stack` used by `check_permissions!` is never actually validated against `params[:stack_id]`. An attacker who obtains such a token — which, unlike other API endpoints, is designed to be passed as a plain query-string `token` param (`authenticate_api_client` calls `ApiClient.authenticate(params[:token])`), making it appreciably easier to leak via logs, referrers, or CI dashboard configuration — can simply substitute any other stack's `stack_id` in the URL and read that stack's CCMenu status, bypassing the stack-scoping the token was supposed to be limited to. [5](#0-4) 

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" binding described in scope. A token that was deliberately scoped to a single stack (via `ApiClient#stack_id`) can be used to read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, `webUrl`) of every other stack in the Shipit instance, which is an unauthorized read of stack state across repository/stack boundaries — matching the "High" impact category ("unauthenticated read of stack state, task streams or deploy output").

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` authentication token that has `read:stack` permission and a non-nil `stack_id` (a normal, commonly-issued "read-only, single project" token type, e.g. for CI status badges). Because this endpoint authenticates via a URL query parameter (as documented and tested — `token: @client.authentication_token`), such tokens are more exposed to leakage (browser history, referrer headers, proxy/access logs, being embedded in third-party CCMenu dashboard tools) than Basic-Auth-only tokens used elsewhere. No further privilege or session is required — the token itself is the credential.

### Recommendation
Make `Api::CCMenuController#stack` reuse the inherited, scoped `stack`/`stacks` helpers from `Api::BaseController` instead of resolving directly from `Stack.from_param!(params[:stack_id])`, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

and remove the override entirely so the same `current_api_client.stack_id?` scoping used by every other API controller also protects this endpoint.

### Proof of Concept
1. Issue (or obtain) an `ApiClient` token scoped to stack A only, i.e. `stack_id` set to A's id, with permission `read:stack` (mirrors `here_come_the_walrus` fixture: [6](#0-5)  ).
2. As the attacker, request `GET /api/<stack_A_or_arbitrary>/ccmenu.xml?stack_id=<owner>/<repo_B>/<environment>&token=<stackA_token>` (route uses `stack_id` param to identify target stack; `CCMenuController#authenticate_api_client` accepts the token via query string): [5](#0-4) 
3. `require_permission :read, :stack` passes because the token has `read:stack` permission, regardless of stack: [4](#0-3) 
4. `stack` resolves stack B directly via `Stack.from_param!(params[:stack_id])`, ignoring that the token's `stack_id` is A: [3](#0-2) 
5. Response renders stack B's CCMenu XML (`lastBuildStatus`, etc.), disclosing stack B's deploy/lock status to a token that was never authorized for stack B.
