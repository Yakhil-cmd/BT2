### Title
Missing `return` after hash-computation failure causes duplicate processing / crashed callback chain in private-payment reassembly - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` re-validates private payment chains that were queued in `unhandled_private_payments` (the store used while ocore is "reassembling" a private payment chain whose ancestor joints have not yet arrived/stabilized, exactly analogous to EAP-pwd's fragment-reassembly buffer). When the head element's payload cannot be hashed, the exception handler fails to stop processing, so an "unexpected fragment" (malformed private-payment element) drives the code into an inconsistent state that double-invokes the completion callback.

### Finding Description
`buildPrivateElementsChain`/`handleOnlinePrivatePayment` accept a `private_payment` chain from an untrusted peer or hub and, for light clients or chains still waiting on ancestor joints, store the raw attacker-supplied JSON in `unhandled_private_payments` with only shallow validation (unit, message_index, output_index) performed in `handleOnlinePrivatePayment` [1](#0-0) . Deep structural validation of `payload` is deferred until the chain is later replayed in `handleSavedPrivatePayments`.

In that later replay, `validateAndSave()` computes a hash of the attacker-controlled `payload`:
```
var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
```
If this throws (e.g., a payload containing a value type unsupported by `getSourceString`/`getJsonSourceString`, such as `undefined`, `NaN`, or a non-JSON-representable structure crafted by the attacker), the `catch` block logs the error, optionally sends a result, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — but there is **no `return`** after this call [2](#0-1) . Execution falls through to build `key` using the now-`undefined` `json_payload_hash`, and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError` callbacks again invoke `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` [3](#0-2) .

This means the `cb` supplied by `async.each`'s iteratee is called twice for the same malformed element — once from the throw path, once from the fall-through validation path. `async`'s iteratee callbacks are documented to be called at most once; calling twice on a crafted, single "unexpected fragment" corrupts the control flow of the whole `handleSavedPrivatePayments` batch (which may be processing many other legitimately queued private payments concurrently), and can throw an uncaught error inside the `async.each` internals, crashing the node process — the same denial-of-service outcome (process termination via mishandled unexpected fragment/reassembly state) described in CVE-2019-11555.

### Impact Explanation
A single attacker-controlled private-payment chain element (reachable by any private-payment counterparty, or via the hub relay for light wallets) can trigger a double callback invocation in the reassembly/replay logic of `handleSavedPrivatePayments`. This can crash the wallet/node process, and — because the DELETE against `unhandled_private_payments` is invoked twice concurrent with the async batch loop — can also corrupt the processing of sibling private payments that are batched in the same `handleSavedPrivatePayments` call, potentially causing a node to fail to correctly process or forward legitimate private payments (denial of service against the wallet's ability to confirm/accept private transactions).

### Likelihood Explanation
Any peer or hub can deliver a `private_payment`/`private_payment_chains` message; a light wallet queues it directly into `unhandled_private_payments` without deep payload validation [4](#0-3) . Triggering `getBase64Hash` to throw only requires crafting a payload with a value unsupported by the source-string serializer, which is straightforward JSON manipulation, not a race condition — making this highly reachable.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain` call inside the `catch` block in `handleSavedPrivatePayments`'s `validateAndSave` function so the fallthrough path is never executed when `json_payload_hash` computation fails, and ensure `cb` is invoked exactly once per queued row.

### Proof of Concept
1. As a paired device/peer, send (or route through the hub) a `private_payment_chains`/`private_payment` message whose head element's `payload` contains a value that `getSourceString`/`getJsonSourceString` cannot serialize (e.g. embed `NaN`, `Infinity`, or a deeply malformed nested object) while still passing the shallow checks in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`.
2. The recipient stores it in `unhandled_private_payments` (light client path, or `ifWaitingForChain`).
3. When `handleSavedPrivatePayments` later processes the row, `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws; the `catch` block runs `deleteHandledPrivateChain(..., cb)` without returning, then falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose callback invokes `deleteHandledPrivateChain(..., cb)` a second time — `cb` is called twice within the same `async.each` iteration, corrupting/crashing the batch handling.

Note: I could not fully trace whether the specific `async` library version in use throws on double-callback invocation (this would need to be confirmed by running the code / checking `package.json`'s `async` version), so the "process crash" severity should be validated experimentally by a Devin session with code-execution access; the double-DELETE / duplicate-processing logic bug itself is confirmed by direct code inspection.

		return callbacks.ifError("invalid output_index");

	var savePrivatePayment = function(cb){
		// we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device.

		db.query(
			"INSERT "+db.getIgnore()+" INTO unhandled_private_payments (unit, message_index, output_index, json, peer) VALUES (?,?,?,?,?)",
