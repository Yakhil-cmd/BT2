### Title
Tokens sent to the controller inside `flash_position` that are not declared in `collaterals` or `refund_assets` are permanently locked - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
Analogous to `msg.value` being silently lost when attached to an ERC20 `fundBountyToken` call, `Controller::flash_position` accepts arbitrary token transfers into the controller during the receiver callback but only reconciles assets the caller explicitly declared in `collaterals` (deposited) or `refund_assets` (refunded). Any other token the receiver transfers to the controller — including a *declared collateral token from the wrong hub's perspective* is fine, but an entirely undeclared asset — is neither credited nor returned, and the controller exposes no recovery path for it.

### Finding Description
`process_flash_position` snapshots controller balances only for the two declared sets before invoking the receiver:

- `collateral_before` covers each `collaterals[i].hub_asset.asset` (contracts/controller/src/strategies/flash_position.rs:125-129)
- `refund_before` covers each entry of `refund_assets` (:130)

After `invoke_receiver` returns (:131-141), settlement touches only those two sets:

- `collect_collateral_deposits` measures deltas for declared collateral assets and supplies them via `process_deposit` (:325-352, :145-146)
- `refund_listed_assets` refunds only positive deltas of `refund_assets` via `refund_controller_balance_delta` (:372-384), which itself only sends the increase since the pre-callback baseline (`payments.rs:41-52`)

There is no catch-all reconciliation. The project's own documentation states: "An undeclared token left on the controller is neither deposited nor refunded" (skills/xoxno-lending-contracts/flash-loans.md:134). Because balance deltas are measured against baselines taken *inside* `with_flash_guard` after the borrow forward (:120-143), even a later `flash_position` call that declares the stuck asset in `refund_assets` cannot reclaim it — its baseline already includes the stuck balance, so `refund_controller_balance_delta` computes a zero delta and refunds nothing. No sweep/rescue entrypoint exists in the controller's allowed surface.

An unprivileged caller reaches this by supplying their own `receiver` contract (`require_wasm_receiver` only requires a contract address, :69) whose `execute_flash_position` transfers an extra token to the controller — e.g., a leftover debt-asset amount they deliberately keep, or any third token — without listing it in `refund_assets`. Note `refund_assets` is further restricted to listed, active assets on the same hub (:240-247), so a receiver that acquires a token from a *different* hub (e.g., via a same-transaction external swap) cannot even declare it for refund.

### Impact Explanation
Permanent freezing of user funds: the undeclared tokens remain on the controller address with no crediting, no refund, and no reachable withdrawal path. This mirrors the original report's "msg.value will be irrecoverable."

### Likelihood Explanation
Requires a user mistake or an oversight in a custom receiver/router composition (extra token pushed to the controller but omitted from `refund_assets`, or a non-listed token acquired mid-callback). The protocol neither reverts on the unexpected inflow nor auto-refunds it, exactly like the missing `require(msg.value == 0)` check in the original. Self-inflicted but enabled by absent validation — consistent with Medium severity.

### Recommendation
After `refund_listed_assets`, verify the controller's post-call balances equal the pre-callback baselines for all assets touched, or provide a generalized refund. Practically: allow `refund_assets` to include any token (drop the same-hub listing restriction, since refunds are plain transfers and deposit gates don't apply), and document/enforce that callers must declare every token the receiver may send. Alternatively, snapshot a caller-supplied superset and refund all positive deltas.

### Proof of Concept
1. Alice deploys a receiver contract implementing `execute_flash_position`.
2. Alice calls `Controller::flash_position` with `debt = USDC`, `collaterals = [(XLM, min)]`, `refund_assets = []`, `receiver = her contract`.
3. Inside the callback, the receiver buys XLM with the forwarded USDC, transfers XLM to the controller (declared → deposited), and also transfers some other token `T` — or leaves residual USDC it re-acquired — to the controller without declaring it.
4. The call succeeds; `T` remains on the controller. No subsequent call can recover it: declaring `T` in a later `refund_assets` measures a zero delta against a baseline that already includes the stuck balance, and no sweep entrypoint exists.
