## Analog Vulnerability Found

### Title
Cross-organization webhook forgery: signing organization is never bound to the acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to check against based on `repository.owner.login` (or `organization.login`) read out of the untrusted JSON body, while every webhook `Handler` subsequently resolves *which stack to act on* using a completely independent field of the same body: `repository.full_name`. Because the HMAC only proves "this body was signed with the secret configured for organization X," and never proves "the repository this body claims to act on belongs to organization X," any party who legitimately controls a webhook secret for *one* organization onboarded onto the Shipit instance can forge a signed payload whose `repository.full_name` names a stack belonging to a *different* organization.

### Finding Description
`verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

It looks up the app/secret with `Shipit.github(organization: repository_owner)` and only checks that the raw body's signature matches *that* organization's `webhook_secret`. Nothing ties `repository_owner` to the repository object that handlers subsequently operate on.

Every `Handler` subclass instead resolves the target `Stack`/`Repository` from a different, independently-controlled field, `repository.full_name`: [3](#0-2) [4](#0-3) 

For example, `PushHandler#process` uses this `stacks` lookup to trigger real work against whatever stack matches `full_name`: [5](#0-4) 

`PullRequest::ClosedHandler` does the same to resolve a `review_stack` and calls `archive!` on it: [6](#0-5) 

The equality the code implicitly (and incorrectly) assumes is:
`organization whose secret signed the request == organization that owns repository.full_name`

Nothing enforces this. GitHub itself would never send such a mismatched payload, but the controller accepts arbitrary raw POST bodies signed with any configured organization's secret — it does not require the request to actually originate from GitHub for that specific repository. Consequently, a party holding a legitimate webhook secret for organization A (e.g., because they administer or were granted a Shipit-connected app/repo under org A) can craft `repository.owner.login = "org-a"` (used only for secret selection) together with `repository.full_name = "org-b/private-repo"` (used to pick the actual `Stack`), compute the HMAC themselves with org A's secret, and POST directly to `/webhooks`. `verify_signature` passes because the signature genuinely matches org A's secret over that exact (attacker-chosen) body; the handler then acts on org B's stack.

### Impact Explanation
This breaks tenant isolation between organizations onboarded onto the same Shipit instance: an actor with only credentials for organization A's webhook can forge events that mutate state belonging to organization B's stacks:
- Forcing spurious `GithubSyncJob` runs and DB state changes (accessible/inaccessible marking, commit append) for an arbitrary victim stack via `PushHandler` → `Stack#sync_github`.
- Forcing `ReviewStack#archive!` (a decommission/teardown-class action) via `PullRequest::ClosedHandler` against a victim organization's live review stack, without ever holding credentials, a session, or an `ApiClient` token for that victim organization.

This satisfies the "unauthorized deploy/rollback" / cross-repository write class described in scope, because the trust boundary broken is exactly "organization that authenticated versus the repository that is written."

I was not able to inspect `ReviewStack#archive!`'s full implementation within the available iterations to confirm precisely what infrastructure-level teardown commands it triggers; this should be verified directly, but the reachable forged-payload path into it is confirmed at the handler level shown above.

### Likelihood Explanation
Requires only a webhook secret for *some* organization already configured in the Shipit deployment (`secrets.yml`/`Shipit.github`) — no access to any other organization, no Shipit user session, and no `ApiClient` token. Any customer/org onboarded to a shared multi-tenant Shipit instance can exploit this against any other onboarded org's stacks, since the request path never validates that the signed organization matches the repository actually referenced by the payload.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization portion of `repository.full_name` (or `organization.login`) used by handlers is identical to `repository_owner`, the value the signature was actually verified against, before dispatching to any handler. Reject the request otherwise.

### Proof of Concept
1. Attacker legitimately controls the GitHub App/webhook configuration for `org-a` (their own onboarded organization) and thus knows `org-a`'s `webhook_secret`.
2. Attacker crafts a JSON body for a `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `sha1=` HMAC over this exact raw body using `org-a`'s known `webhook_secret` (per `Hook::DeliverySigner`/`verify_webhook_signature` algorithm) — [7](#0-6)  — and sets it as `X-Hub-Signature`.
4. Attacker POSTs directly to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s app, and the signature checks out.
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` = `"org-b/victim-repo"`, finds `org-b`'s real `Stack`, and enqueues `stack.sync_github(expected_head_sha: "deadbeef")` — mutating state belonging to `org-b`, an organization the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
