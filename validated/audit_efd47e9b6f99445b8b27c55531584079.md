### Title
Type confusion via `typeof null === "object"` in `hasCases()` causes uncaught exception during AA definition validation - ([File: formula/common.js])

### Summary
`ocore`'s AA (Autonomous Agent) definition validator (`aa_validation.js`) and the AA trigger composer (`aa_composer.js`) both recurse over arbitrary user-supplied AA definition/message JSON structures using a helper `hasCases(value)` defined in `formula/common.js`. This helper relies on `typeof value === 'object'` to decide whether to treat a value as a possible "cases" wrapper, but in JavaScript `typeof null === 'object'` too. If a JSON `null` reaches `hasCases`, it calls `Object.keys(null)`, which throws an uncaught `TypeError`. This is the same class of bug as the reported libxml2 issue: a value whose *nominal* type check ("is this an object?") is fooled by a type-system quirk, leading to a crash where a controlled memory-corruption analog is a controlled unhandled JS exception (denial of service).

### Finding Description
`hasCases` is defined as: [1](#0-0) 
```js
function hasCases(value) {
	return (typeof value === 'object' && Object.keys(value).length === 1 && ValidationUtils.isNonemptyArray(value.cases));
}
```
`typeof null` evaluates to `"object"` in JavaScript, so when `value === null`, the check falls through to `Object.keys(null)`, which throws `TypeError: Cannot convert undefined or null to object`. This exception is not caught anywhere in the call chain.

`hasCases` is invoked from the recursive `validate()` function inside `validateAADefinition()` in `aa_validation.js`, which walks every value of an AA's `messages`/`init`/`getters` structure (values that come directly from user-posted `definition` app payloads): [2](#0-1) 

The very same pattern (`hasCases(value)` checked immediately after `typeof value === 'string'`) is duplicated in `aa_composer.js`'s `replace()` function, used when composing/executing an AA response during trigger handling: [3](#0-2) 

Both `validate()` (aa_validation.js) and `replace()` (aa_composer.js) recurse into every key of every object/array in the AA definition tree via `isNonemptyObject`/`Array.isArray` branches, so any leaf value equal to JSON `null` embedded anywhere in a `messages`, `init`, or `getters` field will reach `hasCases(null)` and throw.

This validation path is reachable by an ordinary AA author: `aa_validation.validateAADefinition` is invoked for every unit posting an AA `definition` app-payload, via `validateInlinePayload` in `validation.js`: [4](#0-3) 
This is executed by every node validating the network's DAG — not just the AA-poster's own node.

### Impact Explanation
An uncaught `TypeError` thrown deep inside an `async.eachSeries`/`async.eachOfSeries` callback chain (as used throughout `validate()`/`replace()`) is not passed through the `cb`/`callback` error-handling convention used everywhere else in this code; it propagates as a genuine JS exception up the (asynchronous) call stack. Because these functions are invoked from deep inside `async` iterators and `nearley`-driven recursive descent, there is no enclosing `try/catch` guarding this specific code path (unlike, e.g., the JSON.parse/nearley-parsing sections which are explicitly wrapped in `try/catch`). An uncaught exception thrown from within a Node.js callback-based execution chain like this will normally propagate to the process' default handler and crash the Node.js process (or hang the event loop, depending on how it is invoked in `validation.js`), meaning any node validating a unit that defines an AA with a stray `null` inside `messages`/`init`/`getters` — or any node processing an AA trigger whose response/state formulas assign a `null` to a message field that is later processed by `replace()` — could crash. Since AA definition validation is executed by every full node when the defining unit is processed on the DAG, this represents a network-wide denial-of-service vector: a single malicious unit could be broadcast to crash all full nodes that attempt to validate it, preventing them from confirming new units.

### Likelihood Explanation
High likelihood of reachability: any account can post a unit containing a `definition` app message defining an AA (a completely permissionless, unprivileged action). The attacker only needs to embed a literal JSON `null` value somewhere within the `messages`/`init`/`getters` tree of the AA template (e.g., as a value at some field position that is walked by the generic `validate()`/`replace()` recursion, rather than being consumed by one of the specific app-type validators like `validatePayload` for known apps). This does not require bypassing signature checks, cryptography, or any privileged role — it is a standard unit posted by an unprivileged unit poster/AA author.

### Recommendation
Fix `hasCases()` in `formula/common.js` to explicitly exclude `null`:
```js
function hasCases(value) {
	return (value !== null && typeof value === 'object' && Object.keys(value).length === 1 && ValidationUtils.isNonemptyArray(value.cases));
}
```
Audit all other `typeof x === 'object'` checks in `aa_validation.js`, `aa_composer.js`, and `formula/*.js` for the same `null` type-confusion pitfall (e.g., the `typeof value === 'object' && (typeof value.if === 'string' ...)` checks that immediately dereference `.if`/`.init` on the value), and add explicit `value !== null` guards. Additionally, wrap the top-level AA-definition validation and AA trigger composition entry points in a `try/catch` that converts unexpected exceptions into validation failures (`cb("internal error")`/bounce) rather than allowing them to crash the node process, so that unforeseen type-confusion bugs degrade gracefully instead of causing full node crashes.

### Proof of Concept
Post (or dry-run) an AA definition whose `messages` structure contains a bare `null` value at a location that reaches the generic `validate()`/`replace()` recursion, e.g. inside an `init`/`if` object wrapper or a nested array/object field not consumed by a specific app validator:
```js
var aa = ['autonomous agent', {
    messages: [
        {
            app: 'state',
            state: '{ }',
            if: null   // reaches "typeof value === 'object' ..." style branches via generic recursion
        }
    ]
}];
```
More directly, since `hasCases` is called unconditionally on every non-string leaf value encountered by `validate()`/`replace()`, any AA field value that is JSON `null` and is not otherwise filtered out earlier by an app-specific validator (e.g., a `null` nested inside a generic object/array field of a `payload`, or a value produced by formula evaluation that ends up as `null` before being fed back into `replace()`) will cause:
```
TypeError: Cannot convert undefined or null to object
    at Function.keys (<anonymous>)
    at hasCases (formula/common.js:96)
```
to be thrown uncaught, crashing the validating node's process. Exact reachability of a concrete field path bypassing all app-specific pre-filters (e.g., `validatePayload`) would require deeper enumeration of every `app` type's payload schema in `aa_validation.js`, which the current investigation could not exhaustively confirm for every `app` due to index size limits — I could not load the complete `aa_validation.js` file to trace every field path. A background engineering session with full file access should confirm the exact minimal AA JSON that reaches `hasCases(null)` unfiltered, and verify whether the resulting exception truly propagates to process crash or is caught by an outer `async`/`domain` boundary.
