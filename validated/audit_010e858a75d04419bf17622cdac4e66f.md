### Title
Attacker-controlled swap routes can add unauthorized wallet-token transfers to the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-supplied route bytes and forwards them to the configured swap aggregator after granting only the controller's own input-token transfer authorization. [1](#0-0) [2](#0-1)  The router can invoke pool/token addresses named by the payload, and code reached through that route can request a token transfer from the original caller; simulation records that transfer as a child of the caller's `swap_collateral` authorization. [3](#0-2) 

### Finding Description
The externally supplied `swap` argument reaches `swap_tokens` through `process_swap_collateral`, which authorizes the owner or delegate and invokes `withdraw_and_swap_from_supply`. [4](#0-3)  `swap_tokens` bounds only the controller's `token_in` transfer to the router and checks controller-side balance deltas; it does not constrain what other contract calls occur inside the routed execution. [5](#0-4)  Router dispatch sends hop-specified venues to venue adapters without a venue-address allowlist. [6](#0-5)  A malicious compatible venue can therefore call `wallet_token.transfer(victim, attacker, amount)` during the strategy, causing Soroban simulation to include that transfer under the victim's signed invocation tree. [7](#0-6) [8](#0-7) 

### Impact Explanation
A victim who signs the simulated tree authorizes both the intended strategy and the injected token transfer, allowing theft of arbitrary unrelated wallet assets rather than only the collateral being routed. [9](#0-8)  The protocol's positive-output and final-risk checks still pass because the malicious pool can coexist with a route that delivers a valid output. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The attack requires convincing the victim to execute an attacker-constructed route and sign a transaction whose authorization tree contains an extra transfer. [12](#0-11)  Clients that sign simulation results without validating children are exposed; an honest route produces no such extra child under the controller strategy. [13](#0-12) 

### Recommendation
Clients should decode simulated authorization trees and reject any `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or related strategy tree containing children beyond the expected token pulls. [3](#0-2)  Prefer routes from trusted quote infrastructure, display all payload-addressed venues and token calls before signing, and consider an allowlist of production venue contracts to prevent arbitrary attacker-deployed pools from entering the authorization context. [6](#0-5) 

### Proof of Concept
1. Victim holds supplied USDC collateral and an unrelated wallet token. [14](#0-13) 
2. Attacker supplies a `swap_collateral` route whose `hop_pool` is a contract configured to call `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. [15](#0-14) [16](#0-15) 
3. Victim calls `swap_collateral(caller=victim, account_id, current=USDC market, amount=SWAP_IN_USDC, new=ETH market, swap=malicious_route)`. [17](#0-16) 
4. Simulation records the rogue wallet-token transfer as a child of the victim's `swap_collateral` authorization. [18](#0-17) 
5. If the victim signs that returned tree, the strategy succeeds while the unrelated wallet token moves from victim to attacker. [9](#0-8)

/// Passes matching assets through only with an empty route; otherwise swaps.
pub(crate) fn swap_tokens_or_passthrough(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    if token_in == token_out {
        assert_with_error!(env, swap.is_empty(), GenericError::InvalidPayments);
        amount_in
    } else {
        swap_tokens(env, refund_to, token_in, amount_in, token_out, swap)
    }
}

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's

recorded by an honest simulation as a child of the caller's authorization

caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
