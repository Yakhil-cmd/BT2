## Analysis Result

### Title
sBTC reward and unstake transfers in pox-5.clar can be permanently blocked by external `sbtc-token` transfer failure, freezing staked/reward sBTC for an entire signer's stakers - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar` performs synchronous, blocking `contract-call?` transfers to the external `sbtc-token` contract inside three state-mutating, unprivileged-account entry points: `claim-rewards`, `unstake-sbtc`, and the private `roll-sbtc` helper (invoked from `register-for-bond`/`stake`). Because Clarity aborts the entire transaction if any nested `try!` call fails, a single failing `sbtc-token transfer` (e.g. the recipient principal is paused/blacklisted by the sBTC bridge, or any other legitimate transfer-time failure) makes it impossible to complete the surrounding pox-5 operation at all. This is the direct analog of the reported bug class: an external ERC20-style `transfer()` failure inside a critical state-changing function (`end()`) blocking the whole transaction and permanently locking funds.

### Finding Description
- `unstake-sbtc` computes new bond/cycle accounting and then calls the external token directly: [1](#0-0) 
If this `transfer` call fails, the whole `unstake-sbtc` transaction reverts (Clarity state changes are all-or-nothing), so the staker's sBTC remains locked inside pox-5 indefinitely with no alternate withdrawal path.

- `claim-rewards` similarly gates the release of a signer's total earned sBTC on one live `transfer` call to `signer` before crediting is finalized: [2](#0-1) 
Because `claim-rewards` is called once per signer on behalf of *all* stakers delegated to that signer (see `signer-manager.clar`'s `claim-rewards` wrapper), a single failure of this transfer (e.g. the signer-manager/recipient principal cannot receive sBTC) blocks reward release for every staker under that signer, not just the caller: [3](#0-2) 

- `roll-sbtc`, used during bond-to-bond/bond-to-stake rollovers in `register-for-bond`/`stake`, also performs a synchronous refund `transfer` from the contract back to the staker when `new-sbtc < old-sbtc`: [4](#0-3) 
A failure here blocks the staker's ability to roll their position forward at all, even though the STX-side lock bookkeeping (handled node-side via `pox_rollover_v5`/`handle_lockup_pox_v5`) is designed to always carry the lock forward: [5](#0-4) 

None of these three call sites implement a pull-based balance/`withdraw()` pattern (as the referenced fix recommends); they all attempt the external transfer synchronously as part of the critical path, so the equality "staked/earned sBTC accounted for the staker/signer == sBTC deliverable to that staker/signer" can never be settled once the destination principal cannot accept a direct `transfer`.

### Impact Explanation
This maps to the "temporary freezing of staked funds" / "permanent freezing of staked STX or sBTC" categories:
- A single staker's `unstake-sbtc` can be permanently blocked, freezing their bonded sBTC in the contract with no rescue mechanism in pox-5.clar.
- `claim-rewards` blocking is worse: it is invoked once per signer for a whole cohort of stakers, so if that call cannot succeed, sBTC rewards already earned by potentially many unrelated stakers under that signer become frozen (unclaimable) indefinitely, since `last-accounted-rewards-only` is never decremented and no other code path releases those already-computed rewards.
- Because the failure is not limited to the caller's own funds (in the `claim-rewards` case it can freeze other stakers' already-earned rewards), this is not merely "the attacker's own stake at risk."

### Likelihood Explanation
Likelihood depends on the `sbtc-token` recipient becoming unable to accept a direct transfer (e.g., a bridge-side pause/blacklist/compliance action on a staker's or signer-manager's principal, or any other legitimate transfer-time revert as acknowledged in the source report). This does not require a malicious admin, miner, or another user's key — any unprivileged staker whose own or whose signer-manager's principal is later restricted by the sBTC token contract triggers the condition through ordinary use of `unstake-sbtc`/`claim-rewards`/`stake`.

### Recommendation
Adopt the same balance-based mitigation referenced in the report: replace the synchronous `transfer` calls in `unstake-sbtc`, `claim-rewards`, and `roll-sbtc` with an internal balance/credit ledger, and add a separate `withdraw`/`claim`-style function that lets a staker/signer pull their sBTC whenever their account is able to receive it, so a transient or permanent inability to receive a transfer for one principal cannot freeze funds owed to that principal (or, in the `claim-rewards` case, to other stakers under the same signer).

### Proof of Concept
1. Alice stakes sBTC into a protocol bond via `register-for-bond`.
2. Before Alice calls `unstake-sbtc`, her principal (or the relevant signer-manager contract) is restricted from receiving `sbtc-token` transfers (bridge-level pause/blacklist, or any other transfer-time revert condition).
3. Alice calls `unstake-sbtc`; the internal accounting mutations execute, then the terminal `contract-call? sbtc-token transfer` reverts, aborting the whole transaction and rolling back all state changes — Alice's sBTC principal is now permanently stuck in pox-5.clar with no alternate exit.
4. Separately, if the signer-manager's `claim-rewards` recipient becomes unable to receive `sbtc-token`, every staker delegated to that signer loses the ability to realize already-earned, computed sBTC rewards, since `claim-rewards`'s `transfer` at [6](#0-5)  reverts and blocks the group-wide reward release for that signer.

```rust
/// Handle responses from pox-5 entry points that lock STX for a staker:
/// `stake` (STX-only) and `register-for-bond` (protocol bond). A first-time
/// call (no existing pox-5 lock) acquires a fresh lock via
/// [`pox_lock_v5`]; a roll-over (the account is already locked from an
/// ending bond or stake) carries the lock forward via
/// [`pox_rollover_v5`] -- the amount may go up or down and the
/// unlock height is rescheduled, so the lock never releases. The contract
/// is responsible for gating the roll-over (non-overlap + L1 unlock window
/// for bond sources); if the contract returns ok, this handler trusts the
/// call is legitimate.
fn handle_lockup_pox_v5(
    global_context: &mut GlobalContext,
    function_name: &str,
    value: &Value,
) -> Result<Option<StacksTransactionEvent>, VmExecutionError> {
    debug!(
        "Handle special-case contract-call to {:?} {function_name} (which returned {value:?})",
        boot_code_id(POX_5_NAME, global_context.mainnet)
    );
    runtime_cost(
        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

    let parsed = parse_pox_stake_result(value).map_err(|e| {
        locking_error_to_vm_error(e, &format!("pox-5 {function_name}: bad response"))
    })?;
    let (staker, locked_amount, unlock_height) = match parsed {
        ParsedStakeResult::Ok {
            staker,
            amount_ustx,
            unlock_burn_height,
        } => (staker, amount_ustx, unlock_burn_height),
        ParsedStakeResult::ContractErr => return Ok(None),
    };

    // A staker rolling from one bond/stake position into another is already
    // locked; carry the lock forward instead of acquiring a fresh one (which
    // would fail with `PoxAlreadyLocked`). A first-time call locks fresh.
    let already_locked = {
        let mut snapshot = global_context.database.get_stx_balance_snapshot(&staker)?;
        snapshot.has_locked_tokens()?
    };

    let lock_result = if already_locked {
        pox_rollover_v5(
            &mut global_context.database,
            &staker,
            unlock_height,
            locked_amount,
        )
        .map(|_| ())
    } else {
        pox_lock_v5(
            &mut global_context.database,
            &staker,
            locked_amount,
            unlock_height,
        )
    };
```
