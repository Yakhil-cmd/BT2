### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on unrelated fields (`repository.full_name`, global `sha`) — cross-organization/cross-repository forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, but the event handlers that subsequently run on the same payload never re-check that the acted-upon repository/commit actually belongs to that same authenticated organization. This breaks the binding: `organization whose secret authenticated the request == repository/commit the handler writes to`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config solely from `repository_owner`, computed as: [1](#0-0) [2](#0-1) 

This value is only used to choose `Shipit.github(organization: repository_owner)` (i.e., which org's `webhook_secret` HMAC key to check the `X-Hub-Signature` against). Once `verified` is true, `create` dispatches the **entire raw JSON payload** to handlers without any further scoping to that organization: [3](#0-2) 

Handlers derive the actual target independently, from a different field of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login` (the field used for signing): [4](#0-3) 

Worse, `StatusHandler` doesn't even scope by repository at all — it looks up commits **globally by SHA**: [5](#0-4) 

`Commit#create_status_from_github!` writes a new commit status/state which feeds directly into deploy gating (`deployable?`) and can auto-schedule a deploy via `schedule_continuous_delivery`: [6](#0-5) [7](#0-6) 

**Binding equality that should hold, but doesn't:**
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository whose state is mutated by the handler (repository.full_name for PushHandler, or the owning stack of the commit sha for StatusHandler)`.

Concretely: any attacker who controls (or knows the webhook secret for) **one** organization/repository connected to this Shipit instance — e.g., their own org where they legitimately administer the GitHub App/webhook — can send a signed webhook whose `repository.owner.login` matches their own org (so it passes `verify_signature`), while other payload fields (`repository.full_name`, `sha`) reference a **different** org's stack/commit. Because the handlers never re-validate those fields against the org that authenticated the request, the attacker can:
- Trigger `GithubSyncJob`/`sync_github` for an arbitrary victim stack via `PushHandler` (`repository_name` = victim's repo, but signed with attacker's own secret). [8](#0-7) 
- Inject a forged "success" commit status for **any** SHA in **any** stack via `StatusHandler`, since it is not scoped by repository at all, potentially satisfying CI requirements gating continuous deployment for a victim stack whose commit SHA is known/public.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as Critical/High: it enables cross-repository writes (forged commit statuses / triggered syncs on repositories the attacker does not own) and, via `schedule_continuous_delivery`, can lead to an unauthorized deploy being triggered on a victim's stack. This satisfies the Critical bucket ("cross-repository writes... an unauthorized deploy").

### Likelihood Explanation
Requires only that the attacker control or know the webhook secret of any single organization/repository already connected to the Shipit instance (an "unprivileged" attacker relative to the victim org) — no `ApiClient` token, no GitHub App private key, no privileged Shipit account, and no repository write access to the victim repo is needed. The victim commit SHA is typically discoverable via GitHub's public API/UI for public repos.

### Recommendation
- In `WebhooksController#verify_signature`/`#create`, after establishing which organization authenticated the request, pass that organization down and have every handler assert that `repository.owner.login` (or `repository.full_name`'s owner segment) matches the authenticating organization before taking any action.
- In `Handler#stacks`/`Handler#repository_name`, reuse the same trusted organization value used for signature verification rather than re-deriving it from an unauthenticated-relative payload field.
- In `StatusHandler#process`, scope the `Commit` lookup by the authenticated repository/stack (e.g., join through `stack.repository.owner`) instead of a bare, cross-tenant `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker has legitimate GitHub App/webhook_secret access for `attacker-org` (their own connected org in this Shipit instance).
2. Attacker computes a valid `X-Hub-Signature` over a crafted `push` payload where `repository.owner.login == "attacker-org"` (so `verify_signature` picks and validates against `attacker-org`'s secret) but `repository.full_name == "victim-org/victim-repo"`.
3. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` succeeds (signed with `attacker-org`'s real secret).
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, and calls `stack.sync_github(expected_head_sha: <attacker-controlled sha>)` on the victim's stack — an action the attacker was never authorized to trigger.
5. Similarly, a `status` event signed with `attacker-org`'s secret but containing `sha` of a commit belonging to `victim-org`'s stack causes `StatusHandler` to write a forged status via `Commit.where(sha:)`, which is not scoped to any organization, potentially unlocking `schedule_continuous_delivery` for the victim stack.
