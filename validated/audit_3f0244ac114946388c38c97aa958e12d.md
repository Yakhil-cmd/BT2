### Title
Webhook signature is verified against the wrong organization's secret, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Just as the external report describes a critical field ("TGE") being used throughout vesting calculations without dedicated validation, `Shipit::WebhooksController#verify_signature` picks which GitHub App/organization secret to validate a webhook against using a field (`repository_owner`) taken from the same **unverified, attacker-controlled** JSON body, while the downstream event `Handler` uses a *different* field (`repository.full_name`) from that same body to decide which `Stack`/`Repository` the payload actually acts on. Neither field is cross-validated against the other, so the "organization that authenticated" and the "repository that is written" are never checked for consistency.

### Finding Description
`verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret` used to compute the HMAC) using: [1](#0-0) [2](#0-1) 

`repository_owner` is computed by reading `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) directly out of the raw request body — the very body whose signature is being checked. Rails' JSON parsing middleware has already populated `params` before this `before_action` runs, so this value is 100% attacker-controlled and is evaluated *before* (and independently of) whether the signature is actually valid for that organization's secret.

Once the signature check passes, `create` re-parses the raw body and dispatches to handlers using the full, unconstrained payload: [3](#0-2) 

Handlers such as `PushHandler` resolve which `Stack` to act on via `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`, which reads a **different** field from the same payload: [4](#0-3) [5](#0-4) 

In a multi-organization deployment, `Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github_app_config(organization)`: [6](#0-5) 

Because `repository.owner.login` (used to select the secret) and `repository.full_name` (used to select the target `Repository`/`Stack`) are two independently attacker-supplied fields of the same JSON body, an attacker who legitimately knows/controls one organization's `webhook_secret` (e.g., an admin of "org-b" onboarded to a shared multi-tenant Shipit instance) can craft a payload where `repository.owner.login = "org-b"` (so the HMAC validates against org-b's secret) while `repository.full_name = "org-a/some-repo"` (so the handler acts on a stack that belongs to a completely different, unrelated organization "org-a"). The binding "organization that authenticated == repository that is written" is never enforced, breaking the trust boundary between tenants/organizations that the per-organization `webhook_secret` config is meant to establish.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" impact bar described in scope: an attacker who only controls one organization's webhook secret can forge a webhook that is accepted as authentic and causes `Shipit::GithubSyncJob` to run against a `Stack` belonging to a different organization/repository, driven entirely by attacker-supplied `ref` and `expected_head_sha` values: [7](#0-6) 
This can trigger commit ingestion/sync (and downstream deploy-spec caching / deploy eligibility) for a stack the attacker has no legitimate relationship to, purely because the "authenticating organization" and the "acted-upon repository" bindings are never checked against each other.

### Likelihood Explanation
This is only exploitable in the multi-organization secrets schema (`secrets.github` keyed by org, each with its own `webhook_secret`), which is an explicitly documented, supported configuration: [8](#0-7) 
Any tenant/organization admin who is issued their own `webhook_secret` for their own GitHub App installation (a normal, low-privilege setup step, not "webhook_secret" of the target org) can exploit this without any additional access to the target organization or its repository. No GitHub write access, Shipit session, or API token is required — only knowledge of one's own org's webhook secret, which is a standard configuration credential handed to onboarding customers.

### Recommendation
Bind the verified organization to the acted-upon repository/organization instead of letting them be selected independently from the same unauthenticated JSON body:
- After signature verification succeeds, re-derive and enforce that the organization that verified the signature (`repository_owner`) matches the owner/organization of `repository.full_name` used by every dispatched handler, rejecting (422) any mismatch.
- Alternatively, verify signatures once per configured organization/secret (looping over all configured secrets) but reject the request unless the organization whose secret verified the payload equals the organization owning the resolved `Repository`/`Stack`.
- Add a `Repository#organization_login` cross-check inside `Shipit::Webhooks::Handlers::Handler` (or a shared before-dispatch check in `WebhooksController#create`) that raises/aborts if the resolved repository's owner is not the same organization that authenticated the webhook.

### Proof of Concept
1. Configure Shipit with multi-org secrets, e.g. `org-a` (target, victim) and `org-b` (attacker's own org), each with its own `webhook_secret`, per `config/secrets.development.shopify.yml`.
2. As an entity that legitimately possesses `org-b`'s `webhook_secret` (e.g., because they configured/own the GitHub App webhook for `org-b`), craft a `push` event JSON payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "org-b" },
       "full_name": "org-a/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=` + `HMAC-SHA1(org-b_webhook_secret, raw_body)` and POST it to `/github/webhooks` (or the mounted webhooks path) with header `X-Github-Event: push`.
4. In `WebhooksController#verify_signature`, `repository_owner` resolves to `"org-b"`, `Shipit.github(organization: "org-b")` is used, and the signature verifies successfully because it was computed with `org-b`'s actual secret — see [1](#0-0) .
5. `create` dispatches the same payload to `PushHandler`, whose `stacks`/`repository_name` resolves `"org-a/victim-repo"` — see [4](#0-3)  — enqueuing `GithubSyncJob` for a stack that belongs to `org-a`, entirely under attacker control of `ref`/`after`, despite the attacker having no credentials for `org-a` whatsoever.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
