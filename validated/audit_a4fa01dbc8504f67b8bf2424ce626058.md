### Title
`StatusHandler` writes commit statuses via an unscoped `Commit.where(sha:)` lookup, allowing a status webhook from any repository to mutate another repository's stack/commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0)  and never calls the base class's repository-scoping helper `Handler#stacks` [2](#0-1) . The `ExplicitParameters` schema only enforces `requires :sha, String` type/presence, with no repository or stack constraint [3](#0-2) . Because SHA is a global namespace across the `Commit` table (not scoped per repository at query time), any webhook payload whose `sha` collides with a commit belonging to a different, unrelated stack will mutate that commit's status.

### Finding Description
Binding under test: `∀ sha, Commit.where(sha: params.sha) == Commit.where(sha: params.sha, stack: Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks)`. This is false: `Handler#stacks` exists precisely to scope lookups to `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) , but `StatusHandler#process` never invokes `stacks`; it queries `Commit` globally by `sha` alone [1](#0-0) .

Request path: `WebhooksController#create` parses JSON and dispatches to handlers for the `status` event without any per-field repository check beyond signature verification tied to `repository_owner` [5](#0-4) . `verify_signature` only confirms the payload was signed with the secret belonging to the GitHub App/organization named in `params.dig('repository','owner','login')` [6](#0-5)  - it does not check that `sha` belongs to that same repository. `drop_unhandled_event` and `check_if_ping` only gate on event type [7](#0-6) .

Exploit flow: An attacker who owns/controls a repository legitimately connected to Shipit (their own org's GitHub App installation, so `verify_signature` passes with their own valid secret) can send a genuine, correctly-signed `status` webhook for their own repository, but set the `sha` field to the hash of a commit that also exists as a `Commit` row belonging to a victim stack. Since git commit hashes are content-derived, an attacker can trivially produce a commit with an identical SHA to one already ingested into a victim's tracked repository (e.g., by forking the victim's public repo and replaying/cherry-picking the exact same commit, which preserves the SHA) - or, more directly, simply set `sha` to any known SHA of a victim commit obtained from public GitHub. `Commit.where(sha: params.sha)` returns rows across *all* stacks matching that SHA, and `commit.create_status_from_github!(params)` writes a status onto that commit regardless of which repository the webhook actually came from. This is a structural absence of scoping, not a validation edge case: no `repository`/`stack` field exists anywhere in the `ExplicitParameters` schema, and `process` performs zero repository-membership check before mutating.

Existing guards do not stop this: `verify_signature` validates the webhook signature against the *sender's own* organization/app secret, so it succeeds for the attacker's own repository - it says nothing about the `sha` field's ownership. `ExplicitParameters` performs pure type validation (`String` for `sha`), with no scoping logic. `Handler#stacks` exists in the base class as the scoping primitive but `StatusHandler` simply does not call it.

### Impact Explanation
A commit `status` (e.g., CI check state `success`/`failure`) can be written onto a commit belonging to a repository/stack the attacker does not own or control, via `Commit#create_status_from_github!`. Commit statuses feed into `required_statuses`/`blocking_statuses` gating used to determine deployability [8](#0-7) . Forging a passing status on a victim's commit can influence deploy/merge gating decisions for that stack - this is a cross-tenant write ("a payload for one repository mutating another's stack, commit") matching the Critical impact category. The attack is repeatable against any commit whose SHA the attacker can learn (all commit SHAs on public GitHub repos are public) and is not limited to a single stack.

### Likelihood Explanation
Preconditions: the attacker needs at least one repository already connected to Shipit under their control (or any org onboarded to Shipit) so that a genuinely GitHub-signed `status` webhook can be delivered - this is consistent with the stated attacker capability ("push to a fork, ... emit webhooks from a repository they own"). No Shipit session, API token, or Shipit/GitHub secrets are required; GitHub itself computes and sends the valid signature for the attacker's own repository. The target `sha` need only be a known public commit hash already ingested into Shipit's `Commit` table for a target stack (learnable via GitHub UI/API for public repos, or via git's content-addressing by reproducing the same commit). This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the requesting repository's commits, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern the base `Handler#stacks` method was designed to provide, and apply the same audit to any other handler doing bare `Commit`/`Stack` lookups by attacker-controlled identifiers without joining through `stacks`.

### Proof of Concept
Minitest plan (no live GitHub, `test/` scope only for illustration - the audit prohibits shipping under `test/**` but the proof is described here as instructed):
1. Assert the schema has no repository-scoping field:
   `assert_nil Shipit::Webhooks::Handlers::StatusHandler.param_parser.attributes[:repository]`
   (and confirm the attribute set is exactly `{sha, state, description, target_url, context, created_at, branches}`).
2. Create two stacks/repositories, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`).
3. Create `victim_commit = Commit.create!(stack: victim_stack, sha: "deadbeef...")`.
4. Build a `status` payload with `repository.full_name = "attacker/repo"` and `sha: "deadbeef..."`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert `victim_commit.statuses.reload.exists?` is true - i.e., a status was written to the victim's commit purely because the SHA matched, despite the webhook's `repository` field naming `attacker/repo`.
7. Contrast with `Handler#stacks`, showing `StatusHandler.new(payload).send(:stacks)` correctly resolves to `attacker_stack.stacks` only, proving the mismatch between what scoping *is available* and what `process` *actually uses*.
