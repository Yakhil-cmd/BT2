### Title
Cross-repository CI status forgery via webhook signature/repository binding mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook is authenticated against the GitHub organization derived from `repository.owner.login` in the payload, but `Shipit::Webhooks::Handlers::StatusHandler#process` applies the resulting `state`/`context`/`target_url` to *any* commit matching the payload's `sha`, with no check that the commit belongs to a repository owned by the authenticated organization. This breaks the binding "organization whose webhook_secret authenticated the request" == "repository/commit whose CI status is written," letting an operator of one legitimately-configured GitHub organization inject fabricated CI status for a commit belonging to a different, unrelated repository/stack in the same shared Shipit instance.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret to validate against using only the organization implied by the payload: [1](#0-0) 

`repository_owner` is read straight out of attacker-controlled JSON body fields: [2](#0-1) 

Verification itself is a pure HMAC check of the raw body against `Shipit.github(organization: repository_owner).webhook_secret`: [3](#0-2) 

Shipit explicitly supports multiple independently-configured GitHub organizations sharing one instance, each with its own `webhook_secret`: [4](#0-3) 

Once signature verification passes (using the secret belonging to `repository.owner.login`), the event is dispatched to `StatusHandler`: [5](#0-4) 

`StatusHandler#process` looks up commits **only by `sha`**, with no scoping to the repository/organization that was actually authenticated: [6](#0-5) 

Because `sha` values are effectively global identifiers with no per-tenant namespacing enforced in this lookup, and the authentication step never re-derives or re-checks which repository the `sha` belongs to, a caller who is a legitimate operator of "OrgA" (and therefore knows OrgA's `webhook_secret`, which they configured themselves) can:
1. Compute a valid `X-Hub-Signature` over an arbitrary JSON body using OrgA's secret.
2. Set `repository.owner.login = "OrgA"` (passes `verify_signature`).
3. Set `sha` to a commit hash belonging to "OrgB"'s repository/stack (a tenant the attacker does not administer).
4. POST to `/webhooks`.

`Commit.where(sha: params.sha)` will match OrgB's commit and call `commit.create_status_from_github!(params)`, writing an attacker-chosen `state`/`context`/`description`/`target_url` onto it — despite the request only ever being authenticated as belonging to OrgA.

### Impact Explanation
CI/commit statuses gate whether a commit is considered "deployable" and whether it can pass the merge queue's required checks (per `Shipit::CommitChecks` / `Stack#deployable_status`, referenced from `app/models/shipit/commit_checks.rb` and `app/models/shipit/stack.rb`). By forging a passing status (e.g. `state: "success"`, matching a `context` a target stack treats as required) on a commit in a repository/organization the attacker has no legitimate access to, the attacker can make that commit appear CI-green, unblocking the deploy button or a merge-queue gate for a stack they do not own — an unauthorized-deploy-enabling condition. This satisfies the "escalation... unauthorized deploy" High-severity bar, mirroring the original report's core defect class: a value (claimable amount / verified status) is written based on unvalidated cross-entity input, letting an attacker cause the system to attribute state to an entity it does not control.

### Likelihood Explanation
Exploitation requires only that the attacker already administers *some* GitHub organization/webhook configuration wired into the same Shipit deployment (a common, low-privilege, self-service scenario for multi-tenant Shipit installs, as documented in `docs/setup.md` and `config/secrets.development.shopify.yml`), plus knowledge of a target commit SHA (trivially obtainable from a public repo's commit history or PR). No access to the victim org's `webhook_secret`, `ApiClient` token, or GitHub App private key is required — only the attacker's own, legitimately-possessed webhook secret for their own org. This is easily scriptable and repeatable.

### Recommendation
`StatusHandler` (and any other handler resolving records purely by payload-supplied identifiers such as `sha`) must scope its lookup to the repository implied by the same trust boundary used for signature verification — e.g., join through `Commit -> Stack -> Repository` and require `repository.full_name`/`repository.owner` (validated against the organization that signed the request) to match before applying the status update, rejecting the event otherwise.

### Proof of Concept
1. Attacker legitimately configures/administers GitHub org `AttackerOrg` on a shared Shipit instance and knows `AttackerOrg`'s `webhook_secret`.
2. Attacker identifies a target commit `sha` belonging to `VictimOrg/victim-repo`, which has a stack in the same Shipit instance.
3. Attacker builds a `status` event payload:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/attacker-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `AttackerOrg`'s known `webhook_secret` over the raw JSON body.
5. POST to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` succeeds (secret matches `AttackerOrg`). `StatusHandler#process` runs `Commit.where(sha: "<victim_commit_sha>")`, finds the commit belonging to `VictimOrg/victim-repo`, and calls `create_status_from_github!`, writing the forged `success` status onto a commit in a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
