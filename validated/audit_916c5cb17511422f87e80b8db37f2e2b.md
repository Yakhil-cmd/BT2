### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but handlers act on the unrelated `repository.full_name` (or `organization.login` for `membership`) taken from the same attacker-controlled JSON body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against by reading `repository.owner.login` (or `organization.login`) out of the raw JSON body, then verifies the raw body against that organization's configured `webhook_secret`. Every downstream `Shipit::Webhooks::Handlers::Handler` then re-reads the *same* JSON body but resolves the target repository/stack/team using a different field (`repository.full_name` for repo-scoped events, `organization.login` for `MembershipHandler`). Nothing ties these two lookups together, so the field that is cryptographically authenticated is not the field that is acted upon.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` maps this attacker-supplied string to one of several independently configured GitHub Apps/organizations, each with its own `webhook_secret` (`github_app_config`) [3](#0-2) . This is Shipit's documented multi-tenant configuration model (`github_organizations`), so a single Shipit instance can legitimately host webhooks for several distinct organizations, each with its own secret that its own repo administrators know (GitHub shows the webhook secret configuration to whoever configures the webhook, i.e., someone with admin rights on Org A's repository/app).

After signature verification, `create` dispatches the very same JSON body to handlers:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [4](#0-3) 

But every handler resolves its target independently of `repository_owner`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 
and `Repository.from_github_repo_name` simply splits `"owner/name"` and looks the row up by those columns [6](#0-5) , with no cross-check against `repository.owner.login`.

Since `repository.owner.login` and `repository.full_name` are two independent keys inside the same attacker-controlled JSON body, an attacker who legitimately administers/owns the webhook for Organization A (and therefore knows Org A's `webhook_secret`, since GitHub itself surfaces webhook secrets to whoever configures them) can POST directly to the shared `/webhooks` endpoint with:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
signed with Org A's secret. `verify_signature` looks up Org A's `GitHubApp`, computes the HMAC over the exact raw body the attacker crafted, and it matches (the attacker controls both the secret input and the body), so the request passes. `PushHandler#process` then resolves `stacks` via `full_name = "org-b/victim-repo"` — a repository/org the attacker has no relationship to — and calls `stack.sync_github(expected_head_sha: params.after)` on it [7](#0-6) , i.e. Org A's authenticated identity is used to trigger actions against Org B's stack.

The same disconnect exists for `MembershipHandler`, which is not repository-scoped at all: it trusts `params.organization.login` to create/attach a `Team` and add/remove members from it [8](#0-7) , again with no verification that this organization matches the one whose secret validated the request signature.

The broken binding, stated as an equality that the code fails to enforce:
`organization_that_signed(repository.owner.login) == organization/repository_acted_upon(repository.full_name / organization.login)`

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. For `PushHandler`/other repo-scoped handlers, an attacker who controls one onboarded organization's webhook secret can force `GithubSyncJob` invocations, commit-status writes (`StatusHandler`), check-run refreshes, and pull-request/review-stack state changes (archive/unarchive, provisioning) against stacks belonging to a completely different, unrelated organization/repository configured on the same Shipit instance — a cross-repository write triggered under another organization's cryptographic identity. For `MembershipHandler`, it can fabricate/alter `Team`/`Membership` records tied to `Shipit.github_teams`-based authorization [9](#0-8) , without ever matching the org whose secret validated the request, which is an escalation into `Shipit.github_teams` authorization.

### Likelihood Explanation
Requires the attacker to already be an administrator of at least one organization configured on a multi-tenant Shipit deployment (so they know that organization's real `webhook_secret`) and to know or guess `owner/name` of a target stack hosted under a different organization on the same instance — both realistic in a shared/multi-tenant Shipit deployment where stack names and repository slugs are visible in the UI/API to any authenticated user.

### Recommendation
After successfully verifying the signature for organization `repository_owner`, require that every field the handler will act upon (`repository.full_name`'s owner segment, or `organization.login` for org-level events) matches `repository_owner` exactly, rejecting (422) any payload where they diverge, instead of independently trusting `repository.full_name`/`organization.login` deep inside each handler.

### Proof of Concept
1. Onboard/administer Organization A on a multi-org Shipit instance and note its configured `webhook_secret` (visible to whoever configured the GitHub App/webhook for Org A).
2. Craft a JSON body:
   ```json
   {"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"}, "ref": "refs/heads/main", "after": "<sha>"}
   ```
3. Compute `X-Hub-Signature: sha1=HMAC_SHA1(org_a_webhook_secret, body)` and set `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "org-a")` and successfully verifies the signature against the attacker-crafted body.
5. `PushHandler` resolves the stack via `repository.full_name = "org-b/victim-repo"` and invokes `stack.sync_github` on Org B's stack, even though only Org A's secret authenticated the request.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
