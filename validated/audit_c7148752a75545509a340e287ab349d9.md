### Title
Overwriting an asset's attestor list revokes access for previously-attested holders, freezing their existing outputs - (File: `storage.js`, `validation.js`)

### Summary
For assets with `spender_attested=true`, the asset definer can post a new `asset_attestors` message that fully replaces the current attestor list. `storage.readAsset()` always resolves the *latest* attestor-list unit and uses only that list to determine who is currently "attested." Every subsequent spend of that asset — including spends of outputs that were already legitimately received and validated as attested at receipt time — is re-checked against this new, possibly disjoint, attestor list. Holders whose attestations came from attestors dropped from the new list become permanently unable to move their existing balance of that asset, exactly mirroring the reported issue where switching a payment-type's balance tracker orphans balances/credits tied to the old tracker.

### Finding Description
`validateAttestorListUpdate` in `validation.js` allows the asset's definer to freely publish a brand-new attestor list for a `spender_attested` asset at any time, with no restriction preventing replacement of an already-set list and no requirement that the new list be a superset of (or compatible with) the old one: [1](#0-0) 

`storage.readAsset()` resolves attestors by selecting only the single most-recent `asset_attestors` unit for the asset and using exactly that list; there is no merging of previous lists or notion of “credit under the old list”: [2](#0-1) 

At spend time, `loadAssetWithListOfAttestedAuthors` and `filterAttestedAddresses` compute attestation membership strictly against attestations from attestors currently in `objAsset.arrAttestorAddresses` (i.e., the *current* list, not the list in force when the funds were received): [3](#0-2) 

`validatePayment` then requires at least one author to be attested by the current list, and for issuance the issuer specifically must be attested: [4](#0-3) 

Critically, when validating each individual payment input being spent, the code checks that the *owner_address of the input's output* is present in `objAsset.arrAttestedAddresses` — the live, current-list-derived set — not the set that was valid when the output was created/received: [5](#0-4) 

This is structurally the same defect as the MechMarketplace.sol issue: a single mutable pointer (`mapPaymentTypeBalanceTrackers` / the "latest asset_attestors unit") is overwritten without any migration of state tied to the old value, and every downstream operation (deliver/withdraw in the Solidity case, spend-validation here) is evaluated against the new value only. Legitimate holders of value validated under the old configuration are left stranded.

### Impact Explanation
This causes freezing of funds for legitimate holders: an address that received a `spender_attested` asset while properly attested by the attestor list in force at that time can be locked out of spending that exact balance forever if the definer later swaps the attestor list to a disjoint set (e.g., replacing a compromised/retired attestor, or a compliance provider migration). The affected holder never re-transacts to trigger re-validation, so the loss is silent and permanent unless the definer restores the old attestors or adds the holder's attestor back. This falls squarely under the accepted impact category of "AA/asset fund loss or freezing," and is more severe than the original low-risk report because here regular (non-privileged) asset holders — reachable simply by receiving/holding an asset — lose access to already-owned funds with no recourse other than depending on the definer's future choices.

### Likelihood Explanation
The path requires only: (1) an asset created with `spender_attested=true` (a completely normal use case for compliance-gated assets), and (2) the definer posting an `asset_attestors` update at some point after users have accumulated balances under the initial/previous list — an entirely permitted, expected, and even necessary maintenance action (e.g., rotating attestors). No malicious collusion, no privileged network role, and no protocol violation is needed; this is triggered by routine administrative asset management combined with normal user activity (receiving and later trying to spend the asset).

### Recommendation
When updating an asset's attestor list, require it to be a superset of, or otherwise preserve validity for, addresses that hold current unspent balances validated under the prior attestor set, or provide an explicit grandfathering/migration mechanism (e.g., allow spending if the owner was attested by *any* attestor list that was current at the time the output was created, verified via the definition/attestation history similar to how `address_definition_changes` retains history for `"seen definition change"`). At minimum, document this as an explicit design tradeoff and warn definers, as was done for the analogous MechMarketplace.sol issue, and consider preventing attestor-list updates that would strand outputs still on the current UTXO set from currently-attested owners.

### Proof of Concept
1. Definer creates asset A with `spender_attested: true` and attestor list `[X]` via the `asset` message (attestors seeded into `asset_attestors`), as recorded by `writer.js` on lines 218-235.
2. Attestor `X` attests holder `H`; `H` receives a payment output in asset `A` (validated successfully because `H` is in `arrAttestedAddresses` computed from list `[X]`, per `validation.js:2504-2507`).
3. Later, the definer posts a new `asset_attestors` message replacing the list with `[Y]` (disjoint from `[X]`), which passes `validateAttestorListUpdate` unconditionally since it only checks that the sender is the definer and the list is well-formed (`validation.js:2829-2848`).
4. `storage.readAsset` now resolves the attestor list to `[Y]` only, discarding `[X]` (`storage.js:1917-1946`).
5. `H` attempts to spend the previously received output. `loadAssetWithListOfAttestedAuthors`/`filterAttestedAddresses` compute `arrAttestedAddresses` against attestor `Y`; since `H` was never attested by `Y`, `H` is excluded, and `validatePaymentInputsAndOutputs` rejects the spend with "owner address is not attested" (`validation.js:2504-2507`), permanently freezing `H`'s previously-valid balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

// filter only those addresses that are attested (doesn't work for light clients)
function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
