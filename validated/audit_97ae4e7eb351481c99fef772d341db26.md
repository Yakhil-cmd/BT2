### Title
`status` webhook resolves commits by SHA alone, letting an org verified only for its own no-secret repository forge deploy-triggering statuses on a different org/stack that runs deploys as `Shipit.user` (bot_login) - ([File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to check purely from `repository.owner.login`/`organization.login` in the JSON body, via `Shipit.github(organization: repository_owner)`. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when that org has no `webhook_secret` configured. `StatusHandler` then does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with zero reference to `repository.full_name`, `repository.owner`, or any stack/organization scoping, so any commit sharing that SHA in any stack in the installation is mutated.

### Finding Description
The broken binding: the code implicitly assumes `repository.owner.login used to pick the signing secret == owner of the repository whose commit rows get mutated`. In fact these two values are never compared:

- `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login')` and `verify_signature` uses it to fetch `Shipit.github(organization: repository_owner)` and validate the HMAC signature against that org's `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that particular org has no `webhook_secret` configured (`lib/shipit/github_app.rb:76-83`), which is intended for single/no-secret setups but, in a multi-org config where at least one configured org has no secret, becomes a free pass to satisfy `verify_signature` for a payload whose real target repository belongs to an entirely different, secret-protected org.
- Once past `verify_signature`, `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not read `repository.full_name`/`owner` from the payload at all — its `ExplicitParameters` schema only declares `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` (lines 7-18). It runs `Commit.where(sha: params.sha)` globally across the whole `commits` table and calls `create_status_from_github!(params)` on every match, regardless of which stack/repository owns that commit.

Exploit flow: attacker registers/controls (or simply names) an organization `no-secret-org` for which the Shipit deployment has no `webhook_secret` configured (or is otherwise able to satisfy the signature check for that org). They send `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login = "no-secret-org"`, and a `sha` equal to a commit that already exists in the victim's stack `commits` table (commit SHAs are public git data the attacker can learn by inspecting the victim's GitHub repo/PRs). `verify_signature` resolves the config for `no-secret-org`, finds no `webhook_secret`, and accepts the request unconditionally. `StatusHandler` then finds the victim's `Commit` row purely by SHA and calls `create_status_from_github!`, injecting a fabricated `success` status. Via `Commit#add_status` → `stack.schedule_merges` and `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287,366-386`), a fabricated passing status can make `deployable?` true and enqueue `ContinuousDeliveryJob`, which triggers an autodeploy. On a stack where `bot_login` is configured, `Shipit.user` resolves to a real `User.find_or_create_by_login!(github.bot_login)` (`lib/shipit.rb:208-214`) that is used as the actor for such auto-triggered deploy/merge actions, so the forged status is not merely cosmetic — it can drive an unauthorized deploy executed under the bot's identity.

None of the listed guards close this gap: `verify_signature` only authenticates that *some* configured org's secret (or lack thereof) matches — it never re-checks that the authenticated org actually owns the repository/commit being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` never require or validate a `repository` field; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` check on this unauthenticated webhook endpoint by design; and `Commit.where(sha:...)` has no `stack_id` or repository predicate at all.

### Impact Explanation
An attacker who can get one weakly/unconfigured org's webhook path accepted (no secret set for that org) can inject fabricated CI status records into **any** commit row in the database matching a known SHA, irrespective of which stack/org that commit actually belongs to — a payload authenticated for one repository/org mutating another's commit/stack state. Where the victim stack has `continuous_deployment?` enabled and a `bot_login` configured, this can escalate to an unauthorized, bot-identity-driven deploy/merge, matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy"). The blast radius spans every stack/tenant sharing the same Shipit installation, since `Commit` lookup is global and unscoped.

### Likelihood Explanation
Preconditions: the Shipit instance must have at least one GitHub org configured with `Shipit.github(organization: X)` returning a config lacking `webhook_secret` (or an org the attacker can otherwise satisfy), and a target stack with commits whose SHAs are learnable by the attacker (trivial for public/forkable repos) and with continuous deployment + bot_login enabled for higher impact. This is a plausible, low-cost, and repeatable operation for an unauthenticated attacker who never needs any Shipit secret, session, or API token — just knowledge of a target SHA and the name of a no-secret org.

### Recommendation
Have `StatusHandler` (and other webhook handlers that resolve records purely by cross-cutting identifiers like SHA) scope their lookup to the repository/organization that authenticated the request — e.g., resolve the target `Stack`/`Repository` from `params.dig('repository','full_name')`, verify it belongs to the same org used in `verify_signature`, and constrain `Commit.where(sha: ..., stack_id: matching_stacks)` before mutating. Additionally, `verify_signature` should be hardened so that an org with no `webhook_secret` cannot be used to authenticate events whose payload claims to affect a different, secret-protected repository/org.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in test secrets: `secret-org` (has `webhook_secret`) owning stack `victim_stack`/commit `victim_commit` (sha `abc123...`), and `no-secret-org` (no `webhook_secret`).
2. Also create, under `no-secret-org`, a commit with a colliding/attacker-chosen sha equal to `victim_commit.sha` belonging to a *different* stack, or directly rely on `Commit.where(sha:)` returning `victim_commit` even though the payload's `repository.owner.login` is `no-secret-org`.
3. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: victim_commit.sha, state: "success", repository: { owner: { login: "no-secret-org" }, full_name: "no-secret-org/some-other-repo" } }`, and no valid `X-Hub-Signature` (or an arbitrary one).
4. Assert: `verify_signature` passes / response is `:ok` (not `:unprocessable_entity`), and `victim_commit.statuses.count` increases by 1 with `state == "success"` — i.e., `Shipit.github(organization: "secret-org")`'s secret was never used/checked, yet `victim_stack`'s commit (owned by `secret-org`) was mutated by a request authenticated only under `no-secret-org`. Optionally assert `ContinuousDeliveryJob` is enqueued for `victim_stack` when `continuous_deployment?` and `bot_login` are set, demonstrating the deploy-triggering effect under the bot identity.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
