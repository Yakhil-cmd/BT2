### Title
Front-running `SystemInstruction::CreateAccount` to permanently DoS deterministic-address account creation via lamport-prefund griefing - (File: `programs/system/src/system_processor.rs`)

### Summary
The Nouns Builder `Governor` bug allowed anyone to permanently block a specific, deterministically-derived identifier (`proposalId`) from ever being used again by writing to the storage slot associated with that identifier before the legitimate creator's transaction landed. The direct Agave analog is the System Program's `CreateAccount` handler, which treats *any* nonzero lamport balance on the target address as proof the account is "already in use" and unconditionally fails, even though a plain lamport transfer carries no authorization semantics for account creation.

### Finding Description
`create_account` in `programs/system/src/system_processor.rs` rejects account creation solely because the destination account already holds lamports: [1](#0-0) 

For any address whose pubkey is publicly derivable ahead of time — e.g. `create_with_seed`/`CreateAccountWithSeed` derived addresses (used pervasively by CLI tooling such as stake account derivation) or any address a program/user reveals before submission (e.g. visible in a pending mempool transaction) — an unrelated party can front-run the legitimate `CreateAccount` transaction with a trivial `SystemInstruction::Transfer` of 1 lamport to that address. Once the target has `lamports > 0`, every subsequent `CreateAccount` targeting that exact address permanently fails with `SystemError::AccountAlreadyInUse`, exactly mirroring how cancelling a front-run Nouns Builder proposal permanently blocks the original `proposalId`. [2](#0-1) 

This shows how derived addresses (via `derive_stake_account_address`/`create_account_with_seed`) are computed deterministically from public inputs (`base_pubkey`, `index`) well before the creating transaction is sent, giving an attacker time to precompute and pre-fund the target address.

Agave's own developers have already identified and partially mitigated this exact class of bug: `SystemInstruction::CreateAccountAllowPrefund` was introduced specifically to allow account creation even when the target address already carries lamports: [3](#0-2) 

The doc comment states it is "intended for use where account has already had rent paid in whole or in part before creation" — an explicit acknowledgment of the prefund-griefing scenario. However, this new instruction is feature-gated and must be deliberately used by callers: [4](#0-3) 

The plain `SystemInstruction::CreateAccount` path used throughout the existing ecosystem (CLI, stake program, vote program, and countless on-chain programs performing `CreateAccountWithSeed`/PDA-adjacent flows) remains fully vulnerable, since it has no equivalent prefund-tolerance and no per-creator nonce/anti-front-running protection analogous to what the Nouns Builder fix would need.

### Impact Explanation
Any unprivileged transaction sender can permanently prevent a specific, otherwise-legitimate account creation from ever succeeding at a known target address, denying service to the intended creator/protocol flow (e.g., blocking a user's or program's `create_with_seed` derived stake/token/PDA account from ever being initialized at that address). This is a low-cost (1 lamport + fee), persistent, address-specific griefing/DoS vector reachable from a single ordinary transaction, matching the "any unsigned fund movement... consensus-visible account state corruption" class of the original finding, scoped down to a griefing/DoS rather than fund theft.

### Likelihood Explanation
The precondition — a publicly predictable destination pubkey before the `CreateAccount` transaction is sent — is common: `create_with_seed` derived addresses are deterministic from `(base, seed, owner)`, and other flows publish target account pubkeys in advance (e.g., through client-side derivation, on-chain PDA-like usage on the System Program, or mempool visibility of a pending `CreateAccount` transaction). The attack itself requires only a 1-lamport `Transfer` and normal transaction fees, no special privilege, and it is 100% reliable due to the strict `lamports > 0` check.

### Recommendation
Apply the same remediation direction already adopted for `CreateAccountAllowPrefund`, but to the default `CreateAccount` path (or otherwise ensure ecosystem migration off the un-mitigated instruction): distinguish "account already meaningfully initialized" (nonzero data length or foreign owner) from "account merely holds stray lamports," and allow `CreateAccount` to succeed by absorbing pre-existing lamports into the new account rather than treating any positive balance as an unconditional `AccountAlreadyInUse` failure. Until adoption is complete, flag `CreateAccount` (unlike `CreateAccountAllowPrefund`) as griefable for any caller relying on precomputed/deterministic target addresses.

### Proof of Concept
1. Attacker observes/derives that address `D` will be the target of a future `CreateAccount` instruction (e.g., `D = Pubkey::create_with_seed(base, seed, owner)`, or `D` is visible as the `to` account in a pending transaction in the mempool).
2. Attacker submits `SystemInstruction::Transfer { lamports: 1 }` from any funded account to `D`, landing before the legitimate creation transaction.
3. The legitimate `CreateAccount` transaction now hits: [5](#0-4) 
and fails permanently with `SystemError::AccountAlreadyInUse`, since `D.lamports() > 0` regardless of who funded it or why.
4. `D` can never be initialized via `CreateAccount` again; only `CreateAccountAllowPrefund` (feature-gated, and requiring the caller to have opted into using this instruction instead) can recover the address, confirmed by the dedicated test `test_create_account_allow_prefund_already_in_use` demonstrating the difference in behavior between the two instructions: [6](#0-5)
