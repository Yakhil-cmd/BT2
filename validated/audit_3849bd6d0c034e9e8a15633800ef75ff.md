### Title
Webhook signature verification is keyed to an attacker-controlled organization field that is decoupled from the repository the event payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, a value read directly out of the untrusted, unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once "verified", every `Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` using a *different* field from the same untrusted body, `params.dig('repository','full_name')`. Nothing binds these two fields together, so the identity that "authenticates" the request (the organization whose secret matched) is not required to equal the identity the request is allowed to mutate (the repository/stack acted on).

### Finding Description [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves a per-organization `GitHubApp` config, whose `webhook_secret` may be blank for a given org: [2](#0-1) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If any organization registered under `Shipit.github_organizations` (multi-org config, see `lib/shipit.rb` `github_app_config`) has no `webhook_secret` configured, `verify_webhook_signature` unconditionally returns `true` for a payload whose `repository.owner.login`/`organization.login` names that org — regardless of the HMAC header supplied. Every downstream `Handler` then determines the actually-affected `Repository`/`Stack` from `repository.full_name` in the very same JSON body: [3](#0-2) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Because `repository.owner.login` (used for signature routing) and `repository.full_name` (used for the actual write target) are independent, attacker-controlled strings in the same unauthenticated body, an attacker can set `repository.owner.login`/`organization.login` to an org with no `webhook_secret` (satisfying the signature check trivially) while setting `repository.full_name` to point at a completely different, legitimately-configured repository's stack. This breaks the binding: organization-that-authenticated == repository-that-is-written.

Handlers reachable this way include `PushHandler` (triggers `stack.sync_github`), `StatusHandler`/`CheckSuiteHandler` style handlers, and the `PullRequest::*Handler`s that archive/unarchive review stacks, update commit statuses, and mutate `PullRequest` records — all keyed off `repository.full_name`, not `repository.owner.login`.

### Impact Explanation
This does not directly grant RCE, but for any Shipit deployment with more than one GitHub organization configured (multi-tenant `secrets.github` schema) where at least one organization's webhook secret is unset/blank, an unauthenticated attacker gains a forgery primitive to inject arbitrary webhook events against any repository/stack tracked by the instance, without ever knowing that stack's real webhook secret. This can drive unwanted syncs, review-stack archive/unarchive, and PR/commit-status state changes on a target repository the attacker does not control — an authorization-boundary crossing between "which org's secret validated this request" and "which repository's state gets mutated." It falls short of the strictly Critical categories (no direct RCE/token exfiltration/cross-repo *write* to source code), but represents an unauthenticated cross-tenant state-mutation path contingent on a specific but plausible multi-org misconfiguration.

### Likelihood Explanation
Requires (a) the instance to run in multi-organization mode and (b) at least one configured organization to have an empty/absent `webhook_secret`. This is a configuration precondition, not a code defect that is universally exploitable — a well-configured deployment with a secret set for every organization is not affected, since `verify_webhook_signature` would then require a real signature per org, and the analog to the Sherlock bug (mismatched bound quantities) would not be reachable without already holding a valid secret (out of scope). Given the reliance on this optional misconfiguration, likelihood is Low-Medium rather than the "always reachable" quality expected of the strongest analogs.

### Recommendation
Require `repository.owner.login`/`organization.login` to match the owner of `repository.full_name` before processing, and/or refuse to treat a blank `webhook_secret` as "verified" — instead reject signature verification entirely (fail closed) when no secret is configured for an organization that has repositories/stacks registered, or bind the signature-verifying organization to the same identity used to resolve the target repository within `Handler#stacks`.

### Proof of Concept
1. Configure Shipit in multi-org mode with organizations `org-a` (no `webhook_secret` set) and `org-b` (real repo `org-b/target-repo` with a stack tracked, `webhook_secret` set).
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
with any (or missing) `X-Hub-Signature` header.
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally.
4. `PushHandler#process` resolves the target via `Repository.from_github_repo_name("org-b/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on `org-b`'s real stack, despite the request never being authenticated by `org-b`'s secret. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
