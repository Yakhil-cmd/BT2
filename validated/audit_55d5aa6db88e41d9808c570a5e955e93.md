Confirmed: `Api::CCMenuController` is nested under the same `/stacks/*stack_id` route scope as the other scoped API resources (deploys, tasks, hooks) [1](#0-0) , but unlike `Api::BaseController#stack`, which resolves the requested stack through the client-scoped `stacks` relation [2](#0-1) , `CCMenuController#stack` bypasses that scoping and resolves directly against the global `Stack` relation [3](#0-2) . Permission checking is purely a flat list-membership test on the `ApiClient#permissions` array and never consults `stack_id` [4](#0-3) .

### Title
Stack-scoped API client can read any stack's build status via CCMenu endpoint (authorization scope bypass) - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token that is deliberately scoped to a single stack (via its `stack_id` column, e.g. `here_come_the_walrus` in the fixtures) is meant to only ever resolve/act on that one stack when calling scoped API endpoints. `Api::CCMenuController` overrides the `stack` resolution method to use the unscoped `Stack.from_param!` instead of the client-scoped `stacks.from_param!` used everywhere else in `Api::BaseController`, letting any valid, minimally-permissioned token read build/deploy status for stacks it was never granted access to.

### Finding Description
`Api::BaseController` defines the authorization-scoping primitive used by every other stack-nested API controller:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the binding: `client.stack_id (if set) == stack resolved from params[:stack_id]`. `Api::DeploysController`, `Api::TasksController`, etc. inherit this and are therefore properly confined to the client's authorized stack, as verified by the "an api client scoped to a stack will only see that one stack" test [5](#0-4) .

`Api::CCMenuController`, mounted under the identical `/stacks/*stack_id/ccmenu` route [6](#0-5) , redefines `stack` to skip this scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [7](#0-6) 

The only gate remaining is `require_permission :read, :stack` [8](#0-7) , which calls `ApiClient#check_permissions!` — a flat membership check against the `permissions` array that never references `stack_id` [4](#0-3) . This mirrors the reported bug class exactly: a check verifies *something is present/true* (`permissions.include?("read:stack")`, analogous to `rd > 0`) instead of verifying the *correct, narrower binding* (`stack_id == requested stack`, analogous to `rd > minDuration_`). Consequently, any `stack_id`-scoped token with `read:stack` permission can pass `stack_id` for a different, unauthorized stack and still get a `200 OK`.

### Impact Explanation
This breaks the "stack a token authorizes vs. stack it touches" binding. A token issued for one repository/stack (e.g., a CI integration token scoped to a private internal stack) can be replayed against `/api/stacks/<other_owner>/<other_repo>/<env>/ccmenu` to read that other stack's `name`, `lastBuildStatus`, `lastBuildLabel` (a commit SHA), `lastBuildTime`, and `webUrl` [9](#0-8)  — data the token holder was never authorized to see. This is an unauthorized cross-stack read of stack/deploy state using credentials that are supposed to be confined to a single stack, matching the "unauthenticated read of stack state, task streams or deploy output" class of High-severity issue via an authorization-scope escalation (the attacker does hold a valid but narrowly-scoped credential, and escalates its reach across stack boundaries).

### Likelihood Explanation
Exploitation only requires possessing a valid, low-privilege, single-stack-scoped API client token (e.g., one deliberately created for a specific project's CI integration) and knowledge/guessing of another stack's `owner/repo/environment` identifier, which is often predictable or discoverable (GitHub org/repo names). No additional secrets, elevated permissions, or session access are needed beyond the already-issued scoped token.

### Recommendation
Make `Api::CCMenuController#stack` reuse the same client-scoped resolution as `Api::BaseController`, i.e. remove the override and rely on `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` binding is enforced consistently across all stack-nested API endpoints, including CCMenu.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to stack `owner/repoA/production` with permission `read:stack` (analogous to fixture `here_come_the_walrus`, scoped to `shipit` stack) [10](#0-9) .
2. Using that client's `authentication_token`, call `GET /api/stacks/other_owner/other_repo/production/ccmenu` (a stack the client is not scoped to).
3. Because `CCMenuController#stack` resolves via unscoped `Stack.from_param!` rather than `current_api_client`-scoped `stacks.from_param!`, the request succeeds with `200 OK` and returns `other_repo`'s build name, last build status, last build SHA (`lastBuildLabel`), and `webUrl`, despite the token only being authorized for `owner/repoA/production`.
