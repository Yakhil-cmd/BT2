### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` binds the validity of an inbound GitHub webhook to a single organization/app config, selected from the payload's `repository.owner.login` (or `organization.login`). Every other webhook handler that touches persisted data additionally scopes its side effects to the repository named in the payload via `Handler#stacks` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`). `StatusHandler`, however, never uses that repository scoping: it looks up commits purely by SHA across the *entire* database and writes a status onto every match, regardless of which repository/organization actually owns that commit.

### Finding Description
`WebhooksController#verify_signature` in [1](#0-0)  selects the GitHub App/organization config used to validate `X-Hub-Signature` from `repository_owner`, computed as: [2](#0-1) 

This only proves the request was legitimately signed *for that organization*. It says nothing about which repository/commit the payload is allowed to mutate.

The base `Handler` class enforces that additional binding for most events by scoping to the repository named in the payload: [3](#0-2) 
`PushHandler` and `CheckSuiteHandler` both use this `stacks` helper to constrain their effects to the repository that was actually authenticated. `StatusHandler` does not: [4](#0-3) 

`StatusHandler#process` calls `Commit.where(sha: params.sha)` with no repository/stack scoping at all, then calls `commit.create_status_from_github!(params)` for every match anywhere in the database. Since git commit SHAs are content-addressed, an attacker who controls any repository that has the Shipit GitHub App installed (their own repo, a fork, etc.) can:
1. Fabricate a commit whose tree, parents, message, author and committer (including timestamps) exactly match a target commit that exists in a victim stack/repository they have no access to (feasible when the victim commit is public, e.g. an open-source repo, or otherwise known).
2. Push that commit to their own repo and post a GitHub Status via the Statuses API (which they can do with only `repo:status` on their own repository) or trigger CI to do it.
3. GitHub sends a `status` webhook, correctly signed with the attacker's own organization's `webhook_secret`, satisfying `verify_signature`.
4. `StatusHandler` matches the SHA against *all* `Commit` rows sharing that value, including the one belonging to the victim stack, and writes the forged state/context/target_url onto it.

This breaks the binding "organization authenticated == repository/commit actually written," because the signature only proves authenticity for the attacker's own org, while the actual write target is chosen purely by SHA equality with no ownership check.

### Impact Explanation
Commit statuses are consumed by `ci.require` checks (`Shipit::DeploySpec`/`Stack` CI gating) to decide whether a commit is deployable. Forging a passing status on a victim commit that the attacker does not control can bypass CI safety gates and enable an unauthorized deploy of that commit in the victim's stack — this matches the Critical "unauthorized deploy" impact category, since the write crosses a repository boundary that the webhook-signature check was supposed to enforce.

### Likelihood Explanation
Exploitation requires only: (a) the attacker's own GitHub App-installed repository (unprivileged relative to the victim — no victim webhook_secret, GitHub App key, or Shipit session needed), and (b) the ability to reproduce an identical commit SHA (straightforward for any publicly known commit, or when timestamps/content can be duplicated). No interaction with the victim's credentials is needed, making this a realistic cross-tenant issue for any Shipit deployment serving multiple repositories/organizations.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the repository via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (or the `stacks` helper already provided by `Handler`) and restrict the `Commit.where(sha:)` lookup to commits belonging to that repository's stacks before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker owns `attacker-org/decoy-repo`, which has the Shipit GitHub App installed (its own `webhook_secret`).
2. Attacker learns/reproduces a commit SHA `S` that also exists in `victim-org/target-repo`, tracked by a Shipit stack requiring CI status `ci-check`.
3. Attacker creates a commit with SHA `S` in `decoy-repo` (matching tree/parents/author/committer/message/timestamps) and posts a `success` status for context `ci-check` via the Statuses API on `decoy-repo`.
4. GitHub sends a `status` webhook signed with `attacker-org`'s `webhook_secret`; `verify_signature` passes because it only checks against `attacker-org`'s app config.
5. `StatusHandler#process` runs `Commit.where(sha: 'S')`, which returns the commit row for `victim-org/target-repo` as well, and calls `create_status_from_github!`, marking the victim's commit as passing `ci-check` — potentially unblocking an unauthorized deploy in `victim-org/target-repo`.
