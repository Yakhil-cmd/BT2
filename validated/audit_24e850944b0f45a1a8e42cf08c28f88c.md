Based on my investigation, I found a genuine analog to the reported gas-limit DoS pattern in ocore's AA payment-composition logic.

### Title
Unbounded iteration over an attacker-inflatable set of outputs in `completePaymentPayload`/`iterateUnspentOutputs` can freeze AA fund responses - (File: aa_composer.js)

### Summary
`BountyCore.getLockedFunds()` in the reference report loops over an attacker-inflatable `deposits` array with no bound, causing `refundDeposit()` to run out of gas. The ocore analog is in `aa_composer.js`'s `sendUnit()` → `completePaymentPayload()` → `iterateUnspentOutputs()`, which iterates over all of an AA's unspent outputs fetched by `readStableOutputs()`/`readUnstableOutputsSentByAAs()` with no `LIMIT` clause, and — for AAs using a "send-all" output pattern — never breaks out of the loop early.

### Finding Description
When an AA response message contains a "send-all" output (`{address: ...}` with no `amount`, a common oscript idiom to "return everything received"), `completePaymentPayload` calls `readStableOutputs`/`readUnstableOutputsSentByAAs` which query:
```
SELECT unit, message_index, output_index, amount, output_id
FROM outputs CROSS JOIN units USING(unit)
WHERE address=? AND asset=... AND is_spent=0 AND sequence='good' AND main_chain_index<=?
  AND output_id NOT IN(...)
ORDER BY main_chain_index, unit, output_index
``` [1](#0-0) 

with no `LIMIT`. `iterateUnspentOutputs` then walks every returned row:
```
if (total_amount === target_amount && payload.outputs.length > 0) {
    bFound = true;
    if (send_all_output)
        continue;   // does NOT break — keeps consuming every row
    else
        break;
}
``` [2](#0-1) 

Because the only anti-dust protection is a per-output minimum size filter (`amount>=FULL_TRANSFER_INPUT_SIZE`, roughly 60 bytes) rather than a cap on the *number* of outputs, an attacker (an unprivileged unit poster) can send an AA address many thousands of tiny payments each just above that threshold. Each payment is a legitimate, individually valid unit that any full/light node would accept via ordinary unit validation — no special privilege is required. This grows the AA's `outputs` row-set without bound; the query and the JS loop scale with that count on every subsequent AA invocation that composes a send-all response.

### Impact Explanation
Whenever the target AA processes a trigger and tries to build a payment response containing a send-all output, it must (re)query and fully iterate the ever-growing output set. This is executed identically by every node validating the AA response unit (AA execution is deterministic and must be reproduced by all validators), so the cost is imposed network-wide, not just on the composer. If the output count grows large enough, unit composition/validation for that AA becomes prohibitively slow or effectively stalls, preventing the AA from ever completing a response. This matches the "AA fund loss or freezing" impact category: the AA's balance becomes permanently locked because it can no longer produce a valid, timely response, and legitimate users can no longer interact with it.

### Likelihood Explanation
Likelihood is moderate-to-high: sending dust payments to a public AA address costs only the standard low unit fee (bytes for a payment message), and no owner/permission is required — this is exactly the "unprivileged unit poster" class of attacker allowed by the scope. The precondition is that the target AA's response logic uses a send-all output (a well-documented, commonly-used AA idiom), which is common in escrow/proxy/vault-style AAs (e.g. `test/samples/fundraising_proxy.oscript` refunds contributions via full-balance transfers). The attack does not require any race condition or timing — steady, cheap spam over time is sufficient to grow the output set.

### Recommendation
- Add a `LIMIT` to `readStableOutputs`/`readUnstableOutputsSentByAAs` bounded by `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (as already enforced for indivisible-asset coin selection, see `arrPayloadsWithProofs.length >= constants.MAX_MESSAGES_PER_UNIT - 1` check in `indivisible_asset.js`) [3](#0-2) , and stop consuming further rows once that many inputs have been collected even for send-all outputs.
- Enforce a minimum-output-value threshold that scales with the number of outputs already held by the address, or track/limit the total number of unspent outputs an address may accumulate from low-value payments, to prevent dust-count inflation regardless of per-output size.
- Consider consolidating/pruning tiny outputs opportunistically (e.g., merging dust on each AA invocation) rather than only filtering by minimum amount.

### Proof of Concept
1. Deploy or target an existing AA whose response logic includes a send-all payment output (e.g., a refund/withdraw pattern like `test/samples/fundraising_proxy.oscript`).
2. As an unprivileged attacker, repeatedly post ordinary payment units sending a large number (e.g., tens of thousands) of tiny outputs (each ≥ `FULL_TRANSFER_INPUT_SIZE`, e.g. 61+ bytes) to the AA's address. Each such unit is independently valid and cheap to post.
3. Trigger the AA so that it attempts to compose a send-all payment response. `readStableOutputs` returns all matching unspent outputs (no `LIMIT`), and `iterateUnspentOutputs` iterates every one of them due to the `continue` (not `break`) branch for `send_all_output`.
4. As the attacker keeps adding dust outputs, the query and iteration cost grows unbounded, making it progressively harder (and eventually practically impossible) for the AA to compose/validate its response, freezing the AA's ability to return funds to legitimate users.
