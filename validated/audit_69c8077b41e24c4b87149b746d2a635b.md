### No vulnerability found for this question.

The premise is factually incorrect: `deposit` (mainnet/contracts/vault/v0-vault-stx.clar:763) computes shares via `convert-to-shares-preview`, not `convert-to-assets-preview` [1](#0-0) . `convert-to-assets-preview` is only used by `redeem` (mainnet/contracts/vault/v0-vault-stx.clar:806) [2](#0-1) , so `deposit` cannot "reach" `convert-to-assets-preview` as claimed.

Additionally, the alleged invariant — "collateral leaving a borrower equals debt cleared scaled by the penalty" — pertains to liquidation logic, which has no connection to this vault's `deposit`/`redeem`/preview-pricing functions [3](#0-2) . There is no shared state written by an unprivileged attacker A through `deposit` that would let them mis-price a victim B's liquidation or redemption in a way that breaks a collateral/penalty invariant; `total-assets-preview` and `total-supply-preview` are deterministic functions of protocol-wide accrual state (`assets`, `principal-scaled`, `index`, `fee-reserve`), not attacker-injectable values that violate any documented invariant [4](#0-3) .

Since the target function is not actually reachable from the stated entrypoint via the stated call path, and the invariant referenced belongs to an unrelated subsystem, this does not meet the bar for a valid, reproducible two-account PoC as required by the rules.
