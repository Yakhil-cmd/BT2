### Title
Webhook signature scoped to organization is not bound to the repository/commit acted on, allowing cross-tenant CI status forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook by looking up the GitHub App/`webhook_secret` for the organization named in `params.dig('repository','owner','login')` and validating the HMAC over the raw body with that organization's secret. [1](#0-0)  The equality this is supposed to establish is "the organization whose secret signed this payload == the organization that owns the repository/commit the payload will mutate." However, `StatusHandler#process` never re-checks the repository at all: it looks up `Commit.where(sha: params.sha)` across the **entire** commits table and writes a GitHub status to every match. [2](#0-1)  On a multi-tenant Shipit install (the documented "Using Multiple Github Applications" configuration, where several distinct GitHub orgs each have their own `webhook_secret`), an organization that legitimately authenticates its own webhook can sign a `status` payload with `sha` copied from a commit belonging to a completely different tenant's stack, and that stack's commit status will be updated as if GitHub had reported it.

### Finding Description
The signature check only binds "which organization's secret signed the request," derived from `repository.owner.login`: [3](#0-2) 
That per-organization key selection is documented for multi-org installs where each organization owns an independent GitHub App with its own `webhook_secret`. [4](#0-3) 

The `status` event is routed straight to `StatusHandler`, whose only required fields are `sha` and `state` — there is no `repository` requirement and no ownership check performed by the handler or its base class: [5](#0-4) 
Contrast this with the base `Handler` class, which *does* define a repository-scoped `stacks` helper keyed off `payload.dig('repository', 'full_name')`, but `StatusHandler` bypasses it entirely and queries `Commit` globally by `sha`. [6](#0-5) 

So the equality the design needs — "organization O that signed the webhook == owner of the commit whose status is being written" — is never enforced. Only "organization O signed *some* payload" is checked; the `sha` inside that payload can reference a commit belonging to any stack/repository/organization configured on the same Shipit instance, because SHA1s are global 40-hex identifiers with no repository namespace baked in, and `StatusHandler` performs no cross-check against `repository_owner`/`repository.full_name`.

`create_status_from_github!` writes a real `Status` record for the targeted commit, [7](#0-6)  and that status feeds directly into `deployable?` and the continuous-delivery trigger: [8](#0-7) [9](#0-8) 
If the victim stack has `continuous_deployment?` enabled and CI is otherwise blocking the deploy, an attacker who controls a second, independently-onboarded organization on the same Shipit instance can forge a `success` status for a targeted commit belonging to the victim organization's stack and trigger `ContinuousDeliveryJob`, resulting in an unauthorized deploy.

### Impact Explanation
This crosses the "Critical: unauthorized deploy" bar defined in scope. An entity that is only entitled to send webhooks for its own organization/repository can inject a fabricated commit status for a repository/stack it does not own, and that status can gate/trigger an actual deploy via `schedule_continuous_delivery`. This is a cross-tenant, cross-repository write that breaks the binding between "organization that authenticated the webhook" and "repository/commit that is written," exactly the analog class called out in the rules.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to already control one of those onboarded organizations (i.e., they can configure/observe their own GitHub App's `webhook_secret`, which is a normal admin capability of their own org, not a privilege over the victim). No `GITHUB_TOKEN`, `api_clients_secret`, or victim credentials are needed — only knowledge of the target commit `sha`, which is often public (visible in PRs, GitHub UI, CI logs) even without repo access. The attack requires no `ApiClient` token and no Shipit session, matching the "unprivileged attacker" framing of the prompt within a multi-org deployment.

### Recommendation
`StatusHandler` (and any other handler that looks up records purely by SHA) should require and validate the `repository.full_name` in the payload against the repository whose organization's secret verified the signature, scoping the `Commit` lookup to `stacks` (i.e., commits belonging to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) exactly as the base `Handler#stacks` helper already does, rather than querying `Commit.where(sha: params.sha)` globally.

### Proof of Concept
1. Shipit is configured with two independent GitHub Apps/organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per the documented multi-org setup).
2. Attacker knows the `sha` of a commit belonging to a stack owned by `victim-org` (e.g., visible from a public PR) that is pending/blocked on CI, on a stack with `continuous_deployment` enabled.
3. Attacker crafts a `status` webhook body: `{"sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}` and signs it with `attacker-org`'s own `webhook_secret` (HMAC-SHA1 over the raw body), exactly as `Hook::DeliverySigner`/`verify_webhook_signature` expect. [10](#0-9) 
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature since it was signed with `attacker-org`'s real secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unrelated to `attacker-org`), and calls `create_status_from_github!`, writing a fabricated "success" status. [2](#0-1) 
6. If this flips the commit's aggregate status to deployable, `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` for the victim's stack, producing an unauthorized deploy. [9](#0-8) 

**Uncertainty note:** I was not able to fully trace `ContinuousDeliveryJob`'s internals or confirm whether additional independent CI/status checks would still block the deploy in every configuration — this depends on the victim stack's `ci.require`/`blocking_statuses` settings, which are configuration-dependent and outside what I verified. The core signature/repository-binding gap in `StatusHandler`, however, is confirmed directly from the code cited above.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
