### Title
Git-Ref Snapshot TOCTOU Lets Post-Snapshot Commits Bypass the Security-Guidance Stop-Hook Review — (File: `plugins/security-guidance/hooks/security_reminder_hook.py`, `plugins/security-guidance/hooks/diffstate.py`)

### Summary

### Finding Description
The `security-guidance` plugin's Stop-hook review gates whether Claude's code changes get flagged for a security re-check on a **git-ref snapshot** taken at `UserPromptSubmit` time, exactly analogous to the Anchor governance poll's `staked_amount` snapshot. `handle_user_prompt_submit` captures `baseline_sha` (via `git stash create`) and `head_at_capture` (via `git rev-parse HEAD`) and persists them to session state [1](#0-0) . When `handle_stop_hook` later fires, it reads this snapshot (`consume_stop_state`) and derives the "review set" — the files that get sent to the LLM reviewer — purely from git state relative to that snapshot [2](#0-1) .

`compute_v2_review_set` computes `review_set = dirty_now ∩ changed_since`, where `dirty_now` is the *currently uncommitted* working-tree diff (`git status --porcelain`) unioned with any commits since `head_at_capture` **only if** that ancestor relationship still holds [3](#0-2) . This mirrors the poll's flaw: the enforcement decision is computed from a point-in-time snapshot (`baseline_sha`/`head_at_capture`), but the *actual* git ref state (HEAD, working tree) can move between snapshot capture and consumption — via a sibling agent in a shared worktree, a background/committed change, or a rebase — invalidating the `_is_ancestor` check in `gitutil.py` [4](#0-3) . The plugin authors explicitly acknowledge this exact race in the `ENABLE_STOP_REVIEW` comment: the Stop-hook diff is "anchored on baseline_sha…HEAD, which a sibling agent in the same worktree can move under us" [5](#0-4) .

Concretely: if code is fully committed between snapshot capture and Stop-hook evaluation (so `dirty_now`, which only reflects uncommitted changes, is empty) and `_is_ancestor(head_at_capture, current_head)` returns false (e.g., HEAD advanced non-linearly due to a concurrent rebase/amend/checkout by another process sharing the worktree), the commit-derived files are never OR'd into `dirty_now`. The intersection `dirty_now ∩ changed_since` then evaluates to an empty review set even though `changed_since` (diff vs. `baseline_sha`) is non-empty — i.e., real, security-relevant code changes exist since the snapshot but are silently excluded from LLM review, exactly as a poll's snapshot fails to account for stake changes made after it was taken.

### Impact Explanation
A user or concurrent agent process that can influence the shared git ref state (worktree-isolated subagents, `/fork`, shared-worktree multi-agent deployments explicitly referenced in the changelog: "Fixed `isolation: 'worktree'` subagents being able to run git-mutating commands against the main repo checkout" and "Hardened cross-session messaging") can cause vulnerable code introduced by Claude to bypass the Stop-hook's automated security review entirely. This defeats the plugin's core security control — the LLM diff review that is supposed to catch injected vulnerabilities before the user sees the response — without any error or warning being surfaced, since the code takes the "no changes since baseline" skip path (`_skip(6)`) silently [6](#0-5) .

### Likelihood Explanation
This requires a specific concurrency condition — non-ancestor HEAD movement between UPS-time snapshot and Stop-hook evaluation while the introduced changes are fully committed (no dirty working tree) — which the plugin's own documentation states occurs in real, supported deployment patterns (multi-agent / shared-worktree setups, per the `ENABLE_STOP_REVIEW` comment). It is not a purely theoretical race; it is a documented known limitation the maintainers already provide a manual kill-switch for, indicating it has been observed as a practical concern rather than a contrived edge case.

### Recommendation
Do not rely solely on `dirty_now ∩ changed_since`, which fails open when a review-eligible change is fully committed and `head_at_capture` is no longer an ancestor of `HEAD`. Instead, always union `changed_since` (diff vs `baseline_sha`) into the review set, using `dirty_now` only to *add* untracked/uncommitted files rather than to gate/restrict `changed_since`. If `_is_ancestor` fails, fail closed (review everything in `changed_since`) rather than falling back to an intersection that can silently shrink to empty. This mirrors the governance-report's checkpointing recommendation: base the review decision on the delta actually observed against the snapshot, not on a live, mutable value (`dirty_now`) that other actors can change out from under the snapshot.

### Proof of Concept
1. Start a Claude Code session; `UserPromptSubmit` captures `baseline_sha=A`, `head_at_capture=A`.
2. Claude writes a file containing an injected vulnerability (e.g., via a compromised skill or prompt injection) and, within the same turn window, a concurrent process sharing the worktree (a sibling worktree-isolated subagent, or a user-run background git operation) performs a `git rebase`/`commit --amend` that advances `HEAD` to `B` such that `A` is no longer an ancestor of `B` (`_is_ancestor(A, B)` → `False`), while also causing Claude's changes to be fully committed (working tree clean, `dirty_now = ∅`).
3. `handle_stop_hook` runs: `compute_v2_review_set` computes `changed_since = diff(A, B)` (non-empty, contains the vulnerable file), but `dirty_now = ∅` and the ancestor check fails, so no commit-range files are OR'd in. `review_set = ∅ ∩ changed_since = ∅`.
4. `handle_stop_hook` hits `if not review_paths: _skip(9, ...)` and exits 0 with no LLM review performed, despite a new vulnerability being present in the diff since the snapshot — the security check silently never ran. [7](#0-6)

def handle_user_prompt_submit(input_data):
    """
    Handle UserPromptSubmit — capture git baseline SHA.
    Called on every user prompt. Updates the baseline so the stop hook
    only reviews changes made since the last prompt.

    Does NOT reset touched_paths/fire_count/previous_findings — those are
    consumed by Stop (consume_stop_state) and time-expired respectively.
    UPS racing the asyncRewake Stop hook caused a meaningful share of reviews
    to be lost when the wipe landed before Stop's state read.

    """
    cwd = input_data.get("cwd", "")
    if not cwd:
        debug_log("UPS: no cwd, skipping baseline capture")
        sys.exit(0)

    session_id = input_data.get("session_id", "default")
    # stash-create and ls-files both walk the worktree (~2-5s each in a very
    # large repo). Run them concurrently so UPS latency stays ≈ max(both).
    import concurrent.futures as _cf
    with _cf.ThreadPoolExecutor(max_workers=2) as _ex:
        _f_sha = _ex.submit(capture_git_baseline, cwd)
        _f_ut = _ex.submit(_list_untracked, cwd)

        # empty when there are no TRACKED changes, but pre-existing untracked
        # files still need to be excluded from the next Stop's review_set —
        # otherwise an untracked-only working tree gets every untracked file
        # reviewed on every turn until something tracked is dirtied.
        untracked_now = _f_ut.result() or {}
    head = _git_rev_parse_head(cwd)

def _is_ancestor(cwd, maybe_ancestor, descendant):
    """True if `maybe_ancestor` is reachable from `descendant` (i.e. HEAD
    moved forward via commit/merge, not sideways via checkout)."""
    try:
        result = subprocess.run(
            [*GIT_CMD, "merge-base", "--is-ancestor", maybe_ancestor, descendant],
            cwd=cwd, capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return False
