### Title
Panic-style DoS in address-definition co-author resolution via duplicate-address authors — ([File: definition.js])

### Summary
`definition.js`'s address-definition resolver assumes a unit's `authors` array can contain **at most one** author whose `address` matches a given `other_address`/`changed_address` chash. When it finds more than one, it does `throw Error("more than 1 address definition")` synchronously inside a DB-callback context that has no surrounding `try/catch`. Because this executes deep inside `async`/DB-callback chains invoked from `validation.js`, the thrown error is not passed back through the `cb`/`callback` error-first convention — it becomes an uncaught exception that crashes the Node.js process, exactly analogous to the Nimiq `unwrap()` panic in `put_chunk`/`put_value`: a value that should be structurally impossible (root key / duplicate co-author) turns a validation error into a process-crashing exception.

### Finding Description
`validateDefinition`'s `'address'` case and `validateAuthentifiers`'s `'address'` case both resolve inner/co-author address definitions the same way: [1](#0-0) [2](#0-1) 

In both places, when `storage.readDefinitionByAddress` reports `ifDefinitionNotFound`, the code searches the unit's own `authors` array for an author matching `other_address` and the same `definition_chash`:

```js
var arrDefiningAuthors = objUnit.authors.filter(function (author) {
    return (author.address === other_address && author.definition && objectHash.getChash160(author.definition) === definition_chash);
});
...
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```

This assumes `objUnit.authors` cannot contain two entries with the same `address`. However, tracing `validation.js`'s top-level `validate()` function, the author list is only mapped to addresses and checked for individual address *validity* (`isValidAddress`), never for **uniqueness**: [3](#0-2) 

No dedup check on `arrAuthorAddresses` (e.g., `_.uniq` comparison) is present in the surrounding validation code I traced (`validate`, `validateAuthors`, `validateAuthor`). An unprivileged unit poster can therefore construct a unit whose `authors` array lists the *same* address twice, each carrying an identical (or chash-matching) `definition` field, referencing that address from within an address/asset spending condition (`['address', other_address]` or `['has definition change'...]`/`'seen definition change'` paths that reference `'this address'`), or by having the unit's own address-definition self-reference an inner "address" op whose target equals one of the co-authors. When `validateDefinition`/`validateAuthentifiers` process such a unit, `arrDefiningAuthors.length` becomes `2`, hitting the `throw Error(...)` path.

Because this throw happens inside a `conn.query(...)`/`storage.readDefinitionByAddress` callback invoked asynchronously from deep inside `async.eachSeries`/`evaluate()` recursion, there is no synchronous `try/catch` wrapping it at the call site in `validation.js` (`validateAuthor` → `validateAuthentifiers` → `evaluate`). An uncaught exception thrown inside a Node.js callback crashes the process (unless a global `uncaughtException` handler exists and chooses to keep running, which for a full node is unsafe/undesirable and typically not configured to swallow such errors).

### Impact Explanation
Any single crafted unit containing two authors that share the same address (with valid/matching definitions or chashes) and reference that address in an inner `'address'`/`'has definition change'`/`'seen definition change'` condition can crash any full node that validates it — full nodes performing normal DAG unit validation, not just state-sync peers. This is a broader-than-`Nimiq` blast radius: every node that receives and validates the malicious unit (via normal gossip) crashes, potentially halting network confirmation ability if repeated against many nodes simultaneously. This satisfies the "network unable to confirm new units" / "node disagreement/crash" impact bar.

### Likelihood Explanation
Likelihood is high for any attacker capable of constructing a raw unit (no special privilege required — this is exactly the "unprivileged unit poster" path). Building a unit with two author entries of the same address is a pure client-side JSON construction; the address itself needs a definition (which the attacker fully controls, since they are the author) and a spending/authentication condition that references that same address (`['address', addr]`), which is a documented, standard oscript definition primitive. No stability, MCI-upgrade gating, or special asset condition seems to guard the uniqueness assumption in the paths reviewed.

### Recommendation
- Add an explicit uniqueness check on `objUnit.authors` addresses early in `validation.js`'s `validate()` (alongside the `arrAuthorAddresses.every(isValidAddress)` check), rejecting units with duplicate author addresses via `callbacks.ifUnitError(...)` instead of allowing the invariant to be silently assumed downstream.
- Defensively replace the `throw Error("more than 1 address definition")` calls in `definition.js` (`validateDefinition` and `validateAuthentifiers`, both `'address'` cases) with proper `cb("...")`/`cb2(false)` soft-failure returns, so that even if the invariant is violated elsewhere, validation fails gracefully instead of crashing the process.

### Proof of Concept
1. Craft a unit with `authors = [{address: A, definition: D, authentifiers: {...}}, {address: A, definition: D, authentifiers: {...}}]` (same address `A` twice, identical definition `D` whose chash equals `A`).
2. Give address `A` (or another address referencing `A`) a spending condition containing `['address', A]` (or use `'has definition change'`/`'seen definition change'` referencing `'this address'` pointing back to `A`).
3. Post the unit to the network / feed it to `validation.validate()`.
4. During `validateAuthor` → `validateAuthentifiers`/`validateDefinition` → the `'address'` case's `ifDefinitionNotFound` branch, `arrDefiningAuthors.filter(...)` returns 2 matches, triggering `throw Error("more than 1 address definition")` uncaught, crashing the validating node process.

Note: I was not able to fully verify within the available search budget that there is no author-address-uniqueness check anywhere else in the codebase (e.g., inside `objectHash.getUnitHash` structural checks or a database-level constraint enforced before this code path executes) — this should be confirmed by directly running the described PoC unit through `validation.validate()` in a test harness before treating this as a confirmed exploit.
