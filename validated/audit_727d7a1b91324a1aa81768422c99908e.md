## Analysis

I found a genuine analog to the "bad-debt bypasses a trust boundary" bug class: `shipit-engine`'s webhook signature check binds authentication to an attacker-supplied **organization login**, while the record actually mutated is selected by an independently attacker-supplied **repository full name**. These two fields are never checked against each other, and the signature check can be trivially satisfied for any organization whose config omits a `webhook_secret` (a documented, supported, optional setting).

### Title
Webhook signature verification is keyed to an attacker-chosen organization login that is decoupled from the repository the payload actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to verify against using `repository_owner`, a value read straight out of the unauthenticated JSON body. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/nil — a state the docs explicitly treat as normal/optional. The handlers that actually mutate data (e.g. `StatusHandler`, `PushHandler`) instead resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` — a second, independently attacker-controlled field. Nothing ties the org used for the (possibly-bypassed) signature check to the repository whose records get written.

### Finding Description
- `verify_signature` computes the "authenticating" org purely from the JSON body: [1](#0-0) 
and uses it to pick the GitHub App / secret to validate against: [2](#0-1) 
- `verify_webhook_signature` short-circuits to `true` when the selected org has no configured secret: [3](#0-2) 
- `webhook_secret` is explicitly documented/shipped as optional (`webhook_secret: # nil`): [4](#0-3) 
- Once "verified", every registered handler is invoked with the raw, still fully attacker-controlled payload: [5](#0-4) 
- Handlers resolve the target stack/repository from a *different* field of the same payload, `repository.full_name`, with no cross-check against `repository_owner`: [6](#0-5) 
- `StatusHandler` uses this to write a `Status` (CI state, description, target_url) onto an *existing* commit that it looks up purely from attacker-supplied `sha`/branch data, with no signature-bound relationship to the repository actually described by the signature-verifying org: [7](#0-6) 

The equality the code implicitly (and wrongly) assumes is:
`organization authenticated by verify_webhook_signature(repository_owner) == owner(repository.full_name)` used by every `Handler#repository_name`.
This equality is never enforced. An attacker who knows (or guesses) the login of *any* organization configured in `Shipit.github` without a `webhook_secret` can satisfy the left side trivially, then set `repository.full_name` on the right side to name **any** repository/stack tracked by the instance, including ones belonging to organizations that *do* have a secret configured.

### Impact Explanation
This breaks the deployment-trust binding between "who GitHub says signed this payload" and "which repository's Shipit state gets mutated." Concretely, via the `status` event, an unauthenticated attacker can forge a commit `Status` (arbitrary `state`, `context`, `description`, `target_url`) against any tracked commit in any stack in the instance — including marking required CI contexts (`ci.require` in `shipit.yml`) as `success` for commits that never actually passed CI. Since Shipit's `release_status`/`ci.require` gating consumes exactly this `Status` data to decide deployability, this is a cross-repository, unauthenticated write that undermines the integrity of the CI gate that legitimate deploy triggers rely on — a "cross-repository writes" class impact per the engine's own data model, achieved with zero credentials, no `ApiClient` token, and no session.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: it requires at least one organization entry under `Shipit.github` (in a multi-org deployment) that has no `webhook_secret` set. This is not a hardening edge case — the shipped example config and setup docs present `webhook_secret` as optional/nilable, so instances with a mix of "public/low-trust" and "internal/high-trust" GitHub orgs are a realistic, docs-encouraged configuration. Once such a config exists, exploitation requires only knowledge of that organization's login (a public, non-secret value) and a single unauthenticated POST.

### Recommendation
Verify the signature using the org actually implicated by the repository being mutated, not a value independently supplied by the payload. Concretely:
1. Require every configured GitHub App/org to have a non-blank `webhook_secret`; refuse to boot (or refuse to verify as "true") when one is missing, rather than treating "no secret" as "always trusted."
2. After signature verification, cross-check that `repository.owner.login` (or `organization.login`) used to select the verifying app matches the owner implied by `repository.full_name` before dispatching to handlers, rejecting mismatches.

### Proof of Concept
1. Configure `Shipit.github` with two orgs: `trusted-org` (has `webhook_secret` set) and `open-org` (no `webhook_secret`, per the documented-optional setting).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "trusted-org/victim-repo" },
  "sha": "<existing commit sha in trusted-org/victim-repo>",
  "state": "success",
  "context": "required-ci-check",
  "target_url": "https://attacker.example/fake",
  "description": "forged"
}
```
3. `verify_signature` resolves `repository_owner` = `"open-org"` (from `repository.owner.login`), calls `Shipit.github(organization: "open-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the bogus `X-Hub-Signature`.
4. `StatusHandler` (dispatched next) resolves the target repository from `repository.full_name` = `"trusted-org/victim-repo"` and creates a `Status` record with attacker-chosen `state`/`context` on that commit — as shown by the existing test flow for the `status` event.
5. Result: an unauthenticated request "signed" under an unrelated, secret-less organization writes forged CI status data into a completely different, trusted organization's repository/stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
