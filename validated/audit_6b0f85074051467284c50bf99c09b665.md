### Title
Forged 'membership' webhook accepted when org `webhook_secret` is unset, allowing unauthorized deauthorization of a `Membership` - (File: `lib/shipit/github_app.rb`)

### Summary
`GithubApp#verify_webhook_signature` returns `true` unconditionally whenever `webhook_secret` is not configured for an organization, meaning any internet client can forge a `membership` webhook for that org. `MembershipHandler#process` then trusts the forged payload's `action: 'removed'` and calls `team.members.delete(member)`, deleting a real `Membership` row without any confirmation from GitHub that the removal actually occurred.

### Finding Description
The broken binding: `Membership(team, user).exists? == GitHub_reports_membership(team, user)` should always hold, but it can be forced false by an attacker with no credentials.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses raw JSON and dispatches to handlers for the `X-Github-Event` header, gated by `before_action :verify_signature` (line 6).
2. `verify_signature` (lines 24-49) resolves `Shipit.github(organization: repository_owner)` from the attacker-controlled `organization.login`/`repository.owner.login` field, then calls `github_app.verify_webhook_signature(...)`.
3. `GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`):
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
If the targeted organization has no `webhook_secret` configured (a documented "optional" setting per `docs/setup.md:30`, and the default in every example secrets file, e.g. `test/dummy/config/secrets.yml:13`, `config/secrets.development.example.yml:11`), verification is bypassed entirely — `head(422) unless verified` never fires because `verified` is `true`.
4. `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then runs unauthenticated attacker data: `find_or_create_team!` looks up an existing `Team` by `params.team.id` (an attacker-guessable/observable numeric GitHub team ID for a team already in `Shipit.github_teams`), `User.find_or_create_by_login!(params.member.login)` resolves the victim's real login, and for `action == 'removed'` calls `team.members.delete(member)`, deleting the `Membership` row.

No other guard intercepts this: `drop_unhandled_event` only checks the event is handled at all; there is no `ExplicitParameters` check tying the payload to a verified source; `force_github_authentication`/`require_permission!`/`User#authorized?` are irrelevant to this unauthenticated webhook endpoint. The only control meant to authenticate the webhook source is `verify_signature`, and it is a no-op when `webhook_secret` is absent — which is the documented, allowed default configuration.

Attacker request: POST `/webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "removed",
  "team": {"id": <real_team_github_id>, "name": "...", "slug": "...", "url": "..."},
  "organization": {"login": "<org-with-no-webhook_secret>"},
  "member": {"login": "<victim-login>"}
}
```
No `X-Hub-Signature` value needs to be valid; any string, or omission, is accepted once `webhook_secret` is nil.

### Impact Explanation
For any organization configured without a `webhook_secret` (the default/optional configuration shown throughout the repo's own setup docs and example secrets files), an anonymous attacker can forge arbitrary GitHub `membership` events. Using `action: 'removed'`, they can silently strip a real, currently-authorized operator's `Membership` in a `Shipit.github_teams` team, flipping `User#authorized?` to `false` without any corresponding change on GitHub — denying that operator's ability to deploy/merge until the periodic `teams:fetch`/next real webhook re-adds them. Using `action: 'added'` the same bypass could instead grant unauthorized team membership to any login. This is a forged-webhook authentication bypass affecting the org's authorization state (`Shipit.github_teams`), repeatable against any team/member pair known to the attacker, for every organization that leaves `webhook_secret` unset.

### Likelihood Explanation
Preconditions: the target organization must have `webhook_secret` unset in its GitHub app config — a state the codebase's own docs (`docs/setup.md:30`, "Webhook secret (optional)") and every shipped example secrets file treat as normal/default. No Shipit session, API token, or GitHub secret is needed. The attacker needs only the org login, a real team's GitHub numeric ID (discoverable via public GitHub API/UI), and a victim login (discoverable via public org membership or the app's own 403 error page team listing, per the question). This is a single unauthenticated HTTP POST, fully repeatable and scriptable.

### Recommendation
Do not treat an absent `webhook_secret` as "trust unconditionally." At minimum:
- Require `webhook_secret` to be configured for any organization that is allowed to send authorization-affecting events (`membership`), and reject/alert on unsigned webhooks for such orgs instead of returning `true`.
- Alternatively, remove the `return true unless webhook_secret` fast path entirely and fail closed (`head(422)`) when no secret is configured, forcing operators to set one.
- Additionally, treat `membership` "removed" events defensively: reconcile against a live GitHub API call (or require corroboration) before deleting `Membership` rows for teams that gate deploy authorization, rather than trusting the webhook payload alone.

### Proof of Concept
Minitest plan (webhook signature + handler, no live GitHub call — dummy app's `Shipit.github` already stubs API access):
```ruby
test "'membership' removed webhook with unset webhook_secret deletes a real operator's Membership" do
  org = "acme"  # configured in test secrets with webhook_secret: nil (see test/dummy/config/secrets.yml)
  team = shipit_teams(:some_team) # a Team whose github_id is present in Shipit.github_teams
  victim = shipit_users(:walrus)
  membership = Membership.create!(team: team, user: victim)

  assert victim.authorized?
  assert_difference -> { Membership.count }, -1 do
    post shipit.webhooks_path, params: {
      action: 'removed',
      team: { id: team.github_id, name: team.name, slug: team.slug, url: 'https://api.github.com/teams/1' },
      organization: { login: org },
      member: { login: victim.login }
    }.to_json, headers: {
      'X-Github-Event' => 'membership',
      'Content-Type' => 'application/json'
      # no valid X-Hub-Signature provided
    }
  end
  assert_response :ok
  refute victim.reload.authorized?
end
```
This asserts the equality `Membership.count(before) - 1 == Membership.count(after)` and `victim.authorized?` flips from `true` to `false` purely from a forged, unsigned webhook — with no real signature and no live GitHub API call, confirming the authentication bypass in `verify_webhook_signature`.
