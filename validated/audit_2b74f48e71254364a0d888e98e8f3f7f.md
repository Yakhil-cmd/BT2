### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` webhook lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's webhook signature check authenticates *which organization* sent a webhook, but the `status` event handler never verifies that the commit being written to actually belongs to that organization's repository. `StatusHandler#process` resolves the target purely by commit SHA, globally, across every stack/repository tracked by the Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the payload itself and validates the HMAC against that organization's own webhook secret: [1](#0-0) [2](#0-1) 

This only proves "this payload was legitimately signed by organization X's GitHub App configuration" — it says nothing about which repository/commit the payload is allowed to mutate. That binding is supposed to be enforced by each event handler.

Every other repository-scoped handler does this correctly by filtering through `Handler#stacks`, which resolves the repository from `payload.dig('repository', 'full_name')`: [3](#0-2) 
e.g. `PushHandler` and `CheckSuiteHandler` both scope their queries through `stacks`: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, looks up commits **globally by SHA only**, with no repository/stack scoping whatsoever: [6](#0-5) 

Because SHA1 commit ids are content hashes, not repository-scoped identifiers, it is entirely normal for the same SHA to exist in more than one Shipit-tracked `Stack`/`Repository` — most commonly for forks, mirrors, or repositories that share initial/cherry-picked history. Any organization that legitimately owns a Shipit-connected repository (and therefore legitimately signs its own `status` webhooks with its own configured secret — no secret compromise required) can produce a real, correctly-signed `status` event whose `sha` also matches a commit that lives in a *different* organization's stack. `StatusHandler` will happily attach that status to the unrelated victim commit:
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`

This breaks exactly the binding called out in the rules: the organization the signature authenticates (`repository.owner.login` used to select the verifying secret) is not equal to the organization/repository whose `Commit` row actually gets written.

### Impact Explanation
Commit statuses are the mechanism `ci.require`/`ci.blocking` deploy gating relies on (documented in the engine's CI configuration, `README.md` §CI). By writing a forged `success` status for a required context onto a victim commit that the attacker does not own or have write access to, an attacker can satisfy that victim stack's CI requirements and enable an **unauthorized deploy** of a commit they don't control write access over — without ever holding a Shipit session, an `ApiClient` token, or the victim's/any webhook secret. This lands squarely in the Critical impact bucket ("unauthorized deploy").

### Likelihood Explanation
Requires: (1) the attacker's own GitHub organization/repository already legitimately onboarded to the same multi-tenant Shipit instance (so their own webhook deliveries are correctly signed with their own secret — a normal, unprivileged setup step, not a secret compromise), and (2) a commit SHA collision between the attacker's repo and the victim's tracked repository. Condition (2) is realistic and not exotic for forks/mirrors/shared-history repositories, which are common in organizations using a shared Shipit deployment across many repos. This is a design/implementation gap rather than a theoretical cryptographic collision.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: only update commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, instead of the unscoped global `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Organization `attacker-org` legitimately configures a Shipit-tracked repository/stack and has a validly configured GitHub App/webhook secret for its own org (normal onboarding, no secret theft).
2. Attacker forks (or otherwise shares initial history with) a repository belonging to `victim-org`, which is also tracked as a Shipit stack, such that a commit SHA `S` exists in both repositories' git history.
3. Attacker triggers (or crafts, since they hold their own legitimate secret) a `status` webhook from `attacker-org`'s repository for commit `S` with `state: success`, `context: <victim's required CI context>`.
4. `WebhooksController#verify_signature` validates successfully (correct secret for `attacker-org`).
5. `StatusHandler#process` runs `Commit.where(sha: 'S')`, which matches the commit row belonging to `victim-org`'s stack (since SHA `S` is shared), and calls `commit.create_status_from_github!(params)`, writing the forged `success` status onto the victim's commit.
6. If `victim-org`'s `shipit.yml` `ci.require` lists that context, the victim commit now appears CI-green and becomes deployable, enabling an unauthorized deploy despite the attacker never having write access to `victim-org`'s repository.
