### Title
Overflow during interest accrual permanently freezes a heavily utilized market - (File: `common/src/rates/scaling.rs`)

### Summary
A permissionless user can create a very large, highly utilized borrow position. Once the borrow index grows enough, interest accrual multiplies the aggregate scaled debt by the index and overflows `i128` before the `MAX_BORROW_INDEX_RAY` cap can clamp it. Because all state-changing market paths accrue the market first, the same overflow subsequently blocks repayment, withdrawal, liquidation, bad-debt cleanup, and further index updates, permanently freezing the market.

### Finding Description
`Cache::calculate_utilization` reconstructs aggregate debt with `scaled_to_original(self.borrowed, self.borrow_index)`, which is simply `scaled.mul(index)` in `common/src/rates/scaling.rs`. [1](#0-0) [2](#0-1) 

`interest::global_sync` executes this accrual before mutating market state, and `ops::market::accrue` exposes the same path through `update_indexes`. [3](#0-2) [4](#0-3) 

The index cap is applied only after `old_index.mul(interest_factor)` and therefore does not prevent the later aggregate debt-value multiplication from overflowing while the index remains below `MAX_BORROW_INDEX_RAY`. [5](#0-4) 

The repository's scenario test creates a one-billion-token 18-decimal market, borrows 98% of it, advances time, and observes `MathOverflow`; the stored borrow index is still below `MAX_BORROW_INDEX_RAY`. Subsequent `withdraw` and `repay` calls fail with the same error because they perform accrual first. [6](#0-5) 

The reachable controller path is:

1. `supply(caller, 0, spoke_id, [(debt_hub_asset, large_amount)])`
2. `supply(caller, collateral_account_id, spoke_id, [(collateral_hub_asset, collateral_amount)])`
3. `borrow(caller, collateral_account_id, [(debt_hub_asset, borrow_amount)], None)`
4. Leave utilization high while interest accrues.
5. Call `update_indexes` or wait for any user to invoke `repay`, `withdraw`, or `liquidate`.

`supply`, `borrow`, `repay`, `withdraw`, and `liquidate` are all public controller entrypoints. [7](#0-6) 

### Impact Explanation
The affected market becomes permanently unable to accrue interest. Since the overflow occurs in the shared pre-mutation accrual step, borrowers cannot repay, suppliers cannot withdraw, liquidators cannot liquidate, and keepers cannot advance indexes. This results in permanent freezing of user funds and can leave debt unresolved until liquidation is economically meaningless.

### Likelihood Explanation
An unprivileged account can create the required state through ordinary `supply` and `borrow` calls, provided the selected asset has sufficient issuance and governance-configured caps permit the position. No callback, privileged call, oracle manipulation, leaked key, or contract upgrade is required. The condition requires a very large market and sustained high utilization, so it is not instantaneous, but once reached the failure is deterministic and cannot be repaired through the exposed market operations.

### Recommendation
Use checked or widening multiplication for aggregate debt and supply valuation before multiplying by the index. In particular:

- Apply `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` before calculating aggregate Ray values.
- Replace fallible `Ray::mul` aggregate calculations with a 256-bit intermediate or checked `mul_div` that explicitly caps the stored index before `i128` overflow.
- Add a pre-accrual guard such as `if borrowed > i128::MAX / borrow_index { cap index or use saturating aggregate accounting }`.
- Ensure `repay`, `withdraw`, `liquidate`, and `clean_bad_debt` can still operate when aggregate accrual reaches the mathematical ceiling.
- Add a regression test that drives the market to the boundary and proves repayments and withdrawals remain possible.

### Proof of Concept
The existing scenario `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` supplies `BILLION * 10^18` units, borrows 98%, advances time until `try_update_indexes_for(["BIG18"])` returns `MathOverflow`, then verifies that both `withdraw` and `repay` fail with `MathOverflow`. The test also records `borrow_index < MAX_BORROW_INDEX_RAY`, proving the configured index cap did not prevent the aggregate-value overflow. [8](#0-7)

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
