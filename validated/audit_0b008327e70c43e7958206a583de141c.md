### Title
AA/formula definition validation performs unbounded CPU-expensive recursive parsing before any economic cost is committed, enabling free repeated DoS - ([File: aa_validation.js])

### Summary
The Obyte core (`ocore`) analog of the Arbitrum "gas charged too late" bug is the recursive validation of `autonomous agent` (AA) definitions and their embedded oscript formulas. This validation is one of the most CPU-expensive operations any unprivileged unit poster can trigger, yet it runs during message validation, and if it fails (or the surrounding unit fails validation for any other reason), the entire unit is rolled back and nothing is ever charged or spent by the attacker — exactly mirroring the WASM-activation pattern where a failed, expensive operation leaves the attacker unpunished.

### Finding Description
When a unit contains a message with `app: "definition"` (an AA definition, possibly nested), validation calls `aa_validation.validateAADefinition`, which recursively walks the entire definition tree and calls the oscript parser (`formula/validation.js` → `nearley` grammar parsing) on every string field that looks like a formula: [1](#0-0) 

This recursive walk is bounded only by `MAX_DEPTH = 100`: [2](#0-1) 
and periodically yields the event loop every 100 iterations via `setImmediate`, which is itself an acknowledgment by the developers that this operation is heavy enough to block the process: [3](#0-2) 

Crucially, this expensive validation occurs inside `validateInlinePayload`'s `"definition"` case, which is reached during `validateMessages`, the **last** step of the overall unit-validation pipeline in `validate()`: [4](#0-3) 

If the unit (or the AA definition itself) fails validation for any reason — including deliberately, after the expensive recursive parse has already run to completion — the whole DB transaction opened for validation is rolled back and no output is ever spent: [5](#0-4) [6](#0-5) 

Because nothing is committed on failure, the UTXO(s) an attacker references as payment inputs remain unspent and can be reused to replay the same expensive-to-validate, deliberately-invalid AA definition unit indefinitely. The attacker only pays the (near-zero) cost of constructing and signing a JSON message; the network/validating nodes pay the full cost of the deep recursive tree walk and repeated oscript grammar parsing (`nearley` parser instantiation per formula) for every replay, with no fee ever locked in or burned. This is the same failure mode described in the report: "if [the expensive operation] fails, the user will not be charged... making the attack cheaper than expected."

### Impact Explanation
This allows an unprivileged unit poster to force full nodes to repeatedly perform the heaviest validation work in the codebase (deep recursive tree walk + oscript grammar parsing at every level, up to `MAX_DEPTH` nesting) for free, since a failing/invalid definition never results in spent funds or a persisted fee. Repeated at scale this degrades node validation throughput and can prevent the network from confirming legitimate units in a timely manner, which maps to "a network unable to confirm new units" under the validation rules.

### Likelihood Explanation
Likelihood is Medium: the attack requires no privileged access, no compromised keys, and no protocol-level exploit — merely crafting a unit whose `definition` message is maximally nested (up to depth 100) with as many distinct formula strings as fit within `MAX_UNIT_LENGTH`, funded by outputs the attacker already owns and can reuse across attempts since failed validation never spends them. The `setImmediate` throttling every 100 recursion steps shows the operation's cost was already recognized as significant by the maintainers, but no upfront charge/deposit was added to make failed attempts costly.

### Recommendation
- Charge (or provisionally lock) the unit's `headers_commission`/`payload_commission` fee-equivalent cost as early as possible relative to the expensive AA-definition/formula validation step, or move cheap structural/size checks (message count, JSON depth/size bounds, formula-count caps) ahead of the recursive `validate()` walk so obviously-invalid or maximally-nested definitions are rejected before the expensive parse runs.
- Consider bounding total formula-parse invocations (not just tree depth) per definition and rejecting definitions that exceed a cheap-to-compute complexity/formula-count estimate before invoking `validateFormula`/`nearley` parsing.
- Review other computationally expensive, user-triggerable operations reachable before economic cost is locked in (e.g., other recursive validators in `definition.js`/`formula/validation.js`) for the same early-exit-without-cost pattern.

### Proof of Concept
1. Attacker owns a small unspent output sufficient to nominally cover unit size fees.
2. Attacker crafts a unit whose first message is `app: "definition"` with an `autonomous agent` definition nested to `MAX_DEPTH` (100 levels), each level containing distinct formula-looking strings (e.g., `"{...}"`) that are syntactically parseable but semantically designed to ultimately fail validation (e.g., referencing an undefined variable at the deepest level, or failing a final unrelated check such as `hasFieldsExcept`).
3. Attacker submits this unit for validation. The node executes `validate()` in `aa_validation.js`, recursively invoking `getFormula`/`validateFormula` (oscript `nearley` parser) across all nested levels — the full expensive traversal completes before the terminal error is returned.
4. Validation fails; `validate()` in `validation.js` issues `ROLLBACK`, releases the connection, and calls `callbacks.ifUnitError`. No output is spent, no fee is recorded.
5. Attacker resubmits the same (or a structurally identical) unit using the same still-unspent output, repeating step 3–4 indefinitely at negligible cost to the attacker but full CPU cost to every validating node.
