### Title
Stack-scoped ApiClient tokens bypass their stack binding to read CI status of any stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` scopes every API-token request to the stack(s) the `ApiClient` is authorized for by routing all stack lookups through `stacks`, which restricts the queryable set to `current_api_client.stack_id` when the client is stack-scoped. `Api::CCMenuController` overrides `stack` to bypass that scoping and resolve `params[:stack_id]` directly against the global `Stack` relation, breaking the binding "stack a token authorizes == stack it touches."

### Finding Description
`BaseController` defines the authorization-scoped lookup helpers used by every other API controller: [1](#0-0) 

`stacks` is deliberately restricted to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` has a `stack_id` set (i.e., it's a stack-scoped token, as created for example by `CCMenuUrlController#client` with `permissions: %w[read:stack]`) [2](#0-1) . All controllers that rely on `stack` (e.g., `Api::StacksController#stack`, and the base implementation used by tasks/deploys/etc.) resolve through this scoped `stacks` relation, so a token scoped to stack A raises `RecordNotFound`/404 if a param references stack B - this is verified by the test "an api client scoped to a stack will only see that one stack" [3](#0-2) .

However, `Api::CCMenuController` (mounted at `GET /api/stacks/*stack_id/ccmenu`, guarded only by `require_permission :read, :stack`) defines its own `stack` method that ignores the scoped `stacks` helper entirely and resolves the id against the unrestricted `Stack` model: [4](#0-3) 

The permission check `require_permission :read, :stack` (from `require_permission!`) only calls `current_api_client.check_permissions!(operation, scope)`, which checks the *permission string* ("read:stack") is present in `ApiClient#permissions` - it never validates that the target `stack_id` param matches the client's bound `stack_id`: [5](#0-4) 

Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the equality that should hold - "stack the token authorizes" == "stack the token touches" - is broken: any valid `read:stack` token, even one bound to a single stack (`stack_id` present on the `ApiClient` record), can supply an arbitrary `stack_id` in the URL and retrieve that other stack's CI/build status.

### Impact Explanation
This matches the High-severity category "unauthenticated read of stack state" from the rubric: possession of any single stack-scoped `read:stack` token (which is trivially obtainable and low-privileged - e.g., auto-created by `CCMenuUrlController` for any logged-in user with `find_or_create_by!`) is sufficient to read `lastBuildStatus`, `lastBuildLabel`, `activity`, and lock status of every other stack in the Shipit instance, not just the one the token creator was authorized for. This crosses a repository/stack authorization boundary the engine is explicitly designed to enforce (as shown by the scoping in `BaseController#stacks` and the corresponding test).

### Likelihood Explanation
Likelihood is high and requires no special conditions: the attacker only needs one legitimately-issued, stack-scoped `read:stack` token (their own, e.g. from viewing their own CCMenu URL) and the target stack's identifier (`owner/repo/environment`), which is often guessable/public. No signature forgery, no privileged account, and no additional credentials are required.

### Recommendation
Change `Api::CCMenuController#stack` to use the inherited scoped lookup, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely (falling back to `BaseController#stack`) achieves the same effect and re-establishes the "token authorizes == token touches" invariant enforced elsewhere in the API.

### Proof of Concept
1. As any authenticated Shipit user, hit `GET /ccmenu/my-owner/my-repo/production` (`CCMenuUrlController#fetch`) to obtain a fresh `ApiClient` scoped to `stack_id = <own stack>` with `permissions: ['read:stack']`, returning a `ccmenu_url` containing `?token=<T>`.
2. Using that token `T`, issue `GET /api/stacks/other-owner/other-repo/other-env/ccmenu?token=<T>`.
3. `Api::CCMenuController#authenticate_api_client` authenticates via `ApiClient.authenticate(params[:token])`, succeeding since `T` is a valid token.
4. `require_permission :read, :stack` passes because the client does have `read:stack` in `permissions`.
5. `CCMenuController#stack` resolves `Stack.from_param!('other-owner/other-repo/other-env')` directly (bypassing the `stack_id`-scoped `stacks` relation), returning the unrelated stack's record and rendering its CI status in the XML response - despite the token only being authorized for the original stack.
