### Title
Membership webhook allows cross-organization escalation into `Shipit.github_teams` authorization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
The `THENA` `_updateFor` bug class ("an update path trusts a value it never validated against the state it is supposed to be bound to") has a direct analog in Shipit's `membership` webhook handler. The handler that materializes GitHub team membership into `Shipit::Team`/`Shipit::Membership` records looks a `Team` up **only by `github_id`**, and only binds the `organization` field to the request the first time the team row is created. Any subsequent `membership` webhook is trusted to mutate that team's members without re-checking that the webhook's authenticated organization still matches the team's `organization`. Because a single Shipit deployment can (and, per its own documented multi-tenant config format, is designed to) serve several independent GitHub organizations, each with its own legitimately-issued `webhook_secret`, an administrator of *any* one of those organizations can forge a `membership` webhook, correctly signed with their own org's secret, that references a `team.id` belonging to a *different* organization and thereby add an arbitrary GitHub login to that team.

### Finding Description
The verification and mutation paths use two different pieces of state as if they were bound together, but they are not:

- Signature verification picks the HMAC secret using `repository_owner`, which for `membership` events falls back to `params.dig('organization', 'login')`: [1](#0-0) 

- The `MembershipHandler` looks up (or creates) the `Team` keyed **only** by the numeric `github_id`, and sets `organization` from the payload solely in the `find_or_create_by!` creation block: [2](#0-1) 

Once a `Team` row for a given `github_id` already exists (e.g., it was created earlier from OrgA's legitimate `membership` webhook, or pre-seeded via `Team.find_or_create_by_handle` / `bin/rake teams:fetch`), any later `membership` event — verified only against the **sender org's own** webhook secret — is accepted and applied to that same `Team` row regardless of which organization's secret signed it. `Team.find_or_create_by!(github_id: ...)` does not re-verify or scope by `organization`, and `team.add_member(member)` / `team.members.delete(member)` unconditionally mutate the pre-existing record: [3](#0-2) 

The binding that is broken is: **the organization whose webhook_secret authenticated the request == the organization whose team membership is being written**. This is exactly analogous to the reported bug: the verified signature (the "vote"/authorized action) covers the raw payload bytes, but the *effect* of processing that payload (`team.add_member`) is applied to state (`Team#organization`) that was captured out-of-band at an earlier, unrelated point in time and is never re-validated against the currently authenticated principal.

`Team` membership is security-relevant: `Shipit.github_teams` gates access to the entire application via `User#authorized?`: [4](#0-3) [5](#0-4) 

### Impact Explanation
In a Shipit instance configured for multiple GitHub organizations (a supported, documented configuration — see the multi-org secrets format and `Shipit.github_organizations`/`github_app_config`), an administrator of a low-trust/less-privileged organization can:
1. Discover the numeric `github_id` of a privileged team belonging to a different, trusted organization configured on the same Shipit instance (team IDs are visible via the GitHub API to anyone with read access to that org's teams, or simply guessed/enumerated since they are small sequential integers).
2. Send a `membership` webhook, signed with their own organization's legitimately obtained `webhook_secret`, containing `team.id` = the victim team's `github_id`, `organization.login` = their own org (so signature verification succeeds), and `member.login` = their own (or any) GitHub login.
3. `MembershipHandler#process` adds that login as a member of the victim `Team` record.

If that `Team` is part of `Shipit.github_teams`, the attacker's GitHub account instantly gains access to every stack in the Shipit instance — deploys, rollbacks, custom tasks, API client management — i.e., an authentication/authorization bypass and cross-organization privilege escalation, matching the "High - escalation into `Shipit.github_teams` authorization" impact bucket.

### Likelihood Explanation
The only prerequisite is administrative control of *some* GitHub organization that is legitimately configured on the shared Shipit instance (a normal, unprivileged capability relative to the victim organization — no Shipit session, no victim `webhook_secret`, no repository write access to the victim repo, and no social engineering are required). This matches a realistic deployment topology that Shipit itself documents and tests (`test/dummy/config/secrets_double_github_app.yml`, `Shipit.github_organizations`). The attack requires only crafting one HTTP request to `/webhooks` with a known/guessable team ID.

### Recommendation
Scope the `Team` lookup/creation and every subsequent mutation by both `github_id` **and** `organization`, and reject (or re-key) the record if the authenticated organization does not match the team's stored `organization`:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
  end
end
```
Additionally, verify in `MembershipHandler#process` that `params.organization.login` equals the `Team#organization` already on record before calling `add_member`/`members.delete`, and drop/alert on mismatches instead of silently applying them.

### Proof of Concept
1. Configure Shipit with two orgs, `victim` and `attacker`, each with its own GitHub App/`webhook_secret` (as in `docs/setup.md`'s multi-org format).
2. `victim`'s legitimate `membership` webhook previously created `Team(github_id: 999, organization: "victim", slug: "admins")`, which is included in `Shipit.github_teams`.
3. Attacker, who administers `attacker` org and thus knows `attacker`'s `webhook_secret`, computes a valid `X-Hub-Signature` for:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "attacker" },
  "member": { "login": "attacker-controlled-login" }
}
```
4. POST to `/webhooks` with `X-Github-Event: membership` and the forged-but-validly-signed body. `verify_signature` succeeds (it validates against `attacker`'s own secret since `repository_owner` resolves to `attacker`).
5. `MembershipHandler#process` finds the existing `Team(github_id: 999)` (still `organization: "victim"`) and calls `team.add_member(User.find_or_create_by_login!("attacker-controlled-login"))`, granting that user membership in `victim/admins`.
6. `attacker-controlled-login` logs into Shipit via GitHub OAuth; `User#authorized?` now returns true because they belong to a team in `Shipit.github_teams`, granting full access to `victim`'s stacks.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end
