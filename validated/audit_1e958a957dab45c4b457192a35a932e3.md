### Title
Stale `index-cache` Entry Lets a Later Same-Block Caller See a Pre-Socialization Vault Index - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`accrue-and-cache` caches a vault's `{index, lindex}` per `(timestamp, aid)` and, once primed by the first caller in a block, every subsequent caller for that vault/timestamp receives the cached value without re-reading the vault. Any state-mutating vault event that changes the true index *without* going through `vault-accrue` (e.g. `vault-socialize-debt`) will not invalidate this cache, so other users' operations later in the same block are evaluated against a stale index.

### Finding Description
`accrue-and-cache` is a shared, on-chain, block-scoped cache: [1](#0-0) 

It is consulted by every collateral/debt accrual path (`accrue-debt-asset`, `accrue-collateral-asset`) for *any* user's transaction in the same block: [2](#0-1) 

The cache key is `{ timestamp: stacks-block-time, aid }` only — it captures "time elapsed" but not "vault state version". This is correct only if the vault's index can change *exclusively* as a function of elapsed time (interest accrual), which is why the cache is safe against ordinary deposit/borrow/repay operations within the same second.

However, `v0-4-market.clar` also exposes `vault-socialize-debt`, a distinct call path that mutates a vault's index directly (bad-debt socialization onto suppliers) and does **not** go through `vault-accrue`/`accrue-and-cache`: [3](#0-2) 

If User A's transaction (e.g. a liquidation that produces bad debt) executes `vault-socialize-debt` for vault `aid` within a block where `index-cache` for `{timestamp, aid}` was already populated earlier in that same block (by A's own prior accrual step, or by any earlier transaction), the cache is never overwritten with the post-socialization index. Any subsequent, unrelated User B transaction in the *same block* that accrues that vault will hit the cache (`accrue-and-cache` cache-HIT branch) and receive the pre-socialization `{index, lindex}` instead of the true, lower post-loss index — directly affecting B's collateral valuation, debt valuation, and health check, none of which B controls.

### Impact Explanation
Because collateral/debt scaling and health checks for User B's position are computed from the stale (too-favorable) index served by a cache that User A's transaction silently invalidated but did not refresh, User B (or an attacker acting as B, or exploiting it against B) can:
- Borrow against collateral that is actually worth less post-socialization, extracting value the vault can't back — protocol insolvency / theft of funds at rest.
- Or have their debt undervalued, evading a liquidation that should otherwise be triggered by the fresh index — again risking insolvency for other suppliers of that vault.

This is a cross-user issue: the victim (any other market participant interacting with the same vault in the same block) never touches the cache-poisoning transaction themselves; the affected/shared state is `index-cache`.

### Likelihood Explanation
Requires: (1) a bad-debt/socialization event in a block, (2) at least one other market operation on the same vault asset occurring in the same block after the cache was primed but reading it via the cache-HIT path. Both are realistic sequencer/user-driven conditions (liquidations producing bad debt are a normal operational event, and multiple market transactions per block are expected), making this moderately likely rather than purely theoretical, though it depends on the exact ordering of transactions the block producer includes.

### Recommendation
Invalidate (or update) the relevant `index-cache` entry inside `vault-socialize-debt` (and any other path that mutates a vault's index outside the `vault-accrue` flow) immediately after the vault call returns the new index, so subsequent accruals within the same block are forced to a cache-MISS and read the fresh state, e.g.:
```clarity
(define-private (vault-socialize-debt (aid uint) (amount uint))
  (let ((result (contract-call? ... socialize-debt amount)))
    (map-set index-cache { timestamp: stacks-block-time, aid: aid } (unwrap! result ERR-...))
    result))
```

### Proof of Concept
1. Block time `T`. Vault `aid = STX` has index `I0`.
2. User B's tx1 calls a market entrypoint that touches STX collateral/debt, triggering `accrue-and-cache` → cache MISS → `vault-accrue` returns `I0` → cached at `{T, STX}`.
3. In the same block, a liquidation produces bad debt on STX; market calls `vault-socialize-debt STX amount`, which updates the real vault index to `I1 < I0` (loss socialized), but `index-cache[{T,STX}]` still holds `I0`.
4. User B (or attacker) submits tx2 in the same block performing a borrow/withdraw against STX collateral; `accrue-and-cache` hits the cache and returns stale `I0` instead of `I1`, overvaluing collateral/undervaluing debt and permitting an operation that would fail (or trigger liquidation) under the correct `I1`.

Full confirmation that `vault-socialize-debt` changes the index instantaneously (independent of elapsed time) could not be verified from the vault contract source within this session; this should be confirmed by inspecting `v0-vault-*.clar`'s `socialize-debt` implementation before treating this as fully proven.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
