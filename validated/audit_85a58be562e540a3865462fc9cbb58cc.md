### Title
Asset definer can unilaterally revoke attestor list via `asset_attestors`, permanently freezing spender-attested-asset balances - (File: validation.js)

### Summary
For assets created with `spender_attested: true`, the asset's `definer_address` can at any time publish an `asset_attestors` message that replaces the attestor list. Every payment message spending or receiving that asset requires both the input owner address and every output address to be currently attested; if the definer changes/shrinks the attestor set to exclude an address that already holds asset balance, that balance becomes permanently unspendable, and if the definer excludes the balance owner entirely (or sets an attestor list none of whose attestors will attest the address again), the funds are frozen forever with no recourse for the holder.

### Finding Description
When an asset is defined with `spender_attested: true`, `validateAssetDefinition` requires an initial attestor list [1](#0-0) . This list is not fixed: it can be updated at any later time through an `asset_attestors` message, and `validateAttestorListUpdate` only requires the message be authored by `objAsset.definer_address` — no other holder, cosigner, or the affected addresses need to consent: [2](#0-1) 

Once the attestor list changes (or the attestors simply stop re-attesting), spending from any previously-attested balance is blocked. `validatePayment` requires the spender to be in `objAsset.arrAttestedAddresses`: [3](#0-2) 

The per-input owner address is likewise checked at input-processing time: [4](#0-3) 

And every output address of the payment must also be attested, or the whole payment is rejected: [5](#0-4) 

Because attestation status is read fresh from the latest stable `asset_attestors` unit at validation time (`storage.readAsset` / `addAttestorsIfNecessary`), a definer can change the list after users have already accumulated balances of the asset: [6](#0-5) 

This is structurally analogous to the reported EigenLayer bug: a privileged party (`strategyWhitelister` / here, the asset `definer_address`) flips a restriction state (`thirdPartyTransfersForbidden` / here, the attestor whitelist) after positions already exist, and the transfer/withdrawal path (`queueWithdrawal` / here, `validatePayment`) has a hard, unconditional requirement tied to that state that ordinary token holders cannot satisfy on their own. There is no way for an affected address to self-remediate: only the definer can publish a new `asset_attestors` message, and nothing forces the definer to include an address once it holds funds.

### Impact Explanation
Any holder of a `spender_attested` asset can have their balance permanently frozen by the asset's definer simply by publishing an `asset_attestors` update that omits the holder's address (or by never re-attesting it). Because this check applies to every payment message for that asset — spends, transfers, and issuance — and both the spender and every output address must be attested, this yields outright unauthorized freezing of user funds, matching the "AA fund loss or freezing" impact bar. This is especially severe for AAs holding such an asset, since an AA cannot obtain attestation on demand and has no way to work around this restriction once triggered.

### Likelihood Explanation
Any asset definer choosing `spender_attested: true` (a normal, documented, supported asset feature) can trigger this at will and at any time after balances accumulate, requiring only a single self-authored `asset_attestors` unit. No special privilege beyond being the asset's own definer is required, and the action is indistinguishable from legitimate attestor-list maintenance, making it easy to exploit either maliciously or accidentally (e.g., definer key rotation, attestor going offline, or simple negligence in re-attesting existing holders).

### Recommendation
Consider one or more of the following:
- Grandfather already-attested addresses so that removing an address from the attestor list does not retroactively invalidate previously granted attestations for balances already held, or provide a decoupled "attestation of address" record (already partially present via `attestations`) that persists independent of the current attestor set.
- Require that any attestor-list update cannot immediately invalidate outstanding balances without a timelock/grace period, giving holders a window to move funds out under the old rules.
- Document this asset feature's centralization risk prominently so wallets/AAs can avoid holding `spender_attested` assets they don't control, and/or disallow AAs from being minted `spender_attested` assets they cannot manage.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and initial `attestors: [X]`.
2. `X` attests address `U` (`attestation` message), so `U` can freely send/receive `A` per `validatePayment`/`filterAttestedAddresses`.
3. `U` accumulates a balance of `A`.
4. `D` publishes `asset_attestors` for asset `A` with `attestors: [Y]` (a different attestor who will never attest `U`) — this passes `validateAttestorListUpdate` since it is signed by `D` alone [2](#0-1) .
5. `U` now attempts to spend from their balance of `A`. `storage.loadAssetWithListOfAttestedAuthors` recomputes `arrAttestedAddresses` from the new attestor list, `U` is no longer in it, and `validatePayment`/`validatePaymentInputsAndOutputs` reject the unit with "none of the authors is attested" / "owner address is not attested" / "some output addresses are not attested" [3](#0-2) [4](#0-3) [5](#0-4) .
6. `U`'s balance of `A` is now permanently unspendable unless `D` chooses to attest `U` again — which `D` is under no obligation to do.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
