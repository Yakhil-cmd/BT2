### Title
AA payment composer can build unbounded-input units when spending an asset with dust outputs, permanently freezing AA funds - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `sendUnit` → `completePaymentPayload` → `iterateUnspentOutputs` iterates over *all* unspent outputs of an AA address to gather enough value to cover a response payment, pushing one input per row with no cap on the number of inputs added. This is directly analogous to `frxETHMinter.depositEther`'s unbounded loop over deposits: the number of loop iterations (and thus the size of the resulting transaction) grows with an attacker-controllable quantity (number of tiny outputs sent to the AA), and there is no `maxLoops`-style limit, so the operation can become impossible to complete.

### Finding Description
`validatePaymentInputsAndOutputs` explicitly disables the input-count cap for AA-authored units: [1](#0-0) 
```
if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA)
    return callback("too many inputs");
```
Because `objValidationState.bAA` is true for AA-generated units, `MAX_INPUTS_PER_PAYMENT_MESSAGE` is not enforced when an AA composes its own outgoing payment.

The AA's payment composer, `iterateUnspentOutputs` in `aa_composer.js`, walks the full list of unspent outputs returned by `readStableOutputs`/`readUnstableOutputsSentByAAs` and pushes one input per output until the accumulated amount reaches the target amount: [2](#0-1) 

For the base (bytes) asset, there is a dust filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) baked into the SQL query: [3](#0-2) 
but for any custom asset, no equivalent dust threshold is applied — the query only filters `asset=<asset>` and `is_spent=0`, with no lower bound on `amount`, and (since the AA-only cap is skipped) no upper bound on the number of qualifying outputs that can be consumed as inputs: [4](#0-3) 

An attacker (any unprivileged unit poster / asset holder) can send a large number of very small-amount outputs of a given asset to an AA address (e.g., 1-unit transfers repeated many times, well within normal payment/asset transfer rules). Later, when a trigger causes the AA to pay out that asset (e.g. a "send all" output, or any payment whose target amount cannot be satisfied by a few big outputs), `iterateUnspentOutputs` must walk through all of these tiny outputs to accumulate enough value, adding one input per output with no loop/size cap.

### Impact Explanation
As the number of dust outputs grows, the resulting AA response unit accumulates more and more inputs. Eventually the composed unit will fail other unrelated limits (e.g., overall unit/message size limits, `MAX_MESSAGES_PER_UNIT`, oversize fee computation blowing past available balance) since input-count itself is unchecked for AA units. When `completePaymentPayload`/`validateAndSaveUnit` fails, `bounce(err)` is invoked, refunding only the bytes fee, but the underlying asset balance remains locked in the AA's dust outputs. Because the same dust set is present on every subsequent trigger that requires spending this asset, the AA can be made to **permanently fail** to construct a valid payout for that asset — the funds become stuck (frozen) with no way for governance/emergency mechanism (there is none for AAs) to recover them, directly matching the "emergency failover"/"funds stuck" impact described in the source report, i.e. AA fund freezing / denial of protocol functionality.

### Likelihood Explanation
Any address (unprivileged unit poster) can send an unlimited number of tiny-amount transfers of any custom asset to a known AA address at negligible cost (limited only by normal per-unit fees), since there is no minimum-amount/dust check on custom-asset outputs paid to AAs. AAs that pay out non-base assets in response to triggers (a common and encouraged pattern) are exposed. No special privileges, race conditions, or malicious peer/node behavior are required — this is reachable purely by posting ordinary payment units to a public AA address, matching the allowed "asset issuance and transfer conditions" / "AA definitions and triggers" attack surface.

### Recommendation
- Apply the same dust filter used for the base asset (`amount>=FULL_TRANSFER_INPUT_SIZE`-equivalent threshold) to custom-asset unspent-output queries in `readStableOutputs`/`readUnstableOutputsSentByAAs`.
- Reinstate (or add an AA-specific) hard cap on the number of inputs `iterateUnspentOutputs` may add per payment message, consistent with `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, and have `completePaymentPayload` fail gracefully (bounce) before assembling an oversized unit, while providing a mechanism (e.g., multiple sequential payments across several triggers) to gradually consolidate dust rather than requiring it all in one unit.
- Consider periodic/administrative consolidation of small outputs into larger ones (a "sweep" mechanism) independent of trigger-driven payments, to bound worst-case input count regardless of how many dust outputs accumulate.

### Proof of Concept
1. Deploy an AA that, on receiving a trigger, sends out (or "send-alls") a custom asset `X` to `trigger.address`.
2. Attacker (or any user) repeatedly sends the AA thousands of transfer messages of asset `X`, each with a minimal amount (e.g., `1` unit), each in its own unit (or many per unit up to `MAX_OUTPUTS_PER_PAYMENT_MESSAGE`), building up thousands of tiny unspent outputs of asset `X` at the AA's address. This is unrestricted because custom-asset outputs to an AA have no dust-amount floor unlike the base asset.
3. Trigger the AA to pay out asset `X` (e.g., a full balance/send-all payout, or any payout whose required amount forces the composer to walk through all the dust outputs, since `MAX_INPUTS_PER_PAYMENT_MESSAGE` is bypassed for AA units per `validation.js:2137`).
4. `iterateUnspentOutputs` in `aa_composer.js` accumulates one input per tiny output; with enough dust outputs pre-seeded by the attacker, the resulting payment message/unit grows unboundedly, eventually failing unit-size/message-count validation in `validateAndSaveUnit`, causing `bounce()` to fire on every future attempt to pay out this asset — the AA can no longer ever release its holdings of asset `X`, freezing those funds indefinitely.
