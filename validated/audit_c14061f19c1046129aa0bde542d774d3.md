### Title
Webhook Repository Binding Bypass via Divergent `repository.owner.login` and `repository.full_name` Fields Allows Cross-Tenant Stack Mutation - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `params.dig('repository', 'owner', 'login')`, but `Handler#stacks` (used by every event handler including `PushHandler`) resolves which `Stack`/`Repository` to mutate using the independent `params.dig('repository', 'full_name')` field from the same attacker-controlled JSON body. Because these two fields are never checked for consistency, an attacker who legitimately owns Org B and knows Org B's real `webhook_secret` can sign an arbitrary payload where `repository.owner.login = "orgb"` but `repository.full_name = "orga/some-repo"`, passing signature verification against Org B's secret while causing the handler to act on Org A's stack.

### Finding Description
The binding the code is supposed to enforce is: `organization whose webhook_secret verified request.raw_post == organization owning the repository/stack that the handler subsequently mutates`. Concretely this should mean `params.dig('repository','owner','login') == Repository.from_github_repo_name(params.dig('repository','full_name')).owner`.

Tracing the code:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, request.raw_post)` [1](#0-0) [2](#0-1) .
- `verify_webhook_signature` just HMAC-verifies the raw body bytes against whichever org's `webhook_secret` was selected — it has no knowledge of, or opinion on, `full_name` [3](#0-2) .
- Once verification passes, `Handler#stacks` resolves the target using a *different* field of the same payload: `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [4](#0-3) .
- `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` lookup with no cross-check against whichever organization actually verified the signature [5](#0-4) .
- `PushHandler#process` then does `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` — a real write/enqueue against Org A's stack [6](#0-5) .

Since the attacker constructs the raw JSON body themselves (this is a forged HTTP POST to `/webhooks`, not a relayed genuine GitHub webhook), nothing forces `repository.owner.login` and `repository.full_name`'s owner segment to agree — GitHub itself would never produce such an inconsistent payload, but Shipit does not require the payload to have come from GitHub beyond the HMAC check, and the HMAC check validates only byte-for-byte body integrity against whichever secret was looked up via `repository.owner.login`. No other guard (`drop_unhandled_event`, `check_if_ping`, `ExplicitParameters` schema in `PushHandler`/`StatusHandler`) inspects or cross-validates `full_name` against `owner.login`.

Attacker request: attacker owns Org B and knows Org B's `webhook_secret` (they configured it on both the GitHub org's webhook settings and it matches what the Shipit operator configured for `Shipit.github(organization: 'orgb')`). They POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": {"login": "orgb"},
    "full_name": "orga/some-repo"
  }
}
```
signed with `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_orgb, raw_body)>`, computed by the attacker themselves since they know `webhook_secret_orgb`.

### Impact Explanation
`verify_signature` passes (Org B's own secret correctly verifies the body), but `PushHandler#process` calls `Repository.from_github_repo_name("orga/some-repo")` and, if that Repository/Stack exists, triggers `stack.sync_github(expected_head_sha: params.after)` on an Org A stack the attacker never authenticated against. This is a payload for one repository (Org B, correctly signed) mutating another repository's stack (Org A) — matching the Critical-severity category explicitly listed in scope ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any existing `orga/*` repository configured in Shipit as long as the attacker can guess/know its `full_name`, and requires no privilege beyond owning any onboarded Org B in the same Shipit instance.

### Likelihood Explanation
Preconditions: the Shipit instance must be multi-tenant (host multiple GitHub organizations each with `Shipit.github(organization: X)` configured), and the attacker must legitimately own/administer at least one onboarded organization (Org B) so they know its real `webhook_secret`. This is a normal, expected configuration for shared Shipit deployments serving multiple GitHub orgs. Attacker cost is trivial: one crafted HTTP POST with a correctly computed HMAC using a secret they already know. The attack is fully repeatable and requires no interaction with Org A or its maintainers.

### Recommendation
In `Handler#stacks`/`Handler#initialize`, cross-check that the `owner` segment of `payload.dig('repository','full_name')` matches `payload.dig('repository','owner','login')` (or better, pass the verified `repository_owner` from the controller into the handler and require the resolved `Repository#owner` to equal it) before returning any stacks; reject/no-op otherwise. Equivalently, have `WebhooksController#verify_signature` also assert the owner segment of `full_name` matches `repository_owner` prior to dispatching to handlers.

### Proof of Concept
Minitest integration test under `test/controllers/webhooks_controller_test.rb` style (illustrative, adapted to existing test helpers for configuring two orgs' `webhook_secret`s):
```ruby
test "push webhook signed by orgb mutates orga's stack via full_name/owner divergence" do
  stub_github_app_config('orga', webhook_secret: 'orga-secret')
  stub_github_app_config('orgb', webhook_secret: 'orgb-secret')

  orga_repo = shipit_repositories(:orga_repo) # owner: 'orga', name: 'some-repo'
  orga_stack = shipit_stacks(:orga_stack, repository: orga_repo, branch: 'main')

  payload = {
    ref: 'refs/heads/main',
    after: 'deadbeef' * 5,
    repository: { owner: { login: 'orgb' }, full_name: 'orga/some-repo' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'orgb-secret', payload)}"

  assert_enqueued_with(job: GithubSyncJob, args: [orga_stack.id, anything]) do
    post shipit.webhooks_path,
      params: payload,
      headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => signature, 'Content-Type' => 'application/json' }
  end

  assert_response :ok
  # binding check: signature verified against 'orgb' secret, yet orga_stack (owned by 'orga') was mutated
end
```
This demonstrates the equality `repository_owner_used_for_verification ('orgb') != repository.full_name_owner_used_for_mutation ('orga')` while the mutation still succeeds, with no live GitHub required.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
