### Title
Missing Authorization on Pending Shared-Address Deletion via `reject_new_shared_address` Device Message - ([File: wallet_defined_by_addresses.js])

### Summary
The `reject_new_shared_address` device-message handler deletes a pending multi-device shared (multisig) address record identified only by its `address_definition_template_chash`, without verifying that the sending device is actually one of the cosigning members of that specific pending address. Any correspondent device that learns or guesses a `definition_template_chash` can unilaterally wipe out another set of users' in-progress shared-address creation, analogous to the reported DolphinScheduler flaw where any logged-in user could delete another user's UDF resource because the delete endpoint lacked an ownership check.

### Finding Description
In `wallet.js`, the hub-message handler for subject `reject_new_shared_address` only validates the format of the `address_definition_template_chash` field and then calls the deletion function directly, without checking that `from_address` participates in the referenced pending shared address: [1](#0-0) 

That deletion function, `deletePendingSharedAddress`, takes only the `address_definition_template_chash` and deletes both `pending_shared_address_signing_paths` and `pending_shared_addresses` rows for it — there is no `device_address`/ownership parameter at all: [2](#0-1) 

This is in clear contrast to the sibling flow for cancelling a single-sig/multisig wallet creation, `deleteWallet`, which explicitly checks that the `rejector_device_address` is a registered, not-yet-approved member of the wallet before deleting anything: [3](#0-2) 

Because `reject_new_shared_address` is not in the whitelist of subjects allowed from non-correspondents, the sender must be a known correspondent device of the victim node, but that correspondent need not be one of the actual cosigners of the targeted shared-address definition. The correspondence check is done generically in `device.js`, not scoped per shared address: [4](#0-3) 

An attacker who is any paired correspondent (or who otherwise learns the `definition_template_chash`, e.g. by being invited as a cosigner in an unrelated/decoy definition that shares the hash context, or by intercepting `create_new_shared_address` traffic when acting as an indirect correspondent) can send a forged `reject_new_shared_address` message and delete a legitimate pending multisig/shared-address record that they are not a party to, matching the "missing authorization to delete another user's resource" pattern of GHSA-r44q-98gx-pmh2 / CVE-2023-49620.

### Impact Explanation
This allows an unauthorized, unprivileged correspondent device to destroy another set of users' in-progress shared/multisig address setup at will (an integrity/availability impact on cosigning state, matching the CVSS vector of the reference advisory: no confidentiality impact, high integrity impact, no direct confidentiality-only spend). Because shared addresses are frequently used to hold and jointly control funds, disrupting their creation process can delay or permanently block legitimate cosigners from finishing setup of an address that a counterparty may already be relying on (e.g., about to fund), effectively griefing wallet/multisig provisioning for victims who never authorized the deleting device to interfere with their pending address.

### Likelihood Explanation
Likelihood is moderate: the attacker must already be a correspondent (paired) device of the victim, and must learn the `address_definition_template_chash` value, which is a 160-bit c-hash of the definition template and not otherwise broadcast publicly. However, it is directly reachable from any correspondent without needing to be a cosigner of that specific pending address, and requires no cryptographic forgery of signatures — only a valid device-message envelope, which is standard "reachable via device message handling" surface.

### Recommendation
In `deletePendingSharedAddress` (or its caller), require and verify a `device_address` argument and check, before deleting, that the requesting device is actually listed in `pending_shared_address_signing_paths` for the given `definition_template_chash` — mirroring the check already performed in `deleteWallet`. Reject the request (respond with an error, do not delete) if the sender is not a recognized member of that specific pending shared address.

### Proof of Concept
1. Device A creates a pending shared address involving devices A and B via `create_new_shared_address` / `createNewSharedAddressByTemplate`, obtaining `address_definition_template_chash` = H.
2. Attacker device C, a correspondent of device A but not a party to H's definition (or who has otherwise obtained H), sends a hub message:
   `{ subject: "reject_new_shared_address", body: { address_definition_template_chash: H } }`
3. On device A, `handleMessageFromHub` dispatches to `walletDefinedByAddresses.deletePendingSharedAddress(H)` with no check that C is a party to H, per [1](#0-0) .
4. The pending shared-address rows for H are deleted from `pending_shared_addresses` and `pending_shared_address_signing_paths`, destroying devices A and B's in-progress multisig setup without their consent.
