### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`) field, proving only that the request was legitimately signed by *that* organization's webhook secret [1](#0-0) . However, `StatusHandler#process` never re-checks that the commit it mutates actually belongs to the repository/stack that was authenticated — it looks up commits engine-wide by `sha` alone: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This breaks the binding "organization that authenticated == repository that is written," since the authenticated org's payload can write a status onto a `Commit` row owned by an entirely different `Stack`/repository/organization whenever a SHA collision (accidental, e.g. shared git history from a fork, or otherwise) occurs across tenants of the same Shipit instance.

### Finding Description
- The base `Handler` class computes `repository_name` from `payload.dig('repository', 'full_name')` and uses it to scope stacks in most handlers (e.g. `PushHandler`) via `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) .
- `StatusHandler`, unlike `PushHandler`, does not use `stacks`/`repository_name` at all. It queries `Commit.where(sha: params.sha)` with no `stack_id`/repository filter [2](#0-1) .
- `Commit#sha` is not unique per Shipit installation — multiple `Stack` records (different repos, potentially different GitHub organizations, e.g. forks or repos sharing squashed/rebased history) can each have their own `Commit` row with the identical `sha` value.
- The signature check in `WebhooksController#verify_signature` only proves the request came from the org named in the payload's `repository.owner.login`; it says nothing about which `Commit` rows in the local database the payload is entitled to modify [4](#0-3) .
- Because `StatusHandler` iterates over *every* `Commit` with a matching `sha` regardless of which stack/org it belongs to, an attacker who controls a legitimate GitHub App installation on their own (unrelated) repository can send a properly-signed `status` webhook referencing a `sha` that also exists as a commit in a victim stack tracked by the same Shipit instance, and `create_status_from_github!` will write a forged status (e.g., `state: success`) onto the victim's `Commit` [5](#0-4) .

Equality broken: `organization authenticated by verify_signature` ≠ `repository/stack whose Commit row is written by StatusHandler`.

Before the attack: victim's commit has its true GitHub-derived status (e.g., pending/failure) recorded only via the legitimate repository's own status webhooks.
After the attacker's webhook: the same `Commit` row (matched purely by `sha`) also has a spoofed status inserted from an unrelated, attacker-controlled repository's webhook.

### Impact Explanation
`Commit#deployable?` computes `success? && !blocked?`, which is derived from the aggregated `status` built from `statuses` records [6](#0-5) [7](#0-6) . Injecting a forged "success" status can flip a commit's deployability and even trigger `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?` [8](#0-7) . This can cause an unreviewed/failing commit to be deployed by continuous delivery — an unauthorized deploy — solely because a SHA happened to collide with a commit an attacker controls in an unrelated repository they can legitimately push webhooks for. This matches the "unauthorized deploy" Critical-impact category.

### Likelihood Explanation
Exploitation requires (a) the attacker to control/own a repository with its own valid GitHub App/webhook configuration recognized by this Shipit instance (multi-tenant deployments), and (b) a SHA collision between a commit in the attacker's repository and a commit in the victim's tracked stack. Genuine SHA collisions across unrelated histories are cryptographically infeasible, but they are realistic in common cases such as forks, repository migrations, or shared submodule histories where identical commits legitimately exist in multiple repositories tracked as separate Shipit stacks — a scenario the report's `vaultID` collision (attacker choosing/observing an identifier that also matches a victim's) directly parallels. Likelihood is therefore low but non-zero, with high impact once triggered, consistent with the source report's own Medium severity rationale.

### Recommendation
Scope the `StatusHandler` lookup to the repository/stack identified by the authenticated webhook payload, mirroring `PushHandler`'s pattern: replace `Commit.where(sha: params.sha)` with a query restricted to `stacks` (derived from `repository_name`/`Repository.from_github_repo_name`), e.g. `Commit.where(sha: params.sha, stack: stacks)`, ensuring a status can only be applied to commits belonging to the same repository that was cryptographically verified as the webhook sender.

### Proof of Concept
1. Attacker owns/administers `attacker/repo`, which has a Shipit-recognized GitHub App installation with its own valid `webhook_secret`.
2. Attacker identifies (or engineers, e.g. via a shared fork/rebase history) a commit `sha` that is identical to a commit tracked under victim stack `victim/repo` in the same Shipit instance.
3. Attacker triggers (or crafts) a `status` event from GitHub for `attacker/repo` referencing that `sha` with `state: success`. Because it is genuinely signed by `attacker/repo`'s app, `verify_signature` passes.
4. `WebhooksController#create` dispatches to `StatusHandler`, whose `process` runs `Commit.where(sha: params.sha)` [2](#0-1)  — this matches the `Commit` row belonging to `victim/repo`'s stack as well.
5. `commit.create_status_from_github!(params)` records the forged "success" status on the victim's commit [5](#0-4) , potentially making a previously non-deployable/failing commit `deployable?` and eligible for continuous delivery deployment on the victim stack — an unauthorized deploy achieved purely through the attacker's own, legitimately-authenticated webhook channel.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified

      Rails.logger.info([

        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
