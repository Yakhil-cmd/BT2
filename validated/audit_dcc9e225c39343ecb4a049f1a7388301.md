### Title
Private-asset deposits sent to an Autonomous Agent (AA) address are permanently locked because AAs are never triggered by private outputs and can never construct private-asset payments themselves - ([File: main_chain.js], [File: aa_composer.js])

### Summary
Any unprivileged unit poster (or private-payment counterparty) can send a private asset to an AA address just like sending it to any regular address. Nothing in the wallet/composer code path blocks this. However, the AA subsystem structurally excludes private outputs from ever triggering an AA, and even where an AA does attempt to act, it explicitly refuses to build outgoing private-asset payments because it cannot generate the required spend proofs. The result: funds sent to an AA in a private asset become permanently unspendable — mirroring the reported class of bug where value is deposited "via" a contract-like address that has no mechanism to interact with the machinery required to move that value back out.

### Finding Description
Two independent code paths converge to create this permanent lock:

1. AAs are only triggered by non-private outputs. The query that populates `aa_triggers` explicitly filters out private outputs with `(outputs.asset IS NULL OR is_private=0)`: [1](#0-0) 
This means a unit that pays a private asset to an AA address never causes `handleAATriggers`/`handleTrigger` to run for that deposit — the AA has no opportunity to react, record, or forward those funds.

2. Even in scenarios where the AA *is* triggered for other reasons and attempts to send a private asset out of its own initiative (e.g., forwarding a balance it thinks it holds), the composer explicitly bounces the response because AAs cannot produce the spend proofs private payments require: [2](#0-1) 

Nothing in the deposit path prevents a wallet or automated payer from directing a private asset to an AA address in the first place. `checkAAOutputs`, the only AA-specific guard invoked from `sendMultiPayment`, checks only that bounce fees are covered — it has no awareness of asset privacy: [3](#0-2) [4](#0-3) 

Private payments also require the recipient to receive the off-chain hidden-chain payload (blinding factors, spend proofs, chain of outputs) via direct wallet-to-wallet delivery in order to later spend the coins — an AA has no device/wallet backend capable of receiving or processing this off-chain private-chain protocol at all, so even disregarding the trigger-filter issue, the AA could never reconstruct the spend proof needed to move the coins (`validateDivisiblePrivatePayment`/`validatePrivatePayment` require prior blinding and output data that only reaches genuine wallet software): [5](#0-4) 

### Impact Explanation
Any private asset sent to an AA address is permanently frozen: the AA cannot be triggered by it, and even if some other trigger caused the AA to try to spend it, the composer aborts the private-asset payment message. There is no path — via the AA's own code, its owner, or the depositor — to recover these funds. This is a High-severity, deterministic freezing-of-funds condition triggerable by any unprivileged user simply by directing a private-asset payment at any AA address (including their own funds by mistake, or by a script/AA-based counterparty automatically forwarding deposits into an AA, echoing the exact "vault forwards to a contract that cannot withdraw" pattern from the source report).

### Likelihood Explanation
Likelihood is high in the sense that it requires no privileged access, malicious peer, or timing race — a single ordinary private-asset payment message directed at any known AA address triggers the condition. It's most likely to occur accidentally (a user or bot script sending a private asset to what they assume is a normal address, or a private-asset-issuing AA/proxy contract forwarding user private-asset deposits into another AA), rather than being intentionally exploited for direct profit, since the loss falls on the depositor rather than benefiting an attacker. Still, it constitutes unconditional, permanent AA fund loss/freezing, matching the "Accept" criteria for AA fund loss or freezing.

### Recommendation
Add an explicit guard, symmetric to the bounce-fee check in `checkAAOutputs`/`sendMultiPayment`, that rejects private-asset payments whose destination is a known AA address before the payment is composed and broadcast. Additionally, consider hardening validation (`validatePayment`/`validatePaymentInputsAndOutputs`) to reject private payment messages whose only output address resolves to an AA address at validation time, so that even manually crafted units cannot lock private-asset funds into AAs, and document this restriction clearly for AA authors and asset issuers.

### Proof of Concept
1. Define and deploy any simple AA (e.g. `test/samples/simple_aa.oscript`), obtaining its address `AA_ADDR`.
2. Issue or otherwise obtain a private, divisible or indivisible asset (`is_private: true`).
3. Using the wallet composer, send a private-asset payment with `to_address: AA_ADDR` — the code path `sendMultiPayment` → `checkAAOutputs` (bounce-fee check only) → `composeDivisibleAssetPaymentJoint`/`indivisible_asset` composer does not block this send.
4. The unit is written and stabilizes; observe that `main_chain.js`'s `handleAATriggers` query never selects this unit/address pair because of the `is_private=0` filter, so no `aa_triggers` row is created and `handleTrigger` never runs for this deposit.
5. Confirm that even if the AA were externally triggered (e.g., by a secondary trigger designed to forward "its balance" of this private asset), `aa_composer.js`'s `sendUnit` path bounces with `"sending private asset from AA"` for any attempt to construct an outgoing payment in that asset.
6. The private-asset funds at `AA_ADDR` remain permanently unspendable by any process.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
