### Title
Global nonce mapping in `SuiBridge.sol` not scoped by source chain causes cross-chain nonce collision and permanent fund lock - (File: bridge/evm/contracts/SuiBridge.sol)

### Summary
`SuiBridge.sol` tracks processed token-transfer bridge messages in `mapping(uint64 nonce => bool isProcessed) public isTransferProcessed`, keyed only by `message.nonce`. On the Move side, `BridgeMessageKey` (and the `seq_num` counter that produces `message.nonce`) is scoped per `source_chain` (`crates/sui-framework/packages/bridge/sources/message.move` lines 40-44, 515-521), so different source chains independently produce sequence numbers starting at 0. Since `chain_ids.move`'s `valid_routes()` allows both `SUI_TESTNET` and `SUI_CUSTOM` to route to the same destination (`ETH_SEPOLIA`/`ETH_CUSTOM`), a single deployed `SuiBridge.sol` instance can legitimately receive committee-signed token-transfer messages from two distinct source chains that reuse the same `nonce` value. Because `isTransferProcessed` is not also keyed by `message.chainID` (the source chain), the second, entirely distinct and validly-signed transfer will be rejected as "already processed," permanently preventing its claim.

### Finding Description
This is the same root-cause class as the external QuickAccManager report: a replay/dedup guard (nonce) is scoped to the wrong entity. In the reference bug, nonces were indexed by `identity` instead of the signer (`accHash`), causing collisions across different identities sharing one signer. Here, the roles are reversed but the defect is structurally identical: the nonce/dedup key omits the entity that must be part of the scope (the source chain), causing two independently-numbered, distinct, validly-signed messages to collide in the dedup table.

- `crates/sui-framework/packages/bridge/sources/chain_ids.move` lines 66-79 defines routes where both `SUI_TESTNET -> ETH_SEPOLIA/ETH_CUSTOM` and `SUI_CUSTOM -> ETH_SEPOLIA/ETH_CUSTOM` are valid simultaneously. [1](#0-0) 
- On the Sui side, sequence numbers used to build `message.nonce` are tracked per `source_chain` via `BridgeMessageKey{source_chain, message_type, bridge_seq_num}`, meaning `SUI_TESTNET` and `SUI_CUSTOM` each independently produce `seq_num = 0, 1, 2, ...`. [2](#0-1) 
- On the EVM side, `SuiBridge.sol` stores processed-transfer state in a single global mapping keyed only by `nonce`, with no source-chain component: [3](#0-2) 
- `transferBridgedTokensWithSignatures` checks and sets this mapping purely by `message.nonce`, and the `verifyMessageAndSignatures` modifier for `TOKEN_TRANSFER` messages explicitly skips chain-ID validation (`if (messageType != BridgeUtils.TOKEN_TRANSFER)`), so `message.chainID` (the source chain) is never enforced to be unique per nonce: [4](#0-3) [5](#0-4) 

Once tokens are deposited/burned on the Sui side via `send_token_internal`, the transfer is recorded and awaits claim on the destination chain; there is no other mechanism to reclaim the tokens if the destination-side claim permanently fails. [6](#0-5) 

### Impact Explanation
If two distinct source chains that route to the same `SuiBridge.sol` deployment (e.g. `SUI_TESTNET` and `SUI_CUSTOM` both routing to `ETH_SEPOLIA`) happen to produce token-transfer messages with the same `nonce` value (which is expected behavior since sequence numbers restart at 0 independently per source chain), only the first message to be relayed can ever be claimed. The second, fully legitimate, committee-signed message will be permanently rejected by `require(!isTransferProcessed[message.nonce], ...)`, because the check does not also require the recorded nonce to match the same source `chainID`. Since the corresponding tokens are already escrowed/burned on the Sui side with no compensating recovery path, this results in a **permanent lock of user funds** — a High-severity impact under the allowed HackenProof bounty categories.

### Likelihood Explanation
This does not require a malicious validator, bridge authority, or governance quorum — it is a deterministic collision inherent to the current EVM contract's dedup design whenever multiple valid source chains are configured for one destination bridge contract, which the Move-side `chain_ids::valid_routes()` table explicitly supports. It requires no privileged action by the trigger: any ordinary user or relayer submitting the second (equally valid) signed message triggers the permanent block. The main uncertainty is whether current mainnet deployment topology multiplexes more than one active source chain onto a single `SuiBridge.sol` instance (mainnet routes appear 1:1), but the testnet/custom routes and the contract code itself provide no defense-in-depth against this regardless of deployment topology.

### Recommendation
Scope the processed-transfer dedup key by both `message.chainID` (source chain) and `message.nonce`, e.g. `mapping(uint8 chainID => mapping(uint64 nonce => bool)) isTransferProcessed`, mirroring the Move-side `BridgeMessageKey{source_chain, message_type, bridge_seq_num}` design. Additionally, verify `message.chainID` against the set of chains actually routed to this contract for `TOKEN_TRANSFER` messages instead of only validating destination chain in `transferBridgedTokensWithSignatures`.

### Proof of Concept
1. Deploy `SuiBridge.sol` configured to accept transfers routed from both `SUI_TESTNET` (chainID=1) and `SUI_CUSTOM` (chainID=2) to `ETH_SEPOLIA`, per `chain_ids::valid_routes()`.
2. On `SUI_TESTNET`, call `send_token` to bridge tokens; the resulting `BridgeMessage` gets `seq_num = 0` for `(source_chain=SUI_TESTNET, message_type=TOKEN_TRANSFER)`.
3. On `SUI_CUSTOM`, independently call `send_token` to bridge different tokens/recipient; because sequence numbers are tracked independently per `source_chain`, this message also gets `seq_num = 0` for `(source_chain=SUI_CUSTOM, message_type=TOKEN_TRANSFER)`.
4. Committee signs both messages independently (both are legitimate, distinct payloads with different `chainID`, `sender`, `recipient`, `amount`).
5. Relay message 1 (`chainID=SUI_TESTNET, nonce=0`) to `transferBridgedTokensWithSignatures`; it succeeds, tokens transferred from vault, and `isTransferProcessed[0] = true` is set.
6. Relay message 2 (`chainID=SUI_CUSTOM, nonce=0`) with its own valid committee signatures; `require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed")` reverts, permanently blocking the second legitimate transfer even though it is a completely different, correctly signed transaction. The tokens are already burned/escrowed on the Sui side with no recovery path, resulting in permanent fund lock for that user.

fun send_token_internal<T>(
    inner: &mut BridgeInner,
    target_chain: u8,
    token: Coin<T>,
    message: BridgeMessage,
) {
    assert!(!inner.paused, EBridgeUnavailable);
    assert!(chain_ids::is_valid_route(inner.chain_id, target_chain), EInvalidBridgeRoute);

    // burn / escrow token, unsupported coins will fail in this step
    inner.treasury.burn(token);

    // Store pending bridge request
    inner
        .token_transfer_records
        .push_back(
            message.key(),
            BridgeRecord {
                message,
                verified_signatures: option::none(),
                claimed: false,
            },
        );
}
