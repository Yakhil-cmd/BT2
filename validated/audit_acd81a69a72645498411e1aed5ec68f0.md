### Title
Whitelisted `shipit.yml` deploy/task variables can override Shipit's own security-relevant environment keys (`GITHUB_TOKEN`, `IGNORED_SAFETIES`) - (File: lib/shipit/task_commands.rb)

### Summary
`EnvironmentVariables#permit` only checks that a *key name* is present in the `deploy.variables`/`tasks.*.variables` whitelist declared in `shipit.yml`; it never checks that the name doesn't collide with a key Shipit itself sets. Because the user-supplied, "permitted" hash is merged **last** when building the final process environment, a variable definition whose `name` matches one of Shipit's own fixed/security-relevant keys lets any caller with ordinary `deploy:stack`/`write:hook` level access silently overwrite it.

### Finding Description
`EnvironmentVariables#sanitize_env_vars` performs pure key-membership filtering with no denylist for Shipit-reserved names: [1](#0-0) 

`Stack#build_deploy` / `Stack#trigger_task` apply this permit-only filter to the caller-supplied `env` and store the result on the `Task`/`Deploy` record: [2](#0-1) 

At execution time, `TaskCommands#env` builds the final process environment by merging, in order: base env → stack env → **Shipit's own fixed keys** (`SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`) → `deploy_spec.machine_env` → **`@task.env`, applied last**: [3](#0-2) 

`Commands#base_env` (inherited via `TaskCommands < Commands`) additionally seeds `GITHUB_TOKEN` and `GITHUB_DOMAIN` into that same base env, which is merged *before* `@task.env`, so it is subject to the same last-write-wins override: [4](#0-3) 

Because `@task.env` is applied last, and its only gate is "is this key name declared in `shipit.yml`'s `deploy.variables`/`tasks.*.variables`", a `shipit.yml` author (or anyone with control over that file — a normal, unprivileged contributor to the deployed repository, not a Shipit admin) can declare a variable literally named `IGNORED_SAFETIES`, `GITHUB_TOKEN`, `TASK_ID`, `GIT_COMMITTER_EMAIL`, etc. Any subsequent caller who is merely allowed to trigger a deploy/task (`deploy:stack` permission, or the standard web UI deploy form) can then supply a value for that "permitted" variable and have it silently clobber the value Shipit itself computed and injected — the binding "environment key permitted (name check against `shipit.yml` whitelist) equals environment key spawned (actual key placed in the deploy script's process environment)" is broken: the whitelist authorizes a *name*, but the merge order lets that name displace a Shipit-internal control value rather than merely adding a new, distinct variable. [5](#0-4) 

### Impact Explanation
The most severe consequence is exfiltration of `GITHUB_TOKEN`: if `shipit.yml` declares a variable named `GITHUB_TOKEN`, the value supplied by the deploying user replaces Shipit's installation-scoped GitHub App token in the child process's environment before the deploy/task shell commands run — but because Shipit's own git/checkout steps (`clone`, `checkout`, `fetch`) also rely on this same environment via `Commands#base_env`/`git`, and because the deploy script itself can simply `echo $GITHUB_TOKEN` to print (exfiltrate) whichever value ends up in scope, an attacker able to control `shipit.yml` variable declarations and trigger a deploy can leak or manipulate `GITHUB_TOKEN` usage. Separately, `IGNORED_SAFETIES` is meant to reflect whether `force`/safety-bypass was actually granted (`Task#ignored_safeties?`, gated by permission checks in the controllers); if a deploy script or downstream tooling trusts this environment variable to decide whether to skip safety checks, an ordinary deployer can flip it to `1` without ever being granted the `force` capability, causing an unauthorized/unsafe deploy to proceed as though safeties were explicitly overridden.

### Likelihood Explanation
This requires only: (1) the ability to add/modify a `deploy.variables`/`tasks.*.variables` entry in the deployed repository's `shipit.yml` (an ordinary, unprivileged contributor capability in many workflows, not a Shipit-admin or API-client privilege), and (2) the standard, low `deploy:stack` permission to trigger a deploy while supplying a value for that variable. No webhook secret, API client secret, or GitHub App private key is needed, and no session/token forgery is required — it uses the engine's own designed variable-passing mechanism exactly as coded, just exploiting the unchecked name collision and merge order.

### Recommendation
In `Shipit::EnvironmentVariables#permit` (or in `TaskCommands#env`), reject or reserve variable names that collide with Shipit-injected environment keys (`GITHUB_TOKEN`, `GITHUB_DOMAIN`, `GIT_ASKPASS`, `SHIPIT`, `SHIPIT_LINK`, `SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, `TASK_ID`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `SHA`, `REVISION`, `DIFF_LINK`, `ENVIRONMENT`, `BRANCH`, `LAST_DEPLOYED_SHA`), either at `shipit.yml` parse time (`VariableDefinition`/`DeploySpec#deploy_variables`/`task_definitions`) or by merging `@task.env` before the fixed keys in `TaskCommands#env` instead of after.

### Proof of Concept
1. In the target stack's `shipit.yml`:
```yaml
deploy:
  variables:
    - name: IGNORED_SAFETIES
      default: "0"
```
2. As a user holding only `deploy:stack` permission (no force/ignore-safeties grant), call the deploy API with `env: { "IGNORED_SAFETIES" => "1" }`:
```
POST /api/stacks/:stack_id/deploys
{ "sha": "<commit>", "env": { "IGNORED_SAFETIES": "1" } }
```
3. `EnvironmentVariables.with(env).permit(deploy_variables)` accepts it because `IGNORED_SAFETIES` is a declared name (`lib/shipit/environment_variables.rb:35-44`).
4. At execution time, `TaskCommands#env` merges `@task.env` last, so the deploy script observes `IGNORED_SAFETIES=1` even though `Task#ignored_safeties?` for this run was never actually true (`lib/shipit/task_commands.rb:33-48`).

<h2 id="script-parameters">Script parameters</h2>

Your deploy scripts have access to the following environment variables:

* `SHIPIT`: Set to `1` to allow your script to know it's executed by Shipit
* `SHIPIT_LINK`: URL to the task output, useful to broadcast it in an IRC channel
* `SHIPIT_USER`: Full name of the user that triggered the deploy/task
* `GITHUB_REPO_NAME`: Name of the GitHub repository being used for the current deploy/task.
* `GITHUB_REPO_OWNER`: The GitHub username of the repository owner for the current deploy/task.
* `EMAIL`: Email of the user that triggered the deploy/task (if available)
* `ENVIRONMENT`: The stack environment (e.g `production` / `staging`)
* `BRANCH`: The stack branch (e.g `main`)
* `LAST_DEPLOYED_SHA`: The git SHA of the last deployed commit
* `DIFF_LINK`: URL to the diff on GitHub.
* `TASK_ID`: ID of the task that is running
* All the content of the `secrets.yml` `env` key
* All the content of the `shipit.yml` `machine.environment` key
