### Title
Same-Epoch Dual Vote Bypasses `LowerBoundBaseFee ≤ UpperBoundBaseFee` Invariant, Permanently Corrupting Base-Fee Calculation — (`kaiax/gov/headergov/impl/header.go`)

---

### Summary

`checkConsistency` validates each governance vote individually against the **currently-effective** parameter set. When `kip71.lowerboundbasefee` and `kip71.upperboundbasefee` are both voted on inside the **same epoch**, each vote passes its individual check against the pre-epoch effective values, but the combined governance data committed at the epoch boundary can have `LowerBoundBaseFee > UpperBoundBaseFee`. `NextMagmaBlockBaseFee` then produces a permanently oscillating, gas-usage-insensitive base fee, breaking the EIP-1559-style fee mechanism for every subsequent block until a corrective governance vote takes effect one full epoch later.

---

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` enforces the cross-parameter invariant at vote time by comparing the proposed value against `GetParamSet(blockNum)`, which returns the **effective** parameter set from the previous epoch boundary — it does not include any pending votes already cast in the current epoch:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)          // effective params, NOT pending votes
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)          // same snapshot
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
```

Because both checks use the same frozen snapshot, two votes cast in the same epoch are never cross-validated against each other.

**Attack path (governance `none` mode — any GC member may vote):**

| Block | Action | Check performed | Result |
|-------|--------|-----------------|--------|
| current effective | `Lower=25 gwei`, `Upper=750 gwei` | — | — |
| 100 (epoch 0) | GC member A votes `Lower = 500 gwei` | `500 ≤ 750` (current upper) | ✅ passes |
| 200 (epoch 0) | GC member B votes `Upper = 100 gwei` | `100 ≥ 25` (current lower) | ✅ passes |
| epoch boundary | governance data `{Lower:500, Upper:100}` committed | no cross-check at `VerifyGov` | ❌ `Lower > Upper` |

`VerifyGov` only verifies that the committed governance data matches the locally-derived vote aggregation; it performs no cross-parameter invariant check:

```go
// (5) the parsed json must exactly match the map derived locally from the previous epoch's votes.
if !reflect.DeepEqual(expected, actual) {
    return ErrGovVerification
}
```

The invalid parameter pair is therefore accepted by every node and persisted to chain state.

---

### Impact Explanation

`NextMagmaBlockBaseFee` in `params/kip71_config.go` assumes `LowerBound ≤ UpperBound`. When the invariant is violated (e.g., `Lower=500 gwei`, `Upper=100 gwei`), the clamping logic at lines 82–86 always fires the first branch:

```go
if parentBaseFee.Cmp(upperBoundBaseFee) >= 0 {   // always true: any fee ≥ 100 gwei
    parentBaseFee = upperBoundBaseFee              // clamp to 100 gwei
} else if parentBaseFee.Cmp(lowerBoundBaseFee) <= 0 {
    parentBaseFee = lowerBoundBaseFee
}
```

After clamping, `parentBaseFee = 100 gwei`:

- **Gas usage < target**: `nextBaseFee` decreases below `lowerBound (500)` → returns `lowerBound = 500 gwei`
- **Gas usage > target**: shortcut `parentBaseFee == upperBound` → returns `upperBound = 100 gwei`
- **Gas usage == target**: returns `parentBaseFee = 100 gwei`

The base fee oscillates between 100 gwei and 500 gwei with no relationship to actual gas demand. Because `VerifyMagmaHeader` checks that each block's `BaseFee` equals `NextMagmaBlockBaseFee`, all honest nodes compute the same wrong value and accept it — there is no consensus split, but the fee mechanism is permanently broken until a corrective vote takes effect one full epoch later (up to 604 800 blocks / ~1 week on Mainnet).

Concrete consequences:
- Every transaction's effective gas cost is set by a corrupted base fee, constituting an incorrect fee charge on KAIA.
- The EIP-1559 congestion-control invariant (base fee rises under load, falls under low load) is destroyed for the duration.
- Wallets and fee estimators that rely on `eth_gasPrice` / `eth_feeHistory` receive wrong data, causing user transactions to be over- or under-priced.

---

### Likelihood Explanation

In **`none` governance mode** (any GC member may vote), two members acting independently — without any coordination or malicious intent — can produce this outcome simply by voting for their preferred bound values in the same epoch. Neither vote is individually invalid; the system provides no signal that the combination is harmful.

In **`single` governance mode** (Mainnet/Kairos), the governing node would have to cast both votes in the same epoch. This could happen accidentally when an operator intends to simultaneously tighten both bounds (e.g., raise the floor and lower the ceiling) without realising the epoch-snapshot check does not protect against the combined result.

---

### Recommendation

Add a cross-parameter check inside `VerifyGov` (or equivalently inside `getExpectedGovernance`) after the epoch's votes are aggregated, before the governance data is committed:

```go
// After aggregating prevEpochVotes into govs:
lower, hasLower := govs[gov.Kip71LowerBoundBaseFee]
upper, hasUpper := govs[gov.Kip71UpperBoundBaseFee]

effectiveLower := h.GetParamSet(blockNum).LowerBoundBaseFee
effectiveUpper := h.GetParamSet(blockNum).UpperBoundBaseFee

if hasLower { effectiveLower = lower.(uint64) }
if hasUpper { effectiveUpper = upper.(uint64) }

if effectiveLower > effectiveUpper {
    return ErrLowerBoundBaseFee  // or a new dedicated error
}
```

Alternatively, enforce the invariant at the epoch-block `VerifyGov` step so that a block containing a governance payload that violates `Lower ≤ Upper` is rejected by all nodes.

### Proof of Concept

**Setup**: governance mode `none`, epoch = 1000, current effective params `Lower=25 gwei`, `Upper=750 gwei`.

1. Block 100: GC member A calls `governance_vote("kip71.lowerboundbasefee", 500_000_000_000)`.
   - `checkConsistency`: `500e9 ≤ 750e9` (current upper) → accepted, written to `header.Vote`.

2. Block 200: GC member B calls `governance_vote("kip71.upperboundbasefee", 100_000_000_000)`.
   - `checkConsistency`: `100e9 ≥ 25e9` (current lower) → accepted, written to `header.Vote`.

3. Block 1000 (epoch boundary): proposer calls `getExpectedGovernance(1000)`, which aggregates both votes into `{Lower:500e9, Upper:100e9}` and writes it to `header.Governance`. `VerifyGov` confirms the data matches the expected aggregation — no cross-check — and the block is accepted by all nodes.

4. Block 1001 onward: `GetParamSet` returns `Lower=500e9`, `Upper=100e9`. Every call to `NextMagmaBlockBaseFee` clamps `parentBaseFee` to `100e9`, then:
   - low-gas blocks → returns `500e9` (lowerBound)
   - high-gas blocks → returns `100e9` (upperBound)

// The blockNum's epoch index must be greater than 0. That is, it must be blockNum >= epoch.
func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}

	makeEvenByCeil(lowerBoundBaseFee)

	var baseFeeDenominator *big.Int
	if kc.BaseFeeDenominator == 0 {
		// To avoid panic, set the fluctuation range small
		baseFeeDenominator = new(big.Int).SetUint64(64)

		parentBaseFee = upperBoundBaseFee
