### Title
Cross-repository Commit/Status webhook processing lets an attacker-signed status flip a victim stack's `ignore_ci` and inject fake CI state - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA globally, with no scoping to the repository that authenticated the webhook, then creates a `Status` on whatever commit(s) matched, which unconditionally calls `commit.stack.enable_ci!` via `Status#enable_ci_on_stack`. A signed status webhook for repo A can therefore mutate stack configuration and CI state belonging to an unrelated stack B whenever a commit SHA collision (including a benign one, e.g. via a fork sharing identical commit objects) occurs.

### Finding Description
The claimed binding is: `webhook.repository.full_name == stack.repository.full_name` for any state mutation triggered by that webhook. Tracing the code shows this binding is **not enforced**:

- `WebhooksController#verify_signature` validates the HMAC signature using `Shipit.github(organization: repository_owner)`, proving only that the payload was genuinely signed by GitHub for the *claimed* `repository_owner` in the payload — it says nothing about which `Stack`/`Commit` rows the handler is allowed to touch. [1](#0-0) 

- The base `Handler` class exposes a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. only stacks belonging to the repo that sent the webhook. [2](#0-1) 

- `StatusHandler#process`, however, **does not use this `stacks` scope at all**. It queries `Commit.where(sha: params.sha)` against the entire `commits` table, across all stacks/repositories, and calls `commit.create_status_from_github!(params)` on every match: [3](#0-2) 

- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` creates a `Status` row scoped to `commit.stack_id` (the victim's own stack, since `commit.stack_id` is fixed per commit), not the attacker's. [4](#0-3) [5](#0-4) 

- `Status` has `after_create :enable_ci_on_stack`, which unconditionally calls `commit.stack.enable_ci!` — no check that the creating webhook's repository matches `commit.stack.repository`: [6](#0-5) 

Because `sha` is a globally-indexed but repository-relative value (`add_index :commits, %i(sha stack_id), unique: true` — unique only per stack, not globally), the same SHA string can legitimately exist for multiple stacks, e.g. a forked public repository shares identical commit SHAs with its upstream since Git SHAs are content-addressed. An attacker who owns a fork of a victim's public repo (a stack the attacker controls, wired into the same Shipit GitHub App installation) can create/update a commit status via the GitHub Status API on a commit SHA that is shared with the victim's stack (inherited unmodified from the fork parent). GitHub signs and delivers that status webhook using the attacker's own repository's identity, passing `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema cleanly — none of these guards check cross-repository ownership of the target `Commit`/`Stack`. The handler then finds the victim's commit row (same SHA, different `stack_id`) and creates a `Status` on it, which flips `ignore_ci` off on the victim's stack and also fabricates arbitrary CI state (`success`/`failure`/`pending`) for that victim commit, affecting `Commit#deployable?` semantics for unrelated tenants.

### Impact Explanation
An attacker-controlled webhook mutates configuration (`Stack#ignore_ci`) and safety-relevant state (fabricated CI `Status` rows) belonging to a stack the attacker does not own and never authenticated for. This matches the "payload for one repository mutating another's stack/commit" Critical category: it can silently re-enable CI enforcement a victim operator deliberately disabled, or conversely inject fabricated success statuses on a victim's real commits, corrupting the `deployable?` decision used before deploys/merges. The bug is repeatable against any stack whose commits happen to share a SHA with an attacker-controlled repository (most straightforwardly, any fork of a public Shipit-tracked repo), so blast radius spans all tenants sharing the Shipit GitHub App installation.

### Likelihood Explanation
Preconditions: the attacker needs a repository (e.g., a fork of the victim's public repo) that is wired into the same Shipit deployment/GitHub App installation as a stack, so the webhook passes `Shipit.github(organization: repository_owner)` in `verify_signature`. Given that, no special privilege is needed beyond normal GitHub status-API access on their own repo/fork — no Shipit session, API token, or secret is required, satisfying the stated attacker model. Producing the exact shared SHA is trivial via forking (Git SHAs are content-addressed and identical across forks for unmodified commits), making this practically feasible rather than theoretical.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring the base `Handler#stacks` helper, e.g. restrict the `Commit` lookup to commits belonging to `stacks` (the repository that signed the webhook) before creating any `Status`, and/or make `Status#enable_ci_on_stack` a no-op unless the originating webhook's repository matches `commit.stack.repository`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or equivalent), add a minitest:
1. Create two stacks/repositories, `attacker_stack` (repository "attacker/fork") and `victim_stack` (repository "victim/repo", `ignore_ci: true`).
2. Create a `Commit` on `victim_stack` with `sha: "deadbeef...".
3. Create a `Commit` with the **same sha** but `stack_id: attacker_stack.id` (simulating the forked/shared commit).
4. Mock `Shipit.github` / signature verification to accept a payload where `repository.full_name == "attacker/fork"`.
5. Spy on `victim_stack` with `Mocha` for `:enable_ci!`.
6. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload_with_sha_and_state)`.
7. Assert `victim_stack.reload.ignore_ci` flips from `true` to `false`, and that `Shipit::Status.where(stack_id: victim_stack.id).exists?` is true — proving a webhook attributed to `attacker/fork` mutated `victim_stack`'s configuration and status history.
