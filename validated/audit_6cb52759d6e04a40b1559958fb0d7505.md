### Title
Webhook signature verification is scoped to `repository.owner.login`, but the event is dispatched against `repository.full_name` — allowing a valid signature from one GitHub organization to authorize writes against another organization's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports a multi-tenant GitHub App configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . The webhook signature is verified using the secret picked for `repository_owner` (derived from `repository.owner.login`, falling back to `organization.login`) [2](#0-1) [3](#0-2) . However, the actual event handlers (e.g. the push handler) look up the target `Repository`/`Stack` using `repository.full_name` from the same JSON body [4](#0-3) . Nothing ties `repository.full_name`'s owner segment to `repository.owner.login`/`organization.login` used for signature verification — they are independent, attacker-controlled fields in the same payload.

### Finding Description
`verify_signature` computes which `GitHubApp`/webhook secret to validate the HMAC against solely from `repository_owner`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization key in the multi-tenant config schema [1](#0-0) .

Once the signature check passes, `create` dispatches the entire parsed JSON body to the matched handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

Handlers resolve which stacks/repository to act on using `repository.full_name`, a separate field of the same body, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository/stack) are two independently attacker-supplied JSON fields in the same request body, and no code cross-checks that the owner segment of `full_name` matches `repository.owner.login`, an attacker who legitimately controls a webhook delivery for *their own* GitHub organization (and therefore knows/derives a signature that is valid for their own org's configured `webhook_secret`) can set `repository.full_name` to `"victim-org/victim-repo"` while keeping `repository.owner.login`/`organization.login` set to their own org. The signature is verified successfully against the attacker's own org secret, yet the handler acts on the victim organization's stack.

This is the exact class of bug described in the report: a value used for the trust/authentication decision (`repository_owner` → which secret verifies the signature) is not the same value that ends up being acted upon (`repository.full_name` → which repository/stack is mutated), breaking the equality `verified_owner == acted_upon_repository_owner` that the design implicitly assumes.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as a valid analog. Depending on which webhook event is routed:
- `push` events enqueue `GithubSyncJob` for the stack resolved from the spoofed `full_name`, `PushHandler` also updates `latest_deployed_ref`-related sync state for a repository the attacker does not own [4](#0-3) , listed as `Repository.from_github_repo_name(repository_name)&.stacks`.
- `status`/`check_suite`/`membership` handlers similarly key off the payload body's `repository`/`organization` sub-objects, letting an attacker with a valid signature from one tenant inject status/check/membership updates that affect a different tenant's stacks — an unauthorized write across repository/organization boundaries, satisfying the "cross-repository writes" Critical impact bucket, contingent on this Shipit instance being configured with the multi-organization GitHub App schema (`secrets.github` keyed by organization).

### Likelihood Explanation
This requires the deployment to use the multi-organization/multi-tenant GitHub App configuration (`Shipit.github(organization:)` with per-org `webhook_secret`s) rather than the single-app schema; single-app deployments (`github_default_organization` is `nil`) use one shared secret and are not affected by this specific owner/full_name split. Where multi-tenant config is used, the attacker only needs to control a GitHub organization/repo that is itself onboarded onto the same Shipit instance (a low bar for shared/multi-tenant Shipit installs), then send a forged webhook delivery with a mismatched `full_name` and a signature computed with their own known/legitimate webhook secret — no `ApiClient` token, session, or GitHub App private key is required.

### Recommendation
In `verify_signature`, derive `repository_owner` from the same field used later for repository resolution (or, conversely, make `repository_name`/`stacks` lookups also verify that the owner segment of `repository.full_name` matches the verified `repository_owner`) before dispatching to handlers. E.g., after verifying the signature, assert:
```ruby
repo_owner_from_full_name = params.dig('repository', 'full_name')&.split('/')&.first
head(422) and return unless repo_owner_from_full_name == repository_owner
```

### Proof of Concept
1. Configure Shipit with multi-tenant GitHub App config: `secrets.github = { "attacker-org" => { webhook_secret: "secretA", ... }, "victim-org" => { webhook_secret: "secretB", ... } }`.
2. Attacker (who legitimately owns `attacker-org` and its webhook secret `secretA`) crafts a push payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "after": "<attacker-controlled sha>"
}
```
3. Attacker computes `X-Hub-Signature` using `secretA` (their own legitimate secret) over this raw body.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and verifies the signature successfully against `secretA` [2](#0-1) .
5. `create` then dispatches the same payload to `PushHandler`, which resolves stacks via `repository.full_name == "victim-org/victim-repo"` [4](#0-3) , enqueuing sync/state changes for a repository the attacker does not control and never proved knowledge of `secretB` for.

Note: I was unable to directly inspect `app/models/shipit/webhooks/handlers/push_handler.rb`'s full contents in this pass (only confirmed its existence and the shared base `Handler#stacks`/`repository_name` logic), so the exact downstream side effects of `PushHandler` beyond `GithubSyncJob` enqueuing could not be fully enumerated. If a full audit of `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, and `membership_handler.rb` is desired to confirm concrete write operations, that would require further reading, ideally in a full Devin session with complete file access.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
