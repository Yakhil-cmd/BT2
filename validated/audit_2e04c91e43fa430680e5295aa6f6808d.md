### Title
Webhook signature scoping uses attacker-controlled `repository.owner.login` while event handlers act on the attacker-controlled `repository.full_name` - cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using a field taken directly from the unauthenticated, attacker-supplied JSON body (`repository.owner.login` / `organization.login`), rather than from any value that was itself verified. The event handlers that subsequently act on the payload identify the target repository/stack using other attacker-supplied fields in the same body (e.g. `repository.full_name`). Because the field used to pick the *verification key* and the field used to pick the *acted-upon resource* are two different, independently attacker-controlled parts of the same unverified JSON, the two are never bound together by the signature check.

### Finding Description [1](#0-0) 

`create` parses the raw JSON body and dispatches it, unmodified, to registered handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
`verify_signature` derives the organization used to fetch the webhook-verification config purely from the body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization: repository_owner)` looks up the corresponding `Shipit::GithubApp` and its `webhook_secret` for verification (`lib/shipit/github_app.rb#verify_webhook_signature`). Critically, `verify_webhook_signature` returns `true` immediately whenever no `webhook_secret` is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
This "authenticates" the organization named in `repository.owner.login`, but does not bind that organization to any other field of the payload. Downstream handlers (e.g. push/status/check_suite handlers) resolve the actual repository/stack to operate on from other body fields such as `repository.full_name`, independent of `repository.owner.login`.

The trust binding the report's `swap_2` bug class targets is: *the entity whose credential/config was verified* must equal *the entity the code subsequently acts on*. Here:
- Verified side: `repository_owner = params.dig('repository','owner','login')`
- Acted-upon side: repository/stack resolved by handlers from `params['repository']['full_name']` (and other body fields)

Since both sides come from the same attacker-controlled, unsigned JSON body, and are never cross-checked against each other, an attacker can supply `repository.owner.login` = an organization with no `webhook_secret` configured (or one whose secret they otherwise know/can compute), while setting `repository.full_name` (and other repo-identifying fields consumed by the handler) to point at a completely unrelated stack/repository configured in the same Shipit instance.

### Impact Explanation
If any organization on the instance is configured without a `webhook_secret` (a documented, valid configuration - see `config/secrets.development.shopify.yml` and `docs/setup.md`, where `webhook_secret` is optional/nilable), signature verification is fully bypassed for a payload merely *claiming* to belong to that organization, while the actual data acted upon (e.g. push ref/sha, status state, check_suite results) can name a different organization's/repository's stack. This lets an unauthenticated, unprivileged attacker inject or forge webhook events (e.g. push events driving `GithubSyncJob`, status events fabricating CI state, check_suite events) against a stack they do not control, without needing a Shipit session, API token, or GitHub credentials of the target repository's owner - only network access to the public webhooks endpoint. Depending on which handler fires, this can move the head SHA Shipit tracks for a stack, mark statuses, or manipulate check-suite state, ultimately influencing the commit set Shipit considers "ready" for deployment.

### Likelihood Explanation
Any multi-organization Shipit deployment (explicitly documented and supported, per `docs/setup.md` "Using Multiple Github Applications") where at least one configured organization has no `webhook_secret` (also an explicitly supported/documented state) is exploitable by anyone able to POST to the public `/webhooks` endpoint - no credentials required. This does not depend on the host application deviating from documented mounting/configuration.

### Recommendation
Bind signature verification to the same identity that handlers act on: verify the signature using the webhook secret associated with the actual target repository (looked up via the already-persisted `Repository`/`Stack` record, not a bare string pulled from the unauthenticated body), and reject payloads where the declared `repository.owner.login`/`organization.login` does not match the owner of the repository identified by `repository.full_name`. Additionally, do not treat a missing `webhook_secret` as an automatic "verified" pass-through for organizations that share an installation with other, secured organizations; require an explicit secret for any organization that is expected to receive webhooks affecting other tenants' stacks.

### Proof of Concept
1. Configure two organizations in `secrets.yml` under `github:` — `org-open` (no `webhook_secret`, per the documented optional field) and `org-target` (has a stack/repository configured, e.g. `org-target/app`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and JSON body:
```json
{
  "repository": {
    "owner": { "login": "org-open" },
    "full_name": "org-target/app"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` computes `repository_owner = "org-open"`, fetches `Shipit.github(organization: "org-open")`, whose `webhook_secret` is `nil`, causing `verify_webhook_signature` to return `true` regardless of the (missing/garbage) `X-Hub-Signature` header (`lib/shipit/github_app.rb`, `return true unless webhook_secret`).
4. `PushHandler` (or other handler) then processes the payload using `repository.full_name = "org-target/app"`, acting on the `org-target` stack despite the signature check never having involved `org-target`'s configuration or secret at all — [2](#0-1) . [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
