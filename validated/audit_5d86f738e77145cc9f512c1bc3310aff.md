### Title
Stack-scoped API token authorization bypass in CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`ApiClient#stack_id`) can only ever resolve the `stack` it was authorized for. `Shipit::Api::CCMenuController` — which extends `BaseController` — overrides the `stack` accessor with an unscoped lookup, silently dropping that authorization binding. Any valid, stack-scoped API token can therefore be used to read the CI/deploy status ("stack state") of an arbitrary other stack simply by changing the `stack_id` path/query parameter.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting resolution of a stack for a request: [1](#0-0) 

`current_api_client.stack_id?` gates whether the client is restricted to a single `Stack`; `stacks.from_param!` then raises unless the requested stack is inside that authorized scope. The fixture `here_come_the_walrus` demonstrates this exact scoping model in the schema/tests: [2](#0-1) 

`CCMenuController`, however, redefines `stack` to bypass that scope entirely and only checks the permission label (`read:stack`), not which stack the token is bound to: [3](#0-2) 

It also overrides `authenticate_api_client` to accept the token via a plain query-string parameter (`params[:token]`) rather than the standard Basic-Auth header used elsewhere, making the attack trivially reachable with a GET request: [4](#0-3) 

The `require_permission :read, :stack` before_action only calls `ApiClient#check_permissions!`, which checks the `permissions` array, never the `stack_id` scope: [5](#0-4) 

**Binding broken (equality):** `current_api_client.stack_id (the stack the token authorizes)` should equal `stack.id (the stack the request actually touches)` for every request served by an `ApiClient`. `CCMenuController#stack` violates this by resolving `Stack.from_param!(params[:stack_id])` unconditionally, independent of `current_api_client.stack_id`.

### Impact Explanation
An attacker who obtains (or is legitimately issued) an `ApiClient` token scoped to a single, low-sensitivity stack (e.g., via `CCMenuUrlController#fetch`, which mints a `read:stack` token, or any admin-provisioned stack-scoped client) can use that same token to query `/api/stacks/:stack_id/cc_menu` (see `config/routes.rb` ccmenu route) for any other stack in the Shipit instance, disclosing that stack's build/deploy status, last build label/time, and web URL. This is an unauthorized cross-stack read of deploy/task state that the token was never granted — matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-severity class, since the scoping mechanism that is supposed to gate this access is defeated by the controller override.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the data model and tests explicitly support and expect this scoping), since exploitation requires only a valid token with `read:stack` permission plus manipulating a single request parameter — no additional privilege, secret, or session is needed beyond the token itself, which the caller is expected to already legitimately hold for the *one* stack it was issued for.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited, scope-respecting `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so that the `current_api_client.stack_id` binding is enforced consistently across all API controllers.

### Proof of Concept
1. Obtain (or have issued) an `ApiClient` token scoped to `stack_id = A` with `read:stack` permission (e.g., via `CCMenuUrlController#fetch` for stack A, or a console-provisioned scoped client as in the `here_come_the_walrus` fixture).
2. Send `GET /api/stacks/B/cc_menu?token=<token-for-A>` where `B` is any other stack in the instance.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing the `current_api_client.stack_id` scoping used everywhere else in `Api::BaseController`), the request succeeds and returns stack `B`'s CI/deploy status, even though the token was only authorized for stack `A`.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
