## Analog Found

### Title
Unchecked `creator` address in `initialize_with_permission` permanently freezes creator trading fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
The original report flags missing `require(_ != address(0))` checks on constructor address parameters in `StrategyCurveSCRVv4_1`/`StrategyBase`, which are later used unguarded in transfer/approve authority operations. The same class of defect exists in `initialize_with_permission`: the pool's `creator` `Pubkey` is accepted from the caller without any non-default/ownership check and is later relied upon as a signer/authority for fee withdrawal.

### Finding Description
In `InitializeWithPermission`, `creator` is declared only as an `UncheckedAccount<'info>` with a `CHECK: creator of pool` comment and no `address`, `constraint`, or zero-check validation: [1](#0-0) 

The unchecked value is stored directly into `pool_state.pool_creator` via `PoolState::initialize`: [2](#0-1) [3](#0-2) 

Downstream, `collect_creator_fee` requires the `creator` account to be a `Signer` whose key equals `pool_state.pool_creator`, and `collect_creator_fee_permissionless` uses that same stored pubkey as the `associated_token::authority` of the ATA that receives the fees: [4](#0-3) [5](#0-4) 

If `pool_creator` is set to `Pubkey::default()` (or any address for which no private key exists), no one can ever satisfy the `Signer` constraint in `collect_creator_fee`, and the permissionless path only ever creates/pays into an ATA whose authority (`creator`) can never sign a transfer out — the accrued creator fees become permanently unspendable.

The codebase's own admin-path fix in `update_config.rs` shows the team is aware of exactly this hazard for `Pubkey` fields, adding `require_keys_neq!(new_owner, Pubkey::default())` when setting `protocol_owner`/`fund_owner`, but the equivalent guard is missing for `creator` in `initialize_with_permission.rs`: [6](#0-5) 

Note that trading fees continue to be split into `creator_fees_token_0/1` and are excluded from the redeemable vault balance used by `vault_amount_without_fee` (used for withdraw ratio/liquidity accounting), so once frozen, this portion of the vault balance is permanently locked and unrecoverable by anyone, including LPs: [7](#0-6) 

### Impact Explanation
Creator fees accrued on every swap for a pool created with `creator = Pubkey::default()` (or any keyless address) become permanently frozen in the pool's vaults — no signer can ever pass the `address = pool_state.pool_creator` constraint in `collect_creator_fee`, and `collect_creator_fee_permissionless` can only route the funds into an ATA controlled by an address nobody can sign for. This is a permanent freezing of protocol/user fee funds inside the vault.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding a valid `permission` PDA (an unprivileged-but-permissioned pool creator), who fully controls the `creator` account passed into the instruction, since it is only an `UncheckedAccount` with no signer or zero-check requirement. Setting it to `Pubkey::default()` requires no special privilege beyond calling the instruction with attacker-chosen accounts, matching a single-transaction, attacker-controlled-accounts scenario.

### Recommendation
Add an explicit non-default check on `creator` in `InitializeWithPermission`, e.g. `require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default())` before calling `pool_state.initialize(...)`, mirroring the `require_keys_neq!` guards already used for `protocol_owner`/`fund_owner` in `update_config.rs`. Consider also validating that `creator` is not a program-owned/non-signable address more generally.

### Proof of Concept
1. Obtain a `permission` PDA for `payer` (via `create_permission_pda`, which is a legitimate but unprivileged path once granted).
2. Call `initialize_with_permission` supplying `creator = Pubkey::default()` (system program ID / all-zero pubkey) as the `creator` account — no signature is required for this account since it's an `UncheckedAccount`.
3. Perform swaps against the pool so that `creator_fee_on`/`enable_creator_fee` causes `creator_fees_token_0`/`creator_fees_token_1` to accrue in `pool_state`.
4. Attempt `collect_creator_fee`: fails permanently because no keypair exists that can sign as `Pubkey::default()` to satisfy the `Signer` + `address` constraint on `creator`.
5. Attempt `collect_creator_fee_permissionless`: succeeds in moving tokens out of the vault, but only into an ATA whose authority is `Pubkey::default()`, from which the tokens can never be moved again — funds are permanently frozen.
