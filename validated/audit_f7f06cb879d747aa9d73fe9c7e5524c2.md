### Title
`Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler#unarchive?` re-provisions review stacks even when `review_stacks_enabled == false` due to operator precedence - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`unarchive?` in `ReopenedHandler` is written as `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` is only ANDed into the `allow_all?` clause, not the `allow_with_label?`/`prevent_with_label?` clauses, so a repository with review stacks explicitly disabled can still have its stack unarchived/re-created via the label-gated branches.

### Finding Description
The intended binding is `review_stacks_enabled == (the single gate applied to every provisioning-behavior branch)`. The actual code: [1](#0-0) 

parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `review_stacks_enabled == false` and `provisioning_behavior == "allow_with_label"` with the configured label present on the pull request, `unarchive?` still returns `true`.

`process` calls `respond_to_pull_request_reopened?`, which is `params.action == "reopened" && unarchive?`, with no other gate on `review_stacks_enabled`: [2](#0-1) 

If it passes, `stack.unarchive!` is invoked on a `ReviewStackAdapter`, which creates the stack if none exists or unarchives and re-enqueues it for provisioning if archived: [3](#0-2) [4](#0-3) 

Exploit flow: on a repository configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` (with a configured label), an attacker (per the stated threat model, capable of opening a PR from a fork and labeling their own PR) opens a PR, attaches the provisioning label, then closes and reopens it (or simply reopens a previously closed PR). GitHub sends a validly-signed `reopened` webhook for the real repository event; no forged signature is needed. `unarchive?` evaluates true despite `review_stacks_enabled == false`, causing `ReviewStackAdapter#unarchive!`/`create!` to run, which enqueues the stack for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)`, ultimately triggering provisioning task execution for a repository whose operator explicitly disabled this feature.

No other guard intervenes: `respond_to_pull_request_reopened?` only checks the action string and `unarchive?`; there is no separate top-level `review_stacks_enabled` check wrapping the whole method the way it's textually intended to.

### Impact Explanation
The attacker causes stack creation/re-provisioning and command/task execution (provisioning queue processing) for a repository whose maintainer intentionally disabled review stacks (`review_stacks_enabled == false`). This is a policy/authorization bypass leading to unauthorized provisioning workflow execution scoped to that one repository — matching the "Critical: unauthorized deploy/rollback... a payload... mutating another's stack" category, since it forces state changes (`ReviewStack` creation/unarchival, provisioning queue enqueue) that the operator's configuration was meant to prevent. The blast radius is limited to repositories that have this specific, non-default configuration combination (`review_stacks_enabled=false` + `provisioning_behavior=allow_with_label`), but is repeatable on every reopen event against such a repository.

### Likelihood Explanation
Requires a repository configured with `review_stacks_enabled == false` and `provisioning_behavior == allow_with_label` (or `prevent_with_label`) with a label configured — this is a plausible but non-default operator configuration (explicitly disabling review stacks while retaining label config). Given that configuration, the attacker cost is low: open a fork PR, apply the label per the stated threat model, and close/reopen it. The event is a legitimate GitHub webhook, so signature verification is not an obstacle. The bug is deterministic and repeatable for every such repository.

### Recommendation
Fix the operator precedence by explicitly grouping the `review_stacks_enabled` check around the entire disjunction, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to `OpenedHandler#provision?`, which has the identical defect.

### Proof of Concept
minitest in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`:
```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with allow_with_label and label present" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Before the fix, this assertion fails because `unarchive?` returns `true` and the stack is unarchived/re-enqueued for provisioning despite `review_stacks_enabled == false`; after applying the recommended fix, the stack correctly remains archived.
