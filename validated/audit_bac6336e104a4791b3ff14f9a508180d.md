Based on my analysis, the Shipit multi-organization webhook flow contains an analog of the bug class: an unverified payload field (`repository.owner.login` / `organization.login`) selects the GitHub App configuration whose secret is used to verify the request's own signature — the selector is trusted before the check it feeds into has actually authenticated anything.

### Title
Attacker-chosen `repository_owner` selects which org's webhook secret authenticates the request, enabling cross-organization webhook spoofing when any configured org has no secret set - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` derives `repository_owner` directly from the unauthenticated JSON body, and uses it to pick a `Shipit::GitHubApp` instance whose `webhook_secret` is then used to verify `X-Hub-Signature`. If that particular organization's config in `secrets.github` has no `webhook_secret` set, verification is unconditionally treated as successful, exactly like the `adminSettleDebt`/`adminSettleDebtLockPeriodEnd` bug where a zero/unset "not yet initiated" value causes a security gate to be bypassed.

### Finding Description
The controller pipeline is: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params`, which come from `request.raw_post` — i.e., attacker-controlled, unauthenticated content — before any signature check has occurred. This value is passed to `Shipit.github(organization:)`, which resolves per-organization config via `github_app_config`: [3](#0-2) 

The resulting `GitHubApp`'s `verify_webhook_signature` is then used to validate the very same request whose organization field picked it: [4](#0-3) 

Critically, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that organization's config (`return true unless webhook_secret`). Because the organization selector itself is taken from the unverified payload, an attacker can craft a webhook body claiming to be for *any* organization known to the Shipit instance's `secrets.github` multi-org map. If even one configured organization omits `webhook_secret` (a valid, non-malicious admin oversight — analogous to `adminSettleDebtLockPeriodEnd` defaulting to `0` because `initiatingAdminSettleDebt` was never called), the check binds a payload field (`repository_owner`) that is never itself covered by any verified signature to the security decision of "was this webhook authentic," breaking the intended binding of *GitHub-authenticated organization* == *organization whose secret verifies the request*.

### Impact Explanation
If exploited against an organization with a missing/blank `webhook_secret`, an attacker can forge `push`, `commit_status`, `deployable_status`, `merge_status`, or `membership` webhook events with `repository.owner.login`/`organization.login` set to that organization. This lets an unauthenticated party inject data that drives `GithubSyncJob`, commit statuses, and team/membership synchronization — an authentication bypass on a security-relevant control gate (`verify_signature`) that the engine's own `before_action` chain is supposed to enforce for every organization uniformly.

### Likelihood Explanation
Low-to-moderate: it requires that the deploying operator configured multiple GitHub organizations under `secrets.github` (the multi-org schema keyed by org name) and that at least one of those organizations was left with a blank `webhook_secret`, whether accidentally or during initial setup/migration. This mirrors the report's "Low likelihood, admin-driven, accidental-config" profile rather than requiring any credential theft.

### Recommendation
Do not let an unauthenticated/unverified field select which secret authorizes the very request carrying that field. Either: (1) require `webhook_secret` to be present for every organization entry validated at boot/config-load time (fail closed instead of defaulting to `true`), or (2) verify the signature against all configured organizations' secrets and only then trust the claimed `repository_owner`, rather than using the claimed owner to pick the verifier.

### Proof of Concept
1. Configure `secrets.github` with two organizations, e.g. `orgA: { webhook_secret: "s3cr3t", ... }` and `orgB: { app_id: ..., installation_id: ... }` (no `webhook_secret` key).
2. Send `POST /webhooks` with `X-Github-Event: push` and a body where `repository.owner.login` = `"orgB"`, with any/garbage `X-Hub-Signature` header (or omit it).
3. `repository_owner` resolves to `"orgB"`; `Shipit.github(organization: "orgB")` builds a `GitHubApp` with `webhook_secret` nil; `verify_webhook_signature` returns `true` unconditionally at [5](#0-4) , and the forged event is processed as if it came from GitHub.

**Uncertainty**: I could not verify from the indexed code whether Shipit enforces a validation step at boot/deploy time that would reject a `secrets.github` multi-org config missing `webhook_secret` for any entry — this was not found in `lib/shipit.rb` or `lib/shipit/github_app.rb`, but a full check would require inspecting the engine's initializer/config validation code, which may not be fully indexed. If the user needs certainty about whether such a boot-time validation exists elsewhere in the app, I'd suggest starting a Devin session to search the complete codebase.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
