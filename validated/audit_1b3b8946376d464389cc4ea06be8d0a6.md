### Title
Autonomous Agents accept fixed-denomination (indivisible/NFT-like) asset deposits but can never send them back out, permanently freezing the funds - ([File: aa_composer.js])

### Summary
An AA can receive and account for `fixed_denominations` (indivisible, NFT-like) assets in its balance the same way it accepts base bytes or divisible assets, but `sendUnit()` unconditionally strips out any outgoing payment message that references such an asset before composing the response unit. There is no code path anywhere in `aa_composer.js` that allows an AA to actually transfer a `fixed_denominations` asset it holds, so any indivisible asset sent to an AA address is permanently locked in that AA's balance with no way for the AA (or anyone) to move it out.

### Finding Description
When a unit pays an AA, `getTrigger()` records the received amount per asset in `trigger.outputs`, including assets whose `fixed_denominations` flag is set (there is no filtering at trigger-collection time): [1](#0-0) 

`updateInitialAABalances()` then credits `trigger.outputs[asset]` into the AA's `aa_balances` table / `assocBalances` unconditionally, again with no special handling or rejection of indivisible assets — the AA's balance in that asset increases just like for any other asset: [2](#0-1) 

However, when the AA tries to actually construct outgoing payment messages in `sendUnit()`, any message whose asset `objAsset.fixed_denominations` is true is explicitly deferred with the comment "will skip it later": [3](#0-2) 

And on the very next pass, all such messages are filtered out of the response unit entirely: [4](#0-3) 

So no matter what the AA's oscript logic instructs (e.g. "forward the deposited NFT/indivisible asset to X"), the payment message for that asset is silently dropped before the unit is built. The AA has no other mechanism to move `fixed_denominations` assets: `completePaymentPayload()`/`pickIndivisibleCoinsForAmount()`-style indivisible-coin selection (used by regular wallets in `indivisible_asset.js`) is never invoked from the AA composer, and private/fixed-denomination assets are also explicitly rejected earlier if private (`"sending private asset from AA"`), leaving public fixed-denomination assets as accepted-but-unspendable AA balances.

This is directly analogous to the reported `OngoingBountyV1` issue: the contract happily accepts NFT deposits via `fundBountyNFT`, tracks them, but the claim/distribution code path (`_claimOngoingBounty`) has no logic to move NFTs out, so deposited NFTs are permanently stuck. In ocore, any AA is the "OngoingBountyV1" and any indivisible/fixed-denomination asset is the "NFT": accepted as a balance, but with no way for the AA to output it.

### Impact Explanation
Any AA that is supposed to hold, escrow, forward, refund, or distribute an indivisible/NFT-like asset (`fixed_denominations: true`) will permanently freeze those funds once deposited, because the AA composer silently discards any payment message attempting to send that asset back out. This is a direct, systemic AA fund loss/freezing bug: user or third-party deposits of such assets into any AA (bounty/escrow AAs, marketplaces, auctions, DEX-like AAs, oracles rewarding NFTs, etc.) become permanently unspendable by anyone, with no bounce, no error surfaced to the depositor, and no recovery mechanism, satisfying the "AA fund loss or freezing" impact criterion.

### Likelihood Explanation
Likelihood is high for any AA author who is unaware of this limitation and designs an AA to accept and later distribute an indivisible/fixed-denomination public asset — a completely reasonable, unprivileged usage pattern (e.g., NFT escrow, NFT-based bounty, ticketing/voucher AA). Any ordinary unit poster can trigger the deposit path simply by sending a payment with a `fixed_denominations` asset to the AA address; no special privileges are required to reach the vulnerable `sendUnit()` code path.

### Recommendation
Either (a) reject/bounce triggers that deposit `fixed_denominations` assets to an AA at trigger-acceptance time (in `getTrigger()`/`updateInitialAABalances()`), refunding the sender instead of silently absorbing the balance, or (b) implement genuine indivisible-asset composition support in `sendUnit()` (mirroring the coin-selection/denomination-matching logic used in `indivisible_asset.js`'s `pickIndivisibleCoinsForAmount`) so that AAs can actually output `fixed_denominations` assets they hold, rather than filtering the outgoing messages away in [5](#0-4) .

### Proof of Concept
1. Issue a `fixed_denominations` (indivisible) public asset `X` (e.g. an NFT-like collectible with `cap`/denominations), not private, not `issued_by_definer_only`-restricted to exclude third parties.
2. Deploy an AA whose oscript, upon receiving asset `X`, attempts to forward it to `trigger.address`:
```
messages: [{
  app: 'payment',
  payload: { asset: '<X_unit>', outputs: [{ address: "{trigger.address}", amount: "{trigger.output[[asset=<X_unit>]]}" }] }
}]
```
3. Send a unit paying `bytes` (to cover bounce fees) plus an output of asset `X` to the AA address as a primary trigger.
4. Observe: `updateInitialAABalances()` credits the AA's `aa_balances` row for asset `X`; `handleTrigger` evaluates the AA formula and builds the intended payment message for asset `X`, but in `sendUnit()`, at [6](#0-5)  the message is deferred, and at [5](#0-4)  it is filtered out entirely — the response unit contains no payment of asset `X` to anyone.
5. The AA's `aa_balances` for asset `X` remains permanently at the deposited amount; no oscript logic and no manual transaction (since only the AA itself owns those outputs) can ever move it out.
