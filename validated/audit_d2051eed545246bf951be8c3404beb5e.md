### Title
ERC20Transactor trusts arbitrary `transfer()` return value without verifying actual balance change, allowing fee-on-transfer/malicious ERC20 tokens to over-credit XCM holding - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move ERC20 tokens by calling the contract's Solidity `transfer()` function and trust the boolean return value as proof that exactly `amount` was moved, exactly the fee-on-transfer accounting flaw described in the source report (crediting shares/holding by the requested amount instead of the amount actually received). Since any user can permissionlessly deploy an arbitrary `pallet-revive` contract implementing `IERC20`, an attacker fully controls what `transfer()` actually does while still returning `true`, decoupling the XCM `AssetsInHolding` credit from real token movement in the shared `TransfersCheckingAccount`.

### Finding Description
`ERC20Transactor` is wired into asset-hub-westend's production `AssetTransactors` tuple: [1](#0-0) , using `ERC20Matcher`, which matches any local `AccountKey20` location as a valid fungible asset regardless of what code is actually deployed there: [2](#0-1) .

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` from the user to a shared `TransfersCheckingAccount`, and on any `true` return value it unconditionally mints an `Erc20Credit(amount)` into the XCM holding register using the *requested* `amount`, never checking the checking account's actual balance delta: [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` transfers the same nominal `amount` out of the checking account to the beneficiary, again trusting the boolean result rather than measuring real balance movement: [4](#0-3) 

Because `bare_call` invokes attacker-deployed bytecode (pallet-revive contract deployment is permissionless), the attacker's `transfer()` implementation can:
- apply a deflationary/fee-on-transfer burn while returning `true`, or
- move `0` (or any amount less than `value`) while returning `true`.

The transactor has no invariant check (e.g., comparing `balanceOf(checking_account)` before/after) analogous to the report's recommended fix ("check the actual balance difference ... before and after the token transfer"). This mirrors exactly the vulnerable pattern in `SemiFungibleVault.deposit()`, which minted shares equal to the nominal `assets` parameter instead of the actually-received balance delta.

### Impact Explanation
The `TransfersCheckingAccount` is a single shared account per ERC20 contract, used across every user's XCM interactions with that asset. Because credits are minted by nominal `amount` and not real balance movement, the checking account's real ERC20 balance can fall behind the sum of nominal credits recorded in various XCM programs over time (structurally identical to the report's "last withdrawer cannot withdraw" scenario), and — more seriously — this over-crediting occurs inside the XCM Holding register, which is the same register used to construct `ReserveAssetDeposited`/derivative-minting instructions when reserve-transferring this asset to other chains. If a destination chain trusts asset-hub-westend as a reserve for this `AccountKey20` asset and mints a 1:1-backed derivative there based on the nominal amount reported by the XCM message, this can result in unbacked issuance on the destination chain, backed by fewer real ERC20 tokens than believed to sit in the checking account. This is a Medium-to-potentially-higher severity accounting/integrity issue depending on downstream reserve trust configuration, which I was **not able to fully verify** within the available iterations — specifically, I could not confirm from the indexed code whether any production sibling-parachain runtime currently configures `IsReserve`/`TrustedReserves` to trust asset-hub-westend as reserve for arbitrary local `AccountKey20` ERC20 locations and mint a corresponding derivative asset. Without that confirmation, the demonstrable/local impact is limited to (a) permanent accounting drift in the shared checking account per malicious ERC20 contract, and (b) potential DoS/fund-stranding for other holders of the same malicious token who use XCM operations (deposit failures once the checking account's real balance falls short of the nominal amount recorded for a pending `DepositAsset`).

### Likelihood Explanation
High likelihood of triggering the underlying condition: no privileged role is required. Any signed account can (1) deploy an arbitrary contract via `pallet-revive` implementing `IERC20` with a fee-on-transfer/deflationary `transfer()`, and (2) reference that contract's address as an `AccountKey20` location in a `pallet-xcm` `execute`/`transfer_assets` call to invoke `WithdrawAsset`/`DepositAsset` against `ERC20Transactor`. This requires no relayer/collator/validator collusion and no governance action — only the transactor being reachable via the `AssetTransactors` tuple, which it is on asset-hub-westend. What remains **unverified** is whether/how a second chain's reserve trust configuration would compound this into unbacked cross-chain issuance versus a self-contained accounting/DoS issue confined to the malicious contract's own checking-account balance.

### Recommendation
Before minting `Erc20Credit(amount)` in `withdraw_asset_with_surplus`, and before releasing the credited amount to beneficiaries in `deposit_asset_with_surplus`, measure the checking account's (or beneficiary's) real ERC20 `balanceOf` before and after the `transfer()` call and use the observed delta — not the requested `amount` — to construct/settle the `AssetsInHolding` credit, mirroring the report's recommendation for `SemiFungibleVault`. Alternatively/additionally, restrict `ERC20Matcher` (or add a gate at the `IsReserve`/asset-registration layer) to only allow XCM-registered/allow-listed ERC20 contracts that have been vetted as standard-conformant (non-deflationary, no fee-on-transfer), rather than accepting any deployed `AccountKey20` contract implicitly.

### Proof of Concept
I was unable to execute a runtime integration test within this session (no code-execution/terminal access; this is a read-only investigation). No live PoC was run and none should be inferred. The concrete reproduction that a Devin agent with repository/test-execution access should perform:
1. In `pallet-revive-fixtures` or a Solidity-compiled fixture, implement an `IERC20`-conformant contract whose `transfer(to, value)` burns/withholds a percentage of `value` (or transfers `0`) but always returns `true`.
2. Deploy it via `pallet_revive::Pallet::<Runtime>::bare_instantiate` in an asset-hub-westend integration test, deriving its `H160` address.
3. Fund a test account with the malicious token's full nominal balance in the contract's own storage.
4. Execute a `pallet_xcm::execute` (or emulated-network `LocalReserve`/`Teleport`-style) XCM program: `WithdrawAsset` of the malicious `AccountKey20` asset for `amount`, then assert:
   - the resulting `AssetsInHolding` reports `amount` (nominal), while
   - `IERC20::balanceOf(checking_account)` increased by less than `amount` (i.e., verify the actual on-chain balance delta via `bare_call` to `balanceOf`).
5. Follow with `DepositAsset` back to a beneficiary for the full nominal `amount` and observe either (a) the deposit succeeding despite the checking account being short (draining balance meant for other users of the same token), or (b) the deposit failing/reverting once accumulated shortfall exceeds available real balance, demonstrating the DoS/fund-stranding pattern.

Given no test was run, this must be reported as an analog requiring confirmation via the above reproduction, and the cross-chain unbacked-issuance escalation specifically requires further verification of a concrete trusting sibling-chain reserve configuration, which was not established from the indexed code available to me.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
