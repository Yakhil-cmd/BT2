### Title
Cross-tenant `check_suite` webhook forgery — signature verified against `repository.owner.login` while stack lookup uses independently-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization used for HMAC verification from `params.dig('repository','owner','login')`, while `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the target repository from the independent field `payload.dig('repository','full_name')`. Because these two fields are never cross-checked against each other, an attacker who owns "Org-Evil" can sign a webhook body with their own legitimate webhook secret while pointing `repository.full_name` at a completely different, victim-owned repository.

### Finding Description
The broken binding is: **organization verifying signature** (`repository_owner` = `params.dig('repository','owner','login')`, checked in [1](#0-0) ) **==** **organization owning the repository the handler acts on** (`repository_name` = `payload.dig('repository','full_name')`, used in [2](#0-1) ).

These are two separate, independently-settable JSON keys inside the same raw POST body. Nothing in `verify_signature` [3](#0-2)  or in `Handler#initialize`/`#stacks` [4](#0-3)  asserts that `full_name` is prefixed by `owner.login`, or that both resolve to the same GitHub organization.

Attack flow:
1. Attacker owns "Org-Evil" and configures/knows its Shipit webhook secret (a legitimate action for their own org).
2. Attacker crafts a `check_suite` JSON payload where `repository.owner.login = "Org-Evil"` and `repository.full_name = "Org-Victim/tracked-repo"`, with `check_suite.head_branch` and `check_suite.head_sha` matching a real branch/commit tracked by a stack under `Org-Victim/tracked-repo`.
3. Attacker computes `X-Hub-Signature` using Org-Evil's real webhook secret over this crafted body and POSTs it to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "Org-Evil")` and successfully verifies the signature against Org-Evil's own secret — passes.
5. `CheckSuiteHandler#process` calls `Handler#stacks`, which resolves `Repository.from_github_repo_name("Org-Victim/tracked-repo")` — an entirely different, victim-owned record — and finds the stack tracking the given branch, matching the given commit sha, and calls `stack.commits...each(&:schedule_refresh_check_runs!)` [5](#0-4) , enqueuing `RefreshCheckRunsJob` for Org-Victim's commit.

Existing guards fail because: `verify_signature` only proves the request body was signed by *someone with a known org's secret*; it never proves that the *repository named in the payload* belongs to that same signing org. There is no format validation coupling `repository.owner.login` and `repository.full_name` anywhere in this code path.

### Impact Explanation
This lets Org-Evil trigger `stack.github_api.check_runs`-style read/refresh calls against Org-Victim's stack, using Org-Victim's own GitHub App credentials, without Org-Evil ever needing access to Org-Victim's repo or webhook secret. No credentials leak to the attacker, but it is unauthorized cross-tenant job scheduling/read-refresh triggered purely by controlling one's own org's webhook signature — matching the "payload for one repository mutating another's stack/commit" Critical category, bounded here to a read/refresh action (`RefreshCheckRunsJob`) rather than a deploy/rollback/merge. The attack is fully repeatable against any stack/branch/commit combination the attacker can guess or observe (branch names and commit SHAs are often public), and against any Org-Victim repository whose full_name the attacker knows.

### Likelihood Explanation
Preconditions: attacker must own (or control) any organization/repo configured in Shipit with its own valid webhook secret — a normal, unprivileged position for a legitimate Shipit customer/org owner, not requiring compromise of Org-Victim's secrets. Attacker needs to know Org-Victim's repository `full_name` (public) and a tracked branch/commit sha (often discoverable via public GitHub data or Shipit's own public UI). Cost is a single crafted HTTP POST; fully repeatable and scriptable.

### Recommendation
In `Handler#repository_name` (or centrally before dispatching to handlers), validate that `payload.dig('repository','full_name')` begins with `payload.dig('repository','owner','login') + '/'`, or better, derive the org actually used for `Shipit.github(organization: ...)` verification from the same `full_name` field used for repository resolution, ensuring a single canonical source of truth for "which organization does this payload claim to belong to." Reject the webhook (422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":check_suite from Org-Evil cannot enqueue RefreshCheckRunsJob for Org-Victim's stack" do
  # Org-Victim's real tracked stack/commit
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.last
  victim_full_name = "#{victim_stack.repository.owner}/#{victim_stack.repository.name}"

  body = {
    "check_suite" => {
      "head_sha" => victim_commit.sha,
      "head_branch" => victim_stack.branch
    },
    "repository" => {
      "owner" => { "login" => "org-evil" }, # attacker's own org, signs with own secret
      "full_name" => victim_full_name       # points at victim's repo
    }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest(
    "sha1", Shipit.github(organization: "org-evil").send(:webhook_secret), body
  )

  request.headers['X-Github-Event'] = 'check_suite'
  request.headers['X-Hub-Signature'] = signature

  assert_no_enqueued_jobs do
    post :create, body: body, as: :json
  end
  # Assert binding: signing org ("org-evil") != resolved repository org (victim_stack.repository.owner)
  # If a job IS enqueued here, the vulnerability is confirmed.
end
```
Assert both sides of the binding explicitly: `signing_org = "org-evil"` vs `resolved_repo_owner = victim_stack.repository.owner` — they differ, yet the current code allows the job enqueue to proceed.
