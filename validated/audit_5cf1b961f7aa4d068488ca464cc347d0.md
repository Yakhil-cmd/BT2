### Title
Cross-repository status forgery leading to unauthorized continuous-delivery deploy — `Shipit::Webhooks::Handlers::StatusHandler#process` (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone (`Commit.where(sha: params.sha)`), without scoping to the repository that authenticated the webhook, unlike other handlers (e.g. push/pull_request handlers) that go through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`. Because `sha` is only unique per `stack_id` (not globally, see the `stack_id`+`sha` index), an attacker who can get a genuinely-signed "status" webhook delivered for a repository they own can apply that status to a `Commit` row belonging to a completely unrelated victim `Stack`, as long as that commit's SHA also exists in the victim stack.

### Finding Description
The broken binding: the question assumes `stack enqueued into ContinuousDeliveryJob == stack whose repository matches params.repository.full_name`. In fact the code enforces only `commit.sha == params.sha` with no repository check at all: [1](#0-0) 

Compare with the base `Handler#stacks` helper, which every repository-scoped handler is expected to use to bind webhook payload to the correct repository/stack: [2](#0-1) 

`StatusHandler` never calls `stacks`; it queries `Commit` directly by `sha`, and `sha` uniqueness is only enforced per `stack_id` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning the same SHA can legitimately exist for multiple stacks/repositories (git commit objects are content-addressed, so a fork/mirror or an attacker copying an identical commit — same tree, parents, author, committer, message, timestamps — into their own repository reproduces the exact same SHA). `create_status_from_github!` then creates a `Status` on whichever `Commit` matches, regardless of which repository the webhook actually came from: [3](#0-2) 

From there, `Status#schedule_continuous_delivery` runs unconditionally on `after_commit`: [4](#0-3) [5](#0-4) 

which calls `Commit#schedule_continuous_delivery`, enqueuing `ContinuousDeliveryJob` for the **victim's** stack (the commit's actual `stack`, not the attacker's): [6](#0-5) 

`ContinuousDeliveryJob#perform` then calls `Stack#trigger_continuous_delivery`, which (if `continuous_deployment?`, not occupied, not delayed, no active task) calls `trigger_deploy`: [7](#0-6) 

**Attacker request**: The attacker owns a repository (or fork) that is served by the same GitHub App/organization installation trusted by the Shipit instance (this is required so `verify_signature` — which validates against `Shipit.github(organization: repository_owner)` — passes with a legitimately GitHub-computed signature; no secret is required from the attacker because GitHub computes and delivers the signature itself for events on installations they control). The attacker pushes/creates a commit object identical to the last commit in the victim stack's `next_commit_to_deploy` ordering (same tree/parents/message/author/committer/timestamps ⇒ identical SHA, since Git objects are content-addressed) into their own repo, then sets a `success` commit status on that SHA via the GitHub API on their own repository. GitHub delivers a genuinely signed `status` webhook naming the attacker's repository, but with the victim's commit SHA.

`verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema (`sha`, `state`, etc.) all pass normally — they validate the webhook's authenticity and shape, not which repository's stacks the SHA is permitted to affect. Because `StatusHandler` never calls `stacks`/`Repository.from_github_repo_name`, the repository identity is discarded after signature verification, and the divergence (attacker's authenticated repo vs. victim's affected stack) is never checked.

### Impact Explanation
An unprivileged GitHub user who controls any repository under an installation trusted by the target Shipit instance can forge a "success" status against an unrelated victim stack's commit, causing `Stack#trigger_continuous_delivery` → `trigger_deploy` → `Command#start`/`PTY.spawn` with `GITHUB_TOKEN` in the environment, deploying the victim repository's code without the victim's repository ever emitting the webhook. This is a payload-for-one-repository-mutating-another's-stack/commit class issue (Critical): it results in an unauthorized deploy execution on the victim's stack. It is repeatable against any stack whose `continuous_deployment` is enabled and whose commit history the attacker can reproduce (feasible for public repositories, forks, or predictable commit trees), and the blast radius spans every stack sharing the multi-tenant Shipit instance.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`, is not occupied/deployed-too-recently, and the attacker needs (a) their own repository under a GitHub App/org installation the Shipit instance already trusts (so `verify_signature` passes with a real signature), and (b) the ability to produce a commit object with a SHA identical to a commit already ingested for the victim stack — trivial for public repos since commits are simply git objects that can be copied/forked bit-for-bit, and setting the status is a normal, low-privilege GitHub API action on a repo the attacker owns. No Shipit secrets, session, or API token are needed. This makes the attack cheap and repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, matching the pattern used elsewhere in the codebase: resolve the stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update commits/statuses belonging to those stacks (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining `Commit` through `stack_id in stacks.pluck(:id)`), instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "a status webhook for repository A must not affect a commit belonging to unrelated stack B" do
  victim_stack = shipit_stacks(:shipit)          # repository "shopify/shipit-engine" (fixture)
  victim_commit = shipit_commits(:first)          # belongs to victim_stack
  victim_stack.update!(continuous_deployment: true)

  attacker_repo_payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "branches" => [{ "name" => victim_stack.branch }],
    "repository" => { "full_name" => "attacker/unrelated-repo", "owner" => { "login" => "attacker" } }
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate genuinely-signed event for attacker's own repo

  assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
    post :create, body: attacker_repo_payload, as: :json
  end
  # Fails today: ContinuousDeliveryJob IS enqueued with args: [victim_stack]
  # even though the webhook's repository.full_name ("attacker/unrelated-repo")
  # does not match victim_stack.repository.full_name.
end
```
This demonstrates `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])` firing from a webhook whose declared `repository.full_name` names an unrelated repository, confirming the binding is broken.
