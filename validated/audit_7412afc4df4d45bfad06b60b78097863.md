### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while handlers act on unguarded `repository.full_name` / global `sha` fields, allowing cross-repository forged events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check based on one field of the untrusted JSON payload, but the handlers that subsequently execute act on a *different*, independently-controlled field of the same payload to decide what gets written. Because these two fields are never cross-validated against each other, an attacker who legitimately controls a webhook secret for *some* organization/repository configured on the Shipit instance can forge a payload whose "authenticated" identity (used for signature verification) differs from the "acted-upon" identity (used for the actual database write). This is the same class of bug as the `LeverageMacroBase` finding: a post-verification / post-action step trusts a positional/derived reference instead of the value the check actually authenticated.

### Finding Description
`verify_signature` derives the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (or falls back to `organization.login`) to select which `GitHubApp`/`webhook_secret` is used for `verify_webhook_signature`. This only proves that *some* configured organization's secret matches the raw body — it does not bind that organization to the entity that will actually be modified.

Once verification "passes", `WebhooksController#create` dispatches the entire payload to handlers unconditionally: [3](#0-2) 

Handlers resolve the target `Repository`/`Stack` from a *different* payload field, `repository.full_name`: [4](#0-3) 

`PushHandler` then updates all matching stacks with attacker-controlled `ref`/`after` (triggers `sync_github`): [5](#0-4) 

`StatusHandler` is even less scoped — it matches commits **globally by `sha` alone**, with no repository/organization check at all, and directly writes a commit status: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used only for signature verification) and `repository.full_name` / bare `sha` (used only for the write) are independent, attacker-supplied fields in the same JSON body, nothing forces them to refer to the same repository. An attacker who is an admin of *any* GitHub organization/repository that is configured as a Shipit "tenant" (i.e., they legitimately know that org's `webhook_secret`, which they themselves set on GitHub's webhook config page for their own repo) can:

1. Craft a JSON body with `repository.owner.login = "attacker-org"` (their own org) so `verify_signature` resolves and validates against their own known secret.
2. Set `repository.full_name = "victim-org/victim-repo"` (a different tenant's repository hosted on the same Shipit instance) or, for the `status` event, simply set `sha` to a commit hash belonging to a stack they do not control.
3. Sign the raw body with their own valid secret and POST it to `/github/webhooks`.
4. `verify_signature` succeeds (their secret matches), and the handler then executes against the victim repository/commit named in the unguarded field.

This mirrors the CDP bug precisely: the "POST CALL CHECK" (webhook signature verification) validates one identity (`repository.owner.login`), while the actual write path (handler dispatch, `Repository.from_github_repo_name`, `Commit.where(sha:)`) trusts a different, unverified identity taken from the same forgeable payload — exactly the "organization that authenticated versus the repository that is written" binding called out as in-scope.

### Impact Explanation
- `StatusHandler` lets an attacker mark an arbitrary commit (in any stack on the instance) as `success`, which feeds directly into `Commit#deployable?` and `Commit#blocked?`/`schedule_continuous_delivery`, bypassing required CI checks and enabling continuous-deployment jobs to fire for a commit whose real CI never passed — an unauthorized/CI-bypassed deploy on a repository the attacker does not control. [8](#0-7) [9](#0-8) 
- `PushHandler` allows spoofed `ref`/`after` values to force `sync_github` on a victim stack the attacker doesn't administer. [5](#0-4) 
- This satisfies the "unauthorized deploy" High/Critical impact bucket, achieved purely by an unprivileged multi-tenant attacker who controls only their own webhook secret, never the victim's repository, Shipit session, or `ApiClient` token.

### Likelihood Explanation
Requires the Shipit deployment to be multi-tenant (multiple `Shipit.secrets.github[organization]` entries with distinct `webhook_secret`s serving unrelated GitHub orgs/repos on one instance) — a supported, documented configuration (`lib/shipit/github_app.rb`, `lib/shipit.rb#github`). Given that configuration, exploitation only needs the attacker to control the webhook secret for their own tenant org, craft a JSON body, and compute one HMAC — no other credential is needed. Likelihood is moderate-to-high in shared/multi-org deployments and none in single-organization deployments.

### Recommendation
Cross-validate that the field used for signature/organization resolution is consistent with the field used for the actual data lookup before dispatching to handlers: e.g., after determining `repository_owner` and resolving the `Repository`/`Stack` via `repository.full_name`, assert `repository.owner_login == repository_owner` (and for `StatusHandler`, scope `Commit.where(sha:)` by the resolved repository/stack rather than matching globally). Reject the webhook (422) if the two derived identities disagree.

### Proof of Concept
1. Configure Shipit with two tenants: `attacker-org` (attacker is a real GitHub org admin, sets `webhook_secret = "S"` both on GitHub and in Shipit secrets) and `victim-org` (unrelated stack, e.g. `victim-org/victim-repo`, tracked by Shipit).
2. Attacker builds a `status` event payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<sha of a real commit belonging to victim-org/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, raw_body)` using their own known secret `S`.
4. POST to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the HMAC matches → verification passes.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (owned by `victim-org/victim-repo`, a stack the attacker has no access to), and calls `create_status_from_github!`, marking it `success` — potentially unblocking/triggering a real deploy of that commit via `schedule_continuous_delivery`, without ever touching `victim-org`'s real webhook secret, GitHub App, or Shipit session.
