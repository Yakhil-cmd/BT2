### Title
Cross-repository PullRequest mutation via organization-fallback signature verification bypass - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb)

### Summary
`Shipit::WebhooksController#repository_owner` selects the GitHub-App config used for signature verification from `params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')` when that path is absent, while every `pull_request` handler (e.g. `EditedHandler`) independently reads the target repository from `params.repository.full_name`. Because `verify_webhook_signature` unconditionally returns `true` for any organization configured without a `webhook_secret`, an attacker can pick an org name with no configured secret for the verification path while pointing `repository.full_name` at a victim's repository, letting the handler mutate the victim's `PullRequest`/review stack without ever proving control of that repository's secret.

### Finding Description
The broken binding is the implicit assumption:
`organization_that_verified_the_signature == owner_of_the_repository_the_handler_mutates`

In code, these are two independent reads:
- Verification org: [1](#0-0) , used at [2](#0-1) .
- Handler target repo: [3](#0-2) , feeding `pull_request` lookup at [4](#0-3) .

`EditedHandler`'s `ExplicitParameters` schema only `requires :repository do requires :full_name, String end` — it does **not** require `repository.owner.login`, so an attacker can supply a `repository` object containing only `full_name` (a victim repo, e.g. `"victim-org/victim-repo"`) while supplying a top-level `organization: { login: "attacker-or-secretless-org" }`. `repository_owner` then evaluates to `"attacker-or-secretless-org"` because `params.dig('repository','owner','login')` is `nil`. See schema: [5](#0-4) .

`WebhooksController#verify_signature` then calls `Shipit.github(organization: repository_owner)` and `verify_webhook_signature`: [6](#0-5) . Critically, line 77 (`return true unless webhook_secret`) makes verification a no-op for **any** organization whose config omits `webhook_secret`. If the multi-tenant Shipit deployment has even one configured GitHub organization/app without a `webhook_secret` (a legitimate, documented configuration state per `TOP_LEVEL_GH_KEYS`/`github_app_config` in [7](#0-6) ), an attacker who merely knows that org's login string can name it in `organization.login` and pass verification with an arbitrary or absent signature.

Once verification passes, `Shipit::Webhooks.for_event('pull_request')` fans every registered PR handler over the same raw params: [8](#0-7)  and [9](#0-8) . `EditedHandler#process` looks up the victim's `PullRequest` purely by `repository.full_name` and `number`, with no re-check that this repository belongs to the org that authenticated the request, and updates it: [10](#0-9) . `ClosedHandler` and `LabelCapturingHandler` follow the identical pattern (`repository.full_name` driving a `review_stacks`/`archive!`/label-write lookup), so the same technique extends to closing/archiving a victim stack or overwriting its labels: [11](#0-10) , [12](#0-11) .

None of the existing guards catch this: `check_if_ping`/`drop_unhandled_event` only filter on event type, not on repository ownership. `verify_signature` verifies against the wrong tenant by design of the fallback. The `ExplicitParameters` schema validates shape/types but never cross-checks `repository.owner.login` against `organization.login` or against the org used for verification.

### Impact Explanation
A payload authenticated under one (secretless) GitHub App/organization configuration can write to `PullRequest`/review-stack records that belong to a completely different repository/organization — this is a Critical cross-tenant state-manipulation impact per the Immunefi rubric ("a payload for one repository mutating another's stack"). Repeatable against any repository already tracked by Shipit, for any handler in the `pull_request` group (`edited`, `closed`, `labeled`, `unlabeled`, etc.), as long as the attacker can name a configured organization/app entry that lacks a `webhook_secret`.

### Likelihood Explanation
Requires the specific precondition that the deployment has at least one configured GitHub organization/app without a `webhook_secret` set (an explicit, supported configuration per `GitHubApp#initialize`/`lib/shipit.rb`). Given that precondition, the attacker cost is trivial: one unauthenticated HTTP POST to `/webhooks` with a crafted JSON body and the `X-Github-Event: pull_request` header — no valid secret, session, or GitHub credential needed. Because I could not fully enumerate every deployment's org/app configuration (that's environment-specific and outside the indexed code), I can only confirm the code-level bypass condition (`return true unless webhook_secret`) exists and is reachable; whether any given production instance actually has a secretless org configured is a deployment-configuration fact outside what the repo's code can confirm by itself.

### Recommendation
- In every PR handler, cross-validate that `params.repository.owner.login` (or `.full_name`'s org segment) matches the organization used to authenticate the webhook (`repository_owner` from the controller), rejecting mismatches.
- Make `repository.owner.login` a required field in the `ExplicitParameters` schema for all handlers, removing the organization-only fallback, or at minimum require it whenever `organization` is also present but disagrees with `repository.owner`.
- Reconsider `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` fallback — treat a missing secret as verification failure (or require secrets to be configured for all orgs) rather than an implicit bypass.

### Proof of Concept
Minitest plan (no live GitHub):
1. Configure two orgs in test credentials: `victim` (with `webhook_secret: "s3cr3t"`) and `no_secret_org` (with `webhook_secret` omitted).
2. Create fixtures: a `Shipit::Stack`/`Shipit::Repository` for `victim/repo`, and an existing `Shipit::PullRequest` on it (`number: 42`, `title: "Original"`).
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body:
```json
{
  "action": "edited",
  "number": 42,
  "pull_request": { "...": "...", "title": "HACKED" },
  "repository": { "full_name": "victim/repo" },
  "organization": { "login": "no_secret_org" },
  "sender": { "login": "attacker" }
}
```
4. Assert response is `:ok` (verification bypassed) and assert `Shipit::PullRequest.find_by(number: 42).reload.title == "HACKED"`, proving the equality `organization_that_verified == owner_of_mutated_repo` is violated (`no_secret_org` verified, `victim` mutated).

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
