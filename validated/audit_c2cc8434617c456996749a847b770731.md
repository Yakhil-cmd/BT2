### Title
Attacker-supplied route pool executes arbitrary token transfers under the caller's `require_auth` tree, draining wallet funds beyond the routed amount — (File: contracts/controller/src/strategies/swap.rs)

### Summary
Like CVE-2021-26920 — where the HTTP `InputSource` accepts a `file://` URL and thereby reaches a resource class the application intended to exclude — the controller's router strategies accept a caller-supplied `swap` XDR whose `pool` addresses are never validated against real DEX pools. A "pool" can be any contract. That contract runs inside the caller's authorized invocation, so any `token.transfer(victim, attacker, …)` it makes is recorded by `simulateTransaction` as a child of the caller's `swap_collateral`/`multiply`/`execute_strategy` auth entry and executes once the caller signs the simulated tree. The payload `min_out`, the controller's `RouterOverspend`/`NoSwapOutput` balance checks, and the final health-factor gate all pass because the stolen transfer is outside the measured `token_in`/`token_out` deltas.

### Finding Description
`swap_tokens` grants the router exactly one `authorize_transfer_as_current` for `amount_in` and then calls `router.execute_strategy(&controller, &amount_in, swap)` with `swap` forwarded verbatim from the user-supplied argument — no allowlist or shape check on the pools it names [1](#0-0) . The router resolves `pool` straight from the payload's `assets` registry into `SwapHop.pool` [2](#0-1)  and dispatches to venue adapters that invoke that address; `dispatch_hop` only measures the router's own `token_in`/`token_out` deltas around the call [3](#0-2) . The threat model explicitly acknowledges that "the router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization," and that the resulting loss "is the caller's wallet, not the routed amount" [4](#0-3) . The harness test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` proves that under recording (simulation) mode the rogue pool's `transfer(alice, attacker, WALLET_BALANCE)` is folded into Alice's `swap_collateral` auth entry, the swap still returns fair output, and Alice's unrelated wallet token is fully drained [5](#0-4) .

### Impact Explanation
Theft of user funds. A victim who executes an attacker-provided route (e.g., via a malicious or compromised quote source) signs the auth tree that simulation produces; that tree contains the hidden `transfer` child, so the rogue pool moves arbitrary wallet tokens unrelated to the swap — unbounded by `amount_in`, `min_out`, or the account's risk gates. The position still receives its fair `token_out`, so nothing on-chain signals the theft. This is exactly the reported class: a parameter typed as one resource ("pool for a DEX hop") resolves to an unintended resource class ("arbitrary contract running under the signer's authorization"), bypassing the restriction the single-input-transfer grant was meant to impose.

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-crafted `swap` payload and sign the simulated auth tree. Soroban's standard flow — simulate, then sign the returned `AuthorizedInvocation` tree — silently includes the extra child; wallets that render only the root call or that users sign without decoding child invocations authorize the theft. The entrypoint (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or a direct `execute_strategy`) is reachable by any unprivileged address with a funded position or wallet, and no privileged role is involved. Rated Medium consistent with the source report.

### Recommendation
Enforce a venue/pool allowlist in the router: resolve `pool` addresses against an owner-managed registry per venue (or pin pool contract WASM hashes / deployer), so a route can only name vetted pool contracts. Additionally, the controller could run the router call inside a sub-context that blocks `require_auth` propagation for the `sender` (e.g., performing strategy swaps under a dedicated strategy account rather than the caller's root entry), and clients should reject simulated auth trees containing any child beyond the single expected input `transfer`.

### Proof of Concept
1. Alice has USDC supplied and holds `WALLET_BALANCE` of an unrelated token. Attacker deploys `RogueHopPool`, whose `swap()` executes `token::Client::new(&wallet_token).transfer(&alice, &attacker, WALLET_BALANCE)` [6](#0-5) .
2. Attacker hands Alice a `swap_collateral` route whose `hop_pool` is the rogue pool but that still pays fair `ETH` output [7](#0-6) .
3. Alice simulates: the rogue `transfer` is recorded as a child of her `swap_collateral` auth entry; the call succeeds and her collateral account is credited `FAIR_OUT_ETH` [8](#0-7) .
4. Alice signs the simulated tree and submits: the host authorizes the child transfer, `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE` [9](#0-8) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
