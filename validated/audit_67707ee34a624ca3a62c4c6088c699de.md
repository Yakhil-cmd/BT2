### Title
EIP-712 domain separator in `pallet-assets-precompiles` permit uses a hardcoded, non-live `ChainId` constant, enabling cross-chain signature replay for chains sharing the same compiled `ChainId` — ([File: substrate/frame/assets/precompiles/src/permit.rs])

### Summary
The `permit` pallet added to `pallet-assets-precompiles` implements EIP-2612-style gasless approvals for ERC20 asset precompiles. Its EIP-712 domain separator is computed with `T::ChainId::get()`, a compile-time pallet constant configured per-runtime (`ConstU64<...>`), rather than any value that is cryptographically bound to the specific live chain's identity (e.g. genesis hash). This mirrors exactly the root cause described in the LooksRareExchange report: a domain separator whose chain-identifying component is fixed independently of the chain's actual live identity, so a signature valid on one deployment remains valid on any other deployment that happens to share the same constant, the same verifying-contract address, and the same asset name.

### Finding Description
`permit::Pallet::compute_domain_separator` builds the EIP-712 `DOMAIN_SEPARATOR` as: [1](#0-0) 

`chain_id` here comes from `T::ChainId::get()`, declared as: [2](#0-1) 

`T::ChainId` is the same type used by `pallet-revive` for EIP-155 replay protection on Ethereum-style transactions: [3](#0-2) 

Crucially, this value is a compile-time `ConstU64<...>` baked into each runtime binary, not derived from the chain's genesis hash or any other value unique to a specific running network instance. Different runtime binaries in this same repository already reuse identical constants: [4](#0-3) [5](#0-4) 

Both use `ConstU64<420_420_420>`. This demonstrates the class of collision the bug report warns about: nothing prevents two independently operated, live chains (e.g. a canary/staging fork of a network, a testnet clone, or any two chains built from the same runtime code/config) from sharing the identical `ChainId` constant.

Unlike ordinary signed extrinsics — which are protected against cross-chain replay by `frame_system::CheckGenesis`, bound to the actual genesis block hash of the chain that produced it: [6](#0-5) 

`permit()` signatures are verified entirely inside the precompile/pallet call (`use_permit` / `permit_digest`) and never pass through `CheckGenesis` or any other chain-binding transaction extension — the EIP-712 digest is the only replay boundary, and it depends solely on `verifying_contract`, `name`, `nonce`, `deadline`, and the fixed `ChainId` constant: [7](#0-6) 

Consequently, if two live deployments share: (a) the same `T::ChainId` constant, (b) the same precompile/verifying-contract address for a given asset (asset ids and precompile address derivation are deterministic from config), and (c) the same asset name/metadata, then a permit signature produced by an owner for use on chain A is byte-for-byte valid on chain B, letting anyone submit it there to grant the same allowance without the owner's consent for that specific chain.

### Impact Explanation
If exploited, an attacker who observes/obtains a valid `permit()` signature intended for use on chain A could replay it on chain B (sharing the same `ChainId`, precompile address, and asset name) to grant themselves (or the same spender) an allowance over the victim's tokens on chain B, potentially followed by `transferFrom` to drain funds there. This is a signature-replay / unauthorized-approval issue analogous to unbacked authorization, though its blast radius is bounded by needing colliding `ChainId` + verifying-contract + asset-name across two live chains, which is narrower than the "any hard fork retains chainID" case in the original EVM report.

### Likelihood Explanation
Likelihood is Low-to-Medium in the general case (requires an operator to configure two independent live chains with identical `pallet_revive::Config::ChainId` and identical asset id/name for the same asset), but the codebase itself already demonstrates this collision pattern occurring by default between multiple runtime binaries (`substrate/bin/node/runtime` and `substrate/frame/revive/dev-node/runtime` both use `420_420_420`). Since `ChainId` is a compile-time constant copied across runtime configs rather than derived from genesis/network identity, any deployment that forks/clones an existing runtime's chain spec without changing this constant (a common and easy-to-miss step, exactly like the original report's chain-fork scenario) reproduces the vulnerability class.

### Recommendation
- Do not rely solely on a static `ChainId` constant for EIP-712 domain separation; incorporate a value bound to the live chain's actual identity, e.g. the genesis hash (as `CheckGenesis` already does for ordinary extrinsics), or cache/verify the domain separator against genesis hash at first use and reject/regenerate on mismatch.
- Alternatively, document explicitly that operators must assign a globally unique `ChainId` per live deployment and add a startup/integrity check (extending `pallet_revive`'s `integrity_test`, which currently only checks `ChainId > 0`) that fails to build if a known/reserved default value is used in a production chain spec.
- Consider adding the genesis hash as an additional field in the `EIP712Domain` struct used by `compute_domain_separator`, matching common OpenZeppelin/ERC-5267 domain-separator best practices for chains where the standard `chainId` alone is not a sufficiently unique/stable identifier.

### Proof of Concept
No executable PoC was run — this environment provides read-only code search/browsing only (no filesystem, terminal, or network access to build/run a Rust/FRAME integration test). The analysis above is based on static code inspection:
- Confirmed `compute_domain_separator` uses `T::ChainId::get()` with no genesis-hash or other per-deployment binding: `substrate/frame/assets/precompiles/src/permit.rs:148-177`.
- Confirmed `T::ChainId` is a compile-time `Get<u64>` constant, not derived at runtime from chain identity: `substrate/frame/assets/precompiles/src/permit.rs:82-89`, `substrate/frame/revive/src/lib.rs:330-336`.
- Confirmed identical constant values already reused across separate runtime binaries in-repo (`420_420_420` in both `substrate/bin/node/runtime/src/lib.rs:1579` and `substrate/frame/revive/dev-node/runtime/src/lib.rs:362`), demonstrating the collision precondition is not hypothetical.
- Confirmed ordinary extrinsics are protected via `CheckGenesis` (`substrate/frame/system/src/extensions/check_genesis.rs:56-61`), but `permit()` signature verification bypasses this protection entirely, relying only on the EIP-712 digest.

A concrete reproduction would require: standing up two test runtimes with identical `pallet_revive::Config::ChainId`, identical asset id/name (hence identical precompile "verifying contract" address and `compute_domain_separator` output), signing a `permit` off-chain for chain A, and submitting the same `(v,r,s)` via `bare_call`/`bare_permit` on chain B to show `use_permit` succeeds and grants an allowance the owner never authorized for chain B — this was not executed due to tooling constraints, and is left as a follow-up integration test using the existing `permit_precompile_tests.rs` harness (e.g. adapting `permit_replay_through_precompile_is_rejected`) with two distinct `ChainId`-identical mock runtimes.

		///
		/// DOMAIN_SEPARATOR = keccak256(abi.encode(
		///   keccak256("EIP712Domain(string name,string version,uint256 chainId,address
		/// verifyingContract)"),
		///   keccak256(name),
		///   keccak256("1"),
		///   chainId,
		///   verifyingContract
		/// ))
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		pub fn compute_domain_separator(verifying_contract: &H160, name: &[u8]) -> H256 {
			let name_hash = keccak_256(name);
			let version_hash = keccak_256(b"1");
			let chain_id = T::ChainId::get();

			// Encode: typehash || name_hash || version_hash || chainId || verifyingContract
			let mut data = Vec::with_capacity(DOMAIN_SEPARATOR_ENCODED_LEN);
			data.extend_from_slice(&DOMAIN_TYPEHASH);
			data.extend_from_slice(&name_hash);
			data.extend_from_slice(&version_hash);
			// Pad chain_id to 32 bytes (big-endian)
			data.extend_from_slice(&[0u8; 24]);
			data.extend_from_slice(&chain_id.to_be_bytes());
			// Pad address to 32 bytes
			data.extend_from_slice(&[0u8; 12]);
			data.extend_from_slice(verifying_contract.as_bytes());

			H256(keccak_256(&data))
