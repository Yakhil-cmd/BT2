### Title
Cross-repository commit-status forgery via globally-unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Finding Description
Webhook signature verification in `Shipit::WebhooksController#verify_signature` only proves that a request was signed with the webhook secret belonging to *one specific GitHub organization* — the one resolved by `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`). [1](#0-0) 

That verified binding is: `organization-that-signed == organization named in the payload`. It says nothing about *which repository/commit record* the event is allowed to mutate. The `status` event handler breaks that binding by writing to commits selected purely by the global `sha` string, with no scoping to the repository/stack that the verified organization owns:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Contrast this with `CheckSuiteHandler`, which correctly scopes to `stacks` (repository-derived) before touching any commit: [3](#0-2) 

and with the base `Handler` class, which already provides a `stacks`/`repository_name` helper for exactly this purpose but `StatusHandler` does not use it: [4](#0-3) 

Because git commit SHAs are content-addressed, the same SHA legitimately exists in multiple `Commit` rows across different `Repository`/`Stack` records whenever histories are shared (forks, mirrors, cherry-picked/rebased commits reproducing an identical tree+parent, or multiple Shipit stacks tracking the same upstream repo). `Commit.where(sha:)` returns **every** such row regardless of which organization/repository the verified webhook belongs to. This is the same bug class as the reported issue: a hash/identifier used as the sole cardinality key for state mutation, without a guaranteed-unique, trust-bound scoping component (there, `dataHash`; here, `sha`).

### Impact Explanation
An attacker who can trigger a legitimately-signed `status` webhook for *some* repository tracked by the Shipit installation (i.e., has commit-status write capability on any one repo/org configured in this Shipit deployment — a far lower privilege than write access to a sensitive target stack) can set `state: success` on a commit row belonging to an unrelated, more sensitive stack, as long as the same SHA exists there (e.g. because the sensitive stack is a fork/mirror of, or shares commit history with, the low-privilege repo).

`Status#state` directly drives `Commit#deployable?`/`Commit#status`, and a transition to `success` triggers `schedule_continuous_delivery` → `Stack#trigger_continuous_delivery` → `trigger_deploy`, i.e. it can cause an **unauthorized deploy** on the victim stack if continuous deployment is enabled, or unblock a manual deploy by satisfying the CI gate. [5](#0-4) [6](#0-5) 

This matches the required High/Critical impact bar ("an unauthorized deploy").

### Likelihood Explanation
Requires only: (a) the attacker controls or has commit-status-write access to any repository whose webhooks are routed through this Shipit instance (which is the normal, low-privileged CI/webhook integration path, not an ApiClient token or admin credential), and (b) a SHA collision achievable through legitimate git operations (forking, mirroring, or replaying identical commit trees) between that repository and a higher-value tracked stack. This is realistic in any Shipit deployment tracking multiple related repositories/forks/mirrors of the same codebase, which is a common pattern (staging/prod mirrors, internal forks). No session, API token, or webhook secret theft is required — only a validly signed webhook from a repository the attacker is legitimately entitled to push CI statuses to.

### Recommendation
Scope `StatusHandler#process` to the repository identified in the verified webhook payload, mirroring the pattern already used by `CheckSuiteHandler`/`PushHandler`:

```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```

More generally, never key a security-relevant mutation solely on a non-repository-scoped identifier (`sha`) when the trust boundary established at verification time is per-organization/per-repository; always intersect the lookup with `Handler#stacks`/`repository_name`.

### Proof of Concept
1. Shipit is configured to receive webhooks for org `victim-org` (owns high-value stack `victim-org/app`) and also for org `attacker-org` (owns a low-privilege, attacker-controlled fork `attacker-org/app` that shares commit history, hence identical SHAs, with `victim-org/app`) — or a single org that hosts both a low-privilege sandbox repo and the sensitive repo sharing history via mirroring.
2. Attacker pushes/forces a commit-status update on `attacker-org/app` for a SHA `abcd123…` that is also present in `victim-org/app`'s `commits` table, e.g. via `POST /repos/attacker-org/app/statuses/abcd123... {"state":"success"}` using credentials scoped only to `attacker-org/app`.
3. GitHub sends the `status` webhook to Shipit, signed with `attacker-org`'s webhook secret. `WebhooksController#verify_signature` succeeds because it only checks that the org owning the payload's `repository`/`organization` field signed it — here that's `attacker-org`.
4. `StatusHandler#process` runs `Commit.where(sha: 'abcd123...')`, which matches the commit row belonging to `victim-org/app` as well (same SHA, different stack), and calls `create_status_from_github!` on it, setting state to `success`.
5. If `victim-org/app`'s stack has `continuous_deployment: true`, this triggers `Commit#schedule_continuous_delivery` → an unauthorized deploy of `victim-org/app`, without the attacker ever having write access to `victim-org/app`.
