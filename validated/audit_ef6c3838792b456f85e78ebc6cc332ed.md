### Title
Stack-scoped ApiClient token can read the CI/CD status of any other stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces token-to-stack binding by scoping every stack lookup through `stacks`/`stack`, but `Shipit::Api::CCMenuController` overrides `stack` for its own custom authentication flow and, unlike the vault contract that forgot to override `mint`/`withdraw`, forgets to preserve the stack-scoping logic it replaces — letting a stack-restricted token read data belonging to any other stack.

### Finding Description
`Api::BaseController` binds an `ApiClient`'s authorization to a specific stack through two cooperating pieces: `check_permissions!` (verifies the permission string, e.g. `read:stack`) and the `stacks`/`stack` helpers, which restrict the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to one stack: [1](#0-0) 

`ApiClient#check_permissions!` only checks that the permission string (`read:stack`) is present in `permissions` — it never checks `stack_id` at all, so the stack-id restriction is enforced *exclusively* by the `stacks`/`stack` scoping method in the base controller: [2](#0-1) 

`Api::CCMenuController` needs a custom `authenticate_api_client` because CCMenu clients (e.g. CruiseControl integrations) pass the token as a query parameter instead of via HTTP Basic auth. To do this it overrides both `authenticate_api_client` and `stack`: [3](#0-2) 

The override of `stack` drops the base class's scoping and resolves the stack from the raw request parameter against the *entire* `Stack` table (`Stack.from_param!(params[:stack_id])`), instead of `stacks.from_param!(params[:stack_id])` as the base class does. The `require_permission :read, :stack` before_action still only calls `check_permissions!`, which (as shown above) never inspects `stack_id`. As a result, any `ApiClient` token that has the `read:stack` permission — even one that was deliberately scoped to a single stack via `stack_id` — can be replayed against `/api/stacks/:stack_id/ccmenu` with an arbitrary `stack_id` belonging to a different stack, and the controller will happily render that other stack's latest deploy/rollback status: [4](#0-3) 

This is the same bug class as the report: the base contract properly gates access (`stacks`/`stack` scoping, analogous to the vault's overridden `deposit`/`redeem`), but a sibling entry point (`CCMenuController`, analogous to the un-overridden `mint`/`withdraw`) re-implements part of the contract without re-implementing the access restriction, breaking the binding "the stack a token authorizes vs. the stack it touches."

### Impact Explanation
An attacker who holds any legitimately-issued `ApiClient` token scoped to one stack (`stack_id` set, `read:stack` permission) — a normal, low-privilege credential type supported by the schema (`belongs_to :stack, optional: true`) — can use that token to read deploy/rollback status of stacks they were never granted access to. This is an unauthenticated-for-that-resource read of stack state (deploy status) across a trust boundary the token was supposed to respect, matching the High-severity category "unauthenticated read of stack state, task streams or deploy output" via a token confusion between authorized scope and touched resource.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` token can trigger this by simply changing the `stack_id` segment of the CCMenu URL — no additional secrets, signatures, or privileged access are required beyond possessing one legitimately scoped token. The only uncertainty (not fully verifiable from the indexed files) is which application-facing feature currently issues `ApiClient` records with a non-null `stack_id` in this exact configuration of the engine (fixtures show it is a supported, tested configuration — e.g. `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`), so the precise UI/API path used to provision such a token could not be fully confirmed with the available index.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the base class's scoping helper (`stacks.from_param!(params[:stack_id])`) instead of querying `Stack` unscoped, so that a stack-restricted token can never resolve a stack outside `current_api_client.stack_id`. Additionally, consider having `ApiClient#check_permissions!` (or a dedicated method) validate `stack_id` match directly, so the restriction is enforced centrally rather than relying on every controller to re-implement the scoped lookup correctly.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to Stack A: `permissions: ['read:stack']`, `stack_id: <Stack A id>` (as in the `here_come_the_walrus` fixture).
2. Authenticate to the API with that token's Basic-Auth-style credentials, or (matching the controller's own auth path) call it with `?token=<token>` on the CCMenu route.
3. Request `GET /api/stacks/<Stack B>/ccmenu` where Stack B ≠ Stack A.
4. Observe that `require_permission :read, :stack` passes (permission string present) and `stack` resolves Stack B via unscoped `Stack.from_param!`, returning Stack B's latest deploy/rollback status — despite the token being scoped only to Stack A.
