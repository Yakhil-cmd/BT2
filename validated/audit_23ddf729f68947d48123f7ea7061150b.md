### Title
Webhook signature is verified against an organization derived from `repository.owner.login`/`organization.login`, but event handlers act on the repository named by the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the inbound webhook HMAC against using `repository_owner`, a value pulled from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). All downstream event handlers, however, resolve the actual `Stack`/`Repository` to mutate using a completely different field, `payload.dig('repository', 'full_name')`. Nothing enforces that these two attacker-supplied fields describe the same repository/organization, so the "org whose secret authenticated this request" and "repo/stack whose state gets written" are two independent, unlinked equalities.

### Finding Description
`WebhooksController` is mounted unauthenticated (it is a raw GitHub webhook receiver) and only gates requests on an HMAC signature: [1](#0-0) 

`repository_owner` is derived purely from client-controlled JSON: [2](#0-1) 

That owner string selects the `GitHubApp` (and thus its `webhook_secret`) used for verification: [3](#0-2) 

If the secret for the resolved organization is blank/`nil` (the documented default in the example config, and a supported per-organization setting when Shipit is configured with multiple GitHub orgs), verification is a no-op: [4](#0-3) [5](#0-4) [6](#0-5) 

Meanwhile, the actual work performed by handlers (which repository/stack gets updated or triggered) is keyed off an entirely separate field, `repository.full_name`, not `repository.owner.login`: [7](#0-6) [8](#0-7) [9](#0-8) 

Since the raw JSON body is parsed fresh in `create` (`JSON.parse(request.raw_post)`) and passed unmodified to handlers, an attacker who controls the payload can set `repository.owner.login`/`organization.login` to any organization Shipit is configured for (in a multi-org deployment, or the sole org if it has no `webhook_secret`), while setting `repository.full_name` to the full name of a *different* repository that Shipit already tracks as a `Stack`. `verify_signature` authenticates the request against the "decoy" org's (weak/absent) secret, but the handler mutates state belonging to the unrelated, real target repository named in `full_name`.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written." Concretely:
- A `push` event with a forged `after` SHA and a `full_name` pointing at a victim stack causes `GithubSyncJob`/`stack.sync_github` to run for that stack, ingesting an attacker-chosen commit SHA into the stack's commit history.
- A `status`/`check_suite` event can inject a fabricated "success" CI status for a chosen commit/stack (`Status.replicate_from_github!`, `commit.schedule_continuous_delivery`), which — combined with a stack having `continuous_deployment: true` — is sufficient to make Shipit enqueue `ContinuousDeliveryJob` and perform an actual, unauthorized deploy of an attacker-chosen commit, entirely without possessing the real target organization's webhook secret.

This lands squarely on the Critical impact bucket of "an unauthorized deploy," since the write (sync/CI-status/CD trigger) targets a stack whose organization never authenticated the request.

### Likelihood Explanation
Exploitability depends on the operator's configuration: it requires that at least one organization/App entry known to the Shipit instance has no `webhook_secret` configured (explicitly supported and shown as the default/`nil` in `config/secrets.development.example.yml`, and realistic in multi-org setups such as `test/dummy/config/secrets_double_github_app.yml` where each org has independent, possibly differently-managed secrets) — the attacker never needs to know any actual secret, only that such an org exists in the deployment. Given `webhook_secret` is documented as optional per-organization and the code path (`return true unless webhook_secret`) is a deliberate no-signature-required branch, this is a realistic, low-effort attacker path, not a purely theoretical one.

### Recommendation
Bind webhook authentication to the same repository that handlers act on: derive `repository_owner` from `repository.full_name`'s owner segment (or require `repository.full_name`'s owner to match `repository.owner.login`/`organization.login` before dispatching), and reject events where these disagree. Additionally, consider making `webhook_secret` mandatory (refuse to boot/serve webhooks for any configured organization lacking one) rather than silently treating a missing secret as "verified."

### Proof of Concept
1. Configure (or observe) a Shipit deployment where organization `decoy-org` has no `webhook_secret` set (per `config/secrets.development.example.yml`) while `victim-org` (with a real, secret-protected GitHub App) has a tracked `Stack` for `victim-org/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any value), and JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "decoy-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "decoy-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) — no valid signature is required.
4. `PushHandler#process` resolves the target stack via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "deadbeef...")`, ingesting the attacker-chosen SHA into `victim-org/victim-repo`'s stack despite the request never being authenticated by `victim-org`'s credentials.
5. Repeating with a forged `status`/`check_suite` event pointing at the same `full_name` and `state: "success"` can subsequently trigger `ContinuousDeliveryJob` if the victim stack has `continuous_deployment: true`, producing an unauthorized deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
