Confirmed root cause. The webhook signature is verified using the organization derived from `repository.owner.login` (or `organization.login`) in the payload, but the actual write target (which `Stack`/`Repository` gets a sync triggered) is derived from a **separate** field, `repository.full_name`, that is never cross-checked against the organization used for verification.

### Title
Webhook signature/organization confusion allows cross-organization repository sync triggering - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once the signature check passes, the entire raw payload is handed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and every handler (e.g. `PushHandler`, via `Shipit::Webhooks::Handlers::Handler#stacks`) independently re-reads `payload.dig('repository', 'full_name')` to determine which `Repository`/`Stack` records to act on [1](#0-0) [2](#0-1) [3](#0-2) .

### Finding Description
This mirrors the Cork Protocol pattern: one code path checks/locks against value A (`repository.owner.login`, used to select the `webhook_secret`/`GitHubApp` for verification) while a different, unguarded field B (`repository.full_name`) is what is actually acted upon (which stacks get synced). The binding that should hold is:

`organization whose secret authenticated the request == owner of the repository whose stacks are modified`

Nothing in `WebhooksController` or `Handler#stacks`/`Handler#repository_name` enforces that `repository.full_name`'s owner segment matches `repository_owner` used in `verify_signature`. An attacker who controls (or has compromised) any single GitHub organization/App installation registered in Shipit's `Shipit.github` config — i.e. knows that organization's legitimate `webhook_secret` because they administer that org's GitHub App installation — can sign an arbitrary JSON payload with that organization's secret, but set `repository.full_name` (and `ref`/`after`) to point at a *different*, victim organization's repository that is also configured in the same Shipit instance. `verify_signature` will succeed because it hashes `request.raw_post` (which is attacker controlled) with the correct secret for the *claimed* owner, and `PushHandler` will then call `Repository.from_github_repo_name(victim_repo_full_name)` and trigger `stack.sync_github(expected_head_sha: attacker_supplied_sha)` for the victim's stacks [4](#0-3) .

`sync_github` enqueues `GithubSyncJob`, which fetches commits from the real GitHub API for that stack's actual repository using the stack's own credentials, so this does not immediately let the attacker inject fake commits — but it does let an unrelated organization's webhook secret trigger sync/refresh activity, and more importantly demonstrates that the trust boundary intended by per-organization secrets ("this webhook really came from GitHub for org X") is not preserved end-to-end into the handler layer, since the handler uses an entirely independent field with no re-validation against the verified organization.

### Impact Explanation
Per the engine's own security model, per-organization `webhook_secret`s exist specifically so that a compromised/malicious organization cannot forge events for other organizations' repositories tracked by the same Shipit instance. Because `full_name` (write target) is never checked against `repository_owner` (verified identity), a party holding one organization's webhook secret can force GithubSyncJob invocations (and associated `expected_head_sha` values used for retry/eventual-consistency logic) against stacks belonging to a completely different, unrelated organization. This is a cross-repository write/trigger crossing an authentication boundary that the per-org secret model was designed to prevent.

### Likelihood Explanation
Requires the attacker to already control one legitimate organization's GitHub App installation/webhook secret configured on the same Shipit instance (multi-tenant deployments configure several orgs, as shown in `config/secrets.development.shopify.yml`) [5](#0-4) . This is a realistic scenario for any Shipit deployment serving multiple organizations, since each org's own admins legitimately know their own webhook secret but should not be able to affect other orgs' stacks.

### Recommendation
In `Handler#repository_name`/`#stacks` (or centrally in `WebhooksController`), validate that the owner segment of `payload.dig('repository', 'full_name')` matches the `repository_owner` value that was used to select the `webhook_secret` during `verify_signature`, rejecting the webhook (422) if they differ.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App installation on a shared Shipit instance and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `push` payload: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen-sha>"}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and succeeds since the signature matches `OrgA`'s secret.
5. `PushHandler#process` reads `repository.full_name = "OrgB/victim-repo"`, looks it up via `Repository.from_github_repo_name`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack — despite `OrgA` never being authorized to act on `OrgB`'s repositories.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
