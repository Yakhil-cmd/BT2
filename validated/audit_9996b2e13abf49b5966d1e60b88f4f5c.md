### Title
Multisig `r of set` / `weighted and` definitions allow duplicate signer branches, silently degrading the M-of-N threshold - (File: `definition.js`)

### Summary
`validateDefinition()` in `definition.js` validates the `set` array of an `r of set` or `weighted and` address-definition operator by checking length, `required` bounds, and recursively validating each branch, but it never checks whether two or more branches of the `set` resolve to the *same* signer (same `sig`/`hash` pubkey, or the same inner `address`). This mirrors the `OwnerList` bug class: a collection that is supposed to represent distinct independent principals (here, distinct co-signers of a multisig address) can contain the same principal more than once, silently breaking the counting/threshold invariant that the rest of the system relies on.

### Finding Description
When an address (or asset spending condition) definition uses `r of set` or `weighted and`, `validateDefinition`'s `evaluate()` only checks:
- `args.set` is an array of length ≥ 2,
- `args.required` is a positive integer ≤ `args.set.length` (or ≤ total weight for `weighted and`),
- each branch of `args.set` individually validates (recursing into `sig`, `hash`, `address`, etc.). [1](#0-0) [2](#0-1) 

There is no check that the resolved signer identities across `args.set` are distinct. A definition author can therefore construct, e.g., `["r of set", {required: 2, set: [["sig",{pubkey:A}], ["sig",{pubkey:A}], ["sig",{pubkey:B}]]}]`, which superficially reads as "2-of-3" but actually only requires control of key `A` (the duplicated branch), because each branch is authenticated independently at its own path in `validateAuthentifiers()`: [3](#0-2) [4](#0-3) 

Since the same signature (over the same unit hash) produced by key `A` is valid for authentifier path `r.0` as well as `r.1` (both just check the signature against `A`'s pubkey), a holder of `A` alone can satisfy `count >= args.required` (or `weight >= args.required`) without ever needing key `B`. This is functionally identical to the reported `OwnerList` issue: a list meant to enumerate independent members allows duplicates, which breaks the "count" logic (`owners.count` there, `required`/`count`/`weight` here) that downstream authorization decisions depend on.

### Impact Explanation
Any address whose definition is built as an "M-of-N" multisig via `r of set` or `weighted and` can have its effective security silently reduced to fewer independent keys than advertised, up to 1-of-N, if any branch is duplicated (by mistake in wallet-generation code, by a malicious co-signer proposing the shared address definition to other members via `wallet_defined_by_addresses.js`'s `handleNewSharedAddress`/`addNewSharedAddress`, or by any unprivileged unit poster defining their own address this way). Since other co-signers/observers rely on `required` reflecting the number of *distinct* approvals needed, an attacker who controls just one of the duplicated keys can single-handedly authorize spends from what appears to be a properly co-signed address — a concrete unauthorized-spending scenario.

### Likelihood Explanation
Reachable by any unprivileged actor: address definitions (including multisig `r of set`/`weighted and` structures) are posted directly by ordinary units' `authors[].definition` field and validated by `validateDefinition`/`validateAuthentifiers` in the normal unit-validation path — no special privilege is required. The check that is missing (distinctness of set members) is a simple oversight analogous to the missing `owners.list[newOwner] == address(0)` check in the reported bug.

### Recommendation
In `validateDefinition()`'s `r of set` and `weighted and` cases, before/while iterating `args.set`, compute a canonical representation of each resolved leaf signer (e.g., normalize `sig`/`hash` pubkey, or dereference `address` to its underlying chash) and reject the definition if any two branches resolve to the same signer, the same way `has equal`/`has one equal` already reject duplicate fields via `assocUsedFields` (`definition.js` lines 533-543).

### Proof of Concept
1. Construct definition `D = ["r of set", {required: 2, set: [["sig",{pubkey:A}], ["sig",{pubkey:A}], ["sig",{pubkey:B}]]}]`.
2. Compute `addr = chash160(D)` and have it accepted as a "2-of-3" shared address (e.g., through `wallet_defined_by_addresses.handleNewSharedAddress`, which only validates via `Definition.validateDefinition`, `wallet_defined_by_addresses.js` lines 520-528).
3. Post a payment unit spending from `addr` with `authors[0].definition = D` and authentifiers `{ "r.0": sigA, "r.1": sigA, }` (same signature value at both paths since both authenticate the same pubkey `A` against the same `unit_hash_to_sign`).
4. `validateAuthentifiers` evaluates `r of set`: path `r.0` and `r.1` both resolve `true` using only key `A`, `count=2 >= required=2` succeeds, and the payment is accepted — spending funds without any signature from `B`, defeating the intended 2-of-3 security guarantee.
