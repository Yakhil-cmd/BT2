### Title
Protocol/fund fee rounds down to zero on small-amount swaps, letting swappers systematically avoid contributing protocol/fund fees - ([File: programs/cp-swap/src/curve/fees.rs])

### Summary
`Fees::protocol_fee` and `Fees::fund_fee` use `floor_div`, which truncates toward zero, while `Fees::trading_fee` (the LP-facing fee) uses `ceil_div`, which always rounds up so LPs never lose their cut. Because `protocol_fee`/`fund_fee` are computed as `trade_fee * rate / FEE_RATE_DENOMINATOR_VALUE (1_000_000)` with floor division, any swap whose `trade_fee` is small relative to `1_000_000 / protocol_fee_rate` (or `/fund_fee_rate`) yields a protocol/fund fee of exactly `0`, even though a non-zero `trade_fee` was collected and credited to LPs.

### Finding Description
In `programs/cp-swap/src/curve/fees.rs`: [1](#0-0) 
`ceil_div` rounds up, `floor_div` rounds down.

`trading_fee` (LP fee) uses `ceil_div`, guaranteeing it is never zero for a non-zero input: [2](#0-1) 

But `protocol_fee` and `fund_fee` both use `floor_div` on the already-small `trade_fee` amount: [3](#0-2) 

These are invoked in `swap_base_input`/`swap_base_output`: [4](#0-3) [5](#0-4) 

and the results are persisted into the pool's accumulated fee ledger via `pool_state.update_fees` inside the permissionless swap instructions reachable by any user with an arbitrary `amount_in`/`amount_out`: [6](#0-5) [7](#0-6) 

Because `FEE_RATE_DENOMINATOR_VALUE = 1_000_000`, any pool configured with typical `protocol_fee_rate`/`fund_fee_rate` values (e.g. tens of thousands of bps out of 1,000,000) will floor `protocol_fee`/`fund_fee` to `0` whenever `trade_fee < ceil(1_000_000 / rate)`. A user can trivially split a larger trade into many tiny `swap_base_input`/`swap_base_output` calls, each individually producing `trade_fee > 0` (paid to LPs, since `trading_fee` rounds up) but `protocol_fee == 0` and `fund_fee == 0` on every single swap due to floor division. Repeating this lets a swapper move an arbitrary total volume through the pool while contributing effectively zero protocol/fund fee revenue, permanently starving the protocol/fund fee ledger relative to the fees the protocol is entitled to.

### Impact Explanation
This is a fee-ledger accounting defect: the protocol and fund fee accumulators (`protocol_fees_token_0/1`, `fund_fees_token_0/1` in `PoolState`, collected later via `collect_protocol_fee`/`collect_fund_fee`) systematically under-accrue relative to the trading volume and configured fee rates whenever trades are structured (or naturally occur) in amounts small enough that `trade_fee * rate / 1_000_000` truncates to zero. Any unprivileged swapper reachable via `swap_base_input`/`swap_base_output` with attacker-chosen `amount_in`/`amount_out` can exploit this deterministically and repeatedly, causing the protocol to permanently lose fee revenue it is entitled to by design — analogous to the referenced Blueberry finding where the withdraw fee rounds down to zero for small amounts.

### Likelihood Explanation
High likelihood: this requires no privileged access, only a series of ordinary swap transactions with small amounts, which is a completely standard, low-cost interaction pattern (e.g., splitting a large swap into many small legs, or naturally occurring low-value swaps on low-decimal or low-priced tokens). No special account setup or race condition is needed.

### Recommendation
Round `protocol_fee` and `fund_fee` up (via `ceil_div`, matching `trading_fee`'s rounding direction), or ensure that when `trade_fee > 0`, at least the smallest applicable unit is allocated to protocol/fund fees before the remainder is left to LPs — analogous to the original recommendation of guarding against amounts too small to produce a non-zero fee share. Alternatively, enforce a minimum swap size such that `trade_fee * protocol_fee_rate / FEE_RATE_DENOMINATOR_VALUE >= 1` and `trade_fee * fund_fee_rate / FEE_RATE_DENOMINATOR_VALUE >= 1` whenever those rates are non-zero.

### Proof of Concept
1. Assume an `AmmConfig` with `trade_fee_rate = 2500` (0.25%, ceil-divided) and `protocol_fee_rate = 120000` (12% of trade fee) — both plausible values passed at `create_amm_config` time, see: [8](#0-7) 
2. An attacker calls `swap_base_input` repeatedly with an `amount_in` chosen such that `trading_fee(amount_in, 2500)` (ceil-divided) yields a small positive value, e.g. `trade_fee = 8`.
3. `protocol_fee = floor_div(8, 120000, 1_000_000) = floor(960000/1000000) = 0`, and similarly `fund_fee` can be made `0` for its rate.
4. `pool_state.update_fees(0, 0, creator_fee, direction)` is called on every such swap: [6](#0-5) 
5. By repeating this many times, the attacker routes arbitrary volume through the pool while the protocol/fund fee ledger never accrues the fee share it is configured to collect, resulting in a systematic accounting loss for the protocol/fund treasury.

fn ceil_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(u128::from(fee_numerator))?
        .checked_add(fee_denominator)?
        .checked_sub(1)?
        .checked_div(fee_denominator)
}

/// Helper function for calculating swap fee
pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(fee_numerator)?
        .checked_div(fee_denominator)
}
