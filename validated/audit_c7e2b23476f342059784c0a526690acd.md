This confirms a concrete field-binding mismatch in the multi-organization webhook flow.

### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while the handled event acts on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-org Shipit deployments (`Shipit.github_organizations` > 1), each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which org's HMAC secret to validate the request against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Once verified, the raw, attacker-controlled JSON body is dispatched unmodified to event handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Those handlers determine the actual `Repository`/`Stack` to mutate using a *different* field, `payload.dig('repository', 'full_name')` [4](#0-3) .

### Finding Description
This is the same class of bug as the rust-lightning race condition: two code paths consult the same untrusted payload for what should be a single authoritative binding, but they read different fields, and only one of those fields is covered by the trust boundary (there, the pending-intercept map; here, the HMAC signature).

The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization owning the repository the handler writes to`

Before the fix (i.e., as implemented today): the HMAC signature is computed over the entire raw body and does cryptographically bind `repository.full_name` in the sense that the whole payload is signed — but the *secret selection* (which org's key to check against) is driven by `repository.owner.login`/`organization.login`, not by `repository.full_name`. An attacker who legitimately owns/controls a repository under Org A (and therefore knows/controls Org A's webhook secret, e.g. because they can configure their own GitHub App/webhook against Shipit, or Org A's secret is weaker/leaked) can send a webhook whose `repository.owner.login` is `"OrgA"` (so `verify_signature` picks Org A's secret) while `repository.full_name` is set to `"OrgB/some-repo"`. If the attacker also knows Org A's secret and signs the payload with it, the signature check in `github_app.verify_webhook_signature` [5](#0-4)  passes because it only checks that *some* configured secret matches the body — it never confirms that the org whose secret matched is the same org as `repository.full_name`'s owner. The handler then acts on `Repository.from_github_repo_name(repository_name)` for Org B's repo [4](#0-3) , e.g. triggering `stack.sync_github(expected_head_sha:)` in `PushHandler#process` for a branch/stack that belongs to a different, unrelated organization [6](#0-5) .

### Impact Explanation
This breaks the org-isolation guarantee that is the entire reason the multi-org config schema exists (`Shipit.github(organization:)` scoping in `lib/shipit.rb`) [7](#0-6) : an entity that can authenticate as one organization's webhook sender can forge events (`push`, `status`, `check_suite`, `membership`, `pull_request`) against a `Stack`/`Repository` belonging to a different, unrelated organization hosted on the same Shipit instance, up to triggering unauthorized `GithubSyncJob`s that update commit head shas and downstream deploy state cross-repository. This matches the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
This is only exploitable on multi-organization Shipit deployments and requires the attacker to already hold a valid `webhook_secret` for *some* organization configured on the instance (their own onboarded org, for example) — this is not a fully unauthenticated attack against a single-org instance, since in that mode `repository_owner` resolves to `nil`→falls back to the sole configured secret and there is no cross-org boundary to cross. I could not find any check anywhere in `WebhooksController` or `Handler` that cross-validates `repository_owner` (the field used for secret selection) against `repository.full_name`'s owner (the field used for the actual write), so the binding gap is real wherever multiple orgs share one Shipit instance.

### Recommendation
After signature verification succeeds, assert that the organization recovered from `repository.full_name`'s owner segment matches `repository_owner` (the same field/value used to select the `webhook_secret`) before dispatching to handlers, rejecting the request otherwise. Alternatively, always verify against the secret for the org derived from `repository.full_name`, not from `repository.owner.login`/`organization.login`, since those are the same field only by convention, not by enforcement.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`) [8](#0-7) .
2. As an attacker controlling OrgA's webhook secret, craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1 of the raw body using OrgA's `webhook_secret`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates successfully [9](#0-8) .
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` for OrgB's stack [6](#0-5) , despite the attacker never holding OrgB's secret or write access to OrgB's repository.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
