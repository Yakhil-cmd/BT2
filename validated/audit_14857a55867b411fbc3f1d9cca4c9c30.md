### Title
PR labels bypass the environment-variable whitelist and reach `Command#unbundled_env` unfiltered - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every label attached to a pull request directly into the deploy/task environment (`LABEL_NAME.upcase => "true"`) with no whitelist check, unlike every other env-injection path (`deploy_params`, `rollback_params`, `task_params`) which are filtered through `EnvironmentVariables#permit` against an explicit `variables` allow-list from `shipit.yml`. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler` captures the raw label array from the webhook payload and persists it verbatim via `pull_request.update!(labels:)`, so a label an attacker attaches to their own PR (e.g. `node_options`) becomes `NODE_OPTIONS=true` in `TaskCommands#env`/`DeployCommands#env`, which is passed unmodified to `PTY.spawn` in `Command#start`/`#unbundled_env`.

### Finding Description
Broken binding: the codebase asserts `TaskCommands#env keys ⊆ deploy_spec.variables ∪ fixed Shipit keys`, enforced everywhere env can be attacker- or user-influenced (`Shipit::TaskDefinition#filter_envs`, `Shipit::DeploySpec#filter_deploy_envs`/`#filter_rollback_envs`, all backed by `Shipit::EnvironmentVariables#permit`, see `lib/shipit/environment_variables.rb:13-18,35-44`). In reality, `Shipit::ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` directly into the stack env with **no call to `EnvironmentVariables.permit`**, so the equality does not hold for review-stack deploys/tasks.

Path: GitHub webhook `pull_request` event → `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#process` → `capture_labels?` (true via `opened_active_stack?`, `labeled_active_stack?`, or `reopened_active_stack?` for any active, non-archived review stack) → `capture_labels` → `pull_request.update!(labels: params.pull_request.labels.map(&:name))` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`), storing the attacker-chosen label names verbatim. On the next deploy/task, `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) does `super.merge(@stack.env)...merge(deploy_spec.machine_env).merge(@task.env)`, pulling in `ReviewStack#env`'s unfiltered label-derived pairs, and `DeployCommandsTest`/`TaskCommandsTest` confirm labels like `wip`/`bug` become `env["WIP"] == "true"` (`test/lib/shipit/task_commands_test.rb:6-16`, `test/lib/shipit/deploy_commands_test.rb:6-15`). That merged hash is handed to `Command#env`/`#unbundled_env` (`lib/shipit/command.rb:34,103-105`) and spawned with `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` (`lib/shipit/command.rb:92`), so `NODE_OPTIONS=true` (or any other label name) is present in the child process's real environment.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only authenticates that the payload really came from GitHub — it does not, and cannot, restrict what an authorized real GitHub webhook for a legitimate `opened`/`labeled`/`reopened` PR event may contain. The rule set grants the attacker the ability to "label their own PR," so a genuine, correctly-signed webhook carrying the attacker's chosen label is the normal, expected path — no forgery is required. `EnvironmentVariables#permit` exists and is used for every human-triggered env path (`deploy_params`, `rollback_params`, `task_params`, `deploy_spec.filter_deploy_envs`/`filter_rollback_envs`, `TaskDefinition#filter_envs`), but `ReviewStack#env` never calls it, so the whitelist is bypassed entirely for this one path. `Stack` model validations only constrain `environment`/`branch` format, not the label-derived env keys.

### Impact Explanation
Any label an attacker (who has permission to label their own PR, per the stated attacker capability) attaches to a review-stack PR is turned into an arbitrary environment variable for every subsequent deploy/task run on that stack's host — including names like `NODE_OPTIONS`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `RUBYOPT`, `PATH`-adjacent overrides, etc. (any string is a valid label; case is normalized via `.upcase`). Because `Command#start` spawns the interpreted deploy/task script via `PTY.spawn` using this exact merged env, a label such as `node_options` directly influences the startup behavior of any Node subprocess invoked during deploy, and other label choices could influence Ruby/Bundler behavior of the deploy script itself. This is repeatable per PR/per label change and scoped to the repository/stack the attacker's PR belongs to; it does not cross tenant boundaries into other repositories' stacks, but within the affected review-stack's deploy pipeline it is an unauthorized-content-into-execution-environment issue matching "a command running that should not" / execution trust violation for that stack.

### Likelihood Explanation
Preconditions: the target repository must use `Shipit::ReviewStack` (PR-based ephemeral environments), the attacker must be able to open a PR and add a label to it (granted by the stated attacker capabilities), and a deploy/task must subsequently run on that review stack (either via continuous deployment or a triggered task) — both very ordinary occurrences for review-stack workflows. No secrets, tokens, or elevated GitHub permissions are needed beyond the ability to label one's own PR, which the problem statement grants to the attacker. This is inexpensive and repeatable for every label change on every review-stack PR the attacker controls.

### Recommendation
Filter `pull_request.labels` in `Shipit::ReviewStack#env` through the same `Shipit::EnvironmentVariables.permit` mechanism (or an explicit label allow-list configured via `shipit.yml`) that already guards `deploy_params`/`rollback_params`/`task_params`, rejecting or dropping label names that are not on that allow-list before merging them into the deploy/task environment.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test)
test "#env does not let arbitrary PR labels set unwhitelisted env vars" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["node_options"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env

  # Binding under test: env keys reaching Command#unbundled_env must be a
  # subset of deploy_spec-declared variables ∪ fixed Shipit keys.
  # Currently this assertion FAILS because ReviewStack#env merges labels unfiltered.
  refute_includes env.keys, "NODE_OPTIONS"
end
```
and, to demonstrate the full webhook-to-env path:
```ruby
# test/models/shipit/webhooks/handlers/pull_request/label_capturing_handler_test.rb
test "captures attacker-controlled label names verbatim, including sensitive env-var names" do
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [{ "name" => "node_options" }]
  stack = create_stack

  LabelCapturingHandler.new(payload).process

  assert_includes stack.reload.pull_request.labels, "node_options"
  assert_equal "true", stack.env["NODE_OPTIONS"]
end
```
