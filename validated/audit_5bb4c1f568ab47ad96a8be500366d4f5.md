The reported bug class is fundamentally an EVM-specific failure mode: Solidity's `transfer`/`send` forward a fixed 2300 gas stipend to the receiving contract, which is easily exceeded on chains like zkSync, causing reverts and stuck ETH. Solana's account model has no equivalent mechanism — lamport transfers are not "calls" with a forwarded, hard-capped gas stipend to arbitrary receiver code.

In the system program, `transfer`/`transfer_verified` simply perform checked lamport subtraction/addition on account structs with no CPI, no fixed sub-call gas budget, and no receiver-executed code path that could revert due to insufficient forwarded compute. [1](#0-0) [2](#0-1) 

Stake withdrawal and vote withdrawal (`programs/system/src/system_instruction.rs` `withdraw_nonce_account`, and the CLI-driven stake/vote withdraw paths) likewise perform direct lamport field mutations rather than invoking receiver code under a constrained gas/CU budget. [3](#0-2) 

Epoch reward distribution similarly credits lamports directly to stake accounts via `store_stake_accounts_in_partition`/`update_epoch_rewards_sysvar` rather than through a gas-limited external call that could fail and strand funds. [4](#0-3) [5](#0-4) 

Since the root cause condition (fixed, insufficient gas stipend forwarded to arbitrary receiver code during an ETH transfer) does not exist as a reachable pattern in agave's system/stake/vote instruction handlers or reward distribution paths, there is no valid unprivileged-user analog per the scan rules.

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}

    /// Update EpochRewards sysvar with distributed rewards
    pub(in crate::bank::partitioned_epoch_rewards) fn update_epoch_rewards_sysvar(
        &self,
        inflation_reward_lamports_minted_and_burned: u64,
        debit_block_reward_lamports: u64,
    ) {
        let mut epoch_rewards = self.get_epoch_rewards_sysvar();
        assert!(epoch_rewards.active);

        epoch_rewards.distribute(inflation_reward_lamports_minted_and_burned);

        self.update_sysvar_account(&sysvar::epoch_rewards::id(), |account| {
            create_account(
                &epoch_rewards,
                self.inherit_specially_retained_account_fields(account),
            )
        });

        // Debit the lamports separately without updating capitalization,
        // since block reward lamports already existed
        let mut account = self
            .get_account_with_fixed_root(&sysvar::epoch_rewards::id())
            .expect("created sysvar account exists");

        // SAFETY: programmer error if we debit too many block rewards
        account
            .checked_sub_lamports(debit_block_reward_lamports)
            .expect("epoch reward sysvar has enough lamports for distribution");
        assert!(
            account.lamports() >= self.get_minimum_balance_for_rent_exemption(account.data().len()),
            "Sysvar account must have enough for rent exemption after debiting block rewards"
        );
        self.store_account(&sysvar::epoch_rewards::id(), &account);
