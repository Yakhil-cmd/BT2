### Title
Webhook signature is bound to the org named in `repository.owner.login`, but downstream handlers act on the unrelated `repository.full_name` — cross-tenant forged webhook events - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a request against using an organization name that is read straight out of the untrusted JSON body, while every `Webhooks::Handlers::Handler` subclass separately re-reads `repository.full_name` from that same body to decide **which stack/repository gets mutated**. Nothing ties these two fields together, so a caller who legitimately holds the webhook secret for *any* org configured in a shared Shipit instance can forge a validly-signed payload that names a *different* org's repository as the target, and have it processed as if GitHub had sent it.

### Finding Description
Signature verification:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
The `webhook_secret` used to validate the HMAC is looked up by an org name taken from the attacker-controlled body (`repository.owner.login`). `verify_webhook_signature` (in `lib/shipit/github_app.rb`) only proves that the raw POST body was HMAC-signed with *that named org's* secret — it says nothing about which repository the event should be attributed to.

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire raw payload* to handlers. Every handler resolves its target purely from a different field of the same body:
```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`repository.owner.login` (used for authentication) and `repository.full_name` (used for authorization/target-selection) are two independent JSON fields inside the same signed body — signing the body does not enforce any relationship between them, and the code never cross-checks that `full_name` actually belongs to `repository_owner`.

This breaks the binding: **`organization that authenticated == repository that is written`**. Before the attack, both sides are naturally equal because GitHub itself always generates consistent `owner.login`/`full_name` pairs for a given webhook. After the attack, an org (call it Org A) whose GitHub App is registered in this Shipit instance (`Shipit.github(organization: 'org-a')` resolves to a real `webhook_secret`) can sign a payload where `repository.owner.login` = `"org-a"` (so verification passes with Org A's own secret) but `repository.full_name` = `"org-b/target-repo"` (an entirely different tenant's repository configured in the same Shipit deployment). The request is accepted and dispatched to handlers operating on Org B's stacks.

### Impact Explanation
This is a cross-repository/cross-tenant write achievable by an org that is legitimately onboarded to Shipit but has no rights over the victim repository — i.e., an "unprivileged attacker" relative to the target stack. Concrete effects depend on which event/handler is abused, e.g.:
- `push` → `Handlers::PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on Org B's stack for an arbitrary SHA the attacker chooses, forcing head-commit changes on a stack the attacker doesn't own.
- `status` → `Handlers::StatusHandler` writes forged CI/commit statuses onto Org B's commits, which can flip `deployable?`/merge-queue checks (`MergeRequest#any_status_checks_failed?`, `Stack#merge_status`) to make a commit look green, enabling an unauthorized deploy/merge of code that never actually passed CI.
- `check_suite` → similarly forges check-run state for a foreign repository.

Because merge/deploy eligibility in Shipit is largely status-driven, forging status/check events into another tenant's repository can be leveraged into an unauthorized deploy or merge — meeting the "High"/"Critical" bar defined in the rules (unauthorized deploy/merge via authorization escalation into another tenant's stack).

### Likelihood Explanation
Requires the attacker to control (or be) an org that is a legitimate, already-configured Shipit tenant — this is not privileged relative to the *target* org and does not require guessing the target's secret, GitHub App private key, or any Shipit session/API token. In any multi-tenant Shipit deployment (multiple orgs configured under `Shipit.github`), any onboarded org can attack any other onboarded org this way. This is a realistic and cheap attack path, analogous to the Plaza Finance issue where a value used for one purpose (`totalSellReserveAmount`/gating) is trivially influenced by an unrelated, attacker-controlled input with no cross-check.

### Recommendation
When resolving the target repository/stack in `Shipit::Webhooks::Handlers::Handler`, verify that `payload.dig('repository', 'full_name')`'s owner matches the org whose secret validated the signature (`repository_owner` used in `verify_signature`), and reject/drop the event if they diverge. Alternatively, thread the verified `organization` through to handler dispatch and have `stacks`/`repository_name` resolution scoped to that verified organization rather than trusting the unrelated `full_name` field independently.

### Proof of Concept
1. Configure two orgs in `Shipit.github`, e.g. `org-a` (attacker-controlled, with known `webhook_secret_a`) and `org-b` (victim, with a Shipit stack for `org-b/target-repo`).
2. Craft a `status` (or `push`) webhook JSON body:
```json
{
  "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/target-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "branches": [{"name": "main"}]
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_a, raw_body)>` using Org A's own webhook secret.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: 'org-a')` (from `repository.owner.login`) and successfully verifies the signature against Org A's secret.
6. `Handlers::StatusHandler` resolves `repository_name` = `"org-b/target-repo"` and writes/updates a commit status on Org B's stack, despite the request never having been authorized by or originating from Org B. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
