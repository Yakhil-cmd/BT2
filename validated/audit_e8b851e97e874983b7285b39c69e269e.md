## Title
Merkle tree verification in `merkle.js` is vulnerable to the second-preimage (node-as-leaf) attack, allowing forged membership proofs in address `'in merkle'` conditions and AA `is_valid_merkle_proof()` checks - (File: `merkle.js`)

### Summary
`ocore`'s Merkle-tree implementation in `merkle.js` uses the same hash function with no domain separation for hashing leaves and hashing internal nodes, and leaves are hashed to the same fixed-length (32-byte/44-char base64) output as internal node hashes. This makes the tree vulnerable to the classic second-preimage attack: any two sibling hashes (leaf or internal) can be concatenated and presented as a forged "leaf" whose hash equals the real internal node, producing a valid Merkle proof for data that was never an actual leaf. This primitive is exposed to unprivileged actors via the `'in merkle'` address-definition authentifier and the AA-oscript `is_valid_merkle_proof()` function.

### Finding Description
`merkle.js` hashes leaves and internal nodes identically: [1](#0-0) 

and verification recomputes the path the same way, starting from `hash(element)`: [2](#0-1) 

The code even contains a developer acknowledgment of this exact issue: `// Node-as-Leaf issue might matter in some cases` [3](#0-2) .

Because `hash()` is applied uniformly to leaves and to the 64-byte-equivalent concatenation of two child hashes (`hash(arrHashes[i] + arrHashes[hash2_index])`), an attacker who knows any two sibling hash values `h_a`, `h_b` in a published tree (leaf hashes and root/sibling values used in legitimate proofs are necessarily public, since users need them to build their own proofs) can:
1. Construct a forged "element" string `forged = h_a + h_b`.
2. Submit `forged` together with the sibling path from that internal node up to the root as a proof.
3. `verifyMerkleProof(forged, proof)` computes `hash(forged) = hash(h_a + h_b)`, which is exactly the internal node value that would have been derived from the real children — so verification succeeds against the genuine root, even though `forged` was never one of the tree's original elements.

This primitive is reachable by unprivileged parties in two places:
- **Address authentifiers** — the `'in merkle'` condition lets an address definition require that a (definition-fixed) `element` be a member of a set whose Merkle root is published by oracles via a data feed. Verification is: [4](#0-3) . The `element` argument is validated only for character format, not for genuine tree membership: [5](#0-4) .
- **AA oscript** — `is_valid_merkle_proof(element, proof)` is a general-purpose builtin intended for AA authors to implement whitelist/allowlist/airdrop-style membership checks against a Merkle root (e.g. stored in AA state or a data feed), fully driven by trigger-supplied data: [6](#0-5) .

### Impact Explanation
Any AA that implements a Merkle-based allowlist/airdrop/claim mechanism using `is_valid_merkle_proof()` (a documented, intended use of this builtin) can be tricked into accepting a forged "leaf" that was never part of the original data set, as long as the attacker can derive it from two known sibling hashes of the real tree (which are normally public, since legitimate users need them to build valid proofs). If the forged leaf encodes attacker-favorable data (e.g., an inflated claim amount or an unauthorized address), this results in unauthorized withdrawal/allocation of AA funds — a direct AA fund-loss scenario. Similarly, an `'in merkle'` address-definition condition intended to restrict spending/signing rights to members of an oracle-approved set can be satisfied with a non-member value, undermining the authorization model of that address.

### Likelihood Explanation
Exploitation requires only knowledge of two sibling hash values from the tree — information that is generally public for any real-world Merkle allowlist/airdrop design (users are given their leaf hash plus sibling path to self-verify). No access to hub/node internals, oracle keys, or private data is needed; the attack is purely a client-side forgery of the `element`/`proof` pair submitted in a trigger unit or embedded in an address definition, making it reachable by any ordinary AA trigger sender or address author.

### Recommendation
Introduce domain separation between leaf hashing and internal-node hashing in `merkle.js`, e.g.:
- Prefix leaf hashing with a distinct tag: `hash('\x00' + element)` vs. `hash('\x01' + left + right)`, or
- Double-hash leaves before insertion, or
- Otherwise ensure leaf preimages cannot collide in format with internal-node preimages (e.g., different length encoding).

Apply the fix in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` in `merkle.js` consistently, and treat any existing on-chain data relying on the current scheme (`'in merkle'` conditions, AA state) as needing migration.

### Proof of Concept
1. Build a real Merkle tree over elements `[e0, e1, e2, e3]` using `merkle.getMerkleRoot`; note leaf hashes `h0..h3` and internal node `n01 = hash(h0+h1)`.
2. An attacker who knows `h0` and `h1` (public, since real users compute proofs against them) constructs `forged_element = h0 + h1`.
3. Attacker submits `is_valid_merkle_proof(forged_element, {index: 0, siblings: [n23], root: root})` (or the equivalent serialized proof) — via `trigger.data` to an AA, or as the `serialized_proof` authentifier for an `'in merkle'` address condition.
4. `verifyMerkleProof` computes `hash(forged_element) = hash(h0+h1) = n01`, then `hash(n01 + n23) = root`, matching the real root — proof accepted, even though `forged_element` (`h0+h1`) was never one of `e0..e3`. [7](#0-6)

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
