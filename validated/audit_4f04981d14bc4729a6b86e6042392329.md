### Title
Caller-controlled route bytes can inject unauthorized token transfers through an unallowlisted swap venue - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints accept caller-supplied `swap` bytes and forward them unchanged to the configured swap router while the caller’s authorization is still active. Because the router route can name arbitrary venue contracts, a malicious venue can inject an additional `token.transfer` from the caller into the simulated authorization tree and steal unrelated wallet tokens if the caller signs that tree. [1](#0-0) 

### Finding Description
`swap_collateral` accepts a raw `StrategySwap` byte argument, authenticates the account owner or delegate, withdraws collateral to the controller, and passes the opaque route into the swap path. [2](#0-1)  `swap_tokens` only checks that the route is non-empty, authorizes the exact controller-to-router input transfer, and invokes `execute_strategy` with the caller-controlled bytes. [3](#0-2) 

The post-call checks only bound the controller’s `token_in` spend and require a positive `token_out` balance delta; they do not constrain which venue contracts the route invokes or prevent venue code from requesting additional authorization from the original caller. [4](#0-3)  This is the same injection shape as the reported issue: attacker-controlled structured input is interpreted inside a trusted transaction context, allowing actions outside the caller’s intended operation.

### Impact Explanation
A malicious route can cause theft of arbitrary tokens held directly by the caller, not merely loss or poor execution of the collateral being swapped. The malicious venue can pay enough of the expected output asset to satisfy the controller’s measured-output check and preserve the account’s final risk position while simultaneously adding a transfer of an unrelated wallet token to the transaction’s authorization tree. [5](#0-4) 

The stolen amount is bounded only by what the victim signs in the poisoned authorization tree. The routed collateral amount, minimum output, and final account checks do not bound that separate wallet transfer.

### Likelihood Explanation
Likelihood is Medium. The attacker must get the victim to submit a malicious route and sign an authorization tree containing the extra transfer, so this is not a fully unauthenticated direct theft path. However, the affected entrypoints are ordinary user-facing strategy operations, routes are opaque bytes supplied to the contract, and the injected authorization can be hidden among transaction simulation output from the user’s perspective. [3](#0-2) 

### Recommendation
Do not allow swap route bytes to select arbitrary venue contracts. Enforce a governance-managed venue/pool allowlist before executing the route, or require the router to prove that every hop address belongs to an approved venue set. Keep the existing exact input authorization and measured input/output checks, but treat them as settlement controls rather than authorization isolation. [6](#0-5) 

### Proof of Concept
1. Deploy a malicious contract implementing the ABI expected for a supported swap venue, including a swap function that transfers the attacker-chosen `wallet_token` amount from the caller to the attacker and then returns enough `token_out` to the router.
2. Construct route bytes whose address registry contains the malicious pool and whose input/output assets match a legitimate `swap_collateral` request.
3. Call `swap_collateral(caller=victim, account_id=victim_account, current=USDC, amount=X, new=ETH, swap=malicious_route)`. [7](#0-6) 
4. The controller withdraws the collateral, authorizes only `USDC.transfer(controller, router, X)`, and invokes the router with the malicious route. [8](#0-7) 
5. During route execution, the malicious venue requests `wallet_token.transfer(victim, attacker, victim_balance)`. Simulation records this as an additional child of the victim’s controller authorization.
6. If the victim signs that simulation result, the malicious venue receives `victim_balance` of `wallet_token`, while the swap output and final account checks can still pass because they measure only the routed `USDC` and delivered `ETH`. [4](#0-3)
