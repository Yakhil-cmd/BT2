### Title
User-controlled swap routes can smuggle unauthorized wallet transfers into the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
High: an attacker can provide a swap route whose venue address points to malicious contract code. During a controller strategy such as `swap_collateral`, that code can request an unrelated token transfer from the victim; Soroban simulation records it as an extra child invocation under the victim’s `swap_collateral` authorization, and signing that tree permits the transfer. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral` authenticates `caller` and requires ownership or delegate authority, but accepts `swap` as opaque bytes and forwards it without inspecting the venue addresses encoded inside. [4](#0-3) [5](#0-4) 

`swap_tokens` authorizes only the intended input-token transfer from the controller to the configured router, then calls `router.execute_strategy(controller, amount_in, swap)`. [6](#0-5) 

The authorization helper creates a single leaf authorizing `transfer(controller, router, amount_in)` and permits no further controller sub-invocations, but it cannot constrain contracts reached through the route from requesting authorization from the original user. [7](#0-6) 

The router payload’s `assets` registry can contain arbitrary pool and token addresses, while `ops` selects them by index; the decoder performs structural bounds checks rather than checking venues against an allowlist. [8](#0-7) [9](#0-8) 

This mirrors the reported injection pattern: a caller-controlled payload is merged into an operation executed beneath a higher-value authorization context, while validation checks payload shape rather than the security-relevant properties of the referenced code. [10](#0-9) [11](#0-10) 

### Impact Explanation
A malicious venue can call `token.transfer(victim, attacker, amount)` for a token unrelated to the lending markets during the routed operation. [12](#0-11) 

Simulation records that transfer as a child of the victim’s `swap_collateral` authorization rather than rejecting it outright. [13](#0-12) 

If the victim signs the poisoned authorization tree, the unrelated wallet balance moves to the attacker while the swap can still return enough output to satisfy the controller’s measured-output and final-risk checks. [14](#0-13) [15](#0-14) 

The resulting loss is direct theft of user funds and is not bounded by the amount routed through the strategy. [3](#0-2) 

### Likelihood Explanation
Any account owner or active delegate can reach `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` with route bytes. [1](#0-0) [16](#0-15) 

The attack does not bypass Soroban authorization: it requires the victim to sign an authorization tree containing the injected transfer. [17](#0-16) 

That precondition is realistic where routes are generated by a quote service or frontend and the user signs the simulation-produced tree without independently decoding every sub-invocation. [18](#0-17) 

The pool’s output and controller solvency checks do not detect the unrelated transfer because they measure only the configured input and output assets. [19](#0-18) 

### Recommendation
Governance should allowlist executable venue/pool addresses, or the router should resolve pool addresses from a trusted registry instead of accepting them directly from the untrusted `assets` registry. [8](#0-7) [11](#0-10) 

At minimum, controller-facing routes should be restricted to vetted venue deployments, and clients should reject any authorization tree containing sub-invocations beyond the expected controller call, token pull, and documented route interactions. [3](#0-2) 

The protocol should also emit or expose decoded route metadata so wallets can display every pool and token contract whose code will execute before signing. [20](#0-19) 

### Proof of Concept
The existing harness registers an attacker-controlled hop contract whose `swap` method calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [21](#0-20) 

The route embeds that malicious hop address and is submitted as the `swap` argument to Alice’s `swap_collateral` call. [22](#0-21) [23](#0-22) 

Recording-mode simulation produces an authorization tree containing `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` beneath `swap_collateral`; the test then shows Alice’s unrelated wallet balance moving to the attacker. [24](#0-23) 

An honest tree without that child fails authorization, while signing the simulation-produced poisoned tree makes the theft succeed. [25](#0-24)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
