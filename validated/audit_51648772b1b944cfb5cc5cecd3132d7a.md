### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!(params[:stack_id])` helper used by every other API controller, so the binding "stack a token authorizes" == "stack the request touches" is broken.

### Finding Description
`Shipit::Api::BaseController` centralizes stack scoping for `ApiClient` tokens: `stacks` restricts the queryable set to the client's own stack when the token is stack-scoped, and `stack` builds on it via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

Every other resource controller (e.g. `StacksController`, deploys/tasks/hooks/locks/outputs) fetches the stack through this scoped helper, so an `ApiClient` created with `stack: some_stack` can only ever touch that one stack, even though its `permissions` list (e.g. `read:stack`) is otherwise generic. [2](#0-1) 

`CCMenuController`, however, overrides `stack` to bypass the scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`require_permission :read, :stack` only checks that the `ApiClient#permissions` array contains `read:stack`; it never checks whether the resolved stack matches `current_api_client.stack_id`. [4](#0-3) 

Because `Stack.from_param!` is called unscoped, any `ApiClient` holding `read:stack` permission — regardless of which single stack it was scoped to at creation — can pass an arbitrary `stack_id` in the URL and read another stack's CCMenu status (deploy state, project name, last build result) belonging to a repository/stack the token was never authorized to see.

This mirrors the analog's root cause: a security boundary (message kind for the staking precompile / stack scope for the API token) is enforced in the "normal" code path but omitted in one specific entry point that reimplements resource lookup instead of reusing the trust-preserving helper.

### Impact Explanation
This crosses the "stack a token authorises vs. stack it touches" boundary called out in scope: a token scoped to Stack A (e.g. the `here_come_the_walrus` fixture pattern, an `ApiClient` with `stack:` set and `permissions: ['read:stack']`) can be used to fetch CCMenu build/deploy status for any other stack in the installation by simply supplying a different `stack_id`. That is an unauthenticated-for-that-resource read of stack/deploy state across a trust boundary, matching the High-severity category "escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly stack-scoped `ApiClient` token with `read:stack` permission (the common case for CI-integration tokens such as the "CCMenu Client" created in `CCMenuUrlController`) can exploit this without any additional privilege — they only need to change one URL parameter. No admin/session access, no signature bypass, and no race condition is required.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped lookup, consistent with the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id?`-based scoping (defined in `BaseController#stacks`) is honored, closing the gap between the stack a token is authorized for and the stack the controller actually operates on.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A (`stack_id` set) with `permissions: ['read:stack']` (e.g., analogous to the `here_come_the_walrus` fixture, or the token minted by `CCMenuUrlController#client`). [5](#0-4) 
2. Authenticate to the API using that token (via `params[:token]`, as `CCMenuController#authenticate_api_client` accepts) and pass `stack_id` for Stack B, a stack the token was never authorized for. [6](#0-5) 
3. `GET /api/stacks/<stack_B_id>/ccmenu.xml` succeeds because `stack` is resolved via unscoped `Stack.from_param!`, returning Stack B's latest deploy/rollback status even though the token is bound to Stack A. [7](#0-6)
