### Title
Webhook signature verified against `repository_owner` while `MembershipHandler#process` attributes the resulting `Team` to a different, attacker-controlled `organization.login` in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `params.dig('repository','owner','login') || params.dig('organization','login')`, but `MembershipHandler#process` never reads `repository`; it attributes the mutated `Team` row using `params.organization.login` directly. An attacker who legitimately controls an organization (and therefore genuinely knows that organization's own `webhook_secret`) can craft a `membership` event whose top-level `repository.owner.login` names their own org (so their own secret is selected and signature verification passes) while the `organization.login`/`team.id` fields name an arbitrary victim organization/team, causing Shipit to create or mutate a `Team`/`Membership` record attributed to an organization that never authenticated the request.

### Finding Description
The binding the code implicitly assumes is:
`repository_owner (used to pick webhook_secret) == organization.login (used to attribute the Team/Membership row)`

Trace:
1. `verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to fetch the per-organization `GitHubApp`/`webhook_secret` via `Shipit.github(organization: repository_owner)`, then HMAC-verifies the raw body against that secret. [1](#0-0) [2](#0-1) 
2. The secret comparison itself is a correct constant-time HMAC-SHA1 check against `@webhook_secret` for whichever organization was resolved. [3](#0-2) 
3. `MembershipHandler#process` only ever reads `params.team.id/name/slug/url`, `params.organization.login`, and `params.member.login` from the same JSON body - it never reads `params.repository` at all - and uses `params.organization.login` to set `team.organization` and `params.team.id` as the lookup/creation key for `Team.find_or_create_by!`. [4](#0-3) 

Because `repository_owner` only falls back to `organization.login` when `repository` is *absent*, an attacker who includes a `repository.owner.login` field pointing at their own (legitimately configured) organization decouples secret selection from the `organization.login`/`team.id` values that `MembershipHandler` actually uses to write the row. `ExplicitParameters` schema in `MembershionHandler.params` only validates types/presence of `team`, `organization`, `member`, `action` - it does not cross-check against `repository_owner` or reject the presence of an unexpected `repository` key. Nothing in `drop_unhandled_event`, `check_if_ping`, or the schema enforces that the org used for verification matches the org named inside `team`/`organization`.

Exploit flow: attacker administers `attacker-org`, which is a real, Shipit-configured GitHub App/organization (attacker legitimately knows `attacker-org`'s own `webhook_secret`, as they configured it). They POST directly to `/webhooks` with header `X-Github-Event: membership` and a body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "x", "slug": "x", "url": "x"},
  "organization": {"login": "victim-org"},
  "repository": {"owner": {"login": "attacker-org"}},
  "member": {"login": "attacker"}
}
```
signed with `attacker-org`'s secret. `verify_signature` resolves `repository_owner` to `attacker-org`, verifies successfully against `attacker-org`'s secret, and lets the request through. `MembershipHandler#process` then creates/updates `Team.find_or_create_by!(github_id: 999)` with `organization = "victim-org"`, and adds `attacker` as a member of that team - a row now falsely attributed to `victim-org`, which never authenticated this request.

### Impact Explanation
The attacker causes a `Team`/`Membership` record to be created/mutated and attributed to an organization (`organization.login`) that did not authenticate the webhook - the verifying organization (`attacker-org`) and the attributed organization (`victim-org`) diverge, exactly matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." If the guessed/known `team.id` collides with a real team id referenced in `Shipit.github_teams` authorization configuration, this also becomes a path toward polluting membership records used for team-based authorization decisions (High: escalation into `Shipit.github_teams` authorization), since the attacker also controls `member.login` and can add arbitrary GitHub usernames (including their own) to the forged team. This is repeatable against any organization name/team id the attacker chooses, from any org they legitimately administer in Shipit.

### Likelihood Explanation
Precondition: attacker must administer at least one organization that is configured in Shipit as a GitHub App/organization with its own `webhook_secret` (a legitimate, low-privilege scenario multiple unrelated orgs can meet independently). No Shipit session, API token, or other org's secret is required. Cost is a single crafted HTTP POST with a valid signature computed from a secret the attacker already legitimately possesses for their own org. Fully repeatable and requires no live GitHub interaction to reproduce.

### Recommendation
In `MembershipHandler` (and any other handler keyed off `organization`/`team`), assert that `params.organization.login` equals the `repository_owner` value used for signature verification (or, better, pass `repository_owner` explicitly into the handler and require exact equality before writing any record). Reject the webhook (422) on mismatch rather than silently trusting attacker-supplied `organization`/`team` fields independent of the field used to select the verifying secret.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership event: verifying org and attributed org can diverge" do
  attacker_org = 'attacker-org'
  victim_org   = 'victim-org'

  payload = {
    action: 'added',
    team: { id: 999, name: 'x', slug: 'x', url: 'x' },
    organization: { login: victim_org },
    repository: { owner: { login: attacker_org } },
    member: { login: 'attacker' }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', Shipit.github(organization: attacker_org).send(:webhook_secret), payload)

  post :create, body: payload, params: {}, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => signature
  }

  assert_response :ok
  team = Shipit::Team.find_by(github_id: 999)
  # Verified org (signature) vs attributed org (record) diverge - both sides of the binding
  refute_equal attacker_org, team.organization
  assert_equal victim_org, team.organization
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
