### Title
Shared mutable joint cache corrupted by AA formula evaluation causes non-deterministic AA state (`formula/evaluation.js: 'unit' case`)

### Summary
The oscript `unit[...]` evaluator, reachable from any AA trigger sender or AA author's formula, retrieves a joint via `storage.readJoint` and then destructively mutates the returned object (`delete objUnit.actual_tps_fee`, `delete m.payload.data` for `temp_data` messages, `objectHash.cleanNulls(objUnit)`) before handing it to the formula as a `wrappedObject`. When the underlying joint comes from a shared, long-lived cache — `archiving.assocCachedPrunedJoints` (populated by `archiving.cachePrunedJoint` and served via `archiving.getCachedPrunedJoint`) — the mutation happens on the single shared object instance kept in the cache for up to `PRUNED_JOINT_CACHE_TTL_ms` (1 hour), not on a private copy.

### Finding Description [1](#0-0) 
shows the `'unit'` opcode: it calls `storage.readJoint(conn, unit, {...})`, and inside `ifFound` it mutates the joint's `objUnit` in place — `delete objUnit.actual_tps_fee`, `objectHash.cleanNulls(objUnit)`, and `delete m.payload.data` for `temp_data` messages — then wraps the *same, mutated* object reference (`new wrappedObject(objUnit)`), not a defensive clone (contrast with the `previous_aa_responses` case which explicitly does `string_utils.cloneDeep`, see [2](#0-1) ).

Separately, `archiving.js` maintains a shared, TTL-based cache of pruned/stripped joints: [3](#0-2) 
`cachePrunedJoint` stores the joint object as-is; `getCachedPrunedJoint` returns that same object reference to every caller for up to an hour.

If `storage.readJoint`'s fallback path for stripped/pruned units returns the object obtained from `archiving.getCachedPrunedJoint` (as its usage in `storage.js` around `updateMinRetrievableMciAfterStabilizingMci`, [4](#0-3) , suggests it is designed to be re-served), then the first oscript evaluation that reads such a unit via `unit[...]` will permanently strip `actual_tps_fee` and any `temp_data` payload from the *cached* object. Every subsequent, unrelated formula evaluation (by other AAs, other triggers, or other nodes with different cache warm-up timing) that reads the same unit afterward will see the already-mutated/stripped content instead of the original.

### Impact Explanation
Because AA formula execution must be perfectly deterministic across all full nodes for consensus to hold, and different nodes will have different cache states (first-reader-mutates-shared-object semantics depend on evaluation order/timing, not on protocol-defined data), nodes can compute different AA response units for the same trigger. This is a "node disagreement on validity" class impact: divergent AA response computation leads to divergent `response_unit` hashes, which can split the network's view of AA state and, in the worst case, of fund movements decided by the corrupted `temp_data`/`actual_tps_fee` fields.

### Likelihood Explanation
Reachability requires: (1) an AA (or nested/secondary AA) whose formula uses `unit[hash]` to read a unit that is a pruned/stripped `temp_data` unit or a voided unit that ends up served from `assocCachedPrunedJoints`, and (2) that this code path is actually reached from `storage.readJoint`'s pruned-content fallback rather than always re-querying the DB fresh. I could not fully confirm the exact wiring of `storage.readJoint`'s pruned-joint fallback within my remaining tool budget — the `readJoint` function body itself was not retrieved, only its existence and the `archiving.js` cache primitives it likely calls into. This is the main unresolved uncertainty.

### Recommendation
- Clone (`_.cloneDeep` / `string_utils.cloneDeep`) any joint object obtained from `storage.readJoint` before mutating it inside the `'unit'` formula opcode, matching the pattern already used for `previous_aa_responses`.
- Alternatively, make `archiving.cachePrunedJoint`/`getCachedPrunedJoint` store and return defensive copies so cached joints are never mutated by any consumer.
- Add a regression test that evaluates `unit[hash]` twice for the same pruned/`temp_data` unit from two different oscript contexts and asserts both reads return the original, unmutated payload.

### Proof of Concept
Conceptual (unverified end-to-end due to inability to trace the full `readJoint` pruned-content path in this session):
1. Post a unit containing a `temp_data` message; let it get pruned/stripped so it becomes eligible for `archiving.cachePrunedJoint` caching.
2. Post AA trigger #1 whose formula evaluates `unit[<that unit hash>]` — this deletes `payload.data` from the shared cached object.
3. Post AA trigger #2 (or have it evaluated on a node that hasn't warmed its cache yet) evaluating the same `unit[<hash>]` — on a node that already ran step 2, `trigger.data`/`payload.data` is missing; on a node that hasn't, it is present, producing different formula results and different response units for logically identical AA logic.

```javascript
// in-memory holdover of joints we just voided (stripped final-bad units), so that for a while after pruning
// we can still serve their full content to peers and recover from spends that raced the pruning locally
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}
```
