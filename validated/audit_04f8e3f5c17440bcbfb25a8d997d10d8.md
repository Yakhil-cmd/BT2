### Title
Membership webhook trusts `params.team.id` across organizations, letting an attacker-controlled org grant Shipit.github_teams membership on a victim org's Team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team.find_or_create_by!(github_id: params.team.id)` using only the numeric `team.id`, ignoring which organization actually verified the webhook signature. `WebhooksController#verify_signature` selects the verifying `GitHubApp`/secret using the attacker-supplied `organization.login` field of the payload, so in a multi-org Shipit deployment where any configured org has no `webhook_secret` (a documented, supported configuration), an attacker can forge a membership event for that org and cause `team.add_member(member)` to run against a Team row that belongs to a completely different, real organization.

### Finding Description
Binding claimed broken: `org whose webhook_secret verified the payload == org owning the Team object mutated by team.add_member`.

- `WebhooksController#verify_signature` computes `repository_owner` for the membership event as `params.dig('organization','login')` (there is no `repository` key in a membership payload) and calls `Shipit.github(organization: repository_owner)`. [1](#0-0) 
- In multi-org config, `Shipit.github` resolves the `GitHubApp` (and its `webhook_secret`) strictly by the attacker-supplied `organization` argument via `github_app_config(organization)`. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is unset — `return true unless webhook_secret` — a configuration explicitly shown as the default (`webhook_secret: # nil`) in `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, and `docs/setup.md`. [3](#0-2) 
- `MembershipHandler#process`/`#find_or_create_team!` then resolves the `Team` purely by `github_id`, with no check that `params.organization.login` matches the found team's `organization`: [4](#0-3) 
  Because `find_or_create_by!`'s block only runs on the `create` path (standard ActiveRecord semantics), when a Team with that `github_id` already exists (owned by a different, victim org), the block that would set `team.organization = params.organization.login` is never invoked — the existing victim `Team#organization`/`slug` are left untouched, but `team.add_member(member)` still executes against that record.
- `Team#add_member` simply appends the resolved `User` to `members` with no organization check. [5](#0-4) 
- `User#authorized?` grants access whenever the user belongs to any Team whose `id` is in `Shipit.github_teams`, which is populated from the `github.oauth.teams` config (organization/slug pairs resolved to Team rows independent of `github_id`). [6](#0-5) [7](#0-6) 

Exploit flow: attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, body `{"action":"added","team":{"id":<victim_team_github_id>,...},"organization":{"login":"attacker-org"},"member":{"login":"attacker-login"}}`. `attacker-org` must be one of the orgs configured under `Shipit`'s multi-org `github` secrets with no `webhook_secret`. Signature check passes unconditionally. The handler finds the existing victim `Team` row by `github_id` and calls `team.add_member(attacker_user)`, creating a real `Membership` row. If that Team's `id` is one of `Shipit.github_teams`, the attacker's `User#authorized?` now returns true.

Existing guards don't stop this: `drop_unhandled_event`/`check_if_ping` don't apply to `membership`; `ExplicitParameters` schema only enforces types (`Integer`, `String`), not cross-object consistency; there is no `require_permission!`/`force_github_authentication` in the webhook pipeline (webhooks are meant to be trusted purely via HMAC, and that HMAC selection is itself attacker-influenced through `organization.login`).

### Impact Explanation
An attacker who can send an arbitrary HTTP POST to `/webhooks` (no session, no token, not in `Shipit.github_teams`) can insert their own `User` into an arbitrary existing `Team` record by guessing/knowing its numeric `github_id`, as long as at least one org configured in Shipit's multi-org `github` secrets has no `webhook_secret`. If that Team backs an `oauth.teams` authorization entry, the attacker gains authenticated/authorized access to the whole Shipit instance (`User#authorized?` true) — this is an authorization escalation into `Shipit.github_teams`, matching the "High" impact category. It is repeatable against any Team `github_id` and does not require any secret; blast radius spans every org configured behind the same Shipit instance.

### Likelihood Explanation
Requires: (1) Shipit deployed in multi-org mode (`github_default_organization` present) with at least one configured org lacking `webhook_secret` — an explicitly documented/example configuration, not exotic; (2) an existing Team row whose `github_id` the attacker can supply (team IDs on GitHub are often discoverable, e.g. from prior public webhook deliveries, org team listing endpoints, or by small-integer enumeration); (3) that Team corresponds to (or shares an id with) one of the `oauth.teams` authorization-gating teams. Attacker cost is a single crafted HTTP POST with no credentials. Single-org deployments (the more common simple setup) are not exploitable this way because `Shipit.github` ignores the `organization:` argument in that mode and always uses the one real `webhook_secret`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if an existing Team with that `github_id` has a different `organization` than the verified webhook's org. Additionally, `WebhooksController#verify_signature` should not allow signature verification to silently succeed for orgs with a blank `webhook_secret` in multi-org configurations (require a secret to be configured for every org, or fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
Minitest plan (webhooks controller/handler test, no live GitHub):
1. Configure test secrets with two orgs: `victim-org` (has `webhook_secret`) and `attacker-org` (no `webhook_secret`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create fixture/record `Team.create!(github_id: 999, organization: 'victim-org', slug: 'engineering', name: 'Engineering')`, and stub `Shipit.github_teams` to include this team (simulating it being configured for OAuth authorization).
3. POST to `/webhooks` with `X-Github-Event: membership`, no valid `X-Hub-Signature` header, body:
   `{"action":"added","team":{"id":999,"name":"Engineering","slug":"engineering","url":"https://example.com"},"organization":{"login":"attacker-org"},"member":{"login":"attacker"}}`.
4. Assert response is `:ok`.
5. Assert `Team.find_by(github_id: 999).organization == 'victim-org'` (unchanged — proving the org binding is not what gates the mutation).
6. Assert `Team.find_by(github_id: 999).members.exists?(login: 'attacker')` (membership created).
7. Assert `User.find_by(login: 'attacker').authorized?` is `true` given the stubbed `Shipit.github_teams`, demonstrating escalation.
