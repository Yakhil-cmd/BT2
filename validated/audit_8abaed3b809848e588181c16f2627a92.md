### Title
Webhook signature verification is bound to an attacker-chosen organization while event handlers act on an unrelated repository/commit from the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a field read directly from the unauthenticated request body. Once the HMAC check passes, the full, unrestricted payload — including a `repository.full_name`/commit `sha` that can point to a completely different organization/repo than the one whose secret validated the signature — is dispatched to event handlers that mutate state (e.g. writing commit statuses). This breaks the binding "organization whose secret authenticated the request" == "repository/commit that gets written," analogous to the Sherlock M-4 report's mismatch between the field validated and the field acted upon.

### Finding Description
`verify_signature` first computes `repository_owner` from the (unverified) JSON body, then fetches the corresponding App config via `Shipit.github(organization: repository_owner)`, and only *then* checks the HMAC signature against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` merely recomputes `HMAC(webhook_secret_for_that_org, raw_body)` and compares it to the header, it never checks that the fields inside the body which the handlers actually use (e.g. `repository.full_name`, `sha`) belong to that same organization: [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps/organizations, each with its own independent `webhook_secret`, keyed by organization name: [4](#0-3) [5](#0-4) 

An attacker who is an admin of (or otherwise legitimately holds the webhook secret for) **one** configured organization's GitHub App knows that org's `webhook_secret` (they created it themselves, per the setup docs). They can then craft a raw JSON body whose `repository.owner.login`/`organization.login` is their own org (so `repository_owner` resolves to the org whose secret they know) while every other field in the same body — `repository.full_name`, `sha`, `state`, `target_url`, `description`, etc. — references a victim stack tracked under a different, unrelated organization. Because the HMAC is computed over the raw body with the secret selected from the attacker's own org, the signature check in `verify_signature` succeeds.

After that, `create` dispatches the entire payload (with the spoofed `repository`/commit fields) to `Shipit::Webhooks.for_event(event)` handlers unmodified: [6](#0-5) 

The status handler is a concrete example of a handler that writes state purely from the payload without any independent GitHub-side verification of the commit/repo ownership: the test fixture shows a `status` webhook payload merged with `repository_params` directly creates a `Status` on the commit identified by `sha`, with `state`, `description`, `target_url` taken verbatim from the attacker-controlled body: [7](#0-6) 

Nothing in this flow re-derives or re-checks that the commit/stack targeted by the handler actually belongs to the organization (`repository_owner`) whose secret validated the signature. The equality that should hold — `organization authenticated by webhook_secret == organization owning the repository/commit acted upon` — is not enforced anywhere between `verify_signature` and the handler dispatch in `create`.

### Impact Explanation
This allows a party with only one legitimate (self-owned) GitHub App/organization webhook secret configured in a multi-org Shipit deployment to forge signed-looking webhooks that mutate state belonging to an entirely different tracked organization/repository. Concretely, via the `status` event this can inject fabricated commit statuses (e.g. a fake "success") onto a victim stack's commits, which can influence Shipit's deploy-readiness/merge-queue checks and lead to an unauthorized deploy or merge of a commit that never actually passed CI — a cross-repository write that meets the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to control a legitimately configured GitHub App/organization entry in the same Shipit instance's multi-org `github` config (i.e., they know one organization's real `webhook_secret`), which is a realistic scenario for any Shipit instance hosting multiple orgs/teams with different trust levels but a shared install. No repository write access, admin session, or token theft is needed — only knowledge of one org's own webhook secret, which by design they legitimately possess.

### Recommendation
After a successful signature check, re-validate that every payload field the dispatched handler consumes (`repository.full_name`, `organization.login`, commit `sha` owner repo, etc.) is consistent with the `repository_owner`/organization that was used to select the `webhook_secret`. Reject the webhook if the acting handler's target repository does not belong to the same GitHub organization/App whose secret validated the HMAC.

### Proof of Concept
1. Deployment configures two GitHub Apps under `github:` — `attacker-org` (attacker is admin, knows its `webhook_secret`) and `victim-org` (hosts the tracked stack `victim-org/victim-repo`), per the multi-org config in `docs/setup.md`.
2. Attacker builds a `status` event JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "description": "forged",
     "target_url": "https://evil.example.com",
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `attacker-org` [2](#0-1) , fetches `attacker-org`'s app, and the signature check passes since the attacker signed with the correct (their own) secret [3](#0-2) .
5. `create` dispatches the full body (referencing `victim-org/victim-repo`) to the `status` handler, which writes a forged "success" status on the victim's commit [7](#0-6) , despite the request never being signed by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
