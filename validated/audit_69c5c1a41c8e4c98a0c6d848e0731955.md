### Title
Cross-repository webhook signature confusion allows an attacker's own GitHub App secret to authorize actions on a victim's Commit - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify against using `repository.owner.login` (or `organization.login`), while `Handler#stacks` (used by `CheckSuiteHandler#process`) resolves the target `Stack`/`Commit` using the independent `repository.full_name` field. Because these two fields are read from the same attacker-controlled JSON body but are never cross-checked, an attacker can sign a payload with their own organization's webhook secret while pointing `repository.full_name` at a victim repository, causing the victim's `Commit#schedule_refresh_check_runs!` to fire.

### Finding Description
The broken binding is: `repository_owner used to select verifying webhook_secret == repository.full_name used to select the target Stack/Commit`. This is FALSE in the code.

- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) .
- `CheckSuiteHandler#process` uses `stacks.where(branch: params.check_suite.head_branch)` and then `stack.commits.where(sha: ...).each(&:schedule_refresh_check_runs!)` [3](#0-2) .
- `stacks` (in the base `Handler`) is resolved via `Repository.from_github_repo_name(repository_name)&.stacks`, where `repository_name` is `payload.dig('repository', 'full_name')` — a completely separate JSON field from the one used in `verify_signature` [4](#0-3) .

Exploit flow: The attacker (who owns/controls a GitHub org with a Shipit-installed App, and therefore knows that org's `webhook_secret`) crafts a `check_suite` payload where `repository.owner.login`/`organization.login` = attacker's own org (so `verify_signature` picks the attacker's own `webhook_secret` and passes signature verification), but `repository.full_name` = the victim's repo (e.g. `"victim-org/victim-repo"`), and `check_suite.head_branch`/`check_suite.head_sha` match a real branch/commit of the victim's `Stack`. The attacker signs this payload with their own known secret via HMAC-SHA1 and POSTs it to `/webhooks`. `verify_signature` succeeds because it never checks that the org whose secret was used equals the org named in `repository.full_name`. `drop_unhandled_event` does not block `check_suite`, and the `ExplicitParameters` schema in `CheckSuiteHandler` only requires `head_sha`/`head_branch` types — it enforces no repository binding either [5](#0-4) . `CheckSuiteHandler#process` then resolves the victim's real `Stack`/`Commit` and calls `schedule_refresh_check_runs!` on it.

### Impact Explanation
The attack causes a mutation/side-effect (triggering `schedule_refresh_check_runs!`, which enqueues `RefreshCheckRunsJob` and performs GitHub API calls scoped to the victim's commit) that is attributable to a payload the attacker forged and self-signed for their own organization but targeting a different, victim repository's `Stack`/`Commit`. This matches the rules' explicit Critical bucket: "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any victim repository/stack/commit combination as long as the attacker can guess or observe a valid `head_branch`/`head_sha` pair (both are often public, e.g. via GitHub's public API or UI), and it works cross-tenant against any Shipit installation with more than one configured GitHub organization/App.

### Likelihood Explanation
Preconditions: the attacker must control a Shipit-registered GitHub organization/App (own their own org's `webhook_secret`), and must know a victim `Stack`'s tracked branch name and an existing `Commit#sha` on that branch — both typically public/discoverable information for open-source or even many private repos (branch names and SHAs are visible via GitHub UI/API to anyone with repo read access, and for public repos to anyone). No Shipit session, API token, or victim secret is required. The attack is a single unauthenticated HTTP POST to `/webhooks` and is fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#stacks`), enforce that the organization whose `webhook_secret` verified the request matches the organization actually referenced by `repository.full_name` used for resolving stacks. Concretely, derive `repository_owner` from the same field used for repository resolution (`repository.full_name`'s owner segment) instead of independently trusting `repository.owner.login`/`organization.login`, or explicitly compare the two and reject the request if they differ.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb` style, no live GitHub — stub `verify_webhook_signature` per org):

```ruby
test "check_suite payload verified under attacker org cannot refresh checks on a victim's commit" do
  victim_stack = shipit_stacks(:shipit) # e.g. repository full_name "Shopify/shipit-engine", branch "master"
  victim_commit = shipit_commits(:first) # belongs to victim_stack, sha known

  body = JSON.parse(payload(:check_suite_master))
  body["repository"]["full_name"] = victim_stack.repository.full_name # victim
  body["repository"]["owner"]["login"] = "attacker-org"               # attacker
  body["organization"]["login"] = "attacker-org"                      # attacker
  body["check_suite"]["head_branch"] = victim_stack.branch
  body["check_suite"]["head_sha"] = victim_commit.sha

  # attacker signs with their OWN org's known webhook_secret
  Shipit.github(organization: "attacker-org").expects(:verify_webhook_signature).returns(true)

  request.headers['X-Github-Event'] = 'check_suite'
  assert_enqueued_with(job: RefreshCheckRunsJob, args: [stack_id: victim_stack.id]) do
    post :create, body: body.to_json, as: :json
    assert_response :ok
  end
  # Assert the binding: attacker_org ("attacker-org") != victim_stack.repository.owner ("Shopify")
  refute_equal "attacker-org", victim_stack.repository.owner
end
```

This demonstrates that a signature verified under the attacker's own org's secret enqueues a job (`schedule_refresh_check_runs!` → `RefreshCheckRunsJob`) against the victim's `Stack`/`Commit`, confirming the binding failure without any live GitHub calls.
