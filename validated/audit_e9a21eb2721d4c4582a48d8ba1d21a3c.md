This confirms the mismatch: `WebhooksController#verify_signature` derives the signing organization from `repository_owner` — `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  — and validates the HMAC signature against that organization's `webhook_secret` via `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` [2](#0-1) . However, every downstream handler resolves the actual repository/stack to act on using a *different* payload field, `payload.dig('repository', 'full_name')` [3](#0-2) .

### Title
Webhook signature verification is bound to `repository.owner.login`, but repository resolution is bound to `repository.full_name` — organization authenticated ≠ repository written - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In a multi-organization Shipit deployment (multiple GitHub Apps/orgs each with their own `webhook_secret`, as documented in `config/secrets.development.shopify.yml`), the webhook signature check authenticates the sender as *some org* using `repository.owner.login`, but the handler that actually looks up and mutates the `Repository`/`Stack` state trusts a separate field, `repository.full_name`, which is never covered by that equality check.

### Finding Description
`WebhooksController#verify_signature` computes the organization to authenticate against solely from `repository_owner`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . It fetches that org's `GitHubApp` config and calls `verify_webhook_signature(signature, raw_body)`, which HMACs the *entire raw body* against that org's `webhook_secret` [4](#0-3) . This only proves "the request body, as a whole, was signed by whoever holds org X's webhook secret" — it does not bind any specific field of the JSON body (like `full_name`) to org X.

Once verification passes, `WebhooksController#create` dispatches to handlers with the raw parsed JSON [5](#0-4) , and `Handler#stacks`/`#repository_name` resolve the target `Repository` using `payload.dig('repository', 'full_name')` [3](#0-2) , not `repository.owner.login`. There is no code path anywhere that checks `full_name`'s owner segment matches `repository.owner.login` used at verification time.

This is precisely the analog of the reported bug class: the value the trust decision is made on (the field covered by the "signature", i.e. `owner.login`) differs from the value the resulting state-changing operation acts on (`full_name`). The report's IBC bug was "closed state acted on but not written to the committed/provable store"; here the equivalent equality that should hold — `organization used to authenticate == organization whose repository is written` — is not enforced.

### Impact Explanation
For this to be exploitable, an attacker needs write access to a repository (or org) that is itself configured as one of Shipit's GitHub Apps/orgs with a known/leaked webhook secret for *that* org, while crafting `repository.owner.login` to equal that org (so verification passes) and `repository.full_name` to reference a *different* org/repo that is also configured in this Shipit instance. Given the constraint that the attacker must already control a valid webhook secret for some org handled by this instance, and that Shipit's own multi-org docs indicate secrets are per-org and not attacker-known by default, this only escalates into cross-repository state changes (e.g. spoofed `push`, `status`, `check_suite`, `pull_request`, `membership` events) if a Shipit operator's org-to-secret mapping allows a signer for org A to forge payloads claiming to be for a repo of org B in the same instance. This does not itself leak `GITHUB_TOKEN` or achieve RCE, but it can drive unauthorized state transitions (e.g., fabricated `status`/`check_suite` events feeding merge/deploy readiness checks, or `membership` events adding users/teams) on a repository the signer does not control, which the rules classify as an authorization-boundary violation.

### Likelihood Explanation
Low-to-Medium. It requires the deployment to run more than one org's GitHub App/webhook secret (an explicitly documented multi-tenant configuration), and requires the attacker to already possess one valid org's webhook secret (which, per the rules, cannot be assumed to be already privileged access to *other* orgs). This is a real logic gap, but exploitability depends entirely on this multi-org configuration and a same-instance sibling org/repo existing, so it's not a per-installation universal issue.

### Recommendation
Bind the field actually used to resolve/act on the target repository to the field used for authentication. Concretely: after locating the org via `repository_owner`, re-validate that `payload.dig('repository', 'full_name')`'s owner segment (or `payload.dig('repository', 'owner', 'login')`) matches the same org before invoking `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create` [5](#0-4) , or have `Handler#repository_name` derive the repo strictly from the same owner field that was cryptographically verified, rejecting any mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` multi-org schema).
2. Attacker (who administers a webhook integration for `orgA`, hence knows `orgA`'s `webhook_secret`) crafts a `push` payload body: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/some-repo"}, ...}`.
3. Attacker signs the raw body with `orgA`'s `webhook_secret` and sets `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s `GitHubApp`, and successfully verifies the signature [2](#0-1) .
5. `create` dispatches to the `push` handler, which resolves `repository_name` = `"orgB/some-repo"` via `payload.dig('repository', 'full_name')` [6](#0-5)  and enqueues a `GithubSyncJob` / mutates state for `orgB`'s repository — despite the signature only proving knowledge of `orgA`'s secret.

*(Note: full exploitation depends on the multi-org secret configuration and the specific push/status/membership handler semantics; I was not able to fully enumerate every registered handler's exact side effects within the available search budget — a Devin session with full repo access could trace `Shipit::Webhooks::DEFAULT_HANDLERS` in `app/models/shipit/webhooks.rb` to confirm the exact blast radius per event type.)*
