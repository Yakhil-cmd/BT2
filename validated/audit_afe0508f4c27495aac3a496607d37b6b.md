### Title
Uniswap-like AA market-maker template lacks slippage/minimum-output protection, enabling sandwich attacks on liquidity provision and swaps - (test/samples/uniswap_like_market_maker.oscript)

### Summary
The reference Obyte AA market-maker template (`uniswap_like_market_maker.oscript`) computes liquidity-share issuance and swap output amounts purely from the AA's balance state *at trigger-processing time*, with no user-supplied minimum-output or minimum-shares parameter and no per-trade size cap. This is functionally identical to the reported `addLiquidity`/swap MEV issue: any unprivileged AA trigger sender can front-run a victim's `invest in MM` or `exchange` trigger with their own trigger(s) to shift the pool ratio, force the victim's trigger to execute at a manipulated price, and back-run to extract the difference.

### Finding Description
In the "invest in MM" case, the AA computes the expected counter-asset amount and the number of `mm_asset` shares to mint strictly from the *current* on-AA balances read when the trigger is processed: [1](#0-0) 

The expected ratio check (`bounce('wrong ratio of amounts...')`) only guarantees the depositor's own inputs match whatever ratio exists at execution time — it does nothing to guarantee that ratio reflects the ratio the user observed when they built and broadcast their trigger unit. The same is true for the swap cases, which compute output using the constant-product formula against live balances: [2](#0-1) [3](#0-2) 

AA triggers are ordinary units posted to the DAG by any address; they are executed by `aa_composer.js`'s `handleTrigger` in the order their carrying units become stable/ordered on the main chain, not in the order a user intends. An attacker (an unprivileged "AA trigger sender") can therefore post: (1) a large front-run swap trigger that shifts `balance[$asset]`/`balance[base]` unfavorably, (2) wait for the victim's `invest in MM` or `exchange` trigger to be processed against the now-skewed balances, and (3) post a back-run trigger reversing the price, capturing the value the victim lost — the classic sandwich pattern described in the source report, just expressed through AA state/balance reads instead of an EVM router's `addLiquidity`.

Unlike the discussion in the disputed report (where the Vader team argued that a max-trade-size cap of 25% per trade with a high fee is intended to make such attacks unprofitable), this ocore sample template has neither a maximum trade-size limit nor any fee parameter nor a caller-supplied minimum-output/minimum-shares guard, so there is no analogous protection here.

### Impact Explanation
A victim providing liquidity via "invest in MM" can be forced to mint fewer `mm_asset` shares than the ratio they intended, or to receive fewer output assets on `exchange bytes to asset` / `exchange asset to bytes`, than expected, while the sandwiching attacker profits from the price round-trip. This is a direct loss of user funds handled by the AA and is exploitable by any unprivileged trigger sender who can observe pending units for a target AA and post units around them — no special privilege, node compromise, or protocol-level defect is required, only ordinary DAG posting.

### Likelihood Explanation
Any address can post AA trigger units; nothing in the AA definition or in `aa_composer.js`'s trigger handling reorders or delays execution to prevent an attacker from bracketing a known pending trigger with their own units before it is processed. Because this file is shipped as the canonical example/reference implementation for building an AMM-style AA on Obyte, developers copying this pattern into production AAs would inherit the same exposure. The report's own PoC scenario (large trade before the victim, reversing trade after) maps one-to-one onto this template's balance-dependent pricing.

### Recommendation
Add a caller-supplied slippage-protection parameter to the `trigger.data` for both the "invest in MM" and "exchange" cases (e.g., `trigger.data.min_shares` / `trigger.data.min_amount`) and `bounce()` if the computed `$issue_amount` / `$amount` is below that threshold. Additionally, consider bounding the maximum fraction of pool balance that a single trigger may swap in one execution (mirroring the 25%-cap mitigation referenced in the disputed report) to reduce the profitability of single-block/sequential sandwich attacks.

### Proof of Concept
1. Pool AA holds `balance[$asset] = A`, `balance[base] = B`.
2. Attacker posts trigger 1: swap a large amount of bytes into the pool via the "exchange bytes to asset" case at [2](#0-1) , sharply reducing `$asset_balance` relative to `$bytes_balance`.
3. Victim's pre-broadcast "invest in MM" trigger (built assuming the pre-attack ratio) is processed next; the ratio check at line 44 forces the victim's deposit to match the now-skewed ratio, so the victim's `$issue_amount` at line 47 is computed against the manipulated balances, effectively depositing at a bad price.
4. Attacker posts trigger 3: reverse swap ("exchange asset to bytes", lines 124-144) restoring the balance and extracting the price difference as profit.
5. No mechanism in the AA (or in `aa_composer.js` trigger ordering) prevents this sequence or lets the victim specify an acceptable minimum share/output amount to abort the trigger if manipulated.
