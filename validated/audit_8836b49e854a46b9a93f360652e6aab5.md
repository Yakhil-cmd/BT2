### Title
Stack-scoped CCMenu token is minted without stack scoping, granting read access to all stacks - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` mints an `ApiClient` with `permissions: %w[read:stack]` but never assigns `stack: stack`, so the created/found record has `stack_id == nil`. Because `Api::BaseController#stacks` treats a `nil` `stack_id` as "not stack-scoped" and falls back to `Stack.all`, the token embedded in the returned `ccmenu_url` — designed to expose only one stack's CI status to an external CCMenu-compatible dashboard — actually grants read access to every stack in the installation to anyone who obtains that URL.

### Finding Description
The intended binding is: `token.stack == Stack A` (the stack the URL was requested for) so that `GET /api/stacks/:id/cc.xml` using that token is restricted to Stack A only.

Code path:
- `CCMenuUrlController#fetch` builds a URL with a token from `client.authentication_token` [1](#0-0) .
- `client` creates/finds the `ApiClient` with `permissions: %w[read:stack]`, but does not set `stack:` on `create_with`/`find_or_create_by!`, so `stack_id` is `nil` for every user (since the record is keyed only on `creator` and `name`, the *same* client is reused across all stacks that user requests a CCMenu URL for) [2](#0-1) .
- `Api::BaseController#stacks` resolves the readable scope from `current_api_client.stack_id?`; when `stack_id` is `nil`/falsy it returns `Stack.all` instead of a restricted set [3](#0-2) .
- `ApiClient` supports an optional `stack` association and only enforces coarse `permissions` (`read:stack`, `write:stack`, etc.) via `check_permissions!`, with no per-stack enforcement beyond the `stacks` scope built from `stack_id` [4](#0-3) .

Because `authenticate_api_client` only verifies the token's signature/existence via `ApiClient.authenticate` (Basic Auth over the API, no Shipit session required) [5](#0-4) , whoever holds the leaked/shared `ccmenu_url` — a URL explicitly designed to be embedded in external CI dashboards, status monitors, or public build badges without any Shipit session — can call `/api/stacks/:any_id/cc.xml` for *any* stack, not just the one it was generated for. This defeats the purpose of the stack-scoped CCMenu token: instead of leaking status of one stack, an inadvertent leak (screen share, public monitor, misconfigured public status page) exposes CI/deploy status of every stack across every team/repository in the Shipit instance.

No existing guard prevents this: `authenticate_api_client` only checks token validity, `require_permission!`/`check_permissions!` only checks the `read:stack` permission string (present on every such token), and the `stacks` method's fallback to `Stack.all` is exactly the divergence point — there is no code that ties the minted token back to the specific stack requested in `fetch`.

### Impact Explanation
Any holder of a leaked `ccmenu_url` (no Shipit session or additional credentials needed — just Basic Auth with the embedded token against the public API) can read CI/CD status (`cc.xml`), and depending on further `read:stack` scoped endpoints, other stack metadata, for **every** stack/repository/team in the Shipit instance, not just the one the URL nominally belongs to. This is a cross-tenant unauthenticated-read disclosure once a single CCMenu URL is leaked — repeatable indefinitely since the token doesn't expire and is reused/created once per user regardless of which stack requested it.

### Likelihood Explanation
Any authenticated Shipit user visiting `GET /stacks/:stack_id/ccmenu_url` for a stack they can see triggers creation of this over-broad token; this is a completely standard, intended use of the CCMenu feature (which exists precisely so third-party dashboards without Shipit accounts can poll build status), so an over-scoped token is minted on every ordinary usage, not just via attacker action. The only extra step needed for exploitation is that URL/token being exposed to an outside party (e.g., pasted into a public monitor, shared status page, or intercepted) — a realistic and expected scenario given the feature's purpose is external, unauthenticated consumption.

### Recommendation
Set the `stack` association explicitly when creating/finding the `ApiClient` in `CCMenuUrlController#client` (e.g., scope `find_or_create_by!` on `creator`, `name`, and `stack: stack`, and pass `stack: stack` into `create_with`), and ensure `Api::BaseController#stacks` (and equivalent authorization checks) reject requests when the token's `stack_id` doesn't match the requested stack.

### Proof of Concept
```ruby
test "ccmenu client token is scoped to the requested stack only" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse)
  user = shipit_users(:walrus)

  # simulate CCMenuUrlController#client for stack A
  client = Shipit::ApiClient.create_with(permissions: %w[read:stack])
                              .find_or_create_by!(creator: user, name: 'CCMenu Client')

  assert_nil client.stack_id, "token minted for stack A has no stack scoping"

  # Api::BaseController#stacks fallback
  stacks_scope = client.stack_id? ? Shipit::Stack.where(id: client.stack_id) : Shipit::Stack.all
  assert_includes stacks_scope, stack_b, "token minted for stack A can read stack B"
end
```
This demonstrates both sides of the equality (`token.stack_id` vs. the intended scope of Stack A) diverge, and that the resulting `stacks` scope includes an unrelated stack B.
