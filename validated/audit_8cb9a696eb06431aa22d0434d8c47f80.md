### Title
Null-pointer-style crash in `attestation()` oscript evaluation via missing mandatory params - (File: formula/evaluation.js)

### Summary
The `attestation` operator handler in the oscript evaluation engine dereferences `.value` on `params.attestors` and `params.address` without first checking that these keys exist on the evaluated-params object, unlike other optional params in the same block (`ifseveral`, `type`) which are explicitly guarded with `if (params.xxx)` before access.

### Finding Description
In the `attestation` case of `evaluate()`, once all supplied params are evaluated into `evaluated_params`, the code proceeds to: [1](#0-0) 
```
params = evaluated_params;
if (typeof params.attestors.value !== 'string')
    return setFatalError('attestors is not a string', { arr }, false, cb);
...
var v = params.address.value;
if (!ValidationUtils.isValidAddress(v))
    return setFatalError('bad address in attestation: ' + v, { arr }, false, cb);
```
`params.attestors` and `params.address` are accessed unconditionally, whereas `ifseveral` and `type` in the very same block are guarded (`if (params.ifseveral) { ... }`, `if (params.type) { ... }`) before their `.value` is read: [2](#0-1) 

If an AA definition contains an `attestation()` call in which the `attestors` or `address` named parameter is omitted (which the oscript grammar allows syntactically, since named params in this construct are supplied as an object literal that is not enforced to contain every key), `evaluated_params.attestors` or `evaluated_params.address` will be `undefined` at evaluation time, and `params.attestors.value` / `params.address.value` throws a synchronous `TypeError: Cannot read properties of undefined`. This mirrors the libsoup bug class: a value is dereferenced without a null/existence check on a code path parsing externally-supplied structured input (here, an oscript formula supplied inside an AA definition).

This is directly analogous to the reported libsoup CVE-2025-4476 bug class (missing null check on a header-derived field leading to a crash during response processing) — except the "malformed input" is the AA's `attestation()` invocation lacking required keys, processed automatically by every node evaluating the AA whenever it is triggered.

### Impact Explanation
The oscript evaluator runs inside the AA-trigger validation/response path used by every full node when an AA is triggered by any user's payment/data message. Since `evaluate()` executes inside `async.eachSeries` callback chains, an uncaught `TypeError` thrown outside of a `try/catch` boundary is not converted into a `setFatalError`/bounce result — it propagates as an unhandled JS exception. Depending on how the surrounding AA-trigger-processing caller (`aa_composer.js`) handles exceptions in these deep callbacks, this can crash the Node.js process handling AA execution, which is a network-wide denial-of-service: any node processing this AA's trigger unit would hit the same deterministic crash, preventing the network from confirming/bouncing units that trigger this AA.

### Likelihood Explanation
Reaching this path requires an unprivileged AA author to post an AA definition using `attestation()` without the `address` (or `attestors`) key, and any unprivileged trigger sender to subsequently trigger that AA. Whether this is actually exploitable depends on whether `formula/validation.js`'s AA-definition-time validation for the `attestation` operator already enforces the presence of `address`/`attestors` as mandatory keys before allowing the AA to be posted — I was not able to fully confirm the content of that validation block within the available tool budget (grep only located references, not full content). If `formula/validation.js` does NOT enforce mandatory presence of these keys (mirroring the asymmetric guard pattern seen in `evaluation.js`), the bug is directly and easily triggerable by any user; if it does enforce it, this specific path is not reachable and the finding would be moot.

### Recommendation
In `formula/evaluation.js`, add explicit existence checks (`if (!params.attestors) return setFatalError(...)`; `if (!params.address) return setFatalError(...)`) before dereferencing `.value`, consistent with the guards already used for `ifseveral` and `type` in the same block. Additionally, audit `formula/validation.js`'s `attestation` validator to confirm it rejects AA definitions where `address`/`attestors` are absent, closing the gap at definition-time as defense in depth.

### Proof of Concept
1. Post an AA definition containing a message whose formula includes:
```
attestation({attestors: 'ATTESTOR_ADDRESS'}, 'field')
```
omitting the `address` parameter (assuming grammar/definition-time validation does not reject this).
2. Trigger the AA with any unit.
3. During evaluation, `evaluated_params.address` is `undefined`, so `params.address.value` throws `TypeError: Cannot read properties of undefined (reading 'value')`, propagating as an unhandled exception in the async evaluation chain — crashing the process of every node that evaluates this trigger.

Note: This finding's exploitability hinges on the AA-definition-time validator in `formula/validation.js` not already rejecting missing `address`/`attestors` params; I was unable to fully verify that file's logic within the available investigation, so this should be confirmed by an engineer with direct file access before treating it as a confirmed exploitable vulnerability.
