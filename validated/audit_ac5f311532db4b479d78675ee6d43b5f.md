### Title
Webhook signature verified against `repository.owner.login`'s secret while handlers act on unrelated `repository.full_name` / global commit `sha` — cross-repository status/stack forgery when any tenant org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC secret) to validate a webhook against using only the `repository.owner.login` (or `organization.login`) field taken from the *same untrusted JSON body* it is about to authenticate. The handlers that then execute the request, however, key their side effects on a different, unrelated field of that same body — `repository.full_name` for stack lookup, or, in `StatusHandler`, nothing at all (a bare `sha` lookup across every `Commit` in the instance). Because `GitHubApp#verify_webhook_signature` explicitly returns `true` when no `webhook_secret` is configured for the selected organization, any multi-tenant Shipit deployment that has at least one organization configured without a webhook secret (documented as "optional" in `docs/setup.md`) allows an unauthenticated attacker to submit a forged webhook whose `repository.owner.login` matches the unprotected org (to sail through `verify_signature`) while every other field — including `repository.full_name` (used by `PushHandler`/`Handler#stacks`) or `sha` (used by `StatusHandler`) — targets a completely different, secret-protected organization's repository/stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

`repository_owner` is read straight from the same JSON payload: [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially passes when the selected org has no secret configured: [3](#0-2) 

and `docs/setup.md` documents the webhook secret as optional:
`"Webhook secret (optional): Fill it with some randomly generated string..."`

Meanwhile, the handlers that consume the body use a *different* payload field, not the one used to select/verify the secret:

`Handler#stacks`/`#repository_name` resolves the target repository purely from `repository.full_name`: [4](#0-3) 

`PushHandler#process` uses that unscoped `stacks` lookup to trigger a real GitHub sync against whatever stack matches `full_name`: [5](#0-4) 

`StatusHandler#process` is even weaker — it does not consult `repository` at all and matches commits globally by `sha` across the entire Shipit instance: [6](#0-5) 

The binding that should hold is: *the organization whose secret validated the signature* == *the organization owning the repository/stack the handler mutates*. Before the attacker's request, this equality holds for legitimate GitHub-originated webhooks because GitHub itself only signs a payload with the secret of the installation that actually owns the event's repository. After the attacker's forged request, the equality is broken: `repository_owner` (used only for secret selection) can name an org with no secret at all (bypassing verification unconditionally), while the operative fields (`repository.full_name` in `PushHandler`, or the global `sha` in `StatusHandler`) name a target belonging to a different, secret-protected organization/stack.

### Impact Explanation
This crosses the "organization authenticated versus repository that is written" trust boundary explicitly in scope. Concretely:
- Via `StatusHandler`, an unauthenticated attacker can forge a `status` webhook (`event=status`) with `repository.owner.login` set to any org configured with a blank `webhook_secret`, and `sha` equal to a commit SHA belonging to a *different, protected* stack. `Commit.create_status_from_github!` will then write an attacker-chosen `state`/`context`/`description` onto that commit. If that stack gates deploys on required commit statuses (`deployable_status`), this lets an attacker mark an otherwise-failing/untested commit as `success`, directly enabling an **unauthorized deploy** on a repository the attacker does not control and never authenticated against.
- Via `PushHandler`, the same org-secret bypass lets the attacker trigger `GithubSyncJob` against an arbitrary tracked stack (`repository.full_name`-driven), forcing unplanned resyncs against repositories outside the attacker's authorized org.

### Likelihood Explanation
Likelihood is conditioned on the (documented, first-class) deployment configuration where a Shipit instance serves multiple GitHub organizations and at least one of them has no webhook secret set — the setup guide explicitly calls the secret "optional," and the shipped `config/secrets.development.shopify.yml` template ships multiple orgs each with `webhook_secret: # nil`. Any such instance is exploitable by a fully unauthenticated network attacker with zero GitHub credentials, no `ApiClient` token, and no repository access — only knowledge (or a guess) of another tracked stack's commit SHA or repository `full_name`.

### Recommendation
Bind the field used to select/verify the signing secret to the same field(s) the handler acts on: derive the org for verification from `repository.full_name`'s owner (not a separately-trusted `repository.owner.login`), and additionally scope `StatusHandler` (and any other handler) to the repository named in the payload rather than performing an unscoped, cross-tenant `Commit.where(sha:)` lookup. Also consider making `webhook_secret` mandatory (or refusing "trivially verified" webhooks against other orgs' payload fields) so that an org without a secret cannot be used as a lever to forge events for other tenants.

### Proof of Concept
1. Deploy Shipit configured for two orgs, e.g. `orgA` (no `webhook_secret`) and `orgB` (has a `webhook_secret`), each with tracked stacks/commits, as in the shipped template `config/secrets.development.shopify.yml`.
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # irrelevant, orgA has no secret

{
  "sha": "<commit sha belonging to orgB's protected stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/whatever" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")` → `verify_webhook_signature` returns `true` unconditionally (no secret configured) — see `lib/shipit/github_app.rb:76-83`.
4. `StatusHandler#process` runs unmodified and writes the forged `success` status onto the commit belonging to `orgB`'s stack — see `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — enabling deploy gating bypass on a repository never authenticated by this request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
