### Title
Signature verification is keyed off an attacker-controlled organization field that is never bound to the repository actually written by webhook handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` picks *which* GitHub App/secret to validate an incoming webhook against using an org name pulled straight out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a value taken from the same JSON body whose authenticity is what the HMAC check is supposed to establish. `Shipit.github(organization: repository_owner)` looks up the `GitHubApp` config for that org and calls `verify_webhook_signature`: [3](#0-2) 

Critically, if that org's `webhook_secret` is blank (which the setup docs and generated templates explicitly show as the default/optional value for every org, including in multi-org configs), `verify_webhook_signature` returns `true` unconditionally, regardless of the `X-Hub-Signature` header or payload contents: [4](#0-3) [5](#0-4) [6](#0-5) 

After `verify_signature` passes (trivially, for the secret-less org), `WebhooksController#create` dispatches the *entire* raw payload to handlers: [7](#0-6) 

Every handler resolves the actual `Repository`/`Stack` to mutate from a **completely different JSON path** — `repository.full_name` — never re-checked against `repository.owner.login`: [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10) 

This is the same class of bug as the referenced `BathToken.initialize()` finding: a security-critical binding (which principal is trusted) is established from one piece of untrusted state (`repository.owner.login`, used to pick the verifying secret), while the actual state-changing operation is driven by a *different* piece of untrusted state (`repository.full_name`) that is never checked for equality against the first. In the Rubicon report the binding that should have held (but didn't) was "the token that re-entered `initialize` == the token actually deployed as the pool's underlying asset." Here the binding that should hold (but doesn't) is:

`organization whose secret verified the signature == organization that owns the repository the handler writes to`

### Impact Explanation
In a multi-organization Shipit deployment (the schema documented in `docs/setup.md` "Using Multiple Github Applications"), if **any single org** in the shared config has no `webhook_secret` configured — a state explicitly presented as valid/"optional" in the docs and default templates — an unauthenticated attacker can:

1. Craft an arbitrary JSON body with `repository.owner.login` set to that secret-less org (any signature or none passes verification for that org).
2. Set `repository.full_name` to `OtherOrg/some-repo`, where `OtherOrg` is a **different, properly-secured** org whose stacks are hosted in the same Shipit instance.
3. Send it to `/webhooks` with the matching `X-Github-Event` header.

Because handlers only look at `repository.full_name` (never re-validating it against the org that satisfied `verify_signature`), the attacker can inject forged events for stacks belonging to `OtherOrg` despite never possessing `OtherOrg`'s webhook secret:
- `push` → triggers `stack.sync_github` with an attacker-chosen `expected_head_sha`, which can advance `next_commit_to_deploy` state and, combined with continuous deployment, lead to an unauthorized deploy of an attacker-influenced commit.
- `status` → forges CI/commit status (`create_status_from_github!`) for arbitrary commits, which can unblock deploy gating checks (`deployable?`) that continuous delivery relies on.
- `check_suite` → forges check-run refresh triggers.

This is a cross-repository/cross-organization authentication-bypass: the trust check ("who signed this") is decoupled from the object of the write ("whose repo is this for"), exactly matching the "organization that authenticated versus the repository that is written" binding this scan targets. It qualifies as High impact (escalation/unauthorized effect on stack state across organizational boundaries via a boundary the app is supposed to enforce) without requiring a Shipit session, API token, or the target org's own webhook secret.

### Likelihood Explanation
Requires only: (a) a multi-org Shipit deployment (an officially documented and supported configuration), and (b) at least one configured org without a `webhook_secret` — a state the setup docs describe as optional and which appears as the default (blank) value in every generated secrets template, including the multi-org example. No credentials, GitHub App keys, or the victim org's secret are needed; the attacker only needs to know (or guess) the name of any org configured on the instance that lacks a secret, and the `full_name`/stack identifiers of the target org's repositories, both of which are typically public information (GitHub org/repo names, visible in Shipit's own public stack list UI).

### Recommendation
Do not let a payload-derived organization value select the verification secret that is then trusted for a completely separate payload-derived write target. Concretely:
- After (or as part of) `verify_signature`, re-derive the repository/stack target strictly from data scoped to the organization that was actually verified, and reject the webhook if `repository.full_name`'s owner segment does not match `repository_owner` used for verification.
- Alternatively, verify the signature using a lookup keyed by the resolved `Repository`/`Stack` record (and its associated org) rather than a raw string taken from the unauthenticated body.
- Consider requiring `webhook_secret` to be present for every configured org (fail closed / raise a configuration error at boot if any org's secret is blank) so a single unsecured org can't become a skeleton key for the rest of the instance.

### Proof of Concept
Given a Shipit instance configured with multiple GitHub orgs where `OrgA` has no `webhook_secret` set (per `docs/setup.md`'s documented optional/blank default) and `OrgB` is a properly secured org with a real stack `OrgB/prod-app`:

```bash
curl -X POST https://shipit.example.com/webhooks \
  -H 'X-Github-Event: push' \
  -H 'Content-Type: application/json' \
  -d '{
    "ref": "refs/heads/master",
    "after": "<attacker-chosen-sha-already-pushed-to-OrgB-repo>",
    "repository": {
      "owner": { "login": "OrgA" },
      "full_name": "OrgB/prod-app"
    }
  }'
```

- `WebhooksController#repository_owner` → `"OrgA"`.
- `Shipit.github(organization: "OrgA").verify_webhook_signature(...)` → returns `true` immediately because `OrgA`'s `webhook_secret` is blank (no signature required at all).
- `create` dispatches to `Shipit::Webhooks.for_event('push')`, i.e. `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/prod-app")` (per `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s real stacks — despite the request never being authenticated by `OrgB`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
