## Analog Found: Async Uncaught Exception in Device Message Decryption Crashes the Entire Node

### Title
Malformed device message triggers an async uncaught exception that permanently crashes the node - (File: device.js)

### Summary
`decryptPackage()` in `device.js` deliberately throws an `Error` from inside a `setTimeout` callback when it receives a device message encrypted to an unrecognized key. Because this throw happens asynchronously (outside the calling stack), it escapes every local `try/catch` wrapper and is caught only by the global `process.on('uncaughtException', ...)` handler in `network.js`, which explicitly re-throws to kill the process. Any device — including one that is not a correspondent — can trigger this by sending a message addressed to a known/guessable device address with a bogus `dh.recipient_ephemeral_pubkey`, permanently crashing the target node until manually restarted. This mirrors the CL-2020-08 pattern: a single malformed inbound message causes an unrecoverable process crash via an unhandled/mis-handled error path.

### Finding Description
When a `hub/message` justsaying is received, `handleJustsaying` in `device.js` verifies the message hash/signature and then calls `decryptPackage` before ever checking whether the sender is a known correspondent: [1](#0-0) 

Inside `decryptPackage`, if the `recipient_ephemeral_pubkey` doesn't match the current temp key, previous temp key, or permanent key, the code schedules a deferred throw and returns `null`: [2](#0-1) 

Because `setTimeout(() => { throw Error(...) }, 100)` executes on a fresh stack, the surrounding synchronous `try { doHandle() } catch (e) { ... }` guard in `wallet.js`'s `handleMessageFromHub` (and the analogous guard around `handleJustsaying` calls) cannot catch it: [3](#0-2) 

The exception is instead caught only by the process-wide handler in `network.js`, which explicitly re-throws to crash the process: [4](#0-3) 

### Impact Explanation
Any counterparty capable of addressing a device message to the victim's device address (a value that is routinely shared during pairing/correspondence setup and is not secret) can force this unhandled path. The result is an unconditional, unrecoverable crash of the entire ocore process — hub, wallet, or full node — not merely a dropped connection. This matches the "High" severity DoS in the analog report: a single malformed message permanently disables the target's ability to process protocol messages until an operator manually restarts it.

### Likelihood Explanation
Reaching this path requires only: (1) knowledge of the victim's public device address, (2) producing a validly self-signed `objDeviceMessage` (attacker signs with their own keypair, so this is trivial), and (3) setting `encrypted_package.dh.recipient_ephemeral_pubkey` to any value that does not match the victim's temp/prev-temp/permanent public keys. All of these are within reach of any peer/device able to deliver a message to the victim's hub, with no special privilege, correspondence pairing, or race condition required.

### Recommendation
Do not throw asynchronously from inside `decryptPackage`. Replace the `setTimeout(() => { throw ... }, 100)` with a synchronous return of an error/null plus a call to `eventBus.emit('nonfatal_error', ...)` (the commented-out line right below already suggests this safer alternative), so that the caller's error-handling path (`respondWithError`) can process it without ever reaching the global `uncaughtException` handler. More broadly, review other deferred/async throws in the message-handling paths to ensure malformed peer/device input cannot escape local error handling and hit the fatal process-crashing handler in `network.js`.

### Proof of Concept
1. Obtain the victim's device address (public, typically shared for pairing).
2. Craft a `hub/message` payload where `objDeviceMessage.pubkey`/`signature` are self-consistent (attacker generates their own keypair and signs), `to` equals the victim's device address, and `encrypted_package.dh.recipient_ephemeral_pubkey` is set to an arbitrary/random base64 string that cannot match any of the victim's known keys.
3. Deliver this via `hub/deliver` to the hub serving the victim, or directly send `hub/message` if you control/are the hub.
4. On the victim node, `decryptPackage` reaches the `else` branch and schedules `setTimeout(() => { throw Error("message encrypted to unknown key...") }, 100)`.
5. 100ms later, the deferred throw fires outside any try/catch, hits `process.on('uncaughtException', ...)` in `network.js`, which logs and re-throws, terminating the node process.
