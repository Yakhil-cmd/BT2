### Title
Webhook signature verification is keyed to attacker-controlled `repository.owner.login`/`organization.login`, decoupling the authenticated GitHub organization from the repository/team actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate a webhook against using a value taken directly from the unauthenticated request body. The handler that subsequently mutates state (`Repository`, `Stack`, `Commit`, `Team`, `User`) resolves the target purely from other fields of that same attacker-controlled body (`repository.full_name`). Nothing binds "the organization whose secret validated this request" to "the repository/organization actually written to."

### Finding Description
`verify_signature` computes the organization used to pick the webhook secret solely from the JSON payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` is used to fetch the `GitHubApp` whose `webhook_secret` verifies the HMAC signature: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank/nil for that organization: `return true unless webhook_secret`. Per Shipit's own multi-org documentation and shipped example configs, `webhook_secret` is explicitly optional per-organization: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (bypassed by choosing an org with no secret configured), `create` parses the *same raw body* and dispatches it to event handlers: [6](#0-5) 

Handlers resolve the actual repository/stack to mutate from `repository.full_name`, a field never covered by the org-scoped check performed above: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

**Binding broken (equality that should hold but doesn't):**
`organization used to select/verify webhook_secret (repository.owner.login / organization.login)` == `organization/repository that handlers actually mutate (repository.full_name / organization.login in payload body)`

Before the attack: an operator configures a multi-org Shipit instance (as documented) where OrgA (low-value/test org) has `webhook_secret: nil` and OrgB (the real target, e.g. holding production stacks) has a properly configured secret. The intent is that only genuine, HMAC-signed GitHub events for OrgB can mutate OrgB's stacks/commits/teams.

After the attacker's request: an unauthenticated POST to `/webhooks` sets `repository.owner.login` (or `organization.login`) to `OrgA` — causing `Shipit.github(organization: 'OrgA')` to be selected, whose `verify_webhook_signature` trivially returns `true` because `webhook_secret` is blank — while every other field in the same payload (`repository.full_name`, `sha`, `team`, `member.login`, etc.) freely references OrgB's repositories/teams/commits. `verify_signature` never re-checks that the org used for verification matches the org actually being written to.

### Impact Explanation
This allows an unauthenticated attacker to forge arbitrary GitHub webhook events against any repository/organization configured on the instance, as long as at least one configured organization has no (or a leaked) webhook secret — a state the product's own setup docs describe as optional/acceptable. Concrete cross-repository writes achievable through existing handlers, without any credential:
- `PushHandler` → enqueues `GithubSyncJob` for any stack matching an attacker-chosen `ref`/`full_name`, causing the app to fetch and ingest commits under the (real) GitHub identity/token of a *different* configured org's GitHub App.
- `StatusHandler` → creates arbitrary commit statuses (`create_status_from_github!`) on any commit by SHA, independent of which org it belongs to, which can gate/unblock deploy safety checks.
- `MembershipHandler` → creates/deletes `Team` membership records and creates arbitrary `User` records for any `organization.login`/`team.id` supplied, affecting `Shipit.github_teams` authorization used elsewhere in the app.
- `CheckSuiteHandler` → schedules check-run refresh for arbitrary stacks/commits.

This is a cross-repository write / authorization-boundary bypass reachable with zero credentials, matching Critical ("cross-repository writes") / High ("escalation into `Shipit.github_teams` authorization") impact criteria.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: it requires the operator to run the documented multi-organization setup where at least one configured org's `webhook_secret` is left blank (explicitly presented as an acceptable/optional configuration in `docs/setup.md` and the shipped example/test configs) or where a secret otherwise leaks/weakens. Any instance meeting that documented configuration pattern is exploitable by a fully unauthenticated network attacker, with no rate limiting or additional gating on `/webhooks`.

### Recommendation
- Verify that the organization whose `webhook_secret` validated the signature is the same organization that owns the resource(s) the event handler is about to mutate (e.g., assert `Repository.from_github_repo_name(repository.full_name).owner == repository_owner` before dispatch, or resolve `repository_owner` strictly from the already-resolved, DB-known repository rather than trusting the raw payload for secret selection).
- Do not allow a single org’s missing/blank `webhook_secret` to short-circuit verification for events whose payload claims to touch a different org’s resources.
- Consider requiring a non-blank `webhook_secret` for every configured organization in multi-org mode, or bind the accepted-and-verified org to the handler’s resolved repository/org before any write occurs.

### Proof of Concept
Given a `secrets.yml` (multi-org form) where:
```yaml
github:
  OrgA:
    webhook_secret: # nil (per docs/setup.md, this is optional)
  OrgB:
    webhook_secret: "s3cr3t-for-real-org"
```
1. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/production-app" }
}
```
2. `verify_signature` calls `Shipit.github(organization: 'OrgA')`; `verify_webhook_signature` returns `true` immediately (`webhook_secret` blank for OrgA) regardless of the (missing/invalid) `X-Hub-Signature` header — [11](#0-10) .
3. `create` parses the body and dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("OrgB/production-app")` — [7](#0-6)  — and triggers `GithubSyncJob` against OrgB's stack, entirely bypassing OrgB's configured webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
