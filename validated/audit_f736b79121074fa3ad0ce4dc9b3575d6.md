### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables blocking-status bypass — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` with no check that the webhook's `repository.full_name` matches the commit's stack's repository, unlike every other handler which scopes work through `stacks` (derived from `payload.dig('repository', 'full_name')`). An attacker who knows (or controls) a commit sha that also exists in `victim/prod`'s commit table — trivial for public repos, or achievable by referencing/forking a commit shared across repos — can send a `status` webhook from their own repository and flip the state of the victim's commit, defeating `Commit#blocking?`/`Stack#blocking_statuses` and unblocking deploys.

### Finding Description
Broken binding: the code should enforce `status.repository.full_name == commit.stack.repository.full_name` before mutating `commit.statuses`, but it enforces nothing of the sort.

`app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit#sha` is unique only per-`stack_id` (each `Commit belongs_to :stack`, `app/models/shipit/commit.rb:11`), not globally, so the same sha string can legitimately belong to commits owned by different stacks/repositories (e.g. shared history, cherry-picks, or an attacker simply naming a `sha` param equal to a known victim commit sha — the webhook payload's `sha` field is attacker-supplied JSON, not cryptographically tied to the `repository` field). All other handlers (`push_handler.rb`, `check_suite_handler.rb`, `pull_request/*`) route through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` before touching any record — `status_handler.rb` conspicuously does not use `stacks` at all.

`GithubHook#verify_signature` (in `webhooks_controller.rb`) only proves the payload came from a GitHub account with the shared webhook secret configured for the *sender's own* repo — it does not, and cannot, prove that the `sha`/`repository` values inside the JSON body correspond to reality. Once past signature check, `drop_unhandled_event`/`ExplicitParameters` only validate types/presence of `sha`, `state`, `context`, etc., not their relationship to the `repository` field (which `StatusHandler`'s param schema doesn't even declare/consume for scoping).

Exploit flow: attacker configures a webhook on any repository they control (or simply POSTs directly to `/webhooks` if `GithubHook.verify_signature` accepts their own repo's valid signature/secret from a repo they administer), with `X-Github-Event: status` and body `{"sha": "<victim commit sha>", "state": "success", "context": "ci/blocking", "repository": {"full_name": "attacker/anything"}}`. `StatusHandler.process` finds `Commit.where(sha: ...)`, which returns the victim's row in `victim/prod`, and calls `commit.create_status_from_github!(params)` → `Status#replicate_from_github!` writes a new `success` status row scoped to `commit.stack_id` (the victim stack). This flips `Commit#blocking?` to false for that commit, which flips `Commit#blocked?` for all later undeployed commits in `victim/prod` (`app/models/shipit/commit.rb:231-237`, `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`), making them `deployable?` and letting `Stack#trigger_continuous_delivery` proceed to deploy commits that were previously safety-blocked.

### Impact Explanation
This is an authentication/authorization-binding bypass: a status update meant to represent CI result on `victim/prod`'s own commit gets forged by an unrelated party, causing `victim/prod` to bypass its own configured blocking-CI safety gate and trigger an unauthorized deploy of code that had not actually passed CI. This matches "a payload for one repository mutating another's stack/commit" and "an unauthorized deploy" — Critical severity. The primitive is fully repeatable against any stack/commit whose sha the attacker can name, and the attacker only needs the victim's commit sha (which is public information for public repos, or can be observed via any means that reveal commit hashes, e.g. PRs, forks, CI logs).

### Likelihood Explanation
Preconditions: `victim/prod` must have a `deploy_spec` with `ci.blocking` contexts configured (a normal, documented Shipit feature), and there must exist an undeployed blocking-pending commit followed by later undeployed commits — an ordinary steady-state condition. Attacker cost is low: they need no Shipit credentials, no GitHub write access to `victim/prod`, just knowledge of a target commit sha and the ability to send a validly-signed `status` webhook from a repository they control (standard GitHub feature available to any repo owner) or a bare POST to `/webhooks` if signature verification is bypassable/absent for their setup. This is directly repeatable per commit/per stack.

### Recommendation
In `StatusHandler#process`, verify the resolved commit's stack repository matches the webhook's `repository.full_name` before calling `create_status_from_github!` — e.g., scope through `stacks` (as other handlers do) and filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, rejecting/ignoring statuses whose sha resolves to a commit in a stack not owned by the reporting repository.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new or extended)
test "status webhook from a foreign repository cannot unblock another stack's commits" do
  victim_stack = shipit_stacks(:shipit) # repo "shopify/shipit-engine" per fixtures
  blocking_commit = shipit_commits(:first)
  later_commit    = shipit_commits(:second) # newer, undeployed

  # Precondition: blocking status pending -> later_commit is blocked
  blocking_commit.statuses.create!(stack_id: victim_stack.id, state: 'pending', context: 'ci/blocking')
  victim_stack.stubs(:blocking_statuses).returns(['ci/blocking'])
  refute later_commit.deployable?, "sanity: should be blocked before forged status"

  # Attacker forges a status webhook claiming to be from a different repository,
  # but naming the victim's commit sha.
  forged_payload = {
    'sha' => blocking_commit.sha,
    'state' => 'success',
    'context' => 'ci/blocking',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  assert_equal 'success', blocking_commit.reload.state,
    "forged status from unrelated repo should not update victim's commit, but it did"
  refute later_commit.deployable?,
    "victim stack should remain blocked; forged cross-repo status must not bypass ci.blocking"
end
```
Before a fix, `blocking_commit.state` becomes `success` and `later_commit.deployable?` becomes true, demonstrating the cross-tenant bypass; after adding repository-scoping to `StatusHandler#process`, the forged payload is ignored and both assertions hold as originally intended.
