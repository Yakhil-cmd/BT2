### Title
Session fixation on login via `Shipit::GithubAuthenticationController#callback` (missing `reset_session`) - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated] = true` directly into the pre-existing session without calling `reset_session` first, and the controller (`ActionController::Base` subclass, not `ApplicationController`) does not run `protect_from_forgery`. If an attacker can plant a known, validly-issued (pre-authentication) session cookie in a victim's browser and the victim completes the real GitHub OAuth flow in that browser, the session is upgraded in place rather than being rotated.

### Finding Description
The broken binding is: `session_id(before callback) == session_id(after callback)`. In `app/controllers/shipit/github_authentication_controller.rb:7-21`: [1](#0-0) 
the action reads `request.env['omniauth.auth']`, calls `sign_in_github(auth)`, and directly assigns `session[:user_id]` / `session[:authenticated]` with no call to `reset_session`. Contrast with `logout`, which does call `reset_session`: [2](#0-1) 

`force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb:20-34`) and `find_current_user` (`app/controllers/concerns/shipit/authentication.rb:36-42`) only check `session[:user_id]`/`current_user.authorized?`; neither guards against a pre-authentication session being reused post-authentication: [3](#0-2) 

Route configuration confirms both GET and POST are wired to `callback` with no forgery protection on this controller: [4](#0-3) 

`GithubAuthenticationController < ActionController::Base` (not the host `ApplicationController`, which does have `protect_from_forgery with: :exception`): [5](#0-4) [6](#0-5) 

Exploit flow: attacker obtains a validly-issued, unauthenticated session cookie from the Shipit host (e.g., by visiting anonymously) and plants that exact cookie in the victim's browser (via a shared-subdomain cookie write or similar out-of-band mechanism, granted as a precondition by the question). Victim's browser, still carrying that cookie, initiates and completes the real GitHub OAuth handshake; `callback` fires with the victim's own `omniauth.auth`, and the controller writes `session[:user_id] = victim.id` into the *same* session object without rotating it. If the host app's session store is ID-based (e.g., `ActiveRecord::SessionStore`, Redis, cache store) rather than the default `:cookie_store` used only in the engine's test dummy app, the attacker's known session identifier now resolves server-side to the victim's authenticated session, and the attacker can replay it to act as the victim.

Note on caveat: with Rails' `:cookie_store` (used in `test/dummy/config/initializers/session_store.rb`), the entire session payload travels in the signed cookie, so the cookie's *content* necessarily changes once `session[:user_id]` is written, meaning the attacker's pre-login cookie value would not decode to the post-login state. The practical exploitability therefore depends on the host application's chosen session store, which this engine does not control. Regardless of store, the absence of `reset_session` is a real deviation from Rails' documented session-fixation mitigation, and no other guard (`force_github_authentication`, `User#authorized?`, CSRF protection) compensates for it.

### Impact Explanation
If the host app uses a server-side, ID-referenced session store, a successful fixation lets the attacker impersonate the victim's authenticated Shipit session — reading and acting on stacks, deploys, and tasks the victim is authorized for, without ever presenting valid GitHub credentials. This is scoped by the audit rules as High ("session fixation / forced OAuth completion"), not Critical, since it requires an out-of-band cookie-planting precondition (not itself provided by this engine) and its real-world impact is store-dependent.

### Likelihood Explanation
Preconditions: (1) attacker must have a way to write a specific cookie value into the victim's browser before the OAuth flow completes (e.g., shared-subdomain cookie scope, or another mechanism outside this engine's control); (2) the host application must use a session store where the session identifier is decoupled from session content (i.e., not the default `:cookie_store`). Given the engine's own dummy/test configuration uses `:cookie_store`, the vulnerability's exploitability is contingent on host deployment choices not visible in this repo. The code-level defect (missing `reset_session`) is confirmed and unconditional; the exploitability of it into a full session takeover is conditional.

### Recommendation
Call `reset_session` in `Shipit::GithubAuthenticationController#callback` before setting `session[:user_id]`/`session[:authenticated]`, preserving `return_url` in a local variable beforehand (since `reset_session` clears the session hash). Optionally add `protect_from_forgery` (or explicit `skip_before_action` documentation) consistent with `ApplicationController`'s pattern, and ensure any session cookie is scoped/`Secure`/`SameSite` appropriately at the host level.

```ruby
test ":callback rotates the session id to prevent fixation" do
  # Simulate attacker obtaining a session before authentication.
  get :request  # or any pre-auth request establishing session[:some_attacker_key] = 'planted'
  session[:planted] = 'attacker_value'
  pre_login_session_id = @request.session.id  # or session.to_hash.dup for cookie store

  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(raw_info: OmniAuth::AuthHash.new(
      id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
      login: 'shipit-user', avatar_url: 'https://example.com',
      api_url: 'https://github.com/api/v3/users/shipit-user'
    ))
  )
  @request.env['omniauth.auth'] = auth

  get :callback

  post_login_session_id = @request.session.id
  # This assertion currently FAILS because callback never calls reset_session:
  refute_equal pre_login_session_id, post_login_session_id, "session id must rotate on login"
  assert_nil session[:planted], "pre-auth session keys must not survive login"
end
```
This test demonstrates the missing binding break directly against `Shipit::GithubAuthenticationController#callback`; it currently fails, confirming the session is not rotated on authentication.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```
