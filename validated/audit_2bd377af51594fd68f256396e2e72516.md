## Title
Stored/Reflected Script Injection via Unsanitized "text" Device Message Displayed to User - (File: wallet.js)

### Summary
`ocore` handles peer-to-peer wallet device messages in `handleMessageFromHub()`. For the `"text"` message subject, the message body is stripped only of specific contract-marker substrings (`prosaic-contract:`, `arbiter-contract-offer:`, etc.) but no HTML/script tags are removed before the raw string is forwarded to the wallet UI via `eventBus.emit("text", ...)` for display.

### Finding Description
In `wallet.js`, the `"text"` case of `handleMessageFromHub()` only validates that `body` is a non-empty string, then performs narrow regex replacements targeting contract-offer markup, and finally emits the raw, unmodified remainder for UI rendering: [1](#0-0) 

Notably, `ocore` sanitizes attacker/peer-controlled *names* elsewhere before they reach storage/UI — e.g. `handlePairingMessage()` strips all `<...>` tags from `device_name`: [2](#0-1) 
and `handleOfferToCreateNewWallet()` strips `<`/`>` from `wallet_name` and cosigner `name`: [3](#0-2) 

This shows the codebase's own established pattern is to sanitize free-text fields originating from a correspondent device before they are persisted/displayed, but the `"text"` chat-message path — explicitly documented as being routed to the UI for display ("the wallet should have an event handler that displays the text to the user") — has no such sanitization. Any paired device (a legitimate but potentially malicious/compromised correspondent) can send an arbitrary `"text"` message subject whose body reaches the wallet UI verbatim, including HTML/script markup, exactly analogous to CVE-2019-10756 where `ui_notification` accepted and rendered raw HTML from an untrusted source by default without escaping.

### Impact Explanation
If the downstream wallet UI (e.g., a GUI/Cordova wallet built on `ocore`) renders the `"text"` event payload as HTML (a common pattern for chat-style notifications, as this codebase's own `chat_storage.js` persists these messages verbatim for later re-display), a malicious or compromised paired device can inject arbitrary JavaScript into the victim wallet's UI context. Given wallet UIs commonly have access to signing dialogs, private keys/xpub material, and device-pairing actions, script injection in this context can be leveraged toward unauthorized fund movement, phishing overlays over signing confirmations, or exfiltration of sensitive wallet state — a realistic Medium-severity impact consistent with the CVE class.

### Likelihood Explanation
Likelihood is Medium: exploitation requires only that the attacker's device is paired (or is an indirect correspondent for the subjects it's allowed) and sends a `"text"` message — a fully within-protocol, low-privilege action reachable by any correspondent, with no special authentication or timing requirements. The only missing precondition is that a specific consumer's UI must render this text as HTML, but the ocore library imposes no restriction preventing that; other equivalent code paths in the same codebase treat this exact risk as real enough to require sanitization.

### Recommendation
Strip or HTML-escape tag/script markup from the `"text"` message body in `handleMessageFromHub()` before emitting it via `eventBus.emit("text", ...)`, consistent with the sanitization already applied to `device_name`, `wallet_name`, and cosigner `name` elsewhere in the codebase (e.g., `body.replace(/<[^>]*>?/g, '')`), or explicitly document/enforce that consuming UIs must treat this payload as plain text only.

### Proof of Concept
1. Device A pairs with Device B (victim) through the normal pairing flow.
2. Device A sends a `"text"` device message to Device B with body:
   `<img src=x onerror=alert(document.cookie)>Hi, check this out`
3. In `wallet.js`, `handleMessageFromHub()` only removes contract-marker substrings, none of which match this payload, and emits the full string via `eventBus.emit("text", from_address, body, message_counter)`.
4. If the receiving wallet UI renders this string as HTML (as implied by the "displays the text to the user" comment and consistent with the message being persisted for chat display in `chat_storage.js`), the injected script executes in Device B's wallet UI context. [4](#0-3)
