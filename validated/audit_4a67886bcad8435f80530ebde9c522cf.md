## Finding: Valid

### Title
Global DAA feature flag bypasses secondary-signer authentication in multi-agent prologue - ([File: aptos-move/framework/aptos-framework/sources/transaction_validation.move])

### Summary
`allow_missing_txn_authentication_key` is a global-feature-flag check, not an account-scoped check. It is reused verbatim inside `multi_agent_common_prologue` to authorize *secondary* signers, even though its "aa verifies authentication itself" rationale only holds for accounts that actually authenticate through the Account Abstraction (AA/DAA) native dispatch path — a path that is only invoked for the transaction *sender(s)* and *fee payer*, never for secondary signers.

### Finding Description
`allow_missing_txn_authentication_key` is defined as: [1](#0-0) 

It returns `true` whenever `features::is_derivable_account_abstraction_enabled()` is set — a single, network-wide governance flag that says nothing about any specific account. It is used to gate the primary sender's missing-auth-key case in `prologue_common`: [2](#0-1) 

and it is reused, unmodified, for *each secondary signer* inside `multi_agent_common_prologue`: [3](#0-2) 

The comment "aa verifies authentication itself" is only true when an actual AA/DAA authentication call (`dispatchable_authenticate`) executes for that address before the prologue runs. Looking at `validate_signed_transaction` in the VM, this native authentication dispatch is performed **only** for the primary sender(s) and the fee payer: [4](#0-3) [5](#0-4) 

There is no equivalent call for secondary signers anywhere in `validate_signed_transaction`. Secondary signer auth material is instead only fed into the prologue as `secondary_signer_public_key_hashes` derived from `secondary_authentication_proofs[i].optional_auth_key()`: [6](#0-5) 

Additionally, at the authenticator level, an `Abstract` `AccountAuthenticator` explicitly skips cryptographic verification and defers it "after prologue": [7](#0-6) 

Putting this together: once `is_derivable_account_abstraction_enabled()` is turned on network-wide (a global rollout decision, unrelated to any specific account opting into AA), `allow_missing_txn_authentication_key(secondary_address)` returns `true` for **any** address. An attacker who controls only the primary sender's key can name an arbitrary, non-AA-registered account as a secondary signer, supply an authentication proof that resolves to `option::none()` (e.g., an `Abstract` proof, whose signature verification is explicitly skipped at the `AccountAuthenticator::verify` layer), and the `multi_agent_common_prologue` check will treat the missing hash as acceptable — without ever calling `dispatchable_authenticate` or checking the real on-chain authentication key of that secondary account. This breaks the secondary-signer binding invariant asserted by `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY`, effectively allowing an unprivileged sender to admit a multi-agent transaction as if an uninvolved account had authorized it.

### Impact Explanation
This allows the sender-controlling attacker to have a transaction admitted and executed with a fabricated/unauthenticated secondary signer, breaking the "intended signer set" binding guarantee for multi-agent transactions (sponsored/secondary-auth flows must not create an approval-confusion path for unprivileged callers). Any module logic that trusts `&signer` for a secondary account (e.g., multi-agent DeFi flows requiring two independent parties, escrow releases, joint-custody operations) can be invoked without the named party ever having signed.

### Likelihood Explanation
Once `derivable_account_abstraction` is enabled network-wide (a global feature toggle, not per-account), any unprivileged party who can construct a normally-signed primary transaction can trivially add a secondary signer entry with a proof that resolves to `None`. No leaked key, no privileged role, and no pre-existing approval from the secondary account is required — only knowledge of a target address to impersonate as secondary signer.

### Recommendation
`allow_missing_txn_authentication_key` used inside `multi_agent_common_prologue` (and the fee-payer paths) must not rely solely on the global `is_derivable_account_abstraction_enabled()` flag. It should require proof that the specific secondary/fee-payer account actually underwent real AA/DAA authentication (i.e., that `dispatchable_authenticate` was executed for that exact address with a matching proof), or the missing-hash exemption should require an account-scoped check equivalent to `using_dispatchable_authenticator(secondary_address)` for all AA variants, and `validate_signed_transaction` should invoke the native authentication dispatch for secondary signers' `Abstract` proofs just as it does for senders and fee payers.

### Proof of Concept
1. On a network with `derivable_account_abstraction` feature enabled, an attacker creates a normal, validly-signed Ed25519 transaction as the primary sender.
2. The attacker adds a target account (not registered for AA/DAA, with a normal Ed25519 auth key) as a secondary signer, and constructs the secondary signer's `AuthenticationProof` such that `optional_auth_key()` returns `None` (e.g., using an `Abstract` authenticator whose `verify()` unconditionally returns `Ok(())` per `types/src/transaction/authenticator.rs:836-847`).
3. Submit via REST/mempool. `validate_signed_transaction` only invokes `dispatchable_authenticate` for `senders`/`fee_payer` (`aptos-move/aptos-vm/src/aptos_vm.rs:1993-2030`), never for the secondary signer.
4. In `multi_agent_common_prologue`, `signer_public_key_hash` is `None`, so it hits the `allow_missing_txn_authentication_key(secondary_address)` branch, which returns `true` purely because the global DAA flag is on (`transaction_validation.move:114-118`, `426-429`), regardless of the target account's actual auth configuration.
5. The transaction is admitted and executed with a `&signer` for the target account that the target never authorized.

A Move unit test to confirm: enable `derivable_account_abstraction` feature only (no AA setup on the secondary account), call `multi_agent_common_prologue` (or `unified_prologue_v2`/`multi_agent_script_prologue_extended`) with `secondary_signer_public_key_hashes = [option::none()]` for a normal (non-AA) secondary account, and assert it does **not** abort with `PROLOGUE_EINVALID_ACCOUNT_AUTH_KEY` — demonstrating the bypass, whereas it should abort since that account never authenticated.
