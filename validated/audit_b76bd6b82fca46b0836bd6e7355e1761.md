### Title
Asset definer can arbitrarily rewrite the `spender_attested` attestor list at any time to freeze or seize control of all holders' funds - (File: `validation.js`)

### Summary
For any asset created with `spender_attested: true`, the asset definer retains unilateral, unbounded, and perpetual control over the list of trusted attestors via the `asset_attestors` message. There is no cap, timelock, or immutability guarantee once the asset is in circulation. This mirrors the `RoyaltyVault` finding: a single privileged party (the asset definer, analogous to the vault "owner") can unilaterally rewrite a parameter that gates fund movement for every other participant, at any point after value has already accumulated in the asset, with no on-chain restriction preventing abuse.

### Finding Description
When an asset is defined with `spender_attested: true`, every payment of that asset requires the spending author to be on the current attestor-approved list, checked in `validatePayment`: [1](#0-0) 

The attestor list itself is fully mutable post-issuance. The `asset_attestors` message lets the definer replace the list at will, and the only party allowed to do so is checked to be the definer — but there is no restriction on *when*, *how often*, or to *what* the list can be changed: [2](#0-1) 

`checkAttestorList` only validates that addresses are well-formed, sorted, and under a count limit — it does not prevent the definer from setting the list to attestors that will never attest anyone, or to itself only, at any time after users already hold and expect to transact with the asset: [3](#0-2) 

This differs from the immutable, issuance-time-only parameters (`cap`, `is_private`, `fixed_denominations`, etc.) set once in `validateAssetDefinition` — `attestors`/`spender_attested` state is explicitly designed to be updatable indefinitely by the definer alone, exactly the "owner can change a critical fund-gating parameter after the fact" pattern flagged in the original report.

### Impact Explanation
Because every payment of a `spender_attested` asset is gated on the live attestor list at validation time, the definer can:
- Freeze all holders' funds instantly and indefinitely by publishing an `asset_attestors` update that clears/replaces the list so that no current holder's address (or none at all) is attested, causing `validatePayment` to reject every payment with "none of the authors is attested" — permanently trapping value already issued to third parties.
- Selectively grief specific holders by excluding them from future attestor lists while allowing others, effectively picking winners/losers of who can move funds within an asset they don't control.

This is a fund-freezing centralization risk directly analogous to the referenced finding: a privileged single-key actor holds standing authority to alter a fund-gating parameter for balances that already belong to other parties, with no cap or delay mechanism.

### Likelihood Explanation
This requires no special exploit — the definer address is unprivileged from the protocol's perspective (any ordinary unit-posting address can define an asset with `spender_attested: true` and later post an `asset_attestors` message), and is the same address type explicitly in-scope ("asset issuer"). Any user who acquires and holds such an asset is exposed to this risk any time after issuance, and the check-in path (`validateAttestorListUpdate` → `asset_attestors`) has no additional guardrails beyond signature-by-definer.

### Recommendation
- Consider requiring attestor-list updates to be time-locked or announced in advance so holders have warning before a change takes effect.
- Consider disallowing removal of all attestors (i.e., require the new list to be non-empty and to include at least one attestor capable of attesting existing/active spenders), or requiring multi-party sign-off for attestor changes on assets already in wide circulation.
- Document/flag prominently (e.g., in wallet UI) that `spender_attested` assets carry this centralization/freezing risk so holders can make an informed trust decision.

### Proof of Concept
1. Address `D` defines asset `X` with `spender_attested: true` and an initial attestor list `[A1]` (validated via `validateAssetDefinition`, `hasFieldsExcept` allowing `attestors` field: [4](#0-3) ).
2. Users acquire and hold asset `X`, expecting to be able to transact once attested by `A1`.
3. `D` (the definer) later posts an `asset_attestors` message setting the attestor list to `[A2]`, where `A2` never attests anyone: this passes `validateAttestorListUpdate` since only definer-authorship and address well-formedness are checked (`validation.js:2829-2848`).
4. Any subsequent payment message for asset `X` fails validation at `validatePayment`'s `spender_attested` branch (`validation.js:2115-2122`) because no holder is attested by `A2`, permanently freezing all balances of asset `X` for every holder except at `D`'s discretion.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
