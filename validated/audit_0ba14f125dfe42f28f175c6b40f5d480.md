## Analysis

**Binding claimed broken:** `repository_owner` (used by `WebhooksController#verify_signature` to select which org's `webhook_secret` authenticates the request) is asserted to equal the org that owns `params.repository.full_name` (used by `ReopenedHandler#repository`/`#stack` to select which `ReviewStack` gets unarchived and re-provisioned). I traced the code and confirmed these are two independent reads of attacker-controlled JSON with no cross-check. [1](#0-0) 

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (fallback `organization.login`) and fetches `Shipit.github(organization: repository_owner)`, then calls `verify_webhook_signature` on the **raw body** using that org's secret. [2](#0-1) [3](#0-2) 

- `verify_webhook_signature` short-circuits: `return true unless webhook_secret` — before even parsing the signature header. If the resolved org has no `webhook_secret` configured, **any** signature (or none) passes. [4](#0-3) 

- The multi-org config schema explicitly supports per-org `webhook_secret: # nil`, so a secret-less org is a documented, legitimate configuration state, not a hypothetical. [5](#0-4) 

- `ReopenedHandler#repository` and `#stack` independently resolve the target repository from `params.repository.full_name` only — never checking `params.repository.owner.login` (the value used for signature verification) or `params.sender.login` against any authorization on that repository. [6](#0-5) 

- `unarchive!` on the `ReviewStackAdapter` re-provisions the stack: `Shipit::ReviewStackProvisioningQueue.add(stack)` followed by `stack.unarchive!`. [7](#0-6) 

- The `ReopenedHandler`'s `ExplicitParameters` schema only requires `repository.full_name` (String) — it does not require or validate `repository.owner.login` to be present or consistent with anything, so an attacker's JSON body is free to set `repository.full_name` to `"victim-org/victim-repo"` while setting `repository.owner.login` to an org whose `webhook_secret` is empty/nil. [8](#0-7) 

**Exploit flow:** Attacker POSTs to `/webhooks` with `X-Github-Event: pull_request` and a body where `repository.owner.login` = an org configured on this Shipit instance with a blank `webhook_secret` (satisfying `verify_signature` trivially, regardless of `X-Hub-Signature` value/absence), but `repository.full_name` = the victim's real (secret-protected) `org/repo`, `number` = the victim's PR number whose `pr#{number}` environment stack was previously archived, and `action` = `"reopened"`. `drop_unhandled_event` passes since `pull_request` is a handled event. `verify_signature` passes because the *resolved* org (from `repository.owner.login`) has no secret. `ReopenedHandler#process` then looks up the *victim's* repository/stack via `full_name`, and if `unarchive?` (provisioning-behavior gate on the victim repo config, e.g. `allow_all`) passes, calls `stack.unarchive!`, which invokes `ReviewStackProvisioningQueue.add(stack)` — a genuine write against a foreign repository's stack triggered by a request that was never authenticated by that repository's own org secret.

**Why existing guards don't catch this:** `drop_unhandled_event` only checks event type. `verify_signature` authenticates the payload against the org named by `repository.owner.login`/`organization.login` — a field independent of `repository.full_name`, which the handler actually trusts to select the stack. There is no code anywhere that asserts these two fields refer to the same org. `ExplicitParameters` validates types/presence only, not cross-field/cross-org consistency. `params.sender.login` is used only to attribute the `User` who unarchives (`review_stack_adapter.rb:52-54`), not as an authorization check.

**Caveat / uncertainty:** This does require a genuine operator misconfiguration — at least one org registered in `Shipit.github`'s multi-org config with a blank `webhook_secret` — for the signature bypass to work at all. I could not fully inspect `app/models/shipit/repository.rb`'s `from_github_repo_name`-equivalent lookup and any name-format validators before the tool budget ran out, so I cannot rule out that repository name format validation (e.g. requiring `full_name` to match `^[\w.-]+/[\w.-]+$`) restricts which strings are accepted — though this would not prevent naming an arbitrary *existing* victim repo, since the attacker only needs to supply a valid existing `"org/repo"` string, not an arbitrary one.

### Title
Webhook signature verification keyed off an attacker-controlled `repository.owner.login` allows cross-org `ReviewStack` re-provisioning via forged `pull_request.reopened` payload - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login`/`organization.login` from the request body itself, while `ReopenedHandler` (and other PR handlers) select the target `Repository`/`ReviewStack` using the independent `repository.full_name` field from the same body. Because nothing enforces these two fields name the same org/repo, and per-org `webhook_secret` may legitimately be blank for some org in a multi-org deployment, an attacker can authenticate as a secret-less org while directing the payload's action at a victim repository under a different, secured org, causing `stack.unarchive!` and `ReviewStackProvisioningQueue.add(stack)` to run against the victim's stack.

### Finding Description
Broken binding: `repository_owner(payload) == owner_of(params.repository.full_name)` is assumed but never checked. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, fetches `Shipit.github(organization: repository_owner)`, and calls `verify_webhook_signature(signature, raw_body)`, which returns `true` unconditionally `unless webhook_secret` [4](#0-3) . Meanwhile `ReopenedHandler#repository`/`#stack` resolve strictly from `params.repository.full_name` [9](#0-8) , and `process` calls `stack.unarchive!` when `respond_to_pull_request_reopened?` (gated on the target repository's own `provisioning_behavior`, not on the requester's identity) [10](#0-9) , which in turn calls `Shipit::ReviewStackProvisioningQueue.add(stack)` [7](#0-6) .

Attacker request: POST `/webhooks`, header `X-Github-Event: pull_request`, body with `action: "reopened"`, `repository: { full_name: "victim-org/victim-repo", owner: { login: "attacker-org" } }`, `number` = the victim PR number whose `pr#{number}` `ReviewStack` was previously archived, and any signature. If `attacker-org` is configured in `Shipit.github` with no `webhook_secret`, `verify_signature` passes unconditionally. The handler then resolves and re-provisions the victim's stack.

### Impact Explanation
A write (`ReviewStackProvisioningQueue.add`, `stack.unarchive!`) executes against a repository/stack that never authenticated the request via its own org secret — the request was only authenticated for an unrelated, secret-less org. This is a cross-tenant mutation of another repository's provisioning state, matching "a payload for one repository mutating another's stack" (Critical). It is repeatable for any victim repo/PR number known to the attacker and blast radius spans all repos configured under other, secured orgs on the same Shipit instance, as long as one org in the deployment has a blank `webhook_secret`.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment where at least one configured org has no `webhook_secret` (a documented, supported configuration state per `config/secrets.development.shopify.yml`), and (2) the victim repository's `provisioning_behavior` (`allow_all`, or label-gated) to satisfy `unarchive?`. Given those preconditions, attacker cost is a single unauthenticated HTTP POST with no secrets, tokens, or GitHub privileges — fully within the stated threat model.

### Recommendation
Bind signature verification to the same identity used for repository resolution: after computing `repository_owner`, require that `Shipit::Repository.from_github_repo_name(params.repository.full_name)`'s owner matches `repository_owner` (or `organization.login`) before dispatching to handlers; reject the webhook (422) on mismatch. Additionally, disallow/alert on org configurations with empty `webhook_secret` in multi-org mode, or require webhook secrets to be mandatory once more than one org is configured.

### Proof of Concept
Minitest (`test/controllers/webhooks_controller_test.rb`-style), no live GitHub:
1. Configure two orgs in `Shipit.stubs(:github)`/secrets: `"attacker-org"` with `webhook_secret: nil`, `"victim-org"` with a real secret.
2. Create `shipit_repositories(:victim)` under `full_name: "victim-org/victim-repo"`, `provisioning_behavior: :allow_all`, and an archived `ReviewStack` for `environment: "pr2"`.
3. POST `/webhooks` with `X-Github-Event: pull_request`, body `{"action":"reopened","number":2,"pull_request":{...},"repository":{"full_name":"victim-org/victim-repo","owner":{"login":"attacker-org"}},"sender":{"login":"attacker"}}`, no/garbage `X-Hub-Signature`.
4. Assert `response.status == 200` (bypassing signature check) and assert `Shipit::ReviewStackProvisioningQueue` received `add` for the victim stack / `stack.reload.archived? == false`, proving `repository_owner("attacker-org") != owner_of(params.repository.full_name)("victim-org")` yet the mutation on `victim-org/victim-repo`'s stack still occurred.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
