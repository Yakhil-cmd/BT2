### Title
Webhook membership handler trusts `team.id` without verifying it belongs to the signing organization, allowing cross-organization team hijacking - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook only against the `webhook_secret` of the organization named in the payload itself (`repository_owner`/`organization.login`), which an attacker fully controls for their own GitHub org. `MembershipHandler#find_or_create_team!` then looks up/mutates a `Team` row keyed solely on the numeric `github_id` from that same attacker-controlled payload, with no check that the `github_id` actually belongs to the organization whose secret signed the request. This lets an attacker with a legitimate, unprivileged webhook from their own org add themselves to any pre-existing privileged `Team` by guessing/enumerating its `github_id`.

### Finding Description
The broken binding: `signing_organization (params.organization.login, verified via evil-org's own webhook_secret)` should equal `team_owning_organization (Team#organization for the Team row identified by params.team.id)`, but the code never enforces this equality.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and fetches `Shipit.github(organization: repository_owner)`, then verifies the signature with that organization's own `webhook_secret` [2](#0-1) . Since `organization.login` in the payload is attacker-supplied and equals `'evil-org'`, this check only proves the attacker owns `evil-org`'s secret — it proves nothing about the `team.id` field also present in the same payload.
2. `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id)`, using `organization.login` only in the creation block (never on lookup) [3](#0-2) . If a `Team` with that `github_id` already exists (created earlier by the legitimate org), `find_or_create_by!` returns that existing row unchanged, regardless of which organization is embedded in the current payload.
3. `#process` then does `User.find_or_create_by_login!(params.member.login)` and, for `action == 'added'`, calls `team.add_member(member)` on the found (legitimate, privileged) team [4](#0-3) .

Exploit flow: attacker sets up `evil-org` on GitHub with a webhook to the Shipit host's `/webhooks`, configures `Shipit.secrets.github['evil-org']` to have their known `webhook_secret` (a normal onboarding step available to any org owner who is allowed to have an entry, or simply computes a correctly signed payload if `evil-org` is any registered org config). They send (or trigger via the GitHub UI) a `membership` event with `team.id` set to the `github_id` of a `Team` already present from a real, privileged organization in `Shipit.github_teams`, `action: 'added'`, `member.login` = attacker's GitHub login, `organization.login: 'evil-org'`. The signature check passes because it's validated against `evil-org`'s own secret. `find_or_create_team!` resolves to the pre-existing privileged `Team`, and the attacker is added as a member.

Why existing guards fail: `verify_signature` only proves message integrity/origin for the *organization named in the payload*, not that every ID field inside the payload (specifically `team.id`) legitimately belongs to that organization. `drop_unhandled_event` and `ExplicitParameters` schema (`params do ... end`) only validate types/presence, not cross-field/ cross-org consistency. There is no `Team#organization == params.organization.login` check anywhere in `find_or_create_team!` or `#process`.

### Impact Explanation
The attacker's `User` gains a `Membership` in a team listed in `Shipit.github_teams`, which is the authorization source used by `Shipit::User#authorized?` and consequently `Authentication#force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb`. This grants the attacker authenticated, authorized access to Shipit (deploy/rollback/merge capability depending on what that team's authorization unlocks), which matches the "escalation into `Shipit.github_teams` authorization" High-severity category (or higher, since it can lead to unauthorized deploys/rollbacks once authorized). This is repeatable against any `Team` `github_id` the attacker enumerates, and any organization configured in `Shipit.secrets.github` can be used as the signing identity, so the blast radius spans every privileged team in the installation.

### Likelihood Explanation
Preconditions: the attacker needs an organization entry in `Shipit.secrets.github` for their own org (typical for self-service GitHub App/webhook integrations where any org can register), and knowledge of a `team.id` — a small sequential GitHub numeric ID that's easy to enumerate or observe from public GitHub team URLs/API. No Shipit secrets, session, or privileged GitHub role are required; only the attacker's own webhook secret, which they legitimately possess. This makes the attack low-cost and highly feasible, and repeatable at will (each `membership`/`added` event re-adds them if removed).

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the found (or newly created) `Team#organization` matches `params.organization.login`, and reject/raise (or no-op) if they diverge instead of mutating an existing team belonging to a different organization. More generally, scope the `Team.find_or_create_by!` lookup to `(github_id:, organization:)` rather than `github_id` alone, and add a `WebhooksController` level check that the `organization`/`team` fields inside a payload are consistent with the organization whose secret verified the request.

### Proof of Concept
Minitest plan (under `test/`, no live GitHub):
1. Seed `Shipit.secrets.github` (via test config) with two orgs: `'legit-org'` (`webhook_secret: 'legit_secret'`) and `'evil-org'` (`webhook_secret: 'evil_secret'`), and add `'legit-org'` to `Shipit.github_teams`.
2. Create a `Team` with `github_id: 123, organization: 'legit-org'`.
3. POST to `/webhooks` with `X-Github-Event: membership`, body `{"action":"added","team":{"id":123,"name":"t","slug":"t","url":"u"},"organization":{"login":"evil-org"},"member":{"login":"attacker"}}`, signed with `evil_secret` via `X-Hub-Signature`.
4. Assert response is `200`.
5. Assert `Team.find_by(github_id: 123).organization == 'legit-org'` (unchanged) — left side of binding.
6. Assert `User.find_by(login: 'attacker')` exists and is a member of that `Team`, and `User.find_by(login: 'attacker').authorized?` is `true` — demonstrating the equality `signing_organization ('evil-org') != team_owning_organization ('legit-org')` was never checked yet the privileged membership was granted.
