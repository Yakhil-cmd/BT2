### Title
Unbounded `RemoteProxyProof::RelayChain.proof` size lets the fixed benchmarked weight of `remote_proxy` undercharge actual PoV/CPU cost - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`Pallet::remote_proxy`'s `#[pallet::weight]` closure charges a flat, benchmark-derived constant (`WeightInfoOf::<T, I>::remote_proxy()`) plus the inner call's declared weight, but never accounts for the size of the caller-supplied `proof: Vec<Vec<u8>>` field of `RemoteProxyProof::RelayChain`. Inside `do_remote_proxy`, `sp_trie::StorageProof::new(proof).into_memory_db(...)` inserts every node the caller submits into an in-memory trie database before `sp_trie::read_trie_value` is even called, so execution cost scales with attacker-controlled `proof.len()` while the charged weight does not.

### Finding Description
The extrinsic weight annotation is: [1](#0-0) 
`WeightInfoOf::<T, I>::remote_proxy()` is a constant derived from benchmarking with a single small, realistic proof (`T::RemoteProxy::create_remote_proxy_proof`), and the autogenerated weight file confirms this is a fixed `Weight::from_parts(18_259_000, 0)` plus a fixed `1846`-byte proof-size component, independent of any runtime input: [2](#0-1) [3](#0-2) 

The actual execution path in `do_remote_proxy` takes the `proof: Vec<Vec<u8>>` directly from the call arguments (fully attacker-controlled, no length/count check) and builds a `MemoryDB` from it before doing the trie lookup: [4](#0-3) 

`sp_trie::StorageProof::new(proof).into_memory_db()` inserts *every* node in the supplied vector into the in-memory database regardless of whether that node is on the path to the target key, so its cost is `O(N)` in the number/size of supplied nodes, not bounded by the single benchmarked value. There is no `MaxEncodedLen`/`BoundedVec` constraint on `proof`, and no explicit per-node or total-size cap enforced by the pallet itself.

The only extrinsic-level guards are the general block/PoV length limits (`BlockLength`) and the byte-based transaction length fee, which charge for encoded transaction bytes — that is a separate fee dimension from the "computation weight" charged via `WeightInfoOf::remote_proxy()`. Length fee scaling does not correct for the mismatch between the fixed weight component and the actual CPU/PoV work of decoding and merkelizing an arbitrarily large `proof` vector; a large-but-still-legal-under-block-length proof can be submitted at a declared/charged weight far below its true execution cost.

### Impact Explanation
An unprivileged signed account can submit `remote_proxy` with a `proof` containing many/large fabricated or duplicated nodes (bounded only by the parachain's max extrinsic length / PoV size, not by the pallet's weight logic). This causes the runtime to spend CPU/PoV time building a large `MemoryDB` while only being charged the fixed, small benchmarked weight for that portion of the call. This is a weight/fee-asymmetry (block-weight and PoV griefing) issue: it can push actual block execution time beyond what the scheduler believes it reserved, at low cost to the attacker (they pay length-based fees and a fixed weight fee, not fees proportional to actual proof-processing cost).

### Likelihood Explanation
Feasible and repeatable by any signed account with only enough balance to cover the transaction fee: no proxy relationship, no privileged origin, and no state precondition beyond having *some* entry in `BlockToRoot` (which is populated automatically via `on_validation_data`/`on_system_event`, not gated) — actually the call can fail at the `UnknownProofAnchorBlock` or `InvalidProof`/decoding stage after the costly `into_memory_db` construction already executed, so the DoS-relevant work happens regardless of whether the proof ultimately validates. This makes the attack cheap and repeatable per block.

### Recommendation
Make the weight of `remote_proxy` / `remote_proxy_with_registered_proof` a function of the actual proof size, e.g. add a per-byte/per-node weight component computed from `proof.iter().map(|n| n.len()).sum()` (or `proof.len()`), calibrated via a dedicated benchmark that varies proof size, and/or enforce a hard cap on the number of proof nodes/total encoded proof size (e.g., via a `Config::MaxProofNodes`/`MaxProofSize` bound checked before `into_memory_db` is called) so the charged weight and the enforced maximum bound the real execution cost.

### Proof of Concept
Rust benchmark/fuzz test plan:
1. In `pallets/remote-proxy/src/tests.rs`, construct a valid anchor block/storage root as in existing tests, then build a `RemoteProxyProof::RelayChain` whose `proof: Vec<Vec<u8>>` contains N large filler byte vectors (e.g., 10,000 x 1 KB duplicated/garbage nodes) in addition to (or without) the real needed trie nodes.
2. Call `Pallet::do_remote_proxy` (or dispatch `remote_proxy`) directly, measuring wall-clock time or instrumented weight of `sp_trie::StorageProof::new(proof).into_memory_db()`.
3. Assert that measured/instrumented execution time for large N significantly exceeds `WeightInfoOf::<T, I>::remote_proxy()` (a fixed constant, e.g. ~18_259_000 ps regardless of N), demonstrating the assertion "declared weight upper-bounds actual weight" is violated as N grows.
4. Repeat with varying `proof.len()` (e.g., 10, 1_000, 100_000 nodes within the parachain's max extrinsic length) to show near-linear growth in actual cost with no corresponding growth in charged weight.
