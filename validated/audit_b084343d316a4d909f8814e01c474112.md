### Title
Node crash via `CHECK`-style assertion failure when validating an address `definition template` whose referenced unit's sequence changes state - ([File: definition.js])

### Summary
`Definition.validateAuthentifiers()` evaluates an address definition tree every time a unit signed by that address needs its signature verified. For the `['definition template', [unit, params]]` opcode, the evaluator queries the referenced unit's stored `definition_template` message and assumes exactly one row will be returned. If that assumption is violated, the code does not return a normal validation error through the callback — it synchronously `throw`s, an uncaught exception that propagates out of the validation pipeline and is caught only by the process-wide `uncaughtException` handler in `network.js`, which deliberately re-throws to crash the node. This mirrors the TensorFlow `CHECK`-fail pattern: an implicit "shape"/cardinality assumption (`rows.length === 1`) is enforced with a hard assertion instead of a graceful validation failure, and that assumption can be falsified by data supplied by an ordinary (unprivileged) unit author.

This snippet lives inside `evaluate()`, nested in `validateAuthentifiers(conn, address, this_asset, arrDefinition, objUnit, objValidationState, assocAuthentifiers, cb)` — the routine `validateAuthor()` calls for **every author of every unit** during `validation.validateAuthors()` / `validateAuthor()` (invoked from `validate()` for every posted joint): [2](#0-1) 

The `sequence` column referenced in the query (`+sequence='good'`) is *not* an immutable property of a unit — it can flip from `'good'` to `'final-bad'` once the DAG resolves a double-spend conflict (this is fundamental to how ocore's nonserial/final-bad resolution works, as seen throughout `validation.js`'s double-spend handling, e.g. `checkForDoublespends`): [3](#0-2) 

An address definition using `['definition template', [templateUnit, params]]` is only checked once at authoring time (when the definition is first bound to an address, via the sibling code path in `validateDefinition()`), when `templateUnit`'s `definition_template` message still has `sequence='good'`. Nothing re-validates the definition template reference afterward. When a later unit is posted that must be *authenticated* against this same address (i.e., signature verification is required), `validateAuthentifiers()` re-runs the same query against the now-current state. If `templateUnit` has since been resolved as `final-bad` (a normal, attacker-influenceable outcome of the DAG's conflict resolution), `rows.length` becomes `0`, and the assumption `rows.length === 1` is violated, triggering the `throw`.

Because this occurs deep inside an asynchronous DB callback with no surrounding `try/catch`, the exception is not caught by the validation orchestration; it becomes an uncaught exception. `network.js` installs a global handler that intentionally crashes the process on any uncaught exception: [4](#0-3) 

### Impact Explanation
Every full node that receives and validates the malicious unit (an ordinary payment/unit spent from the crafted address, requiring authentication) hits the same `throw` and crashes via the `uncaughtException` handler. This is a network-wide denial of service: nodes processing this posted unit become unable to continue processing (the process exits), matching "a network unable to confirm new units" / "node disagreement" impact criteria. Unlike a rejected unit (which would just be an ordinary validation error), this crashes the validating process itself, which is a much more severe availability impact — directly analogous to the TensorFlow `CHECK`-fail DoS.

### Likelihood Explanation
- Any unprivileged user can author an address whose definition contains `['definition template', [unit, params]]` referencing a unit they control.
- They can then intentionally create a double-spend so that the referenced `definition_template` unit is later resolved as `final-bad` (attacker fully controls this fork, since it's their own unit).
- Once resolved, they simply spend from the crafted address (posting a normal unit signed with this definition) — any node/witness that receives and validates that unit crashes.
- No special privileges (witness, hub operator, etc.) are required; this is entirely reachable by a standard unit-poster / address-definition author, satisfying the "unprivileged unit poster ... address definitions and authentifiers" reachability requirement.

### Recommendation
- Change the `if (rows.length !== 1) throw Error("not 1 template");` in `evaluate()`'s `'definition template'` case (definition.js:812, and the analogous branch in `validateDefinition()`'s own evaluator) to return the error through the callback (`return cb(false)` / `return cb2(false)`, matching the surrounding style) instead of throwing.
- Audit all other `throw Error(...)` statements inside asynchronous DB-callback code paths reachable from unit/AA/definition validation (e.g., other `if (rows.length !== 1) throw ...` patterns in `definition.js` and `validation.js`) for the same class of issue, and replace them with graceful validation failures propagated via the existing callback-based error channel, so that state changes attacker-controlled over time (such as `sequence` transitioning between `good`/`final-bad`) cannot turn a previously-valid definition into a crash trigger.

### Proof of Concept
1. Attacker authors address `A` with definition `['definition template', [U, {}]]`, where `U` is a unit the attacker controls that currently carries a stable, `sequence='good'` `definition_template` message. This passes the initial definition-introduction check performed via `validateDefinition()`.
2. Attacker creates a conflicting (double-spend) unit `U2` such that once the DAG stabilizes, `U`'s `sequence` flips from `'good'` to `'final-bad'` (a normal outcome of ocore's own conflict-resolution rules).
3. Attacker posts any unit `T` spending from address `A` (thus requiring signature authentication against `A`'s definition).
4. When nodes validate `T`, `validateAuthor()` → `Definition.validateAuthentifiers()` → `evaluate()` re-runs the `definition template` SQL query against `U`. Because `U.sequence` is now `'final-bad'`, `rows.length === 0`, hitting `throw Error("not 1 template")`.
5. The uncaught exception bubbles up and hits the global `process.on('uncaughtException', ...)` handler in `network.js`, which re-throws, crashing every full node that processed unit `T`.
