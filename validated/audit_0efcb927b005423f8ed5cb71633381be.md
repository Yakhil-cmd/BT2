### Title
User-controlled strategy routes can attach malicious third-party token transfers to the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Account strategy calls accept an opaque, caller-controlled `swap` route and execute it through the configured router. Because route pool addresses are not constrained at the controller boundary, attacker-supplied route code can run below the caller’s authorized invocation and issue additional `token.transfer(caller, attacker, amount)` calls. Transaction simulation records those calls as extra children in the caller’s authorization tree; if the resulting tree is signed, the route can steal wallet assets unrelated to the lending position while still satisfying the controller’s measured-input, output, and solvency checks.

### Finding Description
Every routed strategy eventually reaches `swap_tokens`, which passes the caller-controlled `swap` bytes to `router.execute_strategy` without validating which venue or pool addresses the route contains [1](#0-0) .

For `swap_collateral`, the only account-level check is that `caller` owns or delegates the target account. Afterward, the function withdraws collateral and invokes the swap path using the supplied route [2](#0-1) . The same primitive is reachable through `multiply`, including a third-asset `initial_payment` converted through `convert_swap` [3](#0-2) .

The controller authorizes only one exact controller-to-router input transfer [4](#0-3) , and `authorize_transfer_as_current` creates a leaf authorization for that one token call [5](#0-4) . This bounds the controller’s own grant, but it does not isolate the original caller’s authorization tree from code invoked by the route. A malicious venue can therefore request `caller.require_auth()` indirectly through a token `transfer`, causing simulation to add that transfer as an additional child of the caller’s root authorization.

The post-router checks only compare the controller’s input/output balances and reject overspending or absent output [6](#0-5) . They do not detect a separate authorized transfer from the caller’s wallet to an attacker.

The repository’s own security test demonstrates this host behavior: a route-named rogue pool calls `token.transfer(victim, attacker, amount)` [7](#0-6) , simulation attaches the transfer beneath `swap_collateral` [8](#0-7) , and enforcing auth succeeds only when that extra transfer is signed [9](#0-8) .

### Impact Explanation
An unprivileged attacker can cause theft of user funds that were never supplied to the lending protocol and are unrelated to `token_in`, `token_out`, or `amount_in`. The attacker deploys or controls a route venue that performs a token transfer from the prospective caller. When the victim submits a routed strategy transaction, an honest simulation includes that transfer in the caller’s authorization tree. If the wallet or integration signs the simulated tree without rejecting the unexpected child, the malicious transfer executes atomically with an otherwise valid strategy.

The loss is bounded only by the token amounts included in the signed child transfers, not by the routed amount, `amountOutMin`, final health factor, or collateral checks. Multiple unauthorized children can target multiple assets or approvals represented in the simulated tree.

### Likelihood Explanation
Likelihood is moderate. Exploitation requires user interaction: the victim must sign an authorization tree containing the malicious child transfer. However, route bytes are opaque to most users, strategy routes are commonly produced by external quote infrastructure, and users generally review only the displayed input and expected output rather than decoding every simulated authorization child. An attacker who can supply a route through a malicious quote, interface, or direct message can mount the attack without privileged protocol access.

The protocol explicitly allows route payload contents to select external venue contracts, while controller protections measure only controller balances. A malicious route can still return enough output for the strategy to satisfy `NoSwapOutput`, final solvency, and other account gates.

### Recommendation
Do not allow route-selected contracts to execute beneath the account owner’s authorization without an explicit authorization-tree boundary. Preferred fixes include:

- Restrict strategy routes to a governance-reviewed venue/pool allowlist enforced before invoking the router.
- Require routes to use router-owned venue adapters that cannot initiate caller-scoped token transfers outside the expected input pull.
- Change integration semantics so the strategy authorizes only a narrowly scoped intermediate contract, and ensure third-party calls cannot attach caller transfers below the lending invocation.
- At minimum, hard fail if simulation produces any caller authorization child other than the exact expected payment transfer. This check must occur before signing and must be implemented by every wallet/integration, so it is weaker than enforcing venue admission on-chain.

Any fix should cover `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, and the conversion-swap branch for third-asset initial payments.

### Proof of Concept
Conceptual transaction:

1. Attacker deploys `RoguePool` storing `(victim, wallet_token, attacker, amount)`.
2. `RoguePool.swap()` executes:

```rust
token::Client::new(&env, &wallet_token)
    .transfer(&victim, &attacker, &amount);
```

3. Attacker gives the victim a valid-looking `swap_collateral` route whose hop invokes `RoguePool`.
4. Victim calls:

```text
controller.swap_collateral(
    caller = victim,
    account_id = victim_account,
    current = listed_collateral,
    amount = amount_in,
    new = listed_output_market,
    swap = malicious_route,
)
```

5. Controller authenticates `victim`, withdraws the requested collateral, and invokes the configured router through `swap_tokens`.
6. During route execution, `RoguePool` calls `wallet_token.transfer(victim, attacker, amount)`.
7. Simulation records that token transfer as an extra sub-invocation under the victim’s `swap_collateral` authorization.
8. The victim signs the simulated authorization tree.
9. The route also returns enough `token_out` to satisfy positive output and final account risk.
10. Execution both performs the requested collateral swap and transfers `amount` of `wallet_token` from the victim to the attacker.

A benign control route passes with no extra authorization child, while the malicious route fails under an honest tree and succeeds once the poisoned simulated tree is signed.

    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();

    let recorded = s.t.env.auths();

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),

        sub_invocations: std::vec![stolen_transfer],

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
