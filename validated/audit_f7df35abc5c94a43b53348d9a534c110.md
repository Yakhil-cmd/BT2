### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, allowing a stack-scoped token to read any stack's state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds every stack-scoped endpoint to the authenticated `ApiClient`'s authorized stack via the `stacks` helper, which restricts the queryable `Stack` set to `current_api_client.stack_id` when the client is scoped. `Shipit::Api::CCMenuController` overrides `#stack` and looks the stack up directly with `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping. The equality the platform is supposed to enforce — "stack a token authorizes" == "stack a token touches" — is broken: any valid API token (even one scoped to a single, unrelated stack) can read the CI/CD status (`ccmenu#show`) of every stack in the installation.

### Finding Description
`BaseController#stacks` and `#stack` establish the authorization binding: [1](#0-0) 

`current_api_client.stack_id?` comes from the `belongs_to :stack, optional: true` association on `ApiClient`: [2](#0-1) 

Every other stack-scoped API controller (e.g. `Api::StacksController`, tasks, deploys, hooks, etc.) relies on this `stacks`/`stack` helper so that a token scoped to stack A cannot address stack B by ID. `CCMenuController`, however, redefines `#stack` to use the unscoped `Stack.from_param!` directly, ignoring `current_api_client.stack_id`: [3](#0-2) 

The only guard on the action is `require_permission :read, :stack`, which checks that the token's `permissions` array includes `"read:stack"` — a capability check, not a scope check: [4](#0-3) [5](#0-4) 

Because `require_permission!` never inspects `current_api_client.stack_id`, an `ApiClient` created with a `read:stack` permission and scoped to stack A can supply an arbitrary `stack_id` in the URL for `GET /api/stacks/:stack_id/ccmenu` and receive `NoDeploy`/deploy status data for any other stack B, including its latest deploy id, status, and completion time (rendered by the `shipit/ccmenu/project` view).

### Impact Explanation
This is an unauthenticated-within-scope read of stack state: a token that is only supposed to authorize actions on one stack can enumerate deploy/build status for every stack in the Shipit instance. Per the engine's severity rules, unauthorized read of stack state via a token that authorizes a different stack maps to High severity (escalation beyond the token's authorized stack scope / unauthorized read of stack state).

### Likelihood Explanation
Any actor holding a legitimately-issued, stack-scoped API token (e.g. a CI token meant only to see or drive one repository's stack) can trivially exploit this by changing the `stack_id` path segment — no additional privilege, secret, or session is required beyond the token itself, and `ApiClient` tokens with narrow, single-stack scope are the intended lower-trust deployment (as seen in tests like `"an api client scoped to a stack will only see that one stack"`).

### Recommendation
Remove the `#stack` override in `CCMenuController` (and the associated `authenticate_api_client` bypass that authenticates via `params[:token]` outside the base flow) so that it uses the inherited, scoped `stacks.from_param!(params[:stack_id])` from `BaseController`, ensuring stack-scoped tokens cannot address stacks outside their authorized `stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to Stack A (`stack_id: A.id`) with permission `read:stack` (e.g. via the normal `api_clients` UI/flow described in `app/models/shipit/api_client.rb`).
2. Using that client's `authentication_token`, issue: `GET /api/stacks/<B_owner>/<B_repo>/<B_branch>/ccmenu?token=<token>` where B is a stack the client was never granted access to.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (valid signature via `ApiClient.authenticate`), `require_permission :read, :stack` passes because the token has `read:stack`, and `#stack` resolves `Stack.from_param!` for B directly — the response returns B's latest deploy status/XML, disclosing stack state the token was never authorized to access.
