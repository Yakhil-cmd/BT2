### Title
Bash octal misinterpretation of leading-zero `iteration`/`max_iterations` values bypasses the Ralph loop iteration cap - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
The regex `^[0-9]+$` used to validate `ITERATION` and `MAX_ITERATIONS` accepts any all-digit string, including canonical-looking values with leading zeros such as `019` or `008`. When such a value is later used in a bash arithmetic/numeric-comparison context (`-gt`, `-ge`, `$((ITERATION + 1))`), bash treats leading-zero numbers as octal, and since `8`/`9` are not valid octal digits, the arithmetic evaluation throws a runtime error instead of performing the comparison.

### Finding Description
`stop-hook.sh` extracts `ITERATION` and `MAX_ITERATIONS` from the state file frontmatter and validates them with `[[ ! "$ITERATION" =~ ^[0-9]+$ ]]` and `[[ ! "$MAX_ITERATIONS" =~ ^[0-9]+$ ]]` [1](#0-0) . This regex only checks that the string is composed of decimal digit characters; it does not reject leading zeros. The values are then used directly in bash numeric-context comparisons:

```
if [[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]; then
``` [2](#0-1) 

Bash's `-gt`/`-ge` operators evaluate their operands as arithmetic expressions, and in bash arithmetic a token with a leading `0` (e.g. `019`, `008`) is parsed as an **octal** literal. Since `8` and `9` are invalid octal digits, bash raises a runtime error such as `bash: 019: value too great for base (error token is "019")` and the failing `[[ ]]` test simply returns a non-zero (false) status rather than aborting the script (this is not a fatal parse error, and it occurs inside an `if` condition, where `set -e` is suppressed anyway). Because `&&` short-circuits on the first false test, the entire `if` condition evaluates to false and the max-iteration termination block is skipped — the loop continues even though `ITERATION >= MAX_ITERATIONS`.

The same class of ambiguous octal literal, or an overflow with a very large digit string, will also break `NEXT_ITERATION=$((ITERATION + 1))` at line 131, but the more impactful path is the comparison at line 51 which is the actual enforcement of the iteration cap.

Critically, this is reachable through completely normal, non-privileged usage: the `--max-iterations` argument to `/ralph-loop` is validated in `setup-ralph-loop.sh` with the identical permissive regex `^[0-9]+$` [3](#0-2) , so a value like `019` is accepted there too and written verbatim into the frontmatter (`max_iterations: $MAX_ITERATIONS`) [4](#0-3) . An attacker who can influence the prompt/arguments passed to `/ralph-loop` (e.g. via prompt injection convincing the model to run `/ralph-loop ... --max-iterations 019`) or who ships a pre-crafted `.claude/ralph-loop.local.md` with `active: true` and `max_iterations: 019` in a repository a victim opens, can trigger this bypass without any elevated privilege.

### Impact Explanation
The intended safety control — the hard cap on the number of automated loop iterations (`--max-iterations`) — is silently bypassed, causing the Stop hook to keep blocking session exit and feeding output back to the model indefinitely, well past the operator-configured limit. This is an integrity/enforcement bypass of a state/config guard that results in unconsented, unbounded automation (arbitrary continued command/tool execution cycles) rather than the user-approved bounded loop.

### Likelihood Explanation
The bug is trivially reachable: it requires only that `max_iterations` (or `iteration`) contain a leading `0` followed by an `8` or `9` digit (or an extremely large digit string causing 64-bit overflow), which passes both existing validators (`^[0-9]+$` in both `setup-ralph-loop.sh` and `stop-hook.sh`). No special privileges are needed — a user typing `--max-iterations 019`, or an attacker-supplied repository containing a pre-populated state file, is sufficient. The bug reproduces deterministically every time the loop reaches the point where `ITERATION` would equal/exceed such a value.

### Recommendation
Reject leading-zero numeric strings (other than the literal `0`) in the validation regexes, e.g. use `^(0|[1-9][0-9]*)$` for both `ITERATION` and `MAX_ITERATIONS` in `stop-hook.sh` and in the `--max-iterations` validation in `setup-ralph-loop.sh`. Additionally, force base-10 interpretation explicitly (`$((10#$ITERATION + 1))`) and bound the accepted value to a safe range (e.g. reject strings longer than ~15 digits) to avoid 64-bit arithmetic overflow errors from also defeating the comparison.

### Proof of Concept
Integration test:
1. Create `.claude/ralph-loop.local.md` with frontmatter:
   ```
   ---
   active: true
   iteration: 020
   max_iterations: 019
   completion_promise: null
   ---
   dummy prompt
   ```
2. Provide a minimal valid `transcript_path` JSON via stdin with one assistant text message that does not contain `<promise>`.
3. Run `stop-hook.sh` and capture stderr/exit behavior.
4. Assert: despite `iteration (20) >= max_iterations (19)`, the script does NOT print `"🛑 Ralph loop: Max iterations ... reached."` and does NOT remove the state file — instead it proceeds to output a `"decision": "block"` JSON, proving the cap-enforcement branch at lines 50-55 was skipped due to the bash octal-parse error on `019`.
5. As a control, repeat with `max_iterations: 19` (no leading zero) and confirm the loop correctly terminates, isolating the leading-zero/octal parsing as the root cause.
