### Title
Unfiltered PR label names injected as environment variable keys via `ReviewStack#env` bypass `EnvironmentVariables#permit` before reaching `Command`/`PTY.spawn` - ([File: app/models/shipit/review_stack.rb])

### Summary
The specific binding named in the question — that `Api::TasksController`/`Stack#trigger_task` always route attacker-supplied `env` hashes through `EnvironmentVariables#permit` before writing `@task.env` — holds. `Stack#trigger_task` unconditionally calls `definition.filter_envs(env)` [1](#0-0) , `TaskDefinition#filter_envs` and `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` all delegate to `EnvironmentVariables#permit` [2](#0-1) [3](#0-2) , and this is exercised by passing tests that assert `NotPermitted` is raised for unwhitelisted keys on tasks, deploys and rollbacks [4](#0-3) [5](#0-4) [6](#0-5) . However, while tracing this exact command-environment assembly, a genuinely broken binding of the same vulnerability class was found: `ReviewStack#env` merges GitHub pull-request label names directly as environment-variable **keys**, with no call to `EnvironmentVariables#permit` at all, and this unfiltered hash is merged into the process environment ahead of the (correctly filtered) `@task.env`.

### Finding Description
The broken binding: `keys(ReviewStack#env) ⊆ variable_definitions.map(&:name)` is expected to hold for every hash that reaches `Command`, but for `ReviewStack#env` it does **not** — the label-derived keys are never checked against any whitelist.

`ReviewStack#env` overrides `Stack#env` and merges the pull request's labels, upcased, as env-hash keys with the literal string `"true"` as the value: [7](#0-6) 

Those labels come straight from the GitHub webhook payload and are persisted verbatim (no name allow-list) by `LabelCapturingHandler#capture_labels`: [8](#0-7) 

The params schema only requires `labels` to be an array of objects with a `name` String — no format restriction, so any string (e.g. `PATH`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `RUBYOPT`) is accepted as a label name: [9](#0-8) 

`TaskCommands#env` then builds the process environment for every command run for that stack by merging, in order: engine base env, `@stack.env` (unfiltered, including the label keys), fixed engine keys, `deploy_spec.machine_env`, and finally `@task.env` (the correctly permit-filtered hash): [10](#0-9) 

Because `@stack.env` is merged *before* `@task.env`, any label-derived key that is not itself one of the task's declared variable names is never overwritten and survives into the final env hash unfiltered by `EnvironmentVariables#permit` — the very whitelist mechanism `lib/shipit/environment_variables.rb` implements [11](#0-10) . That final hash is passed to `Command.new(..., env:, chdir:)`, which stores it (coercing values to strings) and uses it when spawning the process: [12](#0-11)  and merged against `BASE_ENV`/`Bundler.unbundled_env` at process spawn time [13](#0-12) .

Attack flow: an unprivileged attacker (per the stated threat model, someone who can "label their own PR") opens a pull request against a repository with an active `ReviewStack`, and adds a label whose name collides with a security-relevant environment variable already present in `BASE_ENV`/the deploy host process, e.g. `PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, or `LD_PRELOAD`. GitHub's `labeled` webhook fires, `LabelCapturingHandler` persists `pull_request.labels` unfiltered, and on the next task/deploy run for that review stack, `ReviewStack#env` injects `"PATH" => "true"` (or similar) into the command environment ahead of `filter_envs`-protected values, with no `NotPermitted` check anywhere in this path.

Existing guards (`EnvironmentVariables#permit`, `filter_envs`, `filter_deploy_envs`, `filter_rollback_envs`) only ever validate hashes that are explicitly routed through them by controllers/`TaskDefinition`/`DeploySpec` — they are never applied to `Stack#env`/`ReviewStack#env`, which was not designed as user/attacker input but is nonetheless populated with attacker-controlled strings via PR labels.

### Impact Explanation
An attacker who can label their own pull request can inject arbitrary-named environment variables into every command run against that review stack (build, review checklist, deploy, custom task steps) via `Command`/`PTY.spawn`. Depending on which host environment variables are keyable (e.g. `RUBYOPT`, `BUNDLE_GEMFILE`, `LD_PRELOAD`, `GIT_SSH_COMMAND`), this can escalate to command/code execution on the deploy host — Critical severity (RCE via `Command`/`PTY.spawn`). The blast radius is scoped to review stacks/repositories where the attacker can label PRs (their own fork/PR against a monitored repo), but is repeatable on every relevant webhook event (`opened`, `labeled`, `reopened`) for that stack.

### Likelihood Explanation
Requires: a repository with `ReviewStack`s enabled (a standard Shipit review-app feature), the attacker being able to open/label a PR against it (explicitly granted in the stated threat model), and the review stack's task/deploy steps executing commands sensitive to one of the overridable env var names. No secrets, tokens, or privileged roles are needed — only the ability to add a label to one's own PR, which is a normal, low-cost, repeatable GitHub action.

### Recommendation
Do not use raw, attacker-controlled strings (PR label names) as environment-variable *keys*. Either: (1) whitelist/validate label names against a strict pattern (e.g. `\A[A-Z][A-Z0-9_]*\z` plus an explicit deny-list of sensitive names like `PATH`, `LD_PRELOAD`, `BUNDLE_*`, `RUBYOPT`, `GIT_*`), or (2) namespace label-derived variables under a fixed prefix (e.g. `LABEL_<NAME>`) so they cannot collide with process/base env keys, and (3) route `ReviewStack#env`'s label-derived hash through `EnvironmentVariables#permit` with an explicit whitelist before merging it into the command environment in `TaskCommands#env`.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_test.rb
require 'test_helper'

module Shipit
  class ReviewStackEnvLabelInjectionTest < ActiveSupport::TestCase
    test "PR label names are merged as unfiltered env keys, bypassing EnvironmentVariables#permit" do
      stack = shipit_review_stacks(:some_review_stack) # fixture with a pull_request
      stack.pull_request.update!(labels: ['PATH', 'BUNDLE_GEMFILE'])

      env = stack.env

      # Binding under test: keys(stack.env) ⊆ variable_definitions.map(&:name)
      # Expected (if not vulnerable): raises NotPermitted for unwhitelisted keys
      # Actual: no exception, and dangerous keys are present verbatim
      assert_includes env.keys, 'PATH'
      assert_includes env.keys, 'BUNDLE_GEMFILE'
      assert_equal 'true', env['PATH']
    end

    test "TaskCommands#env merges stack.env (with label keys) ahead of filtered task.env" do
      task = shipit_tasks(:review_stack_task)
      task.stack.pull_request.update!(labels: ['PATH'])

      commands = Shipit::TaskCommands.new(task)
      final_env = commands.env

      # PATH key from label survives even though it was never passed through
      # EnvironmentVariables#permit / filter_envs for this task.
      refute_nil final_env['PATH']
    end
  end
end
```

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
