### Title
Cross-repository forgery of commit CI status via webhook signature/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check authenticates a payload against the GitHub *organization* named in `repository.owner.login` (or `organization.login`), but the `status` event handler never re-checks that organization/repository against the commit it mutates — it looks the commit up **globally by SHA alone**. An attacker who is an admin of any org/repo already onboarded into this Shipit instance (and therefore knows that org's own `webhook_secret`, which they configured on their own GitHub webhook) can produce a validly-signed `status` webhook whose `repository.owner.login` matches their own org, while the `sha` field names a commit belonging to a completely different, victim stack/repository. The forged status is written onto that unrelated commit.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the payload's `repository.owner.login` (falling back to `organization.login`), fetches that org's `Shipit.github_app`, and verifies the HMAC using that org's `webhook_secret`: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the payload is dispatched to the matching handler with no further tie between the verified organization and the target of the mutation: [3](#0-2) 

`StatusHandler#process` resolves the target purely by `sha`, with **no repository/organization scoping at all**, unlike other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) that at least scope lookups through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`: [4](#0-3) [5](#0-4) 

This is the same "binding mismatch" bug class as the external report: the field that is actually *verified* (the organization owning the webhook secret, taken from `repository.owner.login`) is not the same field that is *acted upon* (the arbitrary `sha` used to select and mutate a `Commit` row that can belong to any repository in the installation). Concretely, the equality the engine implicitly relies on —
`organization authenticated by signature == organization/repository whose commit is mutated`
— is never enforced for the `status` event. An attacker only needs to control one legitimately onboarded org's webhook secret (their own) to forge a status write against a commit belonging to a stack for a completely different repository they have no access to.

### Impact Explanation
Commit statuses in Shipit are used to gate deploy safety checks (required/soft statuses shown on the stack and consulted when determining whether a commit is deployable). By forging a `state: "success"` status with an attacker-chosen `context`/`target_url` on a victim commit, an attacker can make an unrelated repository's commit appear to have passed CI/required checks it did not actually pass, potentially unlocking or masking risk for a deploy of that commit — this falls under "unauthorized deploy" impact, since the status data influencing deploy-readiness decisions is falsified for a repository the attacker does not control.

### Likelihood Explanation
The attacker needs: (1) admin access to a GitHub org/repo that is already onboarded to this Shipit instance (so `Shipit.github(organization: ...)` resolves and has a `webhook_secret` the attacker set themselves), and (2) knowledge of a target commit `sha` in a victim stack (SHAs are public in most GitHub repos, and Shipit stacks display commit histories). No Shipit session, API token, or the victim org's secret is required — only the attacker's own webhook secret, which they legitimately possess. This is a realistic multi-tenant scenario for any Shipit deployment onboarding more than one organization.

### Recommendation
Scope the `status` (and any similarly unscoped) handler's lookup to the organization/repository that was actually verified by the signature check, e.g. pass the verified `repository_owner`/`full_name` through to handlers and require `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: verified_owner })` (or equivalent), rather than a bare `Commit.where(sha: ...)`. More generally, every webhook handler should validate that the payload's `repository.full_name` belongs to the same organization whose secret was used to verify the signature, closing the gap between the authenticated organization and the entity actually mutated.

### Proof of Concept
1. Attacker is an admin of `attacker-org/some-repo`, which is onboarded to the target Shipit instance; attacker configures the GitHub webhook secret themselves and thus knows it.
2. Attacker identifies a `sha` of a commit belonging to `victim-org/victim-repo`, a stack tracked by the same Shipit instance (e.g., visible from the stack's public commit history/UI).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/fake",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker_org_webhook_secret, body)` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully because it was signed with that org's own secret.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matches the victim's commit (no relation to `attacker-org` is ever checked), and calls `commit.create_status_from_github!(params)`, writing the forged `success` status onto the victim commit.
