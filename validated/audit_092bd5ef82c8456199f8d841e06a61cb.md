### Title
`StatusHandler#process` writes `Status` records for any `Commit` matching a bare SHA across all repositories/stacks, with no repository scoping - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no join to `stack.repository` or use of the base `Handler#stacks` helper, unlike `PushHandler` and `CheckSuiteHandler` which properly scope through `stacks` (derived from `payload['repository']['full_name']`). A `status` webhook whose signature is validated only against `repository_owner`'s org secret (`Shipit.github(organization: repository_owner)`) can therefore create/update `Status` rows on any `Commit` record in the database sharing that SHA, regardless of which repository originated the event.

### Finding Description
The broken binding: the intended invariant is `status.stack.repository.full_name == payload['repository']['full_name']` for every `Status` created from a webhook. The actual code enforces only `status.commit.sha == payload['sha']`, with no repository equality check at all.

Path: `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event('status') => [StatusHandler]` [3](#0-2) [4](#0-3) . Before dispatch, `verify_signature` validates the HMAC signature using the GitHub App/org secret keyed by `repository_owner = params.dig('repository','owner','login')` [5](#0-4)  — this only proves the request came from GitHub for *that org's* webhook, not that the `sha`/`context` fields are scoped to any particular repository, since the `status` payload schema in `StatusHandler` doesn't require or use `repository` at all: it only requires `sha`, `state`, and optional `context`/`branches` [6](#0-5) .

`Handler` (the base class) exposes a properly scoped `stacks` method for exactly this purpose: `Repository.from_github_repo_name(repository_name)&.stacks` [7](#0-6) . `PushHandler` and `CheckSuiteHandler` both use it to constrain their side effects to the originating repository's stacks [8](#0-7) [2](#0-1) . `StatusHandler` instead does a bare global `Commit.where(sha: params.sha)` query, so it can and does write into `commit.create_status_from_github!` for any stack whose commit happens to share that SHA [9](#0-8) .

Once a `Status` row is created, `Status#add_status`/`add_status` in `Commit` fires `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges if new_status.pending? || new_status.success?` on state transitions [10](#0-9) , which is exactly the mechanism that can flip a victim stack's merge/deploy gating (via `required contexts`) based on an attacker-controlled `state`/`context` pair, provided the SHA collides with a commit tracked by the victim stack.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `drop_unhandled_event`) check only that the request is a validly-signed `status` event from *some* org Shipit trusts; none of them constrain the `sha` field to the repository that authenticated the request, because the `status` GitHub payload's `repository` object is never consulted by `StatusHandler`.

### Impact Explanation
A repository that has a legitimately configured Shipit webhook (i.e., any org/repo already onboarded to this Shipit instance) can emit a `status` event whose `sha` matches a `Commit` row belonging to an entirely different stack/repository, causing Shipit to write a `Status` for that unrelated commit and potentially flip `deployable_status`/merge-scheduling logic for a victim stack it does not control. This matches the rules' Critical category: "a payload for one repository mutating another's stack, commit, task or team." The practical severity depends heavily on SHA collision feasibility across independently-authored repositories (git SHA-1 is effectively impossible to guess/collide against an arbitrary unrelated commit), which limits real-world exploitability to scenarios where the same commit SHA is legitimately shared across multiple Shipit stacks (e.g., the same repo tracked by more than one stack, mirrors, or forks whose histories overlap with the upstream) rather than a fully attacker-chosen victim SHA.

### Likelihood Explanation
Exploitation requires (a) an org/repo already onboarded and signature-validated by this Shipit instance (attacker needs push/webhook-emitting access to *some* onboarded repo, not the victim's), and (b) a SHA value that also exists as a `Commit` in the victim stack — which in general requires either the same repository being tracked by multiple stacks, or coincidental/engineered SHA sharing (e.g., forked repos with shared commit history, cherry-picks, or PR branches). I could not verify from the available code/tests a concrete, reliable way for an attacker to force an arbitrary, fully independent victim stack's SHA to collide, so likelihood is bounded by this precondition rather than being trivially "any attacker, any victim."

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve `stacks` via the `repository.full_name` in the payload and constrain the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or an equivalent join through `Stack`/`Repository`), rather than the unscoped `Commit.where(sha: params.sha)`.
