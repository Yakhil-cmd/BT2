### Title
Organization bound by webhook signature verification is never checked against the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook delivery against the GitHub App/secret belonging to one organization (extracted from the payload's `repository.owner.login`), but the handlers that actually perform writes (sync a stack, trigger CI status updates, provision review-stacks, etc.) resolve the target `Repository`/`Stack` from a *different, unchecked* payload field: `repository.full_name`. Nothing ties these two values together, so a payload can be crafted to authenticate as "Org A" while acting on a stack that belongs to "Org B".

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration (and thus the HMAC secret it verifies the request against) purely from the payload body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Shipit explicitly supports multiple GitHub Apps/organizations, each with its own independently-configured `webhook_secret`: [3](#0-2) 

Once the signature check passes, `WebhooksController#create` dispatches the raw JSON body to every registered handler for the event, with no further binding of the verified organization to what the handler is allowed to touch: [4](#0-3) 

Every handler resolves its target repository from `payload.dig('repository', 'full_name')` — an entirely separate field from the one used for signature verification, and one that is never cross-checked against the organization that was actually authenticated: [5](#0-4) 

`Repository.from_github_repo_name` performs a plain database lookup by `owner`/`name` parsed out of that string, with no relation to which app/secret validated the request: [6](#0-5) 

Concretely, `PushHandler#process` uses this repository/stack resolution to trigger a real sync against GitHub for whatever stacks match `full_name` + branch: [7](#0-6) 

The equality that should hold but does not: `organization authenticated by verify_signature (repository.owner.login) == organization owning the repository/stack the handler mutates (repository.full_name)`. Before any pull request in this area, the codebase never asserts this equality; the two fields are independently attacker-suppliable within the same signed body, and only one of them is covered by the meaning of "authenticated."

### Impact Explanation
An operator who legitimately owns one onboarded GitHub organization in a multi-org Shipit deployment (and therefore legitimately knows *that organization's* `webhook_secret`, since docs instruct each org to create/register its own GitHub App and secret) can compute a valid `X-Hub-Signature` for an arbitrary JSON body and POST it directly to `/webhooks` — this endpoint is reachable by anyone on the network, not just github.com, since verification is a pure HMAC check on the raw body. By setting `repository.owner.login` (or `organization.login`) to their own org (so `verify_signature` passes) while setting `repository.full_name` to `"<victim-org>/<victim-repo>"`, they cause handlers such as `PushHandler` to look up and act on stacks belonging to a completely unrelated organization/repository that they have no legitimate access to. This is a cross-repository write / forced sync (and, on stacks with `continuous_deployment` enabled, can precipitate an unauthorized deploy), matching the Critical-impact category "cross-repository writes, or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires the attacker to control (or be an admin of) at least one organization already configured in the multi-org Shipit `secrets.yml`, and knowledge of that organization's own webhook secret, which the docs indicate is provided by the organization when the integration is set up. No Shipit session, `ApiClient` token, or GitHub private key is needed — only the ability to send an HTTP POST with a computable HMAC to the public `/webhooks` endpoint. This is directly analogous to the courier bug's low-but-nonzero-probability griefing vector: a legitimate-but-limited-trust actor (one tenant org) can act outside its intended trust boundary (another tenant's repo/stack) because the verification step and the mutation step trust two different, unlinked fields.

### Recommendation
After `verify_signature` succeeds, thread the authenticated organization through to handler dispatch and require every handler to confirm that `repository.full_name`'s owner matches the organization that was actually verified (or resolve/validate the repository via the verified organization rather than trusting the raw payload field). Reject the event if the two disagree.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org example).
2. As an admin of `OrgA`, compute `sha1=HMAC(OrgA_webhook_secret, body)` for a crafted push-event JSON body where:
   - `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`)
   - `repository.full_name = "OrgB/victim-repo"`
   - `ref = "refs/heads/<victim-branch>"`, `after = "<attacker-chosen sha>"`
3. POST this body with header `X-Github-Event: push` and `X-Hub-Signature: sha1=...` to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` [5](#0-4)  and invokes `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack — despite the request never being authenticated against `OrgB`.
