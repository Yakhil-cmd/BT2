### Title
Missing ArbStore fee-cut for fixed-denomination (indivisible) assets in arbiter contract shared-address definition - ([File: arbiter_contract.js])

### Summary
`deriveSharedAddress()` in `arbiter_contract.js` builds the smart-contract definition that governs how funds locked in an arbiter-contract shared address may be spent. For divisible, non-private assets, the definition mandates that when the paying party spends the funds it must simultaneously pay the ArbStore's cut (`arbstoreInfo.cut`) to `arbstoreInfo.address`. For assets with `fixed_denominations` (indivisible/textcoin-style assets), this requirement is unconditionally skipped, and `complete()` mirrors this by sending the peer the **full** `objContract.amount` with no output to the ArbStore at all, exactly the same bug class as the reported "missing fee-cut before payout" issue.

### Finding Description
In `deriveSharedAddress()`: [1](#0-0) 
`isFixedDen` and `hasArbStoreCut` are computed, and the payer-side spending condition only requires paying the reduced amount (and correspondingly requires the arbstore cut output) when `!isFixedDen && hasArbStoreCut`: [2](#0-1) 

Because `isFixedDen` disables the cut requirement, an arbiter contract created for a fixed-denomination asset produces a shared-address definition that never obligates the payer to send anything to `arbstoreInfo.address` — the full `contract.amount` can be spent straight to the counterparty.

This is mirrored client-side in `complete()`, which is the function that actually consummates the payment out of the shared address: [3](#0-2) 
The fee-cut branch (`readSharedAddressDefinition` + computing `peer_amount`/`arbstore_amount`) is entered only `if (objContract.me_is_payer && !(assetInfo && (assetInfo.fixed_denominations || assetInfo.is_private)))`. For fixed-denomination assets (or private assets, handled separately via a data-feed unlock with no cut at all), execution falls into the `else` branch, which sends `objContract.amount` in full to `objContract.peer_address` with no `arbstore_amount` output whatsoever — even though `me_is_payer` is true and the contract is being genuinely completed, not refunded.

This is the direct analog of the reported bug class: a fee that should be deducted before funds are paid out to the counterparty is silently skipped for a subset of asset types, and the treasury-equivalent party (the ArbStore) never receives its due cut.

### Impact Explanation
Any user can create an arbiter contract using an indivisible (`fixed_denominations`) asset and pay out the contract amount in full to the counterparty, bypassing the ArbStore's service fee entirely. Since the shared-address definition itself (not just the wallet UI helper) never requires the ArbStore output for such assets, this is not merely a display/composition bug — the funds can be spent to the counterparty without ever compensating the arbiter/ArbStore, resulting in a guaranteed, systematic loss of income for every arbiter contract that uses a fixed-denomination asset, with no way for the ArbStore to enforce or reclaim its cut after the fact.

### Likelihood Explanation
High for any contract involving a fixed-denomination asset: the condition is deterministic (based purely on `assetInfo.fixed_denominations`), requires no race condition or timing, and is reachable by any two contracting parties choosing such an asset — a normal, unprivileged usage path (asset issuer defines `fixed_denominations: true`, then any user creates an arbiter contract in that asset).

### Recommendation
Either (a) explicitly disallow arbiter contracts denominated in `fixed_denominations` (and `is_private`) assets when the arbiter/ArbStore has a nonzero `cut`, informing users up front, or (b) implement a cut mechanism compatible with indivisible assets (e.g., requiring the payer to additionally transfer a matching amount of a divisible asset, or selecting coin denominations that allow an exact split) so the definition in `deriveSharedAddress()` and the payout logic in `complete()` always enforce payment of the ArbStore's cut whenever `arbstoreInfo.cut > 0`, regardless of the asset's denomination type.

### Proof of Concept
1. An asset issuer defines an asset with `fixed_denominations: true` (an indivisible/textcoin asset).
2. Party A (payer) and Party B create an arbiter contract for this asset with an arbiter whose ArbStore has `cut > 0` (verified via `arbiters.getArbstoreInfo`).
3. `deriveSharedAddress()` builds the definition without any ArbStore cut condition (`isFixedDen` short-circuits lines 500/509/513 in `arbiter_contract.js`), since the "has output" clauses collapse to `contract.amount` for both sides and no arbstore "has" clause is appended.
4. Party A pays the full `objContract.amount` into the shared address via `pay()`.
5. Party A calls `complete()`; because `assetInfo.fixed_denominations` is true, the code takes the `else` branch and sends the entire `objContract.amount` to `objContract.peer_address` with zero output to `objContract.arbstore_address`.
6. The transaction is fully valid per the shared address's own bytecode/definition (which never required an ArbStore output), so it is accepted by the network — the ArbStore permanently loses its service fee for this and any subsequent fixed-denomination-asset contract.
