### Title
Unauthorized STX stacking lock via `StackStxOp` sender spoofing through unsigned PreStxOp output 0 - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::get_sender_txid` only verifies that the StackStx Bitcoin transaction spends `vout == 1` of a prior `PreStxOp` transaction, while the `sender` StacksAddress used for locking STX is taken from that PreStxOp's `output` field, which is parsed from `outputs.get(0)` — an address that requires no signature to populate. This allows an attacker to name an arbitrary victim address as the stacking `sender` while proving nothing more than control over an unrelated change output.

### Finding Description
The broken equality is: `StackStxOp.sender` (the account whose STX get locked and whose reward flows are authorized) should equal the Bitcoin identity that cryptographically authorized the operation. In this code path they diverge.

`PreStxOp::parse_from_tx` derives `output` purely from `outputs.get(0)`'s address, with no signature requirement — it is simply a payment destination chosen unilaterally by whoever constructs the PreStx transaction: [1](#0-0) 

`StackStxOp::get_sender_txid` then only checks that the spending input of the follow-up StackStx transaction references `vout == 1` of that PreStx txid — never `vout == 0`: [2](#0-1) 

`StackStxOp::parse_from_tx` then takes the resolved `PreStxOp.output` and stores it verbatim as `sender`, with no further authorization check tying it to the key that signed the spending input: [3](#0-2) 

Exploit flow:
1. Attacker builds a PreStx transaction from their own Bitcoin UTXOs, with `output[0]` set to victim `V`'s Bitcoin address (public information — no cooperation or signature from `V` is required to receive to an address) and `output[1]` set to an address the attacker controls.
2. Attacker then builds a StackStx transaction whose single input spends `output[1]` of the PreStx tx (signed entirely by the attacker) and whose own `output[0]` (the `reward_addr`) is attacker-controlled.
3. `Burnchain` op-processing resolves the PreStxOp, extracts `sender = V`, validates only that the spending input is `vout == 1` (satisfied, since the attacker controls output 1), and accepts a `StackStxOp` with `sender = V`.
4. Downstream Stacks chainstate processing locks STX held by `V`'s account for `num_cycles`, using `sender` as the account identity with no additional Stacks-level signature check — the burnchain transaction itself is treated as the sole authorization layer, and that layer was never actually signed by `V`.

Existing guards do not prevent this: `get_sender_txid` checks only the outpoint index of the spent input, not which address/key produced output 0; `PreStxOp::parse_from_tx` never records or checks who is entitled to receive output 0; and `StackStxOp::check` only validates `stacked_ustx`, `num_cycles`, and `signer_key` format — none of which validate `sender` authorization.

### Impact Explanation
The attacker can force-lock any existing Stacks account's unlocked STX for up to `POX_MAX_NUM_CYCLES` cycles without that account holder's participation or signature, and redirect the associated PoX/stacking reward stream to an address the attacker controls (`reward_addr` is taken from the attacker's own StackStx transaction output 0). This is theft of stacking rewards derived from a lock the victim never authorized, and an involuntary (though time-bounded) freeze of the victim's STX — matching the "theft ... of locked STX or sBTC rewards" and "unsigned stacking action" categories. It is repeatable against any address with a spendable balance, each time costing only the Bitcoin transaction fees for two chained transactions.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only enough Bitcoin to fund the PreStx and StackStx transaction fees, and no interaction with the victim or privileged role is required. It works in any cycle/phase as long as the victim account has unlocked STX eligible for stacking (subject to any minimum-stacking-amount checks enforced later in the PoX Clarity layer, which do not address authorization). The attack is fully attacker-controlled, cheap, and repeatable across cycles and victims.

### Recommendation
Require that the address which receives `PreStxOp` output 0 (the `sender`/stacker identity) is the same key that signs the spending input of the follow-up StackStx transaction — e.g., by verifying the StackStx transaction's input signature/pubkey against the hash encoded in `PreStxOp.output`, or by requiring the PreStx transaction's own inputs (already signed by its creator) to match the address placed in output 0, rather than trusting an arbitrary, unauthenticated destination address as the locking principal.

### Proof of Concept
Rust integration test (in the style of `stackslib/src/burnchains/tests/db.rs`):
1. Construct a `PreStxOp`/underlying Bitcoin tx with `output[0]` = victim `V`'s address, `output[1]` = attacker's address, inputs signed by attacker's key.
2. Construct a `StackStxOp` Bitcoin tx whose sole input spends `output[1]` of the PreStx tx (signed by attacker), with attacker-controlled `reward_addr`.
3. Run both through `Burnchain` op processing (as in `stackslib/src/burnchains/tests/db.rs`) and assert:
   - `StackStxOp.sender == V` (left side of broken equality: locked-account identity).
   - The Bitcoin input actually authorizing the StackStx tx is signed by the attacker's key, not `V`'s (right side of broken equality: cryptographic authorizer).
4. Assert these two are unequal, confirming `V`'s STX get locked and rewards directed to `reward_addr` (attacker) without any signature from `V`.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
