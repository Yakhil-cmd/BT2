## Analysis

The strongest analog to the ERC20Vault bug (a downstream action keyed off a field that was never the field validated for authenticity) is in `Shipit::WebhooksController` combined with `Shipit::Webhooks::Handlers::Handler`.

**The binding that breaks:** `organization authenticated == repository written`.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` selects the GitHub App (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (fallback `organization.login`): [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` picks the org-specific config (`github_app_config(organization)`), which contains the org-specific `webhook_secret`, in multi-org deployments: [3](#0-2) 
- Once signature verification passes, event handlers determine which `Repository`/`Stack` to act on using a **different field of the same JSON body**: `payload.dig('repository', 'full_name')`, via `Handler#repository_name`/`#stacks`, or the `params.repository.full_name` used directly in `PullRequest::LabeledHandler#repository` and `ClosedHandler#repository`: [4](#0-3) [5](#0-4) 

Nothing in the code enforces that `repository.owner.login` (the field used to pick the signing secret) is consistent with `repository.full_name` (the field used to pick the repository/stack that gets acted on). These are two independent keys inside the same attacker-supplied JSON payload — exactly the same class of bug as the ERC20Vault case, where one field of a message was verified/expected but a different field of the same message was actually used downstream.

**Exploit shape:** In a multi-organization Shipit deployment (`docs/setup.md` explicitly documents this mode, each org with its own `webhook_secret`) [6](#0-5) 
, a party that legitimately holds the webhook secret for their own installed GitHub App on `OrgA` can compute a valid `X-Hub-Signature` for an arbitrary JSON body of their choosing. They then submit a payload where `repository.owner.login` (or `organization.login`) is `"OrgA"` (so `verify_signature` picks OrgA's secret and passes) but `repository.full_name` is `"OrgB/victim-repo"` (so the handler acts on a repository/stack belonging to a completely different organization hosted on the same Shipit instance). This lets an actor authorized only for their own org's webhooks inject forged push/status/pull_request events against another organization's stacks — e.g. forging a `pull_request.labeled` event to flip `archive?`/`unarchive?` on `OrgB`'s review stacks, or forging `push`/`status` events that drive `stack.sync_github` and commit status creation for `OrgB`'s repositories.

This matches the explicitly allowed impact category "cross-repository writes" / escalation across the org boundary that Shipit's own multi-org design is supposed to enforce with per-org `webhook_secret`s.

### Title
Webhook signature verified against `repository.owner.login`'s organization while handlers act on the unrelated `repository.full_name` field, enabling cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` binds HMAC verification to the organization derived from `repository.owner.login`/`organization.login`, but every webhook handler (`Handler#repository_name`, `PullRequest::LabeledHandler#repository`, `PullRequest::ClosedHandler#repository`, etc.) resolves the repository to act on from the independent `repository.full_name` field of the same payload. No code ties these two fields together.

### Finding Description
`verify_signature` fetches the `GitHubApp` for the organization named in `repository.owner.login` (or `organization.login`) and verifies the raw body against that organization's `webhook_secret`: [7](#0-6) 
`Shipit.github(organization:)` resolves per-org secrets via `github_app_config(organization)` in multi-org mode: [3](#0-2) 
Once verified, `WebhooksController#create` dispatches the parsed JSON to handlers unchanged: [8](#0-7) 
Handlers then resolve the target `Repository`/`Stack` using `repository.full_name`, not `repository.owner.login`: [4](#0-3) [9](#0-8) 
Since `repository.owner.login` and `repository.full_name` are independent keys in attacker-controlled JSON, a payload can be crafted where they name different organizations/repositories, allowing verification against org A's secret while the write occurs against org B's repository.

### Impact Explanation
This breaks the org-isolation guarantee that per-organization `webhook_secret`s are documented to provide in multi-org Shipit deployments. An actor holding only one organization's webhook secret can forge events (`pull_request.labeled`/`closed` archiving or unarchiving review stacks, `push`/`status` events driving `stack.sync_github` and commit status writes) targeting a different organization's repositories/stacks hosted on the same instance — a cross-repository write across a trust boundary the application is designed to enforce.

### Likelihood Explanation
Requires (a) a Shipit deployment configured with the documented multi-organization `github:` secrets layout, and (b) the attacker legitimately controlling one organization's GitHub App/webhook secret in that deployment (e.g., an org admin of one tenant of a shared Shipit instance). Given that scenario, forging the payload is trivial — HMAC-sign an arbitrary JSON body with the known secret and set mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
After signature verification, re-derive/require that the repository owner used for authentication (`repository.owner.login`/`organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, or better, always verify the signature using the resolved target repository's configured organization/secret rather than an untrusted top-level field, and reject the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit configured for multi-org mode with `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`).
2. As the operator of the GitHub App on `OrgA`, compute `X-Hub-Signature` (`sha1=HMAC(OrgA_webhook_secret, body)`) over a crafted JSON body: `{"action":"labeled","pull_request": {...}, "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "sender": {"login": "attacker"}}`.
3. POST to the webhooks endpoint with `X-Github-Event: pull_request`; `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature validates.
4. `PullRequest::LabeledHandler#repository` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and archives/unarchives `OrgB`'s review stack, even though the requester only authenticated for `OrgA`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
