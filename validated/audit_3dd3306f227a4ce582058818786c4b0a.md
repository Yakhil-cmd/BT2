### Title
Missing `nonReentrant` Guard on `_requestERC20Transfer` / `onERC20Received` Enables Duplicate `requestNonce` Emission, Permanently Losing Bridged ERC20 Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20._requestERC20Transfer`, reachable via the public `onERC20Received` entry point, increments `requestNonce` **after** making external calls to the registered token contract. A registered ERC20 token with transfer-hook semantics (e.g., ERC-777, tokens with `onTokenTransfer` callbacks) can reenter `onERC20Received` during fee payment or burn, causing two `RequestValueTransfer` events to be emitted with the **same** `requestNonce`. The counterpart bridge's nonce-deduplication logic will fulfill only one; the other is permanently dropped, burning the user's tokens on the source chain with no corresponding release on the destination chain.

---

### Finding Description

`BridgeTransferKLAY._requestKLAYTransfer` is explicitly marked `nonReentrant` and `BridgeFee._payKLAYFeeAndRefundChange` carries the comment *"Caller of this function must be nonReentrant"*. The ERC20 analogue, `_requestERC20Transfer`, carries no such guard. [1](#0-0) 

The ERC20 path:

```
onERC20Received (public, no access control)
  └─ _requestERC20Transfer (internal, onlyRegisteredToken, onlyUnlockedToken)
       ├─ _payERC20FeeAndRefundChange(...)   ← external call to token
       ├─ ERC20Burnable(_tokenAddress).burn(_value)  ← external call to token
       ├─ emit RequestValueTransfer(..., requestNonce, ...)
       └─ requestNonce++                     ← state update LAST
``` [2](#0-1) 

`requestNonce` is read before the external calls and incremented only after them. A reentrant call that enters `_requestERC20Transfer` while the outer call is inside `_payERC20FeeAndRefundChange` or `burn` will observe the **same** `requestNonce = N`, emit `RequestValueTransfer(nonce=N)`, and increment to `N+1`. When control returns to the outer call, it emits `RequestValueTransfer(nonce=N)` a second time and increments to `N+2`.

The `onERC20Received` entry point is `public` with no caller restriction: [3](#0-2) 

The only gate is `onlyRegisteredToken`, which checks `msg.sender` (the token address). Any registered token with a transfer hook satisfies this gate without any additional privilege.

By contrast, `handleERC20Transfer` and `handleERC721Transfer` also lack `nonReentrant` (unlike `handleKLAYTransfer`), but their state updates precede the external call, so the same nonce cannot be replayed there. The request-side path is the critical one. [4](#0-3) [5](#0-4) [6](#0-5) 

---

### Impact Explanation

Two `RequestValueTransfer` events are emitted with identical `requestNonce = N`. The counterpart bridge's `_lowerHandleNonceCheck` / `_updateHandleNonce` logic processes nonce `N` exactly once; the second event is silently rejected. The user's tokens are burned (or locked) on the source chain with no corresponding mint or release on the destination chain — a permanent, unrecoverable loss of bridged assets.

---

### Likelihood Explanation

Token registration is an operator action, but operators routinely register legitimate tokens. ERC-777 tokens and tokens with `onTokenTransfer` / `tokensToSend` hooks are common in production. An operator who registers such a token without auditing its hook behavior unknowingly opens this path. The trigger is a normal user `requestValueTransfer` call — no attacker privilege is required beyond the token being registered.

---

### Recommendation

Add `nonReentrant` to `_requestERC20Transfer` (or equivalently to `onERC20Received`), consistent with the existing protection on `_requestKLAYTransfer`:

```solidity
// BridgeTransferERC20.sol
function _requestERC20Transfer(
    address _tokenAddress,
    address _from,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    internal
    onlyRegisteredToken(_tokenAddress)
    onlyUnlockedToken(_tokenAddress)
    nonReentrant          // ← add this
{
```

Also add `nonReentrant` to `handleERC20Transfer` and `handleERC721Transfer` for defence-in-depth, matching `handleKLAYTransfer`.

---

### Proof of Concept

1. Operator registers a token `MaliciousERC20` (implements ERC-777 send-hook or `onTokenTransfer`) with the bridge.
2. User calls `MaliciousERC20.requestValueTransfer(bridge, amount, ...)`, which triggers `bridge.onERC20Received(user, dest, amount, feeLimit, data)`.
3. Bridge enters `_requestERC20Transfer`; reads `requestNonce = N`; calls `_payERC20FeeAndRefundChange` → internally calls `MaliciousERC20.transferFrom(user, feeReceiver, fee)`.
4. `MaliciousERC20.transferFrom` fires its hook, which calls `bridge.onERC20Received(user, dest, amount, feeLimit, data)` again (reentrant).
5. **Reentrant call**: reads `requestNonce = N` (unchanged), makes external calls, emits `RequestValueTransfer(nonce=N)`, sets `requestNonce = N+1`, returns.
6. **Outer call** resumes: emits `RequestValueTransfer(nonce=N)` again, sets `requestNonce = N+2`.
7. Counterpart bridge operators observe two events with `nonce=N`. `handleERC20Transfer` processes the first; the second fails `_lowerHandleNonceCheck` and is dropped.
8. User's tokens are burned/locked twice on the source chain; only one release occurs on the destination chain. Net loss: one transfer's worth of bridged assets. [7](#0-6) [8](#0-7)

    function _requestERC20Transfer(
        address _tokenAddress,
        address _from,
        address _to,
        uint256 _value,
        uint256 _feeLimit,
        bytes memory _extraData
    )
        internal
        onlyRegisteredToken(_tokenAddress)
        onlyUnlockedToken(_tokenAddress)
    {
        require(isRunning, "stopped bridge");
        require(_value > 0, "zero ERC20 token amount");

        uint256 fee = _payERC20FeeAndRefundChange(_from, _tokenAddress, _feeLimit);

        if (modeMintBurn) {
            ERC20Burnable(_tokenAddress).burn(_value);
        }

        emit RequestValueTransfer(
            TokenType.ERC20,
            _from,
            _to,
            _tokenAddress,
            _value,
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }

    // Caller of this function must be nonReentrant.
    // - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant
    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
