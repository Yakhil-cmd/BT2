Based on my investigation, I found a genuine admission-boundary weakness in the multisig approval-set binding logic, distinct from generic mempool/vm-validator flows (which are already gated correctly, per `aptos-move/framework/aptos-framework/sources/transaction_validation.move`).

### Title
Multisig transaction execution can bind approvals to a different payload than the one voted on when the payload-mismatch check is not enabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::create_transaction` stores a transaction's full `payload` on-chain with `payload_hash = none` [1](#0-0) . Owners then vote via `approve_transaction`/`reject_transaction`, which only record a boolean vote keyed by `sequence_number` — they never re-validate the actual bytes being approved [2](#0-1) . Final admission of the payload happens only inside `validate_multisig_transaction`, which is invoked by the VM as part of the transaction prologue for `MultisigTransaction` — i.e., at the transaction-admission boundary, not at execution/business logic [3](#0-2) .

### Finding Description
In `validate_multisig_transaction`, the payload actually supplied by the executing caller (`payload: vector<u8>`) is only checked against the on-chain stored payload under a feature gate:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty())
{
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, ...EPAYLOAD_DOES_NOT_MATCH);
}
``` [4](#0-3) 

Crucially, this equality check is the *only* binding between the votes an owner group cast and the actual bytes that will be executed as the multisig signer, in the case where the transaction was created via `create_transaction` (full payload stored, `payload_hash = none`). The `payload_hash.is_some()` branch that performs a `sha3_256` comparison is skipped entirely for this transaction type, since `payload_hash` is `none` [5](#0-4) . So the only remaining defense — the raw `payload == stored_payload` equality — is gated by `features::abort_if_multisig_payload_mismatch_enabled()`. If that feature flag is not enabled, an owner submitting the `MultisigTransaction` (who already has "enough approvals" counted purely by `sequence_number`, per `can_be_executed`/`can_execute`) can supply an arbitrary, unapproved `payload` to the VM at admission time, and it will be accepted and executed as the multisig account, since the quorum/timelock checks only look at vote counts for the `sequence_number`, never at the specific bytes [6](#0-5) .

This is the same admission-analog class as the external report: a critical binding check ("does the executed content match what was authorized") is conditionally skipped rather than being an unconditional invariant, producing a state transition (execution as the multisig signer) that the approval set never actually authorized.

### Impact Explanation
If the feature flag defaults to disabled (its very existence and naming — an opt-in "abort if mismatch" flag rather than an always-on check — strongly suggests it was introduced to *patch* pre-existing unchecked behavior), any single owner of a multisig account who can reach quorum count (e.g., colludes with or is one of the approving owners, or simply is the executor once threshold is met) can execute a completely different, unapproved entry function/script as the multisig account signer. This breaks the fundamental multisig approval-set invariant ("approval binds to a specific payload") and can lead to unauthorized fund transfers, owner-list tampering, or arbitrary module calls under the multisig account's authority — a critical, protocol-level authorization bypass.

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is turned on by default/via governance on the target network. I was not able to confirm this default within the available tool budget — my searches for the feature's default value in `features.move`/`on_chain_config` did not resolve before the iteration limit was reached. If the flag is enabled by default on mainnet, this specific path is not exploitable today; if it is off by default (common for defensively-added feature-gated fixes), it is directly exploitable by any multisig owner with sufficient votes on `sequence_number`.

### Recommendation
Make the raw-payload equality check (`payload == *stored_payload`) an unconditional invariant whenever `transaction.payload.is_some()`, independent of the `abort_if_multisig_payload_mismatch_enabled` feature flag, mirroring the unconditional `sha3_256` hash check already performed in the `payload_hash.is_some()` branch. Confirm and, if necessary, force-enable `abort_if_multisig_payload_mismatch_enabled` via governance on all networks before treating this as resolved.

### Proof of Concept
1. Owner A creates a multisig transaction via `create_transaction(owner_A, multisig_account, payload_A)` (a benign transfer), which stores `payload_A` on-chain with `payload_hash = none`.
2. Owners B (and C if needed) call `approve_transaction` on that `sequence_number`, believing they are approving `payload_A`.
3. Once quorum (`num_signatures_required`) is met for that `sequence_number`, any owner submits a `MultisigTransaction` to the VM with a *different* `payload_B` (e.g., a transfer to an attacker-controlled address, or an owner-list swap).
4. If `features::abort_if_multisig_payload_mismatch_enabled()` is false, `validate_multisig_transaction` never compares `payload_B` to `payload_A`; only the vote-count and timelock checks execute, both of which pass because they are keyed solely by `sequence_number`.
5. `payload_B` executes as the multisig account signer despite never having been voted on by the other owners.

**Caveat**: I could not fully verify (a) the default enablement state of `abort_if_multisig_payload_mismatch_enabled`, and (b) the exact code path in `aptos-move/aptos-vm/src/aptos_vm.rs` that supplies the caller-controlled `payload` argument into `validate_multisig_transaction` at transaction-prologue time (my targeted grep for `validate_multisig_transaction`/`MultisigTransactionPayload` in that file returned no matches, conflicting with an earlier broader search that reported matches). Given the ask-only nature and the tool-iteration limit, I recommend a Devin session with full repo/terminal access to confirm the feature flag's default and trace the exact VM call site before treating this as a confirmed, exploitable-today vulnerability.
