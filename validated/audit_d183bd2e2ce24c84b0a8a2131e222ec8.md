### Title
Webhook signature is verified against a GitHub organization derived from an attacker-controlled payload field, while the handler dispatch acts on a different, unchecked payload field (`repository.full_name`), enabling cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) used to validate the HMAC signature by reading `repository.owner.login` straight out of the untrusted JSON body [1](#0-0) [2](#0-1) . Once the signature is accepted, the actual event handlers dispatched via `Shipit::Webhooks.for_event(event)` do not re-use that same organization value; instead they resolve the target `Repository`/`Stack` from a *different* field of the same body, `repository.full_name` [3](#0-2) . In a multi-organization Shipit deployment — a supported, documented configuration where each GitHub org has its own `app_id`/`webhook_secret` [4](#0-3) [5](#0-4)  — this creates a binding break: `organization that authenticated` ≠ `repository that is written`.

### Finding Description
`Shipit.github(organization:)` looks up a distinct `GitHubApp` instance (with its own `webhook_secret`) per configured organization [4](#0-3) . `WebhooksController#verify_signature` picks which secret to HMAC-verify the raw body against using `repository_owner`, which is read from the JSON body itself (`params.dig('repository','owner','login')`) — a value fully controlled by whoever crafts the payload, not by GitHub's transport layer [6](#0-5) [7](#0-6) .

Because the HMAC is computed over the *entire* raw request body, an attacker who legitimately controls one configured organization ("OrgA", with its own real `webhook_secret`, e.g. because they administer OrgA's GitHub App installation and can trigger genuine webhooks or forge a body themselves since they know OrgA's secret) can construct a JSON body where:
- `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's `GitHubApp`/secret, and the attacker signs the whole body correctly with a secret they know), while
- `repository.full_name = "OrgB/some-tracked-repo"` (any other organization's repository already tracked in this Shipit instance).

`verify_signature` passes because the signature matches OrgA's secret. `WebhooksController#create` then dispatches to the registered handler for the event with the full, forged payload [8](#0-7) . Every handler resolves its target repository/stack via `Handler#repository_name`/`#stacks`, which reads `payload.dig('repository', 'full_name')` — i.e. `"OrgB/some-tracked-repo"` — with no cross-check against the organization that was actually used to verify the signature [9](#0-8) . For example `PushHandler#process` will find OrgB's stacks by branch and immediately call `stack.sync_github(expected_head_sha: params.after)` [10](#0-9) , and the `status` event handler (exercised in `test/controllers/webhooks_controller_test.rb`, `":state create a Status for the specific commit"`) creates a `Status` record for a commit sha supplied in the same forged body [11](#0-10) .

Downstream, actions taken against the resolved stack (e.g. `Stack#github_api`) do use the correct organization's real credentials (`Shipit.github(organization: repository.owner)`), so the attacker cannot fabricate arbitrary GitHub API responses [12](#0-11) . But the *trigger* itself — which stack gets synced, and which commit gets an injected CI `Status` — is fully attacker-chosen and crosses an organization boundary the signature check was supposed to enforce. Since Shipit's merge queue and deploy gating rely on `Status`/`CheckRun` records to decide whether a commit is deployable/mergeable, an attacker who only controls OrgA's webhook secret can inject a forged "success" `Status` against a commit belonging to OrgB's stack, potentially satisfying deploy/merge gating checks it does not actually meet.

### Impact Explanation
This breaks the deployment-trust binding `organization authenticated == repository/stack written`. An entity with legitimate credentials for only one configured GitHub organization can force Shipit to act on and mutate state (sync jobs, commit `Status` records used for deploy/merge gating) belonging to a different organization's repository/stack that it has no authorization over. Where those forged `Status` records satisfy CI/deployability requirements, this can lead to an unauthorized deploy or merge on the unrelated stack — meeting the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to be a legitimate holder of a webhook secret/app for at least one organization configured in the same Shipit instance (a supported/documented multi-org configuration in `docs/setup.md` and `lib/shipit.rb`), and requires the multi-org config to be enabled. This is not the common single-org deployment case, so likelihood is limited to multi-tenant Shipit deployments, but no additional session, API token, or repository-write privilege on the *target* org/repo is required — only knowledge of one's own org's webhook secret.

### Recommendation
After verifying the signature with the `GitHubApp` selected via `repository_owner`, re-validate that every field the handlers subsequently act on (`repository.full_name`, and in particular its owner segment) is consistent with the same verified `repository_owner`/organization, rejecting the payload (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` first from the verified organization and reject payloads whose `full_name` owner does not match.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as shown in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who knows `OrgA`'s `webhook_secret` (e.g., administrator of OrgA's GitHub App installation), craft a JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<arbitrary sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/tracked-repo" }
   }
   ```
3. Compute `X-Hub-Signature` as `sha1=HMAC(OrgA_webhook_secret, body)` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature validates.
5. `PushHandler` resolves the target stacks via `repository.full_name` = `"OrgB/tracked-repo"` and calls `sync_github` on OrgB's stack — an action never authorized by anyone with control over `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
