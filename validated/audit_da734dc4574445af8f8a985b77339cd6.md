### Title
StatusHandler#process creates Status rows for every stack sharing a commit sha, not just the webhook's named repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` with no scoping to the repository named in the webhook payload, unlike every other handler in the engine which uses the `Handler#stacks` helper to resolve stacks strictly from `payload.dig('repository', 'full_name')`. Any `Commit` row in the database that happens to share the sha (across unrelated stacks tracking the same upstream, forks, or shared merge-base history) receives a `Status` via `create_status_from_github!` → `Status.replicate_from_github!`, even though the webhook is legitimately signed for only one repository.

### Finding Description
The broken binding: `payload.dig('repository','full_name')` (the single repository that emitted/authenticates the webhook) should equal the set of stacks whose `Status` rows get mutated. In `app/models/shipit/webhooks/handlers/handler.rb:32-38`, this equality is enforced generically via `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) correctly uses `stacks.not_archived.where(branch:)`.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not use `stacks` at all: [1](#0-0) 
It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` — an unscoped, cross-stack, cross-repository query — then for every matching `Commit`, regardless of its `stack_id`/`Repository`, calls `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) which calls `Status.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/status.rb:24-33`), a `find_or_create_by!` scoped only to that commit's `stack_id`, `state`, `description`, `target_url`, `context`, `created_at`.

`WebhooksController#verify_signature` only proves the payload is authentically signed for the organization deduced from `params.dig('repository','owner','login')` (`app/controllers/shipit/webhooks_controller.rb:24-49`); it says nothing about which stack's `Commit` rows should be touched. The signature check and `ExplicitParameters` schema in `StatusHandler` both pass on a completely valid, real GitHub status webhook fired for one repository/PR; the omission of repository scoping in `process` is the sole root cause.

Exploit flow: an unprivileged GitHub user opens a pull request (or pushes to a fork) against a repository/branch that is tracked by Stack A. Real CI (or GitHub itself) posts a legitimately-signed `status` webhook for that commit sha. If Stack B (e.g., a different environment stack on the same `Repository`, or a stack tracking a fork sharing the same historical commit) also has a `Commit` row with that identical sha — a normal occurrence since `Commit.sha` is not unique across stacks and shared history/merge bases are common — the single webhook writes a `Status` row into Stack B as well, even though Stack B's repository never emitted anything and the payload names only Stack A's repository.

### Impact Explanation
A correctly-authenticated webhook for one repository mutates CI-state (`Status`) records belonging to an unrelated stack/tenant. `Status.after_create :enable_ci_on_stack` (`app/models/shipit/status.rb:18,38-40`) and `schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) are triggered on the foreign stack, and `Commit#deployable?`/`blocked?`/branch merge/continuous-delivery logic in `app/models/shipit/stack.rb` consume these statuses to decide whether commits are deployable. This can flip CI state (success/failure/pending) on a stack the attacker does not control, influencing continuous-delivery/merge decisions on that other stack — this is "a payload for one repository mutating another's stack/commit," matching the Critical impact category. It is repeatable against any pair of stacks that happen to share a commit sha (blast radius scales with how many stacks/environments a Shipit install manages against related repos/forks).

### Likelihood Explanation
Precondition: two `Stack` rows must independently contain `Commit` rows with the identical sha — a realistic scenario for staging/production stacks on the same repo, or forked repos sharing merge-base history, both features the engine explicitly supports. No secrets are needed by the attacker: they only need to cause a legitimate, correctly-signed webhook to be emitted for a repository/branch they can influence (opening a PR, pushing a branch) whose head or ancestor commit sha is shared with the victim stack. This requires no privileged Shipit role, no `api_clients_secret`, and no knowledge of `webhook_secret` — the signature check passes because the webhook truly originates from GitHub for the named repository. This is not a misconfiguration issue (e.g. missing `webhook_secret`); it reproduces even with fully-configured, correctly-signed webhooks.

### Recommendation
Scope `StatusHandler#process` to only the stacks belonging to the repository named in the webhook payload, mirroring `PushHandler`/other handlers' use of `stacks`. E.g., restrict via `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so only commits under the payload's `repository.full_name` are affected.

### Proof of Concept
minitest plan (model/controller-level, no live GitHub):
1. Fixture two `Shipit::Stack` rows, `stack_a` and `stack_b`, each with a `Repository` (can be the same or different `full_name`s).
2. Create `Commit` rows with the identical `sha` value under `stack_a` and `stack_b` respectively (`stack_a.commits.create!(sha: 'deadbeef', ...)`, `stack_b.commits.create!(sha: 'deadbeef', ...)`).
3. Build a `status` webhook payload whose `repository.full_name` matches only `stack_a`'s repository, with `sha: 'deadbeef'`.
4. Assert equality-before: `stack_b.commits.find_by(sha: 'deadbeef').statuses.count == 0` and `stack_a.commits.find_by(sha: 'deadbeef').statuses.count == 0`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST to `/webhooks` with `X-Github-Event: status`, stubbing `verify_webhook_signature` to `true` to simulate a legitimately-signed request).
6. Assert equality-after (bug reproduction): `stack_a.commits.find_by(sha: 'deadbeef').statuses.count == 1` AND `stack_b.commits.find_by(sha: 'deadbeef').statuses.count == 1` — i.e. `stack_b`, whose repository was never named in `payload['repository']`, still received a `Status` write, violating the intended "exactly one stack" binding. module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
