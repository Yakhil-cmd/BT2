### Title
Cross-repository forged status mutates a foreign stack's state - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA alone with no repository scoping, unlike every other webhook handler in the same directory which filters through `stacks` (repository-scoped). A `status` webhook signed for an attacker-controlled organization can create a `Status` row on any `Commit` in the database that shares that SHA, including commits belonging to a victim's stack, triggering `Status#after_create :enable_ci_on_stack` (`app/models/shipit/status.rb:38-40`) on the victim's `Stack`.

### Finding Description
The broken binding: `commit.stack.repository.full_name` (the repository actually mutated) MUST equal `payload.dig('repository','full_name')` (the repository whose HMAC was verified in `WebhooksController#verify_signature`), but `StatusHandler#process` never enforces this.

Compare the handlers:
- `PushHandler#process` and `CheckSuiteHandler#process` both scope through `stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` [1](#0-0) , i.e., strictly the stacks belonging to the repository named in the verified payload.
- `StatusHandler#process`, however, does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This is a global, unscoped `Commit` lookup — it never calls `stacks` or filters by `repository_name`. Any `Commit` row in any stack sharing the same `sha` value is affected, regardless of which repository's HMAC was verified.

`WebhooksController#verify_signature` only proves that the payload was signed by the org identified as `repository_owner` in the payload itself (`Shipit.github(organization: repository_owner)`) [3](#0-2) . It says nothing about which `Commit`/`Stack` rows the handler is permitted to touch — that check is exclusively the handler's responsibility, and `StatusHandler` omits it.

Because Git commit SHAs are content-addressed, an attacker who forks a victim's (public) repository inherits identical SHAs for all shared history. If the attacker's org has a legitimate GitHub App/webhook installation on their own low-trust fork (self-service, granting them their own valid webhook secret), they can send a correctly-signed `status` event for `repository: attacker/fork`, `sha: <shared-history-sha>`, `state: 'success'` (or `'pending'`). `WebhooksController#verify_signature` passes because it validates the attacker's own signature/org. `StatusHandler#process` then finds the victim's `Commit` row (same SHA, different `stack_id`) via `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` → `statuses.replicate_from_github!(stack_id, ...)` where `stack_id` is the **victim's** `commit.stack_id` [4](#0-3) . The new `Status` row belongs to the victim's stack, and `after_create :enable_ci_on_stack` fires:
```ruby
def enable_ci_on_stack
  commit.stack.enable_ci!
end
``` [5](#0-4) 
`Stack#enable_ci!` writes `Rails.cache.write(ci_enabled_cache_key, true)` [6](#0-5) , flipping `ci_enabled?` for the victim's stack and suppressing the "not configured for CI" banner used to gate deploy decisions in the UI [7](#0-6) .

Beyond the cache flag, the forged `Status` row itself is written against the victim stack and its `state` (e.g., `'success'`) participates in `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [8](#0-7) , so this is not merely a benign UI-hint flag — it is a real, persisted CI verdict for a commit the attacker's repository/app was never authorized to report on.

None of the existing guards catch this: `verify_signature` validates the sender's own org, not the target stack's ownership; `ExplicitParameters` (`params do requires :sha ...`) only validates payload shape, not repository scope; there is no `stacks`/`Repository.from_github_repo_name` filter anywhere in `StatusHandler`.

### Impact Explanation
An attacker who controls (or forks) a low-trust repository can, with their own legitimately-issued webhook credentials, write a `Status` record — and therefore CI state (`enable_ci_on_stack`, and potentially deployability via `Commit#deployable?`) — onto a completely unrelated victim `Stack` whose repository/organization they were never granted access to. This is a cross-tenant write: a payload authenticated for repository A mutates state belonging to repository B, matching the Critical category "a payload for one repository mutating another's stack, commit". It is repeatable against any commit SHA shared between the attacker's repo and a victim's tracked history (trivially achievable by forking any public victim repository), and the blast radius spans every Shipit stack tracking that repository's commits.

### Likelihood Explanation
Preconditions: the victim repository must be forkable/public (or otherwise share commit history with an attacker-accessible repository) and tracked as a Shipit stack; the attacker needs their own org/repo registered with a working GitHub App installation (self-service in multi-tenant Shipit deployments) so their own webhook signature validates. No Shipit session, API token, or GitHub token belonging to the victim is required. The attack requires zero interaction with the victim other than forking their public repo — a normal, unprivileged GitHub action — making this highly feasible and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures only commits belonging to stacks of the repository named (and cryptographically verified) in the webhook payload can have statuses created against them.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook for a repo whose signature was verified does not mutate a stack of a different repository sharing the same commit sha" do
  victim_stack = shipit_stacks(:shipit)                 # belongs to repo "shopify/shipit-engine"
  attacker_repo = Repository.create!(owner: 'attacker', name: 'fork')
  attacker_stack = Stack.create!(repository: attacker_repo, environment: 'production', branch: 'master')

  shared_sha = victim_stack.commits.first.sha
  # simulate fork: same sha exists as a Commit row under the attacker's stack too
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus), authored_at: Time.now, committer: shipit_users(:walrus), committed_at: Time.now, message: 'shared history')

  before = victim_stack.ci_enabled?
  assert_equal false, before

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => attacker_repo.github_repo_name, 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test: victim_stack.repository.full_name != payload['repository']['full_name'],
  # yet victim_stack mutated.
  assert victim_stack.reload.ci_enabled?, "victim stack's CI flag was flipped by a payload for a different repository"
  assert victim_stack.commits.find_by(sha: shared_sha).statuses.exists?(state: 'success'),
         "a forged Status was written to the victim's stack from an unrelated repository's webhook"
end
```
This demonstrates that `commit.stack.repository.full_name == payload['repository']['full_name']` does not hold, yet the mutation (`Status` creation + `enable_ci!`) still occurs on `victim_stack`.
