### Title
Missing zero-address validation on `creator` in `initialize_with_permission` permanently freezes creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts an arbitrary, unchecked `creator` account and stores its key as `pool_state.pool_creator` with `enable_creator_fee` hard-coded to `true`, without ever validating that the address is non-zero or otherwise controllable by a real signer.

### Finding Description
In `InitializeWithPermission`, `creator` is declared as a bare `UncheckedAccount` with no `constraint`, `address`, or non-default check: [1](#0-0) 

The payer-supplied `creator.key()` is written directly into `pool_state.pool_creator` via `pool_state.initialize(...)`, with `enable_creator_fee` forced to `true` for every permissioned pool: [2](#0-1) 

`PoolState::initialize` performs no validation on `pool_creator` either: [3](#0-2) 

Once the pool is live, swaps accumulate `creator_fees_token_0`/`creator_fees_token_1` in the pool state (funded from real trade fees on every swap). The only two ways to withdraw them are:
- `collect_creator_fee`, which requires the `creator` account to be a `Signer` whose address equals `pool_state.pool_creator`: [4](#0-3) 
- `collect_creator_fee_permissionless`, which lets anyone trigger the transfer, but the destination ATA is always owned by `pool_creator`: [5](#0-4) 

If `pool_creator` is set to `Pubkey::default()` (the all-zero address, which is also the System Program's ID) or to any address with no known private key, no one can ever produce a valid `Signer` matching `pool_creator`, so `collect_creator_fee` can never succeed. `collect_creator_fee_permissionless` will still succeed, but it deposits the accumulated fees into an associated token account whose authority is that unreachable address — funds that can never be moved out again.

### Impact Explanation
This causes permanent freezing of the creator-fee portion of trading fees for the lifetime of the pool: every swap against the pool keeps routing a fee share into `creator_fees_token_0/1`, and `collect_creator_fee_permissionless` will keep sweeping those fees into a token account nobody controls, since `enable_creator_fee` is unconditionally `true` for permissioned pools created this way. Because the vault balance accounting in `vault_amount_without_fee` treats these creator fees as owed/reserved, real trader-contributed funds become permanently locked and unrecoverable, matching the "permanent freezing of ... funds" impact criterion.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account that has previously created a `Permission` PDA for itself (an unprivileged, non-admin flow explicitly in scope). The `creator` account is completely attacker/user-controlled with zero validation, so triggering this requires nothing more than passing `Pubkey::default()` (or any address with no corresponding keypair) as `creator` in a single `initialize_with_permission` transaction — no special privileges, timing, or race conditions needed.

### Recommendation
Add an explicit check in `InitializeWithPermission` (and analogously in `Initialize`, since `creator` there is also written into `pool_creator`) rejecting the default/zero pubkey, e.g. `require_keys_neq!(creator.key(), Pubkey::default())`, before calling `pool_state.initialize(...)`. Consider also validating that `creator` is not a program-owned/non-signable account where fee collection would be structurally impossible.

### Proof of Concept
1. Attacker (or a careless integrator) creates a `Permission` PDA for their own `payer` key via `create_permission_pda`.
2. Attacker calls `initialize_with_permission` supplying `creator = Pubkey::default()` (or any address they don't hold a key for) along with valid mints/vaults/config; the instruction succeeds because no validation exists on `creator`.
3. `pool_state.pool_creator` is now `Pubkey::default()`, `enable_creator_fee = true`.
4. Users perform swaps (`swap_base_input`/`swap_base_output`); each swap accrues `creator_fees_token_0/1` in `pool_state`.
5. Anyone calls `collect_creator_fee_permissionless`; it succeeds and transfers the accrued fees into an ATA owned by `Pubkey::default()`.
6. No one can ever call `collect_creator_fee` (it requires a `Signer` equal to `pool_creator`, impossible for the zero address), and the ATA created in step 5 has no controllable owner — the fees are permanently stuck.
