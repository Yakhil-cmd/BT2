### Title
Cross-organization webhook forgery via organization/repository binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-tenant configurations, `WebhooksController` selects *which* GitHub App webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON payload, while every webhook `Handler` resolves the target `Stack`/`Repository` to act on using `repository.full_name` from the very same payload. Because these two fields are independent, unvalidated keys inside one JSON object, an attacker who controls (and thus knows the webhook secret of) *any* onboarded organization can forge a signature that Shipit will accept for that organization while pointing the actual repository operation (`repository.full_name`) at a completely different organization's stack.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from attacker-supplied payload content: [1](#0-0) [2](#0-1) 

That organization string is then used to look up the correct `GitHubApp`/secret via `Shipit.github(organization:)`, which in multi-org deployments keys the webhook secret off the same organization identifier: [3](#0-2) 

Once the signature check passes, `create` re-parses the identical raw body and dispatches it to the matching `Handlers::Handler` subclass. Every handler resolves the target repository independently, from a *different* key of the same JSON object — `repository.full_name` — with no cross-check against the organization that was used to select/verify the signature: [4](#0-3) [5](#0-4) 

This breaks the intended trust equality: `organization used to authenticate the webhook == repository.full_name that gets acted upon`. Nothing in `verify_signature` or in `Handler#stacks`/`Handler#repository_name` enforces that `repository.owner.login` (or `organization.login`) is a prefix of, or otherwise consistent with, `repository.full_name`. An attacker who legitimately controls Organization B (and therefore knows or can obtain Org B's configured `webhook_secret` — e.g., because they administer Org B's GitHub App installation) can:
1. Set `repository.owner.login` = `"orgB"` (or `organization.login = "orgB"`) so `verify_signature` picks Org B's secret and the attacker computes a valid HMAC over the full raw body with that secret.
2. Set `repository.full_name` = `"orgA/some-private-repo"` (any other onboarded organization/repository), and craft the rest of the payload (e.g. a `push` event's `ref`/`after`, or a `pull_request`/`status` event) to drive the handler logic.
3. `WebhooksController#create` accepts the forged, validly-signed request and dispatches it to the handler, which resolves and mutates `Repository`/`Stack` state belonging to Org A — outside the attacker's actual GitHub permissions — e.g. triggering `GithubSyncJob` to ingest fabricated commits, updating CI/commit statuses used for deploy gating, or driving pull-request/merge-request state transitions on Org A's stacks.

### Impact Explanation
This is a cross-repository write performed by an attacker who has no legitimate GitHub access to the victim organization/repository, achieved purely by exploiting the mismatch between the field used to select/verify the webhook signature and the field used to determine the write target. This matches the Critical impact bar of "cross-repository writes" / an unauthorized effect on a stack the attacker does not control, without requiring any Shipit session, API token, or the victim's webhook secret.

### Likelihood Explanation
Exploitability is gated on the attacker legitimately controlling at least one organization/GitHub App installation configured in the same multi-tenant Shipit instance (so they know a valid `webhook_secret` for *some* org key), which is a realistic scenario for shared/multi-tenant Shipit deployments serving several organizations. No other authentication boundary needs to be crossed — the webhook endpoint is unauthenticated apart from the signature check itself, and the signature check as implemented does not bind the verified organization to the acted-upon repository.

### Recommendation
After verifying the HMAC signature, enforce that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (and `organization.login` when present) before dispatching to any handler; reject the request otherwise. Alternatively, resolve the target `Repository`/`Stack` using the same verified organization value rather than re-deriving it from a separate, unchecked payload field.

### Proof of Concept
1. Attacker administers/owns a GitHub App installation for `orgB`, which is configured in Shipit's `secrets.github` with its own `webhook_secret`.
2. Attacker crafts a JSON body for a `push` event where:
   - `organization.login` / `repository.owner.login` = `"orgB"`
   - `repository.full_name` = `"orgA/target-repo"`
   - `ref` = `"refs/heads/master"`, `after` = attacker-chosen SHA
3. Attacker computes `X-Hub-Signature: sha1=HMAC(orgB_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "orgB")`, verifies the HMAC successfully against `orgB`'s secret [1](#0-0) .
5. `create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("orgA/target-repo")` via `repository_name` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` on Org A's stack [5](#0-4)  — a write the attacker was never authorized to trigger on Org A's repository.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
