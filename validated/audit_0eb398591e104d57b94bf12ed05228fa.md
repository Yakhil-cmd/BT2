### Title
Repository-unscoped `status` webhook handler lets an authenticated organization write commit statuses onto other stacks' commits, enabling unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` resolves the target `Commit` purely by `sha`, without scoping the lookup to the repository/stack that the webhook actually originated from. Every other handler that mutates state (e.g. `CheckSuiteHandler`, `Handler#stacks`) binds the payload's `repository.full_name` to a specific `Repository`/`Stack` before touching any record, but `StatusHandler` does not. This breaks the binding "the organization that authenticated the webhook == the repository being written," because the HMAC signature only proves which GitHub organization's secret produced the payload — it does not constrain which `Commit` row (i.e. which stack/repository) the handler is allowed to mutate.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using `repository_owner`, derived directly from the incoming JSON payload: [1](#0-0) [2](#0-1) 

This only proves the payload was signed with the secret belonging to whichever organization is legitimately configured in Shipit and sending the event (e.g. Org B, a normal, unprivileged Shipit customer/tenant). It says nothing about which `Commit` records the handler should be allowed to touch.

Every handler that mutates provisioning state properly re-derives and scopes to the originating repository/stack, e.g.: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, looks up commits solely by SHA, globally across the entire `commits` table, with no repository/stack filter at all: [5](#0-4) 

Git commit SHAs are content-addressed and are not scoped to a single GitHub repository: any actor who can reproduce the exact same commit object (same tree, parent, author/committer metadata, and message — trivially done by cloning/forking a public repository and pushing the identical objects into a different, attacker-controlled repository) can create a commit with an identical SHA in a repository they administer. If that attacker-controlled repository is registered under an organization Shipit is configured for (i.e., they are a legitimate, unprivileged tenant of the Shipit instance, not a privileged admin of the victim's org/team), they can set any commit status on that commit through the normal GitHub API/UI. GitHub then sends a validly-signed `status` webhook to Shipit. `StatusHandler#process` applies that status to **every** `Commit` row in the database sharing that SHA — including one that belongs to a completely different stack/repository the attacker has no access to.

This status write feeds directly into deploy-gating logic: `Commit#deployable?` and the continuous-delivery trigger both depend on `Status::Group` built from `statuses`/`check_runs`, and a fabricated "success" state can flip a commit from non-deployable to deployable and even auto-trigger continuous delivery: [6](#0-5) [7](#0-6) [8](#0-7) 

**Binding broken:** `organization_authenticated(webhook) == organization_owning(commit_written)` — before the vulnerable code, both sides are implicitly assumed equal because only the originating org's secret was checked; after crafting the colliding-SHA commit in their own tenant repo, the attacker makes the write land on a commit belonging to a different stack/organization while the authentication check still only verified their own org's signature.

### Impact Explanation
This allows an unprivileged tenant of a shared Shipit instance (one org/repo among several configured orgs) to forge CI status ("success"/"failure") on commits belonging to a different, unrelated stack. Because `deployable?`/`schedule_continuous_delivery` gate real deploy actions on commit status, this can trigger an unauthorized deploy on a victim stack, satisfying the "Critical — unauthorized deploy" impact bar. It is a cross-repository state-write primitive achieved purely through the normal, signed webhook path — no Shipit session, API token, or webhook secret compromise is required beyond the attacker's own legitimate org credentials.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment with more than one GitHub organization configured (`config/secrets*.yml` supports this — see multiple orgs each with their own `webhook_secret`), (2) the attacker controlling a repository under one of those orgs, and (3) the target commit's git object being reproducible (straightforward for any public/forked repository, or any commit whose content the attacker can read). This is a moderate-effort, fully unprivileged, and repeatable path — no signature forgery or secret compromise needed, only content replication of an existing commit object, which is a supported git operation.

### Recommendation
Scope `StatusHandler#process` to the stacks/commits belonging to the webhook's own repository, mirroring `Handler#stacks` / `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the mutated `Commit` records to the same repository whose organization signed the webhook, restoring the `authenticated organization == repository written` invariant. Long term, audit all webhook handlers to ensure every state mutation is scoped through `repository_name`/`stacks` rather than globally-unique-looking but not-actually-unique fields like commit SHA.

### Proof of Concept
1. Shipit instance configured with two GitHub orgs, `victim-org` (owns `victim-org/app`, tracked as a Shipit stack with `continuous_deployment: true`) and `attacker-org` (owns `attacker-org/sandbox`, also tracked, attacker has full admin rights there).
2. Attacker forks/clones `victim-org/app`, identifies a specific commit `C` (sha `abc123...`) that is currently *not* deployable (e.g., pending/no CI status) on the victim stack.
3. Attacker pushes the identical commit object `C` (same tree/parent/author/committer/message bytes) into `attacker-org/sandbox`, producing a commit with the same SHA `abc123...` in their own repo.
4. Attacker sets a `success` commit status on `abc123...` in `attacker-org/sandbox` via the GitHub API (fully within their own repo permissions).
5. GitHub sends a `status` webhook to Shipit, signed with `attacker-org`'s `webhook_secret`; `WebhooksController#verify_signature` passes because the signature matches `attacker-org`.
6. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which matches the commit in **both** `attacker-org/sandbox`'s stack and `victim-org/app`'s stack, and calls `create_status_from_github!` on both.
7. The victim stack's commit `C` now shows a `success` status; if it was the last undeployed commit and `continuous_deployment` is enabled, `schedule_continuous_delivery` fires and the victim stack auto-deploys `C` without any legitimate victim-org approval.
