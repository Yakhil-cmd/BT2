### Title
STX-staker reward rounding to zero permanently freezes sBTC rewards in `calculate-rewards` - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`calculate-rewards` in pox-5.clar computes `accrued-rewards-per-ustx` by dividing `stx-staker-rewards` by `cycle-staked-ustx` and scaling by `PRECISION`, exactly the "amount * rate / large-denominator" pattern flagged in the referenced Sherlock report (M-1, Surge Protocol interest rounding to 0). When this integer division truncates to `0` (small `stx-staker-rewards`, large `cycle-staked-ustx`, or `PRECISION` too small relative to the ratio), the sBTC reward is nevertheless irreversibly marked as "already accounted for" via `last-accounted-rewards-only`, permanently freezing that sBTC in the contract with no stacker ever able to claim it and no path to return it to the reserve.

### Finding Description
In `calculate-rewards`: [1](#0-0) 

```
(remaining-rewards (get available-rewards bond-distributions))
(reserve-cut (/ (* remaining-rewards RESERVE_RATIO) u10000))
(stx-staker-rewards (- remaining-rewards reserve-cut))
(cycle-staked-ustx (get-total-shares-staked-for-cycle stx-cycle none))
(current-rewards-per-ustx (get-rewards-per-token-for-cycle stx-cycle none))
(prev-accounted-rewards (var-get last-accounted-rewards-only))
(no-stx-stakers (is-eq cycle-staked-ustx u0))
(accrued-rewards-per-ustx (if no-stx-stakers
    u0
    (/ (* stx-staker-rewards PRECISION) cycle-staked-ustx)
))
...
(var-set last-accounted-rewards-only
    (+ prev-accounted-rewards
        (- gross-accrued-rewards reserve-deposit)
    ))
```

The code only guards against the `cycle-staked-ustx == 0` case (`no-stx-stakers`), but not the case where `cycle-staked-ustx > 0` yet the division `(stx-staker-rewards * PRECISION) / cycle-staked-ustx` still floors to `0`. This is entirely plausible in this contract: `cycle-staked-ustx` is a raw µSTX total which can be very large (many stackers, large minimum stacking amounts), while `stx-staker-rewards` is a share of sBTC (8-decimal token) rewards accrued between successive `calculate-rewards` calls — the reward amount can be tiny relative to `cycle-staked-ustx`, especially if `calculate-rewards` is called frequently (anyone can call it — it is a `define-public` function gated only by the `last-calc` height check, not by caller identity) or if `PRECISION` is insufficient for the ratio of sBTC-decimals to µSTX-decimals.

When `accrued-rewards-per-ustx` rounds to `0`:
- `cumulative-rewards-per-ustx` (the map value that stakers later use to compute their claimable share) does not increase.
- But `last-accounted-rewards-only` still increases by the *entire* `stx-staker-rewards` amount (embedded in `gross-accrued-rewards - reserve-deposit`), since `unallocated-staker-cut` is only added back to the reserve when `no-stx-stakers` is true — not when the per-token rate merely rounds to zero.
- This means the sBTC corresponding to `stx-staker-rewards` is now "spent" from the perspective of `get-new-rewards` (it's baked into `last-accounted-rewards-only`), yet it was never credited to any staker's claimable balance nor returned to `reserve-balance`.

The equality broken: `contract sBTC balance == sum(claimable rewards for all stakers) + reserve-balance + still-uncounted-rewards`. After a rounding-to-zero round, this invariant breaks — sBTC sits in the contract balance that is neither claimable by any staker nor part of the reserve, permanently stranding real value.

### Impact Explanation
This is a permanent freezing of sBTC rewards impact. Because `calculate-rewards` can be called by any unprivileged account, an attacker (or simply routine usage patterns with small, frequent rewards) can trigger many small `calculate-rewards` calls, each accruing a tiny `stx-staker-rewards` amount that rounds to zero against a large `cycle-staked-ustx`. Each such call permanently forfeits that increment of sBTC — it becomes unclaimable and is excluded from future distributable rewards since `get-new-rewards` is computed against `last-accounted-rewards-only`, which has already absorbed it. Over repeated calls this compounds, permanently locking meaningful sBTC value with no admin/staker able to recover it through normal contract flows.

### Likelihood Explanation
Likelihood is moderate-to-high: `calculate-rewards` is public and callable by anyone without incurring loss to themselves (unlike the "reject analogs where the only loss is the attacker's own stake" rule — here the loss is socialized to all stakers/the protocol, not the caller). No special privileges, keys, or admin roles are required — only knowledge of `bond-periods` and the ability to call the contract repeatedly. The larger `cycle-staked-ustx` grows (as adoption increases) relative to per-call sBTC drip, the more likely rounding-to-zero becomes on every call.

### Recommendation
- Track a running remainder (as the referenced report recommends) instead of truncating: keep undistributed sub-`PRECISION` remainders in a persisted "carry" variable and add them into the next `calculate-rewards` invocation's `stx-staker-rewards` before dividing.
- Alternatively, when `accrued-rewards-per-ustx` computes to `0` despite `cycle-staked-ustx > 0`, do not advance `last-accounted-rewards-only` by the truncated `stx-staker-rewards` portion — instead re-add it to `reserve-deposit` (mirroring the `no-stx-stakers` branch) or leave it uncounted so a future call with more accumulated rewards can distribute it without loss.
- Increase `PRECISION` scaling analysis to ensure it is large enough relative to realistic `cycle-staked-ustx` (µSTX) vs `stx-staker-rewards` (sats) ratios so that rounding to zero is not reachable under expected parameter ranges, and add an explicit test/property test asserting `sum(rewards-per-token deltas * cycle-staked-ustx) + reserve-growth == gross-accrued-rewards` per call.

### Proof of Concept
1. Let `cycle-staked-ustx` = `1_000_000_000_000` µSTX (1,000,000 STX from many stackers), `PRECISION` = e.g. `1e8` (consistent with sBTC's 8 decimals, as used elsewhere in the contract for `accrued-rewards-per-sat`).
2. A small sBTC reward trickles in between two `calculate-rewards` calls such that `stx-staker-rewards` = `9` (9 sats-equivalent after reserve cut).
3. `accrued-rewards-per-ustx = (9 * 1e8) / 1_000_000_000_000 = 900_000_000 / 1_000_000_000_000 = 0` (integer division truncates to 0).
4. `cumulative-rewards-per-ustx` is unchanged, so no staker's claimable rewards increase.
5. `last-accounted-rewards-only` is incremented by `gross-accrued-rewards - reserve-deposit`, which includes the full `stx-staker-rewards = 9`, because `no-stx-stakers` is `false` (there are stakers, just the division truncated) so the `unallocated-staker-cut` re-injection into `reserve-deposit` never triggers.
6. Result: those 9 sats of sBTC remain in the contract's token balance forever — not part of `reserve-balance`, not reflected in any staker's `rewards-per-token-for-cycle` entry, and `get-new-rewards` will never re-surface them since `last-accounted-rewards-only` already "counted" them. Repeating this call pattern (which anyone can trigger, since `calculate-rewards` has no access control beyond the height check `> calculation-height last-calc`) compounds the permanently frozen sBTC over time.

*(Note: full confirmation of `PRECISION`'s exact value and of the staker-side claim function (`claim-stx-rewards`-equivalent) that consumes `rewards-per-token-for-cycle` could not be completed within the available search budget — the constant definition and claim function bodies were not fully retrieved. The core rounding/no-return-to-reserve logic shown above, however, is directly visible in the `calculate-rewards` body cited.)*
