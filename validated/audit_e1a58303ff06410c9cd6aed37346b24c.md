### Title
Webhook signature verification silently accepts unsigned/forged payloads when no `webhook_secret` is configured, enabling forged `membership` events to escalate into `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` is the sole authentication gate for `/webhooks` requests. When an organization's `webhook_secret` is not configured (a state the setup docs describe as "optional"), the method returns `true` unconditionally instead of rejecting the request, exactly mirroring the reported oracle bug class: a verification path that correctly validates when the primary safeguard is present, but silently "passes" the unverified data through when the safeguard is simply absent, rather than failing closed.

### Finding Description
The binding that should hold is:

`verify_webhook_signature(signature, payload) == true` **iff** `HMAC-SHA1(webhook_secret, payload) == signature`, for the organization claimed by `repository_owner`.

`WebhooksController#verify_signature` relies entirely on this method to gate every webhook handler: [1](#0-0) 

But the implementation breaks the equality whenever `webhook_secret` is falsy: [2](#0-1) 

`return true unless webhook_secret` means that for any organization configured without a webhook secret (explicitly documented as "optional" in `docs/setup.md`, line 30), **any** POST to `/webhooks` with an arbitrary/absent `X-Hub-Signature` header is accepted as if it came from GitHub. The `check_if_ping` and `drop_unhandled_event` filters do not perform any additional authentication: [3](#0-2) 

This directly parallels the oracle bug: the primary check (HMAC verification) is correct when the guarding value exists, but the "no secret configured" branch — analogous to "no backup oracle configured" — is treated as an automatic pass rather than a rejection.

The most damaging consequence is through `MembershipHandler`, which processes forged `membership` events and mutates `Team`/`Membership` records directly from unauthenticated payload fields: [4](#0-3) 

Authorization in the app is decided by team membership matching `Shipit.github_teams` ids: [5](#0-4) 

If a `Team` row already exists (or is created) with a `github_id` equal to one of the configured `Shipit.github_teams` ids, an attacker forging a `membership` "added" event for a user they control gets that `User` added to `team.members`. Once that GitHub account subsequently completes normal OAuth login, `authorized?` returns `true`, granting full authenticated access to the Shipit instance — bypassing the entire GitHub-team access-control intent without ever needing real organization membership.

### Impact Explanation
This crosses the "authenticated organization vs. repository/data written" trust boundary named in the rules: `repository_owner`/organization identity is supposed to be cryptographically bound to the payload via HMAC, but when no secret is configured the write path (`Team`/`Membership`/`User` creation, plus any other webhook-driven mutation: `push`, `status`, `deployment`, etc.) executes on entirely unauthenticated data. Concretely this yields **escalation into `Shipit.github_teams` authorization** — an explicitly listed High-severity impact — by forging a `membership` webhook to add an attacker-controlled GitHub login to an authorized team.

### Likelihood Explanation
Requires only that an organization's `webhook_secret` be left unset — a state the project's own documentation calls "optional" and multiple bundled example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets*.yml`, `template.rb`) ship with `webhook_secret: nil`/blank by default. No credentials, session, or prior access are required; the attacker only needs the `/webhooks` endpoint URL and the target organization's login/team id, both of which are typically public GitHub information.

### Recommendation
Fail closed instead of open when no secret is configured:
```ruby
def verify_webhook_signature(signature, message)
  return false if webhook_secret.blank?

  algorithm, signature = signature.to_s.split("=", 2)
  return false unless algorithm == 'sha1'

  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```
Additionally, make `webhook_secret` a mandatory configuration value (raise at boot / installation time if absent) rather than documenting it as optional, since it is the only authentication mechanism for `/webhooks`.

### Proof of Concept
1. Deploy Shipit with an organization configured without `webhook_secret` (default/example configuration).
2. Attacker sends:
   ```
   POST /webhooks
   X-Github-Event: membership
   Content-Type: application/json

   {
     "action": "added",
     "team": {"id": <id-of-a-Shipit.github_teams entry>, "name": "x", "slug": "x", "url": "https://x"},
     "organization": {"login": "<target-org>"},
     "member": {"login": "attacker-github-login"}
   }
   ```
   No `X-Hub-Signature` header, or any arbitrary value, is required.
3. `verify_webhook_signature` returns `true` (`webhook_secret` is blank) at `lib/shipit/github_app.rb:77`, so `WebhooksController#verify_signature` proceeds.
4. `MembershipHandler#process` creates/finds the `Team` and adds `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
5. Attacker completes normal GitHub OAuth login with `attacker-github-login`; `User#authorized?` now returns `true` because the forged `Membership` row satisfies `teams.where(id: Shipit.github_teams.map(&:id)).exists?` (`app/models/shipit/user.rb:80-82`), granting full authenticated access to the Shipit instance.
