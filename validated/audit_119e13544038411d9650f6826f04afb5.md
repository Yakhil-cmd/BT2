### Title
Incorrect Access Control in Wallet Signing-Request Handler Allows Unauthorized Sign Requests to Any Local Address's UI - ([File: wallet.js])

### Summary
The `sign` case of `handleMessageFromHub` in `wallet.js` disables the cosigner-membership check for locally-hosted addresses when a paired device sends a `sign` request. The verification that the requesting device is actually a registered cosigner/member of the wallet that owns the address has been explicitly commented out, so any paired device can request a signature/confirmation for any address the node considers "local," irrespective of whether that device is actually a legitimate cosigner.

### Finding Description
When a paired device sends a `"sign"` message to a wallet node, `findAddress()` classifies the target `body.address` as local, remote, merkle, or unknown. In the `ifLocal` branch, the code that used to verify the sender is a genuine cosigner of the wallet owning the address has been disabled: [1](#0-0) 

Instead of checking `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?`, the handler unconditionally calls `callbacks.ifOk()` and proceeds to emit a `"signing_request"` event (or run `network.handleOnlineJoint`) using the caller-supplied `objAddress`, `body.address`, `objUnit`, and `assocPrivatePayloads`: [2](#0-1) 

By contrast, the `ifRemote` branch (forwarding requests for addresses hosted on another device) *does* still enforce cosigner membership via `other_device_addresses.includes(from_address)`: [3](#0-2) 

This asymmetry means: for any address whose keys are locally present on the node (multi-device wallets, shared/multisig addresses where at least one signing key resides on this device), an unrelated/untrusted paired device can trigger a "signing_request" UI event and, for signed messages, submit arbitrary `objUnit`/`private_payloads` content that the local device's UI will present to the user for approval, without any server-side verification that this peer is authorized to request signing for that specific address. Any user who is not careful reading the confirmation dialog (or any automated signing flow) can be tricked into co-signing/authorizing a transaction (or signed message) requested by a party who was never granted cosigning rights on that address's wallet.

### Impact Explanation
An unprivileged paired device (any device the victim has ever paired with for any purpose, e.g. via a chat bot, a merchant pairing code, or a compromised/malicious counterparty in a prosaic/arbiter contract) can issue `sign` requests for addresses it has no legitimate right to co-sign, spoofing `objAddress`/`unsigned_unit` content presented to the user. Because the confirmation-dialog trigger and the message contents (including private payment payloads) are supplied entirely by the requester, this enables social-engineering-driven unauthorized spending or approval of private payments/contract signatures the victim never intended to authorize — i.e., a concrete path to unauthorized spending, matching the "Incorrect Access Control" pattern of the GitLab CVE (an authorization check that should gate a privileged action was removed/bypassed).

### Likelihood Explanation
Exploitation only requires an existing device pairing (a very low bar — pairing is commonly established for merchant interactions, bots, or contract counterparties) and the ability to send hub-relayed `sign` messages, which is standard wallet protocol traffic. No node compromise, hub compromise, or invalid signature is required — the access-control gap is directly in the message handler reachable by any paired device.

### Recommendation
Restore (and correctly implement) the cosigner-membership check that was commented out: before emitting `signing_request` or calling `network.handleOnlineJoint`, verify that `from_address` is actually registered as a cosigning device for the wallet that owns `body.address` (e.g., re-enable the `extended_pubkeys` wallet/device_address lookup, or equivalent check against `wallet_signing_paths`/`shared_addresses` membership tables) and reject with `ifError` if the sender is not an authorized cosigner.

### Proof of Concept
1. Attacker device A pairs with victim device V for any legitimate purpose (chat, merchant flow, contract negotiation).
2. Victim V has a local/shared multisig address `ADDR` for which A is not a registered cosigner.
3. Attacker A sends a hub message: `{subject: "sign", body: {address: ADDR, signing_path: "r", unsigned_unit: <attacker-crafted unit>}}`.
4. On V's node, `findAddress` resolves `ADDR` as local; the disabled cosigner check at `wallet.js:335-338` means no rejection occurs.
5. V's UI receives a `"signing_request"` event sourced from A's crafted `objUnit`, prompting the user to sign/approve a transaction A designed — despite A never having cosigning rights on `ADDR`.
