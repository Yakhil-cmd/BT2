Based on the investigation, ocore has a directly analogous unbounded-array/DOS pattern in the **system voting mechanism** for consensus parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`).

### Title
Unbounded, never-pruned `system_votes` table can be spammed by cheap fresh addresses to DOS the consensus-critical vote-counting routine `countVotes` - (File: main_chain.js)

### Summary
Any unit author can attach a `system_vote` message to a unit, which is unconditionally persisted forever, once per address per subject, into the `system_votes` table [1](#0-0) . Unlike `op_votes`/`numerical_votes` (which keep only the *latest* vote per address via `DELETE` + `INSERT`), `system_votes` has primary key `(unit, address, subject)` [2](#0-1) , so a new row is added for every distinct `(unit, address)` combination and nothing is ever removed. Because creating a fresh address and casting one vote from it costs only ordinary unit fees, an attacker can cheaply grow the set of distinct voting addresses without bound over time — exactly the "array anyone can add elements to" pattern from the reference report.

### Finding Description
When a `system_vote_count` message stabilizes, `countVotes()` reads **all distinct addresses that have ever voted** for the subject and builds an in-memory/SQL list from them:
```
const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
let addresses = address_rows.map(r => r.address);
...
const strAddresses = addresses.map(db.escape).join(', ');
...
await conn.query(`INSERT INTO voter_balances (address, balance) VALUES ` + values.join(', '));
``` [3](#0-2) 

This query and the subsequent balance lookup/temporary-table population scale linearly (or worse, given string concatenation of escaped addresses) with the total number of distinct addresses that have *ever* voted on that subject — a number that only grows and is fully attacker-controlled, since any address (even one with zero or dust balance) that posts a single `system_vote` message is added permanently. There is no cap on distinct voter addresses, no expiry, and no pruning mechanism analogous to the `op_votes`/`numerical_votes` tables.

`countVotes` is not an optional, opt-in read: it is invoked automatically by the core stabilization pipeline whenever a `system_vote_count` message stabilizes [4](#0-3) , and also by the emergency OP-list-change path `applyEmergencyOpListChange`, which additionally iterates the entire in-memory `storage.assocUnstableMessages` map to collect unstable votes [5](#0-4) . Both code paths are reachable purely by posting ordinary units (no special privilege needed): any address can post `system_vote` messages, and after enough legitimate confirmations (or via `SYSTEM_VOTE_COUNT_FEE`), any address can also trigger `system_vote_count` [6](#0-5) .

### Impact Explanation
If an attacker cheaply mints a very large number of addresses (only requiring dust/fee-level funding) and has each cast a single `system_vote` for a subject, the `system_votes` table for that subject grows without bound. The next `system_vote_count` (which every node must process identically to remain in consensus) forces every full node to run a `SELECT DISTINCT address ...` over a huge/growing set and build very large dynamic SQL statements (`strAddresses`, `values.join(', ')`, bulk `INSERT INTO voter_balances`). This can:
- Cause excessive processing time inside `markMcIndexStable`'s synchronous stabilization pipeline, stalling the node's ability to confirm/process new units (a node unable to confirm new units), or
- Hit backend-specific limits (e.g., MySQL `max_allowed_packet`/statement length limits vs SQLite's differing limits) causing some nodes to fail the query while others (with different storage engines) succeed — producing **node disagreement on validity/stability** of the block that stabilizes the `system_vote_count` unit, a consensus-fork risk.

### Likelihood Explanation
Likelihood is limited by the actual cost of creating and funding many distinct addresses and paying for many units carrying `system_vote` messages, and by the fact that a `system_vote_count` can only be triggered periodically/with a fee. However, the growth is strictly monotonic and permanent — votes are never expired or pruned — so the attack cost is a one-time, incrementally-payable cost (spread over any time period) to permanently degrade every future vote count for that subject. No special privilege (OP status, admin, arbiter) is required; this is reachable by any unprivileged unit poster.

### Recommendation
- Cap the number of distinct addresses considered per subject (e.g., only the most-recently-active N voters, or require a minimum balance/last-activity to remain "active" instead of an unbounded historical `DISTINCT address` scan).
- Prune or archive `system_votes` rows for addresses that have been superseded or are inactive/zero-balance, mirroring the "latest vote wins" pattern already used for `op_votes`/`numerical_votes`.
- Avoid building SQL queries via string concatenation over an attacker-influenced, unbounded address list; use paginated/batched processing bounded by a fixed maximum, and enforce that maximum in `countVotes`.

### Proof of Concept
1. Attacker generates `N` fresh addresses (`N` limited only by fee budget) and funds each with a minimal amount of bytes.
2. From each address, attacker posts a single unit containing a `system_vote` message for a fixed `subject` (e.g., `threshold_size`), which is unconditionally recorded in `system_votes` on stabilization [1](#0-0) .
3. Over time (or in one campaign), `N` grows arbitrarily large; no existing mechanism removes old/dust voters from `system_votes`.
4. Any address triggers (or waits for) a `system_vote_count` message for that subject; on stabilization every full node executes `countVotes`, which performs `SELECT DISTINCT address FROM system_votes WHERE subject=?` over the full attacker-inflated set and constructs bulk `INSERT`/`IN(...)` SQL built from that list [7](#0-6) , degrading performance for all full nodes or causing backend-specific query failures leading to divergent stabilization outcomes.

**Note on limitations:** I was not able to fully verify the exact validation rules governing the `system_vote` message payload itself (e.g., whether there is any per-address rate limit beyond ordinary fees) because the relevant validation.js code block for the `system_vote` case (distinct from `system_vote_count`) was not retrieved in full during this session. This affects the precision of the likelihood estimate; a full review of `validation.js`'s `system_vote` handling would be needed to confirm whether any additional anti-spam constraints exist there.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}


async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
