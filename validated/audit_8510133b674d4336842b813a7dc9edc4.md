### Title
Malicious upstream repository content (recursive submodule bomb) can cause persistent sync denial with no built-in mitigation - (File: main.go)

### Summary
`git-sync` treats the content of the `--repo` it is configured to sync as at least semi-trusted, similar to how `Project.sol` treats a "delegated" contractor as trustworthy once granted signing rights. Just as the delegated contractor could push a huge number of tasks (or one huge-cost task) that permanently jams `allocateFunds()` with no way for the builder to selectively undo it, an attacker who controls (or compromises) the content of the synced git repository can craft `.gitmodules` content that defines a very large number of submodules, or deeply/recursively nested submodule chains, which `git-sync` will unconditionally attempt to fetch and initialize on every single sync attempt via `git submodule update --init --recursive`.

### Finding Description
`configureWorktree` runs submodule initialization using the default `submodules=recursive` behavior with no bound on the number or depth of submodules, and only applies `--depth` to submodules if the operator explicitly set a non-zero `--depth` value: [1](#0-0) 

The default value of `--submodules` is `"recursive"`, and `--depth` defaults to `1`, but operators wanting full history commonly set `--depth=0`, which removes any depth constraint entirely (`--depth` is only passed to `git submodule update` when `git.depth != 0`): [2](#0-1) 

Because the submodule graph (`.gitmodules`, submodule URLs, and nesting depth) is entirely determined by content in the remote repository — content that an attacker able to push to (or compromise) the tracked ref fully controls — a malicious commit can define an arbitrarily large or deeply recursive submodule tree. This forces every subsequent `SyncRepo` attempt to spend its entire `--sync-timeout` budget fetching/initializing submodules: [3](#0-2) 

There is no mechanism in the code to cap the number of submodules, bound recursion depth independent of a global `--depth`, or otherwise quarantine a bad commit's submodule graph once it lands on the tracked ref — analogous to how `Project.sol` had no `Disputes`-mediated way to selectively purge the malicious contractor's bad tasks.

### Impact Explanation
If the tracked ref's HEAD is moved to a commit with a submodule bomb, every sync attempt (the periodic loop calling `SyncRepo`) will exceed `--sync-timeout` and fail, repeating indefinitely at `--period` intervals. This is a persistent sync denial: the consumer's `--link` never advances to reflect subsequent legitimate commits, and (depending on `--max-failures`) the container/sidecar may repeatedly crash and restart, disrupting the application it feeds. This matches the accepted "persistent sync denial" impact class.

### Likelihood Explanation
This requires an attacker/compromised actor with push (or ref-move) access to the tracked repository/ref — the same trust boundary implicitly assumed by the operator configuring `--repo`/`--ref`, comparable to the "certain trust incorporated" the original report notes about the delegated contractor. Likelihood is therefore low-to-moderate: it requires an already-somewhat-trusted upstream source to turn malicious, but git-sync's default (`submodules=recursive`, `depth=1` but easily overridden to `0` for full-history use cases) offers no independent safeguard once that trust is abused.

### Recommendation
- Enforce a submodule count/depth ceiling independent of `--depth=0`, e.g. always cap `--depth` for submodule fetches even when the top-level repo uses full history.
- Add an explicit `--max-submodules` or similar guard, and fail fast (skip submodule update, log/alert) rather than let a single sync attempt consume the whole `--sync-timeout` budget.
- Consider decoupling the submodule-update timeout from the overall `--sync-timeout` so a submodule bomb degrades gracefully (e.g., publish content without submodules, with a clear error) instead of blocking the entire sync pipeline.

### Proof of Concept
1. Push a commit to the tracked branch whose `.gitmodules` defines hundreds of submodules, or a submodule chain nested many levels deep (submodule → nested submodule → nested submodule → …).
2. Run `git-sync --repo=<repo> --root=<root> --link=link --depth=0` (or any config where `--submodules` stays at its default `recursive`).
3. Observe that `configureWorktree`'s `git submodule update --init --recursive` step never completes within `--sync-timeout`, and every subsequent periodic sync attempt fails identically, permanently preventing the `--link` symlink from advancing past the last good commit. [1](#0-0) [2](#0-1)
