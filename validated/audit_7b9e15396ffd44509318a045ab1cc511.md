### Title
Emergency OP-list vote count is undermined by pre-existing malicious votes left in the persistent `op_votes` table - (File: main_chain.js)

### Summary
The `applyEmergencyOpListChange`/`countVotes` mechanism in `main_chain.js` is designed to rescue the network when the main chain gets stuck because the current order-providers (OPs/witnesses) are censoring or otherwise failing to advance stability, by force-counting votes (including very recent unstable ones) into a temporary table. However, this emergency counting never touches the underlying persistent `op_votes` table, so any pre-existing (malicious/majority) votes for the old, censoring OP list remain intact. Any unprivileged unit author can immediately follow up with an ordinary `system_vote_count` message, which re-runs the *normal* (non-emergency) vote count against the untouched `op_votes` table and can instantly reinstate the malicious OP list that the emergency mechanism just replaced.

### Finding Description
`system_vote` and `system_vote_count` are ordinary, unprivileged messages that any unit author can attach to a unit [1](#0-0) . `system_vote_count` messages simply record a `subject` and are queued for processing when the unit's MCI stabilizes [2](#0-1) . Once the containing unit becomes stable, `main_chain.js` iterates over the collected `voteCountSubjects` and calls `countVotes` for each — a fully permissionless trigger reachable by any single unit poster [3](#0-2) .

`countVotes` normally tallies balance-weighted votes from the persistent `op_votes` table (populated by `system_vote` messages, see `saveSystemVote`) [4](#0-3) [5](#0-4) .

When the main chain stalls for too long (e.g. because the current OPs are censoring units), `applyEmergencyOpListChange` is invoked to force a vote count using `is_emergency=1`, incorporating recent unstable votes that could not otherwise stabilize [6](#0-5) . Critically, this emergency path copies `op_votes` into a **temporary** table (`op_votes_tmp`), overlays the unstable votes there, computes the new OP list from the temp table, and then drops it — it never updates the real `op_votes` table with the outcome [7](#0-6) .

Consequently, any votes a malicious actor (or Sybil-controlled address set) had previously cast and recorded in the persistent `op_votes` table for the old/malicious OP list are left completely intact after the emergency rescue. As soon as the network is unstuck and a new unit stabilizes, anyone (including the attacker) can attach a plain `system_vote_count` message for `op_list`. This triggers a normal, non-emergency `countVotes` call that reads straight from the still-poisoned `op_votes` table [5](#0-4) , and — because `system_vars` is written with `REPLACE`/`INSERT` keyed by `(subject, vote_count_mci)` with no restriction preventing an immediate re-vote — this can instantly overwrite the emergency-selected OP list with the malicious one that caused the stall in the first place [8](#0-7) .

This mirrors the reported bug class exactly: an emergency governance-override mechanism (`applyEmergencyOpListChange`, analogous to `changePrimaryStrategist`) is undermined because the state backing normal/malicious "proposals" (`op_votes`, analogous to a strategist's pending proposal) is never cleared, letting the attacker's pre-existing influence reassert itself the moment ordinary processing (`system_vote_count`, analogous to executing a timelocked proposal) resumes — and, unlike the original report, triggering that reassertion here requires nothing more than posting an ordinary message, which any unprivileged unit author can do.

### Impact Explanation
The OP list determines which addresses are witnesses/order-providers securing main-chain stability for the entire network. If a malicious voting bloc can cause the emergency-selected (good) OP list to be immediately overwritten back to the malicious/censoring list, the network can be repeatedly forced back into the exact stall condition the emergency mechanism exists to fix, or worse, the malicious OPs can regain control of consensus and repeat censorship/double-spend-enabling behavior. This falls squarely into "node disagreement on validity or stability" and "a network unable to confirm new units," matching the severity bar (network availability/consensus safety).

### Likelihood Explanation
Exploitation only requires: (1) previously accumulating balance-weighted votes for a malicious OP set in the persistent `op_votes` table (feasible if the attacker or colluding parties control significant vote-weighted balance — the same condition that let them capture the OP list and cause the stall in the first place), and (2) posting a single ordinary unit with a `system_vote_count` message for `op_list` as soon as the chain resumes after the emergency fix. No special privileges, timing races beyond "as soon as possible after unstick," or complex preconditions are required, making this straightforward to execute once the initial capture condition exists.

### Recommendation
When applying an emergency OP-list change (`is_emergency=1` in `countVotes`), also purge or reset the persistent `op_votes` (and/or `system_votes`) entries that fed the deposed/malicious OP list, or otherwise make the subsequent normal `countVotes` computation aware of the emergency override so it cannot trivially recompute and reinstate the same malicious result immediately. Consider requiring a cooldown period after an emergency change before a normal `system_vote_count` for the same subject is honored, and/or require that normal vote counting supersede an emergency result only with fresh votes cast after the emergency change's timestamp.

### Proof of Concept
1. A collusive/Sybil group with significant vote-weighted balance casts `system_vote` messages for `op_list` pointing to OP addresses they control; these votes stabilize and are recorded in `op_votes` via `saveSystemVote` [4](#0-3) .
2. These votes get counted through the normal `system_vote_count` flow, installing the malicious OP set into `system_vars.op_list`.
3. The malicious OPs then censor/refuse to cooperate, causing the main chain to stall for longer than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) [9](#0-8) .
4. The emergency mechanism runs, calling `countVotes(..., is_emergency=1, ...)`, which uses `op_votes_tmp` plus fresh unstable votes to select a new, honest OP list and writes it to `system_vars` [6](#0-5) [7](#0-6) . The real `op_votes` table still contains the attacker's original votes, untouched.
5. Once a unit stabilizes under the new honest OPs, the attacker (or anyone) posts a unit containing a `system_vote_count` message for `op_list` — a message with no special authorization requirement [2](#0-1) .
6. At stabilization, `main_chain.js` processes `voteCountSubjects` and calls `countVotes(conn, mci, 'op_list')` (non-emergency), which reads the still-poisoned `op_votes` table and reinstates the malicious OP list [10](#0-9) [5](#0-4) , negating the emergency fix and potentially re-triggering the stall/censorship cycle.

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
