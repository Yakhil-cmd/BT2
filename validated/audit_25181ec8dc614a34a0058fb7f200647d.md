### Title
Webhook signature verified against the payload's `repository.owner.login` while the event is written to the repository identified by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC against using an **unverified** field taken from the JSON body (`repository.owner.login`, falling back to `organization.login`), while every event `Handler` then looks up the target `Stack`/`Repository` using a **different** unverified field, `repository.full_name`. These two fields are never cross-checked against each other.

### Finding Description
`repository_owner` is derived straight from the attacker-controlled request body before the signature is verified: [1](#0-0) 

That value is fed into `Shipit.github(organization: repository_owner)` to pick the app/secret used for `verify_webhook_signature`: [2](#0-1) 

Once the signature check passes, `create` dispatches the same raw, attacker-controlled JSON to the relevant `Shipit::Webhooks::Handlers::Handler` subclasses: [3](#0-2) 

Every handler resolves the repository/stack to act on from `payload.dig('repository', 'full_name')` — a completely independent field from the one used for signature verification: [4](#0-3) 

This is the exact bug class from the report: two values that are supposed to be bound together (the org whose secret authenticated the request vs. the repository the event is applied to) are never actually compared. In multi-organization Shipit deployments (multiple GitHub Apps/orgs configured, e.g. via `Shipit.github(organization:)` supporting per-org config, as documented in `docs/setup.md`), an attacker who controls (or compromises) the webhook secret/app for **Organization A** can send a webhook whose `repository.owner.login`/`organization.login` says "OrgA" (so it authenticates against OrgA's secret) but whose `repository.full_name` says `"OrgB/some-other-repo"` (a repo Shipit tracks under a different, unrelated organization). The signature check passes because it's checking OrgA's HMAC against OrgA's secret, but the actual mutation (new commits appended via `PushHandler` → `GithubSyncJob`, PR opened → review stack provisioning, commit status written, etc.) is applied to OrgB's stack.

Concretely for `push`: [5](#0-4) 
`stacks` here comes from `Handler#stacks`, resolved via `repository.full_name`, not the verified owner.

### Impact Explanation
This breaks the trust binding "organization that authenticated" == "repository that is written," matching the High/Critical bucket for cross-repository writes: an actor holding one organization's webhook secret can forge push/status/check_suite/pull_request events that get applied to a completely different organization's `Stack` records — triggering unintended `GithubSyncJob` syncs, commit status writes, review-stack provisioning, or merge-queue processing for repositories they do not control. Since Shipit uses the synced commit/status data to decide what is deployable and merges pull requests automatically via the merge queue, this can influence which commits are considered deployable/mergeable for a stack outside the attacker's actual authorization scope.

### Likelihood Explanation
Requires the attacker to already possess a valid webhook secret for at least one organization configured in the Shipit instance (this is a documented, legitimately-issued credential for that org, not root/database access). Given that Shipit is explicitly designed to serve multiple organizations/repositories from a single instance (see `docs/setup.md`, `Shipit.github(organization:)`), this is a realistic operational scenario for any deployment with more than one GitHub App/org configured. The out-of-scope rules exclude findings that require "an `ApiClient` token, `webhook_secret` ... or a privileged account," and here the attacker does need a `webhook_secret` — but only for a *different* organization than the one being attacked, i.e., the whole point of the bug is that possessing an unrelated organization's low-value credential is sufficient to write into a different repository's data. This is the same "unprivileged-attacker-relative-to-target" pattern called out by the rules ("an organization that authenticated versus the repository that is written").

### Recommendation
After verifying the signature, cross-check that the organization used to select the webhook secret (`repository_owner`) matches the owner encoded in `repository.full_name` (and in any handler that resolves a `Stack`/`Repository`). Reject the request (422) if they diverge. Alternatively, derive the app/secret to verify with strictly from the same `repository.full_name` (or its owner segment) that handlers use to resolve which `Stack` to mutate, so a single unverified field drives both the authentication and the target-resolution decision.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`), and create a `Stack` for `OrgB/target-repo`.
2. As an attacker who knows only `OrgA`'s `webhook_secret` (e.g., from a compromised/leaked low-value integration), craft a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "full_name": "OrgB/target-repo",
       "owner": { "login": "OrgA" }
     }
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and send it to `POST /webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and the signature verifies successfully (per `app/controllers/shipit/webhooks_controller.rb:24-30` and `app/controllers/shipit/webhooks_controller.rb:59-62`).
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name') == "OrgB/target-repo"` (per `app/models/shipit/webhooks/handlers/handler.rb:32-38` and `app/models/shipit/webhooks/handlers/push_handler.rb`) and enqueues `GithubSyncJob` for `OrgB`'s stack, even though the request never held any credential for `OrgB`.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
