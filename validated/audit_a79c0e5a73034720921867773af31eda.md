### Title
Cross-tenant privilege escalation via `MembershipHandler` writing to shared `Team`/`Membership` records without organization scoping - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` purely by the attacker-controlled `params.team.id` (GitHub's global team ID), never checking that `params.organization.login` matches the resolved team's `organization` column. In a multi-tenant `Shipit.github` deployment, a webhook validly signed with one tenant org's `webhook_secret` can therefore add/remove members on a completely different org's `Team` record, including teams listed in `Shipit.github_teams` that gate application-wide authorization via `User#authorized?`.

### Finding Description
The binding that should hold before any mutation is:

`params.organization.login == Team.find_by(github_id: params.team.id).organization`

but the code never establishes it. `WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate against using `repository_owner`, which for membership payloads (no `repository` key) falls back to `params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 

So the signature is checked only against whichever organization the attacker names in the payload — the attacker's own tenant org, whose `webhook_secret` they legitimately hold as that org's onboarded GitHub App operator. Once verified, `MembershipHandler#process` calls `find_or_create_team!`, which resolves teams solely by the global `github_id`, ignoring organization entirely for pre-existing rows: [3](#0-2) 

The `organization` assignment in the `find_or_create_by!` block only runs on creation; for any team that already exists (e.g. a team already onboarded via `Shipit.github_teams`, which is populated from `Team.find_or_create_by_handle` scoped by `organization`+`slug`), the lookup silently returns the existing record regardless of which org the requesting webhook claims: [4](#0-3) [5](#0-4) 

**Exploit flow:** Attacker administers Org B, a distinct tenant configured in Shipit's multi-org `github:` secrets (per `docs/setup.md`'s "Using Multiple Github Applications" section) and knows Org B's `webhook_secret` (they configured it themselves when creating their GitHub App). They compute a valid `X-Hub-Signature` HMAC over a hand-crafted JSON body — signature verification only checks the raw-body HMAC, it does not validate that the JSON content reflects a real GitHub event: [6](#0-5) 

They POST to `/webhooks` with header `X-Github-Event: membership` and body: `action: 'added', team: { id: <victim_team.github_id>, ... }, organization: { login: 'org-b' }, member: { login: <arbitrary-or-own-login> }`. `verify_signature` validates using Org B's secret and passes. `find_or_create_team!` finds the pre-existing victim `Team` by `github_id` and `team.add_member(member)` runs, inserting a `Membership` row for the attacker (or any GitHub login they name) into a team belonging to an unrelated org — potentially one of the teams in `Shipit.github_teams`.

No existing guard prevents this: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schema only validates shape/types, not cross-field organization consistency; there is no model validation tying `Membership`/`Team` writes to the org that authenticated the request.

### Impact Explanation
A member of an unrelated, distrusted tenant org can insert themselves (or any named GitHub login) into any `Team` record known only by its `github_id`, including teams enumerated in `Shipit.github_teams`. Since `User#authorized?` grants global Shipit access based on membership in `Shipit.github_teams`: [7](#0-6) 

this is a cross-tenant escalation into `Shipit.github_teams` authorization — matching the High severity category. It is repeatable against any team whose `github_id` the attacker can learn (often discoverable via GitHub's own team/org APIs), and the blast radius spans every tenant org sharing the single Shipit instance's `Team`/`Membership` tables, since `Team.github_id` has no org-scoped uniqueness/ownership enforcement at write time.

### Likelihood Explanation
Requires a Shipit deployment using the documented multi-organization `github:` secrets configuration serving at least two mutually-untrusted orgs. The attacker needs no privileged secret beyond the `webhook_secret` of their own legitimately onboarded tenant (which they configured themselves), and needs to know or guess a victim team's numeric GitHub `github_id` — obtainable via GitHub's team/org APIs in many configurations. Cost is a single crafted HTTP POST with a correctly computed HMAC using their own known secret; fully repeatable and automatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and the requesting `params.organization.login`, rejecting or logging a mismatch if an existing `Team` with that `github_id` belongs to a different `organization` than the one that authenticated the webhook. More generally, enforce `organization` as part of the uniqueness/lookup key for `Team`, and validate in `MembershipHandler#process` that `team.organization == params.organization.login` before mutating memberships.

          User.stubs(:find_or_create_by_login!).with('attacker').returns(users(:walrus))

          assert_no_difference -> { Membership.where(team: victim_team).count } do
            MembershipHandler.new.call(payload.deep_stringify_keys)
          end

          # != victim_team.organization ('shopify'), proving the binding is not enforced.
        end

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
