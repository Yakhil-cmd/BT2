### Title
RAY value overflow during interest accrual permanently freezes a market - (File: common/src/rates/index.rs)

### Summary
An unprivileged whale can create a sufficiently large, heavily utilized market position and let interest growth push a scaled-position multiplication past `i128::MAX`. After that, every state-changing market path synchronizes interest before mutating, so `withdraw`, `repay`, `borrow`, liquidation, bad-debt cleanup, and even `update_indexes` revert with `MathOverflow`, permanently freezing the market absent a privileged contract upgrade. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The pool stores supply and debt as scaled RAY shares and derives current balances by multiplying those shares by their respective indexes. [4](#0-3) 

`interest::global_sync` is called by `synced_market` before normal pool mutations, while the public `update_indexes` path calls the same accrual routine for each selected market. [1](#0-0) [5](#0-4) 

During accrual, `calculate_supplier_rewards` computes both `borrowed * old_borrow_index` and `borrowed * new_borrow_index`; analogous supply-value multiplication occurs in `update_supply_index`. [6](#0-5) [2](#0-1) 

Those multiplications must fit the protocol's `i128` RAY-value domain, but the configured market limits do not guarantee that future index growth will keep an admitted position representable. [7](#0-6) [8](#0-7) 

Once the product overflows, the accrual transaction fails before committing a later timestamp or a capped index, and increasing elapsed time cannot make a subsequent accrual succeed. [9](#0-8) [10](#0-9) 

The controller exposes `update_indexes` as a permissionless caller-authorized endpoint, so any address can trigger the accrual once the vulnerable market state exists. [11](#0-10) [12](#0-11) 

### Impact Explanation
This is permanent freezing of user funds and can also leave the protocol unable to resolve the affected market. [1](#0-0) 

Because repayment and withdrawal first synchronize the market, neither borrowers nor suppliers can use the ordinary exit paths after the overflow. [13](#0-12) [14](#0-13) 

The deterministic regression test demonstrates the same cliff: after an eventual `MathOverflow` from `update_indexes`, both a withdrawal and a repayment fail with `MathOverflow`, while the borrow index remains below its configured ceiling. [15](#0-14) 

### Likelihood Explanation
The attack requires an existing market whose caps and asset supply permit approximately one billion 18-decimal tokens of exposure, plus enough collateral to borrow roughly 98% of it. [16](#0-15) 

At that scale, the position's RAY value is already `10^36`; sustained high-utilization accrual only needs to multiply it beyond `i128::MAX`, which the regression test reaches before the `10^36` borrow-index ceiling can protect the market. [17](#0-16) 

The capital requirement makes this less likely than an ordinary small-input bug, but all required state can be created through normal `supply` and `borrow` calls by one funded, unprivileged address, and no governance call or leaked key is needed during exploitation. [18](#0-17) [19](#0-18) 

### Recommendation
Prevent accrual from constructing an unrepresentable RAY total instead of letting `Ray::mul` panic after the index has advanced in memory. [2](#0-1) 

The accrual path should calculate `borrowed * index` and `supplied * index` with a wider intermediate or enforce a per-market scaled-share bound derived from the maximum future index before minting additional shares. [4](#0-3) [20](#0-19) 

If a bound is reached, accrual should clamp the index to the largest representable value or stop interest accrual for that market rather than revert, preserving repayment and withdrawal while reporting the saturation explicitly. [9](#0-8) 

### Proof of Concept
On an existing 18-decimal market with sufficiently high caps and an interest curve capable of sustained high-utilization accrual, one funded attacker can execute the following sequence through the public controller ABI: [21](#0-20) [11](#0-10) 

```text
let target = HubAssetKey { hub_id, asset: target_token };
let collateral = HubAssetKey { hub_id, asset: collateral_token };

// 1e27 base units = 1 billion whole tokens at 18 decimals.
supply(
    caller,
    account_id = 0,
    spoke_id,
    [
        (target, 1_000_000_000 * 10^18),
        (collateral, sufficient_collateral_for_debt),
    ],
);

// Borrow about 98% of the supplied target liquidity.
borrow(
    caller,
    account_id,
    [(target, 980_000_000 * 10^18)],
    None,
);

// After enough interest has accumulated, any caller can trigger the cliff.
update_indexes(caller, [target]);
```

The harness uses this same shape: it supplies `1_000_000_000 * 10^18` target units, supplies separate collateral, borrows 98% of the target principal, advances time, and observes `MathOverflow` from `update_indexes`. [22](#0-21) 

The subsequent withdrawal and repayment calls also fail with `MathOverflow`, proving that the overflow freezes ordinary exit paths rather than merely reverting the triggering keeper call. [23](#0-22)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Borrows to `to` or the authorized owner/delegate, then checks solvency.
/// Persists supply alongside debt when the check restamps supply LTVs.
pub(crate) fn process_borrow(
    env: &Env,
    caller: &Address,
    account_id: u64,
    borrows: &Vec<HubPayment>,
    to: Option<Address>,
) {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_positive_payments(env, borrows);

    validate_position_entry_gates(
        env,
        &account,
        &aggregated,
        &mut cache,
        AccountPositionType::Borrow,
    );
    settle_borrow(env, &mut account, &recipient, &aggregated, &mut cache);

    let restamped = enforce_post_pool_solvency(env, &mut cache, &mut account);
    let sides = if restamped {
        PositionSides::Both
    } else {
        PositionSides::Debt
    };
    finalize_position_flow(env, account_id, &account, &mut cache, sides, false);
}
