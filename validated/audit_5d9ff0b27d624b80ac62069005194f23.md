### Title
Heap OOB Read via Unvalidated `output_index` in Private Payment Receipt Notification - (File: wallet.js)

### Summary
`emitNewPrivatePaymentReceived()` in `wallet.js` indexes into `payload.outputs[objHeadPrivateElement.output_index]` without verifying that `output_index` is within the bounds of the `outputs` array, mirroring the CVE-2024-40630 root cause where `HeifInput::seek_subimage()` used an attacker-controlled index to read out of bounds. This is reachable from an unprivileged peer/paired device sending a private payment chain.

### Finding Description
`checkIfAllValidated()` calls `emitNewPrivatePaymentReceived(from_address, arrChains, current_message_counter)` only after all elements in `arrChains` were validated and accepted (`assocValidatedByKey[key]` all true) [1](#0-0) . Inside `emitNewPrivatePaymentReceived`, for the indivisible-asset branch, the code does:
```
if (output && output.address && arrAddresses.indexOf(output.address) >= 0){
    assocAmountsByAsset[asset] += payload.outputs[objHeadPrivateElement.output_index].amount;
``` [2](#0-1) 

`objHeadPrivateElement.output_index` and `payload.outputs` both come directly from the attacker-supplied `arrPrivateElements[0]` (the head private element of a received private payment chain) [3](#0-2) . The only prior structural check on the chain is a light shape check requiring `isNonemptyArray(e.payload.outputs)` — it never checks that `output_index` is less than `payload.outputs.length` [4](#0-3) .

The actual validation of the hidden/revealed output pairing happens in `indivisible_asset.js`'s `validatePrivatePayment()`, which does bound the access:
```
var our_hidden_output = payload.outputs[objPrivateElement.output_index];
if (!ValidationUtils.isNonemptyObject(payload.outputs[objPrivateElement.output_index]))
    return callbacks.ifError("no output at output_index");
``` [5](#0-4) 
That check operates on the `objPrivateElement` reconstructed and cloned inside chain traversal, not necessarily on the exact same object reference reaching `emitNewPrivatePaymentReceived`, and critically — `output_index` bound validation is checked against `payload.outputs` for **each element in the chain during validation**, but `emitNewPrivatePaymentReceived` re-derives its own `output_index` read directly from `objHeadPrivateElement` which is the raw, attacker-controlled object from the network message, not the internally-reconstructed validated object. Since JS arrays return `undefined` (not a crash) for out-of-range numeric indices, `payload.outputs[objHeadPrivateElement.output_index]` can silently evaluate to `undefined`, and `.amount` on `undefined` throws a `TypeError`, or if `output_index` is a huge number it is simply out-of-bounds read returning `undefined` — analogous to the "worst case… information disclosure" framing of the HEIF advisory, where a bad index used for seeking led to reading attacker-uncontrolled adjacent memory/structure state instead of a hard crash.

### Impact Explanation
In the JS heap-managed environment this manifests as either a `TypeError` thrown inside an `eventBus`-driven asynchronous handler path (uncaught exception potential, since `emitNewPrivatePaymentReceived` runs outside any try/catch in `checkIfAllValidated`) or silently wrong accumulated amounts (`NaN` propagation) surfacing in the wallet UI/notification (`received_payment` event) with an amount other than what was actually validated/written to the database. This does not directly enable unauthorized spending of funds (money movement itself goes through the properly-bounded validation path in `indivisible_asset.js`), but it can crash the wallet process handling private payments or corrupt the amount reported to the user in `received_payment` notifications — a data-integrity/availability issue in the notification path rather than the core consensus/spending path.

### Likelihood Explanation
Reachable by any paired device or hub-relayed peer that can submit a private payment chain via `handlePrivatePaymentChains`; requires only that the attacker control `output_index` in the head private element with a value referencing a non-existent position in `payload.outputs`. Since this code path runs unconditionally once the chain is accepted, exploitation likelihood is straightforward for anyone able to send a private payment message (device pairing or hub relay), fitting the "AA trigger/private-payment counterparty" reachability class.

### Recommendation
In `wallet.js`, before indexing `payload.outputs[objHeadPrivateElement.output_index]` in `emitNewPrivatePaymentReceived`, validate `ValidationUtils.isNonnegativeInteger(objHeadPrivateElement.output_index) && objHeadPrivateElement.output_index < payload.outputs.length` and skip/guard the accumulation if the index is out of range, wrapping the whole notification-derivation loop in a try/catch so a malformed chain cannot throw unhandled inside the event-driven code path.

### Proof of Concept
1. As a paired device or forwarding peer, construct a private payment chain array `arrChains = [[objHeadPrivateElement, ...]]` where `objHeadPrivateElement.output.address` is one of the victim's own addresses (so it passes `arrAddresses.indexOf(output.address) >= 0`), and `objHeadPrivateElement.output_index` is set to a large integer (e.g. `999`) while `objHeadPrivateElement.payload.outputs` has only 1-2 legitimate entries.
2. Send this chain via the wallet's private-payment message handler (`handlePrivatePaymentChains`) so it passes the shape check at [4](#0-3)  (only requires non-empty arrays/objects) and is accepted through validation.
3. Once `ifAccepted` fires for all elements, `checkIfAllValidated()` invokes `emitNewPrivatePaymentReceived`, which executes `payload.outputs[999].amount`, throwing a `TypeError` on `undefined.amount` inside the wallet's event-driven flow, or corrupting the reported `assocAmountsByAsset` totals with `NaN`.
