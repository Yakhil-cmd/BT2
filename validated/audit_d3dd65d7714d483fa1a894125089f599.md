### Title
Untrusted `.gitmodules` submodule URLs in synced content are fetched with `git submodule update --init --recursive` without protocol restriction, enabling attacker-controlled transports and credential exfiltration - (File: main.go)

### Summary
`git-sync` treats the content of the tracked branch/ref as fully trusted and, as part of `configureWorktree`, unconditionally runs `git submodule update --init --recursive` (or `--depth`) against whatever URLs are declared in the synced `.gitmodules` file [1](#0-0) . This mirrors the structure of the reported `AdapterVault` bug: an operation that is supposed to be routine/low-risk (rebalancing / here, submodule fetch) blindly consumes attacker-influenced input (`pregen_info` / here, `.gitmodules` URLs) that a lower-trust actor (a proposer / here, anyone who can land a commit on the synced ref) controls, and that input is fed straight into a privileged action (a swap / here, a `git fetch`/`clone` using globally configured credentials).

### Finding Description
`configureWorktree` performs the checkout and then submodule initialization with no per-URL vetting: [2](#0-1) 

The submodule URLs come entirely from the synced repository's own `.gitmodules` file, which is ordinary tracked content — the e2e tests demonstrate this is exactly how submodule URLs are set and later changed by ordinary commits (`git submodule add`, editing `.gitmodules`) [3](#0-2) . Whoever can get a commit merged/pushed onto the ref that `git-sync` follows can therefore choose the submodule URL and host that `git-sync`'s `git submodule update` will contact — this is the "malicious proposer" analog from the report: a lower-privileged content-contributor influencing which endpoint a privileged workflow talks to.

Two consequences follow from `git-sync`'s credential model:
1. **Credential availability across hosts.** `git-sync` stores primary-repo credentials via `git credential approve` (`StoreCredentials`) and documents that `--credential` exists specifically "for specific URLs, for example when using submodules" [4](#0-3) [5](#0-4) . If an askpass URL, cookie file, or broadly-scoped credential helper is configured (all supported auth modes) [6](#0-5) [7](#0-6) , a malicious `.gitmodules` entry can point a submodule at an attacker-controlled host to try to capture whatever credential/cookie material git's credential negotiation offers for that request (git only sends usernames/passwords when they match stored/helper entries for the exact host, but cookie files and any wildcard/global credential helpers configured by the operator are not scoped the same way, and are explicitly a supported git-sync configuration).
2. **No transport allow-listing.** Production code never restricts `protocol.file.allow`/`protocol.ext.allow`/`GIT_ALLOW_PROTOCOL`; the only place `protocol.file.allow=always` appears is in the test harness (`test_e2e.sh`), not in `main.go` [8](#0-7) . Production `git-sync` relies entirely on the git binary's own default protocol allow-list, which is fine only as long as no operator or downstream config (e.g. `--git-config`, which lets arbitrary `git config` keys be set from a flag [9](#0-8) ) loosens it — at which point `.gitmodules` content fully controls which transport (including `ext::`, which can execute arbitrary local commands) is invoked.

### Impact Explanation
If accepted, an attacker who can only contribute to the synced branch (not an operator, not a leaked-key holder) can:
- Force `git-sync` to make outbound requests to attacker-chosen hosts using whatever ambient auth material (cookie file, askpass response, broadly scoped credential helper) is configured, potentially disclosing credentials/tokens to the attacker's server.
- If the deployment has ever loosened protocol allow-listing (a documented, supported customization via `--git-config`), achieve command execution via `ext::` submodule URLs during `git submodule update`.

This matches the required impact categories: credential/token disclosure, and (conditionally, when `protocol.ext`/`file` are enabled) code execution.

### Likelihood Explanation
Medium. It requires (a) an untrusted contributor able to land a commit/PR that reaches the synced ref (a realistic scenario for git-sync's typical use as a config/GitOps sidecar pulling from repos where CI or bots merge PRs), and (b) either a broadly-scoped credential/cookie configuration or an operator having relaxed the default git protocol allow-list via `--git-config`/`--git-config-add`. The credential-exfiltration variant is more likely (no special config needed beyond common cookie-file/askpass-url auth patterns that are explicitly documented git-sync features); the code-execution variant depends on non-default git protocol configuration.

### Recommendation
- Explicitly pin `protocol.file.allow=user` and `protocol.ext.allow=never` (or stricter) around all fetch/submodule/worktree git invocations, regardless of any operator-supplied `--git-config`, so untrusted `.gitmodules` content can never select a dangerous transport.
- Document/require operators to scope credential helpers and cookie files strictly to the primary `--repo` host, and warn against wildcard credential helpers when submodules are enabled.
- Consider an opt-in flag to disable submodule following entirely by default for untrusted content, or to require an explicit allow-list of submodule URL hosts before `git submodule update --init` is run.

### Proof of Concept
1. Configure `git-sync` with `--cookie-file` or `--askpass-url` (or a global/wildcard `credential.helper`) pointing at credentials valid for the primary `--repo` host, and `--submodules=recursive` (the default).
2. As a low-privilege contributor, submit/merge a commit to the synced branch that adds/edits `.gitmodules` to point a submodule at `http://attacker.example/collect` (following the same pattern as the `submodule_sync_default` test flow, but with an attacker-controlled URL instead of a local `file://` path) [3](#0-2) .
3. On the next sync, `configureWorktree` runs `git submodule update --init --recursive`, which contacts `attacker.example`; depending on the git credential/cookie configuration in use, git may present cached credential material or cookies to that host, which the attacker's server logs [2](#0-1) .
4. If the operator has ever loosened `protocol.ext.allow` via `--git-config`, the same `.gitmodules` entry could instead use `ext::sh -c ...` to achieve command execution during the same `submodule update` step.

```go
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}
```

```go
// CallAskPassURL consults the specified URL looking for git credentials in the
// response.
//
// The expected URL callback output is below,
// see https://git-scm.com/docs/gitcredentials for more examples:
//
//	username=xxx@example.com
//	password=xxxyyyzzz
func (git *repoSync) CallAskPassURL(ctx context.Context) error {
	git.log.V(3).Info("calling auth URL to get credentials")

	var netClient = &http.Client{
		Timeout: time.Second * 1,
		CheckRedirect: func(req *http.Request, via []*http.Request) error {
			return http.ErrUseLastResponse
		},
	}
	httpReq, err := http.NewRequestWithContext(ctx, http.MethodGet, git.authURL, nil)
	if err != nil {
		return fmt.Errorf("can't create auth request: %w", err)
	}
	resp, err := netClient.Do(httpReq)
	if err != nil {
		return fmt.Errorf("can't access auth URL: %w", err)
	}
	defer func() {
		_ = resp.Body.Close()
	}()
	if resp.StatusCode != http.StatusOK {
		errMessage, err := io.ReadAll(resp.Body)
		if err != nil {
			return fmt.Errorf("auth URL returned status %d, failed to read body: %w", resp.StatusCode, err)
		}
		return fmt.Errorf("auth URL returned status %d, body: %q", resp.StatusCode, string(errMessage))
	}
	authData, err := io.ReadAll(resp.Body)
	if err != nil {
		return fmt.Errorf("can't read auth response: %w", err)
	}

	username := ""
	password := ""
	for line := range strings.SplitSeq(string(authData), "\n") {
		keyValues := strings.SplitN(line, "=", 2)
		if len(keyValues) != 2 {
			continue
		}
		switch keyValues[0] {
		case "username":
			username = keyValues[1]
		case "password":
			password = keyValues[1]
		}
	}

	if err := git.StoreCredentials(ctx, git.repo, username, password); err != nil {
		return err
	}

	return nil
```
