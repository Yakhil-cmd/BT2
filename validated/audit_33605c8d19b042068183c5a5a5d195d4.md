### Title
Missing zero-address check for `creator` in `InitializeWithPermission` permanently locks creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts an attacker-controlled `creator` account that is only an `UncheckedAccount`, not a `Signer`, and stores it into `PoolState.pool_creator` with no validation that it is non-zero or otherwise controllable by anyone. Any subsequent creator fees that accrue on the pool become permanently unrecoverable if `creator` is set to the zero address (or any other unowned address).

### Finding Description
In `InitializeWithPermission`, the `creator` field is declared as an `UncheckedAccount` with only a doc comment `/// CHECK: creator of pool` and no signer requirement or zero-address constraint: [1](#0-0) 

The `payer` (any unprivileged caller who owns the `payer_token_0`/`payer_token_1` accounts) is the only signer required, so `payer` can pass an arbitrary `creator` pubkey, including `11111111111111111111111111111111` (the System Program's own address, which is not a keypair-controlled account): [2](#0-1) 

This unchecked `creator.key()` is passed straight into `pool_state.initialize(...)` and stored as `pool_creator` with no validation: [3](#0-2) [4](#0-3) 

`pool_creator` later gates both fee-collection paths:
- `collect_creator_fee` requires `creator` to be a `Signer` whose address equals `pool_state.pool_creator`: [5](#0-4) 
- `collect_creator_fee_permissionless` allows anyone to trigger collection, but still sends the accumulated `creator_fees_token_0`/`creator_fees_token_1` to an ATA whose `authority` is `pool_creator`: [6](#0-5) [7](#0-6) 

If `pool_creator` is set to an address with no corresponding private key (e.g. the System Program's own address, or any other unowned/burn-like pubkey), `collect_creator_fee` can never succeed (no one can produce a valid signature for that address), and `collect_creator_fee_permissionless` will happily create an ATA owned by that unreachable address and irreversibly transfer the accumulated creator fees into it every time it is called.

### Impact Explanation
Creator fees are real user funds withheld from every swap on the pool (`update_fees` in `pool.rs` accumulates `creator_fees_token_0`/`creator_fees_token_1` on each trade) and are meant to be paid out to the pool creator via `collect_creator_fee`/`collect_creator_fee_permissionless`. If the `creator` account is set to an unowned address at pool creation, those fees become permanently frozen/unrecoverable, since no key exists to sign for `collect_creator_fee`, and `collect_creator_fee_permissionless` will only funnel the funds into an ATA controlled by the same unowned address, from which no one can ever transfer them out. This is a permanent freezing of pool-generated funds.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding a valid `Permission` PDA and funding the initial liquidity; the attacker fully controls the `creator` account passed in the instruction, requiring no special privilege beyond calling the pool-creation instruction. Setting `creator` to the zero/unowned pubkey costs nothing extra and is trivially achievable in a single transaction.

### Recommendation
Add an explicit check in `initialize_with_permission` (or in the `InitializeWithPermission` account validation) that `creator.key() != Pubkey::default()` (and ideally is not any other well-known unowned address), rejecting the instruction otherwise, similar to the recommended `require!(_owner != address(0))` pattern from the referenced report.

### Proof of Concept
1. Attacker calls `create_permission_pda` for themselves (as `payer`) to obtain a valid `Permission` PDA.
2. Attacker calls `initialize_with_permission` with `payer` = themselves (signer), and `creator` = `11111111111111111111111111111111` (System Program ID, an UncheckedAccount requiring no signature).
3. `pool_state.initialize(...)` stores `pool_creator = 11111111111111111111111111111111`.
4. Swaps occur on the pool, accruing `creator_fees_token_0`/`creator_fees_token_1` in `pool_state` (per `update_fees`).
5. `collect_creator_fee` can never be called successfully because no signer can match `pool_creator`.
6. `collect_creator_fee_permissionless` can be called by anyone, but it creates/uses an ATA with `authority = 11111111111111111111111111111111` and transfers the fees there — funds are now locked in an account no private key can ever control.
