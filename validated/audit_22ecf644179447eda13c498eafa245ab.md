This confirms the mechanism: `calcEarnings` sums `headers_commission_outputs.amount` per address/range and this total is used directly as the spendable input amount in `validation.js`, with no cross-check against the actual `headers_commission` paid by the payer unit. The rounding happens once at insertion time in `headers_commission.js` and is never reconciled against the total commission actually available.

### Title
Rounding in headers-commission split among multiple earned-commission recipients can inflate total spendable bytes - (File: headers_commission.js)

### Summary
When a headers commission (`hc`) won by a unit is distributed among multiple `earned_headers_commission_recipients`, each recipient's share is computed with `Math.round(full_amount * share / 100.0)` [1](#0-0) . Because each recipient's share is rounded independently to the nearest integer, the sum of the rounded shares can exceed the original `full_amount` (`hc`) that was actually paid by the payer unit as its commission. The resulting inflated total is inserted into `headers_commission_contributions`/`headers_commission_outputs` and later becomes directly spendable, unconditionally, as `type: "headers_commission"` payment inputs.

### Finding Description
`calcHeadersCommissions()` computes, for each payer unit, a fixed `headers_commission` amount owed to the winning child unit's author(s). When the winning unit specifies multiple recipients via `earned_headers_commission_recipients` (each with an integer `earned_headers_commission_share`, validated only to be a positive integer summing to exactly 100 in `validateHeadersCommissionRecipients`) [2](#0-1) , each recipient's payout is computed as:

```js
var amount = (row.earned_headers_commission_share === 100)
    ? full_amount
    : Math.round(full_amount * row.earned_headers_commission_share / 100.0);
``` [3](#0-2) 

Rounding each recipient's fractional share to the nearest integer independently does not guarantee `sum(amounts) == full_amount`. For carefully chosen percentage splits and `full_amount` values, the sum of individually rounded shares can be strictly *greater* than `full_amount`. For example, with `full_amount = 11` and shares `{33, 33, 34}`: `round(3.63)=4`, `round(3.63)=4`, `round(3.74)=4`, summing to `12` — one unit more than the `11` that was actually collected as commission.

The same rounding pattern is used in the MySQL code path via `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` [4](#0-3) .

These per-address amounts are summed into `headers_commission_outputs` [5](#0-4) , and later consumed unconditionally by `mc_outputs.calcEarnings`, which just sums `headers_commission_outputs.amount` over an mci range for an address with no cross-check against the true amount of commission actually paid by the corresponding payer units [6](#0-5) . The result is accepted directly as the input `amount` for a `type: "headers_commission"` payment input during validation [7](#0-6) , with no invariant enforcing that the sum paid out to all recipients cannot exceed the commission actually collected.

Because the recipient list and percentage shares are entirely chosen by the ordinary unit author (single- or multi-authored units may include `earned_headers_commission_recipients`) at the time the unit is posted, an unprivileged unit poster can deliberately select a fine-grained set of recipients/shares whose rounded sum systematically exceeds 100% of the true commission, extracting extra spendable bytes that were never actually paid by any spender.

### Impact Explanation
This is a supply-inflation bug: bytes become spendable that were never deducted from any payer's balance, breaking the fixed total money supply invariant (`TOTAL_WHITEBYTES`) that the network is supposed to preserve. An attacker who repeatedly posts such units (as author of winning child units across many parent units) can accumulate small amounts of "free" bytes indefinitely, and because this happens deterministically from data included in stable, witnessed units, all full nodes will independently compute and accept the same inflated `headers_commission_outputs`, so this is a genuine protocol-level fund creation rather than merely a local inconsistency.

### Likelihood Explanation
Likelihood is High: any user who can post a unit with an `earned_headers_commission_recipients` list (available to single- and multi-authored units alike) that will win future headers commissions can choose share percentages designed to produce this rounding overshoot, and can repeat the strategy across many parent units over time to accumulate the excess.

### Recommendation
Do not round each recipient's share independently. Instead, when splitting `full_amount` across `earned_headers_commission_recipients`, compute shares so they sum exactly to `full_amount` — e.g., round down (floor) each share except the last, and assign the last recipient the remainder (`full_amount - sum_of_previous_shares`), or use a largest-remainder-style allocation. This mirrors the general lesson from the referenced Centrifuge report: rounding direction/behavior must be chosen deliberately (favoring the protocol, i.e., never allowing payouts to exceed the funded amount) rather than applying naive per-item `Math.round`.

### Proof of Concept
1. Attacker (single author, or as one of several authors) posts a unit `U` that will later win headers commission from some ancestor `P`, and includes `earned_headers_commission_recipients` such as `[{address: A, share: 33}, {address: B, share: 33}, {address: C, share: 34}]` (sum = 100, validated by `validateHeadersCommissionRecipients`).
2. Suppose `P.headers_commission` (the `full_amount` computed in `calcHeadersCommissions`) happens to equal `11` bytes (attacker can influence which parent units are targeted / repeat over many parents to find matching amounts, or use many recipients to guarantee an overshoot for arbitrary `full_amount`).
3. `calcHeadersCommissions()` computes:
   - `round(11*33/100) = round(3.63) = 4` for A
   - `round(11*33/100) = round(3.63) = 4` for B
   - `round(11*34/100) = round(3.74) = 4` for C
   - Total inserted into `headers_commission_contributions`/`headers_commission_outputs` = `12`, one byte more than the `11` actually collected as commission from `P`.
4. Addresses A, B, C can later spend these `headers_commission_outputs` as ordinary `type: "headers_commission"` inputs via `mc_outputs.calcEarnings`/`validatePaymentInputsAndOutputs`, with the network accepting a cumulative `12` bytes of spendable commission backed by only `11` bytes actually paid — a 1-byte inflation event, repeatable across many parent units to scale the exploit.

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
