### Title
Fee-payer signature count check in `TransactionAuthenticator::verify` excludes `fee_payer_signer`, allowing unbounded signature verification work - (File: types/src/transaction/authenticator.rs)

### Summary
`TransactionAuthenticator::verify` computes `num_sigs` and enforces `MAX_NUM_OF_SIGS` before dispatching to the per-variant verification logic. For the `FeePayer` variant, this pre-check only sums signatures from `self.sender()` and `self.secondary_signers()` and never accounts for `fee_payer_signer`, even though `fee_payer_signer` is verified later in the same function.

### Finding Description
The `verify` function computes the bound as: [1](#0-0) 

`self.sender()` for the `FeePayer` variant returns only the `sender` field [2](#0-1) , and `secondary_signers()` (not shown above but analogous accessor) returns only the `secondary_signers` field. The `fee_payer_signer` field is completely excluded from this sum, despite being a full independent `AccountAuthenticator` that can itself be a `MultiEd25519` or `MultiKey` authenticator carrying an arbitrary (attacker-chosen) number of signatures.

Later, in the `FeePayer` match arm, `fee_payer_signer` is pushed into the `remaining` verification list and actually verified: [3](#0-2) 

Because the upfront bound at lines 161-169 never includes `fee_payer_signer.number_of_signatures()`, an attacker fully controlling their own `FeePayer`-sponsored transaction (as the fee payer signing their own transaction, or crafting an authenticator with an oversized `MultiEd25519`/`MultiKey` fee-payer signature set) can submit a transaction whose total real signature-verification workload vastly exceeds `MAX_NUM_OF_SIGS`, while the guard silently passes.

### Impact Explanation
This breaks the stated invariant that "total signature verification work is bounded" for a transaction admitted into mempool / accepted by vm-validator: the `MAX_NUM_OF_SIGS` check exists specifically to cap the cryptographic verification cost per transaction, and this gap allows that cap to be circumvented for the fee-payer signer slot. This is a resource-bound violation on the admission path (unbounded/oversized cryptographic work accepted), not a sender/signer-identity spoof — the fee-payer signature set is still cryptographically verified and must be valid, so it does not by itself let an attacker forge control of another account.

### Likelihood Explanation
Trivial to trigger: any unprivileged party constructing a self-sponsored (or attacker-controlled sponsor) `FeePayer` transaction can pick an oversized `MultiEd25519`/`MultiKey` authenticator for the `fee_payer_signer` field. No privileged key or approval is required to build such an authenticator, since the attacker signs it themselves with keys they control.

### Recommendation
Include `fee_payer_signer.number_of_signatures()` in the `num_sigs` computation before dispatching, e.g. compute the bound inside each match arm (or add a helper on `TransactionAuthenticator` that also accounts for `fee_payer_signer` when the variant is `FeePayer`) so `MAX_NUM_OF_SIGS` reflects the true total signature-verification workload.
