### Title
Permanent freezing of accrued creator fees when the pool creator's fixed fee-recipient token account cannot receive transfers - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs] / [File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
`collect_creator_fee` and `collect_creator_fee_permissionless` are the only instructions that can drain the pool's accrued `creator_fees_token_0`/`creator_fees_token_1` accounting fields, and both hard-code the destination token account to the pool creator's canonical associated token account (ATA) for `vault_0_mint`/`vault_1_mint`. If that specific ATA can never receive a transfer (e.g., it is frozen by the mint's freeze authority, or the mint enforces a Token-2022 extension such as a transfer hook / permanent delegate / non-transferable condition that blocks transfers to that account), every future call to either instruction reverts, and the accrued creator fees can never be withdrawn, growing forever.

### Finding Description
Both instructions constrain the receiving accounts to a single deterministic address derived from the immutable `pool_creator` field and the pool's fixed mints: [1](#0-0) [2](#0-1) 

There is no way to redirect the fee payout to an alternate account — unlike `collect_protocol_fee` / `collect_fund_fee`, where the admin/fund owner can freely pick any `recipient_token_0_account`/`recipient_token_1_account` at call time: [3](#0-2) 

`pool_creator` itself is set once at pool creation and there is no admin instruction to change it, so the destination ATA is permanently fixed for the life of the pool.

The actual withdrawal logic performs the transfer via `transfer_from_pool_vault_to_user`, and only resets the accumulated fee counters to zero after the transfer succeeds: [4](#0-3) 

Because Solana transactions are atomic, if the CPI transfer to the creator's frozen/blocked ATA fails, the whole instruction reverts and `pool_state.creator_fees_token_0/1` are never reset — this differs from the original Solidity report (where a failed `safeTransfer` can leave the withdrawal request permanently un-clearable). Here the analogous effect is that the ledger balances `creator_fees_token_0`/`creator_fees_token_1`, which keep accumulating on every swap via `update_fees`, become permanently un-collectible: [5](#0-4) 

Swaps, deposits, and withdrawals are unaffected because they don't touch the creator's ATA, so this is scoped specifically to creator-fee collection — but for that specific accounting bucket, funds become permanently frozen with no recovery path in the program.

### Impact Explanation
The creator fee accounted in `pool_state.creator_fees_token_0`/`creator_fees_token_1` represents real value already sitting in the pool's token vaults (backed 1:1 by vault balance) that is earmarked for the creator. Once the creator's ATA becomes permanently unable to receive transfers (frozen by the mint's freeze authority, or blocked by a transfer-hook/permanent-delegate/non-transferable Token-2022 extension on either `vault_0_mint` or `vault_1_mint`), the accrued creator fees can never be collected by any account — this is a permanent freezing of protocol/creator funds tracked by the fee ledger, satisfying the Medium-severity bar for permanent freezing of fee-ledger accounted funds.

### Likelihood Explanation
Freeze authorities and Token-2022 transfer-blocking extensions (transfer hooks, permanent delegate, non-transferable) are standard, commonly used features of tokens listed on Raydium's permissionless CP-swap pools (`initialize`/`initialize_with_permission` accept arbitrary SPL Token / Token-2022 mints). Any mint whose freeze authority freezes the creator's ATA, or whose transfer hook blocks that specific account, triggers this condition without any special privilege over the raydium program itself — it only requires control of the mint's freeze/hook authority, which is external to (and unrelated to) the cp-swap program's trust model.

### Recommendation
Allow the creator (or an admin, as a fallback) to specify/rotate an alternate destination token account for creator fee collection, or add an explicit escape hatch (e.g., admin-only sweep to protocol treasury) if the creator's designated ATA becomes permanently unusable, so that legitimately accrued fees are not locked forever behind a single, unchangeable token account.

### Proof of Concept
1. Create a pool with `token_0_mint` being a Token-2022 mint that has a freeze authority (or a transfer hook / permanent delegate extension) and set `pool_creator` to an address `C`.
2. Let normal trading occur so that `pool_state.creator_fees_token_0` accumulates a nonzero balance (via `update_fees` in `swap_base_input`/`swap_base_output`).
3. The mint's freeze authority freezes `C`'s canonical ATA for `token_0_mint` (or the transfer hook is configured to reject transfers to `C`'s ATA).
4. Any call to `collect_creator_fee` or `collect_creator_fee_permissionless` now fails at the `transfer_from_pool_vault_to_user` CPI for `token_0`, reverting the whole instruction every time.
5. `pool_state.creator_fees_token_0` can never be reduced/collected again — the funds are permanently stuck in the vault while remaining un-withdrawable by anyone.

    pub fn update_fees(
        &mut self,
        protocol_fee: u64,
        fund_fee: u64,
        creator_fee: u64,
        direction: TradeDirection,
    ) -> Result<()> {
        if !self.enable_creator_fee {
            require_eq!(creator_fee, 0)
        }
        let is_creator_fee_on_input = self.is_creator_fee_on_input(direction)?;
        match direction {
            TradeDirection::ZeroForOne => {
                self.protocol_fees_token_0 = self
                    .protocol_fees_token_0
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_0 = self.fund_fees_token_0.checked_add(fund_fee).unwrap();

                if is_creator_fee_on_input {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                }
            }
            TradeDirection::OneForZero => {
                self.protocol_fees_token_1 = self
                    .protocol_fees_token_1
                    .checked_add(protocol_fee)
                    .unwrap();
                self.fund_fees_token_1 = self.fund_fees_token_1.checked_add(fund_fee).unwrap();
                if is_creator_fee_on_input {
                    self.creator_fees_token_1 =
                        self.creator_fees_token_1.checked_add(creator_fee).unwrap();
                } else {
                    self.creator_fees_token_0 =
                        self.creator_fees_token_0.checked_add(creator_fee).unwrap();
                }
            }
        };
        Ok(())
    }
