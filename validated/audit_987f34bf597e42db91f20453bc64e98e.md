### Title
RawCommentList emits attacker-controlled comment content with zero markdown rendering or ANSI/escape sanitization - (File: pkg/cmd/pr/shared/comments.go)

### Summary
`RawCommentList` and its helper `formatRawComment` write `comment.Content()` straight to the output buffer with `fmt.Fprintln`, with no call to `markdown.Render` and no pass through any ANSI-stripping mechanism (`asciisanitizer`, `iostreams.Untrusted`, or `IO.ContentOut`). This buffer is then written directly to `opts.IO.Out` by the callers in `pkg/cmd/pr/view/view.go` and `pkg/cmd/issue/view/view.go`, so any terminal escape sequence embedded by a remote comment author reaches the victim's output byte-for-byte.

### Finding Description
`RawCommentList` (`pkg/cmd/pr/shared/comments.go:29`) iterates comments/reviews and calls `formatRawComment`, which does: [1](#0-0) 
Note line 48: `fmt.Fprintln(&b, comment.Content())` — the comment body is inserted verbatim, unlike `formatComment` (the human/preview path) which pipes content through `markdown.Render` at [2](#0-1) . So the premise that this is a "markdown/HTML render path" is not accurate — `RawCommentList` performs no rendering at all; it is a raw passthrough of the GraphQL `body` field.

The consumer, `pkg/cmd/pr/view/view.go`, invokes this only when stdout is not a TTY and `--comments` is passed: [3](#0-2) 
The result is written with `fmt.Fprint(opts.IO.Out, ...)` — `IO.Out` is the plain stdout writer (only wrapped for Windows console color translation), not `IO.ContentOut`, which is the writer the codebase uses elsewhere specifically to strip ANSI/OSC sequences via `asciisanitizer` when `sanitizeContent` is enabled: [4](#0-3) . The codebase's own `Untrusted` type documents this exact hazard and the intended mitigation pattern (sanitize on `String()`, require an explicit `Raw()` opt-out for non-terminal consumers): [5](#0-4) . `comment.Content()` is never wrapped in `Untrusted`, and never routed through `ContentOut`.

An attacker who authors an issue/PR comment can embed OSC 8 hyperlink escapes (to display misleading link text pointing at a hostile URL), OSC window-title escapes, or CSI cursor-movement/clear sequences designed to overwrite or spoof prior terminal output (e.g., faking a `y/N` confirmation prompt from a later `gh` command in the same terminal session). Because `--comments` in the non-TTY branch is a common target for scripting/piping/redirection (`gh pr view N --comments | less -R`, `gh pr view N --comments > log.txt` followed by `cat log.txt`), the bytes are highly likely to eventually be interpreted by a real terminal even though the immediate `gh` process itself is not attached to one. The project explicitly treats "escape sequences surviving into a byte stream that may later reach a terminal" as the threat model to defend against, independent of whether the immediate command's stdout is a TTY — see the dedicated regression test for `gh run view --log`: [6](#0-5)  and the equivalent deliberate sanitize/opt-out design in `gh gist view`'s raw-dump path: [7](#0-6) . `RawCommentList` has neither the sanitize-by-default behavior nor an explicit, documented raw opt-out flag — it silently emits unsanitized attacker content.

### Impact Explanation
Terminal escape/ANSI injection via a PR/issue comment that any GitHub user can post. Concrete impacts: spoofed terminal prompts/output (tricking a victim into approving a destructive action they didn't intend), OSC 8 hyperlink text spoofing to steer users to credential-harvesting URLs, and window-title/clipboard manipulation on terminals that support those OSC sequences. This matches "Terminal output/prompt spoofing leading to credential capture or unintended destructive confirmation" (High) as scoped in the question, but is bounded by the precondition that the escape bytes must eventually reach an interpreting terminal (piping to a pager, redirect-then-cat, or a terminal multiplexer/log viewer that renders control codes even for redirected output).

### Likelihood Explanation
Fully unauthenticated/unprivileged: any GitHub user who can comment on an issue/PR the victim later inspects. Requires the victim to run `gh pr view <n> --comments` or `gh issue view <n> --comments` in a context where stdout is not directly a TTY (scripts, CI logs, `| less -R`, redirect + later `cat`) — a common enough workflow, though it does add a precondition compared to a straight interactive TTY view (which instead goes through `formatComment`'s `markdown.Render`, whose sanitization was not verified here and is a separate question).

### Recommendation
Route `comment.Content()` in `formatRawComment` through the same sanitize-by-default wrapper used elsewhere for untrusted external content — e.g., wrap it with `iostreams.NewUntrusted(comment.Content())` and print via `%s`/`.String()` (which sanitizes automatically), or write it through `IO.ContentOut` instead of `IO.Out`. If an explicit escape-passthrough is intentionally desired for raw/plumbing use, gate it behind an explicit `--allow-escape-sequences`-style flag as done in `gh gist view`, rather than making it the unconditional default.

// SetContentSanitization toggles ANSI escape sanitization on ContentOut.
// Commands should call this with false when an explicit opt-out flag (e.g.
// --allow-escape-sequences) is set, so subsequent writes of external content
// pass through unmodified.
func (s *IOStreams) SetContentSanitization(enabled bool) {
	s.sanitizeContent = enabled
	s.ContentOut = newContentWriter(s.Out, enabled)
}

// newContentWriter returns the writer to wire up as ContentOut. When
// sanitize is true it inserts an asciisanitizer in front of the underlying
// writer; otherwise it returns the underlying writer directly so writes
// reach stdout unchanged.
func newContentWriter(out io.Writer, sanitize bool) io.Writer {
	if !sanitize {
		return out
	}
	return transform.NewWriter(out, &asciisanitizer.Sanitizer{})
}

// Untrusted wraps string content the application did not author: HTTP response
// bodies, file contents fetched from a remote, anything that originates outside
// the CLI. The raw bytes are unexported so the only ways out are the methods
// below.
//
// Untrusted satisfies fmt.Stringer, and String sanitizes, so any fmt print path
// (Fprint, Fprintf with %s or %v, Sprint) renders the content with ANSI escape
// sequences neutralized. The only way to reach the raw bytes is Raw, which is
// deliberately easy to grep for and is intended for non-terminal uses such as
// hashing, writing to a file, or piping to another program.
type Untrusted struct {
	raw string
}

// NewUntrusted labels a string as untrusted external content.
func NewUntrusted(s string) Untrusted {
	return Untrusted{raw: s}
}

// NewUntrustedBytes labels a byte slice as untrusted external content.
func NewUntrustedBytes(b []byte) Untrusted {
	return Untrusted{raw: string(b)}
}

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
