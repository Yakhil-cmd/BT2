### Title
`StatusHandler` writes commit-status data selected only by SHA, breaking the binding between the organization that authenticated a webhook and the repository whose commit status is mutated - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `status` webhook event is authenticated by computing an HMAC over the signing organization's webhook secret, but the handler that processes the payload applies its effect purely by commit SHA, without re-checking that the SHA belongs to the repository/organization that was actually verified. This breaks the equality `organization_authenticated_by_signature == repository_whose_commit_is_mutated`.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/secret to verify the incoming signature against using the `repository.owner.login` (or `organization.login`) fields taken directly from the JSON payload: [1](#0-0) [2](#0-1) 

Once the signature is validated against that organization's `webhook_secret` (per-org config in `lib/shipit/github_app.rb` / `lib/shipit.rb#github_app_config`), the parsed params are dispatched to handlers: [3](#0-2) 

Most handlers correctly re-scope by the signed payload's `repository.full_name` before acting (see the base `Handler#stacks`, used e.g. by `PushHandler`): [4](#0-3) [5](#0-4) 

However, `StatusHandler#process` never consults `repository.full_name`/owner at all — it looks up commits **globally by SHA** across the entire Shipit installation and applies the status update to every matching commit, regardless of which repository (and thus which organization/webhook secret) was used to authenticate the request: [6](#0-5) 

Because git commit SHAs are content hashes that are typically public (visible via GitHub UI, PR links, CI logs, etc.) and are frequently shared across forks/mirrors or even collide with commits tracked under a different Shipit-managed repository (e.g., a monorepo split into multiple Shipit stacks, or an org that mirrors another org's history), an attacker who can produce a validly-signed `status` webhook for *some* repository/organization configured in Shipit (i.e., they control a repo where the GitHub App/webhook is installed and can trigger commit-status API calls, or otherwise learn/replay a valid signature for their own org) can supply an arbitrary `sha` that actually belongs to a commit tracked under a *different* Shipit stack/repository/organization. `StatusHandler` will happily create/update that commit's status even though the authenticating signature never proved anything about that other repository or organization.

This is structurally analogous to the reported StableMath issue: the "verified" quantity (organization identity proven by the HMAC) and the quantity actually acted upon (the specific repository's commit whose status is mutated) are computed/selected independently, and the code never asserts they are the same value, allowing the check to be satisfied while the effect lands somewhere the check never covered.

### Impact Explanation
Commit statuses drive Shipit's deploy-gating logic (`deployable_status`, `commit_status` are both webhook events and stack status inputs). Being able to forge a passing (or failing) status for a commit belonging to a repository/stack you do not control is a cross-repository write into another team's commit-status/CI state, and can be used to make an otherwise-blocked commit appear deployable (an unauthorized deploy precondition) in a stack you have no legitimate access to. This matches the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Exploitation requires only the ability to produce one validly-signed `status` webhook event for *any* organization/app configured in the Shipit instance (a bar most legitimate CI systems or App installations meet routinely), plus knowledge of a target SHA belonging to a different tracked repository — SHAs are not secrets. No repository write access, Shipit session, or `ApiClient` token to the *target* stack is required, only the ability to trigger (or replay) a `status` event for *some* configured repository. This is a plausible, medium-to-high likelihood path in any multi-organization/multi-repository Shipit deployment.

### Recommendation
In `StatusHandler#process`, scope the `Commit.where(sha: params.sha)` lookup to commits whose `stack.repository.full_name` matches `payload.dig('repository', 'full_name')` (the same field the signature covers), mirroring the pattern already used by `Handler#stacks`/`PushHandler`. More generally, every handler should assert that the record it mutates belongs to the repository named in the same signed payload used for authentication, not merely look up state by loosely-scoped attributes like a bare SHA.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own GitHub App/webhook secret (multi-org config in `config/secrets.yml`), and tracks a stack for `org-a/repo1` and a stack for `org-b/repo2`.
2. Attacker has legitimate ability to trigger a `status` webhook for `org-a/repo1` (e.g., they operate a CI integration installed there) and knows/observes a commit SHA `S` that is also tracked under `org-b/repo2`'s stack (e.g., a shared vendored commit, monorepo split, or mirrored history).
3. Attacker sends a `status` event with `repository.owner.login = "org-a"`, `sha = S`, `state = "success"`, correctly signed with `org-a`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature against `org-a`'s secret and passes.
5. `StatusHandler#process` executes `Commit.where(sha: S)`, which matches the commit under `org-b/repo2`, and calls `create_status_from_github!` on it — updating `org-b`'s commit status despite the request only ever being authenticated for `org-a`.
