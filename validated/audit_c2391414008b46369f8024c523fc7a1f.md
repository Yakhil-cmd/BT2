### Title
Cross-organization webhook `status` events are applied to any commit by SHA, bypassing the per-organization signature scope - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook by looking up the GitHub App/`webhook_secret` for the **organization named in the payload's `repository.owner.login`** and HMAC-verifying the raw body against it [1](#0-0) . Shipit explicitly supports multiple independent GitHub organizations, each with its own App and `webhook_secret`, configured side by side in `secrets.yml` [2](#0-1) . However, `StatusHandler#process`, which runs after this per-organization signature check, never re-checks the organization/repository the event was authenticated for — it looks up commits **globally by SHA alone**: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Unlike other handlers (`PushHandler`, `CheckSuiteHandler`, the `PullRequest` handlers), which scope their effect through `stacks`/`repository`, derived from `payload.dig('repository','full_name')` via `Handler#stacks`/`Handler#repository_name` [4](#0-3) , `StatusHandler` performs no such scoping at all.

### Finding Description
This breaks exactly the trust binding called out in the target bug class: **the organization whose credential authenticated the request ≠ the repository/stack that is actually written to.**

- `verify_signature` picks the signing secret using `repository_owner` from the payload and confirms only that *some* org known to this Shipit instance signed *this specific payload* [5](#0-4) .
- That verification says nothing about which `Commit`/`Stack` the event is allowed to affect — the payload's `repository` field is completely ignored by `StatusHandler`.
- `Commit#create_status_from_github!` writes an actual `Status` record and recomputes `Commit#status` via `add_status`, which fires `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` [6](#0-5) .
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, i.e. the injected status directly feeds `success?` and thus deploy eligibility / continuous delivery gating (`schedule_continuous_delivery`) [7](#0-6) [8](#0-7) .

So any organization that Shipit trusts enough to have a registered GitHub App/`webhook_secret` — even one that owns only unrelated, low-value repositories — can forge a `status` webhook (signed with its own legitimate secret) whose `sha` field names a commit that belongs to a completely different organization's stack, and flip that commit's CI status to `success`, unlocking deploy/continuous-delivery gating it should never have controlled. This is analogous to the escrow bug: the entity that is cryptographically "approved" (org A's webhook secret) is allowed to write state (`Status` rows / commit deployability) scoped to org B's resource, because the code never re-derives or checks the repository/stack binding after authentication.

### Impact Explanation
This crosses the "unauthorized deploy" impact bar: forging a passing CI status on someone else's tracked commit can make that commit `deployable?` and, if `continuous_deployment` is enabled on that stack, trigger `ContinuousDeliveryJob`/`schedule_continuous_delivery` automatically — i.e. an org that never had write access to the victim's repository can cause an unauthorized deploy or unlock deploy safety checks for an already-queued deploy on a stack it does not own.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (documented, supported configuration) and requires the attacker to control (or be able to trigger a genuine signed webhook from) at least one such organization — plausible in shared multi-tenant Shipit deployments where organizations differ in trust level. The attacker additionally needs the target SHA to be a commit reachable/settable within a repo they can post a status to (e.g., via a fork containing the same commit history), which is a real but non-trivial extra step; I was not able to fully verify GitHub's exact SHA-existence constraints for the Statuses API from within this codebase, so likelihood should be treated as moderate rather than certain.

### Recommendation
`StatusHandler` (and any other handler that does not currently scope by `stacks`) must resolve the target commit only within stacks belonging to the `repository.full_name`/organization that the signature was verified for, mirroring the pattern already used in `Handler#stacks` (i.e. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or equivalent), rather than querying `Commit` globally by SHA.

### Proof of Concept
1. Configure Shipit with two organizations, `trusted-org` (victim, has a tracked `Stack`/`Commit` with SHA `abc123`) and `low-trust-org` (attacker-controlled, also registered with its own GitHub App + `webhook_secret`), per the documented multi-org setup [2](#0-1) .
2. As an admin/CI integrator of `low-trust-org`, arrange for a `status` event to be sent to `/webhooks` whose JSON body has `repository.owner.login = "low-trust-org"` (so `verify_signature` selects and validates against `low-trust-org`'s real `webhook_secret` [9](#0-8) ) but `sha = "abc123"` and `state = "success"` (the victim commit's SHA, obtainable e.g. via a fork of the victim's public repo).
3. The signature check passes because it only validates that `low-trust-org` signed this payload — it never checks that the SHA in the payload actually belongs to a commit under `low-trust-org`.
4. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, which matches the victim's commit under `trusted-org`'s stack, and calls `commit.create_status_from_github!(params)`, marking it `success` [3](#0-2) .
5. `Commit#deployable?` now returns true for that commit; if the victim stack has `continuous_deployment: true`, `schedule_continuous_delivery` enqueues a deploy of attacker-influenced status data on infrastructure the attacker never had access to [10](#0-9) .

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
