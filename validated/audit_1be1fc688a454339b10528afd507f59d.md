### Title
Webhook signature is validated against `repository.owner.login` while the mutated stack is resolved from `repository.full_name` — cross-repository forced sync - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) using `repository_owner` (`payload.dig('repository','owner','login')`), but `Webhooks::Handlers::Handler#repository_name` (used by `PushHandler`) resolves the target `Stack` using `payload.dig('repository','full_name')`. Because these two payload fields are attacker-controlled and independent, an attacker who owns an org with a GitHub App installed but no `webhook_secret` configured can forge a `push` event that "verifies" under their own (secret-less) org while mutating a stack belonging to a completely different, unrelated repository/org.

### Finding Description
The broken binding: `Shipit.github(organization: payload.dig('repository','owner','login')).verify_webhook_signature(...)` should establish trust for `payload.dig('repository','full_name')`, i.e. the invariant should be `repository_owner == owner(repository.full_name)`. This is never checked.

Code path:
- `WebhooksController#verify_signature` [1](#0-0)  picks the `GitHubApp` via `repository_owner`, which is defined as `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank [3](#0-2) .
- On success, `WebhooksController#create` re-parses the raw body and dispatches to registered handlers for the event [4](#0-3) .
- `PushHandler#process` resolves the target stacks via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)`, where `repository_name` is `payload.dig('repository','full_name')` — a completely separate payload field from the one used for signature-org selection [5](#0-4) .
- It then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack whose branch matches [6](#0-5) .

Attacker's request: `POST /webhooks` with `X-Github-Event: push`, no valid `X-Hub-Signature`, and body `{'repository':{'owner':{'login':'attacker-org'},'full_name':'victim-org/prod-stack'},'ref':'refs/heads/master','after':'<attacker_sha>'}`. Since `attacker-org` is a real, configured GitHub App organization in `Shipit.github_apps` but has no `webhook_secret` set (a realistic misconfiguration for orgs onboarded without webhook signing configured, or any org where the operator simply forgot to set it), `verify_webhook_signature` returns `true` for any signature (or none). The controller then proceeds to `create`, and `PushHandler` resolves `victim-org/prod-stack` purely from `full_name`, forcing that unrelated stack to sync/deploy the attacker's chosen SHA.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type is registered [7](#0-6) ; `verify_signature` never cross-checks that the verifying org matches the owner embedded in `full_name`; there is no `ExplicitParameters` validation tying `repository.owner.login` to `repository.full_name`'s owner segment.

### Impact Explanation
A payload "verified" (trivially, due to no secret) under one organization's identity is used to look up and mutate a `Stack` belonging to an entirely different organization/repository, matching the Critical category "a payload for one repository mutating another's stack." The attacker can force `victim-org/prod-stack`'s `master` branch to sync to an arbitrary attacker-chosen SHA (`stack.sync_github(expected_head_sha:)`), which can trigger downstream deploy behavior depending on `continuous_delivery_schedule`/`auto-merge` settings. This is repeatable against any victim stack whose full name the attacker knows, at will, with zero authentication into Shipit, from any organization the attacker controls that happens to have a GitHub App installed but no webhook secret set — cross-tenant blast radius limited only by which orgs are configured that way.

### Likelihood Explanation
Preconditions: attacker must control (own) an org with a GitHub App installed in Shipit's `Shipit.github_apps` config, and that org's config entry must be missing `webhook_secret`. This is plausible/realistic in multi-org Shipit deployments where operators add new orgs' GitHub Apps but forget to configure the webhook secret for each — the code has no fallback requiring a secret to exist. Given that precondition, the attack is trivial: one crafted HTTP POST, no authentication, fully repeatable and scriptable against any victim repository whose full name is known (repository full names are typically public/discoverable).

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), enforce that the organization used to verify the signature matches the owner segment of `repository.full_name` (i.e., reject if `repository_owner != payload.dig('repository','full_name').split('/').first`). Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when no secret is configured for an org that is expected to sign webhooks — either require all configured GitHub Apps to have a `webhook_secret`, or refuse any push/status webhook whose target repository owner doesn't match a properly-secreted app.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
```ruby
test "push payload cannot use one org's (secret-less) signature verification to sync another org's stack" do
  victim_stack = shipit_stacks(:shipit) # belongs to e.g. "shopify/shipit-engine"
  attacker_app = Shipit::GitHubApp.new('attacker-org', { app_id: 1, installation_id: 1, private_key: 'x' }) # no webhook_secret
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(attacker_app)

  forged_sha = 'a' * 40
  body = {
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => victim_stack.github_repo_name },
    'ref' => 'refs/heads/master',
    'after' => forged_sha
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  # no X-Hub-Signature header at all

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: forged_sha)

  post :create, body:, as: :json
  assert_response :ok
end
```
Both sides of the equality (`repository_owner` = `'attacker-org'` vs. owner implied by `repository.full_name` = victim org) diverge before the fix, and `sync_github` is invoked on the victim's stack — demonstrating the vulnerability without any live GitHub calls.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
