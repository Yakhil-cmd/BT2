`TransferAllFungibles`/`TransferAllAssets` is an external trait implementation from the `pallet-bounties`/`pallet-multi-asset-bounties` crates and is not vendored in this repo, so I cannot verify its internal partial-failure semantics beyond what's documented in this codebase's call sites.

### Title
Silently-ignored partial failure in `MigrateBountyAccountAssets` can permanently strand bounty funds at the old sub-account derivation - (File: `system-parachains/asset-hubs/asset-hub-kusama/src/migrations.rs`, `system-parachains/asset-hubs/asset-hub-polkadot/src/migrations.rs`)

### Summary
`MigrateBountyAccountAssets::on_runtime_upgrade` sweeps every listed asset from each bounty's old (`&str`-derived) pot account to the new (`[u8;3]`-derived) account, but discards the result of the transfer with `let _ = Transferer::force_transfer_all_assets(&old, &new);`. This is the same failure pattern as the Sherlock `updateYieldStrategy` bug: an operation that is not guaranteed to move 100% of the funds is treated as if it always succeeds, and the system unconditionally proceeds to the new state (pointing exclusively at the new derivation), leaving the old account orphaned.

### Finding Description
The migration iterates all bounties/child-bounties and calls: [1](#0-0) [2](#0-1) 

The transfer's `Result` is explicitly discarded (`let _ = ...`), so if any asset transfer fails for a given bounty — e.g. an asset is non-sufficient and the old account can't be reaped, a hold/freeze exists, or the reducible balance computation leaves a remainder — the migration continues and reports success (weight is still charged/consumed) with no on-chain error or event indicating the shortfall. This is architecturally identical to `Sherlock.updateYieldStrategy` calling `yieldStrategy.withdrawAll()` and then unconditionally switching the active strategy regardless of whether the withdrawal actually emptied the old strategy: the "old" location (old strategy / old sub-account derivation) becomes unreachable to normal pallet logic once the migration/switch is treated as complete, because after the upgrade `pallet-multi-asset-bounties` only ever computes and uses the new (`[u8;3]`-derived) address.

### Impact Explanation
If any bounty's assets are not fully swept (partial transfer failure), the residual balance is permanently stranded at the old `("mbt", bounty_id)` / `("mcb", parent_id, child_id)` derived account. This is a single-block, non-repeatable `OnRuntimeUpgrade` migration — it only runs once at the version bump — so there is no automatic retry. Recovering the funds would require a follow-up governance-authorized runtime migration or manual root-origin transfer, exactly mirroring the "back-and-forth switches" remediation described in the Sherlock report.

### Likelihood Explanation
The docstring itself acknowledges this is "not theoretical": Kusama referenda are expected to fund multi-asset bounties (some in DOT, some in USDT) shortly before this runtime ships, meaning nonzero bounty balances are expected to exist at migration time. Whether the underlying `TransferAllFungibles`/`force_transfer_all_assets` implementation can genuinely leave a remainder (e.g. due to non-sufficient asset semantics, insufficient existential deposit for account creation and `Preservation::Expendable`, or holds) can't be confirmed from this repo since the trait implementation lives in the external `pallet-bounties`/`pallet-multi-asset-bounties` crates, which are not part of this codebase's indexed contents. This uncertainty is analogous to the original report's dependency on the external lending-market liquidity for `withdrawAll`.

### Recommendation
- Do not discard the transfer result. Track (or emit an event for) any bounty/child-bounty whose old-account balance is not fully zero after the sweep.
- Consider using `try_state`/post-upgrade checks (already used elsewhere in this migrations module) to assert the old accounts are drained to at most existential-deposit-level residue, failing/logging loudly otherwise.
- Keep the ability to re-run a targeted sweep (e.g. via a signed extrinsic, similar to `pallet_ah_ops::transfer_to_post_migration_treasury`) for any account identified as incompletely migrated, rather than relying solely on the one-shot `OnRuntimeUpgrade` hook.

### Proof of Concept
Verification of an actual partial-failure trigger requires inspecting the `TransferAllFungibles`/`pallet_bounties::TransferAllAssets` implementation, which is not present in this repository's indexed files (it is defined in the external `pallet-bounties` crate). Based solely on this repo's code, the exploitable condition is structural: the discarded `Result` at [3](#0-2) [4](#0-3) 
means any transfer failure (of any cause, on any of the listed `BountyMigrationAssets`/`BountyRelevantAssets`) is unconditionally treated as a successful migration to the new derivation, with no event, no re-check, and no retry path — the same root cause class as `updateYieldStrategy` unconditionally removing the old strategy after an unverified `withdrawAll`.
