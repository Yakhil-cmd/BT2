### Title
Unverified `creator` Identity in `initialize_with_permission` Allows Spoofed `pool_creator` Binding - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`InitializeWithPermission` accepts a `creator` account that is a completely unconstrained `UncheckedAccount` — it is neither a `Signer`, nor tied by any `address`/`constraint` check to the `payer` or to the `permission` PDA that gates who may call the instruction. Whatever pubkey the caller supplies for `creator` is written verbatim into the permanent `PoolState.pool_creator` field, which is later treated as the authoritative, privileged identity for creator-fee collection.

### Finding Description
In `initialize.rs`, the permissionless `initialize` instruction binds `pool_creator` to the transaction signer directly (`creator: Signer<'info>`), so the recorded identity is cryptographically authenticated. [1](#0-0) 

In `initialize_with_permission.rs`, however, `creator` is declared as an `UncheckedAccount` with no signer requirement, no `address =` constraint, and no `constraint =` linking it to `payer` or to the `permission` PDA: [2](#0-1) 

The `permission` account used to gate this instruction is derived only from `payer`, not from `creator`: [3](#0-2) 

Yet the caller-supplied, unauthenticated `creator.key()` is what gets permanently persisted as `pool_creator` in `PoolState`: [4](#0-3) [5](#0-4) 

This `pool_creator` field is subsequently treated as a trusted, privileged identity: it is the only account authorized to sign for `collect_creator_fee` (`address = pool_state.load()?.pool_creator` on a `Signer`), and it is the mandatory fee-recipient address in the permissionless variant, `collect_creator_fee_permissionless`. [6](#0-5) [7](#0-6) 

This is the same bug class as the reported libp2p-secio issue: a claimed identity (`DstPeer` / here, `creator`) is written into trusted state without cross-checking it against a cryptographically verified identity (the handshake pubkey / here, the transaction signer `payer` that actually holds the `permission` PDA). Any account holding a valid `Permission` PDA can call `initialize_with_permission` and bind an arbitrary, attacker-chosen `creator` pubkey — including addresses under the attacker's exclusive control that have no relationship to `payer` — as the pool's permanent `pool_creator`.

### Impact Explanation
Because `pool_creator` is the sole gate for `collect_creator_fee`'s signer check and the fixed destination in `collect_creator_fee_permissionless`, an attacker who legitimately holds a `permission` PDA (i.e., is authorized to launch a pool) can bind an arbitrary, unauthenticated address as the perpetual recipient of all accumulated creator fees for that pool, without that address ever proving control or consent. This breaks the intended access-control invariant that `pool_creator` represents a verified identity tied to the party that actually created/funded the pool (as enforced in the un-permissioned `initialize` path via `Signer`). It results in an unauthorized privileged binding baked permanently into on-chain state and misdirected fee-ledger accounting for the life of the pool, since `pool_creator` cannot later be corrected.

### Likelihood Explanation
Reachable by any single transaction from an unprivileged (but permission-holding) pool creator with fully attacker-chosen instruction data for the `creator` account — no elevated Solana-runtime privilege, off-chain component, or non-default feature is required. The only precondition is holding a valid `Permission` PDA, which is the normal, expected precondition for calling this instruction at all; the flaw is that the identity check that should additionally validate `creator` is entirely absent.

### Recommendation
Constrain `creator` in `InitializeWithPermission` the same way `initialize.rs` constrains it: either require `creator` to be a `Signer`, or add an explicit `constraint = creator.key() == payer.key()` (or a documented, verifiable relationship to the `permission` PDA) so the value written into `PoolState.pool_creator` is always tied to a cryptographically authenticated party rather than arbitrary caller-supplied data.

### Proof of Concept
1. Attacker (or any account) obtains a `Permission` PDA for `payer = attacker_key` via `create_permission_pda`.
2. Attacker calls `initialize_with_permission`, supplying `payer = attacker_key` (signs) and `creator = arbitrary_pubkey` (any key, not a signer, unrelated to `attacker_key`).
3. Anchor account validation passes because `creator` has zero constraints; `pool_state.initialize(..., ctx.accounts.creator.key(), ...)` writes `arbitrary_pubkey` into `PoolState.pool_creator`. [8](#0-7) 
4. As swaps occur, `creator_fees_token_0/1` accumulate in `PoolState`, and only `arbitrary_pubkey` (via `collect_creator_fee`, requiring its signature) or a permissionless caller sending funds to `arbitrary_pubkey` (via `collect_creator_fee_permissionless`) can claim them — permanently and by design of the attacker, with no verification that `arbitrary_pubkey` ever authorized or participated in the pool creation.
