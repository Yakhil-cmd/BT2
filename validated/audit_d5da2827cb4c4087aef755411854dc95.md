### Title
Last-Vote-Wins Ratification in `none` Mode Allows Single GC Member to Unilaterally Redirect KAIA Block Reward Distribution — (`kaiax/gov/headergov/impl/header.go`)

---

### Summary

In `none` governance mode, `getExpectedGovernance` ratifies whichever vote was cast **last** in an epoch for each parameter, with no quorum, no majority, and no time-weighting. Any GC member who is the last block proposer in an epoch can unilaterally ratify a change to `reward.ratio`, `reward.mintingamount`, or `reward.kip82ratio`, permanently redirecting KAIA block rewards for the next epoch.

---

### Finding Description

`getExpectedGovernance` collects all votes from the previous epoch, sorts them by block number, and iterates through them — the last vote for each parameter name overwrites all earlier ones:

```go
// kaiax/gov/headergov/impl/header.go:218-233
func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
    prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
    prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
    govs := make(gov.PartialParamSet)

    sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
    slices.Sort(sortedVoteBlocks)

    for _, voteBlock := range sortedVoteBlocks {
        vote := prevEpochVotes[voteBlock]
        govs.Add(string(vote.Name()), vote.Value())  // last write wins
    }
    return headergov.NewGovData(govs)
}

The documentation confirms this is the intended behavior for `none` mode:

> `none` mode: all members of the GC can vote. For each governance parameter, **the last vote in the epoch will be ratified**. [3](#0-2) 

The default governance mode is `none`:

```go

`GovernanceGovernanceMode` is in `AlwaysDeprecated`, meaning once a chain is deployed with `none` mode it cannot be changed via governance vote: [5](#0-4) 

The parameters that can be changed this way include `reward.ratio`, `reward.mintingamount`, and `reward.kip82ratio`, all of which directly control KAIA block reward distribution: [6](#0-5) 

`NewRewardConfig` reads these parameters at block finalization time and uses them to compute the actual KAIA amounts distributed to proposer, stakers, KIF, and KEF: [7](#0-6) 

---

### Impact Explanation

A GC member on a `none`-mode chain who is the last block proposer in an epoch can:

1. Vote `reward.ratio = "100/0/0"` — redirects 100% of minted KAIA to validators, zeroing KIF and KEF fund allocations permanently for the next epoch.
2. Vote `reward.mintingamount = "0"` — stops all KAIA inflation for the next epoch.
3. Vote `reward.kip82ratio = "100/0"` — redirects all staker rewards to the proposer.

The corrupted value is the `reward.ratio` / `reward.mintingamount` / `reward.kip82ratio` stored in the ratified `header.Governance` field of the epoch block, which then drives `NewRewardConfig` → `getDeferredRewardFullKore` / `getDeferredRewardFullFlex` for every block in the following epoch, causing incorrect KAIA amounts to be minted and distributed to wrong addresses. [8](#0-7) 

---

### Likelihood Explanation

- Requires the attacker to be a GC council member (semi-trusted, not fully privileged).
- Requires the attacker's node to be the last proposer in an epoch for the target parameter.
- In `WeightedRandom` policy, the proposer list is pre-generated per interval; an attacker can observe the schedule and time their vote to be the last one in the epoch.
- The default governance mode is `none`, so any chain deployed without explicitly setting `single` mode is affected.
- Mainnet and Kairos use `single` mode and are not affected, but any chain using the default `none` mode is vulnerable.

---

### Recommendation

1. In `none` mode, require a **majority** (e.g., `> N/2`) of distinct council members to have voted for the same value before ratifying a parameter change, rather than ratifying the last vote.
2. Alternatively, implement a time-weighted vote accumulation: votes cast earlier in the epoch carry equal weight to later votes, and the winning value is determined by vote count, not recency.
3. Document clearly that `none` mode provides no protection against a single last-proposer override, and recommend against deploying production chains with `none` mode.

---

### Proof of Concept

Given a chain with `governance.governancemode = "none"`, `epoch = 604800`, and 4 GC members A, B, C, D:

1. At block `k*epoch + 1`, member A votes `reward.ratio = "34/54/12"` (current value, benign).
2. At block `k*epoch + 2`, member B votes `reward.ratio = "34/54/12"`.
3. At block `k*epoch + 3`, member C votes `reward.ratio = "34/54/12"`.
4. At block `k*epoch + 604799` (last block of epoch), member D (attacker) votes `reward.ratio = "100/0/0"`.

At block `(k+1)*epoch`, `getExpectedGovernance` iterates votes sorted by block number. D's vote at block `k*epoch + 604799` is last, so `govs["reward.ratio"] = "100/0/0"` overwrites all earlier votes. The epoch block's `header.Governance` is set to `{"reward.ratio": "100/0/0"}`.

From block `(k+1)*epoch` onward, `NewRewardConfig` reads `reward.ratio = "100/0/0"`, and `getDeferredRewardFullKore` distributes 100% of minted KAIA to validators, with 0 to KIF and 0 to KEF, for the entire next epoch (~604800 blocks × minting amount KAIA per block diverted from system funds). // getDeferredRewardFullKore is for non-Simple policy and after Kore.
func getDeferredRewardFullKore(config *reward.RewardConfig, execFee, burntFee, blobFee *big.Int, si *staking.StakingInfo) (*reward.RewardSpec, error) {
	var (
		spec             = reward.NewRewardSpec()
		minted           = new(big.Int).Set(config.MintingAmount)
		distributableFee = new(big.Int).Sub(execFee, burntFee)
	)

	// Distribute using RewardRatio first. Unlike Legacy, fees are not distributed here
	// because fees are exclusively allocated to proposer. By the way, remainder goes to KIF.
	validators, kif, kef := config.RewardRatio.Split(minted)
	proposer, stakers := config.Kip82Ratio.Split(validators)
	ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
	kif.Add(kif, ratioRemainder)

	// Further distribute using Kip82Ratio. By the way, remainder goes to proposer.
	// After Prague, if the CLStaking is not nil, the proposer and staking rewards are proportionally distributed to both CN and CL.
	// For proposer rewards, see `specWithProposerAndFunds`.
	stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
	proposer.Add(proposer, kip82Remainder)
	stakers.Sub(stakers, kip82Remainder)

	// Proposer gets the fees.
	proposer.Add(proposer, distributableFee)

	spec.Minted = minted
	spec.TotalFee = new(big.Int).Add(execFee, blobFee)
	spec.BurntFee = new(big.Int).Add(burntFee, blobFee)
	spec.Stakers = stakers
	for addr, amount := range stakersAlloc {
		spec.IncRecipient(addr, amount)
	}
	spec = specWithProposerAndFunds(spec, config, proposer, kif, kef, si)
	return spec, nil
}
