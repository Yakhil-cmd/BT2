### Title
Stack-Scoped API Token Can Read Any Stack's CI Status via CCMenu Endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides both the authentication and stack-lookup helpers inherited from `Shipit::Api::BaseController`, and in doing so it drops the stack-scoping enforcement that the base controller normally applies to `ApiClient` tokens restricted to a single stack.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the tokens's authorized stack: [1](#0-0) 

An `ApiClient` can optionally be bound to a single stack (`belongs_to :stack, optional: true`), and `check_permissions!` only checks the client's `permissions` array — it never checks whether the requested stack matches `current_api_client.stack_id`: [2](#0-1) 

The stack-scoping binding (`current_api_client.stack_id? → Stack.where(id: stack_id)`) is what enforces "the stack a token authorises" equals "the stack a token touches" for every other API controller (`DeploysController`, `RollbacksController`, `TasksController`, `HooksController`, `StacksController`, `MergeRequestsController`, `OutputsController` all inherit `stack`/`stacks` unchanged from `BaseController`).

`CCMenuController`, however, redefines both `authenticate_api_client` (to accept a `token` query-string parameter instead of Basic Auth) and `stack` (to do a raw, unscoped lookup): [3](#0-2) 

Because `stack` is overridden to call `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, the `current_api_client.stack_id` restriction from `BaseController#stacks` is never applied. The `require_permission :read, :stack` before_action only verifies that `read:stack` is present in the client's `permissions` list — it does not verify the requested stack belongs to that client: [4](#0-3) [5](#0-4) 

Equality that should hold but is broken:
`stack authorised by the ApiClient (current_api_client.stack_id)` == `stack whose CI/deploy state is served by CCMenuController#show`

Before the request: a stack-scoped `ApiClient` with `read:stack` can only read state for its bound stack via every other endpoint (they use `stacks.from_param!`).
After a crafted request to `GET /:stack_id/ccmenu.xml?token=<scoped-token>` for a *different* `stack_id`, the controller happily renders that other stack's deploy/CI status — the binding is broken.

### Impact Explanation
This allows a client holding a token scoped to Stack A to read the deploy status, last build result, and activity of any other stack in the Shipit instance, including private/internal stacks the token was never meant to see. This matches the "High" impact category: unauthenticated (out-of-scope) read of stack state via a token that is not authorized for that stack — a genuine authorization-scoping bypass, not merely a permission check bypass.

### Likelihood Explanation
Likelihood is straightforward for anyone who already possesses a legitimately-issued, stack-scoped `ApiClient` token with `read:stack` permission (e.g., a CI status badge/token meant only for their own stack). No additional secrets, session, or privileged access is required beyond the token itself; only the `stack_id` path segment needs to be changed to target another stack.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` reuse the scoped `stacks` collection from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that the `current_api_client.stack_id` restriction is enforced consistently with every other API controller.

### Proof of Concept
1. Create an `ApiClient` bound to Stack A (`stack_id` set) with `permissions: ['read:stack']`.
2. Obtain its `authentication_token`.
3. Issue `GET /api/<owner>/<repoB>/<env>/ccmenu.xml?token=<tokenA>` for Stack B (a different, unrelated stack).
4. Because `CCMenuController#stack` bypasses the `stacks` scoping used elsewhere, the request succeeds and returns Stack B's CI/deploy XML, even though the token is only supposed to authorize access to Stack A.

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end
