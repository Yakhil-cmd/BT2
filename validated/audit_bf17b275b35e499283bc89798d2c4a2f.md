### Title
Pull request labels are used to set arbitrary git subprocess environment variables (including `GIT_SSH_COMMAND`) - ([File: app/models/shipit/review_stack.rb], [File: lib/shipit/command.rb])

### Summary
`ReviewStack#env` converts every GitHub PR label into an environment variable (`LABEL.upcase => "true"`) with no allowlist/blocklist, and this hash flows unfiltered through `StackCommands#env`/`TaskCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn` for `git fetch`/`git clone`. A pull request labeled `git_ssh_command` therefore injects `GIT_SSH_COMMAND=true` into the git subprocess environment.

### Finding Description
Binding as claimed: `Command#start` passes to git subprocesses the env keys from `Shipit::Commands#base_env` ∪ `deploy_spec.machine_env`. This binding is **false** once a stack has an associated `PullRequest`, because `ReviewStack#env` adds a third, unfiltered source: [1](#0-0) 

- `pull_request.labels` is populated directly from the GitHub webhook payload's label names, with no filtering of the name string: [2](#0-1)  and [3](#0-2) .
- `StackCommands#env` calls `@stack.env`, which for a `ReviewStack` resolves to the overridden method that merges in the label-derived hash: [4](#0-3) .
- `StackCommands#fetch_commit`/`#fetch`/`#clone` pass this merged `env:` straight into `git(...)`, which builds a `Command` with that exact hash: [5](#0-4)  and [6](#0-5) .
- `Command#start` merges this `@env` on top of `BASE_ENV`/`PATH` and hands it directly to `PTY.spawn`: [7](#0-6) .

Nothing in the chain strips transport-related keys. `base_env` only sets `GITHUB_DOMAIN`, `GITHUB_TOKEN`, and optionally `GIT_ASKPASS`: [8](#0-7) . `deploy_spec.machine_env` is operator-authored YAML, unrelated to PR labels: [9](#0-8) . The webhook path is not a forgery: GitHub itself signs and delivers the `pull_request` `labeled` event using the org's real `webhook_secret`, verified normally by `WebhooksController#verify_signature` / `GithubApp#verify_webhook_signature`: [10](#0-9) . That check confirms the event genuinely originates from GitHub for that repository/org — it does not, and cannot, constrain what a PR author names their own label. The vulnerability is a data-sanitization gap (untrusted PR metadata used verbatim as env var names/keys) rather than a signature-verification bypass.

Repo URLs Shipit uses are HTTPS (`https://#{domain}/#{owner}/#{name}.git`, `app/models/shipit/repository.rb:78-80`), so `GIT_SSH_COMMAND` alone would not be invoked for the default clone/fetch transport in a stock Shopify-hosted config. However: (a) `git_url`/`repo_git_url` is configurable per deployment and installations using SSH remotes are a realistic and supported configuration, and (b) the same mechanism lets a label set any environment variable name (e.g., `GIT_ASKPASS`, `GIT_PROXY_COMMAND`, `GIT_EXTERNAL_DIFF`, `BUNDLE_GEMFILE`, `RUBYOPT`, etc.) that later `git`/task steps read, materially widening the injection beyond just SSH transport override. The `GIT_SSH_COMMAND` test case is the sharpest demonstration but the root defect is broader: any PR label becomes an unsanitized environment variable fed into a `PTY.spawn`'d process.

### Impact Explanation
An attacker who can label a pull request against a tracked repository's review stack can inject arbitrary environment variable names/values (capped to `"true"` string values, uppercase key) into every `git fetch`/`git clone`/task-step subprocess run for that stack. Depending on host configuration (SSH remotes, custom deploy/task scripts reading env vars, `GIT_ASKPASS`/proxy/diff hooks), this can escalate to command execution on the deploy host for that stack — Critical impact (RCE via `Command`/`PTY.spawn`) under the stated impact categories. The blast radius is scoped to the review stack/repository whose PR is labeled; it does not cross-mutate other tenants' stacks directly, but it does affect any deploy host process that shares subprocess execution for that stack (fetch, clone, dependency install, task steps via `TaskCommands#env`).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled and an active `ReviewStack`/`PullRequest` record; the label-setting actor must have permission to add labels on the PR (GitHub normally requires triage/write access for label mutation, which the audit's threat model explicitly grants to the attacker). No secrets, tokens, or privileged Shipit roles are required — the webhook signature check passes because GitHub genuinely signs the real `labeled` event. This is trivially repeatable (relabel/unlabel) against any repository with review stacks enabled where the attacker has label permission.

### Recommendation
Do not let raw PR label text become raw environment variable keys handed to subprocess execution. Concretely, in `app/models/shipit/review_stack.rb#env`, restrict label-derived keys to an explicit allowlist (e.g., only labels matching a safe prefix/pattern that excludes known-sensitive names), or namespace them (e.g., `LABEL_<NAME>`) so they can never collide with transport-sensitive variable names like `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `GIT_PROXY_COMMAND`, `LD_PRELOAD`, `BUNDLE_*`, `RUBYOPT`, `PATH`, etc. Additionally, `Command#unbundled_env`/`#start` should filter out or refuse to override a documented deny-list of transport/interpreter environment variables regardless of source.

### Proof of Concept
```ruby
# test/lib/shipit/stack_commands_test.rb (conceptual addition)
require "test_helper"

class StackCommandsGitSshCommandInjectionTest < ActiveSupport::TestCase
  test "PR label can inject GIT_SSH_COMMAND into git fetch/clone env" do
    stack = shipit_stacks(:review_stack)
    stack.pull_request.labels = ['git_ssh_command']

    command = StackCommands.new(stack).fetch_commit(stack.commits.last)

    assert_equal 'true', command.env['GIT_SSH_COMMAND']
  end
end
```
This demonstrates the equality claimed in the question (`fetch_commit(commit).env['GIT_SSH_COMMAND'] == 'true'`) holds, confirming the label-derived key propagates unfiltered from `ReviewStack#env` through `StackCommands#env` into the `Command` instance ultimately passed to `PTY.spawn`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
