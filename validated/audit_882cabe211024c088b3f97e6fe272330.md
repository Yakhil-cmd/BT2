### Title
Webhook organization confusion allows forging events for another organization's repository when any configured GitHub App has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from an **attacker-controlled field inside the very payload being verified**, while the webhook handlers act on a **different, also attacker-controlled field** (`repository.full_name` / commit `sha`) to decide which `Stack`/`Commit` gets mutated. If any organization configured in `Shipit.github` has a blank `webhook_secret` (a supported, documented configuration), signature verification for that organization becomes a no-op, letting an attacker forge events for a completely different organization's tracked repository.

### Finding Description
`verify_signature` derives the org used for verification purely from the JSON body, before the body has been authenticated: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')` — both fully attacker-controlled fields of the unverified raw POST body.

`Shipit.github(organization: repository_owner)` then returns the `GithubApp` configured for that name, and `GithubApp#verify_webhook_signature` is a **trivial pass** whenever that org's `webhook_secret` is not configured: [3](#0-2) 

`webhook_secret` being blank is a normal, documented state: multi-org configuration examples ship with `webhook_secret: # nil` per organization, and `docs/setup.md` describes setting a webhook secret as something you do only "if you've set a webhook secret during the App creation" (i.e., optional), see the same placeholder pattern reused across configs: [4](#0-3) [5](#0-4) 

Once `verified` is trivially `true` for that secret-less org, the controller dispatches the same untrusted body to handlers, which trust an **independent** field, `repository.full_name` (or commit `sha`), to locate and mutate records for *any* tracked stack — not just stacks belonging to the org that was actually "verified": [6](#0-5) [7](#0-6) 

The security-relevant equality this breaks is:
`organization whose credential (webhook_secret) authenticated the request` **should equal** `organization/repository whose Stack/Commit data is written by the handler` — but nothing enforces this; the two are read from two different, independently attacker-controlled fields of the same unauthenticated JSON body.

### Impact Explanation
An attacker who knows (or guesses) the name of any organization configured in the Shipit instance's `Shipit.github` map that has no `webhook_secret` set can send a forged `X-Github-Event: push` / `status` / `check_suite` / `membership` / `pull_request` webhook with `repository.owner.login` (or `organization.login`) set to that secret-less org, while `repository.full_name` / commit `sha` targets a different, victim organization's stack. This results in cross-repository writes without ever proving control of the victim repository: forged commit statuses can be injected (`StatusHandler`), `GithubSyncJob` can be queued against arbitrary tracked stacks (`PushHandler`), and other handlers (membership, pull_request, check_suite) operate on the same trust assumption. This matches the Critical "cross-repository writes" / unauthorized-state-mutation impact category, since forged commit statuses can influence CI-gated deploy decisions and forged sync/membership events mutate state outside the attacker's actual repository.

### Likelihood Explanation
Exploitation only requires an unauthenticated HTTP POST to the public `/webhooks` endpoint with a crafted JSON body — no GitHub credentials, session, or API token needed. The only precondition is that at least one org known to the Shipit instance has an unset `webhook_secret`, which is an explicitly supported and documented configuration (shown as the default/example in this repo's own dev and test fixtures), making this a realistic operational state rather than a purely theoretical one.

### Recommendation
Do not select the verification secret from a field embedded in the same unauthenticated payload; instead, derive the expected signing organization from a trusted, out-of-band source (e.g., require the caller to sign with a per-repository secret keyed by an authenticated route parameter, or verify against every configured secret and cross-check the resulting authenticated org actually owns the repository referenced in `repository.full_name`/`sha` before dispatching to handlers). Additionally, require `webhook_secret` to be present for every configured GitHub App/organization (fail closed) rather than silently returning `true` in `GithubApp#verify_webhook_signature` when it is blank.

### Proof of Concept
1. Configure Shipit with two organizations (as in `test/dummy/config/secrets_double_github_app.yml`): `OrgOne` (tracks `OrgOne/victim-repo` as a Shipit stack) and `OrgTwo` (`webhook_secret` left blank, as shown in the sample configs).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
}
```
No `X-Hub-Signature` value needs to be valid for `OrgOne`; `repository_owner` resolves to `OrgTwo`, whose `verify_webhook_signature` short-circuits to `true` because `OrgTwo`'s `webhook_secret` is blank.
3. `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) finds stacks by `branch` across all tracked stacks (not scoped to `OrgTwo`) and calls `sync_github` on the `OrgOne/victim-repo` stack, demonstrating a write triggered against a repository never authenticated by the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
