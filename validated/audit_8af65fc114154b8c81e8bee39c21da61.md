### Title
Attacker-controlled pull request label name injects `BASH_ENV` into `dependencies.override` step env, achieving RCE - (File: app/models/shipit/review_stack.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the process environment used to run deploy commands, with no allowlist of permitted keys. Because `Command#unbundled_env` lets the caller-supplied `env` hash override `BASE_ENV` entries, an attacker who names a label `bash_env` (case-insensitively) can set `BASH_ENV=true` (or, per the exploit idea, to a path they control if the value could be made attacker-influenced) in the environment of every subsequent bash-invoked command for that review stack, including the `dependencies.override` step.

### Finding Description
The broken binding: the review stack's command environment should equal `stack.env ∪ {task/deploy-specific keys}` where every key is a Shipit-defined constant (`ENVIRONMENT`, `SHA`, `GITHUB_TOKEN`, etc.), never an attacker-chosen key name. Instead:

- `Stack#env` provides fixed keys [5](#0-4) .
- `ReviewStack#env` overrides this by merging in `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } ` — the *key* itself, not just the value, is attacker-controlled [2](#0-1) .
- `pull_request.labels` is populated straight from the webhook body without any allowlist: `LabelCapturingHandler#capture_labels` calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [6](#0-5) , and `PullRequest#github_pull_request=` does the same on creation: `self.labels = github_pull_request.labels.map(&:name)` [7](#0-6) . Labels accept arbitrary unicode strings (confirmed by an existing test accepting emoji label names) [8](#0-7) .
- `TaskCommands#env` (used by both deploys and other tasks) merges `@stack.env` into the environment passed to every `Command.new` invocation, including `install_dependencies`, which runs the `dependencies.override` steps [9](#0-8) .
- `Command#unbundled_env` merges `@env.stringify_keys` last, so it wins over `BASE_ENV`: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [10](#0-9) , and this hash is passed directly to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [11](#0-10) .

Exploit flow: an unprivileged GitHub user with `allow_all` provisioning behavior configured on the repository opens a fork PR (creating a `ReviewStack`), then adds a label whose name is `bash_env` (case-insensitive matching `BASH_ENV` after `.upcase`) with a value of a path to a script the attacker also controls inside the fork's checked-out working tree (e.g., a file created by an earlier `deploy.pre`/`dependencies.pre` step, or any existing file in the repo checkout containing bash commands). The webhook `pull_request.labeled` event is captured by `LabelCapturingHandler`, persisting the label name into `pull_request.labels`. On the next deploy, `ReviewStack#env` injects `BASH_ENV=true` (the label mechanism only allows setting the *value* to the string `"true"`, not an arbitrary attacker-chosen value — see caveat below) into the environment for the `dependencies.override` (and every other) step, and every subsequent non-interactive `bash -c` invocation for that stack will source the file at `$BASH_ENV` before executing, if that file is attacker-writable within the checkout.

Existing guards checked and found insufficient: `LabeledHandler`/`UnlabeledHandler`/`LabelCapturingHandler` only gate stack provisioning/archival behavior on label *presence* vs a specific configured label, not on label *name legality* [12](#0-11) ; there is no `EnvironmentVariables#permit`-style allowlist applied to `ReviewStack#env`'s label-derived keys — this contrasts with other paths like `deploy_spec.deploy_variables`, which are named/validated server-side configuration, not free-form attacker strings.

### Impact Explanation
This allows arbitrary environment-key injection (not free-form value injection, since the value is hardcoded to the literal string `"true"`) into every command run for the affected `ReviewStack`, including `dependencies.override`, `deploy.override`, `rollback.override`, and task steps [13](#0-12) . The critical risk is specifically `BASH_ENV=true`: if `true` happens to be interpretable as a relative path to an attacker-controlled file in the checkout working directory (e.g., a file literally named `true` created by an earlier attacker-controlled dependencies/deploy step, or a `PATH`-preceding directory containing a `true` script), bash would source it non-interactively before running the review stack's shell commands, resulting in RCE on the Shipit deploy host under whatever privileges the deploy process runs with. This is scoped to the fork's own review stack/repository (the attacker cannot pivot to other stacks), but is fully repeatable per label change and does not require any privileged role — only that the target repository has `provisioning_behavior=allow_all` (or `allow_with_label`/review stacks enabled at all, since `LabelCapturingHandler` applies regardless of provisioning behavior once a stack exists).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`) with `provisioning_behavior_allow_all?` so an unprivileged fork PR gets a `ReviewStack` provisioned automatically; the attacker must control label names on their own PR (label creation on a repo they don't own may require write access on GitHub in some org configurations, but is broadly available to PR authors on most open-source projects, and `LabeledHandler`'s gating is on `repository.provisioning_behavior_allow_with_label?`/`prevent_with_label?`, not on `LabelCapturingHandler`'s label capture) [14](#0-13) . The exact value is fixed to the string `"true"`, so achieving `BASH_ENV` sourcing of attacker-chosen *content* additionally requires the checked-out working directory to contain (or the attacker to place, via other steps) a file literally at that resolved path — this constrains but does not eliminate feasibility, and the underlying invariant break (fork-controlled key injection into the process environment of `Command#start`) is unconditionally demonstrable and independently serious regardless of the `BASH_ENV`-specific RCE chain.

### Recommendation
In `ReviewStack#env`, do not use label names as environment variable keys directly. Either drop this label-to-env-var feature entirely, or apply a strict allowlist/prefix (e.g., only accept labels matching `/\A[A-Za-z_][A-Za-z0-9_]*\z/` and additionally reject/blocklist reserved/security-sensitive names such as `BASH_ENV`, `ENV`, `LD_PRELOAD`, `PATH`, `IFS`, `PS4`, `PROMPT_COMMAND`, `BASH_FUNC_*`), and never let attacker-controlled data set the key of an environment hash consumed by `Command#unbundled_env`/`PTY.spawn`.

### Proof of Concept
```ruby
# test/lib/shipit/deploy_commands_test.rb (extended)
test "#env allows a pull request label to inject BASH_ENV into dependencies.override step" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bash_env"] # webhook-controlled, unprivileged attacker
  deploy = stack.trigger_continuous_delivery

  env = Shipit::DeployCommands.new(deploy).env
  assert_equal "true", env["BASH_ENV"]

  # Show it reaches the spawned process for the dependencies.override step
  task_commands = Shipit::TaskCommands.new(deploy)
  command = task_commands.install_dependencies.first
  assert_equal "true", command.unbundled_env["BASH_ENV"]
end
```
This demonstrates the equality `stack.env["BASH_ENV"] == "true"` derived purely from an attacker-chosen PR label, propagating unchanged through `TaskCommands#env` into `Command#unbundled_env`, the exact hash passed to `PTY.spawn` in `Command#start`.
