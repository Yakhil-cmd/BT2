### Title
`repository.owner.login` vs `repository.full_name` split lets a no-secret org's signature bypass authenticate a webhook that mutates a different org's `PullRequest` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to authenticate the request solely from `repository.owner.login` (via `repository_owner`), while `AssignedHandler#repository` (and other `pull_request` handlers) resolves the target `Repository`/`Stack` solely from `repository.full_name`. These two payload fields are never cross-checked against each other, so an attacker can set `repository.owner.login` to an org that has no `webhook_secret` configured (whose signature check always passes) while setting `repository.full_name` to a repository belonging to a completely different (victim) org/stack.

### Finding Description
The broken binding is the implicit assumption that `repository.owner.login == repository.full_name.split('/').first`. Nothing enforces this equality.

- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` (app/controllers/shipit/webhooks_controller.rb:59-62).
- `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) returns `true` unconditionally when `@webhook_secret` is blank for that org's config (`return true unless webhook_secret`). So any org configured without a `webhook_secret` will accept an unsigned/arbitrarily-signed request as valid.
- After signature "verification" passes, `WebhooksController#create` dispatches to handlers with the full parsed `params` (app/controllers/shipit/webhooks_controller.rb:10-15), and `AssignedHandler#repository` looks up the target repo from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` (app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb:67-69), then `AssignedHandler#pull_request` finds the persisted `Shipit::PullRequest` scoped to that repository (lines 53-65) and `process` calls `pull_request.update(github_pull_request: params.pull_request)` (line 44).

Exploit flow: attacker crafts `POST /webhooks` with header `X-Github-Event: pull_request`, body `action: "assigned"`, `repository.owner.login: "no-secret-org"` (an org present in `Shipit.github_teams`/config but with no `webhook_secret`), and `repository.full_name: "victim-org/victim-repo"`. The signature check resolves the no-secret org's `GitHubApp`, which returns `true` regardless of signature/absence of `X-Hub-Signature`. The handler then updates the `PullRequest` row belonging to `victim-org/victim-repo`'s stack — a write to a repository/stack that never authenticated the request.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schema on `AssignedHandler` only requires `repository.full_name` to be a String, with no relationship enforced to `repository.owner.login`; `verify_signature` never inspects `full_name`; there's no `Repository`/`Stack` ownership check against the authenticating org before dispatch.

### Impact Explanation
An unprivileged internet attacker can write attacker-controlled data (`github_pull_request` JSON blob) into the `PullRequest` record of a victim stack they do not own and never authenticated for, purely by choosing which org name appears in `repository.owner.login` versus `repository.full_name`. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" — cross-tenant state corruption via a forged/unauthenticated webhook. It's repeatable against any victim repository/stack, for any org in the Shipit config that has no `webhook_secret` set, and requires no privileges, tokens or secrets.

### Likelihood Explanation
Preconditions: at least one org configured in `Shipit.github_teams`/GitHub app config without a `webhook_secret` (a stack owner or operator misconfiguration, not attacker-controlled, but plausible/common in multi-tenant Shipit deployments), and a target victim repository/stack the attacker wants to mutate known by full_name. Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body — trivial and fully repeatable. `GithubOrganizationUnknown` only guards against orgs not present in config at all, not against this owner/full_name mismatch, so it does not block the attack as long as `repository.owner.login` names a real (registered, secret-less) org.

### Recommendation
Verify the webhook signature using the org derived from `repository.full_name` (the org that actually owns the mutated repository), not `repository.owner.login`; or, cross-check that `repository.owner.login` matches the first path segment of `repository.full_name` and reject (422) on mismatch before dispatching to any handler. Additionally, consider disallowing/warning on orgs configured without a `webhook_secret` in production configs.

### Proof of Concept
Minitest plan (test/controllers/webhooks_controller_test.rb style, no live GitHub):
1. Configure two orgs in `Shipit.github_teams`/app config: `"no-secret-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret`.
2. Create `victim_repo = Repository.create!(owner: "victim-org", name: "victim-repo")`, a `Stack` for it, and a `PullRequest` row with `number: 42` and known `github_pull_request` content.
3. Build a `pull_request` "assigned" payload where `repository.owner.login = "no-secret-org"`, `repository.full_name = "victim-org/victim-repo"`, `number: 42`, `action: "assigned"`, valid nested `pull_request`/`sender` fields per `AssignedHandler` schema.
4. POST to `/webhooks` with `X-Github-Event: pull_request` and no valid `X-Hub-Signature` for `victim-org`'s secret (e.g., omit header or use garbage).
5. Assert response is `200 OK` (not `422`), proving the no-secret org's bypass accepted the forged request.
6. Assert `PullRequest.find_by(number: 42, ...).github_pull_request` was updated to the attacker-supplied `pull_request` payload — proving a write to `victim-org`'s stack occurred despite the request never being authenticated by `victim-org`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
