### Title
Session fixation via GitHub OAuth callback binding the authenticated GitHub identity to a pre-existing, non-reset session - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The Genesis-Group bug is a "binding" flaw: a value the contract trusts (accepted purchases) is allowed to diverge from the invariant it's supposed to respect (`maxGenesisPrice`), because the code that enforces the constraint doesn't gate the state-changing action. The analogous binding in this engine is: **the GitHub identity returned by the OmniAuth callback** versus **the `User` bound to the Rack session (`session[:user_id]`)**. `GithubAuthenticationController#callback` writes `session[:user_id]` into whatever session currently exists, without first invalidating/rotating that session, so a session established before authentication remains valid and gets silently upgraded to an authenticated one.

### Finding Description
`GithubAuthenticationController#callback` performs the OAuth binding as follows: [1](#0-0) 

Note that `session[:user_id] = sign_in_github(auth)` is set directly on the existing session object, and `reset_session` is never called in this path (it is only called in `logout` and in the unrelated `force_github_authentication` fresh-login-expiry path in the `Authentication` concern): [2](#0-1) 

Because Rails session cookies are not rotated on privilege elevation here, if an attacker can get a victim's browser to carry a session ID chosen or known by the attacker *before* the victim completes GitHub OAuth (classic session fixation via a shared/pre-set session cookie, e.g. on a host that doesn't set `secure`/isolate cookies per subdomain, or via any mechanism that lets an unauthenticated party observe/pre-establish a session id for the target origin), the same session record is reused across the trust boundary: pre-auth (anonymous) and post-auth (`current_user` = victim). The equality that should hold — `session_identity_before_auth == session_identity_after_auth` only when both are anonymous, otherwise the session must be rotated — is violated: the attacker's fixed session, once the victim completes the OAuth dance, becomes bound to the victim's `User` record and `github_access_token`, without any session ID change.

### Impact Explanation
If exploitable, this allows session fixation / forced OAuth completion, letting an attacker who fixates a session take over an authenticated victim session after the victim logs in — gaining the victim's authorization level (`current_user.authorized?`, team membership, deploy/rollback/merge actions) without ever presenting credentials themselves. This matches the explicitly listed High-impact category "session fixation / forced OAuth completion."

### Likelihood Explanation
Exploitability depends entirely on whether the host application's session cookie configuration allows an attacker to fixate a session ID for the victim's browser before OAuth completes (e.g., cookie scope, absence of `httponly`/`secure`, or a subdomain takeover) — this is a session/cookie-management precondition outside `app/**`/`lib/shipit/**` visible here. Within the engine's own code, the missing `reset_session` on the login path is a concrete, verifiable gap: unlike `logout` and the forced-relogin branch, `callback` never calls `reset_session`, so the engine does nothing to defend against this even if the precondition is met elsewhere.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` before assigning `session[:user_id]` (preserving `omniauth.origin` if needed across the reset), matching the pattern already used in `logout` and in `Authentication#force_github_authentication`.

### Proof of Concept
1. Attacker visits the Shipit host and obtains/sets a session cookie value `S` for the target origin (session-fixation precondition, e.g., via a cookie-scoping weakness on a shared host).
2. Attacker gets the victim to open the app with session cookie `S` still attached, and the victim completes GitHub OAuth login.
3. `GithubAuthenticationController#callback` sets `session[:user_id] = victim.id` on the *same* session `S` (`app/controllers/shipit/github_authentication_controller.rb:13`), and never calls `reset_session`.
4. Attacker, still holding session `S`, is now recognized as the victim by `Authentication#current_user` (`app/controllers/concerns/shipit/authentication.rb:36-42`), inheriting the victim's authorization and ability to trigger deploys/rollbacks/merges. [3](#0-2) [4](#0-3)

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
```
