### Title
Fee-on-Transfer ERC20 Token Drains Destination Bridge Liquidity via Unverified `safeTransferFrom` Amount — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, but never verifies the actual balance received. It then emits `RequestValueTransfer` with the caller-supplied `_value`. Bridge operators observe this event and call `handleERC20Transfer` on the counterpart bridge, which unconditionally releases `_value` tokens to the recipient. When the token has fee-on-transfer behavior, the source bridge receives less than `_value`, but the destination bridge releases the full `_value`, draining its reserves.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
// contracts/service_chain/bridge/BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

No balance snapshot is taken before or after the `safeTransferFrom`. The internal `_requestERC20Transfer` then emits the event with the caller-supplied `_value`:

```solidity
// L97-106
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // ← user-supplied, not actual received amount
    requestNonce,
    fee,
    _extraData
);
``` [2](#0-1) 

On the counterpart chain, `handleERC20Transfer` releases exactly `_value` tokens:

```solidity
// L71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [3](#0-2) 

The same flaw exists in the 1-step path. `ERC20ServiceChain.requestValueTransfer` transfers `_amount + _feeLimit` to the bridge (bridge receives less due to the token fee), then calls `onERC20Received` with the original `_amount`:

```solidity
// contracts/testing/sc_erc20/ERC20ServiceChain.sol L44-46
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
``` [4](#0-3) 

`onERC20Received` passes `_value` directly to `_requestERC20Transfer` without any balance verification:

```solidity
// L111-121
function onERC20Received(address _from, address _to, uint256 _value, uint256 _feeLimit, bytes memory _extraData) public {
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
``` [5](#0-4) 

---

### Impact Explanation

In lock/unlock mode (`modeMintBurn = false`), the destination bridge holds a reserve of tokens to fulfill withdrawals. Each transfer of a fee-on-transfer token causes the destination bridge to release `_value` tokens while the source bridge only received `_value * (1 - fee_rate)`. The shortfall (`_value * fee_rate`) is a direct, irreversible loss from the destination bridge's reserve per transfer. An attacker can repeat this to fully drain the destination bridge's token reserve.

Corrupted value: `destinationBridge.balanceOf(token)` decreases by `_value` per handle, while the source bridge only received `_value * (1 - fee_rate)`. The accounting invariant `sum(deposited) == sum(withdrawn)` is permanently broken.

---

### Likelihood Explanation

The trigger requires only that a fee-on-transfer ERC20 token be registered on both sides of the bridge. Token registration is a bridge-owner operation, but:
- A legitimate token may add fee-on-transfer behavior via an upgrade after registration.
- A bridge owner may unknowingly register a token with this property.

Once such a token is registered, any unprivileged user can call `requestERC20Transfer` or `requestValueTransfer` to exploit the discrepancy. No special role is needed after registration.

---

### Recommendation

In `requestERC20Transfer`, snapshot the bridge balance before and after `safeTransferFrom` and use the actual received amount as the transfer value:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived >= _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Apply the same guard in `onERC20Received` by comparing `msg.sender` balance before/after, or by requiring the token to implement a no-fee transfer path.

---

### Proof of Concept

**Setup:** Deploy a fee-on-transfer ERC20 (10% burn on every transfer). Register it on both the parent and child bridge in lock/unlock mode (`modeMintBurn = false`). Pre-fund the destination bridge with 1000 tokens.

**Steps:**
1. Attacker approves source bridge for 100 tokens.
2. Attacker calls `requestERC20Transfer(feeToken, attacker, 100, 0, "")`.
3. Source bridge receives 90 tokens (10% fee deducted), emits `RequestValueTransfer` with `_value = 100`.
4. Bridge operators call `handleERC20Transfer(..., 100, ...)` on destination bridge.
5. Destination bridge calls `safeTransfer(attacker, 100)` — releases 100 tokens.

**Result:** Attacker deposited 90 tokens, received 100 tokens. Destination bridge lost 10 tokens per iteration. After 100 iterations the destination bridge is drained of 1000 tokens while only 900 were ever deposited on the source side.
