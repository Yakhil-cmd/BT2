### Title
Unhandled `throw Error("more than 1 address definition")` crashes the validating node - (File: definition.js)

### Summary
CVE-2018-5740 is a BIND `assertion failure` in `name.c` reachable by attacker-controlled DNS answer data, crashing the resolving process. The analogous bug class in `ocore` is an unhandled `throw` inside asynchronous validation logic that is reachable from unit content supplied by an untrusted peer/poster, which crashes (or corrupts the state of) the validating Node.js process instead of returning a normal validation error.

### Finding Description
In `definition.js`, both `validateDefinition`'s inner `evaluate()` and `validateAuthentifiers`'s inner `evaluate()` handle the `'address'` operator by looking up the referenced address's definition. When the definition is not yet found in storage, the code falls back to looking for an author in the *currently validated* unit that supplies the matching definition: [1](#0-0) [2](#0-1) 

Both blocks do:
```
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```
This `throw` happens inside the async callback of `storage.readDefinitionByAddress`'s `ifDefinitionNotFound` handler — i.e., inside a `conn.query` callback executed on a later tick of the event loop, not inside the synchronous call stack of the code that invoked `validateDefinition`/`validateAuthentifiers`. Callers such as `signed_message.js` wrap the *synchronous* call to `Definition.validateAuthentifiers` in `try/catch`: [3](#0-2) 

but that `try/catch` cannot catch an exception thrown from a callback invoked asynchronously later (after the synchronous call has already returned), so a `throw` from inside `ifDefinitionNotFound` becomes an **uncaught exception** that propagates out of the event loop, analogous to BIND's assertion failure crashing `named`.

### Impact Explanation
An uncaught exception thrown from deep inside unit/message/signed-package validation crashes the Node.js process running the wallet, hub, or full node (Node.js by default terminates on an unhandled exception unless a global handler swallows it). Because this code path is reachable while validating ordinary application data (address definitions embedded in unit authors, AA triggers, or signed packages/private-payment messages that reference nested address definitions), a peer or counterparty can supply a unit/message engineered to trigger this branch and crash the recipient node — a network-wide "unable to confirm new units" condition if witnesses/hubs are affected, matching the accepted impact categories (node crash / inability to validate) analogous to the BIND DoS.

### Likelihood Explanation
Direct triggering from a single top-level unit's `authors` array is blocked, because `validateAuthors`/`validateSignedMessage` enforce that author addresses in `objUnit.authors` are strictly sorted and therefore unique: [4](#0-3) [5](#0-4) 

so a normal `objUnit.authors.filter(author => author.address === other_address ...)` can yield at most 1 match when addresses are unique. However, this dedup/sort guarantee is enforced only for the *outer* authors array construction and is not itself part of `validateDefinition`/`validateAuthentifiers`; it must be independently re-verified for every code path that builds an `objUnit`-like structure before calling into `Definition.*` (e.g., private-payment chain reconstruction, AA-trigger synthesized units, or `wallet_defined_by_addresses.js`/`wallet_defined_by_keys.js` callers). I was not able to fully verify, within the available context, whether every one of those alternate call sites enforces the same uniqueness/sort invariant on the `authors` array they pass in — this needs to be traced in `wallet_defined_by_addresses.js` and `wallet_defined_by_keys.js`, which were not retrievable in this session (index limitations). If any caller constructs a validation-time `objUnit` with two "author" entries for the same address whose definitions both hash to the same `definition_chash` referenced by a nested `'address'` op, the throw fires.

### Recommendation
- Replace both `throw Error("more than 1 address definition")` occurrences with a graceful `cb(false)` / `cb2(false)` (treat as "cannot resolve, condition fails") rather than throwing, since this is attacker/data-reachable code.
- Audit every caller of `Definition.validateDefinition` and `Definition.validateAuthentifiers` (`validation.js`, `signed_message.js`, `wallet_defined_by_addresses.js`, `wallet_defined_by_keys.js`, AA composer paths) to confirm the `authors`/co-signer arrays they build are always deduplicated/sorted by address before being passed in, closing off any path that could produce `arrDefiningAuthors.length > 1`.
- More generally, wrap all validation entry points so any exception thrown asynchronously inside DB-callback continuations is caught and converted into a normal validation error instead of crashing the process (defense in depth against future similar `throw Error(...)` sites in `definition.js`/`validation.js`).

### Proof of Concept
Conceptual (exact reachable call site not fully confirmed due to index limitations noted above):
1. Construct a signed message / private payment chain / AA-trigger synthesized unit whose `authors`-like array contains two entries for the *same address* `A`, each carrying a `definition` field, both of which hash (via `objectHash.getChash160`) to the same `definition_chash` that address `A`'s definition references via `['address', 'A']` in a nested condition, in a context where the top-level unique/sort check on `authors` (`validation.js:1135-1140` / `signed_message.js:147-155`) is not applied to the structure ultimately passed into `Definition.validateAuthentifiers`/`validateDefinition`.
2. Send/post this data to a node performing validation.
3. `arrDefiningAuthors.length > 1` evaluates true inside the async `ifDefinitionNotFound` callback, and the resulting `throw Error("more than 1 address definition")` escapes as an unhandled exception, crashing the node process — the same class of "assertion/exception causes crash on attacker input" root cause identified in CVE-2018-5740.

**Confidence caveat:** Because I could not retrieve the full contents of `wallet_defined_by_addresses.js` and `wallet_defined_by_keys.js` in this session (index size limits may exclude some file contents), I could not conclusively confirm a call site where the authors-array uniqueness invariant is bypassed before reaching this `throw`. A Devin session with full filesystem access should trace those two files and any AA-composer paths that build synthetic `objUnit.authors` to confirm or rule out a concrete unauthenticated trigger.
