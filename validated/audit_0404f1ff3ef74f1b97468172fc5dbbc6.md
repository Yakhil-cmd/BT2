The web UI's `Authentication` concern binds `current_user` strictly to the `session[:user_id]` set during GitHub OAuth [1](#0-0) , but the API's `BaseController` binds `current_user` to an arbitrary, unauthenticated `X-Shipit-User` header supplied by the caller, with no cryptographic or ownership link to the authenticated `ApiClient` [2](#0-1) . ### Title
API actions are attributed to an arbitrary, attacker-chosen `User` via the unauthenticated `X-Shipit-User` header, breaking the identity binding enforced by session-based authentication - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
### Finding Description
Shipit maintains two parallel notions of "current user" that are supposed to represent the same trust concept — the actor performing an operation — but are bound very differently:

- In the web UI, `Shipit::Authentication#current_user` is derived exclusively from `session[:user_id]`, which is only set after a verified GitHub OAuth login flow [1](#0-0) . There is no way for a request to claim to be another `User` without controlling that user's session.
- In the API, `Shipit::Api::BaseController#current_user` is derived from `identify_user`, which simply looks up any `User` record whose `login` matches the client-supplied `X-Shipit-User` request header, with no verification that the caller is actually that person: `User.where('lower(login) = ?', user_login.downcase).first if user_login` [7](#0-6) .

Authentication of the *request* is handled separately via `ApiClient` Basic-auth tokens (`authenticate_api_client`) [8](#0-7) , and permission scope is enforced via `ApiClient#check_permissions!` against the `permissions` array and, optionally, a `stack_id` binding on the `ApiClient` record [9](#0-8) . But nothing ties the `X-Shipit-User` header value to the `ApiClient`'s `creator` or to any authenticated identity of the caller. Any holder of a valid `ApiClient` token — including a narrowly-scoped one limited to a single stack — can set `X-Shipit-User` to the login of *any* existing `User` (e.g., an admin or a team lead) and have every downstream action recorded and authorized as if performed by that impersonated user.

This is the same class of binding failure as the referenced report: the credential that is actually verified (the `ApiClient` token) is not the entity that the code subsequently trusts and acts on behalf of (the `User` identity used for authorship/audit and for user-oriented equality checks such as `lock_author`).

### Impact Explanation
The impersonated `current_user` is passed directly into state-changing, trust-sensitive operations:
- `Stack#lock` / archive, recording an arbitrary `lock_author` [3](#0-2)  and [10](#0-9) .
- Triggering a deploy (`stack.trigger_deploy(commit, current_user, ...)`) [4](#0-3) .
- Triggering or aborting a rollback (`deploy.trigger_rollback(current_user, ...)`, `active_task.abort!(aborted_by: current_user, ...)`) [5](#0-4) .
- Triggering or aborting arbitrary tasks (`stack.trigger_task(..., current_user, ...)`, `task.abort!(aborted_by: current_user)`) [6](#0-5) .

Because deploys/rollbacks/task execution run the repository's `shipit.yml` steps on the deploy host with the app's GitHub credentials, an attacker holding any deploy-scoped `ApiClient` token can cause an unauthorized deploy/rollback while forging the audit trail to implicate a different, legitimate user, undermining accountability and any user-identity-based authorization or review logic that trusts `current_user`.

### Likelihood Explanation
Exploitation requires only possession of a valid `ApiClient` token with the relevant `permissions` entry (`deploy:stack`, `lock:stack`, etc.) — the same minimum precondition the API already requires for these endpoints — plus setting one extra HTTP header. No GitHub credentials, session, or private key are needed beyond what a legitimate low-privilege API client already possesses. This is a low-effort, high-reliability manipulation once any scoped token is available.

### Recommendation
Do not trust the `X-Shipit-User` header as an unauthenticated identity claim. Either remove reliance on it in the API entirely (attribute actions to the `ApiClient`'s `creator` or the `ApiClient` itself), or require that any `X-Shipit-User` value be cryptographically bound to the requester (e.g., validated against a per-user-scoped token, or restricted to `ApiClient`s explicitly authorized to act "on behalf of" that specific user, with an explicit authorization record).

### Proof of Concept
1. Obtain (or be issued) an `ApiClient` token scoped only to `deploy:stack` for a specific stack, as shown in the fixtures (`here_come_the_walrus` scoped to `shipit_stacks(:shipit)`) [11](#0-10) .
2. Send `POST /api/stacks/:owner/:repo/:env/deploys` with `Authorization: Basic <token>` and header `X-Shipit-User: <victim-admin-login>`.
3. `identify_user` resolves `current_user` to the victim `User` record purely from the header [7](#0-6) .
4. `DeploysController#create` triggers the deploy with `current_user` set to the victim, so the resulting `Deploy` is recorded and treated as authored by the victim rather than the actual token holder [4](#0-3) .
