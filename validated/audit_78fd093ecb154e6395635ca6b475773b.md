### Title
Stack-scoped API tokens can read the CI status of any stack via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` re-implements stack lookup instead of using the scoping logic from `Shipit::Api::BaseController`, so a token that was created scoped to a single stack (`ApiClient#stack_id` present) can be used to read the CCMenu (CruiseControl) build status of *any* stack in the installation, not just the one it was authorized for.

### Finding Description
`Shipit::Api::BaseController` implements stack-scoping for tokens as an equality: the set of stacks a request may touch must equal the set of stacks the authenticated `ApiClient` authorizes. [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This means: if `current_api_client.stack_id` is set (i.e. the token was created scoped to one stack), any lookup through `stack` is constrained to `Stack.where(id: current_api_client.stack_id)` — a request for a different `stack_id` param 404s.

`Api::CCMenuController`, however, overrides `stack` and bypasses this scoping entirely, looking the stack up straight from the request parameter with no reference to the authenticated client at all: [2](#0-1) 

```
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

The controller only enforces `require_permission :read, :stack` (a global permission bit check via `ApiClient#check_permissions!`, which never looks at `stack_id`): [3](#0-2) 

The binding broken is: **the stack a token authorizes (`ApiClient#stack_id`) ≠ the stack the request actually touches (`params[:stack_id]` resolved via `Stack.from_param!` in `CCMenuController#stack`)**. Any holder of a valid, stack-scoped `read:stack` token can substitute an arbitrary `stack_id` in the URL and receive that other stack's latest deploy/rollback status, build label, and activity — data belonging to a stack outside the token's intended authorization boundary.

This is the same class of defect as the external report's `SecuritizeRedemption::redeem()` bug: a validation is present, but it is checked against the wrong value (a global permission bit) instead of the value that should gate the actual resource access (the specific `stack_id` the token was scoped to).

### Impact Explanation
This grants unauthenticated (relative to the target stack) read access to stack state/deploy status for stacks the token was never authorized to see, which matches the documented High-severity criterion: "unauthenticated read of stack state, task streams or deploy output." Any consumer holding a single scoped CCMenu/API token (which are routinely embedded in CI dashboards, distributed to less-trusted tooling, etc.) can enumerate and monitor deploy status of every stack in the installation, not just their own.

### Likelihood Explanation
Likelihood is high given how trivial exploitation is: an attacker only needs one legitimately-scoped `read:stack` token (e.g. a CCMenu URL token intended for a single stack) and knowledge/guessing of another stack's `to_param` (repo/owner/environment string, typically not secret) to pull that stack's build status through `GET /ccmenu/:stack_id?token=...`.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it to delegate to the scoped `stacks` collection from `BaseController`, e.g. `stacks.from_param!(params[:stack_id])`) so CCMenu lookups are constrained by `current_api_client.stack_id` exactly like every other API controller.

### Proof of Concept
1. Create/obtain a token scoped to Stack A (`ApiClient` with `stack_id` set to Stack A's id, permission `read:stack`) — e.g. via the "CCMenu Client" flow at `GET /ccmenu/*stack_id` (`Shipit::CCMenuUrlController#fetch`), or an admin-issued scoped token.
2. Issue `GET /ccmenu/<Stack-B-repo_owner>/<Stack-B-repo_name>/<Stack-B-environment>?token=<token-scoped-to-A>` against `Shipit::Api::CCMenuController#show`.
3. Observe the response returns Stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, etc., even though the token was only authorized for Stack A — because `authenticate_api_client` only checks `ApiClient.authenticate(params[:token])` and `stack` resolves `params[:stack_id]` directly via `Stack.from_param!`, never consulting `current_api_client.stack_id`.
