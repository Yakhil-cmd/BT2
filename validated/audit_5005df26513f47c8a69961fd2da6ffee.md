## Finding: Webhook Organization Used for Signature Verification Is Not Bound to the Organization Whose Team Membership Is Mutated

### Title
Membership Webhook Authorization Bypass via Organization/Repository Field Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The bug class described in the report (a callback trusting stale/attacker-influenced state instead of the value that was actually verified) maps to a concrete binding break in Shipit's webhook processing: the **organization used to select the webhook secret for HMAC verification** is not the same field as the **organization used to create/mutate `Team` membership**, even though both come from the same untrusted, attacker-shaped JSON body.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to verify the request signature against using: [1](#0-0) [2](#0-1) 

`repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — it prefers `repository.owner.login` if that key is present at all, only falling back to `organization.login` otherwise.

For the `membership` event, however, the actual mutation is performed by `MembershipHandler`, which reads a **different** JSON field — `params.organization.login` — to decide which `Team` gets created/updated and which `User` is added/removed from it: [3](#0-2) 

Nothing in `MembershipHandler` cross-checks `params.organization.login` against the value that `verify_signature` used to select the signing org. Because the HTTP body is arbitrary attacker-controlled JSON (GitHub only guarantees the *bytes* are signed, not that specific keys correspond to specific semantic entities), an attacker who legitimately controls their **own** GitHub App installation on some `OrgA` (trivial to create — see `docs/setup.md`) knows `OrgA`'s `webhook_secret`. They can craft a payload where:

- `repository.owner.login = "OrgA"` → `verify_signature` selects `OrgA`'s app via `Shipit.github(organization: "OrgA")` and the signature validates because the attacker computed it with `OrgA`'s known secret.
- `organization.login = "OrgB"` (a victim organization already configured in Shipit's multi-tenant `github:` section, per `docs/setup.md:181-209`) → `MembershipHandler` creates/updates a `Team` scoped to `OrgB` and adds the attacker's chosen `member.login` to it.

This breaks the equality that should hold: `{organization authenticating the signature} == {organization whose Team is written}`.

### Impact Explanation
`Team` membership drives `Shipit`'s OAuth authorization scoping via `Shipit.github_teams`/`oauth_teams`, referenced throughout `lib/shipit/github_app.rb` (`oauth_teams`, line 42, 56) and `app/controllers/concerns/shipit/authentication.rb`. By forging a `membership` webhook that is validly signed (with an org the attacker legitimately owns) but targets a **different** organization's `Team` record via the `organization.login` field, an attacker can add an arbitrary GitHub login (including their own) to a `Team` that gates access for a restricted organization, and can also **remove** legitimate members (`case params.action ... when 'removed'`). This is a direct escalation into `Shipit.github_teams` authorization — one of the impacts explicitly listed as in-scope/High in the rules.

### Likelihood Explanation
Exploitation only requires:
1. Creating a personal/organizational GitHub App (unprivileged, self-service, as documented in `docs/setup.md`) and having it be one of the orgs already configured in the target Shipit deployment's multi-org `github:` config, OR compromising the webhook secret of any one configured org.
2. Sending a single forged HTTP POST to the public `/webhooks` endpoint with the crafted JSON described above — no Shipit session, `ApiClient` token, or repository write access is required, satisfying the "unprivileged attacker" constraint.

The gap is a straightforward field-confusion in application logic (`repository.owner.login`/`organization.login` selection in the controller vs. `organization.login` consumption in the handler), not a theoretical/best-practice issue, and is reachable through the engine's own code.

### Recommendation
Ensure `verify_signature` and `MembershipHandler` (and any other handler that trusts a payload-provided `organization`/`repository` field) resolve the authenticating organization from the **same** field, and have `MembershipHandler` explicitly assert that `params.organization.login` matches the organization actually used to select/verify the webhook signature before creating or mutating any `Team`/`Membership` record. More generally, the webhook signature verification should not derive the signing key from a value that downstream handlers use to determine *what* gets written; it should be pinned to a single unambiguous field validated consistently across the controller and every handler.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
X-Hub-Signature: sha1=<HMAC computed with OrgA's known webhook_secret over the exact body below>

{
  "action": "added",
  "team": { "id": <existing OrgB team id>, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/..." },
  "organization": { "login": "OrgB" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "OrgA" } }
}
```
`verify_signature` resolves `repository_owner` to `"OrgA"`, fetches `OrgA`'s `webhook_secret` via `Shipit.github(organization: "OrgA")`, and the signature validates. `MembershipHandler#process` then uses `params.organization.login` ("OrgB") to find/create the `Team` and add `attacker-github-login` as a member of an `OrgB`-scoped team, despite the request never being authenticated against `OrgB`'s webhook secret.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
