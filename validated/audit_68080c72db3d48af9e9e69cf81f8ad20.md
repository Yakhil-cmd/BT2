### Title
Webhook signature verified against `repository.owner.login`'s secret while the target stack is resolved from `repository.full_name` — cross-organization forced sync - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates the request against the GitHub App configured for `payload.dig('repository','owner','login')`, but `Handlers::Handler#stacks`/`#repository_name` (used by `PushHandler#process`) resolves the target `Stack` from the independent field `payload.dig('repository','full_name')`. Nothing in the request pipeline enforces that these two attacker-controlled fields refer to the same repository/organization, allowing an attacker who controls a webhook secret for one org to forge a payload naming a victim org's repository.

### Finding Description
The broken binding: `Shipit.github(organization: payload.dig('repository','owner','login'))` (the entity whose `webhook_secret` verifies the HMAC) is assumed to equal `Repository.from_github_repo_name(payload.dig('repository','full_name'))`'s owning organization (the entity whose `Stack` gets mutated). These are two separately-read, independently attacker-controlled JSON paths with no cross-check.

Code path:
- `verify_signature` computes `repository_owner` via [1](#0-0) , fetches `Shipit.github(organization: repository_owner)` and verifies the raw body against that org's `webhook_secret` [2](#0-1) .
- `#create` re-parses the same raw body and dispatches to `Shipit::Webhooks.for_event(event)` handlers [3](#0-2) .
- `Handler#stacks`/`#repository_name` looks up the target repository using `payload.dig('repository','full_name')`, not `repository.owner.login` [4](#0-3) .
- `PushHandler#process` finds any non-archived stack on the resolved repository matching `branch` and calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4) , which enqueues `GithubSyncJob` with the attacker-chosen `stack_id` and `expected_head_sha` [6](#0-5) .
- `GithubSyncJob#perform` then calls `stack.github_commits`/`stack&.github_api` — i.e., the **victim's** GitHub App credentials for the victim's org — to fetch and append commits into the victim's stack [7](#0-6) .

Exploit: attacker sends `POST /webhooks` with `X-Github-Event: push`, body `{"repository":{"owner":{"login":"org-with-secret"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"<attacker-chosen sha>"}`, HMAC-signed with `org-with-secret`'s own `webhook_secret` (which the attacker legitimately possesses because they control that org/app). `verify_signature` succeeds because it only checks against `org-with-secret`. The handler then resolves and mutates `victim-org/victim-repo`'s stack, entirely bypassing any binding to `org-with-secret`.

No existing guard closes this gap: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` schema in `PushHandler` only requires `ref`/`after` presence, not repository consistency; there is no validation anywhere that `repository.owner.login` matches the owner segment of `repository.full_name`.

### Impact Explanation
An attacker who owns/administers any GitHub organization onboarded into this Shipit instance (and therefore knows that org's `webhook_secret`) can forge a `push` webhook to force a `GithubSyncJob` to run against **any other tracked stack in the deployment**, using the victim stack's own `GITHUB_TOKEN`/App credentials to fetch and append arbitrary attacker-influenced `expected_head_sha` commits. This is a cross-repository/cross-tenant trigger: a payload authenticated for one organization mutates another organization's stack state (new commits, potential downstream deploy scheduling via `continuous_deployment` on the victim stack). This matches "Critical: a payload for one repository mutating another's stack/commit" in the scoped severity list. It is repeatable against every stack tracked by the instance and is not limited to a single request.

### Likelihood Explanation
Preconditions: (1) the Shipit instance hosts multiple GitHub organizations/apps with distinct `webhook_secret`s (a common multi-tenant Shipit deployment), (2) attacker controls at least one onboarded organization/app (e.g., their own org added to `Shipit.github_apps` config) and knows its `webhook_secret`, (3) a `Stack` exists tracking `victim-org/victim-repo` on branch `master`. Attacker cost is a single unauthenticated HTTP POST with a correctly-signed but semantically-inconsistent JSON body — no Shipit session, API token, or GitHub write access to the victim repo is required. This is fully repeatable and requires no timing or race conditions.

### Recommendation
In `WebhooksController` (or in `Handlers::Handler`), after signature verification, enforce that the organization used to verify the signature equals the owner of the repository the handler will act on — e.g., derive `repository_owner` and pass it into the handler, and have `stacks`/`repository_name` reject/short-circuit when `payload.dig('repository','owner','login')` doesn't case-insensitively match the owner segment of `payload.dig('repository','full_name')`. Alternatively, verify the signature using the app resolved from `repository.full_name`'s owner rather than the separate `repository.owner.login` field, so a single, consistent field drives both authentication and lookup.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "push webhook signed by one org cannot sync a stack belonging to another org" do
  victim_stack = shipit_stacks(:shipit) # tracks e.g. "shopify/shipit-engine", branch "master"

  forged_payload = {
    repository: { owner: { login: "org-with-secret" }, full_name: victim_stack.repository.github_repo_name },
    ref: "refs/heads/#{victim_stack.branch}",
    after: "deadbeefcafedeadbeefcafedeadbeefcafebabe"
  }.to_json

  # verify_signature will call Shipit.github(organization: "org-with-secret")
  attacker_app = Shipit::GitHubApp.new("org-with-secret", webhook_secret: "attacker-known-secret")
  Shipit.expects(:github).with(organization: "org-with-secret").returns(attacker_app)
  # Assert Shipit.github is NEVER queried for the victim's real owner during verification
  Shipit.expects(:github).with(organization: victim_stack.repository.owner).never

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-known-secret", forged_payload)
  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: Shipit::GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "deadbeefcafedeadbeefcafedeadbeefcafebabe"]) do
    post :create, body: forged_payload, as: :json
  end
end
```
This demonstrates the equality `Shipit.github(organization: repository_owner from payload).webhook_secret verifies bytes` != `Repository.from_github_repo_name(payload full_name).owner` — the two sides diverge and the divergence is currently unenforced, resulting in `GithubSyncJob` enqueued for the victim stack while only the attacker's org secret was ever validated.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
