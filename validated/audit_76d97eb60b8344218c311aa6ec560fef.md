### Title
Webhook signature verifies the wrong organization/repository binding, allowing cross-tenant forgery of commit statuses and pushes - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App secret to validate a webhook against using one field read straight out of the still‑unverified JSON body (`repository.owner.login`, falling back to `organization.login`), but the event handlers that actually mutate state (`PushHandler`, `StatusHandler`) read *different* fields from that same untrusted body (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all — just a raw commit `sha`). Because the field used to pick "which org's secret proves authenticity" is never checked against the field that decides "which repository/stack/commit gets written to", an attacker who legitimately controls one onboarded organization's webhook secret (in a multi‑tenant Shipit deployment, as documented under "Using Multiple Github Applications") can forge a signed webhook payload that is verified as coming from *their own* organization but that actually targets a *different, unrelated* organization's stacks and commits.

### Finding Description
`verify_signature` computes the organization to authenticate against from the payload, before the signature is checked: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and `Shipit.github(organization: repository_owner)` looks up that organization's `webhook_secret` to verify the HMAC over the raw POST body. This only proves "this exact byte-for-byte body was signed with organization X's secret" — it says nothing about which repository the *rest* of that same body claims to describe.

The generic handler base class, used by `PushHandler`, resolves the target `Repository`/`Stack` from a **different** JSON path in the same body: [3](#0-2) 

Nothing ties `repository.full_name` (used to pick the Stack to act on) back to `repository.owner.login` (used to pick the secret that authenticated the request). Both are arbitrary fields inside a payload the attacker fully controls when POSTing directly to Shipit's single, shared `/webhooks` endpoint.

`StatusHandler` is worse: it doesn't even use `stacks`/repository scoping at all — it looks up commits **globally** by SHA across every stack in the installation: [4](#0-3) 

Git commit SHAs are public (visible on GitHub, in PRs, in Shipit's own UI/API for any stack the attacker can view), so an attacker only needs to know a target commit's SHA in a stack they do **not** control, then forge a `status` webhook — signed with their *own* organization's webhook secret — setting `state: success` (and matching a required `context`) for that SHA. `verify_signature` will authenticate the request as belonging to the attacker's own organization (which is legitimate and expected), but `StatusHandler#process` will write the forged status onto the victim's commit in the victim's stack, because it never checks that the commit's stack belongs to the authenticated organization at all.

This is the exact class of bug described in the report: a binding that should hold (`organization authenticated == repository/stack written`) is never enforced, because the two sides are derived from independent, attacker-controlled parts of the same payload, similar to how effective RPL stake is checked at `claim()` time without being tied to the period it actually covers.

### Impact Explanation
A forged `status` event that marks a victim commit `success` for a required CI context makes `Commit#deployable?` return true (`success? && !blocked?`), even though no real CI ever ran: [5](#0-4) 

If the victim stack has continuous deployment/merge-queue enabled, this can trigger an **unauthorized deploy** (or unblock a merge) of a stack that belongs to a completely different, unrelated GitHub organization — this matches the "Critical: unauthorized deploy" impact category. Similarly, a forged `push` event (mismatched `repository.owner.login` vs `repository.full_name`) causes `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` on a victim's stack that the attacker's organization has no relationship to.

### Likelihood Explanation
This requires only:
- Shipit configured for multiple GitHub organizations (explicitly documented, supported multi-tenant setup — `docs/setup.md` "Using Multiple Github Applications").
- The attacker legitimately controls one onboarded organization and therefore already knows *their own* `webhook_secret` (they configured it when installing their GitHub App) — no access to the victim's secret, `api_clients_secret`, or any session/token is needed.
- The victim's target commit SHA, which is public information.

No GitHub App private key, no `ApiClient` token, no Shipit session, and no privileged account for the victim's organization are required — only knowledge the attacker already legitimately has about their own tenant.

### Recommendation
- After verifying the HMAC signature, re-derive the authenticated organization and require every handler to scope its lookups (`Repository.from_github_repo_name`, `Commit.where(sha:)`, `Team`/`Membership` lookups) to that authenticated organization only, rejecting/ignoring events where `repository.owner.login` (or `organization.login`) does not match the repository/stack actually referenced by the rest of the payload.
- Fix `StatusHandler#process` to scope `Commit.where(sha: ...)` by the repositories owned by the verified organization instead of querying globally by SHA.
- Consider using a single, GitHub-App-scoped webhook secret per installation (as GitHub Apps normally provide) rather than manually cross-referencing a payload-supplied organization name to pick a secret.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, onboarded to a shared Shipit instance, and knows `attacker-org`'s `webhook_secret` (set during onboarding).
2. Attacker learns the SHA of a commit in `victim-org/victim-repo`, tracked by a Shipit stack with CI requirements (`ci.require`).
3. Attacker crafts a `status` webhook JSON body:
   ```json
   { "sha": "<victim-commit-sha>", "state": "success", "context": "<required-context>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" } }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` extracts `repository_owner = "attacker-org"`, loads `attacker-org`'s secret, and the HMAC matches → request is accepted.
6. `StatusHandler#process` runs `Commit.where(sha: "<victim-commit-sha>")`, finds the victim's commit (unrelated to `attacker-org`), and calls `create_status_from_github!`, injecting a fake "success" status that can unlock deploy/merge for `victim-org/victim-repo`.
