### Title
`review_stacks_enabled` gate is bypassable via operator-precedence bug in `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`LabeledHandler#respond_to_label_change?` ANDs `repository.review_stacks_enabled` with the whole label-based decision, so it is a hard top-level gate. `OpenedHandler#provision?` (and `ReopenedHandler#unarchive?`) instead write `repository.review_stacks_enabled && behavior_allow_all? || (behavior_allow_with_label? && has_label?) || (behavior_prevent_with_label? && !has_label?)`, and because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` is only ANDed into the first disjunct (`allow_all`). For a repository configured with `provisioning_behavior: allow_with_label` or `prevent_with_label`, `review_stacks_enabled` is never consulted at all, so the same webhook-driven attacker who is refused by `labeled` can succeed via `opened`/`reopened`.

### Finding Description
Binding under test: for a fixed repository config `(review_stacks_enabled: false, provisioning_behavior: allow_with_label, provisioning_label_name: "pull-requests-label")` and a PR carrying that label, `LabeledHandler#respond_to_label_change?` must equal `OpenedHandler#provision?` (both should be `false`, since the feature is disabled).

Code:
- `LabeledHandler#respond_to_label_change?` [1](#0-0)  unconditionally ANDs `repository.review_stacks_enabled` before evaluating `archive?`/`unarchive?`, which themselves only look at `provisioning_behavior_allow_with_label?`/`provisioning_behavior_prevent_with_label?` [2](#0-1) . So when `review_stacks_enabled` is `false`, the method always returns `false`, regardless of `provisioning_behavior`.
- `OpenedHandler#provision?` [3](#0-2)  is written as `a && b || c || d`, which Ruby parses as `(a && b) || c || d`. Substituting: `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, the `review_stacks_enabled` term is not part of the disjunct that fires, so it has zero effect — the method returns `true` purely from the label check even with `review_stacks_enabled: false`.
- `ReopenedHandler#unarchive?` has the identical structure and the identical bug [4](#0-3) .

Root cause: missing parentheses around `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?` — the author intended `review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`, but Ruby's `&&`/`||` precedence gives a different, weaker result.

Exploit flow: An attacker who has permission to open pull requests against a Shipit-tracked repository (i.e., any external contributor on a public/open repo, or the repo owner themselves) sends/triggers a GitHub `pull_request` `opened` (or `reopened`) webhook with a label matching `provisioning_label_name` (`allow_with_label` case) or without it (`prevent_with_label` case). Even though the repository administrator has explicitly disabled dynamic review-stack provisioning (`review_stacks_enabled = false`) while leaving a non-`allow_all` `provisioning_behavior` set (a state reachable simply by toggling the checkbox off without also resetting the behavior dropdown, both editable independently in `settings.html.erb` [5](#0-4) ), `OpenedHandler#process` proceeds to `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [6](#0-5) , creating (or `ReopenedHandler` unarchiving) a review stack, which subsequently gets queued for provisioning/deploy tasks.

Existing guards do not catch this: webhook signature verification and `drop_unhandled_event` only ensure the payload is a genuine GitHub webhook for a tracked repo/PR — they do not enforce feature-flag semantics, and the `ExplicitParameters` schema only validates payload shape, not business logic. The divergence is purely inside handler business logic.

### Impact Explanation
For a repository whose maintainer has disabled review-stack auto-provisioning (`review_stacks_enabled = false`) but left a stale `provisioning_behavior` of `allow_with_label`/`prevent_with_label`, any user able to open/label/reopen a pull request against that repository can force Shipit to create/unarchive a `ReviewStack` and enqueue its provisioning — an action the operator explicitly opted out of. This is a write for that repository that its own configuration was supposed to prevent, matching the "unauthorized deploy" class of Critical impact, scoped to that specific repository (not cross-tenant) and repeatable on every qualifying PR event.

### Likelihood Explanation
Preconditions: repository must be tracked by Shipit, have `review_stacks_enabled = false` combined with a non-`allow_all` `provisioning_behavior` (a state an operator can reach simply by unchecking the enable box without resetting the dropdown — no unusual admin action required), and the attacker must be able to open/label a PR on it (trivial for any repo accepting external PRs, or for the repo owner's own repo). No secrets, tokens, or elevated Shipit roles are needed. This is easily repeatable — every qualifying `opened`/`reopened`/labeled-matching event reproduces it.

### Recommendation
Fix operator precedence with explicit parentheses so `review_stacks_enabled` gates the entire decision, mirroring `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
test "review_stacks_enabled inconsistently enforced between LabeledHandler and OpenedHandler" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )

  labeled_payload = payload_parsed(:pull_request_labeled)
  labeled_payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }
  labeled_handler = Shipit::Webhooks::Handlers::PullRequest::LabeledHandler.new(labeled_payload)
  assert_equal false, labeled_handler.send(:respond_to_label_change?)

  opened_payload = payload_parsed(:pull_request_opened)
  opened_payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }
  opened_handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(opened_payload)
  assert_equal true, opened_handler.send(:provision?) # bug: bypasses review_stacks_enabled

  assert_no_difference -> { Shipit::Stack.count } do
    labeled_handler.process
  end
  assert_difference -> { Shipit::Stack.count } do
    opened_handler.process
  end
end
```
