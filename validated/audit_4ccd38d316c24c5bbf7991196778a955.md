### Title
`StatusHandler#process` mutates a globally-scoped `Commit`/`Status` row without checking `repository.full_name`, letting a `status` webhook signed for `attacker/repo` write statuses onto a commit belonging to `victim/repo`'s stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that the request was signed with the webhook secret of the GitHub organization named in `payload['repository']['owner']['login']`. `StatusHandler#process` never re-checks that field: it looks up `Commit.where(sha: params.sha)` globally across the entire Shipit installation and writes a `Status` to whatever commit(s) match, regardless of which repository the verified signature belongs to.

### Finding Description
The binding that should hold is: `organization_that_signed(payload) == owner_of_repository(stack_of(commit_mutated))`. Tracing the code shows this equality is never enforced for the `status` event.

- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login')` and validates the HMAC using `Shipit.github(organization: repository_owner)`. This only proves "the sender knows organization `repository_owner`'s webhook_secret" — it says nothing about which specific repository/stack rows may be touched.
- The base `Handler` class *does* provide a correctly scoped accessor: `stacks` derived from `repository_name` (`payload.dig('repository', 'full_name')`) via `Repository.from_github_repo_name(...)` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`). Other handlers use this to scope their work to the repository named in the payload.
- `StatusHandler#process`, however, does not use `stacks`/`repository_name` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
(`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`). `Commit.where(sha:)` is a global, unscoped query across every stack/repository tracked by the Shipit instance; there is no `stack_id`/`repository` filter and no uniqueness constraint on `sha` scoping it to one repository.
- `commit.create_status_from_github!(params)` → `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:23-33`) always uses the **matched commit's own `stack_id`**, i.e. the victim stack, not any stack derived from the payload's `repository` field.

Exploit flow: an attacker who administers a GitHub organization/App that Shipit already trusts (and thus legitimately knows that organization's `webhook_secret`, e.g. via GitHub App settings for `attacker/repo`) crafts a git commit object whose SHA1 collides with an existing `victim/repo` commit already tracked by Shipit (trivial without a hash-collision attack: SHA1 is deterministic over tree, parent, author/committer identities and timestamps, and message — an attacker who can observe/replicate that metadata, e.g. from a public commit, can produce a byte-identical, and thus SHA-identical, commit object under a different repository/parent history using `git commit-tree`). The attacker then POSTs to `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `attacker/repo`'s own organization webhook secret, and a JSON body naming `repository.full_name`/`owner.login` as `attacker/repo` but `sha` equal to the colliding victim commit's SHA. `verify_signature` passes (correctly — the attacker really does know their own secret). `StatusHandler#process` then finds the pre-existing `victim/repo` `Commit` row (created earlier through legitimate victim pushes) purely by `sha` match and appends a `Status` to it, tied to the victim's `stack_id`.

Existing guards do not prevent this: `verify_signature` only authenticates "an org", not "this repository/stack"; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema for `StatusHandler` (`requires :sha`, `:state`, etc.) validates types/presence, not repository ownership; there is no model-level uniqueness constraint scoping `Commit#sha` per repository that would prevent cross-repo sha reuse from being meaningful; and `Handler#stacks`/`repository_name`, which would have correctly scoped the mutation, is simply not invoked by `StatusHandler`.

### Impact Explanation
An attacker who controls only their own repository/organization can inject fabricated CI `Status` rows (state `success`/`failure`/`error`, arbitrary `description`, `target_url`, `context`, `created_at`) onto commits belonging to a victim stack they do not control. Since `Status` creation drives `Commit#state`, `enable_ci_on_stack`, `schedule_continuous_delivery`, and `ProcessMergeRequestsJob` (per `app/models/shipit/status.rb` and `app/models/shipit/commit.rb`), a forged `success` status can push a victim commit toward being eligible for continuous deployment/merge, or a forged `failure`/`error` can block a legitimate deploy — this is "a payload for one repository mutating another's stack, commit" per the Critical impact category. It is repeatable against any stack whose commits' SHAs the attacker can reproduce, and is not limited to a single victim.

### Likelihood Explanation
Preconditions: the attacker must control (or be an administrator of) a GitHub organization/App that is already configured in Shipit's `github:` secrets section (so `Shipit.github(organization: repository_owner)` resolves and their signature is accepted) — this is realistic in any multi-tenant/multi-org Shipit deployment (as documented in `docs/setup.md` "Using Multiple Github Applications"), and the attacker needs no privileges over the victim's repository, team, or Shipit account at all. Producing a SHA1-identical commit object is a low-cost, well-known git technique (no cryptographic collision needed) when the target commit's metadata (tree, parent, author/committer, timestamps, message) is known, e.g. from a public repository. The attack requires only a single HTTP POST per forged status and is trivially repeatable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/stacks derived from the verified payload, mirroring the base `Handler#stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status can only be attached to commits belonging to the stack(s) of the repository named (and cryptographically verified) in the payload.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook for attacker/repo cannot mutate a commit belonging to victim/repo's stack" do
  victim_stack = shipit_stacks(:shipit)              # victim/repo's tracked stack
  victim_commit = shipit_commits(:first)              # belongs to victim_stack

  attacker_org = "attacker"
  attacker_secret = "attacker-secret"
  Shipit.stubs(:github).with(organization: attacker_org).returns(
    Shipit::GithubApp.new(attacker_org, webhook_secret: attacker_secret)
  )

  body = {
    "sha" => victim_commit.sha,           # forged/colliding SHA matching victim's commit
    "state" => "success",
    "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => attacker_org } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, body)

  request.headers["X-Github-Event"] = "status"
  request.headers["X-Hub-Signature"] = signature

  assert_no_difference "victim_commit.statuses.count" do   # EXPECTED after fix; currently FAILS
    post :create, body:, as: :json
  end
end
```
Before the fix, this test fails because `victim_commit.statuses.count` increases by 1 despite the payload only naming and authenticating `attacker/repo`, proving the cross-repository mutation. After scoping `StatusHandler#process` to `stacks` derived from `repository.full_name`, the assertion holds.
