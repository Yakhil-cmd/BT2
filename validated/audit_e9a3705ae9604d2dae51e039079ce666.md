### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository scoping, letting a signed status event for one repository flip statuses on a same-SHA commit belonging to another stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on `repository`/`stack`, unlike every sibling handler (`PushHandler`, `CheckSuiteHandler`, the `pull_request` handlers) which all scope through `stacks`/`from_github_repo_name` before touching records. If two stacks ever contain a `Commit` row with the same `sha` (e.g. shared git history between a fork and upstream, or a mirrored/duplicated repo import), a validly-signed `status` webhook for the attacker's own repository will create a `Status` on the victim's commit too, and on a `continuous_deployment`-enabled stack this feeds directly into `ContinuousDeliveryJob` via `Commit#schedule_continuous_delivery`.

### Finding Description
The broken binding is: **the invariant "a status webhook signed for repository A only affects commits belonging to repository A" is not enforced** — i.e. `Commit#stack.repository.full_name == payload['repository']['full_name']` is never checked.

Trace:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) verifies only that the raw payload is HMAC-signed by `Shipit.github(organization: repository_owner)` — i.e., that some GitHub App installation for that **organization** produced it. It does not check that the `repository.full_name` in the payload corresponds to any particular stack.
- The `Handler` base class exposes a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, and every other handler (`PushHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) uses it before touching any record.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** call `stacks` or `repository_name` at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` against the global `commits` table, matching by bare `sha` only.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally creates a `Status` and re-evaluates `deployable?`/`schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), which enqueues `ContinuousDeliveryJob` if `stack.continuous_deployment?` and `stack.deployable?`.

Exploit flow: an attacker who owns/controls a repository whose organization has the Shipit GitHub App installed can produce a validly-signed `status` event (`context: ci/build`, `state: failure`, arbitrary `sha`) for that repository. If the `sha` also exists as a `Commit` row for a *different*, victim stack — which happens whenever two repositories share commit ancestry (fork vs. upstream before divergence, or byte-identical rebased/cherry-picked commits) — `StatusHandler` will write a `failure` status onto the victim's commit despite the event never having been sent by/for the victim's repository. On a `continuous_deployment`-enabled victim stack this can flip a commit from deployable to blocked (or vice versa for a `success` state) and interacts with `ContinuousDeliveryJob`'s auto-ship logic, forcing an unintended ship/block decision.

None of the existing guards close this gap: `verify_signature` only authenticates the org, not the repository, and it is not repository-scoped by design (`app/controllers/shipit/webhooks_controller.rb:24-49`); `drop_unhandled_event` and `ExplicitParameters` only validate payload shape, not repository binding; there is no `Repository`/`Stack` ownership check anywhere in `StatusHandler`.

### Impact Explanation
A `status` payload authenticated for repository/org A causes a database write (`Status` creation, and downstream `deployable_status`/`ContinuousDeliveryJob` triggering) against a `Commit`/`Stack` that belongs to repository B — i.e., "a payload for one repository mutating another's stack/commit," matching the Critical category (unauthorized deploy/rollback via forced CI-status flip). The blast radius is limited to stacks whose commits happen to share a `sha` with a repo the attacker can emit signed status events for; this is not a general "any SHA can be spoofed for any repo" bug, but a real scoping omission that is trivially reachable whenever such SHA overlap exists.

### Likelihood Explanation
Preconditions: (1) attacker must control (or have write/status access to) a repository under an organization where Shipit's GitHub App is installed, so they can trigger a genuinely GitHub-signed `status` webhook; (2) a `Commit` row with the same `sha` must exist in another, victim stack — realistic for forks sharing history with upstream before divergence, mirrored repositories, or duplicated content commits; (3) the victim stack has `continuous_deployment` enabled and requires/monitors the `ci/build` context. Given these are plausible but non-trivial multi-tenant setups (shared org, shared history), likelihood is moderate rather than universal, but the missing repository check itself is unconditional and code-confirmed.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the repository via `Repository.from_github_repo_name(repository_name)` (or the existing `stacks` helper) and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or a joined query filtering by the commit's `stack.repository`) before calling `create_status_from_github!`, so a status event can never write to a commit outside the repository that authenticated it.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status for repository A does not affect a commit with the same sha in stack B" do
  stack_a = shipit_stacks(:shipit)          # repository: "shopify/shipit-engine"
  stack_b = shipit_stacks(:cyclimse)        # different repository, continuous_deployment: true
  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared history commit")

  # Equality to validate BEFORE: commit_b.statuses.count == 0
  assert_equal 0, commit_b.statuses.count

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'failure', context: 'ci/build',
    repository: { full_name: stack_a.repository.full_name, owner: { login: stack_a.repository.owner } }
  }.to_json

  post :create, body:, as: :json

  # Equality to validate AFTER: expect it to STILL be 0 if properly scoped;
  # the vulnerability manifests when this becomes 1 (status leaked into stack_b's commit)
  assert_equal 0, commit_b.reload.statuses.count
end
```
This directly exercises `StatusHandler#process`'s `Commit.where(sha:)` lookup and demonstrates that a status authenticated only for `stack_a`'s repository writes onto `stack_b`'s commit purely because the SHA collides, with no repository-membership check anywhere in the path.
