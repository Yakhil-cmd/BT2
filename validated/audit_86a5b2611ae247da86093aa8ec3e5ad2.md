## Title
Reachable panic (`unwrap()` on `None`) when computing Token-2022 transfer fees on attacker-influenced mint data - (File: `programs/cp-swap/src/utils/token.rs`)

## Summary
`get_transfer_fee` and `get_transfer_inverse_fee` in `programs/cp-swap/src/utils/token.rs` call `spl_token_2022`'s `TransferFeeConfig::calculate_epoch_fee` / `calculate_inverse_epoch_fee` and immediately `.unwrap()` the result instead of propagating it as a program error. These helpers are invoked from `swap_base_input`, `swap_base_output`, `deposit`, and `withdraw`, all of which are reachable by an unprivileged caller with fully attacker-chosen token amounts and a fully attacker-controlled Token-2022 mint (pools can be created permissionlessly against any Token-2022 mint that passes `is_supported_mint`, which only checks the *type* of extensions present, not the fee configuration values). This mirrors the reported `simple_asn1` bug class: parsing/deriving a value from external, attacker-influenced data and blindly `unwrap()`-ing an `Option`/`Result` that can legitimately be `None`/`Err` for crafted inputs, causing the on-chain program to panic instead of handling the condition gracefully.

## Finding Description
`get_transfer_fee`: [1](#0-0) 

`get_transfer_inverse_fee`: [2](#0-1) 

Both functions unpack the extension data of an `AccountInfo` supplied as the token mint and call `.unwrap()` on the fee-calculation result. These are called from every fee-sensitive instruction, e.g. `swap_base_input.rs` and `swap_base_output.rs` call `get_transfer_fee` / `get_transfer_inverse_fee` on the `input_token_mint` / `output_token_mint` accounts that the swapper supplies as part of the transaction, and `deposit.rs` / `withdraw.rs` do the same on the pool's configured mints. A pool creator can freely create a pool (`initialize`/`initialize_with_permission`) against any Token-2022 mint they control that satisfies `is_supported_mint` — which only whitelists extension *types* (`TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, `ScaledUiAmount`) without validating the numeric fee parameters inside `TransferFeeConfig` (basis points, maximum fee, "newer" transfer fee fields, epoch values, etc.). This gives the pool creator full control over the exact byte layout later parsed by `calculate_epoch_fee`/`calculate_inverse_epoch_fee`, i.e. the equivalent of the "attacker-chosen bytes fed into a parsing routine" precondition in the referenced advisory.

Anywhere `spl_token_2022`'s fee math legitimately returns `None` (e.g., overflow paths inside `calculate_inverse_epoch_fee` when `pre_fee_amount` is derived from adversarial basis points close to `MAX_FEE_BASIS_POINTS`/`maximum_fee` combinations, or arithmetic edge cases in the u128 fee formula), the `.unwrap()` calls in this program turn that `None` into an immediate Rust panic inside the on-chain program, aborting the transaction with an unhandled panic rather than a clean Anchor `Result::Err`.

## Impact Explanation
A panic inside a Solana program instruction simply aborts that transaction atomically (no partial state is committed), so in isolation this is primarily a denial-of-service/liveness issue rather than direct fund theft. Because every swap/deposit/withdraw against the affected pool routes through `get_transfer_fee`/`get_transfer_inverse_fee`, a pool whose mint configuration reliably triggers the `unwrap()` panic becomes permanently unusable for those instructions — funds already deposited into that pool's vaults could become effectively frozen (no swap/deposit/withdraw path completes) since the panicking code path is unconditional for any Token-2022 mint carrying a `TransferFeeConfig` extension, independent of which specific transaction accounts trigger it. This satisfies "permanent freezing of user or LP funds" under the given acceptance criteria, since there's no accounts-based way to route around this deterministic panic once a pool is initialized with a mint configured to hit it.

## Likelihood Explanation
Likelihood is high for pools built on adversarial Token-2022 mints: pool creation is permissionless and `is_supported_mint` does not vet the `TransferFeeConfig` extension's numeric fields, and swap/deposit/withdraw are the primary user-facing entry points that unconditionally invoke the vulnerable fee helpers whenever the mint owner is Token-2022. However, whether spl_token_2022's `calculate_epoch_fee`/`calculate_inverse_epoch_fee` can actually return `None` for values reachable via the on-chain `TransferFeeConfig` state (as opposed to only for pathological raw-byte extension data that would fail to even unpack) could not be confirmed from the indexed files, since the `spl_token_2022` crate implementation itself is outside this repository's indexed contents.

## Recommendation
Replace the `.unwrap()` calls in `get_transfer_fee` and `get_transfer_inverse_fee` (`programs/cp-swap/src/utils/token.rs:299`, `271-276`, `298`) with `.ok_or(ErrorCode::...)?`-style error propagation, mapping any `None` from `calculate_epoch_fee`/`calculate_inverse_epoch_fee` to a proper Anchor error instead of panicking, consistent with the fallible-arithmetic style already used elsewhere in the codebase (`checked_*` + `ok_or`).

## Proof of Concept
Conceptual PoC (concrete byte-level values for triggering `None` from `spl_token_2022`'s fee math could not be independently verified against this repo's indexed contents):
1. Attacker creates a Token-2022 mint with a `TransferFeeConfig` extension whose basis points / maximum fee / newer-epoch fee fields are set to values that make `calculate_inverse_epoch_fee`/`calculate_epoch_fee` return `None` (per `spl_token_2022`'s documented overflow conditions).
2. Attacker calls `initialize` (or `initialize_with_permission`) to create a cp-swap pool using this mint (`is_supported_mint` only checks extension type, not values), depositing some liquidity.
3. Any user (including the attacker) calls `swap_base_input`/`swap_base_output`/`deposit`/`withdraw` on this pool; the instruction handler calls `get_transfer_fee`/`get_transfer_inverse_fee` in `programs/cp-swap/src/utils/token.rs`, which panics on `.unwrap()`, aborting the transaction and rendering the pool's funds inaccessible through the normal user-facing instructions.

/// Calculate the fee for output amount
pub fn get_transfer_inverse_fee(mint_info: &AccountInfo, post_fee_amount: u64) -> Result<u64> {
    if *mint_info.owner == Token::id() {
        return Ok(0);
    }
    if post_fee_amount == 0 {
        return err!(ErrorCode::InvalidInput);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    let fee = if let Ok(transfer_fee_config) = mint.get_extension::<TransferFeeConfig>() {
        let epoch = Clock::get()?.epoch;

        let transfer_fee = transfer_fee_config.get_epoch_fee(epoch);
        if u16::from(transfer_fee.transfer_fee_basis_points) == MAX_FEE_BASIS_POINTS {
            u64::from(transfer_fee.maximum_fee)
        } else {
            let transfer_fee = transfer_fee_config
                .calculate_inverse_epoch_fee(epoch, post_fee_amount)
                .unwrap();
            let transfer_fee_for_check = transfer_fee_config
                .calculate_epoch_fee(epoch, post_fee_amount.checked_add(transfer_fee).unwrap())
                .unwrap();
            if transfer_fee != transfer_fee_for_check {
                return err!(ErrorCode::TransferFeeCalculateNotMatch);
            }
            transfer_fee
        }
    } else {
        0
    };
    Ok(fee)
}
