### Title
Merkle leaf hashing uses the same hash function as internal nodes with no domain separation, enabling node-as-leaf forgery in `is_valid_merkle_proof()` - ([File: merkle.js])

### Summary
`merkle.js` builds the merkle tree and verifies proofs using a single hash function `hash()` for both leaves and internal nodes, with no prefix/tag distinguishing a leaf hash from an internal-node hash. This is the exact bug class reported against NounsBuilder's `mintFromReserve()`: because leaf values are hashed the same way as concatenated child-node pairs, an attacker who knows two sibling hashes in a committed tree can submit a forged "leaf" equal to that concatenation and have it validate as a legitimate tree member.

### Finding Description
`getMerkleRoot`/`getMerkleProof` compute internal nodes as `hash(hash(a) + hash(b))` [1](#0-0)  while leaves passed into `verifyMerkleProof` are hashed via the identical `hash(element)` call with no leaf-specific prefix [2](#0-1) . The code even contains an explicit acknowledgment of this weakness that was never remediated: `// Node-as-Leaf issue might matter in some cases` [3](#0-2) .

This primitive is exposed directly to unprivileged AA trigger senders through the oscript formula function `is_valid_merkle_proof(element, proof)`. Both `element` and the full `proof` object (`root`, `index`, `siblings`) are taken from evaluator-controlled trigger data and passed straight into `merkle.verifyMerkleProof` with no additional structural checks beyond basic type/length limits [4](#0-3) . The grammar/parse rules confirm `is_valid_merkle_proof` is a first-class oscript primitive available to any AA definition author, callable by any trigger sender [5](#0-4) .

Because leaves and internal nodes share an identical hash format (base64-encoded SHA-256 digests concatenated with no separator or leaf/node tag), an attacker who can observe (or reconstruct from a published whitelist/allow-list dataset) any two sibling hashes `H1`, `H2` at some level of the tree can submit `element = H1 + H2` together with a `proof` whose `index`/`siblings` walk that parent node up to the real, expected root. `merkle.verifyMerkleProof` will compute `hash(element) == hash(H1+H2)`, which equals the legitimate internal node value, and the remaining path will correctly reproduce the root — even though `H1+H2` was never an actual whitelisted leaf value.

### Impact Explanation
Any AA that implements a merkle-gated claim/whitelist pattern (e.g., an AA-managed reserve that pays out to addresses proven to be in a committed merkle root via `is_valid_merkle_proof`, mirroring the `mintFromReserve()` pattern) is vulnerable to having its membership check bypassed by a forged, non-whitelisted "leaf" value. Depending on how the AA parses/uses `element`, this can enable unauthorized claims against AA-held funds (AA fund loss), which meets the required impact bar for this analog.

### Likelihood Explanation
Exploitation requires only that the attacker know two adjacent hashes inside the committed tree, which for any merkle-gated allow-list is normally public information (the full leaf set / tree is typically distributed off-chain so legitimate users can generate their own proofs). No privileged access, node compromise, or network-level capability is needed — a single crafted AA trigger from an ordinary, unprivileged user is sufficient to invoke `is_valid_merkle_proof` with the forged inputs.

### Recommendation
Add domain separation between leaf and internal-node hashing in `merkle.js`, e.g. prefix leaves with a distinct tag/byte (such as `0x00`) and internal nodes with another (`0x01`) before hashing, so a leaf hash can never collide in structure with an internal node's hash input, consistent with the OpenZeppelin `MerkleProof` guidance cited in the original report.

### Proof of Concept
1. Oracle/AA author builds a merkle tree over whitelist entries `[e0, e1, e2, e3, ...]` using `merkle.getMerkleRoot` and publishes/distributes the tree (as is standard for allow-list claim designs) [1](#0-0) .
2. Attacker (not an `ei` whitelist member) computes `H1 = hash(e0)`, `H2 = hash(e1)` from the public data and forms `forgedLeaf = H1 + H2` (this equals the real internal parent node's preimage).
3. Attacker sends an AA trigger unit whose `data` contains `element = forgedLeaf` and `proof = { index: <parent's index>, siblings: <the siblings from that level up>, root: <the real committed root> }`.
4. The AA's oscript calls `is_valid_merkle_proof(trigger.data.element, trigger.data.proof)` [6](#0-5) , which internally calls `merkle.verifyMerkleProof(forgedLeaf, proof)`; since `hash(forgedLeaf) == hash(H1+H2)` equals the genuine internal node hash, the walk up the remaining siblings reproduces `root` exactly, and the function returns `true` even though `forgedLeaf` was never an authorized whitelist entry [2](#0-1) .
5. If the AA's payout logic trusts this boolean as sufficient membership proof (as `mintFromReserve()` did), the attacker can claim funds/rewards intended only for genuine whitelist members.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
