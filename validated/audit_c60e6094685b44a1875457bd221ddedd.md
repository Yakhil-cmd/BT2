### Title
Cross-organization webhook authentication/write binding confusion enabling forged commit-status and sync events on another tenant's stack — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate a webhook against using an attacker-supplied field from the very payload being verified, while the handlers that actually act on that payload (write commit statuses, enqueue syncs) resolve the target repository/stack from a *different* field of the same payload. Neither value is cross-checked against the other, so the "organization whose secret authenticated the request" and "the repository that gets written to" are never proven to be the same tenant.

### Finding Description
`verify_signature` derives the signing organization purely from the request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` then loads a *per-organization* secret from `secrets.github` in multi-tenant configurations (`github_app_config`/`github_organizations`): [3](#0-2) 

Once `verify_webhook_signature` succeeds (HMAC-SHA1 over the *entire* raw body using that organization's `webhook_secret`), the raw JSON is dispatched to handlers: [4](#0-3) 

Every handler independently resolves the target `Stack`/`Repository` from a *separate* JSON field, `repository.full_name`, with no relation back to the `repository.owner.login`/`organization.login` value that was used for signature-org selection: [5](#0-4) 

Because the whole raw body is attacker-constructed (this is a forged HTTP request to Shipit, not a real GitHub delivery), an attacker who knows the `webhook_secret` for *any one* organization configured on a shared Shipit instance (e.g., their own tenant org, in the documented multi-org `secrets.github` schema) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org "A" so `verify_signature` selects Org A's `GitHubApp`/secret and signs the request with it — passing verification.
2. Set `repository.full_name` inside the same body to a repository belonging to an unrelated Org "B" that Shipit also hosts.

`verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner, and `Handler#repository_name`/`stacks` blindly trusts `full_name` to pick the `Stack` to mutate.

This is the exact equality-break called for: *"an organization that authenticated versus the repository that is written."* Before the attack: Org A's key authenticates only requests intended for Org A's repositories. After the attack: Org A's key authenticates a request whose payload claims a wholly different Org B repository, and Shipit acts on Org B's `Stack` anyway.

### Impact Explanation
Concretely reachable handlers include:
- `StatusHandler`, which writes GitHub commit statuses directly from unauthenticated-relative-to-target-org payload fields onto any tracked commit — allowing an attacker to forge a passing CI status (e.g. `"state":"success"`) on a commit in Org B's stack, which can defeat `ci.require`/`ci.blocking` deploy gating documented in `README.md` and enable an unauthorized deploy of that commit.
- `PushHandler`, which calls `stack.sync_github(expected_head_sha: params.after)` for the target stack derived from the forged `repository.full_name`/`ref`, letting the attacker drive sync/refresh behavior on a stack they have no GitHub permissions over. [6](#0-5) [7](#0-6) 

Since this can result in an unauthorized deploy of a commit into an organization the attacker does not control (by forging a passing CI status that gates the merge/deploy pipeline), this meets the Critical bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires a multi-organization Shipit deployment (supported natively via `Shipit.github_organizations`/`github_app_config`) where the attacker legitimately administers (or otherwise knows the `webhook_secret` for) at least one hosted organization, while a different, unrelated organization's repositories are also tracked by the same Shipit instance. No GitHub write access, `ApiClient` token, or victim-org secret is required — only knowledge of any one tenant's webhook secret plus the ability to send a crafted HTTP POST to `/webhooks`.

### Recommendation
After `verify_webhook_signature` succeeds, `WebhooksController`/`Handler` must additionally assert that the organization/owner used to select the signing secret is the same organization that owns `repository.full_name` (and any other repository identifier the handler subsequently trusts) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Attacker administers Org A on a shared Shipit instance and knows Org A's configured `webhook_secret`.
2. Attacker crafts a JSON body: `{"action":"...","sha":"<victim-sha>","state":"success","repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"OrgA"`, loads OrgA's `GitHubApp`, and the HMAC check passes because the attacker signed with OrgA's known secret [1](#0-0) .
5. `StatusHandler` resolves the stack via `repository.full_name = "OrgB/victim-repo"` and writes a forged successful status onto `<victim-sha>` in Org B's stack, with no relation ever checked back to `"OrgA"`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
