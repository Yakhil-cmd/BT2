### Title
Cross-organization webhook forgery bypasses repository binding — signature verified against the wrong org's secret while payload writes to another org's repository (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using `repository_owner`, a value read directly out of the unverified JSON body [1](#0-0) , itself derived from `params.dig('repository', 'owner', 'login')` [2](#0-1) . Downstream handlers, however, determine which `Repository`/`Stack` to actually mutate using a *different* field of the same payload: `payload.dig('repository', 'full_name')` [3](#0-2)  or `params.repository.full_name` [4](#0-3) . Nothing ties the org whose secret validated the signature to the org named in `repository.full_name`.

### Finding Description
This is the same bug class as the report's `getPrice()` analog: a value that is *acted upon* (here, `repository.full_name`, which selects the target `Stack`/`Repository` to write to) is never cross-checked against the value that was *authenticated* (here, `repository.owner.login`, which selects the HMAC secret). The signature only proves "the sender knows Org A's `webhook_secret`" — it says nothing about which organization's data the JSON body actually references, because HMAC-SHA1 over the raw body is a proof of possession of the secret, not a semantic binding between the secret's owner and the `full_name` field the handlers trust.

Root cause, in equality-of-bindings terms:
- Verified binding: `signature == HMAC(webhook_secret[repository.owner.login], raw_body)` [5](#0-4) 
- Acted-upon binding: `target_stack == Repository.from_github_repo_name(repository.full_name)` [3](#0-2) 

These are two independent fields inside the same attacker-controllable body. An attacker who legitimately controls (or created) a GitHub App installed for Org A — and thus knows Org A's `webhook_secret` — can construct an arbitrary JSON payload with `repository.owner.login = "OrgA"` (so `verify_signature` selects and validates against OrgA's secret) but `repository.full_name = "OrgB/target-repo"` (so the handler operates against Org B's Stack). Since the attacker computes the HMAC themselves over the whole forged body, the signature check passes even though GitHub never produced this payload.

### Impact Explanation
Any webhook handler keyed off `repository.full_name` can be triggered against a Stack belonging to an organization the attacker has no access to:
- `PushHandler` invokes `stack.sync_github(expected_head_sha: ...)` for the target org's stacks/branches [6](#0-5) .
- `StatusHandler` writes a forged commit status (`state`, `context`, `description`) for arbitrary commit SHAs, which can be used to make CI/deploy gating checks appear green on another org's stack [7](#0-6) .
- `PullRequest::OpenedHandler` can trigger review-stack provisioning for another org's repository [8](#0-7) .

This is a cross-repository write crossing an organizational trust boundary using a webhook the receiving org never sent, satisfying the "cross-repository writes" / status manipulation that can enable an unauthorized deploy path (forged passing status feeding deploy gating).

### Likelihood Explanation
Requires the attacker to control one legitimate, low-privilege GitHub App/organization already configured in the multi-org Shipit `secrets.yml` (i.e., they know their own org's `webhook_secret`) — no Shipit session, API token, or GitHub write access to the victim organization/repository is needed. This is exactly the "unprivileged attacker" model in scope: they break the binding between "organization that authenticated" and "repository that is written."

### Recommendation
After `verify_webhook_signature` succeeds using the secret selected by `repository.owner.login`, validate that `repository.full_name`'s owner segment matches `repository.owner.login` (or otherwise re-derive the target org strictly from the same field used for verification) before handlers resolve `Repository.from_github_repo_name`. Reject payloads where these fields disagree.

### Proof of Concept
1. Configure two orgs in `secrets.yml` per `docs/setup.md`'s multi-org section: `orgA` (attacker-controlled app, known `webhook_secret`) and `orgB` (victim, unrelated secret).
2. Attacker crafts body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC validates successfully [1](#0-0) .
5. `PushHandler#process` resolves stacks via `repository.full_name = "orgB/victim-repo"` [3](#0-2)  and triggers `sync_github` on Org B's stack, despite the attacker having no relationship to Org B.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
