## Analysis Result

Looking for a GLPI-style "endpoint deletes an object by ID without checking the caller actually owns/is-a-party-to it," I found a matching pattern in `ocore`'s shared-address negotiation protocol.

### Title
Arbitrary Deletion of Pending Shared-Address State via `reject_new_shared_address` Device Message - ([File: wallet.js])

### Summary
The `reject_new_shared_address` message handler deletes rows from `pending_shared_addresses` / `pending_shared_address_signing_paths` using only an attacker-supplied `address_definition_template_chash`, without ever verifying that the sending device (`from_address`) is actually one of the cosigners participating in that pending multi-signature address setup.

### Finding Description
In `wallet.js`, the hub-message dispatcher handles the `"reject_new_shared_address"` case by validating only that `address_definition_template_chash` looks like a valid c-hash, then immediately calling the deletion routine with no ownership check: [1](#0-0) 

That routine performs an unconditional delete keyed solely by the chash: [2](#0-1) 

This is inconsistent with the sibling flow for multi-device *wallets*, where the analogous decline handler (`cancel_new_wallet` → `deleteWallet`) explicitly checks that the rejecting `from_address` is a genuine, not-yet-approved member before deleting any rows: [3](#0-2) 

`deletePendingSharedAddress` has no equivalent membership/ownership check — any paired correspondent device that learns or observes a `definition_template_chash` (e.g., because it is itself one of several proposed cosigners in `pending_shared_address_signing_paths`, or is otherwise a device paired with the victim) can wipe out another party's in-progress multi-signature address negotiation for an address it is not authorized to affect.

Compare with `approve_new_shared_address`, whose handler passes `from_address` into `approvePendingSharedAddress`, which then scopes the SQL `UPDATE` to `WHERE definition_template_chash=? AND device_address=?`: [4](#0-3) 
No such `device_address` scoping exists on the delete path.

### Impact Explanation
An unauthorized correspondent device can destroy the shared/multisig-address creation process for other users mid-negotiation (a denial-of-service/griefing on address setup), forcing victims to restart multi-party address creation and potentially delaying or preventing funds from being routed to a jointly-controlled address. This is a lower-severity griefing/DoS on wallet bookkeeping rather than a consensus-breaking bug — it does not directly cause unauthorized spending, double-spend, supply inflation, AA fund loss/freezing of already-existing on-chain funds, or network-wide validity/stability disagreement, since `pending_shared_addresses` rows represent addresses that have not yet been finalized/funded.

### Likelihood Explanation
Exploitation requires the attacker to be a paired correspondent device (per the "paired device can reach" scope) and to know the target `definition_template_chash`, which is exposed to any device already invited to co-sign the same template (via `sendOfferToCreateNewSharedAddress`), making it directly exploitable by a malicious/compromised cosigner without needing to guess a random hash.

### Recommendation
Scope the delete in `deletePendingSharedAddress` to the requesting device, mirroring `approvePendingSharedAddress`'s and `deleteWallet`'s pattern: require and check that `from_address` appears as a `device_address` in `pending_shared_address_signing_paths` for the given `definition_template_chash` before performing the delete (and only delete the that device's own signing-path row, or the whole pending address only if it is the initiator).

### Proof of Concept
1. Device A initiates `create_new_shared_address` template involving cosigner devices B and C; B and C each receive the offer along with `address_definition_template_chash` via `sendOfferToCreateNewSharedAddress`.
2. Malicious device B, instead of approving/rejecting only its own participation, sends `{"subject":"reject_new_shared_address", "body":{"address_definition_template_chash": <chash>}}` to the hub targeting device C (or simply to itself, since the handler applies globally regardless of sender identity/scope).
3. `wallet.js` case `"reject_new_shared_address"` calls `walletDefinedByAddresses.deletePendingSharedAddress(chash)` with no check of `from_address` against the pending signing paths.
4. All rows in `pending_shared_addresses` and `pending_shared_address_signing_paths` for that `chash` are deleted, aborting the multi-party address creation for every legitimate participant, even though device B (or an unrelated third device) had no authority to cancel it on their behalf.
