### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` by SHA alone (`Commit.where(sha: params.sha)`), never checking that the webhook's `repository.full_name` matches the repository owning that commit's stack. Any repository whose webhook is validly signed can therefore write a `Status` row (with attacker-chosen `context`) against a commit that lives in a completely different stack, as long as a commit with the same SHA exists there.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: `commit.stack.repository.full_name` (the repository that actually owns the target `Commit`) must equal `payload.dig('repository', 'full_name')` (the repository that authenticated and sent the webhook). The code never performs this comparison.

Trace:
- `WebhooksController#verify_signature` only checks that the payload is signed by the GitHub App/webhook secret associated with `repository_owner` (`params.dig('repository','owner','login')`) via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) . This proves the payload came from *some* repo whose owner/org is configured in Shipit and matches a valid webhook secret for that org — it does **not** prove the payload came from the specific repository that owns the target `Commit`/`Stack`.
- `Handler` exposes a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, explicitly binding processing to the repository that sent the webhook [2](#0-1) .
- `StatusHandler#process` does **not** use this `stacks` helper. It instead does a global, unscoped lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
- `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using `stack_id` taken from whichever `Commit` row matched by SHA, not from anything derived from the webhook's own repository [4](#0-3) .
- `Status.replicate_from_github!` writes the record with the attacker-supplied `context`, `state`, `description`, `target_url` verbatim [5](#0-4) .

Exploit flow: since git commit SHAs are content-addressed, an attacker can fetch a real, already-known commit from the victim's repository (public commit, PR commit, etc.) and push that identical commit object into a repository they control (a fork, or a new empty repo they create), producing an identical SHA. If that attacker-owned repository belongs to (or the GitHub App/webhook secret is configured at) an organization/owner already registered with Shipit — a very common single-org-wide GitHub App setup — the attacker can trigger (via GitHub Status API on their own repo, which any repo owner/collaborator can do without any Shipit privilege) a `status` webhook carrying `context: "soc/compliance"`, `state: "success"`. `verify_signature` passes because the signature is valid for that owner/org; `StatusHandler#process` matches the commit by SHA regardless of which repository actually sent the event, and writes a `Status` onto the *victim's* stack/commit.

Existing guards fail to stop this because: (1) `verify_signature` authenticates only "this owner/org sent a validly signed webhook," never "this specific repository owns this commit"; (2) the `stacks`/`repository_name` binding pattern that other handlers use is simply not applied in `StatusHandler`; (3) no model validation ties a `Status`'s `context`/`stack_id` back to `payload['repository']['full_name']`.

### Impact Explanation
A forged `Status` with an attacker-chosen `context` string (e.g. `soc/compliance`, `security/code-review`) is written against a commit in a stack the attacker does not control. `Stack#blocking_statuses` / `DeploySpec#merge_request_required_statuses` match purely by `context` string, so this satisfies `ci.blocking`/`merge.require` checks without the real check ever running, unblocking `Commit#deployable?` and merge automation for that commit. This is a payload from one repository mutating another repository's commit/stack state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Preconditions: (a) the victim stack's `shipit.yml` lists the spoofed `context` under `ci.blocking` or `merge.require`; (b) a commit with the exact same SHA as a real commit in the victim's stack must exist, which is trivial for any commit the attacker can read (public repos, PRs, forks — content-addressed SHAs reproduce exactly when the same tree/parents/timestamps are re-pushed); (c) the attacker's own repository must produce a webhook whose signature validates against the org/owner login Shipit has configured (`Shipit.github(organization: repository_owner)`), which is satisfied for any repo under an org that Shipit already trusts with one shared GitHub App/webhook secret — a standard org-wide installation model. No Shipit session, token, or maintainer role is needed; the attacker only needs push/API access to a repository they own. The attack is repeatable against any commit/stack whose SHA the attacker can reproduce.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the sending repository, e.g. use the existing `stacks` helper: resolve `stack = Repository.from_github_repo_name(repository_name)&.stacks` and restrict `Commit.where(sha: params.sha, stack_id: stack.ids)` (or equivalent join) before calling `create_status_from_github!`, so a status can only be attached to a commit belonging to the exact repository that sent the webhook. Apply the same fix to `CheckRunHandler`/other SHA-keyed handlers if they exhibit the same pattern.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from an unrelated repository cannot forge a required check on another stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(cached_deploy_spec: victim_stack.cached_deploy_spec.to_h.deep_merge(
    'ci' => { 'blocking' => ['soc/compliance'] }
  ))
  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit', author: shipit_users(:walrus))

  # Simulate a status webhook whose payload.repository.full_name is an attacker-owned,
  # unrelated repository, but which shares the same commit SHA.
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'soc/compliance',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  assert_includes victim_stack.reload.blocking_statuses.map(&:context), 'soc/compliance' # before: still blocking
  refute victim_commit.reload.deployable?

  Shipit::Webhooks::Handlers::StatusHandler.call(ExplicitParameters::Parameters.new(payload))

  refute_includes victim_stack.reload.blocking_statuses.map(&:context), 'soc/compliance' # after: forged status satisfied it
  assert victim_commit.reload.deployable?
end
```
This demonstrates the equality `commit.stack.repository.full_name == payload['repository']['full_name']` is false yet the status is still accepted and applied to `victim_stack`, flipping `blocking_statuses`/`deployable?`.
