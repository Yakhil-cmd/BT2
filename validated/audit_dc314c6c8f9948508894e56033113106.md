### Title
`StatusHandler#process` writes `CommitStatus` records for any SHA with no repository/org ownership check - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by raw SHA (`Commit.where(sha: params.sha)`) without ever consulting `Handler#stacks`/`#repository_name`, unlike every other handler in the same directory. Since `WebhooksController#verify_signature` only proves the payload was signed by `repository_owner`'s org, not that the named `sha` belongs to that org's repository, an attacker who controls a verified GitHub org (org-attacker) can forge a status for a commit SHA belonging to a completely unrelated victim org's stack.

### Finding Description
The binding that should hold is: `CommitStatus.commit.stack.repository.full_name == payload['repository']['full_name']` (the repository that authenticated the payload via `verify_signature`/`webhook_secret` must be the same repository whose commit gets a new status). This is exactly what `Handler#stacks` enforces for other handlers via `Repository.from_github_repo_name(repository_name)&.stacks`: [1](#0-0) 

`StatusHandler#process`, however, never calls `stacks` or `repository_name`: [2](#0-1) 

It instead does a global lookup `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every matching row, database-wide, regardless of which stack/repository/org that commit belongs to.

`WebhooksController#verify_signature` only checks that the payload signature matches the webhook secret configured for `repository_owner` (derived from the payload's own `repository.owner.login`/`organization.login`), i.e. it proves "this payload came from org X," not "the sha in this payload belongs to a commit under org X's stack": [3](#0-2) 

Exploit flow:
1. Attacker owns/administers a repository under org-attacker, which is a legitimate, verified Shipit org (has a configured `webhook_secret`).
2. Attacker learns victim commit SHAs from GitHub's public API (SHAs are content-addressed and public regardless of org).
3. Attacker sends a `status` webhook event to `POST /webhooks` with `X-Github-Event: status`, a valid signature for org-attacker, and `sha` set to a SHA of a `Commit` that actually belongs to org-victim's `Stack`.
4. `verify_signature` passes because the signature is valid for org-attacker's secret and `repository_owner` in the payload legitimately resolves to org-attacker.
5. `StatusHandler.call` → `#process` finds the `Commit` with that SHA regardless of repository, and calls `commit.create_status_from_github!(params)`, writing a `CommitStatus` for org-victim's commit — attributed entirely to the attacker's forged state (`error`, `failure`, `success`, etc.).
6. This directly affects `Commit#status`, `Commit#blocked?`/`#deployable?` (via `stack.blocking_statuses`, `stack.required_statuses`) and `Stack#deployable?`, enabling either forced CI-bypass (marking failing commits `success`) or denial of legitimate deploys (marking passing commits `failure`/`error`) on a stack the attacker has no relationship to.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, `require_permission!`) check that the sha's owning repository matches the payload's repository — that check exists only as `Handler#stacks`, which `StatusHandler` bypasses entirely.

### Impact Explanation
Any org with a valid Shipit webhook integration (a normal, unprivileged tenant relative to other tenants) can forge `CommitStatus` writes on **any** commit in the entire Shipit database, across arbitrary victim stacks/orgs, purely by knowing a SHA (trivially public via GitHub's API). This can flip `Commit#deployable?`/`Stack#deployable?` to force or block deploys for orgs the attacker has no legitimate access to — this is a cross-tenant authorization bypass and unauthorized-deploy-enabling primitive, matching the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions are minimal and cheap: the attacker needs any legitimate GitHub org onboarded to the target Shipit instance with a valid `webhook_secret` (i.e., they must be a real but unprivileged tenant of the same Shipit install), and knowledge of a target commit SHA (public via GitHub for public repos, or leaked/guessable in other ways for private ones). No GitHub App private key, `secret_key_base`, or victim `webhook_secret` is required. This is trivially repeatable against arbitrary victim commits/stacks by just enumerating known SHAs.

### Recommendation
Have `StatusHandler#process` scope its `Commit` lookup through `stacks`/`repository_name`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern used by `PushHandler` and other handlers, so a status can only be applied to commits belonging to the repository that authenticated the webhook payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack`s under two different `Repository`s (`org-attacker/repo-a`, `org-victim/repo-b`), each with a webhook secret configured (or `Shipit.github(organization:)` stubbed for both).
2. Create a `Commit` under `org-victim`'s stack with a known `sha` (e.g. `"deadbeef" * 5`).
3. Build a `status` payload where `payload['repository']['full_name'] == 'org-attacker/repo-a'` (i.e., verified/signed for org-attacker) but `payload['sha']` equals the victim commit's sha, with `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing HTTP layer, as the vulnerability is inside the handler regardless of successful signature verification).
5. Assert: `victim_commit.reload.statuses.last.state == 'success'` even though `victim_commit.stack.repository.full_name != payload['repository']['full_name']` — i.e., assert the binding `commit.stack.repository.full_name == payload['repository']['full_name']` is false while the `CommitStatus` was still written.
6. Additionally assert `victim_stack.deployable?` (or `victim_commit.deployable?`) changes as a result of the forged status, demonstrating downstream deploy-eligibility impact for org-victim caused by an org-attacker-signed payload.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
