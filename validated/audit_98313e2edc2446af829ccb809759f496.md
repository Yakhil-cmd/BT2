### Title
API client scoped to a single stack can read any stack's CI/build status via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper that the rest of the API relies on for per-token stack scoping, resolving `stack` directly against the global `Stack` table instead of the API client's authorized stack set. This lets any `ApiClient` restricted to a single stack read the CI status of every other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` establishes the authorization binding: a token that is scoped to a stack (`ApiClient#stack_id`) may only touch that stack. [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and every other API controller resolves its target stack through `stacks.from_param!(...)`, so the permission check (`require_permission :read, :stack`) is only meaningful in combination with this scoping. [2](#0-1) 

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving the resource straight from `Stack` (unscoped): [3](#0-2) 

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks the flat `"read:stack"` string against the client's permission list — it never checks which stack the client is bound to: [4](#0-3) 

So the equality the engine is supposed to enforce is:
```
token.stack_id (the single stack the token authorizes)  ==  stack (the record the action actually touches)
```
For every other API controller this holds because `stack` is derived from the scoped `stacks` relation. In `CCMenuController` it is broken: `stack` is derived from `params[:stack_id]` against the entire `Stack` table, so `token.stack_id != stack` is achievable by simply passing a different `stack_id` in the URL.

The controller also supports token-in-query-string authentication (`ApiClient.authenticate(params[:token])`) for the CCMenu XML feed, which is expected for embedding in CI dashboards, but this only strengthens the reachability of the bug since the token doesn't need to be sent via an Authorization header. [5](#0-4) 

### Impact Explanation
The `show` action renders `deploys_and_rollbacks.last`'s id, status (`running?`) and completion time (`ended_at`) for the target stack, via the CCMenu XML template. [6](#0-5) 
An `ApiClient` created with `stack_id` set (the mechanism Shipit provides specifically to restrict a token to one stack/repository, as exercised in tests) is meant to see only that stack. [7](#0-6) 
By hitting `/api/stacks/:any_other_stack/ccmenu` with such a token, an attacker who holds a legitimately-issued, narrowly-scoped token can read the deploy/task state (running vs. idle, latest deploy id, timing) of every stack in the Shipit instance, not just the one it was authorized for. This is an authorization-scope bypass yielding unauthorized read of stack/task state across repositories, which matches the "escalation ... unauthenticated read of stack state, task streams or deploy output" class of impact — here achieved by escalating a single-stack token into a cross-stack read.

### Likelihood Explanation
Any holder of a stack-scoped API token (a routine, low-privilege credential intentionally restricted to one repository/environment) can exploit this with a single GET request, no special conditions or timing required. The route is a normal, documented part of the API (`GET /api/stacks/:stack_id/ccmenu`), so likelihood is high once any such scoped token exists — which is the entire purpose of `ApiClient#stack_id`.

### Recommendation
Make `CCMenuController#stack` honor the same scoping as the rest of the API by resolving through `stacks.from_param!(params[:stack_id])` (the scoped relation from `BaseController`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token can never resolve a stack outside `current_api_client.stack_id`.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack A>` with `permissions: ["read:stack"]` (exactly as `here_come_the_walrus` fixture demonstrates). [8](#0-7) 
2. Using that token (via Basic Auth or `?token=`), request `GET /api/stacks/<owner>/<repo-B>/<env>/ccmenu`, where `repo-B` is an entirely different stack the token was never granted access to.
3. `authenticate_api_client` succeeds because the token is valid and has `read:stack` permission.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning stack B regardless of `current_api_client.stack_id`.
5. `show` renders stack B's latest deploy/rollback id, running status and end time in the XML response — data the token was never authorized to see.
