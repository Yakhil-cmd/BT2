### Title
`identify_user` trusts unsigned `X-Shipit-User` header verbatim to attribute actions, allowing any legitimately-scoped API-token holder to impersonate an arbitrary existing GitHub user - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController#identify_user` sets `current_user` by looking up any user whose `login` matches the client-supplied `X-Shipit-User` header, with no cryptographic binding to the authenticated `ApiClient`. Any caller holding a valid API token with the operation's required permission (e.g. `deploy:stack` for `TasksController#trigger`) can set this header to another user's GitHub login and have all resulting records (tasks, deploys, locks) attributed to that impersonated user instead of the token's actual creator.

### Finding Description
The identity binding that should hold is: `current_user == ApiClient#creator` (or some value cryptographically tied to the authenticated token), not an arbitrary attacker-supplied string. Instead: [1](#0-0) 

`authenticate_api_client` only validates the bearer token via `ApiClient.authenticate` (HMAC-verified via `SimpleMessageVerifier`) and checks the token's `permissions` array: [2](#0-1) [3](#0-2) 

Nothing in this chain ties `X-Shipit-User` to the token's `creator` or restricts who may set it. `TasksController#trigger` requires only `deploy:stack` and passes `current_user` straight into `stack.trigger_task`: [4](#0-3) 

Exploit flow: an attacker who legitimately owns (or has been issued) an `ApiClient` token with `deploy:stack` permission (the specific permission scope is irrelevant to the bug — any endpoint reading `current_user` is affected) sends `POST /stacks/:id/tasks/trigger` with `Authorization: Basic <valid token>` and header `X-Shipit-User: <victim-login>`. `identify_user` resolves `current_user` to the victim's `User` record purely from the header string, and the created `Task`/`Deploy` is attributed to (`requested_by`/`user`) the victim rather than the actual authenticated token holder.

None of the listed guards prevent this: `authenticate_api_client` validates the token signature and scope permissions only, not identity; `require_permission!`/`check_permissions!` check operation scope, not user identity; there is no `verify_signature` or per-header authentication for `X-Shipit-User`.

### Impact Explanation
Any holder of a valid API token can forge attribution of deploys, rollbacks, task triggers, locks, or merge requests to any existing Shipit/GitHub user by name, without that user's knowledge or consent — this is an authentication/identity-binding bypass affecting attribution integrity across all `Api::BaseController` subclasses that read `current_user` (`TasksController`, `LocksController`, `RollbacksController`, `ReleaseStatusesController`, `MergeRequestsController`, `DeploysController`). This matches the Critical category ("unauthorized deploy, rollback... attributed" / authentication bypass of identity), since it lets an attacker cause real deploy/task-trigger actions to be falsely and repeatably attributed to arbitrary victims, undermining audit trails and any authorization logic that depends on `current_user` identity (e.g. `User#authorized?` checks downstream, if any exist on top of `current_user`).

### Likelihood Explanation
The attacker needs a valid `ApiClient` token with the permission required by the target endpoint (e.g. `deploy:stack`) — this is a normal precondition of using the API, not a privileged Shipit role. No GitHub secrets, session, or maintainer status is required. The header is trivially set on any HTTP client; the exploit is fully repeatable against any stack the token has scope over and any existing login string, at zero additional cost per request.

### Recommendation
Do not resolve `current_user` from a fully attacker-controlled, unsigned header on general API requests. Either remove the `X-Shipit-User` impersonation mechanism entirely for token-authenticated requests, or restrict it to a narrowly trusted, separately-authenticated internal integration path (e.g., only honor the header when `current_api_client` is a specially flagged trusted first-party client, and validate that the resolved user is the token's `creator` or is otherwise authorized to be attributed). At minimum, require `X-Shipit-User` to match `current_api_client.creator.login` unless the client is explicitly marked as allowed to impersonate.

### Proof of Concept
```ruby
test "trigger attributes task to X-Shipit-User rather than the actual token creator" do
  actual_owner = shipit_users(:walrus)
  victim = shipit_users(:mrspechal) # or another fixture user
  api_client = create_api_client(permissions: %w[read:stack deploy:stack], creator: actual_owner)

  post "/stacks/#{@stack.to_param}/tasks/trigger",
    params: { task_name: 'restart' },
    headers: {
      'Authorization' => "Basic #{api_credentials(api_client)}",
      'X-Shipit-User' => victim.login
    }

  assert_response :accepted
  task = @stack.tasks.last
  # Broken binding demonstrated: attribution equals the impersonated victim,
  # not the token's actual creator.
  assert_equal victim, task.user
  refute_equal actual_owner, task.user
end
```
