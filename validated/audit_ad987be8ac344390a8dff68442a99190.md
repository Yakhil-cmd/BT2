### Title
Shared, feed-keyed `last-update` timestamp lets a caller for one asset grief price resolution for every other asset sharing the same oracle feed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar`'s oracle-freshness check enforces monotonicity (`ts >= prev`) against a single `last-update` map that is keyed only by the raw oracle feed `{type, ident}`, not by the Zest asset ID. Because multiple distinct assets (e.g. wSTX, zSTX, stSTX, zstSTX, stSTXbtc, zstSTXbtc) are all registered against the same `STX-FEED-ID`, any unprivileged caller who advances that shared timestamp while operating on one asset can cause an unrelated later transaction that legitimately tries to use a different asset on the same feed to revert, even though that second asset's own price data is otherwise fresh and valid. This is the same "unchecked cross-field ordering constraint on shared state" root cause as the referenced ERC721Vestable `vestingStart`/`vestingEnd` bug, just applied to a shared oracle timestamp instead of a shared vesting window.

### Finding Description
Multiple assets are intentionally registered with the identical oracle `ident`/`type` pair but different `callcode` (and potentially different `max-staleness`), because they derive their price from the same base feed: [1](#0-0) 

The freshness check performed on every price resolution is: [2](#0-1) 

and it is applied per-feed against a map keyed only by `{type, ident}`, updated forward whenever any caller supplies a newer timestamp for that key, regardless of which asset ID triggered it: [3](#0-2) 

Because `last-update` is shared across every asset that points at the same feed identity, a transaction that resolves price for asset A (say, wSTX) with a Pyth update timestamp `T1` unconditionally advances the map entry for `STX-FEED-ID` to `T1` (line 391-393: "if newer, map-set"). Any subsequent transaction that tries to resolve price for a different asset B on the same feed (say, stSTX or stSTXbtc) using a price update whose timestamp is `< T1` — which can legitimately happen if that asset's own relayed price update lags behind, or if a user/attacker intentionally submits the freshest available update for asset A first — will fail `(>= ts prev)` and revert with `ERR-ORACLE-INVARIANT`, even though asset B's own price is well within its `max-staleness` window on its own terms.

This is structurally identical to the referenced bug: there, `vestingStart` could be pushed past `vestingEnd` by one setter without checking the other, breaking `vestingDuration` math relied on by every token transfer. Here, the shared `last-update` value can be pushed forward by any caller acting on asset A without any cross-check against what asset B (sharing the same feed) can currently supply, breaking price resolution relied on by every other user's operation (borrow, repay, withdraw, liquidate) on asset B.

### Impact Explanation
This causes temporary freezing of funds: legitimate borrow, repay, collateral withdrawal, and liquidation calls for any asset sharing a griefed feed key will revert with `ERR-ORACLE-INVARIANT` until a price update with timestamp `>= last-update` for that feed becomes available and is submitted. During liquidation-critical windows (e.g. a price crash), an attacker could deliberately submit the freshest obtainable Pyth update for one paired asset (e.g. zSTX) to advance the shared timestamp ahead of what is available for a sibling asset (e.g. stSTXbtc), blocking liquidators/borrowers on that sibling asset from acting until a newer update surfaces - a temporary but externally triggerable denial of service on a specific asset's price-dependent operations, matching the "temporary freezing of funds" impact class.

### Likelihood Explanation
No privileged access is required — any account can submit `price-feeds` in a normal `borrow`, `repay`, `collateral-add`, or `liquidate` call. The condition is naturally reachable whenever paired assets share a feed (which the protocol's own asset registration deliberately does for every underlying/zToken pair, and for stSTX/stSTXbtc vs STX), and can be worsened intentionally by an attacker who simply front-runs with the most recent available price update for the "wrong" asset in the pair.

### Recommendation
Key the monotonic freshness map by asset ID (or by `{type, ident, asset-id}`) instead of by the raw oracle feed identity, so that advancing the timestamp for one asset cannot revert price resolution for a different asset that happens to share the same underlying feed. If a shared feed timestamp is intentionally desired for gas savings, at minimum decouple the "freshness/staleness" check (per-asset `max-staleness`) from the "monotonic ordering" check so a valid, sufficiently fresh price for asset B is never rejected purely because a different asset's caller supplied a newer timestamp first.

### Proof of Concept
1. Assets wSTX (id 0) and stSTXbtc (id 10) are both registered with `ident = STX-FEED-ID` per `mainnet/contracts/proposals/mainnet/v0-init.clar:91-133`.
2. User A calls `collateral-add`/`borrow` for wSTX, submitting a Pyth price update with timestamp `T1` (the latest available Pyth publish for the STX feed). `price-resolve` updates the shared `last-update` map entry for `{type: TYPE-PYTH, ident: STX-FEED-ID}` to `T1` per `mainnet/contracts/market/v0-4-market.clar:390-393`.
3. User B, holding a position collateralized/indebted in stSTXbtc, needs to `liquidate`/`repay` and submits the most recent Pyth update they can obtain for the STX feed, with timestamp `T0 < T1` (e.g., due to relay/publish latency for that specific update round).
4. `oracle-timestamp-fresh(T0, T1, max-staleness)` returns `false` because `T0 < T1`, so `price-resolve` returns `ERR-ORACLE-INVARIANT` per `mainnet/contracts/market/v0-4-market.clar:365-371,386-388`, and User B's transaction reverts — even though `T0` is well within `max-staleness` on its own.
5. User B remains unable to act on their stSTXbtc position until a Pyth update with timestamp `>= T1` propagates, which is entirely outside their control and was triggered solely by User A's unrelated transaction on a different asset.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
