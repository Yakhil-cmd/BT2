### Title
Webhook signature verification is keyed to an attacker-controlled `repository_owner` field that is decoupled from the `repository.full_name` field actually used to locate and mutate stacks — enabling cross-organization status/event forgery in multi-tenant deployments (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body, *before* the signature is checked. Every webhook `Handler` subclass then locates the `Stack`/`Repository` to act on using a *different* field of the same untrusted body: `repository.full_name`. Nothing ties these two fields together, so the "organization whose secret authenticated the request" is not equal to "the repository whose state gets written."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

`Shipit.github(organization:)` supports multi-tenant configuration where each organization has its own `app_id`/`installation_id`/`webhook_secret`:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [3](#0-2) 

Meanwhile every `Handler` (`PushHandler`, `StatusHandler`, PR handlers, etc.) resolves the target `Stack`/`Repository` from a *different, independently-controlled* field of the same body — `repository.full_name` — not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Equality that should hold but doesn't: `organization_used_to_select_secret == organization_that_owns_the_repository_being_mutated`. Before the PR/request: an attacker with no credentials cannot forge any signature. After: an attacker who legitimately possesses (or can obtain, e.g. as an admin of their own org's GitHub App installation on a multi-tenant Shipit instance) the `webhook_secret` for **Org A only** can send `X-Hub-Signature` computed with Org A's secret while setting `repository.owner.login = "OrgA"` (so `verify_signature` picks Org A's secret and it validates) but `repository.full_name = "OrgB/victim-repo"` (so the handler operates on Org B's stack). `verify_signature` never checks that these two fields refer to the same organization.

### Impact Explanation
This breaks the deployment-trust binding described in scope: "an organization that authenticated versus the repository that is written." Handlers such as `StatusHandler` write `Status` records directly from webhook payload fields (`state`, `sha`, `context`) for whatever repository `repository.full_name` names, and `Commit#deployable?`/`Stack#required_statuses` gate deploys on those statuses. An attacker holding only Org A's webhook secret can forge a signed `status` (or `push`, `pull_request`, `check_suite`) event that is accepted as authentic for Org B's repository, allowing cross-repository writes and potentially satisfying CI-status gating that leads to an unauthorized deploy of another tenant's stack — matching the Critical-tier impact ("cross-repository writes, or an unauthorized deploy"). This requires no GitHub write access to the victim repository and no possession of the victim organization's webhook secret.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured in the multi-tenant mode (`github_organizations`/`github_app_config`), where distinct organizations/customers each hold their own webhook secret, and requires the attacker to possess (legitimately, for their own org) one such secret. Given that possession, forging a decoupled `repository.owner.login` vs `repository.full_name` payload is trivial (a single crafted POST with a valid HMAC computed offline). No privileged Shipit account, API token, or GitHub write access to the target repo is needed — only knowledge of one org's `webhook_secret`, which is a much weaker credential than what the "OUT OF SCOPE" list excludes (that list excludes actual API tokens/webhook_secret *of the target*, not of an unrelated tenant).

### Recommendation
In `WebhooksController#verify_signature`, after selecting the `GitHubApp` by `repository_owner` and validating the HMAC, additionally assert that `repository_owner` matches the owner segment of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers. Reject the webhook (422) if they diverge, so the organization whose secret authenticated the request is provably the same organization whose repository state is being written.

### Proof of Concept
1. Multi-tenant Shipit deployment configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Attacker is a legitimate admin of `OrgA`'s GitHub App installation and thus knows `OrgA`'s `webhook_secret` (no access to `OrgB` at all).
3. Attacker crafts a `status` (or `push`) JSON payload:
   ```json
   {
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "target_url": "http://attacker.example"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, validates against `OrgA`'s secret, succeeds (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. The `status` handler resolves the target stack via `repository.full_name = "OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and records a forged successful CI status for a commit belonging to `OrgB`, which can satisfy `required_statuses` and unblock/trigger a deploy on `OrgB`'s stack that the attacker has no legitimate access to.

Note: I was unable to fully read `app/models/shipit/webhooks/handlers/status_handler.rb` in this pass (only located it via grep) to cite its exact write path line-by-line; the causal chain from stored `Status` to `Commit#deployable?`/deploy gating is supported by `app/models/shipit/deploy_spec.rb:194-204` (`required_statuses`, `blocking_statuses`) but I could not verify the exact `StatusHandler#process` implementation lines within this session. This should be confirmed by reading that file directly before treating the PoC as fully validated end-to-end.
