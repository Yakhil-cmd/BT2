## Title
Cross-organization team hijack via `membership` webhook bypasses `Shipit.github_teams` authorization boundary - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
This engine supports multi-organization deployments, where `Shipit.github(organization:)` looks up per-organization GitHub App config (including a distinct `webhook_secret`) via `github_app_config` [1](#0-0) . `WebhooksController#verify_signature` derives the organization to verify against straight from the untrusted JSON payload (`repository.owner.login` or `organization.login`) and authenticates the request using *that* organization's `webhook_secret` [2](#0-1) [3](#0-2) . This correctly proves "the sender knows organization X's webhook secret," but the `membership` event handler then mutates a `Team` record identified **only** by the GitHub-global `github_id`, with no check that the team's `organization` column matches the organization that was actually authenticated: `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3) .

### Finding Description
The binding that should hold is:
`organization authenticated by verify_signature == organization whose Team/membership state is mutated`

`verify_signature` only proves the caller controls organization **A**'s webhook secret (`Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the attacker-controlled JSON body) [5](#0-4) [3](#0-2) . Any organization owner in a multi-org Shipit deployment legitimately knows their own org's `webhook_secret` and can therefore produce a validly-signed `membership` webhook body of arbitrary content for their own org.

`MembershipHandler#process` then looks up (or creates) a `Team` keyed solely by `params.team.id` (GitHub's numeric team id) and adds/removes the specified `member` from it:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [6](#0-5) 

The `organization` attribute is only assigned inside the `find_or_create_by!` block, i.e. only when the `Team` row does **not already exist**. If a `Team` with that `github_id` already exists — belonging to organization **B**, and referenced in `Shipit.github_teams` (which grants login/authorization to Shipit, see `User#authorized?` [7](#0-6)  and `force_github_authentication` [8](#0-7) ) — a webhook validly signed for organization **A** can still call `team.add_member(member)` on organization **B**'s `Team` row [9](#0-8) , because the lookup ignores `organization` entirely.

`github_id` values are GitHub's own numeric team identifiers; they are not secrets and are commonly discoverable (e.g. through the GitHub API, prior webhook deliveries, or the team's own settings/URL). An attacker who administers *any* GitHub organization onboarded to a shared, multi-tenant Shipit instance can enumerate/guess the `github_id` of a privileged team in `Shipit.github_teams` belonging to a different organization, then fire a `membership`/`added` webhook (signed with their own org's secret) naming that `github_id` and their own GitHub login as `member`. `Team#add_member` will add them to that team's `members` association [10](#0-9) , granting them Shipit access/authorization as though they belonged to the victim organization's team — without ever needing credentials, install access, or membership in that organization.

### Impact Explanation
This directly breaks the "escalation into `Shipit.github_teams` authorization" boundary called out as High severity: `Shipit.authentication.authorized?` grants access based purely on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6) . Gaining forged membership in one of these teams grants full access to the Shipit UI/API for stacks that team is scoped to authorize, letting the attacker view stack state, task/deploy output, and (depending on which teams gate which stacks) trigger deploys/rollbacks — all cross-organization, unprivileged with respect to the victim org.

### Likelihood Explanation
Requires the attacker to control a GitHub organization onboarded as a *separate*, legitimately configured tenant of the same multi-org Shipit instance (a normal, unprivileged scenario for shared SaaS-style Shipit deployments), and knowledge/guessing of a target `github_id` for a privileged team (non-secret, GitHub-assigned numeric id). No Shipit session, API token, or victim-org secret is required. This is a realistic misconfiguration-independent flaw specific to the multi-org code path (`github_app_config`) that ships in this engine.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
