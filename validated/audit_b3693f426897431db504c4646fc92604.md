### Title
Open redirect via unvalidated `omniauth.origin` in OAuth callback - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` takes `request.env['omniauth.origin']` verbatim and passes it straight to `redirect_to` after establishing an authenticated session, with no check that the value's host matches `Shipit.host` or any same-origin allowlist. Because OmniAuth's request phase persists the `origin` query parameter into the session and replays it into `env['omniauth.origin']` on callback, an attacker can pre-set an arbitrary external URL and have the authenticated operator's browser redirected there once real OAuth completes.

### Finding Description
The binding that should hold is: `URI(return_url).host == Shipit.host` (or `return_url` is a same-origin path). The code instead does: [1](#0-0) 

`return_url` is sourced only from `request.env['omniauth.origin'] || root_path` with no host/allowlist check, so the equality is violated whenever `omniauth.origin` is attacker-controlled, which it can be: OmniAuth's request phase stores the `origin` request parameter (or referrer) into the session at `/github/auth/github`, and its callback phase later copies that session value back into `env['omniauth.origin']` for the callback action — this handoff mechanism is configured in [2](#0-1)  where `OmniAuth::Builder` is mounted for the `:github` provider with no `origin_param` restriction or `on_failure`/callback validation added by Shipit.

Exploit flow:
1. Attacker sends the operator a link: `https://shipit.example/github/auth/github?origin=https://attacker.example/steal`.
2. Operator clicks it and completes a real GitHub OAuth login (their own legitimate credentials, no secrets needed by the attacker).
3. `callback` runs, sets `session[:user_id]` and `session[:authenticated] = true` (line 13, 18), then executes `redirect_to(return_url)` where `return_url` equals the attacker's URL (line 8, 20).
4. The now-authenticated browser is sent to `https://attacker.example/steal`, which can capture the referrer, present a phishing page, or otherwise abuse the freshly-authenticated session context.

None of the existing guards (`verify_signature`, `force_github_authentication`, `User#authorized?`, `require_permission!`, model validators) apply here — those protect webhook/API paths, not this interactive OAuth callback. There is no code anywhere in `callback` or in the engine initializer that validates `return_url`'s host before redirecting.

### Impact Explanation
The attacker achieves a forced OAuth completion / open redirect from an authenticated context: the victim operator's authenticated Shipit session is used to trigger a browser redirect to an attacker-chosen origin immediately after login. This matches the High-severity category "session fixation / forced OAuth completion" defined in scope. It is repeatable against any operator who clicks the crafted link, and does not depend on any Shipit or GitHub secret — only the operator's own valid GitHub OAuth completion is required. It does not by itself leak `github_access_token` (that's stored server-side, not put in the URL), but it can be chained with phishing/referrer leakage on the attacker's page immediately after authentication.

### Likelihood Explanation
Preconditions are minimal: Shipit must have GitHub OAuth enabled (`Shipit.github.oauth?`), which is the standard configuration for any deployed Shipit instance. The attacker needs no privileges, tokens, or secrets — only the ability to send a link to an operator and have them click it and log in normally. This is a low-cost, highly feasible, and repeatable attack (a single crafted URL per target).

### Recommendation
Validate `return_url` against `Shipit.host` (or restrict to a relative path) before redirecting, e.g.:
```ruby
return_url = request.env['omniauth.origin']
return_url = root_path unless return_url.present? && safe_redirect_url?(return_url)
```
where `safe_redirect_url?` parses the URL and confirms `host == Shipit.host` (or the URL is a relative path starting with `/` and not `//`). Alternatively, only allow the callback to redirect to `root_path` and drop reliance on `omniauth.origin` entirely.

### Proof of Concept
```ruby
# test/controllers/github_authentication_controller_test.rb
test ":callback redirects to attacker-controlled origin (open redirect)" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(
      raw_info: OmniAuth::AuthHash.new(
        id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
        login: 'shipit-user', avatar_url: 'https://example.com',
        api_url: 'https://github.com/api/v3/users/shipit-user'
      )
    )
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example/steal'

  get :callback

  assert session[:authenticated], "session must be authenticated"
  # Binding under test: URI(return_url).host == Shipit.host
  assert_not_equal URI(Shipit.host).host, URI(response.location).host,
    "redirect target host diverges from Shipit.host -- open redirect confirmed"
  assert_redirected_to 'https://attacker.example/steal'
end
```
This demonstrates that after a successful, legitimate OAuth login, the authenticated session is redirected off-host to an attacker-controlled URL supplied via `omniauth.origin`.
