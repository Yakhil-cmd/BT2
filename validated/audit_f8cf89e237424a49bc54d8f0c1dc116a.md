## Title
Webhook signature verification selects the GitHub-App secret from an unverified payload field, letting a signature valid for one organization authorize writes to a repository owned by another organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The reported PRBProxy bug is a "verify against value A, act on mutable value B" flaw: the safety check (`owner_ == owner`) is evaluated against a value that can diverge from the value actually used to authorize the dangerous action. The same class of bug exists in `Shipit::WebhooksController`: which HMAC secret is used to *verify* the webhook signature is selected from an **unverified** field of the JSON body, while the **repository that is actually written to** is resolved from a *different*, independently-controllable field of that same unverified body. Nothing ties the two together.

### Finding Description
In a multi-organization Shipit deployment (`secrets.github` keyed by organization, see `Shipit.github_app_config` / `Shipit.github_organizations` in [1](#0-0) ), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` picks which app/secret to verify against using `repository_owner`, read directly out of the unparsed, unauthenticated JSON body before any signature check has succeeded: [2](#0-1) [3](#0-2) 

The signature check only proves that the request body was signed with *some* org's secret — the one named in `repository.owner.login`/`organization.login`. It does not prove anything about `repository.full_name`, which is a sibling field in the very same JSON object and is what downstream code actually acts on: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` performs a plain DB lookup keyed only on the owner/name string embedded in the payload, with no cross-check against the organization whose secret validated the request: [6](#0-5) 

Because HMAC-SHA1 signs the *entire raw body*, an attacker who legitimately knows (or controls) the webhook secret for **their own** organization/repo configured on the same Shipit instance can craft an arbitrary JSON body where `repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` selects their known secret and the signature check passes) while `repository.full_name` = `"OtherOrg/other-repo"` (so the handler acts on a stack belonging to a completely different, victim organization). This is the exact "verify field A, act on field B" pattern from the PRBProxy report, applied to a signing-key selection instead of an owner-storage-slot check.

### Impact Explanation
This breaks the binding: *the organization whose webhook secret authenticated the request* ≠ *the repository the handler writes to*. Depending on which handler fires, an attacker with only a legitimate webhook secret for one org/repo can:
- Force `PushHandler` to enqueue `sync_github` for a victim stack under another org, using an attacker-chosen `after` SHA, effectively injecting/spoofing commit sync state for a repository they do not control — a cross-repository write.
- Drive `MembershipHandler`/organization-scoped events, or PR handlers, against a victim repository's stacks (archive/unarchive review stacks, update PR state, etc.), all without ever possessing the victim organization's webhook secret.

This matches the "cross-repository writes" Critical-impact category, since state belonging to a repository/organization the attacker is not authorized for is mutated using a signature computed with credentials for an unrelated organization.

### Likelihood Explanation
Requires the Shipit instance to be configured with the multi-organization `secrets.github` schema (documented and supported, see `test/dummy/config/secrets_double_github_app.yml`) and requires the attacker to control (or have leaked) the webhook secret for at least one organization/app hosted on the instance — which is plausible since organization admins/integrators of one org routinely have access to that org's webhook secret. No GitHub App private key, `api_clients_secret`, or Shipit session is needed; only knowledge of one org's `webhook_secret` and the ability to POST to the public `/webhooks` endpoint.

### Recommendation
Do not select the verification secret from the same untrusted body whose authenticity is being established. Either:
- Verify the signature against **every** configured organization's secret and only accept the payload if the resolved repository's owner matches the organization whose secret actually validated it, or
- After signature verification succeeds using `repository_owner`, re-validate that `repository.full_name`'s owner component matches `repository_owner` before dispatching to any handler, rejecting (422) on mismatch.

### Proof of Concept
1. Instance configured with two orgs, `AttackerOrg` (secret known to attacker, e.g. because attacker administers a repo/app there) and `VictimOrg`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "VictimOrg/victim-repo",
    "owner": { "login": "AttackerOrg" }
  }
}
```
3. `X-Hub-Signature` is computed with `AttackerOrg`'s known `webhook_secret` over this exact body.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and successfully verifies the signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on a stack the attacker never had credentials for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
