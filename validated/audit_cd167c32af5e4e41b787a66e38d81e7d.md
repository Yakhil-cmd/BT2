### Title
Cross-tenant commit status corruption via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely `by sha`, with no check that the commit's owning stack/repository matches the repository named in the webhook payload that `verify_signature` authenticated. Any organization/user who owns a valid Shipit-connected repository (and thus a valid webhook secret for that organization) can send a signed `status` event whose `sha` collides with a commit tracked under a stack belonging to a completely different organization, causing that unrelated commit's CI status to be mutated.

### Finding Description
The binding claimed by the question is: `repository_owner` asserted and verified in `verify_signature` (app/controllers/shipit/webhooks_controller.rb:59-62, using `Shipit.github(organization: repository_owner)` at line 25) must equal the repository owning every `Commit` row mutated by `create_status_from_github!`.

Tracing the code:
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) resolves `repository_owner` from `params.dig('repository','owner','login')` and verifies the HMAC signature against `Shipit.github(organization: repository_owner)`'s webhook secret. This only proves the payload was signed by organization A's secret — it establishes nothing about which `Commit` rows in the database should be touched.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query is global across the entire `commits` table — it is **not** scoped by `stack_id`, `repository`, or `repository_owner`. The `params` schema (lines 7-18) never declares/uses `repository.full_name` for filtering.
- `Commit#create_status_from_github!` (app/models/shipit/commit.rb:165-169) unconditionally calls `statuses.replicate_from_github!(stack_id, github_status)`, writing a `Status` row scoped to whatever `stack_id` that particular `Commit` row happens to belong to (`Status.replicate_from_github!`, app/models/shipit/status.rb:24-33).

Because git SHA-1 commit identifiers are content-addressed and not repository-scoped, the exact same 40-character SHA can legitimately exist in multiple unrelated Shipit stacks (e.g., a shared base commit inherited by two forks tracked as separate stacks/organizations, cherry-picks, or two repos initialized from the same template/history). There is no code anywhere in the reachable path that cross-checks `self.stack.repository.full_name` (or `owner`) against the `repository_owner` verified in `verify_signature`.

Existing guards do not close this gap: `verify_signature` authenticates the *sender*, not the *target rows*; `ExplicitParameters` (the `params do ... end` schema) only validates payload shape, not repository ownership; there is no `stacks` scope restricting `Commit.where(sha:)` to stacks under the verified organization.

### Impact Explanation
An attacker who owns/controls any GitHub organization/repository connected to the same Shipit instance (a legitimate, unprivileged use case — anyone who can get their repo onto the shared Shipit host) can send a validly-signed webhook for their own repository naming a `sha` that also exists in a `Commit` row under a different organization's stack. This writes a forged `Status` (state/context/description/target_url) onto that unrelated commit, potentially:
- Marking a commit under organization B as `success` when it should be `pending`/`failure`, allowing `schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287) to trigger scheduling of a deploy for organization B's stack.
- Corrupting CI state (`deployable?`, `blocked?`) that gates B's deploys.

This matches "a payload for one repository mutating another's stack/commit" — Critical, cross-tenant impact. It is repeatable against any SHA collision an attacker can arrange or discover (attacker fully controls their own repo's git history and can deliberately construct commits sharing a target SHA, e.g. via history rewriting to match a known/leaked SHA from a public open-source stack tracked on the same Shipit instance).

### Likelihood Explanation
Preconditions: attacker must own a repository already connected to the target Shipit instance (obtaining a webhook secret is not required — Shipit provisions webhook secrets automatically per configured organization when the repo/stack is created; this is the normal unprivileged "add your repo to Shipit" flow). Attacker must know or engineer a SHA that exists in a target stack (feasible for public/open-source target repos where SHAs are visible, or via crafted commit content producing a chosen SHA in a repo the attacker controls, then pushing that same commit content to also exist in their own repo's history so the webhook fires with that SHA). Attacker cost is a single signed webhook POST; fully repeatable and scriptable across many target SHAs/stacks.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any similar handler using bare `sha`) by the repository asserted in the webhook payload, e.g. filter `Commit.joins(:stack).where(sha: params.sha, stack: { repository_owner: ..., repository_name: ... })`, comparing against `Stack#repository`/`repository.full_name`, matching it to the verified `repository_owner`/`repository.full_name` from the payload before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (no live GitHub, using two `Shipit.github(organization:)` configs A and B):
```ruby
test "status webhook signed by org A mutates a commit belonging to org B's stack on sha collision" do
  # Setup: configure Shipit.github for org "org-a" and "org-b" with distinct secrets
  stack_b = shipit_stacks(:shipit) # belongs to org-b's repository
  colliding_sha = "a" * 40
  commit_b = stack_b.commits.create!(sha: colliding_sha, ...)

  payload = {
    state: "success",
    sha: colliding_sha,
    context: "ci/attacker",
    repository: { full_name: "org-a/attacker-repo", owner: { login: "org-a" } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, payload)

  post "/webhooks", params: payload, headers: {
    "X-Github-Event" => "status",
    "X-Hub-Signature" => signature,
    "Content-Type" => "application/json"
  }

  assert_response :ok
  commit_b.reload
  # Assert: verify_signature only checked repository_owner == "org-a" (A),
  # but the row mutated belongs to stack_b whose repository owner is "org-b" (B).
  refute_equal "org-a", stack_b.repository.owner  # B != A: binding is broken
  assert_equal "success", commit_b.status.state    # B's commit was mutated by A's webhook
end
```
