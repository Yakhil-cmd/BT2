### Title
`DenyReserveTransferToRelayChain` in `Barrier` only inspects top-level instructions, allowing a nested `DepositReserveAsset{dest: Parent}` inside `SetAppendix`/`ExecuteWithOrigin` to bypass the deny rule - (File: `system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs`)

### Summary
The `Barrier` for Asset Hub Kusama wraps `DenyReserveTransferToRelayChain` directly, without the `DenyRecursively` adapter that other system chains in this same repository (e.g. bridge-hub-polkadot, bulletin-polkadot) explicitly use for the same deny rule. Because the deny filter's pattern match only walks the top-level instruction slice of the incoming `Xcm` program, an unprivileged user can hide a `DepositReserveAsset{ dest: Location{parents:1, interior:Here}, .. }` (or `InitiateReserveWithdraw`/`TransferReserveAsset` to Parent) inside `SetAppendix`'s nested program or `ExecuteWithOrigin`'s nested program, both of which are executed by the XCM executor without a second `Barrier::should_execute` invocation.

### Finding Description
The Barrier is defined as: [1](#0-0) 
`DenyThenTry<DenyReserveTransferToRelayChain, (...)>` runs `DenyReserveTransferToRelayChain::should_execute` against the message before trying the allow-list. That deny filter (from `xcm-builder`) matches over the flat, top-level `message` slice for instructions such as `DepositReserveAsset { dest: Location{parents:1, interior:Here}, .. }`. Instructions nested inside another instruction's fields — e.g. the program embedded in `SetAppendix(Xcm(..))`, `ExecuteWithOrigin(_, Xcm(..))`, or `InitiateTransfer`'s `remote_xcm` — are not part of that top-level slice, so the pattern match never sees them.

Elsewhere in this same codebase, the same underlying rule is explicitly hardened against exactly this nesting problem: [2](#0-1) [3](#0-2) 
Both use `DenyRecursively<DenyReserveTransferToRelayChain>`, which recurses into nested `Xcm` programs carried by instructions like `SetAppendix`/`ExecuteWithOrigin` so the denied pattern is detected wherever it appears in the instruction tree, not only at the top level.

Asset Hub Kusama (and also asset-hub-polkadot, bridge-hub-kusama, coretime-kusama/polkadot, collectives-polkadot, encointer, people-kusama/polkadot) instead use the bare, non-recursive `DenyReserveTransferToRelayChain`: [1](#0-0) 

An unprivileged, signed account can reach this path via `pallet_xcm::execute`, which lets any signed origin submit an arbitrary local `Xcm` program subject to the chain's `Barrier`/weight/safe-call checks. A program such as:
```
Xcm(vec![
  WithdrawAsset(ksm.into()),
  SetAppendix(Xcm(vec![
    DepositReserveAsset { assets: All, dest: Location::parent(), xcm: Xcm(vec![]) }
  ])),
  ClearOrigin, // or any harmless trailing top-level instruction
])
```
presents only `WithdrawAsset`, `SetAppendix`, and the trailing instruction to `DenyReserveTransferToRelayChain::should_execute` at the top level — none of which match its deny pattern — so the barrier lets the message proceed to `AllowTopLevelPaidExecutionFrom`/`WithComputedOrigin` and ultimately execution. When the executor later runs the `SetAppendix` payload (after the main program completes), the nested `DepositReserveAsset{dest: Parent}` executes without the Barrier being invoked a second time, since `Barrier` gates only the initially submitted top-level message.

### Impact Explanation
This lets a normal user drive the exact `DepositReserveAsset`-to-Relay pattern that the deny rule is explicitly meant to block, in violation of the chain's documented policy ("Deny executing the XCM if it matches any of the Deny filter regardless of anything else" for reserve-transfer-to-relay-chain patterns). Concretely it can cause user KSM to be withdrawn into holding and consumed via `DepositReserveAsset` targeting the Relay Chain — a path the Relay Chain does not recognize AssetHub as a trusted reserve for, so the deposited assets are not properly credited/backed on arrival, risking loss/trapping of the withdrawn KSM and violating the "assets must remain fully backed" invariant.

### Likelihood Explanation
No privileged access is required: only a signed account able to pay the `pallet_xcm::execute` weight and hold KSM is needed. `SetAppendix` and `ExecuteWithOrigin` are ordinary XCM v4/v5 instructions available to any user-submitted program; the only precondition is being able to construct the nested instruction sequence, which is trivial and fully repeatable.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively` in the Asset Hub Kusama `Barrier` (matching the pattern already used in bridge-hub-polkadot and bulletin-polkadot), i.e. change:
```rust
DenyThenTry<DenyReserveTransferToRelayChain, (...)>
```
to
```rust
DenyThenTry<DenyRecursively<DenyReserveTransferToRelayChain>, (...)>
```
and apply the same fix consistently to the other chains that still use the bare, non-recursive filter (asset-hub-polkadot, bridge-hub-kusama, coretime-kusama/polkadot, collectives-polkadot, encointer, people-kusama/polkadot).

### Proof of Concept
xcm-emulator test on Asset Hub Kusama:
1. Fund a test signed account with KSM.
2. Submit `pallet_xcm::execute` with:
```rust
let xcm: Xcm<()> = Xcm(vec![
    WithdrawAsset(ksm_asset.clone().into()),
    SetAppendix(Xcm(vec![
        DepositReserveAsset {
            assets: Wild(All),
            dest: Location::parent(),
            xcm: Xcm(vec![]),
        },
    ])),
    ClearOrigin,
]);
```
3. Assert current (buggy) behavior: `Outcome::Complete` (or `Incomplete` past the appendix point) rather than `Outcome::Error(ProcessMessageError::Unsupported)`/Barrier error, and observe the account's KSM balance decreasing without a corresponding legitimate reserve-transfer receipt on the Relay Chain.
4. After applying `DenyRecursively`, re-run the same test and assert the Barrier now rejects the message up front with `Outcome::Error(..)` (Barrier), and KSM balance is unaffected.
