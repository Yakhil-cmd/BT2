### Title
Webhook signature verification is keyed on `repository.owner.login`, while the actual write target is resolved from the independent `repository.full_name` field, allowing a valid webhook secret for one GitHub organization to mutate stack state belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` is used to validate the HMAC signature by reading `params.dig('repository', 'owner', 'login')`, while the code that actually performs the mutation reads a completely independent field, `payload.dig('repository', 'full_name')`, to resolve the target `Repository`/`Stack`. Because both values originate from the same attacker-controlled JSON body but are never cross-checked against each other, a webhook that is validly signed for organization "A" can carry a `repository.full_name` pointing at organization "B"'s repository, causing Shipit to act on organization B's stack using organization A's authenticated request.

### Finding Description
The controller's filter chain is: [1](#0-0) 

`verify_signature` derives the signing organization purely from the payload: [2](#0-1) [3](#0-2) 

This picks the `GitHubApp`/`webhook_secret` for `repository.owner.login` (or `organization.login`) and, if the HMAC over the raw body matches that organization's secret, the request is accepted: [4](#0-3) 

Once accepted, `create` dispatches to handlers with the same raw payload: [5](#0-4) 

Every handler resolves the repository/stack to mutate via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a **different** field than the one used for signature-org selection: [6](#0-5) 

`Repository.from_github_repo_name` splits this attacker-controlled string on `/` to find the target repo without any correlation to `repository.owner.login`: [7](#0-6) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated repository) are two independent, unauthenticated-as-a-pair fields inside the same signed JSON body, nothing stops them from referring to different organizations. The HMAC covers the raw bytes, but it certifies only "this body was sent by whoever holds organization A's secret" — it does not certify "the repository referenced inside this body belongs to organization A." Handlers such as `PushHandler` and `StatusHandler` then act on whatever stack `full_name` resolves to: [8](#0-7) [9](#0-8) 

This is precisely the "an organization that authenticated versus the repository that is written" trust binding: the binding `authenticated_org == written_repository_owner` is assumed but never enforced.

### Impact Explanation
An entity that legitimately controls one onboarded GitHub organization's webhook secret (a routine, low-privilege credential distributed to every organization that installs the Shipit GitHub App/webhook — not a Shipit admin credential, `ApiClient` token, or `GITHUB_TOKEN`) can forge webhook deliveries whose signature checks out for their own organization but whose `repository.full_name` targets a stack owned by a **different, victim** organization on the same multi-tenant Shipit instance. Depending on the event type this allows:
- `push` events to trigger `Stack#sync_github(expected_head_sha:)` against a victim's stack, forcing sync/deploy pipeline state changes on a repository the attacker does not own.
- `status`/`check_suite` events to inject fabricated CI `Status`/`CheckRun` records against a victim commit, which can flip `merge_status`/`deployable_status` and enable an unauthorized deploy/merge decision on the victim's stack.

This is a cross-repository/cross-tenant write achieved purely by exploiting the mismatch between the authentication field and the target-resolution field, which meets the "cross-repository writes" / "unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Any organization already onboarded to a shared Shipit deployment (a common multi-tenant setup, since `Shipit.github(organization:)` is looked up dynamically per incoming payload rather than being a single fixed installation) inherently possesses a valid webhook secret for itself. Crafting a payload where `repository.owner.login`/`organization.login` reflects the attacker's own org (to pass signature verification) while `repository.full_name` points at a victim org/repo requires no special access beyond that routine secret and is a straightforward HTTP POST to the public webhook endpoint.

### Recommendation
After signature verification succeeds for `repository_owner`, require that `repository.full_name.split('/').first` (or `organization.login`, for org-scoped events) matches `repository_owner` exactly before allowing handlers to run; reject the request otherwise. More robustly, resolve the target `Repository` first, derive its `owner` from persisted, already-vetted state, and verify the signature using that owner's secret rather than trusting an unauthenticated field pulled from the same payload used for verification.

### Proof of Concept
1. Attacker's organization `attacker-org` is legitimately onboarded to the shared Shipit instance and possesses its own `webhook_secret`.
2. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and POSTs to `/webhooks`.
4. `verify_signature` computes `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully.
5. `create` dispatches to `PushHandler`, which reads `repository.full_name` = `"victim-org/victim-repo"`, resolves `victim-org`'s `Repository`/`Stack`, and calls `stack.sync_github(expected_head_sha: ...)` — mutating a stack the attacker does not own and never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
