### Title
Webhook signature verification is unconditionally bypassed when no `webhook_secret` is configured, letting unauthenticated attackers forge GitHub events (`status`, `push`, `pull_request`, `membership`, `check_suite`) - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` with no check at all whenever `webhook_secret` is blank, and `WebhooksController` derives *which* per-organization `GitHubApp` (and therefore which secret) to check against purely from an attacker-controlled field of the unauthenticated payload. The repository that the handlers actually act on is read from a different, unrelated payload field (`repository.full_name`). The binding "the organization whose credentials authenticated this webhook" == "the repository/commit the handler subsequently mutates" is never enforced, and can degrade to no authentication at all.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config to verify against using a field taken straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

That per-organization `GitHubApp#verify_webhook_signature` is: [3](#0-2) 

`return true unless webhook_secret` means that if the operator has not configured a `webhook_secret` for the organization named in the attacker-supplied `repository.owner.login`/`organization.login` field, the HMAC check is skipped entirely and `head(422)` is never reached — the request is treated as a fully verified GitHub event regardless of its actual origin or content.

Meanwhile, every webhook `Handler` resolves the target `Stack`/`Repository` from a *separate* payload field, `repository.full_name`, which has no relationship whatsoever to the field used to pick the verifying `GitHubApp`: [4](#0-3) 

So the equality the system implicitly relies on — "organization that authenticated" == "repository that is written" — is never actually checked. If any one configured organization (in a single- or multi-org Shipit install) has no `webhook_secret` set, an attacker can:
1. Set `X-Github-Event` and `repository.owner.login`/`organization.login` to that unsecured organization, satisfying `verify_signature` unconditionally.
2. Set `repository.full_name` (and any other business fields) to point at *any* repository/stack actually tracked by this Shipit instance — including ones belonging to a totally different, properly-secured organization.

The status handler, for example, creates a `Commit::Status` straight from attacker-controlled fields once the (bypassable) signature check passes, as demonstrated by the existing test suite for the same code path: [5](#0-4) 

The push handler similarly triggers `GithubSyncJob`/`sync_github` for whatever stack `full_name` resolves to: [6](#0-5) 

### Impact Explanation
An unprivileged internet attacker, with no Shipit session, no `ApiClient` token, no GitHub App private key, and no knowledge of any `webhook_secret`, can forge arbitrary GitHub webhook events against any tracked stack once a single configured organization lacks a `webhook_secret`:
- Forge a passing `status` event on an arbitrary commit sha of a targeted stack, defeating `require_ci`/CI-gating checks used to authorize deploys — a step toward an **unauthorized deploy**.
- Forge `push` events to re-trigger sync/continuous-deployment flows on stacks that belong to organizations the attacker has no relationship to.
- Forge `membership`/`pull_request`/`check_suite` events that create `Team`/`User` records or alter merge-queue state used by Shipit's own authorization (`Shipit.github_teams`) and merge automation.

This breaks the "organization authenticated" vs "repository/stack acted on" trust binding called out in the rules, and its most severe realization (forged CI status enabling an unauthorized deploy) meets the Critical bar.

### Likelihood Explanation
Likelihood depends entirely on the deployment leaving at least one configured GitHub organization without a `webhook_secret`. This is not a hypothetical misconfiguration outside the documented feature set — the webhook secret is an app-level HMAC key the operator must generate and store, and the code path (`return true unless webhook_secret`) exists specifically to support the "no secret configured" state as a first-class fallback, not an error condition. In multi-organization deployments (a documented, supported configuration shape), it only takes one org's secret being blank to open this hole for every other org's repositories/stacks, since the vulnerable comparison never checks that the "authenticating" org and the "acted-upon" repository are the same.

### Recommendation
- Remove the `return true unless webhook_secret` unconditional pass in `GitHubApp#verify_webhook_signature`; require an explicit, opt-in "authentication disabled" flag (mirroring `Shipit.disable_api_authentication`) if unauthenticated webhooks must be supported, rather than defaulting to trust when a secret is merely absent.
- After signature verification, additionally verify that the organization whose secret validated the signature actually owns the repository referenced by `repository.full_name`/`organization.login` used later in `Handler#stacks`/`Handler#repository_name`, closing the gap between the field used to select the verifying key and the field used to select the affected resource.

### Proof of Concept
1. Configure (or find) a Shipit deployment where at least one GitHub organization entry has `webhook_secret` unset (the shipped example configs ship this way by default).
2. `POST /webhooks` with `X-Github-Event: status`, `X-Hub-Signature` set to any arbitrary value, and a JSON body:
```json
{
  "sha": "<real sha of a commit on a tracked stack in a different, secured org>",
  "state": "success",
  "target_url": "https://attacker.example/fake-ci",
  "description": "forged",
  "context": "ci/required-check",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "unsecured-org" } }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally and the request proceeds.
4. `StatusHandler` (exercised identically to `test/controllers/webhooks_controller_test.rb:42-59`) creates a passing `Commit::Status` for the named sha under `victim-org/victim-repo`, even though the attacker never authenticated as, or held a webhook secret for, `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
