## Analysis

The reachable analog is a cross-organization trust bypass in the GitHub `membership` webhook processing pipeline, which mirrors the report's bug class: a field is used for authorization (which credential/scope covers the request) while a *different* field is used for the actual privileged effect, with no consistency check binding the two.

**The binding that should hold:** `organization whose webhook_secret authenticated the request == organization whose Team record is mutated`.

### Root cause

`app/controllers/shipit/webhooks_controller.rb` resolves the signing organization purely from the payload itself: [1](#0-0) [2](#0-1) 

For a `membership` event there is no `repository` key, so `repository_owner` falls back to `params.dig('organization', 'login')`. Verification therefore only proves "this request was signed with the webhook secret configured for organization X (as named in the `organization.login` field)". Shipit natively supports many independently-configured GitHub organizations/apps sharing one instance: [3](#0-2) [4](#0-3) 

`MembershipHandler` then mutates state using `team.id` alone, never re-validating that the team it finds actually belongs to the organization that authenticated the request: [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` looks the team up **only by its numeric GitHub team id**, which is global to GitHub, not scoped to the organization named in the payload. If the team already exists in Shipit's database (e.g. it's a real, previously-synced team belonging to a *different* organization — including a privileged one referenced by `Shipit.github_teams`), the `do |team| ... end` creation block never runs, so `team.organization` is left untouched, but `team.add_member(member)` / `team.members.delete(member)` still execute unconditionally: [6](#0-5) 

Authorization is then decided purely by team membership: [7](#0-6) 

### Exploit path

1. Shipit is configured (per the documented multi-org setup) to serve at least two organizations, e.g. `OrgOne` (attacker-controlled/onboarded) and `OrgTwo` (victim, whose team is in `Shipit.github_teams`).
2. The attacker, as the administrator of the GitHub App installed on `OrgOne`, knows `OrgOne`'s `webhook_secret` — this is a credential they legitimately possess for their own org, not the victim's.
3. The attacker sends a `membership` webhook with `X-Hub-Signature` computed using `OrgOne`'s secret, and a body where `organization.login = "OrgOne"` (so `verify_signature` resolves and validates against `OrgOne`'s own secret) but `team.id` set to the real numeric GitHub id of an existing, privileged `OrgTwo` team already tracked by Shipit.
4. `MembershipHandler#process` finds the existing `OrgTwo` team by `github_id`, and adds an arbitrary Shipit `User` (created on the fly via `User.find_or_create_by_login!`) to it.
5. That user now passes `User#authorized?` and is granted access to every stack under Shipit's authorization model — an escalation into `Shipit.github_teams` authorization performed entirely with a credential scoped to a different, unrelated organization.

This matches the explicitly allowed analog category ("an organization that authenticated versus the repository/entity that is written") and the High-impact bucket ("escalation into `Shipit.github_teams` authorization"), without requiring any Shipit session, `ApiClient` token, or the victim organization's own secret.

### Title
Cross-organization webhook forgery lets one organization's webhook secret grant `Shipit.github_teams` membership in any other organization's team - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a `membership` webhook solely against the organization named in the payload's own `organization.login` field. `MembershipHandler` then looks up and mutates the `Team` purely by its global numeric `github_id`, never checking that this team actually belongs to the organization that produced a valid signature. In a multi-organization Shipit deployment, any organization admin can sign a `membership` payload with their own organization's webhook secret while pointing `team.id` at a team belonging to a completely different, unrelated organization tracked by the same Shipit instance.

### Finding Description
- `verify_signature` derives the signing org from attacker-supplied JSON (`repository.owner.login` or `organization.login`) and validates the signature against that org's configured secret only: [1](#0-0) .
- `MembershipHandler#find_or_create_team!` resolves the target `Team` exclusively via `github_id`, a GitHub-global identifier not namespaced by the authenticated organization, and only sets `team.organization` on first creation: [8](#0-7) .
- `team.add_member` / `team.members.delete` execute unconditionally on whatever `Team` record was found: [9](#0-8) .
- Nothing compares the authenticated `organization.login` to the resolved `team.organization` before mutating membership.

### Impact Explanation
Membership in a `Team` referenced by `Shipit.github_teams` is the sole authorization gate in `User#authorized?`: [7](#0-6) . An attacker who administers any one organization configured in a shared/multi-tenant Shipit instance can grant arbitrary Shipit users membership in a privileged team belonging to a different organization, escalating into `Shipit.github_teams` authorization — meeting the High severity bar defined in scope.

### Likelihood Explanation
Requires only: (a) a Shipit deployment configured with multiple GitHub organizations (explicitly documented/supported feature), (b) the attacker administering the GitHub App/webhook config for one of those organizations (their own, legitimately onboarded org — not privileged access to Shipit or the victim org), and (c) knowledge of the victim team's numeric GitHub team id (discoverable via GitHub's public/organization APIs or prior legitimate webhook traffic). No Shipit session, API token, or victim secret is needed.

### Recommendation
In `MembershipHandler`, scope the team lookup by both `github_id` and the authenticated `organization.login`, and reject/no-op if an existing team's `organization` doesn't match the payload's `organization.login`. More generally, `WebhooksController#verify_signature` should pass the resolved/authenticated organization down to handlers, and every handler that mutates organization-scoped records (teams, memberships) should assert that the authenticated organization matches the record's own `organization`/`repository.owner` before making changes.

### Proof of Concept
1. Configure Shipit with two orgs per the documented multi-org format: `OrgOne` (attacker-administered) and `OrgTwo` (victim, has a team `T` with `github_id = 999` included in `Shipit.github_teams`).
2. Attacker computes `sha1=HMAC(OrgOne_webhook_secret, body)` for:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "organization": { "login": "OrgOne" },
  "member": { "login": "attacker-login" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: membership` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` to `"OrgOne"` and validates successfully against `OrgOne`'s secret.
5. `MembershipHandler#find_or_create_team!` finds the existing `Team` with `github_id: 999` (which belongs to `OrgTwo`) and calls `team.add_member(User.find_or_create_by_login!("attacker-login"))`, granting the attacker's Shipit user membership in `OrgTwo`'s privileged team, satisfying `User#authorized?` for the entire Shipit instance.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
