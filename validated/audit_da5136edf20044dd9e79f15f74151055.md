### Title
Unhandled crash (uncaught `throw`) when an AA's `base_aa` reference cannot be resolved at trigger/estimation time - ([File: storage.js])

### Summary
CVE-2018-1065 is caused by netfilter jumping to a rule-chain reference that was never validated to exist, leading to an unhandled NULL dereference and process crash. The `ocore` AA (Autonomous Agent) engine has an analogous "jump" construct: a parameterized AA definition contains a `base_aa` field that is a pointer/reference to another AA's definition. Multiple code paths resolve this reference by querying the DB and, if the referenced AA is not found, execute an unconditional `throw Error(...)` instead of returning a validation error to the caller. Because these resolution paths run with `mci` values that are not guaranteed to be identical to the `mci` used when the reference was originally validated, a divergence between "definition-time" and "resolution-time" state can turn an attacker-influenced trigger into a crash.

### Finding Description
`storage.readBaseAADefinitionAndParams` resolves a parameterized AA's `base_aa` pointer: [1](#0-0) 

If `arrBaseDefinition` (the referenced base AA) is not found, the function does not signal an error to its callback — it throws, which is an uncaught exception in an async DB-callback context and crashes the Node.js process.

The equivalent "jump" is also present directly in the trigger execution path, `handleTrigger`: [2](#0-1) 

Both of these unconditional `throw Error("base AA not found: " + base_aa)` sites assume that `base_aa` was already validated to exist by `validation.js`'s definition-time check: [3](#0-2) 

That check resolves `template.base_aa` using `top_mci = objValidationState.aa_mci || objValidationState.last_ball_mci` — a value tied to the *unit that defines the parameterized AA*. However, the two crash sites above resolve the same `base_aa` reference using a *different* `mci`:
- In `handleTrigger`, `mci` is the main-chain index of the *unit that triggers the AA*, which can be a different, and in estimation/"air" paths, an approximated value (`aa_composer.js:163-167` rewrites `objMcUnit.timestamp`/`main_chain_index` from caller-supplied data for `estimatePrimaryAATrigger`, explicitly documented as not equivalent to full validation: "unit validation errors are not caught"): [4](#0-3) 
- In `formula/evaluation.js`'s `callGetter`, the resolution uses `objValidationState.last_ball_mci` of the *calling* unit/trigger, not the mci at which the callee's `base_aa` link was validated: [5](#0-4) 

`callGetter` is reachable from ordinary AA formula constructs such as `remote_func_call` / `with_selectors` where the remote AA address is derived from attacker-controlled data (e.g., `trigger.data`), as shown in test fixtures using `trigger.data.aa` as the remote AA address: [6](#0-5) 

This is structurally the same bug class as CVE-2018-1065: a reference/"jump" (`base_aa`) is dereferenced without re-validating its existence at the point of use, and the failure mode is an unhandled crash rather than a graceful validation error — differing only in that here the crash is a JS `throw` instead of a C NULL pointer dereference.

### Impact Explanation
An uncaught `throw` inside an asynchronous DB callback in Node.js is not caught by any surrounding `try/catch` in the call chain (the `throw` occurs after the event loop has already unwound past any calling `try` block), so it propagates as an `uncaughtException`, which by default terminates the Node.js process. Any AA trigger, `dryRun`/estimate call, or getter/remote-function call that hits this code path with a stale or inconsistent `base_aa` resolution causes the node process (full node or light node backend) to crash — a denial of service against the network's ability to process AA triggers and validate/serve units, matching the "network unable to confirm new units" bar for this class of bug.

### Likelihood Explanation
The likelihood is Medium: reaching the crash requires a scenario where `base_aa` was resolvable at AA-definition validation time (`top_mci`) but is not resolvable at trigger/estimation time (`mci`), which should not normally occur on the canonical, fully-synced full-node validation path (since `aa_addresses` rows are never deleted and `top_mci <= mci` in the ordinary case). It is most plausible in the `estimatePrimaryAATrigger`/light-wallet composition paths, which explicitly use approximate or locally-supplied `mci`/timestamp values instead of the fully validated chain state, and in remote-getter calls whose `objValidationState.last_ball_mci` differs from the mci used when the callee AA's own `base_aa` link was accepted.

### Recommendation
- Replace all unconditional `throw Error(...)` on a failed `base_aa`/reference resolution in `storage.readBaseAADefinitionAndParams` (storage.js:823-824), `aa_composer.js` `handleTrigger` (line 438), and `storage.readAAGetters` (storage.js:840) with graceful error propagation via the existing callback/`cb(err)` pattern, consistent with how `formula/evaluation.js`'s `callGetter` already handles the `!arrBaseDefinition` case (line 3308-3309).
- Ensure `mci` used to resolve `base_aa` in trigger execution and getter calls is never smaller than the `mci`/`aa_mci` used to originally validate the reference, or re-validate the full AA definition (including `base_aa` and its target) at every point of use rather than assuming it remains valid.
- Audit `estimatePrimaryAATrigger`/"air" simulation paths for other unconditional `throw` statements that assume full-node-validated invariants that may not hold when driven by externally-influenced/approximate state.

### Proof of Concept
Concrete reproduction requires constructing a scenario where a parameterized AA's `base_aa` was accepted at definition time (`top_mci`) but is unresolvable when a trigger/getter call later resolves it with a different `mci` (e.g., via `aa_composer.estimatePrimaryAATrigger`/light "air" dry-run APIs, which substitute caller-controlled `objMcUnit.timestamp`/`main_chain_index` per `aa_composer.js:163-167`, or via a `remote_func_call`/`with_selectors` getter chain where `objValidationState.last_ball_mci` at the calling unit precedes the mci at which the callee's `base_aa` link was itself confirmed). I was not able to fully verify, purely from static code review, a concrete on-chain sequence of units that forces `top_mci < mci_used_at_resolution` to diverge in the wrong direction on the canonical full-node validation path; this would need to be confirmed by running the AA composer/estimate code against a constructed test fixture (e.g., extending `test/aa_composer.test.js`'s "calling a remote function in a parameterized AA" test to make the base AA unavailable at the mci used by `callGetter`/`estimatePrimaryAATrigger`).
