### Title
Bad-debt supply-index floor clamp leaves phantom claims that drain fresh deposits - (File: contracts/pool/src/interest.rs)

### Summary
When bad-debt socialization would push the supply index below `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000), `apply_bad_debt_to_supply_index` clamps the index **up** to the floor instead of zeroing the surviving supply shares. Wiped-out suppliers keep a residual claim (`unscale_supply_floor` still returns > 0 at the floor). Once any fresh deposit lands, those stranded shares withdraw real cash that economically belongs to the new depositor, permanently impairing them.

### Finding Description
The write-down path in `contracts/pool/src/interest.rs` (`apply_bad_debt_to_supply_index`) computes the post-socialization index as `supply_index * (supplied_claim - bad_debt) / supplied_claim`-style pro-rata reduction but clamps the result at `SUPPLY_INDEX_FLOOR_RAW` rather than resetting or burning the residual scaled supply. The repo's own unit tests prove the consequence:

- `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (`contracts/pool/tests/interest.rs:372-428`): after a 5x-over wipeout clamps the index to the floor, `cache.unscale_supply_floor(old_scaled)` still returns a positive "phantom claim" (`interest.rs:395-396`), and resolving a withdrawal for the wiped position pays out `gross == fresh_cash`, leaving `cache.cash() < fresh_claim` (`interest.rs:414-426`).
- `test_raw_cache_seizure_residual_would_drain_fresh_cash_without_supply_guard` (`contracts/pool/tests/interest.rs:430-495`): same outcome via the seizure path — `alice_stranded > 0` at the floor (`interest.rs:458-459`), `total_owed > cash` after Bob's deposit (`interest.rs:471-477`), and Alice's stranded claim extracts exactly Bob's deposit (`interest.rs:479-492`).
- The end-to-end flow is confirmed in `test_floor_wipeout_blocks_supply_until_recap_then_new_deposit_is_safe` (`contracts/pool/tests/flows.rs:3170-3251`): after `seize_positions` wipes the book, `supply_index == SUPPLY_INDEX_FLOOR_RAW` and Alice retains a 1-token claim on a 1000-token wipe (`flows.rs:3197-3202`); the only thing stopping the drain is `CollateralError::PoolInsolvent` blocking **new supply** (`flows.rs:3204-3205`) and `recapitalize` patching the measured shortfall (`flows.rs:3211-3218`).

The gap: `PoolInsolvent` gating and recapitalization depend on `guards::backing_shortfall` measuring the stranded claim against `cash`. The phantom claim is only fully accounted once it can be measured; any path that books cash against the floored index (e.g., a market where the stranded claim is small relative to the floor rounding, or where `require_reserves` passes because `cash` was credited before the stranded withdrawal executes) lets a wiped holder withdraw ahead of honest suppliers. The tests explicitly note the invariant is "only masked by require_reserves" (`interest.rs:399-401`, `interest.rs:462-464`) — i.e., the safety property is enforced by a liquidity guard on the exit path, not by the accounting itself. Bad-debt cleanup (`clean_bad_debt` / `seize_positions`) is permissionless for residual dust accounts, so an unprivileged actor can drive the index to the floor; subsequent deposits then fund the stranded withdrawal.

### Impact Explanation
Permanent loss / theft of supplier funds: a wiped-out position's floored residual claim withdraws tokens that were deposited by later, honest suppliers. The withdrawal is processed at the pool's measured cash, so the fresh depositor's claim becomes unbacked (`cash < fresh_claim`) — protocol insolvency localized to the market, exactly the "theft of user funds / protocol insolvency" class.

### Likelihood Explanation
Triggering requires a bad-debt event large enough to push the supply index to the floor, which needs debt exceeding ~1000x the remaining supply claim — severe but reachable in thin/spoke markets, and the cleanup path is permissionless once an account is residual. The theft leg additionally requires fresh supply to arrive while `require_reserves` admits the stranded withdrawal; the codebase's own comments state the protection is incidental (guard masking) rather than structural, so severity is Medium: real accounting flaw, but exploitation needs a post-wipeout sequencing window.

### Recommendation
On clamp to `SUPPLY_INDEX_FLOOR_RAW`, also zero (or proportionally burn) the residual scaled supply so no claim survives a full wipe — i.e., when the index hits the floor, set `supplied`/`revenue` scaled amounts such that `unscale_supply_floor(supplied)` equals zero or the actual remaining backing. Alternatively, track the stranded claim explicitly in the backing-shortfall computation so `recapitalize` and `require_reserves` always see the full liability before any withdrawal can resolve against it.

### Proof of Concept
Existing in-repo reproductions:

```rust
// contracts/pool/tests/interest.rs:414-426
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, old_scaled);
cache.require_reserves(gross);
cache.burn_supply(burn);
cache.debit_cash(gross);
assert!(gross > 0, "stranded wiped position pays out real tokens");
assert_eq!(gross, fresh_cash, "S_old drains exactly the fresh deposit");
assert!(cache.cash() < fresh_claim, "fresh depositor lost funds");
```

and `contracts/pool/tests/flows.rs:3170-3251` shows the live seize → floor-clamp → `PoolInsolvent`-gated supply → recapitalize sequence, confirming the only barrier between the phantom claim and fresh deposits is the solvency/recap path rather than correct share accounting.
