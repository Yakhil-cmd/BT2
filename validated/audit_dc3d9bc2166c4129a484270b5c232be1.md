### Title
Webhook signature verification key is selected from an unverified field, letting an attacker forge cross-organization GitHub events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* webhook secret to validate a payload against by reading `repository.owner.login` (or `organization.login`) directly out of the still-unverified JSON body, before the HMAC signature has been checked. Once verification passes, the payload is handed to event handlers that resolve the target repository/stack (or, for `status` events, the target commit) from *other, independently attacker-controlled fields of the same body* (`repository.full_name`, `sha`). Because the field used to select the verifying secret and the field used to select the affected repository/commit are not the same value and neither is bound to the other by the signature, an attacker can pick an organization whose secret is weak/absent to pass verification while targeting a completely different organization's repository or an arbitrary commit SHA anywhere in the instance.

### Finding Description
`verify_signature` derives the verification key from attacker-supplied payload data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up that organization's own app config, including its own `webhook_secret`: [3](#0-2) 

`verify_webhook_signature` explicitly treats a blank/unset secret as "always verified": [4](#0-3) 

`webhook_secret` is a documented optional field (`webhook_secret: # nil`) in the multi-organization configuration schema: [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the *entire, still only partially-checked* payload to handlers: [6](#0-5) 

Handlers resolve their target repository from `repository.full_name` — a field that has no relationship whatsoever to the `repository.owner.login`/`organization.login` value used to pick the verifying secret: [7](#0-6) 

The `status` handler is worse still: it does not consult the repository at all — it matches purely on `sha`, meaning it will apply an attacker-forged CI status to *any* commit with that SHA across the entire multi-tenant Shipit instance: [8](#0-7) 

The `push` handler is scoped by `repository.full_name` via `stacks`, but that field is taken from the same unverified body used to choose the target, independent of which org's secret validated the request: [9](#0-8) 

**Equality broken:** the engine implicitly assumes `organization that authenticated the webhook == organization owning the repository the handlers act on`. In reality:
- `authenticating_org = payload.dig('repository','owner','login') || payload.dig('organization','login')`
- `acted_on_repo = payload.dig('repository','full_name')` (or, for `status`, "any repo containing a commit with this sha")

These two are read from independent, attacker-controlled fields of the same unsigned-at-read-time JSON body, so nothing forces them to refer to the same organization/repository.

### Impact Explanation
In a multi-organization Shipit deployment (a documented, supported configuration), if any one configured organization has no `webhook_secret` set (also a documented valid state) or a weaker/known secret, an attacker can:
1. Send a POST to the public `/github/webhooks` endpoint with `repository.owner.login` (or `organization.login`) set to the weakly-configured organization, so `verify_signature` selects that organization's app and `verify_webhook_signature` returns `true` unconditionally.
2. Set `repository.full_name` (for `push`/`check_suite`/etc.) or `sha` (for `status`) to point at a stack/commit belonging to a *different, properly secured* organization.
3. Have the handler act on that unrelated repository/commit as if it were a legitimate, signed GitHub event.

The most severe path is the `status` handler: it can be used to stamp an arbitrary commit SHA (belonging to any tracked repository system-wide) with a forged passing CI status for any required/blocking status context. Since Shipit gates deploys and continuous deployment on required/blocking statuses, this can make an otherwise-non-deployable or malicious commit appear deployable, resulting in an **unauthorized deploy** — a Critical-severity outcome per the engine's own trust model (signed webhooks are the sole gate for these state-changing events).

### Likelihood Explanation
Requires: (a) a multi-organization Shipit configuration, and (b) at least one configured organization with no/weak `webhook_secret` — both of which are explicitly documented, supported configurations rather than edge-case misuse. No credentials, GitHub App keys, or session are required by the attacker; only knowledge (or a plausible guess) of one org's slug that is unsecured. This is a design-level gap in binding the verifying identity to the acted-upon identity, not a one-off implementation typo, making it likely to recur across any multi-org deployment that leaves one organization's secret unset.

### Recommendation
- After selecting the app/organization used for signature verification, cross-check that `repository.owner.login`/`organization.login` used for verification matches the owner of `repository.full_name` (or the repository owning the commit `sha`) that the handler will act on; reject the event if they diverge.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-organization mode; require an explicit secret per organization, or fail closed.
- In `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup to commits belonging to the repository identified in the verified payload, not merely by SHA globally.
- Centralize "which organization authenticated this request" as a single canonical value threaded through to every handler, instead of letting each handler independently re-derive the acting repository from the raw payload.

### Proof of Concept
1. Configure Shipit with two organizations: `secure-org` (has `webhook_secret: s3cr3t`) and `open-org` (has `webhook_secret:` left blank, per the documented schema).
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit tracked under secure-org/real-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "open-org" }, "full_name": "open-org/anything" }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required.
3. `repository_owner` resolves to `open-org`; `Shipit.github(organization: 'open-org')` has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit under `secure-org/real-repo`, and calls `create_status_from_github!`, marking the required CI context as `success` even though the request was never actually signed by `secure-org`'s GitHub App.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
