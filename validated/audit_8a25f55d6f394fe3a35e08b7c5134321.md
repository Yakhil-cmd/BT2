**Why this doesn't qualify:**

1. **No unprivileged entrypoint.** `on_new_block_v2` and `on_new_epoch` are both `public(friend)` functions gated by `system_addresses::assert_vm(vm)` / `assert_aptos_framework(framework)`, and are only reachable through `aptos_framework::block`'s `block_prologue_ext_v3` and `aptos_framework::reconfiguration_with_dkg::finish`, both of which execute exclusively inside the VM-driven block prologue — never from a user-submitted transaction, authenticator, or REST/BCS input path. [1](#0-0) [2](#0-1) 

2. **No concurrency exists to "race."** Move transaction execution is single-threaded and deterministic. Inside `block_prologue_ext_v3`, `decryption::on_new_block_v2` is called first, synchronously, followed conditionally by `reconfiguration_with_dkg::try_start_with_chunky_dkg()` / `try_advance_reconfig()` — a strict, in-order call sequence within one function body, not two independently-scheduled friends racing each other. [3](#0-2) 

3. **`try_advance_reconfig` → `finish` → `decryption::on_new_epoch`** only fires after DKG/Chunky-DKG completion checks pass, again fully sequential and deterministic within the same VM call stack, not concurrent with the prologue's own state update. [4](#0-3) [5](#0-4) 

Since the path never starts from an unprivileged transaction/authenticator/API and there is no execution-model mechanism for the described interleaving, this falls outside the admission boundary scope required for a valid finding.
