### Title
Webhook signature is verified per-organization while `status` events are applied to commits with no repository/organization scoping, allowing cross-repository forgery of commit statuses - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), then hands the *entire raw payload* to whichever handler matches `X-Github-Event`. `Shipit::Webhooks::Handlers::StatusHandler`, however, never checks that the commit it updates belongs to a stack/repository under the organization whose secret was used to authenticate the request — it looks up commits globally by `sha` alone. This breaks the trust binding "the organization that authenticated the webhook == the repository being written to."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` selects the webhook secret to check with based solely on the organization: [1](#0-0) [2](#0-1) 

The engine explicitly supports multiple GitHub Apps/organizations, each with its own independent `webhook_secret` and installation: [3](#0-2) [4](#0-3) 

Once the HMAC check passes for *some* configured organization, the full JSON payload is dispatched to handlers keyed only by `X-Github-Event`: [5](#0-4) 

`Shipit::Webhooks::Handlers::StatusHandler` is registered for the `status` event: [6](#0-5) 

Its parameter schema requires only `sha`, `state`, and optional metadata — no `repository` field is required or checked, and it does not use the base `Handler#repository_name`/`stacks` scoping helper at all: [7](#0-6) 

The lookup `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` matches **any** commit in the entire Shipit database that has that SHA, irrespective of which stack/repository/organization it belongs to. Since Git commit SHAs are derived from public commit metadata (and are visible to anyone with read access to a repository, e.g. via the GitHub UI/API), an attacker only needs to know a target commit's SHA — not any special access to that repository — to target it.

Because the signature check only proves "this request was signed with organization X's webhook secret," and organization X may be a completely different, attacker-controlled organization configured in the same multi-tenant Shipit instance, this equality is violated:
`organization that authenticated == repository/commit that gets written`.

The status creation is not a no-op: it feeds directly into deploy-readiness logic used to gate/trigger merges and continuous deployment for the *victim's* stack: [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who legitimately controls one GitHub organization/App configured in a multi-tenant Shipit deployment (their own webhook secret) can forge a `status` webhook naming a SHA belonging to a commit in a completely unrelated stack/organization tracked by the same Shipit instance. By setting `state: success` and a `context` matching a `ci.require` entry, the attacker can mark a victim's commit as CI-passing, which (per `Status#enable_ci_on_stack` and `Commit#add_status` → `stack.schedule_merges`/`schedule_continuous_delivery`) can cause the merge queue to advance or continuous deployment to trigger for a repository the attacker has no access to. This matches the "unauthorized deploy, rollback, or merge" and "cross-repository writes" impact categories, since it lets an unprivileged-relative-to-victim actor write `Status` records against, and trigger deploy/merge side effects for, a repository outside their authorization boundary.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with the multi-organization GitHub App schema (explicitly documented and supported), (2) attacker control of one configured organization's webhook secret (achievable simply by being the legitimate owner of that org/app — no compromise of the victim needed), and (3) knowledge of a target commit SHA in the victim stack (trivially obtainable if the victim repo is public, or otherwise via any read access). No compromise of the victim's credentials, GitHub App, or Shipit session is required. In a single-organization deployment the practical severity is smaller (any push access within the org can already forge cross-repo statuses within that org), but the multi-org case crosses an explicit authorization boundary Shipit sets up (one App/secret per org, presumably for isolating unrelated orgs/tenants).

### Recommendation
Bind the webhook signature verification to the specific repository/commit being acted upon, not just the organization: after verifying the signature, `StatusHandler` (and any other handler that doesn't already scope by `repository.full_name`) should re-validate that the commit's `stack.repository` belongs to the same organization (or better, the same specific repository) whose secret authenticated the request, e.g. by requiring and checking `repository.full_name`/`repository.owner.login` against `commit.stack.repository` before calling `create_status_from_github!`. Alternatively, require `repository` in `StatusHandler`'s parameter schema and reject/short-circuit if it doesn't match the commit's own stack repository.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret` values (per `docs/setup.md`'s multi-app schema).
2. As the operator of `AttackerOrg`'s installed GitHub App, obtain a commit SHA from a `VictimOrg` repository tracked by the same Shipit instance (e.g., from the public GitHub commit history) that is currently pending CI.
3. Craft a `status` event JSON body: `{"sha": "<victim_sha>", "state": "success", "context": "<required-ci-context>", "repository": {"owner": {"login": "AttackerOrg"}}}` and sign it with `AttackerOrg`'s `webhook_secret` (`sha1=` HMAC over the raw body), matching the check in `app/controllers/shipit/webhooks_controller.rb:24-30`.
4. POST it to `/github/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
5. `verify_signature` succeeds because it only checks `AttackerOrg`'s secret against `repository_owner = "AttackerOrg"`. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then runs `Commit.where(sha: "<victim_sha>")`, finds the commit belonging to `VictimOrg`'s stack, and creates a `success` status on it — despite the attacker having no relationship to `VictimOrg`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
