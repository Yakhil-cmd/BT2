I now have enough to make a determination.

The vulnerability is real. The core defect is in `Shipit::Webhooks::Handlers::StatusHandler#process`:### Title
Cross-tenant status forgery via global, repository-unscoped `Commit.where(sha:...)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies an incoming `status` webhook to *every* `Commit` row in the entire database that shares the reported `sha`, without checking that the commit belongs to a stack whose repository matches the webhook's authenticated `repository_owner`/`repository.full_name`. Because Git commit objects are content-addressed, the same SHA can legitimately (and trivially) exist in commits belonging to unrelated repositories/organizations (forks, mirrors, copied history), so a webhook that is validly signed for organization A can silently flip CI status on a commit that actually belongs to organization B's stack, feeding `MergeRequest#all_status_checks_passed?` a false "success" signal.

### Finding Description
The binding that must hold is:

`organization authenticated by verify_signature (repository_owner in the payload) == organization that owns the Stack/Repository of every Commit row mutated as a result of that payload`

Tracing the path:

1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON payload (`params.dig('repository','owner','login')`, line 59-61). This only proves that the request was really sent by GitHub for *that* org's installation — it says nothing about which `Commit`/`Stack` rows may be touched.
2. `WebhooksController#create` then dispatches to `Shipit::Webhooks::Handlers::StatusHandler#process`: [1](#0-0) 
   This does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global, unscoped** query across the whole `commits` table, with no join/filter on `stack.repository.owner`/`full_name` matching the authenticated `repository_owner`.
3. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally creates a `Status` on that commit, which (via `Status#enable_ci_on_stack`/`schedule_continuous_delivery`, `app/models/shipit/status.rb:18-19,42-44`) enqueues `ProcessMergeRequestsJob`.
4. `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:21-26`) calls `merge_request.all_status_checks_passed?`, which is `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` (`app/models/shipit/merge_request.rb:193-197`) — this reads the `Status` record just written by the attacker's webhook, with no re-check of which organization created it.

Exploit flow: an attacker who owns a repository/org where the (shared) Shipit GitHub App is installed (a very common multi-tenant SaaS pattern documented in `docs/setup.md:182-209` and `test/dummy/config/secrets_double_github_app.yml`, where one GitHub App's webhook secret is reused verbatim across multiple organization entries in `secrets.github`) can:
- Obtain a commit SHA identical to the victim's PR head/merge commit — trivial when the victim's PR is on a public repo, on a fork of the same public upstream, or in any scenario where the same git commit object legitimately exists in more than one repository (forks/mirrors naturally preserve SHAs).
- Push/create that exact commit into their own attacker-controlled repository and set/trigger a `success` status on it (via their own CI, or directly via the GitHub Statuses API, since they own that repo).
- GitHub sends a genuinely, correctly-signed `status` webhook for the attacker's own repository/org.
- `verify_signature` passes (it correctly authenticates "attacker's org sent this"), but `StatusHandler#process` does not check that the commit it writes the `Status` onto actually belongs to a stack under the attacker's org — it matches by `sha` alone, globally.
- The victim's unrelated `MergeRequest`/`Commit` (which never received real status from the victim's own CI) now shows `success`, and `all_status_checks_passed?` returns `true`, allowing `ProcessMergeRequestsJob` to call `merge_request.merge!` and merge/queue a PR that was never actually approved by CI.

Existing guards (`verify_signature`, `ExplicitParameters` schema in `StatusHandler.params`, `drop_unhandled_event`) only validate the shape/authenticity of the webhook sender, not the scope of which `Commit` rows it is permitted to affect. No code path in `StatusHandler#process` or `Commit#create_status_from_github!` re-derives the repository/org from the authenticated payload and filters the `Commit` lookup accordingly.

### Impact Explanation
A successful attacker can inject a fabricated `success` (or other) CI status onto an arbitrary victim organization's commit/merge-request as long as they can get an identical-SHA commit into a repository they control that shares the same (or a shared-secret) GitHub App installation as Shipit. This can unlock `MergeRequest#all_status_checks_passed?` to return `true` for a PR that never passed real CI, leading `ProcessMergeRequestsJob` to merge it — an unauthorized merge of code into the victim organization's protected branch. This is a payload from one tenant mutating another tenant's stack/commit/merge-request state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The attack is repeatable against any repository whose commits happen to share a SHA reachable by the attacker, and the blast radius spans all organizations configured under the Shipit instance (single global commits table, no per-tenant partitioning of the lookup).

### Likelihood Explanation
Preconditions: the Shipit deployment must host multiple organizations/repos (multi-tenant), the victim `MergeRequest` must be `pending`/awaiting status checks, and the attacker needs a commit with an identical SHA reachable in a repo they control that can deliver a validly-signed webhook to the same Shipit instance. Getting an identical SHA is realistic for public/forked repositories (git objects are content-addressed and are commonly shared byte-for-byte across forks) but harder for genuinely private, unrelated code where the attacker cannot know/reproduce the exact tree+metadata needed to reproduce the SHA. Attacker cost is otherwise low (no privileged Shipit access, no secrets needed) once SHA reuse is achievable — this is a plausible, not merely theoretical, condition for any Shipit instance tracking forks/mirrors of shared/public code, or any setup using one shared GitHub App webhook secret across several organizations, which the codebase's own documentation explicitly supports.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to only commits whose owning `Stack`/`Repository` matches the `repository_owner`/`repository.full_name` from the authenticated webhook payload (e.g., join `commits` to `stacks`/`repositories` and filter by `owner`/`full_name`), rather than matching on `sha` alone across the entire database. The same repository-scoping should be audited on other global-`sha` lookups (e.g., `check_suite`/`check_run` handlers) that ultimately affect `MergeRequest#all_status_checks_passed?`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):
```ruby
test "status webhook from one organization must not affect a commit belonging to a different organization's stack" do
  victim_stack = shipit_stacks(:shipit)              # owned by org "shopify"
  attacker_stack = shipit_stacks(:cyclimse)          # owned by a different org, e.g. "attacker-org"

  shared_sha = "cafebabe" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "victim commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "victim commit")

  merge_request = victim_stack.merge_requests.create!(number: 999, head: victim_commit)

  # Binding under test, stated explicitly BEFORE tracing:
  # organization_authenticated_by_webhook == organization owning merge_request.stack
  assert_not_equal attacker_stack.repository.owner, victim_stack.repository.owner

  refute_predicate merge_request, :all_status_checks_passed? # baseline: no status yet

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate valid signature scoped to attacker's org only
  body = { 'sha' => shared_sha, 'state' => 'success',
           'repository' => { 'full_name' => attacker_stack.repository.full_name,
                              'owner' => { 'login' => attacker_stack.repository.owner } } }.to_json

  post :create, body:, as: :json

  merge_request.reload
  assert_predicate merge_request, :all_status_checks_passed?, # FAILS today: attacker-authenticated webhook flips victim's merge request to passing
    "attacker's own-org webhook must not be able to mark the victim organization's merge request as CI-passed"
end
```
This proves that a webhook authenticated solely for `attacker_stack`'s organization can, through the unscoped `Commit.where(sha:)` lookup, cause `victim_stack`'s `MergeRequest#all_status_checks_passed?` to flip to `true` despite the two stacks belonging to different organizations — the exact broken binding described.
