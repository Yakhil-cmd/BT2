### Title
`review_stacks_enabled` is not evaluated for `allow_with_label`/`prevent_with_label` repositories due to an operator-precedence bug in `ReopenedHandler#unarchive?` and `OpenedHandler#provision?` - (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`ReopenedHandler#unarchive?` and `OpenedHandler#provision?` mix `&&` and `||` without parentheses around the `review_stacks_enabled` check, so Ruby's operator precedence only applies `review_stacks_enabled` to the `allow_all` branch, not to the `allow_with_label` or `prevent_with_label` branches. Consequently, once a repository administrator disables `review_stacks_enabled`, PR reopen (and initial open) events on `allow_with_label`/`prevent_with_label` repositories still trigger `ReviewStackAdapter#unarchive!`/`create!`, re-queuing provisioning and running the new branch's `shipit.yml` content through `Command#start`/`PTY.spawn`.

### Finding Description
The binding the code is supposed to enforce is: `repository.review_stacks_enabled == true` must gate *every* provisioning/unarchiving disjunct, i.e. `unarchive? == (review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)))`.

The actual code in `reopened_handler.rb`: [1](#0-0) 
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` binds tighter than `||` in Ruby, this parses as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
`review_stacks_enabled` is scoped only to the first disjunct. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `unarchive?` is true purely based on label presence, regardless of `review_stacks_enabled`. The identical pattern exists in `OpenedHandler#provision?`: [2](#0-1) 

Exploit flow: with the repo configured for `allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled` true, attacker opens a PR (label present) → `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!` → `create!` builds a `Stack` and queues it via `Shipit::ReviewStackProvisioningQueue.add`. [3](#0-2)  The PR is then closed (`ClosedHandler#process` unconditionally calls `review_stack.archive!` with no `review_stacks_enabled` check at all) [4](#0-3) , archiving the stack. The repository owner then disables `review_stacks_enabled`, believing this halts all future review-stack provisioning. Attacker reopens the PR (having pushed new commits/branch content, e.g. a malicious `shipit.yml`, to `head.ref`) → `ReopenedHandler#process` calls `respond_to_pull_request_reopened?` → `unarchive?` evaluates true (label-only condition satisfied) despite `review_stacks_enabled == false` → `stack.unarchive!` → `ReviewStackAdapter#unarchive!` re-enqueues via `Shipit::ReviewStackProvisioningQueue.add(stack)` and unarchives the stack. [5](#0-4)  The queue worker then provisions the stack (`ReviewStackProvisioningQueue#provision`) [6](#0-5) , ultimately running the attacker's new branch content through the deploy pipeline's `Command#start`/`PTY.spawn`.

No existing guard prevents this: `verify_signature`/`drop_unhandled_event` only validate that the webhook is genuinely from GitHub for that repository (irrelevant here — this is a real webhook, not forged), and none of `ExplicitParameters`, model validations, or `EnvironmentVariables#permit` check `review_stacks_enabled` at all — that check exists solely in the handler predicate methods, which are broken by precedence. The repository test suite (`reopened_handler_test.rb`) exercises `allow_with_label`/`prevent_with_label` behaviors but never sets `review_stacks_enabled: false`, so this gap is untested.

### Impact Explanation
This causes execution of attacker-supplied branch content (via the review-stack provisioning pipeline, which shells out through `Command`/`PTY.spawn`) on a repository whose operator explicitly disabled the review-stacks feature — a control-bypass leading to unauthorized command execution/RCE on the deploy host, matching the Critical category ("RCE on the deploy host via `Command`/`PTY.spawn`"). It is repeatable indefinitely against any repository configured with `provisioning_behavior` of `allow_with_label` or `prevent_with_label` (a common, documented configuration), for as long as that repository accepts PRs from the attacker; it is not limited to a single occurrence, since open/close/reopen can be repeated with new attacker-controlled commits each time.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (not `allow_all`), must have had `review_stacks_enabled` true at some point (to create/label the stack) and then flipped to false, and the attacker must be able to open/label/close/reopen a PR against it (attacker needs at minimum PR-open capability, and label-toggle capability if targeting `allow_with_label`/`prevent_with_label` specifically — label toggling on someone else's PR generally requires write access, but an attacker opening a PR against their own fork-target repo, or a maintainer/contributor with label rights, satisfies this). This requires no secrets, no forged signatures, and no privileged Shipit role — only ordinary GitHub PR actions reflected as legitimate webhooks. The bug is a static logic error (not timing-dependent), so it fires deterministically whenever the precondition combination occurs, making it highly feasible and fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three disjuncts in both `ReopenedHandler#unarchive?` and `OpenedHandler#provision?`:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `OpenedHandler#provision?`, and audit `LabeledHandler`/`UnlabeledHandler` (which already correctly AND `review_stacks_enabled` outside the parenthesized `archive?`/`unarchive?` calls) to confirm they are not similarly affected.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` (or a new test file under `test/models/shipit/webhooks/handlers/pull_request/`):
1. Configure `shipit_repositories(:shipit)` with `provisioning_behavior: :allow_with_label`, `label: "pull-requests-label"`, `review_stacks_enabled: true`.
2. Send `pull_request_opened` payload with the label present via `OpenedHandler#process`; assert a `Stack` is created and `assert_pending_provision(stack)`.
3. Archive the stack (simulate `ClosedHandler#process` or call `create_archived_stack`).
4. Set `repository.update!(review_stacks_enabled: false)`.
5. Build `pull_request_reopened` payload with the label present and a new `head.ref`/branch content; call `ReopenedHandler.new(payload).process`.
6. Assert the binding is violated: `assert_not stack.reload.archived?` and `assert_pending_provision(stack)` — i.e., the stack unarchives and re-queues provisioning even though `repository.review_stacks_enabled == false`, proving `unarchive?` ignored the disabled flag for the `allow_with_label` behavior.
