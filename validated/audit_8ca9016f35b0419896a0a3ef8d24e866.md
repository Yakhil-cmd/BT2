### Title
Unsanitized PR title allows ANSI/control-sequence injection into `gh pr checkout` interactive selection prompt - ([File: pkg/cmd/pr/checkout/checkout.go])

### Summary
`promptingPRResolver.Resolve` builds the candidate strings shown in the `gh pr checkout` interactive picker directly from `pr.Title` after only running it through `text.RemoveExcessiveWhitespace`, which strips/collapses whitespace but does not strip ANSI escape (`0x1B`) sequences. An attacker who opens a PR with a title containing raw ESC sequences can therefore inject terminal control codes into the rendered `prompter.Select` menu.

### Finding Description
In `pkg/cmd/pr/checkout/checkout.go`, `promptingPRResolver.Resolve` constructs each menu candidate as: [1](#0-0) 
`text.RemoveExcessiveWhitespace` only touches Go's `\s+` whitespace class (space, tab, `\n`, `\r`, `\f`, `\v`): [2](#0-1) 
This means literal `\r`/`\n` in a title are collapsed to a single space (so CR/LF-based line-overwrite tricks are neutralized), but ESC-based CSI/OSC sequences (byte `0x1B`) are left completely untouched, since ESC is not a whitespace character. `shared.PrStateWithDraft` similarly returns the raw `pr.State`/"DRAFT" without sanitization, but that field is not attacker-controlled. [3](#0-2) 

The candidate strings are then handed straight to `r.prompter.Select(...)`, which passes them into the underlying `huh`/`survey` TUI renderer with no escape-sequence sanitization at this call site: [4](#0-3) 

By contrast, the codebase does have infrastructure elsewhere specifically built to prevent this class of issue for untrusted content — e.g. `iostreams.Untrusted`/`ContainsEscapeSequence`/`asciisanitizer` for content streams, and a bespoke `sanitizeForTerminal` helper used when rendering skill metadata: [5](#0-4) [6](#0-5) 
None of these sanitizers are applied to `pr.Title` before it is placed into the interactive PR-checkout candidate list.

`pr.HeadLabel()` (owner:branch) is comparatively low-risk here because Git ref names are constrained by `git check-ref-format` rules, which reject ASCII control characters, so `pr.HeadRefName` cannot itself carry raw ESC bytes. The PR title, however, is free-form text accepted by the GitHub API/UI and is not similarly constrained.

### Impact Explanation
An attacker-controlled PR title containing ANSI cursor-movement/erase sequences can manipulate the rendered menu (e.g., overwrite/hide other option lines, redraw fake option text, or move the cursor) when a victim runs `gh pr checkout` interactively. Because the final selection is still resolved by list index against the real `listResult.PullRequests[selected]`, the direct code-execution/credential-exfiltration path is not proven, but this is a real terminal output-integrity/UI-spoofing issue: the victim can be visually deceived into believing they are selecting/checking out a different PR/branch than the one actually chosen, which can be leveraged as a precursor to checking out attacker-controlled code under false pretenses. This corresponds to a low/medium bounty-class "spoofing via unsanitized terminal output" issue rather than a full RCE primitive.

### Likelihood Explanation
Fully attacker-reachable with no special privileges: any user can open a PR with a crafted title against a public repo, and any victim who runs `gh pr checkout` interactively (a normal, common workflow) against that repo will trigger the vulnerable code path. No git-ref restriction applies to the title field, so the ESC-byte payload survives into the candidate string unmodified.

### Recommendation
Sanitize `pr.Title` (and any other attacker-influenced fields rendered into interactive prompts) with the existing `asciisanitizer`/`iostreams.Untrusted` machinery (or the `sanitizeForTerminal`-style helper already used in `pkg/cmd/skills/list/list.go`) before building candidate strings in `promptingPRResolver.Resolve`, rather than relying solely on `text.RemoveExcessiveWhitespace`.
