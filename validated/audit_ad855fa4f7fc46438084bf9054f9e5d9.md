### Title
`StatusHandler#process` writes commit statuses to any Stack whose commit matches the SHA, ignoring the organization whose webhook signature authenticated the request - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook against exactly one GitHub organization derived from the payload (`repository_owner`) using that organization's `webhook_secret` [1](#0-0) [2](#0-1) . However `StatusHandler#process`, invoked after that check passes, looks up the target record with `Commit.where(sha: params.sha)` — a global, unscoped query over every `Commit` in the database, regardless of which stack/repository/organization it belongs to — and writes a new `Status` for every match [3](#0-2) . This is exactly the same class of bug as the report: the authorization check is performed against one identity (the organization that signed the request) while the mutating action is performed on data selected using unrelated, attacker-influenced fields (the SHA) that are never bound to that identity.

### Finding Description
- Authentication binding: `verify_signature` picks the GitHub App/secret for `repository_owner` (derived from `params['repository']['owner']['login']` or `params['organization']['login']`) and validates the raw body's HMAC against that org's `webhook_secret` [4](#0-3) . This only proves the payload was signed by (or on behalf of) the app installed for that specific organization.
- Mutation target: unlike `PushHandler` and `CheckSuiteHandler`, which scope their queries to `stacks` (repository-bound) [5](#0-4) [6](#0-5) , `StatusHandler` never restricts by repository or stack — it matches on `sha` alone across the whole `Commit` table [7](#0-6) .
- The write goes through `Commit#create_status_from_github!`, which creates the `Status` scoped to that commit's own `stack_id` — not to any stack belonging to the organization that authenticated the request [8](#0-7) , and `Status.replicate_from_github!` persists it directly with that `stack_id` [9](#0-8) .
- The binding that should hold is: `organization authenticated by verify_signature == organization owning the stack/repository whose Commit/Status is mutated`. Before the request: the attacker's organization (call it Org A) is authenticated. After processing: any `Stack` anywhere in the Shipit instance — including Stacks belonging to a different organization/repository (Org B) — whose `commits` table happens to contain a `Commit` row with the same `sha` gets a new `Status` written and `add_status` triggers `deployable_status`/`schedule_continuous_delivery` on Org B's commit/stack [10](#0-9) .

### Impact Explanation
`add_status` can flip a commit from non-deployable to deployable (`success`) and calls `stack.schedule_merges` / triggers continuous delivery for that commit's stack [11](#0-10) . Because the Stack acted upon is selected purely by SHA match rather than by the authenticated organization, a status event legitimately signed for Org A's repository can cause `Status` writes and downstream deploy/merge scheduling on a Stack belonging to a completely different, unrelated organization/repository (Org B) if any commit SHA collision or shared-history commit exists between the two. This is a cross-repository/cross-organization write and can lead to an unauthorized deploy of Org B's stack initiated purely via Org A's authenticated webhook — matching the "cross-repository writes" / "unauthorized deploy" Critical-impact class.

### Likelihood Explanation
Exploitation requires two commits (in different Stacks/orgs tracked by the same Shipit instance) to share an identical SHA — either through legitimately shared history (e.g., the same upstream repository added as multiple Stacks, forks, or vendored history) or a deliberately engineered SHA-1 collision. Like the original report, this is explicitly not a hard restriction ("with just time and funds it can be done" — SHA-1 collision attacks such as SHAttered are practical with sufficient compute), and the far more common trigger is simply operating multiple Stacks that track the same or overlapping repository history, which is a supported, ordinary Shipit configuration. No privileged token, session, or repository write access to the victim Stack is required — only a legitimately signed webhook event for the attacker's own organization/repository.

### Recommendation
Scope `StatusHandler#process` (and any other handler that queries by content-derived identifiers such as SHA) to the repository/organization that was authenticated by `verify_signature`, e.g. restrict `Commit.where(sha: params.sha)` to `stacks.where(...)` filtered by the repository named in the payload, mirroring the scoping already used in `PushHandler` and `CheckSuiteHandler`.

### Proof of Concept
1. Attacker controls (or has push access to) a repository under Organization A, which has a legitimately configured Shipit GitHub App installation with its own `webhook_secret`.
2. Attacker sets a commit status via the normal GitHub API/UI on a commit in Org A's repo whose SHA is known (or engineered) to also exist as a `Commit` record belonging to a Stack under Organization B (a different Shipit-tracked repository/org).
3. GitHub sends the `status` webhook to Shipit, correctly signed with Org A's `webhook_secret`; `verify_signature` passes because it only validates the signature for Org A [1](#0-0) .
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the matching commit belonging to Org B's Stack, then calls `create_status_from_github!`, writing a new `Status` scoped to Org B's stack and potentially firing `deployable_status`/continuous delivery for Org B's stack [3](#0-2) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
