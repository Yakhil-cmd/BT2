### Title
Uncontrollable node crash via reachable `throw Error(...)` assertions in oscript/AA formula evaluation - ([File: formula/evaluation.js])

### Summary
`op_panic` (GHSA-4mw5-2636-4535) shows how a JS-sandboxed scripting host can expose a way for the sandboxed (attacker-controlled) code to force a hard panic in the process hosting the runtime, defeating the sandbox's isolation guarantee. ocore's oscript/AA formula engine (`formula/evaluation.js`, driven by attacker-supplied AA definitions and triggers via `aa_composer.js`) is architecturally meant to behave the same way as a sandbox: formula errors must be turned into `setFatalError(...)` results that are returned through a callback and converted into a bounced AA response, never into a raw JS exception. However, the evaluator is riddled with defensive `throw Error(...)` "should never happen" assertions [1](#0-0) [2](#0-1) [3](#0-2)  that assume the separate `formula/validation.js` pass makes the corresponding evaluation branch unreachable. Since validation and evaluation are two independently maintained code paths operating over the same nearley-parsed AST, any divergence between them lets an attacker's AA/formula reach one of these `throw Error()` calls during evaluation.

### Finding Description
The oscript evaluator (`formula/evaluation.js`) parses and executes attacker-controlled AA code (via `evaluate()`), and is explicitly designed so that any problem in the input formula becomes a soft failure through `setFatalError()`, which stores `fatal_error` and invokes the callback instead of throwing [4](#0-3) . This is the sandbox contract: no matter what the AA author writes, the engine must not throw a raw JS exception that escapes the callback-based execution model.

Despite this contract, the file contains numerous unguarded `throw Error(...)` statements that fire directly instead of calling `setFatalError`, for example:
- `throw Error("function called after a return");` in `callFunction()` [1](#0-0) 
- `throw Error("test evaluated to object " + res);` in the `ifelse` handler [2](#0-1) 
- `throw Error("unrecognized function argument: " + func_expr);` in `evaluateFunctionExpression()` [3](#0-2) 
- `throw Error("neither local nor remote: " + funcInfo);` inside the `foreach`/`map`/`filter`/`reduce` handler [5](#0-4) 
- `throw Error("unknown type of max_remote_complexity: " + max_remote_complexity);` in `checkMaxRemoteComplexity()` [6](#0-5) 

These are written as defensive assertions on the premise that `formula/validation.js` already rejected any AST shape that could hit them (e.g. `validation.js`'s own `evaluate()` walks the exact same AST and rejects bad `func_call`/`remote_func_call`/`ifelse` shapes before the formula is ever accepted into an AA definition/trigger) [7](#0-6) [8](#0-7) . Because validation and evaluation are two hand-written, independently evolving implementations over the same grammar, any missed edge case (a new grammar production, an MCI-gated feature check that differs subtly between the two files, a getter/remote-function code path, etc.) turns an "unreachable" assertion into an attacker-reachable one.

Crucially, these throws happen deep inside asynchronous, callback-driven recursion (`evaluate()`, `async.eachSeries`, `setImmediate`), so they are never wrapped by a `try/catch` anywhere in the call chain from `aa_composer.js`'s `handleTrigger`/`evaluateAA` [9](#0-8)  up through `writer.saveJoint` or `network.js`'s dry-run path [10](#0-9) . A synchronous throw from inside one of these callbacks becomes an "uncaught exception" at the top of the Node.js event loop.

ocore installs a global handler that turns any uncaught exception into a guaranteed process crash: [11](#0-10) 
```
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```
This is the direct analog of `op_panic`: the scripting host (oscript engine) is supposed to sandbox attacker-controlled logic (AA formulas), but a reachable internal assertion converts attacker input into an unconditional crash of the entire containing process — exactly the class of bug the advisory describes, just realized through a defensive `throw` instead of an exposed native op.

### Impact Explanation
AA trigger/definition processing is consensus-critical: `handleAATriggers`/`handlePrimaryAATrigger` run deterministically on every full node when a unit posted to an AA address becomes stable [12](#0-11) , and `conf.bDryRunNewTriggers` additionally causes every full node to dry-run AA triggers as soon as a triggering unit is merely validated, before it is even stable [10](#0-9)  (with the comment "if it would crash, let it crash now"). If an attacker can construct any AA definition/trigger combination that reaches one of these unguarded `throw Error()` statements, every full node that processes that unit — both at dry-run time and later at trigger-execution time — hits the same code path and is forced through `process.on('uncaughtException')` to crash. Because this can be triggered by a single ordinary unit posted to any (even attacker-deployed) AA address, this is a network-wide denial-of-service: nodes crash/restart when replaying the same malicious unit from the DAG, and the network is unable to make further progress on this and dependent activity until operators patch or filter the offending unit. This matches the "network unable to confirm new units" criterion.

### Likelihood Explanation
Likelihood is Medium: this is not a single one-line reproducible bug, but a structural weakness — the formula evaluator relies on validation/evaluation code staying in lock-step to keep dozens of `throw Error()` assertions unreachable, and any future feature addition, MCI upgrade gate, or already-existing subtle mismatch between `formula/validation.js` and `formula/evaluation.js` (both very large, hand-maintained ~3000+ line files evaluating the same AST) is a plausible source of a concrete attacker-triggerable path. The historical presence of edge-case bug-fix tests (e.g. `invalid selector`, `invalid state var name`, `bad formula with semantic error location details` in `test/aa_composer.test.js`/`test/aa.test.js`) shows that such validation/evaluation mismatches have occurred before and were only caught after being found reachable.

### Recommendation
- Audit every `throw Error(...)` in `formula/evaluation.js` (and the analogous ones in `aa_composer.js`, e.g. `handleTrigger`'s `throw Error('bad AA definition ' + arrDefinition)` [13](#0-12) ) that is reachable from attacker-controlled AA/trigger data and convert them to `setFatalError()` calls that bounce the AA response instead of throwing.
- Add a top-level `try/catch` around the synchronous portions of `evaluate()`/`callFunction()`/`evaluateFunctionExpression()` so that any residual defensive assertion degrades to a bounced/failed AA response (`setFatalError`) rather than an uncaught exception that reaches `process.on('uncaughtException')`.
- Add fuzzing/differential testing between `formula/validation.js` and `formula/evaluation.js` to detect AST shapes accepted by validation but mishandled by evaluation (and vice versa).
- Reconsider the "crash the process to avoid an inconsistent state" policy in `network.js`'s `uncaughtException` handler for exceptions clearly originating from `formula/evaluation.js`/`aa_composer.js` sandboxed execution, since it converts any oscript-engine bug into an automatic, network-wide DoS primitive.

### Proof of Concept
A fully reproducible AA formula was not confirmed within the scope of this analysis (the index does not let me execute the parser/validator to test candidate ASTs), so this should be treated as a structural finding rather than a verified exploit. The conceptual PoC is:
1. Attacker deploys an AA whose `getters`/`init`/`state` formula is crafted so that the nearley-parsed AST passes `formula/validation.js`'s `evaluate()` walk (e.g. via a `func_call`/`remote_func_call`/`ifelse`/`foreach` construct combined with an MCI-gated feature check) but drives `formula/evaluation.js`'s `evaluate()` into one of the unguarded `throw Error(...)` branches identified above (e.g. `callFunction` firing after `early_return` was already consumed via a nested `remote_func_call`/getter call, or a `func_expr` shape not covered by `evaluateFunctionExpression`).
2. Attacker posts a trigger unit paying to that AA address.
3. Every full node (both via the `bDryRunNewTriggers` pre-check in `network.js` and via `handleAATriggers` at stabilization) evaluates the formula, hits the `throw Error(...)`, and crashes via the global `uncaughtException` handler that re-throws to kill the process — before Devin can further verify the exact triggering AST, a background engineer with full test-harness access (`formula/evaluation.js` + `formula/validation.js` + `test/aa.test.js`/`test/aa_composer.test.js`) should attempt to construct a concrete formula reaching one of the flagged `throw Error()` lines to confirm exploitability end-to-end.
