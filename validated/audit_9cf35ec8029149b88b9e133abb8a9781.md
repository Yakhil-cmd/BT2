### Title
Cross-tenant commit-status forgery enqueues ContinuousDeliveryJob for an unrelated victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by SHA (`Commit.where(sha: params.sha)`) without scoping the query to the repository that authenticated the webhook, unlike `PushHandler`, which correctly uses the `Handler#stacks` helper scoped by `payload['repository']['full_name']`. Any organization with its own valid `webhook_secret` can therefore create a `Status` (and trigger `Commit#schedule_continuous_delivery`) on a commit that belongs to a completely different tenant's stack, as long as a commit with the same SHA exists in both repositories' history (trivially achievable by forking a public/shared repository).

### Finding Description
The broken binding is: `organization whose webhook_secret verified the payload == organization owning the stack of the commit(s) matched by params.sha`. This should hold but does not.

- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) only verifies that the payload was signed by the `webhook_secret` configured for `repository_owner` (`payload.dig('repository','owner','login')`). It says nothing about which commits/stacks the payload is allowed to affect.
- The `Handler` base class provides a `stacks` helper (app/models/shipit/webhooks/handlers/handler.rb:32-34) that correctly scopes to `Repository.from_github_repo_name(repository_name)`, and `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) uses this scoping to only touch stacks belonging to the repository named in the payload.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does **not** use this `stacks` scope. It instead runs:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit` records are unique per `(stack_id, sha)` (see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique by `sha`. So the same SHA can legitimately exist in many different stacks (e.g., because two Shipit-tracked repositories share commit history through a fork). The lookup by bare SHA will match commit rows across every stack/tenant that happens to contain that SHA, regardless of which repository's webhook actually delivered the payload.

Attack: attacker owns organization A with a legitimate `webhook_secret` (a normal, low-privilege onboarding precondition explicitly allowed by the question). Attacker forks the victim's public/shared repository into org A (or otherwise obtains a repo whose history overlaps with the victim stack's tracked repository), so a commit SHA `X` exists both in the victim's Shipit stack (org B) and in the attacker's own repo (org A). Attacker sends a `status` webhook event to `POST /webhooks` for `repository.full_name = "orgA/repoName"`, `sha = X`, `state = success`, signed with org A's own real `webhook_secret`. `verify_signature` passes because the signature is valid for org A. `StatusHandler#process` then matches `Commit.where(sha: X)`, which includes the victim's commit row belonging to stack B, and calls `commit.create_status_from_github!(params)` on it — for a commit and stack the attacker never authenticated against. The new `Status` triggers `after_commit :schedule_continuous_delivery` (app/models/shipit/status.rb:19,42-44) → `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287), which, if stack B has `continuous_deployment` enabled and is otherwise deployable, calls `ContinuousDeliveryJob.set(wait: ...).perform_later(stack)` for the victim's stack — entirely driven by the attacker's own webhook delivery.

None of the existing guards prevent this: `verify_signature` only checks the signer's identity, not the target commit/stack; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc, not repository ownership; there is no `force_github_authentication`, `User#authorized?`, or `stacks` scoping applied in `StatusHandler#process` as there is in `PushHandler#process`.

### Impact Explanation
An attacker who controls any onboarded organization (or repository within it) on a shared Shipit instance can forge a commit-status webhook that creates a `Status` row on, and can enqueue `ContinuousDeliveryJob` against, a stack belonging to a completely different, unrelated tenant, without ever authenticating against that tenant's repository or webhook secret. This is a cross-tenant "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category (unauthorized deploy trigger against a stack the attacker cannot otherwise reach). It is repeatable against any commit SHA the attacker can reproduce or predict (most straightforwardly via forking a repository with shared history), and the blast radius spans every stack across every tenant on the same Shipit instance since `Commit.where(sha:)` is global, unscoped by repository.

### Likelihood Explanation
Requires only the stated precondition: the attacker owns one valid, self-registered webhook_secret/organization on the Shipit instance (no privileged Shipit role, no session, no API token, no access to the victim's secrets). The attacker must also produce a commit SHA that coincides with one tracked by the victim's stack — trivial when the victim's repository is public or has any shared ancestry with a repository the attacker controls (fork scenario), since Git SHAs are identical across clones/forks for identical commits. No GitHub secrets, no TLS interception, and no social engineering are needed; the entire exploit is a single crafted HTTP POST to `/webhooks` correctly signed with the attacker's own secret.

### Recommendation
Scope `StatusHandler#process` (and `create_or_update_check_run_from_github!`/`CheckSuiteHandler` if similarly affected) to the repository that authenticated the webhook, exactly as `PushHandler` does via the `stacks` helper — e.g., restrict the commit lookup to commits whose `stack` belongs to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before calling `create_status_from_github!`, rejecting/ignoring matches on commits belonging to stacks outside that repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "a status webhook from repository A cannot enqueue CD for a commit belonging to stack B" do
          victim_stack = shipit_stacks(:shipit) # owned by "shopify/shipit-engine"
          victim_stack.update!(continuous_deployment: true)
          victim_commit = victim_stack.commits.last # sha shared with attacker's forked repo

          # attacker-owned repository, distinct owner/org, but a commit with the SAME sha
          # exists because the attacker forked/duplicated victim's history
          attacker_payload = {
            "sha" => victim_commit.sha,
            "state" => "success",
            "context" => "ci/attacker",
            "repository" => { "full_name" => "attacker-org/attacker-repo", "owner" => { "login" => "attacker-org" } }
          }

          assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
            StatusHandler.call(attacker_payload)
          end
        end
      end
    end
  end
end
```
Binding assertion before the fix: `attacker_payload["repository"]["full_name"] != victim_stack.repository.full_name` yet `ContinuousDeliveryJob` is still enqueued with `victim_stack` — proving the divergence. After applying the recommended repository-scoped lookup, the same test should assert `assert_no_enqueued_jobs { StatusHandler.call(attacker_payload) }`.
