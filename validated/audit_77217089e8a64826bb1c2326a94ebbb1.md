### Title
Global sha lookup in StatusHandler#process lets one repository's status webhook overwrite Status records on commits belonging to unrelated stacks/repositories - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits via `Commit.where(sha: params.sha)` with no repository scoping, unlike the base `Handler` class which provides a `stacks`/`repository_name`-scoped lookup. Since `sha` is attacker-controlled and git SHAs are not globally unique across independent repositories, a webhook signed for the attacker's own repository can create/update `Status` rows on commits belonging to entirely unrelated stacks that merely happen to share the same SHA.

### Finding Description
The claimed binding: `{stacks mutated by one status webhook} == {stack of the repository named in payload['repository']['full_name']}`. Tracing the code shows this is false.

- `Shipit::WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)`, calling `handler.call(params)` for every matching handler [1](#0-0) .
- `verify_signature` only checks that the HMAC signature matches the secret configured for `repository_owner` derived from the payload — i.e., it proves the webhook was sent by (or on behalf of) the org/repo named in the payload, not that the `sha` field is unique to that repo [2](#0-1) . An attacker who owns/controls a GitHub repository can legitimately trigger a correctly-signed `status` webhook for **their own** repo, with an attacker-chosen `sha` value (they choose what commit to push/reference).
- The base `Handler` class exposes a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, showing the intended pattern is to scope operations to the repository named in the payload [3](#0-2) .
- `StatusHandler#process`, however, ignores this scoping entirely and queries `Commit.where(sha: params.sha)` across the whole table, then calls `commit.create_status_from_github!(params)` on every match regardless of which repository/stack that commit belongs to [4](#0-3) .
- Because SHA is a 40-hex-char content hash of git objects, but nothing in this schema or code enforces SHA uniqueness *across repositories* (only presumably per-repo in practice), two unrelated repositories can and do have identical commit SHAs — trivially so for commits with identical tree/parent/author/message content (e.g., empty initial commits, cherry-picked/copied commits, or an attacker crafting a commit to match a target's known SHA), and even more simply by an attacker forking/importing a target repo so their copy shares real SHAs with the victim's stack.

Exploit flow: attacker creates or forks a repository, ensures at least one commit SHA collides with (or is identical to, via fork) a SHA already tracked in a victim stack's `commits` table, adds that repo/webhook to Shipit (or if already integrated, simply pushes), and sends a `status` event for that SHA with `state: "success"` (or `failure`) via a legitimately signed webhook from their own repository. `StatusHandler#process` finds ALL `Commit` rows with that SHA — including the victim's — and writes a `Status` row on each, regardless of which stack/repository owns them. This falsifies CI status for unrelated tenants' commits without ever needing the victim's webhook secret, session, or API token.

Existing guards fail because they operate at the wrong layer: `verify_signature` authenticates *which repository sent the webhook*, not *which commits the sha should apply to*; `drop_unhandled_event` only filters unknown event types; there is no `ExplicitParameters` validation tying `sha` to `repository_name`; and `StatusHandler` never calls the `stacks`/`repository_name` scoping that `Handler` provides for exactly this purpose.

### Impact Explanation
An attacker-controlled, self-signed webhook can write `Status` records against commits in stacks/repositories the attacker does not own or control, as long as a SHA collision (trivially achievable via fork/import or crafted identical commits) exists. This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team": CI status (used for merge-gating, deploy readiness checks, etc.) for a victim stack can be forged from an attacker-owned repository. This is repeatable indefinitely and scales to N unrelated tenants sharing a colliding SHA, per the PoC idea in the prompt (3 distinct stacks/repositories seeded with the same SHA, one webhook naming only one, all 3 get `Status` rows).

### Likelihood Explanation
Preconditions: the attacker needs a repository integrated with Shipit (or one for which Shipit is configured to accept webhooks, i.e., known to `Shipit.github(organization: ...)`) and a commit SHA that collides with one tracked by a victim stack. The lowest-cost route is forking/importing the victim's repository history (shares real SHAs) or reusing identical initial/empty commits. No secrets, sessions, or elevated privileges are required — only the ability to own a repository and send a normally-signed webhook for it, which is within the stated attacker capability set. This is straightforward and repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring the `Handler#stacks`/`repository_name` pattern, e.g. restrict the commit lookup to `stacks.flat_map(&:commits)` or join through `Repository.from_github_repo_name(repository_name)` before matching on `sha`, so only commits belonging to stacks of the reporting repository can receive a `Status` update.

### Proof of Concept
Minitest plan (no live GitHub, mirrors prompt's proof idea):
1. Create three distinct `Repository`/`Stack` records (`repo_a`, `repo_b`, `repo_c`) each with a `Commit` sharing the identical `sha` value `"deadbeef..." * n` (40 hex chars).
2. Build a `status` webhook payload with `repository.full_name = repo_a.full_name` and `sha` equal to the shared SHA, `state: "success"`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since that's orthogonal — the finding is that a validly-signed webhook for `repo_a` still mutates `repo_b`/`repo_c`).
4. Assert: `Shipit::Status.where(commit: repo_a.stack.commits.find_by(sha: sha)).exists?` is true (expected) AND also assert `Shipit::Status.where(commit: repo_b.stack.commits.find_by(sha: sha)).exists?` and for `repo_c` are true — demonstrating the binding "mutated stacks == {stack of repo_a}" is false, since stacks for `repo_b` and `repo_c` were also mutated by a webhook naming only `repo_a`.
