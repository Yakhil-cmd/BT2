### Title
Webhook signature verified against `repository.owner.login`'s organization secret while the resource actually written is selected from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `payload.dig('repository', 'owner', 'login')`. Every webhook `Handler` (e.g. `Handlers::Handler#stacks`, and the pull-request handlers) instead resolves the repository/stack to mutate using the sibling but independent field `payload.dig('repository', 'full_name')`. Nothing enforces that `repository.owner.login` and the owner segment of `repository.full_name` refer to the same organization in a multi-tenant Shipit deployment. A sender who knows the `webhook_secret` configured for organization A can forge a payload whose `repository.owner.login` is `A` (so the HMAC check passes against A's secret) but whose `repository.full_name` points at a repository belonging to organization B, causing the engine to execute the handler's state transition (e.g. `GithubSyncJob`, `ReviewStackAdapter#find_or_create!`, `stack.archive!`/`unarchive!`) against organization B's stack.

### Finding Description
`Shipit.github(organization:)` supports a multi-organization configuration where each organization key in `secrets.github` has its own `webhook_secret` (`lib/shipit.rb#L170-L200`, `config/secrets.development.example.yml`). The webhook signature check looks up the app/secret for verification using only the payload's `repository.owner.login`: [1](#0-0) [2](#0-1) 

Once signature verification passes, `Handler#stacks`/`Handler#repository_name` (and every pull-request handler's `repository` method) look up the target `Repository`/`Stack` using a *different* field of the same untrusted body, `repository.full_name`: [3](#0-2) [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` lookup with no cross-check against `repository.owner.login`: [5](#0-4) 

Because the signing key is selected from `repository.owner.login` and the acted-upon repository is selected from `repository.full_name`, these two attacker-controlled strings are never required to agree. The binding that should hold is:
`organization authenticated (repository.owner.login → webhook_secret)` == `organization whose repository is written (owner segment of repository.full_name)`
This equality is never checked. Before an attacker's forged request: stack state for org B is only mutated by genuine GitHub deliveries signed with org B's secret. After the forged request: org A's known secret is used to sign a payload whose `full_name` names an org B repository, and the handler still processes it as a legitimate event for org B's stack, because `verify_signature` succeeded (checked against org A's secret) and the handler never re-derives/validates organization identity against `repository.owner.login`.

### Impact Explanation
This allows an unauthenticated remote sender (someone who only knows one organization's `webhook_secret`, e.g. their own organization's onboarded webhook config in a multi-tenant Shipit instance) to inject forged GitHub events that are processed as if they came from a *different* organization's repository. Depending on which handler fires, this can: create/unarchive/archive `ReviewStack`s, enqueue `GithubSyncJob`/`RefreshStatusesJob`/`RefreshCheckRunsJob`, or otherwise mutate CI/PR/commit state for a stack the sender does not control. This is an unauthorized cross-organization state write bypassing the intended per-organization webhook authentication boundary, matching the "organization authenticated vs. repository written" analog class.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (a supported, documented configuration — see `config/secrets.development.example.yml`), and (2) the attacker knowing the `webhook_secret` for at least one of the configured organizations (which is plausible if that organization's admins self-manage/rotate their own webhook secret, or if it leaks). Given those preconditions the exploit is a single crafted HTTP POST with a valid HMAC for org A and a `repository.full_name` pointing to org B — no other authentication or authorization boundary needs to be crossed. Likelihood is moderate: it only applies to multi-org deployments, but no source code change is needed by the attacker, only payload crafting.

### Recommendation
In `WebhooksController#verify_signature`, and in `Webhooks::Handlers::Handler#stacks`/`#repository_name` (and every handler that separately calls `Repository.from_github_repo_name(params.repository.full_name)`), derive the organization used for both signature verification and repository resolution from the *same* single trusted field, and additionally assert that `repository.full_name`'s owner segment matches `repository.owner.login` (or simply derive the resolved organization solely from `full_name` and use that same value to pick the `webhook_secret`) before processing the event.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (per `secrets.github` multi-org schema).
2. As an entity that knows `org-a`'s `webhook_secret` (e.g., an org-a admin who configured that webhook), craft a JSON body:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { ... },
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  },
  "sender": { "login": "attacker" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and succeeds because the signature matches org-a's secret.
5. `Handlers::PullRequest::OpenedHandler#repository` resolves `Repository.from_github_repo_name("org-b/victim-repo")`, and if review stacks/provisioning are enabled for `org-b/victim-repo`, a `ReviewStack` is created/provisioned for that repository — an action the attacker (who only controls org-a's webhook secret) had no authorization to trigger for `org-b`.

**Uncertainty:** I could not verify from the indexed files whether, in a real deployment, an external attacker would in practice have access to another organization's `webhook_secret` value (this depends on operational/administrative practices outside the engine's code, e.g. whether each org self-configures its GitHub webhook secret or whether Shipit's operator centrally manages all secrets). If secrets are always centrally managed and never exposed to any org's admins, the practical attacker surface for this analog is reduced to secret leakage, not straightforward "known-secret cross-org" abuse.
