### Title
`provision?` operator precedence bypasses `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` repos - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` scopes `repository.review_stacks_enabled` only to the `allow_all?` disjunct due to Ruby `&&`/`||` precedence, so repositories configured with `provisioning_behavior: allow_with_label` or `prevent_with_label` will have review stacks created even when `review_stacks_enabled` is `false`. Any user able to open a pull request against such a repository (and control whether their PR carries the configured provisioning label) can trigger creation and provisioning-queue enqueuing of a `Shipit::ReviewStack` on a repository whose maintainer explicitly disabled review stacks.

### Finding Description
The intended binding is: `stack_created == true` requires `repository.review_stacks_enabled == true`. The code at [1](#0-0)  is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label) || (prevent_with_label? && !label)`. The second and third disjuncts never consult `review_stacks_enabled` at all, so `review_stacks_enabled == false` no longer implies `stack_created == false` when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`.

The reachable path is: an unprivileged GitHub user opens a pull request against a Shipit-tracked repository (`action == "opened"`), GitHub sends a signed `pull_request` webhook, `respond_to_pull_request_opened?` calls `provision?` [2](#0-1) , and if it returns `true`, `process` calls `ReviewStackAdapter#find_or_create!` on `repository.review_stacks` [3](#0-2) . `create!` persists a new `ReviewStack` and immediately calls `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) , which sets `awaiting_provision: true` via `enqueue_for_provisioning` [5](#0-4) . A background worker (`ReviewStackProvisioningQueue#work`) subsequently calls `stack.provision`, transitioning `deprovisioned -> provisioning` and invoking `stack.provisioner.up` [6](#0-5) , i.e. running the repository-configured provisioning handler against attacker-controlled branch content, despite the maintainer having explicitly turned `review_stacks_enabled` off.

Webhook signature verification only authenticates that the payload genuinely originates from GitHub for that repository — it says nothing about whether the repository's own `review_stacks_enabled` setting should gate stack creation, so it does not block this divergence. The `Repository` model has no validation coupling `provisioning_behavior` to `review_stacks_enabled` [7](#0-6) , and `NullRepository` (used for untracked repos) always returns `false` for all provisioning predicates, so it is not affected — this only reproduces once a repository record exists with `provisioning_behavior` set to `allow_with_label`/`prevent_with_label`.

I confirmed via `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` that the `configure_provisioning_behavior` test helper defaults `provisioning_enabled: true` and none of the existing `allow_with_label`/`prevent_with_label` tests exercise `provisioning_enabled: false`, so this exact gap is untested. [8](#0-7) 

### Impact Explanation
For any Shipit-tracked repository whose maintainer set `provisioning_behavior` to `allow_with_label` or `prevent_with_label` and left `review_stacks_enabled = false` (intending review stacks to be entirely disabled), an unprivileged contributor who can open a PR (and control the presence/absence of the configured label on their own PR) forces creation of a `Shipit::ReviewStack` and its enqueuing for provisioning. Provisioning invokes the repository's `provisioner.up`, running configured provisioning/deploy logic against attacker-influenced branch content that the maintainer specifically opted out of auto-running. This is repeatable per PR/per repository matching that configuration and constitutes an unauthorized-deploy-class impact (Critical) since it causes execution of infrastructure actions the repository owner never authorized.

### Likelihood Explanation
Preconditions: the target repository must exist as a `Shipit::Repository`, have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`, and `review_stacks_enabled` set to `false`. No Shipit credentials, sessions, or GitHub secrets are needed — the attacker only needs to be able to open a genuine PR against the target (fork-and-PR is sufficient for public repos) and optionally add/omit a label on their own PR. Given that this is a purely configuration-triggered logic defect with no additional barriers once the repo is in that state, exploitation is straightforward and fully repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every disjunct:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to `ReopenedHandler`, which uses the identical expression.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks when review_stacks_enabled is false, even for prevent_with_label with no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion: expected `Shipit::Stack.count` unchanged (`review_stacks_enabled == false` ⇒ `stack_created == false`); actual result with current code is `Shipit::Stack.count` increments by 1, proving the divergence.
