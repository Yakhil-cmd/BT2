### Title
Cross-tenant CI status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `Commit` table with no `stack_id`/`repository_id` filter, unlike sibling handlers (e.g. `CheckSuiteHandler`) which scope through `stacks`. A verified webhook from one repository whose commit sha collides with a commit sha recorded under a different, unrelated stack (e.g. a shared un-diverged ancestor commit between two forks of the same upstream) will write a GitHub status onto the other tenant's commit.

### Finding Description
The broken binding: the code claims `Commit.where(sha: params.sha)` should be equivalent to `Commit.where(sha: params.sha, stack_id: stacks.commits.select(:id))`, filtered through `Handler#stacks`, but it is not. `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) resolves the requesting repository via `Repository.from_github_repo_name(repository_name)` from the payload's `repository.full_name`, and other handlers use it correctly — `CheckSuiteHandler#process` does `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [1](#0-0) . `StatusHandler#process`, however, calls the bare `Commit` model class directly:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit` has a `belongs_to :stack` and no global uniqueness constraint on `sha` alone (uniqueness is necessarily per-stack, since separate stacks each hold their own copies of shared ancestor commits) [3](#0-2) . So `Commit.where(sha: params.sha)` can legitimately return rows belonging to multiple, unrelated stacks/repositories whenever they share a commit sha — which happens naturally for two forks of a common upstream before they diverge, or for GitHub's well-known deterministic empty/initial commits.

Attack path: an attacker who owns/administers their own GitHub repository (added as a Shipit stack, with their own legitimate `webhook_secret` configured for their own org) forks or otherwise shares an ancestor commit sha with a victim stack's repository. `WebhooksController#verify_signature` only checks that the webhook signature matches the secret for the **attacker's own** `repository_owner` (`Shipit.github(organization: repository_owner)`), which passes because it is the attacker's own legitimately configured webhook [4](#0-3) . The attacker then causes (or fabricates, within their own repo's real GitHub status API) a `status` event for that shared sha with an arbitrary `state`/`context`/`description`. Shipit's `StatusHandler.call` fires, and `Commit.where(sha: params.sha)` matches the commit row in the attacker's own stack **and** the identical-sha commit row belonging to the victim's unrelated stack, both receiving `commit.create_status_from_github!(params)`.

None of the existing guards catch this: `verify_signature` only authenticates that the payload came from the *attacker's own* configured org/repo — it says nothing about which `Commit` rows the payload is allowed to touch [5](#0-4) . `drop_unhandled_event` and the `ExplicitParameters` schema only validate that a `status` event exists and has the right shape (`sha`, `state`, etc.) [6](#0-5) , not that the sha belongs to the requesting repository. `Handler#stacks` exists precisely to provide this scoping but `StatusHandler` never calls it.

### Impact Explanation
A successful cross-sha-collision status webhook lets an attacker who controls only their own repository write a fabricated CI status (`success`, `failure`, `error`, `pending`, arbitrary `context`/`description`/`target_url`) onto a commit belonging to a completely unrelated victim stack/repository. Since `create_status_from_github!` drives deployability computation and (per `Commit#schedule_continuous_delivery`) can trigger `ContinuousDeliveryJob` when a commit becomes `deployable?` under continuous deployment, this can result in an unauthorized deploy being scheduled for the victim's stack, or conversely block a legitimate deploy by injecting a false `failure`/`error` status. This is a payload for one repository mutating another's commit/stack state, and matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). Blast radius: any tenant pair sharing a commit sha (common for forks prior to divergence, or shared upstream history) is fully cross-contaminated; the exploit is repeatable for every shared sha the attacker can produce a real status event for.

### Likelihood Explanation
Preconditions: the attacker must (a) control a repository that is registered as a Shipit stack (or can add one, per normal onboarding) with a legitimate webhook/secret pointed at the Shipit host, and (b) identify or engineer a commit sha shared with a victim stack — realistic via forking a shared upstream repository before divergence, or via well-known deterministic empty-tree/initial commits. No victim secret, session, or token is required. Given fork-based development is common and Shipit stacks are frequently added per-fork/per-environment, this precondition is plausible and repeatable at will by the attacker for any sha they can produce a genuine GitHub status event for on their own repo.

### Recommendation
Scope `StatusHandler#process` through the requesting repository's stacks, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `Commit.where(sha: ..., stack_id: stacks.commits.select(:id))` so a status event can only affect commits belonging to stacks tied to the payload's own `repository.full_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not leak status across stacks sharing the same commit sha" do
  shared_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"

  stack_a = shipit_stacks(:shipit) # owned by "attacker/repo"
  stack_b = shipit_stacks(:cyclimse) # unrelated victim stack, different repository

  commit_a = stack_a.commits.create!(sha: shared_sha, message: "shared ancestor", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  commit_b = stack_b.commits.create!(sha: shared_sha, message: "shared ancestor", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => stack_a.repository.full_name },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding under test:
  # Commit.where(sha: shared_sha) == Commit.where(sha: shared_sha, stack_id: stack_a.commits.select(:id))  -- SHOULD hold, but does not
  assert commit_a.reload.statuses.exists?(context: 'ci/attacker'), "attacker's own commit received the status (expected)"
  assert_not commit_b.reload.statuses.exists?(context: 'ci/attacker'),
    "victim stack_b's unrelated commit must NOT receive a status from stack_a's webhook payload"
end
```
Running this against current `StatusHandler#process` fails the final assertion, proving `commit_b` (belonging to an unrelated stack/repository) is mutated by a webhook payload scoped to `stack_a`'s repository.
