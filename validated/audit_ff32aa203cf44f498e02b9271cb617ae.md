### Title
Cross-tenant webhook signature scoping allows attacker-controlled GitHub org to grant itself membership in another org's privileged `Shipit::Team` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` verifies the raw request body only against the `webhook_secret` of the organization named in the payload (`repository.owner.login` or `organization.login`), not against the organization that actually owns the `Shipit::Team` row a `membership` event will mutate. `MembershipHandler#find_or_create_team!` then looks up the `Team` by `github_id` alone, with no `organization` scoping, so a signature valid for `attacker-org` can be used to add an attacker as a member of a pre-existing `Team` belonging to a completely different (higher-privilege) organization.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `organization_that_signed_the_payload (attacker-org, via Shipit.github(organization: 'attacker-org').verify_webhook_signature)` == `organization_owning_the_mutated_Team_row (team.organization, e.g. 'shopify')`. These are asserted to be equal implicitly by the code (any org that signs a `membership` webhook is trusted to mutate the team named in it), but nothing enforces it.

Code path:
1. `WebhooksController#verify_signature` derives the signing org purely from attacker-supplied payload fields: `repository_owner` falls back to `params.dig('organization', 'login')` when there's no `repository` key [1](#0-0)  and then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . Since the attacker legitimately administers `attacker-org` (a configured second tenant per `docs/setup.md`'s multi-org config), this check passes with `attacker-org`'s own valid `webhook_secret` computed via HMAC in `GitHubApp#verify_webhook_signature` [3](#0-2) .
2. `MembershipHandler#process` calls `find_or_create_team!`, which resolves the team **only** by `github_id`, ignoring `params.organization.login` for the lookup (it's only used inside the create block, which never executes if the row exists): [4](#0-3) .
3. `process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))`, inserting a `Membership` row for the attacker against the pre-existing privileged team [5](#0-4) , [6](#0-5) .
4. `User#authorized?` checks membership against `Shipit.github_teams` by `id` with no organization scoping either [7](#0-6) , and `Shipit.github_teams` is populated from the operator's `oauth.teams` config via `Team.find_or_create_by_handle` [8](#0-7) , [9](#0-8) .

No existing guard closes this gap: `verify_signature` only proves the request came from *some* configured tenant, not the tenant matching the `Team`'s `organization`; `find_or_create_team!`'s `find_or_create_by!` predicate is `github_id` only; `Team.add_member`/`Membership` creation has no cross-checks against `params.organization.login`.

### Impact Explanation
A user who only administers a second, legitimately-configured (but unrelated/low-privilege) GitHub organization tenant can forge a `membership` webhook that inserts a `Membership` row tying themselves to any `Shipit::Team` whose `github_id` they can guess or observe (team ids are not secret—visible via GitHub's API/UI to anyone in that org, or brute-forceable since they're small sequential integers). If that team is listed in `Shipit.github_teams`, the attacker's `User#authorized?` immediately becomes `true`, granting full access to every stack, deploy, and merge across the entire Shipit instance — not just resources belonging to `attacker-org`. This is a cross-tenant authentication/authorization bypass, matching the Critical category ("payload for one repository mutating another's ... team", and escalation into `Shipit.github_teams`).

### Likelihood Explanation
Preconditions are realistic and match a documented, supported Shipit deployment mode (multi-org `github:` config, per `docs/setup.md`'s "Using Multiple Github Applications" section). The attacker needs: (1) control of any org configured as a Shipit tenant with its own `webhook_secret` (something an operator would grant to any legitimate but separate customer/org), and (2) knowledge of the target `github_id` of a privileged `Team` row, obtainable via GitHub's public/semi-public team APIs or small-integer enumeration. No Shipit secrets, sessions, or API tokens are required. The attack is a single unauthenticated HTTP POST, fully repeatable and scriptable for arbitrary team ids.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup and enforce equality between the webhook's signing organization and the `Team`'s `organization` column, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` (rejecting/raising if an existing row's `organization` differs from `params.organization.login`), or explicitly reject the event when `team.organization != params.organization.login`. More generally, `verify_signature` should ensure the verified organization matches the organization of every resource the event will mutate, not just the one used to pick the `webhook_secret`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":membership from attacker-org can hijack a team belonging to another org" do
  privileged_team = shipit_teams(:shopify_developers) # organization == 'shopify', already used in Shipit.github_teams
  Shipit.stubs(:github_teams).returns([privileged_team])

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef'

  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  payload = {
    action: 'added',
    team: { id: privileged_team.github_id, slug: 'x', name: 'x', url: 'x' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }.to_json

  assert_difference -> { Membership.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  attacker = Shipit::User.find_by!(login: 'attacker')
  assert Membership.exists?(team: privileged_team, user: attacker)
  assert attacker.authorized?
end
```
Both sides of the binding after the exploit: signing organization = `'attacker-org'`; `privileged_team.organization` = `'shopify'` — unequal, yet the `Membership` write and `authorized?` escalation succeed, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
