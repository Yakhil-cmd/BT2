### Title
Premature "success" callback in `handlePrivatePaymentChains` allows acceptance/forwarding of private payment chains whose validation has not completed or has failed - ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in `wallet.js` processes a batch of private-payment chains (`body.chains`) received from a paired device/counterparty. For each chain it calls `network.handleOnlinePrivatePayment()`; when validation cannot complete synchronously (`ifQueued`), it registers a one-time event listener for the eventual validation result and immediately advances the `async.eachSeries` loop by calling `cb()` *before* the actual validation result is known. As soon as the (synchronous) loop finishes iterating — which happens as soon as everything is queued, not as soon as everything is validated — the final `async.eachSeries` callback unconditionally calls `callbacks.ifOk()` and triggers forwarding of the chains to other wallet members, even though some/all of the queued chains have not yet been cryptographically/economically validated (or may later fail validation via the `bValid=false` branch). This mirrors the CVE-2020-13846 pattern: a bulk "verify all" operation reports overall success while individual elements remain unverified.

### Finding Description
In `wallet.js`, `handlePrivatePaymentChains(ws, body, from_address, callbacks)`: [1](#0-0) 

Key defect:
1. `assocValidatedByKey[key] = false` is set for each chain before calling `network.handleOnlinePrivatePayment`.
2. In the `ifQueued` callback (the common path for light wallets, since private chain joints/stability may not be locally available yet), the code registers `eventBus.once(key, ...)` to be notified later of the real validation outcome, but calls `cb()` immediately — this signals `async.eachSeries` that this *iteration* is done, not that validation is done.
3. The final callback of `async.eachSeries` (reached once all chains have been iterated/queued) does:
```
function(err){
    bParsingComplete = true;
    if (err){
        cancelAllKeys();
        return callbacks.ifError(err);
    }
    checkIfAllValidated();
    handledChainsCache[cache_key] = Date.now();
    callbacks.ifOk();          // <-- called unconditionally, even if some keys are still false
    if (!body.forwarded)
        forwardPrivateChainsToOtherMembersOfOutputAddresses(arrChains, true);  // <-- forwards unvalidated chains
}
```
`checkIfAllValidated()` correctly detects that not all keys are `true` yet and merely logs `'not all private payments validated yet'` without throwing/erroring — but the surrounding function does not gate on this: `callbacks.ifOk()` and `forwardPrivateChainsToOtherMembersOfOutputAddresses` execute regardless. `handledChainsCache[cache_key]` is also set at this point, which will cause a **subsequent, identical re-submission of the same (still‑unvalidated or since‑invalidated) chain set to be short‑circuited as already handled**: [2](#0-1) 
```
if (handledChainsCache[cache_key]) {
    eventBus.emit('all_private_payments_handled', from_address);
    eventBus.emit('all_private_payments_handled-' + arrChains[0][0].unit);
    return callbacks.ifOk();
}
```

This is directly analogous to the Singularity bug: individual verification failures/incompleteness (`WARNING`-equivalent: `assocValidatedByKey[key] === false`) are recorded but the overall "container verified"/`ifOk()`-equivalent success signal, and the exit-code-equivalent (`callbacks.ifOk()`), are still returned.

### Impact Explanation
`callbacks.ifOk()` from `handlePrivatePaymentChains` is used by callers (e.g., the hub message dispatcher for the `private_payments` subject) to acknowledge to the sending peer that chains were accepted, and — critically — the same code path triggers `forwardPrivateChainsToOtherMembersOfOutputAddresses`, propagating the *unvalidated* private-payment chain data to other devices sharing the output address (e.g., co-signers of a shared address) before the local wallet has established the chain is actually valid. Consumers that treat `ifOk`/forwarding as an indication that the private payment is trustworthy can:
- Display/spend against a private balance backed by a chain that later fails validation (`bValid=false`), leading to inconsistent wallet state and potential attempts to spend non-existent/invalid private outputs.
- Have the poisoned/incomplete result cached (`handledChainsCache`), suppressing subsequent legitimate validation retries, effectively causing the wallet to treat an unverified or invalid private payment as durably accepted.
This can enable a malicious payer/paired device to get a private payment "accepted" and forwarded to other wallet members before, or even despite, failing real validation — a fund-related integrity issue for private payment chains, which is explicitly in scope.

### Likelihood Explanation
The `ifQueued` branch is the expected code path for light wallets receiving private payment chains whose full joint history/stability is not yet locally known — a very common, non-adversarial condition, so the race is easily triggered simply by an unprivileged counterparty sending a private payment chain to a light wallet. No privileged position is required: the attacker only needs to act as a normal private-payment counterparty or paired device sending `private_payments` messages, which is an explicitly in-scope actor.

### Recommendation
In `handlePrivatePaymentChains`, do not call `callbacks.ifOk()` / trigger forwarding from the `async.eachSeries` final callback unless `checkIfAllValidated()` confirms every key in `assocValidatedByKey` is `true`. Only call `ifOk()`/perform forwarding/cache the `cache_key` from within `checkIfAllValidated()` once every chain's asynchronous validation has actually completed successfully. If any chain resolves to `bValid=false`, propagate an error state instead of silently caching success.

### Proof of Concept
1. Configure a light wallet (`conf.bLight = true`) that has not yet retrieved the full joint history needed to validate a private-payment chain locally.
2. As a paired device / private-payment counterparty, send a `private_payments` message with `body.chains` containing one or more private-payment chains referencing units the light wallet doesn't have.
3. `network.handleOnlinePrivatePayment` will invoke `callbacks.ifQueued()` for these chains (since the light wallet must fetch/verify the underlying joints asynchronously).
4. Because `async.eachSeries`'s per-item `cb()` is invoked immediately in the `ifQueued` handler (before actual validation), the series completes immediately; the final callback fires with `assocValidatedByKey[key] === false` still pending, yet unconditionally calls `callbacks.ifOk()` and `forwardPrivateChainsToOtherMembersOfOutputAddresses(arrChains, true)`, and sets `handledChainsCache[cache_key]`.
5. Observe that the wallet acknowledges success and forwards the chain to co-signers/other holders of the output address before (or independent of) the eventual `eventBus.emit(key, bValid)` outcome — including the case where `bValid` later resolves to `false`.

Note: I was unable to trace, within the available context, the exact hub-level dispatcher that calls `handlePrivatePaymentChains` and consumes its `ifOk`/`ifError` result (this determines exactly what network-visible acknowledgment is sent to the peer). This does not affect the core finding — the premature success/forward before completed validation is demonstrated directly in the cited code — but a full confirmation of the peer-visible acknowledgment message would benefit from reviewing the full `wallet.js` message dispatch table, which exceeded the scope I could inspect in the remaining iterations.
