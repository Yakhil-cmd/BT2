### Title
AMM-style AA reserve-ratio pricing via live `balance[]` is manipulable within a single atomic unit through chained/secondary AA triggers - (File: formula/evaluation.js, aa_composer.js)

### Summary
Cyrus Finance's `withdrawUSDTFromAny` computed a withdrawal amount from the *current* spot reserves of a PancakeSwap pool, letting an attacker use an atomic flash loan to shift the pool ratio, call the vulnerable function while the ratio was distorted, and extract excess funds. The Obyte AA engine provides an oscript primitive, `balance[asset]`, that lets an AA read its *own live token reserves* to price swaps/withdrawals (as in the reference constant-product AMM pattern), and the engine executes AA-to-AA "secondary trigger" chains fully atomically within a single DAG unit. This gives any unprivileged unit poster an equivalent of a "free," native flash loan: multiple balance-shifting hops can be composed in one posted unit before a reserve-priced payout message executes, with the whole cascade committing or reverting together.

### Finding Description
`balance[asset]` is evaluated by `readBalance()` in `formula/evaluation.js` (case `'balance'` at line 1481, `readBalance` at line 1510), which returns `objValidationState.assocBalances[param_address][bal_asset]` — the AA's *live, in-flight* balance as mutated during the current trigger's processing, not a settled/independent oracle value. [1](#0-0) 

The reference AMM pattern shipped as a canonical AA example uses exactly this live balance to compute a constant-product exchange rate for both directions of a swap and for divestment payouts: [2](#0-1) [3](#0-2) 

`aa_composer.js` processes an entire chain of AA-to-AA "secondary triggers" spawned by a single posted unit synchronously and atomically: `sendUnit`/`sendDummyUnit` mutate `assocBalances` in place as messages are assembled, and `handleSecondaryTriggers` immediately re-invokes `handleTrigger` for every downstream AA that received an output, before the whole response tree is finalized (or reverted together via `revert()`). [4](#0-3) [5](#0-4) 

Because this cascade is atomic (one unit, one commit/rollback), an attacker who controls or composes several AAs (or uses multiple messages that trigger a chain through an AMM and back) can move the AMM's reserve ratio via a first hop, then have a later hop in the same unit read the now-skewed `balance[$asset]`/`balance[base]` to compute a payout — the same "manipulate reserves, then exploit the price-dependent function, all before anything can be arbitraged back" pattern as the Cyrus Finance `withdrawUSDTFromAny` exploit, except here no external flash-loan protocol is even required: ocore's own atomic multi-AA trigger chaining (demonstrated in `test/aa_composer.test.js` "chain of AAs" and multi-hop tests) supplies the equivalent capability natively. [6](#0-5) 

### Impact Explanation
Any AA that prices a swap, withdrawal, or share redemption from its own current `balance[...]` (the documented/canonical way to build an AMM or reserve-backed vault on Obyte) is exposed to atomic, same-unit reserve manipulation. An attacker can extract more value than the AA's economic invariant intends, draining bytes/assets from the AA's treasury — a direct AA fund loss, analogous in class and root cause to the $516,840 loss in the Cyrus Finance incident.

### Likelihood Explanation
Constructing a multi-hop, multi-message unit that chains through one or more AAs to shift an AMM's reserves before a price-sensitive payout is entirely reachable by an ordinary, unprivileged unit poster/trigger sender — no special privileges, malicious nodes, or external protocols are needed, only the ability to author oscript messages and post one unit, exactly matching the "AA trigger sender" reachable-path scope of this scan.

### Recommendation
- Do not use raw, live `balance[asset]` as a same-transaction spot price/reserve source for payout formulas; instead require a settled reference (e.g., a value fixed at the start of the *primary* trigger before any secondary-trigger cascade can alter it, or an externally-attested `data_feed` price) and reject if reserves changed within the current cascade.
- Provide/require an explicit "pre-cascade" snapshot of `assocBalances` for the primary trigger's AA that price-sensitive formulas must reference instead of the live, cascade-mutated value.
- Document in the AA/oscript reference (and update the `uniswap_like_market_maker.oscript` example) that AMM-style AAs relying on `balance[]` are vulnerable to same-unit multi-hop reserve manipulation and should add minimum-output/slippage checks and/or TWAP-like averaging instead of raw spot balances.

### Proof of Concept
1. Deploy an AMM-style AA whose swap/divest payout formula uses `balance[$asset]` / `balance[base]` directly (per `test/samples/uniswap_like_market_maker.oscript`).
2. Craft a single unit whose messages trigger a first AA (or a direct payment) that shifts the AMM's asset/byte reserve ratio (a large one-sided swap).
3. In the same unit's cascading secondary-trigger chain (per `aa_composer.js` `handleSecondaryTriggers`), trigger the divest/withdraw case of the AMM AA while the reserves are still in the skewed state from step 2, so `round($investor_share * balance[$asset])` / `round($p / balance[base])` compute against the manipulated ratio.
4. Because the whole unit's AA cascade commits atomically, the attacker locks in the manipulated payout in one DAG unit, with no possibility for third parties to arbitrage or intervene mid-cascade — mirroring the Cyrus Finance flash-loan-driven `withdrawUSDTFromAny` extraction.

	function handleSecondaryTriggers(objUnit, arrOutputAddresses) {
		conn.query("SELECT address, definition, mci, main_chain_index FROM aa_addresses LEFT JOIN units USING(unit) WHERE address IN(?) AND mci<=? ORDER BY address", [arrOutputAddresses, mci], function (rows) {
			if (rows.length > 0 && constants.bTestnet && mci < testnetAAsDefinedByAAsAreActiveImmediatelyUpgradeMci)
				rows = rows.filter(function (row) {
					if (row.main_chain_index && row.main_chain_index < mci) // previous definition is already stable
						return true;
					var len = storage.getUnconfirmedAADefinitionsPostedByAAs([row.address]).length;
					if (len > 0)
						console.log("not calling secondary trigger from unit " + objUnit.unit + " to AA " + row.address);
					return (len === 0);
				});
			if (rows.length === 0) {
				saveStateVars();
				addUpdatedStateVarsIntoPrimaryResponse();
				return onDone(objUnit, bBouncing ? error_message : false);
			}
			if (bBouncing)
				throw Error("secondary triggers while bouncing");
			async.eachSeries(
				rows,
				function (row, cb) {
					var child_trigger = getTrigger(objUnit, row.address);
					child_trigger.initial_address = trigger.initial_address;
					child_trigger.initial_unit = trigger.initial_unit;
					if ("max_aa_responses" in trigger && mci >= constants.pemCurvesFixMci) // propagate the cap set on the primary trigger to secondary triggers
						child_trigger.max_aa_responses = trigger.max_aa_responses;
					var arrChildDefinition = JSON.parse(row.definition);

					var child_trigger_opts = { ...trigger_opts };
					child_trigger_opts.trigger = child_trigger;
					child_trigger_opts.params = {};
					child_trigger_opts.arrDefinition = arrChildDefinition;
					child_trigger_opts.address = row.address;
					child_trigger_opts.bSecondary = true;
					child_trigger_opts.onDone = function (objSecondaryUnit, bounce_message) {
						if (bounce_message)
							return cb(bounce_message);
						cb();
					};
					handleTrigger(child_trigger_opts);
				},
				function (err) {
					if (err) {
						// revert
						if (bSecondary)
							return bounce(err);

						return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
					}
					saveStateVars();
					addUpdatedStateVarsIntoPrimaryResponse();
					onDone(objUnit, bBouncing ? error_message : false);
				}
			);
		});
