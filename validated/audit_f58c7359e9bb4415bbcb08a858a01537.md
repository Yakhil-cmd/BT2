### Title
Cross-organization webhook forgery via unauthenticated `organization`/`repository.owner.login` selection enables `Shipit.github_teams` authorization bypass - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The report's root cause is a value used to authorize/dispatch a privileged action (`weeklyReward`) that is never actually bound by the check meant to secure it (`msg.value`). The direct analog in Shipit: the org name used to pick which GitHub App's `webhook_secret` verifies an inbound webhook is read straight out of the unauthenticated request body, and is a *different* field than the one the event handler later trusts to attribute the mutation (team/organization membership). When any configured GitHub App has no `webhook_secret` (a supported, documented state), signature verification is unconditionally satisfied for that org, letting an attacker pick that org purely to pass the check while the payload's other fields drive state changes against a completely different, protected org/team.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using a value taken from the still-unverified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` prefers `repository.owner.login` and falls back to the top-level `organization.login` — two independent, attacker-writable JSON fields in the same unauthenticated body.

`GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected app's `webhook_secret` is blank: [3](#0-2) 

`webhook_secret: nil` per organization is an explicitly documented/supported configuration (multi-org setup), not a misconfiguration: [4](#0-3) [5](#0-4) 

Once signature verification is bypassed by pointing `repository.owner.login` at a no-secret org, `WebhooksController#create` re-parses the same body and dispatches it to handlers, which read *other* fields (not the one used for verification) to decide what to mutate: [6](#0-5) 

For the `membership` event, `MembershipHandler#process` trusts `params.organization.login` and `params.team.id`/`params.member.login` to create/find a `Team` and add a member to it — none of these are cross-checked against `repository_owner`: [7](#0-6) 

`Team#add_member` then persists the membership, and `User#authorized?` grants Shipit access based purely on that membership: [8](#0-7) [9](#0-8) [10](#0-9) 

**Binding broken (equality that should hold but doesn't):**
`organization_used_to_verify_signature == organization_whose_state_is_mutated`

Before the attack: an org's webhook_secret gates only that org's own webhooks/state.
After the attack: an attacker chooses `repository.owner.login = <org with blank webhook_secret>` (verification trivially passes) while `organization.login`/`team.id`/`member.login` reference a *different*, protected org's `Team` record — a value never covered by any signature check.

### Impact Explanation
This is an authentication-bypass path into `Shipit.github_teams` authorization (explicitly listed High-impact class in scope). An unauthenticated, credential-less attacker can POST a forged `membership` event to the public `/webhooks` endpoint, causing Shipit to add an arbitrary GitHub login (which the attacker controls, e.g. their own account) as a member of any `Team` row whose GitHub `id` the attacker knows (team IDs are typically discoverable via the public GitHub API). Since `User#authorized?` gates the entire application purely on that Team membership, the attacker can then complete a normal OAuth login and gain full Shipit access — deploys, rollbacks, merges — without ever being a legitimate member of the target GitHub organization or team, and without possessing any Shipit/GitHub secret.

### Likelihood Explanation
Likelihood is high wherever Shipit is configured with more than one GitHub App/org (a documented, supported feature) and at least one of them has no `webhook_secret` set (also a documented default, as shown in the shipped example config). No authentication, GitHub App key, or network position is required — only knowledge of the public `/webhooks` route and a guessable/known GitHub team `id` for the target org.

### Recommendation
- Do not select the verification key from an unauthenticated payload field that differs from the field the downstream handler trusts. Use one canonical, verifiable source for "which org this webhook is for" and enforce that every handler's mutation target belongs to that same org.
- Require `webhook_secret` to be present for every configured org (reject startup/requests otherwise), removing the unconditional `return true unless webhook_secret` bypass in `lib/shipit/github_app.rb`.
- In `MembershipHandler`/`Team`, verify that `params.organization.login` matches the `repository_owner`/org that passed signature verification before creating/mutating `Team` or `Membership` records.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (no `webhook_secret`) and `OrgB` (a real gating team used in `Shipit.github_teams`), as shown in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "repository": {"owner": {"login": "OrgA"}},
  "organization": {"login": "OrgB"},
  "team": {"id": <real_github_team_id_of_OrgB_team>, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "member": {"login": "attacker-github-login"}
}
```
No `X-Hub-Signature` needs to be valid: `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` per `lib/shipit/github_app.rb:76-77`.
3. `create` dispatches to `MembershipHandler#process`, which finds/creates the `Team` with `github_id` matching OrgB's real team and adds `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
4. Attacker signs into Shipit via GitHub OAuth using the `attacker-github-login` account; `User#authorized?` succeeds because of the forged membership, granting deploy/rollback/merge access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
