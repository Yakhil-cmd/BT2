### Title
Cross-repository commit-status forgery: organization authenticated by signature vs. repository whose commit is written - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization used to validate the HMAC signature from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and only that organization's `webhook_secret` is checked. [1](#0-0) [2](#0-1)  Once the signature is accepted, the actual data-mutating handler for `status` events, `Webhooks::Handlers::StatusHandler#process`, ignores the repository entirely and updates commit statuses purely by matching `sha` across the whole `Commit` table: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [3](#0-2) 

### Finding Description
Shipit supports multiple GitHub Apps/organizations configured side by side (`test/dummy/config/secrets_double_github_app.yml` demonstrates a two-organization config). [4](#0-3)  The webhook secret is documented as optional per organization. [5](#0-4) 

The equality the system relies on for authenticity is:

`organization authenticated (repository.owner.login → Shipit.github(organization:).webhook_secret)` == `repository that is actually written to by the handler`

For most handlers (e.g. `PushHandler`, `CheckSuiteHandler`, PR handlers) this holds because they explicitly resolve the target via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, i.e. the same `repository` object whose owner was used for signature verification. [6](#0-5) 

`StatusHandler`, however, breaks this binding: it never consults `repository` or `repository_name` at all — it looks up commits solely by `sha`, globally, across every repository/stack tracked by the Shipit instance. [7](#0-6) 

Attack sequence:
1. Attacker has legitimate access to (or admin of) an organization/repository "OrgA" that is onboarded to the same shared Shipit instance, with a webhook configured (secret possibly blank, or known to the attacker as the repo owner of that org's GitHub App/webhook config).
2. Attacker crafts and signs (or, if OrgA has no `webhook_secret` configured, trivially satisfies `verify_webhook_signature`, which returns `true` when the secret is blank) a `status` event payload: `repository.owner.login = "OrgA"` (used only for signature verification) but `sha` set to a publicly known commit SHA belonging to a completely different, unrelated stack ("OrgB/victim-repo") tracked by the same Shipit instance.
3. `verify_signature` validates the request using OrgA's config and passes. [1](#0-0) 
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no ownership check, finds the victim's commit, and calls `create_status_from_github!`, injecting an arbitrary state/context/description status onto it. [3](#0-2) 

This is a direct analog of the report's root cause: a value/identity checked at one boundary (the signing organization) is silently substituted for a different, unverified value (the target repository/commit) when the actual state-changing effect is applied — exactly the same class of "authorized-for-A, acted-on-B" substitution as `RngRelayAuction`'s stale `reserveForOpenDraw` being counted twice across draw boundaries.

### Impact Explanation
Injecting a forged commit status onto an unrelated stack's commit can flip CI/CD gating signals that Shipit itself consumes for continuous deployment decisions (statuses/check runs are the primary automated-deploy trigger surface in Shipit). An attacker who legitimately controls webhook delivery for one onboarded organization can therefore inject fabricated "success" statuses for commits belonging to a different organization's stack on the same instance, potentially unlocking or misleading an unauthorized deploy decision for a repository/organization they have no legitimate access to — this is a cross-repository write of authoritative state performed under another organization's trust boundary.

### Likelihood Explanation
Requires: (a) a Shipit instance configured with more than one GitHub organization/App (documented/supported configuration), and (b) attacker control (or knowledge of a blank/known webhook secret) over one of those organizations' webhook delivery. Given webhook secrets are explicitly optional and multi-org setups are a supported configuration, this is a realistic misconfiguration a low-privileged external party (a member of one onboarded org) can exploit against another onboarded org sharing the same instance, without needing any Shipit session, API token, or the target org's own secret.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to commits belonging to the repository identified in the payload (as `PushHandler`/`CheckSuiteHandler` already do via `stacks`/`Repository.from_github_repo_name(repository_name)`), so that a status update can only affect commits under the same repository whose organization was used to authenticate the webhook signature.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (webhook secret unset) and `OrgB` (tracks stack `OrgB/victim-repo` with a known commit SHA `deadbeef...`).
2. As an outsider who can trigger/forge a webhook delivery addressed to `OrgA` (e.g. by controlling repository/org settings for OrgA, or because OrgA's secret is blank), POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha in OrgB/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
}
```
3. `verify_signature` authenticates using `OrgA`'s config (trivially passes since its secret is blank / attacker-known) and the request is accepted.
4. `StatusHandler#process` finds the commit by `sha` regardless of repository and creates a forged `success` status on the `OrgB/victim-repo` commit, potentially triggering continuous deployment for a repository the attacker has no legitimate access to.

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```
