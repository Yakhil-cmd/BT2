Confirmed: the vulnerability chain is exact. The `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — [1](#0-0) [2](#0-1) . But every `Handler` (base class used by `PushHandler` and all `pull_request` handlers) resolves the actual repository/stack to mutate using a **separate** field from the same JSON body, `payload.dig('repository', 'full_name')` [3](#0-2) , with no cross-check that `full_name`'s owner matches `repository.owner.login`. In a multi-organization Shipit deployment (a documented, supported configuration where each GitHub org has its own `webhook_secret`) [4](#0-3) [5](#0-4) , this is a genuine binding break: "organization that authenticated" (`repository.owner.login`, verified against that org's secret) vs. "the repository that is written" (`repository.full_name`, used unchecked by handlers to locate stacks/pull requests).

### Title
Cross-Organization Webhook Forgery via Mismatched `repository.owner.login` (Authenticated) and `repository.full_name` (Acted On) — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
In a multi-GitHub-App Shipit deployment, the webhook signature is verified using a `webhook_secret` selected from `repository.owner.login` (or `organization.login`) in the untrusted payload, but every webhook handler subsequently resolves the target repository/stack from a different field of that same untrusted payload, `repository.full_name`, without ever confirming the two agree. A legitimate admin of one onboarded GitHub organization (who therefore knows that org's own `webhook_secret`) can forge a signed webhook whose `owner.login` names their own org (so it passes verification) while `repository.full_name` names a completely different organization's repository, causing Shipit to act on that victim organization's stacks.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against like this:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

Shipit explicitly supports configuring one `webhook_secret` per GitHub organization: `Shipit.github(organization:)` loads a distinct `GitHubApp` (and secret) per org key in `secrets.github` [5](#0-4) , as documented under "Using Multiple Github Applications" [4](#0-3) . Each organization's admin, having created and configured their own GitHub App, legitimately knows their own `webhook_secret`.

Once the signature check passes (using the secret picked from `repository.owner.login`), `WebhooksController#create` just hands the *raw parsed body* to the event handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [7](#0-6) 

All handlers inherit repository resolution from the base `Handler` class, which uses a different field entirely:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses this to trigger `stack.sync_github` for every matching branch [8](#0-7) , and pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `edited_handler.rb`, `assigned_handler.rb`, etc.) independently re-derive the repository from `params.repository.full_name` the same way [9](#0-8) . `Repository.from_github_repo_name` simply splits `"owner/name"` and does a DB lookup, with no relationship to which org's secret validated the request [10](#0-9) .

Because `owner.login` (used for authentication) and `full_name` (used for the actual data mutation) are two independent, attacker-controlled JSON fields in the same unsigned-until-checked body, and nothing ties them together, an attacker who is a legitimate/authenticated tenant for Organization A can forge a valid signature (using Org A's known secret) while making the payload's `repository.full_name` point at Organization B's repository, which Shipit will act upon as if it were an authentic Org B webhook.

### Impact Explanation
This breaks the trust boundary between distinct GitHub organizations sharing one Shipit instance: an entity authorized only for Org A's webhooks can inject forged push/pull_request events attributed to Org B's repositories. Via `PushHandler`, this can force `GithubSyncJob` to fetch and append attacker-chosen commits (bounded by what `stack.github_commits` returns for the *real* victim repo, but the timing/trigger and `expected_head_sha` are attacker-controlled) into Org B's stacks, and via pull-request handlers it can create/archive/deprovision Org B's review stacks and manipulate `PullRequest` records cross-organization — an unauthorized cross-repository/cross-organization write, meeting the "cross-repository writes" Critical-tier impact bar.

### Likelihood Explanation
Requires only that the attacker is a legitimate, non-privileged tenant of at least one GitHub organization already configured in the multi-org Shipit deployment (i.e., they know their own org's `webhook_secret`, which is not a "leaked credential" — it's their own configured value) and knowledge of a target org/repo name that is also hosted on the same Shipit instance. No Shipit session, API token, or GitHub App private key is needed; only the ability to send an arbitrary signed HTTP POST to `/webhooks`.

### Recommendation
After signature verification selects an organization via `repository_owner`, re-derive the acted-upon repository from the *same* verified owner field rather than trusting the independent `repository.full_name` value, or explicitly assert `repository.full_name.split('/').first == repository_owner` before dispatching to handlers. Alternatively, pass the verified `repository_owner` into each handler and require it match the owner portion of `repository.full_name` before any lookup/mutation occurs.

### Proof of Concept
1. Shipit is configured with two orgs, `orgone` and `orgtwo`, each with a distinct `webhook_secret` (per `docs/setup.md`'s multi-app config) [4](#0-3) , both with existing stacks/review-stack repositories tracked.
2. An admin of `orgtwo` (who legitimately knows `orgtwo`'s `webhook_secret`, e.g. because they configured the GitHub App webhook themselves) crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-influenced-sha>",
  "repository": { "owner": { "login": "orgtwo" }, "full_name": "orgone/victim-repo" }
}
```
3. They compute `X-Hub-Signature: sha1=HMAC-SHA1(orgtwo_webhook_secret, raw_body)` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgtwo")` and validates the signature successfully [1](#0-0) .
5. `create` dispatches the parsed body to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("orgone/victim-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: ...)` on `orgone`'s stack [8](#0-7)  — despite the request never having been authenticated as coming from `orgone`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
