### Title
Cross-stack unauthorized read of stack/deploy state via stack-scoped API token in CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` resolves the target stack directly from the request parameter (`Stack.from_param!(params[:stack_id])`) instead of using the stack-scoped lookup (`stacks.from_param!(params[:stack_id])`) that every other API controller inherits from `Shipit::Api::BaseController`. This breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack the request actually touches," letting a token scoped to one stack read CI/build state for any other stack in the instance.

### Finding Description
`Shipit::Api::BaseController` defines the authorization boundary used by every API endpoint: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the `ApiClient` is scoped to a specific stack, and `Stack.all` otherwise. `stack` then performs `from_param!` against that restricted relation, so any controller relying on the inherited `stack` method correctly enforces: token's authorized stack == stack touched.

`Api::CCMenuController` overrides this method and drops the scoping entirely: [2](#0-1) 

It still declares `require_permission :read, :stack` and authenticates via `ApiClient.authenticate(params[:token])`: [3](#0-2) 

`require_permission!` only checks that the `ApiClient`'s `permissions` array includes `read:stack`; it never checks `current_api_client.stack_id` against the requested `stack_id`: [4](#0-3) 

So the equality that should hold — `current_api_client.stack_id == params[:stack_id]` (when the client is stack-scoped) — is never enforced in this controller. `ApiClient` tokens can legitimately be scoped to a single stack (see `belongs_to :stack, optional: true` and the `CCMenuUrlController#client` helper that creates such tokens), and are handed out embedded in a CI-status URL: [5](#0-4) 

Any holder of such a token — which is designed to be pasted into third-party CI dashboard tools, i.e. treated as low-sensitivity/widely shared — can instead pass a different `stack_id` to `Api::CCMenuController#show` and receive that other stack's build status, last build label, lock/lock-reason state, and deploy timing, regardless of which stack the token was originally minted for.

### Impact Explanation
This matches the "High" bucket: unauthenticated (from the target stack's perspective) read of stack state/build/deploy status across repositories that the holder of a narrowly-scoped, low-privilege token was never granted access to. An attacker who obtains one legitimate CCMenu token (e.g. leaked in a shared CI dashboard config) can enumerate/observe deploy state, lock reasons, and build history for every stack managed by the Shipit instance, not just the one the token was created for.

### Likelihood Explanation
High. No special privileges beyond possessing any single valid CCMenu/API token (`read:stack` permission) are required; the attacker only needs to know or guess another stack's `to_param` (owner/repo/environment string), which is often predictable or discoverable from the UI/other stacks' URLs. No cryptographic material, session, or GitHub credentials need to be forged — only substitution of the `stack_id` request parameter.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped lookup instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override so it inherits `BaseController#stack`, restoring the binding between the authenticated `ApiClient`'s `stack_id` and the stack actually rendered.

### Proof of Concept
1. Stack `owner/repoA/production` creates a CCMenu client scoped to it via `GET /stacks/owner/repoA/production/ccmenu_url`, receiving a token `T` bound to `ApiClient#stack_id = A`.
2. Attacker (or any party who obtained `T`) requests:
   `GET /api/stacks/owner/repoB/staging/ccmenu.xml?token=T`
3. `authenticate_api_client` succeeds because `T` is a valid token with `read:stack` permission.
4. `require_permission!(:read, :stack)` passes because it only checks the `permissions` array, not `stack_id`.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning stack B.
6. The response discloses stack B's build/deploy status even though token `T` was only meant to authorize reads of stack A — confirmed by the absence of any test in `test/controllers/api/ccmenu_controller_test.rb` verifying stack-scoped tokens are rejected for other stacks, unlike the equivalent coverage that exists for `Api::StacksController` (`test "an api client scoped to a stack will only see that one stack"`).
