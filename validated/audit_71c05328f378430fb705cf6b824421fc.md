### Title
Cross-organization commit status forgery via unscoped `StatusHandler` webhook lookup — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The Yield report describes a binding break where `Witch.grab` records the previous vault owner keyed only by `vaultId`, and a later `buy` call trusts that stale mapping without re-checking whether the entity currently holding the vault is still the one the record refers to — so control is handed back based on an identity that is no longer valid. The same class of bug — "the entity that was authenticated is not the entity the write ultimately targets" — exists in `Shipit`'s GitHub webhook pipeline: signature verification proves *which organization* sent the payload, but the handler that mutates state (`StatusHandler`) looks records up by a global, org‑agnostic key (`sha`) instead of scoping the write to the verified organization/repository.

### Finding Description
Webhook authenticity in this engine is verified per-organization: [1](#0-0) 

`repository_owner` is derived from the payload itself (`repository.owner.login`, or `organization.login` as fallback) and used to pick which organization's GitHub App/webhook secret should validate the signature: [2](#0-1) 

This only proves the payload legitimately came from *that* organization's GitHub installation — the binding is: `verified organization == payload.repository.owner`. It says nothing about which `Stack`/`Commit` records the handler is allowed to modify.

`StatusHandler#process`, however, updates commit statuses purely by SHA, with no scoping to the verified organization/repository at all: [3](#0-2) 

`Commit` is a global table shared across every `Stack`/`Repository` hosted by the Shipit instance (multi-tenant by design — many orgs/repos can be onboarded). Since the only binding enforced before this write is "signature valid for organization A," but the actual write target is "any `Commit` row anywhere in the database whose `sha` matches," a commit that is shared between two different repositories (e.g., a fork, a subtree/rebase-preserved commit, a shared vendored commit, or simply two stacks pointing at the same underlying repository history) will have its CI status updated by a webhook that only proves authenticity for a *different*, unrelated organization. The equality that is checked (`verified_org == payload.organization`) is not the equality that matters (`commit.stack.repository.owner == verified_org`).

### Impact Explanation
Commit statuses feed directly into `deployable?`/CI-required-status gating and continuous-deployment scheduling. An attacker who administers a low-privilege, low-value repository/organization that is itself legitimately onboarded to this Shipit instance (and can therefore make GitHub emit real, validly-signed `status` webhooks for their own repo, e.g. via their own CI or via GitHub's status API against their own repo) can cause a `success` status to be recorded against any `Commit` row elsewhere in the instance that happens to share the same SHA — including commits belonging to a much more sensitive stack owned by a different organization. If that stack has continuous deployment or "required status" gating configured, this can make an otherwise-not-CI-passed commit `deployable?`, triggering an unauthorized deploy in a stack/org the attacker never had write access to — matching the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own organization/repo already onboarded to the Shipit instance (a realistic scenario for any multi-tenant Shipit install, e.g. an internal platform onboarding many teams' repos), and (2) a commit SHA collision across the attacker's repo and the victim stack's repo — achievable in practice through forks, shared history, cherry-picks, or repos that mirror the same upstream, rather than requiring a SHA-1 preimage break. No privileged Shipit session, API token, or webhook secret of the victim organization is needed; only the attacker's own legitimately-issued webhook credentials are used, satisfying the "unprivileged attacker" constraint.

### Recommendation
Scope `StatusHandler#process` (and any other SHA/ref-keyed handler) to commits belonging to stacks whose `Repository` matches the verified `repository_owner`/`repository.full_name` from the webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner })`, instead of an unscoped `Commit.where(sha: ...)`. More generally, every webhook handler should re-derive and check the owning repository/organization against the value that `verify_signature` actually validated, rather than trusting a bare SHA/ref as sufficient identification of the target record.

### Proof of Concept
1. Onboard organization `attacker-org/low-value-repo` to the Shipit instance (legitimate, low-privilege access).
2. Identify or engineer a commit whose SHA is shared with a commit present in `victim-org/critical-repo`'s stack (e.g., a shared upstream commit, a rebase-preserving cherry-pick, or a repo fork with common history).
3. From `attacker-org`'s repo, generate a genuine, correctly-signed GitHub `status` webhook event (`state: success`) for that shared SHA — GitHub signs it with `attacker-org`'s webhook secret, which `Shipit::WebhooksController#verify_signature` will validate successfully because `repository_owner` resolves to `attacker-org`.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` with no organization filter, and calls `commit.create_status_from_github!(params)` on every matching `Commit`, including the one belonging to `victim-org/critical-repo`.
5. If the victim stack's CI-required-status/continuous-deployment configuration is now satisfied by this forged status, the commit becomes `deployable?` and can be auto-deployed — an unauthorized deploy triggered entirely from the attacker's own, unrelated organization's webhook credentials.
