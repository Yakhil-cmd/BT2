### Title
Uncaught exception in `chash.isChashValid` from malformed address/chash strings crashes node on unit validation - (File: `chash.js`)

### Summary
`chash.isChashValid()` in `chash.js` processes an attacker-supplied base32/base64-encoded chash string. It wraps only the initial decode step in `try/catch`, but the subsequent bit-length dispatch in `separateIntoCleanDataAndChecksum()` throws an uncaught `Error("bad length=...")` if the decoded buffer's bit-length isn't exactly 160 or 288. This function is reached synchronously and unguarded from `isValidAddress()` in `validation.js` while validating author addresses of any freshly posted unit.

### Finding Description
`isChashValid(encoded)` in [1](#0-0)  only guards the decode call:
```
try{
    var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
}
catch(e){
    console.log(e);
    return false;
}
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);
```
`separateIntoCleanDataAndChecksum()` unconditionally throws if the resulting bit length isn't exactly 160 or 288 [2](#0-1) . Because Node's `Buffer.from(str, 'base64')` silently skips invalid/non-alphabet characters rather than throwing, and the `thirty-two` base32 decoder can likewise tolerate malformed input, a crafted 32- or 48-character `address`/chash string can decode to a buffer whose bit length is not 160/288, causing this second-stage `throw` to escape `isChashValid` uncaught.

`isValidAddress()` in [3](#0-2)  calls `isValidChash` → `chash.isChashValid` directly, with no `try/catch` at any layer. `validation.js` calls `isValidAddress` on every author address of a freshly submitted unit with no surrounding `try/catch`: [4](#0-3) . This is notably inconsistent with the rest of `validate()`, which carefully wraps every other exception-prone call (`objectHash.getUnitHash`, `objectHash.getBase64Hash`, `objectLength.getTotalPayloadSize`) in `try/catch` specifically to convert exceptions into `ifJointError`/`ifUnitError` callbacks instead of letting them propagate.

This mirrors CVE-2017-11553: a crafted/malformed input passed to a low-level parsing routine reaches an unguarded illegal-state code path (there, out-of-bounds memory access in `extend_alias_table`; here, an uncaught `throw` deep inside chash length validation) that was not designed to handle attacker-supplied malformed data at that stage.

### Impact Explanation
An uncaught synchronous exception thrown inside `validate()`'s top-level `mutex.lock` callback (outside of any `async.series` step, and thus outside of the `try/catch` blocks that convert errors to callbacks) is not caught by `validate()`'s own error-handling machinery. Depending on how the calling context (`network.js` `handleJoint`, `divisible_asset.js`, `aa_composer.js`, etc.) invokes `validation.validate`, this can escape as an unhandled exception, crashing the node process (since it originates synchronously outside of a promise chain and outside the `async.series` callback that would route it to `ifJointError`). This produces a denial of service for any node that processes a maliciously crafted unit — matching the "remote denial of service" impact of CVE-2017-11553.

### Likelihood Explanation
Any unprivileged party can craft and post a unit with an author `address` field containing a well-formed-looking (correct-length, valid-alphabet-superset) string designed so that `base32.decode`/`Buffer.from('base64')` leniently produces a buffer of unexpected bit-length. This requires no special privileges — the unit only needs to reach the `validate()` function, which happens for every unit broadcast or submitted to a node.

### Recommendation
Wrap the entire body of `isChashValid()` in a single `try/catch` (not just the initial decode call) and return `false` on any exception, ensuring malformed encoded values are rejected as invalid rather than throwing. Additionally, `separateIntoCleanDataAndChecksum` should validate that `bin2buffer`-derived buffers have exactly the expected byte length before further processing, and callers such as `validation.js`'s `arrAuthorAddresses.every(isValidAddress)` should not assume `isValidAddress` is exception-safe.

### Proof of Concept
1. Construct a 48-character string intended to represent a chash288 address/definition-hash field, where several characters fall outside the standard base64 alphabet (e.g., replace some characters with `!`, ` `, or other symbols) such that `Buffer.from(str, 'base64')` silently drops those characters and returns a buffer whose length in bits is not 288.
2. Place this string as an `author.address` (or other chash-validated field) in an otherwise well-formed unit and submit it to a node via the normal unit-posting path.
3. During `validate()`, `arrAuthorAddresses.every(isValidAddress)` at [4](#0-3)  invokes `isValidAddress` → `chash.isChashValid`, which throws inside `separateIntoCleanDataAndChecksum` (`chash.js:45-53`) with no enclosing `try/catch`, propagating as an unhandled exception and crashing the node process.
