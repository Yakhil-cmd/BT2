## Title
Information Exposure of Textcoin Private-Key Mnemonics Through Log File in `claimBackOldTextcoins` - (File: wallet.js)

## Summary
The Liferay advisory describes an LDAP import routine that writes a sensitive identifier (user email address) to the application log file, where any local reader of the log can see data that should stay confidential. `ocore`'s wallet module has an analogous pattern: the textcoin auto-reclaim routine `claimBackOldTextcoins` prints the full textcoin **mnemonic** — which is the actual private key material for that wallet address — to `console.log`, the same sink used throughout the codebase for operational logging that in production hub/wallet deployments is persisted to disk.

## Finding Description
`claimBackOldTextcoins` iterates over `sent_mnemonics` rows containing unclaimed textcoins and, for each one, calls `receiveTextCoin(row.mnemonic, to_address, ...)`. In both the success and failure callback branches, the mnemonic is concatenated directly into a `console.log` call: [1](#0-0) 

Unlike the `assocMnemonics` return value in `sendMultiPayment`, which is handled via callback and stored server-side only in `sent_mnemonics.mnemonic` (a DB column, not a log), this code path unconditionally writes the raw mnemonic string to the process's standard logging channel. `expandMnemonic` (used by `receiveTextCoin`) shows that a mnemonic alone is sufficient to derive the private key, public key, and address for the textcoin funds: [2](#0-1) 

The same file already treats mnemonic disclosure as sensitive elsewhere — e.g., private textcoins are protected by requiring an explicit `getPrivateAssetPayloadSavePath`/zip mechanism rather than being logged, and `expandMnemonic`'s own error path avoids echoing the raw mnemonic on invalid input except in the thrown error message. The `claimBackOldTextcoins` logging statements break this pattern and expose the mnemonic — i.e., spendable private key material for the textcoin — in plaintext through the standard log output, matching the CWE-532 "Information Exposure Through Log File" class from the reference advisory, but the exposed secret here is far more sensitive than an email address: it is a bearer credential to un-claimed funds.

## Impact Explanation
Any process or operator with read access to the node's stdout/log file (a normal deployment artifact for `ocore`-based hubs and wallets, which typically redirect stdout to persistent log files for monitoring) can recover the mnemonic of any textcoin that failed to be claimed within the retry window and remains unclaimed. Because the mnemonic directly yields the signing key for `addrInfo.address`, whoever reads the log can construct and broadcast a spend from that address, i.e., steal the pending textcoin funds before (or instead of) the intended recipient claiming them. This is a concrete unauthorized-spending vector, not merely a privacy leak, since textcoin funds are bearer-instrument style (mnemonic = key).

## Likelihood Explanation
`claimBackOldTextcoins` is invoked automatically (per its own comment: "if a textcoin was not claimed for 'days' days, claims it back") for wallets that use the textcoin feature, so the logging occurs during ordinary operation without any attacker interaction — the same "local, no privileges beyond normal log access" reachability pattern the report calls out for the LDAP case. Every unclaimed/expired textcoin mnemonic that a wallet ever generated over time can end up captured in the log.

## Recommendation
Remove the mnemonic from both `console.log` statements in `claimBackOldTextcoins`; log only non-sensitive identifiers such as the unit hash, target address, or asset, e.g. replace `"failed claiming back old textcoin "+row.mnemonic+": "+err` and `"claimed back mnemonic "+row.mnemonic+...` with messages keyed on `to_address`/`unit` instead of the raw mnemonic: [1](#0-0) 

## Proof of Concept
1. A wallet using textcoins creates one or more unclaimed textcoin outputs (via `sendMultiPayment` with a `textcoin:` prefixed address), which get stored with their mnemonics in `sent_mnemonics`. [3](#0-2) 
2. After the configured number of days elapses without the recipient claiming, an operator-triggered or scheduled call to `claimBackOldTextcoins(to_address, days)` runs.
3. For each unclaimed row, the code executes `console.log("claimed back mnemonic "+row.mnemonic+ ...)` or the failure variant, printing the full mnemonic to stdout/log.
4. Anyone with read access to the resulting log file (e.g., via log rotation, centralized log aggregation, or shared server access) extracts the mnemonic, calls the same `expandMnemonic` logic to derive the private key, and spends the underlying funds before the legitimate reclaim/claim transaction confirms — resulting in fund theft.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
