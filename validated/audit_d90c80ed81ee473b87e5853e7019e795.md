### Title
Cross-organization commit status forgery via webhook signature key confusion - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an incoming webhook against using an attacker-supplied field of the *unverified* JSON body (`repository.owner.login` or `organization.login`), rather than binding the verified payload to the specific organization/repository it is later applied to. Downstream, `Shipit::Webhooks::Handlers::StatusHandler#process` applies the payload's commit status to **any** `Commit` in the database matching `sha`, with no check that the commit belongs to a stack/repository owned by the organization whose secret validated the signature. An operator who legitimately controls one onboarded GitHub organization's webhook secret can therefore forge a webhook that is "signed" with their own secret but whose content (commit SHA, state, description) targets a completely different organization's commit, letting them write CI status for repos they do not control.

### Finding Description
`Shipit::WebhooksController` verifies the shared-secret HMAC before trusting a webhook payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params` (the untrusted, not-yet-verified JSON body) and is used to pick which `GitHubApp`/`webhook_secret` to validate the signature against, via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Since the entire `request.raw_post` (including `repository.owner.login`/`organization.login` and every other field like `sha`, `repository.full_name`, etc.) is under the HMAC, whoever knows *any one* organization's `webhook_secret` (e.g. an admin who legitimately configured Shipit for their own org, as multiple orgs can be configured side-by-side per `docs/setup.md` and `config/secrets.development.shopify.yml`) can construct an arbitrary JSON body, self-sign it with their own known secret, and set `X-Github-Event: status` with a `sha` belonging to a commit tracked under a completely different organization's stack.

`StatusHandler#process` then performs a **global, unscoped lookup** by `sha` and mutates status for every matching commit, with no re-validation that the commit's stack/repository belongs to the organization that authenticated: [4](#0-3) 

The equality that should hold but does not: `organization whose secret verified the signature == organization owning the repository/commit being mutated`. Instead, the verification step consumes an attacker-controlled field solely to *select* a secret, and the write path (`Commit.where(sha:)`) is entirely decoupled from that field, breaking the binding between authentication scope and write scope.

Other push/pull_request handlers resolve the target via `repository.full_name` (`Handler#repository_name`) which is likewise attacker-controlled within the same signed payload and independent from the field used to pick the verifying secret (`repository.owner.login`), so the same class of confusion extends to `PushHandler` (triggering `GithubSyncJob`/deploy sync for arbitrary stacks) as well: [5](#0-4) [6](#0-5) 

### Impact Explanation
This allows a party who is legitimately onboarded to Shipit for one organization (and therefore knows/controls that organization's `webhook_secret`) to forge GitHub CI status events for commits belonging to any other organization's stacks hosted on the same Shipit instance. Commit statuses can gate required CI checks used by Shipit's merge queue and continuous-deployment logic, so forged "success" statuses can be used to push another org's pull request past required-status checks and force a merge or deploy that would otherwise be blocked — an unauthorized deploy/merge outcome across an organizational trust boundary the attacker does not otherwise have write access to. This matches the report's underlying bug class (a signature/authentication check that does not actually bind to the fields it is meant to protect), analogized here as a cross-tenant authorization boundary break rather than the original permit-griefing scenario.

### Likelihood Explanation
Requires the attacker to already be a legitimate, onboarded party for at least one organization configured in the multi-org Shipit deployment (i.e., they know that org's `webhook_secret` because they set it up) — this is a lower bar than compromising `GITHUB_TOKEN`, an `ApiClient` token, or a Shipit user session, and is realistic for any multi-tenant Shipit deployment serving several unrelated GitHub organizations, which the engine explicitly supports (`docs/setup.md`, `lib/shipit.rb#github_app_config`).

### Recommendation
- Bind the verified webhook to the specific repository/organization pair the secret is scoped to and reject or ignore any payload where `repository.full_name`'s owner (or `organization.login`) does not match the organization whose secret validated the signature.
- In `StatusHandler#process`, scope the `Commit` lookup by the verified repository (e.g., `commit.stack.repository == verified_repository`) instead of a bare, cross-tenant `Commit.where(sha:)`.
- Apply the same repository/organization-consistency check in all other `Handler` subclasses that resolve a stack via `repository.full_name`.

### Proof of Concept
1. Onboard/administer OrgA in a multi-org Shipit deployment and note its configured `webhook_secret`.
2. Identify a commit SHA belonging to a stack under OrgB (also hosted on the same Shipit instance), e.g. from public GitHub history.
3. Craft a JSON body:
```json
{
  "sha": "<OrgB commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>`.
5. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` = `"OrgA"`, validates successfully against OrgA's secret.
6. `StatusHandler#process` runs `Commit.where(sha: "<OrgB commit sha>")` and writes a forged "success" status onto OrgB's commit, independent of the fact that only OrgA's secret was verified [4](#0-3) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
