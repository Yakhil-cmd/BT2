### Title
Webhook signature verification is keyed on an attacker-controlled payload field that is decoupled from the repository the handlers actually write to, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated, unparsed JSON body. Every webhook handler then independently re-reads `repository.full_name` from that same JSON body to decide which `Stack`/`Repository`/`Commit` to act on. Because Shipit supports hosting multiple GitHub organizations with independent webhook secrets, an attacker who legitimately controls one onboarded organization (and therefore knows its own valid `webhook_secret`) can sign a payload whose `repository.owner.login` matches their own org (so the signature verifies) while setting `repository.full_name` to a repository belonging to a *different* onboarded organization. The signature check passes, but the handlers write against the spoofed repository.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up a completely separate `GitHubApp` (and its own `webhook_secret`) per organization key when multiple GitHub Apps are configured: [3](#0-2) 

This multi-org configuration is a documented, in-scope feature: [4](#0-3) 

Meanwhile, every handler resolves the target repository from a *different* field of the same untrusted body, with no cross-check against `repository_owner`/the org whose secret validated the signature: [5](#0-4) 

For example, the `StatusHandler` writes a commit status for any commit matching `params.sha`, regardless of which org's secret validated the request: [6](#0-5) 

And pull-request handlers resolve `Repository.from_github_repo_name(params.repository.full_name)` and mutate review stacks (`archive!`/`unarchive!`) based on that same unchecked field: [7](#0-6) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository being written to**. The verified signature only proves "the sender knows the secret of the org named in `repository.owner.login`/`organization.login`"; it proves nothing about the `repository.full_name` (or `sha`, in the `status` handler's case) that the handler subsequently trusts and acts on. Before the attack: two orgs, `OrgOne` and `OrgTwo`, each with independent webhook secrets, both onboarded to the same Shipit instance (as the test fixture `test/dummy/config/secrets_double_github_app.yml` demonstrates is supported). After the attacker's request: a payload signed with `OrgOne`'s secret, but whose `repository` (or commit `sha`) fields reference `OrgTwo`, is accepted and processed against `OrgTwo`'s data.

### Impact Explanation
This breaks a deployment-trust binding equivalent to "an organization that authenticated versus the repository that is written," matching the required impact bar of cross-repository writes. Concretely, an attacker who controls (or is a legitimate low-privilege member of) one onboarded organization can:
- Forge `status` events to alter commit statuses (`Commit#create_status_from_github!`) on repositories belonging to a different, victim organization, which can influence merge-queue and CI-gating decisions Shipit uses to gate merges.
- Forge `push`/`check_suite` events to enqueue `GithubSyncJob`/`RefreshCheckRunsJob` against a victim org's stack.
- Forge `pull_request` events (`opened`/`closed`/`reopened`/`labeled`) to archive/unarchive/create review stacks belonging to a victim org's repository.

This is a cross-repository write achieved purely by crafting a JSON body differently from the field used for authentication — no possession of the victim org's webhook secret, GitHub token, or Shipit session is required.

### Likelihood Explanation
Requires: (1) the deployment to use the documented multi-organization GitHub App configuration, and (2) the attacker to legitimately control (or have signing knowledge of the webhook secret for) at least one of the onboarded organizations — a realistic scenario for any multi-tenant Shipit instance shared across several orgs/teams, where the attacker is an unprivileged member of one tenant attacking another tenant's stacks.

### Recommendation
After `verify_signature` succeeds, bind the verified organization to the rest of request processing: pass the verified `repository_owner`/organization down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and have each handler (and the shared `Handler#repository_name`/`stacks` helper) assert that the resolved repository's `owner` matches the organization whose secret validated the signature, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), both with stacks/repositories onboarded.
2. As an attacker who knows `OrgOne`'s webhook secret (e.g., a member of `OrgOne` with access to its GitHub App settings), craft a `status` webhook payload:
   ```json
   {
     "sha": "<victim-commit-sha-in-OrgTwo-repo>",
     "state": "success",
     "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
   }
   ```
3. Sign the raw body with `OrgOne`'s `webhook_secret` and send it to `POST /webhooks` with header `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and verifies successfully using `OrgOne`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged commit status onto the `OrgTwo` commit — despite the request never being signed by `OrgTwo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
