## Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but the handlers act on the repository named in `repository.full_name` — allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController` selects which GitHub App config (and therefore which `webhook_secret`) to verify a webhook's HMAC signature against by reading `repository.owner.login` (or `organization.login`) out of the *unauthenticated* JSON body. Every webhook handler, however, resolves the `Repository`/`Stack` to act on from a completely different field of the same unauthenticated body: `repository.full_name`. Because these two fields are never checked for consistency, an attacker who knows the `webhook_secret` for **any** GitHub organization configured on the instance can forge a validly-signed webhook whose `repository.full_name` points at a stack belonging to a **different** organization tracked by the same Shipit install, and have Shipit process it as authentic.

### Finding Description
In a multi-organization Shipit deployment (the schema documented/shown in `config/secrets.development.shopify.yml` and `lib/shipit.rb#github_app_config`), each GitHub organization has its own `webhook_secret`. The controller picks the app/secret to verify with like this: [1](#0-0) [2](#0-1) [3](#0-2) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is derived purely from the attacker-controlled JSON body — nothing ties it to any authenticated source (there is no independent GitHub delivery header identifying the true installation/organization). Once signature verification passes, `create` dispatches the same raw, attacker-controlled body to the registered handlers: [4](#0-3) 

Every handler, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field, `repository.full_name`, via the shared base class: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository.owner.login` (used for signature-org selection) and `repository.full_name` (used for target-repository resolution) are independent JSON keys inside the same forgeable body — there is no requirement that `full_name` start with `owner.login`. Concretely:

- `PushHandler` calls `stack.sync_github(expected_head_sha: ...)` on whatever stack `repository.full_name` names: [6](#0-5) 
- `PullRequest::ReopenedHandler`/`ClosedHandler`/etc. resolve their target repository/stack the same way, via `Repository.from_github_repo_name(params.repository.full_name)`: [7](#0-6) 

The equality that must hold for the signature check to mean anything is:
`organization whose secret authenticated the request == organization owning the repository/stack that the handler subsequently mutates`.

That equality is never enforced. An attacker who legitimately controls (or has otherwise obtained the `webhook_secret` for) Organization A can craft a body with `"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/private-app"}`, sign it with Organization A's secret, and Shipit will treat it as a fully authenticated event for Organization B's tracked stack.

### Impact Explanation
This breaks the deployment-trust boundary between tenants of the same Shipit instance (the exact multi-org config Shipit ships and documents). Concretely an attacker holding one organization's webhook secret can:
- Forge `push` events to force `GithubSyncJob`/`sync_github` on an unrelated stack belonging to another org, influencing when new commits are ingested and potentially triggering continuous delivery for that foreign stack.
- Forge `pull_request`/`check_suite`/`status` events against another org's tracked review stacks and commits, manipulating PR/CI state records that other automation (auto-merge, deploy gating) may rely on.

This is a cross-repository/cross-organization write triggered purely from a payload field that was never covered by the signature-selection logic, matching the Critical "cross-repository writes / unauthorized deploy" impact class.

### Likelihood Explanation
Requires the attacker to know a `webhook_secret` for at least one organization configured on the target Shipit instance — realistic for any tenant/org admin in a shared, multi-org Shipit deployment (they legitimately possess their own org's secret) but not for a fully external, unauthenticated attacker. Given that multi-org configuration is a supported, documented mode (`config/secrets.development.shopify.yml`), this is a practical insider/tenant-boundary bypass, not merely theoretical.

### Recommendation
Bind the field used to select/verify the signing secret to the same field used to resolve the target repository (`repository.full_name`), or verify the signature against *all* configured organizations' secrets and confirm that the organization matching the successful secret is actually the owner segment of `repository.full_name` before dispatching to handlers. Reject the webhook if the two disagree.

### Proof of Concept
1. Configure Shipit in multi-org mode with `org-a` and `org-b`, each with a distinct `webhook_secret` (per `config/secrets.development.shopify.yml` schema), and track a stack for `org-b/private-app`.
2. As an actor who knows `org-a`'s `webhook_secret` (e.g., an `org-a` admin), build a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen existing sha in org-b/private-app>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/private-app" }
}
```
3. Compute `X-Hub-Signature` with `org-a`'s webhook secret and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and the signature validates successfully.
5. `Shipit::Webhooks::Handlers::PushHandler` resolves `stacks` via `Repository.from_github_repo_name("org-b/private-app")` — the tracked stack for `org-b` — and calls `stack.sync_github(expected_head_sha: ...)`, forcing sync/deploy behaviour on `org-b`'s stack despite the request never being authenticated by `org-b`'s secret.
