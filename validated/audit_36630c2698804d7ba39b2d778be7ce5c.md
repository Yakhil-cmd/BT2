### Title
Integer (float-precision) overflow in asset denomination cap validation allows supply-inflation of fixed-denomination assets - ([File: validation.js])

### Summary
`validateAssetDefinition()` in `validation.js` computes the total cap declared by an asset's `denominations` array by multiplying attacker-controlled `count_coins` and `denomination` fields without bounding the product to a safely representable integer range. Because JavaScript numbers lose integer precision above `Number.MAX_SAFE_INTEGER` (2^53-1 ≈ 9.007e15), and `constants.MAX_CAP` is `9e15` (just under that limit) while `count_coins` is *not* capped at `MAX_CAP`, an attacker can construct a denomination list whose true product overflows/loses precision, making the cap-consistency check pass on a bogus/inflated value. This is the JS-numeric analog of the reported native integer-overflow class (CVE-2017-12086): an untrusted numeric field is used in an arithmetic computation whose result exceeds the safe/expected range, corrupting downstream state (here, the asset's issuance accounting) instead of raw memory.

In `validateAssetDefinition` (`validation.js`, lines ~2757-2792): [1](#0-0)

`denomInfo.denomination` is bounded by `constants.MAX_CAP` (9e15) [2](#0-1) , but `denomInfo.count_coins` is validated only with `isPositiveInteger`, which imposes no upper bound at all. The product `count_coins * denomination` is therefore unbounded and can trivially exceed `Number.MAX_SAFE_INTEGER`, at which point JavaScript's double-precision arithmetic silently rounds the result. An attacker can choose `count_coins` and `denomination` such that the *rounded* `total_cap_from_denominations` equals the declared `payload.cap`, even though the mathematically true product (and the actual number of coins that can later be issued per denomination) is different from what the cap implies.

The same unguarded multiplication pattern recurs at issuance time in `indivisible_asset.js`: [3](#0-2) 
```
var denomination = row.denomination;
...
var count_coins_to_issue = row.count_coins || Math.floor((remaining_amount+tolerance_plus)/denomination);
var issue_amount = count_coins_to_issue * denomination;
```
and is checked against the unit at validation time in `validation.js`: [4](#0-3) 
```
if (denomInfo.count_coins === null){ // uncapped
    if (input.amount % denomination !== 0)
        return cb("issue amount must be multiple of denomination");
}
else{
    if (input.amount !== denomination * denomInfo.count_coins)
        return cb("wrong size of issue of denomination "+denomination);
}
```
Both of these depend on the same floating point multiplication, so the precision loss introduced at asset-definition time is echoed consistently at issuance/validation time — nodes will agree with each other (since all use the same IEEE-754 arithmetic), but the actual value diverges from what the developer/user intended the cap to enforce, i.e., the numeric “cap” invariant that the codebase relies on to bound supply is not actually enforceable for crafted large `count_coins`/`denomination` pairs.

### Impact Explanation
This allows a rogue asset issuer to define an asset whose declared `cap` does not match the real maximum supply obtainable from its denominations, because the validation multiplication silently loses precision. Depending on the chosen values, the attacker can arrange for the enforced (rounded) cap to be smaller than the value actually needed to pass the “sum of denominations equals cap” check while the perceived per-denomination `count_coins` allows issuing more total value than a naively-computed cap would suggest, resulting in supply inflation for that custom asset beyond its stated cap. This falls under "supply inflation" for AA/asset issuance, one of the accepted high-impact categories.

### Likelihood Explanation
Reaching this code path requires only posting a standard `asset` definition message with `fixed_denominations: true` and a `denominations` array — an action any unprivileged asset issuer can perform without special permissions. Constructing values whose product overflows `Number.MAX_SAFE_INTEGER` while still passing `isPositiveInteger` requires no privileged access, only arithmetic care, making exploitation practically feasible for any user issuing a custom asset.

### Recommendation
- Bound `denomInfo.count_coins` to `constants.MAX_CAP` (or `Number.MAX_SAFE_INTEGER / denomInfo.denomination`) before it is used in any multiplication.
- Before adding to `total_cap_from_denominations`, check that `denomInfo.count_coins * denomInfo.denomination` does not exceed `Number.MAX_SAFE_INTEGER` and matches an exact-integer bignum computation (e.g. use `BigInt` for the cap-consistency check instead of native `Number` multiplication).
- Apply the same safe-integer/BigInt check to the issuance-time computation in `indivisible_asset.js` (`issue_amount = count_coins_to_issue * denomination`) and the validation-time check in `validation.js` (`input.amount !== denomination * denomInfo.count_coins`).

### Proof of Concept
1. Craft an `asset` definition message with `fixed_denominations: true` and a `denominations` array containing an entry where `denomination` is close to `constants.MAX_CAP` (9e15) and `count_coins` is chosen (e.g. a large multi-digit integer) such that `count_coins * denomination`, evaluated in IEEE-754 double precision, rounds to a value equal to the attacker-chosen `payload.cap`, while the mathematically exact product differs.
2. Submit the unit; `validateAssetDefinition` accepts it because `total_cap_from_denominations === payload.cap` under floating-point rounding.
3. Issue coins of that denomination via `indivisible_asset.js`'s `issueNextCoin`, which computes `issue_amount = count_coins_to_issue * denomination` using the same floating-point arithmetic — validation in `validatePaymentInputsAndOutputs`/`validateIndivisibleIssue` accepts it consistently across all nodes, but the resulting total issuable value diverges from the value a correct (BigInt/exact) cap computation would allow, achieving supply inflation relative to the intended cap semantics.

Note: I was not able to fully trace every downstream consumer of `asset_denominations.count_coins` (e.g., `writer.js`'s persistence logic) within the available search budget; a background Devin session with full repository access should verify the exact numeric boundary values needed to construct a working overflow PoC and confirm no additional guard exists elsewhere in `writer.js` or `storage.js`.
