### Title
Multisig timelock override can be bypassed using an unvoted owner's implicit self-approval - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the function invoked by the VM prologue during mempool admission and transaction execution for `MultisigTransaction` payloads, determines whether a pending multisig transaction may execute early despite an active timelock. The override-threshold check (`can_execute_with_timelock`) is fed a vote count that includes the *executing* owner's implicit approval even when that owner never actually cast a vote. This lets an owner who has not voted trigger immediate execution under the override path with fewer real approvals than the configured `override_threshold` requires.

### Finding Description
`validate_multisig_transaction` computes the approval count that is used for both the quorum check and the timelock-override check: [1](#0-0) 

```
// Count approvals, including the executing owner's implicit vote.
let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
    num_approvals += 1;
};
assert!(num_approvals >= num_signatures_required(multisig_account), ...);

// Timelock check — separate from quorum so the error is unambiguous.
assert!(
    can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
    error::invalid_state(ETIMELOCK_NOT_EXPIRED),
);
```

`can_execute_with_timelock` allows bypassing the timelock delay whenever the approval count meets `override_threshold`: [2](#0-1) 

The `num_approvals` value passed in is the *implicit*-inclusive count — it adds 1 for the calling owner even if that owner never voted `approve` on the transaction. This means the override threshold, which is meant to represent a real quorum of owners choosing to bypass the safety delay, can be satisfied by one fewer genuine vote than intended: the last owner to call `execute` can supply their own "vote" for free just by being the executor.

The framework's own test suite documents this exact divergence between `can_execute` (implicit-inclusive) and `can_be_executed` (explicit-only): [3](#0-2) 

```
// owner_3 hasn't voted. can_execute counts their implicit vote (2+1=3 >= override).
assert!(can_execute(address_of(owner_3), multisig_account, 1), 0);
// But can_be_executed doesn't count implicit votes, so it shouldn't pass.
assert!(!can_be_executed(multisig_account, 1), 1);
```

Because `validate_multisig_transaction` (the VM-called admission gate) uses the implicit-inclusive count for the override-threshold check too, an owner with only `override_threshold - 1` genuine approvals can immediately execute the pending transaction bypassing the timelock, simply by being the one who submits the executing transaction. The timelock is intended precisely to give the remaining owners time to react to (and potentially reject) a transaction before it takes effect; the override path is meant to require an explicit supermajority choosing to skip that delay, not to be satisfiable by an owner rubber-stamping their own execution call.

### Impact Explanation
This is a transaction-admission-boundary flaw: `validate_multisig_transaction` is the exact prologue function the VM invokes to decide whether a `MultisigTransaction` may execute (`aptos-move/framework/aptos-framework/sources/multisig_account.move:1328`, doc comment: "Called by the VM as part of transaction prologue ... during mempool transaction validation and as the first step of transaction execution"). A wrong approval-set computation here directly causes execution of a transaction that should not yet be admitted (timelock not expired, insufficient explicit approvals for override). Any state-mutating transaction gated behind a multisig timelock+override policy — funds transfers, upgrades, admin actions — can be pushed through early by a single owner holding just under the override quorum, undermining the safety window the timelock is designed to provide. This is a High-severity admission/approval-set-confusion bug matching the "authenticator/multisig approval validation accepting the wrong approval set" pivot.

### Likelihood Explanation
Exploitation only requires being one of the existing owners (no privilege escalation, no external attacker capability beyond normal owner rights) and requires the account to have configured a timelock with an `override_threshold`. Any owner who is one vote short of the override threshold can trigger this simply by calling execute themselves, since their own implicit vote is silently added to the override count. This is straightforward to trigger and is directly demonstrated by the project's own test (`test_implicit_vote_counts_toward_override`), which proves the discrepancy exists and is currently accepted as passing behavior.

### Recommendation
The override-threshold check in `can_execute_with_timelock`, when invoked from `validate_multisig_transaction`, should use only *explicit* approvals (i.e., the same count `can_be_executed` uses) rather than the implicit-inclusive count that the quorum check uses. Concretely, compute a separate explicit-only approval count for the timelock/override assertion, or require `has_voted_for_approval` for the executing owner before implicit counting is applied to the override check. This preserves the desired semantics: quorum-for-execution may count implicit self-approval, but override-of-timelock must reflect genuine, recorded owner intent to skip the safety delay.

### Proof of Concept
1. Create a multisig account with 3 owners, `num_signatures_required = 2`, and a timelock configured with `override_threshold = 3` (i.e., all 3 owners must explicitly agree to skip the delay).
2. `owner_1` creates a transaction (auto-approves via implicit vote at creation). `owner_2` explicitly approves. Now explicit approvals = 2; `owner_3` has not voted.
3. Before the timelock period elapses, `owner_3` calls execute (submits the `MultisigTransaction`). `validate_multisig_transaction` computes `num_approvals = 2 (explicit) + 1 (owner_3's implicit) = 3`, which meets `override_threshold = 3`.
4. `can_execute_with_timelock` returns `true` and the transaction executes immediately, even though `owner_3` never actually cast an approval vote and `can_be_executed` (explicit-only) would return `false` for the same state — exactly as demonstrated by `test_implicit_vote_counts_toward_override` at [3](#0-2) .

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
