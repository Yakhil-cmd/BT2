### Title
Spot-price-from-reserves oracle pattern in Oscript AAs is manipulable via atomic AA-to-AA call chains - (File: test/samples/uniswap_like_market_maker.oscript, aa_composer.js)

### Summary
The Obyte reference AMM template computes exchange rates directly from an AA's own live `balance[asset]`/`balance[base]` ratio, the same "spot price from pool reserves" pattern that the referenced Abracadabra finding shows is trivially manipulable. In `ocore`, AA-to-AA calls (secondary triggers) execute synchronously within one primary trigger's processing and share the same mutable balance state, so an attacker can shift an AA's reserve ratio and have a dependent AA read the manipulated ratio in the very same top-level unit, without waiting for DAG stabilization.

### Finding Description
`test/samples/uniswap_like_market_maker.oscript` derives all of its trade/issue/divest math from `balance[$asset]` and `balance[base]`, i.e. the AA's own current token reserves, exactly analogous to `MagicLpAggregator._getReserves()`: [1](#0-0) [2](#0-1) 

`balance[]` is evaluated live against `objValidationState.assocBalances`, which is populated either from the `aa_balances` table or from the shared `trigger_opts.assocBalances` object that is passed by reference into every secondary (AA-to-AA) trigger in the same execution chain: [3](#0-2) [4](#0-3) 

Secondary triggers run synchronously as part of the same top-level `handleTrigger` call (`child_trigger_opts = { ...trigger_opts }`), and balances updated by one AA (e.g. a large deposit/swap into the AMM) are immediately visible to the next AA invoked in the chain, all originating from a single unit authored by an unprivileged user: [5](#0-4) 

This means the entire "flash-loan" pattern from the report — inflate reserves, read manipulated price, act on it, and reverse the trade — can be assembled as a single chain of messages/AA calls triggered by one posted unit, without any external capital custody or multi-block delay, because AA-to-AA calls compose atomically and read each other's freshly-updated balances. Unlike the Solidity example, there's no flash loan primitive to borrow free capital, but an attacker can still self-fund a temporary large swap into/out of the AMM and, within the same unit's response chain, have a dependent AA (e.g., a lending or option AA that trusts `balance[]`-derived spot price as its oracle) act on the skewed ratio before the swap is reversed — since remote AAs can also be queried live via getters that read `balance[base]` of another address, as demonstrated by `remote_aa.$f(...)` calling patterns. [6](#0-5) 

### Impact Explanation
Any AA that treats another AA's `balance[]` ratio (or an oracle AA built the same way) as a spot-price source can be driven to mis-price swaps, loans, liquidations, or share issuance within a single attacker-controlled unit. This can lead to unauthorized extraction of AA funds (asset/bytes drained at an artificial rate) or AA insolvency — matching "AA fund loss" impact criteria.

### Likelihood Explanation
The vulnerable pattern (`balance[]`-derived spot price with no TWAP/sanity check) is shipped as the documented reference AMM template for AA authors, so it is likely to be copied into production AAs. Triggering the manipulation requires only posting units with payment messages to chained AAs — reachable by any unprivileged unit poster/AA trigger sender, no special privileges or malicious infrastructure needed.

### Recommendation
- Document (and enforce via linting/tooling) that `balance[]` ratios must not be used directly as a price oracle in Oscript AA templates; recommend TWAP-style state variables (e.g., cumulative price accumulators updated across MCI's) instead of instantaneous reserves.
- For the reference `uniswap_like_market_maker.oscript` template, add minimum-liquidity/maximum-price-impact guards and/or require the price to be read from a MCI-delayed checkpoint rather than the live `balance[]` value so that same-unit AA-to-AA call chains cannot manipulate the ratio actionable by another AA within the same execution.
- Consider warning AA authors in the oscript documentation that secondary triggers execute atomically and share live balance state across the whole chain, so cross-AA price reads must not trust intra-chain, unstabilized balances.

### Proof of Concept
1. Attacker deploys AA `V` that reads `remote_aa.$price()` (or `balance[$asset]`/`balance[base]` of the AMM `M` directly) and acts on it (e.g., grants a loan or mints shares) — following the pattern shown in `test/aa_composer.test.js` "calling a remote function".
2. Attacker posts a single unit that:
   a. Sends a large payment of `base`/`asset` to AMM `M`, shifting `balance[asset]`/`balance[base]` (per `uniswap_like_market_maker.oscript`'s exchange-bytes-to-asset / exchange-asset-to-bytes cases).
   b. As a secondary output/trigger in the same unit's response chain, triggers `V`, which reads the now-skewed `balance[]` ratio of `M` and mis-prices its own operation in the attacker's favor.
   c. Optionally swaps back through `M` in the same chain to restore the ratio.
3. Because secondary triggers share `trigger_opts.assocBalances`/`aa_balances` state synchronously (`aa_composer.js:947-1003`, `1702-1741`), step (b) observes the manipulated reserves from step (a) within the same top-level trigger, with no stabilization delay — reproducing the reserve-manipulation attack from the referenced report inside the ocore AA execution model.
