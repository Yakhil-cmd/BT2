### Title
ERC20Transactor credits XCM holding with the requested amount instead of the actual balance received, allowing fee-on-transfer/deflationary ERC20 tokens to desynchronize escrow accounting and drain the shared checking account - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves ERC20 tokens into a shared `TransfersCheckingAccount` by calling the token contract's `transfer()` and, upon a `true` return value, unconditionally credits the XCM holding register with the *requested* `amount` — never checking how much the checking account's balance actually increased. `deposit_asset_with_surplus` mirrors this: it issues `transfer(beneficiary, amount)` from the checking account for the full `amount` recorded in holding, trusting that balance is actually present.

### Finding Description [1](#0-0) 

`withdraw_asset_with_surplus` computes `(asset_id, amount)` from the XCM `Asset` via `Matcher::matches_fungibles`, then calls `IERC20::transferCall{ to: checking_address, value: amount }` on the arbitrary contract at `asset_id` on behalf of the withdrawing account. If the call succeeds and the ABI-decoded return is `true`, the code does:
```rust
Ok((
    AssetsInHolding::new_from_fungible_credit(
        what.id.clone(),
        Box::new(Erc20Credit(amount)),
    ),
    surplus,
))
```
crediting exactly `amount`, not the delta of the checking account's actual balance before/after the call. This is the direct analog of `CollateralEscrowV1.depositAsset()` recording `collateral._amount = _amount` instead of the real transferred balance. [2](#0-1) 

`deposit_asset_with_surplus` then transfers the full recorded `amount` out of the same shared checking account to the beneficiary, trusting the earlier accounting was accurate. This mirrors the second half of the report: `_withdrawCollateral()` moving `_collateral._amount` (the nominal recorded value) rather than the actually available balance.

Because `Matcher: MatchesFungibles<H160, u128>` only needs to decode a `Location`/`Asset` pair into `(H160, u128)` — it doesn't validate that the referenced contract is a "safe" 1:1 ERC20 — any user-deployed contract address expressed as an `AccountKey20` junction is routed through this transactor. The runtime test `withdraw_and_deposit_erc20s` in `asset-hub-westend/tests/tests.rs` confirms this: a user-deployed contract (`MyToken`) is used directly as an XCM-transactable asset without any registration/allow-listing step visible in this transactor.

`Erc20Credit` (lines 79-107) is a bare, unchecked imbalance wrapper with no invariant tying it to the real token balance held by `TransfersCheckingAccount` — it is purely a counter set from the caller-supplied `amount`.

### Impact Explanation
If the ERC20 contract referenced by `asset_id` implements any transfer-time deduction (fee-on-transfer, rebasing/deflationary supply, a malicious contract that always returns `true` but transfers less, or even zero, tokens), then:
1. `withdraw_asset_with_surplus` will over-credit XCM holding relative to what the shared `TransfersCheckingAccount` actually received.
2. Because `TransfersCheckingAccount` is a single shared pooled account for *all* ERC20 asset transfers routed through this transactor (not a per-user or per-message escrow), the inflated credit lets the depositing message draw down balance that in fact belongs to other users' legitimately-deposited tokens of that same contract, or fails outright if no surplus exists (locking/reverting legitimate transfers).
3. In the worst case this is a theft/unbacked-issuance primitive: an attacker deploys a trivial ERC20 contract whose `transfer()` returns `true` while moving `0` (or a reduced amount) of tokens, obtains an inflated `AssetsInHolding` credit for the full requested `amount`, and can then deposit/forward that credit to any beneficiary — draining real balance from the shared checking account that other users' genuine ERC20 transfers left behind, or corrupting the checking account's ledger relative to the token contract's real state.

This matches the report's category: value fabricated on deposit due to trusting the nominal transfer amount instead of the measured balance delta, later causing either irrecoverable freezing or, in the pooled-account variant here, cross-user fund drainage — a materially worse impact than the original report's own "cannot withdraw" (this can enable value creation/theft rather than mere freezing).

### Likelihood Explanation
Reachability requires only an ordinary signed account: deploy any contract via `pallet_revive` (permissionless), then submit a local `pallet_xcm::execute` (or a message routed through this same `AssetTransactors` tuple) referencing that contract's address as an `AccountKey20` asset location — exactly as exercised in the existing `withdraw_and_deposit_erc20s` test. No governance, no privileged role, no compromised keys are needed. The only prerequisite is that `ERC20Transactor` is wired into the runtime's `AssetTransactors`, which is confirmed for `asset-hub-westend` (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`, `AssetTransactors` tuple including `ERC20Transactor`).

I was not able to fully verify, within the available tool budget, the exact definition of `assets_common::ERC20Matcher` (i.e., whether it applies any additional allow-listing or registration check before routing a given `H160` through this transactor) or whether there is a compensating balance check elsewhere in the XCM executor pipeline that would catch the discrepancy before `deposit_asset_with_surplus` executes. This should be verified before treating this as fully confirmed; if `ERC20Matcher` restricts routing to a pre-vetted, non-fee-on-transfer allow-list, the practical likelihood would be substantially lower.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the `TransfersCheckingAccount`'s (or beneficiary's) actual ERC20 balance immediately before and after the `transfer` call and credit/return only the observed delta, rather than trusting the caller-requested `amount` and the boolean return value. Additionally, consider whether a single pooled `TransfersCheckingAccount` shared across unrelated users' asset transfers is an appropriate design at all, since it makes any accounting desync (not just fee-on-transfer tokens) a cross-user fund-drain vector rather than a self-contained loss.

### Proof of Concept
No executable PoC was run. Based on static code reading:
- Deploy a minimal ERC20-like contract via `pallet_revive` whose `transfer(to, value)` moves less than `value` tokens to `to` (or zero) while still returning `true` (a one-line deviation from the standard `_update` balance logic shown in the repo's own `ERC20.sol` fixture).
- Reference that contract's address as an XCM `AccountKey20` asset location (as done in `withdraw_and_deposit_erc20s`), and construct an XCM program that withdraws some `amount` of this asset (routed to `ERC20Transactor::withdraw_asset_with_surplus`) and deposits it to a beneficiary (routed to `deposit_asset_with_surplus`).
- Expected correct behavior: holding credited only with the amount actually received by `TransfersCheckingAccount`.
- Actual code behavior per lines 197-203 and 251-266: holding is credited with the full nominal `amount`, and the subsequent deposit attempts to move that full nominal `amount` out of the checking account regardless of what it actually holds.

Deployment evidence for the reachable path (arbitrary user-deployed ERC20 contract usable as an XCM asset) is already present in-repo: [3](#0-2) . I did not execute a new integration test reproducing the fee-on-transfer discrepancy itself; this remains a static-analysis-derived finding pending dynamic confirmation.
