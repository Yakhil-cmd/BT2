## Analysis

The reported bug class is: **a privileged list-management function removes an entry from a list without checking whether existing balances/holdings still depend on that entry, causing those holdings to become permanently unusable/locked.**

In ocore, the closest reachable analog is the **`asset_attestors`** message, which lets an asset's `definer_address` (an ordinary, unprivileged asset issuer — no special role required) freely rewrite the list of attestors for a `spender_attested` asset at any time, with no check of who currently holds units of that asset or which attestor they rely on.

### Root cause

- `validateAttestorListUpdate` only checks that the author is the asset definer and that the new list is well-formed (`checkAttestorList`), never whether removing an attestor would strand existing holders: [1](#0-0) [2](#0-1) 

- The attestor list used at spend time is always the *latest* one posted before `last_ball_mci`, not a historical/grandfathered snapshot: [3](#0-2) 

- Attestation membership is re-evaluated dynamically against the *current* attestor list (`objAsset.arrAttestorAddresses`) every time a payment is validated: [4](#0-3) [5](#0-4) 

- `validatePayment`/`validatePaymentInputsAndOutputs` reject spends whose owner address is no longer in the (now-updated) attested list, even for coins that were validly received while the address *was* attested: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact

If a definer removes an attestor from a `spender_attested` asset's attestor list, every holder whose only qualifying attestation came from that removed attestor immediately and permanently loses the ability to spend their existing holdings of that asset — the coins become stuck in the DAG with no code path to reclaim them (short of the definer re-adding the attestor or a new attestor re-attesting the same address, which is outside the holder's control). This mirrors the reported bug exactly: a list-removal operation with no accounting for balances tied to the removed entry, resulting in locked funds.

### Title
Removing an attestor from `asset_attestors` list freezes existing holders' funds with no balance check - (File: validation.js)

### Summary
`validateAttestorListUpdate` allows an asset's definer to rewrite the `spender_attested` attestor list for their asset at any time without checking whether current holders of the asset depend on the attestor being removed for their attestation status.

### Finding Description
Spend validation for a `spender_attested` asset checks the *current* attestor list (fetched fresh via `storage.readAsset`'s `addAttestorsIfNecessary`) rather than a snapshot from when the coins were received. `checkAttestorList` ( [2](#0-1) ) validates only address format and sort order — nothing about the impact on holders. Once a definer posts a new `asset_attestors` message dropping an attestor, `filterAttestedAddresses` ( [4](#0-3) ) will no longer count attestations issued by the removed attestor, so `validatePayment`/`validatePaymentInputsAndOutputs` will reject any spend by an address whose attestation depended solely on that attestor ( [6](#0-5)  and [8](#0-7) ).

### Impact Explanation
This is fund freezing for third-party asset holders: coins legitimately received while attested become permanently unspendable after the definer edits the attestor list, with no on-chain recovery path other than the definer voluntarily restoring/adding an attestor. This is a Medium severity issue matching the report's "lockage" impact, reachable purely by posting a standard `asset_attestors` unit — an action open to any asset issuer, not a privileged-role-only function.

### Likelihood Explanation
Any asset definer of a `spender_attested` asset can trigger this unintentionally (e.g., rotating a compromised or deprecated attestor) or intentionally (to grief holders), since there is no safeguard, warning, or check against holders currently relying on that attestor.

### Recommendation
Either (a) grandfather attestation validity as of the time the coins were received/last spent, rather than re-checking against the live attestor list on every subsequent spend, or (b) require `validateAttestorListUpdate` to preserve previously-attested holders' spendability (e.g., by disallowing removal of an attestor if doing so would strand outstanding balances, or by validating against the union of historical attestor lists at time of issue).

### Proof of Concept
1. Definer issues asset `X` with `spender_attested: true`, `attestors: [A1, A2]`.
2. `A1` attests address `H`. `H` receives units of asset `X` via a normal payment — accepted because `H` is attested (validation.js:2115-2122).
3. Definer posts a new `asset_attestors` message for asset `X` with `attestors: [A2]` (dropping `A1`) — accepted by `validateAttestorListUpdate` since it only checks author/format (validation.js:2829-2864).
4. `H` attempts to spend its previously-received asset `X` units. `loadAssetWithListOfAttestedAuthors` → `filterAttestedAddresses` now checks only against `[A2]`; since `H` was never attested by `A2`, the check fails and the payment is rejected with "owner address is not attested" (validation.js:2504-2507), permanently freezing `H`'s asset `X` balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
