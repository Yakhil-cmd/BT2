### Title
Webhook signature verification is scoped by the attacker-controlled `repository.owner.login`, not by the `repository.full_name` actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body. The repository that is actually looked up and mutated by the event handlers (e.g. `PushHandler`) is a *different* field of the same untrusted body: `repository.full_name`. These two fields are never required to agree, so the "organization that authenticated" and the "repository that is written" are not the same binding.

### Finding Description
`verify_signature` computes the org used for verification from the request body itself, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit::GithubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured — a legitimate, documented state, as shown by `webhook_secret: # nil` in `config/secrets.development.shopify.yml`: [3](#0-2) 

Meanwhile, the event handler that actually performs the write does not use `repository.owner.login` at all — it uses `repository.full_name`, matched against the `Repository` table regardless of which organization's secret (or lack thereof) was used to pass `verify_signature`: [4](#0-3) [5](#0-4) [6](#0-5) 

Equality that should hold but doesn't: `organization authenticated by verify_signature (repository.owner.login)` == `organization owning the repository actually written (repository.full_name)`. Because HMAC-SHA1 covers the whole raw body, an attacker cannot simply alter `full_name` while keeping a valid signature for a *secured* org — but this constraint disappears entirely for any org in `Shipit.github_configs` that has no `webhook_secret` set, since `verify_webhook_signature` returns `true` unconditionally for that org, without inspecting the body or signature header at all. An attacker who knows (or brute-forces) the login of any such weakly-configured org can submit an arbitrary JSON body with `repository.owner.login` set to that org and `repository.full_name` set to any other tracked repository (belonging to a fully-secured org), and the request passes `verify_signature` untouched.

### Impact Explanation
A forged `push` event reaching `PushHandler` resolves the target `Stack` purely from `repository.full_name` and calls `stack.sync_github(expected_head_sha: params.after)`, updating the tracked HEAD commit for that stack: [5](#0-4)  On stacks configured with continuous/auto deployment, advancing the HEAD via a forged sync can trigger an unauthorized deploy of attacker-influenced commit state, satisfying the "unauthorized deploy" High/Critical impact criterion, without the attacker ever possessing the secret of the targeted (secured) organization.

### Likelihood Explanation
Requires only that at least one organization entry in the host's `Shipit.github_configs` be onboarded without a `webhook_secret` (a state the codebase explicitly supports and ships as an example in `config/secrets.development.shopify.yml`), and that the attacker know that org's GitHub login — a low bar, since org logins are public. No GitHub App private key, `ApiClient` token, or Shipit session is required; the webhook endpoint is unauthenticated by design.

### Recommendation
Bind the signature-verification organization to the same repository/organization the handlers will act on: derive the org used to select the webhook secret from `repository.full_name` (or require they match), and reject payloads where `repository.owner.login` and `repository.full_name`'s owner disagree. Additionally, do not allow `verify_webhook_signature` to silently return `true` for organizations with a blank `webhook_secret`; either require every configured organization to define a secret or explicitly reject events for repositories owned by unsecured organizations.

### Proof of Concept
1. Host configures two organizations in `Shipit.github_configs`: `weak-org` (no `webhook_secret`) and `secure-org` (has `webhook_secret`), each with at least one repository tracked as a `Stack`.
2. Attacker (no credentials) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "weak-org" }, "full_name": "secure-org/target-repo" }
}
```
No `X-Hub-Signature` needs to be valid.
3. `verify_signature` calls `Shipit.github(organization: "weak-org")`, whose `verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank: [7](#0-6) 
4. `PushHandler#process` resolves `Repository.from_github_repo_name("secure-org/target-repo")` and calls `sync_github` on its stacks, advancing HEAD/triggering sync for a repository owned by the fully-secured `secure-org`, despite the attacker never possessing `secure-org`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
