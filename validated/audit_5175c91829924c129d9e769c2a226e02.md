### Title
L1 Bitcoin Lockup Outpoints Are Deduplicated Only Within a Single Call, Not Globally — Enabling Reuse of the Same BTC Lockup to Credit Sats Multiple Times ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`verify-l1-lockups` / `validate-l1-lockup` in `pox-5.clar` verify that a BTC lockup output belongs to the correct timelock script and add its `amount` to a running `sum` of credited sats. Duplicate protection (`seen-outpoints`) is only tracked in the local fold accumulator that exists for the lifetime of a single contract call, and is never checked against, or persisted into, any contract-level map that records outpoints already credited to a staker/bond in prior transactions.

### Finding Description
`verify-l1-lockups` [1](#0-0)  initializes `seen-outpoints: (list)` fresh on every invocation and folds over `validate-l1-lockup` [2](#0-1) , which only rejects an outpoint if it already appears in `seen-outpoints` from *within the same call* (`(asserts! (is-none (index-of? seen-outpoints outpoint)) ERR_DUPLICATE_LOCKUP_OUTPOINT)` at line 2086). There is no map such as `used-lockup-outpoints` that is written to and checked across separate transactions.

Because the verification only proves that a given Bitcoin UTXO was locked to the correct timelock script (ownership/format), and never marks that UTXO as "already consumed" persistently, a staker (or anyone submitting the calldata on their behalf) can present the exact same BTC block header, merkle proof, and output index in a subsequent, separate call to whatever public function invokes `verify-l1-lockups` (e.g., a bond-registration flow, based on the `btcLockup` calldata parameter observed in the test suite [3](#0-2) ), and receive `sum` (sats credit) again without ever locking additional BTC. This breaks the equality that "sats credited == sats actually newly locked on Bitcoin (once)" and results in double-counting sats-based shares/stake.

### Impact Explanation
Double-counting `amount-sats` from a single Bitcoin lockup lets a staker register far more effective "locked sats" than they actually locked, letting them capture a disproportionate share of bond rewards (`get-signer-shares-staked-for-cycle` / `total-shares-staked-for-cycle`, used throughout `calculate-bond-rewards` [4](#0-3) ) relative to honest stakers, diluting/stealing reward pool funds that were meant for stakers who genuinely locked BTC. This is a double-counting-of-commitment issue affecting sBTC reward distribution — classified High/Critical per the rules ("double-counting a commitment or reward").

### Likelihood Explanation
Exploitability depends on whether the calling public function(s) that invoke `verify-l1-lockups` can be re-invoked by the same staker/bond with previously-used lockup calldata (e.g., a second `register-for-bond` or a bond-update call reusing the same BTC output proof). The Clarity code itself provides no persistent protection against this regardless of how the outer function is gated, so the safety of the system currently relies entirely on external call-site restrictions (e.g., allowlist single-use semantics) that are not visible/enforced within this verification routine itself. Given the contract's own documented "once per outpoint" comment (line 2028-2030) implies the intent was global uniqueness, but the implementation only achieves per-call uniqueness, this is a genuine root-cause defect regardless of caller-side mitigations.

### Recommendation
Persist consumed outpoints in a contract-level map (e.g. `(define-map used-lockup-outpoints { txid: (buff 32), output-index: uint } bool)`), and check/insert into that map inside `validate-l1-lockup` in addition to the local `seen-outpoints` list, so that a given BTC lockup output can never be credited more than once across the lifetime of the contract, not just within one call.

### Proof of Concept
1. Staker locks BTC to the timelock script derived from `construct-lockup-output-script` for a given bond, producing a valid outpoint `O` with `amount = X` sats.
2. Staker calls the bond-registration entrypoint (the caller of `verify-l1-lockups`) providing `O`'s block header/merkle proof; `validate-l1-lockup` succeeds, `sum = X` is credited as `amount-sats`, and shares are registered.
3. Staker calls the entrypoint again with the exact same `O` (same header/merkle proof/output-index). Because `seen-outpoints` is reinitialized to `(list)` for this new call (line 2013), the duplicate check at line 2086 does not fire, and `X` sats are credited again — with no new BTC ever being locked.
4. Total credited sats for the staker across the two registrations is `2X`, though only `X` sats were ever locked, corrupting `total-shares-staked-for-cycle` and the resulting reward share calculations in `calculate-bond-rewards`.

(define-private (validate-l1-lockup
        (lockup {
            height: uint,
            tx: (buff 100000),
            output-index: uint,
            header: (buff 80),
            leaf-hashes: (list 14 (buff 32)),
            tx-count: uint,
            tx-index: uint,
            amount: uint,
            unlock-burn-height: uint,
        })
        (accumulator-res (response {
            staker: principal,
            minimum-unlock-height: uint,
            staker-unlock-bytes: (buff 683),
            early-unlock-bytes: (buff 683),
            sum: uint,
            seen-outpoints: (list 10 {
                txid: (buff 32),
                output-index: uint,
            }),
        }
            uint
        ))
    )
    (let (
            (accumulator (try! accumulator-res))
            (block (try! (parse-block-header (get header lockup))))
            (unlock-burn-height (get unlock-burn-height lockup))
            (expected-script-hash (try! (construct-lockup-output-script (get staker accumulator)
                unlock-burn-height (get staker-unlock-bytes accumulator)
                (get early-unlock-bytes accumulator)
            )))
            (output (try! (get-bitcoin-tx-output? (get tx lockup) (get output-index lockup))))
            (reversed-txid (get txid output))
            (txid (reverse-buff32 reversed-txid))
            (outpoint {
                txid: txid,
                output-index: (get output-index lockup),
            })
            (seen-outpoints (get seen-outpoints accumulator))
        )
        (asserts! (>= unlock-burn-height (get minimum-unlock-height accumulator))
            ERR_INVALID_UNLOCK_HEIGHT
        )
        (asserts! (< unlock-burn-height BITCOIN_LOCKTIME_THRESHOLD)
            ERR_INVALID_UNLOCK_HEIGHT
        )
        (asserts! (is-eq (get script output) expected-script-hash)
            ERR_INVALID_LOCKUP_SCRIPT
        )
        (asserts! (is-eq (get amount output) (get amount lockup))
            ERR_INVALID_LOCKUP_AMOUNT
        )
        (asserts! (is-none (index-of? seen-outpoints outpoint))
            ERR_DUPLICATE_LOCKUP_OUTPOINT
        )
        (asserts! (verify-block-header (get header lockup) (get height lockup))
            ERR_INVALID_BTC_HEADER
        )
        ;; verify merkle proof
        (asserts!
            (or
                (is-eq (get merkle-root block) txid) ;; true, if the transaction is the only transaction
                (verify-merkle-proof reversed-txid
                    (reverse-buff32 (get merkle-root block))
                    (get tx-index lockup) (get tx-count lockup)
                    (get leaf-hashes lockup)
                )
            )
            ERR_INVALID_MERKLE_PROOF
        )
        (ok {
            staker: (get staker accumulator),
            minimum-unlock-height: (get minimum-unlock-height accumulator),
            staker-unlock-bytes: (get staker-unlock-bytes accumulator),
            early-unlock-bytes: (get early-unlock-bytes accumulator),
            sum: (+ (get sum accumulator) (get amount output)),
            seen-outpoints: (unwrap-panic (as-max-len? (append seen-outpoints outpoint) u10)),
        })
    )
)

(define-private (calculate-bond-rewards
        (bond-index uint)
        (accumulator-res (response {
            ;; Used to ensure that the list of bonds are sorted correctly
            last-bond-stx-value-ratio: (optional uint),
            ;; Used as a tie-breaker in the case of bonds with the same
            ;; stx-value-ratio
            last-bond-index: (optional uint),
            ;; How much rewards are available to be distributed
            available-rewards: uint,
            calculation-height: uint,
            reward-cycle: uint,
        }
            uint
        ))
    )
    (let (
            (accumulator (try! accumulator-res))
            (bond (unwrap! (map-get? protocol-bonds bond-index) ERR_BOND_NOT_FOUND))
            (reward-cycle (get reward-cycle accumulator))
            (total-sats (get-total-shares-staked-for-cycle reward-cycle (some bond-index)))
            (available-rewards (get available-rewards accumulator))
            ;; How much sBTC the bond is supposed to earn per calculation,
            ;; which is (totalSats * apy) / 50
            (target-yield (/ (/ (* total-sats (get target-rate bond)) u10000) u50))
            ;; If there is enough to cover the target yield, use that. Otherwise,
            ;; this bond gets the remaining rewards.
            (earned (if (>= available-rewards target-yield)
                target-yield
                available-rewards
            ))
            (stx-value-ratio (get stx-value-ratio bond))
            (current-rewards-per-token (get-rewards-per-token-for-cycle reward-cycle (some bond-index)))
            ;; Prevent divide-by-zero
            (accrued-rewards-per-sat (if (is-eq total-sats u0)
                u0
                (/ (* earned PRECISION) total-sats)
            ))
            (calculation-height (get calculation-height accumulator))
            (bond-start-height (bond-period-to-burn-height bond-index))
            (bond-end-height (bond-period-to-burn-height (+ bond-index u6)))
        )
        ;; Verify that we're paying out bonds in the right order
        (match (get last-bond-stx-value-ratio accumulator)
            last-ratio
            (asserts!
                ;; In a tie-breaker, we still want deterministic results.
                ;; Thus, enforce that the earlier bond period comes first
                (if (is-eq stx-value-ratio last-ratio)
                    ;; Note that < prevents the same bond period from
                    ;; being included twice
                    (> bond-index
                        (unwrap-panic (get last-bond-index accumulator))
                    )
                    (<= stx-value-ratio last-ratio)
                )
                ERR_INVALID_BOND_PERIOD_ORDERING
            )
            ;; When `none`, this is the first bond we're processing
            true
        )

        (map-set rewards-per-token-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: (some bond-index),
        }
            (+ current-rewards-per-token accrued-rewards-per-sat)
        )

        (asserts!
            (and
                (> calculation-height bond-start-height)
                (<= calculation-height bond-end-height)
            )
            ERR_BOND_NOT_ACTIVE
        )

        (print {
            topic: "bond-distribution",
            bond-index: bond-index,
            target-yield: target-yield,
            bond-rewards: earned,
            bond-staked-sats: total-sats,
            accrued-rewards-per-sat: accrued-rewards-per-sat,
            cumulative-rewards-per-sat: (+ current-rewards-per-token accrued-rewards-per-sat),
        })

        (ok {
            last-bond-stx-value-ratio: (some stx-value-ratio),
            last-bond-index: (some bond-index),
            available-rewards: (- available-rewards earned),
            calculation-height: calculation-height,
            reward-cycle: reward-cycle,
        })
    )
)
