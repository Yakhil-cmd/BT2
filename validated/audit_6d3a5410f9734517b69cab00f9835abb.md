## Analysis

The reported bug class is: an owner-controlled configuration (`setVestingConfig`) can be changed at any time and is re-evaluated *retroactively* against already-accrued/vested state, causing previously unlocked funds to become locked again because validity is checked against the *current* config rather than a snapshot taken when the funds became eligible.

The closest reachable analog in `ocore` is the `spender_attested` asset mechanism, where the asset definer (an "asset issuer", one of the explicitly allowed actors) can update the attestor list for an asset at any time via an `asset_attestors` message, and every subsequent spend of *already-held* asset outputs is checked against the *latest* attestor list rather than the list that was valid when the holder received the funds.

### Title
Asset holders' already-received `spender_attested` tokens can be permanently frozen when the definer updates the attestor list - ([File: validation.js])

### Summary
For assets with `spender_attested: true`, the definer can publish a new `asset_attestors` message at any time to change which addresses are considered attested, via `validateAttestorListUpdate` [1](#0-0)  and `checkAttestorList` [2](#0-1) . Nothing prevents the definer from removing an attestor (or an attested address) that already legitimately holds unspent asset outputs. When such a holder later tries to spend or transfer the tokens they already own, `storage.readAsset` recomputes the attestor list using only the *most recent* `asset_attestors` unit before `last_ball_mci` [3](#0-2) , and `validatePaymentInputsAndOutputs` rejects the spend because the owner address is no longer in `objAsset.arrAttestedAddresses` [4](#0-3) . The same check applies for private fixed-denomination inputs [5](#0-4)  and for output addresses on payment/transfer messages [6](#0-5) .

### Finding Description
Attestation status is not a per-output/per-unit property fixed at the time the output was created; it is re-derived every time from the asset's *current* attestor list. `readAsset`'s `addAttestorsIfNecessary` always looks up the single latest `asset_attestors` unit stable before `last_ball_mci` and uses it as the authoritative list for all attestation checks, regardless of what the list looked like when a given output was produced [7](#0-6) . `validateAttestorListUpdate` places no restriction on this update besides requiring the definer's signature and a well-formed, sorted list [1](#0-0) ; it does not prevent removing addresses/attestors that already back existing unspent balances. Consequently, exactly like the reported `setVestingConfig` issue where a config update is applied retroactively to already-vested amounts, an `asset_attestors` update is applied retroactively to already-issued/transferred asset outputs, converting previously spendable balances into permanently frozen ones (`"owner address is not attested"` / `"some output addresses are not attested"`) [4](#0-3) [8](#0-7) .

### Impact Explanation
Holders who legitimately received a `spender_attested` asset while properly attested can have their existing, unspent balance locked with no path to recovery if the definer (accidentally or maliciously) republishes an attestor list that drops them. Since assets of this kind are commonly used to gate participation (e.g., KYC'd tokens), this results in a genuine freezing of funds for token holders that is entirely under the control of a single privileged party (the asset definer), and the funds cannot be spent by their rightful, previously-attested owner — this is a fund-freezing impact of Medium severity, directly analogous to the reported vesting issue.

### Likelihood Explanation
Any asset defined with `spender_attested: true` (a normal, supported asset feature) is exposed. The definer only needs to publish a single `asset_attestors` unit to change/rotate the attestor set, which is a routine, expected administrative action (e.g., replacing a compromised attestor, or normal attestor rotation) — there is no requirement to consider existing balances, so the freeze can happen unintentionally during ordinary asset administration.

### Recommendation
Attestation checks for spending existing outputs should be based on the attestor list (and attestation) that was valid when the output was created/received, not the list current at spend time — analogous to snapshotting a vesting schedule instead of re-evaluating it against the newest config. Alternatively, require `asset_attestors` updates to only add attestors/addresses (never revoke ones backing existing balances), or provide an explicit unlock/migration mechanism so revocation cannot retroactively strand already-held funds.

### Proof of Concept
1. Asset issuer `D` defines asset `A` with `spender_attested: true` and initial attestor list `[X1]`.
2. Attestor `X1` attests holder address `H`.
3. `H` receives (or is issued) asset `A` output(s) while properly attested — accepted per `validatePayment`'s attestation checks [9](#0-8) .
4. Definer `D` posts a new `asset_attestors` message removing `X1` from the attestor list; `validateAttestorListUpdate` accepts it since it only checks the definer's signature and list well-formedness [1](#0-0) .
5. `H` later tries to spend their existing (previously valid) output of asset `A`. `storage.readAsset`/`addAttestorsIfNecessary` resolves the *new* (empty of `H`) attestor set [3](#0-2) , and `validatePaymentInputsAndOutputs` rejects the spend with `"owner address is not attested"` [4](#0-3) , even though the tokens were validly received while `H` was attested — `H`'s funds are now permanently frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
