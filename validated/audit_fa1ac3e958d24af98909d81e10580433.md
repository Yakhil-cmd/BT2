### Title
Shared-worktree sibling agent can move/invalidate another session's git baseline, silently disabling or blinding its Stop-hook security review - (File: `plugins/security-guidance/hooks/security_reminder_hook.py` / `plugins/security-guidance/hooks/diffstate.py`)

### Summary
The security-guidance plugin's Stop hook computes "what Claude changed this turn" by diffing the working tree against a `baseline_sha`/`head_at_capture` pair stored in per-session JSON state, and treats HEAD's movement between these two SHAs as evidence of "this session's own commits." In a shared-worktree multi-agent deployment, an unprivileged sibling agent operating in the *same* worktree can commit (or otherwise advance HEAD) independently, silently corrupting another session's baseline assumptions. This is the same trust-boundary error as the reported Vault.sol bug: an ordinary, legitimate action by one unprivileged actor mutates a piece of *shared* state (here, git HEAD/refs, there, `totalDebt`) that another actor's accounting/security logic implicitly assumed was exclusively under its own control, breaking that other actor's functionality.

### Finding Description
The Stop hook is documented to rely on `baseline_sha` (a `git stash create` snapshot) and `head_at_capture` (the HEAD SHA at `UserPromptSubmit` time) to isolate "this turn's" changes: [1](#0-0) 

`compute_v2_review_set` treats any HEAD advance between `head_at_capture` and the current HEAD as evidence that *this session* made commits, and folds the newly-reachable files into the review set / diff base: [2](#0-1) 

This logic has no way to distinguish "HEAD advanced because this session committed" from "HEAD advanced because a sibling agent sharing the same worktree committed." The code's own author comments acknowledge exactly this gap and ship a manual opt-out rather than a fix: [3](#0-2) 

Concretely, once a sibling agent commits in the shared worktree:
- The next `UserPromptSubmit` for the *other* session calls `capture_git_baseline`, which runs `git stash create` at the now-sibling-advanced HEAD. This makes the sibling's just-committed (possibly vulnerable, possibly not security-reviewed) code part of the new `baseline_sha`/`head_at_capture` for the victim session, permanently excluding it from all future `changed_since`/diff computations for that session: [4](#0-3) [5](#0-4) 
- If the sibling's commit instead causes `head_at_capture` to become unreachable (e.g. rebased/pruned), `_is_ancestor` fails, and the diff logic falls back or fails; the `get_git_diff` diff comes back `None` and the Stop hook exits without ever performing the LLM security review for that turn: [6](#0-5) [7](#0-6) 

In both cases, the victim session never asked for or authorized the sibling's write to the shared git ref namespace, yet that write silently degrades or disables the victim's own security-review invariant — mirroring how, in the Vault.sol bug, an unprivileged user's legitimate `repayDebt()` call against shared `totalDebt` broke borrowing for every other, uninvolved borrower.

### Impact Explanation
Impact is a availability/integrity break of a security control rather than a financial loss (there is no monetary vault here), but the mechanism is the same class: an unprivileged co-tenant's normal action against shared mutable state (git refs in a shared worktree) causes another party's accounting/gating logic to fail closed (DOS: review silently skipped) or fail open (bypass: sibling's and/or the victim's subsequently-baselined code is never diffed/reviewed by the Stop hook), undermining the plugin's core "review everything Claude changes" guarantee for any session that doesn't own the worktree exclusively.

### Likelihood Explanation
This requires only the documented, supported deployment mode of "multi-agent / shared-worktree deployments" explicitly called out in the code comment, and any sibling agent making an ordinary `git commit` — no privilege escalation, credential theft, or malicious intent is needed, only concurrent legitimate use of a shared worktree, which the codebase itself anticipates and only partially mitigates via an opt-out env var (`ENABLE_STOP_REVIEW=0`) rather than a structural fix.

### Recommendation
Scope `baseline_sha`/`head_at_capture` (and the HEAD-advance heuristic in `compute_v2_review_set`) to a ref/commit range that is provably attributable to the current session (e.g., per-session refs, or require worktree isolation per agent as already done elsewhere for other git safety issues) rather than trusting shared repository HEAD state; treat HEAD movement not caused by the session's own tracked commits as "unknown/foreign" and force a conservative fallback (re-review broadly, or explicitly warn) instead of silently absorbing it into the baseline.

### Proof of Concept
1. Configure two Claude Code sessions/agents to operate in the same shared git worktree (a supported mode per the code comment).
2. Session A's Stop hook captures `head_at_capture = H0`.
3. Session B (sibling) makes an ordinary `git commit` in the shared worktree, advancing HEAD to `H1` with vulnerable code that was never reviewed by commit-review (e.g. commit-review disabled or race-lost).
4. Session A's next `UserPromptSubmit` runs `capture_git_baseline`, which does `git stash create` at the now-current HEAD (`H1`), producing a new `baseline_sha` that already contains B's vulnerable commit as "pre-existing."
5. All subsequent Stop-hook diffs for Session A are computed against this baseline, so B's vulnerable code is never present in any diff Session A's Stop hook reviews — the review is permanently bypassed for that code, without Session A's user or B's operator taking any deliberate misuse action.

## How the git baseline works

On each UserPromptSubmit, the plugin runs `git stash create` to get a SHA representing
the current working tree state (HEAD + any uncommitted changes). This SHA is saved to
the session state file. When the Stop hook fires, it runs `git diff <baseline_sha>` to
get only the changes made since that snapshot. After analysis, the baseline is updated
so the next Stop hook iteration only sees new changes.

This means:
- Only code Claude actually changed is reviewed (not pre-existing code)
- Mid-session commits are handled correctly (diff is against the snapshot, not HEAD)
- Each turn only reviews new changes (baseline updates after each stop hook)

    preserved = {"value": False}

def capture_git_baseline(cwd):
    """
    Capture a git ref representing the current working tree state.
    Uses `git stash create` which creates a commit object for the current state
    (HEAD + uncommitted changes) without modifying the stash list or working tree.
    Falls back to HEAD if the working tree is clean.
    Returns the SHA string, or None if not in a git repo or if the repo has no commits.

    NOTE: `git stash create` does NOT capture untracked files. UPS pairs this
    SHA with a `_list_untracked()` snapshot stored as `untracked_at_baseline`,
    and `compute_v2_review_set` subtracts that set so pre-existing untracked
    files are not reviewed as Claude-authored.
    """
    try:
        # Check if HEAD exists (i.e., repo has at least one commit)
        head_check = subprocess.run(
            [*GIT_CMD, "rev-parse", "HEAD"],
            cwd=cwd, capture_output=True, text=True, timeout=5
        )
        if head_check.returncode != 0:
            # No commits yet — skip review rather than creating commits in the user's repo
            debug_log("No commits in repo, skipping baseline capture")
            return None

        result = subprocess.run(
            [*GIT_CMD, "stash", "create"],
            cwd=cwd, capture_output=True, text=True, timeout=15
        )
        sha = result.stdout.strip()
        if sha:
            return sha

        # Working tree is clean — stash create returns empty. Use HEAD.
        result = subprocess.run(
            [*GIT_CMD, "rev-parse", "HEAD"],
            cwd=cwd, capture_output=True, text=True, timeout=5
        )
        sha = result.stdout.strip()
        return sha if sha else None

def _is_ancestor(cwd, maybe_ancestor, descendant):
    """True if `maybe_ancestor` is reachable from `descendant` (i.e. HEAD
    moved forward via commit/merge, not sideways via checkout)."""
    try:
        result = subprocess.run(
            [*GIT_CMD, "merge-base", "--is-ancestor", maybe_ancestor, descendant],
            cwd=cwd, capture_output=True, text=True, timeout=5,
        )
        return result.returncode == 0
    except (subprocess.TimeoutExpired, FileNotFoundError, OSError):
        return False
