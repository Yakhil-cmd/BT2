## Analysis

CVE‑2022‑4095 is a use‑after‑free in a kernel command queue: an object is unlinked from a list/cache and then dereferenced again through a stale reference held elsewhere. The closest reachable analog in `ocore--008` is in the AA (Autonomous Agent) "dry‑run" execution path, where speculative unit objects are inserted into the same global, shared in‑memory caches used by consensus code, and are later removed ("freed") by a cleanup routine that does not guarantee all outstanding references to those objects have been dropped first.

### Title
Stale references to "freed" speculative AA response units in shared consensus caches during dry‑run trigger execution — ([File: aa_composer.js])

### Summary
`aa_composer.dryRunPrimaryAATrigger()` and the `revert()` path inside `handleTrigger()` execute AA logic against the **production** global caches (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocStableUnits`) rather than an isolated sandbox, then attempt to "undo" the effect via `revertResponsesInCaches()`, which calls `storage.forgetUnit()` for each speculative response unit. [1](#0-0) [2](#0-1) 

### Finding Description
When a unit containing an AA trigger is posted and `conf.bDryRunNewTriggers` is enabled, `network.js` runs `aa_composer.dryRunPrimaryAATrigger()` for every triggered AA address *before* the real unit is saved: [3](#0-2) 

Inside `handleTrigger()`, successful AA responses are built and persisted through the normal `writer.saveJoint()` path even during a dry run, which mutates the same global caches that main‑chain/consensus code reads: [4](#0-3) 

If any part of a multi‑AA call chain fails, `revert()` calls `revertResponsesInCaches(arrResponses)`, which walks `arrResponseUnits` and calls `storage.forgetUnit()` on each one, then fixes `is_free` only using the **first** unit's `parent_units`: [1](#0-0) 

`storage.forgetUnit()` removes the unit's properties object from `assocUnstableUnits`/`assocStableUnits`/`assocCachedUnits`, and tries to unlink the object from `assocBestChildren[parent_unit]` by reference: [5](#0-4) 

`assocBestChildren` and `assocUnstableUnits` are shared, global, mutable structures that are also read (and their entries copied/concatenated into local snapshot arrays) by consensus/stability code such as `readBestChildrenProps()`, `createListOfBestChildrenIncludedByLaterUnits()`, and `determineIfStableInLaterUnits()`: [6](#0-5) [7](#0-6) 

Because Node.js interleaves callbacks only at I/O boundaries, and both the dry‑run path and the real validation/main‑chain path perform many sequential `db.query()` calls (async boundaries), an unrelated unit's validation/stability computation can capture a snapshot that includes the speculative dry‑run unit object while it is still "live" in the caches. If the dry run subsequently reverts (via `forgetUnit`) before that concurrent computation finishes consuming its snapshot, the concurrent code continues operating on a unit props object that has already been unlinked/removed from the authoritative caches — the same class of defect as CVE‑2022‑4095's "unlinked but still referenced/used" object, just realized as stale/incoherent state instead of memory corruption. In addition, `revertResponsesInCaches()` only recomputes `is_free` for the **first** response unit's parents, not every response unit's parents in the chain, so `is_free` flags for intermediate parents can be left incorrect after a revert, independent of any race.

### Impact Explanation
If a concurrent consensus computation (best-parent selection, witnessed-level calculation, or `determineIfStableInLaterUnits`) is contaminated by a speculative unit that is later "freed" from the caches, or operates on `assocBestChildren`/`is_free` state left inconsistent by an incomplete revert, different nodes (or the same node at different times) can compute different results for the same query — i.e., disagreement on unit validity/stability. This is the "node disagreement on validity or stability" impact category explicitly listed as in‑scope, and could ultimately affect finalization decisions for real, non‑speculative units.

### Likelihood Explanation
Reaching this code requires only posting an ordinary unit that triggers an AA (fully within an unprivileged unit poster's capability) on a node running with `conf.bDryRunNewTriggers` enabled. The race window depends on interleaving of async callbacks with other concurrently validated units/AA activity, which is plausible on a busy node but not guaranteed on every run — hence a real but timing‑dependent likelihood, and the `is_free`/parent-chain bug in `revertResponsesInCaches` is deterministic for any reverted multi‑hop AA chain, not merely a race.

### Recommendation
- Do not mutate the production `storage.assocUnstableUnits` / `storage.assocBestChildren` / `storage.assocStableUnits` caches during speculative/dry‑run AA execution; use an isolated overlay/shadow cache for `dryRunPrimaryAATrigger()` and `estimatePrimaryAATrigger()` that consensus code never reads.
- If sharing the caches is unavoidable, hold a global write‑style lock for the entire dry‑run-plus-revert sequence so no other unit's validation/main‑chain code can observe or snapshot the speculative state.
- Fix `revertResponsesInCaches()` to collect and fix `is_free` for the parents of **every** unit in `arrResponseUnits`, not just the first one.

### Proof of Concept
1. Enable `conf.bDryRunNewTriggers` on a node.
2. Define a chain of AAs A → B → C where C is crafted to bounce (e.g., insufficient balance) so that the primary trigger's `revert()` path is exercised, causing `revertResponsesInCaches()` to call `storage.forgetUnit()` on multiple already‑cached response units.
3. Concurrently (e.g. by flooding the node with unrelated valid units around the same time) trigger main‑chain/stability computations (`main_chain.determineIfStableInLaterUnits`, `readBestChildrenProps`) that read `storage.assocBestChildren`/`assocUnstableUnits` while the dry run's speculative units for A/B are still present.
4. Observe (via added instrumentation/tracing, or by comparing two nodes under different scheduling) that the concurrent computation's snapshot includes units later removed by `forgetUnit()`, and/or that `is_free` on intermediate parent units of the reverted chain remains stale after the revert, since only `objFirstUnit.parent_units` is passed to `fixIsFreeAfterForgettingUnit()`.

	// remove the rolled back units from caches and correct is_free of their parents if necessary
	console.log('will revert responses ' + JSON.stringify(arrResponses, null, '\t'));
	var arrResponseUnits = [];

	if (arrResponseUnits.length > 0) {
		var first_unit = arrResponseUnits[0];

		var parent_units = objFirstUnit.parent_units;
		arrResponseUnits.forEach(storage.forgetUnit);
		storage.fixIsFreeAfterForgettingUnit(parent_units);
	}
}
