`NonTransfer` proxy falsely declares itself a superset of `Auction`, letting it self-grant a proxy that bypasses its own `Registrar::swap` denial - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
On both the Westend and Rococo relay-chain runtimes, `ProxyType::is_superset` declares `(ProxyType::NonTransfer, _) => true` — i.e. `NonTransfer` claims to be a superset of *every* other proxy type, including `Auction`. But `NonTransfer`'s `filter` explicitly admits only three narrow `Registrar` call variants (`register`, `deregister`, `reserve`) with an explicit comment "Specifically omitting Registrar `swap`", while `Auction`'s filter admits the *entire* `Registrar` pallet (`RuntimeCall::Registrar(..)`, unrestricted), including `swap`. This is exactly the same class of bug already found and fixed on Asset Hub Westend for `NonTransfer`/`Governance` (see `prdoc/pr_12769.prdoc` and the regression test `non_transfer_proxy_is_not_a_superset_of_governance` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`), but the equivalent `NonTransfer`/`Auction` pair on the relay chains was left unfixed.

### Finding Description
`pallet_proxy::do_proxy` authorizes nested `add_proxy`/`remove_proxy` calls purely via `ProxyType::is_superset`, not by re-deriving admitted-call equivalence: [1](#0-0) 

In `polkadot/runtime/westend/src/lib.rs`:
- `NonTransfer` filter admits only `Registrar::register`, `Registrar::deregister`, `Registrar::reserve`, explicitly *not* `swap`: [2](#0-1) 
- `Auction` filter admits the whole `Registrar` pallet unrestricted, including `swap`: [3](#0-2) 
- `is_superset` nonetheless claims `NonTransfer` is a superset of *all* other types, including `Auction`: [4](#0-3) 

The identical pattern exists in `polkadot/runtime/rococo/src/lib.rs`: [5](#0-4) [6](#0-5) 

This is structurally identical to the already-fixed bug documented in `prdoc/pr_12769.prdoc`: [7](#0-6) 
and its regression test/comment explaining the invariant that must hold across the whole lattice: [8](#0-7) 

**Attack path (relay chain, real signed extrinsics, no privileged role required):**
1. Account `A` (attacker) is given a `NonTransfer` proxy by account `R` (`Proxy::add_proxy(origin=R, delegate=A, proxy_type=NonTransfer)`), a routine delegation.
2. `A` dispatches `Proxy::proxy(origin=A, real=R, force_proxy_type=None, call=Proxy::add_proxy{delegate=A2, proxy_type=Auction, delay=0})`. In `do_proxy`, the nested-call filter checks `def.proxy_type.is_superset(&Auction)` → `NonTransfer.is_superset(&Auction)` → `true` (per the `(NonTransfer, _) => true` arm), so the `add_proxy` call is allowed to go through as `R`.
3. `R` now has an `Auction` proxy delegate `A2` (which `A` controls, e.g. by setting `A2 == A` or a colluding account).
4. `A`/`A2` then dispatches `Proxy::proxy(origin=A2, real=R, ..., call=Registrar::swap{..})`. `Auction`'s filter admits unrestricted `Registrar::swap`, so this succeeds — even though `A`'s original `NonTransfer` proxy filter explicitly denies `Registrar::swap`.

The attacker never held the `Auction` proxy type directly and never had `swap` rights; the escalation happened purely because `is_superset` returned `true` for a pair where `filter` sets are not actually nested — mirroring the Capgo CVE's "empty limits" pattern of minting a broader-scoped credential from a narrower one without validating the broader credential's actual permission set against the caller's.

### Impact Explanation
`paras_registrar::Call::swap` swaps a parachain/parathread slot/lease and associated deposits between two paras — a `NonTransfer`-restricted delegate is explicitly meant *not* to be able to invoke it (per the inline comment), yet through this escalation path it can. This grants unauthorized dispatch of a privileged registrar operation to an account that was only ever trusted with a narrower, non-transfer-adjacent scope, which can disrupt slot ownership/lease state on a live relay chain. This matches the report's "unauthorized dispatch"/scope-escalation class.

### Likelihood Explanation
Requires only two ordinary signed extrinsics through the standard, publicly-reachable `pallet_proxy` interface (`add_proxy` delegation from a real account, then `proxy`-wrapped `add_proxy`/`proxy` calls) — no governance, no stolen keys, no privileged role. The only precondition is that the victim (real) account grants a `NonTransfer` proxy to the attacker, which is a normal, common delegation pattern (e.g. for automation/bots) that assumes `NonTransfer` cannot escalate to `Auction`-only actions like `swap`.

### Recommendation
Apply the same fix pattern used in `prdoc/pr_12769.prdoc` for Asset Hub Westend: remove the blanket `(ProxyType::NonTransfer, _) => true` catch-all in `polkadot/runtime/westend/src/lib.rs` and `polkadot/runtime/rococo/src/lib.rs`, and instead enumerate only the proxy types whose `filter` sets are genuinely subsets of `NonTransfer`'s filter (excluding `Auction`, or add `RuntimeCall::Registrar(paras_registrar::Call::swap{..})` explicitly to `NonTransfer`'s filter if intentional). Add a lattice-consistency test analogous to `proxy_type_superset_relation_matches_call_filters` for both relay-chain runtimes to prevent regressions.

### Proof of Concept
Not executed against a live network. The escalation logic was traced statically through `pallet_proxy::do_proxy`'s nested-origin filter (`substrate/frame/proxy/src/lib.rs:994-1023`) combined with the concrete `filter`/`is_superset` implementations in `polkadot/runtime/westend/src/lib.rs:950-1031` and `polkadot/runtime/rococo/src/lib.rs:918-1009`, which is the same mechanism already proven exploitable and fixed for the `NonTransfer`/`Governance` pair (`prdoc/pr_12769.prdoc`, regression tests in `asset-hub-westend/tests/tests.rs:2486-2559`). No local Rust/FRAME integration test was run in this session to execute the exact `NonTransfer`→`Auction`→`Registrar::swap` sequence; this should be validated with a `pallet_proxy` mock/integration test using the Westend/Rococo `ProxyType` enum before treating this as fully confirmed, since I only performed static code/logic tracing, not runtime execution.

/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}
}
