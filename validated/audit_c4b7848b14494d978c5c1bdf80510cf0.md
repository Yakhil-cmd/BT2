### Title
Webhook signature verification is scoped to `repository.owner.login`, while the repository actually written is selected from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, the HMAC signature on an inbound GitHub webhook is checked against the secret belonging to the organization named in `repository.owner.login` (or `organization.login`), but the handler that actually decides *which* `Stack`/`Repository` gets updated reads a **different** JSON field, `repository.full_name`, which is not covered by that binding. An attacker who legitimately controls one configured GitHub App/organization (and therefore knows that organization's `webhook_secret`) can produce a validly-signed payload whose `owner.login` matches their own org (to pass verification) while `repository.full_name` names a repository belonging to a completely different organization also configured in the same Shipit instance. This lets them inject a push event for a repository/stack they do not own.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration - and thus the secret used to validate `X-Hub-Signature` - purely from the repository owner login in the payload: [1](#0-0) [2](#0-1) 

This only proves that the request was signed with the secret of the organization returned by `repository.owner.login` (or `organization.login` as fallback). It does not bind or cross-check any other field of the payload to that organization.

However, once the signature check passes, the raw, fully-attacker-controlled JSON is dispatched to handlers unmodified: [3](#0-2) 

`Handler#repository_name`, used by every repo-scoped handler (including `PushHandler`) to look up the target `Repository`/`Stack`, reads a **different** field than the one used for signature scoping: [4](#0-3) 

`PushHandler#process` then uses this lookup, together with an attacker-supplied `after` (target SHA) and `ref` (branch), to trigger a sync against any matching, non-archived stacks: [5](#0-4) 

The security-relevant equality that should hold is:
`organization whose secret authenticated the request == organization owning the repository that gets synced`

But the code actually enforces:
`payload["repository"]["owner"]["login"] == <org selected by Shipit.github(organization: …)>`
while acting on:
`payload["repository"]["full_name"]` (an independent, unverified string, e.g. `"other-org/other-repo"`)

Nothing forces `full_name` to start with the same owner login that was used for signature selection - both are attacker-supplied strings inside the same signed JSON body, and GitHub's own webhook format never requires them to be internally consistent from Shipit's point of view; more importantly, since the whole check is just "does *some* configured org's secret validate this raw body", an attacker who controls one configured org's GitHub App secret can construct an arbitrary JSON body from scratch (not relayed from GitHub) with `owner.login` set to their own org but `full_name` pointing at an unrelated org/repo pair also configured on the same Shipit instance, and sign it with their own known secret.

### Impact Explanation
This breaks the trust boundary between "which organization authenticated this delivery" and "which repository's stack gets mutated." An attacker who administers a GitHub App for Organization A (and thus legitimately possesses Organization A's `webhook_secret`, a routine, low-privilege administrative capability for their own org) can forge a `push` event that is accepted as authentic and causes `Stack#sync_github` to run for a `Stack` belonging to Organization B, with an attacker-chosen `expected_head_sha`. This is a cross-organization/cross-repository write into another tenant's stack state via a forged, cross-repository-authenticated payload - matching the Critical criterion of "cross-repository writes / unauthorized deploy" since a spoofed head SHA feeding into sync/deploy-candidate tracking can influence which commit becomes deployable for a stack the attacker does not control.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit configuration (documented and supported, see `config/secrets.development.example.yml` and `docs/setup.md` multi-org example) where more than one organization's GitHub App and `webhook_secret` are registered, and (2) attacker control of at least one such organization's webhook secret - both are ordinary, unprivileged-attacker preconditions relative to Shipit itself (the attacker never needs a Shipit session, API token, or write access to the victim organization's actual GitHub repository). Given those, forging the payload and its HMAC is trivial.

### Recommendation
Do not select the verification secret using an unauthenticated field and then act on a different unauthenticated field. Either:
- Bind the org used for signature selection to the same repository identity used by handlers (verify that `repository.full_name`'s owner segment matches `repository.owner.login`/`organization.login` before dispatch), or
- Look up the `Repository`/`Stack` first, resolve its configured organization from Shipit's own trusted mapping, and verify the signature using that organization's secret rather than trusting `owner.login` from the payload.

### Proof of Concept
1. Shipit is configured with two GitHub Apps: `orgA` (secret `SECRET_A`) and `orgB` (secret `SECRET_B`), each mapped to their own `Repository`/`Stack` records, as supported by the multi-org config format in `docs/setup.md`.
2. Attacker, who administers `orgA`'s GitHub App, knows `SECRET_A`.
3. Attacker crafts a raw JSON body directly (not via GitHub) with a `push` shape:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `sha1=HMAC-SHA1(SECRET_A, body)` and sends `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `"orgA"`, fetches `orgA`'s app, and the signature verifies successfully (app/controllers/shipit/webhooks_controller.rb:24-30, 59-62).
6. `PushHandler#process` resolves the target stack via `Handler#repository_name`, which reads `full_name` = `"orgB/victim-repo"` (app/models/shipit/webhooks/handlers/handler.rb:36-38), and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Organization B's stack (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) - despite the request only having been authenticated with Organization A's secret.

      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
