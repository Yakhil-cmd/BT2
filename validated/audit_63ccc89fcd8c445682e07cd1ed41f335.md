### Title
Webhook signature verification is keyed to an attacker-controlled organization, not the repository the event acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check *before* it knows which repository the event will actually mutate. The app used for verification is derived from `repository.owner.login` (or `organization.login`) in the untrusted payload, while the code path that acts on the event (`StatusHandler`, `PushHandler`, etc.) looks up the target `Stack`/`Commit` via `repository.full_name`, a *separate* field of the same untrusted payload. These two fields are never required to match, so the "organization that authenticated" and "the repository that is written" are not the same equality the code assumes.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
with `repository_owner` read straight from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`GitHubApp#verify_webhook_signature` is a no-op when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

Once verification passes (trivially, for any org whose `webhook_secret` is blank/unset — a state explicitly shown as a normal/example configuration in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`), `WebhooksController#create` dispatches the *entire, attacker-controlled* body to the event handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers resolve the target `Stack`/`Commit` using a completely different payload field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`StatusHandler` does not even scope to a specific repository at all — it finds *any* commit by SHA across the whole install and attaches a forged CI status:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

So the binding the code implicitly relies on — "the organization whose signature was verified == the organization/repository being written to" — does not hold. An attacker who knows (or guesses) that *any one* configured GitHub organization in this Shipit instance has `webhook_secret` unset can:
1. Send a webhook with `X-Github-Event: status`, `repository.owner.login` = that unsecured org (so `verify_webhook_signature` short-circuits to `true` for any/no signature), and
2. `sha` = the head commit of a completely unrelated, security-critical stack belonging to a *different*, properly-secured organization, with `state: "success"`.

This creates a `Status` record on that commit as if the real CI/GitHub had reported success. Because `MergeRequest#all_status_checks_passed?` / `Commit#deployable?` rely on these `Status` rows, this can satisfy required CI checks and lead `ProcessMergeRequestsJob` to auto-merge a pull request via the merge queue, or mark a commit as "deployable" for a stack's continuous-deployment pipeline — all without ever proving anything to the real GitHub App for the target repository.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding described in scope. The consequence is an unauthorized merge/deploy trigger (forged CI status feeding `MergeRequest#merge!` / continuous deployment) on a repository the attacker never controls and whose GitHub App/webhook secret they never possessed — meeting the "unauthorized deploy, rollback or merge" Critical bar, without requiring any Shipit session, ApiClient token, webhook secret of the target org, or repository write access.

### Likelihood Explanation
Exploitability is entirely conditioned on at least one configured GitHub organization on the instance having no `webhook_secret` set. The engine's own example configuration files (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`) ship with `webhook_secret: # nil` as the default/documented value, and multi-org deployments (`docs/setup.md`, "Using Multiple Github Applications") are an explicitly supported configuration where per-org misconfiguration of just one org among several is plausible. Given this, an attacker does not need any secret for the *target* org — only knowledge (from documentation/defaults or reconnaissance) that some org in the instance lacks a webhook secret.

### Recommendation
Verify the webhook signature using the GitHub App that corresponds to the repository the payload will actually act on (`repository.full_name`), not solely `repository.owner.login`/`organization.login`, and reject events where the two disagree. Additionally, do not allow `verify_webhook_signature` to silently accept unsigned traffic when `webhook_secret` is blank for any organization if other organizations require it — either require every configured org to set a secret, or key the verification/dispatch entirely off the resolved target `Stack`'s own organization/app rather than attacker-supplied fields, and scope `StatusHandler`/other handlers to commits that belong to the same repository identified during verification.

### Proof of Concept
Preconditions: Shipit instance is configured with ≥2 GitHub organizations (as documented in `docs/setup.md`), where org `unsecured-org` has `webhook_secret` unset, and org `victim-org/critical-repo` has a stack with an open, otherwise-mergeable PR whose head commit sha is `HEAD_SHA` and which requires a CI status context, e.g. `ci/travis`.

```
POST /webhooks
X-Github-Event: status
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "irrelevant/anything" },
  "sha": "HEAD_SHA",
  "state": "success",
  "context": "ci/travis",
  "description": "forged",
  "target_url": "http://example.com"
}
```
`verify_signature` resolves `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the (absent/garbage) `X-Hub-Signature`. `StatusHandler#process` then matches `Commit.where(sha: "HEAD_SHA")` (any stack, any org) and creates a `success` `Status` on it, independent of `unsecured-org` having any relationship to `victim-org/critical-repo`. This satisfies CI requirements for the pending merge request / deploy eligibility and can be immediately followed by `ProcessMergeRequestsJob`/continuous-deployment automatically merging or deploying it.

Note: I could not execute this against a live instance from this read-only environment, so the end-to-end auto-merge trigger (`ProcessMergeRequestsJob#perform` → `MergeRequest#merge!`) is inferred from the code paths cited above (`app/jobs/shipit/process_merge_requests_job.rb`, `app/models/shipit/merge_request.rb`) rather than observed at runtime.
