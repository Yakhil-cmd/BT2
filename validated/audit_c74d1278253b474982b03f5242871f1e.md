### Title
`recapitalize` pays an unfunded refund and credits unbacked cash, desynchronizing the cash book from physical custody - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `recapitalize` entrypoint trusts that the controller already transferred `amount` tokens in before the call, but the pool itself never measures or verifies an inbound transfer. `accounting` credits `min(amount, backing_shortfall)` to the market's cash book and transfers `amount - applied` back out to `payer` unconditionally. An unprivileged caller can therefore (a) inflate the cash book without depositing anything, and (b) drain real custody by setting `amount` above the current shortfall so the "refund" leg pays pool funds to the attacker. This mirrors CVE-2016-2270's bug class: two inconsistent mappings of the same underlying resource — the bookkeeping view (`state.cash`) versus the physical view (the SAC token balance) — let the contract act on a state that does not correspond to reality, producing insolvency and denial of withdrawals.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`, `accounting` (lines 44-67) computes `applied = amount.min(guards::backing_shortfall(&cache))`, calls `cache.credit_cash(applied)` and `cache.commit()`, then `apply` (lines 26-38) executes `outcome.cache.transfer_out(&payer, outcome.refund)`. There is no balance-delta measurement and no check that `amount` was actually received — the doc comment on line 4 ("The controller transfers `amount` into the pool before this call") states an assumption the pool entrypoint does not enforce.

The pre-existing test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs` (lines 3408-3483) demonstrates the divergence directly on the pool client: after a 10_000_000_000 deposit, `recapitalize(hub_asset, payer, custody)` reduces `token.balance(pool)` to 0 while `state.cash` still reports ≥ the supplier's deposit. The test then shows a supplier `withdraw` passes the pool's own liquidity guards (`InsufficientLiquidity`/`PoolInsolvent` do not fire) and fails only inside the SAC transfer with `BalanceError = 10`, because `require_reserves` reads the overstated book.

Reaching this state requires only a direct call to `pool.recapitalize(hub_asset, payer, amount)` — listed among the permissionless entrypoints (`scripts/permissionless_entrypoints.txt`). When `backing_shortfall` is zero or smaller than `amount`, the attacker receives `amount - applied` tokens out of pool custody without paying in; when it is nonzero, the attacker inflates the cash book by `applied` for free. Either way the book's mapping of custody diverges from the real balance.

### Impact Explanation
Theft of user funds and protocol insolvency. The refund leg transfers real tokens to `payer`, so an attacker can extract `balance - shortfall` of any listed asset in one call. Simultaneously `credit_cash` books unbacked cash, so subsequent `withdraw`/`borrow`/liquidation legs pass `require_reserves` against phantom liquidity and revert only inside the token transfer — permanently freezing supplier exits for the drained asset. Because one physical pool balance backs all markets of a token across hubs (ADR-0002, `docs/explanation/decisions.md` lines 88-93), the desync affects every market book of that asset.

### Likelihood Explanation
A single unprivileged address can call `recapitalize` directly on the pool with `payer` set to itself and `amount` chosen so `refund` equals the pool's free balance. No timing, oracle, or governance precondition is required; the only inputs are a `HubAssetKey`, an address, and an `i128`. Severity: Critical.

### Recommendation
Measure the receipt instead of trusting it: snapshot `token.balance(pool)` before crediting, require the caller to transfer in (or pull via allowance), and credit/refund based on the measured delta, consistent with the pool's measured-receipt policy for supply and repay. Alternatively gate `recapitalize` to controller-only invocation and make the refund leg conditional on an actual overpayment observed in custody.

### Proof of Concept
Demonstrated by `contracts/pool/tests/flows.rs` lines 3408-3483:

```rust
token_admin.mint(&t.pool, &deposit);                       // 10_000_000_000 in custody
t.client().supply(&t.sup(0, deposit));                     // book == custody

t.client().recapitalize(&hub(&t.asset), &payer, &custody); // unfunded call
assert_eq!(token.balance(&t.pool), 0);                     // custody drained to payer
assert!(t.state_snapshot().cash >= deposit);               // book still claims funds

let outcome = t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
// passes pool liquidity guards, fails inside SAC with BalanceError = 10
```

An attacker variant sets `payer` to itself and `amount = pool_balance`; with `backing_shortfall` below `amount`, `transfer_out(&payer, refund)` pays the difference out of custody it never funded.
