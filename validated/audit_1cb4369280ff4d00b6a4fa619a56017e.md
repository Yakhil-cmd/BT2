### Title
Cross-tenant status webhook forgery enables unauthorized merge via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the commit(s) to mutate solely by `sha`, with no check that the webhook's `repository` belongs to the commit's own stack, unlike every sibling handler. An attacker who controls any repository/organization onboarded to the same Shipit instance (and therefore knows that org's own `webhook_secret`) can send a validly-signed `status` webhook whose `sha`/`context` happen to match a victim stack's open `MergeRequest` head commit and `deploy_spec.merge_request_required_statuses`, injecting a `success` status onto the victim's commit and triggering `MergeRequest#merge!` against the victim's real GitHub repo with the victim's `GITHUB_TOKEN`.

### Finding Description
The claimed binding is: `identity verified by verify_signature (payload.dig('repository','owner','login'))` == `repository/stack that owns the mutated Commit (commit.stack_id, tied to payload.dig('repository','full_name'))`.

Tracing the code shows this equality is never enforced for status events:

- `WebhooksController#verify_signature` only checks the HMAC against `Shipit.github(organization: repository_owner)`, where `repository_owner` comes from the attacker-supplied payload's `repository.owner.login` [1](#0-0) [2](#0-1) . This proves only that the sender knows *some* onboarded org's secret — not that they control the repository named anywhere else in the payload.
- Every other handler scopes work through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` — e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)`) and `CheckSuiteHandler#process` (`stacks.where(branch:) ... stack.commits.where(sha:)`) [3](#0-2) [4](#0-3) [5](#0-4) .
- `StatusHandler#process`, however, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an unscoped, table-wide lookup with **no reference to `repository.full_name` and no use of the `stacks`/`Repository.from_github_repo_name` helper at all** [6](#0-5) .

Exploit flow: attacker reproduces the victim's PR head commit SHA in a repository/org they legitimately control on the same Shipit instance (feasible for un-modified upstream commits, since git SHAs are content-deterministic). They send (or cause GitHub to send) a `status` event signed with their own org's known `webhook_secret`, with `sha` = the shared commit and `context` matching `deploy_spec.merge_request_required_statuses`. `verify_signature` passes because it only validates against the attacker's own org. `StatusHandler` then finds the victim's `Commit` row purely by `sha` and calls `commit.create_status_from_github!(params)`, which uses `stack_id` from the commit itself (the victim's real stack) [7](#0-6) , creating a genuine `success` status under the victim stack and calling `stack.schedule_merges` [8](#0-7) .

`ProcessMergeRequestsJob#perform` then runs `reject_unless_mergeable!`, which is satisfied because `any_status_checks_missing?`/`any_status_checks_failed?` read `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)` [9](#0-8) , and the injected status now satisfies the required context. `all_status_checks_passed?` becomes true, and `merge_request.merge!` calls `stack.github_api.merge_pull_request(stack.github_repo_name, number, ...)` using the victim stack's own GitHub App token [10](#0-9) [11](#0-10) .

No existing guard prevents this: `verify_signature` authenticates only the *organization named in the attacker's own payload*, not that the SHA/commit being mutated belongs to that organization; `ExplicitParameters` schema for `StatusHandler` only validates types, not repository ownership; and there is no analog of `Handler#stacks` scoping in this handler.

### Impact Explanation
An attacker who legitimately controls any repository/org onboarded to the shared Shipit instance can inject arbitrary CI status onto an unrelated victim stack's commit purely by SHA collision and context-name guessing, causing Shipit to execute `github_api.merge_pull_request` against the victim's real GitHub repository using the victim's `GITHUB_TOKEN`/App installation token. This is a cross-tenant write ("a payload for one repository mutating another's stack, commit ... or an unauthorized ... merge"), rated Critical. It is repeatable against any stack whose merge queue is enabled and whose required-status context names and PR head SHAs can be predicted/reproduced, and generalizes to any multi-tenant Shipit deployment serving more than one GitHub organization.

### Likelihood Explanation
Requires: (1) `merge_queue_enabled: true` and an open pending `MergeRequest` on the victim stack, (2) attacker controls some repository/org already onboarded to the same Shipit instance (so they legitimately know that org's `webhook_secret`), (3) attacker can reproduce the victim head commit's exact SHA (realistic for unmodified upstream/shared commits) and knows/guesses the required status `context` string (often a well-known CI name like `ci/travis`). No victim secrets, sessions, or GitHub write access are needed. This is a single crafted HTTP POST to `/webhooks`, fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the webhook payload, mirroring every other handler: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and only update statuses on commits belonging to those stacks (`stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), rejecting/ignoring status updates for commits whose `stack.repository` does not match the payload's `repository.full_name`.

### Proof of Concept
Minitest (`test/models/webhooks/handlers/status_handler_test.rb` or controller-level integration test), no live GitHub:
1. Create `victim_stack` (`merge_queue_enabled: true`), a `Commit` with `sha: "deadbeef..."` belonging to `victim_stack`, and a pending `MergeRequest` on `victim_stack` whose `head` is that commit. Stub `victim_stack.cached_deploy_spec.merge_request_required_statuses` to `['ci/shared']`.
2. Create an unrelated `attacker_stack`/`attacker_repository` also configured on the instance, with a known `webhook_secret` for its org.
3. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: "deadbeef...", state: "success", context: "ci/shared", repository: { full_name: attacker_repo_full_name, owner: { login: attacker_org } } }`, signed with the attacker org's `webhook_secret` (mirroring `Hook::DeliverySigner`).
4. Assert: before, `victim_commit.statuses.count == 0`; after POST, `victim_commit.reload.statuses.count == 1` and `victim_commit.status.context == 'ci/shared'` — i.e., a status was written to the victim's commit despite the payload naming the attacker's own unrelated repository (`payload['repository']['full_name'] != victim_stack.github_repo_name`), proving the broken binding.
5. Mock `Shipit.github.api.expects(:merge_pull_request)` (and `pull_requests`, `delete_branch`), run `ProcessMergeRequestsJob.perform_now(victim_stack)`, and assert `merge_pull_request` was called with `victim_stack.github_repo_name`, demonstrating the unauthorized merge caused entirely by the attacker-controlled, cross-repository status webhook.

```ruby
    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
```

```ruby
    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?

      return false unless stack.allows_merges?

        merge_request.refresh!

        rescue MergeRequest::NotReady
```
