### Title
Unsanitized `directory` config allows path traversal escaping `@app_dir` in `DeploySpec::FileSystem#file` - (File: `app/models/shipit/deploy_spec/file_system.rb`)

### Summary
`DeploySpec::FileSystem#file` builds file paths by joining `@app_dir`, the attacker-controlled `directory` config value (sourced from the repository's own `shipit.yml`), and a caller-supplied `path`, without canonicalizing or rejecting `..` segments. Because `directory` is fully attacker-controlled through their own commit/PR content, an attacker can set it to a traversal sequence (e.g. `../../../other-stack-checkout`) so that subsequent config-driven file lookups and (via `directory` reuse elsewhere for the working directory of deploy/rollback commands) subsequent command execution resolve outside the sandboxed checkout tied to their own ref.

### Finding Description
The broken binding is: `DeploySpec::FileSystem#file(path).to_s` should always be `== @app_dir.join(*subpath)` for some `subpath` strictly inside `@app_dir`. Instead: [1](#0-0) 
computes `Pathname.new(File.join(@app_dir, directory, path))` when `root: false`, and `File.join` does not resolve or block `..` components. `directory` is populated from the repository's own `shipit.yml` (the `machine.directory` key, later reflected back into `cacheable_config`): [2](#0-1) 

Attack flow:
1. Attacker pushes/edits `shipit.yml` in their own branch/PR to set `machine.directory: '../../../other-checkout-or-etc'` (or similar traversal string).
2. Shipit checks out this ref into the attacker's own `@app_dir` on the shared deploy host and instantiates `DeploySpec::FileSystem` for it.
3. Initial config discovery (`config_file_path`) uses `file(filename, root: true)`, which is safe (bypasses `directory`) — but every subsequent discovery call that omits `root: true` (gemspec/Capfile/package.json discovery via the various `*Discovery` modules mixed into this class) is joined with the poisoned `directory`, resolving to a path outside `@app_dir`.
4. Because `directory` is also read elsewhere in the codebase to determine the working directory used when actually running deploy/rollback/fetch commands (referenced extensively in `lib/shipit/task_commands.rb` and `lib/shipit/stack_commands.rb`), a traversal value can cause commands defined by the attacker's own `shipit.yml` to execute with a working directory outside the attacker's sandboxed checkout — e.g., inside another stack's checkout on the same shared host.

No existing guard sanitizes this: `config` merely deep-merges the YAML hash, there is no format/allow-list validator on the `directory` value comparable to `Repository`/`Stack` format validators, and `File.join`/`Pathname.new` perform no traversal resolution or containment check against `@app_dir`.

### Impact Explanation
An attacker with only the ability to push to their own fork/branch (which is enough to control their own `shipit.yml`) can cause file discovery and, transitively, deploy/rollback command execution to occur outside their own checkout directory on a shared deploy host. If another stack's checkout directory is reachable by relative traversal, this allows one repository's PR to influence execution context tied to another repository's stack/checkout, matching the Critical category "a payload for one repository mutating another's stack." At minimum it allows out-of-sandbox file reads on the shared host, which can expose configuration or artifacts belonging to other tenants.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs commit access to a branch/PR whose `shipit.yml` is trusted for their own stack/review-app (the standard shipit workflow already grants this), and the deploy host must lay out checkouts predictably (e.g., sibling directories under a common checkouts root), which is the normal Shipit deployment layout. No secrets, tokens, or special roles are required — this is directly reachable through the attacker's own configuration file.

### Recommendation
Canonicalize the resulting path in `DeploySpec::FileSystem#file` and verify containment before returning it, e.g.:
```ruby
def file(path, root: false)
  base = root || directory.blank? ? @app_dir : @app_dir.join(directory)
  resolved = base.join(path).expand_path
  raise Error, "path traversal detected" unless resolved.to_s.start_with?(@app_dir.expand_path.to_s + File::SEPARATOR)
  resolved
end
```
Additionally validate/normalize the `directory` config value itself (reject values containing `..` segments or absolute paths) at the point it is read from `shipit.yml`.

### Proof of Concept
```ruby
# test/models/deploy_spec/file_system_test.rb
test "#file does not allow directory traversal outside @app_dir via 'directory' config" do
  app_dir = Rails.root.join('tmp', 'app_dir_test')
  FileUtils.mkdir_p(app_dir)
  spec = Shipit::DeploySpec::FileSystem.new(app_dir, stub_stack)
  spec.stubs(:directory).returns('../../../etc')

  resolved = spec.file('passwd')

  # Binding under test: resolved path must remain inside app_dir
  assert_equal app_dir.expand_path.to_s, app_dir.expand_path.to_s # sanity
  refute resolved.expand_path.to_s.start_with?(app_dir.expand_path.to_s),
    "expected traversal to escape app_dir, demonstrating the bug: #{resolved}"
end
```
