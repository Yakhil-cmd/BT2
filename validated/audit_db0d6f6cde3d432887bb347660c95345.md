### Title
StatusHandler#process updates commits for every stack sharing a sha, regardless of repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike sibling handlers (`PushHandler`, `CheckSuiteHandler`, pull-request handlers) which all filter through the base `Handler#stacks` scope tied to `payload['repository']['full_name']`. A single `status` webhook whose `sha` matches commits belonging to multiple stacks across unrelated repositories (e.g., the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any other duplicate/copied sha) will mutate the commit status of all of them.

### Finding Description
The claimed binding: number of stacks touched by one `status` webhook == number of stacks whose `repository.full_name == payload['repository']['full_name']` (expected `<= 1`).

Actual code path:
- `Shipit::WebhooksController#create` parses the JSON payload and dispatches to handlers registered for the event type [1](#0-0) .
- `verify_signature` only checks the HMAC signature against `Shipit.github(organization: repository_owner)` — it authenticates that the payload came from a GitHub org's webhook secret, it does **not** bind the payload to a specific stack or restrict which commits/stacks the handler may touch [2](#0-1) .
- `Handler#stacks` is the shared scoping mechanism other handlers use: it resolves `Repository.from_github_repo_name(repository_name)` from `payload['repository']['full_name']` and returns only that repository's stacks [3](#0-2) .
- `PushHandler#process`, for comparison, correctly scopes through `stacks.not_archived.where(branch:)` [4](#0-3) .
- `StatusHandler#process`, however, never calls `stacks` at all — it queries `Commit.where(sha: params.sha)` directly across the entire `commits` table, with no repository filter whatsoever [5](#0-4) .
- Each matched `Commit#create_status_from_github!` then creates a `Status` record and runs `add_status`, which emits `Hook.emit(:commit_status, ...)`/`:deployable_status`, potentially calls `stack.schedule_merges`, and can flip `deployable?` for that commit's stack [6](#0-5) [7](#0-6) .

Attacker request: register/own any GitHub repository (or otherwise cause a `status` event to fire, e.g. by pushing a commit with a colliding sha such as the empty-tree sha to a repo they control), then have GitHub (or a forged-but-signed request from that org, since signature verification is per-organization not per-target-stack) deliver a `status` webhook with `sha=<colliding sha>`, `state=success`. Because `Commit.where(sha:)` is global, if N unrelated stacks (in N different repositories/tenants) each contain a `Commit` row with that sha, all N get their status mutated by this one webhook, even though the signature only proves authenticity for the attacker's own organization/repository.

None of the listed guards close this gap: `verify_signature` checks org-level HMAC, not per-stack scoping; `drop_unhandled_event` just checks the event is registered; the `ExplicitParameters` schema only validates the shape of `sha`/`state`/etc., not their target; there's no `stacks`/repository-scoped query in this handler. This is a real divergence from the intended binding and matches the base `Handler#stacks` pattern that every other handler correctly uses but `StatusHandler` omits.

### Impact Explanation
A single, validly-signed webhook from an attacker-controlled (or attacker-triggered) repository can write `Status` rows and flip commit/stack `deployable?`/CI state for **every stack in every tenant repository** that happens to contain a commit with the same sha as the attacker's commit. Since git sha collisions are trivially engineered for content-identical commits (the canonical example is the empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, but any repo that shares history/cherry-picks/no-op commits could produce identical shas across tenants), this lets one repository's webhook mutate another tenant's `Commit`/`Stack` state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." This can force a target stack's commit to `success`, potentially triggering `stack.schedule_merges` or unblocking `continuous_deployment?`/`ContinuousDeliveryJob`, i.e., contributing to an unauthorized deploy on a completely unrelated stack.

### Likelihood Explanation
Preconditions required: at least one other stack (in a different, unrelated repository) must already contain a `Commit` row with the same sha as a commit the attacker can create/push (trivial for well-known empty-tree/no-op commits, or achievable via commit-graph engineering). The attacker only needs to control (or push to) any repository configured in Shipit that can emit a `status` webhook for that sha — no Shipit session, API token, or secret is required beyond what GitHub already provides them for their own repo. This is fully repeatable: every `status` event they can trigger on their own repo/sha will cross-mutate every other stack sharing that sha, at zero incremental cost per request.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: use the base `stacks` helper (or an explicit `Commit.joins(:stack).merge(stacks)` / `commit.stack.repository.full_name == repository_name` check) so only commits belonging to stacks whose repository matches `payload['repository']['full_name']` are updated, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
Minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or extend `test/controllers/webhooks_controller_test.rb`):
1. Create `repo_a = Shipit::Repository.create!(name: 'repo-a', owner: 'org', ...)` and `stack_a` under it; create `repo_b`/`stack_b` and `repo_c`/`stack_c` similarly, each with distinct `repository_id`.
2. Create three `Shipit::Commit` records, one per stack, all sharing `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`.
3. Build a webhook payload with `repository.full_name` equal to `repo_a`'s full name only, `sha` set to the colliding sha, `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the binding on both sides: expected — only `commit_a.reload.status.state == 'success'`, while `commit_b.reload.status.state` and `commit_c.reload.status.state` remain unchanged (e.g., `'unknown'`/previous state). Actual — assert (reproducing the bug) that all three commits' `status.state == 'success'` after the single call, demonstrating `stacks_touched == 3` instead of the expected `<= 1`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
