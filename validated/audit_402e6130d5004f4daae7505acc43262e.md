### Title
Reversion to a previously-used `address_definition_change` allows replay of stale signed units and double-spending of coins - ([File: validation.js])

### Summary
Ocore addresses can change their signing key/definition at any time via an `address_definition_change` message, and the codebase explicitly permits an address to later revert to a previously-used `definition_chash`. Because signature verification always uses "whatever definition is currently active for the address at `last_ball_mci`" rather than binding a signed unit to a specific, never-reusable key version, a unit that was signed while an old definition was active — but never broadcast/included because the definition had since changed — can become valid again once the address's definition reverts back to that old value. This mirrors the TOB finding about DharmaKeyRegistryV1/DharmaSmartWalletImplementationV2: key/definition changes are reversible, and stale signed messages can "come back to life" and be replayed, here enabling an unspent payment previously signed by the user to be rebroadcast and settle at an unexpected time — including by any party who obtained a copy of that stale signed unit.

### Finding Description
An Obyte/ocore address is only nominally bound to a definition hash (`address = chash(definition)`), but the *effective* definition used for validating any unit signed by that address is looked up dynamically at validation time, not fixed to a particular history point: [1](#0-0) 

`readDefinitionChashByAddress` returns "whatever the latest stable `address_definition_changes` row says as of `max_mci`, or the address itself if none" — with no restriction against that value being a `definition_chash` that was already active for this address at an earlier point in time.

`validateAuthor` uses exactly this dynamic lookup to determine which key is authoritative for checking a unit's signature: [2](#0-1) 

The codebase itself documents that reverting to an old definition is expected/allowed behavior, not defended against: [3](#0-2) 

"(not just in first appearance: it can return to its initial definition_chash sometime later)" explicitly acknowledges that `definition_chash == address` can reappear after intervening changes.

The developers were also aware of a race scenario nearly identical to the TOB report and consciously left it open ("let it be for now"): [4](#0-3) 

"in one particular case, the attacker changes his definition then quickly sends a new ball with the old definition - the new definition will not be active yet ... let it be for now."

Unlike an EVM-style nonce, ocore has no per-address monotonic counter that is bumped by an `address_definition_change`. The only anti-replay mechanisms are:
- `checkNoPendingChangeOfDefinitionChash` / `checkNoPendingDefinition`, which only forbid *new* units from being built on top of an *unstable* pending definition change — they do nothing once the change is stable and later reverted: [5](#0-4) 

- UTXO-based double-spend detection (`checkForDoublespends`), which only fires if the *same* input is spent twice — it does not prevent a single, previously valid-but-unbroadcast payment from later becoming valid and consuming still-unspent outputs: [6](#0-5) 

So the exact TOB pattern applies: (1) a user's wallet signs a unit (payment, AA trigger, data feed, etc.) under definition A; (2) before that unit is included, the address changes its definition to B (key rotation, e.g. after suspected compromise, or a normal key change flow) — causing the old unit's signature check against the *now-current* definition B to fail if resubmitted; (3) later, legitimately or through attacker action, the address's definition is changed back to A; (4) the original, previously "dead" signed unit (or a copy retained by a hub, light-vendor, or attacker who intercepted it) can now be rebroadcast and will pass `validateAuthor`'s signature check again, because ocore's definition lookup treats A as valid once more.

### Impact Explanation
This allows concrete unauthorized spending / double-spend of funds: a stale, previously composed but never-finalized payment unit — signed while an old key/definition was active — becomes valid and spendable again purely because the address's definition history returned to that old value. Any unspent outputs referenced by that stale unit (which the user believed were safe because the signing key had since been rotated away) can be consumed without a fresh signature from the user's *current* intent. The same applies to AA triggers, data-feed posts, or definition-based multisig authorizations composed under an older key, letting an old authorization silently regain force. This meets the "concrete unauthorized spending / double-spend of a stable output" bar from the validation rubric, and is reachable by any unprivileged unit poster who can watch the network for `address_definition_change` messages and hold on to previously observed but rejected signed units for a target address.

### Likelihood Explanation
Likelihood is elevated because: (1) key rotation via `address_definition_change` is a normal, unprivileged, single-authored operation any address owner can perform at will; (2) reverting back to a previous `definition_chash` is explicitly allowed and even documented as expected in `checkWitnessesKnownAndGood`'s comment; (3) no nonce or blacklist of retired `definition_chash` values exists to prevent replay after reversion, and the developers' own comment in `handleDuplicateAddressDefinition` acknowledges the exact race but leaves it unaddressed ("let it be for now"). Any wallet or hub that ever observed/cached a signed-but-unincluded unit (a light vendor, a hub relaying non-serial units, or the user's own offline-signed backlog) is a natural source for later replay.

### Recommendation
Short term: bind signature validity for `address_definition_change` operations to a monotonically increasing per-address sequence number (or timestamp/mci floor) that is stored alongside the definition, and reject any incoming unit whose author is a non-AA address if the referenced definition's activation epoch is older than the address's current epoch — i.e., forbid returning to a `definition_chash` that has already been superseded, unless explicitly re-declared with a fresh signature bound to the current epoch. Alternatively, maintain a per-address blacklist of retired `definition_chash` values (as recommended by the original Dharma report) so `address_definition_change` cannot set `definition_chash` back to a value the address has already moved away from.

Long term: add unit tests that specifically exercise the A→B→A definition-change cycle described in `validation.js`'s own comments, verifying that units signed under the first "A" period cannot be replayed once the address returns to "A", and extend `checkNoPendingChangeOfDefinitionChash`/`checkNoPendingDefinition` logic to cover stable, already-finalized reversions rather than only unstable pending ones.

### Proof of Concept
1. Address `X` starts with `definition_chash = X` (default definition `A`, e.g. `['sig', {pubkey: pubA}]`).
2. User signs (but does not get included, e.g. due to network delay/non-serial rejection) unit `U1`: a payment from `X` spending outputs `O1`, signed under definition `A`.
3. User rotates keys: posts and stabilizes an `address_definition_change` message setting `X`'s definition to `B` (`pubkey: pubB`). `storage.readDefinitionChashByAddress(X)` now returns `chash(B)`.
4. If `U1` is (re)broadcast now, `validateAuthor` (validation.js:1190-1208) reads the *current* definition (`B`) and signature verification against `pubA` fails — `U1` is rejected, and the user reasonably assumes `O1` remains under their control and `U1` is dead.
5. Later, the user (or an attacker able to trigger this, e.g. through social engineering or a "recovery" flow) posts another `address_definition_change` setting `X`'s definition back to `A` (`definition_chash = X` again) — allowed per the comment at validation.js:870-872 ("it can return to its initial definition_chash sometime later").
6. Anyone holding a copy of the originally-rejected `U1` (a hub that saw it, a light vendor cache, or the attacker) rebroadcasts `U1`. `readDefinitionChashByAddress` now again resolves to `A`, `validateAuthor` succeeds against `pubA`, and — provided `O1` is still unspent — `U1` is accepted, spending `O1` without any fresh authorization reflecting the user's current intent.

		max_mci = MAX_INT32;

		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments
							if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
								throw Error("double spending "+type+" without double spending address?");
							cb2();
						}
					});
				},
				function(err){
					if (err)
						return cb(err);
					onAcceptedDoublespends(cb);
				}
			);
		}
	);
}
