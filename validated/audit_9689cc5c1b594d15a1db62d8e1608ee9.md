### Title
Webhook signature verification checks `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub App/organization's `webhook_secret` to verify an inbound webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body [1](#0-0) [2](#0-1) . Once the HMAC check passes, every event handler independently determines *which repository/stack to act on* using a different field of the same payload, `repository.full_name` [3](#0-2) . Nothing cross-validates that the owner segment of `full_name` matches the `owner.login` that was used to pick the verifying secret. In a multi-organization Shipit deployment (`Shipit.github` keyed per-organization, see `TOP_LEVEL_GH_KEYS`) [4](#0-3) , this is the same "field acted on vs field actually authenticated" split as the ETH2 deposit-root bug: the identity that authenticates (`repository.owner.login`) is not the identity whose resource is mutated (`repository.full_name`).

### Finding Description
- Signature check: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) .
- Action target: `Handler#stacks` resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` and dispatches on it (e.g. `PushHandler#process` calls `stack.sync_github`) [3](#0-2) [5](#0-4) .
- Both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside a single JSON body signed as one opaque blob (`OpenSSL::HMAC.hexdigest(...)`) [6](#0-5) . Signing the whole body only proves "whoever holds Organization A's `webhook_secret` sent this exact byte string" — it does not enforce that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same organization.
- Binding broken (equality that should hold but doesn't): `organization authenticated by verify_webhook_signature == organization whose repository/stack is mutated by the handler`. An operator who legitimately controls Organization A's GitHub App (and therefore knows/can trigger delivery of Organization A's `webhook_secret`-signed requests, e.g., via GitHub's webhook redelivery/test-ping tooling or a compromised low-privilege integration) can set `repository.owner.login: "orgA"` (so the correct, known secret is selected and verification passes) while setting `repository.full_name: "orgB/some-repo"` for a stack belonging to a different tenant organization B configured in the same Shipit instance.

### Impact Explanation
This lets an attacker who only has authenticated-webhook capability for Organization A force webhook-driven side effects on Organization B's stacks that they have no relationship to: forcing `sync_github` on arbitrary stacks (`PushHandler`), manipulating check-run/status refresh jobs, or (via `MembershipHandler`, which similarly trusts `organization.login`) creating/deleting `Team`/`Membership` records for a different org's teams — which feed directly into `User#authorized?` and the `Shipit.github_teams` authorization boundary [7](#0-6) . This matches the High-severity class "escalation into `Shipit.github_teams` authorization" and can also drive unwanted deploy-pipeline activity (sync/refresh) across tenant boundaries without the cross-org repository-write permission that should be required.

### Likelihood Explanation
This only matters for installations using the multi-organization `github:` secrets format (`TOP_LEVEL_GH_KEYS`), where more than one organization's webhook secret is trusted by the same Shipit instance [8](#0-7) . Any party capable of getting a validly-signed delivery for their own organization (an installed, but otherwise unprivileged/lower-trust tenant) can immediately forge the `repository`/`organization` fields to target another tenant's stacks, since the controller performs no cross-field consistency check before dispatching handlers.

### Recommendation
After `verify_signature` succeeds, re-derive the organization actually referenced by the event's target fields (e.g., the owner segment of `repository.full_name`, or the `organization.login` used by `membership`/`team` handlers) and assert it equals the `repository_owner` used to select the verifying secret; reject the request (422) on mismatch. Equivalently, verify the signature using the secret keyed by the *target* repository's known owner (looked up from the already-registered `Repository`/`Stack`, not from the untrusted payload) rather than trusting `repository.owner.login` for secret selection.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `orgA` and `orgB`, each with its own `webhook_secret` (`TOP_LEVEL_GH_KEYS` format) [8](#0-7) .
2. As the operator/holder of `orgA`'s webhook secret, craft a push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Sign the raw body with `orgA`'s `webhook_secret` and send it as `X-Hub-Signature` to `POST /webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature verifies successfully [1](#0-0) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on Organization B's stack [5](#0-4) , even though the request was never authenticated for Organization B.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
