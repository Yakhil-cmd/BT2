### Title
Single non-attested/blocked recipient in a multi-output AA payment causes the whole response unit to bounce, blocking payouts to all other legitimate recipients - (File: aa_composer.js, validation.js)

### Summary
When an autonomous agent (AA) composes a response unit that pays multiple recipients in one `payment` message for a restricted asset (`spender_attested`, `transfer_condition`, or `is_transferrable=false`), a single output address that fails the asset's condition causes `validateAndSaveUnit()` to fail for the **entire unit**. This is the ocore analog of the Sherlock M-4 finding: one "blacklisted"/non-qualifying recipient blocks repayment/distribution to everyone else in the same atomic operation, and the failure forces a full bounce/rollback rather than isolating the bad output.

### Finding Description
An AA can be programmed (e.g., a lending/vault-style contract) to pay out to several beneficiaries in one `payment` message of a restricted asset in a single trigger response, analogous to `LiquidityManager.sol` iterating over loans and transferring fees to each creditor from the vault. In ocore, `sendUnit()` builds this response unit and hands it to `validateAndSaveUnit()`: [2](#0-1) 

`validateAndSaveUnit()` performs full protocol validation of the composed unit via `validation.validate()`, and on `ifUnitError` simply returns the error to the caller, which then calls `bounce(err)`: [5](#0-4) 

Crucially, asset-level validation of restricted assets checks that *every* output address in the payment message individually satisfies attestation and transfer-condition requirements, and fails the whole message (and thus the whole unit) if any single output does not: [4](#0-3) 

So if the asset is `spender_attested` and one recipient among many is not (or has since lost) attestation, or the asset has a `transfer_condition` formula that a specific address fails to satisfy, `storage.filterAttestedAddresses`/`Definition.evaluateAssetCondition` returns an error for the *whole payment message*, not just that one output. That propagates up through `validatePaymentInputsAndOutputs` → `validatePayment` → `validation.validate` → `ifUnitError` → `bounce(err)`.

`bounce()` then discards the entire composed unit (`objStateUpdate = null`) and, since state changes/effects had already been applied speculatively during formula evaluation, `revert(err)` is invoked to undo everything: [3](#0-2) 

This means: if an AA's payout logic to multiple parties (e.g., splitting fees/collateral among several creditors or LPs) is written to emit one `payment` message with multiple outputs for a restricted asset, and just one recipient becomes unable to receive it (loses attestation, fails a `transfer_condition` that depends on external data-feed state, etc.), **none** of the intended recipients get paid and any accompanying state update (e.g., "loan marked repaid", "distribution completed") is rolled back. If the trigger sender has no way to retry excluding the blocked address (the AA logic is fixed), this can permanently prevent completion of that operation via that AA call path, mirroring the "creditor blocks all repayment" scenario from the Sherlock report.

### Impact Explanation
This can permanently deadlock legitimate multi-party AA distributions (loan repayments, fee splits, vault withdrawals) built on `spender_attested` or `transfer_condition`-restricted assets: one recipient losing eligibility blocks funds from reaching every other rightful recipient in the same trigger, and any dependent state transition is reverted every time the same trigger/logic is attempted. Depending on the AA's design, this can freeze user/AA funds or force repeated, unresolvable bounces (a form of AA fund freezing / DoS on the distribution logic), which is a Medium-severity availability/fund-freezing issue analogous to the original finding's "forced default."

### Likelihood Explanation
This requires the AA definition to (a) use a restricted asset (`spender_attested` or one with `transfer_condition`) for a payout, and (b) combine multiple recipients into a single payment message without per-output isolation/fallback (e.g., no try/skip logic, no separate messages per recipient with independent bounce handling). Such patterns are plausible for AAs implementing pooled distributions, lending protocols, or DAOs paying out restricted/compliance-gated tokens — a realistic and not uncommon AA design choice, though it depends on the specific AA author's implementation rather than being unconditionally present in the base protocol.

### Recommendation
- Document/strongly recommend that AA authors sending restricted (`spender_attested`/`transfer_condition`) assets to multiple recipients emit **separate** `payment` messages per recipient rather than combining outputs, so a single recipient's condition failure only fails that message/that portion of state (note ocore already supports partial failure isolation only at the message level, not sub-message/per-output level).
- Consider providing an oscript-level primitive or documentation pattern for "attempt payment, catch failure, redirect to escrow/skip" so AA developers can implement the same escrow-based mitigation used in the referenced fix, since ocore's validation currently offers no built-in per-output fallback within a single payment message.
- At minimum, flag this failure mode in AA-authoring guidance so authors avoid batching restricted-asset payouts to multiple untrusted/mutable-eligibility addresses in one message.

### Proof of Concept
1. Define an asset with `spender_attested: true` (or a `transfer_condition` gated on a data feed) and set up two attested addresses A and B as intended recipients.
2. Deploy an AA whose response logic, upon a single trigger, emits one `payment` message for that asset with two outputs: one to A and one to B, e.g. `outputs: [{address: A, amount: 100}, {address: B, amount: 100}]`, alongside a `state` message marking the operation as completed.
3. Before triggering, cause B to lose its attestation (attestor revokes/does not renew attestation) or make B fail the `transfer_condition` formula.
4. Send the trigger unit. In `aa_composer.js` `sendUnit()`, the composed response unit reaches `validateAndSaveUnit()`; `validation.js`'s `validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses`/`Definition.evaluateAssetCondition` over `arrOutputAddresses` (`[A, B]`), which fails because B does not qualify: `validation.js:2630-2659`.
5. Observe that `ifUnitError` fires, `bounce(err)` is called (`aa_composer.js:1408-1410`), and `revert(err)` rolls back the previously-applied state update and both intended payments — **A does not receive its 100 tokens either**, and the "completed" state flag is not set, even though A was fully eligible. Re-sending the identical trigger reproduces the same bounce indefinitely as long as B remains ineligible.
