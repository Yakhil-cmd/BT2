## Title
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank, authenticating unsigned webhooks for any org lacking a configured secret - (File: lib/shipit/github_app.rb)

### Summary
`verify_webhook_signature` explicitly short-circuits with `return true unless webhook_secret`, meaning any organization configured without a `webhook_secret` accepts every webhook request regardless of signature, sender, or content. `WebhooksController#verify_signature` relies solely on this method to gate dispatch to handlers (`push`, `status`, `check_suite`, `pull_request`, `membership`), so an attacker who simply names such an org in the payload gets full handler execution with zero secret knowledge.

### Finding Description
The binding that should hold is: `verify_webhook_signature(signature, body) == true` **iff** the request signature matches an HMAC computed with a secret only Shipit and GitHub know, for orgs that have opted into signature verification. Instead, the code at [1](#0-0)  returns `true` whenever `@webhook_secret` (set from `config[:webhook_secret].presence` at [2](#0-1) ) is blank — with no attacker-supplied signature check at all in that branch.

The controller path is: `WebhooksController#create` runs `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` [3](#0-2) . `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` using `repository_owner`, which is read straight out of the untrusted payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) [4](#0-3) , then calls `github_app.verify_webhook_signature(...)` and only halts with `head(422)` if it returns falsy [5](#0-4) . If verification "passes" (including the blank-secret bypass), `create` parses the body and dispatches to every registered handler for that event via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .

For a concrete handler, `PushHandler#process` looks up stacks by `branch` under the resolved `repository` scope and calls `stack.sync_github(...)` [7](#0-6) ; none of this re-checks the signature or the org's secret — it trusts that `verify_signature` already gated it.

Exploit: attacker sends `POST /webhooks` with header `X-Github-Event: push` and body `{"repository":{"owner":{"login":"<org-without-webhook_secret>"}}, "ref":"refs/heads/master", "after":"<any sha>"}` and no `X-Hub-Signature` (or any garbage value). `repository_owner` resolves to `<org-without-webhook_secret>`, `Shipit.github(organization: ...)` builds/fetches a `GitHubApp` for that org whose `@webhook_secret` is `nil`, and `verify_webhook_signature` returns `true` before ever inspecting the supplied signature or body. The request proceeds to `create`, and the push handler runs, forcing `sync_github` for every non-archived stack on that org's matching branch — fully attacker-controlled read/refresh of stack state, and by extension the same unauthenticated pathway applies to `status`, `check_suite`, `pull_request`, and `membership` handlers keyed off the same `verify_signature` gate.

This is not mitigated by `drop_unhandled_event` (only filters unregistered event types, not authenticity) [8](#0-7) , nor by `ExplicitParameters` schemas on individual handlers (those validate payload shape, not sender authenticity), nor by any check inside `Shipit.github`/`github_app_config` (which only raises if the org is entirely unknown, not if it lacks a secret) [9](#0-8) .

### Impact Explanation
Any org configured in `secrets.github` without a `webhook_secret` value is fully open: an attacker can forge `push`, `status`, `check_suite`, `pull_request`, and `membership` events naming that org and have Shipit process them as genuine GitHub callbacks. Concretely this can force stack `sync_github` calls, task/status state changes, and other side effects driven by these handlers for any repository under that org — a payload-driven write to that org's stacks with zero authentication. This matches the "authentication bypass (forged webhook ... accepted)" Critical impact category. Blast radius is scoped to orgs that omit `webhook_secret`, but in the documented realistic multi-tenant configuration described in the prompt (some orgs configure secrets, others don't), it is a full compromise of the webhook trust boundary for every such org, repeatable at will and for every affected event type.

### Likelihood Explanation
The only precondition is a Shipit deployment configuring at least one GitHub org without `webhook_secret` — which the code explicitly supports as a valid, intentional configuration (`@webhook_secret = @config[:webhook_secret].presence`, tolerating blank/absent values without erroring). The attacker needs no session, token, or secret of any kind — just the ability to send an HTTP POST to the public `/webhooks` endpoint with a crafted JSON body and event header, which matches the stated unprivileged threat model exactly. This is trivially repeatable and scriptable against any number of target orgs/stacks lacking the secret.

### Recommendation
Do not treat a blank `webhook_secret` as an implicit pass. Either: (1) require `webhook_secret` to be present for every configured org and fail closed (raise/log and reject with 422) when it's missing, or (2) if intentionally supporting secret-less legacy configs, make that decision explicit and logged as a deliberate opt-out rather than silently returning `true`, and strongly prefer removing that opt-out entirely so `verify_webhook_signature` always performs the HMAC comparison and never returns `true` without validating the actual signature against a real secret.

### Proof of Concept
```ruby
# test/lib/shipit/github_app_test.rb (conceptual, no live GitHub required)
test "verify_webhook_signature returns true for any signature when webhook_secret is blank" do
  github_app = Shipit::GitHubApp.new('acme', { app_id: 1, installation_id: 1, private_key: 'x' }) # no :webhook_secret key
  assert_equal true, github_app.verify_webhook_signature('sha1=deadbeef', '{"anything":"goes"}')
  assert_equal true, github_app.verify_webhook_signature('garbage', 'no relation to signature')
end

# test/controllers/webhooks_controller_test.rb (conceptual)
test "push webhook without signature is accepted and dispatched for org without webhook_secret" do
  Shipit.stubs(:github).with(organization: 'acme').returns(
    Shipit::GitHubApp.new('acme', { app_id: 1, installation_id: 1, private_key: 'x' })
  )
  stack = shipit_stacks(:shipit) # some stack under repository owned by 'acme', branch 'master'
  stack.expects(:sync_github).once

  post :create,
       params: { repository: { owner: { login: 'acme' } }, ref: 'refs/heads/master', after: 'a' * 40 },
       as: :json,
       headers: { 'X-Github-Event' => 'push' } # deliberately no X-Hub-Signature header

  assert_response :ok
end
```
Both assertions demonstrate the broken equality: `verify_webhook_signature` returns `true` with no valid signature, and the controller proceeds to dispatch the mutating `push` handler for a repository the attacker never authenticated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
