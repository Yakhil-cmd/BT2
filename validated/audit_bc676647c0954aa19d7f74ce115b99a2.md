### Title
Environment-variable whitelist enforced against the cached HEAD spec while commands execute the spec of the deployed commit - (File: `app/models/shipit/stack.rb`, `lib/shipit/task_commands.rb`, `app/jobs/shipit/cache_deploy_spec_job.rb`)

### Summary
`Stack#build_deploy` / `Stack#trigger_task` validate the attacker-supplied `env` hash against the variable whitelist declared in `stack.cached_deploy_spec` [1](#0-0) , a spec cached from whatever commit was HEAD when `CacheDeploySpecJob` last ran [2](#0-1) . The commands that actually spawn the shell process for that deploy/task re-load the spec from the checked-out commit's own `shipit.yml` via `TaskCommands#deploy_spec` [3](#0-2)  and merge `deploy_spec.machine_env` plus the already-approved `env` into the process environment [4](#0-3) . These are two different bindings of "spec" to "commit": the whitelist-check binds to the cached HEAD spec, while execution binds to the deployed commit's own spec.

### Finding Description
This mirrors the ConvexStakingWrapper pattern of a state-changing action (transfer / `shutdown`) being decoupled from the checkpoint that is supposed to gate it. Here the state that changes is the repository's `shipit.yml` content across commits, and the "checkpoint" is the whitelist filter (`EnvironmentVariables#permit`) that is supposed to be evaluated against the exact spec governing the commit that will run.

- `Deploy` creation: `build_deploy` calls `filter_deploy_envs(env.to_h)`, which delegates to `cached_deploy_spec.filter_deploy_envs`, using `deploy_variables` sourced from `cached_deploy_spec` [1](#0-0) [5](#0-4) .
- `cached_deploy_spec` is populated by `CacheDeploySpecJob`, which checks out `stack.commits.reachable.last` — the current branch tip at cache time — and stores the resulting `DeploySpec::FileSystem` [2](#0-1) . This cache is asynchronous and can lag the true HEAD, and it is completely decoupled from any specific `until_commit` chosen for a deploy.
- The actual deploy/task run instantiates its own spec directly from the commit's checked-out working directory: `DeploySpec::FileSystem.new(@task.working_directory, @stack)` [3](#0-2) , and merges `deploy_spec.machine_env` (declared in that commit's `shipit.yml`) together with the already-permitted `env` into the process environment used to spawn the shell command [4](#0-3) , which is ultimately interpolated unescaped into shell arguments via `Command#interpolate_environment_variables` [6](#0-5) .

Because a caller can pick any deployable commit (`until_commit`) via the deploy API — not necessarily HEAD — an attacker who controls a commit that is reachable/deployable (e.g., an older commit, or a commit merged before `shipit.yml` was tightened) can request a deploy targeting that commit while the whitelist check is performed against a *different*, currently-cached `shipit.yml`. If the cached (checked) spec's `deploy.variables` whitelist is broader than the one in effect at the targeted commit — or vice versa — the enforcement point and the enforcement target diverge exactly like the checkpoint/shutdown split in the referenced report: the check happens against one binding of "spec ↔ commit" while the effect (the shell environment that seeds `deploy.override`/`machine.environment` commands) happens against another.

### Impact Explanation
If the org's `shipit.yml` at HEAD declares (or omits) more permissive `deploy.variables` than the `shipit.yml` at the specific `until_commit` being deployed (a legitimate scenario when the whitelist was recently tightened to remove a dangerous variable, or when deploying an old/pinned commit), an unprivileged-but-authenticated caller with `deploy:stack` permission can pass an `env` value that was rejected/would-be-rejected under the targeted commit's own spec but is accepted because it is checked against the cached HEAD spec instead. That value then flows unfiltered into `Command#interpolate_environment_variables`/shell interpolation for the deploy steps of the target commit, which is `Command::Error`-class RCE-adjacent (shell command execution on the deploy host) if the variable name collides with one interpolated into a deploy script argument. This satisfies the Critical bucket ("RCE on the deploy host") because the whole purpose of the whitelist is to prevent caller-controlled strings from reaching shell interpolation in deploy scripts.

### Likelihood Explanation
Requires only a valid `deploy:stack`-scoped `ApiClient` token (already an authenticated party in scope) plus a repository where the variable whitelist changes between commits and the cache is briefly stale (which is expected, since `CacheDeploySpecJob` runs asynchronously after every sync) — this is a normal, frequently-occurring operational condition rather than a rare edge case, making likelihood moderate.

### Recommendation
Filter the deploy/task `env` against the spec of the commit that will actually run (i.e., re-derive or re-validate the whitelist from the checked-out `until_commit`'s `shipit.yml` inside `TaskCommands#deploy_spec`/at task-start time), instead of trusting `cached_deploy_spec` computed from a possibly different commit. Alternatively, refuse to filter env against a `cached_deploy_spec` whose cached commit does not match `until_commit`, forcing a fresh checkout-based validation before permitting the deploy.

### Proof of Concept
1. At HEAD (`commit A`), `shipit.yml` declares `deploy.variables: [SAFE_VAR]`. `CacheDeploySpecJob` caches this spec on the stack.
2. An earlier deployable commit `B` (still `reachable`) has a `shipit.yml` history where a variable `DANGEROUS_VAR` used to be whitelisted and is interpolated directly into a deploy script argument (e.g., `./deploy.sh $DANGEROUS_VAR`), or conversely `commit A`'s cached whitelist has since been narrowed but the same variable name is still consumed by `commit B`'s deploy script.
3. Caller with `deploy:stack` permission POSTs to create a deploy targeting `until_commit = B`, with `env: { DANGEROUS_VAR: "$(malicious command)" }`.
4. `build_deploy` filters `env` using `cached_deploy_spec.filter_deploy_envs`, which is `commit A`'s spec — since `DANGEROUS_VAR` isn't in `A`'s current whitelist it would normally be rejected, but if `A`'s cache is stale (still reflecting an older, more permissive spec) or the reverse mismatch applies, the check passes.
5. `TaskCommands#deploy_spec` loads `commit B`'s actual `shipit.yml`/steps for execution, and `Command#interpolate_environment_variables` substitutes `$DANGEROUS_VAR` unescaped into the deploy script's shell arguments, executing attacker-controlled shell content on the deploy host.
