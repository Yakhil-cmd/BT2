### Title
Missing Staking Info Validation in FastSync/SnapSync Allows Malicious Peer to Corrupt Persisted Staking DB — (`datasync/downloader/queue.go`)

### Summary

During FastSync/SnapSync, a malicious P2P peer can respond to a staking info request with an arbitrary `P2PStakingInfo` payload (tampered `CouncilNodeAddrs`, `CouncilRewardAddrs`, `CouncilStakingAmounts`). The `validate` closure inside `DeliverStakingInfos` unconditionally returns `nil` — explicitly marked as a TODO — so the tampered data passes through the delivery pipeline, is stored in the `fetchResult`, and is subsequently written to the staking DB via `PutStakingInfoToDB`. This corrupts the persisted staking epoch record used for validator selection and reward distribution.

### Finding Description

**1. Missing validation in `DeliverStakingInfos`** [1](#0-0) 

The `validate` closure always returns `nil`. Compare this to `DeliverBodies`, which checks `DeriveTransactionsRoot(...) != header.TxHash`, and `DeliverReceipts`, which checks `DeriveReceiptsRoot(...) != header.ReceiptHash`. [2](#0-1) [3](#0-2) 

Bodies and receipts are cryptographically anchored to the block header via Merkle roots. Staking info has no such commitment in the header, and the TODO comment confirms validation was never implemented.

**2. Staking info is fetched for pre-Kaia-fork staking-interval blocks** [4](#0-3) 

Any block at `header.Number % stakingUpdateInterval == 0` and `!isKaiaFork` triggers a staking info fetch from the sync peer.

**3. Tampered data is written directly to the DB** [5](#0-4) [6](#0-5) 

`PutStakingInfoToDB` calls `WriteStakingInfo`, which JSON-marshals and persists the data unconditionally. No re-derivation from contract state occurs at this point.

**4. `P2PStakingInfo` carries all reward-critical fields** [7](#0-6) 

`CouncilNodeAddrs`, `CouncilRewardAddrs`, and `CouncilStakingAmounts` are all attacker-controlled.

**5. `ToStakingInfo` converts the tampered P2P payload directly into the stored `StakingInfo`** [8](#0-7) 

### Impact Explanation

A syncing node that connects to a malicious peer during FastSync/SnapSync will persist attacker-chosen `NodeIds`, `RewardAddrs`, and `StakingAmounts` for any staking-epoch boundary block. The stored record is subsequently used for:
- Weighted-random validator selection (wrong validator weights)
- Reward distribution calculations (wrong reward addresses and amounts)

This constitutes **unauthorized reward distribution** — a required impact under the allowed gate — because the node will credit the wrong addresses with block rewards based on the corrupted staking amounts.

### Likelihood Explanation

- The attack requires only a standard P2P connection; no privileged access is needed.
- The downloader actively requests staking info from connected peers, so any peer the node connects to during FastSync can serve tampered data.
- The `TODO-Kaia-Snapsync` comment confirms this is a known, unresolved gap in production code.
- The constraint `!isKaiaFork` limits the attack to pre-Kaia-fork epoch blocks, but those records remain in the DB and are read back for historical reward calculations and potentially for the transition period near the fork.

### Recommendation

Implement content validation in the `DeliverStakingInfos` validate closure. Since staking info is derived from the AddressBook contract state (not committed in the block header), validation must re-derive the staking info from the canonical state trie at the relevant block and compare it against the peer-supplied data, or alternatively fetch staking info only from trusted/self-derived sources during sync rather than from untrusted peers.

### Proof of Concept

1. Stand up a syncing node in FastSync mode with `WeightedRandom` proposer policy.
2. Connect a fake peer that responds to staking info requests with a `P2PStakingInfo` where `CouncilStakingAmounts` are all zeroed and `CouncilRewardAddrs` are attacker-controlled addresses.
3. The fake peer's response passes through `DeliverStakingInfos` → `deliver` → `reconstruct` → `result.StakingInfo = stakingInfoList[index]`.
4. After sync completes, `commitFastSyncData` calls `PutStakingInfoToDB` with the tampered payload.
5. Assert via `GetStakingInfoFromDB` that the persisted record contains the zeroed amounts and attacker addresses.
6. Assert that subsequent reward calculations for blocks in that epoch use the wrong amounts and addresses.

func (q *queue) DeliverReceipts(id string, receiptList [][]*types.Receipt) (int, error) {
	q.lock.Lock()
	defer q.lock.Unlock()
	validate := func(index int, header *types.Header) error {
		if types.DeriveReceiptsRoot(types.Receipts(receiptList[index]), header.Number) != header.ReceiptHash {
			return errInvalidReceipt
		}
		return nil
	}

	reconstruct := func(index int, result *fetchResult) {
		result.Receipts = receiptList[index]
		result.SetReceiptsDone()
	}
	return q.deliver(id, q.receiptTaskPool, q.receiptTaskQueue, q.receiptPendPool, receiptReqTimer, len(receiptList), validate, reconstruct)
}
