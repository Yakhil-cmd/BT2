### Title
Membership webhooks are unauthenticated when an organization has no `webhook_secret`, allowing forged team membership escalation - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the target organization, so `WebhooksController#verify_signature` accepts any unsigned POST. Combined with `MembershipHandler#process` blindly trusting `member.login`/`action` from the payload, an unauthenticated attacker can forge a `membership` event that inserts a `Shipit::Membership` for an arbitrary real GitHub login into a team listed in `Shipit.github_teams`.

### Finding Description
The broken binding: `Shipit::Membership.exists?(team_id: T, user: victim)` (Shipit-side state) should equal "GitHub reports `victim` as a member of team `T`" (GitHub-side truth). For an org with `webhook_secret` unset, this equality can be forced false→true by an attacker with zero credentials.

Path: `WebhooksController#create` → `before_action :verify_signature` → `Shipit.github(organization: repository_owner)` (resolved purely from attacker-supplied `organization.login`/`repository.owner.login` in the JSON body) → `GitHubApp#verify_webhook_signature`: [1](#0-0) 
returns `true unless webhook_secret` — i.e. if the org's config has no `webhook_secret` (a documented, supported configuration, e.g. `webhook_secret: # nil` in `docs/setup.md` and `config/secrets.development.example.yml`), **every** payload passes verification regardless of any `X-Hub-Signature` header, valid or absent.

Once past that gate, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler#process`: [2](#0-1) 
which does `Team.find_or_create_by!(github_id: params.team.id)` (attacker-chosen `team.id`, can match a real `Shipit.github_teams` team id known publicly) and `User.find_or_create_by_login!(params.member.login)`. Contrary to the question's premise, `find_or_create_by_login!` does perform a live GitHub API lookup and stores the real `github_id`: [3](#0-2) 
so the created `User` row is correctly bound to the real `victim-admin` GitHub account — the flaw is not in this method's identity binding, it's that a `Membership` between that real user and the team is created purely from an unauthenticated webhook, with no verification that GitHub itself reports that membership. `team.add_member(member)` (`app/models/shipit/team.rb:41-43`) then persists it.

This directly poisons `User#authorized?`: [4](#0-3) 
which checks only local `Membership` rows against `Shipit.github_teams`, not live GitHub state. `Shipit.github_teams` is built from `github.oauth_teams` config, resolved once via `Team.find_or_create_by_handle`: [5](#0-4) 

No other guard intervenes: `drop_unhandled_event` only checks the event is registered, `check_if_ping` is irrelevant, and `ExplicitParameters` (`params do ... end` in `MembershipHandler`) only validates shape, not authenticity/provenance of the values.

### Impact Explanation
An attacker who knows (a) an org configured without `webhook_secret`, (b) a team id/slug belonging to a team in `Shipit.github_teams`, and (c) a real victim's GitHub login, can grant that victim (or, more usefully to the attacker, an account the attacker controls) authorized-team membership in Shipit with a single unauthenticated HTTP POST — no GitHub state required at all. This is a full authentication-bypass path into `Shipit.github_teams` authorization (High/Critical per the stated severity taxonomy — "escalation into `Shipit.github_teams` authorization" / "authentication bypass (forged webhook ... accepted)"). It is repeatable indefinitely and against any org in the installation that lacks a configured `webhook_secret`; blast radius is that organization's whole team-based authorization model, plus any features gated on `User#authorized?`.

### Likelihood Explanation
Requires the target org's GitHub App config to have no `webhook_secret` set — a state explicitly shown as a valid/default configuration in this repo's own docs and example secrets files (`docs/setup.md`, `config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`), i.e., not a hardened-but-misused edge case but a first-class supported mode. Attacker cost is a single crafted JSON POST to `/webhooks` with `X-Github-Event: membership`; no secrets, sessions, or GitHub credentials are needed. Feasibility is high and fully repeatable.

### Recommendation
Require `webhook_secret` to be present for any organization that has security-sensitive event subscriptions (at minimum `membership`), and fail closed (reject with 422) rather than accepting unsigned events when `webhook_secret` is blank. Alternatively, cross-check `membership` webhook state against a live GitHub API call (e.g., confirm the reported membership via `GET /orgs/:org/teams/:team/memberships/:username`) before mutating local `Membership` records, rather than trusting the payload outright.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (no live GitHub, using existing fixtures):
```ruby
test "unsigned membership webhook is accepted and grants forged team membership when webhook_secret is blank" do
  team = shipit_teams(:shopify_developers) # a team id also present in Shipit.github_teams via oauth_teams config
  Shipit.stubs(:github_teams).returns([team])

  # Simulate org with no webhook_secret: GitHubApp#verify_webhook_signature returns true unconditionally
  GithubHook.any_instance.unstub(:verify_signature) if defined?(GithubHook)
  Shipit.github(organization: 'shopify').stubs(:verify_webhook_signature).returns(true) # reflects webhook_secret.blank? path

  @request.headers['X-Github-Event'] = 'membership'
  # No X-Hub-Signature header at all (attacker doesn't have one)
  payload = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: 'https://example.com' },
    organization: { login: 'shopify' },
    member: { login: 'victim-admin' },
    repository: { owner: { login: 'shopify' } }
  }.to_json

  Shipit.github.api.expects(:user).with('victim-admin').returns(
    stub(id: 999, name: 'Victim Admin', login: 'victim-admin', email: 'victim@example.com',
         avatar_url: 'https://avatars.githubusercontent.com/u/999', url: 'https://api.github.com/user/victim-admin')
  )

  assert_difference -> { Shipit::Membership.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  victim = Shipit::User.find_by(login: 'victim-admin')
  refute_nil victim
  assert victim.teams.include?(team) # forged Membership == no real GitHub membership ever existed
  assert victim.authorized?          # binding broken: authorized before victim ever authenticated via OAuth
end
```
This demonstrates the equality `Membership(team, victim-admin) == GitHub-reported membership(team, victim-admin)` is violated: the left side becomes true purely from an unauthenticated webhook while the right side is false (no such GitHub API call establishing real membership is ever made or required).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
