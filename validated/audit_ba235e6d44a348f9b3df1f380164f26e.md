### Title
Unbounded `starting_block` in `pallet_vesting::vested_transfer` permanently locks target funds and exhausts vesting-schedule slots - ([File: substrate/frame/vesting/src/lib.rs])

### Summary
`pallet-vesting`'s `vested_transfer` extrinsic lets any signed account create a vesting schedule for an arbitrary, non-consenting target account. The schedule's `starting_block` field has no upper bound check. By setting `starting_block` to (or near) `BlockNumberFor<T>::max_value()`, an attacker creates a schedule whose "locked" amount can never decrease, so the funds transferred into it are permanently locked and the schedule can never be removed by normal means. Because a victim's schedule storage (`Vesting<T>`) is bounded by `T::MAX_VESTING_SCHEDULES`, repeating this attack fills all of the victim's schedule slots, permanently denying them the ability to ever receive a real vesting grant again — mirroring the sNOTE `coolDownTimeInSeconds` finding, where an unbounded, attacker/owner-controlled parameter caused a critical unlock path to fail forever.

### Finding Description
`VestingInfo::is_valid()` only checks that `locked` and `per_block` are non-zero [1](#0-0) . It performs **no bound check on `starting_block`**. `can_add_vesting_schedule` re-uses only this check before allowing a new schedule to be added [2](#0-1) .

The public, signed extrinsic `vested_transfer` accepts a caller-supplied `VestingInfo` (including `starting_block`) and a `target` account chosen by the caller, with **no consent required from the target**: [3](#0-2) 

`do_vested_transfer` transfers currency to the target and calls `add_vesting_schedule`, which stores the schedule and locks the account via `Currency::set_lock`: [4](#0-3) [5](#0-4) 

The unlock math in `VestingInfo::locked_at` computes `vested_block_count = n.saturating_sub(starting_block)`. If `starting_block` is set to `BlockNumberFor<T>::max_value()`, `n` (current block) can never reach or exceed it, so `vested_block_count` is always `0`, and `locked_at` always returns the full `locked` amount, forever: [6](#0-5) 

`report_schedule_updates`/`write_lock` never drop this schedule (its `locked_at` never reaches zero), so the lock on the target's balance is never released and the schedule is never removed from the bounded `Vesting<T>` storage: [7](#0-6) 

Because `Vesting<T>` is a `BoundedVec<..., MaxVestingSchedulesGet<T>>` [8](#0-7) , once an account accumulates `T::MAX_VESTING_SCHEDULES` such "poison" entries, `can_add_vesting_schedule`'s slot-count check will reject any further `vested_transfer` targeting that account with `Error::AtMaxVestingSchedules`: [9](#0-8) 

`merge_schedules` does not reliably clean this up either: `merge_vesting_info` treats a schedule whose `ending_block_as_balance()` is effectively `BlockNumber::max_value()` as *not yet ended*, and the merged schedule's `ending_block` is the `max()` of the two inputs — so merging a poisoned schedule with a legitimate one propagates the "never ends" property to the merged result instead of clearing it: [10](#0-9) 

The only clean remediation is the privileged, Root-only `force_remove_vesting_schedule` call [11](#0-10)  — exactly analogous to the sNOTE report's mitigation requiring NOTE governance to intervene once a malicious cooldown value is set.

This is a direct structural analog of the reported bug class: an attacker-controlled, unbounded time/duration-like parameter (`coolDownTimeInSeconds` ↔ `starting_block`) with no sanity upper bound causes a critical unlock/withdrawal computation to permanently fail (`safe32` cast reverting forever ↔ `locked_at` never reaching zero), permanently locking funds and requiring privileged/governance recovery.

### Impact Explanation
- Any signed, non-privileged account can permanently lock an arbitrary (attacker-chosen, as low as `MinVestedTransfer`) amount of funds that it transfers to any third-party account, without that account's consent.
- Repeating the attack `T::MAX_VESTING_SCHEDULES` times against the same victim permanently fills their bounded vesting-schedule slots with unremovable poison entries, permanently denying that account the ability to ever receive a legitimate vesting schedule (`vested_transfer`/`force_vested_transfer`) again, unless Root intervenes via `force_remove_vesting_schedule`.
- This is a genuine availability/integrity impact on a core FRAME pallet (`pallet-vesting`) that is wired into production runtimes (e.g., Polkadot/Westend common runtime, node-template) reachable via a normal signed extrinsic with no special role, matching the Medium severity classification given to the original sNOTE finding ("assets not at direct risk of theft, but the function of the protocol or its availability could be impacted... requiring governance to intervene").

### Likelihood Explanation
High reachability, low cost: the attack requires only a signed extrinsic (`vested_transfer`) and the `MinVestedTransfer` amount of funds per attempt, with no governance, no special role, and no cooperation from the victim. It is fully deterministic — no race condition or economic assumption needed.

### Recommendation
Add an explicit upper-bound / sanity check on `starting_block` (and/or on `ending_block_as_balance()`) in `VestingInfo::is_valid()` or `can_add_vesting_schedule`, e.g. reject schedules whose ending block is unreasonably far in the future (a configurable `MaxVestingHorizon`), or require that `starting_block` not exceed `current_block + MaxScheduleHorizon`. Additionally, consider requiring the target to opt-in/claim a vesting schedule (or allow a permissionless cleanup path for schedules that provably can never vest) instead of allowing an arbitrary account to force an unremovable lock/slot-consuming schedule onto an unconsenting account.

### Proof of Concept
Reproduction sketch (based on static code tracing through the existing `pallet_vesting` test harness in `substrate/frame/vesting/src/mock.rs`/`tests.rs`; **not executed** in this analysis — no sandbox/terminal access was available to run it):
1. In the pallet's mock runtime, call `Vesting::vested_transfer(Some(attacker).into(), victim, VestingInfo::new(MinVestedTransfer, 1, BlockNumberFor::<Test>::max_value()))`.
2. Advance the mock block number arbitrarily far (`System::set_block_number(u64::MAX - 1)` or similar) and call `Vesting::vest(Some(victim).into())`; assert `Vesting::vesting_balance(&victim)` still equals the full locked amount (never decreases), confirming the fund lock never releases.
3. Repeat step 1 `T::MAX_VESTING_SCHEDULES` times against the same `victim`.
4. Attempt one more legitimate `vested_transfer` to `victim`; assert it fails with `Error::<Test>::AtMaxVestingSchedules`, confirming permanent denial of service absent a Root `force_remove_vesting_schedule` call.

Guards checked and found insufficient: `VestingInfo::is_valid()` (locked/per_block only) [1](#0-0) ; `can_add_vesting_schedule` (reuses `is_valid()` plus a max-count check, no time-bound check) [2](#0-1) . No consent/authorization check exists on the `target` parameter of `vested_transfer` [3](#0-2) .

Deployment evidence: `pallet-vesting` with this `vested_transfer` extrinsic and `MAX_VESTING_SCHEDULES` bound is used by multiple production runtimes in this repository (Polkadot/Westend common runtime, `substrate/bin/node/runtime`, etc.), confirming real-world reachability; the exact numeric value of `MAX_VESTING_SCHEDULES`/`MinVestedTransfer` per specific live runtime was not independently confirmed in this pass and should be verified before filing, since it determines exact attacker cost and severity magnitude.

	/// Amount locked at block `n`.
	pub fn locked_at<BlockNumberToBalance: Convert<BlockNumber, Balance>>(
		&self,
		n: BlockNumber,
	) -> Balance {
		// Number of blocks that count toward vesting;
		// saturating to 0 when n < starting_block.
		let vested_block_count = n.saturating_sub(self.starting_block);
		let vested_block_count = BlockNumberToBalance::convert(vested_block_count);
		// Return amount that is still locked in vesting.
		vested_block_count
			.checked_mul(&self.per_block()) // `per_block` accessor guarantees at least 1.
			.map(|to_unlock| self.locked.saturating_sub(to_unlock))
			.unwrap_or(Zero::zero())
	}

	fn merge_vesting_info(
		now: BlockNumberFor<T>,
		schedule1: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
		schedule2: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
	) -> Option<VestingInfo<BalanceOf<T>, BlockNumberFor<T>>> {
		let schedule1_ending_block = schedule1.ending_block_as_balance::<T::BlockNumberToBalance>();
		let schedule2_ending_block = schedule2.ending_block_as_balance::<T::BlockNumberToBalance>();
		let now_as_balance = T::BlockNumberToBalance::convert(now);

		// Check if one or both schedules have ended.
		match (schedule1_ending_block <= now_as_balance, schedule2_ending_block <= now_as_balance) {
			// If both schedules have ended, we don't merge and exit early.
			(true, true) => return None,
			// If one schedule has ended, we treat the one that has not ended as the new
			// merged schedule.
			(true, false) => return Some(schedule2),
			(false, true) => return Some(schedule1),
			// If neither schedule has ended don't exit early.
			_ => {},
		}

		let locked = schedule1
			.locked_at::<T::BlockNumberToBalance>(now)
			.saturating_add(schedule2.locked_at::<T::BlockNumberToBalance>(now));
		// This shouldn't happen because we know at least one ending block is greater than now,
		// thus at least a schedule a some locked balance.
		debug_assert!(
			!locked.is_zero(),
			"merge_vesting_info validation checks failed to catch a locked of 0"
		);

		let ending_block = schedule1_ending_block.max(schedule2_ending_block);
		let starting_block = now.max(schedule1.starting_block()).max(schedule2.starting_block());

		let per_block = {
			let duration = ending_block
				.saturating_sub(T::BlockNumberToBalance::convert(starting_block))
				.max(One::one());
			(locked / duration).max(One::one())
		};

		let schedule = VestingInfo::new(locked, per_block, starting_block);
		debug_assert!(schedule.is_valid(), "merge_vesting_info schedule validation check failed");

		Some(schedule)
	}

	// Execute a vested transfer from `source` to `target` with the given `schedule`.
	fn do_vested_transfer(
		source: &T::AccountId,
		target: &T::AccountId,
		schedule: VestingInfo<BalanceOf<T>, BlockNumberFor<T>>,
	) -> DispatchResult {
		// Validate user inputs.
		ensure!(schedule.locked() >= T::MinVestedTransfer::get(), Error::<T>::AmountLow);
		if !schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		// Check we can add to this account prior to any storage writes.
		Self::can_add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		)?;

		T::Currency::transfer(source, target, schedule.locked(), ExistenceRequirement::AllowDeath)?;

		// We can't let this fail because the currency transfer has already happened.
		// Must be successful as it has been checked before.
		// Better to return error on failure anyway.
		let res = Self::add_vesting_schedule(
			target,
			schedule.locked(),
			schedule.per_block(),
			schedule.starting_block(),
		);
		debug_assert!(res.is_ok(), "Failed to add a schedule when we had to succeed.");

		Ok(())
	}

	fn report_schedule_updates(
		schedules: Vec<VestingInfo<BalanceOf<T>, BlockNumberFor<T>>>,
		action: VestingAction,
	) -> (Vec<VestingInfo<BalanceOf<T>, BlockNumberFor<T>>>, BalanceOf<T>) {
		let now = T::BlockNumberProvider::current_block_number();

		let mut total_locked_now: BalanceOf<T> = Zero::zero();
		let filtered_schedules = action
			.pick_schedules::<T>(schedules)
			.filter(|schedule| {
				let locked_now = schedule.locked_at::<T::BlockNumberToBalance>(now);
				let keep = !locked_now.is_zero();
				if keep {
					total_locked_now = total_locked_now.saturating_add(locked_now);
				}
				keep
			})
			.collect::<Vec<_>>();

		(filtered_schedules, total_locked_now)
	}

	/// Write an accounts updated vesting lock to storage.
	fn write_lock(who: &T::AccountId, total_locked_now: BalanceOf<T>) {
		if total_locked_now.is_zero() {
			T::Currency::remove_lock(VESTING_ID, who);
			Self::deposit_event(Event::<T>::VestingCompleted { account: who.clone() });
		} else {
			let reasons = WithdrawReasons::except(T::UnvestedFundsAllowedWithdrawReasons::get());
			T::Currency::set_lock(VESTING_ID, who, total_locked_now, reasons);
			Self::deposit_event(Event::<T>::VestingUpdated {
				account: who.clone(),
				unvested: total_locked_now,
			});
		};
	}

	fn add_vesting_schedule(
		who: &T::AccountId,
		locked: BalanceOf<T>,
		per_block: BalanceOf<T>,
		starting_block: BlockNumberFor<T>,
	) -> DispatchResult {
		if locked.is_zero() {
			return Ok(());
		}

		let vesting_schedule = VestingInfo::new(locked, per_block, starting_block);
		// Check for `per_block` or `locked` of 0.
		if !vesting_schedule.is_valid() {
			return Err(Error::<T>::InvalidScheduleParams.into());
		};

		let mut schedules = Vesting::<T>::get(who).unwrap_or_default();

		// NOTE: we must push the new schedule so that `exec_action`
		// will give the correct new locked amount.
		ensure!(schedules.try_push(vesting_schedule).is_ok(), Error::<T>::AtMaxVestingSchedules);

		debug_assert!(schedules.len() > 0, "schedules cannot be empty after insertion");
		let schedule_index = schedules.len() - 1;
		Self::deposit_event(Event::<T>::VestingCreated {
			account: who.clone(),
			schedule_index: schedule_index as u32,
		});

		let (schedules, locked_now) =
			Self::exec_action(schedules.to_vec(), VestingAction::Passive)?;

		Self::write_vesting(who, schedules)?;
		Self::write_lock(who, locked_now);

		Ok(())
	}

		who: &T::AccountId,
		locked: BalanceOf<T>,
