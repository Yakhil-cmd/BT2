### Title
Webhook signature verification is keyed on `repository.owner.login`, but event handlers act on the independent `repository.full_name` field, allowing cross-organization payload forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the inbound HMAC signature against using `repository.owner.login` from the JSON body itself, while every webhook `Handler` subclass (via the shared `Handler#repository_name`) resolves the target `Repository`/`Stack` using the independent `repository.full_name` field from the same body. These two fields are never cross-validated against each other, so a party who legitimately controls one organization's GitHub App/webhook secret in a multi-org Shipit deployment can forge a signed payload that claims to belong to their own org (to pass signature verification) while pointing `repository.full_name` at a different, victim organization's repository.

using [2](#0-1) 
to fetch `repository_owner` — this value is used only to pick which configured GitHub App's `webhook_secret` (`Shipit.github(organization: repository_owner)`) should validate `X-Hub-Signature` against the raw POST body.

Every webhook handler, however, determines which `Repository`/`Stack` rows to mutate using a *different* field of the same payload: [3](#0-2) 

`Repository.from_github_repo_name` splits this string on `/` to find the owner and repo independently of whatever owner was used for signature selection: [4](#0-3) 

Because Shipit explicitly supports multiple independent GitHub Apps/organizations sharing one Shipit instance (each with its own `webhook_secret`), and the HMAC only proves "this body was signed by whoever knows organization X's secret," it does not prove that the `repository.full_name` inside the body actually belongs to organization X. Nothing in `verify_signature` or in `Handler` cross-checks that `repository.owner.login` (used to pick the verifying secret) equals the owner segment of `repository.full_name` (used to pick the acted-upon repository).

This breaks the trust binding: **organization authenticated (via `repository.owner.login` → selected `webhook_secret`) ≠ repository actually written (via `repository.full_name` → `Repository.from_github_repo_name`)**.

### Impact Explanation
An administrator of one Shipit-registered GitHub organization ("Org A", with its own installed GitHub App and `webhook_secret`) can craft an arbitrary webhook payload, set `repository.owner.login = "org-a"` and `organization.login = "org-a"` so the signature check selects and passes with Org A's secret, but set `repository.full_name = "org-b/victim-repo"`. This payload is accepted (`head(:ok)`) and dispatched to handlers, e.g. `PushHandler`, which will look up Org B's stacks and invoke: [5](#0-4) 
This lets an entity with no relationship to Org B trigger `stack.sync_github(expected_head_sha:)` (and, depending on other registered handlers sharing the same `repository_name` lookup, forge commit statuses or check-suite results) against a stack it does not own — a cross-repository/cross-tenant write. If a forged/replayed SHA or status can influence CI-gated automatic deploys, this can escalate to an unauthorized deploy on Org B's stack.

### Likelihood Explanation
Exploitability requires the attacker to control a legitimately configured Shipit-tenant organization's own `webhook_secret` — i.e., multi-org Shipit deployments where several independent organizations are configured (a documented, supported configuration in `docs/setup.md`/README). Within that documented deployment model, no privileged Shipit session, GitHub App private key, or `api_clients_secret` is needed — only knowledge of one's own org's webhook secret, which any organization admin legitimately possesses. This is a realistic, unprivileged-relative-to-the-victim-org attack path.

### Recommendation
Cross-validate that the owner used to select the verifying `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` (and any other repository-identifying field consumed by handlers) before dispatching to handlers. Alternatively, derive the repository/stack lookup used by handlers from the same verified owner value rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit is configured with two orgs, `org-a` and `org-b`, each with a distinct GitHub App and `webhook_secret` (per `docs/setup.md` multi-org example).
2. Attacker administers `org-a`'s GitHub App and knows `org-a`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<some sha present in org-b/victim-repo>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
4. Signature is computed with `org-a`'s `webhook_secret` over this exact body and sent as `X-Hub-Signature`.
5. `verify_signature` resolves `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, and successfully verifies the signature.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, unaffiliated with `org-a`, and enqueues `stack.sync_github(expected_head_sha: params.after)` on Org B's stack — a write triggered by an entity with no authorization over Org B's repository.
