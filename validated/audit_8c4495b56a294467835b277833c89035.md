The underlying vulnerability is real, though the exact attack sequence in the question needs a small correction to actually work.### Title
Unpaginated GitHub comments fetch allows attacker to hide dispute comments and trigger wrongful auto-close - ([File: scripts/auto-close-duplicates.ts])

### Summary
`autoCloseDuplicates` fetches an issue's comments via `githubRequest<GitHubComment[]>(/repos/${owner}/${repo}/issues/${issue.number}/comments)` with no `per_page`/`page` parameters, so GitHub returns only the first 30 comments by default. Both the bot-dupe-comment detection (`dupeComments`) and the post-dupe dispute detection (`commentsAfterDupe`) operate on this same truncated array, so any comment beyond position 30 is invisible to the script.

### Finding Description
In `autoCloseDuplicates`, comments are fetched once per issue with no pagination loop, unlike the issue-listing fetch a few lines above it which explicitly paginates with `per_page=${perPage}&page=${page}` [1](#0-0)  The comments fetch has no such parameters: [2](#0-1) 

That same 30-item `comments` array is used both to find the bot's "possible duplicate" comment (`dupeComments`, lines 164-181) and to compute `commentsAfterDupe` — the check that gates auto-close by verifying no activity occurred after the bot's dupe comment: [3](#0-2) 

Note on the exact attacker sequence in the question: flooding *before* the bot's dupe comment pushes the bot comment itself off page 1, so `dupeComments` would be empty and the script would `continue` at line 174-179 without closing anything — that specific ordering is self-defeating. The exploitable ordering is: bot posts the "Found ... possible duplicate" comment early (while the issue still has <30 comments) → attacker (or anyone, since GitHub issue comments require no special privilege) posts 30+ filler comments *after* the bot's dupe comment → a genuine dispute/objection comment is posted after the flood, landing beyond position 30. Because `comments` is capped at 30, `commentsAfterDupe` fails to include the real dispute, `commentsAfterDupe.length === 0` evaluates true, and the script proceeds to reactions-check and then calls `closeIssueAsDuplicate`, closing the issue despite the live objection [4](#0-3) 

No existing check (allowlist, pagination, comment-count validation) mitigates this, since the script simply trusts the single-page response as the full comment history.

### Impact Explanation
This causes an automation side effect (issue auto-close with `state_reason: 'duplicate'` and a `duplicate` label) that does not reflect true current issue state, silencing a legitimate objection/dispute after a bot's duplicate-detection comment. This is a logic/automation-integrity bug in repository maintenance tooling — it does not compromise Claude Code's execution sandbox, secrets, or approval flow, but it is a real automation correctness bug: unprivileged GitHub users can manipulate a maintenance bot into taking an incorrect, disruptive administrative action (closing an issue) purely through issue comments.

### Likelihood Explanation
Feasible and repeatable: any GitHub user able to comment on an issue (the issue author disputing their own "duplicate" label, or any third party) can post 30+ filler comments after the bot's detection comment. This requires no elevated privilege, no leaked credentials, and no social engineering — only ordinary comment-posting ability on a public issue tracker. The 3-day window before the script considers a dupe-comment "old enough" (line 189) gives ample time to post the flood.

### Recommendation
Paginate the comments fetch identically to the issues fetch: loop with `per_page=100&page=${page}` until an empty page is returned, accumulating all comments before running `dupeComments`/`commentsAfterDupe` filtering, mirroring the pattern already used for `allIssues` at lines 118-141.

### Proof of Concept
Integration test plan:
1. Mock `githubRequest` for the comments endpoint to return comments split across two pages of 30 (page 1) and 10 (page 2), where a bot "possible duplicate" comment is within page 1 and a dispute comment (non-bot, posted after the bot comment) is on page 2.
2. Run `autoCloseDuplicates` (or an extracted/testable version of its comment-processing logic) against this mocked issue.
3. Assert that with only page 1 fetched (current behavior), `commentsAfterDupe.length === 0` and `closeIssueAsDuplicate` is invoked — demonstrating the bug.
4. After adding pagination to the comments fetch, assert `commentsAfterDupe.length === 1` (the dispute comment is found) and `closeIssueAsDuplicate` is NOT invoked.
