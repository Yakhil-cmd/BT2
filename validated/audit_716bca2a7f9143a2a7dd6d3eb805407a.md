### Title
Webhook signature is authenticated against the payload's `organization`/`repository.owner.login`, but every event handler dispatches work against the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations on one instance, each with its own GitHub App and `webhook_secret` (documented in `docs/setup.md`, "Using Multiple Github Applications"). The webhook signature check selects *which* organization's secret to verify against using one field of the JSON body, while the handlers that actually act on the event use a *different, independently attacker-controlled* field of the same body to decide which `Stack`/`Repository` to operate on. Because HMAC verification covers the raw bytes but not any semantic consistency between these two fields, a sender who legitimately knows the secret for *any* one configured organization can forge events that are processed as if they came from a *different* organization's repository.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` is only used to look up which app config (and thus which `webhook_secret`) to HMAC-verify the raw body against.

Once the signature check passes, every event `Handler` resolves the target stacks from a *different* field of the same payload: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`Repository.from_github_repo_name` splits `full_name` on `/` to find the owner/name pair: [4](#0-3) 

Nothing enforces that `repository.owner.login` (used to pick the verification secret) equals the owner portion of `repository.full_name` (used to pick the stacks that are acted on). Since the whole JSON body is attacker-supplied, these two values can be set independently in a single forged request. `PushHandler`, which inherits `stacks` from `Handler`, then enqueues a resync against whatever `Stack` matches the forged `full_name`: [5](#0-4) 

The bound "binding" that should hold but doesn't is:
`organization authenticated by HMAC (repository.owner.login / organization.login)` == `repository actually written to (repository.full_name used by every Handler)`

### Impact Explanation
On a multi-organization Shipit deployment (a documented, in-scope configuration - `docs/setup.md`, "Using Multiple Github Applications"), an attacker who legitimately controls one configured organization's GitHub App/webhook secret can compute a valid `X-Hub-Signature` for their own org while setting `repository.full_name` (and other event fields such as `ref`, `after`, commit `sha`, or `state`) to reference a stack belonging to an *entirely different, victim organization* on the same instance. Because `PushHandler`, `StatusHandler`, and `CheckSuiteHandler` all inherit the same `stacks`/`repository_name` resolution logic, this allows an out-of-tenant actor to:
- Force `GithubSyncJob` runs and toggle `mark_as_accessible!`/`mark_as_inaccessible!` state on a victim's stack (`app/jobs/shipit/github_sync_job.rb`).
- Inject forged `status`/`check_suite` completion signals against a victim commit, which is the mechanism Shipit's continuous-delivery gating relies on to decide whether a stack is `deployable?` and to `trigger_continuous_delivery` (see `test/unit/shipit_deployment_checks_test.rb` and the continuous delivery / status-check gating described in the README). Forging a passing status can push a victim stack's continuous-delivery pipeline to deploy a commit that has not actually passed its real CI checks - an unauthorized deploy.

This crosses the "organization authenticated versus the repository written" trust boundary called out in scope, and its worst-case consequence (forcing an unauthorized deploy via forged CI status on a different org's stack) meets the Critical impact bar.

### Likelihood Explanation
Likelihood is **Low-to-Medium**: exploitation requires the attacker to be a legitimate, valid holder of a `webhook_secret` for at least one of the organizations configured on the shared Shipit instance (an unprivileged-w.r.t.-Shipit actor, since owning/administering one tenant's own GitHub App is not the same as having any privilege over other tenants). This is only reachable when the operator uses the multi-organization configuration; single-organization deployments are not exploitable this way because there is only one possible `repository_owner`/secret to begin with.

### Recommendation
After signature verification succeeds, derive the organization that authorized the request from the *same* field(s) used to resolve the acted-upon repository (`repository.full_name`), or explicitly validate that `repository.owner.login`/`organization.login` (the value used to select the verification secret) matches the owner segment of `repository.full_name` (and of `organization`/`team` payloads for the `Organization`-scoped events) before dispatching to any `Handler`. Reject the webhook if they disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` and `attacker-org`, each with its own GitHub App and `webhook_secret` (as per `docs/setup.md`).
2. As an administrator of `attacker-org`'s legitimate GitHub App, craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha, e.g. an old/reverted commit that already exists on victim-org/target-repo>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/target-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org webhook_secret, body)>` and POST it to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), and the signature validates successfully against `attacker-org`'s secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name('victim-org/target-repo')`, triggering `sync_github` on `victim-org`'s stack(s) despite the request never being authenticated by `victim-org`'s credentials.
6. The same technique applies to `status`/`check_suite` handlers to inject forged CI-passing signals against `victim-org/target-repo` commits, potentially triggering continuous-delivery auto-deploys.
