### Title
Webhook signature verified against attacker's own GitHub org, but event handlers act on an unrelated `repository.full_name` from the same payload — cross-organization stack takeover ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This maps the "value used to satisfy the trust check ≠ value used to perform the privileged action" class from the Suzaku report (where `elapsedEpochs`/the divided value was decoupled from the amount actually credited) onto Shipit's webhook signature verification: the field used to select **which secret verifies the signature** (`repository.owner.login` / `organization.login`) is different from the field the event **handlers actually act on** (`repository.full_name`), and only the multi-org deployment binds these two fields to different trust domains.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/org config — and thus the HMAC secret — using a value taken straight from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (with an `organization.login` fallback), and it is used to look up the org-scoped app config through `Shipit.github(organization: repository_owner)`: `github_app_config(organization)` does `secrets.github.deep_transform_keys(&:downcase)[organization.downcase.to_sym]`. [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps, one per organization, each with its **own independent `webhook_secret`**: [4](#0-3) 

Once the signature check passes (using whichever org's secret matched `repository_owner`), the raw payload is handed to every registered handler for the event, unfiltered by that organization: [5](#0-4) 

But the handlers do **not** use `repository.owner.login`/the verified organization to select the target — they resolve the affected `Stack`/`Repository` from `repository.full_name`, a sibling field in the same JSON body: [6](#0-5) [7](#0-6) [8](#0-7) 

Because `repository_owner` and `repository.full_name` are independent JSON keys with no cross-validation, an attacker who legitimately controls one org (e.g. installed the Shipit GitHub App on `attacker-org`, and thus knows `attacker-org`'s `webhook_secret`) can craft a webhook body where:
- `repository.owner.login` = `attacker-org` (so the signature check passes with the attacker's own known secret), and
- `repository.full_name` = `victim-org/victim-repo` (an unrelated repository/stack that Shipit also tracks under a *different* installation).

The equality this breaks is: **verified-organization == acted-upon-repository**. Before the attack, both fields point to the same org for any legitimate GitHub-originated webhook. After the attacker's crafted POST, `verified-organization = attacker-org` while `acted-upon-repository.owner = victim-org`, yet the request still passes `verify_signature` because the check only cares that *some* known org's secret matches, not that it matches the org that owns the repository being mutated.

Downstream impact depends on handler: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on the victim's stack — forcing Shipit to fetch/sync arbitrary attacker-supplied `after` SHAs into the victim's deployable history; `pull_request` handlers can archive/unarchive review stacks, or update stored PR state, for a victim repository based on a forged, attacker-authored PR payload. This is a genuine analog of "the entity that authenticated is not the entity being written to" — matching the rule's "an organization that authenticated versus the repository that is written" bullet.

### Impact Explanation
An attacker who has installed/controls one legitimate GitHub App organization on the shared Shipit instance (a very low bar in any multi-tenant Shipit deployment using the documented "Using Multiple Github Applications" configuration) can forge webhook events that are accepted as authentic and are then applied to **stacks belonging to a different organization** they do not control, because the acted-upon `repository.full_name` is never checked against the organization whose secret satisfied the signature. This allows cross-repository writes to review-stack state (`archive!`/`unarchive!`) and forces `GithubSyncJob`s with attacker-chosen `expected_head_sha` against a victim's stack — matching the "cross-repository writes" Critical-impact bucket in the rules.

### Likelihood Explanation
Exploitability requires only that the attacker's own organization is one of the configured GitHub App installations on the target Shipit instance (a normal, low-privilege state for any org onboarded to a shared/multi-tenant Shipit deployment, as explicitly documented in `docs/setup.md`'s "Using Multiple Github Applications" section). No repository write access, API token, or session is needed — only the ability to know/derive one's own org's `webhook_secret` (which the org's own GitHub App admin already has) and send a crafted HTTP POST to `/webhooks`.

### Recommendation
After `verify_signature` selects the org/secret from `repository_owner`, re-validate that every repository-identifying field consumed by handlers (`repository.full_name`, `repository.owner.login`) actually belongs to that same verified organization before dispatching to `Shipit::Webhooks.for_event(event)`. Alternatively, bind the resolved `Stack`/`Repository` lookups in `Handler#stacks` to the organization that was cryptographically verified, rejecting any payload where `repository.full_name`'s owner segment does not match `repository_owner`.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `attacker-org` and `victim-org`, per `docs/setup.md`'s multi-app schema (this is the officially documented supported configuration, not a hypothetical misconfiguration).
2. Attacker, who administers the `attacker-org` GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body: `{"ref": "refs/heads/master", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over this exact raw body, per `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature` logic.
5. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`), and the signature verifies successfully.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on the victim's stack, even though the request was never authenticated by `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
