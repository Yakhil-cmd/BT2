### Title
Commit authorship spoofing via forged `Merge-Requested-By` trailer in non-Shipit-initiated commits - (File: `app/models/shipit/user.rb`)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` treats the `Merge-Requested-By: <login>` commit-message trailer as authoritative proof of authorship for *any* commit synced by `GithubSyncJob`, regardless of whether that commit actually went through Shipit's own merge-queue flow. Anyone who can push a commit to a branch tracked by a Shipit stack (e.g., a repo they own that is registered as a stack) can embed this trailer to attribute the commit to an arbitrary existing GitHub login.

### Finding Description
The broken binding: `commit.author == <the user who wrote/approved this commit>` is expected, but the code actually establishes `commit.author == <any login string an attacker places after "Merge-Requested-By:" in the commit body>`.

Code path:
- `GithubSyncJob#append_commit` calls `stack.commits.create_from_github!(gh_commit)` [1](#0-0) 
- `Commit.create_from_github!` → `Commit.from_github` calls `User.find_or_create_author_from_github_commit(commit)` [2](#0-1) 
- `find_or_create_author_from_github_commit` matches the commit message against `MergeRequest::MERGE_REQUEST_FIELD` and, on match, unconditionally calls `find_or_create_by_login!(match_info[1])`, which trusts a raw substring of the commit body: [3](#0-2) 
- `find_or_create_by_login!` fetches (or creates) the `Shipit::User` for that login via `Shipit.github.api.user(login)` — this only proves the login exists on GitHub, not that the named user authored/approved this specific commit: [4](#0-3) 

The `MERGE_REQUEST_FIELD` trailer is legitimately produced by Shipit itself when it performs a merge through its own merge-queue (`MergeRequest#merge_message`), where `merge_requested_by` is set from an authenticated Shipit session: [5](#0-4) . However, `find_or_create_author_from_github_commit` has no way to distinguish a trailer Shipit itself wrote during a merge it performed from an identical trailer that any repo contributor typed by hand into an ordinary commit message before pushing. The existing test suite confirms the naive trust: a commit fixture with `"...\n\nMerge-Requested-By: walrus\n"` is asserted to bind `commit.author` to that user with no other authentication evidence [6](#0-5) , and a second test only covers the "missing user" fallback path [7](#0-6) .

Attacker request: push a commit with message body `Merge-Requested-By: some-admin-login\n` to a branch tracked by a Shipit stack the attacker controls (their own repo/fork registered as a stack), then trigger (or wait for) the corresponding GitHub push webhook, which enqueues `GithubSyncJob` and reaches the vulnerable code with no further checks. No `verify_signature`/`GitHubApp#verify_webhook_signature` guard is relevant here because the webhook itself is legitimately signed for the attacker's own repository — the signature only proves the payload came from GitHub for that repo, not that the embedded commit-message content is trustworthy.

### Impact Explanation
Every commit synced for the attacker-controlled stack can carry a forged `commit.author`, mis-attributing authorship to any existing GitHub login the attacker names, without that user ever interacting with the push. This value is persisted in the `Commit` record and, downstream, is used to construct the `SHIPIT_USER`/`GIT_COMMITTER_NAME` environment for deploy commands via `TaskCommands#env` (`@task.author`, `@task.user`) [8](#0-7) . I was not able to fully trace, within the available tool budget, whether `Task#author`/`Task#user` is always derived from `Commit#author` for every task type (e.g., automatic deploys), so I cannot definitively confirm every deploy-time consequence; this should be verified directly in `app/models/shipit/task.rb`. What is confirmed by code and tests is the core integrity break: `Commit#author` is bound to attacker-chosen data rather than to a verified identity, blast radius limited to the stack(s) the attacker controls (their own repo), not cross-tenant.

### Likelihood Explanation
Preconditions are modest: the attacker needs push access to a branch of a repository that is registered as a Shipit stack — per the given attacker model this includes "a repository they own," which can legitimately be onboarded as a Shipit stack. No Shipit secrets, session, or API token are required; the webhook is genuinely signed by GitHub for that repo. Cost is a single crafted commit message; the exploit is trivially repeatable against every commit pushed to that stack.

### Recommendation
Only honor the `Merge-Requested-By` trailer when the commit is verified to have been produced by Shipit's own merge process (e.g., match the merge commit against a known `MergeRequest#head`/`merge_commit` record and its `merge_requested_by`, rather than re-parsing arbitrary commit message text supplied by GitHub). Do not treat free-form commit body content as an identity assertion for regular (non-merge-queue) pushes synced by `GithubSyncJob`.

### Proof of Concept
minitest plan (extends `test/models/commits_test.rb` pattern):
```ruby
test '.create_from_github does not trust a forged Merge-Requested-By trailer on a directly-pushed commit' do
  admin = shipit_users(:walrus) # exists locally/on GitHub, never involved in this push
  @stack.commits.create_from_github!(
    resource(
      sha: 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef',
      author: { login: 'attacker' },
      committer: { login: 'attacker' },
      commit: {
        author: { name: 'attacker', email: 'a@a.com', date: Time.now },
        committer: { name: 'attacker', email: 'a@a.com', date: Time.now },
        message: "innocuous change\n\nMerge-Requested-By: walrus\n"
      }
    )
  )
  commit = Commit.last
  # Broken binding demonstrated: commit.author == admin, even though no
  # GitHub authentication event (session, OAuth, or merge-queue action)
  # ties `walrus` to this push.
  assert_equal admin, commit.author
end
```
Both sides of the equality to assert: `commit.author.login` (attacker-controlled trailer value) vs. the identity that actually pushed/authored the commit (`attacker`, from `commit.author`/`commit.committer` payload fields) — these diverge, confirming the spoof.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
