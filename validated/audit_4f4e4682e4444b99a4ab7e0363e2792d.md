### Title
Webhook signature verification selects the GitHub App by an unverified `repository.owner.login` field, allowing cross-organization/repository event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook's HMAC signature against by reading `repository_owner`/`organization.login` straight out of the same untrusted, unverified JSON body whose signature it is about to check. In a multi-organization Shipit deployment, each configured GitHub org has its own distinct `webhook_secret`. The binding that must hold is: *the organization whose secret validated the signature* == *the organization/repository that the payload's handlers subsequently act on*. Because both values come from the same attacker-suppliable body, an actor who legitimately knows (or controls) one configured org's `webhook_secret` can craft a payload that is signed correctly for that org, while setting `repository.full_name` / commit `sha` to point at a completely different, victim stack tracked by the same Shipit instance.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
before_action :check_if_ping, :drop_unhandled_event, :verify_signature
...
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is parsed from `request.raw_post`, i.e. the very body whose authenticity is being checked. It is used only to pick *which* `GithubApp`/`webhook_secret` object performs the HMAC comparison:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

Each configured GitHub organization is expected to have its own independent `webhook_secret`, as shown by the multi-org secrets template: [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the same body to event handlers, which act on the payload's own `repository`/`sha`/`state` fields without re-validating that the org that authenticated matches the org/stack that owns the repository being mutated:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

For example, the `status` handler creates a `Status` record directly from payload fields (`sha`, `state`, `target_url`, `description`, `context`) merged with `repository` fields taken from the body, with no check that the repository named in the payload belongs to the organization whose secret validated the signature: [5](#0-4) 

The push handler similarly enqueues `GithubSyncJob` keyed off `params['repository']['full_name']`: [6](#0-5) 

This breaks the equality that should hold:
`organization authenticated by verify_signature (repository_owner in payload)` == `organization/repository that the dispatched handler actually writes to (repository.full_name / sha in the same payload)`

Because both sides are read from the same attacker-controlled body, an attacker only needs to know **any one** configured org's `webhook_secret` (e.g. their own low-privilege org onboarded to the same multi-tenant Shipit instance) to forge a validly-signed request while pointing the acted-upon repository/commit fields at a **different, victim** org's stack.

### Impact Explanation
By forging a `status` webhook that is HMAC-signed with a `webhook_secret` the attacker legitimately possesses (for their own configured org) but whose `sha`/`repository` fields target a victim stack's commit, an attacker can inject fabricated commit statuses (e.g. mark CI as `success`) for commits they do not control. `MergeRequest#all_status_checks_passed?`/`reject_unless_mergeable!` and `Commit#deployable?` rely on these `Status` records to gate the merge queue and deploy eligibility (`app/models/shipit/merge_request.rb`, `Commit#deployable?`), so forged green statuses can enable an **unauthorized merge/deploy** of a commit that never actually passed CI on the victim repository — meeting the High/Critical impact bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires the attacker to be an unprivileged external actor with respect to the victim stack, but to have legitimate knowledge of at least one `webhook_secret` configured on the same shared Shipit instance (realistic in a multi-tenant setup such as `secrets_double_github_app.yml`, where different teams/orgs each configure their own GitHub App/secret against one shared engine). No Shipit session, `ApiClient` token, or repository write access on the victim repo is needed — only the ability to POST an HTTP request with a correctly computed HMAC to the public `/webhooks` endpoint.

### Recommendation
After selecting the GitHub App/secret via `repository_owner`, cross-validate that the resulting `repository.owner.login` (and any repository identifiers used by downstream handlers, e.g. `repository.full_name`) actually belongs to the Shipit-configured organization that produced a valid signature — reject the payload if the authenticated organization's own known repositories don't match the repository being referenced (or bind org-to-repo association at configuration/installation time rather than trusting the payload body for routing).

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` and `OrgVictim`, each with a distinct `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker legitimately administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha tracked under OrgVictim/repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgVictim/repo"}
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` reads `repository_owner` → `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the signature successfully (since it was computed with `OrgA`'s real secret).
6. `create` dispatches the payload to the status handler, which creates/updates a `Status` for the sha under `OrgVictim/repo`, marking it as CI-passing even though the attacker never had access to `OrgVictim`.
