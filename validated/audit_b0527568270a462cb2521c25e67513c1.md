### Title
Cross-organization webhook signature confusion allows forged push events to trigger `GithubSyncJob` on another organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App / HMAC secret to validate a webhook using only `params.dig('repository','owner','login')`, while the handler that actually mutates state (`PushHandler#process` via `Handler#repository_name`) resolves the target `Stack` using `params.dig('repository','full_name')`. Because these two values are read independently from the same attacker-controlled JSON body and never cross-checked, an attacker who controls any organization configured in `Shipit.github` (and thus knows its `webhook_secret`) can forge a payload whose `repository.owner.login` matches their own org (so the signature check passes) but whose `repository.full_name` names a stack belonging to a different organization, causing `stack.sync_github` to run against that victim stack.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never enforces:
`organization_that_authenticated_the_request (derived from repository_owner) == organization_that_owns_the_mutated_stack (derived from repository.full_name)`.

- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against `request.raw_post` using that org's `webhook_secret`: [1](#0-0) 
- `repository_owner` is read purely from the JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [2](#0-1) 
- After signature verification, `#create` re-parses the same `raw_post` and dispatches to registered handlers with the parsed JSON: [3](#0-2) 
- `Handler#repository_name` reads a *different* field of the same payload: `payload.dig('repository', 'full_name')`, and `#stacks` resolves via `Repository.from_github_repo_name(repository_name)`: [4](#0-3) 
- `PushHandler#process` then updates every non-archived stack on the matching branch by calling `stack.sync_github(expected_head_sha: params.after)`: [5](#0-4) 

Nothing in this path checks that `repository.owner.login` (used for authentication) is consistent with `repository.full_name` (used for stack resolution). `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a DB lookup: [6](#0-5) 

Exploit flow: attacker owns OrgA in GitHub and has a Shipit-configured GitHub App for OrgA (`Shipit.github(organization: 'OrgA')`), knowing OrgA's `webhook_secret` (it's their own secret — no privileged Shipit access is required to know it). They construct a JSON payload with `repository.owner.login = 'OrgA'` and `repository.full_name = 'OrgB/private-repo'`, sign it with OrgA's `webhook_secret`, and POST it to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` and the HMAC verifies successfully because it's computed over the exact bytes the attacker controls with a secret the attacker owns. `PushHandler` then resolves the stack via `full_name = 'OrgB/private-repo'` and invokes `stack.sync_github(expected_head_sha: ...)` on the OrgB stack, an organization that never authenticated this request.

Existing guards that were checked and do not prevent this: `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema in `PushHandler` only requires `ref` and `after` — it does not require or validate `repository.owner.login` against `repository.full_name`; `check_if_ping` is unrelated; there is no `Repository` or `Stack` validation that ties incoming webhook org to stored repository owner at request time — that check exists only for outbound API calls (`Repository#github_app` uses `Shipit.github(organization: owner)`), not for inbound authentication.

### Impact Explanation
An attacker who operates any GitHub organization onboarded to a multi-org Shipit instance can force `GithubSyncJob` to run against an arbitrary victim stack under a different organization, using only credentials for their own org. `GithubSyncJob#perform` (triggered by `sync_github`) fetches commits via the real GitHub API for the victim's actual repository (using the victim org's own GitHub App/token, since `Stack#github_api`/`Repository#github_app` resolve credentials from the stored repository owner) and appends them to the stack, which can also feed into continuous deployment scheduling if `continuous_deployment` is enabled. This is a cross-tenant state mutation: a payload authenticated only by OrgA's secret produces a write against OrgB's stack — matching the "payload for one repository mutating another's stack, commit... or an unauthorized deploy" Critical impact category. The attack is repeatable against any stack/organization pair configured in the same Shipit instance and costs the attacker nothing beyond owning one onboarded organization.

### Likelihood Explanation
Preconditions: a Shipit instance configured with the multi-organization `Shipit.github` config (`github_app_config`/`TOP_LEVEL_GH_KEYS` fallback logic) hosting at least two organizations with distinct `webhook_secret`s, one of which the attacker legitimately controls (their own GitHub org with the Shipit GitHub App installed) and one victim organization with a private stack. This is a realistic and commonly documented Shipit deployment pattern (multi-org support exists explicitly in `lib/shipit.rb`'s `github_app_config`/`github_organizations`). The attacker needs zero Shipit privileges — just their own org's webhook secret, which they legitimately possess as the org's admin — and can send the crafted HTTP request directly to `/webhooks` from the public internet. No GitHub interaction (real push) is even required since the controller only re-parses `raw_post`.

### Recommendation
In `verify_signature` (or immediately after, before dispatch), require that `repository.owner.login`/`organization.login` used to select the webhook secret matches the owner segment of `repository.full_name` in the same payload, rejecting (422) any mismatch. Additionally/alternatively, `Handler#repository_name` and all its consumers (`PushHandler`, pull_request handlers, etc.) should re-derive the owning organization from the authenticated `repository_owner` rather than trusting `repository.full_name` independently, or the controller should pass the already-authenticated organization down to handlers so they can assert consistency before mutating any `Stack`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb

test "cross-organization signature confusion must not sync a different org's stack" do
  # Preconditions: two orgs configured with distinct webhook secrets
  Shipit.stubs(:github_app_config).with('orga').returns(webhook_secret: 'orga-secret')
  Shipit.stubs(:github_app_config).with('orgb').returns(webhook_secret: 'orgb-secret')

  victim_repo = Repository.create!(owner: 'orgb', name: 'private-repo')
  victim_stack = Stack.create!(repository: victim_repo, branch: 'main')

  body = {
    ref: 'refs/heads/main',
    after: 'deadbeef',
    repository: { owner: { login: 'orga' }, full_name: 'orgb/private-repo' }
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'orga-secret', body)

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = signature

  # Binding under test:
  #   authenticating_org (from repository.owner.login) == "orga"
  #   mutated_stack_owner (from repository.full_name)   == "orgb"
  # These must be equal for the request to be legitimate; here they diverge.

  Shipit::Stack.any_instance.expects(:sync_github).never
  # OR, to demonstrate the vulnerable behavior on unpatched code:
  # Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: 'deadbeef')

  post :create, body: body, as: :json

  assert_response :ok # request accepted using orga's secret
  # After fix: victim_stack must NOT have been synced despite 200 response.
end
```
Assert on both sides: capture `repository_owner` (org that authenticated) inside `verify_signature` via a stub/spy, and capture the stack acted on inside `PushHandler#process` (or assert `Stack#sync_github` invocation target); the test fails pre-fix because `sync_github` fires on `orgb`'s stack despite authentication only against `orga`'s secret, and passes post-fix once the owner/full_name consistency check is added.
