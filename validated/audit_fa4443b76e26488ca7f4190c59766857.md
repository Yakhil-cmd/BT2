### Title
Unauthenticated SSE stream of stack update events via unguarded `/events` mount - (File: config/routes.rb)

### Summary
The engine mounts `Pubsubstub::StreamAction` at `/events` directly in `config/routes.rb` with no `before_action :force_github_authentication` guard, and the engine ships no working `UserRequiredMiddleware` (only a stale comment references one). Any unauthenticated request to `GET /events?channels[]=stack.<id>` reaches `Pubsubstub::StreamAction` and can subscribe to `stack.<id>` broadcast events without any session or credential.

### Finding Description
Binding claimed: `force_github_authentication gated this mount == true`. Actual value: `false`.

`config/routes.rb` declares `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [1](#0-0) , at the top level of the engine's route set, outside any controller that includes `Shipit::Authentication`. `Shipit::Authentication#force_github_authentication` is a controller `before_action` mixed into `ShipitController` (and thus `StacksController`, etc.) [2](#0-1) , and `ShipitController` explicitly includes it [3](#0-2) . `Pubsubstub::StreamAction` is a Rack app mounted via `mount`, not a Rails controller action, so it never runs through any `Shipit::Authentication` before_action — Rails' `before_action` mechanism only applies within controllers that include the concern.

The only reference to protection for `/events` is a stale code comment in `GithubAuthenticationController#callback`: "We need to set this so that the /events and /sidekiq endpoint which leverage `UserRequiredMiddleware` will recognize the user is authenticated" [4](#0-3) . A repo-wide search finds no `UserRequiredMiddleware` class definition anywhere in this engine — the only occurrence of the string is that comment. There is no `app.middleware.use` registration for any such class in `lib/shipit/engine.rb`'s initializer, which only conditionally registers `OmniAuth::Builder` and `Shipit::SameSiteCookieMiddleware` [5](#0-4) . So the guard the comment describes does not exist in this engine's own code.

`Stack#broadcast_update` publishes to channel `"stack.#{id}"` on every update: `Pubsubstub.publish("stack.#{id}", { id:, updated_at: }.to_json, name: 'update')` [6](#0-5) , triggered via `after_commit :broadcast_update, on: :update` [7](#0-6) , and commit/status/deploy updates delegate to the same `broadcast_update` [8](#0-7) [9](#0-8) . Stack IDs are small sequential integers, and views expose the channel name directly to any viewer via `subscribe events_path(channels: ["stack.#{@stack.id}"])` [10](#0-9) , making channel names trivially guessable/enumerable (`stack.1`, `stack.2`, ...).

Attacker request: `GET /events?channels[]=stack.1` (no cookie, no auth header) — reaches `Pubsubstub::StreamAction` directly and, if the gem's own action doesn't independently enforce app-level auth (it doesn't; it's a generic reusable SSE engine unaware of Shipit's session model), establishes a live SSE stream of every `update` event for stack 1's lifecycle (deploys starting/finishing, lock changes, commit/status changes) without ever going through `force_github_authentication`, `current_user.authorized?`, or the `Shipit.github_teams` check.

None of the existing guards apply: `force_github_authentication` never executes because `StreamAction` isn't a `ShipitController`; `Shipit::SameSiteCookieMiddleware` only manages cookie attributes, not authorization; there's no rack middleware doing auth on this path; `UserRequiredMiddleware` doesn't exist in the codebase.

### Impact Explanation
An unauthenticated attacker who knows or guesses a numeric stack ID gets a live feed of that stack's update events — deploy state changes, lock/unlock, archive state, commit/status updates — bypassing the "must be a member of `Shipit.github_teams`" restriction that gates every other view in this application. This is a read-only information disclosure (not RCE, not credential exfiltration, not cross-tenant mutation), matching the High severity category "unauthenticated read of stack state, task streams or deploy output." It is trivially repeatable across every stack ID in the installation (sequential IDs), so blast radius covers all tenants/stacks hosted by the instance, though the leaked payload itself is limited to `{id, updated_at}` plus the fact that an `update` event fired — not full deploy output or secrets.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host and knowledge/guessing of a stack ID (trivial due to sequential integer IDs and the ID being embedded in every stack's own path/HTML for authenticated users, and leakable via referrers, logs, or shared links). No Shipit or GitHub secret, session, or team membership is required. Cost to the attacker is a single unauthenticated HTTP GET; the finding is fully repeatable and requires no race condition or timing.

### Recommendation
Wrap the `/events` mount with the same authentication guard as the rest of the app — e.g., require a valid Shipit session before allowing the SSE subscription (a small Rack middleware or a controller action that checks `session[:user_id]`/`session[:authenticated]` and delegates to `Pubsubstub::StreamAction` only if authenticated), and additionally scope which channels a given session is allowed to subscribe to (verify the user is authorized for the specific `stack.<id>` requested) rather than trusting the client-supplied `channels[]` param.

require 'test_helper'

module Shipit
  class EventsEndpointTest < ActionDispatch::IntegrationTest
    test "GET /events without a session is not authenticated and still reaches Pubsubstub" do
      stack = shipit_stacks(:shipit)

      # No session cookie set at all (unauthenticated attacker)
      get "/events", params: { channels: ["stack.#{stack.id}"] },
          headers: { 'Accept' => 'text/event-stream' }

      # Binding under test: force_github_authentication gated this mount == true
      # Reality: no redirect to github_authentication_path, no 401/403
      refute_equal 302, response.status
      refute_equal 401, response.status
      refute_equal 403, response.status

      # Request was handed to Pubsubstub::StreamAction, not rejected by Shipit::Authentication
      assert_includes [200, 200 .. 299], response.status if response.status
    end
  end
end

module Shipit
  module Authentication
    extend ActiveSupport::Concern

    included do
      before_action :force_github_authentication
      helper_method :current_user
    end

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
