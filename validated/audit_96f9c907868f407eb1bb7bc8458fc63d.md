### Title
Webhook signature verification is bound to `repository.owner.login`, but the mutation targets are looked up by attacker-controlled fields with no repository scoping — allowing cross-repository commit-status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate a request against using `repository_owner`, a value read directly out of the unauthenticated JSON body (`repository.owner.login` / `organization.login`). [1](#0-0) [2](#0-1)  Once the request is admitted, the event handler that actually mutates state does not re-validate that the payload belongs to the organization/repository whose secret was used. `Handlers::StatusHandler#process` looks up commits globally by `sha` with no repository or organization filter at all, then writes a CI status onto them. [3](#0-2)  This breaks the intended equality: *organization whose webhook signature was verified == organization/repository whose data is mutated*.

### Finding Description
The trust decision and the mutation are computed from two independent, uncorrelated inputs of the same attacker-controlled payload:

1. **Trust decision**: `verify_signature` picks the GitHub App/secret to check against using `repository_owner`, derived from `params.dig('repository','owner','login')` (fallback `organization.login`). [2](#0-1)  Verification itself is a no-op whenever that organization's `webhook_secret` is blank/unset: `verify_webhook_signature` returns `true unless webhook_secret`. [4](#0-3)  A blank/`nil` webhook secret per organization is an explicitly supported configuration shape in this engine (multiple orgs can be configured independently, each with or without a secret).

2. **Mutation target**: Once `Shipit::Webhooks.for_event(event)` dispatches to a handler, `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no join/filter against `Repository`, `Stack`, or the `repository_owner` that was used to select the signing secret. [3](#0-2)  `sha` is a global 40-hex string with no per-repository namespace, so any commit tracked anywhere on the Shipit instance can be targeted by supplying its SHA, independent of which organization's identity was used to pass the signature check.

Because organization A's `repository.owner.login` is what gates the signature check, but the handler acts on `sha` values that can reference commits belonging to organization B's repositories, an attacker who can produce (or bypass) a valid signature for **any single tracked organization** (e.g., one configured with an empty `webhook_secret`, a low-value/test org, or a leaked/guessable secret for one org among many) can forge `status` events that write arbitrary CI status (`state`, `context`, `description`) onto commits belonging to a **completely different, unrelated repository/stack** also hosted on the same Shipit instance.

This is the same bug class as the reported Oracle issue: a verification/consistency check is performed against one identity (`gcOracleId`/`repository_owner`), while the state-changing operation (`setNumRows`/`create_status_from_github!`) is applied using a different, unchecked identity (`oracleId`/arbitrary `sha` with no owner binding), violating an implicit cross-module invariant that other code relies on (that a verified webhook only affects the repository it claims to be from).

### Impact Explanation
`Status` records feed directly into a stack's required-CI-checks used to compute deployability (`required_statuses` / `blocking_statuses` are configured per stack from `deploy_spec`). [5](#0-4)  By forging a `status` webhook that sets a required context to `success` on a commit belonging to a victim's stack — using only the trust anchor of an unrelated, weakly-configured organization — an unauthenticated attacker can make a commit falsely appear to satisfy CI requirements. On stacks with `continuous_deployment` enabled, or where an operator/CI dashboard trusts the `success` state to greenlight a manual deploy, this can result in an unauthorized deploy of a commit that never actually passed CI, meeting the "unauthorized deploy" Critical-impact bar defined in scope.

### Likelihood Explanation
Exploitation requires no session, `ApiClient` token, or GitHub App private key — only the ability to produce a JSON body admitted by `verify_signature` for **any one** of the GitHub organizations configured on the target Shipit instance (trivial if that org has no `webhook_secret` set, which the code explicitly supports and treats as "always verified"). The rest of the exploit is a plain unauthenticated HTTP POST to `/webhooks` with a crafted `sha`, `state`, and `context`; no interaction with the actual victim repository or organization is needed at any point.

### Recommendation
- In `StatusHandler` (and any other handler that queries records without a repository scope), constrain lookups to the repository identified by the same `repository.full_name`/`repository.owner.login` used during signature verification, e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` scoped via `Repository.from_github_repo_name(repository_name)` as other handlers already do (`Handler#stacks`).
- Make `verify_signature`'s selected `repository_owner` an enforced, immutable binding carried through to every handler's data-access layer, instead of letting handlers independently re-derive scope from the same untrusted payload.
- Treat a blank/missing `webhook_secret` as a hard misconfiguration warning (or disallow it) rather than silently short-circuiting verification to `true`.

### Proof of Concept
1. Identify (or set up) one GitHub organization configured on the target Shipit instance with no `webhook_secret` (a supported configuration state per `lib/shipit/github_app.rb`'s `verify_webhook_signature`).
2. Obtain the `sha` of a commit belonging to a *different*, unrelated tracked repository/stack (commit SHAs are public on GitHub).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-with-no-secret" }, "full_name": "org-with-no-secret/some-repo" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "<required-ci-context-of-victim-stack>",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z"
}
```
4. `verify_signature` passes trivially (no secret configured for `org-with-no-secret`). [4](#0-3) 
5. `StatusHandler#process` finds the victim commit purely by `sha` (no repo/org check) and creates a forged `success` status on it. [3](#0-2) 

*Note*: I could not directly retrieve `app/models/shipit/commit.rb#create_status_from_github!` or the exact `deployable?` implementation within the tool budget available, so the precise mechanics of how a forged `Status` record flips `deployable?`/triggers continuous deployment are inferred from `deploy_spec.rb`'s `required_statuses`/`blocking_statuses` config surface and corroborating test files (`test/models/commits_test.rb`, `test/unit/shipit_deployment_checks_test.rb`) rather than confirmed line-by-line; a full Devin session with file access would be needed to pin down that exact chain end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
