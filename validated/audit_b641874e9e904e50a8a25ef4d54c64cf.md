### Title
Organization-fallback signature verifier selection allows cross-tenant forged `pull_request` webhooks to be accepted for repositories protected by a different org's secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the signing secret) used to authenticate a webhook via `repository_owner`, which falls back from `repository.owner.login` to `organization.login` when the former is absent [1](#0-0) . The handler that actually mutates state, `LabelCapturingHandler`, instead resolves the target repository/stack from the independent `repository.full_name` field [2](#0-1) . In a multi-organization deployment where at least one configured org has no `webhook_secret`, an attacker can craft a payload that verifies against the secret-less org while targeting a repository belonging to a different, secured org.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces: `repository_owner` (used to pick the verifying `GitHubApp`) should equal the owning org embedded in `repository.full_name` (used by the handler to locate the `Repository`/`Stack`). These are read from two independently attacker-controlled JSON fields.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [3](#0-2) .
2. In multi-org mode, `Shipit.github` looks up a per-organization config via `github_app_config(organization)`, and each `GitHubApp` carries its own `webhook_secret` [4](#0-3) [5](#0-4) .
3. `GitHubApp#verify_webhook_signature` returns `true unconditionally if webhook_secret is blank` [6](#0-5) , i.e. any payload with any (or no) signature passes for that org.
4. The attacker sends a `pull_request` webhook with `action: "unlabeled"`, omitting `repository.owner.login`, and setting `organization.login` to the org configured without a `webhook_secret`, while setting `repository.full_name` to `"secured-org/victim-repo"` — a repository belonging to a different org that *does* have a secret configured.
5. `verify_signature` resolves `repository_owner` = the secret-less org (fallback branch), so `verify_webhook_signature` returns `true` for an arbitrary/forged signature, and processing continues.
6. `LabelCapturingHandler` (matched by `Shipit::Webhooks.for_event('pull_request')`) is required to satisfy its `ExplicitParameters` schema, which only demands `repository.full_name` (not `owner.login`) [7](#0-6) , so the forged omission is schema-valid.
7. `repository` is resolved via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , pointing at the victim repo regardless of which org authenticated the request.
8. If `unlabeled_active_stack?` matches (stack present, not archived) and the stack already has a linked `pull_request` record, `capture_labels` persists `params.pull_request.labels.map(&:name)` onto that `PullRequest` [8](#0-7) .

None of the existing guards prevent this: `drop_unhandled_event` only checks the event name exists; `verify_signature`'s only failure mode is `GithubOrganizationUnknown` (unregistered org name), which does not trigger here because the attacker names a real, configured (but secret-less) org; the `ExplicitParameters` schema for `LabelCapturingHandler` does not require or cross-check `repository.owner.login` against `organization.login`; nothing in the controller or handler enforces that the org used for signature verification is the same org that owns the repository being mutated.

### Impact Explanation
An unauthenticated, unprivileged internet requester can write attacker-chosen label names into the `PullRequest.labels` of a review-stack `PullRequest` belonging to a completely different, secured organization's repository, as long as the multi-org deployment has one org (any org) configured without a `webhook_secret`. Because `ReviewStack#env` derives environment variables from these label names (uppercased), this is a payload-for-one-repository-affecting-another's-stack scenario, matching the "Critical: a payload for one repository mutating another's stack" category. The blast radius spans every repository/stack across every org configured under the same Shipit instance, not just repos belonging to the secret-less org — the only precondition is that the target stack has an existing linked pull request. This is repeatable per request with no rate limiting concerns relevant to the exploit itself.

### Likelihood Explanation
Requires: (a) a multi-organization `github:` secrets configuration (top-level keys are org names) — the single-org schema is not exploitable because `Shipit.github` ignores the `organization:` argument entirely when `github_default_organization` is nil [9](#0-8) ; (b) at least one configured org with `webhook_secret` unset (a documented, non-default but legitimate configuration state per `docs/setup.md` and `secrets_double_github_app.yml` fixtures which explicitly show `webhook_secret: # nil` per-org); (c) a target stack with an already-linked pull request. Given these preconditions, exploitation is a single unauthenticated POST with attacker-fully-controlled JSON and no valid signature required — cost and feasibility are trivial and fully repeatable.

### Recommendation
Derive the org used for signature-verifier selection from the same field the handler will use to resolve the target repository (i.e., parse the owner out of `repository.full_name`, not from a separately-provided `organization.login`/`repository.owner.login`), or explicitly validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name` before dispatching to handlers. Additionally, consider treating a missing/blank `webhook_secret` for a configured org as a hard configuration error in production rather than an implicit "accept-all" bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
minitest plan (controller test, `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Stub `Shipit.secrets.github` with two orgs: `SecretOrg` (has `webhook_secret: 's3cr3t'`) and `OpenOrg` (has `webhook_secret: nil`), mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Create `stack = shipit_stacks(...)` under a repository `"SecretOrg/victim-repo"`, and an associated review stack with a linked `PullRequest` (number matching payload).
3. Build a forged `pull_request` payload: `action: "unlabeled"`, `organization: { login: "OpenOrg" }`, no `repository.owner`, `repository: { full_name: "SecretOrg/victim-repo" }`, `pull_request.labels: [{ name: "malicious-label" }]`, and an invalid/garbage `X-Hub-Signature` header.
4. `assert_equal "OpenOrg", repository_owner_from(payload)` and `assert_not_equal "SecretOrg", repository_owner_from(payload)` — establishing the divergence between the verifier-selection field and the actual target owner (`"SecretOrg"` parsed from `repository.full_name`).
5. POST to `/webhooks` with the forged payload/signature; `assert_response :ok`.
6. Reload the `PullRequest` record scoped to `"SecretOrg/victim-repo"`'s stack; `assert_includes pull_request.reload.labels, "malicious-label"` — proving the org whose secret authenticated the request (`OpenOrg`) is not the org that owns the mutated record (`SecretOrg`).

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
