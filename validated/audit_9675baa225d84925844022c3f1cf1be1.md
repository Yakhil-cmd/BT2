### Title
Webhook signature verified against the organization derived from an attacker-controlled payload field, not the repository the event actually writes to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to check the `X-Hub-Signature` against by reading `repository_owner`, a value taken directly out of the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). [1](#0-0)  The signature is verified against `Shipit.github(organization: repository_owner).webhook_secret`, but nothing ties that `repository_owner` to the repository/stack the event handlers subsequently act on inside `create`. [2](#0-1) 

### Finding Description
The binding that should hold is: **organization authenticated (the org whose `webhook_secret` validated `X-Hub-Signature`) == repository actually written to by the event handler**. The controller breaks this equality because both sides are derived from the same untrusted payload, but from different, independently attacker-controllable fields:

- The signature check keys off `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [3](#0-2) 
- `verify_webhook_signature` looks up the `LLMOracleRegistry`-equivalent config, i.e. `Shipit.github(organization:)`, purely to fetch that org's `webhook_secret`, and if no secret is configured for that org it returns `true` unconditionally (`return true unless webhook_secret`). [4](#0-3) 
- Once the signature "passes" the request body is parsed and dispatched to `Shipit::Webhooks.for_event(event)` handlers, which look up the actual `Repository`/`Stack` to mutate using other fields of the same JSON body (e.g. `full_name`, `sha`, commit/status payloads) — fields never checked against the org whose secret validated the request.

Because any organization configured in `config/secrets*.yml` without a `webhook_secret` (or one whose secret is guessable/leaked) satisfies `verify_signature`, and because the org used for verification and the repository whose stack gets updated are two separate, attacker-supplied JSON keys, an attacker can craft a payload where `repository.owner.login` names an org that has no `webhook_secret` configured (so verification is skipped) while `repository.full_name`/`sha`/`branches` inside the same payload reference a *stack belonging to a different, secured organization*. The `check_if_ping`/`drop_unhandled_event`/`verify_signature` filter chain never re-derives or cross-checks organization membership of the repository that the event handler will actually resolve and write to.

This is the direct analog of the reported bug class: a value that is *checked* (here, `repository_owner`, used purely to select which secret to verify against) is not the same value that is *acted upon* (the repository/stack the handler mutates), and the trust boundary between them is not enforced.

### Impact Explanation
An unauthenticated attacker who knows (or can enumerate) one multi-tenant Shipit deployment's list of configured GitHub organizations, and finds any one org lacking a `webhook_secret` (common in single-tenant or partially configured multi-org setups per `config/secrets.development.shopify.yml` where `webhook_secret:` is commonly left `nil`), can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) whose repository-identifying fields target a different, unrelated stack. Handlers such as `check_suite_handler.rb`/`status_handler.rb`/`push_handler.rb` act on those fields to update commit/CI status, enqueue `RefreshCheckRunsJob`, or create commits/teams/users — i.e., they can flip CI/status state that gates deploys, or create bogus team/user records — for a repository whose actual webhook secret was never checked. This crosses the "read/write repository state without the credential meant to authorize it" boundary and can lead to an unauthorized deploy path being unblocked (CI status marked green) which maps to the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: it requires at least one organization in `Shipit.github` config without a `webhook_secret` (or a leaked one) alongside another, secured organization sharing the same Shipit instance — a realistic multi-tenant scenario given the engine explicitly supports multiple `github:` orgs in secrets config and explicitly allows `webhook_secret: # nil`. No authentication, API token, or repository write access is required — only network access to `POST /webhooks`.

### Recommendation
After parsing the payload, re-derive the repository/stack the handler intends to mutate and assert that its owning organization equals the organization whose `webhook_secret` validated the signature, rejecting (422) on mismatch. Additionally, do not treat an absent `webhook_secret` as an automatic pass in `verify_webhook_signature`; require an explicit "insecure/no-secret" opt-in per organization, and fail closed by default.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `orgA` (no `webhook_secret`) and `orgB` (has a `webhook_secret`, contains a real tracked stack).
2. POST to `/webhooks` with `X-Github-Event: status` and a body:
```json
{
  "sha": "<real-commit-sha-in-orgB-repo>",
  "state": "success",
  "branches": [{"name": "master"}],
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/real-repo"}
}
```
No `X-Hub-Signature` header, or any value, is required because `verify_webhook_signature` short-circuits to `true` when `orgA` has no secret. [5](#0-4) 
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "orgA")` (from `repository.owner.login`), passes verification unconditionally, and dispatches the event to `Shipit::Webhooks.for_event('status')`, whose handler resolves the target commit/stack via `full_name`/`sha`, i.e. `orgB/real-repo`, and updates its commit status — without ever having proven possession of `orgB`'s `webhook_secret`. [6](#0-5) 

*Note: I could not load `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, and `handler.rb` bodies in this final pass due to a tool error on the last iteration, so the exact field name used by each handler to resolve the target `Repository`/`Stack` (e.g. `full_name` vs. `repository.id`) is inferred from directory structure and file names rather than directly confirmed; this should be verified by reading those files directly before treating this as final.*

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
