### Title
Unbounded goroutine fan-out over attacker-supplied attestation list causes resource-exhaustion DoS during `gh attestation verify` - (File: pkg/cmd/attestation/api/client.go)

### Summary
`fetchBundleFromAttestations` spawns one goroutine per attestation returned from the (attacker-influenced) attestations API/response, each performing an external HTTP `GET` to a `BundleURL`, with no concurrency cap and no context/cancellation on partial failure other than `errgroup.Wait()` returning the first error. This mirrors the "calls inside loop can address DoS" bug class from the C4 report — instead of Solidity `for` loops calling external contracts, here a Go loop over `range attestations` calls `g.Go(...)` unconditionally for every element, fanning out network I/O with no bound tied to attacker-controlled input size.

### Finding Description [1](#0-0) 

The function iterates over `attestations` (a slice returned from `getAttestations`/`GetByDigest`, ultimately sourced from GitHub's attestations API response for a given digest) and, for every entry with a non-empty `BundleURL`, launches a goroutine that performs `c.getBundle(...)` — an outbound HTTP request to a URL supplied in the attestation record: [2](#0-1) 

There is no limit on the number of concurrent goroutines/HTTP requests created (`errgroup.Group{}` with no `SetLimit`), and the number of attestations that can be returned for a digest is bounded only by the caller-supplied `Limit` parameter (e.g. up to 100 in `pkg/cmd/release/verify/verify.go`, or an even higher value if a user runs `gh attestation verify --limit N` with a large N). Since attestations for an arbitrary artifact digest can be authored/pushed by any party who controls that artifact (a normal, unprivileged workflow use case), an attacker can craft an artifact + a large batch of attestations, each with a distinct `BundleURL` pointing to a slow-responding or non-responding attacker-controlled host. When a victim runs `gh attestation verify` (or `gh release verify`) against that artifact, the client fans out one HTTP request per attestation simultaneously, tying up goroutines/sockets until each request times out (or hangs indefinitely if no client-side timeout is enforced on `getBundle`), degrading or freezing the invoking `gh` process.

This matches the report's mitigation guidance directly: "avoid combining multiple calls in a single transaction... especially when calls are executed as part of a loop" and "always assume external calls can fail" — here the calls are not rate-limited or bounded, and a single slow/malicious endpoint among many can stall completion of the whole batch.

### Impact Explanation
An unprivileged remote party (anyone who can publish attestations for an artifact digest, or control the artifact/repo a victim is asked to verify) can cause the `gh` CLI process performing verification to consume excessive resources (goroutines, open sockets) and stall, denying the local user's ability to complete verification within a reasonable time. This is a client-side availability impact on `gh attestation verify` / `gh release verify` invocations, not a privileged-only condition, and is reachable via a normal `gh` command against attacker-published content — fitting the requested category of "token handling and host trust... attestation verification, downloads to disk."

### Likelihood Explanation
Likelihood is moderate: it requires the victim to run verification against an artifact/digest for which the attacker has published (or can influence) many attestations with slow/malicious `BundleURL`s. This is a realistic scenario for supply-chain verification workflows where verification targets third-party or externally-sourced artifacts. The number of attestations is bounded by the `Limit` parameter the caller chooses (up to 100 in the release-verify path, and configurable/higher for `gh attestation verify`), so the achievable fan-out size is not unlimited but can still be large enough to be disruptive.

### Recommendation
- Bound concurrency in `fetchBundleFromAttestations` using `errgroup.Group.SetLimit(n)` (or a worker pool) so the number of simultaneous outbound HTTP requests is capped regardless of the attestation count.
- Enforce a strict per-request timeout/deadline on `getBundle`/`c.externalHttpClient` calls (via `context.WithTimeout`) so a single slow endpoint cannot stall the whole batch indefinitely.
- Consider treating individual bundle-fetch failures as non-fatal (collect and report which attestations failed) rather than failing the whole verification via `g.Wait()`'s first error, consistent with the "implement contract logic to handle failed calls" guidance, so a single hostile attestation can't be leveraged to abort processing of the rest.

### Proof of Concept
1. Publish (or self-host) an artifact with N attestations attached (N approaching the `--limit` value accepted by `gh attestation verify`, e.g. 100), where each attestation's `BundleURL` points to a distinct attacker-controlled endpoint that accepts the TCP connection but never completes the HTTP response (slow-loris style) or points to a very slow network path.
2. Have the victim run `gh attestation verify <artifact> --owner <attacker-owner>` (or `gh release verify` against a tag with many attestations) against that digest.
3. Observe that `fetchBundleFromAttestations` immediately spawns N concurrent goroutines/HTTP requests (`pkg/cmd/attestation/api/client.go:199-235`), each blocking on the corresponding slow endpoint, exhausting available outbound connections/goroutines and stalling the `gh` process well beyond normal command latency, until client/OS-level socket timeouts eventually fire (if any are configured).

**Uncertainty note:** I could not fully verify the exact HTTP client timeout configuration used for `c.externalHttpClient`/`getBundle`, nor the exact maximum value accepted by the `--limit` flag on `gh attestation verify` (only the release-verify path's hardcoded `Limit: 100` was confirmed), due to index size limits preventing me from reading the full contents of `pkg/cmd/attestation/verify/options.go` and the HTTP client construction code. func (c *LiveClient) fetchBundleFromAttestations(attestations []*Attestation) ([]*Attestation, error) {
	fetched := make([]*Attestation, len(attestations))
	g := errgroup.Group{}
	for i, a := range attestations {
		g.Go(func() error {
			if a.Bundle == nil && a.BundleURL == "" {
				return fmt.Errorf("attestation has no bundle or bundle URL")
			}

			// for now, we fall back to the bundle field if the bundle URL is empty
			if a.BundleURL == "" {
				c.logger.VerbosePrintf("Bundle URL is empty. Falling back to bundle field\n\n")
				fetched[i] = &Attestation{
					Bundle: a.Bundle,
				}
				return nil
			}

			// otherwise fetch the bundle with the provided URL
			b, err := c.getBundle(safeurl.NewImmutableSafeURL(a.BundleURL))
			if err != nil {
				return fmt.Errorf("failed to fetch bundle with URL: %w", err)
			}
			fetched[i] = &Attestation{
				Bundle: b,
			}

			return nil
		})
	}

	if err := g.Wait(); err != nil {
		return nil, err
	}

	return fetched, nil
}
