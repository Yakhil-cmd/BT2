### Title
`provision?` precedence bug creates a `ReviewStack` for an opted-out repository, and `ReviewStackProvisioningQueue#work` provisions it with no re-check of `repository.review_stacks_enabled` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb], [File: app/models/shipit/review_stack_provisioning_queue.rb])

### Summary
`OpenedHandler#provision?` mixes `&&`/`||` without parentheses, so `repository.review_stacks_enabled` only gates the `allow_all` branch and not the `allow_with_label`/`prevent_with_label` branches, letting a `ReviewStack` be created and enqueued for a repository that has review stacks disabled. `ReviewStackProvisioningQueue#work` then processes any row matching `with_provision_status(:deprovisioned)` + `awaiting_provision: true` and calls `stack.provisioner.up` without ever re-checking `repository.review_stacks_enabled`, so the opt-out is silently ignored end-to-end.

### Finding Description
The intended invariant is: `repository.review_stacks_enabled == true` must be true before any provisioning behavior applies (i.e. `review_stacks_enabled` should gate `allow_all`, `allow_with_label`, and `prevent_with_label` equally). The actual code only enforces that equality for one branch: [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && label_present?) || (prevent_with_label? && label_absent?)`. If a repository has `review_stacks_enabled: false` but `provisioning_behavior: allow_with_label` (or `prevent_with_label`) left set from a previous configuration, `provision?` still returns `true` whenever the PR has (or lacks) the configured label.

`respond_to_pull_request_opened?` then returns true and `process` calls: [2](#0-1) 

which creates the stack and immediately enqueues it: [3](#0-2) 

`ReviewStack#enqueue_for_provisioning` simply flips `awaiting_provision` to `true`: [4](#0-3) 

The periodic cron task drives the queue independent of any request context: [5](#0-4) 

`ReviewStackProvisioningQueue#queued_stacks`/`#work` selects strictly by `provision_status` and `awaiting_provision`, with **no join or check against `repository.review_stacks_enabled`**: [6](#0-5) 

`stack.provisioner.provision?` defaults to `true` for the base handler (unless a custom handler is registered): [7](#0-6) 

so `stack.provision` fires, transitioning `deprovisioned -> provisioning` and invoking `stack.provisioner.up` via the state machine's `after_transition` callback: [8](#0-7) 

No guard anywhere in this chain re-derives or re-checks `repository.review_stacks_enabled` after stack creation. `Repository#review_stacks_enabled` and `provisioning_behavior` are independent columns with no validation coupling them: [9](#0-8) 

An attacker who can open a pull request against, or add/omit the configured label on their own PR in, a repository whose maintainer has `review_stacks_enabled: false` but left a stale `provisioning_behavior` (`allow_with_label`/`prevent_with_label`) set, gets a `ReviewStack` created and later provisioned by the cron job — despite the repository having explicitly opted out of review stacks.

### Impact Explanation
Once the queue picks up the row, `stack.provisioner.up` runs for the opted-out repository's stack — this is real infrastructure/state provisioning triggered purely by an unprivileged pull-request action, for a repository whose operator explicitly disabled the feature (`review_stacks_enabled: false`). This is a write/action performed for a repository that did not opt in/authenticate that behavior, matching "a record written for a repository that did not authenticate it" / unauthorized action performed on a non-opted-in tenant. It is repeatable against any repository misconfigured this way and does not require GitHub or Shipit secrets. Blast radius is scoped to repositories with the specific stale-config combination (`review_stacks_enabled: false` + `provisioning_behavior != allow_all`), not all tenants globally.

### Likelihood Explanation
Requires: (1) repository configuration that combines `review_stacks_enabled: false` with a non-`allow_all` `provisioning_behavior` and a set `provisioning_label_name` — a plausible but non-default state (e.g., an operator previously used `allow_with_label`, then toggled `review_stacks_enabled` off, expecting that alone to fully disable provisioning). (2) The attacker only needs to open a PR (and, per the threat model, label their own PR) — no secrets, tokens, or elevated GitHub role required beyond what's already assumed available to the attacker. Given that combination exists, the exploit is fully repeatable and deterministic every time such a PR/label event fires, and again every cron cycle via `Shipit::ReviewStackProvisioningQueue.work`.

### Recommendation
Add explicit parentheses in `provision?` (and the equivalent `unarchive?` in `reopened_handler.rb`) so `review_stacks_enabled` gates all three behavior branches: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && label?) || (prevent_with_label? && !label?))`. Additionally, harden `ReviewStackProvisioningQueue#queued_stacks` to join/filter on `repository.review_stacks_enabled: true` (defense in depth) so a stack created under any future bug cannot be provisioned for an opted-out repository.

### Proof of Concept
```ruby
test "does not create or provision stacks when review_stacks_enabled is false, even with allow_with_label configured" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: repository.review_stacks_enabled == false
  # must imply no ReviewStack is created regardless of provisioning_behavior.
  assert_no_difference -> { Shipit::Stack.count } do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
  end

  # If the assertion above fails (stack created), confirm downstream compounding:
  stack = repository.stacks.last
  assert_equal "deprovisioned", stack.provision_status
  assert stack.awaiting_provision

  assert_changes -> { stack.reload.provision_status }, from: "deprovisioned", to: "provisioning" do
    Shipit::ReviewStackProvisioningQueue.work
  end
end
```

    def work
      queued_stacks.find_each(&method(:provision))
    end

    def queued_stacks
      @queued_stacks ||= Shipit::ReviewStack
                         .with_provision_status(:deprovisioned)
                         .where(awaiting_provision: true)
    end

    private

    def provision(stack)
      if stack.provisioner.provision?
        stack.provision
      else
        Rails.logger.info(
          "Putting review ReviewStack<#{stack.id}> back into the provisioning queue - #provision? was falsey."
        )
      end
    end
