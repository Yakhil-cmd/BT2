### Title
`review_stacks_enabled` gate bypassed by operator precedence in `provision?`, allowing unprivileged PR authors to force ReviewStack provisioning - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled` to be true before any provisioning path runs, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to gate only the `allow_all` branch. The `allow_with_label` and `prevent_with_label` branches evaluate independently of `review_stacks_enabled`, so an attacker who simply opens (or leaves unlabeled) a pull request on a `prevent_with_label` repository triggers stack creation even when the operator has disabled review stacks entirely.

### Finding Description
The claimed binding is: `review_stacks_enabled (operator gate) == the gate enforced before ReviewStackAdapter#find_or_create! runs`. Tracing `provision?`: [1](#0-0) 

parses (per Ruby precedence, `&&` binds tighter than `||`) as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

So when `review_stacks_enabled == false` and `provisioning_behavior == "prevent_with_label"`, the first disjunct is `false`, but the third disjunct `(prevent_with_label? && !has_label)` evaluates purely on `provisioning_behavior` and the PR's labels, independent of `review_stacks_enabled`. An attacker opens a PR without adding the configured provisioning label, `pull_request_has_provisioning_label?` returns `false`, `!false == true`, and `provision?` returns `true`, calling `process` -> `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [2](#0-1)  which creates a `ReviewStack` row, a `PullRequest` record, and enqueues it for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)` [3](#0-2) , which ultimately invokes `stack.provisioner.up` on a state transition [4](#0-3) .

The same precedence bug is duplicated in `ReopenedHandler#unarchive?` [5](#0-4) .

Existing guards do not prevent this: webhook signature verification and payload schema validation (`ExplicitParameters`) only authenticate that the payload came from GitHub for *some* tracked repo/PR event - they do not enforce the `review_stacks_enabled` semantic gate, which is purely an application-level boolean checked in `provision?`. The repository lookup (`Repository.from_github_repo_name`) correctly scopes the attacker to their own tracked repository (no cross-tenant mutation), but within that repository, the operator's explicit intent to disable review stacks (`review_stacks_enabled = false`) is not honored for `allow_with_label` or `prevent_with_label` configurations.

Note: existing test coverage in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` for `prevent_with_label` (lines 159-172) does not set `provisioning_enabled: false` - the helper's default is `true` - so this specific combination (`review_stacks_enabled: false` + `prevent_with_label`) is untested and the bug is a real, unexercised gap in the shipped logic. The test file falls under `test/**`, which is out-of-scope for modification, but this Proof-of-Concept describes what a repro would look like.

### Impact Explanation
Any GitHub user who can open a pull request against a repository tracked by Shipit (i.e., their own PR against that repo) can force creation of a `ReviewStack` and trigger `stack.provisioner.up` even though the repository operator explicitly set `review_stacks_enabled = false`. This is an authorization-bypass on a security-relevant operator control: it results in an unauthorized deploy/provisioning-like record being written and provisioner code running for a repository whose operator explicitly disabled that automation. Repeatable per PR opened against any repository misconfigured this way (any repo left in `prevent_with_label` state with `review_stacks_enabled` toggled off after being set up, or ever left in that state before being fully disabled). It is scoped to the attacker's own accessible repository (no cross-tenant stack mutation), consistent with a Critical-adjacent "unauthorized deploy/provision" impact within that repository's boundary.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`, for the label-present case) while `review_stacks_enabled` is `false`. This is a plausible operator misconfiguration - e.g., an operator disables review stacks temporarily via `review_stacks_enabled` while leaving `provisioning_behavior` unchanged, expecting the boolean to be a hard gate. Attacker cost is trivial: open a PR (or omit a label) against a repo they can already open PRs against, no secrets or elevated Shipit access required. Fully repeatable per PR/repository matching the configuration.

### Recommendation
Add explicit parentheses / restructure `provision?` (and the identical `unarchive?` in `ReopenedHandler`) so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the equivalent fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (illustrative; out-of-scope directory but describes the required assertion):
```ruby
test "does not create stacks when review_stacks_enabled is false, even for prevent_with_label repos" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertion before fix: `repository.review_stacks_enabled == false` while `Shipit::Stack.count` increases by 1 (a `ReviewStack` created and queued for provisioning) - proving the gate enforced in code (`provision?` truthy) diverges from the operator-set gate (`review_stacks_enabled == false`).
