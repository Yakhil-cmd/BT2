### Title
Webhook Signature Verification Uses `repository.owner.login` While Event Handlers Trust `repository.full_name` — Cross-Organization Repository Write - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against based on `repository.owner.login` (or `organization.login`) taken from the unauthenticated request body. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the actual `Repository`/`Stack` to mutate using a *different* field of the same payload: `repository.full_name` [1](#0-0) . The signature check never verifies that the organization whose secret validated the payload actually owns the repository the handlers act on.

The equality that should hold — `organization whose secret authenticated the payload == organization owning repository.full_name` — is never enforced. Since Shipit supports multiple organizations, each configured with a distinct GitHub App / `webhook_secret` (resolved by `Shipit.github(organization:)`), the field used to *select the trust anchor* (`repository.owner.login`) and the field used to *decide what gets written* (`repository.full_name`) are independently attacker-controlled parts of the same JSON body and are never cross-checked. Anyone who can produce a validly signed payload for organization A's webhook secret (e.g., a legitimate GitHub App owner/admin for org A, or anyone able to make GitHub deliver a webhook for a repo under org A) can set `repository.full_name` to `orgB/some-repo` while keeping `repository.owner.login` = `orgA`. `verify_signature` will validate successfully against org A's secret, and the handler will then act on org B's `Repository`/`Stack` records — triggering `sync_github`, creating/mutating commits, statuses, review-stack provisioning, PR handling, etc. for a repository the requester never proved control over.

### Impact Explanation
This breaks the deployment-trust binding between "organization that authenticated" and "repository that is written," enabling cross-repository/cross-organization state mutation without ever proving ownership of the target repository — e.g. forcing `GithubSyncJob` runs, fabricating commit statuses that gate deploys (`StatusHandler`), or auto-provisioning/closing review stacks (`PullRequest::OpenedHandler`/`ClosedHandler`) on a stack that belongs to an organization the attacker does not control. Because commit statuses and check-suite results directly influence whether Shipit considers a commit deployable, this can be leveraged toward an unauthorized deploy on another organization's stack, meeting the "cross-repository writes / unauthorized deploy" bar.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce one validly HMAC-signed payload for *any* organization onboarded to the same Shipit instance (their own org, if they administer a GitHub App/webhook pointed at Shipit, or any org whose webhook secret leaks). Given a multi-tenant Shipit deployment (many customer orgs, each with independent `webhook_secret`s per `Shipit.github(organization:)`), this is a realistic scenario for an org-boundary attacker who is fully unprivileged with respect to the target organization.

### Recommendation
In `verify_signature`, after establishing which organization's secret validated the request, re-derive the same organization identity from `repository.full_name`'s owner segment (or `organization.login`) and reject the request (422) if it does not match `repository_owner`. Alternatively, have each `Handler` verify `payload.dig('repository','owner','login')` matches the resolved `Repository#owner` before acting, so the field used for trust and the field used for mutation are provably the same value.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with distinct GitHub Apps/`webhook_secret`s, both organizations onboarded onto the same Shipit instance.
2. Attacker administers (or otherwise obtains a valid signature for) `org-a`'s webhook secret.
3. Attacker crafts a `push` (or `status`/`pull_request`) payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac using org-a's webhook_secret>` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: 'org-a').verify_webhook_signature(...)`, which succeeds because it was signed with `org-a`'s real secret [2](#0-1) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('org-b/target-repo')` [1](#0-0)  and invokes `stack.sync_github` on `org-b`'s stack, even though the request was never authenticated as coming from `org-b`.

Note: I could not fully verify within the available index whether `Shipit.github(organization:)` in this deployment always resolves to a single global GitHub App/secret versus genuinely per-organization secrets (the multi-tenant config path lives in `lib/shipit/github_app.rb`/`Shipit` config, which the index only partially exposes) — if this Shipit instance is single-tenant with exactly one org/one secret configured, the cross-org signing step in this PoC is not reachable and the exploit degrades to a same-organization confused-repository case only. I recommend confirming the multi-organization GitHub App configuration path (`Shipit.github`) with a full checkout before treating this as confirmed-critical.
