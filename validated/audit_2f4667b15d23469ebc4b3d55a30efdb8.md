### Title
Stack-scoped ApiClient token authorizes read access to any stack via CCMenu API - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
An `ApiClient` token that is scoped to a single stack (via `ApiClient#stack_id`) is intended to only authorize `read:stack` (and other) operations on that one stack. Every other API controller (`StacksController`, `HooksController`, etc.) enforces this by resolving the target stack through the `stacks` scope defined in `BaseController#stacks`, which restricts to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. `Api::CCMenuController` overrides the inherited `stack` method with an unscoped lookup, breaking this binding.

### Finding Description
`BaseController` defines the authorization-respecting accessor: [1](#0-0) 

Every controller that resolves `params[:stack_id]`/`params[:id]` into a `Stack` is expected to go through this `stacks` scope, e.g. `StacksController#stack`: [3](#0-2) 

and `HooksController#stacks`-derived `hooks`, both keyed off `stack.id`, which is itself resolved via the inherited scoped `stack`/`stacks` methods.

However, `Api::CCMenuController` privately re-defines `stack` to bypass the scope entirely: [5](#0-4) 

The `require_permission :read, :stack` check only calls `current_api_client.check_permissions!('read', 'stack')`, which verifies the string `"read:stack"` is present in the client's `permissions` array — it never checks *which* stack the permission applies to: [6](#0-5) 

The equality that should hold is: **stack a token authorizes == stack the request touches**. For a stack-scoped `ApiClient` (e.g., the one automatically created by `CCMenuUrlController` for one specific stack's CCMenu URL), this equality is broken in `CCMenuController#show`: the token authorizes only `stack_id: N`, but `Stack.from_param!(params[:stack_id])` lets the request touch *any* stack `M` simply by changing the `stack_id` URL/query parameter, since the token is passed as a URL query parameter (`?token=...`) rather than tied to a specific path.

This is exploitable specifically because `CCMenuUrlController` mints these scoped tokens and embeds them in URLs meant to be shared with external tools (CI status widgets, dashboards): [7](#0-6) 

An attacker who obtains one such shared/leaked CCMenu URL (which is explicitly designed to be handed out to external, less-trusted CI dashboard tools) can swap the `stack_id` in the URL and read deploy/build status for any other stack in the installation, even ones the token was never meant to authorize.

### Impact Explanation
This matches the High-severity criterion "unauthenticated read of stack state, task streams or deploy output" relative to what the token should be scoped to — a token explicitly minted for one stack's read access instead grants read access (deploy status, last build label/time, lock status) to every stack in the Shipit installation. This is an authorization boundary crossing: token-scope (`ApiClient#stack_id`) is bypassed system-wide for this one endpoint, while the identical mechanism is correctly enforced in `StacksController`, `HooksController`, and others.

### Likelihood Explanation
Likelihood is high given normal usage: `CCMenuUrlController#fetch` is the documented/supported way to generate these tokens and is designed to be embedded in third-party CCMenu-compatible clients/URLs, i.e. is expected to leave the trusted browser session (shared with, e.g., a CI dashboard). No additional privilege beyond possessing one such (intentionally shareable) URL is required to pivot to arbitrary stacks — only changing the `stack_id` query parameter.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the same scoped `stacks` accessor used by `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` token cannot be used to query any stack other than the one it was issued for.

### Proof of Concept
1. As an authenticated Shipit user, visit a stack's settings page to trigger `CCMenuUrlController#fetch` for `stack_id=stack-a`, minting an `ApiClient` scoped to `stack-a` with `permissions: %w[read:stack]`, and obtain the returned `ccmenu_url` containing `?token=<TOKEN_A>`. [8](#0-7) 
2. Share/leak that URL (as intended, to a third-party CI dashboard/CCMenu client).
3. An attacker with only that URL requests `GET /api/stacks/stack-b/ccmenu.xml?token=<TOKEN_A>` (any other stack's `stack_id`) instead of `stack-a`.
4. `authenticate_api_client` in `CCMenuController` authenticates `TOKEN_A` successfully via `ApiClient.authenticate(params[:token])`. [9](#0-8) 
5. `require_permission :read, :stack` passes because `TOKEN_A`'s client has `"read:stack"` in its permissions list, regardless of stack. [6](#0-5) 
6. `stack` resolves via `Stack.from_param!(params[:stack_id])` to `stack-b` — not `stack-a` — and the attacker receives `stack-b`'s deploy status/lock state in the XML response, despite `TOKEN_A` never having been authorized for `stack-b`. [10](#0-9)
