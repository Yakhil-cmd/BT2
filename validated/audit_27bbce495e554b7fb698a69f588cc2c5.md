### Title
StatusHandler writes forged CommitStatus onto any commit matched by sha with no repository binding check - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `params.sha` and calls `commit.create_status_from_github!(params)` without ever checking that the commit's `stack`/`repository` matches the repository or organization named in the verified webhook payload. Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever the resolved organization has no configured `webhook_secret`, an attacker who controls an organization/repo with no secret configured in Shipit can send a signed-as-valid `status` webhook naming their own org but carrying the sha of a commit that actually belongs to a different organization's stack, writing an attacker-controlled `CommitStatus` (state, target_url, context) onto that unrelated commit.

### Finding Description
The binding that should hold is: `commit.stack.repository.owner == repository_owner_from_verified_payload` (i.e., a status row written for a commit should only be written when the payload's verified repository/organization matches the commit's own repository). This binding is never checked.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is read directly, unauthenticated, from the JSON payload (`params.dig('repository','owner','login') || params.dig('organization','login')`, line 59-62). It then calls `github_app.verify_webhook_signature(signature, raw_post)`.
- In `lib/shipit/github_app.rb:76-83`, `verify_webhook_signature` returns `true` immediately if `webhook_secret` is blank for that organization's config. So for any organization X configured in Shipit without a `webhook_secret`, *any* payload naming X as the repository owner is accepted as "verified," regardless of actual signature.
- Once verified, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, including `StatusHandler`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is **global across all stacks/repositories** in the Shipit instance; it has no `stack_id`, `repository`, or organization filter at all.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally creates a `Status` record (`statuses.replicate_from_github!`) for that commit using the payload's `state`, `target_url`, `context`, etc.

Exploit flow: an attacker registers/controls a GitHub organization "X" that the Shipit operator has configured (e.g., because X is a legitimate but low-security tenant with no webhook secret set) or otherwise induces such a configuration. The attacker discovers or brute-forces a commit sha belonging to organization Y's stack (commit shas are often public/guessable via PRs, git log, or leaked from other public endpoints). The attacker POSTs to `/webhooks` with `X-Github-Event: status` and a JSON body: `{"repository": {"owner": {"login": "X"}}, "sha": "<Y's commit sha>", "state": "success", "target_url": "http://evil", "context": "ci/attacker"}`. Because `Shipit.github(organization: 'X').webhook_secret` is nil, `verify_webhook_signature` returns true unconditionally — no valid HMAC signature is required. `StatusHandler` then finds Y's commit purely by sha match and writes the forged success status onto it.

Existing guards do not stop this: `drop_unhandled_event` only checks event type is handled; `ExplicitParameters` only validates the shape of `sha`, `state`, etc., not repository ownership; there is no `require_permission!`/`stacks` scope check anywhere in the webhook path since the webhook path is inherently repository-authenticated only by signature — and that authentication is keyed off attacker-supplied `repository_owner`, and is a no-op for any org lacking a webhook secret.

### Impact Explanation
This allows a payload verified only for organization X's namespace to mutate a `CommitStatus` row belonging to organization Y's commit/stack — this is exactly "a payload for one repository mutating another's stack, commit ... " which the rules classify as Critical. A forged `success` status can flip `Commit#deployable?` to true (satisfying CI requirements), potentially triggering `schedule_continuous_delivery` and an unauthorized auto-deploy of Y's commit, entirely orchestrated by an attacker with no relationship to Y's infrastructure. The attack is repeatable against any sha in the system as long as at least one configured Shipit organization has no webhook secret set (a plausible/common misconfiguration, especially in multi-tenant Shipit deployments where the Shipit-hosting org doesn't require every onboarded org to configure a secret).

### Likelihood Explanation
Preconditions: (1) The Shipit instance is configured to serve multiple organizations/repos (multi-tenant), and (2) at least one configured organization has no `webhook_secret` set — this is a real, documented gap since `verify_webhook_signature` explicitly treats a missing secret as "trust unconditionally" rather than "reject." (3) The attacker needs the target commit's sha, which is often discoverable (public repos, PR pages, git history) even without Shipit access. Attacker cost is a single unauthenticated HTTP POST; no secrets, tokens, or GitHub App keys are needed. This is fully repeatable for any sha and any status content.

### Recommendation
`StatusHandler#process` (and any other sha-keyed handler) must scope `Commit.where(sha: params.sha)` to only commits whose `stack.repository` matches the repository/organization that was cryptographically verified for this request (e.g., pass the verified `repository_owner`/`repo full_name` from the controller into the handler and filter `commit.stack.repository.owner == verified_owner` and `full_name == params.dig('repository','full_name')`). Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in a multi-tenant configuration — either require a webhook secret for every configured organization or make the "no secret configured" behavior an explicit, opt-in developer/test-only mode rather than the default production behavior.

### Proof of Concept
minitest plan (no live GitHub, uses `Shipit.github`/fixtures):
1. Configure two orgs in test config: `Y` with a `webhook_secret` set, `X` with no `webhook_secret` (or stub `Shipit.github(organization: 'X').webhook_secret` to return nil).
2. Create `stack_y = shipit_stacks(:shipit)` (org Y) and `commit_y = stack_y.commits.create!(sha: 'a' * 40, ...)` with no existing statuses.
3. POST to `/webhooks` with header `X-Github-Event: status`, no/garbage `X-Hub-Signature`, and body:
```json
{"repository": {"owner": {"login": "X"}}, "sha": "aaaa...a", "state": "success", "target_url": "http://evil", "context": "ci/attacker"}
```
4. Assert response is `200`/`:ok` (not `422`), i.e., signature verification passed for a payload naming X even though sha belongs to Y.
5. Assert `commit_y.reload.statuses.count` changed from 0 to 1 and `commit_y.statuses.last.state == 'success'` and `target_url == 'http://evil'`, proving the equality `commit.stack.repository.owner == 'X'` is false yet the write still happened — the binding is broken.
6. Assert `Shipit.github(organization: 'X').send(:webhook_secret).nil?` to confirm the precondition that made verification a no-op.
