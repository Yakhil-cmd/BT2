## Title
Stack-scoped API token can read the build/deploy state of **any** stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb](file))

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack (`stack_id`), and every API controller enforces that scope through `BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` and resolves it directly from the request path instead of from the scoped `stacks` relation, so a token authorized (`read:stack`) for stack A can be used to read the CI/build state of any other stack B simply by changing the `stack_id` in the URL.

### Finding Description
`ApiClient` records carry an optional `stack_id` used to limit what stacks a token may act on: [1](#0-0) 

`Api::BaseController` is supposed to be the single place enforcing that scope — `stacks` restricts the queryable set to the client's own stack when one is set, and `stack` is derived from that restricted relation: [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, but it **redefines `stack`** to bypass the scoped `stacks` relation entirely, resolving the stack straight from `Stack.from_param!(params[:stack_id])`: [3](#0-2) 

`require_permission` only checks that the token's `permissions` array includes `read:stack` — it never compares `current_api_client.stack_id` to the requested `stack`: [4](#0-3) 

The result is a broken binding: **the stack a token is authorised for (`ApiClient#stack_id`) ≠ the stack the request actually touches (`params[:stack_id]` in `CCMenuController`)**. Every other stack-scoped API controller (`DeploysController`, `RollbacksController`, `StacksController`, `HooksController`, `TasksController`, …) relies on the inherited `stack`/`stacks` methods and is therefore correctly scoped; `CCMenuController` is the outlier that re-implements stack resolution and drops the scoping check.

A concrete example of a scoped token exists in the fixtures — `here_come_the_walrus` is bound to the `shipit` stack with only `read:stack`: [5](#0-4) 

The existing tests for this controller never exercise a stack-scoped client against a foreign `stack_id`, so the bypass is untested: [6](#0-5) 

The route confirms `stack_id` is fully attacker-controlled per request: [7](#0-6) 

### Impact Explanation
An attacker holding a legitimately-issued, narrowly-scoped API token (scoped to a single, possibly low-sensitivity stack) can enumerate/read the build and deploy status — `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state — of **every stack** in the Shipit instance, including stacks they were never granted access to. This is a cross-stack authorization escalation: the token's `stack_id` scope, meant to be the authorization boundary, is silently ignored for this endpoint. Per the rules this maps to the High-severity category "escalation into … authorization, unauthenticated read of stack state, task streams or deploy output" since the token's own authorization boundary for stacks is bypassed.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a very common configuration, e.g. tokens generated for CI dashboards via `CCMenuUrlController`) can trigger this with a single unauthenticated-permission-check GET request — no privilege escalation beyond having any valid token, and no special conditions are required.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using `stacks.from_param!(params[:stack_id])` from `BaseController`) so that stack-scoped tokens cannot resolve stacks outside their `stack_id`, consistent with every other stack-scoped API controller.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack `owner/repo-a` with only `read:stack` permission (e.g. as `here_come_the_walrus` fixture demonstrates).
2. As that token, issue: `GET /api/stacks/owner/repo-b/production/ccmenu` (a stack the token is not scoped to).
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, the request succeeds and returns `repo-b`'s build/deploy XML status, even though the token's `stack_id` only authorizes `repo-a`.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
