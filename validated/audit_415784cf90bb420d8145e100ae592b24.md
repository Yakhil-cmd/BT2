### Title
Cross-Organization Webhook Forgery Enables Unauthorized Commit Status Injection and Continuous-Delivery Trigger - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), not a value tied to any specific repository being acted upon. Once the HMAC check passes for *any* configured organization, the raw payload is dispatched to handlers that act on unrelated data. `StatusHandler` in particular does no repository/organization scoping at all — it matches purely on `sha` across the entire Commits table — so a signature valid for one configured organization can be used to write status data onto commits belonging to a completely different organization's stack.

### Finding Description
`Shipit::WebhooksController#verify_signature` looks up the signing key like this: [1](#0-0) 
where `repository_owner` is read straight from the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization:)` supports a multi-tenant configuration where each organization has its own `webhook_secret`, set independently by whoever administers that organization's GitHub App: [3](#0-2) 

Because the HMAC is verified over the entire raw body, but the *choice of which secret to use* is itself taken from an attacker-controlled field inside that same body, an actor who legitimately knows the `webhook_secret` for **any one** configured organization (e.g., they administer their own low-trust org that is also onboarded to this Shipit instance) can craft an arbitrary JSON payload, set `repository.owner.login` to their own org (so `verify_signature` selects their own known secret and passes), and sign it with that secret — while every other field in the payload (sha, repository full_name, etc.) references a completely different, unrelated stack/organization.

Once verification passes, the payload is dispatched unmodified to handlers: [4](#0-3) 

`StatusHandler` performs *no* organization or repository check whatsoever — it looks up commits by `sha` globally: [5](#0-4) 

This breaks the intended binding: "the organization that authenticated (whose secret validated the signature) == the organization owning the data written by the handler." `StatusHandler` never checks that the commit's stack belongs to the organization that authenticated the request.

### Impact Explanation
An attacker who is a legitimate administrator of any one organization configured in a multi-tenant Shipit deployment (and thus knows that organization's `webhook_secret`) can forge `status` webhooks affecting **any commit in any other tenant's stack**, without needing credentials, session, or GitHub App access for the victim organization. `Commit#create_status_from_github!` updates the commit's status and can flip a commit from unresolved/pending to `success`: [6](#0-5) 

A forged `success` status can make a commit `deployable?` (bypassing real CI results): [7](#0-6) 

and, if the target stack has continuous deployment enabled, automatically trigger `ContinuousDeliveryJob`, i.e. an **unauthorized deploy** of a commit that never actually passed CI: [8](#0-7) 

This is a cross-organization write into another tenant's deploy-eligibility state and can lead to an unauthorized deploy — matching the High/Critical impact bar (escalation and unauthorized deploy) defined in scope.

### Likelihood Explanation
Requires the attacker to be an authenticated administrator of at least one organization onboarded to a shared, multi-tenant Shipit instance (a realistic and unprivileged-relative-to-other-tenants scenario, since Shipit explicitly supports multiple independent GitHub App configs per instance via `secrets.github`). No access to the victim organization's GitHub App, webhook secret, Shipit session, or API token is needed — only the ability to POST a crafted HTTP request with a correctly-signed payload using the attacker's own known secret. This is straightforward to exploit and requires no timing tricks or race conditions.

### Recommendation
`verify_signature` must not let a payload field determine both which secret validates the request and which entity is later trusted for authorization. At minimum:
1. After signature verification, re-derive and enforce that every handler's target repository/organization matches the *verified* `repository_owner`/organization used to select the secret, rejecting mismatches.
2. `StatusHandler` (and any other handler that doesn't already scope by repository, e.g. relying only on `sha`) must scope its lookup by the repository/stack that belongs to the verified organization, not do a global `Commit.where(sha:)` scan.
3. Consider deriving the organization for secret-selection from a source that cannot be freely rewritten independent of the payload's `repository.full_name` (e.g., verifying both fields are consistent and belong to the same tenant before verification/dispatch).

### Proof of Concept
Given a Shipit instance configured with `secrets.github` for two organizations, `attacker-org` (secret known to the attacker) and `victim-org` (unrelated stack `victim-org/victim-repo` with a tracked commit `SHA_V`):

```
POST /github_webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>

body = {
  "sha": "SHA_V",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" } }
}
```

`verify_signature` calls `Shipit.github(organization: "attacker-org")`, validates with the attacker's own known secret, and succeeds. `StatusHandler#process` then executes `Commit.where(sha: "SHA_V")` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged `success` status onto a commit the attacker never had access to, potentially triggering `schedule_continuous_delivery` and an unauthorized deploy in `victim-org`'s stack.
