### Title
Predictable/grindable pseudo-randomness in oscript `number_from_seed()` allows an unprivileged AA trigger sender to bias outcomes - (File: `formula/evaluation.js`)

### Summary
The `number_from_seed()` oscript function, exposed to Autonomous Agent (AA) formulas, derives a "random" number by taking `sha256(seed)` of an author-supplied seed expression. Because AA formulas can access self-known, pre-computable values such as `trigger.unit` (the hash of the very unit the sender is about to broadcast) or `timestamp`/`mci` (values fixed at unit composition time), an unprivileged trigger sender fully controls or can predict the seed *before* posting the triggering unit. This lets the attacker compute the resulting "random" value for many candidate unit contents locally (grinding), and only actually broadcast the unit whose derived value is favorable — the same fundamental grinding vulnerability described in the external report for `block.number`/`block.timestamp`.

### Finding Description
`number_from_seed` is implemented in `formula/evaluation.js`: [1](#0-0) 

It hashes the seed expression the AA author selects and derives a deterministic Decimal from the digest. Nothing in the implementation or in `formula/validation.js`'s handling of `number_from_seed` enforces that the seed be unpredictable to the trigger sender: [2](#0-1) 

The oscript grammar exposes `trigger.unit`, `trigger.initial_unit`, `timestamp`, and `mci` as first-class expressions available inside AA formulas: [3](#0-2) 

`trigger.unit` resolves to the exact unit hash of the trigger that is being processed — a value the sender computes locally (client-side) before broadcasting the unit, since the unit hash is a hash of author-controlled content (data payload, timestamp, parent selection, etc., composed in `composer.js`). `timestamp` in AA formula context is the last-ball (MC) unit's timestamp, which is also known/estimated by the sender ahead of time via `objMcUnit.timestamp` used in trigger estimation: [4](#0-3) 

Crucially, ocore provides an explicit "dry run" trigger-estimation pathway (`estimatePrimaryAATrigger` / `dryRunPrimaryAATrigger`) that lets a client compute what an AA response — including any `number_from_seed(...)` result — would be for a candidate trigger unit *before* actually posting it: [5](#0-4) 

This dry-run capability is functionally identical to the "attack function" described in the external report: the caller repeatedly evaluates the pending trigger content against known formulas/state and only proceeds to actually submit (post) the unit once the "random" number matches the desired outcome. If an AA developer writes logic such as `number_from_seed(trigger.unit)`, `number_from_seed(timestamp)`, or `number_from_seed(trigger.unit || timestamp)` to pick a winner, split funds, or assign a probabilistic outcome, an ordinary trigger sender can iterate candidate unit content (varying `trigger.data`, nonce fields, or timing) locally/via dry-run, compute the resulting `number_from_seed` value off-chain for each candidate, and only broadcast the one instance whose derived value favors them.

Unlike the original report (which required a compromised layer-zero-endpoint, a privileged actor), this ocore analog requires **no privileged access at all** — any regular AA trigger sender is the "randomness roller," matching the report's core weakness (self-controlled/predictable entropy source feeding a payout decision) but with a strictly *lower* barrier to exploitation.

### Impact Explanation
If an AA relies on `number_from_seed` seeded (even partially) by trigger-controlled or otherwise pre-computable values (`trigger.unit`, `trigger.data`, `timestamp`, `mci`) to make asset-affecting decisions — e.g., selecting a lottery/game winner, splitting a payout probabilistically, or granting a bonus — a malicious trigger sender can grind trigger content until the derived number favors them, guaranteeing a win/payout that was supposed to be probabilistic. This directly causes AA fund loss for the AA (or for other legitimate participants) as the "random" selection is no longer fair, satisfying the "AA fund loss" impact category.

### Likelihood Explanation
Likelihood depends entirely on AA design: this is not a bug in a specific shipped, audited AA in this repository, but a systemic design trap in the oscript primitive itself, since `number_from_seed` is documented and commonly used by third-party AA authors for randomness (lotteries, gambling, giveaways). Given the ease of grinding (client-side hash computation, dry-run trigger estimation already provided by ocore, and full control of unit content prior to broadcast), any AA using an unprotected/trigger-controlled seed is straightforwardly exploitable by an unprivileged attacker — no special access, timing races, or infrastructure compromise required, making exploitation practical whenever the anti-pattern occurs.

### Recommendation
- In documentation and by convention, require the seed passed to `number_from_seed` to include an entropy source that is **not known or influenceable by the trigger sender at compose time** (e.g., a subsequent, independent data feed value, an oracle-provided value tied to a future block/mci not yet known when the trigger was created, or a commit-reveal scheme spanning at least two units separated by finality).
- Consider adding a validation-time warning/lint (in `formula/validation.js`) when `number_from_seed`'s seed expression syntactically depends solely on `trigger.unit`, `trigger.data`, `timestamp`, or `mci` without any external/oracle-derived input, to reduce accidental unsafe usage by AA authors.
- Document in the AA authoring guide (and enforce via linting tooling shipped with ocore) that "random" outcomes must not be derivable/predictable by the same party that constructs the triggering unit, mirroring the report's exact guidance to avoid attacker-controlled/predictable entropy in payout-determining logic.

### Proof of Concept
Consider an AA that awards a bonus to the trigger sender if a coin flip is favorable, seeded from the trigger unit hash:
```
{
    $r = number_from_seed(trigger.unit, 0, 1);
    if ($r == 1) {
        send_payment ... // large payout to trigger.address
    }
}
```
An attacker can grind the outcome as follows, mirroring the report's `attack()` loop but requiring no privileged endpoint:
```
1. Build candidate trigger units locally (e.g., vary trigger.data.nonce or timestamp).
2. For each candidate unit, compute unit_hash = objectHash(candidateUnit)  // trigger.unit
3. Compute r = sha256(unit_hash) -> Decimal in [0,1] range using the same algorithm as
   formula/evaluation.js's `number_from_seed` case (lines 1893-1917).
4. If r == 1 (desired outcome), broadcast candidateUnit as the real trigger.
5. Otherwise, discard candidateUnit and try a new nonce/timestamp; repeat.
```
Because `trigger.unit` is deterministically known to its author before broadcast (and ocore even exposes `estimatePrimaryAATrigger`/`dryRunPrimaryAATrigger` to preview the AA response for a not-yet-posted unit — see `aa_composer.js` lines 152-213), the attacker can iterate until a winning nonce is found and only post that unit, guaranteeing the outcome in their favor.
