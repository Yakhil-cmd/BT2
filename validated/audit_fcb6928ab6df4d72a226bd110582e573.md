### Title
Attacker-controlled route executes arbitrary contract code under the caller's authorization, enabling wallet theft — (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary

The iTop advisory is a code-injection class bug: attacker-supplied data is interpreted as executable code. The analog in XOXNO Lending is the swap router's payload-driven call surface. `execute_strategy` decodes an attacker- (or route-builder-)supplied `StrategyPayload` whose `assets` registry directly names the pool and token contracts each hop calls (`execute_op`, `contracts/swap-aggregator/src/execute/mod.rs:152-158`). The router keeps no allowlist of pools or tokens, so a malicious route injects arbitrary contract code onto the call stack. Because the swap runs beneath the caller's `require_auth` tree (direct `execute_strategy`, or the controller's `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` strategies), injected code can invoke `token.transfer(victim, attacker, …)` and Soroban records it as a child of the victim's authorization entry — executing if the victim signs the simulated tree. The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a rogue hop pool drains Alice's entire unrelated wallet token while paying a "fair" swap output.

### Finding Description

`run` in `contracts/swap-aggregator/src/execute/mod.rs` takes `assets: Vec<Address>` from caller-supplied XDR and indexes it blindly for `hop.pool`, `hop.token_in`, `hop.token_out` (lines 154-156). `venues::dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:23-40`) then invokes the named pool through the venue adapter; the only validation is measured balance deltas on the router's own token balances. Nothing restricts which contract the pool address must be — the venue opcode only selects which function name/ABI is invoked, not which contract.

This is a code-injection primitive: the payload author chooses which code executes. A rogue "pool" contract's `swap` (or `swap_exact_amount_in`, `get_tokens`, etc.) runs with the full call-stack context, including the victim's `require_auth` for the enclosing `execute_strategy`/`swap_collateral`. Per Soroban auth semantics, any `from.require_auth()` the rogue code triggers on a token contract is recorded as a sub-invocation of the victim's entry. The victim's wallet produces the auth tree via `simulateTransaction` in recording mode, which attaches the rogue transfer; if the victim signs that tree — which non-inspecting clients do — the transfer executes. The router's min-out check and the controller's final health-factor gate are both satisfied because the rogue pool (or a real pool behind it) still pays a fair output. The theft is therefore unbounded by the routed amount: it covers any balance/allowance of the victim reachable via `transfer`/`transfer_from` under their auth.

### Impact Explanation

Theft of user funds beyond the routed amount. A single crafted `routeXdr` presented to a victim swapper (via phishing, a compromised/malicious quote frontend, or a malicious strategy suggestion) transfers arbitrary tokens the victim holds — e.g. their entire balance of a token the protocol never listed — to the attacker, as demonstrated in the test (`WALLET_BALANCE` = 77,770 units moved to the attacker while the swap itself settles correctly). The same primitive can also invoke other victim-authorized functions, not only `transfer`, making it a general code-execution-under-auth injection rather than a mere slippage issue.

### Likelihood Explanation

Requires a victim to sign a route containing the injected hop — comparable to AC:H/PR:L in the source advisory. The exposure is structural, not hypothetical: every `execute_strategy` user and every controller strategy user signs an auth tree whose contents are dictated by the route payload, and neither the router nor the controller bounds what that payload calls. The codebase's own threat model (`docs/explanation/threat-model.md:154-165`) acknowledges the path and shifts mitigation entirely to client-side auth-tree inspection, which is an off-chain assumption about wallet behavior rather than a contract control.

### Recommendation

Enforce venue allowlisting in the router: maintain an owner-managed registry of approved pool addresses (per venue) and reject hops whose `pool` is not registered. Short of that, validate pool identity where derivable (e.g., verify Soroswap pools against the factory, Aquarius pools against `share_id`/factory) so the payload cannot name arbitrary contracts. Note the whitelist exists today only for fee placement, not call admission.

### Proof of Concept

`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` already implements it: `RogueHopPool.swap` calls `token.transfer(victim, attacker, amount)` inside a route hop; simulation records the stolen transfer under Alice's `swap_collateral` auth entry, and enforcing mode executes it when signed — Alice loses `WALLET_BALANCE` of an unrelated token while receiving fair ETH output. The real router exposes the identical surface since `hop.pool` is payload-controlled and never checked against an allowlist.
