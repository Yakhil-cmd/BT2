### Title
Webhook signature only authenticates the payload's declared organization, not the repository/commit actually written — cross-repository commit status forgery via `StatusHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `organization.login`) [1](#0-0) . That signature only proves the payload was produced with the secret configured for that particular organization entry in `config/secrets.yml` (Shipit supports one webhook secret per GitHub org) [2](#0-1) . However, once the signature passes, `Shipit::Webhooks::Handlers::StatusHandler#process` acts on the payload's `sha` field with **no repository scoping at all**, updating the status of any commit in the entire Shipit instance whose SHA matches: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . The value that was cryptographically verified (the organization owning the webhook secret) is never checked against the value that is actually mutated (the commit's owning repository/stack).

### Finding Description
In a multi-org Shipit deployment, `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` are keyed per-organization [4](#0-3) [5](#0-4) . Each organization in a multi-tenant configuration typically has its own GitHub App and its own webhook secret, configured by that organization's own administrators. Signature verification therefore proves only "this request was signed with organization A's secret" — it says nothing about which repository or commit the payload's other fields refer to.

`StatusHandler`, which processes GitHub `status` events, never consults `repository.full_name`, `repository.owner.login`, or any other value tying the update to the organization whose secret validated the request. It blindly looks up commits process-wide by `sha` and calls `commit.create_status_from_github!(params)` [3](#0-2) . Commit statuses are used elsewhere by Shipit to determine CI readiness/deployability (e.g., required contexts under `ci.require` gating deploys and the merge queue), so this handler writes security-relevant state.

Other handlers correctly scope by repository via `Repository.from_github_repo_name(params.repository.full_name)` before acting (see `PushHandler`/`Handler#stacks`, and the `PullRequest` handlers) [6](#0-5) [7](#0-6) , but even those still rely on `repository.full_name`, a field that is never included in the signature-selection logic (`repository.owner.login`) — so nothing enforces that `full_name`'s owner segment matches the org whose secret validated the signature. `StatusHandler` is the most severe instance because it has no repository scoping whatsoever.

### Impact Explanation
Any organization onboarded into a shared, multi-org Shipit instance (i.e., any org administrator who legitimately possesses their own GitHub App's webhook secret, which they configured and know) can forge a `status` webhook event — signed correctly with their own org's secret — carrying an arbitrary `sha`, `state: "success"`, and `context` matching a required CI check name used by a victim organization's stacks hosted on the same instance. Because `StatusHandler` performs a global `Commit.where(sha:)` lookup with no ownership check, this forges a passing CI status on a commit belonging to a repository the attacker does not control. If that context is one Shipit checks via `ci.require` before allowing merges/deploys, this can cause an unauthorized merge or unauthorized deploy of a commit that never actually passed CI — matching the Critical impact bucket ("unauthorized deploy, rollback, or merge").

### Likelihood Explanation
Exploitability requires the attacker to control (or be an administrator of) at least one GitHub organization/App entry configured in the same multi-org Shipit installation as the victim organization — a realistic scenario for shared internal deployment platforms serving multiple teams/orgs. No Shipit session, `ApiClient` token, or GitHub org membership in the victim org is required; only knowledge of the attacker's own org's webhook secret (which they set themselves) and the victim commit's SHA (routinely public, e.g., via GitHub UI/API for any commit on a repo pushed to).

### Recommendation
In `StatusHandler` (and any other handler acting on payload data), scope lookups to the repository/stacks whose owning organization matches `repository_owner`/`repository.full_name`, and have `WebhooksController` pass the verified organization down to handlers so they can assert equality between the signed organization and the repository actually mutated, rejecting mismatches. Concretely, change `StatusHandler#process` to iterate `stacks.joins(:commits).where(sha: params.sha)` scoped via `Handler#stacks` (which resolves through `repository.full_name`), and additionally validate that `repository.full_name`'s owner segment equals the `repository_owner` used for signature verification.

### Proof of Concept
1. Shipit is deployed with two GitHub orgs configured, each with its own webhook secret: `victim-org` and `attacker-org` (as supported by `config/secrets.*.yml` multi-org schema) [8](#0-7) .
2. Attacker, an admin of `attacker-org`'s GitHub App, knows `attacker-org`'s webhook secret.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha with a required CI context pending/failing>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
signed with `attacker-org`'s webhook secret (HMAC over the raw body) so it satisfies `verify_signature` [4](#0-3) .
4. `StatusHandler#process` finds the commit by `sha` regardless of which org it belongs to and creates a "success" status on it [3](#0-2) , potentially satisfying `ci.require` for `victim-org`'s stack and enabling deploy/merge of a commit that never passed real CI.

Note: I was unable to fully trace, within tool budget, the exact downstream code path where a forged "success" `GithubStatus` record is consumed by `ci.require`/merge-queue gating logic (`app/models/shipit/commit_checks.rb`, `app/models/shipit/stack.rb`) to confirm the precise deploy-blocking conditions it bypasses; a Devin session with full file access would be needed to enumerate every `ci.require` consumer and confirm end-to-end exploitability against a specific Shipit configuration.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
