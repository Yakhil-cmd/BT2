### Title
Cross-repository forged commit status can trigger continuous deployment on a victim stack via sha-only lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The question's target guard (`Commit#schedule_continuous_delivery`, `app/models/shipit/commit.rb:281-287`) never checks repository identity, but that alone is not exploitable in isolation because a `Status` object only ever reaches that guard through `Status#schedule_continuous_delivery` after a `Status` row is created on a specific `Commit`. The actual break in the binding is one hop upstream: `Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)` — a global, cross-stack lookup with no repository scoping at all — while `WebhooksController#verify_signature` only authenticates the webhook at the *organization* level (`Shipit.github(organization: repository_owner)`), not per repository. Any attacker who can get GitHub to emit a validly-signed status webhook for a commit sha that also exists in a victim's stack (e.g., because their own repo shares that commit, as happens with forks) can write a `Status` into the victim's `Commit`, and that `Status` creation still fires `schedule_continuous_delivery`, `ContinuousDeliveryJob`, and ultimately `Stack#trigger_continuous_delivery` — with the only defense being the victim stack's own lock state, not repository identity.

### Finding Description
The claimed-safe binding would be: `status_webhook.repository == commit.stack.repository` (i.e., a status delivered for repo A can only ever mutate commits that belong to a stack whose `repository` is repo A). Tracing the code shows this equality is never enforced:

- `WebhooksController#verify_signature` [1](#0-0)  authenticates the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e. one webhook secret per GitHub organization/app installation [2](#0-1) , and `verify_webhook_signature` only checks the HMAC against that org-wide secret, with no comparison of `params['repository']['full_name']` to any specific stack's repository [3](#0-2) .
- Once signature verification passes for the event's organization, `StatusHandler#process` resolves target commits purely by sha, across the entire database, regardless of which repository the payload claims: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) .
- `Commit#create_status_from_github!` unconditionally creates the `Status` on whatever commit/stack was matched [5](#0-4) .
- `Status` creation fires `schedule_continuous_delivery` in an `after_commit` callback, delegating straight to `commit.schedule_continuous_delivery` [6](#0-5) .
- `Commit#schedule_continuous_delivery` gates only on `deployable? && stack.continuous_deployment? && stack.deployable?` — none of which reference `params['repository']` or any concept of "who sent this webhook" [7](#0-6) .
- `ContinuousDeliveryJob#perform` re-checks `continuous_deployment?`, the delivery schedule, and `occupied?`, then calls `stack.trigger_continuous_delivery` [8](#0-7)  — again, no repository check.

Root cause: the GitHub App/webhook trust boundary is scoped to an **organization** (one `webhook_secret` per org, configurable multi-org in `secrets.yml` [9](#0-8) ), but the data-layer trust boundary that actually decides which `Commit`/`Stack` gets mutated is scoped only to **sha**, with no re-validation against the specific repository that owns that sha within Shipit's own `Repository`/`Stack` model. Any org member (or any repo the org-wide GitHub App installation covers) that shares a commit sha with a victim's tracked commit — trivially achievable by forking a public repo within the same org, since forked commits retain identical shas — can deliver a real, validly-signed "status" event for their own repo and have it silently attributed to the victim's `Commit`/`Stack`.

Existing guards checked and found insufficient for this path: `drop_unhandled_event` only filters by event type, not repository [10](#0-9) ; the `ExplicitParameters` schema on `StatusHandler` validates field types/presence (`sha`, `state`, etc.) but never validates or cross-checks `params['repository']` [11](#0-10) ; `verify_signature` authenticates the org, not the repo [12](#0-11) .

### Impact Explanation
A "status" webhook forged/emitted for a repository the attacker legitimately owns or controls (within the same GitHub organization/App installation as the victim) can create a `Status` on a victim `Commit` it was never meant to touch, and that write is enough to trigger `ContinuousDeliveryJob` and `Stack#trigger_continuous_delivery` on the victim stack — an unauthorized deploy path gated only by the victim stack's own `lock_reason`/`occupied?`/`continuous_delivery_schedule` state, not by any check that the request actually originated from that stack's repository. This is a payload for one repository mutating another's commit/stack and can drive an unauthorized deploy, matching the Critical impact category. Repeatable against any stack in the installation whose tracked commits happen to share a sha with a repo the attacker controls (most easily via forks of the victim's own public repository within the same org/installation).

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a repository within the same GitHub organization/App installation as the victim's Shipit stack (or any org whose events reach the shared webhook secret), (2) that repository shares at least one commit sha with a commit already tracked in the victim's stack (trivial via forking), (3) the victim stack has `continuous_deployment: true` and is otherwise deployable/unlocked. No Shipit session, API token, or webhook secret is needed by the attacker — GitHub itself signs and delivers the webhook for events on the attacker's own repo. This requires no privileged Shipit role, matching the threat model in the rules.

### Recommendation
Scope commit/status resolution to the reporting repository, not sha alone: in `StatusHandler#process`, restrict `Commit.where(sha: params.sha)` to commits whose `stack.repository` matches the payload's `repository.full_name`/`owner.login` (join through `Stack`/`Repository` and filter), and reject/ignore the event otherwise. Consider moving webhook signature verification to per-stack/per-repository secrets rather than per-organization where feasible.

```ruby
# test/models/webhooks/handlers/status_handler_test.rb (illustrative)
require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    test "cross-repo forged status does not deploy a locked victim stack" do
      victim_stack = shipit_stacks(:shipit) # continuous_deployment: true, lock_reason: "Maintenance"
      victim_stack.update!(continuous_deployment: true, lock_reason: "Maintenance")
      shared_sha = victim_stack.commits.last.sha

      forged_params = OpenStruct.new(
        sha: shared_sha, state: 'success', description: nil,
        target_url: nil, context: 'ci/forged', created_at: Time.now,
        repository: { full_name: 'attacker/unrelated-repo' } # different repo entirely
      )

      assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
        Shipit::Webhooks::Handlers::StatusHandler.new.call(
          'sha' => forged_params.sha, 'state' => forged_params.state,
          'repository' => forged_params.repository
        )
      end
    end

    test "cross-repo forged status deploys an unlocked victim stack" do
      victim_stack = shipit_stacks(:shipit)
      victim_stack.update!(continuous_deployment: true, lock_reason: nil)
      shared_sha = victim_stack.commits.last.sha

      assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
        Shipit::Webhooks::Handlers::StatusHandler.new.call(
          'sha' => shared_sha, 'state' => 'success',
          'repository' => { 'full_name' => 'attacker/unrelated-repo' }
        )
      end
    end
  end
end
```
Both assertions on the same `Commit.where(sha:)` binding demonstrate that the only variable is the victim stack's own lock state — `params['repository']` is read nowhere in the reachable path (`StatusHandler#process` → `create_status_from_github!` → `Status` → `schedule_continuous_delivery` → `ContinuousDeliveryJob`), confirming the equality `status_webhook.repository == commit.stack.repository` is never checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
