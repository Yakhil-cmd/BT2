### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` updates commit statuses by looking up commits solely by SHA, without ever confirming that the `repository` field of the signed webhook payload corresponds to the stack/repository that owns the matched `Commit` record. This breaks the binding between "the organization/repository whose GitHub App signed this webhook" and "the repository whose commit record is written," letting a status event legitimately signed for one repository be applied to a same-SHA commit tracked under a completely different stack.

### Finding Description
GitHub's webhook signature (`X-Hub-Signature`) authenticates that the *entire raw payload* was sent by a specific organization's installed GitHub App — this is checked in `WebhooksController#verify_signature`, which selects the app via `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . This only proves the payload came from GitHub for that org; it says nothing about which `Stack`/`Commit` records in the Shipit database should be mutated as a result — that scoping must be enforced by each handler.

The base `Handler` class defines a `repository_name`/`stacks` helper explicitly intended to scope work to the repository named in the payload [2](#0-1) , and `CheckSuiteHandler` correctly uses it to scope commit lookups to `stacks` derived from `repository_name` [3](#0-2) .

`StatusHandler`, however, bypasses this scoping entirely:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

It never consults `payload.dig('repository', 'full_name')` to filter which `Commit` rows are eligible. Any `Commit` record in the entire Shipit installation that happens to share the SHA in the payload will have its status updated — regardless of which stack/repository it actually belongs to.

This is exploitable whenever the same commit SHA is legitimately reachable in more than one repository tracked by different stacks — e.g. forked repositories, repositories split from a common template/monorepo, or shared ancestor commits before divergence. An attacker who has push/CI access to repository A (where the GitHub App is installed and webhook secret is valid for that org) can create a `status` event — real or via any integration with `repo:status` write access on A — for a commit SHA that is shared with repository B's history. The resulting signed webhook (validated against org A's secret) is processed, and `StatusHandler` updates the status of the matching `Commit` row that belongs to stack B, in a different repository/organization than the one whose signature was verified.

### Impact Explanation
Commit statuses gate deploy safety checks (`ci.require`) and CI-blocking logic used before a commit is considered deployable, per `Shipit::Commit#create_status_from_github!` and the CI-status machinery referenced in `app/models/shipit/commit.rb` and `app/models/shipit/stack.rb`. By forging a passing/successful status on a commit belonging to a stack the attacker has no legitimate relationship to, an attacker can potentially mark an otherwise CI-pending or CI-failing commit in an unrelated repository as deployable, contributing to an unauthorized deploy decision. This crosses the "organization authenticated versus repository written" trust boundary the rules call out, and lands in the High-impact category (escalation affecting deploy-gating state across repositories) — bordering on Critical if it directly enables an unauthorized deploy for another organization's stack.

### Likelihood Explanation
Exploitation requires: (1) the attacker controls a repository/CI integration within an org that has the GitHub App properly installed (so they can generate a validly-signed `status` webhook), and (2) a SHA collision in the literal sense of "same real commit accessible from two different repos tracked as separate Shipit stacks" (e.g., forks, template-derived repos, monorepo splits) — not a cryptographic hash collision. This is a realistic but non-trivial precondition; it depends on Shipit's specific deployment topology (multiple related repos/forks tracked as separate stacks). Likelihood is therefore moderate rather than trivial, but the missing repository-scoping is an unambiguous code defect independent of how often the precondition arises.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks belonging to the payload's repository, mirroring the pattern already used in `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a webhook signed for organization/repository A can only mutate commit-status state for stacks that actually correspond to repository A's payload, restoring the binding between the authenticated repository and the repository being written.

### Proof of Concept
1. Attacker controls (or has CI/status-write access to) `org-a/repo-a`, which has the Shipit GitHub App installed with a valid `webhook_secret`.
2. `org-b/repo-b` is a fork (or template-derived sibling) of `repo-a`, tracked as a separate Shipit stack, and both repos still share commit `sha1` from before divergence; `sha1` is tracked in `repo-b`'s stack as CI-pending.
3. Attacker sets a `success` status on commit `sha1` in `repo-a` (via API/CI integration they control), generating a `status` webhook event with `repository.full_name = "org-a/repo-a"`, correctly signed with org A's `webhook_secret`.
4. `WebhooksController#verify_signature` validates the signature against org A's app and accepts the request [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: 'sha1')`, which also matches the `Commit` row belonging to `repo-b`'s stack, and marks it as having a successful status — despite the webhook never being signed for, or originating from, `repo-b`'s organization [4](#0-3) .
6. `repo-b`'s stack now treats `sha1` as passing the configured `ci.require` status context, potentially unblocking a deploy the attacker has no authorization over.
