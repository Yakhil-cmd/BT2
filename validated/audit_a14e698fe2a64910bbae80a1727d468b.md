## Finding: Uncontrolled Resource Consumption in Private Payment Chain Handling (`wallet.js: handlePrivatePaymentChains`)

### Title
Unbounded String/Array Content in Private Payment Chains Bypasses Node-Count Depth Check, Enabling Resource-Exhaustion DoS - (File: `wallet.js`)

### Summary
`handlePrivatePaymentChains` (invoked for the `private_payments` device-message subject, and from `handlePrivatePaymentFile`) processes attacker-supplied private payment chains (`body.chains`) without any limit on the total content size of the chain data (string lengths, array counts). The only upstream guard, `isTooDeeplyNestedOrHasTooManyNodes`, bounds node *count* and nesting *depth* but not the *length* of string values, so a private-payment counterparty (a paired device) can submit a small number of large-string fields that pass the check yet trigger expensive recursive hashing/stringification/DB operations, echoing the "unbounded allocation while parsing" root cause of GHSA-rxmj-hg9v-vp3p.

### Finding Description
Every message received from a paired device is dispatched through `handleMessageFromHub` in `wallet.js`, which applies a single generic guard: [1](#0-0) 

```
function handleMessageFromHub(ws, json, device_pubkey, bIndirectCorrespondent, callbacks){
	if (isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000))
		return callbacks.ifError("message from hub is too deeply nested or has too many nodes");
```

`isTooDeeplyNestedOrHasTooManyNodes` in `string_utils.js` only counts nodes and nesting depth — it never sums up string lengths: [2](#0-1) 

By contrast, the sibling helper `isTooBigObj` explicitly tracks a `length` accumulator for exactly this reason (to bound total string content), and is used elsewhere (e.g., AA trigger validation, formula evaluation) specifically to stop large-string DoS: [3](#0-2) [4](#0-3) 

`handlePrivatePaymentChains` is reached for the `private_payments` subject and only performs shape/type checks (`isNonemptyArray`, `isNonemptyString`, `isNonemptyObject`) with **no bound on string length, on the number of chains, or on chain length**: [5](#0-4) [6](#0-5) 

It then immediately calls `objectHash.getBase64Hash(arrChains)` over the entire structure to compute a cache key, and for every chain calls `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` — both of which recursively canonicalize/stringify the object (see `getJsonSourceString`, used for hashing) — before any content-size validation occurs: [7](#0-6) [8](#0-7) 

Each chain is then routed to `network.handleOnlinePrivatePayment`, which for light clients with a multi-element chain immediately re-serializes and persists the entire (attacker-sized) chain to the database via `JSON.stringify`: [9](#0-8) 

Unlike the unit/joint intake paths (`'joint'`, `'post_joint'`, `'hub/deliver'`), which all gate on `isTooDeeplyNestedOrHasTooManyNodes` *and* rely on `constants.MAX_UNIT_LENGTH`-style payload size checks downstream in `validation.js` (`objectLength.getTotalPayloadSize`), the private-payment-chain path has no analogous ceiling on aggregate string content: [10](#0-9) [11](#0-10) [12](#0-11) 

### Impact Explanation
A paired device (private-payment counterparty) — an actor explicitly reachable without special privileges — can send a `private_payments` message whose JSON structure has few nodes/shallow depth (satisfying the 20-depth/100000-node limit) but whose individual string fields (e.g. `unit`, `payload.outputs[i].output_hash`, `blinding`, `payload.asset`) are megabytes long. This bypasses the only size guard, forcing the victim wallet to repeatedly canonicalize/hash/stringify and persist these oversized objects to disk (`unhandled_private_payments` table) for each of potentially many chains in a single message, consuming excessive CPU and memory and potentially disk space, causing denial of service on the recipient wallet/light client — consistent with CWE-770/CWE-120 uncontrolled resource consumption.

### Likelihood Explanation
The `private_payments` subject is processed for any correspondent device that has successfully paired with the victim (a normal, low-privilege interaction pattern for chat/wallet apps built on ocore), and `handlePrivatePaymentChains` performs no length-based validation prior to expensive operations, making exploitation straightforward for any paired device or malicious `.textcoin` file content handled via `handlePrivatePaymentFile`.

### Recommendation
Apply an `isTooBigObj`-style aggregate string-length bound (in addition to the existing node/depth check) to `body` in `handleMessageFromHub` before dispatch, and/or add explicit length limits on `arrChains`, chain length, and individual string fields (`unit`, `blinding`, `output_hash`, `asset`) inside `handlePrivatePaymentChains` before calling `objectHash.getBase64Hash` or persisting to the database.

### Proof of Concept
1. Pair a malicious device with the victim wallet.
2. Send a `pairing`-authenticated device message with `subject: "private_payments"` and `body.chains` containing a modest number of chain elements where one or more string fields (e.g., `payload.outputs[0].output_hash`, `unit`, `blinding`) are several megabytes of repeated characters.
3. Because `isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)` only counts nodes/depth (not string length), the message passes this check.
4. `handlePrivatePaymentChains` proceeds to call `objectHash.getBase64Hash(arrChains)` and per-chain hashing/stringification/DB inserts on the oversized payload, consuming disproportionate CPU/memory/disk relative to the message's "small" node count, repeatable at will to exhaust victim resources.

function isTooDeeplyNestedOrHasTooManyNodes(obj, depthLimit = 100, nodesLimit = 10000) {
	let nodeCount = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit)
			return true;
		if (variable === null || typeof variable !== "object")
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			nodeCount += Object.keys(variable).length;
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}

function isTooBigObj(obj, { depthLimit = 100, nodesLimit = 10000, lengthLimit = 1000000 }) {
	let nodeCount = 0;
	let length = 0;

	function check(variable, depth){
		if (depth > depthLimit || nodeCount > nodesLimit || length > lengthLimit)
			return true;
		if (typeof variable === "string")
			length += variable.length;
		else if (typeof variable === "number" || typeof variable === "boolean")
			length += variable.toString().length;
		else if (variable === null)
			length += 4; // "null"
		else if (typeof variable !== "object")
			throw Error("isTooBigObj: unexpected type=" + (typeof variable) + " of " + variable);
		if (length > lengthLimit)
			return true;
		if (typeof variable !== "object" || variable === null)
			return false;
		if (Array.isArray(variable)) {
			nodeCount += variable.length;
			for (let v of variable)
				if (check(v, depth + 1))
					return true;
		}
		else {
			const keys = Object.keys(variable);
			nodeCount += keys.length;
			length += keys.reduce((sum, key) => sum + key.length, 0);
			for (let key in variable)
				if (check(variable[key], depth + 1))
					return true;
		}
		return false;
	}

	return check(obj, 1);
}
