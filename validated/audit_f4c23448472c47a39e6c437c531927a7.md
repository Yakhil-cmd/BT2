### Title
Unauthenticated `PreStxOp.output` lets an attacker impersonate any Stacks address as `sender`/`stacker` in `TransferStxOp`/`StackStxOp`/`DelegateStxOp`, enabling theft of victim STX balances - (File: `stackslib/src/chainstate/burn/db/processing.rs`)

### Summary
`PreStxOp` is accepted with zero validation (`BlockstackOperationType::PreStx(_) => Ok(())`), and its `output` field — later reused as the `sender`/`stacker` identity for `StackStxOp`, `TransferStxOp`, and `DelegateStxOp` — is only derived from the first output of an attacker-controlled Bitcoin transaction, with no signature proving the named address's owner authorized anything. Because Bitcoin authorization only proves control over the second output (vout=1) spent as input to the follow-up op, and that spending key is never required to match `output`, an attacker can name an arbitrary victim Stacks address as `sender` and force real, unconsented STX operations (a direct theft in the `TransferStxOp` case) against that victim.

### Finding Description
The broken equality: the system treats "there exists a `PreStxOp{output: X}` record, later spent at vout=1 by transaction T" as proof that "the owner of X authorized whatever op T encodes." In reality, `X` (the `output` field) is taken from `outputs.get(0)` of the attacker's own `PreStxOp` Bitcoin transaction [2](#0-1) , while the cryptographic authorization for the follow-up op comes only from control of vout=1's private key, checked purely as "does this input reference the PreStxOp's txid, vout=1" via `get_sender_txid` [3](#0-2) . Nothing requires vout=0 (`output`/`sender`) and vout=1 (the input later spent) to be controlled by the same key.

Dispatch confirms `PreStxOp` skips `check()` entirely: [1](#0-0) . The parser for follow-up ops simply looks up the `PreStxOp` by txid and uses `pre_stx.output` as `sender` unconditionally: [4](#0-3) , and identically for `StackStxOp` and `DelegateStxOp` at lines 929-992 of the same file.

`TransferStxOp::check()` only guards against zero amount and self-send, never validating `sender` ownership: [5](#0-4) . The op is then executed with a real, unconditional STX transfer using `sender` as the debited principal: [6](#0-5) , which calls `run_stx_transfer`/`stx_transfer_consolidated` directly against the ledger with no additional signature check [7](#0-6) .

Attacker's exact call/exploit flow:
1. Attacker crafts a `PreStx`-opcode Bitcoin transaction with vout=0 set to the victim's Stacks address (encoded as a Bitcoin address) and vout=1 set to an address the attacker controls.
2. This is accepted unconditionally into `pre_stx_op_map`/`burnchain_db` (no `check()`), recording `PreStxOp{output: victim}`.
3. Attacker crafts a second Bitcoin transaction with the `TransferStx` opcode whose sole input spends vout=1 of the first transaction (signed with the attacker's own key — no involvement of the victim).
4. `TransferStxOp::get_sender_txid`/`parse_from_tx` resolves `sender = pre_stx.output = victim`, `recipient` = attacker-chosen address, `transfered_ustx` = attacker-chosen amount.
5. `TransferStxOp::check()` passes trivially (amount != 0, sender != recipient).
6. `process_transfer_ops` executes `stx-transfer?` moving `transfered_ustx` from the victim's real balance to the attacker's recipient, with no signature from the victim ever checked.

Why existing guards fail: `verify-not-prepare-phase`, `check-pox-lock-period`, `verify-signer-key-grant`, and pox-4/pox-5's `stack-stx` guards (`>= (stx-get-balance tx-sender) amount-ustx)` etc., all operate on the assumption that `tx-sender`/`sender` is a genuinely authorized principal — but for burnchain ops that principal is the unauthenticated `pre_stx.output`, so all downstream contract-level checks (`consume-signer-key-authorization`, balance checks) are checking the wrong party's consent, not preventing the impersonation itself.

### Impact Explanation
This is Critical: it is direct, unbacked theft of a victim's already-existing STX balance via `TransferStxOp` (funds move from `sender=victim` to an attacker-chosen `recipient` with zero victim signature), and, via `StackStxOp`/`DelegateStxOp`, it forces unsigned/unconsented stacking or delegation actions locking a victim's real STX under attacker-chosen PoX reward addresses or delegates — matching "theft ... of ... STX" (Critical) and, at minimum, "an unsigned stacking action" (High) for the Stack/Delegate variants. This is repeatable: each `PreStxOp`/follow-up pair costs only Bitcoin transaction fees and can target any victim address with any balance, any number of times.

### Likelihood Explanation
Preconditions are minimal and entirely within the stated attacker capabilities ("craft burnchain stacking ops from their own Bitcoin inputs, and order their own transactions"): the attacker needs to control two Bitcoin UTXOs to fund a 2-output `PreStx` transaction and a follow-up spending transaction — no privileged role, no victim cooperation, no dependence on prepare-phase/membership state. Attacker cost is limited to Bitcoin transaction fees. This is fully repeatable against any Stacks address with a nonzero balance.

### Recommendation
Require that the follow-up op's authorizing signature (i.e., the key that signs the input spending vout=1) cryptographically match the address encoded in `PreStxOp.output` (vout=0), or eliminate the two-step Bitcoin-op indirection in favor of requiring the `sender`/`stacker` identity to be proven by an actual Stacks-transaction signature (as pox-4/pox-5's Clarity `stack-stx`/`delegate-stx` entry points already do for the non-burnchain-op path). At minimum, add a `PreStxOp::check()` that validates `output` was actually derived from a key controlled by whoever spends vout=1, or remove/disable the legacy burnchain-op-based stacking/transfer/delegate path for any pox version still reachable in this codebase (pox-4/pox-5), since it structurally lacks sender authentication.

### Proof of Concept
Rust integration test (extends the existing pattern in `stacks-node/src/tests/neon_integrations.rs:2126-2161` which already demonstrates constructing `PreStxOp`s manually):
1. Fund two BTC UTXOs controlled by the attacker.
2. Submit `PreStxOp{output: victim_addr}` via `btc_regtest_controller.submit_manual` with vout=0 = victim's legacy BTC address, vout=1 = attacker's own address.
3. Confirm block; assert `BurnchainDB`/`pre_stx_op_map` contains `PreStxOp{output: victim_addr}` — assert equality `pre_stx.output == victim_addr` even though victim never signed anything (mirrors assertion pattern in `stackslib/src/burnchains/tests/db.rs:511-515`).
4. Submit a `TransferStxOp` Bitcoin transaction whose input spends vout=1 of the `PreStxOp` tx, signed only by the attacker's key, with `recipient = attacker_addr`, `transfered_ustx = victim_balance`.
5. Confirm block; assert `get_balance(victim_addr) == victim_balance - transfered_ustx` and `get_balance(attacker_addr) == old_balance + transfered_ustx`, proving STX moved from the victim without any signature from the victim's private key.
6. Assert that at no point in `stackslib/src/chainstate/burn/operations/transfer_stx.rs` or `stackslib/src/chainstate/burn/db/processing.rs` is a signature check performed binding `victim_addr` to the transaction that spent vout=1.

        if self.transfered_ustx == 0 {
