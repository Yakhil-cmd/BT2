This confirms the exact root cause: `Handler#stacks` (used by `PushHandler`, `CheckSuiteHandler`, etc.) correctly scopes to stacks belonging to `Repository.from_github_repo_name(repository_name)` derived from the verified payload's `repository.full_name`. ### Title
`StatusHandler#process` mutates arbitrary `Commit` rows across all repositories based solely on `sha`, ignoring the verified `repository`/organization scope - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that the webhook came from a GitHub App/organization configured with a matching `webhook_secret` for `repository_owner`; it does not bind the signature to the specific `sha` inside the payload. `StatusHandler#process` then runs `Commit.where(sha: params.sha)` with no scoping to the repository or stack that the signature actually authorized, unlike every other handler (`PushHandler`, `CheckSuiteHandler`) which use the shared `Handler#stacks` helper scoped via `Repository.from_github_repo_name(repository_name)`.

### Finding Description
The equality the pipeline implicitly relies on is: `verify_webhook_signature(signature, raw_post) == true` implies `authorized to mutate Commit records belonging to payload.repository.full_name`. In reality, verification only proves `repository_owner (org login) matches Shipit.github(organization:).webhook_secret` — it says nothing about which specific commit/stack rows may be touched.

Path: `WebhooksController#create` parses `params` and dispatches to `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` after `verify_signature` passes [4](#0-3) . `StatusHandler#process` then does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query has no `WHERE` clause tying it to `payload['repository']['full_name']`, `stack_id`, or any org boundary — it matches every `Commit` row in the database sharing that `sha` string, regardless of which `Repository`/`Stack`/organization it belongs to. Compare to `PushHandler`/`CheckSuiteHandler`, which correctly call the private `stacks` helper: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [2](#0-1)  before touching any records — `StatusHandler` is the outlier that skips this scoping entirely.

Because git commit SHAs are content-addressed, an attacker who owns/controls a repository (fork or otherwise) under an organization already configured in Shipit can reconstruct a commit object byte-for-bit identical to a victim's commit (same tree, parents, author/committer identities and timestamps, message) to obtain the exact same SHA1 in their own repo, then use GitHub's Status API on their own repository/sha. GitHub will sign and deliver this webhook using the webhook secret configured for that organization/app — the same secret regardless of which specific repo under the org triggered it. `verify_signature` therefore passes (`repository_owner` matches a valid, configured org), yet `StatusHandler` writes a `Status`/commit-state mutation onto the **victim's** `Commit` row (potentially in a different `Stack`), because the lookup is keyed purely on `sha`, not on the repository that was actually verified.

### Impact Explanation
This is a payload for one repository mutating another repository's/stack's `Commit` state — explicitly listed as a Critical impact category (payload for one repo mutating another's stack/commit/task/team). A forged/replayed status can flip a victim commit's CI status to `success`, which (per `Commit#add_status`) can trigger `stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`, and — if the victim stack has `continuous_deployment: true` — enqueue an actual `ContinuousDeliveryJob`/deploy, as demonstrated by the existing test `"updating state to success triggers new deploy when stack has continuous deployment"` in `test/models/commits_test.rb`. This is repeatable against any `sha` string the attacker can reconstruct or otherwise learn (commit SHAs are public on GitHub commit pages), against arbitrary stacks in the same Shipit instance, and the blast radius spans all repositories/orgs configured under Shipit that don't have SHA collisions ruled out.

### Likelihood Explanation
Preconditions: the attacker needs push/webhook-trigger capability on some repository whose owning organization login is already configured in Shipit (`Shipit.github(organization: repository_owner)` must resolve without raising `GithubOrganizationUnknown`) — this is a low bar for orgs that host many repos/teams, since any member with a personal fork or a repo under that org qualifies. The attacker does not need the `webhook_secret` itself; GitHub computes and sends it. Reconstructing an identical SHA1 by copying the exact commit object (available via `git cat-file`/API for any public commit) is a standard, previously demonstrated technique and requires no cryptographic break. This makes the attack feasible and repeatable without any privileged Shipit role, session, or secret.

### Recommendation
Scope `StatusHandler#process` the same way as every other handler: resolve the repository/stack via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (i.e., reuse `Handler#stacks`) and constrain the `Commit` lookup to `stacks.flat_map(&:commits)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest (`ActionDispatch::IntegrationTest` or `ActionController::TestCase` as used in `test/controllers/webhooks_controller_test.rb`):

1. Set up two stacks/repositories: `attacker_stack` (`repository.owner.login == 'shopify'`, e.g. `shopify/attacker-repo`) and `victim_stack` (`shopify/victim-repo`), both under the same configured org so `Shipit.github(organization: 'shopify')` resolves.
2. Create `victim_commit = victim_stack.commits.create!(sha: 'deadbeef...', ...)`.
3. Build a status payload with `repository.full_name = 'shopify/attacker-repo'` (the attacker's own, legitimately verifiable repo) but `sha = victim_commit.sha` (copied from the victim).
4. Compute a correctly signed `X-Hub-Signature` using the real configured `webhook_secret` for `'shopify'` (as the test environment does via `Shipit.github(organization: 'shopify').webhook_secret`, matching how `GithubHook`/`verify_webhook_signature` is stubbed/exercised in `test/controllers/webhooks_controller_test.rb`).
5. POST to `/webhooks` with `X-Github-Event: status` and the signed body.
6. Assert: `assert_response :ok` (signature verified — LHS of the binding holds for `repository_owner == 'shopify'`), AND `assert_difference('victim_commit.statuses.count', 1) { post ... }` — proving the "attacker's own repo, verified" signature was treated as authorization to mutate the **victim's** `Commit` row, which is the equality violation (`verified for attacker-repo` ≠ `authorized to mutate victim-repo's Commit`).
