## Finding [1](#0-0) 

### Title
API-client stack-scope bypass in `Api::CCMenuController#stack` — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` can only see the stack it is bound to, by resolving stacks through the `stacks` helper before looking one up by param. `Api::CCMenuController` overrides the `stack` lookup and resolves it directly against the *entire* `Stack` table, skipping the scoping check entirely.

### Finding Description
`Api::BaseController` defines the authorization-scoping logic that every API controller is supposed to rely on: [2](#0-1) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

`current_api_client.stack_id?` is true when the `ApiClient` record is bound to a single `Stack` (`belongs_to :stack, optional: true` in [3](#0-2) ). When bound, `stacks` is restricted to that one stack, so `stack.from_param!` will raise `RecordNotFound` if the caller supplies a different `stack_id`. This scoping is exercised and relied upon elsewhere, e.g. in `Api::StacksControllerTest`: "an api client scoped to a stack will only see that one stack" [4](#0-3) .

`Api::CCMenuController`, however, defines its own `stack` method that bypasses `stacks` and queries `Stack` unscoped: [5](#0-4) 

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
```

`require_permission :read, :stack` only checks that the client's `permissions` list contains `read:stack` (`ApiClient#check_permissions!`, [6](#0-5) ); it never checks *which* stack the client is allowed to read. That job is delegated entirely to the `stacks`/`stack` scoping helper — which `CCMenuController` does not use.

The binding that should hold is:
`stack a token authorises == stack it touches`

For every other API controller (`Api::StacksController`, `Api::DeploysController`, etc.) this holds because they call the inherited, scoped `stack`/`stacks` methods. In `CCMenuController` it is broken: `stack a token authorises` (the single stack referenced by `current_api_client.stack_id`) is decoupled from `stack it touches` (any stack in the database, selected purely by attacker-supplied `params[:stack_id]`).

### Impact Explanation
An attacker holding any valid `ApiClient` token that has `read:stack` permission — even one deliberately scoped to a single, low-sensitivity stack — can query `GET /api/:stack_id/cctray.xml?token=...` for an arbitrary `stack_id` belonging to any other, unrelated repository/environment and receive that stack's build/deploy state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, `activity`), as rendered by `CCMenuController#show` ( [7](#0-6) ). This is an escalation from a narrowly-scoped, unprivileged API credential to unauthenticated (with respect to that stack) read of arbitrary stack state, matching the "High" impact category of "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` authentication token with `read:stack` permission — the same low bar as any legitimate integration (e.g. a CI status widget). No repository write access, GitHub credentials, or session is needed; only the `stack_id` of the target stack, which is a predictable, guessable path segment (`owner/repo/environment`), is required. This makes the bypass trivially exploitable by any party who has obtained a scoped read-only token, regardless of the stack it was meant to be restricted to.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it via the inherited `stacks` scope) so that stack-scoped `ApiClient` tokens cannot resolve stacks outside their bound `stack_id`:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create (or obtain) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to stack A (`shipit_stacks(:shipit)` in fixtures, analogous to `here_come_the_walrus` in `test/controllers/api/stacks_controller_test.rb`).
2. Using that client's `authentication_token` (or `token` query param), request:
   `GET /api/<stack_B_owner>/<stack_B_repo>/<stack_B_env>/cctray.xml?token=<clientA_token>`
   where stack B is a different stack not owned/authorized by the client.
3. Observe `Api::CCMenuController#stack` resolves stack B via `Stack.from_param!` (unscoped), and `#show` renders stack B's build status — despite the client only being authorized (`stack_id`) for stack A. Compare against `Api::StacksController#index`/`#show`, which correctly returns only the scoped stack for the same client, per the existing test `test/controllers/api/stacks_controller_test.rb:217-223`.
