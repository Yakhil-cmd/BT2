### Title
Missing cosigner-membership check on local "sign" requests allows any paired device to trigger unauthorized multisig signing prompts - ([File: wallet.js])

### Summary
When a peer device sends a `"sign"` request for an address that is *local* to the receiving wallet (`ifLocal` branch in `handleMessageFromHub`), the code that should verify the requesting device is actually a listed cosigner of that address is commented out. The equivalent check *does* exist in the `ifRemote` branch a few lines below, showing the check was deliberately implemented for one code path but never enforced for the other — the exact "restricted in one path, bypassable through another" pattern described in the reference advisory (an authorization check enforced by the UI/one path but skippable via a direct message/API call).

### Finding Description
In `handleMessageFromHub`, the `"sign"` message handler calls `findAddress(body.address, body.signing_path, {...})`: [1](#0-0) 

```

    ifError: callbacks.ifError,
    ifLocal: function(objAddress){
        // the commented check would make multilateral signing impossible
        //db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
        //    if (sender_rows.length !== 1)
        //        return callbacks.ifError("sender is not cosigner of this address");
            callbacks.ifOk();
```

For the `ifRemote` branch (forwarding a signing request to another device that actually holds the key), the analogous authorization check is present and enforced: [2](#0-1) 

```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
```

So any correspondent device that is paired with the victim's wallet (not necessarily a legitimate cosigner of `body.address`) can send a `"sign"` message referencing an arbitrary local `address`/`signing_path` pair and an attacker-crafted `unsigned_unit`, and the wallet will accept it, hash it, validate it, and emit the `"signing_request"` event that drives the GUI's confirmation dialog — all without ever checking that the sender is one of the actual cosigners recorded for that shared address in `shared_address_signing_paths` / `extended_pubkeys`. The comment explicitly acknowledges the check was intentionally left disabled ("the commented check would make multilateral signing impossible"), but doing so removes any authorization boundary on who may originate a signing request for a device's own address.

### Impact Explanation
This breaks the authorization boundary between "who may legitimately request my device to co-sign a transaction for a shared/multisig address" and "any paired device I've ever exchanged pairing info with." An attacker who is merely a paired correspondent (e.g., a bot/service the user paired with, or any device that previously exchanged a pairing code) can:
- Spoof signing requests for shared addresses they are not a cosigner of, causing the victim's wallet to display a spending confirmation dialog for an attacker-controlled transaction, increasing the chance of social-engineering the victim into approving an unauthorized spend from a multisig address.
- In any headless/automated cosigning setup (services that auto-approve signing requests from known correspondent devices without re-verifying cosigner membership against the address definition) this becomes a fully unattended authorization bypass, letting the attacker obtain valid signatures over transactions the requester was never authorized to request, potentially leading to unauthorized spending from the shared address.

This maps to concrete "unauthorized spending" / node disagreement scope allowed by the rules, reachable purely by a paired device sending a device message — no privileged keys are required.

### Likelihood Explanation
Reachability is straightforward: pairing with a wallet is a normal, low-privilege interaction, and the `"sign"` message handler is reachable by any correspondent device via `handleMessageFromHub`. The missing check is unconditional (not gated behind a feature flag), and the asymmetry between the `ifLocal` and `ifRemote` branches confirms the check is a known, intentional design gap rather than a hardening feature that's simply redundant. The remaining barrier to full exploitation is that, for GUI wallets, a human still must click "approve" on the confirmation dialog; the severity is highest in automated/headless multisig setups or where the dialog does not clearly show which device/cosigner actually requested the signature.

### Recommendation
Restore (in a form compatible with legitimate multilateral signing) the membership check for the `ifLocal` path: before emitting `"signing_request"`, verify that `from_address` is present in the set of device addresses associated with `body.address`'s definition (e.g., via `shared_address_signing_paths` or the equivalent structure used for `other_device_addresses` in the `ifRemote` branch) for the given `signing_path`. Additionally, surface the requesting device's identity/cosigner-status prominently in the confirmation dialog so that even in the interactive path, users are not tricked into approving requests from non-cosigners.

### Proof of Concept
1. Attacker pairs their device with the victim's wallet (a normal, unprivileged pairing operation).
2. Victim wallet has address `A` defined as a shared/multisig address with cosigners `{X, Y}`; attacker's device is neither `X` nor `Y`.
3. Attacker sends a `"sign"` device message to the victim: `{address: A, signing_path: "r.0", unsigned_unit: <attacker-crafted unit spending from A>}`.
4. `findAddress` resolves `A` as local (the victim's device holds a signing key for it) and enters the `ifLocal` branch; because the cosigner-membership check is commented out, `callbacks.ifOk()` fires immediately and the crafted unit is hashed/validated and a `"signing_request"` event is emitted, presenting the victim a confirmation dialog for a transaction requested by a device that is not actually one of `A`'s legitimate cosigners — something the code was clearly designed to prevent (as shown by the equivalent, enforced check in the `ifRemote` branch).

*Note:* I could not fully verify whether any GUI-layer code (outside `ocore`) additionally re-validates cosigner membership before rendering the confirmation dialog, since that logic likely lives in a separate wallet-GUI repository not indexed here. If such a check exists downstream, it does not change the fact that `ocore` itself dropped this authorization check for the `ifLocal` path while enforcing it for `ifRemote`.
