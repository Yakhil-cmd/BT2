### Title
Attestor list updates for `spender_attested` assets can permanently freeze existing holders' funds - (File: validation.js)

### Summary
Assets with `spender_attested: true` restrict who may hold/spend the asset to addresses on a dynamically updatable "attestor" whitelist. The attestor list can be changed at any time after the asset is defined via an `asset_attestors` message [1](#0-0) . Unlike KyberSwap's `Pool.tweakPosZeroLiq`, which forgot to exempt an existing-position-closing/withdrawal path from a newly-enabled whitelist, ocore's payment-spend validation checks the *current* attestor list against the *sender* (owner) address for every transfer, with no fallback path allowing removed/never-attested holders to withdraw or exit their existing balance.

### Finding Description
When an asset is defined with `spender_attested: true`, the definer publishes an initial attestor list and can subsequently update it via an `asset_attestors` message, validated by `validateAttestorListUpdate` and limited to once per asset per unit [1](#0-0) .

The list of "attested" addresses is derived dynamically at validation time — not fixed at issuance — via `storage.loadAssetWithListOfAttestedAuthors`, which is called for every payment validation, both for the payment authors and again for the destination outputs [2](#0-1) .

For every transfer input, the code checks whether the current owner (sender) address is on the current attestor list, not whether it was attested at the time the coins were received:
```
if (objAsset && objAsset.spender_attested && objAsset.arrAttestedAddresses.indexOf(owner_address) === -1)
    return cb("owner address is not attested");
``` [3](#0-2) 

The same real-time check is applied for private, fixed-denomination assets' cached `src_coin.src_output.address` [4](#0-3) .

Finally, in `validatePaymentInputsAndOutputs`, before a payment (including a payment of an already-defined, already-held asset) is accepted, all sender/output addresses must currently be attested:
```
if (!objAsset.spender_attested)
    return cb();
storage.filterAttestedAddresses(
    conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses,
    function(arrAttestedOutputAddresses){
        if (arrAttestedOutputAddresses.length !== arrOutputAddresses.length)
            return cb("some output addresses are not attested");
        cb();
    }
);
``` [5](#0-4) 

There is no exception or "unwind"/"withdraw-only" bypass for addresses that legitimately received the asset while attested but were later dropped from (or never re-added to) the attestor list. Because there is no separate withdraw path (analogous to `tweakPosZeroLiq`) that skips the attestation gate, a holder whose attestation is revoked can neither transfer the asset onward, nor send it back to the definer/anyone else, since every recipient in the payment message must also currently be attested (unless sending back the entire holding is otherwise structured to hit the definer/self exceptions in the transferability check, which spender_attested doesn't relax).

### Impact Explanation
Any asset issuer using `spender_attested` (e.g., a KYC-gated stablecoin or security token on ocore) can, intentionally or by an operational mistake, remove or fail to renew an address from the attestor list after that address has already received/holds asset units. From that point, the held units become permanently unspendable/frozen by protocol-level validation rules — the holder cannot transfer, sell, or withdraw the asset back to the issuer at all, since output addresses (including the issuer/definer) require attestation too and there is no bypass. This is a direct "AA/asset fund freezing" condition: legitimately-owned coins become permanently stuck in the ledger with no path to recovery through normal payment messages.

### Likelihood Explanation
This requires an asset with `spender_attested: true` (opt-in feature, not default) and an attestor-list change event that removes a currently-holding address, or simply lets its attestation lapse without renewal. This is a normal, expected, single-message operation (`asset_attestors`) that any asset definer can execute, and is documented/tested functionality of the codebase, making it a realistic mid-life-cycle scenario for such assets, analogous to KyberSwap's whitelist being turned on after existing positions were created.

### Recommendation
Provide an explicit "exit" mechanism for `spender_attested` assets that allows a holder to unwind/return their balance to the definer (or receive change) even when their address is not currently attested — for example, exempt destination-address attestation checks for outputs directed solely to `objAsset.definer_address`, mirroring how the code already exempts the definer address from the `is_transferrable` check [6](#0-5) . Alternatively, snapshot/permanently record attestation status at the time coins are received so that subsequent attestor-list changes cannot retroactively freeze already-held balances.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and attestor list `[X]`.
2. Address `H` is attested (on list `[X]`, `H` is attested through some proof) and receives units of asset `A` through a normal transfer — this succeeds because at validation time `H` is attested and appears in `arrAttestedAddresses`.
3. Definer later sends an `asset_attestors` update message removing `H`'s attestation (or simply lets the underlying attestation expire/ get superseded), changing the list so `H` no longer resolves as attested via `storage.loadAssetWithListOfAttestedAuthors`.
4. `H` now attempts to send any payment of asset `A` (to any address, including the definer) via `divisible_asset.js`/`indivisible_asset.js` composer; the outgoing unit is submitted to the network.
5. During validation, `validatePaymentInputsAndOutputs` checks `owner_address` (=`H`) against the current `arrAttestedAddresses` at line 2506-2507 and rejects the transfer with "owner address is not attested", and even if that check were bypassed, the output-address check at lines 2630-2641 requires the recipient also be currently attested.
6. `H`'s asset balance is permanently stuck — no valid payment message can move it, freezing the holder's funds with no available network path to recover them.
