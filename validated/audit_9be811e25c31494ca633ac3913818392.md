## Title
`StatusHandler#process` writes GitHub status webhooks to *any* stack sharing a commit SHA, unscoped from the verified repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

## Summary
`StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` instead of scoping through the `Handler#stacks` helper that every other webhook handler uses to bind the effect to the repository whose signature was verified. Any commit sharing that SHA across unrelated stacks (a routine situation whenever a repo is tracked by more than one Shipit `Stack`, e.g. staging/production, or forks sharing history) receives a `Status` row via `Shipit::Status.replicate_from_github!` with that stack's `stack_id`, even though the webhook's signature was only proven valid for one specific repository/org.

## Finding Description
The binding that should hold is: `stack_id used in replicate_from_github!` == `stack_id of the stack whose repository produced/authenticated this webhook`. Tracing the code shows this binding is **not** enforced.

- `WebhooksController#verify_signature` only proves the payload was signed for `repository_owner = params.dig('repository','owner','login')` [1](#0-0)  - it authenticates the *payload*, not the query used afterward.
- `Shipit::Webhooks::Handlers::Handler` exposes a `stacks` helper explicitly meant to scope any handler's effects to `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) .
- `StatusHandler#process` ignores that helper entirely and instead does a bare, cross-tenant lookup:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
- `Commit#create_status_from_github!` then writes using the resolved commit's own `stack_id` (correct *per commit*, but the commit itself was selected without any repository check):
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [4](#0-3) 
- `Status.replicate_from_github!` performs an unconditioned `find_or_create_by!` insert scoped to whatever `stack_id` it's handed: [5](#0-4) .

**Root cause**: `Commit.sha` is not unique per stack — Shipit routinely tracks the same repository under multiple `Stack` records (e.g. one per environment), and forks/rebases can also duplicate commit SHAs across independently-owned repositories that were once related. `StatusHandler` never verifies `commit.stack.repository_id` (or `commit.stack_id`) against the repository that produced the authenticated payload, unlike the pattern `stacks` was built for. Any GitHub webhook `status` event for a SHA that exists in more than one stack row causes a write into all of them, regardless of which one's repository actually emitted the event.

**Attacker request**: An attacker who can push/label/emit a `status` webhook on a repository they control (or any repo whose commits' SHAs are shared with a victim stack — e.g., two Shipit stacks pointing at the same upstream repo, or a fork carrying pre-fork history) sends a `status` event with `sha` equal to a SHA that also exists in the victim's stack. `verify_signature` succeeds because it only checks the attacker's own repository's signature; `StatusHandler#process` then locates and mutates the victim's `Commit`/`Status` rows regardless.

**Why guards fail**: `verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema (`sha`, `state`, etc.) all validate the *shape and authenticity* of the request for the attacker's own repository — none of them constrain which `Commit`/`Stack` rows `StatusHandler#process` is allowed to touch.

## Impact Explanation
A forged/foreign-repository status can flip a victim commit's aggregate CI state to `success` for a stack the attacker never authenticated for. Because `Commit#deployable?` depends on `success? && !blocked?` [6](#0-5) , this can make an unvetted commit appear deployable in the victim's stack, and it also triggers `ProcessMergeRequestsJob` scheduling via `add_status`/`schedule_continuous_delivery`, potentially advancing merge-queue/deploy automation on a repository the attacker never authenticated against. This is a cross-tenant write ("payload for one repository mutating another's stack/commit") and matches the Critical category (unauthorized deploy/merge facilitation via forged data written into a foreign stack).

## Likelihood Explanation
Requires: (1) at least one `Stack` sharing a commit SHA with a stack the attacker controls (common — multi-environment stacks on the same repo, or forks with shared history), and (2) the attacker's own repository having a validly configured GitHub App/webhook secret with Shipit (any repo under an org already onboarded to Shipit). No Shipit session, API token, or GitHub secret is needed beyond what the attacker's own repo naturally has. This is fully repeatable per SHA/stack pair.

## Recommendation
In `StatusHandler#process`, scope the commit lookup through the repository that authenticated the webhook, mirroring the `stacks` helper pattern used elsewhere, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This binds `commit.stack_id` to only the stacks belonging to `Repository.from_github_repo_name(repository_name)`, restoring the equality between the verified repository and the mutated stack.

## Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (or `test/models/webhooks/status_handler_test.rb`):
```ruby
test "status webhook does not create a Status on an unrelated stack sharing the same sha" do
  attacker_stack = shipit_stacks(:shipit)              # repo the webhook is signed for
  victim_stack   = shipit_stacks(:cyclimse)            # unrelated stack, different repository
  shared_sha     = "6d9278037b872fd9a6690523e411ecb3aa181355"

  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, ...)

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'
  body = { 'sha' => shared_sha, 'state' => 'success',
           'repository' => { 'full_name' => attacker_stack.repository.full_name,
                              'owner' => { 'login' => attacker_stack.repository.owner } } }.to_json

  assert_no_difference -> { Status.where(stack_id: victim_stack.id).count } do
    post :create, body:, as: :json
  end
end
```
Before the fix, `Status.where(stack_id: victim_stack.id).count` increments even though the webhook was only signed/verified for `attacker_stack`'s repository, demonstrating the cross-tenant write.
