### Title
Session Fixation in GitHub OAuth Callback Leads to Account Takeover - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` binds a newly authenticated GitHub identity to the *existing* Rack session without first rotating/resetting that session. `reset_session` is only ever called from `logout` and from `force_github_authentication` (when the session is already deemed authenticated but stale). Because the session ID is never regenerated at the moment a user's identity is established, an attacker who can plant a known session ID into a victim's browser before the victim completes the OAuth dance ends up sharing (and thus controlling) the victim's authenticated session afterwards.

### Finding Description
This maps to the report's core bug class: a state/identity binding (`from` account vs `to` account share state in the SuperVault report) is copied/attached without verifying that the receiving container legitimately "belongs" to the same principal. Here the equivalent binding is:

`session_id (pre-auth, attacker-influenced)` == `session_id (post-auth, now bound to victim's `User`)`

Before-state: attacker requests the app once, is issued a session cookie/ID by the framework (unauthenticated, `session[:user_id]` unset). Attacker forces this same session ID into the victim's browser (classic fixation vector: subdomain cookie injection, cookie-setting via a related origin, or any cookie-tossing primitive available to an unprivileged network/web attacker — no Shipit session, API token, or GitHub credentials required).

Victim visits the app with the attacker-fixed session, is redirected to GitHub OAuth, authenticates, and GitHub redirects back to: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

`sign_in_github` resolves/creates the `User` record from the verified OmniAuth payload and stores its ID in `session[:user_id]`: [2](#0-1) 

Critically, the session itself (the container) is never rotated (`reset_session` is not called here), only its *contents* are overwritten — mirroring the report's "entire state copied onto an existing account" pattern, except the fixed asset is the session rather than a vault balance. After-state: the attacker's original session ID (still known/controlled by the attacker, e.g. still valid in their own browser tab) now has `session[:user_id]` == victim's ID and `session[:authenticated] = true`. `current_user` is derived purely from this session value: [3](#0-2) 

The attacker can now use that same session ID to act as the victim across the whole engine (deploys, merges, rollbacks, etc. gated only by `current_user.authorized?`).

Compare with `logout`, which does properly discard the session: [4](#0-3) 

### Impact Explanation
This crosses the explicitly accepted High-impact category ("session fixation / forced OAuth completion"). A successful attack yields full account takeover of any victim who authenticates while using a fixed session — including privileged users belonging to `Shipit.github_teams` — enabling unauthorized deploys, rollbacks, and merges under the victim's identity without ever needing the victim's GitHub credentials, a Shipit session, or an API token.

### Likelihood Explanation
Session fixation via missing `reset_session` on login is a well-known, easily reproducible class of bug in Rails/OmniAuth applications. It requires only the ability to get a session cookie accepted by the victim's browser prior to authentication (a standard, credential-less attacker capability against session-cookie-based apps, e.g. via a sibling subdomain, XSS on a lower-trust path, or any cookie-setting primitive) — no privileged access, no GitHub App keys, and no pre-existing Shipit session are needed on the attacker's part.

### Recommendation
Call `reset_session` (or at minimum regenerate the session ID) at the start of `callback`, immediately before assigning `session[:user_id]`/`session[:authenticated]`, so a fresh session is always issued upon establishing a new identity — analogous to separating "shared state" (the session store) from "identity-specific state" (the authenticated user id) in the original report's recommendation.

### Proof of Concept
1. Attacker visits the Shipit host unauthenticated and notes/sets a known session cookie value `S` (e.g. via a fixation primitive that lets them plant a cookie in the victim's browser for the app's domain).
2. Attacker lures the victim into browsing the app with cookie `S` still attached (unauthenticated at this point, `session[:user_id]` unset for `S`).
3. Victim clicks "Sign in with GitHub," completes OAuth; `GithubAuthenticationController#callback` runs with session `S` and sets `session[:user_id] = victim.id`, `session[:authenticated] = true` — without rotating the session ID.
4. Attacker, still holding cookie `S`, now has `current_user` resolve to the victim via `find_current_user` and can perform any action the victim is authorized for. [5](#0-4) [6](#0-5)

# frozen_string_literal: true

module Shipit
  class GithubAuthenticationController < ActionController::Base
    include Shipit::Engine.routes.url_helpers

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end

    def logout
      reset_session
      redirect_to(root_path)
    end

    private

    def sign_in_github(auth)
      user = User.find_or_create_from_github(auth.extra.raw_info)
      user.update(github_access_token: auth.credentials.token)
      user.id
    end
  end
end

# frozen_string_literal: true

module Shipit
  module Authentication
    extend ActiveSupport::Concern

    included do
      before_action :force_github_authentication
      helper_method :current_user
    end

    module ClassMethods
      def skip_authentication(*args)
        skip_before_action(:force_github_authentication, *args)
      end
    end

    private

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end

    def current_user
      @current_user ||= find_current_user || AnonymousUser.new
    end

    def find_current_user
      session[:user_id].present? && User.find_by(id: session[:user_id])
    end
  end
end
