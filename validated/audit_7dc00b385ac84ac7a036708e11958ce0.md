### Title
Webhook signature verified against the wrong organization's secret, allowing cross-organization write via `repository.full_name` mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the HMAC signature against based on `repository.owner.login` (or `organization.login`), but the event handlers dispatched afterward act on `repository.full_name` — a separate field in the same payload that is never cross-checked against the field used for authentication.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to pick the `GitHubApp` instance whose secret verifies the request signature: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus distinct `webhook_secret`) per organization, as documented for multi-tenant setups: [3](#0-2) [4](#0-3) 

Once the signature check passes, `WebhooksController#create` dispatches the raw parsed JSON body to handlers: [5](#0-4) 

Every handler determines which `Repository`/`Stack` to act on using `repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely different field from the one used for signature verification: [6](#0-5) 

Nothing in the request pipeline asserts that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login`. This breaks the equality that should hold: **organization authenticated (`repository_owner` used to pick the verifying secret) == repository written (`repository.full_name` used by the handler to select the target `Stack`)**.

Consequently, in a deployment hosting multiple organizations (each with its own configured `webhook_secret`, per `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml`), an actor who legitimately controls one onboarded, low-trust organization's webhook secret can sign a payload where `repository.owner.login` is set to their own organization (so verification succeeds against their own secret) while `repository.full_name` is set to `victim-org/victim-repo`. The signature check passes, and the handler then locates and mutates state for the victim's repository/stack.

Concretely for the `push` event, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the target branch of the resolved (spoofed) repository: [7](#0-6) 

For the `status` event, `StatusHandler#process` writes a fabricated CI status onto any existing commit matching the attacker-supplied `sha`, unscoped by organization/owner at all: [8](#0-7) 

Since Shipit deploy safety gates (e.g. "ignore_ci"/CI status checks before a deploy) rely on `Status` records created from these webhooks, an attacker able to forge a `status` event with `state: "success"` against a victim commit sha can flip the perceived CI outcome for that commit and unlock deploys that should have been blocked.

### Impact Explanation
This crosses a genuine authentication/authorization boundary between the organization whose secret is used to authenticate the HTTP request and the repository whose data is mutated as a result — matching the "organization authenticated versus repository written" binding called out in scope. Concrete consequences:
- Forging `push` events for a victim repository can trigger unscheduled `sync_github` calls (`GithubSyncJob`), potentially syncing to attacker-influenced refs/SHAs.
- Forging `status` events can plant a fake "success" `Status` for an arbitrary victim commit `sha`, subverting CI gating for that stack's deploys — this is a High-severity escalation, effectively an authorization bypass of the mechanism used to gate an unauthorized deploy.

### Likelihood Explanation
Exploitability requires the target Shipit instance to be configured for multiple GitHub organizations (the "Using Multiple Github Applications" configuration documented in `docs/setup.md`), and the attacker to control one of the onboarded organizations (a realistic scenario for shared/internal PaaS-style Shipit deployments serving several teams/orgs, none of which are meant to trust each other). No compromise of the victim organization's secret, no Shipit session, and no `ApiClient` token are required — only a legitimate but low-privilege organization already configured on the same Shipit instance.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the `GitHubApp` for `repository_owner`, additionally validate that `params.dig('repository', 'full_name')&.split('/')&.first` (case-insensitively) equals `repository_owner` before accepting the webhook, rejecting the request with `422` otherwise. Alternatively, derive the verifying `GitHubApp` and the repository-resolution key from the same single field to eliminate the possibility of divergence.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `attacker-org` (webhook secret known/controlled by the attacker, e.g. because the attacker administers that org's GitHub App) and `victim-org` (hosting a real stack, e.g. `victim-org/victim-repo`).
2. Craft a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Sign the raw body with `attacker-org`'s webhook secret and send it as `X-Hub-Signature`, `X-Github-Event: push`, to `POST /webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature against the attacker's own secret.
5. `Handler#repository_name` resolves `victim-org/victim-repo`, and `PushHandler#process` invokes `sync_github` on the victim's stack, even though the request was never signed by `victim-org`'s GitHub App/secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
