### Title
`status` webhook writes `Commit#statuses` by bare SHA with no repository scoping, letting a `success` status on a shared SHA flip `blocked?`/`deployable?` for an unrelated stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha).each`, which is a global, table-wide lookup that does not filter by repository, organization, or stack. Any GitHub `status` event that passes the per-organization webhook-signature check (`Shipit::WebhooksController#verify_signature`) can therefore write a `Status` record onto every `Commit` row across every stack that happens to share that SHA, and `Commit#blocked?`/`Commit#deployable?` will react to that forced status.

### Finding Description
The broken binding the code implicitly assumes but does not enforce is:
`Commit#stack.github_repo_name == params.dig('repository', 'full_name')` for every commit touched by `StatusHandler#process`.

Tracing the path:
- `Shipit::WebhooksController#create` parses the raw payload and dispatches to handlers for the event type, with no per-repository filtering beyond signature verification: [1](#0-0) 
- `verify_signature` only checks that the payload was signed for the *organization* (`Shipit.github(organization: repository_owner)`), not that the SHA/commit inside the payload belongs to the specific repository that owns the signature: [2](#0-1) 
- `StatusHandler#process` then resolves the target commit(s) purely by SHA, with no join/filter on repository, stack, or `github_repo_name`: [3](#0-2) 
- `Commit#create_status_from_github!` persists the forced status and recomputes `status`/`blocked?`/`deployable?` for that commit and cascades to `stack.schedule_merges`: [4](#0-3) [5](#0-4) 
- `Commit#blocked?` and `#deployable?` are exactly the "blocking_statuses configured" gates referenced in the question: they scan `stack.commits...any?(&:blocking?)` and combine with `success?`: [6](#0-5) 

Because `Commit` rows are keyed by `sha` (a git object hash) plus `stack_id`, and git commits are content-addressed, the same SHA legitimately exists in multiple `Commit` rows when two different Shipit-tracked repositories share history (a fork of a tracked repo, a repo split/merge, or simply two Stacks tracking the same upstream repo under different branches/environments). An attacker who owns or controls a fork/repo within the same GitHub organization that Shipit's app is installed on can:
1. Push/create a commit whose SHA is already present in the victim stack's `commits` table (e.g., a shared ancestor commit from before the fork point, which is virtually guaranteed for any fork).
2. Trigger (or directly POST, since this is an unauthenticated GitHub webhook endpoint that only checks org-level HMAC) a `status` event with `context: ci/build`, `state: success`, `sha: <shared sha>` for their own repository - a real, validly signed webhook for their own repo satisfies `verify_signature`.
3. `StatusHandler#process` finds and updates every `Commit` row matching that SHA across all stacks, including the victim's, regardless of which repository the payload was signed for.
4. If the victim's stack has `blocking_statuses` configured requiring `ci/build`, this write can flip `blocking?`/`success?` for that historical commit, changing `blocked?` (and thus `deployable?`) for downstream commits in the victim's stack, gating or ungating deploys/merges.

None of the existing guards stop this: `verify_signature` only proves organization-level authenticity of the payload, not repository-scoped authorization of what SHA-keyed record it may mutate; `ExplicitParameters` only validates payload shape (`sha`, `state`, `context` types), not ownership; there is no `require_permission!`/`stacks` scope check anywhere in the webhook path.

### Impact Explanation
A payload validly signed for repository A can mutate `Commit`/`Status` records belonging to stack(s) built from repository B, as long as A and B share a commit SHA (an extremely common condition for forks or multi-branch/multi-environment stacks on the same upstream). This directly matches the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge," since a forced `success` status can clear `blocked?` and unblock a deploy, or a forced `error`/`failure` status can set `blocked?` and block deploys, for a stack the attacker does not own or authenticate against. The blast radius extends to every stack across the Shipit installation that shares a commit SHA with the attacker-controlled repository, which for GitHub App-wide installations spans an entire GitHub organization.

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` configured (a supported, common configuration) and must share at least one commit SHA with a repository the attacker controls (trivial via forking, or via the fact that many orgs maintain multiple Shipit stacks off the same base repo). The attacker needs no Shipit credentials, no API token, and no `webhook_secret`/private key of their own choosing — a fork/repo they legitimately own inside the same installed GitHub App organization naturally produces validly-signed webhooks. Cost is a single `git push`/status POST on their own repo; the exploit is repeatable against any shared SHA and any stack sharing history.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers that resolve records by bare `sha`) to the repository that authenticated the webhook, e.g. join through `Stack` on `repo_owner`/`repo_name` derived from `params.dig('repository', 'full_name')` before selecting `Commit` rows, so only commits belonging to stacks tracking that exact repository are updated: `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repo_owner: owner, repo_name: name })`.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "StatusHandler does not update commits belonging to a different repository sharing the same SHA" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(deploy_spec: <spec with blocking_statuses ["ci/build"]>)
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")
  before_blocked = victim_commit.reload.blocked?

  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:attacker_fork), environment: "production", branch: "master")
  attacker_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/build",
    "repository" => { "full_name" => attacker_stack.repository.full_name, "owner" => { "login" => attacker_stack.repository.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).call

  after_blocked = victim_commit.reload.blocked?

  # Binding under test: victim_commit.stack.github_repo_name == payload["repository"]["full_name"]
  assert_not_equal victim_commit.stack.github_repo_name, payload["repository"]["full_name"]
  # Yet the victim's blocked?/status changed as a result of a payload authenticated for a different repo:
  assert_not_equal before_blocked, after_blocked, "victim stack state changed from a payload signed for a different repository"
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
