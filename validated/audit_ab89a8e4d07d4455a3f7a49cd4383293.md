### Title
Stale vote/stake account entries persist in `StakesCache` when an account's owner changes without its lamports going to zero - (File: `runtime/src/stakes.rs`)

### Summary
`StakesCache::check_and_store` is the single choke-point that keeps the in-memory `Stakes` cache (used for stake-weighting, leader schedule, and epoch reward distribution) synchronized with on-chain stake/vote account state. It only evicts a cached entry when the account's lamports drop to zero. If an account that is currently cached as a vote or stake account is reassigned to a different owner while it still holds lamports, the function falls through without executing either the vote-branch (`solana_vote_program::check_id`) or stake-branch (`stake_program::check_id`), so the previous entry is never removed from the cache, exactly analogous to the RabbitHole bug where `QuestFactory` kept using a stale `rabbitholeReceiptContract` reference after the "authoritative" contract had been re-pointed elsewhere.

### Finding Description
`check_and_store` decides what to do with a cache entry solely from the account's *current* owner and lamports: [1](#0-0) 
The code contains an explicit, unresolved `TODO` acknowledging the gap: [2](#0-1) 
When `account.lamports() != 0` and `owner` matches neither `solana_vote_program::check_id` nor `stake_program::check_id` (i.e., the account has been reassigned away from the vote/stake program while still funded), none of the branches execute (`check_and_store`'s `if solana_vote_program::check_id(owner) { .. } else if stake_program::check_id(owner) { .. }` at lines 118 and 143 both fail), leaving the previously-cached `VoteAccount`/`StakeAccount` entry (and any associated `StakeAccount` used in reward calculation, `stakes.vote_accounts()`, `stakes.stake_delegations_vec()`) untouched in `StakesCache`. This is the same "cached reference to an entity that can be re-pointed elsewhere without update-propagation" pattern as the RabbitHole finding, where `Quest`'s immutable `rabbitHoleReceiptContract` diverged from `QuestFactory`'s mutable `rabbitholeReceiptContract` after an admin update.

The stale cache entry then continues to flow into reward-distribution and point-calculation code paths that trust `stakes.vote_accounts()` / `stake_delegations_vec()` as ground truth, e.g. `get_cached_vote_accounts`, `calculate_reward_points_partitioned`, and `redeem_delegation_rewards`: [3](#0-2) [4](#0-3) 

### Impact Explanation
If an account can be reassigned away from the stake/vote program while retaining lamports (e.g., via a future or existing pathway that performs an owner change without first zeroing lamports), the stakes cache would keep crediting stake/vote weight to an account that is no longer a valid stake or vote account on-chain. Because `stakes.vote_accounts()`/`stake_delegations_vec()` feed directly into epoch-reward point calculation and payout, this could result in rewards being computed and paid against a phantom delegation/vote account (misattributed rewards), or in stake weight participating in consensus/leader-schedule computations using accounts-db state that has already diverged from the cache, which is a cross-node state divergence risk if not all nodes reach the fallthrough condition identically.

### Likelihood Explanation
This is gated entirely on whether any code path in the runtime (system program, stake program, or a CPI) can change an account's owner away from the stake/vote program while its lamports remain non-zero. I was not able to conclusively verify, within the available tool budget, whether such an owner-reassignment-with-nonzero-lamports path currently exists and is reachable by an unprivileged user's transaction (the system program's `Assign`/`Allocate` instructions generally only operate on system-owned accounts, and the stake/vote programs themselves do not appear to expose an "assign new owner" instruction). The `TODO` comment referencing solana-labs/solana#24200 confirms this gap has been a long-standing, acknowledged risk in the reference implementation rather than a purely theoretical one, but I could not confirm an active unprivileged trigger with certainty in this pass.

### Recommendation
In `StakesCache::check_and_store` (`runtime/src/stakes.rs`), before checking the account's *current* owner against the vote/stake program IDs, first check whether the pubkey is already present in the cache as a vote or stake account; if so, and the new owner no longer matches the expected program id (regardless of lamports), explicitly call `remove_vote_account`/`remove_stake_delegation` to evict the stale entry, closing the gap noted in the existing `TODO`.

### Proof of Concept
Conceptual trace based on the code as written:
1. Pubkey `P` is cached in `StakesCache` as a `VoteAccount` (owner = vote program).
2. A transaction changes `P`'s owner to a non-vote/non-stake program while leaving lamports > 0.
3. `check_and_store(P, account, ..)` is invoked with the updated account; `account.lamports() != 0` skips the eviction branch, and `solana_vote_program::check_id(owner)` / `stake_program::check_id(owner)` both evaluate false, so no code path removes `P` from `stakes.vote_accounts()`.
4. Subsequent calls to `get_cached_vote_accounts` / `calculate_reward_points_partitioned` continue to treat `P` as a live vote account for stake-weight and reward calculation purposes. [5](#0-4)

    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
