## Finding

### Title
Webhook signature verification authenticates the payload's `repository.owner.login`, but downstream webhook handlers act on the independent `repository.full_name` field, allowing cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController` selects which GitHub App configuration (and thus which `webhook_secret`) to verify the inbound signature against using `repository.owner.login` (or `organization.login`) from the *attacker-supplied JSON body itself*, but every webhook handler that subsequently acts on the payload resolves the target `Repository`/`Stack` using the unrelated `repository.full_name` field from that same body. Nothing binds these two fields together.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the request payload: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_signature` then does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and its own `webhook_secret`) per organization when Shipit is configured with multiple GitHub Apps, as documented under "Using Multiple Github Applications": [4](#0-3) 

Once the signature is accepted, `create` dispatches the *entire raw payload* to the registered handlers: [5](#0-4) 

Every default handler resolves the affected `Repository` from `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

`Repository.from_github_repo_name` simply splits the string on `/` and does a case-insensitive DB lookup, with no relationship enforced to the owner used for signature verification: [8](#0-7) 

Because `repository.owner.login` (used to pick the verifying `webhook_secret`) and `repository.full_name` (used to pick the acted-upon `Repository`/`Stack`) are two independent, attacker-controlled JSON fields in the same unauthenticated `POST /webhooks` body, an attacker who legitimately knows the `webhook_secret` for **any one** GitHub organization configured on the Shipit instance can forge a payload whose `owner.login` matches that known-secret organization (satisfying `verify_signature`) while `full_name` points at a completely different, unrelated organization/repository tracked by the same Shipit instance. All of `PushHandler`, `OpenedHandler`, `ClosedHandler`, `AssignedHandler`, `EditedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, and `ReopenedHandler` are reachable this way and will act on stacks/repositories belonging to the spoofed `full_name`.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written." A tenant/attacker who only controls (and knows the webhook secret for) one low-trust organization onboarded onto a shared Shipit instance can:
- Trigger `Stack#sync_github` on arbitrary other stacks/repositories (`PushHandler`), which resyncs commits and, for continuous-deployment-enabled stacks, can drive unauthorized deploys.
- Provision/unarchive/close review stacks for pull requests in repositories they don't own (`OpenedHandler`, `ReopenedHandler`, `ClosedHandler`).
- Manipulate PR labels/assignees state cached against other organizations' PRs (`LabeledHandler`, `AssignedHandler`, `EditedHandler`).

This is a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the authentication field and the acted-upon field, qualifying as an unauthorized deploy / cross-repository write.

### Likelihood Explanation
Any Shipit deployment following the documented "Using Multiple Github Applications" multi-tenant pattern (or any deployment where a `webhook_secret` is known to more than one team, e.g. shared infra teams) is exposed. The `/webhooks` endpoint itself requires no session, `ApiClient` token, or GitHub App private key — only knowledge of one configured organization's `webhook_secret`, which by design is shared with, and known to, that organization's own GitHub App administrators.

### Recommendation
Enforce that the organization used to select/verify the webhook secret matches the owner encoded in `repository.full_name` (and any other repository/org references used later by handlers) before dispatching to handlers — reject the request if they diverge.

### Proof of Concept
Assume Shipit is configured with two organizations, `OrgA` (attacker is a legitimate GitHub App installer/administrator, so knows `OrgA`'s `webhook_secret`) and `OrgB` (victim org with a tracked repository `OrgB/victim-repo`, unrelated to `OrgA`).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1 of body using OrgA's webhook_secret>
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, must exist as a commit shipit knows about or trigger resync>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```

`verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully with the attacker-known secret. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on stacks belonging to `OrgB`, entirely bypassing the fact that the request was never actually signed by `OrgB`'s GitHub App/webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
