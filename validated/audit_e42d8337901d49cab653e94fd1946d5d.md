### Title
Cross-repository Status injection via unscoped SHA lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Commit#refresh_statuses!` only ever fetches statuses from GitHub scoped to the owning stack's own `github_repo_name`, but the webhook-driven `StatusHandler#process` resolves the target commit purely by `sha` string equality across the entire `commits` table, with no check that the SHA belongs to the repository named in the webhook payload. This lets an attacker who can send an authenticated `status` webhook for a repository they own write a `Status` record onto a commit belonging to an unrelated stack/repository, provided the sha strings match.

### Finding Description
The broken binding: for `Commit#refresh_statuses!`, `stack.github_api.statuses(github_repo_name, sha, ...)` binds `github_repo_name` (the stack's own repo) == the repo the status data is fetched for [1](#0-0) . For the webhook path, `StatusHandler#process` does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This looks up commits globally by `sha`, with no reference to `payload.dig('repository', 'full_name')` or `stack.github_repo_name` at all — unlike the base `Handler` class, which defines a `stacks` helper that resolves stacks strictly via `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and unlike other handlers (e.g. the `PullRequest` handlers) that iterate `stacks.each` to scope operations to the repository asserted by the payload. `StatusHandler` never calls `stacks`, so the same-repo invariant enforced on the pull side (`refresh_statuses!` always calling `stack.github_api.statuses` with that stack's own `github_repo_name`) is completely absent on the push/webhook side.

`create_status_from_github!` itself performs no repo check either — it simply calls `statuses.replicate_from_github!(stack_id, github_status)` on whatever `commit` was found [4](#0-3) , and `Status.replicate_from_github!` just writes the record [5](#0-4) .

Existing guards do not close this gap:
- `verify_signature` in `WebhooksController` only validates that the payload was signed by the GitHub App/org configured under `repository_owner` from the payload itself [6](#0-5) . It authenticates *that the sender legitimately controls repository_owner's webhook secret*; it says nothing about which `sha` values are legitimate for that repository. An attacker who legitimately owns/administers a repository hooked into a (possibly multi-tenant) Shipit instance can produce a validly-signed `status` payload for their own repo while setting `sha` to any string, including the SHA of a commit that exists in a completely different stack's repo.
- `ExplicitParameters` schema for `StatusHandler` only requires `sha` and `state` be strings; it does not require or verify `repository.full_name` matches anything [7](#0-6) .
- `drop_unhandled_event` and `check_if_ping` are unrelated to this check.

So the binding "the repo used to authenticate is the repo whose commits get statuses written" holds for `refresh_statuses!` but is violated for the `status` webhook path.

### Impact Explanation
An attacker with legitimate control of one repository/stack hooked into Shipit can write arbitrary `Status` rows onto commits belonging to a victim's stack, as long as they can produce (or already know) a matching `sha` string. Because commit `sha`s are frequently public (visible in PRs, git history, CI logs), an attacker does not need an actual SHA-1 collision to exploit this in general — they only need to know the victim's commit SHA and reference it in their own webhook payload. Writing a forged "success" status can flip `commit.deployable?` to true (via `add_status`'s `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`), potentially causing an unrelated commit to become eligible for merge or continuous deployment in the victim stack — this is a payload for one repository mutating another stack/commit's state, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). This is repeatable against any stack whose commit SHAs are known/guessable and is not limited to a single victim.

### Likelihood Explanation
Preconditions: (1) Shipit instance configured for more than one organization/repository (multi-tenant use, which is the engine's normal design), (2) attacker has legitimate ownership/administration of at least one repository already registered as a Shipit stack (so a valid webhook secret is provisioned for their org/repo by Shipit's normal onboarding), (3) attacker knows or can predict a target commit SHA in the victim's repo. Given these, the attack costs the attacker only crafting a `status` event JSON body with the target `sha` and a legitimate signature from their own repo — no GitHub secrets, Shipit session, or victim's credentials are required. This is inexpensive and fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare `Commit.where(sha: ...)`) to the repository asserted in the payload, mirroring the `stacks` helper already used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the invariant that a status write only applies to commits belonging to the same `github_repo_name` that authenticated the webhook, matching the guarantee already enforced by `Commit#refresh_statuses!`.

### Proof of Concept
Minitest plan (model + controller level), no live GitHub required:
1. In `test/models/commits_test.rb`, add a test asserting the equality-binding on `refresh_statuses!`: stub `stack.github_api` and assert it is called with `(stack.github_repo_name, commit.sha, per_page: 100)` — i.e. `stack.github_api.expects(:statuses).with(stack.github_repo_name, commit.sha, per_page: 100)`.
2. In `test/models/webhooks/handlers/status_handler_test.rb` (or `test/controllers/webhooks_controller_test.rb`), create two stacks/commits with the *same* `sha` (`shipit_commits(:first)` in stack A, and a second commit created with the same `sha` in stack B/a different repo). Send a `status` webhook payload whose `repository.full_name` matches stack B's `github_repo_name` only, with `sha` equal to the shared value, and a valid/stubbed signature.
3. Assert: `stack_b_commit.statuses.count` increases (expected, same-repo write) AND `stack_a_commit.statuses.count` also increases (unexpected cross-repo write), demonstrating that `StatusHandler#process` wrote a `Status` onto a commit in a stack whose `github_repo_name` never appeared in the payload — violating the binding that holds for `refresh_statuses!`.
