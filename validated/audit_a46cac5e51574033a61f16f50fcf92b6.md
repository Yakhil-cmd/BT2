### Title
Rule enforcement bypass via relative-path rule discovery in `load_rules` - (File: plugins/hookify/core/config_loader.py)

### Summary
`load_rules` locates hookify guardrail files using a path relative to the process's current working directory (`os.path.join('.claude', 'hookify.*.local.md')`) rather than an absolute path anchored to the trusted project root. Since `pretooluse.py` (and the other hook scripts) invoke `load_rules()` using whatever CWD the Claude Code process/tool happens to have at hook-execution time, an attacker who can influence that CWD (e.g., by getting Claude to `cd` into a subdirectory, nested repo, or worktree before running a `Bash` tool call) can cause the hook to search a `.claude` directory that contains no rule files (or weaker ones), silently disabling the blocking/warning rules that would otherwise fire.

### Finding Description
`load_rules` builds its search pattern relative to the interpreter's CWD: [1](#0-0) 
`glob.glob` resolves `'.claude/hookify.*.local.md'` against `os.getcwd()`, not against a fixed project/plugin root. `pretooluse.py` calls `load_rules(event=event)` on every `Bash`/`Edit`/`Write`/`MultiEdit` tool invocation and feeds the returned rules into `RuleEngine.evaluate_rules` to decide whether to warn/block the action: [2](#0-1) 

Because Claude Code's Bash tool executes shell commands (which can include a `cd`) and the hook script's own working directory tracks the shell/tool CWD, any prompt or repository content that induces the agent to run a command from a different directory (a nested subdirectory lacking a `.claude` folder, a git worktree, a submodule, or any directory reached via `cd ... && <dangerous command>`) will make `load_rules()` glob against that directory's `.claude/` instead of the top-level project's `.claude/`. If no matching directory `.claude` exists there, `glob.glob` simply returns an empty list and `load_rules` returns `[]`, silently disabling all guardrail rules for that call with no warning/error surfaced to the user (the `try/except` blocks in `load_rules`/`load_rule_file` only handle read/parse errors, not "no rules found").

There is no allowlist, workspace-root anchoring, or repo-scoping check anywhere in `load_rules`/`load_rule_file` to ensure the `.claude` directory being searched belongs to the trusted project root.

### Impact Explanation
This is an approval/enforcement bypass: hookify rules are meant to block or warn on dangerous commands/file edits (e.g., `rm -rf`, sensitive file writes) as defined by the maintainer's local rule files. By steering the tool's CWD away from the directory containing those rule files, an attacker-influenced automation flow (e.g., untrusted repo content instructing the agent to `cd subdir && rm -rf ...`) can cause the guardrail to evaluate against zero rules, allowing an otherwise-blocked destructive command or file mutation to execute unimpeded. This matches the "hook enforcement / workspace guard bypass" bounty category since a security control silently and invisibly becomes a no-op.

### Likelihood Explanation
Feasibility depends entirely on whether an attacker (via issue/PR text, repository README, or other content Claude reads) can cause the agent to run a shell command from a different working directory before the sensitive action, which is a common and low-friction pattern in agentic workflows (e.g., `cd build && ...`). No special privileges are required beyond the ability to influence what commands the agent chooses to run, which is within the threat model of "attacker input reachable from ordinary repository content." This is straightforward to reproduce deterministically.

### Recommendation
Anchor rule discovery to a fixed, trusted root instead of the ambient CWD — e.g., use `CLAUDE_PROJECT_DIR`/`CLAUDE_PLUGIN_ROOT` (already used elsewhere in the hook scripts) or the directory where the Claude Code session was originally started, and resolve `.claude/hookify.*.local.md` as an absolute path from that root regardless of the tool's current working directory. Additionally, log/warn when zero rule files are found so a silent bypass is not indistinguishable from "no rules configured by design."

### Proof of Concept
Unit/integration test plan:
1. Create a temp project root `proj/` containing `proj/.claude/hookify.block-rm.local.md` with frontmatter `event: bash`, `pattern: "rm -rf"`, `action: block`.
2. Create `proj/subdir/` with no `.claude` directory.
3. Test A (baseline): `os.chdir('proj')`; call `load_rules(event='bash')`; assert the returned list contains the `block-rm` rule.
4. Test B (bypass): `os.chdir('proj/subdir')`; call `load_rules(event='bash')`; assert the returned list is empty (`[]`), demonstrating that the same logical project's guardrail rule is no longer discovered.
5. Integration test: invoke `plugins/hookify/hooks/pretooluse.py` main() with stdin JSON `{"tool_name": "Bash", "tool_input": {"command": "rm -rf /important"}}` twice — once with CWD at `proj/`, once with CWD at `proj/subdir` — and assert the hook's JSON output blocks/warns in the first case but allows silently in the second, confirming the enforcement bypass.
