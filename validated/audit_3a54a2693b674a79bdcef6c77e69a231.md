## Title
CCMenu API endpoint bypasses stack-scoped `ApiClient` authorization, allowing a stack-restricted token to read any stack's state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The `Api::CCMenuController` authenticates an `ApiClient` by token but resolves the target `Stack` directly from `params[:stack_id]` via `Stack.from_param!`, instead of scoping through `stacks.from_param!` as the rest of the API does. This breaks the binding between "the stack an `ApiClient` token authorizes" (`ApiClient#stack_id`) and "the stack the request actually touches," letting any holder of a stack-scoped, `read:stack`-permitted token read the CI/deploy status of every stack in the installation, not just the one it was issued for.

### Finding Description
`ApiClient` records can be scoped to a single stack via the optional `belongs_to :stack` / `stack_id` association [1](#0-0) . `Api::BaseController` enforces this scoping centrally: the `stacks` helper restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-bound, and every controller is expected to resolve its target stack through `stacks.from_param!` [2](#0-1) . This is exactly how `Api::StacksController#stack` and `Api::TasksController` resolve their stack [3](#0-2) .

`Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely bypassing the `current_api_client.stack_id` restriction, while still only requiring the generic `read:stack` permission bit via `require_permission :read, :stack` [4](#0-3) . `require_permission!` only checks `current_api_client.check_permissions!(operation, scope)`, i.e., whether the string `"read:stack"` is present in the client's `permissions` array — it never checks `stack_id` [5](#0-4) [6](#0-5) .

This is the same class of bug as the external report: a check (permission bit) is satisfied while a different, more specific binding (which resource the credential was scoped to) is silently not re-validated at the point of use, and an untrusted party controls the parameter (`params[:stack_id]`) that determines which resource is actually touched.

### Impact Explanation
Any `ApiClient` token issued with `read:stack` permission and intentionally scoped to a single stack (e.g. the `here_come_the_walrus` fixture pattern used elsewhere in the codebase, or any partner/integration token an operator creates with `stack:` set to restrict blast radius) can be replayed against `Api::CCMenuController#show` with an arbitrary `stack_id` belonging to a *different* stack. The attacker (holder of one legitimately scoped, low-privilege token) obtains CI/build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity, lock state) for stacks they were never authorized to see. This matches the "unauthenticated/unauthorized read of stack state" High-impact category, since the whole point of `stack_id`-scoped `ApiClient`s is to prevent exactly this kind of cross-stack visibility.

### Likelihood Explanation
Exploitation requires only a valid, already-issued API token with `read:stack` permission (the minimal, most commonly granted permission) — no privileged account, no repository write access, and no session is needed beyond what the operator already handed to a limited integration. The only action required is substituting a different `stack_id` in the request URL/params, which is trivial and requires no special tooling.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` helper (i.e. `stacks.from_param!(params[:stack_id])`) exactly as `Api::StacksController` and `Api::TasksController` do, so that a stack-bound `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. As an operator, issue an `ApiClient` with `permissions: ['read:stack']` and `stack: stack_a` (mirroring the `here_come_the_walrus` fixture pattern) [7](#0-6) .
2. Using that client's Basic Auth token, call `GET /api/stacks/:stack_id/ccmenu.xml` where `:stack_id` is `stack_b`'s param (a stack this client is not scoped to).
3. `authenticate_api_client` succeeds (token is valid) [8](#0-7) ; `require_permission :read, :stack` succeeds because the client has `read:stack` regardless of which stack; `stack` resolves `stack_b` via unscoped `Stack.from_param!`, bypassing the intended `stack_id` restriction [9](#0-8) .
4. The response renders `stack_b`'s CI/deploy status, which the token was never authorized to access.

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
```
