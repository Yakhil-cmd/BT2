### Title
Webhook signature verification is keyed by attacker-controlled `repository.owner.login`, decoupled from the `repository.full_name` the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to HMAC-verify a webhook against using `repository_owner`, a value read straight out of the unauthenticated request body. The handlers that actually process the event, however, resolve the target `Repository`/`Stack` using a *different* field of the same body: `repository.full_name`. Because the signature only binds "some organization config accepted this body," not "this specific repository's secret produced this signature," an attacker who can get one single low-value/no-secret organization configured in `Shipit.github` can forge events for any other organization's repositories/stacks configured in the same Shipit instance.

### Finding Description
The controller picks the verification key like this: [1](#0-0) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — entirely attacker-supplied JSON, unauthenticated at this point. It is used to fetch a per-organization `GitHubApp` config and check the signature with that org's `webhook_secret`: [2](#0-1) 

Critically, `verify_webhook_signature` returns `true` unconditionally when that organization's config has no `webhook_secret` set (`return true unless webhook_secret`). This is a documented/supported configuration state — the shipped example configs explicitly show `webhook_secret: # nil` as a valid per-organization setting: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (because the *owner* org happens to have no secret configured), the raw JSON body is dispatched to handlers unmodified. The handlers, however, never re-check `repository.owner.login`; they resolve the target Stack purely from `repository.full_name`: [5](#0-4) 

So the field that gated cryptographic trust (`repository.owner.login`) and the field that determines which real repository is mutated (`repository.full_name`) are two independent, attacker-controlled strings in the same unauthenticated JSON body. Nothing forces them to agree, and nothing re-validates that the "authenticated" owner actually owns the "full_name" acted upon.

This directly parallels the reorg analog's bug class: a value the attacker controls (`Vault`'s minter/salt inputs) is trusted by a downstream contract call without being bound to the value that was actually verified/committed (the deployed address). Here, the "authenticated organization" and "the repository that is written" are supposed to be the same entity but are never bound together.

Concretely exploitable handlers:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for any stack under the forged `full_name`/branch: [6](#0-5) 
- `StatusHandler` writes arbitrary CI status objects (`state`, `description`, `target_url`, `context`) for any commit sha it can guess/know, without any check tying the claimed org back to the commit's real repository: [7](#0-6) 
- `CheckSuiteHandler` schedules check-run refreshes for arbitrary stacks/commits by sha+branch: [8](#0-7) 

### Impact Explanation
Status/check-run data is used by Shipit to gate whether a commit is eligible to ship (statuses/check-runs feed into commit "checks" that continuous-deployment and manual-deploy eligibility rely on). An attacker who can forge `status`/`check_suite` events for a victim's repository — despite that repository's real GitHub App/organization having a properly configured `webhook_secret` — can inject a fabricated "success" status/check-run for an arbitrary commit sha, which is the kind of signal Shipit uses to decide a commit is safe to deploy. Combined with continuous delivery, this can lead to an unauthorized/unintended deploy of a commit that never actually passed CI, i.e., a bypass of the deploy-safety authorization Shipit is meant to enforce.

### Likelihood Explanation
Exploitability is entirely dependent on whether the Shipit deployment hosts more than one GitHub organization and whether any one of them (even an unrelated, low-value org unrelated to the victim's stacks) is configured with a blank `webhook_secret`. Multi-org configuration is an explicitly documented and supported feature (`test/dummy/config/secrets_double_github_app.yml`), and leaving `webhook_secret` blank is shown as a valid, non-error configuration in the shipped example secrets files. No GitHub App private key, `api_clients_secret`, session, or `ApiClient` token is required — only network access to the public `/github/webhooks` endpoint and knowledge of the unsecured org's login name (discoverable, e.g., from public GitHub org pages or Shipit's own public pages listing stacks/repos). This makes it a realistic, low-privilege attack path rather than a purely theoretical one, though it depends on the specific operator's multi-org setup.

### Recommendation
Bind the value used for signature-key selection to the value used for repository resolution:
- After signature verification succeeds, re-derive `repository_owner`/`repository_owner_login` strictly from the same `repository.full_name` field the handlers use, and reject the request (422) if the org that authenticated the signature does not match the owner segment of `repository.full_name`.
- Alternatively/additionally, look up the target `Repository`/`Stack` by full name first, resolve *that* repository's configured GitHub App/org, and verify the signature exclusively against that resolved organization's secret — never against an org name taken opportunistically from the payload.
- Disallow (or at minimum, log loudly and refuse to accept live webhooks for) organizations configured with a blank `webhook_secret` in production, since a single such organization silently disables the entire signature-verification guarantee for events claiming to originate from that org.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs in `Shipit.github`: `victim-org` (has stacks, `webhook_secret: <real-secret>`) and `low-value-org` (any org the admin didn't bother securing, `webhook_secret: nil`), matching the documented multi-org config shape in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "low-value-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://example.com"
}
```
No `X-Hub-Signature` header is required to be valid because `verify_signature` resolves `repository_owner` to `"low-value-org"` [9](#0-8) , whose `GitHubApp#verify_webhook_signature` short-circuits `true` since that org has no `webhook_secret` configured [10](#0-9) .
3. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds the real commit by `sha` (independent of any org/owner check) and writes the forged `success` status onto the victim's commit [7](#0-6) .
4. If `victim-org/victim-repo`'s stack has continuous deployment enabled and this status/check is part of its required checks, the forged green status can make an otherwise-unverified commit eligible for automatic deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
