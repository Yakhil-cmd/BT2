### Title
`StatusHandler` and multi-org webhook signature scoping mismatch allow cross-tenant CI status forgery leading to unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
In a multi-GitHub-organization Shipit deployment, the webhook signature is verified using a `webhook_secret` selected from the organization named inside the payload's own `repository.owner.login`/`organization.login` field, but at least one event handler (`StatusHandler`) never checks that field again when deciding which record to mutate — it looks up commits purely by `sha` across the entire database, with no repository/stack scoping at all. This breaks the intended binding "organization that authenticated == repository/stack that is written," letting a legitimate tenant (an org owner who knows only their own webhook secret) forge CI status updates for any other tenant's commits, which can defeat CI-gating and enable an unauthorized deploy.

### Finding Description
`WebhooksController#verify_signature` derives `repository_owner` from the payload itself and uses it purely to pick which org's secret to verify with: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` supports a config schema where each GitHub organization has its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

So the equality this design is supposed to enforce is: **organization whose secret validated the signature == organization/repository whose data the handler is allowed to mutate**.

Most webhook handlers reconstruct the target repository from `payload.dig('repository', 'full_name')` via the base `Handler#stacks`/`#repository_name`, or via `params.repository.full_name` in the PR handlers: [5](#0-4) 

Critically, `StatusHandler` — used for the `status` GitHub event — does **no repository scoping whatsoever**. It matches by commit `sha` alone, across the whole `Commit` table (i.e., across every stack of every tenant): [6](#0-5) 

This means that in a multi-org configuration, any org onboarded to the shared Shipit instance can send a `status` webhook whose signature is valid for their own org's secret (since `repository_owner` is self-reported in the same payload and only used to pick which secret to check against), while `sha` targets a commit belonging to a **different tenant's** stack. Because `repository.owner.login`/`organization.login` is only used for secret selection and never cross-checked against the actual commit's stack/repository, the "org authenticated" and "repository/commit written" bindings diverge.

`Commit#create_status_from_github!` persists the forged status unconditionally: [7](#0-6) 

That status feeds directly into deployability: [8](#0-7) [9](#0-8) 

And a "success" status transition triggers merges/continuous-delivery scheduling for the victim stack: [10](#0-9) 

### Impact Explanation
An attacker who is a legitimate tenant admin of Org A (knows only Org A's `webhook_secret`, configured for their own GitHub App/org in a shared multi-org Shipit instance) can forge a `status` webhook naming `repository.owner.login = OrgA` (so the signature check passes with OrgA's secret) while setting `sha` to a commit belonging to Org B's stack, and `state: success`. Because `StatusHandler` performs no cross-check against the authenticated organization, this fake "success" status is recorded on Org B's commit. If that commit was previously blocked from deploying due to failing/missing CI (`Commit#deployable?`, `required_statuses`), the forged status can flip it to deployable and trigger `stack.schedule_merges` / continuous delivery, resulting in an **unauthorized deploy** of unreviewed/unvetted code for a different tenant — meeting the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only that Shipit be configured with the documented multi-organization GitHub App feature (explicitly supported and documented) and that the attacker be a legitimate onboarded tenant with their own valid webhook secret — no privileged Shipit account, no `ApiClient` token, and no repository write access to the victim's repo is required. The webhook endpoint (`WebhooksController#create`) is public and unauthenticated beyond the per-payload signature check. The only extra knowledge needed is a target commit `sha` belonging to another tenant, which is often discoverable (public repos, PR pages, etc.).

### Recommendation
In `WebhooksController` (or in each `Handler`), after verifying the signature, cross-check that the organization whose secret validated the request actually matches the repository/stack that the handler is about to mutate — e.g., resolve the `Stack`/`Repository` via `repository.full_name` and confirm its owner equals `repository_owner` before dispatching. Additionally, scope `StatusHandler#process` (and any other handler that doesn't already do so) to commits belonging to the repository named in the payload, not to `sha` alone, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Preconditions: Shipit configured with multi-org GitHub Apps (`OrgA`, `OrgB`), each with its own `webhook_secret`; attacker legitimately controls `OrgA`'s app/secret; `OrgB` has a stack with a commit `<victim_sha>` that is currently not deployable (e.g., failing/missing CI status).

1. Attacker crafts a JSON body:
```json
{
  "sha": "<victim_sha>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` — this is valid because `verify_signature` looks up `Shipit.github(organization: "OrgA")` from `repository.owner.login`, matching the secret used.
3. Attacker sends `POST /github_webhooks` with header `X-Github-Event: status` and the above body/signature.
4. `WebhooksController#verify_signature` passes (correct secret for the self-declared `OrgA`). `StatusHandler#process` runs `Commit.where(sha: "<victim_sha>")` — matching Org B's commit — and calls `create_status_from_github!`, recording a fabricated `success` status on Org B's commit despite no relationship between OrgA and OrgB's repository.
5. If required CI statuses were the only blocker, `Commit#deployable?` now returns true and `stack.schedule_merges`/continuous delivery can trigger an unauthorized deploy on Org B's stack.

Note: I was not able to execute this against a running instance; the analysis is based on static code review of `WebhooksController`, `Shipit.github`/`GitHubApp#verify_webhook_signature`, `Handler`, and `StatusHandler`/`Commit`. Confirming the full exploit chain end-to-end (e.g., exact deploy-trigger side effects) would benefit from a live Devin session against a running Shipit instance configured with multiple organizations.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
