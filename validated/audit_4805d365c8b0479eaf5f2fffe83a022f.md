Confirmed: `Api::StacksController#stack` uses the scoped `stacks.from_param!` helper from `BaseController` [1](#0-0)  which restricts lookup to `current_api_client.stack_id` when set [2](#0-1) , while `Api::CCMenuController#stack` bypasses that scoping entirely by calling `Stack.from_param!(params[:stack_id])` directly [3](#0-2) .

### Title
Api::CCMenuController bypasses ApiClient stack scoping, letting a token authorized for one stack read any stack's status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack via `stack_id`, and `BaseController#stacks`/`#stack` enforce that scoping by restricting lookups to `Stack.where(id: current_api_client.stack_id)` whenever `stack_id?` is true [2](#0-1) . `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, ignoring `current_api_client.stack_id` entirely [3](#0-2) . This breaks the binding "stack a token authorizes == stack it touches": a `read:stack` token minted and scoped to stack A (e.g. via `CCMenuUrlController`, which creates an `ApiClient` bound to a specific stack for CCTray integration) can be replayed against `CCMenuController#show` with a different `stack_id` param to read any other stack's latest deploy/rollback status, regardless of the token's intended scope.

### Finding Description
`CCMenuUrlController#client` mints (or reuses) an `ApiClient` with `permissions: %w[read:stack]`, embeds its `authentication_token` in a CCTray URL scoped to a specific stack [4](#0-3) , and this token is designed to be handed out to third-party CI dashboard tools for a single stack's status feed [5](#0-4) .

`Api::CCMenuController#authenticate_api_client` authenticates any valid `ApiClient` token via `ApiClient.authenticate(params[:token])` [6](#0-5) , and `require_permission :read, :stack` only checks that `"read:stack"` is present in the client's `permissions` array via `ApiClient#check_permissions!` — it never compares `current_api_client.stack_id` to the requested stack [7](#0-6) . The actual per-stack restriction only happens through the `stacks`/`stack` helper in `BaseController`, which every other API controller (e.g. `Api::StacksController#stack`, `Api::TasksController`) relies on via `stacks.from_param!` [2](#0-1) ; `Api::CCMenuController` alone re-defines `#stack` to skip this scoping and go straight to the global `Stack.from_param!` [8](#0-7) .

Consequently, a token that is stored/leaked from one CCTray consumer for stack A — a stack a leaked/shared token was only ever meant to authorize — can be used unmodified against `GET /api/stacks/:stack_id/ccmenu.xml` with any other `:stack_id`, and the response (last deploy/rollback status, running state, timestamps) for that unrelated stack will be returned.

### Impact Explanation
This is an unauthenticated-boundary read: possession of a `read:stack`-scoped token for stack A grants unauthorized read of stack state for stack B, C, … — any stack in the installation — which matches the "unauthenticated read of stack state" High-impact category in scope, since the token was never authorized for those other stacks. It does not require the attacker's own Shipit session, only the previously-issued CCMenu token for a different stack.

### Likelihood Explanation
Any holder of a legitimately-scoped CCMenu token (e.g. a CI dashboard operator, or anyone who can see the generated `ccmenu_url`, which embeds the token in plain query string per `CCMenuUrlController#fetch`) can trivially exploit this by changing the `stack_id` path segment on an otherwise identical authenticated request; no additional secret or privilege is required beyond having any one valid scoped token.

### Recommendation
In `Api::CCMenuController#stack`, use the inherited scoped `stacks.from_param!(params[:stack_id])` helper (as `Api::StacksController` and other API controllers do) instead of calling `Stack.from_param!` directly, so that a token scoped to `current_api_client.stack_id` cannot resolve stacks outside that scope.

### Proof of Concept
1. As an authenticated Shipit user with access to stack A, call `CCMenuUrlController#fetch` (`GET /*stack_id/ccmenu_url` for stack A) to obtain a `ccmenu_url` containing a `token` for an `ApiClient` scoped to stack A with `permissions: ['read:stack']` [9](#0-8) .
2. Take that `token` and issue `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=<token>` for an unrelated stack B.
3. `Api::CCMenuController#authenticate_api_client` accepts the token (it is a valid `ApiClient`) [6](#0-5) , `require_permission :read, :stack` passes because the token has `read:stack` [7](#0-6) , and `#stack` resolves stack B directly via `Stack.from_param!(params[:stack_id])` without checking that the token's `stack_id` is stack A [8](#0-7) .
4. The response renders stack B's latest deploy/rollback status — data the token was never scoped to access.
