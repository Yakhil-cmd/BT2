### Title
Missing `return` after payload-hash exception causes private payment chain to be processed and saved despite reported error - ([File: network.js])

### Summary
In `network.js`, function `handleSavedPrivatePayments` → inner `validateAndSave`, when hashing the head private element's payload throws (`objectHash.getBase64Hash` fails), the code reports the error to the peer and marks the chain for deletion, but does **not** `return` — execution falls through to still validate and save the private payment chain via `privatePayment.validateAndSavePrivatePaymentChain`. This is structurally identical to the Graylog bug class: the correct error is emitted, but the payload is "ingested" (processed/saved) anyway.

### Finding Description
`validateAndSave` at [1](#0-0)  computes `json_payload_hash` inside a `try/catch`. On exception it logs the error, optionally sends an error result to the websocket, and calls `deleteHandledPrivateChain(...)` to mark the chain as handled — but there is no `return` statement inside the `catch` block. Control flow continues past the `try/catch` to line 2478, which builds `key` using the now-`undefined` `json_payload_hash`, and then unconditionally calls: [2](#0-1) 

`privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` is invoked regardless of the earlier failure. This mirrors the disclosed advisory's root cause exactly: the "401"-equivalent (error report + deletion marker) is correctly produced, but the message is nonetheless passed into the downstream ingestion/validation pipeline (`validateAndSavePrivatePaymentChain`), which can insert rows into `outputs`/`inputs` for the asset in question via [3](#0-2) .

Additionally, since `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` was already called in the catch branch, `cb` may be invoked a second time when the subsequent `validateAndSavePrivatePaymentChain(...)` callback (`ifOk`/`ifError`/`ifWaitingForChain`) also calls `deleteHandledPrivateChain(..., cb)` or `cb()` directly, causing double invocation of the `async.each` iteratee callback — a separate but related correctness bug that can lead to premature "done" callback firing, races on `assocNewUnits`, or duplicate event emissions (`emit(key, ...)`), which downstream code (e.g. wallet.js `handlePrivatePaymentChains`'s `eventBus.once(key, ...)`) uses to gate acceptance of a chain.

### Impact Explanation
This code path executes for private (indivisible/divisible) asset payment chains that a device/wallet operator queued in `unhandled_private_payments` and is now trying to finalize (`handleSavedPrivatePayments`). Any attacker-controlled private element whose `payload` triggers a hashing exception in `objectHash.getBase64Hash` (e.g. malformed/edge-case payload shapes that pass upstream `isNonemptyObject`/array checks but break during canonical JSON hashing) causes the local node to:
1. Report the chain as erroneous to the sender/peer, and
2. Still forward the (unhashed / unverified-by-hash) `arrPrivateElements` into `validateAndSavePrivatePaymentChain`, which performs its own SQL-based validation and, on success, inserts `outputs`/`inputs` rows for the private asset — potentially recording spends/issuances that were never properly hash-verified.

Because the payload's `output_hash` correctness (verified in `indivisible_asset.js`'s `validatePrivatePayment` at [4](#0-3)  and asset duplicate-detection logic in `private_payment.js`) depends on other parts of the payload being self-consistent, the fact that the "quick" `objectHash.getBase64Hash` on the head payload failed suggests the payload is malformed in a way the initial hashing step could not handle — yet it is still fed to the full validation/save pipeline that inserts financial records (`outputs`, `inputs`) for a private asset. This can lead to inconsistent/duplicate private-asset ledger state on the receiving node (a form of double-processing / asset-accounting corruption for private payments), which the report classifies as node disagreement on validity or potential loss/duplication of privately transferred asset accounting — a Medium-severity issue analogous to the "ingest despite auth failure" class, reachable by any private-payment counterparty sending a crafted private chain.

### Likelihood Explanation
Reachable by any counterparty in a private payment (asset issuer, private-payment sender) who can control the `payload` of the head private element sent via `hub/deliver`/`private_payments` device messages, which are stored to `unhandled_private_payments` and later processed by `handleSavedPrivatePayments`. Triggering an exception specifically inside `objectHash.getBase64Hash(payload, true)` while the rest of the payload still passes downstream structural checks in `validateAndSavePrivatePaymentChain`/`validatePrivatePayment` requires a fairly narrow malformed input (e.g., a value that breaks canonical-JSON hashing, such as unsupported types or circular-like structures nested in `payload`), making exploitation non-trivial but plausible given the various object-hash edge cases documented elsewhere in the codebase (e.g. `getJsonSourceString` throwing on nulls/empty objects). This keeps likelihood at Medium rather than High.

### Recommendation
Add a `return` (or `return cb()`/`return;`) immediately after `deleteHandledPrivateChain(...)` inside the `catch` block of `validateAndSave` in `network.js`, so that a payload-hashing failure aborts processing of that chain instead of falling through to `privatePayment.validateAndSavePrivatePaymentChain`. Additionally, avoid calling `deleteHandledPrivateChain(..., cb)` in the catch handler if code below might also invoke `cb`, to prevent double-callback issues in the `async.each` iteration.

### Proof of Concept
1. As a peer/private-payment counterparty, construct a `private_payments` message whose chain's head element has a `payload` object that is structurally valid enough to pass the `isNonemptyObject`/array checks performed in `wallet.js handlePrivatePaymentChains` ( [5](#0-4) ), but which causes `objectHash.getBase64Hash(payload, true)` to throw when computing `json_payload_hash` (e.g., malformed nested structures known to break canonical hashing).
2. Send this to the target wallet's device via `hub/deliver`, causing it to be queued in `unhandled_private_payments` and later processed by `network.js`'s `handleSavedPrivatePayments`.
3. Observe that the target sends an error result over the websocket (`result: 'error'`) and calls `deleteHandledPrivateChain`, yet immediately afterward still invokes `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` at [6](#0-5) , which can insert `outputs`/`inputs` rows for the asset if the rest of the SQL-based validation in `private_payment.js`/`indivisible_asset.js` happens to succeed on the same malformed-but-hash-broken payload.
