### Title
Stale index/lindex cache lets bad-debt socialization losses be hidden from other users' collateral pricing within the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's accrual output (`index`, `lindex`) in the `index-cache` map, keyed only by `{ timestamp: stacks-block-time, aid }`. Whichever user's transaction is the first to call `accrue-and-cache` for a given asset in a block primes this cache; every other transaction that touches the same asset later in that same block reads the cached value via `get-cached-indexes` / `resolve-ztoken` instead of re-deriving it, and the market never re-validates the cached entry against the vault's authoritative state before other users consume it. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue-and-cache` implements a classic "write-once, read-many" cache per block: on cache miss it calls `vault-accrue`, stores the returned `{index, lindex}` under the current block timestamp, and on cache hit simply returns whatever was stored earlier in the block, with no check that this value still represents the vault's true current state: [1](#0-0) 

`resolve-ztoken`, used for pricing any zToken collateral (zSTX, zsBTC, zstSTX, zUSDC, zUSDH, zstSTXbtc) during borrow/withdraw/health-factor/liquidation checks, blindly trusts this cached `lindex`: [2](#0-1) 

Meanwhile, the vault's `socialize-debt` function can sharply reduce the true `lindex` — even to `u0` — when bad debt exceeds a vault's total assets, permanently marking down the value backing every holder of that vault's zToken: [3](#0-2) 

The vulnerability mirrors the reported bug class exactly: just as `fallback_backup_kernel` copies backup data back into production storage without checking it is still valid, `accrue-and-cache`/`resolve-ztoken` reuse a previously-stored (cached) index value without checking it is still consistent with the vault's authoritative, possibly just-socialized state. Because the cache key is only `(timestamp, aid)` — not tied to the calling transaction or to the vault's `last-update` — any transaction earlier in the block that primes the cache before a `socialize-debt` event leaves a stale, overstated `lindex` in `index-cache` for the remainder of the block. Any *other*, unrelated user whose position is evaluated later in that same block (borrow, withdraw, health check, or being spared liquidation) will have their zToken collateral priced using this stale, too-high `lindex` instead of the marked-down value that reflects the real bad-debt loss.

### Impact Explanation
This is a shared-cache-poisoning issue between unrelated principals, not a self-harm scenario: one user's early-block transaction (attacker or innocent) primes the cache; a socialize-debt event for a *different* vault/user occurs later in the same block; a *third*, unrelated user's collateral valuation and borrowing capacity for the remainder of the block are computed against the stale, overstated index instead of the corrected one. This lets that third user borrow against collateral that is not actually worth what the market believes, or avoid a liquidation that should otherwise trigger, extracting value that is ultimately backed by (and paid for by) the rest of the pool's suppliers — a socialized loss compounded by mispriced collateral. Depending on the amounts involved this can amount to protocol insolvency or temporary freezing/misallocation of supplier funds.

### Likelihood Explanation
Requires: (1) a bad-debt event large enough to trigger `socialize-debt`'s markdown path, and (2) at least one other transaction touching the same asset earlier in the same block (priming the cache) and one after (consuming the stale cache). Both conditions are plausible in normal operation — liquidations/bad-debt handling and ordinary user activity (borrows, withdrawals, health checks) routinely occur in the same block on an active chain — making this reachable without any privileged access, purely through ordinary transaction ordering within a block.

### Recommendation
Invalidate or refresh the `index-cache` entry for an asset whenever `socialize-debt` (or any operation that mutates a vault's `lindex`/`index` outside the normal `accrue` path) is executed, or eliminate the timestamp-only cache key in favor of always re-reading the vault's authoritative index for calculations that determine solvency-critical values such as collateral pricing and liquidation eligibility.

### Proof of Concept
1. Block N, Tx 1 (any user): calls a market operation on `sBTC`/`zsBTC` that triggers `accrue-and-cache`, caching `lindex = L0` for `{timestamp: T, aid: sBTC}`. [4](#0-3) 
2. Block N, Tx 2: a liquidation leaves uncovered bad debt on the sBTC vault, causing `socialize-debt` to be invoked, which writes down the vault's real `lindex` to `L1 << L0` (or `u0`). [3](#0-2) 
3. Block N, Tx 3 (unrelated user B): borrows against zsBTC collateral or is health-checked. `resolve-ztoken` calls `get-cached-indexes sBTC`, hits the cache from Tx 1, and prices zsBTC using stale `L0` instead of the corrected `L1`. [2](#0-1) 
4. User B's collateral is valued higher than the vault can actually back, letting B borrow beyond real backing or escape a liquidation that should have triggered under the corrected index — extracting value ultimately socialized across the vault's suppliers.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
