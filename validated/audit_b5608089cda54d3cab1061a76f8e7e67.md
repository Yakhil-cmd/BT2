## Title
Cross-stack authorization bypass in CCMenu API endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#show` resolves the target stack with `Stack.from_param!(params[:stack_id])` instead of the stack-scoped helper `stacks.from_param!` used by every other API controller. As a result, an `ApiClient` token that is scoped to a single stack (`stack_id` set) — including the read-only token minted by `Shipit::CCMenuUrlController` specifically to expose one stack's CI status — can be replayed against the `ccmenu` endpoint for *any* stack in the Shipit instance, not just the one it was authorised for.

### Finding Description
Every other stack-scoped API controller resolves its target stack through the `stacks` helper defined in `Shipit::Api::BaseController`: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This enforces the invariant: **the stack a token is allowed to read == the stack it actually touches**, e.g. in `DeploysController`, `TasksController`, and `StacksController`.

`CCMenuController`, however, overrides `stack` and bypasses this scoping entirely: [2](#0-1) 

It only calls `Stack.from_param!(params[:stack_id])` on the bare model class, and only checks the *permission string* `read:stack` via `require_permission :read, :stack` — never verifying that `params[:stack_id]` matches `current_api_client.stack_id`. `require_permission!` just calls `current_api_client.check_permissions!(operation, scope)` which checks the permission list, not any stack binding: [3](#0-2) 

Compounding this, `Shipit::CCMenuUrlController` mints exactly this kind of scoped-looking token for a specific stack and hands the resulting URL to the user to be embedded in third-party/unauthenticated CI dashboard tools (CCTray widgets, status pages, etc.): [4](#0-3) 

The generated `ccmenu_url` embeds `client.authentication_token` as a query-string `token` and is intended, by its name and UI ("CCMenu URL"), to disclose CI status for exactly the stack it was generated for (`app/views/shipit/stacks/settings.html.erb`). Because `CCMenuController#show` doesn't enforce the token's stack scope, anyone who obtains this URL (it is designed to be pasted into low-trust, unauthenticated third-party monitoring tools) can swap `stack_id` in the URL to read the CI status of *every other stack* in the Shipit install, including private/internal ones the token was never meant to expose.

The equality that should hold — "the stack a token authorises == the stack it touches" — is broken specifically inside `CCMenuController`.

### Impact Explanation
This is an unauthenticated read of stack state: holding one leaked/shared CCMenu token (or any `read:stack`-scoped ApiClient token, even one deliberately scoped to a single stack) is sufficient to enumerate and read the last build status, last build label/time, and web URL of every stack managed by the Shipit instance, bypassing the intended per-stack scoping of `ApiClient#stack_id`. This matches the "unauthenticated read of stack state" High-impact category, since the whole point of scoping the token to one stack was to prevent exactly this kind of disclosure when the token/URL is shared with unauthenticated third parties.

### Likelihood Explanation
Likelihood is high given normal usage: the CCMenu URL feature exists precisely to hand out these tokens to be pasted into external tools/dashboards that don't otherwise authenticate to Shipit. Any such leaked token immediately grants cross-stack read access with a single parameter change in the request URL — no additional privilege or secret is required beyond the token itself.

### Recommendation
Change `CCMenuController#stack` to use the scoped helper, consistent with the rest of the API:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This enforces that the request's `stack_id` is restricted to `current_api_client.stack_id` when the client is stack-scoped, matching the behavior of `DeploysController`, `TasksController`, and `StacksController`.

### Proof of Concept
1. As a legitimate Shipit user, open Stack A's settings page and click "Fetch URL" to generate a CCMenu URL. This creates (or reuses) an `ApiClient` named "CCMenu Client" and returns a URL such as:
   `https://shipit.example.com/api/stacks/org/repoA/production/ccmenu?token=<TOKEN>`
2. Embed/share this URL in a low-trust or unauthenticated context (as intended — a CI status monitor).
3. An attacker who obtains `<TOKEN>` (from the shared dashboard/config) requests a *different* stack:
   `GET /api/stacks/org/repoB/staging/ccmenu?token=<TOKEN>`
4. `CCMenuController#show` succeeds and returns Stack B's CI status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.), even though the token/URL was only ever intended to expose Stack A, because `stack` resolves via `Stack.from_param!` with no scoping check against `current_api_client.stack_id`. [5](#0-4)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
