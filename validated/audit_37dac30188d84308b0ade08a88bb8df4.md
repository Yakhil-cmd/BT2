This confirms `create!` adds the stack to `Shipit::ReviewStackProvisioningQueue`, which drives the provisioning task that clones and executes the repository's `shipit.yml` on the deploy host — meaning the logic bug in `provision?` directly leads to unauthorized command execution when an operator believes review stacks are disabled.

### Title
Operator's `review_stacks_enabled = false` is silently ignored for `allow_with_label` and `prevent_with_label`, letting attacker-controlled PRs still provision review stacks - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` uses `&&`/`||` without parentheses to group the `review_stacks_enabled` guard against all three provisioning behaviors, but Ruby operator precedence only applies `review_stacks_enabled` to the `allow_all` branch. As a result, turning `review_stacks_enabled` off has no effect at all when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, so any PR opener can still get a `ReviewStack` created and enqueued for provisioning, executing the repo's `shipit.yml` on the deploy host.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` implies `OpenedHandler#provision? == false` for all values of `provisioning_behavior`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. The second and third disjuncts (`allow_with_label` and `prevent_with_label`) never reference `review_stacks_enabled` at all, so they evaluate purely from `provisioning_behavior` and the PR's labels — regardless of whether review stacks are enabled.

Attacker path: an unprivileged GitHub user opens (or already has) a fork PR against a repository whose operator previously configured `provisioning_behavior = allow_with_label` (or `prevent_with_label`) and later flips `review_stacks_enabled` to `false` believing this disables the feature entirely (via the settings form at [2](#0-1) , persisted through `RepositoriesController#update` / `update_params` at [3](#0-2) ). The attacker simply labels their own PR (for `allow_with_label`) or leaves it unlabeled (for `prevent_with_label`, the default case requiring zero attacker action) and opens/reopens a PR. GitHub's `pull_request` webhook fires `OpenedHandler#process`, which calls `provision?` — true — and then `ReviewStackAdapter#find_or_create!` creates the stack and calls `Shipit::ReviewStackProvisioningQueue.add(stack)`: [4](#0-3) 

This queue entry drives execution of the repository's `shipit.yml` (build/deploy commands) on the deploy host via `Command`/`PTY.spawn`, exactly the unauthorized code execution scoped as Critical impact.

None of the existing guards stop this: `respond_to_pull_request_opened?` only checks `params.action == "opened" && provision?` — it does not independently check `review_stacks_enabled` [5](#0-4) . Webhook signature verification, `ExplicitParameters` schema validation, and `Repository` model validations are all satisfied by a normal, legitimately-signed webhook from the attacker's own repository — they don't validate this business-logic invariant. This is not a signature/auth bypass; it's a broken authorization-toggle invariant reachable by any unprivileged PR author on a repo with this (common) configuration history.

The same precedence bug also exists in the sibling `ReopenedHandler#unarchive?` [6](#0-5) , compounding the issue (reopening a PR after disabling review stacks still unarchives/re-provisions). `LabeledHandler`/`UnlabeledHandler` are unaffected because their `respond_to_label_change?` ANDs `review_stacks_enabled` as a separate top-level term outside the archive/unarchive logic [7](#0-6) .

### Impact Explanation
Once `review_stacks_enabled` is toggled off by the operator (e.g., for cost or security reasons) but `provisioning_behavior` remains `allow_with_label` or `prevent_with_label` from prior configuration, any unprivileged user who can open a PR against that repository (including from a fork, if the repo accepts PRs) can still trigger creation and provisioning of a `ReviewStack`, causing the repository's `shipit.yml` to execute on the Shipit deploy host. This is repeatable per PR/repository and applies to any repository sharing this configuration pattern — a realistic and likely persistent state since disabling the checkbox is the operator's only expressed intent and they have no reason to also reset `provisioning_behavior`. This matches the Critical impact category: RCE on the deploy host via `Command`/`PTY.spawn`-driven provisioning, executed against the operator's explicit intent.

### Likelihood Explanation
Preconditions: a repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` and later have `review_stacks_enabled` set to `false`. This is a very plausible real-world sequence: operators often disable review stacks without downgrading the behavior selector back to a "safe" state, since the UI presents them as independent fields [8](#0-7) . No attacker secrets, sessions, or privileges are needed — only the ability to open a PR (and, for `allow_with_label`, apply a label to their own PR, which any PR author can do on their own PR in many repo configurations) or, for `prevent_with_label`, do nothing at all. This makes the bug trivially and repeatedly exploitable once the precondition configuration exists.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does NOT create stacks when review_stacks_enabled is false even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  # Binding under test: repository.review_stacks_enabled == false  =>  provision? == false
  assert_equal false, repository.review_stacks_enabled
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does NOT create stacks when review_stacks_enabled is false with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_equal false, repository.review_stacks_enabled
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both tests currently FAIL (stack is created and enqueued) against the vulnerable code, demonstrating that `review_stacks_enabled = false` does not stop provisioning for `allow_with_label`/`prevent_with_label`.
