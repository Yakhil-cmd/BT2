### Title
Webhook signature verified against `repository.owner.login`, but downstream handlers act on the unverified `repository.full_name` field, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . But every webhook `Handler` (e.g. `PushHandler`) determines which tracked `Stack`/`Repository` to act on using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) , consumed by `PushHandler#process` to enqueue a sync against arbitrary stacks [4](#0-3) .

### Finding Description
Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own GitHub App and its own `webhook_secret`, selected at verification time via `Shipit.github(organization: repository_owner)` [1](#0-0) , docs confirm this per-organization secret model [5](#0-4) .

The binding the engine relies on is: *the organization whose secret signed this payload* == *the repository the payload will cause writes to*. This equality is never enforced. `repository_owner` is read from `repository.owner.login` (or `organization.login`), while every handler's `stacks`/`repository_name` helper reads `repository.full_name` — an entirely separate key of the same attacker-controlled JSON body [3](#0-2) .

An attacker who legitimately owns a GitHub organization/App that is also connected to this same multi-tenant Shipit instance (a normal, unprivileged relationship with respect to the victim organization — they only know their *own* webhook secret) can craft a raw POST body where:
- `repository.owner.login` = `"attacker-org"` (so `Shipit.github(organization: "attacker-org")` is selected and the HMAC computed with the attacker's own known secret validates), and
- `repository.full_name` = `"victim-org/victim-repo"` (any repository/stack actually tracked by this Shipit instance).

`verify_signature` passes because the signature is valid for the raw body under the attacker's own secret — the controller never checks that `repository.owner.login` matches `repository.full_name`'s owner. `PushHandler` then resolves `stacks` for `victim-org/victim-repo` and enqueues `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` SHA [4](#0-3) , and other handlers sharing the same `Handler#repository_name`/`#stacks` logic (status, check_suite, pull_request, membership) are equally reachable for any tracked repository regardless of which org's secret actually authenticated the request.

### Impact Explanation
This breaks the trust boundary between tenants of a shared Shipit deployment: an attacker with no access to the victim organization or its GitHub App can forge webhook events attributed to any repository tracked by the instance, using only credentials from their own, unrelated organization. This can force syncs and inject forged commit/check-suite state for the victim's stacks, undermining the deploy-safety checks (CI status, checks) that gate deploys — i.e., an unauthorized effect on another organization's stack, crossing the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Requires a specific precondition: the target Shipit instance must be configured with multiple GitHub organizations (per `docs/setup.md`'s "Using Multiple Github Applications" section) and the attacker must control one of them. In a single-organization deployment this does not apply, since only one webhook secret exists and `repository_owner` and `repository.full_name` always belong to the same org tree. Likelihood is therefore conditional on this specific multi-tenant configuration.

### Recommendation
In `WebhooksController#verify_signature`, after resolving `repository_owner`, verify that the resolved organization actually matches the owner implied by `repository.full_name` (and `organization.login` when present) before dispatching to handlers, or have `Handler#repository_name`/`#stacks` re-derive the repository strictly from the same `repository_owner` value used for signature selection, rejecting payloads where the two disagree.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` (attacker-controlled, webhook secret known to attacker) and `victim-org` (has a stack tracked by Shipit), per the multi-org config in `docs/setup.md`.
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s own webhook secret over the raw JSON body.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` selects `Shipit.github(organization: "attacker-org")` and validates successfully [1](#0-0) .
5. `PushHandler` resolves `stacks` via `repository.full_name` = `"victim-org/victim-repo"` [3](#0-2)  and enqueues a sync job against the victim's stack with the attacker's chosen `after` SHA [4](#0-3) , despite the signature only proving authorship by `attacker-org`, not `victim-org`.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
