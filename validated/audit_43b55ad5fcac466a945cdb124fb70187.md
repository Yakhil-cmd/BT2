## Finding

### Title
`DenyReserveTransferToRelayChain` barrier bypass via nested/embedded XCM instructions not covered by non-recursive deny check - (File: system-parachains/encointer/src/xcm_config.rs)

### Summary
Encointer's `Barrier` wraps `DenyReserveTransferToRelayChain` directly, without the `DenyRecursively` wrapper that other system chains in this same repository (bridge-hub-polkadot, bulletin-polkadot) use for the identical deny rule. `DenyReserveTransferToRelayChain`'s `should_execute` only inspects the top-level instruction slice passed to the barrier and does not recurse into nested `Xcm` programs embedded inside instructions such as `DepositReserveAsset { xcm, .. }`, `InitiateReserveWithdraw { xcm, .. }`, `SetAppendix(Xcm<..>)`, or `SetErrorHandler(Xcm<..>)`, so a program that places a Parent-bound reserve-transfer instruction inside one of these nested fields is not matched by the flat pattern scan and is admitted by the barrier.

### Finding Description
The barrier is configured at [1](#0-0)  as `TrailingSetTopicAsId<DenyThenTry<DenyReserveTransferToRelayChain, (...)>>`, using the plain (non-recursive) `DenyReserveTransferToRelayChain` filter imported from `xcm_builder` at [2](#0-1) .

`SendXcmOrigin`/`ExecuteXcmOrigin` in Encointer's `pallet_xcm::Config` are `EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>`, meaning any signed account can call `pallet_xcm::execute` (or `send`) with an arbitrary XCM program, as declared at [3](#0-2) .

`DenyReserveTransferToRelayChain::should_execute` (upstream `xcm-builder`, not vendored in this repo) performs a `message.iter().any(...)` scan of the top-level `&mut [Instruction<RuntimeCall>]` slice, matching only `InitiateReserveWithdraw { reserve: (1, Here), .. }`, `DepositReserveAsset { dest: (1, Here), .. }`, or `TransferReserveAsset { dest: (1, Here), .. }` occurring directly as a top-level instruction. It does not descend into the `xcm: Xcm<Call>` payload embedded inside `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset`, nor into `SetAppendix`/`SetErrorHandler` bodies, which are executed by the same local XCM VM run (appendix/error-handler instructions splice into the same execution without a fresh `Barrier::should_execute` call). An attacker can therefore submit a top-level program whose outer instructions are innocuous (e.g. `WithdrawAsset`, `SetAppendix(...)`, `ClearOrigin`) while embedding `DepositReserveAsset{ dest: Parent, .. }` or `InitiateReserveWithdraw{ reserve: Parent, .. }` inside the appendix/error-handler/nested-xcm field. The outer `message.iter()` scan never observes the inner instruction, so `DenyReserveTransferToRelayChain` returns `Ok(())` and the subsequent allow-set (`TakeWeightCredit`, `WithComputedOrigin<AllowTopLevelPaidExecutionFrom<Everything>, ...>`) lets the whole program execute, ultimately performing the reserve-transfer-to-relay effect the deny rule was meant to block.

This is precisely the gap that `DenyRecursively<DenyReserveTransferToRelayChain>` closes elsewhere in this same repository — it is applied on bridge-hub-polkadot [4](#0-3)  and bulletin-polkadot [5](#0-4) , but the same hardening is absent from Encointer's barrier [6](#0-5)  (and likewise from asset-hub-kusama/polkadot, collectives-polkadot, coretime-kusama/polkadot, and people-kusama/polkadot, which all still use the plain, non-recursive form).

### Impact Explanation
A normal signed local user on Encointer can construct and submit (via `pallet_xcm::execute`) an XCM program that evades `DenyReserveTransferToRelayChain` and still executes a reserve-transfer/withdraw of KSM targeting the Relay Chain, bypassing the intended asset-routing restriction that this deny rule is meant to enforce on system parachains. This breaks the invariant that "filters, barriers ... must not be bypassable by normal users" and undermines the intended accounting/routing boundary between Encointer and the Relay Chain.

### Likelihood Explanation
Preconditions are trivial: any signed account on Encointer holding KSM can call `PolkadotXcm::execute` with a self-crafted program (no privilege needed), since `ExecuteXcmOrigin = EnsureXcmOrigin<_, LocalSignedOriginToLocation>` permits any signed origin. Constructing a program using `SetAppendix`/nested `xcm` fields is standard XCM syntax available to any XCM-composing user; no race conditions or external chain cooperation are required beyond normal remote execution semantics.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` (and any equivalent deny filters) with `DenyRecursively` in Encointer's `Barrier` definition, matching the pattern already used in bridge-hub-polkadot/bulletin-polkadot, so that nested `xcm` payloads inside `DepositReserveAsset`, `InitiateReserveWithdraw`, `TransferReserveAsset`, `SetAppendix`, and `SetErrorHandler` are also scanned for the denied pattern. Apply the same fix consistently to all other system-parachain configs in this repo that still use the non-recursive form (asset-hub-kusama, asset-hub-polkadot, collectives-polkadot, coretime-kusama, coretime-polkadot, people-kusama, people-polkadot).

### Proof of Concept
xcm-emulator integration test plan:
1. Fund a test account on Encointer with KSM.
2. Submit `PolkadotXcm::execute` with a top-level program: `[WithdrawAsset(ksm), SetAppendix(Xcm(vec![DepositReserveAsset{ assets: All, dest: Parent, xcm: Xcm(vec![]) }])), ClearOrigin]` (or equivalently embed the denied instruction inside the `xcm` field of an outer `DepositReserveAsset`/`InitiateReserveWithdraw` targeting a non-Parent `dest`).
3. Assert that execution succeeds (barrier does not reject with `ProcessMessageError::Unsupported`) and that KSM ends up withdrawn/forwarded toward the Relay Chain sovereign/UMP queue.
4. Compare against a direct-form program `[WithdrawAsset(ksm), DepositReserveAsset{ dest: Parent, .. }]`, which the current filter correctly rejects, demonstrating the inconsistency/bypass.
5. Repeat the same test against bridge-hub-polkadot (using `DenyRecursively`) and assert it is correctly blocked in both direct and nested forms, confirming the recursive wrapper is the effective fix.
