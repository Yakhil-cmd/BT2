### Title
Webhook signature verification selects the GitHub App/secret using an unauthenticated payload field decoupled from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login`, a field read straight out of the *unverified* JSON body. The event handlers that subsequently act on the same payload (e.g. locating the target `Repository`/`Stack`) key off a different field, `repository.full_name`. Because both fields are attacker-controlled and independently settable in the same unsigned POST body, an attacker can pick an organization with no `webhook_secret` configured for signature selection while pointing the actual repository/stack resolution at a different, secured organization's repository.

### Finding Description
The verification flow is: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')`, i.e. directly from the JSON payload of the request being verified, before the signature is confirmed valid [2](#0-1) .

`Shipit.github(organization: repository_owner)` is used to select the per-organization `GitHubApp` instance, and thus the `webhook_secret` used for HMAC comparison, per the multi-org configuration schema documented for `config/secrets.yml` [3](#0-2) [4](#0-3) .

Critically, `verify_webhook_signature` trivially returns `true` — bypassing signature checking entirely — whenever the selected organization has no `webhook_secret` configured: [5](#0-4) 

Since `webhook_secret` is documented/shown as optional and defaults to `nil` in every secrets example (`webhook_secret: # nil`) [6](#0-5) [7](#0-6) , it is realistic for at least one organization in a multi-org deployment to have no secret set.

Meanwhile, the actual repository/stack that a handler operates on is resolved from `repository.full_name`, a separate field in the same payload, via `Repository.from_github_repo_name` [8](#0-7) . The test suite confirms these are treated independently — one test freely rewrites only `repository.full_name` while leaving other repository fields (including `owner.login`) untouched to redirect processing to a different repo [9](#0-8) .

This is the equality the rules describe as an in-scope binding: **"an organization that authenticated" (`repository.owner.login`, used only to pick the verifying secret) ≠ "the repository that is written"** (`repository.full_name`, used to resolve and mutate the actual `Stack`/`Repository`/`Commit` records). An attacker fully controls both sides of this equality in one unsigned HTTP POST.

### Impact Explanation
An unprivileged attacker (no Shipit session, no GitHub credentials, no webhook secret) who knows that any one organization configured in the multi-org `secrets.yml` has a blank `webhook_secret` can craft a payload where `repository.owner.login` equals that unsecured organization while `repository.full_name` points at a completely different, secured organization's real repository/stack. This lets the attacker:
- Forge `push` events to enqueue `GithubSyncJob` with attacker-chosen `expected_head_sha` for a real stack it does not control.
- Forge `status` events to write arbitrary commit statuses on commits belonging to that stack (`StatusHandler`), which can be used to fake CI passing/checks required by the merge queue.
- Forge `check_suite`/`membership` events against the target org's data.

Because commit statuses can gate Shipit's merge queue and deploy safety checks, this can lead to an unauthorized merge/deploy being triggered against a properly secured GitHub organization — meeting the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires only:
1. A Shipit deployment using the documented multi-organization GitHub App configuration.
2. At least one configured organization with no `webhook_secret` (shown as the default/example value everywhere in the repo's own config templates).
3. Knowledge of that organization's name (often public/documented) and the target organization's real repository full name (public GitHub data).

No credentials, session, or network position beyond reaching the public `/webhooks` endpoint are needed.

### Recommendation
Do not let any field from the unauthenticated payload determine which secret verifies that same payload. Bind webhook verification to a value that is not attacker-controlled independent of the resource acted upon — e.g., verify against every configured organization's secret (or a single global secret) rather than selecting the secret via a payload field, and/or require that `repository.owner.login` and the owner segment of `repository.full_name` match before processing. Additionally, disallow (or loudly warn on) `webhook_secret: nil` in production configurations with multiple organizations, since a blank secret causes `verify_webhook_signature` to unconditionally return `true`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `unsecured-org` (no `webhook_secret`) and `secured-org` (a real target with an existing Shipit stack for `secured-org/real-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/real-repo"
  },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
No `X-Hub-Signature` header is required to match anything real, because `Shipit.github(organization: "unsecured-org")` resolves to a `GitHubApp` whose `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank) [5](#0-4) .
3. `WebhooksController#create` then dispatches the payload to the `push` handler, which resolves the target repository via `repository.full_name` = `secured-org/real-repo` [10](#0-9) , causing Shipit to act on `secured-org`'s real stack despite the signature check never validating against `secured-org`'s actual secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
