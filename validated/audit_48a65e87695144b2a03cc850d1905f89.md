### Title
Webhook signature verified against the org derived from an unauthenticated payload field, allowing a known-secret organization to forge events for a different tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC signature using `repository_owner`, which is read directly from the *unverified* JSON payload before the signature is checked, not from any authenticated context. [1](#0-0) [2](#0-1)  In a Shipit installation configured with multiple GitHub Apps (one secret per organization, as documented), the org whose secret authenticates the request and the repository that the payload's other fields (`repository.full_name`, commit `sha`, `ref`/`after`) act upon are two independent, attacker-controlled values that are never bound together.

### Finding Description
`Shipit.github(organization: repository_owner)` looks up the per-organization `webhook_secret` from `secrets.github` keyed by the lowercased organization name taken from the payload. [3](#0-2)  The signature is then verified with `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`, i.e., over the entire raw body, using whichever secret corresponds to `repository_owner`. [1](#0-0) 

However, the handlers that actually process the payload never re-check that `repository_owner` matches the owner of the repository being acted on. `Handler#stacks` resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`. [4](#0-3)  The `PushHandler` and `StatusHandler` operate on `repository.full_name`-scoped stacks or on the commit `sha` globally, entirely independent of `repository_owner`. [5](#0-4) [6](#0-5) 

This breaks the intended binding:
`organization that authenticated the request == organization owning the repository the payload mutates`

Before the attack, an attacker who has legitimately received real webhook deliveries (or otherwise knows the `webhook_secret`) for **their own** configured GitHub organization/App can compute a valid HMAC-SHA1 signature over any payload body using that known secret. After the attack, that attacker submits a payload where `repository.owner.login` (or `organization.login`) is set to their own org (so `Shipit.github(organization: repository_owner)` picks the secret they know and the signature check passes), while `repository.full_name` is set to a *different* organization/repository tracked by the same Shipit instance. Because `stacks` and `Commit.where(sha: ...)` never consult `repository_owner`, the forged push/status event is applied to the victim repository's stack — e.g., injecting a fabricated commit `state`/`status` via `StatusHandler` for a SHA belonging to another org's tracked repository, or triggering `stack.sync_github(expected_head_sha: ...)` for a stack whose repository belongs to an organization the attacker does not control.

### Impact Explanation
This allows an entity that only controls one organization's webhook secret in a multi-org Shipit deployment to inject forged CI/commit status data or trigger sync/merge-queue side effects (`schedule_merges`, `deployable_status`) for a completely different, unrelated organization's repository/stack that they have no legitimate write access to — an authorization boundary crossing between "organization that authenticated the webhook" and "repository/stack the webhook payload mutates." Forged `deployable_status`/commit status updates can influence Shipit's merge-queue automation (`stack.schedule_merges`) and downstream deploy decisions for a repository outside the attacker's control.

### Likelihood Explanation
Requires the Shipit instance to be configured for multiple GitHub organizations (the documented multi-org config in `docs/setup.md`) and requires the attacker to possess a valid `webhook_secret` for at least one configured organization (a realistic scenario if they administer their own GitHub App/org that is also connected to the same Shipit instance, e.g. a shared internal Shipit deployment serving several orgs/teams). No other Shipit credentials, sessions, or repository write access are needed to exploit the cross-repository confusion once that one secret is known.

### Recommendation
After signature verification, re-validate that the resolved organization actually matches the owner of `repository.full_name` (or `organization.login`) used elsewhere in the payload before dispatching to handlers, or scope the per-organization `GitHubApp`/secret lookup to also assert `repository.full_name.split('/').first.casecmp(repository_owner).zero?`, rejecting mismatches with `422`.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` (per `docs/setup.md`'s multi-app section).
2. Attacker administers a GitHub App installed on `org-a` and thus knows/can compute a valid `X-Hub-Signature` for `org-a`'s secret (e.g., by triggering a legitimate webhook delivery and reusing the signing capability, or simply owning that secret).
3. Attacker POSTs to `/webhooks` a `status` event body:
```json
{
  "sha": "<victim-commit-sha-in-org-b-repo>",
  "state": "success",
  "context": "ci/attacker",
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"}
}
```
signed with `org-a`'s webhook secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-a')` (from `repository_owner`), and the signature validates successfully since it was computed with `org-a`'s known secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, applying the forged status to the commit belonging to `org-b/victim-repo`, regardless of the fact that the signature was for `org-a`. [6](#0-5)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
