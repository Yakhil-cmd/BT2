### Title
Instant, unrestricted vote commission update for basis-points commission (`UpdateCommissionBps`) removes the anti-front-running delay that legacy commission updates rely on - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The Bima report describes a "slippage protection" bypass: a party who controls a fee/commission parameter (`boostDelegate`) can change conditions immediately before a reward-claiming/consuming transaction executes, so a check that looked safe when the user built their transaction (`fee <= maxFeePct`) is still nominally satisfied at execution time, but the economics have shifted in the fee-taker's favor, causing the honest party to receive less value while still paying the fee. The root cause is the absence of a timing/delay guard on a value that directly determines reward split, combined with a check that only bounds the *rate* and not the *actual value delivered*.

Agave has an almost identical bug class already recognized and explicitly mitigated for legacy vote commission: `update_commission()` in `programs/vote/src/vote_state/mod.rs` enforces that a commission *increase* can only happen in the first half of an epoch (`is_commission_update_allowed`), and the epoch-rewards calculation path additionally uses a snapshot of vote-account commission from a full epoch earlier (`get_cached_vote_accounts` / `CachedVoteAccounts`) specifically "to prevent last minute commission rugs" [1](#0-0) . This is the direct analog of the recommended fix in the Bima report (avoid fees that can be set adversarially right before value is realized).

However, the newer basis-points commission instruction (`VoteInstruction::UpdateCommissionBps`, SIMD-0291) explicitly removes this protection: the code comment states "No commission update rule, per SIMD-0249 and SIMD-0291. Updates are always allowed regardless of epoch position" [2](#0-1) , and the handler for `UpdateCommissionBps` performs no timing check before mutating `inflation_rewards_commission_bps` / `block_revenue_commission_bps` [3](#0-2) .

### Finding Description
`update_commission()` (legacy, percentage-based commission) enforces `is_commission_update_allowed(clock.slot, epoch_schedule)` whenever the new commission is an *increase*, preventing a validator from raising its cut right before a rewards distribution epoch boundary is crossed [4](#0-3) . Additionally, when `delay_commission_updates` is active, the reward-calculation code in `redeem_delegation_rewards()` deliberately reads the commission from a **snapshot taken a full epoch earlier** (`snapshot_epoch_vote_accounts`) instead of the current, potentially just-changed value [5](#0-4) . The `CachedVoteAccounts` doc comment states this exists specifically "to prevent last minute commission rugs" [6](#0-5) .

By contrast, `update_commission_bps()`, which sets `inflation_rewards_commission_bps` and `block_revenue_commission_bps` under SIMD-0291, has neither restriction: it only requires the authorized withdrawer's signature and immediately writes the new commission with no epoch-timing check [3](#0-2) . This is invoked directly from `VoteInstruction::UpdateCommissionBps` in the vote processor with no additional guard beyond the feature-set gate [7](#0-6) .

This mirrors the Bima bug class precisely: stakers delegate to a vote account expecting a certain commission split on their inflation/block-revenue rewards; the vote account's authorized withdrawer (the analog of `boostDelegate`) can raise `block_revenue_commission_bps`/`inflation_rewards_commission_bps` to any value up to 100% at any slot, including immediately before an epoch's rewards are calculated/redeemed, with no equivalent of the legacy `is_commission_update_allowed` gate and (for the `commission_rate_in_basis_points` code path, if `delay_commission_updates` were ever disabled or bypassed for the bps path) no guaranteed one-epoch-old snapshot read.

### Impact Explanation
If a validator's commission-bps update genuinely takes effect for rewards computed/redeemed in the same or an already-in-progress epoch (rather than being delayed a full epoch as the legacy path guarantees), stakers delegated to that vote account would receive misattributed/reduced rewards while the validator's commission account receives a larger, unexpected share — a direct case of "misattributed or duplicated rewards" via lamports being redirected from stakers' share to the commission collector without the staker's consent or ability to react, exactly analogous to the boostDelegate stealing the fee difference from the user in the original report.

### Likelihood Explanation
This is reachable by any validator operator (an unprivileged action relative to delegators/stakers, since only the authorized withdrawer signature is required, no special network role) simply by issuing `UpdateCommissionBps` right before their vote account's rewards are calculated for a given epoch. Whether it is currently *exploitable* depends entirely on whether `delay_commission_updates`'s epoch-snapshot mechanism in `redeem_delegation_rewards()` is unconditionally applied to the bps-based fields as well as the legacy field — from the code reviewed, the snapshot-read branch (`if commission_rate_in_basis_points { vote_state_for_commission.inflation_rewards_commission() }`) does appear inside the `delay_commission_updates` guard, suggesting inflation-rewards-bps commission is in fact protected the same way. I was **not able to fully verify** whether `block_revenue_commission_bps` (used for SIMD-0123 block-revenue-sharing rewards, computed in `calculate_block_reward()`) is subject to any equivalent one-epoch-delay/snapshot mechanism — `calculate_block_reward()` only reads `pending_delegator_rewards()` from the live `distribution_epoch_vote_accounts` and does not appear to reference a commission value or a delayed snapshot at all in the code I examined [8](#0-7) , and I could not locate the code path where `block_revenue_commission_bps` is actually deducted before/at distribution within the reviewed files.

### Recommendation
Confirm and, if missing, add an epoch-delay guard (mirroring `is_commission_update_allowed` / the `CachedVoteAccounts` snapshot mechanism) to whichever code path applies `block_revenue_commission_bps` at reward-distribution time, so that any commission-bps increase — for both `InflationRewards` and `BlockRevenue` kinds — cannot affect rewards already earned or in the current distribution cycle, closing the same front-running/slippage window described in the Bima report.

### Proof of Concept
Not independently reproducible from static code review alone; would require an on-chain/localnet test that (1) delegates stake to a vote account, (2) accrues pending block-revenue rewards, (3) calls `UpdateCommissionBps` with `CommissionKind::BlockRevenue` set to a high value immediately before the reward-distribution slot, and (4) observes whether the increased commission is applied to already-pending rewards rather than being delayed a full epoch as the legacy commission path guarantees. This step was not completed due to reaching the tool-call limit before locating the exact code that consumes `block_revenue_commission_bps`.

        };

pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
