## Finding

### Title
Webhook signature verified against `repository.owner.login` but the acted-upon repository is selected via `repository.full_name`, allowing cross-organization forged webhook events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to use for HMAC verification based on `params.dig('repository', 'owner', 'login')`, extracted from the still-unauthenticated request body [1](#0-0) [2](#0-1) . Once the signature check passes, the payload is dispatched unmodified to event handlers, which independently determine which `Repository`/`Stack` to act on using `payload.dig('repository', 'full_name')` [3](#0-2) . These two fields are never checked for consistency, so the organization whose secret authenticated the request can differ from the repository that is actually written to — the exact "org authenticated vs. repo written" binding break called out for this bug class.

### Finding Description
`verify_signature` computes the app/secret to check the signature against purely from `repository_owner`, which is read straight out of the JSON body before any authentication has occurred: 
`Shipit.github(organization: repository_owner)` → `github_app.verify_webhook_signature(...)` [1](#0-0) .

Once this passes, `WebhooksController#create` hands the raw, unmodified `params` hash to every registered handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

Every handler's base class resolves the target repository/stacks using a *different* field of the same payload — `repository.full_name` — via `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and `Repository.from_github_repo_name` simply splits `owner/name` and does a DB lookup, with no relationship to the org used for signature verification [5](#0-4) .

`PushHandler#process`, for example, uses that repository lookup to find real `Stack` rows and calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-controlled `after` value [6](#0-5) , which enqueues `GithubSyncJob` for that stack [7](#0-6) . Note that the sync job itself fetches commits using the *stack's real* repository owner (`stack.github_api` → `Shipit.github(organization: repository.owner)` from the DB record, not the payload) [8](#0-7) , so the attacker cannot inject fabricated commit content, but they *can* force an out-of-band sync/re-check of any tracked stack belonging to any other GitHub organization at a time of their choosing, using only their own (unrelated) org's webhook secret.

**Binding broken:** organization that authenticated the request (`repository.owner.login`, checked against that org's `webhook_secret`) ≠ repository the handler actually writes to (`repository.full_name`). Before the attacker's forged request, these two are implicitly assumed equal by the code's design (a webhook is only supposed to arrive with a signature matching the repo's own org); after the forged request, they diverge and the equality silently fails to be checked.

### Impact Explanation
An operator of any GitHub organization that has installed the Shipit GitHub App (i.e., any tenant onboarded to a multi-org Shipit deployment, as explicitly supported and documented in `docs/setup.md` "Using Multiple Github Applications" [9](#0-8) ) knows their own org's `webhook_secret` because they configured it when creating their App. That "unprivileged" party (with respect to any *other* tenant's repositories) can sign an arbitrary payload with their own secret while setting `repository.full_name` to point at a completely unrelated, victim organization's tracked stack. This lets them:
- Force `GithubSyncJob` to run against a victim stack at an attacker-chosen time with an attacker-chosen `expected_head_sha`, and
- If `continuous_deployment` is enabled on that victim stack, potentially trigger premature/unauthorized deploy scheduling once new legitimate commits are (or become) reachable, since sync completion feeds into the continuous-delivery pipeline.

This is a cross-tenant authorization bypass: actions that should only be triggerable by GitHub on behalf of the specific repository's own organization can instead be triggered by any other onboarded organization. This falls under the "unauthorized deploy" / cross-repository-write class of Critical impact.

### Likelihood Explanation
Requires only that the Shipit instance host more than one GitHub organization/App configuration (a documented, supported configuration) and that the attacker controls one of those tenant orgs (a low bar — they only need to be a legitimate customer/tenant of the same Shipit instance, not an admin of the victim). No GitHub write access to the victim repo, no Shipit account, and no secret belonging to the victim are required.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after determining `repository_owner` for signature verification, also assert that `params.dig('repository','full_name')` (and `params.dig('organization','login')` for org-scoped events) actually belongs to that same verified organization before dispatching to handlers — e.g., compare the case-insensitive owner segment of `full_name` to `repository_owner` and reject (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same verified organization identity rather than trusting `full_name` independently.

### Proof of Concept
1. Attacker owns GitHub org `AttackerOrg`, which has the Shipit GitHub App installed with a `webhook_secret` the attacker chose/knows (multi-org config as in `docs/setup.md`).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha-attacker-wants-synced>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(AttackerOrg_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "AttackerOrg")` and successfully verifies the signature against the attacker's own secret [1](#0-0) .
5. `PushHandler` resolves `Repository.from_github_repo_name("VictimOrg/victim-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<sha-attacker-wants-synced>")` for the real victim stack [6](#0-5) , enqueuing `GithubSyncJob` for a stack the attacker has no relationship to.
