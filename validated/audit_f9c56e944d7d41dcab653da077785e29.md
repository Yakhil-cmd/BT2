### Title
Webhook signature verification is bound to `repository.owner.login`, but the handled write target is bound to `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the incoming signature against using the organization derived from the payload, while every event `Handler` acts on a completely different, unauthenticated field of the same payload to decide which repository/stack to mutate. When an organization is configured without a `webhook_secret` (an explicitly supported configuration), the "authenticated organization" and the "repository actually written to" are never bound together, letting an unprivileged attacker target a stack belonging to an unrelated org/repository.

### Finding Description
`WebhooksController#verify_signature` resolves the org to authenticate against solely from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit::GithubApp#verify_webhook_signature` short-circuits to `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

`webhook_secret` is documented and tested as an optional per-organization setting (the multi-app fixture even ships with it explicitly blank): [4](#0-3) [5](#0-4) 

Once the request passes `verify_signature` (trivially, for the secret-less org), every `Handler` resolves the *actual* repository/stack to act on from an entirely different field, `repository.full_name`, which is never checked against the organization used for authentication: [6](#0-5) 

`PushHandler#process` then uses that unauthenticated `repository_name` lookup to enqueue a sync with an attacker-controlled `after` sha: [7](#0-6) 

This is exactly the "organization that authenticated versus the repository that is written" binding break: `repository.owner.login` (used to pick/skip the signature secret) ≠ `repository.full_name` (used to pick the Repository/Stack that gets mutated). There is no code path that verifies these two values are the same organization.

### Impact Explanation
An attacker with no Shipit credentials, no webhook secret, and no GitHub access can craft a raw JSON POST to `/webhooks` claiming `repository.owner.login` = an org that has no `webhook_secret` configured, while setting `repository.full_name` to an arbitrary tracked repository belonging to a *different* organization. `verify_signature` passes unconditionally (`return true unless webhook_secret`), and the `PushHandler` will enqueue `GithubSyncJob` for that unrelated repository's stacks with an attacker-chosen `expected_head_sha`, injecting an arbitrary commit as the expected branch head for a stack the attacker has no authorization over. Depending on continuous-deployment settings this can drive an unauthorized deploy/rollback of attacker-chosen commits on a stack outside the attacker's own organization - meeting the Critical "unauthorized deploy" bar.

### Likelihood Explanation
Requires only that at least one configured GitHub organization in `Shipit.github` be set up without a `webhook_secret` — an explicitly supported and documented configuration path in this engine (not a deployment error), so the analog does not depend on the host misconfiguring or failing to mount the engine as documented.

### Recommendation
Bind signature verification and payload processing to the same field: derive the org used to select the webhook secret from the same repository identity (`full_name`'s owner) that handlers use to pick the target Repository/Stack, and reject (rather than allow) events for organizations where `webhook_secret` is unset unless that is a deliberate, closely-scoped opt-out. Additionally, `Handler#repository_name`/`stacks` should cross-check that the resolved `Repository`'s owner matches the organization that passed signature verification before dispatching any mutating operation.

### Proof of Concept
1. Configure Shipit with two orgs per `docs/setup.md`'s "Using Multiple Github Applications", where `OrgA` has `webhook_secret:` left blank (a supported configuration, mirrored in `test/dummy/config/secrets_double_github_app.yml`).
2. As an unprivileged external attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` computes `repository_owner` = `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, and since `webhook_secret` is nil, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `repository_name` from `full_name` = `"OrgB/target-repo"`, finds its `Stack`s, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` for a stack the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
