Based on the investigation, the libevent CVE describes unbounded evbuffer growth in a WebSocket server (`ws.c`) due to missing message-size enforcement on fragmented frames. Searching the Polkadot SDK codebase for an analogous pattern shows the opposite: Substrate's WebSocket handling explicitly enforces bounds. The test WebSocket server sets both `set_max_frame_size` and `set_max_message_size` on the soketto builder before accepting frames [1](#0-0) , and the `Config::max_frame_size` field is explicitly documented as existing "to prevent malicious clients from sending huge frames that would occupy a lot of memory" [2](#0-1) . Similarly, the request-response networking codec enforces `max_request_size`/`max_response_size` checks before allocating buffers for length-prefixed payloads [3](#0-2) , and the JSON-RPC WS client is configured with explicit request/response/buffer limits [4](#0-3) .

More importantly, this class of finding does not fit the required scope: the report method explicitly requires a real runtime entry point — a signed extrinsic, an enabled contract call, a permitted XCM execute/send/transfer, or a public proof submission with established fees/validation — and explicitly excludes "unbounded-loop or memory/storage-growth scenarios" and "oversized-input/flooding/generic resource-exhaustion claims." A WebSocket/network-layer buffer-accumulation issue is a node/transport-level resource-exhaustion concern, not a FRAME/XCM/contracts state-transition bug reachable via a runtime-validated user input, so it cannot be mapped into an eligible Polkadot SDK analog under the stated criteria.
