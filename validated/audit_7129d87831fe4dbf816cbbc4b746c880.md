### Title
CCMenu API endpoint bypasses stack-scoped `ApiClient` authorization, allowing a stack-scoped token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and this scoping is meant to be enforced by `Api::BaseController#stack`, which resolves the requested stack only from the set of stacks the client is authorized for. `Api::CCMenuController` overrides `#stack` with an unscoped lookup, so a token that is authorized for only one stack can be used to fetch CCMenu build-status XML for *any* stack in the installation.

### Finding Description
`Api::BaseController` defines the intended binding between an `ApiClient`'s authorized stack and the stack a request may touch: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is stack-scoped, and `stack` resolves the request's `:stack_id` param only within that restricted set (`from_param!` raises if it's not in scope).

Permission enforcement itself is generic and does not carry any stack context — `ApiClient#check_permissions!` only checks that the permission string (e.g. `read:stack`) is present, with no awareness of *which* stack is being requested: [2](#0-1) 

So the only place that ties "the stack a token authorizes" to "the stack a token touches" is `Api::BaseController#stack`/`#stacks`. `Api::CCMenuController` re-defines `stack` and bypasses that binding entirely: [3](#0-2) 

`Stack.from_param!(params[:stack_id])` resolves against **all** stacks, not `current_api_client`'s scoped set. `require_permission :read, :stack` only guarantees the token carries the `read:stack` permission string; it does not check that `params[:stack_id]` matches `current_api_client.stack_id`.

**Binding broken (equality that should hold but doesn't):**
`stack the ApiClient token authorizes (current_api_client.stack_id)` == `stack the CCMenuController actually reads (params[:stack_id])`

Before the request: an `ApiClient` such as the `here_come_the_walrus` fixture is created with `stack: shipit` and `permissions: [read:stack]`, intended to only ever see the `shipit` stack (confirmed by `Api::StacksControllerTest#index` test: "an api client scoped to a stack will only see that one stack").

After the request: because `CCMenuController#stack` ignores `stacks` (the scoped relation) and calls `Stack.from_param!` directly, that same token can be presented with a different `stack_id` param and will successfully render CCMenu status for a stack outside its authorized scope.

### Impact Explanation
This is an escalation of a legitimately-issued, narrowly-scoped API credential beyond its intended authorization boundary — an unauthorized read of another stack's state (build status, last build label/time, `webUrl`, lock status) via a token that was only ever meant to see one stack. This matches the "High - escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state" impact class in spirit: a credential holder gains read access to build/deploy status of stacks they were never granted visibility into. It does not leak secrets or allow writes, so it sits at the lower end of High severity, but it is a genuine authorization-boundary bypass reachable by anyone already holding *any* valid, narrowly-scoped API token (e.g. a stack's public CCMenu URL/token handed to a third-party CI dashboard integration, as created by `CCMenuUrlController`).

### Likelihood Explanation
Any consumer of a stack-scoped `ApiClient` token (which are explicitly designed to be handed out to less-trusted integrations, e.g. CCMenu build monitors) can trivially exploit this by changing the `stack_id` route/query parameter in their request — no additional privilege, secret, or session is required beyond possessing the token they were legitimately given for one stack.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited scoped `stacks` relation) so that stack-scoped tokens can only resolve stacks within `current_api_client`'s authorized scope, consistent with `Api::BaseController#stack`.

### Proof of Concept
1. Admin creates (or the app auto-creates via `CCMenuUrlController#client`) an `ApiClient` scoped to `stack_id: A`, permissions `["read:stack"]`, and hands its `authentication_token` to a third party for stack A's CI dashboard.
2. That third party (or anyone who obtains the token) issues:
   `GET /api/stacks/B/ccmenu.xml?token=<token-scoped-to-A>`
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully (`ApiClient.authenticate(params[:token])`) — this only checks token validity, not stack scope.
4. `require_permission :read, :stack` passes because the token has the `read:stack` permission string, with no stack context checked (`ApiClient#check_permissions!`).
5. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks`/scoping), returning stack B even though the token is scoped only to stack A.
6. The response renders stack B's build status/lock state/last build info, which the token holder was never authorized to see. [1](#0-0) [3](#0-2) [2](#0-1)
