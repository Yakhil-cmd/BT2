### Title
Null-dereference crash in private payment chain validation via duplicate chain elements - (File: wallet.js)

### Summary
`handlePrivatePaymentChains()` tracks per-chain validation state in a local `assocValidatedByKey` map keyed by `unit-payload_hash-output_index`. Once all keys resolve to `true`, `checkIfAllValidated()` sets `assocValidatedByKey = null` as a duplicate-call guard. If an attacker-controlled private-payment counterparty submits a `private_payment_chains` message containing two chains that share the same head unit/payload-hash/output_index, two `eventBus.once(key, …)` listeners are registered on the same global event key. When the underlying validation completes and the event is emitted once, both `once` listeners fire in the same tick; the first completes processing and nulls `assocValidatedByKey`, and the second then executes `assocValidatedByKey[key] = true` against `null`, throwing an uncaught `TypeError`.

### Finding Description
In `wallet.js`, `handlePrivatePaymentChains` iterates `arrChains` and, for light clients, defers validation via `network.handleOnlinePrivatePayment(..., { ifQueued: function(){ eventBus.once(key, ...) } })`. [1](#0-0) 
The completion handler `checkIfAllValidated` nulls the shared map after all keys resolve, explicitly as a "duplicate call" guard, and the `eventBus.once` callback writes into that same map without checking it is still non-null before/after re-entry: [2](#0-1) 
The structural validation of `body.chains` only checks shape (non-empty arrays/objects/strings) and never rejects duplicate chain-head keys (same `unit` + `payload_hash` + `output_index`) within a single message: [3](#0-2) 
Because `key` is derived purely from `objHeadPrivateElement.unit`, its payload hash, and `output_index`, two duplicate chain entries in one request produce the identical `key` string and each registers its own `eventBus.once(key, …)` listener on the process-global `eventBus`. Node's `EventEmitter` invokes all listeners registered for an event (each `once` listener independently, then removes it) synchronously in the same emit call. The first invocation runs `checkIfAllValidated()`, which — if this was the last outstanding key — sets `assocValidatedByKey = null`. The second (duplicate) listener callback for the same tick then executes `assocValidatedByKey[key] = true;` on a `null` object, throwing an unhandled `TypeError`. This is conceptually analogous to the reported Linux kernel bug class: an object is prematurely freed/invalidated while another queued consumer of that object is still expected to run against it.

### Impact Explanation
An unhandled exception thrown from an `eventBus` listener callback in Node.js propagates as an uncaught exception, which — absent a global handler around this specific code path — crashes the wallet/light-client process handling private payments. This denies the wallet's ability to process further private payments, pairing messages, and other device communications until restarted, and can be triggered repeatedly by any paired device/private-payment counterparty simply by sending crafted duplicate chain entries. This is a concrete, reachable node/wallet availability impact from an unprivileged private-payment counterparty, not a mere resource-exhaustion or peer-only network issue.

### Likelihood Explanation
The trigger requires only that a paired device or private-payment counterparty (already an addressable party in the private-payment protocol) send one `private_payment_chains` message where the `chains` array contains two entries sharing the same head `unit`, `payload_hash` (deterministic hash of `payload`), and `output_index`. No cryptographic break, race with the network layer, or precise timing is needed — duplication is entirely attacker-controlled and deterministic, since `ifQueued` (the light-client path) is the common outcome for chains not yet locally known. This makes the bug straightforward to trigger reliably against light wallets.

### Recommendation
- Deduplicate `arrChains` by the same `key` computation (`unit` + `payload_hash` + `output_index`) before processing, rejecting or collapsing duplicates.
- Guard the `eventBus.once` callback and any other writer of `assocValidatedByKey` with a null-check (`if (!assocValidatedByKey) return;`) before indexing into it, mirroring the guard already present in `checkIfAllValidated`.
- Consider registering listeners with `eventBus.once` keyed by a per-call unique identifier (e.g., include a request/session id) rather than a purely content-derived key, to avoid cross-call listener collisions on the shared global `eventBus`.

### Proof of Concept
1. As a paired device / private-payment counterparty, craft a `private_payment_chains` message whose `body.chains` contains two array entries, each a one-element chain array, where element `[0]` is identical (same `unit`, same `payload` producing the same `objectHash.getBase64Hash(payload,true)`, and same `output_index`/`denomination` setting) but wrapped as two separate top-level chain entries.
2. Send this message to a light wallet via `handleMessageFromHub` → `handlePrivatePaymentChains` (`wallet.js:955`).
3. Both entries produce the same `key`; for a light client, `network.handleOnlinePrivatePayment` will typically resolve via `ifQueued`, registering two `eventBus.once(key, …)` listeners.
4. Once the underlying payment is queued and later validated/emitted on `key` (e.g., via normal join/response processing that calls `eventBus.emit(key, true)`), both listeners fire in the same emit cycle: the first nulls `assocValidatedByKey` inside `checkIfAllValidated`, and the second throws `TypeError: Cannot set properties of null (setting '<key>')` when executing `assocValidatedByKey[key] = true`, crashing the wallet process.
