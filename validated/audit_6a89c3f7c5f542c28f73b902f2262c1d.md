### Title
Webhook signature is verified against an org/secret chosen from an unverified payload field, while a different, uncorrelated payload field is later used to select the stack to act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) used to validate the incoming HMAC signature from a field read out of the **still-unverified** JSON body, while `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every handler to look up the `Stack`/`Repository` to act on, reads a **different** field from that same unverified body. Nothing ties these two fields together, so a request signed with the secret of *organization A* can be crafted to act on a repository belonging to *organization B*.

### Finding Description
`verify_signature` derives the organization used to select the webhook secret directly from attacker-controlled JSON before the signature has been validated: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (falling back to `organization.login`) purely from `params`, which is parsed straight from `request.raw_post` with no prior authentication. `Shipit.github(organization: repository_owner)` then looks up the `GitHubApp` config entry (and its distinct `webhook_secret`) for that organization, and `verify_webhook_signature` checks the raw body's HMAC against *that* secret: [3](#0-2) 

Shipit explicitly supports one distinct GitHub App/webhook secret **per organization**, as documented in the multi-org config format: [4](#0-3) 

After the signature check passes, event handling parses the same payload and resolves the target `Stack` using a **different** field, `repository.full_name`: [5](#0-4) [6](#0-5) 

`repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the target repository/stack) are independent, unrelated JSON fields; the HMAC signature only proves the whole body was signed with *some* known secret, not that these two fields are consistent with each other. Because the *choice* of which secret to check against is itself taken from the unverified body, an actor who legitimately knows the webhook secret for **their own** configured organization (e.g., they administer the GitHub App for "org A" registered in Shipit) can send a raw POST to `/webhooks` with `repository.owner.login = "org-a"` (so `verify_signature` selects and validates against org A's secret, which the attacker computes correctly) but `repository.full_name = "org-b/victim-repo"`. The signature check succeeds, and the `PushHandler`/`CheckSuiteHandler` then acts on `org-b/victim-repo`, a stack the attacker has no authorization over: [7](#0-6) [8](#0-7) 

This is the direct structural analog of the reported Pyth issue: one field (`conf`) is present in the trusted/signed payload but never checked against the value actually used to price the trade; here, the field used to select the *authenticating* secret (`repository.owner.login`/`organization.login`) is never checked for consistency against the field used to select the *acted-upon* resource (`repository.full_name`), even though both come from the same signed body.

### Impact Explanation
An attacker who controls (or has knowledge of) the webhook secret of any single organization configured on a shared Shipit instance can forge webhook deliveries that are accepted as authentic for **any other organization's repositories** hosted on the same instance. This lets them force `GithubSyncJob` runs and check-run refresh scheduling that write `Commit`, `CommitStatus`, and related records against a victim stack/repository they have no authorization over — a cross-organization/cross-repository write triggered purely by an org-boundary field the signature never actually binds to the acted-upon resource. On multi-org Shipit deployments (the exact scenario the engine's own config format is built for), this crosses the "organization that authenticated versus the repository that is written" trust boundary.

### Likelihood Explanation
Requires the attacker to know (or control) the webhook secret of at least one organization already configured in the same Shipit instance — realistic in the documented multi-tenant deployment model where each organization manages its own separate GitHub App/secret against a shared Shipit engine. It requires no Shipit session, API token, or GitHub write access to the victim repository, and no interception of TLS.

### Recommendation
Bind the two fields together before trusting the payload: after `verify_webhook_signature` succeeds, re-derive/require that `repository.owner.login` (or `organization.login`) used for secret selection matches the owner embedded in `repository.full_name` used for target resolution, rejecting the request otherwise. Alternatively, have `Handler#repository_name`/`Repository.from_github_repo_name` scope lookups to the same organization used in `verify_signature`, so that a payload can never resolve a stack outside the organization whose secret validated it.

### Proof of Concept
1. Shipit is configured for two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.shopify.yml` layout).
2. Attacker knows `org-a`'s webhook secret (e.g., they administer `org-a`'s GitHub App).
3. Attacker crafts a `push` event JSON body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
   - `ref`, `after` set to attacker-chosen values.
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#repository_owner` returns `"org-a"`; `verify_webhook_signature` validates successfully against `org-a`'s secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")`, and triggers `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — an action the attacker has no legitimate authorization to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
