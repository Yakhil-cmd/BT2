### Title
Unscoped SHA lookup in `StatusHandler#process` lets any repository's status webhook mutate another repository's commit CI state and force-reject its merge requests - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha` (`Commit.where(sha: params.sha)`) with no check that the reporting `payload['repository']['full_name']` matches the commit's own stack/repository. This breaks the binding "a CI status attached to a commit came from that commit's own repository's CI provider," letting a webhook that is validly signed for one repository/org write a `failure`/`error` `Status` onto a `Commit` that belongs to a completely different repository/stack, which then drives `Shipit::MergeRequest#reject_unless_mergeable!` to reject a healthy, otherwise-mergeable PR.

### Finding Description
The broken binding: `Status.stack_id/commit_id created from webhook payload P` should imply `payload P was authenticated for the same repository as commit.stack.repository`. In code this is not enforced.

- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` across the entire database, ignoring `repository_name`/`stacks` entirely.

Contrast this with every other handler in the same directory, which correctly scopes to the repository that authenticated the webhook via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` (app/models/shipit/webhooks/handlers/handler.rb:32-38):
- `PushHandler#process`: `stacks.not_archived.where(branch:)...` (app/models/shipit/webhooks/handlers/push_handler.rb:13-16)
- `CheckSuiteHandler#process`: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` (app/models/shipit/webhooks/handlers/check_suite_handler.rb:14-16)
- All `PullRequest::*Handler` classes use `from_github_repo_name`.

`StatusHandler` is the only handler that skips this scoping, so the repository binding asserted by `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-38, matching signature to `repository_owner`) is never propagated into the actual data mutation — the signature only proves "this payload came from some org Shipit trusts," not "this `sha` genuinely belongs to the repository named in this payload."

Exploit flow:
1. `Commit#sha` values for pending merge requests are public (visible on the GitHub PR page/API) — no secret is required to learn a victim's head sha.
2. An attacker who has write/push access to some repository under an org already configured in Shipit (i.e., can trigger real, validly-signed webhook deliveries — satisfying `verify_signature`/`GitHubApp#verify_webhook_signature`, `lib/shipit/github_app.rb:76-83`) can create a GitHub Status via the standard Status API (`POST /repos/:owner/:repo/statuses/:sha`) using the *victim's* sha string as the target, even though that sha is not a commit that exists in the attacker's own repository. GitHub does not require the sha to belong to the reporting repo.
3. GitHub delivers a real, correctly-signed `status` webhook whose `repository` field names the attacker's own repo but whose `sha` field is the victim's commit sha and `state: 'failure'`.
4. `WebhooksController#verify_signature` validates the signature against the attacker's own org's config and passes — it never checks that `sha` belongs to that repository.
5. `StatusHandler#process` finds the victim's `Commit` row by raw `sha` match (no repository check) and calls `commit.create_status_from_github!(params)`, which invokes `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) and creates a `failure` `Status` for the victim's commit.
6. `ProcessMergeRequestsJob#perform` (app/jobs/shipit/process_merge_requests_job.rb:10-17) calls `merge_request.reject_unless_mergeable!`.
7. `Shipit::MergeRequest#reject_unless_mergeable!` (app/models/shipit/merge_request.rb:155-162) calls `any_status_checks_failed?` (lines 199-202), which is now true because of the forged `Status`, and rejects the PR with `reject!('ci_failing')`.

None of the existing guards catch this: `verify_signature` only authenticates the *sender org*, not the sha-to-repository relationship; `ExplicitParameters` schema in `StatusHandler.params` only validates types/presence of `sha`/`state`, not repository ownership; `drop_unhandled_event` and `force_github_authentication` are irrelevant here.

### Impact Explanation
This is a cross-repository write: a webhook authenticated for repository A can mutate CI/commit state that belongs to repository B's `Stack`, causing `Shipit::MergeRequest#reject!('ci_failing')` — an unauthorized rejection of another party's merge, matching the "payload for one repository mutating another repository's commit/task" and "unauthorized ... merge" Critical impact categories. It is repeatable against any Shipit-tracked commit sha the attacker can learn (all public PR shas), from any repository the attacker can trigger a signed status webhook from, as long as that repository resolves to an org Shipit already trusts (so `verify_signature` passes). The blast radius is bounded to sha collisions/exact-string matches across stacks known to Shipit, but since shas are 40-char unique identifiers taken verbatim from the payload, this is a deterministic exploit, not a birthday-bound collision — no cryptographic SHA collision is needed, only knowledge of the target sha string, which is public.

### Likelihood Explanation
Preconditions: the victim's `MergeRequest` must be `pending?`; the attacker must control (or have status-write access to) some GitHub repository whose webhook deliveries are validly signed by a `GitHubApp` config that Shipit already trusts (i.e., `repository_owner` resolves without raising `GithubOrganizationUnknown`). This typically means the attacker needs at least a repo/collaborator slot within an org that already has the Shipit GitHub App installed and configured — a materially lower bar than compromising the victim's specific repository or any Shipit secret, and squarely within the "unprivileged GitHub user" threat model for orgs with broadly-scoped or public app installations. No Shipit session, API token, or webhook secret needs to be known by the attacker — GitHub computes the valid signature automatically for any real delivery from an installed app. The victim's head sha is not secret. This makes the attack highly feasible and cheaply repeatable once the precondition (write access to any repo under a Shipit-known org, or ability to have the app installed on an attacker-owned repo) is met.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the other handlers:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ties `Commit` lookup to `Repository.from_github_repo_name(repository_name)` (via `Handler#stacks`), so a status can only be attached to commits belonging to the repository that actually authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extend `test/controllers/webhooks_controller_test.rb`):

```ruby
test "a status webhook from repository A cannot alter a commit's CI state that belongs to repository B" do
  # victim: healthy, pending merge request on stack B, with a passing head commit
  victim_pr = shipit_merge_requests(:shipit_pending) # stack: "shopify/shipit-engine"
  victim_pr.head.statuses.create!(stack: victim_pr.stack, state: 'success', context: 'ci/circle')
  assert_predicate victim_pr, :all_status_checks_passed?
  refute_predicate victim_pr, :any_status_checks_failed?

  # attacker: owns/authenticated for a different repository ("attacker-org/attacker-repo"),
  # sends a validly-signed status webhook naming the VICTIM's sha but the ATTACKER's repository
  forged_payload = {
    'sha' => victim_pr.head.sha,
    'state' => 'failure',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate a genuinely valid signature for attacker-org

  assert_no_difference -> { victim_pr.head.statuses.where(context: 'ci/attacker').count } do
    post :create, body: forged_payload.to_json, as: :json
  end

  # BEFORE FIX: this assertion fails because Commit.where(sha:) matches globally
  # AFTER FIX (Handler scoped via `stacks`): no Status is created and the merge request stays healthy
  victim_pr.reload
  refute_predicate victim_pr, :any_status_checks_failed?
  ProcessMergeRequestsJob.new.perform(victim_pr.stack)
  refute_predicate victim_pr.reload, :rejected?
end
```

This test demonstrates that, prior to the fix, the forged webhook (signed/authorized only for `attacker-org/attacker-repo`) succeeds in attaching a `failure` `Status` to the victim's commit purely via sha matching, which then flows through `ProcessMergeRequestsJob#perform` → `reject_unless_mergeable!` → `any_status_checks_failed?` → `reject!('ci_failing')`, transitioning the victim's healthy PR to `rejected`.
