### Title
Position NFT minted to contract addresses with no capability check can permanently lock a lending account - (File: contracts/position-nft/src/contract.rs)

### Summary
The Position NFT contract's `mint` writes ownership to whatever `Address` the controller passes, with no check that the receiver can ever exercise ownership. On Soroban a contract address cannot produce `require_auth` or invoke `transfer`/`withdraw` unless its own code explicitly does so. Any contract that calls `supply` (or is the receiver of a `flash_position`/`multiply`/`migrate_from_blend` account creation) and lacks an entrypoint that drives the NFT or the controller ends up owning a position it can never move or unwind, permanently freezing its collateral and stranding its debt.

### Finding Description
`PositionNft::mint` (contracts/position-nft/src/contract.rs:68-76) performs `controller(e).require_auth()` and then `Enumerable::sequential_mint(e, &to)` — a plain storage write of `Owner(token_id) = to` and `Balance(to) += 1`. There is no receiver-notification or capability hook analogous to ERC721 `onERC721Received`; Soroban has no such convention, so this is the equivalent of a bare `_mint` with no `safeMint` variant anywhere in the interface.

The controller mints through `create_account_with` (contracts/controller/src/account.rs:62-64), which passes the caller-supplied `owner` directly to `nft_mint_call` (contracts/controller/src/external/position_nft.rs:6-8). Every owner-gated controller verb later resolves authority via `owner_of` — `nft_try_owner_of_call` returns the live owner and the caller must equal it (the position NFT README documents that ownership is never cached). Moving the position requires the stored owner to authorize `transfer`/`transfer_from`/`approve` on the NFT contract; acting on the position requires the stored owner to authorize `withdraw`/`borrow`/`repay`/`supply` on the controller.

A contract address satisfies neither requirement automatically. `require_auth` on a contract address only succeeds if that contract's own code calls `require_auth`/`authorize_as_current_contract` or is in the direct invocation tree performing the sub-call. A generic contract — e.g., a flash-position receiver, a vault, or a multisig wrapper — that opens an account via `supply(caller, account_id=0, ...)`, `flash_position(caller, account_id=0, ...)`, `multiply`, or `migrate_from_blend` and has no code path that calls the NFT or controller will own a permanently immobile account. The test harness itself demonstrates the asymmetry: `FlashPositionTestReceiver` needed a bespoke `set_nft_transfer_target` + `TransferNftMidCallback` mode to move its minted NFT (tests/test-harness/src/receivers/flash_position.rs:218-233), confirming a contract owner without purpose-built code cannot transfer.

The protocol already acknowledges contract callers (the `prod_contract_*` integration flows exercise a `script_runner` contract supplying and moving NFTs through an explicit `NftTransfer` op), so contract ownership is a supported, reachable path — but the mint performs no check that the recipient can actually exercise it.

### Impact Explanation
Permanent freezing of funds. Once the NFT is owned by a contract that cannot authorize transfers or controller calls, all supplied collateral in the account is locked forever: only the NFT owner can `withdraw`, and the NFT itself can never leave. Any outstanding debt becomes unrepayable-by-owner bad debt that can only be cleared through liquidation or `clean_bad_debt`, imposing a loss on suppliers. There is no recovery path — the controller caches no owner, has no override, and `burn` is controller-only and only invoked on account deletion paths that themselves require owner authorization or liquidation.

### Likelihood Explanation
Medium. It requires a contract (rather than an EOA) to be the position owner and to lack NFT/controller-driving code — a plausible integration mistake for vaults, routers, and flash receivers, but it is self-inflicted by the integrator rather than exploitable against third parties. No external attacker is needed; a single mistaken contract caller strand its own funds, matching the accepted Medium severity of the source class.

### Recommendation
Treat `mint` recipients like `safeMint` does. Options:

1. At the controller layer, reject `create_account` when `owner` is a contract address that is not on an allowlist of known-capable contracts, or require the new owner to co-authorize a probe call (e.g., a no-op `renew`/`approve` round-trip) during mint so contracts prove they can authorize before ownership is committed.
2. Alternatively, support mint-then-handoff: allow `create_account` to take an explicit `to` distinct from `caller` is already possible, but document prominently in the controller and NFT READMEs that contract recipients must implement `transfer`/`require_auth` flows, and add a `salvage` owner-escape verb (e.g., a controller admin/governance path to reassign ownership of an account whose contract owner provably cannot act), so locked collateral is not permanent.

### Proof of Concept
1. Deploy a minimal receiver contract `R` implementing `execute_flash_position` that repays correctly but contains no code path calling `PositionNft::transfer` or any owner-gated controller verb (i.e., the `FlashPositionTestReceiver` minus `set_nft_transfer_target`/`TransferNftMidCallback`).
2. `R` calls `controller.flash_position(caller=R, account_id=0, spoke_id, PositionMode::Multiply, ...)` supplying collateral inside the callback — or simply calls `supply(caller=R, account_id=0, ...)` after being funded.
3. The controller mints a fresh NFT to `R` via `create_account_with` → `nft_mint_call`; `owner_of(token_id) == R`.
4. After the call ends, no transaction can succeed in which `R` authorizes `nft.transfer` or `controller.withdraw`, because `R` has no entrypoint that produces `R`'s `require_auth`. `owner_of` keeps resolving to `R`; collateral remains credited to the account indefinitely.
5. The account is only removable via liquidation (if unhealthy) or `clean_bad_debt` (if it becomes bad debt); a healthy collateralized position is frozen permanently.
