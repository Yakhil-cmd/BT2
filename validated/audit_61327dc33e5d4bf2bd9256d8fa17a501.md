### Title
Unauthenticated victim-address spoofing via `PreStxOp.output` lets an attacker lock a victim's STX with only attacker-signed Bitcoin transactions - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` sets `output` to whatever `StacksAddress` is encoded in **vout 0** of the PreStxOp's own Bitcoin transaction, with no requirement that the broadcaster control the private key behind that address. `StackStxOp::get_sender_txid` (and the identical logic in `delegate_stx.rs`/`transfer_stx.rs`) only checks that the *spending* transaction's input 0 references `(PreStxOp.txid, vout=1)` — the **change output**, which the attacker fully controls and signs. Nothing ties the identity named in vout 0 (the future "sender") to the key that authorizes vout 1.

### Finding Description
Broken equality: **STX locked by the applied `StackStxOp` == STX owned by the party whose private key authorized the Bitcoin transactions.**

- `PreStxOp::parse_from_tx` derives `output` purely from the first recipient output of the PreStxOp transaction: [1](#0-0) . This is just a `StacksAddress` (i.e., an hrp/version byte + hash160) reconstructed from a Bitcoin output address — a value that requires no signature or proof of key ownership from the address's owner, since a hash160 is public information anyone can pay to.
- `StackStxOp::get_sender_txid` only validates that input 0 of the spending transaction references vout 1 of that same PreStxOp txid: [2](#0-1) . This only proves the spender controls the *change* UTXO (vout 1) of the PreStxOp transaction, not that they control the address named in vout 0.
- `StackStxOp::parse_from_tx` then takes `sender: &StacksAddress` as an externally-supplied parameter (resolved by the burnchain indexer from the matched `PreStxOp.output`) and stores it verbatim as `self.sender` with no additional identity check: [3](#0-2) .

**Exploit flow:**
1. Attacker crafts a Bitcoin transaction (the PreStxOp) with vout 0 paying to a P2PKH/P2WPKH address whose hash160 equals victim V's Stacks address hash160 (attacker needs no cooperation or signature from V — this is just choosing a known public destination hash), and vout 1 as the attacker's own change output.
2. This is broadcast/parsed as a `PreStxOp` with `output = V` and `txid = T`.
3. Attacker crafts and signs a second Bitcoin transaction (StackStxOp) whose input 0 spends `(T, vout=1)` — entirely signed by the attacker, since that's their own UTXO.
4. `get_sender_txid` passes because vout==1 matches. The chain indexer resolves `sender = PreStxOp.output = V`, and produces a `StackStxOp { sender: V, ... }`.
5. Downstream stacking-lock application treats this exactly as if V had authorized the lock, since the only "authority" check performed anywhere in this code path is the Bitcoin UTXO-spending check in step 3-4 — which never touches V's key.

The existing guard (`vout == 1` check in `get_sender_txid`) only proves control over the *change* output of the PreStxOp transaction; it provides no proof of control over vout 0's address, which is exactly the field copied into `sender`/`output`. No other check in `PreStxOp::parse_from_tx` or `StackStxOp::parse_from_tx` cross-validates that vout 0 and vout 1 belong to the same key.

### Impact Explanation
If this reaches STX-locking application unmodified, an attacker can direct that any address's STX balance (subject to it being unlocked and having sufficient balance) gets locked into stacking under attacker-chosen `reward_addr`/`signer_key`/`num_cycles`, without the victim ever signing a Bitcoin or Stacks transaction. This is a Critical-class issue per the rubric ("unlocking value never locked" / an unsigned stacking action performed on victim's funds), repeatable for every address the attacker can enumerate and for which they can win the mempool race to submit the PreStxOp before the victim uses their account.

### Likelihood Explanation
I was not able to fully trace, within the available tool budget, the downstream code in `stackslib/src/burnchains/burnchain.rs` and the chain-processing/coordinator logic that resolves `sender` from a matched `PreStxOp` and finally invokes the PoX lock (`pox_lock_v4`/`pox_lock_v5`). The parsing-level flaw described (vout-0 vs vout-1 ownership mismatch) is clearly present in `stack_stx.rs`, `delegate_stx.rs`, and `transfer_stx.rs`, but I could not confirm whether an additional check exists later in the pipeline (e.g., in the coordinator or in `.pox-5`'s Clarity-side handling) that re-validates `sender` against something the victim actually controls before debiting their STXBalance. Given the maturity of the Stacks network and the absence of any known incident matching this exact attack, it is likely (though not verified here) that this PreStxOp→StackStxOp two-transaction linkage is a documented, long-standing design (SIP-007 "Stack via Bitcoin") whose security assumption — that a single wallet uses the same key for both vout 0 and vout 1 — is enforced only by wallet convention and not by consensus code, or that a check I could not reach in this session prevents the spoofing from resulting in an actual lock of the victim's balance.

Because I could not conclusively trace the balance-debiting step to confirm or rule out the missing check, I cannot state with full confidence that this results in an exploitable Critical impact as opposed to being an already-mitigated/accepted design assumption.

### Recommendation
If not already enforced downstream, require that the address encoded in `PreStxOp.output` (vout 0) be provably controlled by the same key that signs the spend of vout 1 in the corresponding `StackStxOp`/`DelegateStxOp`/`TransferStxOp` — e.g., by requiring vout 0 and vout 1 to share the same scriptPubKey/address, or by requiring an explicit Stacks-side signature from `sender` authorizing the lock before it is applied.

### Proof of Concept
Not provided — verifying whether this is actually exploitable requires tracing the burnchain-op-to-PoX-lock application path (`stackslib/src/burnchains/burnchain.rs` and the chains coordinator) which I could not complete within the tool budget for this session. A definitive PoC would need a chainstate-based Rust test asserting that after applying such a crafted `PreStxOp`/`StackStxOp` pair, victim V's on-chain STX balance shows a lock via `pox_lock_v5` despite zero transactions signed by V.

    pub fn get_sender_txid(tx: &BurnchainTransaction) -> Result<&Txid, op_error> {
        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
