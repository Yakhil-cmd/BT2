### Title
Stack-scoped ApiClient tokens can read the build status of any stack via CCMenu - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` can be restricted to a single stack via its `stack_id` column, and every other API endpoint enforces that scoping through `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` and looks the target stack up directly from `params[:stack_id]` without ever consulting `current_api_client.stack_id`, so a token that is only supposed to authorize reads on one stack can be used to read the CI/deploy status of every stack in the installation.

### Finding Description
`Api::BaseController` binds an `ApiClient`'s authorization to a specific stack when `stack_id` is present: [1](#0-0) 

Every controller that inherits this `stack`/`stacks` helper (e.g. `Api::StacksController`) is therefore constrained: a client whose `stack_id` is set can never fetch a different stack, even though it authenticates successfully and passes the `read:stack` permission check. This is confirmed by the test `"an api client scoped to a stack will only see that one stack"`.

`Api::CCMenuController`, however, redefines `stack` and drops the scoping entirely: [2](#0-1) 

It still requires the `read:stack` permission via `require_permission :read, :stack` (checked only against the client's `permissions` array, never against `stack_id`): [3](#0-2) [4](#0-3) 

Because `stack` is resolved via `Stack.from_param!(params[:stack_id])` against the entire `Stack` table instead of `current_api_client.stack`, any stack id/slug supplied in the URL is honoured, regardless of which single stack the token was minted for.

The equality that should hold is:
`current_api_client.stack_id (the stack the token authorizes)` == `params[:stack_id] resolved stack (the stack the request actually touches)`

`Api::CCMenuController#show` breaks this equality: the left side is checked nowhere in this controller, only the right side is used.

### Impact Explanation
An attacker who possesses (or is handed, e.g. via the built-in `CCMenuUrlController#fetch` flow which mints and exposes tokens per stack) a stack-scoped, `read:stack`-only `ApiClient` token for one stack can query `GET /api/:stack_id/ccmenu.xml` for *any other stack id* and receive that stack's build/deploy state: `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock status, and webUrl (see `app/controllers/shipit/api/ccmenu_controller.rb` and the CCMenu XML view). This is an authorization-scope escalation: the token authorizes reads on stack A only, but the endpoint lets it read stack state for stack B, C, ... — i.e., "unauthenticated [w.r.t. that stack] read of stack state," matching the High-impact category for scope escalation across stacks.

### Likelihood Explanation
Exploitation requires only possession of any valid, stack-scoped `ApiClient` token with `read:stack` permission (the least-privileged token type Shipit issues, e.g. the one automatically created for the CCMenu "traffic-light" integration) and knowledge/guessing of another stack's id/slug — no write access, no privileged account, and no additional secret is needed beyond the token itself. Since stack ids/slugs are low-entropy and often discoverable (repo/env/branch based `to_param`), this is straightforward to reach once any such token is obtained.

### Recommendation
Make `Api::CCMenuController#stack` reuse the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the client's `stack_id` binding is enforced consistently with the rest of the API surface.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` restricted to Stack A with only `read:stack` permission (mirrors fixture `here_come_the_walrus`, `stack: shipit`, `permissions: [read:stack]`, or the token minted by `CCMenuUrlController#fetch` for Stack A).
2. Using this token, issue `GET /api/<Stack B id or slug>/ccmenu.xml` with HTTP basic auth `token:` (or `?token=`), where Stack B is a completely different, unrelated stack.
3. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` succeeds (`check_permissions!` only checks the permissions array), and `stack` in `app/controllers/shipit/api/ccmenu_controller.rb` resolves Stack B directly from `params[:stack_id]`.
4. The response returns Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.), even though the token was only ever authorized for Stack A.
