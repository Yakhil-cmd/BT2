### Title
Membership webhook signature check silently no-ops when `webhook_secret` is unset, letting an unauthenticated attacker forge `Shipit.github_teams` membership - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as "nothing to verify" and returns `true` unconditionally. `WebhooksController` relies exclusively on this method to authenticate every inbound webhook, including the `membership` event, which directly creates/deletes `Team`/`Membership` rows that drive `User#authorized?`. If an organization is configured without a webhook secret (a documented, supported configuration), any unauthenticated network client can POST a forged `membership` payload and grant an arbitrary GitHub login membership in a team matching `Shipit.github_teams`, bypassing the entire authorization gate (`force_github_authentication`). This is the same trust-binding failure as the reported bug: a control (`sweep()`'s "any token" check / here, "any payload accepted as authentic") is not actually bound to the resource it is meant to protect (BPTs / here, `Shipit.github_teams` authorization), letting an unprivileged actor cross a boundary that the rest of the system assumes is enforced.

### Finding Description
Webhook authenticity is the sole basis on which `WebhooksController` decides whether to trust and act on a payload: [1](#0-0) 

The actual check is: [2](#0-1) 

`verify_signature` delegates to `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, whose implementation is: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If `webhook_secret` is blank/`nil` for that GitHub organization's configuration, **every** webhook for that org is treated as verified, regardless of the actual `X-Hub-Signature` header (or its absence). This is not a hypothetical edge case — the shipped example configs explicitly document `webhook_secret: null`/`webhook_secret: some-secret-value` as an optional setting: [4](#0-3) [5](#0-4) 

Once a payload is treated as "verified," `WebhooksController#create` dispatches it straight into the corresponding handler: [6](#0-5) 

For `X-Github-Event: membership`, the handler mutates `Team`/`Membership` rows directly off the raw JSON body with no secondary corroboration against GitHub, as demonstrated by the controller's own test suite: [7](#0-6) 

These `Membership` rows are exactly what gates application-wide authorization. `User#authorized?` checks membership in any team whose id is in `Shipit.github_teams`: [8](#0-7) 

And every controller in the engine enforces this via `force_github_authentication`: [9](#0-8) 

**The binding that breaks:** the system assumes `Membership` rows are only ever created via GitHub-signed events (`organization that authenticated == the record that is written into Shipit.github_teams authorization`). But when `webhook_secret` is unset, the "authenticated" side of that equation is vacuously true for anyone on the network, while the "record written" side is fully attacker-controlled — an unprivileged, unauthenticated network client can write into `Shipit.github_teams` authorization state.

### Impact Explanation
This is a High-severity finding per the listed criteria: "escalation into `Shipit.github_teams` authorization." An attacker who forges a `membership` webhook can:
1. Create an arbitrary `Team` matching one of `Shipit.github_teams`' handles (or target an existing one), and
2. Add an arbitrary GitHub login (which the attacker controls, since `User.find_or_create_from_github` is invoked with attacker-supplied `login`) as a member.

Once the corresponding user authenticates through the normal (legitimate) GitHub OAuth flow, `authorized?` returns `true` for them, granting full access to the Shipit UI/API for every stack — including triggering deploys/rollbacks/tasks — despite never actually belonging to the real GitHub team. This effectively bypasses the entire authorization layer that the rest of the engine (and the report's underlying theme of "a check that doesn't actually bind to what it's supposed to protect") relies on.

### Likelihood Explanation
Likelihood is high wherever an operator deploys Shipit without configuring a per-organization `webhook_secret` — a state the project's own example configs and docs present as valid/default (`webhook_secret: null`). No credentials, sessions, tokens, or social engineering are required: the `/webhooks` endpoint is unauthenticated by design (it must accept unauthenticated GitHub callbacks), and the only "authentication" is the signature check that silently degrades to a no-op.

### Recommendation
- Fail closed instead of open in `GitHubApp#verify_webhook_signature`: if no `webhook_secret` is configured, reject the webhook (or require an explicit, loudly-logged opt-in) rather than treating it as verified.
- Alternatively/additionally, require `webhook_secret` to be present as part of Shipit's configuration validation (raise at boot if any configured GitHub org lacks one), removing the possibility of silently running with signature verification disabled.
- Consider additionally cross-checking `membership` events against a live GitHub API call before mutating `Team`/`Membership` state, so that authorization-affecting writes are not solely gated by webhook signature verification.

### Proof of Concept
Preconditions: target Shipit instance has an organization configured with `webhook_secret` blank/`nil` (as shown in `test/dummy/config/secrets.test.json` and the `docs/setup.md` example).

1. Unauthenticated attacker sends, with no `X-Hub-Signature` header (or any bogus value):
```
POST /webhooks
Content-Type: application/json
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": 48, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "target-org" },
  "member": { "login": "attacker-controlled-login" }
}
```
2. `WebhooksController#verify_signature` calls `verify_webhook_signature(nil_or_bogus, body)`, which returns `true` immediately because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
3. The membership handler creates/updates the `Team`/`Membership` records exactly as exercised in `test/controllers/webhooks_controller_test.rb:129-149` (`":membership creates the mentioned team on the fly"`, `":membership creates the mentioned user on the fly"`).
4. If `deployers`'s `id`/handle is listed in `Shipit.github_teams`, any user who logs in via the normal GitHub OAuth flow with `login == "attacker-controlled-login"` now passes `User#authorized?` (`app/models/shipit/user.rb:80-82`) and gains full access to the Shipit engine.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
