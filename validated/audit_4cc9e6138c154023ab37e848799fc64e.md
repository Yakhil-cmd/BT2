## Finding [1](#0-0) 

### Title
Silently Ignored Delivery Failure of Private Payment Chains Causes Permanent Loss of Recipient's Private Asset Funds - (File: `wallet_general.js`)

### Summary
`sendPrivatePayments()` in `wallet_general.js` calls `device.sendMessageToDevice()` with empty `ifOk`/`ifError` callbacks, discarding the actual delivery result of the private payment chain (which contains the `spend_proof`s the recipient needs to later spend the private asset). Only the local `onSaved` callback (fired once the message is queued in the local `outbox` table) is used to continue the wallet's commit flow, so the on-chain unit that spends the sender's private-asset inputs is finalized and broadcast regardless of whether the recipient's device ever actually receives the private elements.

### Finding Description
`sendPrivatePayments` is defined as: [2](#0-1) 

It forwards to `device.sendMessageToDevice`, whose `callbacks.onSaved` fires immediately after the message is inserted into the local `outbox` table — before any network delivery to the hub/recipient occurs: [3](#0-2) 

The real delivery result (whether the hub accepted the message, whether encryption/signing to the recipient succeeded, or whether the hub errors out) is only surfaced via `callbacks.ifOk`/`callbacks.ifError` inside `sendPreparedMessageToConnectedHub`: [4](#0-3) 

But `sendPrivatePayments` passes empty no-op functions for exactly these two callbacks:
```js
device.sendMessageToDevice(device_address, "private_payments", body, {
	ifOk: function(){},
	ifError: function(){},
	onSaved: onSaved
}, conn);
```
This is the direct analog of the reported unchecked low-level call: the "call" to the recipient (device message delivery, functionally equivalent to the low-level `call()` to `gnosisAddress`/`ownerAddress`) has its success/failure discarded, and the caller (`onSaved`) proceeds as if the transfer of value/proof had succeeded.

In `wallet.js`, this function is invoked from the `preCommitCb` used when sending a private asset, and its `cb2` (== `onSaved`) directly drives completion of the precommit step that lets the spending unit be saved and broadcast: [5](#0-4) [6](#0-5) 

Because private assets require possession of the actual private elements/`spend_proof` chain to be spendable later (the chain is never published in cleartext on the DAG), if the message never reaches the recipient (e.g., transient network failure, hub rejects due to signature/pubkey mismatch, encryption failure, connection issue) the sender's payment unit is still saved and broadcast, permanently consuming the sender's inputs, while the recipient has no way to reconstruct the private chain to prove/spend the received output. The funds are effectively locked/lost for the private-payment counterparty, with no retry or error surfaced to the sending wallet UI/caller.

### Impact Explanation
A single failed private-asset payment causes real, permanent loss of the recipient's private-asset funds: the on-chain output exists, the sender's inputs are irrevocably spent, but the recipient can never spend the output because the required `spend_proof` chain was never delivered and no automatic retry/backpressure is tied to this specific send. This is a genuine "AA/wallet fund loss" instance triggered purely by a private-payment counterparty interaction, not requiring any malicious peer/hub behavior — an ordinary transient failure suffices.

### Likelihood Explanation
Likelihood is High: any transient failure in `sendMessageToHub`/`sendPreparedMessageToConnectedHub` (network hiccup, hub temporarily rejecting `hub/get_temp_pubkey`, temp-pubkey verification failure, or any other error path in `device.js`) silently no-ops through the empty `ifError` callback, letting the precommit and subsequent broadcast proceed unaffected. No attacker action is required to trigger the loss; ordinary unreliable delivery conditions are sufficient.

### Recommendation
Propagate the real `ifOk`/`ifError` result from `device.sendMessageToDevice` in `sendPrivatePayments` instead of the empty stubs, and make the wallet's `preCommitCb` abort (or explicitly track/retry) the private-asset send when delivery fails, rather than relying solely on `onSaved` (which only reflects local persistence, not actual delivery) to gate commit of the spending unit.

### Proof of Concept
1. Sender initiates a private-asset payment via `wallet.js`'s `sendMultiPayment`, which for private assets registers `preCommitCb` calling `walletGeneral.sendPrivatePayments(recipient_device_address, arrChainsOfRecipientPrivateElements, false, conn, cb2)` (`wallet.js:2407`).
2. `sendPrivatePayments` calls `device.sendMessageToDevice(..., { ifOk: function(){}, ifError: function(){}, onSaved: onSaved }, conn)` (`wallet_general.js:23-27`).
3. `sendMessageToDevice` → `sendMessageToHub` → `reliablySendPreparedMessageToHub` inserts the message into `outbox` and immediately invokes `callbacks.onSaved()` (`device.js:589-597`), which is `cb2`, resolving the precommit step and allowing `saveAndUnlock`/broadcast to proceed.
4. The subsequent actual network delivery attempt (`sendPreparedMessageToHub` → `sendPreparedMessageToConnectedHub`) fails — e.g., the hub returns an error on `hub/get_temp_pubkey` or `hub/deliver` (`device.js:610-666`) — triggering `callbacks.ifError(error)`, which is the no-op function and produces no observable effect.
5. The sending unit spending the sender's private-asset inputs is already committed and broadcast to the DAG; the recipient never receives the `arrChainsOfRecipientPrivateElements` needed to reconstruct spend proofs for the output, permanently losing access to the transferred private-asset funds.
