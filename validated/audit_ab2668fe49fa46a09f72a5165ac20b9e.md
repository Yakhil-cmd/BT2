### Title
Webhook signature verified against attacker-selected organization while payload's `repository.full_name` targets an arbitrary victim stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In Shipit's multi-organization GitHub App configuration (documented in `config/secrets.development.shopify.yml` and `docs/setup.md`), each organization has its own `webhook_secret`. The webhook signature check selects *which* secret to verify against using an attacker-supplied field (`repository.owner.login` / `organization.login`), while the code that actually acts on the payload uses a *different* field from the same untrusted JSON body (`repository.full_name`) to look up the target `Stack`/`Repository`. Because the two fields are not required to be internally consistent, an attacker who legitimately controls one organization's webhook secret (by installing the same multi-tenant Shipit's GitHub App on their own org, which is the documented intended use of this feature) can sign a payload that names *their own* org for signature verification while pointing `repository.full_name` at a victim organization's repository, causing Shipit to act on a stack they do not own.

### Finding Description
The binding that should hold is: **organization authenticated (secret used to verify the HMAC) == organization that owns the repository actually written/acted upon**.

`WebhooksController#verify_signature` computes `repository_owner` from the untrusted payload and uses it purely to select which org's secret to validate the signature with: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` only checks the HMAC of the raw body against the secret for the organization resolved above — it does not tie the signature to any specific repository/organization identity beyond "some configured secret matched": [3](#0-2) 

Downstream, every webhook `Handler` (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field from the very same attacker-supplied payload — `repository.full_name` — with no cross-check against `repository.owner.login` used earlier for authentication: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` splits `full_name` and looks up the repository purely by owner/name pair contained in that field, again independent from `repository.owner.login`: [6](#0-5) 

Since the whole HTTP body is attacker-controlled JSON (not a structurally-consistent object proxied unmodified from GitHub — the attacker crafts it directly), nothing prevents `repository.owner.login` (used to pick the verification secret) from being an org the attacker legitimately controls, while `repository.full_name` (used to find the actual `Stack` to sync/mutate) names a victim's repository. The signature check only proves "this body was signed by *some* configured org's secret" — never that the *acted-upon* repository belongs to that same org.

### Impact Explanation
Multi-org Shipit configurations (explicitly documented and supported per `config/secrets.development.shopify.yml`) are per-design for hosting several tenants' repositories under one Shipit instance. An attacker who is a legitimate installer/admin of the GitHub App for *their own* organization (an "unprivileged" outsider relative to the victim org) obtains a valid `webhook_secret` for their own org. By crafting a webhook body whose `repository.owner.login`/`organization.login` field is their own org (satisfying signature verification) but whose `repository.full_name` field points at a victim's tracked stack, they can trigger real actions Shipit performs on webhook receipt for arbitrary victim repositories they do not own — for the `push` event this forces `GithubSyncJob`/`sync_github` against the victim stack (spoofed head SHA sync), and other handlers (`status`, `check_suite`, `pull_request/*`, `membership`) act on data keyed the same insecure way, letting an attacker inject fabricated commit statuses, check-run/PR state, or team/user membership changes into a stack outside their authorization boundary. This is a cross-repository/cross-tenant write achieved purely by crossing an authentication-vs-target-repository boundary, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (a documented, supported configuration), and (2) the attacker to be a legitimate admin/installer of the GitHub App for at least one of the configured organizations — a bar far lower than repository write access to the victim's repo, and explicitly not one of the "requires privileged account/token/webhook_secret" exclusions since it is the attacker's *own* legitimately obtained secret being (ab)used to forge cross-tenant requests. No signature secret theft, no session, and no GitHub credentials of the victim are needed.

### Recommendation
Bind webhook signature verification to the same identity used for acting on the payload: require that `repository.owner.login`/`organization.login` (used to select the verification secret) be identical to the owner portion of `repository.full_name` before dispatching to handlers, and reject the request otherwise. Alternatively, resolve the target `Repository`/`Stack` using the already-verified organization identity rather than re-parsing an independent field from the same untrusted payload.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker (a legitimate installer of the App for `attacker-org`) knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the signature verifies successfully.
6. `PushHandler#process` resolves `stacks` via `repository.full_name` = `victim-org/victim-repo`, unrelated to the verified `attacker-org`, and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — a write triggered on a repository the attacker never authenticated for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
