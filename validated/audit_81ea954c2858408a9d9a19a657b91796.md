### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but handlers act on the unrelated, attacker-controlled `repository.full_name` / commit `sha` fields inside the same signed payload, allowing cross-repository status/stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against solely from `repository.owner.login` (or `organization.login`), then hands the *entire* raw JSON body to whatever handler is registered for the event. Several handlers, however, resolve *which repository/stack/commit to mutate* from a different field in that same payload (`repository.full_name`, or in the case of `status` events, a bare `sha` with no repository scoping at all). Because the HMAC only proves "this body was sent by whoever holds the secret for the organization named in `repository.owner.login`," it does nothing to bind the value of `repository.full_name`/`sha` to that same organization. An attacker who legitimately controls one org configured in Shipit (and therefore its webhook secret) can forge a payload whose `owner.login` matches their own org (so it authenticates) while `full_name`/`sha` point at a completely different, victim repository tracked by the same Shipit instance.

### Finding Description
- Signature verification: [1](#0-0)  picks the GitHub App via `repository_owner` [2](#0-1)  and verifies the raw body against that org's `webhook_secret`.
- Shipit supports multiple, independently configured GitHub orgs, each with its own secret, selected purely by name: [3](#0-2) .
- The base `Handler` class, used by `PushHandler`, `PullRequest::*Handler`s, `CheckSuiteHandler`, etc., resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')` — a field that is *not* checked against `repository.owner.login`: [4](#0-3) .
- `StatusHandler` is even weaker: it looks up commits by bare `sha` with no repository/stack scoping whatsoever, across the entire Shipit database: [5](#0-4) .
- `PullRequest::EditedHandler`/`AssignedHandler` similarly re-derive the acted-upon repository from `params.repository.full_name` independently of whatever org authenticated the request: [6](#0-5) .

**Binding broken:** `organization that authenticated the webhook` ≠ `repository/commit the handler writes to`. The signature (HMAC over the full raw body) technically covers the `full_name`/`sha` bytes, but signature validity is evaluated per-organization-secret selected by a *different* field in the same body, so it only proves "signed by org X's secret," not "this action targets a resource belonging to org X." Any organization onboarded into the same Shipit instance can spoof events for any other onboarded organization's repositories.

### Impact Explanation
Using an org they legitimately control (and whose webhook secret they therefore know), an attacker can:
- Send a forged `status` event with `sha` equal to a real commit SHA in a victim repository/stack, injecting a fabricated "success" CI status via `Commit#create_status_from_github!`, potentially satisfying `required_statuses`/`blocking_statuses` gates used to permit deploys or GitHub merges in that other stack — an unauthorized-deploy/merge primitive, which is Critical per the rules.
- Send a forged `push`/`pull_request` event with `repository.full_name` pointing at a victim repo/stack tracked by the same instance, triggering `stack.sync_github` or pull-request record mutation (`PullRequest#update(github_pull_request: ...)`) for a stack the attacker's org has no legitimate relationship with — a cross-repository/cross-organization write.

This directly matches the "organization authenticated vs. repository written" binding called out as in-scope.

### Likelihood Explanation
Requires the attacker to control (or compromise) at least one organization that is configured in this Shipit instance's `secrets.github` multi-org map — i.e., they must already be a legitimate tenant/org owner on the instance, not an arbitrary unprivileged internet actor. This is a real but narrower precondition than a fully unauthenticated attack; it is nonetheless unprivileged relative to the *victim* organization/repository being attacked, since no credential or access to the victim org is required — only membership/control of any other org onboarded to the same Shipit deployment.

### Recommendation
When resolving the target repository/stack/commit for a webhook event, require that `repository.owner.login` (the field used to select and verify the signing secret) matches the owner embedded in `repository.full_name`, and reject the event otherwise. For `StatusHandler`, scope the `Commit` lookup by the resolved repository/stack, not by bare `sha` alone.

### Proof of Concept
1. Attacker controls org `attacker-org`, which is configured in this Shipit instance with webhook secret `S_attacker`.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<real sha of a commit in victim-org/victim-repo tracked by this instance>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker signs the raw body with `S_attacker` and sets `X-Hub-Signature`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker legitimately knows `S_attacker` [7](#0-6) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no relation to `attacker-org`, finds the victim's commit, and creates a fabricated success status on it [5](#0-4) , potentially unblocking a deploy/merge gate on `victim-org/victim-repo` despite the request never having been authenticated for that organization.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
