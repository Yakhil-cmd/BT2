### Title
Webhook signature verification keyed on `repository.owner.login` while all event handlers act on the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) . Every webhook handler, however, resolves the actual repository/Stack to act on using a completely different field, `repository.full_name`, via `Handler#repository_name` [2](#0-1) . This is the same "verified scope vs. acted-upon scope" mismatch as the LpFarm bug: the field used to authorize/verify (`repository.owner.login`, used to pick the signing secret) is never bound to the field the business logic actually operates on (`repository.full_name`).

### Finding Description
In a multi-organization Shipit deployment (explicitly documented and supported, see `docs/setup.md` "Using Multiple Github Applications" and `TOP_LEVEL_GH_KEYS`/`github_app_config` in `lib/shipit.rb`), each organization can have its own `webhook_secret`, and that field is optional per app [3](#0-2) . `GitHubApp#verify_webhook_signature` explicitly bypasses verification entirely when no secret is configured for that org: `return true unless webhook_secret` [4](#0-3) .

The controller picks *which* org's `GitHubApp` (and therefore secret) to use purely from the attacker-controlled JSON body: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Nothing ties that value to `repository.full_name`, which is the field every handler actually trusts to look up the `Repository`/`Stack` to act on (`PushHandler`, `StatusHandler`'s `Commit.where(sha:)` scoped by stack via `stacks`, `PullRequest` handlers, etc.) [2](#0-1) [5](#0-4) [6](#0-5) .

Root-cause binding broken: `organization authenticated (repository.owner.login)` ≠ `repository the handler writes to (repository.full_name)`. Before the mismatch: in single-org deployments both fields naturally refer to the same org so the check is effectively sound. After: in a multi-org configuration where one configured org has no `webhook_secret` (a supported, documented configuration), an attacker can set `repository.owner.login` to that no-secret org (verification auto-passes) while setting `repository.full_name` to any other configured org's real repository, e.g. `"other-org/prod-app"`. Since the JSON body is otherwise unconstrained and unsigned/unverified against that inconsistency, this forged, unsigned payload is then processed by handlers exactly as if it came from `other-org`.

### Impact Explanation
Because `StatusHandler` and `PushHandler` (and `CheckSuiteHandler`) trust `repository.full_name` (or SHA matching across all `Commit` records, not scoped by verified org) without any cross-check against the org used for signature verification, an attacker who knows (or can enumerate) that one configured GitHub organization lacks a `webhook_secret` can:
- Forge `status` events for arbitrary commit SHAs belonging to a *different, properly-secured* organization's stacks, injecting fake green CI statuses and unblocking merges/deploys gated on CI status (`Commit#create_status_from_github!`).
- Forge `push` events causing `stack.sync_github` to run against a chosen `expected_head_sha` for another org's stack, which is used to fetch and potentially trigger sync/deploy flows.

This crosses the "unauthorized deploy/merge" boundary defined as Critical/High impact, since a payload not authenticated for the target repository's organization is accepted as if it were.

### Likelihood Explanation
Requires: (1) the host application configured with multiple GitHub Apps (documented, supported feature), and (2) at least one configured organization without a `webhook_secret` set (allowed by config schema, `webhook_secret` is optional). Given these two conditions — both realistic in larger multi-tenant Shipit deployments — no credentials are needed; the attacker just POSTs to the public `/webhooks` endpoint.

### Recommendation
Bind the signature-verification scope to the same identity the handlers act upon: verify using the organization derived from `repository.full_name` (or require they match `repository.owner.login`), and reject (422) when they diverge, rather than trusting an independently attacker-controlled `owner.login`/`organization.login` field. Additionally, consider not allowing verification to silently pass (`return true unless webhook_secret`) for a subset of configured organizations in a multi-org setup, or require secrets to be mandatory once multiple orgs are configured.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `org-a` (no `webhook_secret` set) and `org-b` (with `webhook_secret` set, hosting the real target stack/repo).
2. Send `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<real commit sha belonging to org-b's stack>",
  "state": "success",
  "context": "ci/tests",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/real-repo" }
}
```
No `X-Hub-Signature` header (or any arbitrary value) is required, since `Shipit.github(organization: "org-a").verify_webhook_signature` returns `true` immediately (`webhook_secret` is `nil`) [4](#0-3) .
3. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — not scoped to `org-a` at all — and creates a forged `success` status for the org-b commit [7](#0-6) , which can satisfy `ci.require` checks and enable an unauthorized deploy/merge for `org-b`'s stack despite never presenting a valid `org-b` signature.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
