### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` applies GitHub `status` webhook events to commits by looking them up globally with `Commit.where(sha: params.sha)`, with no scoping to the repository/organization that the webhook signature actually authenticated. Every other comparable handler (`PushHandler`, `CheckSuiteHandler`) scopes its writes through the `stacks` collection tied to the payload's repository, but `StatusHandler` does not. This breaks the equality "the repository whose GitHub App secret authenticated this webhook" == "the repository/stack whose commit gets written," which mirrors the reported bug class (a value that influences a privileged write is never actually bound to what was verified).

### Finding Description
The webhook signature check in `app/controllers/shipit/webhooks_controller.rb#verify_signature` selects the GitHub App/organization to verify against using `repository_owner` (derived from the untrusted payload itself: `params.dig('repository', 'owner', 'login')`), and confirms the raw body is signed by that organization's `webhook_secret`. [1](#0-0) 

Once verified, `WebhooksController#create` dispatches the parsed payload to the registered handler for the event type without any further binding of "which repository does this event belong to" to "which repository/commit does the handler mutate." [2](#0-1) 

For `status` events, `StatusHandler#process` resolves target commits purely by `sha`, across the *entire* `Commit` table (i.e., across every repository/stack tracked by this Shipit instance), and calls `create_status_from_github!` on each match: [3](#0-2) 

Compare this to `PushHandler` and `CheckSuiteHandler`, which both scope their writes through the `stacks` association (bound to the payload's own repository) before touching any commit: [4](#0-3) [5](#0-4) 

Because `StatusHandler` never checks that the resolved `Commit`'s `stack.repository` matches the repository that was actually authenticated by `verify_webhook_signature`, a valid, properly-signed `status` webhook from repository **A** can update the CI status of a commit that happens to share the same SHA in an unrelated repository/stack **B** tracked by the same Shipit instance. This is common in fork/mirror setups where the same commit SHA legitimately exists in multiple GitHub repositories (e.g., a fork tracking upstream, or a repo mirrored into two Shipit-managed remotes).

### Impact Explanation
`Commit#create_status_from_github!` feeds directly into deployability/mergeability logic: `MergeRequest#all_status_checks_passed?`/`#any_status_checks_failed?` use `StatusChecker` against the commit's `statuses`, and `Commit#add_status` schedules `ProcessMergeRequestsJob`, which can trigger an **automatic merge** (`MergeRequest#merge!`) once the required checks pass. [6](#0-5) [7](#0-6) 

If an attacker who controls (or has status-write access to) one Shipit-tracked repository can cause a commit in a *different* Shipit-tracked repository (sharing the same SHA) to receive a forged "success" status, they can satisfy that other stack's merge/deploy status requirements without ever being authorized on that repository — enabling an unauthorized merge or continuous deployment trigger. This lands in the "unauthorized deploy, rollback, or merge" Critical-impact bucket.

### Likelihood Explanation
Exploitation requires: (1) the attacker controls a repository/organization already registered in the target Shipit instance (so their `status` webhook is validly signed), and (2) a commit SHA collision between their repository and the victim stack's repository. Genuine SHA collisions of unrelated commits are cryptographically infeasible, but *identical* SHAs across repositories are common and easy to arrange deliberately: forks of the same upstream, mirrored repositories, or repositories that intentionally share history (monorepo splits) will contain many identical commit SHAs. An attacker who has push/status access to any repository sharing history with a victim stack (e.g., a public fork) can trigger status webhooks against shared commits without any Shipit credential (no session, ApiClient token, or knowledge of another org's `webhook_secret`).

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: resolve target commits through the `stacks` collection bound to the payload's own repository (e.g., `stacks.joins(:commits).where(commits: { sha: params.sha })` or equivalent), rather than querying `Commit` globally by `sha`. This restores the invariant that a webhook can only ever write to the repository/stack it was authenticated for.

### Proof of Concept
1. Register two repositories in the same Shipit instance: `victim/repo` (stack `production`) and `attacker/repo` (an accessible fork of `victim/repo`, sharing common history/SHAs), each under its own GitHub App/organization config with its own `webhook_secret`.
2. Identify a commit SHA that is deployable/mergeable-relevant in `victim/repo`'s stack and also exists (due to shared history) in `attacker/repo`.
3. As a legitimate collaborator on `attacker/repo`, set a commit status (e.g., via GitHub API `POST /repos/attacker/repo/statuses/{sha}`) with `state: success` and the `context` required by `victim/repo`'s `shipit.yml` (`ci.require`).
4. GitHub delivers a `status` webhook, correctly signed with `attacker/repo`'s org secret, to Shipit.
5. `WebhooksController#verify_signature` succeeds (signature matches attacker's own org).
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the shared-SHA commit that also belongs to `victim/repo`'s stack, and records the forged "success" status against it — potentially unblocking merge/deploy in `victim/repo`'s stack despite the attacker having no access there.
