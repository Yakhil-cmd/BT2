### Title
Cross-repository CI status forgery via webhook signature/commit-lookup mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves the target `Commit` purely by SHA, with no check that the commit belongs to the repository/organization whose secret was used to verify the request signature. In a multi-organization Shipit deployment, this lets an attacker who controls (or has legitimately registered) a GitHub App for **any** one tracked organization forge a valid HMAC signature for that organization, then supply an arbitrary `sha`/`state` payload that gets applied to a commit belonging to a **different** organization's stack, forging CI status and potentially triggering an unauthorized deploy.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the signature against using an attacker-supplied field of the very payload being verified: [1](#0-0) [2](#0-1) 

Shipit explicitly supports "Using Multiple GitHub Applications" where each organization has its own `webhook_secret`: [3](#0-2) 

Every mutating handler except one properly re-derives the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` before acting, e.g. the base `Handler#stacks` helper and the pull-request handlers: [4](#0-3) [5](#0-4) 

However `StatusHandler` never consults `repository`/`full_name` at all — it resolves the target purely by commit SHA across the entire commit table, ignoring which organization/app actually signed the request: [6](#0-5) 

This breaks the intended binding: **organization that authenticated (via `verify_webhook_signature` keyed on `repository.owner.login`) ≠ commit/repository that is written (looked up only by global `sha`)**. Because the `repository` object used for signature-org selection and the `sha`/`state` fields used for the actual mutation are independent, attacker-controlled keys inside the same unsigned-until-verified JSON body, an attacker who owns a legitimately connected GitHub App (their own org, with a webhook secret they know) can:
1. Compute a correct `X-Hub-Signature` for their own org's webhook secret over a POST body they fully control.
2. Set `repository.owner.login` in that body to their own org (so `Shipit.github(organization: repository_owner)` picks their secret and verification passes).
3. Set `sha` to the SHA of a commit that exists in a completely unrelated stack/organization (SHAs are public — visible in GitHub commit URLs, Shipit's UI, and the deploy stream).
4. Set `state`/`context`/`description` to forge a passing CI status for that unrelated commit.

`Commit.create_status_from_github!` persists this forged status with no further validation, as exercised in the existing test suite: [7](#0-6) 

### Impact Explanation
Commit statuses gate deploy safety and continuous delivery: `required_statuses`/`blocking_statuses` in the deploy spec determine whether a commit is `deployable?`, and `Stack.schedule_continuous_delivery` automatically deploys stacks with `continuous_deployment: true` once their head commit's statuses are green: [8](#0-7) [9](#0-8) 

By forging a "success" status on an arbitrary tracked commit belonging to an organization the attacker has no legitimate access to, an unprivileged attacker (who only needs to control one, unrelated GitHub App/org configured in the same Shipit instance) can make an otherwise-failing or unvetted commit appear deployable, and — for stacks with continuous deployment enabled — cause it to be deployed automatically with no human action. This is an unauthorized-deploy escalation crossing an organizational trust boundary, satisfying the Critical impact bar ("an unauthorized deploy").

### Likelihood Explanation
The precondition is that Shipit is configured to track more than one GitHub organization (a documented, supported configuration) and that the attacker controls (or can register) a GitHub App for at least one of them — a much lower bar than compromising the victim organization directly. No GitHub write access, Shipit session, or `ApiClient` token is required; the `/webhooks` endpoint is intentionally public and only signature-checked. All other webhook handlers correctly scope by `repository.full_name`, showing this is an isolated oversight in `StatusHandler` rather than an inherent design limitation, which increases confidence this is a genuine, exploitable defect rather than a false positive.

### Recommendation
In `StatusHandler#process`, re-derive the expected repository the same way other handlers do (via `payload.dig('repository', 'full_name')` and `Repository.from_github_repo_name`), and scope the `Commit` lookup to that repository's stacks before calling `create_status_from_github!`. Reject/ignore the event if the commit's stack repository does not match the repository asserted in the payload used for signature verification.

### Proof of Concept
1. Attacker registers/owns GitHub App "Attacker-Org" in the Shipit multi-org config, and knows `webhook_secret` for it (their own, legitimately configured, secret).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a commit belonging to Victim-Org/victim-repo tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "Attacker-Org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_of_attacker_org, raw_body)>` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "Attacker-Org")`, validates the signature successfully (it is genuinely correct for that org's secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the Victim-Org commit — and calls `create_status_from_github!`, persisting a forged "success" status on a commit the attacker has no access to, potentially unblocking/auto-triggering a deploy of that commit in Victim-Org's stack.

Note: I was not able to inspect `Commit#create_status_from_github!` or `deployable?` implementations directly (index truncation), so the exact downstream deploy-trigger mechanics (manual vs. fully automatic) could not be fully confirmed from source; this is inferred from `deploy_spec.rb`'s `required_statuses`/`blocking_statuses` and `Stack.schedule_continuous_delivery`. Starting a full Devin session would allow reading these files in their entirety to confirm the exact deploy-gating logic.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
