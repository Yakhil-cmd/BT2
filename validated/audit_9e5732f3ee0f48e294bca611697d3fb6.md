### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` binds an `ApiClient`'s authorization to a specific `Stack` via `current_api_client.stack_id`, exposing only stacks in that scope through the `stacks`/`stack` helper methods. `Api::CCMenuController` overrides `stack` to look up `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` class, breaking the binding between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`Api::BaseController` defines the scoping contract for all API endpoints: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` only within that restricted relation. Every other resource controller in the API namespace (e.g. `DeploysController`, `StacksController`) relies on this inherited `stack`/`stacks` method, so a token scoped to stack A cannot address stack B.

`Api::CCMenuController`, however, defines its own `stack` method that ignores the scoped `stacks` relation entirely: [2](#0-1) 

`require_permission :read, :stack` only checks that the token holds the `read:stack` permission string; it never checks which stack the client is bound to. Because `stack` calls `Stack.from_param!(params[:stack_id])` on the global `Stack` scope instead of `stacks.from_param!(...)`, any valid token with `read:stack` permission — even one created with a `stack_id` restricting it to a single stack — can pass an arbitrary `stack_id` in the URL (route: `GET /api/stacks/*stack_id/ccmenu`) and receive that other stack's deploy state. [3](#0-2) 

### Impact Explanation
This crosses the "stack a token authorizes vs. stack it touches" trust boundary. An `ApiClient` deliberately scoped to a single stack (`stack_id` set, e.g. fixture `here_come_the_walrus`) is meant to only ever see that one stack's data, per `stacks_controller_test.rb` behavior ("an api client scoped to a stack will only see that one stack"). The CCMenu endpoint defeats this: it discloses `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl` for any stack in the installation to a token that should only have visibility into one stack. This matches the "unauthorized read of stack state / deploy output" High-impact category, since it is an escalation beyond the token's intended authorization scope. [4](#0-3) 

### Likelihood Explanation
No special conditions are required beyond possessing any valid API token with `read:stack` permission (even one intentionally restricted to a single stack by the operator, expecting isolation). The attacker only needs to know or guess another stack's `owner/repo/environment` path segment used as `stack_id`, which is often predictable/public (GitHub repo names).

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` on the unscoped class, so CI status disclosure respects the same per-token stack binding enforced everywhere else in the API.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: <stack-A.id>` with `permissions: ['read:stack']`.
2. Authenticate with that client's token (`Authorization: Basic` or `?token=`).
3. Request `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu` for an unrelated stack B.
4. Observe `200 OK` with stack B's `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc., despite the token being authorized only for stack A — confirmed by the absence of any scope check in `Api::CCMenuController#stack` (compared to `Api::BaseController#stack`, which is scope-aware). [5](#0-4)
