### Title
`StatusHandler#process` matches commits by SHA globally across all stacks with no repository binding, letting an attacker's own webhook mark another tenant's `MergeRequest#head` commit as `success?` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no filtering by `repository_name`/`stacks` from the inbound payload, unlike `PushHandler` which scopes via `stacks.not_archived.where(branch:)`. Because commit SHAs are content-addressed, the same SHA can legitimately exist as a `Commit` row in two unrelated `Stack`s (e.g., shared git ancestry between a victim's repo and an attacker's fork/registered repo), so a status event carrying repository A's identity can silently write a `Status` against a commit belonging to stack B.

### Finding Description
The claimed binding is: `payload.dig('repository','full_name')` (the repo that authenticates/signs the webhook) **must equal** `commit.stack.repository.full_name` (the repo whose merge queue consults the resulting `Status`).

Tracing the code:
- `Handler#stacks` and `Handler#repository_name` exist precisely to enforce this binding [1](#0-0) , and `PushHandler` uses it (`stacks.not_archived.where(branch:)`) [2](#0-1) .
- `StatusHandler#process` never calls `stacks` or `repository_name`; it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This query is global across the entire `commits` table, not scoped to any stack tied to the payload's repository.
- `create_status_from_github!` writes the status using `commit.stack_id` (the commit's actual owning stack), and this stack_id is derived solely from whichever `Commit` row matched the SHA — not from the webhook's `repository` field [4](#0-3) .
- `WebhooksController#verify_signature` only authenticates that the request was signed by the GitHub App/org named in `repository.owner.login` of the payload [5](#0-4) . It does **not** verify that the named repository is bound to the commit(s) being updated. So an attacker who legitimately controls their own GitHub org/repo that Shipit is configured to trust (their own tenant) can produce a fully-valid, correctly-signed `status` webhook (GitHub itself signs it) for **their own** repository/commit context, naming their own repo.
- If that SHA also exists as a `Commit` row belonging to a different stack B (shared history — e.g. attacker forked victim's repo, or a shared upstream commit reachable from both repos' branches, or a rebased/duplicate SHA scenario), `StatusHandler#process` updates/creates a `Status` on stack B's commit, driven entirely by the attacker's own repo's CI/status API call, with `state: success` and any `context` the attacker chooses.
- `MergeRequest#all_status_checks_passed?` reads `head.statuses_and_check_runs` for the victim's `MergeRequest.head` commit [6](#0-5) . If the attacker-injected `Status` satisfies `StatusChecker`/`required_statuses` (e.g. matching `context` used by the victim stack's deploy spec, or simply no required contexts configured so any success is enough), `all_status_checks_passed?` returns true and `reject_unless_mergeable!`'s `any_status_checks_failed?`/`any_status_checks_missing?` guard passes [7](#0-6) , letting `ProcessMergeRequestsJob` call `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` against **stack B's real repository**, using stack B's own `github_access_token` [8](#0-7) , [9](#0-8) .

Existing guards fail because: `verify_signature` authenticates the webhook's claimed org/repo, not the target of the DB write; `Handler#stacks`/`repository_name` exist but are simply unused by `StatusHandler`; there is no unique-per-stack constraint preventing the same SHA existing in multiple `Commit` rows across different stacks (SHAs are unique only within `Commit` semantics by content, not enforced unique globally by the schema in a way that blocks this).

### Impact Explanation
An attacker who fully controls a legitimately-configured Shipit tenant (their own registered repo/org) can, via ordinary and authorized actions on their own repository (setting a commit status through GitHub, which then genuinely and correctly triggers a signed `status` webhook to Shipit), cause a `Status` row to be written against a **different tenant's** commit whenever a SHA collision/overlap occurs between the two repositories' commit histories (a realistic scenario for forks or shared upstream branches). This can push a victim `MergeRequest` past CI-passed checks, causing an unauthorized `merge_pull_request` call against the victim's real GitHub repository using the victim's own `github_access_token` — this is a cross-tenant, unauthorized-merge impact ("a payload for one repository mutating another's stack/commit... an unauthorized deploy, rollback or merge"), matching the Critical impact category. It is repeatable against any stack pair that shares a SHA (e.g. any fork relationship), not a one-off.

### Likelihood Explanation
Preconditions: attacker must control a Shipit-registered repository (their own tenant, which is a normal, permitted configuration — not requiring any secret), and the target victim commit SHA must also exist as a `Commit` row in the victim's stack (realistic for forks/shared branch history, or any scenario where the same commit is synced into two stacks). No Shipit secrets, session, or GitHub App credentials are needed beyond what the attacker already legitimately has for their own repo. The attack is inexpensive (one GitHub status API call on their own repo) and repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`: resolve commits only via `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` (or equivalent `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a `Status` can only be attached to a commit belonging to a stack whose bound repository matches `repository_name` from the verified payload.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (illustrative)
test "status webhook for attacker's repo cannot mark another stack's commit as successful" do
  stack_b = shipit_stacks(:shipit) # victim stack, repo "victim/repo"
  sha = 'deadbeef' * 5
  commit = stack_b.commits.create!(sha:, message: 'test', authored_at: Time.now, committed_at: Time.now)
  merge_request = stack_b.merge_requests.create!(number: 42, head: commit, merge_status: 'pending')

  # Attacker's webhook payload claims a *different* repository (their own tenant),
  # but references the *same* sha as the victim's commit.
  payload = {
    'sha' => sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert merge_request.reload.head.reload.success?, "commit incorrectly marked successful via unrelated repo's webhook"
  assert_predicate merge_request, :all_status_checks_passed?
  # Assert the binding is broken: payload repository ("attacker/unrelated-repo")
  # != stack_b.repository.full_name ("victim/repo"), yet the status was written to stack_b's commit.
  refute_equal payload.dig('repository', 'full_name'), stack_b.repository.full_name
end
```
This demonstrates that `StatusHandler#process` writes a `Status` for `stack_b`'s commit despite the webhook payload naming an entirely unrelated repository, breaking the required binding.

      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
