### Title
Webhook signature is verified against the organization owner in the payload while the affected repository/stack is selected from a different, unchecked field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against using `params.dig('repository', 'owner', 'login')` (or `organization.login`), but every event `Handler` subclass resolves the `Repository`/`Stack` that actually gets mutated using a completely different, independently-controlled JSON field: `payload.dig('repository', 'full_name')`. Nothing cross-checks that the organization whose secret validated the signature actually owns the repository the handler acts on. An attacker who legitimately controls one Shipit-registered GitHub organization (and therefore knows that organization's own `webhook_secret`) can post a correctly-signed request directly to the public `/webhooks` endpoint whose `repository.owner.login` matches their own org, but whose `repository.full_name` names a stack belonging to a different, victim organization onboarded to the same Shipit instance.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . This chooses which organization's `webhook_secret` (configured per-organization, see `@webhook_secret = @config[:webhook_secret].presence` in `lib/shipit/github_app.rb`) is used to validate the raw HMAC-SHA1 signature over the whole body.

Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs in `WebhooksController#create` [3](#0-2) . Every base `Handler` (used by `PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolves the stacks it will act on via:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`repository.owner.login` (used for signature verification / secret selection) and `repository.full_name` (used to select the `Repository`/`Stack` acted on) are two independent fields inside the same attacker-supplied JSON body. Real GitHub webhooks always keep them consistent, but nothing in this code enforces that. Because the HMAC covers the *raw bytes* of whatever body is sent — not a specific parsed field — a party who knows the secret for *any one* organization configured in the Shipit instance can produce a validly-signed request whose `repository.owner.login` matches that organization while `repository.full_name` points at an entirely different organization's repository/stack. `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` [5](#0-4)  on the victim stack, and similarly the `status`/`check_suite`/`pull_request` handlers operate on the victim's `Repository.from_github_repo_name` result — all gated only by the attacker's own organization's secret.

This is the direct analog to the CVE's "tar.gz plugin declares its own path, but the write target is derived from that same untrusted entry without validating it stays within the intended directory" pattern: here, the "authenticated scope" (the organization whose secret validated the signature) is never bound to the "acted-upon scope" (the repository/stack the parsed payload names).

### Impact Explanation
Meets the High-severity bar: "escalation into `Shipit.github_teams` authorization" and (depending on downstream handler effects such as forged CI `status` events triggering `ContinuousDeliveryJob`, or `membership`/`pull_request` handlers mutating victim-org state) can reach the Critical bar of "an unauthorized deploy, rollback or merge," since a forged `status` webhook accepted for a victim stack's existing commit can flip CI state to `success` and, if continuous deployment is enabled on that stack, trigger an automatic deploy of that commit without any real CI having passed.

### Likelihood Explanation
Requires the attacker to control (and know the webhook secret of) at least one organization/repository already onboarded to the same multi-tenant Shipit instance as the victim — a realistic scenario for shared/self-service Shipit deployments serving many orgs, since organization owners configure and thus know their own GitHub App/webhook secret. No GitHub App private key, Shipit session, or `ApiClient` token is required — only a direct HTTP POST to the public `/webhooks` endpoint with a body they sign themselves.

### Recommendation
In `WebhooksController`/`Handler`, derive both the signing organization and the acted-upon repository from the *same* trusted field, and reject the event if `repository.full_name`'s owner segment does not match the organization whose secret validated the signature (e.g., compare `repository.full_name.split('/').first` against `repository_owner` before dispatching to handlers).

### Proof of Concept
1. Attacker legitimately owns organization `attacker-org`, onboarded to the shared Shipit instance, and knows `attacker-org`'s configured `webhook_secret`.
2. Attacker crafts a JSON body for a `status` (or `push`) event:
```json
{
  "sha": "<existing-undeployed-sha-of-victim-stack>",
  "state": "success",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(attacker-org secret, body)` and sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<computed>
```
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and validates successfully because the attacker signed with `attacker-org`'s real secret [6](#0-5) .
5. The corresponding handler resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and processes the forged status/push against the victim's stack, with no verification the two organizations match.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
