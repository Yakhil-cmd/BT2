Now I have enough to establish the vulnerability precisely.

## Analysis

The multi-org GitHub App configuration schema in `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) selects a per-organization `webhook_secret` keyed on an organization name that the `WebhooksController` derives **from the untrusted webhook body itself**, not from a value that is bound to the signature's provenance: [1](#0-0) [2](#0-1) 

`repository_owner` is only used to pick *which secret to check the HMAC against*; `GitHubApp#verify_webhook_signature` explicitly treats an unconfigured/blank secret as automatically valid: [3](#0-2) 

Meanwhile, every webhook handler resolves the actual target `Stack`/`Repository` using a **different, independently attacker-controlled field**: `payload.dig('repository', 'full_name')`: [4](#0-3) [5](#0-4) 

The binding the system relies on is `repository.owner.login == repository.full_name's owner`, i.e. that the organization used to select/verify the signing secret is the same organization whose repository is acted upon. Nothing enforces this equality — both are just two different JSON keys inside the same unauthenticated body, and only one of them is consulted before the signature check decides pass/fail. In a multi-org deployment (as documented in `docs/setup.md` and demonstrated by `test/dummy/config/secrets_double_github_app.yml`, which shows one org configured with `webhook_secret: # nil`), an attacker who can reach `/webhooks` can:

1. Set `repository.owner.login` (or `organization.login`) to an org that Shipit has configured **without** a `webhook_secret` (or one whose secret the attacker knows).
2. Set `repository.full_name` to `otherorg/repo` — a completely different, secret-protected organization's repository that has a Stack configured in the same Shipit instance.

Because `verify_signature` only ever looks at `repository_owner` to pick the `GitHubApp` instance, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank, the forged request sails through signature verification while the handler dispatches against the victim org's repository/stack using `repository.full_name`.

This lets an unprivileged external attacker forge events (e.g. `push` → `GithubSyncJob`, `pull_request` closed/reopened/labeled → archiving/unarchiving review stacks, `status`/`check_suite` → commit status mutation) for any org's stack, as long as *any* org in the multi-org config lacks (or leaks) a webhook secret — without needing that specific org's secret at all.

### Title
Webhook signature verification is keyed off `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name`, letting an attacker pick a weak/unconfigured org's secret to forge events for a different, protected org's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses which GitHub App/webhook secret to validate a request's HMAC against using `repository_owner` (`repository.owner.login` or `organization.login` from the JSON body), but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Stack`/`Repository` to mutate using the separate `repository.full_name` field from the same body. These two fields are never checked for consistency.

### Finding Description
`verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(header, raw_post)`. `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally `unless webhook_secret` is configured for that organization. In multi-org deployments (see `docs/setup.md` "Use this configuration schema if you are configuring multiple Github applications", and `test/dummy/config/secrets_double_github_app.yml` where `OrgTwo` has `webhook_secret: # nil`), it is plausible/documented that some orgs are configured without a webhook secret, or with a secret the attacker otherwise obtains for that one org only.

Handlers such as `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) and the PR handlers use `Handler#repository_name` / `params.repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) to look up `Repository.from_github_repo_name` and act on its stacks — a value structurally independent from `repository_owner` used for signature selection.

Equality broken: `organization authenticated by verify_signature == organization whose repository is written by the handler`. Before the attack, these always coincide for legitimate GitHub-originated webhooks (GitHub always sends a consistent payload). After a crafted request, `repository.owner.login` can name org A (weak/no secret) while `repository.full_name` names `"B/some-repo"`, breaking the equality while still passing verification.

### Impact Explanation
This crosses a repository/authentication boundary: an attacker with no credentials can trigger stack actions (sync from GitHub, archive/unarchive review stacks, mutate commit status/deployable status) for a stack belonging to an organization they don't control and for which they don't hold the correct webhook secret, as long as some other configured organization's secret is weak or absent. This matches "escalation into authorization" / effectively an unauthorized action against protected stack state, satisfying the High-impact bar (unauthenticated manipulation of stack state across the intended per-org trust boundary).

### Likelihood Explanation
Requires a multi-org Shipit deployment where at least one configured organization has no `webhook_secret` (explicitly supported/documented configuration) or a leaked one. Given that setup, the attack requires only crafting and POSTing a JSON body to the public `/webhooks` endpoint — no authentication, no repository access, no token.

### Recommendation
Bind signature verification to the same field the handlers use for authorization: verify the signature using the GitHub App config associated with `repository.full_name`'s owner (or explicitly re-validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs: `OrgA` (no `webhook_secret`) and `OrgB` (has a stack and a webhook secret), per the multi-org schema in `docs/setup.md`.
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` for OrgB, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgB/protected-repo", "owner": { "login": "OrgA" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")`; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the signature header/body.
4. `PushHandler` runs using `repository.full_name = "OrgB/protected-repo"`, triggering `GithubSyncJob` against `OrgB`'s stack.
