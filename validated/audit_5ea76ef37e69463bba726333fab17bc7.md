### Title
Webhook signature verification binds to `organization.login`/`repository.owner.login` while the stack-mutating handler binds to `repository.full_name`, letting an attacker impersonate a secretless org to write to any repository's stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret using `repository.owner.login` with a fallback to `organization.login`, while `LabeledHandler` (via `Handler#repository_name` / `LabeledHandler#repository`) resolves the actual `Stack`/`ReviewStack` to mutate using `repository.full_name` alone. `ExplicitParameters` in `LabeledHandler.params` never requires `repository.owner.login` and never cross-checks it against `repository.full_name`, so these two independently-read fields can point at different organizations. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `organization used to select verify_webhook_signature's secret (repository.owner.login || organization.login)` == `organization implied by repository.full_name used to load the Repository/Stack`. Nothing in the code enforces this.

Path:
1. `WebhooksController#create` parses raw JSON and dispatches to handlers only after `verify_signature` passes. [4](#0-3) 
2. `verify_signature` computes `repository_owner` from the raw, unvalidated JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')`, then calls `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(...)`. [5](#0-4) [1](#0-0) 
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank: `return true unless webhook_secret`. [6](#0-5) 
4. Only after signature verification passes does `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` run, instantiating `LabeledHandler`, whose `ExplicitParameters` schema requires only `repository.full_name` (`String`) — `repository.owner` is never mentioned in the schema at all. [2](#0-1) 
5. `LabeledHandler#repository` resolves the target `Repository` purely from `params.repository.full_name`, independent of whatever `organization`/`owner` was used for signature verification: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`. [3](#0-2) 
6. `LabeledHandler#stack` then builds a `ReviewStackAdapter` scoped to `repository.review_stacks` and `#handle` calls `stack.archive!`/`stack.unarchive!` on it. [7](#0-6) 

Exploit: an attacker who controls (or can freely name) an `organization.login` value that Shipit has configured under `secrets.github` **without a `webhook_secret`** (nothing in the code enforces that every configured org must set `webhook_secret` — see `GitHubApp#initialize`, which does `@webhook_secret = @config[:webhook_secret].presence`, silently accepting `nil`) can POST directly to `/webhooks` with:
- header `X-Github-Event: pull_request`
- a body that omits `repository.owner` entirely, sets `organization.login` to the secretless org, and sets `repository.full_name` to `"victim-org/victim-repo"` (a repo belonging to a different, properly-secured org).

`repository_owner` falls back to `organization.login` (the secretless org), `verify_webhook_signature` short-circuits to `true` because that org's `webhook_secret` is blank, and the request is accepted with no valid HMAC needed. `ExplicitParameters` then happily parses the body because it never required `repository.owner` and never cross-validates it against `organization.login`, and `LabeledHandler` proceeds to archive/unarchive/create the victim org's `ReviewStack` based on `repository.full_name`.

Existing guards do not close this gap: `drop_unhandled_event` only checks the event name; `verify_signature` deliberately supports multi-tenant per-org secrets but never checks that the *acted-upon* repository (`repository.full_name`) belongs to the same org that was used to select the secret; `ExplicitParameters` is a type/presence validator only and is not invoked until after signature verification succeeds, and even then adds no cross-field check.

### Impact Explanation
A successful request causes the attacker's crafted webhook to mutate a `Stack`/`ReviewStack` belonging to a different, unrelated organization/repository than the one whose (absent) secret was used for authentication — i.e., "a payload for one repository mutating another's stack," which is explicitly listed as Critical impact. Concretely, an unprivileged internet requester can trigger `Stack#archive!`/`Stack#unarchive!` (and, via `unlabeled`/other PR handlers using the same pattern, `ReviewStack` creation/deprovisioning) on any repository configured in the target Shipit instance, as long as any org in that instance's config lacks a `webhook_secret`. This is repeatable against arbitrary victim repositories by simply varying `repository.full_name` in the POST body, and the blast radius spans every tenant/org hosted by the same Shipit instance. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The attack requires no Shipit session, token, or GitHub secret, matching the stated attacker model. It does require a config precondition: at least one organization registered in Shipit's `secrets.github` (or the legacy single-org config) with `webhook_secret` blank/absent — nothing in `Shipit.github_app_config`/`GitHubApp#initialize` prevents this, and it's a plausible misconfiguration (e.g., staging orgs, orgs onboarded before rotating a secret in, or intentionally secretless dev/test orgs). Given that precondition, the attack is trivial and fully repeatable: one POST per target repository/label transition, no rate limiting encountered, no GitHub involvement needed at all since the request goes directly to `/webhooks`. [10](#0-9) 

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#initialize`/each handler's `params` schema), require and validate that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to any handler; reject the webhook (422) on mismatch. Additionally, enforce (e.g., via a config-loading assertion) that every organization entry under `secrets.github` defines a non-blank `webhook_secret`, and change `GitHubApp#verify_webhook_signature` to fail closed (return `false`) rather than `true` when no secret is configured, unless the app is explicitly running in single-org/no-signing mode.

### Proof of Concept
Minitest plan (no live GitHub, direct POST to the mounted `/webhooks` route):
1. Configure `test/dummy` secrets with two orgs: `victim-org` (has `webhook_secret: "s3cr3t"`) and `attacker-org` (no `webhook_secret` key at all).
2. Create `Shipit::Repository` `victim-org/victim-repo` with `provisioning_behavior` set so an existing open PR's label change triggers `archive!`; create a matching `Shipit::ReviewStack` for `pr123`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature` (or an arbitrary bogus one), and JSON body:
   - `action: "labeled"`, `number: 123`
   - `pull_request: { id, number: 123, url, title, state: "open", additions, deletions, head: { sha, ref }, user: { login }, assignees: [], labels: [{ name: <provisioning label> }] }`
   - `organization: { login: "attacker-org" }` (no `repository.owner` key present)
   - `repository: { full_name: "victim-org/victim-repo" }`
   - `sender: { login: "attacker" }`
4. Assert both sides of the binding independently: `repository_owner` resolves to `"attacker-org"` (via the controller's fallback logic) while `LabeledHandler#repository` resolves to the `victim-org/victim-repo` `Repository` record — i.e. assert they differ.
5. Assert the response is `200 OK` (not `422`), i.e. `verify_webhook_signature` returned `true` for `attacker-org` despite no valid secret being presented.
6. Assert `ExplicitParameters` parsing succeeded (`LabeledHandler.new(payload).params` does not raise, since `repository.owner` was never required).
7. Assert the victim's `ReviewStack` for `pr123` under `victim-org/victim-repo` transitioned state (e.g., `archived?` became `true`), proving a cross-org write occurred without the attacker ever knowing `victim-org`'s `webhook_secret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
