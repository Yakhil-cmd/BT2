### Title
Attacker-controlled linked-branch name allows git-option injection via unguarded `git -C <worktree> checkout <branch>` - (File: pkg/cmd/pr/shared/worktree.go)

### Summary
`branchName` returned from `api.CreateLinkedBranch`/`api.ListLinkedBranches` (attacker-controlled GraphQL response) flows unsanitized into `checkoutBranch()` in `pkg/cmd/issue/develop/develop.go` and then into `prShared.WorktreeCheckoutCommands`, where the "reuse existing worktree + branch exists" path builds `git -C <path> checkout <branch>` without a `--` separator, so a branch name starting with `-` is parsed as an option to `git checkout` rather than a ref name.

### Finding Description
`checkoutBranch(opts, branchRepo, checkoutBranch, worktreeTarget)` in `pkg/cmd/issue/develop/develop.go:353` receives `checkoutBranch` from `developRunCreate`, which is either `createdBranchName` from `api.CreateLinkedBranch` or a name found via `findExistingLinkedBranchName`/`api.ListLinkedBranches` — both populated directly from `node.Ref.Name` / `mutation.CreateLinkedBranch.LinkedBranch.Ref.Name` in `api/queries_branch_issue_reference.go:15-90`, with no character/leading-dash validation.

That value is passed to `prShared.WorktreeCheckoutCommands(gc, worktreeTarget, checkoutBranch, ...)` (`develop.go:388-393`). In `pkg/cmd/pr/shared/worktree.go:38-52`:
- The two `worktree add` command variants correctly place `branch`/`target.Path` after a `--` separator (lines 49, 51), preventing option injection.
- However, when `target.Reuse` is true and the branch already exists locally, the returned command is:
  ```go
  return [][]string{{"-C", target.Path, "checkout", branch}}, true   // line 43
  ```
  There is **no `--` separator** here. `branch` is passed as a bare positional argument to `git checkout`. If `branch` starts with `-` (e.g. `-b`, `--orphan`, `--patch`, `--conflict=...`), git will parse it as an option to `checkout` instead of a ref name.

This is executed by `runGitCommands` → `client.Command(ctx, args...)` (`develop.go:422-433`), with no argument sanitization at the `git.Client` layer either (`git/client.go:666-668`'s plain `CheckoutBranch` has the same unguarded pattern, confirming this is a systemic gap rather than an isolated bug).

Compare this to `pkg/cmd/pr/checkout/checkout.go:150-152`, which explicitly guards against this exact class of bug:
```go
if strings.HasPrefix(pr.HeadRefName, "-") {
    return fmt.Errorf("invalid branch name: %q", pr.HeadRefName)
}
```
No equivalent check exists in `pkg/cmd/issue/develop/develop.go`, so the `gh issue develop` reuse-worktree path is unprotected against attacker-controlled ref names beginning with `-`.

Regarding the path-traversal portion of the question: `target.Path` originates solely from the victim's own `--worktree` CLI argument (`opts.Worktree`), not from attacker-controlled data, and is further validated by `ensureWorktreePathSafe` and `resolveWorktreeTarget` in `worktree.go:22-91` (rejecting symlinks, paths inside a different repo, or paths inside an existing worktree). There is no attacker-controlled input that can redirect `target.Path` itself, so the path-confinement portion of the reported concern is not exploitable; the confirmed issue is limited to option injection via the branch name.

### Impact Explanation
This is a local git-argument/option-injection primitive, not remote code execution: the reachable options on `git checkout <injected-arg>` (e.g., `-b<name>`, `--orphan`, `--ours`/`--theirs`, `--conflict=<style>`) let an attacker-controlled linked-branch name change local checkout behavior (e.g., force-create/switch to a branch of the attacker's choosing, alter merge-conflict resolution style) inside the victim's already-existing worktree. It does not by itself achieve arbitrary file write outside the worktree or process execution, since `checkout` lacks options that spawn external commands. Best matches a low/informational "unexpected behavior via crafted git ref name" class rather than the higher-severity "arbitrary file write" or "code execution" impact implied by the question's framing.

### Likelihood Explanation
Requires the victim to run `gh issue develop <issue> --worktree <path> --checkout` against an issue whose linked branch was already created/renamed via a malicious/compromised GraphQL host response, and specifically hit the "worktree path already exists and reused, and branch already exists locally" combination (`target.Reuse == true && branchExists == true`) to trigger the unguarded `checkout branch` call — the two `worktree add` paths are already safe. This is a narrow but real precondition; it is deterministic and repeatable once met.

### Recommendation
Add a `--` separator before the branch argument in the reuse+branch-exists case in `pkg/cmd/pr/shared/worktree.go:43`:
```go
return [][]string{{"-C", target.Path, "checkout", "--", branch}}, true
```
Additionally, apply the same leading-dash rejection used in `pkg/cmd/pr/checkout/checkout.go:150-152` to linked-branch names in `pkg/cmd/issue/develop/develop.go` (validate `checkoutBranch` before use in `checkoutBranch()`), and audit `git/client.go`'s other branch-name-consuming methods (`CheckoutBranch`, `CheckoutNewBranch`, `DeleteLocalBranch`) for the same missing `--` separator.

### Proof of Concept
```go
// pkg/cmd/pr/shared/worktree_test.go
func TestWorktreeCheckoutCommands_ReuseExistingBranch_OptionInjection(t *testing.T) {
    cs, teardown := run.Stub()
    defer teardown(t)
    cs.Register(`git rev-parse --verify refs/heads/-b`, 0, "") // branchExists = true

    client := &git.Client{GitPath: "/some/path/git"}
    commands, branchExists := WorktreeCheckoutCommands(
        client,
        WorktreeTarget{Path: "/path/to/wt", Reuse: true},
        "-b", // attacker-controlled linked branch name
        "origin/-b",
    )

    assert.True(t, branchExists)
    // FAILS today: commands == [][]string{{"-C", "/path/to/wt", "checkout", "-b"}}
    // Expected after fix: a "--" separator before the branch argument.
    assert.Equal(t, [][]string{{"-C", "/path/to/wt", "checkout", "--", "-b"}}, commands)
}
```
Expected assertion: without the fix, `commands` contains `checkout` immediately followed by the raw attacker-supplied string with no `--`, so `git checkout -b` is executed with `-b` parsed as an option instead of a ref, rather than erroring or checking out a branch literally named `-b`.
