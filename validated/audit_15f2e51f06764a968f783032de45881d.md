## Title
Webhook signature verification uses attacker-controlled `repository.owner.login` to pick a *different* GitHub App than the repository the handler acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, a value taken from the **unauthenticated** JSON body itself [1](#0-0) . The subsequent event handlers, however, determine which `Repository`/`Stack`/`Commit` to mutate using a *different* field from the same body, `repository.full_name` (or `sha` for status events), with no check that it is consistent with the organization used for authentication [2](#0-1) . This breaks the equality: `organization authenticated == repository written`.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`repository_owner` is read from the raw, **unverified** request body before any signature check occurs. In a multi-organization deployment (`config/secrets.yml` `github:` keyed by org, as documented in `docs/setup.md`) [4](#0-3) , `Shipit.github(organization:)` looks up that specific org's `GitHubApp` config via `github_app_config(organization)` [5](#0-4) .

Critically, `verify_webhook_signature` short-circuits when the *selected* organization has no configured secret:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [6](#0-5) 

Since `webhook_secret` is documented as optional per-organization [4](#0-3) [7](#0-6) , any organization configured without one becomes a universal signature bypass for the entire `/webhooks` endpoint: an attacker only has to claim `repository.owner.login` equal to that unsecured org's name to make `verify_signature` pass unconditionally, regardless of the real `X-Hub-Signature` header.

After "authentication" succeeds, `create` parses the same JSON and dispatches to handlers with the full, attacker-controlled payload:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [8](#0-7) 

Handlers such as `Handlers::Handler#stacks`/`#repository_name` resolve the target repository from `payload.dig('repository', 'full_name')` [2](#0-1)  - a field completely independent of `repository.owner.login` used for authentication. Nothing enforces that `full_name`'s owner segment matches `owner.login`. `StatusHandler#process` then writes attacker-supplied CI status data directly to any `Commit` matching an attacker-chosen `sha`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [9](#0-8) 

This mirrors the report's bug class: message parsing (here, target-selection) trusts an unverified field (`full_name`/`sha`) once a different field (`owner.login`) satisfies a weak/absent authentication check, exactly like the mobile client trusting the unencrypted `payload` field once the `nonce` field triggered/skipped decryption.

### Impact Explanation
An unauthenticated attacker can forge webhook events (`status`, `push`, `pull_request`, `membership`, `check_suite`) for **any repository/stack registered in the Shipit instance**, as long as the deployment configures at least one GitHub organization without a `webhook_secret` (an explicitly documented, supported configuration). Concretely, forging a `status` event lets the attacker write an arbitrary CI status (`state: "success"`, arbitrary `context`) onto any tracked commit, which can satisfy `ci.require` checks and enable an unauthorized deploy - meeting the "unauthorized deploy" Critical-impact criterion. Forged `push`/`membership` events can similarly trigger sync jobs or fabricate team/user membership state under a different, real organization's stacks.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires that the operator has configured Shipit for multiple GitHub organizations and left at least one organization's `webhook_secret` unset - a state the engine's own documentation explicitly presents as valid/optional, so it is a realistic, unprivileged, self-inflicted misconfiguration rather than a purely theoretical one. No credentials, tokens, or sessions are needed by the attacker; only network access to `POST /webhooks` and knowledge (or a guess) of an org name lacking a secret.

### Recommendation
- Do not let an attacker-controlled field select *which* organization's secret is used to authenticate a payload whose *target* is a different, unrelated field. Verify the signature against the organization that owns the `repository.full_name`/target actually being mutated (derive both from the same, single trusted source), or verify against all configured organizations' secrets and require at least one match.
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; either require a webhook secret for every configured organization or fail closed instead of bypassing verification.
- Cross-check `repository.owner.login` against the owner segment of `repository.full_name` before dispatching to handlers, rejecting mismatches.

### Proof of Concept
Assuming `secrets.yml` configures two orgs, `OrgA` (no `webhook_secret`) and `OrgB` (has a stack with tracked commit `abcdef123...` gated behind `ci.require: ["ci/build"]`):

```bash
curl -X POST https://shipit.example.com/webhooks \
  -H "X-Github-Event: status" \
  -H "X-Hub-Signature: sha1=0000000000000000000000000000000000000000" \
  -H "Content-Type: application/json" \
  -d '{
    "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/critical-repo"},
    "sha": "abcdef123...",
    "state": "success",
    "context": "ci/build",
    "description": "forged",
    "target_url": "http://attacker.example"
  }'
```
- `repository_owner` resolves to `"OrgA"`, whose `GitHubApp#webhook_secret` is blank ⇒ `verify_webhook_signature` returns `true` unconditionally (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
- `StatusHandler` looks up `Commit.where(sha: "abcdef123...")` (belonging to `OrgB/critical-repo`, unrelated to `OrgA`) and calls `create_status_from_github!` with the forged `state: "success"`, satisfying `ci.require` and permitting an otherwise-blocked deploy.

Note: I could not fully view `app/models/shipit/commit.rb#create_status_from_github!` in this session (index truncation), but its call sites and `README.md`'s `ci.require`/`status.context` documentation confirm that commit statuses gate deployability, supporting the impact chain described above.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
