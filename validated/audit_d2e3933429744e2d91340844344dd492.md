### Title
AA trigger queue can be permanently stalled by a single unrecoverable trigger, blocking all subsequent triggers - (File: aa_composer.js)

### Summary
`aa_composer.js` maintains a FIFO-style queue of pending AA triggers in the `aa_triggers` table, processed by `handleAATriggers()` via `async.eachSeries`, in strict deterministic order (`ORDER BY aa_triggers.mci, level, aa_triggers.unit, address`). A queue row is deleted only after `handleTrigger()` fully completes and calls back into `onDone`. If processing of any single queued trigger fails to call back (e.g., due to an uncaught JS exception rather than a graceful `bounce()`), the `async.eachSeries` loop for that batch never advances, so no later trigger in that batch is ever processed. This mirrors the reported `KangarooVault` pattern where `queuedWithdrawalHead` never advances past a reverting entry, denying service to everyone queued behind it.

### Finding Description
`handleAATriggers()` reads all pending rows from `aa_triggers` and processes them one at a time with `async.eachSeries`, calling `handlePrimaryAATrigger()` for each row and only calling the iterator's `cb` (which lets `eachSeries` move to the next row) once `handleTrigger()`'s `onDone` fires and the `DELETE FROM aa_triggers ...` for that row completes: [1](#0-0) [2](#0-1) 

The normal AA error path (`bounce()`) is designed to gracefully finish trigger processing (rollback state, still call `finish()`/`addResponse()`/`onDone`), which lets the queue advance normally, as seen in the "remote function that fails" test: [3](#0-2) 

However, several code paths inside `handleTrigger()` and the formula evaluator are not wrapped in `bounce()`'s graceful-recovery machinery and instead `throw Error(...)` synchronously (uncaught), for example:
- The cache-consistency check in `handlePrimaryAATrigger()` itself: `if (!objUnitProps) throw Error(...)` [4](#0-3) 
- The batch-write failure check: `if (err) throw Error("AA composer: batch write failed: "+err);` [5](#0-4) 
- An unguarded invariant check inside `formulaParser.evaluate()`, called synchronously from many places in `handleTrigger()` (`evaluateAA`, `replace`, `executeStateUpdateFormula`, etc.) without any surrounding `try/catch` at the call sites: `if (!ValidationUtils.isPositiveInteger(objValidationState.last_ball_timestamp)) throw Error(...)` [6](#0-5)  called from e.g. [7](#0-6)  and [8](#0-7) 

Because these paths are not funneled through `bounce()`, an exception thrown here propagates out of the synchronous call stack of `handleTrigger`/`handlePrimaryAATrigger` without ever invoking `onDone`/`cb`. Since `handleAATriggers` is invoked deterministically by every node reaching the same stabilized MCI (from `main_chain.js`'s `calcCommissions`/`handleAATriggers` and `writer.js`'s post-stabilization hook), if the trigger causing the exception is deterministic (i.e., reproducible from on-chain data alone, as all AA execution must be), **every** full node hits the identical failure at the identical point in the queue, and the `aa_triggers` row for that unit/address is never deleted: [9](#0-8) [10](#0-9) 

Additionally, `checkBalances()` explicitly treats a non-empty `aa_triggers` table as "unhandled triggers" and skips itself, confirming that the table is expected to always drain and that a stuck row is an abnormal, blocking condition: [11](#0-10) 

### Impact Explanation
If a single queued AA trigger deterministically throws instead of bouncing, `handleAATriggers()`'s `async.eachSeries` for that batch stalls on it forever:
- Any subsequent triggers queued after it (from other units/AAs in the same or later MCIs, since new triggers just keep accumulating in `aa_triggers`) are never executed, because the SELECT in `handleAATriggers()` always orders by `(mci, level, unit, address)` and the earlier stuck row is never removed, and re-invocations of `handleAATriggers()` (e.g., after new units stabilize) would re-process the same stuck row first and hit the same exception again.
- Since AA-trigger processing is a required part of `main_chain.js`'s MC-stability advancement pipeline (`calcCommissions` → `handleAATriggers`), and it is `await`ed before completing `stabilizeMci`/`saveJoint`, a stalled/throwing trigger effectively can hold up completion of the stabilization write path and prevent subsequent AA-driven state and outputs from being confirmed and spendable.
- Because the failure is deterministic and identical for all full nodes (same code, same input data), this is not a single-node crash but a systemic, network-wide processing stall for any unit/AA output depending on the affected trigger completing — directly analogous to "network unable to confirm new units."

### Likelihood Explanation
Reaching this bug requires an attacker to craft a trigger/AA whose processing exercises one of the un-bounced `throw Error(...)` paths (e.g., forcing `formulaParser.evaluate`'s `last_ball_timestamp` invariant check to fail, or another code path outside the normal bounce funnel) rather than a graceful bounce. This is a code-path/edge-case discovery problem rather than a simple parameter like "send funds to an address that always reverts" in the original Solidity report — the original report's condition (payment to an address whose token transfer always reverts) is trivially reproducible by any user; the ocore analog requires finding a specific formula/state combination that trips an unguarded invariant. This is plausible given the number of unguarded `throw` statements identified inside the trigger-processing pipeline, but exact reproducibility (which specific trigger crafting achieves it) was not confirmed in this review — it should be validated by fuzzing/crafting an AA that reaches one of the cited `throw` sites via a primary trigger.

### Recommendation
- Audit every `throw Error(...)` reachable from `handleTrigger()`/`handlePrimaryAATrigger()`/`formulaParser.evaluate()` during ordinary AA trigger execution and route them through `bounce()` (or an equivalent graceful failure path) instead of throwing synchronously, so that `onDone`/`cb` is always eventually called and the `aa_triggers` row is always removed.
- In `handleAATriggers()`, wrap the per-row processing in error handling so that if a row's processing does throw or reject, the row is either retried a bounded number of times, moved to a separate "failed_aa_triggers" table for manual/automatic remediation, or the row is safely deleted with a recorded bounce, rather than blocking `async.eachSeries` indefinitely.
- Add monitoring/alerting for `aa_triggers` rows that persist across multiple `handleAATriggers()` invocations, since `checkBalances()` already signals this condition is abnormal.

### Proof of Concept
Not independently reproduced in this review. Based on static analysis, a proof of concept would need to:
1. Author and deploy an AA whose primary-trigger execution reaches one of the un-bounced `throw Error(...)` sites identified above (most promising candidate: the `last_ball_timestamp` invariant check in `formula/evaluation.js:93-94`, reached synchronously from `aa_composer.js` formula-evaluation call sites that lack `try/catch`).
2. Post a triggering unit to that AA so a row is inserted into `aa_triggers` (via `main_chain.js:1714`).
3. Observe that `handleAATriggers()` throws while processing that row and never issues the `DELETE FROM aa_triggers` (`aa_composer.js:102`), and that any triggers queued after it (posted in the same or subsequent MCIs) never execute.
4. Confirm that `checkBalances()` remains permanently skipped (`aa_composer.js:1957-1962`) because `aa_triggers` never becomes empty again.
