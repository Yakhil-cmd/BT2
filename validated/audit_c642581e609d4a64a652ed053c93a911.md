This confirms the discrepancy: `readDataFeedValue`'s unstable-AA branch explicitly filters out non-`'good'`-sequence units at data_feeds.js:219 (`if (objUnit.sequence !== 'good') continue;`), but the equivalent unstable-scan loop inside `dataFeedExists` (used by the `data_feed`/oscript `in_data_feed[[...]]` boolean check and by the `'in data feed'` address-definition operator with `bAA=true`) has no such filter at all [1](#0-0) .

### Title
Missing sequence='good' filter lets a data feed from a doomed (non-serial) unit satisfy `in_data_feed`/`data_feed` checks - (File: data_feeds.js)

### Summary
`dataFeedExists()` scans `storage.assocUnstableMessages` for `data_feed` messages matching an oracle condition when called in AA context (`bAA=true`), but unlike the sibling function `readDataFeedValue()`, it never checks `objUnit.sequence`, so a unit that is unstable and already known to be non-serial ("temp-bad"/doomed by a conflicting earlier unit) can still be counted as proof that a data feed condition is met.

### Finding Description
`dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, max_mci, bAA, handleResult)` at data_feeds.js:13 has an in-memory fast path used only when `bAA` is true (invoked from `in_data_feed[[...]]` in oscript, `formula/evaluation.js:745`, and from the address-definition operator `'in data feed'` evaluated inside AA validation, `definition.js:940`). This loop iterates `storage.assocUnstableMessages` and, for each candidate unit, checks only:
- `objUnit.bAA` [2](#0-1) 
- `latest_included_mc_index` within `[min_mci, max_mci]` [3](#0-2) 
- author-address intersection with the oracle list [4](#0-3) 

It never checks `objUnit.sequence`. Compare this with `readDataFeedValue()`'s equivalent unstable-scan branch, which explicitly skips any unit whose `sequence !== 'good'` [5](#0-4) . In ocore, `sequence` on an unstable unit can be `'good'`, `'temp-bad'` (currently first-seen but might still be overtaken) or already resolved as non-serial due to a conflicting double-spend; such non-`'good'` units are known at validation time to be losers of a conflict and are destined to be excluded from the final DAG once stable (see the same `sequence` bookkeeping used throughout `main_chain.js`/`storage.js`).

Because the check is missing in `dataFeedExists`, an oracle-posting address (which can be any ordinary address, including an address controlled by the attacker acting as `arrAddresses[i]` — since `'in data feed'`/`data_feed` explicitly allow the oracle list to be attacker-supplied, e.g., derived from `trigger.data` or `input[[...]].address`, as shown in the test suite: `oracles=input[[asset=base]].address` and `oracles=trigger.data.oracle` [6](#0-5) [7](#0-6) ), a data-feed unit whose validity is not yet resolved (and that will eventually be marked non-serial/invalid because of a conflicting double-spend from the same author) can still cause `in_data_feed[[...]]` to evaluate `true`, or cause an address-definition `'in data feed'` authentifier check to pass, purely because the message currently sits in `assocUnstableMessages` with a matching author before stabilization.

### Impact Explanation
An AA (or a plain address using `'in data feed'` in its definition) that gates a payout, asset-transfer condition, or private-payment authorization on `in_data_feed[[...]]`/`data_feed[[...]]` can be tricked into releasing/spending funds based on a data feed value carried by a unit that the node itself already suspects (via `sequence`) is not the surviving branch of a double-spend and will ultimately be excluded from the DAG. This is analogous to the Rikkei Finance incident where the price/oracle input used to authorize a payout was not the legitimate one: here, the "oracle result" the AA trusts is an artifact of an unresolved conflict rather than a stabilized, trustworthy value — a race an attacker can engineer by broadcasting two conflicting data-feed-carrying units from the oracle/self-controlled address to make the check momentarily pass. This can lead to unauthorized AA fund release or address-definition authentication bypass (unauthorized spending) — a concrete impact category explicitly in-scope.

### Likelihood Explanation
Reachable purely by posting units: any unprivileged party who can (a) act as or spoof the oracle address referenced in the condition (which is explicitly attacker-derivable via `trigger.data`/`input[[...]].address` in the oscript grammar) and (b) create a conflicting/double-spending unit from that same address can trigger this in-memory unstable path. No special privileges, hub/node compromise, or leaked keys are required — only the ability to post units and control the timing of a race so the target AA/definition sees the not-yet-`sequence='good'`-resolved unit during evaluation.

### Recommendation
Add the same `if (objUnit.sequence !== 'good') continue;` filter to the unstable-scan loop inside `dataFeedExists()` (data_feeds.js:34-43) that is already present in `readDataFeedValue()` (data_feeds.js:219), so that `in_data_feed`/`data_feed`/`'in data feed'` evaluated against unstable AA units only ever consider units known to be on the good, serial branch, consistent with the rest of the data-feed reading logic.

### Proof of Concept
1. Deploy an AA (or an address using `'in data feed'` in its definition) whose payout/authorization logic includes `in_data_feed[[oracles=$attacker_oracle, feed_name='X', feed_value=..., min_mci=...]]` where `$attacker_oracle` is derived from attacker-controlled input (e.g., `trigger.data.oracle`, mirroring the pattern already exercised in `test/aa.test.js:301-307` and `test/formula.test.js:827-831`).
2. From the attacker's own address, post two conflicting units (double-spending the same input) — one of which includes a `data_feed` message with the desired `feed_name`/value that would satisfy the AA's condition.
3. Before the conflict is resolved and MC-stabilized (while both units are still in `storage.assocUnstableMessages`/`assocUnstableUnits` and before `sequence` for the losing unit is finalized), trigger the AA / attempt to spend via the definition so that `dataFeedExists()`'s unstable-branch loop (data_feeds.js:34-43) scans the data-feed-bearing unit and returns `true` regardless of which branch will ultimately be `sequence='good'`.
4. If the branch carrying the satisfying `data_feed` message is later resolved as non-serial (`sequence != 'good'`), the AA has already released funds / the definition already authenticated based on a value from a unit that never becomes part of the canonical, stable history — demonstrating unauthorized fund release/authentication bypass.

Note: I was not able to execute this scenario in a live node from the index alone (no test/runtime environment access here), so the race-timing feasibility and exact `sequence` state transitions during the vulnerable window should be verified with a running Devin session against `main_chain.js`/`storage.js` sequence-assignment logic before treating this as fully confirmed.
