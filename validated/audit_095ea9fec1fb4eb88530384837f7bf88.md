### Title
Reward-per-token rounding to zero permanently forfeits `pallet-asset-rewards` rewards - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards::reward_per_token` computes the pool-wide accumulator increment as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, with `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) . Every call to `stake`, `unstake`, or `harvest_rewards` triggers `update_pool_and_staker_rewards` -> `reward_per_token`, which then unconditionally advances `last_update_block` to `now` via `update_pool_rewards`, regardless of whether the increment was non-zero [2](#0-1) . This is the exact rounding-to-zero pattern described in the Merit Circle report, applied to a Synthetix-style `reward_per_token` accumulator instead of `pointPerShare`.

### Finding Description
`reward_per_token` is:
```
reward_per_token_stored + reward_rate_per_block * blocks_elapsed * 4096 / total_tokens_staked
``` [3](#0-2) 

Because `PRECISION_SCALING_FACTOR` is only `4096` (2^12) — far smaller than the `10^18` fixed-point precision used by the analogous `nomination-pools` reward counter (`FixedU128`) — the numerator `reward_rate_per_block * blocks_elapsed * 4096` can easily be smaller than `total_tokens_staked` whenever the pool has a reasonably large amount staked relative to the reward rate. When this happens, integer division truncates the increment to `0`, so `reward_per_token_stored` does not change.

Critically, `update_pool_rewards` is called immediately afterward and unconditionally sets `new_pool_info.last_update_block = now` [4](#0-3) . There is no `ensure!`/check that the computed increment is non-zero before consuming the elapsed-block window (unlike the report's suggested fix `require(_amount * POINTS_MULTIPLIER / shares > 0)`). Once `last_update_block` advances, the elapsed blocks that produced a zero increment can never be "recovered" — the reward for that window is permanently lost, not merely delayed.

Any signed, non-privileged staker can trigger this update path via `stake`, `unstake`, or `harvest_rewards` (self-targeted, so the `BadOrigin` origin check permits it) [5](#0-4) [6](#0-5) . Because `reward_per_token_stored`, `total_tokens_staked`, and `last_update_block` are all pool-wide fields shared by every staker in `Pools<T>`, an attacker who repeatedly calls a cheap self-operation (e.g. `stake(1)` then `unstake(1)`, or repeated `harvest_rewards`) every block forces `blocks_elapsed` to be `1` on each recomputation. If `reward_rate_per_block * 4096 < total_tokens_staked`, every single-block recomputation rounds to zero, and the pool's `reward_per_token_stored` never advances — permanently zeroing rewards for **every** staker in the pool, not just the attacker, for as long as the attacker keeps "pinging" the pool once per block.

### Impact Explanation
This is a griefing/rounding-loss vector against `pallet-asset-rewards`, distinct from ordinary "off by one" dust noted in `nomination-pools` (whose reward counter uses 10^18 precision and where residual dust is explicitly swept to the depositor at pool destruction — see `rewards_are_rounded_down_depositor_collects_them` [7](#0-6) ). In `asset-rewards`, the tiny `4096` scaling factor combined with the unconditional `last_update_block` advance means a single unprivileged staker can suppress the entire pool's reward accrual, with rewards silently lost rather than delayed. Depending on the values of `reward_rate_per_block` vs. `total_tokens_staked` for a given pool, this can affect medium-to-large pools where the ratio makes truncation frequent.

### Likelihood Explanation
Likelihood depends entirely on the pool's configured `reward_rate_per_block` relative to `total_tokens_staked` — since both are chosen at pool-creation time by `T::CreatePoolOrigin` and by subsequent stakers, this is not guaranteed to trigger in every pool, only in pools where `reward_rate_per_block * 4096 < total_tokens_staked` holds for single-block windows. This is analogous to the "shares grow large enough" precondition in the original report. I was not able to fully confirm from the index whether any additional runtime-level guard (e.g., minimum stake bounds, or a governance-enforced minimum `reward_rate_per_block`) exists elsewhere in production runtime configuration that would make this unreachable in the deployed configuration — this would need further confirmation with full repository access.

### Recommendation
- Increase `PRECISION_SCALING_FACTOR` significantly (e.g., to `10^12`–`10^18`) to match the precision approach used by `nomination-pools`' `RewardCounter` (`FixedU128`), or use a fixed-point type instead of a raw `u16` multiplier.
- Do not advance `last_update_block` when the computed reward increment is zero and there is a non-zero pending reward rate/elapsed window — instead defer, or accumulate elapsed blocks/leftover remainder to be redeemed at a subsequent update rather than discarding them.
- Add an explicit accounting mechanism to track/handle truncation remainders (mirroring the dust-sweep pattern in `nomination-pools`) so that "in-flight" reward tokens that were transferred into the pool but rounded to zero increment are not orphaned indefinitely.

### Proof of Concept
No executable PoC was run against a test harness within this session (index-only investigation; no filesystem/terminal access available). The mechanism is demonstrated purely via static code inspection:
- `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) 
- `reward_per_token` truncating division [8](#0-7) 
- Unconditional `last_update_block` advance regardless of computed increment [9](#0-8) 
- Public, self-callable entry points (`stake`, `unstake`, `harvest_rewards`) that trigger this path every call [5](#0-4) [6](#0-5) 

A concrete reproduction would require constructing an `ExtBuilder`-based test in `substrate/frame/asset-rewards/src/tests.rs` that creates a pool with `total_tokens_staked` large relative to `reward_rate_per_block`, then repeatedly calls `stake`/`unstake` (1 block apart) and asserts `reward_per_token_stored` and staker `rewards` remain `0` across many blocks despite `deposit_reward_tokens` funding the pool — this reproduction was not executed in this session and its outcome is not confirmed; it should be validated by a background engineering session with full repo/test-harness access before treating this as conclusively proven.

				&staker,
				amount,

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
