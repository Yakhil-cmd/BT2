### Title
Webhook signature is verified against the wrong organization's secret, allowing cross-organization triggering of GitHub sync/deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using a field derived from the *unverified* request body, while the event handlers that actually act on the payload use a *different, independently-controlled* field (`repository.full_name`) to decide which `Stack`/`Repository` gets mutated. Nothing ties these two fields together, so a caller who legitimately controls the webhook secret for **Organization A** can forge a payload whose signature validates for Org A, but whose `repository.full_name` points at a repository belonging to **Organization B**.

### Finding Description
`verify_signature` picks the GitHub App config to validate against like this: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization webhook secret** from `secrets.github`, keyed by org name, and is used purely to determine which secret validates `X-Hub-Signature`: [3](#0-2) 

Once the signature check passes, `create` dispatches to handlers using the same raw, already-verified body, but each handler re-derives its own notion of "which repository/stack to touch" from a *different* JSON field (`repository.full_name`), never cross-checked against `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

The equality this design implicitly assumes but never enforces is:
`repository.owner.login` (used to pick the signing secret) **==** owner segment of `repository.full_name` (used to pick the `Stack` to mutate).

Because Shipit supports multiple organizations sharing one instance, each configured with its own `webhook_secret` (`TOP_LEVEL_GH_KEYS` includes `webhook_secret` per org key in `secrets.github`), a party that legitimately administers Org A's GitHub App/webhook (and therefore knows Org A's `webhook_secret`) can compute a valid `X-Hub-Signature` for a body where:
- `repository.owner.login` (or `organization.login`) = `"org-a"` → passes signature check against Org A's secret.
- `repository.full_name` = `"org-b/victim-repo"` → used by `PushHandler#stacks` / `Handler#repository_name` to locate an unrelated `Stack` belonging to Org B.

The `PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, and `GithubSyncJob#perform` fetches commits/updates the cached deploy spec for a stack the forging party has no legitimate authorization over: [7](#0-6) 

This is the direct structural analog of the reentrancy bug class: a value used for the "authorization check" (`repository_owner`/signing org) is decoupled from the value used for the "effect" (`repository.full_name` driving which stack is mutated), exactly like `pending`/`user.rewardDebt` being computed from state that is stale relative to the transfer actually performed.

### Impact Explanation
An attacker who controls (or has compromised) the webhook secret for any one organization onboarded to a shared Shipit instance can force `GithubSyncJob` to run against any other organization's `Stack`, triggering commit ingestion (`stack.commits.create_from_github!`), spec cache recomputation, and — depending on `continuous_deployment`/CI settings on the victim stack — this can feed into automatic deploy triggering pipelines for a repository the attacker does not control. This crosses the "cross-repository writes" / "unauthorized deploy" bar defined by the rules, without requiring an `ApiClient` token, session, or GitHub App private key for the victim org.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate operator of at least one organization/webhook configured in the same multi-tenant Shipit deployment (i.e., they know their own org's `webhook_secret`), and requires a second organization's repository to have an existing `Stack` in the same instance. This is a realistic configuration for shared/internal Shipit deployments serving several GitHub orgs. It does not require any Shipit session, API token, or the victim org's own secret — only crafting a POST to `/github/auth/github` webhook endpoint... actually to the webhooks endpoint, with a spoofed `repository.full_name`.

### Recommendation
Enforce that the organization used to select/verify the webhook signature matches the organization implied by every repository-scoped field the handlers subsequently act on:
- After verifying the signature, re-derive `repository_owner` and compare it against the owner segment parsed from `payload.dig('repository', 'full_name')` (and any other repo/org fields in the payload) before dispatching to handlers; reject the payload if they diverge.
- Alternatively, have `Handler#stacks`/`repository_name` scope lookups to `Repository` records that belong to the same verified organization, rather than trusting `repository.full_name` in isolation.
- Consider validating that the resolved `Stack`'s repository owner equals the verified `repository_owner` before invoking `sync_github` or any other mutating action.

### Proof of Concept
1. Shipit instance is configured (in Rails credentials) with two orgs, e.g. `secrets.github = { "org-a" => { webhook_secret: "secretA", ... }, "org-b" => { webhook_secret: "secretB", ... } }`, each with its own `Stack`s.
2. Attacker administers Org A's webhook config and thus knows `secretA`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "org-a" },
       "full_name": "org-b/victim-repo"
     }
   }
   ```
4. Attacker signs the raw body with `secretA` and sets `X-Hub-Signature` accordingly, sends `POST /webhooks` (per `config/routes.rb`) with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches Org A's app/secret, verifies successfully.
6. `PushHandler.call` runs `stacks` → `Repository.from_github_repo_name("org-b/victim-repo")` → finds Org B's `Stack` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, enqueuing `GithubSyncJob` against Org B's stack despite the request only being authenticated for Org A.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
