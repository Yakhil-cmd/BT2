### Title
Signature verification is keyed to `repository.owner.login`, but push/status webhook handlers act on unrelated payload fields, enabling cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to validate the HMAC against using `repository.owner.login` (falling back to `organization.login`) taken straight from the unverified JSON body. Once that check passes, the actual handlers that mutate state key off *different* fields in the same payload — `repository.full_name` for push events, and nothing at all (a global commit SHA lookup) for status events. This breaks the invariant that "the organization whose secret authenticated the request" equals "the repository/commit that gets written to."

### Finding Description
`verify_signature` picks the verification key like this: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `webhook_secret` (Shipit explicitly supports [multiple GitHub Applications for different organizations](app/controllers/shipit/webhooks_controller.rb), one per top-level key in `config/secrets.yml`). The signature is verified against `request.raw_post` using whichever org's secret matches `repository.owner.login` — a field the attacker fully controls before verification occurs.

Once verification succeeds, the base `Handler` and its subclasses locate the *actual* resource to act on using a **different** field of the same payload: [3](#0-2) 

`PushHandler` uses this to find stacks and trigger a sync with an attacker-supplied `expected_head_sha`: [4](#0-3) 

`StatusHandler` is worse — it does not scope by repository at all, it matches purely by commit SHA across the entire Shipit instance: [5](#0-4) 

The binding that should hold is: `organization authenticated by the webhook signature == organization that owns the repository/commit being written`. Because `verify_signature` derives its key from `repository.owner.login`/`organization.login` while `Handler#repository_name` (and `StatusHandler`, which ignores repository entirely) resolve the write target from `repository.full_name` or a bare `sha`, an attacker who legitimately controls one GitHub organization onboarded to this multi-tenant Shipit instance can:

1. Set `repository.owner.login` = their own organization (so `verify_signature` fetches *their* known `webhook_secret` and the HMAC they compute passes).
2. Set `repository.full_name` (push) or `sha` (status) to reference a repository/commit belonging to a completely different, unrelated organization tracked by the same Shipit instance.

The request passes signature verification (it's their own org's secret, correctly HMAC'd over the whole body) yet the handler acts on a resource outside that organization's control.

### Impact Explanation
For `StatusHandler`, this allows an attacker to forge a `status` event that creates a `CommitStatus` for *any* commit SHA tracked anywhere in the Shipit instance, on any stack, regardless of which organization owns it — there is no repository check at all, only `Commit.where(sha: params.sha)`. This can mark a fraudulent/malicious commit belonging to another organization's repository as "success", influencing deploy eligibility (`commit.create_status_from_github!`) — a cross-repository write and a path to an unauthorized deploy of a commit that should not have been deployable. For `PushHandler`, an attacker can trigger `GithubSyncJob`/`stack.sync_github` with a forged `expected_head_sha` against a stack belonging to an organization they don't control.

### Likelihood Explanation
This requires the operator to run Shipit configured with multiple GitHub organizations (a documented, supported configuration in `docs/setup.md` — "Using Multiple GitHub Applications"), and the attacker to control at least one such onboarded organization (i.e., be able to trigger legitimate webhook deliveries with their own org's `webhook_secret`, which is normal for any org admin, not a privileged Shipit account). No repository write access, Shipit session, or `ApiClient` token is needed — only control of the sending organization's GitHub webhook configuration, which is the expected trust boundary GitHub webhooks are supposed to enforce per-repository, and which this code does not.

### Recommendation
Verify that the fields used to select the HMAC verification key (`repository.owner.login`/`organization.login`) are the *same* fields subsequently used by handlers to resolve the target Repository/Stack/Commit. Concretely: after verifying the signature, re-derive the target repository from `repository.full_name` and assert its owner equals `repository_owner` used for verification before dispatching to handlers; and make `StatusHandler` scope `Commit.where(sha: ...)` to commits whose stack's repository owner matches the verified organization, instead of a global, repository-agnostic lookup.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`) with two organizations, `OrgA` (attacker-controlled, legitimate GitHub App + known `webhook_secret_A`) and `OrgB` (victim, tracked repo/stack in the same Shipit instance).
2. Attacker crafts a `status` webhook body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" },
  "sha": "<victim commit sha belonging to OrgB's repo>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` using their own known secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies with `webhook_secret_A`, and passes — see [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a status on the victim's commit belonging to `OrgB`, with no relation to `OrgA` at all — see [5](#0-4) .
