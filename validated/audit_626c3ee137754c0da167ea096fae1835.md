### Title
CCMenu API tokens are never scoped to a stack, allowing cross-tenant unauthenticated read of any stack's deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb], [File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`Api::CCMenuController#stack` bypasses the tenant-scoping logic in `Api::BaseController#stacks` by calling `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`. Independently, `CCMenuUrlController#client` mints an `ApiClient` with `permissions: %w[read:stack]` but never sets `stack:`, so even the correctly-scoped `stacks` helper would resolve to `Stack.all` for this token. Either bug alone is sufficient for the token to read any stack's CCMenu XML.

### Finding Description
The binding that should hold is: `stack ∈ current_api_client.stacks` (i.e., `stack.id == current_api_client.stack_id` when the client is stack-scoped). Tracing the code:

- `CCMenuUrlController#client` [1](#0-0)  creates/reuses an `ApiClient` keyed only by `creator` and `name: 'CCMenu Client'`, with `permissions: %w[read:stack]` and no `stack:` attribute. `ApiClient` has `belongs_to :stack, optional: true` [2](#0-1) , so `stack_id` is `nil`.
- Because `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` matches only on creator+name, the *same* `ApiClient` record (and thus the same `authentication_token`) is reused/returned for every stack the user requests a CCMenu URL for [3](#0-2) .
- In `Api::BaseController#stacks`, scoping only applies `if current_api_client.stack_id?` [4](#0-3) ; since `stack_id` is always `nil` for CCMenu tokens, this helper would resolve to `Stack.all` regardless.
- `Api::CCMenuController` compounds this by overriding `stack` to call `Stack.from_param!(params[:stack_id])` directly [5](#0-4) , never invoking the `stacks` scope at all, and only enforces `require_permission :read, :stack` [6](#0-5)  which checks the permission string, not stack identity.

Exploit flow: an authenticated Shipit user fetches a CCMenu URL for stack A via `GET /stacks/:stack_a/ccmenu_url` → receives `token=T`. An attacker who obtains `T` (e.g., it's embedded in an unauthenticated CI radiator widget/URL, commonly pasted into READMEs, dashboards, or shared configs) can request `GET /api/stacks/:stack_b/ccmenu.xml?token=T` for any other stack B and get `200 OK` with stack B's deploy/task state, because nothing ties `T` to stack A. No GitHub credentials, session, or `api_clients_secret` are needed — only knowledge of the CCMenu token string, which by design is meant to be embedded in unauthenticated third-party CCTray/CCMenu clients.

Existing guards that fail to prevent this: `require_permission!` only checks the permission string `read:stack`, not stack identity [7](#0-6) ; there is no `Stack` identity validator or `before_action` tying `params[:stack_id]` to `current_api_client.stack_id` in `CCMenuController`.

### Impact Explanation
Any holder of a valid CCMenu token (which is intentionally embedded in unauthenticated URLs for CI radiator tools) can enumerate and read deploy/build status, last build label, and web URLs for **every** stack in the Shipit instance, not just the one it was issued for. This is an unauthenticated cross-tenant read of stack state — matching the "High" impact category (unauthenticated read of stack state) rather than the RCE/credential-exfiltration Critical categories, since the CCMenu XML only exposes deploy status metadata, not secrets or command execution. It is fully repeatable against arbitrary `stack_id` values with a single valid token.

### Likelihood Explanation
Preconditions: the attacker must possess (not forge) one valid CCMenu token, which is granted to any authenticated Shipit user with read access to at least one stack via `CCMenuUrlController#fetch`. Since CCMenu tokens are specifically designed to be embedded in unauthenticated third-party polling clients/dashboards, such tokens are commonly exposed outside of authenticated sessions (e.g., pasted into CI dashboard configs, browser history, shared documents). Given one such leaked/observed token, the attack costs a single unauthenticated HTTP GET request and is trivially repeatable for any `stack_id`.

### Recommendation
1. In `CCMenuUrlController#client`, scope the `ApiClient` to the specific stack (`stack: stack`) instead of reusing a single client per user across all stacks, and include the stack in the `find_or_create_by!` lookup key.
2. In `Api::CCMenuController#stack`, use the inherited `stacks.from_param!(params[:stack_id])` (i.e., remove the override, or explicitly scope by `current_api_client.stack`) so the token is enforced to only access its bound stack.
3. Consider making `stack_id` a required (non-optional) field on `ApiClient` for stack-scoped permissions like `read:stack` to prevent silently unscoped tokens.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a ccmenu token issued for stack A cannot read stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  client = ApiClient.create!(creator: shipit_users(:walrus), name: 'CCMenu Client', permissions: %w[read:stack])
  # simulate CCMenuUrlController#client never scoping to stack_a
  assert_nil client.stack_id

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack (stack_b) must be a member of client's authorized stacks (only stack_a)
  assert_not_equal stack_a.id, stack_b.id
  assert_response :forbidden # currently fails: actual response is 200 with stack_b data
end
```
This demonstrates the divergence: `current_api_client.stack_id` is `nil` (unscoped) while `params[:stack_id]` resolves to `stack_b`, and the controller returns `200` with stack B's data instead of rejecting the request.
