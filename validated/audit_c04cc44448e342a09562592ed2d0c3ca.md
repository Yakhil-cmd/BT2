## Finding

Based on the investigation, I traced the C4 finding's core invariant — "an admission/history record can be created for one target but later matched/consumed under a different, ambiguous target" — to Aptos's multisig transaction execution flow, where a multisig owner's on-chain **approval is bound to one payload**, but the payload actually executed can be substituted without re-verifying that binding when a feature flag is off.

### Title
Multisig transaction execution can bypass on-chain payload-match verification, allowing an owner to execute an unapproved payload — (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::validate_multisig_transaction` is the VM-invoked prologue that is supposed to guarantee that the payload actually executed for a pending multisig transaction is the one the owners voted on. For hash-only proposals it always checks `sha3_256(payload) == payload_hash`. However, for proposals created with the **full payload stored on-chain** (`create_transaction`), the equivalent check that the payload about to be executed equals `transaction.payload` is only performed when the feature `abort_if_multisig_payload_mismatch_enabled()` is turned on, and only when the caller-supplied payload is non-empty. [1](#0-0) 

### Finding Description
The prologue's approval/quorum checks (`can_execute`/`can_be_executed`, vote counting) are computed purely from `sequence_number`, independent of what payload will actually run: [2](#0-1) 

The payload that will actually be dispatched is derived from the *submitted transaction's own executable* in `run_multisig_prologue` (Rust side), and passed as `provided_payload`/`payload` into the Move prologue: [3](#0-2) 

The final check that binds the vote-approved payload to the executed payload is:
```
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    let stored_payload = transaction.payload.borrow();
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [4](#0-3) 

If `abort_if_multisig_payload_mismatch_enabled` is not active on a given chain/network (it is a Move-stdlib gated feature flag, `EPAYLOAD_DOES_NOT_MATCH` = 2010), this comparison is skipped entirely. Approval accounting (`num_approvals >= num_signatures_required`) still succeeds because it only checks the vote table keyed by `sequence_number`, not the content of the payload being executed. As a result, an owner who is able to submit the "next" pending transaction (i.e., is authorized to call `execute_multisig_transaction`) can supply an **arbitrary entry-function payload** as the actual transaction executable, and it will be admitted and executed under the multisig account's signer, even though the owners voted on a different payload. This is a sender/approval-set confusion at the admission boundary: the approval set was bound to payload A, but payload B executes.

### Impact Explanation
This breaks the fundamental multisig invariant that execution requires quorum approval of the *exact* action being performed. A colluding or compromised single owner (in a k-of-n scheme where they can trigger execution once quorum is nominally met, e.g., via a valid quorum on any *unrelated* stored-payload proposal) can redirect the multisig's on-chain signer capability to execute a completely different, unapproved operation (e.g., drain funds, rotate keys, add new owners). This is a high/critical-impact authorization bypass at the transaction admission boundary — a transaction that should fail admission (payload doesn't match what owners approved) instead executes and commits.

### Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active. I was not able to fully confirm the default/rollout state of this feature flag or how widely it has been enabled across networks within available tool iterations, so likelihood is uncertain — this should be verified by checking `aptos-move/framework/move-stdlib/sources/configs/features.move` default feature bitmap / genesis config and current mainnet feature status before treating this as confirmed-live. The gating pattern (`feature_enabled()`), the specific naming (`abort_if_multisig_payload_mismatch_enabled`), and the existence of a dedicated error code (`EPAYLOAD_DOES_NOT_MATCH`) strongly suggest this was a known gap that was patched behind a feature flag rather than fixed unconditionally, which is consistent with the flag being introduced as a guarded fix for pre-existing deployments and is plausible to still be disabled on some networks/genesis configurations.

### Recommendation
Remove the feature gate and the `!payload.is_empty()` bypass condition so that whenever `transaction.payload.is_some()`, the submitted execution payload is unconditionally required to equal the stored payload (mirroring the unconditional hash check for hash-only proposals). If the feature flag exists purely for staged rollout, ensure it is enabled network-wide and eventually deprecate the gate rather than leaving a permanent bypass path.

### Proof of Concept
Conceptual PoC (pending confirmation of feature-flag default):
1. Owner A creates a multisig transaction with `create_transaction` (full payload stored on-chain) for a benign action, e.g., transferring `X` to owner A. [5](#0-4) 
2. Owners vote until quorum is reached for that sequence number (`num_signatures_required` satisfied) via `approve_transaction`.
3. On a chain where `abort_if_multisig_payload_mismatch_enabled` is disabled, malicious owner A submits an `execute_multisig_transaction`-style transaction whose actual entry-function executable is different (e.g., transferring the entire balance, or rotating owners) instead of the approved payload.
4. `validate_multisig_transaction` passes because: (a) `payload_hash` is `None` (full-payload flow), so the hash check is skipped by construction; (b) the payload-match block is skipped because the feature is off; (c) quorum/vote checks pass since they are keyed only by `sequence_number`.
5. The unapproved payload executes under the multisig account's signer capability, and `last_executed_sequence_number` advances, closing off the original approved proposal's slot as "resolved" even though it never actually ran.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;

        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
