### Title
Webhook signature verification is keyed by an unauthenticated field, allowing cross-organization event forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using a field taken from the *unauthenticated* JSON body itself, while the actual event handler that mutates state resolves the target repository from a *different* field of that same unauthenticated body. An attacker who legitimately controls the webhook secret for any one organization configured on the Shipit instance can forge events for any other organization's repositories.

### Finding Description
`verify_signature` computes the organization used to pick the verifying secret directly from the untrusted payload: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, and this org name is used to select the `github_app`/`webhook_secret` used by `verify_webhook_signature`: [3](#0-2) 

However, the actual event handlers that act on the payload (e.g. `PushHandler`) resolve the affected `Repository`/`Stack` from a **different field** in the same body — `repository.full_name` — via `Handler#repository_name`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` and `repository.full_name` are independent JSON fields in the same attacker-controlled body, nothing in the code ties them together. Shipit explicitly supports multiple organizations each with their own `webhook_secret`, as shown in the example secrets file: [6](#0-5) 

The binding that should hold is: `organization used to verify signature == organization that owns the repository actually written to by the handler`. Before the attack, this holds trivially in the legitimate flow because GitHub always sends consistent `repository.owner.login` and `repository.full_name`. After the attack, an adversary breaks the equality: they set `repository.owner.login = "attacker-org"` (an org they control and whose `webhook_secret` they know, e.g. because they installed the app for their own org on the same Shipit instance) and `repository.full_name = "victim-org/victim-repo"`. `Shipit.github(organization: "attacker-org")` returns the attacker's own app config, `verify_webhook_signature` succeeds because the attacker signs the whole raw body themselves with their own known secret, and the request passes `verify_signature`. `create` then dispatches to handlers (e.g. `PushHandler`), which resolve the stack using `repository.full_name = "victim-org/victim-repo"` and executes the event (e.g. enqueues `GithubSyncJob`, updates commit statuses, mutates `Membership`/`Team` records, etc.) against the victim's repository/stack — despite the request never being authenticated by GitHub for that organization.

### Impact Explanation
This allows an attacker with legitimate control over one configured organization's GitHub App on a shared/multi-tenant Shipit instance to forge arbitrary webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) against any other organization's repositories/stacks hosted on the same instance, without ever possessing that organization's real webhook secret. Depending on the handler, this can trigger unauthorized syncs, injected commit/check statuses that influence deploy safety checks, or membership/team manipulation (`membership` handler creates/removes `Membership` records) — all of which can be leveraged toward triggering an unauthorized deploy/ship for a victim stack, matching the "unauthorized deploy" / cross-repository-write class of impact.

### Likelihood Explanation
Requires only that the Shipit instance is configured to serve more than one GitHub organization (a documented, supported configuration) and that the attacker legitimately controls at least one of those organizations' webhook secret (e.g., they run their own GitHub App installation pointed at the same shared Shipit instance). No privileged Shipit account, `ApiClient` token, or GitHub org write access to the victim org is needed — only a valid secret for *any* org configured on the instance and knowledge of a target victim repository name.

### Recommendation
Do not select the verifying organization/secret from an unauthenticated field of the same body being verified. Instead, either verify the payload against every configured secret (or the specific secret tied to the App/installation ID in the payload verified independently) and require that the resolved `repository.full_name`'s owner matches the organization whose secret validated the signature, rejecting the request if they diverge.

### Proof of Concept
1. Attacker legitimately controls `attacker-org` on the same multi-org Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC(attacker-org secret, raw_body)>` and POSTs to `/github/auth/github` (webhook endpoint) with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, verifies successfully with the attacker's own secret.
5. `WebhooksController#create` dispatches to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's real stack — despite the request never being signed by `victim-org`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
```

**File:** lib/shipit/github_app.rb (L76-83)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
