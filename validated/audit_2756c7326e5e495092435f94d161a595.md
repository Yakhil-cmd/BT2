### Title
Cross-repository status webhook forgery lets an attacker's own repo advance a victim's `MergeRequest` merge queue - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` query instead of scoping to the repository that produced the (correctly signature-verified) webhook, unlike `PushHandler` which scopes via the base class's `stacks` helper. Because the payload's `sha` is attacker-supplied and git SHAs are identical across forks/clones sharing history, a webhook that is validly signed for the attacker's own repository can write a forged commit status onto a `Commit` record that belongs to an entirely different (victim) `Stack`, which can flip `MergeRequest#all_status_checks_passed?` to true and let `reject_unless_mergeable!` fall through to `merge!`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (the repo whose `webhook_secret` verified the signature) MUST equal `commit.stack.repository` (the repo owning the `Commit` record being mutated). Instead, `StatusHandler#process` does: [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, cross-tenant lookup with no join to `stacks`/repository at all. Compare this to the base `Handler` class, which provides exactly the scoping primitive that `StatusHandler` fails to use: [2](#0-1) 

and to `PushHandler`, which correctly scopes all mutations through `stacks`: [3](#0-2) 

`WebhooksController#verify_signature` only proves the payload came from *some* repository owner recognized by `Shipit.github(organization: repository_owner)`; it says nothing about which `Commit`/`Stack` the payload is allowed to affect: [4](#0-3) 

`create_status_from_github!` then writes the status keyed by the `Commit`'s own `stack_id` (the victim's stack), not the originating webhook's repository: [5](#0-4) 

**Exploit flow:** Per the audit's stated attacker model, the attacker owns a repository capable of emitting a validly-signed webhook (e.g. a fork/clone of, or any repo sharing git history with, the victim's tracked repository, or any scenario where a real git commit sha the victim already tracks as a pending `MergeRequest#head` also exists as a reachable object in a repository the attacker controls). Git commit SHAs are content-addressed and identical across any repository holding the same commit object — cloning, forking, or cherry-picking preserves the SHA. The attacker:
1. Identifies (or arranges, e.g. by forking the victim's tracked repo) that some commit sha `X` is both the `head.sha` of a pending `Shipit::MergeRequest` on the victim `Stack`, and a commit reachable in a repository the attacker controls.
2. Sets a commit status (`success`) on sha `X` in their own repository via the GitHub API, which they can do freely since they own that repo.
3. GitHub relays a `status` webhook to Shipit, signed with the webhook secret belonging to the attacker's own repository owner — this passes `verify_signature` legitimately since it correctly matches the payload's `repository_owner`.
4. `StatusHandler#process` executes `Commit.where(sha: 'X')`, which matches the victim's `Commit` row (unscoped by repository), and calls `commit.create_status_from_github!(params)`, writing a `success` status attributed to the victim `Stack`'s commit.
5. `MergeRequest#all_status_checks_passed?` → `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` now returns true using the forged status, and `any_status_checks_failed?`/`any_status_checks_missing?` return false, so `reject_unless_mergeable!` returns `false` (does not reject), allowing the merge queue to proceed to `merge!`. [6](#0-5) 

No existing guard catches this: `verify_signature` validates *who signed*, not *which commit/stack is targeted*; `drop_unhandled_event` only checks event type registration; the `ExplicitParameters` schema in `StatusHandler` only validates shape/types of `sha`/`state`, not ownership; there is no `Repository`/`Stack` scoping applied to the `Commit` lookup at all.

### Impact Explanation
This is a payload for one repository (attacker's) mutating another's commit/stack state (Critical category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge"). The forged status can tip a pending `MergeRequest` into a passing CI state, letting the automatic merge-queue machinery invoke `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request(...)` — an unauthorized merge of a PR whose CI never actually passed on the victim repository. This is repeatable against any commit sha the attacker can get into a repository they control that also happens to be tracked by a victim `Stack`'s `Commit` table (most straightforwardly by forking the victim repository itself, which is a normal unprivileged GitHub action). Blast radius spans any tenant/stack in the same Shipit deployment whose repository history overlaps with a repo the attacker can control.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository under their control capable of emitting a validly-signed webhook for the payload's declared `repository_owner` (feasible per audited attacker capabilities — no privileged Shipit or GitHub credential required), and (b) a shared git commit SHA between their repo and the victim's tracked repo, which is trivially achieved by forking the victim's repository (a completely unprivileged GitHub action) and pointing a status at any historical commit shared with the fork, including commits that later become PR heads. This requires no Shipit session, API token, or webhook secret knowledge. Cost is a single API call (`POST /repos/{attacker}/{repo}/statuses/{sha}`) and is fully repeatable/scriptable against any repository fork relationship.

### Recommendation
Scope `StatusHandler#process` to only operate on commits belonging to the repository that authenticated the webhook, mirroring `PushHandler`'s use of `stacks`. For example, replace `Commit.where(sha: params.sha)` with a query joined through `stacks` (e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`), ensuring `repository_name` (from the verified webhook payload) is used to constrain which `Stack`/`Commit` rows can be mutated, consistent with the rest of the handler suite.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, minitest)
test "status webhook from an unrelated/attacker repository must not update a commit belonging to another repository's stack" do
  victim_stack = shipit_stacks(:shipit) # tracks e.g. "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...) # sha == X
  merge_request = victim_stack.merge_requests.create!(head: victim_commit, ...) # pending

  refute merge_request.all_status_checks_passed?

  attacker_payload = {
    "sha" => victim_commit.sha, # same sha X, present in attacker's own forked repo
    "state" => "success",
    "context" => "ci/attacker",
    "repository" => { "full_name" => "attacker/unrelated-fork", "owner" => { "login" => "attacker" } }
  }

  # signature verified successfully against attacker's own org secret (per audit's attacker model)
  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  merge_request.reload
  assert merge_request.all_status_checks_passed?, "forged cross-repo status flipped victim's MergeRequest checks"
  assert_equal false, merge_request.reject_unless_mergeable!
end
```
This demonstrates that `Commit.where(sha: params.sha)` in `StatusHandler#process` [1](#0-0)  updates a `Commit` regardless of which repository's webhook produced the payload, causing `all_status_checks_passed?` and `reject_unless_mergeable!` [7](#0-6)  to behave as if legitimate CI passed on the victim stack.

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

      false
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
