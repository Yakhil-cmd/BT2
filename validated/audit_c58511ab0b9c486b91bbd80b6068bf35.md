### Title
Cross-tenant Stack mutation via `repository.owner.login` / `repository.full_name` divergence in webhook payload - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/`webhook_secret` used to authenticate an inbound webhook based on `params.dig('repository','owner','login')`, while `PullRequest::OpenedHandler` (and its siblings) resolve the repository to mutate using the independent field `params.repository.full_name` via `Repository.from_github_repo_name`. [1](#0-0) [2](#0-1)  Nothing in the schema or controller enforces that these two fields agree, so in a multi-org deployment an attacker who legitimately controls org‑B (and therefore its `webhook_secret`) can sign a payload with `repository.owner.login = "org-B"` but `repository.full_name = "org-A/repo"`, causing a Stack/PullRequest to be written for org‑A's tracked repository using org‑B's authenticated request.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't: `organization_that_signed(request) == organization_owning(params.repository.full_name)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)` to fetch the `GitHubApp` whose `webhook_secret` is used to HMAC-verify the raw body. [3](#0-2) 
2. In the documented multi-organization configuration, `Shipit.github_app_config(organization)` looks up the config strictly by the `organization` string key supplied — i.e., whichever org's name appears in `repository.owner.login`. [4](#0-3)  This is exactly the "Using Multiple Github Applications" feature documented for supporting several tenants with independent `webhook_secret`s. [5](#0-4) 
3. The signature check therefore validates only that the request was signed by the app belonging to `repository.owner.login`, not by the app belonging to the owner encoded in `repository.full_name`.
4. Once the signature passes, `Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw JSON `params` hash — unchanged — to `PullRequest::OpenedHandler`. [6](#0-5) 
5. `OpenedHandler`'s `ExplicitParameters` schema requires only `repository.full_name`; it never requires or cross-checks `repository.owner.login`. [7](#0-6) 
6. `OpenedHandler#repository` resolves via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which splits the string on `/` and does a straight `find_by(owner:, name:)` — it has no notion of who authenticated the request. [8](#0-7) 
7. If `respond_to_pull_request_opened?`/`provision?` are satisfied for that resolved repository (auto‑provisioning enabled with an appropriate label policy), `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` creates a Stack/PullRequest row scoped to org‑A's repository. [9](#0-8) 

Attacker's exact request: POST `/webhooks` with `X-Github-Event: pull_request`, `X-Hub-Signature` computed with org‑B's `webhook_secret` (which the attacker legitimately possesses because org‑B is their own tenant), and a JSON body where `repository.owner.login = "org-B"` (so `verify_signature` picks org‑B's app/secret and the signature matches) but `repository.full_name = "org-A/repo"` (a real Shipit-tracked repository the attacker does not control). `respond_to_pull_request_closed?`/similar checks in `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `AssignedHandler`, `EditedHandler` share the identical `Repository.from_github_repo_name(params.repository.full_name)` pattern and are equally exposed. [10](#0-9) [11](#0-10) 

Existing guards do not catch this: `verify_signature` only proves the request was signed by *some* configured org's key — it never re-derives that org from `full_name` and compares. `drop_unhandled_event` only filters by event type. `ExplicitParameters` enforces types/presence, not cross-field consistency. `Repository` model validations constrain `owner`/`name` character sets but say nothing about which webhook signer is allowed to reference them. None of these guards close the gap.

### Impact Explanation
An attacker who controls a tenant (org‑B) recognized by the Shipit instance's multi-org `github` secrets configuration can force creation of Stack/PullRequest rows, and — if `provision?`/auto-provisioning conditions align, e.g. `allow_all` or a matching/absent label — trigger `ReviewStackAdapter#find_or_create!`, which provisions a review stack for a repository (org‑A) the attacker never authenticated for. Because review-stack provisioning runs `shipit.yml`-driven tasks against org‑A's actual repository/branch, this can escalate into command execution using org‑A's deploy credentials and configuration, i.e., a payload authenticated for one repository mutating and deploying another's stack — matching the Critical "payload for one repository mutating another's stack" / "unauthorized deploy" category. The attack is repeatable against any Shipit-tracked repository whose owner segment the attacker can guess or enumerate, for every pull_request sub-event handler that resolves `repository` from `full_name` independently of the authenticating org.

### Likelihood Explanation
Requires the Shipit instance to be running in the documented multi-organization `github:` secrets mode with at least two configured orgs (one attacker-controlled, one victim). The attacker needs no Shipit session, API token, or victim secrets — only their own legitimately provisioned GitHub App/webhook_secret for their own org, which is a normal, expected credential for a self-service or shared Shipit deployment. Crafting the divergent JSON body and computing a valid HMAC with a key they own is trivial and fully repeatable at will against any known tracked repository name.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after resolving `repository_owner` and verifying the signature, assert that the owner segment of `params.dig('repository','full_name')` matches `repository_owner` (case-insensitively) before dispatching to handlers; reject (422) on mismatch. Alternatively, have handlers resolve the repository using the authenticated organization rather than trusting `full_name` alone.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`, using the existing `secrets_double_github_app.yml` fixture with orgs `OrgOne`/`OrgTwo`):
```ruby
test "webhook signed by OrgTwo cannot create a stack for an OrgOne repository" do
  org_one_repo = Repository.create!(owner: "orgone", name: "repo")
  org_one_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = JSON.parse(payload(:pull_request_opened))
  payload["repository"]["full_name"] = "OrgOne/repo"
  payload["repository"]["owner"] = { "login" => "OrgTwo" }
  body = payload.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_two_webhook_secret, body)
  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  assert_no_difference -> { Shipit::Stack.count } do
    post :create, body:, as: :json
  end
end
```
Assert both sides of the binding: `repository_owner` derived by the controller (`"OrgTwo"`, matching the signing secret) must NOT equal the owner segment of `params.repository.full_name` (`"OrgOne"`) that the handler uses to resolve and mutate `Stack`/`PullRequest`; the test should fail on current code (`Stack.count` increases) and pass once the fix enforcing owner equality is applied.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

        "repository_owner=#{repository_owner}",

    end

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
