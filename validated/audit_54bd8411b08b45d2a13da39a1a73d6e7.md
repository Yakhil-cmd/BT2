### Title
Unsanitized `machine.directory` from attacker's `shipit.yml` enables path traversal in `DeploySpec::FileSystem#file` and `TaskCommands#steps_directory` - (File: `app/models/shipit/deploy_spec/file_system.rb`, `lib/shipit/task_commands.rb`)

### Summary
`Shipit::DeploySpec::FileSystem#file` and `Shipit::TaskCommands#steps_directory` both build filesystem paths by naively `File.join`-ing `@app_dir`/`@task.working_directory` with the value returned by `DeploySpec#directory`, which is sourced verbatim from `config('machine','directory')` in the review stack's own `shipit.yml`. Because that value is attacker-controlled (it comes from a branch in the attacker's fork) and is never sanitized against `..` traversal, a malicious PR can set `machine.directory: ../../../..` to have Shipit read config files and `chdir` command execution outside the intended per-stack sandbox directory.

### Finding Description
The broken binding: the question claims `file(path, root: false)`'s resolved path == "a path strictly inside `@app_dir/directory`". In code: [1](#0-0) 

`directory` is defined as: [2](#0-1) 

This value comes straight from the parsed `shipit.yml`/`.shipit/shipit.yml` in the checked-out commit, with no validation, escaping, or `Pathname#cleanpath`/`expand_path`+prefix-check. `File.join(@app_dir, directory, path)` performs pure string concatenation; when `directory` contains `../../..`, the OS resolves those `..` components at access time, walking the resulting `Pathname` (or literal string, in `TaskCommands`) above `@app_dir`.

The same unsanitized value is consumed a second, more consequential way in `lib/shipit/task_commands.rb`: [3](#0-2) 

`steps_directory` is passed as `chdir:` to `Command.new` for both dependency installation and deploy/task step execution: [4](#0-3) 

`@task.working_directory` is a fixed, predictable, per-task subdirectory under the stack's shared deploy root: [5](#0-4) 

Call path from the attacker: attacker opens a PR from their fork against a repo with `review_stacks_enabled` + `provisioning_behavior_allow_all`. `Webhooks::Handlers::PullRequest::OpenedHandler#process` → `ReviewStackAdapter#find_or_create!`/`create!` enqueues the new review stack via `Shipit::ReviewStackProvisioningQueue.add`, referenced in `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:72-85` and `app/models/shipit/review_stack_provisioning_queue.rb`. Provisioning and later deploy/task execution eventually call `StackCommands#build_cacheable_deploy_spec` and `TaskCommands#deploy_spec`/`#install_dependencies`/`#perform`, all of which construct `DeploySpec::FileSystem.new(dir_or_working_directory, stack)` and read `directory` straight from the attacker-controlled `shipit.yml` checked out from the fork's branch (`lib/shipit/stack_commands.rb:61-65`, `lib/shipit/task_commands.rb:13-15`).

No existing guard intercepts this: `verify_signature`/webhook auth only prevents payload forgery, not the content of `shipit.yml` on the attacker's own branch (which they legitimately control). `ExplicitParameters`, `Repository`/`Stack` model validations, and `EnvironmentVariables#permit` do not touch `machine.directory`. There is no code anywhere in `DeploySpec::FileSystem#file` or `TaskCommands#steps_directory` that clamps the resolved path to remain inside `@app_dir`/`working_directory`.

### Impact Explanation
Two distinct exploitation surfaces:
1. Config/discovery file read (`DeploySpec::FileSystem#file`, used by `config_file_path`, `capistrano?`, `gemspec`, etc.) — traversal changes which `shipit.yml`/`Gemfile`/`*.gemspec` is discovered and loaded, potentially picking up files from sibling directories on the deploy host.
2. Command execution `chdir` (`TaskCommands#steps_directory`) — this is the more severe path: `Command.new(command_line, env:, chdir: steps_directory)` executes the stack's dependency-install and deploy/task steps with a working directory that can be walked outside the attacker's own sandboxed `@task.working_directory`, into another task's or stack's checkout directory (siblings under the shared deploys root). Since dependency installers (e.g. `bundle install`, `npm install`) execute code found in the target directory's manifest files, this can turn into execution of a script/dependency file belonging to a different tenant's checkout - a cross-tenant "payload from one repo affecting another's stack" scenario, matching the Critical bucket.

### Likelihood Explanation
Requires `review_stacks_enabled` + `provisioning_behavior_allow_all` (or `allow_with_label` if the attacker can self-label their own PR), which are documented, commonly-used configurations for open/low-friction contribution flows. The attacker needs no privileges beyond opening a PR from their own fork with a crafted `shipit.yml` — a normal unauthenticated GitHub contributor action. The exact directory structure of `stack.deploys_path`/`working_directory` must be inferred or brute-forced (relative traversal depth), which adds some friction but is a fixed, low-entropy layout under `Rails.root`/configured deploys path, not a secret.

### Recommendation
In `Shipit::DeploySpec::FileSystem#file`, resolve the joined path with `Pathname#expand_path`/`cleanpath` and assert (raise if not) that the result is still a descendant of `@app_dir` before returning it. Apply the same containment check in `Shipit::TaskCommands#steps_directory` before using it as `chdir:`. Alternatively, reject/sanitize `machine.directory` values containing `..` segments or absolute paths at config-parse time in `DeploySpec#directory`.

### Proof of Concept
```ruby
# test/models/shipit/deploy_spec/file_system_test.rb
test '#file does not escape @app_dir when machine.directory contains traversal' do
  app_dir = '/tmp/shipit-app'
  stack = shipit_stacks(:shipit)
  spec = Shipit::DeploySpec::FileSystem.new(app_dir, stack)
  spec.stubs(:load_config).returns('machine' => { 'directory' => '../../secret' })

  resolved = spec.file('x', root: false).cleanpath.to_s

  assert resolved.start_with?(Pathname.new(app_dir).cleanpath.to_s),
         "expected #{resolved} to stay within #{app_dir}, but it escaped via traversal"
end
```
```ruby
# lib/shipit/task_commands.rb equivalent
test '#steps_directory does not escape task.working_directory' do
  task = shipit_tasks(:running)
  commands = Shipit::TaskCommands.new(task)
  commands.deploy_spec.stubs(:directory).returns('../../other-stack')

  resolved = Pathname.new(commands.send(:steps_directory)).cleanpath.to_s

  assert resolved.start_with?(Pathname.new(task.working_directory).cleanpath.to_s),
         "expected #{resolved} to stay within #{task.working_directory}, but it escaped"
end
```
Both assertions fail against current code, confirming the traversal is unmitigated.
