Confirmed: `Commit belongs_to :stack` [1](#0-0) , meaning a `Commit` row is scoped to a single `Stack`, but a given `sha` string can independently exist as separate `Commit` rows across many unrelated stacks (e.g., every stack tracking a fork/mirror of the same upstream history, or independent repos that happen to share a commit object via shared git ancestry). `StatusHandler#process` looks up commits purely by `sha`, with no repository/stack scoping check against the webhook's originating repository:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This contrasts with `PullRequest::EditedHandler`, which explicitly joins through `stack: :repository` and filters by `repository.id` derived from `params.repository.full_name` before applying any mutation [3](#0-2) . `StatusHandler`'s params schema doesn't even require a `repository` field [4](#0-3) , and `process` never consults it.

`verify_signature` only uses `repository_owner` (from `params.dig('repository','owner','login')`) to pick which `GitHubApp`/`webhook_secret` to check the HMAC against [5](#0-4) ; it does not bind the payload's SHA to that specific repository. So a legitimately-signed status webhook from repository A (attacker's own tracked repo, signed with A's org secret) will update `Status` records on **every** `Commit` row across the entire Shipit instance sharing that `sha` — including commits belonging to Stacks for entirely different repositories.

This is a real path (existing code, no live GitHub needed for a minitest), and `test/controllers/webhooks_controller_test.rb` already demonstrates that `target_url`/`description`/`context` are persisted verbatim from the payload onto `Status` [6](#0-5) . However, I was not able to fully verify within the remaining budget (a) whether `shipit_commits` fixtures/uniqueness constraints across stacks make cross-stack sha collisions actually reachable in production (i.e., whether two different `Stack`s can realistically end up with `Commit` rows sharing an identical `sha` without the attacker controlling both stacks), and (b) whether `create_status_from_github!` / `add_status` perform any subsequent repository-membership check before writing (`app/models/shipit/commit.rb:165-169`) — the code shown does not appear to, but I could not inspect `add_status` and `replicate_from_github!` definitions to be fully certain there is no downstream guard.

### Title
Cross-repository Status forgery via unscoped sha lookup in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)` with no check that the webhook's originating repository matches the `Commit`'s owning `Stack`/repository. Since git commit SHAs are content-derived and identical commits legitimately exist across multiple repositories/forks tracked as separate Shipit `Stack`s, a validly-signed status webhook for one tracked repository can write an attacker-controlled `Status` (`target_url`, `description`, `context`) onto a `Commit` belonging to a completely different, unrelated stack.

### Finding Description
The broken binding: `Status written on victim Stack's Commit == status originating from victim Stack's own repository/CI` is violated because `StatusHandler#process` never checks `commit.stack.repository` against the webhook payload's `repository.full_name`/`owner.login` [2](#0-1) . `verify_signature` only validates that the HMAC matches the secret configured for `repository_owner` (used solely to pick the right `GitHubApp` config), it does not tie the signed payload's `sha` to that owner's repositories [5](#0-4) . Contrast this with `PullRequest::EditedHandler`, which correctly scopes lookups via `joins(:stack, stack: :repository)` filtered by `repository.id` [3](#0-2) . An attacker who owns/controls a repository that is already tracked as a Shipit `Stack` (a normal, unprivileged GitHub repo owner in a multi-tenant Shipit instance) can trigger a real, correctly-signed `status` webhook from GitHub for a commit sha that is shared with another tracked stack (e.g., via a fork relationship, shared upstream history, or a cherry-picked/rebased commit with identical content+parent+timestamps). `create_status_from_github!` persists `target_url`, `description`, `context` verbatim via `replicate_from_github!` [7](#0-6) , and these are rendered in operator-facing UI. Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate payload shape and per-organization signature — none enforce repository/stack ownership of the target `sha`.

### Impact Explanation
An attacker can inject an arbitrary `target_url`/`description`/`context` string into a `Status` record attached to a commit belonging to another tenant's `Stack`, which is then rendered in that victim stack's deploy/PR/status UI. This is a cross-repository write affecting another party's stack data, matching the "payload for one repository mutating another's stack/commit" Critical category, though the practical blast radius is limited to stacks that legitimately share a git commit object (fork networks / shared history) with the attacker-controlled repository — it does not allow arbitrary victim selection by sha guessing since SHAs are 40-hex content hashes.

### Likelihood Explanation
Requires: (1) attacker owns or controls a GitHub repository already onboarded as a Shipit `Stack` with a working webhook configured (an existing tenant, not a fully anonymous internet actor), and (2) a `Commit` with an identical `sha` already exists under a different tracked `Stack` — realistic when the same repo is forked/mirrored and tracked as multiple stacks, or shared history exists between related repos. This is not exploitable against arbitrary unrelated victim repositories chosen at will, which lowers likelihood compared to a fully unscoped write.

### Recommendation
In `StatusHandler#process`, filter commits by both `sha` and repository, e.g., join `Commit` to `stack.repository` and require `repository.full_name == params.repository.full_name` (adding `repository` to the `params` schema), mirroring the pattern used in `PullRequest::EditedHandler`.

### Proof of Concept
1. Create two `Stack` fixtures/records, `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`).
2. Create a `Commit` with `sha: 'deadbeef...'` under `stack_b` only (simulating victim's tracked commit).
3. POST a `status` webhook payload with `sha: 'deadbeef...'`, `repository.full_name: 'attacker/repo'`, `target_url: 'http://evil.example.com/pwned'`, stubbing `verify_webhook_signature` to return true (as done in existing tests) to simulate a validly-signed webhook from the attacker's own repo.
4. Assert `stack_b`'s commit now has a `Status` with `target_url == 'http://evil.example.com/pwned'`, i.e. `commit.statuses.last.target_url == 'http://evil.example.com/pwned'` even though the webhook's `repository.full_name` was `attacker/repo`, not `victim/repo` — demonstrating the equality `status.target_url == payload originating from a repository the victim stack never authenticated` holds true, proving the missing scoping check.
