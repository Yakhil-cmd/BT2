### Title
`has_only()` allowlist bypass via unescaped regex metacharacter `^` in character class - (File: formula/evaluation.js)

### Summary
The oscript `has_only(str, chars)` function is intended to test whether a string consists exclusively of characters from an author-supplied allow-list. It builds a JavaScript `RegExp` directly from the untrusted `chars` argument, blocking only `]` and a trailing `\`, but not `^`. Placing `^` as (or at the start of) the character-class content flips the meaning of the bracket expression from "these characters only" to "any character," exactly mirroring the reported bug class: an incomplete metacharacter blocklist lets one unblocked control character invert the intended allow-list semantics of a downstream interpreter.

### Finding Description
`has_only` is implemented in the evaluation engine: [1](#0-0) 

```
if (op === 'has_only') {
    try {
        console.log('has only ' + str + ' ' + sub);
        if (sub.match(/\\]/) || sub[sub.length - 1] === '\\')
            return setFatalError("invalid character group: " + sub, { arr }, false, cb);
        sub = sub.replace(/]/g, '\\]'); // don't allow to close the group early
        var bMatches = new RegExp("^[" + sub + "]*$").test(str);
    }
    ...
```

The validator side (`formula/validation.js`) performs no additional sanitation of the `chars` operand beyond generic type/complexity checks — it simply evaluates both operands without inspecting their content: [2](#0-1) 

Just as `mcp-shell`'s `security.go` blocked `|&;<>(){}[]$\`` but omitted `!` (the exact character Git needs for its shell-alias escape), `has_only`'s blocklist covers `]` and a trailing `\` (to stop the character class from closing early or leaving a dangling escape) but omits `^`. In a JavaScript/PCRE-style bracket expression, `^` as the very first character inside `[...]` negates the set; an empty negated set `[^]` matches *any* single character (this is a well-known regex quirk, distinct from an ordinary character-class member). Consequently `has_only(str, "^")` (or any allow-string beginning with `^`) does not test "does `str` consist only of the literal `^` character" — it evaluates to true for essentially any string, because `new RegExp("^[^]*$")` matches everything.

This is reachable by any unprivileged AA trigger/definition author: `has_only` is a first-class oscript/AA function exposed through the grammar and evaluator, gated only by the `aa2UpgradeMci` activation flag, with no restriction on who can invoke it or what values flow into either operand. [3](#0-2) 

### Impact Explanation
Any Autonomous Agent (or oscript-evaluating logic) that uses `has_only(input, allowed_chars)` as an allow-list gate for user/trigger-supplied strings before using that string in a spending or accounting decision (e.g., validating a ticker symbol, memo, or key used to index balances/state) can be silently bypassed whenever the character-set argument can begin with `^` (directly, or indirectly via string concatenation the AA author did not anticipate, such as accepting part of the allow-set from `trigger.data`). Instead of rejecting a malformed/unexpected string, the AA would treat it as validated, potentially causing AA fund loss/misdirected payouts or logic bypass. Because the regex evaluation itself is deterministic across all full nodes, this does not, on its own, cause node disagreement/stability forks; the risk is concentrated in AA-level validation being defeated.

### Likelihood Explanation
Exploitation requires an AA design that runs `has_only` with an allow-list string that is even partially influenced by untrusted trigger data (or an AA author simply making the classic mistake of putting `^` at the start of an allow-set string, e.g. `"^A-Z0-9"` intending "letters, digits, and caret" but instead negating the whole set). This is a plausible but not universal pattern; it does not by itself corrupt protocol-level consensus data. Likelihood is therefore moderate — real, deterministic, and trivially triggerable once the pattern exists in an AA, but not a blanket, always-reachable protocol flaw the way the git-alias bug is in `mcp-shell`.

### Recommendation
Harden `has_only` in `formula/evaluation.js` to reject or safely escape `^` (in addition to `]` and trailing `\`) when constructing the character class — e.g., escape it whenever it appears, or reject `chars` strings that begin with `^`, and add the corresponding check to `formula/validation.js` complexity/error path so the same rule is enforced at parse time as at evaluation time. Add regression tests analogous to the existing `has_only invalid escaped ]` / `has_only invalid final \` tests for the `^`-negation case.

### Proof of Concept
Using the existing test harness pattern from `test/formula.test.js`:
```
evalFormulaWithVars(
  { conn: null,
    formula: `has_only("any$tring!contains#unexpected&chars", "^")`,
    trigger: { address: "I2ADHGP4HL6J37NQAD73J7E5SKFIXJOT" },
    locals: {}, stateVars: {}, objValidationState: objValidationState,
    address: 'MXMEKGN37H5QO2AWHT7XRG6LHJVVTAWU' },
  (res) => {
     // Expected (allow-list correctly rejecting unexpected chars): false
     // Actual: true, because new RegExp("^[^]*$") matches any string
     console.log(res);
  }
);
```
This mirrors the referenced report's validation-bypass table: the intended "only `^`" allow-list check silently degrades to "match anything," because the single unblocked metacharacter (`^`) changes the interpretation of the whole expression, just as the unblocked `!` changed the interpretation of Git's `-c alias.NAME=` argument in the original report.
