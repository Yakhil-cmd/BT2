### Title
Unvalidated Zero Destination Address in Service Chain Bridge Request Functions Causes Permanent Loss of Bridged KAIA and Stuck ERC20/ERC721 Transfers — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The service chain bridge's request-side functions (`_requestKLAYTransfer`, `_requestERC20Transfer`, `_requestERC721Transfer`) accept an arbitrary `_to` address without validating it is non-zero. Any unprivileged user can supply `address(0)` as the destination. For KLAY transfers this causes the bridged KAIA to be permanently burned on the destination chain while the source-side KAIA is locked in the bridge forever. For ERC20/ERC721 transfers it creates a permanently stuck bridge nonce: the source-side tokens are burned/locked but every `handleERC20Transfer` / `handleERC721Transfer` attempt on the destination chain reverts, making the funds irrecoverable.

---

### Finding Description

**Root cause — `BridgeTransferKLAY.sol`**

`_requestKLAYTransfer` and its public wrapper `requestKLAYTransfer` accept `_to` without any zero-address guard:

```solidity
// BridgeTransferKLAY.sol L103-L124
function _requestKLAYTransfer(address _to, uint256 _feeLimit, bytes memory _extraData)
    internal unlockedKLAY nonReentrant
{
    require(isRunning, "stopped bridge");
    require(msg.value > _feeLimit, "insufficient amount");
    // ← no require(_to != address(0))
    uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);
    emit RequestValueTransfer(TokenType.KLAY, msg.sender, _to, address(0),
        msg.value.sub(_feeLimit), requestNonce, fee, _extraData);
    requestNonce++;
}

function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData)
    external payable
{
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);   // _to unchecked
}
``` [1](#0-0) 

The bridge operator on the counterpart chain then calls `handleKLAYTransfer` with the same `_to = address(0)`:

```solidity
// BridgeTransferKLAY.sol L98
(bool ok, ) = _to.call.value(_value)("");   // _to == address(0)
require(ok, "handleKLAYTransfer: transfer failed");
``` [2](#0-1) 

In the EVM, a low-level `.call.value(v)("")` to `address(0)` succeeds (`ok = true`). The KAIA is sent to the zero address (burned) on the destination chain, the handle nonce is consumed, and the source-side KAIA remains locked in the bridge forever.

**Root cause — `BridgeTransferERC20.sol`**

`_requestERC20Transfer` and its public wrappers (`requestERC20Transfer`, `onERC20Received`) accept `_to` without a zero-address check:

```solidity
// BridgeTransferERC20.sol L76-L108
function _requestERC20Transfer(
    address _tokenAddress, address _from, address _to,   // _to unchecked
    uint256 _value, uint256 _feeLimit, bytes memory _extraData
) internal onlyRegisteredToken(_tokenAddress) onlyUnlockedToken(_tokenAddress) {
    require(isRunning, "stopped bridge");
    require(_value > 0, "zero ERC20 token amount");
    // ← no require(_to != address(0))
    ...
    emit RequestValueTransfer(...);
    requestNonce++;
}
``` [3](#0-2) 

On the destination chain, `handleERC20Transfer` attempts:
- **lock/unlock mode**: `IERC20(_tokenAddress).safeTransfer(address(0), _value)` → OpenZeppelin ERC20 reverts with `"ERC20: transfer to the zero address"`.
- **mint/burn mode**: `ERC20Mintable(_tokenAddress).mint(address(0), _value)` → OpenZeppelin ERC20 reverts with `"ERC20: mint to the zero address"`. [4](#0-3) 

Because the revert unwinds `_setHandledRequestTxHash` and `_updateHandleNonce`, the handle nonce is never consumed. The bridge operator retries indefinitely and always fails. The source-side tokens are permanently lost (burned in mint/burn mode, or locked in the bridge in lock/unlock mode with no recovery path).

**Root cause — `BridgeTransferERC721.sol`**

Identical pattern: `_requestERC721Transfer` and `requestERC721Transfer` accept `_to` without validation. [5](#0-4) 

On the destination chain, `handleERC721Transfer` calls either `mintWithTokenURI(address(0), ...)` or `IERC721.transferFrom(bridge, address(0), tokenId)`, both of which revert under OpenZeppelin's zero-address guard. [6](#0-5) 

The Go-layer bridge manager (`handleRequestValueTransferEvent`) passes the `to` field from the event directly to the handle call with no zero-address check either: [7](#0-6) 

---

### Impact Explanation

- **KAIA (KLAY) transfers**: Permanent, irreversible loss of bridged KAIA. The source bridge locks the KAIA; the destination bridge sends it to `address(0)` (EVM burn). Both sides finalize successfully, so there is no recovery mechanism.
- **ERC20/ERC721 transfers**: Permanent loss of bridged tokens. Source-side tokens are burned or locked. Destination-side handle transactions revert on every attempt, leaving the bridge in a permanently stuck state for that nonce window. The `requestNonce` on the source is consumed and cannot be replayed.

This satisfies the allowed impact gate: **unauthorized burn and permanent lock of KAIA and bridged assets** caused by a missing invariant check in the bridge's request path.

---

### Likelihood Explanation

Any user interacting with the bridge can trigger this by passing `address(0)` as `_to` in `requestKLAYTransfer`, `requestERC20Transfer`, or `requestERC721Transfer`. No special privilege is required. The call succeeds on the source chain (no revert), so the user receives no on-chain warning. A user who mistakenly or maliciously supplies the zero address will lose their assets with no recourse.

---

### Recommendation

Add a zero-address guard at the entry point of every request function:

```solidity
// BridgeTransferKLAY.sol — _requestKLAYTransfer
require(_to != address(0), "zero destination address");

// BridgeTransferERC20.sol — _requestERC20Transfer
require(_to != address(0), "zero destination address");

// BridgeTransferERC721.sol — _requestERC721Transfer
require(_to != address(0), "zero destination address");
```

Apply the check in the internal `_request*` functions so it covers all public entry points (`requestKLAYTransfer`, `requestERC20Transfer`, `onERC20Received`, `requestERC721Transfer`, `onERC721Received`).

---

### Proof of Concept

1. Deploy the bridge pair (parent + child) as in the existing test harness.
2. Call `requestKLAYTransfer(address(0), value, "0x")` with `msg.value = value + fee` from any EOA.
3. Observe: transaction succeeds, `RequestValueTransfer` event emitted with `to = 0x000...000`, `requestNonce` incremented.
4. Bridge operator picks up the event and calls `handleKLAYTransfer(txHash, from, address(0), value, nonce, blockNum, "0x")`.
5. Observe: `(bool ok,) = address(0).call.value(value)("")` returns `ok = true`; handle nonce consumed; KAIA sent to `address(0)` on destination chain.
6. Source bridge still holds the original KAIA locked. No recovery path exists.

For ERC20: repeat with `requestERC20Transfer(tokenAddr, address(0), value, feeLimit, "0x")`. Observe source tokens burned/locked, then every `handleERC20Transfer` call reverts with `"ERC20: transfer to the zero address"` or `"ERC20: mint to the zero address"`, permanently blocking that nonce.
