### Title
Cross-repository commit-status forgery due to missing repository scoping in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` (`Commit.where(sha: params.sha)`) with no verification that the webhook's originating `repository.full_name` matches the repository owning the found `Commit`/`Stack`, unlike every other handler (`PushHandler`, PR handlers) which scope lookups through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`). A valid, correctly-signed `status` webhook from an attacker-owned repository can therefore forge a `success` status on a commit belonging to a completely unrelated victim stack, as long as the commit SHA matches — which is trivially achievable since a git commit's SHA is a deterministic hash of its own public metadata (tree, parents, author/committer, timestamps, message), all obtainable from the victim's public repo.

### Finding Description
The claimed binding, made explicit: `commit.stack.github_repo_name (repository the forged Status is attributed to) == payload['repository']['full_name'] (repository that actually emitted the webhook)`. This binding is never checked.

- `StatusHandler` params schema requires only `sha`, `state`, and optional fields — it never requires or reads `repository` at all: [1](#0-0) 
- `process` resolves commits globally by SHA and applies the forged state to every match, regardless of which repository the webhook came from: [2](#0-1) 
- Contrast with `PushHandler`, which correctly scopes to the repository via the shared `stacks` helper: [3](#0-2) 
- The shared base `Handler#stacks`/`repository_name` helper (built for exactly this scoping) exists but is not used by `StatusHandler`: [4](#0-3) 
- `WebhooksController#verify_signature` only checks that the payload is authentically from GitHub for `repository_owner`'s org — it says nothing about whether that repository is the one that "owns" the SHA being reported: [5](#0-4) 

Exploit flow:
1. Attacker identifies a public commit in the victim's tracked repo (SHA, tree, parents, author/committer, timestamps, message — all public via `git log`/API).
2. Attacker reproduces a byte-identical commit object (same SHA) inside a repository they own that is within scope of the same Shipit GitHub App installation (a capability the attacker already has per the threat model: "emit webhooks from a repository they own").
3. Attacker calls GitHub's Statuses API on their own repo/commit with `state: success` (they have write access to their own repo) — GitHub sends a correctly signed `status` webhook to Shipit for the attacker's repository.
4. `WebhooksController#verify_signature` passes — the signature is legitimately from GitHub for that org.
5. `StatusHandler#process` matches `Commit.where(sha: ...)` and finds the victim's `Commit` (same SHA, different stack), and calls `commit.create_status_from_github!(params)`, moving `commit.state` to `success`.
6. `Status#schedule_continuous_delivery` / `add_status` fire (`stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`), potentially triggering continuous delivery on the victim stack.
7. If `stack.release_status?` is enabled, the resulting `Deploy` calls `update_release_status` → `append_release_status` → `Commit#create_release_status!`, creating `ReleaseStatus` rows: [6](#0-5) [7](#0-6) 
8. `ReleaseStatus#create_status_on_github!` then posts back to GitHub using `stack.github_api` (victim's own credentials) against `stack.github_repo_name` (the real victim repo), attesting to deploy progress that was never validated by that repo's own CI: [8](#0-7) 

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) checks repository identity for the `status` event, so the divergence is real.

### Impact Explanation
The victim stack's own GitHub credentials (`stack.github_api`) are used to write a `create_status` call to the victim's real repository, and the victim's `Commit#state` becomes `success` from a signal that never touched that repository's CI or code review. This can move an untested commit through `deployable?`/continuous-delivery gating and can trigger `ReleaseStatus` writes attesting false deploy health to GitHub — a payload from one repository mutating another's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any commit whose full metadata is public (any public repo commit), and against any number of victim stacks tracking the same commit SHA (e.g. shared/forked history), since the lookup is fully global (`Commit.where(sha:)`, unscoped by stack).

### Likelihood Explanation
Preconditions: victim stack has `release_status?` enabled (for the ReleaseStatus write-back sub-path) or simply relies on CI status for deploy gating (for the broader `Commit#state` forgery). The attacker needs a repository under the scope of a Shipit-connected GitHub App installation that they can emit real, GitHub-signed webhooks from — explicitly granted as an attacker capability in this threat model. Reproducing an identical commit SHA is not a hash collision; it's a deterministic re-creation of a git object from its own public fields, which is straightforward with `git commit-tree`/`git hash-object` and matching author/committer dates. No secrets are required at any step.

### Recommendation
Scope `StatusHandler#process` by repository, mirroring `PushHandler`/`Handler#stacks`: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(...)`, and only update `Status`/`Commit` records that belong to that repository's stacks (e.g., filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { id: stacks.ids })` or equivalent), rather than matching on `sha` alone across the entire database.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or add to `test/controllers/webhooks_controller_test.rb`):
```ruby
test "a status webhook for repository A does not create a Status for a commit belonging to repository B with the same sha" do
  victim_stack = shipit_stacks(:shipit) # repo == "shopify/shipit-engine"
  shared_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)

  attacker_repository_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulates a validly signed webhook from attacker's own org/app

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body: attacker_repository_payload.to_json, as: :json
  end

  assert_not_equal 'success', victim_commit.reload.state
end
```
Assert both sides of the binding explicitly:
```ruby
assert_not_equal victim_stack.github_repo_name, attacker_repository_payload['repository']['full_name']
# then assert the forged status was NOT applied to victim_commit
```
Currently this test would fail against `StatusHandler#process`, since it matches by SHA alone.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
