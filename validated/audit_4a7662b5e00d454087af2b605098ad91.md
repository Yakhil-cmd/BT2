### Title
Unconstrained `creator` account in permissioned pool creation lets a whitelisted payer assign `pool_creator` fee rights to an arbitrary, non-whitelisted address - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` gates who may create a "permissioned" pool by requiring the `payer` to own a valid `Permission` PDA, but it records an entirely separate, unconstrained `creator` account as `pool_state.pool_creator`, the identity that later gains the on-chain right to sign for and collect accumulated creator fees.

### Finding Description
In `InitializeWithPermission`, the authorization check is bound to `payer`: the `permission` account must exist at `PERMISSION_SEED + payer.key()`, which is only created by the program `admin`/`create_permission_pda_owner` via `create_permission_pda`. [1](#0-0) 

However, the `creator` field used to identify the *beneficiary* of pool-creator privileges is declared as a bare `UncheckedAccount` with no constraint tying it to `payer`, to the `permission.authority`, or to any signer at all: [2](#0-1) 

`pool_state.initialize(...)` then stores `ctx.accounts.creator.key()` directly as `pool_creator`, without any relationship check to the permissioned identity that authorized the call: [3](#0-2) 

By contrast, in the standard, non-permissioned `initialize` instruction there is only a single `creator` role, which is a `Signer` that both pays for and receives the pool-creator identity — there is no split between "who is authorized" and "who is recorded as creator": [4](#0-3) 

This mirrors the MantisBT bug class: a low-privileged/whitelisted actor performs an action they are authorized to perform (create a pool via `initialize_with_permission`), but by tampering with an identity parameter (`creator`, analogous to MantisBT's `user_id`) unrelated to the authorization check (which is keyed to `payer`), they can assign the resulting privileged record (`pool_creator`, which grants a permanent right to sign `CollectCreatorFee` and receive the pool's creator fee stream) to any arbitrary account of their choosing, decoupled from the actual permission grant.

### Impact Explanation
`pool_creator` is a persistent, signer-gated privilege: only the recorded `pool_creator` can sign for `collect_creator_fee`, and even the permissionless variant `collect_creator_fee_permissionless` still routes all collected fees to `pool_state.pool_creator`. [5](#0-4) [6](#0-5) 

Because `creator` in `initialize_with_permission` is not required to be the whitelisted `payer`/`permission.authority`, the whitelisting mechanism does not actually restrict who benefits from the "permissioned" pool-creator role it is meant to gate. A permissioned payer can assign `pool_creator` to any address of their choice — including one they control that never went through the admin's whitelisting process, or (as a griefing vector) an address with no private key at all, permanently locking the accumulated `creator_fees_token_0`/`creator_fees_token_1` since no valid signer will ever be able to satisfy the `address = pool_state.load()?.pool_creator` constraint in `collect_creator_fee`, and `collect_creator_fee_permissionless` will keep funding an ATA nobody can withdraw from. This is a fee-ledger/asset-freezing issue rooted in the missing binding between the authorization check and the privileged identity field.

### Likelihood Explanation
Any account holding a valid `Permission` PDA (an intended, lower-trust "whitelisted pool creator" role) can trivially exploit this in a single transaction by simply passing an arbitrary pubkey as the `creator` account — no additional signatures, special timing, or non-default features are required. The only precondition is possessing a `Permission` PDA, which is the exact scope this instruction is meant to be reachable by.

### Recommendation
Add an explicit Anchor constraint tying `creator` to the account that was actually authorized, e.g. `constraint = creator.key() == permission.authority` (or require `creator` to be a `Signer` equal to `payer`), so the identity recorded as `pool_creator` cannot diverge from the account whose permission was actually verified.

### Proof of Concept
1. Admin runs `create_permission_pda` with `permission_authority = Alice`, creating a `Permission` PDA at `[PERMISSION_SEED, Alice]`. [7](#0-6) 
2. Alice calls `initialize_with_permission` as `payer` (so the `permission` PDA seed check passes), but passes `creator = Mallory` (or a burn/black-hole address), an account with no relation to `Permission.authority`.
3. `pool_state.pool_creator` is set to `Mallory`'s key even though only Alice was ever whitelisted. [3](#0-2) 
4. Going forward, only `Mallory` can sign `collect_creator_fee`; if `Mallory` is an address with no known private key, the pool's accumulated `creator_fees_token_0`/`creator_fees_token_1` become permanently unclaimable, even via the permissionless path, since the ATA authority is fixed to `pool_creator`. [8](#0-7)

#[derive(Accounts)]
pub struct CreatePermissionPda<'info> {
    #[account(
        mut,
        constraint = (owner.key() == crate::admin::ID || owner.key() == crate::create_permission_pda_owner::ID) @ ErrorCode::InvalidOwner
    )]
    pub owner: Signer<'info>,

    /// CHECK: permission account authority
    pub permission_authority: UncheckedAccount<'info>,

    /// Initialize config state account to store protocol owner address and fee rates.
    #[account(
        init,
        seeds = [
            PERMISSION_SEED.as_bytes(),
            permission_authority.key().as_ref()
        ],
        bump,
        payer = owner,
        space = Permission::LEN
    )]
    pub permission: Account<'info, Permission>,

    pub system_program: Program<'info, System>,
}

pub fn create_permission_pda(ctx: Context<CreatePermissionPda>) -> Result<()> {
    let permission = ctx.accounts.permission.deref_mut();
    permission.authority = ctx.accounts.permission_authority.key();
    Ok(())
}
