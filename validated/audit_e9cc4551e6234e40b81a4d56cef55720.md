### Title
Stack-scoped API token bypasses its stack restriction in the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the `stack` lookup helper to resolve `params[:stack_id]` against the global `Stack` table instead of the token-scoped `stacks` relation used everywhere else in the API, so a token that is supposed to be restricted to one stack can read the CI status of any stack.

### Finding Description
`Api::BaseController` enforces stack scoping for every other API controller through two cooperating methods: `stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is scoped to a stack, and `stack`, which resolves the requested resource via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, which only checks that the client's `permissions` array contains `read:stack` — it never checks which stack the permission applies to. [2](#0-1) [3](#0-2) 

Crucially, `CCMenuController` redefines the private `stack` method to bypass the scoped `stacks` relation entirely, resolving directly against the unscoped `Stack` model:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This is the same bug class as the reported issue: a security-relevant equality (`current_api_client.stack_id == requested stack`) is expected to be enforced but the code path that actually looks up the resource never performs that comparison — it only calls `Stack.from_param!`, which succeeds for any stack in the database, not just the one the token is scoped to. `#show` then renders build/deploy state for whatever stack was resolved: [5](#0-4) 

The binding that should hold is: `token.stack_id (the stack an ApiClient is authorized for) == stack.id (the stack whose state is rendered)`. Before the request, this equality is guaranteed by `BaseController#stacks`/`#stack`. After `CCMenuController` overrides `#stack`, the equality is never checked, so an attacker holding a token scoped to stack A can supply `stack_id` for stack B and still receive B's data.

### Impact Explanation
An attacker who has obtained any valid `ApiClient` token with `read:stack` permission that is deliberately scoped to a single stack (e.g. a CCMenu client created via `CCMenuUrlController`, which always creates a `read:stack`-only, stack-scoped client) can enumerate other stacks' names/slugs and read their CI build status, last build label/time, and web URL for any stack in the Shipit instance — not just the one the token was issued for. This is an unauthorized read of stack state across a supposed authorization boundary, matching the "High" impact category of "escalation into `Shipit.github_teams` authorization... or unauthenticated/unauthorized read of stack state." [6](#0-5) 

### Likelihood Explanation
Exploitation requires only a legitimately-issued, narrowly-scoped `ApiClient` token (e.g., one generated automatically for the CCMenu widget, or handed to a third-party CI dashboard integration) and knowledge/guessing of another stack's `to_param` (owner/repo/environment), which is often predictable or discoverable. No privileged access, secret material, or additional authentication is needed beyond the token the attacker already legitimately possesses for their own stack.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the stack-scoping check performed for every other API endpoint is also enforced here.

### Proof of Concept
1. Obtain (or have Shipit auto-generate via `CCMenuUrlController#fetch`) a `read:stack`-only `ApiClient` token scoped to `stack_id = A`.
2. Send `GET /api/{owner}/{repoB}/{env}/ccmenu.xml?token=<token-scoped-to-A>` for a different stack `B`.
3. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` succeeds (token has `read:stack` in its permissions array), and `stack` resolves `B` via the unscoped `Stack.from_param!`, returning `B`'s CI/build status even though the token is only authorized for `A`. [7](#0-6)
