### Title
Webhook signature is verified against the payload's `repository.owner.login`, but every event handler acts on the independently-supplied `repository.full_name` — allowing a webhook authenticated for one GitHub org to forge events (fake CI status, spoofed pushes, PR/label actions) against a stack owned by a completely different org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . However, once the signature check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` (and every subclass: `PushHandler`, `StatusHandler` indirectly via `Commit.where(sha:)`, the `PullRequest::*Handler`s, etc.) resolves the *target* repository/stack from a **different, independently-controlled field**: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties `repository.owner.login` (the field cryptographically bound to the HMAC secret selection) to `repository.full_name` (the field that actually drives which stack/commit gets mutated). Since `Shipit.github(organization:)` supports multiple independently configured GitHub orgs, each with its own `webhook_secret` (as seen in the multi-org fixtures) [4](#0-3) , this breaks the equality that should hold: `organization whose secret authenticated the request == organization owning the repository that gets written to`.

### Finding Description
1. `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches the `GitHubApp` config for *that* org to check the HMAC signature [1](#0-0) .
2. If verification succeeds, `create` dispatches the *entire raw JSON payload* to all registered handlers for the event, unmodified [5](#0-4) .
3. `Handler#stacks` / `#repository_name` look up the target `Repository` using `payload.dig('repository', 'full_name')` — a completely separate JSON field from `repository.owner.login` [3](#0-2) .
4. `StatusHandler#process` finds commits purely `Commit.where(sha: params.sha)` with no repository/org check at all, and calls `commit.create_status_from_github!(params)` [6](#0-5) , meaning a webhook whose signature was verified against Org A's secret can create a commit status on *any* commit tracked by Shipit, regardless of which org/repo it actually belongs to.
5. Similarly `PushHandler` resolves stacks via `repository_name` (from `full_name`) unrelated to which org's secret authenticated the request, and calls `stack.sync_github(expected_head_sha: params.after)` on stacks under a different org than the one that signed the webhook [7](#0-6) .

Concretely: if Shipit is configured for two independent GitHub organizations "OrgA" (attacker-influenced, e.g., attacker is a legitimate webhook-sender for a repo under OrgA) and "OrgB" (victim org, unrelated), an attacker who can trigger/craft a webhook delivery signed with OrgA's `webhook_secret` can set `repository.owner.login = "OrgA"` (to pass signature verification) while setting `repository.full_name = "OrgB/victim-repo"` (to target OrgB's tracked stack). The signature check passes because it only validates against OrgA's secret and never confirms that OrgA actually owns `full_name`.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credential authenticated the webhook" and "the repository whose state is mutated." Concretely reachable impacts:
- Forging `commit_status` events (`StatusHandler`) to mark arbitrary tracked commits (in any org's stack) as passing CI, which can influence/bypass deploy-safety gating decisions elsewhere in the engine that key off commit statuses.
- Forging `push` events to trigger `sync_github`/deploy pipeline actions on stacks belonging to an org the attacker doesn't control.
- Forging `pull_request` label/assignment/review-stack events to archive/unarchive or otherwise manipulate review stacks belonging to a different org's repository.

This matches the "High" tier described in scope (escalation into authorization decisions / unauthenticated write into task/stack state) since it lets a webhook authenticated for one org effectively act on a stack/repository never authenticated by that secret.

### Likelihood Explanation
Requires the attacker to be able to get *some* correctly-signed webhook delivered for an org configured in the Shipit instance (e.g., by controlling or compromising any repository/org that legitimately delivers webhooks to this Shipit deployment), then crafting the JSON body so `repository.owner.login` matches their own org while `repository.full_name` names the victim's tracked repository. This is only meaningful in multi-org Shipit deployments (which the codebase explicitly supports and ships fixtures for), and is not gated by any additional secret beyond the one the attacker already legitimately possesses for their own org.

### Recommendation
In `verify_signature` / `Handler`, enforce that the org used to select and validate the webhook secret is the same org that owns `repository.full_name` (or `organization.login`) used by the handlers — i.e., derive a single canonical "owning org" value once, verify the signature against it, and pass/validate that same value down into `Handler#stacks`/`#repository_name` resolution, rejecting payloads where the two disagree.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `secrets_double_github_app.yml`).
2. Track a repository/stack under `OrgB` (`OrgB/victim-repo`).
3. As a user with legitimate webhook-signing capability for `OrgA` (e.g., admin of any repo under `OrgA` configured to deliver webhooks to this Shipit instance), craft a `status` event payload:
```json
{
  "sha": "<victim commit sha in OrgB/victim-repo>",
  "state": "success",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Sign the payload body with `OrgA`'s `webhook_secret` and send it as `X-Hub-Signature` to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner => "OrgA"`, validates successfully against `OrgA`'s secret [1](#0-0) .
6. `StatusHandler` finds the commit purely by `sha` (no org check) and records the forged status against `OrgB`'s commit [6](#0-5) , despite `OrgA` never having any authority over `OrgB/victim-repo`.
