### Title
Automatic rollback-on-abort bypasses the rollback environment-variable whitelist enforced on manual rollbacks - (File: app/models/shipit/deploy.rb)

### Summary
`Shipit::Api::RollbacksController#create` enforces an environment-variable whitelist by calling `stack.filter_rollback_envs(params.env)` before building a rollback [1](#0-0) . `filter_rollback_envs` delegates to `EnvironmentVariables#permit`, which raises unless every key is present in the stack's `rollback_variables` list [2](#0-1) [3](#0-2) . However, `Deploy#trigger_revert_if_required`, which fires automatically when a deploy is aborted with `rollback_once_aborted`, never calls this filter: it passes the *deploy's own* `env` (permitted only against `deploy_variables`) straight into `trigger_rollback`/`trigger_revert`, which store it verbatim on the new `Rollback` task [4](#0-3) [5](#0-4) .

### Finding Description
The engine's rollback whitelist model relies on an equality that is supposed to be enforced on every path that spawns a rollback: `keys(spawned rollback env) ⊆ rollback_variables`. `deploy_spec.rb` explicitly defines `rollback_variables` as an independent, potentially smaller/stricter list than `deploy_variables` (it only falls back to `deploy_variables` when no rollback-specific variables are configured) [6](#0-5) . The manual path (`RollbacksController#create`) respects this by filtering the caller-supplied `env` with `filter_rollback_envs` before calling `deploy.trigger_rollback` [1](#0-0) .

The automatic path does not:
- `Deploy#trigger_revert_if_required` is invoked via the `aborted` state-machine transition (`after_transition to: :aborted, do: :trigger_revert_if_required`) [7](#0-6) .
- It calls `rollback_once_aborted_to.trigger_rollback(aborted_by, env:, force: true)` or `trigger_revert(force: true, env:)`, where `env` resolves to the aborted deploy's own stored `env` attribute (whitelisted only against `deploy_variables` at deploy-creation time) [4](#0-3) .
- `trigger_revert`/`build_rollback` write this env directly onto the new `Rollback` record with no call to `filter_rollback_envs`/`EnvironmentVariables#permit` [5](#0-4) .
- That stored, unfiltered env is later merged verbatim into the actual process environment used to spawn the rollback's shell commands via `TaskCommands#env` (`.merge(@task.env)`) [8](#0-7) .

This breaks the intended binding: *environment key permitted (for the original deploy, via `deploy_variables`) ≠ environment key spawned (into the rollback's process environment, which should be constrained by the distinct `rollback_variables` whitelist)*. Any key configured as deploy-only (e.g. a dangerous flag intentionally excluded from `rollback.variables` in `shipit.yml` because it is unsafe during rollback) still reaches the rollback task's shell environment as long as it was accepted at deploy time and the deploy is subsequently aborted with `rollback_once_aborted: true`.

### Impact Explanation
This lets a user who only has ordinary "trigger deploy" permission smuggle deploy-only environment variables into a rollback execution context that `shipit.yml` explicitly restricts via `rollback.variables`, bypassing an authorization control the operator configured to keep rollbacks safe (e.g., preventing `FORCE`-style dangerous flags from ever reaching rollback scripts). Since these environment variables are consumed directly by shell commands executed on the deploy host (`Command#unbundled_env`) [9](#0-8) , depending on how the operator's `shipit.yml` scripts consume unwhitelisted variables, this can enable unintended/unauthorized behavior during an automatically-triggered rollback that the whitelist was specifically designed to prevent — an unauthorized rollback behavior change that the stack owner's configuration did not sanction for that code path.

### Likelihood Explanation
Requires only standard "trigger deploy" capability (already needed to create any deploy) plus setting `rollback_once_aborted: true` and then aborting the deploy — both are normal, documented deploy-controller actions, no elevated Shipit role or GitHub write access beyond existing deploy permission is needed. The `rollback_variables`/`deploy_variables` divergence is an intentional, supported `shipit.yml` feature [6](#0-5) , so any stack configured to restrict rollback variables differently from deploy variables is exposed.

### Recommendation
Apply `stack.filter_rollback_envs(env)` inside `Deploy#trigger_revert_if_required` / `Deploy#trigger_revert` / `Deploy#build_rollback` before persisting the env on the `Rollback` record, mirroring the enforcement already done in `RollbacksController#create`, so automatically-triggered rollbacks are held to the same `rollback_variables` whitelist as manually-triggered ones.

### Proof of Concept
1. Configure `shipit.yml` with `deploy.variables: [{name: FORCE}]` and `rollback.variables: []` (or a set excluding `FORCE`), and `rollback_once_aborted` behavior enabled on the stack.
2. Trigger a deploy with `env: {FORCE: "1"}` via the normal deploy API — accepted because `FORCE` is whitelisted in `deploy_variables`.
3. Abort that deploy with `rollback_once_aborted: true` (a normal deploy-aborting action).
4. `Deploy#trigger_revert_if_required` fires and creates a `Rollback` whose `env` is the aborted deploy's `env` (`{FORCE: "1"}`), never passed through `filter_rollback_envs` [4](#0-3) .
5. The rollback task executes with `FORCE=1` in its shell environment despite `FORCE` not being present in `rollback.variables`, whereas an equivalent manual rollback request with `env: {FORCE: "1"}` would be rejected by `RollbacksController#create` with "Variables FORCE have not been whitelisted" [1](#0-0) [10](#0-9) .

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end

    # Rolls the stack back to this deploy
    def trigger_rollback(user = AnonymousUser.new, env: nil, force: false, lock: true)
      rollback = build_rollback(user, env:, force:)
      rollback.save!
      rollback.enqueue

      if lock
        lock_reason = "A rollback for #{rollback.since_commit.sha} has been triggered. " \
          "Please make sure the reason for the rollback has been addressed before deploying again."
        stack.update!(lock_reason:, lock_author_id: user.id)
      end

      rollback
    end

    # Rolls the stack back to the most recent **previous** successful deploy
    def trigger_revert(force: false, rollback_to: nil, env: nil)
      previous_successful_commit = rollback_to&.until_commit || commit_to_rollback_to

      rollback = Rollback.create!(
        user_id:,
        stack_id:,
        parent_id: id,
        since_commit: until_commit,
        until_commit: previous_successful_commit,
        env: env || self.env,
        allow_concurrency: force
      )

      rollback.enqueue
      lock_reason = "A rollback for #{until_commit.sha} has been triggered. " \
        "Please make sure the reason for the rollback has been addressed before deploying again."
      stack.update!(lock_reason:, lock_author_id: user_id)
      stack.emit_lock_hooks
      rollback
    end
