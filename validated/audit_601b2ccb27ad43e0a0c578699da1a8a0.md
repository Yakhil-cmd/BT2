### Title
Legacy Ethereum transactions without a `chain_id` bypass EIP-155 replay protection in `pallet-revive`, enabling cross-chain replay of unprotected transactions - ([File: substrate/frame/revive/src/evm/call.rs])

### Summary
`pallet-revive`'s `GenericTransaction::into_call` (the Ethereum-compatible transaction acceptance path reachable via the public `eth_transact` extrinsic) explicitly permits **legacy** Ethereum transactions with `chain_id == None` to be processed, without requiring the destination to be a contract-creation (`to == None`). This is the same "EIP-155 not enforced" condition described in the zkSync report: a signed transaction whose signature does not bind the `chain_id` can be broadcast/replayed on the Polkadot-SDK chain exactly as it was originally signed on Ethereum (or any other chain), and the recovered signer/nonce checks do not prevent this for a signer's first-ever transaction.

### Finding Description
The entry point is the public, permissionless `Call::eth_transact { payload }` extrinsic, whose `payload` is checked in `EthExtra::try_into_checked_extrinsic`: [1](#0-0) 

This calls `tx.into_call::<T>(...)`, which performs the chain-id check: [2](#0-1) 

The comment explicitly documents the design decision: legacy (`TYPE_LEGACY`) transactions with `chain_id == None` are accepted, mirroring the pre-EIP-155 signing scheme. Critically, this branch is **not** restricted to contract-creation transactions (`to == None`); it accepts any legacy transaction lacking a `chain_id`, including plain value/call transactions with `to` set.

The recovery/verification code confirms the signature itself never binds to chain identity when `chain_id` is absent: [3](#0-2) [4](#0-3) 

The signer address is derived purely from `secp256k1` recovery over the RLP-encoded 6-field payload (no chain id included), then deterministically mapped to a native account via the stateless fallback mapper: [5](#0-4) [6](#0-5) 

Because `to_fallback_account_id` is a stateless, deterministic function of the `H160` address (no on-chain registration required for secp256k1-derived accounts), any Ethereum address's fallback Polkadot account is fully determined by the address alone — identical across every chain using the same mapper. This is exactly analogous to the zkSync report's core observation: an unprotected legacy transaction signed for use on one EVM network is valid input on a completely different chain because nothing in the payload or signature binds it to a specific chain, and the destination account derivation is chain-independent.

This behavior was intentionally introduced by PR #10476 ("Allow for Nick's Method style deployments"), explicitly to support cross-chain deterministic deployments; the PR removed the enforcement that "any transaction without a chain id would fail with Invalid Transaction," changing the check to accept `(None, Some(TYPE_LEGACY))`. The stated purpose was singleton-factory-style contract deployment, but the actual code path does not gate the exemption on `to.is_none()` (contract creation).

### Impact Explanation
If a user's Ethereum-style secp256k1 keypair ever produced a pre-EIP-155 unprotected legacy transaction on Ethereum (or any other EVM chain) — historically common for transactions signed before 2016, and still producible today by any signer that omits `chain_id` — and that user later funds their `pallet-revive` fallback account (which is deterministically derived from the same address, with no opt-in), an attacker who has observed that historical unprotected transaction can resubmit it verbatim via `eth_transact` on the Polkadot-SDK chain. If the transaction's encoded nonce matches the current nonce of the victim's fallback account on this chain (most plausibly nonce `0`, i.e., a signer's very first transaction, which trivially matches a never-used fallback account), the transaction will be accepted, recovered as the victim's signer, and dispatched — moving funds or invoking arbitrary calls as that account, exactly as described in the zkSync report ("attacker replays A's early transaction to steal A's funds, or benefits an unrelated party B who was the original tx's recipient").

This matches the "Medium" classification the zkSync judges converged on: it requires a specific, narrow precondition (an unprotected legacy transaction existing and the victim's fallback account nonce lining up), it is a deliberate design tradeoff (confirmed by the code comment and PRDoc), and it does not require any privileged role — just a public signed payload input to a real, wired extrinsic (`eth_transact`).

### Likelihood Explanation
Low-to-Medium. Exploitability requires: (1) a real, observable unprotected legacy Ethereum transaction signed by the victim (these exist historically, and can also be freshly crafted by a user unaware of chain-id binding), and (2) the victim's fallback account nonce on the target chain matching the transaction's nonce (trivially true for a first-ever transaction, nonce 0). The `CheckNonce`-style validation on the mapped fallback account (see `check_eth_transact_nonce_works` test) prevents replay once nonce has advanced, limiting the practical window largely to first-transaction scenarios, but this is not a hardened defense — it's incidental to nonce tracking, not chain-identity binding. The intentional design (Nick's-Method PR) that widened the exemption beyond deployment-only cases increases exposure versus a narrower "creation-only" exemption.

### Recommendation
Restrict the unprotected-legacy-transaction exemption strictly to contract-creation transactions (`to.is_none()`), matching the stated "Nick's Method" deployment use case, e.g.:
```rust
match (self.chain_id, self.r#type.as_ref(), self.to) {
    (None, Some(super::Byte(TYPE_LEGACY)), None) => {}, // creation only
    (Some(chain_id), ..) => { /* existing check */ },
    _ => { return Err(InvalidTransaction::Call); },
}
```
This preserves the deterministic cross-chain deployment use case while eliminating the ability to replay unprotected legacy *value/call* transactions that move funds or invoke state-changing calls on behalf of a signer whose fallback account exists on this chain.

### Proof of Concept
Not executed against a live network (per instructions). Deployment/reachability evidence:
- The vulnerable branch is live production code in `substrate/frame/revive/src/evm/call.rs:85-97`, reached from the permissionless `Call::eth_transact` extrinsic decoding path in `substrate/frame/revive/src/evm/runtime.rs:338-434`, which is wired into runtimes such as the kitchensink node (`substrate/bin/node/runtime/src/lib.rs:3086-3088`) and Asset Hub Westend (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs:1780-1811`).
- Existing unit test `check_eth_transact_chain_id_works` (`substrate/frame/revive/src/evm/runtime.rs:710-718`) confirms a *mismatched* chain id is rejected, but no existing test asserts rejection of a `chain_id = None` transaction with `to` set to a non-null address (only the creation case is tested via `contract_deployment_with_nick_method_works`, `substrate/frame/revive/src/evm/runtime.rs:828-871`). This gap is consistent with the code path allowing `to.is_some()` unprotected transactions to pass, though I was not able to execute a full local repro (build the pallet-revive mock, craft a raw legacy RLP tx with `to` set and no chain id, sign it, and assert `into_call`/`check` succeeds) within this session — this would need to be run in a Devin session with cargo/test-harness access to obtain a concrete pass/fail result confirming the `to.is_some()` unprotected case is accepted at `check_eth_transact_chain_id_works`-style granularity.
- The intentional-design nature and its stated rationale (deployment-only) versus the actual code's broader scope (no `to.is_none()` gate) is documented in `prdoc/stable2512-1/pr_10476.prdoc:1-58`.

impl TransactionLegacySigned {
	/// Get the recovery ID from the signed transaction.
	/// See https://eips.ethereum.org/EIPS/eip-155
	fn extract_recovery_id(&self) -> Option<u8> {
		if let Some(chain_id) = self.transaction_legacy_unsigned.chain_id {
			// self.v - chain_id * 2 - 35
			let v: u64 = self.v.try_into().ok()?;
			let chain_id: u64 = chain_id.try_into().ok()?;
			let r = v.checked_sub(chain_id.checked_mul(2)?)?.checked_sub(35)?;
			r.try_into().ok()
		} else {
			self.v.try_into().ok()
		}
	}
}
