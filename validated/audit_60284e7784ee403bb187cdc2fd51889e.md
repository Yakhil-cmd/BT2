### Title
`LD_PRELOAD` injection via uppercased PR label name reaches `deploy.override` process spawn - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges PR label names, uppercased, directly into the stack's environment hash with no key allowlist, and `LabelCapturingHandler` persists label names verbatim from the webhook payload. Because `TaskCommands#env` merges `@stack.env` into the environment ultimately passed to `Command#start`, which merges it into `PTY.spawn`'s environment via `unbundled_env`, an attacker-controlled key such as `LD_PRELOAD` set via a label named `ld_preload` propagates into every spawned process for the review stack's deploy, including the `deploy.override` step.

### Finding Description
The broken binding: `ReviewStack#env` keys should be restricted to keys the operator intends to expose (e.g. a controlled allowlist/prefix), but instead `env == super.merge(pull_request.labels.map(&:upcase) => "true")` with **no filtering** [1](#0-0) .

Path: `LabelCapturingHandler#capture_labels` takes `params.pull_request.labels.map(&:name)` straight from the webhook JSON body and stores it as `pull_request.labels`, with the only params-schema constraint being `String` [2](#0-1) . The label name comes from the PR author's own GitHub repository (a label they created/named on their fork, or on a PR to the base repo, they can label since it's their own PR) or from a webhook - either way, an attacker unprivileged user labeled their own PR "ld_preload".

At deploy time, `TaskCommands#env` merges `@stack.env` (which is `ReviewStack#env`, containing `LD_PRELOAD => "true"`) into the env passed to `Command.new(..., env:, chdir: steps_directory)` for every step, including `deploy.override` steps [3](#0-2) [4](#0-3) . `Command#start` then calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` where `unbundled_env` is `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — i.e. the label-derived `LD_PRELOAD` key overrides `BASE_ENV`'s value (or introduces the key if absent) and is passed to `PTY.spawn` [5](#0-4) .

No existing guard prevents this: there is no allowlist or blocklist on label-derived environment keys in `ReviewStack#env`, and `EnvironmentVariables#permit` (used elsewhere to sanitize interpolated env-var references in shipit.yml) is not applied to this hash. The `params` schema in the webhook handler only validates types (`String`), not values, so any label name is accepted.

### Impact Explanation
An attacker who can label their own pull request on a `prevent_with_label`-configured repository can set `LD_PRELOAD` (or any other environment variable name uppercased) for every command run for that review-stack's deploy, task, and rollback commands — including `deploy.override`. This lets the attacker preload an arbitrary shared object supplied via the fork's own build artifacts into every subprocess spawned by the deploy host for that stack, achieving code execution on the Shipit deploy host in the context of the deploy process. This matches the Critical RCE class (`Command`/`PTY.spawn`) described in the rules. Blast radius is scoped to the review stack for that repository/PR (env is stack-specific), but since the attacker fully controls the fork's PR and can label it repeatedly, the exploit is trivially repeatable.

### Likelihood Explanation
Preconditions: the repository must use review stacks with `provisioning_behavior: prevent_with_label` (or any review-stack setup) and the fork PR's `deploy.override` (or any step) shipit.yml section must run some command that can load a shared library (most executables via libc, e.g. anything using dynamic linking) — attacker fully controls their own shipit.yml on the fork, so this is trivially satisfiable. Attacker cost is minimal: create a PR, add a label named `ld_preload`, ensure a step executes a dynamically linked binary, and drop a malicious `.so` in the build directory. No secrets or elevated privileges are required — any GitHub user who can open a PR and add a label to their own PR can do this.

### Recommendation
Restrict `ReviewStack#env` to only emit a safe, prefixed key or an explicit allowlist derived from label names (e.g. only pass through labels matching a strict pattern like `SHIPIT_LABEL_<name>` or reject any label name colliding with a reserved/dangerous environment variable list including `LD_PRELOAD`, `LD_LIBRARY_PATH`, `PATH`, `BUNDLE_*`, etc.). Alternatively, namespace all label-derived keys (e.g. prefix with `SHIPIT_LABEL_`) so they can never collide with security-sensitive environment variables consumed by spawned processes.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual, no live GitHub required)
test "LD_PRELOAD label name reaches spawned process env" do
  stack = shipit_review_stacks(:review_stack) # or build one with a pull_request
  pull_request = stack.pull_request
  pull_request.update!(labels: ["ld_preload"])

  env = stack.env
  assert_equal "true", env["LD_PRELOAD"]

  command = Shipit::Command.new("env", chdir: Dir.tmpdir, env: env)
  spawned_env = command.unbundled_env
  assert_equal "true", spawned_env["LD_PRELOAD"]
end
```
This demonstrates: `stack.env["LD_PRELOAD"] == "true"` (attacker-controlled) equals `command.unbundled_env["LD_PRELOAD"]` (value reaching `PTY.spawn`), violating the invariant that fork-controllable keys such as `LD_PRELOAD` must not reach the spawned process environment.
