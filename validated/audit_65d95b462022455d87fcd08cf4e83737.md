### Title
Unbounded coin-selection loop over dust outputs sent to an AA can freeze the AA's ability to pay out funds - (File: aa_composer.js)

### Summary
The Sherlock report describes `ProtectionPool` looping over an unbounded, attacker-growable array (`activeProtectionIndexes`) inside `lockCapital()` and `_accruePremiumAndExpireProtections()`, causing critical functions to hit the block gas limit and revert, effectively freezing protection payouts. In ocore, the analogous unbounded, attacker-growable collection is the set of unspent outputs (dust) sitting at an Autonomous Agent (AA) address, which is iterated over without a hard cap whenever the AA composes an outgoing payment.

### Finding Description
When an AA needs to send a payment, `sendUnit()` → `completePaymentPayload()` selects UTXOs via `readStableOutputs()` / `readUnstableOutputsSentByAAs()` and then `iterateUnspentOutputs()` loops over every returned row, adding it as an input until `target_amount` is reached: [1](#0-0) 

Any unprivileged user can post ordinary payment messages sending many tiny outputs to a given AA address (above the dust threshold `FULL_TRANSFER_INPUT_SIZE`, which is enforced only to block *sub*-threshold dust): [2](#0-1) 

Each output added as an input increases the required `target_amount` by `FULL_TRANSFER_INPUT_SIZE` (60 bytes) but only contributes its own (small) amount, so an attacker choosing outputs barely above the threshold can force the AA to consume very many inputs to reach a given target when it eventually needs to disburse a larger amount (e.g., a "send-all" response or a swap payout): [3](#0-2) 

Critically, unlike ordinary units, AA-generated payment messages are explicitly *exempted* from the input-count cap that limits regular users: [4](#0-3) 

and AA-generated units are also exempted from the overall unit-size cap: [5](#0-4) 

Because these safety caps (`MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_UNIT_LENGTH`) that would normally bound the loop and the resulting unit size are deliberately bypassed for `bAA`, an attacker can inflate the number of unspent outputs owned by an AA to the point where coin selection and payload construction become the bottleneck: the loop in `iterateUnspentOutputs()` has to walk through, and encode into a single payment message, thousands of dust inputs before the response unit can be finalized. This mirrors the Sherlock H-9 pattern exactly: a critical function (`lockCapital`/`_accruePremiumAndExpireProtections` there, AA fund-disbursement here) is forced to iterate an array whose size is entirely attacker-controlled and unbounded by any protocol-level limit, because the very safety valve that would otherwise cap it (`MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH`) does not apply to this code path.

### Impact Explanation
If the number of dust outputs owned by the AA grows large enough, the AA's outgoing payment(s) may never successfully complete: `handleAATriggers()` runs synchronously inside the write-lock/mutex during main-chain stabilization, so an AA response that must enumerate and spend an enormous number of small inputs can stall trigger processing for that unit indefinitely, or produce a response unit that becomes practically un-composable/un-broadcastable (oversize fees compound with `bChargeOversizeFee` while base amounts stay tiny). Because the input-count and unit-size caps are bypassed for AAs, there is no protocol-enforced ceiling that forces a graceful bounce; the AA can be pushed into a state where it can no longer flush its own balance to users, i.e. AA fund freezing — the same "protection buyers won't be covered" class of impact as in the original report. This also risks stalling stabilization of subsequent MCIs since `handleAATriggers()` blocks further main-chain-stability processing.

### Likelihood Explanation
Sending many small payments to a public AA address is a normal, permissionless operation available to any unprivileged unit poster — no special privileges, hub/peer position, or leaked keys are required. The only cost to the attacker is the standard per-unit and per-byte fees for posting many small payments, which is cheap relative to permanently degrading a popular AA (e.g., a DEX/exchange AA that regularly needs to sweep or pay out balances). The precondition (AA path exempted from `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_UNIT_LENGTH`) is a deliberate, code-confirmed design choice, not a hypothetical.

### Recommendation
- Enforce a hard cap on the number of inputs an AA-generated payment message may include, even though `MAX_INPUTS_PER_PAYMENT_MESSAGE` is currently bypassed for `bAA`; when the cap is reached, either split the payout across multiple secondary AA responses or defer/consolidate dust in a separate housekeeping step.
- Reintroduce (or raise, but not remove) the `MAX_UNIT_LENGTH` bound for AA-authored units so a single response cannot grow unbounded from attacker-supplied dust.
- Consider periodic/opportunistic dust-consolidation logic for AA balances (merging many small unspent outputs into fewer, larger ones) independent of any specific trigger response, so coin selection for a real payout never has to walk an attacker-inflated UTXO set in one pass.

### Proof of Concept
1. Deploy/identify an AA that at some point performs a "send-all" or large payout in the base asset (a common AA pattern).
2. Repeatedly post ordinary payment units from many different addresses, each sending the AA a base-asset output just above `FULL_TRANSFER_INPUT_SIZE` (60 bytes) so it passes the existing dust filter in `readStableOutputs()`.
3. Trigger the AA to make a payout that must sum its balance; `sendUnit()` → `completePaymentPayload()` → `iterateUnspentOutputs()` will be forced to consume most/all of the attacker-created outputs as inputs because `MAX_INPUTS_PER_PAYMENT_MESSAGE` and `MAX_UNIT_LENGTH` are bypassed for AA units (`validation.js:2137-2138`, `validation.js:267-268`).
4. Observe that trigger processing takes disproportionately long or that the composed response unit becomes so input-heavy that it can no longer be feasibly finalized/broadcast, leaving the AA's balance effectively locked.
