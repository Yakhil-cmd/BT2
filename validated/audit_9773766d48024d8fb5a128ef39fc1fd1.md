### Title
CCMenuController bypasses `ApiClient#stack_id` scoping by using `Stack.from_param!` instead of the scoped `stacks` helper - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` restricts stack lookups to a token's own stack via `stacks.from_param!` when `current_api_client.stack_id?` is true [1](#0-0) , but `Shipit::Api::CCMenuController#stack` overrides this and calls the unscoped `Stack.from_param!(params[:stack_id])` directly [2](#0-1) . Any bearer of a stack-scoped `ApiClient` token (one with `stack_id` set and `read:stack` permission) can present that token to the CCMenu endpoint with a different `stack_id` in the URL and read a stack it was never scoped to.

### Finding Description
Broken binding: `current_api_client.stack_id == params[:stack_id]` (or membership of `params[:stack_id]` in the client's authorized stack set) should be enforced for any stack-scoped `ApiClient`, but `CCMenuController#stack` never checks it.

Path: `authenticate_api_client` resolves `@current_api_client = ApiClient.authenticate(params[:token])` [3](#0-2) , which only verifies the SimpleMessageVerifier signature and looks the row up by id [4](#0-3) . It performs no scope check itself — scoping is supposed to happen in the `stack`/`stacks` accessor. `BaseController#stacks` correctly restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped [5](#0-4) , and `BaseController#stack` uses that scoped relation [6](#0-5) . `CCMenuController` re-defines `stack` to call `Stack.from_param!` on the entire `Stack` table, silently discarding the scoping every other API controller inherits [2](#0-1) .

Exploit flow: a Shipit operator issues a stack-scoped read-only `ApiClient` (stack_id = A, permissions = `read:stack`) for use against stack A's endpoints. If that token is ever presented to `GET /api/stacks/:stack_id/cc.xml` with `stack_id = B`, `require_permission!(:read, :stack)` only checks `permissions.include?('read:stack')` [7](#0-6)  — it does not check `stack_id` — and `CCMenuController#stack` happily resolves stack B via the unscoped `Stack.from_param!`, returning stack B's deploy data.

Note: the query-string-vs-header aspect of the original question is not itself a bug — the engine's own test suite explicitly documents and asserts that CCMenu tokens are intended to be accepted via `?token=` because CCMenu clients cannot send `Authorization` headers [8](#0-7) . Likewise, the specific `ApiClient` created by `CCMenuUrlController#client` is never given a `stack_id` [9](#0-8) , so for that particular token the scoped and unscoped code paths behave identically today. The exploitable divergence only manifests for a stack-scoped `ApiClient` (creatable via `Shipit::ApiClientsController`) whose token is replayed against the CCMenu route.

### Impact Explanation
An attacker who obtains any single stack-scoped `read:stack` API token (e.g., leaked in logs, chat, or a browser cache — the same leakage vector cited in the question) can enumerate `stack_id` values against the CCMenu XML endpoint and read deploy/build status for stacks outside that token's authorized scope. This is a High-severity unauthorized read of stack state across tenants/stacks that should have been isolated by `stack_id` scoping, repeatable for every `stack_id` the attacker guesses or enumerates.

### Likelihood Explanation
Requires: (1) an operator has created at least one stack-scoped `ApiClient` (a supported, documented feature via `belongs_to :stack, optional: true` and `BaseController#stacks`), and (2) that token leaks to an attacker via a channel outside this engine's control (URL logging, sharing, etc.). No GitHub secrets, sessions, or additional privileges are needed once the token is obtained. Attacker cost is a single HTTP GET per stack_id guessed.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and rely on the inherited, scoped `BaseController#stack`/`#stacks` methods (i.e., delete lines app/controllers/shipit/api/ccmenu_controller.rb:29-31), so the CCMenu endpoint enforces the same `current_api_client.stack_id` scoping as every other API controller.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (minitest, no live GitHub):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar2"), branch: "main")`.
2. Create a scoped client: `scoped_client = ApiClient.create!(creator: @user, name: 'scoped', permissions: %w[read:stack], stack: stack_a)`.
3. `request.headers['Authorization'] = nil; get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }`.
4. Assert: expected behavior is `assert_response :not_found` (stack_b is outside `scoped_client.stack_id`); actual current behavior is `assert_response :ok` and `assert_payload 'name', stack_b.to_param`, proving `CCMenuController#stack` returns stack B despite the client being scoped to stack A only.
