### Title
Premature success acknowledgment and permanent "handled" cache for private payment chains bypasses async validation outcome - ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in `wallet.js` caches an entire batch of private payment chains as "handled" (`handledChainsCache[cache_key] = Date.now()`) and replies `ifOk()` to the sender **before** the asynchronous validation of the queued chains has actually completed, and the cache is never invalidated if that later-arriving validation fails. Any subsequent resend of the byte-identical `chains` payload then short-circuits straight to `callbacks.ifOk()` with no validation at all, mirroring the CVE-2025-8454 pattern of trusting a "previously processed" cache regardless of whether that previous verification actually succeeded.

### Finding Description
In `handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0) , a cache key is derived from a hash of the whole `chains` array, and if that key is already present in `handledChainsCache`, the function immediately emits the "all handled" events and calls `callbacks.ifOk()` without any re-validation [2](#0-1) .

The cache is populated at the end of the per-chain `async.eachSeries` loop [3](#0-2) . For light-client chains, `network.handleOnlinePrivatePayment` typically returns via the `ifQueued` callback, which calls `cb()` **immediately** to advance `async.eachSeries`, while the actual validation outcome is delivered later, asynchronously, through a one-shot `eventBus.once(key, function(bValid){...})` listener [4](#0-3) .

Because `cb()` fires before that listener resolves, the `async.eachSeries` final callback executes as soon as all chains are merely *queued*, not once they are *validated*. At that point the code calls `checkIfAllValidated()` (a no-op, since `assocValidatedByKey[key]` is still `false`), immediately sets `handledChainsCache[cache_key] = Date.now()`, and calls `callbacks.ifOk()` [5](#0-4) . If the deferred validation later fails, `eventBus.once` fires with `bValid=false` and only calls `cancelAllKeys()` (removing listeners) [6](#0-5) ; nothing ever deletes the `handledChainsCache` entry that was already set.

Consequently, a bit-identical resend of the same chain payload (same `objectHash.getBase64Hash(arrChains)`, computed at line 974) will hit the cache and be acknowledged as `ifOk()` a second time with zero validation, even though the first attempt's real (deferred) validation outcome may have been a failure. The design intent of `handledChainsCache` (to deduplicate legitimate resends, per the comment "clear cache every hour" at lines 948-953) assumes the cache only records genuinely-validated successes, but the write happens on dispatch, not on confirmed validation.

### Impact Explanation
The affected code path handles private (hidden) payment chains delivered to a paired wallet device via the hub/peer channel, matching the "private-payment counterparty" reachable surface. The premature/incorrect caching means:
- A counterparty (or a hub relaying on their behalf) can get `ifOk()` acknowledgments for private payment chains that never passed validation, misleading the sender's client (or any code that gates further actions on the wallet-level ack) into believing the private payment was accepted.
- Because the same cache key also short-circuits legitimate retries, a case where the original in-process validation genuinely failed (e.g., bad spend proof, non-existent asset, wrong denomination) can be "recovered" simply by resending the identical payload — the resend gets `ifOk()` without any of the checks in `divisible_asset.js`/`indivisible_asset.js`/`private_payment.js` being exercised again.
- This does not by itself write bad rows to `outputs`/`inputs` (the actual persistence still goes through `handleSavedPrivatePayments`/`validateAndSavePrivatePaymentChain`), but it breaks the acknowledgment contract between the hub protocol and validation state, which downstream logic (forwarding to other members, "new_my_transactions" emission on the *original* pass, and any UI/business logic keyed off "payment accepted") relies on for correctness.

### Likelihood Explanation
The `ifQueued` branch is explicitly noted in the code as "the most likely outcome for light clients" [7](#0-6) , meaning the race between `cb()` firing early and the real validation completing later is the common case, not an edge case, for light wallets receiving private payments — a routine, unprivileged interaction path.

### Recommendation
- Do not call `cb()` in the `ifQueued` branch until the corresponding `eventBus.once(key, ...)` resolves with the real validation result; propagate `bValid=false` as an error to `async.eachSeries` instead of only calling `cancelAllKeys()`.
- Only populate `handledChainsCache[cache_key]` after confirming that every chain in the batch was actually validated successfully (`assocValidatedByKey[key] === true` for all keys), not merely dispatched/queued.
- On any validation failure discovered after the cache was set (or before setting it), ensure `handledChainsCache[cache_key]` is deleted/never written, so a resend is forced to go through full validation again.

### Proof of Concept
1. A paired device/hub sends a `private_payments` message with `chains` containing at least one chain whose head payload denomination indicates it is a divisible/light-path chain, so `network.handleOnlinePrivatePayment` returns via `ifQueued` (common path per the code's own comment).
2. `handlePrivatePaymentChains` reaches the `async.eachSeries` final callback (line 1065) once all chains are queued (not yet validated), sets `handledChainsCache[cache_key] = Date.now()` (line 1072), and replies `ifOk()` to the sender (line 1073) — before the real, asynchronous validation (triggered later by `handleSavedPrivatePayments`/`eventBus.emit(key, bValid)`) has run.
3. Suppose the deferred validation subsequently fails (e.g. `eventBus.emit(key, false)` from `network.js` line 2496) — `cancelAllKeys()` runs, but `handledChainsCache[cache_key]` is never cleared.
4. The sender (or an attacker who captured/replays the exact same `chains` JSON, since the cache key is a pure content hash and not bound to a session or nonce) resends the identical `private_payments` body.
5. `handlePrivatePaymentChains` sees `handledChainsCache[cache_key]` truthy at the top of the function (lines 979-983) and immediately calls `callbacks.ifOk()` again, with no invocation of `network.handleOnlinePrivatePayment` or any of the payment/asset validation logic at all.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
	try {
		var cache_key = objectHash.getBase64Hash(arrChains);
	}
	catch (e) {
		return callbacks.ifError("chains hash failed: " + e.toString());		
	}
	if (handledChainsCache[cache_key]) {
		eventBus.emit('all_private_payments_handled', from_address);
		eventBus.emit('all_private_payments_handled-' + arrChains[0][0].unit);
		return callbacks.ifOk();
	}
