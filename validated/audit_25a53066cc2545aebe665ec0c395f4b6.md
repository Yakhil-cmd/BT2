### Title
Unrestricted, retroactive update of an asset's `spender_attested` attestor list can freeze already-issued/held coins - (File: `validation.js`, `storage.js`)

### Summary
For assets created with `spender_attested: true`, the ability to spend (or issue) the asset is gated on whether the spender is currently on the asset's *attestor-approved* list, computed on demand from the **latest** `asset_attestors` update, not from the list that was in force when the coins were received. The asset definer can post a new `asset_attestors` message at any later time, unilaterally and without limit, changing the attestor set that governs every already-issued unit of that asset. This mirrors the reported `creditManager` bug class: a privileged party can change parameters that retroactively apply to existing positions/holdings, breaking previously valid state.

### Finding Description
An asset is defined with `spender_attested: true` and an initial `attestors` list in the `asset` message [1](#0-0) . After issuance, the asset's single-authored definer can send an `asset_attestors` message at any time to replace the attestor list; validation only checks that the sender is the asset's `definer_address` and that the new list is well-formed - there is no restriction on how often or how drastically the list can change: [2](#0-1) 

When a payment in this asset is validated (or when checking whether an address is allowed to spend/issue), `storage.readAsset` always resolves attestors from the **most recent** `asset_attestors` unit relative to `last_ball_mci`, not from the list that existed when the payer received the funds: [3](#0-2) 

`filterAttestedAddresses`/`loadAssetWithListOfAttestedAuthors` then check attestations against this freshly-recomputed `arrAttestorAddresses`, and `validatePayment` rejects the payment if the spender is not attested according to the *current* list: [4](#0-3) [5](#0-4) 

Because there is no cap on how many `asset_attestors` updates the definer may post, and because each payment is judged only against the attestor list active at validation time, the definer can:
1. Remove/replace the attestor(s) that previously attested a set of legitimate holders, permanently freezing their already-received coins (they can never satisfy `objAsset.arrAttestedAddresses` again unless re-attested).
2. Swap in a new attestor who attests a different address, letting a different party pass the `issuer is not attested` check for issuance (`bIssue && arrAttestedAddresses.indexOf(issuer_address) === -1`), effectively transferring issuance rights after the fact.

### Impact Explanation
Holders of a `spender_attested` asset have no guarantee that funds legitimately received today remain spendable tomorrow: the definer alone, with a single ordinary unit, can retroactively revoke the attestor whose attestation made those specific holders' funds spendable. This is a concrete "AA/holder fund loss or freezing" scenario - already-issued, already-held coins become permanently unspendable through no fault or action of the holder, purely due to an unrestricted parameter change by the asset definer. It also allows redirecting who is authorized to issue against the asset's cap, changing economic assumptions users relied on when they acquired the asset.

### Likelihood Explanation
Reaching this path requires nothing but ordinary abilities already granted to any asset definer: composing an `asset` message with `spender_attested: true` and later composing an ordinary `asset_attestors` message. Both are standard, unprivileged operations reachable from a single posted unit (`composer.composeAssetDefinitionJoint` / `composeAssetAttestorsJoint`), with no node-privilege, no P2P/consensus tampering, and no protocol upgrade needed: [6](#0-5) 

### Recommendation
Bind the attestor-list snapshot used to validate a payment/issuance to the attestor list that was in effect at the time the spender received/attested the funds (or otherwise make attestor-list changes non-retroactive for already-issued outputs), rather than always resolving to the attestor list current as of `last_ball_mci`. At minimum, rate-limit or otherwise restrict how attestor-list changes affect already-issued coins, similar to the report's recommendation to "restrict params changing" for the `creditManager`-style upgradeable configuration.

### Proof of Concept
1. Definer `D` issues asset `X` with `spender_attested: true`, initial `attestors: [A]`.
2. Attestor `A` posts an `attestation` for holder `H`. `H` receives a payment output in asset `X` and validates/spends normally because `A` is in the current `asset_attestors` list (see `storage.js:1917-1946`, `validation.js:2115-2122`).
3. Definer `D` later posts `asset_attestors` `{asset: X, attestors: [B]}` (`validation.js:2829-2848` allows this unconditionally as long as `D` is `objAsset.definer_address`).
4. `H` now attempts to spend the previously received, still-unspent output of asset `X`. `storage.readAsset` recomputes `arrAttestorAddresses = [B]` (latest list), `filterAttestedAddresses` finds no attestation from `B` for `H`, so `validatePayment` rejects with `"none of the authors is attested"` - `H`'s legitimately-held funds are now permanently frozen, even though nothing `H` did was invalid at the time of receipt.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
