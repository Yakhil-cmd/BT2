Confirmed root cause. I have enough evidence to finalize the finding.### Title
`Api::CCMenuController` bypasses per-token stack scoping, letting a stack-scoped ApiClient token read any other stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the base controller's `stack` resolver with an unscoped lookup, so a `read:stack` token that an admin restricted to a single `Stack` (via `ApiClient#stack_id`) can be replayed against any other stack's CCMenu endpoint and read its deploy/build state.

### Finding Description
`Shipit::Api::BaseController` is designed so that when an `ApiClient` has a `stack_id` set, all stack-scoped reads are constrained to that one stack: [1](#0-0) 

Every ordinary API controller (e.g. `Api::CommitsController`, `Api::StacksController`) relies on this inherited `stack`/`stacks` method, so the binding `stack.id == current_api_client.stack_id` (when the client is scoped) is enforced before any stack data is rendered. [2](#0-1) 

`Api::CCMenuController`, however, redefines `stack` to resolve directly from the URL parameter, completely bypassing the `stacks` scoping helper: [3](#0-2) 

Its permission check only verifies that the token carries the `read:stack` permission string, not that the requested `stack_id` matches the token's authorized `stack_id`: [4](#0-3) [5](#0-4) 

This is the same class of bug as the report's `StrategyDetailsParam.vault`: a value that is supposed to be bound to the caller's authorized scope (`vault` bound to the calling `Vault`; here, `stack_id` bound to `current_api_client.stack_id`) is instead taken unchecked from attacker-controlled input (`params.dig` in the lien case; `params[:stack_id]` here). The equality that must hold — `stack.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` — is silently dropped by the controller override.

### Impact Explanation
Any holder of a legitimately-issued but narrowly-scoped `read:stack` ApiClient token (fixture example: `here_come_the_walrus`, scoped to stack `shipit` — [6](#0-5) ) can query `GET /api/:other_stack_id/ccmenu.xml?token=<their token>` and receive that other stack's name, last build status, last build label/time and web URL — data belonging to a stack they were never authorized to see. This is an authenticated-but-unauthorized cross-scope read of stack state, matching the "High" impact class of unauthorized read of stack state via escalation beyond the token's granted authorization boundary.

### Likelihood Explanation
Any actor who already possesses one valid, narrowly-scoped `read:stack` API token (a routine, low-privilege credential many integrations receive, e.g. via `CCMenuUrlController`, which itself mints a `read:stack` client — [7](#0-6) ) can trivially trigger this by changing the `:stack_id` path segment on the CCMenu URL. No additional privilege, timing, or race condition is required, only the ability to substitute a different stack identifier in an otherwise valid request.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the inherited, scope-aware `stacks` method instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the `current_api_client.stack_id` restriction from `Api::BaseController#stacks` is enforced identically to every other API controller.

### Proof of Concept
1. As an administrator, create/observe an `ApiClient` scoped to `Stack A` with only the `read:stack` permission (e.g. fixture `here_come_the_walrus`, `stack: shipit`, `permissions: [read:stack]`) — [6](#0-5) .
2. Using that client's `authentication_token`, issue: `GET /api/:stack_b_id/ccmenu.xml?token=<token>` where `stack_b_id` is a stack other than the one the client is scoped to.
3. Observe the request succeeds and returns Stack B's build/deploy XML, because `Api::CCMenuController#stack` resolves via unscoped `Stack.from_param!` — [8](#0-7)  — while `require_permission :read, :stack` only checks the permission string, not the stack identity — [9](#0-8) .
4. Compare with any other API controller (e.g. `Api::CommitsController#index`, using inherited `stack`) issued against Stack B with the same token: it returns 404/empty because `stacks` filters by `current_api_client.stack_id` — confirming the CCMenu controller is the outlier that breaks the token↔stack binding.
