### Title
Non-receiving EVM recipient permanently locks bridged ETH in `BridgeVault` on Sui→EVM claims - (File: `bridge/evm/contracts/SuiBridge.sol`)

### Summary
This is the same root cause as the C4 report: an ether transfer to an arbitrary, unprepared recipient contract reverts and blocks a state transition that depends on it succeeding. In Sui's EVM bridge contracts, `SuiBridge.transferBridgedTokensWithSignatures` unlocks ETH to `tokenTransferPayload.recipientAddress` via `BridgeVault.transferETH`, which performs a raw `.call{value: amount}("")` and reverts if the call fails. Because the message's recipient is fixed by the quorum-signed payload and can never be altered, and the nonce is only marked processed after a successful transfer, a recipient that cannot receive ETH causes the claim to fail forever, permanently locking the bridged funds in the vault.

### Finding Description
`send_token` on the Sui side (`crates/sui-framework/packages/.../bridge/bridge.move`, `send_token`) lets any unprivileged caller lock a `Coin<T>` (including native ETH represented as `BridgeUtils.ETH`) and specify an arbitrary `target_address` (an EVM address encoded as raw bytes) with no validation that the address can receive ETH. [1](#0-0) 

Once the Sui validator committee signs the resulting message, anyone can submit it to `transferBridgedTokensWithSignatures`, which decodes the fixed `recipientAddress` from the payload and calls `_transferTokensFromVault`: [2](#0-1) 

For the native-ETH token ID, `_transferTokensFromVault` calls `vault.transferETH(payable(recipientAddress), amount)`: [3](#0-2) 

`BridgeVault.transferETH` performs a low-level call and reverts on failure, exactly mirroring the vulnerable pattern from the external report where an arbitrary, unprepared recipient contract rejects an ether transfer: [4](#0-3) 

Because `isTransferProcessed[message.nonce] = true` is only set after `_transferTokensFromVault` succeeds, a reverting recipient means the nonce is never marked processed: [5](#0-4) 

The recipient address is baked into the already-signed message (derived from the original Sui-side deposit) and cannot be changed or redirected by any subsequent call — there is no retry-with-different-recipient path, no WETH fallback, and no emergency withdrawal path for this specific stuck transfer in `SuiBridge.sol` or `BridgeVault.sol`. `SuiBridgeV2.sol` reproduces the identical pattern in `transferBridgedTokensWithSignaturesV2`/`_transferTokensFromVault`. [6](#0-5) 

### Impact Explanation
If the EVM `target_address` supplied during a Sui→EVM ETH bridge deposit is a contract without a `receive`/`fallback` function (or one that reverts, e.g. due to gas-limited transfers or intentional rejection), the ETH locked in `BridgeVault` for that transfer can never be claimed: the low-level call always reverts, the transaction always reverts, and the nonce is never marked processed, so no alternative claim path exists. This results in permanent fund lock of the deposited ETH inside `BridgeVault`, which matches the High-severity "permanent fund lock ... reachable from public input" impact.

### Likelihood Explanation
The trigger is fully within the depositor's control and requires no privileged action: any unprivileged Sui-side caller of `send_token` can specify an EVM `target_address` that is a non-payable/reverting contract (mistakenly, via a proxy/multisig without a fallback, or through griefing by a front-end/integrator bug). Once the committee signs the resulting message (a routine, automatic step, not requiring any special trust decision about the recipient's payability), the ETH transfer is guaranteed to fail permanently. No malicious validator, bridge authority, or governance action is required.

### Recommendation
Do not let a reverting recipient block finalization of the bridge message. Options mirroring the original report's mitigations:
- Wrap the ETH transfer in a try/catch (or check `success` without reverting the whole claim) and, on failure, deposit into WETH and send the ERC20 WETH to the recipient instead, matching the pattern already used in `BridgeVault.receive()` for wrapping stray ETH.
- Mark `isTransferProcessed[message.nonce] = true` regardless of whether the final asset transfer succeeds (recording the failure), and provide a separate, permissionless "sweep to WETH" or "retry" function keyed by nonce so a stuck transfer can eventually be completed without re-signing.

### Proof of Concept
1. On Sui, an unprivileged user calls `bridge::send_token` with `target_chain`/`target_address` set to the address of a contract with no `receive`/`fallback` (e.g., a plain non-payable contract), sending `amount` of Sui-wrapped ETH. [1](#0-0) 
2. The validator committee observes the deposit event and produces the standard quorum signatures for a `TOKEN_TRANSFER` message with that fixed `recipientAddress`.
3. Anyone submits `transferBridgedTokensWithSignatures(signatures, message)` on `SuiBridge.sol`.
4. `_transferTokensFromVault` calls `vault.transferETH(recipientAddress, amount)`, which performs `recipientAddress.call{value: amount}("")`; since the recipient contract has no payable fallback, `success == false` and the call reverts with `"ETH transfer failed"`. [4](#0-3) 
5. Because the whole transaction reverts, `isTransferProcessed[message.nonce]` is never set to `true`, and every future resubmission of the identical signed message fails identically — the ETH is permanently stuck in `BridgeVault`.

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

        emit TokensClaimed(
            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,
            tokenTransferPayload.recipientAddress
        );
    }

    function _transferTokensFromVault(
        uint8 sendingChainID,
        uint8 tokenID,
        address recipientAddress,
        uint256 amount
    ) private whenNotPaused limitNotExceeded(sendingChainID, tokenID, amount) {
        address tokenAddress = committee.config().tokenAddressOf(tokenID);

        // Check that the token address is supported
        require(tokenAddress != address(0), "SuiBridge: Unsupported token");

        // transfer eth if token type is eth
        if (tokenID == BridgeUtils.ETH) {
            vault.transferETH(payable(recipientAddress), amount);
        } else {
            // transfer tokens from vault to target address
            vault.transferERC20(tokenAddress, recipientAddress, amount);
        }

        // update amount bridged
        limiter.recordBridgeTransfers(sendingChainID, tokenID, amount);
    }

        external
        override
        onlyOwner
        nonReentrant
    {
        // Unwrap the WETH
        wETH.withdraw(amount);

        // Transfer the unwrapped ETH to the target address
        (bool success,) = recipientAddress.call{value: amount}("");

    }
