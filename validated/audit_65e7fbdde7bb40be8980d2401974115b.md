### Title
Cross-tenant Commit status mutation via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up every `Commit` row matching the incoming `sha` with no scoping to the repository/organization whose webhook signature was actually verified, then calls `create_status_from_github!` on all of them. Because Shipit's other webhook handlers scope through `Handler#stacks` (which resolves `Repository.from_github_repo_name(payload['repository']['full_name'])`), but `StatusHandler` does not use that helper at all, a `sha` collision between two unrelated stacks lets a webhook verified only for org A mutate CI status on org B's commit.

### Finding Description
The broken binding, stated as an equality that must hold for every row touched but does not:

`organization_verified_by(WebhooksController#verify_signature) == organization_owning(Commit row mutated by StatusHandler#process)`

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (i.e., org A, the org that actually signed and sent the webhook) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This only proves the HTTP body was signed by org A's `webhook_secret`. [1](#0-0) [2](#0-1) 
2. On success, `create` dispatches the raw parsed JSON to every matching handler: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
3. `Handler` provides a `stacks` helper explicitly meant to scope work to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks`. [4](#0-3) 
4. `StatusHandler#process` ignores that scoping entirely and instead runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query across the whole `commits` table regardless of `stack_id`/organization. [5](#0-4) 
5. `Commit#create_status_from_github!` mutates state (creates a `Status` row and can emit `deployable_status`/`commit_status` hooks and trigger `stack.schedule_merges`) for whatever `stack` the matched commit belongs to. [6](#0-5) [7](#0-6) 

Exploit flow: an attacker forks a public repo containing commit `sha=X` owned by org B's stack (Shipit creates a `Commit` row for `X` under org B's stack when that repo/stack is tracked, e.g. via push/PR events). The attacker pushes the same commit (identical sha) into their own repo under org A, which they control and whose `webhook_secret` they can trigger through normal GitHub webhook delivery for their own repo. When GitHub (or the attacker, replaying a legitimately delivered payload) sends a `status` event for `sha=X` with `repository.owner.login = orgA`, `verify_signature` succeeds using org A's secret. `StatusHandler#process` then updates the status of **every** `Commit` row with `sha=X`, including org B's row, even though the payload's own `repository` field never pointed at org B and the signature never proved anything about org B.

Existing guards do not catch this: `verify_signature` only authenticates the sender is org A; `drop_unhandled_event` only filters unknown event types; `ExplicitParameters` schema only validates payload shape, not organization ownership; `Handler#stacks` exists specifically to prevent this class of bug but `StatusHandler` never calls it.

### Impact Explanation
A webhook signed only by org A's `webhook_secret` rewrites CI/status state (`Status` records, potentially triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`) for a `Commit` belonging to org B's `Stack`, without org B's `webhook_secret` ever being checked. This is a payload for one repository mutating another tenant's commit/stack state — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" category. It is repeatable against any pair of stacks that happen to share a commit sha (most realistically achievable by the attacker forking/duplicating a specific public commit into their own controlled repo, then repeatedly sending `status` webhooks for that sha), and can be used to force-green a commit in a victim stack, unblocking/triggering continuous-delivery merges (`schedule_continuous_delivery`/`schedule_merges`) that require passing CI.

### Likelihood Explanation
Preconditions: both stacks (org A's and org B's) must already exist in Shipit's DB, and a `Commit` row with the identical `sha` must exist in both — realistic since Shipit records `Commit` rows from tracked pushes/PRs per stack, and git commit shas are content-addressed, so any fork/copy of a public commit reproduces the same sha. The attacker needs no Shipit credentials, no session, no API token, and no knowledge of org B's `webhook_secret` — only control of a GitHub repo (fork) registered as a Shipit stack under their own org A, which is within the stated attacker capability ("push to a fork ... emit webhooks from a repository they own"). Cost is low and the attack is fully repeatable for every subsequent `status` event they can trigger on their own repo/commit.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to stacks resolvable from the verified payload's own repository, mirroring the `Handler#stacks` pattern used elsewhere, e.g.: `stacks.flat_map(&:commits).where(sha: params.sha)` or explicitly `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a `status` webhook can only mutate commits under the repository/organization that was cryptographically verified.

### Proof of Concept
Minitest plan (schematic, no live GitHub):
```ruby
test "StatusHandler does not mutate a commit belonging to a different stack's organization" do
  stack_a = shipit_stacks(:cyclimse) # or a fixture stack under org A
  stack_b = shipit_stacks(:shipit)   # fixture stack under org B
  shared_sha = "a" * 40

  commit_a = Shipit::Commit.create!(stack: stack_a, sha: shared_sha, message: "m", author: shipit_users(:walrus))
  commit_b = Shipit::Commit.create!(stack: stack_b, sha: shared_sha, message: "m", author: shipit_users(:walrus))

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }

  # Simulate only org A's webhook_secret verifying (i.e. controller-level verify_signature passed for org A)
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal "success", commit_a.reload.status.state
  # Binding under test: org_verified(A) must equal org_owning(mutated commit).
  # commit_b belongs to org B, which never verified this webhook.
  assert_not_equal "success", commit_b.reload.status.state,
    "Commit belonging to a different, unverified organization/stack was mutated by a webhook verified only for org A"
end
```
This test currently fails against `Commit.where(sha: params.sha)` in `app/models/shipit/webhooks/handlers/status_handler.rb`, because `commit_b.status.state` also becomes `"success"` even though only stack A's organization was authenticated.
