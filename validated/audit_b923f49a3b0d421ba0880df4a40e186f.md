### Title
`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the private `stack` method inherited from `Api::BaseController` to call `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scope that restricts lookup to `current_api_client.stack_id`. Any ApiClient token scoped to one stack (with `read:stack` permission) can therefore fetch ccmenu XML for any other stack in the system by supplying that stack's path in `stack_id`.

### Finding Description
The invariant that should hold is: `stack == stacks.from_param!(params[:stack_id])` where `stacks` is defined as `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [3](#0-2) . That's exactly how `Api::StacksController` and other nested API resources (tasks, deploys, hooks, etc.) resolve `stack`, guaranteeing a stack-scoped token can never resolve a stack outside its `stack_id`.

`Api::CCMenuController`, however, redefines `stack` as:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

This calls the unscoped class method `Stack.from_param!`, which just looks up any stack in the database matching the owner/name/environment path segment, without consulting `current_api_client.stack_id` at all [2](#0-1) .

The only authorization check applied is `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(:read, :stack)` [5](#0-4) , [6](#0-5) . This only checks that `"read:stack"` is in the client's `permissions` array; it never checks whether the requested `stack_id` matches the client's own `stack_id`. So a client explicitly scoped to one stack (e.g. the `here_come_the_walrus` fixture, scoped to `shipit`, holding only `read:stack`) can request `GET /api/stacks/*stack_id/ccmenu` with any other stack's path and successfully render that stack's ccmenu XML, disclosing merge status, lock state, last build time/label, and stack web URL for a stack outside the token's authorized scope.

The `authenticate_api_client` override in this controller (supporting `?token=` query string auth for the CCMenu client, in addition to Basic auth) is not itself the bug — it's the `stack` override that drops the scoping present in the base controller and every other stack-nested API endpoint.

### Impact Explanation
An attacker holding any valid `ApiClient` token scoped to a single stack (a realistic, low-privilege credential type explicitly supported by Shipit, e.g. the auto-generated "CCMenu Client" from `CCMenuUrlController`) can enumerate and read the CI/CD status (`lastBuildStatus`, `activity`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock status) of any stack in the Shipit instance, not just their own. This is an unauthenticated-scope-wise disclosure of stack state across tenants/repositories, matching the "unauthenticated read of stack state ... across tenants" High-severity category. It does not expose task output/logs (ccmenu only exposes summary fields), so the blast radius is limited to stack/build metadata disclosure, not full task streams or deploy output.

### Likelihood Explanation
The attacker needs any valid stack-scoped ApiClient token with `read:stack` permission — a low bar, since such tokens are routinely created and shared (e.g., automatically minted by `CCMenuUrlController#fetch` for the "CCMenu URL" feature and embedded in a URL query string meant for CCTray/CI dashboard tools). No GitHub secrets, admin role, or session are required; the only cost is one crafted GET request with a different `stack_id` path segment. It is fully repeatable against arbitrary stacks.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController`, i.e. remove the override (or change it to `stacks.from_param!(params[:stack_id])`) so it is subject to the `current_api_client.stack_id` restriction, consistent with `Api::StacksController` and other nested resources.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb`, add:
```ruby
test "a token scoped to one stack cannot fetch ccmenu for another stack" do
  authenticate!(:here_come_the_walrus) # scoped to shipit_stacks(:shipit)
  other_stack = shipit_stacks(:cyclimse) # or any stack != :shipit
  get :show, params: { stack_id: other_stack.to_param }
  assert_response :not_found # or :forbidden — must NOT be :ok
end
```
Before the fix: request succeeds with `200 OK` and renders `other_stack`'s XML (violating `stack == stacks.from_param!(params[:stack_id])`). After moving `stack` to use `stacks.from_param!`, the request raises `ActiveRecord::RecordNotFound` (404), matching the behavior of `Api::StacksController#show` for out-of-scope stacks.
