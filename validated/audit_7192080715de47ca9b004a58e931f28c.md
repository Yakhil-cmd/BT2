### Title
Webhook signature verified against `repository.owner.login`, but review-stack provisioning trusts unrelated `repository.full_name` field, letting an org sign an arbitrary victim-repo payload - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` derives the signing organization from `params.dig('repository','owner','login')` (or `organization.login`) and HMAC-verifies the raw body against that organization's `webhook_secret`. `PullRequest::OpenedHandler#repository` independently trusts `params.repository.full_name` to resolve the `Shipit::Repository` that `ReviewStackAdapter#find_or_create!` provisions a stack under. Nothing in the request pipeline checks that `full_name`'s owner segment matches `repository.owner.login`, so a caller who legitimately knows one organization's `webhook_secret` can sign a payload whose `repository.full_name` names a different, victim organization's tracked repository.

### Finding Description
The claimed binding is: `organization whose webhook_secret verified the raw bytes` == `organization owning the Repository/ReviewStack created by the handler`.

Trace:
- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it solely to select which `GitHubApp`/`webhook_secret` to verify the HMAC against: `github_app = Shipit.github(organization: repository_owner); verified = github_app.verify_webhook_signature(...)` [2](#0-1) .
- `OpenedHandler#repository` resolves the target `Repository` from an entirely different field of the same JSON body: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , which splits `"owner/name"` and does a DB lookup [4](#0-3) .
- `process` then gates on `repository.review_stacks_enabled` and `repository.provisioning_behavior_allow_all?` (or label-based variants) and, if satisfied, calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, which creates a `ReviewStack` scoped to that resolved (attacker-named) repository using `branch: params.pull_request.head.ref` [5](#0-4) [6](#0-5) .

Root cause: `repository.owner.login` (used for HMAC org selection) and `repository.full_name` (used for DB lookup/authorization decision) are two independent, attacker-influenced fields of the same JSON body, and no code path cross-checks them. `Shipit.github(organization:)` only maps organizations to distinct `GitHubApp`/`webhook_secret` configs [7](#0-6)  — it says nothing about which repository the payload is allowed to reference.

Attacker's exact request: an attacker who controls (or is) a GitHub organization/app installation registered with this Shipit instance — and therefore legitimately possesses that org's own `webhook_secret` — sends `POST /webhooks` with `X-Github-Event: pull_request`, body `{"action":"opened","number":N,"pull_request":{...,"head":{"sha":"<attacker sha>","ref":"<attacker ref>"},...},"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"sender":{...}}`, and `X-Hub-Signature` computed as `HMAC-SHA1(attacker_org_webhook_secret, raw_body)`. `verify_signature` picks `attacker-org`'s secret (matching `repository.owner.login`), verifies successfully, and passes control to `OpenedHandler`, which then resolves `victim-org/victim-repo` via `full_name` and — if that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all?` — creates a `ReviewStack` under the victim's repository, later queued for provisioning/deployment of the attacker-supplied `head.sha`/`ref`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type exists a handler for; `ExplicitParameters` (`params do ... end`) only validates field types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `Repository` model validations only constrain `owner`/`name` character format, not that they match the signing org.

### Impact Explanation
A stack (`ReviewStack`) is created and queued for provisioning under a **victim** repository, using attacker-controlled `head.sha`/`ref`, triggered entirely by a signature produced with the **attacker's own** organization secret. This is a payload for one repository/organization mutating another's stack — matching the Critical category ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). Blast radius is any repository tracked by this Shipit instance that has `review_stacks_enabled` and `provisioning_behavior_allow_all?` (or reachable via label-based provisioning if the attacker can also forge `pull_request.labels`), regardless of which organization owns it, as long as the attacker controls any one organization's `webhook_secret` in a multi-tenant Shipit deployment. Repeatable per PR/number for as many victim repos as exist with permissive provisioning behavior.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub organizations (`github_default_organization` non-nil, i.e. the multi-org secrets schema) so distinct `webhook_secret`s exist per org, and the attacker legitimately owns/administers one such org's GitHub App installation on this Shipit instance; (2) a victim repository already tracked in Shipit with `review_stacks_enabled` and `provisioning_behavior_allow_all?` (or matching label-based behavior) — both realistic, documented configurations. Given those, the attacker's cost is minimal: compute one HMAC-SHA1 with a secret they legitimately hold and POST to `/webhooks`; no GitHub interaction is strictly required since Shipit's `verify_signature` only checks bytes against the raw body, not that GitHub itself generated it for that specific repo.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler resolving a `Repository`), cross-validate that the `owner.login` used to select the signing organization matches the owner segment parsed from `repository.full_name` (and reject mismatches with `head(422)`). Alternatively, in `Repository.from_github_repo_name`/`OpenedHandler#repository`, require the resolved repository's `owner` to equal the verified `repository_owner` from `verify_signature`, rejecting/no-oping otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure two orgs in `Shipit.stubs(:github_app_config)` (or via secrets fixture) — `attacker-org` and `victim-org` — each with a distinct `webhook_secret`.
2. Create `victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")`.
3. Build payload: `body = payload_parsed(:pull_request_opened).merge("repository" => {"owner" => {"login" => "attacker-org"}, "full_name" => "victim-org/victim-repo"})`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", attacker_secret, body.to_json)`.
5. `request.headers['X-Github-Event'] = 'pull_request'; request.headers['X-Hub-Signature'] = signature`.
6. `assert_difference -> { Shipit::ReviewStack.where(repository: victim_repo).count }, 1 do post :create, body: body.to_json, as: :json end` — asserting a `ReviewStack` row is created under `victim_repo` despite the signature having been verified only against `attacker-org`'s secret, i.e. `repository_owner` (signing org, "attacker-org") != owning org of the created `ReviewStack`/`Repository` ("victim-org").
