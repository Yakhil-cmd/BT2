### Title
Cross-organization commit status forgery bypasses per-org webhook trust boundary and triggers unauthorized deploys — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
In multi-tenant Shipit deployments (`Shipit.github_organizations` > 1), each GitHub organization has its own GitHub App and its own `webhook_secret` used to authenticate inbound webhooks for repositories belonging to that specific org. `StatusHandler`, however, resolves the target `Commit` purely by SHA, with no scoping to the repository/organization whose secret validated the request — breaking the binding "organization whose webhook secret signed the request" == "repository/stack the status is applied to".

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository_owner`, derived from the attacker-controlled JSON body (`repository.owner.login` or `organization.login`): [1](#0-0) [2](#0-1) 

This only proves the request was signed by *some* org onboarded to this Shipit instance — it proves nothing about which repository/commit the payload's other fields refer to. Once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the full payload to `StatusHandler`: [3](#0-2) 

`StatusHandler#process` looks up commits **globally by SHA only** — `Commit.where(sha: params.sha)` — with no `repository`/`stack` scoping at all, unlike other handlers (e.g. `Handler#stacks`, which at least scopes by `payload.dig('repository','full_name')`): [4](#0-3) 

This means an entity legitimately onboarded to the Shipit instance for **their own** organization/app (and thus in possession of *their own* org's `webhook_secret`, which is documented as configurable per-org for exactly this multi-tenant scenario) can sign a `status` event payload with their own secret while setting `sha` to a commit SHA belonging to a **completely different organization's stack**. `create_status_from_github!` will then attach an arbitrary status (state, context, description, target_url) to that victim commit: [5](#0-4) 

### Impact Explanation
A forged "success" status on a victim commit feeds directly into deploy eligibility and continuous delivery logic: [6](#0-5) [7](#0-6) 

If the victim stack has `continuous_deployment` enabled, forging a passing status can trigger an unauthorized deploy of code the attacker doesn't control; it can also bypass `ci.require` checks that gate manual deploys and the merge queue (`stack.schedule_merges` is invoked when status becomes success/pending), potentially causing an unauthorized merge as well. This is a cross-tenant authorization boundary violation — the org-scoped webhook trust is not enforced against the resource being mutated, satisfying the Critical criteria of "unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires the attacker to be a legitimate holder of a webhook secret for at least one org configured on the shared Shipit instance (a realistic scenario for any self-hosted, multi-org Shipit deployment where multiple teams/orgs share one instance, as explicitly documented in `docs/setup.md`'s "Using Multiple Github Applications" section). No access to the victim org's credentials, GitHub App, or repository is needed — only knowledge/guess of a target commit SHA, which is often publicly visible (public repos, PR pages, CI logs). This is a plausible and realistic insider/multi-tenant threat, not a purely theoretical one.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository identified in the payload (`payload.dig('repository','full_name')`) and verify that repository's resolved organization matches the `repository_owner`/org whose secret validated the webhook signature, mirroring the scoping already used by `Handler#stacks`. Reject cross-organization events even when a valid signature for *some* org is present.

### Proof of Concept
1. Deploy Shipit configured with multiple GitHub orgs, e.g. `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications").
2. As an administrator/holder of `AttackerOrg`'s GitHub App webhook secret, obtain the SHA of an existing commit tracked under a `VictimOrg` stack (e.g. from a public PR or CI page).
3. Craft a `status` webhook payload:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
4. Sign it with `AttackerOrg`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
5. `verify_signature` passes (uses `AttackerOrg`'s secret, matching `repository.owner.login`).
6. `StatusHandler` finds the commit by SHA alone (belonging to `VictimOrg`), creates the forged status, and — if the `VictimOrg` stack has `ci.require` on that context or `continuous_deployment: true` — this can unblock or trigger a deploy for `VictimOrg`'s stack.

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
