### Title
CCMenu status token authorizes read access to all stacks, not the stack it was minted for - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` bearer token intended to grant CCMenu/CCTray tools read-only status access to a single, specific stack. The token minted, however, is never bound to that stack, so once it leaves the trust boundary of the Shipit web session (as it is designed to do — it's embedded in a URL meant for third‑party, unauthenticated CI dashboard tooling) it functions as a full `read:stack` API credential for every stack in the Shipit instance.

### Finding Description
`CCMenuUrlController#fetch` builds a public status URL for one stack and appends an `ApiClient` token to it: [1](#0-0) 

The `client` method that mints this token does **not** pass `stack:` to the `ApiClient`, and instead looks the record up purely by `creator` + a fixed `name`: [2](#0-1) 

Because `ApiClient#stack` is `optional: true` and is never set here, the resulting `stack_id` is `nil`: [3](#0-2) 

`ApiClient#authentication_token` is simply the signed client id — no stack, no scope, and no expiry is embedded in the signed message, so the verified signature covers strictly less than what the token is later used to authorize: [4](#0-3) 

Every downstream consumer of this token (`Shipit::Api::BaseController`, which backs the entire read/write API, and `Shipit::Api::CCMenuController`) resolves the accessible stack set from `stack_id` on the `ApiClient` record, not from anything encoded in the token or from the stack the URL was generated for: [5](#0-4) [6](#0-5) 

Since `stack_id` is `nil`, `stacks` resolves to `Stack.all`. This is exactly the bug class in the report: the "leaf" (here, the token/authorization record) is created without binding the entity it is meant to authorize action *for* (the stack), so a value minted for stack A is silently valid for every other stack B, C, … This crosses the "stack a token authorizes versus a stack it touches" boundary explicitly called out in the rules.

The token is also reused across requests: because lookup is `find_or_create_by!(creator:, name: 'CCMenu Client')` with no stack discriminator, requesting the ccmenu URL for stack A and later for stack B returns literally the *same* `ApiClient` record/token, so a single leaked ccmenu URL for one stack grants standing bearer access to all stacks, present and future, in the instance.

### Impact Explanation
The token generated here is a generic `ApiClient` bearer credential usable via HTTP Basic Auth against the entire authenticated API surface (`Shipit::Api::BaseController#authenticate_api_client`), not just the CCMenu XML endpoint: [7](#0-6) 

With `read:stack` permission and no stack scoping, holding this token grants read access to every stack's state, task/deploy history, and (through other `read:stack`-gated API endpoints) deploy/task output for the whole Shipit deployment — matching the High severity criteria "unauthenticated read of stack state, task streams or deploy output." CCMenu/CCTray URLs are specifically designed to be handed to third-party status-monitoring tools and often end up embedded in dashboards, browser history, proxy logs, or public CI aggregators without further authentication — i.e., the credential is expected to leave the trusted Shipit session boundary, making exposure of the over-broad token realistic rather than purely theoretical.

### Likelihood Explanation
Any authenticated Shipit user who can reach `CCMenuUrlController#fetch` for a stack can trigger this — no special privilege beyond ordinary login is required, and the resulting token is meant to be exported outside of the session (that is its entire purpose). The bug is triggered by ordinary, intended use of the feature (fetching a CCMenu URL), not by crafting adversarial input, which makes exploitation likelihood high once such a URL is shared or leaks.

### Recommendation
Bind the minted `ApiClient` to the specific `stack` it is generated for, and look it up by that stack (not just by creator+name), e.g. `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`. Additionally, consider encoding the stack id inside the signed token payload itself (analogous to including `hookAddress` in the leaf hash) so that `Shipit::Api::CCMenuController`/`BaseController` verify the token's scope against the specific stack being accessed rather than trusting an out-of-band `stack_id` column that can be left unset.

### Proof of Concept
1. As any logged-in Shipit user, call the CCMenu URL endpoint for Stack A (e.g. via the UI button on `app/views/shipit/stacks/settings.html.erb`), obtaining a token `T`.
2. Repeat for Stack B as the same user — note the same underlying `ApiClient`/token `T` is returned (`find_or_create_by!` matches only on creator+name).
3. Use `T` via HTTP Basic Auth against any `read:stack` API endpoint (e.g. `GET /api/stacks`, or any other stack's `/api/stacks/:owner/:repo/:branch`) — access succeeds for stacks the token was never intended to cover, because `ApiClient#stack_id` is `nil` and `stacks` in `BaseController` falls back to `Stack.all`. [5](#0-4)

    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end
