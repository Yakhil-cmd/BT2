### Title
Delimiter injection in arbiter contract hash allows contract-content forgery via field-boundary collision - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` computes a contract-identifying hash by joining several attacker-controlled string fields (`title`, `text`, party names) with a fixed, non-escaped delimiter `"[|#|]"`. Because none of these fields is checked for containing the delimiter sequence itself, two semantically different contracts can be crafted whose concatenated "hash source" strings are byte-identical, producing the same SHA-256 hash. This mirrors the livestatus bug class: a text protocol/identifier is built by naive delimiter-joining of untrusted fields without neutralizing the delimiter, letting an attacker shift field boundaries while preserving the resulting identifier.

### Finding Description
`exports.DELIMITER = "[|#|]"` is used in `getHashSrc()` to join contract fields for hashing: [1](#0-0) 

None of `title`, `text`, `my_party_name`/`peer_party_name` are validated to be free of the delimiter substring before being joined (contrast this with `data_feeds`/`aa_validation.js`, which explicitly reject `\n` in feed names/values before using `\n` as a key separator: [2](#0-1)  and [3](#0-2) ). No equivalent check exists for the arbiter-contract `DELIMITER`.

Because of this, an attacker (the contract offeror, who is an unprivileged peer reachable via `createAndSend`) can choose `title = "X" + DELIMITER + "Y"`, `text = "Z"` and, separately, `title = "X"`, `text = "Y" + DELIMITER + "Z"` (with the other fields identical) — both produce the exact same joined string and thus the exact same `hash = getHash(contract)`: [4](#0-3) 

This `hash` is the sole identifier used to:
- tag the contract in the wallet DB (`wallet_arbiter_contracts.hash`) via `createAndSend`/`store`: [5](#0-4) [6](#0-5) 
- build the arbitration/shared-address condition `"CONTRACT_" + contract.hash` written into a data feed that the shared-address definition checks (`in data feed`) to resolve which party receives the funds: [7](#0-6) 
- be forwarded to the arbstore as the disputed contract's identity/content proof during `openDispute`/`appeal`, alongside the actual `title`/`text` sent separately in the encrypted package: [8](#0-7) [9](#0-8) 

Since the hash does not uniquely bind to a single (title, text, party-name) tuple, a malicious offeror can present one narrative to the counterparty at contract-offer time and a different, boundary-shifted narrative to the arbiter at dispute time, while both share the identical `hash` — undermining the very integrity guarantee the hash is meant to provide (that the arbiter judges the same terms the counterparty agreed to).

### Impact Explanation
The arbiter contract mechanism relies on `hash` as a tamper-evident binding of the negotiated contract terms (`title`/`text`/parties/amount/asset). Breaking that binding lets a dishonest party show the counterparty one set of terms and the arbiter a different set of terms with matching hash, i.e., forgery of the "contract text" that the dispute-resolution outcome (and therefore fund release from the shared multisig address) is based on. This can bias arbitration outcomes and result in loss of funds for the honest counterparty in a private-payment/multisig arrangement — fitting the "AA/contract fund loss" impact class, albeit mediated through social/arbitration process rather than pure protocol-level fund theft.

### Likelihood Explanation
Medium: exploitation requires the attacker to be one of the two negotiating parties (offeror) in an arbiter contract, which is a normal, unprivileged capability of any wallet user using this feature (`createAndSend` is reachable by any wallet user). Crafting two strings that hash-collide via delimiter-boundary shifting requires no cryptographic hash break — it is a pure string-construction trick, trivial to script. The only constraint is that the fabricated fields must appear plausible to both the counterparty and the arbiter, which is a social-engineering step, reducing but not eliminating practical exploitability.

### Recommendation
Reject any `title`, `text`, `my_party_name`, or `peer_party_name` value containing the literal `DELIMITER` sequence before calling `getHashSrc`/`getHash` (mirroring the `\n` rejection pattern already used for data-feed names/values), or switch to a length-prefixed / unambiguous serialization (e.g. reuse `string_utils.getSourceString`, which already guards against separator-byte injection) instead of naive delimiter-joining.

### Proof of Concept
```js
var arbiter_contract = require('./arbiter_contract.js');

var base = {
  me_is_payer: true,
  creation_date: '2027-01-01 00:00:00',
  my_address: 'PAYER_ADDR', peer_address: 'PAYEE_ADDR',
  arbiter_address: 'ARBITER_ADDR',
  amount: 1000, asset: null
};

var contractA = Object.assign({}, base, {
  title: 'Sell goods' + arbiter_contract.DELIMITER + 'no warranty',
  text: 'as-is',
});

var contractB = Object.assign({}, base, {
  title: 'Sell goods',
  text: 'no warranty' + arbiter_contract.DELIMITER + 'as-is',
});

console.log(arbiter_contract.getHashSrc(contractA) === arbiter_contract.getHashSrc(contractB)); // true -> same hash despite different (title, text) split
```
Both contracts hash identically even though the human-readable meaning of `title`/`text` differs, letting the offeror show contract A to the counterparty and contract B (or any other boundary split) to the arbiter during a dispute while both reference the same `CONTRACT_<hash>` identifier. function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
