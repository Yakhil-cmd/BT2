### Title
Missing session rotation on GitHub OAuth callback allows session fixation - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`Shipit::GithubAuthenticationController#callback` writes `session[:user_id]` and `session[:authenticated] = true` directly into the pre-existing session without ever calling `reset_session`. Because the session identifier is never rotated at the authentication boundary, an attacker who fixates a pre-auth session ID in a victim's browser inherits full authenticated access once the victim completes real GitHub OAuth on that same session.

### Finding Description
The broken binding is: `session.id(before #callback runs) == session.id(after #callback assigns user_id)`, when a security boundary crossing (anonymous → authenticated) should force `session.id(before) != session.id(after)` via `reset_session`.

Tracing the code: [1](#0-0)  shows `callback` reading `request.env['omniauth.auth']` and, if present, immediately doing `session[:user_id] = sign_in_github(auth)` followed by `session[:authenticated] = true` and a redirect — with no `reset_session` call anywhere in the method. Compare this to `logout`, which explicitly calls `reset_session` [2](#0-1) , confirming the omission in `callback` is not an oversight elsewhere compensated for. `Shipit::Authentication#force_github_authentication` and `#current_user`/`#find_current_user` [3](#0-2)  trust `session[:user_id]` as the sole authentication signal for every subsequent request, so whoever controls the session data at the time `user_id` is written controls the authenticated identity going forward.

Exploit flow: the attacker visits Shipit anonymously to obtain an unauthenticated session cookie value S (test/dummy uses `:cookie_store` per `test/dummy/config/initializers/session_store.rb`, and production Redis/cookie session stores behave equivalently regarding this application-level gap). The attacker gets S fixed into the victim's browser and lures the victim to the OAuth flow. The victim completes the real GitHub login; OmniAuth's callback then runs `session[:user_id] = sign_in_github(auth)` on the *same* session object S instead of a freshly rotated one. The attacker, already holding S, is now authenticated as the victim for every subsequent request against `UserRequiredMiddleware`, `force_github_authentication`, and all stack/deploy endpoints that key off `current_user`.

No existing guard mitigates this: `force_github_authentication` only checks `current_user.logged_in?`/`current_user.requires_fresh_login?`/`current_user.authorized?`, none of which detect or prevent reuse of a pre-authentication session identifier; there is no CSRF/state check on the session identity itself, and `reset_session` is invoked only on logout and on stale-login redirect, never on successful sign-in.

### Impact Explanation
This is a session fixation vulnerability, explicitly categorized as High in the rubric ("session fixation / forced OAuth completion"). Once the victim authenticates on the attacker-known session S, the attacker can issue any request the victim's `User` is authorized for — reading stack state, task/deploy output, triggering deploys/rollbacks/tasks the victim can perform, and creating `ApiClient`s under the victim's identity — as long as the attacker retains/replays session S.     def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
