### Title
Deploy/task variable interpolation silently falls back to the deploy host's real process `ENV`, bypassing the `shipit.yml` variable whitelist - (File: lib/shipit/environment_variables.rb)

### Summary
Shipit's deploy/task variable system is meant to bind script execution to a **whitelist** of variable names declared in `shipit.yml` (`deploy.variables` / `tasks.variables`). `EnvironmentVariables#permit` enforces this whitelist when building the environment hash that gets persisted on a `Deploy`/`Task`, but `EnvironmentVariables#interpolate` — used later to substitute `$VAR` placeholders directly into the shell command that is spawned — is **not** bound to that same whitelist. It transparently falls back to the real OS-level `ENV` of the Shipit worker process for any variable name not found in the permitted hash.

### Finding Description
The binding that should hold is:
`{keys permitted into the deploy/task env by shipit.yml variable declarations}` == `{keys actually substituted into the spawned shell command}`

`permit` builds the "safe" environment from user input, rejecting anything not declared: [1](#0-0) 

But `interpolate`, which substitutes `$VAR` references inside command arguments before they are handed to `PTY.spawn`, does not consult that same whitelist — for any variable not present in the (already-filtered) `@env` hash, it silently reads from the real process environment (`ENV[variable]`) of the machine running the deploy: [2](#0-1) 

This interpolation is invoked right before every command is executed: [3](#0-2) [4](#0-3) 

The permitted variable set is produced from `TaskDefinition#filter_envs`, which is the enforcement point that is supposed to be the single source of truth for what a deploy/task's environment may contain: [5](#0-4) 

Because `permit()` (compile-time-safe allow-list) and `interpolate()` (runtime substitution) read from two different data sources — the sanitized hash vs. the raw process `ENV` — a `$VARNAME` reference inside a `shipit.yml` step that is not covered by a declared/whitelisted variable resolves to whatever the deploy host process actually has in its environment (which typically includes credentials such as `GITHUB_TOKEN`, database URLs, cloud credentials, or other secrets injected into the Shipit worker container/VM), rather than failing closed or being empty. This mirrors the report's bug class exactly: the enforcement layer ("verified"/"permitted" set) does not cover the value that is ultimately acted upon ("spawned"/interpolated set).

### Impact Explanation
An interpolated placeholder that falls through to the real process `ENV` can expose sensitive host-level secrets (e.g. `GITHUB_TOKEN`, database credentials, cloud keys configured on the Shipit worker) into deploy output/logs, which are visible to any authenticated Shipit user able to view task/deploy streams — and the leaked value can be exfiltrated by the deploy script itself. This can qualify as exfiltration of `GITHUB_TOKEN` or other credentials configured on the deploy host, which is one of the explicitly listed Critical impacts.

### Likelihood Explanation
Exploitability depends on a `shipit.yml`/task step referencing a `$VARNAME` that is not covered by a declared variable in that file — this is content that lives in the repository's `shipit.yml`, so it is not purely "unprivileged." I was not able to fully trace, within the available context, whether `Stack#filter_deploy_envs` (referenced from `app/models/shipit/stack.rb`) re-applies the same whitelist before commands are built, or whether the raw/unfiltered `@env` used for interpolation can also be influenced by variables the calling user supplies at deploy-trigger time (e.g., via the `env:` parameter on `trigger_deploy`/`trigger_task`) without needing to modify `shipit.yml` itself. That distinction determines whether this is exploitable purely by a user with "trigger deploy" rights or requires repository write access to `shipit.yml` (which would be out of scope per the rules).

### Recommendation
Make `interpolate` fail closed instead of silently falling back to the process environment: only substitute variables that are present in the sanitized/permitted environment hash, and raise (or leave the literal placeholder untouched) for anything else. Do not allow `ENV` of the Shipit process to leak into interpolated user-facing deploy commands.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
