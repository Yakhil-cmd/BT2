### Title
Unprivileged PR labels inject arbitrary environment variables into deploy `Command#unbundled_env` for any key not proactively declared in `shipit.yml`'s `machine.environment` - ([File: app/models/shipit/review_stack.rb])

### Summary
`Shipit::ReviewStack#env` merges every PR label name (upcased) into the stack environment hash with value `"true"`, with no whitelist or allowed-name filtering. `TaskCommands#env` merges `@stack.env` before `deploy_spec.machine_env`, so a repo owner's declared `machine_env` keys correctly override label values, but any environment variable name not explicitly declared in the repo's own `shipit.yml` passes through unmodified into `Command#unbundled_env` and ultimately `PTY.spawn`.

### Finding Description
The broken binding: the set of keys surviving from `pull_request.labels` into `Command#unbundled_env` must be a subset of `deploy_spec.machine_env`'s declared keys; this does not hold.

Trace:
- `Shipit::ReviewStack#env` at `app/models/shipit/review_stack.rb:84-93` takes `pull_request.labels`, upcases each label name, and merges `{LABEL => "true"}` into `super` (the base `Stack#env`), with no filtering of label content or name.
- Labels are attacker-controlled: `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) writes `params.pull_request.labels.map(&:name)` directly from the incoming webhook payload into `pull_request.labels`, for any repository/PR whose webhook reaches `POST /webhooks` (an unprivileged repo owner can label their own PR to control this value; GitHub label names accept arbitrary characters including letters that map to shell-relevant identifiers like `RUBYOPT`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, etc.).
- `Shipit::TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) computes: `super.merge(@stack.env).merge({fixed vars}).merge(deploy_spec.machine_env).merge(@task.env)`. Because `@stack.env` (label-derived) is merged *before* `deploy_spec.machine_env` (`app/models/shipit/deploy_spec.rb:69-71`, the repo owner's own declared, spec-approved list), only keys the owner proactively declared in `machine.environment` get overridden/neutralized. Any key not present in `machine_env` (and not later present in `@task.env`) survives unmodified into the final merged hash.
- That hash is passed to `Command.new(command_line, env:, ...)` in `TaskCommands#perform`/`#install_dependencies` (`lib/shipit/task_commands.rb:17-27`), stored as `@env` in `Shipit::Command#initialize` (`lib/shipit/command.rb:31-37`), and injected via `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) directly into `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` (`lib/shipit/command.rb:92`) — the exact process spawned on the deploy host for that stack's steps.

Existing guards do not close this gap: `EnvironmentVariables#permit` and `filter_task_envs`/`filter_deploy_envs` restrict `@task.env` (explicit env params passed through the API for triggering deploys/tasks/rollbacks), not the label-derived `@stack.env` path, which is merged earlier and independently. There is no label-name allowlist anywhere in `ReviewStack#env` or `LabelCapturingHandler`.

### Impact Explanation
An unprivileged user who can label a PR on their own repository (which they control, since they opened it) can set arbitrary environment variable names/values (fixed to `"true"`) in the process environment of every subsequent deploy/task command run for that PR's review stack, as long as the repository owner has not proactively declared that same key in `shipit.yml`'s `machine.environment`. Depending on what commands the repo's own `shipit.yml` executes (e.g., `bundle install`, `rake`, custom scripts), attacker-controlled env vars such as `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`, `LD_PRELOAD`-style vectors, or tool-specific injection vectors could influence or hijack execution of the spawned process on the deploy host — this is a Critical-category impact (arbitrary influence over commands run via `Command`/`PTY.spawn`). The blast radius is confined to the attacking repository's own review-stack deploy host process (their own PR triggers their own stack's commands), but is fully repeatable for any review-stack-enabled repository and any label the attacker chooses, with no elevated privileges required beyond opening/labeling their own PR.

### Likelihood Explanation
Preconditions: the target repository must use Shipit's review-stack feature (PR-triggered stacks) and process `pull_request` labeled/unlabeled/opened/reopened webhooks (standard, documented functionality). The attacker only needs to be able to open a PR and add a label — both are actions available to any GitHub user in a repository they control (their own fork/PR), with no Shipit session or secret required. Cost is minimal (one webhook-triggering GitHub action), and the exploit is deterministic and repeatable for every deploy of that stack until the label is removed or the owner adds the matching key to `machine_env`.

### Recommendation
Do not allow arbitrary label names to define arbitrary environment variable keys. Either: (1) require repo owners to explicitly declare an allowlist of permitted label-derived environment variable names in `shipit.yml` and filter `ReviewStack#env`'s label merge against that allowlist before merging, or (2) namespace label-derived variables under a fixed, non-colliding prefix (e.g., `SHIPIT_LABEL_<NAME>`) so they cannot shadow arbitrary process/tool environment variables, and additionally ensure `TaskCommands#env` cannot let unexpected keys survive past `deploy_spec.machine_env` un-vetted.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_label_env_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsLabelEnvTest < ActiveSupport::TestCase
    test "label-derived env variables bypass machine_env for undeclared keys" do
      stack = shipit_stacks(:shipit) # a review-stack-backed stack fixture, or build a ReviewStack
      task = shipit_tasks(:shipit_deploy)
      task.stubs(:stack).returns(stack)

      stack.pull_request.update!(labels: %w[global rubyopt])

      commands = TaskCommands.new(task)
      commands.deploy_spec.stubs(:machine_env).returns({ 'GLOBAL' => '1' })

      env = commands.env

      assert_equal '1', env['GLOBAL'],       "declared machine_env key must win over label"
      assert_equal 'true', env['RUBYOPT'],   "undeclared key must NOT survive from label input, but it does"
    end
  end
end
```
Both assertions demonstrate the broken binding: `env['GLOBAL']` correctly reflects the repo-owner-declared `machine_env` value (label defeated), while `env['RUBYOPT']` — a key never declared by the repository owner — is fully attacker-controlled via the PR label and survives unmodified into the hash passed to `Command#unbundled_env` / `PTY.spawn`.
