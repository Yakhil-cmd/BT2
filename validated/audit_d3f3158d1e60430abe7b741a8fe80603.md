Confirmed: both `sqlite_pool.js` and `mysql_pool.js` wrap the DB driver so that **any error raised inside a query callback is re-thrown synchronously** [1](#0-0) [2](#0-1) , and ocore has **no global `uncaughtException`/`unhandledRejection` handler** in the main process files, so any uncaught `throw` inside a `conn.query` callback propagates out of the event loop and crashes the node process. This is the mechanism that turns an ordinary validation-invariant `throw` into a full-node DoS, analogous to CVE-2017-3273 (crash/hang caused by a malformed but "legal-looking" statement reaching an unguarded code path in DDL processing).

### Title
Unhandled exception on `definition template` re-validation crashes the node - (File: definition.js)

### Summary
`validateAuthentifiers()`'s inner `evaluate()` function re-checks the `'definition template'` operator every time an address using it signs a unit, but instead of returning a graceful validation error it does `throw Error("not 1 template")` when the referenced template unit query does not return exactly one row [3](#0-2) . This throw happens inside an asynchronous `conn.query` callback, and both the MySQL and SQLite connection wrappers re-throw query errors synchronously with no surrounding try/catch, so any thrown error inside such a callback becomes an uncaught exception that kills the process [1](#0-0) [2](#0-1) .

### Finding Description
An address definition may include a `['definition template', [unit, params]]` clause, which at definition-creation time is validated gracefully in `validateDefinition()` (returns `"template not found or too many"` as a normal callback error) [4](#0-3) . However, every time a unit is later signed by that address, `validateAuthentifiers()` is invoked to check the actual signature, and it performs an **independent, unguarded** re-evaluation of the same `'definition template'` clause via its own `evaluate()` function [5](#0-4) [3](#0-2) . The code comment at the call site even states the definition must be "re-validated every time" because the referenced state can legitimately change between validations [6](#0-5) . If the referenced `unit` row count is not exactly 1 (e.g., zero rows because the previously-referenced unit is no longer resolvable under the current `last_ball_mci`/stability window, or more than one row due to a state change), the code throws instead of calling back with an error. This throw occurs inside a `conn.query` callback (an async I/O boundary), which is not on the same call stack as `validateAuthentifiers`'s caller, so no `try/catch` upstream can intercept it, and the throw becomes a fatal, process-crashing `uncaughtException`.

### Impact Explanation
Any single crafted unit — reachable by an ordinary unit poster who defines (or gets someone to co-sign with) an address whose spending condition includes a `'definition template'` clause referencing a unit whose resolvability can be made to diverge from what it was during the address's first validation — can cause every full node/hub that processes it to crash with an unhandled exception (denial of service to the network), matching a "hang or frequently repeatable crash (complete DOS)" impact, the same class described in CVE‑2017‑3273.

### Likelihood Explanation
Exploitability requires an attacker to control or arrange a scenario where the second (authentifier-time) `SELECT ... FROM messages JOIN units ...` lookup for the referenced `definition_template` unit yields a row count different from the first (definition-time) lookup — e.g. by structuring template references near stability boundaries so mci-dependent filtering (`main_chain_index<=?`, `is_stable=1`) returns 0 or unexpectedly >1 rows on the later check. This requires some setup and timing but does not require any privileged network position — only a normal unit-posting capability defining and later using such an address.

### Recommendation
Replace the `throw Error("not 1 template")` (and the sibling `throw Error("more than 1 address definition")`) in `validateAuthentifiers`'s `evaluate()` with a graceful error callback (`cb2(false)` or an explicit validation failure passed through `cb`), mirroring the safe handling already used in `validateDefinition()`. More generally, audit all `throw` statements reachable from inside `conn.query` callbacks in unit-validation code paths, since the DB wrappers re-throw synchronously and no top-level exception handler exists to contain them.

### Proof of Concept
1. Post unit `U1` with `app: 'definition_template'` containing an arbitrary template array (`payload`), and let it become stable.
2. Define address `A` with spending condition `['definition template', [U1, {...}]]` and post a first unit signed by `A`, referencing `U1` while it is still resolvable — this passes `validateDefinition()`'s graceful check.
3. Craft a subsequent unit `V` signed by `A`, structured such that at authentifier-validation time the `SELECT payload FROM messages JOIN units USING(unit) WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1` query for `U1` (using `V`'s `last_ball_mci`) returns 0 rows (e.g., by referencing `U1` from a last-ball position where it is not yet marked stable/`main_chain_index<=?`, or by having it fall out of the retrievable/stable window relative to `V`).
4. When any node validates `V`, `validateAuthentifiers()`'s `evaluate()` hits the `'definition template'` branch, `rows.length !== 1`, and `throw Error("not 1 template")` fires inside the `conn.query` callback, propagating as an uncaught exception and crashing the validating node.
