Found a concrete authorization-scope violation in the CCMenu API controller that matches the "stack a token authorises versus a stack it touches" binding.

### Title
CCMenu API endpoint bypasses `ApiClient` stack-scoping, allowing a stack-scoped token to read any stack's status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that a stack-scoped `ApiClient` can only see the stack it was granted access to, by resolving the target stack through the `stacks` helper, which filters by `current_api_client.stack_id`. `Shipit::Api::CCMenuController` overrides `#stack` and resolves the stack directly via `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping. Any authenticated `ApiClient` holding the `read:stack` permission — even one created with `stack:` set to a single specific stack — can therefore query the CCMenu status of an arbitrary stack by simply changing the `stack_id` URL segment.

### Finding Description
`Shipit::Api::BaseController` defines the intended binding between a token and the stacks it may touch: [1](#0-0) 

`current_api_client.stack_id?` restricts `stacks` (and thus `stack`) to the single stack the `ApiClient` record was created for — this is the equality the code is supposed to preserve: `stack the token authorises == stack actually returned by #stack`.

`CCMenuController`, however, overrides `#stack` and skips the `stacks` scoping helper entirely: [2](#0-1) 

It still declares `require_permission :read, :stack` at the class level, but `ApiClient#check_permissions!` only checks that the permission string `read:stack` is present in the token's `permissions` array — it never checks which stack the token is bound to: [3](#0-2) 

So the only binding left standing is "does this token have `read:stack`", not "does this token have `read:stack` **for this stack**". Because `CCMenuController#stack` uses `Stack.from_param!` directly instead of `stacks.from_param!`, a token that is scoped to stack A (`ApiClient.stack_id == A.id`) can be replayed against `/api/stacks/*stack_id/ccmenu` with any other stack's `to_param` and will successfully render that stack's CI/deploy status.

Note the one built-in `ApiClient` this controller is designed for (created via `CCMenuUrlController`) is deliberately *not* stack-scoped: [4](#0-3) 

but any operator-created `ApiClient` (via `Shipit::ApiClientsController#create`) that is scoped to a specific stack (`belongs_to :stack, optional: true` and settable through the `api_clients` admin UI) and granted `read:stack` for use with CCMenu integrations is silently unscoped by this controller.

### Impact Explanation
This breaks the authorization boundary "the set of stacks a token is allowed to touch" and allows unauthorized cross-stack reads of stack/deploy status — matching the High-impact category "unauthenticated/unauthorized read of stack state, task streams or deploy output." The information disclosed (latest deploy/build status, timestamps, IDs, activity) is exactly what `CCMenuController#show` renders for the impersonated stack.

### Likelihood Explanation
Exploitation requires only a valid, currently-authenticated `ApiClient` token that is scoped to a single stack and has the `read:stack` permission (a normal, supported configuration for giving a team a CCMenu/CCTray integration limited to their own stack). No privileged account, webhook secret, or session is required beyond the caller's own legitimately-issued, narrowly-scoped API token — the attacker simply changes the `stack_id` in the request path/query.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot be used to query stacks outside their authorized scope.

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A: `ApiClient.create!(creator: admin, name: "team-a-cctray", stack: stack_a, permissions: ["read:stack"])`, and obtain its `authentication_token`.
2. Using that token (via Basic Auth or `?token=`), request `GET /api/stacks/<stack_b-owner>/<stack_b-repo>/<stack_b-env>/ccmenu` for an unrelated Stack B.
3. Observe that the request succeeds and returns Stack B's CCMenu status, even though the token is only supposed to authorize access to Stack A — because `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` without checking `current_api_client.stack_id`.
