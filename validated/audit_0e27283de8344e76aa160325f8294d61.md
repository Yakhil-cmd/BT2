### Title
API token scope bypass in CCMenu endpoint allows reading any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by the shared `Api::BaseController#require_permission` authorization check, replacing the scope-aware lookup (`stacks.from_param!`) with an unscoped, global lookup (`Stack.from_param!`). This breaks the binding `stack a token authorizes == stack it touches`: a token scoped to a single stack is checked against the `read:stack` permission list, but the actual record it acts on is resolved without applying the token's `stack_id` restriction, allowing that token to read CI/deploy status for any stack in the installation.

### Finding Description
`Api::BaseController` implements stack scoping centrally: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end

def require_permission!(operation, scope)
  current_api_client.check_permissions!(operation, scope)
end
```

`stacks` is the enforcement point that restricts a scoped `ApiClient` (one that has a non-nil `stack_id`) to only its own stack. `require_permission!` only validates that the client's `permissions` array contains `"read:stack"` — it never checks which stack is being accessed; the *scope* enforcement is entirely delegated to the `stack`/`stacks` helper being used to fetch the record.

`CCMenuController` overrides both `authenticate_api_client` (to accept a `?token=` query param instead of Basic Auth) and, critically, `stack` itself: [2](#0-1) 

```
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
```

Because `stack` here calls `Stack.from_param!` directly instead of `stacks.from_param!`, the `current_api_client.stack_id?` scoping is bypassed. `require_permission :read, :stack` still passes for any client holding the `read:stack` permission, regardless of its `stack_id`.

This client-scoping mechanism exists specifically for this feature: `CCMenuUrlController#client` mints a per-stack, `read:stack`-only `ApiClient` intended to be embedded in a CI status URL: [3](#0-2) 

The whole point of minting this client is that it should only be able to read the one stack it was generated for. The `CCMenuController#stack` override defeats that intent.

### Impact Explanation
An attacker who obtains one legitimate CCMenu token (e.g., pasted into a CI dashboard config, a public CI tray widget, a shared build page, or a log) for **any** stack can supply an arbitrary `stack_id` in the request to `GET /api/:stack_id/cctray.xml` (per `config/routes.rb` mount for `ccmenu#show`) and retrieve the latest deploy/rollback status for **every other stack** in the Shipit installation — data the token was never authorized to see. This is an unauthorized read of stack state across trust boundaries defined by `ApiClient#stack_id`, matching the "High" impact category of escalation past a token's authorized stack scope.

### Likelihood Explanation
Likelihood is Low-to-Medium: exploitation requires possession of a single valid (but narrowly-scoped) CCMenu token, which is by design distributed outside the main authenticated Shipit UI (embedded in CI dashboard/CCTray tool configuration, often as a plain URL query parameter) — a realistic leak vector, but it still requires the attacker to have obtained at least one such token. No authentication bypass or credential forgery is needed beyond that; the exploit is a single crafted request.

### Recommendation
Change `CCMenuController#stack` to reuse the scope-aware `stacks` collection from `BaseController`, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the invariant that `require_permission :read, :stack` and the resolved `stack` record are both constrained by `current_api_client.stack_id`, consistent with every other controller under `app/controllers/shipit/api/**`.

### Proof of Concept
1. As an authenticated Shipit user, visit stack A's settings page to trigger `CCMenuUrlController#fetch` for stack A, obtaining a URL like:
   `https://shipit.example.com/api/<stack-A-param>/cctray.xml?token=<TOKEN_A>`
   `TOKEN_A` authenticates an `ApiClient` with `permissions: ["read:stack"]` and `stack_id = A.id`.
2. As an unprivileged party who only has `TOKEN_A` (e.g., scraped from a public CI dashboard), request:
   `GET /api/<stack-B-param>/cctray.xml?token=<TOKEN_A>`
   where stack B is a different, unrelated stack.
3. `authenticate_api_client` authenticates `TOKEN_A` successfully via `ApiClient.authenticate`.
4. `require_permission :read, :stack` passes because `TOKEN_A`'s permission list contains `read:stack` (the check never looks at `stack_id`).
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` — ignoring `current_api_client.stack_id` — and returns stack B.
6. The response renders stack B's latest deploy/rollback status in `shipit/ccmenu/project.xml`, disclosing data the token was never scoped to access.

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
