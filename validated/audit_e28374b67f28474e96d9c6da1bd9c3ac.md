### Title
Webhook signature verified against the organization derived from `repository.owner.login`, but the record acted upon is looked up from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` derives the GitHub App/organization used for HMAC verification from the payload itself, not from any value tied to the target `Repository`/`Stack` record: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` selects which configured GitHub App's `webhook_secret` is used to validate `X-Hub-Signature` via `verify_webhook_signature`.

Once the signature check passes, the event is routed to a handler (e.g. `PushHandler`) which looks up the `Stack`/`Repository` to act on using a *different* field of the same attacker-supplied JSON body: `repository.full_name`: [3](#0-2) [4](#0-3) 

This is the same class of bug as the `Token.sol` finding: the check is performed on one derived value (`repository.owner.login` → which secret is used), while the security-relevant action is performed using a different, independently-controlled value (`repository.full_name` → which `Stack` is mutated). Nothing in `Handler#repository_name` / `Handler#stacks` re-validates that the resolved repository actually belongs to the organization whose secret validated the signature.

In Shipit's documented multi-organization deployment mode (`docs/setup.md`, "Using Multiple Github Applications"), a single Shipit instance holds a distinct `webhook_secret` per organization, but all organizations' stacks share the same `/webhooks` endpoint and the same `WebhooksController`/`Handler` code path. An entity that legitimately administers "OrgB" (and thus knows OrgB's `webhook_secret`, since GitHub App webhook secrets are configured/visible to whoever set up the App for that org) can send a POST to `/webhooks` where:
- `repository.owner.login = "OrgB"` (so the HMAC is computed/verified with OrgB's secret — passes),
- `repository.full_name = "OrgA/some-tracked-repo"` (an unrelated repository/stack tracked by the same Shipit instance, belonging to a different organization).

The equality that should hold is: `organization whose secret authenticated the request == organization owning the repository/stack that gets mutated`. This binding is broken because the two values are read from independent, both attacker-controlled, JSON fields with no cross-check.

### Impact Explanation
Once past `verify_signature`, event handlers act on whatever stack `Repository.from_github_repo_name(repository.full_name)` resolves to, using other attacker-supplied fields in the same forged JSON body — not anything actually observed on GitHub for that repo. Concretely, `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for the target `OrgA` stack based purely on the forged payload's `ref`/`after` fields. Other in-scope handlers (`status`, `check_suite`, `pull_request`, `membership`) follow the identical `payload.dig('repository','full_name')` resolution pattern in `Handler#repository_name`/`#stacks`, so the same cross-organization confusion applies to commit-status and merge-queue-relevant events, which can influence whether a commit is treated as deployable/mergeable for a repository the forger does not control on GitHub. Because Shipit stacks with `continuous_deployment: true` auto-deploy based on synced state, this can escalate into an unauthorized deploy trigger against a stack belonging to an organization the attacker was never authorized against — crossing the organization boundary Shipit's per-org webhook secrets are meant to enforce.

### Likelihood Explanation
Requires the attacker to be a legitimate administrator/owner of at least one organization ("OrgB") whose GitHub App is configured on the same Shipit instance that also tracks stacks for other organizations ("OrgA") — the documented multi-org configuration. No GitHub write access to OrgA, no Shipit session, and no `ApiClient` token are needed: only OrgB's own `webhook_secret`, which that org's admins already legitimately hold. This is a realistic configuration per `docs/setup.md`'s "Using Multiple Github Applications" section, though it does depend on the operator running multiple orgs off one instance.

### Recommendation
After resolving the target `Stack`/`Repository` from `repository.full_name`, verify that its `owner`/organization matches the `repository_owner` (or `organization.login`) value that was used to select the verifying `webhook_secret`, and reject the event (422) on mismatch — i.e., bind signature verification and target-resolution to the same, single source of truth rather than two independently-controlled payload fields.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App / `webhook_secret`, per `docs/setup.md`. `OrgA/some-repo` is tracked as a Shipit stack with `continuous_deployment: true`.
2. As the legitimate administrator of `OrgB`, know `OrgB`'s `webhook_secret` (you configured it).
3. Craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-existing-sha-in-OrgA/some-repo>",
     "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/some-repo" }
   }
   ```
4. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(OrgB's `webhook_secret`, raw body).
5. POST to `/webhooks` with `X-Github-Event: push` and the computed signature.
6. `verify_signature` resolves `repository_owner = "OrgB"`, verifies successfully against OrgB's secret.
7. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgA/some-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the `OrgA` stack — an event never actually observed on GitHub for `OrgA`, forged entirely using `OrgB`'s credential.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
