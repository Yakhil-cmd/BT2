### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login`, but repository written is resolved from unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which HMAC secret to check the request against using `repository_owner`, an **unauthenticated** field read directly out of the still-unverified JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature check passes, every `Handler` (e.g. `PushHandler`) resolves the *actual* repository/stack to mutate from a *different* field of the same unverified body: `payload.dig('repository', 'full_name')`. In a multi-organization Shipit deployment (`Shipit.github_organizations`/`github_app_config`), nothing binds the `owner.login` used for authentication to the `full_name` used for the write, so a payload can be signed with organization A's webhook secret while acting on organization B's repository/stack.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON, before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`github_app_config`), each with its own independently configured `webhook_secret`: [3](#0-2) 

The HMAC itself (`verify_webhook_signature`) only proves the raw body was signed with *some* organization's secret - it says nothing about which repository the body's other fields should be trusted for: [4](#0-3) 

After signature verification succeeds, handlers resolve the target `Stack`/`Repository` using `repository.full_name` from the same JSON body - a field that was never cross-checked against `repository.owner.login`: [5](#0-4) [6](#0-5) 

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login)` == `repository actually written by the handler (repository.full_name)`

Because both fields live in the same unauthenticated JSON payload and are read independently, an operator who legitimately controls a GitHub organization "attacker-org" configured in this same Shipit instance (and therefore knows/controls "attacker-org"'s `webhook_secret`) can forge a POST to `/webhooks` where:
- `repository.owner.login` = `"attacker-org"` (so `verify_signature` picks "attacker-org"'s secret and the HMAC computed with that secret validates), and
- `repository.full_name` = `"victim-org/victim-repo"` (so `PushHandler`/other handlers resolve and mutate the victim's `Stack`, e.g. via `sync_github`, PR review-stack provisioning/archival, `check_suite`, `membership`, etc.).

This breaks the trust binding "the organization whose secret authenticated the request" vs "the repository that is written," exactly analogous to the SY report's core defect: a value used for a security-relevant decision (asset conversion rate / here, which secret authorizes the action) is decoupled from the value actually acted upon (base asset amount / here, the repository actually mutated), because the two reads are not atomically bound to a single verified quantity.

### Impact Explanation
This allows any operator of one organization onboarded to a shared Shipit instance to trigger state-changing webhook effects (stack sync from a spoofed `after` SHA, review-stack archive/unarchive/provisioning, membership/team changes, check-run refresh) against a *different* organization's stacks, without ever possessing that victim organization's webhook secret. Depending on which handler is reached, this can drive `sync_github` on a victim `Stack` with attacker-chosen `expected_head_sha`, or manipulate `PullRequest`/review-stack lifecycle for a repository the attacker does not own - a cross-repository/cross-tenant write performed purely by forging a webhook payload with mismatched `owner.login`/`full_name`, satisfying the "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one GitHub organization (multi-tenant setup, a documented supported configuration via `github_app_config`), and that the attacker legitimately controls at least one such organization's webhook secret (their own, not the victim's). No GitHub App private key, no victim credentials, and no session/token are needed - this is exactly the "unprivileged attacker" class the rules target, and does not depend on the host mis-mounting the engine.

### Recommendation
Bind the two lookups to the same verified value: after the signature is verified for organization `O`, require that `repository.full_name`'s owner segment matches `O` (or, more robustly, look up the target `Repository`/`Stack` scoped to the authenticated organization rather than trusting `full_name` globally). Reject the webhook (422) if the two disagree.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `attacker-org` (secret known to the PoC author, who administers that GitHub org) and `victim-org` (unrelated, existing `Stack` with `repository.full_name == "victim-org/victim-repo"`).
2. Craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` using `attacker-org`'s known webhook secret over this exact raw body (`OpenSSL::HMAC.hexdigest('sha1', attacker_org_secret, body)`), matching `GitHubApp#verify_webhook_signature`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates successfully (attacker owns that secret).
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` (per `Handler#repository_name`) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack - a write the attacker was never authorized to trigger, using an organization's secret other than the victim's.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
