## Analysis

The `StatusHandler#process` looks up commits purely by `sha` (globally, not scoped to a repository), attaching CI status via `commit.create_status_from_github!(params)`. Combined with the webhook path, this confirms the binding-break: `Shipit::Webhooks::Handler#repository_name` (used to select the target `Stack`/`Repository`) reads `payload.dig('repository', 'full_name')` while `WebhooksController#repository_owner` (used to pick the HMAC secret for signature verification) reads `payload.dig('repository', 'owner', 'login')` — two independent, attacker-controlled fields from the same unauthenticated JSON body that are never cross-checked against each other.

### Title
Webhook signature verification selects the GitHub-app secret by an unverified `repository.owner.login` field, decoupled from the `repository.full_name` the handlers act on - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which configured GitHub App/secret to validate against using `repository_owner`, derived from `params.dig('repository','owner','login')` in the raw, unauthenticated request body [1](#0-0) , and this same fallback logic also reads `organization.login` [2](#0-1) . Meanwhile, the actual repository whose stacks are mutated is resolved by `Handler#repository_name` from `payload.dig('repository', 'full_name')` [3](#0-2) . These are two independently attacker-supplied fields inside the same unsigned-until-verified JSON body.

### Finding Description
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success: `return true unless webhook_secret` [4](#0-3) . `webhook_secret` is documented as optional per organization [5](#0-4) , and the multi-organization config format allows each org to have its own independent `webhook_secret` [6](#0-5) .

Because `verify_signature` selects the app/secret via `Shipit.github(organization: repository_owner)` [7](#0-6) , an attacker who knows that any one configured organization in the install has no `webhook_secret` set can put that organization's name in `repository.owner.login` (or `organization.login`) purely to make `verify_signature` pass unconditionally, while putting a *different*, secret-protected organization/repo's name in `repository.full_name` — the field actually used by `Handler#repository_name` / `Repository.from_github_repo_name` to select which `Stack` receives the event [8](#0-7) . The equality the engine is implicitly assuming, but never enforces, is:

`organization that authenticated the request` == `repository the handler mutates`

For `push` events this reaches `PushHandler#process`, which finds stacks and calls `stack.sync_github(expected_head_sha: params.after)` for any non-archived stack matching the forged branch [9](#0-8) , forcing an out-of-band resync/deploy trigger for a repository that never authorized this request. For `status` events, `StatusHandler#process` resolves commits purely by `sha` (with no repository scoping at all) and attaches an attacker-forged CI status via `commit.create_status_from_github!(params)` [10](#0-9) , which can be used to fake a "success" status on a real commit and unlock deployability checks that gate automatic/continuous deployment.

### Impact Explanation
This breaks the "authenticated organization vs. written repository" binding required by scope: an unprivileged, unauthenticated attacker (no Shipit session, no GitHub credentials, no webhook secret) can forge webhook events for any repository configured in the Shipit install, as long as at least one other configured organization in the same install lacks a `webhook_secret` (an explicitly supported, documented configuration). This can be used to inject forged commit statuses that unlock deploy gating (leading to an unauthorized deploy) or to force a stack resync/deploy trigger via forged `push` events, satisfying the High/Critical bar of "an unauthorized deploy" or "escalation" via the webhook trust boundary.

### Likelihood Explanation
Requires a Shipit deployment configured with multiple GitHub organizations (a supported, documented feature) where at least one organization omits `webhook_secret` — a state explicitly allowed by the docs ("Webhook secret (optional)"). Given that, exploitation requires no credentials, no session, and no knowledge of any secret; only knowledge of the no-secret org's name and the target repo's `full_name`, both learnable from public information (org/repo names are public on GitHub).

### Recommendation
Verify the webhook signature using the secret associated with the organization that actually owns `repository.full_name` (the value the handlers use), not a value independently re-derived from another attacker-controlled field. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for one org while other orgs in the same install do have secrets configured — either require a secret for every org once any org has one, or reject cross-organization mismatches between the field used for authentication and the field used to select the target repository/stack.

### Proof of Concept
Given an install with `OrgA` (has `webhook_secret`) and `OrgB` (no `webhook_secret`, per the documented optional-secret multi-org format [11](#0-10) ):

1. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or an arbitrary one).
2. Body: `{"repository": {"owner": {"login": "OrgB"}, "full_name": "OrgA/victim-repo"}, "ref": "refs/heads/master", "after": "<sha>"}`.
3. `verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the signature header [4](#0-3) .
4. `create` then dispatches to `PushHandler`, which resolves `repository_name` as `"OrgA/victim-repo"` [12](#0-11)  and calls `stack.sync_github` on `OrgA`'s protected stack, all without ever knowing `OrgA`'s webhook secret.

I was not able to fully trace `Stack#sync_github`'s downstream effects (e.g., whether it can trigger continuous deployment directly) within the available context; a Devin session with full repo access would be needed to confirm the exact deploy-triggering chain from `sync_github` and `create_status_from_github!` to a concrete unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
