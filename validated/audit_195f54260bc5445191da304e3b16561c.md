### Title
Webhook signature is verified against an org chosen from the attacker-controlled payload, letting a signer for org A forge trusted events for repositories in org B - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to check the `X-Hub-Signature` against by reading `repository_owner` straight out of the same unauthenticated JSON body it is about to verify. Once the HMAC checks out, the *entire* payload — including a completely different `repository.full_name` — is trusted and dispatched to handlers that resolve the target `Stack`/`Repository` solely from that `full_name` field, with no cross-check that it belongs to the organization that actually produced the signature.

### Finding Description
`verify_signature` computes the authenticating organization like this: [1](#0-0) 
`repository_owner` is derived from: [2](#0-1) 

Both fields (`repository.owner.login` used for verification, and `repository.full_name` used later to locate the target) live inside the same attacker-supplied `request.raw_post`. Shipit explicitly supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, selected via `Shipit.github(organization:)`: [3](#0-2) 

Downstream, every webhook handler locates the affected `Stack` purely from `repository.full_name`, never revisiting `repository.owner.login`: [4](#0-3) 

So an attacker who legitimately controls (or has been granted) a GitHub App installation on organization A — and therefore knows/derives A's `webhook_secret` — can craft a JSON body with `repository.owner.login = "A"` (so `verify_signature` picks A's secret and the HMAC they compute themselves validates) while setting `repository.full_name = "B/victim-repo"` for an unrelated organization B tracked by the same Shipit instance. The signature check only proves "the sender knows org A's secret"; it does not prove anything about org B or about the repository the payload claims to describe. Nothing in the controller or in `Handler#repository_name` reconciles the two fields.

This breaks the intended binding **organization that authenticated == organization whose repository is written**: the equality holds in the legitimate flow (owner and full_name normally refer to the same real GitHub repository) but is never enforced, so it can be forced apart by any payload the attacker constructs.

### Impact Explanation
Once the forged `push` event is accepted, `PushHandler`/`GithubSyncJob` treat it as an authentic event for org B's repository and enqueue a sync that fetches commits from GitHub for that stack and appends them to the deployable history: [5](#0-4) 
Similarly, `status`/`check_suite` handlers would update commit deployability state for repository B based purely on the trusted-but-misattributed payload. Because commit status and "deployable" state gate the merge queue and deploy pipeline, an attacker who only controls a low-trust organization onboarded to the same Shipit instance can inject events that manipulate another organization's stack state, feeding into unauthorized deploys/merges — a cross-repository/cross-organization trust break with no legitimate access to org B required.

### Likelihood Explanation
Requires the multi-organization configuration to actually be used (more than one `github` app/org configured with independent `webhook_secret`s in `secrets.yml`, as documented/tested via `secrets_double_github_app.yml`), and requires the attacker to control/administer at least one of those lower-trust organizations that is legitimately onboarded to the shared Shipit instance. Given Shipit explicitly supports and tests this multi-org configuration, and the webhook endpoint is publicly reachable and unauthenticated apart from the per-payload HMAC, this is a realistic misconfiguration-adjacent but in-scope condition — not a hypothetical.

### Recommendation
After `verify_webhook_signature` succeeds using the organization derived from `repository.owner.login` (or `organization.login`), re-derive the same organization from `repository.full_name` (and any other repository references handlers rely on, e.g. `pull_request.base.repo.full_name`) and reject the payload (422) if they don't match the org that signed it. Alternatively, look up the `Repository`/`Stack` record by `full_name` first and confirm its stored organization matches `repository_owner` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two organizations/apps, `orgA` and `orgB`, each with a distinct `github.webhook_secret` (supported per `lib/shipit/github_app.rb` and `Shipit.github(organization:)`).
2. As an admin of `orgA` (or anyone who knows `orgA`'s webhook secret), craft a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha visible on orgB/victim-repo>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST it to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and the HMAC validates (attacker knows `orgA`'s secret), so the request passes.
5. `PushHandler`/`Handler#repository_name` resolves the target via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"`, enqueuing `GithubSyncJob` for `orgB`'s stack even though the signature only proved knowledge of `orgA`'s secret. [6](#0-5) [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
