### Title
Webhook signature verification is keyed by `repository.owner.login`/`organization.login` while event handlers act on the unrelated `repository.full_name` field, enabling cross-organization webhook forgery in multi-app deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate `X-Hub-Signature` against using `repository_owner`, taken from the *organization*-identifying fields of the JSON body. [1](#0-0) [2](#0-1)  Every event handler, however, resolves the *repository/stack that is actually written to* from a completely different, independently-controlled field: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing ties these two fields together, so the organization whose credentials were checked is not necessarily the organization whose repository is mutated.

### Finding Description
Shipit supports hosting multiple GitHub Apps, one per organization, each with its own independently optional `webhook_secret` (`docs/setup.md` and the shipped multi-org example configs explicitly show `webhook_secret: # nil`). [4](#0-3) [5](#0-4)  `GitHubApp#verify_webhook_signature` unconditionally accepts the request when that org's `webhook_secret` is blank:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [6](#0-5) 

`verify_signature` picks the `GitHubApp` to check against based on `repository_owner`, which is read straight from the unauthenticated JSON body (`repository.owner.login` or `organization.login`) *before* any signature is verified:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [7](#0-6) 

Once past this check, `WebhooksController#create` dispatches the *entire* raw payload to the matching event handlers unchanged. [8](#0-7)  Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) resolves the target `Repository`/`Stack` via `Handler#stacks`/`#repository_name`, which reads `payload.dig('repository', 'full_name')` — a field that is never compared against `repository_owner`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [9](#0-8) 

**The binding that should hold, but doesn't:** `repository_owner (used to authenticate) == owner(repository.full_name) (used to act)`.

Concretely, in a deployment with two configured organizations — `OrgA` (properly secured, `webhook_secret` set) and `OrgB` (no `webhook_secret`, a documented/supported configuration) — an unprivileged attacker can:
1. Send `POST /webhooks` with `X-Github-Event: status` (or `push`, `check_suite`) and body `{"repository": {"owner": {"login": "OrgB"}, "full_name": "OrgA/critical-repo"}, ...}`, and no valid `X-Hub-Signature`.
2. `verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `verify_webhook_signature` returns `true` unconditionally because `OrgB` has no secret configured — the request is accepted without any authentication.
3. The handler then acts on `repository.full_name == "OrgA/critical-repo"`, which belongs to the fully-secured `OrgA`, and is completely unrelated to `OrgB`.

### Impact Explanation
This lets an attacker forge webhook events (`push`, `status`, `check_suite`, `pull_request`) for repositories belonging to an org that is otherwise fully protected by a webhook secret, as long as *any* other configured org lacks one. Concretely this enables:
- Forging `status`/`check_suite` "success" events for arbitrary commits of a protected repository — Shipit's merge queue/deploy gating relies on these CI signals, so this can unlock unauthorized merges/deploys.
- Enqueuing `GithubSyncJob`/`RefreshStatusesJob`/`RefreshCheckRunsJob` against the target stack with attacker-chosen `expected_head_sha`, corrupting Shipit's view of the target repository state.
- Creating/opening review-stack provisioning flows for arbitrary repositories via the `pull_request` handlers, since they also key off the same `repository.full_name` field.

This is a cross-repository write / potential unauthorized-deploy vector triggered purely by an unauthenticated POST, matching the report's core theme: a value the code implicitly trusts as authorizing an action (`repository.owner.login`, checked against the signing secret) is not the same value the code actually uses to decide what gets mutated (`repository.full_name`).

### Likelihood Explanation
Requires a real-world deployment that configures more than one GitHub App/organization (a fully-supported and documented feature, tested via `test/dummy/config/secrets_double_github_app.yml`) where at least one configured organization has no `webhook_secret` set — which the shipped example config files present as the default (`webhook_secret: # nil`). Given `webhook_secret` is explicitly documented as "optional," multi-tenant Shipit installs onboarding a low-value/staging org without bothering to set a secret are plausible, and the attack itself requires no credentials, only network access to `/webhooks`.

### Recommendation
- Do not select the verification key from unauthenticated payload fields and then let handlers act on a different, uncorrelated payload field. Either:
  - Require every configured organization to have a non-blank `webhook_secret` (remove the `return true unless webhook_secret` bypass), or
  - After signature verification, assert that the resolved `repository_owner` used for verification matches the owner segment of `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers.

### Proof of Concept
Assume `config/secrets.yml` configures two orgs: `OrgA` (`webhook_secret: "s3cret"`) and `OrgB` (`webhook_secret:` blank), per the documented multi-org format. [10](#0-9) 

```
POST /webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/critical-repo" },
  "sha": "<victim-pending-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example/",
  "description": "forged"
}
```
- `repository_owner` resolves to `"OrgB"` → `Shipit.github(organization: "OrgB").verify_webhook_signature` returns `true` (no secret configured). [11](#0-10) 
- `StatusHandler`/`Handler#repository_name` resolves `"OrgA/critical-repo"` and updates the commit status for `OrgA`'s repository, an organization the attacker never authenticated against. [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
