### Title
Cross-repository status webhook triggers deploy on unrelated stack via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no scoping to the repository/organization that authenticated the webhook, unlike `PushHandler` which scopes through the `stacks` helper (`.where(branch:)` on stacks belonging to the signing repository). Because git SHAs are content-addressed and deterministic (e.g., the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any commit shared across a fork and its upstream), an attacker who owns an unrelated repository can get a `status` webhook signed with their own `webhook_secret` to flip `deployable?` and trigger a real deploy on a victim's `Stack`.

### Finding Description
The binding the code needs to hold is:
`org(webhook_secret used to sign the request) == org(repository_owner of stack.repository for every Commit row matched by params.sha)`

Trace:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) only validates that the request was signed by `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload's `repository.owner.login` (app/controllers/shipit/webhooks_controller.rb:59-62). This proves the request came from *some* org's webhook secret — the attacker's own org, since they control that repo and its secret.
2. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a **global, unscoped** lookup across the entire `commits` table — it never checks `commit.stack.repository` against the `repository_owner`/`repository.full_name` from the signed payload. Contrast with `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17), which restricts to `stacks.not_archived.where(branch:)`, where `stacks` (defined in `Handler`, app/models/shipit/webhooks/handlers/handler.rb) is scoped to the repository that signed the request. `StatusHandler` bypasses this repository-scoping entirely.
3. `create_status_from_github!` → `add_status` → `Commit#deployable?` (app/models/shipit/commit.rb:227-229): `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. A `success` status flips this true for the victim's commit.
4. `add_status` triggers `Hook.emit(:deployable_status, ...)` and, via the `after_create`/create path, `schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287) enqueues `ContinuousDeliveryJob.perform_later(stack)` — the **victim's** `stack`, since `commit.stack` is whatever stack the matched row belongs to, not anything derived from the attacker's payload.
5. `ContinuousDeliveryJob` calls `Stack#trigger_continuous_delivery` → `trigger_deploy`, deploying the victim's stack.

The attacker's exact request: push an empty-tree commit (or any commit that is byte-identical/SHA-identical to one already recorded for the victim's stack, e.g. via forking the victim's public repo so the shared history commits carry identical SHAs) to a repository they own, then `POST /webhooks` with `X-Github-Event: status`, body `{"sha": "<shared-sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}`, signed with `attacker-org`'s webhook secret. `verify_signature` passes because it only checks that *an* org's secret matches the payload's *claimed* owner — it never cross-checks that this org actually owns the stack whose commit will be mutated.

None of the listed guards catch this: `verify_signature` authenticates the sender's org, not the target stack's org; `ExplicitParameters` (the `params do ... end` schema) only validates the shape of `sha`/`state`, not repository identity; `drop_unhandled_event` and `check_if_ping` are irrelevant; there is no `require_permission!`/`User#authorized?` check in the webhook path since it's machine-to-machine; and `Repository`/`Stack` model validations don't constrain which `Commit` rows a status update may touch.

### Impact Explanation
An attacker fully controlling a throwaway GitHub repository (and its own legitimate webhook secret) can force `Shipit::Commit#deployable?` to become true for a `Commit` row belonging to a completely unrelated victim `Stack`, and with `continuous_deployment: true` on that stack this results in an **unauthorized deploy being triggered for a repository/organization the attacker never authenticated against**. This matches the "Critical" category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". The technique is repeatable against any stack/commit whose SHA the attacker can predict or reproduce (empty-tree SHA is universal and deterministic; forked repositories share ancestor commit SHAs), so the blast radius spans any multi-tenant Shipit install where stacks track different repos/orgs but a commit SHA collision (empty tree, or shared git history via fork) exists.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true` and an undeployed `Commit` row whose SHA the attacker can reproduce (trivial for the well-known empty-tree SHA, or achievable by forking the victim's repo so a common-ancestor commit's SHA is identical). The attacker needs only: a GitHub repo they own (free), the ability to register/trigger a webhook for it (standard GitHub feature, no elevated Shipit permission), and knowledge of the target SHA (discoverable via the victim's public commit history or GitHub PR UI, or the universal empty-tree SHA needing no reconnaissance at all). No Shipit credentials, session, or API token are required. This is fully repeatable and requires no interaction with the victim.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/organization that authenticated the webhook, mirroring `PushHandler`'s use of the `stacks` scope, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
where `stacks` is restricted to stacks whose `repository.owner`/`full_name` matches the payload's `repository` that was verified by `verify_signature`. More generally, every webhook handler that performs a lookup keyed only by content-addressable data (SHA) must additionally scope by the authenticated repository, never trusting a bare `Commit.where(sha:)`/global lookup.

### Proof of Concept
Add a minitest in `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extend `webhooks_controller_test.rb`):
```ruby
test "status webhook from org A's repo cannot deploy org B's stack via shared sha" do
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904' # empty tree sha
  stack_a = shipit_stacks(:cyclimse) # owned by org "cyclimse"
  stack_b = shipit_stacks(:shipit)   # owned by org "shopify", continuous_deployment: true
  stack_b.update!(continuous_deployment: true)

  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'victim commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => 'cyclimse' } } # attacker's own org, signs with cyclimse's secret
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  GithubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # cyclimse's own secret legitimately verifies

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b]) do
    post :create, body: payload, as: :json
  end

  # Binding check: org that signed (cyclimse) != org owning the deployed stack (shopify)
  assert_not_equal 'cyclimse', stack_b.repository.owner
  assert commit_b.reload.deployable?
end
```
Assert both sides of the binding explicitly: `signing_org = 'cyclimse'` vs `stack_b.repository.owner = 'shopify'` — they differ, yet `ContinuousDeliveryJob` is enqueued for `stack_b`, proving the binding is broken.
