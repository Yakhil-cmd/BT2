### Title
Stale block-cached liquidity index lets zToken collateral retain pre-loss valuation after `socialize-debt` in the same block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` caches each vault's `index`/`lindex` in `index-cache-` keyed only by `{ timestamp: stacks-block-time, aid }`, so the cache is shared by every transaction in the same block, not just within one transaction. [1](#0-0)  `vault-socialize-debt` writes down a vault's `lindex` directly on the vault contract, bypassing `accrue-and-cache` entirely. [2](#0-1)  The vault's own `socialize-debt` function marks down `lindex` proportionally to the loss, without going through the market's caching path at all. [3](#0-2)  As a result, if `index-cache-` for that `(timestamp, aid)` was already populated earlier in the same block (e.g., during the liquidator's own accrual step, or by any prior user transaction that touched that vault), the cached, pre-loss `lindex` remains in the map after `socialize-debt` executes.

### Finding Description
`accrue-and-cache` returns whatever is already stored for `{timestamp, aid}` without ever re-checking freshness against the vault's live state: on a cache hit it just returns the cached tuple. [1](#0-0)  This cache is consumed by `accrue-user-collateral`/`accrue-collateral-asset` when resolving zToken prices for collateral valuation and health checks. [4](#0-3) 

Because `socialize-debt` is invoked as a direct vault call from market (`vault-socialize-debt`) rather than through `accrue-and-cache`, it never updates or invalidates `index-cache-`. [2](#0-1)  The vault-side `socialize-debt` reduces `lindex` to reflect a bad-debt loss on suppliers (`new-lindex` computed from `old-total-assets - debt-reduction`), which lowers the real redemption value of that vault's zTokens. [5](#0-4) 

Attacker/victim relationship and shared state:
- **Shared state:** `index-cache-` map in `market.clar`, keyed only by block timestamp and asset id (not by transaction).
- **Attacker:** any user with an existing position holding the affected zToken as collateral, or a liquidator/borrower acting immediately after a socialize-debt event lands in the same block.
- **Victims:** other suppliers of that vault (who already absorbed the loss via lower `lindex`) and the protocol's solvency, since the attacker's collateral/borrow capacity is computed off the stale, higher pre-loss index for the remainder of the block.

Sequence:
1. Earlier in a block, some operation on vault X causes `accrue-and-cache` to populate `index-cache-` for `{timestamp, aid: X}` with the current (pre-loss) `lindex`.
2. A liquidation later in the same block triggers `vault-socialize-debt` on vault X, marking down the real `lindex` on the vault contract directly - `index-cache-` is untouched.
3. Any subsequent transaction in that same block that adds zToken-X collateral, borrows against it, or has its position health evaluated will call `accrue-and-cache` for aid X, get a cache HIT, and use the now-stale, overvalued `lindex` to price that collateral.
4. A user can use this inflated valuation to justify a larger new borrow (their `add-collateral`/borrow capacity check passes using the stale, too-high index) or to make their position appear healthier than it truly is, escaping a liquidation that should otherwise trigger with the corrected valuation - all while other suppliers already bear the socialized loss reflected in the vault's true (marked-down) `lindex`.

### Impact Explanation
This allows a borrower to extract debt/borrowing capacity backed by collateral that is not actually worth what the market believes for the rest of the block, or to dodge a legitimate liquidation immediately following a socialize-debt event. Both outcomes increase uncollateralized/under-collateralized debt beyond what the true (post-loss) collateral value supports, which is a path to protocol insolvency and effectively an additional loss socialized onto honest suppliers beyond the already-recognized bad debt. This lands in the **Critical - protocol insolvency** impact class.

### Likelihood Explanation
Requires: (a) a `socialize-debt` event (already an exceptional, bad-debt event) occurring in the same block as (b) a prior cache-priming operation on the same vault asset and (c) a subsequent same-block operation by the attacker on that asset. Because socialize-debt is triggered as part of liquidation processing of bad debt, an attacker (or a liquidator working with an attacker, e.g. via a bundled/back-run transaction in the same block) has some control over ordering and can prime and then exploit the cache within one block. Likelihood is Low-Medium given it depends on a rare bad-debt/socialization event combined with same-block ordering.

### Recommendation
Invalidate or bypass `index-cache-` for an asset whenever its underlying vault state changes outside of `accrue-and-cache` (in particular after `socialize-debt`), e.g., by calling `accrue-and-cache`/re-caching with fresh indexes immediately after `vault-socialize-debt`, or by removing the entry from `index-cache-` for that `{timestamp, aid}` so the next read forces a fresh `vault-accrue` call.

### Proof of Concept
1. Block N, tx 1: User B performs any operation on vault-STX (e.g., a normal borrow) that causes `accrue-and-cache` to cache `{timestamp: T, aid: STX}` with `lindex = L0`.
2. Block N, tx 2: A liquidation of an underwater position triggers `vault-socialize-debt STX amount`, which calls `vault-stx.socialize-debt`, writing the vault's live `lindex` down to `L1 < L0` to reflect the loss - `index-cache-` for `{T, STX}` still holds `L0`. [3](#0-2) 
3. Block N, tx 3: Attacker calls `collateral-add`/`borrow` using zSTX collateral; `accrue-and-cache` hits the stale cache entry and returns `lindex = L0` instead of the true `L1`, overvaluing the attacker's zSTX collateral and letting them borrow more than the post-loss collateral value justifies. (define-private (accrue-and-cache (aid uint))
```text
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
```
