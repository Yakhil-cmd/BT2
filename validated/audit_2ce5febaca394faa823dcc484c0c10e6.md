### Title
Legacy `pattern:` field inference in `Rule.from_dict` silently fails to block `Write`-tool content, unlike explicit `conditions` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` converts a legacy `pattern:` frontmatter field into a single `Condition` whose `field` is inferred purely from `event` (`event == 'file'` → `field = 'new_text'`), with no awareness of which tool (`Edit` vs `Write`) will actually trigger the hook. `rule_engine.py`'s `_extract_field` only resolves `new_text`/`new_string` from `tool_input.get('new_string', '')`, which is empty for `Write` operations (which only populate `content`). As a result, any `block`/`warn` rule authored with the legacy `pattern:` shorthand for `event: file` never actually inspects content written via the `Write` tool, silently downgrading enforcement compared to an equivalent rule written with explicit `conditions: [{field: content, ...}]`.

### Finding Description
`Rule.from_dict` in [1](#0-0)  infers the condition's `field` from `event` alone when only a legacy `pattern:` key is present, defaulting file events to `new_text` regardless of which tool will fire the hook (`Edit`, `Write`, or `MultiEdit`).

In `rule_engine.py`, `_extract_field` resolves `field == 'new_text'` for `Write`/`Edit` tools as `tool_input.get('new_string', '')` [2](#0-1) . For the `Write` tool, `tool_input` only contains `file_path` and `content` (no `new_string`), so this lookup silently returns `''` instead of `None`. Since `_check_condition` only short-circuits when `field_value is None` (empty string still proceeds to regex/contains matching) [3](#0-2) , the condition is evaluated against an empty string and virtually never matches a real payload pattern, so the rule fails to fire — even for a `block` action.

The equivalent explicit-conditions form (`conditions: [{field: content, operator: regex_match, pattern: ...}]`) does not have this defect, because `field == 'content'` correctly reads `tool_input.get('content') or tool_input.get('new_string', '')` [4](#0-3) . This is precisely the "legacy vs explicit" parsing differential: a rule author (human, `/hookify` generation, or a repo-shipped `.claude/hookify.*.local.md` file) using the documented simple shorthand format [5](#0-4)  for `event: file` produces a rule that is enforced only against `Edit`'s `new_string`, not `Write`'s `content`, despite the README/skill docs implying `pattern:` "matches against ... new_text (file)" without disclosing this tool-specific gap [6](#0-5) .

No validation, allowlist, or workspace guard exists in `config_loader.py` or `rule_engine.py` to detect or correct this mismatch between inferred field and actual tool semantics — `load_rule_file`/`load_rules` only handle I/O/parse exceptions [7](#0-6)  and do not validate field/tool coverage.

### Impact Explanation
Any `action: block` rule created via the documented simple `pattern:` format for `event: file` (whether hand-authored, generated by `/hookify rule creation`, or shipped in a repository's `.claude/hookify.*.local.md` file) provides a false sense of protection: it will correctly block `Edit` operations but silently fail to block equivalent dangerous content written via the `Write` tool (e.g., writing secrets, malicious scripts, or files outside intended scope). This breaks the stated invariant that "default field inference must not broaden rule scope or weaken enforcement," and can result in Claude Code performing a file write that a block-rule was meant to prevent — i.e., an unauthorized file write that bypasses the user/repo-approved policy.

### Likelihood Explanation
This requires no special privilege beyond normal repository/plugin interaction: any actor able to add or influence a `.claude/hookify.*.local.md` file (via `/hookify rule creation`, `/hookify generation`, or a rule file checked into the repository) can trigger this gap simply by using the legacy `pattern:` shorthand for `event: file` rather than explicit `conditions`. Since the shorthand format is the primary documented/simplest way to write rules [8](#0-7) , this is highly likely to occur unintentionally, and can be deliberately engineered by an attacker who controls rule generation content to craft a rule that "looks like" it blocks dangerous writes but doesn't cover the `Write` tool path. The condition is deterministic and 100% reproducible.

### Recommendation
In `Rule.from_dict`, do not infer a single fixed field for `event == 'file'`; instead, either (a) generate multiple conditions covering all relevant fields for that event (`new_text`, `content`, `old_text`) combined with an OR semantic, or (b) require explicit `field:` disambiguation and reject/warn on ambiguous legacy `pattern:` rules for `event: file`. Additionally, `_extract_field` should return `None` (not `''`) when the tool-specific source key is genuinely absent, so `_check_condition` treats missing fields as non-matches consistently rather than matching against an empty string, and documentation should explicitly state that legacy `pattern:` shorthand for file events does not cover `Write`-tool content.

### Proof of Concept
Unit test (pytest style) demonstrating the differential:

```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

# Legacy shorthand rule intended to block secrets in file content
frontmatter = {
    "name": "block-api-key",
    "enabled": True,
    "event": "file",
    "pattern": "API_KEY",
    "action": "block",
}
rule = Rule.from_dict(frontmatter, "Blocked: hardcoded API key")

engine = RuleEngine()

# Case 1: Edit tool -> correctly blocked
edit_input = {
    "tool_name": "Edit",
    "tool_input": {"file_path": "a.py", "old_string": "", "new_string": "API_KEY=secret"},
}
result_edit = engine.evaluate_rules([rule], edit_input)
assert result_edit.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

# Case 2: Write tool with identical payload -> NOT blocked (bug)
write_input = {
    "tool_name": "Write",
    "tool_input": {"file_path": "b.py", "content": "API_KEY=secret"},
}
result_write = engine.evaluate_rules([rule], write_input)
assert result_write == {}  # demonstrates block rule silently bypassed for Write
```

Expected assertions: the `Edit` case returns a `deny` decision, while the `Write` case with the same sensitive content returns `{}` (no block), proving that the legacy `pattern:` field-inference weakens enforcement relative to an equivalent explicit `conditions: [{field: content, ...}]` rule, which should be added as a companion test to confirm it correctly blocks the `Write` case.
