### Title
`EnvironmentVariables#interpolate` falls back to the host process `ENV`, letting attacker-controlled step/variable strings interpolate secrets never added to the task's env - (File: `lib/shipit/environment_variables.rb`)

### Summary
`Command#interpolated_arguments` (via `Command#interpolate_environment_variables`) delegates substitution to `EnvironmentVariables#interpolate`, which resolves `${VAR}` references with `@env.fetch(variable) { ENV[variable] }`. The fallback silently reaches into the real process environment of the Shipit web/worker, not just the deliberately assembled task env (`TaskCommands#env` = `@stack.env` + task fields + `deploy_spec.machine_env` + `@task.env`). Any variable name that exists in the host's `ENV` — regardless of whether it was ever merged into the task's env — becomes interpolatable into a spawned command's argv.

### Finding Description
The intended binding, as stated in the audit target, is: every environment key eligible for interpolation into a spawned argument == a key that `TaskCommands#env` explicitly assembled for that task (`@stack.env ∪ {SHIPIT_USER, EMAIL, BUNDLE_PATH, SHIPIT_LINK, TASK_ID, IGNORED_SAFETIES, GIT_COMMITTER_*} ∪ deploy_spec.machine_env ∪ @task.env`), as seen in [1](#0-0) .

The actual implementation breaks this binding:
```
def interpolate(argument)
  return argument unless @env
  argument.gsub(/(\$\w+)/) do |variable|
    variable.sub!('$', '')
    Shellwords.escape(@env.fetch(variable) { ENV[variable] })
  end
end
``` [2](#0-1) 

`@env` here is the `env` passed into `Command.new` (the merged `TaskCommands#env`), but the fallback block reads the real, global `ENV` of the Shipit process — which is a strictly larger, uncontrolled set including whatever the deploy operator set on the host (e.g. `RAILS_MASTER_KEY`-derived secrets, `DATABASE_URL`, third-party API keys, or any `GITHUB_TOKEN`-style variable exported into the app's runtime). So `keys(@env) ⊊ keys(ENV)` in general, and the two sides of the intended equality diverge.

`Command#interpolated_arguments` is called unconditionally from `Command#start` right before `PTY.spawn`:
```
def interpolated_arguments
  interpolate_environment_variables(@args)
end

def start(&block)
  ...
  @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
``` [3](#0-2) 

Step strings themselves originate from `deploy_spec.deploy_steps!` / `dependencies_steps!`, which are read from `shipit.yml` in the checked-out repository content for that task, via `DeploySpec::FileSystem` [4](#0-3) . Given the stated precondition that a stack can be provisioned/deployed from attacker-controlled branch content (fork/PR), the attacker fully controls the argument string containing `${VAR}` syntax, and can pick `VAR` to be any name they suspect exists in the host's real process environment — not merely the whitelist `TaskCommands#env` builds. None of the existing guards (`deploy_spec.filter_deploy_envs`/`deploy_variables` allowlisting, `EnvironmentVariables#permit`) apply here, because `permit` is a separate method used only to sanitize `deploy.variables` supplied at deploy time; it is never invoked by `interpolate`, so it does not constrain which variable *names* can be resolved during argument interpolation.

### Impact Explanation
If the host process has any sensitive value set as an environment variable that is not part of the deliberately constructed task env (a very common deployment pattern — secrets, DB URLs, third-party tokens, `GITHUB_TOKEN` for the Shipit app's own GitHub App/PAT), an attacker who can get a step string executed (e.g., through `shipit.yml` in a branch/PR that gets deployed) can exfiltrate it by referencing `${THAT_NAME}` in any step argument. The secret then appears in the spawned command's argv, visible via the task's live output stream or via `ps` on the host. This matches the "Critical: exfiltration of ... deploy-time secrets" impact category, and is repeatable per task/step and, depending on how widely the guessed variable name is deployed, across any stack that shares that host environment.

### Likelihood Explanation
The attacker needs: (1) a means to get a controlled step/argument string executed as part of a task (the audit's stated precondition of stack provisioning from attacker-controlled content), and (2) knowledge or a guess of a variable name present in the host process `ENV` but not in the constructed task env. Cost is low — a single crafted `shipit.yml` step and a common secret-name guess (`DATABASE_URL`, `SECRET_KEY_BASE`, `RAILS_MASTER_KEY`, `AWS_SECRET_ACCESS_KEY`, etc.) or brute-forcing well-known variable names. No Shipit session, API token, or secret is required to author the step content itself.

### Recommendation
Remove the `ENV[variable]` fallback in `EnvironmentVariables#interpolate`; only resolve variables explicitly present in the `@env` hash passed to `Command`, and leave any unmatched `$VAR` reference untouched (or raise) instead of reaching into the process's real environment.

### Proof of Concept
In `test/unit/command_test.rb`-style minitest (conceptual, not to be placed under `test/`... but as required proof format):
```ruby
test "#interpolated_arguments leaks host ENV vars never added to the task env" do
  ENV['HOST_ONLY_SECRET'] = 'topsecret-value'
  command = Shipit::Command.new('echo', '${HOST_ONLY_SECRET}', env: {}, chdir: Dir.tmpdir)

  # LHS: intended set of interpolatable keys == keys explicitly merged into env: {}
  assert_equal({}, command.env)

  # RHS: actual resolved value pulled from the real process ENV, not command.env
  assert_includes command.interpolated_arguments, 'topsecret-value'
ensure
  ENV.delete('HOST_ONLY_SECRET')
end
```
This demonstrates that `command.env` (the intended, curated set of exposable variables) is empty, yet `interpolated_arguments` still substitutes a value sourced from the real process `ENV`, confirming the binding `keys eligible for interpolation == keys explicitly merged into task env` is broken.
