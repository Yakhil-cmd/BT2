### Title
`StatusHandler#process` updates commit status for every stack sharing a SHA, not just the stack whose repository authenticated the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no filter on repository or stack, so a single `status` webhook fans out to every `Commit` row across every stack that happens to share that SHA. Combined with `review_stacks_enabled`/`allow_all`, which auto-provisions a review stack from an attacker-controlled PR branch that shares git history (and therefore SHAs) with the target branch, a legitimately-signed status for the PR/review context is also applied to the production stack's identical commit.

### Finding Description
The broken invariant is: *a `ci/coverage` status delivered for repository R's webhook should only mutate commit state belonging to stacks tracking repository R's specific branch/context* — i.e. `status.repository.full_name == commit.stack.repository.full_name` (and ideally `== commit.stack.branch`) should hold before any `Status` row is written. It does not.

Path:
1. `Shipit::WebhooksController#create` dispatches to handlers after `verify_signature`, which only checks that the payload is validly signed for the organization named in `payload.repository.owner.login` [1](#0-0) [2](#0-1) . This proves the sender is a real GitHub webhook for that org/app installation — it says nothing about which repository or stack the `sha` in the body is allowed to affect.
2. `StatusHandler#process` then does:
   ```
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ``` [3](#0-2) 
   There is no `joins(:stack).where(stack: { repository_id: ... })` or any repository scoping at all — every `Commit` row (each `belongs_to :stack`, [4](#0-3) ) with a matching `sha` string, in any stack, is mutated.
3. `create_status_from_github!` -> `add_status` recomputes `status`, and if the simple state flips it emits `deployable_status`/`commit_status` hooks and calls `stack.schedule_merges` [5](#0-4) [6](#0-5) , directly influencing `deployable?` (`success? && !blocked?`) [7](#0-6)  and thus merge/deploy gating for whichever stack owns that Commit row — not just the stack the webhook was meant for.

Exploit flow: with `review_stacks_enabled: true, allow_all: true`, an unprivileged user opens a PR; Shipit auto-provisions a review stack tracking that branch (which shares ancestor commits — and therefore SHAs — with the target/production branch already tracked by the main stack). Any real, correctly-signed `status` webhook for the shared repository/org carrying one of those shared SHAs (e.g. triggered by the attacker's own CI run on their PR branch, or by simply pointing the PR head at an existing upstream commit) is processed by `StatusHandler` and applied identically to the `Commit` row belonging to the production stack, because `Commit.where(sha:)` cannot distinguish "this SHA as tracked by the review stack" from "this SHA as tracked by the production stack." `verify_signature`, `drop_unhandled_event`, `ExplicitParameters`, and model validations only check webhook authenticity and payload shape — none of them scope the SHA lookup to a stack/repository, so none of them stop this.

### Impact Explanation
A correctly-authenticated webhook for one stack's context can flip the `ci/coverage: success` status (and therefore `deployable?`/merge eligibility) of an unrelated stack's identical commit, including a production stack, without that stack's own CI ever reporting success. This is a write to a stack/commit record that did not itself authenticate the status, matching the "payload for one repository mutating another's stack/commit" Critical category, since it can unblock/force a deploy or merge that the target stack's own required checks never actually passed.

### Likelihood Explanation
This requires: (a) `review_stacks_enabled: true` with `allow_all: true` on the victim stack/repository so an arbitrary external PR auto-provisions a review stack, and (b) a SHA that is genuinely shared between the review-stack branch and the production branch (trivially true for any commit on the base branch that is an ancestor of the PR, or achievable by pointing the PR at an existing upstream SHA). No forged signatures or stolen secrets are required — the webhook is a legitimate GitHub-delivered event; the attacker only needs the ability to open a PR and trigger/observe a status on their own branch for a SHA that also exists in the target branch's history. This is realistic for public repositories with review stacks enabled.

### Recommendation
Scope `StatusHandler#process` (and the analogous `CheckRunHandler`, if present) to the repository that actually sent the webhook, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repository: { ...matching payload.repository... })`, or scope by `stack_id` derived from the payload's repository/branch rather than a bare SHA match across all stacks.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks, `production_stack` (repository `acme/widget`, branch `main`) and `review_stack` (repository `acme/widget`, branch `pr-123`, `review_stacks_enabled: true`, `allow_all: true`), each with its own `Commit` row for the same `sha` (e.g. `"deadbeef" * 5`), both requiring `ci/coverage`.
2. Assert precondition: `production_commit.deployable?` is `false` (pending/blocked) and `review_commit.deployable?` is `false`.
3. Build a `status` webhook payload with `sha: "deadbeef"*5, context: "ci/coverage", state: "success"` scoped (in the real payload) to the review PR context, and call `StatusHandler.new(payload).process`.
4. Assert: `production_commit.reload.deployable?` becomes `true` even though no status was ever posted against the production stack/branch context — proving the write crossed stack boundaries — while the equality `status.repository.full_name == production_commit.stack.repository.full_name` (both `"acme/widget"` in this simplified same-repo case, or mismatched in a cross-repo fork variant) shows the handler never checked this binding before writing.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
