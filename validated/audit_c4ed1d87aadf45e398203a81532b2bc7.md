**Reasoning**: The claimed divergence is not supported by the code. `poly_to_kzg_commitment` computes `out = Σ coeffs_i · G1_i` via `g1_lincomb_fast` (Pippenger) [1](#0-0)  while `g1_lincomb_naive` computes the identical sum via straightforward multiply-and-add [2](#0-1) . Elliptic-curve scalar multiplication and summation is a well-defined mathematical operation on the group: for fixed scalars and fixed points, `Σ coeffs_i · G1_i` has exactly one correct value regardless of the algorithm used to compute it (Pippenger's algorithm is purely a performance optimization producing the same multi-scalar-multiplication result as naive accumulation, both operating on the same `blst_scalar`/`blst_p1` representations). There is no code path where the choice of algorithm changes the resulting group element.

For the boundary value `BLS_MODULUS - 1`: `bytes_to_bls_field` parses the big-endian bytes with `blst_scalar_from_bendian` and rejects anything `>= BLS_MODULUS` via `blst_scalar_fr_check` [3](#0-2) . `BLS_MODULUS - 1` is the maximum valid scalar, passes this check cleanly, and is converted to an `fr_t`/`blst_scalar` with no wraparound or truncation, so `g1_lincomb_fast` receives the exact same scalar value that any reference implementation (including consensus-specs' naive approach) would use. The final serialization `bytes_from_g1` uses `blst_p1_compress`, which produces the canonical compressed encoding of the resulting G1 point regardless of how that point was computed [4](#0-3) .

Since both algorithms compute the identical mathematical value from identical, correctly-validated scalars, and serialization is canonical, `bytes_from_g1(commitment)` will match the reference `blob_to_kzg_commitment` output for this input. There is no divergence introduced by using Pippenger's algorithm versus a naive linear combination — this would only be a concern if there were an actual bug in `blst`'s Pippenger implementation, which is out of scope per the audit rules ("defects inside blst ... with no path through this repo").

void g1_lincomb_naive(g1_t *out, const g1_t *p, const fr_t *coeffs, size_t len) {
    g1_t tmp;
    *out = G1_IDENTITY;
    for (size_t i = 0; i < len; i++) {
        g1_mul(&tmp, &p[i], &coeffs[i]);
        g1_add(out, out, &tmp);
    }
}
