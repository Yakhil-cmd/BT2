Now I have found the concrete mismatch: signature verification in `verify_signature` is keyed off `repository_owner` (derived from `params.dig('repository','owner','login')` or `organization.login`), while every handler (`Handler#stacks`, `Handler#repository_name`) resolves the actual repository/stack acted upon from a completely different, independently-controlled payload field: `payload.dig('repository', 'full_name')`.

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unverified `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / HMAC secret to check using `repository_owner`, computed from `repository.owner.login` (or `organization.login`) [1](#0-0) , and validates the HMAC over the *raw* request body with that secret [2](#0-1) . However, every event handler that actually determines *which stack/repository* gets written to derives that target independently from `payload.dig('repository', 'full_name')`, a completely separate JSON field inside the same body [3](#0-2) . Nothing ties `repository.owner.login` (the field the secret-selection/signature check is anchored to) to `repository.full_name` (the field that is actually acted upon by `PushHandler`, `pull_request` handlers, etc.).

### Finding Description
Shipit supports hosting multiple GitHub organizations, each configured with its own distinct `webhook_secret` [4](#0-3) . `Shipit.github(organization: repository_owner)` looks up the app/secret for whichever organization name is present in the payload's `repository.owner.login` (or `organization.login` fallback) [5](#0-4) [1](#0-0) . The HMAC signature check only proves "this byte-for-byte body was produced/signed by the org whose secret we selected using `repository.owner.login`" — it proves nothing about which org's secret *should* have been used for the `repository.full_name` value actually consumed downstream.

`Handler#stacks` and `Handler#repository_name`, used by `PushHandler#process` and the various `pull_request/*` handlers, look up the affected `Stack`/`Repository` purely by `repository.full_name` [3](#0-2) [6](#0-5) . Nowhere is `repository.full_name`'s owner cross-checked against `repository.owner.login`/`organization.login`, i.e., the field the signature-secret-selection binds to.

This breaks the binding: `organization authenticated (repository.owner.login) == organization whose repository is written (repository.full_name)`. Concretely, an attacker who administers (or has push access to) any GitHub organization/repo that has a Shipit-configured GitHub App installed on it can generate a *genuinely GitHub-signed* webhook (e.g. via GitHub's "redeliver"/"Recent Deliveries" replay UI, or by editing and redelivering a captured webhook if GitHub allows body edits on redelivery, or simply by controlling repository metadata fields that GitHub includes verbatim) where `repository.owner.login` matches their own org (so the signature check passes using their own org's `webhook_secret`), while `repository.full_name` is set to reference a stack belonging to a *different*, victim organization/repository tracked by the same Shipit instance. Since only `full_name` is used to resolve the target `Stack`, the handler will operate on the victim stack (e.g. triggering `stack.sync_github`, updating pull request state, archiving/unarchiving review stacks) using a signature that was never computed by/for that victim organization's secret.

### Impact Explanation
This is a cross-repository/cross-organization write: an attacker who is only trusted for organization A can, using a signature that is valid for A, cause Shipit to mutate stack state that belongs to organization B (sync commits, trigger deploy-relevant github sync jobs, archive/unarchive review stacks, mutate pull request records) without ever holding B's webhook secret. This matches the "cross-repository writes" Critical impact category, since it is an unauthorized write to a repository/stack the attacker's authenticated identity (org A) was never authorized to touch.

### Likelihood Explanation
Requires the attacker to control (or have webhook-delivery/administration access to) at least one GitHub organization/repository that is configured in Shipit alongside the target victim organization, i.e. Shipit must be running in the multi-organization configuration shown in `config/secrets.development.example.yml`. It also requires a way to get GitHub to sign a payload whose `repository.full_name` differs from the org the app is actually installed on — plausible for `full_name`-only fields inside handler-controlled payloads (e.g., `pull_request` payloads deep-linking to `params.repository.full_name` used across multiple handlers) if any of those fields can be influenced without matching `repository.owner.login`. This is a real design gap; exploitability depends on the specific multi-org deployment and what payload shapes GitHub actually emits, which limits — but does not eliminate — likelihood.

### Recommendation
Bind the two identities together explicitly: derive the organization used for repository/stack resolution from the *same* verified field used to select the signature secret (`repository.owner.login` / `organization.login`), and reject (422) any webhook where `repository.full_name`'s owner segment does not match `repository_owner`. Concretely, add a check in `WebhooksController#verify_signature` (or centrally in `Handler`) asserting `payload.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with a tracked stack.
2. Obtain a webhook payload that GitHub signs with `S_A` (HMAC over raw body using `X-Hub-Signature`) where `repository.owner.login == "attacker-org"` but `repository.full_name == "victim-org/some-repo"` (e.g., via a crafted/replayed delivery where these fields can diverge).
3. POST this payload with the valid `S_A`-derived `X-Hub-Signature` to `/webhooks`.
4. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully [2](#0-1) .
5. `PushHandler#process` (or a `pull_request` handler) resolves `stacks`/`repository` via `payload.dig('repository','full_name')` = `"victim-org/some-repo"` [3](#0-2) , and mutates the victim's stack (e.g., `stack.sync_github`) despite the signature never having been computed with victim-org's secret.
