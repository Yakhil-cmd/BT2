### Title
Unbounded regex execution in hookify `_regex_match`/`compile_regex` enables ReDoS-based fail-open bypass of PreToolUse blocking rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
`RuleEngine._regex_match` compiles and executes attacker-influenced regex patterns from hookify rule files with no timeout or complexity guard, using plain `re.compile(pattern, re.IGNORECASE).search(text)`. A pathological pattern (e.g. nested quantifiers) matched against adversarial `tool_input` text causes catastrophic backtracking that hangs the `PreToolUse` hook process indefinitely, preventing the deny decision from ever being emitted.

### Finding Description
The call chain is `pretooluse.py::main()` → `load_rules()` (reads any `.claude/hookify.*.local.md` file) → `RuleEngine.evaluate_rules()` → `_rule_matches()` → `_check_condition()` → `_regex_match()` → `compile_regex()`. [1](#0-0)  shows `compile_regex` simply does `re.compile(pattern, re.IGNORECASE)` with no length limit, complexity check, or timeout, and is only guarded by an `lru_cache`, which does nothing to bound execution time of the `.search()` call. `_regex_match` at [2](#0-1)  only catches `re.error` (a compile-time syntax exception) — it has no protection against runtime catastrophic backtracking, which is not an exception but an unbounded CPU loop inside `regex.search(text)`.

The `pattern` string is fully attacker-controllable because rules are parsed straight from Markdown frontmatter of files matching `.claude/hookify.*.local.md`, as loaded in `load_rules()`/`load_rule_file()`/`Condition.from_dict()` [3](#0-2)  — the `pattern` field is taken verbatim from the YAML-like frontmatter with no sanitization, length cap, or regex-safety validation [4](#0-3) . Any actor who can add or modify such a rule file in the workspace (e.g., a rule shipped from an untrusted/synced plugin, or a rule file merged via PR) fully controls this string. The `text` operand comes from `tool_input` fields such as `command`, `new_string`, `content`, etc., extracted in `_extract_field` [5](#0-4) , which is influenced by repository content (e.g., long file contents fed through `Write`/`Edit`/`MultiEdit`).

The hook script wraps evaluation in `try/except Exception` and always exits 0 in `finally`, meaning legitimate exceptions are fail-open by design: [6](#0-5) . However, catastrophic backtracking does not raise an exception — it hangs the process before `finally` is ever reached. The exploitable outcome depends on Claude Code's own hook-timeout handling: if the hook process is killed/times out, the invariant "deny means deny" is broken because the pending `PreToolUse` blocking decision (which would have been emitted for a legitimately dangerous `Bash`/`Write` command matching a `block` rule) never gets emitted, and the tool call proceeds as if no rule matched.

### Impact Explanation
This is a denial-of-service against the hook's enforcement path: a rule intended to `block` dangerous operations (e.g., `rm -rf` detection) can be neutralized by pairing it (or any co-located/synced rule file) with an adversarial pattern/text combination that hangs regex matching, causing the PreToolUse gate to never render its "deny" decision before the surrounding tool call proceeds. Scoped impact matches "hook enforcement bypass leading to unauthorized command/file action" under Claude Code's PreToolUse deny-guarantee invariant.

### Likelihood Explanation
Requires the attacker to be able to place or modify a `.claude/hookify.*.local.md` rule file (e.g. via an untrusted plugin sync, or a merged PR touching workspace rule files) and to have some corresponding `tool_input` text reach that field during rule evaluation. Given rule files are plain, unsandboxed Markdown/YAML with no schema validation on `pattern` and no regex safety linting, crafting a classic ReDoS pattern (e.g., `(a+)+$`, `(.*)*`) is straightforward and fully reproducible.

### Recommendation
Add a hard timeout around `regex.search(text)` (e.g., using a worker thread/process with `signal.alarm` on POSIX or a `concurrent.futures` timeout), cap pattern length and input text length before matching, and consider validating patterns against a ReDoS-safety heuristic (or switching to a linear-time regex engine such as Google's `re2`) when loading rule files in `config_loader.py`. On timeout, the hook should fail closed for `block`-action rules or explicitly surface a warning rather than silently proceeding.

### Proof of Concept
Unit/fuzz test in `plugins/hookify/core/rule_engine.py` test suite:
```python
import time, pytest
from hookify.core.rule_engine import RuleEngine
from hookify.core.config_loader import Rule, Condition

def test_regex_dos_hangs():
    rule = Rule(
        name="redos", enabled=True, event="bash", action="block",
        conditions=[Condition(field="command", operator="regex_match",
                               pattern=r"(a+)+$")],
        message="should block"
    )
    engine = RuleEngine()
    payload = "a" * 40 + "!"  # no trailing match -> triggers backtracking
    start = time.time()
    result = engine.evaluate_rules([rule], {
        "tool_name": "Bash",
        "tool_input": {"command": payload}
    })
    elapsed = time.time() - start
    assert elapsed < 1.0, f"regex_match hung for {elapsed}s, ReDoS confirmed"
```
Expected today: the test times out / takes drastically longer than 1s, demonstrating unbounded backtracking; after the fix, evaluation should complete quickly or fail closed within a bounded timeout.

        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern
            text: Text to match against

        Returns:
            True if pattern matches
        """
        try:
            # Use cached compiled regex (LRU cache with max 128 patterns)
            regex = compile_regex(pattern)
            return bool(regex.search(text))

        except re.error as e:
            print(f"Invalid regex pattern '{pattern}': {e}", file=sys.stderr)
            return False

def load_rules(event: Optional[str] = None) -> List[Rule]:
    """Load all hookify rules from .claude directory.

    Args:
        event: Optional event filter ("bash", "file", "stop", etc.)

    Returns:
        List of enabled Rule objects matching the event.
    """
    rules = []

    # Find all hookify.*.local.md files
    pattern = os.path.join('.claude', 'hookify.*.local.md')
    files = glob.glob(pattern)

    for file_path in files:
        try:
            rule = load_rule_file(file_path)
            if not rule:
                continue

            # Filter by event if specified
            if event:
                if rule.event != 'all' and rule.event != event:
                    continue

            # Only include enabled rules
            if rule.enabled:
                rules.append(rule)

        except (IOError, OSError, PermissionError) as e:
            # File I/O errors - log and continue
            print(f"Warning: Failed to read {file_path}: {e}", file=sys.stderr)
            continue
        except (ValueError, KeyError, AttributeError, TypeError) as e:
            # Parsing errors - log and continue
            print(f"Warning: Failed to parse {file_path}: {e}", file=sys.stderr)
            continue
        except Exception as e:
            # Unexpected errors - log with type details
            print(f"Warning: Unexpected error loading {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
            continue

    return rules
