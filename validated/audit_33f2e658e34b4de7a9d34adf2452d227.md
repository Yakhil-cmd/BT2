### Title
Case-sensitive `action` key lookup silently downgrades intended `block` rules to `warn` - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter` preserves whatever casing appears in the YAML-like key (only whitespace is stripped, not case-normalized), and `Rule.from_dict` reads the action strictly via `frontmatter.get('action', 'warn')`. A frontmatter key written as `Action: block` (or any non-lowercase variant) is stored under the literal key `Action`, so the exact-case lookup for `action` misses and silently falls back to the default `'warn'`, even though the rule author's evident intent was to block.

### Finding Description
`extract_frontmatter` parses each top-level frontmatter line at [1](#0-0) , only calling `.strip()` on the key — no `.lower()` or case normalization is applied. Whitespace variants like `action : block` are parsed correctly because `.strip()` removes the extra spaces, but a capitalization variant like `Action: block` is stored as `frontmatter['Action'] = 'block'`.

`Rule.from_dict` then does an exact, lowercase-only lookup: [2](#0-1) . Since the dict key is `Action` (capitalized) rather than `action`, `.get('action', 'warn')` misses and defaults to `'warn'`.

Downstream, `RuleEngine.evaluate_rules` treats the rule strictly by this string: [3](#0-2) . A rule with `rule.action != 'block'` is routed into `warning_rules`, which only emits a `systemMessage` and does **not** set `permissionDecision: deny` for PreToolUse/PostToolUse events, nor `decision: block` for Stop events (compare the `blocking_rules` branch at [4](#0-3)  vs. the `warning_rules` branch at [5](#0-4) ). The operation (e.g., a dangerous `Bash` command or file edit matched by the rule's conditions) is therefore allowed to proceed, with only a warning message shown.

Full call path: `pretooluse.py:main -> load_rules -> load_rule_file -> extract_frontmatter -> Rule.from_dict` [6](#0-5) , none of which perform case normalization or reject unrecognized keys — `load_rule_file` only warns on missing frontmatter, not on unexpected/misspelled keys [7](#0-6) .

This is exploitable by any unprivileged contributor who can add or modify a `.claude/hookify.*.local.md` file in a PR: a reviewer sees `Action: block` (or `ACTION: block`) in the diff and reasonably believes the rule blocks the dangerous operation, but the rule actually only warns, so the guarded dangerous Bash/file operation still executes for anyone else running Claude Code against that repo.

### Impact Explanation
This is a silent, exploitable weakening of the hookify enforcement guarantee "deny means deny." A rule that is checked into the repo and visually appears to enforce `block` on a dangerous operation (e.g., `rm -rf`, writing to a sensitive path) is instead treated as a non-blocking warning due to a single-character casing difference in the frontmatter key. This allows a dangerous Bash/file operation to execute when the checked-in policy intended to block it — a trust-boundary/hook-bypass issue matching "approval bypass" / "unauthorized command or file action" categories, since the enforcement point that should have denied the tool call instead allows it.

### Likelihood Explanation
High feasibility and fully repeatable: it requires no special privilege beyond the ability to add/modify a `.claude/hookify.*.local.md` file in the repository (e.g., via an accepted PR), which is exactly the "unprivileged attacker who can check in repo content" scenario. The bug is deterministic — any key casing other than exactly `action` (e.g., `Action`, `ACTION`) triggers the silent fallback to `warn` every time the rule file is loaded, with no error or warning emitted by `load_rule_file`.

### Recommendation
Normalize frontmatter keys to lowercase (and strip whitespace) when building the dict in `extract_frontmatter`, or normalize keys before lookup in `Rule.from_dict`. Additionally, consider validating that `action` (once normalized) is one of the recognized values (`warn`/`block`) and emitting a hard warning/error via `load_rule_file` if an unrecognized top-level key resembling a known field (e.g., case-insensitive match to `action`) is present but not used, to avoid silently downgrading blocking intent.

### Proof of Concept
Unit test in `plugins/hookify/core/config_loader.py`'s test area or a new test file:

```python
from hookify.core.config_loader import extract_frontmatter, Rule

def test_capitalized_action_key_is_not_downgraded():
    content = """---
name: block-rm
enabled: true
event: bash
pattern: "rm -rf"
Action: block
---

Blocked!
"""
    fm, msg = extract_frontmatter(content)
    rule = Rule.from_dict(fm, msg)
    # Expected: rule.action == 'block'
    # Actual (bug): rule.action == 'warn' because frontmatter.get('action', 'warn')
    # misses the 'Action' key.
    assert rule.action == 'block'
```

Expected result today: assertion fails, `rule.action` is `'warn'`, demonstrating the operation would only be warned about, not blocked, by `RuleEngine.evaluate_rules`.
