### Title
Webhook Signature Verification Uses `repository.owner`/`organization.login` While Event Handlers Act On `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which HMAC `webhook_secret`) to verify a webhook against based on `repository.owner.login` (or `organization.login`) taken from the JSON body, while every event handler that actually mutates state (push, status, pull_request, etc.) resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, via `Handler#repository_name`. Because Shipit supports multiple independently-configured GitHub organizations (`Shipit.github_app_config`), an operator who legitimately controls one configured organization's webhook secret can forge a payload whose `owner`/`organization` fields point at their own org (so the signature check passes) while `repository.full_name` points at an entirely different, victim organization's repository. ### Finding Description
`verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` or, as a fallback, `params.dig('organization', 'login')`, and uses it to fetch the per-organization GitHub App config via `Shipit.github(organization: repository_owner)`: [4](#0-3) 

`Shipit.github` looks up a distinct config (and distinct `webhook_secret`) per organization when the multi-tenant schema is used: [5](#0-4) 

The HMAC is verified over the *entire raw payload* using that organization's secret: [6](#0-5) 

Once verification succeeds, `create` blindly dispatches the whole parsed payload to the registered handler(s) for the event, with no re-check that the org whose secret validated the request matches the repository the handler will act on: [7](#0-6) 

Handlers determine which `Stack`/`Repository` to mutate using `repository.full_name`, a field that is part of the same signed payload but is never cross-checked against `repository.owner.login`/`organization.login` used for signature routing: [3](#0-2) [8](#0-7) 

Because the HMAC covers the raw body, it does prevent tampering with a *legitimately-signed* payload from a given org's real webhook deliveries. However, it does not prevent an org owner from **originating** their own payload from scratch: since they know their own org's `webhook_secret` (it's configured for their own GitHub App installation), they can freely construct a JSON body where `repository.owner.login`/`organization.login` = `"attacker-org"` (used only for secret selection) but `repository.full_name` = `"victim-org/victim-repo"` (used by the handler to select the actual `Stack`/`Commit`/`Team`), sign it with `attacker-org`'s own secret, and submit it directly to `/webhooks`. This breaks the intended binding: *organization authenticated (whose secret validated the signature) == repository/organization actually written*.

This is functionally analogous to the reported class of "field acted upon but not covered by the binding actually validated" — here the field that gates trust (owner/organization used to pick the verifying secret) is disjoint from the field that gates the actual write (`repository.full_name`), even though both live in the same signed body.

### Impact Explanation
Handlers reachable through this path include:
- `PushHandler`, which enqueues `GithubSyncJob` against any `Stack` matching the forged `repository.full_name`/branch [9](#0-8) .
- The `status` handler, which creates a `Status` on an arbitrary commit using attacker-supplied `sha`/`state`/`target_url`, as exercised in the test suite [10](#0-9) . Since commit statuses feed the merge queue's required/blocking CI checks documented for `shipit.yml`'s `ci.require`/`ci.blocking` settings, an attacker able to forge a "success" status for a victim's PR/commit can influence Shipit's merge-queue decision to merge a commit that never actually passed CI — an unauthorized merge performed with the app's own GitHub credentials against a repository the attacker does not control.
- `PullRequest` handlers and `MembershipHandler`, which create/modify `Team`, `PullRequest`, and `ReviewStack` records scoped by `repository.full_name`/`organization.login` supplied in the same forged payload [11](#0-10) .

This qualifies under the accepted Critical impact category of "an unauthorized deploy, rollback or merge," since forged CI status could bypass merge-queue safety checks and cause the app's GitHub App credentials to merge/write to a repository/organization the attacker does not otherwise control.

### Likelihood Explanation
This requires the attacker to be a legitimate tenant of a multi-organization Shipit deployment (i.e., to know/control the `webhook_secret` for at least one configured GitHub App organization), which is a lower bar than needing GitHub write access to the victim repository itself, and does not require a Shipit session, API token, or the victim's own webhook secret. Any multi-org Shipit installation (using the `github_app_config` per-org schema) is exposed. Single-org deployments are not affected since there is only one secret/org to select from.

### Recommendation
Cross-validate that the organization used to select/verify the webhook signature (`repository.owner.login` / `organization.login`) matches the organization embedded in `repository.full_name` (and any other organization-scoped fields such as `membership`'s `organization.login`) before dispatching to handlers. Reject the webhook if these fields disagree, and additionally verify, post-signature, that the resolved `Repository`/`Stack`/`Team` actually belongs to the authenticated organization before applying any mutation.

### Proof of Concept
1. Deploy Shipit with the multi-tenant `github_app_config` schema configured for two organizations, `attacker-org` (secret known to the attacker/operator of that org's GitHub App) and `victim-org` (a separate tenant), both with stacks tracked by the same Shipit instance.
2. Craft a `status` webhook JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "target_url": "https://example.com",
  "description": "forged",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw JSON body, and set `X-Github-Event: status`.
4. POST to `/webhooks`. `verify_signature` resolves `repository_owner` = `"attacker-org"`, verifies successfully against `attacker-org`'s secret [1](#0-0) , then the status handler creates/updates a `Status` for the commit belonging to `victim-org/victim-repo`, influencing that victim stack's merge-queue CI gating.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
