### Title
Missing zero-address validation on bridge token recipient permanently burns bridged funds - (File: crates/sui-framework/packages/bridge/sources/bridge.move, crates/sui-framework/packages/bridge/sources/message.move)

### Summary
`claim_token_internal` derives the Sui recipient address directly from attacker/user-controlled bytes in the bridge message (`token_payload.token_target_address()`) with no check that the resulting address is non-zero, mirroring the exact "missing `_newValue == address(0)` check" root cause from the external report. When `claim_and_transfer_token` (callable by anyone) is invoked, the minted `Coin<T>` is transferred straight to that address via `transfer::public_transfer`, so a zero target address results in funds being sent to `@0x0` — permanently and irrecoverably locked.

### Finding Description
In `claim_token_internal`: [1](#0-0) 

the owner is computed as `address::from_bytes(token_payload.token_target_address())`, where `target_address` comes straight from BCS-decoded message bytes: [2](#0-1) 

The only validation applied to `target_address` in `extract_token_bridge_payload`/`extract_token_bridge_payload_v2` is a chain-ID check (`chain_ids::assert_valid_chain_id`) and trailing-byte check — there is **no check that the decoded address is non-zero** (analogous to the missing `_newValue == address(0)` guard in `CoverageFundAddress.set`).

After minting, `claim_and_transfer_token` — which "can be called by anyone" per its own doc comment — unconditionally transfers the coin to this unvalidated `owner`: [3](#0-2) 

If `owner == @0x0`, `transfer::public_transfer` sends the coin to the zero address. Unlike the audited `River`/`CoverageFundAddress` case (which merely skips a pull — a benign no-op), here the outcome is an irreversible transfer of newly minted bridged coins to an address nobody controls, since `claim_token` (recipient-gated) would also be unusable (`ctx.sender()` can never equal `@0x0` in a real user transaction), leaving `claim_and_transfer_token` as the only path that actually completes the mint and burns the funds by sending them to `@0x0`.

### Impact Explanation
This matches the "permanent fund lock" / "unintended permanent burning below the 10B cap" High-severity class explicitly listed as in-scope. Bridged coins minted from the treasury are permanently and unrecoverably sent to `@0x0`, destroying value that was supposed to reach a real Sui recipient. Note this operates purely on unprivileged input handling in the Move contract — no malicious validator, committee, or governance action is required.

### Likelihood Explanation
Reachability depends on whether an all-zero (or otherwise-unbound) 20/32-byte target address can end up embedded in a committee-approved bridge message. This can occur if:
- An ordinary user on the EVM side (or an ordinary Sui-side depositor for the reverse direction) supplies a zero/garbage recipient address when initiating a bridge transfer (a plausible unprivileged-user mistake or intentional "burn" attempt), and
- The committee only validates signatures/message structure, not that the target address is non-zero, before approving.

I was not able to fully confirm within the available tool budget whether the EVM-side `bridgeERC20`/`bridgeETH` functions in `bridge/evm/contracts/SuiBridge.sol` / `SuiBridgeV2.sol` themselves reject a zero `recipientAddress` before emitting the deposit event that the committee signs — I found references to these functions via `grep_search` but did not have remaining budget to read their bodies. If the EVM side already validates non-zero recipients before emitting the bridge event, this significantly reduces likelihood (the bad value could then only enter via a corrupted/malicious relay of an already-signed message, which is out of scope). This should be verified before treating the finding as fully confirmed.

### Recommendation
Add an explicit check in `claim_token_internal` (or earlier, in `extract_token_bridge_payload`/`extract_token_bridge_payload_v2`) that `owner != @0x0` (and any other framework-reserved/sentinel addresses), aborting the claim rather than silently completing a transfer to the zero address. Additionally verify and, if missing, add the same check on the EVM-side `bridgeERC20`/`bridgeETH` entry points so a zero recipient can never be embedded into a signed cross-chain message in the first place.

### Proof of Concept
Conceptual PoC (pending confirmation of EVM-side validation, per Likelihood section above):
1. An ordinary user calls the EVM `bridgeERC20`/`bridgeETH` function with `recipientAddress = 0x000...000` (or, for Sui→EVM direction analog, an ordinary Sui user calls `send_token` targeting a zero address on the Sui side, depending on which leg lacks validation).
2. The bridge committee signs the resulting `BridgeMessage` (this is routine committee operation, not a malicious action).
3. Any unprivileged caller invokes `bridge::bridge::claim_and_transfer_token<T>(bridge, clock, source_chain, bridge_seq_num, ctx)`.
4. `claim_token_internal` decodes `owner = address::from_bytes(target_address) = @0x0`, mints `Coin<T>`, and `claim_and_transfer_token` calls `transfer::public_transfer(coin, @0x0)`.
5. The minted coin is now permanently locked at `@0x0` with no path to recovery.

// This function can be called by anyone to claim and transfer the token to the recipient
// If the token has already been claimed or hits limiter currently, it will return instead of aborting.
public fun claim_and_transfer_token<T>(
    bridge: &mut Bridge,
    clock: &Clock,
    source_chain: u8,
    bridge_seq_num: u64,
    ctx: &mut TxContext,
) {
    let (token, owner) = bridge.claim_token_internal<T>(clock, source_chain, bridge_seq_num, ctx);
    if (token.is_some()) {
        transfer::public_transfer(token.destroy_some(), owner)
    } else {
        token.destroy_none();
    };
}

public fun extract_token_bridge_payload(message: &BridgeMessage): TokenTransferPayload {
    assert!(message.message_version() == 1, EInvalidMessageVersion);
    let mut bcs = bcs::new(message.payload);
    let sender_address = bcs.peel_vec_u8();
    let target_chain = bcs.peel_u8();
    let target_address = bcs.peel_vec_u8();
    let token_type = bcs.peel_u8();
    let amount = peel_u64_be(&mut bcs);

    chain_ids::assert_valid_chain_id(target_chain);

    assert!(bcs.into_remainder_bytes().is_empty(), ETrailingBytes);

    TokenTransferPayload {
        sender_address,
        target_chain,
        target_address,
        token_type,
        amount,
    }
}
