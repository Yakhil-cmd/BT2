## Finding

### Title
CCMenu API endpoint ignores API client stack scoping, allowing cross-stack disclosure of deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
Shipit supports issuing `ApiClient` tokens that are scoped to a single stack via the `stack_id` column, so a token can be limited to read-only access on one repository/environment. The `CCMenuController#show` action, however, resolves the target stack directly from the request param instead of going through the scoped `stacks` collection used everywhere else in the API, so the scoping is silently dropped for this one endpoint.

### Finding Description
`Api::BaseController` defines the authorization-scoping primitive that every other API controller relies on: [1](#0-0) 

`stacks` restricts the visible/queryable set of stacks to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to one, and `stack` (used by `CommitsController`, `TasksController`, `LocksController`, `MergeRequestsController`, `HooksController`, etc.) is built on top of that scoped collection.

`Api::CCMenuController` authenticates with the same `ApiClient` mechanism (`ApiClient.authenticate(params[:token])`) and enforces `require_permission :read, :stack`, but it overrides `stack` to bypass the scoped collection entirely: [2](#0-1) 

`check_permissions!` in `ApiClient` only checks that `"read:stack"` is present in the client's `permissions` array — it never checks which stack the token is bound to: [3](#0-2) 

That the `stack_id` scoping is a real, intended trust boundary is proven by the existing test coverage and fixtures, where a client scoped to one stack (`here_come_the_walrus`, bound to stack `shipit`) is asserted to only see that stack through the normal API: [4](#0-3) [5](#0-4) 

The binding that should hold is: `current_api_client.stack_id == requested_stack.id` (when the client is scoped). `CCMenuController#stack` breaks this equality by resolving `Stack.from_param!(params[:stack_id])` against the entire `Stack` table regardless of `current_api_client.stack_id`.

### Impact Explanation
An attacker holding any valid `ApiClient` token with the `read:stack` permission — including one an administrator deliberately scoped to a single stack for limited/low-trust integrations (e.g., a CI status badge or monitoring integration) — can query `GET /api/stacks/*stack_id/ccmenu` with an arbitrary `stack_id` belonging to a different repository/environment and receive that stack's deploy state: `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl`. This crosses a repository boundary the token was never authorized to touch, exposing deployment/build state (including whether a stack is locked/failing) for repositories the token holder should have no visibility into. This falls under unauthorized cross-scope read of stack state.

### Likelihood Explanation
Exploitation requires only possession of any valid, appropriately-permissioned (`read:stack`) API token — no elevated privileges, no session, and no knowledge beyond guessing/enumerating another stack's `owner/repo/environment` path (which is often predictable or discoverable). The scoped-token feature and the vulnerable endpoint are both part of the default engine routes (`config/routes.rb`), so any deployment that issues stack-scoped tokens is affected without any special configuration.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack from the scoped `stacks` collection (as `Api::BaseController#stack` and other controllers do), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot retrieve CCMenu data for any stack other than the one it is authorized for.

### Proof of Concept
1. As an administrator, create (or via console) an `ApiClient` with `permissions: ['read:stack']` and `stack: <stack_A>` (mirrors the `here_come_the_walrus` fixture pattern) — this token is intended to only ever see `stack_A`.
2. As the holder of that token, issue `GET /api/stacks/<stack_A-path>/ccmenu?token=<token>` — succeeds as expected, scoped correctly.
3. Issue `GET /api/stacks/<stack_B-path>/ccmenu?token=<token>` where `stack_B` is a completely different stack the token was never scoped to.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!`, the request succeeds (HTTP 200) and returns `stack_B`'s `lastBuildStatus`, `activity`, `webUrl`, etc., despite the token only being authorized for `stack_A`.
