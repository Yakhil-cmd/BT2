### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login`, but state-mutating handlers key off unrelated, unverified-binding fields (`repository.full_name`, or nothing at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of H-4: the report shows that Olympus computed a *mint/oracle price* from one code path while the *pool it actually wrote to* used a different, independently-controlled input, letting an attacker exploit the gap between "what was priced/verified" and "what actually got acted on." In `shipit-engine`, `WebhooksController#verify_signature` selects the GitHub App/organization whose secret is used to validate the HMAC signature using `repository_owner`, i.e. `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . But the code that actually mutates state per event does **not** bind its target resource to that same organization/repository at all in the `status` event, and instead re-derives the target from a completely different, independently attacker-controlled field (`repository.full_name`) in the pull-request/push/check_suite handlers.

### Finding Description
`Shipit.github(organization: repository_owner)` picks which configured GitHub App (and therefore which `webhook_secret`) is used to `verify_webhook_signature` [2](#0-1) . This binds the signature check to whichever organization login appears in the JSON body, itself part of the same body being signed.

Once the signature check passes, `WebhooksController#create` dispatches the *entire* parsed body to handlers with no further authorization or repository-scoping: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .

- For most handlers, the write target is selected via `Handler#repository_name` = `payload.dig('repository', 'full_name')` and `Handler#stacks` = `Repository.from_github_repo_name(repository_name)&.stacks` [4](#0-3) . Nothing ties `full_name` back to the `owner.login`/`organization.login` value that selected the verifying secret - they are two independent JSON fields inside the same signed body, and an attacker who can compute a valid signature for *any* configured org can freely set `full_name` to point at a different org/repo's `Stack`.
- The `status` handler is worse: it performs **no repository scoping whatsoever** - `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) . Any commit in the entire Shipit instance sharing that SHA gets a fabricated status/check-run record injected, regardless of which organization the signature was actually verified against.

**Binding that should hold, but does not:**
`organization_that_authenticated_signature == organization/repository whose Stack/Commit state is mutated`

Because these are computed from independent JSON fields inside the same HTTP body, an attacker who legitimately controls (or can obtain) a valid signature for **any one** organization/GitHub App integrated with this Shipit instance can forge a `status` (or `push`/`pull_request`) webhook body whose `repository.owner.login` matches their own org (so it passes `verify_signature`), while its `sha`/`full_name` targets a `Commit`/`Stack` belonging to a completely unrelated, victim organization tracked by the same instance.

### Impact Explanation
`Commit#deployable?` gates real deploys on `success? && !blocked?`, which is derived from `Status::Group.compact(self, statuses_and_check_runs)` fed by attacker-injected `Status` rows [6](#0-5) [7](#0-6) . By forging a "success" status against a victim repository's blocking commit SHA using only a webhook secret belonging to a different, attacker-controlled org integration, an attacker can flip `deployable?` to true and cause continuous-deployment/automatic merge/deploy logic (`schedule_continuous_delivery`, `schedule_merges`) to act on unreviewed or CI-failing code in a repository the attacker has no access to. This is a cross-repository write / unauthorized-deploy trigger, which matches the "Critical: cross-repository writes, or an unauthorized deploy" bucket.

### Likelihood Explanation
Requires only that the attacker legitimately control the webhook secret for *some* organization/GitHub App configured on the same Shipit instance (a normal, unprivileged onboarding scenario for any multi-tenant Shipit deployment) - it does not require an `ApiClient` token, a Shipit session, `api_clients_secret`, or any credential belonging to the victim organization. No cooperation from the target org is needed; only knowledge of a target `Commit` SHA (or repo `full_name`) tracked in the same shared instance.

### Recommendation
After computing the verifying organization from `repository_owner`, thread that verified organization/repository identity into the handler dispatch and require every handler (especially `StatusHandler`) to validate that the resource it is about to mutate (`Commit#stack#repository`) actually belongs to that same verified organization/repository before writing, rejecting the event otherwise.

### Proof of Concept
1. Attacker controls a GitHub App/org ("attacker-org") integrated with the target Shipit instance and knows its `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-repo commit SHA that is currently blocking deploy>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact raw body, matching the algorithm implemented in `verify_webhook_signature` [8](#0-7) .
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature [2](#0-1) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally and injects the forged "success" status onto the victim commit [5](#0-4) , with no check that this commit belongs to `attacker-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
