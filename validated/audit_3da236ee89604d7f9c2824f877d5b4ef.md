### Title
Webhook signature verification bound to `repository.owner.login` while stack resolution is bound to `repository.full_name` — allows cross-organization sync in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization config (and thus the `webhook_secret` used to validate `X-Hub-Signature`) using `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) . Downstream handlers, however, resolve the actual `Repository`/`Stack` to act on using a completely different field of the same attacker-supplied JSON body: `repository.full_name`, via `Handler#repository_name` and `Repository.from_github_repo_name` [3](#0-2) . Since `Shipit.github` supports one `GitHubApp`/`webhook_secret` per organization (`github_app_config`) [4](#0-3) , and the two lookup fields are independent JSON keys that are never cross-checked, an attacker who legitimately controls one configured organization's GitHub App (and therefore knows/can produce that org's valid webhook signature) can forge a webhook whose `repository.owner.login` names their own org (so the signature check passes) while `repository.full_name` names a different org/repo tracked by the same Shipit instance. This breaks the intended binding "organization authenticated == repository written."

### Finding Description
- `verify_signature` picks the signing config by `repository_owner`, which reads `params.dig('repository','owner','login')` (falling back to `organization.login`) [2](#0-1) , then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(signature, raw_post)` [1](#0-0) .
- `verify_webhook_signature` just HMACs the raw payload with that org's `webhook_secret` and compares to the header — it does not verify anything about which repository the payload claims to describe [5](#0-4) .
- Handlers never reuse `repository_owner`; instead each handler (e.g. `PushHandler`) resolves stacks via `Handler#stacks`, which calls `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')` [3](#0-2) .
- `PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the resolved branch [6](#0-5) .
- Shipit explicitly supports configuring "multiple Github applications for different Github organizations" in one instance, each with its own `webhook_secret`, `app_id`, `installation_id`, etc., selected by `Shipit.github(organization:)` / `github_app_config` [4](#0-3) ; this is a first-class, documented feature, not a misconfiguration of the host app.

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the target stack) are two independently attacker-controlled JSON fields in the same unauthenticated HTTP POST body, nothing enforces that they refer to the same repository/organization.

### Impact Explanation
In a multi-organization Shipit deployment, an actor who is an administrator of Org A's installed GitHub App (and therefore able to produce valid `X-Hub-Signature` values with Org A's `webhook_secret`, e.g. by triggering real events on their own repos) can craft a `push` (or other handled event) webhook where `repository.owner.login` = "org-a" but `repository.full_name` = "org-b/victim-repo". The signature check passes (Org A's secret matches), but the handler acts on Org B's stack, invoking `stack.sync_github`, which can trigger unwanted deploy-eligibility state changes (and other handlers built on the same `Handler#stacks`/`repository_name` pattern, e.g. `status`, `check_suite`, `pull_request` handlers) against a stack the attacker does not control and was never authorized against. This crosses a repository boundary using credentials scoped to a different repository — a cross-repository write concern.

### Likelihood Explanation
This requires the operator to run a multi-org Shipit configuration and for the attacker to control (or have push access triggering webhooks from) at least one of the configured organizations — a moderate bar, but one explicitly designed for and documented in this engine (`lib/shipit.rb#github_app_config`, `README`'s multi-org secrets schema). No GITHUB private key, `ApiClient` token, or Shipit session is needed; only knowledge of one org's own webhook secret, which any admin of that org's installed GitHub App legitimately possesses.

### Recommendation
After signature verification, validate that `repository.full_name`'s owner (and/or `organization.login`) matches the `repository_owner` used to select the verifying `webhook_secret`; reject the request (422) on mismatch. Alternatively, bind lookup of the target `Repository`/`Stack` to the same organization value that was cryptographically verified, rather than re-parsing an independent field from the unauthenticated body.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per the documented multi-org `secrets.yml` schema).
2. As an admin of `org-a`'s installed GitHub App, compute `sig = "sha1=" + HMAC-SHA1(org_a_webhook_secret, body)` for a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. POST to `/webhooks` with headers `X-Github-Event: push` and `X-Hub-Signature: sig`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, verifies with `org-a`'s secret, succeeds.
5. `PushHandler` resolves `repository_name` = `"org-b/victim-repo"`, finds `org-b`'s stacks, and calls `sync_github` on them despite the request never being signed by `org-b`.

Note: I could not execute this end-to-end (no test harness/terminal access in this mode), so the exploit path is derived from static code review of `WebhooksController`, `GitHubApp`, `Handler`, and `PushHandler`; a Devin session with repo access would be needed to run the fixture-based controller tests to empirically confirm the cross-org dispatch.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
