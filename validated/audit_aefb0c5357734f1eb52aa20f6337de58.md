### Title
`RuleEngine._extract_field` fails to extract `old_string`/`old_text` for `MultiEdit`, letting attackers bypass block rules by switching tools - (File: plugins/hookify/core/rule_engine.py)

### Summary
`RuleEngine._extract_field` implements per-tool field mapping so hookify rules can inspect the actual content of `Bash`, `Write`, `Edit`, and `MultiEdit` operations. The `MultiEdit` branch only extracts `file_path` and `new_text`/`content` (concatenated `new_string` values from each edit) but never extracts `old_text`/`old_string`, even though `Edit` fully supports that field. A block rule authored against `field: old_text` (or `old_string`) to catch dangerous content in the text being replaced will silently never match when the equivalent operation is performed via `MultiEdit` instead of `Edit`.

### Finding Description
`_extract_field` first checks whether `field` is a literal top-level key of `tool_input` [1](#0-0) . For `MultiEdit`, per-edit `old_string`/`new_string` values live inside a nested `edits` list, not as top-level keys, so this generic check never fires for old/new string fields with `MultiEdit`.

The tool-specific fallback then handles `Edit`/`Write` completely, including `old_text`/`old_string` [2](#0-1) , but the `MultiEdit` branch only covers `file_path` and `new_text`/`content`, omitting any `old_string` extraction path [3](#0-2) . Since no other branch handles this case, the function falls through to `return None` [4](#0-3) .

`_check_condition` treats a `None` field value as "condition not satisfied" [5](#0-4) , and `_rule_matches` requires *all* conditions to match for the rule to fire [6](#0-5) . Consequently a `block` rule whose condition targets `old_text`/`old_string` (e.g., "block edits that remove/alter a sensitive marker or secret") will never evaluate to true for `MultiEdit`, regardless of how the `tool_matcher` is configured (even `tool_matcher: "Edit|MultiEdit"` or `"*"`), because the field value itself is always `None` for that tool.

An attacker who can influence which tool Claude Code uses to perform an edit (e.g., via prompt injection, task instructions, or simply directing the agent to prefer `MultiEdit` for multi-part edits) can trivially route the exact same content mutation through `MultiEdit` instead of `Edit`, causing the hookify block rule to silently fail to fire while the destructive edit proceeds normally through `PreToolUse`/`PostToolUse` hook evaluation in `evaluate_rules`.

### Impact Explanation
This is a security-control bypass: a correctly configured hookify block rule intended to deny dangerous file edits (matching against the replaced text) is silently rendered ineffective purely due to tool selection, without any error or warning to the user. This matches the "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries" impact category, since the enforcement mechanism (hookify blocking) can be defeated by choosing an alternate, functionally equivalent tool.

### Likelihood Explanation
Feasibility is high: no privilege escalation or special access is required. Any workflow (including one influenced by prompt injection from repository content, since `MultiEdit` is a normal, commonly-used tool) that causes Claude Code to prefer `MultiEdit` over `Edit` for a matching edit will deterministically bypass an `old_text`/`old_string`-based rule. This is fully reproducible and does not depend on race conditions, timing, or unusual configuration — it's a straightforward code path gap in `_extract_field`.

### Recommendation
Extend the `MultiEdit` branch of `_extract_field` to also support `old_text`/`old_string` extraction, e.g. concatenating `old_string` values across all `edits` entries the same way `new_text`/`content` are concatenated:
```python
elif field in ['old_text', 'old_string']:
    edits = tool_input.get('edits', [])
    return ' '.join(e.get('old_string', '') for e in edits)
```
More generally, unify field extraction so that `Edit`, `Write`, and `MultiEdit` normalize to the same logical field set (`command`, `content`, `new_text`, `old_text`, `file_path`) instead of maintaining three divergent, hand-written per-tool branches, reducing the chance of future field-coverage gaps.

### Proof of Concept
Unit test to add to (or run against) `plugins/hookify/core/rule_engine.py`:
```python
from hookify.core.config_loader import Condition, Rule
from hookify.core.rule_engine import RuleEngine

def test_old_string_bypass_via_multiedit():
    rule = Rule(
        name="block-secret-removal",
        enabled=True,
        event="file",
        action="block",
        tool_matcher="Edit|MultiEdit",
        conditions=[Condition(field="old_text", operator="contains", pattern="SECRET_MARKER")],
        message="Blocked: attempt to remove protected marker"
    )
    engine = RuleEngine()

    # Case 1: Edit tool -- rule correctly blocks
    edit_input = {
        "tool_name": "Edit",
        "tool_input": {"file_path": "f.txt", "old_string": "SECRET_MARKER", "new_string": "x"}
    }
    result = engine.evaluate_rules([rule], edit_input)
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"

    # Case 2: Same dangerous edit via MultiEdit -- rule fails to block (bypass)
    multiedit_input = {
        "tool_name": "MultiEdit",
        "tool_input": {
            "file_path": "f.txt",
            "edits": [{"old_string": "SECRET_MARKER", "new_string": "x"}]
        }
    }
    result2 = engine.evaluate_rules([rule], multiedit_input)
    # Expected (fixed): should also deny; Actual (current bug): returns {} (allowed)
    assert result2.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
```
Currently, the second assertion fails because `evaluate_rules` returns `{}` for the `MultiEdit` case, demonstrating the bypass.
