## Title
Unchecked `payload` field in `handleOnlinePrivatePayment` may crash the node on a malformed private-payment justsaying — (File: network.js)

### Summary
`handleOnlinePrivatePayment()` in `network.js` accesses `arrPrivateElements[0].payload.denomination` before ever checking that `payload` exists, mirroring the Envoy OAuth bug class: code that assumes a required field is present on an attacker-controlled message and dereferences it without validation, leading to an uncaught exception that can crash the process.

### Finding Description
`handleOnlinePrivatePayment` only validates that `arrPrivateElements` is a non-empty array before immediately computing: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

There is no check that `arrPrivateElements[0]` is an object nor that it has a `payload` property before `.payload.denomination` is dereferenced. If `payload` is `undefined` (e.g. the element is `{unit: "...", message_index: 0}` with no `payload` key, or any non-object), this line throws a synchronous `TypeError: Cannot read properties of undefined (reading 'denomination')`.

This is the same bug class as the Envoy OAuth filter issue: the code path assumes a message that "looks like" the expected type (a private-payment element) will always carry a required sub-field (`state` in Envoy's case, `payload` here) and dereferences it unconditionally, instead of validating first.

Unlike the peer-to-peer `hub/deliver` handling in `network.js` (which validates `objDeviceMessage.encrypted_package...` fields defensively before use, see `network.js:3511-3517`), and unlike `private_payment.js:validateAndSavePrivatePaymentChain` (which explicitly checks `if (!headElement.payload) return callbacks.ifError(...)` before touching `.payload`, see `private_payment.js:26-28`), `handleOnlinePrivatePayment` in `network.js` skips this check entirely on the direct-peer path. [2](#0-1) 

### Impact Explanation
An uncaught synchronous `TypeError` thrown inside a message-handling callback in Node.js is not caught by the surrounding `async`/db-callback machinery here (there is no try/catch wrapping this statement), so it propagates as an uncaught exception. Depending on how the top-level request/justsaying dispatcher handles exceptions, this results in abnormal termination of the node process — a remote unauthenticated crash triggerable by any peer or hub client that can send a `private_payment` justsaying/message, causing denial of service (network unable to process further requests from that node) until manually restarted.

### Likelihood Explanation
The trigger requires only sending a malformed private-payment chain element (missing `payload`) directly to a peer or via a hub — something any private-payment counterparty (or anyone who can reach the wallet/hub protocol surface for `private_payment` justsayings) can construct trivially, without needing a valid unit, signature, or accepted joint. This matches the "unprivileged private-payment counterparty" reachability required by the rules.

### Recommendation
Add explicit validation in `handleOnlinePrivatePayment` before dereferencing `arrPrivateElements[0].payload`:
```
var objHead = arrPrivateElements[0];
if (!ValidationUtils.isNonemptyObject(objHead) || !ValidationUtils.isNonemptyObject(objHead.payload))
    return callbacks.ifError("invalid private element or payload");
var unit = objHead.unit;
var message_index = objHead.message_index;
var output_index = objHead.payload.denomination ? objHead.output_index : -1;
```
This mirrors the defensive checks already present in `private_payment.js` and should be applied consistently at the entry point in `network.js` rather than relying on downstream validation that occurs after the crash-prone line.

### Proof of Concept
Send (directly as a peer, or forwarded via a hub) a `private_payment` message whose chain array has a first element without a `payload` field, e.g.:
```
{
  "chains": [
    [
      { "unit": "SOME_VALID_LOOKING_BASE64_HASH", "message_index": 0 }
      // no "payload" key
    ]
  ]
}
```
When `network.js` dispatches this to `handleOnlinePrivatePayment(ws, arrPrivateElements, ...)`, the line
```
var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```
throws `TypeError: Cannot read properties of undefined (reading 'denomination')` before any of the array-content validation performed later in `wallet.js:handlePrivatePaymentChains` (which validates chain elements only in the hub-forwarding wrapper, not in this direct code path) has a chance to reject the malformed input.

**Note on verification limits:** I was unable to trace the exact top-level `case 'private_payment':`/justsaying dispatcher block that calls `handleOnlinePrivatePayment` in `network.js` (the surrounding switch-case text wasn't returned by search), so I cannot confirm with certainty whether an outer try/catch exists at the dispatch level that would turn this into a caught error instead of a full process crash. If a Devin session with full file access is available, this should be checked directly in `network.js` (search for `handleOnlinePrivatePayment(` call sites) to confirm whether the exception propagates uncaught to the process level.
