### Title
`roll-sbtc` in pox-5.clar Credits Staked-sBTC Accounting Without Verifying the Inner `transfer` Boolean, Allowing Inflated `total-sbtc-staked` on a Non-Reverting Transfer Response - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`pox-5.clar`'s `roll-sbtc` helper pulls sats from a staker into the contract and then unconditionally increments `total-sbtc-staked` by the same delta, relying only on `try!` to catch an `(err ...)` from the SIP-010 `transfer` call. `try!` only short-circuits on an `err` response — if `transfer` instead returns `(ok false)` (the SIP-010-legal way to signal "did not move funds" without reverting, mirroring exactly the ERC20 class of bug in the referenced report where `transfer`/`transferFrom` return `false` instead of reverting), `roll-sbtc` treats it as success and credits the staker's/protocol's stacked-sBTC ledger for sats that never left the staker's account and never arrived at the contract.

### Finding Description
`roll-sbtc` is the private helper used by `register-for-bond`/`update-bond-registration` code paths to reconcile a staker's committed sBTC when their bond membership changes: [1](#0-0) 

When `new-sbtc > old-sbtc`, the code does:
```
(try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token
    transfer delta tx-sender current-contract none
))
(var-set total-sbtc-staked (+ (var-get total-sbtc-staked) delta))
``` [2](#0-1) 

`transfer` on a SIP-010 fungible token contract returns `(response bool uint)`. Clarity's `try!` macro only aborts execution when the wrapped expression is an `err`; if the expression evaluates to `(ok false)`, `try!` unwraps it to the boolean `false` and execution *continues normally* — the `false` value is simply discarded here since it isn't asserted against. This is structurally identical to the ERC20 issue described in the report: some tokens signal a failed transfer by returning `false` rather than reverting, and code that checks only "did the call revert" (here, "did the call return `err`") rather than "did the call return `true`" will treat a failed transfer as a success.

Because `pox-5.clar`'s own use of the (out-of-scope) `sbtc-token` contract is exactly what's being examined — not the internal correctness of `sbtc-token` itself — this is in scope: the flaw is that `pox-5.clar` never asserts the boolean payload of the `(ok bool)` response before mutating `total-sbtc-staked`, `protocol-bonds-total-staked`, and staker share maps. The same unchecked-boolean pattern recurs at every other sBTC `transfer` call site in the contract (`unstake-sbtc`, `transfer-from-reserve`, `transfer-stranded-rewards`), all of which wrap the call in `try!` without asserting the inner `true`: [3](#0-2) [4](#0-3) 

### Impact Explanation
If the deployed `sbtc-token` contract ever returns `(ok false)` on a failed inbound transfer (for example, a future upgrade of the bridge token that implements a soft-fail/pause/denylist path returning `false` instead of aborting — precisely the token-compatibility gap the referenced report warns about for ERC20-style tokens), a staker calling into the `roll-sbtc` path could have `total-sbtc-staked`, `protocol-bonds-total-staked`, and their own staker-shares map incremented by `delta` sats while zero real sats were actually escrowed into the contract. This double-counts a stacking commitment that was never backed by real sBTC, inflating the staker's/signer's reward-eligible weight and the pool's accounted collateral relative to the contract's real balance — i.e., it breaks the equality between `total-sbtc-staked` and the sBTC actually custodied by the contract. Downstream reward calculations (`calculate-rewards`), unstake payouts, and reserve accounting all derive from this ledger, so the inflation could ultimately be redeemed against real reserve/other-stakers' funds.

### Likelihood Explanation
The likelihood is contingent on the deployed `sbtc-token` implementation actually returning `(ok false)` rather than `err` on a rejected transfer, which cannot be confirmed from the in-scope files since `sbtc-token` itself is out of scope. Standard Clarity `ft-transfer?`-backed implementations (as in the test stub) always return `(ok true)` or an `err`, which would make this unreachable today. However, the contract's protection against this class of bug (asserting the returned boolean) is entirely absent, so any future or alternate `sbtc-token` deployment/upgrade that follows the ERC20-style "return false, don't revert" convention would silently corrupt pox-5's internal accounting with no additional attacker action required beyond a normal `register-for-bond`/registration-update call.

### Recommendation
At every `sbtc-token`/other-SIP-010-token `transfer` call in `pox-5.clar` (`roll-sbtc`, `unstake-sbtc`, `transfer-from-reserve`, `transfer-stranded-rewards`), replace the bare `(try! (contract-call? ... transfer ...))` with an explicit assertion on the unwrapped boolean, e.g.:
```
(asserts! (try! (contract-call? 'SM3...sbtc-token transfer delta tx-sender current-contract none))
    ERR_SBTC_TRANSFER_FAILED)
```
so that a `(ok false)` result aborts the transaction instead of being silently treated as success, before any ledger mutation (`total-sbtc-staked`, `protocol-bonds-total-staked`, staker-shares maps) is committed.

### Proof of Concept
Not independently reproducible against the current in-scope stub `sbtc-token` (which always returns `(ok true)`/`err` per Clarity's `ft-transfer?` semantics, see `stackslib/src/chainstate/tests/mod.rs:110-120`). The vulnerability is a latent code-pattern defect: a minimal PoC would require substituting a token contract whose `transfer` function does `(ok false)` on a rejected transfer (e.g. `(if (>= balance amount) (ok (ft-transfer? ...)) (ok false))` instead of erring), then calling `register-for-bond`/`update-bond-registration` to trigger `roll-sbtc`'s increase branch with a staker who lacks sufficient balance — `total-sbtc-staked` would increment despite the transfer failing.
