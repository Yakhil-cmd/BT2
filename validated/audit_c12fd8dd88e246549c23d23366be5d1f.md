### Title
Unallowlisted route venues let attacker-named pool code graft a token theft onto the caller's signed auth tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The CodexBar bug class is "a credentialed request is silently forwarded to an attacker-chosen destination." The on-chain analog: `execute_strategy` and every controller strategy that embeds route bytes (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`) dispatch hops to pool addresses taken verbatim from the caller-supplied `StrategyPayload` address registry, with no allowlist. A route that names an attacker-deployed "pool" puts arbitrary contract code on the call stack underneath the victim's `require_auth` entry. That code can call `token.transfer(victim, attacker, amount)` on any token the victim holds; Soroban records it as a sub-invocation of the victim's authorization, simulation faithfully produces the poisoned tree, and a victim who signs the simulated transaction authorizes the drain. Neither the payload `min_out` check, the measured-delta accounting, nor the controller's final risk gates bound the theft, because the stolen tokens never touch the vault/router balance ledger.

### Finding Description
`dispatch_hop` in `contracts/swap-aggregator/src/venues/mod.rs` invokes `hop.pool`, an address selected by a `u8` index into the payload's `assets` registry (`program.rs` decodes `idx_a` as the pool, `MAX_ASSETS = 256`, no allowlist anywhere in `storage.rs`/`program.rs`). The venue adapters wrap the call in router invoker-auth, so the host attributes any nested `require_auth`-triggering call the pool makes to the transaction signer's auth tree. `contracts/controller/src/strategies/swap.rs::swap_tokens` passes the user's `StrategySwap` bytes straight into `router.execute_strategy`, authorizing only the input transfer — it cannot constrain what the route's pools do below the caller's own `require_auth`. The threat model states the resulting exposure plainly: "a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (`docs/explanation/threat-model.md`, lines 154–165). The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end that a rogue pool's `transfer(victim → attacker)` executes exactly when it appears as a child of the signed tree, and that the same route is refused only if the client declines to sign the poisoned tree.

### Impact Explanation
Theft of user funds: the entire wallet balance of any token the victim holds can be moved to the attacker in the same transaction that performs an otherwise honest-looking swap, bounded only by what the victim signs. The measured-output check (`ZeroOutput`, `RouterOverspend`, `NoSwapOutput`) and the post-strategy health-factor gates all pass because the theft is outside the routed amount.

### Likelihood Explanation
Medium. Exploitation requires the victim to submit a route naming the attacker's pool and to sign the auth tree simulation returns — i.e., a malicious/compromised quote or a phishing route, plus a user/wallet that does not decode the signed invocation tree. This mirrors the CVE's `UI:P` (user interaction) and `AC:H` characteristics: the on-chain contracts provide no defense; safety rests entirely on off-chain client diligence, which the protocol's own threat model delegates to "a client must decode the route it signs."

### Recommendation
Enforce a governance-managed venue/pool allowlist in the router (validate `hop.pool` against a stored set at `dispatch_hop`, or pin pool addresses per venue at config time), so route bytes can only reference vetted pool contracts. Alternatively/additionally, have `execute_strategy` restrict authorization scope — e.g., require the sender's signature to cover only the input transfer by performing the pull via a dedicated sub-call, or document and enforce at the SDK layer a hard rejection of any simulated auth tree containing children beyond `token_in.transfer(sender, router, total_in)`.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, amount)` for a wallet token unrelated to the swap; `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` shows the honest route succeeds with a root-only tree, the rogue route is refused under the honest tree, and the identical rogue route succeeds — draining `WALLET_BALANCE` to the attacker — once the simulated (poisoned) tree is signed. The source-account variant proves the grafted child executes even without a per-entry signature.
