### Title
Webhook signature is verified against the wrong organization, allowing cross-organization Stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to use for HMAC verification from an **unverified** field of the incoming JSON body (`repository.owner.login`), while the handlers that actually act on the payload resolve the target `Stack`/`Repository` from a **different** field (`repository.full_name`). Because these two fields are never cross-checked against each other, an attacker who knows the webhook secret of *any* organization onboarded to the Shipit instance can forge a webhook whose signature validates under their own org's secret but whose `repository.full_name` points at a completely different (victim) organization's repository, causing Shipit to process the forged event as if it legitimately came from GitHub for that victim repository.

### Finding Description
`WebhooksController#verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

`repository_owner` is read straight out of the still-unauthenticated JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_webhook_signature` only proves the raw body was HMAC-signed with *that particular organization's* configured secret:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Once the request passes this check, the actual JSON is dispatched to handlers (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) which resolve the target `Stack` using a **different** field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`PushHandler#process` then acts on whatever stacks match that `full_name`, e.g. enqueuing a GitHub sync for the matching branch: [5](#0-4) 

The binding that should hold is:
`organization authenticated (repository.owner.login used to pick the webhook secret) == organization of repository written (owner prefix of repository.full_name used to select the Stack)`

Nothing in `WebhooksController` or `Handler` enforces this equality. An attacker who controls (or has registered) a GitHub App/organization onboarded to the same multi-tenant Shipit instance — and therefore knows that org's `webhook_secret` in `Shipit.github(organization: ...)` config — can submit a `push`, `status`, or `check_suite` event where:
- `repository.owner.login` = attacker's own organization ("A"), so `Shipit.github(organization: "A")`'s secret is used to compute/verify the HMAC (which the attacker can do because they know secret "A"),
- `repository.full_name` = `"victim-org/victim-repo"`, so `Handler#stacks` resolves and acts on the victim's `Stack`.

The signature only ever attests "this body was sent by someone who knows org A's secret" — it says nothing about which repository the body actually targets, because `repository.full_name` is not covered by any binding to the organization whose secret validated the signature.

### Impact Explanation
This breaks the authentication boundary between organizations in a shared/multi-tenant Shipit deployment: a party with no privileges on the victim organization or repository (no Shipit session, no `ApiClient` token, no GitHub write access to the victim repo) can inject GitHub-events-as-if-they-were-real for the victim's stacks. Depending on which handler is targeted this can:
- Force `GithubSyncJob`/`RefreshCheckRunsJob` on a victim stack (`PushHandler`, `CheckSuiteHandler`),
- Forge commit statuses on a victim commit via `StatusHandler`, which can satisfy `required_statuses`/`ci.require` gating used by continuous deployment (`Stack.schedule_continuous_delivery`) or merge-queue validation (`merge_request_required_statuses` in `app/models/shipit/deploy_spec.rb`), potentially causing an **unauthorized deploy or merge** for the victim's stack.

This matches the "High"/"Critical" impact bar: escalation across an authentication boundary leading to an unauthorized deploy/merge trigger on a repository the attacker does not control.

### Likelihood Explanation
Requires the Shipit instance to host more than one organization's GitHub App/webhook config (a documented, supported configuration — `Shipit.github(organization:)` and the `GithubOrganizationUnknown` rescue path exist specifically for multi-org setups). The attacker only needs knowledge of their own organization's webhook secret (which they control/registered) and the victim's `repository.full_name` (public information) — no interaction with the victim or Shipit session is required, making this straightforward to execute for anyone administering a second onboarded organization on the same instance.

### Recommendation
After verifying the HMAC, cross-check that the organization used to select the webhook secret is actually consistent with the repository the payload claims to mutate — e.g., re-derive `repository_owner` from the same `repository.full_name` field that handlers use to resolve `Stack`/`Repository`, and reject the request (422) if they diverge, rather than trusting two independently-read fields from the same unauthenticated body as if they were bound together.

### Proof of Concept
1. Attacker registers/owns organization `A` and has it onboarded into the same Shipit instance, with its GitHub App `webhook_secret` known to them (e.g., they configured it, or it was disclosed during app setup).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": {"login": "A"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secret_A, raw_body)>` using their known secret for org `A`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "A")` (from `repository.owner.login`) and validates the signature successfully against `secret_A`.
5. `PushHandler#process` (via `Handler#stacks`/`repository_name`) resolves stacks for `"victim-org/victim-repo"` and enqueues `sync_github(expected_head_sha: params.after)` for the victim's `main` branch stack — an event the attacker had no legitimate ability to trigger.

**Uncertainty note:** I was unable to fully inspect `lib/shipit.rb`'s `Shipit.github`/multi-organization configuration resolution logic (only partial grep hits were returned, not full file contents) to confirm exactly how per-organization webhook secrets are provisioned in this instance's configuration model. This affects only the precise onboarding/config details, not the core logic flaw shown above, which is fully supported by the cited controller/handler/`github_app.rb` code.
