### Title
Webhook signature verification selects the wrong organization's secret, allowing cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to use for HMAC verification based on an attacker-controlled field inside the unverified JSON body (`repository.owner.login` / `organization.login`), not from any authenticated or fixed source. Because Shipit supports multiple GitHub App configs (one per organization, each with its own, independently-configured `webhook_secret`), and `GitHubApp#verify_webhook_signature` trivially returns `true` whenever the selected org has no `webhook_secret` configured, an attacker can choose *which* org's verification logic runs, while the rest of the forged payload (e.g. `repository.full_name`) is used unmodified by the downstream handlers to act on an arbitrary, unrelated stack/repository.

### Finding Description
The controller derives the verification target purely from payload content: [1](#0-0) 

That value is fed into `Shipit.github(organization: repository_owner)` and used to fetch the corresponding `GitHubApp` instance, whose `verify_webhook_signature` is then called: [2](#0-1) 

`verify_webhook_signature` unconditionally succeeds when the selected org has no secret configured: [3](#0-2) 

Multi-organization deployments are an explicitly supported configuration shape, where different organizations can have different (or absent) `webhook_secret` values: [4](#0-3) 

Once `verify_signature` passes (because the attacker picked an org with no secret, or one whose secret is known/guessable), `create` dispatches the *entire, unmodified* attacker payload — including any `repository.full_name`, `sha`, `ref`, etc. — to the registered handlers for that event type: [5](#0-4) 

Nothing re-validates that the `repository.owner.login`/`organization.login` used to select the verifying secret actually matches the `repository.full_name` (owner/repo) that the handler subsequently uses to locate the target `Stack`/`Repository` and act on it (create commits, update statuses, trigger `GithubSyncJob`, merge/close pull requests, etc., per `Shipit::Webhooks::DEFAULT_HANDLERS`). This breaks the trust binding: **organization authenticated ≠ repository written**. An attacker who knows of any onboarded organization without a configured `webhook_secret` (or with a leaked/guessable one) can forge events for a *different*, properly-secured organization's repository by simply setting the `owner.login`/`organization.login` field to the weak org while pointing `repository.full_name` at the victim repository.

### Impact Explanation
This is a full authentication-bypass path into the webhook subsystem, enabling forged `push`, `status`, `pull_request`, `check_suite`, `commit_status`, and `membership` events for any repository tracked by the Shipit instance — without ever knowing the victim repository's actual `webhook_secret`. Depending on the handler reached, this can lead to unauthorized commit/status injection that marks commits as "deployable" (bypassing CI gating), triggering continuous deployment (`GithubSyncJob` → deploy pipeline), or membership/team tampering — i.e., cross-repository writes and unauthorized deploys, matching the Critical impact bar.

### Likelihood Explanation
Exploitability depends entirely on the operator's configuration: a single organization in the multi-org `secrets.yml` `github` block without a `webhook_secret` (a supported and, per the fixture, real-world configuration) is sufficient to unlock signature bypass for every other organization's repositories on the same Shipit instance, because the webhooks endpoint is shared and unscoped per-org. No credentials, tokens, or repository write access are required — only knowledge (or guessing) of one org's login that lacks a secret.

### Recommendation
Bind webhook verification to a stable, pre-registered mapping (e.g., resolve the target `Stack`/`Repository` from a trusted route/lookup keyed by a value that cannot be forged, or require that the `repository.full_name` used by handlers matches the same repository/org whose secret validated the signature) instead of trusting `repository.owner.login`/`organization.login` taken from the unauthenticated request body to select which secret verifies that very same body. Additionally, disallow (or fail closed rather than fail open) verification when an organization has no `webhook_secret` configured, since `return true unless webhook_secret` silently disables signature checking for that org.

### Proof of Concept
1. Assume the Shipit instance is configured with two orgs in `secrets.yml`: `WeakOrg` (no `webhook_secret`) and `VictimOrg` (has a `webhook_secret`, owns the tracked repo `VictimOrg/app`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "WeakOrg" },
    "full_name": "VictimOrg/app"
  },
  "after": "<attacker-chosen sha>",
  ...
}
```
No valid `X-Hub-Signature` is required, or any arbitrary value works.
3. `WebhooksController#verify_signature` resolves `repository_owner == "WeakOrg"`, loads `WeakOrg`'s `GitHubApp` (no `webhook_secret`), and `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb:76-77`.
4. `create` then dispatches the full payload — with `repository.full_name == "VictimOrg/app"` — to the `push` handler, which operates on the real `VictimOrg/app` stack, e.g. enqueuing `GithubSyncJob`, exactly as if a legitimate GitHub webhook had been received for `VictimOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
