### Title
Cross-repository status forgery via unscoped sha lookup - Shipit::Webhooks::Handlers::StatusHandler#process mutating and emitting hooks for stacks it never authenticated against (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack filter, so a validly-signed `status` webhook for one repository will apply to and emit hooks for every `Stack` in the database that happens to contain a `Commit` with that same sha. Since git SHAs are content-addressed and identical shas commonly recur across unrelated forks/repositories sharing history, an attacker who legitimately owns and controls one small repository can cause `Hook.emit(:deployable_status, stack, ...)` (and `:commit_status`) to fire for a victim's `Stack` whose `Repository` never signed or authorized that webhook.

### Finding Description
The broken binding: `Stack.commit.stack.repository == the repository that produced X-Hub-Signature and populated params.repository` — this is **false** in the code.

`Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only verifies that the payload was signed by the GitHub App belonging to `repository_owner` (`params.dig('repository','owner','login')`). It does not check that the `sha` in the payload belongs to that specific repository, nor does it constrain the handler to operate solely on commits from that repository. [1](#0-0) 

`StatusHandler#process` then resolves target commits globally:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

There is no `where(stack_id: ...)` / repository match against `params.dig('repository', 'full_name')` here. `Commit#create_status_from_github!` calls `add_status`, which computes `new_status`/`previous_status` and, when the simple state changes, calls `Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))` using `stack` (the commit's actual `belongs_to :stack`), regardless of which repository actually sent the webhook. [3](#0-2) [4](#0-3) 

Exploit flow: an attacker owns/controls repository `attacker/foo` (a fork, or a repo sharing history with a victim's tracked repository, e.g. both forked from the same upstream so identical commit SHAs exist in both). The attacker pushes/updates a commit and lets GitHub (or any CI integration they control) send a legitimately-signed `status` webhook for `attacker/foo`. `verify_signature` succeeds because it only checks the signature against `attacker`'s own GitHub App/organization secret — a check the attacker can legitimately satisfy for their own repo. `StatusHandler#process` then finds *every* `Commit` row with that sha, including the victim's `Stack`'s commit (created because the victim's Stack repository shares the same git history/sha), and calls `add_status`, which emits `Hook.emit(:deployable_status, victim_stack, payload)` and can also trigger `stack.schedule_merges` for the victim stack. [5](#0-4) 

None of the existing guards prevent this: `verify_signature` binds to organization/owner, not to the specific commit's owning stack; `drop_unhandled_event` only checks event type; the `ExplicitParameters` schema in `StatusHandler` only validates shape of `sha`/`state`/etc., not repository provenance.

### Impact Explanation
A payload legitimately signed for one repository causes a database write (`statuses.replicate_from_github!`) and hook emission (`Hook.emit(:deployable_status, ...)`, `:commit_status`) scoped to a completely different tenant's `Stack`/`Repository`, and can trigger `stack.schedule_merges` for that victim stack. Any configured Hook subscriber (Slack, generic webhook) on the victim stack will receive attacker-influenced status/state data purporting to describe the victim's commit, and continuous-delivery/merge logic on the victim stack can be nudged by attacker-controlled status transitions. This is repeatable against any stack that happens to share a sha with an attacker-controlled repository (forks, shared upstream history, cherry-picked/rebased commits). This matches the explicitly listed Critical category: "a payload for one repository mutating another's stack, commit."

### Likelihood Explanation
Preconditions: victim Stack must contain a `Commit` row whose `sha` also exists in a repository the attacker controls (common for forks/shared-history repos, not merely theoretical — Shipit stacks tracking forks of the same upstream project are a realistic deployment topology). The attacker needs zero Shipit privileges — only the ability to produce a validly signed webhook for their own repository (which any GitHub repo owner can trigger via a status API call or CI integration). Cost is low and the technique is repeatable per shared-sha match.

### Recommendation
Scope `StatusHandler#process` (and any sibling handlers matching purely by sha, e.g. check-run handlers) to commits belonging to stacks whose tracked `Repository` matches `params.dig('repository', 'full_name')` (and ideally owner-org), e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_matching_payload.id })`, rejecting/ignoring commits on stacks whose repository doesn't match the webhook's named repository.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_cross_tenant_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status webhook for one repository must not emit hooks for another repository's stack" do
          shared_sha = 'a' * 40

          attacker_stack = shipit_stacks(:shipit)
          victim_stack   = shipit_stacks(:cyclimse) # different repository

          attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit')
          victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit (shares sha)')

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci',
            'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
          }

          Hook.expects(:emit).with(:deployable_status, victim_stack, anything).never
          Hook.stubs(:emit) # allow other emits (attacker stack, :commit_status) to proceed

          Shipit::Webhooks::Handlers::StatusHandler.new(payload).call

          # Binding check: victim_stack.repository must NOT equal the repository named in payload
          assert_not_equal victim_stack.repository.full_name, payload['repository']['full_name']
        end
      end
    end
  end
end
```
This asserts the binding `victim_stack.repository == payload['repository']` is false, and that `Hook.emit(:deployable_status, victim_stack, ...)` is nonetheless invoked by the unscoped `Commit.where(sha: ...)` lookup in `StatusHandler#process`, proving the cross-tenant mutation/emission.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
