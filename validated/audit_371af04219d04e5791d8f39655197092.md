### Title
Graduated liquidation curve exponent (`calc-liq-factor-exp`) truncates the fractional power, letting liquidators seize more collateral than the configured curve allows - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`calc-liq-factor-exp` is meant to raise the linear liquidation factor to a fractional power (`factor^(exponent/BPS)`) to produce a graduated liquidation curve, in the same spirit as the referenced Elo report's flawed fractional-exponent decomposition. Instead of computing the fractional power correctly, it truncates the exponent via integer division and only special-cases `exponent == BPS`, silently mis-computing the curve for every other configured exponent. This inflates `liq-pct-scaled`/`liq-penalty` compared to the intended curve, so a liquidator (attacker) calling the public liquidation entrypoint against another user's position (victim) seizes more collateral/imposes a larger penalty than the graduated-liquidation design intends.

### Finding Description
`calc-liq-factor-exp` is defined as: [1](#0-0) 

For `exp > BPS` (e.g. curve-exponent = 15000 representing 1.5), the code computes `pow(factor, exp/BPS) / pow(BPS, exp/BPS - 1)` using **integer** division `exp/BPS`. For `exp = 15000`, `exp/BPS = 1`, so the formula collapses to `factor^1 / BPS^0 = factor` — the fractional `0.5` exponent contribution is entirely discarded. Since `factor <= BPS` (i.e. `factor <= 1` in normalized terms), the mathematically correct `factor^1.5` is strictly smaller than `factor`, but the code returns `factor` unchanged, over-stating the liquidation percentage.

For `exp < BPS` (e.g. 6000, 7500, 9000 — any sub-linear curve), the code unconditionally falls back to `sqrti(factor * BPS)`, i.e. assumes exponent `0.5` regardless of the actual configured value, again deviating from the intended curve for any exponent other than exactly `5000`.

This flawed `liq-pct-scaled` feeds directly into the liquidation-bonus/penalty and debt-repay-cap calculations: [2](#0-1) 

and then into how much debt may be repaid and how much collateral is seized with bonus: [3](#0-2) 

Because `liq-pct-scaled` is over-stated whenever `curve-exponent != BPS` and `!= 5000`, `calc-liq-debt-repay` and `calc-liq-collateral-repay` allow a larger `max-debt-usd` (and correspondingly larger seized collateral with liquidator bonus) than the curve was designed to permit at the given current LTV. This is the same root-cause class as the reported Elo bug: an attempted exponent/offset decomposition that is mathematically wrong for typical inputs, silently producing a badly skewed result.

### Impact Explanation
The liquidator is an unprivileged caller acting against a borrower's (victim's) position that they do not own. With the mis-computed curve, the liquidator can seize collateral (principal + bonus) beyond what the correctly-computed graduated curve would authorize at a given LTV, i.e. a seizure exceeding its intended bound. This is a direct loss of the borrower's collateral beyond the protocol's designed liquidation curve — a theft of user funds at rest (Critical) since the excess collateral taken is not attributable to any legitimate debt-repayment ratio.

Outcome comparison:
- Without the flawed transaction: borrower's position is liquidated according to the intended graduated curve, seizing only the collateral proportional to `factor^(exponent/BPS)`.
- With the attacker's liquidation transaction: borrower loses collateral computed from the inflated `liq-pct-scaled` (effectively `factor^1` or `factor^0.5` instead of the configured curve), resulting in a larger `max-debt-usd` and thus larger seized collateral + bonus for the same position health.

### Likelihood Explanation
Likelihood is high whenever `curve-exponent` is configured to any value other than exactly `BPS` (linear, no curve) or `5000` (pure sqrt) — i.e. any genuine graduated-liquidation configuration, which is the entire point of the feature. Every liquidation call under such configuration is executed with the wrong math; no special conditions or races are needed, only a normal call to the liquidation entrypoint by any liquidator.

### Recommendation
Replace the integer-truncated power split with a proper fixed-point fractional exponentiation (e.g., using log/exp based fixed-point math or a high-precision power library) so `factor^(exponent/BPS)` is computed exactly rather than through an integer-divided decomposition that silently discards the fractional part. Add test vectors comparing `calc-liq-factor-exp` output against the mathematically exact value for a range of `curve-exponent` settings (not just the two values that happen to be handled correctly).

### Proof of Concept
1. DAO/admin configures a graduated liquidation curve with `curve-exponent = 15000` (intending `factor^1.5`) for an egroup.
2. A borrower's position crosses into the partial-liquidation LTV band with `liq-pct-linear (factor) = 8000` (0.8 in BPS terms).
3. Correct behavior: `liq-pct-scaled = 8000^1.5` (normalized) ≈ 7155 (BPS terms), a smaller liquidation percentage than linear.
4. Actual contract behavior: `calc-liq-factor-exp` computes `exp/BPS = 15000/10000 = 1` (integer division), so it returns `pow(factor,1)/pow(BPS,0) = factor = 8000` — no reduction at all, effectively linear instead of the intended sub-proportional 1.5 curve.
5. This overstated `liq-pct-scaled` is passed into `calc-liq-debt-repay` and `calc-liq-collateral-repay`, letting the liquidator repay more debt and seize a correspondingly larger amount of the borrower's collateral (plus liquidator bonus) than the curve author intended at that LTV, at the direct expense of the borrower.
