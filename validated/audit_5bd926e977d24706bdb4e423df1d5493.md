### Title
Commit/push security-review gate can be bypassed by using Git commands that create/publish commits without matching the hook's `if` matcher patterns - (File: plugins/security-guidance/hooks/hooks.json)

### Summary
The `security-guidance` plugin's automated commit/push security review is triggered only when the Bash tool's `PostToolUse` hook `if` condition matches `Bash(git commit:*)` or `Bash(git push:*)`. This is structurally identical to the RDNT bridge-fee bug class: a security-relevant side effect (fee collection / here, a mandatory security review) is enforced on the "obvious" entry point but not on alternate entry points that achieve the same underlying effect (moving tokens / here, creating or publishing a commit).

### Finding Description
`plugins/security-guidance/hooks/hooks.json` registers the review hook conditionally with string-prefix `if` matchers: [1](#0-0) 

The Python side dispatches on the same two intents via regexes `_GIT_COMMIT_RE` and `_GIT_PUSH_RE`, and explicitly documents that routing depends on the command string matching one of these two shapes: [2](#0-1) 

Because the gate is keyed to the literal substring `git commit`/`git push` in the Bash command, any way of producing a commit or publishing history that does not literally invoke `git commit`/`git push` will skip the `if` matcher entirely, so the `PostToolUse[Bash]` hook invocation is never spawned for that call (the hook only fires per registered `if`, unlike `Edit|Write|MultiEdit|NotebookEdit`, which fires unconditionally). Examples of alternate paths that create/publish commits without matching either regex: `git commit-tree`, `git commit --amend` disguised through a wrapper alias, `git -c core.hooksPath=... commit`, `git rebase --exec 'git commit ...'` chains where the literal outer command is `git rebase`, `hub`/`gh` porcelain that shells to git under a different argv0, or pushing via `git-receive-pack`/direct `curl`/API calls to a hosting provider instead of `git push`. In each case, code changes reach the remote repository (analogous to RDNT tokens crossing chains) without ever passing through the plugin's mandatory automated security review (analogous to the bridge fee).

### Impact Explanation
If the routing condition is bypassed, a commit or push containing vulnerable/malicious code is not scanned by the async security reviewer, silently defeating the "layer 2" defense-in-depth control this plugin is designed to provide (its own docstring describes the Stop hook as the last line of defense, and the commit/push hooks as an earlier, more targeted check). This is a security-tooling gap rather than a direct compromise of Claude Code itself: it does not grant new file/shell access, but it does mean a user (or an automated agent acting under instructions) can push unreviewed code while believing (from the tool's design intent) that all Bash-driven commits/pushes are reviewed.

### Likelihood Explanation
Moderate-to-low. Exploitation requires deliberately crafting an unusual git invocation (or Claude autonomously choosing an unusual git subcommand, e.g. during a rebase or amend workflow) that avoids the literal strings `git commit`/`git push`. This is plausible in ordinary git workflows (e.g., `git commit --amend`, `git push -f` via a differently-named remote helper, or scripted git operations wrapped in a shell function) without any attacker intent, making the gap likely to be hit incidentally rather than only through deliberate abuse.

### Recommendation
Broaden the routing/detection logic in `plugins/security-guidance/hooks/security_reminder_hook.py` (and the `if` matchers in `hooks.json`) beyond the literal `git commit`/`git push` prefixes:
- Match on git subcommands that create commit objects (`commit`, `commit-tree`, `commit --amend`, `cherry-pick`, `rebase`, `merge --no-ff`, `am`) and subcommands that publish refs (`push`, `push -f`, direct `git-receive-pack` invocations).
- Consider firing the review unconditionally on every `Bash` invocation (like the `Edit|Write|MultiEdit|NotebookEdit` matcher) and letting the Python-side regex decide whether to act, rather than relying solely on the coarse `if` prefix filter to short-circuit hook spawning.
- Document in the plugin's threat model which git operations are explicitly out of scope, if full coverage is not feasible.

### Proof of Concept
1. Enable the `security-guidance` plugin with `ENABLE_COMMIT_REVIEW`/`ENABLE_CODE_SECURITY_REVIEW` on.
2. Have Claude (or a user via `Bash`) introduce a vulnerable code change (e.g., a hardcoded secret or SQL injection).
3. Instead of `git commit -m "..."`, use `git commit-tree <tree> -p HEAD -m "..."` followed by updating the ref (`git update-ref refs/heads/main <new-sha>`), or use `git push` through a shell function/alias whose literal Bash command does not start with `git push` (e.g. `alias gp='git push'; gp origin main` executed as a single Bash tool call `gp origin main`).
4. Observe that neither the `if": "Bash(git commit:*)"` nor `if": "Bash(git push:*)"` matcher in `hooks.json` fires, so `security_reminder_hook.py`'s `handle_commit_review_posttooluse` / `handle_push_sweep_posttooluse` paths are never invoked for that change — the commit/push completes with no automated security review, even though the plugin is enabled and configured to review every commit/push.

**Caveat:** I could not fully verify the exact contents/behavior of `_GIT_COMMIT_RE`/`_GIT_PUSH_RE` (their precise regex definitions were not returned by the tools available), nor how Claude Code's `if` matcher engine resolves aliases/shell functions internally — the index does not contain the full file. This assessment is based on the docstring/comments explicitly describing the routing logic and the `hooks.json` `if` conditions as literal `Bash(git commit:*)` / `Bash(git push:*)` prefix matches. A Devin session with full repository access would be needed to confirm the exact regex definitions and any additional normalization applied before matching.

```python
    # Handle PostToolUse[Bash] — commit review or push sweep (asyncRewake).
    #
    # hooks.json has two `if` configs under the Bash matcher (`git commit:*`
    # and `git push:*`). CC evaluates each `if` independently and spawns this
    # script ONCE PER MATCH — so `git commit -m x && git push` spawns python
    # twice with the same command string and the same tool_use_id. The python
    # cannot tell which `if` fired it.
    #
    # Routing therefore MUST check commit FIRST so that compound commit+push
    # commands continue to hit commit-review (the pre-existing behaviour) on
    # the commit-matcher invocation. The push-matcher invocation of the SAME
    # compound command is deduped by `_claim_bash_hook_once` below: the second
    # spawn loses the tool_use_id sentinel race and exits early with
    # `bash_hook_dedup`, so commit-review runs exactly once. The alternative —
    # checking push first — would silently DROP commit-review
    # on `git commit && git push`, which is a regression.
    #
    # The push-sweep does NOT run on the compound call. That's acceptable: the
    # just-made commit is recorded by commit-review, so the next standalone
    # push sees it as reviewed and the sweep base advances past it. Older
    # unreviewed commits in the range are caught on that next push.
    if tool_name == "Bash" and hook_event_name == "PostToolUse":
        cmd = (input_data.get("tool_input") or {}).get("command", "") or ""
        if not (_GIT_COMMIT_RE.search(cmd) or _GIT_PUSH_RE.search(cmd)):
            return
        if not _claim_bash_hook_once(input_data):
            # Another spawn for this same tool_use_id already claimed the
            # work (compound matched multiple `if` configs). Emit a single
            # metric so telemetry can count how often the de-dupe kicks in.
            print(json.dumps({"metrics": {"bash_hook_dedup": True}}), flush=True)
            sys.exit(0)
        if _GIT_COMMIT_RE.search(cmd):
            handle_commit_review_posttooluse(input_data)
        elif _GIT_PUSH_RE.search(cmd):
            handle_push_sweep_posttooluse(input_data)
        return
```
