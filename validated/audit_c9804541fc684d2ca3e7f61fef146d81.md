### Title
Malicious borrower can permanently freeze `liquidate-multi` batch liquidations for unrelated victims via `unwrap-panic` on a cache-miss — (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` claims per-position isolation ("Failed liquidations return error codes but don't revert entire batch"), but it is implemented with a plain `map` over `call-liquidate`, which internally calls `liquidate`. Inside `liquidate`'s calculation path, `scale-debt-for-liquidation` unconditionally does `(unwrap-panic (get-cached-indexes asset-id))`. The index cache is only populated for assets present in the borrower's *current* debt/collateral lists at the moment `liquidate` executes (via `accrue-user-debts`/`accrue-user-collateral` over `pos-full`). A borrower can make the targeted debt asset disappear from their own position (e.g., by fully repaying it) with a transaction ordered before the batched `liquidate-multi` transaction in the same block. When their turn in the batch executes, `get-cached-indexes` returns `none` for that asset, `unwrap-panic` triggers a Clarity runtime abort — which aborts the **entire** `liquidate-multi` transaction, not just that one `map`-element response. Every other, unrelated borrower bundled in the same batch fails to be liquidated, even though their positions were legitimately unhealthy.

### Finding Description
`liquidate-multi` is documented and designed so that one bad position in the batch cannot block liquidation of the others: [1](#0-0) 

It relies on `call-liquidate`, a thin wrapper invoking the public `liquidate` function for each list entry: [2](#0-1) 

Inside `liquidate`, the cache used for oracle/index resolution is only populated for the assets present in the borrower's position *at call time*: [3](#0-2) 

Later, `scale-debt-for-liquidation` reads that cache with `unwrap-panic`, assuming a cache hit is guaranteed: [4](#0-3) [5](#0-4) 

If the asset id passed as `debt-ft` for that position is no longer part of the borrower's debt list (e.g., the borrower repaid it), `accrue-user-debts` never calls `accrue-and-cache` for that id, so `get-cached-indexes` returns `none`, and `unwrap-panic` raises a Clarity runtime error. Unlike a `(response ... err)` returned by `liquidate`, a Clarity runtime panic aborts the *whole* transaction — including the surrounding `map` in `liquidate-multi` and every other position's liquidation bundled in it — despite the code comment's claim of per-position isolation.

The shared state/mechanism here is the block-scoped `index-cache` (keyed by `{timestamp: stacks-block-time, aid}`) combined with the single-transaction batch semantics of `liquidate-multi`: one borrower's own, permissionless state change (fully repaying a debt asset) can be timed to precede the liquidator's batch transaction in the same block, corrupting the outcome for every other borrower processed in that batch.

### Impact Explanation
A malicious/self-interested borrower who is one of several unhealthy positions targeted in a single `liquidate-multi` call can, by front-running with a `repay` on the specific debt asset used in their own liquidation entry, cause the liquidator's entire batch transaction to abort. This denies liquidation to all *other*, unrelated borrowers bundled in that transaction for that block, even though those positions remain genuinely unhealthy. This is a temporary freezing of the protocol's ability to liquidate undercollateralized positions in that batch, which delays bad-debt socialization and exposes lenders to additional loss risk while the market continues to move against those positions — a temporary freezing of funds impact affecting depositors/suppliers who did not cause the underlying trigger.

### Likelihood Explanation
Any account with an open debt position that is included in a liquidator's batch can trigger this at will and at negligible cost (a single `repay` call timed before the batch tx in the same block, which is straightforward given Stacks' block/mempool visibility). No special privileges are required, and the liquidator bots that batch multiple positions together (explicitly supported and documented as `liquidate-multi`) are the natural, expected callers this would disrupt.

### Recommendation
- In `liquidate`, do not assume a cache hit; explicitly re-accrue (call `accrue-and-cache` inline, or `unwrap!`/`try!` with a graceful `ERR-*` return) instead of `unwrap-panic` in `scale-debt-for-liquidation`, `iter-price-multi`, and the other `unwrap-panic (get-cached-indexes ...)` call sites so failures surface as `(err ...)` responses rather than runtime panics.
- In `liquidate-multi`, wrap each `call-liquidate` invocation so any unexpected panic degrades to an error response for that entry only (e.g., validate the debt/collateral asset is still present in the borrower's position before calling `liquidate`, and treat "asset no longer present" as an expected, handled error rather than an unwrap-panic condition).

### Proof of Concept
1. Borrower B has an unhealthy position with debt in asset X (eligible for liquidation) and one other unrelated healthy-but-flagged asset.
2. Borrower A (an unrelated, unhealthy borrower) is bundled together with B by a liquidator bot in one `liquidate-multi([...,{borrower: A,...}, {borrower: B, debt-ft: X, ...}, ...])` transaction.
3. B observes the pending `liquidate-multi` transaction in the mempool (or simply repays proactively every block) and submits `repay` for asset X for their own account, fully clearing it, with a transaction that lands earlier in the same block.
4. When `liquidate-multi` executes, `call-liquidate` for B's entry calls `liquidate`; `pos-full` no longer contains asset X in B's debt list, so `accrue-user-debts` never caches index data for X.
5. `scale-debt-for-liquidation`'s `(unwrap-panic (get-cached-indexes debt-aid))` hits `none` and panics, aborting the entire `liquidate-multi` transaction.
6. Borrower A's legitimately unhealthy position (and any other position in the same batch) is not liquidated in that block, despite the liquidator's transaction being otherwise valid.
