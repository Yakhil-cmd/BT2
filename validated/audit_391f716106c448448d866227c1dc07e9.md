### Title
API client token minted for CCMenu status of one stack authorizes reading the CCMenu status of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The analog of the `_reCalFs` bug — using an unverified/wrong quantity (`balanceOf`) instead of the value the authorization was actually meant to be computed from (`earningOf`) — appears in Shipit's CCMenu authorization path. `CCMenuUrlController#client` mints an `ApiClient` token that is intended to authorize CCMenu access to a *single* stack (the URL is built with `stack_id: stack.to_param`), but the underlying `ApiClient` record is never bound to that stack (`stack_id` is left `nil`). `Api::CCMenuController#stack` then resolves the target stack straight from the URL param via `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client`-scoped `stacks` helper that every other API controller relies on. The result: the stack a CCMenu token is supposed to authorize (one project) diverges from the stack(s) it actually touches (every stack in the instance).

### Finding Description
`CCMenuUrlController#client` creates the token without a `stack:` association: [1](#0-0) 

`ApiClient` supports stack-scoping (`belongs_to :stack, optional: true`) and `Api::BaseController` enforces it by default: [2](#0-1) [3](#0-2) 

However, `Api::CCMenuController` overrides `stack` to resolve directly from the request parameter, never consulting `current_api_client.stack_id`: [4](#0-3) 

Because `permissions: %w[read:stack]` only checks the *name* of the permission (`ApiClient#check_permissions!`) and not which stack it was created for: [5](#0-4) 

...the `stack_id? ? Stack.where(...) : Stack.all` scoping in `BaseController#stacks` is never reached for this endpoint, and even if it were, the CCMenu client's `stack_id` is always `nil` so it would resolve to `Stack.all` anyway.

Equality that should hold but is broken:
`stack the token authorizes` (the single stack for which the CCMenu URL/token was generated) `== stack the token touches` (whatever `stack_id` is supplied in the request to `Api::CCMenuController#show`).

### Impact Explanation
Any user who legitimately generates a CCMenu URL for one stack they can view (via `CCMenuUrlController#fetch`, gated only by normal session auth and `read:stack` on that one stack) receives a token that, due to the missing stack binding and the controller's bypass of scoping, can be replayed against `GET /api/stacks/:any_stack_id/ccmenu.xml?token=...` for **any** stack on the instance — including stacks belonging to teams/repositories the user has no authorization to view. This discloses build/deploy status (`lastBuildStatus`, `lastBuildLabel`, activity, lock state) for stacks outside the user's authorized scope, matching the High-impact category of "unauthenticated/unauthorized read of stack state."

### Likelihood Explanation
Likelihood is high for any authenticated Shipit user (even one with access to only a single, low-sensitivity stack): they only need to use the normal, documented CCMenu feature once to obtain a token, then substitute a different `stack_id` in the URL. No secrets, sessions of other users, GitHub credentials, or elevated API-client scopes are required — only the engine's own token-issuance and controller logic are misused.

### Recommendation
- Bind the `ApiClient` created in `CCMenuUrlController#client` to the specific stack: `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, scoping `find_or_create_by!` on `stack` too so distinct stacks get distinct scoped clients.
- Fix `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that any stack-scoped `ApiClient` (CCMenu or otherwise) cannot read stacks outside its `stack_id`.

### Proof of Concept
1. User Alice (member of Team-A, can view Stack-A only) visits Stack-A's page and triggers the CCMenu URL fetch: `GET /stacks/stack-a/ccmenu_url` → receives `https://shipit/api/stacks/stack-a/ccmenu.xml?token=<TOKEN>`. [6](#0-5) 
2. Alice replaces the stack id in the URL: `GET /api/stacks/stack-b/ccmenu.xml?token=<TOKEN>`, where Stack-B belongs to Team-B (Alice has no access).
3. `Api::CCMenuController#authenticate_api_client` accepts `<TOKEN>` (valid `read:stack` permission), and `#stack` resolves `Stack-B` directly via `Stack.from_param!`, ignoring that `<TOKEN>`'s `ApiClient.stack_id` (nil, and even if set, unchecked here) has nothing to do with Stack-B. [7](#0-6) 
4. Response 200 with Stack-B's CI/build status XML is returned to Alice, disclosing state of a stack outside her authorization.
