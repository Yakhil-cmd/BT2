### Title
Integer Overflow in Fixed-Denomination Asset Cap Validation Allows Supply Inflation — ([File: validation.js])

### Summary
`validateAssetDefinition()` computes the declared cap of a fixed-denomination asset by summing `count_coins * denomination` for each denomination entry supplied by the asset issuer, using unchecked native JavaScript number multiplication. Because `isPositiveInteger()` only verifies the value is a finite positive integer with no upper bound, an attacker-controlled `count_coins` can be arbitrarily large, causing the product (and the running total) to exceed `Number.MAX_SAFE_INTEGER` (2^53). This is directly analogous to the ALPINE-CVE-2018-7643 bug class: an integer-overflow in code that parses/validates a length/count field from untrusted input, producing an incorrect computed value that bypasses a downstream sanity check.

### Finding Description
In `validateAssetDefinition()`, the denominations loop is: [1](#0-0) 

Key issue:
- `denomInfo.denomination` is checked with `isPositiveInteger` and, only under certain MCI conditions, capped at `constants.MAX_CAP`: [2](#0-1) 
- `denomInfo.count_coins` is checked only with `isPositiveInteger(denomInfo.count_coins)`, which places **no upper bound** at all: [3](#0-2) 
- The multiplication `denomInfo.count_coins * denomInfo.denomination` accumulates into `total_cap_from_denominations` using plain JS floating-point arithmetic: [4](#0-3) 
- The final consistency check compares this potentially-overflowed sum against the attacker-supplied `payload.cap`: [5](#0-4) 

Since `count_coins` has no cap, an attacker can choose values (e.g., `denomination = 1`, `count_coins = 2^60`) such that the product silently loses precision once it crosses `Number.MAX_SAFE_INTEGER`. By crafting multiple denomination entries, an attacker can make `total_cap_from_denominations` (a lossy floating-point value) equal an arbitrary `payload.cap` of their choosing, even though the true mathematical sum of `count_coins * denomination` across all denominations does not actually equal that cap. This passes the `payload.cap !== total_cap_from_denominations` check with a false sense of integrity.

Downstream, per-denomination coin issuance is tracked and limited via the `asset_denominations` table (`count_coins`, `max_issued_serial_number`) in `indivisible_asset.js`, e.g. in `issueNextCoin()`: [6](#0-5) . Each denomination's `count_coins` independently gates issuance for that denomination, so an inflated/mismatched `count_coins` on any single denomination record directly permits total issuable supply for that denomination (and thus the asset) to diverge from the publicly declared `cap`, without the discrepancy being caught by validation at definition time.

### Impact Explanation
This breaks the invariant that `cap` accurately reflects the maximum issuable supply of a fixed-denomination asset — the same integrity guarantee that `cap` validation exists to enforce (see `MAX_CAP` bound and cap-vs-denominations reconciliation logic in `validateAssetDefinition`). An asset issuer can define an asset whose true issuable supply (via `count_coins` per denomination) is inconsistent with (larger than) the value nodes and downstream consumers believe is the cap, resulting in fraudulent asset over-issuance / supply inflation without triggering the "cap doesn't match sum of denominations" rejection. This satisfies the "supply inflation" impact criterion.

### Likelihood Explanation
Any unprivileged unit poster can issue this crafted "asset" definition message directly in a normal unit — this code path is exercised on every unit containing an `asset` message with `fixed_denominations: true` and a `denominations` array, requiring no special privileges, hub trust, or network position. The only requirement is knowledge of `Number.MAX_SAFE_INTEGER` overflow behavior in JavaScript, which is a well-known bug class (matching the analog CVE's "crafted input triggers integer overflow in size/length computation" pattern).

### Recommendation
- Bound `count_coins` similarly to `denomination` and `cap` (e.g., require `count_coins <= constants.MAX_CAP` and `count_coins * denomination <= constants.MAX_CAP`).
- Perform the multiplication and summation using an overflow-safe method (e.g., `BigInt`, or explicit range checks before/after each multiplication) rather than native floating point, and reject if any intermediate product or the running total exceeds `Number.MAX_SAFE_INTEGER` or `constants.MAX_CAP`.
- Ensure the MAX_CAP bound on `denomination` at line 2771 is unconditional rather than gated behind an MCI/hasBall condition, to avoid pre-upgrade or light-client bypass windows.

### Proof of Concept
1. Attacker composes and posts a unit with an `asset` message:
```json
{
  "fixed_denominations": true,
  "is_private": false,
  "is_transferrable": true,
  "auto_destroy": false,
  "issued_by_definer_only": true,
  "cosigned_by_definer": false,
  "spender_attested": false,
  "cap": <attacker chosen small/misleading value X>,
  "denominations": [
     { "denomination": 1, "count_coins": <N1 chosen so N1*1 plus other terms overflow float precision and sum lossily equals X> },
     { "denomination": D2, "count_coins": <N2 large> }
  ]
}
```
2. Choose `count_coins` values so that the true sum `Σ(count_coins_i * denomination_i)` is astronomically larger than the true issuable amount implied by `X`, but due to floating-point addition in `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` (validation.js:2778), the computed JS `Number` result rounds to exactly `X`.
3. `validateAssetDefinition` passes because `total_cap_from_denominations === payload.cap` at line 2790 (floating point equality after precision loss).
4. The asset is accepted network-wide with `count_coins` per denomination in `asset_denominations` far exceeding what the declared `cap` implies.
5. The issuer (or definer) later calls `issueNextCoin()` in `indivisible_asset.js`, which allows issuing coins up to each denomination's actual (uncapped-by-check) `count_coins`, producing total issued supply greater than the publicly advertised `cap` — supply inflation.

Note: exact numeric values that trigger the precision collision were not computed/verified in this analysis (would require constructing specific floating-point rounding cases against the concrete `constants.MAX_CAP` value); the structural flaw — an unbounded `count_coins` multiplied into a floating-point accumulator that is later compared for exact equality against an attacker-supplied `cap` — is verified directly from the cited code.
