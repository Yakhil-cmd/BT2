### Title
`StatusHandler#process` writes commit status by bare SHA with no repository check, letting a `ci/lint` failure from one repo flip state on another stack's commit and trigger `merge!` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` and never compares the webhook's `repository.full_name`/`repository_owner` against the commit's actual stack/repository. Any accepted `status` webhook therefore mutates the status of **every** `Commit` record sharing that SHA across all stacks in the installation, and because `Commit#create_status_from_github!` schedules merges on success/pending transitions, this can drive `merge_queue_enabled` stacks to advance or stall independent of the repository that legitimately produced the event.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository.full_name == params.dig('repository', 'full_name')`, but this equality is never checked.

Path:
1. `Shipit::WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event('status')`, guarded only by `verify_signature`, which checks the HMAC using `Shipit.github(organization: repository_owner)` [1](#0-0) . This proves the payload came from GitHub for the claimed `repository_owner` **organization**, not that it came from the specific repository whose SHA is referenced.
2. `StatusHandler#process` then runs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across the `commits` table and is not scoped to a stack/repository, unlike, e.g., `PushHandler#process`, which at least scopes to `stacks.where(branch:)` [3](#0-2) .
3. `Commit#create_status_from_github!` calls `add_status`, which reloads the commit's aggregate `status`, emits `commit_status`/`deployable_status` hooks, and — critically — calls `stack.schedule_merges if new_status.pending? || new_status.success?` [4](#0-3) . A `failure` transition instead can flip a previously-green head to red, blocking `merge_queue_enabled` progress for that stack.
4. `MergeRequest` reuses `stack.commits.by_sha` when reconciling GitHub state, confirming commits are looked up by bare SHA within a stack rather than being tied to the webhook's repository at write time [5](#0-4) .

Root cause: SHA collisions across stacks are not a hash-collision concern — they occur naturally whenever two Shipit-tracked repositories share commit history (forks, mirrors, subtree merges, or an org where the GitHub App is installed across multiple repositories). Because the org-level webhook secret (`verify_webhook_signature` in `lib/shipit/github_app.rb`, keyed by `organization`, not by `repository`) is the only authentication boundary, any repository within that org — including a fork the attacker owns — can emit a validly-signed `status` event for a SHA that is also present, as an ancestor or shared commit, in a victim stack tracking a different repository in the same org. `StatusHandler` has no additional repository check to reject cross-repository writes, so the guard the invariant relies on ("`ci/lint` status affects only the repository that authenticated it") is absent in this handler.

None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, model validations) address this: `verify_signature` only proves org-level authenticity, and the params schema only validates types (`sha`, `state`, `context` as strings) [6](#0-5) , not repository identity.

### Impact Explanation
An attacker who can push to any repository within a Shipit-monitored GitHub organization (including their own fork sharing ancestor commits with a victim repository) can send a genuine `status` webhook (`context: ci/lint`, `state: failure` or `success`) for a SHA that also exists as a tracked commit in an unrelated victim stack. `StatusHandler` writes this status to that victim commit regardless of which repository authenticated the event, and `add_status` triggers `stack.schedule_merges`, which can force or block merge-queue progression (`merge_queue_enabled` stacks) and affect deployability computation for a repository the attacker never authenticated for. This matches "a payload for one repository mutating another's stack/commit" and can enable unauthorized ship/block of merge-queue processing — Critical severity per the rubric.

### Likelihood Explanation
Exploitation requires: (1) Shipit configured with a GitHub App/webhook secret shared at the organization level (a common, arguably default configuration for `Shipit.github(organization:)`), (2) the attacker having push/fork access to some repository within that org (a low bar — many orgs allow internal forking or have multiple lightly-permissioned repos), and (3) a SHA collision, which is trivial to obtain via a fork sharing history with the victim repository (ancestor commits are byte-identical and share SHA by construction) or by any repository importing/cherry-picking a known public commit. No secrets, tokens, or elevated GitHub roles are required beyond ordinary contributor/fork access. The attack is repeatable against any SHA the attacker can reproduce or discover in the victim's history.

### Recommendation
In `StatusHandler#process`, restrict the update to commits whose stack's repository matches the webhook's `repository.full_name`/`repository_owner` (e.g., join through `stack.repository` and filter, mirroring how `PushHandler` scopes to `stacks`). Do not rely solely on SHA equality across the whole `commits` table; always verify repository identity before writing GitHub-sourced state (statuses, check runs) onto a `Commit`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for a SHA shared by another repository does not flip an unrelated stack" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, requires "ci/lint"
  shared_sha = shipit_commits(:first).sha
  victim_commit = shipit_commits(:first)
  assert_not_equal victim_stack.repository.full_name, "attacker/other-repo"

  # Attacker-authenticated payload for a different repository, same SHA
  params = ActionController::Parameters.new(
    sha: shared_sha,
    state: "failure",
    context: "ci/lint",
    repository: { full_name: "attacker/other-repo", owner: { login: "attacker" } }
  )

  before_state = victim_commit.reload.state

  Shipit::Webhooks::Handlers::StatusHandler.new.call(params.to_unsafe_h)

  after_state = victim_commit.reload.state

  # Binding under test: repository.full_name authenticated == repository that owns the mutated commit
  refute_equal "attacker/other-repo", victim_stack.repository.full_name
  assert_equal before_state, after_state, "status from an unrelated repository must not mutate victim stack's commit"
end
```
This demonstrates that, absent a repository check, `StatusHandler#process` (and transitively `Commit#create_status_from_github!` / `stack.schedule_merges`) would apply a status write and merge-queue side effect for a commit belonging to a stack that never authenticated the webhook.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
