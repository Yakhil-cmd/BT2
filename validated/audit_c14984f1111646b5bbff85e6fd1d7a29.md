### Title
Webhook signature is verified against `repository.owner.login` while the affected repository/stack is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret used to authenticate the inbound webhook based on `repository.owner.login` (or `organization.login`) taken straight from the unauthenticated JSON body, but every event handler resolves the `Repository`/`Stack` that is actually mutated using `repository.full_name`, a *different* field of that same unauthenticated body. In a multi-organization Shipit configuration, these two fields are never checked for consistency, so a valid HMAC computed with one organization's `webhook_secret` can be attached to a payload whose `full_name` points at a completely different organization's repository.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is read directly from the request body: [2](#0-1) 

`Shipit.github(organization:)` uses that attacker-supplied string to select which per-organization config (and therefore which `webhook_secret`) is used to verify the HMAC: [3](#0-2) 

Meanwhile, every handler resolves the actual `Repository`/`Stack` to act on from a *different* field of the same JSON body, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

Because `verify_webhook_signature` also trivially returns `true` when the selected organization's `webhook_secret` is blank/unset: [6](#0-5) 

an attacker who controls (or is a member of) *any* organization configured in Shipit — including one deliberately left with no `webhook_secret` — can craft a JSON payload where:
- `repository.owner.login` (or `organization.login`) = the attacker's own low-trust organization (whose secret is known/blank, so `verify_signature` passes), while
- `repository.full_name` = `"victim-org/victim-repo"` (or any other organization's repository already tracked by Shipit).

The binding that should hold is:
`organization whose signature authenticated the request == organization owning the repository that gets written`,
but the code only enforces `organization whose signature authenticated the request == params.dig('repository','owner','login')`, a value that is never cross-checked against `params.dig('repository','full_name')` used downstream. Before the PR/attack the two fields always originate from the same real GitHub org and are consistent; after a forged request they can be made to diverge, since neither is covered by the same server-side derivation nor bound to each other by the signature.

### Impact Explanation
This allows an unprivileged holder of a signature for one configured GitHub organization to make Shipit believe pushes/statuses/PR events happened for a totally different organization's repository, without ever holding that organization's `webhook_secret`. Depending on the event this can:
- Force `PushHandler` to enqueue `GithubSyncJob` for an arbitrary tracked stack with an attacker-chosen `expected_head_sha`, influencing sync/retry behavior for that stack.
- Feed forged commit statuses into `StatusHandler`/`Status` model for another org's commit, without any actual access to that org.
- Trigger PR-related state transitions (archive/unarchive review stacks, capture labels) for repositories the attacker has no legitimate relationship with.

This crosses the "organization that authenticated versus the repository that is written" trust boundary named in the rules, and can result in cross-repository writes and unauthorized state changes to another organization's deployment pipeline, which is an unprivileged-attacker forgery against organizations the attacker doesn't control.

### Likelihood Explanation
Exploitability requires Shipit to be configured with the multi-organization GitHub schema (`Shipit.github_organizations` with per-org configs) and at least one organization the attacker has legitimate access to (their own GitHub org integrated into the same Shipit instance) or one org configured with a blank `webhook_secret`. Given this is a documented, supported configuration mode (see `github_app_config`/`TOP_LEVEL_GH_KEYS` handling), this is a realistic deployment for larger installations serving multiple orgs from one Shipit instance.

### Recommendation
- After selecting the GitHub App/secret via `repository_owner` and verifying the signature, re-derive/normalize the organization actually associated with `repository.full_name` and reject the request (422) if the two do not match.
- Prefer deriving `repository_owner` from the same canonical field (`full_name`'s owner segment) used by `Handler#repository_name`, rather than `repository.owner.login`/`organization.login`, so there is a single unambiguous source of truth for organization scoping.
- Require `webhook_secret` to be present for every configured organization (fail closed) rather than allowing verification to pass by default when blank.

### Proof of Concept
Assume Shipit is configured with two organizations, `attacker-org` (attacker is a legitimate member and controls its GitHub App / webhook secret is blank/known) and `victim-org` (repository `victim-org/victim-repo` is tracked with an active `master` branch stack).

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes a valid `X-Hub-Signature` using `attacker-org`'s (known/blank) `webhook_secret`.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `attacker-org`'s secret [1](#0-0) .
4. `PushHandler#process` is invoked with the same payload, resolves `repository_name` from `repository.full_name` = `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stack [7](#0-6)  — despite the request never being authenticated by `victim-org`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
