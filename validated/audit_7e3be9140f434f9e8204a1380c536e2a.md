### Title
Global contract owner can front-run "users" by silently swapping `AccountId`-referenced contract code before their pending calls execute - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
NEP-591's "global contracts" feature lets an account deploy a contract with `GlobalContractDeployMode::AccountId`, after which any other account can attach to it via `UseGlobalContractAction{contract_identifier: AccountId(owner)}` and permanently borrow that owner's code as its own executable logic. The code that actually runs for every "consumer" account is resolved dynamically, on every function call, by looking up the *current* code hash stored under the owner's account id — not a hash pinned at `UseGlobalContract` time. This is structurally the same trust/architecture problem as the MetaSwap adapter bug: users delegate execution of their calls to code controlled by a third party (the global-contract owner), and that owner can redeploy the logic referenced by `AccountId` at any time, effectively swapping the implementation underneath pending calls with no lock, timelock, or versioning commitment.

### Finding Description
When an account deploys with `GlobalContractDeployMode::AccountId`, the contract is referenced by the owner's `AccountId` rather than by an immutable code hash: [1](#0-0) 

A consumer opts in via `UseGlobalContractAction`, which stores `AccountContract::GlobalByAccount(owner_id)` on its own account — it does not pin the code hash that was active at the time of opting in: [2](#0-1) 

Every time any consumer account executes a `FunctionCall`, the runtime resolves the contract to run by re-reading the owner's current global contract code hash from the trie at that moment: [3](#0-2) [4](#0-3) 

This resolution happens fresh for each receipt as it is applied in `apply_action_receipt`: [5](#0-4) 

The owner can redeploy new code under `AccountId` mode at any time via `action_deploy_global_contract` / `initiate_distribution`, which immediately updates the trie entry for that identifier on the deploying shard and starts distributing it to other shards: [6](#0-5) [7](#0-6) 

There is no cool-down, timelock, or opt-in versioning: a redeploy transaction that lands in the same or an earlier chunk than a consumer's pending `FunctionCall` receipt will change the code that receipt executes against, because `RuntimeContractIdentifier::resolve` always reads the latest state for `GlobalContractIdentifier::AccountId`. The only anti-replay mechanism is a monotonic nonce guarding against *stale* distribution receipts overwriting newer ones — it does nothing to prevent the owner from intentionally redeploying malicious code ahead of a specific victim transaction: [8](#0-7) 

This directly mirrors the MetaSwap root cause: any code consumers delegate to (there, adapters called via `DELEGATECALL`; here, contracts referenced via `GlobalByAccount`) can be swapped by its owner at will, so every consumer account implicitly trusts the owner not to maliciously redeploy right before/around their transaction — exactly the front-running/trust assumption the external report flags as a vulnerability class.

### Impact Explanation
Any application built on the "global contract by account id" primitive (e.g., a shared library, wallet, proxy, or protocol contract that many user accounts reference so they don't each need to store the code) is vulnerable to a malicious or compromised owner front-running consumer calls: the owner observes an incoming transaction/receipt targeting a consumer account that uses their global contract (e.g., a call carrying an attached deposit intended to be handled by trusted logic), and deploys new code that alters behavior (e.g., diverting attached deposits, forging balances, or otherwise behaving maliciously) before that call is applied. Because the change takes effect for every consumer account referencing that `AccountId` simultaneously and without their explicit re-consent, this can lead to unauthorized state/balance changes and theft of funds attached to affected function calls — the same "steal from users" outcome described in the original report.

### Likelihood Explanation
This requires only a standard (non-validator, non-privileged) account that has deployed a global contract under `AccountId` mode and has at least one other account referencing it via `UseGlobalContract`. No special network position or validator status is needed — any account owner controlling a popular `GlobalByAccount` contract can redeploy at will using an ordinary `DeployGlobalContractAction` transaction, and the change takes effect for all dependents on the owner's own timing. The likelihood of exploitation scales with adoption of the `AccountId` deploy mode for shared/trusted logic.

### Recommendation
- Treat `AccountId`-mode global contracts the same way the report recommends for adapters: pin the code hash a consumer account is using at `UseGlobalContract` time (i.e., resolve and store the concrete code hash rather than a live, owner-mutable `AccountId` reference), requiring an explicit new `UseGlobalContract` action from the consumer to adopt a newer version.
- Alternatively/additionally, require a delay (timelock) between `DeployGlobalContractAction` (AccountId mode) and the new code becoming effective for existing consumers, and/or emit an explicit, queryable "pending update" so consumers/relayers can react before code changes take effect.
- Document prominently that `GlobalContractDeployMode::AccountId` grants the deploying account full run-time control over the logic of every account that references it, and that this control is not diminished by prior `UseGlobalContract` calls.

### Proof of Concept
1. Owner account `O` deploys benign-looking global contract `C1` with `DeployGlobalContractAction{deploy_mode: AccountId}` (see `action_deploy_global_contract` in `runtime/runtime/src/global_contracts.rs`).
2. Victim account `V` opts in with `UseGlobalContractAction{contract_identifier: AccountId(O)}` (`action_use_global_contract`), setting `V.contract = AccountContract::GlobalByAccount(O)`.
3. `V` sends/receives a `FunctionCall` receipt that, under `C1`'s logic, is expected to safely handle an attached deposit (analogous to a user's swap in the MetaSwap scenario).
4. Before that receipt is applied, `O` submits a new `DeployGlobalContractAction{deploy_mode: AccountId}` transaction with malicious code `C2` (e.g., a method with the same name that instead transfers the deposit to `O`). Because `initiate_distribution` updates the trie for the current shard immediately, and `RuntimeContractIdentifier::resolve` re-reads the code hash for `AccountId(O)` fresh at the moment `V`'s `FunctionCall` is applied (`runtime/runtime/src/lib.rs` and `runtime/runtime/src/contract_code.rs`), `V`'s pending call now executes against `C2` instead of `C1`.
5. `V`'s attached deposit is redirected per `C2`'s logic, without `V` having re-consented to the new code — reproducing the "owner front-runs users by swapping the implementation" scenario from the original report.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract);
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
