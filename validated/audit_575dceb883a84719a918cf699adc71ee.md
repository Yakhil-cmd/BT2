### Title
Webhook signature verified against `repository.owner.login`/`organization.login`, but events are applied to the repository named in `repository.full_name` — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) to validate a webhook against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. Every webhook handler, however, resolves the target `Stack`/`Repository` using a completely different field of the same payload: `payload.dig('repository', 'full_name')`. Since both fields are attacker-controlled in the raw JSON body of an unauthenticated POST to `/webhooks`, nothing forces `repository.full_name`'s organization to match `repository.owner.login`/`organization.login`.

### Finding Description
`verify_signature` picks the GitHub App config to validate against solely from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up per-organization webhook secrets, as documented for multi-org installs: [3](#0-2) 

Signature verification itself only checks the HMAC of the raw body against that one organization's secret: [4](#0-3) 

Once verification passes, `WebhooksController#create` dispatches the entire raw payload to handlers without re-checking that `repository.owner.login` matches `repository.full_name`'s owner: [5](#0-4) 

Every handler resolves its target repository/stack from `repository.full_name`, a field never covered by the org selected for signature verification: [6](#0-5) 

For example `PushHandler` triggers a resync of any stack matching that `full_name`+branch: [7](#0-6) 

This is exactly the "organization that authenticated versus the repository that is written" binding break: the equality the code implicitly (and incorrectly) assumes is
`org(repository.owner.login or organization.login) == org(repository.full_name)`,
but nothing enforces it. In a Shipit deployment configured for multiple GitHub organizations (as `docs/setup.md`/`config/secrets.*.yml` explicitly support), anyone who knows/controls the webhook secret for organization A (e.g., an admin of a low-trust org A onboarded onto the shared Shipit instance) can craft a request with `repository.owner.login: "orgA"` (satisfying signature verification with orgA's secret) while setting `repository.full_name: "orgB/some-repo"` — a repository belonging to a completely different, unrelated organization B whose secret they never had. The forged event is then processed as if it legitimately came from GitHub for org B's repository.

### Impact Explanation
This lets an entity trusted only for organization A forge `push`, `status`, and `check_suite` events for stacks belonging to any other organization B configured on the same Shipit instance:
- `status`/`check_suite` handlers can inject fake CI results (`Status`/`CheckRun` records), which can satisfy `ci.require` gating used by the merge queue and deploy checklist — a path toward an unauthorized deploy/merge of unreviewed code.
- `push` events trigger `GithubSyncJob`, causing the app to fetch/act on attacker-chosen commit SHAs for org B's stacks using the app's own GitHub credentials, effectively an authorization boundary crossing between organizations that Shipit is supposed to keep isolated via per-org secrets.

This matches the High/Critical bar: escalation into cross-organization control of stack state and CI gating that can enable an unauthorized deploy.

### Likelihood Explanation
Requires only that the Shipit instance is configured with multiple GitHub organizations (a documented, supported configuration) and that the attacker holds legitimate access to just one of those organizations' webhook secret/App settings — no access to Shipit itself, no `ApiClient` token, and no privileges in the victim organization are needed. This is a realistic multi-tenant misconfiguration risk rather than a purely theoretical one, given the engine explicitly documents and ships example configs for multi-org secrets.

### Recommendation
After `verify_signature` succeeds, re-derive the organization strictly from the same field used for verification and require that `repository.full_name`'s owner segment match `repository_owner` (or resolve the App/secret to check from the `Repository`/`Stack` actually targeted by `full_name`, not from an independently attacker-controlled field) before dispatching to any handler.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations, `orgA` and `orgB`, each with its own `webhook_secret`.
2. As an entity with access only to `orgA`'s GitHub App webhook secret, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/production-app"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches orgA's app/secret, and the signature check passes (attacker signed with the secret they know). [1](#0-0) 
5. `PushHandler#process` resolves the target repository via `payload.dig('repository', 'full_name')` = `"orgB/production-app"`, and synchronizes that stack, even though the request was never authenticated by orgB's secret. [8](#0-7)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
