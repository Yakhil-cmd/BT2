### Title
Unguarded Return-Data Copy in `handleKLAYTransfer` Permanently Locks Bridged KAIA — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` uses a Solidity 0.5.x low-level call `(bool ok, ) = _to.call.value(_value)("")` to deliver bridged KAIA to the recipient. Even though the return bytes are syntactically discarded, the Solidity 0.5.x compiler still emits `returndatasize` / `returndatacopy` instructions that copy the entire return blob into memory. A malicious or buggy recipient contract that returns a large blob will exhaust the 1/64 gas retained by the caller after the inner call, causing an out-of-gas revert. Because the entire transaction reverts, the bridge nonce for that request is never consumed, and the KAIA locked in the bridge can never be delivered to that address — permanently freezing those bridged funds.

---

### Finding Description

In `BridgeTransferKLAY.sol` at line 98:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
```

Solidity 0.5.x compiles `(bool ok, ) = addr.call.value(v)("")` by:
1. Executing the `CALL` opcode, forwarding 63/64 of remaining gas.
2. After the call returns, unconditionally executing `RETURNDATACOPY` to copy the callee's return data into memory — regardless of whether the Solidity code uses the bytes value.

If `_to` is a contract whose fallback function returns (or reverts with) a large blob, the memory-expansion cost of copying that blob exceeds the 1/64 gas retained by the caller, causing an OOG revert in `handleKLAYTransfer`.

Because all state mutations in `handleKLAYTransfer` (nonce update, tx-hash marking, `handleNoncesToBlockNums` entry) occur **before** the call and are rolled back on revert, the bridge operators can retry — but every retry against the same `_to` address will OOG in exactly the same way. The KAIA is permanently undeliverable to that address.

The same pattern appears in `BridgeFee._payKLAYFeeAndRefundChange` (lines 49 and 54), but those callee addresses (`feeReceiver`, `msg.sender`) are either owner-controlled or self-inflicted, so the primary exploitable path is through `handleKLAYTransfer`.

---

### Impact Explanation

A user on the source chain bridges KAIA to a destination address that is a contract returning a large blob. The source-chain KAIA is already locked/burned. On the destination bridge:

- Every operator call to `handleKLAYTransfer` for that nonce reverts with OOG.
- `lowerHandleNonce` cannot advance past the stuck nonce (the `_updateHandleNonce` loop stops where `handleNoncesToBlockNums[i] == 0`).
- The KAIA held by the bridge for that transfer is permanently frozen — it cannot be delivered, and there is no admin escape hatch to skip a nonce or redirect the funds.

**Broken invariant**: Every successfully requested KLAY bridge transfer must eventually be deliverable on the counterpart chain. Here, a user-controlled destination address can make delivery permanently impossible, locking bridged KAIA in the contract.

---

### Likelihood Explanation

- Any user who bridges KAIA to a contract address whose fallback/receive returns a large payload (maliciously or accidentally — e.g., a proxy that bubbles up a large revert string) triggers this.
- No special privilege is required; the attacker only needs to initiate a bridge request on the source chain with `_to` set to such a contract.
- The bridge operators have no on-chain mechanism to override the destination address or skip the stuck nonce.

---

### Recommendation

Replace the high-level return-data-copying call with an assembly block that ignores return data entirely:

```solidity
// In handleKLAYTransfer and _payKLAYFeeAndRefundChange
bool ok;
assembly {
    ok := call(gas(), _to, _value, 0, 0, 0, 0)
}
require(ok, "handleKLAYTransfer: transfer failed");
```

Using `call(gas(), addr, value, 0, 0, 0, 0)` with output offset and size both set to 0 instructs the EVM to discard return data without copying it, eliminating the memory-expansion OOG vector.

### Proof of Concept

**Malicious recipient contract (deploy on destination chain):**
```solidity
pragma solidity 0.5.6;
contract MaliciousReceiver {
    // fallback: returns 1 MB of data, exhausting caller's retained gas
    function() external payable {
        assembly {
            return(0, 1000000)  // return 1 MB blob
        }
    }
}
```

**Attack steps:**
1. Deploy `MaliciousReceiver` at address `M` on the destination chain.
2. On the source chain, call `requestKLAYTransfer(M, value, extraData)` with any KAIA amount.
3. Bridge operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(..., M, value, nonce, ...)` on the destination bridge.
4. The inner `_to.call.value(_value)("")` forwards 63/64 gas to `M`; `M` returns 1 MB, consuming all forwarded gas.
5. The caller's retained 1/64 gas is insufficient to `RETURNDATACOPY` 1 MB; the transaction reverts with OOG.
6. All retries by operators produce identical OOG reverts.
7. The KAIA (`value`) remains locked in the bridge contract at `BridgeTransferKLAY` with no delivery path.
