### Title
Unfunded `repay` overpayment refund drains pool custody - ([File: contracts/pool/src/ops/repay.rs](contracts/pool/src/ops/repay.rs))

### Summary
The Optimism Portal bug class is: a resource-sufficiency check is evaluated against a declared budget before an intermediate operation consumes part of it, so the downstream transfer receives more (or the forwarded call less) than the checked amount implied. In the pool's `repay` leg the same shape exists with tokens instead of gas: the overpayment refund is computed from the *declared* `action.amount` — assumed to have been prefunded — while the actual intermediate step (the debt burn, i.e. the "SSTORE" that consumes the buffer) may consume zero. The refund is then paid out of the pool's real token custody rather than out of funds just received, so the "call" is funded by other users' liquidity.

### Finding Description
`ops::repay::apply` runs `accounting`, which resolves `amount` into `(burned, overpayment)` via `cache.resolve_repay(amount, position)`, then unconditionally transfers `overpayment` to `payer`:

```rust
// contracts/pool/src/ops/repay.rs
let (burned, overpayment) = cache.resolve_repay(amount, position);
let net_repay = amount.checked_sub(overpayment)...;
assert_with_error!(env, net_repay == 0 || burned.raw() > 0, RepayRoundsToZeroShares);
...
outcome.cache.transfer_out(payer, outcome.overpayment);
```

When the position carries no debt (scaled position is zero, or debt was already repaid), `resolve_repay` treats the entire declared `amount` as overpayment: `net_repay == 0` satisfies the assert, nothing is burned, no cash is credited, and `transfer_out` sends `amount` from pool custody to `payer`. Neither the refund nor `debit_cash` accounts for it — the refund is drawn purely from physical token balance. The repo's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3590-3610) demonstrates that calling `repay` with `amount = custody` on a debt-free market pays the full custody balance to `payer` with `actual_amount == 0`. The sibling comment (flows.rs:3578-3588) documents that neither `recapitalize` nor `repay` refunds debit `cash` or pass `require_reserves`.

The controller normally prefunds the pool with a measured transfer before invoking `repay`, so routed flows are safe. But the pool's `repay` entrypoint itself trusts that `amount` arrived; it never measures `balance(pool)` before/after to confirm receipts cover the refund — the same missing "recompute the buffer after the intermediate spend" mistake as the portal.

### Impact Explanation
If `repay` is reachable without the controller's prefunding step (the unit test invokes the pool client directly with an arbitrary `payer`), any unprivileged address can declare an `amount` equal to the pool's token balance on any market with no outstanding debt on the referenced position and receive the entire custody balance as an "overpayment refund". That is direct theft of suppliers' funds, since the refunded tokens back other users' supply shares while `cash` bookkeeping is unchanged.

### Likelihood Explanation
No special timing, price movement, or privileged role is required — a single call with a crafted `PoolAction` whose `scaled_amount` resolves to zero debt suffices wherever the function is externally invocable. If deployment wiring restricts pool `repay` to the controller only, the reachable variant narrows to any controller path that fails to prefund (none currently do), which would reduce this to a latent invariant violation.

### Recommendation
- Measure the pool's actual receipts for the leg and cap the refund at the measured inbound amount, e.g. snapshot `balance(pool)` before and require `refund <= received_delta`, or require the controller to pass a `funded_amount` it measured via `transfer_amount_measured`.
- Debit the refund against `cash` or gate it behind `require_reserves`, so an unfunded refund cannot pay out of backing liquidity.
- Apply the same fix to `ops::recapitalize::apply`'s `refund` branch, which shares the identical pattern.

### Proof of Concept
Existing in-repo demonstration: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs` calls `client().repay(&payer, &ract(0, custody_before))` on a market with `borrowed == 0` and `cash == custody`, then asserts `actual_amount == 0` and that the payer's balance increased by `custody_before` while the book (`cash`, `supplied`, `borrowed`) is untouched — i.e., the full pool balance was refunded against zero delivered funds.

Note: I was unable to fully verify the authorization surface of the pool contract's `repay` entrypoint within the available iterations; if it is hard-restricted to the controller, the finding's direct-attack path depends on that gate.
