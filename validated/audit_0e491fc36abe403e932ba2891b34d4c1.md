### Title
Webhook signature is verified against the organization in `repository.owner.login`, but events are applied to the stack resolved from the unbound `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to check the `X-Hub-Signature` against based on `repository.owner.login` (or `organization.login`) taken from the raw JSON payload, but every `Shipit::Webhooks::Handlers::Handler` subclass resolves the `Repository`/`Stack` that actually gets written to using a *different* payload field, `repository.full_name`. In a multi-organization Shipit install where at least one configured GitHub App has no `webhook_secret` (a state the shipped config templates explicitly support), an attacker can send a forged webhook whose `repository.owner.login` names the unsecured org (so signature verification is skipped) while `repository.full_name` names a repository belonging to a *different*, secured organization. The handler layer never re-checks that the authenticated org matches the org that owns the acted-upon repository.

### Finding Description
Signature verification and org selection: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The per-org secret check itself is a no-op when no secret is configured: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

`webhook_secret: # nil` is a documented, shipped default for multiple orgs, including in the dummy app's multi-org test config: [4](#0-3) 

Meanwhile, every handler resolves the target `Repository`/`Stack` purely from `repository.full_name`, a completely separate field of the same untrusted JSON body: [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

The same pattern repeats in the pull-request handlers, which resolve `repository` via `params.repository.full_name` independently of whatever org gated the signature check: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret authenticated the request == organization that owns repository.full_name`. Nothing in `WebhooksController` or `Handler` enforces this equality; the two fields are read independently from the same attacker-controlled JSON body, and only one of them (`repository.owner.login`) participates in signature selection.

### Impact Explanation
This maps to the Critical "cross-repository writes" impact category. Concretely:
- `StatusHandler#process` creates a `CommitStatus` for any commit matching `params.sha` on any stack, using attacker-supplied `state`, `context`, `description`, `target_url`: [8](#0-7)  This can be used to spoof CI green/red state on a stack in the secured organization, which factors into `ci.require`/`Commit#deployable?` gating used for continuous deployment and the merge queue.
- `PushHandler#process` enqueues `GithubSyncJob` for the target stack: [9](#0-8) 
- `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` create, archive, or unarchive review stacks and update PR state on the resolved repository, entirely driven by `repository.full_name`.

All of these operations are scoped to whatever repository the attacker names in `repository.full_name`, independent of which org's (possibly unsecured) secret satisfied `verify_signature`.

### Likelihood Explanation
Exploitation requires: (1) a multi-org Shipit deployment (explicitly supported and documented, e.g. `test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`), and (2) at least one configured org left with `webhook_secret` unset — the shipped default in every example config (`webhook_secret: # nil`). Given that default, the attacker needs no secret knowledge at all: they only need to know the name of any onboarded-but-unsecured organization and the `owner/name` of a target repository belonging to a different, secured organization on the same Shipit instance. No session, API token, or GitHub credential is required — the `/webhooks` endpoint is unauthenticated by design (only signature-gated).

### Recommendation
Bind the two identifiers before trusting the payload: after signature verification succeeds, require that the organization used to select the `github_app`/secret (`repository_owner`) matches the owner segment of every `repository.full_name` a handler will act on, or simpler — always verify the signature using the app configured for the owner of `repository.full_name` (never trust a separate `organization.login` fallback that can diverge from the repository actually targeted), and reject the webhook if that owner has no `webhook_secret` configured while any other configured org's stacks could be reached by the same payload. At minimum, log/reject when `repository.owner.login` (or `organization.login`) does not match the owner parsed from `repository.full_name`.

### Proof of Concept
Preconditions: Shipit configured with two orgs, `secured-org` (has `webhook_secret` set) owning stack `secured-org/prod-app`, and `open-org` (no `webhook_secret` configured, per documented default).

1. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or an arbitrary one):
```json
{
  "sha": "<sha of a commit on secured-org/prod-app>",
  "state": "success",
  "context": "ci/circleci",
  "repository": {
    "full_name": "secured-org/prod-app",
    "owner": { "login": "open-org" }
  }
}
```
2. `verify_signature` computes `repository_owner` = `"open-org"`, looks up `Shipit.github(organization: "open-org")`, and calls `verify_webhook_signature`, which returns `true` unconditionally because `open-org` has no `webhook_secret`: [10](#0-9) 
3. `StatusHandler` then runs and creates a fabricated `success` status on the commit belonging to `secured-org/prod-app`, resolved purely via `payload.dig('repository', 'full_name')`, satisfying `ci.require` checks and enabling continuous deployment/merge-queue progression on a stack the attacker never had credentials for.
