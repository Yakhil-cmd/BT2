### Title
Webhook signature is verified against a GitHub org selected from an unsigned field, while event handlers route to a *different* unsigned field to pick the repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to verify the HMAC against by reading `repository.owner.login` straight out of the still-unauthenticated JSON body. All downstream event handlers, however, resolve the target `Repository`/`Stack` using a *different* field of that same unauthenticated body: `repository.full_name`. Because the field used to select the verification key and the field used to select the object mutated are not the same, and neither is bound to the other by the signature, an attacker who legitimately controls one GitHub organization/App configured on a shared Shipit instance can forge a payload whose `owner.login` matches their own org (so the signature check passes with their own known secret) while `full_name` points at a repository belonging to a different org hosted on the same instance.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` selects the signing organization from the raw request body before any cryptographic check: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and `Shipit.github(organization: repository_owner)` looks up that organization's `webhook_secret` to verify `X-Hub-Signature` against `request.raw_post`. Shipit explicitly supports multiple GitHub Apps/organizations configured on one instance, each with its own independent `webhook_secret`: [3](#0-2) 

Once the signature is accepted, `WebhooksController#create` hands the *entire unverified JSON body* to the event handlers: [4](#0-3) 

Every handler resolves the target repository from a *different* field of that body — `repository.full_name` — via `Handler#repository_name`: [5](#0-4) 

For example `PushHandler` uses `stacks` (built from `repository_name`) to find and sync stacks: [6](#0-5) 

and the pull-request handlers similarly look up `Repository.from_github_repo_name(params.repository.full_name)` to archive/unarchive or provision review stacks: [7](#0-6) 

**The binding that is broken:** `organization authenticated by signature (repository.owner.login)` ≠ `repository actually written to (repository.full_name)`. Nothing ties these two fields together, and both live in the same attacker-controlled JSON body that the signature covers as raw bytes but whose *semantic* fields are never cross-checked against each other. This is the same class of bug as TRST-M-7: the check ("is this signed by an org we trust") is performed against one representation of the subject, while the privileged action is performed against a different, unverified representation of the "same" subject supplied in the same request.

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), any actor who is a legitimate admin/installer of *one* onboarded organization's GitHub App (and thus knows that org's `webhook_secret`, which they configure themselves in GitHub's app settings) can craft a webhook body with:
- `repository.owner.login` = their own organization (so `verify_signature` selects their own known `webhook_secret` and the HMAC passes), and
- `repository.full_name` = `victim-org/victim-repo` (a repository belonging to a different, unrelated org hosted on the same shared instance).

This lets them drive `PushHandler` to force `GithubSyncJob`/`stack.sync_github` against the victim's stack, drive `StatusHandler` to inject fabricated commit statuses on the victim's commits, or drive the pull-request handlers to archive/unarchive or auto-provision review stacks for the victim's repository — actions that should only be reachable by someone whose signature was actually issued for that org/repo. This is a cross-organization/cross-repository write achieved purely by owning a different, unrelated GitHub App installation on the same Shipit instance, which is the "unauthorized deploy/write across repository boundary" impact class.

### Likelihood Explanation
Requires only that the target Shipit deployment services more than one GitHub organization (explicitly documented/supported: `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), and that the attacker is a legitimate installer/admin of one of those onboarded orgs (i.e., they know their own org's `webhook_secret`, which is normal and expected for any org owner). No GitHub App private key, Shipit session, or API token for the victim org is needed — only the ability to send a raw HTTP POST to `/webhooks` with a body they sign themselves.

### Recommendation
Bind signature verification to the same identity used for routing: verify the signature using the org/App whose repository is actually referenced by `repository.full_name` (or, better, resolve the target `Repository`/`Stack` first from `full_name`, then verify the signature using that repository's associated App/organization secret), and reject the payload if `repository.owner.login` does not match the owner implied by `repository.full_name`. Consider also validating that a resolved `Repository` record's configured GitHub App/org matches the one whose secret validated the signature before invoking any handler.

### Proof of Concept
1. Configure/observe that Shipit instance `S` has two organizations onboarded: `attacker-org` (attacker is the GitHub App admin, knows `webhook_secret_A`) and `victim-org` (hosts `victim-org/victim-repo`, tracked as a Shipit stack).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, e.g. an old/malicious commit already in victim history>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` using their own known secret for `attacker-org`.
4. `POST /webhooks` with header `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` (from `repository.owner.login`) and validates successfully against the attacker's own secret.
5. `PushHandler.call(params)` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` (from `repository.full_name`) and enqueues `GithubSyncJob`/`stack.sync_github(expected_head_sha: ...)` against the victim's stack — an action the attacker was never authorized to trigger, using only their own org's webhook secret.
