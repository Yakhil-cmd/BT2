## Analysis

The reported bug class ("a generic value-transfer function silently fails / reverts for a class of non-standard tokens, permanently locking them") maps to an analogous flaw in how Autonomous Agents (AAs) build outgoing payment messages in `aa_composer.js`.

### Title
AA outgoing payments for private or fixed-denomination assets are silently dropped or unconditionally bounced, permanently locking non-standard assets held by an AA - (File: `aa_composer.js`)

### Summary
When an AA's `messages` template includes a `payment` message paying out an asset (not `base`), `sendUnit()` looks up the asset's properties and treats two asset classes specially: private assets and fixed-denomination (indivisible) assets. Both classes can never actually be paid out by an AA, yet the AA logic (state changes, balance accounting) proceeds as if the payment were valid, so funds of these asset types can become unrecoverable once held by an AA.

### Finding Description
Inside `handleTrigger`'s `sendUnit()`, each payment message for a non-base asset is checked against its `objAsset` properties: [1](#0-0) 

- If `objAsset.fixed_denominations` is true, the code simply calls `cb()` with the comment "will skip it later" — it never calls `completePaymentPayload`, never attaches inputs, and never completes the message. After the `eachSeries` loop, such messages are unconditionally filtered out of the outgoing unit: [2](#0-1) 

  If this filtering empties the message list, the AA quietly finishes with `handleSuccessfulEmptyResponseUnit(null)` — i.e., the trigger is processed as "successful" even though the intended asset payment never happened.

- If `objAsset.is_private` is true, the code returns `cb("sending private asset from AA")`, which propagates as an error and forces the *entire* trigger to bounce via `bounce(err)`: [3](#0-2) 

Critically, by the time `sendUnit()` runs, `evaluateAA()` has already executed the AA's `init`/`state` formulas (balance bookkeeping, state-variable updates, etc.): [4](#0-3) 

For the fixed-denominations case, this means the AA's internal state (e.g., a `var['balance_'||asset]` accounting variable) is decremented/updated as though the asset was paid out, but the payment message carrying that asset is dropped before the unit is finalized — the asset never leaves the AA. Any subsequent attempt to withdraw is now blocked by the AA's own state bookkeeping (which believes the balance is zero), while the actual asset units remain stuck in the AA's control forever, exactly like non-conforming ERC20 tokens stuck in a contract whose `recoverERC20`/`safeTransfer`-style function cannot process them.

For private assets, the entire trigger unconditionally bounces (`"sending private asset from AA"`), meaning an AA can *never* forward, refund, or sweep a private asset sent to it — any private-asset payment routed through an AA (e.g., a generic escrow/exchange/vault AA per the `test/samples/*.oscript` patterns that accept `trigger.output[[asset!=base]]`) is permanently unspendable from that AA.

### Impact Explanation
Any AA designed to hold, forward, refund, or exchange assets on behalf of users (a common and expected AA pattern, as shown in the sample oscripts `order_book_exchange.oscript`, `a_bank_without_percent.oscript`, `sell_asset_for_bytes.oscript`) will permanently lose access to any private asset or fixed-denomination (indivisible) asset sent to it once the AA attempts to pay it back out. This is a fund-freezing / fund-loss condition reachable by any unprivileged unit poster who simply sends such an asset to the AA's address, matching the "AA fund loss or freezing" impact category.

### Likelihood Explanation
The trigger conditions require no special privilege: any user can send a private asset or a fixed-denomination asset as a normal output to an AA address (this is standard usage — AA addresses accept arbitrary payment outputs per `getTrigger()`). Since generic AA templates that echo back `trigger.data.asset`/`trigger.output[[asset!=base]]` are a documented, encouraged pattern (see the sample scripts), this condition is straightforward to trigger unintentionally (a user depositing a private/fixed-denomination asset expecting it to be withdrawable) or deliberately (an attacker forcing an AA's internal accounting out of sync with real spendable assets).

### Recommendation
- Before executing state-changing formulas that assume a payment message will succeed, `sendUnit()` (or an earlier validation pass in `handleTrigger`) should proactively reject/bounce AA templates that attempt to pay out `fixed_denominations` assets, instead of silently dropping the message after state changes have already been computed.
- Alternatively, disallow (at `aa_validation.js` definition-validation time) AA payment messages targeting fixed_denominations or private assets altogether, so AA authors are forced to design around this limitation rather than unknowingly writing an AA that can accept but never release such assets.
- Document this limitation prominently and, ideally, provide a supported mechanism (e.g., an explicit unconditional bounce for the whole message set before any state formula executes) so state and balance never diverge from actual spendable output composition.

### Proof of Concept
1. Deploy an AA whose `messages` include a `state` message that decrements `var['balance_'||asset]` for a withdrawal, followed by a `payment` message paying out `trigger.data.asset` to `trigger.address` (pattern taken directly from `test/samples/order_book_exchange.oscript` lines 1-25).
2. Have a user issue a fixed-denominations (indivisible) custom asset and send some units of it to the AA, then trigger a withdrawal request for that asset.
3. In `sendUnit()`, the balance-decrementing `state` message has already been evaluated via `evaluateAA()` (`aa_composer.js:1865-1885`), and the accounting variable is reduced.
4. In `sendUnit()`'s `async.eachSeries` (`aa_composer.js:1323-1330`), the payment message for the fixed-denominations asset is skipped (`return cb()`), and it is then filtered out entirely at `aa_composer.js:1356`, so no payment output for that asset is ever produced. If no other messages remain, `handleSuccessfulEmptyResponseUnit(null)` is called at `aa_composer.js:1360`, making the trigger appear to succeed.
5. The asset remains held by the AA address, but the AA's own state now shows a reduced or zero balance, so the AA will refuse to attempt payout again — the deposited fixed-denominations asset is permanently locked.
6. For a private asset instead, step 4 returns `cb("sending private asset from AA")` (`aa_composer.js:1329-1330`), causing `bounce(err)` (`aa_composer.js:1346-1348`) for every trigger that tries to pay it out — meaning the AA can never release a private asset it receives.
