### Title
Zero `CLPoolAddr` from CL Registry Causes KAIA Staking Rewards to Be Credited to `address(0)` — (`kaiax/reward/impl/getter.go`)

### Summary

In the Prague/Osaka hardfork reward distribution path, `cn.CLStakingInfo.CLPoolAddr` is used directly as a KAIA reward recipient without any zero-address guard. Both `assignStakingRewards` and `assignStakingRewardsFlex` write `clAmount` into the allocation map keyed by `CLPoolAddr`, and `specWithProposerAndFunds`/`specWithProposerAndFundsFlex` call `IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)` unconditionally. If the CL registry returns a zero pool address for any validator entry, the corresponding share of KAIA staking rewards is credited to `address(0)` and permanently burned by `FinalizeState`.

### Finding Description

**Root cause — `kaiax/reward/impl/getter.go`:**

`assignStakingRewards` (lines 521–525) and `assignStakingRewardsFlex` (lines 474–477) both execute:

```go
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // ← no zero-address check
}
```

`specWithProposerAndFunds` (lines 633–637) and `specWithProposerAndFundsFlex` (lines 583–587) similarly call:

```go
newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)  // ← no zero-address check
```

**Source of `CLPoolAddr` — `kaiax/staking/impl/getter.go`:**

Both `parseCallResult` (lines 293–302) and `parsePermissionlessCallResult` (lines 214–220) populate `CLStakingInfo.CLPoolAddr` directly from `clRes.ClPools[i]` without any zero-address validation:

```go
clStakingInfos[i] = &staking.CLStakingInfo{
    CLNodeId:        clRes.NodeIds[i],
    CLPoolAddr:      clRes.ClPools[i],   // ← accepted verbatim, no zero check
    CLStakingAmount: ...,
}
```

The sanity check at lines 306–311 of `parseCallResult` validates `kefAddr` and `kifAddr` for zero, but **does not validate any `CLPoolAddr`**.

**Contrast with the guarded paths:** `specWithProposerAndFunds` explicitly checks `si.KIFAddr`, `si.KEFAddr`, and `si.KPFAddr` for zero and redirects those portions to the proposer. No equivalent guard exists for `CLPoolAddr`.

**Effect in `FinalizeState` — `kaiax/reward/impl/blockstate.go` (lines 53–55):**

```go
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)   // addr == common.Address{} → burned
}
```

`IncRecipient` has no zero-address filter either (lines 110–116 of `kaiax/reward/spec.go`), so `address(0)` enters `spec.Rewards` and `AddBalance` is called on it, permanently destroying the KAIA.

### Impact Explanation

Every block in which a validator has a `CLStakingInfo` entry whose `CLPoolAddr` is `address(0)`, the CL-proportional share of that validator's staking reward (`clAmount`, computed by `consolidatedNode.Split`) is credited to `address(0)` instead of the CL pool. This is an **unauthorized burn of KAIA staking rewards** — the CL pool receives nothing, and the tokens are irrecoverably lost. The magnitude equals `clAmount = reward × CLStakingAmount / (CNStakingAmount + CLStakingAmount)` per block, compounding over every block the misconfigured entry persists.

### Likelihood Explanation

The trigger is a CL registry entry with `CLPoolAddr == address(0)`. This can arise if:
- The production CLRegistry contract does not enforce a non-zero pool address on registration (the contract source is not present in this repository to confirm).
- A governance upgrade or misconfiguration introduces a zero pool address.
- A validator registers a CL entry before the pool contract is deployed, leaving the field unset.

The code comment in `consolidateNodes()` states *"One CLStakingInfo per validator is guaranteed by CLRegistry"* but makes no guarantee that `CLPoolAddr` is non-zero. The missing guard is a repository-native defect regardless of the CL registry's current behavior.

### Recommendation

Mirror the existing KIF/KEF/KPF zero-address handling pattern. Before writing `clAmount` to the allocation map or calling `IncRecipient`, check:

```go
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    if !common.EmptyAddress(cn.CLStakingInfo.CLPoolAddr) {
        alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
    } else {
        alloc[cn.RewardAddr] = new(big.Int).Add(alloc[cn.RewardAddr], clAmount) // redirect to CN
    }
}
```

Apply the same guard in `specWithProposerAndFunds` and `specWithProposerAndFundsFlex` before calling `IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)`.

Additionally, add a zero-address validation for each `CLPoolAddr` in `parseCallResult` and `parsePermissionlessCallResult` in `kaiax/staking/impl/getter.go`, analogous to the existing `kefAddr`/`kifAddr` checks.

### Proof of Concept

1. Deploy a CL registry that returns `address(0)` as `clPools[i]` for one validator entry (e.g., a validator whose pool contract is not yet deployed).
2. The validator has `CNStakingAmount >= MinimumStake`, making it reward-eligible.
3. At each block finalization, `getDeferredRewardFullKore` or `getDeferredRewardFullFlex` calls `assignStakingRewards(config, stakers, si)`.
4. `cn.CLStakingInfo != nil` is true (the entry exists), so `cn.Split(reward)` computes `clAmount > 0`.
5. `alloc[common.Address{}] = clAmount` is written.
6. `FinalizeState` iterates `spec.Rewards` and calls `state.AddBalance(common.Address{}, clAmount)`.

```go
func (spec *RewardSpec) IncRecipient(addr common.Address, amount *big.Int) {
	_, ok := spec.Rewards[addr]
	if !ok {
		spec.Rewards[addr] = big.NewInt(0)
	}
	spec.Rewards[addr].Add(spec.Rewards[addr], amount)
}
```

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
```
