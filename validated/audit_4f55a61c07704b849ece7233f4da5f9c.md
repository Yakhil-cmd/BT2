### Title
`OpenedHandler#provision?` operator precedence bypasses `review_stacks_enabled` when `provisioning_behavior == :prevent_with_label` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` is written as `A && B || C || D` where the `&&` binds tighter than `||`, so `repository.review_stacks_enabled` only gates the `allow_all` clause and is never checked for the `prevent_with_label` clause. Any repository configured with `provisioning_behavior: :prevent_with_label` will have review stacks provisioned for unlabeled PRs even if `review_stacks_enabled` is `false`.

### Finding Description
The binding the code is supposed to enforce is: `repository.review_stacks_enabled == true` is required before any provisioning happens, for every behavior. The actual code in `provision?` is: [1](#0-0) 

Due to Ruby operator precedence, this parses as:
```
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Only the first clause checks `review_stacks_enabled`. The second and third clauses (`allow_with_label` and `prevent_with_label`) are entirely independent of `review_stacks_enabled`.

Attacker request: open a pull request (`action: "opened"`) with an empty `labels` array against a repository whose `provisioning_behavior` is `prevent_with_label` and whose `review_stacks_enabled` is `false`. `pull_request_has_provisioning_label?` is `false`, so `!pull_request_has_provisioning_label?` is `true`, and `provisioning_behavior_prevent_with_label?` is `true` — the third clause is `true`, making `provision?` return `true` regardless of `review_stacks_enabled`.

`respond_to_pull_request_opened?` then returns true [2](#0-1) , and `process` calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` scoped only by `repository.review_stacks` (an association, not filtered by `review_stacks_enabled`) using `stack_attributes` built directly from `params.pull_request.head.ref` (attacker-controlled branch name) [3](#0-2) . The new stack is enqueued via `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) , which downstream leads to task execution against the attacker-controlled branch.

Neither `Repository` model validations, `NullRepository`, nor `ReviewStackAdapter` re-check `review_stacks_enabled` before creating the stack — the only guard is `provision?` itself, and it is broken by the precedence bug. This confirms the equality `repository.review_stacks_enabled == true` does NOT hold on the actual authorization path for the `prevent_with_label` and `allow_with_label` branches — the check is silently skipped.

### Impact Explanation
For any repository with `provisioning_behavior: prevent_with_label` (or `allow_with_label`) and `review_stacks_enabled: false`, an unprivileged PR author can force creation of a `Shipit::ReviewStack` and trigger its provisioning task queue, executing the repository's `shipit.yml`/task commands against attacker-controlled branch content — this is unauthorized stack creation and code execution that the `review_stacks_enabled` flag is specifically meant to prevent. The attack is repeatable against any repository configured this way, matching the Critical category of "a payload for one repository mutating another's stack" analog / unauthorized deploy via disabled feature flag bypass.

### Likelihood Explanation
Preconditions: repository must have `provisioning_behavior_prevent_with_label` (or `allow_with_label`) set with `review_stacks_enabled: false` — an operator misconfiguration state that the code should have prevented from having effect, but is a plausible/likely operator configuration (disabling review stacks while leaving behavior setting configured, e.g. during a temporary rollback). Attacker cost is a single unauthenticated `opened` webhook payload (assuming webhook signature validation is otherwise satisfied by the normal PR-open flow) with an empty `labels` array — trivial and fully repeatable.

### Recommendation
Add explicit parentheses / restructure so `review_stacks_enabled` gates every clause:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
Minitest plan in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not provision when review_stacks_enabled is false even with prevent_with_label behavior and no label" do
  repository = shipit_repositories(:shipit).tap do |r|
    r.update!(review_stacks_enabled: false, provisioning_behavior: :prevent_with_label, provisioning_label_name: 'deploy')
  end
  payload = { action: 'opened', number: 1,
    pull_request: { id: 1, number: 1, url: 'x', title: 't', state: 'open', additions: 1, deletions: 1,
      head: { sha: 'a'*40, ref: 'attacker-branch' }, user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { full_name: repository.github_repo_name },
    sender: { login: 'attacker' } }
  assert_no_difference('Shipit::Stack.count') do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
  end
end
```
Before the fix, `assert_no_difference` fails (a stack is created); this demonstrates `repository.review_stacks_enabled == false` yet a `ReviewStack` is created — confirming the broken binding.
