### Title
Webhook signature verification is bound to `repository.owner.login`, not `repository.full_name`, allowing cross-tenant `ReviewStack` archival/deprovisioning - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `params.dig('repository','owner','login')`, while every `pull_request` handler (e.g. `ClosedHandler`) resolves the target `Repository`/`ReviewStack` using the independent `params.repository.full_name` field. Because the controller never checks that these two attacker-supplied fields agree, a request signed with the secret belonging to one GitHub organization can be crafted to operate on a `Repository`/`ReviewStack` belonging to a completely different organization.

### Finding Description
The broken binding is:

`organization_verifying = params.dig('repository','owner','login')` (used in `verify_signature`) **should equal** `organization_owning_target = params.repository.full_name.split('/').first` (used by `ClosedHandler#repository` / `ReviewStackAdapter`), but nothing enforces this equality.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` solely from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and uses it to pick the GitHub App config/secret: `Shipit.github(organization: repository_owner)`, then validates `X-Hub-Signature` against the raw body with that org's `webhook_secret`. [1](#0-0) [2](#0-1) 

2. Once the signature check passes for that organization, `Shipit::Webhooks.for_event('pull_request')` dispatches to `ClosedHandler.call(params)`, which resolves the repository from a **different** field, `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`. [3](#0-2) [4](#0-3) 

3. `ClosedHandler#process` then builds a `ReviewStackAdapter` scoped to that repository's `review_stacks` and calls `archive!`, which unconditionally issues `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user)` for the found stack, with no further authorization check tying it back to the verified organization. [5](#0-4) [6](#0-5) 

Root cause: `repository.owner.login` and `repository.full_name` are two independent, attacker-controlled JSON fields in the same webhook body. `verify_signature` authenticates the sender's organization using the first field but every downstream handler resolves and mutates state using the second. Shipit's own multi-tenant design (`docs/setup.md`, "Using Multiple Github Applications") explicitly supports separate `webhook_secret`s per GitHub organization, each configured/known by that organization's own administrator. [7](#0-6) 

Attacker exploit flow: An attacker who administers "Org A" (onboarded to this Shipit instance with its own `webhook_secret`) knows that secret. They POST directly to `/webhooks` with `X-Github-Event: pull_request`, a body where `repository.owner.login = "org-a"` (so `verify_signature` picks Org A's app/secret and passes) but `repository.full_name = "victim-org/victim-repo"`, `number` set to a real open review-stack PR number in the victim repo, and `action: "closed"`. Signature is computed with Org A's known secret over this exact body, so `verify_webhook_signature` returns true. `ClosedHandler` then resolves `victim-org/victim-repo`'s `Repository`, finds its `ReviewStack` for that PR number, and calls `archive!` → `deprovision`/`archive!(user)`, destroying the victim's review environment.

None of the listed guards prevent this: `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `ClosedHandler` only validates field *presence/type*, not cross-field consistency with the verifying organization; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` step in the webhook path (webhooks are inherently unauthenticated except for the HMAC check); `Repository`'s format validators only constrain `owner`/`name` charset, not that they match the verifying org.

### Impact Explanation
Any organization onboarded to a multi-tenant Shipit instance can, using only its own legitimately-known webhook secret, trigger `stack.remove_from_provisioning_queue`, `stack.deprovision`, and `stack.archive!(user)` against another tenant's `ReviewStack`, deprovisioning/destroying that party's review environment without any authorization from the victim organization. This is repeatable against any repository/PR-number combination the attacker can guess or observe, and matches the Critical category "a payload for one repository mutating another's stack ... or an unauthorized deploy, rollback".

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment configured with per-organization `webhook_secret`s (documented, supported feature), (2) attacker administers/controls at least one onboarded organization and thus knows its own secret, (3) victim repository has an active `ReviewStack` for a guessable/observed PR number. Given these ordinary preconditions (no Shipit or GitHub credentials beyond the attacker's own legitimately-configured secret), the attack is a single crafted HTTP POST, fully repeatable and inexpensive.

### Recommendation
In `WebhooksController` (or in each handler), after determining `repository_owner` for signature verification, require that `params.dig('repository','full_name')` (and `organization.login` when relevant) is prefixed by/equal to the verified `repository_owner` before dispatching to any handler; reject (422) on mismatch. Equivalently, scope repository/stack lookups by including the verified organization as a condition rather than trusting `full_name` alone.

### Proof of Concept
Add a minitest under `test/controllers/webhooks_controller_test.rb` (or a new test file) asserting the equality fails to hold today:

```ruby
test "pull_request closed webhook with mismatched owner/full_name archives a foreign review stack" do
  attacker_org = "attacker-org"
  victim_repo = shipit_repositories(:shipit) # owner: e.g. "shopify"
  review_stack = create_review_stack_for(victim_repo, pr_number: 42) # active, provisioned

  Shipit.stubs(:github).with(organization: attacker_org).returns(fake_github_app_with_known_secret)

  payload = payload_parsed(:pull_request_closed)
  payload["repository"]["owner"] = { "login" => attacker_org }   # verified org
  payload["repository"]["full_name"] = victim_repo.github_repo_name # target org differs
  payload["number"] = 42
  payload["pull_request"]["number"] = 42

  signature = sign_with_known_secret(payload.to_json, attacker_org_secret)

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = signature

  assert_changes -> { review_stack.reload.archived? }, from: false, to: true do
    post :create, body: payload.to_json, as: :json
  end
  assert_response :ok
end
```

Assertions on both sides of the binding: verified organization (`attacker_org`, confirmed by `verify_webhook_signature` returning true) is asserted to differ from the organization owning the mutated `ReviewStack` (`victim_repo.owner`), while `review_stack.deprovision`/`archive!` are still invoked — demonstrating the equality does not hold and the guard is missing.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
