### Title
Webhook Signature Verification Selects the Signing Secret From an Unverified, Attacker-Controlled Payload Field, Allowing Cross-Organization Forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` decides *which* GitHub organization's `webhook_secret` to validate the request against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted request body, before any signature has been checked. The event handlers that subsequently act on the same payload (e.g. `PushHandler`) resolve the target `Stack`/repository from a different field of that same body (`repository.full_name`). Because the field used to pick the *verifying* secret and the field used to pick the *acted-upon* repository are never bound to each other, an attacker who can produce a valid signature for any one organization configured on the instance (a plausible scenario for multi-tenant Shipit deployments, where each org in `secrets.github` has its own independent `webhook_secret`, as shown in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`) can forge events for a *different* organization's repositories/stacks.

### Finding Description
`repository_owner`, used only to select which `GitHubApp`/secret to check the signature against, is taken directly from the JSON body: [1](#0-0) 

That value feeds `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to HMAC-verify the *entire* raw body: [2](#0-1) [3](#0-2) 

However, `PushHandler` (and other handlers) determine which `Stack`(s) to act on independently, from repository identity carried in the same JSON body (`repository.full_name`, via the `stacks` scope), not from `repository_owner`: [4](#0-3) 

`Shipit.github` in a multi-organization configuration looks up an independent config/secret per organization key, exactly the deployment pattern documented and tested in this engine: [5](#0-4) [6](#0-5) 

This is the exact class of bug in the reference report generalized to an authentication/authorization binding: the "key" used to authenticate (`repository.owner.login` → per-org `webhook_secret`) is not the same thing that is ultimately trusted and acted upon (`repository.full_name` → `Stack`). The report's SimpleMap issue is about an unchecked/unbound value driving privileged state; here the unbound value is which secret authenticates a request that writes to an unrelated repository's stack.

### Impact Explanation
If Shipit is configured for multiple GitHub organizations (a supported, documented configuration), possession of the `webhook_secret` for any one onboarded organization is sufficient to forge `push`, `status`, `pull_request`, `membership`, etc. events for stacks belonging to a *different* organization on the same instance, because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the target stack) are never cross-checked. This can trigger unauthorized `GithubSyncJob`s, fabricate CI `status`/`check_run` state to unblock deploys, or manipulate merge/pull-request state for repositories the attacker does not otherwise control — matching the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires (a) a Shipit instance configured for multiple GitHub organizations, and (b) the attacker possessing a valid `webhook_secret` for at least one of the configured organizations (their own, less-trusted org sharing the same Shipit instance, or one whose secret leaked). This is a realistic multi-tenant scenario the engine explicitly supports and tests, and the confused-deputy nature of the check makes it exploitable without ever touching the target organization's own secret.

### Recommendation
Bind the value used to select the verifying secret to the value used to select the acted-upon repository/stack: resolve the organization to verify against from `repository.full_name`'s owner segment (or otherwise confirm `repository.owner.login`/`organization.login` matches the repository ultimately acted upon) rather than trusting an independently-read field of the same unauthenticated payload. Alternatively, verify the payload against *every* configured organization's secret and only accept the match whose organization equals the repository actually targeted.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and a Stack tracking `OrgB/secret-repo`.
2. Attacker controls (or has leaked) `OrgA`'s `webhook_secret`.
3. Attacker builds a `push` payload: `{"ref": "refs/heads/master", "after": "<attacker sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/secret-repo"}}`.
4. Attacker computes `X-Hub-Signature` using `OrgA`'s secret over this exact payload and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` → succeeds, because the signature does match `OrgA`'s secret.
6. `PushHandler#process` resolves `stacks` from `repository.full_name` = `OrgB/secret-repo` and enqueues `GithubSyncJob`/deploy-relevant state changes for `OrgB`'s stack, despite the attacker never holding `OrgB`'s secret.

Note: I was unable to fully read `app/models/shipit/webhooks/handlers/handler.rb` (the base class defining `stacks`) in this session due to tool-call limits, so the exact mechanism by which `stacks` is scoped to `repository.full_name` is inferred from `PushHandler`'s use of `stacks` combined with earlier grep results showing `full_name` usage across the `pull_request` handlers; this should be re-confirmed against `handler.rb` before treating this as fully proven.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
