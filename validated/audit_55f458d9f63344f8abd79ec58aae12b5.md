### Title
Repository-unscoped SHA lookup in `StatusHandler#process` lets a webhook from any repository write CI statuses onto commits owned by a different stack's repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Every other webhook handler (`PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers) resolves the target `Stack`/`Repository` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records, binding the payload's authenticated repository to the record it mutates. `StatusHandler#process` does not do this: it looks up commits by `Commit.where(sha: params.sha)` across the *entire* `commits` table with no repository filter at all, so a status event that GitHub signs for repository B is applied to any `Commit` row anywhere in the database that happens to share that SHA, including one that belongs to repository A's stack.

### Finding Description
The binding that should hold is: `repository whose webhook_secret verified this payload (params.repository.full_name == B) == repository owning the Commit/Stack being mutated (Commit#stack#repository == A)`. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves the payload was signed by the GitHub App configured for `repository_owner` (B's org/owner) — it never re-checks that `params.repository.full_name` matches the resource the handler is about to mutate. Every handler is therefore individually responsible for scoping its writes to the payload's own repository, and `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exists precisely for that purpose, and is used by `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), `CheckSuiteHandler` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`), and all `PullRequest::*` handlers (e.g. `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`).

`StatusHandler` breaks this pattern:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

It never reads `params.repository` (its `params` schema doesn't even declare a `repository` field) and never calls `Repository.from_github_repo_name`, so the query is a global, cross-tenant SHA lookup. `Commit#create_status_from_github!` then creates a real `Status` row on that commit via `Status.replicate_from_github!` [2](#0-1) [3](#0-2) , and this status becomes visible to `MergeRequest#all_status_checks_passed?` via `head.statuses_and_check_runs` [4](#0-3) .

Exploit flow: attacker owns/controls repository B, whose GitHub organization is configured in Shipit (so `verify_signature` succeeds for B's real webhook secret). Attacker arranges for a commit that exists in repository B to have the identical SHA as the head commit of a queued `MergeRequest` on tenant A's stack (trivially achievable if B is a fork/mirror of A's repository, since git commit objects — and therefore SHA1s — are identical across clones/forks with the same history). Attacker triggers a genuine `status` event for that SHA against B (e.g., via a CI integration on their own fork, or by directly emitting a signed `status` webhook for B, since GitHub itself will sign it with B's real secret). `StatusHandler` finds the `Commit` row belonging to stack A (because the SHA matches) and writes a `success` `Status` onto it, attributing it to `stack_id: A`. `all_status_checks_passed?` on the head commit now reads that success status without any check ever having been posted by A's own CI, and `MergeRequest#merge!` proceeds to call `stack.github_api.merge_pull_request` using stack A's GitHub token.

None of the listed guards prevent this: `verify_signature` authenticates the org/app, not the specific repository being mutated; `ExplicitParameters` schema for `StatusHandler` has no `repository` requirement to even validate against; `drop_unhandled_event`, `force_github_authentication`, `User#authorized?`, `require_permission!`, and model validations on `Repository`/`Stack` play no role in webhook processing at all.

### Impact Explanation
A forged/replayed status for a shared SHA lets an unprivileged GitHub user (owner of any repository whose org is configured in the target Shipit instance) inject a fabricated `success` status onto a commit belonging to a different tenant's stack, flipping `all_status_checks_passed?` to true and causing `Shipit::MergeRequest#merge!` to call `stack.github_api.merge_pull_request` with stack A's `GITHUB_TOKEN`, merging a pull request that never passed A's own required CI checks. This is a cross-tenant integrity/authorization bypass (Critical): an unauthorized merge performed with another repository's deploy credentials, and it is repeatable against any stack/commit whose SHA the attacker can reproduce via a shared git history (fork/mirror).

### Likelihood Explanation
Preconditions: (1) attacker's own repository/org must be one that Shipit's `verify_signature` can validate a genuine webhook signature for (i.e., an org with a configured GitHub App/webhook secret in this Shipit deployment — this could be the attacker's own fork's org, or any org the attacker has push/webhook access in that Shipit trusts); (2) attacker needs a commit whose SHA collides with the target commit, which is trivial to obtain by forking/cloning a public target repository (identical commit objects share identical SHA1s across clones). No Shipit session, API token, or GitHub App secret is required — only the ability to make GitHub emit (or self-emit) a correctly signed `status` webhook for a repository the attacker controls. This is fully repeatable against any target commit whose SHA the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository the same way `PushHandler`/`CheckSuiteHandler` do: require `repository.full_name` in the params schema, resolve `stacks` via `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or an equivalent join through `stack: :repository`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create `repository_a` (owner: `tenant-a`, name: `app`) with `stack_a`, and `repository_b` (owner: `attacker`, name: `app-fork`) with `stack_b`.
2. Create `commit_a` under `stack_a` with `sha: "deadbeef..." ` (no statuses yet). Create `commit_b` under `stack_b` with the **same** `sha`.
3. Build/queue a `MergeRequest` on `stack_a` whose `head` is `commit_a`; assert `mr.all_status_checks_passed?` (or the equivalent `StatusChecker.new(commit_a, commit_a.statuses_and_check_runs, stack_a.cached_deploy_spec).success?`) is `false` before the webhook.
4. Stub `verify_signature` to simulate a validly-signed webhook for `attacker/app-fork` (repository B), and POST a `status` payload with `sha: commit_a.sha`/`commit_b.sha`, `state: "success"`, `repository.full_name: "attacker/app-fork"`.
5. Assert a new `Status` row with `state: "success"` was created and attached to `commit_a` (belonging to `stack_a`), i.e. `commit_a.statuses.last.stack_id == stack_a.id` even though the webhook's authenticated repository was B.
6. Assert `mr.all_status_checks_passed?` now returns `true` and that `mr.merge!` (stubbing `stack_a.github_api.merge_pull_request`) is invoked with `stack_a`'s credentials, without any status ever having been posted against `repository_a`.
