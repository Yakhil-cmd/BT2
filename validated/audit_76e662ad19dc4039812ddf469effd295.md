Based on my investigation, I traced the CVE-2017-9126 bug class (missing bounds validation on an attacker-controlled length field before fixed-offset table/buffer processing, causing a crash) to a plausible analog in `chash.js`.

### Title
Uncaught exception / crash in c-hash validation via length mismatch after decoding untrusted data - (File: chash.js)

### Summary
`chash.js` implements checksum-embedded hash encoding/decoding used for Obyte addresses (chash160) and other 288-bit chashes (chash288, e.g. asset/definition hashes). `isChashValid()` decodes an attacker-supplied encoded string and then processes the decoded buffer through fixed-offset table logic (`separateIntoCleanDataAndChecksum`) that only accepts exactly 160 or 288 bits and throws an uncaught `Error` otherwise.

### Finding Description
`isChashValid(encoded)` only checks the *string* length of the encoded input (32 or 48 chars) before decoding, not the *byte* length of the actual decoded result: [1](#0-0) 

The decode step for 48-char inputs uses `Buffer.from(encoded, 'base64')`, which silently tolerates malformed/invalid base64 characters in Node.js and can produce a decoded buffer whose length does not correspond to 36 bytes (288 bits). The try/catch in `isChashValid` wraps only the decode call, not the subsequent processing: [2](#0-1) 

The subsequent call to `separateIntoCleanDataAndChecksum(binChash)` explicitly throws an *uncaught* `Error` when the bit-length is anything other than 160 or 288: [3](#0-2) 

This throw is not caught anywhere inside `isChashValid`, so it propagates out of the function.

The 32-char path (`base32.decode`) is protected because the sole caller that matters for consensus, `isValidAddress()`, pre-filters input with a strict `/^[A-Z2-7]{32}$/` regex before calling into chash validation: [4](#0-3) 

However, `isValidAddressAnyCase()` and the generic `isValidChash(str, len)` helper call straight into `chash.isChashValid()` with **no charset pre-filtering**, relying entirely on `isChashValid` to be crash-safe: [5](#0-4) 

I was not able to fully confirm, within the available tool budget, a concrete unprivileged reachable call site that invokes `isValidAddressAnyCase` or `isValidChash(str, 48)` with fully untrusted/unfiltered attacker input (e.g., directly from a unit's payload field) before this analysis had to stop. My last searches (`isValidChash|isValidAddressAnyCase|getChash288`, `base32.decode`) returned only match locations in `validation_utils.js`, `object_hash.js`, `chash.js`, and one hit in `validation.js`, but I was cut off before I could inspect those specific call sites in `object_hash.js` and `validation.js` to confirm whether the 48-char/chash288 path is reachable from an untrusted unit field without prior regex sanitization.

### Impact Explanation
If a code path exists (as suggested by the `object_hash.js`/`validation.js` hits I could not fully confirm) where `isValidChash`/`isValidAddressAnyCase` is called on unsanitized, attacker-supplied 32- or 48-character strings during unit/message validation, a crafted unit could trigger an uncaught exception during validation on every full node processing that unit, crashing the node process — a network-wide denial-of-service analogous to the heap-overflow crash in the original CVE (a length-derived, insufficiently-validated table/offset assumption blowing up on malformed input).

### Likelihood Explanation
Medium-low confidence: the primary/most obviously-reachable path (`isValidAddress`, used pervasively in unit/AA/address validation) is safe due to the regex pre-check. The risk is confined to the less-common `isValidAddressAnyCase`/generic `isValidChash` helpers, and I could not verify within the available searches whether any of their call sites in `object_hash.js` or `validation.js` accept fully untrusted unit-supplied strings without upstream sanitization.

### Recommendation
Regardless of exact reachability, harden `chash.js` defensively:
- Wrap the full body of `isChashValid` (not just the decode call) in try/catch and return `false` on any exception instead of allowing errors to propagate.
- Validate the decoded buffer's byte length (20 bytes for chash160, 36 bytes for chash288) immediately after decoding, before calling `buffer2bin`/`separateIntoCleanDataAndChecksum`.
- Audit all callers of `isValidChash`/`isValidAddressAnyCase` (in `object_hash.js`, `validation.js`) to confirm whether attacker-controlled strings can reach them without the `[A-Z2-7]{32}` charset pre-filter that protects `isValidAddress`.
