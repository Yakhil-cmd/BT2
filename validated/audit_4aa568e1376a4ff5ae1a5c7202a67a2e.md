### Title
Non-Atomic Batch Liquidation Allows Partial State Mutations (Debt Removal, Collateral Seizure, Bad-Debt Socialization) to Persist Despite a "Failed" Result - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi()` batches individual `liquidate()` calls through `map`, capturing each position's response as a list element instead of propagating failures with `try!`/`unwrap!`. Because the enclosing transaction always returns `(ok ...)`, Clarity's error-triggered state rollback (which is scoped to the outermost successful/failing call of the transaction) never fires for an individual "failed" position. This is the exact same defect class as the reported `BatchTrade.batchTrade()` issue: a batched operation with a "don't revert the whole batch on one failure" design leaves behind state mutations from the failed leg that should have been undone.

### Finding Description
`liquidate-multi` is defined as: [1](#0-0) 

`call-liquidate` invokes `liquidate` as a plain in-contract function call (not gated by `try!`): [2](#0-1) 

Inside `liquidate`, the state-mutating steps — pulling repayment tokens, removing the borrower's scaled debt, and seizing/transferring collateral to the receiver — execute and commit via `try!`/`contract-call?` well before the function reaches its final, fold-based bad-debt-socialization guard: [3](#0-2) 

That guard runs `socialize-debt-asset` over the borrower's remaining debts via `fold`. Each successful fold iteration performs its own real, committing side effects (`vault-socialize-debt`, an `index-cache` overwrite, and `debt-remove-scaled`) before the *next* item is evaluated: [4](#0-3) 

Only after the fold completes does `liquidate` check the aggregate result and abort via `asserts!`: [5](#0-4) 

When called directly (not through the batch), this `asserts!` failure aborts the whole top-level transaction, and Clarity rolls back everything from `liquidate`, including the collateral seizure, the debt removal, and any already-completed `socialize-debt-asset` writes for earlier fold items — this is the correct, atomic "all-or-nothing" behavior the code is designed around.

However, when the same `liquidate` call is driven through `liquidate-multi` → `call-liquidate` → `map`, the `asserts!` failure only causes `liquidate` to return `(err ...)` as *that position's list element*. `liquidate-multi` itself unconditionally wraps the whole list in `(ok ...)`, so the outer transaction never returns an error. Because Clarity's automatic state-rollback is anchored to the outcome of the transaction's outermost call, and that outermost call (`liquidate-multi`) always succeeds, none of the writes performed earlier in the failing `liquidate` invocation are undone: the borrower's debt reduction, the collateral transfer to the liquidator/receiver, and any already-committed `vault-socialize-debt` write-downs against LP depositors all persist — even though the batch's returned response for that position says the liquidation failed.

### Impact Explanation
- LP depositors of the debt asset(s) that were socialized before the failing fold iteration have their liquidity index/value permanently reduced (bad debt written off against suppliers) even though the operation as a whole is reported as failed and the "all-or-nothing" safety check that is supposed to prevent inconsistent partial socialization is bypassed.
- Because `debt-remove-scaled` for the item that triggered the failure never executes, the borrower's ledger can be left in an inconsistent state (some debt reduced/socialized, some not), while collateral has already been fully seized and sent out.
- This lands on the in-scope "socialization charged to all suppliers" pattern and can manifest as permanent loss of LP-supplied funds without the atomicity guarantee the single-call `liquidate()` path relies on — i.e., protocol insolvency / permanent loss of depositor funds.

### Likelihood Explanation
Any unprivileged liquidator can invoke `liquidate-multi` with a position whose debt list is such that one of the later fold entries in `socialize-debt-asset` hits a failure condition (e.g., an edge case in `vault-socialize-debt`/`vault-accrue` for a specific asset), while earlier entries succeed. No special privileges are required, and the position/debt composition needed to trigger a partial failure can be engineered or awaited by an attacker-liquidator, since bad-debt socialization is only reached once a borrower's collateral has already been fully drained by earlier steps in the same call.

### Recommendation
Make `liquidate-multi` (and `call-liquidate`) propagate failures using `try!`/`unwrap!` at the boundary between the batch and each individual `liquidate` call so that a failing position aborts and rolls back exactly like a standalone `liquidate()` call, or restructure `socialize-debt-asset`'s fold so that partial writes are staged and only committed after the aggregate success check passes (rather than allowing prior fold iterations' `vault-socialize-debt`/`debt-remove-scaled` calls to commit independently of the final `asserts!`).

### Proof of Concept
1. Attacker (liquidator) identifies/engineers a borrower position with multiple outstanding debt assets and zero remaining collateral after the primary liquidation leg, such that `socialize-debt-asset`'s fold succeeds for the first debt asset (committing a `vault-socialize-debt` write-down against LP depositors of that asset) but fails for a later debt asset (e.g., hitting an edge condition inside `vault-socialize-debt`/`vault-accrue`).
2. Attacker calls `liquidate-multi` with this position included (single-position batch is sufficient — `map` still returns a list rather than propagating the error).
3. `liquidate` executes: `vault-system-repay`, `debt-remove-scaled`, `collateral-remove` all commit; the fold in `socialize-debt-asset` also commits its first, successful iteration's `vault-socialize-debt` write-down; the fold's later failing iteration causes the outer `asserts!` in `liquidate` to fail, so `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` as its list element.
4. `liquidate-multi` still returns `(ok (list (err ERR-BAD-DEBT-SOCIALIZATION-FAILED)))` — the transaction succeeds overall, so none of the above writes are rolled back.
5. Result: collateral has been seized and sent, debt has been partially written off/socialized against LP depositors, yet the caller-visible result signals a failed liquidation for that position — inconsistent, non-atomic state persists exactly as in the reported `BatchTrade` allowance-inflation bug class. (define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
