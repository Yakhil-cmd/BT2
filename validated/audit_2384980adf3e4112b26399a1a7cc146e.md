## Title
Cross-organization webhook forgery — repository written is never bound to the organization whose secret authenticated the payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the HMAC against using `repository_owner`, a value pulled straight out of the attacker-controlled JSON body (`payload.dig('repository','owner','login')` or `payload.dig('organization','login')`). The very same parsed body is then handed unmodified to every `Shipit::Webhooks` handler, which independently determines the repository/stack to act on from a *different* field of that body: `payload.dig('repository','full_name')`. Nothing ties these two fields together, so proving knowledge of Organization A's webhook secret only proves the signer knows A's secret — it proves nothing about which repository the signed payload's `full_name` refers to.

### Finding Description [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Shipit supports mounting multiple, independent GitHub Apps (one per organization), each with its own `webhook_secret`, as documented and tested: [3](#0-2) [4](#0-3) 

`Shipit.github(organization: repository_owner)` looks up the App/secret keyed purely by the `repository.owner.login` string taken from the JSON body — this string is entirely attacker-controlled input, not derived from any authenticated source (there is no mTLS/App-installation binding, only a shared-secret HMAC keyed by whatever organization name the attacker puts in the payload).

Once `verify_signature` passes, the exact same raw JSON is parsed and dispatched to handlers: [5](#0-4) 

Handlers resolve the target repository/stack from a *different* JSON field, `repository.full_name`, with no cross-check against `repository.owner.login`: [6](#0-5) [7](#0-6) 

**The broken binding (as an equality):**
`organization authenticated (repository_owner used to select the HMAC secret)` ≠ `repository written (repository.full_name used by the handler to resolve the Stack)`

An attacker who legitimately controls (or has webhook access to) Organization A — e.g., they created a repo and installed the Shipit GitHub App there, giving them A's `webhook_secret` — can:
1. Craft a JSON body where `repository.owner.login = "OrgA"` (so signature verification succeeds using A's secret) but `repository.full_name = "OrgB/victim-repo"` (pointing at a stack belonging to a completely different, victim organization B that they have no access to).
2. Sign that exact byte-for-byte body with A's secret and POST it to `/webhooks`.
3. `verify_signature` succeeds (it only checks that the HMAC matches A's secret over the raw body — the raw body is whatever the attacker crafted).
4. `PushHandler#process` (or any other handler) resolves the stack via `Repository.from_github_repo_name('OrgB/victim-repo')` and acts on it — e.g. calling `stack.sync_github(expected_head_sha: params.after)`, which fetches commits and, if the victim stack has `continuous_deployment: true`, can trigger an unauthorized deploy.

### Impact Explanation
This is a cross-organization write: an attacker who is only authorized (has webhook signing capability) for one tenant organization can forge webhook events that are processed against a Stack belonging to an entirely unrelated organization/repository mounted on the same Shipit instance. Depending on the handler invoked this can drive `GithubSyncJob`/`ContinuousDeliveryJob` against the victim stack, causing an unauthorized deploy — matching the Critical criterion "cross-repository writes ... or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitable by any unprivileged attacker who controls (or is granted webhook access to) a single organization/App installation on a multi-organization Shipit deployment — no privileged Shipit account, `ApiClient` token, or GitHub App private key for the *victim* org is required. The only prerequisite is that the Shipit instance is configured with the documented multi-org `github:` secrets schema, which is a standard, documented deployment mode.

### Recommendation
Verify that the organization used to select the webhook secret (`repository_owner`) matches the organization embedded in `repository.full_name` (and in `organization.login`) before dispatching to handlers, and reject payloads with inconsistent owner/full_name organizations. Alternatively, resolve the target Stack/Repository only within the scope of the organization that successfully authenticated the request, rather than trusting the unauthenticated `full_name` field independently.

### Proof of Concept
1. Deploy Shipit with the multi-org `github:` config (`OrgA`, `OrgB`), each with its own `webhook_secret`, and a Stack backed by repository `OrgB/victim-repo` with `continuous_deployment: true`.
2. As an attacker who only knows `OrgA`'s webhook secret, build a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and succeeds because the HMAC matches OrgA's secret over the exact raw body.
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack, which the attacker never had credentials for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
        end
```
