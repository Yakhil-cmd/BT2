### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook handler resolves the target commit by `sha` alone, with no repository scoping, while GitHub webhook signature verification is only bound to the *organization* that owns the payload's `repository`/`organization` object. This breaks the binding: "organization that authenticated" (the org whose `webhook_secret` produced a valid `X-Hub-Signature`) β‰  "repository that is written" (any stack, in any org, containing a commit whose SHA matches).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization config using only `repository_owner` from the payload and validates the HMAC signature against that organization's `webhook_secret`: [1](#0-0) 

That verification only proves the payload was signed for *some organization configured in Shipit*; it says nothing about which repository/stack the payload is allowed to mutate. The generic `Handler` base class does scope most handlers to stacks belonging to `payload.dig('repository', 'full_name')`: [2](#0-1) 

However, `StatusHandler#process` bypasses this scoping entirely and looks up commits globally by SHA, independent of `repository_name`/`stacks`: [3](#0-2) 

Because SHA is looked up with `Commit.where(sha: params.sha)` across the whole `commits` table (no `stack_id`/repository filter), a `status` event that is validly signed for **organization A** (i.e., signed with organization A's `webhook_secret`) can create/update a `Status` on any `Commit` record in the database whose SHA happens to match β€” including commits that belong to stacks/repositories under **organization B**, whose `webhook_secret` the attacker's org never had. Git SHA collisions across distinct commits are (practically) infeasible, but the same content/commit (and therefore the same SHA) legitimately exists in multiple repositories in common scenarios: forks, repositories that share history via `git subtree`/mirrors, or any stack tracking a mirrored/renamed repository still present as a separate `Repository`/`Stack` record in Shipit. In such a setup, an attacker who owns (or compromises) any GitHub organization/repository already onboarded into this Shipit instance (and can therefore get GitHub to emit genuinely signed `status` webhooks for their own commits) can, by pushing a commit whose SHA is shared with a commit that exists in a different, higher-privilege stack, cause `Commit#create_status_from_github!` to write a fabricated CI status (e.g. `state: 'success'`, arbitrary `context`) onto that other stack's commit. Since deploy gating (`ci.require`) reads these `Status` records to decide whether a commit is deployable, this can be used to satisfy CI requirements on a commit in a repository the attacker does not control, enabling an unauthorized deploy path.

### Impact Explanation
This breaks the equality that should hold: `{org authenticated by webhook signature} == {org/repository whose commit statuses get mutated}`. Instead the actual invariant enforced is `{org authenticated} β‰  {repository targeted}` for the `status` event specifically (all other handlers correctly scope via `stacks`/`repository_name`). The consequence β€” forged CI status on a commit belonging to a stack outside the attacker's authenticated organization, potentially satisfying `ci.require` checks and enabling an unauthorized deploy β€” falls under the accepted "unauthorized deploy" impact category.

### Likelihood Explanation
Medium/situational: it requires the attacker to control an organization/repository already onboarded to this Shipit instance (so GitHub will sign real `status` webhooks for them) and requires a shared commit SHA between their repo and a target stack's repo (fork, mirror, or shared-history scenario). It does not require a stolen `webhook_secret`, an `ApiClient` token, or session access β€” only ordinary GitHub push/CI activity in an org that is already a legitimate Shipit tenant.

### Recommendation
Scope `StatusHandler#process` to the stacks matching `repository_name` (as `Handler#stacks` already provides), e.g. resolve commits via `stacks.flat_map(&:commits).where(sha: params.sha)` or restrict via `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a valid signature for organization/repository X can never mutate commit status data belonging to a different repository's stacks.

### Proof of Concept
1. Attacker owns `attacker-org/attacker-repo`, which is a legitimate stack in this Shipit instance (webhook secret configured for `attacker-org`).
2. Attacker arranges (fork, mirror, or shared history) for a commit with SHA `abc123...` to exist both in `attacker-org/attacker-repo` and in `victim-org/victim-repo` (a separately onboarded, higher-trust stack whose CI the attacker cannot influence directly).
3. Attacker pushes/tags that commit in `attacker-org/attacker-repo` and triggers a real GitHub `status` event (e.g., via their own CI reporting success) β€” GitHub signs this payload with `attacker-org`'s `webhook_secret`.
4. `WebhooksController#verify_signature` validates the signature against `attacker-org` and passes it through. [1](#0-0) 
5. `StatusHandler#process` matches `Commit.where(sha: 'abc123...')` globally, finds the `victim-org/victim-repo` commit row, and calls `create_status_from_github!`, writing a forged `success` status onto it β€” even though the signature never authenticated anything about `victim-org`. [3](#0-2) 
6. If `victim-org/victim-repo`'s `shipit.yml` has `ci.require` referencing that status `context`, the commit can now pass CI gating and become deployable, despite the attacker never having authenticated access to `victim-org`.
