### Title
Stack-scoped API tokens can read the CI status of any stack via CCMenu, bypassing the token's `stack_id` binding - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Every other authenticated resource controller resolves the target `Stack` through `BaseController#stacks`, which restricts the record set to `current_api_client.stack_id` when the token is scoped. `Api::CCMenuController` overrides `stack` to bypass that scoping entirely, so a token that was only supposed to authorize reads of one stack can be used to read the build/deploy status of any stack on the instance.

### Finding Description
`Shipit::Api::BaseController` centralizes the trust boundary between an `ApiClient` token and the stacks it is allowed to touch: [1](#0-0) 

`stacks` is filtered to `current_api_client.stack_id` when the client is scoped, and `stack` (used by `Api::StacksController`, `Api::DeploysController`, `Api::LocksController`, etc.) is derived from that scoped relation: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that loads the `Stack` directly from the unscoped `Stack` model, never consulting `current_api_client.stack_id`: [3](#0-2) 

This breaks the binding: `ApiClient#stack_id` (the stack a token authorizes) ≠ the stack whose data `CCMenuController#show` actually returns. The permission check only verifies that the client's `permissions` array contains `read:stack`: [4](#0-3) 

it never checks that `stack.id == current_api_client.stack_id`. A token can be created scoped to one stack from the settings UI (`ApiClientsController#create`, permissions `read:stack` + a specific `stack_id`), matching the `here_come_the_walrus` fixture pattern: [5](#0-4) 

and it correctly gets scoped when used against `Api::StacksController#index` (test: "an api client scoped to a stack will only see that one stack"): [6](#0-5) 

But that same scoped token, when pointed at `Api::CCMenuController#show` with an arbitrary `stack_id` in the URL, resolves via `Stack.from_param!(params[:stack_id])` — completely independent of the token's own `stack_id` — and returns that other stack's CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.).

### Impact Explanation
This is a concrete instance of the "stack a token authorizes vs. stack it touches" binding violation. A holder of a narrowly-scoped, read-only CCMenu token (e.g., one embedded in a CI status widget URL, as generated by `CCMenuUrlController#fetch`) can enumerate/query build status, last deploy label, and lock status of every other stack in the Shipit instance, not just the one it was issued for. This is an authorization escalation resulting in unauthorized read of stack state across stacks the token was never granted access to, matching the "escalation into authorization... unauthenticated/unauthorized read of stack state" High-impact category.

### Likelihood Explanation
High likelihood: `stack_id` in the URL is directly attacker-controlled (`GET /api/:stack_id/ccmenu`), the only server-side check is possession of *any* valid `read:stack` token (does not need to be the correct stack's token), and CCMenu tokens are routinely generated and embedded in client-visible URLs (`CCMenuUrlController#fetch` returns the token in a plaintext query string). No privileged access, session, or GitHub credentials are required beyond having obtained one legitimately-scoped read-only token.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped tokens are restricted to their assigned stack exactly as they are elsewhere in the API.

### Proof of Concept
1. As an authorized user, create (or have auto-created via `CCMenuUrlController#fetch`) an `ApiClient` scoped to Stack A with permission `read:stack` (e.g. fixture `here_come_the_walrus`, `stack: shipit`, `permissions: [read:stack]`).
2. Obtain the token: `client.authentication_token`.
3. Send `GET /api/<stack-B-owner>/<stack-B-name>/ccmenu` (i.e., target a *different* stack, "Stack B") using HTTP Basic auth with the Stack-A token, per `ApiHelper#authenticate!`: [7](#0-6) 
4. Observe the response is `200 OK` with Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, etc.) even though the token's `stack_id` is Stack A — confirmed by `Api::CCMenuController#stack` at [8](#0-7)  never consulting `current_api_client.stack_id`.
