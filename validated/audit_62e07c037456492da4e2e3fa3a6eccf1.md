### Title
Webhook organization-authentication is not bound to the repository/commit being written, allowing cross-tenant commit-status forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
This is the same trust-binding weakness as the Stakehouse Giant-pool bug: a component authenticates one identity (a vault / here, a GitHub organization) but then acts on a *different*, attacker-supplied identity (the funds destination / here, an arbitrary commit belonging to any repository) without re-validating that the two match.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate an incoming webhook using an organization name pulled straight out of the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization GitHub App configs (multi-tenant support), each with its own `webhook_secret`: [3](#0-2) 

Once the signature check passes (proving only that *some* onboarded organization's secret was used to sign this exact raw body — an organization the attacker fully controls if they administer that org's GitHub App), the event is dispatched to a handler that trusts other, independently-controlled fields of the same JSON body. `StatusHandler#process` looks up commits **only by `sha`, with no scoping to the authenticated organization or even to the `repository` object in the payload at all**: [4](#0-3) 

Compare with the generic `Handler#stacks`/`repository_name` helper, which shows the intended (but here bypassed) way handlers are supposed to scope to a repository derived from the payload: [5](#0-4) 

The binding the code implicitly assumes, expressed as an equality that is never enforced, is:

`authenticated_organization(payload.repository.owner.login) == owner_organization(Commit.find_by(sha: payload.sha).stack.repository)`

Before the attacker's request: a webhook signed with Org A's secret can only plausibly represent Org A's events (GitHub itself enforces this on the sending side). After the attacker's crafted request: the attacker sets `repository.owner.login` (and/or `organization.login`) to their own Org A (whose secret they know, since they administer that org's GitHub App on this shared Shipit instance) to pass `verify_signature`, while setting `sha` to a commit SHA that belongs to a completely unrelated Org B's stack. `StatusHandler` never checks that the commit's repository/organization matches the organization that authenticated the request, so the forged status is written onto Org B's commit.

### Impact Explanation
Commit statuses (`Commit#create_status_from_github!`) drive Shipit's deployability/CI-gating and are displayed on the stack UI; a forged "success" status for a commit in a victim organization's stack can be used to make an unsafe/unreviewed commit appear deployable, or a forged "failure"/"pending" status can be used to block a victim's legitimate deploys. Because the write happens across organizational boundaries with no ownership check, this satisfies the "cross-repository writes" / potential "unauthorized deploy" impact bar defined for this scan (a party with credentials for one tenant's webhook integration can write into another tenant's data).

### Likelihood Explanation
Requires only that the attacker legitimately administers (or otherwise obtains the webhook secret of) one organization already onboarded to a multi-tenant Shipit deployment (`Shipit.github(organization:)`/`github_app_config`), a materially lower bar than requiring a Shipit session, an `ApiClient` token, or GitHub write access to the *victim* repository. No additional exploitation primitives are needed beyond crafting a raw JSON POST with a valid HMAC-SHA1 signature for the attacker's own org.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`), verify that the commit/stack resolved from the payload actually belongs to the same organization/repository that was used to authenticate the webhook (i.e., re-derive and compare `repository_owner` against the resolved commit's repository owner before creating the status). More generally, `WebhooksController#verify_signature` should pass the authenticated organization down to handlers, and every handler should assert `payload.dig('repository','full_name')`'s owner matches that authenticated organization before mutating any records.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub config, `secrets.github` containing at least `orgA` (attacker-administered) and `orgB` (victim), each with its own `webhook_secret`.
2. Attacker knows `orgA`'s `webhook_secret` (they manage `orgA`'s GitHub App on this shared instance).
3. Attacker finds/guesses a commit `sha` belonging to a stack under `orgB` (e.g., visible in `orgB`'s public Shipit UI or GitHub commit history).
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<orgB-commit-sha>",
  "state": "success",
  "description": "forged",
  "context": "ci/forged",
  "repository": {"owner": {"login": "orgA"}}
}
```
5. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, raw_body)>`.
6. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully since the attacker used `orgA`'s real secret.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `orgB` commit regardless of the authenticated org — and calls `create_status_from_github!`, writing a forged status onto `orgB`'s commit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
