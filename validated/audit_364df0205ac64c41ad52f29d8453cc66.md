### Title
Cross-repository Status injection via unscoped `Commit.where(sha:)` lookup lets any webhook-authenticated org forge deploy state on another tenant's Stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by matching `sha` across the *entire* `commits` table, with no check that the webhook's authenticated `repository`/`organization` corresponds to the `Commit`'s actual `Stack`/`Repository`. Since a git commit SHA is a pure content hash, an attacker who owns any GitHub repository already onboarded to this Shipit instance (so their webhook signature verifies) can import/graft a victim's exact commit object into their own repo and have GitHub fire a legitimately-signed `status` webhook that Shipit will attach to the *victim's* commit and stack, triggering `Stack#trigger_continuous_delivery` and mutating `continuous_delivery_delayed_since` on the victim's `Stack` row.

### Finding Description
The broken binding: `verified_organization(repository_owner_from_payload) == organization_owning(Commit#stack)`. This is never enforced.

- `WebhooksController#verify_signature` only checks that the HMAC signature is valid for the organization named in the payload's `repository.owner.login` (`app/controllers/shipit/webhooks_controller.rb:24-49`), i.e., it proves "this payload came from an app registered under org X," but does nothing to constrain *which* commit/stack the payload's `status` event is allowed to affect.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This looks up *any* `Commit` row in the whole installation whose `sha` matches, irrespective of which repository/org the verified webhook belongs to. There is no `stack.repository == payload.repository` check anywhere in this handler or in `Commit#create_status_from_github!` / `Status.replicate_from_github!`. [2](#0-1) 

Because a commit's SHA is fully determined by its content (tree, parents, author/committer, timestamps, message), an attacker can copy the exact commit object of a *public* victim repository (e.g., by adding it as a git remote and pushing it) into a repository they control that is already onboarded to Shipit (so `Shipit.github(organization: repository_owner)` resolves and the webhook signature validates). When GitHub later sends a `status` webhook for that SHA from the attacker's repo/org (e.g., their own CI marking the commit `success`), Shipit's `StatusHandler` finds the victim's pre-existing `Commit` row (same SHA, different stack) and calls `commit.create_status_from_github!(params)`, creating a `Status` scoped to the victim's real `stack_id` (`Commit#create_status_from_github!` uses `stack_id` from the found commit) - so the attacker's forged status lands directly on the victim's stack's commit.

That `Status.create` fires `after_commit :schedule_continuous_delivery`, calling `commit.schedule_continuous_delivery` [3](#0-2) , which enqueues `ContinuousDeliveryJob.perform_later(stack)` for the victim's stack [4](#0-3) . `ContinuousDeliveryJob#perform` calls `stack.trigger_continuous_delivery` [5](#0-4) .

`Stack#trigger_continuous_delivery` recomputes `next_commit_to_deploy`, whose deployability depends on the commit's status set (via `deployable_commits`, which reads commit CI/check statuses) - so a forged `success` status can make an otherwise-blocked commit look deployable, matching the "commit freshness wait window" bypass referenced in the question (see the test asserting delay behavior based on how recently a commit was pushed) [6](#0-5) . If the commit is judged resumable/deployable, `continuous_delivery_resumed!` (`update!(continuous_delivery_delayed_since: nil)`) or `trigger_deploy` (which also calls `continuous_delivery_resumed!`) fires on the *victim's* Stack row [7](#0-6) .

None of the existing guards stop this: `verify_signature` validates org-level HMAC only, not commit/repo ownership; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema on `StatusHandler` (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`) never includes or checks `repository` [8](#0-7) ; there is no `Stack`/`Repository` validation involved in this flow at all.

### Impact Explanation
An attacker who controls (or can push to) any GitHub repository already integrated with the target Shipit instance can, without any Shipit credentials, mutate a *different* tenant's `Stack` row (`continuous_delivery_delayed_since`) and, more broadly, inject arbitrary CI status onto a victim's commit, potentially unblocking/resuming continuous delivery on a stack the attacker has no relationship with. This is a cross-repository "payload for one repository mutating another's stack/commit" scenario, matching the Critical impact category. It is repeatable against any commit SHA that Shipit already tracks (i.e., any commit that appears in the victim stack's history), as long as the attacker can get GitHub to emit a signed `status` event for that exact SHA from their own onboarded repo.

### Likelihood Explanation
Preconditions: (1) the attacker needs an org/repo that is already configured in Shipit (`Shipit.github(organization: repository_owner)` must resolve and have a working `webhook_secret` for signature verification) - this is a real-world scenario for large orgs that self-service onboard many repos to one Shipit instance; (2) the victim's repository/commit must be visible enough (public, or otherwise fetchable) for the attacker to obtain the exact commit object to graft; (3) the victim stack must have `continuous_deployment` enabled with a schedule, as stated. Cost is low: git object grafting/pushing an existing commit into another repo is trivial and requires no exploitation of GitHub itself - just standard `git fetch`/`git push` of an object the attacker already has bytes for.

### Recommendation
In `Webhooks::Handlers::StatusHandler#process` (and any other handler resolving commits/stacks by `sha` alone, e.g. check-run handlers), scope the `Commit` lookup to the stack(s) whose `Repository` matches the verified webhook's `repository.full_name`/owner, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })`. The webhook payload's `repository` field should be added to the `StatusHandler` params schema and enforced as authoritative, not just used for signature-org lookup.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from unrelated org cannot mutate a different stack's commit" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  victim_commit = victim_stack.commits.last
  victim_stack.update_column(:continuous_delivery_delayed_since, 1.hour.ago)

  # Attacker's own repo/org is a separate, unrelated stack; attacker pushed
  # the identical commit object (same sha) into their own repo.
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => 'master' }]
  }

  before = victim_stack.reload.continuous_delivery_delayed_since

  Shipit::Webhooks::Handlers::StatusHandler.new.call(attacker_payload)
  perform_enqueued_jobs

  after = victim_stack.reload.continuous_delivery_delayed_since

  # Demonstrates the broken binding: a payload never authenticated for
  # victim_stack's repository/org still mutated victim_stack's row.
  assert_not_equal before, after
end
```
This test does not require live GitHub - it calls the handler directly with a forged payload sharing the victim commit's `sha`, and asserts `continuous_delivery_delayed_since` on the victim's `Stack` changes purely due to processing that unrelated payload.

    def continuous_delivery_delayed?
      continuous_delivery_delayed_since? && continuous_deployment? && (checks? || deployment_checks?)

    def continuous_delivery_delayed!
      touch(:continuous_delivery_delayed_since) unless continuous_delivery_delayed?
    end

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
