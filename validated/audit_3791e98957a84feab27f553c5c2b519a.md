### Title
`OpenedHandler#provision?` operator-precedence bug lets PRs bypass `repository.review_stacks_enabled` that `LabeledHandler` correctly enforces - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` writes `repository.review_stacks_enabled && A || B || C` instead of `repository.review_stacks_enabled && (A || B || C)`. Because Ruby's `&&` binds tighter than `||`, `review_stacks_enabled` only gates the `provisioning_behavior_allow_all?` branch, not the `allow_with_label?`/`prevent_with_label?` branches, so a repository with review stacks disabled can still have a stack auto-provisioned by opening (or labeling-at-open-time) a pull request. `LabeledHandler#respond_to_label_change?` correctly ANDs `review_stacks_enabled` across the whole `(archive? || unarchive?)` expression, so the same repository configuration is safe on the `labeled` path but not on the `opened` path.

### Finding Description
Binding claimed: gating behavior of `review_stacks_enabled` in `OpenedHandler#provision?` == gating behavior in `LabeledHandler#respond_to_label_change?`. Tracing the code shows this does **not** hold.

`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`: [1](#0-0) 
parses (per Ruby precedence, `&&` before `||`) as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:78-83`: [2](#0-1) 
correctly parses as `action == "labeled" && state == "open" && review_stacks_enabled && (archive? || unarchive?)` — `review_stacks_enabled` gates the entire OR expression.

Root cause: missing parentheses around the three OR'd behavior clauses in `OpenedHandler#provision?` (the same bug also exists in `ReopenedHandler#unarchive?` at `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:70-75`, though that is out of scope of this question).

Attacker scenario: repository is registered in Shipit with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) but an operator has explicitly turned `review_stacks_enabled` off. The attacker (an unprivileged GitHub user who can open PRs / control labels on their own fork/branch feeding this repository) opens a pull request carrying the configured provisioning label (for `allow_with_label`) or simply opens a PR without the label (for `prevent_with_label`). GitHub sends a normal, correctly-signed `pull_request` "opened" webhook (signature verification, `verify_signature`/`GitHubApp#verify_webhook_signature`, and `drop_unhandled_event` all pass normally — this is a legitimate webhook, not a forgery) which reaches `OpenedHandler#process` → `respond_to_pull_request_opened?` → `provision?`, which evaluates true and calls `ReviewStackAdapter#find_or_create!`, creating a `Shipit::ReviewStack` and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:72-85`). [3](#0-2) 
If the attacker instead only *labels* an existing open PR on the same disabled repository (rather than opening it with the label already attached), `LabeledHandler#respond_to_label_change?` correctly short-circuits on `repository.review_stacks_enabled` and no stack is created/unarchived. Thus the `opened` event path bypasses a control the `labeled` event path enforces, exactly as posited.

No existing guard blocks this: `verify_signature` only validates HMAC authenticity of the real GitHub webhook (irrelevant here since the webhook is genuine), `drop_unhandled_event` only checks the event type is registered, and there is no other check of `review_stacks_enabled` in the `opened` code path.

### Impact Explanation
An attacker who can merely open a pull request (or open one with a specific label) against a Shipit-tracked repository can force creation and provisioning-queueing of a `Shipit::ReviewStack` even though the repository owner/operator explicitly disabled review-stack auto-provisioning (`review_stacks_enabled = false`). This causes unauthorized infrastructure state to be created and queued for provisioning against that repository/environment (`pr#<number>`), which is a stack write/provisioning trigger that the operator's configuration should have prevented — matching the "unauthorized deploy" class of impact. It is repeatable for every PR opened against any repository configured with `allow_with_label`/`prevent_with_label` and `review_stacks_enabled: false`. It is confined to the repository the attacker can already open PRs against (not a cross-tenant repository-confusion bug), so the blast radius is scoped to that repository's provisioning pipeline, but is still an authorization-flag bypass that operators rely on.

### Likelihood Explanation
Preconditions: repository must be registered in Shipit, `provisioning_behavior` set to `allow_with_label` or `prevent_with_label`, and `review_stacks_enabled` set to `false` (this specific combination is the only state where `OpenedHandler` and `LabeledHandler` diverge). Attacker cost is trivial — open a PR (with or without a label, depending on behavior) against a repository whose webhooks are wired to the Shipit instance; no secrets, tokens, or privileged roles are needed since the webhook is genuinely emitted and signed by GitHub. Fully deterministic and repeatable.

### Recommendation
Add parentheses in `OpenedHandler#provision?` (and the identical bug in `ReopenedHandler#unarchive?`) so `review_stacks_enabled` gates the entire disjunction, matching `LabeledHandler`:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
minitest plan (fixture: repository with `review_stacks_enabled: false`, `provisioning_behavior: allow_with_label`, `provisioning_label_name: "pull-requests-label"`; PR payload includes that label):
1. `test "OpenedHandler creates a stack even when review_stacks_enabled is false"` — call `OpenedHandler.new(payload_parsed(:pull_request_opened_with_label)).process` and `assert_difference -> { Shipit::Stack.count }, 1`.
2. `test "LabeledHandler does not create/unarchive a stack when review_stacks_enabled is false"` — using the same repository fixture and an equivalent `labeled` payload, call `LabeledHandler.new(payload).process` and `assert_no_difference -> { Shipit::Stack.count }`.
3. Assert both tests pass under current code, demonstrating `OpenedHandler#provision?` (`true`) != `LabeledHandler#respond_to_label_change?` (`false`) for identical `review_stacks_enabled: false` repository state — proving the divergence.
4. After applying the parenthesization fix, re-run test 1 and assert `assert_no_difference -> { Shipit::Stack.count }`, confirming the equality now holds.
