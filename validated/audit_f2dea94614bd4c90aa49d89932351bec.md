### Title
Webhook signature verification org is not bound to the repository the handler acts on, enabling cross-organization stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to verify the HMAC signature against using `repository_owner` (`repository.owner.login` or `organization.login`), but the actual event handlers (`Shipit::Webhooks::Handlers::Handler#stacks`, used by `PushHandler`, `CheckSuiteHandler`, and PR handlers) resolve the target `Stack`/`Repository` using an entirely different field: `repository.full_name`. Because these two JSON fields are never cross-validated, a caller who legitimately controls the GitHub App/webhook secret for one configured organization can craft a payload whose `repository.owner.login` matches their own org (used only for signature selection) while `repository.full_name` names a repository belonging to a completely different organization also hosted on the same Shipit instance.

### Finding Description
The relevant binding that should hold is:

`organization whose webhook_secret authenticated the request == organization owning the repository the handler mutates`

Before the pull request/attack, for any legitimate webhook the two org references agree because GitHub itself populates both fields from the same source repository.

After an attacker-crafted request, they can diverge:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `lib/shipit/github_app.rb#verify_webhook_signature` simply HMACs the raw request body with the secret configured for that resolved organization and compares it to `X-Hub-Signature`. [3](#0-2) 
- Once verification passes, `WebhooksController#create` dispatches the *entire raw payload* to handlers with no re-derivation or cross-check against `repository_owner`: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [4](#0-3) 
- The base `Handler#stacks` / `#repository_name` resolves the target `Stack` purely from `payload.dig('repository', 'full_name')` — a different JSON key than the one used for signature-org selection: `Repository.from_github_repo_name(repository_name)&.stacks`. [5](#0-4) 
- `PushHandler#process` uses that unrestricted `stacks` scope to trigger `stack.sync_github(expected_head_sha: ...)` for any matching stack. [6](#0-5) 
- `CheckSuiteHandler#process` similarly acts on `stacks` filtered only by branch/sha, again scoped from `repository.full_name`, not the org that produced the signature. [7](#0-6) 
- `PullRequest::ClosedHandler` independently derives its own `repository` from `params.repository.full_name` and archives/deprovisions whatever `ReviewStack` matches, again bypassing the org used for signature verification. [8](#0-7) 

This layout is explicitly supported/documented: Shipit is designed to host multiple GitHub organizations from a single instance, each with its own `app_id`/`installation_id`/`webhook_secret`/`private_key`, all sharing the same `/webhooks` endpoint. [9](#0-8) 

Because the signature-selection field (`repository.owner.login` / `organization.login`) and the handler-dispatch field (`repository.full_name`) are independent JSON keys in the same attacker-controlled POST body, an entity that legitimately administers **any one** of the configured organizations' GitHub Apps (and thus legitimately knows that org's `webhook_secret`) can produce a validly-signed webhook whose `repository.full_name` targets a **different** organization's repository/stack that they have no authorization over.

### Impact Explanation
This breaks the cross-organization isolation that a multi-tenant Shipit deployment relies on: an administrator/holder of Org A's GitHub App webhook secret can forge webhook events that are dispatched against Org B's stacks. Concretely:
- `push` events can force `GithubSyncJob`/`stack.sync_github` on Org B's stack with an attacker-chosen `expected_head_sha`, corrupting Shipit's view of Org B's deployable revisions and potentially causing an unauthorized deploy or rollback decision downstream (Shipit treats the synced HEAD as deployable).
- `check_suite` events can force re-evaluation of check runs (`schedule_refresh_check_runs!`) for Org B's commits, influencing CI-gated deploy eligibility.
- `pull_request` "closed" events can archive/deprovision Org B's `ReviewStack`s (`stack.deprovision`, `stack.archive!`), an unauthorized destructive write against a repository the attacker's org has no relationship to.

This is a cross-organization / cross-repository write triggered purely by possessing a signing secret scoped to an unrelated, lower-privileged organization — matching the "cross-repository writes" / "unauthorized deploy or rollback" impact class.

### Likelihood Explanation
Requires only: (1) the target Shipit instance is configured to host more than one GitHub organization (a documented, supported configuration), and (2) the attacker legitimately controls one of those organizations' GitHub App (i.e., possesses that org's own `webhook_secret`, which is not "another organization's secret" and thus not out-of-scope credential misuse). No Shipit session, API token, or the *target* org's credentials are needed. The attacker only crafts a raw HTTP POST to the public `/webhooks` endpoint with a mismatched `repository.owner.login` vs `repository.full_name`, computing the HMAC with their own org's secret.

### Recommendation
Bind repository resolution to the same organization used for signature verification. Specifically:
- Update `Handler#repository_name` (and any handler that independently reads `params.repository.full_name`, e.g. `PullRequest::ClosedHandler#repository`) to only resolve stacks/repositories whose owning organization equals the `repository_owner` value that was used to select the webhook secret in `WebhooksController#verify_signature`.
- Pass the verified `repository_owner` (or the resolved `GithubApp`/organization) down into `Handler.call`/`Handler#initialize` so handlers can assert `payload.dig('repository', 'full_name').split('/').first.casecmp(repository_owner) == 0` (or equivalent) before acting, rejecting/discarding events where the two disagree.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret`.
2. Attacker is an admin of `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret` (a credential they are legitimately entitled to for their own org, not `org-b`'s).
3. Attacker crafts a JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POSTs to `https://<shipit-host>/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "org-a"`, fetches `org-a`'s `GithubApp`, and the signature validates successfully against `org-a`'s secret. [1](#0-0) 
6. `PushHandler#process` is invoked with the full payload and resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")`, i.e. an `org-b` stack, and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a write against `org-b`'s stack despite the request only being authenticated as `org-a`. [5](#0-4) [6](#0-5) 

Note: I was unable to execute this end-to-end in a live environment; the analysis is based on static code tracing of the exact controller/handler files cited above. The `test/controllers/webhooks_controller_test.rb` suite confirms the "resolve secret by `repository_owner`" behavior but does not appear to test cross-org `full_name` mismatches, consistent with this gap being unaddressed. [10](#0-9)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
