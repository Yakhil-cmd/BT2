### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits by SHA alone, with no scoping to the repository that authenticated the inbound webhook. Because git commit SHAs are content-addressed and identical across forks/mirrors sharing history, an attacker who owns any repository already connected to the same Shipit instance can send a legitimately-signed `status` webhook for their own repo and have it applied to a `Commit`/`Status` row belonging to a victim stack whose repository they never authenticated for.

### Finding Description
The broken binding is: `repository authenticated by X-Hub-Signature (params.dig('repository','owner','login'))` should equal `repository/stack whose Commit#status the write mutates`. It does not.

- `WebhooksController#verify_signature` only checks that the payload's `repository_owner` org has a valid HMAC signature via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0)  — this proves the payload came from *some* org configured in Shipit, not that the `sha`/commit referenced actually belongs to that org's repository.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query has no `stack_id`/repository filter at all — it matches every `Commit` row across every stack in the entire Shipit instance that shares that SHA string.
- `create_status_from_github!` then unconditionally creates a `Status` on the resolved commit and triggers `add_status`, which fires `Hook.emit(:deployable_status, ...)` and calls `stack.schedule_merges` [3](#0-2) , and via `Status#schedule_continuous_delivery` -> `commit.schedule_continuous_delivery`, this can lead to `Stack#trigger_continuous_delivery` -> `next_commit_to_deploy` -> `deployable_commits` picking up the now-"success" commit and deploying it [4](#0-3) [5](#0-4) .
- Attack path: attacker owns/administers a repository (e.g. a fork of the victim's open-source repo, or any repo they onboarded into the shared Shipit instance) whose org is already configured with a webhook secret in Shipit. Because forked/mirrored repos share git object history, the victim's target commit SHA legitimately exists in the attacker's own repo/fork too. The attacker triggers (or crafts, since GitHub signs based on the configured secret for that org/repo) a real `status` webhook event with `sha` = the shared/victim SHA and `state=success`, `context` matching whatever context the victim stack requires. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` then finds *all* `Commit` rows with that SHA — including the victim stack's row — and writes a success `Status` onto it, even though the attacker never authenticated for the victim's repository/stack.
- None of the listed guards prevent this: `verify_signature` checks org-level HMAC only, not repo/stack identity of the target commit; `ExplicitParameters` schema on `StatusHandler` only validates payload shape (`sha`, `state`, etc.), not ownership; there is no `require_permission!`, `User#authorized?`, or `Repository`/`Stack` scoping applied in this code path at all.

### Impact Explanation
A payload authenticated for repository/org A directly mutates a `Commit`/`Status` record belonging to stack/repository B, which is exactly the "payload for one repository mutating another's stack/commit" category called out as Critical. Concretely: (1) it forges a CI success status on a victim commit, flipping `Commit#deployable?` to true; (2) combined with `Stack#next_commit_to_deploy`'s `maximum_commits_per_deploy` window logic, this can cause `trigger_continuous_delivery` to deploy that commit — an unauthorized deploy advancing the victim org's release window, driven by data the victim's org never approved. This is repeatable against any stack whose commits share a SHA with a repository the attacker controls (most commonly via forks of public/open-source repos, a very common real-world topology for Shipit-managed projects), and the blast radius spans every tenant/stack sharing the multi-tenant Shipit instance.

### Likelihood Explanation
Preconditions are realistic and low-cost: the attacker only needs (a) any repository already onboarded to the shared Shipit instance under an org with a configured webhook secret (which they can arrange themselves if self-service onboarding is allowed, or simply by being a legitimate member of some other org already using the instance), and (b) a target victim commit SHA that also exists in a repo they control — trivially true for forks/mirrors of open-source repositories, since git SHAs are identical across clones. No secrets, no privileged Shipit role, and no GitHub App keys are required; the attacker relies entirely on their own legitimately-issued webhook signature for their own repo. `maximum_commits_per_deploy` narrows which forged commit is most impactful but is not required for the underlying cross-tenant write itself.

### Recommendation
Scope the `StatusHandler` lookup (and the `Status.replicate_from_github!`/`create_status_from_github!` write path in general) to commits belonging to a stack whose repository matches `params.repository.full_name` (or equivalent) from the verified webhook payload, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`, mirroring the repository-scoping pattern already used by `PullRequest` handlers (`Shipit::Repository.from_github_repo_name(params.repository.full_name)`).

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repos in fixtures: `stack_a` (owner org `"attacker-org"`, repository `attacker-org/repoA`) and `stack_b` (owner org `"victim-org"`, repository `victim-org/repoB`), each with `maximum_commits_per_deploy` set on `stack_b` and several undeployed commits on `stack_b`, none created via any action tied to `attacker-org`.
2. Create a `Commit` on `stack_b` with a SHA `shared_sha` (simulating a shared fork commit), with no existing successful status; assert `commit_b.deployable?` is `false` before the webhook.
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.owner.login == "attacker-org"` and `sha == shared_sha`, `state: "success"`, signed with `attacker-org`'s valid webhook secret (stub `GithubHook`/`Shipit.github(organization: "attacker-org")#verify_webhook_signature` to return `true`, matching existing test patterns in `webhooks_controller_test.rb`).
4. Assert: `commit_b.reload.deployable?` is now `true`, and `stack_b.next_commit_to_deploy == commit_b` (or the appropriate commit within the `maximum_commits_per_deploy` window) — demonstrating that a webhook authenticated for `attacker-org` mutated `stack_b`'s (owned by `victim-org`) commit state, i.e. asserting the equality `repository authenticated by signature ("attacker-org") != repository whose stack state changed ("victim-org")`.

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
