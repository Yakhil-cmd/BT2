### Title
`Api::CCMenuController#stack` bypasses stack-scoped `ApiClient` authorization, allowing token holders to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` scopes API access to the stack(s) an `ApiClient` is authorized for via `stacks`/`stack`, but `Api::CCMenuController` overrides `#stack` with an unscoped lookup, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
In the standard API flow, `Api::BaseController` restricts which stacks a given `ApiClient` may see: [1](#0-0) 

`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` through that scoped relation, so `from_param!` will raise `ActiveRecord::RecordNotFound` for any stack outside the client's authorized scope.

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model instead of the inherited scoped `stack` method. The `require_permission :read, :stack` declaration only checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never checks `stack_id` — that check only happens inside the (bypassed) `stacks` scoping method. The controller also supports token-in-query-string authentication, making it trivial to hit with any stack id: [4](#0-3) 

So: the equality that should hold is `stack the token authorizes == stack the request touches` (enforced by `stacks`/`stack` in `BaseController`). In `CCMenuController#show`, that equality is broken: any `ApiClient` with `read:stack` permission — even one explicitly scoped by `stack_id` to a single stack — can pass an arbitrary `stack_id` param and read a different stack's CI/CD status via the unscoped `Stack.from_param!`.

### Impact Explanation
This grants unauthenticated read of another stack's task/deploy state to a caller holding only a narrowly-scoped API token, matching the "unauthenticated/authorized read of stack state, task streams or deploy output" High-impact category. The leaked data (`shipit/ccmenu/project` view) includes the stack name, last build status/label/time and activity for any stack in the installation, regardless of the token's intended scope — a cross-tenant information disclosure enabled purely by an authorization-binding mismatch in code the engine controls.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `ApiClient` token (e.g., one generated via `CCMenuUrlController#fetch`, which explicitly creates read-only, stack-scoped clients) can trivially exploit this by substituting a different `stack_id` in the URL/query string — no privileged access, secrets, or additional preconditions are required beyond possessing any valid token with `read:stack`.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or change it to `@stack ||= stacks.from_param!(params[:stack_id])`) so it inherits the same client-scoped lookup used elsewhere in `Api::BaseController`, restoring the binding between token authorization scope and the stack actually served.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` (e.g. one issued via `CCMenuUrlController#fetch` for Stack A, or any client with `stack_id` set and `read:stack` permission).
2. Send `GET /api/stacks/<stack-B-id>/ccmenu.xml?token=<clientA_token>` where `stack-B` is a stack the client is not scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the inherited scoped `stack` helper, the request succeeds and returns Stack B's CCMenu XML (name, last build status/label/time), even though the token is only authorized for Stack A. [5](#0-4)
