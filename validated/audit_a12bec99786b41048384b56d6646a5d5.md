### Title
`MembershipHandler` binds Team records by global `github_id` alone, letting any org's webhook overwrite/join a team owned by a different organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)` without ever comparing `params.organization.login` to the existing record's `organization` column. The `params` schema only guarantees `team.id` is coerced to a Ruby `Integer`; it enforces no relationship between that id and the organization that signed the webhook, so a correctly-signed webhook from Organization B can match and mutate a `Team` row that was created for Organization A.

### Finding Description
Binding claimed: `team.id ∈ ids_issued_to(params.organization.login)`. Actual binding enforced: `team.id.is_a?(Integer)` only, verified in the schema at [1](#0-0) . There is no `find_or_create_by!(github_id: ..., organization: ...)` compound key and no post-lookup assertion that `team.organization == params.organization.login`, as seen in [2](#0-1) .

`Team#github_id` is a plain integer GitHub team id, globally unique per GitHub, not scoped to Shipit's tenant model in the lookup — `find_or_create_by!` only matches on `github_id`. If a `Team` row already exists (created earlier for a legitimate org, e.g. one of `Shipit.github_teams` used by `User#authorized?` at [3](#0-2) ), any subsequent `membership` webhook carrying the same numeric `team.id` — regardless of which organization it names — resolves to that same row. `team.organization = params.organization.login` inside the `find_or_create_by!` block only runs on **creation**, not when the record already exists, so on the "match" path the attacker's `organization.login` is silently discarded and the pre-existing (victim) team is used.

`process` then does `team.add_member(member)` with `member = User.find_or_create_by_login!(params.member.login)`, both attacker-controlled fields from the webhook payload, at [4](#0-3) .

Attacker's request: any GitHub organization that has a Shipit GitHub App installed (a normal, unprivileged tenant) can trigger a real `membership` webhook (e.g., by adding a bot account to one of their own GitHub teams whose numeric id happens to collide with, or is guessed to equal, another tenant's team id) and can also freely choose the `member.login` value that GitHub embeds. `verify_signature` at [5](#0-4)  only proves the payload was signed by *some* organization's installed GitHub App — it does not prove that organization owns the `team.id` referenced inside the payload. The `ExplicitParameters` schema's `Integer` type only performs numeric coercion (e.g. `'48' -> 48`), which is exactly what an integer DB column comparison would already do; it adds no ownership restriction, confirming the audit's premise that the type check is "false confidence" with respect to cross-org isolation.

### Impact Explanation
A successful match lets an unprivileged organization's webhook add an arbitrary GitHub login as a `member` of a `Team` record belonging to a different, already-provisioned organization. If that `Team` is referenced by `Shipit.github_teams` (used by `User#authorized?`), this is escalation into `Shipit.github_teams` authorization — a listed High-severity impact — because the injected `member` user would subsequently pass `authorized?` and gain whatever privileges Shipit grants to members of that team. This is repeatable per membership event and is not limited to one repository; it can target any `Team` row already present in the database, independent of the attacking org's own repositories.

### Likelihood Explanation
Preconditions: the attacker must control (or be a member of) some GitHub organization that has Shipit's GitHub App installed — this is the normal, low-privilege state the threat model already grants ("any GitHub user ... can ... emit webhooks from a repository they own"). The attacker also needs the numeric GitHub team id of the victim's team, which GitHub team ids are small sequential integers and may be discoverable/guessable, but this is not proven with certainty here (I did not find code in this engine that leaks victim team ids, so exact discoverability is an assumption, not a demonstrated fact). No secrets, sessions, or `Shipit.github_teams` membership are required to send the webhook itself.

### Recommendation
Change the lookup to be scoped to the organization as well as the github id, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and/or add an explicit guard that raises/discards the event when an existing `Team` with that `github_id` has a different `organization` than the payload's `organization.login`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub required)
test "membership handler does not let another organization mutate an existing team by github_id collision" do
  victim_team = Shipit::Team.create!(github_id: 48, organization: 'victim-org', slug: 'core', name: 'Core')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 48, 'name' => 'core', 'slug' => 'core', 'url' => 'https://api.github.com/teams/48' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker-controlled-user' },
  }

  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  victim_team.reload
  # BROKEN BINDING: the team resolved still belongs to 'victim-org', not 'attacker-org',
  # yet the attacker-controlled member was added to it.
  assert_equal 'victim-org', victim_team.organization
  assert_includes victim_team.members.map(&:login), 'attacker-controlled-user'
end
```

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else

          end
