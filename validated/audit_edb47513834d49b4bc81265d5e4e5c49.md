### Title
Reusable L1 Bitcoin lockup proofs allow double-counting staked sats in `pox-5.clar` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
The pox-5 L1-lockup verification path (`verify-l1-lockups` / `validate-l1-lockup`) only de-duplicates a Bitcoin outpoint *within a single call* via a locally-built `seen-outpoints` list that starts empty on every invocation. There is no persistent, contract-level map recording which Bitcoin outpoints have already been consumed to credit sats. This mirrors the "infinite approve" bug class root cause — a value (there, an ERC20 allowance amount; here, a Bitcoin-locked amount) is checked against a caller-supplied/ephemeral state instead of a durable, monotonic record, allowing the same underlying value to be reused across independent calls.

### Finding Description
`verify-l1-lockups` builds its de-dup accumulator fresh on each call: [1](#0-0) 

The fold step `validate-l1-lockup` checks the outpoint (`txid`, `output-index`) against `seen-outpoints`, which is only the list accumulated *during this same call*: [2](#0-1) 

A repo-wide search for any persistent map that would record already-consumed outpoints across separate transactions (e.g. `used-outpoints`, `global-lockup-outpoints`, a `define-map` keyed by `{txid, output-index}`) returned no matches outside of this same local accumulator logic in `pox-5.clar`. This means that, as far as I was able to verify, nothing prevents a staker from calling the function that invokes `verify-l1-lockups` (register-bond/stake path) a second time with the exact same Bitcoin transaction/output proof, crediting the same real-world locked sats to their stake (or to a second bond/reward-cycle) more than once — with no new BTC ever being locked for the second credit.

I was unable to fully trace, within the available context, the public entry point(s) that call `verify-l1-lockups` (e.g., a `register-bond`/`stake` function) to confirm there isn't some additional persistent bookkeeping performed at that outer layer that I did not see in the retrieved snippets. This is a genuine gap in my verification — the index only surfaced this deduplication logic, not the full call chain wiring it into stake/bond state, so I cannot rule out an external guard I didn't retrieve.

### Impact Explanation
If the outpoint dedup is indeed only local to a single call, this breaks the equality "sats credited via L1 proof == sats actually locked on Bitcoin, counted once." A staker could re-submit the identical BTC lockup proof in a later transaction (or across bonds) to register additional stake/signing weight backed by no additional locked BTC. Per the rules, "sats credited by an L1 proof that were never locked on Bitcoin" and "double-counting a commitment" are explicitly in-scope Critical impacts, since this could unlock signing weight or reward eligibility never actually collateralized.

### Likelihood Explanation
Likelihood cannot be confirmed as concrete without seeing the full call graph (the public function invoking `verify-l1-lockups` and whatever state it writes). If no outer, persistent check exists, this is trivially exploitable by any unprivileged staker who resubmits their own valid, unlock-height-satisfying proof.

### Recommendation
Add a durable, contract-level map (e.g., `consumed-l1-outpoints: {txid, output-index} -> bool`) that is checked and updated (via `map-insert`, asserting it wasn't already present) inside `validate-l1-lockup`, so each Bitcoin outpoint can only ever be credited once across the contract's lifetime, not merely once per call.

### Proof of Concept
Not fully constructible from the retrieved context alone, since the outer public function that calls `verify-l1-lockups` and persists its result was not available in my search results. Conceptually: an attacker calls the stake/bond-registration function once with a valid L1 lockup proof to get sats credited, then calls it again (or against a second bond) with the identical `tx`/`output-index`/`header`/`leaf-hashes` payload; because `seen-outpoints` is reinitialized to `(list)` on every call, `validate-l1-lockup` would pass again and re-credit the sum, assuming no other persistent guard exists in the surrounding function.

**Caveat:** Due to index size limits, I could not retrieve the full public entry-point function(s) (e.g., `register-bond`/`stake`) that call `verify-l1-lockups`, so I cannot fully confirm whether an outer persistent check nullifies this issue. I recommend starting a full Devin session with complete file access to `pox-5.clar` to trace the entire call chain and confirm whether a global outpoint-consumption map exists elsewhere before treating this as conclusively exploitable.
