### Title
Webhook signature is verified against the organization in `repository.owner.login`, but every event handler acts on the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization used to validate the HMAC signature solely from `params.dig('repository','owner','login')` (falling back to `organization.login`). Every downstream `Shipit::Webhooks::Handlers::Handler` (push, pull_request, membership, etc.) instead resolves the actual `Repository`/`Stack`/`Team` to mutate from a *different, independently attacker-controlled field in the same JSON body*: `payload.dig('repository','full_name')` (or `organization.login` for membership). In a multi-tenant Shipit install (multiple GitHub orgs configured, each with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), the field that is cryptographically authenticated and the field that is actually acted upon are not the same field and are not required to agree.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is read straight out of the untrusted JSON body and used only to pick which org's `webhook_secret` verifies the HMAC (`lib/shipit/github_app.rb#verify_webhook_signature`). Nothing ties this org to the `repository.full_name` that handlers use to find the target record:

```ruby
# app/models/shipit/webhooks/handlers/handler.rb
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end

The binding that should hold is: *organization whose secret authenticated the request* == *repository owner that gets written to*. Both `repository.owner.login` and `repository.full_name` are ordinary fields inside the same JSON body the attacker fully controls and signs; there is no cross-check that `full_name`'s owner segment matches `owner.login`, nor that the org resolved for signature lookup is the org that owns the target repository/team.

Concretely, an attacker who administers *any* GitHub organization/App installation configured in this Shipit instance (and therefore legitimately knows that org's `webhook_secret`) can craft a payload where:
- `repository.owner.login` = `"attacker-org"` (drives which `webhook_secret` is used to verify)
- `repository.full_name` = `"victim-org/victim-repo"` (drives which `Repository`/`Stack` the handler mutates)

`Shipit.github(organization: "attacker-org")` resolves to the attacker's own app config and its own `webhook_secret`, which the attacker legitimately possesses, so `verify_webhook_signature` succeeds against a payload the attacker forged/signed themselves; but `PushHandler#stacks` / `Repository.from_github_repo_name` then act on `victim-org/victim-repo`. Similarly `MembershipHandler` reads `params.team.id` / `params.organization.login` / `params.member.login` straight from the body and calls `team.add_member(member)`, letting the same forged, self-signed payload add an arbitrary GitHub user to any `Shipit::Team` (including teams mapped into `Shipit.github_teams` authorization) regardless of which org's secret validated the request. This is the same trust-binding-mismatch bug class as the `FarmAccounting` report: a value used to satisfy a "safety"/authentication check (`repository_owner` for signature org lookup / the reward amount checked against `uint176`) is not the same value that downstream logic actually operates on (`repository.full_name` used to pick the mutated record / the FPT computation that overflows because the checked value diverges from the one used in `farmedSinceCheckpointScaled`).

### Impact Explanation
This breaks the "organization that authenticated == repository/team that is written" binding required by the scope rules. It allows escalation into `Shipit.github_teams` authorization (via `MembershipHandler` adding a `member` to a `team`, forged with a secret the attacker legitimately controls for their own org) and cross-organization writes into another tenant's stacks/pull-requests/review-stacks via `PushHandler`, `PullRequest::*Handler`, and `LabelCapturingHandler`, all of which resolve their target purely from `payload.dig('repository','full_name')` independent of which org's secret was used to authenticate.

### Likelihood Explanation
Requires the attacker to be an administrator of at least one GitHub org/App installation configured on the shared Shipit instance (so they know that org's `webhook_secret`) - a realistic condition for any multi-tenant deployment where multiple independent GitHub orgs share one Shipit instance, which the engine explicitly supports (`config/secrets.development.shopify.yml` documents multiple orgs each with a distinct `webhook_secret`). No GitHub App private key, `ApiClient` token, or Shipit session is required — only control of a legitimately-configured organization's own webhook secret plus the ability to send an arbitrary HTTP POST to `/webhooks`.

### Recommendation
Require that the organization used to select the verification secret is the same organization that owns the `repository.full_name` (or `organization.login`) actually acted upon, e.g. verify that `full_name.split('/').first == repository_owner` before dispatching to handlers, or resolve the target `Repository` using the same trusted `repository_owner` value rather than a second untrusted field, rejecting the payload if they disagree.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `attacker-org` (webhook_secret known to the attacker, who administers that org/app) and `victim-org` (hosting `shipit_stacks` the attacker doesn't control).
2. Attacker crafts a `membership` (or `push`) webhook body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/some-repo"}
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: membership`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully using the attacker's own known secret.
5. `MembershipHandler#process` runs `find_or_create_team!` with `organization: "victim-org"` and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`, granting the attacker membership in a team scoped to `victim-org`, entirely authenticated by a secret the attacker controls for an unrelated org.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'

          end
        end
