Confirmed: `pallet-child-bounties` uses only `frame_support::traits::Currency` for its account-balance movement (`substrate/frame/child-bounties/src/lib.rs:67-71`), unlike `pallet-bounties`, which was patched with a `TransferAllAssets` mechanism and a dedicated `reclaim_bounty_funds` extrinsic (`substrate/frame/bounties/src/lib.rs:1047-1090`, `prdoc/pr_11045.prdoc`) specifically to fix "funds stranded in a closed bounty's account" (issue #10996). `close_child_bounty`'s `impl_close_child_bounty` only ever moves the native `Currency::free_balance` of the child-bounty derived account to the parent bounty account (`substrate/frame/child-bounties/src/lib.rs:934-946`), and once the child bounty is closed, the storage entry (`ChildBounties`) is removed (`substrate/frame/child-bounties/src/lib.rs:951`) with no remaining extrinsic that ever revisits that now-orphaned `child_bounty_account_id`.

### Title
Child-bounty derived accounts permanently strand non-native assets after closure - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`pallet-child-bounties` derives a unique sovereign account per child bounty (`child_bounty_account_id`) that is fully controlled by the pallet's own logic and never exposed for arbitrary transfers by the depositor/curator. `impl_close_child_bounty`, invoked by `close_child_bounty`, only sweeps the account's native `Currency` free balance back to the parent bounty account, then deletes the child bounty's storage record. Any other fungible asset (or accidental/child‑bounty‑external native transfer received after the sweep) held by that derived account becomes permanently unreachable, because no other extrinsic in this pallet, or in `pallet-bounties`, ever addresses a *child*-bounty-derived account again once its parent `ChildBounties` entry is gone.

### Finding Description
`child_bounty_account_id(parent_bounty_id, child_bounty_id)` (referenced at `substrate/frame/child-bounties/src/lib.rs:937-938`, `substrate/frame/child-bounties/src/tests.rs:596`) is a deterministic, publicly computable `AccountId` (via `AccountIdConversion`). Because it is a normal account, it is a valid destination for any token transfer — native `Balances::transfer`, `pallet-assets` transfer, or an airdrop distributed by an unrelated protocol/DAO based on address participation, exactly analogous to how `Cooler.sol`'s owner/borrower deposit-holding contract can receive an externally distributed governance-token reward it has no function to claim.

When `close_child_bounty` executes, `impl_close_child_bounty` (`substrate/frame/child-bounties/src/lib.rs:894-960`) only performs:
```
let balance = T::Currency::free_balance(&child_bounty_account);
let transfer_result = T::Currency::transfer(&child_bounty_account, &parent_bounty_account, balance, AllowDeath);
```
This sweeps only the pallet's native `Currency` type. It does not use anything resembling `pallet-bounties`'s `T::TransferAllAssets::force_transfer_all_assets` (`substrate/frame/bounties/src/lib.rs:921-924`, `1077-1080`), which was added specifically to handle "other fungible assets configured via the `TransferAllAssets` associated type" for bounty accounts (`prdoc/stable2603/pr_10399.prdoc`... actually `prdoc/pr_11045.prdoc`, and `prdoc/stable2603/pr_10729.prdoc` "Bounties return balance and assets on close"). `pallet-child-bounties`'s `Config` in this codebase imports only `frame_support::traits::Currency` (`substrate/frame/child-bounties/src/lib.rs:67-71`) — there is no equivalent asset-sweep trait bound.

Once `*maybe_child_bounty = None;` executes (`substrate/frame/child-bounties/src/lib.rs:951`), the `ChildBounties` storage entry is gone, and `close_child_bounty`/`impl_close_child_bounty` can never be invoked again for that `(parent_bounty_id, child_bounty_id)` pair (`ensure_bounty_active`/`ChildBounties::try_mutate_exists` requires the record to still exist). There is no permissionless `reclaim_child_bounty_funds`-style extrinsic mirroring `pallet-bounties::reclaim_bounty_funds` (`substrate/frame/bounties/src/lib.rs:1047-1090`) for the child-bounty derived account. This mirrors precisely the root-cause pattern in the external report: an owner-controlled/derived account that receives value it did not solicit, with a permissioned or narrow sweep path (`delegate`/native-only transfer) but no general-purpose withdrawal for anything beyond the pallet's expected asset type.

### Impact Explanation
Any assets other than the pallet's configured native `Currency` that land in a child-bounty derived account (via `pallet-assets`, an external airdrop, or a delayed/late transfer that arrives after the native sweep in `close_child_bounty`) are permanently locked, unrecoverable by governance, the parent bounty curator, or the treasury. This is a direct, irrecoverable freezing of funds, matching the reported Medium-severity impact class ("voting reward locked in Cooler forever") rather than a Critical loss/theft, because no attacker gains funds — value is simply stranded. Given that `pallet-bounties` explicitly patched this exact bug class for its top-level bounty accounts (issue #10996 / PR #11045), the omission of the same fix for `pallet-child-bounties`'s per-child accounts is a real, demonstrable gap in the current codebase, not a hypothetical.

### Likelihood Explanation
Likelihood is Low-to-Medium: a runtime must (a) actually configure `pallet-child-bounties` and (b) have `pallet-assets` or another fungible in use whose IDs get distributed to holders/derived accounts (e.g., governance airdrops, incentive campaigns based on treasury-derived account activity), or a well-meaning/careless external actor sending assets directly to the known deterministic child-bounty address. No privileged role or malicious behavior is required — the attacker/reporter here is simply an ordinary chain user or external protocol distributing tokens; the "attack" is passive (funds get stuck), matching the Cooler.sol analog exactly.

### Recommendation
Extend `pallet-child-bounties`'s `Config` with the same kind of `TransferAllAssets` associated type used in `pallet-bounties` (`substrate/frame/bounties/src/lib.rs`), and add a permissionless `reclaim_child_bounty_funds`-style extrinsic (or extend `impl_close_child_bounty` to call it) that sweeps all configured assets — not just the native `Currency` — from a child bounty's derived account to the parent bounty account (or treasury) both at closure time and afterward for any account whose `ChildBounties` entry no longer exists, symmetric to `pallet-bounties::reclaim_bounty_funds` (`substrate/frame/bounties/src/lib.rs:1058-1090`).

### Proof of Concept
I was not able to execute a live Rust/FRAME integration test in this environment (no filesystem/terminal access, ask-only mode); the analysis above is based on static code review of `substrate/frame/child-bounties/src/lib.rs` and its `Config` trait bounds (`frame_support::traits::Currency` only, `substrate/frame/child-bounties/src/lib.rs:67-71`), contrasted with the fixed `pallet-bounties::reclaim_bounty_funds` extrinsic (`substrate/frame/bounties/src/lib.rs:1058-1090`) and its regression test `reclaim_bounty_funds_works_after_accidental_refund` (`substrate/frame/bounties/src/tests.rs:2058-2096`), which explicitly proves the analogous "stranded funds in closed bounty account" scenario is exploitable and was worth a dedicated fix for `pallet-bounties`. 	fn impl_close_child_bounty(
		parent_bounty_id: BountyIndex,
		child_bounty_id: BountyIndex,
	) -> DispatchResult {
		ChildBounties::<T>::try_mutate_exists(
			parent_bounty_id,
			child_bounty_id,
			|maybe_child_bounty| -> DispatchResult {
				let child_bounty =
					maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

				match &child_bounty.status {
					ChildBountyStatus::Added | ChildBountyStatus::CuratorProposed { .. } => {
						// Nothing extra to do besides the removal of the child-bounty below.
					},
					ChildBountyStatus::Active { curator } => {
						// Cancelled by parent curator or RejectOrigin,
						// refund deposit of the working child-bounty curator.
						let _ = T::Currency::unreserve(curator, child_bounty.curator_deposit);
						// Then execute removal of the child-bounty below.
					},
					ChildBountyStatus::PendingPayout { .. } => {
						// Child-bounty is already in pending payout. If parent
						// curator or RejectOrigin wants to close this
						// child-bounty, it should mean the child-bounty curator
						// was acting maliciously. So first unassign the
						// child-bounty curator, slashing their deposit.
						return Err(BountiesError::<T>::PendingPayout.into());
					},
				}

				// Revert the curator fee back to parent bounty curator &
				// reduce the active child-bounty count.
				ChildrenCuratorFees::<T>::mutate(parent_bounty_id, |value| {
					*value = value.saturating_sub(child_bounty.fee)
				});
				ParentChildBounties::<T>::mutate(parent_bounty_id, |count| {
					*count = count.saturating_sub(1)
				});

				// Transfer fund from child-bounty to parent bounty.
				let parent_bounty_account =
					pallet_bounties::Pallet::<T>::bounty_account_id(parent_bounty_id);
				let child_bounty_account =
					Self::child_bounty_account_id(parent_bounty_id, child_bounty_id);
				let balance = T::Currency::free_balance(&child_bounty_account);
				let transfer_result = T::Currency::transfer(
					&child_bounty_account,
					&parent_bounty_account,
					balance,
					AllowDeath,
				); // Should not fail; child bounty account gets this balance during creation.
				debug_assert!(transfer_result.is_ok());

				// Remove the child-bounty description.
				ChildBountyDescriptionsV1::<T>::remove(parent_bounty_id, child_bounty_id);

				*maybe_child_bounty = None;

				Self::deposit_event(Event::<T>::Canceled {
					index: parent_bounty_id,
					child_index: child_bounty_id,
				});
				Ok(())
			},
		)
	}

		/// Reclaim funds stranded in a closed bounty's account back to the treasury.
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
	}

#[test]
fn reclaim_bounty_funds_works_after_accidental_refund() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Full lifecycle: propose → approve → fund → curator → award → claim
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		let fee = 4;
		Balances::make_free_balance_be(&4, 10);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, fee));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));
		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));
		go_to_block(5);
		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		// Bounty is now fully closed; verify it is gone from storage.
		assert!(pallet_bounties::Bounties::<Test>::get(0).is_none());

		let bounty_account = Bounties::bounty_account_id(0);
		// Account should already be empty after claim.
		assert_eq!(Balances::free_balance(&bounty_account), 0);

		// Simulate someone accidentally sending funds to the closed bounty account.
		Balances::make_free_balance_be(&bounty_account, 25);
		assert_eq!(Balances::free_balance(&bounty_account), 25);

		let treasury_before = Treasury::pot();

		// Dust the account.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(99), 0));
		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		assert_eq!(Balances::free_balance(&bounty_account), 0);
		assert!(Treasury::pot() > treasury_before);
	});
}
