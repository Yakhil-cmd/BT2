### Title
Single failed sync (attacker-controlled ref content) causes permanent process termination, denying all future syncs - (File: main.go)

### Summary
The reported bug class is a single malicious item permanently blocking an entire processing pipeline (`processWithdrawals` in a shared queue, where one poisoned entry with unbounded gas consumption halts all future withdrawals for every user). The closest reachable analog in `git-sync` is the sync-failure/`--max-failures` handling in the main sync loop [1](#0-0) : with the default configuration, a single failed `SyncRepo` call — which can be triggered purely by content at the remote ref that an attacker controls (a corrupt/oversized object, an unreachable or malicious submodule URL, a fsck failure, etc.) — causes the whole process to call `os.Exit(1)` and never attempt another sync.

### Finding Description
`git-sync`'s main loop repeatedly calls `git.SyncRepo(ctx, syncHooks)` and tracks `failCount`: [2](#0-1) 

`getMaxFailures()` returns `*flMaxFailures`, whose default is `0`: [3](#0-2) 

Because `failCount` starts at `0` and is incremented *before* the check (`failCount++` then `if maxFails >= 0 && failCount >= maxFails`), a single sync failure (`failCount == 1`) already satisfies `1 >= 0` (the default `maxFails`), so `git-sync` exits the process on the very first failure of any kind, unless the operator has explicitly raised `--max-failures` or set it negative.

`SyncRepo` performs several git operations that are driven entirely by content in the tracked repository/ref and can fail for reasons fully under an attacker's control if they can push to (or merge into) the tracked ref, or control a submodule URL referenced by that ref:
- `git fetch` of a corrupt/oversized object or unreachable submodule URL [4](#0-3) 
- `git worktree add` / `git reset --hard` for that hash [5](#0-4) 
- `git submodule update --init [--recursive]`, which can fail if a submodule URL is unreachable, private, or intentionally broken [6](#0-5) 
- `git fsck` sanity checks on the repo/worktree [7](#0-6) 

Any of these failing once is sufficient, by default, to terminate `git-sync` permanently (`os.Exit(1)`) via the loop shown above. In a Kubernetes sidecar deployment (the documented primary use case [8](#0-7) ), the container/pod will restart, re-attempt the same bad ref, fail again immediately, and crash-loop — a persistent denial of sync service until an operator manually intervenes (e.g., changes `--ref`, force-pushes a fix, or raises `--max-failures`). No future good commits are ever synced in the interim, which mirrors the reported bug's impact ("nobody will be able to process any withdrawals" until admin action) even though the underlying mechanism (default flag interacting with attacker-influenced fetch/submodule/fsck failures) is different from a gas-griefing loop.

### Impact Explanation
This is a "persistent sync denial" as defined by the acceptance criteria: with default settings, one attacker-influenced bad commit/ref/submodule reference permanently stops the entire sync sidecar from making further progress, requiring operator intervention to resume — directly analogous to the "permanent DOS on `processWithdrawals`" class in the source report (a single bad queue entry blocks all subsequent processing until an admin/operator manually clears it).

### Likelihood Explanation
Reachability depends on the deployment: `git-sync` is normally pointed at a repo/ref the operator trusts, but the attack surface exists whenever (a) the tracked branch/ref accepts contributions from less-trusted parties (e.g., PR-merge workflows, mirrors of third-party repos), or (b) submodule URLs reference third-party infrastructure that can be made unreachable or return corrupt data. This requires `--max-failures` to be left at its default (`0`) — a very common configuration, since the flag is opt-in to relax. Given this, the likelihood is moderate: it requires no special privileges beyond the ability to get a bad commit merged/pushed to the tracked ref or control of a referenced submodule remote, but it does depend on default flag usage and on the deployment's trust model for the ref's content.

### Recommendation
- Change the default `--max-failures` behavior so that a single transient/content-triggered failure does not immediately terminate the process (e.g., default to retry a few times before aborting, or make `0` mean "retry forever" instead of "abort after first failure").
- Ensure the semantics of `failCount >= maxFailures` match user expectations of "number of failures **allowed**" (currently `--max-failures=0` allows *zero* failures, i.e., it aborts on the very first one, which is easy to misconfigure).
- Document clearly, and/or emit a distinguishing exit code/log message, when termination is due to exceeding `--max-failures` from content-driven sync failures (fetch/fsck/submodule) versus fatal configuration errors, so operators/orchestrators can decide whether to auto-restart or page a human.

### Proof of Concept
1. Deploy `git-sync` with default flags against a `--repo`/`--ref` where a low-trust contributor can merge/push commits (e.g., a branch protected only by review, or a repo with a submodule pointing at third-party infrastructure).
2. Attacker merges/pushes a commit that:
   - references a submodule URL that will fail to clone (deleted/private/unreachable repo), or
   - contains a corrupt git object that fails `git fsck --connectivity-only`, or
   - is force-pushed in a way that breaks the shallow-fetch invariants assumed by `git.fetch`.
3. On the next `--period` tick, `SyncRepo` fails once (`failCount` becomes `1`).
4. Because `--max-failures` defaults to `0`, the check `maxFails >= 0 && failCount >= maxFails` (`0 >= 0 && 1 >= 0`) is true immediately, and `main()` calls `os.Exit(1)` [9](#0-8) .
5. In Kubernetes, the sidecar container restarts, re-fetches the same bad ref, fails identically, and exits again — a crash-loop that never converges without operator action, denying sync of any subsequent (good) commits as well.

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}

// fetch retrieves the specified ref from the upstream repo.
func (git *repoSync) fetch(ctx context.Context, ref string) error {
	git.log.V(2).Info("fetching", "ref", ref, "repo", redactURL(git.repo))

	// Fetch the ref and do some cleanup, setting or un-setting the repo's
	// shallow flag as appropriate.
	args := []string{"fetch", git.repo, ref, "--verbose", "--no-progress", "--prune", "--no-auto-gc"}
	if git.depth > 0 {
		args = append(args, "--depth", strconv.Itoa(git.depth))
	} else {
		// If the local repo is shallow and we're not using depth any more, we
		// need a special case.
		shallow, err := git.isShallow(ctx)
		if err != nil {
			return err
		}
		if shallow {
			args = append(args, "--unshallow")
		}
	}
	if git.filter != "" {
		args = append(args, "--filter", git.filter)
	}
	if _, _, err := git.Run(ctx, git.root, args...); err != nil {
		return err
	}

	return nil
}
