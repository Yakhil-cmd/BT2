### Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, the field used to select which GitHub App/`webhook_secret` verifies a webhook's HMAC signature (`repository.owner.login` or `organization.login`) is not the same field used by the event handlers to decide which `Repository`/`Stack` the event actually acts on (`repository.full_name`). Both fields come from the same attacker-controlled JSON body, so a party who legitimately controls one configured organization's webhook secret can forge a payload whose signature checks out for their own org while `repository.full_name` points at a different, unrelated organization's repository, causing Shipit to act on that other repository.

### Finding Description
`WebhooksController#verify_signature` selects the verification config using a value read directly out of the untrusted, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This `repository_owner` value is used only to pick which `GithubApp` instance (and therefore which `webhook_secret`) `verify_webhook_signature` checks the `X-Hub-Signature` against: [3](#0-2) 

Once the signature is accepted, event handlers (`PushHandler`, `CheckSuiteHandler`, etc.) determine *which repository/stack to act on* using an entirely different field of the same payload, `repository.full_name`, via `Handler#repository_name`: [4](#0-3) [5](#0-4) [6](#0-5) 

Nothing enforces that `repository.owner.login` (used to pick the signing secret) and `repository.full_name`'s owner segment (used to resolve the target `Repository`/`Stack`) refer to the same organization. Shipit explicitly supports configuring several GitHub organizations, each with its own App/`webhook_secret`, in the same installation: [7](#0-6) 

This is the direct analog of the reported bug class: the value that is verified/checked (`repository.owner.login`, driving which secret authenticates the request) is not the value that the code subsequently acts on (`repository.full_name`, driving which repository is written to) — an "organization that authenticated versus the repository that is written" mismatch.

### Impact Explanation
An attacker who legitimately administers a GitHub App/webhook installed on **one** configured organization (org-B) in a multi-org Shipit instance can send a webhook whose `repository.owner.login`/`organization.login` is `"org-B"` (so the signature is verified and accepted using org-B's real secret) but whose `repository.full_name` is set to `"org-A/some-repo"`. `WebhooksController#verify_signature` passes, and the dispatched handler resolves the target stack purely from `repository.full_name`, so the forged event is processed against org-A's repository/stack — a cross-organization write performed by an entity that never authenticated for org-A. Depending on the event type this can trigger unintended `GithubSyncJob` runs, injected commit statuses, or check-run refreshes on a stack/repository the attacker does not control, satisfying the "cross-repository writes" impact class.

### Likelihood Explanation
This requires: (1) the Shipit instance to be configured with more than one GitHub organization (a documented, supported configuration), and (2) the attacker to control a legitimate GitHub App/webhook secret for at least one of those configured organizations. Given those preconditions — which do not require compromising any Shipit-internal secret, session, or the *target* organization's credentials — the forgery itself is a simple crafted POST with a correctly-computed HMAC for the attacker's own org. Likelihood is moderate and scoped to multi-org deployments.

### Recommendation
After verifying the signature, cross-check that the organization used to select the verifying secret (`repository_owner`) matches the organization embedded in `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to any handler; reject the request if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.example.yml`).
2. As the administrator of the `org-b` GitHub App, craft a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "org-b" }, "full_name": "org-a/target-repo" }
   }
   ```
3. Sign the raw body with `org-b`'s real `webhook_secret` and send it as `X-Hub-Signature` to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-b")` (from `repository.owner.login`) and the signature validates successfully.
5. `PushHandler#process` resolves the target via `Handler#repository_name` (`repository.full_name` = `"org-a/target-repo"`), locating `org-a`'s stacks and invoking `stack.sync_github(expected_head_sha: ...)` — acting on `org-a`'s repository despite the request never being authenticated for `org-a`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
