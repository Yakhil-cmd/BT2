### Title
Inline-dict comma-split in `extract_frontmatter` silently truncates/corrupts `pattern` values, allowing disguised hookify rule files to review as strict but enforce a broken/weaker regex - ([File: plugins/hookify/core/config_loader.py])

### Summary
`extract_frontmatter`'s inline-dict parsing branch splits a `- field: ..., operator: ..., pattern: ...` list item on every comma with no awareness of commas embedded in the `pattern` value itself. Any comma inside a `pattern` (e.g. a regex quantifier `{0,1}`, an alternation list, or a comma-delimited pattern) splits the pattern into fragments; fragments without a `:` are silently dropped, so the parsed `Condition.pattern` differs from the pattern actually written in the file, with no warning or error surfaced anywhere in the load path.

### Finding Description
In `extract_frontmatter` (plugins/hookify/core/config_loader.py:164-171), when a list item contains both `:` and `,`, the code does:
```
for part in item_text.split(','):
    if ':' in part:
        k, v = part.split(':', 1)
        item_dict[k.strip()] = v.strip()...
``` [1](#0-0) 

This unconditionally splits the entire compact list item on `,`, including commas that are part of the `pattern` value (e.g. `pattern: rm -rf /(bin|etc|home){0,1}`). The fragment after the embedded comma (`1}`) has no `:` and is silently discarded, so `item_dict['pattern']` becomes `\d{0` / `/(bin|etc|home){0` instead of the intended pattern - with no exception, no stderr warning, nothing logged by `load_rule_file` (plugins/hookify/core/config_loader.py:244-274) since parsing "succeeds".

This mis-parsed `Condition` is then handed to `RuleEngine._regex_match`, which compiles it via `compile_regex` and calls `re.search` (plugins/hookify/core/rule_engine.py:256-273). Python's `re.compile` typically still accepts an unbalanced `{0` (treats it as literal text rather than raising `re.error`), so the rule loads and appears "active", but the regex it actually enforces is semantically different from - and typically weaker/narrower than - what a human reviewer reads in the markdown file.

Since `.claude/hookify.*.local.md` files are loaded unconditionally by `load_rules()` (glob over `.claude/hookify.*.local.md`, plugins/hookify/core/config_loader.py:198-241) and are invoked by the `PreToolUse`/`PostToolUse` hooks (`pretooluse.py`, `posttooluse.py`) to gate `action: block` enforcement (e.g. blocking `rm -rf`, blocking secrets in edits), this file is exactly the kind of "ordinary repository content" that ships with a repo and is trusted implicitly once checked out. An attacker who contributes such a rule file (e.g. via a pull request adding/adjusting a "security" rule, exploiting the fact that reviewers read the markdown source, not the parsed runtime object) can craft a pattern containing an innocuous-looking comma so that the file *reads* as a correctly-scoped blocking rule during review, while the actual enforced regex is truncated/garbled and fails to match the dangerous command/content it was supposed to catch - silently neutralizing the `action: block` protection for every collaborator who later opens the repo in Claude Code.

No existing validation catches this: `load_rule_file`'s broad `except` clauses only catch I/O or attribute errors, not semantic pattern corruption; there is no round-trip check comparing the parsed condition against the literal file text, and `_regex_match`'s `try/except re.error` only guards against outright invalid regex syntax, not silently-altered-but-still-valid regex.

### Impact Explanation
This is a trust-boundary/hook-enforcement bypass reachable purely from ordinary repository content (a hookify rule `.md` file). It lets an attacker disguise a defanged security rule as a strict one in code review, causing `action: block` hookify rules (e.g. blocking dangerous `rm -rf`, blocking secrets/API keys in edits) to fail open for legitimate users, enabling unauthorized command execution / file mutation that the project's own hook policy was supposed to prevent, without any error being surfaced.

### Likelihood Explanation
The precondition is simply that a hookify rule file using the compact inline-list syntax (`- field: x, operator: y, pattern: z`) contains any pattern with an embedded comma — a very common regex construct (`{m,n}` quantifiers, comma-separated alternation lists). No special privileges are needed beyond the ability to add/modify a `.claude/hookify.*.local.md` file that ends up in a shared repository (e.g. via a merged PR), which is squarely within "ordinary repository content" per the audit scope. The bug is deterministic and trivially reproducible.

### Recommendation
Replace the naive `split(',')` inline-dict parser with a proper tokenizer/YAML-aware parser (or use `yaml.safe_load` for the frontmatter block) that respects values containing commas, or require the `pattern` field to always be quoted and parse quoted strings correctly (splitting on commas only outside quotes). At minimum, add a round-trip validation: after parsing, verify that `Condition.pattern` is a substring of the raw list-item text following `pattern:`, and reject/log a hard error if not, rather than silently proceeding with a truncated pattern.

### Proof of Concept
Unit test to add to `plugins/hookify/core/config_loader.py` tests:
```python
def test_inline_condition_pattern_with_comma_is_corrupted():
    content = """---
name: block-bin-etc-home-rm
enabled: true
event: bash
action: block
conditions:
  - field: command, operator: regex_match, pattern: rm -rf /(bin|etc|home){0,1}
---

Blocks rm -rf on critical dirs.
"""
    frontmatter, _ = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, "msg")
    parsed_pattern = rule.conditions[0].pattern

    # Expected (what a reviewer reads in the file):
    expected = r"rm -rf /(bin|etc|home){0,1}"

    # Bug: parser truncates at the embedded comma, dropping ",1}"
    assert parsed_pattern != expected
    assert parsed_pattern == r"rm -rf /(bin|etc|home){0"
```
Follow-up integration assertion showing the security consequence via `RuleEngine`:
```python
def test_corrupted_pattern_fails_to_block_intended_command():
    engine = RuleEngine()
    rule = Rule(
        name="block-rm", enabled=True, event="bash", action="block",
        conditions=[Condition(field="command", operator="regex_match",
                               pattern=r"rm -rf /(bin|etc|home){0")]  # corrupted pattern
    )
    result = engine.evaluate_rules([rule], {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /home"}
    })
    # Reviewer expected this to be blocked; corrupted pattern lets it through
    assert result == {}
```
Both assertions demonstrate that the on-disk rule text and the enforced behavior diverge, with the block silently failing to trigger.
