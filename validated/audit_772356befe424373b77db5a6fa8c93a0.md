### Title
`path_filter` extension checks in `SECURITY_PATTERNS` are case-sensitive and suffix-only, letting mixed-case or double-extension paths silently skip the security reminder - ([File: plugins/security-guidance/hooks/patterns.py])

### Summary
`check_patterns()` normalizes the tool-call path only via `.lstrip("/")` and then runs each rule's `path_filter` lambda (e.g. `child_process_exec`'s `lambda p: p.endswith(_JS_EXTS)`, where `_JS_EXTS` is all-lowercase) directly against that raw-case path, wrapped in a bare `try/except: continue`. An attacker who controls the file path Claude writes to (e.g. `payload.JS` or `payload.js.txt`) can make the `path_filter` evaluate `False` for a file that is/will be treated as executable JavaScript, causing the `child_process_exec` (and similarly `os_system_injection`, `pickle_deserialization`, `eval_injection`) reminder to never fire.

### Finding Description
In `plugins/security-guidance/hooks/security_reminder_hook.py`, `check_patterns()` does: [1](#0-0) 
`normalized_path` is only `file_path.lstrip("/")` — no case-folding, no extension canonicalization. It then calls `pattern["path_filter"](normalized_path)` inside a bare `try/except: continue`, which silently disables the rule on any exception, but more importantly is silently disabled on the ordinary case where `endswith()` legitimately returns `False`.

The `path_filter` in `patterns.py` for `child_process_exec` is: [2](#0-1) [3](#0-2) 
`_JS_EXTS` is a tuple of all-lowercase extensions, and `str.endswith` is case-sensitive and matches only the literal trailing suffix. Therefore:
- `payload.JS` → `endswith((".js", ...))` is `False` (case mismatch) even though many filesystems (macOS default, Windows) and `node`/JS tooling treat `.JS` identically to `.js`.
- `payload.js.txt` → `endswith((".js", ...))` is `False` because the true trailing suffix is `.txt`, even though `node payload.js.txt` or a bundler/loader configured to execute-by-content would still run it as JavaScript, and Claude/human reviewers frequently trust the apparent `.js` component of a double extension.

Because the `child_process_exec` rule requires `path_filter` to return `True` before the `regex`/`substrings` check for `exec(`/`child_process.exec`/`execSync(` even runs, a `False` result causes the whole rule to be skipped for that write — the security reminder is never injected into `additionalContext`, regardless of the actual dangerous content in the file.

### Impact Explanation
This is a fail-open path in a defense-in-depth mechanism: `SECURITY_PATTERNS` entries only add advisory `additionalContext` warnings on `PostToolUse` for `Write`/`Edit`/`MultiEdit` — they do not block or deny the tool call. The scoped impact is that Claude does not receive a command-injection warning while writing/editing a file containing `exec(`, `child_process.exec`, or `execSync(` if the attacker (via a task/prompt that steers the target file path) chooses a case-mangled or double extension, reducing the plugin's guidance coverage for genuinely executable JS/TS files. It does not enable command execution, approval bypass, or workspace escape by itself — it only suppresses an educational nudge that could otherwise have prompted Claude to avoid/fix the injection risk.

### Likelihood Explanation
Trivial to trigger and fully reachable by an unprivileged attacker who can influence a file path used by an ordinary `Write`/`Edit` operation (e.g., via issue/PR text suggesting a filename, or repository content dictating output filenames). No special privileges, no bypass of approval prompts is required beyond choosing an unusual filename extension. It is deterministic and repeatable for any path that fails an exact-lowercase-suffix `endswith` check.

### Recommendation
Normalize both case and extension detection before invoking `path_filter`/`path_check` lambdas: lowercase the path (or extract `os.path.splitext` result and lowercase it) in `check_patterns()`'s `normalized_path` construction, and consider also checking secondary extensions in multi-dot filenames (e.g., split on all dots and check whether any recognized JS/PY extension token appears) rather than relying solely on `str.endswith`. Additionally, avoid using a blanket `except Exception: continue` around `path_filter` calls without at least debug-logging the exception, since it currently masks both genuine filter logic bugs and this suffix/case mismatch class of issues.

### Proof of Concept
Add a unit test in the `patterns.py` test suite exercising `path_filter` case/extension consistency:
```python
from patterns import SECURITY_PATTERNS

CHILD_PROCESS_FILTER = next(
    p["path_filter"] for p in SECURITY_PATTERNS if p["ruleName"] == "child_process_exec"
)

CASES = [
    "payload.js", "payload.JS", "payload.Js",
    "payload.js.txt", "PAYLOAD.JS", "dir/PAYLOAD.Js",
]

def test_path_filter_case_and_extension_consistency():
    results = {p: CHILD_PROCESS_FILTER(p) for p in CASES}
    # Expected (desired) invariant: filter result should not depend on case,
    # and a double-extension "js.txt" file intended to be executed as JS
    # should still be recognized.
    assert results["payload.js"] == results["payload.JS"] == results["payload.Js"] == True
    # Currently FAILS: results["payload.JS"] is False because _JS_EXTS is lowercase-only.
```
Running this against the current `patterns.py` demonstrates `path_filter("payload.js")` returns `True` while `path_filter("payload.JS")` and `path_filter("payload.js.txt")` return `False`, confirming the case/extension-aliasing bypass of the `child_process_exec` reminder gate.
