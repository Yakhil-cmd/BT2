### Title
Webhook organization used for signature verification is not bound to the repository the payload acts on, allowing cross-organization webhook forgery in multi-app Shipit deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-GitHub-App Shipit configurations, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the request signature against using an attacker-supplied field from the *same unverified* JSON body (`repository.owner.login` / `organization.login`), but the `create` action then processes the *entire* payload — including a possibly different `repository.full_name` — through the event handlers. The organization identity used to authenticate the request is never checked against the repository/stack the payload is ultimately applied to, breaking the binding `verified_organization == acted_upon_repository`.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App config purely from data taken out of the raw request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository','owner','login')`, i.e., a value inside the very payload whose authenticity is being decided. `Shipit.github(organization:)` then looks up the app/webhook_secret configuration keyed by that organization name: [3](#0-2) 

In a "Using Multiple GitHub Applications" deployment (documented and supported: `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), each configured organization has its own, independent `webhook_secret`, and that secret is optional per-organization: [4](#0-3) 

Because `webhook_secret` is optional, `verify_webhook_signature` returns `true` unconditionally for any organization configured without one. Nothing then re-validates that the `repository.owner.login` used to pick the (possibly secret-less) verification context actually matches the `repository.full_name`/`repository` object that `create` hands to the handlers: [5](#0-4) 

Handlers such as `PushHandler` and `StatusHandler` act on whatever `repository`/`sha`/`branches` values are present in the body, independent of which organization's secret was used to authenticate the request: [6](#0-5) [7](#0-6) 

The base `Handler#stacks` resolution (used by `PushHandler`) scopes stacks by the payload's repository data, not by the organization context that passed `verify_signature`, so an event "authenticated" as belonging to organization A can freely reference and mutate stacks belonging to repositories under organization B tracked by the same Shipit instance. This exactly mirrors the reported bug class: a field (`repository_owner`) is used to establish trust, while a different field in the same unauthenticated envelope (`repository.full_name`) is what the business logic actually acts on — with no equality check binding the two.

### Impact Explanation
Where at least one configured organization in a multi-org Shipit deployment has no `webhook_secret` set (an explicitly supported, "optional" configuration per `docs/setup.md`), an unprivileged external attacker can send a forged POST to `/webhooks` claiming `repository.owner.login`/`organization.login` equal to that secret-less organization, while setting `repository.full_name`, `sha`, `ref`, `after`, `branches`, etc. to reference a *different*, fully-secured organization's repository/stack. This lets the attacker:
- Inject fabricated `push` events causing `Stack#sync_github` to run for a stack it does not control (`PushHandler`).
- Inject fabricated commit `status` records for arbitrary commits (`StatusHandler`), which can influence `deployable_status`/`merge_status` checks that gate the merge queue and continuous deployment decisions.
- Trigger PR handlers (`ClosedHandler`, etc.) that archive/create stacks based on forged pull-request payloads for arbitrary repositories.

Depending on stack configuration (e.g., continuous delivery schedules or status-gated auto-merge/auto-deploy), forged status/push events can influence which commits are considered deployable or merged, constituting escalation into deploy/merge decision state without any GitHub credential for the target repository. This lands in the "unauthenticated read/manipulation of stack state" and potentially "unauthorized deploy/merge" impact bands.

### Likelihood Explanation
Requires the host to run Shipit's supported multi-GitHub-App mode with at least one org's `webhook_secret` left blank (an explicitly documented/optional configuration choice — not a hypothetical). Given that combination, exploitation requires no credentials, no GitHub App access, and no prior authentication — only knowledge of the target Shipit instance's `/webhooks` URL and the name of the secret-less organization (discoverable, e.g., via any public activity from that org's webhook deliveries or by trial). This is a realistic misconfiguration-adjacent but in-scope condition since the engine itself provides no organization/repository consistency check regardless of secret configuration.

### Recommendation
- After resolving the repository/stack from the payload, verify that its owning organization matches the organization whose webhook_secret was used to authenticate the request (`repository_owner == stack.repository.owner`), rejecting mismatches with `422`.
- Consider requiring a non-blank `webhook_secret` for every configured organization in multi-app mode, or at minimum warn/refuse to boot when any organization lacks one while others are configured with a secret, since this creates the weakest-link condition described above.

### Proof of Concept
1. Shipit is configured with two GitHub Apps, e.g. `OrgSecure` (has `webhook_secret` set) and `OrgOpen` (no `webhook_secret`), as supported by `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker sends, without any valid GitHub signature:
```
POST /webhooks
X-Github-Event: push
{
  "organization": { "login": "OrgOpen" },
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgSecure/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgOpen")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`) regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `create` proceeds to run `PushHandler` against the full payload, which resolves stacks via `repository.full_name` = `OrgSecure/victim-repo`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` — a stack belonging to the fully-secured `OrgSecure`, despite the request only ever being authenticated (vacuously) against `OrgOpen`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
