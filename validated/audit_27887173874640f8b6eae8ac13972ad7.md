### Title
Cross-organization `Team` membership escalation via `github_id`-only lookup in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::User#authorized?` grants application access based on membership in `Shipit.github_teams`, which are `Team` records identified purely by `github_id` [1](#0-0) . `MembershipHandler#find_or_create_team!` looks up teams by `params.team.id` (a bare GitHub-wide integer) with no check that the requesting organization actually owns that team, and `verify_signature` only authenticates that the *payload's own organization* signed the request, not that the `team.id` inside the payload belongs to that organization.

### Finding Description
The binding that should hold is: `Team#organization == payload['organization']['login']` for any `Team` row mutated by a `membership` webhook whose HMAC was verified against that same organization's `webhook_secret`. This binding is never checked.

- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from the payload itself (`repository.owner.login` or `organization.login`) and verifies the HMAC using that organization's configured `webhook_secret` [2](#0-1) [3](#0-2) . This only proves the request was signed by *some* configured organization's secret (in multi-org deployments each org has its own `webhook_secret`, per `Shipit.github_app_config`) [4](#0-3) .
- `MembershipHandler.params` only type-checks `team.id` (Integer), `organization.login` (String), `member.login` (String) — no relationship between them is enforced [5](#0-4) .
- `find_or_create_team!` resolves/creates the `Team` row solely by `github_id: params.team.id`; the `organization` value from the payload is only used inside the creation block (i.e., it is not used as a lookup key, and is not re-validated against an existing row on update) [6](#0-5) .
- `process` then calls `team.add_member(member)` or `team.members.delete(member)` on whatever `Team` row was returned [7](#0-6) .

Exploit flow: an attacker who legitimately controls their own GitHub organization "attacker-org" that is configured in Shipit (with its own valid `webhook_secret`) sends a genuinely-signed `membership` webhook with `organization.login: "attacker-org"` (satisfying `verify_signature`) but `team.id` set to the **numeric GitHub team ID of a team belonging to a different, victim organization** (e.g., a team already present in Shipit's `Team` table, potentially one listed in `Shipit.github_teams`) and `member.login` set to the attacker's own GitHub login. `find_or_create_team!` finds the existing victim team by `github_id` alone, ignoring that the signed organization is "attacker-org", and `team.add_member(member)` adds the attacker as a member of the victim organization's team. If that team is one of `Shipit.github_teams`, `User#authorized?` grants the attacker access to the whole Shipit instance [1](#0-0) [8](#0-7) .

None of the listed guards catch this: `verify_signature` checks organization-to-secret binding, not organization-to-team-id binding; the `ExplicitParameters` schema is type-only; `Membership` model validation only enforces `user_id` uniqueness scoped to `team_id`, not organization consistency [9](#0-8) ; `Team` has no uniqueness/ownership constraint tying `github_id` to `organization` at the database or model level.

### Impact Explanation
A request signed by organization A's own webhook secret can add an attacker-controlled GitHub login as a member of a `Team` (and thus `Membership` row) that actually belongs to organization B. If that team is one of `Shipit.github_teams`, this is a direct escalation into `Shipit.github_teams` authorization (an unprivileged attacker gains full authenticated access to the Shipit instance, matching the High severity category for "escalation into `Shipit.github_teams` authorization"). It is repeatable: every `added`/`removed` action on the same fabricated `team.id` mutates the same cross-tenant `Team` record, and multiple distinct victim teams can be targeted by iterating `team.id`.

### Likelihood Explanation
Requires (a) a Shipit deployment configured for multiple GitHub organizations (each with its own `webhook_secret`) so the attacker legitimately controls one organization's signing key, and (b) knowledge or guessability of a target team's numeric GitHub team ID (team IDs are sequential/enumerable via the GitHub API and are not secret). Attacker cost is a single legitimately-signed HTTP POST from their own org's installed GitHub App/webhook; no Shipit or GitHub secrets need to be exfiltrated. In single-organization deployments (the common case, one `webhook_secret` for the whole app) this specific path collapses because the attacker would need that org's own secret anyway to sign *any* payload naming any team — the risk is concentrated in multi-org configurations, which the engine explicitly supports.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if an existing `Team` with that `github_id` has a different `organization` than the one that signed the webhook, rather than silently reusing it.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossOrgTest < ActiveSupport::TestCase
        test "membership webhook signed by org A can mutate a team belonging to org B" do
          victim_team = shipit_teams(:shopify_developers) # organization: "shopify"
          assert_equal 'shopify', victim_team.organization

          # Payload "signed" as coming from a different organization
          payload = {
            'action' => 'added',
            'team' => {
              'id' => victim_team.github_id,   # victim org's team id
              'name' => victim_team.name,
              'slug' => victim_team.slug,
              'url' => victim_team.api_url
            },
            'organization' => { 'login' => 'attacker-org' }, # different org signs this
            'member' => { 'login' => 'attacker' }
          }

          Shipit.github.api.expects(:user).with('attacker').returns(
            stub(id: 999, name: 'Attacker', login: 'attacker', email: 'a@a.com',
                 avatar_url: 'https://example.com/a.png', url: 'https://api.github.com/user/attacker')
          )

          MembershipHandler.call(payload)

          # Binding check: the team mutated must equal the team owned by the signing org.
          # It does NOT -- membership was added to shopify's team despite "attacker-org" signing.
          assert victim_team.members.exists?(login: 'attacker'),
                 "attacker was added to a team belonging to a different organization than the one that signed the webhook"
        end
      end
    end
  end
end
```
This demonstrates that `find_or_create_by!(github_id: ...)` in `MembershipHandler#find_or_create_team!` [6](#0-5)  ignores the organization named/signed in the payload, breaking the `Team#organization == signing organization` binding.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
