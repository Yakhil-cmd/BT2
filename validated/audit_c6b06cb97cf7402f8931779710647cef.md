## Finding

The Astro-Shield bug is a case where a self-consistent hash (`integrity` attribute, matching the injected content) is treated as proof of legitimate membership in an allow-list (the CSP), when the check never verifies that the content is *currently* authorized. The analogous pattern in `ocore--002` exists in the `'in merkle'` address-definition/authentifier primitive.

### Root cause

The `'in merkle'` authentifier lets a signer prove membership of an `element` in a merkle tree whose root was published by a trusted oracle in a data feed: [1](#0-0) 

`merkle.verifyMerkleProof` only checks internal self-consistency between `element`, the attacker-supplied `siblings`, and the claimed `proof.root` — it proves nothing about *when* or *whether* that specific root is still the currently-valid allow-list: [2](#0-1) 

The claimed root is then checked against the oracle's data feed via `dataFeeds.dataFeedExists`, which — for relation `'='` — scans the entire key range between `min_mci` and `last_ball_mci` (`objValidationState.last_ball_mci`) and returns true if the root value was *ever* posted by the oracle in that range, not only if it is the oracle's *current/latest* root: [3](#0-2) 

### Impact

If an address's signing definition includes an `'in merkle'` condition to represent a dynamic, revocable membership/allow-list (e.g., a rotating committee, KYC-approved list, or subscriber list controlled by an oracle that periodically republishes an updated merkle root to exclude removed members), a member who has been legitimately *removed* from the current set can still produce a valid merkle proof against an *old* root that the oracle posted in the past (when they were still a member). Because `dataFeedExists` accepts any historical match rather than only the newest one, and because `min_mci` in the definition is fixed at definition time (or defaults to 0) and can't be forced to always equal "the most recent post," the revoked party's authentifier still passes `validateAuthentifiers`, letting them continue to co-sign/authorize spends or AA triggers gated by that address indefinitely — a concrete unauthorized-spending / privilege-non-revocation issue, directly analogous to the Astro-Shield bug where a self-matching hash defeated the intended allow-list semantics.

### Recommendation
The membership check via `'in merkle'` should require the referenced data-feed entry to be the *latest* one posted by the oracle for that `feed_name` at or before `last_ball_mci` (i.e., match `MAX(mci)` in range, not "exists anywhere in range"), so that revocations (root rotations) are properly enforced instead of being permanently bypassable by presenting a stale, but still internally-consistent, proof.

### Proof of Concept (conceptual)
1. Oracle `O` maintains a committee list; publishes `data_feed{committee_root: R1}` including member `M`.
2. `M`'s address is defined with `['in merkle', [[O], 'committee_root', M]]` as (part of) its spending condition.
3. `M` requests a merkle proof for inclusion in `R1` and stores it.
4. Later, `O` removes `M` and publishes `data_feed{committee_root: R2}` (without `M`).
5. `M` posts a unit spending from the address, supplying the stale proof for `R1` as the authentifier.
6. `validateAuthentifiers` → `'in merkle'` case calls `dataFeeds.dataFeedExists(..., '=', R1, min_mci, last_ball_mci, ...)`, which still finds the old `R1` entry in the DB/kvstore range and returns `true`, so the unit validates despite `M` having been revoked. [1](#0-0) [3](#0-2) [2](#0-1)

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
