### Title
CCMenu API endpoint bypasses per-stack API client scoping, letting a stack-scoped token read the status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` tokens can be scoped to a single stack via the `stack` association (see fixture `here_come_the_walrus` with `stack: shipit`, `permissions: [read:stack]`). `Api::BaseController` enforces this scoping through its `stacks`/`stack` helpers, but `Api::CCMenuController` overrides `stack` to bypass that scoping, breaking the binding "stack a token authorizes" == "stack the endpoint touches" — directly analogous to the DynamoFinance bug where a computed/verified check (`VoteCount`) was never actually wired into the enforcement action (`replaceGovernanceContract`). Here the enforcement (`stack_id` scoping) is computed and used elsewhere, but the CCMenu controller's own `stack` lookup never consults it.

### Finding Description
`Api::BaseController` defines scoped stack resolution: [1](#0-0) 

`stacks` restricts the queryable set to the client's own `stack_id` when the token is stack-scoped, and `stack` resolves `params[:stack_id]` only within that restricted set — this is the mechanism that turns "read:stack" from a global grant into a per-stack grant for scoped tokens.

`Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves directly against the global `Stack` table: [2](#0-1) 

The only authorization check applied is `require_permission :read, :stack`, which merely checks the boolean permission flag on the token via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never inspects `stack_id`; the stack_id-based restriction only happens in `BaseController#stacks`, which `CCMenuController#stack` deliberately does not call. As a result, a token that was issued with `read:stack` permission and scoped to one specific stack (`stack_id` set) can be used against `Api::CCMenuController#show` with an arbitrary `stack_id` route param to read *any* stack's CI/build status, not just the one it was scoped to.

### Impact Explanation
This is a cross-stack authorization bypass: a deliberately narrow-scoped credential (intended, per its `stack_id`, to expose only one project's build status through the semi-public CCMenu/CCTray endpoint) becomes a global read-access credential for every stack's deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock state, etc.) in the Shipit instance, as shown by the test asserting scoping normally works via the standard `stacks` path but is not exercised by `CCMenuController`: [4](#0-3) [5](#0-4) 

This matches the "High — unauthorized read of stack state" impact class: the equality that should hold, `token.stack_id == stack_id_being_read` (when `stack_id` is set), is violated for this one controller.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` token (these are routinely generated and embedded in CI-dashboard/CCMenu URLs, which are often shared more widely than admin credentials, e.g. via `CCMenuUrlController`) can trigger this simply by changing the `stack_id` path/query parameter of the CCMenu XML endpoint. No additional privilege, session, or secret is required beyond the token itself, and the token's presence is exactly the scenario the `stack_id` scoping feature is meant to contain.

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` collection (as `BaseController#stack` does) instead of querying `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the private `authenticate_api_client` override's implicit trust that `require_permission` alone is sufficient, ensuring stack-scoped tokens are confined to their assigned stack for this endpoint as well.

### Proof of Concept
1. As an admin, create (or use the fixture) `here_come_the_walrus` API client scoped to stack `shipit` with `permissions: ['read:stack']`, and obtain its `authentication_token`.
2. Using that token via HTTP Basic auth (or `?token=`), request `GET /api/{other_stack_owner}/{other_stack_name}/{other_env}/ccmenu.xml`, where `other_stack` is *not* the stack the token was scoped to.
3. Observe the endpoint returns build/deploy status for the unauthorized stack, because `Api::CCMenuController#stack` loads `Stack.from_param!(params[:stack_id])` directly instead of going through the client's `stacks` scope, unlike every other controller inheriting from `Api::BaseController`.
