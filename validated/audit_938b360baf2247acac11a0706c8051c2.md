### Title
Cross-repository CI-status contamination via unscoped `Commit.where(sha:)` in `status` webhook handling - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the `Repository`/`Stack` that authenticated the incoming webhook. Because `Commit` rows are unique only per `(sha, stack_id)` and not globally, any two `Repository` records that happen to track a `Commit` with the same sha (e.g. a shared ancestor commit between an upstream repo and its fork, each onboarded as a separate Shipit-tracked repository) will both be updated when either repository's webhook delivers a `status` event for that sha.

### Finding Description
The broken binding: `Repository(authenticated_by_webhook_signature) == Repository(owns_the_commit_row_written)`. This does not hold in `StatusHandler`.

Webhook signature verification in `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) correctly authenticates that the request originates from the org tied to `repository_owner` (derived from the payload's `repository.owner.login`) — but this only proves *which org sent the event*, not which `Commit`/`Stack`/`Repository` it may legitimately mutate. That constraint is supposed to be enforced downstream by each handler.

Other handlers correctly re-derive the authorized scope from the payload's `repository.full_name` via `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`), e.g.:
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) scopes to `stacks.not_archived.where(branch:)`.
- `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) scopes to `stacks.where(branch:)` then `stack.commits.where(sha:)`.

`StatusHandler#process`, by contrast, does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This never calls `stacks`, never touches `payload.dig('repository', 'full_name')`, and never filters by `stack_id`/`repository_id`. `Commit#stack` (`app/models/shipit/commit.rb:11`) belongs to a `Stack`, and `Stack` belongs to a `Repository`, but the sha itself is only unique per `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, confirmed by schema index `index_commits_on_sha_and_stack_id`), not globally. So if `Repository A` (upstream) and `Repository B` (a fork, onboarded as an independent Shipit-tracked repository under its own org/webhook secret) both have a `Commit` row for a shared ancestor sha, a `status` webhook correctly signed and delivered from B's org will still match and mutate A's `Commit` row.

Exploit flow: the attacker's fork is a fully separate `Repository`/`Stack` configured in Shipit under its own GitHub org, with a legitimate `webhook_secret` for that org (per the question's stated precondition). The attacker's own CI (which they fully control, e.g. GitHub Actions in their fork) posts a `status` event to GitHub for a commit sha that is a shared ancestor with the upstream repo (any commit predating the fork, which is guaranteed to exist and share sha under normal git fork semantics). GitHub signs and delivers this event to Shipit using the fork org's `webhook_secret`. `verify_signature` passes because the signature is valid for the org that genuinely sent it. `StatusHandler#process` then updates every `Commit` row across all repositories that shares that sha — including the upstream's tracked commit — with attacker-controlled `state`, `description`, `target_url`, and `context`.

### Impact Explanation
An unprivileged fork owner can inject fabricated CI status (success/failure/pending, arbitrary `description`/`target_url`/`context`) onto the upstream repository's tracked `Commit`, without any permission on the upstream repository, Shipit session, or API token. This is a cross-tenant write: a payload authenticated for repository B mutates repository A's `Commit`/status state — directly matching the specified Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). Since Shipit stacks commonly gate merges/deploys on required statuses (`Stack#required_statuses`, delegated from `Commit`), a forged "success" status on a shared ancestor commit could contribute to satisfying deploy/merge gating logic for the upstream stack, depending on how required-status checks resolve commits. The attack is repeatable against any pair of repositories sharing ancestor commits (any upstream + any of its forks that are independently onboarded), and costs the attacker nothing beyond controlling their own fork's CI.

### Likelihood Explanation
Preconditions: both the upstream and the fork must be independently onboarded as separate `Shipit::Repository`/org configurations with their own `webhook_secret` (explicitly given in the question as the scenario setup — this is a normal, supported Shipit configuration, not a misconfiguration). The attacker needs only to control their fork and its CI/webhook delivery — capabilities available to any GitHub user who forks a public repo. Shared-ancestor shas are the default outcome of any fork relationship, so no special crafting is required. This is fully repeatable and requires no secrets, sessions, or privileged roles.

### Recommendation
Scope `StatusHandler#process` to only the commits belonging to the authenticated repository's stacks, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ties the mutation to `Repository.from_github_repo_name(repository_name)` (derived from the payload's `repository.full_name`, matching what was signature-verified), closing the sha-collision cross-tenant path.

### Proof of Concept
Minitest plan (e.g. added to `test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create `repository_a` (upstream) and `repository_b` (fork) as two distinct `Shipit::Repository` fixtures, each with its own `Stack` (`stack_a`, `stack_b`).
2. Create `Commit.create!(stack: stack_a, sha: 'deadbeef' * 5[0,40], ...)` and `Commit.create!(stack: stack_b, sha: <same sha>, ...)` — permitted since uniqueness is only `(sha, stack_id)`.
3. Build a `status` webhook payload with `sha` set to the shared value and `repository.full_name` set to `repository_b`'s full name (the fork).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, since that is not the code under test).
5. Assert:
   - `stack_b.commits.find_by(sha: sha).statuses.count == 1` (expected, legitimate update), AND
   - `stack_a.commits.find_by(sha: sha).statuses.count == 1` (unexpected — proves cross-repository contamination; before the fix this assertion passes, demonstrating the bug; after the fix it should fail/be 0).
