### Title
Webhook signature verified against attacker-chosen organization while `status` handler writes to any repository's commit - cross-repository status forgery ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the `X-Hub-Signature` against using an unauthenticated JSON field taken from the request body itself, not from anything else tied to the resource being acted on. Once that check passes, `StatusHandler#process` updates a `Commit`'s status by looking it up **globally by SHA across the entire Shipit instance**, with no re-validation that the verified organization actually owns the repository/commit being modified. This breaks the "organization that authenticated" vs. "repository that is written" binding described in the analog rules.

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` (and therefore which `webhook_secret` to validate the HMAC against) using: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted, unverified JSON payload (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) *before* the signature has been checked. In a multi-organization Shipit deployment (a documented, supported configuration - see `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb`'s `github_app_config`), each organization has its own `webhook_secret`. An attacker who knows (or has leaked/obtained) the webhook secret for **any one** of the configured organizations can set `repository.owner.login` to that organization's name to pass `verify_signature`, while putting arbitrary, unrelated data in the rest of the payload.

The `status` event handler, `StatusHandler`, ignores the repository entirely and updates commit statuses by SHA across the whole install: [3](#0-2) 

There is no check that the commit found by SHA belongs to a stack/repository owned by the organization whose secret validated the signature (unlike the base `Handler` class, which does have a repository-scoped `stacks` helper used by other handlers such as `PushHandler`, `StatusHandler` doesn't use it at all - it queries `Commit.where(sha: params.sha)` unscoped).

Concretely:
- Signature verification binds trust to: `Shipit.github(organization: repository_owner_from_payload)`.
- The actual write (`commit.create_status_from_github!(params)`) is applied to whatever `Commit` row anywhere in the database happens to share that SHA, regardless of which org/stack it belongs to.

These two are never checked against each other, breaking the "organization that authenticated" == "repository that is written" invariant.

### Impact Explanation
`Status` creation is not inert bookkeeping - it feeds directly into deploy gating and continuous deployment:
- `Status#enable_ci_on_stack` flips `stack.ignore_ci` behavior on for the target stack: [4](#0-3) 
- `Status#schedule_continuous_delivery` is fired on every create: [5](#0-4) 
- `Commit#deployable?` is computed purely from locally-stored status state, not live GitHub state: [6](#0-5) 
- `Status#after_commit` `schedule_continuous_delivery` and `Commit#add_status`'s `deployable_status` hook can move a stack toward triggering a deploy once a fabricated "success" status lands: [7](#0-6) 

So an attacker who controls (or leaks) only one organization's webhook secret in a multi-org Shipit instance can forge a `status` event that marks an arbitrary commit belonging to a **different** organization's stack as `success`, bypassing `ci.require`/`ci.blocking` gates, and - on stacks with `continuous_deployment` enabled - trigger an unauthorized/unreviewed deploy of that commit. This satisfies the "Critical - unauthorized deploy" / cross-repository writes bar.

### Likelihood Explanation
Likelihood is **High** in any deployment using the documented multi-organization GitHub App configuration (`docs/setup.md`), which is an explicitly supported and expected mode of operation. The attacker only needs knowledge of a webhook secret belonging to any one organization served by the Shipit instance (e.g., an insider on one team, or a leaked secret for a lower-value org) to forge status updates for repositories owned by unrelated, higher-value organizations tracked by the same Shipit deployment - no GitHub write access, Shipit session, or ApiClient token is required.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository named in the payload (using the same `repository_name`/`stacks` helper already available on `Handler`), and in `WebhooksController#verify_signature`, re-validate that the organization used to verify the signature matches the owner of the repository the handler is about to mutate - reject the webhook if they diverge.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps/orgs, `orgA` and `orgB`, each tracked via stacks in the same Shipit instance (per `docs/setup.md`'s multi-org setup).
2. Obtain (or leak) `orgA`'s `webhook_secret` only.
3. Craft a JSON body: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgA/irrelevant"}, "sha": "<sha of a commit belonging to an orgB stack>", "state": "success", "context": "ci/required-check"}`.
4. Sign the raw body with `orgA`'s secret and send it as `POST /webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
5. `verify_signature` resolves `Shipit.github(organization: 'orgA')` and passes verification.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the `orgB` commit (unscoped by repository), creating a `success` status on it - potentially satisfying `ci.require` and, on a `continuous_deployment` stack, triggering an automatic deploy of that `orgB` commit that the attacker never had access to.
