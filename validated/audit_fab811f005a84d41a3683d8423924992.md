### Title
CCMenu API endpoint ignores `ApiClient#stack_id` scoping and lets a stack-scoped token read any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` supports being scoped to a single stack via `stack_id` (`belongs_to :stack, optional: true`), and `Shipit::Api::BaseController` enforces this scoping through its `stacks`/`stack` helper methods used by every other API controller. `Shipit::Api::CCMenuController`, however, reimplements `stack` to bypass this scoping entirely, resolving the target stack from `Stack.from_param!(params[:stack_id])` against the full, unscoped `Stack` relation. Any token carrying the `read:stack` permission can therefore be used to fetch CCMenu build/deploy status for a stack it was never authorized for, exactly as the `flashProof` finding describes a check performed on the wrong entity (`tx.origin` instead of the actual caller) — here the permission check (`read:stack`) is enforced, but the binding between "the stack this token authorizes" and "the stack this request actually touches" is dropped.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scoped accessor: [1](#0-0) 

which restricts lookups to `Stack.where(id: current_api_client.stack_id)` whenever the authenticating `ApiClient` has a `stack_id` set: [2](#0-1) 

`CCMenuController` requires only the `read:stack` permission and overrides `stack` to query the global `Stack` scope directly, skipping the `stacks` helper (and therefore the `stack_id` restriction) altogether: [3](#0-2) 

`check_permissions!` only validates that the permission string (`read:stack`) is present in the client's permission list; it never checks which stack the request targets: [4](#0-3) 

So the equality that should hold — "the set of stacks a token authorizes" == "the set of stacks a request against that token can touch" — is broken specifically in this controller. Every other stack-scoped consumer of `BaseController` (e.g. `Api::StacksController`, `Api::HooksController`, deploy/task/rollback related API controllers) goes through the scoped `stack`/`stacks` helpers and is unaffected.

### Impact Explanation
An attacker holding any `ApiClient` token limited to `read:stack` and scoped to a single stack (`stack_id` set) can supply an arbitrary `stack_id` param to `Api::CCMenuController#show` and read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock status, etc.) for any other stack in the installation, including private/unrelated repositories' deploy state. This is an authorization-scope escape enabling cross-stack read of deploy state beyond the token's granted authority, matching the "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state ... deploy output" class of High-severity issues for stacks the token was never meant to see.

### Likelihood Explanation
Exploitation requires only possessing any valid `read:stack`-scoped `ApiClient` token (the minimal, narrowly-granted credential the feature is designed to hand out, e.g. via the CCMenu integration flow) and knowledge/guessing of another stack's identifier (`owner/repo/env`), which is not secret. No additional privilege, session, or write access is needed beyond the low-privilege token itself, making this straightforward to exploit once such a token exists.

### Recommendation
Make `CCMenuController#stack` go through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `stack_id` restriction on scoped `ApiClient` tokens is enforced consistently across all API controllers.

### Proof of Concept
1. Create/obtain an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (the intended, authorized stack).
2. Send `GET /api/:stack_id/ccmenu` (or the token/query-string authenticated CCMenu endpoint) with `stack_id` pointing to Stack B, a stack the token was never granted access to, using the token's `authentication_token`.
3. `authenticate_api_client` succeeds because the token is valid and carries `read:stack`; `require_permission :read, :stack` passes because it only checks the permission list.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` against all stacks, not the client's `stacks` scope, returning Stack B and rendering its deploy/build status — data the token was never authorized to read.

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
