### Title
Cross-org forged `status` webhook triggers unauthorized deploy and RCE via `Command#start` using victim's `GITHUB_TOKEN` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App secret of whichever organization the attacker names in `repository.owner.login`, but `StatusHandler#process` then applies the status to *any* commit matching `params.sha` in the entire database with no check that the commit's stack belongs to that same organization. An attacker who controls any org/repo onboarded to this multi-tenant Shipit instance can therefore sign a `status` payload with their own credentials while pointing `sha` at a victim's public commit, forging a `success` status that flows through `Stack#trigger_continuous_delivery` into `Stack#trigger_deploy` and ultimately `Command#start`, executing the victim's deploy pipeline with the victim's `GITHUB_TOKEN`/`GIT_ASKPASS`.

### Finding Description
The broken binding, stated as an equality that the code must enforce but does not:

`organization_verified_by_signature == commit.stack.repository.owner`

where `organization_verified_by_signature = Shipit.github(organization: params.dig('repository','owner','login'))` (used only for HMAC verification) and `commit.stack.repository.owner` is the actual organization whose data gets mutated.

Code path:
1. `WebhooksController#verify_signature` derives the org strictly from attacker-controlled JSON (`repository_owner`) and checks the signature against *that* org's `webhook_secret`: [1](#0-0) 
2. `GithubApp#verify_webhook_signature` HMACs the raw body against the named org's own secret — it says nothing about which commits the payload is allowed to reference: [2](#0-1) 
3. Once the signature is accepted for *whatever org the attacker named*, `StatusHandler#process` ignores `repository` entirely and matches purely by `sha`, globally: [3](#0-2) 
4. `Status#after_create`/`after_commit` callbacks enable CI and schedule continuous delivery for the victim stack owning that commit: [4](#0-3) 
5. `Commit#deployable?` becomes true once a `success` status exists and the commit isn't locked/blocked: [5](#0-4) 
6. `Stack#trigger_continuous_delivery` picks up the commit and calls `trigger_deploy`, gated only by `deployment_checks_passed?`, which trivially returns `true` when `Shipit.deployment_checks` is unset: [6](#0-5) [7](#0-6) 
7. `trigger_deploy`/`build_deploy` persist and enqueue the deploy: [8](#0-7) 
8. `PerformTaskJob` executes the task via the default execution strategy: [9](#0-8) 
9. `Commands#base_env` injects the org's real `GITHUB_TOKEN`/`GIT_ASKPASS` into every `Command` built for that stack: [10](#0-9) 
10. `Command#start` spawns the process with that merged environment via `PTY.spawn`: [11](#0-10) 

Why existing guards fail: `verify_signature` only proves "this request was signed by *some* org's secret" — it never re-checks that the org used for signing matches the org owning the stack/commit the request goes on to mutate. `drop_unhandled_event` and `ExplicitParameters` (`requires :sha, String; requires :state, String`) validate shape, not ownership. `Commit.where(sha: params.sha)` in `StatusHandler#process` is intentionally cross-stack (to support forked/cherry-picked commits across repos) but that design decision silently allows any authenticated-org sender to inject state onto commits it doesn't own.

### Impact Explanation
A single forged, validly-signed (by the attacker's own onboarded org) `status` webhook naming a victim's public commit SHA can trigger an unauthorized deploy that executes arbitrary deploy-spec commands (`Command#start`/`PTY.spawn`) with the victim stack's real `GITHUB_TOKEN` and `GIT_ASKPASS`. This is remote command execution on the deploy host using the victim's credentials, triggered by a party that never authenticated to the victim's stack/org — Critical severity per the rubric ("RCE on the deploy host via `Command`/`PTY.spawn`... using a forged webhook"). It is repeatable against any stack with `continuous_deployment: true` and no `deployment_checks`, across any tenant/org onboarded to the same Shipit instance, as long as the attacker can learn (or guess) a deployable commit SHA of the target — trivial for public repos.

### Likelihood Explanation
Preconditions required: (1) the attacker controls at least one org/repo already onboarded to this multi-tenant Shipit deployment and can produce a validly-signed webhook for it (either because that org has no `webhook_secret` configured, or because they legitimately know their own org's secret); (2) the victim stack has `continuous_deployment: true` and no additional `deployment_checks`/CI-state requirement that blocks a bare `success` status; (3) the attacker knows a commit SHA belonging to the victim's stack (public for public repos). None of these require possessing the victim's secrets, a Shipit session, or API token. Given typical self-hosted multi-tenant Shipit usage (many orgs, one shared instance), this is a low-cost, repeatable attack.

### Recommendation
In `StatusHandler#process` (and any other handler that looks up records purely by attacker-supplied identifiers), scope the lookup to the organization/repository that was cryptographically verified in `WebhooksController#verify_signature` — e.g., only update `commit.create_status_from_github!` for commits whose `stack.repository.owner` (case-insensitively) matches the `repository_owner` used to select the signing `GithubApp`. Reject or ignore statuses whose payload repository does not match the commit's actual repository.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a new integration test):
```ruby
test "cross-org forged status cannot deploy another org's stack" do
  victim_commit = shipit_commits(:third) # belongs to org "shopify"
  victim_stack = victim_commit.stack
  victim_stack.update!(continuous_deployment: true)
  Shipit.stubs(:deployment_checks).returns(nil)

  # Attacker's own org "attacker-org" has a real webhook secret they know.
  attacker_org_app = stub(verify_webhook_signature: true) # simulates attacker validly signing for THEIR OWN org
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(attacker_org_app)

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'branches' => [{ 'name' => victim_stack.branch }],
    'repository' => { 'owner' => { 'login' => 'attacker-org' } } # attacker names their own org for signing
  }.to_json

  request.headers['X-Github-Event'] = 'status'
  request.headers['X-Hub-Signature'] = 'sha1=whatever-attacker-can-compute-for-their-own-secret'

  Shipit::Command.any_instance.expects(:start).never # assert no deploy command is ever spawned

  assert_no_difference -> { victim_stack.deploys.count } do
    post :create, body: payload, as: :json
  end
end
```
The equality to assert on both sides: before the request, `victim_commit.deployable?` is `false`; the claim under test is that after a webhook signed only for `attacker-org` (≠ `victim_stack.repository.owner`, "shopify") is accepted, `victim_commit.reload.deployable?` becomes `true` and `Shipit::Command#start` is invoked with `victim_stack`'s `GITHUB_TOKEN` — demonstrating the signing-org/owning-org equality is never checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def trigger_deploy(*args, **kwargs)
      if changed?
        # If this is the first deploy since the spec changed it's possible the record will be dirty here, meaning we
        # cant lock. In this one case persist the changes, otherwise log a warning and let the lock raise, so we
        # can debug what's going on here. We don't expect anything other than the deploy spec to dirty the model
        # instance, because of how that field is serialised.
        if changes.keys == ['cached_deploy_spec']
          save!
        else
          Rails.logger.warning("#{changes.keys} field(s) were unexpectedly modified on stack #{id} while deploying")
        end
      end

      run_now = kwargs.delete(:run_now)
      deploy = with_lock do
        deploy = build_deploy(*args, **kwargs)
        deploy.save!
        deploy
      end
      run_now ? deploy.run_now! : deploy.enqueue
      continuous_delivery_resumed!
      deploy
    end

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
