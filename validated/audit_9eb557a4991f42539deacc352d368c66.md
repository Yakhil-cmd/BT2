### Title
Cross-repository Commit Status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`'s `params` schema never declares a `repository` sub-object, and `StatusHandler#process` looks up commits with a completely unscoped `Commit.where(sha: params.sha)`, unlike every other handler which relies on `Handler#stacks` (itself scoped via `Repository.from_github_repo_name(repository_name)`). Any org with a registered `webhook_secret` can send a validly-signed `status` webhook whose `repository` field names their own repo but whose `sha` matches a commit belonging to a completely different stack/repository, and the handler will write a `Status` record onto that foreign commit.

### Finding Description
The claimed binding is: `repository_used_to_select_secret (params.dig('repository','owner','login'))` == `repository_whose_commit_is_mutated`. Tracing the code shows this equality is never enforced for `status` events.

- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) picks `Shipit.github(organization: repository_owner)` using only `params.dig('repository','owner','login')` (or `organization.login` as fallback) to select which org's `webhook_secret` verifies `X-Hub-Signature`. It never checks that the signed repository actually owns the data being mutated. [1](#0-0) [2](#0-1) 

- `StatusHandler`'s `params do ... end` block only declares `sha, state, description, target_url, context, created_at, branches` — no `repository` key at all, and no call to the base class's `stacks`/`repository_name` scoping helpers. [3](#0-2) 

- `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exist precisely to scope lookups to the repository named in the payload, but `StatusHandler#process` never calls them. [4](#0-3) 

- Instead, `StatusHandler#process` does a bare, global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. [5](#0-4) 

- `Commit` (`app/models/shipit/commit.rb:11`) `belongs_to :stack`; there is no uniqueness constraint or scoping tying `sha` to a single stack/repository at the model layer visible here — the query matches every `Commit` row across every stack/repository sharing that SHA. [6](#0-5) 

**Exploit flow**: Attacker registers/owns a repository (Org A) with a Shipit-managed `webhook_secret`. They identify a target commit SHA that also exists in a foreign stack (e.g., via a fork sharing git history with the upstream repo tracked by another Shipit stack, or any other means the SHA becomes shared/known — SHA-1 commit ids are content-addressed and identical commits/forks reproduce the same SHA across repositories). The attacker sends `POST /webhooks` with `X-Github-Event: status`, a body where `repository.owner.login` = Org A (so `verify_signature` uses Org A's own legitimate secret and the signature validates), and `sha` = the foreign commit's SHA plus attacker-chosen `state`/`description`/`target_url`/`context`. `ExplicitParameters` raises no error because `repository` is not required or read at all. `StatusHandler#process` then writes a forged `Status` onto every `Commit` row in the database matching that SHA, regardless of which stack/repository it belongs to, which can affect `deployable?`/CI-gating logic (`Commit#status`, `Commit#deployable?`) for a stack the attacker never authenticated against. [7](#0-6) 

No existing guard catches this: `verify_signature` only authenticates *who sent the request*, not *which repository's data may be mutated*; `ExplicitParameters` only validates the declared schema (which omits `repository`); and `StatusHandler` performs no post-hoc repository/stack scoping the way other handlers implicitly do via `Handler#stacks`.

### Impact Explanation
An attacker who controls any Shipit-registered repository (with its own legitimate `webhook_secret`) can write forged CI/commit statuses onto commits belonging to a different, unrelated repository/stack whenever the SHA happens to be shared or is otherwise known/guessable (e.g., shared commit history via forks/mirrors). This can flip a foreign commit's `state`/`status`, influencing `deployable?` and continuous-delivery scheduling (`schedule_continuous_delivery`) for a stack the attacker does not own. This matches the "payload for one repository mutating another's stack/commit" Critical category — it's an authenticated-request that authorizes only the sender's own identity but is applied against another tenant's data.

### Likelihood Explanation
Preconditions: attacker needs a Shipit-registered repository with a working `webhook_secret` (achievable by any GitHub org owner who installs the Shipit webhook on their own repo — no special privilege). The only added requirement beyond "attacker owns a repo" is knowledge of a target SHA that also exists as a `Commit` row in a foreign stack — realistic in fork/mirror scenarios where the shared git history/commit reappears in the attacker's own repo (thus is trivially known to them) while also being tracked by the victim's stack. This is inexpensive and repeatable against any commit SHA the attacker can discover.

### Recommendation
Add a `requires :repository do requires :full_name, String end` block to `StatusHandler`'s `params` (consistent with `OpenedHandler`/`ClosedHandler`), and scope the commit lookup through `Handler#stacks`/`repository_name`, e.g. `Commit.where(sha: params.sha, stack: stacks)` instead of unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (webhooks controller/integration test, no live GitHub):
1. Create two stacks/repositories, `victim/repo` and `attacker/repo`, each with distinct `webhook_secret`s, and a `Commit` with a known `sha` belonging to `victim/repo`'s stack.
2. POST to `/webhooks` with header `X-Github-Event: status`, signature computed using `attacker/repo`'s org `webhook_secret`, and JSON body: `{ "repository": {"full_name": "attacker/repo", "owner": {"login": "attacker"}}, "sha": "<victim commit sha>", "state": "failure", "context": "forged" }`.
3. Assert response is `200 OK` (signature accepted, no `ExplicitParameters` validation error despite the repository/sha mismatch).
4. Reload the victim commit and assert `commit.status.state == 'failure'` / a new `Status` row with `context: 'forged'` exists on the **victim's** commit, proving the equality `repository_used_for_signature (attacker/repo) == repository_mutated (victim/repo)` is false yet the mutation still succeeded.
