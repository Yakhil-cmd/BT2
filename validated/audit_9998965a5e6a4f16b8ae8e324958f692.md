### Title
Webhook signature verification is skipped when any configured GitHub App has no `webhook_secret`, letting an attacker forge `membership` events for arbitrary teams - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) validates an inbound webhook based on an attacker-controlled JSON field (`repository.owner.login` / `organization.login`), and `GithubApp#verify_webhook_signature` unconditionally returns `true` when that app has no `webhook_secret` configured. Because `webhook_secret` is an explicitly optional, per-organization setting, and the value used to select it is never checked against the value later trusted by the event handler, an attacker who targets any configured organization lacking a secret can submit a completely unauthenticated `membership` webhook that creates/edits `Team`s and adds arbitrary GitHub logins to them.

### Finding Description
`repository_owner` is computed from the raw, unauthenticated JSON body before the signature is checked: [1](#0-0) [2](#0-1) 

That value is used to pick which `GitHubApp` performs verification via `Shipit.github(organization: repository_owner)`. `GithubApp#verify_webhook_signature` then trivially bypasses HMAC verification whenever `webhook_secret` is blank: [3](#0-2) 

`webhook_secret` is documented and shipped as an optional per-org field (multiple orgs can be configured in `secrets.yml`, each independently), e.g.: [4](#0-3) [5](#0-4) 

Once the request passes (or is never actually authenticated), `create` dispatches the raw JSON body to registered handlers: [6](#0-5) 

`MembershipHandler` fully trusts fields from that same untrusted payload - `team`, `organization.login`, and `member.login` - to create a `Team` and add/remove a `User`'s `Membership` in it, without any cross-check that this `organization` matches the organization whose `GitHubApp`/secret was used (or bypassed) during `verify_signature`: [7](#0-6) 

Team membership is the basis of `Shipit`'s OAuth team-based authorization (`Shipit.github_teams`/`oauth_teams`), so writing arbitrary `Membership` rows changes who is treated as authorized once such a user authenticates via OAuth.

This breaks the trust binding "an organization that authenticated versus the [team/organization] that is written": the org used to select (and potentially skip) signature verification is an attacker-supplied field, and it is never required to equal the org whose `Team`/`Membership` data the handler subsequently mutates.

### Impact Explanation
An unauthenticated network attacker who knows (or guesses) that any one of Shipit's configured GitHub organizations has no `webhook_secret` set (an explicitly supported, documented default) can send a forged `membership` webhook that:
- creates an arbitrary `Team` record for any organization/slug of the attacker's choosing, and
- adds an arbitrary GitHub login as a member of that team.

Because team membership feeds `Shipit.github_teams` authorization, this can be used to grant an attacker-controlled GitHub identity membership in what Shipit believes is a privileged team, escalating that identity's authorization once it completes OAuth login. This matches the High-impact category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
No Shipit session, `ApiClient` token, GitHub App private key, or webhook secret is required. The only precondition is that at least one of the Shipit deployment's configured GitHub organizations has an unset `webhook_secret` - a state the code and documentation treat as normal/optional rather than disallowed, making this readily reachable in real deployments (especially single-org installs where the operator never set the field, as shown by the codebase's own example configs).

### Recommendation
- Make `webhook_secret` mandatory for every configured GitHub App/organization and refuse to boot (or refuse all webhooks) if it is missing, instead of `verify_webhook_signature` defaulting to `true`.
- Verify the signature using a secret bound to the resource actually being modified (e.g., re-derive/validate `organization`/`repository` identity from the authenticated context, not solely from attacker-supplied JSON), and ensure `repository_owner`/`organization.login` used for verification is cryptographically tied to the payload contents the handlers subsequently act on.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs in `secrets.yml`, one of which (`org-without-secret`) has `webhook_secret` unset (a supported configuration per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`).
2. POST to `/webhooks` with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, with body:
```json
{
  "action": "added",
  "organization": { "login": "org-without-secret" },
  "team": { "id": 999, "name": "Deploy Admins", "slug": "deploy-admins", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" }
}
```
3. `verify_signature` selects the `GitHubApp` for `org-without-secret`; since its `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `MembershipHandler#process` runs, creating the `Deploy Admins` team and adding `attacker-controlled-login` as a member - entirely without a valid signature.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
