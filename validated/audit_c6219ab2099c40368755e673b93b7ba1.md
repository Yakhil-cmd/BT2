## Title
Webhook signature is verified against the payload's organization field but push/status events are dispatched by the payload's `repository.full_name`, letting an attacker with a self-owned GitHub App installation forge sync/status events for a victim's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, which falls back from `repository.owner.login` to `organization.login`. [1](#0-0) [2](#0-1)  However, the event handlers that actually act on the payload resolve the target `Stack` purely from `payload.dig('repository', 'full_name')`, with no cross-check that this repository belongs to the organization whose secret validated the request. [3](#0-2) 

### Finding Description
The binding that should hold is: **organization authenticated (the org whose webhook secret validated `X-Hub-Signature`) == repository being written/acted upon**. In this engine that binding is broken.

- `verify_signature` computes `repository_owner` from the JSON body itself (`params.dig('repository','owner','login') || params.dig('organization','login')`), then fetches `Shipit.github(organization: repository_owner)` to get that org's `webhook_secret` and validate the HMAC. [1](#0-0) [2](#0-1) 
- Because Shipit supports "Multiple Github Applications," each organization installed has its own independent `webhook_secret` in `config/secrets.yml`. [4](#0-3) 
- Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire raw payload to handlers such as `PushHandler`, `StatusHandler`, etc. [5](#0-4) 
- `Handler#stacks`/`#repository_name` looks up the target `Repository` by `payload.dig('repository', 'full_name')` - a completely different field from the one used to pick the verifying secret. [3](#0-2) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack matching that (attacker-supplied) `repository.full_name` and branch. [6](#0-5) 

An attacker who owns/administers their own GitHub organization can install their own GitHub App there (this is a normal, unprivileged GitHub action requiring no Shipit credentials) and thus legitimately knows that org's `webhook_secret`. They can then send a webhook `POST` to Shipit's public webhooks endpoint with:
- `repository.owner.login` (and/or top-level `organization.login`) set to **their own org** (so `verify_signature` selects their own webhook secret and the HMAC computed with it validates), and
- `repository.full_name` set to a **victim organization's repository** that Shipit also manages (e.g. `victim-org/victim-repo`).

Because the handler layer never checks that `repository.full_name`'s owner matches the `repository_owner` used for signature verification, the forged event is accepted and dispatched against the victim's `Stack`.

### Impact Explanation
This crosses the "unauthenticated read of stack state" / "cross-repository writes" thresholds:
- Forged `push` events let the attacker invoke `stack.sync_github(expected_head_sha: ...)` on a victim stack they don't control, causing `GithubSyncJob` to run and mutate commit/tracking state for that stack using an attacker-chosen `expected_head_sha`.
- Forged `status` events (`StatusHandler`) can create/alter `Status` records on a victim commit for an arbitrary context/state, which the merge queue and deploy-gating logic (`Commit#deployable?`, `MergeRequest#all_status_checks_passed?`) rely on to decide whether commits are safe to merge or deploy. [7](#0-6) 
- Since CI status is one of the gates for automatic/continuous deployment and for merge-queue merges, an attacker forging a successful status for a victim's failing/malicious commit could push it toward being merged or deployed - i.e., an unauthorized deploy/merge path, and at minimum an unauthenticated write into another organization's stack state.

### Likelihood Explanation
Requires only: (1) that the deployment hosts multiple GitHub organizations via distinct App configs (an explicitly documented supported setup), and (2) that the attacker owns any org with its own installed GitHub App (fully self-service, no privileged access to Shipit or the victim org needed). The webhook endpoint is unauthenticated by design (relying solely on HMAC), and the only verification performed keys off attacker-controlled JSON fields, so likelihood is Medium-High whenever multi-org configuration is in use.

### Recommendation
After signature verification, re-validate that `repository.owner.login` (or `repository.full_name`'s owner segment) used by the handler layer is identical to the organization whose secret validated the signature - and reject the request otherwise. Do not let handlers resolve the target repository independently from an unauthenticated field once the trust boundary has already been established by a different field.

### Proof of Concept
1. Attacker creates GitHub org `attacker-org` and installs their own GitHub App on it; Shipit is configured (per `docs/setup.md` multi-org config) with `attacker-org`'s `webhook_secret` known to the attacker (they set it themselves).
2. Attacker crafts a JSON payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw JSON body, per `Hook::DeliverySigner`/`verify_webhook_signature` semantics. [8](#0-7) 
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s app, and successfully verifies the signature against the attacker-controlled secret. [1](#0-0) 
6. `PushHandler` resolves the target stack via `repository.full_name = "victim-org/victim-repo"` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for the victim's stack. [6](#0-5) 

Note: I could not fully trace `Stack#sync_github`'s downstream effects (e.g., whether `GithubSyncJob` independently re-fetches/re-validates data from GitHub using `victim-org`'s own credentials in a way that would neutralize an attacker-chosen `expected_head_sha`) within the indexed content available; a full Devin session with complete repo access would be needed to confirm the exact blast radius of the forged `expected_head_sha`/status payload end-to-end.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
