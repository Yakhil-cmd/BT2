### Title
Webhook authenticity is bound to `repository.owner.login` while the acted-upon repository is taken from `repository.full_name`, allowing cross-organization webhook forgery when any configured GitHub org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but the handlers that actually mutate state (`PushHandler`, pull-request handlers, etc.) resolve the target `Repository`/`Stack` using the independent `repository.full_name` field of the very same unauthenticated JSON body. If the organization named in `repository.owner.login` has no `webhook_secret` configured, signature verification is skipped entirely (`return true unless webhook_secret`), yet `repository.full_name` can point at a completely different, secured organization's repository/stack.

### Finding Description
`verify_signature` resolves the GitHub App to use for signature checking purely from the payload's `repository.owner.login` field: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` deliberately treats a missing/blank `webhook_secret` as "always verified": [3](#0-2) 

Shipit explicitly supports (and documents) configuring multiple GitHub organizations, each with an independent, optional `webhook_secret`: [4](#0-3) 

Once the request passes `verify_signature` (or is trivially accepted because the resolved org has no secret), the raw, unauthenticated JSON body is dispatched unchanged to the registered handlers: [5](#0-4) 

Handlers, however, do **not** use `repository.owner.login` to locate the target — they use the separate `repository.full_name` field: [6](#0-5) [7](#0-6) 

This breaks the intended binding: `organization authenticated (repository.owner.login → webhook_secret check)` should equal `repository written (repository.full_name → Stack lookup)`. Both fields are attacker-controlled in the raw JSON body, and nothing ties them together beyond an HMAC that may not even be checked. An unprivileged attacker who knows (or controls) any organization configured in Shipit with a blank/unset `webhook_secret` can craft a POST to `/webhooks` with:
- `X-Github-Event: push` (or any handled event)
- `repository.owner.login` = the org with no secret (so `verify_webhook_signature` short-circuits to `true`)
- `repository.full_name` = `victim-org/victim-repo` — any repository tracked by the Shipit instance, regardless of organization

The push then reaches `PushHandler#process`, which finds the real `Stack` for `victim-org/victim-repo` via `Repository.from_github_repo_name` and calls `stack.sync_github(expected_head_sha: params.after)` — an unauthenticated, cross-organization trigger of an internal sync job that acts on state associated with a repository the attacker never authenticated for. [8](#0-7) 

### Impact Explanation
This meets the High bar: it is escalation into unauthenticated triggering of stack-related actions (`sync_github`, pull-request handler side effects such as label/state changes on review stacks) for repositories/organizations the attacker was never authorized against — an unauthenticated cross-repository/cross-organization state change through the webhook trust boundary, achievable by any unprivileged network attacker with no Shipit session, API token, or the real webhook secret of the targeted org.

### Likelihood Explanation
Requires only that at least one org configured in the multi-org GitHub setup have no `webhook_secret` set — a state the codebase itself treats as a legitimate, documented configuration option (`webhook_secret: # nil`), not a misconfiguration guarded against elsewhere in the code. Given this precondition, exploitation is a single crafted, unauthenticated HTTP POST.

### Recommendation
Reject webhooks where the signature is not cryptographically verified — do not treat a missing configured secret as automatic pass-through in `verify_webhook_signature`, and additionally verify that `repository.owner.login` (the field used to select the verifying org/secret) matches the organization owning `repository.full_name` before dispatching to handlers, so the same payload field set is used consistently for both authentication and action targeting.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `orgA` (no `webhook_secret` set) and `orgB` (has a stack tracked, e.g. `orgB/secure-app`, with a strong secret).
2. Send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/secure-app"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`.
4. `PushHandler` looks up `Repository.from_github_repo_name("orgB/secure-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, an action on `orgB`'s stack triggered without ever passing `orgB`'s webhook verification.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
