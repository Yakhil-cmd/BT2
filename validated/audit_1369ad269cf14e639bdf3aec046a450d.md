Confirmed: there is no persistent map anywhere in `pox-5.clar` that records already-claimed L1 lockup outpoints. The only dedup (`seen-outpoints`) is a local accumulator built and discarded inside a single `validate-l1-lockup` fold call.

### Title
`register-for-bond`'s L1 lockup proof can be replayed across multiple bonds, double-crediting sats never re-locked on Bitcoin - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path validates a Bitcoin Merkle proof for a timelock output but never records that the referenced (txid, output-index) has been consumed. A staker can present the same, single, real Bitcoin lockup transaction to multiple sequential `register-for-bond` calls (across different bonds, once each prior bond's rollover window opens) and receive `sats-total` sBTC-equivalent credit every time, even though only one BTC UTXO was ever locked.

### Finding Description
`register-for-bond` computes the staked sats via `verify-l1-lockups`, which folds over `validate-l1-lockup` [1](#0-0) . Inside the fold, `seen-outpoints` only rules out duplicate outputs *within the same call's `outputs` list* (max 10 entries) via `ERR_DUPLICATE_LOCKUP_OUTPOINT` [2](#0-1) . This accumulator is created fresh on each call and is never persisted in a `define-map`.

The validation only checks:
- `unlock-burn-height` in the lockup ≥ the *current* bond's minimum required unlock height (not equal) [3](#0-2) 
- the output's script matches `construct-lockup-output-script` for `(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)` [4](#0-3) 
- a Merkle proof that the transaction/output is included in the referenced block header [5](#0-4) 

None of these checks are call-scoped-exclusive or globally consumed: the same historical Bitcoin transaction, with the same committed `unlock-burn-height`, satisfies the proof for *any* future bond whose `minimum-unlock-height` (derived from `get-bond-l1-unlock-height`) is ≤ that committed height. Because a staker can only hold one active `protocol-bond-memberships` entry at a time [6](#0-5) , the exploit is sequential rather than simultaneous: roll from bond A into bond B once `verify-bond-rollover-window` opens [7](#0-6) , resubmitting the identical L1 proof each time. Each successful call increments `protocol-bonds-total-staked` and the per-cycle bond/signer shares by `sats-total` again [8](#0-7) , even though no new BTC was ever locked and the sBTC-equivalent custody transfer is explicitly skipped on the L1 path (`new-sbtc` is `u0`) [9](#0-8) .

This breaks the equality the contract is meant to enforce: `sum(sats credited across all bonds for staker) == BTC sats actually locked on L1`. The same L1 lockup event is double- (or N-times-) counted.

### Impact Explanation
Bond reward distribution and signer weight/reward-slot apportionment (`pox_5_make_signer_set`) are driven by the aggregated `stacked_amt`/sats figures pulled from these on-chain bond records [10](#0-9) . Inflating a staker's counted sats via replay lets them claim a disproportionate share of sBTC bond rewards and/or signer reward slots relative to BTC actually locked -- this is a double-counting of a commitment/reward that dilutes honest stakers' share of the fixed reward pool. Severity is High under the stated rubric ("signing weight or reward slots exceeding locked value... double-counting a commitment or reward").

### Likelihood Explanation
Requires only a single real Bitcoin lockup transaction with a sufficiently distant `unlock-burn-height`, plus patience to wait through each bond's rollover window (`verify-bond-rollover-window`) before resubmitting the same proof to the next bond -- no privileged access, no other user's key, and no admin action needed. This is straightforwardly reachable by any unprivileged staker.

### Recommendation
Persist consumed L1 lockup outpoints (e.g., a `define-map used-l1-lockup-outpoints {txid, output-index} bool` or similar keyed by `(staker, txid, output-index)`) and check/insert them in `validate-l1-lockup`/`verify-l1-lockups`, so a given Bitcoin output can only ever be credited toward one live bond/stake position for its entire encoded unlock window, rather than being re-verifiable indefinitely across unrelated `register-for-bond` calls.

### Proof of Concept
1. Staker creates one real Bitcoin timelock output for `sats` BTC with `unlock-burn-height = X` (far in the future), using `construct-lockup-output-script(staker, X, staker-unlock-bytes, early-unlock-bytes)`.
2. Staker calls `register-for-bond` for bond A, whose `get-bond-l1-unlock-height(A) <= X`, submitting the Merkle proof for that output. Bond A's shares/signer delegation increase by `sats`; STX is locked correspondingly. [11](#0-10) 
3. Once `burn-block-height >= get-bond-l1-unlock-height(A)`, `verify-bond-rollover-window` permits a roll-over [7](#0-6) . Staker calls `register-for-bond` for bond B, where `get-bond-l1-unlock-height(B) <= X` still holds, resubmitting the **identical** header/tx/Merkle-proof tuple from step 1.
4. `validate-l1-lockup` re-validates successfully (fresh `seen-outpoints` accumulator, no persisted record of the outpoint), crediting `sats` to bond B as well -- the same BTC lockup now counts toward two (or more, repeated over further bonds) separate bonds' `protocol-bonds-total-staked` and signer/reward shares, despite only one BTC UTXO ever being locked.

    pub(crate) fn pox_5_make_signer_set<I>(
        entries: &mut I,
        pox_constants: &PoxConstants,
    ) -> Result<Pox5SignerSetOutput, ChainstateError>
    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }
