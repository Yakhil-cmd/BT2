**Rationale:**

The `PeerNetworkId` key used in `inbound_peer_rate_limiters` is not attacker-controlled content — it is derived from the network layer's authenticated peer identity, not from the transaction or `MempoolSyncMsg` payload itself.

In `process_received_txns`, the `PeerNetworkId` used to spawn `tasks::process_transaction_broadcast` is constructed from `network_id` (the local network instance receiving the message) and `peer_id`, which originates from the `ReceivedMessage.sender` field set by the network/transport layer, not from unprivileged transaction input. [1](#0-0) 

This peer identity is bound during the Noise-IK handshake: the remote peer's claimed `PeerId` is either checked against a `trusted_peers` set (`authenticate_inbound`) in mutual-auth mode, or cryptographically re-derived from the negotiated x25519 public key and compared against the claimed ID in `MaybeMutual` mode, rejecting any mismatch as `ClientPeerIdMismatch`. [2](#0-1) 

An unprivileged attacker cannot forge this binding from the application layer (mempool message content) — spoofing would require breaking the Noise-IK authenticated transport itself, which is a peer-driven/network-layer attack explicitly excluded by the boundary conditions ("Ignore peer-driven scenarios").

Moreover, even in the hypothetical case of a mismatched rate-limit bucket, this only affects per-peer rate limiting/backoff bookkeeping in mempool's gossip layer, not the transaction's actual sender, signer set, sequence number, expiry, or chain-id, all of which are validated independently against the `SignedTransaction` in VM validator and core mempool admission logic in `gen_ack_response`/`process_transaction_broadcast`. [3](#0-2) 

This does not meet the Admission Impact Gate: no unauthorized execution, replay, sequence/expiry/chain-id/domain rebinding, or authenticator/approval confusion results from this rate-limiter keying — it is, at most, a peer-identity bookkeeping concern gated behind the authenticated transport layer, which is out of scope per the boundary conditions.

/// If we encounter `MempoolIsFull` or `RateLimited` on any of the
/// transactions, provide backpressure to the downstream peer.
fn gen_ack_response(
    message_id: MempoolMessageId,
    results: Vec<SubmissionStatusBundle>,
    peer: &PeerNetworkId,
) -> MempoolSyncMsg {
    let mut backoff_and_retry = false;
    for (_, (mempool_status, _)) in results.into_iter() {
        if mempool_status.code == MempoolStatusCode::MempoolIsFull
            || mempool_status.code == MempoolStatusCode::RateLimited
        {
            backoff_and_retry = true;
            break;
        }
    }

    update_ack_counter(
        peer,
        counters::SENT_LABEL,
        backoff_and_retry,
        backoff_and_retry,
    );
    MempoolSyncMsg::BroadcastTransactionsResponse {
        message_id,
        retry: backoff_and_retry,
        backoff: backoff_and_retry,
    }
}
