## Analysis Result

I found a concrete analog: `WebhooksController#verify_signature` binds the HMAC check to an org selected from an attacker-controlled payload field (`repository.owner.login`), while `StatusHandler#process` performs its write using a completely different, globally-scoped field (`sha`) with no repository/stack binding at all. This breaks the "organization authenticated vs. repository that is written" equality described in the rules.

### Title
Cross-repository commit status forgery via unscoped SHA lookup in webhook status handler - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` will validate the signature using an attacker-supplied payload field: `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. Once verification passes, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-derives or checks the repository/stack from that same organization — it queries `Commit.where(sha: params.sha)` globally across every stack in the installation and calls `commit.create_status_from_github!(params)`. The organization that authenticates the request and the repository whose commit gets written are two independent, uncorrelated fields. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This mirrors the ERC4626-style "inflation" bug class at a structural level: a value that is checked/authorized (the `MIN_LIQUIDITY`/share accounting in the FlatCoin report; here, the *organization* whose secret validated the signature) is decoupled from the value that is actually acted upon (the assets-per-share used at withdrawal time; here, the *commit/stack* whose status gets mutated).

Concretely:
1. `verify_signature` computes `repository_owner` from the JSON body itself (`params.dig('repository', 'owner', 'login')` with fallback to `params.dig('organization', 'login')`), then calls `Shipit.github(organization: repository_owner)` to pick the corresponding configured GitHub App/secret, and verifies the raw body's HMAC against that secret. [4](#0-3) 
2. `Handler#stacks`/`Handler#repository_name` (the base class used by most handlers) scopes lookups by `payload.dig('repository', 'full_name')`, tying writes to the repository named in the payload. [5](#0-4) 
3. `StatusHandler`, however, does **not** use `stacks`/`repository_name` at all. It matches on `params.sha` globally across the entire `commits` table (not scoped by stack or repository), then calls `create_status_from_github!` on every match. [3](#0-2) 
4. `Commit.create_status_from_github!` replicates the forged status/state/description/target_url onto the commit's `statuses` association unconditionally, and triggers `commit_status`/`deployable_status` hook emission and `stack.schedule_merges`. [6](#0-5) [7](#0-6) 

Because `sha` values are attacker-known (git commit SHAs are public via GitHub) and match across the `commits` table irrespective of `stack_id`, an attacker who controls (or is a collaborator/bot member on) **any** GitHub organization configured in Shipit's multi-tenant `github:` config — particularly one whose `webhook_secret` is unset — can:
- Set `repository.owner.login` (or `organization.login`) to the org whose secret they know/whose secret is blank (per `verify_webhook_signature`, `return true unless webhook_secret`, i.e. an org with no configured secret trivially passes verification). [8](#0-7) 
- Set the payload's `sha` to a commit SHA belonging to a **different** organization's stack tracked by the same Shipit instance.
- Have `StatusHandler` write an arbitrary CI status (`state`, `description`, `target_url`, `context`) onto that unrelated commit, because the handler performs no cross-check between the org that authenticated the webhook and the stack that owns the commit.

### Impact Explanation
`Commit#deployable?` depends directly on `success?`/`blocked?`, which derive from the `statuses` written by this handler. [9](#0-8)  A forged "success" status on a target repository's commit can:
- Make an otherwise-failing/un-vetted commit appear `deployable?`, feeding `Stack#schedule_continuous_delivery`/`ContinuousDeliveryJob`, i.e. triggering an **unauthorized deploy** of a commit that never actually passed CI in the target repository. [10](#0-9) 
- Unblock merges via `stack.schedule_merges` on a stack the attacker does not own.

This satisfies the "unauthorized deploy" Critical-impact category and "cross-repository writes," since the write (commit status affecting deployability) crosses from the attacker's authenticated organization into a stack belonging to a different, uninvolved repository/organization.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml` showing two orgs), and (b) that at least one configured org's `webhook_secret` is unset/blank, OR the attacker otherwise knows a valid webhook secret for any one configured org (e.g., their own org's Shipit-managed webhook). [11](#0-10)  Given `verify_webhook_signature` explicitly treats a blank secret as "always verified," this is a realistic misconfiguration this code path was not designed to be safe against, and no repository write access, session, or `ApiClient` token is required — only the ability to send a POST to the public `/webhooks` endpoint with a crafted JSON body and a real (public) target SHA.

### Recommendation
`StatusHandler#process` must scope its `Commit` lookup by the repository named in the *same organization/repository* whose secret validated the signature (i.e., use the `Handler#stacks`/`repository_name` scoping like other handlers, not a bare global `Commit.where(sha:)`). Additionally, `GithubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank; a missing secret should be treated as unverifiable/rejected rather than trivially passing.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (webhook_secret unset or known to the attacker) and `victim-org` (unrelated, tracked stack with commit SHA `abc123...` currently pending/unknown status).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "abc123...",           // real commit SHA belonging to victim-org's tracked stack
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Compute `X-Hub-Signature` using `attacker-org`'s webhook secret (or omit/blank secret if `attacker-org` has none configured).
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and passes verification.
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")` — matching the commit in `victim-org`'s stack — and calls `create_status_from_github!`, injecting a forged "success" status that can unblock deploy/merge for a stack the attacker never had write access to.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
