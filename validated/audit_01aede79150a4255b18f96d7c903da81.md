### Title
ERC20Transactor XCM asset transactor permanently rejects legitimate ERC20 tokens that don't strictly return `bool` on `transfer` - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` treat any ERC20 `transfer` return payload that cannot be strictly ABI-decoded as `bool` as a hard transaction failure (`XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`), even when the underlying token contract call succeeded (did not revert). This is the FRAME/XCM analog of the reported `Erc20CheckedTransfer` bug class: any token whose `transfer`/`transferFrom` doesn't return a canonical `bool` (e.g. many real-world non-standard ERC20s, including legacy tokens with no return data) can never be withdrawn or deposited through this transactor, regardless of whether the transfer actually succeeded.

### Finding Description
`ERC20Transactor` is a `TransactAsset` implementation used to represent EVM/`pallet-revive` ERC20 contracts as XCM fungible assets [1](#0-0) .

In `withdraw_asset_with_surplus`, the code calls the target ERC20 contract's `transfer` via `pallet_revive::Pallet::<T>::bare_call`, and then, if the call did not revert, unconditionally tries to strictly ABI-decode the return data as `bool`: [2](#0-1) 

If `IERC20::transferCall::abi_decode_returns_validate` fails (e.g. because the token has no return value, or returns something else that isn't a strict `bool`), the withdrawal is treated as a `FailedToTransactAsset` error — even though the contract call itself succeeded (`did_revert()` was `false`).

The same pattern is repeated in `deposit_asset_with_surplus`: [3](#0-2) 

This exactly mirrors the reported bug class: "tokens that don't return true on successful transfer will always revert." The reported fix in the Solidity report was to use OpenZeppelin's `safeTransfer`/`safeTransferFrom`, which treats a call that reverts as failure but treats a call that succeeds with *no* return data (or non-boolean-decodable data) as success. `ERC20Transactor` does the opposite: it requires a strictly decodable `bool` and fails otherwise, regardless of actual on-chain success.

This is reachable through a normal, permissionless `PolkadotXcm::execute` extrinsic performing `WithdrawAsset`/`DepositAsset` on an `AccountKey20` asset location pointing at an ERC20 contract, as demonstrated by the existing repository test `smart_contract_does_not_return_bool_fails`, which instantiates a contract implementing `transfer` but returning a `uint256` instead of `bool`, and shows that XCM execution fails: [4](#0-3) 

### Impact Explanation
Because the XCM executor wraps `WithdrawAsset`/`DepositAsset` processing in `Config::TransactionalProcessor::process`, which uses `frame_support::storage::with_transaction` (`FrameTransactionalProcessor`) [5](#0-4) , all storage side effects of the failed instruction — including the ERC20 contract's own storage writes performed inside `pallet_revive::bare_call` — are rolled back together with the XCM holding/fees registers on error [6](#0-5) . This means the flaw does **not** cause fund loss or double-spend; the net effect is a **denial of service**: any legitimate ERC20 token contract that does not strictly return a decodable `bool` from `transfer` (a common real-world non-conformance — many production tokens omit the return value entirely, matching the exact scenario the original report describes) becomes permanently unusable as an XCM fungible asset via this transactor. Users cannot withdraw, deposit, or otherwise move such tokens through XCM `execute`/teleport/transfer paths that route through `ERC20Transactor`, even though the tokens function normally when interacted with directly.

### Likelihood Explanation
High likelihood of being triggered unintentionally: any pre-existing or newly deployed ERC20 contract on `pallet-revive` that deviates from strict OpenZeppelin-style `bool`-returning `transfer`/`transferFrom` semantics (no return value, differently-typed return, etc.) will hit this path on the very first `WithdrawAsset`/`DepositAsset` XCM instruction referencing it. No privileged role or attacker action is required — a completely ordinary signed account executing a permissionless `PolkadotXcm::execute` extrinsic against such a token triggers the failure, as shown by the existing test.

### Recommendation
Follow the same remediation direction as the original report (SafeERC20-style handling) adapted to this ABI-decode boundary:
- Treat a non-reverting call with **empty** return data as success (matching common non-standard ERC20 behavior), rather than requiring a strictly decodable `bool`.
- Only fail decode when the return data is non-empty but does not correctly decode to `bool`, or continue to fail on `did_revert()`.
- Add explicit test coverage for the "no return data, transfer succeeded" case in addition to the existing "wrong-typed return data" test, to avoid conflating the two distinct non-standard-token behaviors.

### Proof of Concept
The repository's own test suite already demonstrates the failure path end-to-end, though it validates the current (overly strict) rejection behavior rather than exercising the "no return data at all" variant explicitly:
- Test: `smart_contract_does_not_return_bool_fails` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` (lines 2028–2081) instantiates an ERC20-like contract (`MyTokenFake`) whose `transfer` returns a `uint256` instead of `bool`, mints/funds all accounts, then submits a signed `PolkadotXcm::execute` XCM program performing `withdraw_asset` against the contract's `AccountKey20` location, and asserts the overall XCM execution `is_err()`.
- This confirms: (1) the entry point is a real, permissionless, signed `pallet_xcm::execute` extrinsic; (2) the failure is deterministic and reproducible with existing test harness code; (3) execution "fails but doesn't panic" — i.e., it is a clean but total rejection of the asset, not a crash, consistent with the DoS characterization above.
- I did not run this test myself (no execution environment available in this session); the PoC status is "code-verified, not executed" — the test exists in-repo and its logic was read directly, but I have not confirmed a live `cargo test` run output in this session.

I was unable to fully verify within this session whether `ERC20Transactor` is the actively wired `AssetTransactor` in the production `asset-hub-westend` runtime XCM config (only grep matches in `xcm_config.rs`/`bridge_to_ethereum_config.rs`/`lib.rs` were found, not the full wiring code), so full "live production wiring" confirmation is incomplete — this should be verified further (e.g., by reading `asset_hub_westend_runtime::xcm_config` in full) before treating this as confirmed-in-production versus configured-but-optional.

/// Transactional processor implementation using frame transactional layers.
pub struct FrameTransactionalProcessor;
impl ProcessTransaction for FrameTransactionalProcessor {
	const IS_TRANSACTIONAL: bool = true;

	fn process<F>(f: F) -> Result<(), XcmError>
	where
		F: FnOnce() -> Result<(), XcmError>,
	{
		with_transaction(|| -> TransactionOutcome<Result<_, DispatchError>> {
			let output = f();
			match &output {
				Ok(()) => TransactionOutcome::Commit(Ok(output)),
				_ => TransactionOutcome::Rollback(Ok(output)),
			}
		})
		.map_err(|error| {
			tracing::debug!(target: "xcm::transactional", ?error, "Failed to process XCM transaction");
			XcmError::ExceedsStackLimit
		})?
	}
}

	/// Execute `f` inside a transactional context that backs up and restores `holding` and
	/// `fees` on failure.
	fn transactional_process(
		&mut self,
		f: impl FnOnce(&mut Self) -> Result<(), XcmError>,
	) -> Result<(), XcmError> {
		self.transactional_process_with_custom_rollback(f, |_| {})
	}

	/// Like [`Self::transactional_process`], but also calls `on_rollback` when the
	/// transaction is rolled back.
	///
	/// NOTE: holding and fees registers are already automatically rolled back. Custom handler
	/// is for _extra_ rollback logic.
	fn transactional_process_with_custom_rollback(
		&mut self,
		f: impl FnOnce(&mut Self) -> Result<(), XcmError>,
		on_rollback: impl FnOnce(&mut Self),
	) -> Result<(), XcmError> {
		let mut backup_holding = BackupAssetsInHolding::safe_backup(&self.holding);
		let mut backup_fees = BackupAssetsInHolding::safe_backup(&self.fees);
		let result = Config::TransactionalProcessor::process(|| f(self));
		if Config::TransactionalProcessor::IS_TRANSACTIONAL && result.is_err() {
			backup_holding.restore_into(&mut self.holding);
			backup_fees.restore_into(&mut self.fees);
			on_rollback(self);
		}
		result
	}
