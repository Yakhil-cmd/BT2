### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` unblocks deploys through the blocking-commit path - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Commit#blocked?` performs no repository-origin verification of its own; it simply asks whether any reachable, undeployed commit in `stack.commits` is `blocking?`, and `blocking?` is a plain delegate to that commit's `status`. The actual binding failure lives upstream in `Webhooks::Handlers::StatusHandler#process`, which resolves target commits with a global `Commit.where(sha: params.sha)` instead of scoping to the webhook's own repository, so a validly-signed status webhook from an attacker-controlled repository can write a `Status` onto an unrelated stack's commit — including an intermediate "blocking" commit — and that forged status is picked up unmodified by `blocked?`/`deployable?`.

### Finding Description
The claimed binding is: `status.commit.stack.repository == payload.repository` (i.e., the Status a `status` webhook creates should only ever attach to a commit belonging to the repository named in that webhook's payload). This binding is broken.

- `Webhooks::Handlers::Handler#stacks` correctly scopes lookups by the payload's own repository: `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) .
- `StatusHandler#process`, however, does **not** use that scoped `stacks` helper. It resolves commits globally by SHA across the entire `commits` table and pushes the status onto every match: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
- `create_status_from_github!` then writes the Status using that matched commit's *own* `stack_id`, not the payload's repository: `statuses.replicate_from_github!(stack_id, github_status)` [3](#0-2) .
- `Commit#blocked?` trusts these Status rows with no additional cross-checking: `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)`, where `blocking?` is delegated straight to `status` [4](#0-3) .
- `deployable?` and `Stack#trigger_continuous_delivery`/`next_commit_to_deploy` consume `blocked?` unchanged [5](#0-4) [6](#0-5) .

Exploit flow: if a victim stack's undeployed history contains a commit (`sha X`) whose CI context is currently failing/pending and configured as `ci.blocking`, and that exact commit content also exists (identical SHA, e.g. via fork/mirror) in a repository the attacker controls within the same GitHub organization that Shipit is configured for, the attacker sets a `success` status on `sha X` in their own repo through GitHub's normal status API. GitHub delivers a real, correctly signed `status` webhook (signature checked per-organization via `Shipit.github(organization: repository_owner)` [7](#0-6) , not per-repository). `StatusHandler#process` then matches the victim's commit purely by SHA and writes the forged `success` Status onto it, using that commit's real `stack_id`. The blocking commit's `blocking?` flips to false, `Commit#blocked?` for the later target commit becomes false, `deployable?` becomes true, and `Stack#trigger_continuous_delivery` ships it.

None of the existing guards prevent this: `verify_signature` only authenticates that the payload came from GitHub for *some* repository under the resolved organization, not that the SHA in question belongs to that repository; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository ownership; `Handler#stacks`'s repository scoping is bypassed entirely because `StatusHandler#process` doesn't call it.

### Impact Explanation
A record (a `Status` row, and transitively a `Deploy`) is written for a repository/stack that never authenticated the triggering event — the forged status originates from the attacker's own repository but lands on a commit owned by a different stack. This satisfies the Critical bucket "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy". The blocking-commit variant is notable because it lets the attacker clear a safety gate (`ci.blocking`) without ever forging a status on the commit that actually gets deployed, making the tampering less directly visible on the deployed commit's own status history. Blast radius is bounded to stacks whose commits share an identical SHA with a repository the attacker can write statuses to — realistically forks/mirrors within the same GitHub organization configured in Shipit's `secrets.github`.

### Likelihood Explanation
Preconditions: (1) a Shipit host configured with per-organization GitHub Apps (`secrets.github`); (2) the attacker controls or can set commit statuses on some repository within one of those configured organizations; (3) a victim stack in the same organization has an undeployed, currently-failing/pending commit configured as `ci.blocking`, whose SHA is duplicated in the attacker's repository (fork/mirror relationship, or any scenario where identical commit content exists in two repos of the same org). Given those preconditions, the attack is cheap and repeatable per matching SHA. It requires no Shipit session, API token, or secret — only ordinary GitHub write access to a repo the attacker controls within the shared organization.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the webhook's own repository/stacks instead of a global SHA query — e.g., resolve via `stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }` (mirroring `Handler#stacks`) rather than `Commit.where(sha: params.sha)`, so a status can only ever be attributed to a commit belonging to a stack whose repository matches the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (no live GitHub):
1. Fixtures: `stack_a` (attacker-owned, repository `attacker/repo`) and `stack_b` (victim, repository `victim/repo`), both under the same configured organization.
2. Create `blocking_commit` in `stack_b` with SHA `X`, CI context configured in `stack_b`'s `ci.blocking`, and a `pending`/`failure` status — assert `blocking_commit.blocking?` is true.
3. Create `target_commit` in `stack_b`, newer than `blocking_commit`, with a passing required status — assert `target_commit.blocked?` is true and `target_commit.deployable?` is false.
4. Create a second commit row with the same SHA `X` attached to `stack_a` (simulating the identical forked commit).
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => 'X', 'state' => 'success', 'context' => <blocking context>, 'repository' => { 'full_name' => 'attacker/repo' }, ...)` directly (bypassing only the HTTP/signature layer, which is out of scope here).
6. Assert: `blocking_commit.reload.blocking?` becomes false; `target_commit.reload.blocked?` becomes false and `deployable?` becomes true; calling `stack_b.trigger_continuous_delivery` creates a `Deploy` for `target_commit` (`assert_difference('Deploy.count', 1)`), demonstrating the equality `status.commit.stack.repository == payload.repository` no longer holds and directly caused an unauthorized deploy.
