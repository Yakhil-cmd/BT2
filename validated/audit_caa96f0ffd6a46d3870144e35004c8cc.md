### Title
Stale `Account.owner` lets a former position-NFT owner keep spending authority after transfer — (`contracts/controller/src/account.rs`)

### Summary
`Controller.withdraw()` and `Controller.borrow()` authorize the caller against `account.owner`, a field written once at account creation and never resynchronized with the position NFT's current owner. Because `require_owner_or_delegate` compares `caller` to this *stored* owner rather than to `position_nft.owner_of(account_id)`, whoever held the NFT at mint time retains full spending authority even after transferring the NFT away. This is the direct analog of the reported missing `_spendAllowance()` flaw: a withdrawal is executed against an account by an address that is no longer its owner, with no check against current ownership.

### Finding Description
- `process_withdraw` loads the account and calls `require_owner_or_delegate(env, account_id, caller, &account.owner)`, then pays out to `to.unwrap_or(caller)` (`contracts/controller/src/positions/supply.rs:140-157`).
- `is_owner_or_delegate` returns `true` when `caller == owner`, where `owner` is `&account.owner` — the `Account` struct field populated at creation in `create_account` (`contracts/controller/src/account.rs:64-70`, `:121-122`, `:130-140`).
- `account.owner` is assigned only in `create_account`; no code path rewrites it on NFT transfer. By contrast, `require_account_owner` (used for `renew_account`, `add_delegate`, `remove_delegate`) correctly resolves the live owner through `storage::account_owner(env, account_id)`, which consults the NFT (`account.rs:143-148`). The owner-only verbs authenticate the *current* NFT holder; the owner-or-delegate verbs (borrow, withdraw, multiply, swap_debt, swap_collateral, repay_debt_with_collateral, migrate_from_blend) authenticate the *stale* stored owner.
- Corollary documented in `docs/reference/invariants.md` (INV-AUTH-02): a delegate grant "is inactive under another owner but can reactivate if the NFT returns" — grants are keyed to the stored owner, confirming the stored owner, not the NFT owner, is the authority root for spending verbs.
- Result: after `position_nft.transfer(seller → buyer)`, the buyer owns the NFT and the account's collateral on paper, but `seller` can still call `withdraw(caller=seller, account_id, withdrawals=whole position, to=Some(seller))` and `borrow(...)` — draining collateral and drawing debt the buyer must now bear — while the buyer cannot call any owner-gated verb at all.

### Impact Explanation
Theft of user funds / protocol insolvency. The previous owner can withdraw all supply positions and borrow up to the account's risk limits after selling or transferring the position NFT, extracting real tokens from the pool while the buyer is left holding an emptied or over-leveraged account NFT. Additionally, the *legitimate* current NFT owner is permanently locked out of `withdraw`, `borrow`, `add_delegate`, and every owner-gated strategy verb on accounts they acquired via transfer, which is also a freezing-of-funds condition for them (they can only receive permissionless operations like `repay` or third-party `supply` top-ups).

### Likelihood Explanation
Reachable by any unprivileged address: the attacker is simply the seller of a position NFT. The path is `position-nft::transfer(from=seller, to=buyer, token_id)` followed by `controller::withdraw(caller=seller, account_id, …, to=Some(seller))`. No privileged role, leaked key, or off-chain component is needed; the only precondition is that a counterparty buys or receives the NFT, which is the designed purpose of a transferable position NFT.

### Recommendation
In `is_owner_or_delegate` (or `require_owner_or_delegate`), resolve ownership via `storage::account_owner(env, account_id)` — the live NFT `owner_of` — instead of the stored `account.owner`, and key delegate lookups to that live owner. Alternatively, add a controller hook invoked by `position-nft::transfer` that rewrites `account.owner`, and clear per-owner delegate grants on transfer (the current design explicitly allows dormant grants to reactivate, compounding the stale-authority problem). All owner-or-delegate entrypoints (`withdraw`, `borrow`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) must authenticate against post-transfer ownership.

### Proof of Concept
1. Alice calls `controller::supply(caller=alice, account_id=0, spoke_id, assets)` → receives `account_id = N` backed by NFT `N`.
2. Alice transfers NFT `N` to Bob via `position-nft::transfer(alice → bob, N)`. `account.owner` remains `alice`.
3. Bob (current NFT owner) calls `controller::withdraw(caller=bob, N, …)` → reverts `NotAuthorized` because `bob != account.owner` and Bob holds no grant keyed to `alice`.
4. Alice calls `controller::withdraw(caller=alice, N, withdrawals=[{hub_asset, 0} (withdraw-all)], to=Some(alice))` → `caller == account.owner` passes, solvency is vacuously satisfied if no debt, and the pool pays Bob's collateral to Alice.

Note on verification: the exploit hinges on `account.owner` never being updated by NFT transfer; my searches found no `account.owner` reassignment or transfer hook in `contracts/position-nft`/`contracts/controller`, and the invariants doc confirms stored-owner-keyed grants persist across transfers. I did not read `position-nft/src/contract.rs` in full before the iteration limit, so if a transfer→controller resync hook exists in unindexed lines, this finding would be invalidated; if none exists, the analog stands.
