### Title
Webhook signature is verified against the organization derived from the payload, but every handler acts on a repository/organization identity read from the same unverified payload with no cross-check - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to HMAC-verify the delivery against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted JSON body. Every event handler then re-reads repository/organization identity fields from that *same* body to decide which `Stack`, `Repository`, or `Team` to mutate, without ever confirming those fields match the organization whose secret was actually used to authenticate the request. This breaks the binding "organization that authenticated == repository/organization that is written."

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` picks the signing organization from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves a per-organization `GitHubApp` instance with its own `webhook_secret`, and `verify_webhook_signature` HMACs the raw body against that org's secret only: [3](#0-2) 

Once verified, the full, still-untrusted `params` hash is dispatched unchanged to every registered handler for the event: [4](#0-3) 

Handlers independently pick their own target repository from a *different* payload field, `repository.full_name`, with no re-validation against `repository.owner.login` used for signing: [5](#0-4) 

For example `PushHandler` uses this repository lookup to select and mutate stacks: [6](#0-5) 

`MembershipHandler` is worse: it trusts `organization.login` from the body to create/attach a `Team`, and that `Team`'s membership is what `Shipit.github_teams` authorization checks against: [7](#0-6) [8](#0-7) 

Because Shipit supports multiple GitHub organizations, each with its own independently-managed `webhook_secret` (`lib/shipit.rb` `github_app_config`/`github` methods build one `GitHubApp` per organization key), signature verification only proves "this body was HMAC-signed with *some* configured organization's secret" — it does not prove that the `repository.full_name`, `organization.login`, or `team` fields inside that same body actually belong to that organization. An attacker who legitimately controls (or has been given) a real GitHub webhook for Organization A can freely author the JSON body delivered to Shipit's endpoint (a webhook is just an HTTP POST triggered by GitHub events on A's repos, but the delivery is proxied through GitHub only for shape/timing — the attacker who administers Org A's webhook already knows Org A's `webhook_secret`, since they configured it). Using that secret, they can sign an arbitrary payload where `repository.owner.login`/`organization.login` = "OrgA" (to pass signature verification) while `repository.full_name` = "OrgB/some-repo" or `team`/`member.login` reference an entirely different organization/team tracked by the same Shipit instance.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding named in scope. Concretely:
- `push`/`status`/`check_suite` handlers can be forged against a `Stack` belonging to a repository/organization the attacker has no access to, using a secret from an unrelated organization they do control — a cross-repository write, since these events mutate `Commit`, `Status`, and `Stack` state (`sync_github`, statuses, check runs) for repos outside the authenticated org.
- `MembershipHandler` can add an arbitrary GitHub login as a member of any `Team` (including one matching `Shipit.github_teams`), which is the exact set gating `User#authorized?`. This is a direct escalation into `Shipit.github_teams` authorization, letting an attacker grant themselves (or an accomplice's GitHub identity) access to the whole Shipit instance without ever having real membership in the authorizing GitHub organization.

Both outcomes map to explicitly in-scope Critical/High impacts (cross-repository writes; escalation into `Shipit.github_teams` authorization).

### Likelihood Explanation
Exploitability requires the attacker to already control a legitimate webhook secret for at least one organization configured in the multi-tenant `secrets.github` map — a realistic scenario for large Shipit deployments serving many orgs/teams, since webhook secrets are typically provisioned per-org and are not treated as globally trusted material equivalent to app-wide credentials. No GitHub API access, TLS interception, or Shipit session is needed; only an HTTP POST to `/github/webhooks` with a body crafted and HMAC-signed by the attacker.

### Recommendation
Bind the identity used for signature verification to the identity acted upon: after selecting `github_app` by `repository_owner`, re-validate that every identity field consumed downstream (`repository.full_name`'s owner segment, `organization.login`, `team.organization`) equals `repository_owner`/the verified organization before dispatching to handlers, and reject mismatches with `422`.

### Proof of Concept
1. Attacker administers Organization A's GitHub App/webhook integration with Shipit and thus knows `webhook_secret_A`.
2. Attacker crafts a `membership` event JSON body:
   ```json
   {
     "action": "added",
     "team": { "id": 999, "name": "Admins", "slug": "admins", "url": "https://api.github.com/teams/999" },
     "organization": { "login": "OrgB" },
     "member": { "login": "attacker-controlled-login" },
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and POSTs to `/github/webhooks` with `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret_A` matches — signature passes.
5. `MembershipHandler#process` runs unmodified against `params.organization.login == "OrgB"` / `params.team.id == 999`, creating/attaching `Team` 999 under `OrgB` and adding `attacker-controlled-login` to it — even though the request was authenticated only for `OrgA`.
6. If `Team` 999 corresponds to one of `Shipit.github_teams`, the attacker's GitHub login now satisfies `User#authorized?`, granting access to the Shipit instance.

**Note:** I could not fully verify from the index how `secrets.github` is provisioned for multi-organization deployments in this particular hosting setup (i.e., whether operators always use one shared secret vs. per-org secrets in practice), which affects the practical likelihood of an attacker holding a *different* org's real webhook secret. This is a config/deployment detail outside `app/**`/`lib/shipit/**`, and I did not find a code-level assertion in this engine that forbids or discourages per-org secrets — the code in `lib/shipit.rb`/`lib/shipit/github_app.rb` clearly supports independent secrets per organization key, which is what makes this binding gap concrete rather than purely theoretical.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
