### Title
Forged `reopened` webhook verified via an unrelated org can re-provision another org's review stack — (File: `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the signing org strictly from `params.dig('repository','owner','login')`, while `ReopenedHandler` (like `OpenedHandler`) resolves the actual repository to act on from a completely separate field, `params.repository.full_name`. Because nothing cross-checks that these two independently-attacker-controlled JSON fields describe the same repository, an attacker who controls an org configured in Shipit with `webhook_secret` unset can forge a `reopened` event whose `repository.owner.login` matches their own (secret-less) org while `repository.full_name` names a repository owned by a different, victim org.

### Finding Description
The claimed binding is: `repository_owner` used by `verify_signature` (i.e. `params.dig('repository','owner','login')`) == owner of the repository resolved and mutated by the handler (`Repository.from_github_repo_name(params.repository.full_name)`'s owner).

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` only, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank/nil: `return true unless webhook_secret`. [3](#0-2) 
- `ReopenedHandler#repository` resolves the acted-upon repository purely from `params.repository.full_name` via `Repository.from_github_repo_name`, which is a separate field of the same JSON body, never compared to `repository.owner.login`: `Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new`. [4](#0-3) 
- `Repository.from_github_repo_name` splits `owner/name` directly out of `full_name` and does a bare DB lookup with no scoping to the verifying org. [5](#0-4) 
- Once resolved, `ReopenedHandler#process` calls `stack.unarchive!`, which is `ReviewStackAdapter#unarchive!`; if no stack exists it calls `create!`, persisting a new `ReviewStack` scoped to `repository.review_stacks` and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` (`stack.enqueue_for_provisioning`), and if one exists (archived), it re-adds it to the provisioning queue and unarchives it. [6](#0-5) [7](#0-6) [8](#0-7) 
- Later, `ReviewStackProvisioningQueue#work` iterates queued stacks and invokes `stack.provision` → `stack.provisioner.up`, which is where `Command`/`PTY.spawn`-based provisioning actually executes. [9](#0-8) [10](#0-9) 

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request` and body:
```json
{
  "action": "reopened",
  "number": <victim PR number>,
  "pull_request": { ... valid schema fields, e.g. head.ref = attacker-controlled branch ... },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sender": { "login": "attacker" }
}
```
Requirement: `attacker-org` must be a Shipit-configured org (multi-org `github:` config, as documented) whose `webhook_secret` is unset — this is an explicitly permitted precondition of the question and a documented (`docs/setup.md`) supported configuration shape (the example templates even show `webhook_secret:` left blank). Because `verify_signature` keys entirely off `repository.owner.login`, no `X-Hub-Signature` value from the attacker's own org is required to pass; the request is accepted, `drop_unhandled_event` passes because `pull_request` is handled, and `ReopenedHandler` fires with `params.repository.full_name` pointing at `victim-org/victim-repo`.

Existing guards fail because: `verify_signature`'s org derivation and `ReopenedHandler#repository`'s org/repo resolution use two disjoint JSON keys of the attacker-controlled body with no equality check between them; `ExplicitParameters` only validates types/presence, not cross-field consistency; `drop_unhandled_event` only checks the event is handled, not repository identity.

### Impact Explanation
An attacker who only controls a Shipit-recognized org with no webhook secret can, without any interaction from the victim org, cause Shipit to create/unarchive a `ReviewStack` scoped to the victim's repository and enqueue it for provisioning, which eventually drives `Command`/`PTY.spawn`-based infrastructure provisioning for that repository — i.e., a payload authenticated for one org mutates another org's stack/infrastructure. This matches the Critical category "a payload for one repository mutating another's stack ... or an unauthorized deploy". The attack is repeatable against any repository already tracked by Shipit (`Repository.from_github_repo_name` must find a match) and for any PR number, letting the attacker force provisioning cycles (and associated deploy commands) on arbitrary victim repos.

### Likelihood Explanation
Requires: (1) Shipit deployed in the documented multi-org configuration mode (`docs/setup.md` "Using Multiple Github Applications") with at least one configured org lacking a `webhook_secret` — a config shape the docs' own example templates show as blank by default; (2) the attacker controls (or names) that org in the forged payload; (3) the target repository is already tracked in Shipit's `repositories` table under a different owner. Attacker cost is a single crafted HTTP POST with no valid GitHub signature and no Shipit credentials. This is fully repeatable and scales to any tracked repository.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, and correspondingly in every `pull_request` handler (`ReopenedHandler`, `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`), enforce that the org used to verify the signature is the same org embedded in `repository.full_name` (i.e., reject if `full_name.split('/').first.casecmp(repository_owner) != 0`), or better, resolve the target `Repository`/org exclusively from the same field used for signature verification, never trusting `full_name` independently for tenant scoping.

### Proof of Concept
Minitest plan (add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` or a new webhook-integration test):
```ruby
test "cross-org forged reopened webhook re-provisions a review stack owned by a different org" do
  victim_repo = shipit_repositories(:shipit) # owner: "shopify"
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  # Simulate an org ("forge-org") configured in Shipit with no webhook_secret
  Shipit.stubs(:github).with(organization: "forge-org").returns(
    Shipit::GitHubApp.new("forge-org", webhook_secret: nil)
  )

  payload = payload_parsed(:pull_request_reopened)
  payload["repository"]["owner"] = { "login" => "forge-org" }         # used by verify_signature
  payload["repository"]["full_name"] = victim_repo.github_repo_name    # used by ReopenedHandler

  # Binding equality that should hold but doesn't:
  # repository_owner ("forge-org") == full_name.split('/').first ("shopify") -> false

  assert_difference -> { Shipit::ReviewStack.count }, 1 do
    Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process
  end

  stack = victim_repo.review_stacks.last
  assert stack.awaiting_provision?, "victim org's stack was enqueued for provisioning by a forged webhook verified via a different org"
end
```
This demonstrates the divergence between the verifying org (`forge-org`, no secret) and the owning org of the mutated repository (`shopify`), and shows a `ReviewStack` for the victim's repository being created/enqueued for provisioning as a direct result.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
