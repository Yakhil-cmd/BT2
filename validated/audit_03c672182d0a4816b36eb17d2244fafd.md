### Title
`pox_lock_update_v5` reschedules the unlock height before validating it is not earlier than the existing lock, allowing `stake-update` to silently shorten a lock - ([File: pox-locking/src/pox_5.rs])

### Summary
`pox_lock_update_v5` calls `snapshot.update_unlock_v5(unlock_burn_height)` unconditionally and only afterwards checks that the *amount* did not decrease (`bal.amount_locked() > new_total_locked`). There is no check that `unlock_burn_height` is not less than the account's pre-existing `STXBalance.unlock_height`, unlike the sibling function `pox_rollover_v5`, which explicitly enforces `unlock_burn_height <= bal.unlock_height() => Err(PoxInvalidUnlockHeight)`.

### Finding Description
The broken equality is: `unlock_height_chosen_at_stake(staker) == unlock_height_honored_after_stake_update(staker)`.

In `pox-locking/src/pox_5.rs`:
```
pub fn pox_lock_update_v5(...) -> Result<STXBalance, LockingError> {
    ...
    snapshot.update_unlock_v5(unlock_burn_height)?;          // <-- unconditional reschedule

    let bal = snapshot.canonical_balance_repr()?;
    let total_amount = ...;
    if total_amount < new_total_locked { return Err(PoxInsufficientBalance); }
    if bal.amount_locked() > new_total_locked { return Err(PoxInvalidIncrease); } // amount-only guard
    snapshot.increase_lock_v5(new_total_locked)?;
    ...
}
``` [1](#0-0) 

The function updates the unlock height first, then only guards against the locked *amount* decreasing — never against the unlock *height* decreasing. Contrast this with `pox_rollover_v5`, which explicitly rejects a non-forward move:
```
if unlock_burn_height <= bal.unlock_height() {
    return Err(LockingError::PoxInvalidUnlockHeight);
}
``` [2](#0-1) 

The call path is: `handle_contract_call` dispatches `"stake-update"` to `handle_stake_lockup_update_pox_v5`, which parses the Clarity `(ok {...})` response from the `stake-update` public function and unconditionally forwards the reported `unlock-burn-height` to `pox_lock_update_v5` with no comparison against the account's current lock: [3](#0-2) , and is registered for `"stake-update"` in `handle_contract_call`: [4](#0-3) .

The node-level function trusts whatever `unlock-burn-height` the Clarity contract's `stake-update` reports without re-deriving or bounding it against the account's actual on-chain `STXBalance.unlock_height`. This is a genuine missing invariant at the Rust boundary: even if the pox-5.clar contract logic is intended to always compute a forward-only unlock height, the node-level locking primitive that actually mutates the account balance provides no independent enforcement of that invariant, unlike its sibling `pox_rollover_v5`. I was unable to fully verify from the Clarity contract (`pox-5.clar`) side within this session whether `stake-update`'s own internal arithmetic (`cycles-to-extend`, `prev-unlock-cycle`, `first-reward-cycle`) can actually be driven to emit a stale/lower `unlock-burn-height` under the corrupted-state scenario described in the question — my searches for the relevant Clarity helper names in `pox-5.clar` did not return matches in this session, so that specific triggering path is not independently confirmed here.

### Impact Explanation
If reachable, this breaks SINGLE UNLOCK for the affected staker: STX becomes spendable at an earlier burn height than the lock the staker (and the reward-set snapshot) committed to. This falls under "unlocking value never locked"/early unlock category (Critical) if a legitimate `stake-update` call path can produce a stale, lower `unlock-burn-height` value. The unconditional call to `update_unlock_v5` before any height-direction check is a genuine node-level correctness gap regardless of contract-level intent, since `pox_lock_update_v5` is the last line of defense at the balance-mutation layer and currently has none for unlock-height direction.

### Likelihood Explanation
Exploitability hinges entirely on whether the Clarity `stake-update` function in `pox-5.clar` can be driven (via `cycles-to-extend = u0` plus a corrupted/stale `prev-unlock-cycle`/`first-reward-cycle` after a prior partial failure) to emit an `(ok {... unlock-burn-height ...})` tuple whose value is lower than the account's true current `STXBalance.unlock_height`. I could not confirm this specific Clarity-side arithmetic path within the available tool budget (no matches found for the relevant Clarity constructs in this session), so likelihood of the full end-to-end attacker-triggerable scenario is **unconfirmed**. What is confirmed is that the Rust-level guard that should categorically prevent this outcome does not exist.

### Recommendation
Add an explicit forward-only check in `pox_lock_update_v5`, mirroring `pox_rollover_v5`, before calling `update_unlock_v5`:
```rust
let bal_before = snapshot.canonical_balance_repr()?;
if unlock_burn_height < bal_before.unlock_height() {
    return Err(LockingError::PoxInvalidUnlockHeight);
}
```
This closes the gap independent of whatever guarantees pox-5.clar's `stake-update` is assumed to provide.

### Proof of Concept
Rust unit test in `pox-locking/src/pox_5.rs` test module:
1. Lock an account via `pox_lock_v5(db, staker, 500_000, unlock_height = 20_000)`.
2. Call `pox_lock_update_v5(db, staker, unlock_burn_height = 10_000 /* < 20_000 */, new_total_locked = 500_000)`.
3. Assert the call returns `Err(LockingError::PoxInvalidUnlockHeight)` (currently it returns `Ok(_)` and mutates `STXBalance.unlock_height` down to `10_000`, which is the bug).
4. Confirming the full attacker-reachable end-to-end scenario additionally requires a Clarity-level test/trace on `pox-5.clar`'s `stake-update` showing it can emit a stale lower `unlock-burn-height` after a `cycles-to-extend = u0` call combined with corrupted `staker-info` — this part requires further investigation of `pox-5.clar` that was not completed in this session.

pub fn pox_lock_update_v5(
    db: &mut ClarityDatabase,
    principal: &PrincipalData,
    unlock_burn_height: u64,
    new_total_locked: u128,
) -> Result<STXBalance, LockingError> {
    if unlock_burn_height == 0 {
        return Err(LockingError::PoxInvalidUnlockHeight);
    }
    if new_total_locked == 0 {
        return Err(LockingError::PoxInvalidLockAmount);
    }

    let mut snapshot = db.get_stx_balance_snapshot(principal)?;

    if !snapshot.has_locked_tokens()? {
        return Err(LockingError::PoxExtendNotLocked);
    }

    snapshot.update_unlock_v5(unlock_burn_height)?;

    let bal = snapshot.canonical_balance_repr()?;
    let total_amount = bal
        .amount_unlocked()
        .checked_add(bal.amount_locked())
        .ok_or(LockingError::PoxBalanceOverflow)?;
    if total_amount < new_total_locked {
        return Err(LockingError::PoxInsufficientBalance);
    }

    if bal.amount_locked() > new_total_locked {
        return Err(LockingError::PoxInvalidIncrease);
    }
```

fn handle_stake_lockup_update_pox_v5(
    global_context: &mut GlobalContext,
    function_name: &str,
    value: &Value,
) -> Result<Option<StacksTransactionEvent>, VmExecutionError> {
    debug!(
        "Handle special-case contract-call to {:?} {function_name} (which returned {value:?})",
        boot_code_id(POX_5_NAME, global_context.mainnet),
    );

    runtime_cost(
        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

    let parsed = parse_pox_stake_result(value).map_err(|e| {
        locking_error_to_vm_error(e, &format!("pox-5 {function_name}: bad response"))
    })?;
    let (staker, amount_ustx, unlock_height) = match parsed {
        ParsedStakeResult::Ok {
            staker,
            amount_ustx,
            unlock_burn_height,
        } => (staker, amount_ustx, unlock_burn_height),
        ParsedStakeResult::ContractErr => return Ok(None),
    };

    match pox_lock_update_v5(
        &mut global_context.database,
        &staker,
        unlock_height,
        amount_ustx,
    ) {
        Ok(_) => {
            // Log the extension in the asset map.
            global_context.log_stacking(&staker, amount_ustx)?;

            let event =
                StacksTransactionEvent::STXEvent(STXEventType::STXLockEvent(STXLockEventData {
                    locked_amount: amount_ustx,
                    unlock_height,
                    locked_address: staker,
                    contract_identifier: boot_code_id(POX_5_NAME, global_context.mainnet),
                }));
            Ok(Some(event))
        }
        Err(e) => Err(locking_error_to_vm_error(
            e,
            &format!(
                "pox-5 {function_name}: failed to extend lock from {staker} until {unlock_height}"
            ),
        )),
    }
}
