### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while every event handler resolves and mutates the target `Repository`/`Stack` from the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and therefore the HMAC secret) used to authenticate an inbound webhook based on `repository.owner.login` (falling back to `organization.login`), but every registered webhook handler (`PushHandler`, `StatusHandler`, the `PullRequest::*` handlers, `Handler#stacks`/`#repository_name`) independently re-reads `repository.full_name` from the same JSON body to decide which `Repository`/`Stack` to act on. These are two separately attacker-controlled fields inside one JSON payload, and nothing ties them together, so the org whose secret authenticated the request is not necessarily the org whose repository gets mutated.

### Finding Description
`verify_signature` computes the signing organization purely from payload data: [1](#0-0) [2](#0-1) 

This selects `Shipit.github(organization: repository_owner)` and verifies the raw body against that org's `webhook_secret`: [3](#0-2) 

Separately, `Handler#stacks`/`#repository_name`, used by `PushHandler`, and the `repository` method used by every `PullRequest::*Handler` (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.), resolve the acted-upon repository from `repository.full_name`, a distinct JSON field from `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `secrets.yml`/`config/secrets.*.yml` supports multiple onboarded GitHub organizations, each with its own `webhook_secret`: [7](#0-6) 

an attacker who legitimately controls (or has leaked/obtained) the `webhook_secret` for one onboarded organization ("OrgA") can build a payload where `repository.owner.login` (or `organization.login`) is `"OrgA"` — so `verify_signature` selects and validates against OrgA's known-to-the-attacker secret — while `repository.full_name` is set to `"OrgB/victim-repo"`, a completely different, also-onboarded organization/repository. The signature only proves knowledge of OrgA's secret over the byte stream; it does not bind the signature to the specific sub-fields the handlers later trust to pick the mutated resource. This is precisely the pattern in the referenced report: a value used for the authorization/verification decision (`repository_owner`) is disjoint from the value the downstream logic actually consumes to select what gets modified (`repository.full_name`), and nothing forces the two to agree.

### Impact Explanation
This breaks the equality that should hold: `organization used to authenticate the webhook == organization owning the repository/stack the handler mutates`. Exploiting it lets an attacker who holds a valid webhook secret for one onboarded org forge events that manipulate stacks/repositories belonging to an unrelated, also-onboarded org on the same Shipit instance — e.g. forcing `PushHandler` to call `stack.sync_github(expected_head_sha:)` on a victim org's stack, or driving `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` to create, archive, or unarchive a victim org's review stacks. Because the actual GitHub API calls these actions eventually perform are scoped through `Repository#github_app`/`Stack#github_app`, which look up the app by the *real* stored `Repository.owner` (not the attacker's owner field), the attacker cannot steal that org's GitHub credentials — but they can trigger unauthorized state changes (spurious syncs, review-stack provisioning/archival) on repositories/organizations they do not control, which matches the “cross-repository writes / unauthorized deploy” class of impact called out in scope, albeit gated behind possession of a valid webhook secret for some onboarded org rather than zero privilege.

### Likelihood Explanation
Exploitation requires the attacker to already know a valid `webhook_secret` for at least one organization configured in this Shipit instance (e.g., an org admin of a legitimately-but-lower-trust onboarded org, or someone who obtained a leaked secret for one org). Given that, no further privileges (no Shipit session, no `ApiClient` token, no repository write access on the target org) are needed to forge the cross-org event. Multi-tenant Shipit deployments with several onboarded GitHub orgs (as explicitly supported by `secrets_double_github_app.yml`) are the direct at-risk configuration.

### Recommendation
Bind webhook signature verification to the same repository identity the handlers use to select their target. Concretely, derive `repository_owner` from `repository.full_name`'s owner component (or otherwise cross-validate `repository.owner.login`/`organization.login` against `repository.full_name`) before dispatching to handlers, and reject the webhook if they diverge. Alternatively, have each handler compare the authenticated `repository_owner` against the owner of the `Repository` it resolves via `full_name`, and refuse to process on mismatch.

### Proof of Concept
1. Shipit is configured with two onboarded orgs, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker knows/controls `OrgA`'s `webhook_secret` (e.g., is an admin of OrgA's GitHub App).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
   signed with `OrgA`'s webhook secret via `X-Hub-Signature`.
4. `WebhooksController#verify_signature` computes `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and successfully verifies the signature using the attacker-known secret: [1](#0-0) 
5. `PushHandler#process` then resolves the target via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha:)` on the matching OrgB stack: [4](#0-3) [5](#0-4) 
   — an org whose secret the attacker never possessed is nonetheless acted upon.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
