### Title
Unauthenticated `sender` in `StackStxOp` combined with un-bound `signer_key` lets an attacker force-lock a victim's STX under an attacker-controlled signer - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`StackStxOp::check` only validates that `signer_key` decodes to a well-formed secp256k1 point; it never asserts any relationship between `signer_key` and `sender`. Because `sender` itself is populated from the unauthenticated `PreStxOp.output` field (no signature required over that address), and because the actual PoX signature check in `pox-4`/`pox-5`'s `stack-stx` binds `signer-sig` to `(pox-addr, reward-cycle, period, amount, max-amount, auth-id)` but not to the `stacker`/`tx-sender`, an attacker can pair a spoofed victim `sender` with a `signer_key` they privately control and pass every validation layer.

### Finding Description
The broken equality: `signing weight assigned to signer_key` should equal `locked value voluntarily committed by the owner of that locked value`. After the exploit, the signing weight is assigned to the attacker's `signer_key` while the locked value is drawn from `sender` = victim's real STX balance, with no consent from the victim.

Code path:
1. `PreStxOp::parse_from_tx` sets `output` directly to the first Bitcoin-output-decoded `StacksAddress` with zero signature check [1](#0-0) . An attacker fully controls this field since it is simply an output address in a transaction they themselves construct.
2. `Burnchain::process_block`'s op parser takes `sender = &pre_stack_stx.output` verbatim and passes it into `StackStxOp::from_tx` [2](#0-1) , so `StackStxOp.sender` inherits the same unauthenticated value.
3. `StackStxOp::check` validates only that `signer_key` is a well-formed key, never that it is tied to `sender`, `stacked_ustx`, or `num_cycles` [3](#0-2) .
4. `StacksChainState::process_stacking_ops` invokes the Clarity `stack-stx` function with `tx-sender = sender` (the spoofed address) and the attacker-chosen `signer_key`/`max_amount`/`auth_id` as call arguments [4](#0-3) , and `collect_pox_4_stacking_args` forwards `signer_key`, `max_amount`, `auth_id` unchanged [5](#0-4) .
5. Inside `stack-stx`, the signer-key authorization check verifies a signature over `(pox-addr, reward-cycle, topic, period, amount, max-amount, auth-id)` produced by the `signer_key` private key — not over `tx-sender`/`stacker`. Since the attacker owns `signer_key`'s private key, they can trivially produce a valid signature for any parameters of their choosing.
6. `stack-stx` locks `amount-ustx` against `tx-sender` (the spoofed victim), and the resulting `(stacker, locked_amount, unlock_height)` is fed into `pox_lock_v4`, which locks the *victim's real on-chain STX balance* [6](#0-5) , while PoX signing weight accrues to the attacker's `signer_key`.

Existing guards do not stop this: `check()` performs no sender/signer binding; the Clarity signature check authenticates only "the signer consented to being used for these stacking parameters," not "the stacker consented to being stacked" — and burnchain ops bypass normal Stacks transaction signature authentication of `sender` entirely.

### Impact Explanation
A victim's real, unlocked STX balance can be force-locked without any signature or consent from the victim, and the PoX signing weight for that locked amount is credited to a signer key the attacker fully controls. This is theft of PoX signing/voting power backed by unconsented locked STX, and freezes the victim's STX for the lock period — matching the Critical category (unlocking/locking value never consented to, signing weight not backed by consenting locked value). The attack is repeatable against any address with sufficient spendable balance, once per reward-cycle lock window, and requires only the attacker's own Bitcoin inputs (to fund the PreStxOp/StackStxOp transactions) and their own signer keypair.

### Likelihood Explanation
Preconditions: attacker needs to fund two Bitcoin transactions (`PreStxOp` and `StackStxOp` spending its second output) from their own UTXOs — no privileged role, no victim cooperation, no compromised infrastructure required. The victim address only needs a sufficient unlocked STX balance at lock time; the attacker does not need to know any victim secret. Cost is limited to Bitcoin transaction fees. This is feasible and repeatable each cycle/lock window, contingent on the victim continuing to hold unlocked, spendable STX at the targeted address.

### Recommendation
Do not derive `StackStxOp.sender` (or any stacking-authorizing identity) purely from an unauthenticated Bitcoin output field. Require the `PreStxOp`/`StackStxOp` mechanism to cryptographically prove that the STX-owning Stacks account authorized the operation, and additionally have `StackStxOp::check` (or the Clarity-level signer-key authorization) bind `signer_key`'s authorization to the specific `sender`/`stacker`, not merely to `pox-addr`/`reward-cycle`/`amount`.

### Proof of Concept
1. Attacker crafts a `PreStxOp` Bitcoin transaction with `output` = victim's `StacksAddress` (an address the attacker does not control), funded from attacker-owned UTXOs.
2. Attacker crafts a `StackStxOp` spending vout 1 of the `PreStxOp` tx, with `signer_key` = attacker's own public key, `stacked_ustx` = victim's actual spendable balance, valid `max_amount`/`auth_id`, and a self-produced `signer-sig` over those parameters (since the attacker owns the signer private key).
3. Run through `Burnchain::process_block` → `StacksChainState::process_stacking_ops` in a local test chainstate (as in `stackslib/src/chainstate/burn/operations/test/mod.rs` / `stackslib/src/chainstate/coordinator/tests.rs` patterns) with the victim account pre-funded and never issuing any Stacks transaction.
4. Assert: (a) `StackStxOp::check()` returns `Ok(())`; (b) the victim's `STXBalance` becomes locked (`amount_locked() == stacked_ustx`, `locked_address == victim`); (c) the reward-cycle reward-set / signer weight table shows `signer_key == attacker_key` credited with weight proportional to `stacked_ustx`; (d) the victim never signed any transaction. This demonstrates the equality break: weight assigned to attacker's key while locked value belongs to, and was never consented to by, the victim.

impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }

    pub fn collect_pox_4_stacking_args(op: &StackStxOp) -> Result<Vec<Value>, String> {
        let signer_key = match &op.signer_key {
            Some(signer_key) => match Value::buff_from(signer_key.as_bytes().to_vec()) {
                Ok(signer_key) => signer_key,
                Err(_) => {
                    return Err("Invalid signer_key".into());
                }
            },
            _ => return Err("Invalid signer key".into()),
        };

        let max_amount_value = match op.max_amount {
            Some(max_amount) => Value::UInt(max_amount),
            None => return Err("Missing max_amount".into()),
        };

        let auth_id_value = match op.auth_id {
            Some(auth_id) => Value::UInt(u128::from(auth_id)),
            None => return Err("Missing auth_id".into()),
        };

        Ok(vec![
            Value::none(),
            signer_key,
            max_amount_value,
            auth_id_value,
        ])
    }
