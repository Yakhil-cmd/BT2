### Title
Cross-organization webhook forgery via `repository_owner`/`repository.full_name` mismatch in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to validate an inbound webhook against based on an **unauthenticated field of the payload itself** (`repository.owner.login` / `organization.login`), while all downstream `Shipit::Webhooks::Handlers::Handler` subclasses select the **repository being mutated** using an entirely different field of the same payload (`repository.full_name`). These two fields are never cross-checked, so the organization whose secret authenticates the request is not bound to the repository whose Stacks/PullRequests are actually written.

### Finding Description
`verify_signature` picks the GitHub App/secret to check with: [1](#0-0) 

`repository_owner` is derived purely from the untrusted request body: [2](#0-1) 

That value is passed to `Shipit.github(organization:)`, which raises `GithubOrganizationUnknown` (→ HTTP 422) only if the organization is not configured at all; if it is configured but has no `webhook_secret` set, verification trivially passes: [3](#0-2) [4](#0-3) 

Meanwhile, every webhook handler (push, pull_request opened/closed/labeled/etc., membership, status, …) resolves the **actual repository/stack it writes to** from `payload.dig('repository', 'full_name')`, completely independent of `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality that should hold is:
`organization authenticated by verify_signature (repository.owner.login/organization.login) == organization owning repository.full_name acted on by the handler`

This is never enforced. In a multi-organization deployment (`config/secrets.*.yml` supporting per-org `webhook_secret`, `oauth`, etc., as shown in `config/secrets.development.shopify.yml`), an attacker can post a forged webhook body where:
- `repository.owner.login` (or `organization.login`) names an org that is configured but has no `webhook_secret` (a legitimate, documented configuration state, e.g. for local/dev orgs, per `config/secrets.development.example.yml`), causing `verify_webhook_signature` to short-circuit `true` with **no HMAC needed at all**, while
- `repository.full_name` names a *different*, protected organization's tracked repository.

Because handlers never re-validate that `repository.full_name`'s owner matches the organization that was cryptographically authenticated, the forged, unsigned request is processed as if it legitimately originated from GitHub for that other org's repository — enabling unauthorized writes such as creating/archiving `ReviewStack`s, updating `PullRequest` records, or enqueuing `GithubSyncJob`/`RefreshCheckRunsJob` for a repository belonging to an organization that does enforce a webhook secret.

### Impact Explanation
This is a repository-write / trust-boundary bypass: it lets an unprivileged, unauthenticated network attacker cause the engine to accept and act on forged GitHub events (push, pull_request opened/closed/labeled, membership, status, check_suite) for repositories under a different, secret-protected organization, without ever presenting a valid signature for that organization. This can trigger unintended `GithubSyncJob` runs, review-stack provisioning/archival, and `PullRequest` record mutation — a cross-repository write achieved purely by choosing which organization key to reference in the JSON body. This matches the required "cross-repository writes" / "unauthorized deploy" impact class, since sync jobs and review-stack provisioning can cascade into deploy-affecting state changes.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint (no session, no token, no secret). It is only exploitable when the deployment is configured with multiple GitHub organizations where at least one configured organization lacks a `webhook_secret` (a state explicitly supported and documented, e.g. `config/secrets.development.shopify.yml` shows `webhook_secret: # nil` per-org) while another organization's tracked repository is the actual write target. This is a realistic, easy-to-hit misconfiguration given the multi-org feature is designed to let each org have independent settings, and the code offers no defense-in-depth check tying the two identity signals together.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler`, cross-validate that the organization used to select the signing secret (`repository_owner`) matches the owner segment of `repository.full_name` used by handlers before any handler is invoked. Additionally, do not allow signature verification to silently pass (`return true unless webhook_secret`) for any organization that has other organizations configured with secrets in the same installation; require an explicit, single decision path so that "verified organization" and "acted-upon repository owner" are provably equal before dispatch.

### Proof of Concept
Given a multi-org config with `orgA` (protected, has `webhook_secret: "s3cr3t"`, owns tracked repo `orgA/critical-repo`) and `orgB` (configured, `webhook_secret: nil`, e.g. left blank for local testing per `config/secrets.development.example.yml`):

```
POST /webhooks HTTP/1.1
X-Github-Event: pull_request
Content-Type: application/json
(no valid X-Hub-Signature needed for orgB)

{
  "action": "opened",
  "number": 1,
  "pull_request": { "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
                     "additions": 0, "deletions": 0,
                     "head": { "sha": "deadbeef", "ref": "feature" },
                     "user": { "login": "attacker" }, "assignees": [], "labels": [] },
  "repository": {
    "owner": { "login": "orgB" },
    "full_name": "orgA/critical-repo"
  },
  "sender": { "login": "attacker" }
}
```

- `verify_signature` computes `repository_owner => "orgB"`, calls `Shipit.github(organization: "orgB")`; since `orgB.webhook_secret` is nil, `verify_webhook_signature` returns `true` unconditionally — no valid signature required.
- `Shipit::Webhooks.for_event('pull_request')` dispatches to `OpenedHandler`, whose `repository` is resolved via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` → `"orgA/critical-repo"`, i.e., the protected org's repository — and `ReviewStackAdapter.find_or_create!` provisions a review stack for it, entirely unauthenticated with respect to `orgA`.

This confirms handlers act on the repository named in `repository.full_name` while authentication is bound to a different, attacker-chosen field (`repository.owner.login`), breaking the intended organization↔repository binding.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
