### Title
Single failing submodule blocks entire sync, causing persistent denial of new content publication - (File: main.go)

### Summary
`repoSync.configureWorktree` runs `git submodule update --init [--recursive]` as one atomic command over all submodules in the freshly-fetched commit [1](#0-0) . If this command returns a non-zero exit code, `configureWorktree` returns the error, and `SyncRepo` aborts the entire sync attempt before ever reaching `publishSymlink` [2](#0-1) [3](#0-2) . This mirrors the reported `LiqFacet::removeLiq` pattern: iterating over multiple sub-resources (vaults / submodules) where a single failing item aborts the whole operation instead of allowing the rest to proceed.

### Finding Description
`git-sync` fetches the tracked ref, creates a worktree for the new commit, and then calls `configureWorktree`, which unconditionally runs submodule initialization for the whole tree when `--submodules` is not `off` [1](#0-0) . Because the submodule set (and their URLs/refs) are defined by `.gitmodules` and gitlinks committed to the tracked repository, any actor who can push a commit to the ref that `git-sync` follows controls this input. A single submodule entry pointing at an unreachable, deleted, or authentication-requiring URL causes the whole `git submodule update` invocation to fail, which propagates up through `configureWorktree` → `SyncRepo` [2](#0-1) , aborting the sync before `beforePublish`/`publishSymlink`/`afterPublish` ever run [4](#0-3) . No partial success path exists — even though the main tree content and any other (working) submodules were already fetched and would be usable, none of it is published because the whole worktree configuration is treated as all-or-nothing, exactly as `removeLiq` treats withdrawal across all vaults as all-or-nothing.

The outer sync loop only retries by re-running the identical `SyncRepo` sequence on a timer [5](#0-4) ; there is no mechanism to skip a broken submodule and still publish the rest. If `--max-failures` is reached (default `0`, meaning abort on first failure), `git-sync` process exits entirely [6](#0-5) , compounding the denial into a crash-loop.

### Impact Explanation
This causes **persistent sync denial**: any legitimate content update pushed to the tracked ref after (or bundled with) a bad submodule change will never be published via the `--link` symlink, and consumers keep serving stale content indefinitely until an operator manually fixes/reverts the submodule reference. With default flags, the git-sync sidecar process itself exits, requiring pod restarts to even retry. This matches the "persistent sync denial" impact class accepted by the validation rules.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to have push access (or merge access via automated processes) to the ref that git-sync is configured to follow — the same untrusted-repo-content threat model used in the original report. No credentials, mocked behavior, or malicious-operator assumptions are needed; a normal contributor-level commit containing a broken/removed submodule reference is sufficient, and `--submodules` defaults to `recursive` [7](#0-6) , so no special flag is required to trigger the vulnerable code path.

### Recommendation
Do not let a submodule failure abort the entire worktree configuration/publish pipeline unconditionally. Options:
- Run submodule updates per-submodule (e.g. iterate `git submodule foreach` targets) and collect errors similarly to how `cleanup` already aggregates errors via `multiError` [8](#0-7) , publishing the worktree with the submodules that succeeded and clearly logging/metric-ing the ones that failed.
- Alternatively, expose a flag to make submodule failures non-fatal for the top-level publish, while still surfacing them via logs/metrics/error-file, so a single bad submodule doesn't block unrelated content from ever being synced.

### Proof of Concept
1. Configure `git-sync` with `--repo=<tracked repo>` and default `--submodules=recursive`.
2. As a contributor with push access to the tracked ref, add a `.gitmodules` entry (or modify an existing submodule's gitlink) to point at a URL that is unreachable or requires missing credentials, and commit it along with an unrelated legitimate file change.
3. Observe that `git.SyncRepo` fails at the submodule-update step inside `configureWorktree` [9](#0-8) , `SyncRepo` returns the error before `publishSymlink` runs [2](#0-1) , and the `--link` symlink continues pointing at the old worktree.
4. Subsequent sync attempts repeat the identical failure every `--period`, and with default `--max-failures=0` the process exits after the first failure [6](#0-5) , demonstrating persistent denial of the unrelated legitimate content update until an operator manually intervenes.

func (git *repoSync) cleanup(ctx context.Context) error {
	// Save errors until the end.
	var cleanupErrs multiError

	// Clean up previous worktree(s).
	if n, err := git.removeStaleWorktrees(); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	} else if n == 0 {
		// We didn't clean up any worktrees, so the rest of this is moot.
		return nil
	}

	// Let git know we don't need those old commits any more.
	git.log.V(3).Info("pruning worktrees")
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Expire old refs.
	git.log.V(3).Info("expiring unreachable refs")
	if _, _, err := git.Run(ctx, git.root, "reflog", "expire", "--expire-unreachable=all", "--all"); err != nil {
		cleanupErrs = append(cleanupErrs, err)
	}

	// Run GC if needed.
	if git.gc != gcOff {
		args := []string{"gc"}
		switch git.gc {
		case gcAuto:
			args = append(args, "--auto")
		case gcAlways:
			// no extra flags
		case gcAggressive:
			args = append(args, "--aggressive")
		}
		git.log.V(3).Info("running git garbage collection")
		if _, _, err := git.Run(ctx, git.root, args...); err != nil {
			cleanupErrs = append(cleanupErrs, err)
		}
	}

	if len(cleanupErrs) > 0 {
		return cleanupErrs
	}
	return nil
