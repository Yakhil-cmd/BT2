### Title
Unbounded merkle-proof sibling array in address-definition `'in merkle'` authentifier verification causes excessive CPU consumption - (File: definition.js)

### Summary
The `'in merkle'` operator in address/AA definitions accepts an attacker-supplied, serialized merkle proof from the unit's `authentifiers` field and verifies it with no bound on the number of siblings, unlike the equivalent oscript `is_valid_merkle_proof` function which explicitly caps siblings at 50.

### Finding Description
`validateAuthentifiers()` in `definition.js` implements the `'in merkle'` definition operator: it reads the raw authentifier string for the given path, deserializes it with `merkle.deserializeMerkleProof()`, and calls `merkle.verifyMerkleProof(element, proof)`. [1](#0-0) 

`deserializeMerkleProof()` simply splits the string on `"-"` and treats everything between the first and last field as `proof.siblings`, with no length limit: [2](#0-1) 

`verifyMerkleProof()` then iterates `proof.siblings.length` times, each iteration performing a SHA-256 hash: [3](#0-2) 

This is directly analogous to CVE-2017-14170's `mxf_read_index_entry_array()`: a length-derived value taken from attacker-controlled input drives a loop with per-iteration cost (hashing), and the loop bound is never checked against any sane maximum before the loop executes. Compare this to the `formula/evaluation.js` `is_valid_signed_package` / `is_valid_merkle_proof` oscript function, which explicitly limits `objProof.siblings.length` to 50 under `bPostPemCurvesFix`: [4](#0-3) 

No equivalent limit exists on the `'in merkle'` definition-language path in `definition.js`. Because `assocAuthentifiers[path]` is just a free-form string supplied by the unit's author for a signing path, an attacker can craft an address whose definition contains `['in merkle', [...]]`, then post a unit signed by that address with an authentifier string containing tens of thousands of `-`-separated "sibling" segments. Each additional segment costs one SHA-256 hash of a growing/adjustable string, and `authentifiers[path]` values are only bounded by `constants.MAX_AUTHENTIFIER_LENGTH` in `signed_message.js`'s `validateSignedMessage` path, but the general unit `validateAuthor`/`validateAuthentifiers` path in `definition.js` does not appear to impose a per-authentifier length cap before merkle verification, so a large but still-message-size-limited string (bounded only by `MAX_UNIT_LENGTH`/message size limits) can still contain a large number of short sibling fields, multiplying the hashing work far beyond what typical definition evaluation costs.

### Impact Explanation
Every full/light node that receives and validates a unit whose author (or AA trigger message) uses such a definition must run `validateAuthentifiers`, forcing it to execute `verifyMerkleProof` and perform proportionally many SHA-256 operations for each of the potentially many authentifier paths/AND branches in the definition. Since address definitions can combine `'in merkle'` with `'or'/'and'/'r of set'` constructs across multiple authentifier paths (each bounded by weight/complexity checks that do not account for merkle proof depth), an attacker can multiply this CPU cost across many candidate definitions/paths evaluated during validation, causing significant CPU consumption on every node that processes the unit — a network-wide DoS vector against the ability to validate/confirm units, without requiring any privileged position (any unprivileged unit poster can trigger it by defining and using such an address).

### Likelihood Explanation
Medium: the attacker needs only to construct a normal address definition using `'in merkle'` (a documented oscript primitive) and post units signed by it with an oversized authentifier string; no special network position, hub/witness control, or leaked keys are required. The construction is straightforward using the existing merkle-proof serialization format.

### Recommendation
Add an explicit cap on `proof.siblings.length` (e.g., the same 50-sibling limit used in the `is_valid_merkle_proof`/`is_valid_signed_package` formula evaluation path) inside `merkle.verifyMerkleProof()` itself, or at minimum at the `'in merkle'` case in `definition.js` immediately after `merkle.deserializeMerkleProof()`, before any hashing occurs. Additionally, enforce a maximum length on individual authentifier strings used for definitions containing `'in merkle'` consistently across all validation entry points (unit validation, signed messages, AA triggers).

### Proof of Concept
1. Craft an address definition `D = ['in merkle', [[oracleAddr], 'feed_name', 'value']]`; compute `address = chash160(D)`.
2. Build a serialized merkle proof string with `N` (e.g. 100,000) short dash-separated "sibling" tokens followed by an index and root, e.g. `"0-s1-s2-...-sN-root"`.
3. Post a unit authored by `address`, with `definition: D` and `authentifiers: {"r": "<the crafted proof string>"}`.
4. On receipt, every validating node calls `validateAuthentifiers` → `merkle.deserializeMerkleProof` (splits into `N` siblings) → `merkle.verifyMerkleProof`, which loops `N` times each doing a SHA-256 hash of accumulating string length, consuming CPU disproportionate to normal unit validation cost, unlike the capped `is_valid_merkle_proof` oscript function which would reject `siblings.length > 50`.

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
