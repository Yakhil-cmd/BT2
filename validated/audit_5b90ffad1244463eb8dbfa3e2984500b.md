### Title
Signed messages / signed packages lack network (`alt`) binding, enabling cross-network replay analogous to the missing chain-fork check - ([File: signed_message.js])

### Summary
Full DAG units in ocore are bound to a specific network via the `alt` field, which is strictly checked during validation, preventing a unit crafted for one network (mainnet/testnet/devnet) from being replayed on another. However, `signed_message`/`signed_package` structures — used by AA oscript (`is_valid_signed_package`), payment-channel contracts, arbiter/prosaic contract responses — carry no equivalent network-binding field, so a signature produced on one network can be verified as valid on any other network sharing the same address space, exactly mirroring the reported NTT bug class where `completeInboundQueuedTransfer` omitted the `checkFork(evmChainId)` check that `executeMsg` performs.

### Finding Description
`validateSignedMessage` only whitelists `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` as allowed top-level fields of the signed package: [1](#0-0) 

There is no `alt`/network identifier in this whitelist, unlike full unit validation, which explicitly rejects units whose `alt` does not match the local network's `constants.alt`: [2](#0-1) 

`constants.js` shows `alt` differs per network (mainnet `'1'`, testnet `'2'`, devnet `'3'`), and it is the sole discriminator used elsewhere in the codebase to reject cross-network units and peers: [3](#0-2) [4](#0-3) 

Because `alt` is not part of the "text to sign" for signed packages (`objectHash.getSignedPackageHashToSign`), and is not checked in `validateSignedMessage`, the exact same signature bytes that authenticate a `signed_message` object on mainnet remain fully valid when re-submitted on testnet/devnet (or vice versa), as long as the signing address/definition is the same (address `chash160` derivation does not depend on the network). This mechanism is exposed to AA oscript via `is_valid_signed_package`, which itself does not add a network check either: [5](#0-4) 

This is the same root-cause shape as the reported bug: a security-critical acceptance path (`completeInboundQueuedTransfer` in the external report, `validateSignedMessage`/`is_valid_signed_package` here) omits the chain/network-identity check that is present and enforced elsewhere in the same codebase for the analogous, "primary" path (`executeMsg` in the report, full-unit validation via `objUnit.alt` here).

### Impact Explanation
AA authors building stateful off-chain protocols (payment channels, fraud proofs, arbiter/prosaic contract acceptance flows — see `test/samples/payment_channels.oscript` and `test/samples/option_contract.oscript`) rely on `is_valid_signed_package`/`validateSignedMessage` as the sole cryptographic guarantee that a message originates from a specific counterparty for a specific channel/period. If the same address (same key) is used to interact with structurally identical AAs deployed on two different ocore-based networks (mainnet and testnet share the exact same oscript engine and AA definition hashing, so an identical AA definition produces an identical address on both networks), a signed package captured on one network can be replayed on the other to force fraudulent channel closes, unlock funds, or falsify off-chain state on the AA that did not itself independently gate on network identity. This can lead to AA fund loss for one of the counterparties.

### Likelihood Explanation
Exploitation requires that the victim reuses the same address/definition across two ocore networks and that an identically-coded AA (channel/contract) exists on both — a realistic scenario for testers, cross-network tooling, or projects that deploy the same oscript to both mainnet and testnet for parity testing. It does not require any privileged access: any private-payment/AA counterparty who already possesses a validly signed package (from legitimate off-chain channel communication) can attempt the replay on the sibling network.

### Recommendation
Include the network's `alt` (or an equivalent explicit chain/network identifier) inside the signed-message hash-to-sign structure, and enforce a match against the local `constants.alt` inside `validateSignedMessage` (and therefore transitively in `is_valid_signed_package`), the same way `validation.js` already enforces `objUnit.alt !== constants.alt` for full units.

### Proof of Concept
1. Generate a keypair and derive address `A` via `["sig", {pubkey}]`; this address is identical on mainnet, testnet, and devnet since `objectHash.getChash160` does not depend on network parameters.
2. Deploy an identical payment-channel AA oscript (as in `test/samples/payment_channels.oscript`) on both mainnet and testnet; because AA address = `chash160(AA definition)`, the AA address is identical on both networks.
3. On testnet, have party A produce a `signed_message` (e.g., a `close`/fraud-proof package) for `channel = this_address`, `period = 0`, signed with A's key, as validated via `is_valid_signed_package` in `formula/evaluation.js:1653-1701`.
4. Submit the identical `signed_message` bytes as `trigger.data.sentByPeer` to the mainnet-deployed instance of the same AA/channel (same address, same initial period).
5. `validateSignedMessage` (`signed_message.js:117-303`) verifies the signature successfully because it never checks any network/`alt` identifier, allowing the mainnet AA to accept a signature that was never intended to be valid there.
