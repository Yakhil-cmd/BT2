### Title
CCMenu token generated for one stack grants read access to every stack's build status - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` for the currently logged-in Shopify/GitHub user in order to expose a per-stack CI-status ("CCMenu") feed URL, but the client it creates is never bound to the specific stack the user requested it for. That unscoped token is then accepted by `Shipit::Api::CCMenuController`, which — unlike every other API controller — resolves the target stack with the raw, unscoped `Stack.from_param!` instead of the `ApiClient`-scoped `stacks` helper defined in `Shipit::Api::BaseController`. The combination lets a token that a user obtained (and is meant to embed in a CI dashboard) for Stack A be replayed against any other stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the stack lookup used by every other API endpoint (deploys, tasks, rollbacks, locks, hooks, etc.) so that a stack-scoped `ApiClient` can only see the stack it was issued for: [1](#0-0) 

`Shipit::Api::CCMenuController` overrides this exact method and bypasses the scoping entirely: [2](#0-1) 

Separately, `CCMenuUrlController#fetch` — the endpoint a logged-in user hits from a stack's settings page to obtain their embeddable CCMenu URL — creates (or reuses) a single, globally-named `ApiClient` per user with `read:stack` permission but does **not** set the `stack:` association on it, so `ApiClient#stack_id` stays `nil`: [3](#0-2) 

Because `ApiClient#stack_id` is optional and this client leaves it unset, `BaseController#stacks` (used everywhere else) would already treat this token as unrestricted (`stacks.where(id: stack_id)` only applies `if current_api_client.stack_id?`): [4](#0-3) [5](#0-4) 

`CCMenuController` doesn't even rely on that scoping — it looks the stack up directly by `params[:stack_id]` with no reference to `current_api_client` at all, so any valid token (this one or another user's/stack's CCMenu token) can be replayed against an arbitrary `stack_id` in the URL to read that other stack's latest build status, name, and last-deploy timestamp.

**Binding broken:** the stack a token is *authorized for* (the single stack whose settings page the user was viewing, `stack.to_param` at generation time) ≠ the stack the token actually *touches* (`Stack.from_param!(params[:stack_id])`, unconstrained to any stack in the installation).

### Impact Explanation
A user who only has write/settings access to one stack (e.g., because `Shipit.github_teams` restricts them) can generate a CCMenu URL for that stack, and the resulting token/URL — commonly pasted into third-party CI dashboards or shared — can be reused to read the build/deploy status (name, last build status, last build label, last build time, web URL) of every other stack in the Shipit instance, including stacks belonging to repositories the user has no authorization for. This is a cross-boundary authorization escape: `read:stack` was intended to be scoped per-stack (as it is for every other stack-scoped API client), but the CCMenu code path both fails to persist that scope on creation and fails to enforce it on lookup.

### Likelihood Explanation
The bug requires no privileged access beyond having settings access to at least one stack (a normal, low-privilege Shipit user) and knowledge of the target's `stack_id` path segment (`owner/repo/environment`), which is often guessable/enumerable from the UI. The generated URL is designed to be shared/embedded externally, increasing the chance of accidental exposure and replay.

### Recommendation
- In `CCMenuUrlController#fetch`, set `stack:` on the `ApiClient` when creating it (`find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`), scoping the token to the requested stack.
- In `Shipit::Api::CCMenuController`, remove the `stack` override and use the inherited, `ApiClient`-scoped `stacks.from_param!(params[:stack_id])` from `BaseController` so a stack-scoped token cannot be replayed against other stacks.

### Proof of Concept
1. User with settings access only to Stack A visits Stack A's settings page and requests the CCMenu URL, triggering `CCMenuUrlController#fetch`, which creates an `ApiClient` named "CCMenu Client" for that user with `permissions: ['read:stack']` and `stack_id: nil`. [6](#0-5) 
2. The returned URL is `GET /api/stacks/<owner>/<repo-A>/<env-A>/ccmenu?token=<token>`.
3. The attacker (or the same low-privilege user) replays the identical token against Stack B, which they have no access to: `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<token>`.
4. `CCMenuController#authenticate_api_client` accepts the token, `require_permission :read, :stack` passes because the permission list contains `read:stack` (not stack-specific), and `stack` resolves Stack B directly via `Stack.from_param!`, returning Stack B's build status. [7](#0-6)

  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end
