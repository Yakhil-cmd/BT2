### Title
Unbounded accumulation of same-address double-spend units causes memory/DAG bloat and validation slowdown - ([File: validation.js])

### Summary
Confirmed root cause: `findConflictingUnits`/`checkSerialAddressUse` in `validation.js` accept an unlimited number of conflicting ("double-spend") units from a single author address into the DAG. Each such unit is marked `temp-bad` but is still inserted into the `units` table and into the in-memory `storage.assocUnstableUnits` cache, and stays there — consuming memory, growing the conflict-detection query result set, and adding CPU work (per-unit `graph.determineIfIncludedOrEqual` graph walks) for every subsequent unit from that address — until the DAG stabilizes past them. There is no `MAX_*` anti-spam constant limiting the number of simultaneously pending non-serial/temp-bad units per address, unlike the caps that exist for parents, authors, messages, inputs, etc. (`constants.js` lines 43-56).

### Finding Description
When a unit is posted, `validateAuthor` → `checkSerialAddressUse` → `findConflictingUnits` (`validation.js:1257-1301`) queries all not-yet-final-bad units from the same address that are not ancestors of the new unit. If any exist, the new unit is accepted as `temp-bad` (or `final-bad` only if it conflicts with an already-stable unit) [1](#0-0) . Critically, there is no limit on how many `temp-bad` units from one address can coexist unstable: an attacker with one address and one small balance can repeatedly compose new units all spending the same output(s), each unit accepted (not rejected outright) as `temp-bad`, and each stored in the `units` table and cached in `storage.assocUnstableUnits` via `initUnstableUnits`/`writer.saveJoint` [2](#0-1) .

Each of these units also participates in the `checkForDoublespends` logic when new units try to spend the same input, requiring a `graph.determineIfIncludedOrEqual` DAG-inclusion check against every existing conflicting record [3](#0-2) . As the number of pending conflicting units from an address grows, so does the number of DAG-inclusion checks performed by every node that revalidates a new unit from that same address, and the number of rows scanned in `findConflictingUnits`/`checkInputDoubleSpend` queries — an attacker-controlled O(n) (or worse) cost growth analogous to Geth's mempool being flooded with thousands of self-conflicting transactions.

Unlike Geth's mempool (which had a design flaw allowing spam to specifically evict *other* pending transactions and block new ones from entering), ocore's DAG doesn't have a bounded "mempool" abstraction to evict from — but it has an unbounded "unstable/free unit" cache (`assocUnstableUnits`, `is_free=1` units) that plays an analogous role for parent-selection and revalidation. Anti-spam limits exist for per-unit structure (`MAX_PARENTS_PER_UNIT`, `MAX_AUTHORS_PER_UNIT`, `MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, etc., `constants.js:43-56`) but none bound the number of pending double-spend ("temp-bad") units per address before stabilization, nor the number of `is_free=1` units per address that a single account can flood into every node's memory and DB.

`purgeUncoveredNonserialJoints` (`joint_storage.js:230-299`) only purges bad units once they are "uncovered" (no children, no dependencies) and either 10 seconds old or after being seen and left uncommitted by witnesses — it does not bound the number of bad units accumulated concurrently, and a sufficiently fast/continuous stream from the attacker keeps replenishing the set faster than the periodic sweep removes it.

### Impact Explanation
An attacker holding funds on a single address can compose and broadcast a large number of self-conflicting ("double-spend") units from that address in a short time. Each of them is validated as a syntactically-valid unit (not rejected as malformed), inserted into every full node's `units` table and into the in-memory `assocUnstableUnits`/free-unit caches, and propagated across the network (since acceptance with `temp-bad` sequence is a valid outcome, not a validation failure) — increasing memory usage and CPU cost of `graph.determineIfIncludedOrEqual` for all subsequent validations touching that address, and slowing down the shared write mutex (`mutex.lock(["write"])`) used by `saveJoint` and stabilization routines. This matches the "resulting in a denial of service" and "unable to confirm new units" criteria: legitimate transactions from the same address (and, due to shared write-path resource contention, potentially network-wide throughput) are delayed while nodes carry and repeatedly re-check the bloated conflict set.

### Likelihood Explanation
Any unprivileged unit poster can trigger this: they only need control of one address with a spendable output and the ability to compose many conflicting payment units referencing the same input(s) with different parents, well within reach of a single poster with no special privileges. Composing such conflicting units is a standard, expected client operation (double-spend attempts are explicitly tolerated by the protocol design as `temp-bad`/`final-bad` sequences), so no exploit of validation logic is needed — only volume.

### Recommendation
Introduce an anti-spam cap analogous to the existing `MAX_*` unit-structure limits: bound the number of simultaneously pending (`is_stable=0`, non-final-bad) conflicting/`temp-bad` units allowed per address (e.g., checked in `findConflictingUnits`/`checkSerialAddressUse` in `validation.js`), rejecting or deprioritizing further conflicting submissions from an address beyond the threshold until earlier ones stabilize or are purged. Additionally, consider tightening/accelerating `purgeUncoveredNonserialJoints` (`joint_storage.js`) to more aggressively evict old temp-bad/uncovered units per-address once a threshold is exceeded, and add per-address rate limiting at the p2p ingestion layer (`handlePostedJoint`/`handleJoint` in `network.js`) independent of validation outcome.

### Proof of Concept
1. Attacker composes unit U1 spending output O of address A, gets it accepted as `good` (first spender).
2. Attacker composes U2..Un (n large, e.g. thousands), each also spending output O (or another already-spent output of A) with different parents/timestamps, all signed validly by A.
3. Each Ui is broadcast; `validateAuthor`→`findConflictingUnits` finds the prior conflicting unit(s) and accepts Ui with `sequence='temp-bad'` (`validation.js:1304-1331`), so it is not rejected — it is written to `units` and cached in `assocUnstableUnits`.
4. Repeating this from many parent-tips at high rate causes `assocUnstableUnits` and the `units`/`unit_authors` conflict-lookup queries to grow with `n`, and every subsequent validation of a unit from address A must re-run the O(n) `findConflictingUnits`/`graph.determineIfIncludedOrEqual` checks, degrading validation throughput node-wide.

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);
					graph.determineIfIncludedOrEqual(conn, objConflictingRecord.unit, objUnit.parent_units, function(bIncluded){
						if (bIncluded){
							var error = objUnit.unit+": conflicting "+type+" in inner unit "+objConflictingRecord.unit;

							// too young (serial or nonserial)
							if (objConflictingRecord.main_chain_index > objValidationState.last_ball_mci || objConflictingRecord.main_chain_index === null)
								return cb2(error);

							// in good sequence (final state); final-bad is excluded by the query and treated as non-existent
							if (objConflictingRecord.sequence === 'good')
								return cb2(error);

							throw Error("unreachable code, conflicting "+type+" in unit "+objConflictingRecord.unit);
						}
						else{ // arrAddressesWithForkedPath is not set when validating private payments

							cb2();

					});
				},
				function(err){
					if (err)
						return cb(err);
