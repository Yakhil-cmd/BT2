### Title
`Api::CCMenuController#stack` bypasses the ApiClient's stack scope, letting a stack-scoped CCMenu token read any stack's deploy state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor that every other API controller inherits from `Api::BaseController`, dropping the scoping that restricts a stack-bound `ApiClient` token to its own stack. This lets the holder of a narrowly-scoped, low-trust CCMenu token (the kind Shipit itself mints and hands out for embedding in third-party CI dashboards) read the deploy/rollback state of *any* stack in the installation, not just the one the token was issued for.

### Finding Description
`Api::BaseController` defines the authorization-scoping primitive used by every API endpoint: [1](#0-0) 

`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is bound to a single stack, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the binding: **stack a token authorises == stack it touches**.

`CCMenuController` (mounted at the CCMenu-format endpoint used by third-party CI/CD dashboard tools) re-implements `authenticate_api_client` to accept the API token via a query-string `params[:token]` instead of HTTP Basic auth (this is expected/documented, since CCMenu XML feeds are typically fetched by tools that can't send custom auth headers) — but it also redefines `stack`: [2](#0-1) 

`Stack.from_param!(params[:stack_id])` performs a global lookup, completely bypassing `current_api_client.stack_id` scoping. `require_permission :read, :stack` only checks that `'read:stack'` is in `current_api_client.permissions` — it never checks which stack the permission applies to. Combined, this means: any client holding a token with the `read:stack` permission — even one created with `stack: <specific stack>` intended to restrict it to a single project — can supply an arbitrary `stack_id` in the URL and read that other stack's latest deploy/rollback status, id, and outcome.

This is the direct analog of the report's root cause: a security boundary (`PausableUpgradeable`'s `whenNotPaused` modifier on `ERC1155`'s actual transfer hook) that is enforced on the "canonical" access path (`BaseController#stack`/`#stacks`) but silently skipped on an alternate path (`CCMenuController#stack`) that overrides/bypasses the very method the rest of the framework relies on for enforcement.

### Impact Explanation
Shipit itself generates and distributes these stack-scoped tokens by design: the `CCMenuUrlController#fetch` action creates a read-only `ApiClient` bound to one stack and returns a URL containing `?token=...` meant to be pasted into third-party tooling (CI dashboards, build-radiators, browser extensions), i.e., a lower-trust credential handed to less-trusted consumers/environments than a full API-signing session. The vulnerability lets any holder of such a URL/token pivot to reading deploy state (`stack.deploys_and_rollbacks.last`, i.e. `lastBuildStatus`, `lastBuildLabel`, `webUrl`, etc.) for every other stack managed by the Shipit instance — an unauthenticated-for-that-resource read of stack state and deploy output across the installation. This matches the "High" impact bucket: escalation into unauthenticated read of stack state / deploy output beyond what the presented credential authorizes.

### Likelihood Explanation
High. Exploitation requires only a single GET request with a different `stack_id` path segment and the leaked/known CCMenu token — no signature forgery, no session, no privileged account, and no interaction with GitHub credentials. Any party who legitimately received a CCMenu URL for one stack (e.g., an external dashboard operator, or anyone who can see it in a CI tool's config) can trivially enumerate/guess other `owner/repo/environment` stack params and read their state.

### Recommendation
Remove the private `stack` override in `CCMenuController` and use the inherited, scope-respecting `Api::BaseController#stack`/`#stacks` methods (which already honor `current_api_client.stack_id`). If CCMenu's query-string authentication needs to remain distinct, keep only the `authenticate_api_client` override and delete the `stack` override so lookups route through `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`.

### Proof of Concept
1. As an admin, create (or use the existing `CCMenuUrlController#fetch` flow) an `ApiClient` scoped to Stack A: `permissions: ['read:stack']`, `stack: StackA`. Obtain its `authentication_token`.
2. Note Stack A's ccmenu URL: `GET /api/1/ccmenu/StackA/owner/repo/environment.xml?token=<token>` → returns Stack A's status (expected).
3. Using the *same* token, request Stack B's identifier instead: `GET /api/1/ccmenu/StackB/owner2/repo2/environment2.xml?token=<token>`.
4. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (`permissions` includes `'read:stack'`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to Stack B — regardless of the token's `stack_id` binding — returning Stack B's deploy/rollback status in the XML response.
