### Title
Unbounded native-memory-equivalent leak: in-memory `assocKnownBadUnits`/`assocKnownBadJoints` maps grow without bound as an unauthenticated unit poster spams invalid units - (File: joint_storage.js)

### Summary
`joint_storage.js` maintains two process-lifetime, never-evicted JS objects, `assocKnownBadUnits` and `assocKnownBadJoints`, that are populated every time a posted unit or joint fails validation. Any unauthenticated peer that can post units to the DAG (the same actor class reachable in the mdex analog — anyone who can get content rendered/processed) can generate an unlimited number of distinct invalid units, each adding a permanent entry to these maps, exhausting heap memory over time exactly like the Rust `Box::leak` issue exhausted native memory: attacker-controlled key cardinality × no cap × no eviction × entries live for the life of the process.

### Finding Description
`joint_storage.js` declares the caches at module scope: [1](#0-0) 

`checkIfNewUnit` consults `assocKnownBadUnits[unit]` before touching the DB, so it is designed to be checked on every future submission of the same unit: [2](#0-1) 

Entries are added by `purgeJointAndDependencies` (called whenever `validation.ifUnitError` fires from `network.js handleJoint`) and by `saveKnownBadJoint` (called on `ifJointError`): [3](#0-2) [4](#0-3) 

The value stored is bounded (`truncate(error, 200)`), but the **key** — the attacker-chosen `unit` hash or `joint` hash — is fully attacker controlled and unique per crafted invalid unit: [5](#0-4) 

Unlike `assocUnhandledUnits`, which is periodically pruned by `purgeOldUnhandledJoints` (units older than 1 hour are deleted from the map): [6](#0-5) 

there is **no equivalent purge, TTL, or size cap** for `assocKnownBadUnits` or `assocKnownBadJoints` anywhere in the file — a full-text search of the repo confirms these two identifiers appear only in `joint_storage.js`, exclusively at insertion sites, with zero `delete` calls. Even the code that reloads persisted bad joints from the DB at startup deliberately `return;`s before repopulating them (`initUnhandledAndKnownBad`), confirming the in-memory copy is meant to be transient per-process but is never trimmed during the process's actual runtime: [7](#0-6) 

Since every distinct crafted unit hash (e.g., a unit that fails `authentifier verification failed`, a malformed DAG reference, a bad merkle proof, etc.) is trivially cheap for an unauthenticated peer to produce and post via the normal `handleJoint` path in `network.js`, and each such failure permanently records a new key in these two objects for the lifetime of the node process, memory grows unboundedly with attacker-controlled cardinality × attacker-controlled frequency — the same "no size cap, no rate limit, no interning, leaked for the life of the process" pattern as the CVE-2026-53429 `Box::leak` bug, just realized as a JS heap leak instead of a native Rust leak.

### Impact Explanation
An unauthenticated actor who can submit units to a node (any peer, or any wallet client relaying units through a hub) can drive the node's heap memory upward without bound by repeatedly posting syntactically distinct but invalid units/joints. Because the maps are checked on the hot path of unit ingestion (`checkIfNewUnit`, `checkIfNewJoint`), this is reachable from the exact same "unprivileged unit poster" surface named in scope. Eventually this leads to OOM and process crash, taking the node offline — a network-availability denial-of-service consistent with the required "network unable to confirm new units" impact bucket, since a crashed node cannot validate/relay/confirm anything.

### Likelihood Explanation
High: producing an invalid unit with a unique hash is trivial and cheap (change any field, timestamp, or a garbage signature) and can be scripted to submit at high volume; the code path from `network.js`'s `handleJoint` into `purgeJointAndDependencies`/`saveKnownBadJoint` is exercised on virtually every rejected unit, with no rate limiting on distinct-hash spam other than general connection-level throttles.

### Recommendation
Add a TTL/size-bounded eviction policy for `assocKnownBadUnits` and `assocKnownBadJoints` analogous to the existing `purgeOldUnhandledJoints` mechanism (e.g., periodically clear entries older than N minutes, or cap total map size with LRU eviction), so that transient in-memory negative-caching of bad units cannot be weaponized into unbounded memory growth.

### Proof of Concept
1. Run a node with `network.js`'s standard joint-handling pipeline.
2. From an unauthenticated peer connection, repeatedly construct and submit syntactically well-formed but validation-failing units (e.g., invalid signature, `authentifier verification failed`, or malformed DAG parent), each with a unique unit hash (trivial: vary any byte, e.g., timestamp or a nonce field, prior to hashing).
3. Each submission triggers `validation.ifUnitError` → `purgeJointAndDependenciesAndNotifyPeers` → `joint_storage.purgeJointAndDependencies`, which sets `assocKnownBadUnits[unit] = truncatedError` (joint_storage.js:155) — a new, permanent key.
4. Observe process RSS/heap growing linearly with the number of distinct invalid units submitted, with no corresponding decrease, until the node hits `watchMemory()`'s crash threshold in `network.js` (lines 4306-4316) or OOMs outright, taking the node offline.

// onPurgedDependentJoint called for each purged dependent unit
function purgeJointAndDependencies(objJoint, error, onPurgedDependentJoint, onDone){
	var unit = objJoint.unit.unit;
	const truncatedError = truncate(error);
	assocKnownBadUnits[unit] = truncatedError;
	db.takeConnectionFromPool(function(conn){
		var arrQueries = [];
		conn.addQuery(arrQueries, "BEGIN");
		conn.addQuery(arrQueries, "INSERT "+conn.getIgnore()+" INTO known_bad_joints (unit, json, error) VALUES (?,?,?)", [unit, JSON.stringify(objJoint), truncatedError]);
		conn.addQuery(arrQueries, "DELETE FROM unhandled_joints WHERE unit=?", [unit]); // if any
		conn.addQuery(arrQueries, "DELETE FROM dependencies WHERE unit=?", [unit]);
		collectQueriesToPurgeDependentJoints(conn, arrQueries, unit, truncatedError, onPurgedDependentJoint, function(){
			conn.addQuery(arrQueries, "COMMIT");
			async.series(arrQueries, function(){
				delete assocUnhandledUnits[unit];
				conn.release();
				if (onDone)
					onDone();
			})
		});
	});
}

function purgeOldUnhandledJoints(){
	db.query("SELECT unit FROM unhandled_joints WHERE creation_date < "+db.addTime("-1 HOUR"), function(rows){
		if (rows.length === 0)
			return;
		var arrUnits = rows.map(function(row){ return row.unit; });
		arrUnits.forEach(function(unit){
			delete assocUnhandledUnits[unit];
		});
		var strUnitsList = arrUnits.map(db.escape).join(', ');
		db.query("DELETE FROM dependencies WHERE unit IN("+strUnitsList+")");
		db.query("DELETE FROM unhandled_joints WHERE unit IN("+strUnitsList+")");
	});
}

function initUnhandledAndKnownBad(){
	db.query("SELECT unit FROM unhandled_joints", function(rows){
		rows.forEach(function(row){
			assocUnhandledUnits[row.unit] = true;
		});
		return; // ignore old known-bads
		db.query("SELECT unit, joint, error FROM known_bad_joints ORDER BY creation_date DESC LIMIT 1000", function(rows){
			rows.forEach(function(row){
				if (row.unit)
					assocKnownBadUnits[row.unit] = row.error;
				if (row.joint)
					assocKnownBadJoints[row.joint] = row.error;
			});
		});
	});
}
