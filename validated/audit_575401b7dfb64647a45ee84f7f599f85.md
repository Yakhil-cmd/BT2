## Analog Vulnerability Found

### Title
Rounding a computed AA payment amount to zero silently drops the payment while adjoining `state` accounting still commits, causing AA fund loss - (File: `aa_composer.js`)

### Summary
The C4 report describes an ERC4626 vault (`SfrxEth.redeem`) that reverts when a proportional redemption amount rounds down to zero, blocking withdrawal but preserving fund safety through atomic revert. In `ocore`'s Autonomous Agent (AA) engine, the equivalent situation — a payment amount computed from a formula (typically a proportional share, e.g. `round(share * balance)`) that rounds to zero — is **not** handled atomically. Instead of aborting the whole trigger, `aa_composer.js` silently drops the zero-amount payment message while any sibling `state` message in the same `messages` array (e.g. one that decrements the user's tracked share/balance) still executes and gets committed, causing an unrecoverable loss of the triggering user's value with no offsetting transfer.

### Finding Description
In `handleTrigger`'s `sendUnit` function, output amounts are sanitized and zero-amount outputs are stripped, then payment messages left with no outputs are removed from the message list: [1](#0-0) 

Only messages with `app === 'payment'` are subject to this removal (`message.app !== 'payment' || message.payload.outputs.length > 0`). Any other message in the same `messages` array — most importantly `state` messages that perform balance bookkeeping — is left untouched and is executed later: [2](#0-1) 

The final `objUnit.messages` (after this filtering) is passed unmodified to `executeStateUpdateFormula`, which applies the `state` message's formula and commits new state vars regardless of whether the corresponding payment survived the filtering: [3](#0-2) 

This exact "proportional share → `round()` → payment output" pattern, which is the root cause class in the C4 report, is present in the repository's own bundled example AA templates that are meant to guide production AA authors, e.g. the "divest MM shares" case in the shipped Uniswap-like market maker sample: [4](#0-3) 

Here `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` and the payout is `round($investor_share * balance[$asset])`. As `var['mm_asset_outstanding']` or `balance[$asset]`/`balance[base]` shrink through many partial divestments (directly analogous to the C4 report's scenario where repeated fractional withdrawals shrink a derivative's balance to near zero), a subsequent divest can compute `round(...) == 0` for one or both payout messages. Those payment messages get filtered by `aa_composer.js`, but the trailing `state` message `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]` is unaffected and still burns the user's shares.

### Impact Explanation
This maps to the "AA fund loss" acceptance criterion. Unlike the original ERC4626 bug (which only causes a revert/DoS while preserving funds), ocore's AA composer converts the same rounding condition into an actual, irreversible loss of value for the AA trigger sender: their shares/claim are debited by the `state` message while the entitled payout silently disappears, and the underlying pool balance is effectively retained by (and redistributed among) the AA's other participants. Any AA using a proportional-share redemption/divest/withdraw pattern with an unconditioned `state` decrement is exposed.

### Likelihood Explanation
Medium. It requires: (1) an AA computing a payout via division/rounding of a shrinking pool balance, and (2) a `state` message that updates accounting independent of whether the payment output ended up nonzero. This is not a contrived edge case — it is the literal pattern present in the project's own official sample AA templates (`uniswap_like_market_maker.oscript`, similarly structured examples in `order_book_exchange.oscript`), which are likely to be copied/adapted by real AA authors, and the underlying balance can be driven toward the vulnerable range by repeated ordinary user activity (proportional partial withdrawals), exactly as described in the original C4 finding for `SfrxEth`.

### Recommendation
- When a `payment` message is stripped down to zero outputs and removed, treat this as a fatal condition for the whole trigger (bounce/revert all associated `state` changes) rather than silently continuing to execute sibling messages, unless the AA author has explicitly guarded for it.
- Alternatively, expose the final, post-filtering payment amounts to the `state` formula evaluation so that `state` message authors can conditionally skip debits when the corresponding payout amount is zero (e.g., `if ($amount == 0) bounce('amount too small');`), and document this pitfall (including in the bundled sample AAs) so AA templates are not shipped with this rounding-related fund-loss issue.

### Proof of Concept
1. Deploy an AA following the "divest MM shares" pattern from `test/samples/uniswap_like_market_maker.oscript`, where divesting computes `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` and pays `round($investor_share * balance[$asset])` / `round($investor_share * balance[base])`, followed by a `state` message unconditionally decrementing `var['mm_asset_outstanding']`.
2. Through many ordinary partial divestments by various users, drive `var['mm_asset_outstanding']` and/or `balance[$asset]`/`balance[base]` down to small integer values (mirroring the "weight set to 0, ~60 sequential 50% withdrawals" scenario from the original report).
3. Have a small remaining holder trigger a divest whose `round(investor_share * balance[...])` evaluates to `0` for one or both payout messages.
4. Observe in `aa_composer.js` (`sendUnit`) that the zero-output payment message(s) are filtered out at lines 1278/1281, yet the `state` message decrementing `var['mm_asset_outstanding']` by the user's full `trigger.output[[asset=$mm_asset]]` still executes and commits (lines 1300-1311, 1403-1408) — the user's shares are burned but they receive nothing back.
