### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by SHA across the entire `commits` table, with no filter tying the match to the repository that was authenticated via the webhook's `X-Hub-Signature` (`repository_owner` → `Shipit.github(organization:)`). Any GitHub organization that can send a validly-signed webhook for its own repository can flip the CI status (and thus `deployable?`) of a commit belonging to an unrelated stack, as long as the two commits share a SHA.

### Finding Description
The broken binding: `organization_that_signed_the_webhook (repository_owner from payload, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` MUST equal `organization_owning_the_Commit_row_mutated (commit.stack.repository.owner)`. It does not.

Code path:
1. `Shipit::WebhooksController#verify_signature` derives `repository_owner` from the attacker-controlled payload's `repository.owner.login` and fetches `Shipit.github(organization: repository_owner)`, then verifies the HMAC signature against that org's `webhook_secret` [1](#0-0) . This only proves the request was signed by whichever org's secret was used — the attacker's own org, `attacker/evil`.
2. `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the raw parsed JSON `params` (which include the attacker-controlled `repository.full_name`) [2](#0-1) .
3. `StatusHandler#process` never touches `repository_name` or `stacks` (the base `Handler` provides exactly these scoping helpers, `stacks` and `repository_name`, which every other handler in this class uses, e.g. `PushHandler#process` calls `stacks.not_archived.where(branch:)`, and `CheckSuiteHandler#process` calls `stacks.where(branch:)`) [3](#0-2) [4](#0-3) [5](#0-4) . Instead, `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which is a global, unscoped lookup across all stacks/repositories [6](#0-5) .
4. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, which creates a `Status` row with the attacker-supplied `state` [7](#0-6) , `Status.replicate_from_github!` persists `state: github_status.state` verbatim [8](#0-7) .
5. `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, so a forged `success` status directly flips `deployable?` to true when `ignore_ci?` is false [9](#0-8) .

Exploit flow: attacker owns `attacker/evil` with a valid `webhook_secret` configured for their org (a normal GitHub App/webhook installation on their own repo, which is legitimate and requires no privilege over the victim). Attacker crafts (or naturally has) a commit whose SHA collides with a SHA already present in `victim/prod`'s tracked commits (trivially achievable with the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which produces a `Commit` row for any repo that ever contains that content-identical tree/commit — or via a manufactured identical patch/commit metadata producing an identical SHA1 in the low-security SHA1 case). Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, JSON body `{"repository": {"full_name": "attacker/evil", "owner": {"login": "attacker"}}, "sha": "<shared-sha>", "state": "success", ...}`, correctly signed with `attacker`'s own webhook secret. `verify_signature` passes because it only checks the signature against `attacker`'s org. `StatusHandler#process` then finds and mutates **every** `Commit` row in the database with that SHA, including the one belonging to `victim/prod`.

Why existing guards don't catch this: `verify_signature` authenticates "this payload was signed by org X," not "org X is authorized to touch stack/commit Y." No other guard (`drop_unhandled_event`, `ExplicitParameters` schema, model validations) checks repository identity for this specific handler, unlike `PushHandler`/`CheckSuiteHandler`/PR handlers which all scope explicitly through `stacks` or `Repository.from_github_repo_name(params.repository.full_name)`.

### Impact Explanation
An attacker fully controlling only their own GitHub org/repo webhook secret can forge a `success` (or `failure`/`error`) CI status on a commit belonging to a completely unrelated stack/repository/organization, as long as a SHA collision exists. This directly matches the "payload for one repository mutating another's stack, commit ... or an unauthorized deploy" Critical category: flipping `Commit#deployable?` to true on `victim/prod` can enable an unauthorized deploy of a commit that never actually passed victim's own CI, bypassing the entire purpose of CI gating. The write is repeatable against any repository/stack for which a colliding SHA can be found (trivially, the empty-tree SHA is a candidate that many repos may share if they have an empty-content commit, though naturally-occurring collisions on populated projects are the main limiting factor — see Likelihood).

### Likelihood Explanation
Preconditions: (1) `victim/prod` stack must already have a `Commit` row with a SHA identical to one the attacker's own commit uses; (2) `ignore_ci?` false on victim's stack (default) so the forged status actually matters for `deployable?`; (3) attacker needs a legitimate GitHub webhook configured on their own repo pointing at the Shipit host (standard low-privilege setup, no victim secrets needed). The primary constraint is finding/engineering a SHA collision with a specific victim commit, which is easy only in specific scenarios (e.g., shared boilerplate/empty-tree commits, generated commits with identical metadata across mirrored/forked histories) rather than being achievable against an arbitrary victim commit at will. Nonetheless, no secret material or privileged role is required, and the request is trivially repeatable once a collision is found.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to the authenticated repository, mirroring `PushHandler`/`CheckSuiteHandler`: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently filter via `Repository.from_github_repo_name(repository_name).stacks.joins(:commits).where(shipit_commits: { sha: params.sha })`, ensuring the `Commit` rows touched belong only to stacks whose repository matches `params.repository.full_name` (and thus the org that signed the webhook).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status from one repository must not mutate a commit belonging to another repository's stack" do
  # victim stack/commit, e.g. shipit_stacks(:shipit) with a shipit_commits fixture sha "deadbeef..."
  victim_commit = shipit_commits(:first) # belongs to victim's repo/org e.g. "shopify/shipit-engine"
  shared_sha = victim_commit.sha

  # attacker stack fixture pointing at a different repo/org, e.g. "attacker/evil"
  attacker_repo_owner = "attacker"

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => attacker_repo_owner } }
  }.to_json

  # Simulate that only attacker's org webhook_secret verified this payload
  Shipit.stubs(:github).with(organization: attacker_repo_owner).returns(
    stub(verify_webhook_signature: true)
  )

  refute victim_commit.reload.success?

  post :create, body:, as: :json

  # Assert both sides of the binding: signer (attacker) != commit owner (victim), yet victim commit mutated
  assert victim_commit.reload.success?, "victim commit's status was forged by a webhook signed only for attacker/evil"
end
```
This demonstrates that a webhook whose signature is verified only against `attacker/evil`'s `webhook_secret` is able to write a `Status` row (and flip `deployable?`) on a `Commit` belonging to an entirely different repository/stack, with no live GitHub calls.
