### Title
Webhook signature check authenticates a different GitHub organization than the one whose repository the handler acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate the payload using `repository.owner.login` (falling back to `organization.login`), but the event handlers that actually perform the write (queue syncs, record CI statuses, archive/unarchive review stacks, etc.) resolve the target `Stack`/`Repository` from a *different* field of the same JSON body: `repository.full_name`. These two fields are never cross-checked against each other.

### Finding Description
In <cite repo="Jortegata/shipit-engine--005" path="app/controllers/shipit/webhooks_controller.rb" start="24,59" end="30,62" /> the controller does: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the per-organization `GitHubApp` config (and thus the `webhook_secret` used for HMAC verification) purely from `repository.owner.login` (or `organization.login`) in the untrusted, attacker-supplied JSON body.

Every handler, however, resolves the repository/stack to act on from a sibling field of the same payload, `repository.full_name`: [3](#0-2) 

For example, `PushHandler` uses this `stacks` scope to enqueue a `GithubSyncJob` for a branch: [4](#0-3) . `StatusHandler` records a commit status by SHA only, with no repository check at all: [5](#0-4) . The pull-request handlers likewise resolve `repository` from `params.repository.full_name` independent of what the signature check used: [6](#0-5) .

Shipit explicitly supports hosting multiple independently-administered GitHub organizations from one instance, each with its own App ID/private key/`webhook_secret`, as documented in the multi-org config sample: [7](#0-6) . Whoever owns/administers one of these configured GitHub App installations (e.g. an org "attackerorg" that has legitimately been onboarded to this shared Shipit instance) knows their own `webhook_secret`.

Because the code never asserts `repository.owner.login == repository.full_name.split('/').first`, an attacker who is the legitimate owner of "attackerorg" (and thus knows attackerorg's `webhook_secret`) can craft a JSON body where:
- `repository.owner.login` = `"attackerorg"` (used only to pick the verification key — HMAC will validate correctly), and
- `repository.full_name` = `"victimorg/some-repo"` (used by every handler to resolve the target stack/repository to mutate).

The signature is computed over the whole `raw_post`, so it *will* validate — the code only checks payload integrity/authenticity against attackerorg's secret, not that the two organization references inside the payload agree.

### Impact Explanation
This breaks the equality "organization that authenticated == organization whose repository is written," which is exactly the binding this scan is chartered to find. An attacker who administers only their own, unrelated GitHub organization on a shared Shipit instance can:
- Trigger `GithubSyncJob`/deploy pipeline refresh cycles against a victim org's stacks via `PushHandler` (potential unauthorized deploy trigger through Shipit's normal commit-sync-then-deploy workflow).
- Inject/forge commit CI statuses for a victim's commits via `StatusHandler`, which is used elsewhere to gate whether a deploy/merge is allowed (`Commit#create_status_from_github!`), enabling a merge/deploy safety bypass.
- Archive/unarchive or otherwise mutate victim review stacks and pull-request metadata via the `PullRequest::*` handlers.

This qualifies as a cross-organization write achieved without any credential belonging to the victim organization — matching the "cross-repository writes / unauthorized deploy" Critical/High impact bucket.

### Likelihood Explanation
Requires no Shipit session, API token, or private key belonging to the victim. The only prerequisite is that the attacker legitimately controls one of the organizations already configured on the shared multi-tenant Shipit instance (a documented, supported deployment topology) and therefore knows their own org's `webhook_secret`. No social engineering or privileged access to the target is required — only knowledge of the field-naming mismatch in the two payload lookups.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select the verification key equals the owner segment of `repository.full_name` (and `organization.login` when the `repository` key is absent) before dispatching to any handler; reject the webhook (422) on mismatch.

### Proof of Concept
1. Shipit instance is configured with two orgs, `attackerorg` and `victimorg`, each with distinct `webhook_secret`s (per the multi-org config schema).
2. Attacker, who owns the `attackerorg` GitHub App installation, knows `attackerorg`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist>",
  "repository": {
    "owner": { "login": "attackerorg" },
    "full_name": "victimorg/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attackerorg_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "attackerorg")` and the signature validates successfully.
6. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"victimorg/victim-repo"` and enqueues `GithubSyncJob` for victim's stack — a write action on an organization the attacker never authenticated as.

Note: I was not able to fully verify from the indexed code alone whether `Shipit.github(organization:)` raises `GithubOrganizationUnknown` for orgs not present in config (it appears to, per the rescue block in `WebhooksController`), which would limit this to configurations that actually host ≥2 organizations; if a Devin session is available it would be worth confirming `lib/shipit.rb`'s `github` lookup implementation directly to validate this edge case precisely.
