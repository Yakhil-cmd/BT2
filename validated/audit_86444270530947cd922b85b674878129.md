### Title
Cross-organization Team hijack via `Team.find_or_create_by!(github_id:)` ignoring organization scope - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id`, and the block that sets `team.organization = params.organization.login` only executes on record *creation*, never on lookup of an existing record. [1](#0-0)  An attacker who owns their own GitHub org (and can therefore legitimately trigger a correctly-signed `membership` webhook for that org) can submit `team.id` equal to the `github_id` of a `Team` record that actually belongs to a different, victim organization, causing the attacker to mutate that victim `Team`'s membership.

### Finding Description
The broken binding, stated as an equality that the code assumes but never checks: `team.organization == params.organization.login` for the `Team` matched by `github_id`. In reality only `Team.find_or_create_by!(github_id: params.team.id)` is checked; `organization` is written only inside the `do |team| ... end` block, which ActiveRecord only invokes when a **new** record is being built, not when an existing row is found. [1](#0-0) 

Request path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the signature using `Shipit.github(organization: repository_owner)`. [2](#0-1) [3](#0-2)  If the attacker omits `repository` and sets `organization.login` to their own org, and signs the request with their own org's legitimately-known `webhook_secret`, verification passes honestly — `repository_owner` really does equal the attacker's own org.
2. `MembershipHandler` schema only requires `team.id`, `organization.login`, `member.login`, with no cross-check against the verified org. [4](#0-3) 
3. `find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id)`. The `teams` table has a unique index only on `[organization, slug]`, **not** on `github_id` alone — confirming nothing in the schema prevents/relates a `github_id` to a specific org either. [5](#0-4)  If a `Team` row with that `github_id` already exists (e.g. seeded from a prior legitimate webhook belonging to a victim org, as in the fixture `cyclimse_cooks` with `github_id: 2`, `organization: cyclimse`), `find_or_create_by!` returns that existing record untouched — the block does not run, so `team.organization` remains the victim's org. [6](#0-5) 
4. Back in `process`, `team.add_member(member)` or `team.members.delete(member)` executes on this victim `Team`, using a `member.login` fully controlled by the attacker. [7](#0-6) 

Exploit request: attacker POSTs `/webhooks` with header `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with their own org's webhook secret, and body `{"action":"added","team":{"id":2,"name":"x","slug":"x","url":"http://x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker-controlled-user"}}` (no `repository` key). `repository_owner` resolves to `attacker-org`, signature verifies honestly, but `team.id: 2` belongs to a different org's `Team` in the DB.

Existing guards fail because: `verify_signature` only proves the *request* came from a legitimate org's GitHub App installation for whichever org string is present in the payload — it never proves that the numeric `team.id` inside the payload belongs to that same org. `find_or_create_team!` has no code path that calls the GitHub API to confirm `team.organization` matches `params.organization.login` when the team already exists in Shipit's database.

### Impact Explanation
An attacker with control of one organization can add or remove arbitrary GitHub users from a `Team` belonging to a different organization inside Shipit's database, without ever needing access to the victim org's webhook secret. Since `User#authorized?` gates the whole app on membership in `Shipit.github_teams`, an attacker who guesses/enumerates the `github_id` of a team listed in `Shipit.github_teams` for a victim installation can grant themselves (or any GitHub login) membership in that team, and thus authorization to log in and use the target Shipit instance's deploy features (privilege escalation into `Shipit.github_teams`). [8](#0-7)  This matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and depending on downstream permission use of those teams could enable further critical actions (deploys, merges) gated by team membership. The attack is repeatable against any pre-existing `Team` row whose `github_id` the attacker can guess (sequential integer GitHub team IDs).

### Likelihood Explanation
Preconditions: the attacker must legitimately own/administer at least one GitHub organization that has installed the Shipit GitHub App (so they know a valid webhook secret for signing), and a `Team` row for the victim org must already exist in Shipit's database with a known/guessable `github_id` (teams IDs are small sequential integers on GitHub, and any prior legitimate membership event for the victim org would have created the row). No Shipit session, API token, or victim secrets are needed. This is a low-cost, fully repeatable attack requiring only crafting one HTTP POST with a correctly signed body under the attacker's own org.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after resolving/creating the `Team`, verify `team.organization == params.organization.login` (case-insensitively) before mutating membership, and raise/reject the event (or re-fetch/validate against `params.organization.login` explicitly using `find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`) so a `github_id` collision across organizations cannot silently reuse another org's `Team` record.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb`, following existing fixtures):
```ruby
test ":membership from attacker's own verified org mutates a different org's Team" do
  victim_team = shipit_teams(:cyclimse_cooks) # organization: 'cyclimse', github_id: 2
  assert_equal 'cyclimse', victim_team.organization

  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'http://x' },
    organization: { login: 'shopify' }, # attacker's own, verified org
    member: { login: 'attacker-controlled-user' }
  }.merge(repository: { owner: { login: 'shopify' } }) # optional/omittable

  # signature computed for 'shopify' org secret (attacker legitimately knows it)
  Shipit.github(organization: 'shopify').expects(:verify_webhook_signature).returns(true)

  assert_no_difference -> { Team.count } do
    post :create, body: payload.to_json, as: :json
  end

  victim_team.reload
  assert_equal 'cyclimse', victim_team.organization # unchanged - still victim's org
  assert victim_team.members.exists?(login: 'attacker-controlled-user') # BUT membership mutated by attacker
end
```
Assertion on both sides of the binding: `victim_team.organization` (`'cyclimse'`) never equals `payload[:organization][:login]` (`'shopify'`), yet the victim team's `members` association is still mutated by the attacker's request — proving the broken binding.
