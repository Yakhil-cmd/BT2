### Title
Uncaught exception in `readDataFeedValue` sort comparator crashes node during AA data-feed evaluation - (File: `data_feeds.js`)

### Summary
CVE-2015-20001 describes Rust's `BinaryHeap` becoming corrupted when a user-supplied comparator panics mid-sort, because the sort routine assumed the comparator was infallible. `ocore` has an analogous pattern: `Array.prototype.sort()` is called with a comparator that can itself `throw`, and that throw is not defensively handled by the calling AA-evaluation code, which assumes `readDataFeedValue`'s callback-style API never throws synchronously.

### Finding Description
In `readDataFeedValue`, when unstable AA-posted data feeds are included (`unstable_opts` truthy but not `'all_unstable'`), multiple matching candidate data-feed messages are collected into `arrCandidates` and sorted: [1](#0-0) 

If two candidates tie on both `latest_included_mc_index` and `level` (which can occur naturally — the DAG places no uniqueness constraint on `level` between unrelated units) and `bIncludeAllUnstable` is false (the case used by AA evaluation, since `unstable_opts` is passed as `bAA === true`, not the string `'all_unstable'`), the comparator executes `throw Error("can't sort candidates "+a+" and "+b);` inside `Array.prototype.sort()`.

This function is invoked synchronously and directly (not inside a `try/catch`) from the `data_feed` oscript operator during AA trigger handling: [2](#0-1) 

Neither `getDataFeed`, nor the `evaluate()` dispatcher in `formula/evaluation.js`, nor the trigger-handling code in `aa_composer.js` wraps this call path in a `try/catch`. A synchronous `throw` from inside `Array.sort()`'s comparator propagates as an uncaught exception through the whole call stack (unlike errors reported through the `cb(err)`/`setFatalError` convention that the rest of the formula evaluator uses consistently). Because AA evaluation runs on the main event loop while processing an untrusted, attacker-posted unit (the primary trigger), an uncaught exception here is a `throw Error` that Node.js will not automatically turn into a rejected promise or caught callback — it bubbles up and, depending on the surrounding call context (synchronous chain from `write.js`/unit processing), can crash the node process or leave batch/db-transaction state partially applied.

This is the closest structural analog to CVE-2015-20001: a sort/heap-like routine that is not "panic-safe" — a comparator throw that the routine's callers never anticipated, occurring on attacker-influenced input reachable by any unit poster (an oracle-like address referenced in an AA's `oracles` parameter) that can arrange for two unstable data-feed units to be posted at the same level/mci with different values before an AA trigger reads them.

### Impact Explanation
An unhandled synchronous exception thrown deep inside `oscript` evaluation of a widely-used primitive (`data_feed[[...]]` with default `ifseveral="last"`) can crash the node process handling AA triggers, or leave the node's in-memory caches / open DB transaction in an inconsistent state if the exception unwinds through code that assumed only asynchronous, callback-delivered errors. That translates into "node unable to process/confirm new units" — nodes hitting this code path can crash or diverge from nodes that never reach the tie condition, causing consensus/availability impact on AA-dependent units.

### Likelihood Explanation
Reaching the throwing branch requires:
1. An AA that reads a data feed with `oracles` including an address (or set of addresses) actively posting unstable data feeds, without specifying `ifseveral="abort"`.
2. Two matching unstable data-feed messages from author(s) in that oracle set with identical `latest_included_mc_index` and identical `level` but different values.

Level ties across unrelated DAG units are not exotic — any two units built without one being an ancestor of the other can end up at the same level, and an attacker controlling the oracle address(es) referenced by a target AA can deliberately post two conflicting unstable data-feed units in parallel (same parents/level) to trigger this. This makes the condition realistically reachable by an unprivileged unit poster who also controls (or colludes with) the oracle address the AA trusts, or in scenarios using `oracles` as a multi-address group where a race between independent posters produces the tie. Likelihood is assessed as medium: it needs a specific tie condition, but that condition is fully attacker-constructible without needing crypto breaks or privileged access.

### Recommendation
Make `readDataFeedValue`'s tie-break deterministic without ever throwing: fall back to an unambiguous, deterministic secondary key (e.g., compare `unit` hash lexicographically) instead of raising an exception for the "ambiguous" case. Additionally, wrap the `.sort()` call (and any other comparator that can throw) in a `try/catch`, converting the failure into a normal `cb(err)`/`bAbortedBecauseOfSeveral` result so it is handled the same way as other data-feed evaluation errors and never escapes as a raw synchronous exception during unit/AA processing.

### Proof of Concept
1. Attacker controls (or is) an address `ORACLE` referenced in an AA's formula as `data_feed[[oracles="ORACLE", feed_name="x"]]` (default `ifseveral="last"`).
2. Attacker crafts two units, both authored by `ORACLE` (or `ORACLE`'s two co-signers if multi-address), each posting `data_feed` message with `payload.x` set to two different values, arranged so both units land at the same DAG `level` and the same `latest_included_mc_index` (e.g., both built directly on the same set of parents with no dependency between them) — both left unstable.
3. Attacker sends a primary trigger unit to the AA that evaluates the `data_feed[[...]]` formula while both candidate units are still unstable.
4. During AA trigger processing, `readDataFeedValue` collects both candidates into `arrCandidates`, finds `latest_included_mc_index` and `level` equal for both, `bIncludeAllUnstable` is `false` (since `unstable_opts === bAA === true`, not `'all_unstable'`), and the sort comparator throws `Error("can't sort candidates ...")`, propagating synchronously out of `Array.prototype.sort()` through `getDataFeed` → `evaluate()` → the AA-trigger handling code, since no `try/catch` intercepts it — an unhandled exception during unit processing.
