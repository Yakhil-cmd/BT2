### Title
Webhook signature verification keyed on `repository.owner.login` while stack mutation is keyed on `repository.full_name` allows cross-organization forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the request against using `params.dig('repository','owner','login')`, but `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler, including `PushHandler`, to resolve the `Stack`/`Repository` that gets mutated) reads a *different* JSON field: `payload.dig('repository','full_name')`. These are two independent, attacker-controlled keys inside the same unsigned-until-verified JSON body, and nothing enforces that they refer to the same organization.

### Finding Description
In a multi-org Shipit deployment (`config/secrets.yml` with multiple `github.<org>` entries, as exercised by `Shipit.github(organization:)` in `lib/shipit.rb:170-181` and `test/dummy/config/secrets_double_github_app.yml`), each organization can have its own `webhook_secret`. `WebhooksController`:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

selects the signing secret using `repository.owner.login`. Meanwhile `Shipit::GitHubApp#verify_webhook_signature`:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

returns `true` unconditionally when that organization's `webhook_secret` is not configured (optional per `docs/setup.md`). So an attacker who controls (or targets) any org config with `webhook_secret: nil` can send an unsigned/arbitrarily-signed payload that passes `verify_signature` purely because `repository.owner.login` resolves to that unsecured org.

However, the actual business logic never re-checks that binding. Every handler resolves the target repository from a *different* field:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and `PushHandler#process` acts on whatever stacks match, triggering `stack.sync_github(expected_head_sha: params.after)`: [4](#0-3) 

Because `repository.owner.login` (used to pick the verifying org/secret) and `repository.full_name` (used to pick the mutated `Repository`/`Stack`) are two separate JSON keys with no cross-validation, an attacker can submit a payload where:
- `repository.owner.login = "org-with-no-webhook-secret"` (satisfies `verify_signature`, which returns `true` unconditionally for that org), while
- `repository.full_name = "victim-org/victim-repo"` (the real, secret-protected repository whose stack actually gets acted upon).

This breaks the intended binding: **organization authenticated (via `repository.owner.login`) == repository actually written (via `repository.full_name`)**. Before the attack, that equality always holds for genuine GitHub-originated webhooks (GitHub always sets both fields consistently); after the attacker's forged request, the equality is violated, letting the attacker drive `GithubSyncJob`, team/membership churn (`membership` handler uses `organization.login` similarly), or `PullRequest` state changes against a repository protected by a different org's `webhook_secret` while only satisfying the check for an unrelated, unsecured org.

### Impact Explanation
This allows unauthenticated writes into stacks belonging to an organization whose webhook secret the attacker does not know, as long as any other configured organization in the same Shipit instance has no `webhook_secret` set (a documented, supported, "optional" configuration). Concretely this can: force `GithubSyncJob`/`RefreshCheckRunsJob` runs against arbitrary stacks, forge `status` (commit) states, spoof `pull_request` opened/closed/labeled events to archive/unarchive review stacks, or fabricate `membership` events. This is a cross-organization write achieved by exploiting a mismatch between the credential-verification key and the mutation key, matching the "Critical: cross-repository writes" impact bucket in a multi-org Shipit deployment.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (`github.<org>` config with more than one organization), and (2) at least one configured organization with `webhook_secret` unset/blank — both are explicitly supported, documented configurations (`docs/setup.md` marks `webhook_secret` "optional"). Given that, the attack requires no credentials, no session, and no GitHub App access — just crafting a JSON POST to `/webhooks` with mismatched `repository.owner.login` / `repository.full_name`.

### Recommendation
In `WebhooksController#verify_signature`, derive the verification key from the same field the handlers use to resolve the target repository (`repository.full_name`'s owner segment), or conversely make `Handler#repository_name` resolve strictly from the same `repository.owner.login` value that was used to verify the signature. Additionally, treat an organization with no `webhook_secret` configured as unable to authenticate other organizations' payloads — do not let `verify_webhook_signature` return `true` implicitly for a fields-mismatched cross-org payload; reject webhooks where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
Preconditions: `secrets.github` configured with two orgs, e.g. `openorg` (`webhook_secret: nil`) and `victim-org` (`webhook_secret: "s3cr3t"`), each installed via a GitHub App, with a Shipit `Stack` tracking `victim-org/victim-repo`.

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "openorg" },
    "full_name": "victim-org/victim-repo"
  }
}
```

1. `WebhooksController#repository_owner` → `"openorg"`.
2. `Shipit.github(organization: "openorg").verify_webhook_signature(...)` → `true` immediately (`webhook_secret` blank), regardless of the supplied `X-Hub-Signature`.
3. `create` runs `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }`, and `PushHandler#stacks` resolves via `payload.dig('repository','full_name')` → `Repository.from_github_repo_name("victim-org/victim-repo")`, enqueuing `GithubSyncJob` for that stack — despite never having presented a valid signature for `victim-org`'s secret.

I was unable to execute this against a live instance (no test/terminal access in this mode); the trace above is derived directly from reading `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`, and `lib/shipit.rb`/`lib/shipit/github_app.rb`. Confirming exploitability end-to-end (including whether any additional consistency check exists elsewhere, e.g. in `Repository.from_github_repo_name` or `GithubSyncJob`) would benefit from a Devin session with full repo/test access.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
