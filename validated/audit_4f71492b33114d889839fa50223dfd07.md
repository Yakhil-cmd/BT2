## Finding

### Title
Permissionless `DepositDelegatorRewards` allows inflating a vote account's shared reward pool during the epoch-rewards distribution window, corrupting reward calculations - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The vote program's `deposit_delegator_rewards` instruction (SIMD-0123) is the on-chain analog of `Shelter.donate()`: it is a fully permissionless "top-up" instruction that any signer can call at any time to add lamports to a shared pool (`pending_delegator_rewards`) that is later divided pro-rata among unprivileged stake-account holders. Like `Shelter.donate()`, this deposit function has no restriction tied to the reward-calculation/"grace" period, so deposits can land after the pool value has already been used to compute payouts for some accounts but not others.

### Finding Description
`deposit_delegator_rewards` lets anyone who signs the source-account transfer add an arbitrary amount to `vote_state.pending_delegator_rewards` with no epoch/timing restriction: [1](#0-0) [2](#0-1) 

`pending_delegator_rewards` is subsequently read as the numerator of the pro-rata "block reward" split among all stake accounts delegated to that vote account, based on each stake's share of `total_active_stake`: [3](#0-2) 

This calculation is invoked both during the original epoch-boundary reward calculation (`calculate_stake_rewards_and_commissions`) and during **recalculation**, which re-derives stake rewards for partitions not yet distributed using the *current* on-chain vote-account state (not a value frozen at the start of the distribution window): [4](#0-3) [5](#0-4) 

The reward distribution itself happens over multiple blocks/partitions determined by a deterministic, publicly-known hash of `parent_blockhash` (`hash_rewards_into_partitions`), meaning the set of stake accounts scheduled for later partitions is knowable in advance: [6](#0-5) 

Because `deposit_delegator_rewards` can be called at any block, including in the middle of an active `EpochRewardStatus::Active` distribution window, an attacker (or even an honest but late depositor) can increase `pending_delegator_rewards` for a vote account **after** some of its delegated stake accounts have already been paid out (using the old, smaller pool value) but **before** the remaining partitions are calculated/recalculated (which will use the new, larger pool value). This directly mirrors the Shelter bug: `savedTokens[_token]`-equivalent (`pending_delegator_rewards`) grows after some "claims" (stake-reward distributions) have already occurred, inflating what remaining stakers receive relative to what earlier stakers received for the same reward epoch — a misattributed/inconsistent reward split within a single distribution.

### Impact Explanation
This causes misattributed rewards among stake accounts delegated to the same validator within the same reward epoch: stake accounts processed in earlier partitions receive a payout computed from a smaller `pending_delegator_rewards` value, while stake accounts in later partitions (whose reward is only finalized when `recalculate_stake_rewards` runs, e.g., after a bank/snapshot restore mid-distribution) receive a payout computed from an inflated value — an unfair, unequal split of what should be a single epoch's reward pool, without changing overall protocol invariants like total supply. It also opens a griefing/self-dealing vector: a party can strategically time a `DepositDelegatorRewards` deposit to selectively skew rewards toward specific not-yet-processed partitions/stake accounts identifiable via the public partition-hash schedule.

### Likelihood Explanation
This requires (a) a mid-distribution bank restart/snapshot-restore that triggers `recalculate_partitioned_rewards_if_active`/`recalculate_stake_rewards` (the code and its tests indicate this is an expected, exercised recovery path, not a purely theoretical one — see `test_delegation_adjustment_at_distribution`-style tests around recalculation), and (b) the `DepositDelegatorRewards` instruction being callable with no check against `EpochRewardStatus`/epoch-rewards-active state. I was not able to fully verify within the available context whether `pending_delegator_rewards` is decremented at distribution time (i.e., whether it is treated as a consumed pool per epoch or a running balance), which affects the precise magnitude/frequency of exploitability; this should be verified before assigning a final severity.

### Recommendation
Add a check in `deposit_delegator_rewards` (or in the block-reward calculation path) that rejects/queues deposits made while `EpochRewardStatus` is `Active` for the vote account's stakers, analogous to the recommended `Shelter.donate()` fix — i.e., require that new deposits are only accepted outside the active distribution window, or snapshot `pending_delegator_rewards` once at the start of the distribution window and use that frozen value consistently for both the calculation and any subsequent recalculation of unpaid partitions.

### Proof of Concept
Not independently reproduced with a test harness in this session due to tool/time limitations; the control-flow trace above (`deposit_delegator_rewards` → `pending_delegator_rewards` → `calculate_block_reward` → `calculate_stake_rewards_and_commissions` called both at initial calculation and in `recalculate_stake_rewards`, with distribution split across blockhash-derived partitions) establishes the reachable path from an unprivileged instruction to inconsistent reward attribution. Confirming the decrement/consumption semantics of `pending_delegator_rewards` at distribution time, and exercising `recalculate_partitioned_rewards_if_active` with an intervening `DepositDelegatorRewards` call, would be needed to produce a concrete PoC.

```rust
/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
```

```rust
impl Bank {
    /// Process reward distribution for the block if it is inside reward interval.
    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );
```
