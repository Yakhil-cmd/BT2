### Title
Webhook signature is bound to the payload's `repository.owner.login` GitHub App, but `StatusHandler`/`PushHandler`/`CheckSuiteHandler` write to state selected by unrelated payload fields (`sha` globally, or `repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (`github: { orgA: {...}, orgB: {...} }`), the webhook signature is verified using the secret belonging to whichever organization the attacker puts in `repository.owner.login` / `organization.login`, but the state-mutating handlers key their side effects off of fields that are never cross-checked against that verified organization: `StatusHandler` looks up commits by `sha` with no repository/organization scoping at all, and `PushHandler`/`CheckSuiteHandler` resolve the target `Stack` via `repository.full_name`, which is likewise never checked against the organization whose secret produced a valid signature.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to verify against based on `repository_owner`, itself taken straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization webhook secrets from the multi-org config schema shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`: [3](#0-2) 

The HMAC only proves "this body was produced by whoever holds OrgA's `webhook_secret`" (i.e., OrgA's own GitHub App admin, who legitimately knows their own secret) - it says nothing about which stack/commit the body's other fields should be allowed to affect. After signature check passes, handlers run and select their target purely from attacker-controlled fields with no re-validation against the organization that was actually authenticated:

- `StatusHandler#process` queries `Commit.where(sha: params.sha)` **globally, with no repository or organization scoping whatsoever**, then writes a status onto every matching commit across the whole installation: [4](#0-3) 

- `PushHandler`/`CheckSuiteHandler`/`Handler#stacks` resolve the target repository purely via `repository.full_name` from the body, independent of `repository.owner.login` used for signature selection: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality that should hold but is broken: `organization_whose_secret_verified_the_HMAC == organization_that_owns_the_repository/commit_being_mutated`. Before the attacker's forged request, an admin of OrgA can only produce webhooks that legitimately originate from OrgA's own GitHub App/webhook config. After the forged request (valid signature using OrgA's own secret, but `repository.full_name`/`sha` referencing OrgB's stack/commit or an arbitrary sha not scoped to any repo), the handler mutates OrgB's (or any organization's) Shipit state, breaking the intended binding between "authenticated GitHub App organization" and "repository actually written."

This is the direct structural analogue of the JBToken finding: minting (an action normally gated by a specific controller-verified authority) is executed with no bound-checking against the amount/target actually being acted upon, once ownership/authority is transferred to an unrelated party. Here, the HMAC "ownership" check verifies against OrgA, but the mutation executes against a target selected by fields never covered by that specific authority-to-target binding.

### Impact Explanation
`StatusHandler` writing a forged, unscoped `success` CI status onto an arbitrary commit (identified only by SHA, guessable/leakable from public PRs/commits) can satisfy Shipit's deploy-gating CI checks for a stack the attacker does not otherwise control, potentially enabling an unauthorized deploy trigger once other gating conditions (e.g., merge, branch state) align. This crosses the required "unauthorized deploy" bar. It also constitutes a cross-repository/cross-organization write of Shipit's internal state (`Status`, `Commit`), matching the Critical-tier "cross-repository writes" criterion, since the write target is not bound to the organization that actually authenticated the webhook.

### Likelihood Explanation
Requires the host to run Shipit with the multi-organization GitHub App configuration (explicitly supported and documented, e.g., `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) and requires the attacker to be an admin/owner of at least one of the onboarded organizations (so they legitimately know that organization's own `webhook_secret`, which they configured themselves when registering their GitHub App). That party does not need any credential belonging to the *other* organization or repository being mutated. No `ApiClient` token, session, or GitHub App private key theft is needed - only knowledge of a secret the attacker's own org's administrator holds for their own onboarded org, and the code's failure to bind that org identity to the record being written.

### Recommendation
- In `WebhooksController`, after `verify_signature` succeeds, propagate the verified `repository_owner`/organization identity into the handler and require every handler to re-validate that the repository/commit/stack it is about to mutate actually belongs to that same verified organization (e.g., compare `Repository#owner` against the verified org before dispatch).
- In `StatusHandler`, scope the `Commit` lookup by repository (via the commit's stack's repository) and assert that repository's owner matches the verified webhook organization, instead of an unscoped `Commit.where(sha:)`.
- Reject/drop events where `repository.owner.login` (used to pick the verification secret) does not match `repository.full_name`'s owner segment.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `config/secrets.development.shopify.yml` schema), and a Shipit `Stack`/`Commit` belonging to `OrgB/some-repo`.
2. As an admin of `OrgA` (who legitimately knows OrgA's own `webhook_secret` because they configured their own GitHub App), craft a `status` event body:
   ```json
   { "sha": "<known-sha-of-OrgB-commit>", "state": "success", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"} }
   ```
3. Sign it with OrgA's `webhook_secret` (`X-Hub-Signature: sha1=<hmac>`), send to `WebhooksController#create`.
4. `verify_signature` succeeds because it only checks the signature against OrgA's secret (`repository_owner` resolves to `OrgA`), per `app/controllers/shipit/webhooks_controller.rb:24-49`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), which matches the OrgB commit regardless of the fact the signature only authenticated OrgA, and creates a forged status record on it.

**File:** lib/shipit.rb (L170-200)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
