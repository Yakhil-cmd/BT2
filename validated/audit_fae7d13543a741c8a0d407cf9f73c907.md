### Title
Malicious Bridge Operator Can Front-Run `deregisterOperator` to Drain Bridge KAIA/ERC20 Funds — (`contracts/service_chain/bridge/BridgeOperator.sol`)

### Summary

The `BridgeOperator.sol` `deregisterOperator` function is submitted as a regular on-chain transaction visible in the public mempool. A malicious operator who monitors the mempool can front-run the deregistration by calling `handleKLAYTransfer` (or `handleERC20Transfer`/`handleERC721Transfer`) with fabricated parameters before the deregistration lands, draining KAIA or ERC20 tokens from the bridge contract while still holding operator status.

### Finding Description

`BridgeOperator.sol` initialises `operatorThresholds[ValueTransfer] = 1` in its constructor, meaning a single operator can unilaterally execute any value-transfer handle call. The `handleKLAYTransfer` function in `BridgeTransferKLAY.sol` only requires:

1. `onlyOperators` — caller is in `operators` mapping.
2. `_lowerHandleNonceCheck` — `_requestedNonce >= lowerHandleNonce`.
3. `_voteValueTransfer` — `closedValueTransferVotes[nonce]` is false and vote count reaches threshold.

There is **no validation** that `_requestTxHash` corresponds to a real transaction on the counterpart chain. `_setHandledRequestTxHash` simply writes `handledRequestTx[hash] = true` without any prior existence check. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The `deregisterOperator` function itself is `onlyOwner` and is submitted as a normal transaction to the public mempool. A malicious operator who monitors the mempool can observe the pending deregistration and submit a `handleKLAYTransfer` call with a higher gas price (or simply earlier in the same block), executing it before the deregistration is mined.

The code comment in `deregisterOperator` explicitly acknowledges that outstanding votes by a deregistered operator are not revoked, but does not address the more severe front-running scenario where the operator actively exploits the mempool window: [5](#0-4) 

### Impact Explanation

With `operatorThresholds[ValueTransfer] = 1` (the default), a single operator can call `handleKLAYTransfer` with:
- An arbitrary `_requestTxHash` (any `bytes32` not yet in `closedValueTransferVotes`)
- `_to` set to an attacker-controlled address
- `_value` set to the full KAIA balance of the bridge contract
- Any unused `_requestedNonce >= lowerHandleNonce`

This causes `_to.call.value(_value)("")` to transfer the entire KAIA balance to the attacker. The same applies to `handleERC20Transfer` (minting or transferring ERC20 tokens) and `handleERC721Transfer`. The corrupted state is: `handledRequestTx[fabricatedHash] = true`, `closedValueTransferVotes[nonce] = true`, and the bridge's KAIA balance is zero — an irreversible unauthorized transfer of bridged assets.

### Likelihood Explanation

Medium. The attacker must:
1. Control a registered bridge operator key (semi-trusted role, not fully public).
2. Monitor the public mempool for a `deregisterOperator` transaction targeting their address.
3. Submit a front-running `handleKLAYTransfer` with higher gas priority before the deregistration is mined.

The service chain uses a public mempool, making step 2 straightforward with standard tooling. The operator key is already in the attacker's possession by definition of the scenario (the owner is removing them because they are malicious).

### Recommendation

1. **Atomic revocation**: When `deregisterOperator` is called, immediately clear all pending `votes` entries for that operator across all open nonces, or mark the operator's existing votes as invalid.
2. **Commit-reveal / timelock**: Require a timelock before a newly registered operator can execute transfers, and similarly freeze an operator's transfer ability the moment deregistration is initiated (two-phase deregistration).
3. **Private mempool**: Execute `deregisterOperator` through a private relay (e.g., Flashbots-equivalent) so the pending transaction is not visible to the operator being removed.
4. **Threshold enforcement at deregistration**: Automatically raise the effective threshold or pause the bridge when a deregistration is pending.

### Proof of Concept

```
Setup:
  - Bridge deployed on service chain with KAIA balance of 1000 KAIA (via chargeWithoutEvent)
  - operatorThresholds[ValueTransfer] = 1 (default)
  - Operator A is registered (operators[A] = true)

Attack:
  1. Owner discovers A is malicious; submits deregisterOperator(A) to the public mempool.
  2. A's monitoring script detects the pending deregisterOperator(A) transaction.
  3. A immediately submits (with higher gas):
       handleKLAYTransfer(
           _requestTxHash    = bytes32(0xdeadbeef...),  // fabricated, unused hash
           _from             = address(A),
           _to               = address(A),              // attacker-controlled
           _value            = 1000 ether,              // full bridge balance
           _requestedNonce   = lowerHandleNonce,        // any valid unused nonce
           _requestedBlockNumber = 1,
           _extraData        = ""
       )
  4. With threshold=1, _voteValueTransfer returns true immediately.
     closedValueTransferVotes[nonce] = true.
     _to.call.value(1000 ether)("") executes → 1000 KAIA sent to A.
  5. Owner's deregisterOperator(A) mines in the next slot.
     A is removed from operators[], but 1000 KAIA is already gone.

Result: Bridge KAIA balance = 0. Unauthorized transfer of 1000 KAIA to attacker.
        handledRequestTx[fabricatedHash] = true (fabricated request accepted as legitimate).

        internal
        returns(bool)

        require(!closedValueTransferVotes[_requestNonce], "closed vote");

    function deregisterOperator(address _operator)
    external
    onlyOwner
    {
        require(operators[_operator]);
        delete operators[_operator];

        for (uint i = 0; i < operatorList.length; i++) {
           if (operatorList[i] == _operator) {
               operatorList[i] = operatorList[operatorList.length-1];
               operatorList.length--;
               break;
           }
        }
        emit OperatorDeregistered(_operator);
    }
