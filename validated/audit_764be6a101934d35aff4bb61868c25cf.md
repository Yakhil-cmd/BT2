### Title
Webhook signature verification uses `repository.owner.login`/`organization.login` for GitHub App/secret selection while all handlers act on the unrelated `repository.full_name` field, allowing a cross-organization forged webhook to trigger unauthorized syncs on a victim's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate the request against solely by reading `repository.owner.login`, falling back to `organization.login`, from the *same* attacker-controlled JSON body it is trying to authenticate. Handlers, however, resolve the target `Stack`/`Repository` using a completely different field of that same payload: `repository.full_name` (via `Handler#repository_name` / `Repository.from_github_repo_name`). Nothing ties these two fields together, so in a multi-organization Shipit deployment (`Shipit.github_organizations`, `Shipit.github_app_config`), an attacker who legitimately controls one configured GitHub organization/App (org A) can forge a payload whose `repository.owner.login`/`organization.login` says "A" (so the signature check uses A's real, attacker-known `webhook_secret`) while `repository.full_name` names a repository belonging to a *different* configured organization/stack (victim org B). The HMAC signature is computed over the raw body which does contain both fields, but since the field used for secret *selection* is independent from the field used for repository *resolution*, a validly-signed-by-A payload can still name B's repository and drive B's stack.

### Finding Description
- `WebhooksController#verify_signature` chooses the `GitHubApp` instance to verify against using: 
`Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- `Shipit.github(organization:)` looks up the config keyed by that organization login and instantiates a `GitHubApp` with that organization's own `webhook_secret` from `secrets.github`. [3](#0-2) 
- `GitHubApp#verify_webhook_signature` HMACs the raw body against the secret belonging to whatever organization was selected in the previous step. [4](#0-3) 
- Once the signature check passes, `WebhooksController#create` dispatches to handlers using the raw parsed JSON, e.g. `PushHandler`. [5](#0-4) 
- Handlers resolve the affected `stacks`/`Repository` purely from `payload.dig('repository', 'full_name')`, an entirely separate field from the one used for secret selection. [6](#0-5) 
- `PushHandler` then triggers a real sync against whichever stacks match that `full_name`, regardless of which organization's secret validated the request. [7](#0-6) 

The broken equality is: **`organization used to select/verify the webhook secret` ≠ `repository whose stacks are written/synced`**. Nothing in `WebhooksController` or `Handler` enforces that the owner segment of `repository.full_name` matches `repository_owner`/`organization.login` used for authentication. In a single-organization deployment (`github_default_organization` is `nil`, the common/documented setup) this is not exploitable because there is only one `webhook_secret` for the whole instance, so any valid signature already authorizes any repository payload it (single config) covers - the field split doesn't matter. But in the explicitly supported multi-organization schema (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS` check in `github_default_organization`), each org has its own independent secret, and this split becomes a genuine authentication/authorization mismatch: possession of *org A's* valid webhook secret is sufficient to make Shipit act on *org B's* repository data in the same payload, because the field checked for authentication and the field checked for authorization are different and both attacker-supplied.

### Impact Explanation
An attacker who has legitimate write access to one configured GitHub organization/App integration (org A, e.g. their own org that happens to be configured in the same Shipit instance as other tenants) can craft and validly sign (using A's real webhook secret, which they can obtain legitimately by triggering real events from their own repo, or simply because they administer App A) a `push` webhook payload whose `repository.full_name` names a stack belonging to a different, victim organization (org B) tracked by the same Shipit instance. This is delivered to `WebhooksController#create`; signature verification succeeds (checked against A's secret because `repository_owner` resolves to A), and `PushHandler` proceeds to enqueue `GithubSyncJob` for the stacks matching the victim's `full_name`, with an attacker-chosen `expected_head_sha`. This lets an unprivileged-with-respect-to-org-B attacker force syncs (and therefore commit ingestion / potential deploy triggering depending on stack auto-deploy configuration) on org B's stack - an authorization boundary crossing (`Shipit.github_teams`/organization boundary) and a path toward unauthorized deploy activity on a repository the attacker does not control. This satisfies the High-impact bar: "escalation into `Shipit.github_teams` authorization" / cross-tenant stack manipulation without genuine authorization on the targeted repository.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit configuration (`secrets.github` keyed by multiple organization names, each with its own `webhook_secret`) - a supported, documented configuration path (`github_organizations`, `github_app_config`); and (2) the attacker controls at least one configured organization's GitHub App/webhook secret (i.e., is a legitimate, but unprivileged-w.r.t.-victim, tenant of the same Shipit instance). No GitHub App private key, `ApiClient` token, or Shipit session is needed - only the ability to deliver an HTTP POST with a valid HMAC computed with a secret the attacker already legitimately possesses for their own org. This is a realistic scenario for shared/multi-tenant Shipit deployments, which the codebase explicitly supports (`TOP_LEVEL_GH_KEYS`, `github_app_config`).

### Recommendation
Bind authentication and authorization to the same value. After signature verification succeeds using the organization derived from the payload, re-derive/validate that the repository whose stacks/handlers will be acted upon (`repository.full_name`'s owner segment) matches the same organization login used to select the webhook secret. Reject the webhook (422) if they diverge, rather than trusting `repository.full_name` from the handler layer as an independent, unauthenticated selector.

### Proof of Concept
1. Configure Shipit in multi-org mode with two organizations in `secrets.github`: `org-a` (attacker-controlled, secret known to attacker) and `org-b` (victim, tracked stack `org-b/victim-repo`).
2. Attacker crafts a JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-secret, raw_body)>` using org A's known secret.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#repository_owner` returns `"org-a"` → `Shipit.github(organization: "org-a")` → signature verifies successfully against org A's secret [1](#0-0) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` [8](#0-7)  and enqueues `GithubSyncJob` for org B's stack with the attacker-supplied `expected_head_sha`, despite the request never being authenticated by org B's secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
