### Title
Webhooks for orgs with no `webhook_secret` are trusted unconditionally, letting an unprivileged attacker forge a `pull_request`/`labeled` event that drives `LabeledHandler` to archive/unarchive an arbitrary review stack - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` short-circuits with `return true unless webhook_secret`, so any org configured without a `webhook_secret` accepts every webhook body unconditionally, with or without any `X-Hub-Signature` header. Combined with `pull_request`/`labeled`, this lets an attacker who only knows the org's login name make `LabeledHandler` archive or unarchive a targeted repository's review stack.

### Finding Description
The claimed broken binding: `verify_webhook_signature(signature, message)` should equal `HMAC-SHA256(webhook_secret, message) == signature` (an authenticated equality) for every accepted webhook; instead, for an org with no configured secret it is defined as `true` unconditionally, independent of `signature` or `message`.

Trace: `Shipit::WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner).verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [1](#0-0)  using `repository_owner`, which is read straight from attacker-controlled JSON (`params.dig('repository','owner','login')` or `params.dig('organization','login')`) [2](#0-1) . Inside `verify_webhook_signature`, the very first line is `return true unless webhook_secret`, which fires before the `signature.split("=", 2)` / `algorithm == 'sha1'` logic is ever reached [3](#0-2) . `webhook_secret` is `@config[:webhook_secret].presence`, set from the (optional) per-org config entry [4](#0-3) ; the shipped example configs explicitly show `webhook_secret:` left blank as a supported, documented state [5](#0-4) .

Consequently, the "legacy sha1 vs sha256" distinction the question frames is not actually the operative mechanism here: when `webhook_secret` is absent, the algorithm/signature branch is never evaluated at all - the attacker does not even need to send an `X-Hub-Signature` header, legacy or otherwise. The real root cause is simply that `verify_webhook_signature` treats "no secret configured" as "always verified," rather than "cannot be verified / must be rejected."

Exploit flow: an attacker crafts a POST to `/webhooks` with `X-Github-Event: pull_request` and a JSON body where `repository.owner.login` (or `organization.login`) matches the login of an org configured in `Shipit.github` without a `webhook_secret`, `action: "labeled"`, `pull_request.state: "open"`, and `repository.full_name` pointing at any real `Shipit::Repository` with `review_stacks_enabled` and provisioning-by-label configured. `verify_signature` passes unconditionally, `drop_unhandled_event`/`check_if_ping` do not block a `pull_request` event, and `Shipit::Webhooks.for_event('pull_request')` dispatches to `LabeledHandler` [6](#0-5) . `LabeledHandler#process` checks `respond_to_label_change?` (action, PR state, `review_stacks_enabled`, label logic) [7](#0-6)  and then calls `stack.archive!` or `stack.unarchive!` on the `ReviewStackAdapter` resolved from `repository.review_stacks` [8](#0-7) , based purely on label names supplied in the forged JSON body.

Existing guards do not stop this: `drop_unhandled_event` only screens event *types*, not authenticity; `ExplicitParameters` (the `params do ... end` block) validates shape, not provenance; there is no session/API-client/team check on this unauthenticated controller by design (it's meant for GitHub's servers). The only intended gate is `verify_signature`, and it is bypassed entirely once `webhook_secret` is unset for the org resolved from attacker-supplied JSON fields.

### Impact Explanation
Any repository belonging to an org whose `Shipit.github` entry has no `webhook_secret` is fully exposed to forged `pull_request` webhooks. For `LabeledHandler` specifically, the attacker can archive a review stack (silencing/hiding it, potentially disrupting an in-progress review/deploy gate) or unarchive one, without ever authenticating as GitHub, a Shipit user, or an API client. This matches the "forged webhook accepted as trusted" authentication-bypass category. The blast radius is scoped to whichever org(s) are configured without a secret - it does not, on its own, cross into other orgs' repositories, since `repository_owner` must still resolve to a `GitHubApp` config entry that exists (`GithubOrganizationUnknown` otherwise returns 422). The severity therefore depends entirely on whether the deployed Shipit instance actually has an org without `webhook_secret` configured.

### Likelihood Explanation
This requires a specific and non-default-safe operator misconfiguration: an org section in `Shipit.github` with `webhook_secret` blank/nil, which the repository's own example/dummy configs show as a valid, supported configuration shape [9](#0-8) . Given that precondition, the attack is trivial and free: a single unauthenticated HTTP POST with no signature header at all is sufficient, and it is fully repeatable against any repository under that org with review-stack labeling enabled. No GitHub secrets, private keys, or sessions are needed.

### Recommendation
Change `GitHubApp#verify_webhook_signature` so that a missing `webhook_secret` results in rejection (`return false unless webhook_secret`) rather than automatic acceptance, or require operators to configure a `webhook_secret` at boot/validation time and refuse to serve `/webhooks` for orgs missing one. Additionally, once a secret exists, support `X-Hub-Signature-256` and reject legacy `sha1`-only headers to close the separate downgrade concern.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative only per rules - not to be placed in `test/**` for this audit but to be handed to engineering):
1. Configure `Shipit.stubs(:github)` (or a real org entry) with `webhook_secret: nil` for org `"unsecured-org"`, and create a `Shipit::Repository` `full_name: "unsecured-org/demo"` with `review_stacks_enabled: true` and a review stack for an open PR.
2. POST to `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature` header, and JSON body: `action: "labeled"`, `pull_request.state: "open"`, `repository.owner.login: "unsecured-org"`, `repository.full_name: "unsecured-org/demo"`, `pull_request.labels: [{name: <provisioning label>}]`.
3. Assert response is `200`/`ok` (not `422`), and assert `stack.reload.archived?` (or `unarchived?`) flips as dictated by the forged label, proving `LabeledHandler` executed a state change from an unauthenticated request.
4. Repeat with `X-Hub-Signature: "sha1=deadbeef"` present (still no real secret) to show the header content is irrelevant - `verify_webhook_signature` returns `true` at line 77 before ever parsing it, confirming the root cause is "no secret ⇒ unconditional trust," not merely the sha1/sha256 header choice claimed in the question.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
