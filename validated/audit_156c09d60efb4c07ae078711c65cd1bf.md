### Title
Unchecked division by zero in `token_price_x32` causes permanent denial-of-service on swaps after full pool drain - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`PoolState::token_price_x32` performs raw, unchecked `u128` division (`/`) instead of `checked_div`, using live vault balances as the divisor. This function is invoked on every `swap_base_input` and `swap_base_output` call via `get_swap_params`. If either vault balance is ever driven to zero, every subsequent swap transaction will panic instead of returning a graceful Anchor error, permanently bricking the pool's swap functionality.

### Finding Description
`token_price_x32` computes the token price ratio using plain division operators, unlike almost every other arithmetic operation in the codebase which uses `checked_*` and gracefully maps failures to Anchor errors: [1](#0-0) 

This function is called unconditionally on every swap through `get_swap_params`: [2](#0-1) 

`swap_base_input` and `swap_base_output` both call `pool_state.get_swap_params(...)` before any curve math, meaning this division executes on every single swap instruction: [3](#0-2) [4](#0-3) 

`withdraw` places no lower bound on how much liquidity can be removed beyond requiring `lp_token_amount > 0` and that the computed trading-token amounts are non-zero; it does not prevent `lp_supply` (and therefore the vault balances) from being reduced all the way to zero if a single account controls the entire LP supply: [5](#0-4) [6](#0-5) 

Once a vault balance for either token reaches exactly zero (e.g., after the sole LP holder withdraws 100% of the supply, which yields an exact proportional `token_0_amount`/`token_1_amount` equal to the full vault balance with `RoundDirection::Floor`), `vault_amount_without_fee` returns `(0, y)` or `(x, 0)`, and the subsequent raw division `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` (or the symmetric expression) divides by zero. In the Solana BPF runtime this causes an unconditional program panic/abort for every future swap attempt against that pool, since the panic occurs before any of the `checked_*` guarded curve logic runs.

I was not able to fully verify from the indexed code whether `initialize.rs` enforces a permanent minimum-liquidity lock (a common AMM safeguard that would prevent `lp_supply`/vault balances from ever reaching exactly zero). If such a lock exists and is unconditionally enforced, this specific zero-vault trigger path would not be reachable; this should be confirmed by inspecting `programs/cp-swap/src/instructions/initialize.rs`.

### Impact Explanation
If a vault balance can reach zero through normal liquidity operations, this bug permanently disables swapping for that pool: every future `swap_base_input`/`swap_base_output` transaction will abort due to the unchecked division, regardless of pool status flags. This is a persistent availability failure affecting any user attempting to swap, matching the "permanent freezing of user or LP funds"-class impact (funds already in flight or newly deposited into vaults become effectively untradeable, since swaps can never succeed again for that pool). It is a direct structural analog to CVE-2020-27750's class of bug (unchecked division producing undefined/aborting behavior on attacker-influenced input), just realized in Rust as a panic-based indefinite denial of service instead of C undefined behavior.

### Likelihood Explanation
Reaching this state requires that a vault balance actually become exactly zero, which is only possible if `withdraw` allows full liquidity extraction (no enforced minimum-liquidity floor was found in `withdraw.rs`). This is a plausible but not fully proven precondition, since I could not confirm the contents of `initialize.rs` regarding a burned/locked minimum-liquidity safeguard. Assuming no such safeguard prevents full drain by the sole LP, likelihood is high for pools with a single dominant LP (common for smaller/newer pools) and low/impossible for pools where a permanent liquidity lock is enforced at initialization.

### Recommendation
- Replace the raw division in `token_price_x32` with `checked_div` and return `ErrorCode::MathOverflow` (or similar) on `None`, consistent with the rest of the codebase's arithmetic handling, so that a degenerate zero-balance case fails gracefully rather than panicking.
- Independently, verify (and if absent, add) a permanent minimum-liquidity lock in `initialize`/`initialize_with_permission` and/or a floor check in `withdraw` that prevents `lp_supply` or either vault balance from reaching exactly zero, to eliminate the root precondition entirely.

### Proof of Concept
1. Pool is initialized normally with token_0 and token_1 liquidity, and the caller ends up holding 100% of the LP token supply (no third-party enforced lock, if `initialize.rs` does not burn/lock a minimum amount).
2. The LP holder calls `withdraw` with `lp_token_amount == pool_state.lp_supply` (their full balance). Because `lp_tokens_to_trading_tokens` with `RoundDirection::Floor` computes `token_0_amount = lp_token_amount * total_token_0_amount / lp_supply`, withdrawing 100% of supply yields `token_0_amount == total_token_0_amount` and `token_1_amount == total_token_1_amount` exactly — draining both vaults to zero: [7](#0-6) 
3. Any subsequent call to `swap_base_input` or `swap_base_output` on this pool invokes `pool_state.get_swap_params(...)` → `token_price_x32(0, 0)` (or `(x, 0)`/`(0, y)` if only one side was drained), triggering `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` with a zero divisor, panicking the transaction and permanently preventing all future swaps against the pool.
