## Title
Webhook signature verified against organization from an unverified payload field while handlers act on a different, unverified repository field — allows cross-organization forged webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) directly out of the *unverified* raw JSON body, before the signature has been checked. Every downstream `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the target `Repository`/`Stack` using a completely different, equally unverified field: `payload.dig('repository', 'full_name')`. Because these two independent JSON fields are never cross-validated against each other, an attacker who legitimately controls (knows) the `webhook_secret` for one configured GitHub organization can forge a webhook whose `repository.owner.login` names that organization (so the signature check passes) while `repository.full_name` names a repository belonging to a *different* organization configured on the same Shipit instance.

### Finding Description [1](#0-0) 
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is [2](#0-1) 
`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

This is the *only* binding enforced: "the org named in the payload" must match "the org whose secret produced a valid HMAC over the whole raw body." Multi-org Shipit deployments configure a distinct `webhook_secret` per GitHub organization, as documented in `docs/setup.md` (lines 182-209) and `config/secrets.development.example.yml`.

But every handler ignores `repository.owner.login` entirely and instead resolves the target repository from a sibling field: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`Repository.from_github_repo_name` splits `"owner/name"` and looks up any repository/stack Shipit tracks for that owner — independent of which org's secret verified the request: [4](#0-3) 

Since an attacker fully controls the raw JSON body they submit (only the signature must match), they can set `repository.owner.login = "OrgA"` (an org whose secret they know) while setting `repository.full_name = "OrgB/some-tracked-repo"` (a different org's repository that Shipit also tracks). `verify_signature` authenticates the request as belonging to OrgA and passes it through; every handler then acts on OrgB's repository/stack, e.g. `PushHandler#process` calling `stack.sync_github` [5](#0-4)  or the pull-request handlers archiving/unarchiving `ReviewStack`s [6](#0-5) . This is exactly the "organization that authenticated versus the repository that is written" binding: `repository_owner (authenticated) == repository.full_name's owner (acted upon)` is assumed but never enforced.

### Impact Explanation
This crosses an organizational trust boundary that Shipit's multi-org design is meant to enforce: possession of one organization's webhook secret should only authorize actions on that organization's repositories. Instead an attacker who knows OrgA's `webhook_secret` (e.g., because they administer or can observe webhook deliveries/secrets for their own onboarded org) can drive Shipit-side state changes for any other tracked organization's repository — forcing resyncs, and, via PR event handlers, archiving/unarchiving `ReviewStack`s (which provision/deprovision real infrastructure per `docs/setup.md`'s Kubernetes/Heroku sections) for repositories they have no authorization over. This is a cross-repository/cross-organization write achieved purely by forging a payload field that is never bound to the credential that authenticated it.

### Likelihood Explanation
Exploitation only requires the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint plus a valid `webhook_secret` for *any one* organization configured on the shared Shipit instance — no GitHub write access to the target organization/repository, no Shipit session, and no `ApiClient` token are required. Multi-organization configuration is a documented, supported deployment mode (`docs/setup.md` lines 182-209), so this is a realistic operating condition, not a contrived setup.

### Recommendation
In `WebhooksController#verify_signature`, after verifying the signature, additionally assert that the organization derived from `repository.full_name`'s owner segment (or `organization.login`) matches the `repository_owner` used to select the verifying secret, and reject the request otherwise. Alternatively, have every `Handler` resolve the repository/organization solely from the same field that was cryptographically verified, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config), each tracking at least one repository/stack.
2. Attacker knows `OrgA`'s `webhook_secret` (e.g., they are a legitimate webhook sender for OrgA) but has no access to `OrgB`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist on OrgB's tracked branch>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/tracked-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature against `OrgA`'s secret [1](#0-0) .
6. `PushHandler` resolves the target stack via `repository.full_name = "OrgB/tracked-repo"` [3](#0-2)  and triggers `stack.sync_github` for `OrgB`'s stack, despite the attacker never having been authenticated for `OrgB`.
