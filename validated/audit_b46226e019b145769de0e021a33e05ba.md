### Title
Missing bridge-pause invariant check in `claim_token_internal` allows claims (minting) while the bridge is emergency-paused - ([File: crates/sui-framework/packages/bridge/sources/bridge.move])

### Summary
The external ibc-solidity report describes a state-machine invariant (the `STATE_FLUSHING` counterparty-upgrade-timeout check) that is enforced in some channel-packet code paths but missing in others (`acknowledgePacket`, `timeoutPacket`), letting protected state transitions slip through unprotected entry points. The same *class* of bug — a state guard enforced inconsistently across parallel entry points of the same subsystem — appears in Sui's native bridge Move module.

### Finding Description
`bridge::bridge` maintains a single `paused: bool` flag on `BridgeInner` that is meant to gate all bridge state-mutating operations when the committee freezes the bridge via `execute_emergency_op` [1](#0-0) .

This guard is explicitly enforced in the outbound path, `send_token_internal`: [2](#0-1) 

It is also enforced in the approval path, `approve_token_transfer`: [3](#0-2) 

However, in the claim path (`claim_token_internal`, invoked by both `claim_token` and `claim_and_transfer_token`) the visible logic — which checks `record.claimed`, target chain, route validity, token type, and the rate limiter, then mints from treasury and marks the record claimed — contains no `assert!(!inner.paused, ...)` guard anywhere in the flow I was able to inspect: [4](#0-3) 

The public entrypoints that call into this function likewise show no pause check before delegating: [5](#0-4) 

I was not able to view the very start of `claim_token_internal` (the portion before line 560) in this session, so I cannot rule out with 100% certainty that a pause check exists earlier in the function body that I did not retrieve. This is a limitation of the indexed context available to me, not a confirmed absence — a full read of the function (and a search for every call site / `EBridgeUnavailable` usage) is necessary to conclusively confirm the gap.

### Impact Explanation
If `claim_token_internal` genuinely lacks the pause check that `send_token_internal` and `approve_token_transfer` both enforce, then freezing the bridge via the emergency-pause governance action would not stop already-approved token transfers from being claimed (minted from `BridgeTreasury`). This is precisely the scenario the pause mechanism exists to prevent — halting mint/burn activity during a security incident (e.g., a compromised or malicious set of committee signatures having already produced approved-but-unclaimed records, or a limiter/committee bug discovered post-approval). Unauthorized minting via a bypassed emergency freeze falls under the "bridge governance or upgrade bypass that enables illegitimate mint" Critical impact category.

### Likelihood Explanation
This can only be exploited by a normal, unprivileged claimant for a record that was already approved (has `verified_signatures`) before or during the pause — the attacker does not need any privileged role. Reachability requires that a transfer record be in the "approved" state at the moment of a freeze, which is a realistic operational scenario (freezes are typically issued *because* something suspicious was already approved).

### Recommendation
Add `assert!(!inner.paused, EBridgeUnavailable);` at the top of `claim_token_internal`, mirroring the guard present in `send_token_internal` and `approve_token_transfer`, so that the pause invariant is enforced uniformly across every bridge state-mutating entrypoint. As a broader remediation, audit all functions on `BridgeInner`/`Bridge` for consistent enforcement of `paused`, exactly as the external report recommends re-auditing every `STATE_FLUSHING` code path in ibc-solidity.

### Proof of Concept
Conceptual sequence (pending confirmation of the missing check via full source review):
1. Committee approves a token transfer via `approve_token_transfer`, storing a `BridgeRecord` with `verified_signatures = some(...)`.
2. Committee detects an issue and freezes the bridge with `execute_system_message`/`execute_emergency_op` (`paused = true`).
3. Attacker (the intended recipient or any caller via `claim_and_transfer_token`) calls `claim_token`/`claim_and_transfer_token` for the already-approved record.
4. Because `claim_token_internal` has no `assert!(!inner.paused, ...)`, the call proceeds past all other checks, mints the token from `BridgeTreasury`, and marks the record claimed — despite the bridge being frozen.

**Caveat:** This finding is based on partial visibility into `claim_token_internal`'s source (lines 560–608 only); the function's preceding lines were not retrievable in this session. Before treating this as a confirmed vulnerability, the full function body and all call sites of `EBridgeUnavailable`/`inner.paused` in `bridge.move` should be reviewed to conclusively verify the guard is absent.

public fun claim_token<T>(
    bridge: &mut Bridge,
    clock: &Clock,
    source_chain: u8,
    bridge_seq_num: u64,
    ctx: &mut TxContext,
): Coin<T> {
    let (maybe_token, owner) = bridge.claim_token_internal<T>(
        clock,
        source_chain,
        bridge_seq_num,
        ctx,
    );
    // Only token owner can claim the token
    assert!(ctx.sender() == owner, EUnauthorisedClaim);
    assert!(maybe_token.is_some(), ETokenAlreadyClaimedOrHitLimit);
    maybe_token.destroy_some()
}

// This function can be called by anyone to claim and transfer the token to the recipient
// If the token has already been claimed or hits limiter currently, it will return instead of aborting.
public fun claim_and_transfer_token<T>(
    bridge: &mut Bridge,
    clock: &Clock,
    source_chain: u8,
    bridge_seq_num: u64,
    ctx: &mut TxContext,
) {
    let (token, owner) = bridge.claim_token_internal<T>(clock, source_chain, bridge_seq_num, ctx);
    if (token.is_some()) {
        transfer::public_transfer(token.destroy_some(), owner)
    } else {
        token.destroy_none();
    };
}

fun execute_emergency_op(inner: &mut BridgeInner, payload: EmergencyOp) {
    let op = payload.emergency_op_type();
    if (op == message::emergency_op_pause()) {
        assert!(!inner.paused, EBridgeAlreadyPaused);
        inner.paused = true;
        event::emit(EmergencyOpEvent { frozen: true });
    } else if (op == message::emergency_op_unpause()) {
        assert!(inner.paused, EBridgeNotPaused);
        inner.paused = false;
        event::emit(EmergencyOpEvent { frozen: false });
    } else {
        abort EUnexpectedOperation
    };
}
