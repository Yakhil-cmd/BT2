Based on my research, the strongest analog to the Ledger bug class here is a signature/identity-binding break in `WebhooksController`: the GitHub organization used to select (and verify) the webhook signature is taken from the same untrusted JSON payload as the organization/repository the webhook subsequently mutates, and these two fields are never cross-checked.

### Title
Webhook signature verification keys off an attacker-controlled `repository_owner`/`organization` field that is never bound to the org/repo actually mutated by the handler - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify against using `repository_owner`, a value read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login') || params.dig('organization','login')`). The very same request body is later handed, unmodified, to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, whose handlers act on whatever organization/repository/team names appear elsewhere in that body. Nothing ties the "authenticating" org field to the "acted upon" org/repo fields, so in a multi-org configuration a payload can be signed against one org's (possibly secret-less) app while its side effects target a different org's stack or team membership.

### Finding Description [1](#0-0) 
`verify_signature` computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)` to obtain that org's `webhook_secret` for HMAC verification: [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly trusts the request when no secret is configured for that org: `return true unless webhook_secret`. [3](#0-2) 

Multi-org configuration is a documented, supported deployment mode where different organizations can have independently-configured (and independently optional) `webhook_secret`s: [4](#0-3) 

Once `verify_signature` passes (trivially, if the org picked via the attacker-controlled `repository_owner` field has no secret configured), the full unauthenticated `params` hash — including `repository.full_name`, `organization.login`, `member.login`, `team` fields, etc. — is dispatched to the real handlers, which perform writes such as creating/removing `Membership` records for any team on any configured org: [5](#0-4) 

The `repository_owner` value used for signature selection and the `organization`/`repository` values used by the handler for mutation both come from the same untrusted body and are never required to match. This is the direct analog of the Ledger `pluginContext` bug: a shared, attacker-influenced piece of state (here, "which org's trust context applies") is not correctly re-derived/isolated per logical operation, so state established for one context (org A's verification) leaks into and authorizes actions in a different context (org B's data).

### Impact Explanation
If any organization configured on the Shipit instance has no `webhook_secret` set (an explicitly documented, supported option), an unauthenticated attacker can craft a webhook whose `repository.owner.login`/`organization.login` names that secret-less org (satisfying `verify_signature`) while embedding a different org's/repo's identifiers elsewhere in the payload for the handler to act on. Concretely, a forged `membership` event can add the attacker to any `Team`, and `User.authorized?` grants access whenever a user belongs to any team in `Shipit.github_teams`: [6](#0-5) 
This is a direct escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes — and can also be used to spoof `push`/`status`/`check_suite` events against stacks belonging to organizations other than the one whose (absent) secret was checked.

### Likelihood Explanation
Requires only that the deployment run more than one configured GitHub organization and that at least one of them has no `webhook_secret` configured — a state the setup docs present as optional/acceptable rather than forbidden. No GitHub credentials, API tokens, repository write access, or knowledge of any secret are required from the attacker; only network access to the public `/webhooks` endpoint.

### Recommendation
After selecting the GitHub App/secret via `repository_owner`, verify that the same organization value is consistent with every organization/repository identifier referenced elsewhere in the payload before dispatching to handlers, and refuse (or clearly scope) processing when they disagree. Consider also disallowing per-org "no secret" configurations when multiple orgs are configured, or requiring a global fallback secret so that signature verification can never trivially succeed for an attacker-chosen `repository_owner`.

### Proof of Concept
1. Configure Shipit with two orgs: `OrgA` (no `webhook_secret`) and `OrgB` (has a stack whose team is in `Shipit.github_teams`, `webhook_secret` set).
2. POST to `/webhooks` with header `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "organization": { "login": "OrgA" },
  "team": { "id": 1, "name": "OrgB Team", "slug": "orgb-team", "url": "https://example.com" },
  "member": { "login": "attacker" }
}
```
3. `repository_owner` resolves to `OrgA`; `verify_webhook_signature` returns `true` unconditionally because `OrgA` has no secret.
4. The `membership` handler processes the payload, creating/associating the `attacker` user with the referenced team, regardless of which org's secret was actually checked, per the behavior demonstrated in [5](#0-4) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
