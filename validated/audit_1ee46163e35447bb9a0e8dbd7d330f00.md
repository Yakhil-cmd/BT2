### Title
StatusHandler resolves commits by SHA only, across all repositories/stacks, enabling forged CI status injection and unauthorized merges - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no scoping to the repository whose webhook signature was verified, unlike `CheckSuiteHandler` and `PushHandler`, which scope through the `stacks` helper (`Repository.from_github_repo_name(repository_name)`). Because a forked repository can share identical commit SHAs with its upstream, an attacker who owns a fork of `victim/repo` can send a legitimately-signed `status` webhook from their own fork and have it applied to the victim's `Commit` record, forging a `success` status on a queued merge request's head commit.

### Finding Description
The broken binding is: the repository whose `webhook_secret` verified the incoming status payload (`repository_owner` derived from `payload.dig('repository','owner','login')`, checked in `WebhooksController#verify_signature`, app/controllers/shipit/webhooks_controller.rb:24-30) must equal `merge_request.stack.repository` (the victim repo owning the `Commit` being mutated). This binding is violated because `StatusHandler#process` never checks `repository_name`/`stacks` at all: [1](#0-0) 

Compare to the pattern used by other handlers that correctly scope by the verified repository via the shared `Handler#stacks` helper: [2](#0-1) [3](#0-2) [4](#0-3) 

`StatusHandler` instead queries `Commit` globally by `sha` alone and calls `create_status_from_github!` on every matching row, regardless of which repository/stack it belongs to: [5](#0-4) 

Root cause: `Commit` records are only unique per `(stack_id, sha)` (see the dedicated index migration `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally unique per `sha`. So the same content SHA can legitimately exist as separate `Commit` rows in two different stacks (e.g., victim's stack and an unrelated attacker-owned stack tracking the attacker's fork, if the attacker's fork/repo is itself onboarded to Shipit or otherwise has a `Commit` row created, such as via `find_or_create_commit_from_github_by_sha!` when the attacker opens a PR referencing that fork). `WebhooksController#verify_signature` only proves the sender controls the org/app secret for the repository *named in the payload* — it says nothing about which `Commit` rows get mutated, and `StatusHandler` performs no additional check that the sha belongs to that named repository's stack.

Exploit flow:
1. Attacker forks `victim/repo`, so a PR's head commit has an identical git SHA in both the fork and `victim/repo` (same tree/parent/message/timestamps content-address the same).
2. A merge request for that PR sits `pending` in `victim/repo`'s merge queue (`merge_queue_enabled`), with `merge_request.head` pointing at the `Commit(sha: X, stack: victim_stack)`.
3. Attacker sends a `status` webhook whose `repository` claims their own repo (so `verify_webhook_signature` passes using their own installation's secret) and whose `sha` is `X`.
4. `StatusHandler#process` runs `Commit.where(sha: 'X')`, which matches the victim's `Commit` row (and any other stack's row with that sha) irrespective of repository, and calls `create_status_from_github!(params)` on it, creating a `success` `Status` record on `victim_stack`.
5. `MergeRequest::StatusChecker#success?` (via `all_status_checks_passed?`, app/models/shipit/merge_request.rb:193-197) becomes `true`.
6. `ProcessMergeRequestsJob#perform` runs `reject_unless_mergeable!` (app/models/shipit/merge_request.rb:155-162), which does not reject on a forged-success state, then calls `merge_request.merge!` (app/jobs/shipit/process_merge_requests_job.rb:21-26), merging the PR into `victim/repo`'s default branch.

### Impact Explanation
This allows an unauthorized merge of a pull request into `victim/repo`'s protected/default branch, driven entirely by a webhook the attacker legitimately signs for their own unrelated repository. This matches "Critical: a payload for one repository mutating another's stack/commit/task, or an unauthorized merge." Any Shipit-managed stack with `merge_queue_enabled` and any required CI/status checks is exposed; the attacker needs only to be able to fork the target repo and control any repository (their own) onboarded/known to Shipit whose `Commit` row can coincidentally or intentionally share a SHA with the victim's PR head. The blast radius spans all stacks sharing the Shipit instance's webhook endpoint, since the vulnerable lookup is completely repository-agnostic.

### Likelihood Explanation
Preconditions: `merge_queue_enabled` on the victim stack; the target `Commit` must already exist as a row tied to two different stacks with the same `sha` (achievable because forked repos naturally share commit SHAs for identical content, and Shipit creates `Commit` rows for PR heads/bases via `find_or_create_commit_from_github_by_sha!` for any stack tracking a repo, including the attacker's own onboarded fork/stack). The attacker needs a Shipit-registered stack/repo they control (or any repo whose GitHub App installation they can trigger a status webhook from) — no privileged Shipit role, session, or secret is required beyond the ordinary GitHub webhook signing that GitHub itself performs for the attacker's own repository. This is repeatable against any repository/stack on the instance.

### Recommendation
Scope `StatusHandler#process` to the repository that was actually verified, mirroring `CheckSuiteHandler`/`PushHandler`: resolve `stacks` from `payload.dig('repository','full_name')` first, then only update `Commit` rows belonging to those stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring a status can never be attached to a `Commit` outside the repository that signed the webhook.

### Proof of Concept
Minitest plan (no live GitHub, using existing `GithubHook.any_instance.stubs(:verify_signature).returns(true)` pattern seen in `test/controllers/webhooks_controller_test.rb`):
1. Create `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/fork`), each with a `Commit` sharing the same `sha` value (`shared_sha`).
2. Create a `MergeRequest` on `victim_stack` with `merge_status: 'pending'`, `head` pointing to `victim_stack`'s `Commit(sha: shared_sha)`.
3. Assert baseline: `merge_request.all_status_checks_passed?` is `false` (no statuses yet), establishing the equality check `merge_request.stack.repository == victim_stack.repository` and that no status yet exists.
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: shared_sha, state: 'success', context: 'ci/attacker', repository: { full_name: 'attacker/fork', owner: { login: 'attacker' } } }`, with `verify_signature` stubbed as verifying only against the payload's own claimed repo/org (i.e. do not stub globally — stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return true).
5. Assert `victim_stack.commits.find_by(sha: shared_sha).statuses.count` increased and its state is `success`.
6. Reload `merge_request` and assert `merge_request.all_status_checks_passed?` is now `true`, and `merge_request.reject_unless_mergeable!` returns `false` (not rejected).
7. Stub `stack.github_api.merge_pull_request` and assert `merge_request.merge!` is invoked/succeeds without any interaction from `victim/repo`'s own webhook secret — demonstrating the equality `repository_that_verified_webhook == merge_request.stack.repository` is false while the merge still proceeds.
