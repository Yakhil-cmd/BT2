Confirmed: `Handler` base class provides a `stacks` helper that scopes lookups to the repository named in the webhook payload (`Repository.from_github_repo_name(repository_name)&.stacks`) [1](#0-0) , and `CheckSuiteHandler` correctly uses this scoped `stacks` before touching commits [2](#0-1) . `StatusHandler`, however, bypasses that scoping entirely and queries `Commit` globally by `sha` [3](#0-2) .

### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` applies a GitHub `status` webhook to every `Commit` row in the database whose `sha` matches the payload, instead of restricting the update to commits that belong to the stack(s) of the repository that actually sent (and cryptographically signed) the webhook. This breaks the binding "organization/repo authenticated by the webhook signature == repository whose commit state is written," letting a webhook that is legitimately signed for repository/organization A modify CI/status state for a commit belonging to an entirely different stack/repository B, as long as the two commits share a `sha`.

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook only against the organization derived from the payload's own `repository.owner.login` (or `organization.login`), using that organization's `webhook_secret` [4](#0-3) . This proves the request came from GitHub for *that* repository/organization — it says nothing about any other repository in the Shipit installation.

Every other event handler correctly narrows further work to the sending repository by using `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records, e.g. `CheckSuiteHandler` [2](#0-1)  and `PushHandler` [5](#0-4) .

`StatusHandler` does not use `stacks`/repository scoping at all. It looks up `Commit.where(sha: params.sha)` across the *entire* `commits` table (every stack, every repository, every organization configured in the Shipit instance) and calls `create_status_from_github!` on each match [3](#0-2) . `Commit#create_status_from_github!` records the status and, through `add_status`, can flip the commit's simple state and even trigger `stack.schedule_merges` for the *unrelated* stack that happens to own the colliding `sha` [6](#0-5) .

Because git object hashes are pure functions of content (tree, parents, author/committer identity and timestamps, message), an attacker who controls a *different* repository that is independently connected to the same Shipit instance (any org/repo with its own valid `webhook_secret`, a normal, unprivileged integration — not the target stack's secret) can construct a commit object in their own repository whose SHA-1 is identical to a target commit's SHA-1 in a different organization's stack (by reproducing the exact tree and commit metadata of a commit they can observe, e.g. via the target's public GitHub history). They then push a `status` event for that sha (e.g., `context: "ci/required-check"`, `state: "success"`) from their own repository. The signature check succeeds (it is a genuine signed webhook for the attacker's own org), but `StatusHandler` applies the resulting status to the victim stack's commit as well, satisfying merge-queue/deploy CI gating (`required_statuses` in `DeploySpec`/`StatusChecker`) for a commit the attacker never had rights over.

### Impact Explanation
This breaks the equality "organization authenticated by the verified webhook signature == repository/stack whose commit-status/CI gate is written," letting an attacker holding only a legitimate but unrelated GitHub App/webhook credential forge a passing CI status on a target stack. If that stack has `merge.require`/`ci.require` statuses configured, `ProcessMergeRequestsJob`/`MergeRequest#all_status_checks_passed?` can be satisfied by the forged status, resulting in an unauthorized merge (`MergeRequest#merge!`) or unblocking of an unauthorized deploy — matching the Critical "unauthorized deploy, rollback, or merge" impact category.

### Likelihood Explanation
Exploitation requires (a) access to some repository whose webhook is registered with this Shipit instance (a normal, low-privilege integration point, not the victim's secret — satisfying the "unprivileged attacker" requirement) and (b) the ability to construct a commit object with a target sha, which is feasible when the attacker can view/clone the target's public commit (reproducing tree + metadata to get an identical SHA-1 is a known, demonstrated technique, not a cryptographic break of SHA-1 itself). Given multiple orgs can share one Shipit install ("Using Multiple Github Applications", docs/setup.md), and stacks with required CI checks are common, the likelihood is Medium.

### Recommendation
Scope `StatusHandler#process` to the sending repository the same way other handlers do, e.g. restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (using the inherited `stacks` helper based on `repository.full_name`), instead of querying `Commit` globally by `sha` alone.

### Proof of Concept
1. Attacker registers/controls Repo B in Org B, which has its own valid Shipit webhook (`webhook_secret_B`), fully legitimate and unrelated to the victim Stack A in Org A.
2. Attacker observes a commit `C` in Stack A's repository (tree, author, committer, timestamps, message — all public in a public repo) that is pending a required CI status (e.g., `context: "ci/required"`).
3. Attacker crafts an identical commit object (same tree/parents/author/committer/timestamps/message) inside Repo B via `git commit-tree`, producing the same SHA-1 as `C`.
4. Attacker triggers a `status` webhook from Repo B/Org B (e.g., by posting a real commit status via the GitHub API on that commit in Repo B) with `state: "success"`, `context: "ci/required"`, `sha: <C's sha>`.
5. `WebhooksController#verify_signature` validates the signature using Org B's `webhook_secret` — verification succeeds because it is a genuine webhook for Org B.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches commit `C` in Stack A (Org A), and calls `create_status_from_github!`, recording a forged "success" status on `C`.
7. If `C` is the head of a pending merge request or deploy in Stack A, `all_status_checks_passed?`/`ProcessMergeRequestsJob` can now consider Stack A's required checks satisfied, leading to an unauthorized merge or deploy in Org A triggered entirely from Org B's webhook.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
