Found a strong analog: the merge queue's "is this PR safe to merge" decision (`MergeRequest#all_status_checks_passed?` / `any_status_checks_missing?` / `any_status_checks_failed?`) is evaluated using `stack.cached_deploy_spec`'s `merge_request_required_statuses`/`merge_request_ignored_statuses` — a spec cached from a **different commit** (the branch's `commits.reachable.last` at cache time) than the PR's own `head` commit that is actually merged and later deployed. This breaks the binding: *ref approved (using `stack.cached_deploy_spec`'s required-statuses list) == ref whose `shipit.yml` steps/requirements actually govern the commit being merged/deployed (the PR head's own file)*.

### Title
Merge-queue status requirements are evaluated against a stale `cached_deploy_spec` instead of the PR head's own `shipit.yml`, allowing required-status bypass on merge - ([File: app/models/shipit/merge_request.rb])

### Summary
`MergeRequest#all_status_checks_passed?`, `#any_status_checks_missing?`, and `#any_status_checks_failed?` build a `StatusChecker` using `stack.cached_deploy_spec` [1](#0-0)  rather than the `shipit.yml` contained in the pull request's own `head` commit. `stack.cached_deploy_spec` is populated asynchronously by `CacheDeploySpecJob`, which checks out `stack.commits.reachable.last` — the tip of the tracked branch at cache time — not the PR's `head` [2](#0-1) .

### Finding Description
`StatusChecker#required_statuses` / `#ignored_statuses` read `deploy_spec.merge_request_required_statuses` / `merge_request_ignored_statuses` [3](#0-2) , and the `deploy_spec` passed in every call site is always `stack.cached_deploy_spec` [1](#0-0) , the branch-tip's cached spec, not the PR head commit's own `shipit.yml`. Any contributor able to open a pull request (no write access needed) controls the content of `shipit.yml` on their PR branch/head commit. Meanwhile the gate used by `reject_unless_mergeable!` to decide whether that PR is safe to auto-merge is driven entirely by the tracked branch's cached spec [4](#0-3) . This creates exactly the CometBFT-style mismatch: the entity whose "vote" (required CI statuses) is checked (branch tip's spec) differs from the entity actually being merged and later executed for deploy steps (the PR head commit, whose own `shipit.yml` is what will govern the resulting merge commit once it becomes the new branch tip and is deployed).

Concretely, if the target branch's `shipit.yml` currently defines a narrow `merge.require` list (or none), the merge queue will happily merge a PR whose head commit rewrote `shipit.yml`'s deploy section to add dangerous `deploy.override` steps, `machine.environment` keys, or to shrink `required_statuses`/`blocking_statuses` for the *next* evaluation, because the current gate never inspected the PR head's own file — only the previously-cached one from the branch tip. Once merged, this commit becomes the new head; `CacheDeploySpecJob` will eventually re-cache from it, but only after the merge has already happened, and any deploy of that merge commit executes the steps that were embedded in that specific commit's tree via `TaskCommands#deploy_spec` (`DeploySpec::FileSystem.new(@task.working_directory, @stack)` checked out to that commit) [5](#0-4) , i.e. the attacker-controlled file.

### Impact Explanation
This allows an unprivileged contributor (PR author only, no repo write access) to smuggle modified `shipit.yml` deploy steps or weakened CI requirements past the merge gate into the protected branch, and subsequently have those steps executed by Shipit with the app's `GITHUB_TOKEN`/deploy credentials once the commit is picked for deployment — an unauthorized merge/deploy path and potential RCE on the deploy host via injected deploy steps.

### Likelihood Explanation
Requires only PR-authoring ability plus knowledge of Shipit's merge-queue caching behavior (fully documented in `CHANGELOG.md`/README as a caching optimization, not a security boundary), and the race window is inherent to how `cached_deploy_spec` is refreshed asynchronously and lazily (`spec_cache_target` skip-if-unchanged logic in `GithubSyncJob`) [6](#0-5) , making it a systemic, reliably reachable design gap rather than a narrow race.

### Recommendation
Evaluate merge-gating requirements (`merge_request_required_statuses`, `merge_request_ignored_statuses`, `max_divergence_*`) from a `DeploySpec` computed from the PR's own `head` commit (or, at minimum, from the target branch commit that will actually result after merge), not from `stack.cached_deploy_spec`. If performance requires caching, key the cache by the exact commit whose statuses are being judged, and re-validate against the head's own spec before calling `merge!`.

### Proof of Concept
1. Attacker opens a PR against a Shipit-tracked repo/branch whose current `shipit.yml` (cached in `stack.cached_deploy_spec`) requires `ci/tests` status.
2. Attacker's PR head commit modifies `shipit.yml` to remove/weaken `merge.require` and add a malicious `deploy.override` step, but does not touch anything the currently required CI check inspects.
3. `MergeRequest#reject_unless_mergeable!` → `any_status_checks_missing?`/`any_status_checks_failed?` are evaluated using `stack.cached_deploy_spec` (branch tip's old spec, unaware of the PR's rewritten file) [7](#0-6) ; checks pass because they only look at the old required-status list.
4. `merge!` merges the PR into the branch [8](#0-7) .
5. On the next deploy, `TaskCommands#deploy_spec` checks out this new commit and loads its (attacker-controlled) `shipit.yml`, executing the malicious `deploy.override` steps with the deploy host's credentials [5](#0-4) .
