### Title
Shared, stack-unscoped CCMenu token grants read access to every stack ever fetched by a user - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Summary
`CCMenuUrlController#client` looks up a single `ApiClient` per user (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')`) with no `stack` binding, and `CCMenuUrlController#fetch` mints a URL embedding that client's `authentication_token`. Because the underlying `ApiClient` is neither created with `stack:` nor checked against the requested `stack_id` anywhere in the authorization path, the token minted for stack A is byte-identical to, and fully authorizes, any subsequent stack B for the same user.

### Finding Description
The claimed binding should be: `token_minted_for(stack_A) == token_minted_for(stack_A) only`, i.e. a token embedded for stack A must authorize `GET /stacks/:A/ccmenu.xml?token=...` and must NOT authorize `GET /stacks/:B/ccmenu.xml?token=...` for any other stack B.

Tracing the code:
- `app/controllers/shipit/ccmenu_url_controller.rb:15-18` — `client` is `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`. The lookup key is only `creator` + `name`; `stack_id` is never part of the `find_or_create_by!` criteria and is never assigned on the record (`ApiClient belongs_to :stack, optional: true`, `app/models/shipit/api_client.rb:8`). Every call to `fetch`, regardless of `params[:stack_id]`, resolves to the exact same `ApiClient` row for a given `current_user`.
- `authentication_token` (`app/models/shipit/api_client.rb:34-36`) is `message_verifier.generate(id)` — a signed encoding of the client's database `id` only. It carries no stack claim whatsoever.
- On presentation, `app/controllers/shipit/api/ccmenu_controller.rb:33-36` authenticates via `ApiClient.authenticate(params[:token])`, which (`app/models/shipit/api_client.rb:24-27`) does `find_by(id: message_verifier.verify(token).to_i)` — again purely by id, with no comparison to `params[:stack_id]`.
- Authorization is enforced only via `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`), which per `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) checks `permissions.include?('read:stack')` — a global capability string, not scoped to any particular stack row.

Consequently: fetching the CCMenu URL for stack A returns `token = T` (encoding client id `N`); fetching again for stack B for the same user returns the same `client` row (id `N`), so the URL again contains `token = T`. `T` is accepted by `api_stack_ccmenu_url(stack_id: B)` exactly as it is by `stack_id: A`, since the authenticate/authorize path never inspects which stack the token was minted for. No existing guard (`require_permission`, `ExplicitParameters`, model validations) checks stack ownership of the `ApiClient`.

Attacker flow: an operator embeds the stack-A CCMenu URL (containing `token=T`) in a public/unauthenticated CI dashboard widget, per the intended use case of this feature. Anyone holding that URL (unprivileged internet user, no session, no secrets) can immediately probe `GET /stacks/:other_stack/ccmenu.xml?token=T` for any stack belonging to the same Shipit instance/user context and receive full stack state (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `webUrl`) without ever needing a "new" token — this works even for stacks that did not exist yet at token-mint time, and does not require the operator to have re-fetched a CCMenu URL for stack B first, since the token is not stack-scoped at all.

### Impact Explanation
This is an unauthenticated read of stack state (build activity, status, labels, web URL) for stacks the token was never explicitly minted for, satisfying the High-severity category "unauthenticated read of stack state." A single leaked/embedded widget URL for one stack silently grants read access to every other stack in the deployment for as long as the shared `ApiClient` id and `Shipit.api_clients_secret` remain unchanged — the blast radius scales with however many stacks exist on the instance, not just the ones the operator explicitly fetched.

### Likelihood Explanation
Preconditions are minimal and match the intended usage pattern of this feature exactly: any authenticated Shipit user generates one CCMenu URL (a normal, documented action) and pastes it into a third-party dashboard widget, which is precisely the feature's stated purpose. No secrets, no GitHub privileges, and no webhook forgery are required by the downstream attacker — they only need the URL text, which is designed to be shared into unauthenticated third-party tooling. This is fully repeatable and requires no live GitHub interaction.

### Recommendation
Bind the `ApiClient` (and thus the token) to a single stack: include `stack_id: stack.id` in both the `find_or_create_by!` lookup and creation attributes in `CCMenuUrlController#client`, and in `Api::CCMenuController#authenticate_api_client` (or via `require_permission`) verify `@current_api_client.stack_id == stack.id` before rendering, rejecting the request otherwise.

### Proof of Concept
```ruby
# test/controllers/ccmenu_url_controller_test.rb (conceptual)
test "CCMenu token is not scoped to a single stack" do
  user = shipit_users(:walrus)
  session[:user_id] = user.id

  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')

  get :fetch, params: { stack_id: stack_a.to_param }
  token_a = URI(JSON.parse(response.body)['ccmenu_url']).query[/token=([^&]+)/, 1]

  get :fetch, params: { stack_id: stack_b.to_param }
  token_b = URI(JSON.parse(response.body)['ccmenu_url']).query[/token=([^&]+)/, 1]

  assert_equal token_a, token_b # proves shared, unscoped token

  # Use stack-A's token against stack B's ccmenu.xml endpoint
  get 'shipit/api/ccmenu#show', params: { stack_id: stack_b.to_param, token: token_a }
  assert_response :ok
  assert_includes response.body, stack_b.to_param # unauthorized cross-stack read succeeds
end
```
This asserts the binding `token_a == token_b` (violating "must authorize exactly the stack named at mint time") and demonstrates that `token_a`, minted for stack A, is accepted for stack B's `ccmenu.xml` with no additional token issuance required.
