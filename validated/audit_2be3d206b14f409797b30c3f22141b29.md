### Title
CCMenu API endpoint bypasses per-stack token scoping, letting a stack-scoped `ApiClient` read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to resolve `params[:stack_id]` directly against `Stack.from_param!`, instead of going through `Api::BaseController#stacks`, which is the method that restricts stack lookup to the calling `ApiClient`'s authorized `stack_id`. This breaks the binding "stack a token authorizes == stack it touches": an `ApiClient` token that was issued and authorized for one specific stack can be replayed against the CCMenu endpoint with a different `stack_id` to read that other stack's deploy/build status.

### Finding Description
`Api::BaseController` defines the canonical, scope-respecting stack accessor: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated client is scoped to a stack, and `stack` builds on top of that scoped relation. Every other API controller (e.g. `Api::StacksController`) relies on this scoping to enforce "the client can only see stacks it is authorized for," as confirmed by the test `"an api client scoped to a stack will only see that one stack"`.

`Api::CCMenuController`, however, redefines `stack` to bypass `stacks` entirely: [2](#0-1) 
It also overrides `authenticate_api_client` to accept the token from a query-string `params[:token]` (for CI tooling convenience): [3](#0-2) 
The only remaining authorization gate is `require_permission :read, :stack`: [4](#0-3) 
which merely calls `current_api_client.check_permissions!(operation, scope)`: [5](#0-4) 
This check validates that the string `"read:stack"` is in the client's `permissions` array — it never compares `current_api_client.stack_id` against the requested `params[:stack_id]`. Because `CCMenuController#stack` never applies the `stacks` (stack_id-restricted) scope, any `read:stack`-permitted token — even one deliberately narrowed to a single stack via `ApiClient#stack_id` — can be used to fetch the CCMenu XML status of *any* stack in the installation by simply changing `stack_id` in the URL.

The legitimate use of `ApiClient.stack` scoping is exercised elsewhere in the suite (`"an api client scoped to a stack will only see that one stack"` in `test/controllers/api/stacks_controller_test.rb`), confirming this is an intended security boundary that `CCMenuController` fails to enforce.

**Binding broken:** `stack a token authorizes (current_api_client.stack_id)` ≠ `stack a token can touch (arbitrary params[:stack_id] via CCMenuController#stack)`.

### Impact Explanation
An attacker who legitimately possesses (or leaks) a narrowly-scoped `ApiClient` token — one intentionally restricted by an administrator to a single, presumably lower-sensitivity stack — can use it to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of every other stack managed by the Shipit instance, including stacks the token was never meant to access. This is an unauthenticated-for-that-resource read of stack state across a stack-scope boundary, matching the "High: escalation into ... unauthenticated read of stack state" impact category.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` credential (which are routinely generated and distributed for CI dashboards via `CCMenuUrlController`) can trigger this by simply substituting a different `stack_id` in the request URL — no special privileges, signature forgery, or additional credentials are required. The endpoint is a public XML endpoint (used by CCTray-compatible tools) meant to be embedded in URLs, increasing real-world exposure.

### Recommendation
Make `CCMenuController#stack` use the scoped `stacks` relation from `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot resolve stacks outside their authorized `stack_id`.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to Stack A (`stack_id = A.id`, `permissions = ["read:stack"]`), e.g. via `CCMenuUrlController#client`.
2. Attacker obtains this token (e.g., from an embedded CCTray URL) and requests:
   `GET /api/<Stack B id>/ccmenu?token=<Stack-A-scoped-token>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully.
4. `require_permission :read, :stack` passes because the token's `permissions` array contains `"read:stack"` (no stack-id check).
5. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping) and returns Stack B.
6. The response renders Stack B's build/deploy status XML, even though the token was only authorized for Stack A.
