### Title
Cross-repository Status creation via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` across the entire `commits` table with no scoping to the repository named in the webhook payload, then calls `create_status_from_github!` on every match. `Shipit::Status.replicate_from_github!`'s `find_or_create_by!` key (`stack_id, state, description, target_url, context, created_at`, no sha) does not change this: the query that selects which commits/stacks get touched is already global before it ever reaches `Status`. A single validly-signed webhook for one repository therefore writes `Status` rows into every stack whose `Commit` table happens to contain a matching sha.

### Finding Description
Binding claimed: `repos_entitled_to_mutate(webhook) == repos_actually_mutated(webhook)`, where `repos_entitled_to_mutate` = 1 (the repository named in `payload['repository']['full_name']`).

Trace:
- `Shipit::WebhooksController#create` parses `params` and dispatches to handlers after `verify_signature`, which checks the signature against `Shipit.github(organization: repository_owner)` — i.e., it authenticates the *organization/repo the payload claims to be from*, nothing more [1](#0-0) .
- `Webhooks::Handlers::Handler` exposes a `stacks` helper that correctly scopes lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [2](#0-1) . `PushHandler` and `CheckSuiteHandler` both use this `stacks` scope before touching any commit [3](#0-2) [4](#0-3) .
- `StatusHandler`, however, does not declare or use `repository` at all in its params schema, and its `process` method queries `Commit` directly and globally: `Commit.where(sha: params.sha).each do |commit| commit.create_status_from_github!(params) end` [5](#0-4) .
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` then `find_or_create_by!`s a `Status` row keyed on `stack_id, state, description, target_url, context, created_at` — no `sha`/`commit_id` is part of the uniqueness key, but this is irrelevant to the cross-repo issue since the `stack_id` used is derived from whichever `commit.stack_id` matched the global sha lookup [6](#0-5) [7](#0-6) .

Root cause: `StatusHandler#process` never restricts the `Commit` lookup to the stacks belonging to the repository asserted in the webhook. Any commit sha that happens to exist in more than one Shipit-tracked stack (a routine occurrence for forks/mirrors of a shared upstream, or shared template-repo initial commits) will get a `Status` row created in *every* one of those stacks from a single webhook delivery, regardless of which repository the webhook was actually signed for.

Why existing guards don't stop this: `verify_signature` only proves the request originated from the org/app whose secret matches `repository_owner` in the payload — it says nothing about which commits that org is allowed to annotate. `ExplicitParameters` schema on `StatusHandler` (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`) never requires or references `repository`, so nothing in the parameter-validation layer can enforce repo scoping even if someone wanted to add it later without changing `process`. There is no `stacks`/repository check in the handler at all.

Attacker exact request: attacker has push/CI access to a repository they control that is tracked by Shipit and shares commit history (forked from, or created from the same template as) one or more unrelated victim repositories also tracked by Shipit. Attacker triggers (or crafts, if they can get GitHub to deliver it, e.g. via their own CI posting a commit status) a `status` event on a commit sha that is common to their repo and the victim repos. GitHub signs the webhook validly for the attacker's own org. `StatusHandler#process` matches `Commit.where(sha: <shared sha>)` across all stacks and writes a `Status` row into each victim stack.

### Impact Explanation
A single, correctly-signed webhook belonging to one repository writes `Status` rows into unrelated stacks/repositories that never authenticated the event. `Status` creation has side effects beyond the row itself: `after_create :enable_ci_on_stack` (silently turning on CI enforcement for a victim stack) and `after_commit :schedule_continuous_delivery` (can enqueue `ProcessMergeRequestsJob`/merge-queue processing, and downstream `deployable_status`/`commit_status` hook deliveries) fire on the victim stack as if the victim's own CI had reported that state [8](#0-7) . This is a payload for one repository mutating another repository's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Repeatable per matching sha, and blast radius scales with however many stacks share history with the attacker's repo.

### Likelihood Explanation
Requires: (1) attacker controls or has status-posting rights on some repository tracked by Shipit (fork, template-derived repo, or a repo where they merely have `repo:status` API scope on their own fork); (2) that repository shares at least one commit sha with a victim stack Shipit has already ingested (common for forks of a shared upstream, or repos scaffolded from the same template with identical initial commits). No secrets, no Shipit session, no team membership needed — only the ability to cause a legitimately-signed `status` webhook for a commit sha that also exists elsewhere. This is a realistic and low-cost precondition in any Shipit deployment tracking multiple forks/derivatives of shared codebases.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the webhook payload, the same way `PushHandler` and `CheckSuiteHandler` do: require `repository.full_name` in the params schema and restrict the commit lookup to `stacks.commits.where(sha: params.sha)` (i.e., only commits belonging to stacks under `Repository.from_github_repo_name(params.repository.full_name)`), instead of a global `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook only creates statuses for commits belonging to the webhook's own repository" do
  victim_stack = shipit_stacks(:cyclimse) # unrelated repository/stack
  attacker_stack = shipit_stacks(:shipit) # attacker's own repository/stack

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now, message: "shared upstream commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now, message: "shared upstream commit")

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'created_at' => Time.now.iso8601,
    'branches' => [{ 'name' => attacker_stack.branch }],
    'repository' => { 'full_name' => attacker_stack.repository.full_name } # signed only for attacker's own repo
  }

  # binding under test: repos_entitled_to_mutate(payload) == 1 (attacker_stack only)
  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
  assert_difference -> { attacker_commit.reload.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
This currently fails: `victim_commit.statuses.count` increases by 1 even though the webhook payload names only `attacker_stack`'s repository, proving `StatusHandler#process`'s unscoped `Commit.where(sha:)` lets one repository's signed webhook mutate another repository's stack state.
