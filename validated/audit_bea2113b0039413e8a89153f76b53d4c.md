### Title
Unset/optional `webhook_secret` causes `GitHubApp#verify_webhook_signature` to accept unsigned webhooks, allowing forged `membership` events to grant `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
The reported smart-contract bug is a class of "unset configuration silently defaults to a permissive/zero value" flaw: an unset `PriceConfig`/`CurvePriceConfig` defaults to `0`, which the pricing function then trusts as valid, giving a free domain. The same bug class exists in `Shipit::GitHubApp#verify_webhook_signature`: if the `webhook_secret` configuration key is unset (which the engine's own setup docs explicitly say is *optional*), the verification function unconditionally returns `true`, i.e. it treats "no secret configured" as "signature verified." This lets any unauthenticated network client send arbitrary, unsigned webhook payloads that the engine processes as genuine GitHub events - including the `membership` event, which directly mutates `Shipit.github_teams` authorization membership.

### Finding Description
`WebhooksController#verify_signature` delegates trust decisions entirely to `GitHubApp#verify_webhook_signature`: [1](#0-0) 

That method is implemented as: [2](#0-1) 

`return true unless webhook_secret` means: if the operator has not configured `webhook_secret` for an organization, **every** webhook request is treated as verified, regardless of whether `X-Hub-Signature` is present, well-formed, or correct. The engine's own setup documentation explicitly labels this key as "optional": [3](#0-2) 

and the multi-org example config even ships with the field blank by default: [4](#0-3) 

Once past this check, `WebhooksController#create` blindly dispatches the attacker-controlled JSON body to registered handlers: [5](#0-4) 

The `membership` event is wired to `MembershipHandler`, which creates/updates a `Team` and adds/removes a `User` from it based purely on the payload fields (`team`, `organization`, `member`, `action`) - none of which are covered by any actual cryptographic check when `webhook_secret` is unset: [6](#0-5) [7](#0-6) 

`Team#add_member` directly appends the attacker-chosen `User` to the team: [8](#0-7) 

Because `User#authorized?` checks membership in `Shipit.github_teams`: [9](#0-8) 

an attacker who can trigger a forged `membership` webhook (naming a team whose `github_id`/`organization`/`slug` matches one of `Shipit.github_teams`, and a `member.login` corresponding to their own already-known GitHub-authenticated `Shipit::User` row) can grant that `User` authorized access to the application, without ever needing a Shipit session, an `ApiClient` token, or the real `webhook_secret`.

**Binding broken (equality):**
- Before: `webhook signature verified == HMAC(webhook_secret, raw_body) matches X-Hub-Signature` (only true when the operator has *set* a secret).
- After (bug): `webhook signature verified == true` whenever `webhook_secret` is unset, decoupling "verified" from any actual GitHub-authenticated origin.

This is the direct analog of the reported issue: an *unset* configuration value (`webhook_secret`, like the unset `PriceConfig`) causes the guarding function (`verify_webhook_signature`, like `getPrice()`) to fall through to a default that is treated as "valid"/"free" rather than raising or rejecting.

### Impact Explanation
This crosses the "GitHub identity vs. the `User` bound to the session" and "authorization escalation" boundaries called out as in-scope impacts. Concretely, it allows:
- Unauthenticated forgery of any handled webhook event (`push`, `status`, `check_suite`, `pull_request`, `membership`) when an operator leaves `webhook_secret` unset for an organization - a configuration explicitly presented as optional by the project's own docs.
- Most severely, forged `membership` events let an attacker escalate their existing `Shipit::User` account into `Shipit.github_teams` authorization, which is explicitly listed as a High-severity impact ("escalation into `Shipit.github_teams` authorization").
- Forged `push`/`status`/`check_suite` events can also manipulate deployability signals (commit statuses, CI check results) that gate automatic/continuous deploys, contributing toward an unauthorized deploy.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: the vulnerability is only present for organizations where `webhook_secret` is left blank. Because the setup docs describe it as "optional" and the shipped example config (`config/secrets.development.shopify.yml`) ships with it commented as nil, it is plausible that real deployments follow this documented path and leave it unset, especially for internal/low-risk orgs or during initial setup. No credential, session, or GitHub App private key is required by the attacker - only network access to the `/webhooks` endpoint and knowledge of a valid team/user login (both discoverable via the public GitHub org). Precise likelihood in a specific deployment cannot be confirmed without knowing that deployment's actual `secrets.yml`; this uncertainty is inherent to a config-dependent flaw.

### Recommendation
Do not treat an unset `webhook_secret` as "verification passed." Instead:
- Require `webhook_secret` to be present as a hard configuration requirement (fail fast at boot / raise `AuthenticationFailed` if not configured for any org that receives webhooks), or
- If truly optional support must remain, explicitly reject all webhook deliveries lacking a valid signature rather than defaulting to `true`, and only allow an explicit administrator opt-in "unsigned webhooks" mode that is clearly documented as unsafe and off by default.
- Additionally, apply extra authorization safeguards on `MembershipHandler` so that a forged/replayed `membership` event cannot silently grant `Shipit.github_teams` membership without corroborating evidence (e.g., verifying team/org linkage against `GithubHook::Organization` records tied to a signed webhook history).

### Proof of Concept
1. Operator deploys Shipit with a `github` config block for org `acme` where `webhook_secret` is left blank (as permitted by `docs/setup.md` and the shipped example `config/secrets.development.shopify.yml`).
2. Attacker sends, without any `X-Hub-Signature` header (or an arbitrary bogus one):
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <id of a team in Shipit.github_teams>, "name": "Developers", "slug": "developers", "url": "https://example.com"},
  "organization": {"login": "acme"},
  "member": {"login": "attacker-github-login"}
}
```
3. `WebhooksController#verify_signature` calls `GitHubApp#verify_webhook_signature(nil_or_bogus_signature, raw_body)`; since `webhook_secret` is blank, `return true unless webhook_secret` short-circuits and the request is accepted (`lib/shipit/github_app.rb:76-83`).
4. `MembershipHandler#process` runs, finds/creates the `Team` matching the payload, finds/creates the `User` for `attacker-github-login`, and calls `team.add_member(member)` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`, `app/models/shipit/team.rb:41-43`).
5. If that `Team` is one of `Shipit.github_teams`, the attacker's already-existing `Shipit::User` (created via normal OAuth login, which does not require org membership) now passes `User#authorized?` and gains full authenticated access to the Shipit UI/actions gated by team membership.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
