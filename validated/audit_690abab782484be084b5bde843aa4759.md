## Title
Headers-Commission Rounding of `earned_headers_commission_recipients` Shares Allows Supply Inflation of Base Currency - (File: `headers_commission.js`)

### Summary
This is a direct analog of the reported `toFixed(2)` rounding bug: independently rounding fractional percentage shares of a single pool of value causes a small but attacker-controllable discrepancy between the value actually available and the value distributed. In the external report this merely mis-displays a UI value; in ocore's headers-commission distribution logic, the same class of rounding error mints extra spendable bytes that were never actually paid in as headers commission, which is a real supply-inflation bug rather than a cosmetic one.

### Finding Description
When a unit wins the headers commission paid by a parent unit, the full amount (`full_amount`, an integer number of bytes) is split among the recipients listed in `earned_headers_commission_recipients` according to each recipient's percentage share: [1](#0-0) 

Each recipient's payout is computed independently as `Math.round(full_amount * share / 100.0)` [2](#0-1)  and again for the DB-driven path [3](#0-2) . Because rounding is applied per-recipient instead of once for the whole pool, the sum of the rounded amounts can exceed `full_amount` (e.g. `full_amount=50`, two recipients at 50% each: `Math.round(50*50/100)=25+25=50` is fine, but with many small shares the error compounds — e.g. `full_amount=50`, 100 recipients at 1% each: `Math.round(50*1/100)=Math.round(0.5)=1` per recipient × 100 recipients = 100, i.e. double the actual `full_amount`).

The only validation performed on `earned_headers_commission_recipients` is that the shares are positive integers, addresses are valid and strictly sorted, and the shares sum to exactly 100 — there is no check that the recipient addresses correspond to actual unit authors, and no limit preventing many recipients with small shares chosen specifically to maximize rounding gain: [4](#0-3) 

The resulting per-address amounts are summed and inserted directly into `headers_commission_outputs` without any subsequent check that the total matches the true `headers_commission` of the payer unit: [5](#0-4) 

These outputs later become spendable as `headers_commission`-type inputs in payment messages, validated only by re-deriving the same (deterministic but inflated) amount via `calcFunc`/`mc_outputs.calcEarnings`: [6](#0-5) 

Since the calculation is deterministic, all full nodes agree on the (already-inflated) numbers, so this does not cause a fork/disagreement — it causes a silent, network-wide creation of extra spendable base-currency value that was never paid in as an actual commission.

### Impact Explanation
An attacker who authors a multi-author unit (or co-authors with a colluding party) can set `earned_headers_commission_recipients` to a large number of addresses under their control with small percentage shares chosen to make `Math.round(full_amount * share / 100)` round up for every recipient, causing the sum of amounts credited to `headers_commission_outputs` to exceed the true `headers_commission` earned by the payer unit. This mints byte balance that can later be spent as ordinary `transfer` inputs, directly inflating the money supply — one of the explicitly in-scope high-impact outcomes (supply inflation).

### Likelihood Explanation
Any address able to author (or co-author) a unit that ends up winning headers commission from a parent — a routine, unprivileged action for any wallet — can set the recipient list of that unit. The attack requires only crafting the `earned_headers_commission_recipients` array with values chosen to maximize aggregate rounding error; no special privileges, timing, or race conditions with other peers are needed, and the win condition ("becoming the winning child of the header commission race") is a normal outcome of ordinary transaction posting, not something requiring malicious network behavior.

### Recommendation
Compute recipient amounts so they always sum exactly to `full_amount`, e.g. round all recipients except the last using `Math.round`, and assign the last recipient `full_amount` minus the sum of all previously rounded amounts (largest-remainder method), instead of rounding each share independently.

### Proof of Concept
1. Attacker controls addresses `A1..A100` (sorted) and crafts a 2-author unit with `earned_headers_commission_recipients` = 100 entries, each `earned_headers_commission_share: 1` (sums to 100, passes `validateHeadersCommissionRecipients`).
2. This unit becomes the winning child for a parent unit whose `headers_commission` (`full_amount`) is, say, 50 bytes.
3. `calcHeadersCommissions` computes, for each of the 100 recipients: `Math.round(50 * 1 / 100) = Math.round(0.5) = 1` byte [2](#0-1) .
4. Total credited to `headers_commission_outputs` = 100 bytes, double the actual 50 bytes earned [7](#0-6) .
5. Attacker later spends these 100 bytes across the 100 addresses as `headers_commission` inputs in ordinary payments; validation re-derives the same inflated 100 via `calcEarnings`/`calcWitnessEarnings` and accepts it [8](#0-7) , permanently inflating total spendable supply by 50 bytes for this single event (repeatable at will).

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
