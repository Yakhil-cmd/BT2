### Title
Webhook organization used for signature verification is decoupled from the repository the payload writes to, allowing cross-repository status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the inbound HMAC signature against, using an organization value taken directly from the untrusted request body. Separately, every `Webhooks::Handlers::Handler` subclass resolves the *actual* repository/stack it will act on from a different field of that same untrusted body. Nothing ties these two values together, so the identity that is cryptographically authenticated is not the identity that is written to.

### Finding Description
`verify_signature` picks the signing organization like this: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` is used to fetch the `webhook_secret` for that organization and verify `X-Hub-Signature` against `request.raw_post`. Because the signature covers the whole raw body, this step only proves the request was signed with *some org's* configured secret — specifically the secret belonging to whatever `repository.owner.login` (or `organization.login`) the attacker put in the body.

Once verification passes, every handler independently determines which repository/stack to act on from a *different* field of the same body: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository_name` (`repository.full_name`) is never cross-checked against `repository.owner.login`/`organization.login`, the value that was actually used to select the verifying secret. In a legitimate GitHub webhook these two fields are always consistent, but the engine does not enforce that — it trusts the JSON body to be internally consistent once *any* valid signature is present.

The binding that should hold is:
`organization authenticated by verify_signature == owner of the repository actually written by the handler`

This binding is broken: an attacker who legitimately knows the `webhook_secret` for **any** organization configured in a multi-org Shipit deployment (see `docs/setup.md` multi-app config, and `test/dummy/config/secrets_double_github_app.yml` showing per-org secrets) can construct an arbitrary payload where `repository.owner.login` (or `organization.login`) is set to *their own* org — satisfying `verify_signature` — while `repository.full_name` names a completely different, victim-owned repository/stack tracked by the same Shipit instance.

This is directly evidenced by the controller/handler test suite, which shows the `status` event handler persisting payload-supplied fields (`state`, `target_url`, `description`, `context`) onto a `Commit` found purely via the repository looked up from the payload: [4](#0-3) 

I was not able to directly inspect `app/models/shipit/webhooks/handlers/status_handler.rb`'s source in this pass (index/tool-call limits), so the exact field-mapping code in that handler is inferred from this test rather than confirmed line-by-line; the decoupling in `handler.rb`/`webhooks_controller.rb` shown above, however, is confirmed directly from source and is the root cause regardless of which specific handler is targeted.

### Impact Explanation
By forging the `repository.owner.login`/`organization.login` field to match an organization whose webhook secret the attacker legitimately possesses, while pointing `repository.full_name` at an unrelated, victim-tracked repository, an attacker can:
- Inject arbitrary commit statuses (`state: "success"`, forged `description`/`target_url`/`context`) onto commits of a victim stack via the `status` handler, which can satisfy Shipit's CI-gating logic used to authorize deploys — this reaches the "unauthorized deploy" impact bar.
- Force `GithubSyncJob` to run against an arbitrary tracked stack via the `push` handler (lower severity here since actual commit content is subsequently re-fetched from the real GitHub API rather than trusted from the payload).

### Likelihood Explanation
Exploitation requires the attacker to control (or know) a `webhook_secret` for at least one organization configured in the Shipit deployment — realistic in any multi-organization Shipit installation where different orgs onboard their own GitHub Apps, since nothing in `verify_signature` ties the authenticated org to the specific repository named later in the same payload. No repository write access, session, or `ApiClient` token to the *victim* repo is required — only knowledge of one legitimate, unrelated org's webhook secret.

### Recommendation
In `Handler#repository_name` (and the `stacks` lookup), require `payload.dig('repository', 'full_name')` to have an owner segment matching `repository.owner.login` (the exact value used in `WebhooksController#repository_owner` for signature verification), or better, pass the authenticated organization down from the controller into each handler and reject/ignore any payload where the two disagree.

### Proof of Concept
1. Attacker legitimately controls org `attacker-org`, which has a GitHub App configured in Shipit with a known `webhook_secret`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "description": "forged",
  "target_url": "https://attacker.example.com",
  "context": "ci/required-check",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org's webhook_secret, body)` and POSTs to `/github/webhooks`.
4. `WebhooksController#repository_owner` returns `"attacker-org"` (from `repository.owner.login`), `Shipit.github(organization: "attacker-org")` succeeds verification using the attacker's own known secret.
5. `StatusHandler#stacks`/`repository_name` resolves `"victim-org/victim-repo"` from the same body and writes the forged status onto the victim's commit — a status the attacker's org has no authorization over.
