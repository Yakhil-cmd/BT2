### Title
`MembershipHandler#find_or_create_team!` never re-validates `params.organization.login == team.organization` before `add_member` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` resolves a `Team` by `github_id` alone via `find_or_create_team!`, and only sets `team.organization` inside the `find_or_create_by!` block that runs solely on record creation. When a `Team` row for `github_id: T` already exists (e.g. `organization: 'V'`), a webhook whose `X-Hub-Signature` is valid for a *different* organization `A` but whose `team.id` field equals `T` will still resolve to the pre-existing org‑V `Team` and call `team.add_member(member)` unconditionally, without ever comparing `params.organization.login` to the persisted `team.organization`.

### Finding Description
The broken binding, stated as an equality that the code never checks: `params.organization.login == team.organization` for the `Team` row being mutated in `Shipit::Webhooks::Handlers::MembershipHandler#process`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and verifies the signature against `Shipit.github(organization: repository_owner)` [2](#0-1) . For a `membership` event payload there is no top-level `repository` key, so `repository_owner` resolves to `params.organization.login` — i.e. whichever organization the attacker names in the JSON body. This means the signature check is scoped to org `A`'s own configured `webhook_secret`, and does **not** constrain which `team.id` may appear in the payload.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . Because the block only executes when the record is newly created, an existing `Team` row with `github_id: T, organization: 'V'` is simply *found*, and its `organization` column is left untouched.
- `process` then unconditionally executes `team.add_member(member)` for the `'added'` action [4](#0-3) , and `Team#add_member` just appends the member with no organization check [5](#0-4) .

Attacker's exact request: a `POST /webhooks` with header `X-Github-Event: membership`, signed with org `A`'s webhook secret (which the attacker, as `A`'s onboarded owner/admin on this Shipit instance, has legitimate access to since GitHub lets an org owner set/see its own webhook secret when the app or webhook is configured against that org), and body:
```json
{"action":"added","team":{"id":T,"name":"...","slug":"...","url":"..."},"organization":{"login":"A"},"member":{"login":"attacker"}}
```
Since `T` is the `github_id` of the pre-existing `Team` for org `V`, `find_or_create_by!` finds that row instead of creating a new one, and `attacker` is appended as a member of a team belonging to org `V`, despite the request only being authenticated for org `A`.

Existing guards do not stop this: `verify_signature` authenticates *that the request came from org A*, not that the `team.id` referenced belongs to org A; `ExplicitParameters` only validates types/presence, not cross-organization consistency [6](#0-5) ; and no code anywhere compares `team.organization` to `params.organization.login` before mutating membership.

### Impact Explanation
If the pre-existing `Team` row `T` is one of the teams referenced by `Shipit.github_teams` (built from `oauth_teams` per-organization config, see `lib/shipit.rb#github_teams`) [7](#0-6) , then adding the attacker as a member grants them `authorized?` == true via `User#authorized?`, which checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) . This is a cross-tenant escalation into `Shipit.github_teams` authorization from an attacker who only controls a different, unrelated organization onboarded to the same Shipit instance — matching the "High: escalation into `Shipit.github_teams` authorization" impact category. It is repeatable against any known/guessable `team.id` (GitHub team IDs are small sequential integers, often discoverable), and does not require any secret belonging to org `V`.

### Likelihood Explanation
Preconditions: (1) the target Shipit instance must be a multi-organization deployment where the attacker's own org `A` is legitimately configured with `secrets.github[:A][:webhook_secret]` (i.e., the attacker is a real, if unprivileged w.r.t. Shipit, owner/admin of org `A` who can trigger `membership` webhooks against their own org and knows/controls that secret); (2) a `Team` row for org `V`/team `T` must already exist and be part of `Shipit.github_teams`; (3) attacker needs to know or guess `T`, GitHub's numeric team id. This is feasible with minimal cost — the attacker only needs their own org's webhook config, which they already legitimately possess as per the threat model, and can trigger this via a normal `membership` "added" event fired against their own org while spoofing the `team.id` field in the JSON body.

### Recommendation
In `find_or_create_team!`, after resolving the `Team`, raise/reject if `team.organization != params.organization.login` (for both the found and newly-created cases), e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "Team #{team.id} organization mismatch" unless team.organization == params.organization.login
  team
end
```
Additionally, consider making the webhook signature verification for `membership` events bind explicitly to `params.organization.login` (already the case) *and* independently validate that the referenced `team.id`'s stored organization matches, closing the gap even if the org is spoofable in future payload shapes.

### Proof of Concept
Minitest (in a webhook/model test file) asserting the binding on both sides:
```ruby
test "membership added webhook cannot hijack a team belonging to another organization" do
  team = shipit_teams(:shopify_developers) # organization == 'shopify', github_id == some T
  assert_equal 'shopify', team.organization

  attacker_org_payload = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }

  @request.headers['X-Github-Event'] = 'membership'
  # signature computed with attacker-org's own webhook secret, valid for 'attacker-org'
  assert_no_difference -> { Membership.where(team_id: team.id).count } do
    post :create, body: attacker_org_payload.to_json, as: :json
  end

  team.reload
  assert_equal 'shopify', team.organization
  refute User.find_by(login: 'attacker')&.authorized?
end
```
This test currently fails (Membership row is created and, if the team is in `Shipit.github_teams`, `authorized?` becomes true) because no code path enforces `team.organization == params.organization.login` before `add_member` executes.
