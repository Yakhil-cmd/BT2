### Title
Webhook Signature Verification Is Keyed by an Unauthenticated Organization Field, Allowing Cross-Organization/Cross-Repository Webhook Forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to verify a webhook against using an untrusted field taken from the very payload being verified. The event handlers that subsequently mutate state, however, key off a *different* field of that same payload (`repository.full_name`) to decide which `Stack`/`Repository` to act on. Because HMAC verification only proves the payload was signed by *some* known organization's secret — not that the organization owner field matches the repository the handlers actually operate on — an attacker who knows (or controls) the webhook secret for any one configured organization in a multi-org Shipit deployment can forge a payload whose `repository.owner.login` names their own organization (to pass signature verification) while `repository.full_name` names an arbitrary tracked repository belonging to a completely different organization, causing Shipit to sync commits, update statuses, or open/close pull requests for a repository the attacker never authenticated against.

### Finding Description
`verify_signature` derives the verifying organization from the same untrusted JSON body it is about to check: [1](#0-0) 

`repository_owner` is read straight from the JSON payload before any cryptographic check occurs: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` instance (and thus the `webhook_secret`) configured for that organization name; Shipit explicitly supports one `webhook_secret` per organization in multi-tenant configuration (see `config/secrets.development.example.yml` / `docs/setup.md`, which document per-org `github:` sub-keys each with its own `webhook_secret`).

`verify_webhook_signature` only proves the raw body was HMAC-signed with *that organization's* secret — it says nothing about whether the repository the handlers will act on belongs to that organization: [3](#0-2) 

Once the signature check passes, `create` dispatches the full (attacker-controlled) JSON body to every registered handler for the event: [4](#0-3) 

All handlers resolve which `Stack`/`Repository` to mutate using a *different* payload field — `repository.full_name` — not `repository.owner.login`: [5](#0-4) 

For example, `PushHandler` uses that repository-derived `stacks` scope to trigger a GitHub sync (which updates commit history/state) for any stack matching the branch in the forged payload: [6](#0-5) 

Pull-request handlers similarly resolve `repository` from `params.repository.full_name` and then create/archive/unarchive review stacks or update pull request state for that repository: [7](#0-6) [8](#0-7) 

**The broken binding, as an equality:**
`organization whose secret authenticated the request` (`repository.owner.login`, used only to pick the HMAC key) **≠** `repository the handler chain mutates` (`repository.full_name`, used by every `Handler#stacks` / `Repository.from_github_repo_name` call). Nothing in `verify_signature` or in `Handler` enforces that these two fields agree, and both are attacker-controlled content of the same unauthenticated-until-verified raw body.

Before the attacker's forged request: organization A's secret authenticates only requests describing organization A's repositories.
After: organization A's secret (known to an attacker with legitimate access to organization A's GitHub App/webhook config) authenticates a payload whose `repository.full_name` points at organization B's tracked repository, and Shipit processes it as a genuine event for organization B's stack.

### Impact Explanation
This is a cross-repository/cross-organization write: an entity with legitimate control over one organization's webhook configuration in a multi-org Shipit deployment can forge signed-looking webhook events that make Shipit believe pushes, pull-request state changes, or membership/label changes happened on a repository belonging to an unrelated organization it has no access to. Depending on the handler this can drive `stack.sync_github`, review-stack creation/archival/unarchival, and pull request/label state changes on a victim stack — actions that ordinarily require legitimate GitHub push/PR access to the victim repository. This matches the "Critical – cross-repository writes" bucket in scope.

### Likelihood Explanation
Requires the attacker to have legitimate GitHub App/webhook configuration for at least one organization tracked by the same multi-tenant Shipit instance (a realistic scenario for shared/hosted Shipit deployments serving multiple orgs, which the engine explicitly supports per its own documented configuration format). No GitHub App private key, `ApiClient` token, or Shipit session is needed — only knowledge of one org's `webhook_secret`, which that org's own administrators legitimately possess. The forged HTTP request to `/webhooks` requires no other privilege.

### Recommendation
Bind signature verification to the same field the handlers act on: require that `repository.owner.login`/`organization.login` used to select the verifying secret is derived from (and equal to) the owner segment of `repository.full_name`, and additionally verify post-signature that the resolved `Repository`/`Stack` actually belongs to the organization whose secret validated the payload before dispatching to handlers.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `github.webhook_secret` (per documented multi-org config).
2. Attacker (who administers `attacker-org`'s GitHub App) knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and the signature validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `create` dispatches the payload to `PushHandler`, which resolves stacks via `repository.full_name = "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), triggering a sync for `victim-org`'s stack despite the request never being authenticated for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
