### Title
`Webhooks::Handlers::StatusHandler#process` mutates `Commit` rows by `sha` alone with no repository/stack scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits globally with `Commit.where(sha: params.sha)` and never consults `repository.full_name` or the `stacks` helper that every other repository-scoped handler (`CheckSuiteHandler`, `PushHandler`) uses to restrict effects to the calling repository. Because the DB's uniqueness constraint on commits is `(sha, stack_id)` rather than `sha` alone, the same SHA can legitimately exist as a `Commit` row under multiple, unrelated `Stack`s (most commonly via a GitHub fork, which preserves upstream commit SHAs), letting an attacker who owns a legitimately-configured repository inject a forged CI status onto a victim stack's commit.

### Finding Description
The broken binding: `payload['repository']['full_name']` (the value `verify_signature`/the webhook envelope vouches for) must equal `commit.stack.repository.full_name` for every `Commit` mutated by the handler. `StatusHandler` never checks this.

- `verify_signature` only uses `repository.owner.login` to pick which org's `webhook_secret` verifies the HMAC [1](#0-0) . It authenticates "this payload was signed by org X's secret," not "this payload's claimed `sha` belongs to org X's commits."
- `StatusHandler#process` does: [2](#0-1)  — a global `Commit.where(sha: params.sha)` scan, with no call to `stacks` or `repository_name`.
- By contrast, `CheckSuiteHandler#process` scopes correctly: [3](#0-2) , using `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3)  before ever touching `Commit` rows.
- The commits table's uniqueness constraint is `(sha, stack_id)`, not `sha` alone: [5](#0-4) , confirming the same SHA is expected to coexist across multiple stacks/repositories (e.g. a fork, or the same upstream tracked by two Shipit stacks).

Exploit flow: attacker forks a victim's public repository they've registered with Shipit as `attacker/repo` (a normal, unprivileged GitHub action). Because a fork retains identical commit SHAs for shared history, at least one `Commit` row exists both under the victim's `Stack` and would match by SHA. The attacker then POSTs `X-Github-Event: status` to `/webhooks` with `repository.owner.login: 'attacker-org'` (so `verify_signature` picks and validates against the attacker's own legitimate `webhook_secret`) and `repository.full_name` set to anything irrelevant (e.g. `attacker/repo`, or garbage), `sha` equal to the shared/colliding commit SHA, and `state: 'success'`. `StatusHandler#process` runs `Commit.where(sha: ...)`, finds the victim's `Commit` row (and any other stack sharing that SHA) and calls `commit.create_status_from_github!(params)` on it — creating a status entirely attributable to the attacker's forged payload, with no verification that the commit actually belongs to `attacker/repo`.

Existing guards fail here because: `verify_signature` binds the request to an organization's secret, not to a specific commit's owning repository; `ExplicitParameters` schema in `StatusHandler` only requires `sha`/`state`/etc., never `repository`; and no model validation on `Commit`/`Status` cross-checks the calling repository against `commit.stack.repository`.

### Impact Explanation
A successful request creates a `Status` on a `Commit` belonging to a stack the attacker does not own, which is exactly the "payload for one repository mutating another's stack/commit" Critical category. Downstream, `Commit#create_status_from_github!`/`add_status` can trigger `ProcessMergeRequestsJob` and, for stacks with `continuous_deployment` enabled, a transition to `success` schedules an actual deploy (`Deploy` `after_transition to: :success, do: :schedule_continuous_delivery`) [6](#0-5) , and related "success"-triggered merge-request processing is exercised in tests [7](#0-6) . So a forged status is not merely cosmetic — on CD-enabled victim stacks it can produce an unauthorized deploy. This is repeatable against any Stack whose repository shares a commit SHA with a repository the attacker legitimately controls (trivially satisfiable via fork).

### Likelihood Explanation
Preconditions: (1) attacker must own/administer a repository that Shipit has configured with a valid GitHub App/webhook secret for the attacker's own org (so `verify_signature` passes) — this is granted by the threat model ("any GitHub user who can push to a fork... and emit webhooks from a repository they own"); (2) attacker's repository must share at least one commit SHA with the victim's tracked stack, trivially achieved by forking the victim's public repository, whose pre-fork commit history retains identical SHAs. No Shipit secrets, sessions, or privileged roles are required. Cost is low and the attack is repeatable against any SHA the attacker can discover from the victim's public commit history.

### Recommendation
In `StatusHandler#process`, scope the lookup through `stacks` (as `CheckSuiteHandler` does) instead of a bare `Commit.where(sha:)`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the mutated `Commit` rows to the repository named in the verified payload, closing the asymmetry with `CheckSuiteHandler`/`MembershipHandler`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, or a new `StatusHandler` unit test):
1. Fixture setup: `victim_stack` belongs to `Repository(owner: 'victim', name: 'repo')`; create `victim_commit = victim_stack.commits.create!(sha: 'deadbeef', ...)`.
2. Create a second `Repository(owner: 'attacker', name: 'repo')` with its own `attacker_stack`, and create `attacker_stack.commits.create!(sha: 'deadbeef', ...)` (simulating the shared-history/fork SHA collision — allowed since the unique index is `(sha, stack_id)`, not `sha`).
3. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (simulating a correctly-signed request under the attacker's own secret) while leaving the victim's org secret untouched/never invoked.
4. POST `:create` with `X-Github-Event: status`, body `{ sha: 'deadbeef', state: 'success', repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } } }`.
5. Assert:
   - `victim_commit.reload.statuses.count` increased by 1 (equality broken: `payload['repository']['full_name'] == 'attacker/repo'` but a `Commit` under `victim/repo`'s stack was mutated).
   - `victim_commit.status.state == 'success'`.
   - (Optional) assert `ProcessMergeRequestsJob`/continuous-deployment scheduling was enqueued for `victim_stack` if `continuous_deployment: true`, demonstrating escalation beyond a benign status write.
