### Title
Cross-organization webhook forgery via `repository_owner`/`repository.full_name` binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Signature verification for inbound GitHub webhooks selects *which* GitHub App/organization secret to check against using one payload field (`repository.owner.login`, falling back to `organization.login`), while every event handler that actually acts on data selects the *target repository/stack* using a different field (`repository.full_name`). Nothing ties these two fields together, so a party who legitimately knows the webhook secret for "their" organization's GitHub App installation can forge a payload that authenticates as that organization but names a repository belonging to a completely different organization hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the signing key exclusively from `repository_owner`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to fetch the matching `GithubApp`/secret via `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that specific secret: [1](#0-0) 

Once the request passes this check, the actual event processing is dispatched to handlers that identify the target repository/stack using an entirely different field, `payload.dig('repository', 'full_name')`: [2](#0-1) 

For example `PushHandler` resolves the stacks to sync purely from `repository.full_name`/`ref`, with no relation to the organization that was used to authenticate the request: [3](#0-2) 

The pull-request family of handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`, `edited_handler.rb`) all resolve `repository` the same way, via `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and then archive/unarchive review stacks or update pull request records for that repository: [4](#0-3) [5](#0-4) 

Shipit explicitly supports hosting multiple independent GitHub organizations from a single instance, each with its own App/`webhook_secret`, as documented in the setup guide: [6](#0-5) 

Because `verify_webhook_signature` is an HMAC over the *entire* raw payload, an attacker who knows the secret for their own organization ("Org A") can compute a valid signature for *any* payload content signed with that secret — including one whose `repository.owner.login` is `"orgA/..."` (so the correct secret is selected and the signature validates) but whose `repository.full_name` is set to `"orgB/some-repo"` (a different, unrelated organization's repository that also has a stack configured on the same Shipit instance). The signature check only proves "this payload was signed by someone who knows Org A's secret" — it does not prove that the repository named inside the payload actually belongs to Org A. No code cross-validates that `repository.full_name`'s owner segment matches the `repository_owner` used to select/verify the signature.

This is the same bug class as the referenced report: two different values derived from the same input are compared/used inconsistently across a boundary — there, `friday8am - timestamp` used the wrong reference epoch for a subset of timestamps; here, `repository_owner` (authentication key selection) and `repository.full_name` (target-of-action selection) are two different projections of the same webhook payload that are never reconciled, breaking the intended binding "authenticated organization == organization being written to."

### Impact Explanation
This breaks the trust boundary between organizations that are supposed to be isolated on a multi-tenant Shipit instance. Anyone who legitimately controls/administers a GitHub App installation for one org (and thus knows or can obtain that org's `webhook_secret`) can forge webhook events attributed to any other organization/repository tracked by the same Shipit deployment, without needing a Shipit session, `ApiClient` token, or any privileged Shipit account. Concretely this enables:
- Forged `push` events causing `GithubSyncJob`/`stack.sync_github` to run against a victim stack.
- Forged `pull_request` events (`opened`/`closed`/`labeled`/`reopened`) that create, archive, or unarchive review stacks belonging to a different org's repository.
- Forged `status`/`check_suite`-type events that could inject fabricated CI status into a victim repository's commits, which downstream feeds Shipit's deploy/merge-gating logic (`required_statuses`, merge queue).

This is a cross-repository/cross-organization write performed entirely by an "unprivileged" (relative to the victim org) attacker, matching the Critical bucket ("cross-repository writes" / "unauthorized deploy, rollback or merge" when chained through CI-status forgery into the merge queue).

### Likelihood Explanation
The precondition is that Shipit is configured, as documented, to host more than one GitHub organization with independently issued webhook secrets (a first-class, documented feature, not a misconfiguration). Any entity that owns/administers one of those GitHub App installations already legitimately possesses (or provisions) its own webhook secret, and can freely POST arbitrary payloads to the public, unauthenticated `/webhooks` endpoint. No other credential, GitHub token, or Shipit account is required. This makes the likelihood high in any genuine multi-organization Shipit deployment.

### Recommendation
After signature verification succeeds, cross-check that the organization encoded in `repository.full_name` (and/or `organization.login`) matches the `repository_owner` that was used to select the verifying secret, and reject (422) the request if they diverge. Alternatively, verify the signature using the secret associated with the actual `repository.full_name` owner rather than a separately-derived `repository_owner`/`organization.login` field, so a single field consistently drives both key selection and the identity that handlers trust.

### Proof of Concept
1. Attacker legitimately owns/administers the GitHub App installation for `org-a` on the shared Shipit instance and therefore knows (or can set) `webhook_secret_a` in `Shipit.github(organization: 'org-a')`'s config.
2. Attacker crafts a JSON payload for the `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_a, raw_body)>` themselves, since they know `webhook_secret_a`.
4. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `WebhooksController#verify_signature` computes `repository_owner = "org-a"`, fetches Org A's app/secret, and the signature validates (it was computed correctly with that secret) — see [7](#0-6) .
6. `PushHandler#process` runs, resolving `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` — see [8](#0-7)  and [2](#0-1)  — and triggers `stack.sync_github` on Org B's stack, even though the request only proved knowledge of Org A's secret.

*(Note: I could not fully load `app/models/shipit/repository.rb`'s `from_github_repo_name` implementation or `lib/shipit.rb`'s `Shipit.github`/`GithubOrganizationUnknown` lookup logic in this final pass due to tool errors on the last iteration; their general behavior — resolving a `GithubApp` config by organization name and raising `GithubOrganizationUnknown` if absent — was already confirmed via `app/controllers/shipit/webhooks_controller.rb`'s rescue clause and `lib/shipit/github_app.rb`'s `verify_webhook_signature`.)*

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:

      private_key:
      oauth:
