### Title
`StatusHandler#process` mutates commit statuses across repositories without repository-scope check - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`) and never restricts the result set to the stacks belonging to the repository named in the webhook payload, unlike `PushHandler` which explicitly scopes via `stacks`. This lets a status webhook that is legitimately signed for one repository mutate `Commit`/`Status` state belonging to a different, unrelated Shipit stack whenever a `Commit` row with the same `sha` exists in both.

### Finding Description
The claimed binding is: `Handler#stacks` resolves to `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, i.e. the set of stacks whose repo matches the webhook's `repository.full_name`, and this should equal the set of `Commit` rows a handler is allowed to mutate (`Commit#stack` must belong to one of those stacks). `PushHandler#process` enforces exactly this by calling `stacks.not_archived.where(branch:)` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) [1](#0-0) .

`StatusHandler#process`, however, does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

It never calls `stacks` or `repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) [3](#0-2) , so the equality is broken: `Commit.where(sha: params.sha)` can return `Commit` rows belonging to stacks whose repository is completely different from `payload.dig('repository','full_name')`.

`commit.create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `add_status`, which emits `Hook.emit(:commit_status/:deployable_status, ...)` and can call `stack.schedule_merges` and, through `Commit#schedule_continuous_delivery`, enqueue `ContinuousDeliveryJob` if the newly-created status makes the commit `deployable?` (`app/models/shipit/commit.rb:281-287`, `366-386`) [4](#0-3) [5](#0-4) . This is a real state mutation with deploy-triggering side effects on a stack the incoming webhook's repository does not own.

Signature verification (`WebhooksController#verify_signature`) only authenticates that the payload originated from GitHub for the named `repository_owner`/organization (`app/controllers/shipit/webhooks_controller.rb:24-49`) [6](#0-5) ; it does not, and cannot, guarantee that no other Shipit-tracked repository/stack happens to contain a `Commit` row with the same `sha` (a common occurrence for forks, mirrors, or repos with shared git history). Nothing downstream of signature verification re-checks repository ownership for `StatusHandler`, so once GitHub delivers a validly-signed status event for the attacker's own repository (an event the attacker can trigger themselves, e.g. by setting a commit status via the GitHub API/Actions on their own repo/fork sharing a sha with a victim stack), `StatusHandler` will write status data onto the victim stack's commit.

### Impact Explanation
An attacker who controls (or forks/shares commit history with) a repository connected to Shipit can forge legitimate-looking commit statuses (state, context, description, target_url) onto a `Commit` belonging to a completely different, victim stack, as long as a `Commit` row with the identical `sha` exists in both. This can flip a victim commit's gating status (e.g. mark a required check `success`), unblocking or triggering an unauthorized deploy via `schedule_continuous_delivery`/`ContinuousDeliveryJob`, or conversely mark a legitimate commit as `failure` to block a victim's deploy — a cross-repository mutation of another party's stack/commit state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
The only precondition is that two `Commit` rows across different Shipit-tracked stacks share the same `sha` — realistic for forks, mirrors, transferred/renamed repositories, or vendored/shared history, all common in real GitHub organizations. The attacker needs no Shipit credentials; they only need the ability to cause GitHub to emit a status event on a repository they control (push access, GitHub Actions, or the GitHub Status API on their own repo), which is squarely within the stated unprivileged attacker capabilities. It is repeatable per status webhook and against any stack whose commit sha happens to collide with one the attacker can influence.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: restrict the affected commits to those belonging to `stacks` derived from `payload.dig('repository','full_name')`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create two `Repository`/`Stack` fixtures, `repo_a` (`owner_a/repo_a`) and `repo_b` (`owner_b/repo_b`), unrelated.
2. Create `Commit` rows on each stack with the identical `sha` value `"deadbeef" * 5`.
3. Build a status payload with `repository.full_name = "owner_a/repo_a"` and `sha` equal to the shared sha.
4. Assert (equality check): `Shipit::Webhooks::Handlers::Handler#stacks` for this payload returns only `repo_a`'s stack (`assert_equal [stack_a], handler.send(:stacks).to_a`).
5. Call `StatusHandler.call(payload)` and assert that **both** `commit_a.reload.statuses` **and** `commit_b.reload.statuses` were updated — demonstrating the handler mutated `commit_b` even though `stack_b` is excluded from `stacks` for this payload, i.e. the equality from step 4 is violated by the actual write behavior.
6. Contrast with `PushHandler`: build an equivalent push payload for `owner_a/repo_a` and assert only `stack_a` is touched (`stack_b.reload.updated_at` unchanged), proving the asymmetry between the two handlers on identical fixture data.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
