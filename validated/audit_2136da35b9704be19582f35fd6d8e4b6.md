### Title
API token scoped to a single stack can read any stack's build status via CCMenu - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` implements the intended trust binding "the stack(s) a token authorises == the stack it can touch" by resolving `stack` through the scoped `stacks` relation. `Api::CCMenuController` re-implements `stack` and `authenticate_api_client` and, in doing so, drops the scoping, letting any valid `ApiClient` token read CI/build state for any stack in the installation, not just the stack it was authorised for.

### Finding Description
`Api::BaseController` defines the authorization binding for every API endpoint: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a stack; `stack` is derived only from that scoped relation. This is the mechanism that enforces `stack authorised by token == stack touched by request`.

`Api::CCMenuController` overrides both `authenticate_api_client` (to accept the token via a query-string parameter instead of Basic auth) and `stack` (to look the record up directly on the unscoped `Stack` model): [2](#0-1) 

Because `stack` is redefined as `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the scoping performed in `BaseController#stacks` is completely bypassed. `require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` never inspects `stack_id`; the stack-scoping is exclusively implemented by the `stacks`/`stack` helpers in `BaseController`. Any controller that (like `CCMenuController`) resolves `stack` outside of that helper silently loses the per-stack restriction.

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches," which the rules explicitly call out as a valid analog class. `ApiClient` records can be created with a `stack_id` (the model has `belongs_to :stack, optional: true` and `BaseController#stacks` is written specifically to special-case `stack_id?`), intended to grant read-only access limited to one stack (e.g. a CI badge/status widget token handed to a third party). Any holder of such a scoped token can instead pass an arbitrary `stack_id` param to `/api/<owner>/<repo>/<env>/ccmenu.xml` and read build status, lock state, and last-deploy metadata (`lastBuildStatus`, `lastBuildLabel`, lock reason, etc.) for every other stack in the Shipit instance, matching the High-impact category "unauthenticated read of stack state...output" (here, cross-stack read using a token intentionally scoped narrower).

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` authentication token that has `read:stack` permission (no repository write access, no session, no admin privilege is required beyond having been issued one such token, which is by design meant to be handed to low-trust external consumers such as CI dashboards). The query-string authentication path in `CCMenuController#authenticate_api_client` makes the token easy to use directly from a browser/URL, increasing the realistic likelihood of misuse once a scoped token leaks (which is the exact threat model such scoping exists to mitigate).

### Recommendation
Have `Api::CCMenuController#stack` resolve through the scoped `stacks` helper (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped token cannot resolve a stack outside its authorised `stack_id`. Audit other controllers that override `stack`/`stacks` (or bypass `BaseController`) for the same divergence.

### Proof of Concept
1. Create (or possess) an `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A (e.g. via console/rake, mirroring how `CCMenuUrlController#client` or any stack-scoped token would be provisioned).
2. Generate its token: `client.authentication_token`.
3. Request `GET /api/<owner_b>/<repo_b>/<env_b>/ccmenu.xml?token=<token>` where `owner_b/repo_b/env_b` is Stack B, a stack the token was never scoped to.
4. `authenticate_api_client` succeeds (token is valid), and `stack` resolves Stack B via `Stack.from_param!`, bypassing the `stacks` scope check that `BaseController` would have applied — the response discloses Stack B's build/lock status even though the token is only authorised for Stack A.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
