### Title
Webhook signature verification keys on `repository.owner.login`, but handlers act on the attacker-controlled `repository.full_name` — cross-organization webhook spoofing - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check with `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the request body itself (`repository.owner.login`, falling back to `organization.login`). All webhook handlers, however, resolve *which* `Repository`/`Stack` to act on using a different field from the very same body: `repository.full_name` (`Handler#repository_name`). In a single/global GitHub App config this is harmless because there is only one secret. But Shipit explicitly supports **multiple GitHub organizations**, each with its own `webhook_secret` (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md` "Using Multiple Github Applications"). In that mode, an attacker who legitimately administers one configured org (and therefore knows/controls that org's `webhook_secret`, since GitHub org admins set it themselves when installing the App) can forge a webhook body where `repository.owner.login`/`organization.login` names *their own* org (so the signature check passes with their own secret) while `repository.full_name` names a repository belonging to a *different* configured org, causing Shipit to run handler logic (sync commits, close/label PRs, archive review stacks, create commit statuses, trigger `check_suite` refreshes) against a stack they do not administer.

### Finding Description
`verify_signature` in [1](#0-0)  derives the app/secret from `repository_owner`, itself computed purely from request JSON: [2](#0-1) 

`Shipit.github` resolves per-organization apps/secrets by that same organization key, supporting the documented multi-org deployment mode: [3](#0-2) 

Meanwhile every handler resolves the target `Repository`/`Stack` using `repository.full_name`, a separate JSON field that is not cross-checked against `repository.owner.login`: [4](#0-3) 

This is used directly by, e.g., `PushHandler#process` (triggers `stack.sync_github`) and `ClosedHandler#repository` (archives a review stack): [5](#0-4) [6](#0-5) 

Because the HMAC signature covers the entire raw JSON body (`request.raw_post`) and not a specific verified sub-field, an attacker who can compute a valid signature for *any one* configured organization (their own org, where they control the webhook secret as its GitHub admin) can freely set every other field of the JSON body, including `repository.full_name`, to point at a different organization's repository. The equality that should hold — "organization whose secret authenticated the request" == "organization/repository the handler is about to act on" — is never enforced; the code trusts `owner.login` for authentication and `full_name` for authorization/action target, without tying the two together.

### Impact Explanation
This breaks a cross-repository trust boundary: an attacker who is only trusted for their own organization's stacks can cause Shipit to execute privileged automation (triggering GitHub syncs that pull commits, closing/archiving review-stacks, injecting commit statuses/CI results that feed into deploy-gating logic such as `required_statuses`/`blocking_statuses`) against stacks belonging to a completely different organization that they have no access to. This is a cross-repository write achieved purely through crafting an unprivileged webhook payload, which matches the Critical "cross-repository writes" / "unauthorized deploy" impact category since commit-status webhooks can flip a stack's deployability and status-based checks used to gate deploys.

### Likelihood Explanation
Requires the specific (but documented and supported) multi-organization Shipit configuration (`github:` keyed by org name, each with its own `webhook_secret`), and requires the attacker to be a legitimate admin/webhook-secret-holder for at least one of the configured organizations. This is a realistic multi-tenant setup and the attacker does not need any Shipit account, API token, or access to the victim organization — only a webhook secret they legitimately possess for their own org, which is an "unprivileged" position relative to the victim org's repositories.

### Recommendation
In `WebhooksController#verify_signature`, after computing `repository_owner` and verifying the signature, cross-check that `repository_owner` matches the organization/owner implied by `repository.full_name` (i.e., `full_name.split('/').first`) before dispatching to handlers, rejecting (422) any payload where the two disagree. Alternatively, have handlers resolve the target repository using the same trusted `repository_owner` value used for signature verification rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-administered, webhook secret `SECRET_A`) and `OrgB` (victim, contains stack `OrgB/victim-repo`), per the multi-org config format shown in `test/dummy/config/secrets_double_github_app.yml`.
2. As the admin of `OrgA`, the attacker knows `SECRET_A` (they configured it when installing/associating the GitHub App with their own org).
3. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(SECRET_A, body)>` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully using `SECRET_A`.
6. `PushHandler#process` resolves `stacks` via `repository.full_name` = `"OrgB/victim-repo"`, and calls `stack.sync_github` on the victim's stack — an action the attacker has no legitimate authorization to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
