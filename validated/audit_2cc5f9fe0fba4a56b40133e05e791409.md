### Title
Webhook organization used for signature verification is not bound to the repository the payload acts on, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify the request against by reading an **unauthenticated field of the same payload** it is about to verify. Once verification passes, the downstream event handlers resolve the *actual* repository/stack to act on using a **different** field from that same payload, with no check that the two fields refer to the same organization. On a multi-organization Shipit installation, this breaks the equality `organization that authenticated == organization whose repository is written`, letting anyone in possession of one organization's `webhook_secret` forge webhook events that act on stacks belonging to a completely different, unrelated organization configured on the same instance.

### Finding Description
`verify_signature` computes the organization used to pick the verifying secret from the request body itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GithubApp` instance holding that organization's own `webhook_secret`, and `verify_webhook_signature` HMACs the *entire raw body* with it: [3](#0-2) 

This only proves "this exact byte string was signed with organization X's secret" — it says nothing about which repository the payload's *content* should be applied to. Once the request passes, `Handler#repository_name` re-reads the repository target from a **different, unrelated JSON field**, `repository.full_name`, to resolve the stacks to operate on: [4](#0-3) 

`PushHandler` then syncs any matching, non-archived stack on that branch: [5](#0-4) 

Shipit explicitly supports multiple independent GitHub organizations/Apps on one installation, each with its own distinct `webhook_secret`, as shown by the multi-org secrets fixtures: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the target stacks) are two independent, attacker-controlled fields inside the same signed body, an actor who legitimately possesses organization A's `webhook_secret` (e.g., they administer their own org's GitHub App / Shipit hook, a routine and intended capability for onboarding an org) can craft a payload where `repository.owner.login = "OrgA"` (so the signature check passes) while `repository.full_name = "OrgB/some-repo"` (so the actual sync/status/action targets a stack belonging to an entirely different tenant organization, OrgB, that this actor has no rights to). No code path re-validates that the organization used for authentication matches the organization implied by the object being mutated.

### Impact Explanation
This crosses a tenant/repository trust boundary that Shipit is documented to rely on the webhook signature to enforce: each org's secret should only authorize events for that org's own repositories. Breaking this binding lets a legitimately-onboarded-but-different-organization actor forge `push`, `status`, `check_suite`, or `pull_request` events for a victim organization's stacks — injecting fabricated commit statuses, triggering `GithubSyncJob`/`CacheDeploySpecJob` runs, or manipulating deployability/merge-status data for stacks the attacker does not own or have any GitHub permissions on. Depending on stack continuous-deployment configuration, this can result in unauthorized state changes feeding directly into the deploy pipeline for a repository outside the attacker's authorization scope.

### Likelihood Explanation
Any Shipit deployment hosting more than one GitHub organization (a supported and documented configuration) is affected. The only precondition is administrative control of one organization's own webhook configuration/secret — a routine, intended capability for org onboarding, not a stolen credential or a privileged Shipit account. Crafting the divergent `repository.owner.login` / `repository.full_name` payload requires no special access beyond that.

### Recommendation
In `WebhooksController#verify_signature` / `Shipit::Webhooks::Handlers::Handler`, ensure the organization used to select the verifying `webhook_secret` is the same one that owns the repository referenced in the rest of the payload (e.g., verify `repository.full_name`'s owner segment matches `repository_owner`, or reject payloads where a `Repository` record's known organization differs from the authenticating organization) before dispatching to handlers.

### Proof of Concept
1. Attacker administers GitHub org `OrgA` with its own Shipit GitHub App and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`, `ref = "refs/heads/master"`, `after = "<arbitrary sha>"`
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` → `"OrgA"`, fetches `OrgA`'s `GithubApp`, and the signature check passes.
5. `PushHandler#process` resolves `repository_name` → `"OrgB/victim-repo"`, finds the matching `Repository`/`Stack`s for `OrgB`, and enqueues `GithubSyncJob` for a stack the attacker has no legitimate authorization over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
