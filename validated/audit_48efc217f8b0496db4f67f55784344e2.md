### Title
Webhook signature verification is keyed by attacker-controlled `repository.owner.login`, letting a payload forged under an unsecured org write events into a different, secured repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify against using `repository_owner`, a value read directly out of the unauthenticated JSON body. `GitHubApp#verify_webhook_signature` then unconditionally trusts the request (`return true unless webhook_secret`) when that org has no `webhook_secret` configured. Every event handler, however, resolves the target `Repository`/`Stack` to write into using a *different* field of the same payload: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. These two fields are never checked for consistency.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner)` to obtain a `GitHubApp`, then verifies the `X-Hub-Signature` HMAC against that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` bypasses verification entirely if that organization's config has no secret set: `return true unless webhook_secret`. [3](#0-2) 
- The documented/example multi-org configuration explicitly allows an org to be configured with `webhook_secret: null` (e.g. secondary/legacy orgs), demonstrating this is a supported real-world state, not a hypothetical. [4](#0-3) 
- After the (bypassed) signature check, every handler resolves the target repository from a **different, independently-controlled** field: `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, and `#stacks` looks up `Repository.from_github_repo_name(repository_name)`. [5](#0-4) 
- Handlers such as the push and status handlers act directly on this looked-up stack/repository without re-validating that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used for the signature check. [6](#0-5) 

The binding that should hold is: **organization that authenticated the request == organization owning the repository being written to**. Because the "authenticating" organization is read from `repository.owner.login`/`organization.login` while the "written" repository is read from the independent `repository.full_name` field, an attacker who can identify (or guess) any org configured in `Shipit.github` with a blank `webhook_secret` can:
1. Set `repository.owner.login` (or top-level `organization.login`) to that unsecured org, so `verify_signature` short-circuits to `true` with no HMAC check at all.
2. Set `repository.full_name` to any *other* tracked repository (belonging to an org that does have a `webhook_secret` configured).
3. Send an arbitrary, unsigned event body (`push`, `status`, `check_suite`, `membership`, etc.) that is processed as if it legitimately originated from GitHub for that other, secured repository.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written," per the scan rubric. Concretely, an unprivileged network attacker (no `ApiClient` token, no GitHub write access, no webhook secret knowledge) can forge webhook payloads for any Shipit-tracked repository as long as at least one configured GitHub org in the multi-tenant install has no `webhook_secret` set. Since commit `status` events write `state`/`context`/`target_url` straight from the payload onto a `Commit` belonging to the targeted (secured) repository, this can be used to forge a passing CI status on an attacker-chosen commit, which the merge queue and deploy CI-gating logic (`ci.require`) rely on to permit merges/deploys — i.e., it can produce an **unauthorized merge**, one of the enumerated Critical impacts.

### Likelihood Explanation
Any Shipit deployment onboarding more than one GitHub organization/App is documented to potentially leave `webhook_secret` unset for some orgs (shown directly in the shipped `secrets.development.shopify.yml` template and `test/dummy/config/secrets.test.json` fixture), and nothing in the code prevents this misconfiguration or cross-checks the owner used for auth against the repo actually written. The only prerequisite is knowledge (or guessing, since org names are usually public) of one such organization slug in the install; no credentials, tokens, or repository access are required.

### Recommendation
Bind the two identities together: after resolving `repository_owner` for signature verification, also require that `payload.dig('repository', 'full_name')` (or `organization.login` for org-scoped events) actually belongs to `repository_owner`, and reject the request otherwise. Additionally, do not implicitly treat a missing/blank `webhook_secret` as "verification passes" — require a secret to be configured for every organization able to also own tracked repositories, or explicitly disable inbound webhook processing for organizations with no secret.

### Proof of Concept
Given a Shipit install with two configured GitHub orgs, `unsecured-org` (no `webhook_secret`) and `secured-org` (webhook_secret set, owns tracked repo `secured-org/prod-app`):

```
POST /github/webhooks
X-Github-Event: status
(no valid X-Hub-Signature required because unsecured-org has no secret)

{
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/prod-app"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```

`verify_signature` computes `repository_owner = "unsecured-org"`, finds no `webhook_secret` for it, and returns `true` unconditionally. `StatusHandler`/`Handler#repository_name` then resolves the target stack via `full_name => "secured-org/prod-app"` and writes a forged `success` status onto the victim commit in `secured-org`'s repository, satisfying `ci.require` checks used to gate merges/deploys for that repository — without ever presenting a valid signature for `secured-org`.

**Note on verification limits:** I was not able to fully trace, within the available index, the exact downstream code path that consumes `Commit::Status` records to gate the merge queue's "safe to merge" decision (e.g. the merge-request/merge-queue models), so the precise mechanics of turning a forged status into an actual unauthorized merge action are inferred from the `ci.require` documentation and status-handling test rather than confirmed line-by-line in the merge queue implementation. A full Devin session with complete repository access would be needed to confirm that exact chain end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
