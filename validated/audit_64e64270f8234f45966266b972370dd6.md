### Title
Unhandled `throw` inside async DB-query callback while evaluating a `'definition template'` address-definition clause causes an uncaught exception that crashes the validating node - (File: `ocore--019/definition.js`)

### Summary
`ALPINE-CVE-2020-36222` is a DoS caused by an assertion failure that fires while `slapd` validates externally supplied `saslAuthzTo` data, crashing the LDAP daemon instead of returning a normal validation error. The equivalent bug class in `ocore` is code that, while validating attacker-controlled data (a unit, an address definition, an AA trigger, etc.), reaches a `throw Error(...)` from inside an asynchronous callback instead of returning a graceful validation error through the `cb`/`callback` chain. Because the throw happens after the synchronous call stack has already unwound (it fires from a `conn.query` callback), it cannot be caught by any `try/catch` around the original call and surfaces as an uncaught exception, crashing the Node.js process for every node that processes the malicious data.

### Finding Description
`validateAuthentifiers`/`validateDefinition` in `definition.js` implement the address-definition/oscript-like evaluator that every unit author's signature is checked against. One of the supported operators is `'definition template'`, which looks up a previously posted unit's `definition_template` message and inlines it: [1](#0-0) 

```
case 'definition template':
    // ['definition template', ['unit', {param1: 'value1'}]]
    var unit = args[0];
    var params = args[1];
    conn.query(
        "SELECT payload FROM messages JOIN units USING(unit) \n\
        WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND +sequence='good' AND is_stable=1",
        [unit, objValidationState.last_ball_mci],
        function(rows){
            if (rows.length !== 1)
                throw Error("not 1 template");
            ...
```

The lookup filters only by `unit=? AND app='definition_template'`; it does not verify that the referenced unit contains exactly one `definition_template` message. Nothing in the validation of that referenced unit's own messages restricts the *number* of `definition_template` messages a single unit may carry, so an attacker can post one ordinary unit containing zero or more than one `app: 'definition_template'` message. Once that unit is stable, *any* address whose definition contains `['definition template', [that_unit, {...}]]` will, on every subsequent signature-verification pass (i.e., every time a unit signed by that address is validated by any node on the network), execute this query and hit `rows.length !== 1`, throwing synchronously inside the asynchronous `conn.query` callback.

The same evaluator contains several other `throw Error(...)` statements reached from async callbacks under attacker influence, e.g. the `'address'` case at: [2](#0-1) 
and the analogous "more than 1 address definition" assertions, illustrating this is a systemic pattern in the address-definition evaluator rather than an isolated typo.

Because these `throw`s occur inside DB-callback closures (not in the synchronous portion of `evaluate`), they are not converted into a `cb(errorMessage)` validation failure the way the rest of the evaluator handles malformed input (e.g. `getFilterError`, `complexity` checks). Node.js has no way to route this back to the caller's promise/callback chain, so it becomes an uncaught exception. Unless the top-level event loop has a domain/`process.on('uncaughtException')` handler that keeps the process alive (only two matches exist in `network.js`, unrelated to the validation worker path), the node process crashes.

### Impact Explanation
Any full/hub node that validates a unit signed by an address using the crafted `'definition template'` reference will crash while performing ordinary unit validation - this is not a peer-trust or operator-only condition, it is triggered by an ordinary, unprivileged unit author defining an address (or an AA/private-payment counterparty using such an address) and then getting any counterparty's node to validate a signature against it. Because validation crashes rather than rejecting the unit, affected nodes are knocked offline, preventing them from confirming new units and creating a live network-wide denial-of-service / consensus-availability failure, matching the "network unable to confirm new units" impact criterion.

### Likelihood Explanation
The prerequisite (posting a unit with 0 or ≥2 `definition_template` messages, then referencing that unit from an address definition) requires only two ordinary, unprivileged unit postings — no elevated trust, no malicious peer/node, and no protocol-level attack. This is well within reach of a single attacker-controlled wallet.

### Recommendation
- Replace the `throw Error("not 1 template")` (and the sibling `throw` statements in the `evaluate` functions of `definition.js`, such as the `'more than 1 address definition'` and `'more than 1 template'` cases) with a call to `cb2(false)` / `cb("invalid definition template reference")` so malformed/ambiguous template references are treated as ordinary validation failures.
- Additionally enforce, at unit-validation time, that a unit may contain at most one `definition_template` message (or make the `SELECT` in `definition.js` deterministic, e.g. `ORDER BY message_index LIMIT 1`) so the "not 1 template" condition can never occur on validated data.
- Wrap the DB-query callbacks in the address-definition evaluator with try/catch that funnels any exception into `cb`/`cb2` as a validation error, ensuring internal invariant violations never propagate to an uncaught exception during untrusted-input processing.

### Proof of Concept
1. Attacker posts unit `U1` containing two messages with `app: "definition_template"` (arbitrary template payloads), which passes existing validation since there is no uniqueness check on the count of such messages per unit, and `U1` becomes stable.
2. Attacker (or anyone) creates/uses an address `A` whose definition includes `['definition template', ['U1', {}]]`.
3. Attacker sends any unit signed by address `A` (e.g., a normal payment) to the network.
4. Every node that validates this unit runs `Definition.validateAuthentifiers` → `evaluate` → the `'definition template'` case in `definition.js:806-818`; the `conn.query` callback receives `rows.length === 2`, executes `throw Error("not 1 template")` inside the async callback, and the process crashes with an uncaught exception, taking the node offline.

Note: I was not able to fully verify within the available tool budget (a) whether some other layer restricts the number of `definition_template` messages allowed per unit, and (b) whether `network.js`'s `uncaughtException` handler (only two references found, contents not inspected) intercepts this specific crash path and prevents process termination. These points should be confirmed by directly reading `writer.js`/`validation.js`'s `definition_template` handling and the `uncaughtException` handler in `network.js` before treating this as fully confirmed.
