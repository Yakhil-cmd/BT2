### Title
Webhook signature verification uses an org key selected from an unverified payload field, letting a multi-org Shipit installation process arbitrary-repository events under another organization's identity - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit configuration (`secrets.github` keyed by organization, as documented in `config/secrets.development.example.yml`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification by reading `repository_owner`, which is derived directly from the **unverified** raw JSON body, before the signature has actually been validated. Once the signature check passes (using the secret belonging to whatever organization the attacker names), the `create` action goes on to process the **entire** payload, including `repository.full_name`, via `Handler#stacks` / `Repository.from_github_repo_name`, with no re-check that the repository actually belongs to the organization whose secret was used to authenticate the request.

### Finding Description
`Shipit.github(organization: repository_owner)` and `verify_webhook_signature` are keyed off `repository_owner`: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON payload (`repository.owner.login`), i.e. attacker-controlled content that is not yet covered by any verified signature at the point it's used to pick the verification secret: [2](#0-1) 

After signature verification succeeds, `create` re-parses the same raw body and hands the *entire* payload — including `repository.full_name`, a field never tied to the `repository_owner` field used for org selection — to registered handlers: [3](#0-2) 

Handlers resolve the target stacks purely from `payload.dig('repository', 'full_name')`, with no cross-check against the organization whose secret validated the request: [4](#0-3) 

`Repository.from_github_repo_name` does a case-insensitive lookup purely by `owner/name` string, again with no tie back to which GitHub App/organization authenticated the webhook: [5](#0-4) 

This breaks the binding: **organization that authenticated (via `repository.owner.login` + its `webhook_secret`) == repository that is written (via `repository.full_name`)**. The two fields are independent parts of the same unsigned JSON body and nothing enforces they refer to the same repository/org. Concretely, in the documented multi-org config (`config/secrets.development.example.yml` shows `github: someorg: ... webhook_secret: ...` / `someothergithuborg: ...`), an attacker who is an installer/owner of one configured organization (`org-A`, knows `org-A`'s `webhook_secret`) can send a POST to `/webhooks` with:
- `repository.owner.login` = `org-A` (so `verify_signature` picks `org-A`'s secret and the HMAC — computed over the attacker's own full raw body with the secret they legitimately possess — passes)
- `repository.full_name` = `org-B/some-repo`, `push`/`status`/`check_suite` event data referencing a stack Shipit tracks for `org-B`

Handlers act on `repository.full_name` and mutate state for `org-B`'s stack (e.g. `PushHandler` triggers `stack.sync_github`, `status`/`check_suite` handlers write commit statuses/check runs) even though the request was never signed by `org-B`'s GitHub App/secret.

### Impact Explanation
This lets an unprivileged-relative-to-org-B attacker (who only controls org-A's GitHub App webhook secret) inject or spoof webhook events (push/status/check_suite/pull_request/membership) against stacks belonging to a different organization configured on the same Shipit instance. Depending on handler, this can trigger unwanted `GithubSyncJob` runs, forge commit statuses/check-run state that gates CI-based deploy safety checks, or create bogus teams/memberships — all cross-organization/cross-repository writes performed without the correct organization's authentication. This matches the "cross-repository writes" / "unauthorized deploy" class of Critical impact, since it lets an authenticated-as-org-A actor cause writes attributed to org-B's repositories.

### Likelihood Explanation
Requires the deployment to run Shipit with **multiple** GitHub organizations configured (an explicitly documented, supported configuration in `config/secrets.development.example.yml`), and requires the attacker to control (own/administer) at least one such configured organization's GitHub App and thus its webhook secret. This is not a purely anonymous internet attack, but it does not require any Shipit session, `ApiClient` token, or `api_clients_secret`, or the *target* organization's credentials — only legitimate ownership of a second, differently-scoped organization sharing the same Shipit deployment.

### Recommendation
After computing the HMAC, verify that `repository.owner.login` (used to select the verifying secret) matches the owner encoded in `repository.full_name` (and any other repository-identifying payload field the handler will act on) before dispatching to handlers. Alternatively, resolve the target `Repository`/`Stack` using only the organization that was cryptographically verified, and reject/ignore events whose `repository.full_name` owner does not match.

### Proof of Concept
1. Deploy Shipit with multi-org config: `github: org-a: {webhook_secret: SECRET_A, ...}` and `github: org-b: {webhook_secret: SECRET_B, ...}`, each with a Shipit stack tracking a repo under its respective org.
2. As the operator of `org-a` (knows `SECRET_A`), craft a `push` webhook payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/target-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(SECRET_A, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, verifies successfully using `SECRET_A` — which the attacker legitimately possesses.
5. `create` dispatches the full payload to `Shipit::Webhooks.for_event('push')`; `PushHandler#stacks` resolves stacks via `Repository.from_github_repo_name("org-b/target-repo")`, matching `org-b`'s real repository and calling `stack.sync_github(expected_head_sha: ...)` — a write against `org-b`'s stack performed without any signature from `org-b`.
