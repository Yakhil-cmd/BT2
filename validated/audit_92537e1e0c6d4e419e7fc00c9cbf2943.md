### Title
Webhook Signature Verified Against Attacker-Controlled `repository.owner.login` While Status/Push Handlers Act On A Different, Unverified Repository/Commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), a field taken directly from the untrusted JSON body. Once that check passes, the event handlers (`Shipit::Webhooks::Handlers::Handler`, `PushHandler`, `StatusHandler`) act on a *different* field of the same body — `repository.full_name` for stack lookup, and for `StatusHandler`, no repository field at all, only a bare commit `sha`. The signature therefore never actually binds "the organization that authenticated" to "the repository/commit that gets written," which is exactly the trust boundary this class of bug (illustrated by the `LendingPool` report: check one field, act on another, unhealthy/unauthorized state) breaks.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration to verify the HMAC with using: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This equality is the trust binding that must hold: `organization whose secret signed the request == organization that owns the repository the handler will mutate`.

Shipit supports hosting several GitHub organizations from one instance, each with its own independently configured `webhook_secret` (see the multi-org fixture [3](#0-2) ). An attacker who legitimately administers **any one** of those onboarded organizations (e.g. sets up their own GitHub App/webhook for "OrgA", which they are entitled to configure) knows OrgA's `webhook_secret` and can compute a valid `X-Hub-Signature` for **any payload body they want**, as long as `repository.owner.login == "OrgA"`.

Once `verify_signature` passes, the actual event handling reads a different field: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` uses these `stacks` (matched by `full_name`, not `owner.login`) to trigger a sync: [5](#0-4) 

Worse, `StatusHandler` does not scope by repository at all — it matches **any** `Commit` in the whole database whose `sha` equals the attacker-supplied value, across every stack/org hosted by the instance, and writes a status onto it: [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

So an attacker who owns "OrgA" (and thus its webhook secret) can sign a `status` webhook body with `repository.owner.login = "OrgA"` (passes `verify_signature`) but `sha` set to a real, public commit SHA belonging to a completely unrelated victim stack/organization ("OrgB/repo"), and `state: success`, `context: <the context OrgB's `ci.require` checks for>`. Shipit will create that status on the victim's commit, because `verify_signature` and `StatusHandler#process` never check the same identity.

### Impact Explanation
Forged, attacker-controlled commit statuses satisfy `ci.require` checks defined in the victim stack's `shipit.yml` (documented mechanism, see README `ci.require`). If continuous deployment/continuous delivery is enabled on the victim stack, or a human later clicks deploy trusting the (forged) green CI status, this results in an **unauthorized deploy** of a commit that never actually passed CI — a Critical-severity impact per the rubric ("unauthorized deploy, rollback or merge"). The same organization/repository mismatch also lets the attacker enqueue `GithubSyncJob`/`sync_github` operations against a victim stack via `PushHandler`, entirely outside the boundary the webhook signature was supposed to enforce.

### Likelihood Explanation
Requires only: (1) the Shipit instance to host more than one GitHub organization, each with its own webhook secret — a supported and documented configuration (`test/dummy/config/secrets_double_github_app.yml`); (2) the attacker to be a legitimate admin/owner of one of those organizations (unprivileged with respect to the victim organization — no Shipit account, no `ApiClient` token, no access to the victim repo needed); (3) knowledge of a real, public commit SHA of the victim stack, trivially obtained from GitHub's public API. No webhook secret of the victim org, no Shipit credentials, and no privileged access are required.

### Recommendation
Bind the verified signing organization to the resource actually mutated:
- In `WebhooksController`, after verifying the signature, re-derive `repository_owner` strictly from `repository.full_name`'s owner segment (not a separate `owner.login`/`organization.login` field) so both checks agree on the same value, and reject if they diverge.
- In `Shipit::Webhooks::Handlers::Handler`/`StatusHandler`, scope the affected `Commit`/`Stack` lookup by the repository that was actually authenticated (i.e., require `commit.stack.repository.owner == verified_organization`), instead of matching `Commit` globally by `sha` alone.

### Proof of Concept
1. Configure/onboard two GitHub orgs on one Shipit instance: `OrgA` (attacker-administered) and `OrgB` (victim), each with distinct `webhook_secret`s, per the supported multi-org config shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, using OrgA's known webhook secret, computes `X-Hub-Signature` (`sha1=HMAC(OrgA_secret, body)`) for a crafted `status` event body:
```json
{
  "sha": "<real sha of OrgB's tracked commit, e.g. from GitHub API>",
  "state": "success",
  "context": "<context required by OrgB's shipit.yml ci.require>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully (attacker knows OrgA's secret) — see [1](#0-0) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which ignores `repository` entirely and matches `Commit.where(sha: params.sha)` — see [6](#0-5) , creating a forged success status on OrgB's commit despite the signature only having proven authorization for OrgA.
