This confirms the pattern: every sibling handler scopes lookups through `stacks` (which is derived from `Repository.from_github_repo_name(repository_name)`) — `PushHandler#process` uses `stacks.not_archived.where(branch:)`, `CheckSuiteHandler#process` uses `stacks.where(branch:).each { |stack| stack.commits.where(sha:) }`, and `PullRequest::OpenedHandler` scopes via `repository.review_stacks`. `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` globally with no repository/stack filter at all.### Title
Cross-tenant status forgery via un-scoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone and writes a `Status` to every matching row, without filtering by the repository/organization that authenticated the webhook. Because `sha` is a content-addressed Git hash that is fully reproducible from public commit metadata (tree, parents, author/committer, timestamps, message), any Shipit tenant that legitimately controls a registered repository/org can forge a `status` webhook, signed with their own genuine `webhook_secret`, that names a `sha` colliding with a commit tracked under a completely different tenant's stack, and get a `Status` row written against the victim's commit.

### Finding Description
The binding that should hold is: `Status.commit.stack_id == Repository.from_github_repo_name(payload.repository.full_name).stacks` — i.e., a status may only attach to commits belonging to the stack(s) of the repository that authenticated the webhook. In `StatusHandler`, this equality is violated: [1](#0-0) 

`process` calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never touches `stacks` (the `Repository.from_github_repo_name(repository_name)&.stacks` helper defined on the base `Handler` class and used by every sibling handler): [2](#0-1) 

Contrast with the sibling handlers in the same directory, all of which scope their lookups through `stacks`/`repository`:
- `PushHandler#process`: `stacks.not_archived.where(branch:).find_each { ... }` [3](#0-2) 
- `CheckSuiteHandler#process`: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [4](#0-3) 
- `PullRequest::OpenedHandler`: resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [5](#0-4) 

`StatusHandler` is the sole outlier that queries the global `Commit` table by `sha` alone, and the `commits` table index/uniqueness is only on `(stack_id, sha)` [6](#0-5) , confirming `sha` is not unique or namespaced at the database level — two `Commit` rows under different `stack_id`s can share the same `sha`.

`WebhooksController#verify_signature` only authenticates *which organization* sent the request (`Shipit.github(organization: repository_owner)`); it never confirms the payload's `sha`/repository actually belongs to that organization's tracked repositories before the handler runs [7](#0-6) . The handler's `stacks` helper exists precisely to bridge that gap, but `StatusHandler` bypasses it.

**Exploit flow**: On a Shipit installation configured for multiple GitHub organizations (a documented, supported configuration — see `docs/setup.md` "Using Multiple Github Applications"), an attacker who legitimately owns/administers Org A (registered in Shipit with its own genuine `webhook_secret`) can:
1. Take any public commit merged into Victim Org B's tracked stack (sha, tree, parents, author/committer identities and dates, message are all public).
2. Reproduce an identical commit object (and thus identical `sha`) via `git commit-tree`/`git commit --date` replay, since Git shas are pure content hashes of these fields.
3. Craft a `status` event JSON body naming Org A's own `repository.full_name` and the replayed `sha`, and HMAC-sign it with Org A's own `webhook_secret` (which they legitimately know).
4. POST it to `/webhooks`. `verify_signature` succeeds because the signature matches Org A's own secret and Org A's own repository name.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the row under Victim Org B's stack (since `sha` collides), and calls `commit.create_status_from_github!(params)`, writing a forged `Status` (e.g., `state: success`) onto the victim's commit — even though the request never referenced Org B or its repository.

Existing guards do not stop this: `verify_signature` authenticates the sender's own org, not the target commit's org; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not ownership; there is no `Repository`/`Stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
A `status` webhook that is fully attacker-authored and validly signed under Attacker Org A's own secret can mutate `Status` records belonging to Victim Org B's commit/stack, with no cross-org authorization check. Since `Status#after_create` calls `enable_ci_on_stack` and `schedule_continuous_delivery` [8](#0-7) [9](#0-8) , a forged `success` status can unblock the victim's merge/deploy pipeline gating logic (continuous delivery scheduling) for a commit the victim's own CI never actually verified. This is a payload for one repository mutating another's commit/stack state — matching the "Critical" impact category (cross-tenant state forgery / a payload for one repository mutating another's stack/commit without authenticating it). It is repeatable against any commit whose full metadata is public and any stack tracked in the same multi-tenant Shipit instance.

### Likelihood Explanation
Requires a Shipit deployment supporting multiple GitHub organizations/apps (a first-class, documented configuration), and requires the attacker to legitimately control at least one such registered org/repo (an attacker who is a genuine tenant, not necessarily the victim's collaborator). Given that, the attack cost is low: no GitHub secrets of the victim are needed, only public commit metadata and standard `git commit-tree`/`--date` replay to reproduce an identical sha, plus a single signed HTTP POST from the attacker's own legitimately-known secret. This is deterministic and repeatable against any sha the attacker chooses to replay.

### Recommendation
Scope `StatusHandler#process` through the authenticated repository's stacks/commits, mirroring `CheckSuiteHandler`, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, or otherwise join through `Commit#stack -> Stack#repository` and reject/ignore commits whose stack's repository does not match `repository_name` from the payload.
