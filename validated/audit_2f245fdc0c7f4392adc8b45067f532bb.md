Let me verify the webhook handlers and multi-org configuration to confirm impact.### Title
Webhook organization used for signature-secret selection is decoupled from the repository the payload writes to, allowing cross-organization webhook spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-org Shipit deployments, `WebhooksController#verify_signature` picks *which* GitHub App/secret to validate against using `repository_owner` (`repository.owner.login` or `organization.login`) read straight out of the **unverified** JSON body, then verifies the *entire* raw body against that secret. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the selected org has no `webhook_secret` configured — a state explicitly supported and documented (`webhook_secret: # nil`) for any subset of orgs in a multi-tenant config. Because the field used to choose the verification key (`repository.owner.login`) is never cryptographically bound to the field later used to determine which repository/stack is actually acted upon (`repository.full_name`, read separately by `Handler#repository_name`), an attacker can forge a payload claiming `repository.owner.login` = an org with no secret while setting `repository.full_name` to a completely different (secured) org's repository. This is the same class of bug as the reported PLONK issue: a value that influences a downstream trust decision is not covered by the verification step that is supposed to authenticate the whole transcript.

### Finding Description
`WebhooksController#verify_signature` [1](#0-0)  resolves the app/secret to check against using an attacker-controlled field: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats a missing secret as automatically valid: [3](#0-2) 

Shipit explicitly supports per-organization configuration, where each org can independently have (or lack) a `webhook_secret`, as shown in the documented multi-org config schema and shipped example secrets files: [4](#0-3) [5](#0-4) 

Once signature verification passes (trivially, because the chosen org has no secret), the request body is dispatched to handlers, which resolve the *actual* target repository from a **different** JSON field, `repository.full_name`, never involved in the verification decision: [6](#0-5) 

Because `repository.owner.login` (used to select the verification key) and `repository.full_name` (used to resolve which stacks/repository the event acts on) are independent JSON fields with no cryptographic binding tying them together, an attacker who knows that at least one configured organization has no webhook secret can craft a forged payload with `repository.owner.login` set to that unsecured org while setting `repository.full_name` (and other content) to point at a different, properly-secured organization's tracked repository. `verify_signature` will look up the unsecured org's `GitHubApp`, get `webhook_secret == nil`, and `verify_webhook_signature` returns `true` unconditionally — regardless of the payload's actual content, including the spoofed `repository.full_name`. The forged event is then processed as if it legitimately originated from the targeted secured repository.

### Impact Explanation
Depending on which handled event type is forged, an unauthenticated network attacker (no session, no API token, no repository access required) can:
- Trigger `GithubSyncJob` for a targeted stack via a forged `push` event.
- Inject fake commit `status` events, potentially marking a commit as CI-green for a stack that gates deploys/merges on required statuses.
- Inject fake `check_suite` events.
- Manipulate `pull_request`/`membership` derived state for a repository/stack they do not control.

This can feed into Shipit's continuous-delivery/merge-queue logic (status-gated deploys, merge-queue advancement) for repositories belonging to organizations that *are* properly secured, purely because a co-tenant organization in the same Shipit installation left its webhook secret unset — a state the engine explicitly allows and documents per-organization. This crosses the "organization that authenticated versus the repository that is written" trust boundary called out as in-scope, and can lead to an unauthorized deploy/merge triggered off forged CI/push signals.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (documented, supported feature), and (2) at least one configured organization with no `webhook_secret` (also documented/shipped as a valid, optional configuration in `config/secrets.development.shopify.yml` and `config/secrets.development.example.yml`). This is a realistic deployment pattern (e.g., a low-priority/sandbox org left unconfigured while the main org is secured), and requires no credentials, sessions, or repository access from the attacker — only knowledge or discovery of which org lacks a secret and the target repository's `full_name`.

### Recommendation
Bind the organization used for signature verification to the actual data acted upon:
- Never treat "no secret configured" as automatically valid for an org whose payload fields are used to resolve a *different* stack/repository. At minimum, cross-check that `repository.full_name`'s owner matches the organization whose secret was used for verification before dispatching to handlers.
- Consider requiring `webhook_secret` to be mandatory for any organization used in a multi-tenant configuration, or reject any webhook if the resolved `repository_owner` does not match the owner encoded in `repository.full_name`.
- Preferably, do not use payload-driven (unauthenticated) `repository_owner`/`organization.login` to select the verification key at all; use context that is out of attacker control (e.g., a distinct URL/subpath, App/installation ID header) for each org's app endpoint.

### Proof of Concept
Setup: Shipit configured with two orgs — `unsecured-org` (no `webhook_secret`) and `secured-org` (repository `secured-org/critical-repo` tracked as a Shipit stack, `webhook_secret` properly set).

Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "secured-org/critical-repo"
  },
  "sha": "<commit-sha-of-critical-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
- `repository_owner` resolves to `"unsecured-org"` [2](#0-1) .
- `Shipit.github(organization: "unsecured-org")` returns a `GitHubApp` with `webhook_secret == nil`.
- `verify_webhook_signature` returns `true` unconditionally regardless of the bogus `X-Hub-Signature` [7](#0-6) .
- The `status` handler processes the payload against `secured-org/critical-repo` (via `repository.full_name`), recording a forged "success" status on the commit for the secured repository/stack, without ever validating anything against `secured-org`'s real webhook secret.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
