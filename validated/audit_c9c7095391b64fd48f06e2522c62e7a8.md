### Title
Deflationary (Fee-on-Transfer) ERC20 Tokens Drain Bridge Liquidity in Lock Mode — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` and `onERC20Received` (via `ERC20ServiceChain.requestValueTransfer`) both record the caller-supplied `_value` in the `RequestValueTransfer` event without verifying the actual token amount received by the bridge. When a fee-on-transfer (deflationary) ERC20 is used, the bridge receives `_value - fee` tokens but emits an event claiming `_value`. The counterpart bridge then releases the full `_value` to the recipient, draining tokens from the bridge's liquidity pool that were deposited by other users.

### Finding Description

**2-step path — `requestERC20Transfer`:**

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The `safeTransferFrom` pulls `_value + _feeLimit` from the caller. If the token charges a transfer fee, the bridge actually receives `(_value + _feeLimit) * (1 - fee_rate)`. However, `_requestERC20Transfer` is immediately called with the original `_value`, which is emitted verbatim in the `RequestValueTransfer` event. [1](#0-0) 

**1-step path — `onERC20Received` via `ERC20ServiceChain.requestValueTransfer`:**

```solidity
// ERC20ServiceChain.sol L44-47
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
```

The token's own `transfer` sends `_amount + _feeLimit` to the bridge (deducting the deflationary fee in transit), then immediately calls `onERC20Received` with the original `_amount`. The bridge has no way to detect the discrepancy. [2](#0-1) 

In both paths, `_requestERC20Transfer` emits `RequestValueTransfer` with `_value` as `valueOrTokenId`: [3](#0-2) 

The counterpart bridge operator observes this event and calls `handleERC20Transfer(_value)`, which in lock mode executes:

```solidity
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [4](#0-3) 

The destination bridge transfers the full `_value` from its liquidity pool, even though the source bridge only received `_value * (1 - fee_rate)`.

### Impact Explanation

In **lock mode** (`modeMintBurn = false`), the destination bridge holds a liquidity pool of tokens deposited by legitimate users. Each cross-chain transfer using a deflationary token silently drains `_value * fee_rate` tokens from this pool — tokens that belong to other users. Repeated transfers progressively deplete the pool, eventually causing legitimate withdrawals to revert with insufficient balance. This constitutes an unauthorized transfer of bridged assets belonging to other users.

In **mintBurn mode**, the source bridge burns `_value` tokens (which it may not fully hold), while the destination bridge mints the full `_value`. This inflates the circulating supply on the destination chain relative to what was actually burned on the source chain, breaking the 1:1 peg invariant.

### Likelihood Explanation

The bridge owner must first register the deflationary token via `registerToken`. Once registered, any unprivileged user can call `requestERC20Transfer` or `requestValueTransfer` to trigger the drain. The bridge owner may register such a token unknowingly (e.g., tokens that add fees via upgrades after registration, or tokens whose deflationary nature is not obvious). Each individual transfer causes a small, silent loss that accumulates over time.

### Recommendation

Measure the actual balance change before and after the `safeTransferFrom` / `transfer` call, and use the measured delta as the canonical transfer amount:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    // Derive actual _value and _feeLimit from actualReceived proportionally, or require exact match
    require(actualReceived == _value.add(_feeLimit), "fee-on-transfer token not supported");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, document that fee-on-transfer tokens must not be registered, and add a validation check in `registerToken` if feasible.

### Proof of Concept

1. Deploy a deflationary ERC20 token `DefToken` that charges a 1% fee on every `transfer`/`transferFrom`, deducted from the received amount.
2. Bridge owner calls `registerToken(defTokenAddr, counterpartDefTokenAddr)` on both bridges.
3. Bridge owner pre-funds the destination bridge with 1000 `DefToken` (lock mode liquidity).
4. Alice calls `requestERC20Transfer(defTokenAddr, bob, 100, 0, "")` on the source bridge.
   - `safeTransferFrom` pulls 100 tokens from Alice; bridge receives **99** (1 token fee deducted).
   - `RequestValueTransfer` event emits `valueOrTokenId = 100`.
5. Operator observes the event and calls `handleERC20Transfer(..., bob, defTokenAddr, 100, ...)` on the destination bridge.
   - Destination bridge calls `safeTransfer(bob, 100)` — Bob receives **99** (another 1% fee), destination bridge balance decreases by **100**.
6. Net result: source bridge received 99, destination bridge paid out 100. **1 token drained from destination bridge's liquidity per transfer.**
7. After 1000 such transfers, the destination bridge's liquidity pool is fully drained, and all subsequent legitimate withdrawals revert. [1](#0-0) [2](#0-1) [4](#0-3)
