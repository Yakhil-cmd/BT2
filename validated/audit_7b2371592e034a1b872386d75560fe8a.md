### Title
Cross-organization CI status forgery via unscoped `StatusHandler` webhook processing - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The Shipit webhook signature check verifies that a request payload was signed by *some* GitHub organization's webhook secret, but the org used for that check is picked from an attacker-controlled field (`repository.owner.login`) in the very payload being verified. Once the signature passes, several webhook handlers act on data that is not re-validated against that authenticated organization. `StatusHandler` in particular resolves its target purely by commit SHA, globally, with no repository/stack scoping at all. This lets an operator of one onboarded GitHub organization forge a webhook that is correctly signed with their own org's secret, yet mutates CI status state for any commit belonging to any other tenant/organization's stack in the same Shipit installation.

### Finding Description
`WebhooksController#verify_signature` selects which organization's secret to check the HMAC signature against using a field taken from the untrusted payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, i.e. a value the sender fully controls. Anyone who legitimately controls a GitHub organization/app installation onboarded into this Shipit instance knows or can obtain a validly signed payload for that org (their own real `webhook_secret`). The signature therefore only proves "this body was signed by organization X's secret" — it proves nothing about which *repository* or *stack* the body's other fields (`repository.full_name`, `sha`, `state`, …) are allowed to reference.

Once signature verification passes, `WebhooksController#create` dispatches the parsed body to all registered handlers for the event type: [3](#0-2) 

Most handlers at least scope themselves to a specific `Repository`/`Stack` via `repository.full_name`: [4](#0-3) 

But `StatusHandler` does not use `repository_name`/`stacks` scoping at all — it looks up commits **globally by SHA** and applies the attacker-supplied `state`/`description`/`target_url`/`context` directly: [5](#0-4) 

`Commit.where(sha: params.sha)` is not filtered by `stack_id`, `repository_id`, or the organization that was authenticated. `create_status_from_github!` then persists the status and fires downstream effects such as `schedule_continuous_delivery` and enabling CI on the stack: [6](#0-5) [7](#0-6) [8](#0-7) 

A `success` status also satisfies merge-queue gating, since `MergeRequest#all_status_checks_passed?` is computed purely from the commit's stored statuses: [9](#0-8) 

and `ProcessMergeRequestsJob` merges any pending merge request whose head passes those checks: [10](#0-9) 

**Binding broken:** *the organization that authenticated the webhook* ≠ *the repository/stack whose commit state is written*. The HMAC check authenticates "org X sent this bytes," but `StatusHandler` writes state for any commit SHA in the entire multi-tenant database, regardless of which org's secret validated the request.

### Impact Explanation
This is a cross-repository write: an attacker who legitimately controls one onboarded GitHub organization (a normal, unprivileged Shipit tenant, not a Shipit admin, GitHub org admin of the victim, or holder of the victim's secret) can forge a `status` event, correctly signed with their own org's webhook secret, targeting the SHA of a commit that belongs to a completely different organization's stack. If continuous delivery is enabled on the victim stack, injecting a fabricated `success` status can trigger `schedule_continuous_delivery`, i.e., an **unauthorized deploy**. If the victim has a merge queue, the same forged status can satisfy `all_status_checks_passed?` and cause `ProcessMergeRequestsJob` to **merge a pull request** that never actually passed CI — an **unauthorized merge**. Both outcomes match the Critical-impact categories (unauthorized deploy/merge, cross-repository writes) called out in scope.

### Likelihood Explanation
The only prerequisite is being an onboarded/legitimate GitHub organization tenant of the same Shipit instance (a routine, unprivileged position for any organization using a shared/multi-tenant Shipit deployment) — no `webhook_secret`/`api_clients_secret` of the *victim* org, no repository write access to the victim repo, and no Shipit session are required, satisfying the "unprivileged attacker" constraint. The target commit SHA of a victim's public repository/PR head is trivially obtainable from GitHub itself. The main uncertainty is whether the shared Shipit deployment in a given environment actually hosts multiple mutually-untrusted GitHub organizations; in a single-org deployment this bug has no cross-tenant blast radius, but the code contains no repository/stack scoping to prevent it in a multi-org one.

### Recommendation
Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository/stack indicated by `repository.full_name` in the payload, and cross-check that this repository actually belongs to the organization that was cryptographically authenticated in `WebhooksController#verify_signature`, e.g. `stacks.joins(:repository).where(repositories: { owner: repository_owner })`, rejecting/ignoring events where the signing organization does not match the resource being mutated.

### Proof of Concept
1. Attacker organization "attacker-org" is a legitimate, unprivileged tenant with its own GitHub App installation and webhook secret configured in this Shipit instance.
2. Attacker crafts a `status` webhook body:
   ```json
   {
     "sha": "<head-sha-of-victim-org/victim-repo-PR>",
     "state": "success",
     "context": "ci/required",
     "repository": { "owner": { "login": "attacker-org" } }
   }
   ```
3. Attacker signs the raw body with `attacker-org`'s real webhook secret (their own, legitimately obtained) and POSTs it to `/github/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, and the signature check passes because it was in fact signed by that org's real secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no owner/stack filter, finds the victim's commit, and creates a `success` `Status` on it [11](#0-10) .
6. Depending on victim stack configuration, this either enables continuous delivery to fire an unauthorized deploy, or lets `ProcessMergeRequestsJob` merge a pending PR on the victim's repository whose real CI never passed.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
