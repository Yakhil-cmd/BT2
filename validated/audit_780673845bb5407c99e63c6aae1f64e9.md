### Title
AA trigger execution order is attacker-selectable via unit `level`, enabling front-running of balance/ratio-dependent AA logic (e.g. AMM/rebalance-style AAs) - (File: aa_composer.js, main_chain.js, writer.js)

### Summary
Autonomous Agent (AA) triggers within the same main-chain index (MCI) are executed in a strictly deterministic order — sorted by `(mci, level, unit, address)` — rather than by real-world arrival time. Since `level` of a unit is simply `max(level of chosen parent_units) + 1`, and unit authors are free to choose which free/eligible parents to build on, an attacker can deliberately keep their own unit's `level` low (or the target's high) to guarantee their trigger unit sorts before a victim's trigger unit within the same MCI, even if the victim's unit was broadcast first. This is the ocore analog of an EVM proposer/searcher reordering (front-running) transactions within a block: any AA that reads `balance[...]` or asset ratios at trigger time (e.g. a Uniswap-style constant-product/ratio-based market maker or a treasury/AMO-style rebalancer built with oscript, as demonstrated in the codebase's own `uniswap_like_market_maker.oscript` sample) can have its expected pre-state manipulated by an attacker who inserts a swap/withdraw/deposit trigger immediately before the victim trigger in the deterministic execution order.

### Finding Description
`aa_composer.handleAATriggers()` selects pending triggers with:
```
ORDER BY aa_triggers.mci, level, aa_triggers.unit, address
``` [4](#0-3) 
and `main_chain.js`'s `handleAATriggers()` collects triggers for a newly-stabilized MCI and explicitly comments that this order is "deterministic": [3](#0-2) 

The `level` field used for this ordering is computed purely from the unit's own `parent_units` choice:
```
function determineMaxLevel(...) { ... max(props.level over parent_units) ... }
function updateLevel(cb){ ... objNewUnitProps.level = max_level + 1; ... }
``` [5](#0-4) 
There is no protocol rule tying `level` to wall-clock broadcast time or requiring a unit to include the most recent free tips as parents — an author may pick any valid, non-conflicting set of parent units (subject to normal DAG consistency rules), including older/shallower ones, to keep their own `level` low.

Because AA execution ordering is `(mci, level, unit, address)` and both the attacker's and victim's units can land in the *same* MCI (since MCI stabilization batches many still-unstable units together), an attacker who observes a victim's not-yet-stable AA trigger unit in the DAG (analogous to observing a pending mempool transaction) can craft a competing unit that (a) targets the same AMM/rebalancer AA, (b) chooses parents that keep its `level` at or below the victim's, and (c) is thus guaranteed to execute first when the MCI stabilizes and `handleAATriggers` runs. This lets the attacker manipulate the AA's balance-derived state (e.g., a pool's asset ratio, as in the `uniswap_like_market_maker.oscript` sample which computes `$current_ratio = $asset_balance / $bytes_balance` at trigger time) right before the victim AA executes a ratio-dependent check, then reverse the manipulation in a follow-up trigger placed immediately after — exactly the sandwich/MEV pattern described in the external xETH `AMO2.sol` rebalance-slippage report, but achieved deterministically via level selection rather than via a searcher/miner colluding on block order.

### Impact Explanation
Any deployed AA (asset issuer's market-maker/AMM AA, a treasury rebalancer AA, or any AA that reads `balance[...]`/computes ratios/prices from its own current balances to decide payout or accept/reject an operation) is vulnerable to sandwich-style manipulation by an ordinary, unprivileged unit poster. This can lead to direct extraction of value from the AA's balances (arbitrage profit at the AA's/other users' expense), analogous to the unauthorized value transfer/arbitrage impact validated in the original finding, since the AA's invariant checks are computed against balances that can be forced into an attacker-favorable state immediately before the check executes.

### Likelihood Explanation
Any unprivileged address can post a unit; choosing parents to control `level` requires no special privilege, only awareness of the victim's pending trigger unit and its `parent_units`/`level`, both of which are public before stabilization. Given ocore's DAG has multiple free tips available for extended periods before consolidation, and any user can freely pick shallow parents, this ordering manipulation is practically achievable for an attentive attacker monitoring the network for balance-ratio-sensitive AA triggers.

### Recommendation
AA authors writing balance/ratio-dependent logic (AMMs, rebalancers, price oracles derived from AA balances) should not treat `balance[...]` observed at trigger time as manipulation-resistant; ocore itself could mitigate the general class by (1) documenting this ordering property prominently for AA authors, (2) considering commit-reveal or TWAP-style state accumulation patterns for sensitive computations, or (3) evaluating whether trigger ordering could incorporate a less attacker-influenced tie-breaker than raw `level` for units that could plausibly collide within one MCI. At minimum, this front-runnable-ordering behavior of `handleAATriggers`/`level` should be explicitly called out in AA-authoring security guidance, since it enables the same slippage/ratio-check bypass pattern documented in the referenced external finding.

### Proof of Concept
1. Deploy an AMM-style AA (e.g., the repository's own `uniswap_like_market_maker.oscript` sample) that computes `$current_ratio = $asset_balance / $bytes_balance` from its live `balance[...]` at trigger time to price deposits/swaps.
2. Attacker observes a victim's unstable trigger unit `U_v` (built on parent `P_v`, giving `level_v`) heading to the same market-maker AA within the not-yet-stabilized MCI.
3. Attacker crafts unit `U_a` targeting the same AA, selecting parent(s) with `level ≤ level_v − 1` so that `level_a < level_v` (or, if `level_a == level_v`, relying on `unit` (hash) tie-break, which is unpredictable but can be tried multiple times/units), ensuring `(mci, level_a, U_a) < (mci, level_v, U_v)` in the sort order used by `aa_composer.handleAATriggers`.
4. When the MCI containing both units stabilizes, `main_chain.js` `handleAATriggers()` inserts both triggers into `aa_triggers`, and `aa_composer.handleAATriggers()` processes `U_a` before `U_v` per the `ORDER BY mci, level, unit, address` query.
5. `U_a`'s trigger moves the pool ratio to a value favorable to the attacker; `U_v`'s subsequent trigger executes against this manipulated ratio, producing a mispriced payout captured by monitoring/attacker follow-up triggers — mirroring the sandwich/arbitrage profit demonstrated in the external xETH `AMO2.sol` report.
