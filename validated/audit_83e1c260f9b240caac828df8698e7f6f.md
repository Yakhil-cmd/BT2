### Title
Stale `transitionResultCache` After Reorg Corrupts Validator Set for Committee Selection and Reward Distribution — (`kaiax/valset/impl/transition.go`, `execution.go`, `getter.go`)

---

### Summary

`transitionResultCache` is keyed by block number (`uint64`) only. Neither `RewindTo` nor `RewindDelete` invalidates it. After a reorg that replaces canonical block N with a different block N', the cache entry for block N+1 retains the `TransitionResult` computed from the evicted chain, causing wrong validators to be used for committee selection and reward distribution at block N+1.

---

### Finding Description

**Cache structure and population:**

`transitionResultCache` is an LRU keyed by `uint64` block number. [1](#0-0) 

When block N is inserted, `PostInsertBlock` → `postInsertBlockPermissionless` calls `getTransitionResult(N+1, parentStatedb)` to warm the cache: [2](#0-1) 

`getTransitionResult` checks the cache first and returns immediately on a hit, without recomputing: [3](#0-2) 

**No invalidation on reorg:**

`RewindTo` only trims validator vote block numbers and clears `validatorVoteBlockNumsCache`. It does **not** touch `transitionResultCache`: [4](#0-3) 

`RewindDelete` only deletes the council entry for the evicted block. It also does **not** touch `transitionResultCache`: [5](#0-4) 

The only place `transitionResultCache` is purged is `Start()`, which runs only at node startup: [6](#0-5) 

**Stale cache survives the reorg:**

After the reorg inserts N', `postInsertBlockPermissionless(N')` calls `getTransitionResult(N+1, statedb_from_N')`. Because `transitionResultCache` already holds an entry for key `N+1` (computed from the evicted block N), `getTransitionResult` returns the stale result immediately and **does not overwrite it**: [7](#0-6) 

**Stale result consumed for block N+1 production:**

When block N+1 is being produced, `qualifiedFromHeaderOrState(N+1)` calls `GetHeaderByNumber(N+1)`, which returns `nil` (block N+1 does not exist yet). It falls back to `getQualifiedValidators` → `getNodes` → `transitionResultCache.Get(N+1)` → stale `TransitionResult.Nodes`: [8](#0-7) [9](#0-8) 

**`VerifyHeader` does not protect against this:**

`VerifyHeader` calls `getQualifiedValidators(num)` which hits the same stale cache. The block producer writes stale validators into the header; the verifier checks against the same stale cache and accepts the block. Both sides are consistently wrong: [10](#0-9) 

---

### Impact Explanation

The stale `TransitionResult.Nodes` at block N+1 causes:
- **Wrong committee selection**: the proposer and committee members for block N+1 are drawn from the pre-reorg validator state, not the post-reorg canonical state.
- **Wrong reward distribution**: block rewards are distributed to the wrong set of validators.
- **Potential consensus divergence**: nodes that processed the reorg differently (e.g., one node restarted and has a cold cache) compute the correct validator set and may reject blocks that stale-cache nodes accept.

The corruption is durable for block N+1 — the stale validators are embedded in the header and accepted by `VerifyHeader` — and only self-corrects at block N+2 (whose cache entry is computed from N+1's state, which is correct).

---

### Likelihood Explanation

Istanbul BFT provides finality, making reorgs rare. However, they are not impossible: a network partition can cause two honest sub-networks to finalize different blocks at the same height. When the partition heals, one chain wins and the other is rewound. This is a legitimate P2P sync path that does not require Byzantine validators or majority collusion. The `reorg` function in `blockchain/blockchain.go` confirms the codebase explicitly handles this case.

---

### Recommendation

In `RewindTo` (and/or `RewindDelete`), remove all `transitionResultCache` entries at or above the rewind target block number. Since the LRU does not support range deletion, the simplest safe fix is to purge the entire cache on any reorg:

```go
func (v *ValsetModule) RewindTo(block *types.Block) {
    trimValidatorVoteBlockNums(v.ChainKv, block.Header().Number.Uint64())
    v.validatorVoteBlockNumsCache = nil
    v.transitionResultCache.Purge() // invalidate on reorg
}
```

A more targeted fix would key the cache by `(blockNumber, blockHash)` or by block hash alone, so a reorg naturally produces a cache miss for the new canonical block.

---

### Proof of Concept

1. Start a Kaia node with permissionless fork enabled.
2. Insert block N (hash H_N) with validator set V_N. `postInsertBlockPermissionless` warms `transitionResultCache[N+1]` with `TransitionResult` derived from V_N.
3. Simulate a reorg: insert a competing block N' (hash H_N', different validator state V_N') at the same height. The blockchain calls `RewindTo` (which does **not** clear `transitionResultCache`) then inserts N'.
4. `postInsertBlockPermissionless(N')` calls `getTransitionResult(N+1, statedb_N')` — cache hit returns stale result from step 2.
5. Call `GetQualifiedValidators(N+1)`. Assert it equals V_N (stale), not the correct result derived from V_N'. The assertion passes, confirming the corruption.
6. Observe that block N+1 is produced and accepted with the wrong validator set embedded in its header, and rewards are distributed to the wrong recipients.

```go
func (v *ValsetModule) getTransitionResult(num uint64, parentStatedb *state.StateDB) (*TransitionResult, error) {
	if num == 0 {
		return nil, errParentHeaderNotFound(num)
	}
	if cached, ok := v.transitionResultCache.Get(num); ok {
		return cached.(*TransitionResult), nil
	}

	// Read ABv2(N-1) + apply transitions for block N
	parentHeader := v.Chain.GetHeaderByNumber(num - 1)
	if parentHeader == nil {
		return nil, errParentHeaderNotFound(num)
	}
	result, err := v.applyTransition(parentHeader, parentStatedb)
	if err != nil {
		return nil, err
	}
	v.transitionResultCache.Add(num, result)
	return result, nil
```
