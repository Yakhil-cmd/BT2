### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler#process` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target `Commit` rows solely by `sha`, with no check that the webhook's `repository` matches the repository that owns the matched commit's stack. Since git commit SHAs are content-addressed and are byte-for-byte preserved when a repository is forked or when an identical commit object is independently created, an attacker who owns a fork of the victim's repository can trigger a legitimately-signed webhook from their own fork that updates the *victim's* `Commit`/`Stack` and causes `Commit#add_status` to fire `Hook.emit(:commit_status, victim_stack, ...)` and `Hook.emit(:deployable_status, victim_stack, ...)` with attacker-controlled `state`/`description`/`target_url`/`context`.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:
`Repository.from_github_repo_name(payload.repository.full_name).stacks` (the stack that authenticated the inbound webhook) `== commit.stack` (the stack whose Hook.emit fires).

Code path:
- `WebhooksController#create` dispatches the raw parsed JSON to handlers after `verify_signature`, which only checks that the HMAC matches the `webhook_secret` configured for `Shipit.github(organization: repository_owner)` — this authenticates that *some* org's GitHub App produced the payload, but places no constraint tying the payload's `repository` to which `Commit`/`Stack` gets mutated. `app/controllers/shipit/webhooks_controller.rb:10-49`.
- `StatusHandler` declares a parameter schema that never requires or reads `repository` at all: `app/models/shipit/webhooks/handlers/status_handler.rb:7-18`.
- `StatusHandler#process` looks up commits purely by `sha`: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`. This contrasts with other handlers (e.g. `PullRequest::OpenedHandler`) that require `repository.full_name` and explicitly scope lookups via `Repository.from_github_repo_name(params.repository.full_name)` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:33-53`) and the base `Handler#stacks` helper which does the same (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) — `StatusHandler` bypasses this pattern entirely.
- `Commit#create_status_from_github!` calls `add_status`, which unconditionally uses `stack` (i.e. `commit.stack`, the DB-owning stack) to fire hooks: `Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status))` and `Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))` — `app/models/shipit/commit.rb:366-386`.

Exploit flow: attacker forks the victim's public/shared repository (or otherwise independently produces an identical commit object — same tree, parents, author, committer, timestamps, message) so that a specific commit SHA is shared between the victim's tracked repo and the attacker's own repo. Because the attacker's fork lives under an org/account where the same GitHub App installation is present (a very common "All repositories" installation scope, or the attacker's own org with the GitHub App and webhook secret shared per Shipit's multi-org config), a status event the attacker triggers on their own fork/commit (e.g., via their own CI push or the GitHub Statuses API) is delivered to Shipit's `/webhooks` endpoint with a **valid** signature for the attacker's own repository_owner. `StatusHandler` ignores `repository` entirely and updates every `Commit` row across the whole database matching that `sha` — including the victim's — feeding attacker-controlled `state`/`description`/`target_url`/`context` into `Hook.emit(:commit_status, victim_stack, ...)`/`:deployable_status`.

Existing guards do not stop this: `verify_signature` only validates payload authenticity for the org that sent it, not that the org owns the mutated record; `drop_unhandled_event` only checks event-type support; `ExplicitParameters` schema for `StatusHandler` never declares/enforces `repository`; there is no `Repository`/`Stack` scoping anywhere in this handler.

### Impact Explanation
A payload authenticated for one repository (the attacker's fork) mutates another repository's `Commit`/`Stack` state and fires that victim stack's outbound `Hook` infrastructure (e.g., Slack/webhook notifiers) with attacker-controlled CI-state fields. Any downstream automation gating on `commit_status`/`deployable_status` (release notes, downstream CD triggers, merge queue processing via `stack.schedule_merges`) is corrupted for the victim's repo/stack, and since `add_status` can also flip `deployable?`/schedule `ProcessMergeRequestsJob`, this can influence merge/deploy automation for a repository the attacker never authenticated against. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team." Repeatable against any Stack whose commits are also reachable (same SHA) via a repository the attacker controls, i.e., any forkable/duplicable repo tracked by Shipit.

### Likelihood Explanation
Preconditions: the victim stack has an outbound `Hook` configured on `:commit_status` or `:deployable_status`; the attacker needs a repository (e.g., a fork) whose GitHub App installation shares Shipit's webhook configuration (common when the App is installed "on all repositories" of an org, or Shipit is configured per-org and the attacker is a legitimate low-privilege member/fork-owner within that org). No Shipit secrets, sessions, or GitHub App keys are required — only the ability to fork a repo and trigger a status update on it, both attacker capabilities per the threat model. This is straightforward and repeatable per targeted commit SHA.

### Recommendation
In `StatusHandler` (and any other webhook handler that resolves records purely by content hash), require and validate `repository.full_name` from the payload, and scope the `Commit` lookup to commits belonging to `Repository.from_github_repo_name(params.repository.full_name).stacks` (mirroring the pattern already used in `Handler#stacks` and the `PullRequest` handlers), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Fixtures: `victim_stack` owned by repository `victim/repo` with an outbound `Hook` subscribed to `:commit_status`/`:deployable_status`; `victim_commit` belonging to `victim_stack` with `sha = "deadbeef..."`.
2. Create a second repository/stack `attacker/repo` (also tracked by Shipit, simulating a fork with an App installation) and a `Commit` row with the **same** `sha = "deadbeef..."` belonging to `attacker_stack` (representing the shared-SHA fork commit).
3. Stub `GithubApp#verify_webhook_signature` to return `true` (as existing tests do) to represent a validly-signed payload from `attacker/repo`'s installation.
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: "deadbeef...", state: "success", description: "forged", target_url: "http://evil", repository: { full_name: "attacker/repo", owner: { login: "attacker" } } }`.
5. Assert both:
   - `victim_stack.commits.find_by(sha: "deadbeef...").statuses.last.state == "success"` and `description == "forged"` — proving the victim's commit/stack was mutated by a payload authenticated only for `attacker/repo`.
   - The victim's `Hook` fired with `payload[:stack] == victim_stack` and `payload[:commit_status].state == "success"`/`target_url == "http://evil"`, e.g. via `expect_hook(:commit_status, victim_stack, matcher) { post :create, ... }` following the existing `expect_hook_emit` helper pattern in `test/models/commits_test.rb`.
6. Assert this occurred even though `repository.full_name` in the payload (`attacker/repo`) never equals `victim/repo` — demonstrating the equality `payload.repository == commit.stack.repository` is not enforced. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
