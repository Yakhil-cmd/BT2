### Title
Webhook signature verification binds to `repository.owner.login`, but repository actions bind to `repository.full_name`, allowing unauthenticated cross-repository event injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a payload's HMAC against using `repository_owner`, a value read straight out of the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every webhook handler, however, resolves the actual `Repository`/`Stack` to mutate using a *different* field of the same unauthenticated body: `payload.dig('repository','full_name')`. Because these two fields are never checked against each other, and because `GithubApp#verify_webhook_signature` short-circuits to `true` whenever an organization has no `webhook_secret` configured (a documented, supported configuration), an unauthenticated caller can craft a payload whose `repository.owner.login` names a secret-less/unknown-to-attacker organization while `repository.full_name` names an arbitrary tracked repository belonging to a *different* organization, and have that forged event fully processed.

### Finding Description
`verify_signature` picks the app config purely from attacker-controlled JSON, before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` trivially returns `true` when the resolved organization has no configured secret: [3](#0-2) 

This "no secret configured" state is explicitly documented/supported (`webhook_secret: # nil` in the example secrets files), not a misconfiguration: [4](#0-3) 

Once past `verify_signature`, every handler resolves the target repository/stack from a *separate* payload field — `repository.full_name` — that was never bound to the signature check: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization authenticated by verify_signature (repository.owner.login) == repository owner actually written to (repository.full_name)`

Before the attacker's request, this equality happens to hold because real GitHub deliveries are self-consistent. After the crafted request, an attacker sets `repository.owner.login` to any organization configured with a blank `webhook_secret` (satisfying `verify_signature` unconditionally) while setting `repository.full_name` to `"other-org/other-repo"` — any repository actually tracked by the Shipit instance, regardless of which organization it belongs to. The controller and handler layer never re-validate that the two fields agree, so the forged event is dispatched to `Shipit::Webhooks.for_event(event)` handlers and acted upon as if it were a legitimately signed event for that other repository: [7](#0-6) 

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" binding named in scope. Depending on the event type dispatched with a forged `repository.full_name`, an unauthenticated caller can enqueue sync jobs for an arbitrary tracked repository/stack, inject fake commit statuses, or trigger check-run refreshes for a repository whose real organization never signed anything — a cross-repository write achieved without any Shipit session, API token, or the real target's `webhook_secret`. This satisfies the "Critical — cross-repository writes" bar defined in the rules.

### Likelihood Explanation
Exploitability only requires that at least one organization configured on the Shipit instance has no `webhook_secret` set — an explicitly supported and documented configuration (used for local/dev setups, and left as an option in production secrets templates). Given that, no secret, token, or GitHub credential of any kind is needed by the attacker; they only need to know the `owner/name` of a tracked repository they want to target, which is public information for any repo followed by Shipit.

### Recommendation
Bind repository resolution to the same identity used for signature verification. Concretely: after successfully verifying the signature for `repository_owner`, ensure every handler/resolution path (`Handler#repository_name`, `Repository.from_github_repo_name`) is only allowed to resolve repositories whose `owner` matches the exact organization/owner value that passed `verify_signature`, and reject events where `repository.full_name`'s owner segment differs from `repository.owner.login`/`organization.login`. Additionally, treat a missing `webhook_secret` as "reject all events" rather than "accept unconditionally," or require an explicit opt-in flag for unsigned webhook acceptance.

### Proof of Concept
1. Configure (or observe an existing deployment that has configured) an organization `no-secret-org` in `Shipit.github` config with `webhook_secret` blank.
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` calls `Shipit.github(organization: "no-secret-org")` and `verify_webhook_signature` returns `true` unconditionally because that org has no `webhook_secret` (see `lib/shipit/github_app.rb:76-83`).
4. `create` dispatches the payload to the `push` handler, which resolves the target stack via `payload.dig('repository','full_name')` → `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, `app/models/shipit/repository.rb:53-56`), causing a `GithubSyncJob` to be enqueued against `victim-org/victim-repo` even though no valid signature for `victim-org` was ever presented.

Note: I could not fully trace the exact push-event handler implementation (only `Handler` base class and `Repository.from_github_repo_name` were available in the index) to show the literal `GithubSyncJob.perform_later` call site; this should be verified directly in a full checkout, as index size limits may have excluded some handler files.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
