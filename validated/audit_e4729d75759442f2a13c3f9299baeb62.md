### Title
Unicode Homograph Spoofing of Asset Display Names via Unrestricted `data` Message Metadata - (File: wallet.js)

### Summary
Any address can act as an asset-metadata "registry" and publish a `data` message naming an arbitrary asset. The `name` field is accepted with no character-set, script-mixing, or confusable-glyph validation, allowing an attacker to mint an asset whose displayed ticker/name is visually indistinguishable from a legitimate, trusted asset (e.g., using Cyrillic/Greek homoglyphs or invisible characters), analogous to the IDN-homograph domain-spoofing UI flaw described in CVE-2019-13757.

### Finding Description
Asset identity in Obyte is the unit hash of the `asset` message, but users interact with assets primarily through a human-readable `name`/`suffix` label resolved via `asset_metadata`. This metadata is populated by `fetchAssetMetadata` in `wallet.js:1427-1488`, which trusts any `data` message whose author matches the caller-supplied `registry_address` and whose payload contains `asset` and `name` fields [1](#0-0) . The only checks performed are that `metadata_unit` has the correct hash length, `registry_address` is a syntactically valid address, and `payload.name` is truthy [2](#0-1) ; there is no restriction on the character set, length, or normalization of `name` itself.

At the protocol level, the generic `data` message app is validated in `validation.js` only by `case "data": if (typeof payload !== "object" || payload === null) return callback(...)` [3](#0-2) , and the AA equivalent in `aa_validation.js` similarly only checks `isNonemptyObject(payload)` for `case 'data':` [4](#0-3) . No component in the stack normalizes Unicode, rejects mixed-script strings, or rejects zero-width/confusable characters in a `name` field used purely for user-facing display, in contrast with the stricter checks applied elsewhere (e.g., feed names in data feeds reject `\n` and enforce a max length via `constants.MAX_DATA_FEED_NAME_LENGTH` [5](#0-4) , but no equivalent script/homograph check exists anywhere for asset names). The uniqueness constraint on `asset_metadata` is only `UNIQUE(name, registry_address)` [6](#0-5) , so a different (attacker-controlled) `registry_address` can freely register a name that is byte-for-byte different but visually identical to an established asset's name.

This mirrors the CVE-2019-13757 bug class: a security-relevant identifier displayed to the user (there, a domain in the Omnibox; here, an asset name/ticker in the wallet) can be spoofed with homograph characters so that the UI misleads the user into believing they are interacting with a different, trusted entity.

### Impact Explanation
A wallet user who receives units of an attacker-issued asset whose display name is a homograph of a well-known, valuable asset (e.g., a stablecoin or popular token) may be deceived into treating the counterfeit asset as valuable. This can lead to concrete financial loss: the victim may complete a real-value trade or private-payment counter-transfer (e.g., sending GBYTE, USD-pegged assets, or fulfilling an OTC deal) based on the false belief that they hold or received the legitimate asset, since the wallet UI presents only the spoofed `name`+`suffix` string built in `readAssetMetadata`/`fetchAssetMetadata` [7](#0-6)  without any indication that the underlying asset unit differs from the genuine one.

### Likelihood Explanation
Any unprivileged party can issue an `asset` unit and separately publish a `data` message declaring itself the metadata "registry" for that asset with an arbitrary `name`, requiring only the ability to post a valid unit — no special privilege, hub cooperation, or elevated trust is needed. Constructing convincing homoglyphs (Cyrillic а/е/о, full-width characters, zero-width joiners) is a well-documented and low-effort technique.

### Recommendation
Reject or visually flag `name`/`suffix` values in asset metadata that mix scripts, contain non-printable/zero-width characters, or resolve to a Unicode-normalized form colliding with an already-known asset name from a different registry. Enforce this both at protocol validation time (`validation.js` `case "data"`, `aa_validation.js` `case 'data'`) for messages that are recognizable as asset-metadata declarations, and defensively in `wallet.js` `fetchAssetMetadata` before persisting or displaying `payload.name`. Additionally, consider always showing the registry address/asset unit hash alongside the display name in the UI so users can positively verify asset identity.

### Proof of Concept
1. Attacker issues a new `asset` unit `A2` (distinct unit hash from the legitimate popular asset `A1`).
2. Attacker's own address `R2` posts a `data` message: `{ app: 'data', payload: { asset: A2, name: "USDТ" /* Cyrillic Т U+0422 instead of Latin T */, decimals: 2 } }`.
3. Attacker tells the victim (or the victim's hub) that `R2` is the registry for `A2`; the victim's wallet calls `fetchAssetMetadata(A2)`, which only validates hash lengths/address format and accepts the payload since `payload.name` is truthy [2](#0-1) .
4. The wallet stores and displays `A2` as "USDТ", visually identical to the legitimate "USDT" (`A1`), in balance/payment screens via `readAssetMetadata` [7](#0-6) .
5. Victim, believing they hold/received the genuine USDT, sends real-value assets to the attacker in a private trade, incurring a loss when the counterfeit asset is later found worthless.
