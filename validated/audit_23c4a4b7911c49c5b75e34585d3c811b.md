### Title
Webhook signature verification is bound to the payload's `repository.owner.login`, but `StatusHandler` writes commit statuses keyed only by `sha`, letting any org whose GitHub App signs the request forge CI status on commits belonging to a different stack/repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC against using `repository_owner`, a value read straight out of the same JSON payload it is verifying [1](#0-0) [2](#0-1) . Once the signature check passes, `Shipit::Webhooks::Handlers::StatusHandler#process` uses that same payload to write a `Status` — but it looks the target `Commit` up **only by `sha`**, with no scoping to the repository/organization that the signature was validated for [3](#0-2) . Every other handler (`Handler#stacks`, `PushHandler`, the `PullRequest` handlers) scopes to `payload.dig('repository', 'full_name')` [4](#0-3) , but `StatusHandler` does not use `stacks`/`repository_name` at all.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the webhook* == *the repository/stack whose commit is written*. The engine breaks this equality for the `status` event.

- `verify_signature` picks the `GithubApp` (and thus the `webhook_secret` used for HMAC) from `repository_owner`, itself taken from the untrusted payload (`params.dig('repository', 'owner', 'login')`) [1](#0-0) [2](#0-1) . In a multi-organization Shipit deployment (documented and supported via the org-keyed `github:` section of `secrets.yml` [5](#0-4) ), each organization has its own distinct `webhook_secret`.
- `StatusHandler#process` completely ignores `repository`/`stacks` scoping and updates **any** `Commit` row across the whole installation whose `sha` matches the attacker-supplied `sha` field:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
- `Commit#create_status_from_github!` writes a real `Status` record and triggers deploy-relevant side effects: it re-evaluates `deployable?`, fires `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` when the injected status is `pending?` or `success?` [6](#0-5) [7](#0-6) , and `deployable?` directly gates whether a commit can be merged/deployed [8](#0-7) .

Because `sha` values are 40-hex-character git commit hashes that are public (visible via GitHub, via Shipit's own commit views, or leaked in PR discussions), an attacker who legitimately controls a repository/organization that has Shipit's GitHub App installed (i.e., can generate a validly-signed `status` webhook by pushing a commit and having their own CI/service report a status on it) can set `sha` to a commit hash belonging to a completely unrelated stack/repository managed by a different organization on the same Shipit instance, and inject a fabricated "success" status for it.

### Impact Explanation
This is a cross-repository/cross-organization write: an actor authenticated only for organization A's webhook channel can flip the CI status (and consequently unblock deploys/merges via `schedule_merges`/`deployable?`) for a commit that belongs to organization B's repository, which A's webhook secret was never meant to authorize. This matches the "cross-repository writes" / "unauthorized deploy or merge" Critical impact category, since a forged success status can make an otherwise-blocked commit `deployable?` and trigger the merge queue for a stack the attacker has no access to.

### Likelihood Explanation
Requires only that:
1. The Shipit instance is configured for more than one GitHub organization (a documented, supported configuration [5](#0-4) ), or that an attacker can otherwise obtain a validly-signed `status` webhook payload for a repository/org they control.
2. The attacker knows the SHA of a commit belonging to a different stack (public information).

No repository write access to the *target* repository, no Shipit session, and no API token are needed — only the ability to have GitHub deliver a legitimately-signed `status` event from an org/repo the attacker does control. This is a realistic, low-effort path, though it is bounded by needing at least one valid webhook-producing foothold (their own installed repo).

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already do so) to the repository identified in the same payload, exactly like `Handler#stacks`/`PushHandler` do, e.g. restrict the `Commit.where(sha: params.sha)` lookup to `stacks` (commits whose `stack` belongs to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) instead of a global, unscoped `sha` lookup across all stacks/organizations.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `org-attacker` and `org-victim`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md`'s multi-org instructions).
2. As a legitimate member of `org-attacker`, trigger any commit-status update on a repository in `org-attacker` (e.g., via a personal CI integration) so GitHub sends a `status` webhook signed with `org-attacker`'s `webhook_secret`, but before delivery/using a proxy, replace the JSON body's `sha` field with the SHA of a commit belonging to a stack under `org-victim` (public, obtainable from Shipit's own UI), while leaving `repository.owner.login` as `org-attacker` so `verify_signature` validates using `org-attacker`'s known-good secret.
3. `WebhooksController#verify_signature` succeeds because it only checks the org named in the payload (`org-attacker`) against its own signature.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the `org-victim` commit and calls `create_status_from_github!`, creating a forged `Status` for a commit the attacker never had access to, potentially unblocking `deployable?` and triggering `schedule_merges` for `org-victim`'s stack.

      already_deployed = deployed?

      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))

      end
      new_status
