### Title
Missing zero-address check in vote account `authorize()` allows permanent loss of withdraw/vote authority - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The vote program's `authorize()` function lets the current authorized withdrawer (or voter) reassign the vote account's `authorized_withdrawer` (or authorized voter) to an arbitrary `Pubkey` with no validation that the new pubkey is non-default/controllable, mirroring the reported `setGov()` bug class of missing zero-address checks on a sole-authority-transfer function.

### Finding Description
`authorize()` in `programs/vote/src/vote_state/mod.rs` handles `VoteAuthorize::Withdrawer` by calling `vote_state.set_authorized_withdrawer(*authorized)` after verifying only that the *current* withdrawer has signed — it performs no check that `*authorized` is a non-zero/controllable key before overwriting the authority: [1](#0-0) 

The `Voter` branch has the analogous pattern, calling `vote_state.set_new_authorized_voter(authorized, ...)` with no restriction on the value of `authorized`: [2](#0-1) 

Because `authorized_withdrawer` is the sole gatekeeper for future withdraw/authorize instructions on the vote account (only the current withdrawer's signature is checked via `verify_authorized_signer(vote_state.authorized_withdrawer(), signers)`), once it is set to `Pubkey::default()` (or any key nobody holds the private key for), no further `Authorize(Withdrawer)` or withdraw instruction can ever be signed for that account — the authority becomes permanently unrecoverable, exactly analogous to `gov` being bricked to the zero address in the original report.

The CLI path that builds these instructions (`process_vote_authorize` in `cli/src/vote.rs`) also performs no zero-address validation on `new_authorized_pubkey` before constructing the `authorize`/`authorize_checked` instruction: [3](#0-2) 

### Impact Explanation
Setting `authorized_withdrawer` to a non-signable pubkey permanently freezes the vote account's withdrawer role: accumulated commission/rewards lamports held in the vote account can never be withdrawn again, and the withdraw authority itself can never be changed back, satisfying the "permanently frozen accounts" impact category. The equivalent applies to the voter role for future vote authorization.

### Likelihood Explanation
This requires the current authorized withdrawer/voter (an unprivileged, ordinary vote-account controller — not a validator/operator-role-specific action) to submit an `Authorize`/`AuthorizeChecked` transaction with a mistaken or malicious target pubkey; there is no on-chain or CLI-level safeguard preventing it, so likelihood is driven entirely by user/tooling error, consistent with the "Medium/footgun" characterization of the original report.

### Recommendation
Add an explicit check in `authorize()` (and/or the CLI `process_vote_authorize`) rejecting `authorized == Pubkey::default()` (and ideally any known-unusable/system-program addresses) for both `VoteAuthorize::Withdrawer` and `VoteAuthorize::Voter` paths before calling `set_authorized_withdrawer`/`set_new_authorized_voter`, returning `InstructionError::InvalidInstructionData` on violation.

### Proof of Concept
1. Create a vote account with authorized withdrawer `W`.
2. `W` signs a `VoteInstruction::Authorize(Pubkey::default(), VoteAuthorize::Withdrawer)` transaction (via `vote_instruction::authorize`, called through the CLI `vote-authorize-withdrawer` subcommand shown in `cli/src/vote.rs`).
3. `authorize()` in `vote_state/mod.rs` accepts the call since it only checks that `W` signed, then executes `vote_state.set_authorized_withdrawer(Pubkey::default())`.
4. All subsequent withdraw/authorize-withdrawer instructions fail signature verification permanently since no private key exists for `Pubkey::default()`, freezing the vote account's lamports/authority indefinitely.

Note: the analogous `StakeAuthorize::Withdrawer`/`Staker` path in the stake program (invoked via `stake_instruction::authorize`, seen used from `cli/src/stake.rs` and `stake-accounts/src/stake_accounts.rs`) likely exhibits the same missing zero-address check, but the stake program's `authorize` implementation source file was not located within the indexed content, so that instance is not confirmed with direct code citation and is flagged as uncertain.
