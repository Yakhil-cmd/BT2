## Analysis

The reported bug class is: a distribution amount is trusted/used without being validated against the actual data it's supposed to cover (Merkle leaves vs. `_amount`), which can leave some recipients unable to be paid because the total promised exceeds what's actually available.

The closest reachable analog in `ocore` is in the AA response-composition logic in `aa_composer.js`, specifically the `issueAsset()` helper used when an AA needs to self-issue units of a capped asset to satisfy its own `payment` message outputs.

### Title
AA self-issuance of a capped asset does not verify the issued amount covers the payment's target amount - (File: aa_composer.js)

### Summary
When an AA's `payment` message needs more of an asset than it currently holds, `completePaymentPayload()` calls `issueAsset()` to self-issue the shortfall. For assets with a fixed `cap`, the code always issues exactly `objAsset.cap`, regardless of how large the actual `target_amount` (the sum of the AA's own declared outputs, computed from oscript formulas) is. [1](#0-0) 

### Finding Description
`issue_amount` is computed as:
```
var issue_amount = objAsset.cap || (target_amount - total_amount);
```
For capped assets, this ignores `target_amount` entirely — it issues the fixed `cap`, not "however much is needed." After `addIssueInput()` adds the input, `total_amount` is incremented and `change_amount = total_amount - target_amount` is computed; if `change_amount <= 0` (i.e., the cap is smaller than what the AA's outputs promise), no change output is added and no error is raised. [2](#0-1) 

Control then returns to `issueAsset`'s caller, which unconditionally calls `sortOutputsAndReturn()` once `issueAsset` completes without an `err`, with no re-check of `bFound`/sufficiency for the capped-asset issuance path. [3](#0-2) 

This mirrors the audited bug: a "total to distribute" value (here, the sum of the AA's payment outputs, driven by oscript expressions the AA author writes, analogous to the off-chain Merkle-tree total) can diverge from the actually available/issuable amount (here, the asset's on-chain `cap`, analogous to the contract balance), and the composition code does not cross-check the two before proceeding.

### Impact Explanation
If an AA is coded (or can be triggered into a state) where the sum of the outputs it wants to pay in a self-issued capped asset exceeds that asset's `cap`, the resulting payment payload has `total_input < total_output`. This unbalanced payload will fail the mandatory balance check in `validatePaymentInputsAndOutputs` (`total_input !== total_output` for asset payments) when the response unit is subsequently validated/saved. [4](#0-3) 

Because this failure occurs after `issueAsset()` reports success (no bounce triggered), the AA can end up unable to produce a valid response unit for a legitimate trigger, or a subsequent response in the same trigger chain gets an inconsistent/incomplete unit assembled — potentially freezing state updates, freezing the trigger's transferred funds (bounce fees consumed but no proper response), or producing divergent outcomes between the AA's expected behavior and what actually gets committed, which is an AA fund-freezing/inconsistent-behavior class issue.

### Likelihood Explanation
This requires an AA definition where `target_amount` for a capped, self-issued asset payment can exceed `cap` — e.g., a poorly-bounded formula-based output, or one output that already consumed part of the cap in an earlier response, but a later trigger's total requested payout again approaches or exceeds the remaining/whole cap. Since the amount and cap are both under the control of the AA author's script logic (and cap is fixed at definition time), this is reachable by any AA author who doesn't explicitly bound outputs by the asset's `cap` in their oscript, and it can also be inadvertently triggered by any AA trigger sender whose trigger data drives an output formula above the cap. This makes the class Medium likelihood — it depends on how the AA is written, not a universal engine flaw, but the missing internal validation makes the engine itself provide no safety net in this specific self-issuance path (unlike the deliberate `total_input !== total_output` checks used everywhere else in payment validation).

### Recommendation
In `issueAsset()` (aa_composer.js), when the asset is capped, verify that `objAsset.cap >= (target_amount - total_amount)` before proceeding, and fail with a proper bounce (`'not enough funds for ' + target_amount + ' of asset ' + asset`) instead of silently continuing to `sortOutputsAndReturn()` with an unbalanced payload. This aligns the self-issuance path with the same "amount must equal/cover what's promised" invariant enforced everywhere else in `validatePaymentInputsAndOutputs`.

### Proof of Concept
1. Define an AA that creates a capped asset (`cap: X`) via an `asset` message.
2. In a later branch of the same AA, construct a `payment` message for that asset with an output (or set of outputs) whose combined amount, computed via an oscript formula from `trigger.data`/`trigger.output`, exceeds `X` and the AA does not yet hold that asset balance.
3. Send a trigger causing this branch to execute for the first time (so `issueAsset` takes the "not yet issued" path).
4. `issue_amount` becomes `cap` (i.e., `X`), which is less than the required `target_amount`; `issueAsset` reports success; `sortOutputsAndReturn()` runs.
5. The resulting payload has unbalanced inputs/outputs, which is then rejected at validation (`validatePaymentInputsAndOutputs`), demonstrating the AA composer produced an internally invalid unit due to the missing sufficiency check in `issueAsset()`.

			function issueAsset(cb2) {
				var objAsset = assetInfos[asset];
				if (objAsset.issued_by_definer_only && address !== objAsset.definer_address)
					return cb2("not a definer");
				var issue_amount = objAsset.cap || (target_amount - total_amount);

				function addIssueInput(serial_number){
					var input = {
						type: "issue",
						amount: issue_amount,
						serial_number: serial_number
					};
					payload.inputs.unshift(input);
					total_amount += issue_amount;
					var change_amount = total_amount - target_amount;
					if (change_amount > 0)
						payload.outputs.push({ address: address, amount: change_amount });
					cb2();
				}
				
				if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
					conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
						if (rows.length > 0) // already issued
							return cb2('already issued');
						addIssueInput(1);
					});
				}
				else{
					conn.query( // filtered by our AA's address, all equally visible on all nodes
						"SELECT MAX(serial_number) AS max_serial_number FROM inputs WHERE type='issue' AND asset=? AND address=?",
						[asset, address],
						function(rows){
							var max_serial_number = (rows.length === 0) ? 0 : rows[0].max_serial_number;
							addIssueInput(max_serial_number+1);
						}
					);
				}
			}
