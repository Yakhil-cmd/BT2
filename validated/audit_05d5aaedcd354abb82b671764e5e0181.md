## Analog Found

### Title
Webhook signature verification authenticates against an attacker-chosen organization while a different, unverified payload field selects the repository/stack that is actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App configuration (and therefore the `webhook_secret` used for HMAC validation) using `repository_owner`, a value taken directly from the untrusted, unverified JSON body. The actual side effects of the webhook (looking up the `Repository`/`Stack` to sync) are performed later using a *different* field of the same untrusted body, `repository.full_name`. Because these two attacker-controlled fields are never checked for consistency, the "organization that authenticated" the request can differ from the "repository that is written" by the downstream handler — the exact confused-deputy shape described in the YAXIS report (using one input/path to compute a value that is applied to a different, unrelated one).

### Finding Description
`verify_signature` resolves the GitHub App/org config using an unverified payload field before HMAC validation happens: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` returns `true` unconditionally when the resolved org has no `webhook_secret` configured — a state that is explicitly documented as optional per app: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`docs/setup.md` documents the webhook secret as `(optional)`, and `config/secrets.development.example.yml` shows Shipit's supported multi-organization configuration where each org can independently set (or omit) its own `webhook_secret`.

The action then dispatches to handlers using the raw parsed body, and the handler resolves the target `Repository`/`Stack` via a completely different field: [4](#0-3) [5](#0-4) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) 

which enqueues `GithubSyncJob` for that stack, regardless of which org's key was actually used to pass the signature check.

**Binding broken**: `verified_organization(payload.repository.owner.login) == acted_upon_repository_owner(payload.repository.full_name)` — the code never enforces this equality, so a request signed (or trivially accepted, if unsigned) under organization A's identity can be crafted to act on organization B's stack, as long as A's `full_name` field is spoofed to point at B's repository.

### Impact Explanation
An unauthenticated, unprivileged attacker who can reach the public `/webhooks` endpoint (no `Shipit` session, no `ApiClient` token, no `webhook_secret` of the *target* org, and no repository write access to the *target* repo are required) can force `GithubSyncJob` to run for any tracked stack, at attacker-chosen timing, by:
1. Setting `repository.owner.login` (or `organization.login`) to any org configured on the Shipit instance whose `webhook_secret` is blank (documented as optional, so realistically present on at least one org in multi-org deployments) — this makes `verify_webhook_signature` return `true` unconditionally, with no valid signature needed at all.
2. Setting `repository.full_name` to the victim stack's actual `owner/repo`.

This forces an out-of-band resync/deploy trigger (`stack.sync_github` → `GithubSyncJob` → potentially `trigger_continuous_delivery` for stacks with `continuous_deployment: true`) for a repository the attacker has no relationship to, i.e. an unauthorized deploy trigger — matching the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
The `/webhooks` endpoint is public and unauthenticated by design (it is only gated by HMAC verification). The exploit only requires that at least one GitHub App/org configured on the instance omits `webhook_secret`, which is explicitly supported and documented as optional. No credential of the target org, target repository, or Shipit session/token is required.

### Recommendation
`verify_signature` must not select the verification organization from an unverified field that differs from the field used by handlers to resolve the affected `Repository`/`Stack`. Either:
- Derive the verifying organization from the same field (`repository.full_name`'s owner segment, or a canonical field) that handlers use to resolve the repository, and require them to match; or
- After signature verification succeeds for organization X, explicitly assert that every `repository.full_name`/`organization.login` referenced in the payload belongs to X before dispatching to handlers; or
- Disallow (or treat as failing) verification when `webhook_secret` is blank in any organization sharing a Shipit instance with other orgs that do configure a secret, since a blank secret makes verification meaningless for that org's namespace.

### Proof of Concept
Given a Shipit instance configured for `orgA` (no `webhook_secret`) and `orgB` (has a stack `orgB/victim-repo` with `continuous_deployment: true`):

```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<known-existing-sha-on-orgB/victim-repo>"
}
```

- `verify_signature` calls `Shipit.github(organization: "orgA")`; `orgA.webhook_secret` is blank → `verify_webhook_signature` returns `true` regardless of signature/absence of `X-Hub-Signature`.
- `create` parses the body and dispatches to `PushHandler`, whose `repository_name` resolves to `"orgB/victim-repo"`, finds the matching `Stack`, and calls `stack.sync_github(expected_head_sha: "<sha>")`.
- `GithubSyncJob` runs for `orgB`'s stack; if `continuous_deployment` is enabled, this can trigger an unscheduled deploy — all without any credential belonging to `orgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
