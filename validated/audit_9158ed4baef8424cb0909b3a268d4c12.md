I have sufficient evidence to confirm the vulnerability. The exploit chain is fully traced: `OpenedHandler#provision?` operator precedence bug → `ReviewStackAdapter#create!` uses attacker-controlled `params.pull_request.head.ref` as `branch:` → stack is provisioned and eventually its `shipit.yml` steps run through `Command#start`/`PTY.spawn`.

### Title
Operator precedence in `provision?` bypasses `review_stacks_enabled` gate, allowing unauthorized review-stack creation from a fork's PR - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `repository.review_stacks_enabled` with `provisioning_behavior_allow_all?` using `&&`, but ORs the `allow_with_label?`/`prevent_with_label?` branches without ever re-checking `review_stacks_enabled`. Consequently, a repository configured with `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label` will still auto-provision a review stack for any unlabeled pull request, letting an unprivileged fork owner get their branch (`params.pull_request.head.ref`) built and their `shipit.yml` steps executed on the deploy host.

### Finding Description
The broken binding: the intended guarantee is `stack_created ⇒ repository.review_stacks_enabled == true`. The code at `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70` is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
In Ruby, `&&` binds tighter than `||`, so this evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `review_stacks_enabled = false` and `provisioning_behavior = :prevent_with_label`, the first clause is `false`, but the third clause `(prevent_with_label? && !has_label?)` evaluates independently of `review_stacks_enabled` and returns `true` whenever the PR carries no provisioning label — which is the attacker's default state (they never add the label).

`respond_to_pull_request_opened?` (`opened_handler.rb:60-63`) returns `true`, and `process` (`opened_handler.rb:41-46`) calls `Shipit::Webhooks::Handlers::PullRequest::ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`. `ReviewStackAdapter#create!` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:72-94`) builds `stack_attributes` with `branch: params.pull_request.head.ref` taken directly from the webhook payload, i.e. the attacker's fork branch, and enqueues the stack via `Shipit::ReviewStackProvisioningQueue.add(stack)`. The queue worker (`app/models/shipit/review_stack_provisioning_queue.rb:29-37`) provisions the stack, after which normal deploy/task machinery reads the repository's `shipit.yml` (`app/models/shipit/deploy_spec/file_system.rb`) from the attacker's branch and executes its steps via `Shipit::Command#start` (`lib/shipit/command.rb:85-101`), which calls `PTY.spawn` on the deploy host.

None of the existing guards intercept this: webhook signature verification only authenticates that GitHub sent the payload, not that the *content* is privileged; `ExplicitParameters` only validates payload shape; and no code re-checks `review_stacks_enabled` before `prevent_with_label?`/`allow_with_label?` branches. The existing test suite (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb:159-172`, "create stacks for repos what prevent_with_label when label is absent") exercises `prevent_with_label` only with the default `provisioning_enabled: true`, so this precedence bug is untested for the `review_stacks_enabled: false` case.

### Impact Explanation
An unprivileged attacker who can open a pull request against any repository configured with `provisioning_behavior: prevent_with_label` (regardless of whether the maintainer set `review_stacks_enabled: false` specifically to opt that repository out of review stacks) can get a `Shipit::Stack` created with attacker-controlled `branch`. Once provisioned, the deploy/task pipeline runs commands defined by the attacker's own `shipit.yml` on the Shipit deploy host via `Command#start`/`PTY.spawn`, i.e. **RCE on the deploy host**. This is repeatable per repository/PR and does not require any secret or privileged role — only opening (or leaving open) an unlabeled PR.

### Likelihood Explanation
Preconditions: target repository must have `provisioning_behavior = :prevent_with_label` (a supported, documented configuration) while `review_stacks_enabled = false`. This is a plausible real-world configuration — an operator disabling review stacks org-wide while leaving a stale/no-op `provisioning_behavior` value, since the two settings are meant to be independently toggleable per the UI (`app/views/shipit/repositories/settings.html.erb`). Attacker cost is a normal GitHub pull request against the repo, with no maintainer approval or label needed since absence of a label is the default state. This is fully feasible and repeatable.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three branches:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, `repository.review_stacks_enabled == false` while `Shipit::Stack.count` still increases by 1 (the equality `stack_created ⇒ review_stacks_enabled == true` is violated); after applying the recommended fix, the assertion passes with `Shipit::Stack.count` unchanged.
