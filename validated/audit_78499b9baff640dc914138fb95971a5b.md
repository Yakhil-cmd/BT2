## Title
Stack-scoped API token authorizes reads of arbitrary stacks in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolution method used by every other API controller. The base controller scopes stack lookups to the stacks an `ApiClient` token is authorized for, but `CCMenuController` replaces that method with an unscoped lookup, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` defines the standard, scope-respecting resolution chain: [1](#0-0) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a single stack (`current_api_client.stack_id?`), and `stack` resolves `params[:stack_id]` only within that restricted set. This is the mechanism by which a stack-scoped `ApiClient` (created via `belongs_to :stack, optional: true` on `Shipit::ApiClient`) is prevented from touching stacks outside its authorization.

`Shipit::Api::CCMenuController` bypasses this entirely: [2](#0-1) 

Its `stack` method calls `Stack.from_param!(params[:stack_id])` directly against the global `Stack` relation, never consulting `current_api_client.stack_id`. Permission enforcement in this controller is only `require_permission :read, :stack`, which is checked via `ApiClient#check_permissions!`: [3](#0-2) 

`check_permissions!` only validates that the token has the `read:stack` permission string in its list — it has no knowledge of *which* stack is being requested. The stack-level restriction is supposed to come exclusively from the `stacks`/`stack` scoping in the base controller, which `CCMenuController` does not use.

As a result: a token created with `stack_id` set to Stack A (i.e., an `ApiClient` intentionally authorized only for Stack A, per the base controller's `stacks` scoping design) can call `GET /api/stacks/:stack_id/cc.xml` (the CCMenu endpoint) with `stack_id` set to Stack B, and successfully receive Stack B's build/deploy status, because `CCMenuController#stack` looks up any stack in the system, not just the ones in `current_api_client`'s authorized scope.

Binding broken: `stack authorized by token (current_api_client.stack_id)` ≠ `stack actually touched by the request (Stack.from_param!(params[:stack_id]))`.

Before the attacker's action: Stack-scoped token T is bound only to Stack A per the base controller's `stacks` method.
After the attacker's action: Using the same token T against `CCMenuController#show`, the request resolves and returns state for Stack B, which T was never authorized to access.

### Impact Explanation
This is an unauthorized read of stack state (build/deploy status, last build label/time, project name) for stacks outside the presenting API token's authorized scope — matching the "unauthenticated read of stack state" class of High-impact findings, since the token is authenticated but not authorized for the disclosed stack. It defeats the purpose of scoping tokens to individual stacks (a documented security boundary in `BaseController#stacks`), letting a token meant for one team's/repo's stack enumerate/read status data for any other stack in the Shipit instance.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a routine, low-privilege credential intended to be limited to one stack) can trigger this by simply changing the `stack_id` route/query parameter on the CCMenu endpoint — no special conditions, timing, or races required, unlike the original bug class trigger (which needs a 180-day sunset cycle). This makes it more directly and immediately exploitable than the original finding.

### Recommendation
Make `CCMenuController#stack` reuse the scoped lookup from the base controller instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that the `current_api_client.stack_id` restriction defined in `BaseController#stacks` is honored, consistent with every other API controller.

### Proof of Concept
1. Create an `ApiClient` with `permissions: ['read:stack']` and `stack: stack_a` (scoped token).
2. Confirm via `Shipit::Api::StacksController#index` (which uses the scoped `stacks` method) that this token only ever sees `stack_a`.
3. Send `GET /api/stacks/:stack_b_id/cc.xml` (routed to `CCMenuController#show`) using the same token's `authentication_token` (Basic Auth or `?token=`), with `stack_id` set to `stack_b`'s id/param.
4. Observe: the request succeeds (200 OK) and returns `stack_b`'s CCMenu XML (`name`, `activity`, `lastBuildStatus`, etc.), even though the token is only authorized for `stack_a`. This can be verified by tracing `CCMenuController#stack` → `Stack.from_param!(params[:stack_id])`, which has no dependency on `current_api_client.stack_id`, unlike `BaseController#stack` used by all sibling controllers (e.g. `Shipit::Api::DeploysController`, `Shipit::Api::StacksController`).
