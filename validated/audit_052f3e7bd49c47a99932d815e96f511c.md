### Title
Unscoped commit-SHA lookup in `StatusHandler` lets any repository's signed status webhook forge CI success for another repository's tracked commit, enabling unauthorized `MergeRequest#merge!` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with a global `Commit.where(sha: params.sha)` query that is never scoped to the `repository` named in the webhook payload. Because git commit SHAs are pure content hashes independent of which repository stores them, an attacker who controls any repository covered by the same GitHub App installation (webhook secret) as the victim's stack can create a byte-identical commit object with the victim's PR head SHA in their own repository, post an arbitrary "success" status on it via the GitHub API, and have Shipit attach that forged status to the victim's tracked commit — breaking the binding that `all_status_checks_passed?` should only reflect statuses genuinely reported against the repository owning the merge request's stack.

### Finding Description
The broken binding, stated explicitly:

`statuses backing MergeRequest#all_status_checks_passed?` (i.e. `head.statuses_and_check_runs` for `head` belonging to the victim's stack) **should equal** `statuses genuinely reported by GitHub for commits in the repository that owns that stack`.

Trace:
1. `WebhooksController#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . This only proves the request came from GitHub for *some* repository in the trusted organization/app installation — it does not bind the payload to any specific repository or stack.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Unlike the `PullRequest` handlers, which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [4](#0-3) , `StatusHandler` never consults `payload.dig('repository','full_name')` or the base `Handler#stacks` scope at all. It matches purely on `sha`, across every stack in the installation.
3. The `commits` table's uniqueness constraint is `(sha, stack_id)`, not `(sha)` alone [5](#0-4) , confirming the schema expects the *same* SHA to legitimately exist in multiple stacks (e.g., shared branches/forks) — exactly the condition `StatusHandler` fails to disambiguate.
4. `Commit#create_status_from_github!` creates the `Status` scoped to `commit.stack_id` — the *found* commit's own stack, not anything derived from the webhook payload [6](#0-5) .
5. `MergeRequest#all_status_checks_passed?` reads exactly this attacker-reachable data: `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [7](#0-6) .
6. `ProcessMergeRequestsJob#perform` calls `merge_request.refresh!` then, only guarded by `all_status_checks_passed?`, calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request(...)` — a real merge into the victim repository [8](#0-7) [9](#0-8) .

Exploit flow: The attacker opens a PR against the victim repository (head commit SHA `X`, a pure content hash of tree/parent/author/committer/message/timestamps). The attacker also controls a second repository reachable by the same GitHub App/org webhook installation (e.g., another repo they own within the same organization). Using `git cat-file`/`git hash-object` (or an equivalent replication of the exact commit object bytes), the attacker inserts an identical commit object — same SHA `X` — into their own repository, pushes it, and calls GitHub's status API on their own repo/commit with `state: success` and any `context` they choose (they have full write access to their own repository). GitHub emits a genuinely, correctly signed "status" webhook naming the attacker's repository but with `sha: X`. `verify_signature` passes (real GitHub signature for the trusted org). `StatusHandler` finds the victim's tracked `Commit` row by SHA alone and attaches the forged "success" status to it, under the victim's `stack_id`.

Existing guards do not stop this: `verify_signature` checks signature validity for an organization, not repository-to-commit ownership; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape; no model validation or the `stacks` scope is consulted by `StatusHandler`.

### Impact Explanation
A successful forged status causes `all_status_checks_passed?` to return `true` for a pull request whose real CI never ran, letting `ProcessMergeRequestsJob#perform` call `merge_request.merge!` and merge attacker-controlled code into the victim repository's default branch — an unauthorized merge, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." The technique is repeatable against any stack within reach of the same GitHub App installation whose deploy spec's required status contexts are known or guessable, and generalizes to any commit SHA the attacker can reproduce byte-for-byte in a repository they control.

### Likelihood Explanation
Preconditions: the attacker needs (a) an open PR against the victim's Shipit-tracked repository (trivial, unprivileged), and (b) write access to some other repository covered by the same organization/GitHub App webhook installation as the victim's stack (plausible in many real deployments where one GitHub App/org covers numerous repositories and members can create their own repos). Reconstructing an identical git commit object in a second repository is a standard, low-cost git operation (`git cat-file`/`hash-object`), requiring no cryptographic collision — SHA reuse here is legitimate content-addressing, not a hash break. No Shipit secrets, sessions, or maintainer roles are required. This is repeatable per-PR and per-stack.

### Recommendation
In `StatusHandler#process` (and generally in `Handler`), resolve the target `Stack`/`Repository` from `payload.dig('repository','full_name')` (as the `pull_request` handlers already do) and scope the `Commit` lookup to `stacks`/that repository (e.g., `Commit.joins(:stack).where(sha: params.sha, stack: { repository_id: repository.id })` or restrict to `stacks.flat_map(&:commits)`), rather than matching `sha` globally across all stacks.

### Proof of Concept
Minitest plan (`test/jobs/process_merge_requests_job_test.rb` style, no live GitHub):
1. Fixture setup: two stacks/repositories `victim_stack` (owning repo `victim/repo`) and `attacker_stack` (owning repo `attacker/repo`), both associated with the same `Shipit.github` organization/app config used by `WebhooksControllerTest`.
2. Create a `MergeRequest` in `victim_stack` with `merge_status: 'pending'` whose `head` is a `Commit` with `sha: SHARED_SHA` in `victim_stack`, and no `Status` rows yet (simulating CI never having run).
3. Create a second `Commit` with the same `sha: SHARED_SHA` but belonging to `attacker_stack` (allowed by the `(sha, stack_id)` unique index).
4. POST to `/webhooks` with `X-Github-Event: status`, a valid signature (stub `verify_webhook_signature` to return true, mirroring `GithubHook.any_instance.stubs(:verify_signature).returns(true)` pattern in `WebhooksControllerTest`), and a JSON body declaring `repository.full_name: "attacker/repo"`, `sha: SHARED_SHA`, `state: "success"`, matching whatever `context` the victim stack's deploy spec requires.
5. Assert: `victim_stack`'s tracked `Commit` (`sha: SHARED_SHA`) now has a `Status` with `state: "success"` — i.e. `assert commit_in_victim_stack.statuses.exists?(state: 'success')`.
6. Run `ProcessMergeRequestsJob.new.perform(victim_stack)` (with `merge_pull_request` stubbed/expected as in `test/jobs/process_merge_requests_job_test.rb`) and assert `merge_request.reload.merged?` — proving `merge!` was invoked purely off the cross-repository forged status, with the equality `statuses backing all_status_checks_passed? == statuses genuinely reported for victim/repo`'s commit being false (the status came from `attacker/repo`, not `victim/repo`) yet the merge still proceeded.
