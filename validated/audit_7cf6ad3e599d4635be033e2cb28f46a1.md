### Title
`StatusHandler#process` resolves commits by bare SHA across all stacks, letting one repository's status webhook poison `Commit#blocked?` on an unrelated stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike `PushHandler` which scopes lookups through the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`). Any commit row anywhere in the `commits` table that shares the pushed SHA gets a new `Status` applied, regardless of which repository/stack authored the webhook, letting a status webhook from repository B mutate commit state on stack A.

### Finding Description
The claimed binding is: `webhook.repository.full_name == commit.stack.repository.full_name` for the commit that gets its status updated. Tracing the code shows this binding is never enforced for the `status` webhook event.

- `WebhooksController#create` dispatches the raw JSON payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` after `verify_signature`, which only checks that the signature matches the app registered for `repository_owner` (the org/owner named in the payload) — it does not tie the payload to a specific stack or repository beyond that org check. [1](#0-0) 
- `Webhooks::Handlers::Handler` provides a `stacks` helper that properly scopes lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks`. `PushHandler` uses this helper to scope its queries. [2](#0-1) [3](#0-2) 
- `StatusHandler#process`, however, does **not** use `stacks`/`repository_name` at all. It queries `Commit.where(sha: params.sha)` directly against the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match: [4](#0-3) 
- The `commits` table's `sha` index is scoped `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning uniqueness of `sha` is only enforced per-stack, not globally — two different stacks (backed by different repositories) can legitimately have `Commit` rows with the identical `sha` value if the same commit content (tree, parents, author, timestamps, message) is pushed to both.
- `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` creates the `Status` under the found commit's own `stack_id`, so once `StatusHandler` finds a same-sha `Commit` row belonging to stack A, the injected status is attributed to stack A even though the webhook was signed for and originated from repository B. [5](#0-4) 
- `Commit#blocked?` on stack A recomputes `stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)`, where `blocking?` delegates to `status`, which is derived from the `statuses` association just poisoned. [6](#0-5) 

Exploit flow: attacker owns/controls repository B, which is a Shipit-integrated repository (any stack). Attacker crafts (or discovers) a commit whose content is byte-identical to an existing "blocking" intermediate commit on victim stack A (git SHA-1 is content-addressed, so pushing the exact same tree/parents/author/timestamp/message into repository B's history yields the identical SHA — this does not require breaking SHA-1, only duplicating public commit content, which is trivial for open commits). Attacker then triggers (or has CI on repository B emit) a genuine, validly-signed `status` webhook with `state: success` for that SHA. `verify_signature` passes because the webhook is legitimately signed for repository B's org. `StatusHandler` finds *all* `Commit` rows with that SHA — including the one on stack A — and calls `create_status_from_github!` on it, flipping stack A's blocking commit to `success`. `Commit#blocked?` on stack A now returns `false` where it previously returned `true`.

None of the existing guards catch this: `verify_signature` validates the webhook's authenticity for its own org/repo, not that the payload's SHA only touches commits belonging to that repo's stacks; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only validates types of `sha`/`state`/etc., not repository ownership; there is no `require_permission!`/`stacks` scope filtering in `StatusHandler#process` as there is in `PushHandler`.

### Impact Explanation
This is a payload for one repository (B) mutating another repository's stack/commit state (A), unblocking a deploy gate that should have prevented a release. Concretely, `Commit#blocked?` flipping from `true` to `false` on stack A removes the CI blocking-status gate, which feeds `deployable?` and downstream deploy/rollback/continuous-delivery logic, potentially allowing an unauthorized deploy to proceed on stack A based on state injected by an unrelated, attacker-controlled repository. This matches "Critical — a payload for one repository mutating another's stack/commit ... or an unauthorized deploy." It is repeatable against any stack whose blocking commit SHA the attacker can reproduce, and the blast radius spans the whole `commits` table (any two stacks with a shared SHA), not just one pair of tenants.

### Likelihood Explanation
Preconditions: attacker needs (1) their own GitHub repository registered as a Shipit stack (multi-tenant Shipit installations are the norm), (2) the ability to push arbitrary commit content (git allows any content-addressed object graph), and (3) knowledge of the SHA/content of the target blocking commit on stack A (trivially available for open-source or otherwise-visible repositories). No secrets, sessions, or elevated roles are required — the attacker only relies on their own legitimate, correctly-signed webhook. This is a purely mechanical, repeatable exploit once the SHA collision-by-duplication is set up.

### Recommendation
Scope `StatusHandler#process` to the repository named in the webhook payload, mirroring `PushHandler`'s use of the `stacks` helper, e.g. `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))` (or join through `stacks`) before calling `create_status_from_github!`, so a status webhook can only mutate commits belonging to stacks of the repository that authored the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for repository B does not update commits belonging to stack A's repository" do
  stack_a = shipit_stacks(:shipit)                     # repo: shopify/shipit-engine
  stack_b = shipit_stacks(:some_other_repo_stack)       # repo: attacker/other-repo

  shared_sha = "deadbeef" * 5
  blocking_commit_a = stack_a.commits.create!(sha: shared_sha, message: "blocking", author: shipit_users(:shipit))
  blocking_commit_a.statuses.create!(stack_id: stack_a.id, state: "pending", context: "ci/required")

  # sanity: blocked? is true on stack A because of blocking_commit_a
  later_commit_a = stack_a.commits.create!(message: "later", author: shipit_users(:shipit))
  assert later_commit_a.blocked?

  # Attacker pushes identical-SHA commit into repo B, then a genuine, correctly-signed
  # `status` webhook for repository B claims success on that SHA.
  Commit.create!(stack: stack_b, sha: shared_sha, message: "blocking", author: shipit_users(:shipit))

  payload = { "sha" => shared_sha, "state" => "success", "context" => "ci/required" }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  blocking_commit_a.reload
  later_commit_a.reload

  assert_equal "success", blocking_commit_a.status.state
  refute later_commit_a.blocked?   # flips from true to false due to repo B's webhook
end
```
