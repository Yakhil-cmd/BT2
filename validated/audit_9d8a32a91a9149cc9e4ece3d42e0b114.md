## Title
Silent Drop of Rounded-to-Zero AA Payment Outputs Causes Unrecoverable Fund Loss in Share/Token-Issuing Autonomous Agents - (File: `aa_composer.js`)

### Summary
Ocore's Autonomous Agent (AA) engine lets an AA compute payment output amounts with arbitrary oscript formulas (division, `round()`, `floor()`, etc.), which is the standard, documented pattern for AAs that issue shares/tokens proportional to a deposit (e.g. the officially shipped `uniswap_like_market_maker.oscript` sample). When such a formula rounds down to `0` for a small-but-legitimate trigger amount, the composer does not bounce the unit or reject the amount — it silently strips the zero-amount output from the message and, if that empties a message's outputs, drops the whole message. [1](#0-0) 

This is the same root cause as the reported ERC4626/Arcadia bug: a legitimate value that rounds down to zero is treated as valid and processed silently instead of being rejected, so the accounting party that should receive the proportional share/token gets nothing while the deposit itself is retained.

### Finding Description
`aa_validation.js` explicitly allows a payment output's `amount` to be a formula string, validated only as a syntactically valid formula, not a value that is provably non-zero: [2](#0-1) 

At execution time, in `handleTrigger`'s `sendUnit`/`completePaymentPayload` flow, after each output amount formula is evaluated, ocore filters out any output whose amount evaluated to `0`, and then filters out any message left with zero outputs: [3](#0-2) 

Only if *all* messages become empty does the AA bounce (refunding the trigger amount minus fees): [4](#0-3) 

This exact behavior is asserted by ocore's own test suite: a message computing `trigger.output[[asset=base]] * 0` is silently removed, and the AA proceeds to a different fallback path rather than reverting the whole trigger: [5](#0-4) [6](#0-5) 

The danger is when an AA has *two* effects tied to the same trigger: (1) it keeps the deposited base/asset funds (the payment that funded the trigger is never returned), and (2) it computes and sends a *separate* payment message minting/transferring shares/tokens proportional to the deposit via division/rounding. Ocore's own reference AA pattern for this — a share-issuing "market maker" — is shipped as a canonical sample: [7](#0-6) 

Here `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` can legitimately round down to `0` for a small deposit relative to the pool's outstanding balance/size, while `trigger.output[[asset=base]] > 1e5` still passes (the "invest" case fires) and the `state` block still executes and is committed: [8](#0-7) 

Because the composer silently strips the `amount: 0` output from the `mm_asset` payment message (rather than treating it as invalid and bouncing the whole trigger), the depositor's base bytes remain permanently owned by the AA (added to `balance[base]`) while the depositor receives zero `mm_asset` shares and no error is surfaced back to them. There is no automatic minimum-deposit enforcement or "expected nonzero output" check at the protocol level to prevent this class of AA logic from silently losing user funds.

### Impact Explanation
Any unprivileged trigger sender can, without any special access, cause AA fund loss for themselves (and, since the pattern is symmetric, for other counterparties in more complex protocols built on the same idiom — e.g., liquidity/vault-style AAs) by sending a trigger sized such that a rounding-down formula for the corresponding issued asset evaluates to `0`. This mirrors the referenced report's core class: "rounding down causes zero token mint, and the system proceeds as if nothing is wrong," except in ocore the silent-drop happens at the unit-composition layer (`aa_composer.js`) rather than at a business-logic revert, making it even less visible to the depositor because no bounce/error message is produced telling them the mint failed — the trigger unit is accepted and finalized normally.

### Likelihood Explanation
The bug is trivially reachable: it requires only a single normal trigger with a valid but small payment amount sent to a share/token-issuing AA — exactly the officially documented and shipped `uniswap_like_market_maker.oscript` pattern. No privileged role, malicious peer/hub, or timing race is needed; the vulnerable condition (`round(...) == 0`) is a pure function of the trigger amount and current pool state, both of which are fully attacker/user controlled or observable.

### Recommendation
- In `aa_composer.js`, do not silently filter `amount === 0` outputs from a payment message that was produced by evaluating a non-constant (formula-based) `amount`; instead bounce the trigger (or at minimum, require AA authors to explicitly opt into "skip if zero" semantics via an `if` condition) so the AA logic doesn't proceed as though a mint/transfer happened when it didn't.
- Alternatively/additionally, provide and document a way for AA authors to assert non-zero results before composing amount fields (already possible in principle via `bounce()` on an explicit check), and update the AA specification/samples (including `uniswap_like_market_maker.oscript`) to add an explicit `bounce('would issue zero shares')` guard, since silently dropping the payment output currently gives no signal that the operation logically failed.

### Proof of Concept
1. Deploy an AA following the shipped `uniswap_like_market_maker.oscript` pattern (init trades set up an `mm_asset` and non-zero `mm_asset_outstanding`/balances).
2. An attacker/user sends a trigger with `trigger.output[[asset=base]]` slightly above `1e5` and `trigger.output[[asset=$asset]] > 0`, sized so that `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` evaluates to `0` (achievable once the pool's `mm_asset_outstanding` and `bytes_balance` are large relative to the new deposit) — see the "invest in MM" branch: [7](#0-6) .
3. `aa_composer.js` evaluates the `mm_asset` payment output amount to `0`, filters it out of the outputs array, and since the message then has no outputs, drops the entire payment message per [3](#0-2) .
4. The `state` message still executes and is committed (adding `0` to `var['mm_asset_outstanding']`), and the AA response unit is finalized successfully — the trigger is not bounced, matching the observed behavior in [9](#0-8) .
5. The base bytes/asset the user sent as part of the trigger remain in the AA's balance permanently, while the user receives `0` `mm_asset` shares and no error indicating the mint failed.
