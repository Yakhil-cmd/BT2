### Title
Webhook signature verified against `repository.owner.login`, but handlers act on the independent, unverified `repository.full_name` field — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, while the event handlers that actually mutate state (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using a *different* JSON field, `repository.full_name`. Because Shipit supports multiple GitHub orgs each with its own `webhook_secret` [1](#0-0) , the signature only proves "this payload was signed with Org A's secret" — it never proves that the repository actually acted upon (`full_name`) belongs to Org A. An attacker who controls (or has push access to) any single repository under an organization configured in this Shipit instance can forge a payload naming a *different* organization's/repository's `full_name` while keeping `repository.owner.login` pointed at their own org, producing a validly-signed webhook that manipulates a repository they do not control.

### Finding Description
`verify_signature` computes the GitHub App/secret to check against solely from the attacker-controlled JSON body, before the signature has been verified: [2](#0-1) [3](#0-2) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`. Multi-org Shipit installations key `webhook_secret` per organization: [4](#0-3) , and `verify_webhook_signature` performs a straightforward HMAC compare against that org's secret and the raw body: [5](#0-4) .

Meanwhile, every handler that performs an action resolves the repository/stack from a **separate** JSON field, `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

Nothing ties `repository.owner.login` (used for the signature-secret lookup) to `repository.full_name` (used for the effect). GitHub's real webhooks keep these consistent, but since the controller parses `request.raw_post` itself and only checks the HMAC of the *whole body* against a secret chosen from body content, an attacker who owns/administers **any org configured in the Shipit instance** can sign an arbitrary body with that org's `webhook_secret`, setting `repository.owner.login` to their own org (to pass the lookup) but `repository.full_name` to `"other-org/other-repo"` (to control the actual target). This breaks the equality: `organization whose webhook_secret authenticated the request == organization whose repository the payload write applies to`.

### Impact Explanation
This lets a user with legitimate delivery access to one configured GitHub organization (i.e., someone who can trigger a real webhook delivery signed with that org's `webhook_secret`, e.g. via a repo webhook they control, or by replaying/crafting HTTP requests carrying a valid signature for their own org) force Shipit to process events — such as `push` (triggering `GithubSyncJob`/stack sync), `status`, `check_suite`, `pull_request` open/close/label, and `membership` — against a `Stack`/`Repository`/`Team` belonging to a completely different organization. Depending on which handler is targeted this can trigger unauthorized syncs, spoof commit `status`, fabricate/close pull-request-driven review stacks, or manipulate `Membership`/`Team` records for an org the attacker does not control — a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the signing identity and the acted-upon identity.

### Likelihood Explanation
Exploitability requires the deployment to be configured with the multi-organization `github:` secrets schema (each org with its own `webhook_secret`) and the attacker to have legitimate delivery/signing capability for at least one of those orgs (e.g., they administer a GitHub App/webhook installed on one lower-trust org that shares the same Shipit instance as a higher-trust org). This is a realistic multi-tenant scenario the engine explicitly supports (`github_app_config`), so likelihood is moderate — it does not require compromising any Shipit session, `ApiClient` token, or the app's GitHub credentials, only mismatched trust between two orgs onboarded to the same instance.

### Recommendation
Verify the webhook signature using the secret associated with the *same* field used to resolve the target repository (`repository.full_name`'s owner segment), not a loosely-related `owner.login`/`organization.login` field. Additionally, after signature verification, re-validate that `repository.full_name`'s owner matches the organization whose secret validated the signature before dispatching to handlers, rejecting the payload otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `low-trust-org` and `high-trust-org`, each with distinct `webhook_secret`s (multi-org schema per `github_app_config`).
2. Attacker controls a repo/webhook under `low-trust-org` and thus knows/can produce a signature valid for `low-trust-org`'s `webhook_secret` (e.g. via GitHub's webhook redelivery/test feature, or a compromised low-privilege webhook endpoint they administer).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "low-trust-org" },
    "full_name": "high-trust-org/production-app"
  }
}
```
4. Attacker signs the raw body with `low-trust-org`'s `webhook_secret` and POSTs it to `/webhooks` with header `X-Github-Event: push` and the resulting `X-Hub-Signature`.
5. `verify_signature` computes `repository_owner == "low-trust-org"`, fetches `low-trust-org`'s `GitHubApp`, and the signature check passes because it was actually signed with that secret [2](#0-1) .
6. `PushHandler` then resolves `stacks` from `repository.full_name = "high-trust-org/production-app"` [6](#0-5)  and triggers `stack.sync_github(expected_head_sha: ...)` on the `high-trust-org` stack — an action the attacker was never authorized to trigger for that repository [8](#0-7) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
