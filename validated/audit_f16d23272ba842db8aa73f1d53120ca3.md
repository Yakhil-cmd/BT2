### Title
Malicious upstream commit with a broken/unreachable submodule causes persistent sync denial - (File: `main.go`)

### Summary
The `OmoVault` bug is a class of "one bad untrusted entry that a privileged read/refresh path cannot skip, causing permanent denial of service with no recovery mechanism." The closest reachable analog in `git-sync` is a malicious or broken submodule entry committed to the synced (attacker-influenced) upstream repository. `git-sync`'s `configureWorktree` unconditionally runs `git submodule update --init [--recursive]` for every checkout, with no way to skip a single bad submodule, no submodule allow-list, and (with default flags) no failure budget — so one bad commit can permanently stop all future syncs.

### Finding Description
When `--submodules` is not `off` (the default is `recursive`), every worktree checkout runs: [1](#0-0) 

This command is not scoped or sandboxed per-submodule — if any submodule URL is unreachable, malformed, points to a private/blocked host, or otherwise fails to clone/checkout, the entire `git submodule update` command fails and `configureWorktree` returns an error, which propagates out of `SyncRepo`: [2](#0-1) 

Because anyone with commit/push access to the synced repository (or an upstream compromise, which is the same threat model as an attacker pushing a bad ref/commit) can add or modify a `.gitmodules` entry, this failure is fully attacker-controlled: they just need to land one commit at the currently-synced ref (branch HEAD, tag, etc.) that adds a submodule with an invalid URL.

In the main sync loop, a `SyncRepo` error increments `failCount` and is checked against `--max-failures`, which **defaults to 0** ("any sync failure will terminate git-sync"): [3](#0-2) [4](#0-3) 

With the default configuration, the process calls `os.Exit(1)` on the very first failure. In Kubernetes, the sidecar is restarted by the kubelet, restarts the sync loop, re-fetches the same bad ref/commit, hits the same submodule failure, and exits again — a crash loop with no forward progress. Even with `--max-failures=-1` (retry forever) or the init-max-failures variant, the loop retries the same bad ref indefinitely without ever publishing new content, since there is no mechanism to skip a failing submodule, fall back to a partial checkout, or advance past the bad commit automatically (an operator would have to intervene with `--submodules=off` or force a different `--ref`, analogous to needing an explicit "remove malicious account" fix in `OmoVault`).

### Impact Explanation
This matches the "persistent sync denial" impact bucket: once the tracked ref points at a commit containing a broken submodule, `git-sync` can no longer publish any update — not the offending commit and not any subsequent good commit, because it keeps re-fetching and re-failing on the same broken submodule graph on every attempt. With default flags the container also crash-loops and exits non-zero repeatedly, which can trip Kubernetes back-off/restart limits and marks the pod as unhealthy via the readiness/liveness endpoint that gates on successful sync: [5](#0-4) 

### Likelihood Explanation
Likelihood is Medium: it requires an attacker (or compromised/erroneous upstream contributor) with the ability to land a commit on the ref that `git-sync` is tracking (a normal push permission on the source repo, or a supply-chain compromise of a dependency added as a submodule). No special git-sync flags beyond the default `--submodules=recursive` are required; `--depth`/`--filter` do not mitigate this because the failure happens in `git submodule update`, independent of clone depth.

### Recommendation
- Make submodule checkout failures non-fatal per-submodule (e.g., continue with other submodules and log/report the one that failed) rather than aborting the whole `configureWorktree`/`SyncRepo` call.
- Add an option to keep serving the last known-good published symlink target when a new sync attempt fails, so a single bad commit cannot regress the served content to nothing (currently the old worktree is retained since publish never re-runs, but the process nonetheless exits/crash-loops under default `--max-failures=0`).
- Add an explicit allow-list or `--submodules` scoping (e.g., restrict submodule URLs to the same host/organization) to reduce attacker ability to introduce unreachable/blocked submodule URLs.
- Document/encourage `--max-failures=-1` and add a metric/alert specifically for "stuck on same failing hash" so operators can detect this class of persistent-denial condition instead of relying on generic crash-loop signals.

### Proof of Concept
1. Start `git-sync` with default flags against a repository, e.g.:
   `git-sync --repo=https://example.com/repo.git --root=/git/root --link=current`
2. As a user with push access to `repo.git` (or via upstream compromise), add a submodule pointing at an unreachable/invalid URL and commit it to the tracked branch:
   ```
   git submodule add https://invalid.example.invalid/nope.git broken-sub
   git commit -m "add broken submodule"
   git push
   ```
3. On the next poll (`--period`), `git-sync` fetches the new commit, creates a new worktree, and calls `configureWorktree`, which runs `git submodule update --init --recursive` (main.go:1737-1747) and fails.
4. `SyncRepo` returns an error; with default `--max-failures=0`, the process logs "too many failures, aborting" and calls `os.Exit(1)` (main.go:1059-1061). Under Kubernetes, the sidecar restarts and repeats steps 3-4 indefinitely — no new content is ever published while the bad commit remains at the tracked ref, reproducing a permanent/persistent sync denial analogous to the un-removable malicious `OmoAgent` account in the `OmoVault` report.

// SyncRepo syncs the repository to the desired ref, publishes it via the link,
// and tries to clean up any detritus.  This function returns whether the
// current hash has changed and what the new hash is.
func (git *repoSync) SyncRepo(ctx context.Context, syncHooks syncHooks) (bool, string, error) {
	git.log.V(3).Info("syncing", "repo", redactURL(git.repo))

	if err := syncHooks.refreshCreds(ctx); err != nil {
		return false, "", fmt.Errorf("credential refresh failed: %w", err)
	}

	// Initialize the repo directory if needed.
	if err := git.initRepo(ctx); err != nil {
		return false, "", err
	}
