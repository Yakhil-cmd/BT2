### Title
Push-Transfer in `handleKLAYTransfer` Allows Malicious Recipient to Permanently Block Bridge Nonce Advancement and Lock Bridged KLAY — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge uses a "push" pattern to deliver KLAY to the recipient address. If the recipient is a contract that reverts on receiving KLAY, the `require(ok, ...)` guard causes the entire transaction to revert — including all nonce-state updates that were written earlier in the same call. Because the nonce is never durably recorded, `lowerHandleNonce` can never advance past that slot, the bridge recovery daemon retries the same failing nonce indefinitely, and the locked KLAY on the destination bridge is permanently undeliverable.

---

### Finding Description

`handleKLAYTransfer` executes in this order:

```
_lowerHandleNonceCheck(_requestedNonce)          // (1) gate check
_voteValueTransfer(_requestedNonce)              // (2) operator vote
_setHandledRequestTxHash(_requestTxHash)         // (3) mark tx hash
handleNoncesToBlockNums[nonce] = blockNum        // (4) record nonce→block
_updateHandleNonce(_requestedNonce)              // (5) advance lowerHandleNonce
emit HandleValueTransfer(...)                    // (6) emit event
(bool ok,) = _to.call.value(_value)("")          // (7) PUSH transfer
require(ok, "handleKLAYTransfer: transfer failed") // (8) revert if failed
``` [1](#0-0) 

If step (7) fails — because `_to` is a contract with no payable fallback or one that deliberately reverts — step (8) causes the entire transaction to revert. Solidity's atomicity rolls back steps (3)–(6): `handledRequestTx[txHash]` is never set, `handleNoncesToBlockNums[nonce]` is never written, and `_updateHandleNonce` never fires.

`_updateHandleNonce` advances `lowerHandleNonce` only through a consecutive run of nonces whose `handleNoncesToBlockNums[i] > 0`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) { ... }
lowerHandleNonce = i;
``` [2](#0-1) 

Because the stuck nonce's entry is never written, `lowerHandleNonce` is permanently frozen at that slot. The `recoveryBlockNumber` also never advances past the block preceding the stuck nonce. [3](#0-2) 

At the Go level, `processingPendingRequestEvents` iterates events in nonce order. On any error from `handleRequestValueTransferEvent`, it re-queues the failing event and all subsequent ones and returns immediately:

```go
if err := bi.handleRequestValueTransferEvent(ev); err != nil {
    bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
    ...
    return
}
``` [4](#0-3) 

This means a transaction-submission-level error on the stuck nonce halts processing of all higher nonces in that batch.

The same push-revert pattern exists in `handleERC20Transfer` (via `IERC20.safeTransfer`) and `handleERC721Transfer` (via `IERC721.transferFrom`): [5](#0-4) [6](#0-5) 

---

### Impact Explanation

- **Permanent asset lock**: KLAY (or ERC-20/ERC-721 tokens) locked in the source-chain bridge contract can never be released on the destination chain for the stuck nonce. The user's funds are irrecoverably frozen.
- **`lowerHandleNonce` frozen**: The bridge's sequential nonce watermark never advances past the malicious nonce. `recoveryBlockNumber` is also frozen, causing the recovery daemon to re-scan the same block range on every tick.
- **Go-level pipeline stall**: If the on-chain transaction submission itself errors (e.g., gas estimation failure due to guaranteed revert), `processingPendingRequestEvents` re-queues and halts, blocking all subsequent nonces in that processing round.
- **Infinite retry cost**: The bridge operator wastes gas submitting transactions that will always revert.

---

### Likelihood Explanation

The attack requires only:
1. Deploying a contract with a reverting fallback (trivial, zero-cost beyond gas).
2. Calling `requestKLAYTransfer` with `_to` set to that contract on the source chain.

The `_to` address is fully user-controlled and is passed verbatim from the `RequestValueTransfer` event into `handleKLAYTransfer`. There is no validation of `_to` before the push transfer. Any user with a small amount of KLAY can execute this attack. [7](#0-6) 

---

### Recommendation

Replace the push pattern with a pull (withdrawal) pattern:

1. **For KLAY**: Instead of `_to.call.value(_value)("")`, record the claimable amount in a mapping (`pendingWithdrawals[_to] += _value`) and let the recipient call a separate `withdraw()` function. This decouples nonce advancement from delivery.
2. **For ERC-20**: Wrap `safeTransfer` in a `try/catch` (Solidity ≥0.6) or use a low-level call with a success check; on failure, credit the amount to a claimable mapping rather than reverting.
3. **For ERC-721**: Same approach — catch transfer failures and store the token ID in a claimable mapping.

This mirrors the fix recommended in the original M-4 report: disconnect the state update (nonce advancement) from the asset delivery so that a reverting recipient cannot roll back the nonce record.
