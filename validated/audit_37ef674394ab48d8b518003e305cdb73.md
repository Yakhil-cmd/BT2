### Title
Unbounded walk of alt-branch descendant units in MC stability determination enables computational DoS that stalls confirmation of new units - (File: main_chain.js)

### Summary
`determineIfStableInLaterUnits()` is invoked from `validateParents()` on essentially every incoming unit whose `last_ball_unit` is not yet marked stable in the local DB but must be checked for stability "in view of the parents" [1](#0-0) . This function walks all "alt branch" (non-main-chain) descendant units below the first unstable MC unit via `createListOfBestChildrenIncludedByLaterUnits()`, recursing through every non-included best-child unit with no bound on the number of units visited [2](#0-1) . Similar to the reported pattern, is an accumulating collection (here: alt-branch units below the first unstable MC point) that grows every time an unprivileged unit poster adds units, and is walked in full by a validation routine without any cap, size limit, or complexity charge, unlike the well-bounded loops elsewhere in the codebase (e.g. `MAX_COMPLEXITY`/`MAX_OPS` in `definition.js` and `formula/validation.js`).

### Finding Description
Any user can post ordinary units that attach as parents to older, non-best-parent branches instead of extending the current main chain tip. Because unit posting has no privilege requirement and no fee proportional to the resulting graph-walk cost, an attacker can keep growing the set of "alt branch" descendants under the first unstable MC unit.

When any node (or the attacker itself) posts a subsequent unit whose `last_ball_unit` references that not-yet-locally-stable ball, `validateParents()` calls `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag()` → `determineIfStableInLaterUnits()` [1](#0-0) . Inside, if there are alt branches, `createListOfBestChildrenIncludedByLaterUnits()` is called, which recursively walks down every non-included best-child of the alt branch roots, issuing a DB query and a `graph.determineIfIncludedOrEqual` check for every unit encountered [3](#0-2) . The recursion is only "yielded" every 100 iterations via `setImmediate` to avoid a stack overflow [4](#0-3) , but there is no upper bound on the total number of units traversed, no `MAX_COMPLEXITY`-style limit, and no charge to the unit poster for the resulting cost. `findBestChildrenNotIncludedInLaterUnits()` additionally re-walks removed best children with `graph.determineIfIncludedOrEqual` for each one [5](#0-4) .

This mirrors the reported bug class: an ever-growing, attacker-influenced collection (alt-branch descendant units) is iterated in full by a core routine, with no cap analogous to the missing "limit the amount of protections" recommendation in the source report.

### Impact Explanation
Because `determineIfStableInLaterUnits` is on the hot path of ordinary unit validation (`validateParents`), an attacker who cheaply grows the alt-branch unit set can make this computation arbitrarily expensive on every subsequent unit that needs its `last_ball` stability re-verified. This can stall or drastically slow down validation of new units across the network — i.e., "a network unable to confirm new units" — without requiring any privileged role, matching the acceptance criteria for this class of finding.

### Likelihood Explanation
Reachable by any unprivileged unit poster: parent selection that avoids the current best parent (creating alt branches) is a normal, permissionless operation, requiring no more than standard unit fees. No witness/hub/operator privilege is needed, and the cost of causing the recursive walk to grow is much lower than the CPU cost imposed on validating nodes, since a single crafted branch can force repeated re-walks on every future unit until stability is achieved.

### Recommendation
Introduce an explicit bound (count and/or depth) on the number of alt-branch units traversed by `createListOfBestChildrenIncludedByLaterUnits`/`goDownAndCollectBestChildrenFast`/`findBestChildrenNotIncludedInLaterUnits`, and fail closed (treat as "not yet determinable"/transient error) once the bound is exceeded rather than continuing an unbounded walk. Consider also charging non-best-parent unit authors an increasing fee or otherwise discouraging large numbers of never-finalized alt branches so the DB-backed traversal set cannot be cheaply inflated.

### Proof of Concept
1. Attacker repeatedly posts valid units that intentionally choose parents other than the current best-parent tip, so they land in a growing set of alt-branch descendants below the first unstable MC unit (permitted by `parent_composer.js`'s general parent-selection logic, no privilege required).
2. Any node validating a subsequent unit whose `last_ball_unit` matches the not-yet-stable ball triggers `validateParents()` → `determineIfStableInLaterUnits()` [1](#0-0) .
3. `createListOfBestChildrenIncludedByLaterUnits()` recurses through every accumulated alt-branch unit with per-unit DB queries and inclusion checks and no size cap [3](#0-2) , so as the attacker-controlled alt-branch set grows, each subsequent validation becomes proportionally slower, degrading or stalling the node's ability to confirm new units.
