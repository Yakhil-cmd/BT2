### Title
Cross-stack Status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes GitHub `status` webhook data to every `Commit` row that matches the bare `sha`, with no check that the commit's `stack.repository` matches the repository that authenticated the webhook. Because `Commit.sha` is not unique across stacks (an index exists on `(stack_id, sha)`, not on `sha` alone), a webhook validly signed for one organization/repository can create a `Status` on a commit belonging to a completely different stack/repository, which then feeds directly into `Commit#add_status` and `Stack#schedule_merges`, i.e. the merge queue.

### Finding Description
The broken binding: the code should enforce
`commit.stack.repository.full_name == payload.repository.full_name`
before writing a status, but it enforces nothing beyond
`commit.sha == params.sha`.

Path:
1. `Shipit::WebhooksController#verify_signature` verifies the webhook signature using `Shipit.github(organization: repository_owner)` [1](#0-0) . This proves only that the request was signed by *some* GitHub App/organization configured in Shipit — it says nothing about which `Stack`/`Commit` the `sha` in the body actually belongs to.
2. `WebhooksController#create` dispatches the parsed JSON straight to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler` [2](#0-1) [3](#0-2) .
3. `StatusHandler#process` loops over `Commit.where(sha: params.sha)` — a global, un-scoped query across every stack in the installation — and calls `commit.create_status_from_github!(params)` on each match [4](#0-3) . There is no filter on `repository`, `full_name`, or `stack_id` derived from the payload.
4. `Commit#create_status_from_github!` → `add_status` records the new `Status` and, whenever the resulting simple state becomes `pending` or `success`, calls `stack.schedule_merges` [5](#0-4) . If that `stack.merge_queue_enabled` is `true`, this schedules `ProcessMergeRequestsJob`, which evaluates the head of the merge queue and calls the merge/ship flow once required statuses (e.g. `sonarqube`) are green.
5. The existence of the migration `index_commits_on_stack_id_and_sha` (an index on `(stack_id, sha)`, not a unique index on `sha` alone) confirms the schema explicitly allows the same `sha` to legitimately exist under multiple different `stack_id`s (e.g. the same repository tracked by two stacks, or repositories sharing commit history through forks/subtree/mirrors). `StatusHandler` does not account for this and treats "same sha" as "same commit for purposes of writing a status."

Attacker request: any actor who can get a validly-signed `status` webhook accepted for *any* org/repo configured in this Shipit instance (e.g. their own repository if it is a tracked Shipit stack) sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: <valid for attacker's own org>
{"sha": "<sha shared with victim stack>", "state": "success", "context": "sonarqube", ...}
```
If any commit in a victim stack (requiring `sonarqube` and with `merge_queue_enabled: true`) has that same `sha` (via shared history), the handler writes a `success` `Status` for `sonarqube` onto the victim's commit, unblocking/advancing that victim stack's merge queue — a write and a merge/ship decision the victim repository never authenticated.

None of the existing guards stop this: `verify_signature` only authenticates the org that sent the request, not the SHA's ownership; `drop_unhandled_event` only checks the event type is registered; there is no `ExplicitParameters` constraint tying `sha` to `repository.full_name`; and `StatusHandler` itself performs no repository/stack scoping.

### Impact Explanation
A payload authenticated for repository A can mutate `Status` records (and, via `schedule_merges`/`merge_queue_enabled`, trigger merge-queue progression and downstream deploy scheduling) for a completely unrelated stack B's commit, as long as the two commits share a `sha`. This is a cross-tenant write: a record created for a repository that did not authenticate it, and it can force ship/merge decisions on the victim stack. This matches the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius is bounded by the requirement that the two commits share an actual SHA (a SHA-1 collision or, more practically, genuinely shared git history such as forks, subtrees, or repos with common ancestry/cherry-picked commits) — it is not an arbitrary attacker-chosen SHA on an arbitrary victim, but is fully repeatable against any stack whose commits are reachable this way.

### Likelihood Explanation
Preconditions: (1) attacker can get one validly-signed `status` webhook accepted, which typically requires controlling a repository/organization that is itself configured/onboarded into this Shipit instance (e.g. their own project); (2) a victim stack exists with `merge_queue_enabled: true` and a required status context (e.g. `sonarqube`); (3) a commit `sha` exists in both the attacker-controlled repo's history and the victim stack's commit table — most realistically via forked/mirrored repositories, shared monorepo history, or subtree-shared code, rather than a brute-forced SHA-1 collision. Given those preconditions, the attack is cheap (a single POST) and fully repeatable for every shared SHA. The likelihood is therefore conditioned on multi-tenant/shared-history topology rather than being universally exploitable against arbitrary unrelated victims, but where that topology exists, exploitation is trivial and requires no privilege beyond triggering one legitimate webhook.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other SHA-keyed handlers) to the repository that authenticated the webhook: join through `stack.repository` and filter `Commit.joins(:stack => :repository).where(sha: params.sha, shipit_repositories: { full_name: params.dig('repository', 'full_name') })` (or equivalent) before calling `create_status_from_github!`, so a status can only ever be applied to commits belonging to stacks whose repository matches the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_scoping_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerScopingTest < ActiveSupport::TestCase
        test "a status webhook authenticated for one repo must not affect a commit under a different repo sharing the same sha" do
          shared_sha = 'a' * 40

          attacker_repo  = Repository.create!(owner: 'attacker-org', name: 'attacker-repo')
          victim_repo    = Repository.create!(owner: 'victim-org',   name: 'victim-repo')

          attacker_stack = Stack.create!(repository: attacker_repo, environment: 'production')
          victim_stack   = Stack.create!(repository: victim_repo,   environment: 'production',
                                          merge_queue_enabled: true)

          # both stacks happen to contain a commit with the same sha (shared history / fork)
          attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared')
          victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: 'shared')

          # binding under test: a status for `sonarqube`, authenticated only for attacker_repo,
          # must equal: victim_commit.statuses.count unchanged
          before = victim_commit.statuses.count

          params = ActionController::Parameters.new(
            sha: shared_sha,
            state: 'success',
            context: 'sonarqube',
            repository: { full_name: attacker_repo.full_name } # what actually got authenticated
          )

          StatusHandler.new.process # invoked with the above params via handler harness

          after = victim_commit.reload.statuses.count

          assert_equal before, after,
            "status authenticated for #{attacker_repo.full_name} must not create a Status " \
            "on a commit belonging to #{victim_repo.full_name}'s stack"
        end
      end
    end
  end
end
```
This test currently fails against `StatusHandler#process`'s unscoped `Commit.where(sha: params.sha)` query, demonstrating the cross-repository write; it will pass once the handler is scoped to `repository.full_name`.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
