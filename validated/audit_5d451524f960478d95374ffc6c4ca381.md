### Title
Webhook authentication binds to `repository.owner.login`/`organization.login` while write targets are selected by `repository.full_name` / commit `sha`, letting an unconfigured-secret org unlock forged events for any tracked stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App config (and thus which `webhook_secret`) to verify the HMAC against using a value taken from the JSON body itself (`repository.owner.login`, falling back to `organization.login`), not from any independently-authenticated source. The actual data-mutating handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) then act on a completely different field of the same body - `repository.full_name` or a bare commit `sha` - without ever checking that it belongs to the organization that was used to select the signing secret. This is the same class of bug as the `_afterTokenTransfer` report: two values that are supposed to move together (the authenticated principal and the entity actually written to) are read from independent, unlinked places.

### Finding Description
`verify_signature` computes the authenticating organization purely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

It then verifies the signature using `Shipit.github(organization: repository_owner).verify_webhook_signature`. Critically, `GitHubApp#verify_webhook_signature` treats an **absent** `webhook_secret` as automatic success: [3](#0-2) 

`webhook_secret` is explicitly documented as **optional** per configured organization: [4](#0-3) 

and the shipped multi-org sample config shows organizations routinely configured with `webhook_secret: # nil`: [5](#0-4) 

So for any Shipit deployment hosting more than one GitHub org/App (a documented, supported topology - `github` is a hash keyed by organization in `lib/shipit.rb`), if even one configured org omits `webhook_secret`, `verify_signature` will accept **any** payload whose `repository.owner.login` (or `organization.login`) names that org, with no HMAC check at all.

Once past `verify_signature`, none of the handlers re-validate that the org used for authentication matches the repository/commit actually mutated. `Handler#repository_name` and every subclass resolve the target purely from `repository.full_name`: [6](#0-5) 

`PushHandler` triggers a real GitHub sync for the resolved stack: [7](#0-6) 

`StatusHandler` writes a `CommitStatus` for **any** commit matching a bare `sha` field, with no relation at all to `repository_owner`: [8](#0-7) 

`CheckSuiteHandler` similarly acts on `repository.full_name` + branch/sha, independent of `repository_owner`: [9](#0-8) 

Binding that should hold: `authenticated_org(repository_owner) == owner(repository.full_name used by handler)`. It does not, because (a) authentication can be trivially satisfied for any org lacking a `webhook_secret`, and (b) `repository.full_name`/`sha` used for writes is never checked against `repository_owner`.

### Impact Explanation
An unauthenticated remote attacker (no session, no `ApiClient` token, no `webhook_secret`, no GitHub App key) can POST a crafted JSON body directly to the public `/webhooks` endpoint. By setting `repository.owner.login` to any org in the instance's `Shipit.github` config that has no `webhook_secret` configured, they bypass signature verification entirely for that request, then set `repository.full_name` (for push/check_suite events) or `sha` (for status events) to target a completely unrelated, tracked stack/commit belonging to a *different*, properly-secured organization. This lets the attacker:
- Forge `commit_status` events (`StatusHandler`) to mark arbitrary commits as CI-passing (`state: success`), which can defeat `ci.require` checks gating deploys/merges for stacks that have nothing to do with the misconfigured org - an unauthorized-deploy vector.
- Force `GithubSyncJob`/`RefreshCheckRunsJob` runs on arbitrary stacks (denial-of-service adjacent, but also usable to prime state ahead of the forged status).

This reaches the "High" bar: escalation past webhook authentication into unauthorized write of stack/commit state, without any credential, purely by exploiting the disconnect between the field used to select the verifying secret and the field used to select the write target.

### Likelihood Explanation
Requires a Shipit instance configured with more than one GitHub org (a documented, supported setup) where at least one org omits `webhook_secret` (also documented as optional, and shown unset in the shipped sample config). Given that, exploitation needs nothing beyond a single unauthenticated HTTP POST - no secrets, no session, no prior access. Likelihood is directly tied to how many real deployments run multi-org with a lax org, which cannot be verified from the code alone (operator-dependent), but the code offers zero mitigation once that condition holds.

### Recommendation
- Do not let `verify_webhook_signature` return `true` when `webhook_secret` is blank; either require `webhook_secret` for every configured org or fail closed.
- Independent of secret presence, every handler that resolves a target repository/commit from the payload (`Handler#repository_name`, `StatusHandler#process`, `CheckSuiteHandler#process`, etc.) should assert that the resolved repository's owner matches the `repository_owner`/`organization` value that was used to select the verifying `GitHubApp`, rejecting the event otherwise.
- Consider deriving the verifying org from the installation/App identity (e.g., `installation.id` claim) rather than from attacker-controlled `repository.owner.login`/`organization.login`.

### Proof of Concept
1. Configure Shipit with two orgs in `github:` — `secure-org` (has `webhook_secret`) and `lax-org` (no `webhook_secret`, per the documented-optional setting).
2. Track a stack under `secure-org/target-repo` with `ci.require` gating deploys, and note an existing commit `sha`.
3. As an anonymous attacker, POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<target commit sha from secure-org/target-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "lax-org" }, "full_name": "lax-org/whatever" },
  "organization": { "login": "lax-org" }
}
```
No `X-Hub-Signature` needed (or any value) — `verify_webhook_signature` short-circuits to `true` because `lax-org` has no `webhook_secret`.
4. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — which matches the commit in `secure-org/target-repo` regardless of the `lax-org` value used for auth — and creates a passing `CommitStatus`, potentially unblocking a deploy that should have been CI-gated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
```
