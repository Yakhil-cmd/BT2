### Title
Reused Bitcoin L1-lockup outpoint can be re-submitted across separate `register-for-bond` calls to double-count sats commitment - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s sBTC/L1 lockup path validates each supplied Bitcoin lockup output via `verify-l1-lockups`, which folds over the supplied `outputs` list and de-duplicates outpoints only *within that single call's accumulator* (`seen-outpoints`) [1](#0-0) . There is no persistent, contract-level map recording previously-consumed outpoints across separate transactions, stakers, or bond registrations. This mirrors the reported `deposit()` bug class: the contract credits protocol-internal value (here, sats-backed bond commitment / reward shares) based on an unvalidated assumption — that presenting a valid Merkle/SPV proof for a UTXO always represents a *fresh* commitment — while never checking whether that exact outpoint has already been consumed to credit a bond elsewhere.

### Finding Description
`verify-l1-lockups` proves that Bitcoin outputs exist, match the expected lockup script, hash into a valid block header, and are unique *within the list passed to a single call* [2](#0-1) . The `seen-outpoints` list is built fresh inside the `fold` for each invocation (part of the `accumulator-res` threaded through `validate-l1-lockup`), so it cannot see outpoints consumed by *previous* transactions. Nothing in the surrounding code establishes a durable map (e.g., `used-l1-outpoints`) that would be checked and set persistently to prevent the same UTXO from being presented again in a later `register-for-bond` call — by the same staker or a different one — to mint additional bond `amount-sats` / reward shares against sats that were already counted once.

Because the same on-chain Bitcoin transaction and Merkle proof remain permanently valid and replayable (Bitcoin data doesn't change), any staker (or a colluding second staker) can resubmit the identical `{height, tx, output-index, header, leaf-hashes, tx-count, tx-index, amount, unlock-burn-height}` tuple in a subsequent `register-for-bond` call to credit `amount-sats` again, inflating `total-sbtc-staked`/bond shares without any additional BTC ever being locked.

### Impact Explanation
This breaks the equality between sats actually locked on Bitcoin and sats credited toward bond membership/reward shares in pox-5 — the exact analog class called out as in-scope ("sats credited by an L1 proof that were never locked on Bitcoin," "double-counting a commitment or reward"). An attacker can inflate their (or an accomplice's) bond stake and reward-share allocation with a single real BTC lockup replayed multiple times, diluting honest stakers' rewards and/or exceeding the signer's actual backing — a High severity impact under the stated criteria (reward weight/allocation exceeding locked value).

### Likelihood Explanation
Likelihood is high if no external persistence layer catches this: the attacker only needs one real, valid L1 lockup transaction and can call `register-for-bond` (or the bond-rollover paths that reuse `verify-l1-lockups`) multiple times with the same proof data, since Bitcoin SPV/Merkle verification is inherently replayable and the only de-duplication found in the reviewed code is scoped per-call.

### Recommendation
Introduce a persistent Clarity map (e.g., `used-l1-outpoints: {txid, output-index} -> bool`) that is checked and set to `true` the first time an outpoint is successfully validated by `verify-l1-lockups`/`validate-l1-lockup`, and have subsequent calls `asserts!` that the outpoint has not already been consumed, returning an error (e.g., `ERR_DUPLICATE_LOCKUP_OUTPOINT`) if so — extending the current in-call-only `seen-outpoints` check to a durable, contract-wide check.

### Proof of Concept
1. Staker A locks BTC in a valid L1 timelock script and obtains the SPV Merkle proof (`{height, tx, output-index, header, leaf-hashes, tx-count, tx-index, amount, unlock-burn-height}`).
2. Staker A calls `register-for-bond` supplying this proof, which passes `verify-l1-lockups`/`validate-l1-lockup` and credits `amount-sats` to their bond.
3. Staker A (or a colluding account B) calls `register-for-bond` again — for a different bond index or reward cycle — presenting the exact same proof tuple. Since `seen-outpoints` is reset per call (built fresh in `verify-l1-lockups`'s fold) [3](#0-2) , the second call again passes all checks and credits `amount-sats` a second time, without any additional BTC being locked.
4. `total-sbtc-staked`/bond reward shares are now double-counted against a single physical Bitcoin lockup — confirmed by the absence of any persistent outpoint-tracking map in the reviewed file.
