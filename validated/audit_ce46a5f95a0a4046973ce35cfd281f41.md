## Title
Merkle proof "node-as-leaf" malleability in `merkle.js` allows forging inclusion proofs for elements never actually in the tree, bypassing `in merkle` address-definition conditions and `is_valid_merkle_proof()` oscript checks - (File: merkle.js)

### Summary
`merkle.js` implements Merkle tree hashing and proof verification using an *unprefixed* SHA‑256 hash for both leaves and internal nodes: `hash(str) = sha256(str)` [1](#0-0)  is applied identically when hashing a leaf element and when hashing the concatenation of two child hashes to build an internal node [2](#0-1) . Because there is no domain-separation tag distinguishing "this is a leaf" from "this is an internal node", any string that happens to equal the *literal concatenation of two already-known hash values* in the tree hashes to exactly the same value as that internal node. `verifyMerkleProof` walks the supplied siblings from the claimed element up to the root with no leaf/node distinction, so it accepts a forged "leaf" that is actually the concatenation of two internal hash values, as long as the remaining sibling path is valid. The code even contains a developer comment acknowledging this exact class of bug: `// Node-as-Leaf issue might matter in some cases` [3](#0-2) . This is the identical bug class reported against tBTC's SPV proofs (leaf/internal-node ambiguity in a Merkle construction), except in ocore it requires **no brute force at all**: the attacker only needs to know two existing hash values in the tree (revealed e.g. via any legitimate proof) and concatenate them verbatim.

### Finding Description
- `getMerkleRoot`/`getMerkleProof` build the tree with `hash(arrHashes[i] + arrHashes[hash2_index])` at every level, with the same `hash()` used for leaves [2](#0-1) .
- `verifyMerkleProof(element, proof)` computes `hash(element)` and then repeatedly combines with `proof.siblings[i]` exactly the same way internal nodes were built, with no tag differentiating a leaf hash step from an internal-node hash step [4](#0-3) .
- Consequently, if an attacker knows two hash values `h_A`, `h_B` that are siblings at some internal level of a real tree (these are routinely exposed as `siblings` in any legitimate proof for a nearby leaf), they can set `element = h_A + h_B` (a literal base64 string ≤ 88 chars) and supply `proof = {index: position_of_that_internal_node, siblings: remaining_path_to_root, root: real_root}`. `verifyMerkleProof` will compute `hash(h_A+h_B)` which equals the real internal node's hash, then walk the true remaining siblings to the real, previously-published root — returning `true` even though `element` was never one of the tree's actual data elements.
- This routine is reachable from two ocore paths open to a single unprivileged unit/AA author:
  1. The `in merkle` address-definition authentifier: `validateAuthentifiers` deserializes an attacker-supplied proof and calls `merkle.verifyMerkleProof(element, proof)`, then checks only that `proof.root` matches a previously published data-feed value from the oracle [5](#0-4) . The `element` format check in `validateDefinition` allows exactly the base64 alphabet (`+`, `/`, `=`, alphanumerics) up to 100 characters [6](#0-5) , which is wide enough to hold two concatenated base64 SHA-256 hashes.
  2. The `is_valid_merkle_proof(element, proof)` oscript function, usable inside AA bounce/trigger logic, calls the same `merkle.verifyMerkleProof` with attacker/trigger-controlled `element` and `proof` [7](#0-6) .

### Impact Explanation
An address whose spending condition includes `["in merkle", [oracle_addresses, feed_name, element, min_mci]]` is meant to allow spending only if `element` is a member of a set whose Merkle root the oracle published via a data feed. Using the forgery above, an attacker who is a co-author/spender of such an address can satisfy this condition for an `element` that was never actually part of the oracle's original dataset, since only `proof.root` is checked against the published data feed value, and `verifyMerkleProof` cannot distinguish a forged internal-node-as-leaf from a real leaf. This results in unauthorized spending of funds locked under such conditions. The same primitive can be used inside Autonomous Agent logic that gates fund releases on `is_valid_merkle_proof`, causing AA fund loss when an attacker fabricates "membership" in a whitelist or dataset that was never granted.

### Likelihood Explanation
Exploitation requires no computational brute force — the attacker only needs to know two hash values that are siblings anywhere on a path in the real tree, which are trivially obtainable from any legitimate merkle proof issued for a neighboring element, or from full disclosure of the dataset (common for auditable oracle-published datasets). This makes the attack practical and cheap wherever `in merkle` or `is_valid_merkle_proof` is used to gate value.

### Recommendation
Add domain separation to `merkle.js`: prefix leaf hashing with a distinct tag/byte (e.g. `hash("leaf:" + str)`) and internal-node hashing with a different tag (e.g. `hash("node:" + left + right)`), or otherwise make it cryptographically infeasible for a leaf value to also be interpreted as an internal-node hash input. Update `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently, and treat this as a protocol/consensus-relevant change requiring an upgrade MCI gate similar to other oscript/format changes in this codebase.

### Proof of Concept
1. Oracle builds a Merkle tree over a private whitelist/dataset with `merkle.getMerkleRoot` and publishes the resulting root as a data feed value from address `O`.
2. Attacker requests/observes a legitimate `merkle.getMerkleProof` for any real element, revealing two sibling hash values `h_A`, `h_B` at some internal level of the tree (via `proof.siblings`).
3. Attacker crafts `forged_element = h_A + h_B` (fits the `in merkle` element regex, ≤100 chars) and `forged_proof = { index: <index of node C = hash(h_A+h_B)>, siblings: <the real remaining siblings from C to the root>, root: <the published root> }`.
4. Attacker posts a unit whose author has address definition `["in merkle", [["O"], "feed_name", forged_element]]`, supplying `assocAuthentifiers[path] = merkle.serializeMerkleProof(forged_proof)`.
5. `validateAuthentifiers` calls `merkle.verifyMerkleProof(forged_element, forged_proof)` [5](#0-4) , which succeeds because `hash(h_A+h_B)` equals the real internal node value, and the remaining path is genuine — `dataFeedExists` then confirms `proof.root` matches the oracle's published root, and the authentifier passes despite `forged_element` never being part of the original dataset.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
