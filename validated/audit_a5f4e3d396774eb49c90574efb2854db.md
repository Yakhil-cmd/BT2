### Title
Division-by-zero panic in `PoolState::token_price_x32` crashes swaps and permanently freezes trading in a pool - ([File: programs/cp-swap/src/states/pool.rs])

### Summary
`PoolState::token_price_x32` divides by `token_0_amount`/`token_1_amount` using raw `/` operators (not `checked_div`). These values come from `vault_amount_without_fee`, which is `vault_balance - accumulated_fees` for each side. Because vault balances can be driven down arbitrarily close to the accumulated (unwithdrawn) fee reserve through normal, permissionless one-directional swaps, an unprivileged swapper can force `token_0_amount` or `token_1_amount` to become exactly `0`, causing an unguarded integer division panic on every subsequent call — permanently breaking the pool's swap path (denial of service), analogous to the FlashMQ division-by-zero DoS.

### Finding Description
`vault_amount_without_fee` computes the "true" tradable balance of each token by subtracting the pool's accrued (but not yet collected) protocol/fund/creator fees from the raw vault balance: [1](#0-0) 

`token_price_x32` then immediately uses these fee-adjusted balances as divisors with plain integer division, which panics in Rust when the divisor is zero — no `checked_div`/`Option` guard is used, unlike almost every other arithmetic operation in this codebase (`Fees::*`, `ConstantProductCurve::*`, `checked_add/sub/mul`): [2](#0-1) 

This function is invoked on **every** swap through `get_swap_params`, which is called unconditionally at the start of both `swap_base_input` and `swap_base_output` before any curve math or slippage checks: [3](#0-2) [4](#0-3) [5](#0-4) 

An unprivileged swapper fully controls the direction and cumulative volume of swaps against a pool. By repeatedly swapping in one direction (e.g. always `OneForZero`, i.e. selling token_1 for token_0), the swapper continuously drains the raw `token_0_vault` balance while `protocol_fees_token_0`/`fund_fees_token_0`/`creator_fees_token_0` (fees which only accrue on `ZeroForOne` swaps) remain fixed from whatever was accrued earlier (potentially `0` for a fresh pool, or a small residual amount). Because vault draining is bounded only by the constant-product curve (checked via `checked_sub` in `ConstantProductCurve::swap_base_output_without_fees`/`swap_base_input_without_fees`), the swapper can choose swap sizes to land the raw vault balance for token_0 exactly at the accrued fee amount, making `total_input_token_amount` (or `total_output_token_amount`) resolve to `0` inside `vault_amount_without_fee`. On the very same or a subsequent transaction, `token_price_x32` then divides `Q32` (or the other side) by that `0` value and panics.

Once this state is reached, **every future swap instruction on that pool** will hit `get_swap_params` → `token_price_x32` and panic before the trade fee/curve logic even runs, because the fee reserves that keep the divisor pinned at zero are only cleared by admin `collect_*_fee` calls — and even a successful collection can be immediately re-triggered back to the zero state by the same one-directional swapping. This is a straightforward "unprivileged input drives a size/rate parameter to a value that a downstream unguarded division treats as its denominator" bug class — the exact analog of the FlashMQ CVE where a remote client's reachable path let a spread/timeout combination compute a zero divisor.

### Impact Explanation
A successful trigger causes any swap transaction (`swap_base_input` / `swap_base_output`) against the affected pool to panic and abort, and — because the zero-divisor condition is a persistent pool-state condition rather than a one-off input — the pool's swap functionality becomes durably unusable until an admin intervenes via `collect_protocol_fee`/`collect_fund_fee`/`collect_creator_fee` (and even that fix can be trivially undone by the same attacker with more one-directional swaps). This constitutes a permanent denial-of-service against the swap functionality of the pool, freezing LPs' ability to have their liquidity traded and freezing swappers' ability to trade against that pool — a legitimate availability impact reachable from a fully unprivileged, permissionless instruction.

### Likelihood Explanation
Reaching exact-zero requires precise sizing of swap amounts relative to the fee reserve, which is attacker-computable off-chain (fee reserves and vault balances are public account data, and swap amounts are fully attacker-controlled inputs to `swap_base_input`/`swap_base_output`). No special permissions, pool-creator or admin role, or non-default configuration is required beyond ordinary swapping — the fee-rate values in `AmmConfig` do not need to be anything unusual; only vault/fee-reserve arithmetic needs to line up, which is achievable by anyone with capital to perform a sequence of swaps.

### Recommendation
Change `token_price_x32` to use `checked_div`/`checked_mul` (matching the pattern in the rest of the codebase) and propagate an `ErrorCode` (e.g. reuse `ZeroTradingTokens`/`InsufficientVault`) instead of panicking on a zero divisor:

```rust
pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
    let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
    let price_1 = (token_1_amount as u128)
        .checked_mul(Q32)
        .and_then(|v| v.checked_div(token_0_amount as u128))
        .ok_or(ErrorCode::ZeroTradingTokens)?;
    let price_0 = (token_0_amount as u128)
        .checked_mul(Q32)
        .and_then(|v| v.checked_div(token_1_amount as u128))
        .ok_or(ErrorCode::ZeroTradingTokens)?;
    Ok((price_1, price_0))
}
```
This turns the crash into a clean, recoverable transaction error, consistent with how the rest of the arithmetic in `calculator.rs`, `fees.rs`, and `constant_product.rs` already handles divide-by-zero risk via `Option`-returning `checked_*` operations.

### Proof of Concept
1. Create a pool via `initialize`/`initialize_with_permission` with token_0/token_1 and default `AmmConfig` fee rates.
2. Repeatedly call `swap_base_output` (or `swap_base_input`) with `trade_direction = OneForZero` (selling token_1 for token_0), sized so that after `checked_sub` in `ConstantProductCurve::swap_base_output_without_fees`, the raw `token_0_vault.amount` converges to exactly `pool_state.protocol_fees_token_0 + pool_state.fund_fees_token_0 + pool_state.creator_fees_token_0` (attacker can compute the exact final swap amount from the publicly-readable vault/fee state before submitting the last transaction).
3. On the transaction where `vault_amount_without_fee(token_0_vault.amount, token_1_vault.amount)` returns `token_0_amount == 0`, the subsequent call `self.token_price_x32(input_vault_amount, output_vault_amount)` inside `get_swap_params` executes `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128`, dividing by zero and panicking, aborting the transaction.
4. Because the fee reserve remains pinned at the vault balance, every subsequent swap transaction against the pool hits the same panic until an admin calls `collect_protocol_fee`/`collect_fund_fee`/`collect_creator_fee` to shrink the reserve relative to the vault — at which point the attacker can simply repeat step 2 to re-trigger the DoS.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
