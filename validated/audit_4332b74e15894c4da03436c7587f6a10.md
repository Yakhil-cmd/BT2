### Title
Open Redirect via unvalidated `omniauth.origin` in `GithubAuthenticationController#callback` - (File: app/controllers/shipit/github_authentication_controller.rb)

### Summary
`GithubAuthenticationController#callback` takes `request.env['omniauth.origin']`, which is populated verbatim from the attacker-controlled `origin` query parameter on the initial `/github/auth/github` request, and passes it unvalidated into `redirect_to` after a successful GitHub OAuth login. This allows an attacker to craft a link that, once the victim completes GitHub authentication on the legitimate Shipit host, redirects the victim's browser to an arbitrary attacker-controlled URL.

### Finding Description
The broken binding: `return_url` used in `redirect_to(return_url)` should satisfy `return_url == a URL scoped to this Shipit host` (e.g., `root_path` or another same-origin path), but instead `return_url == request.env['omniauth.origin']`, which is fully attacker-controlled.

Code path: `Shipit::Authentication#force_github_authentication` at `app/controllers/concerns/shipit/authentication.rb:24,32` redirects unauthenticated users to `github_authentication_path(origin: request.original_url)` — this is the legitimate, safe usage that always sets `origin` to the current same-host URL. However, an attacker does not need to rely on this code path at all: they can directly craft a link to `GET /github/auth/github?origin=https://attacker.example`. The `OmniAuth::Builder` middleware mounted in `lib/shipit/engine.rb:46-51` (`OmniAuth::Strategies::GitHub`) stores the raw `origin` request parameter into `request.env['omniauth.origin']` by default, with no allowlist or same-host restriction configured in this engine. After the victim completes the GitHub OAuth dance and hits `GET/POST /github/auth/github/callback`, `GithubAuthenticationController#callback` (`app/controllers/shipit/github_authentication_controller.rb:8,20`) reads that same unrestricted `omniauth.origin` value and issues `redirect_to(return_url)` with no host validation.

None of the engine's other guards apply here: `force_github_authentication` only constrains the value it sets when *it* builds the redirect link, but it does not constrain what `omniauth.origin` can be if an attacker directly requests the auth start endpoint with their own `origin` param. There is no `verify_signature`, `ExplicitParameters` schema, or `Repository`/`Stack` validation on this flow, because this is a session/browser-redirect path, not a webhook or model-write path.

### Impact Explanation
This matches the High severity category "session fixation / forced OAuth completion" — more precisely, it is a post-authentication open redirect chained onto the OAuth completion of the victim's own Shipit session. The attacker cannot read the victim's session cookie (it's set with the browser's own protections), but they can force the victim's browser, immediately after successfully authenticating to the real Shipit host, to navigate to `https://attacker.example` with a Referer header. This can be used to phish the victim (e.g., presenting a fake Shipit/GitHub-branded page expecting them to be "logged in") or to relay any token/state placed in the URL. No repository, stack, or GITHUB_TOKEN data is directly exfiltrated by this bug alone — the impact is confined to browser redirection abuse rather than credential theft.

### Likelihood Explanation
Preconditions are minimal: Shipit must have GitHub OAuth configured (`Shipit.github.oauth?`, standard production requirement per `lib/shipit/engine.rb:46-50`), which is the default setup per `docs/setup.md`. The attacker needs no Shipit account, no session, and no secrets — only the ability to send the victim a link to `/github/auth/github?origin=<url>` on the legitimate Shipit host. This is trivially repeatable against any victim and does not depend on any specific repository or stack configuration.

### Recommendation
Validate `return_url` in `GithubAuthenticationController#callback` before redirecting — e.g., only allow relative/local paths (`URI.parse(return_url).path` with no host/scheme, or use `_url_host_allowed?`/`local_request?`-style checks), falling back to `root_path` for any URL that isn't same-host relative.
