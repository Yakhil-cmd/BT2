### Title
SSRF via Unvalidated Submodule URLs During `git submodule update` - (File: main.go)

### Summary
`git-sync` executes `git submodule update --init [--recursive]` on every synced worktree, using submodule URLs taken directly from the `.gitmodules` file inside the synced repository. Since `.gitmodules` is ordinary repo content, an attacker who can push a commit (or land a merged PR/branch) to the synced repository fully controls these URLs. `git-sync` performs no validation, allowlisting, or protocol restriction on submodule URLs before invoking git, making the server-side git process fetch attacker-chosen HTTP(S) endpoints — including internal/link-local addresses such as a cloud metadata service (`169.254.169.254`). This mirrors the reported `/nft-http-proxy` SSRF bug class: unvalidated attacker-supplied URLs trigger server-initiated requests to arbitrary/internal network destinations.

### Finding Description
In `configureWorktree`, after the main checkout, if submodules are enabled git-sync unconditionally runs: [1](#0-0) 

This builds the argv `submodule update --init` (optionally `--recursive`, `--depth N`) and executes it via `git.Run` against the checked-out worktree, without ever parsing, validating, or restricting the URLs recorded in `.gitmodules`. There is no protocol allowlist (e.g. no `protocol.file.allow`/`protocol.ext.allow`/`GIT_ALLOW_PROTOCOL` configuration anywhere in `main.go`), and no host/IP filtering of submodule URLs is performed anywhere in the codebase.

Because `.gitmodules` is tracked, versioned repository content, any actor capable of pushing a commit that reaches the synced ref (a malicious contributor, a compromised upstream branch, or an attacker who merges a PR into the tracked branch) can set a submodule `url` to `http://169.254.169.254/latest/meta-data/...` (AWS IMDS), `http://metadata.google.internal/...` (GCP), or any other internal-only endpoint reachable from the git-sync pod's network namespace. When git-sync's periodic sync loop calls `configureWorktree` for the new hash, git itself performs the outbound HTTP(S) request to that URL as part of the submodule fetch — this is the git-sync analog of the reported endpoint blindly proxying user-supplied URLs.

This is distinct from a purely academic concern: the e2e test suite explicitly exercises submodule URLs pointed at attacker/test-controlled hosts (including relative and multi-host submodule chains), confirming the code path is fully reachable and unauthenticated submodule URLs are honored as-is: [2](#0-1) [3](#0-2) 

### Impact Explanation
When git-sync is deployed with `--submodules` enabled (the codebase supports `off`/default/`recursive`/`shallow` modes) and the repository being synced accepts contributions from lower-trust actors (common in GitOps sidecar patterns where `git-sync` polls a shared/team repo), a malicious commit can force the pod running `git-sync` to issue HTTP(S) requests to arbitrary destinations reachable from that pod's network, including cloud-instance metadata services. Depending on the cloud platform and IAM/IMDS configuration, this can result in disclosure of instance credentials or metadata equivalent to the report's example (`droplet_id`, `user_data`, certificates, tokens) — the same class of impact the external report calls out, but the requesting party is git itself rather than a Node.js proxy. On IMDSv1-enabled AWS deployments this can escalate to credential theft for the pod's IAM role.

### Likelihood Explanation
Requires `--submodules` to be set to a non-`off` value (default is not `off`, per flag docs) and requires write/merge access to the synced repository or ref by a lower-trust party — a realistic scenario for shared config repos, GitOps monorepos with external contributors, or a compromised upstream dependency repo. No credentials, special git-sync flags beyond the normal submodule flag, or misconfiguration are needed beyond the default submodule-fetching behavior; git's own default protocol allowances (HTTP/HTTPS are always allowed) make this immediately exploitable without any additional bypass.

### Recommendation
- Do not fetch submodules from repository-controlled URLs without validation. Either disable submodules by default and require explicit opt-in per trusted URL, or resolve/validate submodule URLs against an operator-supplied allowlist of hosts before running `git submodule update`.
- Set `GIT_ALLOW_PROTOCOL` (or `protocol.*.allow` git config) to restrict submodule fetches to an explicit protocol/host allowlist supplied by the operator, not the repo content.
- Consider running submodule fetches through an egress-restricted network policy that blocks link-local/metadata IP ranges (169.254.169.254, metadata.google.internal, etc.) from the git-sync pod's network namespace, independent of code-level fixes, as defense-in-depth.

### Proof of Concept
1. Attacker with push/merge access to the synced repository's tracked branch adds a `.gitmodules` entry:
   ```
   [submodule "evil"]
       path = evil
       url = http://169.254.169.254/latest/meta-data/iam/security-credentials/
   ```
   and commits it (e.g. via `git submodule add http://169.254.169.254/... evil`), analogous to the test harness's own submodule-add pattern: [4](#0-3) 
2. Operator runs `git-sync` against this repo with `--submodules=recursive` (or default) as in normal deployment.
3. On the next sync cycle, `configureWorktree` runs `git submodule update --init --recursive` against the new worktree: [5](#0-4) 
4. Git, running inside the git-sync container, issues an HTTP GET to `169.254.169.254`, causing the metadata service response (potentially containing IAM credentials) to be written into the submodule's `.git` fetch data/error output, which is logged by `git.Run`'s error/output capture and may also be persisted to the working tree of the synced link, exposing the sensitive response content to any consumer of the synced volume.
