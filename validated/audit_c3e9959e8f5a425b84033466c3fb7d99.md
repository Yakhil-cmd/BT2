### Title
Uncaught `throw Error("base AA not found")` in `readBaseAADefinitionAndParams` crashes the node when a parameterized AA references a non‑existent base AA - (File: storage.js)

### Summary
`aa_validation.js`'s `validateAADefinition` only checks that a parameterized AA's `base_aa` field is a syntactically valid address; it never checks that the address actually corresponds to an existing AA definition. Later, when the parameterized AA is triggered, `storage.readBaseAADefinitionAndParams` fetches the base AA definition and, if it is missing, executes an unconditional `throw Error("base AA not found: " + base_aa)` inside an asynchronous DB callback. This is analogous to the FFmpeg `avcodec_open2` bug class: a required "pointer" (here, the base AA definition) is assumed to be valid without verification, and dereferencing/using it when absent crashes the process instead of failing gracefully.

### Finding Description
In `aa_validation.js`, the parameterized-AA branch of `validateAADefinition` performs only format-level checks on `base_aa`: [1](#0-0) 
It never verifies that `template.base_aa` is a real, previously-registered AA address (e.g., via `storage.readAADefinition`). Any unprivileged unit poster can therefore post a unit that defines a brand-new AA whose `base_aa` points to a plain wallet address, an unrelated non-AA address, or any other address that merely satisfies `isValidAddress`.

Later, when a trigger unit sends a payment to this newly defined parameterized AA, the AA execution path resolves the base definition via `storage.readBaseAADefinitionAndParams`: [2](#0-1) 
This calls `readAADefinition` on `base_aa`; if no row is found (because `base_aa` was never a real AA), `arrBaseDefinition` is `null` and the code throws an unhandled `Error` from inside a DB-query callback: [3](#0-2) 

Because this throw occurs inside an asynchronous callback (not inside the `try/catch` wrapped synchronous `validate()` call stack), it becomes an uncaught exception. `network.js` installs a global handler that deliberately re-throws to crash the process rather than continue in a possibly inconsistent state: [4](#0-3) 

### Impact Explanation
Any full node that processes the triggering payment to the malformed parameterized AA will hit the same missing-base-AA condition and crash via the `uncaughtException` handler. Since this is deterministic (same input, same code path on every node), it can be broadcast network-wide, taking down witness/hub/full nodes simultaneously — a network unable to confirm new units, matching the "network can't confirm units" impact class described in the validation rules. This differs from the FFmpeg NULL-deref only in language (JS `throw` vs C NULL pointer dereference), but the root cause pattern is identical: use of an unvalidated referenced object/function without existence checking, ending in a hard-crash instead of controlled error handling.

### Likelihood Explanation
Likelihood is high: the malformed AA definition passes the deployed validation logic (`validateAADefinition` never checks `base_aa` existence), and the crash path in `readBaseAADefinitionAndParams` is a normal part of AA trigger execution reached whenever the AA is invoked — no special privileges or timing needed, and any user able to post a unit (defining an AA and sending a small trigger payment) can exercise it.

### Recommendation
- In `aa_validation.js`'s parameterized-AA validation branch, verify that `template.base_aa` resolves to an actual, already-defined AA (e.g., call `storage.readAADefinition`/an equivalent existence check) before accepting the definition, and reject with a normal validation error (`callback("base_aa is not a defined AA")`) if it does not exist.
- As defense in depth, change the `throw Error("base AA not found: " + base_aa)` in `storage.readBaseAADefinitionAndParams` (storage.js line 824) to propagate a normal error/callback failure instead of throwing, so that a missing base AA at execution time (e.g., due to unforeseen state) does not crash the node.

### Proof of Concept
1. Attacker crafts and posts a unit defining a new AA:
   ```json
   ["autonomous agent", { "base_aa": "SOME_VALID_LOOKING_ADDRESS_THAT_IS_NOT_AN_AA", "params": { "x": "1" } }]
   ```
   `SOME_VALID_LOOKING_ADDRESS_THAT_IS_NOT_AN_AA` is any 32-byte base32 address that passes `isValidAddress` but was never registered as an AA (e.g., a normal wallet address, or simply never used before). `validateAADefinition` accepts this because it only checks `isValidAddress(template.base_aa)`.
2. The unit is accepted and the new parameterized AA address becomes active.
3. Attacker (or anyone) sends a small payment to the new AA address to trigger it.
4. During trigger processing, the node calls `readBaseAADefinitionAndParams`, which calls `readAADefinition(conn, base_aa, ...)`; since no `aa_addresses` row exists for `base_aa`, `arrBaseDefinition` is `null`.
5. `throw Error("base AA not found: " + base_aa)` fires inside the async DB callback, becomes an uncaught exception, and `network.js`'s `process.on('uncaughtException', ...)` re-throws it, crashing the node process — reproducible on every node that processes the trigger.

function readBaseAADefinitionAndParams(conn, address, to_mci, handleDefinitionAndParams) {
	if (!handleDefinitionAndParams)
		return new Promise(resolve => readBaseAADefinitionAndParams(conn, address, to_mci, (arrBaseDefinition, params, storage_size) => resolve({ arrBaseDefinition, params, storage_size })));
	readAADefinition(conn, address, to_mci, function (arrDefinition, unit, storage_size) {
		if (!arrDefinition)
			return handleDefinitionAndParams(null);
		var base_aa = arrDefinition[1].base_aa;
		if (!base_aa)
			return handleDefinitionAndParams(arrDefinition, null, storage_size);
		readAADefinition(conn, base_aa, to_mci, function (arrBaseDefinition) {
			if (!arrBaseDefinition)
				throw Error("base AA not found: " + base_aa);
			handleDefinitionAndParams(arrBaseDefinition, arrDefinition[1].params, storage_size);
		});
	});
}
