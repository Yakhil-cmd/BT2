### Title
Cross-organization/cross-repository CI status forgery via `StatusHandler` — signature verified against attacker's org but write is unscoped to any repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a webhook against using an organization name taken from the *body of the request itself* (`repository.owner.login`, attacker-controlled). `Shipit::Webhooks::Handlers::StatusHandler#process`, however, applies the resulting event globally by commit SHA (`Commit.where(sha: params.sha)`) with no re-check that the matched commit actually belongs to the organization/repository whose secret was used to authenticate the request. In a Shipit instance configured for multiple GitHub organizations, this breaks the binding "organization that authenticated == repository that is written," letting an admin of any one configured organization forge a CI status for a commit belonging to a *different* organization's stack.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration where each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's app/secret to verify the raw request body against by reading `repository_owner`, which is taken straight out of the untrusted JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), before the handlers ever check consistency between that value and the rest of the payload [2](#0-1) .

Because the attacker fully controls the raw body they sign, they can pick any organization they legitimately administer (and thus whose `webhook_secret` they legitimately know, since GitHub App webhook secrets are configured by the org/app owner) as `repository.owner.login`, causing `verify_signature` to authenticate the request using their own org's secret — while placing arbitrary, unrelated content elsewhere in the same signed payload.

For `status` events, `StatusHandler#process` uses only the attacker-supplied `sha` to find the affected commit(s), with no scoping to `repository.full_name`/organization at all, unlike `PushHandler`, which does scope via `Handler#stacks`/`repository_name` [3](#0-2) [4](#0-3) . `Commit#create_status_from_github!` then persists a `Status` record with attacker-controlled `state`, `context`, `description`, and `target_url` for whatever commit matches that SHA in the entire shared Shipit installation [5](#0-4) .

Creating a `Status` triggers `enable_ci_on_stack` and `schedule_continuous_delivery` [6](#0-5) , meaning a forged "success" status matching the victim stack's required `ci.require` context can flip a commit's CI-gating state and, if continuous delivery is enabled on the victim stack, trigger an unauthorized deploy of a commit that never actually passed CI.

Equality broken: `organization authenticated by verify_signature (attacker's own org, via repository.owner.login)` ≠ `organization/repository whose Commit/Status is written (any stack in the shared install, keyed only by sha)`.

### Impact Explanation
This allows an org-admin of *any* organization configured on a shared multi-tenant Shipit instance to forge CI statuses for commits belonging to a completely different organization's stacks (commit SHAs are public/guessable from the victim's GitHub commit history). If the forged status satisfies `ci.require`/`ci.blocking` contexts, and the victim stack has continuous delivery enabled, this results in an unauthorized deploy being triggered — matching the High-impact category "escalation into ... unauthorized deploy" from the rules.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub organizations (`Shipit.github_organizations` returning more than one org — a supported, documented configuration), and (2) the attacker being an admin of at least one such organization (able to configure that org's own webhook secret on the shared GitHub App), which is not a privilege over the victim's org/repo. No `ApiClient` token, no GitHub App private key, and no access to the victim's secret is required.

### Recommendation
In `WebhooksController#verify_signature` and each `Handler`, cross-validate that the authenticated organization (used to select the webhook secret) matches the organization/repository actually referenced by the event payload before processing. In particular, `StatusHandler#process` (and any other handler that doesn't already use `Handler#stacks`/`repository_name`) should scope commit/status lookups to the repository asserted by the verified organization, e.g. `commit.stack.repository.owner == repository_owner`, rejecting the event otherwise.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-org config per `lib/shipit.rb#github_app_config`).
2. As an admin of `attacker-org`, know `attacker-org`'s `webhook_secret`.
3. Craft a `status` event JSON body:
```json
{
  "sha": "<victim-org-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant-repo" }
}
```
4. Compute `X-Hub-Signature` using `attacker-org`'s webhook secret over this exact body.
5. POST to `/github/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and succeeds (attacker knows this secret).
7. `StatusHandler#process` runs `Commit.where(sha: "<victim-org-commit-sha>")`, unrelated to `attacker-org`, and creates a forged `success` `Status` on the victim's commit, potentially satisfying `ci.require` and triggering `schedule_continuous_delivery` on the victim's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
