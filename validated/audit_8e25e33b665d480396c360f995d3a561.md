### Title
`name()`/`symbol()` on the ERC20 asset precompile revert on non-UTF-8 metadata bytes, violating ERC20's non-reverting metadata expectation - ([File: substrate/frame/assets/precompiles/src/lib.rs])

### Summary
The `ERC20` precompile that exposes `pallet-assets` tokens through Solidity's `IERC20Metadata` interface implements `name()` and `symbol()` by decoding the raw metadata bytes stored in `pallet-assets` as UTF-8, and reverts the call if decoding fails. `pallet-assets::set_metadata` does not validate that `name`/`symbol` are valid UTF-8 — it only bounds their length — so any asset owner can store arbitrary non-UTF-8 bytes as an asset's name/symbol. Any external caller (EVM contract, wallet, or aggregator) that subsequently calls `name()`/`symbol()` on that asset's precompile address will receive a revert instead of the ERC20-mandated return value.

### Finding Description
`pallet_assets::do_set_metadata` bounds `name`/`symbol` to `T::StringLimit` bytes but performs no UTF-8 validation: [1](#0-0) 

The extrinsic that invokes it is callable by any signed account that owns the asset (asset creation itself is permissionless / trust-backed in typical AssetHub-style configurations, so an ordinary user can create an asset and immediately call `set_metadata` on it): [2](#0-1) 

The stored bytes are exposed unchanged through the `fungibles::metadata::Inspect` trait: [3](#0-2) 

The ERC20 precompile's `name()` and `symbol()` implementations assume these bytes are valid UTF-8 and revert if `String::from_utf8` fails: [4](#0-3) 

This mirrors the root cause in the referenced report: a function that is expected by the ERC20/IERC20Metadata interface to always return a value is implemented with an unchecked decode step (`abi.decode`/`String::from_utf8`) that can revert when the underlying token/asset data does not conform to the assumed encoding, breaking any caller relying on ERC20-standard, non-reverting metadata accessors.

### Impact Explanation
Any EVM contract, wallet, indexer, or DeFi aggregator that calls `name()` or `symbol()` on the ERC20 precompile address of an asset whose metadata contains non-UTF-8 bytes will have that call revert instead of returning a string, as mandated by `IERC20Metadata`. This is a functional/DoS issue for tooling and any on-chain contract that assumes metadata calls succeed (e.g., batch integrations iterating over token lists), but it does not lead to loss of funds, unbacked issuance, or unauthorized dispatch — the affected asset's core `transfer`/`balanceOf`/`allowance` functionality is unaffected, and the only asset impacted is the one whose owner set the malformed metadata. This bounds the issue to Low/Medium severity, consistent with the equivalent Medium-severity classification given to the original Timeswap `safeName()` finding.

### Likelihood Explanation
Reaching this bug requires no privileged role: any account able to create an asset (in a permissionless asset-creation environment such as AssetHub's trust-backed assets) and set its own metadata via the standard `set_metadata` extrinsic can trigger it, with no governance or root access needed. The precompile's `name()`/`symbol()` are freely callable by any external contract or off-chain caller with no gating. Likelihood is therefore high for occurrence, but impact is limited to the read/metadata surface, not the transfer/settlement path.

### Recommendation
In `substrate/frame/assets/precompiles/src/lib.rs`, avoid an unconditional revert on invalid UTF-8: fall back to a lossy conversion (e.g., `String::from_utf8_lossy`) or return an ABI-encoded raw `bytes`/empty string rather than reverting, similar to how BoringSolidity's `safeName()` degrades gracefully instead of failing. Alternatively/additionally, enforce UTF-8 validation in `pallet_assets::do_set_metadata` (`substrate/frame/assets/src/functions.rs`) so malformed metadata can never be stored in the first place.

### Proof of Concept
Not independently executed against a live network per program rules; the failure path is derivable directly from source: `do_set_metadata` (substrate/frame/assets/src/functions.rs:1058-1104) has no UTF-8 check on `name`/`symbol`; `ERC20::name`/`ERC20::symbol` (substrate/frame/assets/precompiles/src/lib.rs:663-693) call `String::from_utf8(...).map_err(|_| Error::Revert(...))`. A minimal FRAME/pallet-revive integration test would: (1) create an asset with a signed, non-privileged origin, (2) call `set_metadata` with a `name`/`symbol` byte vector containing an invalid UTF-8 sequence (e.g., `vec![0xFF, 0xFE]`), (3) invoke the ERC20 precompile's `name()`/`symbol()` calldata against that asset's precompile address, and (4) assert the call returns `Error::Revert` rather than an ABI-encoded string — confirming the ERC20-metadata revert. This reproduction path was traced through source but not executed as a live test run in this analysis.

	/// Execute the name call.
	fn name(
		asset_id: <Runtime as Config<Instance>>::AssetId,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		env.charge(<Runtime as Config<Instance>>::WeightInfo::get_metadata())?;

		let metadata = pallet_assets::Pallet::<Runtime, Instance>::get_metadata(asset_id)
			.ok_or(Error::Revert(Revert { reason: "Metadata not found".into() }))?;

		let name = alloc::string::String::from_utf8(metadata.name.to_vec())
			.map_err(|_| Error::Revert(Revert { reason: "Invalid UTF-8 in name".into() }))?;

		Ok(IERC20::nameCall::abi_encode_returns(&name))
	}
