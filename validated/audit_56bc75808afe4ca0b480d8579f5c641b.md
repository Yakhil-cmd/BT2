This report describes a vulnerability specific to an EVM-style decentralized exchange contract (e.g., 0x-protocol-like `matchOrders`/`cancelOrder` pattern), where order identity is derived from a `salt` field, filled amounts are tracked in a `fills` mapping, and cancellation sets that mapping entry to `UINT256_MAX`. This pattern — hash-based order identity with a `salt=0` collision between "unfilled" and "cancelled" sentinel values — has no structural analog in the Polkadot SDK codebase I could find.

I searched for order-matching/order-book primitives, salt-based order hashing, and fill-tracking maps across the repo. The closest matches are unrelated concepts:
- `pallet-order-book`-style coretime `on_demand` orders, which are FIFO-queued core purchase requests with no hash/salt identity or fill-tracking semantics [1](#0-0) .
- `salt` usage in `pallet-revive` refers to contract address derivation for `CREATE2`-style instantiation (collision/duplicate-contract handling), not order cancellation [2](#0-1) .
- NFT atomic swaps in `pallet-nfts` have a `cancel_swap` extrinsic, but swaps are keyed by collection/item identifiers, not a salt-derived order hash with a fills-remaining accounting scheme [3](#0-2) .

None of these involve the reported invariant violation (a default/zero sentinel value in a fill-tracking map colliding with an explicit "fully cancelled" sentinel value, allowing salt-0 orders to become uncancelable/unusable). Since the underlying design pattern being reported doesn't exist in this codebase, there is no reachable Polkadot SDK analog to report.

/// All queued on-demand orders.
#[derive(Encode, Decode, TypeInfo)]
pub struct OrderQueue<N> {
	queue: BoundedVec<EnqueuedOrder<N>, ConstU32<ON_DEMAND_MAX_QUEUE_MAX_SIZE>>,
}

impl<N> OrderQueue<N> {
	/// Pop `num_cores` from the queue, assuming `now` as the current block number.
	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}

	fn new() -> Self {
		OrderQueue { queue: BoundedVec::new() }
	}

	/// Try to push an additional order.
	///
	/// Fails if queue is already at capacity.
	fn try_push(&mut self, now: N, para_id: ParaId) -> Result<(), ParaId> {
		self.queue
			.try_push(EnqueuedOrder { para_id, ordered_at: now })
			.map_err(|o| o.para_id)
	}

	fn len(&self) -> usize {
		self.queue.len()
	}
}

doc:
- audience: Runtime Dev
  description: |-
    Fixes https://github.com/paritytech/polkadot-sdk/issues/12639

    A contract's `ContractInfo` is not written to `AccountInfoOf` until its constructor
    frame pops, so the `is_contract` collision guard in `ContractInfo::new` could not see an
    address that was still being constructed. A re-entrant `CREATE2` with the same salt and
    code (which is nonce independent) therefore resolved to the same address and ran a second
    constructor frame for one account, permanently leaking its consumer reference and code
    refcount and orphaning the second child trie's storage deposit.

    `push_frame` now rejects a nested instantiate whose target address already appears as a
    `Constructor` frame on the call stack, returning `DuplicateContract` (matching EIP-684).
