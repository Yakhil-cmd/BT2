### Title
Cross-organization webhook signature confusion allows forging commit statuses for any repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The bug report describes a "lock more to unlock" fairness bug where a check is anchored to the wrong scope (a global gate applied unconditionally to state set before the gate existed). The Shipit analog is a webhook-signature scope confusion: the field used to select *which* organization's secret verifies the signature (`repository.owner.login`) is never bound to the field the handler actually acts on (the commit `sha`, which is not scoped to any repository at all in `StatusHandler`). Anyone who controls a GitHub App/webhook secret for *any* organization configured on the Shipit instance can forge a signed webhook that writes a fabricated CI status onto a commit belonging to a completely different organization's stack.

### Finding Description
`WebhooksController#verify_signature` selects the HMAC secret to check using only the organization named in the attacker-controlled payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app config purely from `params.dig('repository','owner','login')` (or `organization.login`), which is just JSON supplied by the caller and part of the raw body over which the HMAC is computed. This is a legitimate multi-organization feature documented for the operator: each org can be given its own GitHub App and webhook secret. [3](#0-2) 

The signature only proves "this body was signed with organization X's secret" — it does not prove that the payload's other fields (e.g. the repository actually being mutated) belong to organization X. `Shipit::Webhooks::Handlers::StatusHandler` then processes the `status` event by looking up commits **purely by sha, with no repository scoping at all**: [4](#0-3) 

Contrast this with the base `Handler` class, which *does* provide a `stacks` helper scoped to the repository named in the payload — a helper `StatusHandler` never uses: [5](#0-4) 

So the binding that should hold — "organization whose secret authenticated the request" == "organization/repository whose data is written" — is broken. An attacker who owns/administers Organization A (with its own GitHub App configured on this Shipit instance, per the documented multi-org setup) knows Organization A's webhook secret. They can:
1. Learn a target commit `sha` belonging to a victim stack/repository (commit SHAs are public on GitHub).
2. Build a `status` webhook payload with `repository.owner.login = "OrgA"` (so `verify_signature` picks Organization A's secret) but `sha = <victim commit sha>`, `state = "success"`, and fabricated `context`/`description`.
3. Sign the raw body with Organization A's secret and POST it to `/webhooks`.
4. `verify_signature` succeeds (correct secret for the org named in payload), and `StatusHandler#process` writes a fabricated passing status onto the victim's commit — with no check that the commit belongs to a stack under Organization A at all.

### Impact Explanation
`ci.require` / `ci.blocking` in `shipit.yml` gate deploys on GitHub commit statuses: [6](#0-5) 

Because `StatusHandler` writes statuses without any ownership check, an attacker who legitimately controls one organization's Shipit GitHub App/webhook secret can forge a "green" CI status on a commit belonging to an entirely different organization's repository, satisfying required-status gates and enabling an **unauthorized deploy** of code they do not control — a cross-repository / cross-organization integrity break with no dependency on Shipit session cookies, `ApiClient` tokens, or GitHub repository write access. This matches the report's "Critical ... unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability requires only that the attacker administers one organization's GitHub App onboarded to the shared Shipit instance (a documented, supported multi-tenant configuration) and knows a target commit's SHA (public GitHub data). No cross-org privileges, GitHub write access, or Shipit credentials are required — only the ability to send an HTTP POST with a validly-signed body for the attacker's own organization.

### Recommendation
Bind the verified signature to the data actually acted upon:
- Verify the webhook signature using the secret tied to the *repository* being mutated (derived consistently, and cross-checked against `repository.full_name`), not solely the loosely-typed `repository.owner.login`/`organization.login` field.
- In `StatusHandler` (and any other handler that doesn't already do so), scope lookups by the repository the webhook actually names (using `Handler#stacks`) rather than querying `Commit` globally by `sha`.
- Reject webhooks where the organization used to select the verification secret doesn't match the repository owner encoded in `repository.full_name`.

### Proof of Concept
1. Attacker controls "OrgA", which is configured in this Shipit instance's `secrets.yml` `github:` multi-org block with its own `webhook_secret` (known to the attacker, since they configured their own GitHub App).
2. Attacker identifies a commit SHA `deadbeef...` belonging to `victim-org/victim-repo`, tracked by a Shipit stack.
3. Attacker builds JSON body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/some-repo"},
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/circleci",
  "description": "forged",
  "target_url": "https://example.com"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` passes because `Shipit.github(organization: "OrgA")` matches the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` (`app/models/shipit/webhooks/handlers/status_handler.rb:21`), finds the victim's commit (no org/repo check), and creates a fabricated "success" status on it — usable to pass `ci.require` gates and trigger an unauthorized deploy of `victim-org/victim-repo`.

<h3 id="ci">CI</h3>

**<code>ci.require</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to disallow deploys if any of them is missing on the commit being deployed.

```yml

  require:
    - ci/circleci
```

**<code>ci.hide</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want Shipit to ignore.

For example:
```yml
ci:
  hide:
    - ci/circleci
```

**<code>ci.allow_failures</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to be visible but not to required for deploy.

For example:
```yml
ci:
  allow_failures:
    - ci/circleci
```

**<code>ci.blocking</code>** contains an array of the [statuses context](https://docs.github.com/en/rest/reference/commits#commit-statuses) you want to disallow deploys if any of them is missing or failing on any of the commits being deployed.

For example:
```yml
ci:
  blocking:
    - soc/compliance
```
