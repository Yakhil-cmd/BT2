### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` but event handlers act on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery in multi-tenant deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook against using `repository.owner.login` (or `organization.login`), but every event handler that actually mutates state resolves the target `Stack`/`Repository`/`ReviewStack` from an entirely separate JSON field, `repository.full_name`. Because HMAC verification only proves the raw body was signed with *some* configured organization's secret — not that the org whose secret was used matches the org whose repository is acted upon — any tenant who legitimately knows their own organization's `webhook_secret` (a normal, unprivileged fact for a Shipit tenant, not a stolen credential) can forge a signed webhook payload that claims to be from their own org while embedding another organization's `repository.full_name`, causing Shipit to execute privileged repository/stack actions against a victim tenant it has no authorization over.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret this way: [1](#0-0) [2](#0-1) 

`repository_owner` — used only to pick the `Shipit.github(organization:)` config for HMAC verification — comes from `repository.owner.login`. But once verification passes, `create` dispatches the *entire* payload to handlers unchanged: [3](#0-2) 

The base `Handler` class (used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the actual `Repository`/`Stack` it acts on from a different field, `repository.full_name`: [4](#0-3) 

All `pull_request` handlers do the same via `params.repository.full_name`: [5](#0-4) 

`Repository.from_github_repo_name` performs a plain lookup with no cross-check against `repository.owner.login`: [6](#0-5) 

So the field the signature-selection logic trusts (`repository.owner.login` / `organization.login`) and the field the business logic trusts (`repository.full_name`) are two independent, attacker-controlled strings inside the same signed byte blob. HMAC verification only proves *"the body's bytes were signed with organization X's secret"* — it says nothing about which organization's data is inside that body. Any legitimate tenant of a multi-org Shipit installation (who necessarily knows their own `webhook_secret`, since they configured it when onboarding their GitHub App) can therefore sign a payload that names their own org in `repository.owner.login` (to pass verification) while setting `repository.full_name` to a victim tenant's repository. This breaks the binding: `organization that authenticated == repository that is written`.

### Impact Explanation
This lets one tenant of a shared, multi-org Shipit instance perform unauthorized cross-organization writes against another tenant's stacks without ever touching the victim's real GitHub org, webhook secret, or credentials:
- `PushHandler#process` forces `stack.sync_github(expected_head_sha:)` on the victim's stacks: [7](#0-6) 
- `pull_request` handlers create/archive/unarchive `ReviewStack`s belonging to the victim repository and attribute the action to an arbitrary `sender.login` GitHub identity: [8](#0-7) [9](#0-8) 

This is a cross-repository/cross-tenant write triggered by an entity that never authenticated as, or was authorized by, the victim organization — matching the Critical "cross-repository writes" impact criterion.

### Likelihood Explanation
Requires only that the attacker be a legitimate tenant of a shared, multi-organization Shipit deployment (`Shipit.github_organizations` with more than one entry, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section). Knowing one's own `webhook_secret` is not privileged access to Shipit or to the victim — it is normal tenant setup information. No GitHub App private key, `GITHUB_TOKEN`, `api_clients_secret`, or victim credentials are needed. Crafting an arbitrary HTTP POST with a valid HMAC computed from a known secret is straightforward.

### Recommendation
After signature verification, re-derive the organization from the payload's actual target repository (e.g., the owner segment of `repository.full_name`) and require it to match the organization whose secret verified the signature (`repository_owner`). Reject the webhook if they differ, instead of trusting `repository.full_name` unconditionally in handlers.

### Proof of Concept
1. Attacker legitimately administers `AttackerOrg`'s GitHub App on a shared Shipit instance and knows `AttackerOrg`'s `webhook_secret` (set during onboarding).
2. Attacker crafts a raw JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, body)>` and sets `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `"AttackerOrg"`, loads `AttackerOrg`'s app, and the HMAC check succeeds (attacker knows this secret).
5. `Shipit::Webhooks::Handlers::PushHandler.call(params)` runs, reading `repository.full_name` = `"VictimOrg/victim-repo"`, finds `VictimOrg`'s real `Stack`, and forces `stack.sync_github(expected_head_sha: "deadbeef...")` — an action on a repository the attacker has no authorization over, driven entirely by a signature that only ever proved knowledge of the attacker's own secret.
