### Title
Cross-organization commit-status forgery via webhook signature/repository binding mismatch enables unauthorized deploys - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit's webhook signature verification authenticates the *organization* claimed in the payload, but the handlers that act on the payload (in particular `StatusHandler`) never verify that the affected resource actually belongs to that organization. This is the same class of bug as the `EthosVouch` report: an operation (`increaseVouch`) is trusted based on a check performed for a *different, earlier* context (the initial `vouch`) rather than being independently re-verified for the actual value being acted upon. Here, the webhook signature check binds trust to "organization O signed this request," while the effect (`Commit.where(sha:)` / status creation) is applied to whatever `sha` appears in the payload, with no verification that the commit belongs to O's own repositories.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from the payload itself and uses that organization's configured `webhook_secret` to validate the HMAC: [1](#0-0) [2](#0-1) 

Shipit supports multiple GitHub organizations, each with its own independent `webhook_secret` looked up via `Shipit.github(organization:)`: [3](#0-2) [4](#0-3) 

Once the HMAC is valid for *some* organization, `WebhooksController#create` dispatches the raw, attacker-controlled JSON body to the matching event handler with no further scoping: [5](#0-4) 

`StatusHandler#process` then acts on **any** commit in the database matching the `sha` field, without checking that the commit's repository/stack belongs to the organization that signed the request: [6](#0-5) 

The binding being broken is:
`organization that authenticated the webhook (via `repository_owner` / `webhook_secret`)` ≠ `repository/stack whose commit status is actually written (`Commit.where(sha:)`, unscoped by owner)`.

Because a valid HMAC only proves the sender knows *some* organization's `webhook_secret` (an unprivileged party if they legitimately administer their own org's GitHub App installation registered in this multi-tenant Shipit instance), and because `StatusHandler` never cross-checks the payload's `repository` against the commit it is mutating, an attacker who controls organization A can forge a `status` event carrying a `sha` belonging to organization B's stack and set an arbitrary CI status (`state`, `context`, `description`, `target_url`).

### Impact Explanation
Commit statuses created this way feed directly into deploy-gating logic (`ci.require` / `blocking_statuses` in `DeploySpec`, referenced via `required_statuses`): [7](#0-6) 

By forging a `success` status for a required CI context on a commit that never actually passed CI in the victim organization/repository, an attacker without any credentials, repository access, or `ApiClient` token for the victim stack can make that commit appear deployable, leading to an **unauthorized deploy** of unverified code — a cross-repository/cross-organization write bound to the Critical impact bucket (unauthorized deploy).

### Likelihood Explanation
This requires only that the Shipit instance is configured for multiple organizations (`Shipit.github_organizations`/per-org `webhook_secret`), and that the attacker is a legitimate, unprivileged participant for *any one* of those organizations (e.g. they administer their own org's GitHub App/webhook registered in the shared Shipit deployment). No repository write access, no Shipit session, and no victim-org credentials are needed — only knowledge of their own organization's already-authorized webhook secret plus the target `sha`, which is discoverable via the public Shipit UI/API for the victim stack.

### Recommendation
In `StatusHandler#process` (and any other handler resolving global `Commit`/`Repository` records from unscoped payload fields), require that the commit's stack/repository matches the `repository.full_name` (or `repository.owner.login`) that was authenticated in `WebhooksController#verify_signature`, e.g. filter `Commit.where(sha: params.sha)` further by `repository: stacks(payload)` (matching the `Handler#stacks`/`repository_name` helper already used by other handlers) so the authenticated organization cannot write statuses for commits outside its own repositories.

### Proof of Concept
1. Attacker legitimately administers organization `A`, which is registered in this Shipit instance's multi-org GitHub config with its own `webhook_secret`.
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim_org_B_commit_sha>",
  "state": "success",
  "context": "ci/circleci",
  "repository": {"owner": {"login": "A"}, "full_name": "A/some-repo"}
}
```
3. Attacker computes `X-Hub-Signature` using A's own `webhook_secret` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"A"`, looks up A's `webhook_secret`, and the signature validates successfully [1](#0-0) .
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which executes `Commit.where(sha: params.sha)` — matching organization B's commit — and calls `create_status_from_github!`, creating a forged `success` status for B's commit [6](#0-5) .
6. If B's stack requires that CI context for deploys, the commit now satisfies `required_statuses`/deployability checks despite never having passed real CI, enabling an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
