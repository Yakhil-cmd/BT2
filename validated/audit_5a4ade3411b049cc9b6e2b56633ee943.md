### Title
Cross-tenant Team/Membership write via GitHub-ID-only team lookup in `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a `membership` webhook against the organization named in the top-level `organization.login` field (via the `repository_owner` fallback), but `MembershipHandler#find_or_create_team!` looks up the target `Shipit::Team` solely by `params.team.id` (the GitHub team's numeric ID), never checking that the team actually belongs to the organization that was authenticated. An attacker who legitimately controls one organization onboarded into Shipit (and thus possesses that organization's `webhook_secret`) can forge a `membership` event that authenticates as their own org but supplies the `team.id` of a team belonging to a different org already present in Shipit's database, causing that unrelated team's membership roster to be mutated.

### Finding Description
The claimed binding is: `organization_verified_by_repository_owner == organization_of_Team_row_mutated_by_handler`.

- `WebhooksController#verify_signature` resolves `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to select the `GitHubApp` whose `webhook_secret` verifies the HMAC signature [2](#0-1) . `membership` payloads have no top-level `repository` key, so `organization.login` is always the value used to pick the verifying secret.
- Once verified, `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| team.organization = params.organization.login end` [3](#0-2) . The `organization` assignment inside the block only runs on **creation**; when a `Team` row with that `github_id` already exists (belonging to a different organization), `find_or_create_by!` returns the existing row untouched, and the handler proceeds to call `team.add_member(member)` or `team.members.delete(member)` on it [4](#0-3) .
- Nothing in `MembershipHandler`'s `ExplicitParameters` schema or `process` cross-checks that the found team's `organization` column matches `params.organization.login` [5](#0-4) .

Exploit flow: attacker legitimately owns/administers org **A** in the multi-tenant Shipit deployment (has App installed, knows/can trigger deliveries signed with A's `webhook_secret` from `secrets.github[:A]`, resolved via `Shipit.github(organization:)` / `github_app_config` [6](#0-5) ). They send `POST /webhooks` with `X-Github-Event: membership`, a body whose `organization.login = "A"` (so `verify_signature` succeeds using A's secret) and `team.id` set to the known/guessed GitHub numeric ID of a `Shipit::Team` already onboarded for org **B**, plus `member.login` of an account they control. `find_or_create_team!` matches the existing org-B `Team` row purely by `github_id`, and `team.add_member(member)` writes a new `Shipit::Membership` row binding the attacker's controlled account to org B's team — despite the request never being authenticated against org B's secret.

Existing guards do not catch this: `verify_signature` only proves the request was signed by *some* configured org, not that it matches the org whose data is later mutated; the `ExplicitParameters` schema for `MembershipHandler` validates field types/presence but not cross-org consistency; there is no `Team` uniqueness/foreign-key constraint tying `github_id` to `organization` that would reject a mismatched write.

### Impact Explanation
An attacker legitimately controlling one Shipit-configured organization can insert or remove `Shipit::Membership` rows for a `Shipit::Team` belonging to a completely different organization, without ever proving control of that second organization. If the targeted team's handle is listed in `Shipit.github_teams` (used for OAuth-team based authorization, see `lib/shipit.rb:256-258`), the attacker-controlled user gains a `Membership` row that could feed into Shipit's authorization checks — escalation into `Shipit.github_teams` authorization, matching the High severity category in scope. This is repeatable against any `Team` row whose GitHub numeric ID the attacker can learn (team IDs are often discoverable via the public GitHub API), and the write survives regardless of the organization actually authenticated by the signature.

### Likelihood Explanation
Requires (a) a multi-tenant Shipit deployment where the attacker legitimately administers at least one configured organization (and thus its `webhook_secret`), and (b) that a `Shipit::Team` row for a different, victim organization already exists in the Shipit database with a discoverable GitHub team ID. Given those preconditions — realistic for any multi-org Shipit installation — the attack is a single crafted HTTP POST, fully repeatable, and costs the attacker nothing beyond knowing the target team's GitHub ID.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if a `Team` with that `github_id` exists under a different organization instead of silently reusing it.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, illustrative — actual file is out of scope per rules but demonstrates the binding check):
1. Seed `shipit_teams(:shopify_developers)` with `organization: 'shopify'`, `github_id: 48`.
2. Configure a second org `acme` with its own `webhook_secret` in test secrets, and stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` / directly hit `verify_signature` with `Shipit.github(organization: 'acme')`.
3. POST a `membership` event with `organization: { login: 'acme' }`, `team: { id: 48, name: 'Developers', slug: 'developers', url: '...' }`, `member: { login: 'attacker_login' }`, `action: 'added'`, signed with `acme`'s secret.
4. Assert equality that should hold: `params.organization.login` ("acme") used for signature verification must equal `Team.find_by(github_id: 48).organization` ("shopify") for the write to be legitimate — assert they differ (`refute_equal 'acme', Team.find_by(github_id: 48).organization`) yet assert a `Membership` row was still created linking `attacker_login` to `shipit_teams(:shopify_developers)` (`assert Team.find(shipit_teams(:shopify_developers).id).members.exists?(login: 'attacker_login')`), proving the cross-tenant write.

Note: I was unable to fully verify (due to iteration limits) the exact downstream authorization logic in `User#authorized?`/`app/controllers/concerns/shipit/authentication.rb` that consumes `Shipit.github_teams`, nor `db/schema.rb` constraints on the `teams` table; these are cited as areas warranting confirmation but do not change the core finding that `find_or_create_team!` fails to scope by organization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
