### Title
`repository_owner` fallback to `organization.login` lets a webhook signed by one tenant's secret mutate another tenant's `PullRequest` via `AssignedHandler` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to verify the HMAC signature using `repository_owner`, which falls back to `params.dig('organization','login')` whenever `repository.owner.login` is absent from the payload. `AssignedHandler`, however, resolves the target repository/stack strictly from `params.repository.full_name`, a field that is completely independent of `repository_owner`. An attacker who controls a legitimately-configured Shipit tenant/org (and thus its webhook secret) can sign a payload with their own org's secret while pointing `repository.full_name` at a victim repository/stack, causing the handler to overwrite that victim stack's `PullRequest#github_pull_request` record.

### Finding Description
The broken binding the code implicitly assumes is:
`repository_owner (used to select the verifying GitHubApp/secret) == owner(params.repository.full_name) (used by the handler to select the mutated record)`

This is never enforced. `repository_owner` is computed as: [1](#0-0) 
i.e. `params.dig('repository','owner','login') || params.dig('organization','login')`. `verify_signature` uses this value to pick the GitHub App/secret via `Shipit.github(organization: repository_owner)`: [2](#0-1) 

`Shipit.github` resolves per-organization config from `secrets.github`, raising `GithubOrganizationUnknown` only if the named organization has *no* configured entry at all: [3](#0-2) 

Meanwhile, `AssignedHandler`'s params schema only `requires :repository { requires :full_name }` — it does **not** require `repository.owner.login`: [4](#0-3) 

and it resolves the repository/stack purely from `params.repository.full_name`, decoupled from whatever `repository_owner` value authenticated the request: [5](#0-4) 

**Exploit flow:** In a multi-tenant Shipit deployment (multiple orgs configured under `secrets.github`), an attacker who legitimately controls one onboarded organization ("attacker-org") knows its own webhook secret (they configured/received it as that tenant). They craft a `pull_request`/`assigned` webhook payload:
- `organization.login = "attacker-org"` (their own, valid secret)
- `repository` object present but with **no** `owner.login` key, only `full_name = "victim-org/victim-repo"`
- `pull_request` object with attacker-chosen `title`, `assignees`, `labels`, `head.sha`, `additions`/`deletions`, etc.

They sign the raw body with `attacker-org`'s webhook secret and POST to `/webhooks` with `X-Github-Event: pull_request`. `repository_owner` evaluates to `"attacker-org"` (since `repository.owner.login` is absent), so `verify_signature` picks and successfully validates against `attacker-org`'s secret — the request passes authentication. `Shipit::Webhooks.for_event('pull_request')` dispatches to `AssignedHandler#process`, which looks up `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and, if a `PullRequest` with the given `number` exists for that repository's stack, calls `pull_request.update(github_pull_request: params.pull_request)` — overwriting `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, and `head` (creating/looking up a `Commit` by attacker-supplied `head.sha`) on a record belonging to a repository that never authenticated this request.

Existing guards do not stop this: `verify_signature` only checks that the HMAC matches *some* configured org's secret, not that the org matches the repository being mutated; the `ExplicitParameters` schema in `AssignedHandler` does not require `repository.owner.login` at all, so there's nothing forcing the two fields to agree; and there's no cross-check anywhere between `repository_owner` and `params.repository.full_name`.

### Impact Explanation
The attacker can force Shipit to write attacker-controlled data into a `PullRequest` record belonging to a stack/repository they do not own, satisfying the "payload for one repository mutating another's stack, commit, task or team" Critical category. Concretely it lets the attacker: (a) mutate PR metadata (`title`, `state`, `labels`, `assignees`) on the victim stack's tracked pull request, (b) force `find_or_create_commit_from_github_by_sha!` to create/fetch a `Commit` for an attacker-chosen `sha` under the victim's stack via `stack.github_api.commit(...)`, and (c) fire `Hook.emit('pull_request', stack, ...)` on the victim's stack. However, `AssignedHandler` itself does not call `Commit#deployable?`, trigger deploys, or read `ignore_ci`; that codepath belongs to deploy/merge-triggering handlers, not this one — so the "ignore_ci short-circuits CI" premise in the question is not actually exercised by `AssignedHandler`, and no deploy/rollback/merge is directly executed by this handler. The demonstrable impact is limited to unauthorized cross-tenant *record mutation* and Hook emission, not an unauthorized deploy.

### Likelihood Explanation
This requires a specific precondition not fully in the attacker's unilateral control: Shipit must be running the multi-organization GitHub App configuration (`secrets.github` keyed by org) with at least two onboarded organizations, and the attacker must legitimately control one of them (know its webhook secret) while targeting another tenant's repository/stack by name. This is plausible in a genuinely multi-tenant Shipit deployment where multiple independent GitHub orgs are onboarded to a shared instance, but is not exploitable by a fully anonymous internet attacker with zero relationship to any configured org — they need at least one legitimately configured org's secret. Given that constraint, the attack is fully repeatable and costs only one crafted HTTP request per target `(victim repo, PR number)` pair.

### Recommendation
In `WebhooksController`, require that `repository.owner.login` be present and used for signature-verifier selection (do not silently fall back to `organization.login` when `repository` is present but incomplete), and separately, in each handler (e.g., `AssignedHandler`), verify that the repository resolved from `params.repository.full_name` belongs to the same organization/login that authenticated the request (`repository_owner`) before performing any lookup or mutation — reject the event otherwise.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Stub `Rails.application.credentials.github` to return a multi-org config with two orgs: `"attacker-org"` (`webhook_secret: "attacker-secret"`) and `"victim-org"` (`webhook_secret: "victim-secret"`).
2. Create a `victim-org/victim-repo` `Stack` with an existing `PullRequest` (`number: 42`, `title: "original"`).
3. Build payload: `action: "assigned"`, `number: 42`, `pull_request: {... title: "PWNED", head: {sha: attacker_sha, ref: "x"}, assignees: [...], labels: [...] }`, `repository: {full_name: "victim-org/victim-repo"}` (no `owner` key), `organization: {login: "attacker-org"}`, `sender: {login: "attacker"}`.
4. Sign the JSON body with `"attacker-secret"` and POST to `/webhooks` with `X-Github-Event: pull_request` and the computed `X-Hub-Signature`.
5. Assert response is `200`/`:ok` (signature accepted, `repository_owner == "attacker-org"`).
6. Reload the victim `PullRequest` and assert `title == "PWNED"` — proving a request authenticated by `attacker-org`'s secret mutated `victim-org`'s record, i.e. `repository_owner ("attacker-org") != owner(params.repository.full_name) ("victim-org")` yet the write succeeded.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
