### Title
Uncaught exception in `isChashValid` on malformed base64 addresses causes unhandled crash / validity-disagreement risk - (File: chash.js)

### Summary
The CVE-2016-1839 root cause is a size/length-calculation error in libxml2's string dictionary that lets a crafted input drive an internal buffer computation into an inconsistent state, causing an out-of-bounds read that the caller does not expect and cannot recover from. The closest reachable analog in `ocore--004` is `isChashValid()` in `chash.js`, whose base64/base32 decode path length checks are only partially validated: the length invariant it depends on (`160`/`288` bits) is enforced only implicitly via a `throw` deep inside a helper that is called *outside* the function's `try/catch` block, so a malformed but same-length-looking address string can drive the checksum-position logic into a state that throws an uncaught error rather than returning `false`.

### Finding Description
`isChashValid(encoded)` only wraps the *decoding* step in `try/catch`: [1](#0-0) 

After decoding, it calls `buffer2bin(chash)` and `separateIntoCleanDataAndChecksum(binChash)`. The latter enforces the expected total bit length (`160` or `288`) and `throw`s a plain `Error` if the decoded buffer produced a bit-length that doesn't match, e.g. when `chash_length===288`, the base64 branch decodes via `Buffer.from(encoded, 'base64')`, which Node.js decodes leniently (silently skipping characters outside the base64 alphabet) — a 48-character `encoded` string is not guaranteed to decode to exactly 36 bytes if it contains characters Node treats specially: [2](#0-1) 

This `throw` occurs *after* the `try/catch` in `isChashValid` has already exited, so it is unhandled by `isChashValid` itself: [3](#0-2) 

`isChashValid` is the sole validity gate used transitively by `isValidChash`, `isValidAddressAnyCase`, `isValidAddress`, and `isValidDeviceAddress` in `validation_utils.js`: [4](#0-3) 

These address-validation helpers are invoked pervasively while validating externally supplied data: unit authors' addresses, address-definition chashes in `definition.js`, AA addresses in `aa_validation.js`, and payment/asset addresses in `validation.js`. Any code path that calls these helpers on attacker-controlled 32- or 48-character strings without its own additional `try/catch` will propagate the unhandled `Error`, exactly analogous to how libxml2's dictionary function let a crafted length/offset computation escape the caller's normal bounds checking and crash the process instead of failing gracefully.

### Impact Explanation
An unhandled synchronous exception thrown from deep inside address validation, if it occurs on a call path lacking its own guard, can crash the Node.js process handling unit/AA-trigger/joint validation (uncaught exception terminates the process by default in Node unless a top-level domain/handler catches it). If this occurs non-deterministically depending on implementation-specific base64 decoding behavior across engines/versions, different full nodes could also disagree on whether a given unit/address is valid — one node might throw and reject/crash, another might successfully decode and accept — creating a node-disagreement-on-validity condition, which maps to "node disagreement on validity or stability" in the given impact classes.

### Likelihood Explanation
Reaching this requires a single crafted 32- or 48-character address-like string (e.g., embedded as a unit author address, a definition chash, or an AA trigger address) reaching `isValidAddress`/`isValidChash` without an intervening `try/catch`, which is a normal, unprivileged, single-unit-poster-reachable condition. However, whether Node's `Buffer.from(str, 'base64')` can actually be coerced to decode a 48-character string into a byte length other than 36 (rather than simply producing 36 bytes padded/truncated per its documented leniency) needs to be empirically confirmed against the exact Node.js runtime in use; this is uncertain from static review alone. The `throw Error("bad length=...")` and `throw Error("wrong encoded length: ...")` guards elsewhere suggest the maintainers were aware of length-mismatch cases but placed the guard outside the function's protective `try` block.

### Recommendation
- Expand the `try/catch` in `isChashValid()` (and in `separateIntoCleanDataAndChecksum` / `mixChecksumIntoCleanData`) to cover the entire body so any length-mismatch `throw` is converted into a `return false` instead of propagating as an unhandled exception.
- Validate that the decoded buffer's byte length exactly equals the expected `chash_length/8` immediately after decoding, before calling `buffer2bin`, rather than relying on the downstream helper to detect the mismatch.
- Audit all call sites of `isValidAddress`, `isValidChash`, `isValidAddressAnyCase`, and `isValidDeviceAddress` to confirm each caller is wrapped in error handling appropriate for untrusted/attacker-controlled input.

### Proof of Concept
Concrete exploitation requires confirming, in the target Node.js version, an input string of exactly 48 characters for which `Buffer.from(encoded, 'base64')` yields a byte length other than 36 (e.g., a string containing whitespace or non-base64-alphabet characters that Node silently drops during decode, shortening the effective decoded payload while the JS string `.length` remains 48). Passing such a string as `encoded` to `chash.isChashValid()` — reachable via `isValidAddress()`/`isValidChash()` on a unit author address, AA trigger address, or definition chash field of a posted unit — will cause `separateIntoCleanDataAndChecksum` to `throw Error("bad length=...")` outside of `isChashValid`'s `try/catch`, propagating as an unhandled exception in the caller. I was not able to execute this against a live Node runtime to confirm the exact decoded byte length for a crafted string, so this PoC path is a strong hypothesis based on code inspection rather than a verified reproduction.

function isChashValid(encoded){
	var encoded_len = encoded.length;
	if (encoded_len !== 32 && encoded_len !== 48) // 160/5 = 32, 288/6 = 48
		throw Error("wrong encoded length: "+encoded_len);
	try{
		var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
	}
	catch(e){
		console.log(e);
		return false;
	}
	var binChash = buffer2bin(chash);
	var separated = separateIntoCleanDataAndChecksum(binChash);
