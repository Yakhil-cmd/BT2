### Title
Webhook signature verification is bound to an attacker-controlled organization field, letting a forged status/check_suite webhook write to any repository's commits - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to use for HMAC verification based on a field taken directly out of the unauthenticated JSON body (`repository.owner.login`, falling back to `organization.login`). That same body is later handed to event handlers (e.g. `StatusHandler`, `CheckSuiteHandler`) which use a *different*, also attacker-controlled field (`sha`, `repository.full_name`) to decide which `Commit`/`Stack` to mutate. Because the field used to pick the verifying secret is never checked against the field used to select the target repository/commit, a party who knows (or owns) the webhook secret for *any* organization configured in the Shipit instance can forge a validly-signed webhook whose `repository.owner.login` names their own org (to pass signature verification) while its payload (`sha`, `state`, `context`, `check_suite.head_sha`) targets a commit belonging to a completely different organization/stack.

### Finding Description
`verify_signature` in `WebhooksController`: [1](#0-0) 
computes the verifying `github_app` from `repository_owner`, which is read straight out of the untrusted JSON body: [2](#0-1) 

`github_app.verify_webhook_signature` only checks that the raw body's HMAC matches the secret configured for *that* organization: [3](#0-2) 
It never asserts that `repository.owner.login` matches the repository named elsewhere in the same payload (`repository.full_name`), nor that the commit `sha` the handler will act on actually belongs to a stack under that verified organization.

Once the signature check passes, `create` dispatches the parsed body to handlers for the event without any additional binding check: [4](#0-3) 

`StatusHandler#process` looks up commits purely by `sha`, globally, with no repository/organization scoping at all: [5](#0-4) 

`CheckSuiteHandler#process` scopes by `Repository.from_github_repo_name(repository.full_name)` via `Handler#stacks`, a field completely independent from the `repository_owner` used for signature verification: [6](#0-5) [7](#0-6) 

This is the same bug class as the report: a value that is supposed to be re-derived/re-checked at the moment it is actually used (`_lgeTimeStamp` re-validating on each LGE application) is instead left stale/unchecked — here, "the organization whose secret validated the signature" is never re-checked against "the repository/commit the payload actually writes to." The equality that should hold but doesn't is:
`organization_that_authenticated(repository.owner.login) == organization_owning(target_commit/target_repository)`.

### Impact Explanation
An attacker who administers (or has learned the webhook secret of) any single GitHub organization configured in this Shipit instance can forge `status` or `check_suite` webhooks that:
- Set a fabricated CI status (e.g. mark a required check as `success`) on an arbitrary commit belonging to a stack under a *different* organization/repository they don't control, via `StatusHandler`, which has zero repository scoping.
- Trigger `schedule_refresh_check_runs!` / `sync_github` against stacks of arbitrary other repositories tracked by the instance, via `CheckSuiteHandler`/`PushHandler`, which are scoped only by attacker-supplied `repository.full_name`.

Because Shipit gates deploys/merges on commit statuses and CI checks, injecting a forged passing status for a required context on a victim stack's commit can be used to satisfy deploy/merge safety checks that should have required real CI from the victim's GitHub repository — an escalation into deploy authorization decisions using a credential (webhook secret) that was never meant to authorize anything for that repository. This matches the "unauthorized deploy" / escalation criteria in scope.

### Likelihood Explanation
Exploitation requires only knowledge of one legitimately-configured organization's `webhook_secret` in the multi-organization `secrets.yml` (`Shipit.github_organizations`), which is a materially weaker requirement than repository write access, an `ApiClient` token, or `api_clients_secret`. Any tenant/org onboarded into a shared multi-org Shipit deployment inherently possesses this credential for its own org and can immediately use it to target other orgs' stacks, since the code performs no cross-check between the authenticating org and the acted-upon repository.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after verifying the signature, re-derive the organization that owns the target repository/commit from the handler's own resolved `Stack`/`Repository` and require it to equal the organization whose secret validated the signature, rejecting (422) on mismatch — mirroring the report's recommendation to re-validate the binding at the point of use rather than relying on a value established earlier under different trust assumptions. Concretely, `StatusHandler` should scope `Commit.where(sha:)` through `stacks`/`Repository.from_github_repo_name(repository.full_name)` (as `CheckSuiteHandler` does), and the controller should compare that repository's resolved organization against `repository_owner` before dispatching.

### Proof of Concept
1. Attacker administers `org-attacker`, configured in Shipit's `secrets.yml` with a known `webhook_secret`.
2. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "<head sha of a commit belonging to victim stack under org-victim>",
     "state": "success",
     "context": "required-ci-check",
     "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-attacker/some-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature` using `org-attacker`'s webhook secret over the raw body.
4. `verify_signature` resolves `repository_owner` = `"org-attacker"`, loads `org-attacker`'s `github_app`, and the signature verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and creates a status record via `create_status_from_github!`, marking `required-ci-check` as `success` on a commit the attacker never had rights over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
