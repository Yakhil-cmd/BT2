### Title
Pull-request label names bypass `deploy.variables` env whitelist enforced by `EnvironmentVariables#permit` - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Stack#env` values reaching `Command` are supposed to be filtered through `filter_deploy_envs`/`filter_task_envs`, which call `EnvironmentVariables#permit` to raise `NotPermitted` for any key not declared in `deploy.variables`. `ReviewStack#env` injects PR label names directly into the merged env hash without ever calling `filter_deploy_envs`/`permit`, so any collaborator able to attach a label to a PR can set an arbitrary-named environment variable (value `"true"`) on that stack's deploy/task commands, regardless of how restrictively the repository's `deploy.variables` whitelist is configured.

### Finding Description
The broken binding: maintainers assume `deploy.variables` (enforced via `DeploySpec#filter_deploy_envs` → `EnvironmentVariables#permit`, [1](#0-0) ) protects **every** env value that reaches `Command#unbundled_env`/`PTY.spawn`. That is false for `ReviewStack`s.

- `ReviewStack#env` merges one `"true"` entry per PR label (uppercased) directly on top of `Stack#env`, with no call to `filter_deploy_envs`, `filter_task_envs`, or `EnvironmentVariables#permit`: [2](#0-1) 
- `TaskCommands#env` (used by both deploys and generic tasks) merges `@stack.env` unconditionally, then separately merges `@task.env`, which *is* the filtered value (`Stack#build_deploy` calls `filter_deploy_envs(env.to_h)` before persisting `Task#env`, and `Stack#trigger_task` calls `definition.filter_envs(env)`): [3](#0-2) [4](#0-3) 
- `EnvironmentVariables#permit` is the only enforcement point of the whitelist, and it is never invoked on the path from `pull_request.labels` to `TaskCommands#env`: [5](#0-4) 
- The merged hash is passed straight into `Command`, whose `unbundled_env` merges `@env` (stringified) into the process environment given to `PTY.spawn`: [6](#0-5) 

Exploit flow: an attacker (or anyone with label-write access on the target repository, which is typically a collaborator/triage-or-above role — not the repo owner/maintainer who set the restrictive whitelist) adds a label `ld_preload` to a PR that has a corresponding `ReviewStack`. This is captured via the `labeled` webhook by `LabelCapturingHandler#capture_labels`, which stores `pull_request.labels` verbatim: [7](#0-6) . On the next deploy/task, `ReviewStack#env` turns that label into `env['LD_PRELOAD'] = 'true'`, which is merged into `TaskCommands#env` and ultimately into the spawned process's environment — never touching `filter_deploy_envs`/`permit`, even though the identical key submitted through the API's `env` param on `@deploy.env` would be rejected by that exact same repository's `deploy.variables = ['REGION']` whitelist.

Existing guards checked and found not to cover this path: `filter_deploy_envs`/`filter_task_envs`/`EnvironmentVariables#permit` are called for API/form `env` params (`Stack#build_deploy`, `Stack#trigger_task`, `TaskDefinition#filter_envs`) but are structurally absent from `ReviewStack#env` and from `TaskCommands#env`'s merge of `@stack.env`. Webhook signature verification and `capture_labels` correctly authenticate that the label list came from GitHub, but they enforce nothing about which env names labels are allowed to produce — that's an orthogonal control from the whitelist being bypassed.

### Impact Explanation
Any actor who can attach a label to a PR tracked by a `ReviewStack` can inject an arbitrary-named environment variable (fixed value `"true"`) into every deploy/task command run for that review stack, completely bypassing a maintainer-configured `deploy.variables` whitelist meant to restrict which env vars can be set. This value is attacker-controlled only in its *key* (the label name, upcased), not its content — the value is always `"true"`. This still permits behavior-changing injections (e.g., forcing on debug/unsafe flags gated by presence of a specific env var name), and it definitively demonstrates whitelist bypass for the `ReviewStack#env` path versus the API path, matching the "unauthorized configuration reaching the deploy host, bypassing an intentional whitelist" class of issue. Full RCE (e.g., true `LD_PRELOAD` code execution) would additionally require control over the variable's *value* to point at an attacker-supplied shared object on the deploy host, which this bug alone does not grant.

### Likelihood Explanation
Requires: (1) the target repository is configured as a `ReviewStack`-provisioning repo, (2) the attacker (or a compromised/malicious collaborator) has permission to add a label to a PR in that repository — on GitHub this typically requires at least "triage" role, which is a privileged (non-anonymous, granted) permission, not something an arbitrary internet user or a first-time external contributor can normally do. This materially reduces feasibility versus a fully unauthenticated attacker, but the divergence in the whitelist enforcement itself is a genuine code-level bug independent of who can trigger it.

### Recommendation
Route `ReviewStack#env`'s label-derived variables (and any other value merged into `Stack#env`/`TaskCommands#env` from non-operator-controlled sources) through the same `deploy.variables`/`EnvironmentVariables#permit` whitelist used for `@deploy.env`, or explicitly document/enforce that label-derived vars use a separate, clearly-labeled namespace (e.g. `LABEL_<NAME>`) so they cannot collide with or bypass whitelisted variable names.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual addition)
test "label-derived env bypasses deploy.variables whitelist" do
  stack = shipit_stacks(:review_stack)
  stack.cached_deploy_spec = create_deploy_spec(
    "deploy" => { "variables" => [{ "name" => "REGION" }] }
  )
  stack.pull_request.labels = ["ld_preload"]

  # API-path env would be rejected by the whitelist:
  assert_raises(Shipit::EnvironmentVariables::NotPermitted) do
    Shipit::EnvironmentVariables.with('LD_PRELOAD' => 'true')
      .permit(stack.cached_deploy_spec.deploy_variables)
  end

  # But the identical key via ReviewStack#env/label reaches TaskCommands#env unfiltered:
  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  env = Shipit::TaskCommands.new(task).env
  assert_equal 'true', env['LD_PRELOAD']
end
```
