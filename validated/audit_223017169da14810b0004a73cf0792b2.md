### Title
Cross-repository forged commit status accepted globally by SHA, enabling unauthorized `MergeRequest` merge - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` applies incoming GitHub `status` webhook events to every `Commit` row matching the SHA in the payload, with no check that the event's `repository` matches the `stack`/repository that owns that commit. Since `Commit#deployable?` and `MergeRequest#all_status_checks_passed?` both read from `Commit#statuses` populated this way, an attacker who owns an unrelated repository (e.g. a public fork sharing a git object with the victim commit) can push a genuinely-signed webhook from their own repo and have it recorded as a passing status on the victim's `Commit`, driving `ProcessMergeRequestsJob` to merge the victim's pull request.

### Finding Description
The binding that should hold is: `status_payload.repository.full_name == commit.stack.repository_name` (the repository asserting CI success must be the same repository that owns the commit/merge request). This binding is never checked.

- `WebhooksController#verify_signature` derives the GitHub App/organization used for HMAC verification purely from the payload's own `repository.owner.login`/`organization.login` field [1](#0-0) , [2](#0-1) . It only proves the request truly came from GitHub for *that* organization/repo — it says nothing about which `Stack`/commit the payload is allowed to affect.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2)  — this looks up commits **globally by SHA only**, with no `stack_id`/repository scoping, and no comparison of `params['repository']` to the commit's own stack.
- The created `Status` is appended to `commit.statuses`, which feeds `Commit#status`, `Commit#deployable?` [4](#0-3) , and `MergeRequest#all_status_checks_passed?`/`StatusChecker` [5](#0-4) .
- `ProcessMergeRequestsJob` calls `merge_request.all_status_checks_passed?` and, if true, calls `merge_request.merge!`, which invokes `stack.github_api.merge_pull_request` [6](#0-5) , [7](#0-6) .

Exploit flow: an attacker opens a pull request against the victim's repository from a fork they control (an unprivileged action). The PR head commit object is, by construction of git forks, byte-identical (same SHA) in both the victim repo and the attacker's own fork. The attacker then issues (or has GitHub issue) a legitimately-signed `status` webhook for their own repository, referencing that shared SHA with `state: success`. `WebhooksController#verify_signature` validates it as a real, correctly-signed event for the attacker's own repo/org, so the request passes. `StatusHandler#process` then attaches that status to **every** `Commit` row with the same SHA, including the row belonging to the victim's `Stack`/`MergeRequest`, satisfying `all_status_checks_passed?` and permitting `ProcessMergeRequestsJob` to merge the victim's PR.

None of the guards in scope prevent this: `verify_signature` validates authenticity of the sender's org, not the payload's applicability to the target stack; `drop_unhandled_event` only filters unhandled event types; the `ExplicitParameters` schema in `StatusHandler` (`params do ... end`) validates payload shape, not repository ownership [8](#0-7) ; and `Commit` has no uniqueness constraint or lookup scoping by `(stack_id, sha)` in this handler.

### Impact Explanation
This allows a payload signed for one repository to mutate commit/merge-request state belonging to another repository's stack — an unauthorized merge of a pull request via forged CI signal, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any stack/repository whose PR head commit shares a SHA with an attacker-controlled repository (trivially achievable via forking), and requires only opening a pull request and issuing one status webhook — actions fully within an unprivileged GitHub user's capability.

### Likelihood Explanation
Preconditions: the target `Stack` must have merge-queue functionality enabled (`stack.allows_merges?`) and required status checks configured; the attacker needs any repository where Shipit/GitHub webhooks are correctly configured and signed (their own fork or any repo they own can serve, since signature verification is scoped per-organization based on the payload's own `repository.owner`). Attacker cost is minimal: fork the victim repo, open a PR, then fire one legitimate webhook from their own repo referencing the shared commit SHA. This is fully repeatable across arbitrary Shipit-managed repositories that share commit history with an attacker-accessible repo (fork relationship is the common case).

### Recommendation
In `StatusHandler#process` (and analogously in `CheckSuiteHandler`/other SHA-keyed handlers), scope the `Commit` lookup to commits whose `stack.repository` matches `params['repository']['full_name']` (or `stack.github_repo_name`) before applying the status, rather than matching by SHA alone across all stacks.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, added by an engineer per repo conventions — not created here):
1. Create `stack_victim` for repo `victim/repo` and `stack_attacker` for repo `attacker/repo`.
2. Create `commit = Commit.create!(stack: stack_victim, sha: "deadbeef...")` and a `MergeRequest` on `stack_victim` with `head: commit`, `merge_status: 'pending'`.
3. Assert baseline: `refute merge_request.all_status_checks_passed?` (equality check: no status yet ⇒ not passed).
4. Also create `Commit.create!(stack: stack_attacker, sha: "deadbeef...")` to represent the shared-SHA commit in the attacker's own repo.
5. POST a `status` webhook payload with `repository: { full_name: "attacker/repo", owner: { login: "attacker" } }`, `sha: "deadbeef..."`, `state: "success"`, signed with the (test) HMAC secret configured for `attacker`'s org.
6. Assert the victim's `commit.reload.statuses` now contains a `success` status even though the payload's `repository` was `attacker/repo`, not `victim/repo` — i.e., assert `commit.stack.github_repo_name != status_payload_repository_full_name` yet `commit.status.success?` is true.
7. Run `ProcessMergeRequestsJob.perform_now(stack_victim)` and assert `merge_request.reload.merge_status == "merged"` (or that `merge!`/`github_api.merge_pull_request` was invoked), demonstrating unauthorized merge driven by a status signed for an unrelated repository.
