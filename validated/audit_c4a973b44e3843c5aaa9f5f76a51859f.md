### Title
Stale delegate grant re-arms when the position NFT returns to the granting owner, letting a previously removed-in-practice delegate drain the reacquired account - (File: contracts/controller/src/storage/account.rs)

### Summary
The controller invalidates delegate grants lazily by stamping each `DelegateGrant` with `granted_by` and filtering on `granted_by == owner` at read time. On `position-nft` `transfer`/`transfer_from` the grant is not deleted (the NFT contract cannot notify the controller). If the NFT ever returns to the original granter — resale, marketplace round-trip, mistaken transfer, or an attacker-engineered return — the stale grant becomes live again and the old delegate regains full account authority (`borrow`/`withdraw`-style actions up to LTV) without the current owner's consent.

### Finding Description
In `get_delegates`, authority is decided purely by `grant.granted_by == *owner`; nothing records an epoch, transfer count, or explicit revocation:

```rust
// contracts/controller/src/storage/account.rs:176-181
get_user::<DelegateGrant>(env, &ControllerKey::Delegates(account_id))
    .filter(|grant| grant.granted_by == *owner)
    .map(|grant| grant.delegates)
```

`set_delegates`/`add_delegate`/`remove_delegate` only write or delete the single `Delegates(account_id)` slot; there is no hook on NFT transfer, so the entry survives ownership changes (`remove_delegate` deletes a stale grant only if the *new* owner happens to call it — `account.rs:226-247`). The NFT README documents the resurrection directly: "The stale grant stays in storage and re-arms if the token returns to `granted_by`" (`contracts/position-nft/README.md:174-179`). This is the refcount-leak analog: a reference (the delegate grant) acquired under one owner is never released on the ownership transition, so it silently reactivates later.

### Impact Explanation
An unprivileged attacker who is (or was) granted as a delegate on account `A` stamped by owner `O` can wait for — or arrange — `A`'s NFT to return to `O` (e.g., `O` sells the position NFT on a marketplace and later buys an identically-looked position back, or a counterparty transfers it back). The moment `owner_of(A) == O` again, the attacker's grant is live, and the attacker can immediately call controller entrypoints as delegate — `borrow`/`borrow_as_to` against the account's collateral and similar — extracting value while leaving the debt on `O`'s reacquired account. This is theft of user funds reachable entirely through unprivileged calls (`position-nft::transfer`, `controller::add_delegate`, `controller::borrow` family).

### Likelihood Explanation
Medium. Requires (a) a delegate grant existing, (b) the NFT leaving and returning to the granter, and (c) no intervening `add_delegate`/`remove_delegate` by an interim owner. Position NFTs are designed to be freely traded, so ownership cycles are realistic; nothing warns a returning owner that an old grant re-armed. No privileged role, timing race, or oracle dependence is needed.

### Recommendation
Make invalidation monotonic rather than owner-equality based. Options: store the NFT `token_id`-scoped grant alongside a controller-maintained per-account `epoch` counter that is incremented whenever the controller observes an owner change (compare-and-bump on every `try_account_owner` resolution), or stamp grants with `(granted_by, owner_nonce)` where `owner_nonce` increments on each ownership transition, so a returning owner gets a fresh nonce and old grants stay dead regardless of which address holds the token. At minimum, purge `Delegates(account_id)` eagerly wherever the controller detects `granted_by != owner` (as `remove_delegate` already does at `account.rs:236-238`) on all account-mutating paths, not just delegate management.

### Proof of Concept
1. Alice owns account `A` with collateral; calls `controller.add_delegate(Alice, A, Mallory)` → `DelegateGrant{granted_by: Alice, delegates: [Mallory]}` stored.
2. Alice calls `position-nft.transfer(Alice → Bob, A)`. Grant remains; `get_delegates` filters it out for Bob.
3. Bob never calls `remove_delegate`/`add_delegate` (nothing forces him to).
4. Bob transfers the NFT back to Alice (`transfer(Bob → Alice, A)`), e.g., after Alice repurchases the position.
5. `get_delegates(env, A, Alice)` now returns `[Mallory]` — the grant re-activated with no signature from Alice.
6. Mallory calls `controller.borrow`-family entrypoints as delegate on `A`, drawing debt against Alice's collateral and taking the proceeds — funds stolen from Alice's reacquired account.
