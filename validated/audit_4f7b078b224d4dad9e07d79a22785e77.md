## Analog Found

### Title
Permission-gated `AmmConfig` pools can be created without the required `Permission` check by calling the unpermissioned `initialize` instruction - (File: `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
The program exposes two pool-creation entry points that both operate on the same `AmmConfig` resource: the open `initialize` instruction and the gated `initialize_with_permission` instruction. `AmmConfig` has no field marking a config as "requires permission," and `initialize`'s account validation performs no check tying the pool creation to a `Permission` PDA. Consequently, any unprivileged signer can call `initialize` against any `AmmConfig` — including one an admin intends to restrict to permissioned creators — completely bypassing the permission control, analogous to the Plone advisory's incorrect-permission-assignment class where a resource meant to be access-restricted is reachable through a path that omits the permission check.

### Finding Description
`initialize_with_permission` requires an `Account<'info, Permission>` PDA derived from `[PERMISSION_SEED, payer.key()]`, which only exists if an admin previously called `create_permission_pda` for that payer [1](#0-0) , gated by `create_permission_pda_owner`/`admin` only [2](#0-1) .

However, the `Initialize` accounts struct used by the plain `initialize` instruction has no `permission` field or any check at all referencing `Permission`; it only validates `amm_config.disable_create_pool` [3](#0-2) [4](#0-3) . The `AmmConfig` account itself carries no marker distinguishing "must go through the permissioned path" from "open to anyone" [5](#0-4) . Since both instructions accept an arbitrary `amm_config: Box<Account<'info, AmmConfig>>` with the same seeds/derivation, an attacker can simply invoke `initialize` (any signer as `creator`) against the config an admin intended to be reachable only via `initialize_with_permission`, and the on-chain program provides no mechanism to prevent it. This is the incorrect-permission-assignment root cause: the critical resource (permission-gated pool creation for a given `AmmConfig`) is not actually bound to the permission check anywhere in the account/state model — the restriction exists only informally, by convention that a particular instruction "should" be used, not by an enforceable constraint on the shared resource.

### Impact Explanation
Any config an operator sets up expecting permissioned pool creation (e.g., to restrict which addresses can spin up pools under a particular fee schedule/config index, control spam listings, or gate access as an anti-abuse measure) can be freely created by unprivileged actors through `initialize`, with the attacker fully controlling `creator`/`pool_creator`, `open_time`, and initial liquidity, and subsequently collecting creator fees via `collect_creator_fee`/`collect_creator_fee_permissionless`. This is an unauthorized privileged effect: bypass of an access-control gate the protocol explicitly implemented as a separate, permission-checked instruction.

### Likelihood Explanation
Trivial to trigger: it only requires a single transaction calling the existing, always-available `initialize` instruction with attacker-chosen accounts (any `token_0_mint`/`token_1_mint` pair and an in-scope `amm_config`), no elevated privileges or special conditions needed.

### Recommendation
Bind the permission requirement to the `AmmConfig` resource itself (e.g., add a `require_permission: bool` field to `AmmConfig`), and enforce in `initialize`'s account validation/handler that `amm_config.require_permission == false`, returning an error otherwise — mirroring the check `initialize_with_permission` already performs via the `Permission` PDA, so the two entry points cannot diverge on the same config.

### Proof of Concept
1. Admin creates an `AmmConfig` intended to be permission-gated (relying on `initialize_with_permission` + `create_permission_pda` for access control), but `disable_create_pool` remains `false` (needed so legitimate permissioned creators can still call `initialize_with_permission`) [6](#0-5) .
2. An attacker who was never granted a `Permission` PDA calls `initialize` directly with that `amm_config`, `token_0_mint`, `token_1_mint`, and their own token accounts as `creator_token_0`/`creator_token_1` [7](#0-6) .
3. The instruction succeeds because no `Permission` account is referenced anywhere in `Initialize`'s account constraints or handler body, creating a pool under the "gated" config as if the attacker had gone through the permissioned path.

pub fn initialize(
    ctx: Context<Initialize>,
    init_amount_0: u64,
    init_amount_1: u64,
    mut open_time: u64,

    let mint0_associated_is_initialized = support_mint_associated_is_initialized(
        &ctx.remaining_accounts,
        &ctx.accounts.token_0_mint,
    )?;
    let mint1_associated_is_initialized = support_mint_associated_is_initialized(
        &ctx.remaining_accounts,
        &ctx.accounts.token_1_mint,
    )?;
    if !(is_supported_mint(&ctx.accounts.token_0_mint, mint0_associated_is_initialized).unwrap()
        && is_supported_mint(&ctx.accounts.token_1_mint, mint1_associated_is_initialized).unwrap())
    {
        return err!(ErrorCode::NotSupportMint);
    }

    if ctx.accounts.amm_config.disable_create_pool {
        return err!(ErrorCode::NotApproved);
    }
