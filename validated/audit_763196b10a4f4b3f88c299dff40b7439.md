## Title
AA-to-AA payments composed by `handleTrigger`/`sendUnit` never validate destination AA `bounce_fees`, permanently trapping funds at the recipient AA - (File: `aa_composer.js`)

### Summary
`FootiumClub.safeMint()` transfers an NFT to an arbitrary address without checking whether the recipient can actually handle it (no `onERC721Received` check), so the token can become permanently unrecoverable. The same class of bug exists in ocore's Autonomous Agent payment composition: when an AA sends bytes/assets to another AA's address, `aa_composer.js` never verifies that the amount sent is sufficient for the *receiving* AA to process the trigger (i.e., cover its declared `bounce_fees`). This check exists in the codebase (`aa_addresses.checkAAOutputs`) but is wired up only for wallet-composed, human-initiated transactions, not for AA-composed payments.

### Finding Description
`aa_addresses.js` implements `checkAAOutputs()`, which inspects the destination AA's `bounce_fees` and rejects a payment if the amount sent is below what the recipient AA declares as necessary to be able to respond/bounce: [1](#0-0) 

This function is only invoked from `wallet.js`'s `sendMultiPayment`, i.e., only for transactions composed by a human wallet user: [2](#0-1) 

However, when an AA itself composes and sends a payment to another address (including another AA) as part of `handleTrigger`/`sendUnit`, there is no equivalent check. The message/output validation performed inside `sendUnit` only validates address format, amount positivity, and asset format - it never consults `checkAAOutputs` or otherwise checks the recipient's `bounce_fees`: [3](#0-2) 

Meanwhile, on the receiving side, when a trigger unit arrives at an AA with less than the declared `bounce_fees.base` (or any asset in `bounce_fees`), the AA silently swallows it: `bounce()` is invoked, but because the received amount is below the fee needed to send back a bounce response, the AA takes no action at all (`finish(null)`) - no response unit, no refund, and the state stays untouched: [4](#0-3) [5](#0-4) 

This mirrors the `FootiumClub` root cause precisely: the sender (AA composing an output) has no "receiver capability check" analogous to `onERC721Received`, and the recipient logic (AA bounce mechanism) has no fallback path to return value that arrives below its own minimum threshold - it just eats it silently.

### Impact Explanation
Any AA author can write an AA whose payment logic computes an output amount to another AA address (e.g., derived dynamically from `trigger.output`, subtracting fees, or via chained/forwarding AAs as shown in the test suite's "chain of AAs" and "AA with generated definition of new AA" patterns). If that computed amount happens to fall below the destination AA's `bounce_fees` (which is a property of the destination AA that the sending AA has no obligation, and in practice no built-in mechanism, to check before sending), the funds are transferred but the destination AA can never execute a trigger for them nor return them - the value is permanently stuck at that AA address with no code path to move it out, since it entered without being recognized as a valid trigger. This constitutes an AA fund freeze reachable by any AA author or via any chain of AA-to-AA forwarding logic that a user's trigger can activate.

### Likelihood Explanation
This can be triggered unintentionally by common AA design patterns - forwarding/proxy AAs and factory AAs that calculate a derived amount to send onward (seen throughout the test suite, e.g. `test/aa_composer.test.js` "chain of AAs", "AA with generated definition of new AA and immediately sending to this new AA", and `test/samples/fundraising_proxy.oscript`). Any edge case (fee subtraction underflow toward the threshold, rounding, a triggering user sending a marginal amount) can push the forwarded amount under the recipient's `bounce_fees`, and the framework provides no guardrail comparable to the wallet-side `checkAAOutputs`.

### Recommendation
Apply the same `bounce_fees` sufficiency check that `aa_addresses.checkAAOutputs` performs for wallet-composed transactions inside `aa_composer.js`'s message/output validation (around `sendUnit`'s per-output validation, e.g. near [6](#0-5) ), so that an AA response cannot be composed with underfunded payments to another AA address; instead it should bounce with a clear error at composition time rather than silently trapping funds at the destination.

### Proof of Concept
1. Deploy `AA_B` with `bounce_fees: { base: 10000 }` and any trigger-response logic.
2. Deploy `AA_A` (a forwarder) whose payment message computes an output to `AA_B`'s address using a formula such as `trigger.output[[asset=base]] - X`, where for some valid trigger value the result is a positive number below `10000` (e.g., trigger sends `10500` bytes and `X=1000`, forwarding `9500`, as demonstrated by the "less than bounce fees" behavior already covered in the test suite: [7](#0-6) , which shows exactly this bounce-fee-insufficiency response for a *primary* trigger).
3. Trigger `AA_A` with a base amount such that the forwarded amount to `AA_B` is positive but under `10000`.
4. `sendUnit` in `aa_composer.js` composes and sends the payment without any check against `AA_B`'s bounce_fees (no call to `checkAAOutputs`).
5. When the resulting unit becomes a secondary trigger for `AA_B`, the check at [8](#0-7)  combined with the silent no-op bounce path at [9](#0-8)  causes the funds to be accepted into `AA_B`'s balance with no response, no state change, and no way for `AA_B` (or anyone) to recover or route them out through normal trigger logic.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
