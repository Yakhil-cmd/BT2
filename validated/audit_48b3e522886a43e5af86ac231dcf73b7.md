### Title
Rotating an address's definition does not invalidate previously-signed `is_valid_signed_package` authorizations - (File: `formula/evaluation.js`, `signed_message.js`)

### Summary
`is_valid_signed_package` (used by AA oscript, e.g. payment-channel and order-book-exchange templates) validates a caller-supplied `signedPackage` by resolving the signer's address definition *as of the `last_ball_unit` chosen inside the package*, not the definition current at trigger time. An address owner who rotates their signing key via an `address_definition_change` message (the oscript analog of "changing a password") does not revoke the usability of packages signed under the old definition: an attacker who obtained the old private key can still forge a validly-verifying `signedPackage` by pointing `last_ball_unit` at any stable unit that predates the rotation.

### Finding Description
`is_valid_signed_package` in [1](#0-0)  only checks that the supplied `last_ball_unit` is a stable, on-main-chain unit whose `main_chain_index <= mci` (the evaluation mci of the trigger). It imposes no requirement that this mci be recent, nor that it be the *current* definition of the address.

It then delegates to `signed_message.validateSignedMessage`, whose `validateOrReadDefinition` resolves the signer's definition with `storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, ...)` [2](#0-1) , i.e. strictly against the historical definition that was in force at that arbitrary past `last_ball_mci` — never against the definition active at trigger time.

`storage.readDefinitionByAddress`/`readDefinitionChashByAddress` simply picks the latest definition change stable at-or-before the given mci [3](#0-2) ; it has no concept of "has this definition since been superseded/revoked," so any historical definition remains permanently retrievable and usable for signature verification via this API, by design for other use cases (verifying old signed data), but this design assumption breaks when the same primitive is reused as a live authorization check for currently-controlled funds.

Consequently, if a user rotates the definition of their address (e.g. after suspecting key compromise, or as part of normal multisig/cosigner replacement) using `address_definition_change`, anyone still holding the old private key can keep producing new `signedPackage` objects — with fresh `signed_message` payloads — as long as they anchor `last_ball_unit` to any old, still-stable unit from before the rotation. `is_valid_signed_package` will accept it, because the only currency-in-time check is "not in the future relative to the current AA trigger."

### Impact Explanation
`is_valid_signed_package` is intended to let AAs (e.g. payment channels, order-book exchanges — see `test/samples/payment_channels.oscript`, `test/samples/order_book_exchange.oscript`, both matching this primitive) authorize fund releases/settlements based on off-chain signed messages from a counterparty address. If that counterparty's key is compromised and the owner reacts by rotating the address definition (the intended mitigation), the compromised key nonetheless continues to be accepted indefinitely by any AA using `is_valid_signed_package`, because verification is always performed against a self-chosen historical mci rather than the address's live definition. This allows continued unauthorized generation of "valid" authorization proofs after a key rotation, leading to AA fund loss for any contract that relies on this primitive to gate payments (e.g. an attacker replaying/forging channel-closing signatures or trade confirmations with the old, revoked key).

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender: the attacker only needs to submit a trigger whose `data` embeds a self-crafted `signedPackage` (`signed_message`, `authors`, `last_ball_unit`) referencing a `last_ball_unit` that is stable and at or before the current mci — no special permissions, hub, or network position required. The only prerequisite is prior possession of a private key for the address before it was rotated, a realistic threat model (this is exactly the compromise-then-rotate scenario the Dokploy bug models). AA templates using `is_valid_signed_package` for security-relevant checks (payment channels, order books) are part of the standard oscript sample set, making this a directly reachable class of contracts.

### Recommendation
When resolving the signer's definition for `is_valid_signed_package`/`validateSignedMessage`, additionally verify that the definition resolved at the package's `last_ball_mci` is still the address's *current* definition (i.e., there has been no subsequent stable `address_definition_change` for that address as of the AA's evaluation mci), or otherwise bound how old an accepted `last_ball_unit` may be. This closes the gap where a superseded definition remains eternally valid for authorization purposes.

### Proof of Concept
1. Address `A` is defined with key `K1`. `K1` leaks to an attacker.
2. The legitimate owner posts `address_definition_change` for `A`, moving to key `K2`; the change becomes stable.
3. An AA (e.g. a payment channel contract using `is_valid_signed_package(signed_message, 'A')`) is still live and expects only `K2`-signed packages going forward.
4. The attacker, still holding `K1`, crafts a new `signed_message` payload (e.g. a channel-closing balance update favoring themselves) and signs it with `K1`, setting `last_ball_unit` to any stable unit that existed before step 2's definition change became stable.
5. The attacker submits this `signedPackage` inside an AA trigger. `is_valid_signed_package` computes the historical `last_ball_mci` from the chosen `last_ball_unit`, calls `validateSignedMessage`, which resolves `A`'s definition as `K1` (valid at that old mci) and successfully verifies the `K1` signature [4](#0-3) [5](#0-4) .
6. The AA treats the forged, post-revocation package as authorized, releasing/allocating funds accordingly — despite the key having been formally revoked in step 2.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
