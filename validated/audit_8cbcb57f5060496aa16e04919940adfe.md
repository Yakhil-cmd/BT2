### Title
Session fixation on GitHub OAuth login — session ID is not rotated after authentication ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a newly authenticated GitHub identity to whatever session already exists in the browser, without first invalidating/rotating that session. This breaks the intended binding `session identifier == the identity that established it`, allowing a session fixed before login to remain valid — and now privileged — after login, exactly analogous to the reported bug class where a security-relevant transition (vesting → transferable, here anonymous → authenticated) is not re-validated at the moment the state actually changes.

### Finding Description
`GithubAuthenticationController#callback` is the OmniAuth callback endpoint that promotes the current session from anonymous to authenticated: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

Note that it writes `session[:user_id]` directly into the existing session hash. It never calls `reset_session`, unlike the adjacent `logout` action which correctly calls it: [2](#0-1) 

```ruby
def logout
  reset_session
  redirect_to(root_path)
end
```

Because Rails session cookies are identified by a session ID that is normally rotated on privilege changes to prevent session fixation, and this controller skips that rotation, any session ID that existed before OAuth completed continues to be valid — and is now upgraded in place to point at `User#id` — after the callback. The identity check further down the request pipeline (`Shipit::Authentication#find_current_user`) simply trusts `session[:user_id]`: [3](#0-2) 

```ruby
def current_user
  @current_user ||= find_current_user || AnonymousUser.new
end

def find_current_user
  session[:user_id].present? && User.find_by(id: session[:user_id])
end
```

The binding that should hold is: *the session cookie a client presents after login == a session that was created after (not before) that client proved their GitHub identity*. Instead, the pre-existing session cookie's identifier is unconditionally reused and merely mutated with `user_id`. This is the "GitHub identity vs. the `User` bound to the session" binding called out in scope: the session's authorization state changes, but the session's identity (cookie/ID) that an attacker could have pre-established does not.

### Impact Explanation
This is a classic session fixation vulnerability (CWE-384). If an attacker can cause a victim's browser to carry a session cookie value known to the attacker prior to the victim completing GitHub OAuth (e.g., by setting a cookie for the Shipit host from a sibling application on the same parent domain, a non-HttpOnly cookie exposed by another vulnerable co-hosted app, or a network path capable of setting `Set-Cookie` for the host before the OAuth handshake), the attacker's copy of that same session ID becomes a fully authenticated Shipit session once the victim logs in — with no distinguishing signal between the "pre-login" and "post-login" holder of that ID. Explicitly listed in-scope impact: "session fixation / forced OAuth completion" (High). Once hijacked, the session grants the victim's full Shipit access (deploys, rollbacks, merges) subject only to `Shipit.github_teams` checks that the victim (not the attacker) satisfies — i.e., unauthorized deploy/rollback/merge capability transferred to the attacker.

### Likelihood Explanation
The root cause is a straightforward missing `reset_session` call and is unconditionally reachable on every login — no privileged credential, ApiClient token, webhook secret, or GitHub App key is required to trigger it. The only prerequisite is the attacker's ability to plant a cookie value in the victim's browser for the Shipit host prior to login, which is a well-known and commonly exploitable precondition for session-fixation-class findings (and is the exact impact class the scoping rules call out as acceptable, distinct from requiring an existing authenticated Shipit session).

### Recommendation
Call `reset_session` (or otherwise regenerate/rotate the session ID) in `GithubAuthenticationController#callback` before assigning `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `logout`:

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  reset_session
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

### Proof of Concept
1. Attacker obtains a valid, unauthenticated session cookie for the Shipit host (e.g. `_shipit_session=ABC`) and gets it set in the victim's browser (classic fixation delivery: cookie set via a sibling subdomain, a non-secure/non-host-only cookie attribute, or a network injection opportunity — the attack vector itself, not the fixation bug, is what needs "planting").
2. Victim, still carrying cookie `ABC`, visits Shipit and completes the GitHub OAuth login flow at `/github/auth/github/callback`.
3. `GithubAuthenticationController#callback` writes `session[:user_id] = <victim user id>` into the *same* session record identified by cookie `ABC`, without rotating the ID.
4. Attacker replays cookie `ABC` against the Shipit host and is now recognized as the victim by `Shipit::Authentication#find_current_user`, gaining full access to any stacks the victim can deploy/rollback/merge.
