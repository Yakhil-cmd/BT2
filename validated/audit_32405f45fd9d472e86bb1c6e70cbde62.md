### Title
Cross-tenant webhook forgery via `repository.owner.login` / `repository.full_name` mismatch when any configured org has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on the attacker-controlled `repository.owner.login` (or `organization.login`) field, while every downstream handler, including `PullRequestClosedHandler`, resolves the repository/stack to mutate from the separate, also attacker-controlled `repository.full_name` field. Nothing cross-checks that these two fields refer to the same repository/org. If any GitHub org configured on the Shipit instance has a blank `webhook_secret` (an explicitly documented, supported configuration in `docs/setup.md`), `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an attacker forge a fully unsigned `pull_request` "closed" webhook that names a victim's real repository via `repository.full_name`, causing `ClosedHandler#process` to archive the victim's tracked review stack.

### Finding Description
Broken binding: `organization used to select the webhook_secret for signature verification (params.dig('repository','owner','login'))` **should equal** `organization owning the repository whose Stack/PullRequest state is mutated (params.repository.full_name's owner segment, used by ClosedHandler#repository)`. The code never enforces this equality.

Path:
- `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) and calls `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) .
- In a multi-org deployment, `Shipit.github(organization:)` looks up the app config keyed by that org string and builds a `GitHubApp` scoped to it [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank: `return true unless webhook_secret` [4](#0-3) . `docs/setup.md` documents multi-org configs with a `webhook_secret:` key per org that can be left unset, and `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml` show exactly this pattern (`webhook_secret: # nil`) [5](#0-4) [6](#0-5) .
- Once verification passes (or is bypassed), `WebhooksController#create` dispatches the **entire raw JSON body** — not scoped to `repository_owner` — to registered handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [7](#0-6) .
- `PullRequestClosedHandler#repository` resolves the target repository strictly from `params.repository.full_name`, independent of whatever value was used for signature verification [8](#0-7) .
- `#process` then calls `review_stack.archive!`, which finds the real `ReviewStack`/`Stack` for that repo+PR number and deprovisions/archives it: `stack.remove_from_provisioning_queue; stack.deprovision; stack.archive!(user, ...)` [9](#0-8) [10](#0-9) .

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, any/no `X-Hub-Signature`, and a JSON body where `repository.owner.login` (or `organization.login`) is set to a Shipit-configured org that has a blank `webhook_secret`, while `repository.full_name`, `number`, and `pull_request` fields name the victim's real tracked repository and PR. No valid signature, session, API token, or team membership is required, and the attacker need not control the secret-less org at all — they only need to know its name (which is not secret; Shipit org names are visible in the product UI and via GitHub itself).

Existing guards fail because: `verify_signature` only checks the signature is valid *for the org resolved from the (forgeable) owner field*; it does not check that this org matches the repository actually referenced later in the payload, nor does any handler or `ExplicitParameters` schema enforce that `repository.full_name`'s owner segment matches `repository.owner.login`. `drop_unhandled_event` only checks the event type is registered (`pull_request` is), and `respond_to_pull_request_closed?` only checks `action == "closed"`, both trivially satisfied by the forged payload.

### Impact Explanation
An unauthenticated, unprivileged attacker can archive/deprovision another organization's review-stack (a live deploy environment tied to a real PR) using a payload attributed to an unrelated, secret-less org, without ever presenting a valid webhook signature. This is a cross-tenant state mutation ("a payload for one repository mutating another's stack"), matching the Critical impact category. It is fully repeatable against any tracked repository/PR combination as long as one org in the deployment lacks a `webhook_secret`; each request can archive a distinct stack, and combined with other `pull_request` handlers (`LabeledHandler`, `LabelCapturingHandler`, etc.) the same primitive extends to forging labels/state on arbitrary victim PR records.

### Likelihood Explanation
Requires a multi-org Shipit deployment (`Shipit.github(organization:)` per-org config) with at least one configured org whose `webhook_secret` is blank — a configuration explicitly shown as valid/supported in `docs/setup.md` and in the shipped example secrets files. Given that precondition, the attack costs a single unauthenticated HTTP POST with no secrets, tokens, or GitHub privileges of any kind, and is trivially repeatable. Likelihood is contingent on that specific deployment configuration; it is not exploitable in a single-org deployment, since there `Shipit.github` ignores the `organization:` argument and always uses the one configured `secrets.github` app, whose signature check (if a secret is configured) applies uniformly regardless of the forged owner field [11](#0-10) .

### Recommendation
Cross-validate `params.dig('repository','owner','login')` against the owner segment of `params.dig('repository','full_name')` (and `organization.login` when used as fallback) in `WebhooksController#verify_signature`, rejecting mismatches before dispatching to handlers. Additionally, require `webhook_secret` to be present for every configured org (fail closed / raise at boot if any org config omits it) rather than silently allowing unsigned webhooks when it's blank.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, or `test/models/shipit/webhooks/handlers/pull_request/closed_handler_test.rb` style):
1. Configure two orgs via `Shipit.stubs(:secrets)`: `"victim-org"` with a real `webhook_secret`, and `"attacker-org"` with `webhook_secret: nil`.
2. Create a `Shipit::Repository` for `victim-org/victim-repo`, a `Stack`/`ReviewStack` tied to PR number `N`, and assert `stack.archived? == false` beforehand.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and body:
   ```json
   {
     "action": "closed",
     "number": N,
     "pull_request": { "...": "...", "merged": true },
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
     "sender": { "login": "attacker" }
   }
   ```
4. Assert response is `:ok` (not `422`), and assert `stack.reload.archived? == true` — proving the binding `repository_owner used for signature verification == org owning the mutated Stack/PullRequest` does not hold, and a victim's Stack was mutated by a webhook that never carried a valid signature for `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
