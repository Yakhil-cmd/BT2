### Title
Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The specific binding the question hypothesizes (verifying org vs. resolved target org derived from `Handler#repository_name`) actually holds for `CheckSuiteHandler`, `PushHandler`, and `MembershipHandler`, because they all resolve their target through `payload.dig('repository', 'full_name')` or `organization.login` — the same fields GitHub HMAC-signs and that `WebhooksController#repository_owner` reads to select the verifying `GitHubApp`. However, `StatusHandler` never uses `Handler#stacks`/`repository_name` at all: it resolves its target purely via `Commit.where(sha: params.sha)` with zero repository or organization scoping, so a validly-signed webhook from any repository can mutate a `Commit` belonging to a completely unrelated stack/org sharing the same SHA.

### Finding Description
Binding claimed broken: `verifying_org == resolved_target_org`.

Trace:
- `WebhooksController#verify_signature` picks `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) [2](#0-1) . This resolves and validates `verifying_org` against the HMAC over `request.raw_post` using that org's `webhook_secret` [3](#0-2) .
- `Handler#initialize` parses the same already-signed payload and, for handlers that use `Handler#stacks`, resolves the target via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [4](#0-3) . Because `repository.owner.login` and `repository.full_name` are both part of the same GitHub-signed JSON body, an attacker cannot desynchronize them without knowing the org's `webhook_secret`. `CheckSuiteHandler` [5](#0-4) , `PushHandler` [6](#0-5) , and `MembershipHandler` (which resolves/creates the `Team` scoped to `params.organization.login`, the same field used for signature verification) [7](#0-6)  are all consistent — the equality holds for these.

The actual break is in `StatusHandler`: its schema requires only `sha`, `state`, and optional metadata — no `repository` object at all is required [8](#0-7) . Its `process` method performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [9](#0-8)  — a global, cross-tenant lookup by SHA with no repository/organization scoping whatsoever. `Handler#stacks`/`repository_name` are never invoked by this handler, so there is no "resolved_target_org" computed to compare against `verifying_org` in the first place — the binding is absent, not merely unverified.

Because Git commit SHAs are content-addressed, an attacker who forks or otherwise obtains a repository sharing history with a Shipit-tracked repository (e.g., forking a public/internal repo tracked by Shipit) has the identical SHA for shared commits. If the attacker owns a repository on which the Shipit GitHub App is installed (satisfying "push to a fork ... emit webhooks from a repository they own" in the threat model) and pushes a real GitHub status event for their own fork/repo (via GitHub's Status API on a commit that also exists in the victim's fork ancestry), GitHub delivers a genuinely-signed `status` webhook for the attacker's own org/repo. `WebhooksController#verify_signature` validates it correctly against the attacker's own org's `webhook_secret` — `verifying_org` legitimately equals the attacker's org. But `StatusHandler` then updates `Commit` rows matching that SHA regardless of which stack/repository/org they belong to, via `Commit#create_status_from_github!` [10](#0-9) .

### Impact Explanation
A forged/attacker-controlled commit `state` (e.g. `success`) written to a victim's `Commit` flips `Commit#deployable?` (`success? && !blocked?`) [11](#0-10) , which feeds directly into deploy readiness (`Stack#next_expected_commit_to_deploy`/`deployable?`) and merge-queue decisions (`MergeRequest#reject_unless_mergeable!`, `any_status_checks_failed?`, `any_status_checks_missing?` via `StatusChecker`) [12](#0-11) . This can enable an unauthorized deploy or an unauthorized PR merge on a stack/organization the attacker does not own — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius spans every stack in every tenant that happens to share a commit SHA with a repository the attacker controls (forks, mirrors, or common upstream history).

### Likelihood Explanation
Preconditions: (1) attacker must own/control a repository on which the target Shipit's GitHub App is installed (single-secret orgs require attacker membership in that org; multi-org installs widen this to any onboarded org, including ones an outside GitHub user could self-install the app on, if the app permits third-party installation); (2) the victim repository must share commit history (a shared SHA) with the attacker's repo — trivially achievable by forking a public repo tracked by Shipit and creating/pushing an identical commit, then using GitHub's Statuses API (which the repo owner can call for their own repo) to set an arbitrary status on that SHA. No Shipit secret, session, or API token is required — only the ability to legitimately trigger a real, correctly-signed GitHub `status` webhook for a repo the attacker owns. This is fully within the declared attacker capabilities ("push to a fork ... emit webhooks from a repository they own") and is repeatable against any SHA the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook actually pertains to: require `repository.full_name` in the params schema, resolve `stacks`/`Repository.from_github_repo_name` (as `Handler#stacks` already provides), and constrain the `Commit.where(sha: ...)` lookup to `commit.stack.repository == resolved_repository` (or intersect with `stacks`) before calling `create_status_from_github!`. This restores the same binding already present in `PushHandler`/`CheckSuiteHandler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_tenant_test.rb
require "test_helper"

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status webhook mutates a commit belonging to an unrelated repository/org sharing the same sha" do
          victim_repo = Repository.create!(owner: "victim-org", name: "victim-repo")
          victim_stack = Stack.create!(repository: victim_repo, environment: "production", branch: "main")
          shared_sha = "a" * 40
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared commit")

          # Payload legitimately signed for attacker's own org/repo, unrelated to victim_repo
          payload = {
            "sha" => shared_sha,
            "state" => "success",
            "context" => "attacker/ci",
            "repository" => { "full_name" => "attacker-org/attacker-repo", "owner" => { "login" => "attacker-org" } }
          }

          assert_not_equal "attacker-org", victim_repo.owner # verifying_org != resolved_target_org

          Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

          assert_equal "success", victim_commit.reload.state
          # Proves: a payload verified for "attacker-org" mutated victim-org's commit/stack state.
        end
      end
    end
  end
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
