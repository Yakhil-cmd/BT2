### Title
Malicious swap route attaches arbitrary caller token transfers inside strategy authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` pass caller-controlled swap bytes to the configured router, while the controller validates only the router’s measured `token_in` and `token_out` balances. The route can invoke attacker-controlled third-party code that calls an unrelated token’s `transfer(caller, attacker, amount)` while execution remains under the caller’s root `swap_*` authorization. [1](#0-0) 

### Finding Description

`swap_tokens` snapshots only the controller’s balances for `token_in` and `token_out`, authorizes one controller-to-router input transfer, and invokes `router.execute_strategy(controller, amount_in, swap)` inside the flash guard. [1](#0-0)  It later checks that the controller’s input spend did not exceed `amount_in` and that its output balance increased, but those measurements cannot detect a nested transfer that moves tokens directly from the caller’s wallet to an attacker. [2](#0-1) 

The strategy entrypoint authenticates the account owner or delegate before withdrawing collateral and executing the route. [3](#0-2)  Because the arbitrary route executes below that caller-authorized strategy invocation, code reached by the route can request a token transfer from the caller and place that transfer as a child invocation of the caller’s `swap_collateral` authorization. [4](#0-3) 

This is analogous to validating a tar member’s name while not validating its symlink target: the controller validates the declared input/output assets and measured router settlement, but not the indirect code and authorization effects reachable through `swap`. [1](#0-0) 

### Impact Explanation

A victim who signs the poisoned authorization tree can lose an arbitrary amount of an unrelated wallet token while the lending strategy still completes and passes its final account checks. [5](#0-4)  The harness demonstrates a full wallet balance transferred to the attacker while the victim also receives the fair strategy output, making the transaction appear economically successful. [6](#0-5) 

The stolen funds need not be protocol collateral, `token_in`, or `token_out`, so the controller’s router overspend, positive-output, refund, and final-risk checks do not bound the theft. [2](#0-1) 

### Likelihood Explanation

An unprivileged attacker can deploy a malicious contract and encode it into a route supplied to a reachable strategy such as `swap_collateral`. [7](#0-6)  Exploitation requires a victim to sign the expanded authorization tree produced by simulation; an honest client can reveal and reject the extra transfer, while a client that hides, fails to decode, or mechanically signs simulation output can enable the theft. [8](#0-7) 

The repository explicitly tests that simulation records the malicious wallet transfer under the caller’s strategy authorization and that enforcing auth executes it only when the signed tree includes that child invocation. [9](#0-8) 

### Recommendation

Restrict route execution so user-controlled payloads cannot cause arbitrary downstream contracts to run beneath the strategy authorization. The configured router should execute only governance-approved venue contracts and tokens required by the declared route, rather than arbitrary pool, token, or callback addresses supplied in the payload. Clients should additionally decode every signed authorization tree and reject any child invocation other than the expected strategy’s required token transfer.

If preserving arbitrary routes is intentional, add an explicit contract-level separation between strategy authorization and user wallet authorization, or document and enforce a canonical signer-side authorization-tree policy for every route-bearing entrypoint.

### Proof of Concept

1. Victim owns a funded lending account and invokes `swap_collateral(caller, account_id, current, amount, new, swap)` with caller-controlled `swap` bytes. [10](#0-9) 
2. The controller withdraws the specified collateral and calls `swap_tokens_or_passthrough`, which reaches `router.execute_strategy(controller, amount_in, swap)`. [11](#0-10) 
3. The route names an attacker-deployed hop contract. During its `swap` callback, that contract calls `wallet_token.transfer(victim, attacker, wallet_balance)`. [12](#0-11) 
4. Simulation records the token transfer as a child invocation under the victim’s `swap_collateral` authorization. [4](#0-3) 
5. If the victim signs that poisoned tree, the strategy succeeds, the router output is credited, and the attacker receives the victim’s entire unrelated wallet-token balance. [8](#0-7)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
