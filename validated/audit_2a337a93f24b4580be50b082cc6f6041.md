## Confirmed root cause

`app/controllers/shipit/webhooks_controller.rb` selects the HMAC secret to verify a webhook against using `repository_owner`, which reads **`repository.owner.login`** from the request: [1](#0-0) [2](#0-1) 

That org's `GitHubApp` is fetched via `Shipit.github(organization: repository_owner)`, and `verify_webhook_signature` **returns `true` unconditionally when that org has no `webhook_secret` configured**: [3](#0-2) 

However, once the request passes `create`, the actual target repository/stack used by every handler is resolved from a **different field of the same payload**: `repository.full_name`, via `Handler#repository_name`/`#stacks`: [4](#0-3) [5](#0-4) 

Setup docs and the multi-org example config explicitly treat `webhook_secret` as **optional and support multiple independent GitHub App configs per organization**, so it is a supported, documented configuration for at least one org to have no secret set: [6](#0-5) [7](#0-6) 

### The break

`repository.owner.login` (used to pick which org's secret authenticates the request) and `repository.full_name` (used to pick which `Stack`/`Repository` the event actually mutates) are two independently attacker-controlled fields inside the same unauthenticated JSON body. Nothing ties them together before the signature/secret decision is made. An unprivileged attacker who knows (or can guess) that **any** org configured on the instance has a blank `webhook_secret` (e.g. a low-value/staging org) can craft:

```json
{
  "repository": { "owner": { "login": "no-secret-org" }, "full_name": "protected-org/prod-repo" },
  ...
}
```

`verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, finds no secret, and returns `true` — regardless of the `X-Hub-Signature` header. The request is then dispatched to `Shipit::Webhooks.for_event(event)` handlers, which resolve the target stack via `repository.full_name` → `"protected-org/prod-repo"`, a repository belonging to a completely different, actually-secured organization.

This breaks the binding "an organization that authenticated versus the repository that is written": the org whose credentials authenticated the webhook is not the org whose repository is mutated.

### Impact

Depending on which event type is forged, this allows an unauthenticated attacker to inject/forge, without any valid GitHub signature for the target org:
- `push` events → enqueue `GithubSyncJob` for the target stack (drives which commits are considered deployable/lockable).
- `status`/`check_suite` events → forge CI/commit statuses that gate deploy safety checks (`commit_status`/`deployable_status`).
- `membership` events → this is the most severe: `MembershipHandler` creates/looks up a `Team` by `params.team.id` and adds `member` to it based on the **`organization.login`** field (not `repository.owner.login`), so the same class of confusion (using an unrelated field to pick the authenticating org while acting on the org named in the body) lets an attacker escalate an attacker-controlled or arbitrary GitHub login into `Shipit.github_teams` membership, which is what `User#authorized?` checks to gate application access: [8](#0-7) [9](#0-8) 

This satisfies the "High" bar: escalation into `Shipit.github_teams` authorization / unauthenticated write against a stack the attacker does not control.

## Uncertainty

I could not fully load `lib/shipit.rb`'s `Shipit.github(organization:)` implementation in this session (only grep hit counts were returned, not the body), so I cannot 100% confirm how `GithubOrganizationUnknown` is raised versus how a *configured-but-secretless* org is looked up — but the `verify_webhook_signature` short-circuit at `lib/shipit/github_app.rb:77` (`return true unless webhook_secret`) is confirmed and is unconditional once any config for the claimed `repository.owner.login` resolves. If the host application configures every org with a mandatory secret, this specific path is not exploitable — but nothing in the engine enforces that, and the shipped example config explicitly ships `webhook_secret:` as commented/nil-able.

### Title
Webhook signature verification keys off `repository.owner.login` while all handlers act on `repository.full_name`/`organization.login`, letting a secretless org's config forge events for any other org's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository.owner.login`, a field fully controlled by the request body before any authentication occurs. If verification passes (including trivially, when that org has no configured `webhook_secret`), the `create` action and all downstream `Shipit::Webhooks::Handlers` instead resolve the actual `Stack`/`Team` to mutate from unrelated fields of the same body (`repository.full_name`, `organization.login`). These two fields are never cross-validated, so an attacker can authenticate as a low-value/secretless organization while writing events for a different, protected organization's repositories and teams.

### Finding Description
`verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from the payload and fetches `Shipit.github(organization: repository_owner)`; `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that specific org has no secret configured (`lib/shipit/github_app.rb:76-83`). The `create` action then dispatches the raw JSON body to registered handlers, all of which locate the target `Stack` via `Handler#repository_name` = `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`), or, for the `membership` event, via `payload['organization']['login']` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) — none of which is required to match `repository.owner.login`. The engine explicitly supports multi-org configuration with per-org, optional `webhook_secret` values (`docs/setup.md`, `config/secrets.development.example.yml`), making it plausible that at least one configured org lacks a secret.

### Impact Explanation
An unprivileged external party can forge webhook events for any repository/stack tracked by the instance as long as any one configured GitHub organization has no `webhook_secret`, by simply setting `repository.owner.login` to that org while pointing `repository.full_name`/`organization.login` at the real target. This can forge commit statuses/push notifications that influence deploy safety gating, and — via the `membership` handler — add an arbitrary GitHub login to a `Team` backing `Shipit.github_teams`, which is the sole gate checked by `User#authorized?` for granting access to the whole application (deploys, rollbacks, stack management).

### Likelihood Explanation
Requires only unauthenticated HTTP access to `/webhooks` and knowledge that some org on the instance has no secret (discoverable via trial-and-error, since a `422` vs `200`/`204` response leaks whether verification passed for a chosen `repository.owner.login`). No GitHub credentials, session, or API token are required.

### Recommendation
Derive the authenticating organization and the mutated repository/team from the *same*, single trusted field, and reject the request if `repository.owner.login` (or `organization.login`) does not match the owner implied by `repository.full_name`. Additionally, consider requiring `webhook_secret` to be present for every configured organization (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
1. Configure two orgs: `no-secret-org` (no `webhook_secret`) and `protected-org` (secured, unknown secret to attacker).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {"owner": {"login": "no-secret-org"}, "full_name": "protected-org/prod-repo"},
  "after": "<attacker-chosen sha>",
  "ref": "refs/heads/master"
}
```
No valid `X-Hub-Signature` is required (verification for `no-secret-org` trivially returns `true`); `GithubSyncJob` is enqueued for `protected-org/prod-repo`'s stack.
3. Repeat with `X-Github-Event: membership` and `organization.login` set to `protected-org`, `team.id` matching a real `Shipit.github_teams` team, and an attacker-controlled GitHub `member.login`, to gain `authorized?` access to the whole application.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
