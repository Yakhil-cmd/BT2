### Title
API request authentication binds the `ApiClient` token but the acting `User` identity is taken from an unauthenticated `X-Shipit-User` header - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
The Sherlock report's root cause is a computation that uses an unrelated, attacker-influenceable value (`timestamp`/`maxDeadline`) instead of the value that was actually verified (the extension duration), breaking the intended binding between "what was checked" and "what is acted on." The same bug class exists in the Shipit API authentication layer: the credential that is cryptographically verified (the `ApiClient` bearer token) is never bound to the `User` identity that ends up being recorded and used as the actor for deploys, rollbacks and tasks. That identity is instead read from a plain, unsigned `X-Shipit-User` request header.

### Finding Description
`Shipit::Api::BaseController#authenticate_api_client` verifies only the `ApiClient` bearer token via HMAC-signed id (`ApiClient.authenticate`): [1](#0-0) 

Separately, `current_user` — the value used to attribute the action to a specific human `User` — is derived from `identify_user`, which trusts the client-supplied `X-Shipit-User` header verbatim and looks up any `User` by login, with **no signature, no token association, and no check that the authenticated `ApiClient`'s creator matches the claimed login**: [2](#0-1) 

This is confirmed as intended/tested behavior — the test suite documents that any authenticated API caller can "claim" an arbitrary user via the header, and that the claim is used verbatim to set the deploy's author: [3](#0-2) 

The `current_user`/`current_api_client` split is exactly the "authenticated organization vs. written repository" style binding break called out in scope: the verified credential is the `ApiClient` token (scoped to permissions and optionally a single stack via `stack_id`), but the entity actually recorded as having performed the privileged action — deploy/rollback/task trigger (`stack.trigger_deploy`, `stack.trigger_task` in `app/models/shipit/stack.rb` lines 139-172) — is an arbitrary, unauthenticated `User` row chosen by the caller.

This matters beyond simple mislabeling because the claimed user's identity is propagated into the actual deploy execution environment, including git commit identity used by scripts that write to the repository via the app's own GitHub credentials: [4](#0-3) 

So a caller holding only a scoped `ApiClient` token (e.g. one issued for a CI integration with `deploy:stack` permission on a single stack) can impersonate any `User` in the Shipit instance — including admins — for the purposes of authorship attribution, audit trail, and any downstream logic keyed off `task.user`/`task.author` (e.g. `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` baked into commits made by deploy scripts, or `SHIPIT_USER`/`EMAIL` broadcast to hooks and outputs).

### Impact Explanation
This breaks the authentication binding between the credential that was actually verified (the `ApiClient` token) and the identity recorded/acted upon (`User`). Any party with a valid, even narrowly-scoped, `ApiClient` token can forge the identity of any other user for every API-triggered deploy, rollback, or task, corrupting audit trails and forging git commit authorship (`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`) on commits made during deploy scripts, which execute with the application's own `GITHUB_TOKEN`/GitHub App credentials. This is an identity/authentication-binding bypass at the "GitHub identity vs. `User` bound to the session" boundary explicitly listed as in-scope.

### Likelihood Explanation
Any actor with a legitimate `ApiClient` token — even one scoped to a single stack and a minimal permission set — can trivially set the `X-Shipit-User` header on any API request. No additional privilege, secret, or session is required beyond what is already needed to call the API at all, and the behavior is exercised and asserted by the existing test suite.

### Recommendation
Do not allow the acting `User` for API-triggered actions to be freely claimed via a request header. Either (a) require API clients to be created with a bound `creator`/allowed-actor list and validate the `X-Shipit-User` claim against it, (b) drop attribution to the `ApiClient` itself (record `current_api_client`, not an arbitrary `User`) unless a cryptographically-verified per-user token is presented, or (c) remove the header-based identity claim entirely for machine-to-machine tokens.

### Proof of Concept
Using any valid `ApiClient` bearer token with `deploy:stack` permission on a given stack, an attacker sends:
```
POST /api/stacks/org/repo/environment/deploys
Authorization: Basic <base64(valid_api_client_token)>
X-Shipit-User: victim-admin-login
{ "sha": "<commit sha>" }
```
The resulting `Deploy` record's `user` is set to `victim-admin-login`'s `User` row (as shown by the existing test asserting `deploy.user == @user` purely from the header), and the deploy environment is populated with that victim's `SHIPIT_USER`/`EMAIL`/`GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`, with no verification that the request actually originated from that user: [3](#0-2)
