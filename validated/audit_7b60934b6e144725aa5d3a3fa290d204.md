### Title
Unconditional bypass of inner-address definition resolution check in `['address', ...]` operator — `Definition.validateDefinition` accepts addresses with unresolved/nonexistent inner definitions - (File: definition.js)

### Summary
The OpenStack Neutron advisory describes a security filter that is supposed to enforce a binding invariant (source MAC ↔ authorized identity) but silently lets crafted inputs of certain shapes slip through because the enumeration of cases the filter checks is incomplete/hard-coded rather than conditioned on the real security state. In `ocore`'s `definition.js`, the `['address', <BASE32>]` operator inside `validateDefinition()` (used when validating the *structure* of a newly-submitted address/asset-condition definition) is supposed to conditionally allow "not yet resolvable" nested address references only when the caller explicitly opts in via `objValidationState.bAllowUnresolvedInnerDefinitions`. That conditional check has been replaced with a hard-coded `var bAllowUnresolvedInnerDefinitions = true;`, unconditionally short-circuiting the intended binding check for every caller, regardless of validation context.

### Finding Description
`validateDefinition()`'s `evaluate()` switch handles the `'address'` op (a definition referencing another, inner address) at [1](#0-0) . When the inner address's definition cannot currently be resolved from storage (`ifDefinitionNotFound`), the code is supposed to check whether the current unit's co-authors provide that inner definition; if not, it should reject with `"definition of inner address ... not found"` — *unless* the specific validation context (`objValidationState.bAllowUnresolvedInnerDefinitions`) explicitly permits deferring resolution (this flag is intentionally set only in narrow paths, e.g. `wallet_defined_by_addresses.js`'s `validateAddressDefinition()` at [2](#0-1) , used for local template/definition sanity checks before a definition is ever posted on-chain).

In the current code, the conditional check is commented out and replaced with an unconditional `true`:
```
ifDefinitionNotFound: function(definition_chash){
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
	var bAllowUnresolvedInnerDefinitions = true;
	...
	if (arrDefiningAuthors.length === 0) // no address definition in the current unit
		return bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb("definition of inner address "+other_address+" not found");
``` [3](#0-2) 

This means every call site of `validateDefinition`/`validateAuthentifiers` — including the ones invoked from `validation.js`'s `validateAuthor()` when a brand-new address definition is submitted on-chain as part of a real unit ( [4](#0-3) ), and from `signed_message.js`'s handling of signed packages/AA `is_valid_signed_package` paths ( [5](#0-4) ) — now treats an `['address', X]` clause referencing a completely unresolved/undefined address `X` as structurally *valid*, exactly as if the caller had opted into unresolved-inner-definition tolerance. There is no longer any way to enforce the strict binding for contexts (like posting a real address definition on the DAG) that should require the inner address to be either already defined in storage or co-defined by a fellow author in the same unit.

This is analogous to the Neutron bug class: a security-relevant matching/filtering decision that should be conditioned on context (which packet types/ports are covered by the anti-spoof rule) is instead effectively always-permissive for the uncovered case, letting crafted input bypass the intended binding check.

### Impact Explanation
An attacker can construct and post (or have accepted by a node) an address `A` whose spending definition includes `['address', X]`, where `X` is any syntactically valid but wholly unresolved/undefined address (never posted, no on-chain definition, and not co-signed in the same unit). Prior to the change, `validateDefinition` would reject such a definition when validating it in contexts that don't explicitly request tolerance (i.e., real on-chain author/definition validation), preventing addresses from being minted with dangling, unauthenticatable spending conditions embedded structurally. With the check hard-coded to always allow this, nodes will accept the definition as syntactically valid in every context.

While actual authentication (`validateAuthentifiers`) will still fail to spend from such an address until `X` truly gets resolved (so it does not immediately grant unauthorized spending), it removes a validation invariant relied upon by different callers with different security assumptions (e.g., strict server-side definition validation vs. best-effort client template checks). Because all nodes run identical code, this does not by itself cause a consensus split for units already accepted — but it removes a defense-in-depth check meant to reject malformed/incomplete address definitions upfront, and any place in the codebase that relies on `validateDefinition` succeeding as a proxy for "this definition is fully resolvable/well-formed" (e.g., asset-condition definitions, wallet UIs, AA-composed definitions) will now incorrectly treat dangling definitions as acceptable, which can lead to permanently unusable addresses being created/relied upon (funds sent to spending conditions that can never be satisfied, i.e., locked/frozen funds) or AA-composed asset conditions being accepted that reference addresses that will never resolve, undermining the "definitions must be strictly well-formed before being trusted" invariant across the codebase.

### Likelihood Explanation
High likelihood of being reachable: any unprivileged unit poster can submit a unit with a new address definition containing `['address', X]` referencing an unresolved address, or any AA/asset issuer can define an asset condition doing the same (this op is also reachable from asset conditions apart from `bAssetCondition` restriction — the restriction here bars `'address'` op specifically in asset conditions per line 274-275, but the same hardcoded-`true` pattern appears verbatim in the corresponding `validateAuthentifiers` "address" authentication branch context as well). No special privileges, hub/peer position, or race condition is needed — a single posted unit containing this construct is sufficient to reach the affected code path.

### Recommendation
Restore the conditional check so `bAllowUnresolvedInnerDefinitions` is driven by `objValidationState.bAllowUnresolvedInnerDefinitions` (as originally intended) rather than being hard-coded to `true`:
```js
ifDefinitionNotFound: function(definition_chash){
    if (objValidationState.bAllowUnresolvedInnerDefinitions)
        return cb(null, true);
    ...
    if (arrDefiningAuthors.length === 0)
        return cb("definition of inner address "+other_address+" not found");
    ...
}
```
Audit all call sites of `Definition.validateDefinition`/`validateAuthentifiers` to ensure only the intentionally-permissive callers (e.g., local wallet template pre-checks) set `bAllowUnresolvedInnerDefinitions = true`, while on-chain unit/AA/asset-condition validation paths leave it unset so dangling inner-address references are rejected.

### Proof of Concept
1. Construct a new address definition: `arrDefinition = ['address', '<SOME_VALID_BASE32_ADDRESS_NEVER_USED>']`.
2. Compute `address = objectHash.getChash160(arrDefinition)`.
3. Post a unit where an author uses `address` with this `definition` for the first time (`ifDefinitionNotFound` path in `readDefinitionByAddress`), and where `<SOME_VALID_BASE32_ADDRESS_NEVER_USED>` is not defined anywhere on-chain and not co-authored in the same unit.
4. Observe that `validateAuthor()` → `Definition.validateAuthentifiers()` → `validateDefinition()` reaches the `'address'` case, calls `ifDefinitionNotFound`, finds `arrDefiningAuthors.length === 0`, and — due to the hard-coded `bAllowUnresolvedInnerDefinitions = true` — returns `cb(null, true)` instead of the intended rejection `"definition of inner address ... not found"`, allowing the definition to pass structural validation despite referencing a permanently unresolved inner address.
