### Title
`provision?` operator-precedence bug bypasses `review_stacks_enabled = false` for `allow_with_label`/`prevent_with_label` behaviors - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the provisioning-behavior checks using Ruby operator precedence where `&&` binds tighter than `||`, so `review_stacks_enabled` only gates the `allow_all?` branch, not the `allow_with_label?` or `prevent_with_label?` branches. As a result, a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label` still provisions a review stack for any PR carrying the configured label.

### Finding Description
The broken binding, stated as an equality the operator expects to hold but does not:
`repository.review_stacks_enabled == (guard applied to every provisioning_behavior branch)` — this is false in the actual code.

The method: [1](#0-0) 

parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

rather than the operator's evidently intended:
`review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`

With `review_stacks_enabled = false` and `provisioning_behavior = :allow_with_label`:
- Term 1: `false && provisioning_behavior_allow_all?` → `false` (behavior isn't `allow_all` anyway).
- Term 2: `provisioning_behavior_allow_with_label? (true) && pull_request_has_provisioning_label? (true)` → `true`.

The overall `||` expression is `true`, so `provision?` returns `true` despite `review_stacks_enabled` being `false`.

Path: an attacker opens a pull request from a fork against the target repository and applies the repository's configured provisioning label (labels on one's own PR are attacker-controlled) via GitHub, which fires a `pull_request` `opened` webhook. `respond_to_pull_request_opened?` calls `provision?` [2](#0-1) , which returns `true` per above, causing `process` to invoke `ReviewStackAdapter#find_or_create!` [3](#0-2) , creating a `ReviewStack` and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add`, from which a deploy host later runs `shipit.yml` steps sourced from the attacker's fork/branch.

Existing guards do not prevent this: webhook signature verification only authenticates that the payload came from GitHub for that repository — it does not enforce the operator's `review_stacks_enabled` intent inside the handler's business logic. The label check (`pull_request_has_provisioning_label?`) is itself attacker-controlled since the PR author labels their own PR. No model validation or `ExplicitParameters` schema check enforces `review_stacks_enabled` on this branch. `NullRepository#review_stacks_enabled` and other default methods do not change this because the vulnerable repository is a real, persisted `Shipit::Repository`.

### Impact Explanation
An unauthorized `Shipit::ReviewStack` (backed by `Shipit::Stack`) is created and queued for provisioning on a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`). Provisioning ultimately drives deployment of attacker-influenced code/config (`shipit.yml`) from the PR branch onto the deploy host, matching the "unauthorized deploy" and RCE-adjacent Critical impact category. This is repeatable against any repository configured with `review_stacks_enabled: false` plus `provisioning_behavior: allow_with_label` (or `prevent_with_label`, inverted), by any user able to open a PR and set the configured label on it.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = false` and `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) — a plausible/likely operator configuration meant to fully disable auto-provisioning while still using labels for a differently-scoped feature, or simply an operator flipping `review_stacks_enabled` off without realizing the code doesn't respect it uniformly. Attacker cost is trivial: open a PR, add/observe the configured label name (visible in the repo's settings/label list, not secret), and no privileged token or session is required. Fully repeatable per PR/per repository.

### Recommendation
Fix operator precedence in `provision?` by explicitly parenthesizing so `review_stacks_enabled` gates all behavior branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the identical fix to `LabeledHandler`, `UnlabeledHandler`, and `ReopenedHandler`, which share the same pattern per the earlier grep matches.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing suite, not newly out-of-scope since it already exists and would just gain an assertion):
1. Create a `Shipit::Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Build a `pull_request` `opened` payload whose `pull_request.labels` includes `{ name: 'deploy-preview' }`.
3. Assert before: `repository.review_stacks_enabled == false` (operator intent: no provisioning).
4. Invoke `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process` (or trigger via the webhooks controller endpoint).
5. Assert after: `Shipit::Stack.count` / `Shipit::ReviewStack.count` increased by 1 and `Shipit::ReviewStackProvisioningQueue` received the new stack — demonstrating `provision?` returned `true` despite `review_stacks_enabled == false`, breaking the claimed binding.
