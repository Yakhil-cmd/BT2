### Title
Webhook signature is verified against an org selected from an attacker-controlled payload field, letting one org's webhook secret authorize actions against another org's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/`webhook_secret` to validate the HMAC signature against using a value read directly out of the untrusted request body (`repository.owner.login`, falling back to `organization.login`), while the event handlers that actually perform the write (e.g. `PushHandler`) select the target `Repository`/`Stack` using a completely different, independently-controlled field of the same body (`repository.full_name`). Because both fields live inside the same attacker-authored (and attacker-signed, from their own legitimate org secret) payload, nothing binds "the org whose secret validated this signature" to "the repository whose stack gets mutated."

### Finding Description
`verify_signature` computes the verifying `github_app` from a payload field, not from any independently trusted channel: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/`webhook_secret` configured for whatever organization name appears in `repository.owner.login` (or `organization.login`) inside the JSON body itself, then HMACs the raw body against that org's secret [3](#0-2) .

Downstream, `PushHandler#process` (and the shared `Handler#stacks`/`#repository_name`) resolve the actual `Repository`/`Stack` to mutate from a *different* field of the same body — `repository.full_name` — with no cross-check that it belongs to the org that was used to verify the signature: [4](#0-3) [5](#0-4) 

This breaks the equality that should hold: `org(signature-verified) == owner(repository acted upon)`. Before the attack, that equality trivially holds because GitHub itself always sends `repository.owner.login`/`organization.login` consistent with `repository.full_name`, and signs with the secret belonging to that exact org/installation. After the attack, an operator of Shipit-org-A (who legitimately knows org-A's `webhook_secret`, since they or an admin configured GitHub App/Shipit for their own org) can POST a crafted `push` (or `status`, `check_suite`) payload directly to `/webhooks` where `repository.owner.login`/`organization.login` = `"org-A"` (so `Shipit.github(organization: "org-A")` is selected and the attacker's own known secret validates the HMAC), but `repository.full_name` = `"org-B/victim-repo"` (a repository/stack that belongs to a completely different, unrelated organization tracked by the same Shipit instance). The signature check passes because it was computed by the attacker with the correct secret for the org they named, yet the handler acts on org B's stack.

### Impact Explanation
This is a cross-repository/cross-organization write bypassing the intended per-org webhook authentication boundary in a multi-org Shipit deployment (explicitly supported and documented, e.g. `config/secrets.development.shopify.yml` configuring `somegithuborg`/`someothergithuborg` each with their own `webhook_secret`) [6](#0-5) . With `PushHandler`, an attacker who only controls org A's webhook secret can force `stack.sync_github(expected_head_sha: params.after)` on org B's stacks [5](#0-4) , and other handlers keyed the same way (`status`, `check_suite`, `pull_request`) resolve their target `Repository`/`ReviewStack` from `repository.full_name` too [7](#0-6) , so the same cross-org confusion extends to commit status writes, review-stack archive/unarchive, and check-run refresh triggers on repositories the attacker was never granted access to. This matches "cross-repository writes" / "unauthorized deploy or rollback" impact criteria.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration) and that the attacker controls (or is an admin of) at least one of those configured orgs' webhook secret — no privileged Shipit account, GitHub token, or repository write access to the victim org is needed. This is a realistic deployment for any Shipit instance that services several teams/organizations from one host.

### Recommendation
Bind org selection and target-repository validation together: after `verify_signature` resolves `github_app`/organization, re-derive and enforce that every handler's target `Repository#full_name` (or its owner) actually belongs to that same verified organization before acting, rejecting (422) any payload whose `repository.full_name` owner does not match the organization whose secret validated the signature.

### Proof of Concept
1. Configure Shipit with two orgs, `org-A` and `org-B`, each with distinct `webhook_secret`s (as in `config/secrets.development.shopify.yml`).
2. As the operator/admin of `org-A` (who legitimately knows `org-A`'s `webhook_secret`), craft a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "org-B/victim-repo", "owner": { "login": "org-A" } }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(org-A_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"org-A"`, fetches `org-A`'s `github_app`, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`; `lib/shipit/github_app.rb:76-83`).
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-B/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`; `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and triggers `stack.sync_github` for `org-B`'s stack, despite the request never being authenticated for `org-B`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
