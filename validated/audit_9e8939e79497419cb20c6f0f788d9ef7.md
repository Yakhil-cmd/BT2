### Title
Unscoped SHA lookup in `StatusHandler#process` lets a `status` webhook mark commits deployable across unrelated repositories/stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` selects commits with `Commit.where(sha: params.sha)` with no filter tying the match to the repository that produced the webhook, then calls `create_status_from_github!` on every match. Because GitHub SHAs are content-addressed and shared across forks/mirrors of the same history, and because webhook signature verification is scoped to the *GitHub organization* (not the individual repository, and is a no-op entirely when `webhook_secret` is unset — the documented default), any commit sharing the SHA in any stack on the Shipit instance gets its CI state (and therefore `deployable?`) mutated by a webhook that did not originate from its own repository.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:

`commit.stack.repository.full_name == payload.repository.full_name` for every `commit` mutated by `StatusHandler#process`.

Code path:
1. `Shipit::WebhooksController#create` parses the raw JSON body and dispatches it to handlers for the event type, after only `verify_signature` runs. [1](#0-0) 
2. `verify_signature` resolves the signing secret purely from `repository_owner` (the `repository.owner.login` in the payload) via `Shipit.github(organization: repository_owner)`, i.e. **per organization**, not per repository: [2](#0-1) 
3. `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. This is the documented default/example configuration (`webhook_secret: # nil`) shown in `config/secrets.development.example.yml` and `docs/setup.md` ("Webhook secret (optional)"), so an installation following the documented setup has zero authentication on `POST /webhooks`. [3](#0-2) 
4. `StatusHandler#process` then applies the payload globally by bare SHA, with no join/filter on `stack_id`, `repository_id`, or the payload's `repository.full_name`: [4](#0-3) 
5. `Commit#create_status_from_github!` persists the attacker-controlled `state`/`description`/`target_url`/`context` as a `Status` and recomputes the commit's CI state, which feeds `Commit#deployable?` (`success? && !blocked?`), directly gating deploy eligibility in the UI/API. [5](#0-4) 

Even when a `webhook_secret` *is* configured, the signature check is scoped per-org, not per-repo: any repository under the same GitHub App installation (e.g. any repo an attacker legitimately owns within that org, or — in the "multiple GitHub Applications" configuration shown in `docs/setup.md`/`test/dummy/config/secrets_double_github_app.yml` — any org configured on the instance) can emit a genuinely-signed `status` event whose `sha` collides with a commit that also exists (via shared git history — e.g., a fork sharing ancestor commits, or a cherry-pick/identical commit) in a completely different stack's repository. `Commit.where(sha:...)` has no idea which repository actually produced the event and applies the status to all matches.

None of the existing guards close this gap: `drop_unhandled_event` only checks the event type is handled at all; the `ExplicitParameters` schema for `StatusHandler` only validates payload shape (`sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`), not repository ownership; there is no `stacks.where(repository: ...)` filter analogous to what `CheckSuiteHandler` at least partially attempts via branch (and which itself is also unscoped by repository).

### Impact Explanation
A successful request changes the persisted CI status/state of a commit belonging to a stack the attacker does not control, which flips `Commit#deployable?` to `true` and can enable an unauthorized deploy, rollback, or merge decision for that victim stack — this is a payload for one repository mutating another repository's commit/stack state, matching the Critical impact category explicitly listed in the rules. It is repeatable against any repository/stack whose commits share a SHA with a repository the attacker can produce (or forge, when `webhook_secret` is unset) webhook traffic for, and is not limited to a single victim — any stack sharing history (forks, mirrors, monorepo splits) with an attacker-reachable repository is affected.

### Likelihood Explanation
- If the Shipit installation follows the documented example config with `webhook_secret` left blank (shown as the default in `config/secrets.development.example.yml` and allowed as "optional" in `docs/setup.md`), `verify_webhook_signature` always returns `true` and the attacker needs no secret at all — pure unauthenticated `POST /webhooks`.
- Even with a webhook secret configured, an attacker who owns or forks any repository under the same GitHub organization/App installation can trigger genuinely-signed `status` events for SHAs that are shared with a victim repository's history (a very common situation for public forks).
- The attacker needs no Shipit session, API token, or GitHub team membership — only the ability to send an HTTP request or to control CI reporting on a repository they own, both of which are explicitly in-scope "unprivileged" capabilities per the rules.

### Recommendation
Scope `Commit.where(sha: params.sha)` in `StatusHandler#process` (and the analogous unscoped lookups in `CheckSuiteHandler`) to commits belonging to the stack(s)/repository identified by `params.repository.full_name` (or `params.name`, as already present in the `status` payload), e.g. join through `Stack -> Repository` and filter by `full_name`/`owner`+`name` before iterating, mirroring how `push` handling resolves the target stack from the payload's repository. Additionally, consider making webhook signature verification mandatory (reject when no `webhook_secret` is configured) rather than defaulting to open when unset.

### Proof of Concept
minitest plan (no live GitHub required):
1. Seed two `Stack`/`Repository` fixtures, `repo_a` and `repo_b`, in different orgs/full_names, each with a `Commit` sharing the identical `sha` value (simulating shared git history).
2. Stub `GithubHook`/`verify_webhook_signature` to return `true` (as existing tests do), or configure `webhook_secret` to `nil` for the org to reflect default config.
3. POST a `status` webhook to `/webhooks` with `X-Github-Event: status`, `sha` set to the shared SHA, `state: 'success'`, and `repository.full_name` set to `repo_a`'s full name only.
4. Assert BEFORE: `repo_b`'s commit `state` is `'unknown'`/non-success and `deployable?` is `false`.
5. Assert AFTER: `repo_b`'s commit now has a `Status` record with `state == 'success'` and `commit.deployable?` is `true`, even though the payload's `repository.full_name` never matched `repo_b`. This demonstrates the binding `commit.stack.repository.full_name == payload.repository.full_name` is violated for `repo_b`'s commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
