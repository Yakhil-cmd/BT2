## Analysis

This is a case where an unprivileged party can read `Stack`s that their ApiClient token is not authorized for, because the token-to-stack binding enforced elsewhere is not enforced in `Api::CCMenuController`.

### The binding
`stack_id` an ApiClient's token authorizes == `stack_id` the endpoint actually returns data for.

`Api::BaseController` establishes this binding for every other API endpoint: [1](#0-0)  The `stacks` scope is restricted to `current_api_client.stack_id` whenever the client is stack-scoped, and `stack` is looked up only within that scope.

`Api::CCMenuController` overrides `stack` and bypasses this scoping entirely, resolving the stack directly from the request parameter against the global `Stack` table: [2](#0-1)  It only checks `require_permission :read, :stack` (a permission-name check, not a stack-scope check) via `check_permissions!`: [3](#0-2) 

A stack-scoped ApiClient (`belongs_to :stack, optional: true`, see the `here_come_the_walrus` fixture) is meant to be confined to one stack, as proven by the `stacks` helper in `BaseController` and by the dedicated test "an api client scoped to a stack will only see that one stack": [4](#0-3)  and by the `ApiClient` fixture defining a `stack:` scope: [5](#0-4) 

### Before / after
- Before the request: an ApiClient token is minted/scoped to `stack: shipit` only, permission `read:stack`.
- After the request to `GET /api/stacks/:other_stack_id/ccmenu.xml`: `CCMenuController#stack` resolves `other_stack_id` directly via `Stack.from_param!`, ignoring `current_api_client.stack_id`, and the controller renders that other stack's latest deploy/rollback status and build state — data the token was never authorized to read.

This breaks exactly the “stack a token authorises versus a stack it touches” equality called out in the rules, and matches the report’s bug class: the code performs the authorization decision (permission check) against one attribute of the request (`read:stack` permission) while silently ignoring another binding attribute (`stack_id` scope) that should have gated the same operation — analogous to `receive_request` checking `signature_thresholds[data.committee_id]` instead of the value tied to the actually-processed `committee_id`.

### Title
Stack-scoped API tokens can read CCMenu status of unauthorized stacks - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` resolves the target stack from `params[:stack_id]` against the entire `Stack` table instead of using the `stacks` helper that scopes lookups to `current_api_client.stack_id`, as every other API controller does. A stack-scoped ApiClient token can therefore be used to read the CCMenu build/deploy status of any stack, not just the one it was issued for.

### Finding Description
`Api::BaseController` defines the trust boundary for stack-scoped tokens: [1](#0-0)  All controllers inheriting `stack` from this base are confined to the stacks the token is scoped to. `Api::CCMenuController` re-defines `stack` to bypass this scope, going straight to `Stack.from_param!(params[:stack_id])`: [6](#0-5)  The only remaining check, `require_permission :read, :stack`, validates the client's permission list, not which stack it is entitled to touch: [3](#0-2)  The controller even supports authenticating purely via a `?token=` query parameter, making it trivial to hit with an arbitrary `stack_id`: [7](#0-6) 

### Impact Explanation
An attacker holding any valid ApiClient token scoped to a single, low-privilege stack (`read:stack` permission, `stack_id` set) can enumerate/guess other stacks' `to_param` identifiers and retrieve their CCMenu XML, exposing the latest deploy/rollback outcome (`stack.deploys_and_rollbacks.last`), build status, and stack name for stacks the token was never authorized to access. This is an unauthenticated (relative to that stack) read of stack state/deploy output, matching the High-severity impact category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Requires only possession of any valid, low-privilege ApiClient token that is stack-scoped (a normal, supported configuration per `ApiClient#stack` and the `here_come_the_walrus` fixture) — no elevated permissions, no repository write access, and no special conditions beyond knowing/guessing another stack's `to_param`.

### Recommendation
Have `Api::CCMenuController#stack` use the same scoped lookup as `Api::BaseController`, e.g. `stacks.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is honored consistently across all API endpoints.

### Proof of Concept
1. Create/obtain an `ApiClient` with `stack_id` set to Stack A and permission `read:stack` (mirrors the `here_come_the_walrus` fixture).
2. As that client, call `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` where Stack B is a different, unauthorized stack.
3. `authenticate_api_client` succeeds (valid token), `require_permission :read, :stack` passes (client has that permission), and `stack` resolves Stack B directly via `Stack.from_param!`, returning Stack B's deploy/rollback status in the XML response — despite the token only being authorized for Stack A.
