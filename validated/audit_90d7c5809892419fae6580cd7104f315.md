### Title
Unchecked ERC721 `transferFrom` Return Value in Bridge Allows Silent Transfer Failure with Permanent Nonce Consumption — (`contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721` calls `IERC721(_tokenAddress).transferFrom(...)` in two places without any success check or safe-transfer wrapper. The ERC20 bridge counterpart correctly uses `SafeERC20` (`safeTransfer`/`safeTransferFrom`) throughout. The ERC721 bridge has no equivalent protection, so a non-standard ERC721 token that returns `false` instead of reverting causes the bridge to silently proceed: in `handleERC721Transfer` the handle-nonce is permanently consumed and the request is marked handled before the transfer executes, meaning the NFT is never delivered but the slot is irrecoverably spent; in `requestERC721Transfer` the cross-chain event is emitted and `requestNonce` is incremented without the bridge actually receiving the NFT.

---

### Finding Description

`BridgeTransferERC20` imports and applies `SafeERC20` for every token interaction: [1](#0-0) 

All ERC20 outbound transfers in `handleERC20Transfer` and fee-refund paths use `safeTransfer`/`safeTransferFrom`: [2](#0-1) [3](#0-2) 

`BridgeTransferERC721` has no such wrapper. Both call sites use a raw `IERC721.transferFrom`:

**Outbound (handle) path** — state is fully committed *before* the transfer: [4](#0-3) 

The sequence is:
1. `_setHandledRequestTxHash` (line 49) — marks the source tx as handled
2. `handleNoncesToBlockNums[_requestedNonce]` written (line 51)
3. `_updateHandleNonce` (line 52) — advances `lowerHandleNonce`
4. `HandleValueTransfer` event emitted (lines 54–64)
5. **Then** `IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId)` (line 69) — no check

**Inbound (request) path** — event and nonce increment happen after a silent-fail transfer: [5](#0-4) 

The IERC721 interface declares `transferFrom` as returning nothing (`void`): [6](#0-5) 

Solidity 0.5.x ignores any data returned by a `void`-declared external call. If the actual token implementation returns `false` (non-standard but possible), the EVM call succeeds, Solidity discards the return data, and execution continues as if the transfer succeeded.

---

### Impact Explanation

**`handleERC721Transfer` (non-mintBurn mode):** The handle nonce slot is permanently consumed and the source tx hash is permanently marked as handled before the `transferFrom` executes. If the transfer silently fails, the NFT is never delivered to `_to`, and the bridge has no mechanism to retry (the nonce check at line 43 will reject any re-submission). The bridged NFT is permanently lost.

**`requestERC721Transfer`:** If `transferFrom(msg.sender, address(this), _tokenId)` silently fails, the bridge emits `RequestValueTransferEncoded` and increments `requestNonce`. Bridge operators on the counterpart chain observe the event and call `handleERC721Transfer` there, releasing or minting an NFT to the attacker's `_to` address — without the bridge ever having custody of the original NFT. This is an unauthorized mint/unlock of a bridged asset.

---

### Likelihood Explanation

The token must be registered by an operator/owner, which limits the inbound-request attack vector to tokens with non-standard behavior that were registered in good faith. The outbound-handle path is triggered by operators responding to a legitimate cross-chain event; if the registered token on the destination chain has non-standard `transferFrom` behavior, the loss occurs automatically during normal bridge operation. The ERC721 standard (EIP-721) says implementations *should* throw on failure, but does not prohibit returning `false`, and the bridge explicitly supports arbitrary registered tokens.

---

### Recommendation

Introduce a safe ERC721 transfer helper analogous to `SafeERC20`. Use `safeTransferFrom` (which invokes `onERC721Received` and reverts on failure) instead of raw `transferFrom` in both call sites, or add an explicit post-transfer ownership check:

```solidity
// Option A: use safeTransferFrom (reverts on failure)
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);

// Option B: assert ownership changed
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
require(IERC721(_tokenAddress).ownerOf(_tokenId) == _to, "ERC721 transfer failed");
```

Apply the same fix to `requestERC721Transfer` line 129 so that a silent failure reverts the entire transaction before any state is mutated.

---

### Proof of Concept

1. Deploy a malicious ERC721 token whose `transferFrom` always returns `false` (or returns `false` for a specific `tokenId`) without reverting.
2. Register the token on both bridge sides (operator action).
3. Call `requestERC721Transfer(maliciousToken, attacker, tokenId, "")` on the child chain.
   - `transferFrom(msg.sender, address(this), tokenId)` returns `false`; Solidity ignores it (void interface).
   - `_requestERC721Transfer` runs: emits `RequestValueTransferEncoded`, increments `requestNonce`.
   - Bridge operators observe the event and call `handleERC721Transfer` on the parent chain.
   - Parent bridge transfers/mints the NFT to `attacker` — attacker receives an NFT without depositing one.
4. Alternatively, for the handle path: deposit a legitimate NFT, then replace the token implementation (upgradeable proxy) so `transferFrom` returns `false`. The next `handleERC721Transfer` call consumes the nonce and marks the request handled, but the NFT is never delivered. [7](#0-6) [8](#0-7)
