### Title
CCMenuController#stack bypasses tenant-scoped `stacks` lookup, allowing cross-tenant stack read - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stack` scopes lookups through `stacks.from_param!(params[:stack_id])`, where `stacks` filters to `Stack.where(id: current_api_client.stack_id)` when the API client is stack-scoped [1](#0-0) . `CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely ignoring `current_api_client.stack_id` [2](#0-1) . As a control, `HooksController#stack_id` correctly relies on the inherited scoped `stack`/`stacks` (via `Hook.where(stack_id:)`) and 404s for a token scoped to a different stack [3](#0-2) , confirming the vulnerability is specific to `CCMenuController`.

### Finding Description
The intended binding is: for every `Api::BaseController` subclass, `#stack` (or equivalent lookup) must equal `stacks.from_param!(params[:stack_id])`, i.e. scoped to `current_api_client.stack_id?  ? Stack.where(id: current_api_client.stack_id) : Stack.all`. This binding holds for `HooksController` (inherited, unmodified `#stack`/`#stacks`) but is broken in `CCMenuController`, which redefines `#stack` as `Stack.from_param!(params[:stack_id])` — a direct, unscoped class-level lookup [2](#0-1) .

Call sequence for the exploit: attacker holds an `ApiClient` token whose `stack_id` is scoped to their own stack and which has the `read:stack` permission (required by `require_permission :read, :stack` on `CCMenuController`) [4](#0-3) . `CCMenuController#authenticate_api_client` re-authenticates via `params[:token]` instead of Basic Auth, but this still resolves the same `ApiClient` record with the same `stack_id` restriction [5](#0-4) . The attacker requests `GET /api/stacks/:victim_stack/cc.xml?token=<their_token>`. `#show` calls `stack.deploys_and_rollbacks.last`, and `#stack` resolves via `Stack.from_param!(params[:stack_id])`, which — unlike `stacks.from_param!` — is not filtered by `current_api_client.stack_id`, so it succeeds for the victim's stack id [6](#0-5) . `check_permissions!` only checks that the string `"read:stack"` is in the client's `permissions` array; it never checks `stack_id` equality [7](#0-6) , so nothing blocks the divergent path.

Contrast: `HooksController#stack_id` calls `stack.id`, and that `stack` is the inherited `BaseController#stack` method (`stacks.from_param!(params[:stack_id])`), where `stacks` is `Stack.where(id: current_api_client.stack_id)` for scoped tokens [1](#0-0) . For the victim stack id not in that scoped relation, `from_param!` raises `RecordNotFound`, producing 404 as expected.

### Impact Explanation
An attacker with a token scoped to their own stack (and `read:stack` permission) can read another tenant's stack deploy/rollback state (latest deploy id, status, timestamps rendered in the CCTray XML) via `CCMenuController#show`, for any arbitrary victim stack id, repeatably. This is an unauthenticated-for-that-resource read of stack state across tenants, matching the "High" impact category (unauthenticated read of stack state for a repository/stack the token was not scoped to).

### Likelihood Explanation
Preconditions: attacker must possess one valid `ApiClient` token with `read:stack` permission scoped to their own stack (a token they would legitimately be issued for their own repository), and know or guess the victim's stack id (small sequential integer, or discoverable). No GitHub or Shipit secrets are required beyond the attacker's own legitimately-issued token. Cost is a single HTTP GET; fully repeatable against any stack id.

### Recommendation
Change `CCMenuController#stack` to use the scoped lookup consistent with `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the private override entirely so it inherits `BaseController#stack`/`#stacks`, ensuring `current_api_client.stack_id` scoping is enforced identically to `HooksController` and other subclasses.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (conceptual, minitest, no live GitHub)
test "CCMenuController#show leaks a stack outside the token's scope while HooksController#index does not" do
  attacker_stack = shipit_stacks(:shipit)
  victim_stack   = shipit_stacks(:cocoapods) # a different tenant's stack

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'attacker-token',
    stack_id: attacker_stack.id,
    permissions: %w[read:stack read:hook]
  )
  token = scoped_client.authentication_token

  # Control: HooksController correctly 404s for the victim stack
  get "/api/stacks/#{victim_stack.id}/hooks", headers: { 'Authorization' => "Basic #{Base64.strict_encode64(token + '--')}" }
  assert_response :not_found

  # Exploit: CCMenuController succeeds for the same token/victim stack
  get "/api/stacks/#{victim_stack.id}/cc.xml", params: { token: token }
  assert_response :success
  assert_includes @response.body, victim_stack.repo_name # cross-tenant leak
end
```
This test asserts the discrepancy: `stacks.from_param!` (used by `HooksController` via inherited `BaseController#stack`) rejects the victim stack, while `Stack.from_param!` (used directly by `CCMenuController#stack`) accepts it for the same token.
