## Title
Merkle proof verification lacks leaf/node domain separation, allowing forged inclusion proofs ("node-as-leaf" attack) - (File: merkle.js)

### Summary
The core Merkle-tree implementation used to validate `'in merkle'` address-definition authentifiers and the `is_valid_merkle_proof` formula operator does not separate leaf hashes from internal-node hashes. Because `verifyMerkleProof` always performs exactly one extra `hash()` on the supplied `element` before walking the sibling path, an attacker can substitute the raw concatenation of two sibling hash strings as a fake "element" and produce a cryptographically valid inclusion proof for data that was never actually inserted as a leaf of the tree.

### Finding Description
`merkle.js` builds the tree by repeatedly hashing pairs of child hashes with no tag distinguishing "leaf hash" from "internal node hash": [1](#0-0) 

`verifyMerkleProof` reconstructs the root by first hashing the caller-supplied `element` once (treating it as a leaf), then repeatedly combining it with the supplied siblings: [2](#0-1) 

The comment on line 85 — `// Node-as-Leaf issue might matter in some cases` — explicitly acknowledges the flaw. Because a leaf value at any level is just `hash(element)`, and an internal node value is `hash(childA + childB)`, an attacker who knows any two adjacent hash values in the tree (`childA`, `childB` — obtainable either from the tree's public leaf/side data or from any previously-observed proof) can set:

```
element = childA + childB   // raw string concatenation
```

Then `hash(element)` in `verifyMerkleProof` equals exactly the internal node `hash(childA+childB)` that the real tree already contains at that position. Supplying the correct remaining upper-level siblings completes a fully valid path to the true Merkle root, even though `element` (the concatenated hash string) was never one of the tree's original leaves.

This primitive is reachable by any unprivileged unit poster or AA trigger sender through two exposed code paths:

1. **Address-definition authentifier `'in merkle'`** — used to gate spending/signing based on Merkle-root inclusion checked against a value published via `data_feeds`: [3](#0-2) 

2. **`is_valid_merkle_proof` formula operator**, directly reachable from any AA trigger's `data.proof`/`data.element` and evaluated with attacker-controlled trigger data during AA execution: [4](#0-3) 

Both call sites trust a `true` result from `verifyMerkleProof` as proof that a specific value was part of a previously-committed, whitelisted/attested set (e.g., an oracle-published allowlist root, an airdrop-eligibility root, or an asset-issuer-controlled dataset). Since the verification function itself cannot distinguish "real leaf" from "forged concatenation of two internal hashes," any AA or address-definition logic that branches on this boolean (e.g., to authorize a payment, mark an address as eligible, or unlock a private/asset transfer) can be tricked into accepting data that was never actually committed by the publishing party.

### Impact Explanation
Any oscript/AA design pattern that uses `is_valid_merkle_proof` or `'in merkle'` to gate fund release, eligibility, or authorization (airdrops, allowlists, attestation roots, etc.) is vulnerable to a forged-inclusion bypass. An attacker who can observe the tree's internal hash structure (commonly available since Merkle trees of this kind are usually published with full leaf sets, or partial paths are leaked through previous legitimate proofs) can fabricate a syntactically valid proof for non-member data. Depending on how the consuming AA/definition uses the verified boolean, this can lead to unauthorized fund release from an AA, bypass of address-definition authorization checks, or incorrect eligibility determinations — i.e., concrete unauthorized spending or AA fund loss.

### Likelihood Explanation
Exploitation requires knowledge of at least two adjacent hash values within the committed tree, which is readily available in typical use cases where the full leaf set (or a superset of proofs) is public, as is common for airdrop/allowlist Merkle trees. No special privileges beyond posting a normal unit or AA trigger are needed to submit the forged proof; the flaw lives in the fundamental proof-verification primitive shared by all consumers of `merkle.js`.

### Recommendation
Introduce domain separation between leaf and internal-node hashing (e.g., prefix leaves with a distinct tag such as `0x00 + element` and internal nodes with `0x01 + childA + childB`) in `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof`, and version/gate this change behind an upgrade MCI to preserve backward compatibility with already-committed roots, similar to other `constants.*UpgradeMci` gated behavior changes in this codebase.

### Proof of Concept
1. Publisher builds a Merkle tree over leaves `[L0, L1, L2, L3]` using `getMerkleRoot`/`getMerkleProof` and publishes the root via a data feed (or an AA state variable) intended to authorize only `L0..L3`.
2. Attacker, knowing `hash(L0)=h0` and `hash(L1)=h1` (either from the public leaf list or a legitimately obtained proof for `L0`/`L1`), computes `fakeElement = h0 + h1` (raw string concatenation).
3. Attacker submits `is_valid_merkle_proof(fakeElement, {index: 0, siblings: [hash(hash(L2)+hash(L3))], root: R})` (or the equivalent `'in merkle'` authentifier data) in a trigger/unit.
4. `verifyMerkleProof` computes `hash(fakeElement) = hash(h0+h1)`, which equals the real internal node at that position, then combines with the supplied sibling to reproduce the true root `R`, returning `true` — despite `fakeElement` never having been an original leaf of the committed set.

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
