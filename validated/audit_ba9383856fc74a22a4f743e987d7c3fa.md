### Title
Global unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows cross-tenant Status writes - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits solely by `sha`, with no filter on repository/stack, then calls `create_status_from_github!` on every match. [1](#0-0)  Because `sha` is not globally unique across stacks (shared/vendored commits, cherry-picks, or well-known shas like the empty tree), one signed webhook naming a single repository can mutate `Status` rows belonging to unrelated tenant stacks.

### Finding Description
The broken binding: the number of `Stack`s whose data is mutated by one status webhook should equal 1 (the stack tied to `payload.repository.full_name`), but instead equals N = `Commit.where(sha: params.sha).count`, i.e. every stack that happens to have a `Commit` row with that sha.

Tracing the path: `WebhooksController#create` parses the JSON body and dispatches to handlers for the event type, then calls `handler.call(params)`. [2](#0-1)  Before dispatch, `verify_signature` only checks the HMAC signature against the GitHub App configured for `repository_owner` (the org in the payload), proving the request came from someone with a valid webhook secret for *that org* — it says nothing about which `Stack`/`Commit` should be affected. [3](#0-2)  The `StatusHandler` params schema requires only `sha`, `state`, and optional description/target_url/context/branches — notably `repository` is never declared or read. [4](#0-3)  `process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no `stack_id`/repository predicate. [1](#0-0)  `create_status_from_github!` calls `add_status`, which creates a `Status` row, reloads the commit's computed `status`, and — critically — emits `commit_status`/`deployable_status` hooks and can call `stack.schedule_merges`, directly influencing that (unrelated) stack's deploy/merge state. [5](#0-4) [6](#0-5) 

Root cause: the model layer treats `sha` as if it were a repository-scoped identifier for lookup purposes in this handler, but the schema only enforces sha uniqueness per stack (each `Stack` has its own `Commit` rows), not globally. Any attacker who legitimately administers a GitHub App/webhook for *their own* org (satisfying `verify_signature` for their own org) can send a `status` event whose `sha` happens to also exist as a `Commit` row in a completely different tenant's stack (different repo, potentially different org). None of the listed guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `force_github_authentication`, `require_permission!`) constrain the `Commit` scope to the requesting repository — they only gate whether the request is accepted at all, not which records it can touch.

Attacker's exact request: a `status` webhook POST to `/webhooks` for a repository the attacker owns/administers, signed with that repo/org's legitimate webhook secret, with `sha` set to a value known (or engineered, e.g. by pushing an empty commit whose tree/parent produces a colliding sha, or simply using the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`) to also be present as a `Commit` row in a victim tenant's stack.

### Impact Explanation
A single authenticated-for-one-repo webhook write fans out to `Status` records (and therefore computed CI state, `deployable_status`/`commit_status` hooks, and `schedule_merges` triggering) on every tenant `Stack` that has a `Commit` row sharing that sha — not just the stack tied to the requester's repository. This is a payload for one repository mutating another's stack/commit, matching the Critical category. It is repeatable against any set of stacks sharing a sha, and blast radius scales with however many stacks track that sha (bounded only by how many tenants happen to share it).

### Likelihood Explanation
Preconditions: attacker needs a legitimately signed webhook for a repo/org they control (this is a normal, unprivileged GitHub App/webhook installation on their own repository — not a Shipit credential), and at least one victim `Commit` row elsewhere sharing the same `sha`. Shared shas are realistic via vendored dependencies, cherry-picked/rebased commits across forks, or the universal empty-tree sha. Attacker cost is low (one HTTP POST), and the attack is fully repeatable/scriptable against any sha they can confirm or force to collide.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) to the stack(s) matching `params.repository.full_name`/`repository_id`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repo.id })`, instead of a bare `sha` match across the entire table.

### Proof of Concept
1. Fixtures: create 3 `Stack`s in 3 distinct `Repository`s, each with a `Commit` row sharing `sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904"`.
2. POST a `status` event to `/webhooks` with a valid signature for only one of the three repositories (`payload.repository.full_name` = repo A), `sha` = the shared sha, `state = "success"`.
3. Assert: before request, `Status.count` for stacks B and C == 0; after request, `Status.count` increased to 1 for stacks A, B, and C (not just A) — i.e. `Commit.where(sha: shared_sha).map(&:stack_id).uniq.size == 3` mutated stacks versus the expected `1` (only the stack of `payload.repository.full_name`).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
