This confirms the contrast: `CheckSuiteHandler#process` at [1](#0-0)  correctly scopes the lookup through `stacks` (derived from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`) and then `stack.commits.where(sha: ...)`, restricting the match to commits belonging to the repository named in the webhook payload. `StatusHandler#process`, by contrast, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/stack scoping at all, and its `params` schema doesn't even require or reference `repository`.

### Title
Commit status webhook applies attacker-controlled context/description to any commit sharing the same SHA across all stacks, unblocking unrelated stack deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up target commits solely by `Commit.where(sha: params.sha)`, with no check that the commit belongs to the repository named in the webhook payload, unlike `CheckSuiteHandler` which scopes via `stacks` derived from `payload['repository']['full_name']`. Any commit row in the entire `commits` table sharing the SHA from an attacker-controlled but validly-signed status event (`state`, `context`, `description` all attacker-supplied) gets a new `Status` record via `Shipit::Commit#create_status_from_github!` → `Status.replicate_from_github!`, and that status is used unsanitized by `Status::Common#blocking?`/`#required?` and `Commit#blocked?`/`#deployable?` to decide whether stack A's deploy is unblocked.

### Finding Description
The broken binding: "a status context recognized as required/blocking for stack A" should equal "a context repo A's own CI configured for repo A emits, scoped to stack A's commits." In code, this scoping never happens:

- `StatusHandler.params` only requires `sha`, `state`, and accepts `description`/`target_url`/`context`/`created_at`/`branches` — it never requires or inspects `repository` [2](#0-1) .
- `process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , matching any commit row across the whole table by SHA alone, regardless of which repository/stack it belongs to.
- `Commit#create_status_from_github!` forwards straight into `statuses.replicate_from_github!(stack_id, github_status)`, persisting `state`, `description`, `context`, `target_url` verbatim from the attacker-controlled `params` [4](#0-3) [5](#0-4) .
- `Status::Common#blocking?`/`#required?` compare the persisted (attacker-supplied) `context` directly against `commit.blocking_statuses`/`commit.required_statuses` (delegated to `Stack`/`DeploySpec`) with no verification that the context actually originated from repository A's registered CI provider [6](#0-5) .
- `Commit#deployable?` and `#blocked?` consume this status to gate deploys: `deployable?` requires `success? && !blocked?`, and `blocked?` walks undeployed commits checking `blocking?` [7](#0-6) .

Contrast with `CheckSuiteHandler`, which correctly resolves `stacks` from `payload['repository']['full_name']` and scopes the SHA lookup to `stack.commits` [1](#0-0) . `StatusHandler` lacks this equivalent guard.

Exploit flow: attacker owns/controls a GitHub repository (repo B) that is onboarded into the same Shipit instance (e.g. same GitHub org/App installation, a very common multi-tenant Shipit deployment). Attacker obtains — by reading public history, forking, or otherwise legitimately fetching — the exact raw git commit object for a commit that exists in stack A's history, and pushes/imports that identical commit (identical SHA) into repo B's own history/branch. Attacker then calls the GitHub Status API on their own repo B (an entirely unprivileged, self-authorized action for a repo they own) to set a status with `context` equal to one of stack A's `required_statuses`/`blocking_statuses` and `state: success`. GitHub delivers a correctly-signed webhook (`X-Hub-Signature` verified by `WebhooksController#verify_signature` against the org-level `webhook_secret`, which the attacker does not need to know since GitHub itself computes and signs it) to Shipit's `/webhooks` endpoint with `repository.full_name = "owner/repoB"`. `verify_signature` passes because it only checks HMAC validity, not that the claimed repository is authorized to affect stack A. `StatusHandler#process` then finds the commit row(s) with that SHA belonging to stack A (because it never filters by repository) and creates a new `Status` for stack A with the attacker's forged `context`/`description`, satisfying `required_statuses`/unblocking `blocked?` for stack A.

Existing guards that fail to prevent this: `verify_signature` only authenticates that *some* correctly configured GitHub App/org sent the payload — it does not bind the payload's claimed repository to the commits it is allowed to mutate. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not repository ownership. There is no `EnvironmentVariables#permit`-style filtering of `context`/`description`, and `Status::Common#blocking?`/`#required?`/`Commit#blocked?`/`#deployable?` perform no scope check tying the status's provenance to stack A's own configured CI. The `commits` table is indexed on `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same SHA can legitimately have separate rows under multiple different stacks — exactly the condition `StatusHandler` fails to distinguish between.

### Impact Explanation
An attacker who controls any onboarded repository can inject a `Status` row (with attacker-chosen `state`, `context`, `description`) onto any other stack's commit that shares the same SHA, as long as they can get that exact commit object into their own repo's history and trigger a real GitHub status event for it. This satisfies `required_statuses`/`blocking_statuses` checks used by `Commit#deployable?`/`#blocked?`, enabling an unauthorized deploy for a stack (repository A) the attacker does not own or control — a payload for one repository mutating another's stack/commit state, matching the Critical "unauthorized deploy" category. The attack is repeatable against any stack/commit pair sharing a SHA (e.g., forked repos, vendored histories, shared upstream commits, or intentionally recreated commit objects) and is not limited to a single stack.

### Likelihood Explanation
Preconditions: (1) attacker must own/control a repository already onboarded to the same Shipit instance/GitHub App installation as the victim stack (realistic in any multi-tenant/single-org Shipit deployment hosting many teams' repositories); (2) attacker must get a commit with an identical SHA to a victim commit into their own repo's history (achievable by fetching the raw commit object from a public/forked repository and pushing it as a new ref in their own repo — no cryptographic secret required, just knowledge of the commit's exact byte content); (3) attacker must know or guess the exact `context` string configured in the victim stack's `deploy_spec` `ci.require`/`ci.blocking` (often predictable, e.g. `ci/circleci`, or discoverable via the stack's public status page/API). No Shipit secrets, session, or API token are needed — GitHub itself signs the webhook. This is a feasible, repeatable attack within engine code, not a theoretical one.

### Recommendation
Scope `StatusHandler#process` to only match commits within stacks belonging to the repository named in the webhook payload, mirroring `CheckSuiteHandler`: require `repository.full_name` in the params schema, resolve `stacks` via `Repository.from_github_repo_name(params.repository.full_name)`, and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalent joined query) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `webhooks_controller_test.rb`):
1. Create `stack_a` for repository `"org/repo-a"` with `cached_deploy_spec` containing `ci.require: ['ci/important']` (so `stack_a.deploy_spec.required_statuses == ['ci/important']`).
2. Create `commit` under `stack_a` with a known `sha` (e.g., `"deadbeef" * 5`), no statuses yet — assert `commit.blocked?`/`deployable?` is false (binding LHS: context recognized as required for stack A) while asserting no status with that context exists yet from repo A's own CI (binding RHS is empty).
3. POST to `/webhooks` with `X-Github-Event: status`, a validly stubbed/verified signature, and JSON body: `{"sha": commit.sha, "state": "success", "context": "ci/important", "description": "forged", "repository": {"full_name": "org/repo-b"}, "branches": [...]}` — i.e., `repository.full_name` names an unrelated repo B, not stack A's repo.
4. Assert a `Status` row was created on `commit` (`stack_a`) with `context == "ci/important"`.
5. Assert `commit.reload.deployable?` becomes `true` and `commit.blocked?` becomes `false` — proving the binding is broken: a context forged via repo B's webhook was accepted as authoritative for stack A without any check that it originated from repo A.
