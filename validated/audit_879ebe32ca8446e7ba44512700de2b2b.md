I've done sufficient investigation. The strongest, most concretely provable analog to the Xen "half-updated page-table entry" bug class (a multi-field record that becomes durably visible in a partially-updated state due to non-atomic commit ordering across two storage layers) is the AA trigger execution's split commit between RocksDB/LevelDB (`kvstore`) and the SQL database in `aa_composer.js`.

### Title
AA trigger execution state can become permanently half-updated across the kvstore/SQL storage split, allowing state-var double-application and fund/balance divergence on restart - (File: aa_composer.js)

### Summary
`handlePrimaryAATrigger()` in `aa_composer.js` commits an AA trigger's effects to two separate storage engines in the wrong durability order: it durably syncs the `kvstore` batch (containing the AA's updated state variables) *before* committing the SQL transaction that deletes the `aa_triggers` queue row and updates `aa_balances`/`units`/`aa_responses`. If the process is interrupted between these two operations, the record of "has this trigger been executed" becomes half-updated: one storage layer reflects the new state, the other reflects the old state.

### Finding Description
In `handlePrimaryAATrigger()` [1](#0-0) , the sequence is:
1. `handleTrigger()` executes the AA formula, producing new `stateVars` and consumed/created balances, all queued into `batch` (kvstore) and `arrQueries` (SQL), inside a SQL `BEGIN` transaction opened at the top of the function [2](#0-1) .
2. On completion, the code deletes the just-processed row from the `aa_triggers` queue table and updates `units.count_aa_responses` — both still inside the *uncommitted* SQL transaction [3](#0-2) .
3. Only afterward does it call `batch.write({ sync: true }, ...)`, which durably persists the AA's updated state variables (`st\n<address>\n<var>` keys) to the kvstore [4](#0-3) .
4. Only *after* that durable kvstore write succeeds does it call `conn.query("COMMIT", ...)` to make the SQL changes (balance updates, `aa_triggers` deletion, response/unit records) durable [5](#0-4) .

The `aa_triggers` table is explicitly documented as a durable work queue: "the table is a queue... any entries are short-lived... INSERTs are wrapped in the same SQL transactions that write the triggering units" [6](#0-5) . On every node startup, any leftover queue rows are automatically reprocessed: `await aa_composer.handleAATriggers(); // in case anything's left from the previous run` [7](#0-6) , and `handleAATriggers()` simply re-invokes `handlePrimaryAATrigger()` for every row still present in `aa_triggers` [8](#0-7) .

Because the kvstore `sync: true` write is durable and irreversible before the SQL `COMMIT` occurs, a process interruption (crash, OOM kill, power loss, forced restart) in the window between step 3 and step 4 leaves the two storage engines inconsistent: the kvstore already contains the AA's *new* state variables, while the SQL transaction (which contains the `aa_triggers` row deletion, the `aa_balances` deltas, and the new `units`/`aa_responses` rows) is rolled back on restart because it was never committed. The queue row still exists, so `handleAATriggers()` reprocesses the same trigger from scratch: it reads the AA's state variables from the kvstore — which already reflect the previous (uncommitted-in-SQL) execution — and reapplies the AA's formula logic on top of them a second time (e.g., `var['count'] += 1`), while the SQL-side balance changes that were rolled back are recomputed correctly this time. This produces a state-variable set that reflects two applications of the trigger logic while balances/units reflect only one, an internally inconsistent ("half-updated") AA state that other honest nodes (which processed the trigger only once) will not agree with. The identical ordering bug — durable kvstore sync then SQL COMMIT — also occurs in `main_chain.js`'s `stabilizeMci()` [9](#0-8)  and in the additional-stabilization path of `writer.js` [10](#0-9) .

### Impact Explanation
A node experiencing an interruption at the vulnerable moment will, upon restart, compute AA state variables that double-count the effects of one trigger execution while its balance/ledger tables reflect only a single execution. Because AA execution must be fully deterministic for all full nodes to agree on the resulting response units and balances, this divergence causes the affected node's local AA state (and therefore future AA responses computed from that state) to disagree with the rest of the network — a form of node disagreement on validity/stability for the AA's derived state, and it can cause the affected node to compute incorrect balances (fund loss or apparent inflation from that node's local point of view), since `checkBalances()` explicitly asserts that `aa_balances` must always match the sum of live UTXOs [11](#0-10)  — an invariant this scenario can violate.

### Likelihood Explanation
Triggering requires the storage engine (kvstore) to durably persist while the paired SQL transaction is still open, and then an external process interruption to occur precisely inside that narrow window — this is not directly controllable by a remote unit poster or AA trigger sender, only by process-level interruption/crash timing, similar to how the original Xen XSA-347 bug required a specific hypervisor-side race to manifest. This weakens direct attacker-controlled exploitability considerably compared to the Xen case, where a malicious guest could actively race the update.

### Recommendation
Reverse the commit order so the least reversible operation happens last: commit the SQL transaction (including the `aa_triggers` deletion) before performing the durable `kvstore` batch write, or merge both into a single write-ahead-log-protected step so that after a restart either both the SQL changes and the kvstore state are visible, or neither are. Additionally, consider making `aa_triggers` processing idempotent (e.g. checking `aa_responses` for an existing response for the exact trigger unit/AA pair before re-executing) to tolerate reprocessing safely regardless of ordering.

### Proof of Concept
Not directly demonstrable through static analysis alone because it requires inducing a real process interruption at the precise moment between `batch.write()`'s durable completion and `conn.query("COMMIT")` in `handlePrimaryAATrigger()` [12](#0-11) ; a full reproduction would require running a real node, sending an AA trigger unit, and killing the process (e.g., `SIGKILL`) immediately after the "AA batch write took...ms" log line but before "COMMIT" completes, then restarting the node and observing (via `checkBalances()` or direct inspection of `aa_balances` vs. kvstore state variables) that the AA's state variables reflect two applications of the trigger's `state` formula while its balance table reflects only one.

function handlePrimaryAATrigger(mci, unit, address, arrDefinition, arrPostedUnits, onDone) {
	db.takeConnectionFromPool(function (conn) {
		conn.query("BEGIN", function () {
			var batch = kvstore.batch();
			readMcUnit(conn, mci, function (objMcUnit) {
				readUnit(conn, unit, function (objUnit) {
					var arrResponses = [];
					var trigger = getTrigger(objUnit, address);
					trigger.initial_address = trigger.address;
					trigger.initial_unit = trigger.unit;
					handleTrigger(conn, batch, trigger, {}, {}, arrDefinition, address, mci, objMcUnit, false, arrResponses, function(){
						conn.query("DELETE FROM aa_triggers WHERE mci=? AND unit=? AND address=?", [mci, unit, address], async function(){
							await conn.query("UPDATE units SET count_aa_responses=IFNULL(count_aa_responses, 0)+? WHERE unit=?", [arrResponses.length, unit]);
							let objUnitProps = storage.assocStableUnits[unit];
							if (!objUnitProps)
								throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
							if (!objUnitProps.count_aa_responses)
								objUnitProps.count_aa_responses = 0;
							objUnitProps.count_aa_responses += arrResponses.length;
							var batch_start_time = Date.now();
							batch.write({ sync: true }, function(err){
								console.log("AA batch write took "+(Date.now()-batch_start_time)+'ms');
								if (err)
									throw Error("AA composer: batch write failed: "+err);
								conn.query("COMMIT", function () {
									conn.release();
									if (arrResponses.length > 1) {
										// copy updatedStateVars to all responses
										if (arrResponses[0].updatedStateVars)
											for (var i = 1; i < arrResponses.length; i++)
												arrResponses[i].updatedStateVars = arrResponses[0].updatedStateVars;
										// merge all changes of balances if the same AA was called more than once
										let assocBalances = {};
										for (let { aa_address, balances } of arrResponses)
											assocBalances[aa_address] = balances; // overwrite if repeated
										for (let r of arrResponses) {
											r.balances = assocBalances[r.aa_address];
											r.allBalances = assocBalances;
										}
									}
									else
										arrResponses[0].allBalances = { [address]: arrResponses[0].balances };
									arrResponses.forEach(function (objAAResponse) {
										if (objAAResponse.objResponseUnit)
											arrPostedUnits.push(objAAResponse.objResponseUnit);
										eventBus.emit('aa_response', objAAResponse);
										eventBus.emit('aa_response_to_unit-'+objAAResponse.trigger_unit, objAAResponse);
										eventBus.emit('aa_response_to_address-'+objAAResponse.trigger_address, objAAResponse);
										eventBus.emit('aa_response_from_aa-'+objAAResponse.aa_address, objAAResponse);
									});
									onDone();
								});
							});
						});
					});
				});
			});
		});
	});
}
