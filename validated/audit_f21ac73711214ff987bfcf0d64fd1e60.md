### Title
Webhook cross-organization stack write via mismatched authentication and lookup fields - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook using the `webhook_secret` bound to the organization named in `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload (`Handler#stacks`, used by `PushHandler`, `StatusHandler`, etc.) resolve the target `Repository`/`Stack` using an entirely different field: `repository.full_name`. Because the HMAC covers the raw JSON body and is *valid for these values as sent by the party who owns that org's `webhook_secret`*, an attacker who legitimately controls the GitHub App/webhook secret of their own organization can forge a self-signed payload whose `repository.owner.login` matches their own org (so `verify_signature` succeeds using a secret they know), while `repository.full_name` names a different organization's/repo's stack. Since the two fields are never checked for consistency, the org that authenticates the request is not equal to the org whose stack is written to.

### Finding Description
`verify_signature` derives the organization used for HMAC verification from the payload itself: [1](#0-0) [2](#0-1) 

This organization (`repository_owner`) is looked up via `Shipit.github(organization: repository_owner)` to fetch that org's configured `webhook_secret`, and the request's `X-Hub-Signature` is checked against it in `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Shipit supports multiple, independently-configured GitHub Apps/organizations sharing one engine instance (evidenced by the `secrets_double_github_app.yml` fixture and per-organization `webhook_secret` config), so different organizations legitimately possess different secrets.

Once the signature check passes, `WebhooksController#create` dispatches the *entire, unvalidated* JSON body to the event handler: [4](#0-3) 

Handlers such as `PushHandler` resolve which `Stack`s to act on via `Handler#stacks`, which reads a **different** field of the same payload — `repository.full_name` — with no cross-check against the field used for authentication (`repository.owner.login`): [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up any repository/owner pair in the database, with no scoping back to the organization that was authenticated: [7](#0-6) 

This exactly mirrors the reported bug class: a value that gates the protection (`repository.owner.login`, analogous to `maxFeePct`) is decoupled from the value that determines the actual effect (`repository.full_name`, analogous to the real claimed/boosted amount) — the binding "organization that authenticated == repository that is written" is never enforced.

### Impact Explanation
An attacker who legitimately controls one organization's GitHub App configuration (and therefore knows that org's `webhook_secret`) can construct a JSON payload where:
- `repository.owner.login` = their own org (so `verify_signature` validates the HMAC using a secret they possess), and
- `repository.full_name` = `"victim-org/victim-repo"` (an unrelated organization's stack tracked by this Shipit instance).

Because `PushHandler` (and `StatusHandler`, `CheckSuiteHandler`, etc.) act purely on `full_name`/`sha` fields independent of the authenticated org, this lets the attacker inject a forged `push`/`status`/`check_suite` event for a stack they do not own and never authenticated for, causing `stack.sync_github(expected_head_sha: ...)` to run for an attacker-chosen `after` SHA, or fabricate commit statuses/check-suite state for arbitrary commits in another org's stack. This is a cross-repository write: state belonging to one organization's stack is mutated using credentials scoped to a different organization, satisfying the High/Critical "cross-repository writes" impact bar.

### Likelihood Explanation
Requires only network access to the public webhook endpoint plus a legitimately-issued `webhook_secret` for *any one* organization configured in the multi-tenant Shipit deployment — no repository write access, no `ApiClient` token, and no privileged Shipit account is needed. Any organization able to install/configure its own GitHub App against this Shipit instance can mount the attack against any other tracked stack.

### Recommendation
Bind the identity used for signature verification to the identity used for the write. Concretely, in `Handler#stacks` (and any other handler resolving repositories from payload data), verify that the organization derived from `repository.full_name`'s owner matches the organization that was actually used to validate the webhook signature (i.e., thread the verified `repository_owner` through to the handler and assert `full_name.split('/').first == verified_owner`), rejecting the event otherwise.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as supported per `test/dummy/config/secrets_double_github_app.yml`), and a tracked stack for `victim-org/victim-repo`.
2. As an operator/holder of `attacker-org`'s webhook secret, craft a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s `webhook_secret` over the raw JSON body, as done in `Hook::DeliverySigner`/`GitHubApp#verify_webhook_signature`.
4. POST to `/webhooks` with `X-Github-Event: push` and the computed signature. `verify_signature` succeeds (it only checks the org named in `repository.owner.login`), then `PushHandler#process` resolves stacks via `repository.full_name` = `victim-org/victim-repo` and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s stack — a write triggered without ever authenticating as `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
