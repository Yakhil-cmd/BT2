### Title
Webhook signature is verified against the organization derived from the payload while downstream handlers act on an unrelated repository field, allowing cross-repository CI status/event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to verify the HMAC signature with by reading `repository.owner.login` (or `organization.login`) out of the **same untrusted payload** it is trying to authenticate. Once the signature check passes, every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, and in particular `StatusHandler`) trusts *other* fields of that same payload — `repository.full_name`, or for status events nothing at all — to decide which `Stack`/`Commit` to act on. Because Shipit supports multiple organizations each with their own `webhook_secret` (see `config/secrets.development.shopify.yml` and `docs/setup.md`), an attacker who legitimately controls a GitHub App/webhook secret for **their own** organization can craft a payload whose `owner.login` points at their own org (so the signature check passes with a secret they know) while other fields (`repository.full_name`, or a target commit `sha`) reference a completely different, victim-owned repository/stack tracked by the same Shipit instance.

### Finding Description
- `verify_signature` computes the trusted organization purely from payload content:
```ruby
# app/controllers/shipit/webhooks_controller.rb
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

- The HMAC check itself (`GitHubApp#verify_webhook_signature`) only proves the request was signed by *some* org's `webhook_secret` that Shipit knows — it does not bind that org to the specific repository the rest of the pipeline will act on:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [2](#0-1) 

- Handlers then resolve the *target* repository/stack from a different field of the same body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

- `StatusHandler` doesn't even scope by repository at all — it matches purely by commit `sha` across the entire Shipit database:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

The binding that is violated is: **the organization that authenticated the signature (`repository.owner.login`) ≠ the repository/commit that is actually written (`repository.full_name` / `sha`)**. The signature only proves "the sender knows organization A's webhook secret"; it proves nothing about which repository's data is being asserted in the rest of the JSON body, yet Shipit's handlers use unrelated fields of that same body to pick the target `Stack`/`Commit`.

### Impact Explanation
An attacker who is an admin of, or has compromised, a GitHub App/webhook installation for *any* organization tracked by this Shipit instance (a low-privilege, expected-to-be-untrusted-relative-to-other-orgs actor) can forge a `status` (or `push`, `membership`, etc.) webhook whose `owner.login` matches their own org (satisfying signature verification) but whose commit `sha` matches a commit belonging to a **different** organization's/repository's stack. Via `StatusHandler`/`Commit#create_status_from_github!`, this lets the attacker inject an arbitrary CI status (e.g. `success`) for a victim's commit, which feeds directly into `Commit#deployable?` and `stack.schedule_merges`, i.e. it can flip a commit into a "green"/mergeable/deployable state through Shipit's own automation (`schedule_continuous_delivery`, merge queue). That is an unauthorized-deploy/merge primitive achieved purely by an authentication binding that checks the wrong field, matching the report's underlying bug class (a field that is trusted/acted upon but not actually covered by what the signature verification is supposed to guarantee).

### Likelihood Explanation
Requires the attacker to control (or have compromised) at least one organization's webhook secret already configured in this multi-tenant Shipit instance — this is a real, documented deployment mode (`docs/setup.md`, `config/secrets.development.shopify.yml` show multiple orgs configured with independent `webhook_secret`s). No GitHub repository write access or Shipit account is needed for the victim org; only a signature that verifies against *any* configured org's secret. This is realistic for any Shipit deployment shared across multiple orgs/teams with differing trust levels.

### Recommendation
Bind the field used to select/verify the signing secret to the same field(s) used by handlers to determine the target repository/stack. Concretely: after verifying the signature, re-derive `repository_owner`/org strictly from `repository.full_name` (splitting `owner/repo`) rather than from a separate `owner.login`/`organization.login` field, or verify that `repository.owner.login` and the owner segment of `repository.full_name` are identical before dispatching to handlers. For `status`-event handling, scope the `Commit.where(sha: ...)` lookup by the stack(s) belonging to the authenticated repository, not by a global sha search.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org config).
2. Attacker is an admin of `attacker-org`'s GitHub App and thus knows its `webhook_secret`.
3. Attacker finds a commit `sha` belonging to a stack under `victim-org/victim-repo` (commit shas are often discoverable, e.g. via public commit history or the Shipit UI itself).
4. Attacker POSTs to `/github/webhooks` with `X-Github-Event: status`, a body such as:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/decoy"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
5. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature against the attacker-controlled secret [5](#0-4) .
7. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of which org authenticated the request — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto the victim's commit [4](#0-3) [6](#0-5) .
8. This forged status can make the victim commit `deployable?` and trigger `schedule_merges`/continuous delivery on the victim stack [7](#0-6) [8](#0-7) .
