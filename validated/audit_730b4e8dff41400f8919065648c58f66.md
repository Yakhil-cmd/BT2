### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but the sync action trusts a different, unchecked `repository.full_name` field, allowing cross-organization stack sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a GitHub webhook using the organization name taken from the JSON body (`repository.owner.login` / `organization.login`), while the handler that performs the actual action (`PushHandler`, via `Handler#repository_name`) resolves the target `Repository`/`Stack` using a *different* field of the same body: `repository.full_name`. Nothing enforces that these two values refer to the same organization, so an attacker who legitimately controls the webhook secret for one configured GitHub organization can forge a payload whose `full_name` points at a stack belonging to a completely different organization.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml:1-23`, where each org gets an independent `webhook_secret`), the signature check is: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the attacker-controlled JSON body and is used only to select *which* app/secret to check the signature against: [3](#0-2) [4](#0-3) 

Once the signature validates for that org's secret, the payload is dispatched to handlers, e.g. `PushHandler`, which resolves the target stack from a *different* field of the same body — `repository.full_name` — with no cross-check against `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) 

This is structurally the same class of bug as CL-2020-11: a verification step covers one representation of "identity" (the org whose secret matched), while a downstream trust decision (which repository/stack gets acted upon) is made using an independent field that was never checked for consistency with the verified identity. The equality that should hold but is never enforced is:

`organization authenticated by verify_signature (repository.owner.login) == organization implied by repository.full_name used by Handler#stacks`

Because both fields live in the same attacker-supplied JSON body and the attacker who owns a legitimate `webhook_secret` for *their own* org fully controls that body's bytes, they can set `repository.owner.login` to their own org (so the correct secret is selected and the HMAC they compute with their own secret validates) while setting `repository.full_name` to `"<victim-org>/<victim-repo>"`. `GitHubApp#verify_webhook_signature` (lib/shipit/github_app.rb:76-83) only checks the raw body against the secret of the org named in `repository.owner.login` — it has no knowledge of, and does not care about, `full_name`.

### Impact Explanation
A successful forgery lets an attacker who administers (or otherwise knows the webhook secret of) any one configured GitHub organization on a shared, multi-org Shipit instance trigger `GithubSyncJob` (via `PushHandler#process` → `stack.sync_github`) for stacks belonging to an unrelated organization/repository they have no access to. This is a cross-repository, cross-organization write/trigger primitive against Shipit's internal state (syncing commits, marking accessibility, potentially advancing what commits are treated as deployable), which corresponds to the "cross-repository writes" / "unauthorized deploy" category of impact.

### Likelihood Explanation
Exploitability depends on the instance being configured for multiple GitHub organizations (a documented, supported configuration) and on the attacker possessing a valid `webhook_secret` for at least one of them — a credential scoped to their own org, not a privileged Shipit account or `GITHUB_TOKEN`. This still qualifies as an "unprivileged attacker" relative to the victim organization/repository whose stack gets synced, since no credential belonging to the victim org is required.

### Recommendation
When resolving the handler target, verify that the organization embedded in `repository.full_name` (or `repository.owner.login`) used to select the webhook secret matches the organization actually referenced by the repository being acted upon, before dispatching to handlers — e.g., have `Handler#repository_name` cross-check `payload.dig('repository', 'owner', 'login')` against the leading segment of `full_name`, and reject/short-circuit on mismatch in `WebhooksController`.

### Proof of Concept
1. Instance configured with two orgs, each with its own `webhook_secret`: `org-a` (`secret-a`) and `org-b` (`secret-b`), per the `github:` multi-org schema in `config/secrets.development.shopify.yml`.
2. Attacker administers `org-b`'s GitHub App and therefore knows `secret-b`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-b" },
    "full_name": "org-a/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(secret-b, body)` themselves and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-b")`, whose `verify_webhook_signature` recomputes the same HMAC with `secret-b` and succeeds (`lib/shipit/github_app.rb:76-83`).
6. `PushHandler#process` resolves `Repository.from_github_repo_name("org-a/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, `app/models/shipit/repository.rb:53-56`) and enqueues `GithubSyncJob` for `org-a`'s stacks, even though the attacker never had `secret-a` and has no legitimate relationship to `org-a`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
