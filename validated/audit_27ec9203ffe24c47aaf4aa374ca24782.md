## Analysis

The Sherlock finding is a rounding-to-zero bug class: when `creditChange = (paperChange * creditAmount) / paperAmount` truncates to `0`, the seller's paper is consumed but no credit is paid out, because the protocol code that computes the transfer never checks that a non-zero input produces a non-zero output.

An ocore analog of this exact bug class exists in the Autonomous Agent (AA) response-composition pipeline.

### Root cause

AA formulas commonly compute payout amounts using division followed by `round()`/`floor()` (e.g. `share = amount_received / outstanding_shares`, then `payout = round(share * balance)`), as documented in the reference AA templates [1](#0-0)  and [2](#0-1) . The `round`/`floor`/`ceil` opcodes are evaluated with standard decimal truncation semantics in the formula engine [3](#0-2) , so any sufficiently small numerator relative to the denominator legitimately evaluates to `0`.

The AA response composer (`aa_composer.js`) treats a computed `0` payment output not as an error but as something to be silently dropped: [4](#0-3) 

Specifically:
- `payload.outputs = payload.outputs.filter(...output.amount > 0...)` removes any output whose amount rounded to `0`.
- If that was the only output in the message, the whole `payment` message is removed.
- If **all** messages end up empty, the AA doesn't bounce — it silently produces a `handleSuccessfulEmptyResponseUnit`, meaning the trigger unit is treated as successful.

Because in the AA balance model the trigger's `bytes`/asset outputs are absorbed into the AA's balance the moment the trigger unit is processed (independent of what the AA's response does), a trigger sender who is entitled to a payout that rounds down to `0` loses the funds/asset they sent to the AA and receives nothing back — the AA keeps the deposit, and no bounce/refund occurs. This is the same root cause as the JOJO bug: a rounding-to-zero division on a legitimate, non-zero input amount silently destroys value for the depositor instead of reverting.

### Title
Silent 0-output filtering in AA response composer lets rounding-to-zero payout formulas cause fund loss for AA trigger senders - (File: `aa_composer.js`)

### Summary
When an AA's payout formula (a common `amount = round(share * balance)` / division-based pattern, natively supported by oscript's `round`/`floor`/`ceil`) evaluates to `0` for a legitimately-sized deposit, `aa_composer.js` filters the zero-amount output out of the payment message rather than treating it as an error. If this empties all messages, the trigger unit still completes successfully (`handleSuccessfulEmptyResponseUnit`) instead of bouncing. The trigger sender's deposited bytes/asset are already absorbed into the AA balance, so the sender loses the deposited value and gets nothing in return.

### Finding Description
`aa_composer.js` lines 1274-1286 filter out any payment output whose formula-computed `amount` rounds to `0`, and drop empty payment messages, continuing execution ("no messages after removing 0-outputs" is not a bounce condition but a success path). Formulas in AAs frequently divide a triggered amount by an outstanding-shares or price denominator and `round()`/`floor()` the result (see `divest MM shares`/`exchange` cases and `order_book_exchange` cases in the reference oscript templates) [5](#0-4) . For small-enough trigger amounts relative to the pool/denominator, the computed payout is exactly `0`, which is dropped instead of causing a bounce/refund. Since the AA already received and retains the trigger's deposit as part of its balance, the sender permanently loses the deposited value with no compensating output and no bounce.

### Impact Explanation
An AA trigger sender loses funds (bytes or asset) sent to any AA whose response logic uses a division/rounding payout formula, whenever the computed payout underflows to `0`. This is a genuine, unauthorized-style fund loss for the depositor and a fund-retention "gain" for the AA (or its other participants), matching the "Medium" severity class of the reference finding (participant loses funds due to unhandled rounding-to-zero).

### Likelihood Explanation
This is trivially reachable by any unprivileged AA trigger sender: they simply need to send a deposit small enough (or interact with an AA whose outstanding/price ratio is large enough) that `round(share * balance)` computes to `0`. No special privileges, timing, or AA author collusion are required — an adversary could also intentionally shrink another party's expected payout via prior triggers to make a subsequent, otherwise-fair-sized trigger round down to `0`.

### Recommendation
In `aa_composer.js`, when a payment message's outputs are filtered to `0` and this changes the AA's intended behavior (i.e., the pre-filter output count was non-zero, meaning the AA computed a non-zero-then-zero-rounded payout), the AA should bounce rather than silently succeed, or the filtering rule should not treat computed-`0` outputs as "okay to drop" when derived from a formula rather than being explicitly and intentionally `0`. At minimum, document this behavior prominently and provide/require an explicit zero-check pattern (`if (amount == 0) bounce(...)`) in the standard AA templates so authors don't ship this footgun, and consider making empty-messages-after-filtering a bounce condition instead of a successful empty response when the trigger carried a non-trivial deposit.

### Proof of Concept
1. Deploy an AA implementing a share-based payout formula such as the `divest MM shares` case: `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']; amount = round($investor_share * balance[$asset])`.
2. Grow `var['mm_asset_outstanding']` large (via normal use) so that a small `$mm_asset_amount` deposit yields `$investor_share` small enough that `round($investor_share * balance[$asset])` evaluates to `0` for both the asset and base outputs.
3. Trigger the AA with that small `mm_asset` deposit.
4. In `aa_composer.js`, both payment outputs are filtered to `0` and removed; the payment messages become empty and are removed; all messages are now empty, causing `handleSuccessfulEmptyResponseUnit` — the trigger succeeds with no bounce and no refund. The sender's `mm_asset` deposit is retained by the AA/other holders permanently, with the sender receiving nothing back.
