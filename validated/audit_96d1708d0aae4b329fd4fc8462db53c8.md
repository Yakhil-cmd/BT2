### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while every event handler targets a stack by `repository.full_name` - cross-organization webhook forgery causes unauthorized syncs/deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
### Finding Description
The reported bug class is a discrepancy between the field a security check is computed over and the field the code actually acts on, letting an attacker satisfy the check while steering the effect elsewhere. In this engine that exact class of bug exists in webhook processing.

`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`): [1](#0-0) 

Every event handler, however, resolves the target `Stack`/`Repository` using an entirely different field of the same payload: `payload.dig('repository', 'full_name')`, via `Handler#stacks` / `Handler#repository_name`: [2](#0-1) 

and `Repository.from_github_repo_name` simply splits that string into owner/name and looks up the matching `Repository` row, independent of who signed the request: [3](#0-2) 

The binding that should hold is:
`organization whose secret authenticated the request (repository.owner.login)` == `organization whose repository/stack the handler mutates (repository.full_name)`

Because the signature only covers "was this HMAC produced with *some* configured org's secret," and the org used to pick that secret (`repository.owner.login`) is a payload field distinct from the field used to pick the acted-upon repository (`repository.full_name`), an operator of one legitimately configured organization ("OrgA", whose `webhook_secret` in `secrets.yml`/GitHub App config they know because they administer OrgA's webhook) can construct a raw JSON body where:
- `repository.owner.login` = `"orga"` (so `verify_signature` looks up and validates against OrgA's known secret), and
- `repository.full_name` = `"orgb/private-repo"` (an entirely different, unrelated organization/repository hosted on the same Shipit instance).

They sign this crafted body with OrgA's HMAC secret and POST it to `/webhooks`. `verify_signature` succeeds because it only checks the signature against the org named in `owner.login`, which the attacker fully controls and matches to their own known secret. The handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`) then runs the real handler against whatever repository `full_name` claims — OrgB's stacks — not OrgA's: [4](#0-3) 

For the `push` event this reaches `PushHandler#process`, which calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack matching the forged `full_name`/branch, entirely under attacker control of `after` and `ref`: [5](#0-4) 

`sync_github` operates using the target repository's own GitHub App credentials (`Repository#github_app` derives the app from the matched repository's `owner`, not from whoever authenticated the webhook): [6](#0-5) 

If the targeted stack has continuous deployment enabled, a forged sync can drive an unauthorized deploy/rollback trigger on a stack the attacker has no legitimate relationship to, using OrgB's own GitHub token — a cross-organization/cross-repository state change triggered purely by knowledge of a webhook secret belonging to a different, unrelated organization.

### Impact Explanation
This breaks the trust binding between "which organization's credential authenticated the webhook" and "which organization's repository/stack is mutated." It allows a party who administers/controls only one configured GitHub App/organization on a shared Shipit instance to force webhook-driven side effects (repository sync, potential continuous-deploy triggers, check-run refreshes, review-stack provisioning/deprovisioning, membership changes depending on handler) against a completely different organization's stacks, using that other organization's own GitHub credentials to execute the resulting actions. This matches the Critical bucket of "unauthorized deploy/rollback" and cross-repository writes.

### Likelihood Explanation
Medium-to-High on any Shipit deployment that hosts more than one GitHub organization/App (multiple `github:` entries with distinct `webhook_secret`s, as `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` demonstrate is a supported configuration). Any actor who is an admin of one of those configured organizations (i.e., knows/controls its Shipit webhook secret) can perform this without needing any Shipit session, API token, or GitHub access to the victim organization at all — only crafting an HTTP POST with a valid HMAC for their own org's secret and a different `full_name`.

### Recommendation
In `verify_signature` (or the handlers), enforce that the organization whose secret verified the signature is the same organization implied by `repository.full_name` (i.e., compare `repository.owner.login` to the owner segment of `repository.full_name`, and reject if they differ). Alternatively, have `Handler#repository_name`/`Handler#stacks` be scoped by the already-verified organization rather than trusting `full_name` unconditionally.

### Proof of Concept
1. Shipit is configured with two organizations, `orga` and `orgb`, each with its own `webhook_secret` (as supported by `config/secrets.development.shopify.yml`).
2. Attacker administers `orga`'s webhook secret (legitimately, as the operator of that org's integration).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-or-real-sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/private-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orga_webhook_secret, body)>` and sends `POST /webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` as `"orga"`, fetches `Shipit.github(organization: "orga")`, and the signature validates successfully. [7](#0-6) 
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgb/private-repo")` and calls `sync_github` on `orgb`'s stack(s), despite the request never being authenticated by anything belonging to `orgb`. [5](#0-4)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end

    def repository_owner

      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
