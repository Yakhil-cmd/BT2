### Title
System-parameter governance votes are weighted by current spot balance instead of a balance snapshot, enabling flash-stake takeover of `op_list`/fee/threshold votes - (File: main_chain.js)

### Summary
The `system_vote` message lets any address cast a permanent vote for `op_list` (the witness/order-provider set), `threshold_size`, `base_tps_fee`, `tps_interval` or `tps_fee_multiplier`. `countVotes()` in `main_chain.js` re-computes each voter's weight from the address's *current* unspent stable balance every time a vote count runs, rather than from a balance snapshot taken when the vote was cast [1](#0-0) . This is the same missing-snapshot defect described in the external report: voting power is derived from mutable, present-tense state instead of being fixed at the moment the vote was made, so any later change in balance retroactively re-weights a stale vote.

### Finding Description
`system_vote` is validated as an ordinary inline message that any single unprivileged unit author can post, is limited to one per unit, and is stored indefinitely in `system_votes`/`op_votes`/`numerical_votes` until overridden by the same address [2](#0-1) . The schema comment for `system_vars` itself documents the intended (but risky) behavior: "All votes and balance updates up to and including this MCI are taken into account, even if they happen after system_vote_count on its MCI" [3](#0-2) .

When a vote count is triggered (`countVotes`), the code queries `SUM(outputs.amount)` for each voting address using the current set of unspent, stable, good outputs at count time [4](#0-3) , then joins that spot balance against whatever vote each address most recently cast (potentially long ago, and cast with a trivial balance) [5](#0-4) [6](#0-5) . There is no mechanism that records "the balance the address had when it voted" — the vote (choice) and the weight (balance) are decoupled in time, exactly the "missing snapshot" defect in the report: an address can cast a vote while poor, and have that same, unmodified vote later inherit arbitrarily large weight simply because the address temporarily holds a large stable balance at the instant a later MCI stabilizes and `countVotes` runs.

Because the balance requirement is "current holdings," not "locked/held-for-duration" stake, an attacker does not need any special privilege: they can (1) create/control an address, (2) post one `system_vote` unit for a favorable `op_list`/`threshold_size`/`base_tps_fee`/`tps_fee_multiplier` value while the address is empty, (3) at any later point move a large stable balance into that same address for just long enough for one MCI to stabilize, letting `countVotes` pick up the inflated `voter_balances` weight for the old vote, and (4) move the funds back out immediately afterward. The stale vote's *choice* never has to be re-affirmed at the time the stake is held — the snapshot of "who agreed to what, backed by how much, for how long" is never taken.

### Impact Explanation
`system_vars` produced by `countVotes` directly control consensus-relevant parameters: the 12-member `op_list` (order providers/witnesses used for MC stability) and TPS-fee economics (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) [7](#0-6) . Since the balance used to weight a vote can be pumped up momentarily (a "flash stake") without the underlying capital needing to be committed for any real duration or reflecting the original voter's actual, deliberate governance intent at that stake size, an attacker with temporary access to a large stable balance (their own funds moved in and out, or capital borrowed for a short period) can swing the result of `countVotes` for any of these subjects. Replacing legitimate order providers with colluding/malicious ones, or setting disruptive fee/tps parameters, can degrade the network's ability to reach consensus on stability or to confirm new units economically — i.e., a network-wide, protocol-level governance takeover rather than a localized loss.

### Likelihood Explanation
`countVotes` runs automatically on every MCI stabilization for any subject with a pending `system_vote_count` [8](#0-7) , so an attacker only needs to time a large, temporarily-held balance to be stable at the moment a count executes; because `since_timestamp` scans up to years back for eligible past votes [9](#0-8) , a single cheap vote cast long ago (from a nearly-empty address) remains eligible to be re-weighted at any future count. This requires no cooperation from the original voter, no bug in signature/authentication, and no privileged role — only capital access at the right instant, making it realistically reachable by an ordinary unit poster/asset holder.

### Recommendation
Record and use a balance snapshot taken at (or shortly before) the time each `system_vote` unit becomes stable, rather than re-reading the voter's live balance at every subsequent count. Store the voting weight alongside the `unit`/`timestamp` in `system_votes` at insertion time (`saveSystemVote`) and have `countVotes` sum the stored, historical weights instead of `SUM(outputs.amount)` computed against current unspent outputs. Optionally require the balance to have been held continuously (or for a minimum duration) prior to voting to prevent flash-funding.

### Proof of Concept
1. Attacker controls address `A` with a near-zero balance.
2. `A` posts a `system_vote` unit (subject = `op_list`, value = attacker-favored witness set) — accepted because validation only checks message structure, not balance [10](#0-9) .
3. The vote is recorded in `system_votes`/`op_votes` with `timestamp` of that unit [11](#0-10) .
4. Weeks/months later, attacker moves a large stable balance into `A` for the duration of a single MC stabilization event, then withdraws it.
5. The next `system_vote_count` for `op_list` runs `countVotes`, which recomputes `A`'s balance from current `outputs`/`units` at that moment [12](#0-11) , awarding `A`'s old, unrevised vote the full inflated weight and potentially tipping `op_rows`/vote aggregation in the attacker's favor [13](#0-12) .

	console.log('countVotes', mci, subject, is_emergency, emergency_count_command_timestamp);
	if (is_emergency && subject !== "op_list")
		throw Error("emergency vote count supported for op_list only, got " + subject);
	const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
	let addresses = address_rows.map(r => r.address);
	const unstable_votes = (is_emergency && mci >= constants.pemCurvesFixMci) ? getUnstableVotes(emergency_count_command_timestamp) : null;
	if (unstable_votes) {
		for (let { author_addresses } of unstable_votes) {
			for (let address of author_addresses)
				addresses.push(address);
		}
		addresses = _.uniq(addresses);
	}
	const strAddresses = addresses.map(db.escape).join(', ');
	let balances = {};
	// Count all stable-good outputs that have no stable-good spender.
	// This correctly handles outputs whose only spending unit was propagated to final-bad
	// (leaving is_spent=1 in the DB while no good unit claims the output), which the
	// previous two-query approach (bal_rows + spent_rows) silently undercounted.
	const bal_rows = await conn.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);
	console.log('bal rows', bal_rows)
	for (let { address, balance } of bal_rows) {
		balances[address] = balance;
	}
