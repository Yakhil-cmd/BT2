### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read the status of any stack, not just its authorized one - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method used by every other API controller and, in doing so, drops the enforcement that restricts a scoped `ApiClient` token to the single stack it was authorized for.

### Finding Description
Shipit's API authorization model binds an `ApiClient` token to a specific stack via the optional `stack_id` column: [1](#0-0) . The base API controller enforces this binding centrally: `stacks` returns only the client's own stack when `stack_id` is set, and `stack` resolves `params[:stack_id]` against that restricted scope: [2](#0-1) . This is the exact analog of the signed-but-unenforced-field pattern in the report: the token's authorization ("which stack may this token touch") is supposed to gate every stack lookup, just as the bidder's signature was supposed to gate every parameter used by `fulfillDomainBid`.

`CCMenuController`, however, defines its own `stack` method that bypasses this scoping entirely and resolves the stack directly from global `Stack.from_param!`, ignoring `current_api_client.stack_id`: [3](#0-2) 

The permission check performed before the action only validates that the token has the `read:stack` permission *name* via `require_permission :read, :stack` → `current_api_client.check_permissions!(operation, scope)`: [4](#0-3) [5](#0-4) . It never checks *which* stack is being accessed — that check only exists inside the (bypassed) `stacks`/`stack` helper in the base controller.

The binding that should hold is:
`token.stack_id (if present) == params[:stack_id] resolved stack`

After the front-run-style bypass in `CCMenuController#stack`, this becomes:
`token.stack_id (ignored) ≠ params[:stack_id] (attacker-chosen, arbitrary stack)`

This mirrors the report's bug class directly: "a stack a token authorises versus a stack it touches."

The design intent that scoped tokens must be confined to their stack is explicitly tested elsewhere in the codebase for the sibling stacks API: [6](#0-5) , confirming that `CCMenuController`'s bypass is a deviation from the intended authorization model rather than intended behavior.

### Impact Explanation
Any holder of a valid `ApiClient` token — including one deliberately scoped to a single stack for narrow read-only exposure (e.g., a CCMenu client meant to expose only one project's CI status to an external tool) — can use that token to read the deploy/build status (`lastBuildStatus`, `lastBuildLabel`, lock state, activity) of **any** stack in the Shipit instance by simply changing `stack_id` in the request path. This is an unauthorized read of stack state beyond what the token's own scope permits, i.e., escalation past the deployment-trust boundary that `ApiClient#stack_id` is meant to enforce.

### Likelihood Explanation
Exploitation requires possession of any valid API token with `read:stack` permission (even one scoped to just one stack). This is a supported credential grade in Shipit and can be relatively low-privilege/narrow-purpose (e.g. a CCMenu widget token created via `CCMenuUrlController` and embedded in third-party CI dashboards). No further privilege or GitHub credential is needed — the attacker only needs a working `read:stack`-scoped token and the ability to change the `stack_id` path segment, making this straightforward to exploit once such a token is obtained/leaked.

### Recommendation
Remove the overriding `stack` method in `CCMenuController` (or make it delegate through the base controller's scoped `stacks`/`stack` methods) so all API controllers, including CCMenu, resolve `params[:stack_id]` against `current_api_client`'s authorized stack scope rather than against `Stack.from_param!` directly.

### Proof of Concept
1. Obtain (or generate via `CCMenuUrlController#fetch`) an `ApiClient` token scoped to Stack A (`stack_id` set to A's id), with `read:stack` permission.
2. Send: `GET /api/stacks/<STACK_B_ID>/ccmenu.xml?token=<TOKEN_SCOPED_TO_A>` (or via HTTP Basic auth) where Stack B is a different, unrelated stack.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (it is a valid token) and `require_permission :read, :stack` passes because the token has the `read:stack` permission name.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping in `Shipit::Api::BaseController#stacks`), returning Stack B's data instead of rejecting the request, and the response discloses Stack B's build/deploy status — data the token was never authorized to access.
