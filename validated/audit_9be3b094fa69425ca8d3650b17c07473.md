### Title
Webhook signature verified against `repository.owner.login`'s secret while target Stack is resolved from the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on `repository.owner.login` (or `organization.login`) taken from the raw, unauthenticated request body. Once the signature check passes, the actual event handlers (`Handler#stacks`/`PushHandler`, and `StatusHandler`) resolve the target `Stack`/`Repository` using a *different* field of the same attacker-controlled JSON body: `repository.full_name`, or in the `status` event case, nothing more than a bare `sha` lookup across all commits. Because these two values are independently attacker-supplied and nothing enforces that `full_name` is consistent with `owner.login`, an attacker who knows the webhook secret of any one organization/repo onboarded to Shipit can forge signed payloads that act on a completely different (victim) repository's stack.

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == repository/stack the request is allowed to mutate`. This binding is broken.

- `verify_signature` derives the signing organization purely from the payload: [1](#0-0) 
using [2](#0-1) 

- Each `GitHubApp` instance carries its own per-organization `webhook_secret` pulled from that organization's config, and `verify_webhook_signature` just HMACs the raw body against that one secret: [3](#0-2) [4](#0-3) 

- Once the signature is accepted, `create` dispatches the *entire* parsed payload to the event handlers with no further validation: [5](#0-4) 

- The base `Handler` resolves which `Stack`s to act on using `repository.full_name` — a field that was never checked against, or tied to, `repository.owner.login` used for signature selection: [6](#0-5) 

- `PushHandler` then triggers a real sync against the resolved stacks using an attacker-chosen `after` SHA: [7](#0-6) 

- `StatusHandler` is even less scoped: it looks up commits purely by `sha` with no repository/owner check at all and writes a GitHub-originated status directly onto them: [8](#0-7) 

An attacker who legitimately controls any organization/repo that has been onboarded to this Shipit instance (and therefore knows that organization's `webhook_secret`, which is a normal, unprivileged configuration step, not an internal credential) can:
1. Build a webhook body where `repository.owner.login` = their own org (`attacker-org`), but `repository.full_name` = the victim's repo (`victim-org/victim-repo`), and `sha`/`after` point at a victim stack's real commits.
2. Sign the raw body with `attacker-org`'s webhook secret.
3. POST it to `/webhooks`. `verify_signature` looks up `attacker-org`'s `GitHubApp`, verifies successfully, and the request proceeds.
4. `PushHandler`/`StatusHandler` resolve the *victim's* `Stack`/`Commit` via `full_name`/`sha` and mutate its state (`sync_github`, `create_status_from_github!`) — actions the attacker was never authorized to perform on that repository.

### Impact Explanation
This crosses the "organization authenticated versus repository that is written" boundary explicitly called out as in-scope: the secret used to authenticate the request belongs to one repository/organization, but the mutation targets another repository entirely. Concretely, this lets an attacker forge push/status events against a victim stack, causing `Stack#sync_github` to run with an attacker-controlled `expected_head_sha` and letting `create_status_from_github!` fabricate CI statuses for arbitrary commits. On stacks with `continuous_deployment` or CI-gated merge/deploy scheduling enabled, a fabricated "success" status or forced sync can move a victim stack toward scheduling a merge/deploy it should not have made — i.e., cross-repository interference triggering an unauthorized deploy path, without ever holding a Shipit session, `ApiClient` token, or the victim organization's own GitHub credentials.

### Likelihood Explanation
The only precondition is that the attacker controls or has legitimately configured *any* single organization/repository onboarded into the same Shipit instance (a normal, unprivileged, self-service action for many CD platforms), and knows that organization's `webhook_secret` — something they configure themselves. No access to the victim's secrets, GitHub App keys, or Shipit session is required; the vulnerability is purely a payload-field-substitution attack against the webhook endpoint, which is unauthenticated by design (relying solely on HMAC).

### Recommendation
Bind the resolved `Stack`/`Repository` in every handler to the *same* organization/repository whose secret authenticated the request, not to independent fields of the payload. Concretely: derive `repository_name`/`repository_owner` once in the controller, verify the signature against it, and pass that already-authenticated identity down to `Handler#stacks` / `StatusHandler`'s commit lookup instead of re-reading `repository.full_name` or bare `sha` from the untrusted payload. Reject any payload whose `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Attacker configures/owns `attacker-org` in Shipit and knows its `webhook_secret`.
2. Attacker crafts JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Attacker computes `sha1=HMAC-SHA1(webhook_secret_of_attacker_org, raw_body)` and sets it as `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` succeeds using `attacker-org`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
5. `PushHandler#process` resolves stacks via `repository.full_name` = `victim-org/victim-repo` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a mutation the attacker was never authorized to trigger.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
