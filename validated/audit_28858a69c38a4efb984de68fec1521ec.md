### Title
Signed-package primitive (`is_valid_signed_package`) does not bind signatures to an AA/contract context, enabling off-chain signature replay across AA instances - ([File: formula/evaluation.js])

### Summary
The oscript primitive `is_valid_signed_package` (and its underlying support functions `object_hash.getSignedPackageHashToSign` and `signed_message.validateSignedMessage`) only verifies that a `signed_message` payload was signed by a specified address. It places no requirement on the *content* of `signed_message` to include any identifier that binds the signature to a specific AA address, channel, order, or state. Exactly like the ParaSpace `Credit` struct that lacked a `MarketplaceAddress` field, an off-chain signed package here carries no built-in "AA identity" field, so protection against cross-context replay is entirely optional and left to the oscript author.

### Finding Description
`getSignedPackageHashToSign` computes the hash-to-sign purely from whatever fields the caller puts into the package (minus authentifiers): [1](#0-0) 

`validateSignedMessage` verifies the ECDSA signature against `address` and reads/validates `authors`/`definition`, but enforces nothing about the semantic content of `signed_message` beyond structural checks (`hasFieldsExcept`, base64 length, etc.): [2](#0-1) 

In `formula/evaluation.js`, the `is_valid_signed_package` opcode used inside AA oscript simply forwards to `validateSignedMessage` with an address supplied by the AA author and returns true/false — it does not require or check that `signed_message` names the calling AA, a channel id, an order id, or any nonce that ties the signature to *this* particular AA instance: [3](#0-2) 

Because of this, the library's own reference implementation of a payment-channel AA has to manually re-implement context binding by hand-checking `channel` and `period` fields inside the signed payload before trusting the peer's signed balance claim: [4](#0-3) 

If an AA author (or a wallet/dApp built on top of `is_valid_signed_package`, e.g. order-book/exchange contracts using the same primitive, as seen in `test/samples/order_book_exchange.oscript`) omits or gets these binding checks wrong — for instance checking only `address` and reusing the same off-chain signing scheme for multiple AA instances/channels/orders sharing the same two counterparty addresses — a counter-party's signature intended for one context (e.g., a channel with a specific balance state, or an order for a specific asset/price) can be replayed as-is against a different AA instance or a later/different state, because the cryptographic hash never included any context-binding identifier by default. This is structurally identical to the ParaSpace bug: the generic "credit"/"signed package" object is signature-verified without a mandatory field identifying the specific application context (marketplace / AA / channel / order), so the burden of preventing replay across contexts is pushed entirely onto downstream code, which can (and in the wild, likely will) forget it.

### Impact Explanation
If an AA (payment channel, order-book exchange, or any oscript contract relying on `is_valid_signed_package`) fails to independently re-check that the signed package refers to `this_address`/the specific instance/state, a counter-party can present an old or foreign signed package to unlock funds, claim a stale/more favorable balance, or execute a state transition that was never authorized for that specific AA instance — resulting in direct fund loss or theft from the AA's balance. This matches the "AA fund loss" and "unauthorized spending" impact classes.

### Likelihood Explanation
The primitive is generic by design (it must support many different oscript use-cases), so it will not enforce a fixed schema for `signed_message`. Any AA author writing an off-chain-signed-state contract (payment channels, order books, escrow release, etc.) must remember to embed and check a unique context identifier (AA/channel/order id, sequence number, or state hash) themselves — exactly the same omission class that caused the ParaSpace High/Medium finding. The library's own official sample needed hand-rolled checks (`channel`, `period`) to be safe, demonstrating this is a real, easy-to-miss pitfall rather than a purely theoretical one, but it requires an AA author to specifically build such an off-chain-signature-based AA and omit the binding check, so exploitability depends on third-party AA code rather than ocore's own bundled AAs.

### Recommendation
- Document prominently, and ideally enforce in `is_valid_signed_package`/`validateSignedMessage`, that any signed package used for authorizing an AA-mediated fund transfer or state change MUST include and the AA MUST verify a field binding the signature to `this_address` (or another equivalent unique instance/context identifier such as channel-id/order-id) and, where relevant, a state counter/nonce, so that a valid signature cannot be replayed across different AA instances or against stale application state.
- Consider providing a hardened companion opcode (e.g., `is_valid_signed_package_for_this_aa`) that automatically requires and checks `signed_message.aa === this_address` (and, optionally, a caller-supplied sequence/state hash) so that AA authors are not required to remember to add this check manually.

### Proof of Concept
1. Two users A and B use the identical two-address pair to open two independent, structurally identical AA instances (e.g., two separate payment channels or an order book AA reused for two different trading pairs) whose oscript, unlike the official sample, checks only `is_valid_signed_package(trigger.data.sentByPeer, peer_address)` without also verifying `signed_message.channel == this_address` (or equivalent) and a state counter.
2. B, acting honestly, signs an off-chain state package for channel/AA #1 (e.g., `{amount_spent: 100}`).
3. A takes that same signed package (byte-for-byte) and submits it as `trigger.data.sentByPeer` to AA #2 (or replays it later against AA #1 after B has already signed a smaller-amount update), where the AA has no additional binding check.
4. Because `getSignedPackageHashToSign`/`validateSignedMessage` never required any AA/channel-specific field, the signature verifies successfully in the wrong context, and AA #2 releases funds to A based on B's package that was never intended to authorize that transfer.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
