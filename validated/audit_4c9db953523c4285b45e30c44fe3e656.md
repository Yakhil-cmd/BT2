### Title
Bridge KAIA Permanently Locked When Recipient Contract Rejects KLAY in `handleKLAYTransfer` - (File: contracts/service_chain/bridge/BridgeTransferKLAY.sol)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` uses a push pattern to deliver KAIA to the recipient `_to`. If `_to` is a contract that rejects KAIA (no payable fallback or explicit revert), the `require(ok, ...)` guard causes the entire transaction to revert. Because the revert unwinds all state changes, `handleNoncesToBlockNums[_requestedNonce]` is never written, `lowerHandleNonce` is permanently stuck at that nonce, and the KAIA locked in the source bridge can never be delivered. There is no admin escape hatch to skip a stuck nonce.

---

### Finding Description

`handleKLAYTransfer` follows this sequence:

1. Validates the nonce with `_lowerHandleNonceCheck` and collects operator votes via `_voteValueTransfer`.
2. Writes bridge state: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`, `_updateHandleNonce`.
3. Emits `HandleValueTransfer`.
4. **Pushes KAIA** to `_to`:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

If `_to` is a contract with no payable fallback or one that explicitly reverts, `ok` is `false`. The `require` reverts the entire transaction, unwinding **all** state writes including `handleNoncesToBlockNums[_requestedNonce]`.

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive `i` starting from `lowerHandleNonce`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    ...
}
lowerHandleNonce = i;
``` [2](#0-1) 

Because `handleNoncesToBlockNums[N]` is never durably written (every attempt reverts), `lowerHandleNonce` is permanently stuck at `N`. `_lowerHandleNonceCheck` only enforces `lowerHandleNonce <= _requestedNonce`:

```solidity
function _lowerHandleNonceCheck(uint64 _requestedNonce) internal {
    require(lowerHandleNonce <= _requestedNonce, "removed vote");
}
``` [3](#0-2) 

There is no function to skip a nonce, mark it handled without transferring, or refund the source-chain depositor. The `ValueTransferRecovery` mechanism will keep re-submitting the same failing nonce indefinitely.

On the source chain, the user's KAIA was deposited into the source bridge via `_requestKLAYTransfer` / `requestKLAYTransfer`:

```solidity
emit RequestValueTransfer(...);
requestNonce++;
``` [4](#0-3) 

There is no refund path back to the user if the destination-side handle permanently fails.

---

### Impact Explanation

- **Permanent loss of bridged KAIA**: The user's KAIA deposited into the source bridge is irrecoverable. The destination bridge can never deliver it.
- **`lowerHandleNonce` permanently stuck**: `recoveryBlockNumber` never advances past the stuck nonce's block, so the recovery subsystem loops forever over the same block range.
- **`closedValueTransferVotes` memory leak**: Nonces handled after `N` are never cleaned up because `lowerHandleNonce` never advances past `N`.

This matches the allowed impact gate: *unauthorized lock of bridged assets* and *persistent corruption of bridge nonce/state that breaks settlement*.

---

### Likelihood Explanation

Any user can specify an arbitrary address as `_to` in `requestKLAYTransfer`. Contracts without a payable fallback are common (e.g., ERC20 tokens, multisigs, DAOs). A user may accidentally or intentionally specify such an address. No validation of `_to`'s ability to receive KAIA is performed on the source chain before the deposit is accepted.

---

### Recommendation

Replace the push pattern with a pull pattern:

1. In `handleKLAYTransfer`, instead of calling `_to.call.value(_value)("")`, store the pending amount in a mapping: `pendingKLAY[_to] += _value`.
2. Add a `claimKLAY()` function that lets `_to` withdraw its pending balance.
3. This ensures nonce accounting always succeeds regardless of `_to`'s ability to receive KAIA inline.

Alternatively, wrap the transfer in a non-reverting pattern and emit a `TransferFailed` event so operators can take corrective action without the nonce being permanently stuck.

---

### Proof of Concept

```solidity
// 1. Deploy a non-payable receiver on the destination chain
contract NonPayableReceiver {
    // No payable fallback — any KAIA push reverts
}

// 2. User on source chain deposits KAIA targeting NonPayableReceiver
bridge.requestKLAYTransfer{value: 1 ether}(
    address(nonPayableReceiver), // _to
    1 ether,
    ""
);
// Source bridge now holds 1 KAIA; RequestValueTransfer(nonce=N) emitted.

// 3. Operators observe the event and call handleKLAYTransfer on destination bridge
// (threshold votes collected, state written, then...)
// _to.call.value(1 ether)("") → false (NonPayableReceiver reverts)
// require(ok, "handleKLAYTransfer: transfer failed") → REVERT
// All state changes (handleNoncesToBlockNums[N], closedValueTransferVotes[N]) are undone.

// 4. Every subsequent operator retry produces the same revert.
// handleNoncesToBlockNums[N] is never set → lowerHandleNonce stuck at N.
// The 1 KAIA in the source bridge is permanently locked.
// recoveryBlockNumber never advances past N's block.

    // _updateHandleNonce increases lower and upper handle nonce after the _requestedNonce is handled.
    function _updateHandleNonce(uint64 _requestedNonce) internal {
        if (_requestedNonce > upperHandleNonce) {
            upperHandleNonce = _requestedNonce;
        }

        uint64 limit = lowerHandleNonce + 200;
        if (limit > upperHandleNonce) {
            limit = upperHandleNonce;
        }

        uint64 i;
        for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
            recoveryBlockNumber = handleNoncesToBlockNums[i];
            delete handleNoncesToBlockNums[i];
            delete closedValueTransferVotes[i];
        }
        lowerHandleNonce = i;
    }
