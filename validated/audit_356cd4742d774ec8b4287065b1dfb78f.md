### Title
Cross-tenant PR-label injection via webhook signature verified against an attacker-chosen organization, not the repository the payload actually mutates — (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp`/secret used for HMAC verification from `params.dig('repository','owner','login')`, an attacker-controlled JSON field, while `LabelCapturingHandler` (and its sibling `pull_request` handlers) independently resolves the actual `Repository`/`Stack` to mutate from a *different* attacker-controlled field, `params.repository.full_name`. Nothing enforces that these two fields refer to the same organization, so an attacker can pick an org configured with no `webhook_secret` to trivially pass verification while pointing `repository.full_name` at a completely different (secured) org's repository, causing that org's `PullRequest`/`ReviewStack` records to be mutated.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never checks, is:

`organization_used_for_verification == organization_that_owns_the_mutated_repository`

i.e. `params.dig('repository','owner','login')` (or `params.dig('organization','login')`) as read in `WebhooksController#repository_owner` at [1](#0-0)  must equal the organization implied by `params.repository.full_name` as read in `LabelCapturingHandler#repository` at [2](#0-1) . Both values live in attacker-supplied JSON and are never cross-checked, so the equality can be broken trivially.

Code path:
1. `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`, at [3](#0-2) .
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally "unless webhook_secret" is configured for that organization, and otherwise only checks the legacy `sha1=` scheme: [4](#0-3) .
3. `WebhooksController#create` then dispatches the raw, unmodified parsed body to every handler registered for the event: [5](#0-4) .
4. `LabelCapturingHandler#repository`/`#review_stack`/`#stack` resolve the target `Repository`/`Stack`/`PullRequest` purely from `params.repository.full_name`, independent of whatever org was used to verify the signature: [6](#0-5) .
5. `capture_labels` persists attacker-supplied label names directly onto that resolved stack's `PullRequest`: [7](#0-6) .
6. Those labels later become uppercased environment variable keys via `ReviewStack#env`, which are merged into the deploy/task command environment: [8](#0-7) .

Attack: an attacker who knows (from public documentation/config conventions, e.g. `docs/setup.md` and `config/secrets.*.yml` showing multi-org installs where `webhook_secret` is explicitly optional, see [9](#0-8) ) that some org `A` configured in this Shipit instance has no `webhook_secret`, sends `POST /webhooks` with `X-Github-Event: pull_request`, any `X-Hub-Signature` value (verification short-circuits to `true` for a secret-less org, so no signature computation is even required), and a JSON body where `repository.owner.login = "A"` (drives verification) but `repository.full_name = "victim-org/victim-repo"` and `pull_request.labels` contains attacker-chosen names (drives the handler's actual mutation target). `verify_signature` passes because org `A` has no secret; the handler then mutates `victim-org/victim-repo`'s `PullRequest.labels`, entirely bypassing `victim-org`'s own configured `webhook_secret`.

Existing guards do not stop this: `verify_signature` never compares `repository_owner` against `params.repository.full_name`'s owner segment; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema in `LabelCapturingHandler.params` validates types/shape but not organizational consistency between the two repository-identifying fields; and `Repository.review_stacks`/stack lookup scopes only by `full_name`, with no tenant check tying it back to the verifying org.

### Impact Explanation
An attacker who controls no secrets can inject arbitrary label names onto another organization's review-stack `PullRequest`, and those labels are turned into environment variables (`ReviewStack#env`, uppercased `label => "true"`) that get merged into the deploy/task command environment used by `Shipit::DeployCommands`/`Shipit::TaskCommands` for that victim stack's deploys/tasks (see `test/lib/shipit/deploy_commands_test.rb` and `test/lib/shipit/task_commands_test.rb` demonstrating labels flow directly into `env`). This is a cross-repository/cross-tenant state-mutation: one repository's forged webhook payload writes another repository's `PullRequest` record and influences its deployment environment — matching the "Critical: payload for one repository mutating another's stack/commit/task" category. It is repeatable against any repository in the installation as long as at least one configured organization in the same Shipit instance lacks a `webhook_secret` (a documented, optional setting), regardless of whether the victim organization itself has a strong secret configured.

### Likelihood Explanation
Preconditions: the Shipit instance must host at least two organizations in `secrets.github`, and at least one of them must have `webhook_secret` unset (explicitly documented as "optional" in `docs/setup.md`, and shown as `nil` in example multi-org configs like `config/secrets.development.shopify.yml`). No Shipit credentials, sessions, or GitHub secrets are required from the attacker — only knowledge (or a guess) of one org name configured without a secret, which is discoverable via any Shipit UI page listing installed orgs/repos or via trial requests (unknown org names yield 422 with a distinguishable log/response). Given this, the attack is a single unauthenticated HTTP POST, fully repeatable at will, with the only cost being reconnaissance of a valid low-security org identifier.

### Recommendation
In `WebhooksController#verify_signature`, derive the signing/verification organization from the *same* repository identifier the handlers use to resolve the target `Repository` (e.g. parse it from `params.repository.full_name`'s owner segment, or explicitly require `repository.owner.login` to match the first path segment of `repository.full_name` before proceeding). Additionally, do not treat `verify_webhook_signature` as trivially `true` when `webhook_secret` is blank — require a webhook secret to be configured for every organization that owns provisioned stacks, or reject payloads for organizations without one instead of silently accepting them. Also upgrade to enforce (or additionally accept) `X-Hub-Signature-256` and reject legacy sha1-only requests where feasible.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, `ActionDispatch::IntegrationTest`):
```ruby
test "pull_request payload for org without webhook_secret mutates a different org's stack" do
  # Setup: two orgs configured in Shipit.github config —
  # 'no-secret-org' (webhook_secret: nil) and 'victim-org' (webhook_secret: 'strong-secret')
  victim_repo = shipit_repositories(:shipit) # owned by 'victim-org/victim-repo'
  stack = create_review_stack_for(victim_repo) # has an associated PullRequest

  payload = base_pull_request_payload(action: "labeled")
  payload["repository"]["owner"]["login"] = "no-secret-org"   # used by verify_signature
  payload["repository"]["full_name"]      = "victim-org/victim-repo" # used by handler
  payload["pull_request"]["labels"] = [{ "name" => "forged-label" }]

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = "sha1=deadbeef" # arbitrary/invalid — irrelevant since org has no secret

  post :create, body: payload.to_json, as: :json

  assert_response :ok
  # Assert LHS (verifying org) != RHS (mutated org), yet the write succeeded:
  assert_equal "no-secret-org", payload.dig("repository", "owner", "login")
  assert_equal "victim-org/victim-repo", payload.dig("repository", "full_name")
  assert_includes stack.reload.pull_request.labels, "forged-label"
end
```
This demonstrates the invariant `organization_used_for_verification == organization_that_owns_the_mutated_repository` is violated: verification used `no-secret-org`, but the write landed on `victim-org`'s `PullRequest`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
