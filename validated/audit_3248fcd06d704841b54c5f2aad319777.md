### Title
`StatusHandler#process` writes commit status by bare SHA with no repository scoping, allowing cross-stack status/merge-queue manipulation - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever checking that the matched commit's stack corresponds to the repository that authenticated the incoming webhook. This breaks the invariant that a `status` event for repository A can only affect commits belonging to A's stacks, and can flip the required `ci/e2e` context to `success` on an unrelated victim stack, triggering merge-queue advancement (`merge_queue_enabled: true`) and deployability changes.

### Finding Description
The claimed invariant is: `written_stack.repository == payload.dig('repository','full_name')`, i.e. any commit whose status is mutated by a webhook must belong to the repository that signed that webhook.

The code path:
1. `Shipit::WebhooksController#create` verifies the HMAC signature only against `repository_owner` (`params.dig('repository','owner','login')`), then dispatches the parsed JSON to every registered handler for the event type: [1](#0-0)  and [2](#0-1) .
2. `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper explicitly meant to scope handler logic to the repository named in the payload: [3](#0-2) .
3. `StatusHandler#process` does not use that scoping helper at all. It performs a bare, global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this matches every `Commit` row in the entire database with that SHA, across every `Stack`/repository: [4](#0-3) .
4. `Commit#create_status_from_github!` unconditionally replicates the incoming status into that commit's own `stack_id` and recomputes `status`, calling `stack.schedule_merges` when the new status is a success: [5](#0-4)  and [6](#0-5) .
5. `Commit#deployable?` and `blocked?` are computed straight from `status`, so a spoofed success on the required `ci/e2e` context directly changes deployability, and for merge-queue enabled stacks a green head advances `stack.schedule_merges` / `merge!`.

Because `Commit` rows for different `Stack`s can share the same SHA (e.g. shared git history between a fork and upstream, a repository tracked by multiple stacks/environments, or any DB state where two stacks reference overlapping commit ranges), a webhook that is validly signed for the attacker's own repository/organization can still land on `Commit` rows that belong to a completely different, victim stack, because `StatusHandler` never checks `commit.stack.repository == payload_repository`.

Existing guards do not prevent this:
- `verify_signature` only proves the payload came from the organization named in the payload; it does not constrain which `Commit` rows the handler is allowed to mutate. [2](#0-1) 
- The `ExplicitParameters` schema in `StatusHandler` only validates the shape of `sha`/`state`/`context`, not which stack it applies to. [7](#0-6) 
- The `Handler#stacks`/`repository_name` scoping mechanism exists in the base class for exactly this purpose but `StatusHandler` simply doesn't call it. [3](#0-2) 

### Impact Explanation
A cross-repository write of commit status is possible: a webhook validly signed for one repository/organization can flip the `success` status of a `ci/e2e` context on a `Commit` belonging to a stack tracking a different repository, as long as a `Commit` row with the same SHA exists under both. On a stack with `merge_queue_enabled: true`, this changes `deployable?`/`blocked?` for that commit and triggers `stack.schedule_merges`, which can force or block a merge (and, in continuous-deployment stacks, a deploy) of code the attacker does not control the CI outcome of. This matches the "Critical — payload for one repository mutating another's stack/commit" / "unauthorized deploy, rollback or merge" category. Blast radius is limited to stacks whose `Commit` table contains a SHA collision with the attacker-controlled repository's commit history (e.g. shared ancestry, duplicated stack tracking of the same repo under multiple environments, or repositories that were forked/renamed and both retained as stacks) — it is not an arbitrary-repository-to-arbitrary-repository primitive for freshly-invented SHAs, since the attacker cannot forge a new commit whose SHA equals an arbitrary pre-existing victim commit.

### Likelihood Explanation
Preconditions: (1) attacker must be able to produce a validly-signed `status` webhook, which requires their target/originating repository's organization to be a recognized GitHub App/organization in Shipit's config (`Shipit.github(organization: repository_owner)`); (2) a `Commit` row with the identical SHA must already exist under the victim's stack — realistically via shared git history between related repositories/forks or a repository tracked by more than one `Stack` (e.g. different environments of the same repo), rather than an arbitrary attacker-chosen SHA. Given those preconditions, the attack is cheap and repeatable: each qualifying SHA collision lets the attacker send unlimited status webhooks. The code-level bug (missing repository scoping in `StatusHandler#process`) is unconditionally present regardless of deployment configuration.

### Recommendation
Scope `StatusHandler#process` the same way other handlers are expected to via `Handler#stacks`: only update `Commit` rows whose `stack` belongs to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each { ... }`, rejecting/ignoring matches outside that repository's stacks.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack` fixtures for two different repositories, `victim_stack` (`merge_queue_enabled: true`, `required_status_checks` including `ci/e2e`) and `attacker_stack` (different `repository`).
2. Create a `Commit` under each stack with the identical `sha` value `"deadbeef..."` (simulating shared history / duplicated tracking).
3. Build a `status` payload with `repository.full_name` set to the attacker's repository, `sha: "deadbeef..."`, `context: "ci/e2e"`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `victim_stack.commits.find_by(sha: "deadbeef...").deployable?` changed to `true` (or `merge_status`/`schedule_merges` was invoked) even though the webhook's `repository.full_name` never named `victim_stack`'s repository — i.e. `commit_written_for(:victim_stack) == true` while `payload_repository == :attacker_repo`, proving the equality `written_stack.repository == payload_repository` is violated.
