### Title
Unbounded per-invocation contract-instantiation cost (globals / data segments / element segments) not covered by charged gas - ([File: runtime/runtime-params-estimator/src/vm_estimator.rs])

### Summary
nearcore's own gas-cost estimator explicitly documents that Wasmtime's per-call re-initialization work for a contract's globals, data segments, and active element segments is *"not covered by gas"*. A contract with many globals/data segments/table elements can be deployed once (paying only the fixed `DeployContractAction` cost) and then invoked repeatedly via ordinary `FunctionCall` transactions/receipts, each time forcing the runtime to redo this re-initialization work while only being charged `wasm_contract_loading_base` / `wasm_contract_loading_bytes`, which are calibrated on ordinary "real world" sample contracts rather than on this adversarial shape. This is the wasm-metering analog of the "UDP/TCP decompression CPU exhaustion" and "decoder memory multiplication" bug classes in the external report: a cheap, authenticated (here: gas-paid) message triggers disproportionately expensive host-side work that isn't priced correctly.

### Finding Description
The estimator source contains dedicated "adversarial" cost categories whose doc comments state the vulnerability directly: [1](#0-0) 

These are measured by constructing contracts with 50,000 globals, 50,000 data segments, or 10,000 element segments and timing repeated invocations (instantiation + trivial execution) via `measure_instantiation_overhead`: [2](#0-1) 

The contract shapes used to trigger this are generated in `near-test-contracts`, e.g. `many_element_segments_contract`: [3](#0-2) 

Meanwhile, the actual production charge for loading/instantiating a contract on every `FunctionCall` is `wasm_contract_loading_base` + `wasm_contract_loading_bytes * code_size`, which is calibrated via least-squares fit against a small sample of "real" contracts (`REAL_CONTRACTS_SAMPLE`), not against adversarial contracts built specifically to maximize globals/data-segment/element-segment counts per byte: [4](#0-3) 

A related test confirms the general class of bug (unbounded/uncharged instantiation work related to global count) is real enough that Wasmtime's pooling allocator can even reject the module outright (`max_core_instance_size`), and that pre-fix this manifested as a *zero-gas* no-op — i.e., the node did real work (parsing/attempting to load the contract) while charging **zero gas** to the caller: [5](#0-4) [6](#0-5) 

The module-level structural limits that permit such contracts to be deployed at all are documented as intentionally generous: up to 1,000,000 globals, 100,000 data segments, and up to 10,000,000 table entries are allowed by protocol-level validation: [7](#0-6) 

Because `wasm_contract_loading_bytes` is fit against ordinary contracts (mostly code, not adversarially packed metadata sections), an attacker can craft a contract near these limits that maximizes globals/data-segments/element-segments per byte of wasm binary, so the *actual* per-invocation reinitialization cost scales far beyond what `contract_loading_base`/`contract_loading_bytes` charges for that many bytes. Every subsequent `FunctionCall` transaction against that deployed contract then triggers disproportionate CPU work in the validator's execution path for underpriced gas — a direct, unprivileged, transaction-reachable analog of the report's decompression/decoder-multiplication CPU/memory amplification classes.

### Impact Explanation
This is a resource-accounting gap in the wasm metering / gas-accounting layer reachable by any account submitting ordinary `DeployContractAction` + `FunctionCallAction` transactions — no validator or P2P privileges required. If the discrepancy between charged gas and actual CPU time is large enough, it enables:
- Underpriced/free execution: attacker pays gas priced for ordinary contract loading, but the validator burns disproportionately more CPU time on every call.
- Sustained CPU exhaustion across the network, since the same wasm code is executed identically by all validators processing the receipt (consensus-critical, not a single node's problem) — this can degrade chunk-production throughput or, at the extreme, contribute to chain stall if `contract_loading_base/bytes` undercharge severely enough relative to `max_gas_burnt`/per-chunk gas limits.

The severity depends on how large the gap between the estimator numbers and the actually charged/config-committed `wasm_contract_loading_base`/`wasm_contract_loading_bytes` parameters is — a delta I could not directly quantify from the indexed snippets (the concrete numeric estimator outputs and whether they were ever folded back into `parameters.yaml` were not fully visible in the available index). The `test_max_core_instance_size_breached` fix shows the team is aware of and has begun patching related edge cases (turning a zero-gas crash into a gas-bearing abort), suggesting the underlying uncharged-instantiation-work problem is a recognized but not necessarily fully closed class of issue.

### Likelihood Explanation
Medium. Deploying and invoking a contract via a transaction is fully unprivileged and requires no special access, matching the "unpermissioned external attack" tier in the source report. However, exploitability depends on the actual numeric gap between the currently configured `wasm_contract_loading_base`/`wasm_contract_loading_bytes` values (see `core/parameters/res/runtime_configs/parameters.snap`) and the true adversarial-case instantiation cost, which I was unable to fully confirm from the available index — this would need direct benchmarking of a maximal globals/data-segment/element-segment contract against the currently charged fee to establish concrete under-charging magnitude.

### Recommendation
- Recalibrate `wasm_contract_loading_base`/`wasm_contract_loading_bytes` (or introduce dedicated per-global/per-data-segment/per-element-segment gas costs) using the adversarial contract shapes already generated by the estimator (`contract_with_num_globals`, `many_data_segments_contract`, `many_element_segments_contract`) rather than only "real world" sample contracts, so that the charged fee reflects worst-case per-invocation instantiation cost rather than average case.
- Consider tightening the protocol-level structural limits (globals/data segments/table elements) so that even the worst case falls within a bounded, already-priced-for CPU budget, rather than relying purely on linear-in-bytes charging that can be gamed by adversarial encodings.
- Ensure the `fix_contract_loading_error` gas-bearing-abort pattern (already applied to the pooling-allocator oversize case) is generalized so that no failure/edge case in the loading/instantiation path can ever result in the previous zero-gas no-op behavior.

### Proof of Concept
Conceptual (derived from the repo's own adversarial estimator harness, not independently executed):
1. Generate a wasm module near the protocol's structural limits, e.g. `near_test_contracts::many_element_segments_contract(10_000)` (or the many-globals/data-segments equivalents), sized so that it is well under `max_contract_size` and under the Wasmtime pooling allocator's `max_core_instance_size`, but has significantly more globals/data-segments/element-segments per encoded byte than a typical contract.
2. Deploy the contract via an ordinary `DeployContractAction` transaction (paying only per-byte deployment/compilation fees).
3. Submit repeated cheap `FunctionCallAction` transactions/receipts invoking its trivial exported `main` function.
4. Each invocation forces Wasmtime to redo the full instantiation reinit work (globals/data-segments/element-segments), which `runtime/runtime-params-estimator/src/vm_estimator.rs::measure_instantiation_overhead` already shows is measurable and non-trivial, while the caller is charged only the fee computed from `contract_loading_base + contract_loading_bytes * code_size` — a fee calibrated against non-adversarial sample contracts (`runtime/runtime-params-estimator/src/vm_estimator.rs:63-134`), producing an underpriced CPU-consumption primitive analogous to the "decompression CPU exhaustion" attack in the source report, but reachable purely through normal transaction submission.

/// Returns `(a, b)` - approximation coefficients for formula `a + b * x`
/// where `x` is the contract size in bytes. Practically, we compute upper bound
/// of this approximation, assuming that whole contract consists of code only.
fn precompilation_cost(
    gas_metric: GasMetric,
    vm_kind: VMKind,
    verbose: bool,
) -> (GasCost, GasCost) {
    if cfg!(debug_assertions) {
        eprintln!("WARNING: did you pass --release flag, results do not make sense otherwise")
    }
    let cache_store1 = FilesystemContractRuntimeCache::test().unwrap();
    let cache_store2 = NoContractRuntimeCache;
    let use_store = true;
    let cache: &dyn ContractRuntimeCache = if use_store { &cache_store1 } else { &cache_store2 };
    let mut xs = vec![];
    let mut ys = vec![];

    for (path, _) in REAL_CONTRACTS_SAMPLE {
        let raw_bytes = read_resource(path);
        let contract = ContractCode::new(raw_bytes.to_vec(), None);
        xs.push(raw_bytes.len() as u64);
        ys.push(measure_contract(vm_kind, gas_metric, &contract, cache));
    }

    // Motivation behind these values is the same as in `fn action_deploy_contract_per_byte`.
    let negative_base_tolerance = Gas::from_gas(369_531_500_000u64);
    let rel_factor_tolerance = 0.001;
    let (a, b) = GasCost::least_squares_method_gas_cost(
        &xs,
        &ys,
        &LeastSquaresTolerance::default()
            .base_abs_nn_tolerance(negative_base_tolerance)
            .factor_rel_nn_tolerance(rel_factor_tolerance),
        verbose,
    );

    // We multiply `b` by 5/4 to accommodate for the fact that test contracts are typically 80% code,
    // so in the worst case it could grow to 100% and our costs still give better upper estimation.
    // Safety multiplication with 5/4.
    let safety_numer = 5u64;
    let safety_denom = 4u64;
    let (corrected_a, corrected_b) =
        (a * safety_numer / safety_denom, b * safety_numer / safety_denom);

    // Now validate that estimations obtained earlier provides correct upper estimation
    // for several other contracts.
    // Contracts binaries are taken from near-sdk-rs examples, ae20fc458858144e4a35faf58be778d13c2b0511.
    let validate_contracts = vec![
        // File 139637.
        read_resource("res/status_message.wasm"),
        // File 157010.
        read_resource("res/mission_control.wasm"),
        // File 218444.
        read_resource("res/fungible_token.wasm"),
    ];

    for raw_bytes in validate_contracts {
        let contract = ContractCode::new(raw_bytes.to_vec(), None);
        let x = raw_bytes.len() as u64;
        let y = measure_contract(vm_kind, gas_metric, &contract, cache);
        let expect = corrected_a.to_gas().as_gas() as i128
            + corrected_b.to_gas().as_gas() as i128 * (x as i128);
        let error = expect - (y.to_gas().as_gas() as i128);
        if gas_metric == GasMetric::ICount {
            // Time based metric may lead to unpredictable results.
            assert!(error >= 0);
        }
    }

    (corrected_a, corrected_b)
}

/// Warm the compile cache, then measure N invocations (instantiation + trivial execution).
/// The function body is a bare `end`, so execution cost is negligible.
fn measure_instantiation_overhead(
    metric: GasMetric,
    vm_kind: VMKind,
    contract_bytes: &[u8],
) -> GasCost {
    let config_store = RuntimeConfigStore::new(None);
    let mut config = config_store.get_config(PROTOCOL_VERSION).wasm_config.as_ref().clone();
    config.vm_kind = vm_kind;
    let config = Arc::new(config);
    let fees = Arc::new(RuntimeFeesConfig::test());
    let code = ContractCode::new(contract_bytes.to_vec(), None);
    let cache = MockContractRuntimeCache::default();
    let mut fake_external = near_vm_runner::logic::mocks::mock_external::MockedExternal::with_code(
        code.clone_for_tests(),
    );

    let mut run_once = || {
        let context = create_context(vec![]);
        let gas_counter = context.make_gas_counter(&config);
        vm_kind
            .runtime(config.clone())
            .unwrap()
            .prepare(&fake_external, Some(&cache), gas_counter, "main")
            .run(&mut fake_external, &context, Arc::clone(&fees))
            .expect("fatal_error")
    };

    // Warm: compiles and caches the module; subsequent calls only instantiate + execute.
    run_once();

    let n = 10_usize;
    let start = GasCost::measure(metric);
    for _ in 0..n {
        run_once();
    }
    start.elapsed() / n as u64
}

/// Many active element segments, each writing function 0 into table slot 0.
pub fn many_element_segments_contract(num_segments: u32) -> Vec<u8> {
    let mut module = Module::new();
    let mut types = TypeSection::new();
    types.ty().function([], []);
    module.section(&types);
    let mut funcs = FunctionSection::new();
    funcs.function(0);
    module.section(&funcs);
    let mut tables = TableSection::new();
    tables.table(TableType {
        element_type: RefType::FUNCREF,
        minimum: 1,
        maximum: Some(1),
        table64: false,
        shared: false,
    });
    module.section(&tables);
    let mut exports = ExportSection::new();
    exports.export("main", ExportKind::Func, 0);
    module.section(&exports);
    let mut elements = ElementSection::new();
    for _ in 0..num_segments {
        elements.active(
            Some(0),
            &ConstExpr::i32_const(0),
            Elements::Functions(Cow::Borrowed(&[0u32])),
        );
    }
    module.section(&elements);
    let mut code = CodeSection::new();
    let mut f = Function::new([]);
    f.instruction(&Instruction::End);
    code.function(&f);
    module.section(&code);
    module.finish()
}
