### Title
Cross-organization Team membership forgery via unscoped `github_id` lookup in `membership` webhook - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up `Shipit::Team` records solely by the numeric `github_id` field taken from the webhook payload, with no scoping to the organization whose secret verified the request. Because `WebhooksController#repository_owner` (used to pick which org's `webhook_secret` verifies the signature) falls back to the attacker-controlled `organization.login` field for events with no `repository` object (which is the case for `membership` events), an attacker who owns any GitHub organization enrolled in Shipit can sign a `membership` payload with their own webhook secret while naming another organization's `team.id`, causing Shipit to mutate that other organization's `Team` row and add the attacker as a member.

### Finding Description
The broken binding: `organization_that_verified_signature == Team#organization_being_mutated` must hold, but does not.

- `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it to select which org's `webhook_secret` verifies the HMAC signature [2](#0-1) .
- The `membership` event schema requires only `action`, `team`, `organization`, `member` — there is no `repository` object [3](#0-2) . Therefore `repository_owner` resolves to `params.organization.login`, a field fully controlled by the attacker inside the payload they are signing.
- Because the attacker owns their own GitHub org (OrgA) and has legitimately installed the Shipit GitHub App there, they know OrgA's `webhook_secret` and can compute a valid HMAC over any payload of their choosing, as long as `organization.login == "orga"`.
- `MembershipHandler#find_or_create_team!` resolves the target `Team` via `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3)  — this lookup is not scoped by `organization`, only by the numeric GitHub team id. If the attacker sets `team.id` to the real `github_id` of an existing `Shipit::Team` belonging to OrgB, the `find_or_create_by!` block (which sets `organization`) never executes because the record is found, and `find_or_create_team!` returns OrgB's actual `Team`.
- `MembershipHandler#process` then calls `User.find_or_create_by_login!(params.member.login)` (attacker's own GitHub login) and, for `action == 'added'`, `team.add_member(member)` [5](#0-4) , appending the attacker as a member of OrgB's `Team`.
- Membership in a `Team` returned by `Shipit.github_teams` directly satisfies `User#authorized?`, which checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , and `force_github_authentication` grants full application access once `authorized?` is true [7](#0-6) .
- No other guard intervenes: `drop_unhandled_event` and `check_if_ping` don't apply; `verify_signature` succeeds because it validates against the wrong (attacker-controlled) organization; the `ExplicitParameters` schema only enforces types/presence, not cross-field consistency between `organization.login` and `team.id`'s owning org.

Attacker's exact request: `POST /webhooks` with `X-Github-Event: membership`, `X-Hub-Signature` computed with OrgA's known `webhook_secret` over a JSON body `{"action":"added","team":{"id":<OrgB's real Team github_id>,"name":"...","slug":"...","url":"..."},"organization":{"login":"orga"},"member":{"login":"attacker"}}`.

### Impact Explanation
This is a Critical-severity authentication/authorization bypass: a webhook signed with organization A's own credentials can add an arbitrary GitHub user (the attacker) to organization B's `Shipit::Team`, and if that team is enumerated in `Shipit.github_teams`, this directly grants the attacker full authenticated access to Shipit (deploys, rollbacks, stack state, task streams) for organization B's stacks, without ever touching OrgB's secrets. This escalates into `Shipit.github_teams` authorization (High) and, because it constitutes a payload from one tenant mutating another tenant's Team/authorization record and can be leveraged for unauthorized deploys/rollbacks once authorized, it also matches the Critical "payload for one repository mutating another's ... team" and "unauthorized deploy/rollback" categories. It is repeatable against any `Shipit::Team` whose numeric `github_id` the attacker can discover (GitHub team IDs are visible via GitHub's public/team APIs or UI to team members, and are guessable/enumerable), across every organization hosted on the same Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control at least one GitHub organization that is configured as a valid organization in Shipit's multi-org GitHub App configuration (i.e., has a `webhook_secret` known to the attacker because they set it up), and must know or discover the numeric `github_id` of the target `Shipit::Team` in OrgB (obtainable via GitHub's team API/UI if the attacker can view OrgB's team, or via team enumeration since GitHub team ids are sequential/public in many contexts). No Shipit credentials, sessions, or GitHub App private keys are needed. The attack is a single crafted HTTP POST, fully repeatable, and does not require any privileged Shipit role — only ownership of *any* enrolled organization.

### Recommendation
Scope the `Team` lookup by both `github_id` and the verified organization, and reject/ignore mismatches between the payload's `organization.login` and the org that produced a valid signature. Specifically:
- In `MembershipHandler#find_or_create_team!`, look up by `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` rather than `github_id` alone, or explicitly verify that an existing team's `organization` column matches `params.organization.login` before mutating it, raising/aborting otherwise.
- More fundamentally, fix `WebhooksController#repository_owner` so it never trusts an unauthenticated payload field as the sole source of truth for which org's secret to use, or cross-check that the organization used for signature verification matches the organization referenced by the event's actual target entity (team/repository) before allowing any DB mutation.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (new/extended)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandlerCrossOrgTest < ActiveSupport::TestCase
        test "membership event signed by OrgA cannot mutate OrgB's Team" do
          org_b_team = shipit_teams(:shopify) # fixture: organization: 'shopify', github_id: 999

          payload = {
            action: 'added',
            team: { id: org_b_team.github_id, name: org_b_team.name, slug: org_b_team.slug, url: org_b_team.api_url },
            organization: { login: 'orga' }, # attacker's own org, used for signature verification
            member: { login: 'attacker' }
          }.to_json

          # Simulate: attacker signs this exact payload with OrgA's *own* webhook_secret,
          # which WebhooksController#verify_signature will accept because
          # repository_owner falls back to params.organization.login == 'orga'.

          assert_no_difference -> { Team.where(organization: 'orga').count } do
            assert_difference -> { Membership.count }, 1 do
              MembershipHandler.new.call(JSON.parse(payload))
            end
          end

          org_b_team.reload
          attacker = User.find_by(login: 'attacker')

          # BINDING CHECK: the team mutated must equal the org that verified the signature.
          # Expected (secure) behavior: org_b_team.members should NOT include attacker,
          # because the signature only proves authenticity for 'orga', not 'shopify'.
          refute_includes org_b_team.members, attacker,
            "Attacker signed with OrgA's secret but was added to OrgB's Team -- cross-org authorization bypass"
        end
      end
    end
  end
end
```
This test demonstrates that, as currently implemented, `find_or_create_team!`'s unscoped `github_id` lookup causes `org_b_team.members` to include `attacker`, and if `org_b_team` is present in `Shipit.github_teams`, `attacker.authorized?` becomes `true` — proving the cross-tenant authorization escalation.
