### Title
Stack-scoped API token bypasses stack ownership check via unscoped `stack` lookup in `CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#require_permission!` only validates the literal string `"#{operation}:#{scope}"` (e.g. `"read:stack"`) against `ApiClient#permissions`; it never compares the requested stack against `current_api_client.stack_id`. `CCMenuController` compounds this by overriding the `stack` accessor to use `Stack.from_param!(params[:stack_id])` directly instead of the base controller's `stacks.from_param!`, which is the only mechanism that would have scoped lookups to `current_api_client.stack_id`. The result is that any CCMenu token scoped to stack A with `read:stack` permission can read the state of any other stack B by simply changing `params[:stack_id]`.

### Finding Description
Broken binding as equality: the intended security invariant is `current_api_client.stack_id == stack.id` (i.e., a stack-scoped token may only act on its own stack) whenever `current_api_client.stack_id?` is true. The actual code enforces only `permissions.include?("#{operation}:#{scope}")`, which is independent of any stack id — so `required_permission == "read:stack"` holds true for *any* stack, not just the one the token is scoped to.

Code path:
1. `CCMenuController` declares `require_permission :read, :stack` [1](#0-0) , which installs a `before_action` calling `require_permission!(:read, :stack)` [2](#0-1) .
2. `require_permission!` simply forwards to `current_api_client.check_permissions!(operation, scope)` [3](#0-2) .
3. `ApiClient#check_permissions!` builds `required_permission = "read:stack"` and checks only `permissions.include?(required_permission)` — no reference to `stack_id` or any request parameter at all [4](#0-3) .
4. The only place stack-scoping is normally enforced is `BaseController#stacks`, which restricts to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id` [5](#0-4) . However, `CCMenuController` overrides `stack` to bypass this scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [6](#0-5) , an unscoped lookup against *all* stacks.

Attacker flow: possess (or be issued) a legitimate CCMenu API token for stack A with `read:stack` permission and `stack_id = A`. Send `GET /api/stacks/:foreign_owner/:foreign_repo/:foreign_branch/cc_menu.xml?token=<stack-A-token>` (or via Basic Auth) for stack B. `authenticate_api_client` succeeds (valid token) [7](#0-6) ; `check_permissions!(:read, :stack)` passes because the token has `read:stack` in `permissions`, regardless of `stack_id`; `stack` resolves stack B unscoped; `show` renders stack B's latest deploy/build status/lock state [8](#0-7) .

No other guard intervenes: there is no `verify_signature`, no webhook path here, and `ExplicitParameters`/model validations are irrelevant to this read-only endpoint.

### Impact Explanation
An attacker holding any single stack-scoped CCMenu token with `read:stack` can enumerate/read build status, last deploy/rollback state, and lock status for **any** stack in the Shipit instance, not just the one the token was issued for — an unauthenticated-for-that-resource read of stack state across tenants. This matches the High severity category "escalation... unauthenticated read of stack state, task streams or deploy output" and is fully repeatable against arbitrary stacks by varying `stack_id` in the URL, with no rate limiting or additional secret required.

### Likelihood Explanation
Preconditions are met by any existing CCMenu token that has `read:stack` in `permissions` and a non-null `stack_id` (this is the normal/default configuration for stack-scoped CCMenu tokens, as documented by the CCMenu feature). The attacker needs only one such valid token (which they may legitimately hold for their own stack) and knowledge/guessability of another stack's `owner/repo/branch` param — no secrets, sessions, or elevated roles required. Cost is a single HTTP GET.

### Recommendation
In `ApiClient#check_permissions!`, when `stack_id` is present, additionally require that the resource being acted on matches `stack_id` (e.g., pass the target stack/id into `check_permissions!` and compare `current_api_client.stack_id == stack.id`), or fix `CCMenuController#stack` to use the scoped `stacks.from_param!` from `BaseController` instead of the unscoped `Stack.from_param!`.

### Proof of Concept
```ruby
# test/models/api_client_test.rb (illustrative)
test "check_permissions! ignores stack_id mismatch" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')
  client = ApiClient.create!(creator: shipit_users(:walrus), name: 'x',
                              permissions: ['read:stack'], stack: stack_a)
  # No argument ties the check to stack_b, so this returns true even though
  # client.stack_id (stack_a.id) != stack_b.id
  assert client.check_permissions!(:read, :stack)
end

# test/controllers/api/ccmenu_controller_test.rb (illustrative)
test "a stack-scoped token can read a foreign stack's CC menu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')
  @client.update!(stack: stack_a, permissions: ['read:stack'])
  get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }
  assert_response :ok # should be :forbidden/:not_found for a stack-A-scoped token
  assert_payload 'name', stack_b.to_param
end
```
