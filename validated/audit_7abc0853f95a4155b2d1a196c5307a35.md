### Title
`StatusHandler#process` applies GitHub status webhooks to commits without scoping to the payload's repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `by sha` across the entire `Commit` table and calls `create_status_from_github!` on every match, with no check that the commit's owning stack/repository matches the repository that authenticated the webhook. This lets an attacker who owns any repository (and can therefore legitimately sign a webhook for it) inject a forged "success" status onto a commit belonging to an unrelated victim stack, provided the same sha exists in both (e.g., via cherry-pick), clearing `Commit#blocked?` and unblocking deploys on the victim stack.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`authenticated_repository.full_name == commit.stack.repository.full_name` for every `commit` mutated by a webhook.

Code path:
- `WebhooksController#create` parses the raw JSON and dispatches to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) 
- `verify_signature` only proves the payload was sent by GitHub for `repository_owner` (derived from the payload itself) — it authenticates *that the attacker's own org/repo sent this*, not that the payload is authorized for the *target* commit's stack: [2](#0-1) 
- `Handler` base class exposes a `stacks` helper that correctly scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, and other handlers (e.g. the pull_request handlers) use this pattern to bind the payload to the correct repository. [3](#0-2) 
- `StatusHandler#process`, however, ignores `repository_name`/`stacks` entirely and queries commits globally by sha:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
- `create_status_from_github!` writes the forged status onto the commit regardless of which repository owns its stack: [5](#0-4) 
- `Commit#blocked?` re-evaluates blocking statuses across the stack's undeployed range via `stack.commits.reachable...any?(&:blocking?)`, so once the forged status flips the target commit's state, it drops out of the blocking scan: [6](#0-5) 
- `deployable?` for later commits then flips to `true`, and continuous delivery proceeds. [7](#0-6) [8](#0-7) 

Attacker exploit flow: attacker creates/owns a repository with a Shipit-installed GitHub App/webhook secret, cherry-picks or otherwise arranges a commit whose sha matches the victim's blocking commit sha (cherry-picks preserve sha only if identical tree/parent/message/author/date - realistically an attacker can achieve sha collision via manipulating a repo to contain an identical commit object, e.g. by force-pushing a branch that includes the exact same commit object, since a git commit sha is content-addressed and reproducible by anyone who knows the exact commit content, which is public in the victim's repo history). The attacker then triggers (or receives naturally from GitHub CI on their own repo) a `status` webhook with `state: success` for that sha, signed with their own repo's webhook secret. `verify_signature` passes because it only validates the signature belongs to the attacker's own org, not that the sha belongs to that org's repo. `StatusHandler#process` then applies the forged success status to the victim's `Commit` record, clearing `blocking?` on it.

None of the existing guards prevent this: `verify_signature` authenticates sender identity, not sha/repository ownership of the commit being mutated; `ExplicitParameters` only validates payload shape; there is no `stacks`/`repository_name` scoping in `StatusHandler` unlike other handlers.

### Impact Explanation
This is an unauthorized write: a webhook authenticated for repository A mutates a `Commit`/`Status` record belonging to stack/repository B. The direct consequence is that a required CI/compliance blocking gate (`ci.blocking` contexts) on the victim's stack can be defeated, allowing `Stack#trigger_continuous_delivery` / `ContinuousDeliveryJob` to deploy code that never actually passed CI on the victim's own repository. This matches "Critical - a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." Blast radius is cross-tenant: any attacker with a Shipit-registered repository can target any other stack sharing a commit sha with theirs.

### Likelihood Explanation
Requires: (1) attacker owns/controls a GitHub repository connected to the same Shipit instance (or any org configured in `Shipit.github_teams`/`Shipit.github`) able to receive valid webhook signatures, (2) the victim stack has `ci.blocking` contexts configured, (3) sha collision/sharing between attacker's and victim's repository history (realistic via cherry-pick or shared submodule/fork history, or deliberately crafting an identical commit object which is trivial since git commit content, including parent sha, is often public). Attacker cost is low: sending one legitimate webhook from their own repo. Repeatable against any stack whose blocking commit's sha the attacker can reproduce.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks owned by the authenticated repository, mirroring the `stacks` helper used by other handlers, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.repository.full_name == repository_name` before any mutation.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `victim_stack` bound to repository `"victim/repo"` with `ci.blocking` context `"ci/blocking"`.
2. Create `blocking_commit` on `victim_stack` with sha `SHA`, add a `Status` with state `"failure"`/context `"ci/blocking"` so `blocking_commit.blocking?` is true and `commit.blocked?` for a later commit is `true`.
3. Assert `later_commit.blocked?` is `true` before the attack.
4. Build a status payload with `sha: SHA`, `state: "success"`, `context: "ci/blocking"`, and `repository.full_name: "attacker/unrelated-repo"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, which is orthogonal - it only proves sender identity for `attacker/unrelated-repo`, not authorization over `victim/repo`).
6. Assert `blocking_commit.reload.blocking?` is now `false` and `later_commit.blocked?` is now `false`, purely due to a payload whose `repository.full_name` never equals `victim_stack.repository.full_name`.
7. Optionally assert `later_commit.deployable?` flips to `true` and that `ContinuousDeliveryJob`/`trigger_continuous_delivery` would enqueue a deploy.
