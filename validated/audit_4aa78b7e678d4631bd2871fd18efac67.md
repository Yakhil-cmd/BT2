### Title
Webhook signature verification selects the GitHub App/organization by `repository.owner.login`, while every event handler acts on `repository.full_name` (or, for `status` events, no repository check at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the actual target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, and `StatusHandler` doesn't even check the repository - it matches purely on `Commit.where(sha: params.sha)` across the entire installation. This is structurally identical to the NFTX bug: a field (`amounts[i]`) that is used to decide what actually gets acted upon is never covered by the check that is supposed to gate the operation (the ERC721 transfer executes regardless of the unchecked `amounts[i]`). Here, the "verified" identity (organization owning the secret) and the "acted upon" identity (repository/commit actually written to) are two independent fields, and nothing binds them together.

### Finding Description
- `WebhooksController#verify_signature` computes the org used to select the app/secret from the payload itself, before the payload has been proven authentic: [1](#0-0) [2](#0-1) 

- The GitHub App/secret it verifies against is looked up per-organization: [3](#0-2) 

- After the signature is accepted, every handler resolves the stack to mutate using a *different* payload field, `repository.full_name`, not the organization that was authenticated: [4](#0-3) 

- `PushHandler` triggers a GitHub sync for whatever stacks match that `full_name`/branch: [5](#0-4) 

- `StatusHandler` is even less constrained: it matches purely by commit SHA across the entire installation, with no repository check whatsoever: [6](#0-5) [7](#0-6) 

- Injected statuses directly influence deployability gating (`deployable?`/`blocked?`) and trigger continuous delivery: [8](#0-7) [9](#0-8) 

The Shipit engine explicitly supports multi-organization deployments where each org has its own `webhook_secret`, as shown in the fixture/test configs: [10](#0-9) [11](#0-10) 

Because the "which secret authenticates this request" decision (`repository.owner.login`) and "which repository/commit is mutated" decision (`repository.full_name` / bare `sha`) are computed from independent, unauthenticated JSON fields, an actor who legitimately knows *any one* organization's `webhook_secret` (e.g., because they administer that org's GitHub App installation on a shared, multi-tenant Shipit instance) can craft a raw POST to `/webhooks` that:
1. Sets `repository.owner.login` (or `organization.login`) to their own org, so `verify_signature` selects their own org's app and their signature verifies successfully.
2. Sets `repository.full_name` to a victim org/repo tracked by the same Shipit instance (for `push`), or simply supplies a target `sha` belonging to any commit in any stack (for `status`, no owner/org field needs to match at all).

The request is accepted (`head(:ok)`) and dispatched to handlers that operate on the victim's stack/commit.

### Impact Explanation
This breaks the binding: `organization that authenticated == repository (or commit) that is written`. Concretely:
- Via the `status` event, an attacker who controls (or has been granted webhook rights to) any one configured organization can forge a `success` CI status for an arbitrary commit `sha` belonging to a victim stack on the same Shipit instance, with no repository/org correlation check at all. This can flip `Commit#deployable?` to true, unblock `blocking_statuses`, and trigger `schedule_continuous_delivery`, i.e. cause an unauthorized deploy on a stack the attacker has no legitimate access to.
- Via the `push` event, the attacker can force `GithubSyncJob` to run against a victim's stack (cross-repository interaction) despite having only proven ownership of a distinct organization's secret.

This matches the "unauthorized deploy" and "cross-repository writes" impact tier defined by the rules, and the root cause maps exactly onto the requested binding class ("an organization that authenticated versus the repository that is written").

### Likelihood Explanation
Requires the attacker to know one valid `webhook_secret` for *any* organization configured on the shared Shipit instance (their own, in a multi-tenant setup) - this is a normal, low-privilege credential relative to the victim organization, not the victim's own secret, a Shipit session, an `ApiClient` token, or repository write access to the victim repo. Since Shipit natively supports and documents multi-organization configuration (`secrets_double_github_app.yml`), this is a realistic deployment shape. The attack is a single crafted HTTP POST with no rate limiting or retry dependence.

### Recommendation
Bind the field used for signature/App selection to the same field used for locating the target resource:
- In `WebhooksController#verify_signature`, after the signature is verified for the selected organization, re-derive `repository.owner.login` from `repository.full_name` and require they match (reject if they don't) - or better, require that the resolved `Repository`/`Stack`'s configured organization matches the organization whose secret verified the request.
- In `Shipit::Webhooks::Handlers::StatusHandler` (and `CheckSuiteHandler`, etc.), scope the `Commit`/`Stack` lookup by the same `repository.full_name` used elsewhere, and assert it belongs to the organization that authenticated the webhook, rather than matching bare `sha` globally.
- Alternatively, key `Repository#from_github_repo_name` lookups by both `full_name` and the authenticated organization, rejecting cross-organization matches.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgOne` (owns victim stack `OrgOne/app`) and `OrgTwo` (attacker administers this org's GitHub App and therefore knows its `webhook_secret`):

1. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha in OrgOne/app>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgTwo/irrelevant" }
}
```
2. Attacker computes `X-Hub-Signature` using `OrgTwo`'s `webhook_secret` (known to them) over the raw JSON body, sets `X-Github-Event: status`, and POSTs to `/webhooks`.
3. `verify_signature` calls `Shipit.github(organization: 'OrgTwo')`, which verifies successfully since the signature matches `OrgTwo`'s secret. [1](#0-0) 
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on the matched commit regardless of which organization it actually belongs to. [6](#0-5) 
5. The forged `success` status can flip `Commit#deployable?` for the victim stack and trigger continuous delivery, resulting in an unauthorized deploy of `OrgOne/app`. [8](#0-7) [9](#0-8)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
