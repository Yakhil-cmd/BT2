The Solidity vault's "burn-shares-but-receive-zero-assets" rounding pattern is directly mirrored by how Obyte's AA (oscript) engine composes payment messages: `aa_composer.js` silently drops any payment output whose rounded amount is zero instead of bouncing (reverting) the whole trigger, while other messages in the same trigger (e.g. `state` messages that already decremented share/balance counters) still execute and get persisted.

### Title
Silent removal of zero-amount payment outputs in AA composer lets share/LP-style AAs burn a user's tokens while paying zero assets in return - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit`/`completePaymentPayload` logic filters out any payment output whose computed amount rounds down to zero, and then drops the whole payment message if it ends up with no outputs, but it does **not** abort the AA trigger as a whole when other (non-payment) messages remain, such as a `state` message. If an AA's oscript logic computes a proportional payout (`round(share * balance)`), a small enough redemption amount produces `amount == 0`; the payment output is silently discarded while the accompanying `state` update (e.g., decrementing `mm_asset_outstanding`, burning shares, marking the position closed) still applies.

### Finding Description
In `aa_composer.js`, when building a unit for the AA's response: [1](#0-0) 
outputs with `amount === 0` are filtered out of each payment message, and payment messages left with an empty outputs array are removed from the message list entirely. Only if **all** messages are removed does the code bounce/produce an empty response: [2](#0-1) 
This is also confirmed by the accompanying test, which shows that when the *only* message is a zero-output payment, "no messages after removing 0-outputs" leads to no state changes: [3](#0-2) 
However, when an AA emits multiple messages — e.g. a `state` message alongside a `payment` message — and only the payment message's output rounds to zero, that payment message alone is dropped while the `state` message (already executed via `executeStateUpdateFormula`) is retained and its effects persisted.

This exact pattern is present in the officially bundled reference AA sample that implements a Uniswap-like liquidity/share redemption ("vault") design, analogous to the Notional TwoToken/Boosted3Token vaults in the report: [4](#0-3) 
Here, a user's `$mm_asset` (share) tokens are transferred to the AA as part of the trigger (effectively removing them from the redeemer, akin to "burning" strategy tokens), `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` is computed, and the two payout amounts are `round($investor_share * balance[...])`. If `$investor_share * balance[asset]` (or `* balance[base]`) rounds to zero because the redeemed share is too small relative to the pool, the corresponding payment output is silently dropped by the AA composer, yet the `state` message unconditionally executes `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]`, permanently reducing outstanding shares without paying out the corresponding assets to the user.

### Impact Explanation
Any AA implementing a proportional-share redemption/vault pattern (the exact pattern the codebase ships as a reference sample) is exposed to loss of user funds: a caller can transfer/burn their share tokens, have the AA's state permanently updated to reflect the redemption, yet receive zero of the underlying asset(s) due to integer rounding — with no revert/bounce of the transaction. This is a direct fund-loss condition for the AA trigger sender, matching the "concrete unauthorized spending / AA fund loss" criteria.

### Likelihood Explanation
This is easily triggered by any unprivileged AA trigger sender: simply send a small enough amount of the share/LP asset (or bytes) such that `round(share * balance)` evaluates to zero. No special privileges, hub cooperation, or timing conditions are required — only crafting a trigger with a sufficiently small amount relative to the current pool balance/outstanding-shares ratio.

### Recommendation
The AA composer should not treat a payment message that would collapse to zero output as something to silently drop while other messages in the same trigger still commit their effects. Concretely:
- Do not filter/execute remaining `state`/other messages when a payment message would end up empty due to rounding — instead bounce the whole trigger (as already happens when it's the *only* message), or
- Provide/encourage a first-class `is_valid_amount()`/explicit check idiom and document that AA authors must always verify computed payment amounts are non-zero before relying on proportional-share formulas (as is partly attempted in the sample script's initial-deposit special case, but not for the divest path).

### Proof of Concept
1. Deploy an AA equivalent to `test/samples/uniswap_like_market_maker.oscript` (share/LP-token vault pattern) which is included in this very repo as a canonical example.
2. Have another account inflate `var['mm_asset_outstanding']` and the pool `balance[$asset]`/`balance[base]` (normal usage over time).
3. Attacker sends a trigger with a tiny `trigger.output[[asset=$mm_asset]]` amount such that `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` is small enough that `round($investor_share * balance[$asset])` (and/or the bytes payout) evaluates to `0`.
4. In `aa_composer.js`, the zero-amount payment output(s) are filtered out per lines 1274-1278; if not every message becomes empty, the `state` message survives filtering (line 1281) and executes, decrementing `var['mm_asset_outstanding']` by the attacker's already-transferred `mm_asset` amount.
5. The attacker's share tokens are consumed/burned (already sent to the AA as part of the trigger) and the outstanding-share accounting is reduced, but the attacker receives no payment output — a permanent loss of their share value with no bounce/revert.
