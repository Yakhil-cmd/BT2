### Title
Webhook signature is verified against `repository.owner.login`/`organization.login`, but event handlers act on the unverified `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The report's bug class ("a field that is authenticated versus a field that is acted on differ") maps onto how Shipit verifies inbound GitHub webhooks. `WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to check against based on `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` with a fallback to `params.dig('organization', 'login')`. Once the signature passes, the *entire* raw payload — including a separate `repository.full_name` field — is handed unchanged to the registered `Shipit::Webhooks` handlers, which use `repository.full_name` (via `Handler#repository_name`) to resolve the target `Stack`/`Repository`, with no re-check that this field's owner matches the organization whose secret validated the request.

### Finding Description
`verify_signature` computes the authenticating organization purely from the JSON body: [1](#0-0) [2](#0-1) 

The signature itself is only checked using the org's configured `webhook_secret`, resolved through `Shipit.github(organization: repository_owner)`: [3](#0-2) 

But the actual target-resolution logic used by every default handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, pull-request handlers) is based on a *different* field, `repository.full_name`, via the shared `Handler` base class: [4](#0-3) 

`Repository.from_github_repo_name` parses `owner/name` straight out of that field with no cross-check against the value that was used to select the signing secret: [5](#0-4) 

Because Shipit supports multiple organizations configured in `Shipit.github` (each with its own independent `webhook_secret`), the binding that should hold is: **organization whose secret authenticated the request == owner of the repository the handler writes to**. Nothing in the controller or `Handler` enforces this equality. An entity that legitimately controls the webhook configuration/secret for one registered organization (org A) — e.g. because they administer org A's GitHub App installation in a shared multi-tenant Shipit instance — can craft an arbitrary raw JSON body, set `repository.owner.login` (or `organization.login`) to `"orgA"` so `verify_signature` selects and validates against org A's own secret, while independently setting `repository.full_name` to `"orgB/some-repo"`. The signature check only validates that the byte string was signed with org A's secret; it says nothing about which repository the embedded `full_name` claims to be. The forged request then flows into `PushHandler#process` / `StatusHandler#process` etc., which act on stacks belonging to org B.

### Impact Explanation
This breaks the trust boundary between organizations in a shared Shipit deployment: an actor authorized only for org A's GitHub App/webhook secret can forge events that mutate state scoped to org B's repositories/stacks — e.g. forcing `Stack#sync_github` (push event) or forging arbitrary commit statuses via `Commit#create_status_from_github!` (status event, matched by `sha` with no owner scoping at all) for stacks under a different, non-authorized organization. Depending on the host application's continuous-delivery/status-gating configuration, forged deployable statuses can influence whether merges/deploys are permitted, which constitutes an unauthorized cross-repository write and a form of authentication-boundary bypass matching the "organization that authenticated versus the repository that is written" analog class named in the rules.

### Likelihood Explanation
Requires the attacker to already possess a legitimate `webhook_secret` for at least one organization configured in the same multi-org Shipit instance (a low but real bar for anyone administering their own org's GitHub App integration), and requires the Shipit instance to be configured with more than one organization sharing the deployment. Given that, no further privilege (no Shipit session, no `ApiClient` token, no repository write access to the target org) is needed — only the ability to POST a self-crafted, self-signed payload to the `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, enforce that the organization used to validate the signature is the same organization embedded in the field(s) the handler will act on (e.g., assert that `repository.full_name.split('/').first == repository_owner` before dispatching, or derive both values from a single canonical field). Consider also scoping `StatusHandler`'s `Commit.where(sha: params.sha)` lookup by the verified repository/organization rather than matching on `sha` alone across all repositories.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` in `Shipit.github`.
2. Attacker controls (or has legitimately configured) `orgA`'s webhook secret.
3. Attacker builds a raw JSON body for a `push` event: `{"ref": "refs/heads/main", "after": "<attacker-chosen sha>", "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/target-repo"}}`.
4. Attacker computes `X-Hub-Signature` as `sha1=HMAC(orgA_webhook_secret, body)` and sends it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"orgA"` from `repository.owner.login`, fetches `Shipit.github(organization: "orgA")`, and the HMAC check succeeds (signed with the real orgA secret).
6. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves via `Repository.from_github_repo_name("orgB/target-repo")` — a stack the attacker was never authenticated for — and calls `stack.sync_github(expected_head_sha: ...)`. [6](#0-5) [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
