### Title
Recalculation of partitioned stake rewards after a snapshot restore reads the live (attacker-mutable) `StakesCache` delegation amount instead of the frozen epoch-boundary snapshot, causing cross-node bank-hash divergence - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`Bank::recalculate_stake_rewards` (invoked from `recalculate_partitioned_rewards_if_active`, called on snapshot restore) recomputes each pending stake account's reward from `self.stakes_cache.stakes()` at the *current* slot rather than from a value frozen at the original epoch-boundary calculation. An attacker who owns a stake account can `Split`/`Merge` it between the calculation block and their partition's payout block, changing the live `stake.delegation.stake` that feeds directly into the reward-points numerator (`calculate_alpenglow_points` / `calculate_stake_points_and_credits`). If a validator restarts during the distribution window, its recalculated `stake_reward` for that account will differ from the value already frozen in `all_stake_rewards` on validators that never restarted, producing account-lamport (and therefore bank-hash) divergence between nodes for the same slot.

### Finding Description
The reward pipeline is split into two phases:

1. **Calculation** (epoch boundary): `Bank::calculate_rewards_for_partitioning` → `calculate_stake_rewards_and_commissions` reads `stake_delegations` from `self.stakes_cache.stakes()` *at the epoch-boundary block* and computes each stake's `stake_reward`, freezing the whole set into `Arc<PartitionedStakeRewards>` (`all_stake_rewards`) stored in `EpochRewardStatus::Active(Calculation)` [1](#0-0) .

2. **Distribution** (subsequent blocks): under normal operation `distribute_partitioned_epoch_rewards`/`store_stake_accounts_in_partition` simply pays out the *already-frozen* `partitioned_stake_reward.inflation.stake_reward` from `all_stake_rewards`, so a stake account's later mutation (Merge/Split) does not change its payout amount in the non-restart path [2](#0-1) .

However, if the node restarts during the distribution window, `initialize_after_snapshot_restore` calls `recalculate_partitioned_rewards_if_active`, which calls `Bank::recalculate_stake_rewards` [3](#0-2) [4](#0-3) .

`recalculate_stake_rewards` re-derives `stake_delegations` via `get_epoch_params_for_recalculation`, which pulls `stakes.stake_delegations_vec()` from `self.stakes_cache.stakes()` — the *live, current* StakesCache, not a snapshot of the state that existed at the original calculation block [5](#0-4) [6](#0-5) .

Only the *denominator* — `RewardEpochDelegatedStakes` (the AG per-vote-account total delegated stake) — is explicitly preserved as a frozen input via `AlpenglowEpochType::get(self, rewarded_epoch, || RewardEpochDelegatedStakes::get(self))`, as demonstrated by the dedicated regression test `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` [7](#0-6) . The *numerator* input — each individual stake account's own `stake.delegation.stake` — is **not** frozen; it is read fresh from the live `StakesCache` at recalculation time and fed directly into `calculate_alpenglow_points`:

```
let stake_amount = u128::from(delegation_effective_stake(&stake.delegation, ...));
...
earned_credits * stake_amount / total_stake as u128
``` [8](#0-7) 

An attacker who owns a stake account with a pending (unpaid) partitioned reward can submit an ordinary, unprivileged `StakeInstruction::Split` or `StakeInstruction::Merge` transaction against their own account any time after the Calculation block but before their own partition is distributed. This directly changes `stake.delegation.stake` in the live `StakesCache` (via `StakesCache::check_and_store`/`upsert_stake_delegation`) [9](#0-8) . Nothing in `distribute_partitioned_epoch_rewards`, `calculate_stake_rewards_and_commissions`, or the stake program itself blocks Merge/Split while `EpochRewardStatus::Active`; no `get_reward_interval()`/`RewardInterval` check gates stake-program instruction processing in `runtime/src/bank.rs`. If a validator subsequently restarts (a normal operational event — software upgrade, crash recovery, etc., not requiring attacker control of the node) before that account's partition is paid, `recalculate_stake_rewards` will compute a different `stake_reward` for the mutated account than the value already frozen (and already used by non-restarted peers) in `all_stake_rewards`. This causes the restarted node to store a different post-reward lamport balance for that stake account than peers that did not restart, at the same slot/partition — a bank-hash mismatch.

### Impact Explanation
This is cross-node state divergence at consensus level: two honest validators processing the identical block sequence produce different account states (and thus different bank hashes) for the same slot, purely because one of them restarted mid-epoch-reward-distribution and an attacker mutated their own stake account in the interim. This falls into the "cross-node state divergence" / "epoch-boundary halt" bounty category explicitly permitted in scope, since a bank-hash mismatch on a supermajority-divergent set of validators can halt the cluster or fork it. It is also a misattributed-reward bug (the attacker's own account is over- or under-paid relative to the frozen calculation), though the primary severity driver is the potential for a duplicate/inconsistent bank hash across nodes.

### Likelihood Explanation
Preconditions are all attacker-controlled and require no privileged access: the attacker only needs to own a stake account (and its withdraw/stake authority) with a nonzero pending reward in the current epoch's `all_stake_rewards`, and to submit a normal `Merge` or `Split` instruction naming that account before its partition's block height is reached. The only non-attacker-controlled variable is a validator restart during the (multi-block) distribution window, which is a common real-world event (deploys, crashes, planned restarts) rather than a rare corner case, especially since distribution can span many blocks (`REWARD_CALCULATION_NUM_BLOCKS`/`get_reward_distribution_num_blocks`). The existing regression test explicitly protecting the AG *denominator* across restart, while leaving the per-account *numerator* unprotected, indicates this is a real gap rather than already-mitigated behavior.

### Recommendation
Freeze the per-account stake-delegation inputs used for reward numerator calculation at the original Calculation block, the same way `RewardEpochDelegatedStakes` freezes the denominator. Concretely, when persisting `EpochRewardStatus::Active(Calculation)`/`Distribution`, also snapshot (or make `recalculate_stake_rewards` re-derive results strictly from) the stake-delegation state as of the original calculation slot rather than `self.stakes_cache.stakes()` at recalculation time — e.g., by storing the calculation-time `stake_delegations` (or the already-computed `all_stake_rewards` entries) and using those verbatim for any pending/unpaid stake instead of recomputing from the live cache. Alternatively, disallow `Merge`/`Split` (and other instructions that mutate `stake.delegation.stake`) on stake accounts that have an unpaid partitioned reward while `EpochRewardStatus::Active`.

        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,

        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while

        // have not yet been distributed.

        // post_lamport amount if the commission account is NOT the vote account,
