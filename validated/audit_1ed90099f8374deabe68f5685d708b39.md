Found a genuine binding break: `Deploy#build_rollback` never filters the caller-supplied `env` against the stack's permitted rollback variable whitelist, even though every other env-accepting path (`Stack#trigger_task`, `Stack#build_deploy`) does.

### Title
Rollback environment variables bypass the `shipit.yml` variable whitelist and are injected into deploy scripts unfiltered - (File: app/models/shipit/deploy.rb)

### Summary
`Api::RollbacksController#create` sanitizes user-supplied `env` via `stack.filter_rollback_envs(params.env)` [1](#0-0)  before calling `deploy.trigger_rollback(current_user, env: rollback_env, ...)`. However, `Task#trigger_revert_if_required`, invoked from the `Deploy` state machine on abort, calls `trigger_rollback` / `trigger_revert` with a raw `env:` that is **never passed through `filter_rollback_envs`**, and `Deploy#build_rollback` stores `env: env.to_h` directly with no whitelist check at all [2](#0-1) , unlike `Stack#build_deploy` which explicitly calls `filter_deploy_envs(env.to_h)` [3](#0-2)  and `Stack#trigger_task` which calls `definition.filter_envs(env)` [4](#0-3) .

### Finding Description
The binding that should hold is: `env keys permitted by shipit.yml's rollback.variables (or fallback deploy.variables) == env keys spawned into the rollback's shell process`. `EnvironmentVariables#permit` is the only enforcement point of this binding, raising `NotPermitted` for any key not in the variable whitelist [5](#0-4) .

`Deploy#build_rollback` breaks this binding by persisting `env: env.to_h` verbatim [2](#0-1) . This method is reachable through `trigger_rollback`, which is called with an unfiltered `env` from `trigger_revert_if_required` — a private callback fired `after_transition to: :aborted` whenever `rollback_once_aborted?` is set, using `rollback_once_aborted_to.trigger_rollback(aborted_by, env:, force: true)` [6](#0-5) . The `env` value used there is the aborted task's own `env` column (`self.env`, i.e. whatever was stored on the original deploy/task), not something re-validated against the *rollback* variable whitelist.

Since a rollback's `TaskCommands#env` merges `@task.env` last, with no `.slice`/whitelist call at the `Command` execution layer [7](#0-6) , any key present in the (unfiltered) `env` column reaches the spawned shell process directly and can also be used for `$VAR` interpolation into shell arguments via `Command#interpolate_environment_variables` [8](#0-7) .

### Impact Explanation
This breaks the "environment key permitted by shipit.yml vs environment key spawned into the executed process" binding described in the rules. Because `filter_rollback_envs`/`EnvironmentVariables.permit` is the only gate preventing arbitrary environment variables from being injected into deploy/rollback shell commands, bypassing it on the auto-triggered revert path allows environment keys that were never declared in `rollback.variables` (or `deploy.variables`) to be exported into the rollback's shell environment and interpolated into deploy script arguments — a mechanism the whitelist exists specifically to prevent (per `EnvironmentVariables::NotPermitted`). Concretely, whatever `env` was already accepted on a Deploy (which was validated against *deploy* variables, not rollback variables, and originated potentially from a different, less restrictive Stack) is carried over unchecked into a rollback that should be validated against `rollback_variables`.

### Likelihood Explanation
Reaching this path requires no special privilege beyond normal `deploy:stack` permission to trigger a deploy with `rollback_once_aborted: true` and then abort it (a documented, standard flow — `active_task.abort!(aborted_by:, rollback_once_aborted_to:, rollback_once_aborted: true)` in `RollbacksController#create` itself sets this up) [9](#0-8) . It does not require a Shipit session with elevated scope, a GitHub App key, or repository write access — only a deploy-permitted `ApiClient`/user, which is within the intended threat model of "unprivileged attacker."

### Recommendation
Filter `env` through `stack.filter_rollback_envs` (or the applicable variable definitions) inside `Deploy#build_rollback` itself, so the whitelist is enforced at the single choke point regardless of caller, rather than relying on every caller (controller, state-machine callback) to filter before calling `trigger_rollback`/`trigger_revert`.

### Proof of Concept
1. Configure `shipit.yml` with a restrictive `rollback.variables` list (e.g., only `FORCE`), while `deploy.variables` allows a broader set including a sensitive key like `DEBUG_HOOK_URL`.
2. Trigger a deploy through `Api::DeploysController`/`Stack#build_deploy` with `env: {"DEBUG_HOOK_URL" => "http://attacker.example/exfil"}` (valid under deploy variables), and set it up with `rollback_once_aborted: true`.
3. Abort that deploy (`PUT /api/stacks/:id/tasks/:id/abort` equivalent, or `active_task.abort!`), which invokes `Task` state machine → `Deploy#trigger_revert_if_required` → `trigger_rollback(aborted_by, env: self.env, force: true)` → `build_rollback` storing `env.to_h` unfiltered.
4. Observe that the generated `Rollback` task's `env` contains `DEBUG_HOOK_URL`, even though it is not declared in `rollback.variables`, and that `TaskCommands#env` for the rollback merges it in, making it available to the rollback's shell commands — bypassing the whitelist enforced everywhere else (`RollbacksController#create`'s explicit `filter_rollback_envs` call, `Stack#trigger_task`'s `filter_envs` call).
