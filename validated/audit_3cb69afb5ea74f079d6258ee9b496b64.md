### Title
Webhook signature verification authenticates the payload's `organization`/`repository.owner`, not the `repository.full_name` that handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository_owner`, computed purely from the attacker-supplied JSON body (`repository.owner.login` or, as a fallback, `organization.login`). Once the signature check passes, `create` dispatches the *entire raw JSON body* to event handlers, which independently determine which tracked `Repository`/`Stack` to mutate using a different JSON path: `repository.full_name`. Nothing binds these two fields together, so the organization whose secret authenticated the request is not guaranteed to be the repository that ends up acted upon.

### Finding Description
`verify_signature` picks the app/secret to check the signature against like this: [1](#0-0) 

and `repository_owner` is read straight from the unauthenticated request body: [2](#0-1) 

The HMAC verification itself, in `GitHubApp#verify_webhook_signature`, is a no-op when no `webhook_secret` is configured for that resolved organization: [3](#0-2) 

Once `verify_signature` passes (status not set to 422), `create` forwards the whole parsed body to all registered handlers for the event, unmodified: [4](#0-3) 

But every handler resolves the repository/stack to act on from a *separate* field, `repository.full_name`, via the shared base class: [5](#0-4) 

and this name is looked up with no re-validation against the org that satisfied the signature check: [6](#0-5) 

Concrete handlers (e.g. `PushHandler`) then directly enqueue jobs like `sync_github` against whatever `Stack`/`Repository` that lookup returns: [7](#0-6) 

Shipit explicitly supports multiple GitHub App configurations, one per organization, each with its *own, optional* `webhook_secret` (documented as "Webhook secret (optional)"), keyed by the top-level org name in `secrets.github`: [8](#0-7) 

Because `repository_owner` (used only to pick the verifying secret) and `repository.full_name` (used to pick the repository that is actually written to) are two independently attacker-controlled strings in the same unauthenticated JSON body, the "organization that authenticated" and the "repository that is written" are not the same equality that the signature check is meant to enforce. Concretely: `verify(secret_of(payload.organization.login)) == true` does **not** imply `payload.repository.full_name belongs_to payload.organization.login`.

### Impact Explanation
In a multi-organization Shipit deployment, if any one configured organization has no `webhook_secret` set (permitted by design/docs), an unauthenticated attacker can:
1. POST to the public `/webhooks` endpoint with `X-Github-Event: push` (or `status`, `check_suite`, `pull_request`, etc.).
2. Set `repository.owner.login` (or `organization.login`) to the org that has no secret configured, so `verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`), with no signature needed at all.
3. Set `repository.full_name` to a completely different, actively-tracked repository belonging to a *different, secret-protected* organization.

The event handler for that event type never checks that `full_name`'s owner matches the organization that satisfied step 2, so it will act on the victim repository: e.g. `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` for the victim's stacks, `StatusHandler` will forge commit statuses, `pull_request` handlers can archive/unarchive review stacks or manipulate PR-driven provisioning behaviour — all without possessing the victim organization's `webhook_secret`, an `ApiClient` token, or any GitHub credentials. This is an authentication-bypass class issue against stack state (unauthenticated write of stack/commit/PR state), matching the High-impact category ("escalation into authorization boundaries / unauthenticated read/write of stack/task state").

### Likelihood Explanation
Exploitability requires only that the deployment has at least one configured GitHub organization without a `webhook_secret` — a configuration explicitly called out as optional in the setup documentation, not a hardening failure introduced by the operator beyond following the documented default. No GitHub credentials, `ApiClient` token, repository write access, or session are needed; the `/webhooks` route is intentionally public and unauthenticated aside from the HMAC check this bug undermines. The only "skill" required is crafting a raw JSON POST with mismatched `organization`/`repository.owner` vs. `repository.full_name` fields.

### Recommendation
Bind the two identities cryptographically instead of trusting them independently:
- Require every configured organization to have a non-blank `webhook_secret` (remove the `return true unless webhook_secret` bypass in `GitHubApp#verify_webhook_signature`), or
- After signature verification succeeds for `repository_owner`, assert that `payload.dig('repository', 'full_name')` (and `params.dig('organization','login')`, if present) is prefixed by / equal to the same `repository_owner` before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
Assume a Shipit instance configured with two organizations in `secrets.github`: `no-secret-org` (no `webhook_secret`) and `victim-org` (has a `webhook_secret`, and a repository `victim-org/prod` tracked with a stack on `master`).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, no secret configured for no-secret-org

{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "organization": { "login": "no-secret-org" },
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "victim-org/prod"
  }
}
```

- `repository_owner` resolves to `"no-secret-org"` → `Shipit.github(organization: "no-secret-org")` → `verify_webhook_signature` returns `true` unconditionally (no secret configured).
- `PushHandler#process` computes `stacks` from `Repository.from_github_repo_name("victim-org/prod")`, finds the real tracked stack, and calls `stack.sync_github(expected_head_sha: "deadbeef")` — an unauthenticated actor has now driven sync/deploy-adjacent state for `victim-org/prod` despite never possessing `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
