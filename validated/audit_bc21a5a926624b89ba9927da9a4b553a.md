### Title
AA payment messages sending fixed-denomination assets are silently dropped, permanently trapping such assets sent to an AA - ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) in ocore can receive any asset, including assets defined with `fixed_denominations: true`. However, `aa_composer.js`'s response-composition logic (`sendUnit`) explicitly skips normal input/output composition for fixed-denomination assets and then unconditionally filters out any `payment` message that targets such an asset from the AA's response unit, without any fallback mechanism to actually move the asset using its denomination-based inputs. Any AA author who writes an oscript intending to forward, refund, or otherwise redistribute a fixed-denomination asset it received will have that specific `payment` message silently dropped at execution time, and the balance stays stuck in the AA forever since there is no other path to spend it.

### Finding Description
When an AA composes its response messages in `sendUnit`, for a payment message whose `asset` is loaded and found to have `fixed_denominations`, the code intentionally does *not* run `completePaymentPayload` (which selects UTXOs/denominations and fills in `payload.inputs`) — it just calls back immediately: [1](#0-0) 

Then, after all messages have been processed, there is a second-pass filter that unconditionally removes ANY payment message referencing a fixed-denomination asset from the messages array, regardless of what the AA's oscript intended to do with it: [2](#0-1) 

If that filtering results in zero remaining messages, the code takes the "successful empty response" path, silently discarding the entire response (including any state changes the author wanted to accompany the payment) and eating the received coins: [3](#0-2) 

Because indivisible/fixed-denomination assets require selecting specific denomination-valued inputs (unlike divisible base/asset payments handled by `completePaymentPayload`), the AA composer has no code path capable of spending them at all — there is no analog of `completePaymentPayload` for denomination selection inside `aa_composer.js`. Consequently, any `payment` message an AA author writes for a fixed-denomination asset is guaranteed to be dropped every single time the AA executes, with no error surfaced to the trigger sender (the response unit is composed successfully, just without that message). Balances of fixed-denomination assets accumulate in `aa_balances` for the AA address (as tracked by `updateFinalAABalances` reading from `objUnit.messages`, which never contains the dropped message) but can never be paid out through any AA logic, since every attempt is filtered before finalization.

This directly parallels the reported analog: a distribution/fund-forwarding routine that iterates/handles a subset of value types (ERC20 balances) but has no mechanism for a different value type (native ETH) that the contract can nonetheless receive — funds of that type become permanently stuck. Here, the AA payment-composition pipeline handles "regular" assets and base coins via `completePaymentPayload`, but has no equivalent mechanism for fixed-denomination assets, and instead of failing loudly or bouncing, it silently strips the corresponding message from the response.

### Impact Explanation
Any AA that is designed to receive and later re-distribute, refund, or forward a fixed-denomination asset (a legitimate, definable asset type reachable by any unprivileged asset issuer via the standard `asset` message with `fixed_denominations: true`) will permanently lose the ability to move that asset out once it is inside the AA. Since AAs are commonly used to build custodial/exchange/vault-style contracts (as shown by asset-issuance and forwarding samples in the codebase, e.g., `test/samples/fundraising_proxy.oscript` and `test/samples/uniswap_like_market_maker.oscript`), any AA logic layered on top of a fixed-denomination asset would result in an irrecoverable freeze of user funds held by the AA — this is a fund-loss/fund-freezing bug qualifying as Medium/High impact per the given criteria (AA fund loss or freezing), reachable purely by posting a normal trigger unit or issuing a fixed-denomination asset and sending it to an AA.

### Likelihood Explanation
This is deterministic, not probabilistic: any oscript `payment` message referencing an asset that turns out to have `fixed_denominations: true` is unconditionally dropped every time that code path executes, with no configuration needed to trigger it beyond the trigger sender or AA author choosing to interact with such an asset. No malicious actor coordination or special network conditions are needed — a single unprivileged asset issuer defining a fixed-denomination asset and sending it to any AA is sufficient to reproduce the loss.

### Recommendation
Either: (1) reject AA execution with a bounce (rather than silently dropping the message and returning a "successful" empty response) whenever a `payment` message targets a fixed-denomination asset, so the trigger fails cleanly and funds are refunded to the sender/left untouched at the AA's boundary instead of being accepted and then trapped; or (2) implement proper denomination-selection logic in `aa_composer.js` (an analog of `completePaymentPayload` that works with `denominations` inputs) so that AAs can legitimately transfer fixed-denomination assets they hold.

### Proof of Concept
1. Issue an asset `X` with `fixed_denominations: true` and appropriate `denominations` (any unprivileged asset issuer can do this).
2. Deploy an AA whose oscript, upon receiving asset `X` from a trigger, responds with a `payment` message forwarding/refunding asset `X` back to the trigger address (a legitimate oscript pattern, cf. `test/samples/fundraising_proxy.oscript`'s refund case for a regular asset, adapted to a fixed-denomination one).
3. Send a unit that triggers the AA with an output in asset `X`.
4. In `sendUnit`, the message referencing asset `X` is skipped from `completePaymentPayload` at [1](#0-0)  and then removed entirely by the filter at [2](#0-1) .
5. Observe that the AA's response unit contains no payment of asset `X` back to the sender, while `aa_balances` for the AA still shows the received `X` balance credited (per `updateFinalAABalances`) — the asset is now permanently locked in the AA with no oscript path able to move it out.
