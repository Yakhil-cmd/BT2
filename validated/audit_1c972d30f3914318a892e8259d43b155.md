### Title
Webhook signature verified against the organization named in the payload while handlers act on the (independently attacker-controlled) repository full_name from the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the request against by reading an *unverified* field out of the request body itself: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves to a distinct `GitHubApp` config entry (and thus a distinct `webhook_secret`) per organization key, as configured under the multi-app `github:` section documented in `docs/setup.md` (`Using Multiple Github Applications`). This is confirmed by `lib/shipit.rb#github_app_config`, which does `secrets.github.deep_transform_keys(&:downcase)[organization.downcase.to_sym]`.

Once the signature check passes, the *event handlers* (e.g. `PushHandler`, `Handlers::Handler#stacks`) resolve the actual repository to act on using a **different** field of the same JSON body — `repository.full_name` — via `Repository.from_github_repo_name(repository_name)`: [3](#0-2) 

Both `repository.owner.login` (used for auth/secret-selection) and `repository.full_name` (used for the write target) live in the same attacker-controlled JSON body, and nothing enforces that `full_name`'s owner segment matches `repository.owner.login`. Because HMAC verification only proves "the body was signed with organization X's secret," not "the acted-upon repository belongs to organization X," an attacker who knows the `webhook_secret` for *any one* organization configured in a multi-tenant Shipit instance can forge a signed payload where `repository.owner.login` = their own known org (to pass signature verification) while `repository.full_name` = a victim org/repo that is also configured in the same Shipit instance. This breaks the intended binding: **organization that authenticated == repository that is written**.

### Impact Explanation
This allows cross-organization forged GitHub events: an entity that legitimately controls one GitHub App/organization's webhook secret in a multi-org Shipit deployment can trigger `GithubSyncJob`/`sync_github` (`PushHandler`), fabricate commit statuses (`StatusHandler`), or manipulate check runs/pull-request driven review-stack provisioning (`CheckSuiteHandler`, `PullRequest::*Handler`) for a repository belonging to a *different, unrelated* organization, without possessing that organization's webhook secret, an `ApiClient` token, or Shipit session. This is a cross-repository/cross-organization write achieved purely by exploiting the signature-selection/action-target mismatch, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
The precondition is that the Shipit instance is configured with the documented multi-organization `github:` schema (explicitly supported and documented in `docs/setup.md`), and that the attacker legitimately controls at least one of the configured GitHub Apps/orgs (e.g., a business unit or partner org onboarded to the shared Shipit instance). Given multi-tenant setups are a first-class, documented configuration, this is a realistic deployment pattern, though it does not affect single-org Shipit deployments (the common case), which lowers overall likelihood.

### Recommendation
When selecting the webhook secret for verification, also validate — after signature verification succeeds — that the resolved `github_app`'s organization actually matches the owner of the repository the handlers are about to act on (i.e., cross-check `repository.owner.login` against `repository.full_name`'s owner segment, or better, resolve the target `Repository`/`Stack` first and then verify against *that* stack's configured organization's secret instead of a value plucked from the unverified payload).

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. Attacker legitimately owns the GitHub App for `attacker-org` and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw JSON body and POSTs to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature (since it was signed with that exact secret).
6. `PushHandler#process` resolves the target via `repository.full_name` = `"victim-org/victim-repo"`, and `Repository.from_github_repo_name` finds and acts on `victim-org`'s stacks — triggering `GithubSyncJob` for a repository the attacker has no authorization over.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
