### Title
Uncaught exception in private-payment duplicate-check crashes the node on a re-sent divisible private payment - (File: private_payment.js)

### Summary
`validateAndSavePrivatePaymentChain()` in `private_payment.js` performs a "check if duplicate" query before validating and saving an incoming private payment chain. For divisible (non-fixed-denomination) private assets, the duplicate-check SQL query intentionally omits the `output_index` filter, so it can legitimately return more than one row once a multi-output divisible private payment has already been saved. The code treats `rows.length > 1` as an "impossible" condition and does `throw Error(...)` instead of returning it through the `callbacks.ifError` chain. Because this throw happens inside a raw asynchronous `conn.query` callback (not a promise, no surrounding try/catch), Node.js treats it as an uncaught exception and terminates the whole process.

### Finding Description
In `private_payment.js`: [1](#0-0) 

For an indivisible (`fixed_denominations`) asset, `output_index` is added to the `WHERE` clause, guaranteeing at most one matching row. For a divisible asset, no such filter is applied, so the SQL `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` matches every output row belonging to that payment message. A normal divisible private payment message can have multiple outputs (e.g., a payment output plus a change output), which `divisible_asset.js`'s `validateAndSaveDivisiblePrivatePayment` inserts in one batch: [2](#0-1) 

Once such a multi-output message has been saved once (2+ rows now exist for that `unit`+`asset`+`message_index`), any subsequent delivery of a private-payment chain element referencing the *same* unit/asset/message_index (e.g., retransmission via a hub, resend by counterparty, or a maliciously repeated/duplicated `private_payment` device message or `light/private_payment` catch-up message) causes the duplicate-check query to return more than one row, hitting the unconditional `throw Error("more than one output ...")` at line 74-75. This throw occurs synchronously inside the low-level DB driver's query callback with no enclosing `try/catch`, so it becomes an uncaught exception that crashes the entire Node.js process (wallet or hub), not just the current request.

This is directly reachable by: (a) any private-payment counterparty sending a divisible private payment (e.g., to a wallet or hub) more than once, (b) a light client re-syncing/re-delivering the same private chain via `handleSavedPrivatePayments`/`network.js` catch-up path, or (c) a malicious peer intentionally re-sending an already-accepted `private_payment` message to a target node — all normal, unprivileged actions requiring no special network position, matching the "private-payment counterparty" reachable actor class in scope.

### Impact Explanation
An uncaught exception thrown from a database-callback in Node.js is fatal by default: it unwinds past all promise/callback boundaries and crashes the entire process. For a full node/hub this means denial of service for every user connected to it (network unable to process/confirm new units until manually restarted); for a wallet it kills the user's own wallet process. Because this is trivially reproducible by re-delivering payment data that is otherwise completely valid (not even malformed), it is a reliable, repeatable crash primitive rather than a rare edge case.

### Likelihood Explanation
High. Multi-output divisible private payments (payment + change output) are the normal case for private-asset spending, so this is not a contrived edge case. Duplicate delivery of a `private_payment` message is a routine occurrence in this codebase's design (the hub relays private payments to multiple devices, light wallets resync/backfill private chains, and peers can legitimately resend), and there is even an explicit "duplicate private payment" handling path right below the throw — showing that duplicate delivery is an anticipated, common event that the assertion was supposed to (but fails to) also handle safely for the divisible-asset, multi-output case.

### Recommendation
Add the missing `output_index` disambiguation (or otherwise deduplicate) for divisible-asset outputs in the "check if duplicate" query so that it can never legitimately return more than one row, and replace the `throw Error(...)` assertion with a normal `transaction_callbacks.ifError(...)` (or equivalent recoverable error path) so that any unexpected inconsistency is reported instead of crashing the process. More generally, audit `conn.query(...)` callbacks reachable from attacker/counterparty-controlled network or device-message input for bare `throw Error(...)` statements, since none of them are protected by a surrounding try/catch and each represents a full-process DoS vector.

### Proof of Concept
1. Alice and Bob are correspondent devices; Alice sends Bob a divisible private-asset payment whose payment message has two outputs (e.g., payment output to Bob + change output back to Alice), producing a unit `U` with `message_index=M`.
2. Bob's node processes the incoming `private_payment` device message normally via `network.handleOnlinePrivatePayment` → `private_payment.validateAndSavePrivatePaymentChain`, which stores 2 rows in `outputs` for `(unit=U, asset=A, message_index=M)`.
3. Alice (or the hub relaying store-and-forward messages, or a malicious peer replaying captured traffic) re-sends the identical `private_payment` chain for `(U, A, M)` to Bob a second time.
4. Bob's node re-enters `validateAndSavePrivatePaymentChain`, runs the duplicate-check query `SELECT ... FROM outputs WHERE unit=U AND asset=A AND message_index=M` (no `output_index` filter since the asset is divisible), gets back 2 rows, and executes `throw Error("more than one output ...")` inside the `conn.query` callback.
5. The exception is uncaught, and Bob's wallet/hub process crashes immediately, denying service to Bob (and, if Bob runs a hub, to every connected user) until manually restarted.
