Now I have the full picture of the webhook signature-to-payload binding.

### Title
Multi-organization webhook signature verification is keyed on `repository.owner.login`/`organization.login`, but event processing is keyed on `repository.full_name`, letting a holder of one organization's webhook secret forge events for a repository owned by a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to use for HMAC verification by extracting the *organization* login from the payload: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
``` [2](#0-1) 
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature is accepted, event dispatch and stack resolution never re-check the organization at all — they resolve the target purely by `repository.full_name`: [3](#0-2) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

The equality that is supposed to hold is: **"organization whose secret authenticated the request" == "organization that owns the repository being acted on"**. This binding is only checked implicitly by trusting that `repository.owner.login` and `repository.full_name` inside the *same* signed payload are consistent — GitHub itself guarantees that. But this engine's `verify_signature` derives the org from `repository.owner.login`, while every handler resolves the target stack from `repository.full_name`. This engine supports being configured for *multiple* organizations, each with its own `Shipit.github(organization: X)` / `webhook_secret` (`lib/shipit.rb#github`, `github_app_config`): [4](#0-3) 

### Finding Description
This is the direct analog of the UniV3 "fee treated as wildcard" bug: the field that is *checked* (`repository.owner.login` used to pick the HMAC key) is not the same field that is *acted upon* (`repository.full_name` used to resolve the `Stack`/`Repository` to mutate). In the UniV3 case, `details.fee == 0` silently widened the accepted-fee set to "any fee." Here, the verification step widens trust to "any payload whose `repository.owner.login` matches an organization I have a valid signature for," while the mutation step trusts a *different, unverified-as-bound* field (`full_name`) to decide which repository/stack is affected.

Concretely: `GithubHook.any_instance.stubs(:verify_signature)`/fixtures show membership events are verified using the top-level `organization.login` fallback branch, while push/status/pull_request events use `repository.owner.login`. Because `repository_owner` and `stacks`/`repository_name` are computed from two different, independently-settable JSON paths in the raw POST body, and the *only* cryptographic binding is the raw-body HMAC computed over the whole payload with **one** organization's secret, the security property that "verifying with org A's secret implies the payload may only affect org A's repositories" holds **only as long as GitHub itself always sends `repository.owner.login` and `repository.full_name` referring to the same owner** — i.e., it depends entirely on the honesty of whoever holds a valid `webhook_secret` for *some* configured organization, not of the specific organization being written to.

### Impact Explanation
If Shipit is configured with the multi-organization `github:` schema (`lib/shipit.rb#github_app_config`, `docs/setup.md`) and an operator (or a compromised/malicious member with delivery access) obtains the `webhook_secret` for organization A, they can craft a payload with `repository.owner.login: "org-a"` (to pass signature verification against org A's secret) while setting `repository.full_name: "org-b/some-repo"` (to target a stack that belongs to organization B). This would let a party trusted only for organization A's webhooks trigger `GithubSyncJob`, membership/team creation, or `RefreshCheckRunsJob` against organization B's stacks — i.e., a cross-repository/cross-organization write bypassing the very isolation the multi-tenant secret system was designed to enforce.

### Likelihood Explanation
This requires knowledge of one organization's `webhook_secret` in a multi-org Shipit deployment. The engine explicitly supports and documents this multi-org configuration (`config/secrets.development.example.yml` shows the multi-org `github:` schema), so it is a supported, non-hypothetical deployment mode, not "host application not mounting the engine as documented." An attacker still needs a single org's `webhook_secret` (which is lower-privilege than repository write access or a Shipit API token), making this a genuine privilege-boundary crossing between "trusted for org A's webhooks" and "can write to any repository."

### Recommendation
After signature verification succeeds, re-derive the organization from the same field used for verification (`repository.owner.login`) and enforce that it matches the owner encoded in `repository.full_name` before dispatching to handlers, or better, verify the payload against the webhook secret of the organization actually referenced by `repository.full_name` (single source of truth), rejecting the request if the two disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org example).
2. Obtain `org-a`'s `webhook_secret` (e.g., as a member permitted to configure org-a's GitHub App webhook).
3. Craft a `push` event JSON payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled sha already known to Shipit>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
4. Sign the raw body with `org-a`'s `webhook_secret` and send it to `/webhooks` with header `X-Hub-Signature: sha1=<hmac>`.
5. `WebhooksController#verify_signature` computes `repository_owner == "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the HMAC validates successfully.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — a write triggered by a party who was only ever authenticated for `org-a`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
