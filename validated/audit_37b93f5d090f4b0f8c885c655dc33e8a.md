### Title
Scope-restricted ApiClient can read any stack's CC-Menu status via CCMenuController's `stack` override - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` overrides `Api::BaseController#stack`/`#stacks` and resolves `params[:stack_id]` against the unscoped `Stack` relation instead of the client-scoped `stacks` relation. `require_permission :read, :stack` only checks that `read:stack` is present in `current_api_client.permissions`, never that `params[:stack_id]` equals `current_api_client.stack_id`, so a client restricted to one stack can read any other stack's CC-Menu status.

### Finding Description
The binding that must hold is: `permission checked` (`current_api_client.permissions.include?('read:stack')`) `== permission needed` (`read:stack` for the specific stack identified by `params[:stack_id]`, i.e. `current_api_client.stack_id == stack.id` when the client is scoped). `ApiClient#check_permissions!` only implements the first half: [1](#0-0) 

The scoping-to-stack half is implemented centrally in `BaseController`, via `stacks`/`stack`: [2](#0-1) 

`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves `params[:stack_id]` against that restricted relation - this is what makes the equality hold for `TasksController`, `CommitsController`, `MergeRequestsController`, and `LocksController`, all of which inherit `stack`/`stacks` unmodified.

`CCMenuController` breaks this by redefining `stack` to bypass the scoped `stacks` relation entirely: [3](#0-2) 

`require_permission :read, :stack` (line 6) still only calls `check_permissions!(:read, :stack)`, which is a pure permissions-array check. The `stack` method (lines 29-31) resolves `params[:stack_id]` against `Stack.from_param!` on the entire `Stack` table, not `stacks.from_param!`. Consequently, any `ApiClient` whose `permissions` include `read:stack` - regardless of its own `stack_id` - can pass `stack_id` for any other stack in the URL and get a 200 with that stack's CC-Menu XML (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`).

Attacker request: authenticate as an `ApiClient` (token obtained legitimately for stack A, e.g. via the CCMenu-URL flow at `CCMenuUrlController#fetch`) with `permissions: ['read:stack']`, then `GET /api/stacks/:owner/:repo-for-stack-B/ccmenu?token=<token>`. Because `stack` never checks `current_api_client.stack_id`, the request succeeds for stack B's data even though the client was only meant to see stack A.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters`, `force_github_authentication`, model validations) are irrelevant here - the only relevant guard, `require_permission!`/`check_permissions!`, is present but insufficient, and the compensating scoping logic (`stacks`) that other controllers rely on is explicitly overridden/bypassed in this controller.

### Impact Explanation
A stack-scoped `ApiClient` (e.g., a CCMenu client auto-created by `CCMenuUrlController#fetch` for a specific stack, which is granted only `read:stack`) can read build/deploy status of any stack in the Shipit instance, not just the one it was created for - deploy activity, last build status/label/time, and the stack's web URL. This is an unauthorized cross-tenant read of stack state, matching the High-severity bucket "unauthenticated/unauthorized read of stack state." It is fully repeatable against any stack ID reachable in the routes, for as long as the attacker holds any valid `read:stack` token.

### Likelihood Explanation
The attacker needs a valid `ApiClient` token with `read:stack` permission - this is not a high privilege in this system; the built-in CCMenu integration itself creates such clients for any authenticated Shipit user via `CCMenuUrlController#fetch`, and the same token type is usable by anyone who can obtain one (e.g., any user with an account, or anyone who intercepts/holds a CCMenu URL/token). No GitHub secrets, webhook signing keys, or admin roles are required. The only action is a single crafted `GET` request substituting an arbitrary `stack_id`; this is trivially repeatable across all stacks.

### Recommendation
In `Api::CCMenuController`, remove the local `stack` override (or change it to route through the scoped `stacks` relation from `BaseController`), e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the same client-scoping guarantee (`current_api_client.stack_id`) that `TasksController`, `CommitsController`, etc. already rely on.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a client scoped to another stack cannot read this stack's cc_menu" do
  other_stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
  @client.update!(permissions: ['read:stack'], stack_id: other_stack.id)

  get :show, params: { stack_id: @stack.to_param, token: @client.authentication_token }

  # binding under test: current_api_client.stack_id (other_stack.id) != requested stack (@stack.id)
  assert_response :forbidden # currently fails: response is :ok, leaking @stack's CC-Menu data
end
```
