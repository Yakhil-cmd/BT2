### Title
Pool creator can be set to an unclaimable address in `initialize_with_permission`, permanently freezing creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` accepts `creator` as an arbitrary `UncheckedAccount` that is never validated to be a signer, never validated to equal the `payer`, and never validated against `Pubkey::default()`. This value is stored directly as `pool_state.pool_creator` while `enable_creator_fee` is hard-coded to `true`, so creator fees begin accruing on every swap for a fee recipient the caller fully controls — including an address nobody can ever sign for. This is the same root-cause pattern as the reported bug: a positive fee parameter is allowed to persist alongside an unreachable/zero fee recipient, permanently burning the accrued fees.

### Finding Description
In `Initialize` (permissionless pool creation), `pool_creator` is always set to the `creator` `Signer`, so it is guaranteed to be a valid, controllable key [1](#0-0) .

In `InitializeWithPermission`, however, `creator` is declared as an `UncheckedAccount` with no signer requirement and no constraint tying it to `payer` [2](#0-1) . The instruction then writes this attacker-supplied value straight into `pool_state.pool_creator`, and hard-codes `enable_creator_fee = true` (the last argument) regardless of who `creator` is: [3](#0-2) 

Once the pool is live, every swap accrues a `creator_fee` amount into `pool_state.creator_fees_token_0/1` via `update_fees`, gated only by the `enable_creator_fee` flag — not by whether `pool_creator` is a real, reachable address: [4](#0-3) 

Collection of these fees is strictly bound to `pool_creator`:
- `collect_creator_fee` requires the signer to equal `pool_state.pool_creator` exactly [5](#0-4) .
- `collect_creator_fee_permissionless` allows anyone to trigger collection, but the tokens are still sent to an ATA owned by `creator` (i.e., `pool_creator`) [6](#0-5) .

If the pool creator (the `payer`, who must hold a `Permission` PDA to call this instruction) sets `creator` to `Pubkey::default()` or any other address with no known private key, no one can ever produce a valid `Signer` for `collect_creator_fee`, and the permissionless variant will only ever deposit fees into an ATA owned by that unclaimable key. The `creator_fee_rate` set in `AmmConfig` (analogous to `feeMantissa`) is positive and active, but the designated recipient (`pool_creator`, analogous to `feeRecipient`) is unreachable — funds accrue and are permanently locked, exactly mirroring the reported bug class.

### Impact Explanation
Creator fees accumulated on every swap through this pool become permanently unrecoverable (frozen/burned funds), since no valid signer exists for `pool_creator` and the permissionless collection path only relocates the funds into an equally unreachable token account. This is a real loss of value extracted from swappers via the creator-fee component of the trade fee, with no path to recovery — a concrete permanent freezing of funds impacting anyone who trades through the pool.

### Likelihood Explanation
Reaching this requires only a single transaction to `initialize_with_permission` by any account holding a valid `Permission` PDA (an in-scope, explicitly listed reachable instruction), with `creator` set to an attacker-chosen unreachable pubkey. No elevated protocol-admin privilege (`crate::admin::ID`) is needed — only possession of a `Permission` account, which is the intended precondition for calling this instruction. The `creator_fee_rate` need only be non-zero in the referenced `AmmConfig` (a normal operating configuration), and `enable_creator_fee` is unconditionally `true` in this code path.

### Recommendation
Require `creator` to be a `Signer` in `InitializeWithPermission` (mirroring `Initialize`), or explicitly disallow `creator == Pubkey::default()` and require it to sign or otherwise prove ownership before allowing `enable_creator_fee = true`. Alternatively, allow `pool_creator` to be updated later by a signed instruction so misconfigured/unreachable recipients can be corrected before fees accumulate.

### Proof of Concept
1. Attacker (or any account with a `Permission` PDA obtained via `create_permission_pda`) calls `initialize_with_permission`, passing `creator = Pubkey::default()` (or any address they don't control) while `payer` is their own signer.
2. Instruction succeeds: `pool_state.pool_creator` is set to the unreachable address, `enable_creator_fee` recorded as `true`. [3](#0-2) 
3. Users perform swaps on the pool; each swap adds to `pool_state.creator_fees_token_0`/`creator_fees_token_1` per `update_fees`. [4](#0-3) 
4. `collect_creator_fee` can never be called because no signer can match `pool_state.pool_creator == Pubkey::default()`. [5](#0-4) 
5. `collect_creator_fee_permissionless` can technically be invoked, but it only moves the accrued fees into an ATA owned by the unreachable `creator` key, so the funds remain permanently inaccessible. [6](#0-5)
