### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for the `prevent_with_label` branch due to missing parentheses - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` combines four conditions with `&&`/`||` without parentheses grouping `review_stacks_enabled` across all disjuncts. Because `&&` binds tighter than `||` in Ruby, `review_stacks_enabled` is only ANDed with the `allow_all?` branch, leaving the `allow_with_label?` and `prevent_with_label?` branches reachable even when review stacks are disabled for the repository.

### Finding Description
The broken binding: the code implies `review_stacks_enabled == (value gating all three provisioning_behavior branches)`, but the actual parsed expression is:

```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
``` [1](#0-0) 

`review_stacks_enabled` is not consulted at all for the `prevent_with_label` (and `allow_with_label`) disjuncts. With `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, opening a PR with no label makes `provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?` evaluate to `true`, so `provision?` returns `true` regardless of `review_stacks_enabled`.

Exploit flow: an attacker who owns/controls a repository connected to Shipit (or any repo where they can open PRs and GitHub delivers the correctly-signed webhook) sets `provisioning_behavior` to `prevent_with_label` (attacker doesn't even need to set this — whoever configured the repo with `review_stacks_enabled: false` + `prevent_with_label` is exposed) and opens a PR without the provisioning label. `process` calls `respond_to_pull_request_opened?` → `provision?` → `true`, then invokes `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` row via `scope.create!(stack_attributes)` and calls `Shipit::ReviewStackProvisioningQueue.add(stack)` to enqueue it for provisioning, despite the repository having review stacks disabled. [2](#0-1) [3](#0-2)  The queue worker then calls `stack.provisioner.provision?` and `stack.provision` on the created row [4](#0-3) , which drives the checkout/build machinery used for legitimate stacks (task execution against the repository's code).

Existing guards do not prevent this: webhook signature verification (`verify_signature`) only confirms the payload came from GitHub for the linked repository — it does not enforce the `review_stacks_enabled` policy, since that check is purely internal application logic in `provision?`. `NullRepository` correctly hard-codes `review_stacks_enabled` to `false` and all provisioning-behavior predicates to `false`, but this only matters for unknown repos, not for the vulnerable branch discussed here.

### Impact Explanation
For any repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, an unlabeled PR causes Shipit to create a `ReviewStack` and enqueue it for provisioning — a feature the operator explicitly disabled. This leads to unauthorized stack creation and subsequent provisioning/checkout task execution against that repository, which the operator believed was turned off. This is repeatable per-PR and confined to repositories with this specific configuration; it does not cross tenant/repository boundaries (the `scope: repository.review_stacks` ties the created stack to the same repository). Severity aligns with "an unauthorized deploy/provisioning action occurring against a repository that did not authorize it," matching a Critical/High-leaning logic flaw, though it is bounded to the misconfigured repository itself rather than cross-tenant.

### Likelihood Explanation
Preconditions: a repository must have `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (a real, supported configuration combination per the `PROVISIONING_BEHAVIORS` enum and `review_stacks_enabled` flag) [5](#0-4) . No secrets are required by the attacker beyond the ability to open a PR on a repo that is already integrated with this Shipit instance and receives real GitHub webhooks. Attacker cost is a single unlabeled PR open event; fully repeatable.

### Recommendation
Add explicit parentheses to `provision?` so `review_stacks_enabled` gates every disjunct:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
minitest plan (non-test-dir description, to be added under `test/`):
```ruby
test "provision? does not trigger when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: 'prevent_with_label')

  params = pull_request_opened_params(repository: repository, labels: [])
  handler = Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(params)

  assert_no_difference -> { Shipit::ReviewStack.count } do
    handler.process
  end
end
```
Before the fix: `Shipit::ReviewStack.count` increases by 1 and `Shipit::ReviewStackProvisioningQueue.add` is invoked (assert via mock/stub `Shipit::ReviewStackProvisioningQueue.expects(:add)` never called), demonstrating `review_stacks_enabled: false` is bypassed. After applying the parenthesization fix, `provision?` returns `false` and no `ReviewStack` or queue entry is created.
