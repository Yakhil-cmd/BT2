### Title
Webhook signature verification selects the GitHub App secret from an unverified field, decoupling the authenticated organization from the repository the event acts upon - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using a value taken directly from the still-unverified JSON body, while the actual event-processing code (`Handler#repository_name`) reads a *different* field of that same unverified body to decide which `Stack`/`Repository` the event acts on. Nothing ties these two fields together, so in a multi-organization Shipit deployment an attacker who knows (or has leaked) one organization's `webhook_secret` can sign a payload that authenticates as that organization but whose `repository.full_name` targets a stack belonging to a different, victim organization/repository configured in the same Shipit instance.

### Finding Description
`verify_signature` derives the organization used to look up the verification secret from the payload itself, before the signature has been validated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` selects a `GitHubApp` instance (and its `webhook_secret`) keyed by `repository_owner`, which is `params.dig('repository','owner','login')` or `params.dig('organization','login')` — both attacker-supplied fields inside the raw JSON body whose signature has not yet been checked at this point in the request lifecycle. `verify_webhook_signature` then HMACs the raw body against that org's secret: [3](#0-2) 

Once the signature check succeeds (using whatever secret corresponds to the attacker-chosen `repository_owner`/`organization.login`), the *entire* raw body — including a completely independent field, `repository.full_name` — is handed unchanged to the registered webhook handlers: [4](#0-3) 

Handlers such as `PushHandler` resolve which `Stack`s to act on purely from `repository.full_name`, with no cross-check against the organization that was used to authenticate the request: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` looks up the target `Repository`/`Stack` purely by the owner/name parsed out of `repository.full_name`, independent of which GitHub App/org secret validated the request: [7](#0-6) 

This breaks the intended binding: `organization authenticated by verify_signature` == `repository/stack the handler code actually writes to`. Multi-organization support is a documented, first-class configuration (`Shipit.github(organization:)` keyed lookups, `secrets_double_github_app.yml`), so a Shipit instance hosting stacks for `OrgA` and `OrgB` with distinct `webhook_secret`s is a realistic reachable configuration: [8](#0-7) 

### Impact Explanation
An attacker who has obtained (e.g. via a leak, misconfiguration, or a compromised low-privilege organization's GitHub App settings) the `webhook_secret` for **one** organization configured in a shared Shipit instance can forge a webhook whose `X-Hub-Signature` validates against that organization's secret, while setting `repository.full_name` (and the push/status/check_suite payload fields) to reference a **different** organization's repository/stack hosted on the same Shipit instance. This lets the attacker trigger `GithubSyncJob`, commit status updates, check-run refreshes, or merge/lock-related webhook side effects against a repository/stack they have no legitimate access to — an unauthorized cross-repository state change driven entirely by forged, unauthenticated-for-that-repo webhook traffic. This matches the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
This requires: (1) a Shipit deployment configured with multiple GitHub organizations/apps (a supported, documented configuration), and (2) the attacker knowing one organization's `webhook_secret` without knowing the victim organization's secret. Obtaining a single low-value organization's webhook secret (e.g., a sandbox/test org) is plausible and does not require repository write access, an `ApiClient` token, or session access, keeping this within the unprivileged-attacker constraint. The bug is a structural/logic flaw (verification key selection and target-resolution key are different, unlinked payload fields), not a probabilistic or environment-dependent issue, so once the prerequisite secret is obtained, exploitation is deterministic.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the authorized organization strictly from the *verified* body and enforce that `repository.owner.login` (or `organization.login`) used for signature selection matches the owner encoded in `repository.full_name` before dispatching to handlers. Alternatively, have `Handler#repository_name`/`stacks` resolution take the already-authenticated organization as an explicit, separate parameter (not re-derived from the same unverified body) and reject events whose repository owner does not match the organization whose secret validated the signature.

### Proof of Concept
1. Deploy Shipit with two organizations configured, e.g. `OrgA` (secret `S_A`) and `OrgB` (secret `S_B`), each with their own stacks, per `config/secrets.development.example.yml`'s multi-org schema.
2. Attacker knows `S_A` (e.g., leaked from a low-security sandbox org) but not `S_B`.
3. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "organization": { "login": "OrgA" },
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_A, body)` and POSTs to `/github/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`), verifies successfully against `S_A`.
6. `create` dispatches the full body to `Shipit::Webhooks.for_event('push')`, and `PushHandler#stacks` resolves the target via `Repository.from_github_repo_name('OrgB/victim-repo')`, enqueuing `GithubSyncJob` for `OrgB`'s stack — despite the request never having been authenticated by `OrgB`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
