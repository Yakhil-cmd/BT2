### Title
Untrusted route payload executes attacker-chosen contract code beneath the caller's authorization, draining unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2019-1010200 is an OS-command injection: attacker-supplied query parameters reach a shell `exec` and run arbitrary commands. The on-chain analog exists in the controller's strategy verbs. `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`/`flash_position` all accept a caller-supplied `swap: Bytes` route and forward it verbatim to the swap aggregator, which invokes whatever pool and token addresses the payload names. The router keeps no allowlist of those addresses, so a route embeds arbitrary contract code that executes inside a call tree rooted at the victim's signed authorization. A malicious hop contract can then issue `token.transfer(victim, attacker, amount)` on any token the victim holds; the host records that call as a child of the victim's `swap_collateral` auth entry, standard transaction simulation produces exactly that tree, and a wallet that signs it loses the funds — none of it bounded by the payload's min-out, the controller's risk gates, or the swap amounts.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-38` authorizes only one exact input transfer to the router, then calls `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is user-supplied bytes. The controller checks only its own balance deltas (`RouterOverspend`, `NoSwapOutput` at lines 40-54) — it constrains what happens to the *controller's* balances, not what the routed code does to the *caller's* authorization tree.

Inside the router, `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs:23-40`) dispatches to venue adapters that call `env.invoke_contract(&ctx.hop.pool, ...)` where `hop.pool` and `hop.token_in/token_out` are arbitrary addresses decoded from the payload (`StrategyPayload.assets`), with no allowlist (documented in `docs/explanation/threat-model.md:154-165`: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization").

Because `swap_collateral`/`swap_debt`/`repay_debt_with_collateral` open with `caller.require_auth()`, the victim's signature is the root authorization for the entire call stack. Any nested `token.transfer(victim, to, amount)` performed by route-selected code is recorded by the host as a `sub_invocation` of that root entry and executes if the signed tree includes it. The dedicated test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves both halves: simulation records the rogue pool's wallet transfer under the caller's `swap_collateral` entry (lines 194-227), and enforcement mode moves the victim's full `WALLET_BALANCE` of an unlisted, unrelated token to the attacker exactly when the simulated tree is signed (lines 229-269).

The injected code is not limited to one transfer: the route can name multiple hops/pools, and anything reachable under the victim's `require_auth` — transfers of every token the wallet holds, NFT transfers, arbitrary sub-invocations the wallet is authorized for — can be appended to the recorded tree.

### Impact Explanation
Theft of user funds. The victim loses tokens entirely unrelated to the lending position — the test drains 77,770 units of a token the protocol never listed. The stolen amount is bounded only by the victim's wallet balances, not by `amount_in`, `amountOutMin`, or the account's health factor; the swap itself can still produce a fair-looking output so the position passes all post-action risk gates and the transaction succeeds.

### Likelihood Explanation
High in the phishing/blind-signing threat model. Any party that can feed a route to a victim — a malicious or compromised quote path, a doctored frontend, a social-engineered `swap_collateral`/`multiply` transaction — can embed the rogue hop. Standard `simulateTransaction`-based preparation automatically generates the poisoned auth tree (recording mode accepts non-root `require_auth`), so a wallet that signs "what simulation returned" authorizes the theft without any visible extra step. No protocol privilege, leaked key, or oracle manipulation is required; the attacker needs only to supply bytes and a deployed hop contract.

### Recommendation
- At the contract layer, the controller cannot fully fix this because the auth-tree shape is decided at signing time, but it can narrow exposure: accept only venue-pinned routes, or require a governance-registered venue/pool allowlist consulted before forwarding `swap` (the threat model notes the router currently keeps none).
- Operationally, wallets and the quote pipeline must decode `routeXdr` and reject any simulated authorization tree containing children beyond the single expected `token_in.transfer` (the verifier in `skills/xoxno-swap-aggregator/payload.md` checks payload fields but should also diff the simulated auth tree against the honest baseline).
- Document for integrators that `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, and `flash_position` inherit the same exposure, so client-side auth-tree verification must wrap every strategy verb, not just standalone `execute_strategy`.

### Proof of Concept
The repository ships an executable PoC: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

- `UnlistedPoolRouter` (lines 34-48) stands in for the aggregator and invokes `route.hop_pool` — the address named inside the attacker-built `RoutedSwap` XDR.
- `RogueHopPool` (lines 51-71) is the injected "command": on `swap` it calls `token::Client::transfer(victim, attacker, amount)` on an unrelated wallet token.
- `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194-227): Alice calls `Controller::swap_collateral` with the malicious route; the recorded auth tree contains her root `swap_collateral` entry with the rogue `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child, and her wallet balance goes to 0 while the attacker receives `WALLET_BALANCE` — all while her position still receives a fair `FAIR_OUT_ETH` output.
- `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (lines 229-269): with the honest root-only tree the transfer is rejected and the call reverts; signing the simulation-produced tree authorizes the theft. This confirms the only barrier is client-side verification of the auth tree — the protocol's own checks do not stop it.
