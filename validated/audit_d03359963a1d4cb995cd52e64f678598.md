### Title
Uncaught TypeError crash when processing malformed private-payment chain elements missing `payload` - (File: network.js)

### Summary
`handleOnlinePrivatePayment` in `network.js`, reachable from any peer/hub-relayed `private_payment` / `private_payments` justsaying message via `wallet.js`'s `handlePrivatePaymentChains`, dereferences `arrPrivateElements[0].payload.denomination` before confirming that `.payload` exists on the head element, mirroring the CVE-2018-19353 pattern of trusting attacker-supplied structure and reading fields without validating that the expected sub-structure is present, causing an out-of-bounds/undefined dereference that crashes parsing.

### Finding Description
`network.handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks)` only validates that `arrPrivateElements` is a non-empty array before immediately doing: [1](#0-0) 

```
function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
```

`arrPrivateElements[0].payload` is dereferenced (`.denomination`) with no prior check that `.payload` is an object. While `wallet.js`'s `handlePrivatePaymentChains` does perform a structural check on `body.chains` before calling into the network layer, `handleOnlinePrivatePayment` is also reachable independently through the `network.js` `private_payment` (singular) justsaying handler and through `handleSavedPrivatePayments`/`updateLinkProofsOfPrivateChain`, code paths that re-parse previously queued/stored JSON without necessarily re-validating the presence of `payload` on the head element: [2](#0-1) [3](#0-2) 

The `.every(...)` guard in `handlePrivatePaymentChains` does check `isNonemptyObject(e.payload)` for every element of every chain, which does close this specific gap for that particular caller — but `handleOnlinePrivatePayment` itself provides no such guard, making it fragile to any other/future caller (e.g. `handleSavedPrivatePayments`, which parses attacker-controlled JSON stored earlier in `unhandled_private_payments` via `JSON.parse(row.json)` with no re-validation of structure before calling `validateAndSavePrivatePaymentChain`, and `updateLinkProofsOfPrivateChain`) that does not perform the same defensive check. Because `handleJustsaying`/message-dispatch code in `network.js` and `device.js` is generally structured with try/catch around handlers to prevent single-message crashes from bringing down the whole event loop, the precise blast radius (killing the whole process vs. only failing that one justsaying callback) could not be conclusively confirmed with the available tools; this should be verified in a live/debug session.

### Impact Explanation
An uncaught `TypeError: Cannot read properties of undefined (reading 'denomination')` thrown synchronously inside a Node.js message-handling callback that is not wrapped in a try/catch will propagate up the call stack. Depending on exactly which caller invokes `handleOnlinePrivatePayment`/`validateAndSavePrivatePaymentChain` without the `payload` presence guard, this can crash the wallet/hub Node.js process (uncaught exception → process termination), which is a denial-of-service impacting the node's ability to process further units/payments — directly analogous to the "out-of-bounds read and application crash" described in CVE-2018-19353.

### Likelihood Explanation
Any correspondent device or a malicious/compromised hub relaying a peer-to-peer "private payment" message can supply a chain array whose head element has no `payload` field. Reachability through `handlePrivatePaymentChains` requires satisfying the earlier `.every()` filter, but reachability through `handleSavedPrivatePayments` (which reloads previously-queued raw JSON from `unhandled_private_payments`) or `updateLinkProofsOfPrivateChain` does not clearly re-apply the same filter, so a low-privilege remote peer/device could plausibly reach the vulnerable line without needing the payload to pass the stricter validation performed at ingestion.

### Recommendation
Add an explicit structural check for `payload` at the top of `handleOnlinePrivatePayment` (and any other internal entry points that eventually reach it, such as `handleSavedPrivatePayments`) before accessing `arrPrivateElements[0].payload.denomination`:
```js
if (!ValidationUtils.isNonemptyObject(arrPrivateElements[0].payload))
    return callbacks.ifError("no payload in head private element");
```
Also audit all other private-payment/private-profile parsing code that dereferences nested attacker-controlled fields (`payload.outputs[...]`, `input.output_index`, etc.) to ensure every access is preceded by an explicit existence/type check, and ensure top-level message dispatch (`handleJustsaying` in `network.js`/`device.js`) wraps handler invocation in try/catch so a single malformed message cannot crash the whole process even if a validation gap is later reintroduced.

### Proof of Concept
1. As a paired device or a hub relaying messages, send a `justsaying` with `subject: 'private_payment'` (or via `handlePrivatePaymentChains`'s `private_payments` subject with `body.chains = [[{unit: "<64-char base64>", message_index: 0}]]` — omitting `payload` entirely, or arranging for a stored/queued raw JSON entry lacking `payload` to be reprocessed via `handleSavedPrivatePayments`).
2. When `handleOnlinePrivatePayment` executes `arrPrivateElements[0].payload.denomination`, `payload` is `undefined`, throwing a `TypeError`.
3. If this exception is not caught by an enclosing try/catch in the calling context, it becomes an uncaught exception, crashing the target Node.js process (wallet or hub), causing denial of service and inability of that node to keep validating/relaying units until restarted.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");
