### Title
Cross-Organization Commit Status Forgery via Unscoped `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook by looking up the GitHub App/secret for a single organization derived from the payload, but the handler that actually mutates state (`StatusHandler`) writes to *any* `Commit` row in the database whose `sha` matches, without checking that the commit belongs to a repository owned by the organization that was cryptographically verified. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects the `GithubApp` (and therefore the HMAC secret) used to validate `X-Hub-Signature` based on `repository_owner`, which is read straight from the payload: [1](#0-0) [2](#0-1) 

Once the signature is confirmed to have been produced with *that organization's* `webhook_secret`, the raw params are dispatched to every registered handler for the event with no further repository/organization scoping: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up commits purely by SHA, across the whole `commits` table, and writes a GitHub-supplied status onto every match: [4](#0-3) 

Unlike `PushHandler` and `CheckSuiteHandler`, which scope their side effects through `Handler#stacks`/`Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [5](#0-4) 

`StatusHandler` never consults `repository_name`/`stacks` at all, so the repository field that was part of the signed payload (and used to pick the verifying organization) plays no role in deciding which `Commit` rows get mutated.

Because Shipit is explicitly designed to host multiple independent GitHub organizations behind one instance, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`), a legitimate but unprivileged member of Organization A can:
1. Obtain (or construct) a commit in their own repository whose SHA1 collides with, or is chosen to equal, a target commit's SHA tracked by Organization B's stack (git SHA1s are computable offline; an attacker fully controls tree, parents, author, committer and timestamp of their own commit, making an intentional match to a target public/forked commit feasible), or more simply target a monorepo/fork scenario where the same commit SHA is legitimately synced into multiple `Repository`/`Stack` rows tracked by Shipit.
2. Trigger a real `status` webhook from GitHub for their own Organization A repository/commit. GitHub signs this webhook with Organization A's real `webhook_secret`, so `verify_webhook_signature` succeeds using the App configured for `repository_owner = "orgA"`.
3. `StatusHandler#process` then updates `Commit.where(sha: params.sha)` — which is not restricted to Organization A's repositories — so if Organization B (a different, unrelated tenant of the same Shipit install) has a `Commit` row with that SHA, its CI status gets overwritten with attacker-controlled `state`/`context`/`description` data, even though the signature only proved authorization for Organization A.

### Impact Explanation
This is a cross-repository write: an entity cryptographically authenticated only for repositories under Organization A can mutate commit-status records that belong to Stacks under Organization B. `Commit#create_status_from_github!` feeds into the `ci.require` gating documented in `README.md` ("`ci.require` ... disallow deploys if any of them is missing on the commit"), so forged success statuses can satisfy the CI-readiness check enforced before a deploy is allowed, undermining the deploy-safety guarantee tied to signature verification and enabling downstream unauthorized deploys of a commit that never actually passed the target organization's CI.

### Likelihood Explanation
Requires the attacker to control a repository behind any GitHub App configured on the same Shipit instance (a normal, low-privilege scenario in a shared/multi-tenant Shipit deployment) and to produce a colliding or matching SHA for a target commit. This is non-trivial for arbitrary targets (git SHA1 pre-image/collision), but becomes realistic in common setups: monorepos, mirrored/forked repositories, or shared history across stacks where the exact same commit SHA is legitimately present in multiple `Repository` rows tracked by the same Shipit instance — a scenario the code makes no attempt to prevent because `StatusHandler` performs no repository-scoping at all, unlike its sibling handlers.

### Recommendation
Scope `StatusHandler#process` to the repository identified in the verified payload, mirroring `Handler#stacks`, e.g. restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any `Commit` row, so a verified organization can only ever write statuses for commits inside its own repositories.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (as shown possible in `config/secrets.development.shopify.yml`).
2. Ensure Shipit tracks a `Stack`/`Commit` for `orgB/repo` with a known SHA `deadbeef...`.
3. As a low-privileged collaborator on `orgA/repo`, craft/push a commit in `orgA/repo` whose SHA1 equals `deadbeef...` (achievable when targeting shared/forked history, or by controlling all SHA1 inputs for a chosen target ahead of time) and set a commit status on it via the GitHub API.
4. GitHub sends a `status` webhook to Shipit signed with `orgA`'s `webhook_secret`. `WebhooksController#verify_signature` succeeds because `repository_owner` resolves to `orgA` and the signature matches `orgA`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the `orgB` commit row (same SHA), and calls `create_status_from_github!`, overwriting `orgB`'s commit status — despite the request never being authenticated for `orgB`.
