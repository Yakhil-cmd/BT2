### Title
Unvalidated swap routes can inject unauthorized token transfers into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller’s strategy entrypoints accept attacker-constructed `swap` bytes and forward them unchanged to the configured aggregator while the caller’s authorization remains active. [1](#0-0) [2](#0-1)  A malicious route can therefore place arbitrary route-selected contract code beneath the caller’s `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` authorization and request unrelated token transfers from that caller. [3](#0-2) 

### Finding Description
`swap_tokens` only checks that `swap` is non-empty, snapshots the controller’s input and output balances, authorizes exactly one input-token transfer from the controller to the router, and invokes `execute_strategy(controller, amount_in, swap)`. [2](#0-1)  After execution, it bounds only the controller’s own input spend and measured output receipt; it does not constrain what the payload causes other contracts to request under the original caller’s authorization. [4](#0-3)  The router ABI accepts the payload as opaque `Bytes`, so the controller has no route-structure validation point before the payload executes. [3](#0-2)  `swap_collateral` reaches this path after only caller and account authorization and destination-listing checks. [5](#0-4) 

### Impact Explanation
A malicious route can add a nested token transfer from the victim to an attacker-controlled address while still returning enough output for the lending operation to satisfy the controller’s positive-output and final account-risk checks. [4](#0-3)  If simulation records that child invocation and the victim signs the resulting authorization tree, the injected transfer executes and steals wallet assets unrelated to the lending position. [3](#0-2)  The routed collateral itself is bounded by the exact controller authorization, but the injected child authorization is not bounded by that transfer’s amount. [6](#0-5) 

### Likelihood Explanation
An unprivileged attacker can deploy route-selected code and supply or publish a malicious route; the victim only has to invoke an affected strategy with that payload and sign the authorization tree produced by simulation. [1](#0-0)  No privileged role, oracle manipulation, upgrade, or protocol liquidity is required. [7](#0-6)  Exploitation requires the victim to authorize the poisoned tree, so it is not an unconditional remote theft and fits Medium severity. [8](#0-7) 

### Recommendation
Require the swap executor to use a bounded venue allowlist and enforce that route hops invoke only approved pool/token functions with arguments derived from the declared route. Clients should additionally decode the submitted route, simulate the exact transaction, reject any authorization child other than the expected controller input transfer, and display all nested token transfers before signing.

### Proof of Concept
1. Deploy a malicious pool contract that exposes the route hop’s expected swap function but also calls `token::transfer(victim, attacker, victim_wallet_balance)` for an unrelated token held by the victim.
2. Construct a `StrategyPayload` whose `assets` identify an honest input token, an honest output token, and the malicious pool address, and whose instruction stream dispatches the swap through that pool.
3. Have the victim invoke `Controller::swap_collateral(victim, account_id, current_asset, amount, new_asset, malicious_swap_xdr)`. [1](#0-0) 
4. The controller authorizes only the intended input-token transfer to the router, then calls `execute_strategy` with the opaque payload. [9](#0-8) 
5. During router execution, the malicious pool calls the unrelated token’s `transfer`; simulation attaches this invocation as a child of the victim’s `swap_collateral` authorization.
6. If the victim signs that tree, the unrelated-token transfer executes, while the route’s nominal output can still make `received > 0` and allow the controller’s measured-output check to pass. [10](#0-9)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
