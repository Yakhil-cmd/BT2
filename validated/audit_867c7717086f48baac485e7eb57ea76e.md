### Title
Cross-organization webhook forgery: repository owner used for signature verification does not bind to the repository whose stacks are mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on one field of the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), while every webhook `Handler` subclass resolves the actual repository/stack to mutate from a *different* field of the same body (`repository.full_name`). These two fields are never cross-checked against each other, so a payload can be signed correctly for organization A while acting on a repository belonging to organization B.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) [2](#0-1) 

using `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` to pick which org's `Shipit.github(organization: ...)` (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature` against the raw body.

Once the signature check for that claimed organization succeeds, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs, and every handler resolves the target repository independently: [3](#0-2) 

i.e. `repository_name = payload.dig('repository', 'full_name')`, used by `Repository.from_github_repo_name(repository_name)` to locate the `Stack`(s) that the handler acts on (e.g. `PushHandler#process` calling `stack.sync_github(...)`): [4](#0-3) 

The binding that should hold is:
`organization authenticated via repository.owner.login (or organization.login) == owner of repository.full_name acted upon`

Because Shipit supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`, `lib/shipit/github_app.rb` initializing `@webhook_secret` per-organization config), this equality is a hard security requirement: the webhook secret proves the payload came from GitHub for a specific, single organization's installation. Nothing in the controller or in `Handler#repository_name` enforces that `repository.full_name`'s owner segment matches `repository_owner`/`organization.login` used to select the secret. Since the entire JSON body is attacker-controlled prior to signature verification (the signature only proves the raw bytes match a valid HMAC for the org named by `repository.owner.login`), an attacker who legitimately controls (or has valid webhook delivery/secret access for) organization A can set `repository.owner.login = "A"` (satisfying the signature check against A's secret) but `repository.full_name = "B/victim-repo"` (targeting a stack that belongs to a completely different, unrelated organization B configured on the same Shipit instance).

### Impact Explanation
This breaks the authorization boundary between separately configured GitHub organizations on a multi-tenant Shipit instance: an attacker with legitimate signing capability for one organization can forge webhook events (`push`, `status`, `check_suite`, pull_request events, etc.) that are dispatched against another organization's `Stack` records purely because the two "which org" fields inside the payload are decoupled. Depending on the handler this enables cross-repository writes such as forcing `Stack#sync_github` on a foreign repo, injecting forged commit statuses that influence merge-queue decisions (`schedule_merges`), or altering pull-request/review-stack state (archiving/unarchiving stacks, capturing labels) for a repository the attacker has no legitimate relationship with. This matches the "cross-repository writes" / "unauthenticated read of stack state" high/critical impact class, since it lets a party trusted only for org A perform state-changing operations against org B's stacks.

### Likelihood Explanation
Exploitation requires the attacker to possess valid HMAC signing capability for at least one organization configured on the Shipit instance (e.g., control of a legitimate GitHub App installation/webhook secret for org A). This is a real-world condition on any Shipit deployment serving multiple organizations (as documented and tested in `secrets_double_github_app.yml`), which is an explicit supported configuration, not a hypothetical one. No repository write access or session token is required — only the ability to deliver an HTTP POST with a matching signature for one org while claiming a different org's repository.

### Recommendation
In `WebhooksController#verify_signature`, and in `Handler#repository_name`/`stacks`, cross-validate that the organization/owner used to select the webhook secret matches the owner segment of every repository reference used later to resolve stacks (e.g., require `repository.full_name.split('/').first == repository_owner`, or resolve the target `Repository`/`Stack` scoped to the authenticated organization rather than trusting `repository.full_name` verbatim). Reject the webhook if these fields diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker with access to `OrgA`'s webhook secret (e.g., a legitimate but low-trust integrator for OrgA), craft a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` using `OrgA`'s webhook secret over the raw body.
4. POST to `/github/webhooks` (routed to `WebhooksController#create`). `verify_signature` resolves `repository_owner = "OrgA"`, verifies successfully against `OrgA`'s secret.
5. `PushHandler#process` resolves `repository_name = "OrgB/victim-repo"` via `Handler#repository_name`, looks up `Repository.from_github_repo_name("OrgB/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "deadbeef")` on a stack belonging to `OrgB`, despite the request never being validated by `OrgB`'s secret.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
