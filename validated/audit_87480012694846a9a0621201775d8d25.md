### Title
Cross-organization webhook forgery via signature/repository binding mismatch in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to check the `X-Hub-Signature` against using the `repository.owner.login` (falling back to `organization.login`) field from the JSON body, but the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Stack`/`Repository` using the independent `repository.full_name` field. Because these two fields are never cross-checked against each other, a caller who knows the `webhook_secret` for *any* one organization configured on the Shipit instance can produce a validly-signed request whose `repository.owner.login` matches that known-secret org, while setting `repository.full_name` to point at a stack belonging to a *different* organization managed by the same Shipit instance.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` picks the `GitHubApp` (and therefore the secret used to verify `X-Hub-Signature`) purely from the payload: [1](#0-0) [2](#0-1) 

The signature is computed over the *raw* request body via HMAC, so it does authenticate the payload content — but it only proves the request was signed by the holder of the secret belonging to `repository_owner`, not that `repository_owner` matches the repository the handler will subsequently act on.

The handler that performs the state-changing action resolves the repository from a *different* field, `repository.full_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

Because Shipit explicitly supports hosting multiple GitHub organizations from a single instance, each with its own app/secret configuration: [6](#0-5) 

...an attacker who is the legitimate owner/admin of one onboarded organization (call it OrgA, whose `webhook_secret` they know because they configured the GitHub App for it) can craft an HTTP POST directly to `/webhooks` with:
- `repository.owner.login = "OrgA"` (so `verify_signature` authenticates against OrgA's known secret and passes),
- `repository.full_name = "OrgB/victim-repo"` (an unrelated org/repo also hosted on the same Shipit instance),
- a valid `X-Hub-Signature` computed with OrgA's own secret over that exact body.

This satisfies `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) even though the payload's *acted-upon* repository (`full_name`) has nothing to do with the organization whose secret was used to authenticate it. The `push` handler will then run `stack.sync_github(expected_head_sha: params.after)` for `OrgB`'s stack using an attacker-supplied `after` SHA.

This is the binding-break described by the report's bug class: `payload field acted on (repository.full_name) != payload field covered by verified signature (repository.owner.login)`.

### Impact Explanation
`GithubSyncJob` (triggered via `stack.sync_github`) fetches and appends commits up to the attacker-chosen `expected_head_sha`, updates the stack's cached deploy spec, and — for stacks with `continuous_deployment` enabled — this sync can lead to an automatic deploy of newly-synced commits without any legitimate push having occurred on that organization. This crosses an organizational trust boundary (an authenticated OrgA request being used to mutate an OrgB-owned stack) and can result in an unauthorized deploy trigger on a stack the attacker does not control, which matches the "unauthorized deploy" / cross-repository-write impact bar.

### Likelihood Explanation
Exploitation requires the Shipit instance to be configured in the documented multi-organization mode (one instance serving several GitHub orgs, each with its own `webhook_secret`), and requires the attacker to be a legitimate tenant/admin of at least one of those organizations (i.e., they know their own org's `webhook_secret`, which they may control since they set up that org's GitHub App). This is a realistic configuration for shared/managed Shipit deployments as explicitly documented, though it does not apply to single-organization deployments where only one secret exists (in that case `repository_owner` and the acted-upon repository are effectively the same tenant).

### Recommendation
After successfully verifying the signature, revalidate that the repository/organization actually referenced by the payload's `repository.full_name` (or the resolved `Stack`/`Repository`) belongs to the same organization used to select the webhook secret in `verify_signature`, rejecting (422) any request where these two do not match. Alternatively, derive the verifying `GitHubApp`/secret directly from the resolved `Repository`'s owner rather than trusting an unauthenticated payload field prior to signature verification, or bind organization to repository at the model layer and check that binding before dispatching to handlers.

### Proof of Concept
1. Configure Shipit in multi-org mode with `OrgA` and `OrgB`, each with a distinct `webhook_secret` (`docs/setup.md:182-209`).
2. As the admin of `OrgA` (knows `OrgA`'s `webhook_secret`), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha-existing-on-github>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push` and the above signature.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
6. `Shipit::Webhooks::Handlers::PushHandler#process` resolves the target stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and enqueues `stack.sync_github(expected_head_sha: <attacker-chosen-sha>)` for a stack the attacker does not own or control.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
