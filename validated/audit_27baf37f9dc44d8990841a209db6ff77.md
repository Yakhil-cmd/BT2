### Title
ValExiting Slot Exhaustion via Rule 1 MinStake Transitions Silently Blocks Rule 2 Severe PFS Demotion — (`kaiax/valset/impl/transition_context.go`)

### Summary
In `applyViolationTransition`, Rule 1 (MinStake violations) and Rule 2 (PFS violations) share a single live `hasSlot` closure over the same in-progress `newValidators` map. Rule 1 runs to completion before Rule 2 starts. An attacker who controls `MaxSlotAvailable` ValPaused nodes can withdraw their stake below MinStake, causing Rule 1 to fill every ValExiting slot. Rule 2 then finds `hasSlot(ValExiting) == false` and silently skips the severe PFS violator, leaving it in `ValActive` and eligible for block rewards.

### Finding Description
`applyViolationTransition` defines `hasSlot` as a closure that counts live nodes in the target state:

```go
hasSlot = func(state valset.NodeState) bool {
    return newValidators.CountByState(state) < ctx.MaxSlotAvailable
}
``` [1](#0-0) 

Rule 1 transitions `ValPaused` nodes below MinStake to `ValExiting` using only `hasSlot(ValExiting)`:

```go
case valset.ValPaused:
    if hasSlot(valset.ValExiting) {
        val.State = valset.ValExiting
    }
``` [2](#0-1) 

Rule 2 then checks `canDemoteActive(ValExiting)` for severe PFS violators:

```go
if pfs >= ctx.PfsThreshold {
    if canDemoteActive(valset.ValExiting) {
        val.State = valset.ValExiting
    } else {
        logger.Trace("PFS severe violation: slot full, skipping transition", ...)
    }
}
``` [3](#0-2) 

Because Rule 1 runs entirely before Rule 2, and `hasSlot` reads the live count, any ValPaused→ValExiting transitions in Rule 1 consume slots that Rule 2 would need. There is no priority mechanism giving PFS violations precedence over MinStake violations for slot allocation.

`MaxSlotAvailable` is small by design — for a 4-validator set it equals 1, for a 10-validator set it equals 2:

```go
func maxSlotAvailable(n uint64) uint64 {
    if n < 4 { return 0 }
    return (n/3 + 1) / 2
}
``` [4](#0-3) 

### Impact Explanation
`IsRewardEligible()` returns `true` only for `ValActive`:

```go
func (s NodeState) IsRewardEligible() bool {
    return s == ValActive
}
``` [5](#0-4) 

A severe PFS violator that should have been demoted to `ValExiting` remains `ValActive`, continues to be selected as a block proposer, and continues to receive block rewards it is no longer entitled to. The validator set is persistently corrupted until the next epoch drains `ValExiting` slots and Rule 2 can run unobstructed.

### Likelihood Explanation
The attack requires only permissionless on-chain actions:
1. The attacker runs multiple validator nodes — permissionless under the permissionless fork.
2. Some nodes accumulate minor PFS violations (attacker controls proposal behavior), landing in `ValPaused`.
3. The attacker withdraws stake on those `ValPaused` nodes to below `MinStake` — a standard staking contract call.
4. On the target block, Rule 1 drains the `ValPaused` nodes into `ValExiting`, filling all slots.
5. Rule 2 silently skips the attacker's `ValActive` node.

For small validator sets (n ≤ 7), only **one** sacrificial `ValPaused` node is needed. The attacker's `ValPaused` nodes were going to be moved to `ValExiting` anyway (they are below MinStake), so the only cost is timing the stake withdrawal to coincide with the block where the `ValActive` node's PFS crosses the threshold.

### Recommendation
Decouple slot accounting between Rule 1 and Rule 2, or give PFS severe violations unconditional priority over MinStake violations when allocating `ValExiting` slots. One approach: run Rule 2 first and reserve slots for severe PFS violators before Rule 1 consumes them. Alternatively, maintain separate slot budgets for MinStake-driven and PFS-driven demotions so that MinStake transitions cannot starve PFS enforcement.
