### Title
Bridge Operator Can Drain Funds by Submitting Fabricated `_requestTxHash` Without Source-Chain Proof — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`)

---

### Summary

The Kaia service-chain bridge contracts `handleKLAYTransfer` and `handleERC20Transfer` accept an arbitrary `_requestTxHash` parameter and immediately execute a value transfer (KAIA send or ERC-20 mint/transfer) once the operator voting threshold is met. Neither function verifies that `_requestTxHash` corresponds to a real `RequestValueTransfer` event on the counterpart chain. With the default threshold of **1**, a single bridge operator can fabricate a non-existent deposit and drain the bridge's KAIA balance or mint unbacked ERC-20 tokens to any address.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` and `handleERC20Transfer` in `BridgeTransferERC20.sol` share the same structure:

```
onlyOperators
_lowerHandleNonceCheck(_requestedNonce)
_voteValueTransfer(_requestedNonce)   // passes at threshold=1 with one operator
_setHandledRequestTxHash(_requestTxHash)  // only marks as "handled", no existence check
... transfer/mint assets to _to ...
``` [1](#0-0) 

`_setHandledRequestTxHash` only writes `handledRequestTx[_requestTxHash] = true` — a replay-prevention map, not a proof-of-existence check. [2](#0-1) 

`_voteValueTransfer` uses `keccak256(msg.data)` as the vote key, so operators vote on the full calldata. But the calldata itself is attacker-controlled — there is no on-chain oracle, Merkle proof, or receipt proof that `_requestTxHash` actually exists on the source chain. [3](#0-2) 

The `BridgeOperator` constructor initializes `operatorThresholds[ValueTransfer] = 1`, meaning a **single operator** satisfies the vote immediately. [4](#0-3) 

The bridge owner is automatically registered as an operator at construction time and is also the only party who can register additional operators, so the owner/operator role is the minimum required attacker privilege. [4](#0-3) 

In `modeMintBurn` mode, `handleERC20Transfer` calls `ERC20Mintable(_tokenAddress).mint(_to, _value)` — creating tokens out of thin air. [5](#0-4) 

In lock/unlock mode, `handleKLAYTransfer` sends `_value` wei from the bridge's balance to `_to` via a low-level call. [6](#0-5) 

---

### Impact Explanation

- **KAIA drain**: An operator calls `handleKLAYTransfer(fakeHash, attacker, attacker, bridgeBalance, freshNonce, anyBlock, "")`. With threshold=1 the vote closes immediately and the bridge sends its entire KAIA balance to the attacker.
- **Unbacked ERC-20 mint**: An operator calls `handleERC20Transfer(fakeHash, attacker, attacker, tokenAddr, arbitraryAmount, freshNonce, anyBlock, "")`. In `modeMintBurn` mode, `ERC20Mintable.mint` is called with an arbitrary amount, inflating supply without any real deposit on the counterpart chain.
- **ERC-20 drain (lock/unlock mode)**: Same call drains the bridge's ERC-20 token reserves via `safeTransfer`.

The corrupted values are: the bridge's KAIA balance (sent to attacker), the ERC-20 token supply (inflated), and the `handledRequestTx` mapping (permanently poisoned with a fake hash, consuming that nonce slot).

---

### Likelihood Explanation

The bridge owner is automatically an operator with threshold=1 at deployment. No additional setup is required. The attack requires only a single operator key — no majority collusion, no external service compromise. The operator key is the same key used by the automated `SubBridge` relayer process (`bridgeAccounts.pAccount`), so its compromise or malicious use is a realistic scenario. [7](#0-6) 

---

### Recommendation

1. **On-chain receipt proof**: Require operators to submit a Merkle/receipt proof that `_requestTxHash` is included in a finalized block on the counterpart chain, and verify it inside `handleKLAYTransfer`/`handleERC20Transfer`.
2. **Minimum threshold enforcement**: Enforce `operatorThresholds[ValueTransfer] >= 2` at the contract level (or at deployment), so no single operator can unilaterally execute a transfer.
3. **Counterpart event binding**: Bind the vote key not just to `keccak256(msg.data)` but also to a cryptographic commitment to the source-chain event log (e.g., a receipt root), so operators cannot vote on fabricated parameters.

---
