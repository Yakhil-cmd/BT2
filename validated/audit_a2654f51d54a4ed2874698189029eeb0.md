### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any signed webhook mutate CI state on any repository's commit, including production stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with a bare, cross-tenant `Commit.where(sha: params.sha)` lookup instead of scoping to the repository that authenticated the webhook. Because `verify_signature` only proves the payload matches the secret of *some* organization/repository (the attacker's own), an attacker who controls a repository with a webhook configured (their own fork/org) can forge a `status` event for `context: ci/kubernetes` on a SHA that also exists in a victim stack, flipping that victim commit's CI status even when the victim stack is a `production` environment.

### Finding Description
The broken binding: the code assumes `commit.stack.github_repo_name == payload.repository.full_name`, but never enforces it — i.e. it should hold that `for all c in Commit.where(sha: params.sha): c.stack.github_repo_name == repository_name_from(payload)`, and it does not.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)`, passing the whole `params` payload.
2. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the HMAC signature matches the GitHub App secret for `repository_owner = params.dig('repository','owner','login')`. This proves the request came from GitHub for *that org's* webhook, but says nothing about which repository's commits the handler is allowed to touch.
3. `Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb`) exposes a `stacks` helper that correctly scopes via `Repository.from_github_repo_name(repository_name)&.stacks`, used by other handlers (push, pull_request, check_suite).
4. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does **not** use `stacks`/`repository_name` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries the entire `commits` table by SHA across every repository/stack in the Shipit instance.
5. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a `Status` row and calls `add_status`, which re-evaluates `deployable?`/`blocked?` and triggers `stack.schedule_merges` (`app/models/shipit/commit.rb:379-384`) when state becomes success/pending.

Exploit flow: attacker owns Repo A (any GitHub repo, webhook configured to their own Shipit-connected org/app, or any org whose GitHub App secret they can produce a valid signature for since `verify_signature` is keyed only by `repository_owner` in the payload, not by which repo/stack exists in Shipit). Attacker crafts a commit (or reuses a well-known content-addressed SHA, e.g. an empty tree/commit, or a SHA shared through a fork with common history) so that the same `sha` also exists as a `Shipit::Commit` under victim Stack B, which has `environment: "production"` and lists `ci/kubernetes` in `required_statuses`/`blocking_statuses`. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for Repo A, and body `{ "sha": "<shared_sha>", "context": "ci/kubernetes", "state": "success", "repository": {"full_name": "attacker/repoA", "owner": {"login": "attacker-org"}} }`. `StatusHandler` finds the victim's `Commit` row purely by SHA match and writes a success status to it, unblocking/enabling deploy or merge on Stack B — despite the request never being signed for, or associated with, Stack B's repository.

Existing guards do not prevent this: `verify_signature` validates the signature against `repository_owner`, not against the specific stack being mutated; `drop_unhandled_event` only filters event *types*; the `ExplicitParameters` schema in `StatusHandler.params` validates the *shape* of `sha`/`context`/`state` but not their relationship to the authenticated repository; there is no `Repository`/`Stack` scoping check anywhere in `StatusHandler#process`, unlike the sibling handlers that call `stacks`.

### Impact Explanation
A payload authenticated for repository A can write a `Shipit::Status` for a commit belonging to repository B's stack. If that stack is configured as `production` and gates deploys/merges on `ci/kubernetes`, the forged success status can flip `deployable?` to true and trigger `stack.schedule_merges`/continuous delivery, enabling an unauthorized deploy of attacker-influenced code, or forging a failing/error status to block a legitimate production deploy (denial of legitimate release). This is a cross-tenant write: "a payload for one repository mutating another's stack, commit, task" — matching the Critical impact category. Blast radius is any Shipit instance with more than one connected repository/stack, and is repeatable per-SHA/per-victim-commit at will.

### Likelihood Explanation
Preconditions: attacker needs a repository/org for which they can produce a validly-signed webhook to Shipit's `/webhooks` endpoint (trivial - they can add the Shipit webhook to their own repo, or use any org they control), and a target commit `sha` value that also exists as a `Shipit::Commit` on a victim stack. The `sha` collision is the main constraint: it requires either object-identical content (e.g., initial/empty commits, common merge-base/ancestor commits shared via fork history, or SHA1 identical objects), which is realistic in forked-repository scenarios common to Shipit's GitHub-integration model. Attacker cost is a single unauthenticated HTTP POST; the attack is fully repeatable and scriptable.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring the other handlers' use of `stacks`/`repository_name`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha) # or equivalent join through Repository -> Stack -> Commit
        .each { |commit| commit.create_status_from_github!(params) }
end
```
Concretely, restrict the `Commit` lookup to commits whose `stack.github_repo_name` matches `repository_name` derived from the payload, so a status can never be written to a commit outside the repository that authenticated the webhook.
