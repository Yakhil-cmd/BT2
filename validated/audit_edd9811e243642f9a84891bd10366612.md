### Title
Cross-tenant Stack takeover via `organization.login` HMAC-org fallback diverging from `repository.full_name` Stack lookup - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using `repository_owner`, which falls back to `params.dig('organization','login')` when `repository.owner.login` is absent. `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`, used by `PushHandler#process`, independently resolves the target `Repository`/`Stack` from `payload.dig('repository','full_name')`. These two values are never required to agree, so a payload signed with one organization's secret can target a `Stack` owned by a different organization's repository.

### Finding Description
The broken binding is: `organization_that_verified_hmac (repository_owner) == organization_owning_repository (repository.full_name.split('/').first)`. This is never enforced.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:59-62` — `repository_owner` returns `params.dig('repository','owner','login') || params.dig('organization','login')`.
- `app/controllers/shipit/webhooks_controller.rb:24-30` — `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the raw body HMAC against that org's `webhook_secret` [1](#0-0) .
- `lib/shipit.rb:170-181,196-200` — `Shipit.github(organization:)`/`github_app_config` look up a distinct `webhook_secret` per organization key from `secrets.github`, confirming this is a genuine multi-tenant secret scheme [2](#0-1) .
- `app/models/shipit/webhooks/handlers/handler.rb:32-38` — `stacks`/`repository_name` derive the target repository purely from `payload.dig('repository','full_name')`, with no reference to `repository_owner` or the org used for signature verification [3](#0-2) .
- `app/models/shipit/webhooks/handlers/push_handler.rb:7-17` — `PushHandler`'s `ExplicitParameters` schema only `requires :ref, :after`; it does **not** require `repository.owner.login` or otherwise validate consistency, so a payload missing `repository.owner` sails through [4](#0-3) .
- `app/models/shipit/repository.rb:53-56` — `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain DB lookup, with no cross-check against the verifying organization [5](#0-4) .

Attacker request (owns `org-attacker`, whose GitHub App/webhook secret they legitimately control/know, and both orgs are configured as separate tenants in `secrets.github`):
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker secret, raw_body)>
{
  "repository": { "full_name": "org-victim/app" },
  "organization": { "login": "org-attacker" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
`repository_owner` resolves to `org-attacker` (since `repository.owner.login` is omitted), so `verify_signature` validates against `org-attacker`'s secret, which the attacker knows and can therefore forge a valid signature. `PushHandler#stacks` then resolves `Repository.from_github_repo_name('org-victim/app')` and syncs any of `org-victim`'s branch-matching `Stack`s via `stack.sync_github(expected_head_sha:)`, enqueuing `GithubSyncJob` for the victim's stack, which creates commits and, if the target stack has `continuous_deployment` enabled, can propagate into `ContinuousDeliveryJob#perform` deploy triggers.

No existing guard closes this gap: `verify_signature`'s only checks are HMAC validity and organization-config existence (`GithubOrganizationUnknown`), neither of which compares `repository_owner` to `repository.full_name`'s owner segment; `ExplicitParameters` schemas for push/pull_request/status handlers do not require or cross-validate `repository.owner`.

### Impact Explanation
An attacker who controls one tenant's org (`org-attacker`) in a multi-organization Shipit deployment can forge webhooks that authenticate under their own org's secret but mutate any other tenant's (`org-victim`) `Stack`/`Repository` records purely by naming `repository.full_name` differently from `organization.login`/`repository.owner.login`. This is a cross-repository write for a repository that never authenticated the request — matching the Critical category "a payload for one repository mutating another's stack, commit, task or task". It is fully repeatable against any repository name in the datastore, and if the victim stack has continuous deployment enabled, this can cascade into unauthorized deploy triggering via `ContinuousDeliveryJob`.

### Likelihood Explanation
Requires a Shipit deployment configured for multiple GitHub organizations (`secrets.github` keyed by org, i.e. `github_default_organization` non-nil) — a supported and documented configuration in this codebase (`lib/shipit.rb#github_organizations`). The attacker needs no Shipit credentials, only knowledge of their own org's configured `webhook_secret` (which they set up themselves when integrating their org with Shipit) and the target repository's `full_name`, both trivially obtainable. The attack is a single unauthenticated HTTP POST, fully repeatable, and requires no interaction from the victim.

### Recommendation
Enforce that the organization used to verify the HMAC matches the organization actually owning the target repository before dispatching to handlers: require `repository.owner.login` explicitly (do not silently fall back to `organization.login` for repository-scoped events like `push`/`status`/`pull_request`), and/or after signature verification, re-derive the repository owner from `repository.full_name` and assert it equals `repository_owner` before calling any handler, rejecting the request (422) on mismatch.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (conceptually, no live GitHub needed — stub `verify_webhook_signature` per org):
```ruby
test "push payload with mismatched organization vs repository.full_name syncs a different tenant's stack" do
  # arrange two distinct org configs with distinct secrets
  Shipit.stubs(:github).with(organization: 'org-attacker').returns(
    stub(verify_webhook_signature: true)
  )
  victim_stack = shipit_stacks(:shipit) # belongs to repository owned by "org-victim" per fixtures
  payload = {
    repository: { full_name: "org-victim/app" }, # no owner sub-key
    organization: { login: "org-attacker" },
    ref: "refs/heads/#{victim_stack.branch}",
    after: "deadbeef"
  }.to_json

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = 'sha1=anything' # accepted because org-attacker's app is stubbed to verify true

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: "deadbeef"]) do
    post :create, body: payload, as: :json
  end

  # Assert the binding is broken:
  assert_equal 'org-attacker', JSON.parse(payload).dig('organization', 'login') # org that verified HMAC
  assert_equal 'org-victim', victim_stack.repository.owner                       # org owning mutated Stack
  refute_equal 'org-attacker', victim_stack.repository.owner
end
```
This demonstrates that `organization_that_verified_hmac` ("org-attacker") differs from `organization_owning_repository` ("org-victim") while the victim's `Stack` is still mutated (`GithubSyncJob` enqueued for it).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
