### Title
Webhook signature verification keys on `repository.owner.login`, but repository-scoped handlers act on the unverified `repository.full_name` field - cross-organization webhook forgery in multi-org configurations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a delivery against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). Every handler that actually acts on the payload, however, resolves the target `Repository`/`Stack` from a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Because the whole raw body is HMAC-signed as one blob but only the `owner.login` sub-field is bound to the choice of secret, an operator of one configured GitHub organization (who legitimately possesses that organization's `webhook_secret`) can craft a signed delivery whose `repository.owner.login` matches their own org (passing signature verification) while `repository.full_name` names a repository belonging to a different organization hosted on the same Shipit instance.

### Finding Description
- `app/controllers/shipit/webhooks_controller.rb` `verify_signature` computes:
  `github_app = Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then calls `github_app.verify_webhook_signature(header, raw_body)`. [1](#0-0) 
- `Shipit` supports multiple GitHub Apps/organizations, each with its own independent `webhook_secret`, as documented in `config/secrets.development.example.yml`. [2](#0-1) 
- `GitHubApp#verify_webhook_signature` only checks the HMAC of the raw payload against the secret picked for that one organization; it does not further constrain which repository the payload may reference. [3](#0-2) 
- Once the request passes this per-organization check, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolve the acted-upon repository from `payload.dig('repository', 'full_name')` — a sibling field of `owner.login` inside the same payload, never itself covered by any binding to the org whose secret validated the signature. [4](#0-3) 
- `PushHandler#process` uses this repository/stack resolution directly, with no re-check that `full_name`'s owner equals `repository_owner`, and triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack. [5](#0-4) 
- `Stack#sync_github` enqueues `GithubSyncJob`, which fetches commits via the shared app-level `github_api` and, upon success, can enqueue `CacheDeploySpecJob`; if the affected commit later reports a passing CI/check status, `Commit#schedule_continuous_delivery` will trigger `ContinuousDeliveryJob` for stacks with `continuous_deployment: true`, which calls `Stack#trigger_continuous_delivery` → `trigger_deploy`. [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is: `repository_owner used to select webhook_secret == owner of repository.full_name acted on by handlers`. This equality is never enforced, so an attacker who legitimately controls one organization's GitHub App/webhook secret can forge a delivery whose signature verifies for their own org while its `repository.full_name` targets a completely different organization's repository configured on the same Shipit instance.

### Impact Explanation
This breaks the org-authenticated-vs-repository-written binding explicitly called out in scope. In a multi-organization Shipit deployment (the officially documented configuration), it lets a party who only administers Organization A's GitHub App force `push`/other webhook-driven side effects — resync of commits, cache invalidation, and ultimately continuous-deployment triggering — against stacks belonging to Organization B, without ever possessing Organization B's webhook secret or write access to Organization B's repository. This can result in an unauthorized deploy being kicked off for a repository the attacker does not control, which matches the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation requires the Shipit instance to be configured for multiple GitHub organizations (documented as a first-class supported configuration) and requires the attacker to possess the `webhook_secret` of at least one of those configured organizations — something any organization admin onboarded to the shared Shipit instance would have by design, without needing any Shipit account, `ApiClient` token, or repository write access on the target org. Given that this is a normal capability of a legitimate but low-trust tenant of a shared multi-org install, likelihood is moderate to high wherever the multi-org feature is used.

### Recommendation
Bind the field used to select the verifying secret and the field used to resolve the acted-upon repository. Concretely, after selecting `github_app` by `repository_owner`, verify that `payload.dig('repository', 'full_name')`'s owner segment equals `repository_owner` (or `organization.login`) before dispatching to handlers, and reject (422) any delivery where they diverge. Alternatively, have handler-level `repository_name`/`stacks` resolution consult the already-verified `repository_owner` rather than trusting the unrelated `full_name` field independently.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.example.yml`), both hosting stacks on the same Shipit instance.
2. As an administrator of `org-a`'s GitHub App (legitimately possessing `org-a`'s `webhook_secret`), craft a `push` event JSON body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/target-repo"`
   - `ref = "refs/heads/<org-b-stack-branch>"`, `after = "<sha>"`
3. Sign the raw body with `org-a`'s `webhook_secret` using `sha1=HMAC-SHA1(secret, body)` and send it to `POST /webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `Shipit.github(organization: "org-a")` and successfully verifies the signature. [9](#0-8) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/target-repo")` and calls `sync_github` on `org-b`'s stack, enqueuing `GithubSyncJob`, despite the request never being signed by `org-b`'s secret. [4](#0-3) [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
