## Analysis

The reported PyTorch bug is a "free"/deallocation routine (`caching_allocator_delete`) that corrupts allocator-tracked state when invoked improperly. The closest reachable analog in `ocore` is the unit-cache "free" routine `storage.forgetUnit()`/`storage.fixIsFreeAfterForgettingUnit()` combo used to roll back speculative in-memory DAG state after an AA response chain is reverted. The caller `revertResponsesInCaches()` in `aa_composer.js` performs an incomplete cleanup pass that is directly analogous to a partial/incorrect "free" that leaves allocator (cache) bookkeeping in a corrupted, inconsistent state.

### Title
Incomplete in-memory DAG cache invalidation on AA response rollback leads to persistent state corruption - (File: aa_composer.js)

### Summary
`revertResponsesInCaches()` only computes the `parent_units` to "fix" (recompute `is_free`) from the **first** unit of a multi-unit AA response chain, then calls `storage.forgetUnit()` on **every** unit in the chain but calls `storage.fixIsFreeAfterForgettingUnit()` with only the first unit's parents. Any real, external parent referenced by later (non-first) response units in the reverted chain never has its `is_free`/best-children bookkeeping recomputed, corrupting the in-memory `assocUnstableUnits`/`assocBestChildren` caches relative to the true DAG state.

### Finding Description
`revertResponsesInCaches()` is the cleanup routine invoked whenever a chain of AA responses must be discarded from memory: [1](#0-0) 

It gathers all response units of the chain into `arrResponseUnits`, but only reads `parent_units` off the **first** unit (`objFirstUnit = storage.assocUnstableUnits[first_unit]`). It then calls `storage.forgetUnit` on every unit in the chain, and only afterwards calls `storage.fixIsFreeAfterForgettingUnit(parent_units)` with that single, incomplete parent set.

`forgetUnit()` itself correctly removes a unit from its own parents' `assocBestChildren` list (this part is per-unit and correct): [2](#0-1) 

But `fixIsFreeAfterForgettingUnit()` is the only function that recomputes the `is_free` flag of a parent once its last remaining unstable child is removed: [3](#0-2) 

A primary AA trigger can fan out into several secondary AA calls (`handleSecondaryTriggers`), each producing its own response unit with its own `parent_units` (which, depending on unit composition/tip selection at that moment, can include real, external DAG units besides the previous response in the chain): [4](#0-3) 

If any secondary AA in the chain fails, the primary trigger's `revert()` path is taken, which invokes `revertResponsesInCaches(arrResponses)` for the **entire accumulated response chain** (not just the first unit) before rolling back to the savepoint: [5](#0-4) 

Because only `objFirstUnit.parent_units` is used to call `fixIsFreeAfterForgettingUnit`, any external parent referenced only by the second/third/... response unit in the chain keeps a stale `is_free = 0` in `storage.assocUnstableUnits` forever (or until the node restarts and caches are rebuilt from the DB), even though the child unit that made it non-free has just been deleted from memory. This is functionally identical in nature to the PyTorch bug class: a "delete" routine that does not fully synchronize the tracked allocation/ownership bookkeeping, corrupting subsequent lookups against that (cache) allocator state.

### Impact Explanation
`is_free` and `assocBestChildren` are core in-memory bookkeeping structures used by:
- `main_chain.js` (`goUpFromUnit`/best-parent determination, which walks `assocBestChildren`/unstable unit props) to compute the best parent and, transitively, the main chain and stability points.
- `joint_storage.js`'s `purgeUncoveredNonserialJoints()`, which selects candidate units for archiving based on `is_free=1` in the DB, while the in-memory copy in `assocUnstableUnits` can now diverge from what the DB thinks.
- Own-unit composition logic that picks "free" tips.

An unprivileged AA trigger sender can deterministically drive an AA (or a chain of AAs they compose/trigger) into a bounce inside `handleSecondaryTriggers`, forcing `revert()`→`revertResponsesInCaches()` on a multi-unit response chain, corrupting the in-memory `is_free` state for units that are not part of the reverted chain. Because this leaves the node's live, non-reverted DAG bookkeeping permanently inconsistent with the database (until the periodic `shrinkCache`/restart resets it), it can produce incorrect best-parent/main-chain computations relative to a node that has not hit this code path (or hit it with different timing/set of connected peers), which fits the "node disagreement on validity or stability" impact category.

### Likelihood Explanation
Any user can define or interact with a chain of AAs (or trigger an existing multi-hop AA setup) that fails partway through a secondary call — this is a common, easily engineered condition in oscript (e.g. an assertion/`bounce()` call in the last AA of a chain). No special privileges, hub/peer position, or timing races are required; only posting an ordinary unit that triggers the AA chain.

### Recommendation
Fix `revertResponsesInCaches()` to collect and de-duplicate the **union** of `parent_units` from every unit in `arrResponseUnits` (excluding parents that are themselves being forgotten in the same batch), and call `storage.fixIsFreeAfterForgettingUnit()` with that complete set, e.g.:
```js
var allParentUnits = [];
arrResponseUnits.forEach(function (u) {
    var props = storage.assocUnstableUnits[u];
    if (props) allParentUnits = allParentUnits.concat(props.parent_units);
});
arrResponseUnits.forEach(storage.forgetUnit);
storage.fixIsFreeAfterForgettingUnit(_.uniq(allParentUnits).filter(p => !arrResponseUnits.includes(p)));
```

### Proof of Concept
1. Deploy AA `A` (primary) whose response sends outputs simultaneously/sequentially to secondary AAs `B` and `C` (or a longer chain `A → B → C`), forming a response chain of length ≥ 2 with parent units drawn from different real DAG tips at composition time.
2. Craft trigger data so `C` (the last AA in the chain) calls `bounce()`/raises an error under attacker-controlled input.
3. Post the triggering unit; `handleTrigger` for `A`'s primary run accumulates response units for `A` and `B` in `arrResponses`, then `C` fails, causing `revert()` → `revertResponsesInCaches(arrResponses)`.
4. Because `objFirstUnit.parent_units` (only `A`'s response parents) is used, any external parent referenced only by `B`'s speculative response unit is never passed to `fixIsFreeAfterForgettingUnit`, leaving that parent's in-memory `is_free` flag stuck at `0` despite `B`'s response (its only non-free child) having been removed from `assocUnstableUnits`.
5. Repeat with different chain shapes/timings across nodes to observe divergent in-memory `is_free`/`assocBestChildren` state, which can be inspected via `storage.assocUnstableUnits`/`storage.assocBestChildren` in a running node (as already exercised by the cache-equality assertions in `test/aa_composer.test.js`, e.g. `t.deepEqual(storage.assocBestChildren, old_cache.assocBestChildren)`). [6](#0-5)

// parent_units are parent units of the forgotten unit
function fixIsFreeAfterForgettingUnit(parent_units) {
	parent_units.forEach(function(parent_unit){
		if (!assocUnstableUnits[parent_unit]) // the parent is already stable
			return;
		var bHasChildren = false;
		for (var unit in assocUnstableUnits){
			var o = assocUnstableUnits[unit];
			if (o.parent_units.indexOf(parent_unit) >= 0)
				bHasChildren = true;
		}
		if (!bHasChildren)
			assocUnstableUnits[parent_unit].is_free = 1;
	});
}
