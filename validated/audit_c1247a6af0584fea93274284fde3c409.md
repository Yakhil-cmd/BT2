### Title
Webhook signature verified against the wrong organization's secret while handlers act on an unrelated repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the *unverified* JSON body, but the handlers that subsequently act on the payload identify the target `Repository`/`Stack` using other fields inside the same body (e.g. `repository.full_name`). Because the app never binds "the org whose secret validated this request" to "the org/repo the handler will actually mutate," anyone who controls a legitimate GitHub App installation for **one** organization onboarded to this Shipit instance can forge events that are cryptographically valid (signed with their own known secret) while pointing all repository-identifying fields at a **different** organization/repository.

### Finding Description
`Shipit::WebhooksController#verify_signature` computes: [1](#0-0) 

and derives the organization used to pick the secret purely from the payload itself: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves a per-organization `GitHubApp` instance, each configured with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

The HMAC is only proof that *whoever crafted this raw body knows the secret configured for the organization named at `repository.owner.login`/`organization.login`*. It says nothing about the other repository-identifying fields in the same JSON body (`repository.full_name`, `repository.name`, etc.), which downstream handlers use to resolve the actual `Repository`/`Stack` record that gets mutated (pull request handlers, status handlers, etc. key off `full_name`): [5](#0-4) 

Since the attacker fully controls the JSON body they sign, they can set `repository.owner.login` (used only to pick the verification secret) to an organization they legitimately administer in this Shipit instance, while setting `repository.full_name`/other identifying fields to point at a completely different organization's repository. The signature check passes (it's their own secret), yet the handler dispatched in `create` processes the payload as if it legitimately originated from — and pertains to — the spoofed repository.

This is the same class of bug as the reported issue: a restriction is enforced on one field (`refund`'s caller address / here, the org used for signature verification), while the actually consequential field (token transferability / here, the repository actually mutated) is never covered by that check, letting a legitimate actor sidestep the intended trust boundary.

Binding broken (equality that should hold but doesn't):
`organization authenticated by verify_signature (params.dig('repository','owner','login'))` == `organization/repository actually written by the dispatched handler (params.dig('repository','full_name') / etc.)`

### Impact Explanation
Any org onboarded to the Shipit instance (i.e., any customer/team with their own GitHub App + webhook secret configured under `Shipit.github`) can forge webhook events that are accepted as authentic for a **different** organization's repository. Depending on which handler fires, this can translate into: injecting fake commit statuses that feed CI/merge-queue gating (`commit_status`/`status` handlers), spoofing `pull_request`/`membership`/`push` events that mutate `Stack`, `Commit`, `Team`, or `Membership` records belonging to a repository the attacker does not own. This is a cross-organization write into state the attacker has no legitimate access to, potentially enabling an unauthorized merge or corrupting deploy-gating state for another org's stack — matching the "cross-repository writes / unauthorized deploy or merge" High/Critical impact bar.

### Likelihood Explanation
Requires the attacker to be a legitimate admin of at least one organization/GitHub App installation already configured in the same multi-tenant Shipit instance (so they know their own org's `webhook_secret`) — this is an "unprivileged" relationship with respect to the victim org, since no access to the victim's credentials, repo, or Shipit session is needed. This matches the report's core class: a trusted-but-limited actor circumvents a restriction meant to be scoped by using a field the restriction never actually covers.

### Recommendation
- After verifying the signature, re-derive the organization from the same trusted context used to select the verification secret, and cross-check it against every repository/organization field the dispatched handler will use (`full_name`, `owner.login`, etc.) — reject the event if they don't match.
- Prefer resolving the `webhook_secret` from Shipit's own `Repository`/`Stack` record for the target repository (looked up by `full_name`) rather than trusting `repository.owner.login` from the unauthenticated payload to pick which secret to check against.

### Proof of Concept
1. Attacker administers `OrgA`'s GitHub App installed on this Shipit instance and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a webhook body (e.g. a `status` event) with:
   - `repository.owner.login = "OrgA"`, `organization.login = "OrgA"` (used only for secret selection)
   - `repository.full_name = "OrgB/victim-repo"`, `sha`, `state: "success"`, `context: "<required-ci-context>"` (used by the handler to resolve/mutate `OrgB`'s commit/stack state)
3. Attacker signs the raw body with `OrgA`'s known `webhook_secret` and sends it to `/webhooks` with `X-Github-Event: status` and the resulting `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature — see `WebhooksController#verify_signature` at [6](#0-5) .
5. `create` dispatches the status handler with the full params, which resolves and updates the commit status for `OrgB/victim-repo` based on `full_name`, even though only `OrgA`'s secret was ever validated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
