## Title
API client stack-scoping bypass in CCMenu endpoint discloses status of unauthorized stacks - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports scoping a token to a single stack via its `stack_id` column, and `Api::BaseController#stack` enforces that binding by resolving stacks only from the client's authorized scope. `Api::CCMenuController` overrides that method and resolves the stack directly from `Stack.from_param!`, completely bypassing the per-client stack scope, so a token scoped to stack A can read CI/deploy status for any stack B.

### Finding Description
`Api::BaseController` defines the authorization-respecting resolution chain: [1](#0-0) 

`stacks` is deliberately restricted to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is stack-scoped, otherwise it returns `Stack.all`: [2](#0-1) 

`Api::CCMenuController` requires only the coarse `read:stack` permission and then redefines `stack` to bypass the scoped `stacks` relation entirely, looking the stack up straight from the global `Stack` table using attacker-controlled `params[:stack_id]`: [3](#0-2) 

`ApiClient#check_permissions!` only checks that the operation/scope pair (`read:stack`) is present in the token's permission list — it never checks which specific stack the token is bound to: [4](#0-3) 

The route confirms `stack_id` is fully attacker-controlled per-request: [5](#0-4) 

This breaks the intended binding: **stack a token authorizes == stack it touches**. Every other API controller (`Api::StacksController`, tasks, deploys, hooks, etc.) inherits `BaseController#stack`/`stacks` and is properly scoped, as verified by test coverage for `StacksController` (`"an api client scoped to a stack will only see that one stack"`). `CCMenuController` is the outlier that reimplements the lookup without the scope check, and its own test suite never exercises cross-stack scoping, only permission-forbidden and “success” cases.

### Impact Explanation
Any `ApiClient` token — even one deliberately created to be scoped to a single stack (e.g. the CCMenu URL generator in `CCMenuUrlController` creates exactly such tokens with `permissions: %w[read:stack]` scoped to one stack) — can be replayed against `/api/stacks/*stack_id/ccmenu` with a different `stack_id` to read another stack's build/deploy status (last deploy state, running/failure, stack name), which is stack state the token was never authorized to see. This is a horizontal privilege escalation / unauthorized read of stack state across the authorization boundary that `ApiClient.stack_id` is supposed to enforce.

### Likelihood Explanation
Any holder of a legitimately-issued, narrowly-scoped read-only CCMenu token (which is intentionally distributed to CI-status widgets/clients, see `CCMenuUrlController#client`) can trivially exploit this by changing the `stack_id` segment of the URL — no additional privileges, secrets, or session are required beyond the token they already legitimately possess.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and rely on the scoped `stacks`/`stack` implementation from `Api::BaseController` (i.e., use `stacks.from_param!(params[:stack_id])`), so the per-client `stack_id` scope is honored consistently with the rest of the API.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to Stack A with `permissions: ['read:stack']` (e.g., via `CCMenuUrlController#fetch`, which mints exactly such a token).
2. Send `GET /api/stacks/<owner-b>/<repo-b>/<env-b>/ccmenu` using Basic Auth with that token, substituting Stack B's identifiers instead of Stack A's.
3. `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` scoping), returning Stack B's CI/deploy status even though the token is only authorized for Stack A.
