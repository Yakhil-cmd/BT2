### Title
Malicious AA can permanently DoS batched multi-recipient payments in another AA's response, causing fund loss/freezing - (File: aa_composer.js)

### Summary
When an Autonomous Agent (AA) sends a payment message with outputs to multiple addresses and one of those addresses belongs to another AA, `aa_composer.js` synchronously fires a "secondary trigger" for that AA as part of the *same atomic* execution of the primary trigger. If the secondary AA bounces — which it can do for free and unconditionally — the entire primary trigger, including all state changes and payments already made to *other, unrelated* recipients in the same response, is rolled back via `revert()`. An attacker can deploy a trivially cheap AA whose definition always bounces, get it included as one of many payees of a batch-paying AA (e.g., a queue/vault/distribution contract), and permanently block that AA from ever completing its multi-recipient payout, freezing funds meant for all other legitimate recipients — directly analogous to the Y2K `depositQueue` DoS caused by an unsafe external call inside batch processing.

### Finding Description
`handleTrigger()` collects every distinct output address from an AA's payment messages into `arrOutputAddresses`: [1](#0-0) 

After the response unit is validated and saved, `handleSecondaryTriggers()` is invoked for these addresses. For any address that is itself an AA, a secondary/child trigger is executed **synchronously, in the same conn/batch transaction** as the primary trigger, in series: [2](#0-1) 

Crucially, if any one of these secondary triggers bounces, `async.eachSeries` short-circuits and, for a primary (non-secondary) trigger, calls `revert()` — which rolls back the *entire* primary trigger's execution, including any payments already successfully delivered to other, earlier secondary AAs in the same output list: [3](#0-2) 

`revert()` clears the batch and rolls back to the savepoint taken at the start of the primary trigger, undoing all state and balance changes for that trigger, then re-bounces the primary trigger (returning bytes to the trigger sender minus the bounce fee): [4](#0-3) 

Critically, a secondary AA is exempt from having to hold funds to cover bounce fees, since "they never actually send any bounce response or change state when bounced" — meaning any AA author can write a definition that unconditionally errors/bounces at essentially zero cost, with no balance requirement: [5](#0-4) 

This mirrors the Y2K `depositQueue` bug exactly: an untrusted, attacker-controlled "recipient" (there, an ERC1155 receiver contract; here, an AA address) is invoked synchronously as part of processing a batch intended to benefit multiple unrelated parties, and that recipient can unconditionally revert, which rolls back the whole batch rather than only the offending entry. Any AA design that pays out to several addresses in one trigger — vaults, escrow/auction settlement, staking reward distribution, deposit/withdrawal queues that advance a state-var "cursor" as part of the same trigger that pays users — is vulnerable: if the malicious AA's address is ever placed among the payees (attacker can register their own AA address as `receiver`/`beneficiary` just like the Y2K `receiver` parameter), every future attempt to process that batch/queue will hit the malicious entry, bounce, and roll back, so the "cursor"/queue state can never advance past it. This freezes AA funds owed to all other legitimate parties in that batch indefinitely, with no way for anyone (not even the AA author) to skip the poisoned entry, since AAs have no privileged bypass mechanism.

### Impact Explanation
This enables a cheap, permanent denial-of-service against any AA (asset issuer/AA author's contract) that pays multiple recipients — including AAs — within a single trigger response, e.g., withdrawal queues, batched distributions, or escrow settlements. Funds destined for legitimate, unrelated users can be permanently frozen inside the victim AA, since the bounce-and-rollback semantics guarantee that no partial progress on the payout batch is ever retained. This matches "AA fund loss or freezing," a qualifying High-severity impact.

### Likelihood Explanation
Likelihood is high: deploying a malicious "always-bounce" AA definition costs only the standard unit-posting fee, and the malicious AA needs no balance to bounce as a secondary trigger. The only prerequisite is that the malicious AA's address ends up among the output addresses of some victim AA's payment message — trivially achievable whenever the victim AA lets a user-supplied trigger parameter determine a payee/recipient address (a common oscript pattern, analogous to the `receiver` argument in the Y2K `deposit()` call).

### Recommendation
Do not roll back the entire primary trigger's already-successful state/payments when a secondary AA bounces. Instead, treat a bounced secondary trigger as an independent failure: keep the funds sent to it (or return them to the sending AA's own balance) without invalidating unrelated payments/state changes made to other addresses in the same response. Alternatively, process each output-address-triggered secondary AA independently (isolated sub-transaction/savepoint) so a single misbehaving secondary AA cannot unwind unrelated, already-completed transfers to other parties.

### Proof of Concept
1. Deploy AA `M` with a definition whose only message is a `state` formula that unconditionally errors, e.g. `{ bounce("always fail"); }` — no `bounce_fees` needed since secondary triggers are exempt (`aa_composer.js` line 1850).
2. Deploy/observe a victim AA `V` that implements a payout queue: on each trigger it reads the next pending recipient from a state var, sends it a payment, and advances the queue pointer state var in the same trigger execution (a common oscript pattern for batched/queued withdrawals).
3. As an ordinary user, submit a deposit/registration transaction to `V` specifying `M`'s address as the recipient of a future payout (analogous to the Y2K `receiver` parameter), placing `M` into `V`'s payout queue among other legitimate depositors.
4. When `V`'s trigger later attempts to pay out to `M` (whether alone or alongside other addresses in the same payment message), `handleSecondaryTriggers()` invokes `M`'s trigger, which bounces per the "always fail" formula.
5. Per `aa_composer.js` lines 1743-1756 and 1759-1783, this causes `V`'s entire trigger execution to `revert()`: `V`'s state (including the queue-pointer update) rolls back to before the trigger ran, so on every subsequent processing attempt `V` again attempts to pay `M` and again bounces — `V`'s queue is permanently stuck, freezing funds owed to all subsequent (and, if the payout was batched, also earlier) legitimate recipients in that trigger.
