## Analog Analysis: Cross-Repository Commit Status Forgery in `StatusHandler`

### Title
Unauthenticated cross-repository commit status forgery via global SHA lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `ProposalManager` bug binds voting power to a `tokenId` at a historical timestamp without checking that the token wasn't reused/transferred — the check that authorized the vote (past ownership) doesn't bind to the actual current, single-use entity. The equivalent binding break in this engine is in `Shipit::Webhooks::Handlers::StatusHandler`: the webhook signature is verified against the **organization** derived from the payload's `repository.owner.login` [1](#0-0) , but the handler that actually mutates state looks up commits **globally by `sha` alone**, with no scoping to that same repository/organization [2](#0-1) .

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using `repository_owner`, itself read from the untrusted JSON payload (`params.dig('repository', 'owner', 'login')`) [3](#0-2) [4](#0-3) . This only proves the request was signed with *some organization's* configured `webhook_secret` — Shipit supports hosting stacks for multiple distinct GitHub orgs/repos under one instance, each with its own webhook secret [5](#0-4) .

Once signature verification passes for organization A, `Shipit::Webhooks.for_event(event)` dispatches the entire (attacker-controlled) JSON body to the handler [6](#0-5) . `StatusHandler#process`, however, does not use `repository`/`stacks` scoping (unlike `CheckSuiteHandler`, which correctly scopes to `stacks.where(branch: ...)` derived from `repository.full_name` [7](#0-6)  via `Handler#stacks`/`#repository_name` [8](#0-7) ). Instead it does a bare, instance-wide lookup:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit` has no unique-per-repository scoping enforced here; it just `belongs_to :stack` [9](#0-8) , and any commit anywhere in the Shipit instance whose `sha` matches the attacker-supplied value will have a fabricated status recorded via `create_status_from_github!` → `statuses.replicate_from_github!` [10](#0-9) .

This breaks the binding: **organization/repo whose `webhook_secret` authenticated the request** ≠ **repository whose commit state is mutated**. An attacker who owns/administers their own GitHub repo/App installed on the same Shipit instance (a legitimate, low-privilege scenario per the "Using Multiple GitHub Applications" configuration Shipit explicitly supports) can sign a valid `status` webhook for their own org, but set `sha` to a commit SHA belonging to a completely different, higher-privilege repository/stack they don't own. Because `Commit.where(sha: ...)` is global, the forged status is applied to that unrelated commit.

### Impact Explanation
`create_status_from_github!` updates the commit's `Status::Group`, which feeds directly into `deployable?` [11](#0-10) , `schedule_continuous_delivery` (triggers `ContinuousDeliveryJob`) [12](#0-11) , and `stack.schedule_merges` when status becomes `pending` or `success` [13](#0-12) . Merge-queue processing (`ProcessMergeRequestsJob`) checks `all_status_checks_passed?`, which is driven by exactly these forged statuses, before calling `merge_request.merge!` which invokes `stack.github_api.merge_pull_request` with the app's own GitHub credentials [14](#0-13) [15](#0-14) . A forged/fabricated "success" status on an unrelated, cross-org commit can therefore cause an unauthorized deploy trigger or an unauthorized merge on a repository the attacker does not control — satisfying the Critical "unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
Requires only that the attacker control (or be granted access to) any single GitHub App/webhook secret configured on the same shared Shipit instance — a legitimately unprivileged position relative to the victim's repository, exactly analogous to Malory legitimately receiving a transferred NFT and using its unrelated historical voting power. No access to the victim's repository, GitHub token, or Shipit session is required; only knowledge or guessing of a target commit SHA (which is often public, e.g. via GitHub commit URLs) is needed.

### Recommendation
Scope `StatusHandler#process` (and any other handler using a bare model lookup by identifier) to the repository/stacks derived from the verified webhook payload, mirroring `CheckSuiteHandler`'s use of `Handler#stacks` (`Repository.from_github_repo_name(repository_name)`), instead of querying `Commit` globally by `sha`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/orgs per the documented multi-org setup, each with its own `webhook_secret` [5](#0-4) .
2. As an attacker who administers `org-attacker/repo-attacker` (installed webhook secret S_A), obtain the SHA of a commit belonging to `org-victim/repo-victim`'s stack (public GitHub commit SHAs are typically discoverable).
3. Send a `status` webhook to `/webhooks` signed with `S_A`, with body `{"repository":{"owner":{"login":"org-attacker"}}, "sha": "<victim-sha>", "state": "success", "context": "ci/some-check"}`.
4. `verify_signature` succeeds because it only checks the signature against `org-attacker`'s secret, matching `repository_owner` = `org-attacker` from the same payload [3](#0-2) .
5. `StatusHandler#process` executes `Commit.where(sha: "<victim-sha>")`, finds the victim's commit (not scoped to `org-attacker`), and records a forged "success" status on it, potentially unblocking `deployable?`/merge-queue processing for `org-victim`'s stack.
