### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read deploy state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by every other API controller and resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, completely skipping the `stacks` scoping method that all other endpoints rely on to enforce the binding between an `ApiClient`'s `stack_id` authorization and the stack it is allowed to touch.

### Finding Description
Every other API controller resolves the acted-upon stack through `Shipit::Api::BaseController#stack`, which is scoped by the authenticated `ApiClient`: [1](#0-0) 

`stacks` restricts the queryable `Stack` relation to `current_api_client.stack_id` when the client is scoped to a specific stack (`ApiClient#stack_id?`), otherwise it defaults to `Stack.all`. This is the intended equality binding: `token.stack_id == stack acted upon` (or unrestricted only when the token has no `stack_id`).

`Api::CCMenuController`, however, defines its own private `stack` method that discards this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model rather than on `stacks`. `require_permission :read, :stack` only checks that the authenticated `ApiClient` has the `read:stack` permission string in its `permissions` array — it does not check which stack that permission applies to: [3](#0-2) [4](#0-3) 

Consequently, any `ApiClient` token with `read:stack` permission — including one deliberately created with a `stack_id` to scope it to a single stack (as the `here_come_the_walrus` fixture demonstrates the model supports) — can be replayed against `/api/stacks/:stack_id/ccmenu` for an arbitrary `stack_id` and will successfully render that other stack's deploy/rollback status, because the controller never re-applies the `current_api_client.stack_id` restriction.

This also affects the first-party flow that mints these tokens: `CCMenuUrlController#client` creates an unscoped `ApiClient` (no `stack:` attribute set) with `read:stack` permission and exposes its `authentication_token` in a plaintext URL: [5](#0-4) 

Even where an operator explicitly scopes a client to one stack via `stack_id` to limit blast radius (the documented/supported mechanism enforced by `BaseController#stacks`), the CCMenu endpoint silently ignores that restriction.

Binding broken: `ApiClient.stack_id` (the stack a token is authorized for) ≠ `params[:stack_id]` (the stack whose state is actually read) once the request is routed through `Api::CCMenuController`.

### Impact Explanation
This allows unauthorized read of stack/deploy state: a caller holding any valid `read:stack`-scoped API token — even one intentionally restricted to a single stack — can enumerate and read the last deploy/rollback status (`stack.deploys_and_rollbacks.last`) of every other stack managed by the Shipit instance, bypassing the per-stack authorization boundary that the rest of the API enforces. This matches the High-impact category of unauthenticated/unauthorized read of stack state.

### Likelihood Explanation
Likelihood is high for anyone already holding any `read:stack` API token (which is routinely minted per-user via `CCMenuUrlController` for CI status widgets and is often shared/embedded in dashboards). No additional privilege or write access is required — only a token that the application itself considers appropriately scoped to a single, low-sensitivity stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so the `current_api_client.stack_id` restriction is enforced consistently with every other API endpoint.

### Proof of Concept
1. An operator creates (or the app auto-creates via `CCMenuUrlController`) an `ApiClient` scoped to `stack_id: A` with permission `read:stack`, intending it to only ever answer CCMenu queries for stack A.
2. Using that same token's `authentication_token`/basic-auth credentials, issue `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu` for an unrelated stack B.
3. `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks`), successfully resolving stack B; `require_permission :read, :stack` passes because the token merely has the `read:stack` permission string, with no stack check performed.
4. The response renders stack B's latest deploy/rollback status via `shipit/ccmenu/project`, even though the token was never authorized for stack B — confirming the `token.stack_id` vs `stack_id acted upon` binding is not enforced in this controller.
