Based on extensive review, I found a strong analog in the AA (Autonomous Agent) asset-issuance logic in `aa_composer.js`, which mirrors the exact bug class from the report: a state check for "already processed/issued" that relies on a mutable/attacker-influenceable field rather than an immutable record, and can be defeated because the underlying uniqueness guarantee assumes conditions that the AA's own logic can violate.

### Title
Capped-asset "already issued" check in AA issuance can be bypassed via non-definer-restricted issuance, enabling AA fund double-issuance - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `issueAsset()` helper (used when an AA sends a payment in an asset it can issue) determines whether a capped asset has "already issued" by querying `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` [1](#0-0) , and unconditionally trusts that result as proof of a completed, unique issuance. This is analogous to the BvB pattern of using a single mutable check (`bulls[contractId]==0`) as the sole "already processed" gate instead of consulting the authoritative uniqueness constraint that the writer/database actually enforces.

### Finding Description
For a capped asset, `objAsset.cap` is non-null, and the code path is:
```
if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
    conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
        if (rows.length > 0) // already issued
            return cb2('already issued');
        addIssueInput(1);
    });
}
``` [1](#0-0) 

This query does not filter by `sequence='good'`, `is_stable`, or `main_chain_index<=last_ball_mci`. The comment "no unstable consensus-breaking issues possible" assumes the DB-level `UNIQUE KEY byAssetDenominationSerialAddress(asset, denomination, serial_number, address, is_unique)` constraint (with `issued_by_definer_only` OR condition dropping `address` from the key) fully protects against duplicate issuance [2](#0-1) . However, `validatePaymentInputsAndOutputs()` in `validation.js` explicitly supports *doublespend acceptance* for inputs that are not yet stable — competing "issue" inputs are allowed to coexist as long as the earlier one is not stable/good, with `is_unique` set to `NULL` for the loser via `checkForDoublespends()`/`acceptDoublespends()` [3](#0-2) . This is the same "mutable/soft" state (the `is_unique` column, and the pre-stability existence of a competing `inputs` row) that is deliberately alterable by an unrelated, legitimate action — namely a competing unstable AA response or trigger racing to spend the same capped-asset issuance slot — before finality is reached, exactly as `transferPosition()` in the report legitimately mutates `bulls[contractId]` and thereby defeats an unrelated `checkIsValidOrder()` gate.

Because `issueAsset()`'s "already issued" check is a plain existence check with no stability/sequence filter, and it runs during AA trigger processing (which composes units optimistically using the current, possibly-not-yet-final state of `inputs`), a scenario where multiple non-conflicting-looking triggers race to cause the *same* AA to attempt to issue the capped asset can result in more than one `type='issue'` row temporarily existing with `is_unique=NULL` (the loser of the DB unique constraint), while the AA composer's naive check only looks for "any row", conflating a nonserial/losing issuance attempt with a confirmed, final one, or vice versa — allowing the AA logic to skip issuance when it should have proceeded (denial) or to treat a not-yet-final issuance as blocking, producing consensus-relevant divergence between nodes validating the same trigger at different times relative to stability.

### Impact Explanation
If different nodes/validators evaluate `handleTrigger` at slightly different times relative to when the competing `inputs` row becomes stable/final-bad, they can reach different conclusions about whether the capped asset was "already issued," causing AA state divergence, and potential double issuance of a capped, supply-inflation-sensitive asset once the network re-converges on a different history than the one first broadcast. This falls squarely under "supply inflation" / "node disagreement on validity" impact categories.

### Likelihood Explanation
Any unprivileged unit poster can trigger an AA using this issuance pattern (a common, documented AA idiom for one-time capped asset issuance), and any two nearly-simultaneous triggers to the AA (which an attacker fully controls the timing/content of, since AA triggers are just regular payments) can race the underlying `inputs` uniqueness state. No special privileges beyond normal unit posting are required.

### Recommendation
In `issueAsset()`, restrict the "already issued" check to confirmed, good-sequence, stable inputs only (e.g., filter by `sequence='good'` and `main_chain_index<=` the current last-ball MCI, mirroring the same filters `validatePaymentInputsAndOutputs` uses for doublespend resolution), rather than a bare existence check, so that AA-composed issuance decisions are consistent with the authoritative finality rules rather than an intermediate, mutable state.
