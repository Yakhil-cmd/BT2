### Title
Signature verification uses `repository.owner.login` while the handler resolves the target `Repository` via `repository.full_name`, allowing a no-secret organization to forge `pull_request` events that poison a victim stack's `PullRequest#labels` and `ReviewStack#env` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret) to validate a webhook using `params.dig('repository','owner','login')`, but `LabelCapturingHandler#repository` resolves the actual target `Repository`/`Stack` using the independent field `params.repository.full_name` [1](#0-0) [2](#0-1) . Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the selected organization's config has no `webhook_secret` [3](#0-2) , an attacker who controls (or registers) a Shipit-configured GitHub organization with no `webhook_secret` can put that org's login in `repository.owner.login` to pass verification, while setting `repository.full_name` to the victim's real, secret-protected repository, so the forged event is processed against the victim's stack.

### Finding Description
The broken binding is the implicit assumption that:
`params.dig('repository','owner','login') == owner_of(params.repository.full_name)`

Nothing in the request pipeline enforces this equality. `before_action :verify_signature` computes `repository_owner` purely from `repository.owner.login` [4](#0-3)  and looks up `Shipit.github(organization: repository_owner)` to get the `GitHubApp` used for HMAC verification [5](#0-4) . If that organization is configured in `secrets.github` but has no `webhook_secret` set, `verify_webhook_signature` short-circuits to `true` [6](#0-5) , accepting the raw forged body with no cryptographic check at all.

Once past `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the same, unvalidated `params` to `LabelCapturingHandler` [7](#0-6) . That handler locates the target repository independently, via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , and the target stack via `repository.review_stacks` and the PR `number` [8](#0-7) . Because `repository.full_name` is never cross-checked against the org used for signature verification, an attacker can decouple the two: use the no-secret org login for the verification field and the victim's real, secret-protected `owner/repo` for the resolution field.

For `action=unlabeled`, `unlabeled_active_stack?` allows processing as long as the victim's review stack exists and is not archived [9](#0-8) , and `capture_labels` persists `params.pull_request.labels.map(&:name)` — fully attacker-controlled strings — onto the victim's `PullRequest#labels` [10](#0-9) . `ReviewStack#env` then uppercases each label and merges it as `"true"` into the stack's environment, which flows into the commands/`PTY.spawn` environment used by subsequent deploy/task commands [11](#0-10) .

Existing guards do not prevent this: `drop_unhandled_event` only checks the event type; the `ExplicitParameters` schema in `LabelCapturingHandler.params` validates shapes/types, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `verify_signature` itself is the exact place the divergence is introduced.

### Impact Explanation
An unprivileged attacker who registers/owns a GitHub organization that happens to be configured in Shipit without a `webhook_secret` (a misconfiguration but one the rules stipulate as the premise) can forge a `pull_request`/`unlabeled` webhook whose `repository.full_name` names an arbitrary victim repository/stack with a properly configured, secret-protected `webhook_secret`. This lets the attacker write arbitrary environment-variable-shaped keys (via labels) into the victim `ReviewStack#env`, which is consumed by deploy/task commands run under the stack's configured bot identity. This is "a payload for one repository mutating another's stack," matching the Critical impact category for unauthorized manipulation of deploy environment/state across tenants, and is repeatable against any victim stack as long as one no-secret organization exists in the Shipit deployment.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is multi-org configured (`secrets.github` keyed by organization) with at least one organization lacking `webhook_secret`, and (2) a victim repository/stack exists elsewhere in the same instance with an active (non-archived) review stack and a `PullRequest` record. Both are plausible operational states in multi-tenant Shipit deployments and require no privileged access — the attacker only needs to control an organization that is (mis)configured without a secret, and can then target any other configured repository by forging `repository.full_name`. The attack is a single unauthenticated HTTP POST, fully repeatable.

### Recommendation
Tie signature verification to the same repository identity used for handler resolution: derive the `GitHubApp`/secret from `params.repository.full_name` (or its owner) rather than the independent `repository.owner.login`/`organization.login` fields, or explicitly validate that `repository.owner.login` matches the owner segment of `repository.full_name` before proceeding. Additionally, treat a missing `webhook_secret` as a hard misconfiguration error (fail closed) rather than an implicit bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style):
1. Configure `secrets.github` with two orgs: `"attacker-org"` (no `webhook_secret`) and `"victim-org"` (with `webhook_secret` set and `bot_login` set).
2. Create `Shipit::Repository` for `victim-org/victim-repo`, an active `Shipit::ReviewStack` for it, and an associated `Shipit::PullRequest` with `number: 42` and empty `labels`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary bogus one), and body:
   ```json
   {
     "action": "unlabeled",
     "number": 42,
     "pull_request": { ..., "labels": [{"name": "evil_flag"}] },
     "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
     "sender": { "login": "attacker" }
   }
   ```
4. Assert response is `200 OK` (not `422`), proving `verify_signature` passed via the no-secret `attacker-org` path.
5. Assert `victim_pull_request.reload.labels == ["evil_flag"]`, proving cross-repository state mutation.
6. Assert `review_stack.env["EVIL_FLAG"] == "true"`, proving the forged label reached the deploy environment binding — i.e., `params.dig('repository','owner','login')` (attacker-org, unverified) ≠ owner of `params.repository.full_name` (victim-org, secret-protected), yet the write succeeded.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
