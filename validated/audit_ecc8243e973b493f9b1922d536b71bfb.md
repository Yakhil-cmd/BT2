### Title
CCMenu API token is never scoped to the stack it was issued for, allowing cross-stack build/deploy status disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb, app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints (or reuses) a single, permanently shared `ApiClient` named `'CCMenu Client'` per user with `permissions: %w[read:stack]` and no `stack_id`, then returns a URL whose only per-stack binding is the `:stack_id` path segment, not the token itself. `Api::CCMenuController#stack` compounds this by resolving `params[:stack_id]` via `Stack.from_param!` directly instead of the scoped `stacks.from_param!` helper used everywhere else in `Api::BaseController`, so the token's authorization is never checked against the stack being requested.

### Finding Description
The claimed binding is: `token.authorized_stack == requested_stack.id`. Tracing the code shows this equality is never established or checked.

- `CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) creates/finds one `ApiClient` per `current_user` named `'CCMenu Client'`, with `permissions: %w[read:stack]` and no `stack_id` set at all — `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` never passes `stack_id`.
- `#fetch` (`app/controllers/shipit/ccmenu_url_controller.rb:7-11`) builds `api_stack_ccmenu_url(stack_id: stack.to_param)` and appends `client.authentication_token` — the URL's stack scoping lives only in the path, the token itself carries no stack restriction.
- On the consuming side, `Api::BaseController#stacks` (`app/controllers/shipit/api/base_controller.rb:74-76`) would normally restrict lookups to `current_api_client.stack_id` when set: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. But since the CCMenu client never has a `stack_id`, this scope is `Stack.all` regardless.
- Worse, `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) overrides this entirely with `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scope helper. Even if a future/different `ApiClient` did have a `stack_id` set, this controller would still ignore it.
- The only guard is `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`), which checks the client has the `read:stack` permission string — a permission unrelated to *which* stack — via `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`). There is no stack-identity check anywhere in this path.

Attacker flow: a legitimate Shipit user for Stack A calls `GET /stacks/:stack_A_id/cc_menu` (`CCMenuUrlController#fetch`), receiving a URL like `.../api/1/stacks/stack-A/cc.xml?token=T`. This URL is designed to be embedded/shared externally (CCTray/CI badge use case), so it is expected to leave the hands of authenticated users. Anyone in possession of `T` (an internet user, no session, no privileged role) can then request `GET /api/1/stacks/stack-B/cc.xml?token=T` for any other stack B and receive Stack B's build/deploy status, because `ApiClient.authenticate(token)` (`app/models/shipit/api_client.rb:24-26`) only validates the signed client id, and `Api::CCMenuController#stack` resolves whatever `stack_id` is in the URL, with no cross-check against a stack the client was actually issued for.

### Impact Explanation
Any holder of one CCMenu token can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc., rendered by `Api::CCMenuController#show`) for every stack in the Shipit instance, not just the one the URL nominally names. This is unauthenticated read of stack state across tenants/repositories — matching the High severity category "unauthenticated read of stack state, task streams or deploy output." The attack is fully repeatable: the same token works indefinitely and against any `stack_id`, since the token carries no stack binding.

### Likelihood Explanation
Precondition: attacker must obtain one previously-issued CCMenu token, e.g. by finding it in a public CI dashboard, README badge, or any place such tokens are conventionally shared. No Shipit or GitHub secret is needed; no privileged role is needed. Given the token, exploitation is a single unauthenticated GET request with a different `stack_id` path segment — trivial cost, fully repeatable, and requires no code execution or session control on the attacker's part.

### Recommendation
- Persist a `stack_id` on the `ApiClient` created in `CCMenuUrlController#client`, scoping the created client to `stack.id` (e.g., `find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`), or otherwise mint a distinct client per stack.
- Fix `Api::CCMenuController#stack` to use the inherited scoped `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`, so a stack-scoped `ApiClient` (`current_api_client.stack_id`) is actually enforced, consistent with the rest of `Api::BaseController`.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb (new test)
test "a ccmenu token issued for one stack can read another stack's status" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

  # Simulate CCMenuUrlController#fetch minting the shared client for stack_a
  client = ApiClient.create_with(permissions: %w[read:stack])
                     .find_or_create_by!(creator: shipit_users(:walrus), name: 'CCMenu Client')
  token = client.authentication_token

  # Attacker reuses the same token against stack_b
  get :show, params: { stack_id: stack_b.to_param, token: token }

  assert_response :ok
  assert_payload 'name', stack_b.to_param # succeeds even though token was only ever handed out for stack_a
end
```
This demonstrates that `token.authorized_stack` (none/nil) is never equated to `requested_stack.id` (stack_b), confirming the binding is broken.
