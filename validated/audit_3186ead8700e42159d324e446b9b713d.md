### Title
`StatusHandler#process` applies GitHub `status` webhooks to commits owned by *any* stack matching the SHA, not just the authenticated organization's stack — enabling cross-repository status forgery and unauthorized merges - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by SHA alone (`Commit.where(sha: params.sha)`) with no scoping to the repository/organization that authenticated the webhook. An attacker who controls any GitHub organization already configured in Shipit (i.e. has a valid webhook secret for their own repo) can send a `status` webhook for a commit SHA that is shared with a victim stack (e.g. via a fork of the victim's public repo, which reproduces identical commit SHAs), and Shipit will write a forged `Status` onto the victim's commit, potentially unblocking a queued `MergeRequest`.

### Finding Description
The broken binding, stated explicitly: `verify_signature` proves `repository_owner (from payload) == organization owning the secret that signed the payload`, but `StatusHandler#process` never checks `commit.stack.github_repo_name/owner == repository_owner`. These are treated as equal when they are not.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` — this only proves the payload was signed for *that* organization's app credentials. [1](#0-0) 
2. Once verified, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('status')`, which is `StatusHandler`. [2](#0-1) 
3. `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global, unscoped** lookup across the entire `commits` table, matching any stack/repository whose commit happens to share that SHA. [3](#0-2) 
4. `Commit#create_status_from_github!` creates a `Status` row scoped to `commit.stack_id`, and `Status` triggers `after_commit :schedule_continuous_delivery` → `commit.schedule_continuous_delivery` → enqueues `ProcessMergeRequestsJob` for that commit's (victim's) stack. [4](#0-3) [5](#0-4) 
5. `ProcessMergeRequestsJob#perform` calls `merge_request.all_status_checks_passed?`, which delegates to `StatusChecker.new(head, head.statuses_and_check_runs, ...).success?` — now satisfied by the forged `Status`. [6](#0-5) [7](#0-6) 
6. If `merge!` proceeds (no other rejection triggers), the attacker has caused an unauthorized merge on the victim's repository. [8](#0-7) 

Attacker's exact request: sign a `status` webhook payload (`{"sha": "<shared-sha>", "state": "success", "repository": {"owner": {"login": "<attacker-org>"}}}`) with the webhook secret for their own organization/app credentials, and POST it to `/webhooks` with header `X-Github-Event: status`. Since `repository_owner` in the payload matches the attacker's own org, `verify_signature` succeeds legitimately — the forgery is not in the signature check but in the subsequent unscoped commit lookup.

Existing guards that fail to prevent this: `verify_signature` only authenticates the *organization*, not the *repository/stack* being mutated; `StatusHandler`'s `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` scoping applied to the `Commit.where(sha:)` query.

### Impact Explanation
A payload correctly signed for one organization's repository mutates commit/status state belonging to a completely different stack/organization in Shipit, satisfying the "payload for one repository mutating another's stack/commit" Critical category. If the victim stack has `merge_queue_enabled?` and a `MergeRequest` pending solely on CI status, this forged status can directly cause `MergeRequest#merge!` to execute against the victim's GitHub repository — an unauthorized merge. This is repeatable against any stack sharing a commit SHA with an attacker-controlled repository (trivially achievable by forking any public victim repo, since git commit SHAs are content-addressed and identical across forks for shared history).

### Likelihood Explanation
Preconditions: attacker needs a GitHub organization/repository already registered with a valid Shipit webhook secret (their own, standard onboarding — no special privilege), and the victim commit SHA must be shared (trivial via fork, since content-identical commits produce identical SHAs regardless of repository). No `Shipit.github_teams` membership, API token, or session is required — this is purely a webhook-signature-valid-for-wrong-scope issue. Cost is a single signed HTTP POST; fully repeatable and automatable against any victim stack with a pending merge request and a forkable/shared history.

### Recommendation
Scope the `StatusHandler#process` commit lookup to the repository that authenticated the webhook, not by bare SHA across all stacks — e.g., resolve `stack`/`repository` from the verified `repository_owner`/`repository.full_name` and constrain `Commit.where(sha: params.sha, stack: matching_stacks)`. More generally, thread the authenticated repository identity from `WebhooksController` into every handler and require it to match `commit.stack.github_repo_name` before creating/updating status/check-run records.

### Proof of Concept
Minitest under `test/models/webhooks/handlers/status_handler_test.rb` (or extending `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":status webhook signed for org A mutates a commit belonging to stack owned by org B when SHAs collide" do
  victim_stack = shipit_stacks(:shipit) # e.g. owner "shopify"
  attacker_owner_login = "attacker-org"

  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  merge_request = shipit_merge_requests(:...) # pending, head: victim_commit, on victim_stack with merge_queue_enabled

  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'owner' => { 'login' => attacker_owner_login } }
  }.to_json

  Shipit.stubs(:github).with(organization: attacker_owner_login)
    .returns(stub(verify_webhook_signature: true))

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack]) do
    post :create, body: payload, as: :json
  end

  assert_equal 'success', victim_commit.reload.state
  assert merge_request.reload.all_status_checks_passed?, "forged cross-org status satisfied victim MergeRequest"
end
```
This demonstrates both sides of the (broken) equality: `repository_owner == attacker_owner_login` (the side actually checked) vs. `victim_commit.stack.github_repo_name/owner == attacker_owner_login` (the side that should be checked but isn't), while `all_status_checks_passed?` and `ProcessMergeRequestsJob` enqueue prove the exploitable divergence with no live GitHub calls.
