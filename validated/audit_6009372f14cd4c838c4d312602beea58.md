### Title
Blackholed (disabled) correspondent device can be silently re-enabled via replay of a previously issued pairing secret - (File: device.js)

### Summary
`device.js`'s `handlePairingMessage()` unconditionally clears the `is_blackhole` flag on any correspondent that presents a valid `pairing_secret`, even when that correspondent was explicitly disabled ("blackholed") by the user. If the pairing secret is the permanent one (which is never deleted after use), a device that was intentionally cut off can replay it at any time to restore its trusted-correspondent status without the user's consent.

### Finding Description
When a user chooses to ignore unpair requests (`conf.bIgnoreUnpairRequests`), instead of removing a misbehaving/malicious paired device, `wallet.js` marks it as blackholed rather than deleting it: [1](#0-0) 
This sets `correspondent_devices.is_blackhole=1` for the device, which is meant to make the wallet stop treating messages from that device address as coming from a trusted correspondent — the equivalent of an administrator explicitly "disabling" the client.

However, `handlePairingMessage()` in `device.js` re-processes any incoming `pairing` message whose `pairing_secret` matches a still-valid row in `pairing_secrets` (including the *permanent* pairing secret that a device generates once and reuses for repeat pairing, via `getOrGeneratePermanentPairingInfo`): [2](#0-1) [3](#0-2) 

Critically, on any successful pairing-secret match it does:
```js
db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], ...
``` [4](#0-3) 
This unconditionally clears `is_blackhole` for the sender's device address, with no check for whether the device was blackholed on purpose, and no re-authorization by the user. Since the permanent pairing secret (`is_permanent=1`) is deliberately never deleted (`if (pairing_rows[0].is_permanent === 0){ ... DELETE ... }` only fires for non-permanent secrets — see lines 833-837), the disabled device can indefinitely hold and replay this "registration access token" analog (the permanent pairing secret it obtained before being blackholed) to flip itself back to a trusted, non-blackholed correspondent.

This mirrors the Keycloak bug class: a previously issued credential (here, the permanent pairing secret) that should not confer re-enable rights over an entity the operator explicitly disabled, is nonetheless accepted to silently reverse that disable action.

### Impact Explanation
Once `is_blackhole` is cleared, the attacker-controlled device is again treated as a normal paired correspondent. Message handling in `wallet.js`'s `handleMessageFromHub` (`doHandle()`) dispatches numerous privileged device-message subjects to a correspondent by address (payments, signing requests, shared/multisig wallet setup messages, arbiter contract offers, text triggering UI actions, etc.): [5](#0-4) 
Restoring trusted status re-opens all of these flows from an address the user had intentionally shut off — e.g., resuming spam/phishing signing requests, shared-address/multisig setup abuse, or other correspondent-scoped device-message workflows that assume the correspondent relationship reflects current user intent. This is a device/wallet-layer integrity bypass of an explicit user "disable" action reachable purely by a peer replaying a previously obtained token, which fits the paired-device attack surface allowed by the rules.

### Likelihood Explanation
Exploitation requires only that the attacker previously paired (obtaining the permanent pairing secret) and was later blackholed rather than fully removed — a supported, documented configuration (`conf.bIgnoreUnpairRequests`). No additional secrets or race conditions are needed; the attacker just resends the standard `pairing` device message with the permanent secret it already possesses. This is straightforward to trigger by any peer previously paired with a victim.

### Recommendation
`handlePairingMessage()` should not clear `is_blackhole` unconditionally on every pairing-secret match. Either:
- Skip clearing (or reject the pairing attempt entirely) when the existing `correspondent_devices` row for `from_address` has `is_blackhole=1`, requiring an explicit user action to un-blackhole, or
- Invalidate/rotate the permanent pairing secret whenever a device is blackholed, so a disabled device cannot re-pair using previously issued credentials.

### Proof of Concept
1. Device B pairs with Device A normally; B obtains/uses A's permanent pairing secret (via `getOrGeneratePermanentPairingInfo`) as part of the pairing flow, or simply already has A's `pairing_secret`/permanent secret from an earlier legitimate exchange.
2. Device A's user configures `conf.bIgnoreUnpairRequests = true` and later blackholes B (either B sends `removed_paired_device` which flips `is_blackhole=1`, per `wallet.js:132-135`, or the operator otherwise sets it).
3. B sends a fresh `pairing` device message to A reusing the still-valid permanent `pairing_secret`.
4. `handlePairingMessage()` in `device.js` finds the secret in `pairing_secrets` (still present since it's permanent, never deleted at lines 833-837) and executes `UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?`, restoring B as a fully trusted correspondent of A without any user consent.

// {pairing_secret: "random string", device_name: "Bob's MacBook Pro", reverse_pairing_secret: "random string"}
function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}
