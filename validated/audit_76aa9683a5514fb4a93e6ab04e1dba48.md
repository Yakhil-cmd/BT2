### Title
Session Fixation via Unregenerated Session ID on GitHub OAuth Login - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` [1](#0-0)  completes the OmniAuth GitHub flow, resolves the authenticated GitHub identity, and then writes the resulting `User` id directly into the *existing* session (`session[:user_id] = sign_in_github(auth)`), without ever calling `reset_session` to rotate the session identifier. This breaks the binding "GitHub identity authenticated ⇔ `User` bound to the session": the session cookie an attacker planted before authentication remains valid and becomes bound to the victim's account the moment the victim finishes login.

### Finding Description
The report's underlying bug class is that a security-critical action is performed using a value that was never actually validated/covered by the mechanism meant to protect it (unlimited slippage/deadline despite a "swap" that looks bounded). The analog here is the session lifecycle: Shipit trusts `session[:user_id]` as the sole proof of "this browser is User X" for the entire application (see `current_user` resolution used throughout the engine, and `session[:authenticated]` gating in `UserRequiredMiddleware`), yet the controller responsible for establishing that trust binding never rotates the session identifier at the point where the security context changes from anonymous to authenticated: [1](#0-0) 

Compare with `logout`, which does call `reset_session`: [2](#0-1) 

Because `callback` skips `reset_session`, an attacker who can fix the session identifier of a victim's browser before the OAuth flow completes (a classic session-fixation primitive — e.g. via a `Set-Cookie` for a shared/parent domain, a response-splitting/XSS bug elsewhere in the deployment, or simply handing the victim a login link containing a pre-set session id if `config.session_store` allows session id in URL/param) will find that, after the victim authorizes with GitHub, the *same* session id the attacker already knows is now bound to the victim's `User` record, `github_access_token`, and all of Shipit's authorization checks (`current_user`, team membership, etc.). No GitHub App credentials, `ApiClient` tokens, or webhook secrets are needed — this is purely an engine-side session-handling gap in the trust-establishing controller.

### Impact Explanation
This matches the explicitly accepted High-impact category "session fixation / forced OAuth completion." A successful attack yields full session takeover of the victim's Shipit identity — including whatever `Shipit.github_teams` authorization the victim's account carries, deploy/rollback/merge rights on stacks the victim can access, and exposure of the victim's `github_access_token` persisted via `user.update(github_access_token: auth.credentials.token)` [3](#0-2)  to any code path within the attacker's control that can read the session-bound user (e.g. `current_user.github_access_token` usage elsewhere in the app).

### Likelihood Explanation
Requires an unprivileged attacker to be able to set/predict a session identifier that the victim's browser will subsequently use when hitting `/auth/github/callback` — a well known and still relevant technique against session stores that do not force ID rotation on privilege change, particularly exploitable through cookie-tossing on related subdomains or lax `SameSite`/CSRF configuration around the OAuth `origin` redirect flow already handled by `request.env['omniauth.origin']` [4](#0-3) . No secret material is required, matching the ask-only scope constraints.

### Recommendation
Call `reset_session` (or otherwise rotate the session id) immediately before assigning `session[:user_id]`/`session[:authenticated]` in `callback`, mirroring the rotation already performed in `logout`:

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?

  user_id = sign_in_github(auth)
  reset_session
  session[:user_id] = user_id
  session[:authenticated] = true

  redirect_to(return_url)
end
```

### Proof of Concept
1. Attacker obtains/plants a known session cookie value in the victim's browser for the Shipit host (e.g., via a cookie-tossing vector on a shared parent domain, or any mechanism that lets the attacker fix the pre-auth session id).
2. Victim, using that same (attacker-known) session, navigates to `/auth/github` and completes the GitHub OAuth consent flow, hitting `GithubAuthenticationController#callback`.
3. Because `callback` never calls `reset_session`, the session id remains the one the attacker fixed in step 1, but now `session[:user_id]` is set to the victim's `User#id` and `session[:authenticated] = true`.
4. Attacker reuses the known session cookie against the Shipit host and is now treated as the authenticated victim by `current_user`/`UserRequiredMiddleware` across the engine, inheriting the victim's team-based authorization and access to their `github_access_token`.
