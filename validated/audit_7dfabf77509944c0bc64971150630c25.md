### Title
Webhook signature verification selects the wrong tenant's secret, letting an attacker with one organization's webhook secret forge events against another organization's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate a delivery's HMAC using `repository_owner`, a field read straight out of the *unverified* JSON body. The event handlers, however, resolve the repository/stack that the event actually acts on using a *different* field from the same body: `repository.full_name`. Because Shipit supports multiple GitHub Apps/organizations each with its own `webhook_secret` (as shown by the multi-app fixture `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls one configured organization (and therefore knows that organization's `webhook_secret`) can craft a payload whose `repository.owner.login` matches their own org (so their own secret validates it) while `repository.full_name` points at a repository belonging to a completely different, unrelated organization hosted on the same Shipit instance.

### Finding Description
- `verify_signature` derives the signing key from the payload before the payload is trusted: [1](#0-0) 
- `repository_owner` is read directly from the attacker-controlled JSON body: [2](#0-1) 
- The org-to-secret lookup and HMAC check happen in `GitHubApp#verify_webhook_signature`, keyed per organization config: [3](#0-2) 
- Once the signature is accepted, every registered `Handler` resolves the target repository/stack from a **different** field of the same body, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 
- `Repository.from_github_repo_name` performs a straightforward DB lookup by `owner/name` parsed out of that field, with no re-check against the org whose secret validated the request: [5](#0-4) 
- `PushHandler` (and other handlers) then act on whatever stacks that lookup returns, e.g. triggering a GitHub sync: [6](#0-5) 

The equality this breaks is: **the organization whose secret authenticated the request** must equal **the repository the event is applied to**. Before the attack: `repository_owner` (used for auth) == `repository.full_name`'s owner (used for the write) for any genuine GitHub-originated delivery, because GitHub itself generates a self-consistent payload. After the attack: an adversary who owns/administers one configured organization ("org-a", with known `webhook_secret_a`) can POST directly to `/webhooks` with `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` and `webhook_secret_a` are selected and the attacker-computed HMAC validates) but `repository.full_name = "org-b/victim-repo"` (an entirely different, unrelated tenant's repository on the same Shipit instance). The signature check passes even though the event now acts on a repository whose real owner never authorized or signed anything.

### Impact Explanation
This breaks the binding between the authenticated organization and the repository actually written to, letting an attacker cross tenant boundaries within a single Shipit deployment. Concretely, forged `push` events can force `Stack#sync_github` to run against a victim stack's repository, and other spoofable event types processed the same way (e.g. `status`/`check_run`-derived deployable-status events, which the same `Handler#repository_name` pattern applies to) can flip a victim commit's CI/deployable status. Because Shipit's auto-deploy/merge pipeline consumes those statuses to decide whether a commit is safe to ship, an attacker who only controls one configured organization's webhook secret can influence deploy/merge decisions for a repository belonging to a different organization on the same instance — an unauthorized cross-repository action, satisfying the Critical bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate administrator of at least one organization configured in this Shipit instance's `github_apps` (i.e., they know that org's own `webhook_secret`, which they configure themselves when wiring up their GitHub App) — this is exactly the documented multi-tenant setup shown by `test/dummy/config/secrets_double_github_app.yml`. No GitHub compromise, TLS interception, Shipit session, or `ApiClient` token is needed; the attacker simply computes an HMAC with a secret they legitimately possess and POSTs a crafted JSON body to the public `/webhooks` endpoint.

### Recommendation
After selecting the GitHub App/secret via `repository_owner` and verifying the signature, re-validate that the same field used for org selection matches the owner segment of `repository.full_name` (or any other repository/stack-resolving field) before dispatching to handlers, rejecting deliveries where they diverge.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (per `test/dummy/config/secrets_double_github_app.yml`), and a stack for `org-b/victim-repo`.
2. As the administrator of `org-a` (who legitimately knows `webhook_secret_a`), craft a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(webhook_secret_a, raw_body)` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner` = `"org-a"`, loads `Shipit.github(organization: "org-a")`, verifies successfully against the attacker's own secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `repository.full_name = "org-b/victim-repo"` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack, an action the `org-a` administrator never had authorization to trigger.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
