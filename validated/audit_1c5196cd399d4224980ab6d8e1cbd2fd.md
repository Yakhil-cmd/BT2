### Title
Zero `last_ball_timestamp` for network-unaware signed packages silently bypasses `timestamp`-based authorization conditions in address definitions - (File: signed_message.js)

### Summary
`validateSignedMessage()` sets `last_ball_timestamp = 0` whenever a signed package omits `last_ball_unit` (the "network-unaware" case), instead of rejecting the use of any time-dependent authentifier op. Any address definition that relies on the `timestamp` op (e.g. to expire an authorization after a deadline) will silently evaluate that condition against the sentinel value `0` rather than a real reference time, exactly mirroring the CVE-2016-7431 pattern where a zero origin-timestamp bypassed NTP's anti-spoof check instead of failing safely.

### Finding Description
In `signMessage`/`validateSignedMessage`, a signed package is "network-unaware" when it has no `last_ball_unit` field: [1](#0-0) 

For this branch, the definition is taken from the message itself and `last_ball_mci`/`last_ball_timestamp` are hard-coded (`-1`/`0`) with the comment "no last_ball_unit of its own; before the fix, always behave as before (-1) to keep old units re-evaluating the same way." This `0` timestamp then flows into `objValidationState.last_ball_timestamp` used during authentifier evaluation: [2](#0-1) 

Inside `Definition.validateAuthentifiers`, address definitions can embed a `timestamp` op that compares this exact field against an attacker/definer-chosen constant: [3](#0-2) 

Because `objValidationState.last_ball_timestamp` is `0` for any signed package lacking `last_ball_unit`, a `timestamp` condition intended to gate authorization to "before deadline D" (`['timestamp', ['<', D]]`) is *always* satisfied (`0 < D`), and a condition gating "after time T" (`['timestamp', ['>=', T]]`) is *always* false — regardless of the real current time. This is analogous to the NTP bug: a sentinel/default value of `0` for a temporal reference silently defeats the intended timestamp-based check instead of causing a hard validation error.

This path is reachable by any unprivileged AA trigger sender / private counterparty: `is_valid_signed_package` in the oscript formula engine accepts signed packages with or without `last_ball_unit` and forwards them straight to `validateSignedMessage`: [4](#0-3) 

A contract author who protects a signed authorization with a time-bound address definition (e.g. multisig combined with `['timestamp', ['<', deadline]]` to expire stale off-chain-signed payment/channel-closing messages) can be defeated by a counterparty submitting the same signature package without a `last_ball_unit`, because the omission is a fully valid, "unauthenticated" way to force `last_ball_timestamp` to `0` and make the timestamp condition evaluate as if time were `0` — permanently "before" any real deadline.

### Impact Explanation
If any AA or wallet-side definition uses `timestamp` to time-box a signed authorization (a documented use case of `is_valid_signed_package`, e.g. payment channels, escrows, time-limited permissions), an attacker can strip `last_ball_unit` from the signed package to force the reference time to `0`, defeating the deadline check. Depending on how the deadline is used (e.g. authorizing a stale, more favorable balance/state after a channel should have expired, or admitting an authorization that should no longer be valid), this can lead to unauthorized fund movement or state changes inside the AA — an AA fund-loss/authorization-bypass class impact.

### Likelihood Explanation
Exploitation only requires crafting a `signed_message` object without the `last_ball_unit` field (a normal, spec-valid form of a signed package) and submitting it as trigger data to an AA that checks `is_valid_signed_package` against a definition using the `timestamp` op. No special privileges, node compromise, or network position are needed — a single unprivileged AA trigger sender can construct and submit it.

### Recommendation
Do not silently substitute `0` for `last_ball_timestamp` (and `-1` for `last_ball_mci`) in the network-unaware branch of `signed_message.js`. Either reject authentifier evaluation for definitions that use `timestamp`/`mci`/`age` ops when the signed package lacks `last_ball_unit` (fail closed), or require `last_ball_unit` whenever the target definition contains any of these context-dependent ops, so a trustworthy reference time/mci is always used.

### Proof of Concept
1. Address `X` uses definition `['and', [['sig', {...}], ['timestamp', ['<', DEADLINE]]]]`, intended to let a counterparty use a signature only before `DEADLINE`.
2. Counterparty crafts and signs a `signed_message` package as `{signed_message: {...}, authors: [{address: X, authentifiers: {...}}]}` — deliberately omitting `last_ball_unit`.
3. Submits this package as AA trigger data; the AA formula calls `is_valid_signed_package(trigger.data.pkg, X)`.
4. `validateSignedMessage` takes the "no `last_ball_unit`" branch, sets `last_ball_timestamp = 0` (`signed_message.js:251`).
5. `definition.js`'s `timestamp` op evaluates `0 < DEADLINE` → always `true`, so the authorization is accepted by the AA even though real time has passed `DEADLINE`.
