### Title
Cross-repository status webhook forges CI state and can trigger an unauthorized deploy on an unrelated stack sharing a commit sha - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha` across the entire installation, with no check that the commit's stack belongs to the repository named in the (correctly signed) webhook payload. An attacker who controls repo A can cause a `status` event to be delivered for a sha that also exists in an unrelated stack B (e.g. via a shared git history/fork), injecting a fabricated `success` status into stack B's copy of that commit and, if `continuous_deployment` is enabled on B, triggering a real deploy of a commit B never actually validated with its own CI.

### Finding Description
The claimed binding is: `commit.stack_id` (the stack whose CI state is mutated) `== payload['repository']['full_name']`'s owning stack (the stack the verified webhook is scoped to). Tracing the code shows this equality is never enforced.

- `WebhooksController#verify_signature` only checks that the payload was signed by the GitHub App belonging to `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates *which organization/app* sent the webhook, not which *stack/commit* the payload may affect: `app/controllers/shipit/webhooks_controller.rb:24-49`.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`. This lookup is **global**, scoped only by `sha`, never by `params.dig('repository','full_name')` or `repository_owner`.
- `Commit#create_status_from_github!` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, using the commit's *own* `stack_id` (i.e. stack B's id), not any id derived from the webhook payload: `app/models/shipit/commit.rb:165-169`.
- `Status.replicate_from_github!` creates the `Status` row with `state: github_status.state` taken directly from the attacker-controlled payload: `app/models/shipit/status.rb:24-33`.
- `Status#schedule_continuous_delivery` (via `after_commit`) calls `commit.schedule_continuous_delivery`, which (per `app/models/shipit/stack.rb`'s `schedule_continuous_delivery`/`ContinuousDeliveryJob`) enqueues `ContinuousDeliveryJob.perform_later(stack)` for stack B.
- `ContinuousDeliveryJob#perform` checks `stack.continuous_deployment?`, schedule window, and `stack.occupied?`, then calls `stack.trigger_continuous_delivery` (`app/jobs/shipit/continuous_delivery_job.rb:10-21`), which internally calls `next_expected_commit_to_deploy`/`next_commit_to_deploy` → `commits_to_deploy.find(&:deployable?)` (`app/models/shipit/stack.rb:332-342`) and `Commit#deployable?` returns true once `success?` is true and the commit isn't `blocked?`/`locked?` (`app/models/shipit/commit.rb:227-229`).
- The existing test `test/models/shipit/stack_test.rb:700-708` confirms `trigger_continuous_delivery` really creates a `Deploy` once these conditions hold, and `test/models/commits_test.rb:291-297` / `241-261` confirm the same status-creation-triggers-CD path is exercised elsewhere in the suite, just never with a cross-repo sha collision scenario.

For this to fire, the attacker needs a commit sha in their own repo A that is identical to an sha already present in stack B's `commits` table (fully feasible for forks/mirrors of public/shared history, or any situation where the same content-addressed commit is reachable from two differently-owned repositories). The attacker then only needs to set a `success` status on that sha in repo A (trivially done via GitHub's status API on their own repo, or their own CI), which GitHub will deliver as a correctly-signed `status` webhook for organization A. `verify_signature` passes because it's a genuine signature for org A — it says nothing about stack B. `drop_unhandled_event` and `ExplicitParameters` schema checks pass because `sha`/`state` are present and well-formed. Nothing in the model layer (`Commit`, `Status`, `Stack`) re-derives or checks repository ownership before writing the status or before letting the resulting state feed `deployable?`.

### Impact Explanation
An attacker who owns/controls repository A (no Shipit credentials required) can write a `Status` record onto a commit belonging to an entirely different tenant's stack B, and where `continuous_deployment: true` is enabled on B, can trigger a genuine `Deploy` of an already-existing but previously-undeployed commit in B — i.e., a payload for one repository mutating another repository's stack/commit and causing an unauthorized deploy. This matches the "Critical" impact category (payload for one repo mutating another's stack/commit/task, unauthorized deploy). The blast radius spans every stack in the installation whose commits happen to share a sha with anything reachable by the attacker (forks, mirrors, shared history, or any repo the attacker can arrange to have the same content-addressed commit in). This is repeatable per colliding sha.

### Likelihood Explanation
Preconditions: stack B must have `continuous_deployment: true`, must have a genuine undeployed commit C, and C's sha must also be producible/controllable in a repo A that the attacker owns and that has a Shipit GitHub App installation (so a legitimately-signed webhook can be sent). This is realistic for forked/mirrored public repositories where commit shas are shared across many repos by construction, or for monorepo/multi-remote setups. No Shipit secrets, sessions, or privileged roles are needed — only ordinary control over a GitHub repository plus the ability to set a commit status (via GitHub UI, API, or a CI job) on a commit whose sha collides with a target stack's pending commit. The attacker cost is low and the action is repeatable against any stack sharing a colliding sha.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to only mutate commits belonging to stacks whose repository matches the payload's `repository.full_name`/owner, e.g. filter `Commit.where(sha: params.sha)` further by `joins(:stack).where(stack: { repository: matched_repository })`, or resolve the repository from the payload first and constrain the query to that repository's stacks before iterating.

### Proof of Concept
```ruby
test "status webhook from a different repository cannot forge CI state and trigger a deploy on an unrelated stack" do
  repo_a = shipit_repositories(:repo_a) # attacker-owned
  repo_b = shipit_repositories(:repo_b) # victim
  stack_b = shipit_stacks(:stack_b, repository: repo_b, continuous_deployment: true)
  shared_sha = "deadbeef" * 5

  commit_b = stack_b.commits.create!(sha: shared_sha, message: "x", author: shipit_users(:shipit),
                                       committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature genuinely valid for repo_a's org

  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => repo_a.full_name, 'owner' => { 'login' => repo_a.owner } }
  }.to_json

  assert_enqueued_with(job: ContinuousDeliveryJob) do
    assert_difference -> { Deploy.count }, +1 do
      post :create, body:, as: :json
      commit_b.reload
      assert_predicate commit_b, :deployable?   # binding equality: stack_b == webhook's stack -> false, yet status applied
    end
  end
end
```
This demonstrates the broken binding: the equality `commit_b.stack == repository_owning_stack(repo_a payload)` is false, yet `commit_b`'s status is mutated and a `Deploy` for `stack_b` is enqueued/created anyway.
