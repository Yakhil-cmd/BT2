## Title
Stack-scoped API token can read CCMenu status of any stack, not just the one it authorizes - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`ApiClient` records can be scoped to a single `Stack` via `belongs_to :stack, optional: true` and the `stack_id` column, as demonstrated by the `here_come_the_walrus` fixture (`stack: shipit`) which is documented and tested as "an api client scoped to a stack will only see that one stack." [1](#0-0) [2](#0-1)  The generic `BaseController#stack` method enforces this scope by first filtering the queryable `stacks` collection to `current_api_client.stack_id` before resolving the URL param. [3](#0-2)  However, `Api::CCMenuController` overrides `stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id` restriction. [4](#0-3) 

## Finding Description
The binding that should hold is: **the stack a token authorizes == the stack the endpoint touches**. `BaseController` establishes this invariant generically:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

Every other API controller (e.g. `Api::HooksController`, `Api::StacksController`) inherits this `stack`/`stacks` behavior and is therefore correctly restricted to the token's own stack when `stack_id` is set. `Api::CCMenuController`, however, redefines `stack`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

This query is scoped to `Stack.from_param!`, i.e. **all** stacks, not `current_api_client.stacks`. The controller still enforces the `read:stack` permission check via `require_permission :read, :stack` [6](#0-5)  — but that check only validates the permission bit, not which specific stack the client is bound to. `check_permissions!` in `ApiClient` only inspects the `permissions` array, never `stack_id`. [7](#0-6) 

Before the equivalent of the "fix" (i.e., using `BaseController#stack`) would apply: a token scoped to stack A with `read:stack` permission is denied access to stack B because `stacks` filters by `current_api_client.stack_id`. After the actual code path in `CCMenuController`: the same token can pass `stack_id=B` in the request and successfully render CCMenu XML status (build status, last build label, activity, web URL) for stack B, since `Stack.from_param!` is unscoped. This exactly mirrors the FrankenDAO class of bug — a verified/authorized scope (`proposalsCreated`/here, `stack_id`) not being the field actually acted upon (`proposalsPassed`/here, the stack looked up and returned).

## Impact Explanation
This is an authorization bypass: it grants unauthenticated read of stack state/deploy status across stacks whose visibility is supposed to be restricted per-token. This matches "High - unauthenticated read of stack state, task streams or deploy output" for any stack, using a token that is documented and designed to be limited to one specific stack. The CCMenu endpoint exposes build/deploy status details (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) for arbitrary stacks. [8](#0-7) 

## Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token with `read:stack` permission (e.g., a CCMenu token intentionally issued to a specific team/stack via `CCMenuUrlController`) can trivially trigger this by changing the `stack_id` route/query parameter to another stack's identifier — no additional privilege or secret is required beyond the token they already legitimately hold for their own stack.

## Recommendation
Change `Api::CCMenuController#stack` to reuse the scope-respecting resolution from `BaseController`, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

removing the override entirely (or delegating to `super`), so that a stack-scoped token can only resolve stacks within `current_api_client.stacks`.

## Proof of Concept
1. Admin issues a CCMenu/API token scoped to `stack_id = A` (`ApiClient` with `stack: A`, `permissions: ['read:stack']`), analogous to the `here_come_the_walrus` fixture. [2](#0-1) 
2. Attacker (holder of that token) sends `GET /api/stacks/:B/ccmenu.xml` with `stack_id` (or path param) set to stack `B`, using Basic Auth with the token as documented in `CCMenuUrlController`/tests. [9](#0-8) 
3. `Api::CCMenuController#show` calls `stack.deploys_and_rollbacks.last`, where `stack` resolves via the unscoped `Stack.from_param!(params[:stack_id])`, returning stack `B`'s data despite the token only being authorized for stack `A`. [10](#0-9) 
4. Response renders stack `B`'s CCMenu status successfully (HTTP 200), confirming the scope bypass.
