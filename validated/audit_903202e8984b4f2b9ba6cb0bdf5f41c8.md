## Title
`handleJoint()`'s async `ifOk` dry-run of AA triggers can throw while holding the global `handleJoint` mutex, permanently deadlocking all future unit validation - ([File: network.js])

### Summary
`network.js:handleJoint()` acquires the global lock key `'handleJoint'` via `mutex.lock(['handleJoint'], ...)` before validating any incoming/posted unit, and only calls the returned `unlock()` once processing of that unit finishes on every branch. The `ifOk` branch, however, is declared `async function(objValidationState, validation_unlock)` and, when `conf.bDryRunNewTriggers` is enabled, performs `await aa_composer.dryRunPrimaryAATrigger(...)` for any payment output that lands on a registered AA address, before ever calling `unlock()`. If this dry run throws (synchronously or via an unresolved rejection deep inside `aa_composer.js`'s `handleTrigger`, which is full of un-caught `throw Error(...)` invariant checks), the exception surfaces as a rejection of the `async` `ifOk` promise. Because `validation.validate()` invokes `callbacks.ifOk(...)` without awaiting/catching its return value, this rejection is never observed, `unlock()` is never invoked, and the `'handleJoint'` mutex key remains locked forever.

### Finding Description
`mutex.lock`/`mutex.exec` only marks a key array as unlocked, and drains the `arrQueuedJobs` queue, when the `unlock` callback handed to `proc` is invoked: [1](#0-0) 

`network.js:handleJoint()` acquires this lock for every unit (network-received or locally posted) before validation: [2](#0-1) 

The `ifOk` callback is `async` and, when `conf.bDryRunNewTriggers` is set, awaits a dry run of the AA trigger logic for every output address that resolves to a registered AA, *before* `writer.saveJoint(...)` is reached and *before* `unlock()` is called: [3](#0-2) 

`dryRunPrimaryAATrigger()` calls into `handleTrigger()`, which is riddled with un-guarded `throw Error(...)` statements executed synchronously inside nested DB callbacks (e.g. bad AA definition shape, missing `base_aa`, unexpected params): [4](#0-3) [5](#0-4) 

Because `ifOk` is an `async function` invoked as a plain callback (not awaited) from `validation.js`, any exception thrown while executing the dry run turns `ifOk`'s implicit promise into a rejected promise that nothing observes. Execution never reaches the `writer.saveJoint(...)` call, so `validation_unlock()` and the outer `unlock()` (for key `'handleJoint'`) are never invoked. Since `mutex.exec()` never calls `release(['handleJoint'])` or `handleQueue()` in that case, the `'handleJoint'` key stays permanently marked as locked in `arrLockedKeyArrays`.

Every other user of the same lock key — including a node's own composed transactions (`divisible_asset.js:320`, `indivisible_asset.js:833`) and every subsequently received/posted unit in `network.js:handleJoint`) — will be queued via `isAnyOfKeysLocked(['handleJoint'])` and never dequeued, since `handleQueue()` is only invoked from inside `unlock()`. [6](#0-5) [7](#0-6) [8](#0-7) 

This mirrors the CVE-2026-80678 bug class exactly: a shared resource (there, `i2c_imx->slave`; here, the `'handleJoint'` mutex key) is only released/cleared on the success path, and an error path that occurs after the resource was claimed but before the operation completes leaves it permanently stuck, breaking every subsequent, unrelated consumer of that same shared resource.

### Impact Explanation
Once the `'handleJoint'` mutex is permanently stuck, the affected node can never validate or save another unit: neither units received from peers nor units the node itself wants to broadcast (wallet payments, AA responses, etc.) can proceed, since they all funnel through `mutex.lock(['handleJoint'], ...)`. This matches the allowed impact category "a network unable to confirm new units" for that node, and if triggered broadly (any full node running with `conf.bDryRunNewTriggers` enabled processes the same triggering unit) it stalls transaction processing/finality across affected nodes.

### Likelihood Explanation
The trigger is a single unit posted by any unprivileged party: a payment to a registered AA address is enough to enter the dry-run code path in `ifOk`. The dry run then runs the full, complex `handleTrigger`/formula-evaluation pipeline, which contains many un-caught `throw` statements for conditions not fully excluded by AA-definition validation at registration time (e.g., parameterized/base_aa chains, `params` mismatches). Reaching one of these edge cases requires crafting a payload/definition combination that AA definition validation missed but that dry-run execution flags as an invariant violation — plausible given the size and complexity of `handleTrigger`, but not trivially guaranteed for every code path, so likelihood is assessed as medium rather than high.

### Recommendation
- Wrap the `await aa_composer.dryRunPrimaryAATrigger(...)` (and the preceding `await db.query(...)`) in `network.js`'s `ifOk` in a `try { ... } catch (e) { ... }` that always calls `validation_unlock()` and `unlock()` before propagating/logging the error.
- More generally, make `handleJoint`'s `ifOk` callback robust to promise rejection: since `validation.validate()` invokes it fire-and-forget, any unexpected exception must be caught locally and must release the mutex before further action, exactly analogous to how the kernel fix moved slave/lock housekeeping to guarantee it happens under all code paths.
- Consider defensively converting `handleTrigger`'s internal invariant `throw Error(...)` calls into structured error returns so a single malformed/unexpected AA definition edge case cannot escape as an uncaught exception from deep inside dry-run execution.

### Proof of Concept
1. Enable `conf.bDryRunNewTriggers` (as recommended/used in typical hub/node configuration) so `network.js:1271` dry-run branch is active.
2. Register an AA definition whose structure passes `validate_definition` at registration time but causes `handleTrigger`/`aa_composer.js` to hit one of its un-guarded `throw Error(...)` invariants when actually executed with attacker-chosen trigger data (e.g., a payload/`params` combination that differs at dry-run evaluation time from what static definition validation checked, matching one of the guard checks at `aa_composer.js:419-445`).
3. As an unprivileged party, broadcast/post a unit containing a `payment` message whose output goes to that AA's address.
4. `network.js:handleJoint()` acquires the `'handleJoint'` mutex, validates the unit, and — because the output targets a registered AA — invokes `aa_composer.dryRunPrimaryAATrigger` inside the `async ifOk` handler before calling `unlock()`.
5. The crafted trigger data causes `handleTrigger` to synchronously `throw`, which is not caught anywhere in the call chain; the `async` `ifOk` promise rejects silently (uncaught rejection, not awaited by `validation.js`), and `unlock()` for `'handleJoint'` is never called.
6. Observe that `mutex.getCountOfLocks()`/`isAnyOfKeysLocked(['handleJoint'])` remains permanently true, and all subsequent calls to compose/send payments (`divisible_asset.js`, `indivisible_asset.js`) or to process any further posted/received unit (`network.js:handleJoint`) queue indefinitely and never execute, confirming the permanent DoS on unit confirmation for that node.
