Found the analog: the webhook signature is verified against the GitHub App configured for the **organization** derived from `params.dig('repository','owner','login')` (with a fallback to `params.dig('organization','login')`), but the event handlers resolve the target **repository/stack** from a completely different, independently-controlled payload field: `payload.dig('repository', 'full_name')`.

### Title
Webhook signature validated against `repository.owner.login`/`organization.login` while event handlers act on the independently-controlled `repository.full_name` field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Once the signature passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full raw JSON body to handlers such as `PushHandler`, which resolve the affected repository via `Handler#repository_name`, reading `payload.dig('repository', 'full_name')` and looking it up with `Repository.from_github_repo_name` [2](#0-1) [3](#0-2) .

### Finding Description
The binding that should hold is: **organization authenticated (signature verified against) == organization owning the repository the handler writes to**. The signature check trusts `repository.owner.login` (or falls back to a separate top-level `organization.login` key) to pick which App's `webhook_secret` validates the HMAC [4](#0-3) . However, the field actually consumed by the business logic to determine which Stack/Repository gets acted on is `repository.full_name`, taken from the very same attacker-supplied JSON body and never cross-checked against `repository.owner.login` [5](#0-4) . In a single-organization installation this is not exploitable because there is only one webhook secret. But in the documented multi-organization configuration (`config/secrets.development.example.yml` shows `github: { someorg: {...}, someotherorg: {...} }`), each org has its own `webhook_secret`, and `Shipit.github(organization:)` selects among them by name. An attacker who holds a valid webhook secret for org A (e.g., because they administer a GitHub App/repo under org A that is also connected to this Shipit instance) can craft a payload where `repository.owner.login` = `"orgA"` (so the signature validates against org A's secret) while `repository.full_name` = `"orgB/some-repo"`. The signature check passes using org A's secret, but the dispatched handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves and mutates state for `orgB/some-repo` — a repository under a different, uncompromised organization.

### Impact Explanation
This breaks the trust boundary between organizations that the multi-org `github:` webhook configuration is designed to enforce, allowing cross-repository/cross-organization writes: an attacker who controls only org A's webhook secret can trigger `Stack#sync_github` (push handler), inject fabricated commit statuses (`StatusHandler`), or manipulate check-suite/pull-request state for stacks belonging to org B, without ever possessing org B's webhook secret or repository write access. Depending on which handler is targeted, this can affect deploy-eligibility signals (CI status, check suites) that gate `Shipit.yml`-driven deploy/merge logic, i.e., an unauthorized influence over deploy decisions for a repository the attacker does not control.

### Likelihood Explanation
Exploitability requires the deployment to use the documented multi-organization `github:` config with distinct `webhook_secret`s per org and requires the attacker to legitimately hold (or have access to configure) a webhook secret for at least one onboarded organization — this is a real, supported deployment mode per `docs/setup.md`, not a hypothetical misconfiguration, but it is not the default single-org case, and cross-org attacks additionally require guessing/knowing the victim's exact `owner/repo` full name, which is generally public information on GitHub. Given these preconditions, likelihood is moderate rather than trivial.

### Recommendation
In `Handler#repository_name` (or in `WebhooksController`), verify that `payload.dig('repository', 'owner', 'login')` (the field the signature was checked against) matches the owner segment of `payload.dig('repository', 'full_name')` before resolving/acting on the target repository, rejecting the webhook if they diverge.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` per `docs/setup.md`'s multi-org example.
2. As an attacker with a valid `orgA` webhook secret, craft a `push` event JSON body: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/target-repo"}, "ref": "refs/heads/main", "after": "<attacker-chosen sha>"}`.
3. Sign the raw body with `orgA`'s `webhook_secret` and set `X-Hub-Signature` accordingly; `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and the signature validates [4](#0-3) .
4. `PushHandler.call(params)` runs `repository_name` → `"orgB/target-repo"` → `Repository.from_github_repo_name` looks up and mutates stacks belonging to `orgB` [6](#0-5) , even though the request never proved knowledge of `orgB`'s secret.

**Caveat on confidence**: I was unable to fully confirm within the tool budget whether the `organization` webhook event or other handlers perform additional owner-consistency checks elsewhere in `app/models/shipit/webhooks/handlers/**` beyond `handler.rb`'s base `repository_name`, nor whether `MembershipHandler` (which creates teams from `organization.login`) has separate binding issues. A Devin session with full file access would be needed to exhaustively check every handler subclass for owner/full_name cross-validation.
