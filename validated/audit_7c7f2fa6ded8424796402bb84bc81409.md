Based on the code in `runtime/src/inflation_rewards/mod.rs`, the claimed vulnerability does not hold.### No vulnerability found for this question.

**Rationale:** The exploit theory requires `commission_split_preserve_lamports` to create new lamports when aggregated across many stake accounts, but the function is provably an exact partition of its input.

`commission_split_preserve_lamports` floors the staker portion and assigns the exact remainder to the voter, guaranteeing `voter_rewards + staker_rewards == on` for every single call — this is enforced by an existing property-based test in the repo (`test_commission_split_preserve_lamports_properties`, Invariant 1: `prop_assert_eq!(voter + staker, rewards)`). [1](#0-0) [2](#0-1) 

The `rewards`/`on` value passed into this function per stake account is itself computed upstream as an independent floor-division of that stake's points against the epoch's `point_value.points`/`point_value.rewards` (`tower_points.checked_mul(point_value.rewards).checked_div(point_value.points)`), which can only under-allocate relative to the true proportional share (floor of a fraction), never over-allocate. [3](#0-2) 

Since each per-stake call conserves its own input exactly (`voter+staker == on`), summing this exact identity over any number of attacker-controlled stake accounts yields `sum(voter_i)+sum(staker_i) == sum(on_i)`, which is bounded above by the pre-computed, floor-truncated per-stake reward pool — never by more. There is no rounding "remainder duplication" mechanism: the remainder assigned to the voter in each call is drawn from that same call's already-fixed `on`, not from any shared or reused budget. This is further backstopped by an explicit runtime assertion at the aggregate distribution stage checking `point_value.rewards >= distributed_lamports + distributed_to_incinerator_lamports + burned_lamports + total_stake_rewards_lamports`, which would panic (halt) rather than silently over-mint if some other code path violated conservation. [4](#0-3) 

Setting `inflation_rewards_commission_bps` to boundary values (1 or 9999) does not change this conservation property — the property test explicitly covers the full `0..=u16::MAX` commission range and all `u64` reward values and the invariant holds unconditionally, including at boundaries (Invariants 3–4). [5](#0-4) 

Therefore, controlling both the vote account's commission collector and delegated stake accounts, and repeating the operation over many low-value epochs, cannot net-mint lamports relative to `point_value.rewards` through this function.

fn commission_split_preserve_lamports(commission_bps: u16, on: u64) -> (u64, u64, bool) {
    const MAX_BPS: u16 = 10_000;
    const MAX_BPS_U128: u128 = MAX_BPS as u128;
    match commission_bps.min(MAX_BPS) {
        0 => (0, on, false),
        MAX_BPS => (on, 0, false),
        split => {
            let staker_bps = MAX_BPS
                .checked_sub(split)
                .expect("commission cannot be greater than MAX_BPS");
            let staker_rewards = u128::from(on)
                .checked_mul(u128::from(staker_bps))
                .expect("multiplication of a u64 and u16 should not overflow")
                / MAX_BPS_U128;
            let staker_rewards = staker_rewards as u64;
            let voter_rewards = on
                .checked_sub(staker_rewards)
                .expect("staker rewards cannot exceed total rewards");

            (voter_rewards, staker_rewards, true)
        }
    }
}
