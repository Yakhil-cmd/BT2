### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no constraint tying the webhook's originating repository to the `Commit`/`Stack` it mutates. Because git commit SHAs are content-addressed and are shared across forks/duplicated history, a legitimately-signed webhook from an attacker-owned repository can carry a `sha` that also exists as a `Commit` row in a victim's unrelated stack, causing the handler to write a forged `Status` into the victim's stack.

### Finding Description
The broken binding, stated explicitly: for every `Status` row belonging to `Commit` `c`, it should hold that `status.stack_id == stack_of_repository_that_emitted_the_status_event`. The code instead guarantees only `status.stack_id == commit.stack_id` for whichever `Commit` row happens to match the incoming `sha` — with no check that `commit.stack_id`'s repository is the repository named in the webhook payload.

Code path:
- `StatusHandler#process` [1](#0-0)  does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. The `params` schema accepts only `sha, state, description, target_url, context, created_at, branches` [2](#0-1)  — there is no repository identifier used to filter which `Commit`/`Stack` should receive the status.
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using **that commit's own** `stack_id` [3](#0-2) .
- `Status.replicate_from_github!` does `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` [4](#0-3) , which correctly scopes idempotency by `stack_id`, but this offers no protection because the `stack_id` handed to it is derived from *whichever* matching `Commit` row is being iterated — including one that belongs to a repository that never sent this webhook.

Root cause: because git SHAs are content-addressed, a fork of the victim's repository (or any repository sharing history/commits with the victim, e.g. via merge, cherry-pick, or common upstream) will contain `Commit` rows with identical `sha` values across two different `Stack`s. Since `Commit.where(sha: params.sha)` has no repository scoping, a single incoming status webhook — legitimately signed by GitHub for the attacker's own repository/webhook secret — is applied to **every** `Commit` row in the database sharing that `sha`, including the victim's stack. The attacker does not need the victim's webhook secret or any Shipit credential: they only need a repository they control (with the GitHub App/webhook configured, which any GitHub user can do for their own repos/forks) whose history overlaps the victim's, and they repeatedly POST `success` status events for that shared sha.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) validate that the request was really sent by GitHub for the attacker's own installation/repo — they do not, and cannot, validate that the `sha` referenced belongs only to that repository's commit graph, since Shipit has no concept binding a `Status` write to the specific repository asserted in the webhook payload versus the `Commit` row(s) that happen to match by SHA.

### Impact Explanation
An attacker can cause `success`/`failure`/`error`/`pending` `Status` rows to be written into a victim's `Stack` for a `Commit` the victim's own stack tracks, without ever authenticating to or being a maintainer of the victim's repository. This directly affects `Commit#state`/`Commit#deployable?` [5](#0-4)  and can enable deploys to proceed on a commit the victim believes is failing CI, or conversely poison the victim's CI history with fabricated failures — a payload from one repository mutating another's stack/commit, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable indefinitely and applies to any pair of repositories that share commit history (very common with forks, which is the standard GitHub collaboration model), so the blast radius spans any multi-tenant Shipit instance hosting forked/related repositories.

### Likelihood Explanation
Preconditions are attacker-cheap: the attacker needs (1) a repository they control that shares commit history with the victim's repository (trivially achieved by forking a public victim repo — shared ancestor commits carry identical SHAs), and (2) that repository configured as a Shipit stack with its own legitimately-issued webhook credentials (which the attacker can set up for their own fork/repo without any victim or operator privilege). No Shipit session, API token, or GitHub secret belonging to the victim is required. This is realistic and repeatable, not a theoretical hash collision — fork-shared history guarantees identical SHAs for shared ancestor commits.

### Recommendation
Scope `StatusHandler#process` (and other SHA-keyed handlers) by the repository asserted in the webhook payload: resolve the target `Repository`/`Stack` from `payload.repository` (matched against the app's `Repository` record, ideally via GitHub repo ID) first, then only query/update `Commit` rows belonging to that stack (e.g., `commit.stack.repository.github_id == payload.repository.id`), instead of matching solely on `sha` across the whole database.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status event for one repository must not write into an unrelated stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:some_other_repo), environment: "production", branch: "master")

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  # Attacker's own, legitimately-signed webhook for their own repo/sha
  payload = { sha: shared_sha, state: "success", context: "ci/attacker" }
  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  victim_commit.reload
  # Binding under test: status.stack_id must equal the stack of the repo that emitted it (attacker_stack),
  # NOT the victim_stack, even though both Commit rows share the sha.
  assert_empty victim_commit.statuses.where(context: "ci/attacker"),
    "victim stack must not receive a status event that originated from the attacker's repository"
  assert attacker_commit.reload.statuses.where(context: "ci/attacker").exists?
end
```
This demonstrates that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup writes into `victim_commit.statuses` despite the event never being authorized by or for the victim's repository, violating the stated binding.
