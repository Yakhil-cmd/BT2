### Title
Cross-repository commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming `status` webhook against the GitHub organization named in the payload (`repository.owner.login`), but `Shipit::Webhooks::Handlers::StatusHandler` never checks that the commit being updated actually belongs to a stack/repository owned by that authenticated organization. It looks up and mutates commits by raw SHA alone, across the entire `commits` table. This breaks the binding "organization that authenticated == repository that is written," allowing any onboarded, otherwise-legitimate GitHub organization to inject a commit status onto a commit belonging to a completely different, unrelated repository/organization tracked by the same Shipit instance, as long as that commit's SHA also exists there (trivially true for forks, which are common on GitHub and share identical, content-addressed commit SHAs with their upstream).

### Finding Description
Signature verification is performed once, per-request, keyed off the organization named in the payload itself: [1](#0-0) [2](#0-1) 

This only proves that the request was signed with the webhook secret belonging to whatever organization is named inside `repository.owner.login`/`organization.login` in the same payload — it does not constrain which commits/stacks the handler is allowed to touch.

`StatusHandler`, unlike every other handler in the codebase (which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting, see `Handler#stacks`/`#repository_name` and the pull-request handlers), performs no repository scoping at all: [3](#0-2) 

It requires only `sha` and `state` and runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` against the global `commits` table, with no `stack_id`/repository filter, unlike the generic `Handler#stacks` helper other handlers use: [4](#0-3) 

`create_status_from_github!` then calls `add_status`, which has real side effects: it emits `commit_status`/`deployable_status` hooks and — critically — calls `stack.schedule_merges` whenever the new status is `pending` or `success`: [5](#0-4) 

The test suite confirms a `success` status transition enqueues `ProcessMergeRequestsJob` for the affected stack: [6](#0-5) 

**Attack path (equality broken):** `organization that signed the webhook (repository.owner.login checked in verify_signature)` ≠ `repository/stack whose commit is mutated (looked up purely by sha in StatusHandler)`.

Because Git commit SHAs are content-addressed, any GitHub fork of a tracked repository shares identical commit SHAs with the upstream repository for all commits present at fork time. An attacker who legitimately controls *any* organization/repository already onboarded onto the shared Shipit instance (i.e., they know or can generate a validly signed webhook for their own org — no signature forgery is required, GitHub itself will sign it) can:
1. Fork or otherwise obtain a repository sharing history with the victim's tracked repository (or otherwise learn a SHA also present in the victim repo).
2. Post (or trigger, e.g. via the GitHub API/Checks/Commit Status API on their own repo) a `status` event for that SHA with `state: "success"`.
3. GitHub delivers this webhook to Shipit, correctly signed with the attacker's own org's `webhook_secret`; `verify_signature` passes because it only checks that org's secret against the payload.
4. `StatusHandler` finds ALL `Commit` records across the entire Shipit database with that SHA — including the one belonging to the victim's unrelated stack — and applies the forged status to it, triggering `schedule_merges` (kicking off `ProcessMergeRequestsJob`) and hook emission on the victim's stack.

### Impact Explanation
This is a cross-repository write: an actor with control of one onboarded organization can inject a forged CI status onto a commit belonging to a different organization/repository's stack, without any credentials for that target repository. Since a forged `success` status feeds directly into `Commit#add_status` → `stack.schedule_merges`, this can cause an unauthorized merge/deploy to proceed on a target stack whose actual CI never reported success — meeting the "unauthorized deploy, rollback or merge" Critical bar, and independently the "cross-repository writes" Critical bar (a `Status` record and its associated hooks are created on a stack the attacker's organization does not own).

### Likelihood Explanation
Likelihood is realistic in any deployment of this engine that follows the documented multi-organization configuration pattern (`config/secrets.development.example.yml` shows a supported multi-org `github:` block, each with its own `webhook_secret`). No secret needs to be stolen or brute-forced — GitHub will correctly sign the forgeable webhook using the attacker's own legitimately configured org credentials. The only prerequisite is a commit-SHA collision with the victim's tracked repository, which is trivially satisfied for any forked repository (a very common scenario for open-source or internally-forked codebases) since Git SHAs are deterministic over content and forks initially share full commit history.

### Recommendation
- Short term: In `StatusHandler#process`, scope the `Commit` lookup to the repository identified by the payload's `repository.full_name` (as every other handler already does via `Handler#stacks`/`repository_name`), e.g. `stacks.commits.where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`, and require the `repository` field in the handler's `params` block so it is enforced.
- Long term: Audit all webhook handlers to guarantee that any lookup keyed by a value that is not unique per-repository (SHA, branch name, PR number) is always additionally scoped by the repository resolved from the authenticated payload, and add a regression test asserting that a `status` event for a shared SHA does not affect commits in unrelated stacks/repositories.

### Proof of Concept
1. Configure two organizations in Shipit's multi-org `github:` config, `victim-org` (tracks `victim-org/app`, stack `production`) and `attacker-org` (tracks `attacker-org/app-fork`, a fork of `victim-org/app`).
2. Confirm `attacker-org/app-fork` contains a commit with SHA `abc123...` identical to one tracked in `victim-org/app`'s `production` stack (guaranteed for shared fork history).
3. From `attacker-org/app-fork`, trigger (via GitHub UI/API, e.g. a status check on that commit) a `status` webhook event with `sha: abc123...`, `state: success`. GitHub signs this webhook with `attacker-org`'s real `webhook_secret`.
4. Shipit's `WebhooksController#verify_signature` validates successfully against `attacker-org`'s secret (since `repository.owner.login == "attacker-org"`).
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")`, finds the matching `Commit` row belonging to `victim-org/app`'s `production` stack, and calls `create_status_from_github!`, which records a forged `success` status and invokes `stack.schedule_merges` on the victim's `production` stack — despite the request never being signed by `victim-org`'s webhook secret.

module Shipit
  module Webhooks

          requires :state, String

        def process

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
