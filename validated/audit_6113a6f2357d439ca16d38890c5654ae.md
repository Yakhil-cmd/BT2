## Title
AA `attestation[[]]` getter misattributes historical attestations to a reused address after its controlling definition changes - ([File: formula/evaluation.js])

## Summary
The `attestation[[...]]` oscript function, callable from any AA formula, looks up attestations by `address` alone and does not check whether the address's controlling definition changed after the attestation was issued. This is the same class of bug as the reported `NodeId` reuse issue: a value (an attestation) that was validly bound to a specific historical controller of an identifier (`address`) is later resolved via the *current* mapping of that identifier, which can belong to a different party after a legitimate address hand-off. Notably, ocore already has the correct mitigation pattern implemented for the identical scenario in `storage.filterAttestedAddresses()`, but it was not applied to the AA-facing `attestation[[]]` getter.

## Finding Description
In ocore, an address is a fixed chash, but the *definition* that controls signing rights for that address can be changed at any time via an `address_definition_change` message, effectively transferring control of the address to a different key/party while its chash (and hence external identity) stays the same.

`storage.filterAttestedAddresses()` correctly accounts for this: it only accepts an attestation as valid if it was posted *after* the last definition change for that address, filtering it via the `address_definition_changes` table: [1](#0-0) 

This function feeds asset conditions such as `spender_attested`, so an old attestation about a stale controller of an address cannot be reused as proof-of-attestation for the new controller of the same address chash.

However, the `attestation[[...]]` getter used inside AA formulas (reachable by any AA author and any AA trigger sender) performs the lookup without this protection. It queries the `attestations`/`attested_fields` tables filtered only by `attestor_address` and `address`, with no join against `address_definition_changes`: [2](#0-1) 

The oscript-level `attested` condition used in address/asset definitions has the same protection via `storage.filterAttestedAddresses`: [3](#0-2) 

but the AA formula `attestation[[]]` getter does not call this function, and instead re-implements the query directly without the definition-change cutoff.

Because attestation records store only `unit`, `attestor_address`, and `address` (with no snapshot of the controlling definition at attestation time): [4](#0-3) 

any AA formula relying on `attestation[[attestors=..., address=X]]` cannot distinguish "X was attested while controlled by party A" from "X is now controlled by party B, but still shows as attested."

## Impact Explanation
Any AA that gates a payout, whitelist entry, unlock, or other financial decision on `attestation[[...]]` (e.g., KYC gating, reputation gating, oracle-attested identity checks for staking/rewards) can misattribute the benefit of a stale attestation to whoever currently controls the address, after the address's definition has legitimately changed hands (e.g., ownership transfer via `address_definition_change`, key rotation to a new custodian, or resale of a wallet address). This directly causes AA fund loss/misallocation to an unintended party — mirroring the reward misattribution in the original report — and is reachable purely by posting units (address definition change) and AA triggers, with no privileged access required.

## Likelihood Explanation
The prerequisite (an address changing its controlling definition after being attested, then the new controller triggering an AA that relies on `attestation[[]]`) is a normal, permitted operation in ocore (`address_definition_change` is a standard message type), and AA developers are expected to use `attestation[[]]` for identity/whitelist gating since it is a documented oscript primitive. The bug is a straightforward logic gap (missing filter that already exists elsewhere in the codebase for the identical purpose), making it plausible to trigger without any adversarial cooperation from the original attested owner.

## Recommendation
Apply the same protection used in `storage.filterAttestedAddresses()` to the `attestation[[]]` formula getter in `formula/evaluation.js`: join/filter attestations so they are only honored if `main_chain_index` of the attestation is greater than the `main_chain_index` of the most recent `address_definition_change` for that `address` (as of the relevant `last_ball_mci`/`mci`), both for the stable-unit query and, analogously, for the unstable/recent-AA-response branch.

## Proof of Concept
1. Attestor `ATTESTOR` posts an `attestation` message attesting `address=X` (e.g., `{kyc: 'passed'}`) while `X` is controlled by Alice's definition.
2. Alice posts an `address_definition_change` for `X`, transferring signing control of `X` to Bob's key (a normal, permitted operation).
3. An AA is deployed with logic such as:
   ```
   if: `{attestation[[attestors=ATTESTOR, address=trigger.address, field='kyc']] == 'passed'}`
   messages: [ { app: 'payment', payload: { outputs: [{address: "{trigger.address}", amount: "{trigger.output[[asset=base]]}"}] } } ]
   ```
4. Bob triggers the AA from address `X`. `attestation[[...]]` in `formula/evaluation.js` (lines 966-1004) still returns `'passed'` because it never checks whether `X`'s definition changed since the attestation, so the AA releases funds to Bob based on an attestation that was only ever valid for Alice.
