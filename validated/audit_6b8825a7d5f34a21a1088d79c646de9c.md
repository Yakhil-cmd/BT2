### Title
`OpenedHandler#provision?` skips the `review_stacks_enabled` gate for `allow_with_label`/`prevent_with_label` behaviors, letting an attacker provision a `ReviewStack` on a repository with review stacks disabled - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
The binding the operator expects is `repository.review_stacks_enabled == true` is required before any `ReviewStack` is created for that repository. Due to Ruby operator precedence in `provision?`, `review_stacks_enabled` is only ANDed with the `allow_all?` branch; the `allow_with_label?` and `prevent_with_label?` branches are combined with `||` and never test `review_stacks_enabled` at all, so an attacker can trigger provisioning on a repo that has explicitly disabled review stacks.

### Finding Description
The claimed binding: `repository.review_stacks_enabled == true` must hold before `Shipit::ReviewStack.create!` runs for that repository. Actual code: [1](#0-0) 

Because `&&` binds tighter than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`.

If a repository has `review_stacks_enabled == false` and `provisioning_behavior == 'allow_with_label'` (or `prevent_with_label`), the first clause is false regardless, but the second (or third) clause can still evaluate `true` purely from the PR's labels, with no reference to `review_stacks_enabled` anywhere.

Exploit flow: an attacker forks the target repo, opens a pull request (`action: "opened"`) and adds a label whose name matches `repository.provisioning_label_name` (a value visible in `app/views/shipit/repositories/settings.html.erb` / discoverable, and not secret). GitHub delivers the `pull_request.opened` webhook. `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?`, which returns `true` via the `allow_with_label?` branch [2](#0-1) . `ReviewStackAdapter#find_or_create!` then calls `create!`, which persists a `Shipit::ReviewStack` and enqueues it for provisioning with no additional `review_stacks_enabled` check [3](#0-2) .

Existing guards do not catch this: webhook signature verification only authenticates that GitHub sent the payload (any repo/PR the attacker controls satisfies this), `ExplicitParameters` validates payload shape not business logic, and `Repository` model validations do not constrain `provisioning_behavior` against `review_stacks_enabled` combinations [4](#0-3) . `NullRepository` correctly returns `false` for all provisioning predicates [5](#0-4) , but that's irrelevant here since the target repository exists and is registered.

### Impact Explanation
An unprivileged GitHub user who can open a PR and label it can force Shipit to create and provision a `ReviewStack` (which triggers deployment infrastructure via `ReviewStackProvisioningQueue` and provisioning handlers) against a repository whose operator explicitly opted out of review stacks (`review_stacks_enabled == false`). This is an unauthorized write/provisioning action for a repository that did not authorize it via its intended configuration, matching the Critical category "a payload for one repository mutating another's stack... or an unauthorized deploy." It is repeatable against any repository configured with `allow_with_label` or `prevent_with_label` and `review_stacks_enabled: false`.

### Likelihood Explanation
Preconditions: target repository must have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible/likely misconfiguration since these are two independent settings exposed in the same settings UI [6](#0-5) . Attacker cost is trivial: open a PR, add a label (or omit a label for `prevent_with_label`). No secrets or elevated roles are needed. Repeatable at will.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates every branch:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` style, not shown per scope but described here):
1. Build/stub a `repository` double with `review_stacks_enabled => false`, `provisioning_behavior_allow_with_label? => true`, `provisioning_behavior_prevent_with_label? => false`, `provisioning_behavior_allow_all? => false`, `provisioning_label_name => "deploy-preview"`.
2. Stub `params.pull_request["labels"]` to `[{"name" => "deploy-preview"}]`.
3. Assert `handler.send(:provision?) == true` while `repository.review_stacks_enabled == false` — demonstrating the two sides of the binding (`review_stacks_enabled == true` required vs. actual `false` yet `provision?` true) diverge.
4. Additionally, call `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` and assert a `Shipit::ReviewStack` record is persisted, confirming write-side impact with no `review_stacks_enabled` check in `create!`.
