### Title
`X-Shipit-User` header spoofs deploy/rollback/merge/lock attribution without being covered by the API token's signature - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The `Api::BaseController#current_user` resolves the acting user from the client-supplied `X-Shipit-User` header, a value that is never covered by the cryptographic signature that authenticates the request (the `ApiClient` bearer token). Any holder of a valid, deploy-scoped `ApiClient` token can therefore attribute deploys, rollbacks, merges, aborts and locks to an arbitrary existing `Shipit::User` — including users whose GitHub identity carries elevated trust in the mirrored repository/organization — without ever proving control of that identity.

### Finding Description
Authentication of an API request happens purely at the `ApiClient` level: `authenticate_api_client` verifies the bearer token with `ApiClient.authenticate`, which uses `Shipit::SimpleMessageVerifier` keyed by `Shipit.api_clients_secret` to recover an `ApiClient` id. [1](#0-0) [2](#0-1) 

That signature only binds the request to an `ApiClient` (and its `permissions`/`stack_id`), never to a `Shipit::User`. Separately, `current_user` is derived from the unauthenticated, attacker-controlled `X-Shipit-User` request header and looked up by login with no additional check that the caller is actually that user: [3](#0-2) 

This `current_user` value is then used as the acting principal for consequential, identity-attributed operations across the API surface: triggering deploys, triggering tasks, aborting tasks, locking/unlocking stacks, reporting release health, and — most significantly — requesting merges: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is: `identity verified by the request's cryptographic signature == identity the state-changing operation is attributed to`. Before a malicious request: an `ApiClient` token proves possession of *that* token only, and `merge_requested_by` / `deploy.user` / `aborted_by` should reflect a genuinely authenticated actor. After the attacker sets `X-Shipit-User: <victim-login>` on a request signed only by their own (possibly narrowly-scoped) token, the equality breaks — the signature still only proves "holder of client X's token", but the recorded/acted-upon identity becomes an arbitrary `User` row picked by the attacker via `User.where('lower(login) = ?', ...)`. [8](#0-7) 

This is directly analogous to the reported Morpho Blue bug class: a field that participates in a security-relevant action (`msg.sender`/checkpoint owner there, `current_user`/attribution here) is trusted and acted upon without being covered by the mechanism (`_update` override / signature verification) that is supposed to keep it consistent with the authenticated actor.

### Impact Explanation
`MergeRequest.request_merge!` persists `merge_requested_by: user`, and `merge_message` embeds `merge_requested_by.login` into the commit message that is sent to GitHub via `stack.github_api.merge_pull_request` during `merge!`: [9](#0-8) [10](#0-9) [11](#0-10) 

An attacker holding any API token scoped only to `deploy:stack` on a single stack can cause Shipit to record and act as though a specific other user (e.g., a senior engineer or release manager) requested/authorized the merge, deploy, rollback, or lock — an identity-spoofing/impersonation primitive that undermines audit trails and attribution across `deploy`, `rollback`, `abort`, `lock`, and `merge` actions. Because the merge/deploy/rollback themselves are already gated by `require_permission`, this is not a permission-scope bypass, but it is a forged attribution of an "unauthorized... merge" request in the sense that the merge is requested and recorded as coming from a user who never made the request and whose credentials were never checked.

### Likelihood Explanation
High for any party already in possession of a valid `ApiClient` token (e.g., a CI system or narrowly-scoped integration): setting one HTTP header is sufficient, no additional secret or credential is required, and the lookup by `login` accepts any existing `User` in the database.

### Recommendation
Do not derive `current_user` from a caller-supplied header. Either bind the acting user to the token itself (e.g., `ApiClient#creator`, as already used for `api_client_token` display) or require a signed/verified assertion of identity (e.g., a per-user signed token, similar to `ApiClient.authenticate`) before trusting `X-Shipit-User`, and audit all call sites (`DeploysController#create`, `TasksController#trigger/#abort`, `LocksController#create/#update`, `RollbacksController#create`, `ReleaseStatusesController#create`, `MergeRequestsController#update`) that attribute actions to `current_user`.

### Proof of Concept
1. Obtain (or be issued) a `Shipit::ApiClient` token scoped only to `deploy:stack`/`read:stack` for a specific stack (e.g., a routine CI deploy key), authenticated via HTTP Basic auth as in `authenticate!`/`BasicAuth.authenticate`. [12](#0-11) 
2. Send `POST /api/:stack_id/merge_requests/:number` (or `/deploys`, `/rollbacks`, `/locks`, `/tasks/:name/abort`) with header `X-Shipit-User: <victim-login>` set to the login of a privileged/trusted user known to exist in the Shipit `User` table.
3. `identify_user` resolves `current_user` to the victim's `User` record purely from the header value, with no further verification: [8](#0-7) 
4. The merge request (or deploy/rollback/abort/lock) is created/updated with `merge_requested_by`/`user`/`aborted_by` set to the victim, and for merges the victim's login is embedded in the GitHub merge commit message, all without the victim ever making the request. [9](#0-8)
