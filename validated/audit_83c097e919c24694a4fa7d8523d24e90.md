## Title
Silent Acceptance of `new_shared_address` Device Messages Without User Confirmation Allows an Unprivileged Paired Device to Register the Wallet as Cosigner of an Attacker-Chosen Multi-Signature Address - (File: wallet_defined_by_addresses.js)

### Summary
The external report describes a class of bug where an RPC/message handler mutates persistent wallet/snap state (upserting ERC-20 token metadata) without ever asking the user to confirm the change, letting any connected/untrusted party silently alter local state. `ocore` has the same bug class in its device-message handling for shared (multi-signature) addresses: the `new_shared_address` subject is processed by `handleNewSharedAddress()` / `addNewSharedAddress()` and persists a brand-new shared address and its signing paths into the local database with no user-confirmation event at all, unlike the sibling `create_new_shared_address` flow which explicitly documents that it "should trigger a confirmation dialog."

### Finding Description
Device-to-device messages arriving through the hub are dispatched in `handleMessageFromHub()` in [1](#0-0)  . For the `create_new_shared_address` subject, the code explicitly comments that the resulting event "should trigger a confirmatin dialog, user needs to approve creation of the shared address" [2](#0-1) .

However, the `new_shared_address` subject — which is the final step that actually persists a shared address in the DB and is normally sent only after all cosigners approved via the `create_new_shared_address`/`approve_new_shared_address` handshake — is routed straight into `walletDefinedByAddresses.handleNewSharedAddress()` with no confirmation event emitted: [1](#0-0) 

`handleNewSharedAddress()` only checks that the definition hashes to the claimed address, that signer addresses are syntactically valid, and that the definition is well-formed via `Definition.validateDefinition`; it then calls `addNewSharedAddress()` directly with `callbacks.ifOk` as the completion handler — no UI/user confirmation step is invoked anywhere in this path: [3](#0-2) 

`addNewSharedAddress()` unconditionally writes the new `shared_addresses` row and the associated `shared_address_signing_paths` rows to the database and emits only informational `new_address` events (used to refresh the UI address list, not to request confirmation): [4](#0-3) 

Because this handler is reachable from any already-paired correspondent device (the "device pairing"/"paired device" trust boundary explicitly allowed in scope) simply by sending a `new_shared_address` justsaying message, an attacker-controlled paired device can construct an arbitrary address definition that references the victim's device address at some signing path (satisfying the `signers` validation) and have the wallet silently register itself as a shared-address member — completely bypassing the `create_new_shared_address` → `approve_new_shared_address` consent handshake that the codebase's own comments indicate is required for this kind of state change.

### Impact Explanation
Once a shared address is silently registered, `findAddress()` in [5](#0-4)  will recognize it via `shared_address_signing_paths` and route signing requests for it through the normal signing-request flow. This means the wallet begins tracking/watching an address the user never agreed to be part of, and — depending on the definition supplied by the attacker (e.g. `or` branches, nested definitions, or paths that make the victim's key appear as a spender alongside attacker-controlled branches) — the local wallet can be maneuvered into producing signing requests, exposing balance information for the bogus shared address, or cosigning outputs the user never intended, undermining the address-definition trust model this validation and signing machinery is meant to enforce.

### Likelihood Explanation
Any device that has previously paired with the victim (a normal, unprivileged occurrence — pairing itself requires no special trust beyond exchanging a pairing code) can send this message at any time with no rate limiting or user-visible confirmation, making exploitation straightforward and repeatable, directly mirroring the ease of exploitation in the original `addErc20Token` report.

### Recommendation
Require explicit user confirmation before calling `addNewSharedAddress()` in the `new_shared_address` path, or, at minimum, verify that the address was previously offered/approved through the `create_new_shared_address`/`approve_new_shared_address` handshake (e.g. by checking a matching `pending_shared_addresses` record signed off by the local user) before persisting it, consistent with the confirmation dialog already documented for `create_new_shared_address`.

### Proof of Concept
1. Attacker device pairs with victim device (normal pairing flow).
2. Attacker crafts an address definition array, e.g. `["or", [["address","$address@ATTACKER_DEV"], ["address","$address@VICTIM_DEV"]]]`, replacing `$address@VICTIM_DEV` with the victim's actual device address so `extractAddressPathsFromDefinition`/`signers` validation in `handleNewSharedAddress` passes.
3. Attacker computes `address = objectHash.getChash160(definition)` and sends a device `justsaying` message with `subject: "new_shared_address"`, `body: {address, definition, signers}` via the hub.
4. Victim's `wallet.js` `doHandle()` routes it straight to `walletDefinedByAddresses.handleNewSharedAddress()` [1](#0-0) , which validates and calls `addNewSharedAddress()` [4](#0-3) , persisting the shared address into the victim's DB with zero user interaction — no confirmation dialog was ever shown, unlike the `create_new_shared_address` counterpart.

	db.query(
		"INSERT "+db.getIgnore()+" INTO shared_addresses (shared_address, definition) VALUES (?,?)",

			var arrQueries = [];
			for (var signing_path in assocSignersByPath){
				var signerInfo = assocSignersByPath[signing_path];
				db.addQuery(arrQueries, 
					"INSERT "+db.getIgnore()+" INTO shared_address_signing_paths \n\
					(shared_address, address, signing_path, member_signing_path, device_address) VALUES (?,?,?,?,?)",

				console.log('added new shared address '+address);

					onDone();

					forwardNewSharedAddressToCosignersOfMyMemberAddresses(address, arrDefinition, assocSignersByPath);

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
