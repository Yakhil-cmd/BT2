### Title
Remote unauthenticated crash of any ocore node via crafted `hub/deliver` device message with an unrecognized DH recipient key - ([File: device.js])

### Summary
Any node that exposes a WebSocket listener (which is the default for full nodes, and effectively any node that has `my_device_address` set) can be crashed remotely by a single crafted `hub/deliver` network request whose `encrypted_package.dh.recipient_ephemeral_pubkey` does not match any of the target's known keys, when the target device address equals the message's `to` field (`bToMe` case). This reaches `decryptPackage()` in `device.js`, which on an "unknown key" condition schedules an unconditional `throw Error(...)` inside a `setTimeout`, which is caught by the global `uncaughtException` handler in `network.js` and deliberately re-thrown to crash the process. This is directly analogous to CVE-2024-51428's "crafted data channel packet causes DoS" class: an externally supplied, unauthenticated message payload triggers an unconditional fatal error path.

### Finding Description
The `hub/deliver` request handler in [1](#0-0)  validates only structural fields, address format, nesting depth, and the message's self-signature. When the destination device address equals the receiving node's own device address (`bToMe`), the handler **skips** the `keys.includes(recipient_ephemeral_pubkey)` check that is otherwise performed for messages destined to *other* locally-registered devices [2](#0-1) , and immediately re-emits the message for local processing: [3](#0-2) 

This event is handled by `handleJustsaying` in `device.js`, which performs signature/hash checks on the *outer* envelope [4](#0-3)  and then calls `decryptPackage()` **before** ever checking whether the sender is a known correspondent [5](#0-4) .

Inside `decryptPackage()`, if `dh.recipient_ephemeral_pubkey` doesn't match the temp, previous-temp, or permanent device key, the function schedules a deferred unconditional throw: [6](#0-5) 

Because this `throw` happens inside a `setTimeout` callback, it becomes an uncaught exception. The global handler in `network.js` intentionally treats *any* uncaught exception as fatal and re-throws it to kill the process: [7](#0-6) 

No pairing, correspondent relationship, `bLoggedIn`, or `bServeAsHub` configuration is required to reach this path via the `bToMe` branch — an attacker only needs to know the target's public device address (routinely shared for pairing/wallet use) and send one `hub/deliver` request with a bogus `recipient_ephemeral_pubkey`.

### Impact Explanation
A single unauthenticated network message crashes the entire ocore process (full node, witness, hub-serving node, or wallet backend). Repeated messages allow a trivial, low-cost, unauthenticated remote DoS against any reachable node, disrupting DAG unit propagation/validation and light-client/hub services — matching "a network unable to confirm new units" impact category, and going beyond a simple resource-only bug into full process termination.

### Likelihood Explanation
High. The attack requires only: (1) knowledge of the target's device address (public, shared during pairing/wallet advertising), and (2) the ability to open a WebSocket connection to the target and send one crafted `hub/deliver` request — both trivial for any peer able to connect to the node's WS port. No authentication, pairing, or special privilege is needed because the vulnerable code path is reached before the correspondent check.

### Recommendation
- Remove the unconditional `throw` inside the `setTimeout` in `decryptPackage()`'s "unknown key" branch [6](#0-5) ; instead, log and return `null`/emit a `nonfatal_error` event (the commented-out `eventBus.emit('nonfatal_error', ...)` on the next line suggests this was already intended) rather than crashing the process.
- Re-apply the `recipient_ephemeral_pubkey` whitelist check for the `bToMe` case in `network.js`'s `hub/deliver` handler [3](#0-2)  so self-addressed messages get the same validation as messages to other local devices.
- Ensure the global `uncaughtException` handler in `network.js` [7](#0-6)  does not treat externally-triggerable, input-validation-style errors as fatal crashes.

### Proof of Concept
1. Obtain the target node's device address `TO_ADDR` (routinely public for pairing).
2. Connect via WebSocket to the target node.
3. Send a `request` frame with `command: 'hub/deliver'` and `params` = a self-consistent, validly-signed `objDeviceMessage`:
   - `to`: `TO_ADDR`
   - `pubkey`/`signature`: attacker's own keypair, self-signed per `objectHash.getDeviceMessageHashToSign` (passes the outer signature check).
   - `encrypted_package`: valid shape (`iv`, `authtag`, `encrypted_message`, `dh.sender_ephemeral_pubkey`, `dh.recipient_ephemeral_pubkey`) but with `dh.recipient_ephemeral_pubkey` set to an arbitrary base64 public key not equal to any of the target's temp/prev-temp/permanent device keys.
4. Because `to === TO_ADDR === my_device_address`, `bToMe` is true, the recipient-key whitelist check is skipped, and the message is handed directly to `decryptPackage()`, which schedules the fatal `throw`, crashing the target process within ~100ms.
