### Title
Cross-repo Status webhook write updates commits in unrelated stacks via unscoped `Commit.where(sha:)` lookup, enabling unauthorized deploy unblocking - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub Status webhook using only `Commit.where(sha: params.sha)`, with no scoping by the repository named (and signature-verified) in the webhook payload. Because `sha` is not guaranteed unique across stacks/repositories in this schema, a webhook verified for repository A can mutate the status — and therefore `blocking?`/`deployable?` state — of a commit belonging to an unrelated repository B, which is exactly the chain consumed by `Commit#blocked?` and `Commit#deployable?`.

### Finding Description
The binding the system needs to hold is: `verified_webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` mutated by that webhook. This binding is broken.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) verifies the HMAC signature against the organization named in `params.dig('repository','owner','login')` via `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), then dispatches to `Shipit::Webhooks.for_event(event)` handlers with the raw parsed JSON — this only proves the payload was signed for *that* org/repo, not that the SHA inside it belongs to that repo's stacks.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query has no `stack_id`/repository filter at all — it matches *every* `Commit` row across *every* stack (i.e., every tenant/repository) sharing that SHA.
3. `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169`, `360-386`) writes a new `Status` row and, on state transition, calls `stack.schedule_merges` for the affected stack — a real state mutation with deploy-triggering side effects.
4. `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) evaluates `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`, and `blocking?` is delegated to `status` (line 219), which is now derived from the just-injected status row. If the attacker's webhook flips the earlier blocking commit to `success`, `blocking?` becomes false, and a later victim commit's `blocked?` → `deployable?` flips to `true`, enabling `stack.schedule_merges`/continuous delivery to proceed.

Why existing guards don't stop this: `verify_signature` authenticates *which organization/repo sent the webhook*, but never constrains *which `Commit` rows* the payload is allowed to touch — that authorization gap lives entirely in the unscoped `Commit.where(sha: ...)` query. `drop_unhandled_event`, `check_if_ping`, and the `ExplicitParameters` schema in `StatusHandler` only validate payload shape (`sha`, `state`, etc.), not repository ownership of the matched commit. There is no unique-by-stack constraint enforced at the lookup site.

The attacker's request: a genuine GitHub Status webhook (correctly signed by GitHub for a repository/org the attacker owns and that is registered as some Shipit stack) whose `sha` field is crafted/chosen to equal the SHA of a commit in the victim's unrelated stack.

### Impact Explanation
A successful collision lets an unprivileged actor write a `Status` record for a `Commit` belonging to a repository/stack they never authenticated for, directly altering `blocking?`/`blocked?`/`deployable?` outcomes and triggering `stack.schedule_merges` for that victim stack — this is the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" category (Critical). Repeatable against any stack/commit whose SHA the attacker can reproduce, blast radius spans all tenants sharing the Shipit instance since the vulnerable query has zero repository scoping.

### Likelihood Explanation
The attacker must (a) control a repository already onboarded as some Shipit stack so that GitHub will emit a webhook that passes `verify_signature`, and (b) produce a commit whose SHA-1 exactly equals the victim's target commit SHA. (b) is the binding constraint: since SHA-1 is a hash over commit content/metadata (tree, parents, author/committer, timestamps, message), forcing an exact collision against an arbitrary pre-existing victim SHA generally requires a SHA-1 (chosen-prefix) collision construction — expensive but not theoretical (publicly demonstrated, e.g. SHAttered/shambles-style attacks), and cost has decreased over time. No Shipit secrets, sessions, or `api_clients_secret`/`webhook_secret`/GitHub App keys are needed — the weakness is purely in the unscoped repository binding of `StatusHandler#process`, independent of the collision-construction cost.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogously in `CheckRunHandler`/other SHA-keyed handlers) by the repository identified in the verified webhook payload, e.g. join through `stack.repository` (owner/name) and filter `Commit.joins(:stack).merge(Stack.where(repository: repo)).where(sha: params.sha)`, so a webhook can only mutate commits belonging to the exact repository whose signature was verified.

### Proof of Concept
Minitest under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extending `test/models/commits_test.rb`):
1. Create `stack_a` (repo `attacker/repo`) and `stack_b` (victim, repo `victim/repo`), each independent tenants.
2. In `stack_b`, create `blocking_commit` (earlier, currently failing/pending blocking status) and `gated_commit` (later, undeployed) such that `gated_commit.blocked?` is `true` and `gated_commit.deployable?` is `false`.
3. In `stack_a`, create `attacker_commit` with `sha` deliberately set equal to `blocking_commit.sha` (simulating the SHA-1 collision precondition without needing live GitHub).
4. Assert binding before: `attacker_commit.stack.repository.full_name != blocking_commit.stack.repository.full_name` (foreign tenants).
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new.process` (or call `Commit.where(sha: attacker_commit.sha)` directly) with a `state: 'success'` status payload keyed to `attacker_commit.sha`.
6. Assert that `blocking_commit.reload.blocking?` is now `false` even though the webhook never verified against `stack_b`'s repository, and that `gated_commit.reload.deployable?` flips to `true` — demonstrating the cross-repo mutation and unauthorized unblocking.
