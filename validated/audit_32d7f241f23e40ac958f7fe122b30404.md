### Title
Cross-organization review-stack provisioning via mismatched `repository.owner.login` vs `repository.full_name` in webhook payload - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC-verifying `GitHubApp` using `params.dig('repository','owner','login')` (falling back to `organization.login`), while `OpenedHandler#repository` (and every other `PullRequest` handler) resolves the target `Shipit::Repository` using an entirely different field, `params.repository.full_name`. Because these two fields are never checked against each other, a caller who can produce a valid signature for one configured GitHub organization can name a repository belonging to a *different* configured organization in `full_name` and have `OpenedHandler` act on it.

### Finding Description
The broken binding: `params.dig('repository','owner','login')` (used to pick the verifying `GitHubApp`/`webhook_secret` in `WebhooksController#verify_signature`, [1](#0-0) ) must equal the owner portion of `params.repository.full_name` (used by `OpenedHandler#repository` to look up the `Shipit::Repository` via `Shipit::Repository.from_github_repo_name`, [2](#0-1) ). Nothing in the request path enforces this equality.

`Shipit.github(organization: repository_owner)` picks a per-organization `GitHubApp` instance/`webhook_secret` out of `secrets.github`, supporting the documented "Multiple Github Applications" setup [3](#0-2) . `GitHubApp#verify_webhook_signature` only checks the raw body against that one org's `webhook_secret` [4](#0-3) ; it has no notion of which repository the payload claims to describe. `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a `find_by(owner:, name:)` lookup with no cross-check against the `repository.owner.login` used for signature selection [5](#0-4) .

Exploit flow, assuming a Shipit instance configured for multiple GitHub organizations (org A, controlled/administered by the attacker, and org B, the victim, both with the Shipit GitHub App installed and tracked repositories):
1. Attacker knows org A's `webhook_secret` (they administer the GitHub App installed on their own org A, a precondition explicitly given in the question).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: pull_request`, body JSON where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/victim-repo"`, `action = "opened"`, and a valid HMAC-SHA1 signature computed with org A's `webhook_secret`.
3. `verify_signature` calls `Shipit.github(organization: "orgA")`, verifies the signature against org A's secret — it passes, because the attacker legitimately knows that secret.
4. `OpenedHandler#process` runs; `respond_to_pull_request_opened?` calls `provision?`, which reads `repository` resolved from `full_name = "orgB/victim-repo"` — a repository the attacker does not own and never proved control over via signature.
5. If `orgB/victim-repo` has review stacks enabled with `allow_all` (or another matching policy), `ReviewStackAdapter#find_or_create!` creates a `ReviewStack` and enqueues provisioning for it [6](#0-5) .

Existing guards fail to prevent this because: `verify_signature` only authenticates "some request signed by org A's secret," not "a request that legitimately concerns any specific repository named in the body"; there is no re-validation of `repository.owner.login == full_name.split('/').first` anywhere in `WebhooksController` or `OpenedHandler`; the `ExplicitParameters` schema in `OpenedHandler` only requires `repository.full_name` to be a `String`, imposing no consistency constraint.

### Impact Explanation
A verified webhook payload for organization A can cause Shipit to create/provision a `ReviewStack` (running a `ProvisioningHandler#up`, e.g. deploying to Kubernetes/Heroku per `docs/review_stacks.md`) for a repository belonging to organization B, entirely without organization B's webhook secret ever being used or compromised. This is a payload for one repository mutating another repository's stack state — matching the Critical impact category ("a payload for one repository mutating another's stack"). It is repeatable against any tracked repository whose owner differs from the attacker's own organization, as long as that repository has review-stacks provisioning enabled, and the same technique applies identically to `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, and other handlers that resolve `repository` from `params.repository.full_name` (`grep` shows `from_github_repo_name` used across all the `PullRequest` handlers).

### Likelihood Explanation
This requires a Shipit deployment configured with multiple GitHub organizations (the "Using Multiple Github Applications" mode documented in `docs/setup.md`), and the attacker must administer/know the `webhook_secret` for at least one of those configured organizations (a precondition explicitly stated as available to the attacker in the question). Given that precondition, the attack cost is a single crafted HTTP POST with a valid HMAC computed over attacker-controlled JSON — no GitHub-side action or live delivery from GitHub is needed, since Shipit's `/webhooks` endpoint accepts any POST with a valid signature regardless of true origin. It is fully repeatable and requires no privileged Shipit session, API token, or victim credentials.

### Recommendation
In `WebhooksController#verify_signature` (or in a shared handler concern), after signature verification succeeds, additionally verify that the organization used to select the signing `GitHubApp` (`repository_owner`) matches the owner segment of `params.dig('repository','full_name')` (and, ideally, of `params.dig('organization','login')` when present) before dispatching to handlers. Reject the webhook (422) on mismatch. This closes the gap without needing per-handler changes to `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, configured with two orgs `shopify` and `other-org` in `secrets.github`):
```ruby
test "rejects pull_request payload whose full_name owner differs from signing organization" do
  request.headers['X-Github-Event'] = 'pull_request'

  payload = {
    action: 'opened',
    number: 99,
    pull_request: { id: 1, number: 99, url: 'x', title: 'x', state: 'open',
                     additions: 1, deletions: 1,
                     head: { sha: 'a' * 40, ref: 'feature' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { owner: { login: 'other-org' }, full_name: 'shopify/shipit-engine' }, # mismatch: signed as other-org, claims shopify repo
    sender: { login: 'attacker' }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', OTHER_ORG_WEBHOOK_SECRET, payload)}"
  request.headers['X-Hub-Signature'] = signature

  assert_no_difference -> { Shipit::ReviewStack.count } do
    post :create, body: payload, as: :json
  end
  assert_response :unprocessable_entity # currently fails: returns :ok and creates a ReviewStack for shopify/shipit-engine
end
```
Assert on both sides of the binding: before the fix, `repository_owner` (`"other-org"`) ≠ owner segment of `full_name` (`"shopify"`), yet the request is accepted and a `ReviewStack` is created for `shopify/shipit-engine`; after the fix, the mismatch causes a `422` and no `ReviewStack` is created.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
