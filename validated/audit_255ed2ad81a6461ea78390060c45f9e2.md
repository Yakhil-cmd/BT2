### Title
Membership webhook handler binds Team by GitHub numeric ID while signature verification is scoped to a different (attacker-chosen) organization, allowing self-escalation into `Shipit.github_teams` authorization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which webhook secret) is used to validate the incoming request based on a field read directly out of the unauthenticated JSON body, while the `membership` event handler mutates team membership using a *different* field from the same body (a raw numeric GitHub team ID) without cross-checking that the team actually belongs to the organization whose signature was verified. This decouples "the organization that authenticated the request" from "the team record that is written," letting an attacker forge a `membership` webhook against any organization whose app config lacks a `webhook_secret` and add themselves to an existing, unrelated, and possibly privileged Shipit `Team`.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

For a `membership` event, there is no `repository` key in the payload, so `repository_owner` falls back to `organization.login` — a value the attacker fully controls and can point at *any* organization configured in `secrets.github`.

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [3](#0-2) 

This is a normal, documented configuration state — every example secrets file in the repo shows `webhook_secret: # nil` by default, and the multi-org config format explicitly supports per-organization secrets: [4](#0-3) 

So if *any* configured organization (e.g., a secondary/staging org, or one whose secret was never set) has no `webhook_secret`, requests claiming `organization.login` = that org will pass signature verification trivially, regardless of what the payload actually does.

Once past the signature gate, `MembershipHandler#process` looks up the `Team` purely by the attacker-supplied numeric `team.id`, and only sets `organization` inside a `create` block that is skipped if the team already exists: [5](#0-4) 

Team GitHub IDs are not secrets — they are visible via the public GitHub API (`GET /orgs/{org}/teams`). An attacker who knows the numeric `github_id` of a `Team` that Shipit already trusts for authorization (created earlier via `Shipit.github_teams` / `bin/rake teams:fetch`, see `Team.find_or_create_by_handle`) can: [6](#0-5) 

1. Forge a `membership` webhook with `organization.login` set to some org lacking a `webhook_secret` (bypassing signature verification for that "authenticated" org).
2. Set `team.id` to the numeric GitHub ID of an unrelated, privileged team actually used by `Shipit.github_teams`.
3. Set `member.login` to their own GitHub login.

`MembershipHandler` finds the existing (privileged) `Team` by `github_id` (step 2 succeeds regardless of the org lie in step 1), creates/finds the attacker as a `User`, and adds them as a member: [7](#0-6) 

Shipit's authorization gate then trusts DB team membership directly: [8](#0-7) [9](#0-8) 

The attacker then logs in with their own legitimate GitHub OAuth identity (no stolen credentials needed) and is now `authorized?` in Shipit, gaining access to stacks, deploys, and API client management gated solely by `Shipit.github_teams` membership.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization — explicitly a High-impact category. It grants an anonymous, unprivileged external attacker (someone with only a GitHub account and no Shipit access) the ability to self-provision membership in a Shipit-trusted team and thereby gain deploy/API-client privileges within the application, purely by exploiting the organization/team-identity trust-binding break in webhook processing.

### Likelihood Explanation
Requires: (1) the deployment uses (or has ever used) more than one configured GitHub org, or any org, with an unset `webhook_secret` — a state the project's own example configs default to; (2) knowledge of the numeric GitHub team ID of an authorized team, obtainable via the public GitHub API for any team the attacker can view, or guessable via brute-force since IDs are small sequential integers. No token, no repository write access, and no privileged Shipit account are required, matching the unprivileged-attacker threat model.

### Recommendation
- In `MembershipHandler#process`, verify that the resolved `Team#organization` matches the `organization.login` from the verified webhook payload before mutating membership, rejecting mismatches.
- In `WebhooksController#verify_signature`, treat any org configured without a `webhook_secret` as unverifiable for authorization-affecting events (or require `webhook_secret` to be mandatory for any Shipit deployment that uses `github_teams`-based authorization).
- Add a natspec/documentation note (or a runtime warning) when `github_teams` authorization is enabled while any configured GitHub app lacks a `webhook_secret`.

### Proof of Concept
1. Deploy Shipit with two orgs configured per `docs/setup.md` "Using Multiple Github Applications": `victim-org` (has `webhook_secret` set, and its team `Shipit/deployers` with GitHub ID `1234` is in `Shipit.github_teams`) and `decoy-org` (`webhook_secret` left blank, as in the example configs).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1234, "name": "Deployers", "slug": "deployers", "url": "https://example.com" },
  "organization": { "login": "decoy-org" },
  "member": { "login": "attacker-handle" }
}
```
No `X-Hub-Signature` needed since `decoy-org` has no secret — `verify_webhook_signature` returns `true` per [10](#0-9) .
3. `MembershipHandler` finds `Team` with `github_id: 1234` (the real `victim-org` team) and adds `attacker-handle` as a member.
4. Attacker logs in to Shipit via GitHub OAuth as `attacker-handle`; `User#authorized?` now returns `true` because they belong to a team in `Shipit.github_teams`, granting them access to stacks/deploys.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
