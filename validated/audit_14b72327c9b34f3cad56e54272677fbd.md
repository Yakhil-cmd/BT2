### Title
Cross-organization webhook signature bypass allows CI-status forgery and unauthorized deploy triggering in multi-app deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against using `repository_owner`, which is read straight from the untrusted, unsigned-at-selection-time JSON body (`repository.owner.login`, falling back to `organization.login`). Every webhook handler that actually processes the payload (e.g. `PushHandler`, `StatusHandler`) instead resolves the target `Repository`/`Stack` via `repository.full_name`. In a "Using Multiple GitHub Applications" deployment (a documented, supported configuration), these two fields are never checked for consistency, so the "organization whose secret authenticated the request" and "the repository that is actually written to" are two different, independently-supplied fields inside the same payload. [1](#0-0) 

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization app config, and in a multi-app deployment each organization has its own independent `webhook_secret`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` critically returns `true` unconditionally whenever `webhook_secret` is blank for the selected organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

After signature "verification" passes, the raw, attacker-controlled JSON is dispatched to handlers, and it is `payload.dig('repository', 'full_name')`—not `repository_owner`—that determines which tracked `Repository`/`Stack` is acted upon: [5](#0-4) [6](#0-5) [7](#0-6) 

The equality that the design implicitly assumes but never enforces is:
`organization used to select the verifying secret (repository.owner.login / organization.login)` == `organization implied by repository.full_name used to resolve the Stack that gets mutated`.

An unprivileged attacker who is aware of (or can trivially discover, e.g. because it's the documented default of `webhook_secret: # nil`) any one organization configured in this Shipit instance whose `webhook_secret` is unset can send a POST to `/webhooks` with:
- `repository.owner.login` / `organization.login` = the org with no secret (bypasses verification entirely, any/no `X-Hub-Signature` accepted), and
- `repository.full_name` = `<victim-org>/<victim-repo>` (a different, secret-protected org/repo actually tracked by this Shipit instance).

The request passes `verify_signature` unconditionally, and the handler then acts on the victim repository/stack using the attacker's own field values (e.g. `after` SHA for push, or `state`/`sha` for a commit status).

### Impact Explanation
The most damaging reachable handler is `StatusHandler`, which creates a `CommitStatus` for an arbitrary existing commit sha in the victim's tracked stack based purely on attacker-supplied `state`: [8](#0-7) 

`Commit#deployable?` and the deploy safety gating rely on `success?`/CI status derived from these stored statuses: [9](#0-8) 

Forging a `success` status for a commit that never actually passed CI on GitHub can flip `deployable?` to true and can also trigger `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` is enabled: [10](#0-9) 

This is capable of causing an unauthorized/CI-bypassing deploy to be triggered on a repository the attacker does not control and for which they never had a valid webhook secret — matching the "unauthorized deploy" Critical impact criterion. `PushHandler` similarly allows forcing a `GithubSyncJob` for an arbitrary tracked branch/stack using an attacker-chosen `expected_head_sha`, expanding the attack surface (sync uses the victim's real GitHub credentials to fetch, so it does not itself inject fake commits, but it does let an attacker trigger stack sync/processing across organizational boundaries at will).

### Likelihood Explanation
This requires: (1) the deployment to use the documented multi-organization GitHub App configuration (`config/secrets.yml` with per-org keys), and (2) at least one configured organization lacking a `webhook_secret` — which is explicitly shown as the default/example value (`webhook_secret: # nil`) in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`. No credentials, session, or API token are required — only knowledge that such an org exists in this Shipit instance's config, which can be inferred from public GitHub App installation info. This is squarely an unprivileged-attacker, no-auth vector once the precondition (multi-org + one no-secret org) holds.

### Recommendation
In `WebhooksController#verify_signature`, do not use `repository.owner.login`/`organization.login` merely to select which secret to check against, then trust an entirely separate field (`repository.full_name`) for authorization of the write. Either:
- Require that `repository.full_name`'s owner exactly match `repository_owner` (case-insensitively) before dispatching to handlers, rejecting mismatches with 422; and/or
- Stop treating an unset `webhook_secret` as "always verified" (`return true unless webhook_secret`) for any organization used as an authentication anchor — instead reject/log webhooks for orgs with no configured secret, or require secrets to be mandatory in multi-org configurations; and
- Re-derive the authorizing organization from the same field (`repository.full_name`'s owner) that handlers use to resolve the Stack, so the org that authenticates the signature is provably the org whose data is mutated.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `no_secret_org` (no `webhook_secret` set — the documented default) and `victim_org` (properly configured, has a tracked `Stack` for `victim_org/victim_repo` with `continuous_deployment` enabled and CI checks required).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or garbage value):
```json
{
  "repository": { "owner": { "login": "no_secret_org" }, "full_name": "victim_org/victim_repo" },
  "sha": "<real, currently-pending commit sha in victim_org/victim_repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "no_secret_org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (invalid) signature header.
4. `Shipit::Webhooks.for_event('status')` handler (`StatusHandler`) runs and calls `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, writing a forged "success" status onto the victim's real commit — ` [8](#0-7) `.
5. If that flips the commit to `deployable?` and CD is enabled, `ContinuousDeliveryJob` is scheduled, resulting in an unauthorized deploy of `victim_org/victim_repo` — ` [11](#0-10) `.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
