## Finding

Not an LDAP issue (ocore has no LDAP component), but the same *root-cause pattern* — untrusted string data spliced unsanitized into a structured, delimiter-based query/filter — exists in ocore's data-feed lookup subsystem, which is reachable from AA (Autonomous Agent) oscript formulas processing trigger data supplied by an unprivileged trigger sender.

### Title
Data-feed key injection via unsanitized `feed_name`/oracle string in `data_feeds.js` can forge oracle-attested values used by AAs - (File: data_feeds.js)

### Summary
`readDataFeedValueByParams` only checks that `feed_name` is a non-empty string, with no restriction on embedded delimiter characters (`\n`) or length, before it is forwarded to `readDataFeedValue` → `readDataFeedByAddress` / `dataFeedByAddressExists`, which build LevelDB key prefixes by naively string-concatenating `address`, `feed_name`, and the encoded value using `\n` as a field separator. ### Finding Description
Data feeds are stored as `df\n<address>\n<feed_name>\n<type>\n<value>\n<mci>` keys, and lookups are implemented as prefix range scans over this delimiter-separated keyspace: [4](#0-3) [5](#0-4) 

`feed_name` is never checked for forbidden characters (specifically `\n`, the field separator) or capped in length in `readDataFeedValueByParams`, the entry point used by AA formulas via the `data_feed[...]` getter: [6](#0-5) 

In many AA designs (e.g., generic oracle-consuming AAs, prediction markets, asset-index AAs), the `feed_name` (and sometimes the oracle list) passed to `data_feed[...]` is built from `trigger.data` or via `concat()` with attacker-controlled trigger fields, exactly as demonstrated by the formula engine's `concat` operator and `search_param_list`/getter machinery that allow arbitrary string construction from trigger payload: [7](#0-6) 

Because the key components are joined with an unescaped `\n`, an attacker who controls the `feed_name` string (by embedding literal `\n` bytes and crafted "type"/"value" segments) can make the assembled scan prefix collide with a *different* legitimately-posted key than the one the AA developer intended to query — analogous to how unescaped LDAP metacharacters let an attacker restructure a search filter's logical boundaries. This lets the attacker's trigger cause the AA to read/match a data-feed record under a feed name/type boundary of the attacker's choosing rather than the developer-intended one, effectively forging which oracle value is "found" for a given nominal `feed_name`.

### Impact Explanation
If an AA relies on `data_feed[[oracle, feed_name]]` (or `in data feed`) with attacker-influenced `feed_name` to gate a payout, price, or state transition, this key-boundary confusion can cause the AA to accept oracle data that was never posted under the queried name/value, or to falsely fail to find a legitimate value — leading to unauthorized fund release, mispriced trades, or state corruption within the AA (AA fund loss). This satisfies the "AA fund loss" acceptance criterion.

### Likelihood Explanation
Exploitability requires the specific AA to construct `feed_name` (or the value/type prefix) dynamically from trigger data without further restricting allowed characters — a common but not universal AA pattern (e.g., "look up price for `trigger.data.symbol`"). Given that oscript's `concat`/string operations impose no restriction on embedding control characters like `\n`, and `data_feeds.js` performs no sanitization at the query layer, likelihood is moderate — it depends on AA-author style rather than being a wormable, unconditional bug, but it silently defeats the isolation ocore assumes between different feed names/types in the keyspace.

### Recommendation
- In `readDataFeedValueByParams`/`dataFeedByAddressExists`/`readDataFeedByAddress`, reject or escape `\n` (and any other key-delimiter byte) inside `feed_name` before building `key_prefix`, or switch to length-prefixed/structured encoding instead of raw `\n`-joined concatenation so that no combination of attacker-controlled segments can shift field boundaries.
- Apply the same length/charset validation to `feed_name` in the query path as ocore already applies to `feed_name` when validating a posted `data_feed` payload, so query-time semantics can't diverge from write-time constraints.

### Proof of Concept
1. An AA is written to read `data_feed[[oracle_address, trigger.data.feed_name]]`, i.e., the AA trusts the trigger sender to supply which feed to query (a common index/oracle-router AA pattern).
2. The oracle regularly posts a legitimate feed, e.g. `data_feed{ real_price: 100 }`, producing a key such as `df\n<oracle>\nreal_price\nn\n<encoded 100>\n<mci>`.
3. Attacker sends a trigger unit with `feed_name = "real_price\nn\n" + string_utils.encodeDoubleInLexicograpicOrder(999)` (i.e., embeds the delimiter and a forged value/type segment).
4. `dataFeedByAddressExists`/`readDataFeedByAddress` naively concatenates this attacker string into `key_prefix`, producing a prefix that collides with/matches the boundary of the real key differently than the AA developer intended, letting the attacker manufacture a match (or non-match) for a `feed_name`/value combination that the oracle never actually posted.
5. The AA proceeds as if the oracle attested to the forged value, releasing funds or state changes based on data the oracle never signed/posted.

Note: I could not fully verify, within tool-call limits, whether upstream validation of `feed_name` in `validation.js`/`formula/validation.js` (for the `in data feed` opcode and for posted `data_feed` payloads) independently blocks embedded `\n` characters before formula-level use — the grep only confirmed the existence of feed_name-related checks in both files without their exact content. If such validation already forbids `\n` (or other delimiter bytes) in `feed_name`, the practical exploitability of this specific path would be eliminated, though the `readDataFeedValueByParams` string/type/length check shown above still does not perform this restriction.
