### Title
Missing newline validation in AA state variable names allows key-namespace injection in kvstore storage - (File: formula/evaluation.js)

### Summary
The `hyper-staticfile` bug allowed a "path" string to escape its intended directory scope because the validation logic used an incomplete definition of what counts as a path-escaping character (missing the Windows drive-letter case). In ocore, AA state variable names are persisted as `"st\n" + address + "\n" + var_name` in the LevelDB/RocksDB kvstore, where `\n` is the reserved namespace separator between `address` and `var_name`, and is also used internally in `var_name` when representing nested/dictionary keys (e.g. `assocFields` composite keys, seen throughout `storage.js`/`aa_composer.js`). The state-var-name validation in `state_var_assignment` and `var` formula operators checks only `MAX_STATE_VAR_NAME_LENGTH` and `isWellFormed()`, but never rejects `\n`, unlike the equivalent and structurally identical `data_feed` name/value validation which does explicitly reject `\n` for exactly this reason.

### Finding Description
`formula/evaluation.js`'s `state_var_assignment` case validates a user/AA-controlled `var_name` before writing to the AA's persistent state:
```
if (var_name.length > constants.MAX_STATE_VAR_NAME_LENGTH)
    return setFatalError("state var name too long: " + var_name, ...);
if (!var_name.isWellFormed())
    return setFatalError("state var name not well formed: " + var_name, ...);
```
`isWellFormed()` only rejects lone UTF-16 surrogate code units; it does not reject `\n` (`\x0A`). The resulting `var_name` is then used unmodified as part of a kvstore key: `"st\n" + address + "\n" + var_name` (`storage.js:readAAStateVar`, `readAAStateVars`). Because `\n` is the field separator of this key scheme, an AA whose oscript is attacker/trigger-controlled (since `var_name` can be a formula-computed expression, not just a literal) can craft a `var_name` containing embedded `\n` characters to produce keys that visually/structurally "escape" the intended `address\nvar_name` boundary — analogous to how `c:/windows/...` escaped the intended base directory in the hyper-staticfile bug because the separator-detection logic was incomplete.

This is reachable by any unprivileged AA author: any deployed AA can execute a `state_var_assignment` (`var['a\nb'] = 1;`) or dynamic `var[computed_name] = 1;`), and the trigger sender only needs to invoke the AA to reach the vulnerable code path.

### Impact Explanation
This could allow an AA to corrupt or forge entries within the shared `st\n` keyspace of the kvstore, potentially:
- Writing state that appears (when scanned by prefix, e.g. `light/get_aa_state_vars`'s `var_prefix_from`/`var_prefix_to` range scan in `network.js:3965-3995`, or `readAAStateVars`'s `gte`/`lte` prefix range) to belong to a different, unintended var-name prefix than the AA actually owns, misleading light clients or other AAs/bots that rely on `var_prefix` filtering to determine another AA's state.
- Since `address` is always exactly 32/34 bytes with no `\n` inside it (Base32 addresses can't contain `\n`), the immediate cross-address confusion is bounded; the primary risk is namespace confusion within one address's own state var space (nested-key ambiguity) and confusing off-chain/light-wallet consumers that parse `readAAStateVars` results by string-splitting on `\n`, e.g. `tools/find_longest_state_var.js` splits on the first `\n` to separate address from var_name, and any similar downstream splitting logic in bots/wallets could mis-attribute state to the wrong var.

### Likelihood Explanation
High likelihood of reachability (any AA author can trigger `state_var_assignment` with a computed name), but the concrete "spending" or "fund loss" impact is not proven — the practical damage is limited to key/namespace confusion for downstream consumers that parse `\n`-delimited state var keys, not a direct fund-loss or double-spend primitive.

### Recommendation
Add an explicit rejection of `\n` in the state-var-name validation in `formula/evaluation.js` (both `state_var_assignment` and the `var`/`balance` read case), mirroring the check already present for `data_feed` names in `validation.js`:
```
if (var_name.indexOf('\n') >= 0)
    return setFatalError("state var name contains \\n", { arr }, false, cb);
```
Apply the same check wherever state-var names are validated statically in `formula/validation.js`.

### Proof of Concept
1. Deploy an AA with a `state` message containing:
```
{
  var['a\nb'] = 1;
}
```
2. Trigger the AA. `var_name = "a\nb"` passes `isWellFormed()` and the length check.
3. The state var is persisted at kvstore key `"st\n" + address + "\na\nb"`.
4. Query `light/get_aa_state_vars` with `var_prefix = "a"` — the scan range `gte="st\n"+address+"\na"`, `lte="st\n"+address+"\na\uFFFF"` will include this entry, and clients splitting the returned key/`var_name` on `\n` will parse it as var name `"a"` with sub-path `"b"`, diverging from the AA's actual intended flat var name `"a\nb"` — demonstrating the namespace-boundary confusion.
