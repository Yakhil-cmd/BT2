### Title
Cross-organization webhook forgery via decoupled signature-org selection and repository-resolution fields - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Once verification passes, `Webhooks::Handlers::Handler#repository_name` resolves the actual `Repository`/`Stack` to act on using a **different** payload field: `payload.dig('repository', 'full_name')`. Because these two fields are never cross-checked, in a multi-organization Shipit deployment an attacker who can produce a validly-signed payload for one configured organization (e.g., an org with `webhook_secret` unset, which causes `verify_webhook_signature` to `return true unless webhook_secret`) can set `repository.full_name` to point at a repository belonging to a **different** organization/stack and trigger handler actions (e.g., `PushHandler` calling `stack.sync_github`) against that unrelated stack.

### Finding Description
- Signature/org selection: `app/controllers/shipit/webhooks_controller.rb:24-30,59-62` picks the `GitHubApp` via `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `repository.owner.login` (or `organization.login`). [1](#0-0) [2](#0-1) 
- Signature check itself: `lib/shipit/github_app.rb#verify_webhook_signature` explicitly bypasses verification (`return true unless webhook_secret`) when the resolved organization has no secret configured — a configuration state the docs present as normal/optional per-org. [3](#0-2) 
- Action/stack resolution: `app/models/shipit/webhooks/handlers/handler.rb#repository_name` and `#stacks` resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`, independent of `repository_owner` used above. [4](#0-3) 
- Concrete handler exploiting this mismatch: `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on every not-archived stack matching the branch of whatever repository was resolved from `full_name`. [5](#0-4) 

This breaks the equality that should hold: `organization authenticated by signature == organization whose repository/stack is written by the handler`. The signature check authenticates "this payload came from whoever holds Org A's secret," but the code then acts on Org B's repository because `full_name` (not `repository.owner.login`) drives the actual database lookup.

### Impact Explanation
In a Shipit instance configured for multiple GitHub organizations (a documented, supported setup — see `docs/setup.md` "Using Multiple Github Applications"), if any one configured organization has no `webhook_secret` set (also a documented/allowed configuration, `config/secrets.development.example.yml`, `config/secrets.development.shopify.yml` show `webhook_secret: # nil` as a normal placeholder), signature verification for that org is unconditionally skipped. An attacker who can reach the webhook endpoint (no credentials needed for that org) can send a payload with `repository.owner.login` set to the secret-less org (or omit signature checks entirely) while setting `repository.full_name` to `victim-org/some-repo`. This causes cross-organization actions such as forced `GithubSyncJob` execution (`PushHandler`), commit-status writes (`StatusHandler`), or check-run refresh scheduling (`CheckSuiteHandler`) against a stack that belongs to an organization the attacker never authenticated against — a cross-repository/cross-organization write that the current design does not prevent.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment, and (2) at least one configured organization with `webhook_secret` unset (or otherwise weak/known). Both preconditions are explicitly supported/documented configurations rather than edge cases, and the webhook endpoint itself requires no authentication to reach — only a correctly-shaped GitHub event payload and header (`X-Github-Event`). No GitHub App private key, `api_clients_secret`, or session is needed.

### Recommendation
Cross-validate the organization used for signature verification against the organization embedded in the payload actually used for stack/repository resolution. Concretely, derive the repository/stack lookup from the same verified `repository_owner` (or verify that `repository.full_name`'s owner segment matches `repository_owner`) before dispatching to any `Webhooks::Handlers::Handler`. Additionally, consider requiring `webhook_secret` to be present for every configured organization (reject/log instead of silently trusting unsigned payloads) to remove the bypass path in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations: `orgA` (no `webhook_secret` set) and `orgB` (has a stack for `orgB/victim-repo`).
2. POST to the webhook endpoint with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`; since `orgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header. [6](#0-5) 
4. `PushHandler#process` resolves the stack via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, an action on `orgB`'s stack despite no valid credential for `orgB` having been presented. [5](#0-4) [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
