## Finding: Multisig transaction payload substitution due to feature-gated payload-match check

### Title
Multisig Execution Accepts a Different Payload Than the One Owners Approved — ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`validate_multisig_transaction`, the VM prologue function that gates execution of an Aptos native multisig account, only verifies that the *count* of approvals meets the required threshold for the pending `sequence_number` — it does not unconditionally verify that the payload actually being executed is the one the owners voted on. When the multisig transaction was created with the full payload stored on-chain (`create_transaction`, as opposed to `create_transaction_with_hash`), the check that the executor-supplied `payload` matches the on-chain `transaction.payload` is wrapped in `features::abort_if_multisig_payload_mismatch_enabled()`. If that feature is not enabled, an executing owner can submit an arbitrary, different payload at execution time and it will be run as the multisig account, even though the owners approved a different transaction body.

### Finding Description
`validate_multisig_transaction` [1](#0-0)  checks quorum (`can_execute`/`can_be_executed`) and timelock purely based on `sequence_number` — the vote tally is keyed only by the transaction id, not by payload content.

The only content-binding checks are:
1. If the transaction was created with a hash only (`payload_hash.is_some()`), the supplied `payload` is hashed and compared — this is unconditional. [2](#0-1) 
2. If the transaction was created with the full payload stored on-chain (`transaction.payload.is_some()`), the comparison of the supplied `payload` against the stored payload is **only performed if `features::abort_if_multisig_payload_mismatch_enabled()` is true**: [3](#0-2) 

This means that for the common case where owners call `create_transaction` (full payload on chain, no hash), the equality check between the approved payload and the executed payload is optional/feature-gated rather than an invariant. If the guarding feature is disabled, an owner who has accumulated enough approvals for sequence number N can execute that slot using a completely different payload than the one the other owners approved — the on-chain vote tally does not actually bind to a specific transaction body in that mode.

This is a direct analog of the reported ERC20 approve/transferFrom race: the "approval" (owners' votes) is meant to authorize one specific action, but the code path that should bind the approval to the exact action executed is conditionally skippable, letting the approved authorization be redirected to unapproved content.

### Impact Explanation
If `abort_if_multisig_payload_mismatch_enabled` is not active, quorum-approved votes for a multisig account do not guarantee that the approved transaction body is what executes. Any owner who can reach quorum (including an owner colluding with just enough other owners to hit threshold, or in a compromised-owner scenario) can substitute an arbitrary payload (e.g., draining funds, changing owners, rotating auth key) at execution time while other owners believe they approved something else. This breaks the core security guarantee of the multisig module — that owners are agreeing to fixed transaction content — and can result in unauthorized state transitions / fund movement under the multisig account's signer authority.

### Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is turned on in the deployed framework version. I could not determine from the repository alone whether this feature flag is enabled by default on Aptos mainnet/testnet at the current framework version — that requires checking on-chain `Features` state, which is outside the scope of local code inspection. The existence of the flag (rather than the check being unconditional) indicates this was previously an actual gap that had to be fixed via a feature-gated migration; environments/networks that have not yet enabled it remain exposed.

### Recommendation
Make the payload-match check for stored-payload multisig transactions unconditional (drop the feature gate) so that quorum approval is always cryptographically/structurally bound to the exact payload executed, consistent with how hash-based transactions are always checked. If backward compatibility requires a feature flag during rollout, ensure the flag is enabled on all networks before considering the fix complete, and treat any state where it is disabled as vulnerable.

### Proof of Concept
1. Deploy/enable a multisig account with `k`-of-`n` owners on a network where `abort_if_multisig_payload_mismatch_enabled` is disabled.
2. Owner A calls `create_transaction(owner, multisig_account, payload_X)` — payload_X is stored fully on-chain (`payload_hash` is `none`).
3. Owners vote until quorum for `payload_X` is reached via `approve_transaction`.
4. Instead of executing `payload_X`, the executing owner submits the `MultisigTransaction` execution with a different payload, `payload_Y` (e.g., transferring funds to their own address or adding themselves as an owner).
5. In `validate_multisig_transaction`, since `transaction.payload_hash` is `none`, the hash check is skipped; since the feature flag is disabled, the `payload == stored_payload` check is skipped entirely.
6. `payload_Y` executes as the multisig account despite only `payload_X` having been approved by quorum. [3](#0-2)

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );
