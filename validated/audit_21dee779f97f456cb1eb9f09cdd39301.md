I found a concrete authorization-boundary break in the CCMenu API endpoint that matches the "stack a token authorises versus a stack it touches" binding class.### Title
Stack-Scoped API Token Can Read CI/Deploy Status of Any Stack via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` bypasses the `ApiClient#stack_id` scoping enforced everywhere else in the API, so any `ApiClient` token with the `read:stack` permission — including one explicitly restricted to a single stack — can read the CI/deploy status (`deploys_and_rollbacks.last`) of *any* other stack in the installation by supplying a different `stack_id` in the URL.

### Finding Description
`ApiClient` supports being scoped to a single stack via the `stack_id` column [1](#0-0) . This scoping binding — "the stack a token authorizes" — is enforced centrally in `Api::BaseController`:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every controller that inherits `stack` from `BaseController` (e.g. `CommitsController`, `LocksController`, `TasksController`) is correctly restricted to the api client's authorized stack. However, `Api::CCMenuController` overrides `stack` to bypass this scoping entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`ApiClient#check_permissions!`, invoked by `require_permission :read, :stack`, only checks the permission string list and never checks `stack_id` at all:

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [4](#0-3) 

So the only place the "token authorizes stack X" binding is checked is the `stacks`/`stack` scoping helper in `BaseController`, and `CCMenuController` breaks that binding by re-resolving `params[:stack_id]` against the unscoped `Stack` relation.

**Binding broken:** `ApiClient.stack_id` (stack the token authorizes) ≠ `params[:stack_id]` (stack the request actually touches) for the CCMenu endpoint, even though every other `Api::*` controller preserves this equality.

### Impact Explanation
A token created and scoped to a single stack (e.g. `here_come_the_walrus`, fixture confirms `stack: shipit`, permission `read:stack` only) [5](#0-4)  can be used to query `GET /api/:stack_id/ccmenu` for any other stack_id and receive that stack's latest deploy/rollback status, lock state, and build result — data the token was never authorized to see. This is an unauthorized cross-stack read of stack state/deploy output, matching the "High - unauthenticated read of stack state, task streams or deploy output" impact category (here, "unauthorized" rather than fully "unauthenticated", since a valid but narrowly-scoped credential is required).

### Likelihood Explanation
Any party holding a legitimately-issued, narrowly-scoped `ApiClient` token (e.g. one handed to an external CI/monitoring integration for a single stack) can trivially exploit this by changing the `stack_id` path/query parameter — no additional privilege, secret, or session is required beyond the token they were already given for one stack.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, properly-scoped `stack`/`stacks` helper from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the `ApiClient#stack_id` binding is honored consistently across all API endpoints.

### Proof of Concept
1. As an authorized Shipit user, create (or have created via `CCMenuUrlController#fetch`) an `ApiClient` scoped to stack `A` with permission `read:stack` only, and note its `authentication_token`.
2. Call `GET /api/<owner>/<repoA>/<env>/ccmenu?token=<token>` — succeeds as intended, returns stack A's status.
3. Call `GET /api/<owner>/<repoB>/<env>/ccmenu?token=<token>` for an unrelated stack B that the token was never scoped to — because `CCMenuController#stack` calls `Stack.from_param!` directly (ignoring `current_api_client.stack_id`), this request also succeeds and returns stack B's deploy/lock/CI status, despite the token only authorizing stack A.
