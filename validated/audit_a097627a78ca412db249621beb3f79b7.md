## Title
Cross-stack authorization bypass in CCMenu API — `ApiClient.stack_id` scope not enforced by `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`Shipit::Api::BaseController` scopes stack lookups to the authenticated `ApiClient`'s `stack_id` when the client is stack-scoped, but `Api::CCMenuController` overrides the `stack` accessor with an unscoped lookup, breaking that binding.

## Finding Description
The intended invariant, enforced everywhere else in the API, is: **stack a token authorizes == stack it touches**. `BaseController#stacks` establishes this: [1](#0-0) 
`Api::StacksController` relies on this scoped relation for its `stack` accessor: [2](#0-1) 

However, `Api::CCMenuController` defines its own `stack` method that bypasses the scoped `stacks` relation entirely, using the global `Stack.from_param!` instead: [3](#0-2) 

Permission enforcement (`require_permission :read, :stack`) only checks that the string `"read:stack"` exists in the client's `permissions` array — it never checks that `params[:stack_id]` matches `current_api_client.stack_id`: [4](#0-3) 

This is the same class of bug as the analog report: one accounting/authorization value (`sETHStakedBalanceForKnot`) is updated/checked while a related value it should stay consistent with (`sETHUserClaimForKnot`) is not, so the entitlement actually used diverges from the entitlement that was authorized. Here, the entitlement is `ApiClient#stack_id` (the single stack a scoped token is meant to read), and the value actually acted on is `params[:stack_id]` resolved through an unscoped `Stack.from_param!`.

## Impact Explanation
This matches the High-severity impact category "unauthenticated read of stack state, task streams or deploy output." A stack-scoped, read-only token (e.g. `here_come_the_walrus` fixture: `stack: shipit`, `permissions: [read:stack]`, as modeled at) — [5](#0-4) 
— is meant to only ever see the single stack it was scoped to (as verified for `Api::StacksController#index`) — [6](#0-5) 
— but when the same token is presented to `GET /api/stacks/:stack_id/cctray.xml` with an *arbitrary* `stack_id`, `CCMenuController#stack` resolves any stack in the installation, disclosing that stack's name, lock status, and last build/deploy status/label/time regardless of the token's intended scope.

## Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped `read:stack` `ApiClient` token (a routine, low-privilege credential meant to be handed to CI dashboards/CCMenu clients) can immediately enumerate/read the state of every other stack in the Shipit instance simply by varying the `stack_id` path parameter — no additional exploitation steps or privilege escalation needed.

## Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot resolve stacks outside their `stack_id`.

## Proof of Concept
1. Admin issues a stack-scoped API client for `stack_id: A` with `permissions: ['read:stack']` (mirrors fixture `here_come_the_walrus`).
2. Attacker (holder of that token) sends:
   `GET /api/stacks/B/cctray.xml` with `Authorization: Basic base64(token)`, where `B` is any other stack id/slug in the installation.
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes because `check_permissions!` only checks the permission string, not `stack_id`.
4. `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` — unscoped — and returns stack `B`, whose build/deploy status is rendered in the XML response, even though the token was only ever authorized for stack `A`.
