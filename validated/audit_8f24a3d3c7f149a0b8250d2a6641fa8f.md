### Title
Weak 128-bit-effective `chash160` addresses enable a birthday-attack takeover of unused/underfunded addresses via first-definition-binding - (File: chash.js, validation.js)

### Summary
`ocore`'s address scheme (`getChash160` in `chash.js`) truncates the 160-bit RIPEMD160 hash down to 128 bits of independent entropy (a 32-bit checksum is mixed back in, but it is fully *derived* from those same 128 bits, so it adds no extra collision resistance). Addresses are bound to whichever definition is *first seen* on the network with a matching `chash160` (`storage.readDefinitionByAddress` / `validateAuthor` in `validation.js`), with no other proof of legitimate prior ownership required. Combining a birthday attack on the 128-bit truncated hash (feasible with ~2^64 hash operations, dramatically cheaper than the ~2^80–2^81 the referenced report showed to be a multimillion-dollar/near-term threat for 160-bit Uniswap-style truncation) with the "first-use wins" address-binding rule allows an attacker to precompute a definition that collides with a not-yet-used address and race to bind it, hijacking any funds later or previously sent there.

### Finding Description
`chash.js` builds addresses as follows: [1](#0-0) . The RIPEMD160 output (160 bits) has its first 4 bytes (32 bits) dropped, leaving 128 bits of "clean data"; a 32-bit checksum is then computed purely as a `sha256` digest of that same 128-bit clean data ( [2](#0-1) ) and mixed back into the 160-bit encoded value. Because the checksum carries zero independent entropy (it's a deterministic function of the 128 bits), the entire 160-bit-looking `chash160` address only offers **128 bits** of real collision resistance instead of the expected 160.

This is used pervasively as the address for definitions/wallets/AAs: `object_hash.getChash160` ( [3](#0-2) ) is the canonical address derivation function used by `validateAuthor`/`validateDefinition` in `validation.js` to accept the *first* definition observed for an address as authoritative: [4](#0-3) 

and in the more general `validateAuthor` flow: [5](#0-4) 

Note the code comment confirming the semantics: *"first use of the definition_chash (in particular, of the address, when definition_chash=address)"* (`validation.js:220`, `signed_message.js:220`). In other words, **whoever first posts a unit whose `definition` hashes (via the weakened `chash160`) to a given address becomes the permanently recognized owner of that address**, with no further authentication of "who should own it."

Given the birthday paradox, an attacker only needs ~2^64 `ripemd160`+`sha256` evaluations (not 2^80) to find a pair of definitions — one fully attacker-controlled (e.g., a simple `['sig', {pubkey: attacker_pubkey}]`) and one plausible/likely-to-be-generated definition (e.g., matching common wallet/HD-derived `sig` or multisig templates used by exchanges, textcoin generators (`wallet.js` `expandMnemonic`/`receiveTextCoin`), or shared-address templates in `wallet_defined_by_addresses.js`) — that produce the identical `chash160` address. 2^64 keccak/ripemd-class hashes is achievable with commodity GPU/ASIC clusters at a small fraction of the cost estimated in the source report for a 2^80–2^81 attack (which was already assessed there as economically viable within a decade); 128-bit birthday resistance is roughly 65,000× weaker and is already within reach of well-resourced attackers or nation-state actors today.

### Impact Explanation
If an attacker locates such a collision before the legitimate address is ever "used" (i.e., before its owner has posted any unit from it — which is common for addresses that only *receive* funds, such as textcoin addresses, donation addresses, deposit addresses generated by exchanges/services, or freshly derived HD-wallet addresses that have received but not yet spent funds), the attacker can broadcast a unit using the colliding, attacker-controlled definition first. Per the first-use binding rule, the network will thereafter treat the attacker's definition as authoritative for that address, letting the attacker sign and spend all funds sent to that address — a direct unauthorized-spending / fund-theft primitive reachable by any unprivileged unit poster, requiring no special privilege beyond being first to post a colliding definition. This is qualitatively the same "invalid validation via truncated-hash collision" root cause as the referenced Panoptic finding, adapted to ocore's address/definition-binding model instead of Uniswap-V3 pool-callback verification.

### Likelihood Explanation
The precomputation cost (~2^64 hashes) is large but no longer implausible for a well-funded adversary, and is drastically cheaper than the ~2^80/2^81 scenario the source report already argued was "prudent to fix" given a multi-year outlook; ocore's 128-bit-effective address space is far more exposed than typical 160-bit UTXO-chain addresses (e.g., Bitcoin's P2PKH, which does not have this checksum-truncation weakness). The attack also benefits from ocore's large surface of predictable/templated definitions (HD-derived `sig` addresses, multisig templates, AA definitions) that make the "target set" side of the birthday search practically enumerable, similar to how Panoptic's `PoolFeatures` (token0/token1/fee) provided an attacker-enumerable target set.

### Recommendation
Do not derive the checksum from the same truncated hash bits that constitute the address's core entropy; either (a) use the full, untruncated hash output (e.g., stop dropping the first 4 bytes of RIPEMD160, keeping the full 160 bits as address material with a checksum computed independently/externally, similar to Base58Check), or (b) increase the underlying hash width so that even after truncation for the checksum, at least ~160 bits of independent post-truncation entropy remain. Additionally, consider strengthening the "first-use wins" binding rule (in `validation.js`'s `validateDefinition`/`validateAuthor`) with additional proof-of-possession requirements (e.g., requiring a valid signature under the claimed definition from the moment funds are first sent, not merely at spend time) to reduce the impact of any future hash-collision discovery.

### Proof of Concept
1. `chash.js:getChash160` computes `ripemd160(data)`, drops the first 4 bytes, leaving a 128-bit `truncated_hash` (`chash.js:125-127`).
2. `getChecksum` computes the 32-bit checksum solely from `truncated_hash` via `sha256` (`chash.js:115-120`) — it is fully determined by, and adds no entropy beyond, the 128-bit truncated hash.
3. Therefore, any two definitions `D1`, `D2` that produce the same 128-bit RIPEMD160 tail will produce the identical `chash160` address, achievable via a birthday search of ~2^64 evaluations (vs. the theoretical 2^80 a naive 160-bit hash implies).
4. An attacker precomputes a large batch of self-controlled `sig` definitions and searches for a collision against a plausible/target definition template (e.g., `['sig', {pubkey}]` addresses commonly minted by `wallet_defined_by_keys.js:deriveAddress`/`checkAddress`, or `wallet.js:expandMnemonic` textcoin addresses).
5. Once a collision is found for an address that has not yet had any unit posted from it, the attacker submits a unit whose `author.definition` is the attacker's colliding definition; `validation.js:1464-1479` (`ifDefinitionNotFound`) accepts it purely because `objectHash.getChash160(arrAddressDefinition) === definition_chash`, permanently binding the address to the attacker's definition and giving the attacker spending control over all current and future funds sent to that address.
