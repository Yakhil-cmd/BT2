### Title
`StatusHandler#process` writes commit statuses by bare SHA with no repository/stack scoping, letting a `github-actions` status intended for one repository flip status on a commit belonging to a different stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Finding Description
The broken binding: the invariant the system should enforce is `commit.stack.github_repo_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a `status` webhook. `StatusHandler#process` never checks this.

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike other handlers, `StatusHandler` never calls the base class's `stacks` helper, which is the only mechanism that ties a webhook payload to the repository that actually sent it via `Repository.from_github_repo_name(repository_name)`: [2](#0-1) 

Instead it queries the global `commits` table by bare `sha` across all stacks/repositories and calls `commit.create_status_from_github!(params)` on every match, which appends a `Status` row and re-evaluates `deployable?`/`schedule_continuous_delivery` for whichever stack that commit happens to belong to: [3](#0-2) [4](#0-3) 

`Commit.sha` has no application-level uniqueness constraint scoped to `stack_id`; it is only unique in practice because SHA-1 is content-derived. This means any two stacks (repositories) whose `commits` tables contain a row with the identical `sha` (which happens whenever repos share git history - forks, mirrors, subtree merges, monorepo split stacks tracking the same upstream commits) are cross-wired: a `status` event authenticated for repository A will be applied to the commit row for repository B if both have ingested that SHA.

Signature verification does not close this gap. `WebhooksController#verify_signature` resolves the GitHub App/secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's own `repository.owner.login`/`organization.login`: [5](#0-4) 

This verifies that the request was signed by *some* valid webhook secret for the organization named in the attacker-controlled payload, not that the SHA inside the payload actually belongs to the repository named in that payload. `StatusHandler` then discards the payload's `repository` field entirely and resolves by SHA only, so the org-level signature check provides no repository-scoping guarantee at all for this handler.

Exploit flow:
1. Attacker owns/controls a repository (or a GitHub App installation) that is legitimately configured to send Shipit webhooks (e.g., their own fork tracked by their own low-privilege Shipit stack).
2. Attacker identifies a SHA that is present both in their own repository's commit history and in the victim stack's `commits` table (common with forks/mirrors of the same upstream, or monorepo split into multiple Shipit stacks).
3. Attacker triggers (or directly POSTs, since they control CI/webhook delivery for their own repo) a `status` event with `context: github-actions`, `state: failure`, `sha: <shared-sha>`. The signature validates because it is genuinely signed for the attacker's own org/repo.
4. `StatusHandler#process` matches `Commit.where(sha: ...)` across all stacks, finds the victim's `Commit` row with the same `sha`, and calls `create_status_from_github!` on it, writing a `failure` status for `github-actions` onto the victim's commit.
5. If the victim stack has `continuous_deployment` enabled and requires the `github-actions` context, this flips `deployable?`/`blocked?` on the victim's commit and re-triggers `schedule_continuous_delivery` / `ContinuousDeliveryJob`, forcing a ship or a block on a commit the attacker does not control the CI signal for.

None of the existing guards catch this: `verify_signature` only proves org-level authenticity of the *sender*, not repository ownership of the *SHA in the body*; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema for `StatusHandler` validates types, not repository scope; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler#process` the way there is in the shared `Handler#stacks` helper (which this handler simply never uses).

### Impact Explanation
A payload legitimately authenticated for repository/org A can write a `Status` record (and drive `deployable?`, `blocked?`, and `ContinuousDeliveryJob` scheduling) against a `Commit` belonging to stack/repository B, whenever B has ingested a commit with the same SHA (fork/mirror/monorepo scenarios). This is a cross-tenant data-integrity violation matching the "payload for one repository mutating another's stack/commit" Critical category: on a `continuous_deployment`-enabled victim stack, a forged `failure` status can block deploys of legitimate green commits, and (depending on which context is being flipped) a forged `success`/passing sequence could instead unblock deploys of an attacker-influenced commit, resulting in unauthorized deploy or rollback. The attack is repeatable against any pair of stacks that share commit history and is not limited to a single request.

### Likelihood Explanation
Exploitability requires the attacker to control a webhook source (their own repository/fork) whose signature validates for whatever `repository_owner` they place in the payload, and requires a real SHA collision (in the git sense) between that source and the victim's `commits` table - i.e., shared git history from forking, mirroring, or splitting a monorepo into multiple stacks, which is a common real-world Shipit deployment pattern. No Shipit credentials, sessions, or API tokens are needed; the attacker only needs the ability to have a genuinely-signed `status` webhook delivered (via their own repo's Actions/CI or a webhook they control) referencing a shared SHA. This is a realistic, low-cost, repeatable precondition rather than a purely theoretical one, given how common fork-based/mirrored Shipit stack setups are.

### Recommendation
Scope `StatusHandler#process` (and mirror the pattern the base `Handler#stacks` helper already provides) to only update commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, or equivalently join through `Stack`/`Repository` before calling `create_status_from_github!`. Additionally, do not treat organization-level webhook signature verification as sufficient proof of repository identity for the payload body — validate that any repository/commit resolution matches the authenticated organization/repository context.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `stack_a` (attacker's repo, e.g. `attacker/fork`) and `stack_b` (victim, `victim/upstream`) with `continuous_deployment` enabled and `required_statuses` including `github-actions` on `stack_b`.
2. Create a `Commit` with `sha: "deadbeef" * 5` (or any fixed 40-char sha) under `stack_b`, with an existing passing `github-actions` status such that `commit.deployable?` is `true` and, on the victim's environment, `ContinuousDeliveryJob` would ship it.
3. Also create a `Commit` with the identical `sha` under `stack_a` to simulate the shared-history condition (or bypass by directly asserting `Commit.where(sha:)` returns the `stack_b` row when only `stack_a`'s repository is named in the payload).
4. Build a payload: `{ 'sha' => sha, 'state' => 'failure', 'context' => 'github-actions', 'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert: `stack_b`'s commit (`commit_b.reload.deployable?`) is now `false` / `blocked?` is `true`, even though the payload's `repository.full_name` (`attacker/fork`) never matched `stack_b`'s repository (`victim/upstream`) — i.e. `commit_b.stack.github_repo_name != payload['repository']['full_name']` yet the status was still applied to `commit_b`, proving the binding is broken. Compare against the expected-safe behavior where `commit_b`'s status/deployability should remain unchanged because the webhook was not authenticated for `victim/upstream`.
