## Title
Multisig transaction execution admits a payload that was never voted on when `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, invoked by the VM during transaction prologue (both mempool admission and the first step of execution), is supposed to bind the payload that owners approved to the payload that is actually executed. When the multisig transaction was created with the full payload stored on-chain (via `create_transaction`, as opposed to `create_transaction_with_hash`), that binding is only enforced if the governance feature `abort_if_multisig_payload_mismatch_enabled()` is turned on. If it is off, an owner who has accumulated the required quorum of approvals for sequence number N can submit a **different** payload at execution time and it will be admitted and executed as the multisig account, bypassing what the other owners actually approved.

### Finding Description
`validate_multisig_transaction` is the admission function run by the VM prologue for `MultisigTransaction` payloads: [1](#0-0) 

The actual bytes checked against on-chain state come from the transaction's own executable, not from any separately-approved record — `run_multisig_prologue` derives `provided_payload` directly from the `TransactionExecutableRef` of the transaction being validated/executed: [2](#0-1) 

Inside `validate_multisig_transaction`, quorum/timelock is checked first, then payload binding: [3](#0-2) 

Two binding paths exist:
1. If the transaction was created with `create_transaction_with_hash` (`payload_hash.is_some()`), the hash is always checked — this path is safe.
2. If the transaction was created with `create_transaction` (full `payload` stored, `payload_hash` is `None`), the equality check `payload == *stored_payload` is only performed when `features::abort_if_multisig_payload_mismatch_enabled()` is true.

If that feature is disabled, an owner who already commands the signature threshold for sequence number N (having gathered votes for whatever payload was originally proposed) can submit any arbitrary executable at admission time; `validate_multisig_transaction` will not detect the mismatch, and the VM will proceed to execute that arbitrary payload as the multisig account (`successful_transaction_execution_cleanup` records success against the *original* stored `transaction_payload`, not what was actually run) — see the cleanup function, which takes the executed `transaction_payload` as a caller-supplied argument in the same call: [4](#0-3) 

This is exactly the admission-boundary defect class described in the external report (a required binding check exists but can be skipped), here manifesting as a **wrong approval set being accepted**: votes cast for payload A are treated as authorization to run payload B.

### Impact Explanation
This breaks the core multisig invariant that execution requires k-of-n approval of the *specific* action being taken. A single owner (or colluding subset reaching quorum, which could be as low as 1-of-N) can execute an arbitrary entry function or script as the multisig account's signer — moving funds, changing owners, or invoking any module — without the other owners ever approving that specific payload. Given multisig accounts are frequently used to hold significant treasury/asset value or control privileged capabilities, this is a High/Critical unauthorized-execution vulnerability at the transaction admission boundary.

### Likelihood Explanation
Exploitability depends entirely on whether `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is enabled on the target network at the time of exploitation. If the flag is disabled (its pre-activation/default state on some networks or a freshly-forked chain that has not yet enabled all governance flags), the bypass is straightforward for any owner who has reached quorum for any transaction ID, without needing any additional privilege beyond being a normal multisig owner with vote-gathering ability for the pending sequence number. The precondition is a feature-flag state rather than a special code path, so likelihood is a function of on-chain configuration rather than attacker sophistication.

### Recommendation
Remove the feature-flag gate on the payload-match assertion for the full-payload (non-hash) creation path so binding is unconditional, e.g.:
```move
if (transaction.payload.is_some()) {
    let stored_payload = transaction.payload.borrow();
    assert!(
        payload == *stored_payload,
        error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
    );
};
```
removing the `features::abort_if_multisig_payload_mismatch_enabled() && !payload.is_empty()` conditions, or at minimum make the check unconditional if `payload` is non-empty regardless of the feature flag, since the flag should only ever have gated a *migration/rollout* concern, not a security-relevant invariant.

### Proof of Concept
1. Deploy a multisig account with 2 owners, threshold 2 (owners A and B).
2. On a network/build where `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is disabled, owner A calls `create_transaction(multisig, payload_transfer_1_APT_to_A)`, sequence number N.
3. Owner B, believing it's a benign 1 APT transfer, calls `approve_transaction(multisig, N)`.
4. Quorum (2/2, or the executing owner's implicit vote plus B's explicit vote) is now met for sequence N.
5. Owner A crafts and submits (or executes) a `MultisigTransaction` at the VM level whose `executable` is a *different* entry function (e.g., transferring the entire multisig balance to A, or rotating owners) instead of the approved 1 APT transfer.
6. `run_multisig_prologue`/`validate_multisig_transaction` computes `provided_payload` from this new executable, finds `payload_hash` is `None` (full-payload path), and — because the feature flag is off — skips the `payload == stored_payload` comparison entirely.
7. Quorum and timelock checks pass (based on votes for the original payload), and the VM executes the *substituted* payload as the multisig account, draining/reconfiguring it without owner B's actual consent.

```rust
pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
```
