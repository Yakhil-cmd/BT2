### Title
Stack-scoped API token bypasses stack authorization in CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup method to load the stack directly from `params[:stack_id]` instead of going through the `current_api_client`-scoped `stacks` collection that every other API controller uses. This lets a token that is authorized ("scoped") for one specific stack read deploy status for **any** stack in the installation.

### Finding Description
`Shipit::Api::BaseController` enforces a binding between an `ApiClient`'s authorized stack and the stack it can act on: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, and `stack` resolves the requested stack from that restricted set: [1](#0-0) 

`CCMenuController` re-defines `stack` to bypass this restriction entirely, resolving the stack from the global `Stack` scope regardless of the token's `stack_id`: [2](#0-1) 

`require_permission :read, :stack` only checks that the `read:stack` string is present in the token's `permissions` array via `ApiClient#check_permissions!`; it never checks that the *scope's stack instance* matches the token's `stack_id`: [3](#0-2) 

Because `CCMenuUrlController` mints exactly this kind of stack-scoped, read-only token to be embedded unauthenticated in a URL (e.g. for CI dashboard tooling): [4](#0-3) 

and `CCMenuController#authenticate_api_client` accepts the token purely via the `?token=` query parameter (no basic-auth/session needed): [5](#0-4) 

any holder of one such single-stack token can request `GET /api/stacks/:other_owner/:other_repo/:other_branch/ccmenu` and successfully load and render deploy status for a stack it was never authorized to see: [6](#0-5) 

This reproduces the report's bug class: a value that is checked/authorized (the stack a token is bound to) diverges from the value that is actually used at execution time (the stack the request touches), because the authorization check for that binding was silently skipped in this one controller.

### Impact Explanation
This crosses the "a stack a token authorises versus a stack it touches" trust boundary explicitly listed as in-scope. The result is unauthenticated (query-param-token-only) disclosure of another stack's deploy/rollback status (deploy id, timestamps, running state) to a party who was only ever granted `read:stack` for a *different, specific* stack. This matches the "High" impact bucket: unauthenticated read of stack state / deploy output.

### Likelihood Explanation
Any low-privilege actor who legitimately obtains one CCMenu URL/token for their own stack (these are designed to be shared in URLs, e.g. embedded in CI dashboard configs) can trivially swap `stack_id` in the path to any other `owner/repo/branch` combination known to them and read that stack's status too. No additional secret, session, or elevated permission is required beyond the one CCMenu token they already legitimately hold.

### Recommendation
Remove the `stack` override in `CCMenuController` (or make it consult `stacks` like `BaseController#stack` does) so the CCMenu lookup is restricted to `current_api_client.stack_id` when the client is stack-scoped, i.e. reuse `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`.

### Proof of Concept
1. Legitimately obtain a CCMenu URL for stack A via `GET /ccmenu/*stack_A` (as in `CCMenuUrlController#fetch`), which mints a token scoped to stack A with `permissions: ['read:stack']`.
2. Note the `token` query parameter value from the returned `ccmenu_url`.
3. Send `GET /api/stacks/<owner_B>/<repo_B>/<branch_B>/ccmenu?token=<token>` for an unrelated stack B.
4. Observe that the request succeeds (200 OK) and returns stack B's real deploy status, even though the token's `stack_id` only authorizes stack A.
