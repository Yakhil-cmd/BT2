### Title
Webhook signature verification is keyed on an attacker-controlled `repository.owner.login`/`organization.login` field that is decoupled from the identity fields (`repository.full_name`, `organization.login`) actually consumed by webhook handlers, allowing forged cross-organization events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a request against by reading `repository_owner` straight out of the unauthenticated JSON body, then uses that *same* body's independent `repository.full_name` (or, for membership events, `organization.login`) to decide which `Stack`/`Team` the payload actually mutates. Nothing enforces that these two fields refer to the same organization. An attacker who can produce a validly-signed payload for *any* configured organization (including one with no `webhook_secret` set, which the docs call optional) can freely pick a different `repository.full_name`/`organization.login` naming a completely unrelated, victim-owned Shipit stack or team, and have the handler act on it as if it came from GitHub for that repository.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49` computes the organization used for HMAC verification purely from the payload: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) simply HMACs the raw body with the secret for whatever organization was named by `repository_owner`, and — critically — always returns `true` if that organization has no `webhook_secret` configured: [3](#0-2) 

Once verification passes, `create` dispatches the *entire, unmodified* payload to handlers: [4](#0-3) 

But handlers resolve the target `Stack`/`Repository` from a *different* payload field, `repository.full_name`, not from `repository.owner.login`: [5](#0-4) 

and, e.g., `PushHandler` triggers a real GitHub sync job against those stacks using purely payload-derived branch/sha data: [6](#0-5) 

The `MembershipHandler` is worse: it derives the `Team#organization` and adds/removes arbitrary GitHub logins as team members purely from `params.organization.login` and `params.member.login`, again independent of `repository_owner`: [7](#0-6) 

**Binding that is broken (as an equality):**
`organization used to authenticate the webhook signature` (`repository_owner` = `payload.dig('repository','owner','login')`) MUST equal `organization/repository whose Shipit state is written` (`payload.dig('repository','full_name')` for stack-scoped handlers, `payload.dig('organization','login')` for `MembershipHandler`). The engine never asserts this equality — it only checks that *some* configured organization's secret matches the raw body, and then blindly trusts unrelated identity fields inside that same body to select the object being mutated.

### Impact Explanation
This directly maps to the "High — escalation into `Shipit.github_teams` authorization" impact bucket: by crafting a payload where `repository.owner.login`/verification succeeds cheaply (e.g., against an org configured without a `webhook_secret`, which `docs/setup.md` and `config/secrets.development.example.yml` both document as optional) while `organization.login` names the victim's protected GitHub organization, an attacker can call the `membership` webhook to add an arbitrary GitHub login (their own account) to a `Team` that backs `Shipit.github_teams` authorization (`app/controllers/concerns/shipit/authentication.rb`), or remove legitimate members. This escalates an unprivileged external caller into the authorization group gating access to the whole Shipit UI/API. The same owner/full_name decoupling also lets an attacker trigger `push`/`status`/`check_suite` driven jobs (`GithubSyncJob`, `RefreshCheckRunsJob`, etc.) against stacks belonging to organizations they don't control, corrupting deploy/CI state used for unattended continuous-deployment decisions.

### Likelihood Explanation
The `/webhooks` endpoint is deliberately public and unauthenticated apart from the HMAC check (`docs/setup.md` instructs exposing it at `<host>/webhooks`), so any external, unprivileged actor can POST directly to it — no GitHub session, `ApiClient` token, or repository write access is required, satisfying the "no host application deviation" and "no privileged account" constraints. The only prerequisite is a Shipit deployment tracking more than one GitHub organization (explicitly documented and supported, "Using Multiple Github Applications") where at least one configured organization omits `webhook_secret` (explicitly documented as optional), or an attacker who otherwise knows one org's `webhook_secret` (e.g., their own org's app). Given the docs actively market both multi-org support and optional webhook secrets, this is a realistically reachable configuration, not a theoretical edge case.

### Recommendation
Require and enforce that the organization used to select/verify the webhook secret matches the organization implied by every identity field the corresponding handler consumes (`repository.full_name`'s owner, or `organization.login` for org-scoped events) before dispatching to handlers. Reject payloads where these fields disagree, and make `webhook_secret` mandatory (or scope handler lookups to the verified organization) rather than allowing organizations with no secret to authenticate arbitrary cross-organization payloads.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`, "Using Multiple Github Applications") with two orgs: `victim-org` (has `webhook_secret` set) and `attacker-org` (misconfigured/left blank per the "optional" docs, or an org the attacker independently controls and knows the secret for).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}
}
```
3. `verify_signature` computes `repository_owner` = `"attacker-org"` (from `repository.owner.login`) and validates the HMAC using `attacker-org`'s (blank/known) secret — this succeeds trivially.
4. `MembershipHandler#process` reads `params.organization.login` = `"victim-org"` and `params.member.login` = `"attacker-github-login"`, creating/updating the `victim-org` `Team` and adding the attacker's GitHub login as a member — all without ever touching `victim-org`'s real webhook secret.
5. If `Shipit.github_teams` includes this `victim-org` team, the attacker's GitHub account now passes `current_user.authorized?` in `app/controllers/concerns/shipit/authentication.rb`, gaining access to the Shipit UI/API for that deployment.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
```

```ruby
          member = User.find_or_create_by_login!(params.member.login)

        end
```
