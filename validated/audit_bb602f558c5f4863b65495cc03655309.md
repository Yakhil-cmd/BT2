### Title
Bridge `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` Missing `isRunning` Guard Allows Asset Drain from a Stopped Bridge — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge exposes a `bool public isRunning` flag (the direct analog of ENS's `live` modifier) that the owner can set to `false` to halt bridge operations. Every **outbound** (request) path enforces this flag. Every **inbound** (handle) path — `handleKLAYTransfer`, `handleERC20Transfer`, `handleERC721Transfer` — does **not** enforce it. Registered operators can therefore drain KLAY and bridged tokens from a bridge that the owner has explicitly stopped.

---

### Finding Description

`BridgeTransfer.sol` declares `bool public isRunning = true` and exposes `setRunningStatus(bool)` / `start(bool)` (both `onlyOwner`) to pause the bridge. [1](#0-0) 

All three **request** (outbound) functions enforce the flag:

- `_requestKLAYTransfer` — `require(isRunning, "stopped bridge")` [2](#0-1) 
- `_requestERC20Transfer` — `require(isRunning, "stopped bridge")` [3](#0-2) 
- `_requestERC721Transfer` — `require(isRunning, "stopped bridge")` [4](#0-3) 

All three **handle** (inbound) functions carry only `onlyOperators` (and `nonReentrant` for KLAY) — **no `isRunning` check**:

- `handleKLAYTransfer` — modifiers: `onlyOperators nonReentrant` [5](#0-4) 
- `handleERC20Transfer` — modifier: `onlyOperators` [6](#0-5) 
- `handleERC721Transfer` — modifier: `onlyOperators` [7](#0-6) 

The concrete asset movements that execute without the guard:

- KLAY: `_to.call.value(_value)("")` [8](#0-7) 
- ERC20: `IERC20(_tokenAddress).safeTransfer(_to, _value)` or `ERC20Mintable.mint` [9](#0-8) 
- ERC721: `IERC721.transferFrom` or `ERC721MetadataMintable.mintWithTokenURI` [10](#0-9) 

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` — e.g., in response to a security incident, a migration, or a counterpart-chain compromise — the intent is to freeze all asset movement through the bridge. Because the handle functions bypass `isRunning`, any registered operator can continue to submit (or replay previously queued) handle transactions, causing the bridge contract to push KLAY or tokens to arbitrary `_to` addresses. In `modeMintBurn = true` mode the impact extends to unbounded minting of bridged ERC20/ERC721 tokens on the destination chain.

---

### Likelihood Explanation

Operators are semi-trusted accounts registered by the owner (`registerOperator` is `onlyOwner`). In a normal bridge deployment there are multiple operators. If even one operator is compromised, or if the owner stops the bridge precisely because an operator is suspected of misbehaviour, that operator can still execute handle calls. The Go-layer bridge manager (`node/sc/bridge_manager.go`) automatically submits handle transactions in response to counterpart-chain events, so the path is exercised in every normal bridge run. [11](#0-10) 

---

### Recommendation

Add `require(isRunning, "stopped bridge")` at the top of each handle function (after `_lowerHandleNonceCheck`), or introduce a shared `onlyRunning` modifier in `BridgeTransfer.sol` and apply it to all six public transfer entry points symmetrically:

```solidity
modifier onlyRunning() {
    require(isRunning, "stopped bridge");
    _;
}
```

Apply to `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer`.

---

### Proof of Concept

1. Deploy `Bridge` (lock-mode, `modeMintBurn = false`) with 10 ETH of KLAY liquidity.
2. Register `operator` via `registerOperator(operator)`.
3. Owner calls `setRunningStatus(false)` — bridge is stopped.
4. `operator` calls:
   ```solidity
   bridge.handleKLAYTransfer(
       txHash, from, attacker, 10 ether,
       nonce, blockNum, ""
   );
   ```
5. Transaction succeeds; `attacker` receives 10 KLAY from the stopped bridge.
6. Repeat with `handleERC20Transfer` / `handleERC721Transfer` for token assets.

The same path is triggered automatically by the Go bridge manager whenever it processes a pending `RequestValueTransfer` event, meaning no manual operator action is required — the relay daemon itself will drain the bridge after the owner stops it.

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
