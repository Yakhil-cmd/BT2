### Title
Webhook signature verified against payload-derived organization while handlers act on a different, attacker-controlled repository/organization field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to validate a webhook against by reading an unauthenticated field out of the JSON body itself, while the downstream event handlers key their writes off a *different* field in the same body. In a multi-organization Shipit deployment (a documented, supported configuration), this creates exactly the "authenticated organization ≠ repository/organization written" binding break called out in the rules, mirroring the fee-double-counting root cause: a value is trusted/acted on before (and independently of) the check that is supposed to bind it to the verified credential.

### Finding Description
`verify_signature` computes the org used to fetch the webhook secret like this:

<cite repo="Camomtat/shipit-engine--001" path="app/controllers/shipit/webhooks_controller.rb" start="24-30" />
<cite repo="Camomtat/shipit-engine--001" path="app/controllers/shipit/webhooks_controller.rb" start="59-62" />

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is used only to pick `github_app = Shipit.github(organization: repository_owner)` and validate `X-Hub-Signature` against *that org's* configured `webhook_secret`. It is never re-checked against the data the event handlers actually operate on.

The handlers, however, resolve the target `Repository`/`Stack` from a completely separate field, `repository.full_name`:

<cite repo="Camomtat/shipit-engine--001" path="app/models/shipit/webhooks/handlers/handler.rb" start="32-38" />

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then writes to whatever stacks match that `full_name`, calling `stack.sync_github(expected_head_sha: params.after)`:

<cite repo="Camomtat/shipit-engine--001" path="app/models/shipit/webhooks/handlers/push_handler.rb" start="12-17" />

Because `repository_owner` falls back to `organization.login` when `repository.owner.login` is absent, an attacker who controls a payload's `organization` object independently of its `repository` object can make signature verification run against Org A's secret (which the attacker legitimately knows, e.g. because they administer a GitHub App installation on Org A) while `repository.full_name` in the very same signed body points at Org B's repository/stack. `Repository.from_github_repo_name`/`Stack` records are global, not scoped per-org-config:

<cite repo="Camomtat/shipit-engine--001" path="app/models/shipit/repository.rb" start="53-56" />

The multi-org configuration this depends on is explicitly documented as a supported setup, each org having its own distinct `webhook_secret`:

<cite repo="Camomtat/shipit-engine--001" path="config/secrets.development.example.yml" start="18-38" />

Before vs. after the attacker's request:
- Before: signature covers a payload whose `organization.login` = "OrgA" (secret known/available to the attacker) and whose `repository.full_name` = "OrgB/target-repo" (a stack unrelated to Org A, which the attacker does not administer).
- After: `verify_signature` passes (Org A's secret matches), but `PushHandler` (or `CheckSuiteHandler`, which also uses `repository_name`/`stacks`) executes `stack.sync_github(...)` against Org B's stack — i.e., it authenticates as Org A and writes to Org B.

The binding that should hold is: `organization used to verify signature == organization owning the repository/stack that is mutated`. The code breaks this equality because the field feeding the signature-secret lookup and the field feeding the mutated resource are independently attacker-controlled inside one payload, and nothing cross-validates them.

### Impact Explanation
This is a cross-repository/cross-organization write: an actor who is only authorized (has webhook credentials) for one GitHub organization's Shipit App installation can cause writes (commit sync, and — if `continuous_deployment`/CI-driven automation is enabled on the target stack — subsequent automated deploys) against a stack belonging to a different, unrelated organization/repository that they have no access to. This matches the "Critical - cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
This requires the operator to run Shipit with more than one GitHub organization configured (a first-class, documented feature) and requires the attacker to control (or know the webhook secret for) at least one of those organizations' App installations — a realistic scenario in shared/self-service Shipit deployments where multiple teams each install their own GitHub App into the same Shipit instance. No repository write access, session, or `ApiClient` token to the *target* org is needed, satisfying the "unprivileged attacker" requirement relative to the victim org.

### Recommendation
Bind the same field used for signature verification to the field used for resource resolution: after verifying the signature with the org derived from `repository.owner.login`/`organization.login`, re-derive/validate that `repository.full_name`'s owner segment equals that same verified `repository_owner` before dispatching to any handler, rejecting the webhook (422) otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `github: { orga: { webhook_secret: SECRET_A, ... }, orgb: { webhook_secret: SECRET_B, ... } }`, each with a Shipit stack for their own repo.
2. As an administrator of Org A's GitHub App installation (holder of `SECRET_A`), craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "organization": { "login": "orga" },
  "repository": { "full_name": "orgb/target-repo" }
}
```
(omit `repository.owner.login` so `repository_owner` falls back to `organization.login`).
3. Sign the raw body with `SECRET_A` and send it as `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` looks up `Shipit.github(organization: 'orga')` and validates successfully against `SECRET_A`.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('orgb/target-repo')` and calls `sync_github` on Org B's stack, even though the request was only authenticated as Org A.
