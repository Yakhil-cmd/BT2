### Title
Webhook signature check authenticates the org derived from `repository.owner.login`, but event handlers act on the org/repo derived from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App (and thus which webhook secret) to use for HMAC verification based on a payload field, `repository.owner.login`, that is **not itself covered by any signature yet** (the signature hasn't been checked when this value is read). Once verification "succeeds", the actual event handlers that write to the database use a **different** payload field, `repository.full_name`, to resolve the target `Repository`/`Stack`. These two fields can be set independently in an attacker-crafted JSON body, breaking the binding: *organization that authenticated == repository that is written*.

### Finding Description
`verify_signature` picks the GitHub App/secret using `repository_owner`: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` resolves per-org config, including `webhook_secret`, and `GitHubApp#verify_webhook_signature` **bypasses verification entirely (`return true unless webhook_secret`) when that org has no secret configured**: [3](#0-2) [4](#0-3) 

Once the `before_action` chain passes, `create` dispatches the raw JSON body to every registered handler for the event: [5](#0-4) 

Every handler resolves its target repository/stack from a **different** field, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`: [6](#0-5) [7](#0-6) 

Because a GitHub webhook payload is just JSON with no internal consistency guarantee, and `Shipit` explicitly supports multiple independently-configured GitHub Apps/organizations sharing one instance (documented multi-org config, several example configs shipping with `webhook_secret: # nil`): [8](#0-7) [9](#0-8) 

an attacker who can trigger a POST to `/webhooks` for any org configured **without** a `webhook_secret` can set:
- `repository.owner.login` = that unsecured org (or `organization.login` if `repository` key is absent for that lookup) → used only to choose the (secret-less) app, verification auto-passes.
- `repository.full_name` = `"<victim-org>/<victim-repo>"` → used by every handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) to look up and mutate the real `Stack`/`Repository`.

This lets the request "authenticate" as the unsecured org while actually writing state (commit statuses, pull-request status, triggering `GithubSyncJob`, etc.) for a completely unrelated, secured organization's repository — an unprivileged cross-organization write, exactly the class of binding break called out in the rules ("an organization that authenticated versus the repository that is written").

### Impact Explanation
This is a cross-repository/cross-organization write achievable by an unauthenticated network attacker (anyone who can POST to the public `/webhooks` endpoint), as long as any one org on the multi-tenant Shipit instance is configured without a webhook secret (a state the shipped example configs actively encourage via `webhook_secret: # nil`). The attacker can forge `push`/`status`/`pull_request`/`check_suite` events against a victim org's stacks — creating fake commit statuses, marking commits deployable, or queuing sync/refresh jobs for repositories they have no GitHub-side relationship with, all without possessing a webhook secret, API token, or repository access for the victim org.

### Likelihood Explanation
Medium-to-High wherever multi-org support is used (an explicit, documented feature) and at least one configured org has no `webhook_secret` (also a documented/shipped default). No credentials are required beyond knowledge that Shipit is multi-tenant and that one org lacks a secret — discoverable by simply sending an unsigned webhook and observing whether it's accepted.

### Recommendation
Do not select the verification org from unauthenticated payload fields that differ from the fields event handlers use to determine the write target. Either (a) verify the signature against every configured org's secret and require the winning org to match `repository.full_name`'s owner, or (b) after selecting the org from `repository_owner`, require handlers to reject/branch away from any event whose `repository.full_name` owner does not match the org that was used to authenticate the request, and never treat "no configured webhook_secret" as an automatic pass when other orgs on the instance are secured.

### Proof of Concept
1. Configure Shipit multi-org with `OrgA` (no `webhook_secret`) and `OrgB` (has `webhook_secret`, hosts a real tracked stack `OrgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` computes `repository_owner` = `"OrgA"`, loads `OrgA`'s `GitHubApp` (no secret) → `verify_webhook_signature` returns `true` unconditionally, request passes.
4. `create` dispatches to `Handlers::PushHandler`, which resolves `repository_name` from `full_name` = `"OrgB/victim-repo"` and enqueues `GithubSyncJob` (or updates commit state) for the victim's real stack — an unauthenticated cross-org write.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
