### Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login` field while the actual repository/commit acted upon is resolved from an unrelated payload field, allowing unauthenticated forgery of GitHub events - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate against by reading `repository.owner.login` (or `organization.login`) directly out of the untrusted, unauthenticated JSON body, *before* any HMAC has been checked. The HMAC is computed only over the raw body using whichever org's secret was selected this way. Every downstream `Handler` then resolves the actual repository/commit to mutate using a *different* field of the same body (`repository.full_name` in `Handler#repository_name`, or a bare `sha` lookup with no repository scope at all in `StatusHandler#process`). Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured, an attacker who simply names an org that has no secret configured breaks the binding between "the org whose signature was checked" and "the repository/commit that gets written."

### Finding Description
The verification flow is: [1](#0-0) 

`repository_owner` is taken straight from the POST body: [2](#0-1) 

`Shipit.github(organization:)` looks up a per-org config and instantiates `GitHubApp`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` bypasses verification entirely if that org's `webhook_secret` is blank — which is an explicitly documented/optional setting (`webhook_secret: # nil` in the shipped config examples): [4](#0-3) [5](#0-4) 

Meanwhile, every handler determines the entity it will mutate from a *different* payload field, `repository.full_name`, which is never checked against `repository_owner`: [6](#0-5) 

`StatusHandler` is worse still — it doesn't scope by repository at all, matching commits globally by SHA across every stack in the instance: [7](#0-6) 

`PushHandler` similarly acts on stacks matched only by `branch`/`repository.full_name`, independent of `repository_owner`: [8](#0-7) 

**Broken binding (equality that must hold but doesn't):**
`organization whose secret authenticated the request == organization that owns the repository/commit being written`.

In a multi-org deployment (the engine explicitly supports this, see `Shipit.github_organizations` / `TOP_LEVEL_GH_KEYS` in `lib/shipit.rb:63,190-200`), each org has an independently optional `webhook_secret`. An unauthenticated attacker who simply knows (or guesses) the name of any org onboarded to the instance that has no `webhook_secret` configured can:
1. POST directly to the public `/github/webhooks` endpoint (this route is unauthenticated by design — it exists to receive GitHub's callbacks).
2. Set `repository.owner.login` (or `organization.login`) in the JSON body to that secret-less org name — `verify_signature` calls `verify_webhook_signature` which returns `true` unconditionally since `webhook_secret` is blank, regardless of the `X-Hub-Signature` header content.
3. Set `repository.full_name` (or, for `status` events, just `sha`) to reference *any other repository/commit tracked by the instance*, entirely unrelated to the org used in step 2.
4. The handler (`PushHandler`, `StatusHandler`, `check_suite` handlers, `pull_request` handlers, etc.) processes the event against the victim repository/commit as if it were a legitimate signed GitHub event.

### Impact Explanation
This is an authentication bypass on the webhook ingestion path that allows cross-repository/cross-organization writes without any credential: an attacker can forge `status` events to mark arbitrary commits (in any repo tracked by the instance) as `success`, which downstream deploy/merge gating logic in Shipit relies on, enabling an unauthorized deploy or merge decision; forge `push` events to trigger `GithubSyncJob` against arbitrary tracked stacks; or manipulate PR-driven review-stack provisioning/archival via the `pull_request` handlers. This matches the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability depends only on one organization in the Shipit deployment having no `webhook_secret` set — a state the shipped configuration templates (`config/secrets.development.shopify.yml`, `config/secrets.development.example.yml`, `template.rb`) explicitly present as a normal, supported value (`webhook_secret: # nil`), and the setup docs describe it as optional ("If you've set a webhook secret during the App creating, you should copy it here" — implying it may not be set). No attacker credentials, GitHub App keys, or Shipit sessions are required; the webhook endpoint is intentionally exposed publicly.

### Recommendation
Do not derive the trust-establishing organization from the same untrusted payload that is later used to select the repository/commit to act on. Concretely: verify the signature against the specific `Repository`/`Stack`'s own configured secret resolved from a value that is independently authorized (e.g., matched only after confirming `repository.full_name` belongs to the org used for verification), and make `verify_webhook_signature` fail closed (reject) when `webhook_secret` is not configured rather than returning `true`. Additionally, scope `StatusHandler#process` (and any handler using bare SHA lookups) to the specific repository derived from the verified payload rather than a global `Commit.where(sha:)` search.

### Proof of Concept
Assume a multi-org Shipit deployment with orgs `attacker-org` (no `webhook_secret` configured) and `victim-org` (tracked stacks/commits exist).

```
POST /github/webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "sha": "<victim commit sha tracked by Shipit>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "http://attacker.example",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```

- `WebhooksController#repository_owner` → `"attacker-org"`.
- `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)` → `true` (webhook_secret blank per `lib/shipit/github_app.rb:76-77`), regardless of the bogus `X-Hub-Signature`.
- `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a forged `success` status on the victim's commit, with no verification tying `attacker-org` to that commit's actual repository.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
