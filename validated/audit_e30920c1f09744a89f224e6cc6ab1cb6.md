### Title
Cross-organization commit-status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub `status` webhook against the `webhook_secret` belonging to the organization named in the payload's `repository.owner.login` field. [1](#0-0)  That authentication only proves the payload was sent by *that* organization's GitHub App installation. However, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that the commit being updated actually belongs to a stack/repository owned by the authenticated organization — it performs a global, unscoped lookup by SHA across the entire database. [2](#0-1) 

### Finding Description
The base `Handler` class defines a `stacks` helper that properly scopes lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks`. [3](#0-2)  `PushHandler` and `CheckSuiteHandler` both correctly use this scoped `stacks` relation before acting on any data. [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores this scoping entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This is the same class of bug as the referenced report: a value from the verified payload (`sha`) is used to select the record to act on, but the write is applied without confining it to the record set actually bound by the signature verification (the authenticated organization's own repository). The "offset" that was verified (the organization/repository named in `repository.owner.login`) is not the "offset" that gets written to (any `Commit` row anywhere in the Shipit instance whose `sha` column matches).

Since a git commit SHA is a hash of the commit's content (tree, parents, author, message, timestamps), it is entirely feasible for an attacker who controls a repository in Organization A (with a legitimate, correctly configured GitHub App/Shipit integration) to import/reference a commit object that is byte-for-byte identical to a real commit tracked by an unrelated Organization B's stack (e.g. by fetching a public commit from Organization B's repository into their own repository, or by reproducing an identical commit locally). The attacker then creates a GitHub Status on that SHA within their own Organization A repository through the normal GitHub API. GitHub delivers a fully legitimate, correctly signed `status` webhook for that event, signed with Organization A's `webhook_secret`.

`WebhooksController#verify_signature` legitimately verifies this signature, because it truly is a webhook from Organization A. [1](#0-0)  But `StatusHandler#process` then applies the attacker-chosen `state`/`context`/`description` to **every** `Commit` row across the whole Shipit deployment matching that SHA — including the row belonging to Organization B's stack — even though nothing about Organization B was ever authenticated by this request.

### Impact Explanation
`Commit#create_status_from_github!` persists the forged status and can trigger consequential state changes: it calls `enable_ci_on_stack`, and (via `Commit#add_status`) schedules continuous delivery and re-evaluates merge queue eligibility whenever the new status is `pending` or `success`. [6](#0-5) [7](#0-6)  A forged "success" status for a required CI context on a targeted commit in an unrelated organization's stack can satisfy `StatusChecker`-based CI requirements used by both `Deploy` (`Commit#deployable?`) and `MergeRequest#all_status_checks_passed?`/`reject_unless_mergeable!`, resulting in an unauthorized deploy (via continuous deployment) or an unauthorized merge of a pull request in a repository the attacker never had access to. This satisfies the "unauthorized deploy, rollback or merge" Critical-impact criterion.

### Likelihood Explanation
Exploitation only requires: (1) the attacker have push/status-creation privileges on a repository in *any* organization onboarded to the same Shipit instance (an "unprivileged" cross-tenant position relative to the victim organization), and (2) the ability to produce/reference a commit object with an identical SHA to a real commit tracked in the victim's stack, which is achievable for any commit whose full contents (tree, parents, author/committer identities and timestamps, message) are known/public — e.g. simply fetching the target commit object from a public GitHub repository into the attacker's own repository. No compromise of `webhook_secret`, API tokens, or GitHub credentials belonging to the victim organization is needed; the forged webhook is a genuinely GitHub-signed event from the attacker's own, legitimately configured organization.

### Recommendation
Scope `StatusHandler#process` (and any other handler performing DB lookups keyed only by attacker/GitHub-controlled fields like `sha`) to the `stacks` relation derived from the verified `repository.full_name`/owner, exactly as `PushHandler` and `CheckSuiteHandler` already do:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Repository`/`Stack` so that only commits belonging to the authenticated repository can be updated.

### Proof of Concept
1. Attacker onboards/owns repository `attacker-org/repo` in Shipit with a properly configured GitHub App (Organization A), giving them a legitimately signed webhook channel.
2. Attacker identifies a target commit `C` (SHA `deadbeef...`) in `victim-org/repo`'s Shipit-tracked branch that is missing a required CI status (e.g., `ci/travis`), blocking deploy/merge.
3. Attacker fetches/reconstructs an identical commit object with the same SHA `deadbeef...` into `attacker-org/repo` (e.g. via `git fetch` of the public victim commit, or reproducing an equivalent commit locally with matching metadata).
4. Attacker calls the GitHub Statuses API on `attacker-org/repo` for SHA `deadbeef...` with `state: success`, `context: ci/travis`.
5. GitHub sends a `status` webhook to Shipit, signed with `attacker-org`'s `webhook_secret`; `WebhooksController#verify_signature` accepts it since it's a genuine webhook. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: 'deadbeef...')`, which matches and updates the `victim-org/repo` commit row, marking it `ci/travis: success`. [2](#0-1) 
7. If `victim-org`'s stack has continuous deployment enabled or an active merge queue, this forged status triggers an unauthorized deploy or merge.

**Note on verification limits:** I was unable to fully confirm (due to index/tool constraints on this session) whether `Commit` records enforce a unique index only on `(stack_id, sha)` versus a global unique constraint on `sha` alone — the schema/migration files (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, `test/dummy/db/schema.rb`) suggest per-stack scoping of the index (supporting that multiple stacks can hold rows with the same `sha`), but I could not read their full contents in this session to give a definitive line citation. This should be confirmed by a background engineer with full file access before finalizing severity.
