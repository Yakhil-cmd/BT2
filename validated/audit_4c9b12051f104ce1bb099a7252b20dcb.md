### Title
Unrestricted `ERC20Mintable.mint()` on Service Chain Allows Draining Parent-Chain Bridge Locked Balance — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/testing/sc_erc20/sc_token.sol`)

---

### Summary

In Kaia's service-chain bridge operating in `modeMintBurn=true` mode, the child-chain token (`ServiceChainToken`) inherits `ERC20Mintable`, which grants the deployer (and any address they add via `addMinter`) the ability to call `mint()` freely. Because `_requestERC20Transfer` only burns the tokens and emits a `RequestValueTransfer` event without verifying that the tokens were legitimately bridged in, an attacker with `MinterRole` can mint tokens on the child chain, trigger a bridge exit, and drain real tokens locked in the parent-chain bridge.

---

### Finding Description

`ServiceChainToken` inherits `ERC20Mintable`: [1](#0-0) 

`ERC20Mintable.mint()` is callable by any address holding `MinterRole`: [2](#0-1) 

`MinterRole` assigns the role to the deployer at construction and allows any existing minter to add more minters: [3](#0-2) 

On the child-chain bridge (`modeMintBurn=true`), `_requestERC20Transfer` simply burns whatever tokens the caller holds and emits `RequestValueTransfer` — no check that those tokens were legitimately received via `handleERC20Transfer`: [4](#0-3) 

On the parent-chain bridge (`modeMintBurn=false`), `handleERC20Transfer` responds to that event by transferring real locked tokens out: [5](#0-4) 

The bridge operator's off-chain relayer (`handleRequestValueTransferEvent`) faithfully relays every `RequestValueTransfer` event it observes, with no additional authenticity check: [6](#0-5) 

---

### Impact Explanation

The parent-chain bridge holds real ERC20 tokens deposited by legitimate users. An attacker with `MinterRole` on the child-chain token can:

1. Mint an arbitrary amount of child-chain tokens to themselves (no cost beyond gas).
2. Call `requestERC20Transfer` on the child-chain bridge; the bridge burns the minted tokens and emits `RequestValueTransfer(amount)`.
3. The bridge operator relays the event and calls `handleERC20Transfer` on the parent-chain bridge.
4. The parent-chain bridge transfers `amount` real tokens to the attacker.

This drains the parent-chain bridge's locked balance, causing all other users' deposits to become unrecoverable (stranded on the child chain with no corresponding parent-chain liquidity). The corrupted value is the parent-chain bridge's ERC20 token balance — a direct, unauthorized transfer of bridged assets.

---

### Likelihood Explanation

The `MinterRole` is granted to the deployer of `ServiceChainToken` at construction. Any existing minter can call `addMinter` to extend the role to additional addresses without owner approval. In a service-chain deployment where the token deployer is a different party from the bridge operator (a realistic multi-party setup), this is a semi-trusted but reachable trigger. The attack requires no special on-chain privileges beyond holding `MinterRole`, which is the default state for the token deployer.

---

### Recommendation

Restrict `mint()` so it can only be called by the bridge contract itself. The simplest fix is to remove `ERC20Mintable` inheritance from service-chain tokens and replace the public `mint()` with an internal function callable only from the bridge address (analogous to how `ERC20ServiceChain` already stores and checks `bridge`):

```solidity
function mint(address account, uint256 amount) external {
    require(msg.sender == bridge, "only bridge can mint");
    _mint(account, amount);
}
```

Alternatively, after deployment, the deployer should immediately call `renounceMinter()` and ensure only the bridge contract holds `MinterRole`.

---

### Proof of Concept

**Preconditions:** Parent-chain bridge has `modeMintBurn=false` and holds 1,000 tokens deposited by legitimate users. Child-chain bridge has `modeMintBurn=true`. Attacker is the deployer of `ServiceChainToken` (holds `MinterRole` by default).

1. **Attacker mints 1,000 child-chain tokens to themselves:**
   ```solidity
   // MinterRole.constructor() already gave deployer the role
   ServiceChainToken(childToken).mint(attacker, 1000e18);
   ``` [2](#0-1) 

2. **Attacker approves child-chain bridge and calls `requestERC20Transfer`:**
   ```solidity
   childToken.approve(childBridge, 1000e18);
   childBridge.requestERC20Transfer(childToken, attacker_on_parent, 1000e18, 0, "");
   ```
   Bridge burns the 1,000 minted tokens and emits `RequestValueTransfer`. [4](#0-3) 

3. **Bridge operator relays the event to the parent-chain bridge:**
   ```go
   bi.bridge.HandleERC20Transfer(auth, txHash, from, attacker_on_parent, parentToken, 1000e18, nonce, blockNum, nil)
   ``` [6](#0-5) 

4. **Parent-chain bridge transfers 1,000 real tokens to the attacker:**
   ```solidity
   IERC20(parentToken).safeTransfer(attacker_on_parent, 1000e18);
   ``` [7](#0-6) 

**Result:** Attacker receives 1,000 real parent-chain tokens. Legitimate users' 1,000 tokens are permanently stranded on the child chain with no corresponding parent-chain liquidity to back them.
