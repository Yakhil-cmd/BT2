### Title
Webhook signature verification authenticates the wrong org, letting an unprivileged attacker forge events for any other org's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the `Shipit::GitHubApp` used to check the HMAC signature based on `params.dig('repository','owner','login')`, but the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) key off `payload.dig('repository','full_name')`. Nothing ties these two fields together, so the "organization authenticated" and the "repository that is written" are two independently attacker-controlled JSON fields in the same forged POST body.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` resolves the GitHub App to verify against solely from `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit::GitHubApp#verify_webhook_signature` short-circuits to `true` when the org's `webhook_secret` is blank — a documented, supported configuration: [3](#0-2) [4](#0-3) 

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the **same raw JSON** to a handler, and every handler resolves the target `Stack`/`Repository`/`Commit` from a *different* field, `payload.dig('repository','full_name')` (or, for `status`/`check_suite`, purely by `sha`, with no repository scoping at all): [5](#0-4) [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to pick the signing org) and `repository.full_name` (used to pick the target repo) are just two independent keys in one attacker-supplied JSON body, an unprivileged attacker can:
1. Set `repository.owner.login` to any organization that is configured in `secrets.github` **without** a `webhook_secret` (an explicitly documented, valid setup — see `docs/setup.md` "If it's missing, the Shipit installation will be public unless you setup another authentication method"). For that org, `verify_webhook_signature` returns `true` regardless of the `X-Hub-Signature` header, so no secret of any kind is required.
2. Set `repository.full_name` (for `push`) or simply `sha` (for `status`, which is not even repo-scoped) to point at a completely different, victim organization's repository/commit.
3. POST the forged payload to `/webhooks` with any/no signature header.

The request is accepted (`head(:ok)` after processing) and the handler acts on the victim repository using the victim org's real `Stack`/`Commit` records, even though the signature only ever proved knowledge of "nothing" for the unrelated, secret-less org.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," which the rules class as a Critical/High analog. Concretely:
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: params.sha)` globally, with no repository/org scoping at all, and calls `commit.create_status_from_github!(params)`. An attacker who only controls a secret-less org's name can inject a fabricated `success` status (arbitrary `context`, `state`, `target_url`) onto a real commit belonging to a completely unrelated victim stack, which can satisfy status requirements gating deploys/merges — an unauthorized-deploy-adjacent primitive.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) triggers `stack.sync_github(expected_head_sha:)` for a victim stack chosen via a forged `repository.full_name`, causing the victim stack to sync against an attacker-chosen "expected" SHA — a cross-repository interaction the attacker never authenticated for.
- `CheckSuiteHandler` similarly lets an attacker schedule check-run refreshes on a victim stack's commits by supplying `check_suite.head_sha`/`head_branch` while authenticating only against an unrelated org.

This satisfies "cross-repository writes" / "unauthorized deploy" impact criteria without any GitHub App private key, `webhook_secret`, `ApiClient` token, session, or repository write access — only the ability to send an HTTP POST to the public `/webhooks` endpoint, which is unauthenticated by design.

### Likelihood Explanation
Likelihood is High whenever a Shipit deployment uses the documented multi-org configuration (`docs/setup.md` "Using Multiple Github Applications") and at least one configured organization has no `webhook_secret` set — an explicitly supported, non-default-forbidden state shown in the example configs (`config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`). No credentials, sessions, or prior access are required; the attacker only needs to know the name of the secret-less organization (which is often public, e.g., visible from the app's own GitHub App installation pages or simply guessable) and the target repository's `full_name`/commit SHA (public information for any public repo tracked by Shipit).

### Recommendation
- Verify the webhook signature using the organization actually referenced by every field the handlers will use (i.e., require `repository.full_name`'s owner segment to match the org whose secret was used, and reject payloads where they diverge).
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is unset for any org that shares a Shipit instance with other authenticated orgs; require an explicit signature for all orgs, or fail closed by default and only allow "open" mode when it is the sole configured org.
- Scope `StatusHandler`/`CheckSuiteHandler`/`PushHandler` lookups by the verified organization/repository, not by attacker-supplied `full_name`/`sha` alone, e.g., resolve `stacks`/`Commit` through the same `repository_owner` value that governed signature verification.

### Proof of Concept
1. Deploy Shipit with the multi-org config (`docs/setup.md`), where `secrets.github` contains:
   - `attacker-org`: no `webhook_secret` configured.
   - `victim-org`: normal config, owns a tracked `Stack` with commit `abc123` gating a deploy on CI status `ci/required`.
2. As an unauthenticated attacker, POST to `/webhooks`:
```json
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "abc123",
  "state": "success",
  "context": "ci/required",
  "description": "forged",
  "target_url": "http://evil"
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`; since `attacker-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally, bypassing the check entirely.
4. `StatusHandler` runs `Commit.where(sha: 'abc123')` — matching the victim's real commit — and calls `create_status_from_github!`, writing a forged `success` status for `ci/required` on the victim stack's commit, without ever touching `victim-org`'s secret, token, or session.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
