### Title
Webhook signing organization is not bound to the repository the payload updates, allowing cross-repository status/sync forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to HMAC-verify a webhook against using `repository_owner`, a value taken straight from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature check passes, the same raw body is handed to event handlers, which resolve the actual `Stack`/`Repository` to mutate using a *different* field of that same body: `repository.full_name` (`Handler#repository_name`). Because these two fields are never checked against each other, a request signed with the webhook secret of one configured GitHub organization can be crafted to act on a repository belonging to a different organization on the same Shipit instance.

### Finding Description
The controller picks the verification key from attacker-controlled JSON before the signature is checked: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` then HMACs the raw body against the `webhook_secret` belonging to whatever organization `repository_owner` names: [3](#0-2) 

The event is dispatched with the same fully attacker-supplied `params` object once verification passes: [4](#0-3) 

But the base `Handler` class resolves the target `Stack` using a **different** field from the same JSON body — `repository.full_name` — not `repository.owner.login`: [5](#0-4) [6](#0-5) 

Shipit explicitly supports hosting multiple GitHub organizations, each with its own App and `webhook_secret`, in `config/secrets.yml`: [7](#0-6) 

Because `repository.owner.login` (used for signature key selection) and `repository.full_name` (used for target-repository resolution) are independent JSON fields with no cross-check, an attacker who legitimately controls (or has compromised) the webhook secret for **Org A** hosted on the instance can craft a body where `repository.owner.login = "OrgA"` (so the correct, known secret validates the HMAC) but `repository.full_name = "OrgB/victim-repo"` (a different tenant's repository). The equality that should hold — *the organization whose secret authenticated the request* == *the repository the handlers act on* — is broken.

Concrete handler impact once this forged, "verified" payload reaches `Shipit::Webhooks.for_event`:
- `PushHandler` will force a resync of the victim stack to an attacker-chosen `after` SHA: `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [8](#0-7) 
- `StatusHandler` will write arbitrary CI/commit statuses (`state`, `context`, `description`, `target_url`) onto victim commits: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [9](#0-8) 

Since Shipit uses commit statuses/CI state as a deploy-safety gate, forging green statuses on a victim's commits from a different, self-controlled organization's webhook credentials can allow bypassing deployability checks for repositories the attacker does not otherwise control.

### Impact Explanation
This crosses the "organization authenticated vs repository written" trust boundary explicitly called out as in-scope: an attacker who is a legitimate, unprivileged party for **their own** configured organization/App on the same Shipit instance can inject events (fake CI statuses, forced sync to an attacker chosen commit) into a **different** organization's repositories/stacks without ever needing that victim organization's webhook secret, GitHub credentials, or Shipit session. Forged commit statuses that feed deploy-safety checks can facilitate an unauthorized deploy of an attacker-influenced commit, which maps to the "unauthorized deploy" Critical/High impact category.

### Likelihood Explanation
Requires the instance to be configured for multiple GitHub organizations (documented, supported multi-tenant configuration) and requires the attacker to hold a valid webhook secret for at least one org on that instance (e.g., their own legitimately-installed org). No GitHub write access, Shipit session, or API token is needed — only knowledge of one org's `webhook_secret`, which is not a privileged Shipit credential and is routinely known to any org admin who installed the shared Shipit app.

### Recommendation
After signature verification succeeds, assert that the `repository.owner.login` used to select the verifying GitHub App equals the owner segment of `repository.full_name` (and of `organization.login`, if present) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, derive the target repository from the same authenticated organization context used for signature verification rather than re-parsing `full_name` independently in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit for two orgs, `OrgA` and `OrgB`, each with its own `webhook_secret`, per the documented multi-org setup [7](#0-6) ; attacker controls `OrgA`'s webhook secret.
2. Attacker crafts a `status` (or `push`) event body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/tests"
}
```
3. Attacker signs the raw body with `OrgA`'s webhook secret and sends `X-Hub-Signature: sha1=<hmac>` to `POST /github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and validates successfully against the attacker-known `OrgA` secret [1](#0-0) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — the victim commit under `OrgB/victim-repo` — and writes the forged `success` status onto it [9](#0-8) , with no check that the commit's repository owner matches `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
