## Title
A malicious secondary-trigger AA can permanently block a primary AA's payout/cancel logic by always bouncing - (File: aa_composer.js)

### Summary
In `aa_composer.js`, when an Autonomous Agent (AA) sends a payment to another address as part of its response, and that address is itself an AA, `handleSecondaryTriggers()` is invoked to fire a secondary trigger on the recipient AA [1](#0-0) . If that secondary AA's evaluation bounces, the *entire* primary AA response is reverted via `revert()`, which rolls back all balance/state changes made by the primary AA and instead sends the primary trigger's own bounce response [2](#0-1) [3](#0-2) . This mirrors the reported Stream.sol issue: a payment recipient (here, a recipient AA the payer AA sends funds to) can unconditionally control whether the payer AA's operation (e.g. a stream cancellation, escrow settlement, or any AA that must pay a counterparty AA as part of finalizing an action) ever succeeds, by simply always bouncing.

### Finding Description
When a primary AA response includes a payment output whose destination address is a deployed AA, `sendUnit()` calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)` after saving the primary AA's response unit [4](#0-3) . For each such output address that is an AA, `handleTrigger()` is invoked recursively as a secondary trigger [5](#0-4) .

If the secondary AA's own logic decides to bounce (e.g. `bounce("...")` in its oscript, or any validation failure), the `async.eachSeries` callback receives an error and the whole flow is unwound:
```
function (err) {
    if (err) {
        // revert
        if (bSecondary)
            return bounce(err);
        return revert({message: "one of secondary AAs bounced with error: ", callChain: {address, next: err}});
    }
    ...
}
``` [6](#0-5) 

`revert()` then rolls back to the savepoint taken before the primary AA's balance updates, clears the write batch, discards all state var changes made by the primary AA, and finally calls `bounce()` on the *primary* trigger — meaning the primary AA's intended action (state changes, any of its other outputs) is entirely undone and replaced with a plain bounce refund [3](#0-2) .

Because the recipient AA is an independent, permissionlessly deployable contract, its author fully controls whether it bounces on receipt of funds from a specific payer AA (e.g. based on `trigger.address`, `trigger.data`, or amount). This is analogous to the ERC-777 `tokensReceived()` hook in the original report: the "recipient" contract's callback (its AA trigger evaluation) has the power to force-fail the sender's transaction. Any ocore AA design that must pay out to a caller-supplied or counterparty AA address as part of completing a state transition (cancellation, settlement, closing a channel/escrow, releasing a stream, etc.) is vulnerable to having that transition permanently blocked.

### Impact Explanation
A payer AA (e.g. implementing a payment stream/vesting/escrow pattern where the recipient is an AA address) can be indefinitely prevented from completing a "cancel" or "settle" style operation if the recipient AA always bounces its secondary trigger. Each attempt by the payer to trigger cancellation:
1. Executes the payer AA's logic and computes state changes / a payment to the recipient AA.
2. Triggers the recipient AA as a secondary trigger.
3. The recipient AA deliberately bounces.
4. `revert()` undoes all of the payer AA's balance and state changes, and the primary trigger only receives back its bounce-fee-refund.

This lets a hostile/adversarial counterparty AA freeze funds inside the payer AA and prevent state finalization — matching the High severity impact class of "AA fund loss/freezing" and "node/protocol logic permanently unable to complete a legitimate operation," analogous to the original report's "payer can never cancel the stream."

### Likelihood Explanation
Any AA design pattern that pays to a peer/counterparty address without first checking whether that address is itself an AA (and without a pull-based alternative) is exposed. Because AAs are freely and permissionlessly deployable by anyone (any user can define and use an "asset issuer", "AA trigger sender", or "private-payment counterparty" AA as the recipient in this pattern), the attack requires no special privilege — only that the payer's payout in a cancel/settle branch goes to an address that the attacker controls as an AA that unconditionally bounces. This is a design-level trap in `handleSecondaryTriggers`/`revert` that any real-world ocore AA implementing streams, escrows, payment channels, or vesting to arbitrary/attacker-influenced AA addresses would need to specifically defend against.

### Recommendation
- Favor pull-based settlement in payer AAs: rather than pushing funds to a counterparty AA as part of a single atomic response (which can be reverted by the counterparty bouncing), record the payable amount in state and let the counterparty withdraw it in a separate, counterparty-initiated trigger.
- Where push payments to attacker-influenced destination AAs are unavoidable, make critical state changes (e.g. marking the stream cancelled) unconditionally durable regardless of whether the destination happens to be an AA that bounces, e.g. by not depending on secondary-trigger success for the primary AA's own accounting.
- Consider hardening `handleSecondaryTriggers`/`revert` semantics so a documented pattern exists for AA authors to explicitly opt out of atomic secondary-trigger dependency when sending payments to externally-controlled AA addresses.

### Proof of Concept
1. Deploy `RecipientAA` whose logic unconditionally calls `bounce('nope')` for every trigger it receives.
2. Deploy `StreamAA` that, on a `cancel` trigger from the payer, computes remaining balances and sends a payment output to `RecipientAA`'s address as part of settling the stream, then updates its state (`var['cancelled'] = true`).
3. Payer posts a unit triggering `StreamAA`'s cancel branch.
4. `sendUnit()` saves `StreamAA`'s response unit with the payment to `RecipientAA`, then `handleSecondaryTriggers()` fires a secondary trigger on `RecipientAA` [7](#0-6) .
5. `RecipientAA` bounces, causing `async.eachSeries`'s final callback to invoke `revert()` [6](#0-5) , which rolls back `StreamAA`'s state change (`cancelled` never gets set) and refunds only the bounce fee to the payer [3](#0-2) .
6. Repeating step 3 indefinitely never lets the payer cancel the stream, as long as `RecipientAA` keeps bouncing.
