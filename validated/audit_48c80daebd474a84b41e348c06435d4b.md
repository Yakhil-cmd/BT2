This confirms the multi-organization webhook secret architecture: `Shipit.github(organization: repository_owner)` resolves a distinct `webhook_secret` per organization via `github_app_config(organization)` [1](#0-0) , and each organization has its own independent secret in `secrets.github`.

### Title
Webhook signature verified against `repository.owner.login`, but event handlers dispatch on the unrelated `repository.full_name` field, allowing cross-organization/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based solely on `repository.owner.login` (falling back to `organization.login`), while the actual event handlers that mutate Shipit state key off the sibling field `repository.full_name` from the very same payload. Because these two fields are never cross-checked, a payload can be signed with the correct secret for organization A but declare a `full_name` belonging to a completely different repository/organization B, causing the event to be applied to B's stack.

### Finding Description
`repository_owner` is computed as:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 
and used to select the verifying app/secret:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 

`Shipit.github(organization:)` looks up a per-organization secret from `secrets.github` via `github_app_config(organization)` [1](#0-0) , meaning each configured organization has an independent `webhook_secret`.

However, the code path that determines *which repository/stack the event actually applies to* uses a different key from the same JSON body:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 
which is used by `PushHandler`, all `PullRequest::*Handler` classes, etc., to resolve `Repository.from_github_repo_name(...)` and dispatch state-changing actions (e.g. `stack.sync_github`, `review_stack.archive!`, `pull_request.update`) [5](#0-4) [6](#0-5) .

There is no assertion anywhere that `repository.owner.login` (the field bound by the signature-secret lookup) matches the owner portion of `repository.full_name` (the field the handlers actually trust). An attacker who legitimately controls a GitHub App installation for organization A (and therefore knows/can produce a valid signature using A's `webhook_secret`) can craft a payload where `repository.owner.login == "A"` (to pick A's secret for verification) but `repository.full_name == "victim-org/victim-repo"` (to target a stack belonging to a different, unrelated organization/repository configured on the same Shipit instance).

This is the direct structural analog of the reported `_maxSumOfPrices` bug: a constraint is validated on one representation of the data (`_maxSumOfPrices` / `repository.owner.login`) while the code that actually executes/spends the resource operates on a different, unchecked representation (`newRentals` sum after 10% bump / `repository.full_name`), breaking the intended binding between "what was authorized" and "what was acted upon."

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository that is written." Exploiting it allows an attacker who is a legitimate customer of a self-hosted, multi-organization Shipit instance (holding a real webhook secret for their own org) to forge `push`, `pull_request`, or `status`/`check_suite` events for a stack belonging to a different organization hosted on the same instance, triggering unauthorized `sync_github`, review-stack `archive!`/`unarchive!`, PR metadata updates, or status changes — i.e., an unauthorized action on another repository's stack that this instance operator did not consent to. This matches the "cross-repository writes / unauthorized deploy" high-severity impact class for this engine.

### Likelihood Explanation
Requires the Shipit deployment to be configured for multiple GitHub organizations with independent per-org `webhook_secret`s (the `github_app_config`/`TOP_LEVEL_GH_KEYS` multi-tenant schema in `lib/shipit.rb`). In that configuration, no additional privilege beyond controlling one legitimate organization's webhook secret is required — the attacker only needs to POST a crafted JSON body with mismatched `owner.login` vs `full_name` and a signature computed with their own known secret. No stolen credentials, GitHub App private key, or write access to the victim repository is needed.

### Recommendation
After successfully verifying the signature, re-derive and enforce that the organization implied by `repository.full_name` (or `organization.login`) matches the organization (`repository_owner`) whose secret was used to verify the signature, rejecting the request (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` first from a trusted, single source of truth (the organization the request was authenticated against) rather than trusting an independent `full_name` field from the same unauthenticated-until-verified payload.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s under `secrets.github` (multi-org schema).
2. Attacker, who legitimately owns the GitHub App installation for `attacker-org`, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw JSON body (as done in `Hook::DeliverySigner`/`verify_webhook_signature`) [7](#0-6) .
5. `WebhooksController#verify_signature` resolves `repository_owner` as `attacker-org`, fetches `attacker-org`'s app/secret, and successfully verifies the signature [3](#0-2) .
6. `PushHandler#process` resolves the target stacks via `repository.full_name = "victim-org/victim-repo"` [8](#0-7)  and triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stack [9](#0-8)  — an event forged by `attacker-org` is applied to `victim-org`'s repository/stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
