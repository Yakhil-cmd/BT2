### Title
Webhook signature is verified against the attacker-controlled `repository.owner.login`/`organization.login` org while all handlers act on the unrelated `repository.full_name` field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification by reading `repository.owner.login` (or `organization.login`) directly out of the *unverified* JSON body, then verifies the signature of the *whole* raw body against that org's secret. But every webhook handler (e.g. `PushHandler`) determines which `Stack`/`Repository` to mutate using a *different* field from the same body, `repository.full_name`, without ever checking that its owner matches the org that was used to select the verification secret. In a multi-org Shipit deployment (explicitly documented and supported), or in any deployment where one configured org has no `webhook_secret` set (also explicitly documented as "optional"), this breaks the trust binding `verification-org == repository actually written`.

### Finding Description
`verify_signature` derives the org used to pick the GitHub App/secret from attacker-supplied JSON before any cryptographic check occurs: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` verifies the raw body against that org's secret, but returns `true` unconditionally when no `webhook_secret` is configured for that org: [3](#0-2) 

After that check passes, the handler pipeline dispatches the entire unmodified `params` to registered handlers: [4](#0-3) 

Handlers such as `PushHandler` locate the target `Repository`/`Stack` using `repository.full_name`, a field completely independent from the `repository_owner`/`organization` value that was used to pick the verification secret: [5](#0-4) [6](#0-5) [7](#0-6) 

The binding that should hold is: `org used to authenticate signature == owner encoded in repository.full_name used by the handler`. Nothing in the controller or in `Repository.from_github_repo_name` enforces this. `Shipit.github(organization:)` config supports multiple, independently-secreted GitHub Apps for different orgs sharing the same `/webhooks` endpoint, as documented: [8](#0-7) 

and per-org `webhook_secret` is explicitly documented as optional: [9](#0-8) 

**Attack:** In a multi-org Shipit instance where at least one configured org (`OrgA`) has no `webhook_secret` set, an unauthenticated attacker POSTs to `/webhooks` with `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
`repository_owner` resolves to `"OrgA"`, so `Shipit.github(organization: "OrgA")` is used; since `OrgA` has no `webhook_secret`, `verify_webhook_signature` returns `true` with **no signature required at all**. The request proceeds to `PushHandler`, which looks up `Repository.from_github_repo_name("OrgB/victim-repo")` — a repository belonging to an entirely different, secret-protected org — and calls `stack.sync_github(expected_head_sha: params.after)`, forcing that victim stack to sync/deploy against an attacker-chosen commit SHA.

### Impact Explanation
This is a cross-organization / cross-repository write: an attacker with no credentials of any kind (no `webhook_secret`, no `ApiClient` token, no GitHub App key, no repository access) can force `GithubSyncJob`/deploy-triggering behavior for a `Stack` belonging to a completely unrelated, properly-secured GitHub organization, purely by supplying a mismatched `repository.owner.login` for a co-hosted org that lacks a secret. This maps to the "cross-repository writes" / "unauthorized deploy" Critical impact bucket, since continuous-deployment-enabled stacks will pick up and deploy the attacker-influenced `after` SHA.

### Likelihood Explanation
Requires only that the Shipit instance hosts more than one GitHub organization (an explicitly documented, supported configuration) and that at least one of those orgs has an unset `webhook_secret` (also explicitly documented as an acceptable/optional configuration). No membership, no repository access, and no secret knowledge is needed by the attacker — only knowledge (or guessing) of one configured org name lacking a secret and the full name of the target repo, both of which are often discoverable/public.

### Recommendation
- After verifying the webhook signature, enforce that the org used for verification actually owns the repository referenced in the payload (e.g., compare `repository_owner` against `payload.dig('repository','full_name').split('/').first`) before dispatching to handlers.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; either require a secret for every configured org or explicitly restrict such orgs from being used to authorize actions on repositories belonging to other orgs.
- Consider deriving the "authenticating org" strictly from `repository.full_name`'s owner rather than a possibly-divergent `repository.owner.login`/`organization.login` field.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `OrgA` (no `webhook_secret`) and `OrgB` (with `webhook_secret`, hosting a real `Stack` for `OrgB/victim-repo`), per the multi-org format in `docs/setup.md`.
2. As an anonymous attacker, POST to `/webhooks` with header `X-Github-Event: push` and no (or garbage) `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "0000000000000000000000000000000000dead",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, uses `OrgA`'s (secret-less) `GithubApp`, and `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb` line 77).
4. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "0000000000000000000000000000000000dead")`, affecting `OrgB`'s stack despite the request never being authenticated against `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
