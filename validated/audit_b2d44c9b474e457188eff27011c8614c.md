### Title
`OpenedHandler#provision?` creates review stacks for repositories with `review_stacks_enabled == false` when `provisioning_behavior == prevent_with_label` and the PR omits the label - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` uses Ruby's `&&`/`||` operator precedence such that `review_stacks_enabled` is only ANDed into the first disjunct (`allow_all?`), while the third disjunct (`prevent_with_label? && !has_label?`) is evaluated completely independently of `review_stacks_enabled`. Any repository configured with `provisioning_behavior: prevent_with_label`, regardless of `review_stacks_enabled`, will have review stacks created for any PR that simply doesn't carry the provisioning label — the default state of any newly opened PR.

### Finding Description
The binding the product intends is: `review_stacks_enabled == true` is required for **any** stack provisioning to occur, i.e. `provision? => true` should imply `repository.review_stacks_enabled == true` for all three provisioning-behavior branches.

The actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Due to Ruby precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is scoped only to the first term. The third term, which governs `prevent_with_label` repositories, never reads `review_stacks_enabled` at all.

Call path: `process` calls `respond_to_pull_request_opened?`, which calls `provision?` [2](#0-1) . If true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs `create!`, writing a new `ReviewStack` row with `branch: params.pull_request.head.ref` and `environment: "pr#{params.number}"` [3](#0-2) .

Attacker request: any GitHub user opens a pull request (no label) against a repository whose Shipit configuration is `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`. The `pull_request.opened` webhook payload reaches `OpenedHandler`; no signature/authorization check is affected here (this is purely a boolean-logic flaw downstream of signature verification, which is out of scope of this bug and assumed to pass or be otherwise addressed) — the divergence is strictly in `provision?`'s logic, not in the webhook auth layer.

`Repository#provisioning_behavior` and `review_stacks_enabled` are independent DB columns/enum with no validation coupling them [4](#0-3) , so this configuration state (`review_stacks_enabled: false` + `provisioning_behavior: prevent_with_label`) is fully reachable/valid in the schema — it is not blocked by any model validation.

### Impact Explanation
For any repository administrator who sets `provisioning_behavior` to `prevent_with_label` (a legitimate, documented configuration intended to let PR authors opt OUT of stack creation via a label) while leaving/setting `review_stacks_enabled: false` (intending to disable review stacks entirely), any external PR author gets an unauthorized `ReviewStack` record created with attacker-controlled `branch` (the PR's head ref) and deterministic `environment`. This stack later feeds provisioning/deploy machinery (environment/checkout used by `Command#start`), so an attacker-controlled branch enters the deploy pipeline for a repository whose operator explicitly disabled review stacks. This is repeatable per PR/branch, and reproducible against any repository with that specific config combination (not a global bypass across all tenants, but a real per-repository authorization bypass of the `review_stacks_enabled` gate). This matches "a payload for one repository mutating [creating resources for] a stack that did not authenticate/enable that behavior."

### Likelihood Explanation
Preconditions: the target repository must be configured with `review_stacks_enabled == false` AND `provisioning_behavior == prevent_with_label`. This is a plausible, non-adversarial admin misconfiguration (e.g., an operator disables review stacks broadly but leaves a stale `prevent_with_label` setting, or considers `review_stacks_enabled: false` sufficient to disable review stacks under any `provisioning_behavior`). No secrets, tokens, or privileged roles are needed by the attacker — opening a PR without adding a label is the default action. This is highly feasible and trivially repeatable.

### Recommendation
Fix operator precedence/logic so `review_stacks_enabled` gates all three branches, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
minitest under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` (existing file, add case):
```ruby
test "provision? is false when review_stacks_enabled is false even if provisioning_behavior is prevent_with_label and PR has no label" do
  repository = stub(
    review_stacks_enabled: false,
    provisioning_behavior_allow_all?: false,
    provisioning_behavior_allow_with_label?: false,
    provisioning_behavior_prevent_with_label?: true
  )
  # build params with pull_request.labels == []
  handler = OpenedHandler.new(params_with_no_label)
  handler.stubs(:repository).returns(repository)

  assert_equal false, handler.send(:provision?)
  # Currently this fails: provision? returns true, and process/find_or_create! would create a Shipit::ReviewStack row
end
```
Assert on both sides of the binding: `repository.review_stacks_enabled == false` (given) should imply `handler.send(:provision?) == false` (expected) — the current implementation returns `true`, demonstrating the broken binding.
