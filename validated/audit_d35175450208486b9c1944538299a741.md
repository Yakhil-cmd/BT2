Found a genuine array-index-out-of-bounds analog in `wallet.js`'s private-payment handling, reachable by an unprivileged private-payment counterparty sending a crafted head private element.

### Title
Array index out of bounds on `output_index` in indivisible private-payment head element causes wallet/light-client crash - (File: wallet.js)

### Summary
`emitNewPrivatePaymentReceived` in `wallet.js` accesses `payload.outputs[objHeadPrivateElement.output_index]` using an attacker-supplied `output_index` from a private payment chain's head element, without validating that the index is within the bounds of the `outputs` array, mirroring the free5GC `GetSUCI` bug class of trusting an externally supplied index into a fixed/variable-length array.

### Finding Description
When a private-payment counterparty sends a chain of private elements via `handlePrivatePaymentChains` in `wallet.js`, each chain is passed to `network.handleOnlinePrivatePayment` for validation [1](#0-0) . Whether or not the deeper chain validation checks `output_index` bounds against `payload.outputs.length`, once a chain becomes locally "received" (via the `new_direct_private_chains`/similar event path leading into `emitNewPrivatePaymentReceived`), the code re-reads the raw untrusted `objHeadPrivateElement.output_index` value and indexes directly into `payload.outputs`: [2](#0-1) 
There is no bound check (`output_index < payload.outputs.length`) before this access, and `output_index` is read straight from `objHeadPrivateElement`, an object built from the JSON payload of a private-payment message controlled by the payer/counterparty device. If `output_index` is set to a value >= `payload.outputs.length` (or negative), `payload.outputs[output_index]` evaluates to `undefined`, and `.amount` on `undefined` throws a `TypeError`. Because `emitNewPrivatePaymentReceived` is invoked from inside asynchronous DB callbacks (`db.query(...).then(...)` style nested callbacks) rather than inside the `try/catch` wrapper used in `doHandle()` in `wallet.js` [3](#0-2) , this exception is not caught and results in an uncaught exception in the Node.js process, crashing the wallet/light client — directly analogous to the free5GC AMF panic from indexing past the end of a 5-element array with attacker-controlled index.

### Impact Explanation
An uncaught `TypeError` thrown inside async callbacks crashes the running Node.js process (wallet/light node), a denial-of-service condition. Any peer who is a "private-payment counterparty" (a normal capability, not requiring special privileges) can send a malformed indivisible private payment head element with an out-of-range `output_index` to a wallet, crashing it whenever the receiving logic attempts to compute the received amount. This matches "a network unable to confirm new units" / node crash impact classes accepted by the validation rules, since it denies wallet/light-client service to legitimate users.

### Likelihood Explanation
Likelihood is high: crafting a private payment chain with an indivisible `payload.denomination` and an `output_index` outside `[0, payload.outputs.length)` requires no special access — only the ability to act as a private-payment counterparty/payer, which is the normal use case of private asset transfers. If earlier validation in `network.handleOnlinePrivatePayment`/`privatePayment.validateAndSavePrivatePaymentChain` does not strictly bound-check `output_index` against `outputs.length` before it reaches `emitNewPrivatePaymentReceived`, this is trivially reachable.

### Recommendation
Add an explicit bounds check before indexing:
```js
var output = objHeadPrivateElement.output;
if (output && output.address && arrAddresses.indexOf(output.address) >= 0){
    var idx = objHeadPrivateElement.output_index;
    if (!ValidationUtils.isNonnegativeInteger(idx) || !payload.outputs[idx])
        return console.log('bad output_index in private payment', objHeadPrivateElement);
    assocAmountsByAsset[asset] += payload.outputs[idx].amount;
    assocMyReceivingAddresses[output.address] = true;
}
```
Additionally, ensure `output_index` bounds are validated as part of the mandatory private-payment-chain schema validation (in `private_payment.js`) before any code paths (including notification/UI paths like `emitNewPrivatePaymentReceived`) trust it, and wrap `emitNewPrivatePaymentReceived`/similar handlers in `try/catch` to prevent uncaught exceptions from crashing the process regardless of root-cause fixes.

### Proof of Concept
1. As a payer device, construct a private payment chain for an indivisible (denominated) asset where the head private element has:
   - `payload.denomination` set (making it "indivisible")
   - `payload.outputs` containing, e.g., 2 entries
   - `output_index` set to `99` (out of range) and `output.address` set to the victim's known address
2. Send this chain to the victim's wallet via the normal private-payment delivery path (`handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment`).
3. If the chain is accepted as "ifAccepted"/queued and later processed for "new_direct_private_chains"/notification, `emitNewPrivatePaymentReceived` executes `payload.outputs[99].amount`, which is `undefined.amount`, throwing a `TypeError` inside a `db.query` callback, crashing the wallet process because it is not guarded by the top-level `try/catch` used elsewhere in `wallet.js`.
