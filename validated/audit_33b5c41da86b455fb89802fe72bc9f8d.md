## Analysis

This maps to the rule's binding class: **"an organization that authenticated versus the repository that is written."**

### Finding

In `Shipit::WebhooksController`, signature verification is scoped by `repository_owner`, which selects the per-organization `GitHubApp` config (and thus the `webhook_secret` used for HMAC verification):

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Shipit supports multi-organization deployments where each org has its own `app_id`/`webhook_secret`, selected via `Shipit.github(organization:)` → `github_app_config(organization)`:

```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [2](#0-1) 

Once the signature check passes, the actual event handler resolves the target `Repository`/`Stack` **not** from `repository.owner.login`, but from `repository.full_name` — a separate, independent field of the same JSON payload:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler` uses this same `stacks` scope to trigger `sync_github` (which drives deploys/builds) directly from attacker-controlled payload data:

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

`PullRequest::OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`, etc. independently derive `repository` from `params.repository.full_name` as well, entirely decoupled from `repository.owner.login`:

```ruby
def repository
  @repository ||= Shipit::Repository.from_github_repo_name(params.repository.full_name) || Shipit::NullRepository.new
end
``` [5](#0-4) 

### The Binding Break

`verify_signature` authenticates **`repository.owner.login`** (which org's secret is used), while every handler acts on **`repository.full_name`** (which repository/stack is written to). These two fields live in the same attacker-suppliable JSON body and are never cross-checked for consistency. In a multi-org Shipit deployment (`Shipit.github_organizations`, documented in `config/secrets.development.shopify.yml` / `docs/setup.md`), an org administrator who legitimately controls a GitHub App on **Org A** (and therefore knows Org A's `webhook_secret`, since they configured the App and gave that secret to the Shipit operator) can send a webhook whose `repository.owner.login` = `"OrgA"` (so it authenticates against Org A's known secret) but whose `repository.full_name` = `"OrgB/victim-repo"` (a stack belonging to a different, unrelated organization Org B they do not administer). Because `verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner segment, and the `Handler` base class only consults `full_name`, the forged payload passes signature verification under Org A's secret while driving `sync_github`/deploy-triggering logic for Org B's stack.

This is however only exploitable in **multi-tenant Shipit configurations** where distinct organizations have independently-known webhook secrets configured on the same Shipit instance — the rules require an unprivileged-attacker analog, and here the "attacker" must at minimum be an administrator of *some* org onboarded to the same Shipit instance, not a fully anonymous third party. That is a privileged party relative to Shipit as a whole, but unprivileged/unauthorized with respect to the victim organization's repositories — consistent with the DYAD analog's "authenticated vs. written" mismatch (Kerosene Manager licensing one set of vaults while another function actually queries a different set).

### Title
Webhook signature verified against `repository.owner.login`-selected org secret while handlers act on independently-controlled `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`), but every `Webhooks::Handlers::Handler` subclass (including `PushHandler`, which triggers deploy-relevant `sync_github`, and pull-request handlers) resolves the affected `Stack`/`Repository` from the unrelated `repository.full_name` field of the same payload.

### Finding Description
The two fields — `repository.owner.login` (authentication scope) and `repository.full_name` (action scope) — are independent, attacker-suppliable strings inside the same JSON webhook body, and are never cross-validated. See `app/controllers/shipit/webhooks_controller.rb` lines 24-62 and `app/models/shipit/webhooks/handlers/handler.rb` lines 32-38.

### Impact Explanation
On a multi-organization Shipit deployment, a party controlling one onboarded organization's GitHub App secret can forge a webhook that authenticates as their own org while causing write/deploy-trigger side effects (`stack.sync_github`, review-stack creation/archival, label capture) against a different organization's stack — a cross-organization action driven by a mismatched trust boundary.

### Likelihood Explanation
Requires a multi-org Shipit configuration and requires the attacker to already be an admin of at least one onboarded organization (to know that org's `webhook_secret`); it is not exploitable by a fully anonymous, credential-less third party against a single-org deployment, which is the majority default setup.

### Recommendation
In `verify_signature` / `Handler`, validate that the organization segment of `repository.full_name` matches `repository.owner.login` (the value used to select the verifying secret) before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
Not independently runnable without a live multi-org Shipit instance and a legitimate second-org `webhook_secret`; the mismatch is demonstrated structurally by the cited code (verification keyed on `repository.owner.login`, action keyed on `repository.full_name`), analogous to the report's demonstration that the design contradiction "cannot be shown [by PoC] since it's broken functionality" in isolation but is provable by code inspection alone.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
