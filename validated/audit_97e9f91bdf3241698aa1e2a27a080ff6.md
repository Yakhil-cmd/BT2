### Title
AA can be permanently DoS'd/drained via unbounded dust-asset input consumption during send-all responses - (File: aa_composer.js)

### Summary
`AlignedLayerServiceManager`'s bug is that `batchersBalances[]` is a scarce resource tied to one specific address, can be drained by normal operation or malice, and there is no permissionless way to top it off, leaving posted tasks permanently unrespondable. The analogous root cause in ocore is in `aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` flow: an AA's ability to respond to a legitimate trigger depends on its own scarce `base` (bytes) balance being enough to cover the tx fee of the *entire* response unit, and an unprivileged third party can inflate that fee arbitrarily by spamming the AA's address with worthless dust outputs of a chosen asset, with no cap or dust-filter for non-base assets.

### Finding Description
When an AA composes a response unit, any non-base asset payment message is completed via `completePaymentPayload()`, which selects unspent outputs to consume by querying `readStableOutputs()`/`readUnstableOutputsSentByAAs()`: [1](#0-0) 
Note the WHERE clause: for the base asset there is an explicit dust filter `amount>=FULL_TRANSFER_INPUT_SIZE` (documented at the "prevent dust attack" comment) but for any *named* asset (`asset ? "="+conn.escape(asset) : ...`) there is **no minimum-amount filter at all**: [2](#0-1) 

If an AA's oscript logic ever issues a "send-all" output in a non-base asset (`{address: X}` with no `amount`, common in exchange/proxy/vault-style AAs), `completePaymentPayload()` must iterate and consume *every single* unspent output of that asset sitting at the AA's address until the `send_all_output` is resolved. An attacker can pre-fund the AA's address with thousands of dust outputs of an asset they control (assets are freely issuable, cheaply, by anyone) before triggering the AA.

Consuming N inputs inflates `objUnit`'s total size, and the *total* unit fee (`headers_commission + payload_commission`, plus `oversize_fee`) is computed only after all messages (including the bloated asset-payment message) are finalized: [3](#0-2) [4](#0-3) 
That fee must then be funded entirely from the AA's own `base` balance via the base payment message's `completePaymentPayload()` call (`target_amount`), because AAs are always the sole author/fee-payer of their own response units. If the AA lacks sufficient base balance to cover the inflated size, `completePaymentPayload` returns `'not enough funds for ... bytes'` and the whole trigger `bounce()`s: [5](#0-4) [6](#0-5) 

Because the dust outputs remain permanently unspent and un-filtered for assets, every future attempt by the AA to send-all in that asset re-triggers the same oversized/failing computation — there is no permissionless way for anyone (including the AA owner or trigger senders) to "top up" or bypass this once the dust set is large enough, mirroring the batcher-balance freeze in the original report: a resource controlled by one address (the AA's base balance) can be exhausted or made structurally insufficient by an unrelated party, with no recovery path.

### Impact Explanation
This allows an unprivileged party to freeze an AA's ability to ever pay out a given asset (fund freezing), and/or force the AA to burn real byte balance paying oversized fees to sweep attacker-supplied dust it never asked for (fund loss), purely by sending cheap self-issued asset dust to the AA's address before it needs to do a send-all in that asset. Contract/AA logic that promises users a full balance withdrawal (send-all pattern, common in exchange- or vault-style AAs) can thus be permanently bricked for that asset, which is a concrete AA fund loss/freezing outcome.

### Likelihood Explanation
Reaching this requires only posting ordinary payment messages with an asset (creatable by anyone, cheaply, since asset issuance is permissionless) to the target AA address before a normal trigger causes a send-all in that asset — this is fully reachable by an unprivileged unit poster/asset issuer with no special permissions, matching the report's "unprivileged, no-owner-involvement" theme. The main uncertainty is how commonly production AAs use unconditioned send-all-in-asset patterns and whether other constants (e.g. a cap on message/input counts enforced by `validation.js`) limit the maximum number of inputs before this becomes impactful; I was not able to confirm within available tool calls whether such a cap exists and at what value, so the exact dust-count threshold needed to make this practically damaging is unverified.

### Recommendation
Apply the same minimum-amount ("dust") filter used for the base asset to non-base assets in `readStableOutputs()`/`readUnstableOutputsSentByAAs()`, or cap the number of inputs consumed per payment message, so the response fee an AA must fund is bounded independent of how much dust an outside party deposits at its address.

### Proof of Concept
1. Deploy an AA whose response logic includes, in one of its branches, a payment message with a send-all output (`{ app: 'payment', payload: { asset: MY_ASSET, outputs: [{ address: '{trigger.address}' }] } }`).
2. As an attacker, issue a cheap/free asset and send a very large number (e.g. thousands) of 1-unit dust outputs of that asset to the AA's address, each in a separate cheap unit.
3. Send a normal trigger that causes the AA to execute the send-all branch for that asset.
4. Observe that `completePaymentPayload()` in `aa_composer.js` (readStableOutputs at lines 1140-1154) consumes all the dust inputs with no filtering, inflating `objUnit.payload_commission`/`headers_commission`, and the subsequent base-fee computation (lines 1382-1400) requires the AA to pay a correspondingly inflated `base` fee; if the AA's base balance can't cover it, the trigger bounces (`'not enough funds for ... bytes'`) as reproduced by the existing test pattern at `test/aa_composer.test.js:287-325`, permanently freezing that response path until the dust is somehow cleared — which no unprivileged party can do.
