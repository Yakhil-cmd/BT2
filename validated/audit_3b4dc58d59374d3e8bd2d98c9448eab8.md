### Title
Stack-scoped API tokens can read the deploy status of any stack via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a specific stack (`stack_id` set on the `ApiClient` record) can only resolve stacks from that same `stack_id` [1](#0-0) . `Shipit::Api::CCMenuController`, however, overrides the `stack` resolution method to look up **any** stack by id, completely bypassing the scoping enforced by the base class, while still only checking the coarse `read:stack` permission string [2](#0-1) .

### Finding Description
The binding that should hold is: *the stack(s) an `ApiClient` token authorizes == the stack(s) it can touch*. This binding is implemented once, correctly, in the base controller:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every other Api controller that needs a `stack` (e.g. `StacksController`) inherits this scoped resolution, so an `ApiClient` whose `stack_id` is set to stack A can never resolve stack B, no matter what `params[:stack_id]`/`params[:id]` says [3](#0-2) . This scoping is explicitly tested: `"an api client scoped to a stack will only see that one stack"` [4](#0-3) .

`CCMenuController`, though, defines its own private `stack` method that ignores `stacks` entirely and resolves against the full `Stack` table:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

The only authorization check performed before `#show` runs is `require_permission :read, :stack` [6](#0-5) , which only calls `ApiClient#check_permissions!`, a pure string-membership check against the client's `permissions` array — it never looks at `stack_id` [7](#0-6) .

The `ApiClient` model supports per-stack scoping (`belongs_to :stack, optional: true`) [8](#0-7) , and this is precisely the security property that stack-scoped tokens are supposed to rely on (as demonstrated by the base-controller enforcement and its test coverage). `CCMenuController` silently drops that enforcement for its own route.

### Impact Explanation
An `ApiClient` token that was deliberately restricted (via `stack_id`) to only operate against a single stack — and only for read access — can nonetheless be used to fetch the CI/deploy status (last deploy/rollback, success/failure, timestamps) of **any other stack** in the Shipit instance by hitting the CCMenu endpoint with an arbitrary `stack_id` param. This is an authorization boundary break: a credential explicitly scoped by its issuer/operator to a single repository/stack ends up leaking build/deploy state for every stack managed by the installation, i.e., an unauthorized cross-stack read of stack/deploy state, matching the High-severity class "unauthenticated (unauthorized) read of stack state, task streams, or deploy output" for a token that was never granted rights to that stack.

### Likelihood Explanation
Any holder of a stack-scoped API token — which by design is meant to carry only least-privilege, single-stack `read:stack` access — can trivially exploit this by making a GET request to the CCMenu endpoint with a different `stack_id`; no additional secrets, sessions, or elevated access are required beyond the token itself, which the attacker already legitimately possesses within its intended (narrower) scope.

### Recommendation
Have `CCMenuController#stack` reuse the base class's stack-scoping (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so tokens restricted to a specific `stack_id` cannot resolve or read state for any other stack.

### Proof of Concept
1. An operator creates (or the system creates, e.g. via `CCMenuUrlController`) an `ApiClient` with `stack_id` set to Stack A and `permissions: ['read:stack']`.
2. Using that client's Basic-Auth token, request:
   `GET /api/stacks/<Stack-B-id>/ccmenu` (per `config/routes.rb` CCMenu route)
3. `authenticate_api_client` succeeds (valid token) [9](#0-8) ; `require_permission :read, :stack` passes because the token has `read:stack` [7](#0-6) ; `stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `stack_id`-based restriction [5](#0-4) .
4. The response returns Stack B's latest deploy/rollback status XML — data the token was never authorized to access.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end
