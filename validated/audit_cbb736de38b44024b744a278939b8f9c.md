### Title
Stale Operator Votes Not Cleared on `deregisterOperator()` Allow Deregistered Operator's Vote to Execute Bridge Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from the `operators` mapping and `operatorList` but does not clear that operator's existing vote records from the internal `votes` mapping. A deregistered operator's vote count persists in `votes[VoteType.ValueTransfer][nonce].voteCounts`, and a remaining active operator's subsequent vote on the same nonce can push the count to the threshold, executing a bridge value transfer that was authorized in part by a revoked operator's vote.

---

### Finding Description

`deregisterOperator()` performs two cleanup steps: [1](#0-0) 

It deletes `operators[_operator]` and removes the address from `operatorList`. It does **not** touch:

- `votes[uint8(VoteType.ValueTransfer)][nonce].voted[_operator]`
- `votes[uint8(VoteType.ValueTransfer)][nonce].voteCounts[voteKey]`

The threshold check in `_voteCommon()` reads directly from `voteCounts`: [2](#0-1) 

Because the deregistered operator's count is never decremented, it silently contributes to the threshold comparison for every nonce on which that operator had already voted.

`_voteValueTransfer()` then closes the nonce and returns `true`: [3](#0-2) 

`handleKLAYTransfer()` proceeds to transfer KLAY to the recipient: [4](#0-3) 

The code itself acknowledges the incomplete cleanup in a comment but treats it as a known operator-management concern rather than fixing it: [5](#0-4) 

---

### Impact Explanation

A bridge KAIA/ERC20/ERC721 transfer can be executed on the destination chain using a vote cast by an operator whose authority has since been revoked. The effective quorum for that transfer is lower than the configured `operatorThresholds[ValueTransfer]` because one of the counted votes belongs to a deregistered (no longer trusted) operator. This constitutes an unauthorized transfer of bridged assets authorized by a revoked principal — matching the allowed impact category of bridge privilege escalation that changes asset ownership.

---

### Likelihood Explanation

The scenario is realistic during normal bridge operations:

- Operator rotation (replacing a key)
- Emergency deregistration of a compromised operator key
- Threshold increase combined with operator removal

In all these cases the owner deregisters an operator while value-transfer requests from the source chain may already be in flight and partially voted. The window between the operator's vote and the deregistration transaction is non-zero on any live chain.

---

### Recommendation

In `deregisterOperator()`, iterate over all open (non-closed) nonces and decrement or zero out the deregistered operator's vote contribution before removing them:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);

    // Revoke outstanding ValueTransfer votes cast by this operator
    // (iterate over known open nonces or use a per-operator vote index)
    for (uint64 n = lowerHandleNonce; n <= upperHandleNonce; n++) {
        if (closedValueTransferVotes[n]) continue;
        VotesData storage vd = votes[uint8(VoteType.ValueTransfer)][n];
        bytes32 key = vd.voted[_operator];
        if (key != bytes32(0)) {
            vd.voteCounts[key]--;
            delete vd.voted[_operator];
        }
    }

    delete operators[_operator];
    // ... remove from operatorList ...
}
```

Alternatively, add a guard in `_voteCommon()` that skips vote counts from addresses no longer in `operators`, though this requires iterating `voters[]` on every vote.

---

### Proof of Concept

1. Deploy `Bridge` (which inherits `BridgeOperator`). Owner registers operators A, B, C. Set `operatorThresholds[ValueTransfer] = 2`.
2. Operator A calls `handleKLAYTransfer(txHash, from, to, 1 ether, nonce=5, blockNum, "")`.  
   → `votes[0][5].voted[A] = voteKey`, `votes[0][5].voteCounts[voteKey] = 1`. Threshold not yet met; returns.
3. Owner calls `deregisterOperator(A)`.  
   → `operators[A]` deleted, A removed from `operatorList`.  
   → `votes[0][5].voteCounts[voteKey]` **remains 1**.
4. Operator B calls `handleKLAYTransfer(txHash, from, to, 1 ether, nonce=5, blockNum, "")`.  
   → `_voteCommon` increments `voteCounts[voteKey]` to **2 ≥ threshold(2)** → returns `true`.  
   → `closedValueTransferVotes[5] = true`.  
   → `_to.call.value(1 ether)("")` executes; 1 KAIA transferred to `to`.

The transfer was authorized with one active operator (B) plus one revoked operator (A), violating the invariant that only currently-registered operators' votes count toward the threshold. [6](#0-5) [7](#0-6)

    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
