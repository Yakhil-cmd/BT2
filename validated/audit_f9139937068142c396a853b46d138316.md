### Title
Webhook signature verification is bound to `repository.owner.login`, but the write action (stack sync) is bound to `repository.full_name` from the same unverified payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the untrusted request body, while the actual write action — locating and syncing a `Stack` — is driven by a *different* field from the same body, `repository.full_name`. These two fields are never cryptographically bound to each other, so an attacker can pick an organization whose webhook is unauthenticated to select the verification path, while pointing the actual write at a repository belonging to a different, properly-secured organization.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App config using: [1](#0-0) 
and [2](#0-1) 

`repository_owner` is read straight from the JSON body (`repository.owner.login`), and `Shipit.github(organization: repository_owner)` is used solely to fetch that organization's `webhook_secret` for signature verification: [3](#0-2) 

Critically, `GitHubApp#verify_webhook_signature` treats a blank/unset `webhook_secret` as automatic success: [4](#0-3) 

The setup docs explicitly describe `webhook_secret` as **optional** per configured GitHub App/organization: [5](#0-4) 

Once `verify_signature` passes (trivially, for any org without a configured secret), `WebhooksController#create` parses the *entire* raw body and dispatches it, unmodified, to event handlers: [6](#0-5) 

The handler base class then determines the actual repository/stack to act on using a *different* field, `repository.full_name`, not `repository.owner.login`: [7](#0-6) 

`PushHandler#process` uses that lookup to enumerate real `Stack` records and trigger a GitHub sync: [8](#0-7) 

Shipit natively supports multiple organizations each with independently configured (and independently optional) `webhook_secret`s, confirmed by `Shipit.github_organizations`/`github_app_config`: [9](#0-8) 
and by the multi-org fixture `secrets_double_github_app.yml`, in which every org's `webhook_secret` is `nil`: [10](#0-9) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization authenticated (repository.owner.login, used to pick which webhook_secret gates the request)` == `repository actually written to (repository.full_name, used by Handler#stacks/#repository_name to locate and mutate the target Stack)`.

Both fields come from the same attacker-controlled JSON body and are never cross-checked against each other. If the Shipit instance hosts at least one organization without a configured `webhook_secret` (an explicitly supported, documented configuration), an attacker can craft a payload where `repository.owner.login` names that unsecured organization (so `verify_webhook_signature` short-circuits to `true` regardless of the `X-Hub-Signature` header) while `repository.full_name` names a repository under a *different*, properly secured organization. The request sails through signature verification, then the handler acts on the real, secured repository's stacks using the untouched payload.

### Impact Explanation
This breaks the authentication boundary the webhook signature is meant to enforce: an unauthenticated attacker (no `ApiClient` token, no session, no GitHub App private key, no repository write access) can forge GitHub webhook events for a properly-secured repository as long as the multi-org Shipit deployment includes any organization with no `webhook_secret` set. Concretely this enables:
- Forged `push` events causing `PushHandler` to trigger `stack.sync_github` against the properly-secured stacks, and
- Forged `status` events (confirmed handled and persisted per `test/controllers/webhooks_controller_test.rb` ":state create a Status for the specific commit") that write CI/commit statuses used by Shipit's deploy-gating logic.

Forged commit statuses can satisfy required-status checks that gate deploys, which can result in an unauthorized deploy — matching the Critical impact bar (unauthorized deploy) defined for this analysis.

### Likelihood Explanation
Requires only: (1) the target Shipit instance to run in multi-organization mode with at least one configured organization lacking a `webhook_secret` (an explicitly documented, supported, "optional" setting), and (2) knowledge of that organization's login name (discoverable, e.g., via the Shipit UI/API which lists stacks/orgs) plus the target repository's `full_name`. No credentials, sessions, or GitHub write access are needed — the attacker only POSTs to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification to the same repository identity used for the write action: resolve the organization/app config from `repository.full_name`'s owner segment (or otherwise ensure `repository.owner.login` and `repository.full_name`'s owner component are identical) before selecting which secret verifies the request. Additionally, avoid treating a blank `webhook_secret` as automatic verification success in `GitHubApp#verify_webhook_signature`; require every configured organization to have a mandatory secret, or reject requests for organizations without one.

### Proof of Concept
1. Configure Shipit with two organizations: `OrgA` (no `webhook_secret`, per `secrets_double_github_app.yml`-style config) and `OrgB` (has a `webhook_secret` and a tracked stack `OrgB/target-repo`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `OrgA`'s `webhook_secret` is blank — the bogus signature is never actually checked.
4. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/target-repo")` and enqueues a sync/`GithubSyncJob` for `OrgB`'s real stack, despite the request never being authenticated against `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
