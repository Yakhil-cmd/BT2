Confirmed: the webhook handlers key off `repository.full_name` (via `Handler#repository_name` at `app/models/shipit/webhooks/handlers/handler.rb:36-38` and per-handler `params.repository.full_name` lookups) to select the `Stack`/`Repository` that gets mutated, while `WebhooksController#verify_signature` selects the *secret used to verify the signature* using a **different** field: `repository.owner.login` (or `organization.login`) via `repository_owner` at `app/controllers/shipit/webhooks_controller.rb:59-62`. These two fields are independent, attacker-controlled strings inside the same JSON body, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` — skipping HMAC comparison entirely — whenever that organization's `webhook_secret` is `nil` (a state the setup docs explicitly present as optional, e.g. `docs/setup.md:30`, `config/secrets.development.shopify.yml:9`).

### Title
Webhook signature is verified against `repository.owner.login`'s org secret while the mutated repository is selected via the independent `repository.full_name` field, enabling cross-organization unauthenticated writes when any configured org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which `webhook_secret`) to verify against using `repository_owner` = `params.dig('repository','owner','login')` (falling back to `organization.login`). The actual mutation performed by every webhook handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, and duplicated per-handler logic in `PushHandler`, `PullRequest::OpenedHandler`, etc.) is instead keyed on `params.dig('repository','full_name')`. Both fields live in the same attacker-supplied JSON body and are never cross-checked against each other.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49` performs:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
with `repository_owner` at line 61 reading `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

`lib/shipit/github_app.rb:76-83`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
If the organization resolved from `repository.owner.login` has no `webhook_secret` configured — an explicitly supported, documented configuration (`docs/setup.md:30`: "Webhook secret (optional)"; multi-org example in `docs/setup.md:181-209` and `test/dummy/config/secrets_double_github_app.yml` show `webhook_secret: # nil` per org) — signature verification is bypassed entirely, regardless of the `X-Hub-Signature` header's value.

Meanwhile, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`app/controllers/shipit/webhooks_controller.rb:12`) dispatches the *whole, unverified* payload to handlers that resolve the target `Stack`/`Repository` via `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`, and equivalently in `PushHandler#process`, `PullRequest::OpenedHandler#repository`, etc.), not via `repository.owner.login`.

Because the org-selection field (`repository.owner.login`) and the mutation-target field (`repository.full_name`) are independent strings inside the same unsigned/unverified body, an attacker can craft a payload where `repository.owner.login` names any organization configured **without** a `webhook_secret` (bypassing verification unconditionally) while `repository.full_name` names a repository belonging to a **different**, secured organization actually onboarded to Shipit. The handler resolves and mutates that secured org's `Stack` via `Repository.from_github_repo_name(repository_name)`.

### Impact Explanation
This breaks the trust binding "an organization that authenticated versus the repository that is written." It allows an unauthenticated attacker to trigger unauthorized writes against any Stack belonging to a properly-secured organization — e.g. enqueuing `GithubSyncJob` (`PushHandler#process`), creating `Status` records, creating/removing `Team`/`Membership` records, or archiving/unarchiving/creating `ReviewStack`s for pull requests — as long as any other organization configured on the same Shipit install has an optional/unset `webhook_secret`. This is an unauthorized deploy-adjacent write path (sync/status/PR-driven stack lifecycle mutation) achieved with zero credentials, matching the Critical impact bucket ("cross-repository writes" / "an unauthorized deploy, rollback").

### Likelihood Explanation
Likelihood is contingent on deployment configuration: it requires a multi-organization Shipit install (explicitly supported and documented, see `docs/setup.md:181-209`) where at least one configured organization has an unset `webhook_secret` (also explicitly documented as optional). Given the docs present `webhook_secret` as optional per-org and multi-org setups as a first-class feature, this is a realistic operator configuration, not a contrived edge case.

### Recommendation
Bind signature verification to the same identifier used for mutation: derive `repository_owner` and the org used for handler dispatch/mutation from the same verified field, and reject the request if `repository.owner.login` does not match the owner embedded in `repository.full_name`. Additionally, consider making `webhook_secret` mandatory (fail closed) rather than silently returning `true` in `GitHubApp#verify_webhook_signature` when it is blank, per-organization.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md`'s multi-org example: `SecuredOrg` (with a real `webhook_secret`) owning an onboarded repo `SecuredOrg/target-repo` with an active `Stack`, and `OpenOrg` (with `webhook_secret` left `nil`, as the docs permit).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and an arbitrary/garbage `X-Hub-Signature`, and a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OpenOrg" },
    "full_name": "SecuredOrg/target-repo"
  }
}
```
3. `verify_signature` computes `repository_owner = "OpenOrg"`, resolves `Shipit.github(organization: "OpenOrg")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` unconditionally — the bogus signature is accepted.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("SecuredOrg/target-repo")` and calls `stack.sync_github(expected_head_sha: params.after)`, mutating `SecuredOrg`'s stack despite never presenting a valid signature for `SecuredOrg`.
