### Title
Front-running of deterministic AA addresses via the `definition` app message squats `aa_addresses.address` and corrupts balance backfill (analog of "attacker squats a future-safe unique key before the honest party can register it") - (File: `storage.js`)

### Summary
The Optimism report describes an attacker who pre-computes a future "safe" unique identifier (the L2 output root) and registers it early via a globally-unique key (`getGameUUID`), so that when the honest value becomes final the legitimate submission is rejected because the UUID already exists. The equivalent primitive in `ocore` is the `app: 'definition'` message, which lets **any unprivileged unit author** register an autonomous-agent (AA) definition at `aa_addresses.address` — a value that is deterministic and often predictable in advance (e.g. child AAs produced by public factory-AA bytecode). Because `aa_addresses.address` is a `PRIMARY KEY` and insertion uses `INSERT IGNORE`, an attacker who predicts the address and posts it first "wins" the row, silently blocking the legitimate AA response from registering the address under its intended defining unit/mci.

### Finding Description
Any regular (non-AA) unit may include an `app: 'definition'` message. Validation only checks that `payload.address === chash(payload.definition)` and that the definition is well-formed AA code — there is no requirement that the poster be the AA that "should" have defined it: [1](#0-0) 

When such a message stabilizes, `insertAADefinitions()` performs an `INSERT IGNORE INTO aa_addresses (address, definition, unit, mci, base_aa, getters) ...` keyed by `address`: [2](#0-1) 

If a row for that `address` already exists (i.e., some other unit defined the identical AA definition first), the current call is dropped:
- for another *AA-defined* AA it just logs and returns (`storage.js:923-925`)
- for a definer whose `unit` differs from the one already recorded, it is unconditionally ignored: "ignoring repeated definition of AA … in another unit …" (`storage.js:932-936`).

Only when the *same* `unit` re-triggers the insert does the code take the "recalculate balances" (`bAlreadyPostedByUnconfirmedAA`) path that fixes up `aa_balances` for payments received between definition and stabilization: [3](#0-2) 

The comment explicitly documents the assumption that is broken here: "for AA-defined AAs, mci is the trigger mci whose triggers were already selected before this AA existed, so outputs on this mci can never trigger it and must be counted here" (`storage.js:947-948`). This is exactly the “safe/final” assumption in the Optimism report — the unique key (`address`) is supposed to only be registered together with the *correct* `mci`/`unit` pair belonging to the actual triggering event.

Many AA factories generate child AAs whose bytecode/address is fully deterministic from public data (see the tested pattern where a factory AA computes `$child_aa_address = chash160($child_aa)` from hard-coded template plus trigger data): [4](#0-3) 

An attacker observing the still-unstable trigger (via `storage.assocUnstableMessages`/mempool-equivalent) can reconstruct the identical `['autonomous agent', {...}]` array and submit their own plain unit containing an `app: 'definition'` message with the same `address`/`definition`, ahead of, or racing, the real AA response’s stabilization. Because `INSERT IGNORE` is first-writer-wins on `address`, whichever unit stabilizes/registers first is permanently recorded as `aa_addresses.unit`/`aa_addresses.mci`, and the legitimate factory-produced `definition` message for the same address is dropped forever (`prev_unit !== unit` branch, `storage.js:933-936`), never triggering the balance-recalculation/backfill path that is required for correctness.

### Impact Explanation
If the attacker's squatting unit stabilizes with an `mci` earlier than the real triggering mci, the `mci_cond` balance backfill logic in `insertAADefinitions` (`storage.js:944-961`) is invoked with a wrong `mci` boundary (or, since `bForAAsOnly`/`prev_unit!==unit` short-circuits return before backfill on the legitimate side at all, the balance backfill for legitimate pre-existing payments to that address is skipped entirely). This produces a state where the recorded defining `unit`/`mci` for a real, functioning AA no longer matches the trigger flow that actually created it, corrupting the invariant that `aa_balances` == sum of eligible `outputs` for the address (the very invariant asserted by `checkBalances()`): [5](#0-4) 

This can silently miscount an AA's funds (loss or duplication) or permanently prevent an intended child AA from being correctly initialized/funded as designed by its factory, i.e. **AA fund loss/inconsistency** and **node disagreement about which unit legitimately owns the AA address**, without the attacker needing any bond or stake — merely predicting deterministic AA bytecode and racing a unit into the DAG, mirroring the "squat the safe/future identifier before the honest party" pattern from the Optimism report.

### Likelihood Explanation
Exploitability requires an attacker to (a) predict a to-be-created AA's exact byte-for-byte definition (feasible whenever a factory AA's template + trigger inputs are public, which is common for AA factory patterns), and (b) get their own `definition`-carrying unit accepted/stabilized before or racing the legitimate AA-response unit. This is materially cheaper than the Optimism analog (no bond, no locked capital, low gas-equivalent cost — one ordinary unit), which raises likelihood relative to the original finding, though it still requires timing precision around DAG stabilization and only affects factory-style AA deployment flows (not all AAs).

### Recommendation
- Do not allow plain, non-AA units to squat `aa_addresses.address` for a definition that a specific AA response is expected to produce; e.g., bind the AA-defined-AA registration to the triggering context, or require the recalculation/backfill path (`bAlreadyPostedByUnconfirmedAA`) to run regardless of whether `prev_unit === unit`, keyed instead on “was this the first `definition` payload for this content,” and reconcile balances against the *originally intended* trigger mci rather than silently dropping the second registration.
- Alternatively, disallow externally (non-AA-response) submitted `definition` messages from address-squatting an AA address that is deterministically reachable from a currently-unstable AA trigger already known to the node (similar in spirit to rejecting a dispute-game UUID computed from unsafe/future data before it is finalized).

### Proof of Concept
1. Deploy `factory_aa`, a public AA whose `init` code deterministically builds `$child_aa` (fixed bytecode) and `$child_aa_address = chash160($child_aa)` from public/known trigger fields, as in: [6](#0-5) 
2. Watch the DAG for a trigger unit addressed to `factory_aa` while it is still unstable (available via `storage.assocUnstableMessages`/network propagation before stabilization).
3. Independently compute the identical `child_aa` array/`child_aa_address` off-chain (deterministic, no secret inputs) and immediately author and broadcast an ordinary (non-AA) unit containing `{ app: 'definition', payload: { address: child_aa_address, definition: child_aa } }`.
4. If the attacker's plain unit stabilizes (becomes part of `assocStableUnits`) before the factory AA's own `definition` response message is processed at `main_chain.js` stabilization time, `insertAADefinitions()`'s `INSERT IGNORE` (`storage.js:921`) registers the attacker's `unit`/`mci` as the official definer.
5. When the factory AA's own `definition` payload is later processed for the same `address`, it hits the `prev_unit !== unit` branch (`storage.js:932-936`) and is silently dropped — the balance backfill query for outputs sent to that address never runs with the correct trigger-mci semantics described in `storage.js:947-948`, producing balance-invariant violations later caught (or, worse, not caught) by `checkBalances()`.
