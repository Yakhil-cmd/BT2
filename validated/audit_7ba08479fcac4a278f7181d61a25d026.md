## Title
`actual_tps_fee` is excluded from the unit-signing hash, letting a bundler/co-signer inflate what a signer actually pays after signature - ([File: object_hash.js])

### Summary
`getUnitHashToSign()` builds the hash that authors' signatures cover by calling `getNakedUnit()`, which explicitly strips `headers_commission`, `payload_commission`, `oversize_fee`, `main_chain_index`, and — critically — `actual_tps_fee` before hashing. [1](#0-0) [2](#0-1) 

This is the same bug class as the reported VerifyingPaymaster issue: a cost-determining field is excluded from what is actually signed, so it can be changed after the signature is produced without invalidating that signature.

### Finding Description
The code contains an explicit acknowledgement of the risk for `tps_fee`/`actual_tps_fee`:

```
//	delete objNakedUnit.tps_fee; // cannot be calculated from unit's content and environment, users might pay more than required
delete objNakedUnit.actual_tps_fee;
``` [3](#0-2) 

`tps_fee` (the fee the author intends to pay/declare) is kept inside the naked unit and therefore is covered by the signature via `getUnitHashToSign` → `getNakedUnit`. `actual_tps_fee`, however — the value that is ultimately charged/used by validators/the network at write time — is deliberately deleted before hashing, exactly as `paymasterValidationGasLimit`/`postOpGasLimit` were excluded from `VerifyingPaymaster.getHash()` in the referenced report. Whoever finalizes/broadcasts the unit (e.g. a co-signer completing a multisig/shared-address unit, or any party in the signing pipeline who receives an already author-signed but not yet broadcast unit and can still fill in/alter `actual_tps_fee` before submission) can set `actual_tps_fee` to a value different from what the original signer intended, without breaking any authentifier, because the signed hash never included it.

The comment itself concedes the field "cannot be calculated from unit's content and environment", i.e. it is filled in dynamically at write/broadcast time rather than being a deterministic function of the already-signed content — the same characteristic that made the paymaster's per-op gas limits tamperable in the ERC-4337 report.

### Impact Explanation
`actual_tps_fee` represents real value paid from the address's balance for including the unit under the TPS-fee mechanism. Because it sits outside the signed payload, a party that has legitimate access to the signed-but-unbroadcast unit (e.g., the composer/proposer in a multi-authority shared address flow, or a device that relays the finished unit to the network on the signer's behalf) can inflate `actual_tps_fee` before submission. Since the signature does not attest to this number, the network/validators would still accept the unit as validly signed while the affected address is charged an amount the actual signer never agreed to — an unauthorized-spending outcome analogous to the paymaster being left liable for gas it didn't approve.

### Likelihood Explanation
Exploitation requires a party in the unit-finalization/broadcast path (not the original signer) with the ability to modify `actual_tps_fee` between signing and network submission — most plausibly a co-signer or relaying device in a multi-party signing flow (e.g., shared addresses, sign requests forwarded via `wallet.js`'s `"sign"` handler where the unsigned unit is passed around and later completed by another party) where trust between the involved principals is not already total. This is a narrower window than the paymaster scenario (which is exploitable by any `userOp` sender), so likelihood is lower, but the underlying root cause — a fee-relevant field deliberately excluded from the signed hash — is identical.

### Recommendation
Include `actual_tps_fee` (or bound it deterministically, e.g., cap it by a `max_tps_fee` value that *is* covered by the signature) in the hash computed by `getUnitHashToSign()`, so that any party who did not originally author/sign the unit cannot alter the amount charged without invalidating the existing authentifiers. If `actual_tps_fee` genuinely cannot be known at signing time (since it depends on network conditions at inclusion), the signed unit should instead carry a maximum acceptable `tps_fee` (already partially the intent of the kept `tps_fee` field) that the network is contractually bound not to exceed, with `actual_tps_fee` validated to never surpass it.

### Proof of Concept
Not independently reproducible from static analysis alone — verifying actual exploitability requires tracing how `actual_tps_fee` is populated end-to-end in `writer.js`, `network.js`, and `light.js`, and confirming which principal in the unit lifecycle (composer vs. broadcaster vs. co-signer) can set/modify it after signatures are collected but before the unit reaches consensus. This could not be fully confirmed within available search results; the analog is drawn primarily from the explicit code comment and the structural similarity of the exclusion in `getNakedUnit()`/`getUnitHashToSign()`.

function getUnitHashToSign(objUnit) {
	var objNakedUnit = getNakedUnit(objUnit);
	for (var i=0; i<objNakedUnit.authors.length; i++)
		delete objNakedUnit.authors[i].authentifiers;
	var sourceString = (typeof objUnit.version === 'undefined' || objUnit.version === constants.versionWithoutTimestamp) ? getSourceString(objNakedUnit) : getJsonSourceString(objNakedUnit);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
