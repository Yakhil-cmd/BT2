### Title
Webhook write-target repository is never bound to the signature-verifying organization, allowing cross-organization writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate `X-Hub-Signature` based on `repository_owner`, taken from `payload.dig('repository', 'owner', 'login')`. However every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used transitively by `PushHandler`, the `pull_request/*` handlers, `ReviewStackAdapter`, etc.) resolves the repository/stack to act on from a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the organization whose secret authenticated the request is not the organization whose repository is actually written to.

### Finding Description
This is the webhook analog of the `MFDBase.stake()` bug: staking (here, HMAC verification) is scoped to one actor (`repository.owner.login`), but the mutation (here, resolving `Repository.from_github_repo_name` / `stacks`) is performed against a second, independently-controlled field (`repository.full_name`) that the verified signature never covers as a bound value.

This engine explicitly supports multi-organization deployments where each organization has its own independent `webhook_secret` (see the multi-org secrets fixture): [7](#0-6) . `Shipit.github(organization:)` picks the App config purely by the organization name string, case-insensitively: [8](#0-7) .

Binding that should hold, but doesn't:
`organization_that_authenticated(repository.owner.login) == organization_that_is_written(repository.full_name.split('/').first)`

Before the report's analog reasoning: nothing enforces this equality anywhere between `verify_signature` and any `Handler`. An entity that legitimately controls a GitHub App installation for `OrgA` (and therefore can compute a valid `X-Hub-Signature` for `OrgA`'s `webhook_secret`, e.g. by directly posting to the public, unauthenticated `/webhooks` endpoint rather than relying on GitHub to deliver the event) can set `repository.owner.login = "OrgA"` (to pass `verify_signature`) while setting `repository.full_name = "OrgB/victim-repo"` (to select an arbitrary tracked repository/stack belonging to a different tenant organization `OrgB` on the same shared Shipit instance).

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. Depending on the event type dispatched, the attacker can:
- Force `PushHandler` to invoke `stack.sync_github(expected_head_sha:)` for a victim's stacks in `OrgB`, forging what Shipit believes is the new head SHA for that branch and triggering deploy/CI sequencing tied to a commit chosen by the attacker.
- Force `pull_request/*` handlers to archive/unarchive or provision/deprovision review stacks in `OrgB`, and update label/PR state used for merge queue and status gating in a repository the attacker doesn't own.

Because Shipit uses commit statuses, `merge` and CI-status webhooks to gate continuous deployment, corrupting these cross-tenant leads to unauthorized triggering of the deploy pipeline against another organization's repository — this maps to the "unauthorized deploy" / "cross-repository writes" Critical category defined in scope.

### Likelihood Explanation
Exploitability requires the attacker to control a validly-configured GitHub App installation for at least one organization tracked by the same shared Shipit instance (i.e., they can compute a correct HMAC for that org's `webhook_secret`), which is realistic in any multi-tenant self-hosted Shipit deployment (the engine ships explicit support and test fixtures for multiple organizations, each with independently held secrets: `test/dummy/config/secrets_double_github_app.yml`). The `/webhooks` endpoint is unauthenticated by design (it's meant to be called by GitHub) and accepts any JSON body as long as the HMAC matches, so no session, `ApiClient` token, or repository write access on the victim org is required — only knowledge of one tenant's own webhook secret, which every onboarded GitHub App owner necessarily has (it is configured by them or accessible in their GitHub App settings).

### Recommendation
In `Handler#repository_name` (and in `WebhooksController#verify_signature`), require that the organization used to select/verify the webhook secret and the organization prefix of `repository.full_name` refer to the same organization; reject (422) any payload where `repository.owner.login` does not case-insensitively match the owner segment of `repository.full_name`. Alternatively, resolve the target repository directly from `repository.owner.login` instead of trusting a second unrelated field, and use one canonical, verified identifier throughout signature verification and business logic.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
- `WebhooksController#verify_signature` looks up `Shipit.github(organization: "OrgA")`, computes the HMAC with `OrgA`'s `webhook_secret`, and — since the attacker knows `OrgA`'s secret — it matches, so the request passes verification (`app/controllers/shipit/webhooks_controller.rb:24-30`).
- `PushHandler#process` then computes `stacks` via `Handler#repository_name`, which reads `repository.full_name` = `"OrgB/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` for every matching, non-archived stack on the target branch belonging to `OrgB` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) — an organization the attacker never authenticated as.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
