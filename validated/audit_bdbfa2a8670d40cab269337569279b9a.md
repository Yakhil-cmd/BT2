### Title
Webhook signature verification silently returns `true` (no-op) when `webhook_secret` is unset, letting an unprivileged attacker forge GitHub webhooks for any organization that lacks a secret - ([File: lib/shipit/github_app.rb])

### Summary
The bug report's pattern — a security-relevant function that "only returns `true`" instead of performing its real check — is directly reproduced by `GitHubApp#verify_webhook_signature`. When an organization's `webhook_secret` is not configured, the method unconditionally returns `true`, completely skipping HMAC verification of the `X-Hub-Signature` header. Because the organization used to select which `GitHubApp`/secret verifies a given webhook is derived from the **unauthenticated payload itself**, an attacker can pick any org in the deployment that has no `webhook_secret` set and have their forged webhook accepted as genuine.

### Finding Description
`WebhooksController#verify_signature` picks the verifying app purely from attacker-controlled JSON, before any cryptographic check occurs: [1](#0-0) 

`repository_owner` is read straight out of `request.raw_post`: [2](#0-1) 

That value is fed to `Shipit.github(organization:)`, which resolves per-organization config for multi-org installs (an officially documented and shipped configuration pattern): [3](#0-2) [4](#0-3) 

The resulting `GitHubApp` instance's verification method is the root cause: [5](#0-4) 

`@webhook_secret` is simply `@config[:webhook_secret].presence`, so any organization block that omits `webhook_secret` (shown as the literal example default in the repo's own config templates) makes `verify_webhook_signature` a permanent `return true`: [6](#0-5) [7](#0-6) [8](#0-7) 

**The broken binding, as an equality:**
`organization asserted by the unverified JSON payload` (`repository_owner`, used only to pick which secret *would* verify the request) **==** `organization actually cryptographically authenticated by a verified HMAC signature`.

Before the attacker's request: for orgs with a secret configured, this equality holds because a valid HMAC over the exact payload is required. For any org without a secret configured, the equality is vacuous — `verified` is `true` regardless of what signature (or no signature at all) is supplied, so the "authenticated" side of the equality is never actually established.

After the attacker's request: the attacker submits an arbitrary JSON body whose `repository.owner.login` (or `organization.login`) names an org with no `webhook_secret`, and whose `repository.full_name` / event fields target any stack the Shipit instance tracks for that org. `verify_signature` calls `head(422)` only `unless verified`, and `verified` is `true`, so the request proceeds straight to `WebhooksController#create`, which dispatches the attacker-controlled payload to the real event handlers (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) exactly as if GitHub had sent it.

### Impact Explanation
This is an authentication bypass on the webhook ingestion boundary, not merely a hardening gap:
- Forged `status` events let an attacker mark any commit's CI status as `success`, defeating `require_ci`/deployable checks and clearing the way for an unauthorized deploy.
- Forged `push` events can enqueue `GithubSyncJob` against a stack's tracked branch.
- Forged `membership` events (`Shipit::Team`, `Shipit::Membership` models, seen exercised in `test/controllers/webhooks_controller_test.rb`) let an attacker add an arbitrary GitHub login to a `Shipit.github_teams`-linked team, which is exactly the check `Authentication#force_github_authentication` uses to authorize dashboard/API access — i.e., escalation into `Shipit.github_teams` authorization.

Both an "unauthorized deploy" and "escalation into `Shipit.github_teams` authorization" are explicitly in-scope Critical/High impacts per the validation rules.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: the vulnerable path only triggers for an organization whose `webhook_secret` is left unset. This is not a hypothetical corner case — it is the literal default shown in the shipped example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) and the multi-org documentation, where `webhook_secret:` is left blank per org unless explicitly filled in. Any operator who follows the documented multi-org setup and forgets (or has not yet obtained) a webhook secret for one organization exposes that organization's entire webhook surface, unauthenticated, to the public internet, since `WebhooksController` has no other authentication mechanism (`skip_before_action :verify_authenticity_token`, no session/token check).

### Recommendation
`verify_webhook_signature` must never treat "no secret configured" as "verified." Concretely:
- Require `webhook_secret` to be present for every configured organization at boot/config-validation time and refuse to serve (or explicitly disable) webhook processing for an org missing one, rather than silently accepting unsigned requests.
- Fail closed (`return false`) instead of `return true` when `webhook_secret` is blank, and make this a hard configuration error surfaced to operators (log/raise), not a silent bypass.
- Additionally, avoid selecting the verifying organization from unauthenticated payload fields before any cryptographic check — e.g., iterate/attempt verification against all configured secrets, or otherwise decouple "which secret to try" from attacker-supplied data.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config (`docs/setup.md`, "Using Multiple Github Applications") where `OrgA` has a configured `webhook_secret` and `OrgB` does not (matching the shipped example templates).
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: status` and a JSON body such as:
```json
{
  "sha": "<target-commit-sha-tracked-under-OrgB>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/some-repo" }
}
```
with any (or no) `X-Hub-Signature` header.
3. `verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`) without inspecting the supplied signature.
4. The request proceeds to `create`, and the forged `status` event is processed by `Shipit::Webhooks` handlers as if it came from GitHub, flipping the commit's CI status and enabling deploy eligibility that a real, unauthenticated actor should never be able to influence.

(Note: I was not able to inspect the full body of `app/models/shipit/webhooks/handlers/status_handler.rb`, `push_handler.rb`, and `membership_handler.rb` within this session's tool budget to quote their exact processing logic; their existence and general behavior are inferred from `test/controllers/webhooks_controller_test.rb` and file listings.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
