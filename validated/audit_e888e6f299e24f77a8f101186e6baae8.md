### Title
CCMenu controller bypasses stack-scoped ApiClient authorization, allowing cross-stack read of build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!` used by `BaseController` and every other API controller. This means a stack-scoped `ApiClient` token (one with `stack_id` set and `read:stack` permission) can be used to read the CCMenu XML (build/deploy status) of any stack, not just the one it was issued for.

### Finding Description
The intended binding is: for a scoped `ApiClient`, `current_api_client.stack_id == stack.id` for any resource resolved during the request. `BaseController` enforces this via [1](#0-0)  — `stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves through that relation.

`CCMenuController`, however, defines its own `stack` method that skips this scoping entirely: [2](#0-1)  It calls `Stack.from_param!` on the unscoped `Stack` class, so any stack ID/slug can be resolved regardless of the authenticated client's `stack_id`.

The controller only enforces `require_permission :read, :stack` at the class level: [3](#0-2) , which maps to `require_permission!` → `current_api_client.check_permissions!(operation, scope)` [4](#0-3) . That check only verifies the permission string `"read:stack"` is present in `ApiClient#permissions` [5](#0-4)  — it never compares `stack_id`. Authentication itself, `ApiClient.authenticate`, likewise only verifies the signed id and does not touch `stack_id` [6](#0-5) .

Attack: attacker holds/guesses a valid signed token for an `ApiClient` scoped to stack A with `read:stack` permission (a leaked or legitimately-issued CI token, e.g. used for CCMenu integration is a plausible real-world token to leak since it's designed to go in a public CCTray URL). They send `GET /ccmenu/<stack_B_id>?token=<tokenA>`. `authenticate_api_client` in `CCMenuController` succeeds and sets `@current_api_client` to the client scoped to stack A [7](#0-6) . `require_permission!` passes because the client has `read:stack`. `stack` then resolves stack B via unscoped `Stack.from_param!`, and `show` renders stack B's latest deploy/build status XML [8](#0-7) .

Every other API controller (`StacksController`, etc.) uses the inherited scoped `stack`/`stacks` and is not affected [9](#0-8) .

### Impact Explanation
An attacker with a stack-A-scoped `read:stack` token can enumerate/read build and deploy status for any stack on the Shipit instance (stack name/slug, latest deploy id, status, timestamps) — an unauthorized cross-tenant/cross-stack read of stack state. This is repeatable for every stack on the instance with a single valid, narrowly-scoped token, matching the "unauthenticated read of stack state" High-severity category since the token was never authorized for the target stack (the token's authorization boundary is stack A only). It does not grant write/deploy capability, but it defeats the entire purpose of per-stack API client scoping for this endpoint.

### Likelihood Explanation
Preconditions: possession of any valid `ApiClient` token that has `read:stack` permission and is scoped to some stack (stack_id set) — no special stack targeted, since the vulnerable code path accepts any signed token regardless of its `stack_id`. Such tokens are the intended credential for CCMenu/CCTray integrations, which are typically embedded in URLs pasted into CI dashboards or configuration and thus more prone to leakage than admin tokens. No GitHub/webhook secrets are needed. Given a leaked token, exploitation is a single unauthenticated GET request with a different `stack_id` — trivial and fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation like `BaseController` and `StacksController` do, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
removing the override entirely (inherit from `BaseController`) or explicitly reusing `stacks.from_param!`.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`, illustrative — not to be placed under `test/**` for production fix but to validate the finding):
```ruby
test "a token scoped to stack A cannot read ccmenu status of stack B" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine_production) # any other fixture stack

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: "scoped-to-a",
    stack_id: stack_a.id,
    permissions: %w[read:stack]
  )

  get :show, params: { stack_id: stack_b.to_param, token: scoped_client.authentication_token }

  # Binding under test: current_api_client.stack_id (stack_a.id) == stack.id (should be stack_b.id -> mismatch)
  assert_not_equal scoped_client.stack_id, stack_b.id
  assert_response :not_found # expected/fixed behavior
  # Currently (vulnerable): assert_response :ok and body contains stack_b's build status, proving the leak
end
```
This demonstrates that `current_api_client.stack_id` (A) and the resolved `stack.id` (B) diverge, yet the request still succeeds and discloses stack B's status.
