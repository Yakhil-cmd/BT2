### Title
Unauthenticated actor attribution via forged `X-Shipit-User` header - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController#identify_user` resolves `current_user` purely from the client-supplied `X-Shipit-User` request header, looking up any `User` by login with no verification that the login corresponds to the presenting `ApiClient`'s creator. Any request bearing a valid API token (or when `Shipit.disable_api_authentication` is enabled) can therefore attribute a deploy, rollback, lock, or merge action to an arbitrary existing user simply by setting that header.

### Finding Description
The broken binding is: `current_user` (used for authorization/attribution in downstream actions) should equal the identity actually authenticated by `current_api_client` (i.e., `current_api_client.creator`), but instead `current_user` == whatever `User` record matches the attacker-controlled `X-Shipit-User` header value.

Code path: `authenticate_api_client` (`app/controllers/shipit/api/base_controller.rb:48-61`) sets `@current_api_client` from Basic Auth token verification (or `UnlimitedApiClient` when `disable_api_authentication` is set) — this only proves possession of a token/permission, not any specific human identity. Separately, `current_user` (`base_controller.rb:65-67`) calls `identify_user` (`base_controller.rb:69-72`):
```ruby
def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```
This performs a case-insensitive lookup keyed solely on the header value, with zero cross-check against `current_api_client.creator` or any other proof of identity. `ApiClient` (`app/models/shipit/api_client.rb`) has no field or method relating `creator` to arbitrary request headers, and `check_permissions!` only validates scope/operation, not user identity. `DeploysController#create` (`app/controllers/shipit/api/deploys_controller.rb:19-27`) then calls `stack.trigger_deploy(commit, current_user, ...)`, passing this spoofed user directly as the deploy's triggering actor.

Attacker request: holding any API token scoped to `deploy:stack` for stack A (or when the deployment runs with `disable_api_authentication`), send:
```
POST /api/stacks/<A_slug>/deploys
Authorization: Basic <valid token>
X-Shipit-User: <victim-admin-login>
{"sha": "<commit sha>"}
```
Since a `User` record with that login exists, `identify_user` returns it, and the deploy is attributed to the victim with no verification.

Existing guards do not stop this: `require_permission!`/`check_permissions!` only checks the API client's permission list against operation/scope, not the acting user; `authenticate_api_client` never binds the header to a verified identity; there is no `verify_signature` or `ExplicitParameters` rule constraining the header's value to the client's creator.

### Impact Explanation
An attacker holding any valid API credential — even one narrowly scoped to a single stack, or none at all if `disable_api_authentication` is set — can attribute a `POST /api/stacks/<slug>/deploys` (or analogous rollback/lock/merge) action to an arbitrary existing `User`, including admins or team leads, with no proof they control that identity. This is an authentication/attribution bypass matching the Critical category ("an unauthorized deploy, rollback or merge" / record attribution not authenticated to the acting party). It is repeatable against any stack the token has permission for, and if `disable_api_authentication` is enabled organization-wide, against every stack.

### Likelihood Explanation
Preconditions: attacker needs a valid API token with `deploy:stack` (or equivalent) permission for the target stack, or the deployment must run with `Shipit.disable_api_authentication` enabled; and a `User` row with the victim's login must exist (trivially true for any team member who has ever logged in via GitHub OAuth). Attacker cost is a single crafted HTTP request with a custom header — no cryptographic material, GitHub secrets, or session is required beyond the API token already held. Fully repeatable per request.

### Recommendation
Bind `current_user` to a verified identity rather than a client-supplied header: either derive the acting user from `current_api_client.creator` directly, or require that `X-Shipit-User` match `current_api_client.creator.login` (rejecting/ignoring the header otherwise), and disallow header-based impersonation entirely for `UnlimitedApiClient`/`disable_api_authentication` mode.

### Proof of Concept
Minitest under `test/controllers/api/deploys_controller_test.rb`:
```ruby
test "#create attributes the deploy to an arbitrary user via a forged X-Shipit-User header" do
  api_client = shipit_api_clients(:shipit)  # token scoped to stack A only, creator != victim
  victim = shipit_users(:walrus)            # unrelated admin user record
  authenticated_request(api_client)
  request.headers['X-Shipit-User'] = victim.login

  post :create, params: { stack_id: @stack.to_param, sha: @commit.sha }

  deploy = Deploy.last
  assert_equal victim.id, deploy.user_id,        # current_user == victim (forged)
    "current_user should equal current_api_client.creator, not the spoofed header"
  refute_equal api_client.creator_id, deploy.user_id
end
```
Both sides of the intended binding (`current_user == current_api_client.creator`) diverge: the test shows `deploy.user_id == victim.id` while `api_client.creator_id != victim.id`, proving the header alone determines attribution. [1](#0-0) [2](#0-1) [3](#0-2)

# frozen_string_literal: true

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }

    class << self
      def authenticate(token)
        find_by(id: message_verifier.verify(token).to_i)
      rescue Shipit::SimpleMessageVerifier::InvalidSignature
      end

      def message_verifier
        @message_verifier ||= Shipit::SimpleMessageVerifier.new(Shipit.api_clients_secret)
      end
    end

    def authentication_token
      self.class.message_verifier.generate(id)
    end

    def check_permissions!(operation, scope)
      required_permission = "#{operation}:#{scope}"
      unless permissions.include?(required_permission)
        raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
      end

      true
    end
  end
