### Title
Unconfirmed correspondent devices are processed identically to confirmed ones, allowing unapproved peers to trigger wallet/AA-adjacent message handling - (File: device.js)

### Summary
`ocore`'s hub-client message pipeline treats a correspondent device as "known" purely based on the existence of a row in `correspondent_devices`, without ever checking the `is_confirmed` flag that is supposed to represent the local user's explicit approval of that peer. This mirrors the Mastodon FASP bug: an entity that is only *provisionally* registered (an unapproved FASP / here, an unconfirmed correspondent device) is treated by downstream logic as if it had been fully approved, letting it drive privileged processing paths that were meant to be gated behind user approval.

### Finding Description
When a hub message arrives, `handleJustsaying` looks up the sender purely by `device_address`: [1](#0-0) 

This `SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?` never references `is_confirmed`. If any row exists — confirmed or not — the message is routed straight into `handleMessage()` and ultimately into `eventBus.emit("handle_message_from_hub", ...)`, which is consumed by `wallet.js`'s `handleMessageFromHub`/`doHandle()` switch that processes dozens of privileged subjects (`text`, `object`, `new_shared_address`, `approve_new_shared_address`, `my_xpubkey`, `signing_request`-inducing signed messages, private-payment forwarding, arbiter/prosaic contract flows, etc.).

A correspondent row can be created with `is_confirmed=0` via `addUnconfirmedCorrespondent`: [2](#0-1) 

and the initial contact can be established even from a completely unknown device, because a fixed whitelist of subjects is allowed through before any correspondent row exists at all: [3](#0-2) 

`is_confirmed` is set to `1` only inside the explicit pairing flow (`handlePairingMessage`): [4](#0-3) 

but it is never read back anywhere as a gating condition — the only two writers of `is_confirmed` are the `INSERT`/`UPDATE` in `handlePairingMessage`, and the `INSERT ... is_confirmed) VALUES (...,0)` in `addUnconfirmedCorrespondent`. No code path in `device.js` or `wallet.js` conditions message acceptance/processing on `is_confirmed=1`. Consequently, once a device address has any correspondent row (even one inserted as unconfirmed, e.g. via the `my_xpubkey`/`wallet_fully_approved` whitelist path used during multi-device wallet setup), all subsequent messages from that device — regardless of subject — are fully processed by the wallet message-handling switch exactly as though the user had explicitly approved the contact.

This is analogous to the Mastodon flaw where FASP subscription/backfill actions "did not check properly whether the FASP was actually approved," letting an unapproved registrant act with the privileges of an approved one.

### Impact Explanation
Because `is_confirmed` is not enforced, a device that only ever reached the unconfirmed state (e.g. through the `my_xpubkey`/`wallet_fully_approved` whitelist entry point, which is explicitly designed to be reachable from non-correspondents) can subsequently send arbitrary wallet-protocol messages that are processed with full trust: initiating/approving shared (multi-sig) address definitions (`new_shared_address`, `approve_new_shared_address`), engaging in private-payment/contract negotiation, or repeatedly re-triggering the message pipeline. Since all such device messages are serialized through a single mutex (`mutex.lock(["from_hub"], ...)`), an unapproved correspondent can flood this pipeline, causing the same "queue pressure" DoS pattern as the original CVE, while also risking that state intended to require explicit user approval (contact confirmation) is bypassed for actions like shared-address composition.

### Likelihood Explanation
The unconfirmed-correspondent state is a normal, frequently exercised part of the multi-device/multisig wallet setup flow (`addUnconfirmedCorrespondent`, whitelisted `my_xpubkey`/`wallet_fully_approved` subjects), so no special privilege is required to reach it — any device that can complete the whitelisted first-contact handshake ends up in this state, after which all further authorization relies on an `is_confirmed` flag that is never checked.

### Recommendation
Add an explicit `is_confirmed` check in the hub-message dispatch path (`device.js` handleJustsaying`'s correspondent lookup at line 204, and/or in `wallet.js`'s `doHandle` before switching on `subject`), and restrict processing for unconfirmed correspondents to the same whitelist used for unknown correspondents until the user explicitly confirms the contact.

### Proof of Concept
1. Attacker device sends a `my_xpubkey` (whitelisted) message to victim's hub, causing `addUnconfirmedCorrespondent` to insert a row with `is_confirmed=0`.
2. Attacker device immediately sends further messages (e.g. `new_shared_address`, `text`, `object`, or contract-negotiation subjects) to the same hub.
3. `handleJustsaying` at device.js:204 finds the correspondent row (ignoring `is_confirmed`) and forwards the message into `handleMessageFromHub`/`doHandle`, which fully processes it as if the correspondent had been explicitly confirmed by the user — no code path ever consults `is_confirmed` to reject it.
