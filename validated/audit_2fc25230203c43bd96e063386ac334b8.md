### Title
Webhook signature verified against `repository.owner.login` while event handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports a multi-organization GitHub App configuration where each GitHub organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature with using the `repository.owner.login` (falling back to `organization.login`) field from the JSON body [2](#0-1) [3](#0-2) . However, once the signature passes, the event handlers that actually mutate state look up the target `Repository`/`Stack` using a *different* field entirely: `repository.full_name` [4](#0-3) . Because the signature only cryptographically binds to "some org's secret verified this raw payload," not to "this specific `repository.full_name` was reviewed by that org's secret," an attacker holding a valid webhook secret for their own organization/repo can forge a payload whose `repository.owner.login`/`organization.login` matches their org (so verification passes with their key) while `repository.full_name` points at an unrelated repository/stack hosted under a different organization also configured in the same Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` resolves a `GitHubApp` instance per organization, each with its own independently configured `webhook_secret` [1](#0-0) . The `verify_webhook_signature` check only proves that the raw POST body was HMAC-signed with *some* org's key; it does not further constrain that only fields "belonging" to that org can be trusted [5](#0-4) .

After verification, `WebhooksController#create` dispatches the full parsed JSON body, unmodified, to every registered handler for the event type: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) . Each handler resolves its target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`, e.g. the base `Handler#stacks`/`#repository_name` helper [4](#0-3) , and the same pattern in `pull_request` handlers (`OpenedHandler#repository`, `LabeledHandler#repository`, `ClosedHandler#repository`, etc.), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [7](#0-6) [8](#0-7) .

This creates exactly the class of binding break described in the report: the field used for the trust decision (`repository.owner.login`, which selects the verifying secret) is not the field acted upon (`repository.full_name`, which selects the mutated repository/stack). Just as the contract applied a collateral factor to one representation of balance while checking margin against a combined total that could be manipulated by shifting balance between representations, here the controller "trusts" the payload based on one identifier while the handler "acts" on a different, unguarded identifier inside the same signed body. Since the whole JSON body is attacker-controlled up to producing a valid signature with their own key, and only the `owner.login`/`organization.login` sub-field is constrained to match their own org, the `repository.full_name` field is free for the attacker to set to any string, including a repository belonging to a different organization configured on the same Shipit instance.

Concretely, for handlers like `PullRequest::OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ClosedHandler`, `ReopenedHandler`, and the generic push/status handlers reached through `Handler#stacks`, an attacker who owns/administers one org's GitHub App (and thus its `webhook_secret`) could send a `pull_request` (or `push`/`status`) webhook where:
- `organization.login` / `repository.owner.login` = attacker's own org (verification passes with attacker's own legitimately-known secret)
- `repository.full_name` = `"victim-org/victim-repo"` (a stack registered under a different, unrelated organization in the same Shipit deployment)

This would let the attacker's forged event archive/unarchive review stacks, create review stacks, or otherwise trigger repository/stack-scoped side effects for a repository they do not control, purely because they possess a webhook secret for a *different* org hosted on the same instance.

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated" == "repository that is written." A party who legitimately controls the webhook secret for org A can act on stacks/repositories belonging to org B, which is an unauthorized cross-repository write path (stack archival/unarchival/provisioning triggered without the legitimate B-org signature), matching the report's High/Critical impact bucket for cross-repository writes.

### Likelihood Explanation
This requires the deployment to actually configure more than one GitHub organization with independent `webhook_secret`s (the multi-org config schema in `lib/shipit.rb`) — a supported and documented mode, not a hypothetical one [9](#0-8) . Given that precondition, the exploit needs only a normal webhook delivery crafted by an attacker holding the org-A secret (e.g., an org-A GitHub App admin or anyone who can trigger org-A's webhook delivery with attacker-controlled body content, such as a `pull_request` payload whose `repository.full_name` is spoofable client-side before signing). I could not fully verify within the available context whether any additional cross-checks exist elsewhere (e.g., in `Repository.from_github_repo_name` or stack lookup) that might implicitly re-validate organization ownership beyond `full_name` string matching — this is a gap in my analysis that would benefit from a full-repo review by a Devin session.

### Recommendation
Bind the verified organization to the acted-upon repository: after `verify_signature` resolves `repository_owner`, re-derive/validate that `repository.full_name`'s owner segment matches the verified `repository_owner`/`organization.login` before dispatching to handlers, rejecting (422) any payload where they diverge.

### Proof of Concept
Conceptual (not runnable without a live multi-org Shipit instance, since `test/**` is out of scope and I have read-only access):
1. Deploy Shipit configured with two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `lib/shipit.rb` `github_app_config`).
2. As an attacker who administers/owns `org-a`'s webhook secret, craft a `pull_request` `opened` event JSON body where `organization.login` / `repository.owner.login` = `org-a`, but `repository.full_name` = `org-b/private-repo` (an existing stack under org-b).
3. Sign the raw body with `org-a`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: pull_request` and the resulting `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'org-a')` and successfully verifies the signature [2](#0-1) .
5. `OpenedHandler#process` resolves `Repository.from_github_repo_name('org-b/private-repo')` and creates/provisions a review stack for org-b's repository, entirely driven by attacker-controlled content signed only with org-a's key [10](#0-9) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
