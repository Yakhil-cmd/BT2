This confirms the multi-org configuration architecture: `Shipit.github(organization:)` looks up a per-organization `GitHubApp` config (each with its own `webhook_secret`) via `Shipit.github_app_config` [1](#0-0) , exactly matching the documented multi-org setup in `config/secrets.development.example.yml`.

### Title
Webhook signature verification is scoped to `repository.owner.login` while event handlers act on `repository.full_name`, allowing a controller of one configured GitHub organization to spoof events against stacks in a different organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the inbound `X-Hub-Signature` against using `repository_owner`, a value read from the JSON payload's `repository.owner.login` (or `organization.login`) field [2](#0-1) . Once the signature check passes, every webhook handler (`PushHandler`, `PullRequest::*Handler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`) instead resolves the target `Repository`/`Stack` using a *different* payload field, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name` and `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . Since Shipit supports hosting multiple GitHub organizations, each with its own `webhook_secret` configured independently under `secrets.github` [1](#0-0) , the field used to select/authenticate the signing secret (`repository.owner.login`) is never cross-checked against the field used to pick the object that gets written to (`repository.full_name`).

### Finding Description
For a Shipit instance configured with multiple GitHub organizations (a first-class, documented configuration, see `config/secrets.development.example.yml`), each organization has its own `GitHubApp` instance and `webhook_secret`, retrieved via `Shipit.github(organization: repository_owner)` [5](#0-4) . An attacker who administers their own registered GitHub App for `OrgA` (one of the configured organizations) knows `OrgA`'s `webhook_secret` and can freely construct and sign an arbitrary JSON body themselves — they do not need to go through GitHub's actual webhook delivery.

They can craft a payload where:
- `repository.owner.login` = `"OrgA"` (used only for signature-secret selection in `verify_signature`)
- `repository.full_name` = `"OrgB/some-repo"` (used by the handler to find the actual `Repository`/`Stack` to act on)

Because `verify_signature` computes the HMAC using `OrgA`'s `webhook_secret` and the attacker controls that secret, the signature check succeeds [6](#0-5) . `WebhooksController#create` then dispatches to the registered handler with the full parsed payload [7](#0-6) , and the handler resolves its target repository purely from `repository.full_name`, with no re-validation that this matches the organization whose secret authenticated the request [8](#0-7) [9](#0-8) .

This lets the attacker trigger, for `OrgB/some-repo` stacks that they have no relationship to:
- `PushHandler#process`: enqueue `sync_github` for arbitrary branches/SHAs on the target stack.
- `PullRequest::OpenedHandler`/`ReopenedHandler`/`UnlabeledHandler`: create, archive, or unarchive review stacks.
- `MembershipHandler`: create/delete `Team`/`Membership` records tied to `OrgB`.
- `StatusHandler`/`CheckSuiteHandler`: forge commit statuses / trigger check-run refreshes for `OrgB` commits.

The binding that should hold — "the organization whose secret authenticated this request" == "the repository the handler is permitted to write to" — is broken because the two are read from independent, unvalidated fields of the same self-authored payload.

### Impact Explanation
This crosses an authentication boundary: it allows cross-repository/cross-organization writes and unauthorized state changes (unarchiving review stacks, forging CI status/check results that feed into deploy gating, enqueuing GitHub syncs, mutating team/membership records) on a `Repository`/`Stack` the attacker does not own, using only credentials for an unrelated, attacker-controlled organization also hosted on the same Shipit instance. This matches the "cross-repository writes" Critical-impact category, since a forged `status`/`check_suite` event can flip `Commit#deployable?` gating used by deploy flows for a repository the attacker doesn't control.

### Likelihood Explanation
This requires a Shipit deployment configured with multiple GitHub organizations, and the attacker must control (be an admin of) at least one of those configured organizations/GitHub Apps — a normal, unprivileged relationship w.r.t. the *other* organizations hosted on the same instance. No Shipit session, `ApiClient` token, or the victim organization's secret is needed. Given multi-org hosting is an explicitly documented and supported configuration, this is readily reachable for any Shipit instance serving more than one organization.

### Recommendation
After signature verification succeeds, re-derive `repository_owner` from `repository.full_name` (or explicitly compare `repository.owner.login` against the owner segment of `repository.full_name`) and reject the request (422) if they differ. Alternatively, have handlers resolve the repository via the already-authenticated `repository_owner`/organization rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, as supported by `config/secrets.development.example.yml`.
2. As an attacker who is an admin of `OrgA`'s registered GitHub App (and thus knows `OrgA`'s `webhook_secret`), craft:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates successfully against the attacker's own secret [6](#0-5) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues a `sync_github` job for the victim's stack [10](#0-9) , despite the request never being authenticated with `OrgB`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first

  end

  end
