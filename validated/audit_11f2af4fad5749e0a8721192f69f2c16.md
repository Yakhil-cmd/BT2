### Title
Webhook signature check keyed to the payload's own `repository.owner.login` allows an org with no `webhook_secret` to author events for an unrelated repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App config (and therefore the HMAC secret it verifies against) using a field that is itself inside the attacker-supplied, not-yet-verified JSON body (`repository.owner.login`), while the downstream event handlers act on a different field (`repository.full_name`) from that same unverified body. If any configured organization in the installation has no `webhook_secret` set, signature verification for that organization is a no-op, letting an unauthenticated caller submit an event whose "authenticating" org (`repository.owner.login`) is the secret-less org, but whose "acted-upon" repository (`repository.full_name`) belongs to a completely different, victim organization/stack.

### Finding Description
The controller derives the org used to select the verifying `GithubApp` purely from the request body itself, before that body has been authenticated: [1](#0-0) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` — a value fully controlled by the request payload — and `Shipit.github(organization: repository_owner)` returns the `GithubApp` instance configured for that name. `verify_webhook_signature` then does: [2](#0-1) 

`return true unless webhook_secret` — if the org picked out of the unverified body has no `webhook_secret` configured, the signature check trivially passes regardless of the actual `X-Hub-Signature` header. This is a documented, supported configuration state, shown directly in the shipped secrets templates (`webhook_secret: # nil`): [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (because the "authenticating" org has no secret), the full, still-attacker-controlled `params` hash is dispatched unchanged to the event handlers: [5](#0-4) 

Every handler resolves which `Stack`/`Repository` to act on from the *same payload*, but from a *different key* — `repository.full_name` — not `repository.owner.login`: [6](#0-5) 

Nothing ties `repository.owner.login` (used to pick the verifying secret) to `repository.full_name` (used to pick the target stack). In a real GitHub-issued webhook these are always consistent (`full_name` is `"#{owner.login}/#{repo}"`), but because the whole JSON body is attacker-supplied before any authentication occurs, an attacker can set them independently: e.g. `repository.owner.login = "org-with-no-secret"` while `repository.full_name = "victim-org/victim-repo"`.

`PushHandler` then triggers `stack.sync_github(expected_head_sha:)` for the victim stack: [7](#0-6) 

and `StatusHandler` sets a commit status on any matching commit sha in the database, with no repository scoping whatsoever: [8](#0-7) 

This breaks the trust binding: `organization that authenticated == repository that is written` is assumed but never enforced.

### Impact Explanation
`StatusHandler` can forge a `success` state for any required/blocking CI status context on any commit in any stack, without any relation to the org that "authenticated" the request. Because deploy safety (`required_statuses`/`blocking_statuses`) and continuous-delivery gating rely on stored `Status` rows being trustworthy, an attacker who can reach a Shipit install where at least one configured GitHub org has an empty `webhook_secret` can inject fabricated green statuses for a victim repository's commits, potentially enabling an **unauthorized deploy** via continuous delivery, or making an otherwise-blocked commit deployable. `PushHandler` similarly lets the attacker force a `sync_github` against a stack it doesn't own, causing the app to fetch attacker-influenced GitHub state for it. Both are unauthenticated-attacker, cross-organization writes into another org's stack data — matching the Critical "unauthorized deploy" / cross-repository-writes impact category.

### Likelihood Explanation
Requires no session, token, or GitHub credentials — the webhook endpoint is public. The only precondition is that the multi-org Shipit deployment has at least one configured GitHub organization with a blank `webhook_secret`, which is an explicitly supported and documented configuration (shown in the shipped secrets templates), not a misconfiguration outside the engine's own code. Any deployment operating multiple orgs where even one (e.g., a low-stakes/dev org) omits a webhook secret exposes every other org's stacks to this cross-organization write.

### Recommendation
Do not derive the verifying organization from a field independent of the field the handlers use to select the target repository/stack. Either (a) require that the org used for `verify_webhook_signature` be re-derived from, and checked for equality against, the owner implied by `repository.full_name` that the handler will actually act on, or (b) resolve the target `Stack`/`Repository` first, obtain its known organization, and use that (not attacker-supplied `repository.owner.login`) to select the `GithubApp`/secret. Additionally, `StatusHandler` should scope `Commit.where(sha:)` lookups to commits belonging to the repository named in the (now-verified) payload rather than matching sha globally across all stacks.

### Proof of Concept
1. Configure Shipit with two orgs: `secretless-org` (webhook_secret unset/nil) and `victim-org` (has a webhook_secret, hosts `victim-org/victim-repo` as a tracked stack).
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or an arbitrary bogus one), and body:
```json
{
  "repository": { "owner": { "login": "secretless-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "required-ci-check"
}
```
3. `repository_owner` resolves to `secretless-org` → `Shipit.github(organization: "secretless-org")` has a blank `webhook_secret` → `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` matches the commit by `sha` (no repo check) and writes a forged `success` status usable to satisfy `victim-org/victim-repo`'s blocking/required statuses, potentially triggering an unauthorized continuous deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
