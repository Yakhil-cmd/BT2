The Cooler.sol issue is EVM-specific: a lending contract hardcodes `DECIMALS_INTEREST = 1e18` in `interestFor()` while accepting arbitrary ERC20 collateral tokens with differing `decimals()`, causing systematic truncation for low-decimal tokens like USDC or GUSD.

Searching this polkadot-sdk repository for an analogous "loan/interest calculation using a hardcoded decimal constant across heterogeneous token decimals" pattern did not surface a comparable FRAME pallet:

- There is no lending/interest-accrual pallet in this codebase equivalent to Cooler.sol's `interestFor()`.
- The closest decimal-scaling logic is in the custom `pallet-psm`, which explicitly stores per-asset decimal snapshots (`AssetDecimals`, `StableDecimals`) and implements `external_to_internal`/`internal_to_external` conversion helpers that scale by `10^(decimals_diff)` using the asset's actual decimals rather than a hardcoded constant [1](#0-0) . This is the opposite of the reported bug pattern — it was built specifically to handle mixed-decimal assets correctly, as documented in the PR notes [2](#0-1) .
- `pallet-asset-rate` uses `FixedU128` multiplicative conversion rates (`native_amount = asset_amount * rate`), which is decimal-agnostic by construction since the rate itself encodes the ratio, not a fixed decimal assumption [3](#0-2) .
- Fee/pricing conversions elsewhere (e.g., Snowbridge's `convert_from_ether_decimals`, the bridge relay's `convert_to_token_balance`) explicitly parameterize on the token's actual decimals rather than hardcoding 18 [4](#0-3) [5](#0-4) .

Since there is no reachable FRAME extrinsic/pallet that hardcodes a token-decimal-dependent constant analogous to `DECIMALS_INTEREST` while accepting variable-decimal collateral, and the closest real analog (`pallet-psm`) was specifically engineered to avoid this exact class of bug, this EVM-specific rounding issue does not have a demonstrable FRAME analog in this repository.
