## Finding

`Shipit::Api::CCMenuController` breaks the binding between the stack an `ApiClient` token is scoped to authorize and the stack it actually operates on, allowing any valid API token with `read:stack` permission to read build/deploy status for **any** stack in the Shipit instance, not just the one it was issued for.

### Root cause

`Shipit::Api::BaseController` scopes stack lookups to the calling `ApiClient`'s authorized stack when one is set: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the deployment-trust binding: `ApiClient.stack_id` == the only `Stack` that token may touch (enforced by every other controller, e.g. `StacksController`, `DeploysController`, which inherit `stack` unmodified).

`CCMenuController`, however, overrides `stack` to bypass the `stacks` scope entirely and query the unscoped `Stack` model directly: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

The controller still declares `require_permission :read, :stack` [3](#0-2) , but `ApiClient#check_permissions!` only checks the `operation:scope` string, never the specific stack: [4](#0-3) 

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

So the equality that should hold — `current_api_client.stack_id == stack.id` (or "any stack" only when `stack_id` is unset) — is never enforced in `CCMenuController#show`. A token issued with `stack_id` set to stack A (e.g. the `here_come_the_walrus` fixture, restricted to `shipit`) [5](#0-4)  can be used with a different `stack_id` param to fetch CCMenu XML (deploy status, last build result, project name) for any other stack, including ones belonging to repositories the token's creator has no relationship with.

### Impact

Authenticated read of stack state / deploy output across stack boundaries — an unauthorized cross-stack information disclosure that defeats the per-stack scoping mechanism that is the entire purpose of `ApiClient.stack_id`. Any Shipit deployment that issues stack-scoped tokens (a documented, intended restriction, see `ApiClient` model and its test fixtures/tests such as "an api client scoped to a stack will only see that one stack" [6](#0-5) ) is affected, since `CCMenuController` is the one endpoint that doesn't respect that scoping.

### Proof of Concept

1. Create/obtain an `ApiClient` restricted to stack A (`stack_id: A`, permission `read:stack`) — e.g. via `POST /api_clients` as any Shipit user, restricting the client to a single stack.
2. Call `GET /api/ccmenu/<stack-B-id-or-slug>.xml?token=<clientA_token>` where stack B is a different stack the client is not authorized for.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` passes (the client does have `read:stack` in its permission list), and `stack` resolves via `Stack.from_param!(params[:stack_id])` — unscoped — returning stack B's data instead of raising `RecordNotFound`/403.
4. The response renders stack B's CCMenu project XML (name, last build status, build time, etc.), even though client A was only ever authorized for stack A.

### Recommendation

Change `CCMenuController#stack` to reuse the scoped `stacks` collection instead of the raw `Stack` model:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the binding between `current_api_client.stack_id` and the stack actually served, consistent with every other API controller inheriting from `BaseController`.
