### Title
Signer-key authorization/signature is not bound to `tx-sender`, allowing front-running to burn a one-time `auth-id` and block the intended stacker's stacking action - (File: `stackslib/src/chainstate/stacks/boot/pox-4.clar`)

### Summary
`pox-4.clar`'s signer-key authorization scheme lets a signer pre-authorize (via `set-signer-key-authorization`) or sign off-chain (`signer-sig`) a one-time-use permission for a stacking action (`stack-stx`, `stack-extend`, `stack-increase`, `stack-aggregation-commit(-indexed)`). Neither the stored authorization tuple nor the signed message hash includes the `tx-sender`/stacker's identity, so any address that learns the signature or sees an on-chain authorization can call the target function first with a trivial valid amount, consuming the single-use `auth-id` and permanently blocking the intended stacker from using that exact authorization — an unprivileged griefing analogous to the reported `reset()` front-running bug, where a one-time authorization state is consumed by someone it was never meant to protect against.

### Finding Description
`verify-signer-key-sig` checks the signature/authorization strictly against `{signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount}` — there is no `tx-sender`/stacker binding anywhere in the hash construction: [1](#0-0) 

`consume-signer-key-authorization` marks the authorization as used the first time any `tx-sender` successfully calls with a valid `signer-sig`/pre-set authorization, via a one-time `map-insert` into `used-signer-key-authorizations`: [2](#0-1) 

Because `amount` only has to satisfy `amount <= max-amount` (not `amount == max-amount`), and because nothing ties the call to the address the signer/pool operator actually intended to authorize, any onlooker (e.g. observing a broadcast `signer-sig` in the mempool, or reading the public `signer-key-authorizations` map after `set-signer-key-authorization`) can front-run with a minimal `amount-ustx`, call `stack-stx`/`stack-increase`/`stack-extend`/`stack-aggregation-commit` themselves, and consume the `auth-id` before the intended stacker's transaction lands. Once consumed, `verify-signer-key-sig` rejects any further attempt with `ERR_SIGNER_AUTH_USED`: [3](#0-2) 

This mirrors the reported vulnerability class: a permission/state-clearing action (`reset`) that anyone can trigger without a check tying it to whoever is entitled to rely on it, "using up" a resource meant for a specific counterparty and griefing them. Here the resource is the one-time `auth-id`, and the victim is the stacker/pool member who obtained a signer authorization for a specific reward cycle.

### Impact Explanation
`stack-stx` requires `first-reward-cycle` to equal the *next* reward cycle relative to the current burn height (`ERR_INVALID_START_BURN_HEIGHT`): [4](#0-3) 
so once the attacker burns the `auth-id` for that specific `reward-cycle`/`period`/`topic`/`pox-addr`, the legitimate stacker cannot simply retry with the same authorization — they miss the reward cycle for that lock. This is a temporary freezing of the intended stacking action for at least one full reward cycle (funds remain unlocked/unstacked when the stacker meant to lock them), satisfying the "temporary freezing of staked funds" / "unsigned stacking action" bar since the actual lock recorded on-chain (if any, since the front-runner can also lock a trivial amount to the pox-addr) is not the one the signer/stacker authorized.

### Likelihood Explanation
Requires only observing a public `set-signer-key-authorization` transaction or a `signer-sig` transaction/payload before it confirms (mempool front-running), both of which are realistic in pool-operator/signer workflows where authorizations are shared with intended stackers ahead of time. No special privileges are needed.

### Recommendation
Bind the authorization to the intended stacker by including `tx-sender` (or an explicit `stacker`/`recipient` principal parameter) inside `get-signer-key-message-hash` and inside the `signer-key-authorizations` / `used-signer-key-authorizations` map keys, so a given `auth-id` can only be consumed by the principal it was actually authorized for.

### Proof of Concept
Conceptual sequence (based on the contract logic above):
1. Signer/pool operator calls `set-signer-key-authorization` on-chain (or shares `signer-sig` off-chain) authorizing `auth-id=1`, `max-amount=X`, `pox-addr=P`, `reward-cycle=R`, `topic="stack-stx"` for stacker Alice.
2. Attacker observes this and calls `stack-stx` first with `amount-ustx=1`, the same `pox-addr`, `reward-cycle`, `period`, `signer-key`, `max-amount=X`, `auth-id=1`.
3. `consume-signer-key-authorization` succeeds and inserts the `used-signer-key-authorizations` entry, per [5](#0-4) .
4. Alice's subsequent `stack-stx` call with the same parameters now fails with `ERR_SIGNER_AUTH_USED` (see check at [6](#0-5) ), and since `stack-stx` enforces `first-reward-cycle` must equal the next reward cycle, Alice cannot simply wait and retry with the same authorization — she must obtain a brand-new signature/authorization for a future cycle, having missed the one intended.

```text
;; This function does two things:
;;
;; - Verify that a signer key is authorized to be used
;; - Updates the `used-signer-key-authorizations` map to prevent reuse
;;
;; This "wrapper" method around `verify-signer-key-sig` allows that function to remain
;; read-only, so that it can be used by clients as a sanity check before submitting a transaction.
(define-private (consume-signer-key-authorization (pox-addr { version: (buff 1), hashbytes: (buff 32) })
                                                  (reward-cycle uint)
                                                  (topic (string-ascii 14))
                                                  (period uint)
                                                  (signer-sig-opt (optional (buff 65)))
                                                  (signer-key (buff 33))
                                                  (amount uint)
                                                  (max-amount uint)
                                                  (auth-id uint))
  (begin
    ;; verify the authorization
    (try! (verify-signer-key-sig pox-addr reward-cycle topic period signer-sig-opt signer-key amount max-amount auth-id))
    ;; update the `used-signer-key-authorizations` map
    (asserts! (map-insert used-signer-key-authorizations
      { signer-key: signer-key, reward-cycle: reward-cycle, topic: topic, period: period, pox-addr: pox-addr, auth-id: auth-id, max-amount: max-amount } true)
      (err ERR_SIGNER_AUTH_USED))
    (ok true)))
```
