### Title
Cross-repo `Status` forgery via `Shipit::Webhooks::Handlers::StatusHandler#process` matching commits by `sha` alone, laundering into `deployable?` / `deploy_state == 'allowed'` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb], also `app/models/shipit/commit.rb`, `app/models/shipit/undeployed_commit.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no check that `params.repository.full_name` (or `params.repository.owner.login`) corresponds to the stack/repository the matched commit belongs to. Because webhook signature verification (`WebhooksController#verify_signature`) only proves the request came from *some* GitHub organization configured in `Shipit.github_teams`/`secrets.yml` — selected using the attacker-controlled `repository.owner.login` field in the JSON body — an attacker who controls a repository with its own installed Shipit GitHub App (and thus knows that app's own `webhook_secret`) can send a fully-signed `status` webhook that references a `sha` belonging to a completely different, victim repository's commit, causing a `Status` row to be attached to the victim stack's commit and potentially flip `Commit#deployable?` to true.

### Finding Description
The broken binding is:

`Status.stack_id == Commit(sha).stack_id` **should imply** `webhook.repository.full_name == Commit(sha).stack.repository.full_name`

but the code never checks the right-hand side.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes straight from the parsed JSON body (`params.dig('repository','owner','login')`, line 61) — entirely attacker-supplied. If the attacker names their own GitHub org/app in this field, the HMAC signature check passes using *their own* known `webhook_secret`. This is legitimate multi-tenant behavior for routing to the correct app config, not a bug by itself.
2. `WebhooksController#create` then dispatches the full parsed body to `Shipit::Webhooks.for_event('status')`, i.e. `StatusHandler.call(params)`.
3. `StatusHandler`'s param schema (`app/models/shipit/webhooks/handlers/status_handler.rb:7-18`) requires only `sha`, `state`, and optional cosmetic fields — it does **not** require or use `repository` at all, unlike other handlers (`Handler#repository_name`, `Handler#stacks`) which properly scope work via `Repository.from_github_repo_name(repository_name)`.
4. `process` (line 20-24) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a **global, unscoped** lookup across the entire `commits` table, spanning every repository/stack tenant in the Shipit instance.
5. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) creates a `Status` scoped to `commit.stack_id` — i.e., the **victim's** stack, not the attacker's.
6. If the forged `state` is `success` (and the attacker knows/guesses the required context, e.g. `ci/travis`), `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) can become true, and `UndeployedCommit#deploy_state` (`app/models/shipit/undeployed_commit.rb:18-19`) will render `'allowed'` to any legitimate viewer of the stack (`StacksController#show`, `Api::CommitsController`), and `Stack#next_expected_commit_to_deploy`/`trigger_continuous_delivery` (`app/models/shipit/stack.rb:332-342`) can pick this commit for continuous deployment, all without any request ever being signed by the victim's own GitHub App.

The attacker's exact request: `POST /webhooks` with header `X-Github-Event: status`, body `{"sha": "<victim-commit-sha>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "<attacker-org>"}}}`, signed with `X-Hub-Signature` computed using the attacker's own, self-known `webhook_secret` for `<attacker-org>`.

Why existing guards fail:
- `verify_signature` only authenticates *which GitHub org sent this*, not *which repository/commit the payload is allowed to mutate*. It is satisfied by design when the attacker owns a configured org.
- `drop_unhandled_event` and the `ExplicitParameters` schema pass because `status` is a handled event and the schema doesn't require a `repository` block for this handler.
- `Repository`/`Stack` model validations never run here because no `Repository`/`Stack` record is created or modified — only a `Status` row, and its `stack_id` is derived from the pre-existing victim `Commit`, not from anything in the forged payload.

### Impact Explanation
An unprivileged internet user who controls any repository connected to Shipit (with any installed/configured GitHub App, even a brand-new one they set up) can write arbitrary CI status data (`success`/`failure`/`pending`, `context`, `description`, `target_url`) onto commits belonging to **any other tenant's stack** in the same Shipit instance, as long as they know the target commit's `sha` (public/derivable info for public repos, PRs, or via other leaked identifiers). This can make an otherwise-non-deployable commit appear `deployable?`/`deploy_state == 'allowed'`, which is read by dashboards, the stack UI, and `Stack#next_expected_commit_to_deploy`/continuous-delivery cron — leading to an unauthorized deploy being triggered by a completely legitimate, unrelated actor (operator or cron) with no victim-signed webhook ever involved. This matches "Critical — an unauthorized deploy … a payload for one repository mutating another's stack/commit" per the given severity taxonomy. It is repeatable against any commit sha in any stack across the whole instance, so the blast radius spans all tenants sharing the Shipit deployment.

### Likelihood Explanation
Preconditions: attacker needs (a) any repository with a configured/installed GitHub App in this Shipit instance (trivial if the instance allows self-service onboarding, or if the attacker is a legitimate but unprivileged tenant of a multi-tenant Shipit install), and (b) the target commit's `sha`. No victim secrets, sessions, or team membership are required. Cost is a single crafted HTTP POST with an HMAC computed from a secret the attacker legitimately possesses. Fully repeatable/scriptable against arbitrary shas.

### Recommendation
In `StatusHandler` (and equivalently `check_suite`/`check_run` handlers if they share this pattern — not verified here), require the `repository.full_name` field in the params schema and scope the commit lookup through `Repository.from_github_repo_name(params.repository.full_name)&.stacks&.commits`. Only create/replicate a `Status` for commits belonging to a stack whose repository matches the payload's declared, signature-verified repository — mirroring the pattern already used in `Handler#stacks`/`Handler#repository_name`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "cross-repo status forgery: attacker cannot flip a victim stack's commit to deployable" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:fifth) # currently not deployable (no success status)
  refute_predicate victim_commit, :deployable?

  attacker_owner = 'attacker-org' # a distinct, Shipit-configured org the attacker controls
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate a validly-signed request from attacker's own org

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'owner' => { 'login' => attacker_owner }, 'full_name' => 'attacker/unrelated-repo' }
  }.to_json

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    post :create, body: body, as: :json
  end

  assert_predicate victim_commit.reload, :deployable?
  undeployed = Shipit::UndeployedCommit.new(victim_commit, index: 0)
  assert_equal 'allowed', undeployed.deploy_state
  # Assert the binding is broken: the Status was written for victim_stack even though
  # the signed/authenticated repository (attacker_owner/unrelated-repo) != victim_stack.repository.full_name
  refute_equal 'attacker/unrelated-repo', victim_commit.stack.repository.full_name
end
```
This demonstrates the equality `Status.stack_id == victim_commit.stack_id` is achieved purely from an unrelated, self-signed attacker webhook whose declared `repository` never matches the victim stack, with no `victim_stack.repository`-signed webhook involved — proving the binding is broken end-to-end.
