### Title
Cross-organization CI status forgery via webhook enables unauthorized deploys - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
This is the same trust-binding class of bug as the Putty M-07 finding: the field that is cryptographically verified is not the same field the engine subsequently acts on. `WebhooksController#verify_signature` authenticates a webhook payload against the GitHub App/webhook secret of one specific organization, derived from `repository.owner.login` / `organization.login` in the payload. However, `Shipit::Webhooks::Handlers::StatusHandler`, which reacts to the `status` event, never checks that the commit being updated actually belongs to a repository/stack of that authenticated organization — it updates any `Commit` row in the whole database that matches the attacker-supplied `sha`.

### Finding Description
The signature check binds `verified` to "the HMAC over `raw_post` matches the secret configured for `repository_owner`": [1](#0-0) [2](#0-1) 

In a multi-organization Shipit deployment, each onboarded GitHub organization has its own `webhook_secret` in the `github:` config block, and each org's admins legitimately know/control that secret through their own GitHub App setup: [3](#0-2) 

Once the signature passes, the controller dispatches the entire JSON `params` to every registered handler for the event, with no re-validation that other fields inside that same payload are consistent with the organization whose secret was used: [4](#0-3) 

`StatusHandler#process` then acts purely on the attacker-controlled `sha` field, with no scoping to the repository/organization that produced a valid signature: [5](#0-4) 

Compare this to the base `Handler` class, which does define a `repository_name`/`stacks` helper scoped to `payload.dig('repository', 'full_name')` for other handlers such as `PushHandler`: [6](#0-5) [7](#0-6) 

`StatusHandler` doesn't inherit that scoping check at all — it queries `Commit.where(sha: params.sha)` globally across the entire Shipit instance and calls `create_status_from_github!` on every match, regardless of which repository/organization owns that commit.

The equality that should hold is:
`organization whose webhook_secret authenticated the request == organization owning the repository/commit being mutated`

Instead, the engine only enforces: `organization whose webhook_secret authenticated the request == some org configured in Shipit.github(...)`, while the actual mutation target (`Commit` row matched by `sha`) is chosen from an unrelated, unauthenticated field with no cross-org restriction.

### Impact Explanation
A commit is uniquely identified by its SHA, and SHAs of target/victim repositories are frequently public knowledge (public repos, PR links, CI logs, Slack messages, etc.). An attacker who is a legitimate but unprivileged admin of *their own* onboarded GitHub organization on a multi-org Shipit instance can:
1. Legitimately obtain/know their own organization's `webhook_secret` (they configure their own GitHub App integration).
2. Craft a `status` webhook payload with `sha` set to a commit belonging to a completely different, victim organization's stack, and `state: success` plus a `context` matching a CI check name required by that victim stack's `ci.require` in `shipit.yml`.
3. Sign it with their own organization's valid webhook secret, which passes `verify_signature` because verification is scoped only to `repository_owner`, not to the commit being mutated.
4. `StatusHandler` creates a forged successful `CommitStatus` on the victim's commit, satisfying the victim stack's CI gating and enabling an **unauthorized deploy** to be triggered for a repository/organization the attacker has no access to.

This is a cross-repository/cross-organization write causing an unauthorized deploy — matching the "Critical" impact bar (unauthorized deploy via cross-repository writes) defined for this engine.

### Likelihood Explanation
Requires only: (a) a multi-org Shipit deployment (documented, supported configuration), and (b) the attacker administers any one onboarded organization (an unprivileged actor relative to the victim organization/stack). No `ApiClient` token, no GitHub App private key, and no repository write access to the victim repo is needed — only a valid signature for the attacker's own org and knowledge of a target commit SHA and CI context name (often discoverable). This is a realistic, low-effort path.

### Recommendation
`StatusHandler` (and any other handler acting on payload identifiers) must scope its lookup by the authenticated organization/repository — e.g. resolve `Commit` only through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`'s stacks, and additionally verify that `repository.owner.login`/`organization.login` used for signature selection matches `repository.full_name`'s owner before processing. In general, every field consumed by a handler that has security consequences should be validated as belonging to the same organization/repository that produced the verified signature, not merely "some field in the same JSON blob."

### Proof of Concept
1. Configure two organizations, `attacker-org` and `victim-org`, both onboarded to the same Shipit instance (`config/secrets.yml` multi-org `github:` block), each with a distinct `webhook_secret`.
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org's GitHub App).
3. Attacker finds a commit SHA `S` that is the head of a `victim-org` stack currently blocked from deploying by `ci.require: [some-check]`.
4. Attacker POSTs to `/github/webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature: sha1=<HMAC(raw_body, attacker-org_secret)>`
   - Body: `{"repository":{"owner":{"login":"attacker-org"}}, "sha":"S", "state":"success", "context":"some-check", "branches":[{"name":"main"}]}`
5. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s secret, and the signature validates.
6. `StatusHandler#process` runs `Commit.where(sha: "S")` — finds the victim's commit (no org/repo check) — and creates a `success` status for it via `create_status_from_github!`, satisfying `victim-org`'s CI gate for an unauthorized deploy.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
