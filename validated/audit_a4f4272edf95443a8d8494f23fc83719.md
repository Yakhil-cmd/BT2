### Title
Webhook signature check is bound to `repository.owner.login` while every event handler acts on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository_owner`, which is read from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`, falling back to `params.dig('organization', 'login')`). Every downstream handler, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field of the same untrusted body: `payload.dig('repository', 'full_name')`. The signature check therefore never establishes that the organization whose secret validated the request is actually the owner of the repository the handlers will act on.

### Finding Description [1](#0-0) 
verifies the signature like this:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
`repository_owner` comes straight from the body: [2](#0-1) 

But `Shipit::Webhooks::Handlers::Handler` — the base class for every webhook handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers, etc.) — resolves the target repository/stack from a different field of the same JSON body: [3](#0-2) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler#process`, for example, uses `stacks` (derived from `full_name`) to enqueue `sync_github`: [4](#0-3) 

The additional layer that makes this exploitable without any secret is that `GitHubApp#verify_webhook_signature` treats an absent secret as automatically verified: [5](#0-4) 
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
The webhook secret is explicitly documented as *optional* per organization/app, both for single- and multi-organization installs: [6](#0-5) [7](#0-6) 

Putting this together: the "identity" that is cryptographically checked (`repository.owner.login` → which `webhook_secret` is used, or "no secret configured → automatically verified") is not the same identity that the handlers use to decide *what gets written* (`repository.full_name`). Nothing in the controller or `Handler` base class cross-checks that `full_name.split('/').first == repository_owner`.

### Impact Explanation
In a multi-organization Shipit deployment (explicitly documented as a supported configuration), or in any deployment where at least one configured GitHub organization has no `webhook_secret` set (also explicitly documented as optional), an unauthenticated actor can POST an arbitrary JSON body to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to the organization whose secret check is bypassable (missing secret, or a secret the attacker knows for their own org), and
- `repository.full_name` set to any *other* organization's tracked repository (e.g. `"victim-org/production-app"`).

`verify_signature` passes because it only checks the `repository_owner` organization's secret (or skips the check entirely when that organization has no secret configured), while every handler acts on the unrelated `repository.full_name`. This lets the attacker:
- Trigger `PushHandler` → `stack.sync_github(expected_head_sha: attacker_controlled_sha)` for a repository/stack they do not own — a cross-repository write into Shipit's tracked commit history for a stack under a different organization.
- Trigger `StatusHandler` to inject forged commit statuses on victim-org commits, which can flip a commit from "not deployable" to "deployable" and let it pass through Shipit's CI-gating logic used before deploys/merges — enabling an unauthorized deploy or merge queue admission.
- Trigger `check_suite`/`pull_request` handlers similarly scoped only by `full_name`.

This crosses the "cross-repository writes" / "unauthorized deploy, rollback or merge" bar defined as Critical impact, and requires no Shipit session, no `ApiClient` token, and (in the missing-secret case) no knowledge of any secret at all — only knowledge of a target repository's `owner/name`, which is typically public.

### Likelihood Explanation
The `/webhooks` endpoint is intentionally unauthenticated (it's meant to be hit by GitHub, not by logged-in users), and `docs/setup.md`/`config/secrets.*.yml` explicitly document `webhook_secret` as optional and document multi-organization configuration where each organization has its own independent secret. Any Shipit deployment that (a) tracks more than one GitHub organization, or (b) has any organization configured without a webhook secret (a documented, supported state), is exploitable by simply crafting a POST request with mismatched `owner.login` / `full_name` values — no privileged access or reconnaissance beyond public repository names is required.

### Recommendation
In `WebhooksController`/`Shipit::Webhooks::Handlers::Handler`, after signature verification, assert that the organization used to select/validate the webhook secret is the same organization that owns `repository.full_name` (e.g. compare `repository_owner` against `payload.dig('repository', 'full_name')&.split('/')&.first`), and reject the request (422) on mismatch. Additionally, consider treating an unset `webhook_secret` as "reject" rather than "always verified" by default, or at minimum log/alert loudly when an organization is configured without one, since it silently disables all authenticity guarantees for that organization's webhooks.

### Proof of Concept
Assume Shipit is configured with two GitHub organizations, `attacker-org` (no `webhook_secret` set, or a secret known to the attacker) and `victim-org` (repository `victim-org/prod-app` tracked as a Shipit stack).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<omit or forge trivially if attacker-org has no secret>
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha, must exist on victim's real fork/mirror or be an existing valid sha for the branch>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/prod-app"
  }
}
```
- `verify_signature` calls `Shipit.github(organization: "attacker-org")` and either finds no `webhook_secret` (auto-verified) or is verified against a secret the attacker controls.
- `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/prod-app")`, entirely ignoring `attacker-org`, and enqueues `GithubSyncJob`/`sync_github` for the victim's stack — a write the attacker was never authorized to trigger.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

```yml

  github:

      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
