### Title
ERC20 XCM Asset Transactor credits fungible holding based on an attacker-controlled contract's return value, without verifying any real balance movement - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implement the XCM `TransactAsset` trait for ERC20 tokens deployed on Asset Hub via `pallet-revive`. [1](#0-0)  The `asset_id` (an `H160` contract address) used for each transfer is derived directly from the XCM `Asset` location supplied by the caller via `Matcher::matches_fungibles`, and per the PRDoc for this feature, any asset id of the form `AccountKey20 { key, network }` is matched, with `key` being an arbitrary contract address chosen by the user. [2](#0-1)  Both functions determine success purely by decoding the boolean return value of a `transfer()` call made to that attacker-chosen contract, never checking that the checking account's or beneficiary's ERC20 balance actually changed. [3](#0-2) [4](#0-3) 

This is the direct FRAME/XCM analog of the reported EVM bug: a caller (there, an NFT; here, an ERC20 "token" contract deployed by the attacker) is trusted to *say* a transfer happened (`onERC721Received` being callable / `transfer()` returning `true`) without the protocol *verifying* that the underlying asset actually moved.

### Finding Description
`withdraw_asset_with_surplus` is invoked by the XCM executor when processing a `WithdrawAsset` instruction whose `asset_id` resolves (via `ERC20Matcher`) to an arbitrary `H160` address embedded in the `Location` (`AccountKey20 { key, .. }`). [5](#0-4)  It calls `bare_call` to invoke `transfer(checkingAccount, amount)` on that address, signed by the withdrawing user, and if the call does not revert and the ABI-decoded return value is `true`, it unconditionally mints an `AssetsInHolding` credit of `amount` for that asset id:
```
if is_success {
    Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
}
``` [6](#0-5) 

Because `asset_id` is fully attacker-controlled (any deployed `pallet-revive` contract address the caller owns), the caller can deploy a trivial contract whose `transfer()` function always returns `true` (ABI-encoded `0x…01`) without moving any real balance and without reverting. Since `T::AddressMapper::to_address` / the `checking_address` passed to that call is also attacker-observable, a malicious contract can special-case the checking account to always succeed while doing nothing internally. `withdraw_asset_with_surplus` has no post-call check that the checking account's actual token balance increased by `amount` — the `Erc20Credit` imbalance type explicitly documents this: "does not perform runtime-level balance enforcement... the actual balance constraints are enforced by the ERC20 smart contract itself". [7](#0-6)  That assumption is false when the contract is attacker-controlled and adversarial — exactly the "malicious NFT contract can fake the transfer" scenario from the report, applied to `transfer()` return values instead of `onERC721Received`.

The symmetric bug exists in `deposit_asset_with_surplus`, which similarly trusts the return value of a `transfer()` call made from the checking account to the beneficiary contract, without verifying the beneficiary's balance actually increased. [4](#0-3) 

`ERC20Transactor` is registered as one of the `AssetTransactors` in the live Asset Hub Westend XCM configuration, reachable from any signed account via `pallet_xcm::execute` (self-executed XCM program with `WithdrawAsset`/`DepositAsset` instructions) or via ordinary XCM message execution. [8](#0-7)  No privileged origin, governance, or validator misbehavior is required — only deploying an ordinary EVM contract via `pallet-revive` and submitting a self-executed XCM program, both of which are permissionless operations available to any user.

### Impact Explanation
The XCM executor's holding abstraction (`AssetsInHolding`) is relied on throughout the executor as a faithful representation of value actually possessed by the chain on the user's behalf; every subsequent instruction (`DepositAsset`, `ExchangeAsset` via `AssetConversion`/`PoolAssetsExchanger`, fee payment, `Trader`) treats holding credits as real. Because `withdraw_asset_with_surplus` mints such a credit purely from an unverified boolean return value of an attacker-deployed contract, an attacker can fabricate holding credits for an "ERC20 asset" backed by nothing. `pallet_asset_conversion::create_pool`/`add_liquidity` accept arbitrary `Location`s as `AssetKind` (including `AccountKey20` ERC20 locations) as demonstrated by the AssetConversion configuration on Asset Hub Westend, where `AssetKind = xcm::v5::Location` and pools can be created between the native asset and any matched fungible asset. [9](#0-8)  This creates a laundering path: fabricate unbacked "ERC20" credit via the transactor bug, seed/inflate an AMM pool paired with a real asset (native WND or a trust-backed asset), then swap or remove liquidity to drain the real backing asset — i.e., unbacked issuance convertible into theft of real value from other pool participants. This matches the report's "Critical/High: unbacked issuance / theft" category rather than a purely cosmetic bug.

### Likelihood Explanation
High. The only prerequisites are: (1) ability to deploy a `pallet-revive` (EVM) contract — permissionless; (2) ability to submit a self-executed XCM program via `pallet_xcm::execute` referencing that contract's address as an `AccountKey20` asset id — permissionless and gas/fee-metered only; no validator, collator, or governance collusion is needed. The vulnerable code path is exercised on every `WithdrawAsset`/`DepositAsset` for ERC20-matched assets, and there is no defensive check anywhere in the call chain (executor, `ERC20Matcher`, or the transactor itself) that cross-validates the contract's on-chain storage/balance against the claimed `amount`.

### Recommendation
Before minting the `AssetsInHolding` credit in `withdraw_asset_with_surplus` (and before returning success in `deposit_asset_with_surplus`), read back the actual ERC20 `balanceOf` of the checking/beneficiary account (via an additional `bare_call` or a state read) and assert it changed by exactly `amount`, rather than trusting the `transfer()` return value alone. This mirrors the report's own recommendation to verify the NFT was actually received (e.g., checking `balanceOf`/ownership) before treating a lien as repaid, instead of trusting a callback/return flag that a malicious contract fully controls.

### Proof of Concept
A full concrete Rust/FRAME integration reproduction (deploying a malicious `transfer()`-always-`true` contract via `pallet-revive`, executing a self-signed XCM `WithdrawAsset`/`DepositAsset` program referencing it as `AccountKey20`, and asserting `AssetsInHolding` is credited with no real balance movement, followed by pool creation/liquidity drain) was **not executed** in this session — no filesystem/terminal access is available in this ask-only mode. The finding is based on static code inspection of `erc20_transactor.rs`, its registration in `AssetTransactors` on Asset Hub Westend, the `ERC20Matcher`/`AccountKey20` matching described in the feature's own PRDoc, and the `pallet_asset_conversion::Config` accepting arbitrary `Location` (including ERC20-matched) asset kinds for pool creation. This is a proof-of-concept design/logic gap identified through code review; a background Devin agent with repository and compiler access would be required to build and execute the described integration test to obtain concrete pass/fail evidence with attacker cost and before/after balance assertions.
