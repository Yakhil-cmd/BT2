### Title
Missing-webhook-secret bypasses signature verification, allowing forged `membership` events to mutate Team rosters - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` resolves the organization via `repository_owner`, which falls back to `params.dig('organization', 'login')` when no `repository` key is present, and hands it to `GitHubApp#verify_webhook_signature`. That method contains `return true unless webhook_secret`, so for any org configured without a `webhook_secret`, signature verification is a no-op and any unsigned POST to `/webhooks` is accepted and dispatched to handlers, including `MembershipHandler`, which mutates `Team`/`Membership` state.

### Finding Description
The broken binding: "every request that reaches a webhook handler is HMAC-authenticated against that organization's real `webhook_secret`" is claimed to hold, but in code:

- `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) accepts `params.dig('organization', 'login')` as a fallback with no requirement that a `repository` key exist — this is valid per GitHub's org-level event shape (e.g. `membership`), so an attacker can freely choose which org's `GithubApp`/config gets looked up simply by setting `organization.login` in the JSON body.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) does `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) starts with `return true unless webhook_secret`. If the resolved org's config has no `webhook_secret` set (`@webhook_secret = @config[:webhook_secret].presence`, line 50), verification always returns `true`, regardless of whether any `X-Hub-Signature` header was sent.
- `drop_unhandled_event` and `check_if_ping` do not block `membership` events since `MembershipHandler` is a registered handler for that event; `verify_signature` runs afterward and passes trivially.
- `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) then does `Team.find_or_create_by!(github_id: params.team.id)`, `User.find_or_create_by_login!(params.member.login)`, and `team.add_member(member)` / `team.members.delete(member)` — directly mutating team roster rows based entirely on unauthenticated attacker-controlled JSON.

Attacker request: `POST /webhooks` with header `X-Github-Event: membership`, no `X-Hub-Signature`, and body containing `organization.login` set to an org whose `Shipit::GithubHook` config has no `webhook_secret`, `team.id` equal to an id in `Shipit.github_teams` (an authorizing team), and `member.login` set to the attacker's own GitHub login, with `action: "added"`.

No existing guard intercepts this: `ExplicitParameters` schema only validates payload shape, not authenticity; `ApiClient`/session-based authorization (`current_user`, `require_permission!`) is not used on this controller at all; `verify_signature` is the only authenticity gate and it is bypassed by design when `webhook_secret` is unset.

### Impact Explanation
An attacker who forges this request causes the Shipit host to add their own (or any) GitHub login as a member of a `Team` whose `github_id` matches an entry in `Shipit.github_teams`. Since `Shipit.github_teams` controls authorization elevation (per `User#authorized?` / team-membership-based access checks referenced in `app/models/shipit/user.rb`), this is a direct escalation into `Shipit.github_teams` authorization — matching the High severity bucket ("escalation into `Shipit.github_teams` authorization") at minimum, and could enable further Critical actions (unauthorized deploys/merges) once elevated. This is repeatable for every organization configured in `Shipit.github_teams`/`GithubHook` without a `webhook_secret`, and does not require attacking any specific repository — only the target org's login string, which is public knowledge.

### Likelihood Explanation
This requires only that the host application's Shipit installation has at least one organization's `GithubHook` config with `webhook_secret` unset — a state explicitly permitted by the code (`@webhook_secret = @config[:webhook_secret].presence`, treating blank/nil as "no secret configured") and by the setup docs, which show `webhook_secret` as a configurable-but-optional field. No secret, token, or session is needed by the attacker; only network access to `POST /webhooks`. This is a real, low-cost, and repeatable misconfiguration-triggered bypass, not a theoretical one, given the fallback in `repository_owner` and the `return true unless webhook_secret` short-circuit are unconditional engine code.

### Recommendation
Do not silently trust unsigned webhooks. Options: require `webhook_secret` to be present for every configured organization (fail closed if missing rather than returning `true`), or explicitly reject events where `X-Hub-Signature` is absent, or restrict `repository_owner`'s organization fallback and require operators to configure secrets for any org enabled for `membership`/team-mutating events. At minimum, change `verify_webhook_signature` to return `false` (not `true`) when `webhook_secret` is blank, and treat "no secret configured" as a deployment error surfaced at boot/config-validation time rather than a runtime bypass.

### Proof of Concept
```ruby
# test/lib/shipit/github_app_test.rb (conceptual)
test "verify_webhook_signature returns true with no secret configured, and no signature header" do
  app = Shipit::GitHubApp.new('acme-org', { webhook_secret: nil })
  assert_equal true, app.verify_webhook_signature(nil, '{"any":"payload"}')
end

# test/controllers/webhooks_controller_test.rb (conceptual)
test "membership event mutates Team without any signature when org has no webhook_secret" do
  Shipit.github_app_config_stub('acme-org', webhook_secret: nil) # org configured without secret
  team = teams(:some_authorizing_team) # github_id in Shipit.github_teams

  assert_difference -> { team.reload.members.count }, 1 do
    post :create, params: {
      action: 'added',
      team: { id: team.github_id, name: team.name, slug: team.slug, url: 'https://api.github.com/teams/1' },
      organization: { login: 'acme-org' },
      member: { login: 'attacker' }
    }.to_json, headers: { 'X-Github-Event' => 'membership' } # deliberately NO X-Hub-Signature
  end

  assert team.reload.members.exists?(login: 'attacker')
end
```
Both sides of the binding — "handler executed" vs "request cryptographically authenticated" — diverge: the handler runs and mutates state (`true`) while authentication never occurred (`false`), confirming the bypass.
