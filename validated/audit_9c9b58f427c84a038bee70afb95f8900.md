### Title
Block-Revenue-Sharing reward calculation reads `pending_delegator_rewards` without ever decrementing it or debiting the vote account, causing the same deposited rewards to be minted/duplicated to stakers every epoch - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs, runtime/src/bank/partitioned_epoch_rewards/distribution.rs)

### Summary
This is the same bug class as the reported `ClaimFees` issue: a reward-distribution routine derives the amount to pay out from a value that represents an *accumulated pool* rather than an explicitly reconciled delta, and never clears/reduces that pool or the account holding the underlying lamports after paying it out. In `GaugeCL`, the pool was "whatever balance sits in the contract," and it was swept in full every call. In Agave's SIMD-0123 block-revenue-sharing path, the pool is the vote account's `pending_delegator_rewards` counter (funded via the permissionless `DepositDelegatorRewards` instruction), and `calculate_block_reward` reads it every epoch to compute each stake account's share, but the codebase gives no evidence that this counter, or the vote account's lamport balance that backs it, is ever reduced after distribution.

### Finding Description
`DepositDelegatorRewards` lets anyone transfer lamports into a vote account and increments `VoteStateV4::pending_delegator_rewards` by the deposited amount via `add_pending_delegator_rewards`: [1](#0-0) [2](#0-1) 

At every epoch's reward calculation, `calculate_block_reward` reads `vote_state.pending_delegator_rewards()` and computes each delegated stake's pro-rata share of that *entire* pending value (clamped to `pending_delegator_rewards`, not to any per-epoch delta): [3](#0-2) 

This value is then minted straight into each stake account's lamports via `checked_add_lamports` in `build_updated_stake_reward`/`store_stake_accounts_in_partition`: [4](#0-3) [5](#0-4) 

Critically, `distribute_epoch_rewards_in_partition` only adjusts capitalization for `stake_reward_lamports_minted` (inflation) and `block_reward_lamports_burned`; it never subtracts `block_reward_lamports_distributed` from capitalization, nor does any code path shown debit the *vote account's* lamports by the amount just paid to stakers, nor reset/decrement `pending_delegator_rewards`: [6](#0-5) 

Across the full search of the reward-calculation and reward-distribution code (`calculation.rs`, `distribution.rs`, `sysvar.rs`, `vote_state/mod.rs`, `vote_state/handler.rs`), no function that clears, decrements, or otherwise reconciles `pending_delegator_rewards` against the amount actually paid out was found, and no code debits the vote account's lamport balance when block rewards are minted into stake accounts. This mirrors the `GaugeCL._claimFees` root cause exactly: the payout amount is derived from a stale/cumulative counter (analogous to "whole token balance") rather than a value that is reconciled to zero (or reduced by the exact amount distributed) once it is consumed, so the same underlying funds get paid out again in the next epoch's calculation.

### Impact Explanation
If `pending_delegator_rewards` is not decremented after being distributed as `block_reward`, every subsequent epoch's `calculate_block_reward` call will again see the (undiminished) pending amount and mint the same lamports into stakers' accounts a second, third, ... time — each time incrementing stake-account lamports without any matching capitalization decrease or vote-account debit. This is a direct case of duplicated/misattributed reward minting: lamports are created out of nothing relative to the bank's capitalization accounting, silently inflating the supply and corrupting the guarantee that `capitalization` tracks total lamports in the system. It also breaks the vote-account's economics, since the delegator who deposited the funds expected them consumed once, not repeatedly redistributed while the underlying deposit sits untouched.

### Likelihood Explanation
Reachability requires only unprivileged, permissionless actions: (1) anyone can call `DepositDelegatorRewards` to fund `pending_delegator_rewards`, and (2) `block_revenue_sharing` reward calculation runs automatically every epoch for any bank with the feature enabled — no privileged/validator role is required to trigger the repeated distribution once the initial deposit is made. Every epoch boundary is a trigger point.

### Recommendation
`calculate_block_reward`/the distribution path must reconcile `pending_delegator_rewards` against what is actually paid out: after computing and minting `block_reward` for each stake account in a partition, the aggregated `block_reward_lamports_distributed` (and `_burned`) for a given vote account must be subtracted from that vote account's `pending_delegator_rewards` field, and the vote account's lamports balance must be debited by the same amount (mirroring the recommended fix in the source report: compute the amount paid as an explicit, reconciled delta and immediately consume/zero that delta from the source of funds, rather than re-reading a stale accumulator on every distribution cycle).

### Proof of Concept
Conceptual reproduction (cannot be executed here, but derivable from the cited code paths):
1. Attacker/delegator calls `DepositDelegatorRewards` to deposit `D` lamports into a validator's vote account, setting `pending_delegator_rewards = D`. [7](#0-6) 
2. At epoch N's reward calculation, `calculate_block_reward` computes each delegator's share of `D` and mints it into their stake accounts via `checked_add_lamports`. [8](#0-7) [4](#0-3) 
3. Absent any code that resets/decrements `pending_delegator_rewards` or debits the vote account, at epoch N+1's reward calculation the same `pending_delegator_rewards = D` value is read again by `calculate_block_reward`, and the same `D` lamports are minted a second time into stake accounts — with capitalization accounting (`distribute_epoch_rewards_in_partition`) never subtracting the distributed block reward, compounding the duplication every epoch. [9](#0-8) 

Note: because the index available to this analysis may not include every file in the reward pipeline, it is possible a reconciliation/decrement step exists elsewhere that was not located by search; this should be explicitly verified by a Devin session with full repository access before treating this as a confirmed exploit rather than a strong analog finding.

```rust
/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
```

```rust
/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
```

```rust
    /// Process reward credits for a partition of rewards
    /// Store the rewards to AccountsDB, update reward history record and total capitalization.
    fn distribute_epoch_rewards_in_partition(
        &self,
        partition_rewards: &StartBlockHeightAndPartitionedRewards,
        partition_index: u64,
    ) {
        let pre_capitalization = self.capitalization();
        let (
            DistributionResults {
                stake_reward_lamports_minted,
                stake_reward_lamports_burned,
                block_reward_lamports_distributed,
                block_reward_lamports_burned,
                updated_stake_rewards,
            },
            store_stake_accounts_us,
        ) = measure_us!(self.store_stake_accounts_in_partition(partition_rewards, partition_index));

        // increase total capitalization by the distributed rewards
        self.capitalization
            .fetch_add(stake_reward_lamports_minted, Relaxed);

        // decrease total capitalization by burned block rewards
        self.capitalization
            .fetch_sub(block_reward_lamports_burned, Relaxed);

        // decrease distributed capital from epoch rewards sysvar
        self.update_epoch_rewards_sysvar(
            stake_reward_lamports_minted + stake_reward_lamports_burned,
            block_reward_lamports_distributed + block_reward_lamports_burned,
        );

        // update reward history for this partitioned distribution
        self.update_reward_history_in_partition(&updated_stake_rewards);

        let metrics = RewardsStoreMetrics {
            pre_capitalization,
            post_capitalization: self.capitalization(),
            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),
            partition_index,
            store_stake_accounts_us,
            store_stake_accounts_count: updated_stake_rewards.len(),
            distributed_rewards: stake_reward_lamports_minted,
            burned_rewards: stake_reward_lamports_burned,
            distributed_block_rewards: block_reward_lamports_distributed,
            burned_block_rewards: block_reward_lamports_burned,
        };

        report_partitioned_reward_metrics(self, metrics);
    }
```
