### Title
Uncaught TypeError in address definition `'in merkle'` evaluation due to missing type validation of attacker-supplied authentifier - (File: `definition.js`)

### Summary
The `metadata-extractor` advisory describes a library that throws various uncaught exceptions while parsing crafted, attacker-controlled input, crashing the consuming application (CWE-755, improper handling of exceptional conditions). The analogous pattern exists in ocore's address-definition evaluator: the `'in merkle'` definition opcode passes an attacker-supplied authentifier value directly into `merkle.deserializeMerkleProof()` without first validating that the value is a string, unlike the equivalent, better-guarded `is_valid_merkle_proof` oscript opcode used by AAs.

### Finding Description
In `definition.js`, the `'in merkle'` case of the address-definition evaluator (used when validating the authentifiers of a posted unit) does: [1](#0-0) 

```
case 'in merkle':
    if (!assocAuthentifiers[path])
        return cb2(false);
    ...
    var serialized_proof = assocAuthentifiers[path];
    var proof = merkle.deserializeMerkleProof(serialized_proof);
    if (!merkle.verifyMerkleProof(element, proof)){
```

The only check performed on `assocAuthentifiers[path]` is a truthiness check (`if (!assocAuthentifiers[path]) ...`), which does not exclude non-string values such as objects, arrays, or numbers. `serialized_proof` is then handed straight to `merkle.deserializeMerkleProof`: [2](#0-1) 

```
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	...
}
```

If `serialized_proof` is not a string (e.g. it is an object or array, since authentifiers in a unit's `authors[].authentifiers` map are attacker-controlled JSON values and this branch is reached before any string-type enforcement on this specific value), `.split` does not exist on the value and a `TypeError` is thrown. Neither `deserializeMerkleProof` nor its caller in `definition.js` wraps this call in a `try/catch`, so the exception propagates up through the definition-evaluation callback chain uncaught.

This differs from the equivalent AA-oscript `is_valid_merkle_proof` handler in `formula/evaluation.js`, which explicitly checks `typeof proof === 'string'` before calling `merkle.deserializeMerkleProof`, and wraps the follow-on `verifyMerkleProof` call in `try/catch`: [3](#0-2) 

The lack of an equivalent type guard/try-catch in the address-definition path (`definition.js`) is the root-cause asymmetry that reproduces the "uncaught exception on crafted input" bug class described in the advisory.

### Impact Explanation
An address that includes an `'in merkle'` clause in its definition is a legitimate, commonly reachable construct (data-feed/merkle-proof based conditions). Any unprivileged unit poster who controls (or colludes with) an author of such an address, or crafts a unit whose author list references such a definition with a malformed (non-string) authentifier value at the corresponding signing path, can trigger `deserializeMerkleProof` to throw a `TypeError` that is not caught anywhere in the `validateAuthentifiers` → `evaluate` call chain in `definition.js`. Because this code runs during unit validation on every node that processes the posted unit, an uncaught exception here can crash or destabilize the validating node process, preventing that node (and potentially the wider network if broadcast widely) from validating/confirming the unit and subsequent units — a denial-of-service on unit validation.

### Likelihood Explanation
Reaching this code requires an address with an `'in merkle'` clause in its definition and a unit specifying a non-string authentifier value for the corresponding path. This is a narrow but realistic precondition: an attacker who defines such an address (or is one of the signers) can craft the authentifier payload freely, since authentifiers are user/attacker-supplied JSON in the posted unit and only checked for truthiness here, not for type. No special network position, hub, or peer privilege is needed — a single posted unit suffices.

### Recommendation
Add an explicit type check (`typeof serialized_proof === 'string'`) before calling `merkle.deserializeMerkleProof` in the `'in merkle'` case of `definition.js`, returning `cb2(false)` (or setting a validation error) for non-string values, mirroring the guard already present in `formula/evaluation.js`'s `is_valid_merkle_proof` handler. Additionally, wrap the `deserializeMerkleProof`/`verifyMerkleProof` sequence in `definition.js` in a `try/catch` as defense-in-depth, consistent with other exception-prone parsing paths in the codebase (e.g. `chash.js:isChashValid`, `signature.js:verify`).

### Proof of Concept
1. Create/define an address whose definition includes an `'in merkle'` clause, e.g. `['in merkle', [[<oracle_address>], 'feed_name', 'element']]`, and register it as `my_address`/`shared_address` normally.
2. Construct a unit authored by that address where `authors[0].authentifiers[<path>]` is set to a non-string value (e.g. an array `["x","y"]` or an object `{}`) instead of the expected dash-separated proof string.
3. Submit the unit for validation (post it to a node). During `validateAuthentifiers` in `definition.js`, the `'in merkle'` branch is reached, `assocAuthentifiers[path]` is truthy (an array/object), and `merkle.deserializeMerkleProof(serialized_proof)` executes `serialized_proof.split("-")`, throwing an uncaught `TypeError` inside the evaluation callback chain, which is not caught by any surrounding `try/catch` in this path — an exact analog of the metadata-extractor crash-on-malformed-input CWE-755 issue.

Note: I was not able to fully trace, within the available search iterations, whether an earlier stage of `validation.js`/`validateAuthentifiers` enforces that every entry in `authentifiers` must already be a string before this evaluate call is reached for the `'in merkle'` path specifically. If such a blanket string-type check exists upstream and covers this exact value, the practical exploitability of this specific finding would be reduced; this should be verified against the full `validation.js`/`definition.js` authentifier-validation logic.
