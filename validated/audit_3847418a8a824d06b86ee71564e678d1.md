Based on my review of the webhook signature verification flow, I found a valid analog: the controller selects **which** GitHub App configuration (and thus which HMAC secret) to verify a webhook against using an **unauthenticated field taken directly from the request body**, and this selection is never re-checked against the data the resulting handlers actually act on.

### Title
Webhook signature verification key is selected from an unauthenticated payload field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization (and therefore the HMAC secret used to validate `X-Hub-Signature`) from `repository_owner`, which is read straight out of the untrusted JSON body before the signature is checked. Because the same JSON body also contains `repository.full_name` — the field every downstream webhook handler actually uses to locate the `Repository`/`Stack` to mutate — an attacker who legitimately controls (and knows the `webhook_secret` of) *any one* organization configured on a multi-tenant Shipit instance can sign a forged payload with a mismatched `repository.owner.login` and `repository.full_name`, and have it accepted as authentic for a completely different, victim organization's repository.

### Finding Description
The verification logic is: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves the `GitHubApp` instance (and thus `webhook_secret`) keyed by that attacker-supplied string, as shown by the multi-org configuration Shipit natively supports: [3](#0-2) 

The verification itself only checks that the signature was produced with *that selected org's* secret: [4](#0-3) 

Once `head(422)` is not triggered, the entire raw JSON `params` — including `repository.full_name`, which is a **different** field from the one used to pick the verification key — is dispatched unmodified to every registered handler: [5](#0-4) 

The binding that should hold is:
`organization whose secret authenticated the signature == organization owning the repository the handlers write to`

Because `repository_owner` (used to pick the key) and `repository.full_name` (used by handlers to find/create the `Repository`/`Stack`/`Commit`/`Team`/`Membership` records) are two independently-controlled fields inside the same unauthenticated JSON body, an attacker can set them inconsistently. If the attacker is an authorized operator/admin of Org A (and thus legitimately knows Org A's `webhook_secret`, e.g. from their own GitHub App settings), they can:
1. Set `repository.owner.login` (or `organization.login`) to `"org-a"` so `Shipit.github(organization: "org-a")` selects the secret they know.
2. Compute a valid `X-Hub-Signature` over the raw body using Org A's secret.
3. Set `repository.full_name` (and any other repository-identifying fields used by handlers) to `"org-b/victim-repo"`.

The controller only checks that the payload was signed by *someone* holding Org A's secret — it never confirms that Org A actually owns the repository named inside the payload that the handlers subsequently act on.

### Impact Explanation
This breaks the deployment-trust binding described by the prompt's "organization authenticated vs. repository written" category. Depending on which event type is forged, the impact ranges from unauthorized state changes to security-relevant automation triggers:
- `status` events can flip a victim commit's CI status to `success`, which `Commit#deployable?`/continuous delivery logic relies upon to decide whether a commit is safe to auto-deploy — enabling an **unauthorized deploy** on the victim's stack.
- `push` events can enqueue `GithubSyncJob` for an arbitrary victim stack ID, forcing a resync from data the attacker controls indirectly through the crafted payload.
- `membership` events create/modify `Team`/`User`/`Membership` records for a victim organization's team, which feeds directly into `Shipit.github_teams` authorization checks in `Shipit::Authentication#force_github_authentication`. [6](#0-5) [7](#0-6) 

Forging membership data could let an attacker escalate into `Shipit.github_teams` authorization for a stack they shouldn't have access to, matching the High-severity "escalation into `Shipit.github_teams` authorization" category, and the status/push forgery path matches the Critical "unauthorized deploy" category.

### Likelihood Explanation
This requires:
- Shipit configured for multiple GitHub organizations (an explicitly documented, supported configuration — see `config/secrets.development.shopify.yml`).
- The attacker legitimately administering/operating at least one of those organizations' GitHub Apps (so they know that org's own `webhook_secret`) — this is not privileged access to the *victim* org, satisfying the "unprivileged attacker" requirement relative to the target.
- No GitHub App private key, `api_clients_secret`, Shipit session, or repository write access to the victim repo is needed at all — only knowledge of one tenant's own webhook secret, which that tenant necessarily possesses to operate their own integration.

### Recommendation
- After signature verification succeeds for organization `X`, cross-check that every repository-identifying field used downstream (`repository.full_name`, `repository.owner.login`) actually belongs to organization `X` before dispatching to handlers, or reject payloads where `repository.owner.login`/`organization.login` doesn't match the owner segment of `repository.full_name`.
- Alternatively, look up the target `Stack`/`Repository` first (from `repository.full_name`), derive its associated organization, and use *that* organization's secret to verify the signature, rather than trusting the `repository.owner.login`/`organization.login` field emitted by the sender.

### Proof of Concept
1. Attacker operates a GitHub App installed on `org-a`, which is one of the organizations configured in this Shipit instance's `github:` config (multi-org setup), and thus knows `org-a`'s `webhook_secret`.
2. Attacker crafts a JSON body for a `status` (or `push`/`membership`) event:
   ```json
   {
     "organization": { "login": "org-a" },
     "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-b" } },
     "sha": "<victim commit sha>",
     "state": "success",
     ...
   }
   ```
   (Depending on handler, only `repository.owner.login` needs to say `org-a` for key selection; `repository.full_name` can point at the victim repo for the handler logic — the exact field precedence is defined in `repository_owner`, which prefers `repository.owner.login` and falls back to `organization.login`.)
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and sends the POST to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")`, verifies the signature against `org-a`'s secret, and succeeds — even though the payload's `repository.full_name` refers to `org-b`'s repository.
5. The `status` handler processes the forged payload against `org-b/victim-repo`'s commit, marking it with a fabricated CI status, potentially triggering continuous deployment for `org-b`'s stack. [8](#0-7)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
