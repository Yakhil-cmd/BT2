### Title
Global `Commit.where(sha:)` lookup in `StatusHandler#process` writes GitHub status data without repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table and calls `commit.create_status_from_github!(params)` on every match, without ever invoking `Handler#stacks` or `repository_name` to restrict the write to the repository that emitted the webhook. This differs structurally from `PushHandler#process`, which scopes mutations through `stacks.not_archived.where(branch:)`.

### Finding Description
The binding that should hold, mirroring `PushHandler`, is:
`StatusHandler#process` mutated rows ⊆ `Handler#stacks` (i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`).

Tracing the code:
- `StatusHandler#process` at [1](#0-0)  does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. It never calls `stacks` or `repository_name`.
- `PushHandler#process` at [2](#0-1)  explicitly scopes via `stacks.not_archived.where(branch:)`.
- `Handler#stacks`/`repository_name` are defined at [3](#0-2) , and `StatusHandler` never references either, confirmed by reading the full file — the `params` block only declares `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches`, none of which are `repository`-scoped [4](#0-3) .
- `Commit#create_status_from_github!` calls `add_status` which appends to `statuses` and triggers `Hook.emit` and merge scheduling on the commit's own `stack` [5](#0-4) , [6](#0-5) . The `commits` table has no per-request repository filter anywhere in this path — `sha` is not scoped to a stack in the query.

Root cause: git commit SHAs are content-addressed but not guaranteed globally unique across independent repositories tracked by different Shipit stacks — most importantly, forks and repositories sharing history (cherry-picks, common upstream commits, or repositories that were forked and later diverged into different Shipit-tracked stacks) will have identical SHAs for the shared commits. An attacker who controls a repository (fork) that shares one or more commits with a victim repository's tracked stack can send a `status` webhook (`POST /webhooks`) naming their own repository in `payload['repository']['full_name']` but with a `sha` value that also exists on the victim's stack. `StatusHandler` never checks `payload['repository']`, so `Commit.where(sha: params.sha)` matches the victim's `Commit` row too, and the attacker's crafted `state`/`context`/`description`/`target_url` get written as a `Status` on the victim's commit, potentially flipping `deployable?`/`blocked?` semantics and triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`.

This is not prevented by any existing guard: `verify_signature`/`GitHubApp#verify_webhook_signature` (out of scope here per audit, but even so) authenticates that *some* registered app sent the payload, not that the `repository` field matches the commit's owning stack; `ExplicitParameters` only validates field *types*, not repository ownership; `drop_unhandled_event` only filters unhandled event types.

### Impact Explanation
An attacker controlling any repository that shares commit history with a targeted Shipit-tracked repository (e.g., a fork) can write arbitrary GitHub `Status` records (state, context, description, target_url) onto the victim stack's commits without ever authenticating against that stack. This can influence deploy-gating logic (`deployable?`, `blocked?`, `schedule_merges`) and constitutes a payload for one repository mutating another's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker must be able to name a repository containing a commit whose SHA also exists in the victim's tracked stack (trivial via forking, since forks initially share full commit history) and must be able to send a `status` webhook event to the Shipit host for their own repository (or any endpoint reachable as an unprivileged webhook sender). No Shipit session, API token, or webhook secret for the *victim* repository is required — only the ability to trigger/craft a `status` event, which is achievable for any repository the attacker owns via GitHub's normal status API/webhooks, or by directly POSTing to `/webhooks` if signature verification for the attacker's own registered app succeeds for their own repo. Repeatable against any victim stack that shares any commit SHA with an attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` through `stacks` like `PushHandler` does, e.g. restrict the `Commit` lookup to commits belonging to stacks resolved from `payload.dig('repository','full_name')`: `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalent join), so a status payload can only mutate commits belonging to the reporting repository's own stacks.

### Proof of Concept
```ruby
test "StatusHandler#process never scopes writes through Handler#stacks" do
  handler_class = Shipit::Webhooks::Handlers::StatusHandler
  payload = {
    'sha' => shipit_commits(:shipit_first).sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }

  handler = handler_class.new(payload)

  # Binding under test: process mutations must be ⊆ Handler#stacks scoped to repository_name
  handler.define_singleton_method(:stacks) { raise "stacks should have been called" }

  assert_nothing_raised do
    handler.process
  end
  # process succeeded WITHOUT ever calling stacks/repository_name,
  # proving no repository-scoping invariant is enforced.
end
```
This demonstrates that `StatusHandler#process` can write a `Status` onto a commit belonging to a stack unrelated to `payload['repository']['full_name']`, because `stacks`/`repository_name` are structurally absent from its code path.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
