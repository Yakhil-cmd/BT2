### Title
Unchecked `.unwrap()` on Token-2022 transfer-fee calculations causes on-chain panic and can permanently freeze pool funds - (File: `programs/cp-swap/src/utils/token.rs`)

### Summary
`get_transfer_fee` and `get_transfer_inverse_fee` in `programs/cp-swap/src/utils/token.rs` compute Token-2022 `TransferFeeConfig` fee amounts and `.unwrap()` the `Option<u64>` results returned by the SPL Token-2022 extension's `calculate_epoch_fee` / `calculate_inverse_epoch_fee`, instead of propagating an error. These functions are invoked unconditionally in `swap_base_input`, `swap_base_output`, `deposit`, and `withdraw` with attacker-influenced mint/amount data, so a crafted Token-2022 mint (freely creatable by any pool creator) combined with certain amounts can drive the fee calculation to return `None`, causing the on-chain program to panic instead of returning a graceful error.

### Finding Description
`get_transfer_inverse_fee` and `get_transfer_fee` unpack the mint's `TransferFeeConfig` extension and blindly `.unwrap()` the calculation results: [1](#0-0) [2](#0-1) 

These helpers are reached directly from swapper- and LP-facing instructions with attacker-chosen `input_token_mint` / `output_token_mint` accounts and attacker-chosen amounts: [3](#0-2) [4](#0-3) 

`deposit.rs` and `withdraw.rs` similarly call these helpers on the pool's fixed `token_0_mint`/`token_1_mint` (per grep matches in those files), meaning once a pool is created with a Token-2022 mint whose `TransferFeeConfig` and combined amounts push the internal fee math to overflow/return `None`, *every* subsequent `deposit`, `withdraw`, or `swap` touching that mint will panic rather than fail gracefully.

This mirrors the GnuTLS CVE-2024-28835 bug class: a specially crafted input (a `.pem` bundle there, a crafted Token-2022 mint extension config here) drives the "verification"/calculation logic into an unhandled panic path instead of returning a controlled error.

### Impact Explanation
Because `deposit`/`withdraw` share the same unguarded `.unwrap()` path as `swap`, a pool whose associated Token-2022 mint (freely chosen by the permissionless `initialize`/`initialize_with_permission` caller) triggers this condition becomes unable to process withdrawals for the affected token, permanently trapping LP funds in the vault — this is a fund-freezing condition rather than a mere availability blip, matching the required "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Any unprivileged user can create a pool with `initialize`/`initialize_with_permission` using a Token-2022 mint they control and configure its `TransferFeeConfig` extension arbitrarily (basis points and maximum fee), then choose amounts in swap/deposit/withdraw calls that drive the internal fee arithmetic in `calculate_epoch_fee`/`calculate_inverse_epoch_fee` past its safe range. No privileged signer or off-chain component is required — a single crafted transaction with attacker-chosen accounts and data is sufficient to reach the panic.

### Recommendation
Replace the `.unwrap()` calls in `get_transfer_fee` and `get_transfer_inverse_fee` with proper error propagation (e.g., `.ok_or(ErrorCode::TransferFeeCalculateNotMatch)?` or a dedicated overflow error), so malformed/edge-case `TransferFeeConfig` values return a controlled Anchor error instead of panicking, and add validation at pool-initialization time to reject mints whose extension configuration can cause the fee math to overflow at realistic amounts.

### Proof of Concept
1. Create a Token-2022 mint with the `TransferFeeConfig` extension configured with values (basis points/maximum fee) chosen to make `calculate_epoch_fee`/`calculate_inverse_epoch_fee` return `None` for some valid `u64` amount (per spl-token-2022's documented overflow conditions in its fee math).
2. Call `initialize`/`initialize_with_permission` to create a pool using this mint as `token_0_mint`/`token_1_mint`.
3. Call `deposit`, `withdraw`, `swap_base_input`, or `swap_base_output` with an amount that triggers the `None` case.
4. Observe the transaction panics inside `get_transfer_fee`/`get_transfer_inverse_fee` (`programs/cp-swap/src/utils/token.rs`) instead of returning a handled `Result::Err`, and that this reproduces for every subsequent `withdraw` attempt on that pool, permanently trapping deposited funds.
