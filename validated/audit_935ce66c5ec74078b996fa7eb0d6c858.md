### Title
No Recovery Mechanism for KLAY Permanently Locked in Source Bridge When Destination Recipient Rejects KLAY — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` delivers KLAY to `_to` via a low-level `.call.value()`. If `_to` is a contract without a payable fallback, the call always reverts, operators can never successfully settle the nonce, and the user's KLAY deposited in the source bridge is permanently locked with no refund path.

---

### Finding Description

When a user initiates a cross-chain KLAY transfer, `_requestKLAYTransfer` accepts `msg.value` into the source bridge contract and emits `RequestValueTransfer`. The KLAY is held by the source bridge for the lifetime of the request. [1](#0-0) 

On the destination chain, operators call `handleKLAYTransfer`, which delivers KLAY to `_to` using:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [2](#0-1) 

If `_to` is a contract without a `payable` fallback (e.g., a multisig, DAO treasury, or any non-payable contract), `ok` is `false` and the `require` reverts the entire transaction. Because Solidity reverts all state changes on failure, `closedValueTransferVotes[_requestNonce]` is also rolled back, so operators can retry — but every retry will fail identically. [3](#0-2) 

The `valueTransferRecovery` subsystem (`vt_recovery.go`) only re-submits the same `handleKLAYTransfer` call; it does not provide a refund path. [4](#0-3) 

No function in any bridge contract (`BridgeTransferKLAY`, `BridgeTransfer`, `BridgeHandledRequests`, `BridgeFee`, `BridgeTokens`) allows the owner or user to withdraw KLAY that was deposited into the source bridge for a stuck request.



---

### Impact Explanation

The user's KLAY is held in the source bridge from the moment `_requestKLAYTransfer` executes. There is no `sweepToken`, `fallbackWithdraw`, or equivalent function to return it. The KLAY is permanently unrecoverable: operators cannot deliver it (destination always reverts), and no on-chain path exists to refund the source-side deposit.

**Corrupted value**: the user's KLAY balance — deposited into the source bridge — is irrecoverably lost.

---

### Likelihood Explanation

Any user who specifies a contract address as `_to` that lacks a `payable` fallback triggers this condition. Common real-world examples include multisig wallets deployed without a receive function, governance contracts, and protocol treasuries. The user has no on-chain warning before submitting the request.

---

### Recommendation

1. **Add a `fallbackWithdraw` / `sweepKLAY` function** (owner-controlled) on the source bridge to return locked KLAY to the original sender when the corresponding destination nonce is provably undeliverable.
2. **Alternatively**, record the original `_from` address in the source bridge alongside the locked amount, and allow the user to reclaim it after a timeout or after operators signal failure.
3. Mirror the fix applied to XVS (`sweepToken` + admin flag) adapted for KLAY: add an owner-callable function that can redirect a stuck nonce's KLAY to an alternate address.

---

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.5.6;

// Deployed on destination chain — no payable fallback
contract NonPayableRecipient {
    // No receive() or fallback() payable
}
```

**Steps:**

1. Deploy `NonPayableRecipient` on the destination chain.
2. On the source chain, call:
   ```solidity
   sourceBridge.requestKLAYTransfer{value: 1 ether}(
       nonPayableRecipient, // _to
       1 ether,             // _value
       ""
   );
   ```
   Source bridge now holds `1 ether`. `RequestValueTransfer` is emitted with `_to = nonPayableRecipient`.
3. Operators call `handleKLAYTransfer` on the destination bridge with `_to = nonPayableRecipient`.
4. `_to.call.value(1 ether)("")` returns `ok = false` → `require` reverts.
5. Operators retry indefinitely; every attempt reverts.
6. The `1 ether` in the source bridge has no on-chain recovery path. [5](#0-4) [1](#0-0)

    // _requestKLAYTransfer requests transfer KLAY to _to on relative chain.
    function _requestKLAYTransfer(address _to, uint256 _feeLimit,  bytes memory _extraData)
        internal
        unlockedKLAY
        nonReentrant
    {
        require(isRunning, "stopped bridge");
        require(msg.value > _feeLimit, "insufficient amount");

        uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);

        emit RequestValueTransfer(
            TokenType.KLAY,
            msg.sender,
            _to,
            address(0),
            msg.value.sub(_feeLimit),
            requestNonce,
            fee,
            _extraData
        );
        requestNonce++;
    }

// recoverPendingEvents recovers all pending events by resending them.
func (vtr *valueTransferRecovery) recoverPendingEvents() error {
	defer func() {
		vtr.childEvents = []IRequestValueTransferEvent{}
		vtr.parentEvents = []IRequestValueTransferEvent{}
	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))
	}

	vtRequestEventMeter.Mark(int64(len(vtr.childEvents)))
	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))
	for i, event := range vtr.childEvents {
		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))
	}

	vtHandleEventMeter.Mark(int64(len(vtr.parentEvents)))
	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))
	for i, event := range vtr.parentEvents {
		events[i] = event
	}
	vtr.cBridgeInfo.AddRequestValueTransferEvents(events)

	return nil
