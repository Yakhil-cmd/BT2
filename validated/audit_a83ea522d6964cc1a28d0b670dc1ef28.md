### Title
Malicious swap routes can attach arbitrary caller-authorized token transfers - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary
`swap_collateral` accepts caller-controlled route bytes and executes them through the configured router. Although the controller narrowly authorizes only the controller’s own input-token transfer, route-selected third-party code can request additional authorization from the original caller. If the user signs the simulated authorization tree containing that hidden child invocation, the route contract can transfer unrelated wallet tokens to an attacker while the lending operation still produces valid collateral output. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`process_swap_collateral` authenticates `caller` and requires the caller to be the account owner or an active delegate, after which it sends the caller-supplied `swap` bytes to `withdraw_and_swap_from_supply`. [4](#0-3) 

The generic swap helper authorizes only `token_in.transfer(controller, configured_router, amount_in)` on behalf of the controller and then invokes `router.execute_strategy(controller, amount_in, swap)`. [5](#0-4)  That narrow controller authorization protects the routed lending input, but it does not constrain authorization requests made to the original `caller` by contracts reached through the route. [6](#0-5) 

The focused test demonstrates the resulting behavior: a router invokes a payload-selected hop pool, and that pool calls `token.transfer(victim, attacker, amount)` for an unrelated token. [7](#0-6) [8](#0-7)  During simulation, the transfer is recorded as a child of Alice’s `swap_collateral` authorization; enforcing mode succeeds only when Alice signs a tree containing that child, after which her unrelated wallet balance is transferred to the attacker. [9](#0-8) [10](#0-9) 

### Impact Explanation
A successful route can steal assets that were never supplied to XOXNO Lending and are unrelated to the requested swap. [11](#0-10)  The lending operation can still deposit the expected output and pass its account checks, so the wallet-token theft is not bounded by `amount`, `new`, collateral value, minimum output, or the final solvency checks. [12](#0-11) [6](#0-5) 

### Likelihood Explanation
Exploitation requires the victim to execute a malicious route and sign an authorization tree containing the unexpected token transfer. [13](#0-12)  The attack is realistic for opaque route payloads because the caller controls only the serialized `swap` bytes while route-selected pool and token addresses are not constrained by the controller’s measured input/output checks. [14](#0-13) [6](#0-5)  A correctly implemented client that displays and rejects unexpected authorization children prevents the theft, which limits likelihood but leaves the reachable loss critical when signing fails to enforce that check. [15](#0-14) 

### Recommendation
Prevent arbitrary route-selected contracts from executing beneath an account owner’s or delegate’s authorization. [4](#0-3)  Practically, constrain `StrategySwap` execution to an allowlisted set of audited venues, or change the integration so user strategies interact only with a router implementation that cannot invoke caller-supplied pool addresses under the caller’s authorization. [2](#0-1)  Until protocol-level venue restriction exists, wallets and quoting clients must decode routes and reject any authorization tree containing children other than the expected lending/input-token calls. [15](#0-14) 

### Proof of Concept
The repository’s focused harness constructs a debt-free account with USDC collateral and gives Alice an unrelated wallet token. [16](#0-15) 

```rust

// The rogue hop transfers an unrelated token from the original caller.

```

The first statement is implemented by the test router and the second by its route-selected pool. [7](#0-6) [8](#0-7) 

The test calls `controller.swap_collateral(Alice, account_id, USDC, amount, ETH, malicious_route)`; simulation records `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)` as a child of Alice’s authorization and moves the full `77_770_000_000` balance. [17](#0-16) [9](#0-8)  Signing that simulated tree makes the enforced transaction succeed, leaving Alice’s unrelated token balance at zero and the attacker’s balance at `WALLET_BALANCE`. [10](#0-9)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
