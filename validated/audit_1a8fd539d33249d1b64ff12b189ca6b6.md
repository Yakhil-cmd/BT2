### Title
Unauthenticated forged `pull_request` `reopened` webhook bypasses signature verification for orgs configured without `webhook_secret`, allowing attacker to unarchive/recreate arbitrary review stacks - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` returns `true` immediately when the resolved organization's config has no `webhook_secret`, bypassing HMAC verification entirely. Because `repository_owner` in `WebhooksController#verify_signature` is read straight from attacker-controlled JSON body (`params.dig('repository','owner','login')`), any unauthenticated caller can pick any Shipit-configured organization lacking a `webhook_secret` and submit a forged `pull_request` `action=reopened` event targeting an arbitrary `repository.full_name` belonging to that org, causing `ReopenedHandler` to unarchive or (re-)create a `ReviewStack` for a PR the attacker never actually opened/reopened on GitHub.

### Finding Description
The broken binding: the invariant should be `repository_owner_used_for_signature_verification == organization_that_actually_owns_the_repository_the_event_claims_to_affect`, and no forged webhook should be accepted without a valid HMAC over the actual configured secret. In practice:

1. `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (attacker-supplied JSON), then does `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(header, raw_post)` [1](#0-0) .
2. `verify_webhook_signature` short-circuits to `true` when `@webhook_secret` is blank for that org's config: `return true unless webhook_secret` [2](#0-1) .
3. If the org that owns the targeted victim `Repository`/`ReviewStack` is configured in Shipit but its config entry has no `webhook_secret` key, any payload claiming `repository.owner.login` equal to that org (and `repository.full_name` equal to the victim repo) passes verification unconditionally — no HMAC, no secret knowledge required.
4. `Shipit::Webhooks.for_event('pull_request')` dispatches to `ReopenedHandler#process`, which resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , and if `unarchive?` conditions on the repo's `provisioning_behavior` are met, calls `stack.unarchive!` on a `ReviewStackAdapter` scoped to that repository's `review_stacks` [4](#0-3) .
5. `ReviewStackAdapter#unarchive!` either unarchives an existing archived `ReviewStack` (calling `stack.remove_from_provisioning_queue`, `stack.deprovision`... wait, actually re-provisioning path) or creates a brand-new `ReviewStack` record and `PullRequest` with attacker-supplied `branch: params.pull_request.head.ref` [5](#0-4) .

Existing guards fail because: `drop_unhandled_event` only checks the event type exists in the handler registry, not authenticity; `ExplicitParameters` schema only validates JSON shape, not origin; and `verify_signature`'s only real check (`verified`) is neutralized by the blank-secret short-circuit. The org lookup and the repository lookup are both derived from the same untrusted payload, so there is no independent binding between "the org whose secret was checked" and "the org that actually controls the targeted repository" — but critically, the actual root requirement is that the *specific victim org* must be configured with no secret; this is an organization-provisioning/configuration issue rather than a cross-org secret confusion (a differently-secreted org's signature cannot forge this event).

### Impact Explanation
For repositories under Shipit organizations configured without a `webhook_secret`, an unauthenticated attacker can trigger `stack.unarchive!` (re-provisioning a deprovisioned review environment, restarting deploy/provisioning tasks) or fabricate a new `ReviewStack` + `PullRequest` record with attacker-chosen `branch`, `title`, `additions`, `labels`, etc., for any PR number/repository under that org, without ever creating a real PR reopen event on GitHub. This is a repository/stack-state-mutation impact triggered without authentication, matching "a payload for one repository mutating another's stack" only insofar as the attacker fully controls the JSON body describing the target stack/PR, while the actual authorization boundary (webhook signature) is not enforced at all for that org.

### Likelihood Explanation
This requires a specific, non-default misconfiguration: a Shipit-configured GitHub organization whose config hash omits `webhook_secret` (or leaves it blank) — i.e., an operator error, since `webhook_secret` is expected/documented to always be set. If that precondition holds, exploitation costs nothing beyond crafting an HTTP POST with a JSON body satisfying `ReopenedHandler`'s `ExplicitParameters` schema (`action`, `number`, `pull_request.{id,number,url,title,state,additions,deletions,head.{sha,ref},user.login,assignees,labels}`, `repository.full_name`, `sender.login`) — no signature header value is even checked once `webhook_secret` is blank.

### Recommendation
Do not allow `verify_webhook_signature` to return `true` for blank `webhook_secret`; instead treat a missing/blank secret as a hard misconfiguration that rejects all webhooks for that organization (fail closed), and/or require `webhook_secret` presence validation at Shipit organization configuration load time so this state cannot exist in a running instance.

### Proof of Concept
minitest (`test/controllers/shipit/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure `Shipit.github_config` (or stub `Shipit.github(organization:)`) so organization `"no-secret-org"` resolves to a `GitHubApp` built with a config hash that has no `:webhook_secret` key.
2. Create `repository = Shipit::Repository.create!(owner: 'no-secret-org', name: 'victim', review_stacks_enabled: true, provisioning_behavior: 'allow_all')`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or an arbitrary bogus one), and JSON body `{ action: 'reopened', number: 42, pull_request: {...minimal valid schema, head: { ref: 'attacker-branch' }}, repository: { full_name: 'no-secret-org/victim' }, sender: { login: 'attacker' } }`.
4. Assert response is `200 OK` (not `422`), and assert `Shipit::ReviewStack.find_by(environment: 'pr42')` exists with `branch == 'attacker-branch'` — proving a stack was created/unarchived from a forged, unsigned request.
5. Contrast with a control case using an org that has `webhook_secret` set and no/invalid signature: assert response `422` and no `ReviewStack` created, to prove the divergence is specifically due to the blank-secret short-circuit in `GitHubApp#verify_webhook_signature`.
