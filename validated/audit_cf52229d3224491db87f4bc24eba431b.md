### Title
Repository-unscoped commit status webhook (`StatusHandler#process`) allows cross-repository status injection via shared commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) with a bare, repository-unscoped query (`Commit.where(sha: params.sha)`), so a validly-signed `status` webhook from an attacker-owned repository will update the CI status of every `Commit` record in the database that happens to share that SHA, including one belonging to a victim's stack. Because Shipit's CI-gating logic (`Commit#deployable?`, `Commit#blocked?`, `Stack#schedule_merges`) reads state purely from these `statuses` records, this can trigger or unblock a deploy/merge on the victim stack without the victim repository ever emitting the event.

### Finding Description
The broken binding is: **a status update for commit `sha` should only be applied to `Commit` records belonging to the stack(s) of the repository that authenticated the webhook**, i.e. `commit.stack.repository.full_name == payload.dig('repository','full_name')`. In the actual code this equality is never checked.

`StatusHandler#process` is:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike the pull-request handlers, this handler never calls the base `Handler#stacks` helper, which is precisely the mechanism designed to scope work to `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 

`WebhooksController#verify_signature` only authenticates that the payload was signed by *some* GitHub App/organization matching `repository_owner` in the payload — it does not restrict which `Commit` rows the handler may touch: [3](#0-2) 

`Commit.sha` has no uniqueness constraint scoped globally the code assumes SHA collisions across different `stack_id` are possible and legitimate (Shipit stores one `Commit` row per `(stack, sha)` pair, so the same SHA — e.g., shared history via a fork, cherry-pick, or a rebased identical commit — produces separate rows in both an attacker's and a victim's stack). `Commit.where(sha: params.sha).each` iterates over **all** of them, and `commit.create_status_from_github!(params)` writes the attacker-controlled `state`/`context` (`ci/integration`) into `victim_commit.statuses`, invalidating the invariant.

Downstream, `Commit#status` aggregates from `statuses_and_check_runs`, and `add_status` triggers `stack.schedule_merges` and deployability re-evaluation when `new_status.pending? || new_status.success?`: [4](#0-3) 
and `deployable?`/`blocked?` gate continuous delivery and merges based solely on this status state: [5](#0-4) [6](#0-5) 

**Exploit flow**: The attacker owns/controls repository `attacker/repo`, which is registered in Shipit (so a webhook secret exists and `verify_signature` will pass for `repository_owner = attacker`). The attacker arranges (e.g., via fork, shared upstream branch, or cherry-pick) for a commit with SHA `S` to exist both in `attacker/repo` and in the victim's monitored repository/stack. GitHub (or a forged-but-validly-signed status event the attacker triggers on their own repo for that SHA) sends a `status` webhook with `context: ci/integration`, `state: success`, `sha: S`. `StatusHandler#process` looks up `Commit.where(sha: S)` — this returns both the attacker's own commit row and the victim's commit row (different `stack_id`s) — and writes a `success` status to both, unblocking/deploying the victim's commit.

None of the existing guards prevent this: `verify_signature` only checks that the *event* payload matches the sender's own organization's secret, not that the SHA lookup is confined to that organization's repositories; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not scope; there is no `stacks`/repository filter applied in `StatusHandler` at all.

### Impact Explanation
A single valid status webhook from an attacker-controlled repository can flip CI status (success/failure/pending) on a completely different, victim-owned stack's commit whenever a SHA happens to be shared, causing `Stack#schedule_merges`/continuous-delivery to fire or the commit to be marked deployable/blocked. This is a cross-tenant/cross-repository state mutation: a payload authenticated for one repository (the attacker's) writes into another repository's (victim's) `Commit`/`Status` records, matching the Critical "payload for one repository mutating another's stack, commit, task" category. The attack is repeatable against any victim stack whose commit history overlaps with an attacker-controlled repository (forks, shared upstream, or crafted identical commits are the realistic vector).

### Likelihood Explanation
Preconditions: the attacker must control (own or have push access to) a Shipit-registered repository so a genuine webhook signature can be produced for the `status` event, and a commit SHA must exist identically in both the attacker's repository and the victim's monitored repository/stack (achievable via forking a victim's public repo and pushing the fork's own commits/history, or via any shared-upstream/rebase scenario producing identical SHAs). No Shipit session, API token, or team membership is required just the ability to emit a `status` webhook event on their own repo. This is a low-cost, fully unauthenticated (from Shipit's perspective) attack once the SHA-sharing condition is met, and is repeatable for any subsequent commit sharing a SHA.

### Recommendation
Scope `StatusHandler#process` to the commits belonging only to the repository that authenticated the webhook, e.g. use the existing `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) to constrain the `Commit` lookup: `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the scoping already used by pull-request handlers.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, conceptually):
1. Create `attacker_stack` for repository `attacker/repo` and `victim_stack` for repository `victim/repo`, both requiring status `ci/integration`.
2. Create `Commit.create!(stack: attacker_stack, sha: 'abc123...')` and `Commit.create!(stack: victim_stack, sha: 'abc123...')` (same SHA, different stacks) — assert `attacker_commit.sha == victim_commit.sha` and `attacker_commit.stack_id != victim_commit.stack_id`.
3. Assert precondition: `victim_commit.deployable?` is `false` (no successful `ci/integration` status yet).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => 'abc123...', 'state' => 'success', 'context' => 'ci/integration', 'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker' } })` (simulating a validly-signed webhook from the attacker's own repo).
5. Reload `victim_commit` and assert `victim_commit.status.state == 'success'` and `victim_commit.deployable? == true`, proving the attacker's own-repo webhook mutated the victim stack's commit state — violating the equality `commit.stack.repository.full_name == payload['repository']['full_name']`.
