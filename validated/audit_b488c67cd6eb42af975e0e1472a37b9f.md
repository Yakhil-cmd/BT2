### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` triggers unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to attach a forged CI status purely by `sha`, with no filter on the `repository`/`owner` named in the webhook payload, unlike `PushHandler`/`CheckSuiteHandler` which both scope their lookups through `stacks` (derived from `payload.dig('repository', 'full_name')`). An attacker who controls any GitHub repository/org onboarded to the same Shipit instance can reproduce a victim commit's exact SHA in their own repo and legitimately trigger a real, correctly-signed "status" webhook naming their own repo, causing Shipit to write a `success` status onto the victim's identically-shaed `Commit` row and drive `stack.schedule_merges` → `ProcessMergeRequestsJob` → `MergeRequest#merge!` for the victim's stack using the victim's own stored GitHub credentials.

### Finding Description
Broken binding: the commit status written should satisfy `commit.stack.github_repo_name == payload['repository']['full_name']`; instead `StatusHandler#process` enforces no such equality at all.

```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Contrast with the other two handlers, which both properly derive `stacks` from the payload's repository name before touching any commit:
```ruby
def process
  stacks.where(branch: params.check_suite.head_branch).each do |stack|
    stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
  end
end
``` [2](#0-1) 
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [3](#0-2) 

`Handler#stacks` resolves `Repository.from_github_repo_name(repository_name)&.stacks` from the payload's `repository.full_name`, which is exactly the scoping primitive `StatusHandler` fails to use. [4](#0-3) 

`WebhooksController#verify_signature` only verifies that the payload's signature matches the GitHub App/webhook secret for the `repository_owner` named in the *attacker's own* payload — it says nothing about which `Commit` rows the handler is allowed to touch:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [5](#0-4) 
So a webhook that is legitimately signed for `attacker/repoA` (GitHub computes this signature itself when the attacker sets a status on their own repo/commit — the attacker never needs Shipit's secrets) passes signature verification, then reaches `StatusHandler`, which ignores the repository entirely and matches on `sha` across the whole `commits` table.

Exploit flow:
1. Victim opens (or already has) a PR on `victim/repoB` whose head commit has SHA `X` (visible publicly since PRs are typically public, or observable if attacker is a collaborator/anyone with read access).
2. Attacker reproduces the exact commit object (same tree, parent, author/committer identities and timestamps, message) in their own repo `attacker/repoA`, git being content-addressed this yields the identical SHA `X` in the attacker's own history.
3. Attacker sets (or has CI set) a `success` status on that commit in `attacker/repoA` via the normal GitHub API using their own credentials, causing GitHub to deliver a validly HMAC-signed `status` webhook to Shipit naming `attacker/repoA` and SHA `X`.
4. `verify_signature` passes (signature is genuinely valid for `attacker/repoA`'s org).
5. `StatusHandler#process` runs `Commit.where(sha: X)`, which returns the **victim's** `Commit` row in `repoB` (same SHA), and calls `commit.create_status_from_github!(params)` on it.
6. `create_status_from_github!` → `add_status` uses the commit's own `stack_id` (the victim's stack), creates a `success` `Status`, and since the state transitioned, calls `stack.schedule_merges` / enqueues `ProcessMergeRequestsJob`. [6](#0-5) 
7. `ProcessMergeRequestsJob` calls `merge_request.refresh!` then `merge_request.all_status_checks_passed?`, which is now true, and calls `merge_request.merge!`, which merges using `stack.github_api` — the victim's own stored GitHub credential. [7](#0-6) [8](#0-7) 

None of the existing guards prevent this: `verify_signature` only checks the HMAC matches the claimed org, not that the claimed org owns the touched commit; `drop_unhandled_event` doesn't apply (status is a handled event); the `ExplicitParameters` schema on `StatusHandler` only validates presence/type of `sha`/`state`, not repository ownership. [9](#0-8) 

### Impact Explanation
A `success`/`pending` status forged from an attacker-controlled, correctly-onboarded repository can be written onto an unrelated victim stack's commit purely by SHA collision, and this can trigger `MergeRequest#merge!` on `victim/repoB` using that stack's real stored `github_access_token`/App installation credentials — an unauthorized merge executed with the victim's own merge credential on code that never passed the victim's real CI. This matches the "Critical — a payload for one repository mutating another's stack/commit... or an unauthorized merge" category. Blast radius is any stack/repository configured on the same Shipit instance whose commit history can be duplicated by an outside party (any public PR/commit is a candidate), and the attack is repeatable against any repository for which the attacker can produce SHA-identical content and control a signed webhook source.

### Likelihood Explanation
Preconditions: (a) the attacker must control (or be able to trigger status webhooks from) at least one repository/org that is legitimately onboarded to the same Shipit instance (has a valid GitHub App installation/webhook secret known only to GitHub) — plausible in any multi-tenant Shipit deployment where onboarding an org is self-service or already broad; (b) the attacker must be able to reproduce the exact victim commit object byte-for-byte to get an identical SHA, which is feasible when the victim's commit is fully visible (public PR) since git commits are deterministic hashes over already-known fields (tree, parents, author/committer name+email+timestamp, message) — no cryptographic collision is required, just content duplication; (c) `victim/repoB` must have merge-queue auto-merge enabled and a pending `MergeRequest` whose head matches the duplicated SHA. Attacker cost is a single webhook delivery from their own repo/org, no Shipit secrets needed, and the technique is repeatable against any repository whose commits can be duplicated.

### Recommendation
Scope `StatusHandler#process` by the payload's repository, mirroring `PushHandler`/`CheckSuiteHandler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.github_repo_name == payload['repository']['full_name']` before any status is written, closing the cross-repository binding gap.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or extending `test/controllers/webhooks_controller_test.rb`):
1. Create `stack_a` for repo `victim/repoB` and `stack_b` for repo `attacker/repoA` (two distinct `Stack`/`Repository` records).
2. Create `commit_victim` under `stack_a` with `sha: 'sharedsha123...'` and no existing status (`state` defaults to `unknown`).
3. Create a `MergeRequest` on `stack_a` with `head: commit_victim`, `merge_status: 'pending'`.
4. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name == 'attacker/repoA'`, `repository.owner.login == 'attacker'`, `sha == 'sharedsha123...'`, `state == 'success'`, `branches: [{name: 'attacker-branch'}]` — stub `Shipit.github(organization: 'attacker')` (or the relevant org) to return `verify_webhook_signature` `true` (simulating a genuinely valid signature for the attacker's own onboarded org, not the victim's).
5. Assert equality-before check: before the request, `commit_victim.reload.state != 'success'` and `merge_request.all_status_checks_passed? == false`.
6. Assert on the broken binding: after the request, `commit_victim.reload.statuses.last.state == 'success'` even though the status's originating payload named `attacker/repoA`, i.e. assert `commit_victim.stack.github_repo_name == 'victim/repoB'` while `payload['repository']['full_name'] == 'attacker/repoA'` — proving the mutation crossed repository ownership.
7. Assert `merge_request.reload.all_status_checks_passed? == true`.
8. Assert `ProcessMergeRequestsJob` was enqueued for `stack_a` (`assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_a])`), and, running the job with `merge_pull_request` stubbed, assert `merge_request.merge!` is invoked and transitions to `completed`, demonstrating an unauthorized merge on `victim/repoB` was driven entirely by a forged status from `attacker/repoA`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

    def merge!
      raise InvalidTransition unless pending?

        merge_message,

      end

      true

      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.

    end
