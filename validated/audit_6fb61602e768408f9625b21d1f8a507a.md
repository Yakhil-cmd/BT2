### Title
Cross-repository status webhook forges `shipit/checks` state via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no repository/stack scoping, and applies the incoming GitHub status to every matching `Commit` record. Since Shipit's commit table is not partitioned per-repository in this lookup, a `status` webhook payload that is only cryptographically tied to the originating repository ends up mutating commit status state for any other stack that happens to have a commit with the same SHA.

### Finding Description
The broken binding: the invariant should be `commit.stack.repository == webhook.repository` for every `Commit` mutated by a `status` event, i.e. a `shipit/checks` status should only ever affect the repository that authenticated/originated it.

In `app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This query has no `stack_id`/repository filter — it is a bare `sha` lookup across the entire `commits` table, which spans all stacks/repositories configured on the Shipit instance. Any `Commit` row anywhere with a matching `sha` receives `create_status_from_github!(params)`, which calls `statuses.replicate_from_github!` and then re-evaluates state via `add_status`: [2](#0-1) [3](#0-2) 

That status feeds directly into `blocking?` and `blocked?`: [4](#0-3) [5](#0-4) 

which gates `deployable?` and can trigger `stack.schedule_merges` when the resulting `simple_state` transitions to success/pending: [6](#0-5) [7](#0-6) 

Exploit flow: an attacker who controls a repository (or otherwise causes a commit with a known/colliding SHA to exist, e.g. cherry-picks, empty commits, or any workflow that produces identical SHAs across repos) sends `POST /webhooks` with a `status` event: `context: "shipit/checks"`, `state: "success"`, `sha: <victim-shared-sha>`. Because `Commit.where(sha:)` is global and unscoped, if a victim stack's `blocking_statuses` includes `shipit/checks` and has a `Commit` row with that same SHA, the victim's commit `blocking?`/`blocked?` evaluation flips based on the attacker's forged status, independent of the victim repository's actual GitHub state.

Existing guards do not prevent this: webhook signature verification only authenticates that the payload came from the sender's own registered repository/secret — it says nothing about which `Commit` rows the handler is permitted to touch. The `StatusHandler` params schema (`ExplicitParameters`) validates payload shape only, not repository ownership, and there is no `repository_owner`/`Repository` check anywhere in `process`.

### Impact Explanation
A forged status from an unrelated, attacker-controlled repository can flip `blocking?`/`blocked?`/`deployable?` state on a victim's `Commit`, and that state feeds `Stack#schedule_merges` and deploy gating. This is a cross-tenant write: one repository's webhook payload mutates another repository's stack/commit state without that repository ever authenticating the change. This matches the "Critical — payload for one repository mutating another's stack/commit" impact category, since it can force or block deploys/merges on a victim stack.

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` (or similarly, `required_statuses`) configured, and there must be a `Commit` record sharing the exact `sha` value across the two stacks. SHA collisions are not generally attacker-forgeable (SHA-1 second-preimage attacks are infeasible), but they occur naturally and are attacker-*causable* in real workflows: forked repos with identical commit history/cherry-picks, monorepo mirrors, or repositories that are added to Shipit as multiple stacks tracking the same underlying commits (common CD setup, e.g. staging/production stacks or multiple GitHub repos mirroring the same upstream). In such configurations, the attacker's cost is a single unauthenticated `POST /webhooks` with a known SHA already present in the victim stack's history. Repeatable at will against every stack sharing that SHA.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogously in any other handler using bare `sha`/`ref` lookups) to only commits belonging to stacks whose `Repository` matches the webhook's authenticated repository, e.g.:
```ruby
Commit.joins(stack: :repository)
      .where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })
      .each { |commit| commit.create_status_from_github!(params) }
```
Reject or ignore any commit whose stack's repository does not match the webhook's originating repository, mirroring the scoping already expected by the invariant "a `shipit/checks` status affects only the repository that authenticated it."

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` style, no live GitHub):
1. Create two stacks, `stack_a` (repo `attacker/repo`) and `stack_b` (repo `victim/repo`), with `stack_b.blocking_statuses` configured to include `shipit/checks`.
2. Create `commit_a = stack_a.commits.create!(sha: "deadbeef" * 5, ...)` and `commit_b = stack_b.commits.create!(sha: "deadbeef" * 5, ...)` (same SHA, different stacks).
3. Assert precondition: `commit_b.blocked?` reflects victim's real state (e.g., `assert commit_b.blocked?` because no success status exists yet, or set up a prior blocking status).
4. Build a `status` webhook payload as if from `attacker/repo`: `{ sha: commit_a.sha, state: "success", context: "shipit/checks" }` and invoke `Shipit::Webhooks::Handlers::StatusHandler.new(...).process` (bypassing only the HTTP signature layer, as is standard for handler unit tests).
5. Assert the broken binding: before processing, `commit_a.stack_id != commit_b.stack_id` and both have independent status state; after processing, assert `commit_b.reload.statuses.exists?(context: "shipit/checks", state: "success")` is `true` even though the webhook never referenced `victim/repo`, and assert `commit_b.blocked?`/`commit_b.deployable?` changed value as a direct result — proving the attacker's payload for `attacker/repo` mutated `victim/repo`'s commit/stack state.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
