### Title
Double-counting of a single Bitcoin lockup across multiple `register-for-bond` calls in pox-5.clar - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 proof path (`verify-l1-lockups` / `validate-l1-lockup`) verifies that a Bitcoin UTXO exists, is unspent-looking (via merkle proof + header), and matches the staker's committed lockup script, but it never records the outpoint (`txid`, `output-index`) in any persistent, contract-wide map. The `seen-outpoints` accumulator that guards against `ERR_DUPLICATE_LOCKUP_OUTPOINT` is scoped only to the single `fold` call inside one transaction. Nothing prevents the same on-chain BTC lockup output from being submitted again in a later `register-for-bond` call (by the same staker, in a different bond period, or after unstaking/rolling over), crediting `sats-total` for a bond membership that has no additional Bitcoin backing it.

### Finding Description
`validate-l1-lockup` ( [1](#0-0) ) checks the outpoint's uniqueness only inside the `seen-outpoints` list that is built and discarded within a single `fold` invocation, initialized fresh on every call to `verify-l1-lockups`: [2](#0-1) 

`register-for-bond` then uses the returned `sats-total` directly to set `amount-sats` in `protocol-bond-memberships` and to increase `protocol-bonds-total-staked`: [3](#0-2) 

Because the merkle-proof/header verification in `validate-l1-lockup` only proves that the sats were locked into the timelock script *at some point in Bitcoin history* — it does not, and cannot, prove that the STX-side commitment is being made for the first time — the same physical BTC output can be replayed:
- across independent `register-for-bond` calls in different (non-overlapping) bond periods,
- or by the staker after `unstake`/`update-bond-registration`, re-registering with the identical L1 proof bytes for a new bond.

Each replay increments `protocol-bonds-total-staked` and grants the staker `amount-sats`-derived signer weight/reward eligibility for a *new* bond, even though no new Bitcoin was locked. This breaks the equality "sats credited by pox-5 == sats actually locked on Bitcoin for that specific bond period," since one Bitcoin lockup transaction is used to originate the sats credit for more than one bond commitment.

### Impact Explanation
This is a Critical-class issue under the rules: "double-counting a commitment or reward." A staker's signer weight, sats-total, and STX-collateral ratio (used to compute `min-ustx-for-sats-amount`) are all derived from `sats-total`, so double/triple-counting the same L1 lockup inflates the staker's apparent stake and reward share across multiple bond periods without a matching increase in locked Bitcoin, which can distort reward distribution and the sBTC/STX backing invariant that `pox-5`'s L1-lockup design is meant to guarantee.

### Likelihood Explanation
No privileged role is required — an ordinary allow-listed staker (the intended, unprivileged caller of `register-for-bond`) can simply resubmit the same `btc-lockup` proof struct (same `tx`, `header`, `output-index`) they used previously, once eligible to register for a subsequent bond period (e.g., after their prior bond's term completes or during a permitted rollover window). The proof bytes are fully public/reusable since they are just serialized Bitcoin chain data, not a consumable token.

### Recommendation
Persist a durable, contract-wide map (e.g. `l1-lockup-outpoint-usage: {txid, output-index} -> {staker, bond-index}` or similar) that is checked and updated by `validate-l1-lockup`/`verify-l1-lockups`, rejecting any outpoint that has already been credited to an active or historical bond membership (or scoping validity to the specific bond/lock period so a given outpoint can only ever back one live commitment at a time).

### Proof of Concept
1. Staker A performs a real Bitcoin timelock deposit of `S` sats to the P2WSH computed by `construct-lockup-output-script` for bond 0 and calls `register-for-bond(bond-index=0, ..., btc-lockup=(ok {outputs: [proof], ...}))`. This succeeds, crediting `sats-total = S` to bond 0's membership. [4](#0-3) 
2. After bond 0's term ends (or via the rollover path), Staker A calls `register-for-bond(bond-index=6, ..., btc-lockup=(ok {outputs: [same proof], ...}))` using the exact same `tx`/`header`/`output-index` bytes.
3. `validate-l1-lockup` re-verifies the merkle proof and header against real historical Bitcoin data (still true, since the transaction is immutably on-chain) and re-accepts it because `seen-outpoints` is reset per-call. [5](#0-4) 
4. Bond 6's membership is credited `sats-total = S` again, `protocol-bonds-total-staked` for bond 6 increases by `S`, even though no new BTC was locked — the same `S` sats now back two bonds' worth of signer weight/reward eligibility.

(define-private (validate-l1-lockup
        (lockup {
            height: uint,
            tx: (buff 100000),
            output-index: uint,
            header: (buff 80),
            leaf-hashes: (list 14 (buff 32)),
            tx-count: uint,
            tx-index: uint,
            amount: uint,
            unlock-burn-height: uint,
        })
        (accumulator-res (response {
            staker: principal,
            minimum-unlock-height: uint,
            staker-unlock-bytes: (buff 683),
            early-unlock-bytes: (buff 683),
            sum: uint,
            seen-outpoints: (list 10 {
                txid: (buff 32),
                output-index: uint,
            }),
        }
            uint
        ))
    )
    (let (
            (accumulator (try! accumulator-res))
            (block (try! (parse-block-header (get header lockup))))
            (unlock-burn-height (get unlock-burn-height lockup))
            (expected-script-hash (try! (construct-lockup-output-script (get staker accumulator)
                unlock-burn-height (get staker-unlock-bytes accumulator)
                (get early-unlock-bytes accumulator)
            )))
            (output (try! (get-bitcoin-tx-output? (get tx lockup) (get output-index lockup))))
            (reversed-txid (get txid output))
            (txid (reverse-buff32 reversed-txid))
            (outpoint {
                txid: txid,
                output-index: (get output-index lockup),
            })
            (seen-outpoints (get seen-outpoints accumulator))
        )
        (asserts! (>= unlock-burn-height (get minimum-unlock-height accumulator))
            ERR_INVALID_UNLOCK_HEIGHT
        )
        (asserts! (< unlock-burn-height BITCOIN_LOCKTIME_THRESHOLD)
            ERR_INVALID_UNLOCK_HEIGHT
        )
        (asserts! (is-eq (get script output) expected-script-hash)
            ERR_INVALID_LOCKUP_SCRIPT
        )
        (asserts! (is-eq (get amount output) (get amount lockup))
            ERR_INVALID_LOCKUP_AMOUNT
        )
        (asserts! (is-none (index-of? seen-outpoints outpoint))
            ERR_DUPLICATE_LOCKUP_OUTPOINT
        )
        (asserts! (verify-block-header (get header lockup) (get height lockup))
            ERR_INVALID_BTC_HEADER
        )
        ;; verify merkle proof
        (asserts!
            (or
                (is-eq (get merkle-root block) txid) ;; true, if the transaction is the only transaction
                (verify-merkle-proof reversed-txid
                    (reverse-buff32 (get merkle-root block))
                    (get tx-index lockup) (get tx-count lockup)
                    (get leaf-hashes lockup)
                )
            )
            ERR_INVALID_MERKLE_PROOF
        )
        (ok {
            staker: (get staker accumulator),
            minimum-unlock-height: (get minimum-unlock-height accumulator),
            staker-unlock-bytes: (get staker-unlock-bytes accumulator),
            early-unlock-bytes: (get early-unlock-bytes accumulator),
            sum: (+ (get sum accumulator) (get amount output)),
            seen-outpoints: (unwrap-panic (as-max-len? (append seen-outpoints outpoint) u10)),
        })
    )
)
