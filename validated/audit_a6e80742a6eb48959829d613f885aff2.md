### Title
AA `trigger.address` is derived only from the first author of a multi-authored triggering unit, misattributing deposits/refunds when several distinct addresses jointly sign one payment - ([File: aa_composer.js])

### Summary
An Autonomous Agent (AA) derives the identity of the party that funded or triggered it purely from `objUnit.authors[0].address` of the triggering unit, i.e., the first (alphabetically sorted) author. A single unit can legitimately have multiple co-signing authors (a multi-authored/multi-signature payment) while carrying payment outputs addressed to the AA. Because `getTrigger()` never checks how many distinct authors exist nor which author's funds are actually being deposited, `trigger.address`, and thus every balance credited, refunded, or authorization check performed by the AA's oscript (`var[...||trigger.address||...]`, bounce refunds to `trigger.address`, withdrawal eligibility checks such as `trigger.address == $addressA`), is bound to whichever author address sorts first — not necessarily the address that actually deposited the funds or that the depositor intended to control the resulting balance/rights.

### Finding Description
`getTrigger()` sets the trigger identity unconditionally to the first author of the triggering unit: [1](#0-0) 

This trigger object is then used throughout `handleTrigger()` as the canonical identity for balance crediting, bounce refunds, and any oscript logic keyed by `trigger.address`, e.g. in the bounce handler which sends the refunded amount back to `trigger.address`: [2](#0-1) 

At the unit level, ocore explicitly supports multi-authored units where several distinct addresses co-sign a single unit; this is validated generically (sorted, deduplicated authors) with no restriction preventing a multi-authored unit from being a trigger to an AA: [3](#0-2) 

Widely-used AA design patterns (bank/deposit tracking, payment channels, withdrawal authorization) key all balances and access-control checks exclusively off `trigger.address`, as seen in shipped sample AAs: [4](#0-3) [5](#0-4) 

Because the composer-level rule "one payment can have several inputs (authors) and outputs" maps directly onto AA triggers, a unit that is co-signed by two or more addresses (e.g., a shared/multisig address usage, or two independent addresses jointly authoring one unit to combine fee-paying and funding) collapses into a single `trigger.address` — the smallest author address by string ordering — regardless of which author's coins were actually spent into the AA's payment output, and regardless of the depositor's actual intention. An attacker who can get a victim to co-sign or who controls a smaller-sorting address among several co-authors can cause the AA to attribute a deposit (and hence balance credit, bounce refund, or privileged state change) to the attacker-controlled address instead of the true depositor, or vice versa cause funds intended for the attacker to be redirected to another co-author.

### Impact Explanation
Any AA that uses `trigger.address` as an implicit ownership/identity key (bank-style deposit/withdraw AAs, payment channels, escrow, staking, auctions) can have deposits misattributed to the wrong co-author address when the triggering unit is multi-authored. This can lead to loss of funds for the actual depositor (their deposit is credited to someone else's balance and can be withdrawn by that party) or unauthorized fund/state control gained by an attacker who manages to be included as a co-author. This is a concrete fund-loss/fund-misattribution vector reachable by any unprivileged unit poster who composes or is invited to co-sign a payment to an AA address.

### Likelihood Explanation
Composing a multi-authored unit is a standard, fully-supported ocore feature (multi-sig/shared addresses, joint payments) and requires no special privilege — it only needs valid signatures from each author for that specific unit, which an attacker can obtain by presenting a shared-address/multisig payment flow to a victim (e.g., "pay together to this AA to open a channel/deposit"), or simply by being one of several signers in a legitimate multi-owner wallet that interacts with an AA. No malicious peer, hub, or node behavior is required.

### Recommendation
Either (a) reject AA triggers whose triggering unit has more than one author, mirroring the restriction already imposed on AA-generated units (`objValidationState.bAA && arrAuthors.length !== 1`), or (b) expose the full list of author addresses to oscript (not just `authors[0]`) so that AA authors can explicitly decide how to handle multi-authored triggers, and update documentation/samples to warn that `trigger.address` reflects only the first author, requiring AAs that rely on `trigger.address` for balance/identity to explicitly guard against multi-authored triggers.

### Proof of Concept
1. Two addresses, `A` (attacker) and `V` (victim), jointly author a single unit that pays `outputs.base` to a bank-style AA that credits deposits to `var['balance_' || trigger.address]` (as in `test/samples/a_bank_without_percent.oscript`).
2. `V` believes they are depositing funds that should be credited to their own address `V`, e.g. because they are a co-signer of a shared/multisig setup, or because a wallet UI/dApp instructs them to co-sign a joint payment.
3. Because `A` sorts before `V` alphabetically, `getTrigger()` sets `trigger.address = A` for this unit.
4. The AA credits the entire deposited amount to `var['balance_A_base']`, not `var['balance_V_base']`.
5. `A` can now withdraw the funds that `V` deposited by sending a trigger with `trigger.data.withdraw = true` from address `A`, while `V` has no claim to the credited balance despite having contributed the funds in the joint unit.

	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';

				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
