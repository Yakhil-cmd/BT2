### Title
`StatusHandler#process` resolves commits by SHA with no repository scope, letting a signed webhook from one repository write a `Status` onto a colliding-SHA commit belonging to a different stack/repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the entire `commits` table, without any repository or stack filter, unlike sibling handlers (e.g. `CheckSuiteHandler`) which correctly scope through `stacks`. Because `commits.sha` has no cross-repository uniqueness guarantee, a validly-signed status webhook for repository A can create/update a `Status` record on a commit that actually belongs to repository B's stack, if the two repositories happen to share a SHA (e.g. via a shared GitHub template-repo bootstrap commit or the well-known empty-tree SHA).

### Finding Description
The intended binding is: *a status webhook for repository R should only affect commits belonging to R's own stack(s)*, i.e. `webhook.payload.repository.full_name == commit.stack.repository.full_name` for every `Commit` mutated. 

Tracing the code:
- `WebhooksController#verify_signature` [1](#0-0)  verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the payload's `repository.owner.login` [2](#0-1) . This only proves the payload came from a GitHub App/organization the attacker legitimately owns/controls (their own repo) — it says nothing about which `Commit` rows may be touched.
- `Handler#stacks` / `#repository_name` exist specifically to scope lookups to the webhook's own repository [3](#0-2) , and `CheckSuiteHandler` uses this correctly: `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [4](#0-3) .
- `StatusHandler#process`, however, bypasses `stacks`/`repository_name` entirely and queries the *global* `Commit` table: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .
- `Commit#create_status_from_github!` then writes a `Status` scoped to that commit's *own* `stack_id` (i.e., the victim stack), via `statuses.replicate_from_github!(stack_id, github_status)` [6](#0-5) , and `Status.replicate_from_github!` persists state/description/target_url from the attacker-controlled payload [7](#0-6) .

Exploit flow: the attacker creates a GitHub repo from the same template as `victim/prod` (or one that otherwise shares a commit SHA, e.g. the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`), onboards it to Shipit as their own stack (fully within their rights), and its first commit gets imported via `Commit.create_from_github!` sharing that SHA with the victim's commit already tracked by Shipit. The attacker then triggers (or has GitHub send) a legitimately-signed `status` webhook for their own repository referencing that shared SHA with `state: 'success'`. Because `StatusHandler#process` never checks `repository_name`, the query `Commit.where(sha: ...)` returns both the attacker's commit and the victim's colliding-SHA commit, and a `Status` row is created on the victim's commit under the victim's `stack_id`. This can flip `Commit#state` to `success`, trigger `Hook.emit(:deployable_status, ...)`, `stack.schedule_merges`, and `commit.schedule_continuous_delivery` on the victim's stack [8](#0-7)  — potentially causing an unauthorized deploy/merge decision on a repository the attacker never authenticated for.

None of the listed guards prevent this: `verify_signature` only authenticates that the payload's *claimed* organization signed it, not that the affected `Commit` rows belong to that organization; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; there is no `require_permission!`/`stacks` scoping call inside `StatusHandler#process` at all.

### Impact Explanation
An attacker who owns an independent, Shipit-tracked repository can cause a `Status` record (and downstream CI-state changes, deployable-status hooks, and continuous-delivery scheduling) to be written onto a commit belonging to a **different repository's stack** that they do not control, without ever authenticating against that victim repository. This is a cross-tenant mutation triggered by a payload the attacker fully controls, matching "a payload for one repository mutating another's stack/commit" and "an unauthorized deploy" impact category (Critical). The blast radius is bounded by SHA-collision probability, but SHA collisions are readily engineerable via GitHub template repos or well-known fixed-content commits (empty tree), making this a repeatable, attacker-achievable condition rather than a cryptographic long-shot.

### Likelihood Explanation
Requirements: (1) attacker onboards their own repository into the same Shipit instance as a legitimate stack (assumed possible per the multi-tenant threat model implied by the question), (2) attacker engineers a SHA collision with a targeted victim commit (trivial via shared template-repo bootstrap commits or universally-known fixed SHAs like the empty tree), (3) attacker sends a normally-signed webhook for their own repo. All three are within an ordinary GitHub user's rights and require no secrets belonging to Shipit or the victim. This is a genuine code-path bug (missing repository scoping), not merely a theoretical SHA-forgery scenario.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `webhook.repository_name == commit.stack.repository.full_name` before any `Status` is created, closing the cross-repository SHA-collision channel. Additionally, consider adding a uniqueness constraint on `(repository_id, sha)` at the database level to make the invariant explicit.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub required):
1. Create two `Repository`/`Stack` fixtures, `repo_a` and `repo_b`, representing attacker and victim.
2. Create `commit_a = repo_a.stack.commits.create!(sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904", ...)` and `commit_b = repo_b.stack.commits.create!(sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904", ...)` — same SHA, different stacks.
3. Build a `status` webhook payload with `repository.full_name = repo_a.full_name` and `sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904"`, `state: "success"`.
4. Call `StatusHandler.call(payload)`.
5. Assert (equality check both sides):
   - `assert_equal 1, commit_a.reload.statuses.count` (expected: attacker's own commit gets the status)
   - `assert_equal 0, commit_b.reload.statuses.count` — **this assertion currently fails** with the present code, because `Commit.where(sha: ...)` matches `commit_b` too, proving the cross-repository write; a passing test after the fix demonstrates the binding `webhook.repository_name == commit.stack.repository.full_name` is restored.
