### Title
Webhook signature is checked against an org derived from the payload, but the repository/stack acted on is taken from an unrelated payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate an inbound webhook's HMAC using `repository_owner`, a value pulled out of the very same JSON body it is about to validate (`params.dig('repository','owner','login')`, falling back to `params.dig('organization','login')`). Once the signature check passes, event handlers act on a *different* field of the same body - `repository.full_name` - to resolve the `Repository`/`Stack` that gets written to. Nothing ties "the organization whose secret validated this request" to "the organization that owns the repository being mutated." [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`Shipit::WebhooksController` is a single, unauthenticated public endpoint (`POST /webhooks`) shared by every organization onboarded to a given Shipit instance (multi-org config is a first-class feature: `Shipit.github(organization:)` looks up per-org `app_id`/`webhook_secret` from `secrets.yml`). [4](#0-3) [5](#0-4) 

`verify_signature` resolves which org's `webhook_secret` to validate the HMAC against **using data from inside the very payload being validated**:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This only proves that the requester possesses *some* org's `webhook_secret` - specifically the secret for whichever org they named in `repository.owner.login`. It never confirms that the organization owning that secret is the same organization that actually owns the repository the handlers are about to mutate.

After signature verification, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the matching handler, and every handler resolves its target `Repository`/`Stack` from `repository.full_name`, a sibling field of `repository.owner.login` inside the same JSON body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler`, for example, uses this to load every non-archived stack of the named repository matching the pushed branch and calls `sync_github`, which is the trigger for continuous-deployment/GitHub sync flows:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Repository`) are independent, attacker-controlled fields inside the same raw body, an operator of any org onboarded to this Shipit instance - who legitimately possesses their own org's `webhook_secret` - can hand-craft a POST body where:
- `repository.owner.login` = `"MyOrg"` (their own org, so `verify_webhook_signature` succeeds using their own secret), while
- `repository.full_name` = `"VictimOrg/critical-repo"` (any other repository tracked by the same Shipit instance).

Every handler that resolves state via `Handler#repository_name`/`#stacks` (push, pull_request opened/closed/labeled/etc., status, check_suite) will then act on `VictimOrg`'s stacks - e.g. forcing `stack.sync_github`, archiving/unarchiving review stacks, or writing commit statuses - despite the request only ever being authenticated as belonging to `MyOrg`. [7](#0-6)  This is precisely the "organization that authenticated vs. repository that is written" trust binding failing to hold.

(Separately, `verify_webhook_signature` also `return true unless webhook_secret` - so if any onboarded org has no secret configured, the same cross-tenant forgery works with *no* secret at all - but the core defect is that the org-selection field and the write-target field are never cross-checked, regardless of that shortcut.) [8](#0-7) 

### Impact Explanation
This breaks the binding "organization authenticated == repository written," letting one onboarded tenant forge and control webhook-driven state transitions on another tenant's stacks in the same instance: triggering `sync_github`/continuous-deployment flows, archiving/unarchiving review stacks, and injecting fabricated commit statuses that the merge queue consults. That maps to cross-repository/cross-tenant writes and unauthorized deploy-adjacent actions - Critical impact per the scope's criteria.

### Likelihood Explanation
Any org onboarded to a multi-tenant Shipit instance can perform this - they only need their own valid `webhook_secret` (which they legitimately hold as the owner of their own GitHub App installation), not the victim's. No Shipit session, ApiClient token, or GitHub write access to the victim repo is required. The attack is a single hand-crafted HTTP POST to the public `/webhooks` endpoint.

### Recommendation
After signature verification succeeds for organization `O`, cross-check that `repository.full_name`'s owner also equals `O` (or, better, resolve the `Repository`/`Stack` by `repository.owner.login`/`organization.login` rather than trusting `repository.full_name` independently) before invoking any handler. Reject the webhook (422) if the two fields disagree.

### Proof of Concept
1. Onboard/operate `MyOrg` on a shared Shipit instance with its own legitimate `webhook_secret`.
2. Craft:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "VictimOrg/critical-repo", "owner": { "login": "MyOrg" } }
}
```
3. Compute `X-Hub-Signature` using `MyOrg`'s known `webhook_secret` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "MyOrg")` and validates successfully. `PushHandler` then resolves `Repository.from_github_repo_name("VictimOrg/critical-repo")` and calls `sync_github`/continuous-delivery flows on `VictimOrg`'s stacks, despite the attacker never authenticating as `VictimOrg`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
