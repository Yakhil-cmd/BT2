### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` amplified by `ignore_ci` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes GitHub status updates to every `Commit` record matching the raw `sha` from the webhook payload, with no check against the repository that authenticated the request. Because a stack with `ignore_ci: true` treats CI as fulfilled once any status of the required context exists, a forged/replayed status for a shared SHA can flip deployability for a victim stack that never authenticated that event.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository.full_name == params.dig('repository','full_name')`, but this equality is never checked.

`StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This is a bare `sha` lookup across the entire `commits` table, with no `stack_id`/repository scoping. Contrast this with `PushHandler#process`, which scopes to `stacks.not_archived.where(branch:)` before acting [2](#0-1) , i.e. push events are constrained to the stacks associated with the authenticated repository, while status events are not.

`WebhooksController#verify_signature` only validates the HMAC signature against the GitHub App configured for the payload's `repository_owner` (organization level), not against the specific repository:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
``` [3](#0-2) 

So any repository within the same GitHub App installation (organization) that emits a signed `status` webhook is authenticated only at the org level — the handler itself never re-validates that the SHA actually belongs to the repository that signed the request. If a `Commit` with the same `sha` exists under a different `Stack` (e.g. multiple stacks/repos sharing commit history through forks, submodules, or repos migrated/renamed under the same org), `StatusHandler` will happily attach the attacker-controlled `state`/`context: ci/circleci` to that unrelated commit via `Status.replicate_from_github!` [4](#0-3) .

Once a `Status` row exists, `Status#enable_ci_on_stack` calls `commit.stack.enable_ci!` unconditionally [5](#0-4) , and `after_commit :schedule_continuous_delivery` reevaluates whether the commit is now deployable, feeding into `Stack`/`Commit` deployability logic (`ignore_ci`-flagged stacks were confirmed to reference `ignore_ci` directly in `app/models/shipit/commit.rb`, with `deployable?` methods present in both `stack.rb` and `commit.rb`).

### Impact Explanation
An attacker who controls a commit `sha` shared with a victim stack (through any legitimate cross-repo SHA collision path, e.g. forked/renamed/migrated repositories under the same GitHub organization) can inject arbitrary `state`/`context` status records onto the victim's commit without that victim repository ever having authenticated the webhook. Combined with `ignore_ci: true`, this can force a commit to appear "shippable" and trigger continuous deployment, or conversely block a legitimate deploy — an unauthorized deploy/rollback affecting a stack/repository that did not send the triggering request. This matches the "payload for one repository mutating another's stack/commit" Critical impact category.

### Likelihood Explanation
This requires: (1) a `status` webhook signed validly for some repository under the same GitHub App/organization installation as the victim stack, and (2) a `Commit` row with a matching `sha` already existing under the victim's stack (i.e., real SHA reuse across stacks, most plausible with shared/forked history or multiple stacks tracking overlapping git ancestry), and (3) the victim stack configured with `ignore_ci: true` for `ci/circleci`. The attacker does not need any Shipit credentials — only the ability to trigger a `status` event on a repository within the installation. The precondition of SHA reuse across independent commits (not just shared ancestor history) limits arbitrary cross-tenant exploitation somewhat, but the code path itself performs zero validation that the sha belongs to the requesting repository, which is the underlying defect being asked about.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook: resolve target stacks via `stacks` (repository-scoped, as `PushHandler` does) and filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, or compare `commit.stack.repository.full_name` against `params.dig('repository', 'full_name')`/`repository_owner` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
test "StatusHandler must not update commits belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # repository "shopify/shipit-engine"
  victim_stack.update!(ignore_ci: true, required_statuses: ['ci/circleci'])
  shared_sha = 'deadbeef' * 5

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:walrus))

  # Attacker owns a different repository under the same GitHub App org,
  # and triggers a status event for the same sha with a forged success state.
  forged_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/circleci',
    'repository' => { 'full_name' => 'attacker/other-repo', 'owner' => { 'login' => 'shopify' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new(forged_payload).call
  end

  refute victim_commit.reload.deployable?
end
```
Before the fix: `victim_commit.statuses.count` increases and `deployable?` becomes true even though `attacker/other-repo` never authenticated for `victim_stack`'s repository — demonstrating the broken `commit.stack.repository.full_name == payload.repository.full_name` binding. After scoping `StatusHandler` to the authenticated repository, the assertion holds.

**Caveat**: I could not directly view the body of `Commit#deployable?` / `Stack#deployable?` and the exact `ignore_ci` short-circuit logic within this session (only confirmed their existence via grep matches), so the precise mechanics of how `ignore_ci` bypasses CI requirements are inferred from method presence rather than fully read source. The core defect — `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup with no repository check, contrasted with `PushHandler`'s repository-scoped `stacks` — is directly confirmed from source.
