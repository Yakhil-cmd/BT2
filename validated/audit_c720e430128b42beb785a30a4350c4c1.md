### Title
Wrong Variable in Governing Node Vote Consistency Check Allows Governance Authority Transfer to Non-Council Member - (File: `kaiax/gov/headergov/impl/header.go`)

---

### Summary

In `checkConsistency`, the `gov.GovernanceGoverningNode` case validates a vote to change the governing node by checking whether the **current** governing node (`params.GoverningNode`) is in the council — instead of checking whether the **proposed new** governing node (`vote.Value().(common.Address)`) is in the council. This is a direct analog to the "useless assertion" bug: the wrong variable is compared, making the guard permanently ineffective and allowing governance authority to be transferred to any arbitrary address.

---

### Finding Description

In `kaiax/gov/headergov/impl/header.go`, the `checkConsistency` function handles the `GovernanceGoverningNode` vote case as follows:

```go
case gov.GovernanceGoverningNode:
    params := h.GetParamSet(blockNum)
    if params.GovernanceMode != "single" {
        return nil
    }
    council, err := h.ValSet.GetCouncil(blockNum - 1)
    if err != nil {
        return err
    }
    if slices.Contains(council, params.GoverningNode) {  // BUG: checks current, not proposed
        return nil
    }
    return ErrGovNodeNotInValSetList
``` [1](#0-0) 

The intent of this check — as evidenced by the error name `ErrGovNodeNotInValSetList` — is to reject a vote that would set a non-council member as the new governing node. The correct check should be:

```go
if slices.Contains(council, vote.Value().(common.Address)) {
```

Instead, the code checks `params.GoverningNode` (the **current** governing node), which is already in the council under normal chain operation. As a result, the guard always passes when the chain is in a healthy state, and the proposed new governing node address is never validated against the council.

This function is called from two entry points:
1. `VerifyVote` during block header validation (on-chain enforcement)
2. The `Vote` API handler (`api.go`) before queuing a vote [2](#0-1) [3](#0-2) 

---

### Impact Explanation

In `single` governance mode (the configuration of Kaia Mainnet and Kairos testnet), only the governing node can cast votes. The governing node can vote to change `governance.governingnode` to any arbitrary address — including one that is not a council member — because the council-membership check examines the **current** governing node (which is in the council) rather than the **proposed** new address.

Once ratified at the next epoch boundary, the new governing node address gains exclusive authority to cast governance votes, including:
- `reward.ratio` — controls KAIA distribution among validators, KIF, and KEF
- `reward.mintingamount` — controls per-block KAIA inflation
- `reward.kip82ratio` — controls proposer vs. staker reward split
- `governance.unitprice` — controls the unit price

This constitutes a governance privilege escalation: a non-validator address acquires the sole authority to alter protected chain parameters that directly govern KAIA reward distribution. [4](#0-3) 

---

### Likelihood Explanation

Exploitation requires the current governing node to act maliciously or be compromised. In single mode, the governing node is a trusted entity. However, the invariant that "only council members can hold governance authority" is a hard security boundary that the code explicitly attempts to enforce via `ErrGovNodeNotInValSetList`. The bug silently nullifies that boundary. Any future compromise of the governing node key, or a malicious governing node operator, can exploit this without any additional privilege.

---

### Recommendation

Replace the check on the current governing node with a check on the proposed new governing node:

```go
// Before (buggy):
if slices.Contains(council, params.GoverningNode) {

// After (correct):
if slices.Contains(council, vote.Value().(common.Address)) {
``` [5](#0-4) 

---

### Proof of Concept

1. The current governing node calls `governance_vote("governance.governingnode", "0xArbitraryNonCouncilAddress")`.
2. `checkConsistency` is invoked. It fetches `params.GoverningNode` (the current governing node, which **is** in the council) and calls `slices.Contains(council, params.GoverningNode)` → `true` → returns `nil` (no error).
3. The vote is queued and inscribed in a block header by the governing node when it next proposes a block.
4. `VerifyVote` on all other nodes calls the same `checkConsistency` path and also passes.
5. At the next epoch boundary, `VerifyGov` confirms the ratification matches the collected votes, and the new governing node address is committed to chain state.
6. From the next epoch onward, `0xArbitraryNonCouncilAddress` is the sole entity authorized to cast governance votes, controlling reward ratios, minting amounts, and other protected parameters — despite never being a validator.

// checkConsistency checks if vote values are consistent with chain states such as other parameters and validator set.
func (h *headerGovModule) checkConsistency(blockNum uint64, vote headergov.VoteData) error {
	switch vote.Name() {
	case gov.GovernanceGoverningNode:
		params := h.GetParamSet(blockNum)

		// compare with governing node only in single mode.
		if params.GovernanceMode != "single" {
			return nil
		}

		// we'll use blockNum-1 for the blocknumber of GetCouncil since blockNum cannot be available(eg. vote)
		// it's definite that the valSet vote is not included in this block
		// so the council(blockNum - 1) and council(blockNum) should be same
		council, err := h.ValSet.GetCouncil(blockNum - 1)
		if err != nil {
			return err
		}

		if slices.Contains(council, params.GoverningNode) {
			return nil
		}
		return ErrGovNodeNotInValSetList
