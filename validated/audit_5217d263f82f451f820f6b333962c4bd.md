## Title
Cross-organization CI status forgery via organization/repository binding mismatch in webhook processing - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) to validate a webhook against based solely on `repository.owner.login` (or `organization.login`) extracted from the *unauthenticated* JSON body, while the event handler that actually mutates state — `StatusHandler#process` — never re-checks that binding at all: it looks up commits globally by `sha` across the entire Shipit instance, with no repository/stack scoping whatsoever. This breaks the equality "organization whose signature authenticated the request == repository/commit that is written."

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unauthenticated JSON payload and uses it only to pick *which* configured GitHub App's `webhook_secret` to check the signature against: [1](#0-0) [2](#0-1) 

This only proves the request was signed with *some* configured organization's secret — it in no way constrains which repository/commit the payload is allowed to reference. In a multi-org Shipit deployment (the engine explicitly supports configuring multiple independent GitHub orgs, each with its own `webhook_secret`, see `lib/shipit.rb#github_app_config`) an entity that legitimately controls one low-trust organization's GitHub App (and therefore knows that org's `webhook_secret`) can produce a validly-signed webhook body containing **arbitrary** JSON fields, because the signature covers the raw body bytes, not any specific field semantics.

`StatusHandler#process`, invoked for the `status` event, then acts on that payload with no repository check at all: [3](#0-2) 

It looks up `Commit.where(sha: params.sha)` — a bare SHA lookup with no `stack_id`/repository scoping — and calls `commit.create_status_from_github!(params)` for every matching commit in the *entire* database, regardless of which organization or repository it belongs to: [4](#0-3) 

Compare this to `PushHandler`/`Handler#stacks`, which correctly scope processing to the repository named in the payload via `Repository.from_github_repo_name(repository_name)`: [5](#0-4) 
`StatusHandler` deliberately bypasses this scoping mechanism entirely.

Since GitHub commit SHAs for public (or previously observed) repositories are knowable/guessable by an attacker (they are simply git object hashes, visible in any public repo history, PR, or CI log), an attacker who controls one organization's webhook secret can forge a `status` webhook naming a SHA that belongs to a *different* organization's stack tracked by the same Shipit instance, and inject a fabricated CI status (`state: "success"`, arbitrary `description`/`target_url`) for that foreign commit.

### Impact Explanation
`Commit#deployable?` and `Commit#status` gate whether a commit is eligible to be deployed and whether continuous delivery proceeds: [6](#0-5) [7](#0-6) 

An attacker who only controls a low-privilege GitHub App/webhook secret for one organization onboarded to a shared Shipit instance can inject a forged "success" status for a commit belonging to a completely different organization's repository/stack, satisfying `required_statuses`/`deployable?` checks and potentially triggering `schedule_continuous_delivery`, leading to an unauthorized deploy of that foreign stack — this is a cross-repository write causing an unauthorized deploy, which falls in the Critical impact category defined by scope rules.

### Likelihood Explanation
Requires only: (1) administrative control of a GitHub App/organization already configured in Shipit's multi-org `secrets.github` config (a legitimate but low-trust tenant, not a privileged Shipit account or GitHub org that owns the target repo), and (2) knowledge of a target commit SHA, which is public information for any repository whose commits are visible (PRs, pushes, CI logs, GitHub API). No `ApiClient` token, session, or `webhook_secret` of the *victim* organization is needed — only the attacker's own organization's secret, which they legitimately possess.

### Recommendation
`StatusHandler` (and any handler relying on cross-cutting lookups like SHA) must scope its processing to the repository actually named in the payload, exactly like `Handler#stacks`/`PushHandler` do — i.e., restrict `Commit.where(sha: params.sha)` to commits belonging to `stacks` derived from `payload.dig('repository','full_name')`, and additionally `verify_signature` should assert that `repository_owner` matches the owner segment of `repository.full_name` before dispatch, so the org that signed the request is provably the org whose repository is being mutated.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `attacker-org` (attacker controls the installed GitHub App and thus knows its `webhook_secret`) and `victim-org` (has a tracked stack with commit `abc123...` currently pending/no status).
2. Attacker crafts a JSON body:
```json
{
  "sha": "abc123...",          // real commit SHA belonging to victim-org's tracked stack
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sends it to `/github_webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: "abc123...")` — finds the victim-org commit (no repository check) — and calls `create_status_from_github!`, recording a forged "success" status on the victim stack's commit (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, `app/models/shipit/commit.rb:165-169`).
6. If that status satisfies `stack.required_statuses`/`ignore_ci?` gating, the victim stack may become `deployable?` and continuous delivery may trigger a deploy the victim never approved.

*Note: I was unable to execute this end-to-end in a live environment; this analysis is based on static code review of the cited files. Confirming the exact deploy-trigger conditions (`required_statuses`, `continuous_deployment?`) for a specific stack config would require examining that stack's `shipit.yml`, which is out of scope per the rules.*
