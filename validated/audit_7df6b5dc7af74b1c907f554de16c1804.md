### Title
Signature verification binds to the payload's declared `repository.owner.login`, but every webhook handler dispatches on the independently-controlled `repository.full_name` field, letting an org whose webhook secret is known authenticate a payload that mutates another org's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret and HMAC-verifies the raw body using an organization derived from the payload itself (`repository.owner.login`, falling back to `organization.login`), rather than from any binding tied to the actual resource the handlers will mutate. [1](#0-0) [2](#0-1) 

Once the signature check passes, every event handler determines which `Repository`/`Stack` to act on using a *different*, independently-attacker-suppliable field of the same JSON body: `repository.full_name`. [3](#0-2) [4](#0-3) 

Shipit explicitly supports multi-tenant configuration with one `webhook_secret` per organization: [5](#0-4) 

### Finding Description
The equality that should hold is: **organization whose secret authenticated the request == organization owning the repository/stack that the handler mutates**. The code breaks this binding because the two fields (`repository.owner.login` used for signing/verification, `repository.full_name` used for dispatch) are both plain, unauthenticated JSON fields inside the same signed body, and nothing cross-checks that they refer to the same organization.

- `verify_signature` looks up `Shipit.github(organization: repository_owner)` and verifies the HMAC using that org's configured `webhook_secret`. [1](#0-0) 
- `repository_owner` is read straight from the attacker-controlled payload (`repository.owner.login` or `organization.login`). [2](#0-1) 
- All default handlers (`PushHandler`, pull-request handlers, etc.) resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, feeding `Repository.from_github_repo_name`, which does a straight `owner/name` DB lookup with no reference back to the org whose secret validated the signature. [3](#0-2) [4](#0-3) [6](#0-5) 

Because `repository.owner.login` and `repository.full_name` are two separate JSON keys the attacker fully controls before signing, an attacker who possesses (or is a legitimate webhook sender for) OrgA's `webhook_secret` can build a payload where `repository.owner.login = "OrgA"` (so the HMAC computed with OrgA's secret validates) while `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a different configured organization, OrgB, that is registered in this Shipit instance). The signature check only proves the sender knows OrgA's secret; it proves nothing about the repository the handlers will actually operate on.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Depending on the handler invoked, the practical outcome is a cross-organization/cross-repository write against Shipit's own state despite valid authentication for a different tenant:
- `push` → `PushHandler` enqueues `GithubSyncJob` against OrgB's stack, causing Shipit to fetch and append OrgB's github commits based on a forged `expected_head_sha`/`ref` under an attacker-chosen effective payload, and to update the review/deployment state of a repository the caller was never authenticated for. [7](#0-6) [8](#0-7) 
- Pull-request handlers similarly resolve `repository.full_name` to archive/unarchive OrgB's review stacks. [9](#0-8) 

This matches the required High/Critical bar (cross-repository writes / unauthorized state changes) since it lets an authenticated-for-org-A actor drive state mutation for org B's stacks, which is only possible in this multi-tenant configuration that Shipit itself documents and supports.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for at least one organization configured on the shared Shipit instance (e.g., they are a legitimate GitHub App admin/webhook operator for their own tenant org in a multi-org Shipit deployment), and for the victim org's repository to already be registered as a `Repository`/`Stack` in that same Shipit instance. This is a realistic scenario for shared/multi-tenant Shipit deployments, which the engine explicitly documents (`config/secrets.development.shopify.yml`, multi-org config block in `docs/setup.md`), but it does not apply to a single-organization Shipit instance where only one `webhook_secret` exists.

### Recommendation
After `verify_signature` succeeds, re-derive the organization used for the HMAC check and assert it matches the organization portion of `repository.full_name` (and of `organization.login`, `sender.login` where relevant) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, pass the verified organization into `Handler#initialize` and have `repository_name`/`stacks` scope lookups to that organization instead of trusting the raw payload's `full_name` independently of the field used for signature verification.

### Proof of Concept
1. Configure Shipit multi-org with `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both having repositories registered as Shipit `Stack`s.
2. Attacker (who controls or is the legitimate webhook sender for `OrgA`) crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over this exact raw body (they know this secret).
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and validates the HMAC successfully with `OrgA`'s secret. [10](#0-9) 
6. `PushHandler#process` resolves `stacks` via `repository_name` = `payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"`, and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack — mutating state belonging to a different, unauthenticated-for org. [3](#0-2) [7](#0-6)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
