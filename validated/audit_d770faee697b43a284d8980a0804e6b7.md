### Title
Commission-update delay (SIMD-0249) can be bypassed for vote accounts missing from the snapshot epoch, letting a validator apply a raised commission before the intended one-epoch notice period elapses - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
The `delay_commission_updates` mechanism is meant to guarantee that a commission increase cannot affect reward distribution until a full epoch has passed, protecting delegators from "last-minute commission rugs." The delay is implemented by falling back through two cached, epoch-boundary vote-account snapshots. When a vote account is absent from the older ("snapshot_epoch") snapshot, the code silently falls back to the newer ("rewarded_epoch") snapshot, which can already contain a commission raised mid-epoch, since the on-chain rule that restricted increases to the first half of an epoch is explicitly disabled once `delay_commission_updates` is active.

### Finding Description
Commission changes are applied to vote-account state immediately by `update_commission`, and the old "only allowed in first half of epoch" restriction is only enforced when `delay_commission_updates` is *not* active: [1](#0-0) [2](#0-1) 

Because that timing rule is disabled once the delay feature is live, the intended protection for delegators is supposed to come entirely from the reward-calculation side: rewards should be computed using a commission value that is at least one full epoch stale, per the comment in `get_cached_vote_accounts`: [3](#0-2) 

That function builds two candidate snapshots:
- `snapshot_epoch_vote_accounts` = vote accounts as of `epoch_stakes(rewarded_epoch)` (taken a full epoch before use, intended to be immune to same-epoch commission edits).
- `rewarded_epoch_vote_accounts` = vote accounts as of `epoch_stakes(self.epoch())` (the *current* epoch's stake snapshot, taken at epoch-boundary but still much closer in time and computed from state that already reflects commission changes submitted during the rewarded epoch).

The actual commission used for a stake account's reward is chosen with a fallback chain that prefers the older snapshot but falls through to the newer one if the vote account isn't present there: [4](#0-3) 

The vote account is absent from `snapshot_epoch_vote_accounts` whenever it had no delegated stake recorded in that older epoch-stakes snapshot (e.g., it is newly created, or it temporarily had zero effective delegated stake at that snapshot boundary). In that case the code uses `rewarded_epoch_vote_accounts` instead — i.e., the vote account's commission as observed at the *beginning of the same epoch that is being rewarded*, which can already embed a commission change made earlier in that same epoch (since, as shown above, mid-epoch commission increases are permitted once `delay_commission_updates` is enabled). If the vote account is also missing from that second snapshot, the code falls back to the *live* current vote state (`vote_state`), which trivially includes any commission change made at any point, including immediately before reward distribution.

The unit tests for this exact code path acknowledge and exercise this fallback as intended behavior for "new" vote accounts, but do not distinguish a genuinely new account from a validator that strategically ensures it is absent from the epoch-N snapshot (e.g., no delegated stake recorded at that boundary) and then re-attracts stake and raises commission within the very epoch being rewarded: [5](#0-4) 

### Impact Explanation
If a malicious/self-interested validator can arrange for their vote account to be absent from the `epoch_stakes(rewarded_epoch)` snapshot (e.g., because their delegated stake was fully deactivated/zero at that specific epoch-boundary snapshot, or the account is newly (re)created), they can raise their commission mid-epoch — which the on-chain rule now permits since `delay_commission_updates` disables the "first half of epoch" gate — and have that higher commission applied immediately to reward distribution for that same epoch, rather than being delayed by a full epoch as the mechanism is documented to guarantee. This results in delegators receiving less than the expected reward and the validator's commission-collector account receiving a larger, un-telegraphed cut — a misattribution/theft-of-lamports outcome for the affected delegators, achieved purely through normal, permissionless `UpdateCommission` instructions and ordinary stake (de)activation, with no special validator/operator privilege beyond being the vote account's withdraw authority.

### Likelihood Explanation
Likelihood is moderate: it requires the vote account to be missing delegated stake at the specific epoch_stakes(rewarded_epoch) snapshot boundary, and depends on stake activation/deactivation timing that a determined operator can engineer (e.g., timing full deactivation of self-stake to intentionally miss the snapshot, then quickly reactivating and raising commission within the same epoch). Ordinary rotation of delegators or genuinely new vote accounts will also legitimately hit this fallback, which somewhat masks intentional abuse and reduces the chance of easy detection.

### Recommendation
Do not fall back to `rewarded_epoch_vote_accounts` (or live state) purely because the vote account is absent from the older snapshot when the vote account already existed prior to that epoch. Only apply the "new vote account" fallback when the vote account itself did not exist as of the target snapshot epoch (not merely "had no delegated stake" or "missing from the stakes map"), so that an existing validator cannot game the mechanism by manipulating delegation timing to escape the intended one-epoch delay. Alternatively, track and use the vote account's commission value directly (with its own delayed-effect timestamp/epoch), independent of whether it appears in the delegated-stake snapshot for a given epoch.

### Proof of Concept
1. Validator `V` operates a vote account with commission `C0` and has delegated stake through epoch `N-1`.
2. Just before epoch `N`'s `epoch_stakes(N)` snapshot is taken, `V` ensures its vote account has zero effective delegated stake (e.g., fully deactivates self-stake), so it does not appear in `stakes().vote_accounts()` for epoch `N` — this is exactly the "missing from cache" condition handled at [6](#0-5) .
3. Early in epoch `N`, delegators (re)delegate stake to `V`'s vote account.
4. Mid-epoch `N`, `V` submits `UpdateCommission` to raise commission from `C0` to `C1` (allowed at any slot position because `delay_commission_updates` disables `is_commission_update_allowed` enforcement, per [7](#0-6) ).
5. At epoch `N`'s reward distribution, `redeem_delegation_rewards` looks up `snapshot_epoch_vote_accounts` (epoch `N`'s stakes snapshot) — `V` is absent — and falls back to `rewarded_epoch_vote_accounts`, which already reflects commission `C1`, per [8](#0-7) .
6. Delegators' rewards for epoch `N` are computed using `C1` instead of `C0`, one full epoch earlier than the mechanism's documented guarantee — reproducing the same "double-set within the latency window bypasses the timelock" bug class described in the external report, adapted to Agave's vote-commission delay design.

pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

    /// Get cached vote account state from the past few epochs so that some vote
    /// state configuration changes are delayed before being used in reward
    /// calculation.
    fn get_cached_vote_accounts<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        distribution_epoch_vote_accounts: &'a VoteAccounts,
    ) -> CachedVoteAccounts<'a> {
        // Snapshot of vote account state from the beginning of the epoch prior to
        // the rewarded epoch. This snapshot state is saved a full epoch before
        // being used to prevent last minute commission rugs.
        let snapshot_epoch_vote_accounts = self
            .epoch_stakes(rewarded_epoch)
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        // Vote account state from the beginning of the rewarded epoch.
        let rewarded_epoch_vote_accounts = self
            .epoch_stakes(self.epoch())
            .map(|epoch_stakes| epoch_stakes.stakes().vote_accounts());

        CachedVoteAccounts {
            snapshot_epoch_vote_accounts,
            rewarded_epoch_vote_accounts,
            distribution_epoch_vote_accounts,
        }
    }

        // delay the effect of commission updates by at least one
        // full epoch.
        // When `commission_rate_in_basis_points` is true, use the new field
        // `inflation_rewards_commission_bps`; otherwise use the legacy
        // percentage field and convert to basis points by multiplying by 100.
        let commission_bps = if delay_commission_updates {
            let vote_state_for_commission = snapshot_epoch_vote_accounts
                .and_then(|eva| eva.get(&vote_pubkey))
                .or_else(|| rewarded_epoch_vote_accounts.and_then(|eva| eva.get(&vote_pubkey)))
                .map(|vote_account| vote_account.vote_state_view())
                .unwrap_or(vote_state);
            if commission_rate_in_basis_points {
                vote_state_for_commission.inflation_rewards_commission()
            } else {
                vote_state_for_commission.commission() as u16 * 100
            }

            vote_state.inflation_rewards_commission()
        } else {
