### Title
Webhook signature verification is keyed by `repository.owner.login`/`organization.login` while every event handler acts on `repository.full_name` — allows cross-organization webhook forgery in multi-org Shipit deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook based on `repository.owner.login` (falling back to `organization.login`) taken directly from the unauthenticated JSON body. All downstream event handlers, however, resolve the target `Stack`/`Repository` using a *different* field of the same body: `repository.full_name`. Because these two fields are never cross-checked, and the HMAC only proves "this body was signed with the secret of whichever org name appears in the body," a party who legitimately possesses the `webhook_secret` for one configured organization can forge a signed payload whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` points at a repository belonging to a *different* organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` derives the authenticating organization purely from attacker-controlled JSON, then fetches that organization's `GitHubApp` and verifies the signature against it: [1](#0-0) [2](#0-1) 

The secret used is `Shipit.github(organization: repository_owner)`'s `webhook_secret`, verified with a straightforward HMAC over the raw body: [3](#0-2) 

Multi-organization deployments are an explicitly documented and supported configuration, each org having its own independent `webhook_secret`: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the *entire* raw JSON to all registered handlers for the event, with no re-validation that the repository/org referenced by the handler matches the org whose secret produced the signature: [6](#0-5) 

Every handler independently resolves its target repository/stack from `repository.full_name`, a field that was never covered by the org-selection logic used in `verify_signature`: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

This is the same trust-binding defect pattern as the referenced report: the field that is cryptographically *authenticated* (the org used to pick the HMAC key, sourced from `repository.owner.login`/`organization.login`) is not the field that is subsequently *acted upon* (`repository.full_name`, used to select which Stack/Repository/Commit is mutated). Since the signature covers the raw body but the body's own contents determine both which secret verifies it and which unrelated repository is targeted, an attacker who legitimately holds one organization's `webhook_secret` (e.g. an app installed across multiple orgs onboarded onto a shared Shipit instance, per the documented multi-org config) can self-sign a payload naming their own org in `repository.owner.login`/`organization.login`, but naming a victim org's repository in `repository.full_name`. `verify_signature` succeeds (correct secret for the org name in the body), and the handler then operates on the victim's repository/stack.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding described in scope. Concrete consequences depending on event/handler:
- `push` → `PushHandler` resolves stacks via `repository.full_name` and enqueues `GithubSyncJob`, which syncs commits from GitHub into the victim stack and can advance the deployable commit queue for the victim repository — a cross-repository write into Shipit's tracked state for a repo the attacker's own webhook secret was never scoped to. [11](#0-10) 
- `status` → `StatusHandler` writes forged CI statuses onto arbitrary commits by `sha` (global lookup, not even repo-scoped), which can influence deployability checks for any tracked commit. [10](#0-9) 
- `pull_request` → handlers such as `OpenedHandler`/`LabeledHandler` create/archive/unarchive review stacks for the victim repository based purely on `repository.full_name`. [9](#0-8) [12](#0-11) 

This crosses a repository/organization trust boundary that the webhook-secret model is meant to enforce, resulting in cross-repository writes to Shipit's tracked deployment state — matching the in-scope Critical impact category ("cross-repository writes"), and can indirectly influence deploy eligibility (status/commit state) for repositories the attacker's own credential was never authorized for.

### Likelihood Explanation
Exploitation requires the attacker to already legitimately hold a `webhook_secret` for at least one organization configured on the same Shipit instance (the documented multi-org setup). This is a real, supported deployment topology (`config/secrets.development.shopify.yml`, `lib/shipit.rb#github_app_config`), so any tenant/org onboarded to a shared instance is a candidate attacker against every other onboarded org — the attacker does not need any Shipit session, API token, or the victim org's secret. No GitHub-side spoofing is needed since GitHub's own delivery guarantees are irrelevant here — the attacker sends the forged request directly to Shipit's `/webhooks` endpoint.

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the acted-upon repository. Concretely, `verify_signature` (or the handlers) should re-derive/validate that `repository.full_name`'s owner matches the same organization whose secret validated the signature (e.g. require `repository.full_name.split('/').first == repository_owner`, or better, resolve the target `Repository`/`Stack` first and verify the signature using the secret configured for that specific repository's owner, rejecting mismatches).

### Proof of Concept
1. Attacker administers Org A, which is one of several organizations configured in a shared Shipit instance (`secrets.github.orgA.webhook_secret`, `secrets.github.orgB.webhook_secret`), per the supported multi-org schema.
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` using their own known Org A secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#repository_owner` returns `"orgA"` → `verify_signature` validates successfully against Org A's secret (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
6. `PushHandler#stacks` looks up `Repository.from_github_repo_name("orgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim's stacks — despite the attacker only ever proving control of Org A's secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
