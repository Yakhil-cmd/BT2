**Rationale:**

The `A_BLINDER`/`B_BLINDER` constants cited in the question are declared with the `#[test_only]` attribute in `ristretto255_bulletproofs.move` [1](#0-0) , meaning the Move compiler excludes them from any non-test build target — they are not reachable from production code paths at all, let alone the transaction-admission stack.

`pedersen::new_commitment_for_bulletproof` itself is a generic cryptographic primitive that takes a value and randomness scalar supplied entirely by the caller [2](#0-1) ; it makes no claim about enforcing sender-specific entropy, and the module's own doc comments state the commitment binding responsibility (choosing unpredictable `r`) belongs to the caller, not this primitive [3](#0-2) . The verifier (`verify_range_proof_pedersen`) only checks that a value inside a given commitment is in-range and matches the domain-separation tag — it never claims or attempts to bind the proof to a specific sender/account [4](#0-3) .

This module is part of `aptos-stdlib`'s generic cryptography library, not part of the mempool, vm-validator, authenticator, or VM signature-verification code that governs transaction admission (sender/signer/sequence/chain-id/expiry binding). No downstream production module was found that reuses these test-only constants — the finding requires a hypothetical "downstream module mistake" that doesn't exist in the reviewed code and is out of scope per the boundary conditions restricting review to admission-path code.
