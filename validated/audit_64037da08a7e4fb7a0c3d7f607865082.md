### Title
Unprivileged dust `supply` into a victim's existing position silently restamps their cached liquidation risk parameters - (File: contracts/controller/src/positions/supply.rs)

### Summary
`supply` allows any unprivileged caller to add tokens to an *existing* supply position of an account they do not own or delegate for (`require_third_party_existing_supply` only checks that the hub-asset key already exists in `account.supply_positions`). Every merged supply leg then calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, which overwrites the position's stamped entry LTV, liquidation threshold, liquidation bonus, and liquidation fees with the *current* spoke/market parameters. An attacker can therefore inject a 1-stroop supply leg into a victim's collateral leg and forcibly discard the victim's grandfathered risk tuple — a direct analog of CVE-2019-11282's "crafted request content mutates another user's data through a scope the victim did not authorize."

### Finding Description
The protocol deliberately caches per-position risk weights (`entryLtvBps`, `entryLiquidationThresholdBps`, `entryLiquidationBonusBps`, `entryLiquidationFeesBps`) so that a governance parameter change does not retroactively rewrite open positions; they are restamped only on owner-driven actions (supply, withdraw, `update_account_threshold`, and LTV-only refreshes on borrow/strategy calls). [1](#0-0) [2](#0-1) 

However, `process_supply` splits authorization awkwardly:

1. `require_third_party_existing_supply` permits a third party to supply into any hub-asset the account already holds — no owner/delegate auth is required for those legs. [3](#0-2) 
2. `merge_supply_leg` unconditionally calls `refresh_supply_risk_params(..., RiskRefreshScope::FullTuple)` on the victim's position for every leg, including attacker-funded ones. [4](#0-3) 

The amount is attacker-chosen and only must be positive (`aggregate_positive_payments`, `AmountMustBePositive`), so a single base unit suffices. [5](#0-4)  The threat model explicitly acknowledges third-party top-ups as intended ("supply top-ups require existing positions") but treats them as risk-neutral, which the `FullTuple` restamp contradicts. [6](#0-5) 

### Impact Explanation
Theft of user funds. After governance tightens a market (lower `liquidation_threshold`, higher `liquidation_bonus`/`liquidation_fee`, lower LTV), existing positions keep their old, more favorable stamped tuple by design. An attacker can:

- restamp the victim's collateral leg to the new lower threshold, pushing the account's health factor below 1 and then liquidating it for the bonus, or
- restamp to a higher liquidation bonus/fee so an already-liquidatable victim loses more collateral and pays more protocol fee per seized unit than their entry terms implied.

Either way the victim suffers collateral loss they were grandfathered against, induced by a request they never authorized — the same "injected content alters another user's record" shape as the SCIM injection, with on-chain economic loss instead of information disclosure.

### Likelihood Explanation
Requires only: (a) the victim has an existing supply position in a spoke asset, and (b) that asset's current risk config differs unfavorably from the victim's stamped tuple — i.e., any tightening governance operation creates the precondition for every open position in that market. The attack costs one base unit of the asset plus fees, needs no privileges, no flash capital, and can be batched across many victims in one transaction per account. Likelihood is bounded by how often governance tightens parameters, but the window after each such change is permanent for every stale-stamped position.

### Recommendation
In `merge_supply_leg`, only run `refresh_supply_risk_params` when `caller` is owner-or-delegate of the account (or pass a flag computed once in `process_supply` mirroring the `require_third_party_existing_supply` check). Third-party top-ups should credit shares at the current index but leave `entry_*` fields untouched. Alternatively, skip the `FullTuple` restamp for legs the caller funded but does not own, and let `update_account_threshold` remain the explicit (already public, but at least transparent and single-purpose) restamp path.

### Proof of Concept
1. Alice supplies 10,000 USDC when `liquidation_threshold = 0.85`, `bonus = 5%`; her position stores `entry_liquidation_threshold_bps = 8500`.
2. Governance later executes an operation lowering USDC threshold to 0.70 and raising bonus to 15%. Existing stamped positions retain 0.85 by design.
3. Attacker calls `controller.supply(attacker, alice_account_id, spoke_id, [(HubAssetKey{hub_id, USDC}, 1)])`. `require_third_party_existing_supply` passes because Alice already holds USDC; `merge_supply_leg` restamps her leg to 0.70/15%.
4. Alice's health factor drops below 1 (or her already-liquidatable position now pays 15% instead of 5%); attacker calls `liquidate` and seizes collateral at the new, worse terms — profit funded by Alice's forcibly rewritten risk tuple.

fn require_third_party_existing_supply(
    env: &Env,
    account_id: u64,
    resolved_account_id: u64,
    caller: &Address,
    account: &Account,
    aggregated: &AggregatedPayments,
) {
    if account_id != 0
        && !account::is_owner_or_delegate(env, resolved_account_id, caller, &account.owner)
    {
        for (hub_asset, _) in aggregated.iter() {
            assert_with_error!(
                env,
                account.supply_positions.contains_key(hub_asset.clone()),
                GenericError::NotAuthorized
            );
        }
    }
}

pub(crate) fn merge_supply_leg(
    env: &Env,
    account: &mut Account,
    action: &PoolAction,
    result: &PoolPositionMutation,
    cache: &mut Context,
) {
    let hub_asset = &action.hub_asset;
    let asset_config: AssetConfig = cache.require_spoke_asset(account.spoke_id, hub_asset);

    let mut position = account.get_or_create_supply_position(hub_asset, &asset_config);
    let old_scaled = position.scaled_amount;

    refresh_supply_risk_params(
        env,
        cache,
        account,
        hub_asset,
        &mut position,
        &asset_config,
        RiskRefreshScope::FullTuple,
    );

    let outcome = LegOutcome::from(result);
    position.scaled_amount = outcome.new_scaled;
