### Title
Fee-on-transfer ERC20 tokens permanently trap the withdrawn (post-fee) amount in the shared `TransfersCheckingAccount` when used through `ERC20Transactor` - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` treat a successful `IERC20::transfer` boolean return value as proof that the *entire requested `amount`* moved, without ever comparing the checking account's actual ERC20 balance before/after the call. Any ERC20 contract that implements a fee-on-transfer (or otherwise delivers less than `value` while still returning `true`) causes the XCM holding register to be credited with more tokens than the `TransfersCheckingAccount` actually received, so a subsequent `DepositAsset` for that inflated amount fails and the real, reduced amount is left stranded in the checking account with no extrinsic path to recover it — the same root cause and impact class as the referenced Allo `DonationVotingMerkleDistributionVaultStrategy` report (assume `amount` transferred == `amount` recorded, no pre/post balance diff check).

### Finding Description
`ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` tuple (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:240-246`) and is reachable by any signed account via `pallet_xcm::execute` (demonstrated directly by the existing test `withdraw_and_deposit_erc20s` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`, which builds and dispatches exactly this XCM program). The ERC20 contract itself is fully attacker-controlled: `pallet_revive::Config::InstantiateOrigin = EnsureSigned<Self::AccountId>` (seen for the reference `substrate/bin/node/runtime/src/lib.rs:1575`), so any signed user can deploy an arbitrary WASM/EVM ERC20 contract and reference it by `AccountKey20` in the XCM `Asset` location — no privileged role required.

Root cause, in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`:
- `withdraw_asset_with_surplus` (lines 150-216) calls `IERC20::transferCall{ to: checking_address, value: amount }` from the user to the shared `TransfersCheckingAccount`. On `Ok(true)` it unconditionally mints holding credit for the full requested `amount`:
```
if is_success {
    Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
}
```
There is no check of `balanceOf(checking_address)` before/after — exactly the missing check flagged in the Allo report.
- `deposit_asset_with_surplus` (lines 225-306) mirrors this on the way out: it calls `transfer(beneficiary, amount)` *from* the checking account and only inspects the boolean return value.

If the ERC20 contract skims a fee on transfer (e.g. burns/redirects X% to a third party while still returning `true`), the checking account's real balance increase after `withdraw_asset_with_surplus` is `amount - fee`, but the XCM executor's holding register believes it holds the full `amount` (this credited `Erc20Credit` amount is a synthetic, unconstrained imbalance type per its own doc comment: "does not perform runtime-level balance enforcement... actual balance constraints are enforced by the ERC20 smart contract"). When the program later executes `DepositAsset`/`InitiateTransfer` for that inflated `amount` (e.g., depositing to a different beneficiary or forwarding cross-chain), `deposit_asset_with_surplus` issues `transfer(beneficiary, amount)` from the checking account, which the fee-on-transfer contract will refuse (insufficient balance) or itself skim again, so the instruction returns `XcmError::FailedToTransactAsset`.

Per `xcm-executor::lib.rs` `transactional_process` (`polkadot/xcm/xcm-executor/src/lib.rs:900-928`) and `DepositAsset`'s handling (`polkadot/xcm/xcm-executor/src/lib.rs:1186-1197`), only the *failing* `DepositAsset` instruction is rolled back at the holding-register level; the earlier, already-committed `WithdrawAsset` instruction (which performed the real, on-chain ERC20 transfer moving `amount - fee` into the checking account) is not undone, because it succeeded and its storage effects were already committed outside the failing transactional block. The net observable outcome is `Outcome::Incomplete` (see `polkadot/xcm/xcm-executor/src/tests/deposit_with_retry.rs` and `initiate_transfer.rs` for the general "trap on failed deposit" pattern) — but the *trap* mechanism (`Config::AssetTrap`) only knows about the executor's synthetic holding-register credit (`Erc20Credit(amount)`), not the real, smaller ERC20 balance backing it. The token actually delivered into the checking account (`amount - fee`) sits in a pallet-controlled account (`ERC20TransfersCheckingAccount`) that has no dedicated extrinsic to reclaim it; it is not withdrawable by ordinary users, unlike `pallet_balances`/`pallet_assets`, whose `transfer` implementations return the *actual* transferred amount from `decrease_balance`/`increase_balance` (see `substrate/frame/support/src/traits/tokens/fungible/regular.rs:321-339` and `fungibles/regular.rs:373-393`), which is exactly the fix the Allo report recommended and which FRAME's own asset traits already implement — but `ERC20Transactor` bypasses this pattern entirely by trusting the ERC20 boolean return instead of measuring the real balance delta.

### Impact Explanation
Funds (the ERC20 tokens actually received by the checking account, post-fee) become permanently unreachable by the user who withdrew them, and by anyone else, since the checking account is only moved by the `ERC20Transactor`'s own internal logic driven by XCM instructions that assume the un-skimmed `amount` — a mismatch that reproduces every time the same fee-on-transfer token is routed through this path. This is a Medium-severity "funds trapped" bug, matching the cited report's own severity, not a direct theft, because (a) each ERC20 contract's checking-account balance is isolated per-contract (no cross-user pool draining), and (b) the failure mode is a stuck deposit rather than an inflated payout to an attacker.

### Likelihood Explanation
Likelihood is Medium: it requires only (1) a signed account instantiating an arbitrary contract via `pallet-revive` (permissionless on the reference runtime), and (2) using `pallet_xcm::execute`/`transfer_assets` with that contract's `AccountKey20` as the asset location — both ordinary, unprivileged user actions already exercised by the codebase's own `withdraw_and_deposit_erc20s` test. No governance, no validator/collator collusion, no stolen keys are needed. The main uncertainty is whether the currently deployed/whitelisted set of ERC20 contracts accepted by `ERC20Matcher` on live Asset Hub is restricted to a fixed allow-list (which would gate this to any token later trusted by governance rather than fully arbitrary user-supplied contracts); the reference code shows `Matcher: MatchesFungibles<H160, u128>` as a generic parameter and the test uses an arbitrary freshly-compiled contract, suggesting no runtime-level allow-list is enforced by the transactor itself.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf(checking_address)` (or the source/beneficiary) immediately before and after the `IERC20::transfer` call and use the *actual* balance delta as the amount credited to/debited from the XCM holding register, instead of assuming the requested `amount` was moved in full whenever the call returns `true`. This mirrors the fix already applied throughout FRAME's own fungible/fungibles traits, which return the real transferred amount from `decrease_balance`/`increase_balance` rather than echoing the caller's requested amount.

### Proof of Concept
Not executed against a live network; no test run was performed and none is claimed. A reproduction path exists conceptually using the codebase's own harness:
1. Compile a minimal Solidity/EVM ERC20 whose `transfer()` skims e.g. 10% to a fixed burn/fee address while still returning `true` (a straightforward variant of the fixture used in `substrate/frame/revive/fixtures/contracts/external/openzeppelin/contracts/token/ERC20/ERC20.sol`).
2. Deploy it via `pallet_revive::bare_instantiate` from an unprivileged signed account (as done in `withdraw_and_deposit_erc20s`, `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`).
3. Build an XCM program: `withdraw_asset((AccountKey20{fee_token}, 100))`, then `deposit_asset(AllCounted(1), beneficiary)`, dispatched via `PolkadotXcm::execute`.
4. Expected/failed guard: `withdraw_asset_with_surplus` succeeds and credits holding with `Erc20Credit(100)`; the real checking-account ERC20 balance increases by only 90. `deposit_asset_with_surplus` then issues `transfer(beneficiary, 100)` from the checking account, which reverts/fails for insufficient balance, yielding `Outcome::Incomplete`/`FailedToTransactAsset`. Actual state: checking account keeps the 90 tokens with no extrinsic able to move them out; expected state (per correct accounting): holding should have only ever recorded 90, and depositing 90 to the beneficiary should have succeeded, leaving nothing trapped.
