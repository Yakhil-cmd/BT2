### Title
Webhook signature verification uses `repository.owner.login` while push handling trusts `repository.full_name`, allowing a repo owned by one GitHub org to trigger a sync on a different org's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC-verifying `GitHubApp` using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. `Shipit::Webhooks::Handlers::Handler#repository_name` (used by `PushHandler#process`) instead resolves the target stack via `payload.dig('repository', 'full_name')`. Nothing in the controller or handler enforces that these two fields refer to the same repository/organization, so an attacker who controls a valid webhook secret for their own organization can forge a payload naming a victim repository and have `stack.sync_github` invoked on the victim's stack.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`organization_that_signed_the_bytes` (`params.dig('repository','owner','login')` in `verify_signature`, [1](#0-0) ) `==` `organization_owning_the_mutated_stack` (derived from `payload.dig('repository','full_name')` in `Handler#repository_name`, [2](#0-1) ).

Trace:
1. `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs before `#create`. `verify_signature` calls `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature`, then only `head(422)` on failure — no exception raised on success path that would stop `#create` from proceeding, and the value used for org selection is `repository.owner.login`, not `repository.full_name`. [3](#0-2) 
2. `#create` re-parses `request.raw_post` into `params` and dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the same JSON payload. [4](#0-3) 
3. `PushHandler#process` finds stacks via `stacks` → `Repository.from_github_repo_name(repository_name)`, where `repository_name = payload.dig('repository', 'full_name')`. [5](#0-4) [6](#0-5) 
4. `Shipit.github_app_config`/`Shipit.github` support a genuine multi-org `secrets.yml` schema keyed by organization login, confirming that distinct organizations legitimately have distinct `webhook_secret`s in production deployments. [7](#0-6) 

Attacker request: the attacker owns `attacker-org` with a real installed Shipit GitHub App and knows/controls its `webhook_secret` (a legitimate credential for their own org). They send `POST /webhooks` with `X-Github-Event: push`, `X-Hub-Signature` computed over the raw body using `attacker-org`'s secret, and a body where `repository.owner.login == "attacker-org"` (used only for signature-org selection) but `repository.full_name == "victim-org/victim-repo"` (used only for stack resolution), plus `ref: refs/heads/master` and an attacker-chosen `after` SHA.

Exploit flow: `verify_signature` fetches `Shipit.github(organization: 'attacker-org')`, HMACs the raw body with the attacker's own known secret, and it matches — verification succeeds legitimately for attacker-org's bytes. `#create` then hands the same payload to `PushHandler`, which never re-checks `repository.owner.login` against `repository.full_name`; it resolves `victim-org/victim-repo`'s stacks directly from `full_name` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack, on the `master` branch. This bypasses the intended guarantee that only GitHub, holding the org's shared secret, can trigger events for that org's repos — because the two fields consulted for "who signed this" and "whose repo do I act on" are independent, attacker-controlled JSON keys with no cross-validation.

None of the listed guards mitigate this: `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` (`PushHandler.params`) only validates presence of `ref`/`after`, not repository/owner consistency; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` in this unauthenticated webhook path; `Repository.from_github_repo_name` looks up by `full_name` alone with no organization check.

### Impact Explanation
A single POST causes `GithubSyncJob`-driving logic (`stack.sync_github(expected_head_sha:)`) to run against an arbitrary victim `Shipit::Repository`/`Stack` that the attacker does not own or control, using only a secret the attacker legitimately possesses for their own unrelated organization. This is a cross-tenant write: any organization with its own valid Shipit webhook secret (a routine, low-privilege credential in a multi-org deployment) can force syncs on any other onboarded organization's non-archived stacks on any branch name they can specify. The attack is fully repeatable against arbitrary victim repositories/branches by simply changing `full_name`/`ref`/`after` in the forged payload — no interaction with the victim required. This matches "Critical – a payload for one repository mutating another's stack" in the given severity rubric.

### Likelihood Explanation
Preconditions are realistic for exactly the deployment pattern the engine documents and tests support: a multi-org `secrets.yml` (`github: { orgA: {...}, orgB: {...} }`), confirmed in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`. Any organization admin who legitimately installed the Shipit GitHub App for their own org already knows/controls that org's `webhook_secret` (or can set/rotate it in GitHub App settings) — this is not a stolen secret, it's a credential the "attacker" (an org owner in a multi-tenant Shipit instance) is entitled to for their own org, misused to target another. No GitHub interaction with the victim, no Shipit session, and no privileged Shipit role is required — only network access to `POST /webhooks` and a valid signature for the attacker's own org's secret. The attack is trivially repeatable and cheap.

### Recommendation
In `Shipit::WebhooksController`, derive the signature-verification organization and the payload's repository identity from the same trusted field, and reject the request if `repository.owner.login` does not match the owner portion of `repository.full_name`. Concretely: after computing `repository_owner`, also compute the owner segment of `params.dig('repository', 'full_name')` and `head(422)` if they differ before calling `Shipit.github(organization: ...)`. Additionally, `Handler#repository_name`/`stacks` should validate that the resolved `Repository`'s owner matches the organization whose secret verified the request (pass the verified organization down to handlers, or re-check it against `Repository.from_github_repo_name(repository_name)`'s owning org) rather than trusting `full_name` unconditionally.

### Proof of Concept
Minitest integration test plan (no live GitHub, stub `verify_webhook_signature`):

```ruby
test "push webhook signed for attacker-org can trigger sync_github on a victim-org stack" do
  victim_stack = shipit_stacks(:shipit) # e.g. repository full_name "victim-org/victim-repo", branch "master", not archived

  attacker_org_app = mock('GitHubApp')
  attacker_org_app.stubs(:verify_webhook_signature).returns(true)
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(attacker_org_app)

  body = {
    ref: 'refs/heads/master',
    after: 'deadbeef' * 5,
    repository: {
      owner: { login: 'attacker-org' },      # binding side A: org that "signed"
      full_name: 'victim-org/victim-repo'      # binding side B: org actually mutated
    }
  }.to_json

  assert_equal 'attacker-org', JSON.parse(body).dig('repository', 'owner', 'login')
  assert_equal 'victim-org/victim-repo', JSON.parse(body).dig('repository', 'full_name')
  # assert the two differ -> binding broken before tracing further

  post webhooks_url, params: body, headers: {
    'X-Github-Event' => 'push',
    'X-Hub-Signature' => 'sha1=irrelevant-because-stubbed',
    'CONTENT_TYPE' => 'application/json'
  }

  assert_response :ok
  assert_enqueued_with(job: Shipit::GithubSyncJob, args: [victim_stack.id, expected_head_sha: 'deadbeef' * 5])
end
```

Assertions on both sides of the equality: (1) `repository_owner` resolved by `verify_signature` == `'attacker-org'`; (2) the organization whose stack is mutated (derived from `full_name`) == `'victim-org'`; (3) these are unequal yet the sync job is still enqueued for the victim stack, proving the missing cross-check.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
