The Polkadot SDK's closest analog to the ERC-20 `approve` race condition is `pallet-assets-precompiles`' `approve` function, which intentionally implements standard ERC-20 "set" semantics (matching OpenZeppelin's `IERC20.approve`) and explicitly documents that it does **not** mitigate the well-known approve front-running race condition, instructing callers to zero the allowance first or use increase/decrease-allowance patterns instead [1](#0-0) . This is the same inherent limitation present in every standard ERC-20 implementation, including OpenZeppelin's own reference `IERC20.sol`, which documents the identical caveat in its NatSpec comments [2](#0-1)  and is mirrored in the SDK's own `ethereum-standards/IERC20.sol` interface [3](#0-2) .

The underlying `pallet-assets` `approve_transfer`/`do_approve_transfer` extrinsic is additive by design (not a plain overwrite), and a dedicated `prdoc` (`pr_11279.prdoc`) documents that the precompile was specifically patched to implement ERC-20 *set* semantics on top of that additive primitive by cancelling any existing non-zero approval before applying the new one [4](#0-3) , and this is verified by dedicated regression tests (`approve_nonzero_to_nonzero`, `permit_nonzero_to_nonzero`) [5](#0-4) .

This is not a novel defect: it is a deliberate, disclosed design choice that reproduces the same behavior as the ERC-20 standard itself and every mainstream ERC-20 token (including OpenZeppelin's), and the residual front-running risk is explicitly called out in the code comments as known and unmitigated by design. Per the scan method's exclusion criteria, "pure front-running/economic attacks" are not reportable findings, and there is no attacker-controlled input path here that breaks an invariant beyond what the ERC-20 spec itself already accepts.

/// Directly overwriting a non-zero allowance with a different non-zero value must use set
/// semantics (cancel + re-approve). The allowance must equal the new value — not the sum of
/// old and new — and only a single deposit should be reserved.
#[test_case(PRECOMPILE_ADDRESS_PREFIX)]
#[test_case(PRECOMPILE_ADDRESS_PREFIX_FOREIGN)]
fn approve_nonzero_to_nonzero(asset_index: u16) {
	use frame_support::traits::fungibles::approvals::Inspect;

	new_test_ext().execute_with(|| {
		let asset_id = 0u32;
		let asset_addr = H160::from(set_prefix_in_address(asset_index));

		let owner = 123456789u64;
		let spender = 987654321u64;

		Balances::make_free_balance_be(&owner, 100);
		Balances::make_free_balance_be(&spender, 100);

		let spender_addr = <Test as pallet_revive::Config>::AddressMapper::to_address(&spender);

		setup_asset_for_prefix(asset_id, asset_index);
		assert_ok!(Assets::force_create(RuntimeOrigin::root(), asset_id, owner, true, 1));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(owner), asset_id, owner, 100));

		let deposit: u128 = <Test as pallet_assets::Config>::ApprovalDeposit::get();

		// Approve 100 (0 → 100).
		call_approve(owner, asset_addr, spender_addr, U256::from(100));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 100);
		assert_eq!(Balances::reserved_balance(&owner), deposit);

		// Overwrite with 50 directly (100 → 50), no zeroing in between.
		call_approve(owner, asset_addr, spender_addr, U256::from(50));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 50);
		// Deposit reserved exactly once — cancel unreserved the old one, approve re-reserved.
		assert_eq!(Balances::reserved_balance(&owner), deposit);

		// Overwrite upward (50 → 200) to confirm it works in both directions.
		call_approve(owner, asset_addr, spender_addr, U256::from(200));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 200);
		assert_eq!(Balances::reserved_balance(&owner), deposit);
	});
}
