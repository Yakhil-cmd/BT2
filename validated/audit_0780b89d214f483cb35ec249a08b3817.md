### Title
Attacker-induced Aquarius LP price outage permanently shields an underwater account from liquidation and bad-debt cleanup — ([File: contracts/price-aggregator/src/providers/aquarius.rs])

### Summary
A borrower can add a dust supply leg priced via an Aquarius LP share, then — as a liquidity provider in that pool — withdraw reserves until the pool's WAD value drops below `min_pool_value_wad`. The price aggregator then fails closed with `InsufficientAquariusLiquidity` on every read of that asset. Because liquidation, `clean_bad_debt`, and force-socialization all require a strict price for every supply leg of the account, the single poisoned leg bricks all risk-reducing paths while the debt keeps accruing.

### Finding Description
`supply` credits collateral without reading a price: `process_supply` → `process_deposit` performs measured transfers and merges legs, never valuing them [1](#0-0) . So an unprivileged borrower can supply a minimal amount of an Aquarius LP share as an extra collateral leg.

Later, `liquidate` → `build_liquidation_plan` → `risk::calculate_account_risk_totals` must price **every** supply position [2](#0-1) . In the Aquarius provider, `read` computes `pool_value_wad` and returns `Err(OracleError::InsufficientAquariusLiquidity)` whenever it is below `lp.min_pool_value_wad` [3](#0-2) . Reserves are read live via `aquarius_pool_reserves_call` [4](#0-3) , so any LP — including the borrower — can manufacture the outage by withdrawing liquidity from the pool. The same missing price blocks `clean_bad_debt` and governance force-socialization, which also evaluate the account's full collateral set. The project's own threat model confirms this exact path: "an indebted borrower can add a dust leg of any listed collateral and choose which feed outage shields the account. For an Aquarius LP leg, liquidity providers can cause that outage by withdrawing pool value below `min_pool_value_wad`. The same leg blocks bad-debt cleanup and force-socialization" [5](#0-4) .

### Impact Explanation
While the outage persists the account cannot be liquidated at any size, and once insolvent it cannot be cleaned up or force-socialized either — every path reverts on the unpriceable leg. Interest continues accruing on the debt, so the book's measured shortfall grows. Suppliers' backing is frozen in the affected market (bad debt cannot be written down and recapitalized), which maps to permanent freezing of funds and protocol insolvency rather than a mere transient rejection. The attacker can sustain the outage indefinitely by staying withdrawn, or re-enter the pool after competitors give up.

### Likelihood Explanation
Requires only: (1) a listed collateral whose oracle source is an Aquarius LP share, (2) the attacker supplying dust of it before borrowing, and (3) enough LP position in that pool to pull reserves under `min_pool_value_wad` — or waiting for organic withdrawals. All steps are permissionless: `supply` needs no price, and Aquarius withdrawals are open to any LP. Cost is the dust collateral plus temporary withdrawal of liquidity the attacker already controls. Severity: High.

### Recommendation
For liquidation and bad-debt paths, treat an unpriceable supply leg as zero-value collateral instead of failing the whole call — e.g., skip/zero legs whose strict price read fails, then value remaining collateral for the HF check and size pro-rata seizure only over priced legs (seizing zero of the unpriceable leg). Alternatively, add a liquidation-specific oracle fallback (last-good price within an extended TTL) for collateral legs, so one dust LP leg cannot veto repayment and cleanup of all other positions.

### Proof of Concept
1. Governance lists `LP_AQU` (Aquarius share token) as collateral with `AquariusLpSource { pool: P, min_pool_value_wad: M }`.
2. Attacker (an LP in pool `P`) calls `supply(account_id=0, assets=[(USDC, large), (LP_AQU, dust)])` — succeeds; no price read.
3. Attacker calls `borrow` against the USDC leg, then market movement (or a second manipulated leg) pushes `HF < 1`.
4. Attacker calls `P.withdraw_liquidity(...)` until `pool_value_wad < M`. Every subsequent `read` for `LP_AQU` returns `InsufficientAquariusLiquidity` [6](#0-5) .
5. Any `liquidate(liquidator, account_id, payments, SeizeMode::Transfer)` reverts inside `calculate_account_risk_totals` — even offers covering 100% of debt, since the dust leg is still a supply position [7](#0-6) .
6. `clean_bad_debt` and force-socialization revert identically; debt accrues while supplier backing remains locked.

pub(crate) fn process_deposit(
    env: &Env,
    caller: &Address,
    account: &mut Account,
    aggregated: &AggregatedPayments,
    cache: &mut Context,
) {
    validate_position_entry_gates(
        env,
        account,
        aggregated,
        cache,
        AccountPositionType::Deposit,
    );
    let pool_addr = cache.cached_pool_address();
    let mut entries: Vec<PoolSupplyEntry> = Vec::new(env);
    for (hub_asset, amount_in) in aggregated.iter() {
        let asset_config: AssetConfig = cache.require_spoke_asset(account.spoke_id, &hub_asset);
        let received = payments::transfer_amount_measured(
            env,
            &hub_asset.asset,
            caller,
            &pool_addr,
            amount_in,
            GenericError::AmountMustBePositive,
        );
        let position = account.get_or_create_supply_position(&hub_asset, &asset_config);
        entries.push_back(PoolSupplyEntry {
            action: make_pool_action(&position, received, hub_asset.clone()),
        });
    }

    let results = pool_supply_call(env, &pool_addr, &entries);
    for_each_leg(env, &entries, &results, |entry, result| {
        merge_supply_leg(env, account, &entry.action, &result, cache);
    });
}
