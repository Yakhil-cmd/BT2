### Title
Cross-repository CI status forgery via organization-scoped webhook signature check bypassing repository binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub `status` webhook against the GitHub *organization* named in the payload, then hands the raw JSON to `StatusHandler`, which writes a `Status` for **any** commit in the entire Shipit database matching the given `sha` — with no check that the commit's repository/organization is the one whose secret validated the signature. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against purely from attacker-supplied JSON fields: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository','owner','login')` or `params.dig('organization','login')` — both attacker-controlled JSON, not the actual GitHub org that produced the request. `Shipit.github(organization: repository_owner)` then picks that organization's configured `webhook_secret` and `verify_webhook_signature` checks the request body against it: [3](#0-2) 

This only proves the payload was signed by *some* organization configured on this Shipit instance — the one named in `repository.owner.login`/`organization.login`. It says nothing about which repository/commit the handler actually acts on.

For the `status` event, `StatusHandler` never re-derives or validates a repository at all (unlike other handlers, e.g. `Handler#repository_name`/`#stacks`, or `PushHandler`, which scope work to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`): [4](#0-3) [5](#0-4) 

`StatusHandler#process` matches `Commit.where(sha: params.sha)` **globally**, across every stack/repository tracked by the entire Shipit installation, and calls `commit.create_status_from_github!(params)` for each match — regardless of which organization authenticated the request.

Concretely, in a multi-tenant Shipit deployment (multiple orgs configured in `config/secrets.yml`, each with its own `webhook_secret`, as shown in `docs/setup.md` and `config/secrets.development.shopify.yml`), any attacker who controls one configured organization's GitHub App (and thus legitimately possesses that org's `webhook_secret`) can:
1. Craft a `status` event payload with `repository.owner.login` = their own org (so `verify_signature` picks their own valid secret and passes),
2. Set `sha` to a commit SHA belonging to a **different** organization's repository/stack tracked by the same Shipit instance,
3. Set `state` to `success`.

Because `StatusHandler` never checks `repository_owner` (or any repository field) against the commit being updated, the forged, validly-signed request creates a fabricated passing CI status on a commit the attacker does not control.

### Impact Explanation
Writing an attacker-controlled `Status` (`state: success`) onto a victim commit has direct pipeline effects: [6](#0-5) [7](#0-6) 

`add_status` calls `stack.schedule_merges if new_status.pending? || new_status.success?`, and `Status#schedule_continuous_delivery` is triggered `after_commit`. This can satisfy CI-gating conditions used by the merge queue (`MergeRequest#reject_unless_mergeable!` / `any_status_checks_missing?` / `any_status_checks_failed?`) and by continuous deployment, resulting in an **unauthorized merge or deploy** on a repository the attacker does not own — matching the Critical impact category "unauthorized deploy, rollback or merge."

### Likelihood Explanation
Requires the attacker to legitimately control one organization already configured on the shared Shipit instance (a realistic scenario for any multi-tenant/shared Shipit deployment serving multiple GitHub orgs) and to send a single crafted HTTP POST to the public `/github/webhooks` endpoint — no Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed. The vulnerable code path (`StatusHandler`) has zero repository scoping, so exploitation requires only knowledge of a target commit SHA, which is public on GitHub.

### Recommendation
`StatusHandler` (and any other handler operating on cross-cutting resources like `Commit`) must scope lookups to the repository asserted by the signature-verifying organization: require and validate `payload.dig('repository','full_name')`/owner against `repository_owner` used in `verify_signature`, and restrict `Commit.where(sha:)` to commits belonging to stacks under that repository, mirroring the pattern already used in `Handler#stacks`/`#repository_name`.

### Proof of Concept
1. Configure Shipit with two organizations, `victim-org` and `attacker-org`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. `attacker-org` legitimately owns its GitHub App and knows its own `webhook_secret`.
3. Attacker crafts JSON: `{"sha": "<victim commit sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}}}`.
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, raw_body)`.
5. POST to `/github/webhooks` with `X-Github-Event: status`.
6. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature validates successfully.
7. `StatusHandler.process` runs `Commit.where(sha: "<victim commit sha>")` — found in `victim-org`'s stack — and creates a `success` `Status`, potentially unblocking merge/deploy for a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String

          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
```
