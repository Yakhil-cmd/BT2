### Title
Unauthenticated crash: uncaught `throw` in `Definition.validateAuthentifiers`/`validateDefinition` on duplicate co-author address definitions - (File: `definition.js`)

### Summary
The Go advisory describes a panic (uncaught exception) caused by code that assumes an invariant which an attacker-supplied cryptographic structure does not actually guarantee, hit while validating an untrusted certificate chain. `ocore` has an analogous pattern: several branches of address-definition evaluation assume "at most one co-author can define a given address in this unit" and enforce that assumption with a bare `throw Error(...)` instead of returning a validation error through the callback chain. Because these branches are reached while validating an ordinary, attacker-crafted unit (or an AA trigger / private-payment definition path that reuses the same evaluator), a peer can construct a unit that violates the assumption and drive the validator into an uncaught synchronous `throw`.

### Finding Description
`Definition.validateDefinition` and `Definition.validateAuthentifiers` both implement the `'address'` op, which lets a definition reference another address and recursively evaluate that address's definition. When the referenced address's definition is not yet found in storage, the code falls back to looking for a definition supplied by a co-author of the *same unit*: [1](#0-0) 

and, in the authentifier evaluator: [2](#0-1) 

Both blocks filter `objUnit.authors` for authors whose `address` equals the referenced `other_address` **and** whose `definition` hashes to the expected `definition_chash`, then explicitly `throw Error("more than 1 address definition")` if more than one such author is found. This throw is not caught anywhere in the call chain — it is not wrapped in a `try { } catch` at the call sites (`validateDefinition`/`validateAuthentifiers` recursive `evaluate()`), and it happens inside an asynchronous `storage.readDefinitionByAddress` callback (via `ifDefinitionNotFound`), so a `try/catch` placed by a distant caller (e.g. `validateAuthor` in `validation.js`, `validateSignedMessage` in `signed_message.js`) cannot intercept it — the callback runs on its own stack frame once the DB query completes.

A single unit can legally list multiple authors (up to `constants.MAX_AUTHORS_PER_UNIT`), and nothing before this code enforces that two authors cannot share the same `address` while each supplying an (identical-hashing) `definition` for that address — the only ordering/uniqueness check enforced upstream is in `signed_message.js`'s `validateSignedMessage` (`author.address <= prev_address` check), which is a *different* validation path (signed private messages), not the general unit-authors validation path used for AA triggers, address definitions inside ordinary units, and nested/co-author address references. In the general path (`validation.js` `validateAuthor` and the recursive definition evaluator in `definition.js`), duplicate author addresses referencing the same inner address via `['address', other_address]` are not filtered out before reaching the `arrDefiningAuthors.length > 1` check, making the `throw` reachable from ordinary unit posting.

This mirrors the reported bug class: an implicit assumption ("this situation cannot happen / this interface always implements Equal") is enforced via an unconditional runtime panic on attacker-controlled input, instead of graceful rejection.

### Impact Explanation
An uncaught exception thrown from inside an async database-callback during unit validation is not caught by the caller's promise/callback error handling; in Node.js this becomes an uncaught exception that (absent a global `process.on('uncaughtException')` safety net catching *every* code path identically on all nodes) crashes the node process or leaves validation in an inconsistent state. Because unit validation is on the hot path for accepting any incoming unit, a single crafted unit can be used to repeatedly crash full nodes/witnesses that receive and validate it, which is a direct match for the accepted impact "network unable to confirm new units" / node disagreement on validity (nodes that crash cannot participate in stabilizing the DAG, and any node that has different global exception-handling behavior may diverge in whether it processes the unit at all).

### Likelihood Explanation
Reachable by an unprivileged unit poster: the attacker only needs to construct a unit with two authors sharing the same address, where at least one other author's or its own address definition references that address via `['address', <address>]` (either directly in its own definition or in a definition template/nested definition), causing the recursive evaluator to collect more than one matching author when resolving the inner address. No special privileges, hub/peer trust, or network position are required — this is triggerable purely through unit content, and the two vulnerable code paths (`validateDefinition`'s definition-validation pass and `validateAuthentifiers`'s signature-evaluation pass) are both exercised for every unit with an address-referencing definition.

### Recommendation
Replace both `throw Error("more than 1 address definition")` occurrences in `definition.js` (lines ~299 and ~795) with proper error propagation through the `cb`/`handleResult` callback (e.g. `return cb("more than 1 address definition")` / `return cb2(false)`), so malformed/duplicate-author units are rejected as invalid rather than crashing the validator. Additionally, enforce (in `validation.js` `validateAuthor` / the unit-level author list validation) that author addresses within a single unit are unique and sorted, consistent with the invariant already enforced in `signed_message.js`, closing the root cause rather than only the symptom.

### Proof of Concept
1. Craft a unit with two authors, `A1` and `A2`, both having `address = X` (identical), where at least one of them supplies `definition` for `X`, and some other participant's definition (or `X`'s own definition being validated) contains `['address', X]` at a point where `storage.readDefinitionByAddress` for `X` returns `ifDefinitionNotFound` (i.e., `X` has never been used on-chain before, so the definition_chash equals `X` itself).
2. Post the unit to the network / feed it to `validation.js` unit validation.
3. During evaluation of the `'address'` op, `objUnit.authors.filter(...)` returns both `A1` and `A2` as matching definers for `X`, so `arrDefiningAuthors.length === 2`, hitting `throw Error("more than 1 address definition")` inside the `ifDefinitionNotFound` callback of `storage.readDefinitionByAddress`.
4. This throw escapes the async callback uncaught, crashing the validating node process (or otherwise producing inconsistent/undefined validation behavior across nodes).
