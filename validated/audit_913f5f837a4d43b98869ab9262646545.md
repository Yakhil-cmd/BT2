**Rationale:**

`TypeInfoResource` in `types/src/account_config/resources/type_info.rs` derives `Eq, PartialEq` on the full struct, meaning any comparison of two `TypeInfoResource` instances already requires `account_address`, `module_name`, AND `struct_name` to all match — there is no code path that compares `struct_name` alone. [1](#0-0) 

More importantly, `TypeInfoResource`/`TYPE_INFO_RESOURCE_TYPE` is not part of the transaction-admission path at all. A repo-wide search shows it is only referenced in three places: its own definition file, `types/src/account_config/events/coin_register_event.rs` (used to record type-reflection info in an event emitted by `account::CoinRegisterEvent`), and `execution/executor-benchmark/src/db_access.rs` (a benchmark test helper that fabricates resource state). [2](#0-1) [3](#0-2) 

Gas-payer / fee-currency binding in the actual admission/execution path (`aptos-move/framework/aptos-framework/sources/transaction_validation.move`) does not resolve the gas currency via a runtime `TypeInfoResource` lookup at all. It uses the statically-typed Move generic `CoinType`/FA balance checks (`aptos_account::is_fungible_balance_at_least(gas_payer, ...)`), and the fee payer's identity/address itself is bound and authenticated directly via `fee_payer_address`/`fee_payer_public_key_hash` checks in `unified_prologue_fee_payer_v2` and `epilogue_gas_payer_extended`/`unified_epilogue_v2`, not through struct-tag string matching. [4](#0-3) [5](#0-4) 

Since (1) equality on `TypeInfoResource` is already strict full-tuple equality, and (2) this type is never consulted by any mempool, vm-validator, authenticator, or fee-payer/gas-currency resolution logic on the admission path, the proposed collision scenario has no exploitable code path to bind to.

            module_name: bcs::to_bytes(&struct_tag.module.to_string())?,
