### Title
`pending_delegator_rewards` is never decremented after block-reward distribution, causing repeated over-payout from the same fee pool - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
This is the same bug *class* as the Perennial `incrementFees` issue: a "leftover" value is derived from a running fee/reward pool, a portion of that pool is paid out to one party, but the pool total is never reduced by the amount already paid out before the next payout calculation runs against it. In Agave this pattern appears in the SIMD-0123/block-revenue-sharing block-reward path: `pending_delegator_rewards` on the vote account is accumulated from transaction fees via `deposit_delegator_rewards`/`deposit_or_burn_fee` [1](#0-0) , and is then used every epoch as the numerator for `calculate_block_reward`, which computes each delegator's proportional share of `pending_delegator_rewards` [2](#0-1) .

### Finding Description
`calculate_block_reward` reads `vote_state.pending_delegator_rewards()` and computes each stake account's share as `pending_delegator_rewards * stake / total_active_stake` [3](#0-2) . This value is folded into `PartitionedStakeReward.block_reward` for every delegation [4](#0-3) , and later minted directly into each stake account via `checked_add_lamports(partitioned_stake_reward.block_reward)` in `build_updated_stake_reward` [5](#0-4) .

Across the searched code paths (`vote_state/mod.rs`, `vote_state_view_mut.rs`, `fee_distribution.rs`, `calculation.rs`, `distribution.rs`), the only mutation of `pending_delegator_rewards` found is `add_pending_delegator_rewards` inside `deposit_delegator_rewards` [6](#0-5) . No corresponding subtraction/reset of `pending_delegator_rewards` by the amount already distributed as `block_reward` was found in the reward-distribution flow (`begin_partitioned_rewards`, `distribute_reward_commissions`, `store_stake_accounts_in_partition`, `build_updated_stake_reward`). Comments elsewhere in the codebase assert the opposite is expected: e.g. `clone_and_filter_for_vat` explicitly states "Pending delegator rewards are deducted at the start of the epoch, so this operation reflects the actual expected balance" [7](#0-6) , implying a deduction step exists somewhere in the epoch-boundary logic that removes the already-earmarked block reward — but this deduction was not locatable in the code paths inspected within the available search budget.

This mirrors the Perennial `incrementFees` defect exactly: a pool total (`marketFeeAmount` / `pending_delegator_rewards`) is used to compute a component that is paid out (`keeper` / `block_reward`), but the pool total used for subsequent/other splits is not reduced by that already-disbursed component, so the same lamports can be counted (and potentially paid) more than once.

### Impact Explanation
If `pending_delegator_rewards` is indeed not decremented by the amount already paid out as `block_reward` (which the available evidence suggests but could not be 100% confirmed within this investigation), the same pool of lamports would be used as the basis for computing block rewards in every subsequent epoch, in addition to whatever new fees are deposited via `deposit_delegator_rewards`. Since the reward lamports actually distributed are minted into stake accounts and reflected in `Bank::capitalization` (see `distribute_epoch_rewards_in_partition` / `pre_cap + inflation_rewards_minted == post_cap` in the tests) [8](#0-7) , repeated payout from a never-reduced pool would translate into unbacked capitalization growth / duplicate stake rewards each epoch — a stake/reward corruption issue.

### Likelihood Explanation
I was unable to fully verify the absence of a deduction step across the entire reward-distribution code path due to search/tool budget limits, so this cannot be stated as a confirmed vulnerability with full confidence. The comment in `vote/src/vote_account.rs` suggests the intended design does include a deduction "at the start of the epoch," which — if implemented correctly elsewhere (e.g., in code not surfaced by these searches) — would mean this is not exploitable. Given this significant uncertainty, likelihood should be treated as low-to-unconfirmed pending direct code reading of the full epoch-boundary reward-distribution sequence (particularly around `begin_partitioned_rewards`/`distribute_reward_commissions` and any sysvar/vote-account mutation performed after `store_stake_accounts_in_partition`).

### Recommendation
A background engineer should directly trace, end-to-end, every mutation of `pending_delegator_rewards` for a vote account across an epoch boundary (deposit via `deposit_delegator_rewards`, read via `calculate_block_reward`, and any deduction after `block_reward` is actually distributed in `distribution.rs`), confirming whether `pending_delegator_rewards` is reduced by exactly the `block_reward` amount that was successfully minted into stake accounts. If no such deduction exists, `calculate_block_reward` (or the caller in `calculate_stake_rewards_and_commissions`) must subtract the distributed amount from `pending_delegator_rewards` and persist that back to the vote account state, analogous to fixing `donationAmount` in the Perennial report by subtracting the already-disbursed `keeper` fee.

### Proof of Concept
Not constructed — full confirmation requires locating (or confirming the absence of) the deduction step for `pending_delegator_rewards` post-distribution, which was not reachable within the available tool budget. This should be the first step for a background agent: search `runtime/src/bank/partitioned_epoch_rewards/*.rs` and `runtime/src/block_component_processor/vote_reward.rs` for any write to `pending_delegator_rewards` or `set_pending_delegator_rewards`/`VoteStateHandler` mutation occurring after `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition`.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation.stake_v2(
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
