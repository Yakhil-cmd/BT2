### Title
Private payment DoS via duplicate-detection bypass causing legitimate transfer to be silently dropped - ([File: private_payment.js])

### Summary
The Mastodon bug lets an attacker who already knows the content of a quote (before it reaches the server through the normal path) pre-seed server state so that when the real object arrives, it is misidentified as already-processed and dropped, permanently breaking correct processing of that specific item. In ocore, private payments follow the same "recipient/counterparty knows the payload before the network/hub sees it" pattern, and `private_payment.js`'s duplicate-detection logic that guards `unhandled_private_payments`/`outputs` processing is reachable by any private-payment counterparty (recipient, cosigner, or device on the same wallet) before the real chain is delivered.

### Finding Description
`validateAndSavePrivatePaymentChain` in [1](#0-0)  performs a pre-check against the `outputs` table keyed by `(unit, asset, message_index[, output_index])` to detect duplicate submissions of the same private payment (explicitly to support "recipient and cosigner on the same device" scenarios, per the comment in [2](#0-1) ). If a stored row's `address`/`blinding`/`amount` match the attacker-supplied claimed output, the function calls `transaction_callbacks.ifOk()` immediately and **skips calling `assetModule.validateAndSavePrivatePaymentChain`** entirely — meaning no `inputs` row is inserted and the source output's `is_spent` flag is never set (see [3](#0-2)  for what that skipped save step normally performs).

Because a private payment is transmitted device-to-device (via `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`, [4](#0-3)  and [5](#0-4) ) before the corresponding public unit and its private chain are fully processed by all parties, a malicious counterparty who already knows the real output's `address`/`blinding`/`amount` (because they are the intended recipient or a co-signer who received the real chain out-of-band) can race the network by first delivering their own private-payment message for the same `(unit, message_index[, output_index])`. Once that first submission is processed and its output row is saved with the matching values, the dedup check in [6](#0-5)  will treat the subsequent, legitimate delivery of the same chain (e.g., via `handleSavedPrivatePayments`, [7](#0-6) ) as a harmless duplicate and short-circuit it with `ifOk()`, even though the full chain (with its inputs, spend proofs, and the marking of the source coin as spent) was never actually validated or saved for that flow of the chain. This mirrors the analog bug class: an attacker who knows the "real" identifying data ahead of time can pre-empt correct processing and make the network node believe the transaction is already handled when it is not.

### Impact Explanation
For divisible or indivisible private assets, silently short-circuiting `validateAndSavePrivatePaymentChain` means the source input is never marked spent by that flow and the transfer's `inputs` row is never created for that path. Depending on which device/party this occurs on, this can (a) cause the wallet to permanently disagree with the actual DAG state (freezing/losing track of a private balance it should show as received or spent — "node disagreement on validity" for private payment data local to that node), and (b) create a race where the real transfer is never fully recorded, while the underlying public payment message (and its funds) is committed on-chain — a private-payment counterpart DoS that a single unprivileged private-payment participant can trigger against another party's wallet.

### Likelihood Explanation
The attack requires the attacker to be a legitimate party to the private payment (recipient or co-signer) who already possesses the real output's address/blinding/amount ahead of the normal delivery — a condition inherent to how private payments are exchanged in ocore (recipients/cosigners see chain data via direct device messages before/independently of full validation completing on every device). No node authority or elevated privilege is required beyond being a normal wallet counterpart, matching the "unprivileged... private-payment counterparty" reachable actor required by scope.

### Recommendation
Do not short-circuit the real save step based solely on matching `address`/`blinding`/`amount` in `outputs`. The duplicate check should also confirm that the full chain (specifically the `inputs` row and `is_spent` update for the source coin) was already applied for this exact submission before returning `ifOk()` without saving, or it should require that the *entire* incoming chain (not just the head output fields) exactly matches a chain that was already fully validated and persisted, e.g. by tracking a hash of the whole processed chain rather than partial output fields.

### Proof of Concept
1. Attacker Bob is the designated recipient of a private payment chain from Alice for asset A, unit U, message_index M, output_index O, with known address/blinding/amount (Bob legitimately knows these as the intended recipient).
2. Before Alice's genuine `private_payment` message is delivered/handled through the normal hub/device path (`handlePrivatePaymentChains` → `handleOnlinePrivatePayment` → `validateAndSavePrivatePaymentChain`), Bob crafts and submits his own private-payment message for the same `(unit, message_index, output_index)` with the correct address/blinding/amount fields matching what he expects the real chain to contain, targeting a node/device he wants to disrupt.
3. That submission gets processed first, and the dedup-check path in `private_payment.js` inserts an `outputs` row with `address`/`blinding` set to the (attacker-known) legitimate values.
4. When the real chain from Alice subsequently arrives at the same node/device, the duplicate check at [6](#0-5)  matches and calls `ifOk()` without invoking `assetModule.validateAndSavePrivatePaymentChain`, so the `inputs` row and `is_spent` marking for the true transfer are never created on that node/device — the legitimate chain is treated as already handled while its critical bookkeeping (spend tracking) never actually happens.

**Note:** I was not able to fully verify from the available index whether the `outputs` table enforces a `PRIMARY KEY`/unique constraint on `(unit, message_index, output_index)` for indivisible vs divisible schemas (the SQL schema files were only partially retrievable), which affects whether a second legitimate `INSERT` would additionally throw an SQL error or be silently ignored in some code paths. Confirming the exact `outputs` schema and constraints, and reproducing the race in a test harness, would require a full Devin session with complete file/database access.

				var src_message_index = input.message_index;
				var src_output_index = input.output_index;

					address = input.address || arrAuthorAddresses[0];

						(unit, message_index, input_index, type, \n\
						src_unit, src_message_index, src_output_index, \
						serial_number, amount, \n\
						asset, is_unique, address) VALUES(?,?,?,?,?,?,?,?,?,?,?,"+(address_sql || conn.escape(address))+")",
					[unit, message_index, j, type,

				if (type === "transfer"){
					conn.addQuery(arrQueries,

		}
	});

		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");

		var cache_key = objectHash.getBase64Hash(arrChains);
