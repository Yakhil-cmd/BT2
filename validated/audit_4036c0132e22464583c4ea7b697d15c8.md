### Title
Repository-owner used for webhook signature selection is decoupled from `repository.full_name` used for record targeting, letting a no-secret-org payload mutate another stack's `PullRequest` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the secret used for HMAC verification) purely from `repository.owner.login`/`organization.login`, while `AssignedHandler#repository` independently resolves the target `Repository`/`Stack`/`PullRequest` from the unrelated `repository.full_name` field. Because `GitHubApp#verify_webhook_signature` trivially returns `true` when the selected org's config has no `webhook_secret`, an attacker can authenticate a forged payload against a no-secret org while pointing `repository.full_name` at an entirely different, victim stack, causing `AssignedHandler#process` to persist attacker-controlled `PullRequest` fields for a repository that never validated the request.

### Finding Description
The broken binding: the code implicitly assumes `repository.owner.login == owner(repository.full_name)`, i.e. that the org used to select/verify the webhook secret is the same org that owns the repository the handler acts on. This is never enforced.

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) computes `repository_owner` from `params.dig('repository','owner','login')` (line 61) and looks up `Shipit.github(organization: repository_owner)`, then calls `github_app.verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb` (lines 76-83) returns `true` unconditionally when `@webhook_secret` is blank (line 77): `return true unless webhook_secret`. So any org configured in Shipit without a `webhook_secret` accepts arbitrary unsigned bodies.
- `AssignedHandler#repository` in `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb` (lines 67-69) resolves the target repository from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, a field completely independent of `repository.owner.login` used above.
- `AssignedHandler#pull_request` (lines 53-65) then finds the persisted `Shipit::PullRequest` scoped to that resolved repository's stack, and `process` (lines 41-45) calls `pull_request.update(github_pull_request: params.pull_request)` when `action` is `assigned`/`unassigned`.
- `PullRequest#github_pull_request=` (`app/models/shipit/pull_request.rb` lines 36-50) overwrites `state`, `title`, `additions`, `deletions`, `user`, `assignees`, `labels`, and `head` on the record.

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, an `X-Hub-Signature` of any value (or none), and a body where `repository.owner.login` (or `organization.login`) is set to an org configured in Shipit with no `webhook_secret`, while `repository.full_name` is set to `victim-org/victim-repo` — a completely different, real, victim stack (which may itself have a properly configured `webhook_secret`; that secret is never consulted). `action` is `unassigned`. `verify_signature` passes trivially because of the no-secret org. `AssignedHandler` then locates and overwrites the victim stack's `PullRequest` row.

Existing guards do not catch this: `drop_unhandled_event` only checks the event type exists a handler for it; `ExplicitParameters` only validates payload shape, not cross-consistency between `repository.owner.login` and `repository.full_name`; there is no `force_github_authentication`/`require_permission!`/`User#authorized?` check on this unauthenticated endpoint by design.

Regarding the specific amplification claimed in the question — that a forced state change causes `blocked?` to flip and gate deploys via `blocking_statuses` — this does **not** hold. `Commit#blocked?` (`app/models/shipit/commit.rb` lines 231-237) is driven exclusively by `Status`/`CheckRun` records (`stack.commits...any?(&:blocking?)`), and `AssignedHandler`/`PullRequest#github_pull_request=` never creates or touches a `Status`/`CheckRun` record; it only rewrites `PullRequest.state`, `title`, `assignees`, `labels`, and `head`. So `blocking_statuses` configuration on the victim stack is irrelevant to this handler's effect, and the claimed "blocked?/deploy-gating" causal chain is not present in the code.

### Impact Explanation
The real, demonstrable impact is a cross-tenant write: a payload authenticated using one (no-secret) organization's identity can overwrite another repository's/stack's persisted `PullRequest` record (state, title, assignees, labels, and pointer to a `head` commit fetched from GitHub) without ever presenting that target's `webhook_secret`. This matches the rules' Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any stack/repo whose `full_name` the attacker knows, as long as some org configured in Shipit lacks a `webhook_secret`. However, it does not achieve the specific "gate/unblock deploys via `blocking_statuses`" effect the question describes, since `blocked?` is unaffected by any field this handler writes.

### Likelihood Explanation
Preconditions: (1) at least one GitHub organization configured in Shipit (`Shipit.github_app_configs`/equivalent) with a blank/missing `webhook_secret`; (2) knowledge of a victim repository's `full_name` and an open PR number on that stack (both are publicly discoverable via GitHub). No Shipit or GitHub secrets, sessions, or team membership are required. Cost is a single unauthenticated HTTP POST. This is fully repeatable and does not depend on `blocking_statuses` being configured on the victim stack (that condition, present in the question, is not actually load-bearing for the write to succeed).

### Recommendation
Bind webhook authentication to the same repository being mutated: derive the org/secret used for `verify_webhook_signature` from the same `repository.full_name` (or its owner segment) that handlers use to resolve `Repository`/`Stack`, and reject the request if the two disagree. Additionally, treat orgs with no `webhook_secret` configured as unauthenticated-by-default and require an explicit opt-in (e.g., a `Shipit.github_teams`-style config flag) before allowing any handler to mutate state based on their payloads, or refuse verification entirely (return `false`, not `true`) when `webhook_secret` is blank.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual minitest, no live GitHub)
test "pull_request unassigned for a no-secret org cannot mutate another stack's PullRequest via mismatched full_name" do
  # Arrange: victim stack/repo "victim-org/victim-repo" with blocking_statuses configured,
  # and a persisted PullRequest#number == 42 with known state/assignees/labels.
  victim_repository = shipit_repositories(:shipit)
  victim_stack = victim_repository.stacks.first
  victim_pr = victim_stack.pull_requests.create!(number: 42, state: 'open', ...)

  # Configure an org "no-secret-org" in Shipit.github_app_configs with no webhook_secret.
  # (binding under test)
  before_state = victim_pr.reload.state

  post :create, body: {
    action: 'unassigned',
    number: 42,
    pull_request: { id: 1, number: 42, url: '...', title: 'x', state: 'closed',
                     additions: 0, deletions: 0,
                     head: { sha: victim_pr.head.sha, ref: 'x' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    repository: { full_name: 'victim-org/victim-repo', owner: { login: 'no-secret-org' } },
    sender: { login: 'attacker' }
  }.to_json, headers: { 'X-Github-Event' => 'pull_request', 'X-Hub-Signature' => 'sha1=deadbeef' }

  after_state = victim_pr.reload.state

  # Binding equality to test: before_state == after_state (an unauthenticated,
  # cross-org payload should NOT change victim_pr's persisted state).
  assert_equal before_state, after_state, "no-secret org payload mutated a stack it never authenticated"
end
```
Note: this PoC validates the cross-tenant `PullRequest` mutation, not a `blocked?`/deploy-gating effect — tracing `Commit#blocked?` confirms it is unaffected by any field `AssignedHandler` writes, so no additional assertion on deploy gating is supportable from the code as written.
