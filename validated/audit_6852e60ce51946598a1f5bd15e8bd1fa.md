### Title
Explicit `conditions:` rules silently bypass blocking due to unvalidated field names and AND-only semantics, unlike legacy `pattern:` rules - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`Rule.from_dict` supports two ways to specify a match: the legacy `pattern:` field, which always maps to a guaranteed-valid field (`command`/`new_text`/`content`) inferred from `event`, and the newer explicit `conditions:` list, which accepts arbitrary attacker/generator-supplied `field`/`operator`/`pattern` triples with zero validation and combines them with AND-only semantics. Because `_check_condition` treats an unrecognized or mismatched `field` as `None` → `False`, a single bogus or mismatched condition entry silently neutralizes an entire `block` rule forever, with no warning surfaced to the user, unlike the legacy path which can never produce this state.

### Finding Description
`Condition.from_dict` performs no validation on `field` or `operator` values [1](#0-0) . `Rule.from_dict` prefers the explicit `conditions:` list over the legacy `pattern:` field whenever `conditions` is present and non-empty [2](#0-1) , while the legacy path always derives a known-good `field` (`command`, `new_text`, or `content`) directly from `event` [3](#0-2) .

At evaluation time, `RuleEngine._rule_matches` requires ALL conditions in `rule.conditions` to match (AND semantics), and any single condition failing short-circuits the whole rule to "no match" [4](#0-3) . `_extract_field` returns `None` for any field name it does not explicitly recognize for the current tool [5](#0-4) , and `_check_condition` immediately returns `False` when `field_value is None` [6](#0-5) . There is no logging, warning, or validation anywhere in `load_rule_file`/`Rule.from_dict` that flags a condition referencing an unknown/mismatched field — the rule loads successfully and is reported as `enabled` [7](#0-6) .

Exploit flow: frontmatter for a rule (either shipped in a repository's `.claude/hookify.*.local.md` file, or auto-generated by `/hookify` from user/repo-derived text) declares `action: block` with an explicit `conditions:` list that includes one condition on a field name that does not apply to the tool/event in question (e.g. `field: new_text` for a `bash` event, or a misspelled field like `filecontent`). The rule appears legitimate — it has a real name, message, and `block` action — but because of the AND-all-conditions requirement and the silent `None`-on-unknown-field behavior, it can never fire. Since equivalent legacy `pattern:` rules cannot express this broken state (the field is always correctly inferred), the two forms diverge: a rule author or generator can produce what looks like a working block rule that is permanently inert, allowing the operation it was meant to block (e.g. writing/exfiltrating secrets, code, diffs, or transcripts) to proceed without any warning or block being emitted.

### Impact Explanation
An intended `block` rule (e.g., "block writes containing API keys" or "block exfiltration of code/diffs to network tools") can be rendered permanently non-functional through crafted or auto-generated frontmatter, without any error surfaced to the operator. This directly undermines the hookify enforcement layer's guarantee that legacy and explicit rule definitions provide equivalent protection, and can result in sensitive code, prompts, tokens, diffs, or local files being written/executed/transmitted to unintended sinks that the rule was supposed to stop [8](#0-7) .

### Likelihood Explanation
No special privileges are required: any actor able to influence a repository-shipped `.claude/hookify.*.local.md` file, or the text fed into `/hookify`'s rule-generation flow, can produce this pattern. The bug is deterministic and trivially reproducible — a single condition with a `field` value not recognized by `_extract_field` for the given tool/event always yields no match, silently. Because `load_rule_file` swallows structural issues without raising, and there is no schema validation of `field`/`operator` values, this is easy to trigger unintentionally as well as maliciously, and there is no compensating control preventing it. I was not able to independently verify the exact `/hookify` slash-command generation code path within the available tool budget, so the "generator produces this frontmatter automatically" leg of the exploit chain is inferred from the parsing/evaluation logic rather than directly confirmed in the generator's source.

### Recommendation
- Validate `field` and `operator` values in `Condition.from_dict` / `Rule.from_dict` against an explicit allowlist per event type (mirroring the legacy inference table), rejecting or warning loudly (and failing closed for `block` rules) on unknown fields.
- Change `_extract_field` to raise/log a distinguishable "unknown field" signal instead of returning `None`, and have `_check_condition` treat unknown-field conditions as a load-time error rather than a silent runtime non-match.
- Add a normalization/equivalence test ensuring any legacy `pattern:` rule and its explicit `conditions:` equivalent produce identical `_rule_matches` results across a fuzz corpus of tool inputs.
- Optionally require at least one condition per rule to reference a "core" field type (e.g. `command`, `content`, `new_text`, `file_path`) for `block` actions, so an all-invalid-field rule cannot be created.

### Proof of Concept
Add a unit test to `plugins/hookify/core/` test suite:

```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

frontmatter_legacy = {
    "name": "block-rm",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "pattern": r"rm\s+-rf",
}

frontmatter_explicit_broken = {
    "name": "block-rm-explicit",
    "enabled": True,
    "event": "bash",
    "action": "block",
    "conditions": [
        {"field": "command", "operator": "regex_match", "pattern": r"rm\s+-rf"},
        {"field": "new_text", "operator": "regex_match", "pattern": ".*"},  # invalid field for bash event
    ],
}

legacy_rule = Rule.from_dict(frontmatter_legacy, "danger!")
explicit_rule = Rule.from_dict(frontmatter_explicit_broken, "danger!")

engine = RuleEngine()
input_data = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Bash",
    "tool_input": {"command": "rm -rf /"},
}

legacy_result = engine.evaluate_rules([legacy_rule], input_data)
explicit_result = engine.evaluate_rules([explicit_rule], input_data)

# Expected (current buggy) behavior demonstrating the differential:
assert legacy_result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"
assert explicit_result == {}  # block silently bypassed despite identical intent
```

This demonstrates that semantically-equivalent legacy and explicit rule definitions produce divergent enforcement outcomes for the same dangerous input, with the explicit form silently failing open.

    def _extract_field(self, field: str, tool_name: str,
                      tool_input: Dict[str, Any], input_data: Dict[str, Any] = None) -> Optional[str]:
        """Extract field value from tool input or hook input data.

        Args:
            field: Field name like "command", "new_text", "file_path", "reason", "transcript"
            tool_name: Tool being used (may be empty for Stop events)
            tool_input: Tool input dict
            input_data: Full hook input (for accessing transcript_path, reason, etc.)

        Returns:
            Field value as string, or None if not found
        """
        # Direct tool_input fields
        if field in tool_input:
            value = tool_input[field]
            if isinstance(value, str):
                return value
            return str(value)

        # For Stop events and other non-tool events, check input_data
        if input_data:
            # Stop event specific fields
            if field == 'reason':
                return input_data.get('reason', '')
            elif field == 'transcript':
                # Read transcript file if path provided
                transcript_path = input_data.get('transcript_path')
                if transcript_path:
                    try:
                        with open(transcript_path, 'r') as f:
                            return f.read()
                    except FileNotFoundError:
                        print(f"Warning: Transcript file not found: {transcript_path}", file=sys.stderr)
                        return ''
                    except PermissionError:
                        print(f"Warning: Permission denied reading transcript: {transcript_path}", file=sys.stderr)
                        return ''
                    except (IOError, OSError) as e:
                        print(f"Warning: Error reading transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
                    except UnicodeDecodeError as e:
                        print(f"Warning: Encoding error in transcript {transcript_path}: {e}", file=sys.stderr)
                        return ''
            elif field == 'user_prompt':
                # For UserPromptSubmit events
                return input_data.get('user_prompt', '')

        # Handle special cases by tool type
        if tool_name == 'Bash':
            if field == 'command':
                return tool_input.get('command', '')

        elif tool_name in ['Write', 'Edit']:
            if field == 'content':
                # Write uses 'content', Edit has 'new_string'
                return tool_input.get('content') or tool_input.get('new_string', '')
            elif field == 'new_text' or field == 'new_string':
                return tool_input.get('new_string', '')
            elif field == 'old_text' or field == 'old_string':
                return tool_input.get('old_string', '')
            elif field == 'file_path':
                return tool_input.get('file_path', '')

        elif tool_name == 'MultiEdit':
            if field == 'file_path':
                return tool_input.get('file_path', '')
            elif field in ['new_text', 'content']:
                # Concatenate all edits
                edits = tool_input.get('edits', [])
                return ' '.join(e.get('new_string', '') for e in edits)

        return None
