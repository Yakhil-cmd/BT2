### Title
Unhandled exception in AA formula evaluator crashes the node process (DoS via crafted AA trigger/definition) - ([File: formula/evaluation.js])

### Summary
The MariaDB CVE describes a crash (DoS) triggered by specially crafted SQL statements that reach a code path (`Item_subselect::init_expr_cache_tracker`) which does not gracefully handle the malformed/unexpected input, causing the server to abort. In ocore, the analogous "expression evaluator" is the oscript/AA formula interpreter in `formula/evaluation.js`. This interpreter contains numerous `throw Error(...)` statements used as internal invariant assertions (e.g. `default: throw Error('unrecognized op '+op);` at [1](#0-0) , `throw Error("unknown op: " + op);` at [2](#0-1) , and similar asserts at lines 2051, 2083, 2106, 1395, 3132) that assume every AST node reaching `evaluate()` was already accepted by the separately-implemented pre-validator in `formula/validation.js`. Because these two "grammar interpreters" are maintained independently (with duplicated but not always identical switch-case coverage), any semantic mismatch between what `formula/validation.js` accepts and what `formula/evaluation.js` implements results in an uncaught, synchronous `throw` deep inside an asynchronous callback chain during AA trigger execution.

### Finding Description
`formula/evaluation.js` parses and caches an oscript AST via `nearley` (`cache[formula]`, [3](#0-2) ) and then recursively evaluates it with `evaluate(arr, cb, bTopLevel)`. Throughout the giant `switch(op)` block, many branches assume specific, previously-validated invariants and fall back to `throw Error(...)` instead of calling the error callback `cb(...)` when those invariants don't hold (e.g. unknown op in the outer `switch` default, unknown assignment operator, unknown comparison operator, unrecognized function-argument node). These are true JavaScript exceptions, not soft validation errors funneled through `setFatalError`/`cb`.

Separately, `formula/validation.js` implements its own AST walker (`exports.validate`) with its own `switch(op)` that is supposed to reject any formula whose AST would trigger one of these evaluator-side asserts. `aa_validation.js`'s `validateFormula` calls into `formula/validation.js` at AA-definition time (`validateAADefinition` → `validateFormula` → `formulaValidator.validate`, [4](#0-3) ), and this is the only gate protecting `formula/evaluation.js` from unexpected AST shapes. Because the two files are large (~3000 lines each), independently coded, and evolve with feature flags gated by different `mci` thresholds (`aa2UpgradeMci`, `aa3UpgradeMci`, `pemCurvesFixMci`, etc., see e.g. [5](#0-4)  vs. the corresponding evaluator branch), a permanent 1:1 semantic equivalence between them is not structurally enforced anywhere in the codebase.

Critically, `network.js` installs a global handler that deliberately kills the entire node process on *any* uncaught exception: [6](#0-5) 
```
process.on('uncaughtException', (err) => {
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```
This means that if an attacker can post a unit (AA definition or AA trigger) whose oscript AST passes `formula/validation.js`'s checks but reaches an unhandled branch (or throws for any other reason) inside `formula/evaluation.js`'s `evaluate()` — reached during trigger execution via `aa_composer.js`'s `handleTrigger`/`evaluateAA` ( [7](#0-6) ) or via a getter call (`callGetter`, [8](#0-7) ) — the resulting synchronous `throw` is not caught anywhere in the async callback chain and bubbles up to `process.on('uncaughtException')`, which re-throws and terminates the node.

This is directly analogous to the MariaDB bug class: a syntactically well-formed but semantically edge-case input (crafted SQL / crafted oscript formula) reaches an internal execution/cache component that lacks defensive handling for that specific shape, crashing the server process — Denial of Service, no confidentiality/integrity impact, matching CVSS `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`.

### Impact Explanation
A node process crash triggered by a single posted AA-trigger unit is a severe, network-wide availability issue: any full node (and any light/hub node relaying and validating such units) that processes the malicious trigger crashes. If reproduced against enough nodes (or against witnesses), it can stall main-chain progression and prevent the network from confirming new units — a "network unable to confirm new units" outcome. Because the crash occurs inside unit/AA-trigger validation and execution, an unprivileged AA author or trigger sender is sufficient to reach it; no special network/hub privilege is required.

### Likelihood Explanation
Exploitability requires finding one concrete AST shape where `formula/validation.js` accepts a formula (or an earlier stage such as `aa_validation.js`'s structural checks accepts it) but `formula/evaluation.js`'s switch does not have a matching branch, or where evaluation-time type coercion produces a value that trips one of the internal `throw Error(...)` asserts instead of hitting `setFatalError`. Given the size and evolving feature-gated logic (multiple `mci` upgrade thresholds independently checked in both files), such a mismatch is plausible, but I was not able to conclusively pinpoint one exact case within the available search budget — the two switch statements are very large and a byte-for-byte diff of validated vs. evaluated op coverage would be needed to nail down the precise trigger. This should be treated as a concrete, high-value area for manual audit/differential testing rather than a proven, fully-demonstrated PoC.

### Recommendation
- Replace all internal-assumption `throw Error(...)` statements inside `formula/evaluation.js`'s `evaluate()` (and helper functions such as `evaluateFunctionExpression`) with calls to `setFatalError(...)`/`cb(...)` so that any unexpected AST shape degrades to an AA formula-evaluation failure (bounced trigger) rather than an uncaught process-level exception.
- Wrap the top-level call into `formulaParser.evaluate()` (in `aa_composer.js`, `callGetter`, and any other invocation sites) in a `try/catch` that treats synchronous throws as evaluation failures.
- Add exhaustive tests asserting that every `op` accepted by `formula/validation.js` has a corresponding, non-throwing branch in `formula/evaluation.js` for all supported `mci` ranges, ideally via a shared, single source of truth for the list of valid ops instead of two independently maintained switch statements.
- Consider softening `process.on('uncaughtException')` in `network.js` for formula-evaluation-originated errors specifically (e.g., by ensuring such errors can never escape as uncaught in the first place, per the two points above), while keeping the fail-fast behavior for other, more fundamental invariant violations.

### Proof of Concept
Not fully demonstrated. A concrete PoC would require constructing an AA definition/trigger whose oscript formula's AST is accepted by `formula/validation.js`'s `evaluate()` walker (formula/validation.js:272-1348) but drives `formula/evaluation.js`'s `evaluate()` (formula/evaluation.js:126-2758) into one of its internal `throw Error(...)` branches (e.g. the outer `default: throw Error('unrecognized op '+op);` at formula/evaluation.js:2757-2758, or a type-mismatch assert such as formula/evaluation.js:2083/2106/1395/3132). Confirming this requires a systematic diff of the op-handling coverage between the two files across all `mci`-gated feature branches, which was not completed within the scope of this analysis.
