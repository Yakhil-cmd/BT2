### Title
`X-Shipit-User` header is trusted for identity attribution without any authentication - allows forging deploy/task authorship as an arbitrary Shipit user - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController#identify_user` derives `current_user` purely from the client-supplied `X-Shipit-User` request header, looking up any `User` by login with no verification that the caller is actually that user. `current_api_client`'s permission check (`check_permissions!`) authorizes the operation (e.g. `deploy:stack`) but is entirely decoupled from `current_user`, so a caller holding a narrowly-scoped `ApiClient` token can attribute deploys, task triggers, aborts, etc. to any existing privileged user by name.

### Finding Description
The claimed binding is: `current_user == the identity that authenticated this request`. In `app/controllers/concerns/shipit/authentication.rb`, `current_user` is legitimately derived from `session[:user_id]` set during OAuth login (`find_current_user`), which does tie identity to an authenticated session. However, `Shipit::Api::BaseController` overrides `current_user`/`identify_user` for the JSON API path: [1](#0-0) 

`authenticate_api_client` only validates the bearer token into `current_api_client`, and `require_permission!` (invoked via the `require_permission` class helper) only checks `current_api_client.check_permissions!(operation, scope)` — it never validates or restricts the `X-Shipit-User` header against the authenticated `ApiClient`: [2](#0-1) 

`ApiClient#check_permissions!` checks only `operation:scope` membership in the client's own `permissions` array; it has no concept of, or link to, which `User` the request is allowed to claim: [3](#0-2) 

Exploit flow: an attacker holds a legitimate `ApiClient` token scoped to their own stack with `deploy:stack` permission (a normal, low-privilege integration credential). They call `POST /api/stacks/1/tasks/trigger` (or `POST /api/stacks/:id/deploys`) with `Authorization: Basic <their token>` and `X-Shipit-User: some-admin-login`. `identify_user` resolves `some-admin-login` to the real privileged `User` record and sets it as `current_user`, which is then passed straight into `stack.trigger_task(params[:task_name], current_user, ...)` (`app/controllers/shipit/api/tasks_controller.rb:21`) or `stack.trigger_deploy(commit, current_user, ...)` (`app/controllers/shipit/api/deploys_controller.rb:25`), causing the resulting `Task`/`Deploy` record to be attributed to the admin. [4](#0-3) [5](#0-4) 

No existing guard prevents this: `force_github_authentication` (`app/controllers/concerns/shipit/authentication.rb`) is not included in `Shipit::Api::BaseController`, so it never runs for API requests; `verify_signature`/webhook checks are irrelevant here; and `require_permission!` checks the API client's own scope, not the impersonated user's authorization. The equality the code assumes — that the caller who presents `X-Shipit-User: some-admin-login` actually is `some-admin-login` — is never verified anywhere in this path, so it diverges from the true identity (the ApiClient's `creator`, or nobody at all).

### Impact Explanation
Any request attributed to `current_user` (deploy/task creation, aborts, lock/unlock authorship, comments, etc.) can be forged to appear as originating from an arbitrary existing Shipit user, including admins/operators, using only a low-privilege API token. This is a forged-attribution/authentication-bypass issue: audit logs, "deployed by" records, and any downstream logic that trusts `current_user`'s identity (not just its display name) for authorization decisions can be spoofed. It does not directly grant the attacker the ability to act on stacks outside their token's own permission scope (that boundary is still enforced by `check_permissions!` on `current_api_client`), but it breaks accountability/non-repudiation for every mutating API action and can deceive any code or human reviewer who relies on `Task#user`/`Deploy#user` to determine who actually performed the action. This is repeatable on every request and against any stack the attacker's token has access to.

### Likelihood Explanation
Preconditions are modest: attacker needs any valid `ApiClient` token with at least `deploy:stack` or `write:stack` on some stack (a normal, commonly issued integration credential) and knowledge of a target user's login (logins are often public via GitHub). No GitHub secrets, session, or elevated Shipit role are required — this exactly matches the attacker profile in scope. The cost is a single crafted HTTP header; it is trivially repeatable.

### Recommendation
Do not derive `current_user` from an unauthenticated header. Either remove the `X-Shipit-User` attribution feature entirely for the JSON API, or bind it cryptographically/structurally to the authenticated principal — e.g., only honor `X-Shipit-User` if it matches `current_api_client.creator`, or require a separate signed assertion, and reject the request (401/403) if `X-Shipit-User` does not match the authenticated principal's own login rather than silently trusting it.

### Proof of Concept
Minitest plan (`test/controllers/api/tasks_controller_test.rb` or `deploys_controller_test.rb`):
1. Create fixtures: `admin_user` (login `admin`, privileged), `attacker_user` (creator of the api client), and an `ApiClient` scoped to `attacker`'s stack with only `deploy:stack` permission (no relation to `admin_user`).
2. Send `POST /api/stacks/:id/tasks/trigger` (or deploys `create`) with `Authorization: Basic <attacker_api_client.authentication_token>` and header `X-Shipit-User: admin`.
3. Assert response succeeds (2xx/202) and assert the resulting `Task#user` (or `Deploy#user`) equals `admin_user`, i.e. `assert_equal admin_user, Shipit::Task.last.user` — demonstrating `current_user == admin_user` even though the authenticated caller was `attacker_api_client`/`attacker_user`, proving `identify_user`/`current_user` is not bound to the actual authenticated caller.

      def authenticate_api_client
        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end
        return if @current_api_client

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
        render(status: :unauthorized, json: { message: 'Bad credentials' })
      end

      attr_reader :current_api_client

      def current_user
        @current_user ||= identify_user || AnonymousUser.new
      end

      def identify_user
        user_login = request.headers['X-Shipit-User'].presence
        User.where('lower(login) = ?', user_login.downcase).first if user_login
      end

      def stacks
        @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
      end

      def stack
        @stack ||= stacks.from_param!(params[:stack_id])
      end

      def require_permission!(operation, scope)
        current_api_client.check_permissions!(operation, scope)
