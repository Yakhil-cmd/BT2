### Title
Unrestricted asset attestor-list updates by the asset definer can retroactively freeze already-received "spender_attested" asset units - ([File: validation.js])

### Summary
`XChainController.setVaultChainAddress` let the DAO silently overwrite `vaultUnderlyingAddress` after initial setup, breaking every later `balanceOf` lookup that assumed the mapping was set once and never mutated. The equivalent mutable-mapping-with-no-reassignment-guard pattern exists in ocore's `spender_attested` asset mechanism: the asset definer can update the trusted-attestor mapping for an asset at any time via the `asset_attestors` message, and payment validity for that asset is always checked against the *current* attestor list rather than the list that was in force when the coins were received.

### Finding Description
An asset can be created with `spender_attested: true`, meaning only addresses attested by a definer-controlled attestor list are allowed to spend it [1](#0-0) . The definer publishes and can subsequently freely republish this list via an `asset_attestors` message, validated only by `validateAttestorListUpdate`, which enforces nothing beyond "single author == definer" and a sorted/length check — there is no restriction on how often or how the list may be changed, and no protection for addresses that were attested when they last received funds: [2](#0-1) 

`storage.readAsset` always resolves the attestor list to the *latest* stable update before `last_ball_mci`, i.e. whichever list is current at validation time of the new unit, not the list that applied when the funds were originally transferred: [3](#0-2) 

Payment validation then rejects any spend if none of the unit's authors are currently attested: [4](#0-3) 

This is the same root-cause class as the reported issue: a mapping (`vaultUnderlyingAddress` / attestor list) that downstream logic (`balanceOf` / spend validity) implicitly assumes is stable can be changed at will by a single privileged actor reachable through normal protocol messages (asset issuer), with no safeguard preventing the change from invalidating state that other parties already relied on.

### Impact Explanation
A holder of a `spender_attested` (optionally private+indivisible) asset can legitimately receive coins while attested. The definer can later remove that address from the attestor list at any moment before the holder gets a chance to spend/forward the coins. When the holder then tries to spend, `arrAttestedAddresses.length === 0` triggers "none of the authors is attested" and the payment is rejected, permanently freezing the previously valid holdings tied to that UTXO chain (this is aggravated for `is_private` assets, since light clients cannot even verify attestations and must trust the sender). This matches the "AA/asset fund loss or freezing" impact class validated by the rules.

### Likelihood Explanation
The only actor required is the asset's own definer (an "asset issuer" role explicitly in-scope per the assessment rules) issuing a normal, always-valid `asset_attestors` unit — no special privileges, race conditions, or node cooperation needed. Any asset marked `spender_attested` is exposed to this by design of the mutable list, so likelihood is high whenever such an asset is used with multiple/rotating spenders.

### Recommendation
Bind spend-eligibility for a given output to the attestor list that was current when that output was created (similar to how the report recommends preventing `vaultUnderlyingAddress` reassignment once already set), e.g., record/verify attestation against the list version in effect at the payment's creation MCI rather than the list current at spend time, or require attestor-list changes to only add addresses (never silently revoke already-attested spenders' ability to move coins they already hold).

### Proof of Concept
1. Definer issues asset X with `spender_attested: true` and publishes attestor list `{A}`.
2. Definer (or an attested issuer) sends X to address `A`.
3. Definer publishes a new `asset_attestors` message with list `{B}` (removing `A`) — accepted by `validateAttestorListUpdate` since no restriction exists.
4. `A` attempts to spend the previously received X; `storage.readAsset`/`filterAttestedAddresses` resolve the now-current list `{B}`, `arrAttestedAddresses` for `A` is empty, and `validatePayment` rejects with "none of the authors is attested" — `A`'s funds are permanently frozen despite being valid, attested holdings at time of receipt. function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
