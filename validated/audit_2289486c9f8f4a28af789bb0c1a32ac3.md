### Title
Atomic multi-hop AA composability enables flash-loan-style price manipulation of balance-derived exchange rates - ([File: aa_composer.js])

### Summary
Harvest Finance was drained because an attacker used a flash loan to atomically swing the spot price inside a single Ethereum transaction, then exploited a strategy contract that derived a share/exchange price directly from the pool's instantaneous on-chain balances, minted/redeemed at the distorted rate, and reversed the swap — all before anyone else could react. The ocore engine provides an analogous atomicity primitive for AAs: a chain of "secondary triggers" stemming from one primary trigger unit is validated and committed as a single all-or-nothing batch, and the same AA address can be re-entered multiple times within that one chain, with its balance/state changes from earlier hops immediately visible to later hops. Any AA whose exchange-rate formula reads `balance[asset]` (its own live coin holdings) to price mint/redeem operations is exposed to the same atomic-price-manipulation pattern that hit Harvest Finance.

### Finding Description
`handlePrimaryAATrigger` runs the entire chain of AA responses for one triggering unit inside a single DB transaction and a single `kvstore` batch, only writing/committing once the whole chain of `handleTrigger` calls (primary + secondary triggers) finishes: [1](#0-0) 

Within that one chain, an AA can be triggered more than once — its own response to a bounce/forwarder AA can loop back and re-enter it with updated state, all before anything is written to disk. This is exactly demonstrated by the test `issue recently defined asset`, where `asset_aa` is invoked, forwards a payment to `bouncer_aa`, and `bouncer_aa`'s reflection re-triggers `asset_aa` a second time in the same atomic batch, letting the second invocation read the state variable set by the first: [2](#0-1) 

The secondary-trigger dispatch mechanism that makes this possible is `handleSecondaryTriggers`, which recursively calls `handleTrigger` for every AA address that received a payment from the current response, using the *live* `trigger_opts` (including `assocBalances`) rather than any post-commit, stabilized state: [3](#0-2) 

Balances used inside AA formulas (`balance[asset]`) come from `trigger_opts.assocBalances`, which is updated synchronously as messages are processed within the same chain (`updateInitialAABalances` / `updateFinalAABalances` / the balance deduction inside `sendDummyUnit`): [4](#0-3) [5](#0-4) 

The repository's own reference AMM pattern, `uniswap_like_market_maker.oscript`, prices LP-share issuance/redemption directly from this live, mutable balance:
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
$current_ratio = $asset_balance / $bytes_balance;
$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
...
$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding']);
``` [6](#0-5) 
and the swap logic for both directions likewise uses `balance[$asset]`/`balance[base]` at the moment of the call: [7](#0-6) 

Because (a) the entire multi-hop AA chain triggered from one posted unit is atomic (single tx, single batch, no interleaving by other units/oracles), and (b) the same AA can be re-entered several times within that chain with each hop seeing the balance mutations of the previous hop, an attacker-controlled orchestrating AA can, within one atomic chain:
1. Swap a large amount of bytes/asset into the pool AA to skew `$current_ratio` / `$asset_balance`, `$bytes_balance`.
2. Immediately (same chain, same batch, same trigger lineage) invest/divest at the now-skewed ratio to obtain more `mm_asset` (or more of the underlying asset) than the pool's true depth warrants.
3. Reverse the initial swap, restoring the pool to its original ratio and pocketing the difference extracted from other liquidity providers.

This is structurally identical to the Harvest Finance exploit: no external observer, oracle, or competing party can intervene between steps because the whole sequence resolves and commits as one unit before the network sees any intermediate state — the AA-chain equivalent of a flash loan executing atomically within a single Ethereum block.

### Impact Explanation
An attacker can extract value from other depositors/LPs of any balance-priced AMM-style AA (fund loss for AA and its investors), without needing any privileged role — only the ability to post a triggering unit and define/compose ordinary AAs, which is available to any unprivileged unit poster / AA author. This matches the "AA fund loss" acceptance criterion. The severity depends on how much liquidity the target pool AA holds and how the attacker's helper AA is designed, but the mechanism itself (atomic re-entrant AA composability exposing balance-derived pricing) is a systemic Medium/High-severity risk class inherent to the AA-chain execution model, not merely a "no-impact" theoretical concern, since it is directly analogous to a $24M real-world loss caused by the same bug class (spot-price manipulation atomically bracketing a mint/redeem operation).

### Likelihood Explanation
Likelihood is High for any AA that follows the documented pattern of pricing off `balance[asset]`/`balance[base]` (as ocore's own reference sample does) combined with allowing swap and invest/divest logic to be reachable in the same atomic AA-response chain via an attacker-authored orchestrating AA. Building the attacking AA requires no special privilege — any user can define and trigger arbitrary AAs (`app: 'definition'` + subsequent payment, as shown working end-to-end in `test/aa_composer.test.js`'s AA-chaining tests) — and the exploit does not require waiting for stabilization/confirmation between steps, only ordinary unit composition within one primary trigger's chain.

### Recommendation
- AA authors should never derive mint/redeem pricing purely from the AA's own instantaneous `balance[asset]`/`balance[base]` within the same call chain that can also mutate that balance (swap-then-price-then-invest). Use a state-var-tracked reserve that is only updated at well-defined checkpoints, or require a two-step (two separate primary triggers, across MCI boundaries) process for invest/divest so manipulation cannot be reversed atomically.
- Consider adding engine-level guidance/lint warnings (in AA validation, `aa_validation.js`) flagging formulas that read `balance[...]` inside the same case that also performs asset swaps, or provide a documented best practice of using time-weighted/state-var-cached reserves instead of spot `balance[...]` for pricing.
- Update the official reference sample `uniswap_like_market_maker.oscript` (used as a documented pattern for developers) to defend against intra-chain price manipulation, e.g., by tracking `var['reserve_asset']`/`var['reserve_base']` explicitly rather than trusting live `balance[...]`, since this sample is likely to be copied by real AA authors.

### Proof of Concept
Conceptual chain (all inside one primary-trigger batch, matching the atomicity already proven working in `test/aa_composer.test.js`'s `chain of AAs` / `issue recently defined asset` tests):
1. Attacker deploys `MM` AA using the `uniswap_like_market_maker.oscript` pattern (already seeded with liquidity by legitimate users) and an `Attacker` AA that orchestrates the attack.
2. Attacker's unit sends bytes to `Attacker` AA.
3. `Attacker` AA immediately forwards a large payment to `MM` (case "exchange bytes to asset"), which uses `balance[$asset]` / `balance[base]` at that instant to compute `$amount` and sends the asset back to `Attacker` AA as a secondary-trigger response — this response arrives back at `Attacker` in the same atomic chain (mirrors `bouncer_aa` reflection pattern in `test/aa_composer.test.js:450-527`).
4. `Attacker` AA, still within the same chain, sends a further payment into `MM`'s "invest in MM" case with both asset and base outputs computed to match the now-skewed `$current_ratio`, minting `mm_asset` shares priced off the distorted balance.
5. `Attacker` AA reverses step 3's swap (or lets the pool naturally settle), then, in a following ordinary "divest MM shares" trigger, redeems the shares at the restored, undistorted ratio for a profit funded by existing LPs.

Because every hop in steps 3–4 executes inside `handleSecondaryTriggers`/`handleTrigger` before any batch write/commit (`aa_composer.js:91-115`, `1702-1741`), no other market participant, oracle, or competing transaction can intervene — reproducing the core mechanic of the Harvest Finance flash-loan attack inside ocore's AA execution model.
