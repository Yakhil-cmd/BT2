### Title
Unscoped `status` webhook allows SHA-collision cross-repository status injection, enabling merge-queue bypass - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) by a bare SHA lookup across the entire `commits` table, with no constraint on the repository/organization that produced the webhook. Other handlers in the same codebase (e.g. `CheckSuiteHandler`) explicitly scope by `stacks`/repository, but `StatusHandler` does not, so a status event that GitHub legitimately signs for one repository can update CI state for a commit belonging to a completely different tenant's stack if the two commits happen to share a SHA.

### Finding Description
The broken binding is: `commit.stack_id` (the tenant whose merge queue is being advanced) should equal the tenant `repository_owner`/`repository.full_name` that GitHub's signed `status` webhook actually pertains to. In `StatusHandler#process`, that binding is never checked: [1](#0-0) 

`Commit.where(sha: params.sha)` performs a global, cross-repository lookup and iterates every matching record, calling `commit.create_status_from_github!(params)` for each one, regardless of which stack/repository owns it. Compare this to `CheckSuiteHandler`, which correctly scopes commits to `stacks.where(branch: ...)` derived from `payload.dig('repository', 'full_name')` before touching any commit: [2](#0-1) 

The base `Handler` class even provides a `stacks` helper, scoped via `Repository.from_github_repo_name(repository_name)`, that `StatusHandler` simply does not use: [3](#0-2) 

`WebhooksController#verify_signature` only checks that the webhook's HMAC signature matches the GitHub App secret for the organization named in `params.dig('repository','owner','login')` — i.e., it proves the event genuinely came from GitHub for *that* repository, not that the SHA inside it belongs to that repository: [4](#0-3) 

Exploit flow: an attacker who owns/controls a repository (their own fork or an independent repo) can produce a commit whose SHA collides with a target tenant's tracked commit (e.g., by reproducing the exact same tree, parents, author/committer identity and timestamps — trivial for a cherry-pick or an empty/no-op commit with deterministic metadata). The attacker then triggers a `status` event on their own repository (e.g., via their own CI reporting to that SHA, or any mechanism that causes GitHub to emit a signed `status` webhook for their repo). GitHub signs this webhook with the attacker's own org's webhook secret; `verify_signature` passes because it is a legitimate webhook for the attacker's own org. `StatusHandler#process` then matches `Commit.where(sha: params.sha)` against **all** commits system-wide, finds the target tenant's commit row (same SHA, different `stack_id`), and calls `create_status_from_github!`, which updates that commit's status/CI state in the target's stack and can trigger `stack.schedule_merges` inside `Commit#add_status`: [5](#0-4) 

Because `MergeRequest#all_status_checks_passed?` and the merge scheduling logic rely on `Commit#status`/`state`, injecting a fabricated `success`/`pending` status for the target's commit can push a merge-queue entry the attacker does not own toward `merge!`, resulting in an unauthorized merge/deploy trigger on a tenant the attacker never authenticated against.

### Impact Explanation
This is a payload for one repository mutating another's commit/stack state: an attacker-controlled webhook (legitimately signed for the attacker's own repository) writes CI status records against another tenant's `Commit`/`Stack`, and can flip `stack.schedule_merges` and merge-request eligibility for a repository the attacker does not own or have any authorization on. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge"). The blast radius is any Shipit installation hosting multiple tenants/repositories sharing the same commit-status table, and is repeatable against any commit SHA the attacker can reproduce.

### Likelihood Explanation
The primary precondition — producing a commit with an identical SHA to a target's commit — is the actual bottleneck. Git SHA-1 collisions are not free; the described technique (cherry-pick / empty-commit reproduction with identical tree, parent SHAs, author, committer, and timestamps) can reproduce an identical SHA only when the attacker can fully control/replicate all of the target's commit metadata, which is realistic mainly when: the target commit is a well-known, publicly-visible commit (e.g., an open-source upstream commit merged into multiple tenant forks/mirrors that Shipit tracks across different `Stack`s), or the attacker already has read access to the exact commit object (author, committer, timestamps, parents) they want to collide with. It is not a full SHA-1 collision attack; it exploits the fact that identical commit content produces identical SHA1 regardless of which repository imports it. Given that Shipit is a multi-tenant deploy tool and commit provenance is not otherwise cryptographically bound to a repository at the `Commit` model level, this is a plausible attack when a target repository is a public/open-source project or when multiple tenants track overlapping commit history (forks, mirrors, vendored branches).

### Recommendation
Scope `StatusHandler#process` by repository, mirroring `CheckSuiteHandler` and the `Handler#stacks` helper: resolve `stacks` from the webhook's `repository.full_name`, and restrict the `Commit` lookup to `stack.commits.where(sha: params.sha)` for stacks belonging to that repository, instead of a global `Commit.where(sha: ...)`.

### Proof of Concept
Minitest plan (no live GitHub required):
1. In a test under `test/models/shipit/webhooks/handlers/status_handler_test.rb`, create two `Repository`/`Stack` fixtures in different "repos" (e.g. `github.com/tenant-a/app` and `github.com/attacker/app`).
2. Create `commit_a` under `stack_a` and `commit_b` under `stack_b`, both with the identical `sha: "deadbeef..."` (simulating the SHA collision), both initially with `status.state == 'unknown'`/pending, and with `stack_a` having an open `MergeRequest` awaiting status checks.
3. Build a `status` webhook payload referencing only `attacker/app`'s repository, `sha: "deadbeef..."`, `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is out of scope here since it legitimately passes for the attacker's own org).
5. Assert:
   - `commit_b.reload.status.state == 'success'` (expected, same-repo case), AND
   - `commit_a.reload.status.state == 'success'` (the bug: `commit_a` belongs to a different repository/tenant and should NOT have been altered).
   - Additionally assert `MergeRequest#all_status_checks_passed?` now returns `true` for `stack_a`'s merge request, and/or that `stack_a.schedule_merges` was invoked (e.g., via `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_a])`), demonstrating the merge queue for the un-owned tenant advanced.
