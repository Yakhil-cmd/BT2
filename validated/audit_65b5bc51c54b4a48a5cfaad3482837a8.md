### Title
Permissionless dust top-up strips an account's LTV outside the health-factor gate that protects the rest of the risk tuple - (File: contracts/controller/src/risk/params.rs)

### Summary
Each supply position caches its own `loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees`, copied from the spoke listing at creation. When a listing is tightened, the design gates propagation of the "liquidator-favoring" tuple (lower LT, higher bonus, lower fee) behind a hypothetical health-factor check of `HF >= 1.05` (`THRESHOLD_UPDATE_MIN_HF_RAW`). However, `refresh_supply_risk_params` writes `position.loan_to_value = effective_config.loan_to_value` unconditionally, before and outside that gate. Because third-party `supply` top-ups to an existing leg and `update_account_threshold(has_risks = false)` are permissionless, any unprivileged address can force-strip a victim's stored LTV at any health factor — including exactly the unhealthy states where the gate exists to shield the account from tightened parameters. This mirrors CVE-2015-1350: an operation underspecifies its requirements, so a security-relevant attribute (the LTV stamp) is dropped through a path that was supposed to be gated.

### Finding Description
In `contracts/controller/src/risk/params.rs`, `refresh_supply_risk_params` assigns the new LTV with no condition, then calls `apply_gated_liquidation_params` only for the LT/bonus/fee tuple. `apply_gated_liquidation_params` skips updates that favor the liquidator when the account has debt and `clears_min_hf` fails — but LTV has already been overwritten by that point.

Two unprivileged entrypoints reach this:

1. `supply(caller, account_id = victim, assets = [dust of an asset the victim already supplies])` → `merge_supply_leg` (`contracts/controller/src/positions/supply.rs:275`) calls `refresh_supply_risk_params` with `FullTuple`. A stranger may top up an existing leg (`revalidation_third_party_can_top_up_only_existing_leg` confirms only new-leg creation requires owner auth).
2. `update_account_threshold(caller, has_risks = false, [victim])` → `sync_account_thresholds` uses `LtvOnly` scope, restamps LTV with no HF check, never loads debt, and never reverts.

The inconsistency is concrete: with `has_risks = true` and post-change HF < 1.05, the call reverts with `HealthFactorTooLow` and leaves every stamp untouched; with `has_risks = false` or a dust `supply`, the LTV component of the same tightening lands anyway on the same unhealthy account. Harness tests pin the gap: `poc_third_party_top_up_force_restamps_ltv`, `regression_supply_skips_bonus_only_raise_below_min_hf` ("LTV rides outside the gate"), `poc_lt_cut_stays_sticky_when_hf_below_min` (LT held at 8000 while LTV restamped to 5000), and `risk_ltv_low_hf` in `tests/integration/flows/admin.sh` (LTV restamped on an account whose full-batch update reverts).

### Impact Explanation
The borrow limit uses `min(stored LTV, stored LT)`. Once a listing's LTV is reduced — including to `0` when governance sets `can_collateral = false` / zeros the LTV — a one-stroop top-up or an `LtvOnly` keeper call permanently restamps the victim's position to the floor value. The victim's borrows then fail with `InsufficientCollateral` even though the account's health factor and liquidation terms were explicitly preserved by the gate. This is a denial of borrowing capability (temporary freezing of the account's leverage/credit function) inflicted by an unprivileged third party, and it is asymmetric with the protection the protocol deliberately built for the same parameter-change event: the account is too unhealthy to safely take the new LT, yet still forced to take the new LTV. The victim cannot restore the old stamp; only a subsequent listing change or repayment-plus-resupply path alters it.

### Likelihood Explanation
Requires a preceding admin `edit_asset_in_spoke` that lowers LTV (a routine risk-tightening operation, per the documented runbooks) and a victim account holding that asset as a supply leg. After that, the trigger is one permissionless call costing dust. Every borrow and withdrawal also restamps LTV unconditionally (`restamp_listed_supply_ltv`), so the reduction applies to all accounts over time regardless — the attack merely makes it immediate, targeted, and effective on accounts the HF gate was designed to exempt. Impact is capped at borrow denial (no direct fund loss or HF change), which places it at Medium.

### Recommendation
Extend the `favors_liquidator`/`clears_min_hf` gate to cover a *decrease* in `loan_to_value` for accounts with debt, i.e., skip the LTV write (or skip the whole restamp) when the new LTV is lower and the hypothetical HF floor is not met — or document that LTV reduction is intentionally ungated and have `update_account_threshold(has_risks = false)` refuse accounts where the LTV cut would breach the same floor the `FullTuple` path enforces.

}

pub(crate) fn apply_gated_liquidation_params(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &mut AccountPosition,
    effective_config: &AssetConfig,
) {
    if favors_liquidator(position, effective_config)
        && !account.debt_free()
        && !clears_min_hf(
            env,
            cache,
            account,
            hub_asset,
            position,
            effective_config.liquidation_threshold,
        )
    {
        return;
    }

    position.liquidation_threshold = effective_config.liquidation_threshold;
    position.liquidation_bonus = effective_config.liquidation_bonus;
    position.liquidation_fees = effective_config.liquidation_fees;
}

pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
}

pub(crate) fn merge_supply_leg(
    env: &Env,
    account: &mut Account,
    action: &PoolAction,
    result: &PoolPositionMutation,
    cache: &mut Context,
) {
    let hub_asset = &action.hub_asset;
    let asset_config: AssetConfig = cache.require_spoke_asset(account.spoke_id, hub_asset);

    let mut position = account.get_or_create_supply_position(hub_asset, &asset_config);
    let old_scaled = position.scaled_amount;

    refresh_supply_risk_params(
        env,
        cache,
        account,
        hub_asset,
        &mut position,
        &asset_config,
        RiskRefreshScope::FullTuple,
    );

    let outcome = LegOutcome::from(result);
    position.scaled_amount = outcome.new_scaled;

#[test]
fn poc_third_party_top_up_force_restamps_ltv() {
    let mut t = LendingTest::new().standard_two_asset_dust_disabled();

    t.supply(ALICE, "USDC", 10_000.0);
    let id = t.resolve_account_id(ALICE);

    t.edit_asset_config("USDC", |c| {
        c.loan_to_value = 5_000;
        c.liquidation_threshold = 5_500;
    });

    t.try_supply_to_account(BOB, ALICE, "USDC", 1.0)
        .expect("third-party top-up of existing leg allowed");
    let (ltv, _) = supply_ltv_and_lt(&t, id, "USDC");
    assert_eq!(
        ltv, 5_000,
        "H-RISK-03: third-party top-up force-restamps LTV"
    );

    let blocked = t.try_borrow(ALICE, "ETH", 3.5);
    assert_contract_error(blocked, errors::INSUFFICIENT_COLLATERAL);

    t.borrow(ALICE, "ETH", 2.0);
    t.assert_healthy(ALICE);
}
