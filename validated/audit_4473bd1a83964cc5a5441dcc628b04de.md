## Admission Analog Found: Multisig transaction execution binding is not enforced to the approved payload when only a full payload (not a hash) is stored on-chain

### Title
Multisig approval-to-execution payload binding can be bypassed, letting an owner execute a different transaction than the one owners voted for - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`validate_multisig_transaction`, the function invoked by the VM prologue during mempool admission and execution of a `multisig_account` transaction, is supposed to guarantee that the payload actually executed is the same payload that owners voted `num_signatures_required` approvals for. The function only enforces this binding in two cases: when a `payload_hash` was stored on creation, or when a feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on and a full payload was stored. If a multisig transaction was created via the "store full payload" path (no hash) and the mismatch-guard feature is not enabled, the function performs no comparison at all between the on-chain approved payload and the `payload` argument supplied at execution/admission time.

### Finding Description
`validate_multisig_transaction` runs the approval-count and timelock checks, then attempts to bind the caller-supplied `payload: vector<u8>` to what owners actually approved: [1](#0-0) 

```
// If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored on chain.
if (transaction.payload_hash.is_some()) { assert!(sha3_256(payload) == *payload_hash, ...) };
// If the transaction payload is stored on chain and there is a provided payload,
// verify that the provided payload matches the stored payload.
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, ...);
}
```

This shows two disjoint guarded branches:
1. `transaction.payload_hash.is_some()` — this is set only when the transaction was created via the hash-committing path (e.g. `create_transaction_with_hash`), which stores `payload_hash: option::some(...)`, `payload: option::none()`.
2. The second branch, comparing the actually stored full payload, is gated behind `features::abort_if_multisig_payload_mismatch_enabled()`.

If a transaction was created with the "store full payload" path (`payload_hash` is `option::none()`, `payload` is `option::some(...)`) and the `abort_if_multisig_payload_mismatch` feature is not enabled, **neither branch executes**. The function then falls through, having validated only the quorum count and timelock, without ever asserting that the caller-supplied `payload` bytes equal `transaction.payload` (the payload owners actually voted `num_approvals >= num_signatures_required` for).

Since `validate_multisig_transaction` is explicitly documented as "Called by the VM as part of transaction prologue, which is invoked during mempool transaction validation and as the first step of transaction execution" [2](#0-1) , this is exactly the admission boundary in scope: the outer transaction's real entry-function payload (constructed independently by whoever submits the executing transaction, typically the last approving owner) is what actually executes on the multisig account's behalf, while the quorum of owners believed they were approving `transaction.payload`.

The existence of the `abort_if_multisig_payload_mismatch_enabled` feature flag and its associated comment strongly indicate this exact class of payload-substitution issue was previously identified, and the fix was shipped as an opt-in feature flag rather than unconditional logic — meaning any network/environment where the flag has not been activated is still exposed to the gap.

### Impact Explanation
This breaks the "approval validation accepting the wrong signing material or wrong approval set" invariant explicitly called out in the admission pivots: the multisig quorum's approval is bound to `transaction.payload`, but admission does not enforce that the executed instruction matches what was approved. An owner (the one submitting the executing transaction, who need not even be one of the quorum-approving owners beyond meeting the numeric threshold) could construct a transaction whose real entry-function call differs from what the other owners saw and voted on, and it would pass `validate_multisig_transaction` cleanly as long as quorum count and timelock are satisfied. This can be used to authorize/execute unintended state transitions (e.g., asset transfers, capability grants) under the multisig account's authority that were never actually approved, which is a high-severity unauthorized-execution outcome under the wrong approval set.

### Likelihood Explanation
Exploitability depends entirely on: (a) the multisig transaction being created via the "store full payload" path rather than the hash-committing path, and (b) `abort_if_multisig_payload_mismatch_enabled` not being active in that environment. I was not able to confirm within the available tool budget whether this feature is enabled by default on current mainnet/testnet genesis, nor did I fully verify the sibling `create_transaction` (non-hash) function body to confirm it always leaves `payload_hash` as `option::none()`. This is a real gap in my verification and should be checked before treating this as confirmed-exploitable on any specific live network; however, the code-level logic itself unambiguously permits payload substitution whenever these two conditions hold.

### Recommendation
Remove the feature-flag gating and always enforce `payload == *transaction.payload.borrow()` whenever `transaction.payload.is_some()`, mirroring the unconditional hash check performed for `payload_hash.is_some()`. Alternatively, deprecate/disallow the "store full payload without hash" creation path so that on-chain payload commitments are always either a hash or an unconditionally-enforced full payload.

### Proof of Concept
1. Owner A calls `create_transaction(owner, multisig_account, payload_A)` (the no-hash path), storing `transaction.payload = Some(payload_A)`, `transaction.payload_hash = None`.
2. Owners B, C (sufficient for quorum) call `approve_transaction`, believing they are approving `payload_A`.
3. On an environment where `abort_if_multisig_payload_mismatch_enabled` is false, Owner A (or any party constructing the actual on-chain transaction executed against the multisig account) submits a transaction whose real BCS-encoded `payload` argument is `payload_B` (a different, unapproved instruction).
4. `validate_multisig_transaction` checks `transaction.payload_hash.is_some()` → false (skip), checks feature flag → false (skip) → falls through with no payload equality assertion, then proceeds to execute `payload_B` under the multisig account's authority despite only `payload_A` having quorum approval.
