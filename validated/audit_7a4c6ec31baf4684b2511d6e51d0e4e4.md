### Title
Webhook signature is checked against `repository.owner.login`, but event handlers act on `repository.full_name` from the same unverified payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC against using an organization name taken directly out of the untrusted request body, while the downstream event handlers pick which `Stack`/`Repository` to mutate using a different field from that same untrusted body. Because nothing binds these two fields together, an attacker who can produce a validly-signed (or default-unsigned) payload for one organization can make the request act on a repository belonging to a different, unrelated organization.

### Finding Description
The signature check derives the signing organization purely from the JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks a `GitHubApp` config by `repository.owner.login` (or `organization.login`) from the payload, and `verify_webhook_signature` is checked against that org's `webhook_secret`: [3](#0-2) 

Notice `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for the selected organization (a common/default state, see `webhook_secret: # nil` in every documented config example: `config/secrets.development.example.yml`, `test/dummy/config/secrets.yml`).

However, the actual side-effecting handlers never look at `repository_owner` at all. They resolve the target repository/stack from a completely separate field, `repository.full_name`: [4](#0-3) 

`PushHandler` uses this to trigger a GitHub sync on all matching stacks, and `StatusHandler` uses `params.sha` (also unauthenticated payload data with no repository-consistency check) to write a commit status on any `Commit` with a matching SHA across the whole install: [5](#0-4) [6](#0-5) 

**The broken binding (equality that should hold but doesn't):**
`organization whose signature was verified (repository.owner.login)` == `organization owning the repository actually written to (repository.full_name's owner)`.

Before the attack: for a legitimate webhook, GitHub always sends `repository.owner.login` and `repository.full_name` consistently for the same repo, so this equality holds implicitly (not because the code enforces it).

After the attack: an attacker directly POSTs to `/webhooks` (this endpoint has no authentication other than the HMAC check) with:
- `X-Github-Event: push` (or `status`)
- `repository.owner.login` = an organization configured in `Shipit.github` with **no `webhook_secret`** (or one whose secret the attacker can compute/obtain), so `verify_webhook_signature` trivially returns `true`.
- `repository.full_name` (for `push`) or `sha` (for `status`) = a value that matches a real tracked `Repository`/`Commit` belonging to a **different** organization/stack.

The signature check passes (organization A), but the handler acts on organization B's stack/commit, since `Handler#stacks`/`StatusHandler#process` never re-check `repository.owner.login` against the resolved `Repository`'s actual owner.

### Impact Explanation
This maps to the "unauthenticated read/write of stack state" and, depending on downstream effects, potentially "unauthorized deploy" categories:
- Via `StatusHandler`, an attacker can inject arbitrary commit statuses (`create_status_from_github!`) onto any commit in the installation just by knowing its SHA, without ever authenticating to the actual owning organization/repo. If a stack uses required-status-based deployability or continuous deployment gating on commit status, this can influence deploy eligibility.
- Via `PushHandler`, an attacker can force `stack.sync_github(expected_head_sha: ...)` to run against arbitrary tracked stacks by forging `repository.full_name`, using only a signature that is valid (or trivially bypassed) for an unrelated/no-secret organization.

### Likelihood Explanation
Requires: (a) the Shipit instance to be multi-org configured or to have at least one organization with a blank `webhook_secret` (the documented default in every setup example), and (b) knowledge of a target commit SHA or repository full name for a different tracked stack — both of which are typically public information (git history, PR/commit links). No repository write access, GitHub App credentials, or Shipit session is needed; the request goes straight to the public `/webhooks` endpoint.

### Recommendation
Bind the two fields explicitly: after resolving the target `Repository`/`Commit` in `Handler#stacks` (and in `StatusHandler`), verify that the resolved repository's actual GitHub owner matches the `repository_owner`/organization whose signature was verified for this request, and reject the event otherwise.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (no `webhook_secret`) and `OrgB` (tracked stack `OrgB/real-repo`, commit `sha` present in DB).
2. POST to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/anything"},
  "sha": "<known sha of OrgB/real-repo commit>",
  "state": "success"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `OrgB` commit — and calls `commit.create_status_from_github!(params)`, injecting a forged `success` status onto `OrgB`'s commit despite never signing anything for `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
