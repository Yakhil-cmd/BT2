### Title
Cross-organization webhook forgery: signature verified against `repository.owner.login`'s app, but repository acted upon is selected from the unbound `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`config/secrets.yml` with a per-organization `github:` map, e.g. `test/dummy/config/secrets_double_github_app.yml`), the webhook signature is authenticated against the GitHub App belonging to the organization named in `repository.owner.login` (or `organization.login`), but the actual repository/stack a handler mutates is looked up independently from `repository.full_name` in the same payload. Nothing binds these two fields together, so a payload can validly authenticate as "Org A" while acting on "Org B/repo".

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using only the organization name taken from the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config (`app_id`, `installation_id`, `webhook_secret`) from `secrets.github`, supporting exactly this multi-tenant model: [3](#0-2) 

Signature checking is delegated to `GitHubApp#verify_webhook_signature`, which — critically — **returns `true` unconditionally if that organization has no `webhook_secret` configured**: [4](#0-3) 

Meanwhile, every webhook `Handler` resolves the repository/stack to act on using a *different* field of the same JSON body — `repository.full_name` — with no cross-check against the `repository.owner.login`/`organization.login` value used for signature selection: [5](#0-4) 

The same independent-field pattern repeats in every concrete handler (`PushHandler`, `StatusHandler`, `OpenedHandler`, `ClosedHandler`, etc.), which use `stacks`/`Repository.from_github_repo_name(params.repository.full_name)`: [6](#0-5) [7](#0-6) [8](#0-7) 

**The binding that is broken (as an equality):**
`organization_authenticating_signature (payload.repository.owner.login)` MUST equal `organization_owning_repository_acted_upon (prefix of payload.repository.full_name)`.

Before the attack: for genuine GitHub-originated webhooks, GitHub always sets both fields consistently for the real repository, so the equality holds implicitly.

After the attack: an unprivileged party who can produce *any* validly-signed payload for organization A (trivially true if A has no `webhook_secret` configured — the documented/default state shown in every secrets example, `webhook_secret: # nil`) can set `repository.owner.login = "A"` (or `organization.login = "A"`) while setting `repository.full_name = "B/victim-repo"` for a completely unrelated organization B hosted on the same Shipit instance. `verify_signature` passes (A's app requires no secret, or the attacker otherwise knows/controls A's secret), yet the handler acts on B's repository, which the attacker never authenticated for.

This directly matches the requested bug class: "an organization that authenticated versus the repository that is written."

### Impact Explanation
This is a **cross-tenant, unauthenticated webhook injection**. Concretely, on a shared Shipit instance serving multiple GitHub organizations:
- `StatusHandler` lets the attacker set arbitrary CI status (`state`, `context`, `target_url`) on any `sha` belonging to `Commit` rows under organization B's stacks — `Commit#create_status_from_github!` can be used to mark a malicious commit as CI-`success`, satisfying `ci.require`/`blocking_statuses` gating and enabling an **unauthorized deploy** if continuous deployment is enabled for that stack.
- `PushHandler` can trigger `GithubSyncJob`/`sync_github` against B's stacks using an attacker-chosen `after` SHA.
- `PullRequest::OpenedHandler`/`ClosedHandler` can create or archive Review Stacks for org B's repositories, and other pull_request handlers manipulate label/assignee state used for provisioning.

Because none of these require a Shipit session, an `ApiClient` token, or knowledge of org B's secret, this crosses the "unauthorized deploy" / cross-repository-write impact bar for a Critical/High finding, contingent on org A having no (or a leaked) `webhook_secret` — which is the default/common configuration shown in every shipped example (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`).

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported feature — "Using Multiple GitHub Applications"), and (2) at least one of those organizations having a blank/absent `webhook_secret` (shown as the default `nil` in all shipped config examples) or an attacker who otherwise knows that organization's secret (e.g., they administer that org's own GitHub App). Given that condition, the attack is a single unauthenticated HTTP POST to the public webhooks endpoint with attacker-controlled JSON — no additional access needed.

### Recommendation
In `WebhooksController#verify_signature`/`Handler`, enforce that the organization used to select the verifying GitHub App matches the owner of `repository.full_name` (or `organization.login`) that the handler will subsequently act on, e.g. reject the payload if `payload.dig('repository','full_name')&.split('/')&.first&.downcase != repository_owner&.downcase`. Additionally, do not silently accept payloads for organizations with a blank `webhook_secret` in multi-tenant configurations; require an explicit secret per organization when more than one GitHub App is configured.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (no `webhook_secret` set / default nil) and `OrgB` (a real customer with active stacks), per `test/dummy/config/secrets_double_github_app.yml`.
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-malicious-sha-under-OrgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
3. `verify_signature` resolves `Shipit.github(organization: 'OrgA')`; since `OrgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of any/no `X-Hub-Signature` header.
4. `StatusHandler#process` looks up `Commit.where(sha: ...)` under `OrgB`'s stacks (via `full_name`) and creates a `success` status, potentially unblocking a deploy that OrgB's own CI never approved.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
