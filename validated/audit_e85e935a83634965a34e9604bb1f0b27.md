### Title
Newly-created worktrees are published via symlink without integrity verification, unlike existing worktrees — (File: main.go, function `SyncRepo`/`configureWorktree`)

### Summary
`git-sync` verifies that a worktree's actual `HEAD` matches its expected hash (via `sanityCheckWorktree`) only when it decides *not* to re-sync (i.e., `currentHash == remoteHash`). When a *new* worktree is created for a changed remote hash, the code trusts that `git worktree add` + `git reset --hard` + `git submodule update` succeeded and produced the correct content, and immediately calls `beforePublish`/`publishSymlink`/`afterPublish` without re-running the same `rev-parse HEAD` / `fsck` sanity check that is applied to the "no change" path.

### Finding Description
In `configureWorktree` [1](#0-0) , git-sync runs `git reset --hard <hash> --` and, if submodules are enabled, `git submodule update --init [--recursive] [--depth N]` against attacker-influenced repository content (remote ref/commit, `.gitmodules`, submodule URLs, sparse-checkout file). The function only checks the exit code of each git invocation; it never confirms afterward that the worktree's `HEAD` actually equals the intended `hash`, nor runs `git fsck`.

Compare this to the only place such a check does exist, `sanityCheckWorktree` [2](#0-1) , which performs exactly that verification (`rev-parse HEAD` equality and `fsck --connectivity-only`). In `SyncRepo`, this function is invoked solely in the branch where `currentHash == remoteHash` (i.e., nothing changed) [3](#0-2) . When a change is detected, the flow instead goes: `createWorktree` → `configureWorktree` → `syncHooks.beforePublish` → `publishSymlink` → `syncHooks.afterPublish`, with no equivalent check on the freshly built worktree [4](#0-3) .

This means the "publish" decision is made purely on git command exit codes, not on a verified post-condition that the on-disk content actually corresponds to `remoteHash`. If any step in the untrusted-content-driven checkout/submodule pipeline (e.g., a submodule pointing at a different/attacker-controlled ref, a sparse-checkout file interaction, or any git operation that exits 0 while leaving the tree in a state that doesn't match the intended commit) silently diverges from the intended commit, git-sync will still flip the symlink and fire `afterPublish` (webhook/exechook) hooks — trusting the outcome exactly the way the referenced `FeeBuyback.submit` trusted its post-swap token balance without checking it actually resulted from swapping the correct asset.

### Impact Explanation
If the checked-out worktree content diverges from `remoteHash` (whether due to submodule manipulation, sparse-checkout interference, or any other git behavior that returns success without producing the intended tree), consumers reading through `--link` receive incorrect or partial content while git-sync still reports success, updates readiness/liveness state, and fires `afterPublish` webhooks/exechooks as if the correct commit was published. This matches "publishing wrong or partial content" and "persistent sync denial to correct state" since the local check that would normally catch such divergence (`sanityCheckWorktree`) is skipped on the newly-created worktree path.

### Likelihood Explanation
This requires an attacker who controls the remote repo content (a supported and expected threat model for git-sync, since `--repo` is explicitly synced from a possibly-untrusted or compromised source) to craft repository state (e.g., submodule config, sparse-checkout files) that causes one of the checkout-related git subcommands to exit successfully while not producing the exact intended commit tree. The exact reliability of forcing such a divergence deterministically is git-version/config dependent, which lowers likelihood, but the missing verification is a clear, reachable gap in the code path itself, unconditionally present for every sync that changes hash.

### Recommendation
Call `sanityCheckWorktree` (verifying `rev-parse HEAD == hash` and `fsck --connectivity-only`) on the newly created/configured worktree in `SyncRepo` before invoking `beforePublish`/`publishSymlink`, mirroring the check already performed on the "unchanged" path, so that the symlink flip and hook firing occur only after positively confirming the worktree matches the fetched remote hash.

### Proof of Concept
1. Point `git-sync` at an attacker-controlled `--repo` with `--submodules=recursive` (or a `.git-sparse-checkout` file supplied via `--sparse-checkout-file`).
2. Craft the repository so that on the relevant commit, `git worktree add --no-checkout` + `git reset --hard <hash>` + `git submodule update --init --recursive` each return exit code 0, but the resulting working tree does not fully/exactly correspond to `<hash>` (e.g. a submodule config that resolves differently than expected, or sparse-checkout rules unexpectedly excluding/including paths).
3. Observe in `SyncRepo` [4](#0-3)  that no call equivalent to `sanityCheckWorktree` is made on `newWorktree` before `syncHooks.beforePublish`/`publishSymlink`/`syncHooks.afterPublish` run, so the symlink is flipped and webhooks fire against the divergent content, unlike the "no change" path which would have caught and rejected such a mismatch via `sanityCheckWorktree` [3](#0-2) .

// sanityCheckWorktree tries to make sure that the dir is a valid git
// repository.  Note that this does not guarantee that the worktree has all the
// files checked out - git could have died halfway through and the repo will
// still pass this check.
func (git *repoSync) sanityCheckWorktree(ctx context.Context, worktree worktree) bool {
	git.log.V(3).Info("sanity-checking worktree", "repo", git.root, "worktree", worktree)

	// If it is empty, we are done.
	if empty, err := dirIsEmpty(worktree.Path()); err != nil {
		git.log.Error(err, "can't list worktree directory", "path", worktree.Path())
		return false
	} else if empty {
		git.log.V(0).Info("worktree is empty", "path", worktree.Path())
		return false
	}

	// Make sure it is synced to the right commmit.
	stdout, _, err := git.Run(ctx, worktree.Path(), "rev-parse", "HEAD")
	if err != nil {
		git.log.Error(err, "can't get worktree HEAD", "path", worktree.Path())
		return false
	}
	if stdout != worktree.Hash() {
		git.log.V(0).Info("worktree HEAD does not match worktree", "path", worktree.Path(), "head", stdout)
		return false
	}

	// Consistency-check the worktree.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, worktree.Path(), "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "worktree fsck failed", "path", worktree.Path())
		return false
	}

	return true
}
