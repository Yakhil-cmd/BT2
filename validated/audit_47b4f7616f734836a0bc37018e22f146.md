### Title
Stale `Team` record reused by slug allows former GitHub team members to retain Shipit authorization after the team is deleted and recreated - ([File: app/models/shipit/team.rb](app/models/shipit/team.rb))

### Summary
`Shipit.github_teams` resolves each configured `organization/slug` handle to a `Shipit::Team` record via `Team.find_or_create_by_handle`, which looks the record up **only by `organization` and `slug`**, never by the GitHub team's numeric `id`. `Membership` rows (the actual authorization grants) hang off that `Team` record and are only refreshed on demand. If the underlying GitHub team is deleted and a new team is later created with the same slug, Shipit will silently rebind the new team to the old, stale `Team` row — along with all of its previously granted `memberships` — instead of treating it as a distinct team.

### Finding Description
`Team.find_or_create_by_handle` resolves purely by `organization`/`slug`: [1](#0-0) [2](#0-1) 

This is the path used to build `Shipit.github_teams`, the list of teams that gate access to the whole engine: [3](#0-2) 

Authorization itself is checked against the `memberships` join table: [4](#0-3) 

Separately, the `membership` webhook handler resolves/creates `Team` rows keyed by GitHub's numeric `github_id`, not by slug: [5](#0-4) 

Because two different code paths key the same logical "team" concept by two different identifiers (`organization+slug` for config resolution/`refresh_members!`, vs `github_id` for webhook-driven membership add/remove), nothing ever deletes or invalidates the `Team` row (and its `memberships`) when the real GitHub team behind a given `organization/slug` is deleted and later recreated with a different `github_id`. The binding that should hold — *the GitHub team currently owning `organization/slug` == the Shipit `Team` row (and its member list) granting access for that handle* — breaks: the old row, and its old members, keep being treated as "the" team for that handle until an operator happens to run `rake teams:fetch` (`refresh_members!`), which is the only code path that resyncs membership from GitHub for handle-based teams: [6](#0-5) 

This mirrors the reported bug class exactly: removal of the authoritative entity (the GitHub team) does not clear the associated privilege data (`memberships`) tied to the identifier (`organization/slug`) that gets reused, so a newly created entity sharing that identifier inherits the old entity's access grants.

### Impact Explanation
Users who were legitimately part of an old, now-deleted GitHub team retain Shipit access (escalation into `Shipit.github_teams` authorization) even though they are not members of the GitHub team that currently owns that `organization/slug`, until the periodic `teams:fetch` rake task is run. Since `force_github_authentication` gates the entire engine on `current_user.authorized?`, this is a real authorization-bypass window scoped to the High-impact category "escalation into `Shipit.github_teams` authorization." [7](#0-6) 

### Likelihood Explanation
This requires a GitHub org owner (not a Shipit-privileged user) to delete and recreate a team with the same slug — an action outside Shipit's control — and relies on the operational gap that `teams:fetch` is not run immediately/automatically after such a change. It is a real, exploitable trust-boundary gap in the code (no code path clears stale memberships on team deletion), but it depends on an external GitHub-side event and an unrefreshed cache window, making exploitation opportunistic rather than trivially attacker-triggered on demand.

### Recommendation
Key `Team` resolution consistently by `github_id` (as the webhook handler already does) rather than by `organization`/`slug`, and/or clear a team's `memberships` whenever its `github_id` no longer matches the currently resolved GitHub team for a given `organization/slug`. Alternatively, invalidate/expire cached `Team`/`Membership` data automatically (not only via manual `rake teams:fetch`) whenever `Shipit.github_teams` re-resolves a handle.

### Proof of Concept
1. Configure `Shipit.github_teams` with handle `acme/ops`; `Team.find_or_create_by_handle` creates `Team(organization: "acme", slug: "ops", github_id: 111)` with members `[alice]` via `refresh_members!`.
2. Alice is authorized because `alice.teams` includes this `Team` row.
3. On GitHub, org owner deletes team `ops` (id `111`) and later creates a new team also named/slugged `ops` (id `222`) with different membership (`[bob]`), intended to be unrelated to Shipit access.
4. Shipit never receives/handles a "team deleted" signal for the handle-based `Team` row; the old `Team(organization: "acme", slug: "ops")` row and its `memberships` (`alice`) remain untouched in the database.
5. Until an operator manually runs `rake teams:fetch`, `Shipit.github_teams` still resolves to the same stale `Team` row, so `alice.authorized?` remains `true` even though she is no longer part of the actual GitHub team `acme/ops` (id `222`), and `bob`, the real current member, is not reflected at all.
