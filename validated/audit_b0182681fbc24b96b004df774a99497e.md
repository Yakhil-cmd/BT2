## Analysis

The sherlock finding is a "trust an unvalidated value" bug class: `PricerInternal` reads an oracle's `answer` but never checks the paired `updatedAt` field, so a stale/incorrect value is treated as authoritative. The closest analog in shipit-engine is the webhook trust boundary: the *organization used to select and verify the webhook signature* is never bound to the *organization/team fields that the handler actually writes to the database*. The signature proves "this org's configured secret signed this raw body", but the fields consumed inside that body (`organization.login`, `team.id`, `member.login`) are trusted at face value without being cross-checked against the verified organization scope, exactly like `updatedAt` never being cross-checked against the `answer` in the original bug.

`WebhooksController#verify_signature` selects the `GitHubApp` (and its secret) using an untrusted, attacker-supplied field from the very payload it's about to verify: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [3](#0-2) 

`MembershipHandler#process` then trusts `params.organization.login`, `params.team.id`, and `params.member.login` from the payload to create/find a `Team` and add an arbitrary `member` to it, with no re-validation against GitHub itself: [4](#0-3) 

`Team.add_member` unconditionally appends the member with no membership re-check: [5](#0-4) 

`User#authorized?` relies purely on local `teams` association rows populated by this handler, never re-querying GitHub at authorization time: [6](#0-5) 

Any organization configured in Shipit without a `webhook_secret` (documented as "optional" in `docs/setup.md`) accepts unsigned webhook payloads, so an unprivileged attacker can POST a forged `membership` event granting any GitHub login membership in any `Shipit.github_teams`-tracked team, escalating that GitHub account into Shipit's authorization group without ever having real GitHub team membership.

### Title
Membership webhook trusts unauthenticated payload to grant local team authorization when `webhook_secret` is unset - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` short-circuits to `true` whenever the targeted organization has no `webhook_secret` configured, and even when signed, the signature only proves the raw body came from *some* sender possessing that org's secret — it does not bind the specific `organization.login`, `team.id`, or `member.login` fields inside the payload to anything re-verified against GitHub. `MembershipHandler#process` uses these unverified fields directly to create a `Team` record and call `Team#add_member`, which is later consulted by `User#authorized?` to gate access to the entire Shipit application.

### Finding Description
The equality that should hold is: *GitHub org/team membership state == Shipit local `Membership` rows used for authorization*. The webhook pipeline breaks this equality in two ways:

1. `verify_webhook_signature` returns `true` when `webhook_secret` is blank [3](#0-2) , so for any org without a configured secret (an explicitly optional setting per `docs/setup.md`), no cryptographic binding exists between the payload and the real GitHub, letting an unprivileged attacker forge any webhook event by simply POSTing to `/webhooks`.
2. Even where a signature check occurs, it is selected using `repository_owner`, an attacker-controlled field read out of the very payload being verified [2](#0-1) , and the handler subsequently trusts other fields in the same payload (`organization.login`, `team.id`, `member.login`) without any secondary check against GitHub's actual team roster [7](#0-6) .

The `member.login` is resolved into a real or newly-created `User` and unconditionally appended to the `team.members` association [5](#0-4) . That local `teams` association is exactly what `User#authorized?` checks to grant application-wide access [6](#0-5) .

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization, matching the High-severity criteria in scope. An attacker who can reach `/webhooks` for a Shipit org that has no `webhook_secret` configured can grant any GitHub login (including a login the attacker controls and can OAuth-login as through `GithubAuthenticationController#callback`) membership in a team Shipit trusts for authorization, bypassing the intended GitHub-team-membership gate entirely and obtaining full access to stacks, deploys, and task streams.

### Likelihood Explanation
Likelihood depends on whether the targeted organization has a `webhook_secret` configured. The setup documentation explicitly lists it as optional [8](#0-7) , and the shipped example secrets templates ship with `webhook_secret: # nil` [9](#0-8) , so operators following the documented "optional" path are exposed by default. Where a secret is configured, the payload fields consumed by `MembershipHandler` still aren't independently re-verified against GitHub's team API, so any legitimate webhook delivery (e.g., a compromised or malicious member of the sending org triggering their own membership events) can still inject unrelated team/member combinations.

### Recommendation
- Require `webhook_secret` to be present for all configured organizations and refuse to process any webhook (return 422) when it is absent, rather than treating an absent secret as automatically verified.
- In `MembershipHandler#process`, re-validate that `params.organization.login` matches the verified signing organization, and consider re-fetching team membership from the GitHub API (as `Team#refresh_members!` already does) rather than trusting the webhook body's `member`/`team` fields directly for authorization-relevant state.

### Proof of Concept
1. Configure (or find) a Shipit organization entry under `github:` without a `webhook_secret` (the documented default/optional configuration).
2. As an unprivileged external attacker, `POST /webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Fake", "slug": "fake-team", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-controlled-login" }
}
```
3. `verify_signature` calls `verify_webhook_signature` which returns `true` because `webhook_secret` is blank for `victim-org` [10](#0-9) .
4. `MembershipHandler#process` creates a `Team` with `github_id: 999` if `999` matches an id referenced by `Shipit.github_teams`, and appends the `attacker-controlled-login` user to it [11](#0-10) .
5. The attacker then completes OAuth login as `attacker-controlled-login`; `User#authorized?` returns `true` because the forged `Membership` row exists locally [6](#0-5) , granting full access to Shipit despite never having real GitHub team membership.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

          end
        end
      end
```
