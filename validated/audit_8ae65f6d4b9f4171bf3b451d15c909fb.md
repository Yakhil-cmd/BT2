Confirmed: unlike `PushHandler` (which uses `stacks` — scoped via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) and the pull-request handlers (which all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)`), `Shipit::Webhooks::Handlers::StatusHandler#process` never looks at the payload's `repository` field at all. It runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, which matches every `Commit` row in the entire database whose `sha` column equals the attacker-supplied string, across every stack/repository/tenant.

### Title
Cross-repository Status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's `repository.full_name` matches the repository owning that commit's stack. A `status` webhook that GitHub genuinely delivers and signs for repository A (which the attacker legitimately controls or pushes to) can create a `Status` row attached to a `Commit` belonging to an unrelated stack/repository B, as long as the two commits share a `sha`. This directly writes CI state for a repository that never authenticated that state, which then flows into `Commit#state`/`#status` and `StacksHelper#deploy_button`/`UndeployedCommit#deploy_state`, rendering the victim stack's deploy button as `allowed`.

### Finding Description
Binding that should hold: `Status.state written for stack S's commit C` must equal `state reported by webhook whose payload.repository.full_name == S.repository.full_name (== C's own stack's repo)`. In `StatusHandler#process` ( [1](#0-0) ) that equality is never checked — `Commit.where(sha: params.sha)` is a global, un-scoped lookup, unlike `Handler#stacks`, which every other handler (`PushHandler`, the `PullRequest::*Handler`s) uses to resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before touching any records: [2](#0-1) , [3](#0-2) .

`create_status_from_github!` then creates a `Status` row unconditionally tied to `commit.stack_id` derived from whichever `Commit` matched, and calls `add_status`, which reloads the commit and re-derives `Commit#status`/`#state` from `statuses_and_check_runs`: [4](#0-3) [5](#0-4) [6](#0-5) .

`WebhooksController#verify_signature` only checks the HMAC signature against `Shipit.github(organization: repository_owner)` where `repository_owner` is taken from the *attacker-controlled* payload's own `repository`/`organization` field: [7](#0-6) [8](#0-7) . This proves the signature is validated against the *sending* repository's own org secret — it says nothing about which `Commit`/stack the event is allowed to mutate. So a genuinely-signed, GitHub-originated `status` event for repository A passes `verify_signature` and `drop_unhandled_event` cleanly, then in `StatusHandler#process` is applied to any commit sharing that `sha`, regardless of repository.

Exploit flow: attacker pushes/controls a repository A (in an org where the Shipit GitHub App is installed, so `status` events are genuinely delivered/signed for A), and picks a `sha` value equal to a commit that exists in victim stack B (feasible e.g. via a fork of a public victim repo, which shares identical git objects/SHAs with upstream, or any other way two tracked repos come to share a commit sha). Attacker sets that commit's status to `success` in repo A (via the GitHub Status API, a legitimate self-service action on their own repo). GitHub delivers a properly-signed `status` webhook naming repository A. `StatusHandler#process` ignores `payload['repository']` and finds `Commit.where(sha: ...)`, which includes stack B's commit; it creates a `Status(state: 'success', stack: B, commit: <B's commit>)`. `commit.reload` in `add_status` invalidates `@status` memoization ( [9](#0-8) ), so `Commit#state`/`#deployable?` now reflect `success` for B's commit. `StacksHelper#deploy_button` reads `commit.deploy_state`, which for `UndeployedCommit` returns `'allowed'` once `deployable?` is true ( [10](#0-9) [11](#0-10) [12](#0-11) ). An operator viewing stack B's dashboard now sees a clickable "allowed" deploy button driven entirely by a status that repository B never reported.

None of the listed guards catch this: `verify_signature` validates the sender org's HMAC, not commit ownership; `drop_unhandled_event` only checks the event type is registered; the `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`/etc., it never requires/validates `repository.full_name` (unlike `PullRequest::ClosedHandler`'s schema, which does: [13](#0-12) ); model validations on `Status`/`Commit` don't constrain cross-stack association.

### Impact Explanation
A webhook genuinely authenticated for repository A results in a `Status` record being written for, and CI state being computed for, a `Commit` belonging to a completely different repository/stack B. This matches the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team." The immediate visible effect is deceptive UI state (`deploy_button` rendered `allowed`) for an operator with genuine access to stack B, and if that operator clicks deploy, `Api::StacksController#create_deploy`/`StacksController#deploy` proceeds based on the forged state — an unauthorized deploy triggered off cross-tenant forged CI data. This is repeatable against any stack that happens to share a commit sha with a repository the attacker can post statuses to (most practically, forks of public victim repos sharing identical git history/shas), and blast radius spans every stack tracked by the same Shipit instance.

### Likelihood Explanation
Requires: (1) the Shipit GitHub App/webhook to be actually delivering `status` events for some repository the attacker controls (push access or ability to set statuses, e.g. a fork under the same installation scope, or any repo in an org where the App is installed org-wide), (2) a shared `sha` between that repository and the victim's tracked commit — trivially true for forks of public repos (identical git objects), which is a common, low-cost real-world setup, not a hash-collision attack. No Shipit secrets, sessions, or team membership are needed. This is fully within the declared unprivileged-attacker capability ("emit webhooks from a repository they own").

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup through the same repository-resolution path used elsewhere: resolve `stacks` (or the target `Repository`) from `payload.dig('repository','full_name')` first, and restrict `Commit.where(sha: params.sha)` to `stack_id: stacks.select(:id)` (or equivalently `commit.stack.repository == resolved_repository`) before calling `create_status_from_github!`. Also add `requires :repository { requires :full_name, String }` to the `StatusHandler` params schema so the repository is a mandatory, validated part of the payload, consistent with other handlers.

### Proof of Concept
Minitest plan (webhook-level, mirrors existing `test/controllers/webhooks_controller_test.rb` structure):
```ruby
test ":status from an unrelated repository must not update a commit belonging to a different stack" do
  victim_commit = shipit_commits(:first)                 # belongs to stack `shipit`, repo shopify/shipit-engine
  attacker_repo_payload = { 'sha' => victim_commit.sha, 'state' => 'success',
                             'repository' => { 'full_name' => 'attacker/unrelated-repo',
                                                'owner' => { 'login' => 'attacker' } } }

  request.headers['X-Github-Event'] = 'status'
  Shipit.stubs(:github).with(organization: 'attacker').returns(stub(verify_webhook_signature: true))

  assert_no_difference 'victim_commit.statuses.count' do
    post :create, body: attacker_repo_payload.to_json, as: :json
  end

  assert_not_equal 'success', victim_commit.reload.state
end
```
Both sides of the binding to assert: `victim_commit.reload.state` (CI state shown to the operator for stack `shipit`) must equal the state genuinely reported only by webhooks whose `payload['repository']['full_name']` matches `victim_commit.stack.repository.full_name` — after posting the attacker's `attacker/unrelated-repo` payload, the state must remain unchanged (`assert_not_equal 'success', ...`) rather than flipping, and `Shipit::StacksHelper#deploy_button`/`UndeployedCommit#deploy_state` for that commit must not render `'allowed'` as a result of this cross-repo payload.
