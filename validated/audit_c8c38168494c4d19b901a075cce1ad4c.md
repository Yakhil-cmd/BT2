### Title
Flash-loan reentrancy guard only covers controller-initiated flash loans; direct `pool.flash_loan` bypasses it and lets the callback commit accrual that the pool's stale cache then drops - (File: contracts/controller/src/strategies/flash_loan.rs)

### Summary
The `FlashLoanOngoing` reentrancy flag lives in the controller's temporary storage and is set only by `storage::with_flash_guard`, which wraps `pool_flash_loan_call` inside `process_flash_position`'s guarded window. When an unprivileged user calls `pool.flash_loan` directly, the controller flag is never set, so every controller entrypoint that checks `require_not_flash_loaning` — most importantly the permissionless `update_indexes` — is fully reachable from the flash receiver callback. The pool's flash settlement commits the market `Cache` it loaded before the callback, overwriting the accrual committed by the nested `update_indexes` call and erasing it. The protection exists on one path (controller-originated flash) but is missing on the symmetric path (direct pool flash) — the same "one address family encrypted, the other plaintext" asymmetry as CVE-2026-34992.

### Finding Description
`process_flash_loan` wraps the pool call in `storage::with_flash_guard(env, ...)`, which sets `SessionKey::FlashLoanOngoing` in controller temporary storage for the duration of the pool call and its receiver callback. `require_not_flash_loaning` in `contracts/controller/src/risk/validation.rs:19-25` asserts `!is_flash_loan_ongoing(env)` and is invoked by `require_authorized_caller` and directly in `process_liquidation` (`positions/liquidation/mod.rs:43-44`), `process_clean_bad_debt` (`mod.rs:196-199`), `process_force_socialize_bad_debt` (`mod.rs:246-248`), and the other state-changing entrypoints (the `tests/test-harness/tests/meta/reentrancy_matrix.rs` test pins `FLASH_LOAN_ONGOING` for supply, borrow, repay, withdraw, liquidate, `update_indexes`, `claim_revenue`, `update_account_threshold`, `clean_bad_debt`, `recapitalize`, `migrate_from_blend`, `multiply`, etc.).

The flag is controller-local. A receiver contract invoked via `pool.flash_loan` directly (bypassing `controller.flash_loan`) runs its callback with `FlashLoanOngoing` unset. The repo's own test documentation confirms the hazard: `tests/test-harness/tests/controller/bad_debt_netting_and_exit_timing.rs:327-331` states that `pool_update_indexes_call` "commits accrual with no flash guard" and that if reached from a flash callback, "pool `flash::apply` would then commit the `Cache` it loaded before the callback and drop that accrual." That path is normally unreachable only because (a) the guard blocks it when the flash loan originates at the controller and (b) Soroban host re-entry blocks re-entering the controller while it is on the call stack — neither holds for a direct pool flash loan, where the controller is not on the stack and the flag was never set.

From the callback the attacker invokes the permissionless `controller.update_indexes` for the flashed market. `update_indexes` commits accrued supply/debt indexes to the pool; the pool's flash apply then writes back the cache snapshotted before payout, discarding the accrual. Borrowers' scaled debt is effectively repriced against the pre-accrual index.

### Impact Explanation
Each dropped accrual erases interest owed by borrowers on the targeted market: debt that was committed to the pool index is rolled back, transferring the corresponding yield away from suppliers. An attacker holding a large open borrow position can run this repeatedly (direct `pool.flash_loan` → callback → `update_indexes`) whenever accrual is pending, systematically suppressing the debt index on their own market and retaining yield that belongs to suppliers — theft of unclaimed yield and direct reduction of protocol debt accounting. Because the receiver only needs to repay principal plus fee, the attack is cost-bounded by the flash fee and repeatable per block/accrual chunk.

### Likelihood Explanation
- Reachability: `pool.flash_loan` is a public pool entrypoint; `update_indexes` is a permissionless controller entrypoint guarded only by `require_not_flash_loaning`, which reads controller storage that a direct pool call never sets.
- Preconditions: a market with outstanding borrows (so accrual is non-trivial) and a receiver contract; both are available to any unprivileged address. Holding a borrow position in the target market amplifies the gain.
- No privileged role, oracle manipulation, or off-chain component is required.

### Recommendation
Bind the flash guard to the pool operation rather than the controller wrapper. Options:
- Have the pool expose (or the controller read) a pool-side "flash in progress" flag set inside `pool_flash_loan_call`/`flash::apply`, and have `require_not_flash_loaning` check that flag, so direct pool flash loans also block `update_indexes` and other monetary entrypoints; or
- Make the pool's flash settlement recompute/commit accrual after the callback instead of blindly writing back the pre-callback `Cache`; or
- Restrict `pool.flash_loan` to the controller (or gate `update_indexes` on pool cash consistency with the pool's expected post-callback balance).

### Proof of Concept
1. Attacker deploys a receiver contract and opens a large borrow in market M via `controller.borrow`, maximizing pending accrual.
2. Attacker calls `pool.flash_loan(hub_asset = M, amount, receiver, data)` directly (not via `controller.flash_loan`). `SessionKey::FlashLoanOngoing` in the controller remains unset because `with_flash_guard` (`contracts/controller/src/storage/account.rs:306-314`) was never entered.
3. In `execute_flash_loan`, the receiver calls `controller.update_indexes` for M. `require_not_flash_loaning` passes; `pool_update_indexes_call` commits accrued indexes into pool storage.
4. The receiver approves `amount + fee` to the pool and returns.
5. The pool's `flash::apply` commits the `Cache` loaded before payout (per `tests/.../bad_debt_netting_and_exit_timing.rs:327-331`), overwriting the committed accrual — the debt-index increase is discarded.
6. Repeat each accrual window; the attacker's scaled debt never reflects the skipped interest, while suppliers' supply index and revenue shares lose the corresponding yield.

Caveat on verification: I confirmed the controller-side guard wiring and the documented stale-cache overwrite in the repo's own test comments, but I could not read `contracts/pool`'s flash apply path within this session to confirm the exact cache-commit ordering and that `pool.flash_loan` is unrestricted. If the pool itself restricts the flash entrypoint to the controller or refreshes accrual at settlement, this analog does not hold.
