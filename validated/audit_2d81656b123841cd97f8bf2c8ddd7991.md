### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name`, allowing cross-organization stack writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, `Shipit.github(organization:)` picks a per-organization `webhook_secret` keyed by an organization name extracted from the payload [1](#0-0) . `WebhooksController#verify_signature` derives that organization name from `repository.owner.login` (falling back to `organization.login`) [4](#0-3) . However, every event handler (`PushHandler`, `StatusHandler` via `Commit.where(sha:)`, `CheckSuiteHandler`, PR handlers, etc.) determines which `Stack`/`Repository`/`Commit` to mutate using `payload.dig('repository', 'full_name')` through `Handler#stacks`/`#repository_name` [2](#0-1) , a completely separate field of the same JSON body that is never cross-checked against `repository.owner.login`.

### Finding Description
The trust binding that should hold is: `organization authenticated` (the org whose `webhook_secret` produced a valid `X-Hub-Signature`) `== organization that owns the repository being written to` (derived from `repository.full_name`). The controller only verifies the *signature* using the org name found in `repository.owner.login`/`organization.login` [5](#0-4) ; it never checks that this same org name is a prefix of, or otherwise matches, `repository.full_name`. Since a legitimate administrator of *any* organization configured in Shipit (`Org A`) knows `Org A`'s own `webhook_secret` (they configured it when wiring up their GitHub App/webhook on both GitHub's side and Shipit's `secrets.github` config), that admin can craft an arbitrary raw JSON body containing:
```json
{
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
sign it with `Org A`'s `webhook_secret`, and POST it to `WebhooksController#create`. `verify_signature` computes `repository_owner = "org-a"`, fetches `Org A`'s `GitHubApp`, and successfully verifies the HMAC [5](#0-4) . `create` then dispatches to `Shipit::Webhooks.for_event(event)` handlers with the same `params` hash [6](#0-5) , and e.g. `PushHandler#process` resolves `stacks` from `repository.full_name = "org-b/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on Org B's stacks — an org that never signed anything [7](#0-6) .

### Impact Explanation
This breaks the authentication boundary between tenants of a shared Shipit instance: an org with a legitimately configured, valid GitHub App integration on the same Shipit host can forge webhook events that mutate another organization's stacks/commits/check-runs — e.g., force `sync_github` on a victim stack, inject fabricated commit statuses via `StatusHandler`, or trigger `RefreshCheckRunsJob` on victim commits via `CheckSuiteHandler`. Depending on `shipit.yml`/continuous-delivery configuration on the victim stack, a forged `push`/`status`/`check_suite` sequence can influence whether continuous delivery considers a commit deployable, constituting an unauthorized-write / cross-repository-write against the victim's stack state.

### Likelihood Explanation
Requires only that the attacker be a legitimate admin of some organization already onboarded to the shared multi-tenant Shipit instance (i.e., they know their own org's `webhook_secret`, which is not privileged relative to the victim org). No access to the victim org's GitHub, secrets, or Shipit account is needed, and the payload fields involved (`repository.owner.login` vs `repository.full_name`) are ordinary, attacker-controlled JSON keys with no cross-validation in the code path.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`/`#stacks`), enforce that the organization used to select the verifying `GitHubApp`/`webhook_secret` matches the owner segment of `repository.full_name` (and of `organization.login` when used as fallback) before dispatching to handlers — reject the request with `422` on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with a distinct `webhook_secret` in `secrets.github` (multi-org schema per `lib/shipit.rb:170-200`).
2. As an admin of `org-a` (who knows `org-a`'s `webhook_secret`), craft:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POST to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")`, verifies successfully [5](#0-4) .
5. `PushHandler#process` runs against `Repository.from_github_repo_name("org-b/victim-repo")`'s stacks, calling `sync_github(expected_head_sha: "deadbeef...")` — a write to `org-b`'s stack authorized only by `org-a`'s credential [7](#0-6) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations

    secrets.github.keys
  end

  end
