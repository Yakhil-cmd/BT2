## Confirmed vulnerability found

### Title
Webhook signature is scoped to the sender's own GitHub organization while the write target (`Repository`/`Stack`/`Team`) is taken unchecked from attacker-controlled payload fields, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `webhook_secret` to HMAC-verify a request against based on `repository_owner`, a value read directly out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The signature therefore only proves "the sender knows the webhook secret configured for organization X" — it says nothing about which repository/stack/team the payload subsequently targets. Every downstream `Webhooks::Handlers` class re-parses the **same untrusted body** and resolves the object to mutate purely from `payload.dig('repository', 'full_name')` (`Handler#stacks`/`#repository_name`) or from `params.team.id` / `params.organization.login` (`MembershipHandler`), with no comparison back to the organization that was actually authenticated.

### Finding Description
The binding the standard verifies is: *organization authenticated by HMAC == organization whose GitHub App produced the event*. In this multi-tenant configuration (`config/secrets.*.yml` supports a `github: { orgA: {...}, orgB: {...} }` map, each with its own `webhook_secret`), the equality that actually matters is:

`organization key used to look up webhook_secret == organization that owns the repository/team being written to`

This equality is never enforced:

- `app/controllers/shipit/webhooks_controller.rb:24-38` picks `Shipit.github(organization: repository_owner)` where `repository_owner` (line 59-62) comes straight from the request body, and verifies the HMAC using that org's secret. [1](#0-0) [2](#0-1) 
- Once signature verification succeeds, `create` re-parses `request.raw_post` and dispatches to handlers with the full, attacker-supplied `params` hash — the same hash that supplied `repository_owner`. [3](#0-2) 
- `Handler#stacks` resolves the target purely by `payload.dig('repository', 'full_name')`, with no check that this repository belongs to the organization whose secret was used to authenticate. [4](#0-3) 
- `PushHandler#process` then triggers a real sync job against any stack matched this way. [5](#0-4) 
- `StatusHandler#process` writes a `Status` on any `Commit` in the whole database matching an attacker-chosen `sha`, again without any organization/repo binding check. [6](#0-5) 
- `MembershipHandler#process` creates/updates a `Team`/`Membership` (which feeds directly into `Shipit.github_teams` authorization, per `current_user.authorized?` in `app/controllers/concerns/shipit/authentication.rb:26-30`) using `params.team.id` / `params.organization.login` taken from the same unchecked body, with no verification that this team belongs to the org that supplied the signature. [7](#0-6) [8](#0-7) 

**Before the attack**: only holders of OrgA's webhook secret can affect OrgA's repositories/teams (the intended, documented model — each GitHub App's webhook secret only signs events for that org's own installation).
**After the attack**: any principal who legitimately knows one configured org's `webhook_secret` (e.g., an administrator of their own small GitHub organization that is also configured on the same shared Shipit instance) can forge a payload whose `repository.owner.login`/`organization.login` is set to their own org (to pick the correct secret for HMAC), while `repository.full_name` (for push/status) or `team.id`/`organization.login` (for membership) point at a completely different, unrelated organization's repository or team tracked by the same Shipit instance.

This is a direct analog of the report's root cause: a value that is used to select/validate the trust boundary (there: L2 `totalSupply()` used as burn amount without accounting for pending cross-domain messages; here: `repository_owner` used to select the signing secret without binding the rest of the payload to that same organization) is disjoint from the value that the subsequent state-changing operation actually uses (there: tokens minted via `receiveMessage()` after migration; here: `repository.full_name`/`team.id` used to select the object mutated).

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" and "cross-repository writes" thresholds explicitly listed as High/Critical impacts:
- Forged `membership` events let an attacker (who only controls their own org's webhook secret) add arbitrary GitHub logins to a `Team` object that `Shipit.github_teams` uses for authorization checks in `force_github_authentication`, potentially granting unauthorized users the "must be a member of ... team" access to the whole Shipit instance.
- Forged `push`/`status` events let the attacker trigger `stack.sync_github` or fabricate commit/CI statuses on stacks belonging to organizations they do not control, which can influence deploy decisions (e.g. spoofed green CI status feeding into deploy gating) — a cross-organization/cross-repository write outside their authorization boundary.

### Likelihood Explanation
High: any environment using the documented multi-organization `github:` config (as shown in `config/secrets.development.shopify.yml` and `docs/setup.md`) with more than one tenant organization is affected. The attacker needs no access to the target organization at all — only a legitimate webhook secret for any one configured org, which they can obtain simply by being an admin of their own (unrelated) org that happens to be configured on the shared instance, then crafting one arbitrary HTTP POST with a correct HMAC over a payload whose `repository`/`team` fields reference the victim org.

### Recommendation
After selecting the signing organization and verifying the HMAC, re-validate that every entity resolved by the handlers (`repository.full_name`'s owner, `team`/`organization.login`) actually belongs to the same organization used for signature verification (`repository_owner`) before performing any write. Concretely, thread the authenticated `repository_owner`/organization into `Handler.call`/`Handler#initialize` and have `Handler#stacks` and `MembershipHandler#find_or_create_team!` reject (or no-op) when the payload's own organization/repository owner does not match the one that produced a valid signature.

### Proof of Concept
1. Configure Shipit for two organizations, `victim-org` and `attacker-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`/`config/secrets.*.yml` multi-org format).
2. Attacker legitimately owns `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "victim-admins", "slug": "victim-admins", "url": "https://github.com/orgs/victim-org/teams/victim-admins" },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-controlled-user" }
}
```
   Note `organization.login` is set to `attacker-org` (so `repository_owner` resolves to attacker's own org, whose secret they know), but `team.id`/`team.url` reference the victim's actual team object already known to Shipit (e.g., discovered via `bin/rake teams:fetch` output or prior legitimate membership events for `victim-org`).
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: membership`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and the signature verifies successfully. [1](#0-0) 
6. `MembershipHandler#process` executes `team.add_member(member)` on the victim's team object (looked up by `params.team.id`, unrelated to `attacker-org`), granting `attacker-controlled-user` membership in a team that gates access via `Shipit.github_teams`. [9](#0-8)
