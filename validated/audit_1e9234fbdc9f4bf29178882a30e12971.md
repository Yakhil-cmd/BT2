## Title
Data-feed value/unit delimiter injection allows spoofing the reporting unit — ([File: data_feeds.js])

## Summary
The CVE describes a class of bug where fixed-delimiter serialization (cookie file lines) is later split back into fields without protecting against the delimiter appearing inside attacker-controlled data, letting one field's content bleed into another and be mis-attributed (a cookie meant for one domain gets accepted for another). Ocore's data-feed storage/retrieval path has the same shape: values are concatenated with the reporting unit hash using a bare `\n` separator and later split back apart by the same character.

## Finding Description
When a `data_feed` message is stabilized, `addDataFeeds()` writes the "latest value" index entry as `value + '\n' + unit` under key `dfv\n<address>\n<feed_name>\n<mci>`: [1](#0-0) 

The same concatenation pattern is used in the KV migration path: [2](#0-1) 

When this entry is later read back (e.g. to answer `data_feed[[...]]` formula lookups by `value=null` / "get the latest value" queries), `readDataFeedByAddress()` blindly splits the stored string on `\n` and treats the first fragment as the feed value and the second as the reporting `unit`: [3](#0-2) 

If the oracle-controlled `value` string itself contains an embedded newline character, `data.value.split('\n')` produces more than two parts. `arrParts[0]` (the value) is then an attacker-chosen truncated string, and `arrParts[1]` — which the code trusts as the authoritative "unit that posted this data feed" — is actually just the next attacker-controlled segment, not the real posting unit. This is structurally the same flaw as CVE-2016-8615: content that should stay confined to one field (the value) leaks across the delimiter into an adjacent, security-relevant field (the unit identifier), because parsing assumes the delimiter cannot appear inside the data it is separating.

`aa_validation.js` shows the project is aware that data-feed values must never contain `\n`, but that check is only enforced for message templates embedded inside an *AA's own definition* (i.e., messages an AA would compose and send itself), not necessarily for arbitrarily crafted `data_feed` messages authored directly by any address and posted to the DAG: [4](#0-3) 

If the equivalent `indexOf('\n')` guard is not applied to a plain, directly-posted `data_feed` message's payload in the general unit-validation path, any address (including an unprivileged oracle-mimicking account) can post a `data_feed` message whose string value contains an embedded newline followed by a forged/target unit hash. Once stable, this corrupts the `dfv\n...` index so that `data_feed[[what='unit']]` (or any code relying on `objResult.unit` from a `value=null` lookup) returns an attacker-chosen unit hash instead of the unit that truly authored the message.

## Impact Explanation
Any AA logic that trusts `data_feed[[...]]` with `what='unit'` to identify "which unit reported this value" (a common pattern for building oracle-authenticity or dispute/proof checks in AAs) can be deceived into believing a forged/arbitrary unit hash is the source of a data feed value. Depending on how the AA uses that unit reference (e.g., feeding it into further validation, cross-referencing it as proof, or releasing funds conditioned on "the reporting unit satisfies X"), this can lead to AA fund loss or incorrect contract execution decisions driven by attacker-supplied unit identifiers rather than genuine oracle attestations.

## Likelihood Explanation
The attack requires only posting a normal `data_feed` message from any address (unprivileged unit poster) with a crafted string value containing a literal newline character, which is trivially representable in valid JSON. The exploitability hinges entirely on whether the general `data_feed` payload validator (in `validation.js`) rejects embedded `\n` the same way `aa_validation.js` does for AA-authored message templates — this specific validator function's contents could not be retrieved within the current investigation due to index limits, so this must be verified directly in the repository before treating this as confirmed-exploitable.

## Recommendation
- Confirm whether `validation.js`'s `data_feed` payload validation (used for real, directly posted units) rejects `\n` in feed names and values, mirroring the check already present in `aa_validation.js`.
- If it does not, add the same `indexOf('\n')` rejection there.
- Regardless, harden the storage/parsing layer defensively: avoid concatenating attacker-controlled `value` with `unit` using a bare `\n` in `main_chain.js`'s `addDataFeeds()` and `migrate_to_kv.js`; instead, length-prefix the value or otherwise make the split unambiguous, and have `readDataFeedByAddress()` in `data_feeds.js` fail safe (or use a fixed suffix length, since `unit` is a known-length base64 hash) rather than trusting `split('\n')[1]`.

## Proof of Concept
1. Craft and post a unit containing a `data_feed` message where `payload = { "feed_name": "<value with an embedded raw newline>\n<forged_unit_hash>" }` (the raw newline appears only after JSON parsing, so `\n` is written as the escape sequence `\\n` in the JSON text, which is valid JSON).
2. Once the unit stabilizes, `main_chain.js`'s `addDataFeeds()` writes `dfv\n<address>\n<feed_name>\n<mci>` → `<value>\n<unit>` where `<value>` already contains a `\n`.
3. Any subsequent `data_feed[[address=..., feed_name=..., what='unit']]` lookup via `readDataFeedByAddress()` in `data_feeds.js` calls `data.value.split('\n')`, and `arrParts[1]` no longer equals the real posting unit but an attacker-controlled fragment resembling `<forged_unit_hash>`.
4. Any AA relying on this "unit" value for authentication/authorization logic can be misled.

Note: this PoC's real-world validity depends on the unresolved question above (whether `validation.js` already blocks `\n` in ordinary `data_feed` payloads); this could not be confirmed with the available tooling and should be checked directly in `validation.js` before treating the finding as fully exploitable.
