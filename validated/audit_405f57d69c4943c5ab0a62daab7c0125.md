### Title
Cross-tenant Team Membership deletion via unscoped `team.id` lookup in forged `membership` webhook - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#process` resolves the `Team` purely by the attacker-supplied `params.team.id` and the `User` purely by `params.member.login`, with no check that the organization which produced/signed the webhook actually owns that team. Combined with `GitHubApp#verify_webhook_signature` returning `true` whenever the resolved organization's `webhook_secret` is blank, and the fact that the "resolved organization" is itself read straight from the attacker's JSON body, an attacker can delete a `Shipit::Membership` row belonging to any team/organization configured in the Shipit instance.

### Finding Description
The intended binding is: *a `Shipit::Membership` row deleted by a `membership`/`removed` webhook == a membership GitHub actually revoked for the team identified in that webhook, sent by the organization that owns that team.*

In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end
``` [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the attacker's own payload (`organization.login` for membership events, since there's no `repository` key). This value both selects which `GitHubApp`/secret is used to verify the HMAC *and* is trusted as "the org this event is about." In `lib/shipit/github_app.rb`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [3](#0-2) 

If the organization named in the payload has no `webhook_secret` configured (documented as "optional" in `docs/setup.md` and defaulted to `nil` in `config/secrets.development.example.yml`/test fixtures), signature verification passes unconditionally for *any* body, no signing capability required at all.

Then in `app/models/shipit/webhooks/handlers/membership_handler.rb`:
```ruby
def process
  team = find_or_create_team!
  member = User.find_or_create_by_login!(params.member.login)
  case params.action
  when 'removed'
    team.members.delete(member)
  ...
end

def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [4](#0-3) 

`Team.find_or_create_by!(github_id: params.team.id)` looks the team up **globally by numeric GitHub team id**, with no scoping to `params.organization.login` (the `organization=` assignment only fires inside the `find_or_create_by!` block, i.e. only on first creation, not on subsequent lookups). So an attacker who can get *any* webhook accepted by `verify_signature` (either by owning/signing for an org configured in the instance, or by targeting an org whose `webhook_secret` is blank) can set `team.id` to a **different** team's GitHub id and `member.login` to a victim's GitHub login, and the handler will delete that victim's `Membership` row for that unrelated team.

Existing guards do not stop this: `ExplicitParameters` (`params do ... end`) only validates types/presence, not ownership; `verify_signature` validates a signature but keys the verification on an attacker-chosen organization value, not on the team being mutated; there is no equivalent of `require_permission!`/`stacks` scoping for webhook-driven `Team`/`Membership` mutation.

### Impact Explanation
A successful forged request deletes a `Shipit::Membership` row for an arbitrary `Team` listed in `Shipit.github_teams` (used for oauth authorization gating, see `Shipit#github_teams` in `lib/shipit.rb`) tied to an arbitrary GitHub login, regardless of which organization actually sent the event. This is a cross-tenant mutation of another organization's team state driven entirely by attacker-controlled `team.id`/`member.login`/`organization.login` fields, matching the "payload for one repository/org mutating another's team" Critical category. Repeated calls can strip any/all currently-authorized users' team memberships used for Shipit access control, denying legitimate operators access without their knowledge. [5](#0-4) 

### Likelihood Explanation
Preconditions: the target Membership must exist, and the attacker must get *some* organization to pass `verify_signature` — either by controlling an org already configured in the multi-org `github:` secrets block, or (more commonly, since `webhook_secret` is explicitly documented as optional) by naming any organization in the payload whose `webhook_secret` is unset, which causes `verify_webhook_signature` to short-circuit to `true` with no signature needed at all. `team.id` (GitHub's numeric team id) and `member.login` are both discoverable/public GitHub information, so the attacker cost is very low, the request is trivially POST-able, and it is fully repeatable against any team/login pair.

### Recommendation
- Do not use an attacker-controlled field (`organization.login`) to select the verification key when the payload does not correspond to a `repository`-scoped event under the resolved organization; explicitly require the webhook's own top-level `organization` claim to match a real, distinct signing context per configured org.
- In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject (or no-op) the event if an existing team's `organization` does not match the payload's `organization.login`.
- Treat a blank `webhook_secret` as "reject all webhooks for this org" rather than "verification not required," or require `webhook_secret` to be mandatory in configuration.

### Proof of Concept
Add a minitest in `test/controllers/webhooks_controller_test.rb` (repo already has a fixture `Team` bound to organization `shopify`, e.g. `shipit_teams(:shopify_developers)`, and `Membership` rows via `shipit_memberships`):
```ruby
test ":membership from an unrelated/no-secret organization can delete a victim org's membership" do
  victim_team = shipit_teams(:shopify_developers)
  victim_login = shipit_users(:walrus).login # an existing authorized member of victim_team

  @request.headers['X-Github-Event'] = 'membership'
  assert_difference -> { Membership.where(team: victim_team, user: shipit_users(:walrus)).count }, -1 do
    post :create, body: {
      action: 'removed',
      team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
      organization: { login: 'attacker-org-with-no-webhook-secret' },
      member: { login: victim_login },
      repository: { owner: { login: 'attacker-org-with-no-webhook-secret' } }
    }.to_json, as: :json
    assert_response :ok
  end
end
```
Assert both sides of the binding: before the request, `Membership.exists?(team: victim_team, user: victim_user)` is `true` and `victim_team.organization == 'shopify'` while the forged payload's `organization.login == 'attacker-org-with-no-webhook-secret'`; after the request, the membership no longer exists, proving deletion occurred despite the mismatched/uncontrolled organization identity.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
