### Title
Response fields rendered via `gh api --template` bypass `CopyGuardedContent`'s terminal escape-sequence guard - (File: pkg/cmd/api/api.go)

### Summary
`processResponse` in `pkg/cmd/api/api.go` routes any response through `template.Execute` whenever `--template` is set, entirely skipping the `CopyGuardedContent`/`ErrEscapeSequence` guard that is applied to the raw-body branch. Since `-f field=@path` (`magicFieldValue`) reads arbitrary local file bytes verbatim and sends them as a request field, an attacker-controlled file inside a cloned repo can end up in a response field that is echoed unsanitized to the terminal via `{{.field}}`.

### Finding Description
`magicFieldValue` reads the referenced file byte-for-byte with `opts.IO.ReadUserFile` and returns it as a string with no sanitization: [1](#0-0) . That string is placed into the request `params` map by `parseFields` and later serialized into the outgoing request body in `apiRun`.

In `processResponse`, when `opts.Template != ""`, the response body is executed against the user-supplied template directly, with none of the escape-sequence/binary guarding applied to the raw-output branch below it: [2](#0-1)  compared to the guarded raw branch which explicitly calls `iostreams.CopyGuardedContent` and checks for `iostreams.ErrEscapeSequence`/`BinaryTerminalError`: [3](#0-2) . The comment at line 530 ("A raw non-JSON body is the only response the transport does not sanitize") documents the intended invariant that only the raw branch needs escape-guarding — but this is incorrect, since the template branch (line 515-519) writes to `bodyWriter` (ultimately `opts.IO.Out`) without ever calling `CopyGuardedContent` or checking `ContainsEscapeSequence`, regardless of whether the templated data originated from JSON fields containing attacker-controlled bytes.

`CopyGuardedContent` itself is the only place in the codebase implementing the escape-sequence check (`ContainsEscapeSequence`) for this code path: [4](#0-3) . The existing test `Test_processResponse_template` confirms the template path writes whatever field values are present straight to stdout, with no escaping logic exercised: [5](#0-4) .

Exploit flow: victim clones/checks out an attacker-authored repo containing a file with ANSI escape sequences (e.g., cursor movement, screen-clear, or OSC sequences for terminal title/clipboard manipulation). Victim runs `gh api -f body=@./attacker-file.txt --template '{{.body}}' ...` (or any command with `-F/-f @file` + `--template` referencing that field, e.g. `gh api graphql -f query=@- ...` variants, or workflow `run` command which reuses the same unguarded `magicFieldValue` pattern [6](#0-5) ). If the API host reflects the field back in its JSON response (common for create/update endpoints returning the submitted resource, e.g. issue/comment body), the raw bytes — including ESC (0x1B) sequences — reach the victim's terminal unsanitized through `tmpl.Execute`/`tmpl.Flush()` → `opts.IO.Out`.

### Impact Explanation
This allows terminal escape sequence injection on the victim's TTY (e.g., terminal title spoofing, screen manipulation, potential OSC-52 clipboard writes, or in vulnerable terminal emulators more severe effects), matching the "terminal escape sequence execution/prompt spoofing" impact class. It does not grant direct code execution but can be leveraged for spoofing/social engineering against the victim's terminal session.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs to publish a repo/file with escape sequences and have the victim run an ordinary `gh api` (or `gh workflow run`) invocation combining `-f field=@path` with `--template`, against an endpoint that reflects the field value back in its JSON response. This requires the victim to explicitly opt into `--template` output, which narrows real-world likelihood somewhat, but no other special conditions (elevated privileges, MITM, social engineering beyond normal repo interaction) are required.

### Recommendation
Apply the same escape-sequence/binary guard used in the raw-output branch to the `--template` output path — e.g., wrap `bodyWriter` passed to `template.New` (or the final `tmpl.Flush()` target) with the same sanitization used for `ContentOut`/`CopyGuardedContent`, or scan template output for `ContainsEscapeSequence` before flushing to a TTY, honoring the existing `--allow-escape-sequences` opt-out flag consistently across both branches.

```go
// CopyGuardedContent writes external content from r to w under the safety model
// used by byte-moving commands: binary content is refused when w targets a
// terminal and streamed verbatim otherwise, while textual content is refused when
// it carries terminal escape sequences. Binary content streams without buffering;
// only textual content is buffered, so its escapes are caught before any byte is
// written. On refusal the output stream is left untouched; otherwise it receives
// the full content. isTTY reports whether w targets the user's terminal.
//
// It returns [BinaryTerminalError] or [ErrEscapeSequence] so callers can add
// command-specific guidance. Callers that must stream verbatim (an explicit
// opt-out, or output bound for a file) should copy directly instead.
func CopyGuardedContent(w io.Writer, r io.Reader, isTTY bool) error {
	head := make([]byte, contentSniffLen)
	n, err := io.ReadFull(r, head)
	if err != nil && !errors.Is(err, io.EOF) && !errors.Is(err, io.ErrUnexpectedEOF) {
		return err
	}
	head = head[:n]

	if mime, ok := BinaryContentType(head); ok {
		if isTTY {
			return BinaryTerminalError{MIME: mime}
		}
		if _, err := w.Write(head); err != nil {
			return err
		}
		_, err := io.Copy(w, r)
		return err
	}

	rest, err := io.ReadAll(r)
	if err != nil {
		return err
	}
	content := append(head, rest...)
	if ContainsEscapeSequence(content) {
		return ErrEscapeSequence
	}
	_, err = w.Write(content)
	return err
}
```
