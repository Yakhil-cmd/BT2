### Title
Cross-organization webhook forgery: signature is verified against the org named inside the unsigned-selection field, not the org that actually owns the acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* `webhook_secret` to HMAC-verify against by reading `repository_owner` straight out of the untrusted, attacker-supplied JSON body, before any authentication has happened. Every downstream `Handler` then independently re-reads the target repository from that same body via `payload.dig('repository', 'full_name')`. Nothing ties "the org whose secret validated the signature" to "the repository whose stacks get mutated." In a multi-organization Shipit deployment (the `github: { org1: {...}, org2: {...} }` credentials schema), anyone who legitimately controls one configured organization's GitHub App/webhook secret can forge a signed payload whose `repository.owner.login` matches their own org (so it passes signature verification with the secret they know) while `repository.full_name` names a repository belonging to a completely different, victim organization also configured on the same Shipit instance.

### Finding Description
- Signature verification selects the app/secret from body content: `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- `Shipit.github` resolves per-organization config/secret from `secrets.github`, supporting multiple orgs each with their own `webhook_secret`. [3](#0-2) 
- `verify_webhook_signature` only checks that the HMAC-SHA1 over the raw body matches using the secret resolved above — it says nothing about which repository the body actually targets. [4](#0-3) 
- After verification, every `Handler` re-derives the actual target purely from the same unsigned/attacker-controlled body field `repository.full_name`, independent of which org's secret was used to authenticate: [5](#0-4) 
- `PushHandler`, for example, uses `stacks` (resolved via that `repository_name`) to enqueue `GithubSyncJob` per matching stack, which fetches commits and mutates stack state: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization whose secret validated the signature == organization owning the repository that gets mutated`. Because both values are read from the same attacker-controlled JSON body with no cross-check, an attacker who knows OrgA's `webhook_secret` (e.g., because they administer OrgA's GitHub App on the same shared Shipit instance) can set `repository.owner.login: "OrgA"` (so `verify_signature` succeeds against OrgA's known secret) and `repository.full_name: "OrgB/victim-repo"` in the same payload. The signature computed over the whole raw body with OrgA's secret is valid Because the attacker controls the entire body they sign, so it passes `verify_signature`, yet the `Handler` acts on OrgB's stacks.

### Impact Explanation
This breaks the trust boundary between authentication (which org's secret is honored) and the object being written (which org/repo's stacks are mutated) on a multi-tenant Shipit install — the exact class of binding the engine's threat model calls out ("an organization that authenticated versus the repository that is written"). Depending on which webhook event/handler is targeted, this enables cross-organization/cross-repository state injection: forging `push` events to trigger `GithubSyncJob` and fabricate commits for another org's stack, forging `status`/`check_suite`/`commit_status` events to fake CI state and unblock deploys, or forging `pull_request`/`merge_status` events to manipulate another tenant's review-stack/merge pipeline — all without ever needing credentials for the victim organization. This is a cross-repository write achieved purely by knowing one (unrelated) tenant's webhook secret, satisfying the Critical "cross-repository writes" / unauthorized-deploy impact bar.

### Likelihood Explanation
Requires: (1) Shipit configured in multi-organization mode (`secrets.github` keyed by multiple org names, a documented supported schema in `lib/shipit.rb#github_app_config`), and (2) the attacker legitimately knows the `webhook_secret` for at least one of the configured organizations (e.g., they are an admin of that org's GitHub App, which does not require any privilege in Shipit itself or in the victim organization). No Shipit session, `ApiClient` token, or GitHub repository-write access to the victim org is needed — only crafting a raw HTTP POST to `/webhooks` with a body they sign themselves.

### Recommendation
Bind the resolved repository to the verified organization: after determining the org used for signature verification, require that `payload.dig('repository', 'full_name')` (and `payload.dig('organization','login')`) actually belongs to that same organization before any handler executes, e.g. reject the webhook if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`. Alternatively, derive the verification organization strictly from a value that cannot diverge from the value used for repository resolution (compute both from the identical, single field) rather than from two independently-read/fallback-prone paths.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per the multi-org schema in `lib/shipit.rb`).
2. Attacker is only an admin of `OrgA`'s GitHub App and knows `OrgA`'s `webhook_secret`; they have no access to `OrgB`.
3. Attacker crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
   }
   ```
   (`repository.owner.login` set to `OrgA` so `repository_owner` in `webhooks_controller.rb` resolves to `OrgA`'s secret; `repository.full_name` set to the victim's repo for handler resolution.)
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully since the attacker used OrgA's real secret over the exact bytes sent. [1](#0-0) 
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for `OrgB`'s stack, mutating OrgB's commit history/state despite the attacker having no credentials for `OrgB`. [5](#0-4) [6](#0-5)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
