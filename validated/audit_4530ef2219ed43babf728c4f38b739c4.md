### Title
Session Fixation on GitHub OAuth Callback Allows Account Takeover - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds the authenticated GitHub identity to the current session by writing `session[:user_id]` without first invalidating/regenerating the pre-existing session. An attacker can fixate a known session identifier on a victim's browser and then have the victim complete the GitHub OAuth flow, after which the attacker can reuse the same session identifier to be treated as the victim's `User`.

### Finding Description
The callback action is the single point where a verified GitHub identity (`request.env['omniauth.auth']`) is bound to the Rails session: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

No `reset_session` call precedes the assignment of `session[:user_id]`. This is the equality the deployment-trust model expects to hold: `session_id before login == session_id after login` should never leak an attacker-controlled identifier into a post-authentication session. Because the same session id/cookie that existed pre-authentication is reused, an attacker who can pre-set a known session identifier on a victim's browser (session fixation — e.g. via a subdomain that shares the cookie domain, response header injection, or any mechanism that lets the attacker write a session cookie before the victim logs in) can log the victim in under a session ID the attacker also knows, and then use that same session ID to authenticate as the victim's `User` after the victim completes the GitHub OAuth handshake.

For contrast, `logout` correctly calls `reset_session`: [2](#0-1) 

The rest of the authentication layer trusts `session[:user_id]` unconditionally to resolve `current_user`: [3](#0-2) 

### Impact Explanation
This breaks the "GitHub identity versus the `User` bound to the session" binding explicitly called out as in-scope: an attacker who forces a victim to complete the GitHub App's OAuth authorization (which is not privileged and requires no Shipit credentials) can subsequently hijack the victim's authenticated Shipit session, gaining access as that user — including whatever `Shipit.github_teams` authorization, deploy/rollback/merge, and stack-lock privileges the victim's account holds. This matches the "session fixation / forced OAuth completion" High-severity category defined in scope.

### Likelihood Explanation
Exploitability depends on the attacker being able to fix a known session identifier in the victim's browser before the victim authenticates. Whether this is practically achievable depends on details outside the engine's own code (the host app's session store configuration, e.g. whether it uses `ActionDispatch::Session::CookieStore` with `secret_key_base` signing/rotation semantics, or a server-side store such as `redis-session-store`, and whether `config.session_store` sets cookie flags such as `HttpOnly`/`SameSite`). The engine itself does not enforce session ID rotation on login, so the exposure exists regardless of host configuration; only the ease of fixating the session ID varies with the deployment's session store choice, which is standard Rails app configuration and thus outside this engine's own code. I was not able to inspect the host application's `config/initializers/session_store.rb` (only the test dummy app's is indexed) to confirm which store is used in a real deployment, so I cannot state with certainty how easily an attacker fixates the ID in a specific deployment — but the missing `reset_session` in the engine's own controller is the root cause regardless of session-store choice.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` before writing `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `#logout`, so that a fresh session identifier is issued upon every successful authentication.

### Proof of Concept
1. Attacker obtains/sets a session cookie value `S` in the victim's browser (session fixation vector, e.g., cookie-tossing via a shared parent domain or an XSS/response-splitting bug elsewhere in the deployment).
2. Attacker lures the victim to `GET /github/auth/github` while their browser still carries session cookie `S`.
3. Victim completes the GitHub OAuth consent screen; `GithubAuthenticationController#callback` fires and executes `session[:user_id] = sign_in_github(auth)` using session `S`, without rotating the session ID: [4](#0-3) 
4. Attacker, who already knows session `S`, sends requests using cookie `S` and is now recognized as the victim by `current_user`: [3](#0-2)
