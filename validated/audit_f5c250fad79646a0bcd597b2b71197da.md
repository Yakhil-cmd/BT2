## Analysis

The Discourse bug class is: an access-revocation mechanism (removing a user from a private message) is not consistently enforced across all code paths, so the "revoked" actor can still use another surface (invites) to keep or regain access.

The `ocore` correspondent-device model has an equivalent structural gap around `is_blackhole`, the flag used to represent a **revoked** correspondent when full deletion isn't possible.

### Root cause

When a peer sends `removed_paired_device` (asking to be unpaired) but is *not removable* (e.g. it is still a signer/cosigner referenced by `shared_address_signing_paths`, `wallet_signing_paths`, `prosaic_contracts`, etc., per `readNonRemovableDevices`), and `conf.bIgnoreUnpairRequests` is set, the node does not delete the correspondent — it only sets a revocation flag: [1](#0-0) 

```js
determineIfDeviceCanBeRemoved(from_address, function(bRemovable){
    if (!bRemovable)
        return callbacks.ifError("device "+from_address+" is not removable");
    if (conf.bIgnoreUnpairRequests){
        db.query("UPDATE correspondent_devices SET is_blackhole=1 WHERE device_address=?", [from_address]);
        return callbacks.ifOk();
    }
    ...
```

`is_blackhole` is meant to cut off the device: it is checked and enforced on the **outbound** path, [2](#0-1) 

```js

	...
	conn.query("SELECT hub, pubkey, is_blackhole FROM correspondent_devices WHERE device_address=?", [device_address], function(rows){
		if (rows.length !== 1 && !conf.bIgnoreMissingCorrespondents)
			throw Error("correspondent not found");
		if (rows.length === 0 && conf.bIgnoreMissingCorrespondents || rows[0].is_blackhole){
			console.log(... "not sending to " + device_address + " which is set as blackhole");
			...
```

But it is **never checked** on the **inbound** path that processes messages received through the hub: [3](#0-2) 

```js
db.query("SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?", [from_address], function(rows){
    if (rows.length > 0){
        if (json.device_hub ... ) ...
        else
            handleMessage(rows[0].is_indirect);
    }
    else{ // correspondent not known
        var arrSubjectsAllowedFromNoncorrespondents = ["pairing", "my_xpubkey", "wallet_fully_approved"];
        ...
    }
});
```

The query only selects `hub, is_indirect` and only checks `rows.length > 0` — `is_blackhole` is not fetched or examined, so a blackholed (locally "revoked") device is still treated as a fully-trusted correspondent for every inbound subject (`new_shared_address`, `signature`, `private_payment` forwarding via `handlePrivatePaymentChains`, `create_new_shared_address`, etc.), all of which are dispatched from `handleMessageFromHub`: [4](#0-3) 

### Impact

A device that the wallet believed it had revoked (because it is non-removable due to sitting on a live multisig/shared-address, exactly like a PM the attacker was previously in) can:
- keep sending `new_shared_address` messages, i.e. "invite" itself or other devices into new shared/multisig addresses tied to member addresses the local user controls, via `handleNewSharedAddress` / `addNewSharedAddress` / `forwardNewSharedAddressToCosignersOfMyMemberAddresses`: [5](#0-4) 
- keep forwarding/injecting `private_payment` chains that get validated and stored via `handlePrivatePaymentChains`: [6](#0-5) 
- keep participating in signing coordination for shared addresses.

This mirrors the reported bug class exactly: "access" (here, trusted-correspondent status enabling shared-address and private-payment coordination) that the user tried to revoke is still exercisable through a parallel path (inbound hub messages) that never re-checks the revocation flag — effectively the same "PM access granted/retained after access revocation" pattern, but manifesting as continued private shared-address/private-payment participation rather than PM visibility.

### Likelihood

Requires `conf.bIgnoreUnpairRequests = true` (an opt-in operator setting) and the peer being non-removable due to an existing shared-address/wallet relationship — a realistic configuration for wallets that don't want multisig coordination to break on naive unpair, but the missing inbound check silently defeats the intended isolation.

### Recommendation

Include `is_blackhole` in the correspondent lookup inside the `hub/message` handler in `device.js` and reject/ignore messages (except perhaps re-pairing) from blackholed device addresses, mirroring the check already present in `sendMessageToDevice`. [3](#0-2) 

Given the ambiguity of this being a genuine exploitable analog versus a defense-in-depth gap in an opt-in feature (`bIgnoreUnpairRequests`), treat this as the best available match; I found no other unprivileged-reachable analog in the checked areas (private payment chains, shared-address definitions, AA triggers, asset issuance) that maps as closely to "access granted/retained through an invite-like mechanism after revocation."

function sendMessageToDevice(device_address, subject, body, callbacks, conn){
	if (!device_address)
		throw Error("empty device address");
	conn = conn || db;
	conn.query("SELECT hub, pubkey, is_blackhole FROM correspondent_devices WHERE device_address=?", [device_address], function(rows){
		if (rows.length !== 1 && !conf.bIgnoreMissingCorrespondents)
			throw Error("correspondent not found");
		if (rows.length === 0 && conf.bIgnoreMissingCorrespondents || rows[0].is_blackhole){
			console.log(rows.length === 0 ? "ignoring missing correspondent " + device_address : "not sending to " + device_address + " which is set as blackhole");
			if (callbacks && callbacks.onSaved)
				callbacks.onSaved();
			if (callbacks && callbacks.ifOk)
				callbacks.ifOk();
			return;
		}
		sendMessageToHub(rows[0].hub, rows[0].pubkey, subject, body, callbacks, conn);
