## Analysis

The SAML plugin bug class is: **an authenticated request lacking a replay cache**, allowing anyone who observes the wire traffic (no credentials required) to resubmit a previously valid authentication artifact and re-trigger its effect. Searching polkadot-sdk for genuine, non-nonce-based signature/proof authorization paths (the closest analog to a SAML assertion), the strongest candidate is `pallet-people`'s `AsPerson` transaction extension, which authorizes `RawOrigin::None` (i.e., completely unsigned/unauthenticated-origin) extrinsics purely from a cryptographic proof/signature embedded in the extension, with only a partial, admittedly incomplete replay-protection scheme — as opposed to `frame_system::CheckNonce`, `pallet_meta_tx`, `pallet_verify_signature`, and the `permit` precompile, which all implement full nonce-based replay caches and are demonstrably safe.

### Title
Incomplete replay protection in `pallet-people`'s `AsPerson` transaction extension allows unauthenticated replay of `set_personal_id_account`/`set_alias_account` to oscillate account bindings - ([File: substrate/frame/people/src/extension.rs])

### Summary
The `AsPersonalIdentityWithProof` and `AsPersonalAliasWithProof` variants of `AsPersonInfo` authorize dispatch of `set_personal_id_account`/`set_alias_account` from origin `None` purely by verifying a signature/proof over the call and a `call_valid_at` block number, gated by an `account_setup_time_tolerance()` window [1](#0-0) . Replay protection is implemented only as "does the target account already match the record", not as a consumed-once/nonce-based cache, and the pallet's own doc comments admit that two overlapping-validity captured extrinsics targeting two different accounts "can be replayed indefinitely for the duration of the overlapping period" [2](#0-1) .

### Finding Description
`AsPerson::validate` accepts a `None` origin, meaning **anyone** (no signing key, no privileged role) can submit the raw extrinsic bytes to the pool, as long as the embedded proof/signature was valid for the encoded `(EXTENSION_VERSION, call, other_tx_ext)` payload [3](#0-2) . The only anti-replay check is:
```
if People::<T>::get(index).is_some_and(|record| record.account.is_some_and(|stored_account| stored_account == *account)) {
    return Err(InvalidTransaction::Stale.into());
}
``` [4](#0-3) 

This check only rejects re-submission of a transaction that would produce a *no-op* (setting the account to the value it's already at). It does **not** implement a true replay cache (e.g., consuming a nonce or tracking used signatures/message IDs), so any previously broadcast valid transaction remains replayable by any observer as long as `call_valid_at + tolerance` has not elapsed and the current bound account differs from the call's target account. The identical structural gap exists in `AsPersonalAliasWithProof` [5](#0-4) .

The pallet's own `replay_protection_for_identity` test confirms the exact "SAML-style" replay: transaction 1 (account=10, valid at block N) and transaction 2 (account=11, valid at block N+1) can each be independently replayed once inside the overlapping tolerance window, flipping `AccountToPersonalId` back and forth between 10 and 11, without any new signature [6](#0-5) .

### Impact Explanation
An unprivileged attacker who merely observes two overlapping-validity `set_personal_id_account`/`set_alias_account` extrinsics on-chain (public block data — no interception of secrets, no privileged role) can indefinitely replay them to override which account is currently bound as a person's `PersonalId`/alias account, for as long as the overlapping tolerance window persists. This is an unauthorized-dispatch/integrity break of the personhood-identity binding invariant that the pallet is designed to protect (only the true key-holder should control which account represents their personhood), analogous to the SAML replay allowing an attacker to "authenticate as that user" repeatedly without new credentials.

### Likelihood Explanation
Requires the victim (or their wallet infra) to have broadcast two account-setup transactions whose `call_valid_at` + `account_setup_time_tolerance()` windows overlap — a realistic but non-default condition (e.g., a user changing their mind about which account to bind, or key rotation flows). No attacker privilege, governance control, or stolen key is needed; the attacker only needs to observe and resubmit public transaction bytes. This is a self-acknowledged limitation in the pallet's own doc comments [7](#0-6) , indicating the maintainers are aware of it as a known/accepted tradeoff rather than an accidental defect — this substantially reduces bounty eligibility even though the code path is real and demonstrable.

### Recommendation
Replace the "does the target already match" check with a true replay cache: either bind the proof to a per-index/per-account monotonically increasing nonce or a consumed-signature set (similar to `permit::Pallet::use_permit`'s nonce-consumption pattern [8](#0-7) ), so a given signed proof can be used exactly once regardless of how the current stored state compares to its target value.

### Proof of Concept
The existing unit test `replay_protection_for_identity` in `substrate/frame/people/src/tests.rs` (lines 2833-2904) is a working, already-merged reproduction of this exact behavior: it constructs two `AsPersonalIdentityWithProof` extrinsics with overlapping validity windows and demonstrates that both remain independently replayable ("Somebody replays the transaction 1, it must succeed. It is within time tolerance.") inside the overlap, with no additional signing step required from the attacker [9](#0-8) . No PoC execution was performed beyond confirming this test exists and asserts the described oscillation; the finding is reported as a documented/self-acknowledged Low/Medium-severity gap rather than a novel Critical/High vulnerability, per the instruction to preserve rather than inflate or discard accepted findings.
