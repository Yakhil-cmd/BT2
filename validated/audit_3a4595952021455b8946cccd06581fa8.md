### Title
`MembershipHandler#process` binds team membership by `github_id` alone, letting a webhook from one organization mutate a `Team` belonging to a different organization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
Webhook signature verification in `Shipit::WebhooksController#verify_signature` is scoped per-organization (it looks up the webhook secret via `Shipit.github(organization: repository_owner)`), but `MembershipHandler#find_or_create_team!` resolves the target `Team` by `github_id` only, with no check that the payload's `organization.login` matches the found team's `organization`. An attacker who legitimately controls webhooks for their own registered organization can send a `membership` event whose `team.id` collides with the `github_id` of a `Team` row that belongs to a completely different, unrelated organization also listed in `Shipit.github_teams`, causing `team.add_member(member)` to add the attacker as a member of that other org's authorized team.

### Finding Description
The broken binding is the implicit equality the code assumes but never checks:
`params.organization.login == team.organization` for the `Team` row matched by `Team.find_or_create_by!(github_id: params.team.id)`.

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from the payload (`params.dig('organization', 'login')` for membership events) and fetches `Shipit.github(organization: repository_owner)` to get that organization's `webhook_secret`, then HMAC-verifies the signature [1](#0-0) . This only proves the request came from GitHub for the organization named in the payload's `organization.login` field — it says nothing about `team.id`.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [2](#0-1) . `github_id` is looked up globally across all `Team` rows regardless of organization; if a `Team` with that `github_id` already exists (e.g., created earlier for `shopify/developers`), the `find_or_create_by!` block (which would reassign `organization`) never runs, and the pre-existing team from the *other* organization is returned unmodified in its `organization` field but is the object operated on next.
3. `team.add_member(member)` appends the attacker's `User` (created via `User.find_or_create_by_login!(params.member.login)`) to that team's `members` [3](#0-2) .
4. `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [4](#0-3) , matching by local `Team.id`, not `github_id`/organization — so membership in the mismatched team row is sufficient for global authorization.

Attacker's exact request: attacker owns webhooks for their own org (e.g. `cyclimse/cooks`), which is registered in Shipit with its own real `webhook_secret`, so they can sign a valid `membership` webhook themselves. They set `organization.login: "cyclimse"` (matches their real org, so signature check passes), `action: "added"`, `team.id: <github_id of an existing Team row for shopify/developers already in Shipit.github_teams>`, and `member.login: <attacker's own login>`. Because signature verification only validates the org named in the payload, not the correspondence between `team.id` and that org, the request passes verification while still granting membership in a team the attacker's real organization has no relationship to.

Existing guards that fail to prevent this:
- `verify_signature` validates only that the payload's *organization* is legitimate, not that `team.id` belongs to that organization [1](#0-0) .
- `find_or_create_team!` has no `where(organization: params.organization.login)` scoping and no verification that a matched existing row's `organization` equals the payload's `organization.login` [2](#0-1) .
- `Team#add_member` performs no authorization or organization check either [3](#0-2) .

### Impact Explanation
A successful exploit lets an attacker who controls a webhook integration for any organization known to Shipit self-grant membership in an arbitrary pre-existing `Team` row (identified by guessing/observing its `github_id`, which are small sequential GitHub-assigned integers and thus guessable/brute-forceable across organizations), as long as that `github_id` is already present in the `teams` table. Since `User#authorized?` trusts local `Team.id` membership via `Shipit.github_teams`, this is a direct authorization bypass into any Shipit-protected action gated by team membership (deploys, rollbacks, stack settings, etc.) for repositories/orgs the attacker has no legitimate relationship with. This matches the "High: escalation into `Shipit.github_teams` authorization" category, and depending on downstream actions gated on authorization it can enable actions closer to Critical (unauthorized deploy/rollback approval). It is repeatable per request and not limited to a single tenant — any organization with a registered webhook integration in Shipit can be abused this way against any other organization's teams whose `github_id` happens to be known or guessed.

### Likelihood Explanation
Preconditions required: `Shipit.github_teams` must list multiple `Team` rows across different organizations, and the target `Team` row's `github_id` must already exist in the `teams` table (e.g. from a prior legitimate sync). The attacker needs control of a webhook-integrated organization in Shipit (which the threat model in the question grants — "a repository/organization the attacker genuinely controls webhooks for"). `github_id` values are not secret and are discoverable via GitHub's public team APIs or by observing Shipit's team-sync rake tasks/UI, making the attack feasible with modest reconnaissance. This is repeatable at will since it only requires POSTing a self-signed webhook.

### Recommendation
Scope the team lookup in `MembershipHandler#find_or_create_team!` to the payload's organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally verify that any existing matched `Team` row's `organization` equals `params.organization.login` before calling `add_member`/`delete` — raising/dropping the event otherwise. Consider adding a uniqueness validation on `github_id` scoped by `organization`, and asserting the `repository_owner`/`organization.login` derived for signature verification matches the org attached to the resolved `Team` before mutating membership.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/membership_handler_test.rb`, not included in the audited scope but describing the required proof):
1. Create `team_a = Team.create!(github_id: 555, organization: 'shopify', slug: 'developers')` and add it to `Shipit.github_teams` (stub `Shipit.github_teams` to include `team_a`).
2. Create a second organization context `cyclimse` with its own valid webhook secret configured in `Shipit.github(organization: 'cyclimse')`.
3. Build a `membership` webhook payload with `organization.login: 'cyclimse'`, `team.id: 555` (colliding with `team_a.github_id`), `action: 'added'`, `member.login: 'attacker'`, signed with `cyclimse`'s webhook secret.
4. POST to `/webhooks` with `X-Github-Event: membership` and the correct `X-Hub-Signature` for `cyclimse`.
5. Assert the response is `200 OK` (signature check passes).
6. Assert `Membership.count` incremented and `team_a.members.reload.map(&:login)` includes `'attacker'` — i.e. `team_a.organization == 'shopify'` while the request was authenticated for `organization.login == 'cyclimse'` (`'shopify' != 'cyclimse'` yet the membership write still succeeded on `team_a`).
7. Assert `User.find_by(login: 'attacker').authorized?` is `true`, proving escalation into `Shipit.github_teams` authorization purely via a self-signed webhook from an unrelated organization.
