## Title
Unhandled `throw Error("more than 1 address definition")` on crafted unit with duplicate co-author addresses causes node process crash — analogous to CVE-2016-8883's assertion-failure DoS ([File: definition.js])

## Summary
CVE-2016-8883 describes an assertion failure (`abort()`/process crash) in JasPer's `jpc_dec_tiledecode` triggered by a crafted file that violates an internal invariant the decoder assumed could never be false. `ocore`'s address-definition evaluator contains the same anti-pattern: an internal invariant ("a unit can only carry one definition per co-author address") is enforced with a bare `throw Error(...)` deep inside an asynchronous DB-query callback, rather than being routed through the validation callback chain. Because the invariant is checked against attacker-controlled unit content (`objUnit.authors`), a hand-crafted unit that violates it triggers an unhandled/synchronous throw that is not caught by `validate()`'s error-handling paths, crashing the full node process — a network-reachable, single-unit DoS.

## Finding Description
`definition.js` evaluates address-reference operators (`'address'`) both while validating a definition (`validateDefinition`) and while validating authentifiers/signatures (`validateAuthentifiers`). In both places, when the referenced address's stored definition cannot be found (`ifDefinitionNotFound`), the code falls back to looking for a definition supplied inline by a co-author of the same unit: [1](#0-0) [2](#0-1) 

In both spots, if more than one author in the same unit matches the target address and hashes to the referenced `definition_chash`, the code does:
```
if (arrDefiningAuthors.length > 1)
    throw Error("more than 1 address definition");
```
This is a synchronous `throw` executed inside a `conn.query`/`storage.readDefinitionByAddress` callback (asynchronous context), so it cannot be caught by the `try/catch` blocks that wrap the synchronous parts of `validate()` in `validation.js`. An uncaught exception thrown from inside an async callback in Node.js propagates to the top of the event loop and (absent a global `uncaughtException` handler that keeps running safely) terminates the process — the direct analog of an assertion failure crashing a decoder in JasPer.

Root-cause condition: `objUnit.authors` is only checked for `isValidAddress()` per author before author validation begins: [3](#0-2) 
There is no check here (or found elsewhere in the reviewed validation flow) that rejects a unit whose `authors` array contains two entries with the *same* `address`. That means an attacker can post a unit with two co-authors sharing the same address, each supplying an inline `definition` that, when chash-hashed, equals the `definition_chash` referenced by some address-referencing spending condition (`['address', other_address]`) evaluated during signature/definition validation of that same unit (or of another address whose definition references it via `'address'`/`'definition template'`). This satisfies `arrDefiningAuthors.length > 1`, hitting the unguarded `throw`.

## Impact Explanation
An uncaught exception thrown inside a DB-callback during unit validation is not a normal "unit rejected" outcome funneled through `ifUnitError`/`ifJointError`/`ifTransientError`; it crashes the Node.js process running the full node. Any node (hub or full node) that receives and attempts to validate the crafted unit goes down, matching the "network unable to confirm new units" impact bucket (validating nodes crash, halting processing of that peer's unit stream and potentially requiring restarts network-wide if the unit propagates). This is reachable by any ordinary unit poster — no special privileges, hub cooperation, or nested private-payment/AA trigger flow are required, only a specially crafted `authors` array.

## Likelihood Explanation
Likelihood is limited by the specific structural conditions required: (1) two authors sharing the same `address` in one unit, (2) each carrying an inline `definition` array whose chash equals a `definition_chash` that some evaluated `['address', ...]` reference resolves to, and (3) that reference must actually be evaluated during validation (either as part of the unit's own definition validation or via another address/asset condition that references the duplicated address). Because attackers fully control the unit's authors/definitions/messages content, and the "definition_chash not found in storage but present in current unit's authors" lookup path is a documented, intentional fallback (`bAllowUnresolvedInnerDefinitions`), constructing such a unit is feasible without any real privileges — it requires understanding of the definition-evaluation logic but no cryptographic breaks. This yields Medium likelihood, consistent with the "unprivileged unit poster" reachability required by the scan rules.

## Recommendation
- Replace both bare `throw Error("more than 1 address definition")` statements in `definition.js` (lines ~298-299 in `validateDefinition`'s `'address'` case, and ~794-795 in `validateAuthentifiers`'s `'address'` case) with calls to the appropriate callback (`cb("more than 1 address definition")` / `cb2(false)`), so the condition becomes an ordinary validation error (`ifUnitError`) rather than a process-crashing exception.
- Additionally, enforce at the top of `validate()`/`validateAuthors()` in `validation.js` that no two entries in `objUnit.authors` share the same `address`, closing off the root cause that allows `arrDefiningAuthors.length > 1` to ever be true.
- Audit other `throw Error(...)` statements inside asynchronous DB-callback closures throughout `definition.js` (e.g., `'definition template'` case's `throw Error("not 1 template")`) for the same unhandled-exception-in-async-context DoS pattern, and convert them to callback-routed errors.

## Proof of Concept
Conceptual unit structure (illustrating the trigger condition; exact byte-level unit construction requires matching valid hashes/commissions per normal unit-composition rules):
```
objUnit.authors = [
  { address: "SHARED_ADDR", definition: defA, authentifiers: {...} },  // defA hashes to chash X
  { address: "SHARED_ADDR", definition: defB, authentifiers: {...} }   // defB also hashes to chash X (or same defA duplicated)
]
```
Where some spending/definition condition evaluated for this unit contains `['address', 'SHARED_ADDR']` and `storage.readDefinitionByAddress` reports `ifDefinitionNotFound(X)` (i.e., `SHARED_ADDR` has no confirmed stored definition with chash `X` yet). The `ifDefinitionNotFound` handler filters `objUnit.authors` for `author.address === 'SHARED_ADDR' && getChash160(author.definition) === X`; with two matching authors, `arrDefiningAuthors.length === 2 > 1`, hitting: [4](#0-3) 
which throws synchronously inside the `conn.query` callback of `storage.readDefinitionByAddress`, crashing the validating node process.
