### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `sha` across the entire `commits` table and never restricts the query to the repository that sent the webhook. Since `Handler` provides `repository_name`/`stacks` helpers that scope lookups to the payload's own repository but `StatusHandler` never calls them, any repository owner can send a `status` webhook with a sha that happens to collide with a `Shipit::Commit` row belonging to a completely different stack/repository and flip that unrelated commit's CI status.

### Finding Description
The binding that should hold is: `payload.dig('repository', 'full_name')` (the repository that authenticated/signed the webhook, call it R2) must equal `commit.stack.repository.full_name` for every `Commit` row mutated by the request (call it R1). `StatusHandler` never checks this.

Code path:
- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler`, per `app/controllers/shipit/webhooks_controller.rb:10-12` and `app/models/shipit/webhooks.rb:19`.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) only verifies that the HMAC signature matches the GitHub App/webhook secret configured for `repository_owner` (derived from `payload['repository']['owner']['login']` or similar). This proves the request really came from GitHub for **R2**, the attacker's own repo — it proves nothing about R1.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha` with no `stack_id`/repository filter, unlike `Handler#stacks`/`Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), which exist precisely to scope a handler's mutations to the repository that sent the webhook, but which `StatusHandler` never invokes.
- `Commit#create_status_from_github!` (defined in `app/models/shipit/commit.rb`) creates a `Shipit::Status` row tied to `commit.stack`/`commit`, which via `Status#add_status`-style flow (`app/models/shipit/commit.rb:366-386`) updates `previous_status`/`new_status`, emits `commit_status`/`deployable_status` hooks, and calls `stack.schedule_merges` when the new state is `pending` or `success` — i.e., it can directly trigger continuous-deployment merge scheduling for R1.

Exploit flow: an attacker who owns/controls repository R2 (any GitHub repo they can push to) creates a commit whose sha collides with a `Commit` row that already exists for a target stack's repository R1. Since Git commit shas are content-addressed, an attacker can engineer such a collision deliberately (e.g., an empty-tree/no-parent commit, or any commit whose tree+metadata reproduce an existing sha from a squash/rebase in R1) and push it to R2. They then send (or GitHub sends, upon their push) a `status` webhook for R2 with that `sha` and `state: success`. `verify_signature` validates fine because the webhook genuinely originates from R2 with R2's valid signature. `StatusHandler#process` then matches `Commit.where(sha: ...)` against **all** stacks in the database, including the unrelated R1 commit, and calls `create_status_from_github!` on it, mutating R1's CI status without R1 ever having authenticated anything.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema validation on `sha`/`state`, `force_github_authentication`, `Repository`/`Stack` validations) check that the sha's owning stack's repository matches the webhook's `repository.full_name`. The `stacks`/`repository_name` scoping helpers exist in the base `Handler` class precisely for this purpose but are unused by `StatusHandler`.

### Impact Explanation
A successful match lets an attacker owning any repository R2 write a `Shipit::Status` (`pending`/`success`/`failure`/`error`) against a `Shipit::Commit` belonging to an arbitrary, unrelated stack R1 whose sha they can predict or engineer a collision for. Because `success`/`pending` transitions trigger `stack.schedule_merges` and `deployable_status`/`commit_status` hooks (`app/models/shipit/commit.rb:379-384`), this can move R1's continuous-delivery pipeline forward (merge scheduling, deploy triggers) based on a webhook that R1 never authorized — this is a payload for one repository mutating another repository's stack/commit state, matching the "Critical" impact category (cross-tenant record mutation without that repository's authentication).

### Likelihood Explanation
The attacker needs: (1) their own GitHub repository configured as a Shipit-tracked repository (so `verify_signature` succeeds using R2's own legitimate webhook secret — no Shipit or GitHub secret theft required), and (2) a sha collision between a commit they control in R2 and an existing `Commit` row in the target R1 stack. Git shas are 160-bit SHA-1 values, so blind collision is infeasible, but the question's proof idea — deterministic, parent-less "empty-tree" commits, or shas that coincidentally repeat across repos due to squash/rebase producing identical tree+commit metadata — is a real, narrower, but non-zero-cost avenue; more generally, any scenario where the same commit (e.g., a vendored/cherry-picked commit, a shared base commit imported into multiple stacks) exists as a `Commit` row in two different stacks is directly and trivially exploitable, without needing hash engineering at all: the attacker only needs an R2 repository containing a commit whose sha matches any existing `Commit.sha` in the target stack. This is highly likely for shared history (forks, vendored commits, monorepo splits) and requires no privileged access — only ownership of an arbitrary repository connected to the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, using the existing `Handler#stacks`/`repository_name` helpers, e.g.:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently `Commit.joins(stack: :repository).where(sha: params.sha, shipit_stacks: { repository_id: Repository.from_github_repo_name(repository_name)&.id })`, ensuring only commits belonging to stacks of the repository named in `payload['repository']['full_name']` can be mutated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers_test.rb` or `test/controllers/webhooks_controller_test.rb` pattern):
```ruby
test "status webhook from repository R2 must not mutate a Commit belonging to repository R1's stack" do
  stack_r1 = shipit_stacks(:shipit)          # owned by repository R1
  stack_r2 = shipit_stacks(:cyclimse)        # owned by a different repository R2 (fixture)
  refute_equal stack_r1.repository_id, stack_r2.repository_id  # binding check: repos differ

  collided_sha = "e69de29bb2d1d6434b8b29ae775ad8c2e48c5391" # empty-tree sha, or any shared sha
  commit_r1 = stack_r1.commits.create!(sha: collided_sha, ...)
  commit_r2 = stack_r2.commits.create!(sha: collided_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = { 'sha' => collided_sha, 'state' => 'success',
           'repository' => { 'full_name' => stack_r2.github_repo_name, 'owner' => { 'login' => stack_r2.repository.owner } } }.to_json

  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  post :create, body: body, as: :json

  commit_r1.reload
  commit_r2.reload

  assert_equal 'success', commit_r2.state       # R2's own commit legitimately updated
  refute_equal 'success', commit_r1.state       # FAILS today: commit_r1.state becomes 'success' too, proving cross-tenant mutation
end
```
This test currently fails (i.e., both `commit_r1` and `commit_r2` transition to `success`), demonstrating that `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup breaks the repository-ownership binding.
