### Title
Cross-organization webhook forgery lets a valid webhook secret for one GitHub organization authorize writes against any other organization's repositories - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* organization's HMAC secret to validate a webhook against by reading an attacker-controlled JSON field (`repository.owner.login` / `organization.login`), while the event handlers that actually mutate state pick *which repository/stack* to act on from a different, independently-controlled JSON field (`repository.full_name`). Because these two fields are never checked for consistency, a party who legitimately knows the webhook secret for organization B (e.g. because they administer a GitHub org/repo that is configured to send webhooks to this shared Shipit instance) can forge a signed payload that authenticates as org B but names a repository belonging to org A, causing Shipit to perform org-A-scoped actions (sync, review-stack archival, status writes, etc.) on behalf of an unrelated organization.

### Finding Description
Signature verification and payload dispatch use two different attacker-controlled identifiers:

- `verify_signature` derives `repository_owner` from the JSON body itself and uses it to select the `GitHubApp`/secret to check the signature against: [1](#0-0) [2](#0-1) 

- The signature is a plain HMAC-SHA1 over the raw body computed with the secret belonging to whatever organization `repository_owner` names: [3](#0-2) 

- `Shipit.github(organization:)` resolves per-organization webhook secrets from `secrets.github`, confirming this engine supports multiple independently-secreted GitHub organizations sharing one Shipit deployment: [4](#0-3) 

- Once the signature check passes (using the secret for the org named by `repository.owner.login`), the raw params are dispatched unmodified to every registered handler for the event: [5](#0-4) 

- Every handler resolves the target `Stack`/`Repository` from a *different* JSON field, `repository.full_name`, with no cross-check against the field used for signature verification: [6](#0-5) 

Concretely, `PushHandler` looks up stacks by `repository.full_name` and triggers a GitHub sync using an attacker-supplied `after` SHA: [7](#0-6) 

`PullRequest::ClosedHandler` resolves the repository the same way and archives its review stack: [8](#0-7) 

Attack: an attacker who administers organization B's GitHub org (and therefore legitimately knows the webhook secret configured for B in `secrets.github`) crafts a raw POST directly to the shared `/webhooks` endpoint with:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgA/target-repo", "owner": { "login": "OrgB" } }
}
```
signed with `X-Hub-Signature: sha1=<hmac using OrgB's webhook_secret>`. `repository_owner` resolves to `"OrgB"`, the signature check succeeds against B's real secret, and the handler then acts on `OrgA/target-repo`, a repository the attacker has no relationship with in Shipit or GitHub. The equality that should hold — `organization that authenticated == organization that owns the repository being written` — is broken; the code enforces only "some org's secret matches the whole raw body," not "the org that owns that secret is the org whose repository is affected."

### Impact Explanation
This crosses an organization boundary that Shipit's per-org secret model is meant to enforce. Depending on which handler is targeted, the impact reaches into the "Critical/High" categories called out by the rules:
- `PushHandler` forces org A's stacks to re-sync against an attacker-chosen `after` SHA, using Shipit's own GitHub credentials for org A — an unauthorized write/trigger against a repository outside the attacker's control.
- PR handlers (`ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, etc.) can archive/unarchive review stacks or otherwise mutate org A's stack state purely from a forged, org-B-signed payload.
- `StatusHandler`/`CheckSuiteHandler` can inject/alter commit statuses and check-run refreshes for org A's commits, potentially influencing whether org A's changes are considered "deployable" and unblocking an actual deploy in Shipit's UI.

This is effectively a cross-repository/cross-organization write achieved without any Shipit application credential (`ApiClient` token, session, GitHub App private key) — only knowledge of a webhook secret for *some other, unrelated* organization on the same shared Shipit instance.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where `secrets.github` is configured with more than one organization (a supported, documented configuration per `Shipit.github_app_config`/`TOP_LEVEL_GH_KEYS`). Any legitimate administrator of *any one* of those organizations can execute this attack against *any other* organization on the same instance, since the only prerequisite is knowing your own org's webhook secret and being able to reach the shared `/webhooks` endpoint (which is unauthenticated by design, as it's meant to be hit by GitHub). No privileged Shipit account, ApiClient token, or GitHub App private key is needed.

### Recommendation
After verifying the signature, re-derive the acting organization from the same trusted field used for signature selection and require it to match the organization owning `repository.full_name` before any handler is allowed to act (i.e., verify `repository.owner.login`/`organization.login` used for secret selection is the same organization that owns the `Repository` resolved from `repository.full_name`, rejecting the request otherwise). Alternatively, bind webhook secrets to the specific `Repository`/`Stack` record rather than to a bare organization login, so verification and dispatch are keyed off the exact same, already-persisted trust boundary rather than two independently attacker-supplied JSON fields.

### Proof of Concept
1. Configure Shipit (per README multi-org support) with two organizations in `secrets.github`, e.g. `OrgA` and `OrgB`, each with its own `webhook_secret`. Assume the attacker legitimately administers `OrgB` and its webhook secret, and there exists a Shipit `Stack` tracking `OrgA/target-repo`.
2. Attacker builds a raw JSON push payload:
```json
{"ref":"refs/heads/master","after":"<arbitrary sha>","repository":{"full_name":"OrgA/target-repo","owner":{"login":"OrgB"}}}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, raw_body)>` and POSTs it to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` reads `repository_owner` = `"OrgB"` [2](#0-1) , fetches `Shipit.github(organization: "OrgB")`, and the HMAC check succeeds because the attacker used OrgB's real secret [3](#0-2) .
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler.call(params)`, which resolves stacks via `payload.dig('repository','full_name')` = `"OrgA/target-repo"` [9](#0-8)  and calls `stack.sync_github(expected_head_sha: params.after)` for OrgA's stack [10](#0-9)  — an action on a repository/organization the attacker has no legitimate relationship to, triggered solely by possession of an unrelated organization's webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
