### Title
Cross-organization webhook forgery: signature verified against one organization's secret while events are applied to a repository/stack belonging to a different organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which GitHub organization's `webhook_secret` to use for HMAC verification from a field in the attacker-controlled request body (`repository.owner.login`, falling back to `organization.login`), but the downstream event handlers resolve the `Stack`/`Repository` to mutate from a different field of that same body (the repository's full name). Because these two values are never cross-checked against each other, a party who legitimately knows the `webhook_secret` for **one** organization onboarded to a shared Shipit instance can forge a signed payload whose `repository.owner.login` matches their own org (so verification passes) while the embedded repository/full-name points at a **different** organization's tracked repository, letting them inject fabricated commits/CI statuses into a stack they do not control.

### Finding Description
`verify_signature` picks the GitHub App/org config purely from payload content: [1](#0-0) 
and: [2](#0-1) 

Verification is delegated to `GitHubApp#verify_webhook_signature`, which HMACs the raw body with the secret configured for **that** org only: [3](#0-2) 

Once verification succeeds, `create` dispatches the entire attacker-controlled JSON to all handlers for the declared event, with no re-derivation or cross-check tying the org whose secret validated the signature to the repository the handlers act on: [4](#0-3) 

Shipit is explicitly designed to host multiple GitHub organizations behind one instance (`Shipit.github(organization: ...)` resolves per-org config, raising `Shipit::GithubOrganizationUnknown` only if the org isn't configured at all). The binding this breaks is: **organization that authenticated (whose secret validated `X-Hub-Signature`) == repository that is written (the Stack/Repository the handler updates)**. If `repository.owner.login` (used to pick the secret) and the repository identity used by the push/status/check-suite handlers to locate the target `Stack` (via `Repository.from_github_repo_name`/`full_name`) are not required to agree, an attacker who is a legitimate admin of Org A — and therefore genuinely possesses Org A's own `webhook_secret` — can correctly sign a payload where the `owner.login` says "org-a" but the repository object otherwise describes "org-b/private-repo", a stack belonging to an unrelated, victim organization tracked by the same Shipit deployment.

I was not able to fully re-verify, within the remaining tool budget, whether the individual handlers (`app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`) perform any additional owner-consistency check before resolving/creating commits or statuses against `Repository.from_github_repo_name`. This is the one piece of root-cause detail that remains unconfirmed from the index; the controller-level authorization gap (secret selection field ≠ any enforced binding to the acted-upon repository) is confirmed directly from `app/controllers/shipit/webhooks_controller.rb` and `lib/shipit/github_app.rb`.

### Impact Explanation
If confirmed end-to-end, this allows an attacker who administers any single organization onboarded to a multi-tenant Shipit instance to forge commit/status/push/check-suite events for a repository belonging to a completely different organization. Because commit statuses and check-suite results feed the merge queue's `all_status_checks_passed?`/CI-gating logic and deploy safety checks (`Shipit::MergeRequest`, `Shipit::Status`), this could be used to make a victim stack appear "green" (bypassing required CI) or otherwise pollute its commit/status history, ultimately enabling an unauthorized merge or deploy on a repository the attacker has no legitimate access to. That maps to the Critical/High "cross-repository writes / unauthorized deploy or merge" impact bucket.

### Likelihood Explanation
Likelihood is moderate and conditioned on: (1) Shipit hosting more than one GitHub organization with independently configured `webhook_secret`s (a supported, common multi-tenant configuration per `GitHubApp#initialize`), and (2) the event handlers not independently validating that the `repository.owner.login` used for signature selection matches the org of the repository actually being written. Point (1) is confirmed by the code; point (2) could not be fully confirmed from the retrieved snippets in the time available, so this should be validated against the handler implementations before treating it as fully proven.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the organization from the exact same repository object the handlers will use to resolve the `Stack`/`Repository` (i.e., use one canonical field, such as `repository.full_name`, for both secret selection and target resolution), and reject the webhook if the two disagree. Alternatively, have `Webhooks.for_event` handlers explicitly assert `stack.repository.owner == repository_owner` (the value used for signature verification) before mutating any state.

### Proof of Concept
Conceptual (pending confirmation of handler internals):
1. Shipit instance tracks `org-a/app` (secret `S_A`) and `org-b/secret-app` (secret `S_B`), where the attacker is a legitimate admin of `org-a` and knows `S_A`.
2. Attacker crafts a `push` (or `status`) payload where `repository.owner.login == "org-a"` (so `WebhooksController#repository_owner` selects `S_A`) but the repository's `full_name`/`name` fields identify `org-b/secret-app`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, raw_body)` and POSTs to `/webhooks`.
4. `verify_webhook_signature` succeeds (correct secret for the org it looked up) per [3](#0-2) .
5. If the `push`/`status` handler resolves the target `Stack` via the repository's full name rather than re-validating against `org-a`, fabricated commits/statuses are written into `org-b/secret-app`'s stack despite `S_B` never being known to the attacker.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
