### Title
Webhook signature verification is keyed by `repository.owner.login`, but event handlers act on the independent `repository.full_name` field — cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate an inbound webhook against using `repository_owner`, a value read from the JSON body (`repository.owner.login`, falling back to `organization.login`). Every downstream `Webhooks::Handlers::Handler` subclass, however, determines *which repository/stack to act on* using a completely different, unchecked field of the same body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a webhook that is cryptographically authenticated as belonging to organization A can be crafted to act on a repository belonging to organization B, exactly mirroring the `GoatV1Pair.takeOverPool()` pattern where one field (`token` amount) was checked while a sibling field (`initialETH`) controlling the same operation was not.

### Finding Description
- `verify_signature` picks the signing key/app based on `repository_owner`: [1](#0-0) [2](#0-1) 

- `repository_owner` selects a `GitHubApp` instance, and thus a `webhook_secret`, via `Shipit.github(organization:)`, which is a per-organization config in multi-org deployments (see `github_app_config`, `github_organizations`): [3](#0-2) 

- Verification itself is a pure HMAC check against whatever secret was resolved for that organization: [4](#0-3) 

- Once `head(422)` is *not* raised (i.e., the signature matched **some** configured organization's secret), `create` dispatches the **entire raw payload** to every registered handler for the event, unfiltered by `repository_owner`: [5](#0-4) 

- Every handler resolves the actual repository/stack to operate on from a *different* JSON key — `repository.full_name` — with no cross-check against the `repository.owner.login` value used for signature selection: [6](#0-5) 

The security-relevant binding that should hold is:
`organization used to select/verify the signing secret == organization that owns the repository the handlers write to`

The code never enforces this equality. `repository.owner.login` (or `organization.login`) is used purely to pick a key for HMAC verification; `repository.full_name` is used purely to pick the target `Stack`/`Repository`/`PullRequest` records to mutate. An attacker who can produce a validly-signed webhook for *any one* organization configured on the Shipit instance (e.g., their own organization that they legitimately installed the Shipit GitHub App on, per `docs/setup.md`, or an org whose `webhook_secret` happens to be unset since it's documented as optional) can set `repository.owner.login` to that organization while setting `repository.full_name` to `victim-org/victim-repo`. The signature check passes (it only validates the org named in `repository.owner.login`), and every handler then reads `repository.full_name` to find and mutate the victim's `Stack`/`PullRequest` state: [7](#0-6) [8](#0-7) 

The multi-org configuration is a first-class, documented feature of the engine (each org has its own `app_id`/`webhook_secret`), so this cross-org confusion is directly reachable in that supported configuration: [9](#0-8) 

### Impact Explanation
This breaks the trust boundary between "which GitHub organization authenticated this request" and "which repository's state gets written," resulting in cross-repository writes: an attacker who only controls (or has valid webhook credentials for) organization A can trigger state-changing operations against organization B's stacks — forcing `GithubSyncJob`/`stack.sync_github` on arbitrary target stacks (`PushHandler`), archiving a victim's review stack (`PullRequest::ClosedHandler#process` → `review_stack.archive!`), toggling `unarchive!` on `ReopenedHandler`, or injecting fabricated commit statuses (`StatusHandler` writes `Commit#create_status_from_github!` keyed only by `sha`, with no repository binding at all). These are unauthorized cross-repository writes performed without the target organization's authentication, matching the "cross-repository writes" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to possess valid signing capability for *any single* organization connected to the shared Shipit instance — a realistic scenario for any Shipit deployment onboarding multiple GitHub organizations (a documented, supported configuration), or for a deployment where one org's optional `webhook_secret` is left blank (also documented as optional). No access to the target repository, target organization's secret, or any Shipit session/API token is required, satisfying the "unprivileged attacker" bar.

### Recommendation
In `WebhooksController#verify_signature` / `create`, after successfully verifying the signature for `repository_owner`, enforce that every handler restrict its lookups to repositories actually owned by that same, verified organization — e.g., pass the verified organization into `Handler#initialize` and have `stacks`/`repository` lookups filter on it, or reject the webhook outright if `repository.full_name`'s owner segment does not case-insensitively match the `repository_owner`/`organization.login` value that was cryptographically verified.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`); attacker legitimately controls `OrgA` and knows/has `OrgA`'s `webhook_secret` (or `OrgA`'s secret is unset).
2. Attacker sends a `pull_request` "closed" webhook to `/webhooks` with:
   - `X-Github-Event: pull_request`
   - `X-Hub-Signature` computed with `OrgA`'s `webhook_secret` over the full body
   - Body: `repository.owner.login = "OrgA"`, but `repository.full_name = "OrgB/victim-repo"`, `pull_request.number` matching a real open review-stack PR in `OrgB`.
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the HMAC matches → request accepted (`app/controllers/shipit/webhooks_controller.rb:24-30`).
4. `PullRequest::ClosedHandler` resolves `repository` from `params.repository.full_name = "OrgB/victim-repo"` (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb:49-53`) and calls `review_stack.archive!`, archiving `OrgB`'s review stack despite the request never being authenticated by `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
