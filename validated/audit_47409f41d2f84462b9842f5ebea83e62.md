### Title
Webhook authentication is bound to `repository.owner.login`/`organization.login` while the mutated `Stack` is selected via a different field, `repository.full_name` - allowing cross-organization webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret used to authenticate an inbound GitHub webhook based on `repository.owner.login` (or `organization.login`) read from the untrusted JSON body, then verifies the *entire* raw body against that org's secret. Every webhook `Handler` subclass, however, decides which `Stack`/`Repository` to mutate using a completely different field of the same body: `repository.full_name`. Because these two fields are never cross-checked, a payload can be crafted so that the field used to select "who authenticated" (org A) diverges from the field used to select "what gets written" (org B's repository), letting a webhook that's valid for org A's secret drive side effects against org B's stacks.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to check against using: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (falling back to `organization.login`) straight out of the unverified JSON body, and that value is used only to pick which org's `webhook_secret` HMAC-checks the raw request body: [3](#0-2) 

If verification succeeds (or the target org has no `webhook_secret` configured at all, in which case `verify_webhook_signature` unconditionally returns `true`), the payload is dispatched to handlers. Every handler inherits `stacks`/`repository_name` from the base `Handler` class, which selects the `Repository`/`Stack` records to act on using a *different* field of the same body — `repository.full_name` — with no cross-check against `repository_owner`: [4](#0-3) 

For example, `PushHandler#process` uses `stacks` (i.e. repositories resolved from `repository.full_name`) to trigger a GitHub sync: [5](#0-4) 

This is the exact analog of the `FeeWrapper` bug class: the binding the code relies on for authorization (`repository.owner.login` used to select the authenticating secret) is not the same binding used to perform the privileged action (`repository.full_name` used to select the repository that is written). As an equality that must hold but doesn't: `repository_owner(payload) == owner_of(repository.full_name(payload))` is never asserted.

### Impact Explanation
An attacker who knows (or controls) the webhook secret for any single organization configured on a multi-tenant Shipit instance — or targets an org entry that has no `webhook_secret` set, which the setup docs explicitly treat as a valid, if less secure, configuration — can submit a raw POST to `/webhooks` where `organization.login`/`repository.owner.login` names their own org (satisfying signature verification) while `repository.full_name` names a repository belonging to a different, victim organization tracked by the same Shipit deployment. Handlers such as `PushHandler` will then enqueue `GithubSyncJob`/`stack.sync_github` against the victim's stacks, and other handlers (membership, pull_request family) will mutate state (teams, PR-driven review stacks) tied to a repository the attacker never authenticated for. This is a cross-repository/cross-tenant write and can drive unauthorized sync/deploy-adjacent actions on stacks the attacker does not own, matching the Critical "cross-repository writes / unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitation requires no Shipit session, API token, or GitHub App private key — only knowledge of the webhook HMAC secret for one org hosted on the instance (or an org configured without a secret, which the maintainers' own docs present as acceptable). In any Shipit deployment that multiplexes several GitHub organizations under `config/secrets.yml`'s `github:` map (as the setup docs describe), this is a realistic, low-effort forgery: the attacker only needs to construct one JSON body and compute one HMAC with a secret they legitimately possess for their own org.

### Recommendation
After verifying the signature, `WebhooksController`/`Handler` should re-derive the organization from the same field used for resolving the target repository (`repository.full_name`'s owner segment) and reject the payload if it doesn't match `repository_owner`/`organization.login` used for HMAC selection. Alternatively, verify the signature using the secret tied to the resolved `Repository`/`Stack`'s actual configured organization rather than a value taken from the unauthenticated payload.

### Proof of Concept
1. Shipit is configured with two orgs, `attacker-org` (secret `S_A`, known to the attacker) and `victim-org` (owns stack `victim-org/app`).
2. Attacker builds a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "victim-org/app",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` and sets `X-Github-Event: push`.
4. `WebhooksController#repository_owner` resolves `"attacker-org"`, `Shipit.github(organization: "attacker-org")` is used, and `verify_webhook_signature` succeeds because the attacker used their own valid secret.
5. `PushHandler` is invoked with the full payload; `Handler#repository_name` resolves `"victim-org/app"` and `stacks` returns `victim-org`'s stacks, on which `sync_github` is triggered — a mutation on a repository the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
