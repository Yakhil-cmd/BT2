Found: `harvest_rewards` in `substrate/frame/asset-rewards/src/lib.rs` calls `update_pool_and_staker_rewards` but never persists the returned, updated `pool_info` to `Pools::<T>` storage — the exact "compute updated state but caller forgets to save it" pattern from the Sherlock report, though the impact here differs from the original (loss of accrued rewards for other stakers vs. loss of a user's own funds).

### Title
`harvest_rewards` computes updated `Pools` reward-per-token state but never persists it to storage - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`Pallet::<T>::update_pool_and_staker_rewards` is explicitly documented as having "no side-effects... the responsibility of the caller" [1](#0-0) . It returns a freshly computed `(PoolInfoFor<T>, PoolStakerInfo<...>)` pair, where the pool half carries an updated `reward_per_token_stored` and `last_update_block` computed by `update_pool_rewards` [2](#0-1) . In `stake` and `unstake`, the caller correctly re-inserts the returned `pool_info` into `Pools::<T>` before returning [3](#0-2) [4](#0-3) . However, in `harvest_rewards`, the returned `pool_info` is bound immutably and used only to read `reward_asset_id`/`account` for the transfer — it is never written back with `Pools::<T>::insert(pool_id, pool_info)` [5](#0-4) .

### Finding Description
`update_pool_rewards` advances `reward_per_token_stored` to the value accrued up to the current block, and sets `last_update_block = now` [2](#0-1) . This "checkpointing" is what makes `reward_per_token` correctly compute *only the newly-elapsed blocks* on the next call: `rewardable_blocks_elapsed = last_block_reward_applicable(expiry) - pool_info.last_update_block` [6](#0-5) . If `Pools::<T>::get(pool_id).last_update_block` is never advanced by `harvest_rewards`, the on-chain `Pools` entry retains its old `last_update_block`/`reward_per_token_stored` after a harvest call, exactly mirroring the reported Vault bug: the function that "settles"/"checkpoints" state produces an updated in-memory struct that the caller drops instead of persisting.

The staker side is persisted (`PoolStakers::<T>::insert`/`remove` after resetting `rewards` to 0) [7](#0-6) , but the pool side is not. On a subsequent `stake`/`unstake`/`harvest_rewards` call for that same pool, `reward_per_token` will be recomputed from the stale `last_update_block`, counting the blocks between the stale checkpoint and now — blocks that were already accounted for and paid out during the dropped update in `harvest_rewards`.

### Impact Explanation
Because `reward_per_token_stored` recomputation is idempotent given a fixed `last_update_block`/`reward_rate_per_block`/`total_tokens_staked`, and because `derive_rewards` for other stakers is `amount * (reward_per_token - staker.reward_per_token_paid) + staker.rewards` [8](#0-7) , the practical effect of the stale `last_update_block` is that the same block range gets "replayed" into `reward_per_token` on the next update call for the pool. This does not fabricate new reward-asset tokens (the pool still only pays out from its `account`'s actual balance via `T::Assets::transfer`), so it is not a direct unbacked-issuance bug, but it corrupts pool reward-accounting invariants and can lead to incorrect distribution among stakers (some may be able to claim disproportionate shares, or the pool's real-token balance can be exhausted faster than intended for other legitimate claimants), since `reward_per_token` calculations for *other* stakers become desynchronized from actual elapsed/accrual time. This is a self-inflicted accounting corruption in a permissionless, no-privilege-required pallet extrinsic (`harvest_rewards` requires no special origin beyond being the staker or calling after expiry) — no governance, no malicious validator, no privileged role needed.

### Likelihood Explanation
`harvest_rewards` is a normal user-facing extrinsic that any staker can call any time they have a non-empty `PoolStakers` entry [9](#0-8) . Every single harvest call reproduces the missing write, so likelihood of triggering the bug is effectively certain on any pool where harvesting is used — this is not an edge case requiring special timing.

### Recommendation
In `harvest_rewards`, persist the pool half of the tuple returned by `update_pool_and_staker_rewards`, mirroring `stake`/`unstake`: add `Pools::<T>::insert(pool_id, pool_info);` immediately after computing `(pool_info, mut staker_info)` and before/after the transfer, consistent with how `stake` and `unstake` do it.

		#[pallet::call_index(3)]
		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Computes update pool and staker reward state.
		///
		/// Should be called prior to any operation involving a staker.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}
