### Title
Webhook signature verification is keyed on a different payload field than the repository the event acts on, allowing cross-organization stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub organizations behind a single Shipit instance, each with its own GitHub App config and its own (optional) `webhook_secret` [1](#0-0) . The webhook signature check selects which organization's secret to validate against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, but the handlers that actually mutate state look up the target `Stack`/`Repository` using a *different* field of the same body, `repository.full_name`, with no verification that its owner matches the organization whose secret validated the request.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the HMAC secret) to check the signature against based on a payload-derived value: [2](#0-1) [3](#0-2) 

`repository_owner` is read straight from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — both fully attacker-controlled fields in the raw POST body, before any signature has been validated.

Once verification passes (or is skipped, since `verify_webhook_signature` returns `true` unconditionally when the resolved org's `webhook_secret` is blank/nil — an explicitly supported, documented configuration [4](#0-3) [5](#0-4) ), the raw payload is dispatched unmodified to all registered handlers: [6](#0-5) 

Every handler resolves the target repository from a completely independent field, `repository.full_name`, via `Shipit::Repository.from_github_repo_name`: [7](#0-6) [8](#0-7) [9](#0-8) 

`from_github_repo_name` performs a plain string lookup by owner/name with no linkage back to which organization's App/secret authenticated the request. Nothing in the request pipeline enforces the equality:

`organization_that_authenticated(repository.owner.login used in verify_signature) == organization_of(repository.full_name used by handlers)`

This is exactly the "reference confirmed by an approver differing from the reference whose logic actually executes" pattern from the analog report, applied to an "organization that authenticated versus the repository that is written" binding: the signature check authenticates one organization identity taken from the payload, while the mutating code path trusts an entirely separate, also attacker-supplied, field to decide which `Stack` (potentially belonging to a completely different, more sensitive organization already registered in the same Shipit instance) gets acted upon.

### Impact Explanation
In a multi-org Shipit deployment (the documented `Using Multiple Github Applications` configuration, exemplified by `test/dummy/config/secrets_double_github_app.yml`'s `OrgOne`/`OrgTwo`), if any one configured organization has no `webhook_secret` set (an explicitly optional field per `docs/setup.md`), an unauthenticated network attacker can:
1. POST a forged JSON body to `/webhooks` with `X-Github-Event: push` (or `pull_request`, `membership`, etc.).
2. Set `repository.owner.login`/`organization.login` to the org with no secret — `verify_signature` will resolve that org's `GitHubApp` and `verify_webhook_signature` will return `true` unconditionally.
3. Set `repository.full_name` to `"OrgTwo/protected-repo"` — a stack belonging to a fully secured, unrelated organization hosted on the same instance.
4. The handler dispatch resolves the repository/stack purely from `full_name` and executes side effects against it: e.g. `PushHandler` triggers `stack.sync_github` (which can drive continuous delivery/deploys), `MembershipHandler` creates arbitrary teams/users, and the `PullRequest::*Handlers` can archive/unarchive review stacks and merge-queue state for `OrgTwo`'s repositories — all without ever proving control of `OrgTwo` or its GitHub App.

This constitutes a cross-organization write and can cascade into an unauthorized deploy/rollback trigger, matching the report's "High" impact bucket (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Likelihood is Medium: it requires (a) a multi-org Shipit deployment, and (b) at least one configured organization with no `webhook_secret` set — both of which are explicitly supported/optional per the engine's own documentation and are plausible in real deployments (e.g., a low-risk sandbox org onboarded without bothering to set a webhook secret, or during initial rollout before all secrets are configured). No credentials, sessions, or tokens are required from the attacker in that configuration.

### Recommendation
When resolving the target repository/stack in `Shipit::Webhooks::Handlers::Handler#repository_name` (and equivalently in each handler), verify that the owning organization of `repository.full_name` matches the organization (`repository_owner`) that was actually used to select and validate the webhook signature in `WebhooksController#verify_signature`. Reject (422) any event where these two organization values differ, and consider making `webhook_secret` mandatory (raise at boot / config-validation time) for every configured GitHub organization rather than allowing it to be silently blank.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgOne` (no `webhook_secret` set) and `OrgTwo` (has a `Stack` for `OrgTwo/protected-repo`, secured or not — irrelevant, since it's never checked):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "deadbeefcafefeed0000000000000000000000",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/protected-repo"
  }
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the (even missing) `X-Hub-Signature` header. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("OrgTwo/protected-repo")` and triggers `stack.sync_github` for `OrgTwo`'s stack — a state-changing action against an organization the request never actually authenticated as.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
