### Title
Reused Bitcoin Lockup Outpoints Are Not Globally Tracked, Allowing the Same L1-Locked Sats to Be Credited More Than Once - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar`'s L1 lockup verification (`verify-l1-lockups` / `validate-l1-lockup`) accepts a Bitcoin SPV proof (header, merkle proof, tx, output) and credits `sats` to a staker's bond after checking the output pays the expected P2WSH lockup script. The de-duplication of Bitcoin outpoints (`seen-outpoints`) is scoped only to the single call's fold accumulator (max list of 10), and is discarded once the call returns — there is no persistent, contract-wide map recording which `(txid, output-index)` pairs have already been used to credit sats. This can allow the same real Bitcoin lockup transaction to be replayed across separate `register-for-bond` invocations (e.g., different `bond-index` values, or re-submission after a prior credit) to be credited multiple times, breaking the equality "sats credited by an L1 proof == sats actually locked on Bitcoin once."

### Finding Description
`validate-l1-lockup` explicitly documents that its outpoint tracking is call-scoped: [1](#0-0) 

The dedup check only looks at the in-memory accumulator built during that single fold: [2](#0-1) 

`verify-l1-lockups` initializes `seen-outpoints` fresh to `(list)` on every invocation and returns only the summed `sats`: [3](#0-2) 

I searched `pox-5.clar` for any persistent registry of consumed Bitcoin outpoints (patterns such as `used-outpoint`, `credited-outpoints`, `global-outpoints`) and found none, only the ephemeral per-call `seen-outpoints` field inside the fold accumulator's tuple type. This means nothing in the contract prevents the exact same Bitcoin transaction output from being supplied again in a later, independent call to the lockup-verification path (e.g., a subsequent `register-for-bond` for a different `bond-index`, or after a bond rollover) — the script hash, merkle proof, and header would all validate identically because the underlying Bitcoin data doesn't change, and the on-chain check that would reject it (outpoint dedup) does not persist between transactions.

Because `verify-l1-lockups`'s output (`sum`) directly determines how many sats are recognized as locked for a staker/bond in `register-for-bond`, replaying the same lockup allows an attacker to have the same BTC-locked sats counted toward multiple bonds/registrations, or reused after being credited once, without locking any additional Bitcoin.

### Impact Explanation
This breaks the equality that sats credited toward a stacker's bond must correspond 1:1 to sats actually and currently locked in a specific, unspent Bitcoin UTXO. Double-crediting the same locked BTC lets an attacker inflate their effective stake/signing weight or reward eligibility across multiple bonds without providing additional collateral — this is a double-counting of a commitment, which the rules class as Critical impact ("double-counting a commitment or reward").

### Likelihood Explanation
Exploitation only requires an ordinary staker with a single real (or even historical) Bitcoin lockup output and the ability to call `register-for-bond` (or whatever entry point re-invokes `verify-l1-lockups`) more than once with the same proof data across different bonds/cycles — no privileged role, signer key, or admin access is required. The main uncertainty is whether some *other* part of the contract (outside what I was able to review in this pass, given the large number of maps in `pox-5.clar`) independently tracks a global "outpoint used" set and rejects the second submission; I was unable to fully enumerate all 50 `define-map` declarations in the file within the available search budget, so this should be verified directly against the full contract before treating this as conclusively exploitable.

### Recommendation
Persist consumed Bitcoin outpoints in a contract-level map (e.g., `(define-map used-l1-outpoints { txid: (buff 32), output-index: uint } bool)`), and check/insert into it inside `validate-l1-lockup` (or immediately after `verify-l1-lockups` returns) so that any given Bitcoin output can only ever be credited once across the entire contract lifetime, not just within a single call's fold.

### Proof of Concept
1. Staker A locks `N` sats to the pox-5 P2WSH lockup address (as derived by `construct-lockup-output-script`) in a single Bitcoin transaction `tx0`.
2. Staker A calls `register-for-bond` for `bond-index: 0`, submitting the SPV proof for `tx0`'s output; `verify-l1-lockups` validates it and credits `N` sats to bond 0.
3. Staker A calls `register-for-bond` again for `bond-index: 1` (or after a rollover to a new bond), submitting the *same* SPV proof for `tx0`'s output. Since `seen-outpoints` was reset for this new call and no persistent registry blocks reuse, `validate-l1-lockup`'s checks (`ERR_INVALID_UNLOCK_HEIGHT`, `ERR_INVALID_LOCKUP_SCRIPT`, `ERR_INVALID_LOCKUP_AMOUNT`, `ERR_DUPLICATE_LOCKUP_OUTPOINT`) all pass again, and bond 1 is also credited `N` sats.
4. Staker A now has `2N` sats credited across two bonds from a single `N`-sat Bitcoin lockup — a double-count of the same locked value.

*(Note: full confirmation requires reviewing the complete `register-for-bond` function and all maps in `pox-5.clar` to rule out an independent global anti-replay check that I could not fully verify within this session's tool budget.)*
