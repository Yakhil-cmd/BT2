### Title
AA-generated response unit hitting an unexpected `ifJointError`/`ifTransientError`/`ifNeedParentUnits`/`ifOkUnsigned` validation branch causes an uncaught `throw`, halting all full nodes during stabilization - (File: aa_composer.js)

### Summary
When a stabilized unit triggers an Autonomous Agent (AA), `aa_composer.js` composes a response unit and validates it internally via `validateAndSaveUnit()`. This function assumes the composed unit can only ever be perfectly well-formed or fail with a benign `ifUnitError` (which is turned into a bounce). Every other validation outcome (`ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`) is treated as impossible and handled by an unconditional `throw Error(...)`. [1](#0-0) 

### Finding Description
`validateAndSaveUnit` runs `validation.validate()` on the freshly composed AA response joint: [2](#0-1) 
Only `ifUnitError` is passed through as a recoverable error (`cb(err)`, which the caller uses to `bounce()` the trigger). All the other callback branches unconditionally `throw Error(...)`, which is an uncaught exception in the middle of the deterministic AA-trigger execution path (`handleAATriggers` → `handlePrimaryAATrigger` → `handleTrigger` → `sendUnit` → `validateAndSaveUnit`), itself invoked synchronously from `writer.saveJoint()` while a stable MCI's triggers are processed. [3](#0-2) [4](#0-3) 

`validation.js` has multiple checks that resolve to `ifJointError` rather than `ifUnitError` for conditions that are plausible to hit for an internally-composed unit due to any edge-case bug in AA-unit composition (`sendUnit`/`completePaymentPayload`) — e.g. mismatched `headers_commission`/`payload_commission` computed independently by `object_length.js` vs. those baked into the unit by the composer, or unexpected fields: [5](#0-4) [6](#0-5) 

The composer computes `headers_commission`/`payload_commission`/`oversize_fee` independently in `sendUnit()` using the same `objectLength` helper functions, but through a different, more complex incremental code path (accounting for send-all outputs, storage-size top-ups, oversize-fee-excluding-payments, temp-data fees, etc.): [7](#0-6) [8](#0-7) 
If any edge case in this incremental fee/size computation (e.g. rounding, ordering of `payload_commission` recomputation after `completeMessage()` changes `payload_hash`, or an as-yet-undiscovered interaction between `oversize_fee`, `tps_fee`, and `max_aa_responses`) produces a unit whose independently-recomputed `headers_commission`/`payload_commission` in `validation.js` (line 257-262) doesn't match what the composer wrote, the callback fired is `ifJointError`, not `ifUnitError`. `validateAndSaveUnit` then executes `throw Error("AA validation joint error: " + err)`, crashing the node's write/stabilization flow with an uncaught exception.

Because AA trigger execution and response-unit composition are fully deterministic and run identically on every full node that processes the same DAG state (this is required for consensus — see `writer.js:685-785` which stabilizes further MCIs and runs `aa_composer.handleAATriggers()` again in a loop), a bug that makes one node hit this crash will make **every full node** hit the identical crash at the identical MCI. This is the direct analog of the mx-chain-go bug: an “invalid” internally-generated unit is not handled through the normal recoverable error path, so instead of bouncing gracefully the whole node (and by extension the network of full nodes) is unable to proceed past that stabilization point — mirroring "the metachain would have stopped notarizing blocks from the shard chains."

### Impact Explanation
An uncaught exception thrown deep inside the deterministic write/stabilization pipeline stops the process (or corrupts the DB transaction state depending on how the exception propagates through `async`/promise chains, since `conn`/`batch` may be left mid-transaction). Since the trigger inputs and AA definitions are fully attacker-influenced (any user can post a payment to any AA address with attacker-chosen data/formula-triggering conditions), an attacker who can craft a trigger that drives the composer into one of these edge cases can deterministically crash every full node that processes that MCI, i.e. a network-wide denial of confirmation of new units — matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
This requires a genuine discrepancy between the AA composer's fee/size calculation and `validation.js`'s independent recomputation, which is a narrow, hard-to-trigger edge case (analogous to the original CVE, which also required a specific edge condition — a cross-shard invalid-username transaction). The likelihood is Medium: the code paths involved (temp-data fee extraction, storage-size top-ups, oversize-fee-excluding-payments) are complex and have already needed several MCI-gated bug-compatibility branches (`aa3UpgradeMci`, `pemCurvesFixMci`, `aaStorageSizeUpgradeMci`) suggesting this exact class of discrepancy has occurred before and been patched piecemeal, without eliminating the root design flaw: `validateAndSaveUnit` treats any future/unknown discrepancy as `throw` instead of a safe bounce.

### Recommendation
- In `aa_composer.js`'s `validateAndSaveUnit`, do not `throw` on `ifJointError` / `ifTransientError` / `ifNeedParentUnits` / `ifOkUnsigned`; instead treat any non-`ifOk` outcome as a bounce condition (log diagnostics and call `cb(err)`), the same way `ifUnitError` is already handled.
- Add defensive parity checks/asserts between the incrementally-computed `headers_commission`/`payload_commission`/`oversize_fee` in `sendUnit()`/`completePaymentPayload()` and `object_length.js`'s canonical computation *before* calling `validateAndSaveUnit`, surfacing a controlled bounce rather than relying on validation to catch it.
- Add fuzz/property-based tests exercising `completePaymentPayload` with combinations of send-all outputs, storage-size top-ups, temp_data messages, and near-`MAX_UNIT_LENGTH` payloads to catch fee/size mismatches before they can occur in production.

### Proof of Concept
No concrete repro payload was constructed (would require crafting an AA definition/trigger sequence that forces `completePaymentPayload`'s incremental size/fee accounting to diverge from `object_length.getHeadersSize`/`getTotalPayloadSize`, e.g. by exploiting the interaction between `send_all_output` change-output insertion for storage-size (`aa_composer.js:1078-1081`) and the independent oversize-fee recomputation gated by `pemCurvesFixMci`) — full exploitation requires deeper empirical testing of `aa_composer.js`'s fee bookkeeping that is out of scope for static analysis alone.
