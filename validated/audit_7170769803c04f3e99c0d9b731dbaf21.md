### Title
Ambiguous string concatenation without delimiter in prosaic contract hash allows content-hash collision - (File: prosaic_contract.js)

### Summary
`prosaic_contract.js` computes the identifying hash of a prosaic (offline) contract by directly concatenating `title`, `text`, and `creation_date` with no separator, in both the current and legacy hashing functions. This is the same bug class as the reported `abi.encodePacked` issue: concatenating multiple attacker-influenced, variable-length strings without a delimiter is ambiguous and lets different `(title, text)` pairs produce an identical hash.

### Finding Description
`getHash` and `getHashV1` both build the source string via naive concatenation instead of using a length-prefixed or delimited encoding: [1](#0-0) 

Both `title` and `text` are free-form, user/peer-supplied strings that are transmitted in the `prosaic_contract_offer`/`prosaic_contract_shared` device messages and stored directly in the `prosaic_contracts` table: [2](#0-1) [3](#0-2) 

Because there is no delimiter between `title` and `text` (unlike `arbiter_contract.js`, which explicitly fixed this same problem by introducing `exports.DELIMITER = "[|#|]"` for hashing after `NEW_HASH_DATE`): [4](#0-3) 

an attacker who controls the `title`/`text` split (e.g., a peer sending a contract offer, or a party constructing a signing request) can produce two different `(title, text)` pairs whose concatenation is byte-identical, yielding the same SHA-256 hash. For example, `title="AB", text="CD"` and `title="A", text="BCD"` collide identically under this scheme.

This hash is the sole binding between the human-readable contract text and the on-chain reference to it: `handleReceivedSigningUnit` compares the `data` message's `contract_text_hash` field against the locally stored `contract.hash` to confirm that the unit posted to the DAG corresponds to the agreed-upon contract text: [5](#0-4) 

### Impact Explanation
Because the identifying/verification hash does not uniquely bind `title` and `text`, a party crafting a contract offer (or later re-sending an altered contract with a shifted title/text boundary) can present one rendering of the contract to a counterparty for review/signature while a different split of the same bytes is stored/propagated elsewhere, yet both hash identically and both pass the `contract_text_hash` check in `handleReceivedSigningUnit`. Since a signed prosaic contract is meant to be the off-chain "proof" tied immutably to an on-chain `data` message via this hash, an attacker could exploit the ambiguity to make the recorded contract hash match text different from what the counterparty actually reviewed and consented to sign, undermining the integrity guarantee the hash is supposed to provide for a bilateral (often financial) agreement. This is a data-integrity/authentication weakness in a private-payment/contract flow reachable by any unprivileged counterparty who composes the contract offer, matching the severity class (ambiguous packed encoding) of the referenced report, though the concrete blast radius here is limited to prosaic-contract text integrity rather than direct fund loss.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to control message construction (which is normal for the party proposing/offering a prosaic contract) and to choose a colliding split, which is straightforward given they fully control both `title` and `text` before sending the offer. No privileged access or race condition is required — any wallet user proposing a prosaic contract to a peer can attempt this.

### Recommendation
Use a delimiter that cannot appear in `title`/`text` (or, more robustly, a length-prefixed encoding) when concatenating `title`, `text`, and `creation_date` for hashing in `getHash`/`getHashV1`, mirroring the fix already applied in `arbiter_contract.js`'s `getHashSrc`, which joins fields via `exports.DELIMITER` and rejects/escapes delimiter collisions. Alternatively, hash `title` and `text` structurally (e.g., via `object_hash.getSourceString`, which already prefixes each string with a type tag and null-byte separator and rejects embedded null bytes) rather than via raw string concatenation.

### Proof of Concept
1. Party A composes contract offer 1: `title = "AB"`, `text = "CD"`, `creation_date = "2026-01-01 00:00:00"`.
2. Party A composes contract offer 2: `title = "A"`, `text = "BCD"`, same `creation_date`.
3. `getHash`/`getHashV1` compute `sha256(title + text + creation_date)` for both — both yield the exact same hash because `"AB"+"CD"+date === "A"+"BCD"+date`.
4. Party A sends offer 1 for review/acceptance to the counterparty (who signs based on the displayed title/text), but stores/propagates contract metadata consistent with offer 2 (or a `data` message referencing the shared hash with different attached content elsewhere), since `handleReceivedSigningUnit` only checks `dataMessage.payload.contract_text_hash === contract.hash`, which cannot distinguish the two splits.

function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}

function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}

function handleReceivedSigningUnit(contract, unit, retry_count = 0) {
	db.query("SELECT 1 FROM unit_authors WHERE unit=? AND address=?", [unit, contract.shared_address], async function (rows) {
		if (rows.length === 0) {
			if (retry_count >= 10)
				return console.log(`signing tx ${unit} not found in db after 10 retries, giving up`);
			console.log(`signing tx ${unit} not yet in db, waiting for 30 seconds and trying again`);
			return setTimeout(handleReceivedSigningUnit, 30000, contract, unit, retry_count + 1);
		}
		console.log(`signing tx ${unit} found in db, setting contract's unit`);
		const objUnit = await storage.readUnit(unit);
		const dataMessage = objUnit.messages.find(message => message.app === "data");
		if (!dataMessage)
			return console.log(`data message not found in purported prosaic signing unit ${unit}`);
		const { payload } = dataMessage;
		if (payload.contract_text_hash !== contract.hash)
			return console.log(`data message payload does not match contract ${contract.hash} in purported prosaic signing unit ${unit}`);
		setField(contract.hash, "unit", unit);
	});
}

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
