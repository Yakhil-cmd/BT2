### Title
Rounding in headers-commission split among multiple `earned_headers_commission_recipients` can pay out more than was actually earned - (File: `headers_commission.js`)

### Summary
The reported issue is a bonding-curve rounding bug where per-transaction rounding-down of a price can, across multiple batches, cause the sum paid out to diverge from the sum collected, leaving the last claimant unable to be paid. `ocore` has an analogous rounding pattern in `headers_commission.js`, where a single `full_amount` of headers commission earned from a parent unit is split among several `earned_headers_commission_recipients` using independent `Math.round()` calls per recipient instead of an integer-preserving allocation (e.g., floor + remainder-to-last).

### Finding Description
When a unit with multiple authors (or an explicit `earned_headers_commission_recipients` list) wins headers commission from a parent unit, the full amount is split per recipient with: [1](#0-0) 
and, in the mysql/db-reconciliation path, the same rounding is applied again when aggregating recipient shares: [2](#0-1) 

Each recipient's payout is computed independently as `Math.round(full_amount * share / 100.0)`. Because `Math.round` is applied per recipient rather than once with the remainder assigned deterministically, the sum of the rounded amounts is not guaranteed to equal `full_amount`. It can be either less (dust lost) or, importantly, **more** than `full_amount` when several recipients' fractional parts each round up (e.g., two recipients with 50/50 shares and an odd `full_amount` both round `x.5` up via `Math.round`'s round-half-up behavior, producing a sum that exceeds the original amount by 1 or more units).

The `earned_headers_commission_recipients` field is fully attacker/user-controlled: any unprivileged user composing a multi-authored unit can set arbitrary shares (as long as they are positive integers summing to 100), which is the only invariant enforced at validation time: [3](#0-2) 

The resulting per-recipient amounts are persisted into `headers_commission_contributions` and then aggregated into `headers_commission_outputs`: [4](#0-3) 
These `headers_commission_outputs` become spendable balances via `commission`-type inputs, validated and summed with `mc_outputs.calcEarnings`: [5](#0-4) 

Since `headers_commission` of the payer unit is a fixed, deterministic value tied to what that payer already "paid" (deducted from its balance as a network fee) when the unit was created, any positive rounding discrepancy that makes `sum(recipient amounts) > full_amount` results in new spendable bytes being created that were never backed by an equivalent debit — i.e., new money appears in the system that no one paid for.

### Impact Explanation
Every stable unit with more than one author (or with a custom `earned_headers_commission_recipients` list) whose ancestor unit's headers commission is won triggers this split. An attacker who repeatedly posts multi-authored units, choosing recipient share fractions engineered to maximize rounding-up across all recipients (e.g., N recipients with shares such that each recipient's `full_amount*share/100` lands just above `x.5`), can systematically mint small amounts of extra spendable balance on each occurrence. Repeated at scale (many units over time), this becomes a supply-inflation vector — new bytes are created that are not backed by any burned/committed input, violating the network's fundamental accounting invariant that total commission redistributed cannot exceed total commission collected.

### Likelihood Explanation
Medium. The mechanism requires no special privilege — any user can author a multi-authored unit and freely choose `earned_headers_commission_recipients` shares (subject only to summing to 100 and being positive integers). Triggering headers-commission wins is a routine, expected part of DAG operation (any unit can become the "best child" of a parent and win its headers commission), so the attacker only needs their crafted unit to become the winning child of a parent, which is influenced by hash-based tie-breaking (`getWinnerInfo`) but is not unpredictable-proof against a patient attacker submitting many candidate units.

### Recommendation
Replace independent per-recipient rounding with an allocation method that preserves the total: compute rounded amounts for all recipients except the last, then assign the last recipient `full_amount - sum(previous roundings)` so that the total always exactly equals `full_amount`. Apply the same fix in both the RAM-based aggregation and the SQL-based aggregation paths in `headers_commission.js` (and audit the analogous `Math.round` split of `payload_commission` among multiple paid witnesses in `paid_witnessing.js` for the same class of issue).

### Proof of Concept
Given a unit with two `earned_headers_commission_recipients` at 50%/50% shares, and a parent unit whose `headers_commission` (the `full_amount` in `headers_commission.js`) is an odd number, e.g. `full_amount = 101`:
- Recipient A: `Math.round(101 * 50 / 100) = Math.round(50.5) = 51`
- Recipient B: `Math.round(101 * 50 / 100) = Math.round(50.5) = 51`
- Total distributed = 102, exceeding the actual earned `full_amount` of 101 by 1 unit.

This extra unit is inserted into `headers_commission_contributions` and later summed into `headers_commission_outputs`, becoming spendable via a `commission` input in a payment message, effectively minting 1 byte of unbacked value per occurrence. Repeating this pattern across many multi-authored units compounds the effect over time.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
