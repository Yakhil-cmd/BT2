### Title
Pre-mint donation to pallet-asset-conversion pool account inflates LP-token share of first depositor - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion::add_liquidity` (Uniswap-V2-style AMM used on Asset Hub and other parachains) computes the amount of LP tokens to mint for a *zero-total-supply* pool using only the newly-transferred `amount1`/`amount2`, while the pool's actual on-chain reserves (`reserve1`/`reserve2`, read live from the pool account's balances) can already be non-zero because any account can transfer tokens directly to the deterministically-derivable pool account before any LP tokens are ever minted. This mirrors the "donate into an empty vault to inflate NAV, then redeem inflated shares" pattern in the SummerFi/FleetCommander report: value is counted from a live balance query with no accounting for who put it there or whether it was priced fairly, and the first depositor's minted shares are priced against a subset of the pool's real value.

### Finding Description
In `add_liquidity` [1](#0-0) , the pool's reserves are read directly from the pool account's balance: [1](#0-0) 

Because `reserve1`/`reserve2` are simple balance queries on the pool account (`Self::get_balance`), and because `PoolLocator::pool_address`/`PoolLocator::address` deterministically derives the pool account for a given asset pair (confirmed by the `get_reserves` view function using the same derivation, see [2](#0-1) ), *any* signed account can transfer `asset1`/`asset2` directly to that address using an ordinary `Assets::transfer`/`Balances::transfer` — no `add_liquidity` call, no LP mint, no privileged role required. This is explicitly exercised (for a different purpose) in the existing test `add_tiny_liquidity_directly_to_pool_address`, which force-sets a balance directly on the pool account before calling `add_liquidity` and only asserts the call succeeds, never checking the resulting LP-token/value accounting [3](#0-2) .

The critical flaw is that the "is this the first mint" branch is driven by `total_supply.is_zero()`, a state variable that is *independent* of whether `reserve1`/`reserve2` are already non-zero: [4](#0-3) 

If `total_supply` is zero (no LP tokens minted yet) but `reserve1`/`reserve2` are already non-zero (due to a prior direct "donation" transfer), the code takes the `reserve1.is_zero() || reserve2.is_zero()` == false branch first to determine `amount1`/`amount2` (using the donated reserves only to compute the *ratio*, via `quote`), then computes `lp_token_amount = Self::calc_lp_amount_for_zero_supply(&amount1, &amount2)` — a function whose signature takes only the newly-supplied `amount1`/`amount2`, with no reference whatsoever to the pre-existing `reserve1`/`reserve2` already sitting in the pool account. The depositor is minted LP tokens priced only against their own small contribution, yet `total_supply` after minting represents a claim on the *entire* pool account balance (donated funds + new contribution), because subsequent `remove_liquidity`/swap pricing use the real, full balances (`get_reserves`) for payout, not the artificially small `amount1`/`amount2` basis used for minting.

Concretely: an attacker (1) permissionlessly creates or targets an existing empty pool, (2) transfers a large amount of `asset1`/`asset2` directly to the pool account (no `add_liquidity`, so `total_supply` stays `0`), (3) calls `add_liquidity` with a minimal `amount1_desired`/`amount2_desired` matching the donated ratio (so it passes the `quote`-derived min-amount checks), receiving `lp_token_amount` computed only from that minimal contribution while `T::MintMinLiquidity::get()` is permanently locked to the pool account, and (4) calls `remove_liquidity` for their `lp_token_amount`, which is computed proportionally against the pool's *full* (donated + contributed) reserves via `get_reserves`, effectively reclaiming the donated funds attributed to a symbolic minimal deposit. If a second, honest LP now adds liquidity in between steps (3) and (4) using the same inflated reserve as pricing basis, their minted share is diluted by the attacker-controlled ratio, and the attacker's redemption on step (4) extracts a disproportionate share of the honest LP's contribution as well.

### Impact Explanation
This breaks the fundamental AMM invariant that LP-token supply must always represent a proportional, honestly-priced claim on the pool's real reserves. An attacker can mint LP tokens that are undervalued relative to the pool's true balance at mint time, then redeem them for a share of value they never contributed (their own donated funds plus any interleaved honest LP's contribution). This is a direct, unbacked-value-extraction / share-inflation bug of the same class as the SummerFi FleetCommander exploit (donate assets into an empty/near-empty pool leg to manipulate the value:shares ratio before extracting), reachable by any ordinary signed account with no privileged role, governance action, or external chain compromise, on any Polkadot-SDK-based chain running `pallet-asset-conversion` (e.g., Asset Hub).

### Likelihood Explanation
Medium-High. The precondition (send tokens directly to a derivable pool account while `total_supply == 0`) requires no special access — it is a plain `transfer` extrinsic followed by an `add_liquidity` extrinsic, both public entry points with standard fees. The scenario is realistic for any freshly created pool (before the creator's first `add_liquidity` executes) or any pool whose LP tokens have been fully burned back down to zero supply. The existing test suite already demonstrates the "donate directly to pool account" primitive works mechanically (`add_tiny_liquidity_directly_to_pool_address`), but does not verify LP-token/value correctness in the zero-supply case, indicating this path is exercised in tests yet unguarded against the inflation consequence.

### Recommendation
In `add_liquidity`, when `total_supply.is_zero()`, compute the zero-supply LP mint using the *combined* post-transfer balances (`reserve1 + amount1`, `reserve2 + amount2`) rather than `amount1`/`amount2` alone, or equivalently reject/absorb any pre-existing reserve into the minted amount so that the first minter's LP tokens are priced against the pool's actual full value. Alternatively, have `do_create_pool`/`add_liquidity` sweep or account for any balance already present in the pool account before allowing the zero-supply mint path, and add an explicit regression test asserting that LP token minted for the first depositor is proportional to the *total* pool value (donated + contributed), not just the contributed amount.

### Proof of Concept
Not executed against a live/public network. Based on static code analysis of `substrate/frame/asset-conversion/src/lib.rs` (lines 800-893) and the existing test `add_tiny_liquidity_directly_to_pool_address` (`substrate/frame/asset-conversion/src/tests.rs:469-522`), the following integration-test outline (using the pallet's own mock/test harness, analogous to the existing test but with added assertions) would demonstrate the issue:
1. `create_pool(user, asset1, asset2)` — pool exists, `total_supply == 0`, `reserve1 == reserve2 == 0`.
2. Directly `transfer`/`force_set_balance` a large donation of `asset1` and `asset2` to the derived `pool_account` (as already done in the existing test) — `total_supply` remains `0`.
3. `add_liquidity(attacker, asset1, asset2, amount1_desired=<small>, amount2_desired=<small>, ...)` — assert `lp_token_amount` returned is computed via `calc_lp_amount_for_zero_supply(amount1, amount2)`, ignoring the donated reserve, and that `total_supply` after mint is `lp_token_amount + MintMinLiquidity`.
4. `remove_liquidity(attacker, asset1, asset2, lp_token_amount, ...)` — assert the attacker receives back an amount proportional to `lp_token_amount / total_supply * (donated_reserve + contributed_amount)`, i.e., materially more value than the small `amount1_desired`/`amount2_desired` they contributed.
This reproduction was not run in this session; the relevant source lines and the pattern of the existing (assertion-light) test were confirmed via source inspection only, so verifying the exact numeric outcome (and whether any unseen guard in `do_create_pool` or `calc_lp_amount_for_zero_supply` mitigates it) requires running the above test in the pallet's own `mock.rs`/`tests.rs` harness — the source for `calc_lp_amount_for_zero_supply`'s internal formula and `do_remove_liquidity`'s exact payout formula were not retrieved in full within this session's tool budget and should be double-checked by a follow-up agent before filing.
