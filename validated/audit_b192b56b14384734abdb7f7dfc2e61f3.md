### Title
Cross-tenant webhook forgery via decoupled `repository.owner.login` and `repository.full_name` in unsigned payloads — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) using `repository.owner.login`, while `Handler#repository_name` (used to locate the `Stack`/`Repository` to mutate) reads the unrelated `repository.full_name` field from the very same unverified JSON body. If any configured organization has no `webhook_secret` (a documented, supported configuration per `docs/setup.md`'s "Using Multiple Github Applications" and the shipped example secrets files), an attacker can name that org as the owner to trivially pass signature verification while pointing `full_name` at a completely different organization's tracked repository, causing writes (e.g. `GithubSyncJob`) against that other org's `Stack`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`organization whose webhook_secret verified the request bytes (derived from repository.owner.login)` == `organization owning the repository/stack that Shipit::Webhooks handlers mutate (derived from repository.full_name)`

Trace:
1. `WebhooksController#repository_owner` reads `params.dig('repository', 'owner', 'login')` and passes it to `Shipit.github(organization: repository_owner)` in `#verify_signature`: [1](#0-0) 
2. `GitHubApp#verify_webhook_signature` short-circuits to `true` when that specific app's `webhook_secret` is blank: [2](#0-1) 
3. `#create` then dispatches the *raw, unmodified* JSON body to every registered handler: [3](#0-2) 
4. `Handler#repository_name` (used by `Handler#stacks` and thus by e.g. `PushHandler#process`) resolves the target repository from `payload.dig('repository', 'full_name')` — a completely independent field from the one used for signature-app selection: [4](#0-3) 
5. `PushHandler#process` uses those stacks to call `stack.sync_github(expected_head_sha: params.after)`, which enqueues `GithubSyncJob`: [5](#0-4) , [6](#0-5) 

Root cause: nothing enforces that `repository.owner.login` (verification key) matches the owner segment of `repository.full_name` (mutation key). Both are attacker-supplied fields in the same unauthenticated JSON body, and Shipit explicitly supports multiple GitHub Apps, some of which may have no `webhook_secret` configured (shown as `webhook_secret: # nil` in `config/secrets.development.example.yml` lines 11 and 24-33, and in `test/dummy/config/secrets_double_github_app.yml`). If organization `OrgA` has no secret, `verify_webhook_signature` returns `true` unconditionally for a payload claiming `repository.owner.login = "OrgA"`, regardless of the `X-Hub-Signature` header's actual validity or absence.

Attacker request: `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{ "ref": "refs/heads/<target-branch>", "after": "<any-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" } }
```
No `X-Hub-Signature` header is required at all, because `OrgA`'s app has no secret.

Why existing guards fail:
- `drop_unhandled_event` only checks the event type exists, not payload consistency.
- `verify_signature` validates bytes against `OrgA`'s (non-existent) secret, never touching `OrgB`.
- `ExplicitParameters` schemas (e.g. `PushHandler.params`) only require `:ref`/`:after`, not any owner/full_name consistency.
- No model validation ties the two fields together at the webhook layer; `Repository.from_github_repo_name` simply looks up whatever `full_name` says.

### Impact Explanation
An attacker can force `GithubSyncJob` (and any other push/pull_request/status/check_suite handler logic keyed on `repository_name`) to run against any organization's tracked `Stack`/`Repository`, as long as at least one *other* organization configured on the same Shipit instance has no `webhook_secret`. This causes commit ingestion (`stack.commits.create_from_github!`) and cache-spec recomputation for a repository the attacker never authenticated against, and — for handlers like `pull_request` opened/labeled handlers that also key off `repository.full_name` — can drive `ReviewStack` creation/mutation for arbitrary repos. This is a cross-repository/cross-tenant write triggered by an unauthenticated request, matching "a payload for one repository mutating another's stack, commit, task or team" (Critical).

### Likelihood Explanation
Preconditions: the Shipit instance must be configured with multiple GitHub Apps (documented, supported feature), and at least one configured organization must have `webhook_secret` unset/blank — a state the shipped example secrets templates (`config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`) explicitly show as valid/default. Given that, the attack requires no secrets, no GitHub account privileges, and is a single unauthenticated HTTP POST, fully repeatable against any tracked repository/stack, matching a plausible operational configuration for a shared Shipit deployment.

### Recommendation
Bind signature verification to the same organization/repository actually used for mutation: derive `repository_owner` from `repository.full_name`'s owner segment (or verify that `repository.owner.login` matches the owner portion of `repository.full_name`) before dispatching to handlers, and reject the payload if they diverge. Additionally, consider making a missing `webhook_secret` a hard configuration error rather than an implicit bypass.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "cross-org payload with unsigned owner org enqueues GithubSyncJob against unrelated org's stack" do
  # OrgA has no webhook_secret configured (github_double_app fixtures)
  # OrgB owns the stack the attacker targets
  target_stack = shipit_stacks(:shipit) # owned by e.g. 'shopify' / 'shipit-engine'

  request.headers['X-Github-Event'] = 'push'
  # No X-Hub-Signature header sent at all
  payload = {
    "ref" => "refs/heads/#{target_stack.branch}",
    "after" => "deadbeef",
    "repository" => {
      "owner" => { "login" => "OrgA" }, # app configured with webhook_secret: nil
      "full_name" => target_stack.github_repo_name # e.g. "shopify/shipit-engine" (OrgB)
    }
  }.to_json

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: target_stack.id, expected_head_sha: "deadbeef"]) do
    post :create, body: payload, as: :json
    assert_response :ok
  end
end
```
Equality checked on both sides: before the fix, `Shipit.github(organization: "OrgA")` (no secret) "verifies" the request, while `GithubSyncJob` is enqueued for the stack owned by the org named in `full_name` ("OrgB")—the two organizations differ, proving the binding is broken. After applying the recommended fix, the request would be rejected with `422` because `repository.owner.login` ("OrgA") does not match the owner segment of `repository.full_name` ("OrgB/..."), and no job would be enqueued.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
