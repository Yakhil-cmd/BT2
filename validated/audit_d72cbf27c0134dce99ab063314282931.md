### Title
Unhandled internal AA-response validation states crash every full node - ([File: aa_composer.js])

### Summary
The Oracle CVE describes a crash/hang DoS triggered by exercising an unusual internal server code path with attacker-supplied input. The closest reachable analog in ocore is `aa_composer.js`'s internal validation of self-composed AA response units: any AA trigger (sendable by any unprivileged unit poster) can cause the deterministic AA-execution engine to reach a code branch that the engine treats as "impossible" and therefore crashes the whole process with an uncaught `throw`, rather than degrading gracefully.

### Finding Description
When an AA responds to a trigger, `aa_composer.js` builds a response unit and re-validates it through the normal `validation.validate()` pipeline via `validateAndSaveUnit()`: [1](#0-0) 

Unlike the handling of units received from the network in `network.js`'s `handleJoint()`, which gracefully handles `ifJointError`, `ifTransientError`, `ifNeedHashTree`, and `ifNeedParentUnits` outcomes (purging, retrying, or requesting missing content): [2](#0-1) 

the AA-internal call treats every one of those same outcomes as a fatal, unrecoverable condition and throws an uncaught `Error`, which is re-thrown by the global `uncaughtException` handler and crashes the node process: [3](#0-2) 

Because AA execution is fully deterministic and mandatory — every full node runs `handleAATriggers()` / `handleTrigger()` synchronously as part of `writer.saveJoint()`'s stabilization logic once the triggering unit becomes stable — any trigger crafted by an ordinary, unprivileged unit poster that causes the composed AA response to fall into one of these "impossible" branches (e.g. `ifTransientError` from `validateParents()`'s "last ball just advanced" branch, or `ifNeedParentUnits` due to a parent-picking edge case) will be executed identically, and crash identically and simultaneously, on every full node in the network at the same MCI: [4](#0-3) [5](#0-4) 

This mirrors the CVE's bug class: an internal component ("Partition"/AA execution engine) reaches an unexpected state on attacker-influenced but nominally valid input, and the server's response to that state is an unconditional crash rather than a handled error.

### Impact Explanation
If a trigger can be crafted to exercise one of these throw branches, every full node processing the stabilization of that MCI crashes with the same uncaught exception. Because stabilization is retried deterministically on node restart before other progress can occur, this can cause a repeatable crash loop across the network, preventing further main-chain stabilization — i.e., the network becomes unable to confirm new units, which is one of the accepted high-impact outcomes for this exercise.

### Likelihood Explanation
Reaching this is not guaranteed by simply posting any trigger — it requires finding an input that pushes the deterministic AA-response composition/validation into one of the "impossible" branches (`ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, or non-`good` sequence). This requires some AA/formula crafting skill, but no special privilege: any address can post a trigger to any AA. The likelihood is Medium because the exact triggering condition is not proven here, only the systemic design flaw (treat internal anomaly as fatal, unconditional `throw`) that removes the safety net network.js otherwise provides for externally validated joints.

### Recommendation
- Do not unconditionally `throw` on `ifJointError`, `ifTransientError`, `ifNeedHashTree`, and `ifNeedParentUnits` in `aa_composer.js`'s `validateAndSaveUnit()`. Instead, log full diagnostic context, bounce/fail the specific AA response instead of crashing the whole node, or at minimum ensure the failure is handled the same defensively as in `network.js`.
- Audit all reachable transient/joint/dependency error conditions in `validation.js` (e.g. `validateParents`'s "last ball just advanced" path) to confirm whether they are truly unreachable for internally-composed AA response units; add regression tests forcing each branch.
- Consider isolating AA response validation failures so a single AA's misbehavior cannot halt stabilization for the entire chain.

### Proof of Concept
Not reproduced end-to-end here; a concrete PoC would require constructing an AA whose deterministic response composition, when independently re-validated via `validateAndSaveUnit()`, lands in one of the `ifJointError`/`ifTransientError`/`ifNeedHashTree`/`ifNeedParentUnits` branches (e.g. via racing state during MC stabilization or via a nested/edge-case formula that produces a payload violating an invariant assumed safe by the composer). Given the index's coverage limits, deeper confirmation of an exact triggering formula would require running the code directly.
