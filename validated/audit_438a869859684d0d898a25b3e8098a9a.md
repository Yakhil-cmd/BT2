### Title
Spot-balance based price oracles in AAs can be atomically manipulated via `balance[address][asset]` and chained secondary triggers - (File: `formula/evaluation.js`, `aa_composer.js`)

### Summary
Obyte's oscript engine lets any Autonomous Agent (AA) read the live token/byte balance of *any other address*, including another AA, via the `balance[address][asset]` construct, and lets a single posted unit atomically trigger a chain of AAs (secondary triggers) that all execute or all bounce together. Any AA that derives a "price" from another AA's reserve ratio (the exact pattern shown and encouraged in the bundled reference AAs `uniswap_like_market_maker.oscript` and `fundraising_proxy.oscript`) is exposed to the same reserve/spot-price manipulation class described in the external report: an attacker can shift the reserve ratio and have the manipulated ratio consumed by a dependent AA within the same atomic unit, with no need for repayment because everything settles in one all-or-nothing operation.

### Finding Description
`formula/evaluation.js` implements the `balance` operator so any AA can query another address's asset balance directly and live: [1](#0-0) 

This is a documented, intended feature: the bundled reference AA `fundraising_proxy.oscript` uses `balance[$destination_aa][base]` — the balance of a *different* AA — as an input to its own economic logic: [2](#0-1) 

Similarly, the bundled `uniswap_like_market_maker.oscript` AA computes an exchange rate purely from its own instantaneous reserves (`balance[$asset]` / `balance[base]`), the same constant-product spot-price mechanism flagged as manipulable in the external Chainlink/MagicLpAggregator report: [3](#0-2) 

Crucially, `aa_composer.js` allows one posted unit to atomically drive a *chain* of AA triggers: after a primary AA sends a payment to another AA, that payment automatically fires a "secondary trigger" on the receiving AA, all within the same DB transaction/atomic unit, and if any AA in the chain bounces, the whole chain (and its balance changes) is reverted: [4](#0-3) [5](#0-4) 

Combining these two core capabilities, an attacker can, in a single unit:
1. Send a large swap to a reserve-based AMM/oracle AA, shifting its `balance[base]`/`balance[asset]` ratio.
2. In a chained/secondary message of the *same unit*, trigger a second AA (e.g., a lending, stablecoin, or fundraising AA) that reads the first AA's `balance[...][...]` as a price/valuation input and acts on it (issuing debt, minting an asset, releasing collateral, etc.).
3. Because everything is part of one atomic unit, if anything fails the whole thing reverts, and if it succeeds the attacker can unwind the price-shifting swap within the same or an immediately following bundle, extracting value without ever needing a real, revertible flash loan — the atomicity of unit/AA-chain execution provides the same guarantee.

This is the same root cause the external MagicLpAggregator report identifies (using instantaneous pool reserves as a price oracle, manipulable atomically), reproduced here as the core engine feature (`balance[address][asset]`, chained secondary triggers) that any AA author's design necessarily depends on. Nothing in `formula/validation.js` restricts how the balance value may be used, nor does the AA-chain mechanism impose any TWAP/staleness/cross-check constraint on economic AAs.

### Impact Explanation
Any AA (lending protocol, stablecoin, insurance/futures contract, DAO treasury proxy) built on top of another AA's `balance[...]`-derived exchange rate inherits this manipulation surface. An attacker who can post a single unit combining a manipulative swap and a value-extraction trigger can:
- Mint/borrow more of an asset than warranted by real market prices (supply inflation / AA fund loss), or
- Drain another AA's balance by triggering payouts computed off the manipulated ratio.
This matches the "unauthorized spending / supply inflation / AA fund loss" impact bar, since the underlying primitive (`balance[]` combined with atomic chained triggers) is a first-class, reachable capability of the ocore AA engine rather than a mistake confined to one contract.

### Likelihood Explanation
Any unprivileged unit poster can define and interact with AAs; no special privileges are required to compose a chain of payments/triggers in one unit, and `balance[address][asset]` is a normal, validated oscript primitive (`formula/validation.js` lines 748-780) available to every AA author. Because the reference implementations shipped with ocore (`uniswap_like_market_maker.oscript`, `fundraising_proxy.oscript`) explicitly model this exact reserve-based pricing pattern as best practice, real-world AAs are highly likely to replicate it, making exploitation practical whenever an economically significant AA reads another AA's live reserves as a price feed.

### Recommendation
- Document prominently (and, where feasible, warn at AA-validation time) that `balance[address][asset]` reflects the *current, atomically-manipulable* state of another AA and must not be used directly as a price oracle without TWAP, external data-feed cross-checks (`data_feed[[...]]`), or minimum-liquidity/deviation guards.
- Encourage/require economically sensitive reference AAs to compare `balance[]`-derived ratios against an independent `data_feed` oracle price and bounce if the deviation exceeds a safe threshold, mirroring the recommended mitigation in the external report.
- Consider adding an oscript primitive or convention for time-weighted/last-stable-balance snapshots so dependent AAs are not forced to rely on the pre-trigger instantaneous balance.

### Proof of Concept
1. Deploy an AMM-style AA identical to `test/samples/uniswap_like_market_maker.oscript`, holding asset X and bytes, whose "exchange asset to bytes"/"exchange bytes to asset" branches price trades purely from `balance[$asset]` and `balance[base]`.
2. Deploy a second, dependent AA (e.g., modeled like `test/samples/fundraising_proxy.oscript`) that reads `balance[$amm_aa][$asset]` / `balance[$amm_aa][base]` to value collateral or determine payout amounts.
3. Post a single unit containing: (a) a large payment to the AMM AA that swaps a large amount of bytes for asset X, sharply moving its `balance[]` ratio; (b) a payment/trigger to the dependent AA in the same unit, which via `aa_composer.js`'s secondary-trigger mechanism (`handleSecondaryTriggers`, `aa_composer.js:1702-1755`) executes atomically after step (a) and reads the now-manipulated ratio.
4. Observe the dependent AA compute an inflated/deflated valuation based on the manipulated `balance[]`, issuing more of an asset or releasing more collateral than the pre-manipulation market price would allow — all within one atomic, revert-safe unit (analogous test harness: `test/aa_composer.test.js:156-252` "chain of AAs").
