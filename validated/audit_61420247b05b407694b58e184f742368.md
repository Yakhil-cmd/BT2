### Title
Non-injective hashing of prosaic/arbiter contract fields allows two different contract offers to collide on the same `hash` identity - (File: prosaic_contract.js, arbiter_contract.js)

### Summary
`prosaic_contract.js` and `arbiter_contract.js` derive a contract's unique identity (`hash`, used as the primary lookup/merge key for the whole contract lifecycle) by concatenating variable-length, attacker/peer-controlled string fields with either no delimiter at all or with a fixed constant delimiter, and hashing the result. Because the field boundaries are not length-prefixed or otherwise unambiguously encoded, two structurally different contracts can produce byte-identical hash input, and therefore the identical `hash`. This is the same root-cause class as the Traefik advisory: a non-injective identity construction from concatenated fields lets a counterparty force an identity collision with someone else's object, silently overwriting/hijacking it (`maps.Copy`-equivalent here is `INSERT ... IGNORE`/`UPDATE ... WHERE hash=?`).

### Finding Description
`prosaic_contract.js` builds the contract hash with a bare string concatenation and no separator: [1](#0-0) 

```js
function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}
function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}
```

`title` and `text` are both attacker/peer-supplied free-text fields with no length restriction or reserved delimiter. Since `title + text` is literal string concatenation, any pair of strings `(title1, text1)` and `(title2, text2)` with `title1 + text1 === title2 + text2` (e.g. `title1="AB", text1="CD"` vs. `title2="ABC", text2="D"`) yields byte-identical input to SHA-256, hence an identical `hash`, for the same `creation_date`. No SHA-256 collision needs to be broken — the ambiguity is purely structural, exactly like the Traefik `%s-%s-...` key construction that ignored the fact that component values could themselves contain the delimiter.

`arbiter_contract.js` has the same defect, additionally showing the "old-format" fallback still uses bare concatenation with `join("")`: [2](#0-1) 

```js
const src = contract.creation_date > exports.NEW_HASH_DATE
	 ? [...].join(exports.DELIMITER)
	 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
```

Even the "fixed" branch that joins with `exports.DELIMITER = "[|#|]"` is not safe against collisions unless every field is proven never to contain that literal substring — `title`, `text`, and party names are free-form user text, so the delimiter can be embedded by a peer, again producing the classic "delimiter injection" identity collision (`"a[|#|]b"` vs. `"a", "[|#|]b"` boundary shift).

The resulting `hash` is used as the primary identity/merge key for the whole contract record:
- `createAndSend` computes `objContract.hash = getHash(objContract)` and stores it as the row key: [3](#0-2) 
- `store()` performs `INSERT ... IGNORE INTO prosaic_contracts (hash, ...)`, so if a row with a colliding `hash` already exists, the peer's new contract is silently discarded and the *existing* stale row is treated as canonical for that hash: [4](#0-3) 
- All later operations (`getByHash`, `setField`, `handleReceivedSharedAddress`, `handleReceivedSigningUnit`) key exclusively on `hash`, comparing it against `payload.contract_text_hash` from an incoming signed data message to authorize actions on the contract: [5](#0-4) 

Because the identity used everywhere downstream is the ambiguous `hash` rather than the actual `(title, text, creation_date)` tuple, a peer who controls one side of the negotiation can choose `title`/`text` values that collide with another contract's hash (their own earlier contract, or — if `creation_date` also matches — another party's contract), causing the wrong contract row/content to be treated as matching during `handleReceivedSigningUnit`'s hash check, or causing an `INSERT IGNORE` to silently swallow a distinct contract offer.

### Impact Explanation
The `hash` here plays the role of the "router identity" in the Traefik bug: it is the sole key by which `prosaic_contract.js`/`arbiter_contract.js` distinguish, merge, and authorize contract records exchanged between two paired devices (a private, off-chain agreement later anchored to the DAG via a `data` message with `contract_text_hash` and a shared multi-sig address). A counterparty (a device the victim has explicitly paired with — reachable, unprivileged relative to the wallet's on-chain assets) can:
- Force `store()`'s `INSERT IGNORE` to silently drop a legitimately distinct contract offer because its computed `hash` collides with a previously stored one, corrupting the victim's local contract state.
- Craft `title`/`text` so that `getHash()` matches a `contract_text_hash` supplied in a `data` message for a *different* actual contract, causing `handleReceivedSigningUnit` to accept a signing unit as authorizing/finalizing the wrong contract text, potentially completing/marking-as-signed a contract whose displayed terms do not match what was cryptographically hashed and referenced on-chain.

This does not directly enable unauthorized fund movement by itself (the shared address / multisig definition is still separately verified via `objectHash.getChash160`), but it breaks the integrity guarantee that `hash` uniquely identifies contract content — the same failure mode (non-injective identity → silent overwrite/misattribution) as the Traefik CVE, applied to prosaic/arbiter contract negotiation state rather than Gateway routes. Given the CWE-694 (non-injective identity) class match and the concrete corruption/misattribution of contract state between paired devices, this is a Medium-severity analog.

### Likelihood Explanation
Exploitation requires only that the attacker control one side of a paired-device contract negotiation (already an ordinary interaction available to any peer the wallet exchanges a pairing code with) and be able to choose the `title`/`text` free-text fields of the contract they send — no special privilege, network position, or cryptography-breaking capability is needed, only carefully chosen string boundaries. This mirrors the "AC:H" rating in the original advisory: the attacker needs favorable/contrived field values, but no elevated access.

### Recommendation
Replace ad hoc string concatenation with an unambiguous, length-prefixed or delimiter-escaped source-string construction (the codebase already has such a primitive in `string_utils.getSourceString`, which prefixes each component with its type and joins with the reserved `\x00` byte after rejecting fields containing that byte) for all identity-hash computations in `prosaic_contract.js` (`getHash`, `getHashV1`) and `arbiter_contract.js` (`getHashSrc`), instead of `title + text + creation_date` or `.join(DELIMITER)`/`.join("")` over untrusted free-text fields.

### Proof of Concept
1. Party A sends a prosaic contract offer with `title = "AB"`, `text = "CD"`, `creation_date = "2026-09-15 00:00:00"`.
   `hash1 = sha256("AB" + "CD" + "2026-09-15 00:00:00")`.
2. Party A (or a colluding second identity) later sends another offer with `title = "ABC"`, `text = "D"`, same `creation_date`.
   `hash2 = sha256("ABC" + "D" + "2026-09-15 00:00:00") = hash1` — identical hash despite different structured content, because `getHash()` in `prosaic_contract.js:98-100` concatenates without any separator.
3. When `store()` runs its `INSERT ... IGNORE INTO prosaic_contracts (hash, ...)` for the second offer (`prosaic_contract.js:55-70`), the row for `hash1` already exists, so the second, differently-worded contract is silently dropped, and any device querying `getByHash(hash1)` continues to see only the first contract's `title`/`text`, while a subsequently received `data` message referencing `contract_text_hash = hash1` cannot be distinguished as belonging to offer 1 vs. offer 2 in `handleReceivedSigningUnit` (`prosaic_contract.js:159-177`).

function store(objContract, cb) {
	var fields = '(hash, peer_address, peer_device_address, my_address, is_incoming, creation_date, ttl, status, title, text';
	var placeholders = '(?, ?, ?, ?, ?, ?, ?, ?, ?, ?';
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, true, objContract.creation_date, objContract.ttl, objContract.status || status_PENDING, objContract.title, objContract.text];
	if (objContract.shared_address) {
		fields += ', shared_address';
		placeholders += ', ?';
		values.push(objContract.shared_address);
	}
	fields += ')';
	placeholders += ')';
	db.query("INSERT "+db.getIgnore()+" INTO prosaic_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb)
			cb(res);
	});
}

function handleReceivedSigningUnit(contract, unit, retry_count = 0) {
	db.query("SELECT 1 FROM unit_authors WHERE unit=? AND address=?", [unit, contract.shared_address], async function (rows) {
		if (rows.length === 0) {
			if (retry_count >= 10)
				return console.log(`signing tx ${unit} not found in db after 10 retries, giving up`);
			console.log(`signing tx ${unit} not yet in db, waiting for 30 seconds and trying again`);
			return setTimeout(handleReceivedSigningUnit, 30000, contract, unit, retry_count + 1);
		}
		console.log(`signing tx ${unit} found in db, setting contract's unit`);
		const objUnit = await storage.readUnit(unit);
		const dataMessage = objUnit.messages.find(message => message.app === "data");
		if (!dataMessage)
			return console.log(`data message not found in purported prosaic signing unit ${unit}`);
		const { payload } = dataMessage;
		if (payload.contract_text_hash !== contract.hash)
			return console.log(`data message payload does not match contract ${contract.hash} in purported prosaic signing unit ${unit}`);
		setField(contract.hash, "unit", unit);
	});
}

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
