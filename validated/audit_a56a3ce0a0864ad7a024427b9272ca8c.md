### Title
Cross-organization Team hijack via `github_id`-only lookup in `MembershipHandler#find_or_create_team!` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves teams solely by the numeric `github_id` sent in the payload, without ever checking that the found `Team`'s `organization` column matches `params.organization.login` of the verified webhook. Because Shipit supports multi-tenant GitHub App configuration (each org with its own `webhook_secret`), a genuinely-signed `membership` webhook from an attacker-controlled organization (OrgB) naming a `team.id` that collides with a pre-existing `Team` row created for a trusted organization (OrgA) will be matched to OrgA's row, letting the attacker add arbitrary Shipit users to OrgA's authorized team.

### Finding Description
The broken binding is: `Team.find_or_create_by!(github_id: params.team.id).organization == params.organization.login`. This equality is **not enforced**. `find_or_create_by!` builds its `WHERE` clause only from `github_id:` [1](#0-0) ; the block that sets `team.organization = params.organization.login` only executes when a **new** record is being created (ActiveRecord semantics), never when an existing row matches `github_id`.

Path: `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1)  and calls `Shipit.github(organization: repository_owner)`, verifying the HMAC signature using that specific organization's `webhook_secret` [3](#0-2) . Shipit explicitly supports per-organization GitHub App credentials, each with its own `webhook_secret`, as documented under "Using Multiple GitHub Applications" [4](#0-3) . This means a signature that verifies as genuine for OrgB tells you only that the sender legitimately controls OrgB's App — it says nothing about OrgA.

`MembershipHandler#process` then calls `find_or_create_team!`, which finds (not creates) the pre-existing `Team` row whose `github_id` equals `params.team.id`, and calls `team.add_member(member)` [5](#0-4) . `Team#add_member` unconditionally appends the member to `members` [6](#0-5) . Since GitHub team IDs are a global namespace, an attacker who controls OrgB (and knows/guesses the numeric `github_id` of OrgA's Shipit-authorized team — discoverable via public team pages, enumeration, or leakage) can name that ID in a genuine, correctly-signed `membership`/`added` event from OrgB.

None of the existing guards catch this: `verify_signature` only proves the sender owns *some* configured org, not the org the `Team` row belongs to; `ExplicitParameters` only validates the shape/types of `team.id`, `organization.login`, etc., not their relationship to existing records [7](#0-6) ; there is no `require_permission!` or scoping by `organization` in `find_or_create_team!`.

### Impact Explanation
Successful exploitation lets an attacker with no Shipit privileges add an arbitrary Shipit `User` (including a user they control, or induce) as a member of a `Team` listed in `Shipit.github_teams`, directly flipping `User#authorized?` to `true` for that user [8](#0-7) . This is an authorization escalation into `Shipit.github_teams`, matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable for every distinct `github_id` an attacker can enumerate and for every additional member/login they wish to add, and it affects any tenant/organization whose `Team.github_id` an attacker-controlled org can collide with.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (documented, supported feature) or the attacker otherwise controlling a genuinely-registered org with its own `webhook_secret`; (2) knowledge of the target `Team`'s numeric `github_id` (obtainable via public team pages/enumeration, since GitHub team ids are small sequential integers and often discoverable); (3) ability to trigger a `membership` `added` event naming that id, which any org owner/admin can do by adding a user to any team in their own org (GitHub does not scope `team.id` uniqueness checks to the sender in Shipit). No Shipit secrets, sessions, or tokens are needed — only control of one's own GitHub organization and App installation, which is attacker-obtainable at zero privilege relative to Shipit.

### Recommendation
Scope the lookup in `find_or_create_team!` to the verified organization, e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, or explicitly re-verify `team.organization == params.organization.login` after find and raise/reject on mismatch instead of silently reusing the record.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook from a different organization cannot hijack an existing Team by github_id" do
  org_a_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1
  attacker_user = User.find_or_create_by_login!('attacker_controlled_user')

  payload = {
    action: 'added',
    team: { id: org_a_team.github_id, name: org_a_team.name, slug: org_a_team.slug, url: org_a_team.api_url },
    organization: { login: 'orgb' }, # attacker-owned org, genuinely signed
    member: { login: attacker_user.login }
  }

  # Signature verified against OrgB's own configured webhook_secret (multi-org support)
  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload.deep_stringify_keys)

  assert_equal 'shopify', org_a_team.reload.organization, "Team.organization must remain OrgA's"
  refute_includes org_a_team.members, attacker_user,
    "Attacker from OrgB must NOT be able to add a member to OrgA's authorized team by reusing github_id"
end
```
Currently, `assert_equal` passes but `refute_includes` **fails** — `attacker_user` is added to `org_a_team`, and if `org_a_team` is in `Shipit.github_teams`, `attacker_user.authorized?` becomes `true`, confirming the cross-tenant escalation.
