### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors due to `&&`/`||` precedence - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
Ruby's `&&` binds tighter than `||`, so `provision?` only gates the `allow_all` branch with `repository.review_stacks_enabled`. The `prevent_with_label` (and `allow_with_label`) disjuncts never check `review_stacks_enabled` at all, so an unprivileged PR author can trigger `ReviewStack` provisioning on a repository whose owner has explicitly disabled review stacks.

### Finding Description
The claimed binding is: `repository.review_stacks_enabled == true` must hold for any `ReviewStack` to be provisioned from a pull request. The code in [1](#0-0)  is:

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. If `repository.provisioning_behavior == 'prevent_with_label'` and `review_stacks_enabled == false`, the third disjunct `(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` evaluates purely on the PR's labels and is completely independent of `review_stacks_enabled`. Any PR opened without the configured provisioning label makes `provision?` return `true`, `respond_to_pull_request_opened?` returns `true` at [2](#0-1) , and `process` calls `ReviewStackAdapter#find_or_create!`, which calls `create!`, persisting a `Stack` with the attacker's branch and enqueuing it via `Shipit::ReviewStackProvisioningQueue.add(stack)` at [3](#0-2) .

No existing guard intercepts this: `params do ... end` only validates payload shape, not business rules; `verify_signature`/webhook auth (not shown here) only authenticates that GitHub sent the payload, not that the PR author is privileged — opening a PR is itself an unprivileged action available to any contributor/fork owner. The existing test suite does not catch this because its `prevent_with_label` test case at [4](#0-3)  never sets `provisioning_enabled: false`, leaving the `review_stacks_enabled`-off interaction with `prevent_with_label`/`allow_with_label` completely untested.

### Impact Explanation
An attacker who can open a pull request (fork owner/contributor) against a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` (or `allow_with_label`, by adding the label instead) can force Shipit to create and enqueue-for-provisioning a `Stack`/`ReviewStack` bound to their attacker-controlled branch, even though the repository owner explicitly opted out of review-stack automation. This is a write for a repository state (`Stack` record + provisioning queue entry) that should not exist per the repository's own configuration, and the provisioned stack's branch/environment (from the attacker's fork) then becomes subject to whatever provisioning/deploy tooling processes the queue — a payload-for-one-configuration mutating a config-protected resource. This matches the Critical category ("a payload...mutating another's stack" / "an unauthorized deploy") since it bypasses an explicit repository-level authorization gate (`review_stacks_enabled`) that operators rely on to prevent automatic provisioning.

### Likelihood Explanation
The only precondition is a repository configured with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — a plausible, legitimate configuration for teams that disabled review stacks broadly but left a prior label-based behavior set (these two settings are independent enum/boolean fields, not mutually validated, per `update_params` in [5](#0-4) ). Once that configuration exists, the attack is a single, repeatable, zero-cost action: open a PR (with or without a label depending on which behavior is set). It is repeatable against any number of PRs/branches on the same repository.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix this fails (`Stack.count` increases by 1) because `provision?` returns `true` regardless of `review_stacks_enabled == false`; after applying the recommended parenthesization it passes.
