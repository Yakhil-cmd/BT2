### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets any onboarded repository forge CI status on another stack's commit, defeating `MergeRequest#all_status_checks_passed?` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit for an incoming `status` webhook purely by `sha`, with no scoping to the repository/stack that the webhook actually belongs to. Any repository legitimately onboarded onto the same Shipit instance (attacker's own repo/fork, verified with its own webhook secret) can therefore write a `Status` row onto a `Commit` record belonging to an unrelated victim stack, as long as the sha matches — which is trivial to arrange by duplicating a public commit's exact content/metadata into an attacker-controlled fork rather than requiring an actual SHA-1 collision. That forged status is consumed unmodified by `MergeRequest::StatusChecker#success?` via `all_status_checks_passed?`, enabling an unauthorized `merge!` using the victim stack's `GITHUB_TOKEN`.

### Finding Description
The broken binding: `head.statuses` used by `MergeRequest#all_status_checks_passed?` (which calls `StatusChecker.new(head, head.statuses_and_check_runs, ...)` at [1](#0-0)  ) should equal exactly the set of statuses GitHub reported for that PR's head sha **within the same repository**. It does not, because the webhook ingestion path is not scoped by repository: [2](#0-1) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates over **every** `Commit` row across **every** stack whose `sha` column matches, with no `stack_id`/repository filter. `Commit#create_status_from_github!` then unconditionally appends the reported state to that commit's `statuses` association [3](#0-2) , which feeds `statuses_and_check_runs` [4](#0-3)  and is exactly what `all_status_checks_passed?`/`any_status_checks_failed?` in `MergeRequest` read.

`WebhooksController#verify_signature` only verifies that the payload's signature matches the GitHub App/secret configured for `repository_owner` taken from the payload itself [5](#0-4) . It authenticates *which org sent the webhook*, but nothing in `StatusHandler` re-checks that the sha being updated actually belongs to a commit that was fetched from that same repository/stack. An attacker who owns (or forks) any repository that is itself onboarded to the same Shipit installation can:
1. Fork victim-org/A's public repository (or otherwise reproduce byte-identical commit content/parent/author/committer/message/timestamps of the victim PR's head commit) into their own repo/stack B, yielding an identical git sha without needing a cryptographic collision.
2. Trigger a real, correctly-signed `status` webhook from their own repo B (e.g. via GitHub's API/UI on their own commit) with `state: success` and a `context` matching one of stack A's `merge_request_required_statuses`.
3. Because `StatusHandler` matches by sha only, this legitimately-signed webhook for repo B also creates a `Status` row on stack A's `Commit` for the victim PR's real head sha.
4. `ProcessMergeRequestsJob`'s revalidation reads `all_status_checks_passed?` as true (or `any_status_checks_failed?` as false) for stack A's merge request, calls `reject_unless_mergeable!` (no rejection) and then `merge!`, which calls `stack.github_api.merge_pull_request` [6](#0-5)  using **stack A's** `GITHUB_TOKEN`, merging the PR before or regardless of whether GitHub itself ever reports a real passing/failing status for that context on repo A.

Existing guards do not prevent this: `verify_signature` authenticates the sender org but not the sha/commit ownership; `ExplicitParameters` on `StatusHandler` only validates payload shape, not repository scoping; there is no `stack_id`/`repository` filter anywhere in the `Commit.where(sha: params.sha)` lookup.

### Impact Explanation
This is a cross-tenant confused-deputy: a webhook that is entirely legitimate for repository B is used to mutate CI status state for an unrelated repository A's commit, causing `Shipit::MergeRequest#merge!` to execute `stack.github_api.merge_pull_request` with stack A's `GITHUB_TOKEN` — an unauthorized merge into a repository the attacker never authenticated against. This matches the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). It is repeatable against any stack with `merge_queue_enabled` whenever an attacker can get a sha match (trivial via forking public repos), and it also affects `continuous_deployment?`/`deployable?` paths since `Commit#deployable?` and `schedule_continuous_delivery` depend on the same polluted `status` [7](#0-6) , so the blast radius extends beyond merge queues to auto-deploys as well.

### Likelihood Explanation
Requires: (a) the Shipit instance hosts multiple independently-onboarded repositories/orgs (typical for a shared/SaaS-style Shipit deployment), (b) `merge_queue_enabled` on the victim stack, (c) attacker controls at least one onboarded repo/fork capable of emitting a legitimately-signed webhook (explicitly listed as an attacker capability), and (d) the ability to produce a commit with an identical sha to the victim's PR head — achievable without any cryptographic collision by replaying identical patch content/metadata into a fork sharing history with the victim repo. No secrets, sessions, or privileged roles are needed. This is a config-independent code defect (missing scoping), not a rare timing coincidence, making it reliably repeatable.

### Recommendation
Scope the webhook-to-commit resolution by repository, not sha alone. In `StatusHandler#process`, join through the owning `Stack`'s `repository` (matching `params.dig('repository', 'full_name')` against `stack.repository.full_name`) before applying `create_status_from_github!`, e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository: repo_from_payload }).each { ... }`. Apply the same repository-scoping check anywhere else commits are resolved solely by sha from webhook input.

### Proof of Concept
Minitest plan (no live GitHub, using fixtures/Mocha):
1. Create two stacks, `stack_a` (victim) and `stack_b` (attacker), each with a `Commit` row sharing the identical `sha` value (simulating the forked/duplicated commit).
2. Build a `Shipit::MergeRequest` on `stack_a` whose `head` is `stack_a`'s commit, with `merge_status: 'pending'` and `stack_a.cached_deploy_spec` requiring a status context `"ci"`.
3. Simulate the attacker's webhook for `stack_b` by invoking `Shipit::Webhooks::Handlers::StatusHandler.new.call(sha: shared_sha, state: 'success', context: 'ci', ...)` — bypassing `verify_signature` since it is a unit test of the handler, representing an already-validated payload for repo B.
4. Assert: `stack_a.commits.find_by(sha: shared_sha).statuses.count` increased and `merge_request.all_status_checks_passed?` returns `true` — proving `Commit.where(sha:)` in `status_handler.rb` line 21 applied repo B's status to repo A's commit, i.e. the equality `head.statuses (stack A) == statuses reported by GitHub for stack A's repo` is broken.
5. Mock `stack_a.github_api.merge_pull_request` with a Mocha `expects` and call `merge_request.merge!`; assert the mock is invoked, proving an unauthorized merge is triggered using `stack_a`'s credentials solely due to the cross-repo forged status.
