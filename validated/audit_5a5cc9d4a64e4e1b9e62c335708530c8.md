### Title
Unsolicited `my_xpubkey` device message accepted from non-correspondents lets an attacker impersonate/hijack a multisig wallet co-signer - (File: `wallet.js`, `wallet_defined_by_keys.js`)

### Summary
The matrix-android-sdk2 flaw was that key-forwarding messages were accepted from any sender, including devices that were never verified or that weren't responding to a request, letting an attacker impersonate the true author of a message. Ocore has a structurally analogous trust gap in its device-messaging layer: the `my_xpubkey` and `wallet_fully_approved` message subjects are explicitly whitelisted to be accepted **from non-correspondents** (unpaired, unverified devices) at [1](#0-0) , and the handlers for those subjects write attacker-supplied key material into the `extended_pubkeys` table keyed only by an attacker-chosen `wallet` id and the sender's self-derived `device_address`, with no check that the sender was actually invited as a cosigner of that wallet.

### Finding Description
When a `hub/message` arrives, `device.js` only verifies that the message is correctly signed by the claimed `pubkey` and that the encrypted `from` matches the signing pubkey [2](#0-1) . That proves the message really came from the device owning that pubkey, but it does **not** prove that device is who the receiver expects for the given exchange. When the sender is not a known correspondent, only a short whitelist of subjects is allowed through: `pairing`, `my_xpubkey`, `wallet_fully_approved` [1](#0-0) .

In `wallet.js`, the `my_xpubkey` case is explicitly commented "allowed from non-correspondents" and passes the caller-supplied `wallet` id and `body.my_xpubkey` straight into `walletDefinedByKeys.addDeviceXPubKey` [3](#0-2) .

`addDeviceXPubKey` performs an unconditional upsert into `extended_pubkeys` for `(wallet, device_address)`, sets `approval_date`, and — if this happens to complete the required cosigner set — triggers `checkAndFullyApproveWallet`, which is the step that finalizes which pubkeys form the multisig/shared address: [4](#0-3) .

There is no verification that:
- the sender device address is one of the addresses actually listed in `body.other_cosigners`/`arrWalletDefinitionTemplate` of the original `create_new_wallet` offer, or
- a `create_new_wallet` handshake for that `wallet` id was even initiated with this sender.

Compare this to the analogous `create_new_wallet` path, `handleOfferToCreateNewWallet`, which *does* cross-check that the offering device's declared `other_cosigners` list matches the wallet-definition template's derived device addresses before accepting anything [5](#0-4) . No equivalent binding check exists for `my_xpubkey`/`wallet_fully_approved`, which are reachable by design from unpaired devices.

Because the wallet's address is `chash160(definition)` and the definition embeds each cosigner's device address (`'$pubkey@'+device_address` template, resolved later to `extended_pubkey`), whichever xpubkey ends up recorded for a given `device_address` in `extended_pubkeys` becomes part of the final multisig/shared address definition. An attacker who can observe or guess the `wallet` id (the sha256 hash of the initiator's xpubkey, transmitted in the `create_new_wallet` offer to the intended cosigners, and also echoed back by legitimate cosigners in later `my_xpubkey`/`wallet_fully_approved` messages) can race to insert or overwrite the `extended_pubkey` value for a `device_address` before the legitimate cosigner's key is confirmed, since the code performs `INSERT OR IGNORE` followed by an unconditional `UPDATE ... approval_date=now()` regardless of whether that device_address's key was already approved.

### Impact Explanation
If an attacker can inject or race a bogus `extended_pubkey` value for a cosigner slot of a shared/multisig address before the legitimate cosigner's key is recorded, the resulting shared address definition (`["r of set", {set: [...]}]` combined into a chash160 address) will incorporate the attacker's key instead of the rightful cosigner's key. Funds subsequently sent to that shared address could then be spent unilaterally or with attacker cooperation, i.e., unauthorized spending / fund loss from a shared/multisig address — matching the "concrete unauthorized spending... AA fund loss" bar required by the validation rules. This is a direct analog of the "impersonation" root cause in the referenced advisory: key material is accepted from an unauthenticated/unrequested party and trusted to represent a legitimate participant in an ongoing cryptographic exchange, without the receiving code confirming that the sender was actually solicited for this exchange or slot.

### Likelihood Explanation
Exploitation requires the attacker to learn the `wallet` id (a 32-byte hash, transmitted in E2E-encrypted device messages) and to win a race with the legitimate cosigner's own `my_xpubkey`/`wallet_fully_approved` message before the wallet is finalized. This significantly limits the practical likelihood versus the original matrix bug (which required no id-guessing), but the missing authorization check is a genuine, root-cause-verifiable defect: the code path is reachable from any device address (paired or not) that can reach the target's hub/websocket layer and supply a matching `wallet` id, and no cryptographic binding ties the accepted `my_xpubkey` to the specific handshake that was actually offered to that device.

### Recommendation
Require that `my_xpubkey` and `wallet_fully_approved` only be accepted for `(wallet, device_address)` pairs that were explicitly recorded as expected cosigners at the time `create_new_wallet`/`approveWallet` was processed (i.e., check that a row already exists in `extended_pubkeys` for that `wallet`+`device_address` from the legitimate offer/approval flow, and reject or ignore unsolicited inserts of new `device_address` rows for a wallet from unpaired devices). Additionally, once an `extended_pubkey`/`approval_date` for a `(wallet, device_address)` pair has been set, subsequent `my_xpubkey` messages for the same pair should be rejected rather than silently overwritten, closing the race-condition overwrite window.

### Proof of Concept
1. Attacker device (not a correspondent of Victim) learns/obtains a `wallet` id that Victim is in the process of setting up as a multisig cosigner with intended cosigner device `D` (e.g., by compromising or racing `D`, or observing the value via any leak of the `create_new_wallet`/`my_xpubkey` exchange).
2. Attacker sends a signed `hub/message` to Victim's hub with `subject: "my_xpubkey"`, `body: {wallet: <target wallet id>, my_xpubkey: <attacker's own xpubkey>}`, using the attacker's own device pubkey.
3. Victim's `device.js` accepts the message because `my_xpubkey` is whitelisted for non-correspondents [1](#0-0) .
4. `wallet.js` forwards it to `walletDefinedByKeys.addDeviceXPubKey(wallet, attacker_device_address, attacker_xpubkey, ...)` [6](#0-5) .
5. `addDeviceXPubKey` inserts/updates `extended_pubkeys` for `(wallet, attacker_device_address)` and, if the intended device_address slot for cosigner `D` in the wallet template equals the attacker's device_address (or if the attacker's message races/overwrites before `D`'s legitimate message lands), `checkAndFullyApproveWallet` finalizes the shared address using the attacker's key [4](#0-3) .
6. Funds later sent to the resulting shared/multisig address can be spent using the attacker's key as one of the required signers.

function addDeviceXPubKey(wallet, device_address, xPubKey, onDone){
	db.query(
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],
		function(){
			db.query(
				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[xPubKey, wallet, device_address],
				function(){
					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}
			);
		}
	);
}
