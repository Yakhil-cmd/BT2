### Title
`claim-staker-rewards-for-signer` skips `settle-rewards`, letting a malicious signer permanently zero staker rewards against a stale `signer-rewards-per-token-for-cycle` snapshot - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`claim-staker-rewards-for-signer` calls `settle-staker-rewards` directly without first refreshing the signer's `signer-rewards-per-token-for-cycle` snapshot via `settle-rewards`, unlike every other staking-mutation path in the contract. A signer (i.e. the attacker's own registered `signer-manager` contract, which is `contract-caller`) can invoke this on a staker who staked under it before ever calling `claim-rewards`/`settle-rewards` for that cycle, causing `earned` to be computed against a stale/default rewards-per-token rate and the staker's true balance to be zeroed via `map-set staker-unclaimed-rewards-for-cycle`.

### Finding Description
The broken equality: sBTC that should be claimable by `staker` for `(signer, reward-cycle, bond-index)` — i.e. `compute-earned-rewards(shares, get-rewards-per-token-for-cycle(reward-cycle, bond-index), rpt-paid, pending)` — must equal the amount actually recorded in `staker-unclaimed-rewards-for-cycle` before it is zeroed out.

Code path:
- `settle-rewards` (pox-5.clar:2530-2574) is the only function that refreshes the per-signer snapshot map `signer-rewards-per-token-for-cycle` from the true, live rate `get-rewards-per-token-for-cycle`: [1](#0-0)  and [2](#0-1) .
- `settle-staker-rewards` (pox-5.clar:2581-2614) computes the staker's `earned` using `get-signer-rewards-per-token-for-cycle` — the *snapshot*, not the live rate — and then immediately persists it as the settled rate: [3](#0-2) .
- `claim-staker-rewards-for-signer` (pox-5.clar:2444-2470) calls `settle-staker-rewards` directly, with **no preceding call to `settle-rewards`**, and then permanently zeroes the staker's pending balance: [4](#0-3) .
- Every other state-mutating flow in the contract enforces the opposite order — e.g. `update-bond` explicitly calls `settle-rewards` for both signers *before* calling `settle-staker-rewards`: [5](#0-4) , and `add-staker-to-signer-for-cycle` does the same: [6](#0-5) . `claim-rewards` itself refreshes the snapshot through `update-claimable-rewards` → `settle-rewards` before any payout logic runs: [7](#0-6) .

Attacker's exact call and exploit flow:
1. Attacker deploys a `signer-manager` contract and registers it as `signer` (standard, permissionless onboarding flow used by every signer, e.g. `register-signer` referenced in `test-pox-5-signer.clar:33-37`).
2. A staker locks/delegates funds against that signer for `reward-cycle`; the reward-cycle ends and sBTC rewards are distributed to pox-5 for that signer/bond, so `get-rewards-per-token-for-cycle` for the cycle is now non-zero/true-rate.
3. The signer never calls `claim-rewards` (and no other staking mutation touched this signer for this `reward-cycle`/`bond-index`), so `signer-rewards-per-token-for-cycle` for that key remains at its stale/default value.
4. Attacker's `signer-manager` (as `contract-caller`) calls `claim-staker-rewards-for-signer(staker, reward-cycle, bond-index)` directly against pox-5 (or via the `claim-staker-rewards` wrapper shown in `signer-manager.clar:228-238` / `test-pox-5-signer.clar:59-67`).
5. `settle-staker-rewards` computes `earned` from the stale snapshot rate (understated versus the true rate), writes that understated value into `staker-unclaimed-rewards-for-cycle`, and `claim-staker-rewards-for-signer` then unconditionally `map-set`s that entry to `u0` — discarding even the understated amount.
6. No later call can recover the difference: once `staker-rewards-per-token-settled-for-cycle` is advanced to the stale rate and `staker-unclaimed-rewards-for-cycle` is `u0`, the staker's true accrued share for that cycle/bond-index is permanently unreachable — the sBTC was distributed to pox-5 but never credited to `staker-unclaimed-rewards-for-cycle` at the correct amount, and `claim-rewards` for the signer subsequently pulls the whole cycle's remaining sBTC through `update-claimable-rewards`, letting the signer capture the delta instead.

`validate-no-reentrancy` (called *after* the state mutation) only guards against reentrant signer-manager trait calls and does not validate the rate; `verify-not-prepare-phase` is not invoked at all in this function; none of the existing guards check that `settle-rewards` was executed for the current true rate before `settle-staker-rewards` runs.

### Impact Explanation
The staker's sBTC reward entitlement for `(signer, reward-cycle, bond-index)` is permanently frozen/lost (recorded amount < true entitlement, and then zeroed), while the excess sBTC remains claimable by the signer through the normal `claim-rewards` path. This is a permanent freezing of a staker's already-distributed sBTC rewards, matching the Critical severity bucket ("permanent freezing of staked STX or sBTC"). Any signer (including an attacker-controlled one) can repeat this for every staker under it and for every cycle/bond-index it never explicitly settles, at zero cost beyond a single contract call.

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: deploying a `signer-manager` contract and registering as a signer is permissionless; the only external dependency is that at least one staker chooses to stake/delegate under that signer and that a reward cycle completes with sBTC distributed. The attacker does not need to be the bond admin, pause admin, or hold any privileged role — they only need to be the signer/signer-manager operator, which any unprivileged account can become. The bug is deterministic (skipping `settle-rewards` is the default, cheapest path) and repeatable across every cycle/bond-index the signer chooses not to settle first.

### Recommendation
In `claim-staker-rewards-for-signer`, call `settle-rewards contract-caller reward-cycle bond-index` to refresh `signer-rewards-per-token-for-cycle` to the current true rate before invoking `settle-staker-rewards`, mirroring the ordering already used in `update-bond` and `add-staker-to-signer-for-cycle`.

### Proof of Concept
Integration test plan (Rust, extending `stacks-node/src/tests/pox_5_integrations.rs` style harness):
1. Register attacker's `signer-manager` contract as `signer` via `grant-signer-key`/`register-signer`.
2. Have `staker` stake/delegate to `signer` for `reward-cycle` via the normal staking entry point, producing non-zero `staker-shares-staked-for-cycle`.
3. Advance past `reward-cycle` and distribute sBTC to the pox-5 contract for that cycle (so `get-rewards-per-token-for-cycle(reward-cycle, bond-index)` > 0).
4. Do **not** call `claim-rewards` (or any other mutating entry point) for `signer`/`reward-cycle`/`bond-index`, leaving `signer-rewards-per-token-for-cycle` at its default value.
5. Compute `true_earned = compute-earned-rewards(shares, get-rewards-per-token-for-cycle(reward-cycle, bond-index), rpt-paid=0, pending=0)`.
6. Call `get-earned-staker-rewards(signer, reward-cycle, bond-index, staker)` — assert it returns `stale_earned < true_earned` (or `0` if the snapshot default is `0`).
7. Call `claim-staker-rewards-for-signer(staker, reward-cycle, bond-index)` as `contract-caller = signer`.
8. Assert `staker-unclaimed-rewards-for-cycle` for the key is now `u0`.
9. Assert `stale_earned != true_earned`, proving sBTC distributed for the staker's share was not credited/claimable and is now permanently unreachable via this path.
