### Title
StatusHandler#process resolves `Commit.where(sha:)` without scoping to the verified repository, letting `Status.replicate_from_github!` write rows into a foreign stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` globally across the entire Shipit database instead of using the `stacks` helper (scoped to `repository_name` from the payload) that other handlers such as `push_handler.rb` and the `pull_request/*` handlers rely on. Any commit sharing that SHA in a different, unrelated stack gets `commit.create_status_from_github!(params)` invoked on it, which calls `Status.replicate_from_github!(commit.stack_id, github_status)` and inserts a `Status` row into that foreign stack using attacker-supplied `state`/`description`/`target_url`/`context` values.

### Finding Description
The broken binding: the code assumes `stack_id used in replicate_from_github! == stack_id of the organization that verified the webhook` for every commit touched during `process`. In reality, `stack_id` is `commit.stack_id`, taken from whichever `Commit` row(s) happen to match `params.sha`, with no relation to `repository_owner`/`repository_name` from the verified payload.

Code path: `WebhooksController#create` → `verify_signature` (validates only that the payload's `repository_owner` organization's webhook secret matches — i.e., that the request genuinely originates from that organization's own GitHub App/webhook config) → `Shipit::Webhooks.for_event(event)` dispatch → `StatusHandler.call(params)` → `StatusHandler#process`: [1](#0-0) 
which does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, unlike `Handler#stacks`, which scopes lookups via `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 
`Commit#create_status_from_github!` then does: [3](#0-2) 
and `Status.replicate_from_github!` writes a row scoped to whatever `stack_id` it's handed: [4](#0-3) 

`verify_signature` only proves the request came from the organization named in the payload's own `repository.owner.login`; it says nothing about which `Commit`/`Stack` rows in Shipit's database should be touched: [5](#0-4) 

Root cause: `StatusHandler#process` fails to filter `Commit.where(sha:)` by the stacks belonging to the verified repository, so if a git commit SHA happens to exist in `Commit` rows for two different stacks (e.g., a public upstream repo and any fork/derivative registered as its own Shipit stack, or any two stacks that legitimately share commit history), a status webhook signed by one organization writes into the other organization's `Status` table.

Exploit flow: attacker owns/administers a repository (e.g., a public fork sharing history with a victim's tracked repo) that is itself registered as a Shipit stack, or simply controls a repo whose commit history overlaps a victim stack's commit SHAs. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own organization, and `sha` equal to a SHA present in the victim's `Commit` table. `StatusHandler#process` iterates every `Commit` with that SHA regardless of stack, and creates a `Status` row for the victim's stack with attacker-controlled `state`, `description`, `target_url`, `context`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) authenticate that the *organization* sending the request is legitimate for the *payload's declared repository*, but they never constrain which `Commit`/`Stack` rows the handler is allowed to mutate — the `stacks`/`repository_name` scoping mechanism exists in `Handler` but `StatusHandler` doesn't use it.

### Impact Explanation
A payload authenticated for one repository/organization causes a database write (`Status` row insertion) scoped to another tenant's stack — this is a cross-tenant write with attacker-controlled content (`state`, `description`, `target_url`, `context`), matching the "Critical" category ("a payload for one repository mutating another's stack, commit, task or team"). Since `Status` states drive `deployable?`/CI gating (`blocked?`, `blocking_statuses`) and trigger `enable_ci_on_stack`, `schedule_continuous_delivery`, and `MergeRequests` jobs, injected statuses (e.g., forging a `success` CI status) can influence deploy/merge decisions on the victim stack. This is repeatable against any pair of stacks that share a commit SHA.

### Likelihood Explanation
Requires the precondition that `Commit.where(sha:)` returns rows in more than one stack for the same SHA — this occurs naturally for forks/mirrors of the same upstream repository (identical commit objects preserve identical SHA1 across clones/forks) when both the upstream and a fork are tracked as separate Shipit stacks, or more generally whenever two tracked stacks share commit history. The attacker needs no Shipit credentials — only control of a GitHub organization/repo that is registered as a Shipit stack and whose commit history intersects the target's. This is a real, low-cost attack for any Shipit deployment tracking both an upstream project and forks/mirrors of it (common in open-source CI/CD setups).

### Recommendation
Scope `StatusHandler#process` (and similarly audit `CheckRunHandler`/other handlers relying on raw SHA lookups) to only the `Commit` rows belonging to `stacks` derived from the verified `repository_name`, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
using the existing `Handler#stacks`/`repository_name` helper, mirroring the pattern already used by `push_handler.rb` and the `pull_request/*` handlers.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar, though `test/**` is out of scope for this audit per the rules — described conceptually):
1. Create `attacker_stack` (repo `attacker/repo`) and `victim_stack` (repo `victim/repo`), each with a `Commit` row sharing the identical `sha` (simulating shared history/fork).
2. Build a `status` webhook payload with `repository.owner.login` = attacker's org, `sha` = shared sha, `state: 'success'`.
3. Assert before: `Status.where(stack_id: victim_stack.id).count == 0`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing signature verification as it's legitimately signed by attacker's own org secret in a full webhook POST test).
5. Assert after: `Status.where(stack_id: victim_stack.id).count == 1`, and the new row's `state`/`description`/`context` match attacker-supplied payload values — proving the equality `stack_id used == stack_id of verified organization` is violated for the victim commit.
