### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, exposing any stack's deploy status to a stack-scoped token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` lookup helper with a version that ignores the `ApiClient`'s `stack_id` scoping, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
`Shipit::Api::BaseController` enforces per-token stack scoping through two cooperating methods: `stacks`, which restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack`, which resolves `params[:stack_id]` only within that restricted set via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`Shipit::Api::CCMenuController` however redefines `stack` to resolve directly against the entire `Stack` table, completely bypassing the `stacks` scoping method and therefore the `current_api_client.stack_id` restriction: [2](#0-1) 

The controller only checks a coarse-grained permission string (`read:stack`) via `require_permission :read, :stack`, which is enforced by `ApiClient#check_permissions!` — this only verifies the client has the `read:stack` permission somewhere in its `permissions` array; it says nothing about which specific stack the token is scoped to: [3](#0-2) [4](#0-3) 

An `ApiClient` can legitimately be scoped to a single stack via its `stack` association/`stack_id` column (as seen in the `here_come_the_walrus` fixture, which is `stack: shipit` with only `read:stack`), and this scoping is explicitly relied upon elsewhere in the API layer (e.g. `Api::BaseController#stacks` and its use in the stacks index/show actions). [5](#0-4) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, any token carrying `read:stack` — including one deliberately restricted to a single stack — can query the CCMenu status/deploy-output summary of *any* stack in the installation simply by changing `params[:stack_id]` (or `stack_id` in the `/ccmenu/*stack_id` route), regardless of the `stack_id` binding baked into the token when it was minted.

This is exactly the class of bug the external report describes at a structural level: a helper re-implements interaction with a resource (here, stack lookup/authorization) using an interface/contract that no longer matches — and effectively drops — the check present in the canonical implementation, causing the "verified" scoping to silently not apply.

### Impact Explanation
This allows a holder of any `read:stack`-permitted token — even one that was explicitly and deliberately scoped by an administrator to a single non-sensitive stack — to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, activity, lock state, etc., rendered via the `shipit/ccmenu/project` view) for every stack managed by the Shipit instance. This is an unauthenticated-for-that-resource read of stack state across repository boundaries, matching the "High — unauthorized/escalated read of stack state" impact bucket. It does not itself allow writes, deploys, or credential exfiltration, so it is bounded to information disclosure of deploy status metadata across stacks the token was not meant to see.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (a documented, first-class feature — `ApiClient belongs_to :stack, optional: true`) and also exposes the CCMenu endpoint (`scope '/ccmenu/*stack_id'` in `config/routes.rb`, a documented CI-status integration feature). No special privilege beyond possessing any valid `read:stack` token is required, and the exploit is a single GET request with a different `stack_id` value. [6](#0-5) 

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController`, or reimplement it to route through the base `stacks`/scoped lookup (e.g. `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient`'s `stack_id` is enforced the same way it is in `Api::BaseController`.

### Proof of Concept
1. As an administrator, create an `ApiClient` scoped to `stack_id: A` with only the `read:stack` permission (mirrors the `here_come_the_walrus` fixture). [5](#0-4) 
2. Using that client's `authentication_token`, issue `GET /ccmenu/*stack_id_of_B` (a different, unrelated stack `B`) either via the `Authorization: Basic` header or `?token=` query param supported by `CCMenuController#authenticate_api_client`. [7](#0-6) 
3. The request succeeds and returns stack `B`'s deploy/build status because `stack` resolves `Stack.from_param!(params[:stack_id])` against the whole table, unfiltered by `current_api_client.stack_id`, unlike `Api::BaseController#stack`, which would have restricted the client to stack `A` only. [8](#0-7)
