### Title
Node crash via uncaught `throw Error` when a private divisible-asset payment chain is replayed - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain()` performs a duplicate-check SQL query before delegating to the asset-specific saver. For non-fixed-denomination (divisible) private assets, this duplicate-check query is not filtered by `output_index`, so once a payment message with more than one output (e.g. a recipient output plus a change output) has been saved, replaying/resending the same private-payment chain causes the duplicate-check query to return more than one row, which trips an unconditional `throw Error(...)` inside a raw `db.query` callback. Because this throw happens outside any try/catch and is not routed through the `ifError` callback, it becomes an uncaught exception that is caught by the global `process.on('uncaughtException', ...)` handler in `network.js`, which deliberately re-throws to crash the whole node process.

### Finding Description
The duplicate check lives in `validateAndSavePrivatePaymentChain`: [1](#0-0) 

For divisible (non-fixed-denomination) private assets, the `output_index` filter is only added when `objAsset.fixed_denominations` is true: [2](#0-1) 

This means for divisible private assets the SELECT matches every output row already saved for that `(unit, asset, message_index)`, regardless of `output_index`. The first time a chain for that message is validated and accepted, `divisible_asset.js`'s saver inserts a row for **every** output in `payload.outputs` (recipient output, change output, etc.) in one shot, because divisible private payments must reveal `address` and `blinding` for all outputs up front (enforced in `validation.js`): [3](#0-2) [4](#0-3) 

Consequently, once that first save completes, the `outputs` table already contains ≥2 rows for that `message_index`. If the very same (or any of the sibling) chain(s) for that message is submitted again — a normal occurrence given that the protocol legitimately sends the recipient chain and the cosigner/change chain as separate messages, and a malicious or buggy counterparty can trivially resend one of them — the duplicate-check query now returns more than 1 row, hitting:

```js
if (rows.length > 1)
    throw Error("more than one output "+sql+' '+params.join(', '));
```

This `throw` occurs inside the `db.query` result callback, not inside the `validateAndSave` promise chain's try/catch, so it propagates as an uncaught exception. `network.js` installs a global handler that intentionally crashes the process on any uncaught exception to avoid running with inconsistent state: [5](#0-4) 

### Impact Explanation
This is reachable by an ordinary private-payment counterparty (a wallet peer, hub-mediated device, or the sender itself resending a message) through the standard private-payment delivery paths:
- `wallet.js`'s `handlePrivatePaymentChains` (message from a hub/peer device) which forwards individual chains to `network.handleOnlinePrivatePayment`: [6](#0-5) 
- `network.js`'s `handleOnlinePrivatePayment`, which calls `privatePayment.validateAndSavePrivatePaymentChain` once the underlying unit is known: [7](#0-6) 

A crafted or accidental resend of an already-accepted divisible private payment message (one that has more than one output) crashes the receiving node/wallet/hub process — a denial-of-service that halts that node's ability to process/confirm any further units until it is restarted, directly analogous to the BIND DNS64 assertion-failure crash in CVE-2017-3136 (a crafted, protocol-conformant input triggers an internal invariant check that terminates the process).

### Likelihood Explanation
No special privileges are required beyond being a normal private-payment counterparty (recipient, cosigner, or device relaying a private chain via a hub). Resending an already-processed chain is a low-effort action (network hiccups, a misbehaving hub, or a deliberately malicious peer can trigger it), and the in-memory `handledChainsCache` in `wallet.js` only dedupes by the hash of the exact same `arrChains` array sent together — sending the recipient's chain and the cosigner/change chain as two separate deliveries (which is the documented normal flow) or resending only one of them again bypasses that cache and reaches the vulnerable code path.

### Recommendation
In `private_payment.js`, make the duplicate-check query for divisible private assets also disambiguate correctly (e.g. match against the specific output being validated, or `LIMIT`/aggregate rather than assuming exact cardinality), and replace the unconditional `throw Error("more than one output...")` with a call to `transaction_callbacks.ifError(...)` so malformed/duplicate input degrades to a validation error instead of crashing the process.

### Proof of Concept
1. Two wallets complete a divisible private-asset payment where the payment message has 2 outputs (recipient output + change output), so the `outputs` table ends up with 2 rows for that `(unit, message_index)` at the recipient's node.
2. The counterparty (or a compromised hub) resends the previously delivered private-payment chain (either the exact same head element again, or the sibling cosigner/change chain that references the same `unit`/`message_index`) to the same wallet/hub via `handlePrivatePaymentChains` → `handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`.
3. The duplicate-check `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` (no `output_index` filter, since the asset is not fixed-denomination) returns 2 rows.
4. `rows.length > 1` is true, so `throw Error("more than one output ...")` executes inside the `db.query` callback, becomes an uncaught exception, and `process.on('uncaughtException')` in `network.js` re-throws it, crashing the victim's node process.
