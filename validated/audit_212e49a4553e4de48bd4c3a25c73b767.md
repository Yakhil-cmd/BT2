Confirmed: there is no persistent, global map recording L1 BTC lockup outpoints already credited to a staker. `validate-l1-lockup`'s duplicate check only walks `seen-outpoints`, an accumulator that is initialized fresh to `(list)` on every call to `verify-l1-lockups` [1](#0-0) , and is discarded once `register-for-bond` returns [2](#0-1) . This is the direct analog to the reported bug class: attacker/staker-controlled data (a Bitcoin outpoint + merkle proof) is validated for well-formedness but the *scope* of that validation (rejecting reuse) is not enforced against any persistent state, so the same "path" (outpoint) can be reused across calls the same way the report's traversal payload escaped its intended directory boundary because the destination wasn't checked against a durable base.

### Title
Unbounded reuse of the same L1 BTC lockup outpoint across multiple `register-for-bond` calls double-counts sats credit - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path computes `sats-total` via `verify-l1-lockups` → `validate-l1-lockup`, which checks that a Bitcoin output pays the staker's committed timelock script, has the right amount, and is not repeated *within the same call's list of outputs*. It does not check the outpoint against any contract-wide "already-consumed" ledger. Because `sats-total` gates `sats-total <= allowance` and the staker's bond-signer weight/allowance, a staker can present the exact same already-broadcast L1 lockup transaction to `register-for-bond` again — after unregistering/rolling to a new bond, or with a stale/duplicate submission — and be credited the same sats a second time without locking any additional BTC.

### Finding Description
`verify-l1-lockups` folds over the caller-supplied `outputs` list with a fresh accumulator each call: [3](#0-2) 

Inside the fold, `validate-l1-lockup` verifies the script, amount, BTC header, and merkle proof, and only rejects duplicates that appear *within this one accumulator*: [4](#0-3) 

There is no `define-map` anywhere in the contract (or elsewhere in scope) that records previously-credited `(txid, output-index)` pairs across separate transactions — confirmed by exhaustive search of the repo for any such persistent structure. This mirrors the `IO::FS::WRITE` root cause pattern: the check exists locally (rejecting `..` within a single path/within a single call) but the boundary that actually matters — "has this real-world resource already been counted?" — is never enforced against durable state.

Once `sats-total` is computed, it is trusted as the amount of sats that were locked on Bitcoin for this bond registration and drives:
- the allowlist/allowance check `(<= sats-total allowance)` [5](#0-4) 
- `protocol-bond-memberships` and `protocol-bonds-total-staked` bookkeeping [6](#0-5) 
- `add-staker-to-bond-cycles`, which allocates the staker's share of the sBTC reward pool for that signer/bond [7](#0-6) 

Since a staker who has rolled out of a bond (`ERR_ALREADY_REGISTERED` guard only blocks *overlapping* memberships, not reuse of the underlying BTC proof) can re-submit the identical BTC lockup evidence for a fresh bond period, the same physical BTC collateral is counted as backing two (or more) separate bond/reward allocations.

### Impact Explanation
This breaks the equality that reward-slot/allowance weight granted by pox-5 must correspond 1:1 to sats actually locked on Bitcoin. Reusing one BTC lockup proof to satisfy multiple `register-for-bond` calls double-counts a commitment: the staker obtains bond membership/allowance credit and sBTC-reward eligibility for cycles where no corresponding new BTC was locked. This falls squarely under the allowed High/Critical impact category "double-counting a commitment or reward," since sats-backed reward-slot capacity now exceeds actual locked value.

### Likelihood Explanation
Reachable entirely by an unprivileged staker who is already in a bond's allowlist (a normal precondition for participating at all): stake once with sBTC or via a genuine L1 lockup, and later replay the very same lockup outputs on a subsequent `register-for-bond` call (e.g., after rolling into a new bond period, or with a bond-index for which the staker is separately allowlisted). No admin, miner, or third-party key is required — only the previously-recorded lockup bytes, which the staker already possesses since it is their own BTC transaction.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g., `(define-map used-l1-lockup-outpoints { txid: (buff 32), output-index: uint } bool)`), and have `validate-l1-lockup` check-and-insert against that global map instead of (or in addition to) the per-call `seen-outpoints` list, rejecting any outpoint that has ever been credited to any bond.

### Proof of Concept
1. Staker A is allowlisted for `bond-index 0`. They mine a real BTC lockup output paying the timelock script computed by `construct-lockup-output-script(staker=A, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes-of-bond-0)`.
2. A calls `register-for-bond(bond-index=0, signer, amount-ustx, ok({outputs:[output], staker-unlock-bytes}), signer-calldata)`. `verify-l1-lockups` validates the proof and credits `sats-total` sats; A becomes a bond-0 member.
3. A later exits (e.g., via `announce-l1-early-exit` or lets the bond term end) so `protocol-bond-memberships` for A is cleared/rolled over, and A is separately allowlisted for `bond-index 6` (a later period reusing the same allowance mechanics).
4. A calls `register-for-bond(bond-index=6, signer, amount-ustx, ok({outputs:[the SAME output/proof], staker-unlock-bytes}), signer-calldata)`. Because `validate-l1-lockup`'s dedup only inspects the fold accumulator built fresh for this single call, and no persistent map records the outpoint from step 2, the identical BTC lockup proof passes validation again, crediting the same sats a second time for bond-index 6 with no new BTC ever locked.
