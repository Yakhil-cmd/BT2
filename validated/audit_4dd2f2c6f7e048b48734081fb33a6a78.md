### Title
Webhook signature is verified against the payload's declared `repository.owner.login`, but events are dispatched using `repository.full_name` — allowing cross-organization/cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on a field read out of the attacker-supplied JSON body itself (`repository.owner.login` or `organization.login`), rather than a value tied to a fixed, pre-registered endpoint or credential. Once the signature is accepted, the actual event handler (`Shipit::Webhooks::Handlers::Handler`) looks up the target `Repository`/`Stack` using a *different* field from the same body (`repository.full_name`). Nothing enforces that the organization whose secret authenticated the request is the same organization whose repository/stack is acted upon.

### Finding Description
`verify_signature` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the untrusted request body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) and used to select which `GitHubApp` config (and thus which `webhook_secret`) to verify the HMAC against via `Shipit.github(organization: repository_owner)`.

After the signature check succeeds, `create` dispatches the same raw JSON body to handlers: [3](#0-2) 

Handlers determine the actual `Repository`/`Stack` to act on from an entirely different field of the body: [4](#0-3) 

This is the exact bug-class analog from the report: a value used to establish trust (`repository.owner.login`, which selects the verifying secret) is not the same value that is subsequently acted upon (`repository.full_name`, which selects the repository/stack that is mutated). Shipit explicitly supports multiple GitHub Apps/organizations sharing a single instance (`TOP_LEVEL_GH_KEYS`, multi-org `secrets.yml` format documented in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), so a party who legitimately possesses a valid `webhook_secret` for one onboarded organization (e.g. their own org's GitHub App on a shared Shipit instance) can compute a valid HMAC over a crafted body where `repository.owner.login` is their own org (so verification passes with their known secret) while `repository.full_name` names a different, victim organization's repository/stack hosted on the same instance.

The equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login / organization.login)` == `repository/stack acted upon by the handler (repository.full_name)`

Before the attack: only webhooks genuinely signed by a given organization's GitHub App can affect that organization's stacks.
After the crafted request: a request signed with org A's secret, but carrying `repository.full_name` = "orgB/repo", is accepted by `verify_signature` (org A branch) and then processed against org B's `Repository`/`Stack`.

### Impact Explanation
Handlers reachable this way include `PushHandler` (enqueues `GithubSyncJob` for `stack.sync_github`) and `StatusHandler`/`CheckSuiteHandler`, which record CI statuses/check results on commits: [5](#0-4) . Because Shipit's merge queue and deploy eligibility rely on recorded commit statuses/checks, forging status events against another organization's stack can influence merge-queue/deploy gating for repositories the attacker does not control — a cross-repository write/trust violation reachable without any Shipit session, API token, or repository write access, only knowledge of a webhook secret belonging to any one organization configured on the shared instance.

### Likelihood Explanation
Requires the attacker to already hold a valid `webhook_secret` for at least one organization configured on a multi-tenant Shipit deployment (a scenario the engine explicitly documents and supports). This is a narrower precondition than "any anonymous user," but no repository write access, Shipit account, or API token is needed for the *victim* organization — only the field `repository.owner.login`/`organization.login` needs to diverge from `repository.full_name` in the forged payload.

### Recommendation
Bind signature verification to the same repository identity that handlers act on: derive the verifying organization from `repository.full_name`'s owner segment (or, better, from a fixed per-installation identifier resolved from `installation_id`) rather than the loosely-matched `repository.owner.login` fallback logic in `webhooks_controller.rb`. Reject events where the organization used for HMAC selection does not match the owner segment of `repository.full_name` used by `Handler#repository_name`.

### Proof of Concept
1. Deploy Shipit with two organizations configured (`OrgA`, `OrgB`), each with its own `webhook_secret`, as in `test/dummy/config/secrets_double_github_app.yml`.
2. As a holder of `OrgA`'s webhook secret, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and successfully verifies against `OrgA`'s secret.
5. `create` dispatches the body to `PushHandler`, whose `repository_name` reads `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`, causing it to sync/act on `OrgB`'s stack despite the request never being signed by `OrgB`.
