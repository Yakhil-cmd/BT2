## Title
Asset definer can instantly change the attestor list of a `spender_attested` asset, front-running or freezing pending payments - (File: validation.js)

### Summary
For an asset created with `spender_attested: true`, the list of trusted attestors is not fixed at issuance. The asset definer can post an `asset_attestors` message at any time to replace the whitelist, and the new list takes effect for validation purposes as soon as it is included and stable before the `last_ball_mci` of a subsequent unit — with no time lock, advance notice, or waiting period. This mirrors the reported bug class exactly: a privileged role (`asset definer`) can change security-critical parameters "without warning," enabling front-running of pending transactions or accidental/malicious freezing of user funds.

### Finding Description
`asset_attestors` messages are validated in `validateAttestorListUpdate`, which only checks that the sender is the asset's `definer_address` and that the new attestor list is well-formed; there is no cooldown, minimum interval, or two-step commit process: [1](#0-0) 

When any payment in this asset is validated, `readAsset`/`loadAssetWithListOfAttestedAuthors` always pick the *latest stable* attestor-list unit (`ORDER BY level DESC LIMIT 1`, bounded only by `last_ball_mci`) rather than the list that was in effect when the sender composed/broadcast the transaction: [2](#0-1) [3](#0-2) 

`filterAttestedAddresses` then determines, at validation time, whether the payer/output addresses are attested under whatever list is current: [4](#0-3) 

Finally, `validatePayment`/`validatePaymentInputsAndOutputs` reject the unit outright if the required addresses are no longer attested: [5](#0-4) [6](#0-5) 

Because the attestor list can be swapped by the definer at any moment and takes effect as soon as the `asset_attestors` unit stabilizes (no waiting period, unlike the OP-list/system-var governance mechanism, which requires a full voting/counting process before taking effect — see `validation.js:1860-1883` and `main_chain.js` `countVotes`), an unprivileged holder who composed a valid, correctly-attested payment can have it invalidated by a same-timeframe attestor-list change from the definer. Conversely, the definer can also *add* an unattested party's key just ahead of a specific transaction to let a particular output through, or remove a party's attestor right before their broadcast unit becomes final to grief them — classic admin front-running with no mitigations (no delay, no notice, no dispute window).

### Impact Explanation
This lets the asset definer:
- Freeze/deny an otherwise-valid transfer or issuance from a legitimate, previously-attested holder by revoking the attestor whose attestation they rely on immediately before the holder's payment is included/stabilized, causing the holder's unit to fail validation ("none of the authors is attested" / "some output addresses are not attested"). This is a fund-freezing/DoS impact on user funds for an asset the definer does not otherwise control custody of.
- Selectively front-run: swap in/out attestors around specific counterparties' transactions to bias who is allowed to hold/spend the asset at a given moment, contrary to users' expectation that attestation status they observed when composing their transaction still holds when it settles.

Since this only affects `spender_attested` assets (opt-in feature used for regulated/whitelisted tokens), the blast radius is limited to holders and counterparties of such assets, but the loss/freezing of funds for those holders is concrete and directly caused by ocore's validation design (no timelock on attestor-list changes), not by any external system.

### Likelihood Explanation
Likelihood is high for any deployed `spender_attested` asset: the definer is a single address (or its multisig) that unilaterally controls the trigger (`asset_attestors` message) and needs no cooperation from witnesses or the network; the change is picked up by the very next unit that references it as parent/last-ball, i.e., effectively immediately (one or two units of propagation/stabilization), which is far faster than the multi-step, vote-based delay used for `system_vote`/`system_vote_count` changes elsewhere in ocore. No special conditions or race beyond normal DAG propagation are required.

### Recommendation
Introduce a mandatory delay between an `asset_attestors` update and the moment it becomes effective for payment validation, analogous to the two-phase "announce then commit" pattern recommended in the report:
- Require attestor-list updates to only take effect after N stable main-chain indices (or a minimum elapsed time) since being posted, giving holders advance notice.
- Alternatively/additionally, validate a payment's attestor requirement against the attestor list that was current at the payment's `last_ball_mci` *at the time the payment's inputs/parents were chosen*, rather than the latest list as of validation time, to prevent silent retroactive freezing of in-flight transactions.
- Emit a clear warning/notification (event) when an attestor list changes so wallets relying on `spender_attested` assets can react before the change becomes binding.

### Proof of Concept
1. Definer `D` creates asset `A` with `spender_attested: true` and initial attestors `[X]`.
2. Attestor `X` attests holder `H`'s address. `H` composes and broadcasts a valid `payment` of asset `A` (attested, satisfies `objAsset.arrAttestedAddresses` check at compose time).
3. Before `H`'s payment stabilizes, `D` posts an `asset_attestors` message removing `X` (validated solely via `validateAttestorListUpdate`, no delay imposed): [1](#0-0) 
4. `D`'s update unit stabilizes (or otherwise becomes the "latest" attestor-list unit visible with `main_chain_index<=last_ball_mci`) before/alongside `H`'s payment's last_ball_mci advances.
5. When `H`'s payment is (re-)validated (e.g., on inclusion or resubmission), `readAsset`/`filterAttestedAddresses` now return the *new* attestor list without `X`, so `H`'s address is no longer attested: [4](#0-3) 
6. `validatePayment` rejects the unit: "none of the authors is attested" / "some output addresses are not attested": [5](#0-4) 

`H`'s legitimately-composed transaction is invalidated purely due to `D`'s unannounced, delay-free change — demonstrating the front-running/fund-freezing scenario described in the external report, reachable entirely through normal, unprivileged unit posting (`H` and `D` are both regular asset participants, not network operators).

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],

// note that light clients cannot check attestations
function loadAssetWithListOfAttestedAuthors(conn, asset, last_ball_mci, arrAuthorAddresses, bAcceptUnconfirmedAA, handleAsset){
	if (arguments.length === 5) {
		handleAsset = bAcceptUnconfirmedAA;
		bAcceptUnconfirmedAA = false;
	}
	readAsset(conn, asset, last_ball_mci, bAcceptUnconfirmedAA, function(err, objAsset){
		if (err)
			return handleAsset(err);
		if (!objAsset.spender_attested)
			return handleAsset(null, objAsset);
		filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAuthorAddresses, function(arrAttestedAddresses){
			objAsset.arrAttestedAddresses = arrAttestedAddresses;
			handleAsset(null, objAsset);
		});
	});
}
