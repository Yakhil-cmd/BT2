### Title
`NonTransfer` proxy on Westend relay chain can escalate to an `Auction` proxy and reach `Registrar::swap`, a call it explicitly excludes - ([File: polkadot/runtime/westend/src/lib.rs])

### Summary
On the Westend relay chain runtime, `ProxyType::is_superset` unconditionally treats `NonTransfer` as a superset of every other proxy type (`(ProxyType::NonTransfer, _) => true`), including `ProxyType::Auction`. However, `NonTransfer`'s own call `filter` deliberately excludes `paras_registrar::Call::swap` (comment: "Specifically omitting Registrar `swap`"), while `ProxyType::Auction`'s filter admits the entire `Registrar` pallet, including `swap`. Because `pallet_proxy` authorizes nested `add_proxy`/`remove_proxy` purely via `is_superset` (not `filter`), a delegate holding only a `NonTransfer` proxy can grant itself an `Auction` proxy for the same delegator and thereby reach `Registrar::swap`, which the delegator's `NonTransfer` grant was specifically designed to deny. [1](#0-0) 

### Finding Description
`pallet_proxy::do_proxy` gates escalation of `add_proxy`/`remove_proxy` calls made *through* an existing proxy solely on `def.proxy_type.is_superset(proxy_type)`, not on `filter`: [2](#0-1) 

In the Westend relay-chain runtime's `ProxyType` implementation:
- `filter` for `NonTransfer` matches only `Registrar::register`, `Registrar::deregister`, `Registrar::reserve`, explicitly commented as omitting `Registrar::swap`.
- `filter` for `Auction` matches `RuntimeCall::Registrar(..)` unconditionally — i.e. it admits *all* Registrar calls, including `swap`.
- `is_superset` declares `(ProxyType::NonTransfer, _) => true` for any non-`Any` type, with no carve-out for `Auction` (unlike the carve-out that was later added for `Governance` on Asset Hub Westend). [3](#0-2) [4](#0-3) 

This is the identical bug class that was already found and patched for `NonTransfer` vs `Governance` on Asset Hub Westend (PR referenced in `prdoc/pr_12769.prdoc`), where the fix removed `Governance` from the set of types `NonTransfer` falsely claims as a subset, specifically because `pallet_proxy` authorizes `add_proxy`/`remove_proxy` via `is_superset` before consulting `filter`: [5](#0-4) [6](#0-5) 

That fix, and the added regression test asserting the superset/filter lattice invariant across "the whole lattice", was applied only to the Asset Hub Westend runtime: [7](#0-6) 

The relay chain (Westend) `ProxyType` implementation was not updated with the equivalent fix or an equivalent lattice-invariant test, leaving the `NonTransfer` → `Auction` → `Registrar::swap` escalation path open.

Attack path:
1. A delegator (Alice) grants a `NonTransfer` proxy to Bob via `pallet_proxy::add_proxy` — a routine, permitted delegation intended to withhold the ability to call `Registrar::swap` (and other transfer-adjacent calls) from Bob.
2. Bob calls `Proxy::proxy(real = Alice, force_proxy_type = None, call = Proxy::add_proxy { delegate: Bob, proxy_type: Auction, delay: 0 })`. `do_proxy`'s override filter checks `def.proxy_type.is_superset(&Auction)`, i.e. `NonTransfer.is_superset(&Auction)`, which is `true` per the wildcard rule, so the nested `add_proxy` succeeds and Alice now (unknowingly, from Bob's action) has an `Auction`-type proxy registered for Bob.
3. Bob calls `Proxy::proxy(real = Alice, force_proxy_type = Some(Auction), call = Registrar::swap { .. })`. `find_proxy` locates the `Auction` proxy definition, and `Auction.filter(&Registrar::swap)` returns `true`, so the call dispatches as Alice.

Bob has thus reached a capability (`Registrar::swap`) that Alice's original `NonTransfer` grant was specifically written to deny him, without Alice's consent to widen the proxy.

### Impact Explanation
This reproduces the structural violation identified in the Consul CVE analog: a delegated write permission (`NonTransfer` proxy) is used to reach functionality (`Registrar::swap`) that the delegator explicitly did not authorize, via a missing check that lets the delegate self-escalate its own proxy grant. The severity depends on what `paras_registrar::Call::swap` does to the affected para's registration/deposit ownership; I was not able to fully read `polkadot/runtime/common/src/paras_registrar/mod.rs::swap` in the remaining tool budget to confirm its exact origin requirements and fund/deposit side effects, so the concrete blast radius (e.g., whether it can redirect a para registration deposit or swap lease/para ownership tied to funds) is **unverified** and should be confirmed by a follow-up session reading that function directly. Independent of that, the authorization-bypass mechanism itself — bypassing an explicitly-denied call via proxy self-escalation — is concretely demonstrated and directly analogous to the sibling bug already fixed on Asset Hub Westend, which was treated as a genuine authorization escalation worth a runtime patch.

### Likelihood Explanation
High for the escalation mechanism itself: it requires only a signed account with an existing `NonTransfer` proxy grant (a normal, expected configuration) and two ordinary extrinsics (`Proxy::proxy` wrapping `add_proxy`, then `Proxy::proxy` wrapping the target call). No privileged role, governance, or validator/collator control is needed — exactly the attacker model required by the task (no privileged prerequisite). The only uncertainty is the downstream impact of `Registrar::swap`, not the reachability of the escalation.

### Recommendation
Add an explicit carve-out in `polkadot/runtime/westend/src/lib.rs`'s `ProxyType::is_superset` so that `NonTransfer` is not treated as a superset of `Auction` (mirroring the fix already applied for `Governance` on Asset Hub Westend), or narrow `Auction`'s filter to exclude `Registrar::swap`, or widen `NonTransfer`'s filter to admit it if that is actually intended. Additionally, port the lattice-invariant regression test (`proxy_type_superset_relation_matches_call_filters`) from `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` to the Westend relay chain runtime test suite so this class of bug cannot recur silently across other `ProxyType` pairs in that runtime.

### Proof of Concept
Not executed against a live network. Reasoning derived purely from static analysis of the cited source:
- `NonTransfer.filter` explicitly excludes `Registrar::swap` (comment at line 977).
- `Auction.filter` admits `RuntimeCall::Registrar(..)` unconditionally (lines 1004–1010), which includes `swap`.
- `NonTransfer.is_superset(&Auction)` returns `true` via the wildcard arm (line 1027), with no exclusion analogous to the one added for `Governance` on Asset Hub Westend.
- `pallet_proxy::do_proxy`'s nested-call filter (lines 1005–1013) authorizes `add_proxy`/`remove_proxy` solely via `is_superset`, so the `NonTransfer` → `Auction` self-escalation path is unguarded.

A minimal FRAME integration reproduction (not run here) would: (1) `add_proxy(delegate=Bob, NonTransfer)` from Alice, (2) `proxy(real=Alice, call=add_proxy{delegate=Bob, Auction})` from Bob, expecting `Ok`, (3) `proxy(real=Alice, force_proxy_type=Auction, call=Registrar::swap{..})` from Bob, expecting the call to dispatch (bypassing `NonTransfer`'s explicit denial). This mirrors the already-existing `non_transfer_proxy_is_not_a_superset_of_governance` test in the Asset Hub Westend suite, which would need an analogous `non_transfer_proxy_is_not_a_superset_of_auction` (or equivalent lattice test) added for the Westend relay chain runtime to catch this. Execution against `paras_registrar::swap`'s real authorization/deposit logic to confirm final fund-impact was **not completed** in this pass and is flagged as an open verification item for a background Devin session with file access to `polkadot/runtime/common/src/paras_registrar/mod.rs`.

	fn do_proxy(
		def: ProxyDefinition<T::AccountId, T::ProxyType, BlockNumberFor<T>>,
		real: T::AccountId,
		call: <T as Config>::RuntimeCall,
	) {
		use frame::traits::{InstanceFilter as _, OriginTrait as _};
		// This is a freshly authenticated new account, the origin restrictions doesn't apply.
		let mut origin: T::RuntimeOrigin = frame_system::RawOrigin::Signed(real).into();
		origin.add_filter(move |c: &<T as frame_system::Config>::RuntimeCall| {
			let c = <T as Config>::RuntimeCall::from_ref(c);
			// We make sure the proxy call does access this pallet to change modify proxies.
			match c.is_sub_type() {
				// Proxy call cannot add or remove a proxy with more permissions than it already
				// has.
				Some(Call::add_proxy { ref proxy_type, .. }) |
				Some(Call::remove_proxy { ref proxy_type, .. })
					if !def.proxy_type.is_superset(proxy_type) =>
				{
					false
				},
				// Proxy call cannot remove all proxies or kill pure proxies unless it has full
				// permissions.
				Some(Call::remove_proxies { .. }) | Some(Call::kill_pure { .. })
					if def.proxy_type != T::ProxyType::default() =>
				{
					false
				},
				_ => def.proxy_type.filter(c),
			}
		});

/// `pallet_proxy` authorizes `add_proxy`/`remove_proxy` through `ProxyType::is_superset`, so a
/// proxy type that *declares* itself a superset of another must also *admit* every call that other
/// type admits. Otherwise the "smaller" type is reachable as an escalation: the declared superset
/// can grant itself the subset proxy and thereby gain permissions its own filter denies.
///
/// This checks that property across the whole lattice rather than a single pair, so the class of
/// bug cannot silently reappear on another edge.
#[test]
fn proxy_type_superset_relation_matches_call_filters() {
	use frame_support::traits::InstanceFilter;

	let calls = representative_proxy_calls();

	for superset in all_proxy_types() {
		for subset in all_proxy_types() {
			if !superset.is_superset(&subset) {
				continue;
			}

			for call in calls.iter() {
				if subset.filter(call) {
					assert!(
						superset.filter(call),
						"lattice violated: {superset:?} declares itself a superset of {subset:?}, \
						 but rejects {call:?} which {subset:?} admits",
					);
				}
			}
		}
	}
}
