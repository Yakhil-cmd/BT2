### Title
Unbounded RAY debt valuation overflows and permanently freezes a high-utilization market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary

Market accrual values the entire scaled debt book as `borrowed * borrow_index` in RAY. Although the borrow index itself is capped at `10^36`, that cap is applied only after index multiplication and does not bound the subsequent debt-value product. On a sufficiently large, highly utilized market, `borrowed * new_borrow_index` can exceed `i128::MAX`, causing `MathOverflow` before the index cap is reached. Because every mutating pool operation accrues first, the market then becomes permanently unrecoverable through ordinary `supply`, `borrow`, `withdraw`, `repay`, liquidation, or `update_indexes` calls.

### Finding Description

`accrue_chunk` calls `accrue_step` before committing any market operation. That step invokes `calculate_supplier_rewards`, which computes both old and new aggregate debt values using RAY multiplication:

- `old_total_debt = borrowed * old_borrow_index`
- `new_total_debt = borrowed * new_borrow_index`

These products must fit in `i128` even though the RAY-scaled result can exceed `i128::MAX`. The borrow-index ceiling only bounds the index itself: `update_borrow_index` multiplies the old index by the interest factor and then clamps the resulting index to `MAX_BORROW_INDEX_RAY`; it does not reduce or bound `borrowed * new_borrow_index`. The production test demonstrates the resulting cliff: a billion-token, 18-decimal market at 98% utilization overflows RAY valuation before reaching `MAX_BORROW_INDEX_RAY`; subsequent `update_indexes`, `withdraw`, and `repay` calls all fail with `MathOverflow`.

The unprivileged path is:

1. Call controller `supply(caller, account_id, spoke_id, assets)` with a sufficiently large position in the target `(hub_id, asset)` market.
2. Call controller `borrow(caller, account_id, payments, receiver)` to establish sustained high utilization.
3. Allow enough time to elapse so the next accrual raises `borrowed * borrow_index` above the RAY/`i128` domain.
4. Any subsequent `update_indexes` transaction through `pool_update_indexes_call` accrues first and panics.

The pool enforces this ordering structurally: `supply`, `borrow`, `withdraw`, `repay`, and `update_indexes` all run through `ops::run_batch` or `ops::market::accrue`, while `global_sync` must execute before the market state is committed.

### Impact Explanation

Permanent freezing of funds in the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot resolve the position, and direct index synchronization cannot advance the market. Since accrued debt keeps growing with elapsed time, retrying later cannot move below the overflow boundary. Admin parameter replacement also accrues before writing new parameters, so changing the interest-rate model does not provide an ordinary recovery path.

The affected market’s cash may remain physically held by the pool token contract, but all pool accounting paths that would release it first trap on the overflowing RAY valuation. This qualifies as permanent freezing of user funds unless governance uses the separate code-upgrade path to deploy a repair.

### Likelihood Explanation

Medium. No privileged role, malformed transaction, leaked key, third-party oracle deviation, or protocol bug outside the listed entrypoints is required. The attacker must nevertheless control an extremely large amount of the target asset and enough collateral to sustain approximately 98% utilization long enough for the RAY debt product to reach the ceiling. The repository’s own boundary test reaches this condition below the configured index ceiling. Once reached, the failure is deterministic and affects every user of that market, not only the attacker.

### Recommendation

Bound aggregate scaled debt and aggregate RAY value, not merely the borrow index. In particular:

- Check `borrowed * candidate_borrow_index` against the representable RAY domain before accepting additional supply/borrow or committing an index update.
- Prefer a debt-value cap derived from the market’s scaled principal that is strictly below `i128::MAX`.
- Apply the cap before `calculate_supplier_rewards`, or make `calculate_supplier_rewards` operate on a widened intermediate and explicitly cap `new_total_debt`.
- Add a recovery path for the already-overflowing state, such as a bounded accrual calculation that can clamp aggregate debt value and socialize or cap the excess under a clearly specified rule.
- Extend boundary tests to cover `supply`, `borrow`, `liquidate`, `clean_bad_debt`, `claim_revenue`, and `update_params` at the first ledger after the debt-value ceiling is crossed.

### Proof of Concept

The repository’s boundary test reproduces the condition. It creates an 18-decimal market, raises caps to the admitted token/RAY maximum, supplies `1_000_000_000 * 10^18` base units, supplies sufficient collateral, and borrows 98% of the supplied asset. After repeated annual accruals, `try_update_indexes` fails with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`; the same overflow then rejects both `withdraw` and `repay`.

```rust
// common/src/rates/index.rs
```

```rust

```

```rust
// contracts/pool/src/interest.rs
while let Some(nonzero) = NonZeroU64::new(remaining) {
```

The decisive point is that the index cap does not prevent the separate `borrowed * new_borrow_index` product from overflowing.
