### Title
Attacker-controlled swap routes can execute unauthorized wallet-token transfers under the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategies accept attacker-controlled `swap: Bytes` and pass it to the configured router, which can invoke route-selected contracts without an on-chain venue allowlist. [1](#0-0) [2](#0-1) 

A malicious contract reached through the route can request `token.transfer` authority for the transaction signer; if the signer accepts the simulated authorization tree containing that child invocation, unrelated wallet assets are transferred to the attacker. [3](#0-2) 

### Finding Description
`swap_collateral(caller, account_id, current, amount, new, swap)` exposes a user-controlled `Bytes` route through the controller’s public entrypoint. [1](#0-0) 

The controller authorizes only `token_in.transfer(controller, router, amount_in)` and relies on balance deltas to bound the router’s direct token spend. [4](#0-3) 

That accounting does not constrain calls made to arbitrary route-selected contracts because the router has no allowlist of pool or token addresses and can place third-party code below the caller’s authorization. [5](#0-4) 

The same pattern is reachable through `multiply`, `swap_debt`, and `repay_debt_with_collateral`, each of which accepts route bytes and invokes the shared router path. [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
A successful poisoned route can transfer any signer-held token to an attacker, including assets unrelated to the lending markets and not supplied as protocol collateral. [9](#0-8) 

The route can still return a valid swap output, so measured output and final account-risk checks do not prevent the unrelated wallet theft. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
Exploitation requires the victim to submit a crafted route and sign the authorization tree returned by simulation, because a correctly constrained authorization tree causes the host to reject the rogue transfer. [12](#0-11) 

This is nevertheless reachable through normal route construction because simulation records the rogue wallet transfer as a child of the caller’s `swap_collateral` authorization and the signed poisoned tree executes it. [13](#0-12) 

### Recommendation
Constrain route execution to governance-approved venue and pool contracts, or replace opaque route-selected contract addresses with a bounded on-chain registry of approved adapters and venues. [5](#0-4) 

At minimum, reject any route whose simulation produces authorization children beyond the expected input-token transfer and make that invariant part of the controller-facing integration rather than relying on clients to inspect opaque route bytes. [14](#0-13) 

### Proof of Concept
Deploy a malicious pool contract that stores the victim, an arbitrary wallet token, an attacker recipient, and an amount, then calls `wallet_token.transfer(victim, attacker, amount)` from its route-invoked `swap` function. [15](#0-14) 

Construct `swap` route bytes naming that malicious pool and call `swap_collateral(alice, account_id, HubAssetKey(USDC), amount, HubAssetKey(ETH), swap)` with a route that also returns sufficient ETH output. [16](#0-15) 

Simulating that transaction records `wallet_token.transfer(alice, attacker, amount)` as a child of Alice’s `swap_collateral` authorization. [17](#0-16) 

If Alice signs that simulated tree, the controller completes the collateral swap while the malicious route transfers her unrelated wallet-token balance to the attacker. [3](#0-2)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
