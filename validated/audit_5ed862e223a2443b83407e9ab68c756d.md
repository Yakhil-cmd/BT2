### Title
Unhandled crash in AA dry-run trigger evaluation reachable from any posted unit - ([File: network.js])

### Summary
When `conf.bDryRunNewTriggers` is enabled, every successfully-validated unit that pays to an AA address causes the node to synchronously call `aa_composer.getTrigger()` and `aa_composer.dryRunPrimaryAATrigger()` from inside the async `ifOk` handler of `handleJoint`, with no `try/catch` around the call.

### Finding Description
In `handleJoint`'s `ifOk` callback, after `validation.validate()` accepts a unit, the code builds a trigger from the raw posted unit and immediately executes a "dry run" of the AA it targets, purely for diagnostic purposes, before `writer.saveJoint` is called: [1](#0-0) 

The comment "if it would crash, let it crash now, not when we execute the trigger for real" makes explicit that the authors expect this call path can throw, and they deliberately let it propagate. `aa_composer.getTrigger` itself can throw synchronously (`throw Error("no outputs to " + receiving_address)`), and `dryRunPrimaryAATrigger` → `handleTrigger` → `evaluateAA`/formula evaluation contains numerous `throw Error(...)` statements that assume internal consistency of DB state and definitions (e.g. `throw Error("base AA not found: " + base_aa)`, `throw Error('bad AA definition ' + arrDefinition)`), any of which is reachable if an attacker crafts a unit with `trigger.data` or payment structure that drives AA execution into one of these "should never happen" assumption checks: [2](#0-1) [3](#0-2) 

Because `ifOk` is declared `async` and this call is not wrapped in `try/catch`, a thrown exception here becomes either an unhandled exception inside an async callback (in this codebase's own event loop) or an unhandled promise rejection, which is not caught by the surrounding `validation.validate` callback machinery in `network.js`. The process installs a global `uncaughtException` handler that deliberately re-throws to crash the process: [4](#0-3) 
This means any code path that reaches an uncaught throw in this section results in the entire node crashing — a remotely triggerable, unauthenticated denial of service, analogous to the GNU patch NULL-pointer/segfault bug class described in the report: malformed-but-structurally-valid input (a unit whose AA trigger data is inconsistent with what the AA execution engine expects) drives an internal consistency assumption to fail, and the resulting unhandled fault crashes the process instead of being handled gracefully.

### Impact Explanation
Any full node operator running with `conf.bDryRunNewTriggers = true` can be crashed remotely by any unprivileged peer or client that posts a single valid-looking unit with a payment output to an existing AA address, crafted so that the AA's execution logic hits one of the internal `throw Error(...)` assumption checks in `aa_composer.js` during dry-run. This is a network-wide denial-of-service vector: an attacker does not need to control a hub, be a witness, or have any special privilege — merely being able to broadcast/post a unit is sufficient, and the crash occurs on every full node with the flag enabled that receives/validates the unit, potentially halting the network's ability to process new units until nodes are restarted or the flag is disabled.

### Likelihood Explanation
Likelihood depends on: (1) `bDryRunNewTriggers` being enabled by default (this could not be conclusively confirmed with the available search — the flag is only referenced in `network.js`, and its default value is set in `config.js`, which was not fully retrievable via the indexed search; a Devin session with full file access should confirm this), and (2) an attacker being able to construct AA definition/trigger data combinations that reach one of the internal `throw Error` sanity checks in `aa_composer.js`. Given the numerous unguarded `throw Error(...)` statements deep in AA composition/formula-evaluation code that assume validated invariants (e.g. `base AA not found`, `bad AA definition`, `no outputs to <address>`), and given that AA definitions themselves are attacker-postable data, the likelihood of finding at least one reachable crash path is considered non-trivial, but precise reproduction requires further investigation of `aa_composer.js`'s full `handleTrigger`/`evaluateAA` implementation that was not completely enumerated here.

### Recommendation
Wrap the entire dry-run block in `network.js` (`getTrigger` + `dryRunPrimaryAATrigger` invocation) in a `try/catch` (or a `.catch()` on the promise) that logs the error and safely skips the dry run instead of allowing the exception to propagate and crash the process. Additionally, audit `aa_composer.js` and the formula evaluation engine for `throw Error(...)` statements that are reachable from attacker-controlled trigger/definition data (as opposed to being true internal-invariant violations), and convert those into graceful validation failures/bounces rather than unhandled throws.

### Proof of Concept
Conceptual PoC (not fully verified against live AA execution internals due to search-tool limitations):
1. Enable a node with `bDryRunNewTriggers: true`.
2. Post/define an AA whose definition or associated stored state can be manipulated (e.g., via a race in `insertAADefinitions`/`readBaseAADefinitionAndParams`, or via crafted `trigger.data` that formula evaluation cannot safely digest) such that when `dryRunPrimaryAATrigger` executes `handleTrigger`, one of the "should never happen" `throw Error(...)` checks in `aa_composer.js` (e.g., `base AA not found`, `bad AA definition`) is hit.
3. Broadcast a simple payment unit sending funds to that AA's address.
4. On any node with `bDryRunNewTriggers` enabled that validates this unit, the `ifOk` handler's unguarded call throws, propagates as an uncaught exception, and is caught by the global `process.on('uncaughtException', ...)` handler in `network.js`, which deliberately re-throws to crash the process — denying service to that node.

Note: full confirmation of the exact input needed to trigger one of the internal `throw Error` assumptions inside `aa_composer.js`'s `handleTrigger`/`evaluateAA`, and confirmation of the default value of `bDryRunNewTriggers`, requires deeper access to `aa_composer.js` (the full file) and `config.js` than was retrievable through the indexed search; a Devin session with full repository access is recommended to pin down the exact minimal malicious unit.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
