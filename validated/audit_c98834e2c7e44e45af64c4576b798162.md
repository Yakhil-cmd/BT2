### Title
Webhook signature verification binds only to `repository.owner.login`, not to the repository/stack actually acted upon, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a valid analog of the reported bug class: a value used to satisfy a security check (`repository_owner`, used to pick which webhook secret authenticates the request) is disconnected from the value that determines what gets mutated (`repository.full_name`, used to resolve the target `Stack`s). Just as the `TemporaryHoldings` bug let an approved-for-a-short-time actor use an unrelated, unbounded parameter (`durationBlocks`) to keep long-term control, here an actor who legitimately controls the webhook secret for **one** configured GitHub organization can forge an event whose "acted upon" field (`repository.full_name`) names a stack belonging to **any other** organization on the same Shipit instance, because the two fields are never checked for consistency.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks which org's HMAC secret to verify against using a field read directly out of the untrusted JSON body, before any authentication has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight from the request body. `Shipit.github(organization: repository_owner)` then looks up that organization's configured `webhook_secret` and verifies the HMAC of the raw POST body against it, as implemented in: [3](#0-2) 

Once the signature check passes (proving only that *some* known org's secret was used to sign this exact body), the event is dispatched to a handler that determines the actual target using a **different, independently-controlled** field of the same body — `repository.full_name` — with no cross-check against `repository.owner.login`: [4](#0-3) 

For example, `PushHandler` resolves every non-archived `Stack` on the matching branch for that repository name and forces a resync: [5](#0-4) 

Because Shipit supports multiple GitHub organizations/Apps configured on one instance (each with its own independent `webhook_secret`, as reflected in the multi-org secrets fixture), the binding that should hold is:

`organization whose secret authenticated the request == organization owning the repository/stack being mutated`

The code only establishes the left-hand side (secret selection) using `repository.owner.login`, and separately trusts the right-hand side (`repository.full_name`) for the actual write, without ever confirming they name the same organization. A configured-but-unrelated org's credentials are therefore sufficient to sign a body whose `repository.full_name` claims a completely different org's repository.

### Impact Explanation
An attacker who controls the webhook secret for any one GitHub organization/App configured on the shared Shipit instance (a legitimate, low-privilege tenant of that instance) can forge `push`, `status`, `check_suite`, or `pull_request` webhook deliveries that pass signature verification, but whose `repository.full_name` names a `Stack` belonging to an entirely different organization. This lets the attacker trigger unauthorized `Stack#sync_github` state changes (and, transitively, continuous deployment / merge-queue processing) on stacks they have no GitHub repository permission over — a cross-repository write / unauthorized-deploy-class impact reachable without any `ApiClient` token, `webhook_secret` of the victim, or GitHub repository access to the victim repo.

### Likelihood Explanation
Likelihood is medium: it requires the attacker to be a legitimate, low-privileged tenant/org-admin on a Shipit instance that is configured to serve multiple GitHub organizations with independent webhook secrets (a supported, documented configuration, not a misconfiguration). No compromise of the victim org's credentials, GitHub App, or `Shipit.api_clients_secret` is needed — only the attacker's own org's already-possessed webhook secret.

### Recommendation
After `verify_signature` succeeds, validate that the organization used to select the webhook secret (`repository_owner`) matches the owner segment of `repository.full_name` (and of `organization.login` where present) before dispatching to any handler; reject the event otherwise. Alternatively, resolve the target `Repository`/`Stack` scoped by the authenticated organization rather than trusting `full_name` in isolation, mirroring the report's recommendation to validate the "acted upon" parameter against the same authority that governs the trusted action.

### Proof of Concept
1. Instance operator configures two GitHub orgs in `Shipit.github`, `AttackerOrg` and `VictimOrg`, each with its own `webhook_secret` (supported multi-tenant setup, cf. `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who legitimately administers `AttackerOrg`'s GitHub App/webhook secret, crafts a `push` event JSON body:
   - `repository.owner.login = "AttackerOrg"`
   - `repository.full_name = "VictimOrg/victim-repo"`
   - `ref = "refs/heads/master"`, `after = "<attacker-chosen sha>"`
3. Attacker computes `X-Hub-Signature` as `sha1=HMAC(AttackerOrg_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "AttackerOrg")`, verifies the signature successfully (it was legitimately signed with `AttackerOrg`'s secret over this exact body).
5. `PushHandler#process` calls `Handler#stacks`, which resolves `Repository.from_github_repo_name("VictimOrg/victim-repo")` — a repository/org the attacker never authenticated for — and invokes `stack.sync_github(expected_head_sha: params.after)` on it, causing unauthorized state changes / sync on `VictimOrg`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
