### Title
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` ignore `review_stacks_enabled` for `allow_with_label`/`prevent_with_label` behaviors due to `&&`/`||` precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` (and the structurally identical `unarchive?` in `ReopenedHandler`) is written as `a && b || c || d`. Because `&&` binds tighter than `||` in Ruby, `repository.review_stacks_enabled` is only ANDed into the first disjunct (`allow_all?`); the `allow_with_label?` and `prevent_with_label?` disjuncts are completely unguarded by `review_stacks_enabled`. This is not a timing race — it is a deterministic logic error that reproduces every single time on any repository configured with `provisioning_behavior: allow_with_label` or `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`.

### Finding Description
Binding claimed by the operator's configuration: `repository.review_stacks_enabled == false` must imply `provision? == false` for every pull request, regardless of `provisioning_behavior`.

Actual code [1](#0-0) :
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Ruby operator precedence parses this as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` never appears in the second or third disjunct. So if `repository.provisioning_behavior == "prevent_with_label"` and `review_stacks_enabled == false`, evaluating `provision?` for an unlabeled PR yields `false || false || true == true`. The stack is provisioned even though the operator has explicitly disabled review stacks. The identical pattern exists in `ReopenedHandler#unarchive?` [2](#0-1) .

Attack request: an unprivileged GitHub user opens a pull request (or reopens one) against a tracked repository whose operator has set `provisioning_behavior: prevent_with_label` (or `allow_with_label`) and has toggled `review_stacks_enabled: false` — the `opened`/`reopened` webhook payload requires no special privilege beyond opening a PR in one's own fork against the repo, or having the webhook delivered by GitHub as usual.

Existing guards do not prevent this: `LabeledHandler#respond_to_label_change?` does correctly AND `review_stacks_enabled` into the top-level guard [3](#0-2) , showing the intended pattern was to gate the entire decision on `review_stacks_enabled`; `OpenedHandler`/`ReopenedHandler` fail to do this. `ExplicitParameters`, signature verification, etc. are irrelevant here since the flaw is purely in the boolean logic after the payload is validated and trusted.

Note on the question's framing: the scoped question describes this as a "race" during an operator's edit window. That framing is inaccurate — no race or precise timing is required. The bug is a permanent, deterministic mis-scoping of `review_stacks_enabled`, reproducible any time that flag is `false` together with `allow_with_label`/`prevent_with_label`, independent of when a PR is opened relative to any configuration change.

### Impact Explanation
For a repository whose operator has disabled review stacks (`review_stacks_enabled: false`) while retaining `allow_with_label`/`prevent_with_label`, an unprivileged PR author can still trigger `ReviewStackAdapter#find_or_create!`, creating a `Stack` and enqueuing it for provisioning (`awaiting_provision?`/`deprovisioned?` state per `assert_pending_provision` in tests) [4](#0-3) . Provisioning drives `ProvisioningHandler` hooks and downstream task execution for that repository/environment, an action the operator believed was disabled. This is scoped to the repository that owns the PR (not cross-tenant), constituting an authorization-bypass of the operator's explicit configuration decision, resulting in an unauthorized deploy-adjacent action (stack creation/provisioning) that should not have occurred.

### Likelihood Explanation
Preconditions: repository must already be tracked by Shipit, and an operator must have configured `provisioning_behavior` to `allow_with_label` or `prevent_with_label` while setting `review_stacks_enabled: false`. No attacker-controlled secrets or elevated privileges are needed beyond opening/labeling a PR. Given that `review_stacks_enabled: false` combined with a non-`allow_all` behavior is a plausible, even expected, transitional/permanent configuration (e.g., disabling review stacks while still nominally allowing labeled ones), this is fully deterministic and trivially repeatable on every PR against such a repository — not a narrow race window.

### Recommendation
Fix operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` so `review_stacks_enabled` gates all three disjuncts, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # operator disabled review stacks
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []   # unlabeled PR

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Binding assertions: LHS = `repository.review_stacks_enabled` (`false`); RHS = "current authorized decision" (no provisioning allowed) → expected `Shipit::Stack.count` unchanged. Current code fails this assertion (`assert_difference`, not `assert_no_difference`, actually holds), demonstrating the divergence.
