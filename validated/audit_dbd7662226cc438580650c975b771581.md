## Title
Authorization bypass in `my_xpubkey` / `wallet_fully_approved` device-message handlers allows any device to inject itself into a victim's multisig wallet without membership checks - (File: `wallet.js`, `wallet_defined_by_keys.js`)

### Summary
The DDP-style device message handlers `my_xpubkey` and `wallet_fully_approved` in `wallet.js` accept a caller-supplied `wallet` identifier and pass it straight into `wallet_defined_by_keys.js`'s `addDeviceXPubKey()` / `handleNotificationThatWalletFullyApproved()` without verifying that the sending device is actually one of the invited cosigners of that wallet (i.e. without checking membership against the wallet's `definition_template`/`wallet_signing_paths`). This mirrors the Wekan `copyBoard` pattern: a privileged, multi-party object (a private board / a private multisig wallet) is mutated by ID with no ownership/membership check, only here it is a `db.query(...INSERT...)` on `extended_pubkeys` rather than a full document copy.

### Finding Description
In `wallet.js`, both handlers are explicitly marked as usable by devices that are not even paired correspondents: [1](#0-0) 

`my_xpubkey` only validates that `body.wallet` and `body.my_xpubkey` are non-empty strings of bounded length, then forwards directly to `walletDefinedByKeys.addDeviceXPubKey(body.wallet, from_address, body.my_xpubkey, callbacks.ifOk)` — `from_address` is fully attacker-controlled (derived from the sender's own device pubkey), and `body.wallet` is any string the attacker supplies/knows.

`addDeviceXPubKey` performs no check that `wallet` exists as a known wallet nor that `device_address` is part of that wallet's agreed cosigner set (`wallet_signing_paths`): [2](#0-1) 

It unconditionally `INSERT`s (with `IGNORE`) a new row keyed by `(wallet, device_address)` into `extended_pubkeys`, sets `approval_date`, and then calls `checkAndFullyApproveWallet`, which determines whether all rows for that wallet have `approval_date`: [3](#0-2) 

Likewise `wallet_fully_approved` is also allowed "from non-correspondents": [4](#0-3) 

and `handleNotificationThatWalletFullyApproved` similarly `INSERT`s a bare row for the attacker's own `device_address` and sets only `member_ready_date`, again with no membership validation: [5](#0-4) 

`checkAndFinalizeWallet` requires **every** row associated with the wallet (via the unconditioned `LEFT JOIN extended_pubkeys USING(wallet)`) to have `member_ready_date` set before the wallet is ever marked `ready_date`: [6](#0-5) 

Because an attacker's injected row via `my_xpubkey` gets `approval_date` set (but never `member_ready_date`, unless the attacker also sends `wallet_fully_approved` for itself), this bogus, permanently-unready row causes the `rows.some(row => !row.member_ready_date)` check in `checkAndFinalizeWallet` to be perpetually true for that wallet — the real multisig wallet's `ready_date` (and thus its usability, since address derivation in `deriveAddress`/`issueAddress` depends on wallet state) can never legitimately finalize as long as the injected row remains, and the attacker's row (having no `extended_pubkey` unless supplied, or an attacker-chosen one) also risks breaking `deriveAddress`, which iterates **all** `extended_pubkeys` rows for the wallet and `throw`s if any lacks `extended_pubkey`: [7](#0-6) 

None of `deleteWallet`, `addDeviceXPubKey`, or `handleNotificationThatWalletFullyApproved` check that `from_address` is among the device addresses derived from the wallet's `wallet_definition_template`/`wallet_signing_paths`, unlike other handlers in the same file (e.g. `deleteWallet` does check `extended_pubkeys` membership before acting, but only to allow no-ops, not to reject unauthorized wallet IDs; and it too accepts any caller-supplied `wallet`).

### Impact Explanation
An attacker who merely learns/guesses a target's `wallet` identifier (a SHA-256 hash of the initiator's xpubkey — not cryptographically secret information, and can be seen in local UI dialogs, backups, or if the attacker was previously invited/cancelled from a wallet-creation flow) can, without ever being paired as a correspondent or invited as a cosigner:
- Permanently prevent the victim's genuine multisig wallet from reaching `ready_date`/full approval (denial-of-service/freeze on the wallet setup and on future address issuance, since `deriveAddress`/`issueAddress` depend on all `extended_pubkeys` rows for the wallet having a valid `extended_pubkey`), and
- Corrupt subsequent address derivation for that wallet by causing `deriveAddress` to throw for a row missing `extended_pubkey`.

This matches the "AA fund loss or freezing" / "node disagreement... unable to confirm" impact class analogous to the Wekan report (unauthorized mutation of a shared/private multi-party resource by ID, with no membership check), scoped to wallet/contract message handling explicitly allowed by the assessment rules.

### Likelihood Explanation
The two handlers are explicitly documented in-code as reachable "from non-correspondents", i.e. by design any device pubkey can send these messages to a hub-connected wallet without any pairing relationship. The only unknown the attacker needs is the target `wallet` id, which is not treated as a secret by the protocol (it's derived deterministically from a public xpubkey hash and is exchanged during normal wallet-setup device messages such as `create_new_wallet`, `cancel_new_wallet`, `new_wallet_address`, so it can leak to devices involved in any stage of setup, including rejected/cancelled cosigner candidates). No signature over the wallet's actual definition is required to inject the row, only knowledge of the `wallet` string.

### Recommendation
Before mutating `extended_pubkeys` for `my_xpubkey`/`wallet_fully_approved`/`cancel_new_wallet` handling, verify that `from_address` is one of the device addresses derived from the target wallet's stored `definition_template` (`wallets.definition_template` / `wallet_signing_paths`), rejecting the message otherwise, consistent with the check already used for other wallet flows (e.g. `validateWalletDefinitionTemplate`). Reject unknown `wallet` identifiers outright instead of silently `INSERT`ing new rows keyed by arbitrary caller-supplied IDs.

### Proof of Concept
1. Attacker device (never paired with victim, no invitation) obtains/guesses the victim's real multisig `wallet` id (e.g., observed during a wallet-creation flow the attacker was briefly part of, or via `cancel_new_wallet`/other leak channels).
2. Attacker sends a device message: `{subject: "my_xpubkey", body: {wallet: "<victim_wallet_id>", my_xpubkey: "<attacker_xpubkey_base58>"}}` to the victim's hub/device.
3. `wallet.js`'s `my_xpubkey` case forwards straight to `addDeviceXPubKey` with no membership check, inserting a permanent row for the attacker's `device_address` in `extended_pubkeys` for the victim's wallet, with `approval_date` set but `member_ready_date` never set.
4. `checkAndFullyApproveWallet`/`checkAndFinalizeWallet` for that wallet will now perpetually see an unready row, blocking `wallets.ready_date` from ever being set, and future `deriveAddress` calls for the wallet may throw once they iterate over the corrupted `extended_pubkeys` set.

function checkAndFullyApproveWallet(wallet, onDone){
	db.query("SELECT approval_date FROM wallets LEFT JOIN extended_pubkeys USING(wallet) WHERE wallets.wallet=?", [wallet], function(rows){
		if (rows.length === 0) // wallet not created yet
			return onDone ? onDone() : null;
		if (rows.some(function(row){ return !row.approval_date; }))
			return onDone ? onDone() : null;
		db.query("UPDATE wallets SET full_approval_date="+db.getNow()+" WHERE wallet=? AND full_approval_date IS NULL", [wallet], function(){
			db.query(
				"UPDATE extended_pubkeys SET member_ready_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[wallet, device.getMyDeviceAddress()], 
				function(){
					db.query(
						"SELECT device_address FROM extended_pubkeys WHERE wallet=? AND device_address!=?", 
						[wallet, device.getMyDeviceAddress()], 
						function(rows){
							// let other members know that I've collected all necessary xpubkeys and ready to use this wallet
							rows.forEach(function(row){
								sendNotificationThatWalletFullyApproved(row.device_address, wallet);
							});
							checkAndFinalizeWallet(wallet, onDone);
						}
					);
				}
			);
		});
	});
}

function addDeviceXPubKey(wallet, device_address, xPubKey, onDone){
	db.query(
		"INSERT "+db.getIgnore()+" INTO extended_pubkeys (wallet, device_address) VALUES(?,?)",
		[wallet, device_address],
		function(){
			db.query(
				"UPDATE extended_pubkeys SET extended_pubkey=?, approval_date="+db.getNow()+" WHERE wallet=? AND device_address=?", 
				[xPubKey, wallet, device_address],
				function(){
					eventBus.emit('wallet_approved', wallet, device_address);
					checkAndFullyApproveWallet(wallet, onDone);
				}
			);
		}
	);
}

function deriveAddress(wallet, is_change, address_index, handleNewAddress){
	db.query("SELECT definition_template, full_approval_date FROM wallets WHERE wallet=?", [wallet], function(wallet_rows){
		if (wallet_rows.length === 0)
			throw Error("wallet not found: "+wallet+", is_change="+is_change+", index="+address_index);
		if (!wallet_rows[0].full_approval_date)
			throw Error("wallet not fully approved yet: "+wallet);
		var arrDefinitionTemplate = JSON.parse(wallet_rows[0].definition_template);
		db.query(
			"SELECT device_address, extended_pubkey FROM extended_pubkeys WHERE wallet=?", 
			[wallet], 
			function(rows){
				if (rows.length === 0)
					throw Error("no extended pubkeys in wallet "+wallet);
				var path = "m/"+is_change+"/"+address_index;
				var params = {};
				rows.forEach(function(row){
					if (!row.extended_pubkey)
						throw Error("no extended_pubkey for wallet "+wallet);
					params['pubkey@'+row.device_address] = derivePubkey(row.extended_pubkey, path);
					console.log('pubkey for wallet '+wallet+' path '+path+' device '+row.device_address+' xpub '+row.extended_pubkey+': '+params['pubkey@'+row.device_address]);
				});
				var arrDefinition = Definition.replaceInTemplate(arrDefinitionTemplate, params);
				var address = objectHash.getChash160(arrDefinition);
				handleNewAddress(address, arrDefinition);
			}
		);
	});
}
