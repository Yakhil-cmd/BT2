### Title
`StatusHandler` resolves commits by SHA with no repository/stack scoping, enabling cross-tenant CI status forgery leading to unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, without ever checking that the webhook's `repository` field corresponds to the commit's actual `stack`/repository. Because git commit SHAs are content-addressed and identical across forks, an attacker who forks (or otherwise possesses) a commit that is also the pending head of a Victim's merge-queued PR can send a genuinely-signed status webhook from their own repository and have Shipit write a forged `Status` (e.g. `state: success`) onto the Victim's `Commit`, which can cascade through `ProcessMergeRequestsJob` into `MergeRequest#merge!` calling `stack.github_api.merge_pull_request` with the Victim's credentials.

### Finding Description
The broken binding is: **`params.dig('repository', 'full_name') == commit.stack.repository.full_name`** is never checked, even though `Handler#stacks`/`Handler#repository_name` exists in the base class and is used by nearly every other handler (`PullRequest::*Handler`) via `Repository.from_github_repo_name(repository_name)`.

`StatusHandler` diverges from that pattern: [1](#0-0) 
Its `params` schema only requires `sha`, `state`, `description`, `target_url`, `context`, `created_at`, `branches` — no `repository` field is required or consulted — and `process` does a *global*, unscoped lookup:
```
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
```
This matches **every** `Commit` row in the entire installation with that SHA, across all stacks/tenants, and applies the attacker-supplied `state`/`context`/`description` to each one via `create_status_from_github! -> add_status -> statuses.replicate_from_github!(stack_id, ...)`. [2](#0-1) [3](#0-2) 

`WebhooksController#verify_signature` only picks *which organization's* webhook secret to verify the signature against (`repository_owner`), it does not bind the payload's repository to the commits it's allowed to mutate: [4](#0-3) 
So a genuinely GitHub-signed webhook for Attacker's own repository (signed with Attacker's org's real webhook secret, which GitHub itself computes and sends — Attacker never needs to know the secret) passes signature verification, and `StatusHandler` then executes unconditionally against any commit sharing that SHA, regardless of which repository the payload names.

Exploit flow:
1. Attacker forks/possesses a repository containing the exact same commit object as Victim's pending PR head (git SHAs are content-addressed; forking preserves identical commit hashes for identical content — no hash collision needed).
2. Attacker sets a commit status (e.g. via the GitHub Status API, or CI configured on their own repo) on that commit inside **their own** repository, with `state: success` and a `context` matching whatever CI context Victim's `deploy_spec` requires (often discoverable from a public CI badge/context name).
3. GitHub emits a `status` webhook to Shipit, signed with Attacker's own org's real webhook secret, `repository.full_name` = Attacker's repo.
4. `WebhooksController#create` -> `Shipit::Webhooks.for_event('status')` -> `StatusHandler.call(params)`.
5. `StatusHandler#process` does `Commit.where(sha: ...)`, finds Victim's `Commit` (same SHA, different stack), and calls `commit.create_status_from_github!(params)`, writing a `Status` row with `stack_id: victim_commit.stack_id`.
6. `Status#schedule_continuous_delivery` / commit state transition to `success` enqueues `ProcessMergeRequestsJob` for Victim's stack. [5](#0-4) 
7. `ProcessMergeRequestsJob#perform` calls `merge_request.refresh!`, `reject_unless_mergeable!` (false, since `mergeable` isn't `false`/`nil`), then `all_status_checks_passed?` — now true because of the forged status — then `merge_request.merge!`. [6](#0-5) 
8. `MergeRequest#merge!` calls `stack.github_api.merge_pull_request(stack.github_repo_name, number, ..., sha: head.sha, ...)` — using **Victim's** stored `GITHUB_TOKEN` against **Victim's** repo/PR. [7](#0-6) 

Existing guards fail to prevent this: `verify_signature` only authenticates *that the payload came from GitHub for some org*, not that the named repository is the one whose data is being mutated; `ExplicitParameters` schema for `StatusHandler` never requires/validates `repository`; and unlike the `PullRequest::*` handlers, `StatusHandler` never calls `Repository.from_github_repo_name` or scopes the query through `stacks`.

### Impact Explanation
An attacker with no privileges on the Victim's stack can cause GitHub to be told the Victim's PR has passing CI, driving Shipit's automated merge queue to call `stack.github_api.merge_pull_request` for the Victim's repository using the Victim's GitHub credentials — an unauthorized merge performed with Victim's own token, satisfying the "Critical" category ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy, rollback or merge"). This is repeatable against any repository/stack pair that happens to share a commit SHA with a repository the attacker controls (trivially achievable via forking public repos), and is not limited to a single tenant — any Shipit-managed stack with `merge_queue_enabled: true` is at risk once the attacker aligns a fork's commit history with a pending PR's head SHA.

### Likelihood Explanation
Preconditions: Victim stack has `merge_queue_enabled? == true` and a pending `MergeRequest` whose `mergeable != false/nil`; Attacker must control (or fork) a repository whose org is already onboarded to the same Shipit installation (needed so `verify_signature` succeeds using that org's real, GitHub-issued webhook secret) and must know/guess the CI `context` string Victim's deploy spec requires. Attacker cost is low: forking a public repository preserves identical commit SHAs by construction, and setting a commit status on a commit in one's own repo requires no special privilege beyond push/API access to that repo. The scenario is realistic for any Shipit deployment serving multiple organizations/repos where an attacker can create or use a repository under an onboarded org.

### Recommendation
In `StatusHandler`, require and validate the `repository` field like every other handler, and scope the commit lookup by repository/stack, e.g.:
```ruby
params do
  requires :sha, String
  requires :state, String
  requires :repository do
    requires :full_name, String
  end
  ...
end

def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
  end
end
```
using the existing `Handler#stacks`/`Handler#repository_name` helpers, so a status webhook can only affect commits belonging to the repository that actually sent it.

### Proof of Concept
Minitest plan (no live GitHub, uses fixtures/mocks):
```ruby
test "status webhook for attacker's repo must not affect commit belonging to a different stack/repository" do
  victim_stack = shipit_stacks(:shipit) # repo e.g. "shopify/shipit-engine"
  victim_commit = shipit_commits(:first)
  # Simulate: attacker's fork contains an identical commit object (same sha)
  # by directly asserting the binding that should hold but doesn't:
  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/forked-repo', 'owner' => { 'login' => 'attacker' } }
  }

  assert_not_equal victim_stack.repository.full_name, attacker_payload['repository']['full_name']

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end
  # Demonstrates params.repository.full_name != commit.stack.repository.full_name
  # yet the Status was written to the Victim's commit/stack anyway.
end

test "forged status enables merge_pull_request call on victim's repo/creds via attacker webhook" do
  victim_stack = shipit_stacks(:shipit)
  merge_request = shipit_merge_requests(:one) # pending, mergeable: true, head sha == X
  attacker_payload = {
    'sha' => merge_request.head.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/forked-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit.github.api.expects(:merge_pull_request).with(
    victim_stack.github_repo_name, merge_request.number, anything, has_entries(sha: merge_request.head.sha)
  ).once

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  ProcessMergeRequestsJob.perform_now(victim_stack)
end
```
This proves the equality `params.repository.full_name == commit.stack.repository.full_name` is not enforced before the state-mutating `Status` write, and that this divergence is sufficient to drive `stack.github_api.merge_pull_request` for the Victim using only an Attacker-signed webhook naming Attacker's own repository.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

      raise InvalidTransition unless pending?

      end

      true

      reject!('merge_conflict')
      false
