## Analysis

This confirms the vulnerable binding. In `Shipit.github_app_config` and `Shipit.github`, when multi-org mode is enabled (`config/secrets.yml` has one key per GitHub organization, each with its own independently-generated `webhook_secret`), the org lookup used to select the verification key is derived purely from an unauthenticated field in the request body, while the field that ultimately drives all side effects is a *different* field in that same unauthenticated body.

### Title
Webhook Signature Verified Against Unrelated `repository.owner.login` While Handlers Act on `repository.full_name` — Cross-Organization Webhook Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` looks up the GitHub App config, and hence the HMAC secret used to validate `X-Hub-Signature`, using `repository_owner`, which is read straight out of the *unverified* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Once the signature validates, `create` re-parses the same raw body and dispatches it unchanged to every registered handler for the event. [3](#0-2) 

Every handler, however, resolves the target repository/stack from a **different** field of the body — `repository.full_name` — not from `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

`Shipit.github_app_config` shows that in multi-org mode each org is a fully independent trust domain with its own `webhook_secret`, key by key: [7](#0-6) 

### Finding Description
The binding that should hold is: `organization whose secret authenticated the request == organization that owns the repository the request is allowed to act on`. Instead the engine implements: `organization derived from repository.owner.login (unverified) == organization whose secret is used to compute the HMAC`, and separately: `repository.full_name (also unverified, same body) == repository/stack that is actually mutated`.

Because `repository.owner.login` and `repository.full_name` are two independent, attacker-writable JSON fields inside the *same* raw body, and because the signature is verified using a secret selected from the first field but applied over the whole body (which is fine on its own), an operator who legitimately controls **any one** of the configured GitHub organizations (i.e., knows that org's own `webhook_secret`, which they themselves generated when creating their GitHub App, per `docs/setup.md`'s multi-org instructions) can construct a POST directly to `/webhooks` with:
- `repository.owner.login` = their own org (so `Shipit.github(organization: ...)` selects their own known secret and the HMAC they compute with it validates), and
- `repository.full_name` = `"other-org/some-repo"` (so the dispatched handler resolves and acts on a stack belonging to a completely different, unrelated organization via `Repository.from_github_repo_name`). [8](#0-7) 

This is not a request relayed by GitHub — it is a raw HTTP request crafted by the attacker and signed with a secret they legitimately possess for their own tenant, but whose payload content targets someone else's tenant. The controller never checks that `repository.owner.login` (the field used to pick the signing key) matches `repository.full_name`'s owner (the field the handler actually consumes).

### Impact Explanation
Depending on the forged event, this crosses meaningful trust boundaries for an entirely unrelated repository/organization:
- `push` → enqueues `GithubSyncJob`/`stack.sync_github` for the victim org's stack with an attacker-chosen `expected_head_sha`. [9](#0-8) 
- `status`/`check_suite` → forges CI/check state for the victim org's commits, which downstream deploy-gating logic uses to decide if a commit is deployable — an operator working on the victim org could ship a commit whose real CI never passed.
- `pull_request` (labeled/unlabeled/reopened/closed) → archives/unarchives/creates review stacks for the victim org's repositories. [10](#0-9) 

The most severe of these (forged `status` enabling a commit that never passed real CI to be treated as deployable) matches the rules' High-impact category of escalating trust/authorization state used to gate deploys. This requires no `ApiClient` token, no `github_access_token`, and no privileged Shipit account — only knowledge of a webhook secret for *any one* configured organization, which is inherent, self-chosen knowledge for that organization's own GitHub App owner.

### Likelihood Explanation
This only applies to installations using the documented multi-organization configuration (`docs/setup.md`, "Using Multiple Github Applications"), where distinct orgs are onboarded with independent secrets under one Shipit instance. Within that documented, supported configuration, the attack requires nothing beyond direct HTTP access to `/webhooks` and a legitimately-owned secret for one tenant, which is exactly the kind of "unprivileged relative to other tenants" actor this scan targets. In single-organization deployments (the common case) `repository_owner` and `repository.full_name`'s owner are the same trust domain by construction, so the mismatch is not exploitable there.

### Recommendation
After `verify_signature` succeeds, re-derive the acting organization from the same field the handlers will use (`repository.full_name`'s owner segment, or `organization.login` for org-level events) and assert it matches `repository_owner` used for key selection; reject the request (422) on mismatch. Alternatively, key selection and payload authorization should both be derived from a single canonical field, validated once, and passed to handlers.

### Proof of Concept
1. Configure Shipit in multi-org mode with `orgA` and `orgB`, each with their own GitHub App and `webhook_secret` (per `docs/setup.md` multi-org section).
2. As the (unprivileged w.r.t. `orgB`) owner of `orgA`'s GitHub App, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_orgA, body)>` using the known `orgA` secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository.owner.login`), validates the signature against `webhook_secret_orgA`, and passes — because the attacker knows this secret.
6. `create` dispatches the parsed body to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack, despite the request never being authenticated for `orgB`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
