### Title
Webhook signature verification is keyed on the payload's `repository.owner`/`organization` field, but handlers act on the independent, unauthenticated `repository.full_name` field, allowing cross-organization writes in multi-org Shipit deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the equality-binding analog of the `nord` `decode_action` bug: there, the signature bytes covered the wrong/undersized data (a length-mismatch panic). Here, the binding broken is: `organization used to select and verify the webhook signature` ≠ `repository the webhook handler actually writes to`. Shipit's webhook controller derives which `GitHubApp` (and thus which `webhook_secret`) to verify against from `repository.owner.login`/`organization.login`, but every handler resolves the actual `Repository`/`Stack` to mutate from the sibling field `repository.full_name` — a field never covered by that org-selection logic, only by the raw-body HMAC that was computed under the attacker's *own* legitimately-known secret.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the JSON payload and uses it to pick which configured GitHub App/secret to verify with: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, etc.) in a multi-tenant deployment, as documented and configured via `secrets.yml`'s per-org `github:` map: [3](#0-2) [4](#0-3) 

Signature verification only checks that the HMAC matches the secret belonging to `repository_owner` — it never checks that `repository_owner` corresponds to the repository the payload claims to act on: [5](#0-4) 

Once verification passes, `Shipit::Webhooks.for_event` dispatches to handlers that resolve the target repository purely from `repository.full_name`, a completely different JSON key never used in the signature-selection step: [6](#0-5) [7](#0-6) [8](#0-7) 

An attacker who legitimately administers **their own** GitHub organization/App installation registered in the same multi-tenant Shipit instance (e.g., organization `A` in `secrets.yml`) knows `A`'s real `webhook_secret` (or can simply cause GitHub to send a real, correctly-signed webhook for org `A`, then intercept/replay/modify it because HMAC of the *body* is verified before any binding check exists — but the body itself carries the two independent fields). They can craft (or amend a legitimately-signed) payload where:
- `repository.owner.login` / `organization.login` = `A` (so `verify_signature` selects `A`'s webhook_secret and the signature is computed correctly with it), and
- `repository.full_name` = `"B/victim-repo"` (a repository belonging to a different, unrelated organization `B` also hosted on the same Shipit instance).

`verify_signature` succeeds because the HMAC is valid for the body under `A`'s secret. Then `PullRequestHandlers`, `PushHandler`, `StatusHandler`, etc. resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` → org `B`'s repository/stack, and perform writes (e.g. `ClosedHandler#process` calls `review_stack.archive!`; `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!`, provisioning a review stack that later runs `shipit.yml` deploy steps) against org `B`'s stack — despite the request never being authenticated against org `B` at all.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written," matching the Critical criterion "cross-repository writes." A tenant with no privileges on organization `B` can trigger state changes (review-stack creation/archival, commit status updates, sync jobs, and downstream task/deploy execution) against `B`'s stacks, using only a webhook secret they legitimately possess for their own unrelated organization `A`.

### Likelihood Explanation
This requires a multi-organization Shipit configuration (explicitly supported and documented, e.g. `config/secrets.development.shopify.yml`) where at least two independent GitHub orgs are onboarded to the same Shipit instance. Any tenant/organization admin who controls their own org's webhook secret (an unprivileged actor with respect to the *other* org) can exploit this without needing a Shipit session, `ApiClient` token, or GitHub App private key — they only need what they already legitimately hold for their own org.

### Recommendation
After signature verification, re-derive `repository_owner` from `params.dig('repository', 'full_name')` (or equivalently re-validate that `full_name`'s owner segment equals the `repository_owner`/`organization.login` used to select the verifying app) and reject the request if they diverge, before dispatching to any handler. Concretely, in `WebhooksController#verify_signature` (or `#create`), assert `repository_owner == params.dig('repository', 'full_name').to_s.split('/').first` and return 422 otherwise.

### Proof of Concept
1. Configure Shipit with two organizations `A` and `B` per the multi-org schema in `config/secrets.development.shopify.yml`.
2. As the administrator of org `A`'s GitHub App, capture (or construct) a `pull_request` "closed" webhook JSON body where:
   - `organization.login` / `repository.owner.login` = `"A"`
   - `repository.full_name` = `"B/victim-repo"` (an org `B` repo that has an active Shipit review stack)
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(A_webhook_secret, raw_body)>` using org `A`'s known secret.
4. POST the body with headers `X-Github-Event: pull_request` and the above signature to `/webhooks`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "A").verify_webhook_signature(...)`, which succeeds. `ClosedHandler` then resolves `Shipit::Repository.from_github_repo_name("B/victim-repo")` and calls `review_stack.archive!`, mutating org `B`'s stack state despite the request never being authenticated for org `B`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
