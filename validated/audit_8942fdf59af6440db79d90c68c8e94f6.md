### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup enables bot-identity deploy/merge on an unrelated stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `params.sha` with no repository/stack scoping, then calls `commit.create_status_from_github!`, which can toggle `deployable?`/`merge_status` and enqueue `ContinuousDeliveryJob`/`ProcessMergeRequestsJob`. Because `WebhooksController#verify_signature` authenticates the webhook only against the *organization* extracted from the attacker-supplied `repository.owner.login` field, not against the specific repository whose commit is being mutated, a validly-signed webhook for one repository in an org can write a `Status` row onto a `Commit` belonging to a *different* stack/repository whenever the SHAs coincide (e.g., shared git history between a fork and its upstream, or any commit that is reachable in more than one tracked repository).

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == payload.repository`, i.e. that a `Status` created from a webhook only ever applies to the repository that authenticated the request. In reality:

- `WebhooksController#verify_signature` resolves the signing app via `Shipit.github(organization: repository_owner)` where `repository_owner` is read directly from attacker-controlled JSON: `params.dig('repository', 'owner', 'login')`. [1](#0-0) [2](#0-1) 
- This check only proves the request was HMAC-signed with the secret configured for that *organization's* GitHub App/webhook — it says nothing about which specific repository or commit the event applies to.
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no filter on `stack_id`, `repository_id`, or even the `repository` sub-object of the payload. [3](#0-2) 
- `Commit#create_status_from_github!` → `add_status` mutates the commit's status list, re-evaluates `simple_state`, and — on a `pending`/`success` transition — calls `stack.schedule_merges` (enqueues `ProcessMergeRequestsJob`) and fires `deployable_status`/`commit_status` hooks. [4](#0-3) 
- Separately, `Commit#after_create` schedules `ContinuousDeliveryJob`, and any stack with `continuous_deployment: true` is picked up by `Stack.schedule_continuous_delivery` / cron and runs `trigger_continuous_delivery`, which calls `trigger_deploy(commit, Shipit.user, ...)` — i.e. the deploy is created and run **as the configured bot identity (`Shipit.user`)**, not as any external actor. [5](#0-4) [6](#0-5) 

Exploit flow:
1. Victim stack A tracks `victim/app` with `continuous_deployment: true` and a required `ci/coverage` context; it has a commit with SHA `S` (e.g. present because `victim/app` was forked, or `S` is a commit that is reachable from both the upstream and a fork due to shared git history).
2. Attacker owns/administers a different repository under the *same GitHub organization* as `victim/app` (or any repository whose org uses the same webhook signing secret configuration resolved via `Shipit.github(organization: ...)`), and can trigger a genuinely-signed `status` webhook from GitHub for that repository (e.g., by posting a commit status via the GitHub API on a commit that also carries SHA `S`, which GitHub then relays to Shipit's webhook endpoint with a valid HMAC signature for that org).
3. The webhook payload's `repository.owner.login` matches the org used for signing (so `verify_signature` passes), but the payload's `sha` is `S`, which also exists in victim stack A.
4. `StatusHandler#process` finds **all** `Commit` rows with `sha == S` across every stack/repo in the Shipit instance — including the one belonging to victim stack A — and calls `create_status_from_github!` on it with `context: 'ci/coverage', state: 'success'`, flipping A's required-context status without victim A's own repository ever authenticating this data.
5. This changes `commit.deployable?`/`stack.merge_status` for stack A, triggering `ProcessMergeRequestsJob` and/or being picked up by `ContinuousDeliveryJob`, which runs `trigger_deploy` using `Shipit.user` (the bot identity configured via `bot_login`), producing an unauthorized deploy/merge signed off as the bot.

Existing guards do not stop this: `verify_signature` checks only the org-level HMAC, not per-repository correspondence; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema on `StatusHandler` (`params do requires :sha ... end`) validates types only, not repository ownership; there is no `Repository`/`Stack` scoping anywhere in the read (`Commit.where(sha: params.sha)`) or write (`create_status_from_github!`) path.

### Impact Explanation
A payload authenticated for one repository/org context can write a `Status` record — and consequently trigger a deploy/merge — for a `Commit` belonging to an unrelated stack, provided the two repositories share a commit SHA (structurally guaranteed for forks/upstream pairs, and possible whenever any tracked repository's history overlaps another's). Because auto-triggered continuous delivery deploys run as `Shipit.user` (the configured bot identity from `bot_login`), the attacker can force a "ship" (or block a required check to cause a "block") on the victim stack without ever authenticating against the victim repository directly. This is a payload for one repository mutating another's stack/commit, resulting in an unauthorized deploy — matching the Critical impact category.

### Likelihood Explanation
Preconditions: victim stack must have `continuous_deployment: true` and/or merge-queue behavior gated on the flipped context (`ci/coverage`), and there must be a SHA shared between the attacker's authenticated repository/org and the victim's tracked commit — most naturally via a public fork relationship, which is trivial and unprivileged for the attacker to set up (any GitHub user can fork a public repo and it will share commit SHAs with the upstream by construction). The attacker needs the ability to generate a validly-signed webhook for *some* repository under an org configuration Shipit trusts — this can be their own repository if Shipit's GitHub App/webhook secret is shared at the organization level (common GitHub App configuration), which is within the stated attacker capabilities ("push to a fork... emit webhooks from a repository they own"). No Shipit session, API token, or maintainer role is required.

### Recommendation
Scope the status lookup and write to the repository/stack that actually authenticated the webhook: pass the payload's `repository` (owner/name) into `StatusHandler#process` and constrain the query to `Commit.joins(:stack).merge(Stack.where(repository: matching_repo)).where(sha: params.sha)` (or equivalent `stack.repository.full_name == payload.repository.full_name` check) before calling `create_status_from_github!`. Reject or ignore the event if the payload's repository does not match any stack whose repository corresponds to the org/repo that produced the verified signature.

### Proof of Concept
minitest plan (no live GitHub, uses existing `GithubHook.any_instance.stubs(:verify_signature).returns(true)` pattern seen in `test/controllers/webhooks_controller_test.rb`):

```ruby
test "a status payload for repository B flips a required context on an unrelated stack A sharing the same sha" do
  stack_a = shipit_stacks(:cross_tenant_victim) # continuous_deployment: true, bot_login configured, requires ci/coverage
  shared_sha = "deadbeefcafefeed0000000000000000000000"
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)

  before = commit_a.deployable? # explicit equality being tested
  refute before

  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/coverage',
    'branches' => [{ 'name' => stack_a.branch }],
    'repository' => { 'owner' => { 'login' => 'attacker-org-or-shared-org' }, 'full_name' => 'attacker/unrelated-repo' }
  }.to_json

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_a]) do
    post :create, body: payload, as: :json
  end

  commit_a.reload
  after = commit_a.deployable?
  assert after # binding "status only affects the authenticating repository" is broken: before != after despite payload.repository != stack_a.repository
end
```

Assertions on both sides of the equality: `commit_a.stack.repository.full_name` (victim, e.g. `victim/app`) vs `payload['repository']['full_name']` (attacker-controlled, e.g. `attacker/unrelated-repo`) — these differ, yet `commit_a.deployable?`/`stack_a.merge_status` still changes, proving the invariant "A `ci/coverage` status affects only the repository that authenticated it" is violated.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
