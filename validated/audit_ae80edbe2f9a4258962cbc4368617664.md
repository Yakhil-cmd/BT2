### Title
Organization-fallback signature bypass lets an attacker forge a `status` webhook and mark an arbitrary victim commit deployable/ship it - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#repository_owner` picks the verifying `GitHubApp` from `params.dig('repository','owner','login') || params.dig('organization','login')`, while `Shipit::Webhooks::Handlers::StatusHandler#process` never consults any repository field at all — it matches purely on `Commit.where(sha: params.sha)` across the whole `commits` table. This means signature verification is bound to whatever organization the attacker names in `organization.login`, but the resulting state mutation (`commit.create_status_from_github!`) is applied globally by SHA, decoupled from that organization/repository. If the attacker selects an organization whose `GitHubApp` has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`), so the forged event needs no valid signature at all.

### Finding Description
The invariant that should hold: `verified_owner(repository_owner) == authoritative_owner_of(mutated_commit)`. In this codebase that binding does not exist:

- `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) is computed purely from attacker-supplied JSON: `params.dig('repository','owner','login') || params.dig('organization','login')`.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) calls `Shipit.github(organization: repository_owner)` and checks `github_app.verify_webhook_signature(header, raw_post)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) has `return true unless webhook_secret` — i.e., if the selected organization's app config has no `webhook_secret` set, **any** signature (even a garbage/missing one) passes.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no `repository`/`full_name` check anywhere in this handler; any commit row in the database with a matching `sha`, regardless of which stack/repository it belongs to, gets mutated.

Exploit flow:
1. Attacker identifies (a) any organization configured in Shipit's multi-org GitHub app config that lacks a `webhook_secret` (or otherwise has a weak/absent secret), and (b) the `sha` of a real, pending commit belonging to a victim's stack (commit SHAs are typically visible via the stack's public commit list/GitHub itself).
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status`, no `repository` key, but `organization: { login: "<org-without-secret>" }`, and body `{ "sha": "<victim sha>", "state": "success", "context": "<required-context>" }`.
3. `drop_unhandled_event` passes (`status` is handled). `verify_signature` computes `repository_owner` = the attacker-chosen org, fetches that org's `GitHubApp`, and since it has no `webhook_secret`, verification returns `true` regardless of the actual `X-Hub-Signature` sent.
4. `StatusHandler.process` runs `Commit.where(sha: ...)` and finds the victim's commit (owned by an entirely different, unrelated repo/org), and calls `create_status_from_github!`, writing a new `Status` row.
5. If this satisfies `stack.required_statuses`/`blocking_statuses`, `Commit#deployable?` becomes true (`app/models/shipit/commit.rb:227-229`), and `schedule_continuous_delivery`/`stack.schedule_merges` can trigger an automatic deploy or merge of the victim's commit (`app/models/shipit/commit.rb:281-287, 379-384`) — with no relation to the organization that "verified" the webhook.

None of the documented guards stop this: `verify_signature` only checks the *attacker-selected* organization's secret, not the actual owner of the mutated resource; `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates types/presence of `sha`/`state`, not repository ownership; there is no `require_permission!`/`stacks` scoping in the webhook path since it is intentionally unauthenticated (webhook signature is the only guard, and it is misapplied here).

### Impact Explanation
An unauthenticated, unprivileged internet requester can write `Status` rows for a commit belonging to any stack/repository in the Shipit installation, as long as (a) they know/guess a valid commit SHA already tracked by Shipit for the victim stack, and (b) at least one organization exists in the multi-tenant GitHub app config without a `webhook_secret` (or with a leaked/reused organization identity they can otherwise pass through). This is a cross-tenant "payload for one repository mutating another's commit/stack" issue matching the Critical category: it can flip `Commit#deployable?` to true and trigger `schedule_continuous_delivery`/auto-merge for a victim's commit, i.e., an unauthorized deploy or merge triggered by data attributed to no verified repository. It is repeatable against any commit SHA the attacker can enumerate and any stack in the installation, not limited to a single tenant.

### Likelihood Explanation
Requires: (1) a multi-organization GitHub app configuration in `secrets.github` (`github_default_organization`/`github_app_config`) where at least one configured organization omits `webhook_secret` — a realistic real-world misconfiguration for staging/legacy orgs, but not guaranteed on every deployment; (2) knowledge of a victim commit's SHA, which is generally discoverable via GitHub itself or Shipit's own (potentially public) stack pages. No Shipit session, API token, or GitHub secret is needed. If the precondition (an org without a secret) holds, the attack is trivial and repeatable with a single unauthenticated HTTP POST per target commit.

### Recommendation
- Bind the verified organization to the actual resource being mutated: require `repository.full_name`/`repository.owner.login` in the payload for every handled event and reject events where the field is absent, rather than falling back silently to `organization.login`.
- After signature verification, re-derive the target commit/stack strictly by the verified repository (e.g., `Stack` scoped by `repository_owner`/`repository_name`), and have `StatusHandler` scope `Commit.where(sha: ..., stack: { repository: verified_repo })` instead of an unscoped, cross-tenant `Commit.where(sha: ...)`.
- Make `GitHubApp#verify_webhook_signature` fail closed when `webhook_secret` is blank instead of returning `true`, or at minimum log/alert and refuse events for orgs with no configured secret.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
```ruby
test "status webhook via organization fallback mutates a commit in a repo the attacker does not own" do
  # Arrange: two orgs configured; "victim-org" has a real webhook_secret,
  # "no-secret-org" has none.
  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', {}) # no webhook_secret set
  )

  victim_stack = shipit_stacks(:shipit)   # belongs to victim repo/org
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

  # Binding under test, stated explicitly:
  # verified_owner = repository_owner(payload) == 'no-secret-org'
  # authoritative_owner_of(victim_commit) == victim_stack.repo_owner ('shopify' or similar)
  # These MUST differ, yet the mutation must still succeed -> proves the break.

  payload = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'ci/required',
    organization: { login: 'no-secret-org' } # no `repository` key at all
  }.to_json

  post '/webhooks', params: payload, headers: {
    'X-Github-Event' => 'status',
    'X-Hub-Signature' => 'sha1=deadbeef', # garbage signature
    'Content-Type' => 'application/json'
  }

  assert_response :ok
  victim_commit.reload
  assert_equal 'success', victim_commit.status.state
  # Assert the divergence: verifier organization != commit's actual repository owner
  refute_equal 'no-secret-org', victim_stack.repository.owner
end
```
This demonstrates that `repository_owner` used for `verify_signature` ("no-secret-org") is not equal to the authoritative owner of the mutated `Commit` (`victim_stack.repository.owner`), yet the status mutation on the victim's commit succeeds — confirming the cross-tenant integrity violation.
