### Title
Webhook signature verified against `repository.owner.login` but write target resolved from `repository.full_name` — cross-organization webhook spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . However, once the signature check passes, the actual repository/stacks that are mutated are looked up using a *different* field of the same attacker-controlled JSON body: `Shipit::Webhooks::Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` [2](#0-1) , and `Repository.from_github_repo_name` splits that string into owner/name and looks up any repository row regardless of which organization's secret validated the request [3](#0-2) .

### Finding Description
Shipit supports multi-organization GitHub App configuration, where each organization has its own `webhook_secret`, looked up via `Shipit.github(organization:)` / `github_app_config(organization)` [4](#0-3) . The binding the engine relies on is: *"the organization whose secret signed this webhook" == "the organization/repository whose state is written."* This binding is broken because the two sides are read from two independent, equally attacker-controlled JSON fields in the raw POST body:

- Signature validation org: `params.dig('repository','owner','login')` (fallback `params.dig('organization','login')`).
- Write-target repository: `payload.dig('repository','full_name')`, consumed by `Handler#stacks` → `Repository.from_github_repo_name` → `Stack` lookups [5](#0-4) .

An attacker who administers (or has push access to) any single repository/organization configured in Shipit can create a GitHub webhook on that repository, choosing the `webhook_secret` themselves (since GitHub webhook secrets are set by whoever configures the webhook). They can then send Shipit a forged POST whose body sets `repository.owner.login` to their own organization (so the HMAC computed with their own known secret passes `verify_signature`), while setting `repository.full_name` to an arbitrary `"other-org/other-repo"` value. Because `verify_signature` only checks the raw body bytes against a secret chosen by the (attacker-controlled) owner field — not that the owner field is consistent with `full_name` — the forged payload is accepted, and the handler acts on the victim repository's stacks using data entirely dictated by the attacker.

### Impact Explanation
For `PushHandler`, this lets the attacker enqueue `GithubSyncJob` for any stack belonging to a victim repository/organization they don't own, by supplying an attacker-chosen `after` (expected head SHA) and `ref` [6](#0-5) . `GithubSyncJob` fetches commits from the real GitHub API for that stack using its legitimately configured GitHub App token and appends/creates local `Commit` rows from whatever the actual GitHub history shows for the victim repo [7](#0-6) , and this in turn is what stacks/deploy pipelines observe as "new commits available to deploy" — i.e. it can be used to force a resync/trigger deploy tooling on a repository the attacker has no authorization over, purely by spoofing a webhook that appears organizationally valid. This maps to the rules' "unauthorized deploy" impact category, since the sync directly feeds the deploy-eligible commit list for a stack the attacker doesn't control, and other handlers (`status`, `check_suite`, `membership`) similarly key their writes off attacker-controlled payload fields once the mis-scoped signature check passes.

### Likelihood Explanation
Requires an attacker to control a webhook secret for at least one organization/repository already onboarded to the same Shipit instance (e.g., they are an admin of one of many repos hosted by a shared Shipit deployment), which is a realistic multi-tenant scenario given the engine explicitly supports `github_organizations` with per-org secrets. No Shipit session, API token, or GitHub App private key is needed — only the raw HTTP POST and knowledge of a webhook secret the attacker configured themselves.

### Recommendation
Bind signature verification and repository resolution to the *same* trusted field, and validate that they agree: derive the target repository/org strictly from `repository.full_name`, verify the signature using the secret associated with that resolved repository's actual organization (as stored in Shipit's `Repository` record, not the payload's `owner.login`), and reject payloads where the payload-provided owner does not match the resolved repository's real owner.

### Proof of Concept
1. Shipit is configured with two organizations, `victim-org` and `attacker-org`, each with its own `webhook_secret` (multi-org config per `lib/shipit.rb#github_app_config`).
2. Attacker registers a GitHub webhook pointed at Shipit's `/github/auth/../webhooks` endpoint (any repo they administer under `attacker-org`), choosing `webhook_secret = "known-to-attacker"`.
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. `X-Hub-Signature` is computed with `attacker-org`'s secret (`known-to-attacker`) over the raw body.
5. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against the attacker's own secret [8](#0-7) .
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, which is unrelated to `attacker-org`, and enqueues `GithubSyncJob` for `victim-org/victim-repo`'s stacks [9](#0-8) .

This demonstrates the analog break of "organization authenticated" (via signature) vs. "repository that is written" (via `full_name`), consistent with the reported bug class of parameters/fields acted upon that are not covered by the verification step.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
```
