### Title
Recipient Contract Reverting on KLAY Receipt Permanently Locks Bridged KAIA and Corrupts Bridge Nonce State — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` delivers KLAY to a user-supplied `_to` address via a raw low-level call and hard-reverts the entire transaction if the call fails. Because `_to` is taken directly from the user's `requestKLAYTransfer` call with no validation, any user can specify a contract that reverts on KLAY receipt. Every operator attempt to settle that nonce will revert, permanently locking the bridged KAIA and freezing `lowerHandleNonce` and `recoveryBlockNumber` at the poisoned nonce.

---

### Finding Description

`requestKLAYTransfer` accepts an arbitrary `_to` address with no validation:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [1](#0-0) 

On the destination chain, operators call `handleKLAYTransfer`. After updating nonce bookkeeping state, it delivers KLAY via a raw call and hard-reverts if the call fails:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [2](#0-1) 

Because `require(ok, ...)` causes the entire transaction to revert, all state mutations that occurred earlier in the same call — `_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber`, and `_updateHandleNonce` — are also rolled back:

```solidity
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
``` [3](#0-2) 

`_updateHandleNonce` advances `lowerHandleNonce` only while `handleNoncesToBlockNums[i] > 0` for consecutive nonces starting from `lowerHandleNonce`. Since the poisoned nonce's entry is always reverted to zero, `lowerHandleNonce` can never advance past it:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [4](#0-3) 

The VT recovery system reads `RecoveryBlockNumber` and `LowerHandleNonce` from the bridge contract to determine where to begin scanning for unhandled events:

```solidity
hint.blockNumber, err = to.bridge.RecoveryBlockNumber(nil)
...
handleNonce, err := to.bridge.LowerHandleNonce(nil)
``` [5](#0-4) 

With both values frozen at the poisoned nonce, the recovery system perpetually re-scans the same range and perpetually fails to settle it.

---

### Impact Explanation

- **Bridged KAIA permanently locked**: The user's KLAY is deposited into the source bridge on `requestKLAYTransfer`. On the destination side, `handleKLAYTransfer` can never succeed, so the KAIA is irrecoverable.
- **Bridge nonce state corruption**: `lowerHandleNonce` and `recoveryBlockNumber` are permanently frozen at the poisoned nonce, corrupting the bridge's accounting of which transfers have been settled.
- **VT recovery system disruption**: The off-chain recovery daemon (`valueTransferRecovery`) will detect the stuck nonce as a perpetual pending event and keep retrying, wasting operator gas and preventing the recovery system from making progress on subsequent legitimate transfers.

---

### Likelihood Explanation

The trigger requires no special privilege. Any user can call `requestKLAYTransfer` with `_to` set to a contract that has no payable fallback or that explicitly reverts on KLAY receipt. Such contracts are trivially deployable. The user sacrifices the bridging fee but permanently disrupts the bridge's nonce state and locks their own KAIA — a viable griefing vector. A malicious actor could also target another user's pending transfer if they can influence the `_to` field.

---

### Recommendation

Replace the hard-revert pattern with a pull-payment or try-catch pattern. Instead of reverting the entire transaction when `_to` rejects KLAY, record the failed delivery in a claimable mapping so the nonce is consumed and `lowerHandleNonce` can advance:

```solidity
(bool ok, ) = _to.call.value(_value)("");
if (!ok) {
    pendingWithdrawals[_to] += _value;
    emit KLAYDeliveryFailed(_to, _value, _requestedNonce);
}
```

Alternatively, validate at `requestKLAYTransfer` time that `_to` is an EOA (i.e., `_to.code.length == 0`), though this prevents legitimate contract recipients.

---

### Proof of Concept

1. Attacker deploys `MaliciousReceiver` on the destination chain:
   ```solidity
   contract MaliciousReceiver {
       receive() external payable { revert("no KLAY"); }
   }
   ```

2. Attacker calls `requestKLAYTransfer(address(maliciousReceiver), value, "")` on the source bridge, paying `value + fee`. The source bridge emits `RequestValueTransfer` with nonce N and locks the KLAY. [6](#0-5) 

3. Operators observe the event and call `handleKLAYTransfer(..., address(maliciousReceiver), value, N, ...)` on the destination bridge. The call reaches line 98, `MaliciousReceiver.receive()` reverts, `require(ok, ...)` fires, and the entire transaction reverts — including the `handleNoncesToBlockNums[N]` write. [2](#0-1) 

4. Every subsequent operator retry for nonce N reverts identically. `lowerHandleNonce` remains at N, `recoveryBlockNumber` remains at the block before N. The KAIA is permanently locked in the source bridge. The VT recovery daemon loops indefinitely on nonce N. [4](#0-3)
