### Title
Missing `return Err(...)` after invalid `num_cycles` check allows out-of-range cycle counts to pass `StackStxOp::check()` - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`StackStxOp::check()` validates `stacked_ustx` and the signer key with early `return Err(...)` on failure, but the `num_cycles` guard only logs a `warn!` and falls through to `Ok(())`, so a `StackStxOp` with `num_cycles == 0` or `num_cycles > POX_MAX_NUM_CYCLES` is accepted as valid and forwarded for pox-locking.

### Finding Description
The equality that must hold is: for every `StackStxOp` that reaches PoX-locking, `0 < op.num_cycles <= POX_MAX_NUM_CYCLES`. This is enforced for `stacked_ustx` (`return Err(op_error::StackStxMustBePositive)` at [1](#0-0)  ) and for the signer key (`.map_err(|_| op_error::StackStxInvalidKey)?` at [2](#0-1) ), but the `num_cycles` branch only warns without returning: [3](#0-2) 

Because there is no `return` statement in that `if` block, control flow falls through to `Ok(())` at line 418 regardless of the value of `num_cycles`. An attacker constructs a burnchain `StackStx` operation (their own BTC inputs, a `PreStxOp` first as normal) with `stacked_ustx > 0` (satisfying the first guard) and `num_cycles = 0` or `num_cycles = 255` (or any value `> POX_MAX_NUM_CYCLES`). `check()` returns `Ok(())`, and the op is passed on to be applied to the PoX contract with an out-of-range cycle count, which the wire encoding permits since `num_cycles` is serialized as a raw `u8` ( [4](#0-3) , [5](#0-4) ).

I was unable to fully trace, within the available index, the exact downstream Clarity call in `pox-5.clar`/boot contract handling of L1 `stack-stx` burnchain ops (the `.pox-5` contract call site translating `StackStxOp.num_cycles` into a Clarity `num-cycles` argument), so I cannot confirm from source whether `pox-5.clar`'s own internal cycle-count clamping (if any) provides a second layer of defense that would neutralize this at the contract level. This is a limitation of the current search; a full trace would require reading the boot contract dispatch code (e.g. `chainstate/stacks/boot/mod.rs` or `contract_call_new_stackstx` type functions) which did not return matches in this pass.

### Impact Explanation
If no downstream guard exists in the PoX contract logic, an attacker can lock STX with `num_cycles = 0`, potentially causing the reward-cycle/unlock-height computation to be undefined or to compute an unlock height that has already passed (instant unlock, i.e., unlocking value that was never properly time-locked and possibly claiming reward-slot participation without honoring the lock duration), or with `num_cycles` far above `POX_MAX_NUM_CYCLES`, causing the computed unlock height to be pushed out arbitrarily far, permanently freezing the staker's own STX. This matches Critical impact (permanent freezing of staked STX, or unlocking value never properly locked for the claimed duration) as defined in scope.

### Likelihood Explanation
This is trivially triggerable: the attacker only needs to craft their own burnchain `PreStxOp`+`StackStxOp` pair (any account with STX/BTC can do this per the threat model), setting the `num_cycles` byte in the OP_RETURN payload to `0` or `> POX_MAX_NUM_CYCLES`. No privileged role, timing, or membership state is required beyond `stacked_ustx > 0`. It is repeatable per stacking operation the attacker submits.

### Recommendation
Add a `return Err(op_error::StackStxInvalidCycles)` (or equivalent existing error variant) immediately after the `warn!` in the `num_cycles` check block in `StackStxOp::check()`:
```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(...);
    return Err(op_error::StackStxMustBePositive); // or a dedicated variant
}
```

```rust
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
```
