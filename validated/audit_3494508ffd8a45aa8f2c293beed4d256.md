### Title
Cross-organization webhook forgery via mismatched signature-verification and repository-lookup fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret used to validate the HMAC signature from the attacker-controlled JSON body field `repository.owner.login` (falling back to `organization.login`), while the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`) look up the target repository/stack from a *different* field in the same body: `repository.full_name`. Because both fields are inside the same signed payload and are independent of each other, the "organization whose secret authenticated the request" and "the repository that is written to" are never bound together.

### Finding Description
`verify_signature` computes `repository_owner` from the request body itself and uses it to pick which `GitHubApp`/secret to verify against: [1](#0-0) [2](#0-1) 

Once the signature check passes, the actual event handler resolves the repository/stack to act on using an entirely different field of the same payload: [3](#0-2) 

`Repository.from_github_repo_name` then splits and looks up by `owner/name` from that field with no cross-check against the organization used to authenticate the request: [4](#0-3) 

Shipit explicitly supports hosting multiple organizations' GitHub Apps/webhook secrets side by side in one instance, as shown by the multi-org secrets fixture used in tests (`OrgOne`, `OrgTwo`, each with its own `webhook_secret`): [5](#0-4) [6](#0-5) 

In this supported multi-tenant configuration, a member of `OrgOne` (who legitimately owns and knows the webhook secret for `OrgOne`'s installed GitHub App) can craft a webhook body where:
- `repository.owner.login` = `OrgOne` (so `verify_signature` picks `OrgOne`'s secret, which the attacker knows, and the HMAC validates)
- `repository.full_name` = `OrgTwo/some-repo` (so the handler resolves and acts on a stack belonging to a completely different organization)

This breaks the intended equality: `organization whose secret authenticated the webhook == repository the handler mutates`. Before the fix (i.e., today) these two are decoupled; the correct invariant would require the handler to only act on repositories owned by the same organization used for signature verification.

### Impact Explanation
This allows an attacker who administers their own organization's GitHub App entry (but has no privileges over the victim organization) to forge events against another organization's stacks that are hosted on the same Shipit instance — e.g. spoofed `push` events (`Handlers::PushHandler`) forcing `stack.sync_github` against another org's stack, spoofed `status`/`check_suite` events affecting deployability signals, or `membership`/`pull_request` events affecting another org's review stacks and merge queue state. This crosses a repository-ownership trust boundary the signature check was meant to enforce, matching the "Critical – cross-repository writes / unauthorized deploy or merge" impact bucket in a multi-organization Shipit deployment.

### Likelihood Explanation
The requisite conditions — a Shipit install configured for multiple organizations, each with its own webhook secret (an explicitly documented/tested configuration) — are realistic for shared/central Shipit instances. Any authenticated GitHub App owner for one of the configured orgs can trivially compute a valid HMAC over an arbitrary body they fully control (since they own the secret for their own org) and simply set `repository.full_name` to point at a victim org/repo pair hosted on the same instance. No Shipit session, API token, or repository write access to the victim repo is required.

### Recommendation
After signature verification, re-derive `repository_owner` from the verified request and enforce that it matches the owner encoded in `repository.full_name` (or better: pass the verified organization into the handler and have `Handler#stacks`/`Repository.from_github_repo_name` reject any repository whose owner differs from the organization used to verify the signature) before dispatching to `Shipit::Webhooks.for_event`.

### Proof of Concept
1. Deploy Shipit configured with two GitHub Apps, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As a member/administrator of `OrgOne`'s GitHub App (attacker), craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1 with OrgOne's known webhook_secret over the raw body>`.
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` uses `Shipit.github(organization: "OrgOne")` and succeeds because the attacker knows `OrgOne`'s secret.
5. `PushHandler#process` resolves `repository_name` from `repository.full_name` = `"OrgTwo/victim-repo"`, finds `OrgTwo`'s stacks via `Repository.from_github_repo_name`, and triggers `stack.sync_github` (or, for `status`/`check_suite`/`pull_request` events, other write operations) on `OrgTwo`'s data — despite the signature only proving control of `OrgOne`.
