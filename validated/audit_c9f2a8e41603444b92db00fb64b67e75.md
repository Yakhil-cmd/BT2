### Title
Same-batch write/read lock check-then-apply race lets `try_lock_transaction_batch` grant conflicting write+read locks on one account - (File: accounts-db/src/account_locks.rs)

### Finding Description
`try_lock_transaction_batch` splits validation into two separate passes over the batch instead of validating-and-locking each transaction atomically: [1](#0-0) 

The first pass calls `can_lock_accounts` (which calls `can_write_lock`/`can_read_lock`) for **every** transaction in the batch against the *same, unmutated* `self` state, because `self` is not updated inside this loop — locks are only mutated in the second pass via `lock_accounts` → `lock_write`/`lock_readonly`: [2](#0-1) 

`can_write_lock`/`can_read_lock` only check the pre-existing lock table, not sibling transactions in the same batch: [3](#0-2) 

Because the check phase never sees the effect of earlier transactions in the same batch, two conflicting transactions (e.g. transaction 1 writes account `A`, transaction 2 reads account `A`) both pass `can_lock_accounts` when `A` had no pre-existing lock, since the check for transaction 2 runs before `A`'s write lock is ever applied. In the second pass, `lock_accounts`/`lock_write`/`lock_readonly` are called unconditionally with no re-validation, so both locks get applied: `write_locks[A] = 1` and `readonly_locks[A] = 1` simultaneously. Both transactions are returned as `Ok(())`, violating the documented invariant ("a write-locked account cannot be read-locked and vice versa").

An unprivileged attacker only needs to submit two transactions in the same processing batch: one that writes a target account (e.g., a `StakeInstruction::Withdraw` on a stake account, or any writable-account instruction) and one that merely lists the same account as a readonly account (any account can be referenced readonly by anyone regardless of ownership — no signer/owner check is required for readonly locking). No validator, leader, or privileged access is needed; only crafting two transactions that land in the same `try_lock_transaction_batch` call (e.g., submitted together in the same slot/batch by the client).

### Impact Explanation
This breaks the fundamental read/write mutual-exclusion invariant that the runtime's parallel transaction scheduler relies on to guarantee that accounts under concurrent write are never concurrently read. If both a writer and reader transaction on the same account are granted locks in the same batch, they can be scheduled to execute concurrently, allowing the reader to observe a partially-updated/torn account state depending on thread interleaving. Because interleaving is not deterministic across the network (it depends on runtime scheduling, not on a canonical instruction order), this can produce different execution results for the same block on different validators — cross-node state divergence, one of the explicitly in-scope high-impact categories.

### Likelihood Explanation
The precondition is trivial and fully attacker-controlled: submit two ordinary transactions (a write-locking one and a read-locking one on the same target pubkey) so they are processed in the same `try_lock_transaction_batch` invocation. No signer authority over the target account, no elevated privileges, and no timing race against other network participants is required — it is deterministically reproducible via a direct unit test against `AccountLocks`.

### Recommendation
Make the check-then-lock sequence atomic per transaction (validate and immediately apply the lock for that transaction before checking the next), or perform a single pass that both validates against `self` state and against already-processed transactions in the same batch, aborting (or marking `Err`) instead of leaving stale `Ok` results when an intra-batch conflict is detected. Concretely, merge `can_lock_accounts` and `lock_accounts` into a single per-transaction step within one loop over `validated_batch_keys`, rather than two independent loops.

fn test_try_lock_transaction_batch_intra_batch_conflict() {

    let tx2_keys: Vec<(&Pubkey, bool)> = vec![(&key_a, false)];

        Ok(tx2_keys.into_iter()),

    // Expected (correct) behavior: exactly one Ok and one Err(AccountInUse).
    let ok_count = results.iter().filter(|r| r.is_ok()).count();

        ok_count, 1,
        "write and read locks on the same account must not both succeed within one batch"
    );

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }
