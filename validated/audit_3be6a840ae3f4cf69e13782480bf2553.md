### Title
`swap_debt` validates activity of the repaid debt's hub but never validates the newly borrowed debt's hub, bypassing hub deprecation for new borrowing - (File: contracts/controller/src/strategies/swap_debt.rs)

### Summary
The Crawl4AI SSRF is a sibling-path gap: the non-streaming `/crawl` handler ran `validate_url_destination`, while `/crawl/stream` routed to the same fetch sink with no validation. In the controller's router strategies, `process_swap_debt` is the analogous asymmetric sibling: it calls `config::require_hub_active` on `existing_debt.hub_id` — the leg being repaid, which is always a safe operation — but performs no `require_hub_active` check on `new_debt`, the leg being borrowed. Every sibling strategy that opens exposure (`repay_debt_with_collateral`, `multiply`) gates the risk-increasing asset's hub. A deprecated hub's market can therefore still be borrowed into via `swap_debt`.

### Finding Description
In `contracts/controller/src/strategies/swap_debt.rs:44`:

```rust
config::require_hub_active(env, existing_debt.hub_id);
```

`existing_debt` is the position being *repaid* (`repay_debt_from_controller` at lines 74–85). Repayment never increases protocol risk, so gating its hub provides no protection — and per the spoke-removal docs in `contracts/controller/src/lib.rs:624-625`, repayment must remain available on deprecated/removed books.

The risk-increasing leg is `borrow_into_controller(..., new_debt, new_debt_amount, ...)` at `swap_debt.rs:55-63`, and `new_debt.hub_id` is never passed to `require_hub_active`. Compare `contracts/controller/src/strategies/repay_debt_with_collateral.rs:47-48`, which checks *both* legs:

```rust
config::require_hub_active(env, collateral.hub_id);
config::require_hub_active(env, debt.hub_id);
```

and `multiply` (`contracts/controller/src/strategies/multiply.rs`, entrypoint at `lib.rs:225-253`), where the borrowed `debt` asset is the leg that must be hub-active. The result: after governance deprecates a hub (`remove_spoke`/hub deprecation is intended to block new exposure while leaving exits open), any owner or delegate account can still mint fresh debt in that hub by calling `swap_debt(account_id, existing_debt_in_active_hub, amount, new_debt_in_deprecated_hub, swap)`. Because `existing_debt != new_debt` is asserted (`swap_debt.rs:39-43`) and same-asset cross-hub keys pass through `swap_tokens_or_passthrough`, the attacker can even refinance identical underlying assets across hubs — repaying debt in the active hub while re-creating it in the deprecated one, or escalating an existing small position in the deprecated hub.

### Impact Explanation
Hub deprecation exists to freeze new risk in a market governance has judged unsafe (stale oracle, broken asset, wind-down). `swap_debt` re-opens that gate permissionlessly for any account holding debt in a still-active hub: new borrow shares are minted (`borrow_into_controller`), spoke usage and debt accrue, and `strategy_finalize` (`strategies/mod.rs:48-56`) only re-checks solvency, not hub activity. The accepted impact classes are protocol insolvency and permanent freezing: an account can amass debt in a market whose other entry paths (supply/borrow/multiply/flash_position) are closed, blocking orderly wind-down and, if the deprecated hub's pricing or liquidity is impaired (the usual reason for deprecation), accumulating unliquidatable debt that is later socialized into the supply index via `clean_bad_debt`/`force_socialize_bad_debt`. Severity: Medium (requires an existing debt position in an active hub and a deprecated-but-still-listed hub asset; impact is circumvention of a risk-off switch rather than direct theft).

### Likelihood Explanation
Reachable by a single unprivileged address: `swap_debt` requires only owner/delegate authorization (`require_authorized_caller`, `require_owner_or_delegate`, `swap_debt.rs:37,48`) on the caller's own account, plus a non-empty `existing_debt` position — satisfiable by borrowing in any active hub first. The trigger condition is governance deprecating a hub while the `new_debt` spoke asset remains listed (deprecation blocks entrypoints, it does not necessarily unlist the asset, since `remove_asset_from_spoke` reverts while borrow usage exists, `lib.rs:712-719`). One caveat: I could not fully verify within the available passes whether `borrow_into_controller`/`positions::debt.rs` re-checks hub activity per-asset; if it does, this collapses to a redundant-check inconsistency. The code as read shows the check applied to the wrong leg, which is at minimum a validation bug matching the source advisory's shape.

### Recommendation
Replace the existing-leg check with a check on the borrowed leg, or check both:

```rust
config::require_hub_active(env, new_debt.hub_id); // was: existing_debt.hub_id
```

in `contracts/controller/src/strategies/swap_debt.rs:44`, mirroring the dual check in `repay_debt_with_collateral.rs:47-48`. Add a regression test that deprecates the `new_debt` hub and asserts `swap_debt` reverts — the same fix pattern as the advisory's per-handler test hardening rather than an occurrence count.

### Proof of Concept
1. Setup: hub A active with assets X (spoke lists X), hub B later deprecated with asset Y; attacker account has debt in X in hub A.
2. Call `swap_debt(caller, account_id, existing_debt={hubA, X}, amount, new_debt={hubB, Y}, swap=route Y→X)`.
3. `require_hub_active(existing_debt.hub_id = A)` passes (A is active); `borrow_into_controller` mints `amount` of Y debt in deprecated hub B; swap proceeds repay X debt; `strategy_finalize` passes solvency.
4. Result: fresh debt exists in hub B despite deprecation — the check that guards every other borrow path (`borrow`, `multiply`, `flash_position` via `require_hub_active` on the borrowed asset) is absent on this sibling route.
