### Title
`TaskCommands#env` lets attacker-controlled `shipit.yml` `machine.environment` override `GITHUB_TOKEN`/`GIT_ASKPASS` from `Commands#base_env` - (File: `lib/shipit/task_commands.rb`)

### Summary
`Shipit::TaskCommands#env` builds the environment passed to every task/deploy `Command` by merging `deploy_spec.machine_env` — sourced from the `shipit.yml` checked out from the stack's own branch — after the secrets set in `Shipit::Commands#base_env` (`GITHUB_TOKEN`, `GIT_ASKPASS`). For a `ReviewStack`, that branch is the PR author's own fork branch, so a PR author fully controls the final values of these keys before they reach `PTY.spawn` in `Command#start`.

### Finding Description
The broken binding: the question asserts that the set of environment **keys** reaching `PTY.spawn` should equal an operator-sanctioned allowlist; in fact no such allowlist is enforced anywhere in this merge chain.

Trace:
- `Shipit::Commands#base_env` sets `GITHUB_TOKEN` and, when `Shipit.use_git_askpass?`, `GIT_ASKPASS`: [1](#0-0) 
- `Shipit::TaskCommands#env` calls `super` (i.e. `base_env`) first, then merges `@stack.env`, task metadata, then `deploy_spec.machine_env`, then `@task.env`, in that order — with later merges winning: [2](#0-1) 
- `deploy_spec` is `DeploySpec::FileSystem.new(@task.working_directory, @stack)`, and `machine_env` reads straight from `config('machine', 'environment')`, i.e. the parsed `shipit.yml` content checked out into `@task.working_directory`: [3](#0-2) [4](#0-3) 
- For a `ReviewStack`, `stack_attributes` sets `branch: params.pull_request.head.ref` when the stack is created from the webhook payload, i.e. the attacker's own fork branch: [5](#0-4) 
- `Shipit::EnvironmentVariables#permit` is the only allowlist mechanism in the codebase, but it is never invoked in this merge path — `TaskCommands#env` merges `deploy_spec.machine_env` unconditionally with no whitelist/blocklist filtering: [6](#0-5) 

There is no code anywhere in `TaskCommands#env`, `DeploySpec#machine_env`, or `DeploySpec::FileSystem` that strips or rejects reserved keys such as `GITHUB_TOKEN`, `GIT_ASKPASS`, `PATH`, or `RUBYOPT` from `machine.environment`. The existing test suite even documents the merge behavior as intended ("`#env` merges shipit.yml `machine_env`"), confirming machine_env is expected to override prior values, without carving out reserved keys: [7](#0-6) 

Exploit flow: an attacker forks a repository with review stacks enabled (`allow_all` or satisfies label policy), commits a `shipit.yml` on their fork branch containing `machine: {environment: {GIT_ASKPASS: "/tmp/evil.sh", GITHUB_TOKEN: "..."}}`, and opens a PR. `PullRequest::OpenedHandler` provisions a `ReviewStack` on that branch. Any task/deploy run against that stack (checks, deploy steps) calls `TaskCommands#env`, which checks out the attacker's `shipit.yml` into `@task.working_directory` and merges `machine_env`, clobbering `GIT_ASKPASS`/`GITHUB_TOKEN` before `Command#start` invokes `PTY.spawn(unbundled_env, ...)`.

### Impact Explanation
If `Shipit.use_git_askpass?` is enabled, overriding `GIT_ASKPASS` to a script the attacker controls (checked into their own repo, referenced by absolute/relative path within the checkout) lets that script execute with `GITHUB_TOKEN` available in the environment, enabling exfiltration of `GITHUB_TOKEN` to an attacker-controlled destination, or arbitrary command execution as the Shipit deploy user (RCE) since the script runs on the deploy host during any `git` invocation that triggers the askpass prompt. Overriding `PATH`/`RUBYOPT` can hijack subsequent command resolution or Ruby subprocess behavior for any step run under that task's env, escalating to full RCE on the deploy host. This matches the Critical severity bar (RCE via `Command`/`PTY.spawn`, exfiltration of `GITHUB_TOKEN`).

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled with a provisioning policy the attacker can satisfy (`allow_all`, or `allow_with_label`/`prevent_with_label` which the attacker controls via their own PR labels), and `Shipit.use_git_askpass?` enabled (a documented feature, not exotic) for the most direct `GITHUB_TOKEN` exfiltration path; even without that flag, overriding `PATH`/`RUBYOPT` is possible purely from `machine.environment` merge order regardless of the askpass flag. The attacker needs no privileges beyond opening a PR from their own fork — a capability explicitly granted to "any GitHub user." This is fully repeatable against any repository with review stacks enabled and is a one-shot PR without further interaction.

### Recommendation
In `Shipit::TaskCommands#env` (and any other `Commands` subclass merging `deploy_spec.machine_env`), reject or strip reserved keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GITHUB_DOMAIN`, `PATH`, `RUBYOPT`, and any other security-sensitive key set by `base_env`) from `deploy_spec.machine_env` before merging, or re-apply `base_env`'s sensitive keys after all other merges so they cannot be overridden by repository-controlled configuration.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_security_test.rb
require "test_helper"

class TaskCommandsSecurityTest < ActiveSupport::TestCase
  test "#env does not allow shipit.yml machine_env to override GIT_ASKPASS/GITHUB_TOKEN" do
    stack = shipit_stacks(:review_stack) # or a fixture ReviewStack on attacker-controlled branch
    task = shipit_tasks(:shipit_restart)
    task.stack = stack

    commands = Shipit::TaskCommands.new(task)
    commands.stubs(:deploy_spec).returns(
      stub(
        machine_env: { "GIT_ASKPASS" => "/tmp/evil-askpass.sh", "GITHUB_TOKEN" => "stolen", "PATH" => "/tmp/evilbin:$PATH" },
        directory: nil
      )
    )

    env = commands.env

    expected_askpass = Shipit::Engine.root.join('lib', 'snippets', 'git-askpass').realpath.to_s
    assert_equal expected_askpass, env['GIT_ASKPASS'], "attacker-supplied GIT_ASKPASS overrode the trusted base_env value"
    assert_equal Shipit.github(organization: stack.repository.owner).token, env['GITHUB_TOKEN'], "attacker-supplied GITHUB_TOKEN overrode the trusted base_env value"
  end
end
```
Both assertions currently fail against the code in [2](#0-1) , because `.merge(deploy_spec.machine_env)` is applied after `super` (base_env) with no key filtering, demonstrating the divergence between the intended binding (trusted keys immutable) and actual behavior (attacker-controlled override).
