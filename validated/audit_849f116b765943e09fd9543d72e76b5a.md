## Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The GitHub `status` webhook handler resolves target commits purely by SHA, without ever scoping the lookup to the repository that the verified webhook signature actually belongs to. This breaks the same class of binding failure described in the referenced report: a value used to authenticate the request (the payload's `repository.owner.login`, used to select which organization's webhook secret to verify) is not the same value used to decide what gets written (a global `Commit.where(sha:)` query with no repository filter). Any organization able to receive a validly-signed `status` webhook for its own repository can therefore write a forged CI status onto a commit belonging to a completely different, unrelated tracked stack, as long as an identical commit SHA exists there (trivially achievable for public repositories via forking, since forks share git objects and therefore commit SHAs).

### Finding Description
`WebhooksController#verify_signature` derives the GitHub App/organization used for HMAC verification strictly from the payload's own `repository.owner.login` (or `organization.login`) field: [1](#0-0) [2](#0-1) 

This only proves that *some* organization O legitimately sent this payload — i.e., the binding being verified is "organization O is authenticated". Every other handler that acts on the payload is expected to also scope its writes to the repository declared in that same payload, via the base `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')`: [3](#0-2) 

`CheckSuiteHandler`, for example, correctly uses this repository-scoped `stacks` relation before touching any commit: [4](#0-3) 

`StatusHandler`, however, never calls `stacks` at all. It queries the global `Commit` table by SHA only and mutates whatever rows match, regardless of which repository/organization actually sent the webhook: [5](#0-4) 

The equality the code assumes is:
`organization authenticated by verify_signature (via repository.owner.login)` == `repository whose commits are updated (via Commit.where(sha:))`

But `Commit.where(sha: params.sha)` has no relationship at all to `payload['repository']`. Any Commit row anywhere in the Shipit instance with a matching `sha` column will be updated, including commits belonging to stacks tracking completely different GitHub repositories/organizations. Since Git commit SHAs are content-addressed and are shared identically between a repository and any of its forks, an attacker who forks (or otherwise obtains an object-identical copy of) a commit that Shipit already tracks for a victim's stack can trigger a legitimately-signed `status` webhook from their own, unrelated, attacker-owned repository/organization, and have `StatusHandler` write a forged status (e.g., `state: "success"`) onto the victim's tracked commit.

### Impact Explanation
`Commit#create_status_from_github!` persists CI status entries that Shipit's merge/deploy checklist and merge-queue gating logic read to decide whether a commit is safe to deploy or merge (status checks are one of the standard checklist items gating deploys in this engine). By forging a passing status on an arbitrary victim commit from an attacker-controlled organization's webhook, an attacker can make a commit appear to have passed required CI checks it never actually passed, enabling an unauthorized/unsafe deploy or merge-queue advance on a stack the attacker has no legitimate access to — this crosses the "cross-repository writes" / "unauthorized deploy" impact bar, since the write is not scoped to the authenticated repository at all.

### Likelihood Explanation
This requires no privileged credentials, Shipit session, `ApiClient` token, or `webhook_secret`/`api_clients_secret` knowledge — the attacker only needs a GitHub organization/repository of their own with Shipit's GitHub App (or configured webhook) installed, which is the normal, unprivileged onboarding flow for any Shipit customer/organization on a shared instance. Obtaining a SHA-identical commit to a public victim commit is trivial via a GitHub fork. The remaining requirement — Shipit tracking a stack for the attacker's own repository — is a standard, non-privileged setup step, not an elevated permission.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve commits only through `stacks.commits.where(sha: params.sha)` (i.e., restrict the lookup to commits belonging to stacks whose repository matches `payload['repository']['full_name']`) instead of querying the global `Commit` table by SHA alone.

### Proof of Concept
1. Attacker controls organization `Attacker/evil-repo` with Shipit's GitHub App installed and a stack tracked (unprivileged, normal onboarding).
2. Victim organization `Victim/target-repo` has a tracked Shipit stack with a public commit `abc123...`.
3. Attacker forks `Victim/target-repo` into `Attacker/evil-repo` (or otherwise reproduces the identical commit object), so `abc123...` now also exists in the attacker's repo, sharing the exact same SHA.
4. Attacker triggers (e.g., via their own CI, or the GitHub Statuses API on their fork, or a crafted push to a CI system webhooked into their org) a `status` event for commit `abc123...` with `state: "success"` in `Attacker/evil-repo`.
5. GitHub signs and delivers this webhook using Attacker's org's webhook secret; `WebhooksController#verify_signature` validates it successfully because it only checks that the org owning `Attacker/evil-repo` is authenticated.
6. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which matches the row for the *victim's* tracked commit as well, and calls `create_status_from_github!`, writing a forged "success" status onto the victim's commit — with no repository/organization check ever performed. module Shipit
  module Webhooks

        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|

          end
        end
      end
