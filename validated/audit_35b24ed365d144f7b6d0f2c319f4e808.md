### Title
Missing Zero-Address Validation in `handleKLAYTransfer` Enables Permanent KLAY Drain from Bridge Liquidity — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`requestKLAYTransfer` and `handleKLAYTransfer` in `BridgeTransferKLAY.sol` perform no `require(_to != address(0))` check. Any user can call `requestKLAYTransfer(address(0), ...)` on the source bridge, causing the destination bridge to irrecoverably send KLAY to `address(0)` via a low-level `.call.value()`, permanently destroying KLAY from the bridge's liquidity pool.

---

### Finding Description

`requestKLAYTransfer` accepts a caller-supplied `_to` address with no zero-address guard: [1](#0-0) 

It delegates to `_requestKLAYTransfer`, which also performs no zero-address check and emits a `RequestValueTransfer` event with whatever `_to` was supplied: [2](#0-1) 

The bridge relayer (`node/sc/bridge_manager.go`) reads this event and faithfully calls `handleKLAYTransfer` on the counterpart chain, passing the `_to` from the event verbatim: [3](#0-2) 

`handleKLAYTransfer` then executes a raw low-level call with value directly to `_to`, with no zero-address guard: [4](#0-3) 

In the EVM, `address(0).call.value(v)("")` succeeds and returns `true` (address(0) has no code; the call does not revert). The `require(ok, ...)` check passes, the nonce is consumed, and the KLAY is permanently lost.

This is asymmetric with the ERC20 and ERC721 handle paths: `handleERC20Transfer` calls `ERC20Mintable.mint(_to, _value)` or `safeTransfer(_to, _value)`, both of which revert on `address(0)` via OpenZeppelin's internal guards: [5](#0-4) 

`handleERC721Transfer` similarly calls `mintWithTokenURI` or `IERC721.transferFrom`, both of which revert on `address(0)`: [6](#0-5) 

No equivalent protection exists for native KLAY.

---

### Impact Explanation

In non-mintBurn mode, the destination bridge holds a KLAY liquidity pool. Each successful `handleKLAYTransfer` with `_to = address(0)` drains `_value` KLAY from that pool to the zero address. The source bridge simultaneously locks the user's KLAY. The net result is:

- Destination bridge loses `_value` KLAY (permanently unrecoverable).
- Source bridge accumulates locked KLAY that can never be matched to a successful destination transfer.
- Bridge liquidity is progressively drained, eventually preventing all future legitimate KLAY withdrawals.

This is an unauthorized burn of system-managed bridge funds (KAIA/KLAY) satisfying the allowed impact gate.

---

### Likelihood Explanation

The trigger is fully unprivileged: any EOA can call `requestKLAYTransfer(address(0), value, extraData)`. The attacker pays `value + fee` in KLAY on the source chain per drain event, making it a costly but executable griefing attack. Accidental triggering (user error) is also plausible. The operator has no on-chain mechanism to reject a zero-address destination once the source-chain event is emitted.

---

### Recommendation

Add a zero-address guard at both the request and handle entry points:

In `_requestKLAYTransfer` (source side):
```solidity
require(_to != address(0), "zero destination address");
```

In `handleKLAYTransfer` (destination side):
```solidity
require(_to != address(0), "zero destination address");
```

The same guard should be added to `_requestERC20Transfer` and `_requestERC721Transfer` for defense-in-depth, even though their handle-side token contracts currently revert on `address(0)`.

---

### Proof of Concept

1. Deploy source and destination bridge contracts in non-mintBurn mode; fund destination bridge with 100 KLAY.
2. Call on source bridge:
   ```solidity
   sourceBridge.requestKLAYTransfer{value: 10 ether}(
       address(0),   // _to = zero address
       9 ether,      // _value
       ""
   );
   ```
   Transaction succeeds; `RequestValueTransfer` event emitted with `_to = address(0)`.
3. Bridge relayer picks up the event and calls on destination bridge:
   ```solidity
   destBridge.handleKLAYTransfer(
       txHash, from, address(0), 9 ether, nonce, blockNum, ""
   );
   ```
4. `address(0).call.value(9 ether)("")` returns `true`; `require(ok)` passes.
5. Destination bridge balance drops from 100 KLAY to 91 KLAY; 9 KLAY is permanently lost.
6. Repeat to fully drain the bridge liquidity pool. [7](#0-6) [1](#0-0)
