### Title
`ProxyType::NonTransfer` in `collectives-westend` and `coretime-westend` fails open by omitting `pallet_xcm` from its deny-list, letting a "non-transfer" delegate teleport the delegator's funds off-chain - ([File: cumulus/parachains/runtimes/collectives/collectives-westend/src/lib.rs])

### Summary
Both the `collectives-westend` and `coretime-westend` runtimes implement `ProxyType::NonTransfer` as a **deny-list** (`!matches!(c, RuntimeCall::Balances { .. })` and a similarly narrow exclusion) rather than an allow-list. Any `RuntimeCall` variant not explicitly named is implicitly permitted. `pallet_xcm` (`PolkadotXcm`) is not in either deny-list, even though `pallet_xcm` exposes signed extrinsics (`transfer_assets`, `limited_teleport_assets`, `limited_reserve_transfer_assets`, `teleport_assets`, `reserve_transfer_assets`) that move the caller's own native balance out of the chain. A delegate holding only a `NonTransfer` proxy — explicitly documented as "can execute any call that does not transfer funds" — can therefore still move the real account's WND via XCM teleport, which is exactly the class of "no assigned scope ⇒ silently gets full/administrator-level access" bug described in CVE-2016-7078 (a permission dimension that is unset/omitted results in unrestricted behavior instead of the intended restriction).

### Finding Description
`pallet-proxy`'s `do_proxy` dispatches the wrapped call through an origin filtered by `T::ProxyType::filter`, at [1](#0-0) . The filter is the *only* gate preventing a delegate account from acting beyond its granted `ProxyType`.

In `collectives-westend`, `ProxyType::NonTransfer`'s filter is: [2](#0-1) 
which only rejects `RuntimeCall::Balances { .. }`. The runtime's `pallet_xcm::Config` permits local signed accounts to execute XCM (`ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalOriginToLocation>`, `XcmExecuteFilter = Everything`, `XcmTeleportFilter = Everything`) and defines `TrustedTeleporters` for the native WND token to the Relay/AssetHub, as seen in the analogous `coretime-westend` config: [3](#0-2) . Because `RuntimeCall::PolkadotXcm(..)` is never matched by the `NonTransfer` deny-list, a `NonTransfer` delegate can call `pallet_xcm::limited_teleport_assets`/`transfer_assets` (dispatchables confirmed present in `polkadot/xcm/pallet-xcm/src/lib.rs`) with the delegator (`real`) as the dispatch origin, moving the delegator's native balance to an arbitrary destination account on another chain — a direct fund transfer, contradicting the pallet's own doc comment "Can execute any call that does not transfer funds."

`coretime-westend`'s `NonTransfer` filter has the identical structural flaw: it excludes `Balances` and a handful of `pallet_broker` calls but not `PolkadotXcm`: [4](#0-3) .

This exact bug class (deny-list "fails open" on `NonTransfer` proxies) has already been identified and fixed elsewhere in this codebase:
- `asset-hub-westend` explicitly denies `RuntimeCall::PolkadotXcm(..)` in `NonTransfer`, with a regression test added specifically for issue #12466: [5](#0-4)  and [6](#0-5) .
- `pallet-staking-async-parachain-runtime` received the same category of fix for `ForeignAssets`/`PoolAssets`: [7](#0-6) .

Neither `collectives-westend` nor `coretime-westend` received the equivalent fix for `pallet_xcm`, so the omission (a permission dimension left unset in the deny-list) causes the proxy to silently behave like `Any` for the specific vector of XCM-based transfers — mirroring CVE-2016-7078's "no scope assigned ⇒ full access" pattern, here "no explicit deny entry for a pallet ⇒ full access to that pallet's transfer capability."

### Impact Explanation
A user who grants a `NonTransfer` proxy to a delegate (e.g., for governance/voting convenience) reasonably expects that delegate cannot move their funds. In `collectives-westend`/`coretime-westend`, the delegate can nonetheless drain the delegator's native token balance via `pallet_xcm` teleport/reserve-transfer calls to any destination they control. This is a direct theft-of-funds primitive available to anyone holding a lesser-privileged proxy, which is a genuine breach of the proxy's confidentiality/authorization guarantee, though it requires the victim to have already granted a `NonTransfer` proxy to the attacker (a normal, expected FRAME `pallet-proxy` usage pattern, not a privileged prerequisite).

### Likelihood Explanation
Moderate-to-high: `pallet-proxy` and `NonTransfer` proxies are a standard delegation pattern; granting a `NonTransfer` proxy to a semi-trusted party (e.g., a voting/collator-management bot) is common. Exploiting the gap requires only calling `pallet_xcm::limited_teleport_assets`/`transfer_assets` through `Proxy::proxy`, standard extrinsics, no special privilege, no governance action, no malicious peer/node involvement.

### Recommendation
Add `RuntimeCall::PolkadotXcm(..)` (and any other value-transferring pallet not covered) to the `NonTransfer` deny-list in `collectives-westend` and `coretime-westend`, matching the pattern already applied in `asset-hub-westend`'s `ProxyType::NonTransfer` filter. Add a regression test analogous to `non_transfer_proxy_rejects_value_moving_calls` in `asset-hub-westend/tests/tests.rs` for both runtimes to prevent recurrence, and audit any other runtime using a deny-list-style `InstanceFilter` for the same gap.

### Proof of Concept
I was not able to execute a live integration test within this investigation (no terminal/build access in this ask-only session). The finding rests on static verification of:
- The `NonTransfer` filter logic in both runtimes (deny-list omitting `PolkadotXcm`), confirmed by direct file read.
- Existence of signed, fund-moving `pallet_xcm` dispatchables (`transfer_assets`, `limited_teleport_assets`, etc.) confirmed via `grep_search` in `polkadot/xcm/pallet-xcm/src/lib.rs`.
- `pallet_xcm::Config` in `coretime-westend` (and structurally similar in `collectives-westend`) permitting local signed-origin XCM execution and teleport of the native token to the Relay/AssetHub.
- The precedent fix and its dedicated regression test in `asset-hub-westend`, which was never backported to `collectives-westend`/`coretime-westend`, and the `pr_12922` prdoc confirming the same bug class was independently found and patched for `staking-async-parachain`.

A concrete PoC would be: `Proxy::proxy(delegator, Some(ProxyType::NonTransfer), Box::new(RuntimeCall::PolkadotXcm(pallet_xcm::Call::limited_teleport_assets { dest: <attacker-controlled chain>, beneficiary: <attacker account>, assets: [delegator's native balance], fee_asset_item: 0, weight_limit: Unlimited })))` dispatched by the delegate account, executed as an integration test in the `collectives-westend`/`coretime-westend` runtime test harness, following the same structure as `asset-hub-westend/tests/tests.rs::non_transfer_proxy_rejects_value_moving_calls`. This exact execution was not run in this session; the recommendation is to reproduce it in a Devin session with build/test access before treating this as bounty-confirmed.

/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12466>.
///
/// `ProxyType::NonTransfer` is documented as permitting "any call that does not transfer funds or
/// assets", but it is implemented as a deny-list and so fails open. `ForeignAssets` and
/// `PoolAssets` transfers were reachable, as were swaps, XCM transfers, contract calls carrying a
/// value, and index transfers (which repatriate the reserved deposit).
#[test]
fn non_transfer_proxy_rejects_value_moving_calls() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// Collected rather than asserted one by one, so a regression reports every call that slipped
	// through instead of only the first.
	let mut leaked = Vec::new();
	for (name, call) in value_moving_calls() {
		if ProxyType::NonTransfer.filter(&call) {
			leaked.push(name);
		}
		// The call is otherwise well-formed and reachable by a fully permissioned proxy.
		assert!(ProxyType::Any.filter(&call), "Any must permit {name}");
	}

	assert!(
		leaked.is_empty(),
		"NonTransfer must reject calls that move funds or assets, but permitted: {leaked:?}",
	);
}
