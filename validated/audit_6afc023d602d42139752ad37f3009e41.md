### Title
`try_forward` admission-check/deduction mismatch allows a single receipt to zero out a shard's entire outgoing-gas budget - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`ReceiptSinkV2::try_forward` clamps the *admission* gas threshold to `allowed_shard_outgoing_gas` when `ProtocolFeature::ClampOutgoingGasAdmission` is enabled, but then deducts the full, unclamped receipt gas from `forward_limit.gas`. A single receipt with `total_prepaid_gas` far above `allowed_shard_outgoing_gas` (but still within per-action/per-receipt gas limits so it never triggers `HostError::GasLimitExceeded`) can pass the clamped admission check yet consume (saturate to zero) the receiving shard's whole per-round outgoing gas budget.

### Finding Description
In `try_forward`:
```
let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission.enabled(...) {
    gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
} else {
    gas
};

if forward_limit.gas >= admission_gas && forward_limit.size >= size {
    outgoing_receipts.push(receipt);
    forward_limit.gas = forward_limit.gas.saturating_sub(gas);
    ...
}
``` [1](#0-0) 

The admission test is against `admission_gas = min(gas, allowed_shard_outgoing_gas)`, meaning any receipt only needs `forward_limit.gas >= allowed_shard_outgoing_gas` to be admitted — regardless of how large its actual `gas` is. But the subsequent deduction uses the raw, unclamped `gas` value via `saturating_sub`. If an attacker crafts a `FunctionCall` receipt whose `total_prepaid_gas` (computed by `action_receipt_congestion_gas` from `total_prepaid_exec_fees` + `total_prepaid_send_fees` + `total_prepaid_gas` of attached function calls) is many times `allowed_shard_outgoing_gas`, that receipt still clears the admission check as long as the current `forward_limit.gas` is at least `allowed_shard_outgoing_gas` at the start of the round, but the `saturating_sub` then drives `forward_limit.gas` to `0` for the rest of the round. This receipt gas is computed and reused identically for both the buffer/forward path (`forward_or_buffer_receipt`) and the buffer-draining path (`forward_from_buffer_to_shard`) [2](#0-1) [3](#0-2) , so the bug is reachable from ordinary receipt processing every chunk, not just a corner case.

Nothing in the size/`HostError` checks in `errors.rs` (e.g. `GasLimitExceeded`, `ContractSizeExceeded`) bounds `total_prepaid_gas` relative to `allowed_shard_outgoing_gas`: those limits bound gas per individual action/function call and receipt byte size, not the aggregate congestion-control gas figure computed by `action_receipt_congestion_gas` (prepaid exec + prepaid send + gas attached to functions) [4](#0-3) . As long as the total stays under the chain-wide max gas per receipt/transaction (bounded by things like max attached gas per call and the 300 Tgas chunk gas limit) and the serialized receipt stays under `max_receipt_size`, this congestion-gas figure can legitimately be constructed by an ordinary transaction (e.g. a `FunctionCall` with `gas_weight`/attached gas that sums to a large `prepaid_gas` while remaining a single small receipt) with no special privileges.

### Impact Explanation
This is a receipt/congestion-accounting failure that violates the progress-preservation invariant of congestion control: a single unprivileged-attacker-controlled receipt can zero the outgoing-gas budget the local shard is allowed to send to a target shard for the entire chunk round. All other legitimate receipts destined for that shard are deferred to the outgoing buffer for that round via `ReceiptForwarding::NotForwarded` [5](#0-4) . If the attacker resubmits such a receipt every chunk (feasible since it is a normal transaction any account can send), the shard's outgoing throughput to the target shard can be starved indefinitely, causing a targeted chain-stall/liveness degradation for cross-shard traffic to that shard — matching NEAR's "chain stall" / liveness-impact bounty class.

### Likelihood Explanation
Preconditions: `ProtocolFeature::ClampOutgoingGasAdmission` enabled (protocol-version gated feature) and a target shard whose `allowed_shard_outgoing_gas` is much smaller than a single receipt's achievable `total_prepaid_gas`. Constructing the receipt requires only a normal `FunctionCall`/`Transfer` transaction from any account with enough balance to cover gas fees; no elevated privileges are needed. It is trivially repeatable every chunk by resubmitting similar transactions, so the attack is both cheap and sustainable, though the actual severity depends on how large `allowed_shard_outgoing_gas` is configured relative to the maximum congestion-gas value obtainable in one receipt (a value I could not fully confirm in this session, but the code path itself unambiguously contains the check/deduction mismatch).

### Recommendation
Use the same clamped value consistently for both the admission check and the deduction, e.g.:
```rust
forward_limit.gas = forward_limit.gas.saturating_sub(admission_gas);
```
or alternatively deduct `min(gas, forward_limit.gas)` so the budget can never go negative/be zeroed by a single oversized receipt beyond its clamped admission share, while still tracking the "excess" gas separately (e.g. against a per-shard cumulative counter) if the intent of `ClampOutgoingGasAdmission` was to allow oversized receipts through while charging them only their clamped share against the round budget.

### Proof of Concept
Integration test in `runtime/runtime/src/tests/apply.rs`:
1. Enable `ProtocolFeature::ClampOutgoingGasAdmission` via `apply_state.current_protocol_version`.
2. Set `congestion_control_config.allowed_shard_outgoing_gas` to a small value (e.g. matching production ratio).
3. Craft one `Receipt` (Action/FunctionCall) whose `total_prepaid_gas` (as computed by `action_receipt_congestion_gas`) is e.g. 100x `allowed_shard_outgoing_gas`, but with a serialized size well under `max_receipt_size`.
4. Populate several other legitimate receipts destined for the same target shard with normal/small gas.
5. Apply a chunk where `forward_or_buffer_receipt`/`try_forward` processes the attacker receipt first.
6. Assert that after processing, `outgoing_limit[target_shard].gas == 0` (or unexpectedly near zero) and that the subsequent legitimate receipts are routed via `ReceiptForwarding::NotForwarded` into `outgoing_buffers` instead of `outgoing_receipts`.
7. Repeat across several simulated chunks/rounds to show the buffer for legitimate receipts grows unboundedly while the attacker's disproportionate receipt keeps being admitted first.

    fn forward_from_buffer_to_shard(
        &mut self,
        buffer_shard_id: ShardId,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        shard_layout: &ShardLayout,
    ) -> Result<(), RuntimeError> {
        let mut num_forwarded = 0;
        let mut outgoing_metadatas_updates: Vec<(ByteSize, Gas)> = Vec::new();
        for receipt_result in
            self.outgoing_buffers.to_shard(buffer_shard_id).iter(&state_update.trie, true)
        {
            let receipt = receipt_result?;
            let gas = receipt_congestion_gas(&receipt, &apply_state.config)?;
            let size = receipt_size(&receipt)?;
            let should_update_outgoing_metadatas = receipt.should_update_outgoing_metadatas();
            let receipt = receipt.into_receipt();
            let target_shard_id = receipt.receiver_shard_id(&shard_layout)?;

            match Self::try_forward(
                receipt,
                gas,
                size,
                target_shard_id,
                &mut self.outgoing_limit,
                &mut self.outgoing_receipts,
                apply_state,
                &mut self.stats,
            )? {
                ReceiptForwarding::Forwarded => {
                    self.own_congestion_info.remove_receipt_bytes(size)?;
                    self.own_congestion_info.remove_buffered_receipt_gas(gas.as_gas().into())?;
                    if should_update_outgoing_metadatas {
                        // Can't update metadatas immediately because state_update is borrowed by iterator.
                        outgoing_metadatas_updates.push((ByteSize::b(size), gas));
                    }
                    // count how many to release later to avoid modifying
                    // `state_update` while iterating based on
                    // `state_update.trie`.
                    num_forwarded += 1;
                }
                ReceiptForwarding::NotForwarded(_) => {
                    break;
                }
            }
        }

        self.outgoing_buffers.to_shard(buffer_shard_id).pop_n(state_update, num_forwarded)?;
        for (size, gas) in outgoing_metadatas_updates {
            self.outgoing_metadatas.update_on_receipt_popped(
                buffer_shard_id,
                size,
                gas,
                state_update,
            )?;
        }
        Ok(())
    }

```rust
fn action_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
    action_receipt: VersionedActionReceipt,
) -> Result<Gas, IntegerOverflowError> {
    let prepaid_exec_gas =
        total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
            .gas
            .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee().gas)
            .ok_or(IntegerOverflowError)?;
    // account for gas guaranteed to be used for creating new receipts
    let prepaid_send_cost = total_prepaid_send_fees(config, &action_receipt.actions())?;
    let prepaid_gas = prepaid_exec_gas.checked_add_result(prepaid_send_cost.gas)?;

    // account for gas potentially used for dynamic execution
    let gas_attached_to_fns = total_prepaid_gas(&action_receipt.actions())?;
    let gas = gas_attached_to_fns.checked_add_result(prepaid_gas)?;

    Ok(gas)
}
