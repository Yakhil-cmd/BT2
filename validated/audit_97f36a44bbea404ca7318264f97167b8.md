### Title
Webhook signature is verified against a webhook secret keyed by an attacker-controlled `repository.owner.login` field that is never bound to the `repository.full_name` actually acted upon by handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to HMAC-verify the raw request body against by reading `repository.owner.login` (or `organization.login`) straight out of the *same unauthenticated JSON body* it is about to verify. `Shipit::Webhooks::Handlers::Handler#repository_name` (and every handler, e.g. `PushHandler`, `StatusHandler`) then act on `payload.dig('repository', 'full_name')`, a *different* field of the same body, without ever checking that it matches the organization whose secret validated the signature. `StatusHandler` goes further and doesn't scope by repository at all - it matches purely on `Commit.where(sha: params.sha)` globally.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) using `repository_owner`, computed as: [1](#0-0) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is looked up in `Shipit.github(organization: repository_owner)` and its `webhook_secret` is used to HMAC-verify `request.raw_post`: [2](#0-1) 

Meanwhile, every event handler resolves the target repository/stack using a *different* field of the identical body, `repository.full_name`: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing in the controller or in `Handler` cross-validates that `repository.owner.login` (the field used to select the HMAC secret) actually corresponds to the owner encoded in `repository.full_name` (the field used to select the affected repository/stack). Both fields are plain, attacker-supplied JSON — GitHub's real HMAC signs the whole body, but Shipit's `Shipit.github(organization: ...)` selection logic trusts the body's own `owner.login` before the signature check is even meaningful for that value, and after verification passes it separately trusts `full_name` for authorization/target-selection purposes.

Concretely: in a multi-organization Shipit deployment (`config/secrets.*.yml` supports multiple GitHub orgs each with its own `webhook_secret`, see `Shipit.github_app_config`) [4](#0-3) , an attacker who controls (or has compromised) the webhook secret for **one** configured organization, "org-A", can HMAC-sign a payload where `repository.owner.login = "org-A"` (so `verify_webhook_signature` succeeds using org-A's secret) while setting `repository.full_name = "org-B/some-repo"` (a repository belonging to a completely different, unrelated organization "org-B" also hosted on the same Shipit instance). The signature check equality that Shipit implicitly relies on — "organization whose secret validated the signature" == "organization/repository the event is applied to" — is broken.

`StatusHandler` is the most severe consequence: it does not even use `repository_name`/`full_name` scoping, but matches on a bare commit SHA across the whole database: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Since commit SHAs are 40-hex-char but frequently public/predictable (mirrored repos, shared commits, public GitHub history), an attacker who can produce *any* valid signature for *any* configured org can forge a `status` event against a commit belonging to a totally different org's stack. `Commit#create_status_from_github!` / `#add_status` feeds directly into `deployable?` and continuous-deployment triggers (`ProcessMergeRequestsJob`, `deployable_status` hook, CD scheduling) as shown in `test/models/commits_test.rb`.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly targeted by the task rules. An attacker in control of one organization's legitimate webhook secret (a credential they already validly hold as an admin of *some* org onboarded to the shared Shipit instance) can:
- Forge `push` events for stacks belonging to an unrelated organization's repository (`PushHandler` triggers `stack.sync_github`).
- Forge `status`/CI-success events for arbitrary commits in a different organization's stack, flipping `Commit#deployable?` to true and triggering continuous-deployment `Deploy`s (unauthorized deploy) — this is a Critical-impact category ("unauthorized deploy") per the given impact list.
- Forge `pull_request`/`membership` events that create/archive review stacks or manipulate `Team`/`Membership` records tied to a different org's authorization model (escalation into `Shipit.github_teams` authorization territory).

### Likelihood Explanation
Exploitation requires the attacker to be able to produce one valid HMAC signature for the body under some org's `webhook_secret` configured in the same Shipit instance — realistic in any deployment that serves multiple orgs/tenants from one Shipit install (which the config format explicitly supports), or if a single org's webhook secret leaks/rotates improperly. No repository write access, GitHub App private key, or Shipit session is required beyond that one secret; the flaw is a pure server-side field-confusion, not a cryptographic break.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the org via `repository_owner` and verifying the signature, assert that `params.dig('repository', 'full_name')` is actually owned by that same `repository_owner` (e.g. `full_name.split('/').first == repository_owner`) before dispatching to handlers, and reject otherwise. Independently, `StatusHandler#process` should scope by `repository_name`/`full_name` (via `stacks`/`Repository.from_github_repo_name`) rather than a bare global `Commit.where(sha:)` lookup, so a forged status cannot cross repository or org boundaries even if signature validation is otherwise correct.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `org-a` (secret `S_A`) and `org-b` (secret `S_B`), each with stacks for their own repos.
2. As an attacker who only knows `S_A` (e.g., legitimate admin of `org-a`'s GitHub App), craft a `status` webhook body:
```json
{
  "sha": "<known/guessed sha of a commit in org-b/some-repo>",
  "state": "success",
  "context": "ci/travis",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/some-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POST to `/github/webhooks`.
4. `verify_signature` resolves `repository_owner` → `"org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature validates successfully because it was signed with `S_A`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the org-b commit regardless of org-a/org-b confusion — and calls `create_status_from_github!`, potentially flipping the commit to `deployable?` and firing continuous deployment for `org-b`'s stack, despite the attacker never having had access to `org-b`'s webhook secret or repository.
