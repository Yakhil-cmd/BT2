### Title
Webhook signature verification authenticates a GitHub organization while handlers dispatch writes based on a different, unverified `repository.full_name` field in the same payload - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which per-organization webhook secret to use, and thus which organization is "authenticated," from `repository.owner.login` (or `organization.login`), while every downstream `Handler` resolves the actual `Repository`/`Stack` to write to from a *different* field of the same payload, `repository.full_name`. On a multi-organization Shipit deployment (the officially documented `config/secrets*.yml` layout with a `github:` hash keyed per organization, each with its own `webhook_secret`), an attacker who legitimately administers one configured organization knows that organization's webhook secret and can forge an arbitrary raw POST body to `/webhooks` that authenticates as their own org but names a victim org's repository as the write target.

### Finding Description
`verify_signature` computes the organization used for HMAC verification purely from attacker-suppliable JSON: [1](#0-0) [2](#0-1) 

It looks up the app config with `Shipit.github(organization: repository_owner)` and checks the signature against that organization's `webhook_secret`. If the signature verifies, `create` dispatches the parsed body to every matching event handler: [3](#0-2) 

However, none of the handlers use `repository.owner.login` (the field that determined *which secret authenticated the request*) to select the target. They all use `repository.full_name` via the shared base class: [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` on `/` and does a plain `find_by(owner:, name:)` lookup, with no cross-check against the organization that was actually cryptographically verified: [5](#0-4) 

Concrete handler sinks that trust `full_name` unconditionally:
- `PushHandler#process` triggers a GitHub sync for any stack under the named repo/branch: [6](#0-5) 
- `StatusHandler#process` writes a commit status directly from payload fields for any commit `sha` matching in the DB, with no repository scoping check at all beyond the sha lookup: [7](#0-6) 
- `PullRequest::ClosedHandler#repository` resolves the target repository purely from `params.repository.full_name` and can archive a review stack belonging to it: [8](#0-7) 

This is a direct binding break: **organization that authenticated the signature (`repository.owner.login`) ≠ repository that is written (`repository.full_name`)**. Because Shipit's documented multi-org configuration puts a distinct `webhook_secret` per organization in `config/secrets.yml`/`config/secrets.development.shopify.yml`, an org administrator (an "unprivileged attacker" with respect to any *other* onboarded org/stack) legitimately knows their own org's webhook secret, and can use it to sign a payload whose `full_name` names a victim organization's repository.

### Impact Explanation
This crosses the required boundary of **cross-repository writes**: an actor whose only credential is validity for one configured GitHub organization's webhook secret can cause the engine to perform state changes (queue `GithubSyncJob`, create arbitrary commit statuses via `Commit#create_status_from_github!`, or archive a review stack) attributed to a completely different organization's repository, without ever possessing that organization's webhook secret, App credentials, or repository access. Forged commit statuses in particular can influence deploy-readiness/merge gating logic elsewhere in the engine that consults `Commit` statuses, and forged push/check_suite events can force out-of-band syncs against victim stacks.

### Likelihood Explanation
Requires only that the target Shipit instance be configured for more than one GitHub organization (the documented, supported configuration shape) and that the attacker be an authenticated administrator/owner of one of those organizations (i.e., possesses that org's `webhook_secret`, which they legitimately created). No repository write access, no `ApiClient` token, and no interaction with GitHub itself is required — the request is a direct forged POST to `/webhooks`. This is a realistic multi-tenant misconfiguration-independent flaw since separate webhook secrets per org are the intended isolation mechanism, and this bug defeats that isolation by never checking that the verified org matches the written repository's owner.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, after signature verification succeeds, assert that the organization used to select the webhook secret (`repository_owner`) matches the owner portion of `repository.full_name` (and of `organization.login`/`repository.owner.login` used anywhere else in the payload) before dispatching to handlers; reject the request otherwise.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.shopify.yml` layout) [9](#0-8) .
2. Attacker, who owns/administers `attacker-org` and therefore knows `attacker-org`'s `webhook_secret`, crafts a raw JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "branches": [{"name": "master"}]
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, raw_body)>` and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `verify_signature` extracts `repository_owner = "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker signed with the correct (their own) secret [1](#0-0) .
5. `create` dispatches to `StatusHandler`, which looks up `Commit.where(sha: params.sha)` — a commit belonging to `victim-org/victim-repo` — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled CI status onto the victim's repository commit, with no check that `attacker-org` has any relationship to `victim-org` [7](#0-6) .
