**Analysis:**

The reported issue is specific to the EVM/Solidity `ERC721` token-receiver pattern: OpenZeppelin's `_mint` (unlike `_safeMint`) skips the `onERC721Received` callback check, so an NFT sent to a contract address that cannot handle ERC721 tokens can become permanently stuck.

This bug class does not have a structural analog in the Polkadot SDK. In FRAME pallets such as `pallet-nfts` and `pallet-uniques`, ownership of an item is represented purely as a storage-map key (`AccountId` → `(CollectionId, ItemId)`), with no callback/interface-implementation requirement for the receiving account to "accept" the asset [1](#0-0) . Both the permissionless `mint` dispatchable and the `mint_into` trait method insert item ownership unconditionally for any valid `AccountId`, including pallet-derived or contract-derived accounts, with no equivalent to Solidity's `IERC721Receiver` check [2](#0-1) . Unlike Ethereum contract accounts, a Substrate `AccountId` does not need to implement any interface to hold an asset — there is no code-execution gate on receiving storage-based ownership, so there is no "receiver doesn't support this token" failure mode to replicate.

I also checked `pallet-revive`'s asset/fungible bridging code, which does route ERC-20-style transfers through contract calls and does check the boolean return value of `transfer` [3](#0-2) , but this is fungible-token specific and already validates success/failure of the contract call — it isn't an NFT-mint-without-safety-check analog, and no similar contract-mediated NFT mint path with a missing receiver-callback exists in the indexed code.

Since the underlying invariant violated in the report (skipping a receiver-interface check during token creation) has no reachable, semantically equivalent counterpart in FRAME's storage-based ownership model, there is no demonstrable Polkadot SDK analog to report.
