## Finding

The binding that should hold is:
`organization_that_authenticated_the_webhook (params.dig('repository','owner','login'), verified via `Shipit.github(organization: repository_owner).verify_webhook_signature`) == organization_that_owns_the_Commit_row_being_mutated_by_the_webhook (commit.stack.repository)`

Tracing `StatusHandler#process`, this binding is never checked — it's broken.### Title
`StatusHandler#process` writes GitHub status onto any `Commit` sharing a SHA, ignoring the repository that authenticated the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by SHA alone (`Commit.where(sha: params.sha)`), with no scoping to the repository/organization whose webhook secret authenticated the request. Any organization that owns a repository connected to Shipit can therefore make GitHub emit (or, functionally, send) a legitimately-signed `status` webhook for a commit in their own repo, and if any other tenant's stack happens to contain a `Commit` row with the identical SHA, Shipit writes a `Status` for that foreign commit as well.

### Finding Description
`WebhooksController#verify_signature` resolves the signing organization purely from the incoming payload itself: `repository_owner` is `params.dig('repository','owner','login')` [1](#0-0)  and is used to pick which org's secret to verify against: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) . This only proves "GitHub signed this payload for organization X" — it says nothing about which `Commit` rows in Shipit's database the payload's `sha` is allowed to affect.

`StatusHandler#process` then dispatches purely on `sha`, with zero use of the payload's `repository` field to scope the query:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

Note that the base `Handler` class already provides a repository-scoping helper, `stacks`, built from `payload.dig('repository','full_name')` [4](#0-3) , and other handlers such as `PullRequest::OpenedHandler` correctly resolve and scope to `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [5](#0-4) . `StatusHandler` uniquely omits this scoping and doesn't even declare `repository` as a required param.

`Commit#create_status_from_github!` unconditionally creates a `Status` scoped to that commit's own `stack_id` [6](#0-5) , and `Status#enable_ci_on_stack`/`schedule_continuous_delivery` fire on creation [7](#0-6) , enqueuing `ProcessMergeRequestsJob` which calls `merge_request.all_status_checks_passed?` (via `StatusChecker.new(head, head.statuses_and_check_runs, ...)` [8](#0-7) ) and can trigger `merge_request.merge!` [9](#0-8) .

**Exploit flow**: The attacker owns/controls a repository connected to Shipit (their own org/repo, or any repo they can add). They craft a commit whose SHA1 is bit-identical to a target victim commit — feasible via cherry-pick/rebase preserving tree, parent, author/committer identities and timestamps, and commit message, all of which determine the SHA1 — and push it into their own PR/branch. Their own (attacker-controlled) CI, or the attacker directly, posts a `status` webhook for that SHA with `state: success`. GitHub (or the attacker, if they can reach the CI integration) signs this with the attacker's own org's webhook secret, which `verify_signature` accepts because the payload's `repository.owner.login` names the attacker's own org. `StatusHandler#process` then finds *every* `Commit` row across the whole Shipit install with that SHA — including the victim's — and writes a `success` `Status` onto it, even though the victim's org's CI never ran.

Existing guards do not catch this: `verify_signature` only authenticates the org named in the payload (the attacker's own), not the org that owns the affected `Commit` row; `ExplicitParameters` in `StatusHandler` requires only `sha`/`state`, no `repository`; and no `Repository`/`stacks` scoping is applied before the `Commit.where(sha:)` write.

### Impact Explanation
A single, correctly-authenticated webhook from an attacker-controlled repository can cause an unauthorized `Status` (`success`) to be written onto a commit belonging to a victim organization's stack that Shipit has no other relationship with — a payload for one repository mutating another's commit/stack state. If that commit is the `head` of a pending `MergeRequest`, this directly flips `MergeRequest#all_status_checks_passed?` and can drive an unauthorized merge via `ProcessMergeRequestsJob`/`MergeRequest#merge!`, which matches the "Critical — a payload for one repository mutating another's stack/commit/task, or an unauthorized merge" category. The attack is repeatable against any stack/commit pair that shares a SHA, and blast radius spans all tenants sharing the Shipit instance, not just one repo.

### Likelihood Explanation
The hard precondition is a SHA collision between an attacker-controlled commit and a victim commit tracked by Shipit. Git SHA1 is fully determined by tree, parents, author/committer identity+timestamp, and message, so an attacker cannot forge an arbitrary victim SHA from scratch, but can reliably reproduce it when the victim commit itself originated from (or was cherry-picked/rebased into) a shared/forked history — a realistic scenario in open-source or monorepo-with-forks workflows, exactly as scoped in the question. Once that SHA exists in an attacker-owned repo/PR, no privileged credentials are needed: normal GitHub CI integration produces a legitimately signed webhook for the attacker's own org. This is a code-level scoping bug, not a probabilistic hash attack, so it is deterministic and repeatable whenever the SHA-sharing precondition holds.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring the `stacks` helper already present in the base `Handler` class, e.g. restrict the query to `stacks.commits.where(sha: params.sha)` (or equivalent join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) instead of an unscoped `Commit.where(sha: params.sha)`, and make `repository.full_name` a required param for `StatusHandler` so unscoped webhooks are rejected outright.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Fixtures: two stacks in different orgs, `victim_stack` (org `victim-org`) and `attacker_stack` (org `attacker-org`), each with a `Commit` row sharing the exact same `sha` value (`shared_sha`).
2. Create a `MergeRequest` on `victim_stack` whose `head` is the `victim_stack` commit with `shared_sha`; assert `merge_request.all_status_checks_passed?` is `false` (no statuses yet) — LHS/RHS of the binding: `authenticated_org = 'attacker-org'`, `commit.stack.repository.owner = 'victim-org'` — not equal.
3. Stub `GithubHook`/`verify_signature` (as existing tests do) to simulate a legitimately-signed webhook only for `attacker-org` (`Shipit.github(organization: 'attacker-org')` succeeds; no secret for `victim-org` is used or needed).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ sha: shared_sha, state: 'success', repository: { owner: { login: 'attacker-org' }, full_name: 'attacker-org/attacker-repo' } }`.
5. Assert `victim_stack`'s commit (`Commit.find_by(sha: shared_sha, stack: victim_stack)`) now has a `Status` with `state: 'success'` — demonstrating the write into a stack never authenticated by this request.
6. Reload `merge_request` and assert `merge_request.all_status_checks_passed?` is now `true`, proving the merge-gate flipped from a single attacker-authenticated POST with no `victim-org` credential involved.
