### Title
Webhook signature verification selects the GitHub organization/secret from an unverified payload field that is disjoint from the repository field handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate the request signature against using `repository.owner.login` (or `organization.login`) taken directly from the still-unverified JSON body. Once the signature is confirmed valid *for that organization*, the same raw payload is dispatched to event handlers that instead resolve the target `Stack`/`Repository` using a completely different field, `repository.full_name` (`Shipit::Webhooks::Handlers::Handler#repository_name`). These two payload fields are never checked for consistency. Anyone who legitimately controls the webhook secret for *one* configured organization can therefore craft a payload whose `repository.owner.login` matches their own org (so the HMAC check passes) while `repository.full_name` points at an arbitrary *other* org's repository/stack, causing handlers to mutate that victim stack's state.

### Finding Description
`verify_signature` derives the organization used for HMAC verification from the raw, not-yet-authenticated body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-organization config (`app_id`, `installation_id`, `webhook_secret`) and `verify_webhook_signature` runs `SecureCompare.secure_compare` against `OpenSSL::HMAC.hexdigest('sha1', webhook_secret, message)`: [3](#0-2) 

This only proves the sender knows the webhook secret configured for *`repository_owner`* (the value read from `repository.owner.login`/`organization.login`). It says nothing about the value of `repository.full_name`, which is a sibling, independently-controlled field in the same JSON object.

After the signature check, `create` hands the raw parsed body to every registered handler for the event: [4](#0-3) 

Every handler resolves the affected stacks via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` - not the field used for signature selection: [5](#0-4) 

Concrete handlers act on whatever `Repository.from_github_repo_name(repository_name)` returns, e.g.:
- `PushHandler#process` forces `stack.sync_github(expected_head_sha: params.after)` for any not-archived stack on the matching branch: [6](#0-5) 
- `StatusHandler#process` writes a commit status for any commit with a matching sha in the whole DB (independent of repository at all): [7](#0-6) 
- `CheckSuiteHandler#process` schedules check-run refreshes on the victim stack's commits: [8](#0-7) 
- `MembershipHandler#process` creates/updates `Team`/`User`/`Membership` records keyed on `params.organization.login` and `params.team.id`, which are also payload-controlled and not reconciled with the "authenticated" organization used for signature selection: [9](#0-8) 

The binding that is broken is exactly of the class called out in the rules: **"an organization that authenticated versus the repository that is written."** The equality that should hold and does not is:
`organization_used_to_select_webhook_secret (repository.owner.login) == organization_owning_the_repository_actually_mutated (repository.full_name)`.

Because Shipit is explicitly designed to host multiple independently configured GitHub organizations side by side (`config/secrets.development.shopify.yml` shows a `github:` map keyed by org, each with its own `webhook_secret`, `app_id`, `private_key`), a party who controls (or has been granted) the webhook secret for organization "A" (e.g. because they operate their own GitHub App installation registered with the Shipit instance) can sign an arbitrary payload with A's secret while setting `repository.full_name` (and, for `MembershipHandler`, `organization.login`/`team`) to reference any other organization/repository/team known to the Shipit instance. `verify_signature` passes because the HMAC matches for organization "A", and the handler then mutates state belonging to a completely different, victim organization.

### Impact Explanation
This crosses the "cross-organization" boundary the engine is supposed to enforce between tenants sharing one Shipit instance: an actor authenticated as organization A can use the webhook channel to write into stacks/repositories/commits/teams that belong to organization B, without any credentials for B. Concretely reachable effects (all with no session, no `ApiClient` token, no repository write access to B, only knowledge of A's own webhook secret):
- Forced `stack.sync_github` calls and commit-status writes on arbitrary victim stacks (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`).
- Creation/modification of `Team`/`Membership` records tied to an arbitrary `organization.login` via `MembershipHandler`, which is the same `Team` model consulted for `Shipit.github_teams` authorization elsewhere in the app - i.e. this can be used to escalate into `Shipit.github_teams` authorization, matching the "High" impact bullet in the rules ("escalation into `Shipit.github_teams` authorization").

This satisfies the rule's required impact category (escalation into `Shipit.github_teams` authorization / unauthorized state mutation of another tenant's stack).

### Likelihood Explanation
Exploitability requires only:
1. The Shipit instance being configured for more than one GitHub organization (a documented, supported configuration - see `config/secrets.development.shopify.yml` and `docs/setup.md`), and
2. The attacker having legitimate knowledge of the webhook secret for *any one* of those configured organizations (e.g. as the operator/admin who set up their own org's GitHub App integration on a shared Shipit instance).

No compromise of TLS, no GitHub App private key, no `ApiClient` token, and no privileged Shipit account are needed - only the ability to compute a valid HMAC-SHA1 with a secret the attacker legitimately possesses for their own tenant, and to reference a different tenant's repository/organization/team identifiers (which are knowable/public, e.g. `owner/repo` names and GitHub team slugs/ids). This is a realistic scenario for any multi-tenant Shipit deployment.

### Recommendation
Bind the payload's `repository`/`organization` identity to the organization whose secret validated the signature, and reject requests where they diverge:
- In `WebhooksController`, after `verify_signature` succeeds, re-derive `repository_owner` (and, where present, `params['organization']['login']`) and assert it is identical to the organization used to select the webhook secret, before dispatching to handlers.
- In `Shipit::Webhooks::Handlers::Handler`, do not trust `payload.dig('repository', 'full_name')` alone; cross-check `payload.dig('repository', 'owner', 'login')` against the verified organization, or pass the already-authenticated organization down into handlers explicitly instead of re-deriving it from unauthenticated payload fields.
- For `MembershipHandler`, similarly ensure `params.organization.login` matches the organization that was cryptographically verified for this request.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs:
   ```yaml
   github:
     attacker-org:
       webhook_secret: "attacker-known-secret"
       ...
     victim-org:
       webhook_secret: "victim-secret-unknown-to-attacker"
       ...
   ```
2. Attacker (who knows `attacker-known-secret`, e.g. because they configured the GitHub App used for `attacker-org`) crafts a `push` event body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, "attacker-known-secret")>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, and the HMAC matches -> request passes.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `Handler#repository_name` reads `"victim-org/victim-repo"` and resolves the real victim `Stack`, calling `stack.sync_github(expected_head_sha: "deadbeef...")` on a stack the attacker has no legitimate access to.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
