### Title
Cross-organization Team hijack via `github_id`-only lookup in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
The Move contract bug leaves a state structure (`investor.wallets`) unsynchronized with the authoritative counter (`wallet_count`) after a removal, so later code (`investor_wallet_balance_total`) trusts stale entries. The analogous flaw in this engine is that `Shipit::Webhooks::Handlers::MembershipHandler` resolves the `Team` record to mutate using only the GitHub-assigned `team.id`, without verifying that the `organization` the webhook signature was actually verified for still owns that team record. This breaks the equality that should hold: `organization whose secret verified the signature == organization that owns the Team being mutated`.

### Finding Description
`WebhooksController#verify_signature` picks which organization's webhook secret to check the HMAC against using a payload field: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) 

For `membership` events specifically, that resolves to `params['organization']['login']` — i.e., the org the attacker's own GitHub App installation belongs to, in a multi-tenant Shipit deployment (`config/secrets.yml` supports multiple orgs, each with its own `webhook_secret`). [2](#0-1) 

Once the signature is verified for *that* organization, `MembershipHandler#process` finds or creates the `Team` to mutate purely by the GitHub `team.id`, ignoring the organization that was actually authenticated:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 

The `organization:` block only runs on record *creation*; if a `Team` row with that `github_id` already exists (e.g., previously synced from the legitimate authorized organization), `find_or_create_by!` returns the existing record untouched, and `team.add_member(member)` / `team.members.delete(member)` operates on it. [4](#0-3) 

This `Team` is exactly the object that gates application-wide authorization: `Shipit::User#authorized?` checks membership against `Shipit.github_teams`. [5](#0-4) [6](#0-5) 

So the binding that should hold is: `organization authenticated by verify_signature == organization owning the Team object mutated by MembershipHandler`. Because the lookup key (`github_id`) is disconnected from the organization used for signature verification, and because it isn't re-validated against `params.organization.login` for existing records, a webhook that is validly signed for one tenant organization can write membership state belonging to a different, authorized organization's `Team` — provided the attacker knows (or can enumerate) the numeric GitHub team ID of the target team, which is not secret (team IDs are visible via the GitHub API/UI for many team-visibility configurations, and are exposed historically through any prior legitimate webhook delivered to Shipit).

### Impact Explanation
If exploited, an attacker who controls (or is an owner in) any one of the GitHub organizations configured as a Shipit tenant can add themselves (or any GitHub login) as a member of a `Team` object that corresponds to a *different*, security-sensitive organization/team referenced in `Shipit.github_teams`. Since `User#authorized?` merely checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, this grants full authenticated access to Shipit — bypassing the intended GitHub-team gate on stacks, deploys, rollbacks, and API client management. This matches the "escalation into `Shipit.github_teams` authorization" High-impact category.

### Likelihood Explanation
Exploitation requires: (1) the Shipit instance configured with multiple GitHub organizations (a documented, supported configuration), (2) the attacker owning or administering at least one of those organizations (not the "authorized" one) so they can legitimately trigger a signed `membership` webhook, and (3) knowledge of the target `Team`'s numeric GitHub `id`. Condition (3) is the main uncertainty — GitHub team IDs are not always trivially discoverable for a team the attacker isn't a member of, though they may leak through prior events, integrations, or org enumeration depending on visibility settings. Given this, likelihood is Medium: the vulnerable code path (unscoped `find_or_create_by!(github_id:)`) is real and directly reachable by any tenant with a signed webhook, but full exploitation needs auxiliary ID discovery.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (matching `params.organization.login`), and reject/re-key the record if the existing team's stored `organization` does not match the organization that was actually verified for this webhook delivery, e.g.:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login) do |team|
    team.github_team = params.team
  end
end
```
Additionally, `verify_signature` should assert that the resolved `repository_owner`/`organization` matches the organization actually referenced by every entity the handler subsequently mutates, closing the same class of gap the audited `remove_wallet` fix addressed (keeping the authoritative binding in sync on every write).

### Proof of Concept
1. Shipit is configured with two tenant orgs: `authorized-org` (referenced in `Shipit.github_teams`, e.g. `authorized-org/admins` with GitHub team id `1000`) and `attacker-org` (attacker is an owner, with its own registered `webhook_secret`).
2. Attacker discovers `authorized-org/admins`'s GitHub team id (`1000`) through any available leak (prior webhook logs, API responses, GitHub UI enumeration for orgs with permissive team visibility, etc.).
3. Attacker triggers a real GitHub `membership` webhook in `attacker-org` (e.g., adds a dummy team/member in their own org) or crafts a payload of the form:
```json
{
  "action": "added",
  "team": { "id": 1000, "name": "admins", "slug": "admins", "url": "..." },
  "organization": { "login": "attacker-org" },
  "member": { "login": "attacker-handle" }
}
```
and lets it be signed with `attacker-org`'s legitimate `webhook_secret` (which the attacker knows because they set up that GitHub App).
4. `WebhooksController#verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature. [7](#0-6) 
5. `MembershipHandler#process` calls `find_or_create_team!`, which finds the *existing* `Team` row with `github_id: 1000` (the real `authorized-org/admins`), and calls `team.add_member(User.find_or_create_by_login!("attacker-handle"))`. [3](#0-2) 
6. `attacker-handle`'s Shipit `User#authorized?` now returns `true` because they belong to a `Team` whose id is in `Shipit.github_teams`, granting them full access to the Shipit instance. [5](#0-4)
