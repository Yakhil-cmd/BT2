### Title
Webhook-driven `Status` creation is not scoped to the requesting repository, allowing a `status` webhook from an attacker-owned repo to write a `Status` onto a victim stack's commit via matching SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the *entire* installation and unconditionally calls `commit.create_status_from_github!(params)`, without ever checking `params`'s `repository.full_name` against the found commit's stack/repository. This contrasts with `Commit#create_release_status!`, which explicitly and correctly binds the write to `self.stack`, and with `PushHandler`, which correctly scopes lookups through `Repository.from_github_repo_name(repository_name)&.stacks`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`stack_id used for Status write` == `stack_id implied by the verified webhook's own repository (Repository.from_github_repo_name(payload.repository.full_name))`

Trace:
- `WebhooksController#verify_signature` only authenticates that the payload was signed by *some* organization matching `payload.dig('repository','owner','login')`; it never restricts which repository/commit that payload is allowed to reference. [1](#0-0) 
- `StatusHandler` declares no `repository` requirement and never calls the base class's `stacks`/`repository_name` helpers used by other handlers to scope: [2](#0-1) 
- Compare to `PushHandler`, which correctly restricts to `stacks` derived from `Repository.from_github_repo_name(repository_name)`: [3](#0-2)  and the base helper it relies on: [4](#0-3) 
- `StatusHandler#process` instead performs a global, unscoped SHA lookup and calls `create_status_from_github!` on whatever `Commit` rows match, regardless of stack/repo: [5](#0-4) 
- `Commit#create_status_from_github!` then writes the `Status` using the *victim* commit's own `stack_id` attribute, never validating it against the webhook payload's repository: [6](#0-5) 
- `Status.replicate_from_github!` persists `stack_id` verbatim as passed: [7](#0-6) 

By contrast, `Commit#create_release_status!` explicitly passes `stack:` from `self.stack`, i.e. it is scoped correctly and is only reachable in-process from `Deploy#append_release_status` (authenticated deploy flow), never from an unscoped webhook: [8](#0-7) [9](#0-8) 

Exploit flow: an attacker forks a victim's public GitHub repository that is tracked by a Shipit stack. Git forks share commit objects, so commits already present upstream have identical SHAs in the fork. If the attacker's account/org has the Shipit GitHub App/webhook installed for their own fork (a normal, self-service action for a public GitHub App, requiring no privilege from Shipit operators or the victim), the attacker can use GitHub's own Statuses API against their fork (`POST /repos/{attacker}/{fork}/statuses/{sha}`) — an action they are fully authorized to perform on their own repository — to make GitHub emit a legitimately-signed `status` webhook event to Shipit's `/webhooks` endpoint, with `repository.full_name` pointing at the attacker's fork but `sha` equal to a commit that Shipit already tracks under the victim's stack. `verify_signature` passes because the webhook is genuinely signed for the attacker's own installation/organization; `drop_unhandled_event` passes because `status` is a handled event; `StatusHandler` then finds the victim's `Commit` row purely by `sha` and writes a `Status` scoped to the victim's `stack_id`, with attacker-chosen `state`, `description`, `target_url`, and `context`.

None of the existing guards catch this: `verify_signature` only authenticates the sender's organization, not the commit ownership; the `ExplicitParameters` schema for `StatusHandler` has no `repository` requirement; `force_github_authentication`, `User#authorized?`, and `require_permission!` are irrelevant since this path never goes through an authenticated controller action.

### Impact Explanation
An unprivileged attacker who forks a victim's tracked repository and self-installs the Shipit webhook integration on their own fork can inject arbitrary CI `Status` records (`success`/`failure`/`pending`/`error`, with attacker-controlled `context`, `description`, `target_url`) onto a commit belonging to a stack they neither own nor authenticated against. Since `Status` creation drives `Commit#deployable?` gating (via `blocking?`/`success?`) and triggers `ProcessMergeRequestsJob`/continuous delivery (`Status#schedule_continuous_delivery`, `after_create :enable_ci_on_stack`), this can unblock or trigger an unauthorized deploy or auto-merge on the victim's stack. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge." The attack is repeatable against any repo with shared commit history (any public repo an attacker can fork) and does not require secrets, sessions, or API tokens.

### Likelihood Explanation
Preconditions: the attacker needs (1) to fork a publicly-forkable repository tracked by a target Shipit stack, and (2) to have the Shipit GitHub App/webhook installed on their own repo/account (a self-service, privilege-free action for a public integration). No Shipit secret, session, or GitHub team membership is required — only ordinary GitHub actions on a repo the attacker owns (forking, setting a status via the Statuses API on a commit reachable in their fork). This is low-cost and repeatable at will for any shared commit SHA.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the webhook's own verified repository, e.g. restrict to `stacks` (as `PushHandler` does) or otherwise verify that `commit.stack.repository` matches `Repository.from_github_repo_name(params.repository.full_name)` before calling `create_status_from_github!`. Additionally, `Commit#create_status_from_github!`/`Status.replicate_from_github!` should validate that the `stack_id` being written belongs to the repository asserted by the webhook payload, mirroring the explicit `stack:` binding already used in `create_release_status!`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, `test/models/commits_test.rb`):

1. In-app authorized path (control): `Commit#create_release_status!` — assert that `ReleaseStatus.last.stack_id == commit.stack_id` always, and that this method is only reachable through `Deploy#append_release_status`, itself gated by `require_permission :deploy, :stack` in `ReleaseStatusesController`.
2. Webhook path (exploit): create two stacks/repositories, `victim_stack` (repository `victim/repo`) with `commit = victim_stack.commits.create!(sha: shared_sha, ...)`, and simulate an attacker's payload with `repository.full_name == "attacker/fork"` and `sha == shared_sha`.
   ```ruby
   payload = {
     'sha' => shared_sha, 'state' => 'success',
     'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } }
   }
   GithubHook.any_instance.stubs(:verify_signature).returns(true)
   request.headers['X-Github-Event'] = 'status'
   assert_difference '-> { commit.statuses.count }', 1 do
     post :create, body: payload.to_json, as: :json
   end
   status = commit.statuses.last
   assert_equal victim_stack.id, status.stack_id   # written despite payload repository being "attacker/fork"
   ```
3. Assert the binding fails: `status.stack_id == victim_stack.id` while `Repository.from_github_repo_name(payload['repository']['full_name'])` does **not** equal `victim_stack.repository` — proving `create_status_from_github!` never checks stack identity against the verified webhook repository, unlike `create_release_status!`.
