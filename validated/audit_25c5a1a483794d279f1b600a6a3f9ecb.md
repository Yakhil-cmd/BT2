### Title
Mid-Epoch CandTesting Entrant's Failures Silently Dropped via Stale CPMatrix Checkpoint — (`kaiax/vrank/impl/scoring.go`)

### Summary

A candidate who enters `CandTesting` mid-epoch will never have their `cfReport` failures counted toward their CFS score, because every checkpoint and cache entry written by `PostInsertBlock` carries a `CPMatrix` that was seeded before the candidate existed. The `if _, ok := cpMatrix[candidate]; !ok { continue }` guard in `applyBlocksForCPMatrix` silently discards every failure report for that candidate, leaving `CFS[C1] = 0` at epoch end and allowing an incorrectly-performing candidate to pass the VRank threshold and transition from `CandTesting` to `ValActive`.

---

### Finding Description

**Seed construction — cold path vs. checkpoint path**

`lookupCFSSeed` has three branches:

```
cache hit  → return (cachedNum+1, cachedMatrix)
checkpoint → return (cpNum+1, checkpointMatrix)
cold       → newCPMatrix(blockNum) → GetCandTesting(blockNum)
             return (epochStart, freshMatrix)
``` [1](#0-0) 

The **cold path** is actually safe: `newCPMatrix(blockNum)` calls `GetCandTesting(blockNum)` — the *query* block, not `epochStart` — so a candidate who entered at `epochStart+100` is present when querying at `epochStart+200`. [2](#0-1) 

The **checkpoint path** is the problem. `PostInsertBlock` calls `getCPMatrix(blockNum)` for every inserted block and writes a checkpoint at every `scoreCheckpointInterval()` boundary: [3](#0-2) 

The checkpoint at block `epochStart+50` is computed from `GetCandTesting(epochStart+50)`, which does not include C1 (who enters at `epochStart+100`). That checkpoint is then used as the seed for all subsequent `lookupCFSSeed` calls within the same epoch.

**Failure propagation through `applyBlocksForCPMatrix`**

Once the stale checkpoint is the seed, every block from `epochStart+51` onward is processed with a `CPMatrix` that has no entry for C1:

```go
for _, candidate := range cfReport {
    if _, ok := cpMatrix[candidate]; !ok {
        logger.Warn("cfReport contains address not in candidates list; skipping", ...)
        continue          // ← C1's failures are silently dropped here
    }
    cpMatrix.Increment(candidate, reporter)
}
``` [4](#0-3) 

`getCPMatrix` caches its result after every block: [5](#0-4) 

So the cache chain from `epochStart+51` onward is also stale. Every subsequent checkpoint written by `PostInsertBlock` is built on top of the stale cache and also lacks C1. The condition is permanent for the entire epoch: **C1 is never added to the matrix, and `CFS[C1]` stays 0 regardless of how many times C1 is reported.**

Note that `VerifyHeader` explicitly permits C1 to appear in `cfReport` for any block after `epochStart+100`, because it validates against `GetCandTesting(N-1)` which does include C1: [6](#0-5) 

So the reports are consensus-valid, but the scoring layer discards them.

**Downstream state-transition impact**

`GetCFS` feeds the `CandTesting → ValActive` transition in `kaiax/valset/impl/transition.go`. With `CFS[C1] = 0`, C1 passes the VRank threshold unconditionally and is promoted to `ValActive` even though it failed to respond to candidate messages throughout the epoch.

---

### Impact Explanation

An adversarial or simply poorly-performing node can register as a candidate mid-epoch, accumulate failures that would normally disqualify it, and still be promoted to `ValActive` because its CFS is permanently zero. This is an invalid state transition: a node that should remain in `CandTesting` (or be demoted) instead joins the active validator set, degrading consensus liveness and potentially enabling further privilege escalation within the validator set.

---

### Likelihood Explanation

This triggers on every node that enters `CandTesting` after the first checkpoint of an epoch — a routine event in any epoch where new candidates register. No special privileges, key compromise, or majority collusion is required. The checkpoint interval is a fixed configuration parameter, so the window is predictable and repeatable.

---

### Recommendation

When `applyBlocksForCPMatrix` encounters a `cfReport` address that is absent from the current `CPMatrix`, it should **add the candidate on the fly** rather than skip it:

```go
for _, candidate := range cfReport {
    if _, ok := cpMatrix[candidate]; !ok {
        // Late-entering candidate: initialize their row before recording the failure.
        cpMatrix[candidate] = make(map[common.Address]uint64)
    }
    cpMatrix.Increment(candidate, reporter)
}
```

Alternatively, `lookupCFSSeed` should merge the current `GetCandTesting(blockNum)` into any checkpoint-derived seed before returning it, ensuring all currently-active candidates are always present in the matrix.

---

### Proof of Concept

1. Configure `scoreCheckpointInterval = 50`, `vrankEpoch = 1000`.
2. At `epochStart`, no candidate C1 exists.
3. At `epochStart+50`, `PostInsertBlock` writes checkpoint CP50 with `cpMatrix = {}` (C1 absent).
4. At `epochStart+100`, C1 enters `CandTesting` via a permissionless staking transaction.
5. For blocks `epochStart+101` through `epochStart+200`, every proposer includes C1 in `header.VRank` (C1 fails to respond). `VerifyHeader` accepts these headers because C1 is in `GetCandTesting(N-1)`.
6. Call `GetCFS(epochStart+200)` (or observe it via `PostInsertBlock`):
   - `lookupCFSSeed(epochStart+200)` finds CP50 → seed has no C1.
   - `applyBlocksForCPMatrix(epochStart+51, epochStart+200, seed)` runs; every C1 entry hits `continue`.
   - `generateCFSFromCPMatrix` returns `{}` — C1 is absent.
7. At epoch end, `GetCFS(epochEnd-1)` returns `CFS[C1] = 0`; C1 passes the VRank threshold and transitions to `ValActive` despite 100 consecutive failures.
