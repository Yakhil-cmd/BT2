### Title
Webhook Signature Verifies the Payload's Self-Declared Organization, Not the Repository/Commit Actually Mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to HMAC-verify against using a field taken directly from the attacker-suppliable JSON body (`repository.owner.login` / `organization.login`), rather than from any value derived from the actual signature or a trusted routing key. Nothing then binds that authenticated organization to the repository/commit that the corresponding webhook handler subsequently mutates, most severely in `StatusHandler`, which writes commit status by a bare global `sha` lookup. This mirrors the reported Merkle bug class: a value that is checked (challenge/leaf hash resolved against `treeDepth`) is not the same value that is actually acted upon (leaf data written via `setNode`), so writes happen without being covered by the intended verification.

### Finding Description
`verify_signature` derives the organization used for HMAC validation entirely from the untrusted payload: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` then computes/validates the HMAC using that organization's configured `webhook_secret` against the raw body: [3](#0-2) 

Note also that if an organization is configured without a `webhook_secret` (a documented, supported configuration — `webhook_secret: nil`), verification is unconditionally skipped: [4](#0-3) [5](#0-4) 

Once "verified," the handler layer looks up the target repository from a *different, independently-controlled* field of the same payload (`repository.full_name`), not from the field used to select the verifying secret (`repository.owner.login`): [6](#0-5) 

Worse, `StatusHandler` — used to set CI/commit status that gates continuous deployment — does not even scope by repository; it matches purely by commit `sha` across the entire Shipit instance: [7](#0-6) 

**Binding that should hold, expressed as an equality:**
`organization whose webhook_secret authenticated the request` == `organization/repository owning the commit/stack that the handler writes to`.

**What actually happens:** the controller verifies the signature using `payload["repository"]["owner"]["login"]` (or `organization.login`) to pick the secret, but the handlers act on `payload["repository"]["full_name"]` (for stack lookup) or on a bare `sha` (for `StatusHandler`) — fields the same attacker fully controls in the same request body used to produce the signature. There is no assertion anywhere that these fields agree with each other or with the org whose secret validated the HMAC.

### Impact Explanation
An attacker who legitimately administers or has the webhook secret of any single GitHub organization/repository configured on this Shipit instance (or any organization configured with no `webhook_secret`, a supported default) can craft a POST to `/github/webhooks` whose `repository.owner.login`/`organization.login` matches their own org (so `verify_signature` passes) while `repository.full_name` and `sha` reference a victim stack/commit belonging to a completely different, unrelated repository/organization also hosted on the instance. This yields:
- Forged commit CI status (`status` event, `StatusHandler`) for arbitrary commits anywhere on the instance, which can flip `deployable_status`/`merge_status` checks and enable continuous deployment of a commit that never actually passed CI — an unauthorized deploy.
- Forged `push`/`pull_request`/`membership` events acting on a repository the attacker does not control, since `PushHandler` and PR handlers resolve target stacks purely from the attacker-controlled `repository.full_name` string.

This is a cross-repository-write / authentication-bypass condition: authentication is scoped to "some org configured in Shipit," but the write is scoped to "whatever repository/commit the attacker names in the same JSON body."

### Likelihood Explanation
Requires no session, no `ApiClient` token, and no GitHub private key — only the ability to send an HTTP POST to the public webhooks endpoint with a body whose HMAC matches one org's secret (which is often just as available as being a member/admin of any one org connected to the shared Shipit instance, or trivially bypassed when that org has no `webhook_secret` set, a state explicitly supported by the config template). Multi-tenant Shipit deployments hosting many independent organizations/repositories are the most exposed.

### Recommendation
- After signature verification succeeds, cross-check that `repository.owner.login` (the field used to select the verifying secret) equals the owner embedded in `repository.full_name` before dispatching to handlers; reject mismatches.
- In `StatusHandler` (and any other handler that looks up domain objects only by loosely-scoped fields like a bare commit `sha`), additionally scope the lookup to the repository identified by the verified organization, not merely by `sha`.
- Reconsider allowing `webhook_secret: nil` to silently disable verification; at minimum warn loudly or refuse to route events for such organizations in production.

### Proof of Concept
1. Shipit instance hosts two orgs: `attacker-org/attacker-repo` (attacker is an authorized admin, secret `S_a` known to attacker) and `victim-org/victim-repo` (unrelated stack, e.g. `shipit_canaries`, with `continuous_deployment: true` and a required status context).
2. Attacker crafts a `status` webhook JSON body:
```json
{
  "sha": "<victim commit sha awaiting real CI>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_a, body)` using their own known secret `S_a`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (regardless of `attacker-org/attacker-repo` in the payload), and calls `commit.create_status_from_github!(params)`, marking the victim commit's required status as `success` even though it was never sent by GitHub for `victim-org/victim-repo`.
6. If `victim-org`'s stack has `continuous_deployment: true` and this was the last blocking status, the forged status can trigger an unauthorized deploy of that commit. [8](#0-7) [3](#0-2) [7](#0-6)

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
