### Title
Webhook signature is verified against `repository.owner.login`, but event handlers act on `repository.full_name`/`sha`, allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `allowance()`/`withdraw()` bug is a case where the value used to *authorize* an action (`allowance()`) is never actually bound to the value used to *execute* it (`withdraw()`’s `amounts`), so the check can be satisfied while the real effect diverges. Shipit's webhook pipeline has the same shape: the field used to pick which secret authenticates the HMAC signature (`repository.owner.login`) is not the same field used to resolve which `Repository`/`Stack`/`Commit` is actually mutated (`repository.full_name`, `sha`). Both fields live in the same attacker-supplied JSON body, and nothing ties them together after the signature check passes.

### Finding Description
`Shipit::WebhooksController#verify_signature` picks the GitHub App/organization (and therefore the HMAC secret) to validate the incoming payload using only: [1](#0-0) [2](#0-1) 

That organization lookup is keyed on `params.dig('repository', 'owner', 'login')` (or `organization.login`), which is just an unauthenticated field of the same request body whose signature is later checked with `SecureCompare.secure_compare` in `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature check passes (using the secret belonging to whatever `owner.login` value the attacker put in the body), the payload is dispatched to handlers that resolve the target `Repository`/`Stack` using a *different* field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [4](#0-3) 

`PushHandler#process` uses that repository lookup, plus the attacker-controlled `ref`/`after`, to force a git sync on any matching stack: [5](#0-4) 

`StatusHandler#process` is worse: it doesn't even use the repository scoping helper — it looks up commits globally by `sha` across the whole install and writes a GitHub-style commit status onto them: [6](#0-5) 

Because Shipit explicitly supports multiple GitHub organizations sharing one Shipit instance, each with its own `webhook_secret`: [7](#0-6) 
an attacker only needs to be a legitimate admin of *one* tracked GitHub organization (their own `webhook_secret`) to craft a signed webhook whose `repository.owner.login` matches their own org (satisfying `verify_signature`) while `repository.full_name` (`PushHandler`) or `sha` (`StatusHandler`) references a completely different, victim organization's repository/commit that is also tracked by the same Shipit instance. The binding that should hold — "the organization whose secret authenticated this request" == "the repository being written to" — is never enforced.

### Impact Explanation
This crosses the repository trust boundary explicitly listed as in-scope: an organization that authenticated a webhook versus the repository that is actually written by the handler. Concretely:
- `StatusHandler` lets the attacker forge arbitrary CI status (`state`, `context`, `description`, `target_url`) on any commit (by SHA, discoverable via GitHub) belonging to a victim stack tracked in the same Shipit instance, regardless of which org owns it. Forged "success" statuses can satisfy `ci.require`/blocking-status checks and enable an unauthorized deploy of the victim's stack.
- `PushHandler` lets the attacker trigger `stack.sync_github(expected_head_sha:)` on the victim's stacks for a matching branch name, forcing Shipit to advance/mutate its tracked commit state for a repository the attacker does not control.

This matches the required High/Critical impact bucket "cross-repository writes" / "an unauthorized deploy", achieved with no repository write access, no ApiClient token, and no privileged Shipit account — only legitimate admin control of one, unrelated, tracked GitHub organization's webhook secret (or none at all, if that org has `webhook_secret: nil`, which is the documented default).

### Likelihood Explanation
Any Shipit deployment using the documented multi-org configuration (`docs/setup.md`, "Using Multiple Github Applications") is exposed to any org owner among the configured orgs. The attack requires no special access beyond being able to send a raw HTTP POST to `/webhooks` with a body they construct themselves (not proxied through GitHub), and knowledge of a target commit SHA or branch name, both of which are public GitHub metadata.

### Recommendation
Bind the authenticated organization to the resource being mutated: after signature verification succeeds, re-derive the target `Repository` using the same `repository.owner.login`/organization that was used to select the webhook secret (not `full_name` alone), and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits belonging to stacks under that verified repository/organization. Reject the webhook if `full_name`'s owner segment does not match the verified `owner.login`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, webhook secret known to attacker) and `OrgB` (victim), both tracked by the same Shipit instance, as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-orgb-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s real `webhook_secret` over this exact body and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates successfully (attacker's own secret matches attacker's own signed body).
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged "success" status onto the victim's `OrgB` commit — with no check that the commit's repository/organization matches `OrgA`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
