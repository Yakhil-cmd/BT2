### Title
Webhook organization used for signature verification is decoupled from the repository acted on by handlers, allowing cross-repository writes via an unsigned/mis-attributed payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, which is read from the JSON body itself (`repository.owner.login`, falling back to `organization.login`) [1](#0-0) [2](#0-1) . But the actual repository/stack that gets mutated by the event handlers is looked up from a *different* field of the same attacker-controlled body, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks` [3](#0-2) . Nothing binds these two fields together, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the selected organization [4](#0-3) .

### Finding Description
The trust binding that should hold is: `organization that authenticated == organization that owns the repository being written`. Concretely:

1. `verify_signature` computes `repository_owner` from the raw JSON payload (`params.dig('repository','owner','login') || params.dig('organization','login')`), and uses it to select a `GitHubApp` instance via `Shipit.github(organization: repository_owner)` [1](#0-0) .
2. That `GitHubApp`'s `verify_webhook_signature` HMACs the *entire raw body* against the secret configured for that organization — but per the docs, the webhook secret is **optional** per GitHub App / per organization [5](#0-4) , and when it is blank the method short-circuits to `return true unless webhook_secret` [6](#0-5) .
3. Once `create` runs, it re-parses the same raw body and dispatches to handlers (`PushHandler`, `StatusHandler`, etc.) [7](#0-6) . These handlers resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` — a completely independent field from the one used for org/secret selection in step 1 [3](#0-2) .

Because the field that gates the signature check (`repository.owner.login`) is never cross-checked against the field that determines which repository/stack is written to (`repository.full_name`), an attacker who can produce a request that passes verification for *any* configured organization (e.g., one Shipit installation added without setting a `webhook_secret`, which is explicitly documented as optional) can set `repository.full_name` to point at a completely different, victim organization's stack. The `push` handler will then call `stack.sync_github` for that victim stack based on unsigned/unauthenticated attacker-controlled data [8](#0-7) , and the `status` handler will create commit statuses for arbitrary commits by sha regardless of which repository they belong to [9](#0-8) , since `StatusHandler` doesn't scope by repository at all.

This is directly analogous to the ERC721 report's root cause: the code performs a privileged action (`transferFrom`) using a field/context that was never covered by the check meant to authorize it (approval was granted for a different actor than the one enforced by `onERC721Received`). Here, the "signature belongs to organization X" check never constrains "the write happens to organization X's repository."

### Impact Explanation
This allows cross-repository writes and unauthorized state changes to a stack belonging to an organization whose webhook was never actually verified in this request — matching the Critical bar for "cross-repository writes." Specifically:
- `push` events can trigger `GithubSyncJob`/`sync_github` on an arbitrary victim stack, causing Shipit to fetch and append attacker-influenced commit metadata for that stack.
- `status` events can inject or forge commit statuses (`create_status_from_github!`) for a commit belonging to any repository, since `StatusHandler` only looks up `Commit.where(sha:)` without validating repository ownership at all, which can be used to spoof CI status and unblock a deploy/merge for a stack the attacker doesn't control.

### Likelihood Explanation
Requires only that one organization/app configured in the multi-org `secrets.yml` (`docs/setup.md` "Using Multiple Github Applications" section) has an unset `webhook_secret` — an explicitly documented, supported, optional configuration — while another configured organization has a real production stack the attacker wants to target. No GitHub credentials, Shipit session, or `ApiClient` token are needed; the attacker only needs unauthenticated network access to `/webhooks` and knowledge of a target stack's repository `full_name`.

### Recommendation
Bind the signature-verifying organization to the repository actually mutated: after computing `repository_owner` for HMAC verification, re-derive the owner from `repository.full_name` (the same field handlers use) and reject the request if the two disagree. Additionally, do not treat an absent `webhook_secret` as an implicit "signature verified" — require organizations without configured secrets to be either explicitly marked as insecure/rejected, or require a secret to be present for all configured GitHub Apps. `StatusHandler` should also validate that the commit's stack/repository matches `repository.full_name` from the payload before creating a status.

### Proof of Concept
1. In `secrets.yml`, configure two GitHub orgs: `attacker-org` (no `webhook_secret` set) and `victim-org` (has a real Shipit stack and a `webhook_secret`).
2. Send `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
Omit/forge `X-Hub-Signature` arbitrarily.
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which returns `true` because `attacker-org` has no `webhook_secret` [6](#0-5) .
4. `create` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name` = `"victim-org/victim-repo"` [3](#0-2)  and triggers `sync_github` on the victim's real stack — despite the request never being validated against `victim-org`'s webhook secret.

**Uncertainty note:** I was not able to fully trace whether `Repository.from_github_repo_name` performs any additional cross-check against the requesting organization before resolving `full_name` to a `Stack` (index coverage limits prevented locating that model's implementation). If such a check exists there, it could partially or fully mitigate this specific push/status path; a Devin session with full repo access should verify `app/models/shipit/repository.rb` (`from_github_repo_name`) to confirm whether any additional binding exists before treating this as fully exploitable end-to-end.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
