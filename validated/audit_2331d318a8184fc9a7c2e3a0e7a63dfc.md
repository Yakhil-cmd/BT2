### Title
Uncaught exception in c-hash validation on malformed 32-char address strings crashes node processing – DoS via `isChashValid` / `isValidAddressAnyCase` - (File: chash.js)

### Summary
CVE-2017-10929 concerns `grub_memmove`/GRUB disk-read code performing a heap copy whose length is derived from untrusted input without validating that the actual decoded size matches the expected size, leading to an out-of-bounds memory operation and a crash. The analogous bug class in `ocore` is `chash.js`'s address/definition checksum verification, which decodes an attacker-controlled base32/base64 string and then performs fixed-length bit-splitting logic (`buffer2bin`, `separateIntoCleanDataAndChecksum`, `bin2buffer`) that assumes the decoded buffer always has exactly 160 or 288 bits. When the assumption is violated, the code `throw`s an `Error` from deep inside `separateIntoCleanDataAndChecksum` — outside of any `try/catch` in the caller — turning a routine "is this address well-formed" check into an uncaught exception that can crash the node process validating an incoming unit, trigger, or address reference.

### Finding Description
`isChashValid()` in [1](#0-0)  only wraps the base32/base64 **decode** step in `try/catch`:
```
try{
    var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
}
catch(e){
    console.log(e);
    return false;
}
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);
```
`separateIntoCleanDataAndChecksum()` [2](#0-1)  unconditionally throws if the decoded bit-length is not exactly 160 or 288:
```
var len = bin.length;
...
else
    throw Error("bad length="+len+", bin = "+bin);
```
This throw happens **outside** the try/catch that wraps only the decode call, so any code path that reaches this branch propagates an uncaught exception up the call stack rather than returning `false` like a normal validation failure.

The reachable path is through `isValidAddressAnyCase()`:
```
function isValidChash(str, len){
	return (isStringOfLength(str, len) && chash.isChashValid(str));
}
function isValidAddressAnyCase(address){
	return isValidChash(address, 32);
}
``` [3](#0-2) 

Unlike `isValidAddress()`, which first applies a strict regex `/^[A-Z2-7]{32}$/` restricting the input to the standard base32 alphabet before calling `isValidChash` [4](#0-3) , `isValidAddressAnyCase()` has **no charset restriction** — it only checks the string length is 32 and then hands the raw string straight to `base32.decode()`. Because `thirty-two`'s decoder is lenient/case-insensitive and does not enforce the same charset, a 32-character string containing characters outside the canonical alphabet (or unusual padding) can decode into a buffer whose bit length is not exactly 160, causing `separateIntoCleanDataAndChecksum` to throw uncaught.

`isValidAddressAnyCase` is used where case-insensitive address checks are performed (wallet/address-book style lookups reachable from attacker-supplied strings such as AA trigger data, oscript address parameters, or definition/authentifier fields that are validated as addresses without the strict-case regex).

### Impact Explanation
An attacker who can get a crafted 32-character string evaluated through `isValidAddressAnyCase` → `chash.isChashValid` (e.g., as part of an AA trigger payload, an `is_valid_address`/`is_aa` oscript evaluation input, or an address field checked case-insensitively) can force an uncaught `Error` to propagate through core validation/evaluation code. Depending on where it's caught by the surrounding async control flow, this can crash the node process handling the unit/trigger (denial of service), analogous to the crash impact of CVE-2017-10929's heap overflow — here manifesting as an uncaught JS exception rather than a memory-safety violation, since Node.js buffers are bounds-checked, but the outcome (crash of the party processing untrusted input) is the same class of impact: a network participant becomes unable to process further units/triggers, i.e., a node disagreement/availability issue when reached during unit/AA validation.

### Likelihood Explanation
Reachability requires a caller in the trigger/oscript/AA path that calls `isValidAddressAnyCase` on attacker-controlled strings without first constraining the charset via a strict regex. This is a narrower path than the general `isValidAddress` used throughout `validation.js`, which does properly regex-check the charset before hashing. The exact severity therefore depends on identifying a concrete caller of `isValidAddressAnyCase` that feeds it fully attacker-controlled 32-byte strings (e.g. from oscript, AA state variables, or trigger data) at unit/AA-validation time; I was not able to enumerate all such call sites within the available tool budget.

### Recommendation
- Move the length-mismatch checks in `separateIntoCleanDataAndChecksum` (and `mixChecksumIntoCleanData`) inside a `try/catch` in `isChashValid`, returning `false` instead of throwing, so malformed input is a clean "invalid chash" rather than an uncaught exception.
- Restrict `isValidAddressAnyCase` (and any other consumer of `chash.isChashValid`) to validate the decoded buffer length immediately after `base32.decode`/`Buffer.from` and return `false` on mismatch, mirroring the defensive regex check already used by `isValidAddress`.
- Audit all call sites of `isValidAddressAnyCase` to confirm whether attacker-controlled data reaches it during unit, AA-trigger, or oscript evaluation, and wrap those call sites in try/catch as defense in depth.

### Proof of Concept
```js
const chash = require('./chash.js');
// 32-character string using characters outside canonical base32 alphabet,
// accepted by isValidAddressAnyCase's plain length check (no regex),
// but potentially decoded by thirty-two into a non-20-byte buffer.
const malformedAddr = "0189abcdefghijklmnopqrstuvwxyz01"; // illustrative; exact byte-length mismatch depends on thirty-two's decode behavior for out-of-alphabet chars
try {
    console.log(chash.isChashValid(malformedAddr));
} catch (e) {
    console.log("uncaught crash:", e.message); // "bad length=..., bin = ..."
}
```
