### Title
Cross-stack CI-status disclosure via `CCMenuController#stack` bypassing ApiClient stack scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Shipit's API layer enforces a "stack a token authorizes" binding: every `ApiClient` can optionally be scoped to a single `stack_id`, and `Api::BaseController#stacks`/`#stack` restrict lookups to that scope. `Api::CCMenuController` re-implements its own `stack` method that calls `Stack.from_param!` directly, completely skipping the `current_api_client.stack_id` restriction. Any valid, otherwise properly-scoped `read:stack` `ApiClient` token can therefore be used to fetch the CCMenu (CI status/deploy) XML of *any* stack in the installation, not just the one it was issued for.

### Finding Description
`Api::BaseController` defines the authorization scoping that all API stack-resource controllers are expected to rely on: [1](#0-0) 

`current_api_client.stack_id?` gates whether the client is restricted to a single `Stack`; if it is, `Stack.where(id: current_api_client.stack_id)` is the only lookup scope, and `stack` (used by every other resource, e.g. `Api::DeploysController`, `Api::TasksController`) is built on top of that scoped relation.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

`Stack.from_param!` performs a global, unscoped lookup by `repo_owner/repo_name/environment`: [3](#0-2) 

`ApiClient#check_permissions!` only checks that the permission string (`read:stack`) is present in the client's permission list — it has no concept of *which* stack the operation is being performed on: [4](#0-3) 

So the only place stack-scoping is actually enforced is the `stacks`/`stack` helper in `BaseController` — and `CCMenuController` doesn't use it. The route is mounted per-stack (`/api/stacks/:stack_id/ccmenu`), so the `stack_id` in the URL is fully attacker-controlled independent of the token's own scope: [5](#0-4) 

The existence of stack-scoped tokens as an intended security boundary is confirmed by the test suite, which explicitly asserts that a stack-scoped client "will only see that one stack" for the sibling `StacksController`: [6](#0-5) 

This is exactly the "stack a token authorizes vs. stack it touches" trust binding: for `Api::StacksController`/`DeploysController`/`TasksController`, `token.stack_id == accessed_stack.id` is enforced; for `Api::CCMenuController` it is not — the equality silently becomes `token.stack_id == any_stack.id`.

### Impact Explanation
A holder of a legitimately-issued, narrowly-scoped `read:stack` `ApiClient` token (intended only to expose CI-status for one stack, e.g. to a CI badge/dashboard integration) can enumerate and read the deploy/CI state (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, `webUrl`, activity) of every other stack managed by the Shipit instance, including stacks belonging to unrelated repositories/teams. This is an authorization-scope escalation and unauthorized cross-stack read of stack state, matching the "High - escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state" impact bucket, since it defeats the deliberate per-token stack restriction that the rest of the API enforces.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (the documented/tested use case) to third parties or CI integrations with limited trust: exploitation requires only that token and knowledge/guessing of another stack's `repo_owner/repo_name/environment` path segment (which is often predictable or discoverable), and a single unauthenticated-relative-to-scope GET request.

### Recommendation
- **Short term**: Make `Api::CCMenuController#stack` reuse the inherited, scope-aware `stacks`/`stack` helper from `Api::BaseController` instead of calling `Stack.from_param!` directly, so `current_api_client.stack_id` restrictions apply uniformly.
- **Long term**: Centralize all stack resolution in API controllers through a single scoped helper (never call `Stack.from_param!`/`Stack.find` directly from an `Api::*Controller`), and add a regression test asserting a stack-scoped `ApiClient` cannot fetch another stack's CCMenu output.

### Proof of Concept
1. As an admin, create (e.g. via console/seed, mirroring the fixture used in `test/controllers/api/stacks_controller_test.rb`) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id. Issue its `authentication_token` to a third party.
2. The third party calls `GET /api/stacks/<Stack-B-owner>/<Stack-B-repo>/<Stack-B-env>/ccmenu` using HTTP Basic auth with the token from step 1, where Stack B is a different stack than the one the token was scoped to.
3. Compare with the equivalent call to `Api::DeploysController#index` (`GET /api/stacks/<Stack-B>/deploys`) using the same token — that endpoint correctly returns 404/`RecordNotFound` because `stacks` filters to Stack A only, while `ccmenu#show` returns 200 with Stack B's CI/deploy XML, proving the scoping bypass.
