### Title
Bridge KAIA Permanently Locked When Recipient Contract Rejects Native Token Push — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in the Kaia service-chain bridge pushes KAIA directly to the caller-supplied `_to` address via a low-level `.call.value()`. If `_to` is a contract that reverts on receiving native tokens, every operator attempt to settle that nonce reverts, the nonce is never consumed, and the user's KAIA locked in the source bridge is permanently unrecoverable.

---

### Finding Description

`BridgeTransferKLAY.handleKLAYTransfer` is the destination-side handler that operators call to release KAIA to the intended recipient after a cross-chain request. The final two lines of the function are:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

The `_to` address is taken verbatim from the original `RequestValueTransfer` event emitted on the source chain when the user called `requestKLAYTransfer`:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [2](#0-1) 

Any user can supply any address as `_to`, including a contract with no `payable` fallback or one that explicitly reverts on receipt. When operators relay the request and call `handleKLAYTransfer`, the entire transaction reverts (including the preceding `_updateHandleNonce` state changes), so the nonce is never marked as handled:

```solidity
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
// ...
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [3](#0-2) 

`_updateHandleNonce` advances `lowerHandleNonce` only through a consecutive run of handled nonces (`handleNoncesToBlockNums[i] > 0`). A permanently unhandleable nonce stops this scan:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    recoveryBlockNumber = handleNoncesToBlockNums[i];
    ...
}
lowerHandleNonce = i;
``` [4](#0-3) 

There is no admin escape hatch to skip a nonce, redirect funds, or override `_to`. The bridge contract exposes no such function.

---

### Impact Explanation

- The user's KAIA deposited into the source bridge via `requestKLAYTransfer` is permanently locked; the source bridge holds the funds and there is no refund path.
- The stuck nonce prevents `lowerHandleNonce` from advancing, freezing `recoveryBlockNumber` at the pre-stuck value. The off-chain recovery daemon (`ValueTransferRecovery`) will perpetually re-scan from that old block, and the stuck request will be retried indefinitely without success.
- All subsequent nonces can still be individually processed (the `_lowerHandleNonceCheck` only requires `lowerHandleNonce <= _requestedNonce`), but the bridge's sequential accounting is permanently corrupted for that nonce slot.

---

### Likelihood Explanation

Any user who bridges KAIA to a smart-contract address that lacks a `payable` fallback (e.g., a multisig, a DAO treasury, a DeFi protocol, or any contract deployed without a receive function) triggers this condition. No privileged access is required. The user only needs to call `requestKLAYTransfer` with such a `_to`. This is a realistic scenario given that many protocol treasuries and smart-contract wallets do not accept raw KAIA pushes.

---

### Recommendation

Replace the push-payment pattern with a pull-payment (escrow) model on the destination bridge:

1. Instead of `_to.call.value(_value)("")`, credit the amount to an internal mapping: `pendingWithdrawals[_to] += _value`.
2. Add a `withdraw()` function that lets `_to` pull their KAIA at any time.
3. This ensures `handleKLAYTransfer` always succeeds regardless of `_to`'s ability to receive native tokens, and the nonce is always consumed.

Alternatively, add a bridge-owner function to redirect a stuck nonce to a different address, allowing recovery without a full protocol redesign.

---

### Proof of Concept

1. Alice deploys a contract `Vault` on the destination chain with no `payable` fallback.
2. Alice calls `requestKLAYTransfer(Vault, 1 ether, "")` on the source bridge, sending `1 ether + fee`. Her KAIA is locked in the source bridge; a `RequestValueTransfer` event is emitted with nonce N.
3. Bridge operators observe the event and call `handleKLAYTransfer(txHash, Alice, Vault, 1 ether, N, blockNum, "")` on the destination bridge.
4. The call reverts with `"handleKLAYTransfer: transfer failed"` because `Vault` has no payable fallback.
5. Operators retry indefinitely — every attempt reverts.
6. `handleNoncesToBlockNums[N]` is never set; `lowerHandleNonce` is stuck at N.
7. Alice's 1 KAIA is permanently locked in the source bridge with no recovery path. [5](#0-4) [6](#0-5)
