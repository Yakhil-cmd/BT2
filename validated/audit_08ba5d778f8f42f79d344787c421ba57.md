### Title
Wallet Contract permanently hardcodes the Address Registrar account, so registrar migration silently breaks relayer fraud-detection for already-deployed ETH-implicit accounts - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract (deployed to every ETH-implicit account, per NEP-518) hardcodes the `AddressRegistrar` contract's account id at compile time via `include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID")`, which currently resolves to `address-map.near`. This value is baked into the wasm binary that is deployed once, permanently, to each ETH-implicit account, and that account's code can never be redeployed or its state manually fixed because ETH-implicit accounts have no full-access key and cannot be deleted. If the `AddressRegistrar` contract is ever migrated to a new account (the same category of event the external report calls out for `OriginToken`/`TokenMigration`), every already-deployed Wallet Contract will keep querying the old, now-stale registrar forever, silently degrading the fraud-detection check that protects users from a faulty/malicious relayer misrouting funds.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is a compile-time constant read from a file and embedded directly in the contract binary: [1](#0-0) 

It is used, without any on-chain override or update mechanism, whenever a relayer submits an emulated EOA base-token transfer whose target resolves to another ETH-implicit account: [2](#0-1) 

The purpose of this call is safety-critical: it detects a lazy or faulty relayer that set `target` to the raw ETH-implicit address instead of resolving it to the real named account that has since registered that address. If the registrar says the address *is* registered, the relayer is banned and the transfer is blocked; if the registrar (incorrectly, because it's stale) says the address is *not* registered, the transaction proceeds as an ordinary transfer straight to the ETH-implicit target: [3](#0-2) 

Crucially, once a Wallet Contract is deployed to an ETH-implicit account, it can never be redeployed or updated by any user action, because ETH-implicit accounts cannot receive a full-access key and cannot be deleted: [4](#0-3) 

This means there is no protocol-level or user-level path to update `ADDRESS_REGISTRAR_ACCOUNT_ID` for accounts that already exist at the time of any future registrar migration — exactly the class of bug described in the report: "the Marketplace contract does not update the references to the previously deployed OriginToken address... resulting in broken functionality."

### Impact Explanation
If the `AddressRegistrar` (`address-map.near`) is ever migrated to a new account (e.g. due to a bug fix, storage-layout change, or any reason requiring redeployment under NEP-141/NEP-145-style upgrade), every ETH-implicit account created before the migration keeps calling the old, now-authoritative-in-name-only registrar. New registrations made after the migration in the new registrar will be invisible to those legacy Wallet Contracts. Consequently:
- The `address_check_callback` fraud-detection path can be bypassed: a relayer (malicious or merely stale) supplying a target that hashes to an address newly registered post-migration will not be flagged, and the transfer executes as a direct transfer to the raw ETH-implicit account rather than being rejected/banned.
- Funds can be misdirected to an unintended account instead of the properly registered named account, i.e., an unauthorized diversion of user balance that the safety check was specifically designed to prevent.
- Because affected accounts can never have their code redeployed, this is not a one-time incident but a permanent, irreversible loss of the safety guarantee for every ETH-implicit account created before the migration.

### Likelihood Explanation
This requires an actual migration/redeployment of the `AddressRegistrar` contract to occur; no such migration exists in the codebase today, so this is a latent architectural weakness rather than an actively exploited bug. However, given the registrar's account id is hardcoded with no upgrade path, and ETH-implicit accounts are explicitly documented as immutable, the likelihood of this becoming a real incident is directly proportional to any future operational need to move or redeploy the registrar — a routine kind of maintenance for other contracts in the ecosystem (as the original report's `TokenMigration` precedent shows). Exploitation additionally requires a relayer prepared to submit the misrouting transaction, which is an unprivileged, permissionless role by design (any account can relay transactions for a Wallet Contract).

### Recommendation
- Short term: Do not treat `ADDRESS_REGISTRAR_ACCOUNT_ID` as an immutable compile-time constant referenced by all historically-deployed Wallet Contracts. Provide a protocol-level mechanism (e.g., a system parameter read at execution time, similar to `registrar_account_id` already used elsewhere in the runtime config) so the registrar reference can be updated for all ETH-implicit accounts without requiring code redeployment.
- Long term: Design and test a migration strategy for the `AddressRegistrar` contract analogous to what the report recommends for `OriginToken`/`Marketplace`, ensuring that any future registrar migration is validated against all already-deployed Wallet Contract instances before being considered safe.

### Proof of Concept
1. Deploy `AddressRegistrar` at `address-map.near` (as currently hardcoded) and register account `alice.near` for address `0xAAA...`.
2. Deploy an ETH-implicit Wallet Contract account today; it hardcodes `address-map.near` as its registrar per `ADDRESS_REGISTRAR_ACCOUNT_ID`.
3. Simulate a future migration: deploy a new `AddressRegistrar` at `address-map-v2.near`, and register `bob.near` for a fresh address `0xBBB...` only in the new contract (the old `address-map.near` never learns of this registration).
4. Have a relayer submit an RLP transaction through the pre-migration Wallet Contract with `target` set to the ETH-implicit account matching `0xBBB...` (instead of resolving to `bob.near`).
5. `inner_rlp_execute` triggers the `address_check` flow, which calls `lookup` on the stale `address-map.near` registrar per [5](#0-4) ; this returns `None` because the registration only exists in `address-map-v2.near`.
6. `address_check_callback` therefore does not detect the faulty relayer and instead executes a direct transfer to the ETH-implicit target account per [6](#0-5) , silently bypassing the safety check that should have redirected/blocked the transfer to `bob.near`.
