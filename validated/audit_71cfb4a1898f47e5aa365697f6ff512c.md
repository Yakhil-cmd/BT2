### Title
Webhook status/push events verified against one organization's secret but acted upon by cross-tenant/global lookups that ignore that organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the *same* untrusted JSON body it is about to verify. Once the signature checks out (i.e. it was produced by *some* organization legitimately configured in `secrets.yml`), the event is dispatched to handlers that consume a *different* field of the same body to decide what data to mutate. In `StatusHandler`, that field is `sha`, and the lookup `Commit.where(sha: params.sha)` is **global** - it is never scoped to the organization/repository that authenticated the request.

### Finding Description [1](#0-0) 
`verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and uses it purely to pick which configured `Shipit.github(organization:)` webhook secret verifies the HMAC: [2](#0-1) 

Verification only proves the payload was signed by *an* organization present in the multi-tenant `github:` config (see the documented multi-org setup in `docs/setup.md`), it proves nothing about the content of any other field in that same payload.

The dispatched handler for `status` events is: [3](#0-2) 
`Commit.where(sha: params.sha)` has no `stack_id`/repository scoping at all - it matches any commit in the entire Shipit installation sharing that SHA, regardless of which organization the commit's stack/repository belongs to.

More generally, the base `Handler` class does resolve a `repository_name` from `payload.dig('repository','full_name')` for scoping (`stacks`) in most handlers: [4](#0-3) 
but this `full_name` is an independent field from `repository.owner.login` used for signature routing - nothing cross-checks that the organization whose secret verified the signature actually owns the repository named in `full_name` (or, in `StatusHandler`'s case, any repository at all).

**Binding broken:** `organization_that_authenticated (repository.owner.login → webhook_secret used for HMAC) ≠ repository/commit_that_is_written (repository.full_name / sha used by the handler)`.

**Concrete exploitation path (multi-tenant Shipit instance, as documented in `docs/setup.md` "Using Multiple Github Applications"):**
1. Attacker administers/owns "OrgA", one of the organizations legitimately registered in the shared Shipit instance's `secrets.yml` (`somegithuborg`). They have a real, valid `webhook_secret` for OrgA (e.g. by configuring a webhook on any repo they control under OrgA, or by having genuine, low-privilege access to trigger real GitHub events from their own org - no Shipit session, `ApiClient` token, or access to the victim org is required).
2. Attacker crafts a `status` (or `push`) POST to `/github/webhooks` with `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's secret) but with `sha` (for `status`) or `repository.full_name` (for `push`) referring to a commit/repository belonging to "OrgB", a completely different, unrelated tenant.
3. The HMAC, computed over the full raw body with OrgA's real secret, verifies successfully because the controller only ever checks *whose* secret was used, never whether that organization actually owns the resource being mutated.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on any matching commit(s) anywhere in the database, including those belonging to OrgB's stacks.

### Impact Explanation
A forged commit status on another tenant's commit can flip `Commit#deployable?` (`stack.ignore_ci? || (success? && !blocked?)`) and `blocking_statuses` evaluation, i.e. the attacker can mark an otherwise CI-blocked commit as "success" for a stack they have no access to. Where `merge_queue_enabled?` is set and `allows_merges?` depends on `merge_status == 'success'`, this forged status can unblock automatic merges/deploys for a stack that belongs to an organization the attacker does not control, without ever needing a Shipit session, `ApiClient` token, or write access to the victim repository - a cross-tenant integrity break that can contribute to an unauthorized deploy/merge. This aligns with the "High" bucket (escalation across an authorization boundary) and potentially contributes to "Critical" (unauthorized deploy/merge) depending on downstream automation (merge queue, continuous delivery schedule) configured on the victim stack.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit instance with more than one organization configured (explicitly documented as a supported feature in `docs/setup.md`), and (b) the attacker controlling a legitimate, low-privilege GitHub App/webhook_secret for *any one* of those organizations - not the victim's. Given that Shipit deployments commonly onboard many internal teams/orgs onto a single shared instance, and that `StatusHandler`'s lookup is unconditionally global, likelihood is non-trivial for any shared/multi-org deployment. For single-org deployments, this specific `StatusHandler` gap collapses (the only entity that can produce a valid signature is the sole configured org, which already owns all stacks), so the analog is primarily meaningful in the documented multi-org configuration.

### Recommendation
- In `WebhooksController`/`Handler`, after verifying the signature, cross-check that the resource actually mutated (repository `full_name`'s owner, or the commit's `stack.repository`) matches the `repository_owner`/organization whose secret validated the signature. Reject the event otherwise.
- Scope `StatusHandler#process` (and any other handler using bare identifiers like `sha`) to commits belonging to a `Repository`/`Stack` whose owning organization matches the authenticated `repository_owner`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner })`.

### Proof of Concept
Conceptual request against a Shipit instance configured with two organizations (`OrgA`, `OrgB`) in `secrets.yml`, where the attacker legitimately controls OrgA's webhook secret:

```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>

{
  "sha": "<sha of a commit belonging to OrgB's stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" } }
}
```
`verify_signature` selects OrgA's secret (valid, attacker-computed), passes; `StatusHandler#process` then updates the status of OrgB's commit globally via `Commit.where(sha: ...)`, with no cross-org check. This could be replayed for `push` events by likewise mismatching `repository.owner.login` (used only for the secret) against `repository.full_name` (used by `PushHandler`/`Handler#stacks` to trigger `GithubSyncJob` for OrgB's stacks).

Note: I could not execute this against a live multi-org test fixture within this session; the analysis is based on static code tracing of `verify_signature`, `Handler#stacks`/`#repository_name`, and `StatusHandler#process`, and the documented multi-organization configuration in `docs/setup.md`. If further confirmation is needed (e.g., exact behavior of `Shipit.github(organization:)`'s org-key matching or `merge_queue`/CD automation triggers), a full Devin session with repository access would be required to run the existing test suite (`test/controllers/webhooks_controller_test.rb`, `test/unit/shipit_test.rb`) against a crafted multi-org fixture.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
