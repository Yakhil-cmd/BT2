### Title
Webhook signature is verified against the organization named in the payload, but downstream handlers act on a different, unvalidated `repository.full_name` field — allowing cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the HMAC against based on `repository_owner`, itself parsed out of the *unverified* JSON body. All webhook handlers (`PushHandler`, `PullRequest::*Handler`, etc.), however, resolve the target `Repository`/`Stack` using a *different* field of the same body — `repository.full_name`. Nothing ties these two fields together, so a party who legitimately controls the webhook secret for **any one** organization configured on the Shipit instance can forge a signed payload whose `repository.owner.login` matches their own org (so the secret check passes) while `repository.full_name` names a **completely different** organization's repository tracked by the same Shipit instance.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handler acts on`

Concretely:
- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and fetches the app config via `Shipit.github(organization: repository_owner)`, then verifies the HMAC signature with that org's `webhook_secret`. [1](#0-0) 
- `repository_owner` is derived purely from attacker-supplied JSON, read before/independently of any cryptographic check — it is only used to pick *which* secret to check against, not validated itself. [2](#0-1) 
- Every handler (`Handler#repository_name`, and the `PullRequest::*` handlers) instead identifies the target repository/stack via `payload.dig('repository', 'full_name')`, completely independent of `repository.owner.login`. [3](#0-2) [4](#0-3) 
- `Repository.from_github_repo_name` looks the repo up purely from the string `full_name`, with no cross-check against the org whose secret validated the request. [5](#0-4) 

Shipit is explicitly designed to be multi-tenant on a single webhook endpoint: multiple GitHub organizations, each with its own `webhook_secret`, can be configured simultaneously in `secrets.yml` (see `somegithuborg` / `someothergithuborg`), and all of them POST to the same `WebhooksController#create` endpoint. [6](#0-5) 

Because `repository.owner.login` (used only to select the verification secret) and `repository.full_name` (used to find the actual `Repository`/`Stack` acted upon) are never checked for consistency, anyone who possesses a valid `webhook_secret` for **one** organization hosted on the instance can sign an arbitrary payload with `repository.owner.login` set to their own org (secret matches, so `verify_signature` passes) while setting `repository.full_name` to `victim-org/victim-repo` — a repository belonging to a completely different, unrelated organization also tracked by the same Shipit instance.

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" trust binding, letting a party with only one organization's webhook secret act as if they own an unrelated organization's repository. Concretely, the forged `push` event drives `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: ...)` for the victim's stack. That in turn triggers `GithubSyncJob`, which fetches "missing commits" from GitHub using the Shipit app's own installation token (`stack.github_api`), appends them as tracked commits, and re-caches the deploy spec. [7](#0-6)  If the victim stack has continuous deployment enabled, this can drive an unauthorized deploy of attacker-influenced commit history using the app's own GitHub credentials against a repository the attacker does not otherwise have push access to — satisfying the "unauthorized deploy" / cross-repository-write impact class. Other handlers (`pull_request` family) allow archiving/unarchiving review stacks or updating PR metadata for victim repositories under the same forged-secret condition.

### Likelihood Explanation
Exploitation requires the attacker to already know a valid `webhook_secret` for at least one organization configured on the target Shipit instance — a realistic bar for any of the organizations that use the shared instance (e.g., a partner/subsidiary org's GitHub App admin, or anyone who can read that org's `secrets.yml`/App settings), but not the victim organization's own secret. Given Shipit's documented support for hosting multiple organizations behind one webhook endpoint, this is a plausible deployment topology, though exploitability depends on the operator actually configuring more than one organization on the instance.

### Recommendation
After the HMAC signature is verified for `repository_owner`, additionally assert that `repository.full_name`'s owner segment matches `repository_owner` (or `organization.login`) before dispatching to any handler; reject the webhook otherwise.

### Proof of Concept
1. Operator configures two orgs on one Shipit instance: `org-a` (webhook_secret `SECRET_A`) and `org-b` (webhook_secret `SECRET_B`), each with stacks tracking their own repos, per `config/secrets.development.shopify.yml`.
2. Attacker, who legitimately administers `org-a`'s GitHub App and therefore knows `SECRET_A`, crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-reachable-in-org-b/victim-repo>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")`, verifies the signature against `SECRET_A` — passes.
5. `PushHandler#repository_name` reads `full_name` = `"org-b/victim-repo"`, resolves `org-b`'s `Stack`, and enqueues `GithubSyncJob` for it — despite the request never being authenticated by `org-b`'s own secret.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
