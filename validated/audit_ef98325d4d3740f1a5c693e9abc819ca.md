## Finding

Note: `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb:21`) matches statuses purely by `Commit.where(sha: params.sha)` — it never scopes by repository/stack at all, so any commit sha across any repo/stack in the whole Shipit instance can have its CI status overwritten by a "status" webhook. Combined with the signature-selection design in `WebhooksController`, this is worth flagging precisely.

### Title
Webhook signature is verified against the org derived from the payload's `repository.owner.login`, but the acted‑upon repository is derived independently from `repository.full_name`/commit `sha`, letting a valid signer for one GitHub org forge state for another org's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the `webhook_secret` used to authenticate the request based on `repository_owner`, a value read straight out of the untrusted, attacker-influenced JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and never cross-checks it against the field(s) actually consumed by the event handlers (`repository.full_name` for `Handler#repository_name`, or bare `sha` for `StatusHandler`). This is exactly the class of bug in the reported contract issue: one field is what gets "authorized" (the emission cap / the signing org), while a *different* field is what gets *acted on* (the reward amount / the target repository or commit), and nothing enforces they refer to the same entity.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` resolves the GitHub App/secret with: [1](#0-0) 
using `repository_owner`, defined as: [2](#0-1) 

In a multi-org deployment (`docs/setup.md` documents per-organization `webhook_secret`s), this means the HMAC is checked against *whichever* org's secret matches the `repository.owner.login` claimed in the payload. Once verified, `create` dispatches the entire raw JSON to every registered handler for the event: [3](#0-2) 

Handlers do not re-derive/re-check the organization used for signature verification. `Handler#repository_name` reads `repository.full_name`: [4](#0-3) 

and `StatusHandler#process` is worse still — it doesn't even consult the repository field, it matches purely by commit `sha` across the entire commits table: [5](#0-4) [6](#0-5) 

So the binding actually enforced is: `signature valid for org(repository.owner.login)`. The binding that is *needed* for safety is: `signature valid for org(repository.owner.login) == org that owns the Stack/Commit being mutated`. Nothing in the code ties these together — an entity that legitimately controls a webhook secret for OrgA (i.e., is a valid GitHub App installer/admin for OrgA, not a Shipit user, not holding any Shipit credential) can send an HMAC computed with OrgA's `webhook_secret` while filling the body with `repository.full_name`/`sha` values belonging to an entirely different org/stack (OrgB) tracked by the same Shipit instance. `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) only checks the raw body against one secret; it has no knowledge of, and does not enforce, consistency between `repository.owner.login` and `repository.full_name`, nor does it scope which repos can be referenced.

For `status` events specifically, this lets an attacker with OrgA's webhook secret write an arbitrary state/description/target_url/context for *any* commit sha in *any* stack in the whole install via `Commit#create_status_from_github!`, which is used by `Commit#deployable?` (`stack.ignore_ci? || (success? && !blocked?)`) and `Commit#blocked?`, i.e., it directly feeds Shipit's CI-gating logic used before deploys.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out in scope. Forging a `success` status for a required CI context on a commit in a target stack removes the safety gate (`deployable?`) that governs whether that commit is eligible to deploy, and can also flip `blocked?`/unlock merges via `stack.schedule_merges` (`Commit#add_status`, `app/models/shipit/commit.rb:374-384`). This can enable an unauthorized/unsafe deploy or merge to proceed on a stack the attacker has no legitimate GitHub or Shipit relationship to, satisfying the "unauthorized deploy/merge" High/Critical impact bar, without requiring any Shipit session, API token, or GitHub write access to the target repository — only possession of a *different* org's webhook secret.

### Likelihood Explanation
Requires: (1) the Shipit instance configured with multiple GitHub Apps/organizations (documented, supported feature — `docs/setup.md:182-209`), and (2) the attacker controlling the webhook secret of at least one of those orgs (e.g., as a legitimate GitHub App installer/admin of their own onboarded org — an "unprivileged" party relative to the *other* org/stack being attacked). Given webhook secrets are configured per-org and Shipit is designed to host many orgs/repos in one instance, this is a realistic misuse path for any tenant who is not fully trusted by the others sharing the instance.

### Recommendation
After signature verification, re-validate that the organization derived from the verifying secret matches the owner encoded in every repository reference the handler will act on (`repository.full_name`'s owner segment), and reject/short-circuit otherwise. For `StatusHandler`, additionally scope the `Commit` lookup by the resolved `Repository`/`Stack` (via `repository_name`) rather than matching bare `sha` across the whole install, so a status can only ever be applied to commits that actually belong to the org whose secret validated the webhook.

### Proof of Concept
1. Shipit configured with two GitHub Apps/orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`), each with stacks tracking their own repos.
2. Attacker holds `OrgA`'s `webhook_secret` (e.g., legitimately installed OrgA's GitHub App for their own org) but has no access to `OrgB`.
3. Attacker crafts a `status` event JSON body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/decoy"}, "sha": "<sha of a real pending/failing commit in an OrgB stack>", "state": "success", "context": "<OrgB's required CI context>", ...}`.
4. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over the raw body and POSTs to `/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the signature validates successfully because it was computed with the correct (OrgA) secret.
6. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — which finds the OrgB commit regardless of which repository/org field was in the payload — and calls `create_status_from_github!`, marking it `success` for the required context, potentially flipping `deployable?` to `true` and unblocking deploy/merge for a stack the attacker never had legitimate access to.
