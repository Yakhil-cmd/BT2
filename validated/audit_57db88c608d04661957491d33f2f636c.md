### Title
A malicious/untrusted commit pushed to a tracked ref can permanently break `git-sync`'s sync loop, causing persistent sync denial - (File: main.go)

### Summary
The reported CollateralToken/PublicVault bug shows how attacker-controlled content (a malicious ERC721 `approve()`) can make one required step of a larger operation revert, and because that step is a hard dependency for all subsequent processing, the entire pipeline (liquidation, then epoch rollover for the whole vault) becomes permanently stuck. The same fragile "any single required git command must succeed or the whole pipeline halts" pattern exists in `git-sync`'s `SyncRepo` function: an attacker who can push a commit to the tracked ref (e.g. a malicious/broken submodule reference, a corrupt object, or content that fails Git's built-in sanity checks) can make every subsequent sync attempt against that ref fail, permanently denying sync to all consumers of the sidecar.

### Finding Description
`repoSync.SyncRepo` performs a strictly sequential set of git operations to converge the local worktree with the remote ref: fetch, `rev-parse`, optional `sanityCheckWorktree` (`git fsck`), `git reset`, `worktree add`, and then `configureWorktree`, which runs `git reset --hard` and, when submodules are enabled (the default is `recursive`), `git submodule update --init --recursive`: [1](#0-0) 

Any error returned from these steps aborts `SyncRepo` for that cycle with no partial success and no skip logic: [2](#0-1) 

Because `--ref` always points at the same branch/tag, and the fetch/rev-parse/checkout of that same broken commit is repeated identically on every loop iteration, the failure is deterministic and will recur every single period. The outer loop increments `failCount` and, once `--max-failures` is exceeded, calls `os.Exit(1)`: [3](#0-2) 

The default value of `--max-failures` is `0`, meaning "any sync failure will terminate git-sync": [4](#0-3) 

In a Kubernetes sidecar deployment (the tool's primary documented use case) this results in a crash-loop: the container restarts, re-attempts the same commit, and fails again indefinitely, since the underlying git content that causes the failure (e.g. a submodule pointing at an unreachable/malicious URL, a bad `.gitmodules` entry, or a tree that fails `git fsck --connectivity-only`) does not change until a new commit is pushed to fix or revert it. Submodule handling explicitly runs untrusted, attacker-supplied URLs from the tracked repo's `.gitmodules`: [5](#0-4) 

This mirrors the reported bug class: a single attacker-influenced step (approve/`submodule update`) that is a hard prerequisite of the whole synchronization/liquidation pipeline can be made to fail, and the surrounding retry/abort logic has no way to make forward progress past it, leading to a persistent denial of service for the entire consuming system (the vault's epoch processing / all consumers of the synced volume) rather than only the malicious element.

### Impact Explanation
If an attacker (or compromised collaborator) can push a commit to the ref that `git-sync` tracks — for example a submodule entry referencing an unreachable/hostile URL, or content that trips `git fsck`'s connectivity check — every future sync attempt against that ref will fail identically. With the default `--max-failures=0` this crashes the process; under Kubernetes it becomes a permanent `CrashLoopBackOff`, and the published symlink is frozen at the last-good commit (or never created on first sync), denying updates to every application container consuming the sidecar's data indefinitely, until an operator manually intervenes (e.g. force-push a fix, or set `--max-failures=-1` and manually resolve the offending commit). This is a persistent sync denial matching the impact criteria in the validation rules.

### Likelihood Explanation
This requires only push access (or PR-merge access) to the specific ref git-sync is configured to track — the exact "untrusted repo content / attacker-pushed commit" reachability the rules call out as in-scope. No special git-sync flags beyond the default submodule/sanity-check behavior are needed; `--submodules=recursive` is the default, and `sanityCheckWorktree`'s `git fsck` runs unconditionally on every reused worktree. Any environment where the tracked branch accepts contributions from less-trusted parties (shared branch, automated merges from forks, etc.) is exposed.

### Recommendation
- Make a single bad step in `SyncRepo` non-fatal to the overall loop where feasible: e.g., detect a specific "poison" commit hash and skip/backoff on it (do not repeatedly retry the exact same doomed operation) while surfacing a clear error/metric.
- Consider decoupling `git fsck`/submodule failures from the higher-level abort path so partial or previous good state stays published rather than crash-looping the whole sidecar.
- Document/expose a way to "pin back" to last-known-good and continue attempting only new refs rather than being stuck retrying a known-bad HEAD.
- Recommend operators set `--max-failures` intentionally and monitor `git_sync_count_total`/error metrics so a stuck ref is detected instead of silently crash-looping.

### Proof of Concept
1. Deploy `git-sync` tracking a branch that accepts pushes from a less-trusted contributor, with default flags (`--submodules=recursive`, `--max-failures=0`).
2. Attacker pushes a commit to that branch adding a submodule entry pointing at a URL that will fail to clone/update (e.g., an unreachable host, or a URL requiring credentials git-sync doesn't have), as demonstrated by the legitimate submodule test flow in [6](#0-5) , but pointing at a host that will always fail.
3. On the next poll, `configureWorktree`'s `git submodule update --init --recursive` step fails [7](#0-6) , `SyncRepo` returns an error, `failCount` reaches `--max-failures` (0), and `os.Exit(1)` is called [8](#0-7) .
4. Under Kubernetes, the pod restarts and repeats step 3 forever (CrashLoopBackOff) because the same bad commit is fetched again, resulting in persistent denial of sync for all consumers until an operator manually fixes/reverts the offending commit.

```go
func (git *repoSync) SyncRepo(ctx context.Context, syncHooks syncHooks) (bool, string, error) {
	git.log.V(3).Info("syncing", "repo", redactURL(git.repo))

	if err := syncHooks.refreshCreds(ctx); err != nil {
		return false, "", fmt.Errorf("credential refresh failed: %w", err)
	}

	// Initialize the repo directory if needed.
	if err := git.initRepo(ctx); err != nil {
		return false, "", err
	}

	// Find out what we currently have synced, if anything.
	var currentWorktree worktree
	if wt, err := git.currentWorktree(); err != nil {
		return false, "", err
	} else {
		currentWorktree = wt
	}
	currentHash := currentWorktree.Hash()
	git.log.V(3).Info("current state", "hash", currentHash, "worktree", currentWorktree)

	// This should be very fast if we already have the hash we need. Parameters
	// like depth are set at fetch time.
	if err := git.fetch(ctx, git.ref); err != nil {
		return false, "", err
	}
```
