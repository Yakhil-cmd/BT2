### Title
Spending authority resolves against the stale `Account.owner` snapshot instead of the live position-NFT owner, freezing the transferee's funds and leaving control with the previous holder - (File: contracts/controller/src/account.rs)

### Summary
CVE-2025-41248 is about a security check that silently resolves against the wrong target — an annotation on a method in a parameterized supertype is never detected, so the guard is effectively applied to a different method than the one invoked. The analog in XOXNO Lending: the account spending-authority check `require_owner_or_delegate` resolves authority against the `owner` field baked into the `Account` struct at mint time, while the authoritative notion of ownership is the transferable position-NFT's `owner_of`. After a `position-nft::transfer`, every value-moving entrypoint keeps authenticating the *old* holder.

### Finding Description
When an account is created, `create_account_with` stores `owner` inside the `Account` struct (`contracts/controller/src/account.rs:64-70`). All spending paths (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) funnel through `require_owner_or_delegate(env, account_id, caller, &account.owner)` (`account.rs:102`, `account.rs:106`, and the strategy modules), which only checks `caller == owner` or a delegate keyed under that stored owner (`is_owner_or_delegate`, `account.rs:115-127`). The `account.owner` field is never resynced afterward — the only update path is account deletion via `remove_account_and_burn_nft`.

Meanwhile the protocol's own canonical ownership source is the NFT: `require_account_owner` (used by `add_delegate`, `remove_delegate`, `renew_account`) deliberately reads `storage::account_owner(env, account_id)` — the live `owner_of` — not `account.owner` (`account.rs:143-148`). The position NFT is a fully transferable stock OpenZeppelin `NonFungibleToken` (`contracts/position-nft/src/contract.rs:131-133`), and its header documents that "the token owner (`owner_of`) is the account owner" (`contract.rs:1-3`). So the system maintains two notions of ownership that diverge after any `transfer`/`approve`+`transfer_from`, and the check that guards the money reads the stale one — precisely the CVE's shape of a guard resolved on the wrong member.

### Impact Explanation
Two-sided loss, both reachable by unprivileged addresses via the in-scope `position-nft::transfer`/`approve`/`transfer_from` surface plus standard controller entrypoints:

- **Permanent freezing of funds for the transferee.** The new NFT holder — who per `contract.rs` *is* the account owner — cannot `withdraw`, `borrow`, `repay_debt_with_collateral`, or run any strategy; `is_owner_or_delegate` rejects them with `NotAuthorized` because `caller != account.owner` and they hold no delegate grant under the old owner. Only the TTL-renewal and delegate-management paths (which read the live NFT owner) work for them. Their collateral is permanently locked unless the old holder cooperates.
- **Theft of user funds.** The *previous* holder retains full spending authority: `caller.require_auth()` plus `caller == account.owner` still passes, so a seller can transfer the NFT to a buyer and then immediately `withdraw` the collateral or `borrow` against it, keeping the sale proceeds and draining the position's value.

Either outcome satisfies the acceptance bar (theft of user funds / permanent freezing of funds).

### Likelihood Explanation
No special conditions are needed: any account owner can call `position-nft::transfer` at any time — it is stock OZ functionality with no controller hook to resync `account.owner`. An NFT marketplace trade, an OTC position sale, or even an accidental transfer instantly desynchronizes the two ownership sources. The attack on a buyer requires only that the victim purchase a position NFT, a documented use of the contract.

### Recommendation
Make the spending guard consult the same ownership source as the rest of the system: in `require_owner_or_delegate` / `is_owner_or_delegate` (`contracts/controller/src/account.rs:115-140`), resolve `storage::account_owner(env, account_id)` (the live NFT `owner_of`) instead of `account.owner`, and key delegate lookups under that live owner. Alternatively, remove the `owner` field from `Account` entirely so there is a single canonical ownership record, or disable NFT transfers if positions are intended to be non-transferable.

### Proof of Concept
1. Alice supplies USDC via `controller::supply(caller=alice, account_id=0, ...)`; the minted `Account` stores `owner = alice` (`account.rs:64-70`).
2. Alice sells/transfers the position NFT to Bob: `position_nft::transfer(alice, bob, token_id)`. `owner_of` is now Bob; `account.owner` remains Alice.
3. Bob calls `controller::withdraw(caller=bob, account_id, ...)`. `load_or_create_account`/`require_owner_or_delegate` compares `bob == account.owner(alice)` → `is_owner_or_delegate` returns false → `GenericError::NotAuthorized`. Bob's collateral is frozen (`account.rs:130-140`).
4. Alice calls `controller::withdraw(caller=alice, account_id, ...)`: `alice == account.owner` passes `is_owner_or_delegate` (`account.rs:121-123`), post-pool risk gates are evaluated on the still-solvent account, and Alice receives Bob's collateral — theft of user funds.
5. The asymmetry is observable directly: Bob *can* call `add_delegate`/`renew_account` because `require_account_owner` reads `storage::account_owner` (`account.rs:143-148`), while being rejected from every value-moving path — proving the two guards resolve different owners for the same account.

Note: I verified the stale-owner divergence and the two divergent guard implementations; I did not exhaustively confirm that no other code path rewrites `account.owner` on NFT transfer (no sync call exists in `position-nft`, whose mint/burn/upgrade are controller-only and `transfer` is the stock OZ implementation with no controller callback — `contract.rs:131-133`), so the absence of a resync hook is inferred from the NFT contract having no notification path to the controller.
