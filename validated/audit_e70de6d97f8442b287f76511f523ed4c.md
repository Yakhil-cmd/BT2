### Title
Cross-Organization Webhook Confirmation Bypass Enables Forged Commit Status on Any Stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook's HMAC signature against based on an **attacker-controlled JSON field** (`repository.owner.login` / `organization.login`), while the handler that actually acts on the payload (`StatusHandler`) resolves its target purely by commit `sha` with **no repository/organization scoping at all**. This breaks the binding "organization whose secret authenticated the request == repository/commit the request is allowed to affect," letting an attacker who legitimately controls one onboarded GitHub organization forge a commit-status webhook that is validated with *their own* organization's secret but is applied to a commit belonging to a completely different organization's stack.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret to check against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted, attacker-supplied JSON body (`params.dig('repository','owner','login')`), and `Shipit.github(organization: repository_owner)` selects the corresponding webhook secret (Shipit supports one webhook secret per organization, as shown in `config/secrets.development.shopify.yml`). If the attacker legitimately installed the Shipit-integrated GitHub App on their own organization (`orgB`), they know `orgB`'s `webhook_secret` and can produce a valid `X-Hub-Signature` for any payload, as long as `repository.owner.login` (or `organization.login`) in that payload is set to `"orgB"`.

Once signature verification passes, the event is dispatched to handlers based on the `event` header, and those handlers independently read `repository.full_name` (a separate JSON field, uncorrelated with `repository.owner.login`) to resolve the target stack — see the shared `Handler#repository_name` helper: [3](#0-2) 

Critically, `StatusHandler` doesn't even use `repository_name`/`stacks` scoping — it resolves target commits purely by SHA across the entire installation: [4](#0-3) [5](#0-4) 

Because `Commit.where(sha: params.sha)` has no `stack_id`/repository filter, any commit sha known to the attacker (e.g., obtained from a public PR, from Shipit's own UI, or from monitoring another organization's activity) can have an arbitrary status (`state`, `context`, `description`) attached, regardless of which organization's secret validated the request.

This is precisely the reported bug class translated to this engine: the report's `Leap.depositEth()` checked a global invariant (`totalRaised` vs `maxRaiseAmount`) using state that could be manipulated between check and use by an unprivileged party; here, the "check" (webhook signature verification, scoped to `repository_owner`) and the "use" (status/commit mutation, scoped independently by `sha`/`repository.full_name`) are two disjoint bindings on the same request that the attacker can decouple, because nothing enforces that the authenticated organization equals the repository/commit being mutated.

### Impact Explanation
Forged commit statuses feed directly into merge and continuous-deployment safety gates: [6](#0-5) [7](#0-6) [8](#0-7) 

`all_status_checks_passed?`, `deployable?`, and `schedule_continuous_delivery` all rely on the `Status`/`CheckRun` records that `StatusHandler` writes without any repository check. An attacker who legitimately controls one onboarded GitHub org (a low-privilege, unprivileged-relative-to-other-tenants position) can post a "success" status for a required CI context on a commit belonging to a stack/repository they have no access to, causing `MergeRequest#merge!` to proceed via `ProcessMergeRequestsJob`, or `ContinuousDeliveryJob` to fire a deploy — i.e., an **unauthorized merge or deploy** on a repository/stack the attacker does not control. This matches the "Critical: unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
Requires the attacker to control (or know the `webhook_secret` of) at least one organization already onboarded onto the shared Shipit instance — a realistic multi-tenant scenario per `config/secrets.development.shopify.yml`'s documented multi-org support — plus knowledge of a target commit SHA in another organization's repository (commonly discoverable via public GitHub activity, Shipit's own public-facing pages, or the `merge_status` endpoint which is explicitly `skip_authentication`). No repository write access or Shipit session is needed; only the ability to sign an HTTP POST to `/webhooks`.

### Recommendation
- Verify the webhook signature using the secret that corresponds to the repository/stack actually referenced by `repository.full_name` in the payload, not an independently attacker-chosen `repository.owner.login`/`organization.login` field — or verify both are consistent before proceeding.
- Scope `StatusHandler#process` (and any other handler that queries by `sha` alone) to the resolved `stacks`/`Repository` context derived from the verified organization, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, instead of a global `Commit.where(sha:)`.
- Consider binding the webhook secret to the specific installation ID present in signed GitHub App payloads rather than a client-supplied login string.

### Proof of Concept
1. Attacker legitimately installs/onboards the Shipit GitHub App on `org-attacker`, obtaining its `webhook_secret`.
2. Attacker identifies a commit SHA `deadbeef...` belonging to a stack under `org-victim/private-repo` (e.g., visible via a public PR or Shipit UI).
3. Attacker crafts a `status` event payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/private-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_org-attacker, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner => "org-attacker"`, loads `org-attacker`'s secret, and the signature matches — request passes.
6. `Shipit::Webhooks::Handlers::StatusHandler#process` executes `Commit.where(sha: "deadbeef...")` (global lookup, no org scoping) and creates a "success" `Status` on the victim's commit.
7. If this was a required/blocking status, `MergeRequest#all_status_checks_passed?` or `Commit#deployable?` now evaluate true for the victim's stack, potentially triggering an automatic merge or continuous deploy that the victim never authorized.
