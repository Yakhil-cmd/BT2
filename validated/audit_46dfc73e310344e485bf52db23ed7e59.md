### Title
Webhook signature verification keys off `repository.owner.login` while event processing acts on `repository.full_name`, letting an attacker with valid credentials for one GitHub organization forge deploy-affecting events for a repository belonging to another organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate an inbound GitHub webhook using an organization name pulled straight out of the untrusted, unverified request body, while the handlers that actually execute the corresponding side effects (queueing syncs, writing commit statuses, archiving/unarchiving stacks) key off a *different* field of that same untrusted body: `repository.full_name`. Because both fields are attacker-controlled parts of the payload being signed, and multi-org Shipit deployments keep a distinct `webhook_secret` per organization, an attacker who legitimately controls (or has compromised) the GitHub App installation/webhook secret of Organization A can forge a payload that authenticates as Organization A but whose `repository.full_name` points at a repository owned by Organization B, causing Shipit to act on Organization B's stack.

### Finding Description
In multi-org mode, secrets are stored per organization and looked up via `Shipit.github_app_config(organization)`: [1](#0-0) 

The webhook signature is verified using the organization name derived from the same JSON body whose signature is being checked: [2](#0-1) [3](#0-2) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, which is a **separate JSON field** from `repository.full_name`. Nothing ties these two fields together — an attacker fully controls both, and only needs the signature to validate against the org named in `owner.login`.

Once the signature check passes, the event dispatch and every handler resolve the target repository/stack from `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

This pattern repeats across `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`, and the `pull_request/*` handlers, all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (or the equivalent `repository_name`/`stacks` helper on the base `Handler` class) to find the stack to mutate, e.g.: [5](#0-4) 

The binding that should hold is:
`organization whose webhook_secret authenticated the request == organization that owns the repository being written to`

but the code instead enforces only:
`organization named in payload.repository.owner.login (attacker-controlled) == organization whose secret verified the signature`

with no cross-check that `payload.repository.full_name`'s owner segment matches `payload.repository.owner.login`, or that the resolved `Stack`/`Repository`'s organization matches the organization that authenticated the request.

### Impact Explanation
An attacker holding a legitimate GitHub App installation (and therefore knowledge of the `webhook_secret`) for *any* organization configured in this Shipit instance's `secrets.github` multi-org map can forge webhook deliveries that are processed as if they originated from a different, victim organization's repository. Concretely:
- Forging a `status` event with `repository.full_name` set to a victim stack's repo can inject a fabricated passing CI status for an arbitrary commit SHA, which can satisfy `ci.require` checks and trigger an unauthorized continuous deployment of that stack (see `README.md` `ci.require` docs referenced in the deployment flow), i.e. an unauthorized deploy.
- Forging `pull_request` events (`labeled`/`unlabeled`/`reopened`/`closed`) lets the attacker archive/unarchive review stacks belonging to the victim organization's repository, a cross-organization write to state that should be scoped to the authenticated org.

This crosses the "organization authenticated versus the repository that is written" trust boundary called out for this class of finding, and lands in the High/Critical impact bucket (unauthorized deploy / cross-repository writes) without requiring any Shipit session, API token, or the victim's own `webhook_secret`.

### Likelihood Explanation
Exploitability requires the attacker to control (legitimately or via compromise) at least one organization's GitHub App installation that is configured in the *same* multi-org Shipit deployment as the victim organization — a realistic scenario for shared internal Shipit instances that onboard many teams/orgs, which is exactly the use case the multi-org `secrets.github` schema (`TOP_LEVEL_GH_KEYS`, `github_app_config`) was built for. No other authentication artifact (no `ApiClient` token, no user session) is required; only the ability to send an HTTP POST to `/webhooks` with a crafted body and a valid HMAC for the attacker's own org.

### Recommendation
In `WebhooksController#verify_signature`, after locating `github_app` by `repository_owner`, additionally verify that the resolved `Stack`/`Repository` for the event's `repository.full_name` actually belongs to that same organization before dispatching to handlers — e.g. reject the event if `Repository.from_github_repo_name(params.dig('repository','full_name'))&.owner&.casecmp?(repository_owner)` is false. Alternatively, derive the organization used for `Shipit.github(organization: ...)` lookup from the resolved `Stack`'s configured organization rather than from the raw, unauthenticated payload field.

### Proof of Concept
1. Shipit is configured in multi-org mode with `secrets.github` containing both `attacker-org` (with `webhook_secret: S_A`, controlled/known by attacker) and `victim-org` (owning stack for `victim-org/victim-repo`, with CI requirement `ci.require`).
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha awaiting CI>",
  "state": "success",
  "context": "required-ci-check",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker signs the raw body with `S_A` (their own known secret) and sets `X-Hub-Signature` accordingly, `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC validates successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. The `status` handler resolves the target stack via `repository.full_name == "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and creates a passing `Status` for the victim stack's commit, potentially satisfying `ci.require` and triggering an unauthorized deploy of `victim-org/victim-repo`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
