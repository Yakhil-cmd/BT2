### Title
StatusHandler#process resolves commits by `sha` alone, allowing a webhook authenticated for Repo A to write a `Status` and trigger a deploy on a different, unrelated Repo B's stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever checking that the matched commit's stack belongs to the same repository/organization that authenticated the webhook. Because `sha` is only unique per `(sha, stack_id)` pair in the database, not globally, a `status` webhook that is cryptographically valid for Repo A's organization can create a `Status` row on a completely different Repo B's stack if any `Commit` row with a matching `sha` exists there, which then drives `Stack#trigger_continuous_delivery` for Repo B.

### Finding Description
The claimed binding is: `organization that signed the webhook (repository_owner of params.repository.full_name) == organization owning the stack whose Status/Commit is mutated`. This does not hold in code.

`WebhooksController#verify_signature` only checks that the request's HMAC signature matches the GitHub App secret for `repository_owner` (derived from `params.dig('repository','owner','login')`): [1](#0-0) 
It never further constrains which `Commit`/`Stack` rows the handler is allowed to touch — that responsibility is left to each `Handler` subclass.

The base `Handler` class provides exactly this scoping primitive, `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` from `payload.dig('repository','full_name')`: [2](#0-1) 

`StatusHandler#process`, however, never calls `stacks` or checks `repository_name`/`repository.full_name` at all — it queries `Commit` globally by `sha`: [3](#0-2) 

`Commit` rows are only unique per `(sha, stack_id)`, not globally unique by `sha`: [4](#0-3) 
so the same `sha` value can legitimately exist as separate `Commit` rows belonging to different stacks/repositories (e.g., identically-constructed git commit objects, or an attacker deliberately crafting a git commit object with the same tree/parents/author/committer/timestamps as a public commit already known to exist in Repo B's history and already synced into Shipit as a `Commit` row for stack B).

`Commit#create_status_from_github!` writes the `Status` using `stack_id` taken from the matched `Commit`, not from the webhook payload's repository: [5](#0-4) 

`Status.replicate_from_github!` persists the row with that `stack_id` verbatim: [6](#0-5) 

and `after_commit :schedule_continuous_delivery` on `Status` delegates to the commit, which is the commit belonging to the mismatched stack: [7](#0-6) [8](#0-7) 

**Exploit flow:**
1. Attacker owns Repo A, which is legitimately onboarded to the same Shipit instance (so Repo A's org has a real `webhook_secret`).
2. Attacker identifies a commit that already exists as a `Commit` row for Repo B's stack (synced there by a normal push webhook via `PushHandler`/`GithubSyncJob` when Repo B's own maintainers pushed it) — a commit whose `state` (`success`/`context`) they want to forge for Repo B's stack, where the stack has `continuous_deployment: true`, `ignore_ci: false`.
3. Attacker crafts (locally, with `git`) a commit object in Repo A with **identical** `sha` to that Repo B commit. Since git SHA-1 is a pure function of tree, parent(s), author, committer, message and timestamps, this requires no cryptographic collision — the attacker only needs to reproduce the exact object content (feasible if Repo B's commit metadata is public, e.g., empty-tree "initial commit" objects, or objects the attacker can otherwise observe/replicate).
4. Attacker pushes this commit to Repo A and/or directly POSTs a forged `status` GitHub webhook event to `/webhooks` with `sha`, `state: success`, and a `context` chosen to satisfy Repo B's `blocking_statuses`, with `repository.full_name`/`repository.owner.login` set to Repo A.
5. `verify_signature` validates the payload using Repo A's real secret — it succeeds, because the check is scoped to signature validity for the *stated* repository owner, not to which `Commit` rows get mutated downstream.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the Repo B `Commit` row (in addition to, or instead of, any Repo A row), and calls `create_status_from_github!` on it, writing a `Status` with `stack_id` = Repo B's stack.
7. `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob` for Repo B's stack; `Stack#trigger_continuous_delivery` calls `trigger_deploy`, deploying Repo B's code on Repo B's deploy host — all driven by a payload that only Repo A's organization authenticated.

None of the existing guards prevent this: `verify_signature` checks org-level HMAC only; `drop_unhandled_event` just checks event type is handled; the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, `context`, etc.) does not constrain `sha` to the requesting repository; and `Handler#stacks`/`repository_name` scoping exists in the base class but is simply not used by `StatusHandler`.

### Impact Explanation
An attacker with control of any onboarded Repo A can cause a `Status` row to be written against an arbitrary other stack (Repo B) and can trigger `ContinuousDeliveryJob`/`trigger_deploy` for Repo B, resulting in an unauthorized deploy on Repo B's deploy host driven by a payload Repo B never authenticated. This is a cross-tenant mutation ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy") and is repeatable against any stack that has a `Commit` row sharing a `sha` the attacker can reproduce, across the entire multi-tenant Shipit instance, not limited to Repo A's own organization.

### Likelihood Explanation
Preconditions: both Repo A and Repo B onboarded to the same Shipit instance; Repo B's target `Commit` (sha) already synced into Shipit (normal for any actively-deployed branch); Repo B's stack has `continuous_deployment: true` and `ignore_ci: false` (or attacker forges `context`/state matching required blocking statuses); attacker needs no privileged Shipit role, session, token, or secret — only ownership of any legitimately onboarded Repo A and the ability to reproduce a git commit object with a specific `sha` (achievable via standard `git` commit-crafting with matching tree/parents/author/committer/timestamps/message, not a SHA-1 preimage break). This is inexpensive and repeatable per target commit/stack.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to the repository that authenticated the webhook, mirroring the `stacks` helper already provided by `Handler`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
i.e., resolve commits via `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` before matching by `sha`, so a `Status` can never be attributed to a stack outside the authenticated repository.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status webhook authenticated for repo A must not create a Status on repo B's stack" do
  repo_a = shipit_stacks(:shipit) # onboarded, webhook_secret verified for its org
  repo_b_stack = shipit_stacks(:cyclimse) # different org/repo entirely
  shared_sha = 'deadbeefdeadbeefdeadbeefdeadbeefdeadbeef'

  # Simulate a Commit row for Repo B already synced from a legit push
  commit_b = repo_b_stack.commits.create!(sha: shared_sha, author: shipit_users(:shipit),
    authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now, message: 'init')

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  request.headers['X-Github-Event'] = 'status'

  body = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => repo_a.github_repo_name, 'owner' => { 'login' => repo_a.github_organization } }
  }.to_json

  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [stack_id: repo_b_stack.id]) do
    assert_difference -> { commit_b.statuses.count }, 1 do
      post :create, body:, as: :json
    end
  end

  # Binding check: the org that signed (repo_a's org) != the org owning the mutated stack (repo_b_stack's org)
  assert_not_equal repo_a.github_organization, repo_b_stack.github_organization
  assert_equal repo_b_stack.id, commit_b.statuses.last.stack_id
end
```
This asserts both sides of the broken binding explicitly and demonstrates `ContinuousDeliveryJob` enqueued for Repo B despite the webhook only authenticating Repo A.
