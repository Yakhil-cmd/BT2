### Title
Unbounded disk-write during extension asset download allows attacker-controlled repository to exhaust user's disk space - (File: pkg/cmd/extension/http.go)

### Summary
The reported Brahma issue is a class of vulnerability where an untrusted, attacker-influenced value (`tx.gasprice`) is used without any upper bound to determine how much of a victim's resource is consumed, letting the attacker unilaterally drain the victim. The closest reachable analog in `gh` is in the extension-installation download path: `gh extension install <owner/repo>` streams a GitHub release asset directly to disk with no size limit, where the asset's existence, name, and size are entirely controlled by the (potentially malicious) extension-repository owner that the user is installing from.

### Finding Description
`downloadAsset` in `pkg/cmd/extension/http.go` performs the actual byte transfer for `gh extension install`: [1](#0-0) 

It issues an HTTP GET to `assetURL` (built from the release's `APIURL`, itself taken from data returned by the extension owner's repository release), opens the destination file, and calls `io.Copy(f, resp.Body)` with no `io.LimitReader`, no `Content-Length` check, and no maximum-size enforcement: [2](#0-1) 

This is invoked from `installBin` in `pkg/cmd/extension/manager.go`, which selects the platform-matching release asset and downloads it to a path under the extension install directory: [3](#0-2) 

Because the asset's byte stream originates from a third-party repository the user chose to install an extension from (`gh extension install owner/gh-extension`, including custom GHES hosts per the command's own documentation), the "gas price" analog here is the response body: the remote repository owner fully controls how many bytes are served for the named asset, with no client-side cap. A malicious extension author can publish a release whose binary asset is arbitrarily large (or an endless/streaming response), and `gh` will write it to disk in full.

### Impact Explanation
Unlike the original financial-drain report, there is no monetary loss here, but the impact is directly analogous: an attacker (extension publisher, or a compromised release pipeline) unilaterally decides how much of the victim's resource — disk space — is consumed during a routine, expected `gh` operation, with no client-side cap. This can fill the user's disk, causing operational disruption to other host or system processes writing to the same volume, and is fully attacker-driven with no user consent to the actual size.

### Likelihood Explanation
Reachable via a normal, unprivileged, remote-attacker-controlled path: any user can be induced (or can choose) to run `gh extension install <owner/repo>` against an attacker-owned or attacker-compromised repository/release, which is a documented, first-class `gh` workflow (`pkg/cmd/extension/command.go` `install` subcommand text explicitly supports installing from arbitrary GitHub/GHES repositories). No elevated privilege or MITM is required — only that the user willingly (or via social engineering, e.g. a "recommended extension" link) install from the attacker's repo.

### Recommendation
Bound the download in `downloadAsset` (and the analogous `pkg/cmd/run/download/http.go` / `pkg/cmd/release/download/download.go` paths) by:
- Checking `resp.ContentLength` against a sane maximum before starting the copy.
- Wrapping `resp.Body` in `io.LimitReader` with a hard cap and treating truncation/overflow as an error.
- Optionally streaming to a temp file first, verifying size, then renaming into place, so partial oversized downloads don't leave stray large files on disk.

### Proof of Concept
1. Attacker creates a public repository `attacker/gh-evilext` with a GitHub Release containing a binary asset matching the victim's platform naming convention (e.g. `gh-evilext-linux-amd64`), but sets the asset content to a very large or effectively unbounded stream (e.g. via a release asset proxy/redirect to a slow, endless data source, or simply an extremely large legitimate asset).
2. Victim runs `gh extension install attacker/gh-evilext`.
3. `Manager.Install` → `installBin` → `downloadAsset` (`pkg/cmd/extension/http.go:79-111`) issues `httpClient.Do(req)` and unconditionally `io.Copy`s the entire response body to `binPath` on the victim's local disk with no size cap, consuming disk space entirely at the attacker's discretion.

// downloadAsset downloads a single asset to the given file path.
func downloadAsset(httpClient *http.Client, assetURL safeurl.SafeURL, destPath string) (downloadErr error) {
	var req *http.Request
	if req, downloadErr = http.NewRequest("GET", assetURL.String(), nil); downloadErr != nil {
		return
	}

	req.Header.Set("Accept", "application/octet-stream")

	var resp *http.Response
	// TODO(api-client-rollout)
	// This has been deferred from moving to api.Client due to its custom Accept header and binary response streaming.
	if resp, downloadErr = httpClient.Do(req); downloadErr != nil {
		return
	}
	defer resp.Body.Close()

	if resp.StatusCode > 299 {
		downloadErr = api.HandleHTTPError(resp)
		return
	}

	var f *os.File
	if f, downloadErr = os.OpenFile(destPath, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, 0755); downloadErr != nil {
		return
	}
	defer func() {
		if err := f.Close(); downloadErr == nil && err != nil {
			downloadErr = err
		}
	}()

	_, downloadErr = io.Copy(f, resp.Body)
	return
}
