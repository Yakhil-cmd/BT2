### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler#process` enables unauthorized PR merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone, with no scoping to the repository that signed the incoming webhook, unlike the base `Handler` class which exposes a repository-scoped `stacks` helper that this handler never uses. An attacker who owns any GitHub repository can send a validly-signed `status` webhook for their own org, but with an arbitrary `sha` (and `state: success`) value, and Shipit will apply that status to *any* `Commit` record in the database whose `sha` matches — including a completely unrelated victim stack's pending merge-request head commit — enabling an unauthorized merge.

### Finding Description
The broken binding is: `request signer (Shipit.github(organization: repository_owner_from_payload))` should equal `stack.repository.owner` for every `Commit` record mutated by the request, but `StatusHandler#process` never checks this.

Code path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled JSON payload (`params.dig('repository', 'owner', 'login')`). This only proves the payload was signed by *some* org's webhook secret — the attacker's own, since they configured it on their own repo. It proves nothing about which commits the payload is allowed to affect.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, with no join/filter on `stack`/`repository`. Contrast with `Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), which other handlers use to scope by `Repository.from_github_repo_name(repository_name)` — `StatusHandler` bypasses that mechanism entirely.
3. `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`) creates a new `Status` record using the *victim* commit's own `stack_id`, and `Commit#add_status` (`app/models/shipit/commit.rb:366-386`) calls `stack.schedule_merges` when the new status is `success`, enqueuing `ProcessMergeRequestsJob` for the **victim's** stack.
4. `ProcessMergeRequestsJob#perform` (`app/jobs/shipit/process_merge_requests_job.rb:10-32`) calls `merge_request.refresh!`, then `all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`), which reads `head.statuses_and_check_runs` — now containing the forged success `Status` — and returns true, so `merge_request.merge!` is invoked, calling `stack.github_api.merge_pull_request` on the **victim's** repository/PR.

Attacker's exact action: knowing (from the public PR page) the victim's PR head commit sha, the attacker configures a webhook on a repository they own, and sends (or causes GitHub to send, e.g. by creating a commit status via the API on any sha string in their own repo) a `status` event payload: `{"sha": "<victim_head_sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker/repo"}}`. This is signed with the attacker's own webhook secret, so `verify_signature` passes.

Existing guards fail because: `verify_signature` only authenticates the *organization/secret*, not the *sha ownership*; `ExplicitParameters` schema (`params do ... requires :sha ... end`) only validates types/presence, not repository binding; `drop_unhandled_event` and `check_if_ping` are irrelevant; there is no `Repository`/`Stack` scoping applied before the `Commit.where(sha:)` lookup, unlike what `Handler#stacks` would provide.

### Impact Explanation
A single forged, self-signed webhook from an attacker-owned repository causes a merge of a victim's pull request whose real CI status is failing, on `stack.github_api.merge_pull_request` (`app/models/shipit/merge_request.rb:169-176`) — an unauthorized merge of unreviewed/CI-red code into the victim's protected branch. This is repeatable against any victim stack/commit sha the attacker can learn (PR head shas are typically public), and is not limited to one tenant — any Shipit-managed stack with `merge_queue_enabled` and a pending merge request is exposed, satisfying the "payload for one repository mutating another's stack/commit/merge" Critical-impact criterion (unauthorized merge).

### Likelihood Explanation
Preconditions required: victim stack has `merge_queue_enabled`/`allows_merges?` true and a `pending` `MergeRequest`; attacker needs only to own any GitHub repository (to get a legitimate webhook secret) and to know the victim's PR head sha (public information for open PRs). No Shipit credentials, session, API token, or GitHub App keys are needed. Cost is a single crafted HTTP POST to `/webhooks`; the attack is trivially repeatable against multiple victim stacks in the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` to the repository asserted by the verified webhook payload, mirroring `Handler#stacks`: join `Commit` to `Stack`/`Repository` and only update commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')` (i.e., `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), rejecting/ignoring status updates for shas not owned by the authenticated repository.

### Proof of Concept
Minitest plan (using existing test helpers, no live GitHub):
```ruby
test "status webhook from an unrelated repository cannot forge a status onto another stack's commit and trigger a merge" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled, allows_merges? stubbed true
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim head')
  merge_request = victim_stack.merge_requests.create!(number: 42, head: victim_commit, merge_status: 'pending')

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }

  # Signature verified with attacker-org's own legit secret (simulate WebhooksController#verify_signature passing)
  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  victim_commit.reload
  refute victim_commit.statuses.where(state: 'success').exists?,
    "status forged by an unrelated repository's webhook must not attach to another stack's commit"

  victim_stack.github_api.expects(:merge_pull_request).never
  Shipit::ProcessMergeRequestsJob.new.perform(victim_stack)
end
```
Assert both sides of the binding: `attacker_payload['repository']['full_name']` (the authenticated repository) must equal `victim_commit.stack.repository.full_name` before any `Status` row tied to `victim_commit` is created; currently they diverge and the status is still created, and `merge_pull_request` still fires, proving the vulnerability.         stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
