### Title
Unbounded/attacker-controlled Merkle proof loop causes hangs and false verification results in oscript `is_valid_merkle_proof` and `in merkle` address conditions - (File: `merkle.js`)

### Summary
`merkle.verifyMerkleProof(element, proof)` iterates strictly `proof.siblings.length` times, using an `index` value taken directly from attacker-supplied data with no bounds/type validation. Both `formula/evaluation.js` (`is_valid_merkle_proof`) and `definition.js` (`in merkle`, `case 'in merkle'` around lines 1004-1020) feed externally-controlled proof objects/strings into this function reachable from a single posted unit, AA trigger, or address definition.

### Finding Description
In `merkle.js`:
```
function verifyMerkleProof(element, proof){
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){ return false; }
}
``` [1](#0-0) 

`index` comes from `proof.index`, which in the `formula/evaluation.js:is_valid_merkle_proof` path can be an arbitrary object/wrapped value taken straight from the trigger data — `objProof = merkle.deserializeMerkleProof(proof)` for strings, or `objProof = proof.obj` when the caller passes a plain object [2](#0-1) . Post-fix (`bPostPemCurvesFix`) code only checks `Array.isArray(objProof.siblings)`, each sibling is a nonempty string, and caps `siblings.length <= 50` [3](#0-2) , but it never validates `objProof.index` is a number, is non-negative, or is consistent with `siblings.length` (i.e., that repeatedly halving `index` by the proof depth would ever legitimately reach the root). Similarly, `definition.js`'s `'in merkle'` branch deserializes `assocAuthentifiers[path]` (an attacker/unit-author supplied authentifier string) and calls `verifyMerkleProof` without validating `index` [4](#0-3) .

Because the loop bound is `proof.siblings.length` (already capped at 50 in the post-fix formula path, and implicitly bounded by string length via `deserializeMerkleProof`'s `split("-")` in the `in merkle` path), a classic unbounded infinite loop as in the Wireshark CVE is not directly reproducible in the formula path due to the length cap, but the `in merkle` path in `definition.js` has **no such cap on `siblings.length`**: `deserializeMerkleProof` simply splits the entire authentifier string on `-`, so an attacker who controls `assocAuthentifiers[path]` (i.e., the signature/authentifier data for their own address's `in merkle` condition) can supply an arbitrarily long dash-separated string, producing an arbitrarily large `siblings` array and hence an arbitrarily long (though still O(n)) SHA-256 hashing loop per validated unit — this is a large amplification/DoS primitive gated only by the overall unit size limit (`constants.MAX_UNIT_LENGTH`), not by any dedicated bound on proof depth, and the `index` type/value is never checked to be a sane small non-negative integer, so `index % 2` can behave unpredictably on a corrupted/oversized numeric-string value (e.g., leading zeros, non-numeric substrings coerced to `NaN`, extremely large numeric strings) without ever causing a validation error — it silently returns a hash mismatch (safe) or, in edge cases with type coercion quirks, could yield inconsistent results between nodes if `Math.floor(NaN/2)` propagates NaN through hashing consistently (deterministic across nodes, so not itself a consensus-fork bug, but demonstrates the missing integer-type/range validation called out in the CVE).

### Impact Explanation
The primary concrete impact is a per-unit CPU amplification via unbounded `siblings` array length in the `in merkle` address-definition authentifier path (no size cap unlike the formula path's 50-element cap), allowing a unit poster to force expensive repeated SHA-256 hashing during address/AA-trigger validation, degrading node validation throughput. This does not by itself cause double-spend, inflation, or fund loss, and does not appear to produce cross-node disagreement on validity (the computation is deterministic), so it falls short of the strictest "network unable to confirm new units" bar unless amplification is combined with many messages/authors in a single unit up to `MAX_UNIT_LENGTH`.

### Likelihood Explanation
Reachable by any unpriviledged unit poster who defines an address (or AA) using an `in merkle` condition and supplies a crafted authentifier string as the "proof" — no special privileges are needed, only a definition matching one's own address `chash`.

### Recommendation
In `merkle.js:verifyMerkleProof`, validate that `proof.index` is a finite non-negative integer and that `proof.siblings` is bounded (e.g., matching the same `<= 50` cap enforced in `formula/evaluation.js`) before entering the loop; apply the same explicit bound in `definition.js`'s `'in merkle'` handler when calling `merkle.deserializeMerkleProof`/`verifyMerkleProof` on `assocAuthentifiers[path]`, rejecting proofs whose `siblings.length` exceeds a small fixed maximum (e.g., 50, consistent with the formula-path fix) rather than relying solely on the overall unit-size limit.

### Proof of Concept
Not independently executed; based on static code reading. A concrete PoC would: (1) construct an address whose definition includes `["in merkle", [[oracleAddr], "feed_name", "elem"]]`; (2) as the address owner, submit a unit where the corresponding authentifier at that path is a string with several thousand dash-separated fake "siblings" segments (e.g., `"0-" + "AAAA-".repeat(5000) + "root"`), forcing `deserializeMerkleProof` to build a `siblings` array of thousands of entries and `verifyMerkleProof` to perform thousands of SHA-256 operations per validating node, before ultimately failing the proof check (since the root won't match) — repeatable across many authors/messages within `MAX_UNIT_LENGTH` to amplify CPU cost network-wide.

**Uncertainty note:** I could not fully confirm from static reading alone whether `MAX_UNIT_LENGTH`/message-count limits already bound the total achievable amplification to a level that is not "Medium/High" severity in practice, nor whether there is a separate depth/size check elsewhere in the authentifier-collection pipeline (`validateAuthentifiers`) that rejects oversized `assocAuthentifiers` values before reaching `definition.js`'s `'in merkle'` case. A Devin session with the full test suite and dynamic tracing would be needed to measure actual amplification bounds and confirm severity.
