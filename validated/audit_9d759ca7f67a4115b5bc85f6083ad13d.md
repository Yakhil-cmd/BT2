## Broken Binding

The code implicitly assumes:
`Team.find_or_create_by!(github_id: params.team.id).organization == params.organization.login` — but this is **never re-checked after creation**. [1](#0-0) 

### Title
`membership` webhook mutates a pre-existing `Team` by numeric `github_id` alone, with no organization re-validation, making cross-org team hijack deterministic and freely replayable — ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by the numeric `params.team.id`, setting `organization` only on the `create` branch (`find_or_create_by!` block). Once a `Team` with a given `github_id` exists (e.g., an authorized `Shipit.github_teams` team belonging to organization A), any subsequently *validly signed* `membership` "added" webhook that reuses that same `team.id` — regardless of which organization actually signed it — matches the existing record and calls `team.add_member(member)`, adding an attacker-controlled `member.login` to that team.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects the GitHub App config to verify against using `repository_owner`, which for `membership` events is taken straight from the attacker-controlled payload field `organization.login` [2](#0-1) . In a multi-org Shipit deployment (a documented, supported configuration, see `docs/setup.md`'s "Using Multiple Github Applications" section), each organization has its own `webhook_secret`, and `Shipit.github(organization:)` picks the config keyed by the org named in the payload [3](#0-2) . This means an attacker who legitimately controls **their own** configured org (org B) can sign a fully valid `membership` "added" webhook — no compromise of org A's secrets is needed.

The root cause is that `find_or_create_team!` binds solely on `github_id`, never re-checking `organization` for already-existing records:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [1](#0-0) 

If org B's attacker crafts a payload with `team.id` equal to org A's authorized team's numeric GitHub ID (team IDs are visible/guessable via GitHub's public API) and `member.login` equal to their own controlled account, the lookup returns org A's existing `Team` record, and `team.add_member(member)` is invoked [4](#0-3) . If that team is one of `Shipit.github_teams`, `User#authorized?` becomes `true` for the attacker's account [5](#0-4) .

Regarding replayability: `Team#add_member` already guards against duplicate `Membership` rows via `members.append(member) unless members.include?(member)` [4](#0-3) , backed by `Membership`'s `validates :user_id, uniqueness: { scope: :team_id }` [6](#0-5) . There is no nonce, timestamp, or single-use enforcement anywhere in `WebhooksController` or `MembershipHandler` — the same signed payload can be resent at any time. If an operator manually deletes the malicious `Membership` as remediation, the attacker can resend the identical, still-validly-signed payload (from either org) to recreate it, since neither `find_or_create_team!` nor `team.add_member` depend on request freshness. `Membership.count` increases by exactly 1 the first time and stays flat on replay (idempotent at the DB level), while authorization access is granted/re-granted deterministically regardless of which org's secret signed the specific request.

None of the existing guards intervene: `verify_signature` only proves the payload was signed by *some* org's configured secret, not that the org matches the team being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not organization ownership of the numeric `team.id`; there is no `force_github_authentication`/`require_permission!` check in the webhook path since it's a machine-to-machine endpoint by design.

### Impact Explanation
An attacker with legitimate credentials for **any one** org configured in a multi-org Shipit deployment can grant themselves membership in **another org's** `Shipit.github_teams`-authorized team, which `User#authorized?` [5](#0-4)  treats as sufficient for full application access (deploys, rollbacks, merges). This is a cross-tenant authorization bypass — a payload signed for organization B mutates organization A's team/authorization state — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The action is fully repeatable/deterministic: resending the same payload re-establishes access after manual revocation, with `Membership` uniqueness only preventing duplicate rows, not re-authorization.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (a documented, supported setup, not the default single-org mode), (2) the attacker controls one such configured org's GitHub App/webhook_secret (achievable simply by being a legitimate tenant/customer of a shared Shipit instance — no secret theft needed), and (3) knowledge of the target team's numeric `github_id` (discoverable via GitHub's public team API for public orgs, or brute-forceable given small ID ranges). No GitHub App private key, session, or `api_clients_secret` is needed. In a single-org deployment this specific escalation is not reachable, since there is only one webhook_secret and no organization-to-org routing ambiguity.

### Recommendation
In `find_or_create_team!`, always verify that the resolved `Team#organization` matches `params.organization.login` for both new and pre-existing records, and raise/drop the event on mismatch instead of silently reusing the record:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
  raise ArgumentError, "Team/organization mismatch" unless team.organization == params.organization.login
  team
end
```
Additionally, consider scoping the `Team` lookup by `github_id` **and** `organization` together, rather than `github_id` alone.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition, multi-org fixture)
test "membership webhook from org B cannot hijack org A's team by github_id, and replay is idempotent" do
  team = shipit_teams(:org_a_authorized_team) # github_id: 999, organization: 'org-a'
  payload = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'org-b' }, # attacker-controlled org, distinct signing key
    member: { login: 'attacker' }
  }.to_json

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = sign_with_org_b_secret(payload)

  assert_difference -> { Membership.count }, 1 do
    post :create, body: payload, as: :json
  end
  assert team.reload.members.map(&:login).include?('attacker')

  # Replay identical payload/signature: deterministic, idempotent re-grant
  assert_no_difference -> { Membership.count } do
    post :create, body: payload, as: :json
  end
  assert team.reload.members.map(&:login).include?('attacker') # access persists/re-confirmed
end
```
This demonstrates that `team.organization` ('org-a') never matches the signing organization ('org-b') on either request, yet the `Membership` is created once and access remains deterministically granted on replay — confirming the binding break is repeatable and organization-independent.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
