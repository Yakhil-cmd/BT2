### Title
Webhook signature verification binds to the outer `organization`/`repository.owner.login`, while status/push handlers act on arbitrary commits and stacks named elsewhere in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification purely from `repository.owner.login` (falling back to `organization.login`), while the handlers that actually act on the payload resolve their target using a completely different field (`repository.full_name`, or in the case of status events, no repository scoping at all — just a global `sha` lookup). Because Shipit explicitly supports multi-organization deployments where `webhook_secret` is documented as optional per-org, and because `verify_webhook_signature` returns `true` unconditionally when no secret is configured for the selected org, an attacker who names an unprotected/no-secret organization in `repository.owner.login` can pass signature verification while acting on any other repository or commit named elsewhere in the same JSON body.

### Finding Description
`verify_signature` picks the GitHub App config to validate against using only: [1](#0-0) 
and validates the signature against that org's `webhook_secret` via: [2](#0-1) 

`verify_webhook_signature` explicitly bypasses verification entirely when no secret is configured for the resolved organization: [3](#0-2) 

Multi-org Shipit deployments are a documented, supported configuration where `webhook_secret` is optional per org: [4](#0-3) [5](#0-4) 

Once past `verify_signature`, event handlers resolve their real target from a different payload field, `repository.full_name`, entirely independent of the field used for authentication: [6](#0-5) 

`PushHandler` uses that mismatch-prone `stacks` helper to trigger a GitHub sync of any matched stack's branch: [7](#0-6) 

`StatusHandler` is worse: it does not even scope by repository — it matches purely on commit SHA across the entire Shipit instance and writes an attacker-controlled commit status (`state`, `description`, `target_url`, `context`) onto any commit with that SHA: [8](#0-7) 

The binding that should hold is: *organization whose `webhook_secret` authenticated the request* == *organization/repository the handler subsequently writes to*. Because the outer envelope field used for authentication (`repository.owner.login` / `organization.login`) is disjoint from the field used to select the write target (`repository.full_name`, or nothing at all for status events), this equality is not enforced anywhere in the request path.

### Impact Explanation
An attacker who can name, in `repository.owner.login`/`organization.login`, any organization configured on the Shipit instance without a `webhook_secret` (a supported, documented configuration) obtains a free pass through `verify_signature` for the entire request body. They can then set `repository.full_name` (push/check_suite events) to any other tracked repository, or simply reuse a known/guessable commit SHA (status events) belonging to a *different*, secret-protected organization's stack, and:
- Forge a passing/failing `status` on any commit, which can subvert `ci.require` gating and enable an unauthorized deploy of unreviewed code, or
- Force `GithubSyncJob`/`sync_github` runs against arbitrary tracked stacks.

This crosses an authentication boundary between organizations that is supposed to isolate tenants from one another, and can lead to an unauthorized deploy via forged CI status — matching the Critical impact bar ("an unauthorized deploy") for this engine.

### Likelihood Explanation
Requires only that the Shipit instance (a) is configured for more than one GitHub organization (a documented/supported feature) and (b) leaves `webhook_secret` unset for at least one of them (also documented as "optional"). No GitHub App credentials, `ApiClient` token, or session are needed — only knowledge of the org's login name (public) and the target repository's full name/commit SHA (also generally public/observable). This is a realistic misconfiguration, not a purely theoretical one, given the docs explicitly present `webhook_secret` as optional.

### Recommendation
Bind signature verification and the acted-upon target to the same trust domain: after resolving `repository_owner`, require that any `repository.full_name` (or commit lookup) processed by a handler actually belongs to that same verified organization, and reject events whose internal repository/organization references don't match the one that authenticated the request. Additionally, `StatusHandler` should scope `Commit.where(sha:)` lookups by repository/stack derived from the verified organization rather than a global SHA match.

### Proof of Concept
1. Configure Shipit (per documented multi-org support) with:
   - `orgA` (attacker-known name) — no `webhook_secret` set.
   - `orgB/victim-repo` — has `webhook_secret` set and is deployed via Shipit, with `ci.require` gating deploys on a status context.
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<known sha of a commit on orgB/victim-repo awaiting CI>",
     "state": "success",
     "context": "required-ci-check",
     "repository": { "owner": { "login": "orgA" } }
   }
   ```
3. POST to `/webhooks` with header `X-Github-Event: status` and any `X-Hub-Signature` value (or omit it).
4. `verify_signature` resolves `repository_owner` = `"orgA"`, calls `Shipit.github(organization: "orgA").verify_webhook_signature(...)`, which returns `true` unconditionally because `orgA` has no `webhook_secret` (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` — finds the `orgB/victim-repo` commit and writes the forged `success` status (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), satisfying `ci.require` and enabling an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
