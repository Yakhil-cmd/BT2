### Title
Improper validation of `feed_name`/`feed_value` in oscript `data_feed()`/`in_data_feed()` allows key-injection into the data-feeds key-value store - (File: formula/validation.js)

### Summary
The restforce advisory (CVE-2018-3777) is a case of untrusted, unsanitized input being spliced into a structured request (URL path) without checking for the delimiter/format characters that separate logical fields, letting an attacker smuggle extra path/query segments and redirect the request. ocore's oscript `data_feed()`/`in_data_feed()` formula functions build lexicographic, `\n`-delimited keys for the LevelDB/RocksDB "data feeds" store directly from formula-evaluated strings (`feed_name`, `feed_value`) that are only checked for non-emptiness, not for embedded `\n` delimiter characters, unlike the equivalent literal-message validation elsewhere in the codebase.

### Finding Description
Whenever a `data_feed` message is posted directly as a unit payload, the validators explicitly reject `feed_name`/value strings that contain a newline: [1](#0-0) [2](#0-1) 

However, when the *same* `feed_name`/`feed_value` parameters are supplied to the oscript formula operators `data_feed(...)` and `in_data_feed(...)` (used inside AA definitions to query oracle-posted data), the corresponding validators only check that the string is non-empty (`value.trim() === ''`) — they never check for `\n`: [3](#0-2) [4](#0-3) 

At AA-trigger execution time, the evaluated formula parameters are only type-checked (`isValidValue` — string/number/boolean), with no content restriction: [5](#0-4) [6](#0-5) 

These attacker-influenced `feed_name`/`value` strings are then concatenated, unescaped, directly into `\n`-delimited lookup keys for the KV data-feed index: [7](#0-6) [8](#0-7) 

The key format is `df\n<address>\n<feed_name>\n<type>\n<value>\n<mci>` (and `dfv\n<address>\n<feed_name>\n<mci>`), where `\n` is the field separator relied on by `options.gte/lte/gt/lt` range scans (`dataFeedByAddressExists`, `readDataFeedByAddress`) and by `string_utils.getMciFromDataFeedKey`/`getValueFromDataFeedKey`, which split on `\n` and expect a fixed number of parts: [9](#0-8) 

Because `feed_name` (and `value`, when used as a string) is not sanitized against embedded `\n` in the oscript-formula path, an AA author who builds `feed_name`/`feed_value` from trigger data supplied by an unprivileged trigger sender (a very common oracle-consumption pattern, e.g. `data_feed[oracles=..., feed_name=$id, feed_value=$outcome]`) can be handed a crafted string containing extra `\n`-delimited segments. This corrupts the field boundaries the range-scan logic assumes, letting the constructed `key_prefix`/`gte`/`lte`/`gt`/`lt` bounds unintentionally overlap adjacent, unrelated keys already present in the KV store (e.g., a different `feed_name`, a different `type` field, or a different `mci`-encoded suffix that the real oracle posted for something else). This is the direct analog of the restforce bug: an unsanitized user-controlled string is spliced into a structured "path" (here, the KV key), and the missing check for the separator character lets the attacker manipulate which underlying record the query actually resolves against, contrary to the querying AA's intent.

### Impact Explanation
An AA that resolves a decision (e.g., paying out escrow, settling a bet/prediction market, releasing collateral) via `data_feed()`/`in_data_feed()` with a trigger-sender-controlled `feed_name` or `feed_value` component can be tricked into matching a record the oracle never posted for that logical name/value, because the `\n` boundary between `feed_name`/`value`/`type`/`mci` fields can be shifted by the attacker. Depending on the concrete AA logic, this can cause the AA to believe an oracle attested to something it did not, leading to unauthorized fund release from the AA (AA fund loss) or a wrong branch being taken that a legitimate trigger sender should not have been able to force. Because a single posted AA trigger unit (attacker-controlled, no special privilege required) is enough to reach this code path during normal unit validation/AA execution, this satisfies the "concrete AA fund loss" bar.

### Likelihood Explanation
The likelihood is dependent on how a specific AA constructs `feed_name`/`feed_value` — it requires that an AA definition passes attacker-influenced trigger data into these formula parameters without its own additional sanitization (a routine and encouraged pattern for oracle/id-lookup based AAs, since the AA-definition validator itself performs no `\n` check and thus doesn't warn AA authors of the risk). This is a moderate-likelihood, definition-dependent issue rather than a universal one, but the root cause (missing validation identical to a check present elsewhere in the same codebase for the non-formula code path) is a genuine, provable gap in `formula/validation.js`.

### Recommendation
Add the same `\n`-content checks used in `validation.js`/`aa_validation.js` for direct `data_feed` messages to `validateDataFeed()` and `validateDataFeedExists()` in `formula/validation.js` for the `feed_name` and `feed_value` (string) parameters, and additionally enforce `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH` limits there, or reject any evaluated string value containing `\n` before it is used to build KV-store keys in `data_feeds.js` (`dataFeedByAddressExists`, `readDataFeedByAddress`, `dataFeedExists`, `readDataFeedValueByParams`) as a defense-in-depth check at the data layer itself.

### Proof of Concept
1. Deploy an AA whose oscript definition includes a data-feed lookup keyed by trigger data, e.g.:
   `{ if: $r = data_feed[oracles="ORACLE_ADDRESS", feed_name=trigger.data.id, feed_value=trigger.data.outcome] ... }`
   This passes `aa_validation.js`/`formula/validation.js` checks because `feed_name`/`feed_value` are formulas (not literals), so `validateDataFeed`/`validateDataFeedExists` only verify non-emptiness, never `\n` content. [10](#0-9) 
2. Have the oracle post an unrelated but real data feed, e.g. `feed_name="game42_win"`, value `"yes"`, stored as key `df\nORACLE\ngame42_win\ns\nyes\n<mci>`. [11](#0-10) 
3. As the trigger sender, submit `trigger.data.id = "gameX\ns\nyes"` (embedding the delimiter sequence the store uses for a string value), and `trigger.data.outcome` crafted so the resulting `key_prefix`/range-scan bounds computed in `dataFeedByAddressExists`/`readDataFeedByAddress` unintentionally overlap the already-posted `game42_win` key. [12](#0-11) 
4. The AA's `data_feed()`/`in_data_feed()` call resolves against the oracle's unrelated `game42_win` record instead of failing (as it should for a feed_name the oracle never posted), because the query boundary was corrupted by the unescaped `\n` in the attacker-supplied string. This is analogous to how restforce's unsanitized ID let `0016000000MRatd/describe` redirect a `select()` call to a different endpoint than intended.

**Note on verification depth:** I was not able to execute this AA/trigger scenario against a live node to confirm which exact adjacent record would be matched for a given crafted string (the exact overlap depends on precise byte-ordering of `options.gte/gt/lt` computed from `key_prefix`), so the concrete exploitability for a *specific* AA/oracle pairing is not fully proven end-to-end — only the root-cause validation gap (`formula/validation.js` lacking the `\n` check present in `validation.js`/`aa_validation.js`) is concretely confirmed by direct code comparison.

				case 'ifnone':
					break;

					break;

		}

	}

function encodeMci(mci){
	return (0xFFFFFFFF - mci).toString(16).padStart(8, '0'); // reverse order for more efficient sorting as we always need the latest
}

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}

// df:address:feed_name:type:value:strReversedMci
function getValueFromDataFeedKey(key){
	var m = key.split('\n');
	if (m.length !== 6)
		throw Error("wrong number of elements in data feed "+key);
	var type = m[3];
	var value = m[4];
	return (type === 's') ? value : decodeLexicographicToDouble(value);
}
