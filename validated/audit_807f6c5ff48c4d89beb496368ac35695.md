### Title
`handleERC20Transfer` Accepts Unregistered Token Addresses Without Validation, Allowing a Single Operator to Drain or Mint Arbitrary ERC20 Tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.handleERC20Transfer()` accepts a caller-supplied `_tokenAddress` without the `onlyRegisteredToken` or `onlyUnlockedToken` modifiers that guard the outbound path (`_requestERC20Transfer`). Because the default operator threshold is **1**, a single bridge operator can immediately execute a handle call with any arbitrary ERC20 address, causing the bridge to either mint tokens from an unregistered contract (mintBurn mode) or transfer any ERC20 it holds to an arbitrary recipient (lock mode).

---

### Finding Description

`_requestERC20Transfer` (the outbound/deposit path) is decorated with both `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)`: [1](#0-0) 

`handleERC20Transfer` (the inbound/withdrawal path) carries only `onlyOperators` and performs no token-address validation before executing the asset movement: [2](#0-1) 

The asset movement at the end of `handleERC20Transfer` is:

```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
```

`BridgeOperator` initialises every vote-type threshold to **1** in its constructor: [3](#0-2) 

With threshold = 1, `_voteValueTransfer` returns `true` on the very first call from any registered operator, so no second operator is needed: [4](#0-3) 

The vote key is `keccak256(msg.data)`, which encodes the full calldata including `_tokenAddress`. A single operator can therefore supply any address they choose and the vote passes immediately.

---

### Impact Explanation

**mintBurn mode** — the operator calls `handleERC20Transfer` with an arbitrary `ERC20Mintable` contract address. The bridge calls `.mint(_to, _value)` on that contract. If the bridge holds minter rights on any token (which is the normal setup for wrapped/bridged tokens), the operator can mint an unbounded supply to any address, inflating the token supply and stealing value.

**lock mode** — the operator calls `handleERC20Transfer` with the address of any ERC20 token the bridge contract holds (e.g., accumulated fees, liquidity, or any token accidentally sent to the bridge). The bridge calls `safeTransfer(_to, _value)`, draining those tokens to an attacker-controlled address.

Both paths constitute an **unauthorized transfer or mint of bridged assets** — a protected-state impact within the allowed scope.

---

### Likelihood Explanation

The default threshold is 1, so no collusion is required. Any single registered bridge operator can trigger this unilaterally. Bridge operators are semi-trusted relayers; a compromised or malicious operator key is a realistic threat model for a bridge system. The asymmetry between the guarded outbound path and the unguarded inbound path makes this easy to miss and easy to exploit.

---

### Recommendation

Add `onlyRegisteredToken(_tokenAddress)` and `onlyUnlockedToken(_tokenAddress)` to `handleERC20Transfer`, mirroring the guards already present on `_requestERC20Transfer`:

```solidity
function handleERC20Transfer(
    bytes32 _requestTxHash,
    address _from,
    address _to,
    address _tokenAddress,
    uint256 _value,
    uint64 _requestedNonce,
    uint64 _requestedBlockNumber,
    bytes memory _extraData
)
    public
    onlyOperators
    onlyRegisteredToken(_tokenAddress)   // ADD
    onlyUnlockedToken(_tokenAddress)     // ADD
{
    ...
}
```

Apply the same fix to `handleERC721Transfer` in `BridgeTransferERC721.sol`, which has the identical omission.

---

### Proof of Concept

1. Deploy `Bridge` with `modeMintBurn = true`. The deployer is automatically the sole operator with threshold = 1.
2. Register a legitimate token pair (e.g., `tokenA → ctokenA`).
3. As the operator, call:
   ```
   bridge.handleERC20Transfer(
       txHash,
       attacker,          // _from (irrelevant)
       attacker,          // _to   (recipient)
       arbitraryToken,    // _tokenAddress — NOT in registeredTokens
       1_000_000e18,      // _value
       0,                 // _requestedNonce
       1,                 // _requestedBlockNumber
       ""
   )
   ```
4. Because threshold = 1, `_voteValueTransfer` returns `true` immediately.
5. The bridge calls `ERC20Mintable(arbitraryToken).mint(attacker, 1_000_000e18)`.
6. If the bridge is a minter on `arbitraryToken`, 1 000 000 tokens are minted to the attacker with no corresponding deposit on the counterpart chain.

The `onlyRegisteredToken` modifier defined in `BridgeTokens.sol` would have blocked step 5: [5](#0-4)
