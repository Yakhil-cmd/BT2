### Title
PR label names bypass DeploySpec env allow-list and reach `PTY.spawn` unfiltered - ([File: lib/shipit/task_commands.rb])

### Summary
`Shipit::ReviewStack#env` injects attacker-controlled, PR-label-derived keys (e.g. `BUNDLE_GEMFILE`, or `PATH`) into the environment hash with a fixed `"true"` value. `TaskCommands#env`/`StackCommands#env` merge `@stack.env` unconditionally, never passing it through `DeploySpec#filter_deploy_envs`/`filter_task_envs`/`EnvironmentVariables#permit`, so the deploy_spec's `env_variables` allow-list (backed by `Shipit::VariableDefinition`) only constrains explicitly-submitted task/deploy `env` params, not the label-derived keys baked into `Stack#env`.

### Finding Description
The claimed binding is: *the set of keys in `Command#unbundled_env` == the set of variables permitted by `deploy_spec.machine_env` + `VariableDefinition` allow-lists (`deploy_variables`/`rollback_variables`/task `variables`)*. Tracing the code shows this binding is false whenever a stack is a `ReviewStack`.

- `Shipit::ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `super` (base `Stack#env`, `app/models/shipit/stack.rb:54-63`) with a hash built from `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }`. Any label name becomes an env var key with value `"true"`. [1](#0-0) 

- Labels are captured from GitHub webhook payloads with no allow-list on label text: `LabelCapturingHandler#capture_labels` does `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [2](#0-1) 

- `TaskCommands#env` unconditionally merges `@stack.env` with no call to `deploy_spec.filter_task_envs`/`filter_deploy_envs`: `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`. Only `@task.env` (the very last merge) has ever been through the allow-list, applied earlier in `Stack#trigger_deploy`/`Stack#trigger_task` (`app/models/shipit/stack.rb:139-172`, `deploy.rb:64` `delegate :filter_deploy_envs, to: :stack`), via `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`), which only sanitizes the caller-supplied `env` argument, not `@stack.env`. [3](#0-2) [4](#0-3) [5](#0-4) 

- The merged env flows into `Command#env`, then `Command#unbundled_env` = `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`, and directly into `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`. [6](#0-5) [7](#0-6) 

Root cause: the allow-list (`VariableDefinition`/`EnvironmentVariables.permit`) is applied only at the point where a *caller* (API/UI) supplies an `env:` argument to `trigger_deploy`/`trigger_task`/`build_rollback`. It is never applied to `Stack#env`/`ReviewStack#env`, which is merged directly and last-but-one in `TaskCommands#env` (only `@task.env` comes after it). Because `@stack.env` merge happens before `deploy_spec.machine_env` and is never routed through `filter_deploy_envs`, any label name the attacker chooses becomes a literal environment variable name delivered to `PTY.spawn`, including names that collide with security/behavior-critical variables such as `PATH`, `BUNDLE_GEMFILE`, `GIT_SSH`, `RUBYOPT`, etc. Existing tests in the repo (`test/lib/shipit/task_commands_test.rb`, `test/lib/shipit/deploy_commands_test.rb`, `test/models/shipit/review_stack_test.rb`) already assert that arbitrary PR labels ("wip", "bug") pass straight through into `TaskCommands#env`/`DeployCommands#env`, confirming this is not filtered by any allow-list check. [8](#0-7) [9](#0-8) 

Existing guards checked and found insufficient/orthogonal:
- `deploys_controller`/`api/deploys_controller` do filter user-submitted `env` params via `filter_deploy_envs` (confirmed by `test/controllers/deploys_controller_test.rb:72-76` and `test/controllers/api/deploys_controller_test.rb:42-47`), but this only protects the explicit `env:` HTTP param, not `Stack#env`. [10](#0-9) 
- Webhook signature verification (`verify_signature`) gates whether the webhook is accepted at all, but does not restrict label *content* once a legitimately-signed webhook (from GitHub, triggered by the PR author labeling their own PR) is processed by `LabelCapturingHandler`.
- `ExplicitParameters` schema on the webhook (`requires :labels, Array do requires :name, String end`) validates shape only, not content — any string is a valid label name.

### Impact Explanation
Any user able to label a pull request against a repository with review-stacks enabled (an action available to repository collaborators/triggerable via a legitimately signed GitHub webhook) can inject an arbitrary-named environment variable (fixed value `"true"`) into every task and deploy command executed for that review stack, completely bypassing the deploy_spec's `env_variables` allow-list. This is a Critical impact per the scoped criteria: attacker-controlled data reaches `Command`/`PTY.spawn` execution environment for a repository's stack, and because the attacker chooses the variable **name**, they can target security-relevant variables (e.g., overriding `PATH`, `BUNDLE_GEMFILE`, `GIT_SSH`, `RUBYOPT`) that influence what binaries/config get loaded during deploy step execution — an allow-list bypass enabling execution-environment tampering on the deploy host. This is repeatable per-label per-PR and scoped to whichever stack/repository the PR belongs to (not cross-tenant by itself, but affects every deploy/task run against that review stack until the label is removed).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with dynamic PR-based stacks (a documented, common configuration — see `docs/review_stacks.md`), and the PR must be open and tracked as a `ReviewStack`. Labeling an open PR typically requires write access to the repo (not a pure external-fork attacker), but the audit's stated attacker model explicitly grants "label their own PR" as an available unprivileged action. No secrets, tokens, or elevated Shipit roles are required — only a correctly signed GitHub webhook event, which GitHub sends automatically whenever the label action occurs. This makes the exploit trivially repeatable by anyone who can add a label.

### Recommendation
Route `Stack#env`/`ReviewStack#env` (or at minimum the PR-label-derived portion) through the deploy_spec's env allow-list (`filter_deploy_envs`/`filter_task_envs`/`EnvironmentVariables.permit`) before merging into `TaskCommands#env`/`StackCommands#env`, or namespace label-derived variables under a prefix (e.g., `LABEL_<NAME>`) that cannot collide with security-sensitive variable names, and explicitly exclude reserved names such as `PATH`, `BUNDLE_GEMFILE`, `GIT_SSH`, `RUBYOPT` from ever being settable via labels regardless of allow-list configuration.

### Proof of Concept
minitest plan (`test/lib/shipit/task_commands_test.rb` style, adapted to assert the bypass):
```ruby
test "#env leaks PR labels even when deploy_spec restricts env_variables" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bundle_gemfile"]

  # deploy_spec configured with a restrictive allow-list that does NOT include BUNDLE_GEMFILE
  deploy_spec = Shipit::DeploySpec.new(
    'env' => { 'variables' => [{ 'name' => 'SAFE_VAR' }] }
  )
  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  commands = Shipit::TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(deploy_spec)

  env = commands.env

  # Binding claim: BUNDLE_GEMFILE should NOT be in env because it is not in deploy_spec's allow-list
  assert_not_includes deploy_spec.deploy_variables.map(&:name), "BUNDLE_GEMFILE"
  # Actual behavior: it leaks through anyway
  assert_equal "true", env["BUNDLE_GEMFILE"]
end
```
This demonstrates that `deploy_spec.deploy_variables` (the allow-list) excludes `BUNDLE_GEMFILE`, yet `TaskCommands#env["BUNDLE_GEMFILE"]` is present with value `"true"`, proving the divergence and that it reaches the merged environment ultimately passed to `Command#unbundled_env`/`PTY.spawn`.
