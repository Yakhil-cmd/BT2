### Title
Fallthrough after failed hash calculation causes double-processing / premature cleanup of an unhandled private payment - ([File: network.js])

### Summary
In `handleSavedPrivatePayments()`, the inner `validateAndSave` closure computes a canonical hash of an attacker-supplied private-payment payload inside a `try/catch`. When the hash computation throws, the `catch` block starts cleanup (deleting the row and invoking the `async.each` item callback `cb`) but does **not** `return`, so execution falls through and the same (already being cleaned up) `arrPrivateElements` is passed into `privatePayment.validateAndSavePrivatePaymentChain(...)`, which will independently invoke `cb` again through one of its own callbacks. This mirrors the reported bug class (an error-cleanup path that keeps operating on data it has already started to tear down), reachable by any private-payment counterparty who sends a malformed/private chain payload.

### Finding Description
`handleSavedPrivatePayments()` iterates over rows previously queued by `handleOnlinePrivatePayment()` (populated straight from network input sent by a private-payment counterparty/device, see `network.js` `handleOnlinePrivatePayment`, `savePrivatePayment`). For each row it defines: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

`deleteHandledPrivateChain` deletes the row from `unhandled_private_payments` and, once the DB delete completes, invokes `cb()` (the `async.each` completion for this item): [2](#0-1) 

There is no `return` after the `catch` block, so once `getBase64Hash` throws (attacker-controlled `objHeadPrivateElement.payload` deserialized straight from `row.json`, itself derived from a peer/device-supplied `private_payment`/`private_payment_chains` message, see `network.js` `handleOnlinePrivatePayment` at lines 2376-2441 and `wallet.js` `handlePrivatePaymentChains`), execution unconditionally continues to build `key` (with `json_payload_hash === undefined`) and to call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same element that just failed canonicalization and whose backing row is concurrently being deleted: [3](#0-2) 

That downstream call will, on its own `ifOk`/`ifError`/`ifWaitingForChain` branch, call `deleteHandledPrivateChain(...)` (or `cb()` directly for `ifWaitingForChain`) a second time, so the same `async.each` iteration's `cb` is invoked twice — once from the `catch` block, once from the subsequent full validate-and-save pipeline that runs regardless of the earlier failure. This is the JS analog of “the error/cleanup path continues to operate on data that a preceding cleanup step already started to release”: `deleteHandledPrivateChain` deletes the DB row (the “free”) while the `try` block’s continuation still proceeds to run `indivisible_asset.js`/`divisible_asset.js` validation and *insertion* (`INSERT ... INTO inputs/outputs`, see `validateAndSavePrivatePaymentChain` in `indivisible_asset.js` lines 239-297) against a payload that has already been judged unhashable/invalid and whose queue entry no longer exists.

### Impact Explanation
- Calling the `async.each` item callback twice is undefined behavior for the `async` library and can corrupt the iteration state of `handleSavedPrivatePayments`, causing the final callback (which emits `new_my_transactions` and unlocks the `saved_private` mutex) to fire early/twice or to hang, depending on library version semantics.
- More importantly, a payload that fails canonical hashing is, by construction, not verifiable against the `payload_hash` stored for the corresponding on-chain message, yet it is still fed into `validateAndSavePrivatePaymentChain`, which will attempt real DB writes (`inputs`/`outputs` tables) for hidden/private outputs. Depending on what made `getBase64Hash` throw (e.g., a specially crafted nested value in an otherwise well-formed JSON payload), this can let a private-payment counterparty push a chain into the write pipeline that the normal validation path was never meant to reach in this state, risking inconsistent/duplicate private-output bookkeeping (double-processing of the same private chain) on the recipient wallet.
- Reachable by any device that can send a `private_payment` message to a wallet/light client (no special privileges beyond being a payment counterparty), satisfying the "AA fund loss/freezing or node disagreement"-class bar via corrupted private-payment state on the receiving wallet.

### Likelihood Explanation
Triggering requires only sending a private-payment chain whose head element’s `payload` cannot be canonically hashed by `objectHash.getBase64Hash` — an unprivileged private-payment counterparty fully controls this payload's shape via `handlePrivatePaymentChains` (`wallet.js`) or `handleOnlinePrivatePayment` (`network.js`), both of which only apply generic shape checks (`isNonemptyObject`, `isNonemptyArray`, etc.) before the payload is queued into `unhandled_private_payments` and later replayed through this exact code path. I could not fully verify from the indexed code which specific payload shapes cause `object_hash.js`'s underlying `getSourceString`/`getJsonSourceString` to throw (the function bodies were not returned by search), so likelihood of finding a concrete throwing input is plausible but not proven with certainty from the available index.

### Recommendation
Add a `return` (or restructure with an `if/else`) after the `catch` block in `validateAndSave` so that once `deleteHandledPrivateChain` is invoked (and `cb` scheduled), execution does not fall through to call `privatePayment.validateAndSavePrivatePaymentChain` again on the same, already-being-removed element. E.g.:
```
catch (e) {
    ...
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```

### Proof of Concept
Could not be fully constructed/verified against real code because the exact input that makes `objectHash.getBase64Hash` throw for a `payload` object could not be confirmed from the indexed contents of `object_hash.js`/`string_utils.js` (the function bodies were not retrievable via search in this session). Conceptually: a private-payment counterparty sends (via wallet hub or direct P2P `private_payment`) a chain whose head element's `payload` contains a value that `object_hash.getSourceString`/`getJsonSourceString` rejects (thrown, not just returning a mismatched hash) after it has already passed the coarse `isNonemptyObject`/`isNonemptyArray` checks in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`. Once queued into `unhandled_private_payments`, the next invocation of `handleSavedPrivatePayments()` hits the fallthrough bug described above.
