### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire database, with no scoping to the repository that authenticated the webhook. `WebhooksController#verify_signature` only checks that the webhook is validly signed for the organization named in the payload's own `repository.owner.login`, not that the `sha` inside the payload actually belongs to that repository. An attacker who owns a GitHub repository (and can therefore emit legitimately signed webhooks for it) can name a `sha` shared with a victim stack (e.g. via a fork with common history) and flip that commit's CI status on the victim stack.

### Finding Description
The broken binding: the code implicitly assumes `commit.stack.repository == payload.repository`, but nothing enforces this equality.

- `WebhooksController#verify_signature` derives `repository_owner` from the attacker-controlled `params.dig('repository', 'owner', 'login')` and verifies the HMAC signature against `Shipit.github(organization: repository_owner)`'s webhook secret [1](#0-0) . This only proves the payload was signed for *that* organization/app installation — it says nothing about which repository's commit the `sha` field refers to.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) , with no filter on `stack_id` or repository — every `Commit` row in the database matching that SHA (across all stacks/repos) gets the status applied.
- Compare with the base `Handler` class, which *does* provide repo scoping (`stacks` scoped from `Repository.from_github_repo_name(repository_name)`) [3](#0-2) , but `StatusHandler` does not use it — it bypasses that scoping entirely.
- `Commit#create_status_from_github!` writes the status and, via `add_status`, calls `stack.schedule_merges` when the new status becomes `pending?` or `success?` [4](#0-3) . On a stack with `merge_queue_enabled` true, a green head advances the merge queue, ultimately triggering `merge!`/deploy logic in `Stack`/`MergeRequest`.

Exploit flow: attacker registers/owns a GitHub repo, forks or otherwise obtains a commit SHA that is also present in a victim stack (e.g., by forking the victim's public repo — a common commit exists in both histories, or the SHA is guessable/observable since commits/SHAs are often public). Attacker sends a `status` webhook for `context: ci/circleci`, `state: success`, `sha: <shared sha>` to `POST /webhooks`, signed with their own app's webhook secret (which they legitimately possess for their own installation). `verify_signature` passes because it only checks the organization tied to the *attacker's* `repository.owner.login` in the payload, not the SHA ownership. `StatusHandler` then updates **every** `Commit` row across the database with that SHA — including the one belonging to the victim's stack — flipping its CI state and potentially advancing/blocking the victim's merge queue and deploys.

Existing guards fail because: `verify_signature` validates the *organization* named in the payload, not the *commit's true owning repository*; `ExplicitParameters` schema only validates types, not repo scoping; and `StatusHandler` deliberately omits the `stacks`/`repository_name` scoping that the base `Handler` class provides for other handlers (e.g., `PushHandler`).

### Impact Explanation
A payload authenticated for one repository (attacker's own) mutates commit/CI state belonging to another repository/stack that never authenticated it — this is the "payload for one repository mutating another's stack/commit" category. On a stack with `merge_queue_enabled`, this can force a merge (`merge!`) or block a legitimate merge/deploy, i.e., unauthorized merge/deploy of attacker-influenced state. Blast radius spans any tenant/stack whose commit history intersects (or is fabricated to intersect) with the attacker's own repo — repeatable per SHA collision, one HTTP request per attempt, no privileges required beyond owning any GitHub repo with an app/webhook installed.

### Likelihood Explanation
Preconditions: attacker needs a repository they control with a webhook/app installation issuing a valid signature (something any GitHub user with a webhook or the public GitHub App installed on their own repo can obtain), and a SHA that also exists as a `Commit` row for the victim's stack (most straightforwardly achieved by forking the victim repository, which shares commit history/SHAs, or by any coincidental/engineered SHA overlap). Victim stack must have `merge_queue_enabled: true` and use `ci/circleci` as a required/blocking status context for the "ship" amplification, though the core cross-repo write (flipping CI status on someone else's commit) is possible regardless of merge-queue settings. Attacker cost is a single unauthenticated `POST /webhooks` request; the flaw is deterministic and repeatable against any repository sharing a SHA with the attacker's own.

### Recommendation
In `StatusHandler#process`, scope commit lookup to the repository that authenticated the webhook (mirroring `Handler#stacks`/`repository_name`), e.g. restrict to `Commit.joins(:stack).merge(Stack.where(repository: Repository.from_github_repo_name(payload.dig('repository','full_name')))).where(sha: params.sha)` instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, conceptually — actual location may vary):
1. Create `attacker_repo` (owned by attacker org) and `victim_repo`/`victim_stack` with `merge_queue_enabled: true` and `ci/circleci` as a required status.
2. Create a `Commit` on `victim_stack` with `sha: "deadbeef...".freeze` and no successful status (state currently pending/unknown).
3. Assert precondition equality-to-violate: `victim_stack.repository.full_name != attacker_payload_repository_full_name` (i.e., the two are genuinely different tenants) while `victim_commit.sha == attacker_payload['sha']`.
4. Build a `status` payload with `repository.full_name = attacker_repo.full_name`, `sha` equal to the victim commit's sha, `context: "ci/circleci"`, `state: "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, which is orthogonal and passes for attacker's own repo).
6. Assert `victim_commit.reload.success?` is now `true` and/or that `victim_stack.schedule_merges`/merge-queue advancement was triggered — proving a payload authenticated for `attacker_repo` mutated `victim_stack`'s commit state, violating the invariant that a status for `ci/circleci` should only affect the repository that authenticated it.

      already_deployed = deployed?

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end

      end
      new_status
    end
