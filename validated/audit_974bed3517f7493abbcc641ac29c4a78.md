### Title
Naive substring-based `---` splitting in `extract_frontmatter` silently truncates YAML frontmatter, downgrading `action: block` rules to default `warn` - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`extract_frontmatter` locates the frontmatter block with a plain substring split rather than a line-anchored delimiter match: [1](#0-0) 

`content.split('---', 2)` finds the *first two literal occurrences* of `---` anywhere in the text — not just at line boundaries as real YAML frontmatter delimiters require. If a field value that appears earlier in the frontmatter block (e.g. a multi-line `message:` field authored with a block scalar `|`) contains an embedded `---` (a common markdown horizontal-rule/separator token), that embedded token is consumed as the *closing* delimiter. Everything physically written after it — including subsequent `action: block` and `pattern:` lines, and the file's real closing `---` — is shoved into `parts[2]` (treated as message body) and never parsed as frontmatter.

Downstream, `Rule.from_dict` reads `frontmatter.get('action', 'warn')` and `frontmatter.get('pattern')`: [2](#0-1) 

Because the truncated `frontmatter` dict never contains `action` or `pattern`/`conditions` (they fell into the discarded body), the resulting `Rule` silently defaults to `action='warn'` with no pattern/conditions, even though the file's author wrote (and a reviewer would visually see) `action: block` with a working pattern. `load_rule_file` treats this truncated dict as valid because it is non-empty (it still contains `name`/`enabled`/`event` from before the embedded `---`), so no warning is emitted and the degraded rule loads silently: [3](#0-2) 

The plugin's own README explicitly invites this exact trust model — rule files are meant to be authored/shared and merged via PR ("Contributing: Found a useful rule pattern? Consider sharing example files via PR!"), and rule correctness is expected to be verified by visually reading the rendered frontmatter (`action: block`, `pattern: ...`) as shown in the documented examples: [4](#0-3) [5](#0-4) 

This creates a "confused reviewer" condition: what a human sees in the file (a blocking rule for dangerous commands) does not match what `load_rules()` → `load_rule_file()` → `extract_frontmatter()` → `Rule.from_dict()` actually constructs at runtime, because the parser's delimiter detection is not line-anchored.

### Impact Explanation
A hookify rule intended by the repository owner to block dangerous Bash commands (e.g. `rm -rf`, `dd`, `mkfs`) can be silently reduced to a non-blocking `warn` rule with no active pattern/conditions, purely due to a stray `---` substring inside an earlier multi-line field value. `pretooluse.py` (`load_rules` → `RuleEngine.evaluate_rules`) will then never enforce the block, allowing unauthorized Bash execution that the repo owner explicitly configured hookify to prevent. This is a "deny means deny" invariant violation: an operator-authored blocking control is downgraded to advisory-only without any error or warning surfaced to the user.

### Likelihood Explanation
Feasibility is high and repeatable: the file is plain text authored/committed by anyone with repo write/PR access (no privileged install needed), and the split-based bug is deterministic — any `---` substring anywhere before the intended closing delimiter (including inside a legitimately-formatted multi-line YAML block scalar) reliably truncates the frontmatter. The bug is purely mechanical (`str.split` semantics), requires no interaction beyond a normal rule file being loaded by `load_rules()`, and the resulting downgrade is silent (no warning path is triggered since `frontmatter` is non-empty).

### Recommendation
Replace the substring-based split with a line-anchored parse: only treat a line that is *exactly* `---` (after stripping) at the start of a line as a delimiter (e.g., iterate lines and count only lines matching `^---\s*$`), consistent with how the bash reference tooling in the repo does it (`sed -n '/^---$/,/^---$/...'` and `awk '/^---$/{i++; next} i>=2'`), which are anchored to line boundaries rather than raw substrings. Additionally, `load_rule_file` should validate that all frontmatter keys the file's raw text appears to declare (via a defensive re-scan for `action:`/`pattern:` lines) were actually captured, or emit a warning if the parsed frontmatter looks incomplete relative to the file's line count, to fail safe instead of silently defaulting to `warn`.

### Proof of Concept
Unit test to add near `extract_frontmatter`/`Rule.from_dict` tests:

```python
def test_embedded_dashes_do_not_truncate_block_rule():
    content = """---
name: block-dangerous-rm
enabled: true
event: bash
message: |
  Warning header
  ---
  more text
pattern: rm\\s+-rf
action: block
---

Blocked!
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Expected (correct) behavior:
    assert rule.action == 'block'
    assert rule.pattern == 'rm\\s+-rf'
```

With the current implementation, `frontmatter` only contains `name`, `enabled`, `event`, and a truncated `message`; `action` and `pattern` are absent, so `rule.action == 'warn'` and `rule.pattern is None`, failing the assertions above and demonstrating the silent downgrade from `block` to `warn`.

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule
```
