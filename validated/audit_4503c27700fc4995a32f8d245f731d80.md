### Title
Route-controlled pool can execute hidden victim-authorized token transfers - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` and the other router-backed strategy entrypoints accept caller-supplied `swap` bytes and pass them to the configured aggregator without restricting the venue addresses encoded in that route. The router interprets each hop’s `assets[idx_a]` entry as the pool contract and invokes it. A malicious pool can therefore execute arbitrary contract calls during the swap, including `token.transfer(victim, attacker, amount)`, which Soroban simulation records as a child of the victim’s signed authorization tree. If the victim signs the simulated tree, the route both completes the expected collateral swap and steals unrelated wallet funds. [1](#0-0) [2](#0-1) 

### Finding Description
The controller grants the configured router one exact authorization for `token_in.transfer(controller, router, amount_in)`, but the user’s `swap` payload determines which external contracts are invoked below that call. [3](#0-2) 

Inside the aggregator, a swap instruction constructs `SwapHop` directly from payload-controlled `assets` indexes: `idx_a` is the pool, `idx_b` is the input token, and `idx_c` is the output token. No deployment registry, venue allowlist, token registry, or contract-code check constrains `pool` before dispatch. [4](#0-3) 

Phoenix, Sushi, and similar adapters invoke the supplied pool’s `swap` function after registering only the router’s own pool-pull authorization. [5](#0-4)  The dispatcher checks only that the router’s input decreased by exactly `amount_in` and its output increased by a positive amount; it does not limit what other calls the pool makes while executing. [6](#0-5) 

A rogue pool can satisfy those measurements—pull or receive the input and transfer a sufficient output back—while also calling an unrelated token’s `transfer(victim, attacker, victim_balance)`. Because that token’s `transfer` calls `victim.require_auth()`, transaction simulation records the malicious transfer under the user’s `swap_collateral` authorization. A repository test demonstrates that simulation records exactly such a rogue-pool wallet transfer as a child of the caller’s `swap_collateral` entry and that enforcing mode succeeds when that poisoned tree is signed. [7](#0-6) [8](#0-7) 

This is analogous to the Vim issue: attacker-controlled data selects code that runs during an apparently ordinary user action, and the security-sensitive side effect rides on the user’s existing authorization rather than requiring the victim to submit a separate transfer.

### Impact Explanation
A victim who signs the simulated authorization loses funds unrelated to the lending position. The stolen amount is not limited to the routed collateral, router input, minimum output, or the account’s final health checks. Any token whose `transfer` method requires the victim’s auth and whose transfer is included in the signed tree can be drained. [9](#0-8) 

The protocol strategy can still settle normally: the malicious pool can provide enough output to satisfy router measurement, and the controller can pass positive-output and account-risk checks. The result is theft of user funds in the same transaction as a legitimate `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` route. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious pool-compatible contract, construct valid `StrategyPayload` bytes naming that contract as a hop pool, and deliver those bytes to a victim through a compromised quote path, phishing interface, copied transaction, or malicious integration. The user-facing trigger is merely signing and submitting a route that appears to produce the expected output.

The exploit does require the victim to sign an authorization tree containing the malicious token-transfer child. That lowers likelihood because wallet tooling can display or reject the extra invocation, but it does not eliminate the issue: the router itself accepts the unallowlisted route and simulation produces the poisoned tree automatically. The protocol documentation explicitly warns clients to decode the signed route and reject any child beyond the expected input transfer, confirming that this is a reachable production trust boundary rather than a purely hypothetical test artifact. [9](#0-8) 

### Recommendation
Do not allow arbitrary route-selected contracts to execute under the caller’s authorization context.

- Maintain an on-chain venue/pool registry governed by the router owner and require every hop’s `pool` to resolve to a registered venue deployment before invoking it.
- Prefer routing through immutable venue adapter configuration or pool hashes rather than trusting `assets[idx_a]` as an unconstrained callback target.
- At minimum, have the router mark routes containing non-registry pools as non-composable with controller strategies.
- Keep the measured-input/output checks; they bound the routed amount but cannot bound unrelated calls made by the malicious pool.
- Update integrator and wallet guidance to reject any authorization tree containing children other than the expected input pull, but treat that as defense-in-depth rather than the protocol fix.

### Proof of Concept
1. Attacker deploys `RoguePool` with a Phoenix-compatible `swap(sender, token_in, amount_in, ...)` function.
2. `RoguePool` calls the legitimate input-token `transfer(router, pool, amount_in)`, sends a sufficient quantity of the expected output token from itself to the router, and returns normally.
3. In the same function, `RoguePool` also calls `unrelated_token.transfer(victim, attacker, victim_balance)`.
4. Victim submits `Controller::swap_collateral(victim, account_id, current_asset, amount, new_asset, routeXdr)`, where `routeXdr` is valid XDR whose swap instruction has `idx_a = RoguePool`, `idx_b = current_asset`, and `idx_c = new_asset`.
5. `swap_collateral` withdraws collateral and calls `swap_tokens`; `swap_tokens` authorizes the exact input pull and invokes `router.execute_strategy(controller, amount_in, routeXdr)`. [11](#0-10) 
6. The router decodes the payload, resolves the attacker pool from `assets`, invokes its `swap`, and accepts the resulting measured balances. [12](#0-11) [13](#0-12) 
7. Simulation records `unrelated_token.transfer(victim, attacker, victim_balance)` beneath the victim’s `swap_collateral` authorization. If the victim signs that tree, enforcement executes both the visible swap and the hidden wallet transfer.
8. The repository’s hostile-route test demonstrates this final state: the attacker receives the victim’s unrelated wallet token while the victim still receives the fair strategy output. [14](#0-13)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
