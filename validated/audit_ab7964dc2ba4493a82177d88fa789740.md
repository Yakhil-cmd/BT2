### Title
Cross-organization commit-status/push forgery via organization-scoped webhook signature verification vs. globally-scoped event handlers - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects *which* organization's webhook secret to HMAC-verify a webhook against using a field taken from the still-unverified JSON body (`repository.owner.login`, falling back to `organization.login`). The rest of the payload — in particular the `repository.full_name` used by most handlers, and the bare `sha` used by `StatusHandler` — is never re-checked against that same organization after signature verification succeeds. In a multi-org Shipit deployment (`docs/setup.md#using-multiple-github-applications`, `test/dummy/config/secrets_double_github_app.yml`), this breaks the binding "organization whose secret authenticated the request == repository/commit the handler is allowed to act on."

### Finding Description
`Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` (line 59-62) is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — parsed straight out of the attacker-supplied JSON body, before any signature check has taken place. `Shipit.github(organization:)` (`lib/shipit.rb:170-181,196-200`) looks up a per-organization `GitHubApp` (and its own `webhook_secret`) from `secrets.github`, as documented for multi-org setups.

Once `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) succeeds using **that organization's** secret, the raw body is parsed again and dispatched to handlers (`create`, line 10-15) which use *different* fields to decide what to act on:
- `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) uses `payload.dig('repository', 'full_name')` — a completely independent string field within the same signed body, not cross-checked against the org whose secret validated the signature.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) is worse: it looks up commits **globally by SHA alone**, with no repository/organization scoping at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`.

Because the webhook secret is set per-organization (and, per `docs/setup.md`, is known/managed at the level of whoever configures that organization's GitHub App in Shipit), a party who legitimately controls organization **A**'s webhook secret can craft a raw JSON body where `repository.owner.login` (or `organization.login`) is set to `"A"` — so `verify_signature` resolves and validates against Org A's secret, which the attacker knows — while every other field in the same body (`repository.full_name`, or in the `status` event, `sha`) references a repository/commit belonging to an unrelated organization **B** also hosted on the same Shipit instance. The signature check passes (it only proves "some HMAC computed with Org A's secret over this exact byte string"), but the handler's authorization decision is driven by unrelated fields that were never tied back to Org A.

Equality that should hold but doesn't:
`organization whose secret produced a valid HMAC == organization owning the repository/commit the handler mutates`

This is a direct structural analog of the reported bug class: a value used to select/validate a security parameter (here, "which organization's secret authenticates this request") is decoupled from the value actually acted upon (here, "which repository's stack/commit gets mutated"), exactly as the reported formula used the wrong scaling term for what was actually consumed downstream.

### Impact Explanation
For `status` events, this enables a cross-organization **unauthorized deploy**: `Status.after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:18-19`), together with `Commit#add_status` (`app/models/shipit/commit.rb:366-384`) call `stack.schedule_merges if new_status.pending? || new_status.success?`, and `Deploy`/`Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`) will fire `ContinuousDeliveryJob` and `trigger_deploy` once a commit shows a passing status, for stacks with `continuous_deployment` enabled. Because `StatusHandler` matches purely on `sha` with zero repository scoping, an attacker who only controls one organization's webhook secret can inject a fabricated "success" status for a real commit SHA belonging to a stack under a completely different, unrelated organization, triggering an unauthorized automatic deploy of that stack — a Critical-tier impact (unauthorized deploy) achieved without ever holding a Shipit session, API token, or write access to the victim organization's repository.

For `push` events, the same organization/repository decoupling lets Org A's secret holder forge push notifications that enqueue `GithubSyncJob` against Org B's stacks (`PushHandler#process`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), i.e. unauthorized manipulation of another organization's stack sync state.

### Likelihood Explanation
Requires the Shipit deployment to use the documented multi-organization GitHub App configuration (`docs/setup.md`'s "Using Multiple Github Applications" section) with more than one organization's `webhook_secret` configured, and requires the attacker to already legitimately possess one organization's webhook secret (e.g., as that organization's own GitHub App administrator) — this matches the "unprivileged attacker" bar since knowledge of Org A's secret grants no legitimate authority over Org B's repositories. Given multi-tenant Shipit instances are an explicitly supported and documented configuration, this is a realistic deployment shape, though it does not apply to single-organization Shipit installs (the common case, where `github_default_organization` resolves to `nil` and only one secret exists).

### Recommendation
- In `WebhooksController#verify_signature`, after signature verification succeeds, re-derive the organization from the same trusted field the handler will use to act (e.g., `repository.full_name`'s owner segment or the `Repository` record's stored `owner`) and reject if it doesn't match the organization whose secret validated the HMAC.
- In `StatusHandler#process`, scope the `Commit` lookup by the repository referenced in the payload (join through `Stack`/`Repository`) instead of matching by bare `sha` across all repositories.
- More generally, ensure every handler resolves its target `Stack`/`Repository` from a field that is provably bound to the same organization whose credential authenticated the request, not from an independently-attacker-controlled field within the same signed blob.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. per `docs/setup.md`:
   ```yaml
   github:
     OrgA:
       webhook_secret: secretA   # known to the attacker (Org A's own GitHub App admin)
     OrgB:
       webhook_secret: secretB   # unknown to the attacker; OrgB/some-repo has a stack with continuous_deployment: true
   ```
2. Attacker (an OrgA admin) crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<real sha of the tip commit of OrgB/some-repo's tracked branch>",
     "state": "success",
     "context": "ci/attacker",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secretA, raw_body)` and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully because the attacker legitimately knows `secretA`.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the commit under OrgB's stack (unrelated organization), and calls `create_status_from_github!`, creating a `success` `Status` on it.
6. If that OrgB stack has `continuous_deployment: true`, `Commit#add_status` schedules `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery` and deploys OrgB's stack — an unauthorized deploy triggered entirely with OrgA's webhook secret.

(Note: I was unable to fully retrieve `Commit#create_status_from_github!`'s exact body due to a tool error on the final iteration; its call sites and downstream effects (`Status.after_create`/`after_commit` hooks and `Commit#add_status`) were confirmed via `app/models/shipit/status.rb` and `app/models/shipit/commit.rb`.)
