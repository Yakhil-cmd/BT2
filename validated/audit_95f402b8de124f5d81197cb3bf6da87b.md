### Title
Cross-organization webhook forgery via mismatched organization/repository fields in signature verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App webhook secret to validate a request against using the `repository.owner.login` (or `organization.login`) field taken directly from the untrusted JSON request body, while every webhook `Handler` subsequently determines which `Repository`/`Stack` to mutate using the independent `repository.full_name` field from that same body. Because both fields live inside the single payload the requester constructs and signs themselves, a successful signature check against Organization A's secret provides no guarantee that the `repository.full_name` field also refers to Organization A's repository.

### Finding Description
`verify_signature` picks the app config to verify against like this: [1](#0-0) 

`repository_owner` is read straight out of the attacker-supplied JSON body: [2](#0-1) 

`verify_webhook_signature` HMACs the *entire raw body* with the secret belonging to whichever organization was selected above: [3](#0-2) 

Once the signature passes, the full payload is dispatched to every registered handler for the event, unmodified: [4](#0-3) 

Every handler resolves the repository/stack to act on using a *different* field of the same payload, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

This pattern repeats across concrete handlers, e.g. `PushHandler`, which triggers `stack.sync_github` for whatever repository `full_name` resolves to: [6](#0-5) 

and PR handlers such as `ClosedHandler`, which archives review stacks for the repository named in `params.repository.full_name`: [7](#0-6) 

Shipit natively supports hosting multiple GitHub organizations with independent webhook secrets in a single instance — this is the exact scenario the `repository_owner` selection logic and `GithubOrganizationUnknown` rescue clause are built for, and it is reflected in the shipped multi-org secrets format: [8](#0-7) 

**The broken binding:** the organization whose secret authenticated the request (`repository.owner.login`, used only for signature selection) is never checked for equality against the repository/organization the handler actually writes to (`repository.full_name`, used for the actual mutation). An attacker who knows (or has legitimately configured) the webhook secret for Organization A — a valid Shipit-integrated org they administer — can send a single POST to `/webhooks` where:
- `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` is selected and the attacker's HMAC, computed with OrgA's own secret, passes `verify_webhook_signature`), and
- `repository.full_name = "OrgB/sensitive-repo"` (a different, unrelated organization/repository also configured on the same Shipit instance).

Because the signature check only proves the body was signed with *some* known secret and never re-validates that the acted-upon repository belongs to that same organization, the forged event is accepted and dispatched to handlers operating on OrgB's stacks.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust boundary explicitly called out in scope. Concretely, an attacker controlling one organization's webhook secret can:
- Force `PushHandler` to call `stack.sync_github(expected_head_sha:)` against another organization's stack, corrupting its known-deployed revision state.
- Force PR handlers (`ClosedHandler`, `OpenedHandler`, `LabeledHandler`, etc.) to archive/unarchive/create review stacks belonging to another organization's repository.
- Inject fabricated commit statuses (`StatusHandler`) or check-suite state for another organization's commits, which can influence CI-gated deploy/merge decisions in Shipit.

This constitutes unauthorized, cross-repository writes into a stack that does not belong to the authenticating organization — a Critical-tier impact per the engine's deployment-trust model.

### Likelihood Explanation
The only prerequisite is possession of a webhook secret for *any one* organization integrated with the shared Shipit instance (e.g., a low-trust org an attacker administers, or a leaked/rotated secret) — no Shipit session, `ApiClient` token, or repository write access to the target organization is required. Building the forged payload and its correct HMAC is trivial for anyone who legitimately owns OrgA's GitHub App/secret. Any Shipit installation configured for more than one GitHub organization (an explicitly supported configuration, as shown by the multi-org secrets layout) is exposed.

### Recommendation
After verifying the HMAC, require that the organization used to select the verifying secret matches the owning organization of `repository.full_name` (and any other repository/organization fields consumed by handlers) before dispatching the payload — i.e., derive the acting organization exclusively from the value that was cryptographically bound to the verified secret, and reject the webhook if `repository.full_name`'s organization segment differs from `repository_owner`.

### Proof of Concept
1. Configure/operate a Shipit instance for two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` format).
2. As an attacker who legitimately controls `OrgA`'s webhook secret, craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/sensitive-repo"
  }
}
```
3. Compute `sha1=<hmac>` over the raw body using `OrgA`'s webhook secret and set it as the `X-Hub-Signature` header, `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` selects `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and the signature validates successfully.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("OrgB/sensitive-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `OrgB`'s stack — despite the request only ever having been authenticated against `OrgA`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
