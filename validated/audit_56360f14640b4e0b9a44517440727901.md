### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository or stack scoping, so a `status` webhook that is legitimately authenticated for one organization/repository (including one an attacker fully controls) can create/overwrite CI status records on a completely different stack's commit whenever the SHA values collide (e.g. a fork sharing history with the victim). This is compounded by `GitHubApp#verify_webhook_signature` deriving its verification key purely from the attacker-suppliable `repository.owner.login`/`organization.login` field, and by silently treating orgs with no configured `webhook_secret` as fully verified.

### Finding Description
The broken binding is: **"a `status` event's effect should be scoped to the repository whose secret authenticated it" == "a `status` event only ever mutates commits belonging to that same repository/stack."** The code breaks this equality.

1. `Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `repository_owner`, which is read straight out of the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`): [1](#0-0) [2](#0-1) 

2. `GitHubApp#verify_webhook_signature` only accepts the legacy `sha1=` prefixed `X-Hub-Signature` header (rejecting `X-Hub-Signature-256`), and — critically — returns `true` unconditionally whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

3. Once past signature verification, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which does a completely global, repository-agnostic lookup: [4](#0-3) 

4. `Commit` records `belongs_to :stack`, i.e. each stack owns its own commit rows, but `StatusHandler` never filters by `stack_id` or by the `repository` in the payload: [5](#0-4) 

Exploit flow: an attacker owns/administers a repository or org that Shipit tracks (their own fork, or an org with no `webhook_secret` configured — the “no-secret org” case where verification is a no-op). That fork shares a commit SHA with the victim's tracked repo/stack (trivial to arrange: fork the victim repo before divergence, or reference any commit SHA the victim stack already has recorded). The attacker POSTs a forged `status` event to `/webhooks` with `X-Github-Event: status`, `X-Hub-Signature: sha1=<valid-for-their-own-org-or-absent-secret>`, `repository.owner.login` set to their own (attacker-controlled or secret-less) org, and `sha` set to the shared SHA with `state: "success"`. `verify_signature` passes because it only checks that the payload is validly signed *for the org named in the payload* (which the attacker controls or which has no secret at all). `StatusHandler` then runs `Commit.where(sha: attacker_sha).each { |c| c.create_status_from_github!(params) }`, which matches and mutates the victim's `Commit` row too, since the query has zero repository/stack scoping.

None of the existing guards catch this: `verify_signature` only proves the payload matches *some* org's secret, not that the org matches the commit being mutated; `ExplicitParameters` in `StatusHandler` only validates the shape of `sha`/`state`/etc., not repository ownership; there is no `Stack`/`Repository` scoping anywhere in the handler.

### Impact Explanation
A successful forged `status` webhook writes a fabricated `Status` record (`create_status_from_github!` → `add_status`) onto the victim stack's commit. This can flip a commit from pending/failing to `success`, which feeds directly into `Commit#deployable?` and `schedule_continuous_delivery`, potentially triggering an unauthorized/auto deploy of a commit that never actually passed CI, or unblocking a merge that depends on required statuses. This is a payload from one repository/organization mutating another repository's stack/commit state — matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any stack whose commits' SHAs the attacker can predict or reproduce (trivial via forking).

### Likelihood Explanation
Preconditions: the attacker needs Shipit to track at least one repository/org they control (a very low bar for any GitHub org member using a shared/multi-tenant Shipit instance, or exploiting an org with no `webhook_secret` configured), and a commit SHA shared with the victim stack (achievable by forking the victim repo before it diverges, or targeting commits already known/public). No Shipit session, API token, or GitHub App private key is required. This is an unauthenticated `POST /webhooks` request, fully repeatable and scriptable.

### Recommendation
Scope `StatusHandler#process` (and any other SHA/commit-based handler) to the stack(s) actually associated with `params.dig('repository','full_name')` or `params.dig('repository','id')`, e.g. `Commit.joins(:stack).merge(Stack.where(...matching repo...)).where(sha: params.sha)`, rather than a bare global `Commit.where(sha:)`. Additionally, tie webhook signature verification to the specific repository/stack being mutated (not just the payload-declared `repository.owner.login`), and treat organizations without a configured `webhook_secret` as unverifiable/rejected rather than auto-verified.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Create two `Stack`/`Commit` fixtures in different "repositories" (e.g. `shipit_stacks(:shipit)` commit A and a second stack `victim_stack` with a `Commit` having the **same** `sha` value as commit A).
2. Configure `Shipit.github(organization: 'attacker-org')` with either no `webhook_secret` or a known test secret; stub/allow `verify_webhook_signature` to pass for `attacker-org` only (simulating the attacker's own authenticated org).
3. POST to `/webhooks` with `X-Github-Event: status`, `X-Hub-Signature: sha1=<valid-for-attacker-org>`, body `{ "sha" => shared_sha, "state" => "success", "repository" => { "owner" => { "login" => "attacker-org" } } }`.
4. Assert: `victim_stack`'s `Commit` (belonging to a stack never touched by `attacker-org`'s credentials) gains a new `Status` row with `state == "success"` — i.e. `assert_difference('victim_commit.statuses.count', 1) { post :create, body:, as: :json }` — proving the binding "status effect scoped to authenticating repository" is violated.

    end
