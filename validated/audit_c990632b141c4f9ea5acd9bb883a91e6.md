### Title
Bandwidth-grant bypass via receipt-size clamping in `try_forward` allows oversized receipts to consume more bytes than granted - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`ReceiptSinkV2::try_forward` clamps the `size` value used for the `OutgoingLimit.size` admission check and for decrementing `forward_limit.size` to `apply_state.config.wasm_config.limit_config.max_receipt_size`, but it still pushes the full, unclamped `receipt` into `outgoing_receipts`. An unprivileged attacker can deploy and call a contract that (via the already-tracked bug referenced in the code comment, github.com/near/nearcore/issues/12606) produces an action receipt whose real serialized size exceeds `max_receipt_size` after `output_data_receivers` is appended post-validation, causing the true byte count transmitted to a shard link to exceed what the bandwidth scheduler granted for that link.

### Finding Description
`forward_or_buffer_receipt` computes `size = compute_receipt_size(&receipt)` and passes it to `ReceiptSinkV2::try_forward`. Inside `try_forward`, the code explicitly clamps `size` to `max_receipt_size` when the receipt is bigger than that, per the comment "Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck," [1](#0-0) . The admission check `forward_limit.gas >= admission_gas && forward_limit.size >= size` and the subsequent bookkeeping `forward_limit.size -= size` both use this clamped value, while `outgoing_receipts.push(receipt)` pushes the original, unclamped (oversized) receipt [2](#0-1) . As a result the ledger `forward_limit.size`, which is derived from `bandwidth_scheduler_output.granted_bandwidth.get_granted_bandwidth(...)` [3](#0-2) , is decremented by less than the actual byte count added to `outgoing_receipts`, so the real bytes forwarded to the target shard can exceed the bandwidth grant for that link.

Oversized receipts are reachable today because validation of a fresh receipt (`ValidateReceiptMode::NewReceipt`) only checks size once, before actions/side effects like `output_data_receivers` are appended, while `ValidateReceiptMode::ExistingReceipt` intentionally tolerates already-oversized receipts to remain compatible with this known defect [4](#0-3) . The integration test `test_max_receipt_size_promise_return` in this repo demonstrates exactly this: a promise-return receipt is built at `max_receipt_size`, then `output_data_receivers` is appended afterward, pushing it above the limit, and it is not rejected [5](#0-4) .

### Impact Explanation
This maps to a congestion/bandwidth-accounting bypass: an attacker-controlled shard can push more real bytes onto an inter-shard link than the bandwidth scheduler granted, degrading throughput or increasing memory/storage pressure for the receiving shard beyond what congestion control intended to allow. It does not cause balance/gas metering bypass or fund loss; it is a bounded accounting/congestion-control defect whose magnitude is limited by how far `output_data_receivers` (or similar post-validation additions) can push a receipt beyond `max_receipt_size`, not an unbounded amplification.

### Likelihood Explanation
The precondition (crafting a receipt that grows past `max_receipt_size` after initial validation via the promise-return-then-append-output-data-receivers pattern) is demonstrated as reproducible in the existing test suite using only a deployed contract and public RPC calls, requiring no privileged access. The excess is bounded per receipt by the size contributed by the appended output data receivers, so it is repeatable but not unbounded per single receipt; an attacker could still repeat it many times to accumulate excess bandwidth usage on a link.

### Recommendation
Do not silently clamp the accounting `size` while pushing the real, unclamped receipt. Instead, either: (1) subtract the real (unclamped) size from `forward_limit.size` (allowing it to go negative/saturate to 0) so subsequent receipts are correctly blocked, while still forwarding the current one to avoid it getting permanently stuck; or (2) reject/re-validate the receipt as oversized and drop/refund it rather than forwarding it, closing off the #12606 root cause instead of only mitigating its downstream symptom.

### Proof of Concept
Extend `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs`) into a two-shard `test-loop` scenario: deploy the contract on shard A, trigger the promise-return receipt so its real serialized size exceeds `max_receipt_size` while targeting a receiver on shard B under a tight bandwidth grant (e.g. via `BandwidthSchedulerOutput` test hooks used in `test-loop-tests/src/tests/bandwidth_scheduler.rs`). After `Runtime::apply` processes the chunk, assert that the sum of `compute_receipt_size` over all receipts actually placed in `outgoing_receipts` for the A→B link exceeds `forward_limit.size`/`granted_bandwidth` recorded before forwarding, demonstrating the accounting decrement (`forward_limit.size -= size` with clamped `size`) understates the true bytes transmitted.
