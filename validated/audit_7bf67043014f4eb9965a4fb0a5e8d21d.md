### Title
Signature verification uses `repository.owner.login` while `MembershipHandler` writes the `Team` under `organization.login`, letting an attacker-signed webhook mutate a victim organization's Team - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `MembershipHandler#find_or_create_team!`, however, scopes the `Team` it creates/updates using `params.organization.login` only, and never checks it against `repository_owner`. An attacker who owns any GitHub App/org (and thus its own `webhook_secret`) can therefore sign a `membership` event whose `repository.owner.login` is their own org (so it passes signature verification) but whose `organization.login` names a victim org, causing a `Team` row to be created/mutated under the victim's organization and letting the attacker add an arbitrary GitHub login as a team member of that record.

### Finding Description
The binding the code implicitly assumes is:
`organization_that_signed_the_request (used in verify_signature) == organization_whose_Team/Membership_is_written (used in MembershipHandler)`

Trace:
- `WebhooksController#repository_owner` [1](#0-0)  resolves the org used to pick the webhook secret from `params.dig('repository','owner','login') || params.dig('organization','login')` — `repository.owner.login` wins if present.
- `verify_signature` uses that resolved value to fetch `Shipit.github(organization: repository_owner)` and verify the HMAC against the *raw* request body [2](#0-1) .
- `create` reparses the same raw body and dispatches it unchanged to the handler [3](#0-2) .
- `MembershipHandler` requires `organization.login` and `team`/`member`, but does **not** require or validate `repository` at all [4](#0-3) , and scopes the created `Team` using `params.organization.login` exclusively: `team.organization = params.organization.login` [5](#0-4) .

Because `repository` is entirely optional/unchecked by the handler, an attacker can craft:
```json
{
  "action": "added",
  "team": {"id": 999999, "name": "x", "slug": "x", "url": "http://x"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
signed with `attacker-org`'s own registered `webhook_secret`. `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, which correctly verifies the signature (the attacker legitimately controls that secret), so the request passes. The handler then executes `Team.find_or_create_by!(github_id: 999999) { team.organization = 'victim-org' }` and adds `attacker` as a member of that Team — a write into `victim-org`'s data authorized by `attacker-org`'s credential.

None of the existing guards catch this: `verify_signature` never compares its resolved organization against the one the handler will use; the `ExplicitParameters` schema for `MembershipHandler` doesn't declare/require `repository` so extra fields are simply ignored by `parse!`; `drop_unhandled_event` only filters unregistered event types (membership is registered); session/API-token guards (`force_github_authentication`, `User#authorized?`, `require_permission!`) don't apply to `WebhooksController`, which is unauthenticated by design and relies solely on `verify_signature` for trust.

### Impact Explanation
A successful request creates or mutates a `Shipit::Team` record scoped to an arbitrary victim organization and can add an attacker-chosen GitHub login as a member of it, using only a secret the attacker owns. `Team` membership feeds `Shipit.github_teams`-style authorization flows in this engine (teams synced via `Team.find_or_create_by_handle`) [6](#0-5) , so if a victim's Shipit configuration authorizes access based on team membership for an org named `victim-org`, an attacker can plant/poison a Team row and membership for that org without ever authenticating as, or holding secrets for, `victim-org`. This is a cross-tenant write where a payload signed for one org (`attacker-org`) mutates another org's (`victim-org`) records — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team") and, if it feeds authorization, the High category (escalation into team-based authorization).

### Likelihood Explanation
Requires only that Shipit be configured with per-organization `webhook_secret`s (multi-org `secrets.yml`), and that the attacker legitimately controls at least one such registered organization/App and its `webhook_secret` — no access to victim secrets is needed. The attacker crafts one HTTP POST to `/webhooks` with `X-Github-Event: membership`, signs it with their own secret, and can repeat this against any `github_id`/`organization.login` value they choose since nothing binds `organization.login` to `repository_owner`. This is directly reachable by any internet host that can reach the Shipit `/webhooks` endpoint and register/administer one GitHub App — a low-cost, repeatable attack.

### Recommendation
In `MembershipHandler` (and any other handler that trusts `organization.login`/`repository.owner.login` independently of the value used for signature verification), require and cross-check that the organization used to authenticate the webhook (`repository_owner`) matches the organization the handler is about to mutate. Concretely: pass the verified `repository_owner` value down to handlers (e.g. via the payload or an explicit argument) and have `MembershipHandler#find_or_create_team!` assert `params.organization.login == verified_organization` (case-insensitively) before writing, rejecting the event otherwise. Alternatively, make `verify_signature` always derive the org strictly from `organization.login` when present for org-scoped events, and forbid handlers from trusting fields not covered by the verified org.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (conceptually — since `test/**` is out of scope for the fix, this is only the reproduction plan):
1. Configure two orgs with distinct secrets in test secrets fixture (`attacker-org`, `victim-org`), each with its own `webhook_secret`.
2. Build a `membership` payload: `organization.login = 'victim-org'`, `repository.owner.login = 'attacker-org'`, `team.id` unused elsewhere, `member.login = 'attacker'`.
3. Sign the raw JSON with `Shipit.github(organization: 'attacker-org')`'s secret and set `X-Hub-Signature`.
4. POST to `/webhooks` with `X-Github-Event: membership`.
5. Assert `Shipit.github(organization: 'attacker-org')` (not `'victim-org'`) was the one whose `verify_webhook_signature` succeeded (e.g. via `expects`/spy on `GithubApp#verify_webhook_signature` for `'attacker-org'`).
6. Assert response is `200 OK` and `Team.find_by(organization: 'victim-org')` now exists with the attacker's `member.login` in its `members`, proving the write landed under `victim-org` despite the signature belonging to `attacker-org`.

Both sides of the equality diverge after the request: signed-for organization = `attacker-org`, written-to organization = `victim-org`.
