### Title
Stack-scoped ApiClient token authorises access to any stack via CCMenu API - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::ApiClient` supports being scoped to a single stack via `stack_id` [1](#0-0)  and `BaseController#stacks` enforces that scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [2](#0-1) , with `stack` built on top of that scoped relation via `stacks.from_param!(params[:stack_id])` [3](#0-2) . `CCMenuController` redefines `stack` to bypass this scoping entirely: `@stack ||= Stack.from_param!(params[:stack_id])` [4](#0-3) .

### Finding Description
The binding that should hold is: `stack a token authorises == stack it touches`. For every other API controller (`TasksController`, `DeploysController`, `LocksController`, `RollbacksController`, `MergeRequestsController`, `CommitsController`, `OutputsController`, `ReleaseStatusesController`), `stack` resolves through the inherited `BaseController#stack`, which is derived from `stacks`, itself filtered by `current_api_client.stack_id` when the client is stack-scoped [5](#0-4) . `CCMenuController` is the only controller that overrides `stack` to call `Stack.from_param!` directly on the unscoped `Stack` model [4](#0-3) , so the `stack_id` restriction on the `ApiClient` is never applied here. The controller only checks `require_permission :read, :stack` [6](#0-5) , which validates the permission string is present in `ApiClient#permissions` but performs no check that the target stack matches `stack_id` [7](#0-6) .

This is exactly the class of bug the report hints at: a value that gates trust (the callback/token's authorized scope) is checked against the wrong target — here, an `ApiClient` created and intentionally scoped down to one stack (a common workflow, e.g. `CCMenuUrlController#client` itself creates such a scoped client: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [8](#0-7) , whose token is embedded directly in a URL exposed to CI dashboard tools) can use its `read:stack` permission to read the CCMenu XML status of any stack in the installation, not just the one it was scoped to.

### Impact Explanation
This is an authorization-boundary break: a token an admin/user believed was restricted to a single stack (`stack_id`) can, in fact, enumerate `stack_id` params and read `deploys_and_rollbacks` / build status output for every stack in the Shipit instance, including stacks belonging to repositories/teams the token holder has no legitimate access to. This maps to "High - escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state" since it defeats the per-stack authorization scoping that the rest of the API deliberately enforces. It is a read-only disclosure (build status/name, last build info) rather than RCE or write access, so it sits at the lower end of "High."

### Likelihood Explanation
Likelihood is high for anyone who already legitimately possesses one stack-scoped CCMenu token (these tokens are handed out routinely, e.g. embedded in the CCMenu URL fetched by `CCMenuUrlController#fetch` [9](#0-8) , intended for consumption by CI-status widgets/tools outside the trusted admin boundary). Exploitation requires only changing `stack_id` in the request URL — no privilege escalation or additional secrets are needed beyond the token itself, which is exactly the kind of narrowly-scoped credential this bug defeats.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and rely on the inherited `BaseController#stack`/`stacks` scoping (or otherwise explicitly check `stack.id == current_api_client.stack_id` when `current_api_client.stack_id?`) so that stack-scoped tokens cannot access stacks outside their assigned `stack_id`.

### Proof of Concept
1. As an admin, create/observe a stack-scoped `ApiClient` (e.g. via `CCMenuUrlController#fetch`, which creates `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(...)` bound to a specific stack) and obtain its `authentication_token`. [10](#0-9) 
2. Using that token as Basic-Auth credentials, call `GET /api/ccmenu/*stack_id` with a *different* `stack_id` belonging to another team/repository.
3. Because `Shipit::Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!` used elsewhere [4](#0-3) , `require_permission :read, :stack` only checks that `"read:stack"` is in the client's `permissions` array [7](#0-6)  and the request succeeds, returning the CCMenu XML (build name/status/timestamp) for the unrelated stack — data the token was never authorized to access.
