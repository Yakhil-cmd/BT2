### Title
Webhook signature is validated against the organization embedded in the payload while handlers act on a completely different repository/commit scope taken from the same untrusted payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects *which* organization's secret to validate the incoming webhook against purely from attacker-controlled JSON in the body itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
with [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). The `GithubApp#verify_webhook_signature` method treats an unconfigured secret as automatically valid: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```
Shipit ships a documented multi-org configuration format where `webhook_secret` can legitimately be left blank per organization (`config/secrets.development.shopify.yml` shows `webhook_secret: # nil` as a valid template entry). This is the exact analog of `WETH.allowance()`'s missing `return`: a verification function that silently returns a "pass" result under a normal, reachable code path, and the value it verifies (`webhook_secret` chosen via `repository_owner`) is never bound to the value that is actually acted upon.

Once `verify_signature` passes (either because the attacker knows/guesses a configured-but-blank secret's org name, or because any tenant org in a multi-org install has no `webhook_secret`), the handler layer derives what to act on from an *entirely different field* of the same unauthenticated body: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`repository_owner` (used for auth-org selection) and `repository_name`/`full_name` (used for target selection) are read independently from the same JSON body and are never compared. Worse, `StatusHandler` doesn't even scope by repository at all — it looks up commits globally: [5](#0-4) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`create_status_from_github!` writes an attacker-controlled `state`/`context`/`description` directly into the commit's status list, and `Commit#deployable?` / `#blocked?` gate continuous delivery purely off stored status state: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
The binding broken is: `organization whose webhook_secret authenticated the request` == `repository/commit that the handler subsequently writes to`. Before the attack, an attacker with no Shipit session, no `ApiClient` token, and no GitHub repository access can only fail signature verification for any org they don't control. After the attack, by naming an org with a blank/known `webhook_secret` in `repository.owner.login`, the attacker satisfies `verify_signature` while independently choosing an arbitrary `repository.full_name` (for `PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) or an arbitrary commit `sha` with no repository scoping at all (`StatusHandler`) belonging to any other, unrelated, and properly-secured stack/organization in the same Shipit instance. Via `StatusHandler`, this lets the attacker forge a passing CI status for any commit sha, which combined with `Commit#deployable?` / `#schedule_continuous_delivery` can cause an unauthorized automatic deploy for a stack under continuous deployment — satisfying the "unauthorized deploy" Critical-impact bar. This requires only that the multi-tenant Shipit instance contains one organization with a blank `webhook_secret` (a state explicitly represented in shipped configuration templates), which is a materially weaker precondition than compromising `webhook_secret`, `api_clients_secret`, or a GitHub App key for the victim organization itself.

### Likelihood Explanation
Requires the Shipit deployment to host at least two GitHub organizations where one has an unset/blank `webhook_secret` (a state the shipped config format explicitly supports and does not forbid) or a secret the attacker otherwise knows, while other organizations in the same instance are properly secured and hold the deployable stacks being targeted. This is a realistic, unprivileged, network-only attack path against the public, unauthenticated `WebhooksController` endpoint (CSRF is explicitly skipped and no session/API auth is required).

### Recommendation
- Bind the verification identity to the acted-upon identity: derive the org used for signature selection from the same field(s) used by handlers (`repository.full_name`'s owner), and reject if `repository.owner.login`/`organization.login` doesn't match the owner portion of `repository.full_name`.
- Do not silently treat a missing `webhook_secret` as "signature verified"; either require a secret for every configured organization or explicitly document/gate this as an intentionally insecure mode, and never let it authorize acting on unrelated repositories.
- Scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to the repository named by `repository.full_name` (via `stacks`), consistent with the other handlers, instead of a global, cross-tenant lookup.

### Proof of Concept
1. Shipit instance hosts organizations `open-org` (webhook_secret left blank, per the shipped `secrets.development.shopify.yml` template) and `victim-org` (properly configured, hosts a stack with `continuous_deployment: true`).
2. Attacker (no Shipit session, no API token, no GitHub access to `victim-org`) sends:
   ```
   POST /github/webhooks
   X-Github-Event: status
   X-Hub-Signature: sha1=anything   # ignored because open-org's secret is blank
   {
     "sha": "<victim-org commit sha the attacker wants to fast-track>",
     "state": "success",
     "context": "ci/required-check",
     "repository": {"owner": {"login": "open-org"}, "full_name": "open-org/whatever"}
   }
   ```
3. `verify_signature` calls `Shipit.github(organization: "open-org")`; `verify_webhook_signature` returns `true` unconditionally because `open-org`'s `webhook_secret` is blank.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `victim-org` commit by sha regardless of the `repository` field in the payload — and calls `create_status_from_github!`, injecting a forged "success" status.
5. If that commit becomes the head of a `victim-org` stack with CI-gated continuous deployment, `Commit#deployable?`/`#schedule_continuous_delivery` can trigger an unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
