### Title
Unvalidated P2P Staking Info Injection During FastSync Corrupts Proposer-Selection DB — (`datasync/downloader/queue.go`)

### Summary

The `validate` callback in `queue.DeliverStakingInfos` is a permanent no-op stub. A registered P2P peer that is assigned staking-info fetch requests during FastSync/SnapSync can respond with arbitrary `P2PStakingInfo` content. The fabricated data is written unconditionally to the staking DB. Because `GetStakingInfo` treats the DB as authoritative over the state trie, the corrupted record is used by `calcBaseProposers` → `generateProposerListWeighted` to build the WeightedRandom proposer list, causing the synced node to diverge from the honest network on proposer and committee selection.

### Finding Description

**Step 1 – P2P entry point (no content check)**

`handleStakingInfoMsg` decodes the peer's response and forwards it to the downloader with no content validation: [1](#0-0) 

**Step 2 – Empty validate stub**

`queue.DeliverStakingInfos` passes a `validate` callback that unconditionally returns `nil`. Compare this with `DeliverReceipts`, which verifies `DeriveReceiptsRoot` against `header.ReceiptHash`: [2](#0-1) [3](#0-2) 

The `deliver` helper does check that the peer had a pending request for those block hashes (preventing unsolicited injection), but it performs no content validation once the peer is assigned a request. [4](#0-3) 

**Step 3 – Unconditional DB write**

Both `commitFastSyncData` and `commitPivotBlock` write `result.StakingInfo` directly to the staking DB without any cross-check against the canonical state trie: [5](#0-4) [6](#0-5) 

**Step 4 – DB takes priority over state trie**

`GetStakingInfo` returns the DB entry immediately, before ever consulting the state trie. Once the corrupted record is written, it is never re-derived from state: [7](#0-6) 

**Step 5 – Corrupted data drives proposer selection**

`calcBaseProposers` calls `GetStakingInfo` and feeds the result into `generateProposerListWeighted`. Zeroed amounts collapse all weights to zero (every validator gets one slot, uniform distribution); inflated amounts skew the list toward the attacker's validator: [8](#0-7) [9](#0-8) 

The same staking amounts also gate `DemotedValidators` (amounts vs `MinimumStake`). Zeroing all amounts can demote every validator, producing an empty qualified set and breaking consensus entirely on the synced node.

### Impact Explanation

The synced node computes a different WeightedRandom proposer list and a different qualified-validator set than honest full-sync nodes. This is persistent consensus divergence: the node will reject valid blocks from the correct proposer or accept blocks from the wrong one. In the extreme case (all amounts zeroed), the qualified set is empty and the node cannot participate in consensus at all. The corruption survives node restarts because it is written to the persistent staking DB.

### Likelihood Explanation

- Any registered P2P peer can be assigned staking-info fetch requests during FastSync/SnapSync; P2P peer registration is permissionless on the public network.
- The attack window is the FastSync/SnapSync phase, which is the normal bootstrap path for new nodes.
- The attack is limited to pre-Kaia-hardfork block ranges (staking DB is only consulted before the Kaia fork; after it, staking info is re-derived from state each block).
- No special privilege, governance key, or validator-majority collusion is required.

### Recommendation

Replace the TODO stub with a real validation function that re-derives the staking info from the canonical state trie at the referenced block and compares it against the peer-supplied data, analogous to how `DeliverReceipts` verifies `DeriveReceiptsRoot` against `header.ReceiptHash`. If the state is not yet available during sync, defer DB writes until the state is committed and verified.

### Proof of Concept

1. Connect a malicious node as a registered P2P peer to a victim node that is performing FastSync.
2. When the victim requests staking info for block hashes at staking-update-interval boundaries, respond with `P2PStakingInfo` structs where `CouncilStakingAmounts` are all zero (or inflated for the attacker's validator).
3. The victim's `queue.DeliverStakingInfos` accepts the data (validate stub returns nil), stores it in `fetchResult.StakingInfo`, and `commitFastSyncData` writes it to the staking DB via `PutStakingInfoToDB`.
4. After sync completes, call `GetStakingInfo(updateNum)` on the victim node. It returns the corrupted DB record.
5. Observe that `calcBaseProposers` produces a proposer list that differs from the list computed by honest full-sync nodes, confirming consensus divergence.

Property test: for any `P2PStakingInfo` delivered via `DeliverStakingInfos`, assert that `staking.ToStakingInfo(p2pInfo).StakingAmounts` equals the amounts derivable by calling `getFromStateByNumber(p2pInfo.BlockNum)` on the canonical state trie. This assertion currently fails for any malicious peer response because the validate stub never checks it.

func generateProposerListWeighted(qualified *valset.AddressSet, si *staking.StakingInfo, useGini bool, blockHash common.Hash) []common.Address {
	var (
		addrs          = qualified.List()
		stakingAmounts = collectStakingAmounts(addrs, si)
		gini           = computeGini(stakingAmounts) // si.Gini is computed over every CN. But we want gini among validators, so we calculate here.
		exponent       = 1.0 / (1 + gini)
		totalStakes    = float64(0)
	)

	// Adjust staking amounts and calculate the sum
	if useGini {
		for addr, amount := range stakingAmounts {
			stakingAmounts[addr] = math.Round(math.Pow(float64(amount), exponent))
			totalStakes += stakingAmounts[addr]
		}
	} else {
		for _, amount := range stakingAmounts {
			totalStakes += amount
		}
	}

	// Calculate percentile weights
	weights := make(map[common.Address]uint64)
	if totalStakes > 0 {
		for _, addr := range addrs {
			weight := uint64(math.Round(stakingAmounts[addr] * 100 / totalStakes))
			if weight <= 0 {
				weight = 1
			}
			weights[addr] = weight
		}
	} else {
		for _, addr := range addrs {
			weights[addr] = 0
		}
	}

	// Generate weighted repeated list
	proposerList := make([]common.Address, 0)
	for _, addr := range addrs {
		for i := uint64(0); i < weights[addr]; i++ {
			proposerList = append(proposerList, addr)
		}
	}
	// If the list is empty (i.e. all weights are zero), list each validator once.
	if len(proposerList) == 0 {
		for _, addr := range addrs {
			proposerList = append(proposerList, addr)
		}
	}

	seed := valset.HashToSeedLegacy(blockHash)
	return valset.NewAddressSet(proposerList).ShuffledListLegacy(seed)
