### Title
Delimiter injection in arbiter contract hash construction allows forging a colliding `CONTRACT_hash` that binds a shared address to attacker-chosen terms - (File: arbiter_contract.js)

### Summary
`getHashSrc()` in `arbiter_contract.js` builds the arbiter-contract hash by naively joining user-supplied fields (`title`, `text`, party names, `arbiter_address`, addresses, `amount`, `asset`) with a fixed delimiter string `exports.DELIMITER = "[|#|]"` and hashing the result with SHA-256, exactly the same bug class as the reported pymetasploit3 issue: a "structural" character sequence that is supposed to separate distinct fields can itself be injected into a field value by an untrusted party, letting them break the intended field boundaries and make two semantically different contracts serialize to the identical byte string (and thus identical hash), the same way a raw `\n` injected into an RHOSTS-like parameter broke the intended command boundary in Metasploit console. [1](#0-0) [2](#0-1) 

### Finding Description
`createAndSend()` is invoked by a paired-device peer (`peer_device_address`) offering an arbiter contract; the contract's `hash` is computed purely from a delimiter-joined concatenation of caller-controlled strings, with no check that any field is free of the delimiter substring `"[|#|]"`: [3](#0-2) [4](#0-3) 

None of `title`, `text`, `my_party_name`, `peer_party_name` are validated to reject the delimiter sequence before being fed into `getHashSrc`/`getHash`. Because `Array.prototype.join` does not escape occurrences of the delimiter inside individual elements, a party can craft `title`/`text`/`party_name` values that contain the literal substring `"[|#|]"` so that the resulting concatenated string — and therefore the SHA-256 hash — is identical to the concatenation produced by a different, benign-looking contract with different field boundaries (e.g., shifting bytes from `text` into `payer_name`, or from `title` into `text`). This is structurally identical to the reported vulnerability: attacker-controlled data crossing a delimiter boundary that the receiving logic relies on to reconstruct "the intended structure."

This hash is not just a display label — it is embedded directly into the security-critical shared-address definition used to control fund release for both public and private assets: [5](#0-4) 

The oracle-lookup keys `"CONTRACT_" + contract.hash` and `"CONTRACT_DONE_" + contract.hash` are the *sole* mechanism by which the arbiter's data-feed and the private-asset "done" signal authorize release of the funds locked in the multisig-AND-oracle shared address definition. If two different contracts (with different terms shown to each party, but colliding hash) can be engineered to share the same hash, then an arbiter's resolution — or a "done" signal — intended for contract A also unlocks the shared address created for colliding contract B, and `parseWinnerFromUnit` / `deriveSharedAddress` cannot distinguish them because they only ever key off `contract.hash`: [6](#0-5) 

Additionally, the hash is used as the primary key of `wallet_arbiter_contracts` (`getByHash`), so a party could also engineer their own contract's hash to *collide* with a hash they expect a cosigner or victim to already have stored, muddying `store()`/`respond()`/`shareContractToCosigners` flows which trust hash equality as the join key between the two parties' independent, unverified copies of the "same" contract.

Note: the pre-`NEW_HASH_DATE` legacy hash format (`join("")` with no delimiter at all) is even more directly injectable — with no separator whatsoever between `title`, `text`, `creation_date`, etc., trivial field-boundary shifting is possible for any contract still using dates ≤ 2026-11-01, and the "fix" merely changed to a low-entropy multi-character delimiter that is still not validated to be absent from any field, so the underlying class of bug persists. [7](#0-6) 

### Impact Explanation
A malicious counterparty (a paired-device peer negotiating an arbiter contract — squarely in scope as a "private-payment counterparty / paired device") can construct contract text/title/party-name fields containing the delimiter sequence so that the resulting SHA-256 `contract.hash` collides with a hash they anticipate for a different set of terms. Since `contract.hash` is embedded verbatim into the `["in data feed", [...], "CONTRACT_" + contract.hash, ...]` conditions of the multisig shared-address definition that gates release of locked funds (for both the public-asset payout path and the private-asset `CONTRACT_DONE_` completion path), a hash collision lets an attacker cause the arbiter's resolution intended for one contract, or a "done" completion signal from one contract, to also satisfy the release condition of a different shared address — enabling unauthorized release/diversion of funds locked under a colliding contract without a legitimate matching arbiter decision or counterparty completion signal. This is a concrete asset-freezing / fund-diversion risk within the wallet/contract message-handling surface.

### Likelihood Explanation
Exploitation requires the attacker to find or engineer two field combinations that concatenate to the identical byte string under a fixed, publicly-known 5-character delimiter with no built-in escaping — a purely computational/social-engineering exercise (crafting plausible-looking title/text/party-name text containing `"[|#|]"`) rather than needing any privileged access, key compromise, or network position. Any user who can propose/negotiate an arbiter contract with another wallet (a standard, unprivileged wallet feature) can attempt this, making the likelihood moderate-to-high for an actor motivated to defraud a specific counterparty or arbiter-store integration, though it does require some cooperation/social engineering (the victim must accept a contract with a crafted title/text) rather than being a fully passive network attack.

### Recommendation
Reject (or unambiguously escape) any occurrence of the delimiter substring `"[|#|]"` in `title`, `text`, `my_party_name`, and `peer_party_name` before computing `getHashSrc`/`getHash` (mirroring the existing `\n`-rejection pattern already used for `data_feed` payloads in `validation.js`/`aa_validation.js`). Preferably, switch to a length-prefixed or otherwise unambiguous encoding scheme (e.g. reuse `string_utils.getSourceString`'s type-tagged, `\x00`-guarded serialization, which already throws if a component contains the join character) instead of a fixed-string `Array.join` delimiter, so that field-boundary confusion is structurally impossible rather than merely discouraged by delimiter-content checks.

### Proof of Concept
1. Party A proposes contract 1 with `title = "Deal"`, `text = "pay for goods[|#|]2026-06-01[|#|]PAYER_ADDR..."` etc., crafted so that `getHashSrc` yields byte string `S`.
2. Party A (or a colluding party) separately constructs contract 2 with different `title`/`text` splits — e.g. moving bytes across the `title`/`text` boundary — such that `getHashSrc(contract2)` also yields the same byte string `S` (feasible because `[contract.title, contract.text, ...].join(DELIMITER)` performs no escaping of `DELIMITER` occurrences inside `title`/`text`).
3. Both contracts hash to the same `contract.hash` via `getHash()`. 
4. Contract 1's shared address is derived via `deriveSharedAddress` with `["in data feed", [arbiter_address], "CONTRACT_" + hash, "=", offeror_address]`. When the arbiter (or the private-asset counterparty via `CONTRACT_DONE_` in `complete()`) posts a data feed keyed on that same `hash` intending to resolve/complete contract 1, the identical `hash` also satisfies the release condition embedded in contract 2's shared-address definition, allowing funds locked under contract 2 to be released using a data feed/resolution never intended for contract 2. function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
