### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, letting a token authorized for one stack read status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports a `stack_id` scope so a token can be restricted to a single stack: `Api::BaseController#stacks` filters `Stack.where(id: current_api_client.stack_id)` when `stack_id` is set, and `Api::BaseController#stack` resolves the requested resource through that scoped relation (`stacks.from_param!`) [1](#0-0) . `Api::StacksController` (and other API controllers) correctly reuse this scoped `stack`/`stacks` helper, e.g. `@stack ||= stacks.from_param!(params[:id])` [2](#0-1) . `Api::CCMenuController`, however, overrides `stack` to resolve directly against the unscoped `Stack` model: `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) . Permission checking (`require_permission :read, :stack`) only verifies that the string `"read:stack"` is present in the token's `permissions` array via `ApiClient#check_permissions!`; it never checks `stack_id` [4](#0-3) . The stack-scope restriction is therefore enforced only by the `stacks` helper in `BaseController`, which `CCMenuController` deliberately bypasses.

### Finding Description
This is the same accounting/binding-mismatch class as the reported issue (a value the system trusts as "already accounted for/authorized" is not the value actually used at the point of effect). Here the equality that should hold is:

`stack authorized by ApiClient.stack_id == stack touched by Api::CCMenuController#show`

Before the attacker's request: an admin creates an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (a legitimate, supported scoping mechanism verified by the test "an api client scoped to a stack will only see that one stack" [5](#0-4) ). The intended invariant is that this token can only read/act on Stack A through any API endpoint.

After the attacker's request: the holder of that Stack-A-scoped token calls `GET /stacks/:stack_id/ccmenu.xml?token=<token>` with `:stack_id` pointing to Stack B (any other stack in the installation). `CCMenuController#authenticate_api_client` authenticates the token via `ApiClient.authenticate(params[:token])` [6](#0-5) , `require_permission :read, :stack` passes because the token does have `read:stack` in its permission list, and `stack` then resolves Stack B directly via `Stack.from_param!`, completely ignoring `current_api_client.stack_id`. The controller renders Stack B's CCMenu project status (latest deploy/rollback, build status, name) to a caller who was only ever authorized for Stack A.

### Impact Explanation
This breaks the deployment-trust binding between "the stack an API token authorizes" and "the stack it actually touches," exactly the class of accounting/scope mismatch called out in the reported bug (debt tracked at one scale, spent at another). The result is a High-severity unauthorized read of stack state (deploy/rollback history, build status, stack name) across tenant/repository boundaries using a token that was explicitly scoped away from that stack. Confidentiality of deploy state, environment names, and stack existence is exposed cross-repository without any repository write access or privileged account being required by the attacker.

### Likelihood Explanation
Likelihood is high for any installation using scoped `ApiClient` tokens (a documented, supported feature): any legitimate stack-scoped token holder (e.g., an external monitoring integration granted read-only access to one stack) can trivially enumerate other stacks' `stack_id`/param and pull their CCMenu status just by changing the URL path parameter — no additional secret or privilege escalation needed, since the check is a simple `permissions.include?` test that is scope-agnostic and the resolver method bypasses scoping entirely.

### Recommendation
Make `Api::CCMenuController#stack` use the same scoped resolution as the rest of the API (`stacks.from_param!(params[:stack_id])`, using `Api::BaseController#stacks`) instead of resolving against the unscoped `Stack` model, so the `ApiClient#stack_id` restriction is enforced consistently everywhere a scoped token is accepted.

### Proof of Concept
1. As an admin, create an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (e.g., via the API clients UI/`ApiClient.create!(creator:, name:, permissions: ['read:stack'], stack_id: stackA.id)`).
2. Confirm scoping works normally: `GET /api/stacks?token=<token>` returns only Stack A (matches the existing scoping test) [5](#0-4) .
3. Call the CCMenu endpoint for a different stack B that the token was never granted: `GET /<ownerB>/<repoB>/<envB>/ccmenu.xml?token=<token>` (routed to `Api::CCMenuController#show`).
4. Observe the request succeeds with HTTP 200 and returns Stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, etc.), because `stack` in `app/controllers/shipit/api/ccmenu_controller.rb:29-31` resolves via unscoped `Stack.from_param!` and `check_permissions!` never inspects `stack_id`.
