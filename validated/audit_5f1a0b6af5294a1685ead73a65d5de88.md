### Title
Unhandled TypeError on stale `storage.assocStableUnits[trigger.unit]` cache entry crashes the node during AA-trigger execution - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `handleTrigger()` dereferences `storage.assocStableUnits[trigger.unit].count_aa_responses` without checking that the cache entry still exists, even though the sibling code path in `handlePrimaryAATrigger()` explicitly guards against exactly this condition. `storage.js`'s `shrinkCache()` can delete a unit's entry from `assocStableUnits` concurrently with pending AA-trigger execution because the two operations are protected by different mutex keys (`'write'` vs `'aa_triggers'`). If an attacker can make the `aa_triggers` queue lag far enough behind the current MCI, the stabilized trigger unit gets evicted from the in-memory cache before `handleTrigger()` runs the check, causing an uncaught `TypeError` that is analogous to the FreeRDP report's pattern of using a reference to state that was already freed/invalidated by a concurrent close/cleanup path.

### Finding Description
`handlePrimaryAATrigger()` reads the AA trigger from the `aa_triggers` DB table and, after processing, defensively checks the in-memory cache: [1](#0-0) 
```
104|			let objUnitProps = storage.assocStableUnits[unit];
105|			if (!objUnitProps)
106|				throw Error(`handlePrimaryAATrigger: unit ${unit} not found in cache`);
```
This shows the code is aware that `storage.assocStableUnits[unit]` can become `undefined` for a unit still being processed via the `aa_triggers` table.

However, earlier in the very same trigger's execution path, inside `handleTrigger()`, the same cache is dereferenced **without** any existence check: [2](#0-1) 
```
1860|			// skip this check for dry-run which uses genesis unit as trigger unit
1861|			if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
1862|				return bounce('a second primary trigger from the same unit is not allowed');
```
If `storage.assocStableUnits[trigger.unit]` is `undefined` at this point, `.count_aa_responses` throws a `TypeError`, which is not caught anywhere in this call chain (`handleTrigger` is invoked from deeply nested `db.query`/`conn.query` callbacks with no surrounding try/catch or domain).

The cache entry can be invalidated concurrently by `storage.shrinkCache()`, which runs on a `setInterval` every 5 minutes and evicts `assocStableUnits[unit]` for any unit whose `main_chain_index` is older than `top_mci` (last_stable_mci minus `COUNT_MC_BALLS_FOR_PAID_WITNESSING` minus 10): [3](#0-2) 

Critically, `shrinkCache()` acquires the `"write"` mutex: [4](#0-3) 
while AA trigger execution (`handleAATriggers`) is serialized only under the **different** mutex key `'aa_triggers'`: [5](#0-4) 
Because these are distinct mutex keys, `shrinkCache()` is not blocked by in-flight AA trigger processing (and vice versa), so the two can race.

`aa_triggers` rows are inserted whenever a unit is stabilized and its message triggers an AA, and they are processed strictly sequentially under `mutex.lock(['aa_triggers'])`. Any user (unprivileged unit poster / AA trigger sender) can post many units whose stabilization schedules AA triggers faster than `handleAATriggers()` can drain them (each trigger execution does multiple sequential DB round trips and formula evaluation). If the queue backlog grows large enough that a still-unprocessed trigger's originating unit falls behind `top_mci`, `shrinkCache()`'s periodic timer will delete that unit from `assocStableUnits` while it is still sitting, unprocessed, in the `aa_triggers` table — mirroring the CVE's "async completion referencing state freed by a concurrent close path" pattern.

### Impact Explanation
When the race is hit, `handleTrigger()` throws an unguarded `TypeError` deep inside an asynchronous callback chain that has no exception handling, crashing the Node.js process. Because AA-trigger execution is mandatory for advancing/confirming the network's state (it runs synchronously as part of `writer.saveJoint`'s stabilization flow, see `writer.js:715-774`), a crash here halts the affected node's ability to process new stabilized units and their AA responses — i.e., "network unable to confirm new units" for that node. If exploited against enough full nodes/hubs simultaneously (all running the same public logic, reachable by any unprivileged unit poster who can post enough units/AA triggers to build the backlog), it can degrade network-wide unit confirmation, matching the FreeRDP bug's `VA:H` (availability) profile.

### Likelihood Explanation
Reaching the race requires the attacker to sustain a large backlog in the `aa_triggers` queue (on the order of `COUNT_MC_BALLS_FOR_PAID_WITNESSING + 10` main-chain indexes, i.e. a substantial and sustained flood of AA-triggering units) so that `shrinkCache()`'s 5-minute timer fires while a specific trigger is still queued. This is plausible under sustained flooding by an unprivileged user (posting many units that trigger AAs, e.g. cheap AAs with minimal bounce fees), but it is not a single-unit, always-reachable trigger — it depends on the relative timing of a periodic background job versus queue depth, which is somewhat probabilistic and timing-dependent (unlike a fully deterministic UAF).

### Recommendation
Add the same defensive check used in `handlePrimaryAATrigger()` before dereferencing `storage.assocStableUnits[trigger.unit]` in `handleTrigger()`:
```js
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir) {
    const objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
    if (!objTriggerUnitProps)
        throw Error(`handleTrigger: trigger unit ${trigger.unit} not found in cache`); // or handle gracefully via DB read-through
    if (objTriggerUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
        return bounce('a second primary trigger from the same unit is not allowed');
}
```
Additionally, consider having `shrinkCache()` and `handleAATriggers()` share the same mutex (or have `shrinkCache()` avoid evicting units that still have pending rows in `aa_triggers`) to eliminate the underlying race rather than only guarding the symptom.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live node/test harness):
1. Deploy an AA with a very low `bounce_fees.base` so trigger execution is cheap and fast to queue.
2. Flood the network with many units addressed to this AA over a period spanning multiple main-chain advances, faster than `handleAATriggers()` (serialized on `mutex.lock(['aa_triggers'])`) can drain the `aa_triggers` table, so that the backlog depth in MCI terms exceeds `COUNT_MC_BALLS_FOR_PAID_WITNESSING + 10`.
3. Let the process run past a 5-minute `shrinkCache()` tick (`storage.js:2296`) while some old trigger units are still unprocessed in `aa_triggers`.
4. When `handleAATriggers()` finally reaches one of the now-evicted trigger units and calls `handleTrigger()`, the line `storage.assocStableUnits[trigger.unit].count_aa_responses` (`aa_composer.js:1861`) throws `TypeError: Cannot read properties of undefined`, which propagates unguarded and crashes the node process, halting stabilization/AA processing on that node.
