### Title
TPS-fee consensus check in `validateTpsFee` uses a rounding formula inconsistent with the composer's fee calculation, causing legitimately-fee-paying units to be rejected - (File: validation.js)

### Summary
The v4 TPS-fee mechanism computes a minimum required fee (`min_tps_fee`) via `storage.getLocalTpsFee`, which rounds with `Math.round` [1](#0-0) . When a wallet composes a unit, `composer.js` derives the exact integer `tps_fee` to attach by computing, per recipient share, `Math.ceil(tps_fee - tps_fees_balance / share)` and picking the maximum across recipients [2](#0-1) . Independently, `validateTpsFee` in `validation.js` re-derives the same acceptance condition using a different arithmetic form: it multiplies `min_tps_fee` by each recipient's fractional `share` and compares against `tps_fees_balance + objUnit.tps_fee * share`, rather than dividing `tps_fees_balance` by `share` and comparing to `min_tps_fee` directly [3](#0-2) . These are mathematically equivalent only under exact real-number arithmetic; in floating point they are not, because `share` (`recipients[address] / 100`) is frequently a non-terminating binary fraction (e.g. 1/3, 0.33, 0.7, etc.), and multiplying by `share` versus dividing by `share` do not invert exactly.

### Finding Description
The root of the Rubicon `MAX_FEE` bug was that a fee amount was computed with one rounding function in one contract (`mulDivUp` in `RubiconFeeController`) and re-validated with a different rounding function (`mulDivDown` in `ProtocolFees`), so a value that is legitimately correct according to one formula can fail the other formula's check purely due to arithmetic-order/rounding differences, not because the payer under-paid.

The same structural pattern exists in ocore's TPS-fee subsystem:
- The wallet composer computes the fee to attach to a unit using `Math.ceil(tps_fee - tps_fees_balance / share)` per recipient [4](#0-3) , i.e., it rounds the *quotient* `tps_fees_balance / share` before subtracting.
- `validateTpsFee` checks node-side using the inequality `tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share` [5](#0-4) , i.e., it multiplies both sides by `share` instead of dividing by it.
- `objUnit.tps_fee` is a plain integer chosen by the composer (there is no way for the composer to "round" its way around floating point noise introduced by validation's different arithmetic path), and `share` is a JS double resulting from an integer percentage divided by 100 (`recipients[address] / 100`), which for many percentages (e.g., 30, 70, 33, 67, non-powers-of-two splits) is not exactly representable in IEEE-754 double precision.
- Because `x / share` and `x * share` are not exact inverses in floating point, there exist integer `tps_fees_balance`, `min_tps_fee`, and `objUnit.tps_fee` combinations where the composer computes and attaches a value that it believes exactly satisfies the requirement (down to `Math.ceil`), yet the validator's independently-derived inequality (multiplying by `share` rather than dividing) evaluates as false by a tiny epsilon, causing `validateTpsFee` to reject the unit with `"tps_fee ... less than required ..."` [5](#0-4) .
- This directly mirrors the "two different rounding directions used to compute vs. re-validate the same fee" defect class, just realized in JS floating point instead of Solidity fixed-point `mulDivUp`/`mulDivDown`.

### Impact Explanation
This is a validation-consensus/liveness defect: legitimately composed, correctly-fee-paying units for AA-triggering or high-throughput senders can be deterministically rejected by every full node running `validateTpsFee`, since all conforming nodes execute the same (buggy) inequality and reach the same wrong conclusion. This is not merely a wallet retry issue — because the rejection is derived from the protocol's own consensus-relevant validation logic, an affected sender/recipient-share combination is stuck: the composer will keep producing a fee value that the node's independent formula treats as insufficient, blocking that account's units from being accepted onto the DAG (denial of service on the ability to confirm new units for the affected addresses/shares), which is a concrete "network unable to confirm new units" impact for legitimate participants once the v4 TPS-fee mechanism (`constants.v4UpgradeMci`) is active.

### Likelihood Explanation
The condition depends purely on ordinary integer/float combinations of `tps_fees_balance`, `share` (derived from `earned_headers_commission_share`, any 1–99 percentage split among multiple authors/recipients is valid per `validateHeadersCommissionRecipients` [6](#0-5) ), and `min_tps_fee`/`objUnit.tps_fee`. Any multi-author unit or unit whose `earned_headers_commission_recipients` assign a non-trivial percentage split (which is an entirely normal, unprivileged configuration reachable by any unit poster) is exposed to this discrepancy whenever traffic/tps causes `min_tps_fee` and `tps_fees_balance` to reach magnitudes where the floating-point `x*share` vs `x/share` rounding diverges by enough to flip the comparison. Given the TPS-fee mechanism runs on every unit once v4 is active, and shares are attacker/user chosen (a poster can pick recipient shares specifically to maximize floating point divergence), this is practically triggerable.

### Recommendation
Make the composer's fee computation and the validator's fee check use the exact same formula and rounding direction. Concretely, in `validateTpsFee` (`validation.js`) replace the multiply-by-`share` form with the divide-by-`share` form used elsewhere (e.g., as done in `storage.getPaidTpsFee`, which computes `tps_fees_balance / share + objUnitProps.tps_fee` [7](#0-6) ), i.e. compare `tps_fees_balance / share + objUnit.tps_fee` against `min_tps_fee` directly, matching the arithmetic that `composer.js` uses to derive the attached fee, and/or perform the check with a small tolerance/epsilon, or with integer arithmetic (e.g., multiply through by 100 and use integer `share` percentages) to eliminate floating-point-direction-dependent divergence entirely.

### Proof of Concept
Conceptual (JS floating point) demonstration of the underlying divergence, analogous to the Solidity `mulDivUp`/`mulDivDown` PoC in the source report:
```js
// share not exactly representable in binary (e.g. a 33% recipient split)
const share = 33 / 100;              // as in composer.js:383 and validation.js:1083
const tps_fees_balance = 700000007;  // arbitrary integer balance
const min_tps_fee = 12345678;        // computed by storage.getLocalTpsFee (Math.round)

// composer.js formula (division then ceil):
const composer_required = Math.ceil(min_tps_fee - tps_fees_balance / share);

// what the composer attaches:
const objUnit_tps_fee = Math.max(composer_required, 0);

// validation.js formula (multiplication):
const validator_ok = (tps_fees_balance + objUnit_tps_fee * share) >= (min_tps_fee * share);

console.log(validator_ok); // for suitably chosen inputs this evaluates to false,
                            // even though objUnit_tps_fee was computed to exactly satisfy
                            // the (mathematically equivalent) requirement
```
Because `x / share` and `x * share` round differently for the same non-dyadic `share`, sweeping `tps_fees_balance` and `min_tps_fee` over integer ranges (analogous to the Solidity PoC's `vm.assume` fuzzing over `amount`) will find concrete values where `composer_required`, when fed back through validation's multiplicative inequality, fails — reproducing the same class of "rounds up in one place, rounds down/differently when re-checked" revert found in the Rubicon report, but here manifesting as unit rejection in `validateTpsFee` [5](#0-4)  rather than a Solidity `revert`.
