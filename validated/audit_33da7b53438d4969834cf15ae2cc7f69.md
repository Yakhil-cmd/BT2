### Title
Cross-organization webhook signature confusion allows escalation into `Shipit.github_teams` via `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` records solely by the numeric `github_id` in the webhook payload, with no check that the payload's organization matches the `Team#organization` already stored. Because webhook signature verification is scoped per-organization but the team lookup is not, an attacker who owns a second, legitimately-configured GitHub organization can send a genuinely signed `membership` webhook from their own org that mutates a `Team` belonging to a different, victim organization.

### Finding Description
The broken binding is: `repository_owner` (the org whose `webhook_secret` verified the request, derived from `params.dig('organization','login')` in `app/controllers/shipit/webhooks_controller.rb` lines 25/61) MUST equal `Team#organization` for the record subsequently mutated by the handler — but nothing enforces this.

`WebhooksController#verify_signature` [1](#0-0)  resolves `Shipit.github(organization: repository_owner)` from the payload's own `organization.login` and verifies the signature against that org's configured secret. Since the attacker owns `attacker-org` with a real, correctly configured GitHub App/`webhook_secret`, this verification legitimately succeeds for a payload the attacker fully controls.

`MembershipHandler#process` then calls `find_or_create_team!`, which does: [2](#0-1) 
`Team.find_or_create_by!(github_id: params.team.id)` — the lookup key is `github_id` only. There is no `where(organization: params.organization.login)` clause. If a `Team` row already exists for `victim-org/admins` with that `github_id` (created earlier through the normal, legitimate flow, e.g. via `Team.find_or_create_by_handle` [3](#0-2) ), the attacker's payload — signed only by `attacker-org`'s secret — finds and returns that exact victim `Team` object. The handler then executes `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , adding the attacker's own GitHub login as a member of the victim team.

`User#authorized?` grants full application access based purely on team membership, independent of organization: [5](#0-4) 
Since the mutated `Team` is configured in `Shipit.github_teams`, the attacker's `User#authorized?` becomes `true`.

None of the existing guards catch this: `verify_signature` only checks that the payload was signed by *some* legitimately configured org, not that it's the *correct* org for the resource being mutated; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in the handler only validates payload shape, not org/team ownership; there is no `require_permission!` or org-equality check anywhere in `MembershipHandler`.

### Impact Explanation
A single forged-but-legitimately-signed webhook from an attacker-controlled organization lets the attacker add themselves (or any GitHub login they control) as a member of a pre-existing `Team` that happens to share a `github_id` collision path is not even required — the attacker only needs the victim team's already-known `github_id` (team IDs are visible via GitHub's API/UI) to target it precisely. This directly escalates the attacker into `Shipit.github_teams` authorization, granting full Shipit application access (`User#authorized?` == true) — matching the High/Critical impact category "escalation into `Shipit.github_teams` authorization." The attack is repeatable against any victim team whose numeric `github_id` is known, is not limited to a single tenant, and works across any pair of organizations configured on the same Shipit instance.

### Likelihood Explanation
Preconditions are realistic for any multi-tenant Shipit deployment: `Shipit.github_organizations` > 1 (multiple GitHub Apps configured), a `Team` row for the victim org already existing (created through normal onboarding), and that team listed in `Shipit.github_teams`. The attacker only needs to control their own GitHub organization (freely creatable) with its own registered GitHub App/webhook, and know the victim's team `github_id` (obtainable via GitHub's public/team APIs). No Shipit secrets, sessions, or privileged roles are required — exactly matching the stated attacker capability of "any internet user who can send HTTP requests... including POST /webhooks" once they own a configured org.

### Recommendation
Scope the `Team` lookup by both `github_id` and organization, and reject/no-op when the payload's organization does not match the existing record's organization:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team && team.organization != params.organization.login
    raise ArgumentError, "Team #{params.team.id} organization mismatch"
  end
  team || Team.create!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```
More generally, verify that `repository_owner`/`params.organization.login` matches the resource's owning organization before any mutation in every multi-org webhook handler, not just signature validity.

### Proof of Concept
Minitest plan (in `test/models/webhooks/handlers/membership_handler_test.rb`-style, or via `WebhooksController#create`):
1. Fixture: create `Team` `t = Team.create!(github_id: 999, organization: 'victim-org', slug: 'admins', ...)`; add `t` to `Shipit.github_teams` config (or stub `Shipit.github_teams` to include `t`).
2. Build payload: `{ action: 'added', team: { id: 999, name: 'admins', slug: 'admins', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'attacker' } }`.
3. Stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (simulating a genuinely signed attacker webhook — no Shipit/GitHub secret needed for the stub, only demonstrating the verified-but-wrong-org path).
4. POST to `WebhooksController#create` with header `X-Github-Event: membership` and the above body.
5. Assert: `Membership.exists?(user: User.find_by(login: 'attacker'), team: t)` is `true` — i.e., a record was written for `victim-org`'s team though only `attacker-org`'s secret verified the request (the equality `repository_owner == t.organization` is false: `'attacker-org' != 'victim-org'`, yet the mutation succeeded).
6. Assert: `User.find_by(login: 'attacker').authorized?` is `true`, proving escalation into `Shipit.github_teams`.
