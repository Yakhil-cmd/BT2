### Title
Cross-Organization Webhook Forgery via Mismatched Signature-Key Selection and Target Repository Fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-tenant Shipit deployment (multiple GitHub Apps/organizations configured under `secrets.github`), the webhook signature is verified using a secret selected by the **`repository.owner.login`** field of the untrusted payload, but the code that determines **which repository/stack is actually acted upon** reads a *different* field — **`repository.full_name`**. Nothing enforces that these two fields refer to the same organization. An attacker who legitimately controls one configured organization's GitHub App/webhook secret can therefore forge a signed payload whose `repository.owner.login` matches their own org (so it passes signature verification with their own secret) while `repository.full_name` points at a completely different org/repo hosted on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` selects the app/secret to validate against using an attacker-controlled field: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` performs a per-organization secret/config lookup keyed exactly on that field, and this multi-org schema is a documented, supported configuration: [3](#0-2) 

Meanwhile, every webhook `Handler` determines the stack(s) to act on using a **separate** field of the same untrusted, attacker-fully-controlled JSON body: [4](#0-3) 

Because `request.raw_post` is HMAC-signed as a whole, an attacker only needs to know **one** organization's `webhook_secret` (e.g., their own org, which they legitimately administer as a Shipit tenant) to produce a validly-signed payload with an arbitrary `repository.full_name`/`repository.owner.login` combination. The verification step trusts `repository.owner.login` to pick the key, and the signature check only proves "signed with OrgX's secret" — it does not prove the payload actually originated from a real GitHub event for OrgX's repository, nor that `full_name` is consistent with `owner.login`. The equality this breaks is:

`organization whose secret authenticated the request` == `organization/repository that Shipit writes to as a result of processing that request`

Before the attacker's request, these are implicitly assumed equal (as they always are for genuine GitHub-originated webhooks). After a forged request, they can diverge arbitrarily, since the attacker fully controls the JSON body content, subject only to knowing one org's `webhook_secret`.

Concretely, `StatusHandler` (state) and `PushHandler`/`CheckSuiteHandler` resolve target stacks via `Handler#stacks`/`#repository_name`, which uses `repository.full_name` — not the org used for signature verification: [5](#0-4) 

This lets a tenant with legitimate access to OrgX's Shipit webhook secret forge, for example, a `status` event claiming `state: success` for an arbitrary commit SHA on a stack belonging to OrgY (a different, unrelated tenant on the same Shipit instance), as long as the request is signed with OrgX's secret while `repository.owner.login` is set to `"OrgX"` and `repository.full_name` is set to `"OrgY/victim-repo"`.

### Impact Explanation
Forged commit statuses/check-suite refreshes on another organization's stack can satisfy CI-gating conditions used by the merge queue and deploy checklist (`MergeRequest#any_status_checks_failed?`, `#all_status_checks_passed?`, `Stack#merge_status`) — see: [6](#0-5) 
This can cause an unauthorized merge (`MergeRequest#merge!` invoked from the merge queue processing job) or unblock a deploy for a repository the attacker does not control — a cross-tenant, cross-repository write and potentially an unauthorized merge/deploy, matching the report's Critical-impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge"). This is only exploitable in the documented multi-organization configuration (`docs/setup.md` "Using Multiple Github Applications"), where distinct orgs/tenants each have distinct webhook secrets but share one Shipit instance/database.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub Apps/organizations (a documented, supported feature), and (2) the attacker legitimately administers/knows the `webhook_secret` for at least one configured organization (e.g., because they are a legitimate customer/tenant of that org, or because that org's secret otherwise leaked — a realistic scenario in a shared/multi-tenant Shipit deployment). No GitHub session, Shipit session, or `ApiClient` token is needed — only the ability to send an HTTP POST to `/webhooks` with a correctly computed HMAC. This is a moderate-likelihood, high-impact scenario specific to multi-org deployments.

### Recommendation
After verifying the signature for organization `O` (derived from `repository.owner.login`/`organization.login`), re-validate that `repository.full_name` (and any other repository-identifying fields used by handlers) actually belongs to organization `O` before dispatching to handlers — e.g., reject the webhook (422) if `repository.full_name.split('/').first.casecmp(O) != 0`. Alternatively, bind handlers to look up stacks scoped by the verified organization rather than trusting `repository.full_name` alone.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgX` (attacker-administered) and `OrgY` (victim), each with a distinct `webhook_secret`, per `docs/setup.md` "Using Multiple Github Applications".
2. Attacker crafts JSON body:
```json
{
  "repository": {"owner": {"login": "OrgX"}, "full_name": "OrgY/victim-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  "branches": [{"name": "master"}]
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgX_webhook_secret, raw_body)>` and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"OrgX"`, fetches OrgX's `GitHubApp`, and `verify_webhook_signature` succeeds (valid HMAC for OrgX's secret).
5. `StatusHandler` (via `Handler#stacks`/`#repository_name`) resolves the target stack using `repository.full_name` → `"OrgY/victim-repo"`, and creates/updates a `Status` record for that commit on the victim's stack — a write to a repository the attacker does not administer, potentially satisfying CI gating used for merges/deploys on `OrgY`'s stack.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
