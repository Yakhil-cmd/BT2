## Title
Stack-scoped `ApiClient` tokens bypass their stack restriction in `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::BaseController` restricts a stack-scoped `ApiClient` (one with a non-nil `stack_id`) to only ever resolve stacks through the `stacks` scope, so `stack` becomes `stacks.from_param!(params[:stack_id])`, i.e. `Stack.where(id: current_api_client.stack_id).from_param!(...)`. [1](#0-0)  `Api::CCMenuController`, however, overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, without going through the `stacks` scope. [2](#0-1)  This breaks the binding "stack a token authorises == stack it touches": permission checking (`require_permission :read, :stack`) only validates the permission string via `ApiClient#check_permissions!`, never the `stack_id` restriction. [3](#0-2) 

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`), as seen in the `here_come_the_walrus` fixture, which is scoped to the `shipit` stack yet only holds `read:stack` permission. [4](#0-3)  The intended invariant, enforced in `BaseController#stacks`/`#stack`, is that such a client can only resolve/read the one stack it is bound to. [1](#0-0) 

`CCMenuController` is reachable with the same bearer/basic-auth token (it falls back to `super` from `BaseController#authenticate_api_client` when no `?token=` param is given) and requires only `read:stack`. [5](#0-4) [6](#0-5)  But its private `stack` helper does `Stack.from_param!(params[:stack_id])` — an unscoped, global lookup — instead of the inherited `stacks.from_param!(params[:stack_id])`. [7](#0-6)  `check_permissions!` never receives or checks the requested `stack_id`; it just verifies that `"read:stack"` is present in the client's `permissions` array. [3](#0-2) 

Consequently, an `ApiClient` token that is deliberately scoped to Stack A (holding only `read:stack`, with no access to Stack B intended) can call `GET /api/stacks/:stack_id/ccmenu` with `stack_id` set to Stack B, and the controller will happily render Stack B's build/deploy status (`stack.deploys_and_rollbacks.last`) via the unscoped lookup.

### Impact Explanation
This is an unauthenticated-read-of-stack-state issue for holders of a legitimately-issued but narrowly-scoped API token: the "stack a token authorises" (Stack A only) is broken against the "stack it touches" (any stack in the system) equality. It allows a client that was only ever meant to see one repository/environment's build status to enumerate and read the CI/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc., rendered via `shipit/ccmenu/project`) of every other stack in the Shipit instance. This matches the High-severity class "unauthenticated read of stack state, task streams or deploy output" defined for this engine.

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token (a routine, low-privilege credential explicitly designed to be handed out for narrow purposes, e.g. CCMenu integration, as generated by `CCMenuUrlController#client`) can trigger this simply by requesting the CCMenu endpoint for a different `stack_id` — no elevated privileges, no additional secrets, and no race condition are required. Likelihood is high given the endpoint is unauthenticated beyond the token itself and the misuse requires only changing a path parameter.

### Recommendation
Change `Api::CCMenuController#stack` to use the inherited, scope-respecting resolver instead of the raw model:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This reuses `BaseController#stacks`, which already applies the `current_api_client.stack_id?` restriction, so a stack-scoped token cannot resolve stacks outside its own scope. More generally, any controller/action that overrides `BaseController#stack` or performs its own `Stack.find`/`Stack.from_param!` should be audited to guarantee it also passes through the `stacks` scope, or `ApiClient#check_permissions!` should be extended to also validate the target stack against `stack_id` for every action, not just those relying on the default `stack` helper.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to Stack A with only `read:stack` permission (mirrors fixture `here_come_the_walrus`, bound to stack `shipit`). [4](#0-3) 
2. Using that client's `authentication_token` (Basic Auth) or `?token=` query param, request `GET /api/stacks/<owner>/<repo>/<environment-of-stack-B>/ccmenu` for a different stack B that the client should not have access to.
3. `authenticate_api_client` accepts the token (it's a valid `ApiClient`). [5](#0-4) 
4. `require_permission :read, :stack` only checks `permissions.include?('read:stack')`, which is true, regardless of `stack_id`. [3](#0-2) 
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` (Stack B), bypassing the `stacks` scope that would have restricted it to Stack A. [7](#0-6) 
6. The response renders Stack B's build/deploy status, which the token holder was never authorized to see.
