### Title
Formula (Template) Re-Injection in Dynamically Generated AA Definitions via `app='definition'` Payloads - (File: aa_composer.js)

### Summary
The AA composer's `replace()` function walks an Autonomous Agent's message tree and evaluates any string that is fully wrapped in `{...}` as an oscript formula, substituting the computed result back into the message. When the resulting value looks like a *formula string itself*, the composer explicitly rejects this for dynamically-computed **object keys** (`"calculated value of ... looks like a formula again"`), but performs no equivalent check for computed **values**. This is intentionally exploited by the platform's own "dynamic AA generation" feature (`app: 'definition'` messages), where an AA author deliberately double-wraps a formula (`"{'{...}'}"`) so the generated child AA definition contains a live formula that is evaluated again, in the child AA's own trigger context, the next time it runs. If the outer (author-authored) formula concatenates unescaped `trigger.data`/`trigger.address` content while building that inner `{...}` template, an attacker who posts the triggering unit can smuggle arbitrary, unescaped oscript formula code into a field of the dynamically-created child AA that the parent author intended to hold plain data — analogous to reflecting attacker input into a server-side template that later gets rendered/executed.

### Finding Description
`aa_composer.js` documents the mechanism explicitly: [1](#0-0) 
"note that app=definition is also replaced using the current trigger and vars, its code has to generate `{}`-formulas in order to be dynamic" — meaning AA authors intentionally produce new `{...}`-wrapped formula strings as literal values by writing double-brace expressions such as `"{'{trigger.address}'}"`.

The `replace()` function evaluates any string that fully matches the formula pattern: [2](#0-1) 
For **values** (the branch above), once the inner formula evaluates, the result `res` is assigned directly with `assignField(obj, name, res)` with **no check** on whether `res` itself again looks like a formula.

Contrast this with the **key**-substitution branch a few lines above, where the platform explicitly guards against exactly this class of re-injection: [3](#0-2) 
`if (getFormula(res) !== null) return cb({message: "calculated value of " + name + " looks like a formula again: " + res, xpath});`

This asymmetry means: if an AA author writes a nested AA template (embedded via an `app: 'definition'` message) where a message field is built as `"{'{' || trigger.data.x || '}'}"` (or similar concatenation that folds unsanitized trigger data into the inner `{...}` body), the computed value that ends up stored in the generated child AA's on-chain definition is a full, live oscript formula whose source includes attacker-controlled bytes. Because this generated definition still must pass `aa_validation.validateAADefinition` when the child-defining unit is accepted: [4](#0-3) 
the injected formula is syntactically constrained and complexity-limited, but it is fully evaluated inside the child AA's trust boundary (its own `balance[...]`, `state vars`, payment outputs, etc.) the next time that child AA is triggered — using the *new* trigger's context, not the context the parent author wrote the template under.

The existing test suite documents the exact re-evaluation semantics that make this reachable: [5](#0-4) [6](#0-5) 
Here `trigger_address: "{'{trigger.address}'}"` produces the literal string `"{trigger.address}"` which becomes a genuine field of the newly-created AA's `app: 'data'` message; when that new AA is later triggered by the forwarder's payment, `trigger_address` is filled with the *new* trigger's address (`forwarder_address`), proving the double-brace value is fully re-parsed and re-evaluated as oscript in a later, independent execution.

### Impact Explanation
If any AA author's dynamic-AA-generation code interpolates attacker-supplied `trigger.data` (or other externally influenced values) into the inner `{...}` body when constructing a nested `app: 'definition'` payload, a malicious trigger sender can inject arbitrary (though complexity-bounded and syntax-valid) oscript formula code into fields of the resulting child AA — e.g. payment `amount`/`address` expressions, `state` updates, or `bounce_fees`-adjacent logic — that the parent author intended to be inert data. Because the injected formula executes with the full authority of the child AA (its balance, state vars, and payment composition) the next time it is triggered, this can be leveraged to divert or drain AA funds, corrupt state variables, or force unintended payment outputs, i.e. concrete AA fund loss/freezing, which meets the impact bar for this analog.

### Likelihood Explanation
Reachability requires no privileged position: any address can post the triggering unit whose `trigger.data`/`trigger.address` feeds the vulnerable, author-written dynamic-definition formula, and can then post the follow-up unit that triggers the newly-created AA to realize the injected formula's effect. The prerequisite is that some deployed AA's author uses the platform's documented double-brace dynamic-definition pattern while concatenating unescaped external trigger data — a realistic and encouraged pattern for AA-factory-style contracts (as shown directly in the project's own test suite). The missing "looks like a formula again" safeguard for values (present only for keys) makes this a latent, systemic gap in the framework rather than a one-off application bug.

### Recommendation
Apply the same safeguard used for dynamically-computed key names to dynamically-computed **values** whenever they are destined for a nested `app: 'definition'` payload (or, more conservatively, whenever a formula's result is itself a string matching `getFormula(res) !== null`): reject the message/definition with an error such as "calculated value looks like a formula again" unless the field is explicitly documented/allowed to regenerate formulas (and even then, require an explicit escaping API rather than raw string concatenation) in `aa_composer.js`'s `replace()` function around lines 658-695.

### Proof of Concept
1. Deploy a "factory" AA whose `app: 'definition'` message builds a child AA payment message as:
   `outputs: [{address: "{trigger.address}", amount: "{'{' || 'balance[base]' || '}'}"}]` — i.e., an author who (mistakenly, but per the documented dynamic-definition pattern in [1](#0-0)  and demonstrated in [5](#0-4) ) concatenates externally-influenced content into the inner formula body instead of a fixed literal.
2. Replace the hard-coded `'balance[base]'` substring with a value derived from `trigger.data` supplied by the triggering unit's poster (e.g. `"{'{' || trigger.data.injected_formula || '}'}"`).
3. Post a triggering unit with `data.injected_formula = "balance[base]"` (or any other valid, complexity-bounded oscript expression) to the factory AA; the factory defines and deploys the child AA whose payment `amount` field is now literally `"{balance[base]}"`.
4. Trigger the child AA; per the semantics verified in [7](#0-6) , `replace()` re-evaluates `"{balance[base]}"` in the child AA's own execution context, causing it to pay out its entire balance rather than the amount the factory author intended, demonstrating attacker-controlled formula injection into a supposedly-fixed AA field.
