### Title
Asset Definer Can Unilaterally Freeze Existing Holders' Funds by Rewriting the `spender_attested` Attestor List - (File: `validation.js`)

### Summary
For any asset created with `spender_attested: true`, the asset's **definer** (the address that authored the `asset` message) retains a standing, single-authored, unlimited-frequency power to republish the list of trusted attestors via an `asset_attestors` message. Every payment validation of that asset re-reads only the *latest* attestor list (not the list in effect when a holder received their funds) to decide whether the spender is authorized. This lets the definer retroactively remove any existing token holder's attestor from the trusted list at any time after issuance, freezing that holder's already-received, unspent balance — with no consent or say from the affected holder. This mirrors the reported Splitter `addPayee`/`adjustShare` pattern: an administrative, owner-controlled parameter change unilaterally alters the economic rights of parties who already hold value in the system, and the team's stance in the original report ("this aligns with our expectations") suggests this kind of asymmetry is often treated as accepted design rather than fixed.

### Finding Description
An asset's `spender_attested` flag and its attestor list are asset-level settings set once at creation and thereafter editable only via `asset_attestors` messages restricted to the definer address: [1](#0-0) 

Critically, when validating who is allowed to spend the asset, `storage.readAsset` does not use the attestor list that was current at the time a specific output/holder was attested or funded — it always fetches whichever attestor-list unit is *stable and most recent*: [2](#0-1) 

That freshly-fetched `arrAttestorAddresses` is then intersected against the current payment's authors in `validatePayment`, and if the spending author is not attested, the payment is rejected outright: [3](#0-2) 

Because the check is always against the *current* list rather than a list fixed per-output at issuance/transfer time, the definer can, after holders already possess unspent balances of the asset, publish a new `asset_attestors` unit that drops those holders' attestations. From that point forward those holders can no longer move their existing balance — the exact "unclaimed value gets unilaterally re-parameterized by an administrative actor" pattern described in the external Splitter report, except here the effect is fund freezing rather than value dilution.

### Impact Explanation
This is reachable by any ordinary, unprivileged asset issuer (no special network privilege needed — anyone can define an asset with `spender_attested: true` and become its definer) and affects any counterparty who is later given/transacts in that asset. The impact falls squarely in the "AA/asset fund loss or freezing" category: existing holders' balances become permanently unspendable at the sole discretion of the definer, without any multi-party consent, timelock, or ability for holders to react before losing access. Unlike a bug the network would reject, this is consensus-valid behavior, so all nodes will agree the frozen holder cannot spend — it is a protocol-level authorization footgun baked into the `spender_attested` asset feature, not a client bug.

### Likelihood Explanation
Likelihood is high for any asset that opts into `spender_attested`: the capability is a first-class, always-available feature of the definer role (no special permission or unusual sequence of events is required — just publishing one more `asset_attestors` unit), and downstream token holders generally have no visibility mechanism forcing them to notice an attestor-list change before it takes effect against their existing balance.

### Recommendation
Consider decoupling "authorization to receive/hold" from "authorization to spend" so that once a holder receives an attested balance, later attestor-list changes by the definer do not retroactively strip their ability to spend it — e.g., snapshot/pin the attestor list applicable to an output at receipt time, or require that removed holders be given a grace/cooldown period or an explicit exit path before losing spend rights. At minimum, this should be clearly documented as a trust assumption of `spender_attested` assets so wallets/holders can treat the definer as a semi-trusted party capable of freezing their funds.

### Proof of Concept
1. Definer `D` creates asset `X` with `spender_attested: true` and an initial attestor list `[A]` (via the `asset` message processed in `writer.js`, lines around asset/`asset_attestors` insertion): [4](#0-3) 
2. `D` (or another eligible issuer) attests/authorizes address `A`, and `A` receives a payment of asset `X`, leaving `A` with an unspent output.
3. `D` submits a new `asset_attestors` message for asset `X` with a list that excludes `A`, e.g. `[B]`. This message is single-authored by `D` and passes `validateAttestorListUpdate` because `D` is `objAsset.definer_address`: [5](#0-4) 
4. `A` now attempts to spend the previously received output of asset `X`. `storage.readAsset` fetches the newest attestor list `[B]` (not `[A]` that was valid when `A` received funds): [6](#0-5) 
5. `validatePayment` finds `A` is not in `arrAttestedAddresses` and rejects the spend with `"none of the authors is attested"`, permanently freezing `A`'s balance until/unless `D` chooses to re-attest `A`: [3](#0-2)

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
