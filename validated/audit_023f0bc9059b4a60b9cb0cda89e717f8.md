### Title
Webhook signature is verified against an attacker-chosen organization while the mutated repository/commit is selected from an unrelated field, letting a foreign org's secret forge CI status for any stack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization's `webhook_secret` to validate a request against based on a field taken straight from the untrusted JSON body, but the handlers that actually perform writes (in particular `StatusHandler`) select the record to mutate using a completely different, also attacker-controlled field, without re-checking that it belongs to the org that authenticated the request.

### Finding Description
`verify_signature` resolves the signing organization purely from the request body: [1](#0-0) [2](#0-1) 

`repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`) is used to fetch `Shipit.github(organization: repository_owner)` and verify the HMAC with that specific organization's configured `webhook_secret`. Shipit explicitly supports one `webhook_secret` per organization in multi-org deployments: [3](#0-2) 

Once the signature check passes (using whichever org's secret matched the attacker-chosen `repository_owner`/`organization.login` value), the whole raw JSON body is dispatched to event handlers with no further binding to that organization: [4](#0-3) 

`StatusHandler`, which drives commit CI status, does not scope by repository or organization at all — it matches purely by commit SHA across the entire installation: [5](#0-4) 

Other handlers (`PushHandler`, `CheckSuiteHandler`) use `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a field independent from the `repository.owner.login`/`organization.login` field used for signature selection: [6](#0-5) [7](#0-6) [8](#0-7) 

The equality that must hold is: **organization whose `webhook_secret` authenticated the delivery == organization owning the repository/commit that gets written**. Because both the authenticating field and the acted-upon field are read from the same attacker-supplied JSON body, and are never cross-checked against each other, this equality can be broken by construction: an attacker who legitimately knows/controls one organization's `webhook_secret` (e.g., because they own an org that has the shared GitHub App installed) can sign a payload whose `repository.owner.login`/`organization.login` names their own org (so the secret lookup and HMAC check succeed) while embedding a `sha`, `repository.full_name`, or `check_suite.head_sha` belonging to a completely different organization's stack tracked by the same Shipit instance.

### Impact Explanation
This is a genuine cross-organization authentication/authorization boundary break, not a same-tenant issue: signature verification is meant to prove "this event really came from GitHub for organization X", but the code only proves "this request carries a valid HMAC for whichever org name the attacker put in the body", and no subsequent code re-derives or re-validates that the mutated resource belongs to that same org. Concretely, `StatusHandler` lets the attacker set `state: success` (or `failure`) on any commit `sha` in the whole Shipit install, regardless of organization, as long as they can produce a validly-signed body for *any* configured org. Since deploy/merge-queue safety logic in Shipit relies on commit CI status, forging a passing status for a victim organization's commit can enable code to be merged/deployed that never actually passed CI review — i.e., an unauthorized deploy/merge, which is explicitly a Critical-tier impact.

### Likelihood Explanation
Exploitability requires the attacker to possess (or be able to derive) a `webhook_secret` valid for *some* organization configured on the shared Shipit instance — a realistic bar in any genuinely multi-tenant deployment (Shipit's own docs describe configuring one App/secret per org on a single install), since an attacker can be a legitimate, low-trust member/owner of one of those orgs while targeting a different, higher-trust org's stack. No repository write access, session, or `ApiClient` token to the *victim* organization is required — only knowledge of a secret belonging to *any* org on the instance.

### Recommendation
After a signature is verified, re-derive and enforce that every field the handler uses to select a mutable record (`repository.full_name`, `commit.sha`'s owning stack/repository, `check_suite.head_sha`'s owning stack) actually belongs to the same organization/repository that was used to select the `webhook_secret` in `verify_signature`. In particular, `StatusHandler` should scope `Commit.where(sha: params.sha)` to commits whose stack's repository organization matches `repository_owner`, and `WebhooksController` should reject events where `repository.owner.login`/`organization.login` and `repository.full_name`'s owner segment disagree, rather than trusting either field independently.

### Proof of Concept
1. Attacker is a member of (or controls) `org-attacker`, which has the shared Shipit GitHub App installed with a known/leaked `webhook_secret` configured for `org-attacker` in this Shipit instance's multi-org config (`config/secrets.*.yml`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim-org's-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-attacker" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_of_org-attacker, body)` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, and the signature verifies successfully because the attacker legitimately knows that org's secret [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim organization's commit purely by SHA, with no org check — and creates a `success` status on it [5](#0-4) , letting the victim stack's deploy/merge-queue logic treat that commit as CI-green despite the request never having been authenticated for the victim's organization.
