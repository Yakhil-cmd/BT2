### Title
Stack-scoped API token bypasses its stack restriction on the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`ApiClient` records can be restricted to a single stack via `stack_id`, and `Api::BaseController#stacks`/`#stack` enforce that restriction by scoping lookups through `Stack.where(id: current_api_client.stack_id)` before resolving the `stack_id` param. [1](#0-0)  `Api::CCMenuController` overrides `#stack` to bypass this scoping entirely, resolving the stack directly from the global table. [2](#0-1)  This breaks the binding "the stack a token authorizes" == "the stack the token can touch": a token scoped to stack A can read CCMenu build-status data for any other stack B.

### Finding Description
`ApiClient#stack_id?` (via ActiveRecord attribute predicate) determines whether a token is scoped to a single stack. The generic API scoping logic enforces this:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

Every controller that relies on the inherited `#stack` method (e.g. `Api::StacksController`) is correctly restricted to the client's authorized stack(s). However `Api::CCMenuController` redefines `#stack` to query the unscoped `Stack` model directly:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller still declares `require_permission :read, :stack`, which only checks the client's `permissions` array (e.g. `read:stack`) — it does not check which specific stack the client is bound to. [4](#0-3)  `ApiClient#check_permissions!` performs only that permission-string check, with no notion of stack scope. [5](#0-4) 

As a result, any token holding `read:stack` (even one deliberately minted and scoped to a single, low-sensitivity stack via `stack_id`) can be replayed against `GET /api/:stack_id/ccmenu.xml` with an arbitrary `stack_id` value belonging to a different stack, and the controller will happily render that other stack's build/deploy status, defeating the purpose of scoping the token in the first place.

This is precisely the "token authorizes stack A" vs. "endpoint touches stack B" equality violation called out in the rules: `current_api_client.stack_id (== A)` should equal `stack.id` for every stack-scoped endpoint, but `CCMenuController#stack` makes `stack.id` independent of `A`.

### Impact Explanation
This grants unauthenticated read of stack state (deploy status/build outcome) to a token holder beyond the stack they were authorized for — the exact impact category "unauthenticated read of stack state, task streams or deploy output" (High) called out in the scope rules, since the CCMenu response exposes `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, etc. for any stack in the installation, not just the one the token creator intended to expose. [6](#0-5)  While this is a read-only disclosure rather than RCE/credential theft, it directly matches the High-severity "unauthenticated read of stack state" bucket, because the requester is not authenticated as a client for the target stack — only for a different, unrelated one.

### Likelihood Explanation
Likelihood is high given ease of exploitation: any holder of a valid `read:stack`-permissioned token (regardless of its `stack_id` restriction) simply substitutes an arbitrary `stack_id` in the URL — no additional credentials, signatures, or privilege are required, and `CCMenuUrlController` itself demonstrates that such stack-scoped-looking tokens are handed out to ordinary authenticated users for CI-status-badge integration purposes. [7](#0-6) 

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` and use the inherited, properly-scoped `Api::BaseController#stack`/`#stacks` methods so that a stack-restricted `ApiClient` cannot resolve stacks outside `current_api_client.stack_id`.

### Proof of Concept
1. Create (or have an admin create) two stacks, `stack-a` and `stack-b`.
2. Create an `ApiClient` scoped to `stack-a` (`stack_id = stack-a.id`) with permission `read:stack` — for example the flow used by `CCMenuUrlController#client`, or directly via `ApiClientsController#create` followed by setting `stack_id`.
3. Using that token's `authentication_token`, issue:
   ```
   GET /api/stack-b/ccmenu.xml?token=<token for stack-a>
   ```
4. Observe: the request succeeds (HTTP 200) and returns `stack-b`'s build/deploy status (`name`, `lastBuildStatus`, `lastBuildLabel`, etc.), even though the token was only ever authorized for `stack-a`, because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unconditionally instead of `stacks.from_param!(params[:stack_id])`.
