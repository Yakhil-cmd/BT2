### Title
Webhook signature verification binds to the payload's `repository.owner.login`/`organization.login` field while event handlers target the repository via the independent, uncorrelated `repository.full_name` field, allowing a webhook signed with one tenant's secret to write to another tenant's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

Every event `Handler` however resolves the repository/stack it will actually act on using a *different* field parsed from the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) 

Nothing cross-validates that `repository.owner.login` (used for signature/tenant selection) belongs to the same repository as `repository.full_name` (used for stack resolution and mutation, e.g. `PushHandler#process` → `stack.sync_github`). [4](#0-3) 

### Finding Description
Shipit supports hosting multiple GitHub organizations/Apps on a single engine instance, each with its own `webhook_secret`, keyed by organization login in `Shipit.github(organization:)`. [5](#0-4) 

The equality the engine is supposed to enforce is:
`organization whose secret validated the signature == organization that owns the repository the handler mutates`

In `verify_signature`, the "authenticating organization" is taken from `repository.owner.login` / `organization.login`: [1](#0-0) 

But `Handler#repository_name` (used by every concrete handler, e.g. `PushHandler`, status/check_suite/pull_request handlers, via `Handler#stacks`) resolves the target `Repository` from `repository.full_name`: [3](#0-2) 

These are two independently-controlled fields inside the *same* attacker-suppliable JSON body — the HMAC signature covers the raw bytes, but signature validation only proves "this body was signed with organization X's secret," not "the repository this body describes belongs to organization X." An entity that legitimately controls a GitHub App/webhook_secret for *any* organization configured on the shared Shipit instance (e.g. a different, unrelated tenant "OrgA") can compute a valid HMAC over a crafted body where `repository.owner.login = "OrgA"` (so `verify_signature` picks OrgA's own secret and passes) while `repository.full_name = "OrgB/victim-repo"` (a completely different tenant's repository). `Repository.from_github_repo_name` then resolves the victim's `Repository`/`Stack` by parsing `full_name` alone, with no relationship enforced between the two organizations. [6](#0-5) 

### Impact Explanation
Once the crafted, self-signed request passes `verify_signature`, any registered webhook handler runs against the victim stack:
- `push`: `PushHandler` triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stack with an attacker-chosen `after` SHA, forcing `GithubSyncJob` to run against a repository the attacker does not control. [4](#0-3) [7](#0-6) 
- `status`/`check_suite`/`deployable_status`-style events resolved through the same `Handler#stacks`/`repository_name` mechanism can write bogus commit statuses or deployability signals onto the victim repository's commits, which Shipit uses to gate whether a commit is safe to deploy. Forging a "success" status this way can make an unreviewed or failing commit appear deployable to legitimate, authorized deployers of the victim stack, which is an unauthorized-deploy-enabling condition.

This crosses the "organization authenticated vs. repository written" trust boundary called out as in-scope, and its worst realization (tricking the deploy-gating status into allowing a deploy of an attacker-influenced commit) falls under the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Requires the attacker to control a legitimate GitHub App/organization already configured on the same multi-tenant Shipit instance (i.e., they are a normal, unprivileged party with respect to the *victim* tenant, but a legitimate admin of their own unrelated tenant) — no session, `ApiClient` token, or the victim's `webhook_secret` is needed. The request is a direct HTTP POST to `/webhooks` with a self-computed HMAC, bypassing GitHub entirely. Likelihood is moderate: it depends on the engine being deployed multi-tenant (documented and supported configuration, see `config/secrets.development.shopify.yml`) and on the attacker's own org being one of the configured tenants.

### Recommendation
Cross-validate that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` before dispatching to handlers, or better, resolve the target `Repository`/`Stack` using the same trusted organization identifier that was used to select the `webhook_secret`, rather than trusting an independent, unauthenticated-relative-to-selection field from the payload.

### Proof of Concept
1. Attacker is an admin of `OrgA`, a GitHub organization/App already configured on the shared Shipit instance with its own `webhook_secret`.
2. Attacker crafts a JSON body: `{"ref": "refs/heads/master", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and sends `POST /webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully against `OrgA`'s secret. [1](#0-0) 
5. `PushHandler` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `OrgB`'s stack, despite the request never being authenticated for `OrgB`. [4](#0-3)

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
