### Title
Meta-transaction (`DelegateAction`/`NEP-366`) signatures omit a chain/network identifier, enabling cross-network signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The message hash signed by an account for a `DelegateAction` (meta-transaction, NEP-366/461) is built from a fixed `MessageDiscriminant` (NEP number + on/off-chain flag) plus the `DelegateAction` fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). No `chain_id`/`genesis_hash`/network identifier is mixed into the signed payload, so the same signature is valid on any nearcore-derived network (mainnet, testnet, a forked/cloned chain, or a network booted from an exported state snapshot) as long as the target account/access-key state matches.

### Finding Description
`SignedDelegateAction::verify()` / `VersionedSignedDelegateAction::verify()` hash the `DelegateAction` via `get_nep461_hash()`, which wraps it in a `SignableMessage` tagged only with a `MessageDiscriminant` (NEP number 366/611 plus on-chain/off-chain bit): [1](#0-0) [2](#0-1) 

The hashed struct itself carries no chain/network binding: [3](#0-2) [4](#0-3) 

Replay protection for a `DelegateAction` relies exclusively on the receiver's on-chain access-key nonce (`validate_delegate_action_key`), which is state that is local to a single chain: [5](#0-4) 

This mirrors exactly the structure of the reported Opera-Bridge bug: the signed payload binds to "batch"/state-derived fields but never to `block.chainid`/`address(this)` (contract/chain identity). In nearcore's case, any two networks that share account state and access-key nonces at the point of divergence — e.g. a hard fork, a testnet/sandbox bootstrapped from a mainnet state export, or a NEAR-based network cloned via the same genesis — will accept the identical `SignedDelegateAction` bytes as valid, because `verify()` never checks which chain it is running on.

### Impact Explanation
If a network is forked or cloned from an existing nearcore chain's state (a supported and used pattern, e.g. via `tools/mirror`'s genesis/state export utilities, or a testnet reset from mainnet state), a previously-signed but not-yet-executed `SignedDelegateAction`/`VersionedSignedDelegateAction` — signed once by a user for a relayer on chain A — remains a valid, executable meta-transaction on chain B, since the signature and hash contain nothing tying it to chain A. An attacker who can observe such a delegate action (broadcast to a relayer, held in a mempool, or exposed via any public relay) can resubmit it on the divergent network to execute the same authorized actions (e.g. transfers, `AddKey`, function calls) against the victim's account there, causing unauthorized state/balance changes exactly as in the referenced report's cross-bridge replay scenario. Because nonce state at the fork point is by construction identical on both chains, the nonce check in `validate_delegate_action_key` provides no protection in this scenario.

### Likelihood Explanation
Exploitation requires a scenario where two nearcore-derived networks share identical account/access-key state (a chain fork, or a network deliberately bootstrapped from another chain's state/genesis) and a not-yet-consumed signed delegate action is available to replay. This is a narrower precondition than a routine attack, but nearcore explicitly supports and documents tooling for exactly this kind of state migration/forking (see `tools/mirror`), which increases plausibility relative to a purely theoretical fork. It is not a "malicious validator/node" bug — it is exploitable by any unprivileged holder of a previously-signed delegate action once such a divergent network exists.

### Recommendation
Bind the meta-transaction signature to a network/chain identity, analogous to adding `block.chainid` in the reported fix. Concretely, incorporate a chain-specific value (e.g. `genesis_hash`/`chain_id` from `ChainId`/genesis config, akin to how `SignedTransaction` already uses `block_hash` for freshness) into the `SignableMessage`/`DelegateAction`/`DelegateActionV2` payload that is hashed and signed, so that a signature produced for one network cannot be replayed on a different (forked or cloned) network even when account/access-key state is identical.

### Proof of Concept
1. On chain A, user Alice signs a `SignedDelegateAction` (`DelegateAction{ sender_id: alice, receiver_id: bob, actions: [Transfer], nonce: N, max_block_height: H, public_key: pk }`) via `SignedDelegateAction::sign`, intended for relayer R to submit — see the signing pattern in `core/primitives/src/action/delegate.rs:92-95` and test helpers in `integration-tests/src/user/mod.rs:299-311`.
2. Before R submits it, chain A's entire state (including Alice's account and access key with nonce N-1) is exported/cloned to bootstrap chain B (a supported use case, see `tools/mirror/src/genesis.rs`), or chain A undergoes a hard fork producing chain B with identical state at the fork height.
3. On chain B, an attacker (or the relayer) submits the exact same `SignedDelegateAction` bytes inside a new outer `SignedTransaction` addressed to Alice's account.
4. `validate_delegate_action_key` on chain B sees `delegate_nonce (N) > current_nonce (N-1)` — identical to chain A's state — and `SignedDelegateAction::verify()` succeeds because the hash/signature never encoded which chain it belonged to, so the transfer executes a second time on chain B using only the original chain-A signature.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

    }

    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
        let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
        hash(&bytes)
