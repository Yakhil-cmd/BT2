### Title
Cross-tenant webhook forgery — signing organization is decoupled from the repository the payload acts on (`WebhooksController#verify_signature` vs `Handler#repository_name`) - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
In Shipit's multi-organization configuration, incoming GitHub webhooks are authenticated against the webhook secret belonging to one JSON field (`repository.owner.login`, falling back to `organization.login`), while the actual repository/stack that handlers act on is resolved from a completely different field (`repository.full_name`). No code ties these two values together, so the "authenticated organization" and the "repository written to" are two independent bindings that should be, but never are, checked for equality.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization config (and therefore which `webhook_secret`) to verify the HMAC signature against, using: [1](#0-0) [2](#0-1) 

Once the signature is accepted, `create` simply dispatches the raw parsed payload to every registered handler for the event: [3](#0-2) 

Every handler (`PushHandler`, `PullRequest::ClosedHandler`, `StatusHandler`, etc.) resolves the target `Repository`/`Stack` independently, from a *different* payload field, `repository.full_name`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` just splits `owner/name` and does a DB lookup — no cross-check against the organization whose secret verified the request: [6](#0-5) 

Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `app_id`/`installation_id`/`webhook_secret` block under `github:` in `secrets.yml`: [7](#0-6) 

**Binding that should hold but doesn't:** `organization_whose_secret_verified_signature == owner(repository_acted_on)`. Concretely, before the attacker's request: for a legitimate webhook, `repository_owner` (used to pick the secret) and `repository.full_name`'s owner segment (used to pick the target Stack/Repository) are always the same, because GitHub itself generates both fields from the single real event. After the attacker's crafted request: an actor who legitimately knows the `webhook_secret` configured for *their own* organization (e.g., because they created/own that GitHub App entry supplied to the Shipit operator) can POST directly to `/webhooks` with `repository.owner.login` (and/or `organization.login`) set to their own org — so `verify_signature` selects their own secret and the HMAC passes — while setting `repository.full_name` to `victim-org/victim-repo`. Because the entire raw body is HMAC-signed with the attacker's own known secret, the signature check succeeds even though the payload content targets an unrelated organization's repository.

### Impact Explanation
This breaks a repository-write authorization boundary the same way the sequencer-uptime finding breaks a "price-approved vs price-executed" boundary: a value the system implicitly trusts (which org "owns" this event) is never actually re-checked against the value that determines what gets mutated (which repository the event acts on). Concrete cross-repository consequences reachable through existing handlers:
- `PushHandler` can enqueue `GithubSyncJob`/deploy-triggering syncs against a `Stack` belonging to a repository the attacker's organization has no relationship to.
- `PullRequest::ClosedHandler` can archive/mutate `ReviewStack` state on the victim repository.
- `StatusHandler` can inject fabricated commit statuses onto the victim's commits, which stacks may gate deploys/CI checks on.

This satisfies the "Critical - cross-repository writes" impact bar defined in scope, since state belonging to a repository/organization other than the authenticating one is written without any authorization check tying the two together.

### Likelihood Explanation
Requires only knowledge of a legitimately-provisioned `webhook_secret` for *some* organization already configured on the Shipit instance — which is realistic for any operator-hosted, multi-tenant deployment (as documented) where each customer/org provides/owns their GitHub App credentials. No repository write access, session, `ApiClient` token, or GitHub App private key for the *victim* org is needed; only the attacker's own organization's webhook secret, which they legitimately possess, and the ability to send an arbitrary HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Enforce that the resolved target repository's owner matches the organization whose secret verified the signature. E.g., after `verify_signature` succeeds, compare `repository_owner` (or `organization.login`) with the owner segment of `payload.dig('repository','full_name')` and reject (422) on mismatch, or have `Handler#stacks` take the authenticated organization as an explicit argument and filter `Repository.from_github_repo_name` results to that organization rather than trusting the payload's `full_name` field in isolation.

### Proof of Concept
1. Shipit is configured for two organizations, `org-attacker` and `org-victim`, each with its own `webhook_secret` in `secrets.yml` (per the multi-app setup in `docs/setup.md`).
2. Attacker knows `org-attacker`'s `webhook_secret` (they provisioned that GitHub App/installation).
3. Attacker crafts a `push` payload JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to exist on victim stack>",
  "repository": { "full_name": "org-victim/victim-repo", "owner": { "login": "org-attacker" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker webhook_secret, raw_body)>` and sends the POST to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, and the HMAC check passes because the attacker used the correct secret for that org.
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves the repository via `payload.dig('repository','full_name')` = `"org-victim/victim-repo"` and triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stack — an action entirely outside the attacker's own organization, despite the request having been authenticated only against `org-attacker`'s secret.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
