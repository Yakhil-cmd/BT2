### Title
Bridge ERC20 Transfer Request Emits Declared Amount Without Verifying Actual Received Balance — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls tokens via `safeTransferFrom` and then emits `RequestValueTransfer` using the caller-supplied `_value` parameter without verifying the actual balance delta. For any fee-on-transfer ERC20 token registered with the bridge, the source bridge receives fewer tokens than declared, but the counterpart bridge releases the full declared amount, draining the counterpart bridge's reserves.

### Finding Description

`requestERC20Transfer` in `BridgeTransferERC20.sol` executes the following sequence:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

`safeTransferFrom` is a thin wrapper that only checks the return value is not `false`; it does not verify the actual amount credited to `address(this)`:

```solidity
function safeTransferFrom(IERC20 token, address from, address to, uint256 value) internal {
    callOptionalReturn(token, abi.encodeWithSelector(token.transferFrom.selector, from, to, value));
}
``` [2](#0-1) 

After the pull, `_requestERC20Transfer` is called. It pays the bridge fee from the bridge's own balance, then emits `RequestValueTransfer` with the original caller-supplied `_value`:

```solidity
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // ← declared, not verified
    requestNonce,
    fee,
    _extraData
);
``` [3](#0-2) 

The same pattern exists in the 1-step path: `ERC20ServiceChain.requestValueTransfer` calls `transfer(bridge, _amount.add(_feeLimit))` and then immediately calls `onERC20Received` with the original `_amount`, which forwards it unchanged to `_requestERC20Transfer`: [4](#0-3) [5](#0-4) 

The bridge operator on the counterpart chain observes the `RequestValueTransfer` event and calls `handleERC20Transfer` with the declared `_value`, which either mints or transfers the full declared amount to the recipient: [6](#0-5) 

### Impact Explanation

In lock/unlock mode (`modeMintBurn = false`):

- Source bridge receives `_value + _feeLimit − tokenTransferFee` tokens.
- After paying the bridge fee and refunding change, the source bridge holds `_value − tokenTransferFee` tokens.
- The `RequestValueTransfer` event carries `_value`.
- The counterpart bridge releases `_value` tokens to the recipient.
- **Net loss per transfer**: `tokenTransferFee` tokens are drained from the counterpart bridge's reserves.

For a token with a 1% built-in transfer fee, every bridge transfer of 1000 tokens drains 10 tokens from the counterpart bridge. An attacker can repeat this at scale to fully drain the counterpart bridge's liquidity.

In mint/burn mode the `burn(_value)` call will revert if the bridge received fewer than `_value` tokens, so that path is self-protecting. The vulnerability is exploitable in lock/unlock mode.

### Likelihood Explanation

The `onlyRegisteredToken` modifier restricts the attack to tokens registered by bridge operators. However:

1. Fee-on-transfer tokens (e.g., tokens with built-in redistribution or deflationary mechanics) are a well-known token class that operators may legitimately register.
2. Once such a token is registered, **any unprivileged user** can call `requestERC20Transfer` to trigger the discrepancy on every transfer.
3. No malicious operator intent is required; a well-intentioned operator registering a fee-on-transfer token is sufficient.

### Recommendation

Record the bridge's token balance before and after `safeTransferFrom`, and use the delta as the actual transferred amount for both the event and subsequent logic:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived >= _value.add(_feeLimit), "insufficient tokens received");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Apply the same fix to the `onERC20Received` path by verifying the balance delta before accepting the declared `_value`.

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token `FeeToken` where every `transferFrom` silently deducts 10% and transfers only 90% of the declared amount.
2. Register `FeeToken` on the source bridge (operator action, one-time setup).
3. Attacker calls `requestERC20Transfer(feeToken, victim, 1000e18, feeLimit, "")`.
4. `safeTransferFrom` is called for `1000e18 + feeLimit`; bridge receives only `900e18 + 0.9*feeLimit` tokens (10% fee deducted by the token).
5. `_requestERC20Transfer` emits `RequestValueTransfer` with `_value = 1000e18`.
6. Bridge operators on the counterpart chain observe the event and call `handleERC20Transfer(..., 1000e18, ...)`.
7. Counterpart bridge transfers `1000e18` tokens to the attacker's `_to` address.
8. **Result**: Attacker received `1000e18` tokens on the counterpart chain while the source bridge only received `900e18` tokens. The counterpart bridge is short `100e18` tokens per iteration.
9. Repeat until the counterpart bridge's reserves are exhausted.
