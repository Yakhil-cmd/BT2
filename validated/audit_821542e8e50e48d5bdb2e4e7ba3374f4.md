### Title
Stale `byte_balance` used to enforce the storage-size deposit lets an AA response spend bytes below its state-storage reserve - ([File: aa_composer.js])

### Summary
`ocore`'s Autonomous Agents keep two conceptually different balances that should never be conflated: (1) the `storage_size` "deposit" that must remain locked in the AA's byte balance to guarantee it can always store its state variables, and (2) the AA's ordinary spendable byte balance used to pay for outgoing payment messages/bounce fees. Exactly as in the "separate stake and prepayment" bug class described in the external report (StakeManager mixing anti-sybil stake with gas prepayment), `aa_composer.js` mixes these two funds because the enforcement check that is supposed to keep the spendable balance from dropping below the storage reserve (`updateStorageSize`) is evaluated against a `byte_balance` variable that is captured once at the start of trigger handling and never refreshed after the AA sends a payment.

### Finding Description
When a trigger is handled, `byte_balance` is set once from the balance available before any outgoing payment is computed: [1](#0-0) [2](#0-1) 

`storage_size` is the amount of bytes the AA must keep reserved as a "deposit" for its own state (analogous to the locked stake in the report), read from `aa_addresses.storage_size`: [3](#0-2) 

The AA then composes and sends its response payment via `sendUnit`/`completePaymentPayload`, which subtracts the outgoing amounts from the AA's real balance (only adding a protective change output for the *send-all* case, guarded by `storage_size`): [4](#0-3) 
For an explicit-amount payment (not a send-all output), no such protective output is added, so the AA can freely pay out bytes down toward (or below) the reserved `storage_size` amount.

After the response unit is built and saved, `updateStorageSize` is the only place that checks the reserve invariant, but it checks it against the stale, pre-spend `byte_balance` captured before the response payment was ever computed: [5](#0-4) 

Because `byte_balance` is never updated to reflect the bytes that `completePaymentPayload`/`sendUnit` just paid out, this check does not actually verify that the *post-response* balance still covers `new_storage_size`. It only verifies that the balance the AA had *before spending* covered the reserve - the "stake" (storage reserve) and "prepayment" (funds paid out in the response) are not properly separated/accounted for, so an AA definition/trigger sequence that pays out most of its base balance while simultaneously growing its state variables can pass the `updateStorageSize` gate even though the AA's real remaining byte balance is now below its own storage_size deposit.

This mirrors the reported StakeManager issue precisely: funds meant to be walled off for a specific protective purpose (data storage guarantee here, anti-sybil stake there) are tracked using the same accounting path as ordinary spendable/prepaid funds, and the boundary-enforcement check operates on the wrong (stale) balance snapshot.

### Impact Explanation
If an AA's actual byte balance can fall below its recorded `storage_size` without detection, the invariant enforced elsewhere (e.g. by the integrity check `checkStorageSizes`, which asserts DB `storage_size` matches on-disk key-value state size) is not itself violated, but the *purpose* of the reserve - guaranteeing the AA always has enough bytes to keep persisting/growing its state and to pay for bounce fees - is defeated. Subsequent triggers to the same AA can then be bounced or fail unexpectedly because there are not enough real bytes to cover the storage reserve plus bounce fees, effectively freezing the AA's ability to operate (fund/state freezing), which is one of the explicitly in-scope impacts (AA fund loss or freezing).

### Likelihood Explanation
Any AA author or trigger sender can reach this path with an ordinary AA definition that both writes/grows state variables and sends an explicit (non send-all) base-asset payment in the same response - a very common oscript pattern (e.g., exchanges, bank/withdraw AAs seen in the test samples). No privileged actor or network-level condition is required; this is reachable purely by posting units/triggers to a normally deployed AA.

### Recommendation
Update `byte_balance` after each payment computed in `sendUnit`/`completePaymentPayload` (or recompute it from `trigger_opts.assocBalances[address].base` / `objValidationState.assocBalances[address].base` right before the `updateStorageSize` check) so the storage-size reserve check in `aa_composer.js` (around line 1564) is evaluated against the AA's true balance after the response payment has been deducted, not the balance captured before the trigger's outgoing payment was computed. Ensure the check runs for both send-all and explicit-amount payment paths consistently.

### Proof of Concept
1. Deploy an AA whose response `messages` include: (a) a `state` message that adds/grows several state variables (increasing `storage_size`), and (b) a `payment` message with an explicit (non send-all) `amount` field that pays out most of the AA's base balance to `trigger.address`.
2. Trigger the AA with just enough base bytes to cover the bounce fee and initial storage but where, after the explicit payment output executes, the AA's true remaining balance would be less than the new `storage_size`.
3. Because `byte_balance` in `handleTrigger` (aa_composer.js) still reflects the balance from before the explicit payment was deducted, `updateStorageSize`'s comparison `byte_balance < new_storage_size` passes even though the AA's real balance after sending the response is now below the `storage_size` reserve.
4. Observe that the AA's DB `storage_size` is increased and accepted while its real spendable balance is insufficient to safely cover it, so future triggers to the AA (which need bytes for bounce fees / storage growth) can start failing/bouncing - illustrating the loss of the previously-guaranteed reserve.
