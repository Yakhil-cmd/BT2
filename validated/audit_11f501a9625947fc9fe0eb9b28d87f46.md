### Title
Cross-repository `Status` forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` triggers unauthorized deploy/merge on victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by bare SHA (`Commit.where(sha: params.sha)`), with no scoping to the repository/stack that the webhook's signature actually authenticated. Because commit SHAs are identical across forks/mirrors that share history, an attacker who owns any repository with a valid GitHub App webhook installation can emit a signed `status` event for a SHA that is shared with a victim stack, and have `Status` rows created for the victim's commit, which can flip CI state and drive `Commit#schedule_continuous_delivery` / `stack.schedule_merges`.

### Finding Description
The broken binding the code should enforce is:
`status.stack_id == webhook.authenticated_repository.stack_id`
but the actual code enforces only:
`Shipit.github(organization: repository_owner).verify_webhook_signature(...) == true`
with no further constraint tying the located `Commit` rows to that `repository_owner`.

Path:
1. `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` passes.
2. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) derives `repository_owner` from the attacker-controlled payload and checks the signature against `Shipit.github(organization: repository_owner)`. This only proves the request came from *some* GitHub App installation belonging to `repository_owner` — an org/account the attacker legitimately owns (e.g., their own fork). It does **not** prove any relationship between that repository and the commit SHA being reported.
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
   ```ruby
   def process
     Commit.where(sha: params.sha).each do |commit|
       commit.create_status_from_github!(params)
     end
   end
   ```
   This is a bare, unscoped lookup by `sha` across **all** `Commit` rows in the database, i.e. across every stack/repository tracked by the Shipit instance. There is no `stack.repository == payload.repository` check anywhere in this handler.
4. `Commit#create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:366-386`) creates the `Status`, and if the state transitions meaningfully, calls `stack.schedule_merges` and (via `after_create`/`after_commit` callbacks on `Status`, `app/models/shipit/status.rb:18-19`) `commit.schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`), which enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` and `stack.deployable?` are true.

Exploit flow: the attacker forks or otherwise obtains a repository that shares commit history (identical SHAs) with a victim's tracked repository (a common real-world situation for upstream/fork pairs, mirrored repos, or repos merged from a common base). The attacker installs/owns a GitHub App webhook on their own repository (something they legitimately control) and sends a `status` webhook with `context: ci/kubernetes`, `state: success` (or `failure` to block), and `sha` equal to a commit shared with the victim's stack. `verify_signature` passes because it only validates that *a* valid installation for the attacker's own org sent it. `StatusHandler` then writes a `Status` onto the victim's `Commit` row for that SHA, because the lookup is unscoped. If the victim stack has continuous deployment or auto-merge configured (using a configured bot identity for the actual GitHub write operations, e.g. merging or updating status on GitHub), this drives a real deploy/merge/block action for a repository the attacker never authenticated against.

Existing guards fail because: `verify_signature` authenticates the *sender's own organization*, not the *target commit's owning repository*; `ExplicitParameters` (the `params do ... end` block) only validates payload shape, not scoping; and `StatusHandler` has no analog to a `repository.full_name` equality check that other handlers (e.g. `PushHandler`) would need to locate the correct stack.

### Impact Explanation
A payload authenticated for one repository (the attacker's own) mutates state (`Status`) belonging to another repository/stack that never authenticated it, which is explicitly listed as a Critical-severity outcome. Depending on the victim stack's configuration (`continuous_deployment?`, required/blocking statuses, merge queue), this can autonomously trigger `ContinuousDeliveryJob` (an unauthorized deploy) or block a legitimate deploy pipeline by injecting a `failure`/`error` status for a required context like `ci/kubernetes`. The blast radius extends to any stack across the Shipit instance whose tracked repository shares commit history with any repository the attacker can obtain a valid webhook signature for — this is repeatable per shared SHA and not limited to a single victim.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control that can emit a validly-signed `status` webhook (achievable simply by owning any GitHub repo/org with the app installed, which is a normal unprivileged capability for "any internet user" per the threat model), and (b) a commit SHA shared with the victim's stack (trivially achievable by forking the victim's repository, since forks retain identical commit objects/SHAs for shared history). No Shipit secrets, session, or API token are required. This is low-cost and repeatable.

### Recommendation
Scope the `StatusHandler` (and any other handler performing bare `Commit`/`sha` lookups) to only the repository that authenticated the webhook. Concretely, resolve the `repository`/`stack` from the verified payload's `repository.full_name` (as `PushHandler` presumably does) and constrain the query, e.g.:
```ruby
def process
  Commit.joins(:stack).merge(Stack.where(repository: repository)).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
ensuring `repository` is derived from the same verified `repository_owner`/`full_name` used in `verify_signature`, not solely from `params.sha`.
