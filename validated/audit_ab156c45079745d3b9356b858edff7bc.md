### Title
Webhook signature verification silently no-ops when an organization's `webhook_secret` is unset, allowing unauthenticated forged GitHub events (including team membership escalation) - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` treats a blank/unconfigured `webhook_secret` as an automatic pass, rather than rejecting the request. This mirrors the reported bug class exactly: a verifier value that can end up "unset" causes every claim (payload) to be accepted as authentic, regardless of what it says or who sent it. In Shipit this lets an unauthenticated network attacker POST arbitrary payloads straight to `/webhooks` and have them processed as genuine GitHub events, including a `membership` event that adds an attacker-chosen GitHub login to any `Shipit.github_teams`-authorized team.

### Finding Description
`WebhooksController#verify_signature` is the sole gate protecting the `/webhooks` endpoint (`skip_before_action :verify_authenticity_token` is set, so there is no CSRF protection layered on top): [1](#0-0) 

It delegates the actual check to `GitHubApp#verify_webhook_signature`: [2](#0-1) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If the organization's `webhook_secret` config value is blank (`@webhook_secret = @config[:webhook_secret].presence`, set in the constructor at [3](#0-2) ), `verify_webhook_signature` unconditionally returns `true` — no `X-Hub-Signature` header is even required. This is the same failure mode as the reported bug: the code path meant to bind "claimed data" to "an authorized signer" degenerates into an always-true check the moment the signer/secret is absent, so a forged claim (here, a forged webhook payload) is accepted as legitimate.

The binding that should hold is:
```
verified_signer(raw_post, X-Hub-Signature) == the GitHub organization whose state the handler mutates
```
When `webhook_secret` is blank, the left side becomes vacuously true for any payload from any source, breaking this equality completely.

Once past `verify_signature`, the `membership` event handler trusts the payload at face value to mutate team membership: [4](#0-3) 

`team.add_member(member)` adds an attacker-supplied `member.login` to the named team. Team membership is exactly what gates access in `User#authorized?`: [5](#0-4) 

An attacker who knows (or creates via OAuth) an account with a matching `login`, and who forges a `membership` "added" event against an org whose `webhook_secret` is unset, becomes a member of a `Shipit.github_teams`-authorized team and thus `authorized?`, gaining access to trigger deploys, rollbacks, and merges through the authenticated UI/API (protected only by `force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb`).

The same missing verification also lets an attacker forge `push`, `status`, and `check_suite` events (see `app/models/shipit/webhooks/handlers/status_handler.rb`, `push_handler.rb`, `check_suite_handler.rb`), letting them fabricate green CI statuses or trigger sync/merge jobs for repositories the engine tracks.

### Impact Explanation
This maps to the report's "High" bucket: escalation into `Shipit.github_teams` authorization via forged, unauthenticated webhook traffic, and (through forged `status`/`push`/`check_suite` events) fabrication of commit state that gates unauthorized deploys/merges. No credential, session, or `ApiClient` token is required — only that the deployment leaves `webhook_secret` unset for the targeted organization, which the engine's own code (not host misconfiguration) treats as a valid, fully-verified state rather than rejecting.

### Likelihood Explanation
Any operator who omits the (labeled) webhook secret for an organization is silently left with no webhook authentication at all, and the engine gives no indication of this at runtime — `verify_signature` logs `status=200`-style success info identically to a properly verified request. Given `/webhooks` is an unauthenticated, internet-reachable POST endpoint by design, exploitation requires no more than knowing/observing the org's login name and issuing a crafted JSON body with the correct `X-Github-Event` header.

### Recommendation
Change `verify_webhook_signature` to fail closed: if `webhook_secret` is blank, reject the webhook (return `false`) instead of returning `true`, and require operators to explicitly opt in to disabling signature verification (e.g., via a distinct, clearly-named flag) rather than have "unset" implicitly mean "trust everything."

### Proof of Concept
1. Deploy Shipit with an organization entry in `secrets.github` that has no `webhook_secret` (a supported/blank value).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: membership` and no (or garbage) `X-Hub-Signature`, body:
```json
{
  "action": "added",
  "team": {"id": 999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999"},
  "organization": {"login": "target-org"},
  "member": {"login": "attacker-controlled-login"}
}
```
3. `GitHubApp#verify_webhook_signature` returns `true` (no secret configured), `MembershipHandler#process` runs and adds `attacker-controlled-login`'s `User` record to team `deployers`.
4. If `deployers` is listed in `Shipit.github_teams`, the attacker's account is now `authorized?` and can log in (via normal GitHub OAuth, using an account with that login) to trigger deploys/rollbacks/merges on any stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
