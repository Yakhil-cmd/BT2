## Title
Cross-organization webhook signature confusion allows attacker-controlled organization to spoof events for repositories in other organizations - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to verify the incoming signature against using one payload field (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually act on the event resolve the target `Repository`/`Stack` using a *different* payload field (`repository.full_name`). In a multi-organization Shipit deployment, these two fields are never cross-checked for consistency, so a party who legitimately controls a webhook for Organization A can forge a payload whose `repository.owner.login` says "A" (which HMACs correctly with A's known `webhook_secret`) but whose `repository.full_name` names a repository belonging to Organization B, causing Shipit to act on Organization B's stack/repository/PR state as though it were an authentic event.

## Finding Description
`Shipit.github(organization:)` supports per-organization configuration, each with its own `webhook_secret` [1](#0-0) . The webhook signature check derives the organization used to fetch the verifying secret purely from the payload body:

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once `verify_signature` passes, `create` dispatches the raw, attacker-controlled JSON to the matching event handler(s) unmodified [3](#0-2) . Every handler, however, resolves the repository/stack to mutate from a *separate* field, `repository.full_name`:

```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

and `Repository.from_github_repo_name` simply splits that string on `/` and looks up by `owner`/`name` with no relation back to `repository.owner.login` [5](#0-4) . The same pattern repeats in every PR handler (`AssignedHandler`, `ClosedHandler`, `EditedHandler`, `LabelCapturingHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`), all of which call `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to decide which stack to archive/unarchive/update [6](#0-5) [7](#0-6) .

This is the same bug class as the H-8 report: the value that is verified/authenticated (`repository.owner.login`, used to pick the HMAC secret) is not the value that is subsequently acted upon (`repository.full_name`, used to select the repository/stack to mutate). The equality `verified_organization == acted_upon_repository_owner` is assumed but never enforced.

**Attack precondition**: the attacker must legitimately administer at least one GitHub organization that is configured in Shipit's `secrets.github` with a `webhook_secret` they know (this is a normal, unprivileged part of onboarding a repo to a multi-tenant Shipit instance — it does not require compromising another org or Shipit's server). Real GitHub-originated payloads always have consistent `owner.login` and `full_name` prefixes, so this mismatch can only be produced by an attacker who forges the raw POST body themselves and signs it with their own org's known secret, rather than relying on GitHub to deliver it.

**Before the attacker's request**: for organization A's webhook secret, the only valid payloads (from GitHub) always have `repository.owner.login == "A"` and `repository.full_name` prefixed with `"A/"` — the verified organization and the acted-upon repository owner are always equal.

**After the attacker's request**: the attacker submits a raw POST directly to `/github/webhooks` with `X-Hub-Signature` computed over a body where `repository.owner.login = "A"` (or `organization.login = "A"`) but `repository.full_name = "B/victim-repo"`. `verify_signature` fetches `Shipit.github(organization: "A")` and validates successfully against A's own secret [8](#0-7) , then the handler acts on repository `B/victim-repo` [4](#0-3) . The equality is broken.

## Impact Explanation
This breaks the deployment-trust binding "organization that authenticated == repository that is written," resulting in a cross-repository/cross-organization write: an attacker who legitimately controls Organization A's webhook secret can archive/unarchive review stacks, mutate pull-request state (`pull_request.update(github_pull_request: ...)`), or otherwise trigger stack provisioning behavior for repositories that belong to a completely unrelated organization B onboarded to the same Shipit instance [9](#0-8) . This matches the "Critical - cross-repository writes" impact bucket, since it is a real cross-tenant state mutation with no dependency on rate limiting, DoS, or third-party gem defects.

## Likelihood Explanation
This requires a multi-organization Shipit deployment (`secrets.github` configured per-organization) and requires the attacker to already administer one organization's webhook configuration — a normal, low-privilege onboarding action, not a compromise of Shipit or of the victim organization. Given that precondition, forging the raw POST body and its HMAC signature is trivial once the attacker knows their own org's secret. Likelihood is Medium: it depends on a multi-tenant deployment topology, but requires no privileged Shipit session, GitHub App key, or victim credentials.

## Recommendation
After verifying the signature, cross-check that the organization derived from `repository.owner.login` (used to select the verifying secret) matches the owner-prefix of `repository.full_name` (used by handlers to resolve the target repository), and reject the webhook (422) if they differ. Alternatively, have handlers resolve the repository/stack using the same verified `repository_owner`/organization value rather than trusting `repository.full_name` independently.

## Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org_a` (with `webhook_secret: SECRET_A`) and `org_b`.
2. As a legitimate admin of `org_a`, compute `sha1=<HMAC-SHA1(SECRET_A, body)>` for a crafted `pull_request` "labeled" event body where:
   - `repository.owner.login = "org_a"`
   - `repository.full_name = "org_b/victim-repo"`
   - `action = "labeled"`, with the provisioning label matching `org_b/victim-repo`'s configured `provisioning_label_name`.
3. POST this body with header `X-Hub-Signature: sha1=<computed>` and `X-Github-Event: pull_request` to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "org_a")` and validates successfully against `SECRET_A` [8](#0-7) .
5. `LabeledHandler#repository` resolves `Shipit::Repository.from_github_repo_name("org_b/victim-repo")` and archives/unarchives the corresponding stack in `org_b`, despite the request never being signed with `org_b`'s secret [9](#0-8) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
