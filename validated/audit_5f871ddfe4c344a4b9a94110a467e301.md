### Title
Missing validation of `creator` account in `initialize_with_permission` permanently freezes creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`initialize_with_permission` records `pool_state.pool_creator` from an unchecked, non-signer account with no validity/zero-address check. A pool creator can set this field to an unspendable address (e.g. `Pubkey::default()`), which permanently locks all creator fees accrued by the pool because no keypair exists to ever claim them.

### Finding Description
In `InitializeWithPermission`, the `creator` account is declared as a plain `UncheckedAccount<'info>` with no `Signer` requirement and no constraint validating it against `payer` or against `Pubkey::default()`: [1](#0-0) 

This account's key is then written directly into pool state without any sanity check: [2](#0-1) 

which flows into `PoolState::initialize`, assigning `self.pool_creator = pool_creator.key();` with no validation: [3](#0-2) 

This is the exact bug-class described in the external report — a value that becomes a permanent access/ownership anchor is copied from caller-supplied input with no zero-address check. Contrast with the ordinary `Initialize` instruction, where `creator` is a `Signer<'info>`, guaranteeing it holds a valid keypair and can never be `Pubkey::default()`: [4](#0-3) 

Once `pool_creator` is set to an unspendable pubkey, both fee-collection paths become permanently unusable/fund-locking:
- `collect_creator_fee` requires `creator` to be a `Signer` whose address equals `pool_state.pool_creator`; if that address has no private key, this instruction can never succeed: [5](#0-4) 
- `collect_creator_fee_permissionless` doesn't require a creator signature, but it derives an associated token account whose `authority` is the unspendable `creator` pubkey and pays out the accumulated creator fees into it: [6](#0-5) 
Tokens transferred into that ATA are irrecoverable since nobody can sign as the token-account authority to move them out again.

### Impact Explanation
Any tokens routed into `creator_fees_token_0` / `creator_fees_token_1` for a pool created via `initialize_with_permission` with an attacker-chosen non-spendable `creator` become permanently frozen — no account can ever authorize their withdrawal. This is a permanent loss of funds accruing to the pool over its lifetime (trading fee revenue), matching the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
The path is directly reachable in a single transaction: whoever holds a valid `Permission` PDA (an explicitly in-scope, non-admin actor able to call `initialize_with_permission`) simply passes `Pubkey::default()` (or any other keypair-less/unrelated PDA) as the `creator` account. No additional privilege, race condition, or unusual configuration is required beyond calling the instruction with attacker-chosen account inputs.

### Recommendation
Add an explicit check in `InitializeWithPermission`/`initialize_with_permission` (and in `PoolState::initialize`) rejecting `Pubkey::default()` for the `creator` account, e.g. `require_keys_neq!(ctx.accounts.creator.key(), Pubkey::default())`, mirroring the fix already applied to `set_new_protocol_owner`/`set_new_fund_owner` in `update_config.rs`: [7](#0-6) 
Consider also constraining `creator` to be consistent/expected (e.g., requiring it be a valid, funded account or requiring `payer`'s consent) rather than an arbitrary unchecked pubkey.

### Proof of Concept
1. Attacker (holding a valid `Permission` PDA for their `payer` key) calls `initialize_with_permission`, supplying `creator = Pubkey::default()` (System Program address) instead of a real wallet.
2. No Anchor constraint rejects this since `creator` is `UncheckedAccount` with no signer/zero-check requirement.
3. `pool_state.pool_creator` is set to `Pubkey::default()` via `pool_state.initialize(...)`.
4. As trades occur on the pool, `creator_fees_token_0`/`creator_fees_token_1` accumulate normally.
5. `collect_creator_fee` can never be called (no keypair exists for `Pubkey::default()` to sign).
6. `collect_creator_fee_permissionless` can be called by anyone, but it sends the accumulated fees to an ATA whose authority is `Pubkey::default()` — funds land in an account nobody can ever move, permanently freezing that fee revenue.
