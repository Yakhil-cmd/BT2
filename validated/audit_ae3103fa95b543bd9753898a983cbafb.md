### Title
Unbounded concurrent HTTP request handling in the JSON-RPC server allows memory-exhaustion DoS - ([File: chain/jsonrpc/src/lib.rs])

### Summary
The near-jsonrpc HTTP server, built with Axum in `create_jsonrpc_app()`, only applies CORS and a request-body size cap as middleware, but never limits the number of concurrently in-flight HTTP requests it will process.

### Finding Description
`create_jsonrpc_app()` builds the Axum `Router` with routes for `/`, `/status`, `/health`, `/network_info`, `/metrics`, `/openapi.json`, and (when enabled) `/debug/*`, and applies only two layers before starting the server: [1](#0-0) 

No `tower::limit::ConcurrencyLimitLayer`, `Throttle`-equivalent middleware, or per-connection/per-IP concurrency cap is present anywhere in the router construction. `start_http()` then binds the listener and serves the app directly via `axum::serve`, with no additional concurrency guard at that layer either: [2](#0-1) 

Each inbound request is dispatched to `rpc_handler()` → `JsonRpcHandler::process()` → `process_request()` → `process_request_internal()`, which sends async messages to backend actors (`ClientActor`, `ViewClientActor`, `RpcHandlerActor`, `PeerManagerActor`) and awaits their responses: [3](#0-2) 

Because Axum/Tokio will accept and spawn a task per incoming connection/request without any global concurrency ceiling, an attacker can open a very large number of concurrent connections (e.g., to `/` with expensive `query` calls, or simply many simultaneous requests) and drive the process to spawn unbounded numbers of in-flight request tasks, each holding buffers, actor-message futures, and (for `query`/state-view calls) potentially large state read results in memory simultaneously. This is directly analogous to the reported Staking API bug class: an HTTP service that accepts unlimited concurrent requests and has no throttle/concurrency-limiting middleware, leading to unbounded memory growth and process termination by the OS OOM killer.

The only existing protections are a 10 MB `RequestBodyLimitLayer` (bounding a single request's body size) and CORS — neither of which bounds the *number* of concurrent requests: [4](#0-3) 

Backend query throughput is separately bounded per-request-type in places (e.g., `receipt_to_tx_max_outcomes_per_request`, `view_client_threads`, `state_request_throttle_period`/`state_requests_per_throttle_period` for state sync requests): [5](#0-4) 
but these limit backend actor thread pools/per-request cost, not the number of concurrently-accepted front-end HTTP connections/requests, so a flood of connections can still exhaust memory in the HTTP layer (buffered requests, Tokio tasks, response futures) before backend throttling has any effect.

### Impact Explanation
An attacker who knows the (by design, public) JSON-RPC endpoint of a nearcore node — the same reachability model as the Staking API — can open a large number of concurrent HTTP requests. Unbounded concurrent request handling causes unbounded memory growth in the node's RPC process, which can lead to OOM termination of the `neard` process. For an RPC-serving node this denies wallets/dApps/relayers the ability to submit transactions or query state through that node (unbounded resource use / DoS), matching the reported bug class. This does not compromise consensus, balances, or state correctness, but it can disable the RPC availability of the affected node(s).

### Likelihood Explanation
High. Any nearcore node exposing the JSON-RPC HTTP endpoint (the default `neard` configuration, port 3030) is reachable by anyone who can send it standard HTTP requests — no privileged account, staking, or protocol-level action is required. This mirrors the reported likelihood rationale (the endpoint is "publicly known" and requires no special access).

### Recommendation
Add a concurrency-limiting middleware layer (e.g., `tower::limit::ConcurrencyLimitLayer`, or a `tower_governor`/custom semaphore-based layer) to the Axum router built in `create_jsonrpc_app()` in `chain/jsonrpc/src/lib.rs`, capping the number of in-flight HTTP requests the JSON-RPC server will process concurrently, and optionally add per-IP rate limiting for the `/` endpoint. Combine this with a documented recommendation for operators to place the RPC endpoint behind a reverse proxy / CDN (e.g., Cloudflare) providing connection-level DoS protection, consistent with the conclusion reached for the analogous Staking API report.

### Proof of Concept
1. Start a `neard` node with the default JSON-RPC config (`addr: 0.0.0.0:3030`, no additional reverse proxy).
2. From an attacker-controlled client, open a large number (e.g., tens of thousands) of concurrent TCP connections/HTTP requests to `http://<node>:3030/` sending valid JSON-RPC bodies (e.g., cheap `status` or `query` calls) without closing the connections or reading responses promptly.
3. Observe process memory grow unbounded as `axum::serve` accepts and spawns a task per request with no concurrency ceiling (`create_jsonrpc_app()` / `start_http()`), eventually leading to OOM kill of the `neard` process, denying RPC service to legitimate users.

impl JsonRpcHandler {
    async fn process(&self, message: Message, source: RequestSource) -> Message {
        let id = message.id();
        match message {
            Message::Request(request) => {
                Message::response(id, self.process_request(request, source).await)
            }
            _ => Message::error(RpcError::parse_error(
                "JSON RPC Request format was expected".to_owned(),
            )),
        }
    }

    // `process_request` increments affected metrics but the request processing is done by
    // `process_request_internal`.
    async fn process_request(
        &self,
        request: Request,
        source: RequestSource,
    ) -> Result<Value, RpcError> {
        let timer = Instant::now();
        let (metrics_name, response) = self.process_request_internal(request, source).await;

        metrics::HTTP_RPC_REQUEST_COUNT.with_label_values(&[&metrics_name]).inc();
        metrics::RPC_PROCESSING_TIME
            .with_label_values(&[&metrics_name])
            .observe(timer.elapsed().as_secs_f64());

        if let Err(err) = &response {
            metrics::RPC_ERROR_COUNT
                .with_label_values(&[&metrics_name, &err.code.to_string()])
                .inc();
        }

        response
    }
