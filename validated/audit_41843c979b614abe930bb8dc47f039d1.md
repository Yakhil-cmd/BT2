## Analysis

Confirmed root cause in the codebase: in ocore, when an Autonomous Agent (or any unit) sends a non-base-asset `payment` message with multiple outputs, the asset's spender-attestation and transfer-condition checks are evaluated **once for the entire payment message**, not per-output. If a single recipient in the batch fails the check, validation of the whole message (and thus the whole unit) fails. [1](#0-0) 

Specifically:
- If `objAsset.spender_attested` is true, `storage.filterAttestedAddresses` is called on the full `arrOutputAddresses` list, and if even one address in that list is not attested, the callback returns `"some output addresses are not attested"`, failing the entire payment. [2](#0-1) 
- Likewise, `objAsset.transfer_condition`/`issue_condition` is evaluated via `Definition.evaluateAssetCondition` against the whole unit/payload; if not satisfied, `"transfer or issue condition not satisfied"` fails the entire payment. [3](#0-2) 

On the AA side, when an AA constructs a response unit containing a batched payment to multiple addresses (e.g., a payout/rollover/queue-distribution AA), `sendUnit` builds the payment via `completePaymentPayload` and then calls `validateAndSaveUnit`. If `ifUnitError` fires (e.g., due to the attestation/condition failure above), the error propagates to `cb(err)` and ultimately to `bounce(err)`, which discards/reverts the **entire** AA response — including outputs destined for all other, unrelated, legitimate recipients batched into the same message. [4](#0-3) [5](#0-4) 

This is a structural analog of the Sherlock finding: just as `Carousel.mintRollovers` loops and does one `safeTransfer` per receiver whose failure (USDC blacklist) reverts the whole batch, an ocore AA that pays out several addresses in one `payment` message of a `spender_attested` or `transfer_condition`-restricted asset will have the **whole batch blocked** if a single included address is unattested or fails the condition — a state fully reachable by an unprivileged AA-trigger sender who can cause themselves (or an accomplice address) to be included in the batch.

### Title
Single unattested/condition-failing recipient blocks an entire multi-output AA asset payment - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs` checks `spender_attested` and `transfer_condition`/`issue_condition` against the full set of output addresses in a payment message rather than per-output. An AA that batches payouts of a restricted asset to multiple recipients in a single `payment` message will have the entire message — and therefore the entire AA response, per `sendUnit`/`bounce` in `aa_composer.js` — fail if any single recipient in the batch is not attested or fails the transfer condition.

### Finding Description
`storage.filterAttestedAddresses` is invoked once with the complete `arrOutputAddresses` array; if the count of attested addresses returned doesn't match the input length, the callback fails with `"some output addresses are not attested"` [2](#0-1) . Similarly, `Definition.evaluateAssetCondition` is evaluated on the aggregate payload, and a single unsatisfied condition fails the whole message [3](#0-2) . There is no mechanism to skip or continue for individual failing outputs while still processing the rest, mirroring the missing "skip on failure" handling identified in the external report's `Carousel.mintRollovers`. When this validation failure occurs inside AA-unit construction (`validateAndSaveUnit`/`ifUnitError`), the error bubbles up through `completePaymentPayload`'s `async.eachSeries` callback to `bounce(err)`, discarding the entire response unit [4](#0-3) .

### Impact Explanation
Any AA design that batches distribution of a `spender_attested` or condition-restricted asset to multiple addresses in one payment message is vulnerable to denial-of-service: a single unattested/blacklisted/malicious recipient address in the batch causes bounce of the whole AA trigger, reverting payouts owed to all other legitimate participants in that same response and consuming their expected funds/state updates. This matches "AA fund loss or freezing" and "node disagreement" categories are not implicated, but fund freezing for legitimate participants is directly reachable.

### Likelihood Explanation
Reaching this requires only that: (1) an asset used by the AA has `spender_attested: true` or a `transfer_condition`, and (2) the AA logic combines multiple recipients' payouts into a single `payment` message (a common batching optimization for gas/size efficiency). An attacker can trivially ensure they (or a controlled address) are included in a batch while being unattested, deliberately griefing all co-batched recipients — no special privilege is needed since AA triggers are posted by ordinary unprivileged units.

### Recommendation
Avoid combining multiple recipients into a single payment message for assets with `spender_attested` or `transfer_condition` restrictions in AA logic; validate/attest each recipient individually before batching, or split payments per recipient into separate messages/response units so that one failing recipient does not block payouts to others. Alternatively, document this constraint clearly for AA authors and provide oscript primitives to check `asset[...].is_issued`/attestation status per-address before adding an address to a shared payment message.

### Proof of Concept
1. Issuer defines asset `A` with `spender_attested: true` and attestor list `L`.
2. An AA is written to batch-pay users from a queue in one `payment` message with `asset: A`, outputs `[{address: userX}, {address: userY}, ...]` (e.g., rewards/rollover-style distribution AA).
3. User `Y` is a legitimate queue participant who is/was never attested for asset `A` (or is later removed from the attestor list).
4. When the AA's trigger fires and attempts to send the batched payment, `validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses` on the full output list; since `userY` is not attested, validation fails with `"some output addresses are not attested"` [6](#0-5) .
5. `validateAndSaveUnit`'s `ifUnitError` fires, `cb(err)` propagates and `bounce(err)` is invoked in `sendUnit`, discarding the whole response unit [7](#0-6) , so `userX` and every other legitimate recipient in that batch fail to receive their payout even though only `userY` was invalid.
