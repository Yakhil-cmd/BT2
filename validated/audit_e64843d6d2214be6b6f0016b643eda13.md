### Title
KLAY Fee Refund Sent to Intermediate Contract Instead of Originating User in `_payKLAYFeeAndRefundChange()` - (File: `contracts/service_chain/bridge/BridgeFee.sol`)

---

### Summary

`BridgeFee._payKLAYFeeAndRefundChange()` refunds excess KLAY fee-limit to `msg.sender`. When a contract intermediary calls `requestKLAYTransfer()` on behalf of a user (a pattern the protocol explicitly supports for ERC20 via `ERC20ServiceChain`), the refund is sent to the intermediary contract rather than the originating user. If that contract has no KLAY withdrawal mechanism, the refunded KLAY is permanently stuck.

---

### Finding Description

`BridgeFee._payKLAYFeeAndRefundChange()` always refunds the excess fee-limit to `msg.sender`:

```solidity
// BridgeFee.sol lines 53-55
if (feeRefund > 0) {
    (bool ok, ) = msg.sender.call.value(feeRefund)("");
    require(ok, "refund fee failed");
}
// ...
// lines 61-63
if (_feeLimit > 0) {
    (bool ok, ) = msg.sender.call.value(_feeLimit)("");
    require(ok, "refund fee failed");
}
``` [1](#0-0) 

This is called from `BridgeTransferKLAY._requestKLAYTransfer()`, which is the internal handler for both `requestKLAYTransfer()` and the fallback:

```solidity
// BridgeTransferKLAY.sol lines 111
uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);
``` [2](#0-1) 

The public entry points `requestKLAYTransfer()` and the fallback are both `external payable`, meaning any contract can call them on behalf of a user. When a contract intermediary does so, `msg.sender` inside `_payKLAYFeeAndRefundChange` is the intermediary contract, not the originating user.

**The protocol already demonstrates this exact pattern for ERC20.** `ERC20ServiceChain.requestValueTransfer()` calls `onERC20Received()` on the bridge, passing the real user as `_from`. The ERC20 fee refund path correctly uses the explicit `from` parameter:

```solidity
// BridgeFee.sol line 78
IERC20(_token).safeTransfer(from, feeRefund);
``` [3](#0-2) [4](#0-3) 

The KLAY path has no equivalent `from` parameter — it blindly uses `msg.sender`. Any KLAY wrapper contract analogous to `ERC20ServiceChain` would silently trap refunds.

---

### Impact Explanation

Any contract that wraps KLAY bridge transfers (e.g., a `KLAYServiceChain`-style contract, a DeFi aggregator, or any protocol that calls `requestKLAYTransfer` on behalf of users) will receive the KLAY fee refund instead of the originating user. If the wrapper contract has no KLAY withdrawal function, the refunded KLAY is permanently locked. This is an unauthorized diversion of native KLAY from the user to an intermediate contract with no recovery path — a direct asset loss matching the allowed impact gate.

---

### Likelihood Explanation

The ERC20 1-step pattern (`ERC20ServiceChain`) is a first-class supported design in the protocol. Any developer building the equivalent for KLAY (a natural extension) would trigger this bug. The trigger requires only a valid contract caller of `requestKLAYTransfer` with a non-zero `feeLimit` exceeding the actual `feeOfKLAY`. No privileged access is required.

---

### Recommendation

Mirror the ERC20 approach: add an explicit `from` address parameter to `_payKLAYFeeAndRefundChange` and pass `msg.sender` at the call site in `_requestKLAYTransfer`. Any wrapper contract can then pass the actual user's address as `from`, ensuring refunds reach the correct recipient.

```solidity
// BridgeFee.sol
function _payKLAYFeeAndRefundChange(address payable from, uint256 _feeLimit) internal returns(uint256) {
    ...
    if (feeRefund > 0) {
        (bool ok, ) = from.call.value(feeRefund)("");  // refund to actual user
        ...
    }
    ...
    if (_feeLimit > 0) {
        (bool ok, ) = from.call.value(_feeLimit)("");  // refund to actual user
        ...
    }
}

// BridgeTransferKLAY.sol
uint256 fee = _payKLAYFeeAndRefundChange(msg.sender, _feeLimit);
```

---

### Proof of Concept

1. A `KLAYServiceChain` wrapper contract is deployed (analogous to `ERC20ServiceChain`). It holds a reference to the bridge and calls `bridge.requestKLAYTransfer{value: amount + feeLimit}(to, amount, extraData)` on behalf of users.
2. Alice calls `KLAYServiceChain.requestValueTransfer(to, 1 KLAY, extraData)` sending `1.5 KLAY` (1 KLAY value + 0.5 KLAY feeLimit).
3. The bridge's `feeOfKLAY` is `0.1 KLAY`. Inside `_payKLAYFeeAndRefundChange`, `feeRefund = 0.5 - 0.1 = 0.4 KLAY`.
4. The refund is sent to `msg.sender` = `KLAYServiceChain` contract address, not Alice.
5. `KLAYServiceChain` has no `withdraw()` function. Alice's `0.4 KLAY` is permanently locked in the wrapper contract. [5](#0-4) [6](#0-5) [4](#0-3)

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

        }

        }
