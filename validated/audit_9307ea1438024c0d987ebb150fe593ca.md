Analysis of the code confirms this is not exploitable.

**Key mechanics:** `redeem_stake_rewards` (runtime/src/inflation_rewards/mod.rs:97-169) computes `new_delegation_with_rewards = stake.delegation.stake.saturating_add(staker_rewards)` and uses `delegation_may_need_adjustment` only as a boolean gate deciding whether the reward entry is included in the partition, not to compute the actual final delegation value. [1](#0-0) 

The real capping happens later, at distribution time, via `adjust_delegation_for_rent` in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`:

```rust
let new_delegation = std::cmp::min(
    new_delegation_with_rewards,
    lamports_with_rewards.saturating_sub(minimum_lamports),
);
``` [2](#0-1) 

Because this is a `std::cmp::min`, the resulting `new_delegation` can **never exceed** `new_delegation_with_rewards` (which equals `delegation.stake + staker_rewards`), regardless of how large `lamports_with_rewards` (i.e., the attacker-funded balance) is made. Increasing `current_lamports`/`account.lamports()` before the epoch boundary can only push the second `min()` operand higher, which at most removes the rent-based reduction and lets the delegation reach its "natural" value of `delegation.stake + staker_rewards` — it can never push the result above that natural value. The property the question asks to falsify, `new_delegation_with_rewards - delegation.stake <= staker_rewards`, is therefore an algebraic invariant guaranteed by the `min()` construction itself, both in the calculation-time helper `delegation_may_need_adjustment` (`runtime/src/inflation_rewards/mod.rs:177-194`) and the distribution-time `adjust_delegation_for_rent` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:55-76`). [3](#0-2) 

Separately, actual lamport minting into the account (`stake_reward_lamports_minted`, added to `self.capitalization`) is driven by `partitioned_stake_reward.inflation.stake_reward`, computed independently in `calculate_stake_rewards` from vote credits/points — it has no dependency on the attacker's self-funded balance top-up. [4](#0-3) 

Existing tests (`rent_adjusted_stake_delegation_calculations`, `test_delegation_adjustment_at_distribution`) explicitly exercise the "attacker transfers extra lamports before distribution" scenario and confirm the delegation only ever reaches `pre_delegation + legitimate reward`, never beyond it. [5](#0-4)
