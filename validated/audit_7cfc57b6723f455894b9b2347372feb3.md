### Title
Cross-tenant webhook signature confusion allows unauthenticated attacker to archive/unarchive a victim org's ReviewStack - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used to verify the HMAC signature from the attacker-controlled `repository.owner.login` field of the raw JSON body, while `UnlabeledHandler#repository` (and its `pull_request/*` siblings) resolves the actually-mutated `Repository`/`ReviewStack` from the independently attacker-controlled `repository.full_name` field. Because these two fields are never cross-checked and can be set inconsistently in a hand-crafted payload, an attacker can pick an org that is configured in Shipit with no `webhook_secret` (which makes `verify_webhook_signature` return `true` unconditionally) for the `owner.login` check, while pointing `full_name` at a completely different, victim org's repository.

### Finding Description
Binding claimed: `Shipit.github(organization: repository_owner)` (the org whose signature check ran) == the org owning the repository that `UnlabeledHandler#repository` resolves and mutates.

- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , then calls `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(signature, request.raw_post)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/unset: `return true unless webhook_secret` [3](#0-2) . This is a real, documented configuration state (multi-org secrets.yml, per-org `webhook_secret` optional) [4](#0-3) .
- `UnlabeledHandler#repository` resolves the repository purely from `params.repository.full_name`, a separate string field of the same attacker-supplied JSON body, via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) . Note `from_github_repo_name` just splits the string on `/` and does a DB lookup, with no relation at all to `repository.owner.login` [6](#0-5) .
- Nowhere in the code is `repository.owner.login` compared against the owner segment of `repository.full_name`. The `ExplicitParameters` schema for `UnlabeledHandler` only requires `repository.full_name` to be present, and does not require or validate `repository.owner.login` at all [7](#0-6) .
- Attacker's exact request: `POST /webhooks` with `X-Github-Event: pull_request`, body JSON with `action: "unlabeled"`, `pull_request.state: "open"`, `repository.owner.login: "attacker-org"` (an org configured in Shipit's `secrets.github` map with no `webhook_secret`), and `repository.full_name: "victim-org/victim-repo"` naming a real, review-stacks-enabled repo. Any `X-Hub-Signature` value (or none) is accepted because `verify_webhook_signature` short-circuits to `true`.
- Exploit flow: `verify_signature` resolves `Shipit.github(organization: 'attacker-org')`, which has no `webhook_secret`, so it returns `true` regardless of signature bytes → request passes. `Webhooks.for_event('pull_request')` dispatches to `UnlabeledHandler#call` → `#process` → `#repository` looks up `victim-org/victim-repo` via `full_name`, and if that repository has `review_stacks_enabled` and label-based provisioning configured matching the attacker's crafted `pull_request.labels`, `stack.archive!`/`stack.unarchive!` executes on the victim's `ReviewStack` [8](#0-7) .
- Existing guards fail to prevent this: `drop_unhandled_event` and `check_if_ping` don't inspect payload consistency; `verify_signature`'s `rescue Shipit::GithubOrganizationUnknown` only triggers if the attacker names an org not configured in Shipit at all — but the attack requires (and the question specifies) picking a *configured* org with no secret, so this rescue path is never hit; `ExplicitParameters` only enforces types/presence, not cross-field consistency.

### Impact Explanation
This is a payload for one repository (attacker's org/repo, used only to select a lenient signature-verification path) mutating another org's stack — specifically archiving or unarchiving a victim's `ReviewStack`, which per the severity rubric is Critical impact ("a payload for one repository mutating another's stack"). Every `pull_request` handler that derives `repository` solely from `params.repository.full_name` (`UnlabeledHandler`, `LabeledHandler`, `OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `AssignedHandler`, `EditedHandler`, `LabelCapturingHandler`) is subject to the same cross-tenant confusion, so the blast radius spans archiving, unarchiving, provisioning/deprovisioning, and mutating `PullRequest` records across any victim repo, repeatable at will per request with no rate limiting concerns in scope. This is fully unauthenticated — no session, API token, or GitHub credential is required.

### Likelihood Explanation
Preconditions: the Shipit deployment must use the multi-organization GitHub App config (`secrets.github` keyed by org name) and have at least one configured org with `webhook_secret` unset/blank — a real, documented, supported configuration in this codebase (test fixtures `test/dummy/config/secrets_double_github_app.yml` and `test/dummy/config/secrets.yml` show `webhook_secret: # nil` as an accepted config shape) [9](#0-8) . The victim repository must exist in Shipit with `review_stacks_enabled` and a provisioning behavior/label matching what the attacker crafts. Attacker cost is trivial: a single crafted HTTP POST, no GitHub interaction required, fully repeatable.

### Recommendation
In `WebhooksController#verify_signature`, verify the signature using the org actually resolved from `repository.full_name` (not a separately-trusted `owner.login`), and additionally validate that `repository.owner.login` (when present) matches the owner segment of `repository.full_name` before dispatching to handlers. Alternatively, do not treat `verify_webhook_signature` returning `true` for orgs with no configured `webhook_secret` as "verified" — require an explicitly configured secret for any org before accepting webhooks for repositories under that org, and reject/log-and-drop payloads where `repository.owner.login` and `full_name`'s owner disagree.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in the test `Shipit.stubs(:github)`: `attacker-org` with `webhook_secret: nil` (so `verify_webhook_signature` always returns `true`), and set up a real `Shipit::Repository`/`ReviewStack` fixture owned by `victim-org` with `review_stacks_enabled: true` and `provisioning_behavior: :allow_with_label`.
2. Build a `pull_request` `unlabeled` payload where `repository.owner.login == "attacker-org"` and `repository.full_name == "victim-org/victim-repo"`, with `pull_request.state == "open"` and labels missing the provisioning label (so `archive?` is true).
3. `post :create, body: payload.to_json, as: :json` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature`.
4. Assert `response.status == 200` (request accepted despite bogus signature because `attacker-org` has no secret) — confirming `Shipit.github(organization: 'attacker-org').verify_webhook_signature(...) == true` while the signature verified nothing tied to `victim-org`.
5. Assert `victim_stack.reload.archived? == true` — confirming the victim's `ReviewStack` was mutated by a request whose signature-verifying org (`attacker-org`) is not the org owning the mutated repository (`victim-org`), i.e., the equality `verifying_org == owning_org` is false yet the mutation still occurred.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
