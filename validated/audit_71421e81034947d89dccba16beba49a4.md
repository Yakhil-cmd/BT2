### Title
Improper Control of Generation of Code in AA-composed `definition` messages allows an unprivileged trigger sender to influence generated address definitions - (File: aa_composer.js)

### Summary
The Kibana bug class is: a configuration value influenced by an authenticated-but-lower-privileged actor is interpolated into a server-side generated script/definition, and that generated artifact is executed with privileges beyond what the original actor was authorized to reach. The analogous surface in `ocore` is the AA `definition` message app, where an AA's `messages[].payload.definition` field is a template composed from oscript formulas (`{...}`) that are evaluated using attacker-controlled `trigger.data`/`trigger.output`/`params` and then written on-chain as a brand-new address (AA) definition via `aa_composer.js`'s `replace()`/`evaluateAA()` pipeline [1](#0-0) . Any unprivileged unit poster can send a trigger to an AA that dynamically composes a new AA definition using the trigger's own supplied fields, and that generated definition subsequently becomes a first-class, independently addressable AA whose messages (payments, asset issuance, definition changes, etc.) are executed with the full authority of whatever address ends up being derived — this is confirmed to be an intended, tested feature (`test/aa_composer.test.js:922-1011`, `test/aa_composer.test.js:557-649`) [2](#0-1) [3](#0-2) .

### Finding Description
`aa_composer.js`'s `replace()` function walks the AA definition template and, for any string wrapped as `{formula}`, evaluates the formula using the current `trigger`, `params`, `locals`, and `stateVars`, then substitutes the result back into the object — this applies uniformly to every field of the template, explicitly including the `definition` app payload: "note that app=definition is also replaced using the current trigger and vars, its code has to generate `{}`-formulas in order to be dynamic" [4](#0-3) .

Because `trigger.data`, `trigger.address`, and `trigger.output[...]` are fully attacker-controlled (any unprivileged unit poster picks these when they post the triggering unit), an AA author who naively builds a `definition` message whose fields are derived from `trigger.data` effectively lets the trigger sender author part of a new address/AA definition that is then hashed into a `chash160` address and posted on-chain as a `definition` app message (see `test/aa_composer.test.js:944-984`, where `$child_aa` is built inside an `init:` formula from static values, but the pattern of building an entire `["autonomous agent", {...}]` array from formula-composed fields — including ones influenced by trigger data — is exactly the mechanism available to any AA author) [5](#0-4) .

Validation of the resulting definition happens only at the generic `validateAADefinition`/`validateDefinition` level (structural/complexity checks in `aa_validation.js`) [6](#0-5) , and the top-level `definition` app message validation in `validation.js` only checks that `payload.address` matches the chash of `payload.definition` — it performs no semantic check on whether the definition's authorization logic was itself derived from data supplied by an unprivileged party rather than from the AA author's static template [7](#0-6) . This mirrors the Kibana root cause: an insufficiently-validated, user-influenced field is spliced into a generated artifact (there: an ingest pipeline script; here: an on-chain address/AA definition) that is subsequently trusted and executed with authority the originating actor never possessed.

### Impact Explanation
If an AA author writes a factory-style AA (a documented, intended pattern — see the "define new AA and activate it" test) whose `definition` payload's authorization-relevant fields (e.g., `messages[].payload.outputs[].address`, `bounce_fees`, or an embedded `sig`/`hash`/`address` condition) are built from `trigger.data` without the AA author explicitly and correctly constraining the possible values, an attacker who is merely a trigger sender can shape the resulting address definition's spending conditions [8](#0-7) . Since the newly created address is a real, independently funded AA (money is sent to `forwarder_address`/`$child_aa_address` in the same response chain, see `test/aa_composer.test.js:600-611` and `:967-976`), an attacker able to influence the generated definition could redirect payouts, define spending/authentication conditions that favor themselves, or otherwise escalate control over funds that the AA author intended to remain under the AA's own logic — i.e., unauthorized spending / fund loss originating from a single posted trigger, which meets the "concrete unauthorized spending... or AA fund loss" bar.

### Likelihood Explanation
Likelihood depends entirely on third-party AA authors writing "factory" AAs that interpolate `trigger.data` (or other attacker-controlled trigger fields) directly into the `definition` payload without sanitizing/whitelisting the substituted values — a pattern the codebase's own test suite demonstrates and therefore implicitly encourages as a supported idiom (`test/aa_composer.test.js`) [2](#0-1) . `ocore` itself provides no additional guardrail (e.g., taint tracking or restriction preventing trigger-controlled values from reaching authorization-relevant fields of a generated `definition`), so the vulnerability's presence is a property of the platform's generic templating mechanism rather than a specific AA; likelihood of exploitation is governed by how carefully individual AA authors write their oscript, which is outside `ocore`'s control but a direct consequence of the platform allowing unconstrained trigger-data substitution into `definition` messages.

### Recommendation
Add defense-in-depth for the AA `definition`/`definition_template` composition path in `aa_composer.js`'s `replace()`: either (a) disallow trigger/param-controlled sub-formulas from resolving into fields of a generated `definition` payload that affect authorization logic (`sig`, `hash`, `address`, `definition template` args, `attestors`, etc.), or (b) require that such generated definitions be re-validated against a stricter policy that flags when authorization-critical leaves derive from `trigger.*`/`params` rather than AA-author-controlled constants/state vars, surfacing a validation error instead of silently allowing composition. At minimum, document the risk explicitly and provide a lint/test-time warning in `aa_validation.js`'s `validateAADefinition` for `definition` app payloads whose formula ASTs reference `trigger.data`/`trigger.output` inside authorization-relevant subtrees.

### Proof of Concept
Conceptual construction (not confirmed executable without a running Devin session against this repo):
1. Deploy a "factory" AA whose `messages` contains a `definition` app message where `payload.definition` is built via a formula referencing `trigger.data`, e.g. embedding `trigger.data.evil_address` as the payout `address` inside the generated child AA's `messages[].payload.outputs`, following the exact composition style shown in `test/aa_composer.test.js:944-970` [5](#0-4) .
2. An attacker posts a trigger unit to the factory AA supplying `trigger.data.evil_address` = an address they control.
3. The factory AA composes and posts the `definition` message (via `replace()`/`evaluateAA()` in `aa_composer.js:589-618`), creating a new on-chain AA address whose payout logic now sends funds to the attacker's address instead of the intended recipient.
4. Funds subsequently routed to the newly created AA are diverted to the attacker, demonstrating unauthorized spending / fund loss originating from a single posted trigger.

This PoC requires constructing and running the exact oscript/AA definitions end-to-end in a Devin session with the full `ocore` test harness (`test/aa_composer.test.js` patterns) to confirm concretely; the index-based review here confirms the mechanism (`replace()` applying trigger-derived formulas to `definition` payloads) exists and is exercised by existing tests, but does not by itself prove that no additional guard exists elsewhere in the pipeline restricting which sub-fields of a `definition` payload may be trigger-derived.
