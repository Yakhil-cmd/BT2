### Title
Repository-owner spoofing in webhook signature verification allows cross-organization stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the webhook secret to verify a request using `repository_owner` (`params.dig('repository','owner','login')`), while every `Handler` subclass (e.g. `PushHandler`) resolves the target `Repository`/`Stack` using `payload.dig('repository','full_name')` (`Handler#repository_name`). These two values are never checked for consistency, so an attacker who controls a registered GitHub App organization can forge a `repository.full_name` pointing at any other tenant's repo while keeping `repository.owner.login` (and thus the signature) tied to their own org.

### Finding Description
The broken binding is: `Shipit.github(organization: params.dig('repository','owner','login')).verify_webhook_signature(...)` (used to authenticate the request) must equal, in trust scope, the organization backing `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (used to select which stacks get mutated). These are two independently attacker-controlled JSON fields inside the same untrusted payload with no cross-validation.

Code path:
- `WebhooksController#verify_signature` at [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and verifies the HMAC signature with that org's secret.
- `repository_owner` is defined as [2](#0-1)  — read from `params.dig('repository', 'owner', 'login')`.
- After verification passes, `#create` dispatches to handlers with the full raw JSON payload: [3](#0-2) .
- `Handler#repository_name` (base class used by all handlers, including `PushHandler`) resolves the repo from a **different** field: [4](#0-3) .
- `PushHandler#process` iterates `stacks.not_archived.where(branch:)` from that resolved repo and calls `stack.sync_github`, enqueuing `GithubSyncJob`: [5](#0-4) .
- `Shipit.github(organization:)` looks up per-organization config purely by the string key passed in, with no relation to what repository the payload later claims to describe: [6](#0-5) .

Attacker request: an attacker who owns `attacker-org/some-repo` (with `attacker-org` registered as a Shipit `GithubApp` per `docs/setup.md`'s multi-org config) sends `POST /webhooks` with `X-Github-Event: push`, a body where `repository.owner.login = "attacker-org"` but `repository.full_name = "shopify/shipit-engine"`, and `X-Hub-Signature` computed with `attacker-org`'s own `webhook_secret` (which the attacker legitimately possesses since they administer that org's GitHub App/webhook). `verify_signature` fetches `attacker-org`'s `GitHubApp`, verifies successfully against the attacker's own secret, and the request proceeds. `PushHandler` then resolves `shopify/shipit-engine`'s stacks via `repository_name` and enqueues `GithubSyncJob` for `shopify`'s stack, using an `after` SHA the attacker fully controls.

No existing guard catches this: `verify_signature` never compares `repository_owner` against `repository.full_name`'s owner segment; `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` schemas in handlers only validate types/presence, not cross-consistency with the authenticated owner; there is no `Repository`-level check that the syncing organization matches the verified webhook organization.

### Impact Explanation
An attacker in one tenant/org can trigger `GithubSyncJob` against another tenant's stack (e.g. `shopify/shipit-engine`) using a payload never authenticated by that tenant's `webhook_secret`. The `expected_head_sha` (`params.after`) is attacker-supplied, and `GithubSyncJob` will fetch and append commits from the real GitHub repo up to whatever SHA is reachable, potentially causing spurious/forced syncs, unwanted commit ingestion, or stack state changes on a target the attacker doesn't own. Other handlers built on the same `Handler#repository_name` (pull request labeled/unlabeled/assigned/edited/closed) are similarly affected, enabling cross-repo review-stack archiving/unarchiving or pull-request state writes for stacks the attacker never authenticated against. This is a cross-tenant write triggered from a repository whose owner never signed the payload — matching the "payload for one repository mutating another's stack" Critical category.

### Likelihood Explanation
Requires Shipit to be configured in multi-org mode (`Shipit.github(organization:)` with multiple orgs each having their own `webhook_secret`, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section) and requires the attacker to own/administer at least one registered org (trivial — they control their own webhook secret). No Shipit session, API token, or victim secret is required. The attack is a single crafted HTTP POST, fully repeatable against any other configured organization/stack by simply changing `repository.full_name` while keeping `repository.owner.login` and signature tied to the attacker's own org.

### Recommendation
In `WebhooksController#verify_signature`, additionally derive the organization from `payload.dig('repository', 'full_name')` (or equivalently normalize/compare the owner segment of `full_name` against `repository.owner.login`) and reject the request (422) if they diverge before dispatching to handlers. Alternatively, change `Handler#repository_name`/`stacks` resolution to use the same verified `repository_owner` value rather than trusting `full_name` independently, ensuring a single source of truth for "which organization authenticated this payload."

### Proof of Concept
Minitest integration test in `test/controllers/webhooks_controller_test.rb` style:
1. Configure two orgs (`attacker-org`, `shopify`) via `Shipit.stubs(:github)` or fixture secrets similar to `test/dummy/config/secrets_double_github_app.yml`, each with distinct `webhook_secret`.
2. Create `shipit_repositories(:shipit)` (owner `shopify`) with an associated stack tracking branch `master`.
3. Build a push payload: `repository.owner.login = "attacker-org"`, `repository.full_name = "shopify/shipit-engine"`, `ref = "refs/heads/master"`, `after = "<attacker-chosen sha>"`.
4. Stub/mock `Shipit.github(organization: "attacker-org").verify_webhook_signature` to return `true` (simulating a signature validly computed by the attacker with their own secret) — assert this is the org actually queried (`repository_owner == "attacker-org"`).
5. POST to `/webhooks` with `X-Github-Event: push` and any `X-Hub-Signature`.
6. Assert `GithubSyncJob` is enqueued with `stack_id: <shopify stack id>` (i.e., `repository_name == "shopify/shipit-engine" != repository_owner == "attacker-org"`), proving the mismatch was never checked and the shopify stack was mutated by a payload authenticated only against attacker-org's secret.
