### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while the repository/stack actually mutated is selected from the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / `webhook_secret` to validate the `X-Hub-Signature` against solely based on `repository_owner`, a value read directly out of the still-unverified JSON body. Once the signature check passes, the handler that actually performs the write (e.g. `PushHandler`) resolves the target `Stack` using a *different* field from the same unverified body, `repository.full_name`. Because the field that gates cryptographic verification and the field that determines the actual write target are not the same, and neither is cross-checked against the other, an attacker who can produce a validly-signed payload for organization/repo "B" (including the trivial case where "B" has no `webhook_secret` configured) can swap in `repository.full_name` for a stack belonging to a different, unrelated organization "A" and have Shipit act on A's stack.

### Finding Description
The controller's flow is:
1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and fetches `Shipit.github(organization: repository_owner)` to get that organization's `webhook_secret`, then calls `verify_webhook_signature(header, raw_post)`. [1](#0-0) [2](#0-1) 

2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: `return true unless webhook_secret`. [3](#0-2) 

3. Once verification passes, `create` dispatches the *entire raw JSON* to the registered handlers, e.g. `PushHandler`, unmodified. [4](#0-3) 

4. `Handler#stacks` / `#repository_name` resolve the actual `Stack`/`Repository` to mutate using `payload.dig('repository', 'full_name')` — a completely separate field from the one used for signature-organization selection, and one that was never itself bound by the signature check (the signature only proves the *entire raw body* was signed by *some* organization's secret, but the controller trusts the unverified `repository.owner.login` sub-field to decide *which* secret to check against). [5](#0-4) [6](#0-5) 

In a multi-organization deployment (`Shipit.github_organizations`, `github_app_config`), each organization can have its own independent `webhook_secret`, and Shipit's single `/webhooks` endpoint serves all of them without an organization or repository segment in the route. [7](#0-6) 

This breaks the intended equality "the organization whose credential authenticated the request == the organization owning the repository/stack the request mutates." An attacker who can obtain a validly signed webhook body for *any one* organization they legitimately control on the shared Shipit instance (or for an organization configured with no `webhook_secret`, which trivially bypasses the whole check), can then substitute `repository.full_name` (and any other handler-consumed field not itself covered by the signing key selection) to point at a different organization's/repository's stack, and craft a `push`/`status`/`pull_request` payload that Shipit will act on as if it came from that other organization's legitimate GitHub App.

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" boundary called out as Critical impact: an attacker with signing capability for one tenant on a shared Shipit instance (or for an org with no configured secret) can trigger `GithubSyncJob` (`PushHandler`), fabricate commit `Status` records that gate CI checks (`StatusHandler`), or manipulate `Membership`/`PullRequest` state for a completely different organization's stack, none of which they are authorized to touch. This can be leveraged toward triggering an unauthorized deploy/merge on another team's repository.

### Likelihood Explanation
Exploitability requires the deployment to be a multi-organization Shipit instance (multiple `github` entries in secrets, each potentially with distinct `webhook_secret`s) and requires the attacker to control at least one organization's webhook secret (or find one configured without a secret) — this is the documented, supported configuration mode (`Shipit.github_organizations`, `github_app_config`), not a misconfiguration outside the engine's design. No repository write access, session, or `ApiClient` token is needed — only the ability to send an HTTP POST to the shared `/webhooks` endpoint with a validly-signed (or unsecured-org) payload whose `repository.full_name` differs from the organization used to select the verification key.

### Recommendation
After signature verification succeeds, cross-check that the organization that authenticated the request (`repository_owner`, matched to the verifying `GitHubApp`) is the same organization that owns the `repository.full_name` (or `organization.login`) actually used by the handler to locate the `Repository`/`Stack`. Reject the webhook (422) if these do not match, and refuse to treat "no webhook_secret configured" as an automatic pass for organizations that share an installation-serving endpoint with other secured organizations.

### Proof of Concept
1. Configure two organizations in `secrets.github`: `orgA` (has `webhook_secret: SECRET_A`, owns `stack-a`) and `orgB` (has `webhook_secret: SECRET_B`, or no secret at all, owns nothing sensitive).
2. As an attacker who knows `SECRET_B` (or where `orgB` has no secret configured), craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgB" },
    "full_name": "orgA/stack-a"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(SECRET_B, body)>` (or send no valid signature if `orgB` has no secret, since `verify_webhook_signature` returns `true` unconditionally in that case), and set `X-Github-Event: push`.
4. POST to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: "orgB")` and verifies successfully against `orgB`'s secret (or trivially passes if unset).
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgA/stack-a")` and enqueues `GithubSyncJob` for `stack-a`, even though the request was never signed with `orgA`'s secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
