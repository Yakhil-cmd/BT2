### Title
Prosaic contract hash uses unambiguous-free string concatenation, allowing content substitution while preserving the committed hash - (File: prosaic_contract.js)

### Summary
`prosaic_contract.js`'s `getHash()` computes a contract's identity/commitment hash by naively concatenating three free-form fields (`title`, `text`, `creation_date`) with no delimiter, length prefix, or type tagging before hashing. This is the same class of bug as the reported `abi.encodePacked` issue: packing variable-length fields together without an unambiguous encoding makes the mapping from `(fields) -> hash` non-injective, so different `(title, text)` pairs can be crafted to produce an identical hash.

### Finding Description
`getHash` is defined as: [1](#0-0) 

Unlike `object_hash.js`'s `getSourceString`, which was specifically hardened against this exact ambiguity — it type-tags each value (`"s"`, `"n"`, `"b"`), joins components with an explicit `STRING_JOIN_CHAR` (`\x00`), and throws if any string field itself contains that separator byte — `prosaic_contract.getHash` performs a raw `title + text + creation_date` concatenation: [2](#0-1) 

Because `title` and `text` are attacker/user-controlled free text with no length restriction and no check that they don't contain characters that could shift a "boundary" between the two fields, two different `(title, text)` pairs can produce byte-for-byte identical concatenated strings (and thus identical SHA-256 hashes) as long as `title1 + text1 === title2 + text2` and `creation_date` matches. For example, `title="AB", text="CD"` and `title="A", text="BCD"` both concatenate to `"ABCD"`, yielding the same hash.

This hash is used as the primary identifier and integrity commitment for the contract throughout the flow: it's stored as the contract's `hash` when offered (`createAndSend`), used as the primary lookup key (`getByHash`/`getBySharedAddress`), and — critically — it is compared against the `contract_text_hash` field of a `data` message payload found in the on-chain signing unit to confirm that the unit posted to the DAG corresponds to the agreed-upon contract text: [3](#0-2) 

Since the hash is the sole binding between the human-readable contract terms (`title`/`text`) and the on-chain commitment, and the concatenation is ambiguous, a counterparty (or the contract offeror) can construct alternate `title`/`text` values that produce the exact same `hash`/`contract_text_hash` while conveying different substantive terms.

### Impact Explanation
Prosaic contracts are used as legally/financially meaningful agreements between two on-chain-paired parties, secured by a shared address and later referenced via the `contract_text_hash` written into a DAG unit as proof that both parties agreed on specific text. Because the hash function is not an injective encoding of the contract fields, a malicious counterparty could present one version of the contract text during negotiation/display and later produce (or have already produced) a different, boundary-shifted version of `title`/`text` that hashes identically. This lets an attacker deny or substitute the terms a party believed they agreed to (e.g., shifting words between the title and body) while the immutable hash recorded on-chain still validates as "matching." This undermines the non-repudiation guarantee that the entire prosaic-contract mechanism exists to provide, directly causing a party to be bound to (or need to dispute) terms they never actually agreed to, and it can defeat the integrity check performed in `handleReceivedSigningUnit`.

### Likelihood Explanation
Likelihood is High: any unprivileged party who can compose the initial contract offer (`createAndSend`) or influence the negotiated title/text controls fully attacker-chosen strings, with no server-side validation preventing boundary shifting between `title` and `text`. Crafting a colliding pair requires no cryptographic effort — it is a straightforward string-split trick, not a hash-preimage attack, so exploitation is trivial and reliably reproducible.

### Recommendation
Replace the naive concatenation in `getHash` with an unambiguous encoding, consistent with the pattern already used elsewhere in the codebase (`string_utils.getSourceString`/`getJsonSourceString`, which are specifically designed to avoid this class of ambiguity via type tags and an explicit separator that is disallowed inside field values), e.g. `objectHash.getBase64Hash({title, text, creation_date})` instead of `objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date)`. Also add explicit validation to reject `title`/`text` values that could otherwise create parsing ambiguity if a delimiter-based scheme is used instead.

### Proof of Concept
```js
const crypto = require('crypto');
function getHash(contract) {
  return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}

const c1 = { title: "AB", text: "CD", creation_date: "2026-09-15 00:00:00" };
const c2 = { title: "A",  text: "BCD", creation_date: "2026-09-15 00:00:00" };

console.log(getHash(c1) === getHash(c2)); // true - colliding hash for different contract terms
```
This shows the same `hash`/`contract_text_hash` results from two contracts with different actual `title`/`text` content, matching the ambiguous-packed-encoding bug class described in the source report.

function getSourceString(obj) {
	var arrComponents = [];
	function extractComponents(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				if (variable.includes(STRING_JOIN_CHAR))
					throw Error("00 byte in string value in " + JSON.stringify(obj));
				arrComponents.push("s", variable);
				break;
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
				arrComponents.push("n", variable.toString());
				break;
			case "boolean":
				arrComponents.push("b", variable.toString());
				break;
			case "object":
				if (Array.isArray(variable)){
					if (variable.length === 0)
						throw Error("empty array in "+JSON.stringify(obj));
					arrComponents.push('[');
					for (var i=0; i<variable.length; i++)
						extractComponents(variable[i]);
					arrComponents.push(']');
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0)
						throw Error("empty object in "+JSON.stringify(obj));
					keys.forEach(function(key){
						if (typeof variable[key] === "undefined")
							throw Error("undefined at "+key+" of "+JSON.stringify(obj));
						if (key.includes(STRING_JOIN_CHAR))
							throw Error("00 byte in object key in " + JSON.stringify(obj));
						arrComponents.push(key);
						extractComponents(variable[key]);
					});
				}
				break;
			default:
				throw Error("getSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	extractComponents(obj);
	return arrComponents.join(STRING_JOIN_CHAR);
}
