### Title
Saturated scaled cap conversion silently disables supply-cap enforcement after a bad-debt index write-down — (File: common/src/rates/scaling.rs)

### Summary
`calculate_scaled_cap` converts an asset-unit cap into scaled RAY terms using `mul_div_floor_saturating`, which clamps to `i128::MAX` on overflow instead of reverting. `enforce_spoke_cap` then compares post-operation scaled usage against this saturated bound, so once the market's supply index drops below 1 RAY the configured `supply_cap` is silently unenforced — any `supply` entry succeeds regardless of size, with no error, event, or truncation marker. This is the same bug class as the report: a hard limit whose overflow produces a quiet non-error state rather than an enforceable rejection, leaving callers to falsely assume the limit held.

### Finding Description
Cap enforcement for each (spoke, asset) book happens in `enforce_spoke_cap` at `contracts/controller/src/spoke_usage.rs:144-156`:

```rust
let cap_scaled = calculate_scaled_cap(env, cap, decimals, index);
let next_scaled = Ray::from(side.scaled(usage)).checked_add(env, delta_scaled);
assert_with_error!(env, next_scaled <= cap_scaled, side.cap_error());
```

`calculate_scaled_cap` at `common/src/rates/scaling.rs:26-33` computes `floor(cap_ray * RAY / index)` via `fp_core::mul_div_floor_saturating`, documented in its own doc comment to saturate at `i128::MAX` "so the cap check fails open rather than trapping an entry path." The project documentation confirms the reachability conditions: the borrow index never falls below 1 RAY, but the supply index is driven below 1 RAY — down to a floor of `10^24` (`RAY / 1000`) — by the bad-debt write-down formula `new_supply_index = max(10^24, floor(old_supply_index * reduction_ray / RAY))` in `docs/reference/formulas.md:391-394`. `docs/reference/invariants.md` (INV-HALT-03) states the consequence directly: "once saturated, the configured asset-unit limit is not enforced."

The bad-debt write-down is reachable by an unprivileged address through `clean_bad_debt` on a market that has accumulated bad debt after liquidations. Once the supply index sits below 1 RAY (any index in `[10^24, 10^27)`), a supply cap larger than `index/RAY` of the admitted maximum produces a scaled cap of `i128::MAX`, and `next_scaled <= cap_scaled` is vacuously true for every subsequent `supply` call on that spoke — including bulk multi-leg `supply` entries routed through `SpokeUsageContext::apply_entry` at `spoke_usage.rs:102-115`. Like the `SecureStore` warning, the failure is silent: the call succeeds, positions are credited, and nothing signals that the governance-configured exposure bound ceased to apply.

### Impact Explanation
The supply cap is the governance-set bound on how much of an asset a single spoke may lend into the pool. After saturation it is completely unenforced: a single unprivileged account can deposit arbitrarily large amounts of the affected asset — the asset that just produced bad debt — far beyond the intended exposure limit. The protocol silently accumulates uncapped risk in an impaired market, undermining the risk-isolation guarantee that per-(hub, spoke, asset) caps exist to provide, and magnifying the pool's exposure precisely when the market has already proven loss-making. This maps to protocol insolvency risk: post-write-down markets with silently disabled caps can be filled with distressed collateral/debt exposure far beyond configured bounds. Severity is bounded to Medium because the borrow-cap side can never saturate (borrow index ≥ 1 RAY) and the precondition requires a preceding bad-debt event severe enough to push the supply index below 1 RAY.

### Likelihood Explanation
The trigger requires a `clean_bad_debt` write-down deep enough to move the supply index below 1 RAY — i.e., bad debt large enough that `floor(old_index * remaining/total_supply)` lands under `10^27`. Such events are rare but are exactly the tail-risk scenario caps are meant to bound, and the write-down clamps at the `10^24` floor rather than reverting, so the vulnerable window persists indefinitely until the index re-accrues above 1 RAY. Once in that window, exploitation is a single ordinary `supply` call by any unprivileged address; there is no cap error, no event, and no telemetry distinguishing an enforced cap from a saturated one.

### Recommendation
Reject on cap-conversion overflow instead of saturating: use a checked `mul_div_floor` in `calculate_scaled_cap` and panic with the side's cap error (or a dedicated overflow error) when `cap_ray * RAY` overflows `i128` at the live index. If fail-open is a deliberate design choice for liveness, at minimum emit an event when `cap_scaled` saturates so indexers and risk monitoring can detect that the configured cap is no longer binding, and add a regression test that supplies beyond the configured cap after a simulated write-down to `index < RAY`.

### Proof of Concept
1. Establish a market where a borrower accrues unbacked debt (e.g., collateral value collapses; liquidation leaves residual debt against insufficient supply-side backing).
2. An unprivileged address calls `clean_bad_debt` on the pool/controller for that `HubAssetKey`. The write-down computes `reduction_ray = floor((total_supply_ray - bad_debt_ray) * RAY / total_supply_ray)` and stores `new_supply_index = max(10^24, floor(old_index * reduction_ray / RAY))`, pushing `supply_index < 10^27`.
3. The same or another unprivileged address calls `controller.supply` with legs for that `HubAssetKey` totaling more than the configured `supply_cap`. Inside `process_supply`, `apply_entry` → `enforce_spoke_cap` calls `calculate_scaled_cap(cap, decimals, supply_index)`; the division `cap_ray * RAY / supply_index` overflows `i128` and saturates to `i128::MAX`, so `assert_with_error!(next_scaled <= cap_scaled, SpokeSupplyCapReached)` passes for any `next_scaled`.
4. The supply succeeds and the position is credited; `SpokeUsageRaw.supplied_scaled_ray` now corresponds to an asset-unit exposure exceeding `supply_cap`, with no error or event emitted.
