## Analysis

This bug class matches a real design characteristic of `spender_attested` assets in ocore. When an asset is defined with `spender_attested: true`, the asset definer must maintain a whitelist of trusted `attestors` [1](#0-0) . The *definer* can freely republish this list at any time via an `asset_attestors` message, and validation always uses only the **most recent** attestor list, computed dynamically each time the asset is read [2](#0-1) .

Whenever a `payment` message moves this asset — whether it is an `issue` or an ordinary `transfer` — `validatePaymentInputsAndOutputs` requires **every output address** to currently be attested against that latest attestor list, with no exception carved out for spending/redeeming already-held balances: [3](#0-2) 

The attestation check itself (`filterAttestedAddresses`) matches only against the asset's *current* `arrAttestorAddresses` [4](#0-3) , so as soon as the definer removes an attestor (or replaces the whole attestor whitelist) an address that was previously attested by the now-removed attestor stops counting as attested for all future payments of that asset.

Because divisible payments almost always require a change output back to the spender when the whole balance isn't consumed in one output, a holder who becomes "de-whitelisted" this way can no longer even redeem/transfer their existing balance — any attempt that produces a change output to their own (now unattested) address is rejected with `"some output addresses are not attested"`, even though the tokens were legitimately acquired while the holder was attested. This mirrors the reported UXDController pattern: removing an actor from a whitelist blocks legitimate withdrawal/movement of already-issued balances rather than only blocking new issuance, and it is entirely under the control of the asset definer, an in-scope "asset issuer" persona.

### Title
Spender-attested assets can permanently freeze already-issued balances when the attestor whitelist is updated - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, `validatePaymentInputsAndOutputs` enforces the attestation check on every payment output regardless of whether the payment is an `issue` or a plain `transfer`/redemption of previously issued coins. The set of valid attestors is always taken from the latest `asset_attestors` unit published by the definer, so a later whitelist update instantly invalidates the attested status of any address that relied on a removed attestor.

### Finding Description
`readAsset`/`addAttestorsIfNecessary` always resolves `objAsset.arrAttestorAddresses` from the most recently published `asset_attestors` list [2](#0-1) . `filterAttestedAddresses` then checks each candidate address against attestations issued only by attestors in that current list [4](#0-3) . The payment-validation path applies this exact check to `arrOutputAddresses` unconditionally — for `bIssue` or ordinary transfers alike — with no distinction between "minting new units" and "moving/redeeming already-held units":

```
if (!objAsset.spender_attested) return cb();
storage.filterAttestedAddresses(conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses, ...)
``` [3](#0-2) 

The asset definer can update the attestor whitelist at will via `asset_attestors`, subject only to being the definer [1](#0-0) . Once an attestor a holder relied on is dropped from the list, that holder's address is no longer "attested," and any subsequent payment of this asset that would produce an output to that address (including a mandatory change output when only partially spending) is rejected.

### Impact Explanation
A holder of a `spender_attested` asset can be permanently prevented from moving or redeeming coins they legitimately hold, purely because the definer rotated/pruned the attestor whitelist (e.g., replacing a compromised or discontinued attestor service) — an action unrelated to the holder's own conduct. This is a fund-freezing condition: balances become stuck at the address, unable to be transferred out via any payment that requires a change output back to the (now unattested) sender, matching the reported bug class where whitelist maintenance blocks legitimate withdrawal instead of only blocking new issuance.

### Likelihood Explanation
Any asset definer who legitimately rotates or updates their attestor list (a normal administrative action explicitly supported by the protocol) can trigger this for existing holders without intending to freeze funds. No malicious behavior by the attestor, node, or network is required — it is a consequence of the asset's own validation rules on ordinary transfer/redeem payments.

### Recommendation
Do not require the attestation check for outputs on transfer payments that merely return/consolidate a holder's own already-attested balance (e.g., exempt self-addressed change outputs), or alternatively evaluate attestation against the attestor list that was current when the coins were most recently received rather than the always-latest list, mirroring "Option 1/2" from the original report (allow spending/redeeming even if the current whitelist would reject a *new* issuance/transfer to a de-whitelisted party).

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and attestor `T1`.
2. `T1` attests address `H`; `H` receives units of `A` (issue or transfer to `H`, output attested — succeeds).
3. Definer publishes a new `asset_attestors` message listing only `T2` (dropping `T1`).
4. `H` attempts to transfer part of its balance of `A` to any address; the payment must include a change output back to `H`.
5. `validatePaymentInputsAndOutputs` calls `filterAttestedAddresses` with the *new* attestor list (`T2` only); `H` is not attested by `T2`, so the change output fails `"some output addresses are not attested"` [5](#0-4) .
6. `H`'s remaining balance of `A` is now permanently unspendable/unredeemable through any partial transfer.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
