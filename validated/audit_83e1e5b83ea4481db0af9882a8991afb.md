### Title
Cross-repository status webhook forgery mutates victim stack's CI-enabled state via unscoped SHA lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) by SHA alone — `Commit.where(sha: params.sha)` — without ever checking `payload['repository']['full_name']` against the commit's stack repository, unlike every other webhook handler in this engine which scopes lookups through `Handler#stacks` / `Repository.from_github_repo_name`. Any commit that shares a SHA across two Shipit-tracked stacks (trivial via a public fork, since git commit hashes are deterministic content hashes) lets a `status` event genuinely emitted by repository R2 create a `Status` and flip `Stack#ci_enabled?` for an unrelated stack S1.

### Finding Description
Binding claimed: `Status#stack (via commit.stack) == repository that emitted the webhook (payload['repository']['full_name'])`.

Trace:
- `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('status') => [Handlers::StatusHandler]` [1](#0-0) , after `verify_signature`, which is computed per `repository_owner`, not per exact repository [2](#0-1) .
- `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This never reads `payload['repository']['full_name']` and never uses the base class's repository-scoped `stacks` helper, unlike `PullRequest::*Handler`s which call `stacks`/`Repository.from_github_repo_name(repository_name)` [4](#0-3) .
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!(stack_id, github_status)` → `Status.find_or_create_by!(stack_id:, state:, ...)` on the commit's *own* `stack_id`, which is whatever stack the pre-existing `Commit` row belongs to — not necessarily the repository that sent the webhook [5](#0-4) , [6](#0-5) .
- `Status` has `after_create :enable_ci_on_stack`, which unconditionally calls `commit.stack.enable_ci!` [7](#0-6) .
- `Stack#enable_ci!` writes `Rails.cache.write(ci_enabled_cache_key, true)` with no expiry and no correlation to the originating repository [8](#0-7) .

Exploit: attacker owns/controls repository R2 (e.g., a public fork of victim's repo R1, which shares identical commit objects and therefore identical SHAs for the forked history), and R2 already has a working Shipit webhook (attacker capability explicitly includes "emit webhooks from a repository they own"). Attacker triggers (or crafts, if the app is publicly installable) a `status` event on R2 for a SHA `X` that Shipit already has recorded as a `Commit` under victim stack S1 (put there by S1's legitimate push history). The webhook signature check only validates `repository_owner` against the app config for that owner/org — it does not tie the payload to the specific repository that "should" own the commit — so a legitimately signed event from R2 passes `verify_signature`. `StatusHandler#process` then matches `Commit.where(sha: X)` which returns the S1 commit row and creates a `Status` on it, triggering `enable_ci_on_stack` and flipping `S1.ci_enabled?` to `true` in cache, permanently, from R2's traffic alone.

Existing guards fail because: `verify_signature` only authenticates that *some* webhook for `repository_owner` is legitimate, not that the specific commit/stack targeted belongs to that repository; `ExplicitParameters` schema for `StatusHandler` only validates shape (`sha`, `state`, etc.), not repository ownership; and `Handler#stacks`/`repository_name` scoping exists in the base class but is simply not invoked by `StatusHandler`.

### Impact Explanation
The attacker causes a database write (`Status` record) and a cache write (`ci_enabled_cache_key` for stack S1) attributable to a repository (R1/S1) that never authenticated or emitted the event — this is exactly "a payload for one repository mutating another's stack" (Critical bucket). Because `ci_enabled?` gates deploy/CI-dependent logic downstream (`Stack#ci_enabled?` is read elsewhere to decide CI-gating behavior), and the cache write persists indefinitely (no TTL, no automatic rollback if the forged `Status` is later deleted/disputed), this is a durable cross-tenant state corruption. It is repeatable against any stack S1 for which the attacker can find/produce a SHA collision (most easily via forking a public repo tracked by Shipit), and the blast radius spans every stack whose commits collide with an attacker-controlled repository's commits.

### Likelihood Explanation
Preconditions: (1) victim stack S1's tracked repository is public/forkable so the attacker can reproduce identical commit SHAs in a repository they own (R2); (2) R2 has (or the attacker can obtain) a validly signed webhook channel to the Shipit host — this matches the stated attacker capability of "emit webhooks from a repository they own" and requires no secrets, sessions, or elevated GitHub roles. Cost is low: fork the repo, ensure Shipit tracks the fork or trigger a genuine `status` webhook from GitHub for a SHA that also exists in S1. This is repeatable per SHA/stack pair with no rate limiting concerns in scope.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the repository derived from `payload['repository']['full_name']` in addition to `sha`, mirroring the `stacks` helper already used by the `PullRequest::*` handlers, e.g. iterate `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status from repository R2 flips ci_enabled? for unrelated stack S1 sharing a commit sha" do
          s1 = shipit_stacks(:shipit) # victim stack, repo R1
          r2_repo_full_name = "attacker/r2"       # attacker-owned repo, unrelated to s1
          shared_sha = shipit_commits(:first).sha # sha already present under s1

          assert_equal shipit_commits(:first).stack_id, s1.id
          refute Rails.cache.fetch(s1.ci_enabled_cache_key)

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/forged',
            'repository' => { 'full_name' => r2_repo_full_name }
          }

          StatusHandler.call(payload)

          # Equality check: stack whose CI flag flipped vs stack of repository that emitted the event
          assert_equal true, Rails.cache.fetch(s1.ci_enabled_cache_key) # BROKEN: flips victim S1's flag
        end
      end
    end
  end
end
```
This demonstrates that a `status` payload whose `repository.full_name` is an unrelated, attacker-owned repository (`R2`) still mutates `Stack#ci_enabled?` for victim stack `S1` purely because the SHA matches a pre-existing `Commit` row, confirming the binding violation traced above.
