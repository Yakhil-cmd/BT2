I have sufficient evidence to confirm this vulnerability. The `StatusHandler` at `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` creates a `Status` record directly from webhook payload fields (`state`, `description`, `target_url`, `context`) by looking up `Commit.where(sha: params.sha)` — a match purely on SHA across the entire installation, with no re-verification against `repository.full_name` or `repository.owner.login`. Combined with the org/repo binding gap in `verify_signature`, this is exploitable.

### Title
Webhook signature verification binds trust to `repository.owner.login`, not to the `repository.full_name` actually acted upon, allowing cross-organization status/event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to use for HMAC verification based solely on `repository_owner` (`params.dig('repository','owner','login')` or `organization.login`), then treats the entire raw payload as trusted once that single field's owner matches a configured org. Every downstream handler, however, acts on a *different* field of the same payload — `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) for most handlers, or, in the case of `StatusHandler`, an even weaker binding: a bare commit `sha` lookup across the whole database (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) with no repository/owner cross-check at all.

### Finding Description
In a multi-tenant deployment (explicitly supported and documented in `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github_app_config`), Shipit maintains one GitHub App (and one `webhook_secret`) per organization key in `config/secrets.yml`. When a webhook arrives: [1](#0-0) 

`repository_owner` is read from the JSON body itself, and `Shipit.github(organization: repository_owner)` looks up the app config for *that* org to fetch its `webhook_secret` and validate `X-Hub-Signature`. This ties cryptographic trust only to the equality: `signature == HMAC(webhook_secret[repository.owner.login], raw_body)`.

Once verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the *entire* parsed body to handlers, which key off `repository.full_name` (a sibling field never checked against `repository.owner.login`): [2](#0-1) 

Nothing in the request pipeline enforces `repository.full_name.start_with?("#{repository.owner.login}/")`. An org that legitimately controls its own GitHub App installation (and therefore its own `webhook_secret`, which is disclosed to that org's admins/CI during app setup per `docs/setup.md`) can produce a validly-signed webhook whose `repository.owner.login` is their own org (so it authenticates), while `repository.full_name` names a stack belonging to an entirely different tenant on the same shared Shipit instance.

The `StatusHandler` makes this materially worse because it doesn't even require `repository.full_name` to be checked — it matches purely by commit SHA globally: [3](#0-2) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` creates a `Status` (state/description/target_url/context taken verbatim from the forged payload) for *any* commit in *any* stack across the whole Shipit instance that happens to share that SHA — and SHAs are attacker-influenceable/guessable (e.g., commits cherry-picked/rebased across repos, or an attacker-controlled repo deliberately crafted to produce a colliding/duplicate commit that also exists in a victim's tracked branch).

This breaks the deployment-trust binding described as: "an organization that authenticated versus the repository that is written."

### Impact Explanation
A forged `status` event can inject a fabricated `state: "success"` for a commit on a victim stack. `Status#after_create :enable_ci_on_stack` and `schedule_continuous_delivery` (`app/models/shipit/status.rb:18-19`) feed directly into `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`, `!locked? && (stack.ignore_ci? || (success? && !blocked?))`), which gates `Stack#deployable?` and continuous deployment (`app/models/shipit/stack.rb:376-378`, `test/models/commits_test.rb:233-243` showing CD triggers off a status create). An attacker who only controls their own org's GitHub App installation can therefore mark an untested/malicious commit on someone else's tracked stack as CI-green, causing an unauthorized/unreviewed deploy to proceed via continuous deployment — meeting the "unauthorized deploy" bar. `PushHandler` and `pull_request` handlers are somewhat mitigated because they trigger a re-sync against the real GitHub API (`stack.sync_github`), but `StatusHandler` writes attacker-controlled data straight into the trust decision with no such reconciliation.

### Likelihood Explanation
Requires the attacker to be an admin/owner of at least one organization that is a legitimate, separately configured tenant on the same shared Shipit instance (so they know/control that org's `webhook_secret`), plus knowledge or reproduction of a target commit SHA tracked by another tenant's stack. This is a realistic scenario for any shared/hosted Shipit deployment serving multiple orgs, which the engine explicitly supports and documents.

### Recommendation
- In `WebhooksController`, after verifying the signature against `repository_owner`'s secret, additionally assert that `params.dig('repository','full_name')` (and any other repository identifiers used downstream) belongs to that same verified owner before dispatching to handlers.
- In `StatusHandler`, scope the `Commit.where(sha: ...)` lookup by the repository/stack derived from the verified `repository.full_name`, not by a bare global SHA match, mirroring what `Handler#stacks`/`Handler#repository_name` already does for other handlers.

### Proof of Concept
1. Configure Shipit in multi-org mode with `AttackerOrg` and `VictimOrg` each having their own installed GitHub App and `webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker (an admin of `AttackerOrg`) obtains `AttackerOrg`'s `webhook_secret` (they set it up themselves) and identifies a commit `sha` that exists on a `VictimOrg`-owned stack tracked by Shipit.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body `{"sha": "<victim-commit-sha>", "state": "success", "context": "ci/whatever", "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "AttackerOrg/irrelevant-repo"}}`, and `X-Hub-Signature` computed with `AttackerOrg`'s `webhook_secret`.
4. `verify_signature` resolves `repository_owner` = `AttackerOrg`, fetches `AttackerOrg`'s app, and the signature verifies successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the matching commit under `VictimOrg`'s stack (no ownership check performed), and creates a `success` `Status` on it, potentially triggering continuous deployment of that commit on `VictimOrg`'s infrastructure.
