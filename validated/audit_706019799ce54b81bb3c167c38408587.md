## Analysis

The `enrollCourier()` bug class — a permissionless "claim‑an‑id‑first" function where `require(couriers[id].cut == 0)` lets a front‑runner seize an identity slot and its associated permanent economic rights — has a direct analog in the `initialize()` pool‑creation instruction.

### Title
Front-Running of Pool Creation Permanently Steals `pool_creator` Fee-Collection Rights - (File: `programs/cp-swap/src/instructions/initialize.rs`)

### Summary
`initialize()` derives the `pool_state` PDA deterministically from `[POOL_SEED, amm_config, token_0_mint, token_1_mint]` and, once created, permanently binds `pool_creator = ctx.accounts.creator.key()` (the `msg.sender`-equivalent signer) into `PoolState`. This is functionally identical to the `enrollCourier()` pattern: a slot (the pool for a given config/mint pair) can only be claimed once, and whoever's transaction lands first permanently owns the associated privilege — here, the right to collect `creator_fees_token_0`/`creator_fees_token_1` forever via `collect_creator_fee`/`collect_creator_fee_permissionless`.

### Finding Description
`create_pool()` computes the expected PDA and requires the target account be system-owned (uninitialized) before allocating it: [1](#0-0) 

Once initialized, `pool_state.initialize(...)` records `ctx.accounts.creator.key()` as the pool's `pool_creator`, which cannot be changed afterward: [2](#0-1) 

That `pool_creator` field is the sole authority over creator-fee withdrawal in both the permissioned and permissionless collection paths: [3](#0-2) [4](#0-3) 

Because a legitimate user's `initialize` transaction (with chosen `amm_config`, `token_0_mint`, `token_1_mint`) is public in the mempool before confirmation, an attacker can observe it, front-run with the same three PDA-seed accounts (and their own equivalent liquidity amounts and token accounts), and get their own `initialize` transaction confirmed first. The victim's transaction then reverts (`pool_account_info.owner != &system_program::ID` fails the `NotApproved`-style check), and the attacker is permanently recorded as `pool_creator` for that config/mint-pair pool. All future creator-fee revenue generated by swaps against that pool (`creator_fee` computed in the curve, e.g. `Fees::split_creator_fee`) accrues to the attacker instead of the intended deployer.

### Impact Explanation
This is an unauthorized privileged effect and a permanent diversion of protocol-designed fee revenue: the attacker gains perpetual rights to `collect_creator_fee`/`collect_creator_fee_permissionless` on a pool the victim intended to own and be compensated from, for as long as that pool exists and trades. The legitimate creator is denied the incentive stream that the `pool_creator` mechanism was designed to grant, mirroring exactly the "loss of incentives" and "denial of registration" impact described in the reference finding for `enrollCourier()`.

### Likelihood Explanation
The `POOL_SEED` PDA (`amm_config`, `token_0_mint`, `token_1_mint`) is fully attacker-computable from public information (well-known AMM config accounts and mint addresses), and Solana transactions broadcasting an `initialize` call are visible pre-confirmation, making front-running straightforward for anyone monitoring pending pool-creation transactions for a desirable/high-volume token pair. The attacker only needs to supply matching liquidity into `creator_token_0`/`creator_token_1`, which is a bounded, known cost relative to the perpetual fee stream gained.

### Recommendation
Do not bind `pool_creator` to the first signer of a racable, deterministically-seeded PDA without additional protection. Options include: requiring the `pool_state` PDA creation to be a signed/randomized account (as already supported via the `random_pool_id` path in the client) for cases where creator identity matters, adding a commit-reveal or fee/deposit-gated creation step, or allowing the intended creator to update/reassign `pool_creator` via a governance/verification step if front-running is detected.

### Proof of Concept
1. Victim submits `initialize(amm_config=C, token_0_mint=M0, token_1_mint=M1, init_amount_0, init_amount_1, open_time)`, computing `pool_state` PDA = `find_program_address([POOL_SEED, C, M0, M1])`.
2. Attacker observes this pending transaction, and submits their own `initialize` call with the same `amm_config`, `token_0_mint`, `token_1_mint` (same PDA), supplying their own liquidity amounts into `creator_token_0`/`creator_token_1`, with higher priority fee/compute unit price.
3. Attacker's transaction lands first; `create_pool()`'s `pool_account_info.owner != &system_program::ID` check now fails for the victim's now-redundant transaction, causing it to revert with `NotApproved` [5](#0-4) .
4. `pool_state.pool_creator` is permanently set to the attacker's key [6](#0-5) .
5. As swaps occur on the pool, `creator_fee` accumulates in `PoolState.creator_fees_token_0/1`, and only the attacker (as `pool_creator`) can withdraw it via `collect_creator_fee`/`collect_creator_fee_permissionless` [7](#0-6) .
