## Analysis

Found a valid analog. The bug-class in the report is "a field that is used to authorize/verify an action is disconnected from the field that actually determines what gets mutated." In Shipit, the equivalent binding is: **the GitHub organization whose secret verifies the webhook signature ≠ the repository/stack whose data is actually written by the handler.**

### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler` lets a webhook authenticated for one GitHub organization write commit statuses onto stacks belonging to any other organization - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate an inbound webhook using the organization derived from the payload (`repository.owner.login` or `organization.login`), then dispatches the whole payload to the registered handler for the event. [1](#0-0) [2](#0-1) 

Every other webhook handler re-derives the target scope from the same payload's `repository.full_name` before acting, via the shared `Handler#stacks`/`Handler#repository_name` helpers. [3](#0-2) 

`StatusHandler`, however, never consults `repository` at all - it looks up commits globally by SHA and mutates whatever it finds:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

### Finding Description
The equality that should hold is:
`organization_that_authenticated(signature) == organization_that_owns(commit_being_written)`

Before the payload is verified, `WebhooksController#repository_owner` reads `repository.owner.login` (or `organization.login`) purely to pick which `GitHubApp`/`webhook_secret` performs HMAC verification: [1](#0-0) . This mirrors the multi-tenant configuration documented in `docs/setup.md`, where each GitHub organization installed against the same Shipit instance gets its own `app_id`/`installation_id`/`webhook_secret`. [5](#0-4)  and is echoed in `lib/shipit.rb#github_app_config`. [6](#0-5) 

Once the signature check passes (proving only that the request was signed by *some* configured organization's secret - the org the attacker's own repository is installed under), `Shipit::Webhooks.for_event('status')` invokes `StatusHandler.call(params)`. [7](#0-6)  `StatusHandler#process` performs `Commit.where(sha: params.sha)` with no filter on `repository`/`stack`/`organization`, so if a commit with that SHA exists under **any** stack in the installation - belonging to a completely different, unrelated organization - its status gets overwritten. [4](#0-3) 

Contrast this with `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*Handler`s, which all resolve `Repository.from_github_repo_name(repository_name)` first and then scope their side effects to that repository's stacks. [8](#0-7) [9](#0-8)  `StatusHandler` is the outlier that trusts the verified-organization boundary to also imply repository ownership of the target commit, which it does not.

Commit statuses reported through this path are exactly what `ci.require` in `shipit.yml` checks before allowing a deploy or a pull request merge. [10](#0-9) 

### Impact Explanation
An entity that operates its own GitHub organization/repository with the Shipit GitHub App installed (and therefore possesses that organization's legitimate `webhook_secret`, satisfying `verify_webhook_signature`) can forge a `status` webhook naming a commit SHA that exists in a victim organization's stack (SHAs of public commits are frequently observable), and set `state: success` for whatever `context` the victim's `ci.require` demands. This lets an attacker outside the victim organization's trust boundary manufacture a passing CI check on the victim's commit, unblocking an unauthorized deploy or PR merge on the victim's stack - satisfying the "unauthorized deploy, rollback, or merge" High-impact criterion, without ever holding an `ApiClient` token, session, or write access to the victim repository.

### Likelihood Explanation
Requires only: (1) control of any GitHub organization/repository configured on the same multi-tenant Shipit instance (a normal, unprivileged customer of the installation, not the victim), and (2) knowledge of a target commit SHA in the victim's repository (commit SHAs are frequently public). No GitHub write access, ApiClient token, or Shipit session is needed - only the ability to send a raw HTTP POST to `/webhooks` with a signature computed from the attacker's own org's secret.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, matching the pattern used by every other handler:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Repository.from_github_repo_name(repository_name)` before touching `Commit`, so the verified organization can only mutate state that belongs to its own repository.

### Proof of Concept
1. Attacker controls `github.com/attacker-org/whatever`, installed on the shared Shipit instance with its own `webhook_secret` (`S_attacker`), per the multi-org config documented in `docs/setup.md`. [5](#0-4) 
2. Attacker observes/obtains a commit SHA, `deadbeef...`, that is deployed on victim-org's Shipit stack (public repo commit history).
3. Attacker crafts a JSON body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required-check",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(S_attacker, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC verifies successfully since the attacker legitimately owns that secret. [1](#0-0) 
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")` - which matches the victim's commit record regardless of `repository.full_name` in the payload - and calls `create_status_from_github!`, writing a forged "success" status onto the victim's commit. [4](#0-3) 
7. If the victim's `shipit.yml` gates deploys/merges on that `context` via `ci.require`, the forged status unblocks an unauthorized deploy or merge on the victim's stack.

If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
