### Title
Malicious swap-route venue can join the caller’s authorization tree and drain unrelated wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
User-controlled `StrategySwap` bytes allow a route to place attacker-controlled code below a signed controller or router call. That code can invoke `token.transfer(caller, attacker, amount)`; Soroban simulation records it as a child of the caller’s authorization entry. If the generated tree is signed, the unauthorized-looking transfer succeeds even though the lending operation only needed authorization for the strategy itself.

### Finding Description
Controller strategy entrypoints accept caller-supplied route bytes:

- `swap_collateral(caller, account_id, current, from_amount, new, swap)`
- `swap_debt(caller, account_id, existing_debt, new_debt_amount, new_debt, swap)`
- `multiply(..., swap, initial_payment, convert_swap)`
- `repay_debt_with_collateral(..., swap)`

For `swap_collateral`, `process_swap_collateral` authenticates the caller, authorizes the account owner or delegate, and passes `swap` into `withdraw_and_swap_from_supply`. The shared router helper in `contracts/controller/src/strategies/swap.rs` then calls the configured router with those uninterpreted bytes. It protects only the controller’s own input balance: it authorizes one exact controller-to-router input transfer, rejects measured overspend, refunds controller-held input, and requires positive measured output.

Those checks do not constrain what a route-designated venue or pool does while it is below the caller’s authorization context. A malicious venue can call an unrelated token’s `transfer` function with the caller as `from`. During transaction simulation, that invocation is attached as a child of the caller’s controller authorization. Signing the simulated tree therefore authorizes both the intended strategy and the malicious transfer.

The repository contains a direct reproduction in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: a rogue hop pool transfers Alice’s entire unrelated wallet-token balance to the attacker, simulation records the theft as a child of her `swap_collateral` authorization, and enforcing mode succeeds when that poisoned tree is signed. The honest authorization tree rejects the transfer, demonstrating that the theft depends on the extra dynamically recorded child rather than an intended lending allowance.

### Impact Explanation
This is theft of user funds. The stolen assets need not be the swap input, output, supplied collateral, or any token listed by the protocol. The route minimum, controller balance-delta checks, and final account risk checks do not bound the loss because the malicious venue transfers tokens directly from the caller’s wallet to the attacker.

A victim can receive a seemingly successful collateral swap while losing unrelated tokens held by the same address. The same authorization-tree poisoning pattern applies to other route-bearing controller strategies and to direct router swaps.

### Likelihood Explanation
Likelihood is moderate. The attacker cannot unilaterally drain an arbitrary account: the victim must initiate a route-bearing operation and sign the poisoned authorization tree. However, routes and authorization trees are commonly produced by simulation/tooling, and the malicious transfer appears as a nested authorization rather than as an obvious top-level transaction argument. An attacker who supplies or convinces a user to use a poisoned route can exploit any unprivileged strategy entrypoint that accepts `StrategySwap` bytes.

### Recommendation
Do not allow route payloads to name arbitrary executable venue/pool addresses. Restrict router hop targets to a governance-maintained allowlist of reviewed venue contracts, and bind each allowed venue call to the expected adapter ABI.

At the integration boundary, clients should also reject any authorization tree containing unexpected children. This is defense in depth, not a substitute for on-chain validation. The controller documentation and integration checks should explicitly state that an honest controller strategy must not add caller-authorized child invocations beyond the expected token pull.

### Proof of Concept
The included test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` demonstrates the full primitive:

1. Alice supplies USDC and owns a `swap_collateral` account.
2. The attacker deploys a route-designated pool containing a plan to call `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`.
3. Alice invokes `swap_collateral` with route bytes naming that pool.
4. The pool pays a valid-looking swap output, while its nested code calls the unrelated wallet token.
5. Simulation records that transfer beneath Alice’s `swap_collateral` authorization.
6. Signing the recorded tree transfers `WALLET_BALANCE` from Alice to the attacker while also crediting the expected swap output.

The companion enforcing-mode test shows the transfer fails with the honest root-only authorization tree and succeeds when the simulated poisoned tree is signed.
