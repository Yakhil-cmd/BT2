## Finding

I found a valid analog. The break is between the **organization whose webhook secret authenticated the request** and the **stack/commit that is actually mutated**, exactly mirroring the "compare related values before acting" bug class from the report.

### Title
Cross-organization forged CI status triggers unauthorized merges and deploys - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using an attacker-supplied field from the very payload being verified (`repository.owner.login`), while `StatusHandler#process` never re-checks that the `sha` in the same payload belongs to a repository/stack owned by that verified organization — it queries `Commit` globally by SHA across the entire Shipit installation.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret based on `repository_owner`, which is read straight out of the JSON body: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub organizations, each with its own `webhook_secret`, selected by this same `organization` key: [3](#0-2) [4](#0-3) 

Once the signature check passes (using **whatever org's secret matches `repository.owner.login`**), `StatusHandler#process` looks up the target commit **globally by `sha` alone, with no scoping to the authenticated organization's repositories or stacks**: [5](#0-4) 

That status update flows into `Commit#add_status`, which schedules real, consequential actions: emitting `deployable_status`, and — critically — `stack.schedule_merges` (`ProcessMergeRequestsJob`) whenever the new state is `pending` or `success`: [6](#0-5) 

`ProcessMergeRequestsJob` merges pending pull requests once their status checks appear to pass: [7](#0-6) 

Separately, `Status` triggers continuous delivery on its owning stack: [8](#0-7) [9](#0-8) 

The equality that should hold but doesn't: `organization_that_signed_request == organization_owning(commit.stack.repository)`. Before the attack: any org's own webhook events only ever carry a `sha` that genuinely belongs to that org's repo (GitHub itself generates the payload). After the attack: an attacker who merely knows/controls the webhook secret for **any one** organization configured on the Shipit instance (e.g., their own, less-trusted org in a multi-org deployment, whose webhook secret they can view/rotate in that org's own GitHub App settings) can self-sign an arbitrary JSON body and set `sha` to a commit belonging to a **completely different** organization's stack, with no relation between the two enforced anywhere in the request path.

### Impact Explanation
This breaks the binding "an organization that authenticated versus the repository that is written," and results directly in **unauthorized merges and unauthorized deploys** on a stack the attacker has no legitimate access to — matching the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability only requires knowledge of one organization's webhook secret in a Shipit install that manages multiple GitHub organizations (a documented, supported configuration) — plus the target SHA, which is often public (e.g., visible in a public PR/commit). No Shipit session, API token, or write access to the target repository is needed.

### Recommendation
`StatusHandler` (and other handlers that key off `sha`/`repository.full_name`) must verify that the resolved `Stack`/`Repository` actually belongs to the same organization that was used to select the webhook secret in `verify_signature`, rejecting the event otherwise.

### Proof of Concept
1. Shipit is configured with orgs `AttackerOrg` and `VictimOrg`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org config).
2. Attacker, an admin of `AttackerOrg`, retrieves `AttackerOrg`'s `webhook_secret` from their own GitHub App settings.
3. Attacker crafts a `status` event JSON body: `{"sha": "<victim-commit-sha>", "state": "success", "context": "<required-ci-context>", "repository": {"owner": {"login": "AttackerOrg"}}}`.
4. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s secret and POSTs to `/github/webhooks`.
5. `verify_signature` resolves and validates against `AttackerOrg`'s secret and passes, `StatusHandler` finds the commit in `VictimOrg`'s stack purely by `sha`, creates a passing status, and triggers `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` on `VictimOrg`'s stack, causing an unauthorized merge or deploy.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

# frozen_string_literal: true

module Shipit
  class ProcessMergeRequestsJob < BackgroundJob
    include BackgroundJob::Unique
    on_duplicate :drop

    queue_as :default

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
  end
end
