### Title
Cross-tenant `PullRequest#labels` write via `repository_owner` fallback vs handler's `repository.full_name` divergence - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's HMAC secret authenticates a webhook using `repository_owner`, which falls back to `params.dig('organization','login')` when `repository.owner.login` is absent. `LabelCapturingHandler`, however, resolves the target `Repository`/`Stack` from the independently-set `params.repository.full_name` field. Because these two values are never checked for consistency, an attacker who legitimately controls a webhook secret for their own configured organization can forge a `pull_request` `unlabeled` event whose `repository.full_name` points at a victim repository, causing `LabelCapturingHandler` to persist attacker-chosen labels onto the victim's `PullRequest` record.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`repository_owner` (used to select the HMAC verifier) == owner of `params.repository.full_name` (used by the handler to select the target `Stack`/`Repository`).

- `Shipit::WebhooksController#repository_owner` at `app/controllers/shipit/webhooks_controller.rb:59-62` computes: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. If the payload omits `repository.owner.login`, verification falls back to `organization.login`.
- `verify_signature` (lines 24-49) does `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This selects the webhook secret configured for whatever organization `repository_owner` resolves to.
- `LabelCapturingHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:110-114`) instead does `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, using the `full_name` field of the same `repository` object, which is required by the handler's schema (`requires :repository do requires :full_name, String end`, lines 33-35) but does not require `owner.login`.

Exploit flow: The attacker (who owns/maintains an org+repo legitimately configured in Shipit, e.g. `attacker-org/attacker-repo`, and thus knows that org's webhook secret) crafts a raw JSON body for a `pull_request` `unlabeled` event where:
- `repository: { full_name: "victim-org/victim-repo" }` (no `owner` key)
- `organization: { login: "attacker-org" }`
- `pull_request.labels` containing attacker-chosen label names
- `number` matching an existing PR/review-stack environment (`pr#{number}`) on the victim stack

The attacker signs the raw body with `attacker-org`'s webhook secret (which they legitimately possess) and sends it to `POST /webhooks` with `X-Github-Event: pull_request`. `verify_signature` resolves `repository_owner` to `attacker-org` (via the organization fallback) and validates successfully against the attacker's own secret. Once verification passes, `WebhooksController#create` invokes `LabelCapturingHandler.call(params)` on the full, unmodified payload — the handler never re-checks which organization actually authenticated the request. `unlabeled_active_stack?` matches (`action == "unlabeled"` and the resolved victim stack is present and unarchived), so `capture_labels` runs: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` (line 101), overwriting the victim's `PullRequest#labels`.

Because `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) merges `pull_request.labels.each { |name| labels[name.upcase] = "true" }` into the deploy/task environment, the attacker fully controls arbitrary uppercase env-var keys/values injected into any subsequent deploy or task run against the victim's review stack. If the victim stack's deploy spec keys `blocked?`/gating logic or `blocking_statuses` off environment variables or off status checks that read stack state influenced by labels, the attacker can toggle deploy-blocking behavior on a repository they do not own, without ever authenticating as that repository.

None of the existing guards prevent this: `verify_signature` only checks the HMAC against whichever organization `repository_owner` resolves to — it never binds that organization to the repository the handler will act upon. `drop_unhandled_event` and `ExplicitParameters` schema validation (`requires :repository { requires :full_name }`) only check shape/presence, not cross-consistency between `organization.login`/`repository.owner.login` and `repository.full_name`. There is no `Stack`/`Repository` scoping tied to which secret authenticated the request.

### Impact Explanation
An unprivileged GitHub user who controls a webhook secret for any Shipit-configured organization (e.g., because they administer their own repo/organization that is registered in Shipit) can forge webhook payloads that mutate `PullRequest` records — and therefore deploy-time environment variables via `ReviewStack#env` — belonging to a completely different, victim organization/repository. This is a cross-tenant state manipulation: one repository's authenticated payload writes another repository's records, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is repeatable against any victim repository/stack whose `environment` (`pr#{number}`) the attacker can guess or enumerate, and is bounded only by needing a legitimate webhook secret for some org configured in the Shipit instance.

### Likelihood Explanation
Preconditions: (1) the Shipit instance hosts multiple organizations/repositories, each with independently configured webhook secrets in `Shipit.github`; (2) the attacker legitimately owns or administers at least one such configured org/repo (a normal, low-privilege scenario for any GitHub App/Shipit multi-tenant deployment); (3) the victim stack is a `ReviewStack` with a known/guessable PR number. Attacker cost is low: crafting a JSON payload and computing HMAC-SHA1 with a secret they already legitimately hold. This is feasible and repeatable for every event handled from the `repository.full_name`/`organization.login` divergent fields (not just this handler), but the question specifically demonstrates it against `LabelCapturingHandler`.

### Recommendation
Bind the authenticated organization to the actual acted-upon repository: after resolving `repository_owner` for signature verification, require that the same value equals the owner segment parsed from `params.dig('repository','full_name')` (or reject the request entirely if `repository.owner.login` is absent while `repository.full_name` is present). Alternatively, resolve and authenticate strictly from `repository.full_name`'s owner (splitting `"owner/repo"`) rather than a separately-fallback-able `organization.login`/`repository.owner.login` field, eliminating the two-field divergence.

### Proof of Concept
Under `test/controllers/webhooks_controller_test.rb` (or a new label_capturing test), add a minitest that:
1. Configures two orgs in `Shipit.github` fixtures: `attacker-org` (with a known webhook secret the test controls) and `victim-org` (owning `victim-org/victim-repo`, with a review stack `pr123`, `blocking_statuses` configured).
2. Builds a raw JSON body for event `pull_request`, `action: "unlabeled"`, `number: 123`, `repository: { full_name: "victim-org/victim-repo" }` (no `owner` key), `organization: { login: "attacker-org" }`, and `pull_request.labels` set to an attacker-chosen array, e.g. `[{name: "FORCE_UNBLOCK"}]`.
3. Signs the raw body with `attacker-org`'s webhook secret and sets `X-Hub-Signature`/`X-Github-Event` headers.
4. POSTs to `/webhooks`.
5. Asserts response is `200`, and asserts `Shipit::PullRequest.find_by(stack: victim_stack).labels == ["FORCE_UNBLOCK"]` — i.e., the victim's `PullRequest` record was mutated by a request authenticated with `attacker-org`'s secret, not `victim-org`'s.
6. Optionally assert `victim_stack.env["FORCE_UNBLOCK"] == "true"` via `ReviewStack#env` to show the downstream environment-variable injection.

Before the fix: assertions in steps 5/6 pass (proving the vulnerability). After applying the recommended fix (rejecting mismatched/absent `repository.owner.login` vs authenticated org, or authenticating strictly off `repository.full_name`), the request should be rejected with `422` and the victim's `PullRequest#labels` must remain unchanged.
