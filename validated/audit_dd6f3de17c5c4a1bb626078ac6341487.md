Based on the codebase evidence, I can identify a genuine analog of the SSRF trust-binding break: webhook signature verification is scoped by **organization**, but the handlers that act on the payload are scoped only by fields inside the payload (SHA / branch name) with no re-validation that the acted-upon commit/stack actually belongs to the organization whose secret was verified. This breaks exactly the binding class called out in the rules ("an organization that authenticated versus the repository that is written").

### Title
Webhook signature is verified per-organization but status/check_suite handlers write to any repository's commits/stacks matched by SHA/branch alone - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: app/models/shipit/webhooks/handlers/check_suite_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC against using a value taken directly from the untrusted JSON body (`repository.owner.login` or `organization.login`), not from any pre-established, trusted mapping tied to the specific repository being mutated. Once the signature check passes for that organization, the raw `params` are handed to every registered handler for the event, and at least two of the built-in handlers (`StatusHandler`, `CheckSuiteHandler`) locate the `Commit`/`Stack` records to mutate purely by `sha` or `branch` name, globally across the whole Shipit instance, with no check that the commit/stack actually belongs to the organization/repository that was cryptographically verified.

### Finding Description
`verify_signature` in the webhook controller does: [1](#0-0) 
selecting `Shipit.github(organization: repository_owner)`, where: [2](#0-1) 
`repository_owner` is read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')`). This value only determines *which secret* is used to HMAC-verify the *whole* raw body — it establishes trust in "this request was signed by organization X's webhook secret," nothing more.

After that check, `create` dispatches the entire payload to handlers: [3](#0-2) 

`StatusHandler#process` then mutates state using only the `sha` field from that same payload, with no scoping to the repository/organization that was verified: [4](#0-3) 

`CheckSuiteHandler#process` similarly scopes only by branch name across `stacks`, not by repository ownership: [5](#0-4) 

Additionally, `verify_webhook_signature` in `GitHubApp` trivially returns `true` when no `webhook_secret` is configured for that organization: [6](#0-5) 

The equality that should hold is: *organization whose secret authenticated the request* == *organization/repository whose commit/stack state is mutated*. Instead, the code only enforces: *organization named in the payload* == *organization whose secret is checked*, and the mutation target is chosen independently from a global, unscoped lookup (`Commit.where(sha: ...)`, `stacks.where(branch: ...)`) that spans every repository configured in the Shipit instance.

### Impact Explanation
Given a multi-tenant Shipit deployment (multiple GitHub organizations/repositories configured, which is the documented, standard use case), an attacker who can get a validly-signed webhook accepted for *any one* onboarded organization (either because they control that org's webhook secret, or because that org has no `webhook_secret` configured at all, in which case verification is skipped entirely) can forge a `status` event with an arbitrary `sha` belonging to a commit in a completely different organization's stack, and set `state: success`. This can satisfy `ci.require`/deployable checks for a repository the attacker has no access to, enabling an **unauthorized deploy or merge** on a victim repository — matching the Critical-impact bucket ("unauthorized deploy, rollback or merge"). The `check_suite` handler exhibits the same cross-tenant scoping gap for CI check-run refresh across any stack matching the branch name.

### Likelihood Explanation
Exploitation requires only an HTTP POST to the public `/webhooks` endpoint with attacker-controlled JSON — no `ApiClient` token, no GitHub App private key, no privileged Shipit account, and no TLS interception. The main precondition is a multi-org Shipit instance where the attacker legitimately controls (or can obtain the secret for) at least one onboarded organization, or where at least one onboarded organization has skipped configuring a `webhook_secret` — a realistic, commonly-seen misconfiguration for public/low-risk repos. Given that GitHub commit SHAs of target repositories are typically public information, guessing/knowing a target `sha` is trivial.

### Recommendation
Scope handler lookups by the verified repository/organization, not solely by fields taken from the unauthenticated part of the trust decision. Concretely: pass the verified organization/repository identity from `WebhooksController` into each handler and require `StatusHandler`/`CheckSuiteHandler` (and any other handler that mutates `Commit`/`Stack` state) to filter `Commit`/`Stack` records by `stack.repository` matching that verified identity, in addition to `sha`/`branch`. Alternatively, deny requests for organizations without a configured `webhook_secret` rather than treating them as automatically verified.

### Proof of Concept
1. Shipit instance hosts stacks for both `org-attacker/low-value-repo` (attacker-controlled or unsecured webhook) and `org-victim/high-value-repo` (target).
2. Attacker learns/controls `org-attacker`'s webhook secret (or `org-attacker` has no `webhook_secret` configured).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, a body:
```json
{
  "repository": { "owner": { "login": "org-attacker" } },
  "sha": "<victim commit sha from org-victim/high-value-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
signed (or unsigned, if `org-attacker` has no secret) so that `verify_signature` passes using `org-attacker`'s configuration.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` globally, finds the victim's commit (SHAs are effectively globally unique), and creates a successful status on it — bypassing CI requirements for the victim repo's merge/deploy gating.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
