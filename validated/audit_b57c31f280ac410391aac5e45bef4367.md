### Title
Webhook signature verification is bound to an attacker-controlled organization field, decoupled from the repository the event actually writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to HMAC-verify a webhook against by reading `repository_owner` straight out of the unauthenticated request body, then every downstream `Handler` (in `app/models/shipit/webhooks/handlers/*`) resolves the `Stack`/`Repository` to act on from a *different* body field, `repository.full_name`, with no check that this repository actually belongs to the organization whose secret validated the request.

### Finding Description
The verification flow is: [1](#0-0) 

`repository_owner` is derived from the same untrusted, not-yet-verified payload: [2](#0-1) 

That organization name is used only to select which `GithubApp`/secret validates the HMAC (`Shipit.github(organization: repository_owner)` then `verify_webhook_signature`): [3](#0-2) 

Once the signature check passes, the raw params are dispatched unmodified to handlers: [4](#0-3) 

Every handler then determines the actual `Stack`(s) to mutate using a **separate** field of the same payload, `repository.full_name`, never re-checked against `repository_owner`: [5](#0-4) 

This is the same bug class as the referenced report: the field that is validated (the organization login used to pick the HMAC secret) is not the field that is acted upon (`repository.full_name`, used to look up and mutate the target `Stack`). Nothing in `verify_signature` or `Handler` enforces `repository.full_name.start_with?("#{repository_owner}/")`. Any party who legitimately controls one configured GitHub organization's webhook secret (i.e. is the admin of one org onboarded onto the same Shipit instance) can send a request with `repository.owner.login` set to *their own* org (so it authenticates against their own known secret) while setting `repository.full_name` to `"other-org/other-repo"`, causing the event (push, status, check_suite, membership, pull_request, etc.) to be processed against a stack that belongs to a completely different, unrelated organization.

### Impact Explanation
This breaks the trust binding "the organization whose secret authenticated the webhook" versus "the repository whose Stack is written by the webhook." Concretely this permits a cross-organization/cross-repository write: an attacker holding webhook credentials for one onboarded org can forge `push` events to trigger `GithubSyncJob` against a stack of an unrelated repository, forge `status`/`check_suite` events to alter commit statuses/deployability of a stack they do not own, or forge `pull_request`/`membership` events to manipulate review stacks or team membership tied to another org's repositories — all without ever holding credentials for the victim organization. This matches "cross-repository writes" / "unauthorized deploy" impact criteria, since manipulated commit statuses and check runs can unblock deploy gating (`Deployable` status) on a stack that isn't the attacker's.

### Likelihood Explanation
Requires only that Shipit is configured to serve more than one GitHub organization (a documented, supported multi-tenant configuration — see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` showing multiple `github:` orgs), and that the attacker is a legitimate, but unprivileged-relative-to-the-victim-repo, holder of one org's webhook secret (e.g. an org admin who installed the Shipit GitHub App on their own org). No access to the victim org's secret, no Shipit session, and no `ApiClient` token is required — only the ability to send an HTTP POST to `/webhooks` with a validly-signed-for-org-A body whose `repository.full_name` field claims to be a repo of org B.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization actually used to validate the signature matches the owner of `repository.full_name` before dispatching to handlers — e.g. reject the request if `payload.dig('repository','full_name')&.split('/')&.first != repository_owner` (with the same organization fallback logic), rather than trusting `repository.full_name` independently downstream.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (a supported, documented setup per `docs/setup.md`).
2. As the admin who installed the Shipit GitHub App on `OrgA`, obtain `OrgA`'s `webhook_secret`.
3. Craft a `push` event JSON body with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"`.
4. Compute `X-Hub-Signature: sha1=<hmac_sha1(OrgA_webhook_secret, raw_body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, and the HMAC matches, so the request passes.
6. `Shipit::Webhooks::Handlers::PushHandler` (via `Handler#stacks`) resolves stacks from `repository.full_name` = `"OrgB/victim-repo"`, dispatching a `GithubSyncJob` against `OrgB`'s stack — despite the request never being authenticated against `OrgB`'s secret.
