### Title
Cross-tenant commit-status forgery via SHA-only lookup triggers unauthenticated `ProcessMergeRequestsJob` scheduling - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no check that the webhook's authenticated repository matches the repository owning the `Commit`'s `Stack`. Any GitHub account that can generate a genuinely signed "status" webhook for a repository sharing a commit SHA with a Shipit-tracked stack (e.g., a public fork) can inject a status onto the victim's `Commit`, which propagates through `Commit#add_status` into `Stack#schedule_merges`, enqueuing `ProcessMergeRequestsJob.perform_later(victim_stack)` for a stack the attacker never authenticated against.

### Finding Description
The claimed binding is: `commit.stack.repository == webhook.repository_owner/full_name` (i.e., the stack whose merge automation gets scheduled must be the same repository that authenticated the inbound webhook). This binding is never checked.

Path:
1. `WebhooksController#create` dispatches the parsed JSON payload to handlers for the event, after `verify_signature` confirms the payload was genuinely signed by GitHub for `repository_owner` (`params.dig('repository','owner','login')`). [1](#0-0) [2](#0-1) 

2. `verify_signature` only proves "this event really came from GitHub for organization X's installation" — it never compares `params['repository']['full_name']` against the repository owning the commit that will actually be mutated. [3](#0-2) 

3. `StatusHandler#process` looks up commits by `sha` alone, across the entire `commits` table, with zero scoping to the repository that sent the webhook:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

4. `create_status_from_github!` -> `add_status` writes a `Status` record for the matched commit and, on a `pending?`/`success?` transition, calls `stack.schedule_merges` — where `stack` is `commit.stack`, i.e., the **victim's** stack, not any stack tied to the webhook's authenticated repository: [5](#0-4) [6](#0-5) 

5. `Stack#schedule_merges` unconditionally enqueues `ProcessMergeRequestsJob.perform_later(self)`: [7](#0-6) 

Root cause: git commit SHAs are content-addressed and are preserved identically across a public fork's shared history with its upstream. An attacker who forks a victim's repository (any public repo tracked as a Shipit stack) shares SHAs for all pre-existing commits. The attacker can set a commit status on that shared SHA within their own, fully-owned fork (via the GitHub Statuses API, which they can call with their own token because they own the fork), which causes GitHub to deliver a **legitimately signed** `status` webhook whose `repository.owner.login` is the attacker's own account/org. `verify_signature` passes because the signature is valid for that (attacker-owned) installation. `StatusHandler` then blindly matches on `sha`, finds the victim's `Commit` (belonging to the victim's `Stack`), writes a forged `Status`, and reaches `stack.schedule_merges` for the victim's stack — a cross-tenant, unauthenticated trigger.

None of the listed guards close this gap: `verify_signature` validates provenance of the webhook, not ownership of the target commit; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema in `StatusHandler` only validates payload shape, not repository binding; there is no `Repository`/`full_name` comparison anywhere in `status_handler.rb` or `Commit#create_status_from_github!`.

### Impact Explanation
A forged, but genuinely GitHub-signed, status webhook from an attacker-owned fork can write a `Status` record into a victim stack's `Commit` (a record written for a repository that did not authenticate the victim's stack) and unconditionally enqueue `ProcessMergeRequestsJob.perform_later(victim_stack)` — privileged stack automation belonging to a tenant the attacker never authenticated against. This is repeatable against any Shipit-tracked repository the attacker can fork and for any historical SHA shared between fork and upstream, so it is not limited to a single repository pair. Per the rubric this matches "a payload for one repository mutating another's stack, commit... or an unauthorized... merge [trigger]" — Critical severity for the scheduling/write primitive itself (this question is scoped only to the trigger, not the merge outcome, per the prompt).

### Likelihood Explanation
Preconditions: victim stack has `merge_queue_enabled` (only affects whether the scheduled job does anything interesting, not whether the trigger fires — the trigger fires on any `pending?`/`success?` transition regardless); the victim repository must be public (or otherwise forkable) so the attacker can create a fork sharing SHAs; the attacker needs a GitHub identity capable of creating a status on their own fork (trivial — repo owners can set statuses on their own repository via API/PAT) and the Shipit GitHub App/webhook integration must be reachable for events on the attacker's account/org (this depends on how broadly the Shipit GitHub App installation is scoped — if it is installed only on the victim's org and not on arbitrary forks, this specific SHA-collision path requires the fork to remain under an org where the same installation applies, or the attacker to install the app on their own account, which is a self-service action GitHub allows for GitHub App owners on their own repos). This part of feasibility could not be fully verified from the code available and depends on `Shipit.github` / GitHub App installation configuration outside this repo. No secrets are required by the attacker; cost is a fork, a PAT with `repo:status`, and one API call — cheap and repeatable.

### Recommendation
In `StatusHandler#process` (and any other SHA/branch-keyed handler such as check-run handlers), scope the `Commit` lookup to the repository asserted by the webhook: join/filter by `commit.stack.repository` matching `params.dig('repository','full_name')` (or the resolved `repository_owner`/`repo` from the verified installation) before calling `create_status_from_github!`, rejecting or ignoring matches whose stack repository does not equal the authenticated repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, minitest + Mocha)
test "status webhook for unrelated repository must not schedule merges for a same-sha commit in a different stack" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(merge_queue_enabled: true)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  # attacker's own repo/stack, unrelated tenant, but a Commit record with the SAME sha
  attacker_stack = Shipit::Stack.create!(repo_owner: 'attacker', repo_name: 'fork')
  attacker_commit = attacker_stack.commits.create!(sha: victim_commit.sha, message: 'attacker commit')

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/fork', 'owner' => { 'login' => 'attacker' } }
  }

  ProcessMergeRequestsJob.expects(:perform_later).with(victim_stack).never
  ProcessMergeRequestsJob.expects(:perform_later).with(attacker_stack).once

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)
end
```
This test asserts `ProcessMergeRequestsJob.perform_later(victim_stack)` (the equality binding, `commit.stack == authenticated repository's stack`) is currently violated because `Commit.where(sha:)` matches the victim's commit purely by SHA and calls `stack.schedule_merges` on `victim_stack`, not `attacker_stack`. A fix enforcing repository binding should make this test pass (only `attacker_stack` scheduled, never `victim_stack`).
