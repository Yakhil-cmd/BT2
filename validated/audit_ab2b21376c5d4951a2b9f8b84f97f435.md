## Title
Broken ownership validation in `handleNewSharedAddress` allows a paired device to silently register a forged joint address embedding the victim's own address - (File: `wallet_defined_by_addresses.js`)

### Summary
`wallet_defined_by_addresses.js`'s `handleNewSharedAddress()` is the message handler invoked whenever a correspondent device sends a `new_shared_address` network message [1](#0-0) . It is reachable by any paired device without any prior negotiation, and it accepts and locally persists a shared-address definition as long as *any* address referenced inside that definition happens to already belong to the receiving wallet — it never verifies that the sender is actually authorized to bundle that address into a new composite definition, nor does it require any cryptographic proof of consent from the embedded address's real owner.

### Finding Description
`handleNewSharedAddress` performs only structural checks: that the c-hash of the supplied definition matches the claimed address, that each signer entry is a syntactically valid address, and that the signer map is consistent with the address paths extracted from the definition [2](#0-1) .

The only "ownership" gate is `determineIfIncludesMeAndRewriteDeviceAddress`, which collects **all** addresses referenced anywhere in the proposed definition and accepts the message as long as at least one of them is found in the local `my_addresses` or `shared_addresses` tables: [3](#0-2) 

This is analogous to the LibrePhotos flaw: a "sharing" relation (here, `shared_addresses` / `shared_address_signing_paths`, the ocore equivalent of `shared_to`) is created/updated without validating that the requester actually owns or was authorized to include the target resource (the victim's address) in the new relation.

Because a definition such as `["or", [["address", VICTIM_ADDR], ["address", ATTACKER_ADDR]]]` structurally validates fine via `Definition.validateDefinition` (called with `bAllowUnresolvedInnerDefinitions: true`) [4](#0-3) , an attacker only needs to know the victim's already-public payment address (trivially obtainable, e.g. from a prior payment) to craft a valid, self-consistent shared-address message. The legitimate, mutual-consent workflow (`createNewSharedAddressByTemplate` / `sendOfferToCreateNewSharedAddress` / `approvePendingSharedAddress`) that requires each device to explicitly approve its own inclusion is explicitly marked `unused` [5](#0-4) [6](#0-5)  — the actually-used path (`new_shared_address` handled by `handleNewSharedAddress`) skips this consent step entirely.

Once accepted, `addNewSharedAddress` inserts the forged address into `shared_addresses`/`shared_address_signing_paths`, emits `new_address`, and for light clients adds it to `unprocessed_addresses` for watching [7](#0-6) . The wallet now silently tracks and treats this attacker-controlled "or" address as one of its own spendable addresses without any user confirmation.

### Impact Explanation
Because the forged definition uses `or` logic, either party alone can authorize spending from the resulting address. If the victim's wallet (which now silently watches/tracks it as "its" address) or any third party who is shown this address (e.g. via the attacker socially engineering it as a "joint"/escrow address) ever sends funds to it, the attacker can unilaterally sweep the funds using their own signing path — resulting in concrete unauthorized spending/asset loss, reachable purely by a paired-device correspondent sending one crafted `new_shared_address` message, with no cooperation or mistake required from the victim beyond having a known payment address.

### Likelihood Explanation
Any device that has previously paired with the victim (a normal, low-privilege relationship established simply by exchanging a pairing code, e.g. after a single payment) can send this message at will. The victim's address is not secret information required for the attack — it is inherently public once used to receive a payment. No race condition or timing dependency is needed; the message is processed immediately upon receipt.

### Recommendation
Restore/require the mutual-consent flow: reject `new_shared_address` messages that were not preceded by a corresponding local `pending_shared_addresses` offer created via `createNewSharedAddressByTemplate`, or otherwise require that the sending device's address be a member referenced by *its own* definition path (not merely that some unrelated address in the definition matches a local address), and require explicit user approval before persisting any new shared address that embeds a wallet's own local address.

### Proof of Concept
1. Attacker device pairs with victim (standard, low-privilege step).
2. Attacker learns `VICTIM_ADDR`, a normal receiving address of the victim (e.g., from any past payment).
3. Attacker computes `arrDefinition = ["or", [["address", VICTIM_ADDR], ["address", ATTACKER_ADDR]]]` and `address = chash160(arrDefinition)`.
4. Attacker sends a `new_shared_address` device message: `{address, definition: arrDefinition, signers: {"r.0": {address: VICTIM_ADDR}, "r.1": {address: ATTACKER_ADDR, device_address: ATTACKER_DEVICE}}}`.
5. Victim wallet's `handleNewSharedAddress` validates the c-hash/signer consistency, `determineIfIncludesMeAndRewriteDeviceAddress` finds `VICTIM_ADDR` in `my_addresses` and accepts, and `addNewSharedAddress` persists the new joint address and starts watching it.
6. If any funds are later sent to `address` (accidentally by the victim, or by a third party the attacker tricks), the attacker can spend them unilaterally via the `or` branch containing `ATTACKER_ADDR`.

	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));

	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {

	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
