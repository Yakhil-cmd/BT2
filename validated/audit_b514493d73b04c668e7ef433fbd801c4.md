### Title
Webhook `membership` events can be forged to grant unprivileged GitHub identities `Shipit.github_teams` authorization when a configured GitHub organization has no `webhook_secret` — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the signing secret to check based on an attacker-controlled field of the *unauthenticated* inbound payload (`repository.owner.login` / `organization.login`), and `GithubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success. Because Shipit explicitly supports multiple GitHub organizations, each with its own optional `webhook_secret`, any organization slot configured with a blank secret becomes an unauthenticated event injector for the whole Shipit instance. This breaks the equality that should hold between "the organization whose secret validated this delivery" and "the resources (teams, memberships, repositories) the payload is allowed to mutate."

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` gates every webhook request. `verify_signature` does: [1](#0-0) [2](#0-1) 

It picks the `github_app` (and thus the secret to verify against) using `repository_owner`, which is read straight out of the JSON body being verified, not from any pre-authenticated source: [3](#0-2) 

`GithubApp#verify_webhook_signature` short-circuits to `true` whenever no secret is configured for that organization: [4](#0-3) 

Shipit's own setup templates show `webhook_secret` as an optional, commonly-nil field, and explicitly document multi-organization configuration: [5](#0-4) [6](#0-5) 

Once past `verify_signature`, the controller dispatches the event to handlers using only the JSON body, with no re-validation that the resources referenced (team, membership, repository) belong to the organization that was supposedly verified: [7](#0-6) 

The `membership` event handler creates `Team`/`User`/`Membership` records purely from payload content — this is demonstrated by the test suite (which stubs signature verification and then posts freeform `membership` payloads): [8](#0-7) 

These `Membership`/`Team` records are exactly what `User#authorized?` checks against: [9](#0-8) 

**Equality broken:** `organization_that_authenticated_the_delivery == organization_whose_teams/memberships_are_mutated_by_the_delivery` is not enforced. If any configured organization has `webhook_secret` unset (a state the shipped config templates present as normal/default), `verify_webhook_signature` returns `true` for *any* payload claiming that organization as `repository.owner.login`/`organization.login` — regardless of which team/user/membership fields are actually inside the body.

### Impact Explanation
An unprivileged, unauthenticated attacker (no Shipit session, no `ApiClient` token, no GitHub App key needed) who can reach the `/webhooks` endpoint can forge a `membership` event that adds an arbitrary GitHub login to a `Team` that is part of `Shipit.github_teams`. Since `User#authorized?` is the sole gate behind `force_github_authentication` for the entire application UI, this escalates an arbitrary identity into full `Shipit.github_teams` authorization — the exact "High" impact category called out in the rules ("escalation into `Shipit.github_teams` authorization"). It also allows fabricating `push`/`status`/`pull_request` events tied to stacks the attacker does not control, since nothing re-validates the payload's `repository` object against the organization used for signature selection.

### Likelihood Explanation
Exploitability depends entirely on operational configuration: at least one configured GitHub organization must have a blank `webhook_secret`. Shipit's own setup docs and secrets templates present this as the default/no-op state (`webhook_secret: # nil`), so it is a realistic, likely-occurring misconfiguration rather than a theoretical one, especially in the single-organization deployment mode where operators may not realize a secret is expected. This mirrors the structure of the referenced report: the binding between "who is trusted to act" and "what gets acted upon" is never enforced by the code, only by an operator's diligence in setting an optional field.

### Recommendation
- Make `webhook_secret` mandatory for every configured organization (fail startup/config validation if absent) rather than silently trusting unsigned payloads.
- After selecting `github_app` from `repository_owner`, verify that every resource actually mutated by the handler (team `organization`, `repository.owner`, etc.) matches the same organization that supplied the verified secret, rather than trusting nested fields uncritically.
- Consider signing/validating on a value that cannot be chosen by the sender (e.g., require `X-GitHub-Hook-Installation-Target-ID` / app-level context) instead of trusting `repository.owner.login` from the same untrusted body being verified.

### Proof of Concept
1. Deploy Shipit with multi-org config where `orgA.webhook_secret` is unset and `orgB.webhook_secret` is set (mirrors `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with header `X-Github-Event: membership`, no valid `X-Hub-Signature`, and body:
```json
{
  "action": "added",
  "organization": { "login": "orgA" },
  "team": { "id": 1, "name": "orgB-admins", "slug": "orgb-admins" },
  "member": { "login": "attacker-controlled-login" }
}
```
Because `repository_owner` resolves to `orgA` (whose `webhook_secret` is blank), `verify_webhook_signature` returns `true` unconditionally per [10](#0-9) , and the membership handler creates the `Membership` for `team: orgb-admins` regardless that the request was never actually validated for `orgB`, per the behavior demonstrated in [11](#0-10) . If `orgb-admins` is part of `Shipit.github_teams`, `attacker-controlled-login`'s corresponding `User` now passes `authorized?`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
