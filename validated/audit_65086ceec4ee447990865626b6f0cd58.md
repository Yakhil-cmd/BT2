The binding claimed broken: `TaskCommands#env` keys (specifically `GIT_ASKPASS`, `GITHUB_TOKEN`, `GIT_ASKPASS` set in `Commands#base_env`) should equal only operator-approved values, but `deploy_spec.machine_env` is merged unfiltered afterward.### Title
Attacker-controlled `machine.environment` in `shipit.yml` overrides `GIT_ASKPASS`/`GITHUB_TOKEN` for Review Stacks, yielding RCE with real deploy credentials - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` merges `deploy_spec.machine_env` — raw, unfiltered key/value pairs taken straight from a repository's `shipit.yml` — after `Commands#base_env` sets `GIT_ASKPASS`/`GITHUB_TOKEN`, so any key in `machine.environment` silently overrides Shipit's own security-critical env vars. For a `Shipit::ReviewStack`, `DeploySpec::FileSystem` loads `shipit.yml` from the PR's own head branch, which is fully attacker-controlled, letting an unprivileged PR author point `GIT_ASKPASS` at a script inside the checked-out working directory and get it executed by git with the real `GITHUB_TOKEN` in the environment.

### Finding Description
The broken binding: the set of environment variable keys reaching `PTY.spawn` in `Command#start` (specifically `GITHUB_TOKEN` and `GIT_ASKPASS` set by `Commands#base_env`, `lib/shipit/commands.rb:37-50`) is claimed to be operator-controlled and immutable per task, but is actually `== deploy_spec.machine_env.keys ∪ base_env.keys` with `machine_env` taking precedence, because `TaskCommands#env` does:

```ruby
super.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)
``` [1](#0-0) 

Unlike `deploy_variables`/`rollback_variables`/task `variables`, which are always passed through `EnvironmentVariables#permit` (`lib/shipit/environment_variables.rb:13-18`, used by `DeploySpec#filter_deploy_envs`/`filter_rollback_envs` and `TaskDefinition#filter_envs`), `machine_env` (`config('machine', 'environment')`, `app/models/shipit/deploy_spec.rb:69-71`) has no whitelist and is merged directly.

For a `ReviewStack`, `stack.branch` is set to `params.pull_request.head.ref` at creation time (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:87-93`), i.e. the PR author's own branch. `DeploySpec::FileSystem` reads `shipit.yml` from whatever commit is checked out in the task's working directory for that branch (`app/models/shipit/deploy_spec/file_system.rb:98-107`), which is content the PR author wrote.

Exploit flow: an unprivileged user opens a PR (or pushes to their own branch) against a repository with review-stack provisioning enabled, adding:
```yaml
machine:
  environment:
    GIT_ASKPASS: /path/inside/checkout/malicious-script
```
When the review stack is created/provisioned or any subsequent task (deploy, custom task, dependency install) runs, `TaskCommands#env` builds the env for `git` commands via `Commands#git` (`lib/shipit/commands.rb:28-32`) and other steps; `Command#start` calls `PTY.spawn(unbundled_env, ...)` (`lib/shipit/command.rb:92`), where `unbundled_env` includes the attacker's `GIT_ASKPASS` (`lib/shipit/command.rb:103-105`). Any git network operation that solicits credentials over HTTPS invokes the attacker's askpass script instead of the legitimate one (`lib/snippets/git-askpass`), executing arbitrary code as the Shipit process, with `GITHUB_TOKEN` present in the environment.

Existing guards do not prevent this: `EnvironmentVariables#permit` is never applied to `machine_env`; `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs` only cover deploy/rollback/task *user-supplied* variables, not the shipit.yml-declared machine environment; `Repository`/`Stack` model validations do not constrain `shipit.yml` content since it is loaded at runtime from the git checkout, not stored/validated as a model attribute.

### Impact Explanation
Successful exploitation executes arbitrary shell commands on the Shipit deploy host, in a process that has `GITHUB_TOKEN` (the app's real GitHub App/OAuth token) in its environment, satisfying the Critical "RCE on the deploy host via `Command`/`PTY.spawn`" and "exfiltration of `GITHUB_TOKEN`" categories. Blast radius is scoped to the repository/stack where review apps are enabled but the compromised process and its token are shared with the rest of the Shipit installation, so the attacker can pivot to reading/writing other repositories the token has access to. Repeatable on every task run (provisioning, deploy, custom task) for the malicious branch as long as the working directory or the loaded `shipit.yml` reflects the attacker's `machine.environment`.

### Likelihood Explanation
Requires: (1) the target repository has review-stack provisioning enabled with a permissive behavior (`allow_all` or `allow_with_label` where the attacker can self-label), (2) `Shipit.use_git_askpass?` enabled on the host so `GIT_ASKPASS` is used by base_env (a common configuration for HTTPS-based GitHub auth), and (3) a git operation in the task triggers a credential prompt (fetch/clone/push against a private repo, or any HTTPS remote). Attacker cost is minimal: opening a PR from an unprivileged account is sufficient, no secrets or elevated roles needed. This is directly repeatable against any repository with review apps enabled.

### Recommendation
Do not allow `shipit.yml`-declared `machine.environment` to shadow or override Shipit-managed security-critical keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GIT_COMMITTER_*`, etc.). Concretely, merge `deploy_spec.machine_env` before `base_env` (or explicitly strip reserved keys from `machine_env`), and additionally run `machine_env` through an explicit denylist/whitelist (similar to `EnvironmentVariables#permit`) that rejects `GIT_ASKPASS`, `GIT_SSH*`, `GITHUB_TOKEN`, `BUNDLE_*` overrides, etc. For Review Stacks specifically, consider not trusting `machine.environment` from the PR's own head branch at all (e.g., only read it from the base/default branch's `shipit.yml`, mirroring how many CI systems restrict fork PR secrets).

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb
test "#env: attacker-controlled machine_env overrides GIT_ASKPASS set by base_env" do
  task = shipit_tasks(:shipit)
  commands = TaskCommands.new(task)

  commands.stubs(:deploy_spec).returns(
    stub(machine_env: { 'GIT_ASKPASS' => '/tmp/checkout/malicious-script' })
  )

  base_git_askpass = commands.send(:base_env)['GIT_ASKPASS']

  env = commands.env

  # Binding under test: env['GIT_ASKPASS'] should equal Shipit's trusted
  # base_env['GIT_ASKPASS'], never an attacker-supplied shipit.yml value.
  refute_equal base_git_askpass, env['GIT_ASKPASS']
  assert_equal '/tmp/checkout/malicious-script', env['GIT_ASKPASS']
end
```
This demonstrates `TaskCommands#env['GIT_ASKPASS']` is fully attacker-controlled via `deploy_spec.machine_env`, with no `EnvironmentVariables#permit` filtering applied, confirming the divergence between the intended trusted binding and actual behavior.
