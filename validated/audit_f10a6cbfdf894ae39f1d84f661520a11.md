## Analysis Summary

The Sherlock report's root cause is: **a global pause mechanism blocks the *challenge/veto* path while the underlying malicious/queued action still executes**, creating a window where the safety-net cannot be exercised. I traced a structural analog in the polkadot-sdk governance stack: `pallet-safe-mode` (and equivalently `pallet-tx-pause`) is designed to be composed into `frame_system::Config::BaseCallFilter`, and that filter is **unconditionally bypassed for `RawOrigin::Root`** but *not* for the collective/council origins that `pallet-democracy`'s `VetoOrigin`/`CancellationOrigin` resolve to. Meanwhile, `pallet-democracy` enacts passed referenda via `pallet-scheduler` using `frame_system::RawOrigin::Root`, which the scheduler doc explicitly says "will get no filter." This produces the same asymmetry as the Sherlock finding: the passing/execution path is immune to the pause, but the intervention/challenge path is not.

Critically, `SafeMode::enter` is **permissionless** — any signed account can trigger it by paying a configured deposit — matching the "attacker with no privileged role" requirement.

### Title
Permissionless `SafeMode`/`TxPause` activation blocks Democracy's `veto_external`/`emergency_cancel` challenge path while Root-origin scheduled enactment still executes - ([File: substrate/frame/safe-mode/src/lib.rs])

### Summary
`pallet-safe-mode`'s `enter()` extrinsic can be called by any signed account (with a bounded deposit) to activate a global call filter for `EnterDuration` blocks [1](#0-0) . Once entered, all runtime calls except those in `WhitelistedCalls` are rejected with `CallFiltered` [2](#0-1) . In the reference node runtime, `SafeModeWhitelistedCalls` only exempts `System`, `SafeMode`, and `TxPause` — `Democracy` calls are not exempted [3](#0-2) . Meanwhile, `RuntimeOrigin::filter_call` unconditionally bypasses all filters when the caller is `Root` [4](#0-3) , and Democracy's referendum enactment is always scheduled with `frame_system::RawOrigin::Root` via `pallet-scheduler` [5](#0-4) , which itself dispatches with no filter for root-origin tasks [6](#0-5) .

### Finding Description
Democracy's emergency safety valves — `veto_external` (gated by `VetoOrigin = EnsureMember<TechnicalCollective>`) and `emergency_cancel` (gated by `CancellationOrigin = EnsureProportionAtLeast<CouncilCollective, 2, 3>`) — are configured in the node runtime [7](#0-6) . These calls are dispatched from *non-Root* origins (a technical-committee member's signed origin, or a collective "Members" origin produced by council `execute`/`propose` flows), which are still subject to `frame_system::Config::BaseCallFilter` per `OriginTrait::filter_call`'s Root-only bypass [8](#0-7) .

If `SafeMode` (or `TxPause`, which pauses specific pallet/call names [9](#0-8) ) is composed into `BaseCallFilter`, and Democracy's veto/cancel calls are not on the whitelist, then while safe-mode/tx-pause is active:
- `veto_external` and `emergency_cancel` fail with `CallFiltered`.
- The already-scheduled, previously-approved referendum enactment (queued via `Scheduler::schedule_named` with `RawOrigin::Root`) is **not** filtered, because Root bypasses the filter entirely, and still executes on its scheduled block.

Because `SafeMode::enter()` is permissionless (any signed account can call it, subject only to a configurable deposit) [10](#0-9) , an attacker (or a party who benefits from a pending malicious/undesirable referendum enacting unchallenged) can call `enter` right before the council/technical-committee window to veto or emergency-cancel closes, disabling that intervention path for the configured duration while the Root-scheduled enactment proceeds unimpeded — exactly mirroring the "pausing disables challenging" bug class from the audit report.

### Impact Explanation
If exploited, a malicious or erroneous proposal that has already passed a referendum vote could be shielded from council/technical-committee intervention (`veto_external`/`emergency_cancel`) during the safe-mode window, while its Root-origin enactment (e.g., an arbitrary `Balances`/`Treasury`/`System` call approved via governance) executes unhindered. This could result in irreversible on-chain state changes (fund transfers, parameter changes) that governance intended to be revocable.

### Likelihood Explanation
This requires: (1) `pallet-safe-mode` or `pallet-tx-pause` actually wired into `BaseCallFilter` in the deployed runtime, (2) Democracy's cancel/veto calls not included in `WhitelistedCalls`, and (3) a live scenario where a pending referendum enactment coincides with the safe-mode window. I was able to confirm (1) is the intended, documented composition pattern for both pallets (their own module docs specify `type BaseCallFilter = InsideBoth<DefaultFilter, SafeMode/TxPause>`), and (2) is true for the specific reference `substrate/bin/node/runtime` configuration examined. I was **not able to fully verify** the exact `type BaseCallFilter = ...` line content in that runtime file within the available tool budget (only a match was found, not its content), so I cannot state with certainty that this exact runtime wires `SafeMode`/`TxPause` into `BaseCallFilter` in production. This is a design/configuration risk inherent to combining `pallet-safe-mode`/`pallet-tx-pause` with `pallet-democracy` (or similarly `pallet-referenda`, whose `cancel`/`kill` calls are gated by `CancelOrigin`/`KillOrigin` and are likewise not automatically Root) without deliberately whitelisting the governance safety-valve calls.

### Recommendation
- Always include governance safety-valve calls (`Democracy::veto_external`, `Democracy::emergency_cancel`, `Democracy::cancel_referendum`, `Referenda::cancel`, `Referenda::kill`) in `SafeMode`'s and `TxPause`'s `WhitelistedCalls` so they remain callable while the pause is active.
- Alternatively, make Root-origin scheduled enactments also subject to a pause-aware check (e.g., have the scheduler consult `SafeMode`/`TxPause` state directly rather than relying purely on `BaseCallFilter`'s Root bypass), removing the asymmetry between "execute" and "cancel" paths.
- Audit any runtime that combines `pallet-safe-mode`/`pallet-tx-pause` with `pallet-democracy`/`pallet-referenda` to ensure this whitelist is explicit and tested.

### Proof of Concept
Not executed against a live network. The chain of evidence supporting reachability was assembled from source inspection only:
1. `SafeMode::enter` — permissionless, `ensure_signed` only [1](#0-0) .
2. `SafeMode::is_allowed`/`Contains` impl rejects non-whitelisted calls while entered [11](#0-10) .
3. Node runtime whitelist excludes Democracy [3](#0-2) .
4. Root-origin bypass of all filters [4](#0-3) , confirmed by an existing unit test [12](#0-11) .
5. Democracy enactment always scheduled as Root [5](#0-4) .
6. Veto/cancellation origins are non-Root collective origins [7](#0-6) .

I did not run an integration test (e.g., a ext_builder-based repro dispatching `SafeMode::enter`, then `Democracy::veto_external`/`emergency_cancel`, then advancing blocks to observe scheduled enactment succeed) because I could not confirm within the tool budget that the reference runtime's `BaseCallFilter` type actually composes `SafeMode`/`TxPause`— I only located the match location, not its content. **This is the key unresolved gap**: a background engineer with full repo/test access should (a) read the exact `type BaseCallFilter` definition in `substrate/bin/node/runtime/src/lib.rs`, and (b) write a `substrate/bin/node/runtime` (or a minimal mock-runtime) integration test combining `pallet-safe-mode`, `pallet-tx-pause`, and `pallet-democracy` to confirm `veto_external`/`emergency_cancel` fail with `CallFiltered` while a Root-scheduled enactment still fires, before treating this as a confirmed, shippable finding rather than a design-risk analog.
