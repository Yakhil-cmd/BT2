### Title
Precompile signature verification bypasses compute-unit metering, decoupling leader-side cost accounting from actual cryptographic work - ([File: program-runtime/src/invoke_context.rs])

### Summary
Precompile instructions (`secp256k1`, `ed25519`, `secp256r1`) perform real, CPU-expensive cryptographic verification (`libsecp256k1` ECDSA recovery, OpenSSL `BigNum`-based ECDSA verification, ed25519 strict verification) but are executed through `InvokeContext::process_precompile`, which never calls `compute_meter.consume_checked(...)`, unlike every other builtin program which is wrapped by the `declare_process_instruction!` macro that always meters CU before running. The leader's cost model only assigns a fixed, count-based estimate for these signatures (`SIGNATURE_COST`, `SECP256K1_VERIFY_COST`, `ED25519_VERIFY_STRICT_COST`, `SECP256R1_VERIFY_COST`) which is *credited back* after execution because 0 CU are actually consumed from the meter. This is directly analogous to the Unbound CVE: a limiting mechanism (the compute-budget/cost-model bound on per-transaction work) exists, but the specific code path that performs the expensive hashing/cryptography (`process_precompile` / the `verify` functions in `precompiles/src/{secp256k1,ed25519,secp256r1}.rs`) never consults or is bound by it.

### Finding Description
Normal builtin/native programs consume compute units up front via the `declare_process_instruction!` macro: [1](#0-0) 

However, precompile instructions are routed through a separate path that skips this metering entirely: [2](#0-1) 

The actual verification work performed for "free" (from the compute-meter's perspective) includes a full loop of `libsecp256k1` signature-recovery operations for every signature packed into a `secp256k1` instruction, bounded only by a `u8` count (up to 255) and instruction-data-size checks, with no compute-unit cost applied per iteration at runtime: [3](#0-2) 

The `secp256r1` precompile performs OpenSSL `BigNum`/`EcPoint` arithmetic (more CPU-expensive than the k1 recovery path) for up to 8 signatures per instruction, again unmetered at runtime: [4](#0-3) 

The cost model only ever assigns a static per-signature cost for scheduling/block-limit purposes: [5](#0-4) 

This is confirmed by an existing test that explicitly documents the mismatch: a transaction containing a single precompiled instruction reserves `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` CU in the cost model, but "VM Execution: consume 0 from CU-meter," so the entire reserved cost is credited back (`cost_adjustment == MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT`): [6](#0-5) 

In other words, the mechanism that is supposed to bound per-transaction/per-block computational work (the compute budget and cost tracker, which back `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS`) does not take into account the real cost of precompile cryptographic verification — exactly the same bug class as the reported Unbound CVE, where the DS-negative-cache code path failed to consult the NSEC3 hash-count limit that was supposed to bound expensive hashing.

### Impact Explanation
Because the actual EC/BigNum verification work for precompiles is unmetered by the compute budget, and the cost model refunds the full reserved allocation once the (zero) CU consumption is observed, an attacker can construct transactions packed with the maximum number of precompile instructions/signatures (multiple `secp256k1`, `secp256r1`, and `ed25519` instructions, each carrying their maximum signature counts) that are accounted at near-zero real cost in the leader's cost tracker while performing substantial real CPU-bound cryptography (elliptic curve recovery/verification) during execution and during replay by every downstream validator. Since leader-side cost limits (`MAX_BLOCK_UNITS`, `MAX_WRITABLE_ACCOUNT_UNITS`) are computed from the (incorrect, refunded) cost-model estimate rather than the real work performed, an attacker can fill blocks with far more actual cryptographic computation than the cost limits are designed to allow, degrading leader and replaying-validator throughput and potentially causing slow block production or missed slots under sustained load — a leader-side cost-limit bypass DoS.

### Likelihood Explanation
This is reachable by any unprivileged transaction sender: constructing transactions with `secp256k1_program`, `ed25519_program`, and `secp256r1_program` instructions with maximal signature counts requires no special privileges, and the discrepancy between the cost model estimate and zero actual CU consumption is explicitly exercised and asserted by the repository's own test (`test_builtin_ix_precompiled`), confirming the behavior is deterministic and not a corner case.

### Recommendation
Meter precompile verification against the compute budget proportionally to the real cryptographic work performed (e.g., consume CU per signature verified, mirroring `SECP256K1_VERIFY_COST`/`SECP256R1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST` at the point the verification is actually executed in `InvokeContext::process_precompile`), rather than only estimating it statically in the cost model and refunding it post hoc. Ensure the cost-model estimate and the compute-meter charge for precompiles converge so that leader block-cost limits accurately bound real CPU work.

### Proof of Concept
Not independently executed (index-only investigation); the discrepancy is demonstrated by the existing repository test `test_builtin_ix_precompiled` in `core/tests/scheduler_cost_adjustment.rs` (lines 381-402), which shows a transaction containing a single precompile instruction consumes 0 CU from the meter and has its entire reserved cost-model allocation credited back — a concrete Devin session with a running validator/test harness would be needed to construct and measure wall-clock/CPU impact of a transaction packed with maximal secp256k1/secp256r1/ed25519 signature counts across multiple precompile instructions to fully quantify the leader-side cost-limit bypass.

                    $inner

                let consumption_result = if $cu_to_consume > 0
                {
                    invoke_context.compute_meter.consume_checked($cu_to_consume)

                            .map_err(|err| Box::new(err) as Box<dyn std::error::Error>)
                    })

            }
        );

pub fn verify(
    data: &[u8],
    instruction_datas: &[&[u8]],
    _feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    if data.is_empty() {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let count = data[0] as usize;
    if count == 0 && data.len() > 1 {
        // count is zero but the instruction data indicates that is probably not
        // correct, fail the instruction to catch probable invalid secp256k1
        // instruction construction.
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let expected_data_size = count
        .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
        .saturating_add(1);
    if data.len() < expected_data_size {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    for i in 0..count {
        let start = i
            .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
            .saturating_add(1);
        let end = start.saturating_add(SIGNATURE_OFFSETS_SERIALIZED_SIZE);

        let offsets: SecpSignatureOffsets = bincode::deserialize(&data[start..end])
            .map_err(|_| PrecompileError::InvalidSignature)?;

        // Parse out signature
        let signature_index = offsets.signature_instruction_index as usize;
        if signature_index >= instruction_datas.len() {
            return Err(PrecompileError::InvalidInstructionDataSize);
        }
        let signature_instruction = instruction_datas[signature_index];
        let sig_start = offsets.signature_offset as usize;
        let sig_end = sig_start.saturating_add(SIGNATURE_SERIALIZED_SIZE);
        if sig_end >= signature_instruction.len() {
            return Err(PrecompileError::InvalidSignature);
        }

        let signature = libsecp256k1::Signature::parse_standard_slice(
            &signature_instruction[sig_start..sig_end],
        )
        .map_err(|_| PrecompileError::InvalidSignature)?;

        let recovery_id = libsecp256k1::RecoveryId::parse(signature_instruction[sig_end])
            .map_err(|_| PrecompileError::InvalidRecoveryId)?;

        // Parse out pubkey
        let eth_address_slice = get_data_slice(
            instruction_datas,
            offsets.eth_address_instruction_index,
            offsets.eth_address_offset,
            HASHED_PUBKEY_SERIALIZED_SIZE,
        )?;

        // Parse out message
        let message_slice = get_data_slice(
            instruction_datas,
            offsets.message_instruction_index,
            offsets.message_data_offset,
            offsets.message_data_size as usize,
        )?;

        let message_hash: [u8; 32] = solana_keccak_hasher::hash(message_slice).to_bytes();
        let pubkey = libsecp256k1::recover(
            &libsecp256k1::Message::parse_slice(&message_hash).unwrap(),
            &signature,
            &recovery_id,
        )
        .map_err(|_| PrecompileError::InvalidSignature)?;
        let eth_address = eth_address_from_pubkey(&pubkey.serialize()[1..].try_into().unwrap());

        if eth_address_slice != eth_address {
            return Err(PrecompileError::InvalidSignature);
        }
    }
    Ok(())
}

pub fn verify(
    data: &[u8],
    instruction_datas: &[&[u8]],
    _feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    if data.len() < SIGNATURE_OFFSETS_START {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    let num_signatures = data[0] as usize;
    if num_signatures == 0 {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }
    if num_signatures > 8 {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }

    let expected_data_size = num_signatures
        .saturating_mul(SIGNATURE_OFFSETS_SERIALIZED_SIZE)
        .saturating_add(SIGNATURE_OFFSETS_START);

    // We do not check or use the byte at data[1]
    if data.len() < expected_data_size {
        return Err(PrecompileError::InvalidInstructionDataSize);
    }

    // Parse half order from constant
    let half_order: BigNum =
        BigNum::from_slice(&SECP256R1_HALF_ORDER).map_err(|_| PrecompileError::InvalidSignature)?;

    // Parse order - 1 from constant
    let order_minus_one: BigNum = BigNum::from_slice(&SECP256R1_ORDER_MINUS_ONE)
        .map_err(|_| PrecompileError::InvalidSignature)?;

    // Create a BigNum for 1
    let one = BigNum::from_u32(1).map_err(|_| PrecompileError::InvalidSignature)?;
