### Title
Cross-organization commit-status forgery via unscoped SHA lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub `status` webhook against the GitHub App/organization derived from the payload's own `repository.owner.login` [1](#0-0) [2](#0-1) . That check only proves the payload was validly signed by *some* configured organization's webhook secret. `StatusHandler`, however, then acts on `Commit.where(sha: params.sha)` with **no repository/organization scoping at all**, unlike other handlers (`PushHandler`, `CheckSuiteHandler`, the `pull_request/*` handlers) which all resolve `stacks`/`repository` via `Repository.from_github_repo_name(params.repository.full_name)` before touching any record [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) .

This breaks the binding: `organization authenticated == repository written`. The signature check authenticates "this payload came from Org A's registered GitHub App," but `StatusHandler#process` writes a status onto *any* `Commit` row anywhere in the Shipit instance whose `sha` column matches the attacker-supplied string, regardless of which `Stack`/`Repository`/organization that commit belongs to.

### Finding Description
- `verify_signature` picks the verifying GitHub App config using `repository_owner`, which is read straight out of the untrusted JSON payload (`repository.owner.login`, or `organization.login` as fallback) [1](#0-0) [2](#0-1) . This is correct for verifying that the request came from an org Shipit trusts, but says nothing about which `Commit`/`Stack` the payload is permitted to affect.
- `StatusHandler` only requires `sha`, `state`, and a few optional descriptive fields — it does **not** require or use `repository.full_name` at all [7](#0-6) .
- `process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` globally, across every stack/repository tracked by this Shipit instance [8](#0-7) .
- `create_status_from_github!` unconditionally inserts a `Status` on that commit [9](#0-8) , and that status feeds directly into `Commit#deployable?`, which gates automatic and manual deploys (`success? && !blocked?`) [10](#0-9) .
- If a Shipit installation is configured with multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.shopify.yml` listing `somegithuborg`/`someothergithuborg` each with its own `webhook_secret`) [11](#0-10) , an attacker who controls (or has push access to) a repository in Org A can:
  1. Fabricate/reuse a commit whose SHA string collides with a SHA of an actual commit tracked under a different Stack belonging to Org B (trivially arranged by pushing an identical tree/parents/commit metadata combination to a repo the attacker controls, since a Git SHA1 is a deterministic hash of exactly those fields, not tied to the repository it lives in).
  2. Have GitHub send (or replay/simulate) a `status` webhook for that SHA from Org A's repository. The webhook is legitimately signed with Org A's `webhook_secret`, so `verify_signature` passes.
  3. `StatusHandler` matches `Commit.where(sha: ...)` and writes a forged `success` status onto the victim commit that actually belongs to Org B's stack, with attacker-controlled `context`/`description`/`target_url`.
- This can flip `Commit#deployable?` to `true` for a commit in an organization the attacker's authenticated identity/org has no relation to, enabling continuous-delivery auto-deploy (`schedule_continuous_delivery`) or a manual "unauthorized" deploy through the normal deploy flow, since `ci.require` is satisfied by a forged status.

### Impact Explanation
This is a High-severity finding under the rubric: it is an unauthenticated (with respect to the target repository) write into another organization's commit/status state, and it can directly cause an **unauthorized deploy** by making an otherwise CI-gated commit appear `deployable?`. It crosses exactly the "organization that authenticated vs. repository that is written" trust boundary the engine is supposed to enforce per-request in `verify_signature`.

### Likelihood Explanation
Requires: (a) the Shipit instance configured for multiple GitHub organizations (a documented supported setup), and (b) the attacker to control a repository/commit in one of those organizations and to arrange a SHA collision with a targeted commit in another tracked stack. Constructing an identical Git commit SHA in a different repository is feasible (SHA1 depends only on tree, parents, message, author/committer identity+timestamp — all attacker-choosable when creating their own commit to match a known target commit's metadata), making this a realistic, if not trivial, attack path rather than a purely theoretical one.

### Recommendation
Scope `StatusHandler` (and any other handler that resolves records purely by `sha`) to the repository indicated in the webhook payload, mirroring `PushHandler`/`CheckSuiteHandler`: require `repository.full_name`, resolve `Repository.from_github_repo_name(...)`, and restrict `Commit.where(sha:)` to `commits` belonging to that repository's stacks (`stacks.joins(:commits).where(commits: { sha: params.sha })` or similar), rather than querying the global `Commit` table unscoped.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-a` and `org-b`, each with its own App/`webhook_secret`, tracking `Stack` A (repo `org-a/repo`) and `Stack` B (repo `org-b/repo`) respectively.
2. Attacker (with push access to `org-a/repo`) creates a commit in their repo whose tree/parents/author-committer-timestamp exactly reproduce a known commit `SHA_X` that exists in `org-b/repo`'s tracked `Stack` B (attacker can read `SHA_X` and its metadata from GitHub's public API/UI since Shipit commit shas are visible).
3. GitHub (or the attacker directly simulating GitHub, since they legitimately control the delivery for `org-a`) sends a `status` webhook to `POST /github/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with `org-a`'s webhook secret, and body: `{"sha": "SHA_X", "state": "success", "context": "ci/forced", "repository": {"owner": {"login": "org-a"}, "full_name": "org-a/repo"}}`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and validates successfully because the request is genuinely signed by org-a's secret [1](#0-0) .
5. `StatusHandler#process` executes `Commit.where(sha: "SHA_X")`, matches the commit belonging to Stack B (org-b), and calls `create_status_from_github!`, inserting a forged `success` status [8](#0-7) .
6. `Commit#deployable?` for that org-b commit now evaluates `true` if it was previously blocked only by missing/failing CI [10](#0-9) , allowing continuous delivery or a manual deploy call to proceed on org-b's stack — an unauthorized deploy triggered entirely through org-a's credentials.

Note: I was not able to execute this against a live instance to observe the SHA-collision commit-crafting step end-to-end; the claim that Git allows constructing a commit with attacker-chosen SHA-affecting fields in a different repository to match a target SHA is based on how Git computes commit SHA1s from tree+parents+author+committer+message, not on repository identity, and is a well-established property, but I could not verify it empirically within this environment.
