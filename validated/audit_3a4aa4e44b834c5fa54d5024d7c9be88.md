### Title
Stale stored `Account.owner` keeps spending authority after position-NFT transfer, letting the previous owner drain the new owner's account - ([File: contracts/controller/src/account.rs](contracts/controller/src/account.rs))

### Summary
The controller authorizes every account-spending operation (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) against the `owner` field stored inside the `Account` struct at creation time, not against the live position-NFT owner. The position NFT is a freely transferable stock OpenZeppelin NFT with no controller callback, so a transfer changes `account_owner` while `Account.owner` still names the previous holder. The previous holder retains full delegate-equivalent authority and can borrow against or withdraw the account's collateral — the analog of CVE-2024-36537's "insecure permissions let an attacker reuse a service account's authority to escalate privileges."

### Finding Description
`create_account` fixes `Account { owner, ... }` once, at mint:

```rust
// contracts/controller/src/account.rs
let account = Account {
    owner: owner.clone(),   // frozen at creation
    ...
};
```

All spending gates then trust that stored field. `load_or_create_account` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` for `Migrate` and `Multiply`, and `is_owner_or_delegate` short-circuits on `caller == owner` — the stored owner, not the NFT owner:

```rust
// contracts/controller/src/account.rs
pub(crate) fn is_owner_or_delegate(...) -> bool {
    if caller == owner {          // `owner` = stored Account.owner
        return true;
    }
    ...delegate check...
}
```

Meanwhile, the account's real ownership lives in the position NFT (`mint`, `burn`, `upgrade` are keyed to the construction-time controller address, but `transfer`/`transfer_from`/`approve` are stock NonFungibleToken methods callable by any holder). Only `require_account_owner` — used by `renew_account`, `add_delegate`, `remove_delegate` — reads the live owner via `storage::account_owner`. The money-moving paths read the stale `account.owner`.

So after `position-nft::transfer(from=victim_old_owner, to=buyer, token_id)`:

- The buyer (new NFT owner) is rejected by `require_owner_or_delegate` — they cannot `withdraw`, `borrow`, or manage their own collateral (temporary freezing of funds).
- The seller (stale `account.owner`) still passes the auth gate and can call `withdraw` to pull out all supply collateral, or `borrow` to max out debt against the account and walk away.

The declared invariant list confirms the intent: "the NFT owner is the account owner, so each one moves or delegates control of a whole lending account" — but the authority actually granted by `is_owner_or_delegate` tracks the stored field, not the NFT.

Caveat: I could not fully verify whether any code path (e.g., `storage::get_account` or an explicit resync in the transfer flow) rewrites `Account.owner` after an NFT transfer; no such resync was found in `account.rs`, and the position NFT ships stock OpenZeppelin transfer logic with no controller hook, so there is no obvious synchronization point. If a resync exists elsewhere, this finding collapses.

### Impact Explanation
Theft of user funds and freezing of the legitimate owner's funds. A seller lists/transfers a funded account NFT; the buyer pays for the position, then the seller calls `withdraw(account_id, ...)` and `borrow(account_id, ...)` using their stale authority to extract all collateral and borrowed proceeds, leaving the buyer an empty or maximally indebted NFT. The buyer cannot even defend themselves, since the same stale-owner check blocks their calls. Impact class: theft of user funds; secondary: temporary/permanent freezing of funds for the new owner.

### Likelihood Explanation
Fully reachable by a single unprivileged address via `position-nft::transfer` followed by `controller::withdraw`/`borrow` — both are declared caller-auth permissionless entrypoints. The attack needs a victim willing to receive a funded account NFT (sale, OTC deal, "gift" of a leveraged position), which is the exact use case the NFT design enables. No privileged role, leaked key, or off-chain component is required, matching the cert-manager bug class of weak permission binding rather than a missing check outright.

### Recommendation
Derive spending authority from the live NFT owner everywhere, not the stored `Account.owner`:

- In `is_owner_or_delegate`/`require_owner_or_delegate`, resolve `owner` via `storage::account_owner(env, account_id)` (the NFT `owner_of`) instead of `account.owner`.
- Treat `Account.owner` as a creation-time record only, or remove it and always read the NFT.
- Ensure delegate grants keyed to the old owner cannot outlive a transfer: `get_delegates(env, account_id, owner)` is already keyed per-owner, so resolving `owner` live automatically scopes stale delegates to the seller.
- Add a test mirroring `tests/test-harness/tests/controller/ownership.rs`: transfer NFT → assert old owner cannot `borrow`/`withdraw` and new owner can.

### Proof of Concept
```rust
// Setup: user A creates account, supplies USDC collateral.
let account_id = ctrl.supply(&user_a, &0, &usdc_key, &SPOKE, &supply_amt, &PositionMode::Basic);

// Attacker path: user A "sells" the account NFT to victim B.
nft.transfer(&user_a, &user_b, &(account_id as u32));

// Invariant break: live NFT owner is B, stored Account.owner is still A.
assert_eq!(nft.owner_of(&(account_id as u32)), user_b);

// A retains spending authority via stale `account.owner` in is_owner_or_delegate:
ctrl.borrow(&user_a, &account_id, &usdc_key, &SPOKE, &borrow_amt);   // succeeds
ctrl.withdraw(&user_a, &account_id, &usdc_key, &SPOKE, &supply_amt); // drains B's collateral

// B is locked out of their own account:
// ctrl.withdraw(&user_b, ...) -> NotAuthorized
```

Root cause: `is_owner_or_delegate` compares `caller` to stored `Account.owner` (account.rs:121) while ownership is actually defined by the transferable NFT; `require_owner_or_delegate` on the spending path is reachable by `controller::borrow`/`withdraw` via the caller-auth surface.
