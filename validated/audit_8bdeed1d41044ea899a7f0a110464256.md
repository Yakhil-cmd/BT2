### Title
Malformed/missing `author.definition` in `arbiter_contract_response` is silently accepted and cached as a valid peer address definition - ([File: wallet.js])

### Summary
Eclipse Mosquitto's CVE-2018-12551 stems from a parser that treats malformed credential-file entries as valid, implicitly authenticating a party that supplied bad/incomplete data instead of rejecting it. The `arbiter_contract_response` handler in `wallet.js` contains an analogous validation gap: the check that a peer's address actually corresponds to the address-definition it claims is skipped whenever `author.definition` is falsy, and the (possibly `null`/malformed) value is then persisted into `peer_addresses` as if it were a verified definition.

### Finding Description
When a contract counterparty accepts an arbiter contract, the hub-message handler validates the outer `signed_message` (real signature check) but then separately trusts a distinct, attacker-controlled `body.authors` array to update the local `peer_addresses` cache: [1](#0-0) 

The critical defect is the conditional definition check:
```
if (author.definition && (author.address !== objectHash.getChash160(author.definition)))
    return callbacks.ifError("incorrect definition received");
``` [2](#0-1) 

This only validates the address-to-definition binding **when `author.definition` is truthy**. A malicious/compromised peer device can omit `definition` (send `null`/`undefined`) while keeping `author.address` equal to the expected `objContract.peer_address` (which passes the separate `isValidAddress` check trivially, since it's just a known, legitimate-looking address string). The subsequent code path unconditionally writes this incomplete/malformed record into the `peer_addresses` table:
```
INSERT ... INTO peer_addresses (address, device_address, signing_paths, definition)
VALUES (?, ?, ?, ?)   -- definition = JSON.stringify(author.definition) = "null"
``` [3](#0-2) 

This mirrors the mosquitto bug class exactly: malformed/blank data (`no definition`) is treated as an implicitly valid entry rather than being rejected outright, and gets stored as authoritative peer/cosigner metadata (`device_address`, `signing_paths`, `definition`) associated with `from_address` for a legitimate-looking address. The `peer_addresses` table is subsequently consulted by wallet routing logic to decide which device address is authoritative for a signing path and whether an address is a valid candidate cosigner for a shared/multisig address: [4](#0-3) [5](#0-4) 

### Impact Explanation
By exploiting the falsy-`definition` bypass, a malicious device claiming to be `objContract.peer_address` can get itself recorded as the `device_address` responsible for that address's signing paths in `peer_addresses`, using authentifier key names taken from the *validated* `signed_message` (`Object.keys(objSignedMessage.authors[0].authentifiers)`) but with a `definition` field that is `null`/malformed rather than the real address definition. Because entries are inserted only if `rows.length` from `my_addresses`/`shared_addresses` is zero (i.e., `author.address` is not one of the local user's own addresses), and updated via `INSERT ... IGNORE` / fallback `UPDATE`, an attacker can also overwrite a previously-cached legitimate definition for a peer address (since the primary key is `address`, and the code deliberately updates on conflict), corrupting the cache used to route future signing requests and multisig-cosigner discovery (`findAddress`, `readAdditionalSigningAddresses`). This can misdirect signing-request routing to the wrong/attacker device_address for a peer's signature contribution to a shared address, or cause a shared/arbiter-contract multisig transaction to be built with corrupted/missing cosigner metadata — a fund-loss/fund-freezing risk for the wallet relying on this cache for private-payment/contract counterparties, reachable purely from a peer sending a crafted `arbiter_contract_response` device message.

### Likelihood Explanation
The trigger is reachable by any unprivileged peer device that has been offered (or is negotiating) an arbiter contract — no special privilege, hub cooperation, or network-level attack is required, only a normal paired-device message (`arbiter_contract_response`) with a validly-signed `signed_message` for the correct `peer_address` but a separate, unvalidated `body.authors[0]` lacking `definition`. Because the outer signature check (`signed_message.validateSignedMessage`) only certifies the `signed_message` payload, not the `body.authors` array used for the peer_addresses cache update, the exploit condition is straightforward to construct.

### Recommendation
Require `author.definition` to be present and require its hash to match `author.address` unconditionally (reject when `!author.definition`), rather than only checking the hash match when `definition` is truthy. Additionally, validate that `objectHash.getChash160(author.definition)` corresponds to a definition consistent with the arbiter-contract's expected multisig template before persisting into `peer_addresses`, and avoid silently overwriting a previously-verified `peer_addresses` entry with a downgraded/incomplete one.

### Proof of Concept
1. Attacker device pairs with victim and negotiates/accepts an arbiter contract as `objContract.peer_address`.
2. Attacker crafts a valid `signed_message` (satisfying `signed_message.validateSignedMessage`) for `objContract.title`, signed by `objContract.peer_address`, but sends the outer `arbiter_contract_response` body with:
   - `status: "accepted"`
   - `signed_message: <base64 of the valid signed message>`
   - `authors: [{ address: objContract.peer_address }]` — **omitting `definition`**
3. In `wallet.js` `processResponse`, the `author.definition` falsy check bypasses the hash-consistency validation (`wallet.js:886`), and the record is inserted/updated into `peer_addresses` with `definition = "null"` for `objContract.peer_address`, associated with the attacker's `from_address` device (`wallet.js:899-904`).
4. Later wallet operations that consult `peer_addresses` (`findAddress`, `readAdditionalSigningAddresses`) route signing requests for `objContract.peer_address` to the attacker's device / use the corrupted metadata when composing a shared-address multisig transaction, per `wallet.js:1289-1311` and `wallet.js:1869-1898`.
