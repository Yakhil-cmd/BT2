Found the exploitable binding break: the `StatusHandler` binds a webhook-supplied `sha` to *every* commit in the database sharing that SHA, across all repositories and organizations — not just commits belonging to the organization whose secret validated the signature.

### Title
Cross-repository commit status forgery via organization-scoped webhook signature but global `sha` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook using the secret of the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field, and only that field is used to select the verifying secret. Once verified, the raw JSON is dispatched by event type, and `StatusHandler#process` looks up commits purely by `sha`, with no repository or organization scoping: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }`.

### Finding Description
The equality that should hold is: *the organization whose webhook secret authorized this request* == *the repository/organization whose data gets mutated*. The signature check binds trust to `repository_owner` (derived only from `repository.owner.login`/`organization.login`), while the actual mutation performed by `StatusHandler` is scoped by `sha` alone, with no re-check against the organization that authenticated the request: [1](#0-0) [2](#0-1) 

Because commit SHAs are 40-hex Git object identifiers, not organization- or repository-specific values, an attacker who legitimately controls (or can install the Shipit GitHub App on) any low-privilege organization/repository tracked by the same Shipit instance can send a `status` webhook, correctly signed with their own organization's `webhook_secret`, whose `sha` field is copied from a commit that also exists in an unrelated, higher-privilege repository/stack (e.g., an identical commit shared via a fork, cherry-pick, or a colliding/attacker-chosen commit uploaded to their own throwaway repo and then also present upstream). `StatusHandler` will attach the attacker-controlled `state`/`context`/`target_url`/`description` to *that* commit's status in Shipit, regardless of which repository it belongs to, because `Commit.where(sha:)` is not scoped to the `Repository` derived from the authenticated `repository_owner`. Compare this with `Handler#stacks`, which does scope by `repository_name`, showing the codebase is aware such scoping is required elsewhere but `StatusHandler` bypasses it: [3](#0-2) 

This is directly analogous to the `strncpy` finding: the verification step (`idx`/`num` bound check, here the org/webhook-secret check) covers one field (destination bound / `repository_owner`), while the actual write operation (`memset`/commit-status write) is keyed off a different, unguarded quantity (`num` counted from the wrong origin / raw `sha` with no owner check), causing memory outside the verified region — here, commit records outside the verified organization/repository — to be overwritten.

### Impact Explanation
Commit statuses drive Shipit's CI gating and merge-queue decisions (`ci.require`, deploy safety checks). A forged "success" status on a commit belonging to a stack the attacker does not control can enable an unauthorized deploy/merge of that commit by satisfying CI requirements it did not actually pass — this falls under the "unauthorized deploy, rollback or merge" Critical-impact category, achieved through a cross-repository/cross-organization write that the webhook signature was never supposed to authorize for that target.

### Likelihood Explanation
The attacker only needs the ability to have a `status` webhook fired from an organization/repository they legitimately control on the same Shipit instance (a normal, unprivileged capability if Shipit tracks multiple orgs/tenants, or is installed on a public GitHub App usable by outside collaborators) and to arrange for a commit SHA to be shared or predicted between their own low-privilege repository and the target repository (e.g., via forks, cherry-picks, or empty/no-op commits that are byte-identical and thus SHA-identical across repositories). This requires no session, no API token, and no compromise of the target's own secret — only a valid webhook from any tracked, distinct organization.

### Recommendation
- Short term: In `StatusHandler#process`, scope the `Commit` lookup to commits belonging to the repository resolved from the verified `repository_owner`/`repository.full_name`, mirroring the `Handler#stacks` pattern (`Repository.from_github_repo_name(repository_name)&.stacks`) instead of a bare `Commit.where(sha:)`.
- Long term: Audit every webhook handler for the same class of "authenticate on field A, act on field B" gap and enforce a shared helper that always joins any DB record being mutated through the repository resolved from the authenticated organization.

### Proof of Concept
1. Shipit tracks two stacks: `victim-org/critical-app` (target) and `attacker-org/throwaway` (attacker-controlled, with its own legitimately configured `webhook_secret`).
2. Attacker pushes an identical (empty or cherry-picked) commit to `attacker-org/throwaway` that happens to also exist as a tracked commit in `victim-org/critical-app` (same SHA), e.g. by cherry-picking a public commit from `critical-app` into their own repo.
3. Attacker crafts (or lets GitHub genuinely send) a `status` event payload for `attacker-org/throwaway` with that shared `sha` and `state: "success"`, `context: "ci/required-check"`, correctly HMAC-signed with `attacker-org`'s own `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s `webhook_secret`, and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the commit row belonging to `victim-org/critical-app`, and calls `create_status_from_github!`, marking the victim commit as passing CI in Shipit — potentially unblocking merge/deploy for a commit the attacker never had rights over.
