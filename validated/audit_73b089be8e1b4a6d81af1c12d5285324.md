### Title
Webhook signature verified against the org named in the unsigned payload, not the repository the event actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `webhook_secret` to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, not-yet-verified request body. Handlers, however, resolve the actual `Stack`/`Repository` to act on using an entirely different payload field, `repository.full_name`. Because Shipit natively supports multiple independently configured GitHub organizations (each with its own `webhook_secret`), an attacker who legitimately controls one configured organization can forge a correctly-signed webhook whose signature verifies against their own org's secret while its `repository.full_name` field names a stack belonging to a different, victim organization.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is defined as: [2](#0-1) 
This value is taken directly from the JSON body the attacker controls, before the signature has been checked. `Shipit.github` looks up the corresponding `GitHubApp` config/secret purely by this attacker-supplied name, as implemented in [3](#0-2) , and the engine explicitly supports per-organization webhook secrets, documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`.

Once the signature is accepted, `create` dispatches the same raw JSON body to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` ( [4](#0-3) ). Handlers resolve the target repository/stack from a **different** field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [5](#0-4) 
This same pattern (`Repository.from_github_repo_name(params.repository.full_name)`) is used by `StatusHandler`, `PushHandler`, and every `PullRequest::*Handler`.

This breaks the binding: **the organization whose secret authenticated the request ≠ the repository the handler actually writes to.** Nothing ties `repository.owner.login` (verified) to `repository.full_name` (acted upon) — they are read from independent, equally attacker-controlled JSON paths inside the same unsigned-until-late body.

### Impact Explanation
An attacker who is an admin of any one GitHub organization onboarded to a multi-org Shipit instance (a normal, unprivileged scenario for that org, not requiring any Shipit credential) knows that organization's `webhook_secret` (visible in their own GitHub App settings) and can therefore produce a validly signed payload for it. By setting `repository.owner.login` to their own org (to pass signature verification) and `repository.full_name` to a victim stack's `owner/repo` string, they can forge arbitrary webhook events against a repository they do not control, specifically:
- `status` events processed by `StatusHandler#process` ( [6](#0-5) ), which calls `commit.create_status_from_github!(params)` for any matching `Commit` — allowing an attacker to fabricate a passing CI/status check on a victim's commit, unlocking that commit for continuous deployment.
- `push` events processed by `PushHandler#process` ( [7](#0-6) ), forcing a resync against an attacker-chosen `expected_head_sha` on the victim stack's tracked branch.

Forging a passing status on a victim commit that a continuous-deployment-enabled stack subsequently ships is an unauthorized deploy driven entirely by a forged signal, satisfying the "unauthorized deploy" Critical-impact bucket.

### Likelihood Explanation
Requires only that the attacker control (be an org admin of) one org configured in a multi-tenant Shipit deployment — an unprivileged position with respect to the victim's stacks — and knowledge of their own org's webhook secret, which they legitimately possess. No Shipit session, `ApiClient` token, or GitHub write access to the victim repository is needed.

### Recommendation
After computing `repository_owner` for secret lookup, verify that it matches the owner segment of `repository.full_name` (or `organization.login`) used by downstream handlers, and reject the webhook if they diverge. Alternatively, resolve the target `Stack`/`Repository` first and require that its configured organization equals the organization whose secret validated the signature, before invoking any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`), and a `Stack` tracking `VictimOrg/victim-repo`.
2. As the attacker (who legitimately owns `AttackerOrg` and knows its `webhook_secret`), build a `status` (or `push`) payload:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Compute `X-Hub-Signature` using `AttackerOrg`'s known `webhook_secret` over the raw JSON body.
4. POST to `Shipit::WebhooksController#create` with `X-Github-Event: status`. `verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` and validates successfully.
5. `StatusHandler#process` then creates a `Status` on the victim's commit via `Commit.where(sha: ...).each { |c| c.create_status_from_github!(params) }`, even though the request was never signed by `VictimOrg`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
