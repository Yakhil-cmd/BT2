### Title
Webhook signature verified against organization named in unverified payload, while handlers act on a different repository field in the same payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization configuration (and thus which `webhook_secret`) to validate the incoming HMAC signature against, using a value pulled directly from the **unauthenticated** JSON body itself. The actual write target (which `Stack`/`Repository` gets synced) is later derived from a **different** field of the same unverified body. The signature never binds the "organization that authenticated" to the "repository that gets written."

### Finding Description
`verify_signature` computes the org used for verification from the raw JSON body before any cryptographic check has occurred: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the `GithubApp` config (and its `webhook_secret`) tied to whatever organization name appears in `repository.owner.login` of the payload. `verify_webhook_signature` then just checks the HMAC-SHA1 of the raw body against that organization's secret: [3](#0-2) 

Once the signature check passes, the actual event handler resolves the target repository/stacks from a **different** field of the same JSON body — `repository.full_name` — via `Handler#repository_name`/`#stacks`: [4](#0-3) 

and `PushHandler#process` uses that to look up and sync a `Stack` with attacker-supplied `ref`/`after` sha: [5](#0-4) 

Because the HMAC only covers the raw bytes and is not scoped to a claimed organization, any organization onboarded to this multi-tenant Shipit instance can produce a validly-signed payload (signed with *their own* organization's `webhook_secret`, which they legitimately possess/administer as owner of their own GitHub org's webhook settings) while setting `repository.owner.login` to their own org (so verification picks their own secret and succeeds) and `repository.full_name` to a victim organization's repository tracked by a different `Stack` in the same Shipit instance. This breaks the binding: "organization authenticated == repository written."

### Impact Explanation
This allows a low-privilege actor — an admin of any one organization/repo onboarded to a shared Shipit instance — to inject fabricated push/status/PR events that are processed as if they came from a completely different, victim organization's repository. For `push`, this triggers `Stack#sync_github` with an attacker-chosen `after` SHA against the victim's stack, and other handlers (status, check_suite, pull_request, membership) similarly key off `repository.full_name` while verification keys off `repository.owner.login`, enabling cross-repository/cross-organization state manipulation without the victim organization's own webhook secret. This matches the "Critical: cross-repository writes" impact category.

### Likelihood Explanation
Any organization/tenant already integrated with a shared Shipit instance (a normal, unprivileged position relative to other tenants) can exploit this by crafting one JSON body with mismatched `owner.login` vs `full_name` and signing it with their own legitimately-known secret — no access to the victim's secret, GitHub App key, or any Shipit account is required.

### Recommendation
Bind signature verification to the same identity used for routing: after selecting the org/app config, re-derive `repository_owner` (and ideally the full `repository.full_name`) strictly from that same verified organization's known repositories, or reject the webhook if `repository.owner.login` does not match the organization owning the `full_name` repository (e.g., look up `Repository.from_github_repo_name(full_name)` and require its owner org to equal the one whose secret validated the HMAC) before dispatching to handlers.

### Proof of Concept
1. Attacker administers org `attacker-org`, onboarded to the shared Shipit instance with a known `webhook_secret`.
2. Attacker crafts a `push` payload: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/master", "after": "<attacker-chosen sha>"}`.
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` and sets `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC check passes (attacker knows this secret).
5. `PushHandler` resolves `stacks` via `full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
