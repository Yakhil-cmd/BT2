### Title
Stack-scoped API token bypasses its own `stack_id` restriction in `CCMenuController#stack` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides `BaseController#stack` and resolves the target stack directly via `Stack.from_param!(params[:stack_id])`, bypassing the `stacks` scoping helper that every other API controller relies on to enforce the `ApiClient#stack_id` restriction.

### Finding Description
`ApiClient` records can be scoped to a single stack (`belongs_to :stack, optional: true`) [1](#0-0) . `Api::BaseController` is supposed to enforce this binding for every request: it defines `stacks` to restrict the queryable set of stacks to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]` through that restricted relation via `stacks.from_param!(params[:stack_id])` [2](#0-1) .

`Api::CCMenuController`, however, redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, completely skipping the `stacks` scoping method: [3](#0-2) . The `require_permission :read, :stack` before_action still runs and only checks that the token has the `read:stack` permission bit via `ApiClient#check_permissions!` [4](#0-3)  — it never checks *which* stack the permission applies to. `#show` then renders the CI status of whatever stack was resolved [5](#0-4) .

This breaks exactly the "stack a token authorises versus stack it touches" binding: a client token whose `stack_id` is meant to equal the stack being read is not enforced — an attacker holding *any* stack-scoped API token with `read:stack` (e.g. a CCMenu token minted for one stack, as created by `CCMenuUrlController` for any authenticated user [6](#0-5) ) can pass a different `stack_id` and read the CI/deploy status of any other stack in the installation, including private/unrelated repositories they have no GitHub access to.

### Impact Explanation
This matches the "High" impact bucket defined by the rules: "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state, task streams or deploy output" for stacks the token holder was never authorized to see. It discloses deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`) for arbitrary stacks in the Shipit installation to a holder of any single stack-scoped, read-only token, cross-repository/cross-stack information disclosure that the `stack_id` binding on `ApiClient` was specifically designed to prevent.

### Likelihood Explanation
The likelihood is high for an unprivileged-but-token-holding actor: `CCMenuUrlController#fetch` mints a `read:stack` token scoped to a single stack for any logged-in Shipit user on demand [7](#0-6) , and that token can then be replayed against `Api::CCMenuController#show` with an arbitrary `stack_id` in the URL — no additional secrets, GitHub App keys, or privileged accounts are required, just possession of one legitimately-issued, narrowly-scoped read token.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the inherited `stacks.from_param!(params[:stack_id])`) so the `ApiClient#stack_id` scoping restriction from `BaseController#stacks` is applied consistently, just as it is in every other API controller.

### Proof of Concept
1. User A is granted access only to `Stack #1` (`shopify/private-app`). They visit `GET /1/ccmenu_url` (or the equivalent path), which calls `CCMenuUrlController#fetch`, creating (or reusing) an `ApiClient` with `permissions: ['read:stack']` and `stack: Stack #1`, and returns a URL containing `token=<signed_id_of_that_client>` [7](#0-6) .
2. User A (or anyone who obtains that URL/token) sends `GET /api/2/ccmenu.xml?token=<token>` where `2` is the `stack_id` of an unrelated, private `Stack #2` they have no access to.
3. `Api::CCMenuController#authenticate_api_client` authenticates the token to the `ApiClient` scoped to `Stack #1` [8](#0-7) ; `require_permission :read, :stack` passes because the client does have `read:stack` [4](#0-3) .
4. `#show` calls `stack`, which resolves `Stack.from_param!(params[:stack_id])` — i.e., `Stack #2` — ignoring the client's `stack_id` restriction, and renders `Stack #2`'s deploy/build status XML to the requester [9](#0-8) .
