### Title
`BridgeCommittee.initializeConfig` is unauthenticated and callable by anyone before the deployer's call lands, letting a frontrunner permanently bind the bridge committee to a malicious `BridgeConfig` — ([File: bridge/evm/contracts/BridgeCommittee.sol])

### Summary
This is the same root cause as the reported `DeployGovernance.s.sol` bug: deployment and initialization are split across separate transactions, leaving a public window in which an unprivileged actor can front-run the "real" initializer call. In `sui`, this exact anti-pattern is reproduced in the EVM bridge deployment flow: `BridgeCommittee.initialize(...)` is safely bound atomically inside the UUPS proxy constructor, but `initializeConfig(address _config)` is a **separate, completely unguarded external function** that is called *after* the `BridgeCommittee` proxy is already live and *after* `BridgeConfig` is deployed [1](#0-0) .

### Finding Description
`BridgeCommittee.initializeConfig` has no `initializer`, `onlyOwner`, or committee-authorization modifier — its only guard is a one-time-set check on the `config` variable itself:
```solidity
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
``` [2](#0-1) 

The deployment script confirms this is invoked as a standalone, later transaction rather than atomically with proxy creation: `BridgeCommittee` and `BridgeConfig` are each deployed via `Upgrades.deployUUPSProxy(...)` (which does bind `initialize` atomically in the proxy constructor), but `initializeConfig` is invoked afterwards, in its own broadcasted call, once `bridgeConfig`'s address is known:
```solidity
address bridgeCommittee = Upgrades.deployUUPSProxy("BridgeCommittee.sol", abi.encodeCall(BridgeCommittee.initialize, (...)), opts);
...
address bridgeConfig = Upgrades.deployUUPSProxy("BridgeConfig.sol", abi.encodeCall(BridgeConfig.initialize, (...)), opts);

// initialize config in the bridge committee
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));
``` [3](#0-2) 

Between the `bridgeCommittee` proxy going live and this later `initializeConfig` transaction confirming, `config` remains `address(0)`, and the function is public with zero access control — exactly the "temporarily uninitialized proxy, corruptible by anyone" pattern from the external report. Any address can submit `initializeConfig(attackerConfig)` for the known `bridgeCommittee` address and win the race, permanently locking in a malicious `config`, since the guard only prevents *re*-initialization, not *unauthorized* initialization.

### Impact Explanation
`committee.config()` is the trust anchor used throughout the bridge for decoding and validating cross-chain messages — e.g., `SuiBridge.transferBridgedTokensWithSignatures` reads `config.chainID()`, `config.tokenAddressOf(...)`, and `config.tokenSuiDecimalOf(...)` to determine which ERC20 token and how much to release from the vault for a given Sui-side bridge message [4](#0-3) . If an attacker front-runs `initializeConfig` with a malicious `IBridgeConfig` implementation, they can permanently corrupt the mapping from `tokenID` to `tokenAddress`/decimals that governs fund releases from the vault — this is a direct instance of "bridge message forgery... that enables illegitimate mint or unlock," which is listed as a Critical impact.

### Likelihood Explanation
Uncertain/lower confidence: this requires the attacker to observe the pending, unconfirmed `initializeConfig` transaction (mempool visibility) for a specific, publicly known `bridgeCommittee` proxy address and front-run it with a higher gas bid before the deployer's transaction confirms — a real but narrow race-condition window that exists only during initial deployment (not during normal operation), and is arguably closer to an operational/deployment risk than a always-exploitable on-chain invariant break. I was not able to fully verify whether the actual production/mainnet deployment used a batched/atomic multicall (e.g., via a deployer contract or the exact same transaction) to close this window, since only the Foundry script is present in the repo and I don't have access to the actual deployment transaction history.

### Recommendation
Bind `config` atomically at `BridgeCommittee.initialize(...)` time (pass the config address, or a deterministic/precomputed `CREATE2` address, into the initializer) rather than exposing a separate unguarded `initializeConfig` entrypoint; alternatively, gate `initializeConfig` behind the same committee-authorization used elsewhere (e.g., requiring `onlyOwner`/deployer signature) so it cannot be called by an arbitrary address even during the brief window before the "official" configuration call lands.

### Proof of Concept
1. Deployer broadcasts `Upgrades.deployUUPSProxy("BridgeCommittee.sol", initialize(...))`, producing a live `bridgeCommittee` proxy with `config == address(0)`.
2. Deployer broadcasts `Upgrades.deployUUPSProxy("BridgeConfig.sol", initialize(...))`.
3. Deployer's transaction calling `BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig))` is submitted to the mempool.
4. Attacker observes step 3's pending transaction, computes/deploys their own malicious `IBridgeConfig`-conforming contract, and submits `BridgeCommittee(bridgeCommittee).initializeConfig(maliciousConfig)` with higher gas, landing first.
5. `require(address(config) == address(0))` succeeds for the attacker; `config` is now permanently set to `maliciousConfig`; the deployer's original transaction reverts because `config != address(0)`.
6. Subsequent `SuiBridge.transferBridgedTokensWithSignatures` calls use the attacker-controlled `config.tokenAddressOf`/`tokenSuiDecimalOf` mappings, allowing incorrect token/amount resolution for vault withdrawals.
