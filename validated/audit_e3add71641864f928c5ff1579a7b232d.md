### Title
CCMenu API endpoint ignores API-client stack scoping, allowing a single-stack token to read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack via `stack_id` and are meant to only ever see that one stack, enforced through `Api::BaseController#stacks`/`#stack` [1](#0-0) . `Api::CCMenuController` overrides `#stack` and resolves the target stack directly from `Stack.from_param!(params[:stack_id])`, never consulting `current_api_client.stack_id` [2](#0-1) . This mirrors the H-09 pattern: a state-check codepath (`mint`/here, `#show`) omits a scoping check (`paused` market/here, `stack_id` binding) that is enforced everywhere else, letting an authenticated-but-narrowly-scoped credential act outside the boundary it was issued for.

### Finding Description
`Api::BaseController#authenticate_api_client` authenticates the caller into `@current_api_client`, and `#stacks`/`#stack` are the only sanctioned way controllers narrow the visible stack set to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped [1](#0-0) . `Api::StacksController` correctly reuses this via `stacks.from_param!(params[:id])` [3](#0-2) .

`CCMenuUrlController#client` mints exactly such a scoped token, explicitly tied to one stack via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` and associated with `stack.to_param` in the generated URL [4](#0-3) . However, `Api::CCMenuController#stack` does not call the inherited scoped `stacks` method; it calls `Stack.from_param!(params[:stack_id])` unconditionally [2](#0-1) , and `require_permission :read, :stack` only checks that the `read:stack` permission bit is present on the token, not which stack it is bound to [5](#0-4) .

The equality that should hold is: `stack a token authorizes == stack the token can query`, i.e. `current_api_client.stack_id == stack.id` whenever `current_api_client.stack_id?`. Because `CCMenuController#stack` never reads `current_api_client.stack_id`, this equality is not enforced: a token minted for stack A, when given `stack_id=B` as the query param, willingly renders stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, activity) [6](#0-5) .

### Impact Explanation
This satisfies the "High" bar of "unauthenticated read of stack state" in effect: an attacker who obtains one legitimately-issued, narrowly-scoped `read:stack` CCMenu token (e.g., leaked from a CI status badge/URL, which is explicitly designed to be embedded in third-party continuous integration dashboards) can enumerate and read the deploy status of every stack in the Shipit instance, not just the one it was issued for. This defeats the stack-scoping authorization model that the rest of the API (e.g. `StacksController`) relies on and is a direct escalation of a token's authorized scope.

### Likelihood Explanation
Likelihood is high for anyone already holding a CCMenu token: no additional secret or session is required, only changing the `stack_id` query parameter of an otherwise valid, low-privilege request. CCMenu URLs are designed to be shared with external CI tooling, increasing the chance such tokens circulate outside the trusted operator set.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited scoped lookup, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that stack-scoped `ApiClient` tokens can only ever resolve to the stack they were issued for, consistent with `Api::StacksController`.

### Proof of Concept
1. As a legitimate user, visit `CCMenuUrlController#fetch` for Stack A; this creates/reuses an `ApiClient` named "CCMenu Client" scoped to `stack: A` with `permissions: [read:stack]`, and returns a URL containing `token=<A's token>` [7](#0-6) .
2. An attacker who obtains this token (from a shared badge URL, CI config, etc.) sends `GET /api/stacks/:B/ccmenu.xml?token=<A's token>` where `B` is any other stack in the instance.
3. `authenticate_api_client` in `CCMenuController` authenticates successfully using `ApiClient.authenticate(params[:token])`, yielding `current_api_client` scoped to stack A [8](#0-7) .
4. `require_permission :read, :stack` passes because the token does carry `read:stack`, regardless of which stack.
5. `#show` calls `stack` which resolves `Stack.from_param!(params[:stack_id])` = stack B directly, bypassing the `current_api_client.stack_id` check, and renders stack B's build/deploy status to the attacker [9](#0-8) .
