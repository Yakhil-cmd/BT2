### Title
Malicious swap route can drain a caller's wallet by riding on their authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller's routed strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) and the router's `execute_strategy` accept user-supplied route bytes that name arbitrary pool/venue contracts. A route can name an attacker-deployed "pool" that, during the hop call, invokes `token.transfer(victim, attacker, amount)` on any token. Because the victim's `require_auth` frame is still on the stack, that transfer is recorded as a child of the victim's own authorization entry. If the victim signs the simulated authorization tree (the default wallet flow), the transfer executes and the attacker receives funds that were never part of the swap — a direct analog of the `DepositStableCoinToDealer` arbitrary `swapTarget`/`data` theft.

### Finding Description
`swap_collateral` pulls collateral and hands the raw `swap` bytes to the router without restricting which contracts the route invokes (`contracts/controller/src/strategies/swap_collateral.rs:55-65`, `interfaces/controller/src/lib.rs:98-106`). The router calls whatever pool addresses the payload names and keeps no venue allowlist; its own balance-delta measurement (`RouterOverspend`/`NoSwapOutput`) only bounds what the *controller* loses, not what code inside a hop does under the caller's auth frame.

The repository's own test proves the primitive end to end: in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, a `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, amount)` for a token the protocol never listed. Recording mode (i.e., `simulateTransaction`) attaches that transfer as a sub-invocation under Alice's `swap_collateral` auth entry, the swap succeeds, and Alice's wallet balance of the unrelated token goes to zero while the attacker receives it. The enforced-auth test confirms the theft executes whenever the signed tree includes that child, which is exactly the tree simulation returns to the wallet.

The threat model acknowledges this exposure: a route "can put third-party code on the call stack below the caller's authorization," the loss "is then the caller's wallet, not the routed amount," and the only defense is that "a client must decode the route it signs and refuse an authorization tree with any other child" — i.e., safety depends on off-chain client behavior, not on the contracts (`docs/explanation/threat-model.md:154-165`). There is no venue allowlist, no check that the signed tree contains only the expected input transfer, and no on-chain bound on hop calldata targets.

### Impact Explanation
Any user of `execute_strategy` directly, or of controller routed strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`), who signs a transaction built from an attacker-supplied route can have their entire balance of *any* token in their wallet stolen — not just the routed amount and not just protocol-listed assets. Theft of user funds; severity High.

### Likelihood Explanation
Requires the victim to submit a transaction built from an attacker-influenced route (e.g., a poisoned quote/UI or a malicious counterparty-provided `swap` argument) and to sign the simulation-produced auth tree without auditing sub-invocations — the default signing flow for Soroban wallets. Unprivileged: the attacker only needs to deploy a rogue contract and get the route bytes to the victim. Constrained by requiring a signed poisoned tree rather than a standing allowance, so below the EVM original's triviality, but no on-chain mitigation exists.

### Recommendation
- Maintain an allowlist of permitted venue/pool contracts in the router (or pin venue adapters to registered pools), so route bytes cannot direct calls to arbitrary contracts.
- Alternatively/additionally, have the controller and router invoke hops such that user authorization cannot flow beneath them (e.g., require the router to pull input under its own invoker auth before dispatching hops — already done for venue pulls — and reject any route that would request additional caller authorization).
- Document/enforce in the controller that a signed strategy transaction's auth tree must contain exactly the input-token `transfer` child and nothing else, and surface this check in the SDK verification helpers.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Attacker deploys `RogueHopPool` whose `swap()` executes `token.transfer(alice, attacker, WALLET_BALANCE)` on an arbitrary token (`RogueHopPool::swap`, lines 62-72).
2. A `RoutedSwap` payload naming that pool is passed as `swap` bytes to `swap_collateral(alice, account_id, usdc, amount, eth, route)` (lines 111-125, 147-164).
3. In recording mode the rogue transfer is attached under Alice's `swap_collateral` auth entry and the call succeeds: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE` (lines 194-227).
4. In enforcing mode, signing the simulation-returned tree (with the stolen-transfer child) executes the theft; signing the honest tree reverts — confirming the only barrier is client-side tree inspection (lines 229-269).
