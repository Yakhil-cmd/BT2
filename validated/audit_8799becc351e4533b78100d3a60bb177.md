### Title
Storage-stake check ignores `pending.paid_from_balance`, allowing pending-queue transactions to pass with insufficient reserved balance - (File: `runtime/runtime/src/verifier.rs`)

### Summary
`runtime/runtime/src/verifier.rs` maintains a `PendingConstraints` value that tracks balance already reserved by other transactions queued for the same account in the same chunk (`pending.paid_from_balance`), analogous to the FIVA report's `storage::sy_locked`/`storage::pt_locked`. The `NotEnoughBalance`/`NotEnoughBalanceForDeposit` checks correctly subtract this reserved amount before validating a transaction, but the subsequent `check_storage_stake` call — in both the regular and gas-key transaction verification paths — is invoked with a balance computed from the *full* `account.amount()` minus only the current transaction's cost, without also subtracting `pending.paid_from_balance`. This is the same class of bug as the report: one validation path in the same code region correctly accounts for "reserved/locked" balance while a sibling validation path does not, producing an inflated available-balance figure for the storage check.

### Finding Description
In `verify_and_charge_tx_ephemeral`, the primary balance check correctly nets out pending reservations: [1](#0-0) 

But the value passed into `check_storage_stake` right after is derived from `account.amount()` directly, not from `available_balance`: [2](#0-1) 

The same pattern repeats in the gas-key transaction path: the deposit-balance check nets out `pending.paid_from_balance`, [3](#0-2) 

yet `check_storage_stake` is again called with `new_account_amount`, which was derived from the raw `account.amount()` rather than from `available_balance`: [4](#0-3) 

`check_storage_stake` itself only compares `account_balance + account.locked()` against the storage requirement — it has no notion of `pending.paid_from_balance` at all: [5](#0-4) 

Consequently, when multiple transactions from the same account are queued/pending in the same chunk (the `PendingConstraints`/pending-transaction-queue mechanism in `chain/client/src/pending_transaction_queue.rs` and `chain/client/src/rpc_handler.rs`), the storage-stake sufficiency check for a later transaction is evaluated against a balance that pretends the earlier pending transactions' reservations don't exist. This mirrors exactly the FIVA defect: the "total supply" check (`account.amount()`) is used where the "available" check (`account.amount() - locked/pending`) should be used.

### Impact Explanation
If the storage-stake check passes using the inflated (un-netted) balance while the true available balance (after other pending transactions are applied) would have been insufficient, an account could be validated as able to cover storage staking for multiple concurrently pending transactions when it actually cannot. Depending on how these `TxVerdict`s are later reconciled against actual chunk execution, this can lead to a mismatch between the verifier's ephemeral/pending acceptance and true state after all pending debits are applied — i.e., the same "accounting says one thing, actual balances say another" divergence described in the report, potentially causing failed/rejected receipts, wasted gas, or acceptance of transactions that will fail storage-stake enforcement once fully applied.

### Likelihood Explanation
The `PendingConstraints`/pending-transaction-queue feature only has effect when `pending.paid_from_balance` is non-zero, which happens in the RPC/chunk-production pending-queue path (not on the strict consensus/apply path, where `pending` is default/zero per the code comments). Triggering it requires an account to have multiple transactions queued/pending simultaneously in the mempool/pending-queue such that combined costs approach the account's storage-stake threshold — a state reachable by any ordinary account submitting several transactions in quick succession, not requiring any privileged access.

### Recommendation
- **Short term**: In both `verify_and_charge_tx_ephemeral` and `verify_and_charge_gas_key_tx_ephemeral`, compute the balance passed to `check_storage_stake` from `available_balance` (i.e., netting out `pending.paid_from_balance`) minus the current transaction's cost, consistent with how the `NotEnoughBalance`/`NotEnoughBalanceForDeposit` checks are computed, instead of using `account.amount()` directly.
- **Long term**: Add integration tests in `chain/client/src/pending_transaction_queue.rs` / `test-loop-tests/src/tests/pending_transaction_queue.rs` that submit multiple pending transactions from the same account near the storage-stake threshold to ensure the storage-stake check is evaluated consistently with the reserved/pending balance across all verification paths.

### Proof of Concept
Not independently executed; reasoning is based on static code review of `runtime/runtime/src/verifier.rs`. A concrete PoC would: (1) create an account near the storage-stake balance threshold, (2) submit two transactions in the same chunk/pending window from that account, the first of which is queued (setting `pending.paid_from_balance` for the second), and (3) show the second transaction's `check_storage_stake` call passes because it is checked against `account.amount() - tx_cost` rather than `available_balance - tx_cost`, even though the true remaining balance after both transactions apply would fail the storage-stake requirement.

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
}
