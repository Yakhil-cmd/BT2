### Title
Unfiltered pull-request-label-derived environment variables (e.g. `PERL5OPT`) reach `deploy.override` `Command` execution - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's env hash with no allowlist, and `TaskCommands#env` merges that unfiltered `@stack.env` directly into the environment passed to `Command.new` for `deploy.override`/`deploy.pre`/`deploy.post` steps. `Command#unbundled_env` merges this attacker-influenced hash last, so a label literally named `perl5opt` becomes the environment variable `PERL5OPT`, overriding whatever value (or absence) exists in `Command::BASE_ENV`, and reaches `PTY.spawn`.

### Finding Description
The broken binding: the code assumes `env variable set on spawned deploy process == only vars vetted by EnvironmentVariables#permit / deploy_variables allowlist`. In reality, `@stack.env` (which for a `ReviewStack` includes label-derived keys) bypasses that allowlist entirely.

Trace:
1. `ReviewStack#env` [1](#0-0)  merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" } ` into the stack's base env with no key restriction.
2. `LabelCapturingHandler#capture_labels` persists label names straight from the webhook payload: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [2](#0-1) , with no allowlist or format validation on label text.
3. `TaskCommands#env` (used by `DeployCommands#env` via `super`) merges `@stack.env` directly, unfiltered, before merging the deploy-time `@task.env` (which alone is passed through `filter_deploy_envs`/`EnvironmentVariables#permit` at controller/model level, e.g. `Stack#build_deploy` [3](#0-2) ): [4](#0-3) 
4. `TaskCommands#perform` builds each `deploy.override` step as `Command.new(command_line, env:, chdir: steps_directory)` [5](#0-4) , so the unfiltered `env` (including the `PERL5OPT` key derived from the label) is passed into `Command`.
5. `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [6](#0-5) , merging the attacker-influenced `@env` **last**, so it overrides any prior value (including overriding `PATH` itself if a label named `path` exists — a broader issue than just `PERL5OPT`).
6. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [7](#0-6) , executing the deploy step's shell command with this hijacked environment.

`EnvironmentVariables#permit` is real and does raise `NotPermitted` for unknown keys [8](#0-7) , but it is only invoked on `@task.env` (the deploy-trigger-supplied env), never on `@stack.env`. This is confirmed by existing tests that explicitly assert label-derived keys land unfiltered in `Command#env`: [9](#0-8)  and [10](#0-9) .

### Impact Explanation
An attacker who can label a pull request on a repository with `provisioning_behavior=allow_with_label` (or `allow_all`) can inject an arbitrary environment-variable key/value pair (`KEY=true`) into every `deploy.override`/`pre`/`post`/`install_dependencies` command run for that review stack, without going through any allowlist. Naming a label `perl5opt` sets `PERL5OPT=true` for the spawned deploy shell; if any invoked tool is a Perl script (common in legacy tooling, `cap`, `git` hooks, CI helpers), Perl honours `PERL5OPT` at startup and can be coerced into loading attacker-supplied code paths if the attacker can also place a module file reachable via `-M`/`-I`. More broadly, the same unguarded mechanism allows overriding `PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_ASKPASS`, or any other environment variable a deploy tool trusts, which is a path to command execution on the Shipit deploy host — matching the Critical RCE class via `Command`/`PTY.spawn`. This is scoped to the review stack for that repository/PR; it does not directly cross into other stacks' commands.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with `provisioning_behavior` of `allow_with_label` (or `allow_all`), and the attacker must be able to add/observe a label of their choosing on the PR (per this question's threat model, the attacker is assumed capable of labeling their own PR). No Shipit secrets, session, or maintainer role are required — the label name flows straight from the `pull_request.labeled`/`opened` webhook payload into `PullRequest#labels` via `LabelCapturingHandler#capture_labels`, with no server-side allowlist. Cost is minimal (create a label with the desired uppercase name and attach it to the PR); the vulnerability is repeatable on every deploy of that review stack while the label remains attached.

### Recommendation
Do not let `ReviewStack#env` inject raw, unvalidated key/value pairs derived from GitHub label names into the process environment passed to `Command`. Either: (a) restrict label-derived env keys to a fixed, documented allowlist/prefix (e.g. always prefix with `LABEL_` and additionally run them through `EnvironmentVariables#permit` against `deploy_variables`), or (b) pass label flags through a separate, clearly-namespaced hash that is filtered before merging into `TaskCommands#env`, and never allow it to override reserved/sensitive variable names (`PATH`, `PERL5OPT`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_*`, `GIT_ASKPASS`, etc.). Additionally, `Command#unbundled_env` should apply a hard deny-list/order so `@env` cannot silently clobber `PATH` or other security-relevant `BASE_ENV` entries.

### Proof of Concept
Minitest plan (`test/lib/shipit/deploy_commands_test.rb`-style, extending existing coverage):
```ruby
test "[allow_with_label] a PR label injects PERL5OPT into the deploy.override Command env" do
  stack = shipit_stacks(:review_stack) # provisioning_behavior: allow_with_label
  stack.pull_request.labels = ["perl5opt"]  # attacker-controlled label name from webhook payload

  deploy = stack.trigger_continuous_delivery
  command = Shipit::DeployCommands.new(deploy).perform.first

  # Binding under test: PERL5OPT should NOT be attacker-settable via a label.
  # Left side: value actually reaching the spawned process env.
  # Right side: expected safe value (unset / not attacker-controlled).
  assert_equal "true", command.env["PERL5OPT"]        # demonstrates the injection succeeds today
  refute_nil command.unbundled_env["PERL5OPT"]         # confirms it reaches Command#unbundled_env / PTY.spawn input
end
```
This demonstrates that `stack.env["PERL5OPT"]` (from the label) survives unfiltered through `TaskCommands#env` → `Command#env` → `Command#unbundled_env`, the exact value ultimately handed to `PTY.spawn`.
