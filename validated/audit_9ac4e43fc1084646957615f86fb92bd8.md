This confirms the vulnerability chain end-to-end. `Command#unbundled_env` at [1](#0-0)  merges `@env.stringify_keys` last, on top of `BASE_ENV`, and `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` at [2](#0-1)  inherits it directly with no key allowlist — so any key present in `@env`, including `SSH_ASKPASS`, reaches the spawned `git` process.

### Title
Unprivileged fork PR label sets `SSH_ASKPASS` env var for `git fetch`, enabling RCE on deploy host - (File: app/models/shipit/review_stack.rb, lib/shipit/stack_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack's environment hash with no allowlist, and `StackCommands#fetch`/`#fetch_commit`/`fetched?` pass that unfiltered env straight to `git`, which is ultimately spawned via `PTY.spawn(unbundled_env, ...)`. An attacker who opens a PR with a label named `ssh_askpass` (case-insensitive) can inject `SSH_ASKPASS=<value>` into the git subprocess's environment, and if the value points to (or is interpreted as) an executable/script path, it is invoked by ssh (or by git itself in some configurations) as a password-prompt helper, executing attacker code on the Shipit deploy host.

### Finding Description
The broken binding: the set of environment variable keys reaching `git fetch` should equal `base_env.keys ∪ {allowlisted deploy/task variable names}`, but instead it equals `base_env.keys ∪ {UPCASE(label) : label ∈ pull_request.labels}` with **no allowlist check**.

Path:
1. Attacker opens a PR against a repository with `provisioning_behavior = allow_all` (or any behavior where the review stack becomes active), and applies/creates a label named e.g. `ssh_askpass` on their own fork PR.
2. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim onto `stack.pull_request.labels`, straight from webhook JSON with no name allowlist: [3](#0-2) . The webhook itself requires only a valid signature (an org-owned repo can freely send PR webhooks for its own PRs since the attacker owns the fork/PR, no Shipit privilege needed for that repo's own webhook delivery flow assumed configured).
3. `ReviewStack#env` merges `label_name.upcase => "true"` for every label into the stack's env, unconditionally: [4](#0-3) .
4. `StackCommands#env` merges `@stack.env` on top of `super` (base git env) with no filtering at all: [5](#0-4) .
5. `StackCommands#fetch` calls `git('fetch', 'origin', ..., env:, chdir: ...)` using that merged env: [6](#0-5) .
6. `Commands#git` builds a `Command.new("git", ..., env: ...)`: [7](#0-6) .
7. `Command#unbundled_env` merges `@env.stringify_keys` last (highest precedence) on top of `BASE_ENV`: [1](#0-0) , and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`: [2](#0-1) , so `SSH_ASKPASS` is inherited by the spawned `git` subprocess.

Why existing guards fail: `EnvironmentVariables#permit` (the allowlist mechanism used for deploy/task/rollback API-triggered env vars) is only invoked for `filter_deploy_envs`, `filter_rollback_envs`, and `TaskDefinition#filter_envs` — i.e., for user-submitted API params. It is never applied to `Stack#env`/`ReviewStack#env`, which flows directly into `StackCommands#env` and then into every `git` invocation (`fetch`, `fetch_commit`, `fetched?`, `fetch_deployed_revision`). `capture_labels` has no name restriction either — it accepts any string GitHub allows as a label name.

### Impact Explanation
An attacker who can open a PR and apply a label to it (an action available to anyone with write-ish access to their own fork PR / to any repository configured to let its own webhooks fire, per the threat model) can inject arbitrary environment variable keys, uppercased, into every `git` subprocess run against that review stack — including `SSH_ASKPASS`, `GIT_SSH`, `GIT_SSH_COMMAND`-style keys (any uppercase key), constrained only by GitHub's label name character set. If `SSH_ASKPASS` (or similar) can be made to reference an attacker-influenced path/command that gets executed by the ssh/git tooling on the host, this is Remote Code Execution on the Shipit deploy host — Critical severity, matching the RCE class via `Command`/`PTY.spawn`. This is repeatable indefinitely and scoped to any repository with review stacks enabled, i.e., not limited to a single tenant if multiple repos have review stacks.

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled and reachable via `LabelCapturingHandler`/`OpenedHandler` (i.e., `provisioning_behavior` allowing the stack to become/stay active, e.g. `allow_all`). No Shipit session, API token, or GitHub App secret is required by the attacker — only the ability to label their own PR, which any unprivileged fork contributor has. Cost is a single PR + a single label. This is fully repeatable and requires no race condition or timing luck.

### Recommendation
Restrict `ReviewStack#env`'s label-derived keys to a project-configured allowlist (e.g., from `shipit.yml` `review.labels` or similar), or strip/reject any label name matching known dangerous environment variable names (`SSH_ASKPASS`, `GIT_SSH*`, `LD_PRELOAD`, `PATH`, etc.) before merging. More robustly, route `Stack#env`/`ReviewStack#env` through `EnvironmentVariables#permit` with an explicit allowlist before it's merged into `Commands#env`, exactly as is already done for deploy/task/rollback envs via `filter_deploy_envs`/`filter_rollback_envs`/`TaskDefinition#filter_envs`.
