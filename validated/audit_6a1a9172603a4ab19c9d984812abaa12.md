### Title
Cross-tenant stack mutation via decoupled webhook-signature org and `repository.full_name` lookup - (File: `app/models/shipit/webhooks/handlers/handler.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-org Shipit deployments (`secrets.github` keyed by organization, as in `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects the HMAC secret using `repository.owner.login`, while `Handlers::Handler#stacks` resolves the target `Repository`/stacks using the separate `repository.full_name` field. These two fields are never cross-validated, so a payload signed with one tenant's `webhook_secret` can carry a `full_name` pointing at a completely different tenant's repository.

### Finding Description
The broken binding is: `Shipit.github(organization: repository_owner).webhook_secret` (keyed off `payload.dig('repository','owner','login')`) is implicitly assumed to equal the organization that owns `payload.dig('repository','full_name')` used later for `Repository.from_github_repo_name`. Nothing enforces `full_name.split('/').first == repository.owner.login`.

Code path:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from `params.dig('repository','owner','login')` and verifies the raw body HMAC against `Shipit.github(organization: repository_owner).webhook_secret`.
- `WebhooksController#repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`).
- After signature verification succeeds, `Handlers::Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) independently reads `payload.dig('repository', 'full_name')` and calls `Repository.from_github_repo_name(repository_name)` (`app/models/shipit/repository.rb:53-56`), which parses `owner/name` straight out of that string with no relation to `repository_owner` used for signing.
- `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) both consume `stacks` and mutate/act on whatever `Stack` rows belong to the `Repository` resolved from `full_name`.

Attacker's exact request: an attacker who is the legitimate admin of GitHub org "AttackerOrg" — a real Shipit tenant configured with its own `webhook_secret` in `secrets.github["attackerorg"]` — knows/controls that org's webhook secret (they configured it themselves as part of onboarding their own org's webhook integration, per the documented multi-org config schema). They craft a raw JSON body where `repository.owner.login = "AttackerOrg"` (so `verify_signature` computes a valid HMAC using AttackerOrg's secret) but `repository.full_name = "VictimOrg/victim-repo"` (a different tenant's registered `Repository`). They sign the body with AttackerOrg's `webhook_secret` and POST it to `/webhooks` with `X-Github-Event: push` (or `check_suite`).

`verify_signature` passes because the signature matches AttackerOrg's secret and the raw body. `drop_unhandled_event`/`ExplicitParameters` schema checks only validate types, not that `full_name`'s owner segment matches `repository.owner.login`. `stacks` then resolves `VictimOrg/victim-repo`'s actual `Stack` rows, and `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA, or `CheckSuiteHandler` schedules check-run refreshes for attacker-chosen `head_sha`/`head_branch` against VictimOrg's stacks — none of which required any credential belonging to VictimOrg.

### Impact Explanation
A payload validly signed by tenant A's own webhook secret can mutate tenant B's `Stack` state (queueing `GithubSyncJob` with an attacker-controlled `expected_head_sha`, or scheduling check-run refresh jobs) despite zero authentication from tenant B. This is a cross-tenant authorization bypass matching the "payload for one repository mutating another's stack" critical impact category. It is repeatable against any repository/stack pair as long as the attacker knows any org's configured webhook secret (their own, in a multi-tenant install) and any target `Repository.full_name` string (which is guessable/public, since it's just `owner/repo`). Blast radius spans every tenant Repository configured on a shared Shipit instance.

### Likelihood Explanation
Requires a multi-org Shipit deployment (`secrets.github` keyed by organization, each with independent `webhook_secret`) — a configuration explicitly supported and documented in this repo (`test/dummy/config/secrets_double_github_app.yml`). The attacker only needs to be a legitimate but malicious tenant admin of their own onboarded org (not a Shipit operator, not a GitHub org admin of the victim, no session/API token needed) — well within the defined "unprivileged attacker" envelope since owning one's own org's webhook secret is a normal part of onboarding, not a privileged Shipit role. Cost is a single crafted HTTP POST.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handlers::Handler`), enforce that the organization segment of `repository.full_name` matches `repository.owner.login` (the value used to select the signing secret) before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push payload signed by OrgOne cannot mutate OrgTwo's stack via mismatched full_name" do
  # Precondition: multi-org secrets like secrets_double_github_app.yml, OrgOne webhook_secret known to attacker.
  victim_repo = shipit_repositories(:shipit) # owner: "shopify", name: "shipit-engine"
  victim_stack = shipit_stacks(:shipit)

  body = JSON.parse(payload(:push_master))
  body["repository"]["owner"]["login"] = "OrgOne"          # attacker's own org
  body["repository"]["full_name"] = victim_repo.full_name  # "shopify/shipit-engine", victim's repo

  raw = body.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", Shipit.github(organization: "OrgOne").webhook_secret, raw)

  request.headers["X-Github-Event"] = "push"
  request.headers["X-Hub-Signature"] = signature

  # EQUALITY UNDER TEST:
  # repository_owner ("OrgOne")  ==  full_name.split("/").first ("shopify")  ?  -> false
  assert_not_equal body.dig("repository", "owner", "login"),
                    body.dig("repository", "full_name").split("/").first

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: body["after"]]) do
    post :create, body: raw, as: :json
  end
  assert_response :ok # currently succeeds — should instead be :unprocessable_entity
end
```
This demonstrates the signature-selecting org (`OrgOne`) diverging from the stack-resolving org (`shopify`) while the request is still accepted and the victim's stack is mutated.
