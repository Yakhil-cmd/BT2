## Title
Webhook organization identity used for signature verification is never bound to the repository the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate an inbound webhook against using `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')` (falling back to `payload.dig('organization', 'login')`). [1](#0-0) [2](#0-1) 

Every event handler, however, resolves the *target* repository/stack from a completely different field of the same JSON body: `payload.dig('repository', 'full_name')` (base `Handler#repository_name`/`#stacks`), and `StatusHandler` doesn't even scope by repository at all - it matches on commit SHA globally. [3](#0-2) [4](#0-3) 

Shipit is explicitly designed to host multiple independent GitHub Apps/organizations, each with its own `webhook_secret`. [5](#0-4)  `GithubApp#verify_webhook_signature` only checks the HMAC against the secret picked for the `organization` argument passed in - it has no notion of which repository the payload targets. [6](#0-5) 

### Finding Description
The trust binding that should hold is: **organization authenticated (secret used to verify `X-Hub-Signature`) == organization owning the repository the handler writes to**. Nothing enforces this equality - `repository.owner.login` (used for org/secret selection) and `repository.full_name` / bare commit `sha` (used for the actual write) are independent, attacker-controlled fields inside the very payload whose *contents* are signed, but whose *internal consistency* is never checked.

Concretely, someone who legitimately administers a GitHub App/org "A" on this Shipit instance (and therefore knows `webhook_secret_A`) can POST directly to `/github/webhooks` with a body where:
- `repository.owner.login = "A"` (or `organization.login = "A"`) - so `verify_signature` looks up and verifies against `webhook_secret_A`, which they can correctly compute since it's their own secret,
- `repository.full_name = "B/victim-repo"` (or, for `status` events, simply a `sha` matching a commit that exists in org B's stack) - so the handler acts on org B's data.

This breaks the equality "organization that authenticated == repository that is written," letting an org-A-scoped operator reach into org B's stacks:
- `PushHandler` will enqueue `GithubSyncJob` for org B's stack with an attacker-chosen `expected_head_sha`, forcing an unscheduled sync/deploy trigger on a stack outside the attacker's organization. [7](#0-6) 
- `CheckSuiteHandler` will schedule check-run refreshes for org B's commits. [8](#0-7) 
- `StatusHandler` is worse: it has **no repository scoping whatsoever** - `Commit.where(sha: params.sha)` matches any commit in the entire Shipit installation with that SHA, across all organizations/stacks, and calls `create_status_from_github!(params)` on it. [4](#0-3)  An org-A operator can forge a `success` CI status (any `context`, `description`, `target_url`) for a commit SHA belonging to org B, satisfying `ci.require` gating and merge-queue checks for a stack they don't control.
- `PullRequest::OpenedHandler`/`LabeledHandler`/etc. similarly resolve `repository` via `params.repository.full_name`, letting an org-A-authenticated payload provision/archive/unarchive review stacks belonging to org B. [9](#0-8) 

### Impact Explanation
This crosses an organization boundary that the multi-tenant GitHub App configuration is meant to enforce: [10](#0-9)  possession of one organization's webhook secret should never grant the ability to influence another organization's stacks. The most severe path is `StatusHandler`, which can inject a forged, unscoped "success" CI status onto any commit in the system, potentially satisfying `ci.require`/merge-queue gates and enabling an unauthorized merge/deploy of a commit in a repository the attacker has no legitimate relationship to. `PushHandler`/`GithubSyncJob` also let the attacker force out-of-band syncs (and, on stacks with `continuous_deployment: true`, out-of-band deploys) of another organization's stack on demand. This satisfies the "unauthorized deploy/merge" and "cross-repository writes" Critical/High impact categories.

### Likelihood Explanation
Requires only that the attacker be an authenticated administrator/operator of *some* organization already integrated with this Shipit instance (i.e., they legitimately know their own org's `webhook_secret`) - they need no Shipit session, `ApiClient` token, or access to the target organization/repository. The webhook endpoint is unauthenticated apart from the per-org HMAC, and no code anywhere cross-checks `repository.owner.login`/`organization.login` against `repository.full_name` or the commit's actual owning repository.

### Recommendation
- In `Handler#stacks`/`#repository_name`, derive the repository strictly from the same organization identity used for signature verification (`repository.owner.login`/`organization.login`), and reject the payload if `repository.full_name`'s owner segment does not match.
- In `StatusHandler`, scope `Commit.where(sha: params.sha)` to stacks belonging to the verified organization (via `repository_name`) instead of a global, cross-tenant lookup.
- Alternatively, pass the verified organization through to each handler and have every repository/stack lookup filter by it, rather than trusting unrelated payload fields.

### Proof of Concept
1. Shipit is configured (per `config/secrets.development.example.yml`) with two GitHub Apps: org "A" (`webhook_secret_A`, known to its own admin) and org "B" (victim), each with stacks in Shipit.
2. The org-A admin computes `sha256=<hmac>` of a crafted JSON body using `webhook_secret_A`:
```json
{
  "sha": "<sha of a real commit belonging to org B's stack>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z",
  "repository": { "owner": { "login": "A" } }
}
```
3. POST to `/github/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "A")` and verifies successfully with `webhook_secret_A`. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching org B's commit regardless of the "A" identity used to authenticate — and records a forged `success` status on it. [4](#0-3) 
6. This forged status can satisfy `ci.require` for org B's stack, enabling merge-queue progression/deploy eligibility the attacker was never authorized to influence.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
