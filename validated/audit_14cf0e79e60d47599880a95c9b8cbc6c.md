### Title
`StatusHandler#process` resolves commits by SHA alone, letting a webhook authenticated for one repository write Statuses onto another Stack's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Status.replicate_from_github!(stack_id, github_status)` performs no ownership check on `stack_id` [1](#0-0) , and its only caller, `Commit#create_status_from_github!`, passes `commit.stack_id`, which is simply whatever the matched `Commit` row already belongs to [2](#0-1) . The real gap is one level up: `StatusHandler#process` selects candidate commits with `Commit.where(sha: params.sha)` — a global, cross-tenant query that never scopes to the repository that actually authenticated the webhook [3](#0-2) .

### Finding Description
Broken binding: `stack_id passed into replicate_from_github! == stack.id resolvable from Repository.from_github_repo_name(payload.repository.full_name).stacks` (the `stacks` helper the base `Handler` class exposes precisely for this purpose) [4](#0-3) . `StatusHandler#process` never calls `stacks` at all; it instead does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , which matches **every** `Commit` row across **every** `Stack` sharing that SHA, regardless of which repository's webhook fired.

`WebhooksController#verify_signature` only proves the payload was genuinely signed by GitHub for the organization named in `payload['repository']['owner']['login']` — i.e. it authenticates *which repository sent this event*, not *which commits the event may touch* [5](#0-4) . Nothing downstream re-derives the caller's repository/stack from that authenticated context before touching `Commit`/`Status` rows.

Exploit flow:
1. Attacker owns/controls Stack A in Shipit (a legitimate repository they administer, with a real GitHub webhook configured to Shipit).
2. Attacker crafts a git commit object with identical content (tree, parent SHA, author/committer, timestamps, message) to a commit that already exists in victim Stack B — feasible with plumbing commands (`git commit-tree`) against a publicly visible victim commit, producing an identical SHA-1 without needing write access to the victim's repo.
3. Attacker pushes this commit to a branch on their own repository and triggers/relays a `status` event (e.g., via their own CI) for that SHA. GitHub signs and delivers this webhook; `verify_signature` passes because it is a real event for the attacker's own org/repo.
4. `StatusHandler#process` finds `Commit.where(sha: <colliding sha>)`, which returns both the attacker's Stack A row and the victim's Stack B row.
5. For the Stack B commit, `commit.create_status_from_github!(params)` calls `statuses.replicate_from_github!(commit.stack_id, github_status)` — `commit.stack_id` is Stack B's id, entirely attacker-controlled by choice of `state`/`description`/`target_url`/`context` in the forged status payload, and Stack A's identity is never checked against Stack B.

Existing guards do not prevent this: `verify_signature` only authenticates the sender's own organization/repo [6](#0-5) ; the `ExplicitParameters` schema only validates payload shape [7](#0-6) ; and the `stacks` scoping helper that exists for exactly this purpose is simply not used by `StatusHandler` [4](#0-3) .

### Impact Explanation
A `status` webhook that GitHub genuinely signed for the attacker's own repository can create a `Status` record (state `success`/`failure`/`error`, attacker-chosen `description`/`target_url`/`context`) on a commit belonging to an unrelated victim `Stack` [1](#0-0) . Because `Commit#add_status` re-evaluates `deployable?`/`schedule_continuous_delivery` and can enqueue `ContinuousDeliveryJob` on state transitions [8](#0-7) , injecting a fabricated `success` status can push a victim commit into a "deployable" state and trigger continuous deployment/merge scheduling the attacker does not control and never authenticated for. This is a cross-tenant write ("payload for one repository mutating another's stack/commit/task") and can lead to an unauthorized deploy — matching the Critical severity bucket.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own Stack/repository already integrated with Shipit (trivial, self-service), and (b) the ability to produce a git commit whose SHA-1 collides with a specific victim commit — achievable deterministically by reproducing identical tree/parent/author/committer/message metadata for any publicly-visible victim commit, using standard git plumbing, no private secrets required. No Shipit session, API token, or `Shipit.github_teams` membership is needed. The attack is repeatable against any victim Stack/commit whose metadata is public, at low cost per attempt.

### Recommendation
Scope `StatusHandler#process` (and analogous handlers) to only touch commits belonging to stacks resolvable from the authenticated webhook's repository, e.g. `Commit.where(sha: params.sha, stack: stacks)` using the existing `stacks` helper, or otherwise verify `commit.stack.repository == Repository.from_github_repo_name(repository_name)` before calling `create_status_from_github!`. Additionally, `Status.replicate_from_github!` should not blindly trust a passed-in `stack_id`; call sites should always derive it from an already-authorized `Stack`/`Commit` association.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, in scope since it is not under an excluded path — actual file would live under `test/` per repo convention, but conceptually):
```ruby
test "status webhook authenticated for repo A must not write a Status on a commit belonging to Stack B" do
  stack_a = shipit_stacks(:shipit) # repo A, attacker-owned
  stack_b = create_stack!(repository: create_repository!(full_name: "victim/repo"))
  colliding_sha = "a" * 40

  create_commit!(stack: stack_a, sha: colliding_sha)
  victim_commit = create_commit!(stack: stack_b, sha: colliding_sha)

  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }

  # binding under test: stack_id passed to replicate_from_github! must equal
  # Repository.from_github_repo_name(payload['repository']['full_name'])&.stacks&.pluck(:id)
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_empty victim_commit.reload.statuses,
    "Status must not be created on victim Stack B from a webhook authenticated only for Stack A's repository"
end
```
This test fails against current code because `StatusHandler#process` matches `victim_commit` via the global `Commit.where(sha:)` lookup and writes a `Status` row under `stack_b.id` with no repository cross-check.
