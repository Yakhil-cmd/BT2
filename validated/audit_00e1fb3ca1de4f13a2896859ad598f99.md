### Title
Front-running of AMM-style AA deposit calculations can imbalance/grief investor positions - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The bug class described in the Perennial report — an unprivileged actor front-running a state-dependent operation (`makerLimit`) to force a victim's subsequent transaction into an unfavorable, unbalanced position — has a direct analog in Obyte's Autonomous Agent (AA) execution model. AAs read shared, mutable state (balances, state vars) at the time their trigger is processed rather than at the time the trigger unit is composed, and trigger units are ordered by DAG/MCI stability rather than submission order. Any unprivileged unit poster can therefore submit a trigger that gets sequenced immediately before a victim's trigger and mutate the balance/ratio the victim's calculation depends on.

### Finding Description
`handleTrigger` in `aa_composer.js` processes each primary AA trigger using the AA's live balances and state vars read from the database/kv-store at execution time (`updateInitialAABalances`, ordered by main-chain-index stability), not by any value fixed when the user composed and broadcast their unit. [1](#0-0) 

The `uniswap_like_market_maker.oscript` sample AA (a documented, shipped reference pattern for building constant-ratio market-maker/vault-style AAs on ocore) computes the amount of shares to issue to a depositor purely from the AA's current on-chain balances at execution time:
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
...
$current_ratio = $asset_balance / $bytes_balance;
$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
if ($expected_asset_amount != trigger.output[[asset=$asset]])
    bounce('wrong ratio of amounts, expected ' || $expected_asset_amount || ' of asset');
``` [2](#0-1) 

Because `balance[$asset]`/`balance[base]` are evaluated using `readBalance` against the live `aa_balances` table/`objValidationState.assocBalances` at the moment the trigger is actually processed (which is determined by unit stability order in the DAG, something any user's own unit can influence relative to another pending unit), any unprivileged party can post their own payment/trigger to the same AA address that changes this ratio and gets ordered ahead of a victim's deposit trigger. [3](#0-2) 

This mirrors the reported `BalancedVault` bug exactly: the vault (or AMM AA) commits to "the biggest/whatever position is currently available" at execution time, and a griefer can manipulate that state immediately beforehand so that the honest depositor's payment either bounces (denial of service via the `bounce('wrong ratio...')` path) or is executed against a ratio that differs from what the depositor observed when composing their unit, exposing them to loss just like Alice's unintended one-sided exposure in the report.

### Impact Explanation
A user depositing bytes/asset into this class of AA can be forced into: (1) a wasted bounce fee if the front-runner shifts the ratio so the check fails, or (2) an unfavorable price if a griefer manipulates balances of both legs to change `$current_ratio` between the depositor computing their expected deposit off-chain and the trigger actually executing. This directly parallels the "unexpected exposure to one leg of a market" impact in the source report and can be used to grief or extract value from any Obyte AA following this common invest/divest pattern.

### Likelihood Explanation
Likelihood is high: no special privileges are required, the attacker only needs to post an ordinary payment/trigger unit to the same AA address before the victim's unit stabilizes, which is well within reach of any unprivileged unit poster, and the pattern (computing ratios/shares from live `balance[...]` at execution time) is the officially documented approach for building market-maker/vault-style AAs on ocore.

### Recommendation
AA authors building this pattern should have the depositor commit to expected amounts and slippage tolerance in `trigger.data` and have the AA verify the resulting shares/ratio fall within the depositor-specified bounds (analogous to the report's recommendation to cap deposits by a limit computed from validated inputs) rather than unconditionally trusting the live balance ratio at execution time. Where possible, ocore documentation/samples for this pattern should be updated to include an explicit slippage-protection parameter to prevent this classic front-running griefing vector.

### Proof of Concept
1. Victim composes a unit sending `base` and `$asset` to the market-maker AA sized according to the `$current_ratio` observed at broadcast time (per `test/samples/uniswap_like_market_maker.oscript` lines 34-47). [4](#0-3) 
2. Attacker composes and posts their own unit to the same AA (e.g., an "invest" or "divest" trigger) designed to land in an MC-index/DAG position ahead of the victim's trigger, changing `balance[$asset]`/`balance[base]`.
3. When the AA engine processes triggers in stability order (`handlePrimaryAATrigger` → `handleTrigger` → `updateInitialAABalances`), the victim's trigger is evaluated against the now-changed balances, causing `$expected_asset_amount` to differ from what the depositor originally computed, triggering `bounce('wrong ratio of amounts...')` or an unexpected fill ratio. [5](#0-4)
