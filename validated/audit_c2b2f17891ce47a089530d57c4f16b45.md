## Title
AA-issued capped asset can be permanently "already issued"-bricked by front-run issuance from a non-definer address - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `issueAsset()` function assumes that for a capped asset it composes on behalf of an AA, "only our AA can issue" the asset, and treats any pre-existing `issue` input for that asset as fatal ("already issued"), permanently bouncing the AA whenever it later tries to issue the same asset. [1](#0-0) 
This mirrors the reported Beam-auction bug class: a sequential/one-shot mint operation that silently assumes exclusivity of the minter role, but the underlying validation layer does not actually enforce that exclusivity unless the asset is defined with `issued_by_definer_only` restricted to the AA's own address.

### Finding Description
When an AA response message issues a capped asset, `issueAsset()` only checks `objAsset.issued_by_definer_only && address !== objAsset.definer_address` to reject issuance if the caller isn't the definer. [2](#0-1) 
If the asset was defined (by the AA's own `asset` message, or otherwise) with `issued_by_definer_only=false`, then per the consensus validation rules in `validatePaymentInputsAndOutputs`, the double-spend/uniqueness check for `type='issue'` inputs on a capped asset only adds an `address` filter when `!objAsset.issued_by_definer_only`: [3](#0-2) 
This means any address (not just the AA) is permitted to author a valid, standalone `issue` payment message for that asset with `serial_number=1` and `amount === cap`, as required by the general issue-input validation rules. [4](#0-3) 

Once any such foreign issuance unit is accepted and becomes part of a stable/good unit, the AA's own `issueAsset()` logic will forever see:
```
conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
    if (rows.length > 0) // already issued
        return cb2('already issued');
``` [1](#0-0) 
and unconditionally fail/bounce every subsequent trigger that reaches this code path — permanently, since the check has no way to distinguish "issued by us" from "issued by anyone else" (unlike the uncapped branch, which explicitly filters `AND address=?` on the AA's own address). [5](#0-4) 

This is the direct analog of the reported issue: a sequential/one-shot minting flow (there, NFT ID 1; here, the single capped-asset issuance) that can be irrevocably front-run by an unprivileged unit poster, because the framework does not force `issued_by_definer_only` to be scoped to the AA address for capped assets composed via `issueAsset()`.

### Impact Explanation
Any AA that defines/uses a capped asset without setting `issued_by_definer_only=true` restricted to itself is permanently and irrecoverably bricked from ever performing its intended issuance logic once a third party front-runs the single allowed `issue` input. Because `cap` assets require the issuer to supply the entire `cap` amount in one shot, the front-runner also captures the entire token supply for themselves instead of the AA (fund loss / unauthorized appropriation of the intended issuance), and the AA's business logic path that depends on `issueAsset()` succeeding becomes permanently non-functional (denial of service / fund freezing for anyone who was expecting the AA to distribute the asset).

### Likelihood Explanation
Exploitation requires only posting a single ordinary payment unit with an `issue` input for the target asset (`asset`, `serial_number=1`, `amount=cap`) before the AA gets a chance to issue it — something any unprivileged unit poster can do, with no special permissions, as long as the AA developer configured the capped asset with `issued_by_definer_only=false` (or omitted this restriction). This is a plausible, low-cost misconfiguration for AA authors who are not aware that the framework only protects capped-asset issuance exclusivity through this flag+address restriction.

### Recommendation
- In `aa_composer.js`'s `issueAsset()`, for capped assets, verify not just `rows.length > 0` but that the existing issuance was actually made by the AA's own address (or otherwise reject/document that capped assets used by AAs must be created with `issued_by_definer_only=true` and `definer_address` equal to the AA address).
- Enforce, at asset-creation time within an AA (`case 'asset'` handling), that any capped asset an AA intends to self-issue is forced to `issued_by_definer_only=true` with the definer pinned to the AA's own address, closing off the front-run window at the validation layer rather than relying on convention.
- Alternatively, have `issueAsset()` bounce gracefully and retry with adjusted logic (e.g., treat foreign issuance of a capped asset as a permanent, expected terminal condition documented to AA authors) rather than silently assuming "only our AA can issue."

### Proof of Concept
1. An AA is deployed whose `messages` include an `asset` definition message creating asset `X` with `cap: N`, `is_transferrable: true`, and (misconfigured) `issued_by_definer_only` not set to restrict issuance to the AA's own address, and a later `payment` message that relies on `issueAsset()` in `aa_composer.js` to issue asset `X`'s cap to a trigger sender.
2. Before the AA's own response unit that issues asset `X` becomes stable/executes, an unprivileged user posts an ordinary unit with a `payment` message: `{asset: X, inputs: [{type: "issue", amount: N, serial_number: 1}], outputs: [...]}`. This unit passes `validatePaymentInputsAndOutputs`'s issue-input checks because `objAsset.cap` forces `serial_number=1` and `amount === cap`, and the double-spend check does not require the issuer's address to equal the AA's definer address (per the `!objAsset.issued_by_definer_only` condition). [6](#0-5) 
3. This unit is accepted by the network as a valid `issue` input for asset `X`.
4. On the next and all subsequent AA triggers, `issueAsset()`'s query `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` returns a row, so it returns `cb2('already issued')`, permanently failing the AA's response for this code path. [1](#0-0) 
5. The AA can never issue asset `X` again; the front-runner has captured the entire capped supply intended for the AA's use, and the AA's dependent logic is permanently broken.
