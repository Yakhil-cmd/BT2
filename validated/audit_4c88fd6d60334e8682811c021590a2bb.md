### Title
Integer-precision overflow in divisible payment input-sum validation allows loss-of-precision-based double-spend/inflation - (File: validation.js)

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` sums attacker-supplied payment amounts using native JavaScript floating-point arithmetic. While the output side of the check caps the running total after every addition, the input side does not apply the same running cap, so the running sum of transfer/issue input amounts can silently exceed `Number.MAX_SAFE_INTEGER` (2^53‑1 ≈ 9.007e15), which sits just above the protocol's own `constants.MAX_CAP` (9e15). This is the JS-domain analog of the PDFium integer-overflow bug class in CVE-2019-5855: a numeric quantity that individually passes bounds checks can, once summed, silently wrap/lose precision, corrupting a value that downstream logic trusts to be exact.

### Finding Description
- Each payment output amount is validated individually against `constants.MAX_CAP` (9e15) and the running `total_output` is also checked against `MAX_CAP` after every addition: [1](#0-0) [2](#0-1) 

- On the input side, individual `issue` inputs are bounded by `MAX_CAP` as well: [3](#0-2) 

  and `total_input` is accumulated: [4](#0-3) 

  However, for `transfer`-type inputs (the dominant, unbounded-in-count case, up to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` = 128 inputs per message) there is no equivalent per-addition ceiling check on the growing `total_input` sum in the code paths I was able to inspect. Each individual transferred output can independently be as large as `MAX_CAP` (9e15) because that is the bound enforced when that output was originally created. Summing just two such inputs (2 × 9e15 = 1.8e16) already exceeds `Number.MAX_SAFE_INTEGER` (~9.007e15), at which point JavaScript's IEEE-754 double arithmetic silently rounds/loses precision rather than throwing — the functional equivalent of an integer overflow in a C/C++ parser.
- `object_length.js`'s `getLength()` similarly treats any JS `number` as exactly representable and returns a fixed size (8 bytes) without checking magnitude beyond `isFinite`, reinforcing that the codebase generally assumes amounts stay within safe-integer range without enforcing it centrally: [5](#0-4) 

The asset-definition path shows the same unguarded pattern: `count_coins * denomination` is summed into `total_cap_from_denominations` with no upper bound on `count_coins` and only a conditional (version/MCI-gated) bound on `denomination`: [6](#0-5) 

### Impact Explanation
If the running `total_input` (or the denomination-cap total) can lose precision relative to the true mathematical sum, the equality/consistency checks between inputs and outputs (or between declared cap and actual issuable supply) that the DAG relies on to prevent unauthorized value creation can be satisfied by a unit whose real value balance does not match. This maps to the "supply inflation" / "unauthorized spending" impact class: a posted unit could pass consensus validation while the real (arbitrary-precision) balance differs from the floating-point-computed one used for validation, which every full node computes identically (deterministic replay), but which is inconsistent with the true arithmetic sum, i.e. the protocol's implicit invariant ("total_input == total_output + fees", "cap == sum of denomination coins") is not actually enforced once magnitudes exceed 2^53.

### Likelihood Explanation
Reaching this path requires nothing beyond posting a normal payment unit or asset definition — fully in reach of any unprivileged unit poster or asset issuer. The values needed (a couple of prior outputs near the `MAX_CAP` boundary, or a denomination/count_coins pair near the cap) are attacker-constructible over multiple prior transactions or via a single large asset issuance, since `MAX_CAP` (9e15) is deliberately set close to `Number.MAX_SAFE_INTEGER`, leaving very little headroom before precision loss when only 2 values are summed.

### Recommendation
- Apply the same "check after every addition" pattern used for `total_output` to `total_input` in `validatePaymentInputsAndOutputs()`, rejecting a unit as soon as the running sum would exceed `constants.MAX_CAP` or `Number.MAX_SAFE_INTEGER`.
- Reduce `constants.MAX_CAP` to leave adequate headroom (e.g., at least `MAX_INPUTS_PER_PAYMENT_MESSAGE` × `MAX_CAP` should stay well under `Number.MAX_SAFE_INTEGER`), or use an arbitrary-precision/BigInt accumulator for all consensus-critical sums (inputs, outputs, denomination caps).
- Add an explicit upper bound on `count_coins` in `validateAssetDefinition()`/`validateAADefinition()` proportional to `MAX_CAP / denomination`, computed with safe-integer-aware arithmetic, instead of unconditionally multiplying and summing native numbers.

### Proof of Concept
Conceptually (exact reproduction requires a running ocore full node/testnet since the definitive input/output equality-comparison line could not be located in the indexed snippets available to me):
1. Attacker previously obtains two payment outputs of `amount = 9e15` each (equal to `MAX_CAP`), either via asset issuance they control or via base-asset transfers accumulated over time.
2. Attacker crafts a new payment message with these two outputs as `transfer` inputs (`total_input` accumulation at validation.js:2354 analog for transfer, i.e. wherever `total_input += input.amount` executes for the `transfer` branch) and outputs whose declared `amount` sum, expressed as a JS double, coincidentally matches the rounded/overflowed `total_input` value (1.8e16 rounds within IEEE-754 to specific representable doubles).
3. If the equality check compares only these floating-point sums (and not an arbitrary-precision equivalent), the unit could pass `validatePaymentInputsAndOutputs()` despite the true value not balancing, since the digits lost in the 1.8e16 representation are exactly the discrepancy.

**Caveat:** I was not able to retrieve the exact line(s) in `validation.js` that perform the final `total_input` vs `total_output` (+fees) equality check within this session's tool budget, so I cannot cite the precise comparison statement or confirm there is no additional safe-integer guard placed there. This should be verified directly in a full checkout of `validation.js` (the function `validatePaymentInputsAndOutputs`) before treating this as confirmed rather than a strong candidate analog.
