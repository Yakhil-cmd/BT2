### Title
RAY market-value overflow during mandatory interest accrual permanently freezes high-utilization markets - (File: contracts/pool/src/interest.rs)

### Summary
A sufficiently large borrowed or supplied position can make `scaled_amount * index` exceed the `i128` RAY-value domain before the borrow-index cap is reached. Because `accrue_step` computes these values before updating or capping the index, the overflow reverts `global_sync`; every market mutation that first synchronizes the market then reverts permanently.

### Finding Description
`global_sync` splits elapsed time into bounded chunks and calls `accrue_chunk` for each one, only marking the market accrued after the complete loop succeeds [1](#0-0) . Each chunk calls `accrue_step` with the stored scaled supply, debt, and indexes [2](#0-1) .

`accrue_step` first computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` for utilization [3](#0-2) . `scaled_to_original` delegates to `Ray::mul` [4](#0-3) , which computes `scaled * index / RAY` through the checked multiply-divide helper [5](#0-4) . Results that cannot fit in `i128` produce `GenericError::MathOverflow` [6](#0-5) .

The borrow-index ceiling is only applied later inside `update_borrow_index` [7](#0-6) . Therefore, a market whose scaled balance times its index exceeds `i128::MAX` fails during utilization calculation before the configured index bound can stop growth.

The exposed controller path is permissionless after the initial position is created: `update_indexes(caller, assets)` forwards the requested `HubAssetKey`s to the pool [8](#0-7) . Pool mutations load a synchronized market through `synced_market`, which unconditionally calls `global_sync` [9](#0-8) . The controller exposes the affected user paths including `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, and `flash_loan` [10](#0-9) .

### Impact Explanation
Once the boundary is crossed, `last_timestamp` is not advanced because `mark_accrued` occurs only after every chunk completes [11](#0-10) . Any subsequent `update_indexes`, withdrawal, repayment, liquidation, bad-debt cleanup, or other market mutation repeats the same accrual calculation and reverts again.

This permanently freezes supplier cash and borrower collateral in that market and prevents repayment or liquidation of the associated debt. Since even explicit `update_indexes` calls execute the same failing path [12](#0-11) , there is no unprivileged recovery path that can advance the market past the overflow.

### Likelihood Explanation
The attacker must create an unusually large, highly utilized market and allow the borrow index to grow enough that `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`. That requires substantial token liquidity, enough separate collateral to pass the controller’s post-borrow risk checks, and sustained interest accrual.

The condition can be reached through ordinary calls: supply the debt-market asset, supply collateral, borrow most of the debt market, then call `update_indexes` as time advances. No privileged parameter, oracle manipulation, leaked key, malformed token, or external service is required. The capital and duration requirements make exploitation costly, but the resulting market-wide freeze affects all users, so the finding is Medium severity.

### Recommendation
Make the accrual precondition index-aware instead of evaluating total value before the cap. In particular, project and cap the new borrow index before `scaled_to_original` where feasible, or introduce a checked utilization path that detects value overflow and clamps the market to a safe terminal state that still permits repayment, withdrawal, liquidation, and bad-debt processing.

At minimum, add a production guard before `scaled_to_original` that recognizes an unrepresentable market value and handles it deterministically rather than reverting the mandatory accrual preamble. Regression coverage should assert that an oversized high-utilization market remains able to repay, withdraw, liquidate, and clean bad debt when the borrow index approaches its configured cap.

### Proof of Concept
1. An unprivileged attacker calls `Controller::supply(attacker, 0, spoke_id, [(debt_hub_asset, principal)])` with an extremely large principal, creating an account.
2. The same attacker supplies enough collateral through another `supply` call, then calls `borrow(attacker, account_id, [(debt_hub_asset, borrow_amount)], None)` with `borrow_amount` near the available liquidity.
3. As ledger time advances, anyone calls `update_indexes(attacker, [debt_hub_asset])`.
4. When scaled debt or supply times its index exceeds `i128::MAX`, `global_sync` reverts in `accrue_step` during `scaled_to_original`.
5. Because the panic occurs before `mark_accrued`, the stale timestamp is preserved. Subsequent `update_indexes`, `withdraw`, `repay`, `liquidate`, and `clean_bad_debt` calls all re-enter the same overflowing accrual and cannot complete.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();

pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
