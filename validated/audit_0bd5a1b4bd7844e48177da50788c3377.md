### Title
Cross-Organization Commit Status Forgery via Unscoped `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit supports hosting multiple GitHub organizations behind a single instance, each with its own GitHub App and webhook secret [1](#0-0) . Webhook authenticity is verified per-organization: `WebhooksController#verify_signature` selects the GitHub App keyed by the `repository_owner` derived from the incoming payload and checks the HMAC signature against that organization's `webhook_secret` [2](#0-1) . This proves only that the payload's *claimed* organization signed it — it says nothing about which `Commit`/`Stack` the payload is allowed to affect. Every other event handler enforces that binding by scoping to the repository named in the payload via `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`) — e.g. `PushHandler` and `CheckSuiteHandler` [3](#0-2) [4](#0-3) . `StatusHandler`, however, looks up commits globally by SHA with no repository/organization filter at all: [5](#0-4) .

### Finding Description
The equality that should hold is: **organization authenticated by `verify_signature` == organization whose commits are written by the handler**. For `status` events this equality is broken.

- `verify_signature` authenticates only that "some organization X signed this payload," using `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-controlled payload's `repository.owner.login` (fallback `organization.login`) [6](#0-5) .
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — an instance-wide, unscoped lookup across every `Stack`/`Repository` configured in that Shipit installation [5](#0-4) .

Because organization X's own webhook secret is sufficient to pass `verify_signature`, organization X can send a forged `status` webhook whose `sha` value is a commit belonging to a completely different organization Y's stack (also hosted on the same Shipit instance) and have `create_status_from_github!` write an arbitrary state/description/`target_url` onto that commit, as if GitHub itself reported it.

### Impact Explanation
A forged `Status` record directly feeds CI/deploy gating logic: `Commit#deployable?` (`success? && !blocked?`) and `Commit#statuses_and_check_runs` used by `StatusChecker` in the merge queue's `all_status_checks_passed?` / `any_status_checks_failed?` [7](#0-6) [8](#0-7) . By injecting a fake `success` status for organization Y's commit, organization X can make an otherwise CI-failing/CI-pending commit appear deployable, or unblock it from the merge queue so `MergeRequest#merge!` merges it via `stack.github_api.merge_pull_request` [9](#0-8) . This is a cross-repository/cross-organization write leading to an unauthorized deploy or merge in a tenant the attacker has no legitimate access to — matching the Critical bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Low-to-moderate: it requires the Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration) and requires the attacker's organization to know a target commit SHA belonging to another tenant's stack (often discoverable via public repos, shared CI systems, PR links, or other status/webhook traffic). No privileged Shipit account, `ApiClient` token, or private key is needed — only control of a legitimate, independently-authenticated GitHub App installation for the attacker's own org.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the target repository from the payload (`payload.dig('repository', 'full_name')` via `Handler#stacks`/`Repository.from_github_repo_name`) and restrict the `Commit` lookup to commits belonging to that repository's stacks, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, rather than a global `Commit.where(sha: ...)`.

### Proof of Concept
1. Shipit is configured per `docs/setup.md` with two GitHub Apps: `orgX` and `orgY`, each with its own `webhook_secret`.
2. `orgY` hosts a stack tracking commit `abcdef123...` that currently has a failing/pending CI status, blocking deploy/merge.
3. An actor with control over `orgX`'s GitHub App (a legitimate, unprivileged-with-respect-to-orgY tenant) crafts a `status` webhook payload:
   ```json
   {
     "sha": "abcdef123...",
     "state": "success",
     "context": "ci/travis",
     "repository": { "owner": { "login": "orgX" }, "full_name": "orgX/some-repo" }
   }
   ```
4. Signs it with `orgX`'s own `webhook_secret` and POSTs to `/webhooks`. `WebhooksController#verify_signature` looks up `Shipit.github(organization: 'orgX')` and successfully verifies the signature [10](#0-9) .
5. `StatusHandler#process` executes `Commit.where(sha: 'abcdef123...')`, finds the commit under `orgY`'s stack, and calls `create_status_from_github!`, marking it `success` regardless of `orgX` having no relationship to `orgY`'s repository [5](#0-4) .
6. `orgY`'s commit now appears deployable/mergeable, enabling an unauthorized deploy or merge triggered through normal Shipit flows.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
