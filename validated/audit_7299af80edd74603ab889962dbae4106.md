### Title
Cross-tenant webhook forgery via organization/repository binding mismatch in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which tenant's `webhook_secret` to validate an incoming webhook against using an attacker-controlled field (`repository.owner.login` / `organization.login`) from the *unverified* JSON body, but the handlers that subsequently act on the request select the target `Stack`/`Repository` using a *different* attacker-controlled field (`repository.full_name`) from the same body, with no check that the two refer to the same GitHub organization/installation.

### Finding Description
In a multi-tenant Shipit deployment, `config/secrets.yml` can define a separate GitHub App (and separate `webhook_secret`) per organization, exactly as documented in `docs/setup.md` ("Using Multiple Github Applications") and exercised in `test/dummy/config/secrets_double_github_app.yml`. [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves the app/secret purely by the organization name key. [3](#0-2) 

`WebhooksController#verify_signature` picks the organization used for HMAC verification from `repository_owner`, which is read straight out of the untrusted, not-yet-verified JSON payload: [4](#0-3) [5](#0-4) 

Once the signature is accepted, `create` dispatches to handlers over the same raw payload: [6](#0-5) 

But every handler resolves the target repository/stacks from an entirely separate field, `repository.full_name`, with no cross-check against the organization that was used to validate the signature: [7](#0-6) 

For example `PushHandler` uses that unscoped `stacks` lookup to trigger a GitHub sync for any matching stack: [8](#0-7) 

and `StatusHandler` writes a commit status purely by `sha`, again independent of which organization's secret validated the request: [9](#0-8) 

The binding that should hold is: `organization whose secret authenticated the request == organization owning the repository the handler mutates`. Because the controller derives the verification key from one payload field and the handlers derive the acted-upon repository from a different, independently attacker-settable payload field, this equality is never enforced — mirroring the report's root cause (a matching/processing step trusting stale/inconsistent state from an earlier attacker-influenced field rather than re-validating it against the field actually used for the security decision).

### Impact Explanation
A tenant that legitimately administers **one** organization's GitHub App (and therefore knows that organization's `webhook_secret`, which they configured themselves when creating the App per `docs/setup.md`) can craft an HMAC-valid webhook body whose `repository.owner.login`/`organization.login` refers to their own org (satisfying `verify_signature`) while `repository.full_name` refers to a **different tenant's** repository on the same shared Shipit instance. This lets a single-tenant attacker trigger actions against another tenant's stacks — forcing GitHub syncs, injecting fabricated commit statuses (`Commit#create_status_from_github!`), or affecting other status/PR-driven state — none of which their own credentials should reach. This is a cross-tenant authorization boundary break reachable only by an entity that is unprivileged with respect to the victim tenant.

### Likelihood Explanation
Requires a shared multi-tenant Shipit deployment using the documented "Using Multiple Github Applications" configuration, and requires the attacker to control (and know the webhook secret of) at least one onboarded organization. This is a real, documented supported deployment mode of the engine, not a hypothetical misconfiguration, so the precondition is squarely within scope. The rest of the exploit (crafting a JSON body with mismatched `repository.owner.login` and `repository.full_name`) requires no special privilege beyond normal webhook delivery.

### Recommendation
After `verify_signature` succeeds, the organization used to resolve the `webhook_secret` must be cross-checked against the organization portion of `repository.full_name` (and any organization used by handlers to resolve `Repository`/`Stack`) before dispatching to handlers, rejecting the request if they diverge.

### Proof of Concept
1. Configure Shipit with two tenants, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the administrator of `OrgA` (who knows `OrgA`'s `webhook_secret`), build a `push` payload:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` as `"OrgA"`, fetches `OrgA`'s `webhook_secret`, and the signature checks out.
5. `PushHandler#process` resolves `stacks` from `repository.full_name` = `"OrgB/victim-repo"` and triggers `sync_github` for `OrgB`'s stack, even though the request was only ever authenticated as belonging to `OrgA`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
