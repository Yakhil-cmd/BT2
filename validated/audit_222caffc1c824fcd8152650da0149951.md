### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized deploy trigger - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `commits` table, without verifying that the commit's `stack`/`repository` matches the repository that signed the incoming webhook. `WebhooksController#verify_signature` authenticates only that the payload came from *some* org named `repository.owner.login` in the payload — it never checks that this org actually owns the stack(s) whose commits get matched. Because git commit SHAs are content-addressed and identical commits (same tree/parents/author/committer/timestamps/message) can legitimately exist in multiple repositories' histories (forks, mirrors, cherry-picks, shared upstream history), an attacker who controls a repository with a Shipit webhook installed can emit a signed `status` event for a SHA that also exists on a victim stack, causing Shipit to create a `Status` record on the victim's commit and potentially trigger `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob` → `Stack#trigger_continuous_delivery`, deploying the victim stack.

### Finding Description
The binding the system should enforce is: `commit.stack.repository == webhook_payload.repository` (i.e., the stack that receives the status update must belong to the same GitHub repository/org that produced and signed the webhook). This binding is broken.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) computes `repository_owner` from `params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. This proves the *request* was signed by organization A's webhook secret — nothing more.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` globally by `sha`, with **no filter on `stack_id`, `repository_id`, or the webhook's `repository_owner`/`repository.full_name`**. Any commit row across any tenant's stack whose SHA matches is picked up.
3. `Commit#create_status_from_github!` → `Status.replicate_from_github!` creates a `Status` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`).
4. `Status` callbacks fire: `after_create :enable_ci_on_stack` (`app/models/shipit/status.rb:18,38-40`) and `after_commit :schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) → `commit.schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`):
```ruby
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
```
5. If the victim's `stack.continuous_deployment?` is `true` and the commit is otherwise `deployable?` (not locked, `ignore_ci?` or `success? && !blocked?`), `ContinuousDeliveryJob.perform_later(stack)` is enqueued for the **victim's** stack — even though the webhook was signed by, and originated from, organization A, not the victim's organization.

Existing guards do not close this gap: `verify_signature` authenticates the org that sent the webhook but is never cross-checked against which stack's commit gets updated; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate shape (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler#process` or in `Commit.where(sha:)`.

Attacker action: control (or fork) a repository whose commit history intersects with a victim stack's commit history (e.g., a shared upstream/fork relationship, or replaying a `status` webhook body for a SHA known to also be tracked by a victim's stack), and send/trigger a `status` event via a legitimately signed webhook from the attacker's own installation naming a SHA present in the victim stack.

### Impact Explanation
A successful forged/replayed status causes Shipit to write a `Status` record against a commit belonging to a stack the attacker's organization does not own, and — when that victim stack has `continuous_deployment: true` — enqueues `ContinuousDeliveryJob` which calls `Stack#trigger_continuous_delivery`, ultimately calling `trigger_deploy`, which runs deployment commands for the victim's stack. This is a cross-tenant write (a payload for one repository mutating another's stack/commit) and can culminate in an unauthorized deploy, matching the Critical severity category defined in the rules. The blast radius spans any stack that shares commit SHAs with the attacker-controlled repository (forks, mirrors, monorepo-split history, vendored histories) and is repeatable per matching SHA/webhook delivery.

### Likelihood Explanation
Preconditions: the victim stack must have `continuous_deployment: true` and an undeployed commit whose SHA is also reachable/known by the attacker (e.g., shared git history via fork/mirror, or a previously-observed SHA from the victim's public commit log/PR). The attacker needs a repository with a Shipit-configured webhook under their control (which is explicitly listed as within the unprivileged attacker's capability), and knowledge of a SHA tracked by the victim. No Shipit credentials, session, or `webhook_secret` of the victim's org are required — only the attacker's own signing secret for their own org. This makes the attack low-cost and repeatable for any SHA collision the attacker can produce or observe.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogous handlers) to commits whose `stack.repository` matches the webhook's `repository.full_name`/`repository_owner`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repository_name })`, ensuring a status can only ever be applied to commits belonging to the repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar):
1. Create `stack_a` under `Repository(owner: "org-a", name: "repo-a")` and `stack_b` under `Repository(owner: "org-b", name: "repo-b")`, `stack_b.update!(continuous_deployment: true)`.
2. Create `commit_b = stack_b.commits.create!(sha: "deadbeef", ...)` (undeployed, otherwise deployable).
3. Also create `commit_a = stack_a.commits.create!(sha: "deadbeef", ...)` sharing the same SHA (simulating shared history/fork).
4. Build a `status` webhook payload with `repository.owner.login = "org-a"`, `sha: "deadbeef"`, `state: "success"`.
5. Stub `Shipit.github(organization: "org-a").verify_webhook_signature` to return `true` (simulating a validly signed request from org A only).
6. Mock `ContinuousDeliveryJob` and call `StatusHandler.call(payload)` (or POST through `WebhooksController#create`).
7. Assert: `commit_a.statuses.count == 1` (expected write for org A's own commit) AND `commit_b.statuses.count == 0` — i.e., assert `ContinuousDeliveryJob` is never enqueued with `stack_b`, and `commit_b.statuses.reload` remains empty.
8. Current code fails this assertion: because `Commit.where(sha: "deadbeef")` returns both `commit_a` and `commit_b`, a `Status` is created on `commit_b` too, and `ContinuousDeliveryJob.perform_later(stack_b)` is enqueued, demonstrating the binding `commit.stack.repository == webhook.repository` does not hold.
