### Title
Webhook signature is verified against the organization named in `repository.owner.login`/`organization.login`, but the Stack/commit written is chosen from the unrelated `repository.full_name` field, allowing cross-organization forged events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` picks the GitHub App (and therefore the HMAC secret) to validate the inbound webhook against using `repository_owner`, taken from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). The signature check only proves the raw body was signed with **that org's** `webhook_secret`. It never checks that this org actually corresponds to the `repository` object the payload event handlers subsequently act on. Every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`'s underlying `Commit` lookup, the `PullRequest` handlers, etc.) resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`. `repository.owner.login` and `repository.full_name` are independent, attacker-controlled JSON fields in the raw POST body and are never cross-validated against each other. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Shipit supports hosting multiple GitHub Apps, one per organization, each with its own `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb#github_app_config`). `WebhooksController#verify_signature` uses:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [4](#0-3) 

where
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

This binds "which secret authenticated the request" to `repository.owner.login`. Once verified, `create` dispatches the **entire raw JSON body** to the handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [6](#0-5) 

But the handler base class resolves the *acted-upon* repository from a different field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

`PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching stack, causing GitHub commits to be fetched/appended: [8](#0-7) . `GithubSyncJob#perform` then writes commit records via `append_commit`/`stack.commits.create_from_github!` for the targeted stack: [9](#0-8) .

The trust equality that is supposed to hold is:
`organization that authenticated the signature == organization owning the repository/stack that gets written`

Because `repository.owner.login` (used for signature org selection) and `repository.full_name` (used for stack selection) are two independent, unauthenticated JSON fields inside the same signed byte stream, an attacker who legitimately possesses the `webhook_secret` for one configured organization ("OrgA" — e.g., because they administer the GitHub App installation for their own org, which is a normal, unprivileged-relative-to-other-tenants position in a multi-org Shipit deployment) can sign a payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` succeeds using OrgA's secret)
- `repository.full_name` = `"OrgB/some-repo"` (a completely different, victim organization's tracked repository)

The controller has no code path that ever compares these two fields, so the forged payload passes signature verification and is then handled as if it legitimately originated from OrgB, driving pushes/commits/statuses/PR events against OrgB's stacks.

### Impact Explanation
This breaks the binding between "the organization whose credential authenticated the webhook" and "the repository that is written," resulting in cross-organization writes: an attacker with legitimate credentials scoped to their own tenant/org in a multi-app Shipit deployment can inject forged `push`, `status`, and `pull_request` events for a completely unrelated organization's tracked repositories, causing bogus commits to be appended to another org's deploy queue, bogus CI statuses to be attached to real commits (potentially unblocking deploy gating), and spurious review-stack/PR state changes — all without ever touching OrgB's `GITHUB_TOKEN`, `webhook_secret`, or `api_clients_secret`. This is a cross-repository write vulnerability (Critical, per the given impact taxonomy).

### Likelihood Explanation
Exploitability requires only that the Shipit deployment is configured with the documented multi-org GitHub App feature and that the attacker holds a valid webhook secret for at least one tenant org (e.g. an org admin who configured their own GitHub App integration) — no elevated Shipit account, API token, or access to the target org is needed. This is a realistic multi-tenant configuration explicitly documented in `docs/setup.md`, making the likelihood moderate-to-high wherever that feature is used.

### Recommendation
In `WebhooksController`/`Shipit::Webhooks::Handlers::Handler`, ensure the organization used to select the verifying `webhook_secret` is the same value used to resolve the target `Repository`/`Stack`, e.g. derive both from `repository.full_name`'s owner segment (or, after successful signature verification for org X, restrict handler repository resolution to repositories where `Repository#owner == X`), rejecting/logging any payload where they diverge.

### Proof of Concept
1. Deploy Shipit with multiple GitHub Apps configured (`OrgA`, `OrgB`) per `docs/setup.md`, each with distinct `webhook_secret`s, both orgs having tracked stacks.
2. As a legitimate admin/attacker who knows OrgA's `webhook_secret` (e.g., because they configured OrgA's App), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POST to `/github/webhooks` (route defined in `config/routes.rb`) with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')` and succeeds because the signature matches OrgA's secret.
5. `Shipit::Webhooks::Handlers::PushHandler` resolves `stacks` via `Repository.from_github_repo_name('OrgB/victim-repo')`, matching OrgB's real tracked stack, and enqueues `GithubSyncJob` against it — despite the request never being authenticated as originating from OrgB.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
