### Title
Webhook signature verification binds only the signing organization, not the repository the payload writes to - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field. Once the HMAC check passes, the entire raw JSON payload — including fields never covered by that per-organization identity check — is dispatched to event handlers. The `status` webhook handler in particular resolves the target `Commit` purely by `sha`, with no scoping to the repository/organization that produced the valid signature. This breaks the binding: "organization whose secret authenticated the request" == "repository/stack whose data is written."

### Finding Description
The webhook signature check is org-scoped: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GithubApp`/webhook secret configured for whatever organization the attacker names in `repository.owner.login`. Any actor who can install the Shipit GitHub App on their own, unprivileged GitHub organization (a self-service action requiring no access to the target Shipit instance) legitimately obtains a valid webhook secret for *that* organization, and can therefore produce payloads that pass `verify_signature`.

Once verified, the payload is handed unmodified to the registered handlers: [3](#0-2) 

The base `Handler` class exposes two different ways handlers bind payload data to Shipit records. `PushHandler` scopes by `repository.full_name` (a field distinct from and never compared against `repository.owner.login` used for signing): [4](#0-3) [5](#0-4) 

`StatusHandler` goes further and does not scope by repository at all — it looks up commits globally by `sha` across the entire Shipit instance and writes a GitHub-reported CI status onto whatever `Commit` record matches, regardless of which repository/stack owns it: [6](#0-5) 

So the equality the signature is supposed to guarantee — "the organization that signed this payload is the organization whose repository/commit is being mutated" — does not hold. The signature only proves *an* organization with a Shipit-registered GitHub App sent the request; it says nothing about which `repository.full_name` or `sha` inside the JSON body is acted upon, and those fields are never cross-checked against `repository_owner`.

### Impact Explanation
An attacker who legitimately installs the Shipit GitHub App on their own, unrelated GitHub organization can:
- Craft a `status` webhook event whose `sha` matches a commit belonging to a completely different, unrelated stack tracked by the same Shipit instance (commit SHAs of public repos are public/guessable, and Shipit's own UI/API exposes them), with `state: success` and an arbitrary `context`/`description`. This injects a forged "green" CI status onto that commit via `Commit#create_status_from_github!`, which feeds into `Commit#deployable?` and the release/merge-queue gating logic used to authorize deploys and merges elsewhere in the engine.
- Craft a `push` webhook whose `repository.owner.login` matches their own org (to pass signature verification) but whose `repository.full_name` names a different repository, causing `PushHandler` to enqueue a `GithubSyncJob`/`stack.sync_github` against a stack the attacker does not control.

Forging a passing CI/deployable status for a commit in a stack the attacker has no legitimate relationship to can enable an unauthorized deploy or merge-queue progression, matching the "unauthorized deploy, rollback or merge" Critical impact criterion.

### Likelihood Explanation
The only prerequisite is the ability to install the Shipit GitHub App on any GitHub organization and configure a webhook pointed at the target Shipit instance — a self-service, unprivileged action that requires no access to the victim's Shipit deployment, `GITHUB_TOKEN`, or any Shipit-issued credential. The victim commit's SHA is the only piece of information needed and is generally public for open-source targets, making this practically exploitable wherever the Shipit instance handles webhooks from more than one GitHub App/organization installation.

### Recommendation
Bind the webhook's authenticated identity to the data it is allowed to mutate:
- In `StatusHandler#process`, scope the `Commit` lookup by the repository derived from the payload (`repository.full_name`) rather than a bare `sha` match across the whole instance.
- In `WebhooksController#verify_signature` / `Handler`, verify that the `repository.owner.login` (or `organization.login`) used to select the webhook secret matches the `repository.full_name` owner actually referenced by the payload before dispatching to handlers, so a signature valid for one organization cannot be replayed to mutate records belonging to another organization/repository.

### Proof of Concept
1. Attacker creates GitHub organization `attacker-org` and installs the Shipit GitHub App on a repository there, obtaining a legitimate per-organization `webhook_secret` configured in Shipit for `attacker-org`.
2. Attacker sends a `status` event to `POST /webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature` computed with `attacker-org`'s webhook secret over the raw body
   - Body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/decoy"}, "sha": "<victim-repo-commit-sha>", "state": "success", "context": "ci/required-check", "branches": [...]}`
3. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, verifies successfully against `attacker-org`'s secret.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matching the commit belonging to an unrelated victim stack, and calls `create_status_from_github!(params)`, writing a forged successful status onto that commit — with no check that `attacker-org` owns or is associated with that commit's repository.
