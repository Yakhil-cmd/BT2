### Title
Cross-stack unauthenticated read via `Api::CCMenuController#stack` bypassing `current_api_client.stack_id` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces the binding `stack ∈ stacks(current_api_client.stack_id)` by resolving the requested stack through `stacks.from_param!(params[:stack_id])` [1](#0-0) , but `Api::CCMenuController` overrides `#stack` to call the unscoped `Stack.from_param!(params[:stack_id])` directly, breaking that binding for any request to the CCMenu endpoint [2](#0-1) . This lets a holder of any `read:stack` ApiClient token that is bound to a single stack (`ApiClient#stack_id` set) read the deploy/rollback history of an arbitrary other stack.

### Finding Description
The intended binding is: `stack requested by an API call == an element of stacks scoped by current_api_client.stack_id` (i.e. `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is stack-restricted, else `Stack.all`) [3](#0-2) .

`ApiClient` supports being bound to exactly one stack via `belongs_to :stack, optional: true` [4](#0-3) , and `BaseController#stacks` is the sole enforcement point of that restriction; every other API controller (e.g. `Api::StacksController`) resolves stacks through this scoped helper.

`Api::CCMenuController`, however, defines its own private `stack` method that ignores the `stacks` scope entirely and resolves directly against the global `Stack` relation:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Authentication still passes through `ApiClient.authenticate(params[:token])` [5](#0-4) , and `require_permission :read, :stack` only checks that the client's `permissions` array includes `"read:stack"` [6](#0-5) ; it never checks which stack the permission applies to. So an `ApiClient` created with `stack_id: stack_a.id` and permission `read:stack` — a legitimately supported, narrowly-scoped API credential — passes `authenticate_api_client` and `require_permission!`, then `#show` calls `stack` which resolves `params[:stack_id]` against *all* stacks, not just stack A. The attacker sends `GET /stack_b_owner/stack_b_repo/stack_b_env/ccmenu.xml?token=<stack-A-scoped token>` and receives stack B's `deploys_and_rollbacks` history.

Note on the question's specific PoC premise: the token minted by `CCMenuUrlController#fetch` is not actually a good illustration of this bug, because that controller creates a shared, unscoped `ApiClient` (`find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with no `stack:` attribute set) [7](#0-6) . Since that client's `stack_id` is `nil`, `stacks` already resolves to `Stack.all` for it even under the correct `BaseController#stack` implementation — so for *that specific* token the equality already holds trivially and there's no divergence to exploit. The real, demonstrable divergence requires an `ApiClient` whose `stack_id` is explicitly set to a single stack (a first-class, supported configuration per the model), at which point `CCMenuController`'s bypass becomes a genuine authorization break.

### Impact Explanation
An attacker holding any `read:stack` API token that is bound to a single stack can read the deploy/rollback timeline (deploy status, commit SHAs, timing) of any other stack in the installation by hitting the CCMenu XML endpoint with a different `stack_id`. This is an unauthenticated-for-that-resource read of stack state across tenants/repositories, matching the High severity category ("unauthenticated read of stack state ... across tenants"). It does not, by itself, allow writes, deploys, or credential exfiltration, so it stops short of Critical.

### Likelihood Explanation
Requires the operator to have issued at least one stack-scoped `read:stack` ApiClient token (a supported, documented feature via `ApiClient#stack_id`). Once such a token exists (e.g. given to a third-party CI dashboard restricted to one stack), any holder of it can immediately pivot to read any other stack by changing `stack_id` in the URL — no additional secrets, sessions, or GitHub access needed, and the request is trivially repeatable against every stack id in the system.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped helper, matching every other API controller:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
and remove the private override entirely so it inherits `BaseController#stack`/`#stacks`.

### Proof of Concept
```ruby
class Api::CCMenuControllerTest < ActionDispatch::IntegrationTest
  setup do
    @stack_a = shipit_stacks(:shipit)
    @stack_b = create_stack(repository: create_repository(name: 'other'))
    @client = ApiClient.create!(creator: shipit_users(:walrus), name: 'scoped', stack: @stack_a, permissions: %w[read:stack])
    @token = @client.authentication_token
  end

  test "stack-scoped token cannot read another stack's ccmenu data" do
    # Binding under test: stack requested == element of Stack.where(id: current_api_client.stack_id)
    assert_equal [@stack_a.id], Stack.where(id: @client.stack_id).pluck(:id)

    get api_stack_ccmenu_url(stack_id: @stack_b.to_param, token: @token)

    # Correct behaviour: request for stack_b must be rejected (404/RecordNotFound) because
    # @stack_b.id is not in Stack.where(id: current_api_client.stack_id)
    assert_response :not_found
  end
end
```
Against the current code, `Stack.from_param!(params[:stack_id])` in `Api::CCMenuController#stack` resolves `@stack_b` successfully and returns `200 OK` with stack B's deploy/rollback XML, proving the binding is broken.
