### Title
Asset issuer can retroactively revoke attestor list, freezing already-attested funds with no grace period - (File: `storage.js`, `validation.js`)

### Summary
For any `spender_attested` asset, the asset definer/issuer can post an `asset_attestors` message at any time to change the list of trusted attestors. When payments are validated, the protocol always looks up the *current, latest* attestor list rather than the attestor list that was in effect when the holder's coins were received. This lets an issuer instantly and retroactively invalidate previously legitimate holdings, freezing user funds without any buffer/time-lock — the same root-cause pattern as the referenced report, where a privileged party mutates a security-critical parameter that affects already-established positions with immediate, unavoidable effect.

### Finding Description
When an asset is defined with `spender_attested: true`, spending its outputs requires the owner address to be attested by one of the asset's attestors [1](#0-0) . The list of attestors that is checked, however, is not the list that applied when the funds were received; it is always the single *latest* attestor list unit found before `last_ball_mci`: [2](#0-1) 

The definer can publish a new `asset_attestors` update at any time to replace the attestor list, and validation only enforces that the sender is the asset's definer — there is no restriction tied to existing outstanding balances or any delay before the new list takes effect: [3](#0-2) 

Because `readAsset()`/`filterAttestedAddresses()` always resolve attestations against the newest list, and payment validation re-checks `spender_attested` ownership against `arrAttestedAddresses` on every spend attempt (not just at receipt time), an address that was validly attested under an old attestor list can lose the ability to spend previously-received, perfectly legitimate coins the moment the definer swaps out the attestor set: [4](#0-3) 

This mirrors the external report's root cause exactly: a single privileged actor (there, `PoolAdmin` via `setAssetCollateralParams`; here, the asset definer via `asset_attestors`) can change a parameter that retroactively governs already-existing positions/holdings, with no timelock, no grandfathering, and no opportunity for affected holders to react before the change takes effect.

### Impact Explanation
- Any holder of a `spender_attested` asset can have their funds instantly frozen (rendered unspendable) the moment the definer updates the attestor list, even though the funds were legitimately acquired while properly attested.
- There is no mechanism to grandfather in-flight balances or give holders a window to move/spend funds before the new list becomes effective.
- Because the definer can only ever set the list going forward, and unit propagation/finality happens asynchronously, holders have no reliable way to preempt or contest the change — their coins can be locked indefinitely (until/unless the definer reinstates them).

This is a concrete freezing-of-funds impact reachable purely through an asset issuer's normal, permitted `asset_attestors` message — no malicious node/peer, collusion, or external assumption is required.

### Likelihood Explanation
Any asset issuer who defines a `spender_attested` asset already has the unilateral, unrestricted right to post attestor-list updates at any main chain index; this is a standard, expected action supported natively by the protocol (`app: "asset_attestors"`). No special conditions or race are needed beyond the definer choosing to update the list — which could be triggered by compromise of the definer's key, a mistaken configuration change, or an intentional decision to exclude a subset of previously-attested holders. Because the effect is immediate and retroactive by design of `readAsset()` always fetching the newest list, likelihood of user impact is high whenever an active issuer rotates attestors on an asset with existing circulating balances.

### Recommendation
- Cache/pin the attestor list that was active at the time each output was created (or at time of last successful spend-check), and validate future spends of that specific output against the pinned list rather than always the latest list.
- Alternatively, introduce a delay (buffer of some number of MCIs) before an `asset_attestors` update takes effect for spend validation, giving existing holders time to move funds under the old list before the new list becomes binding.
- Ensure `asset_attestors` updates cannot instantaneously invalidate already-attested, currently-held balances; any narrowing of the attestor set should only affect future issuance/attestation, not funds already legitimately obtained.

### Proof of Concept
1. Definer `D` creates asset `X` with `spender_attested: true` and initial `attestors: [A1]`.
2. `A1` attests address `U`; `D` (or another party) pays `U` some amount of asset `X`. At validation time, `U` is in `arrAttestedAddresses` (via `A1`), so the payment to `U` is valid and accepted per `validatePayment()` [1](#0-0) .
3. Some time later, `D` posts an `asset_attestors` update for asset `X` setting `attestors: [A2]` (removing `A1`). This is accepted because `D` is the definer [5](#0-4) .
4. `U` (who was never attested by `A2`) now tries to spend the previously-received `X` coins. `readAsset()` looks up the latest attestor list unit (the `[A2]` update) [6](#0-5) , `filterAttestedAddresses` finds `U` is not attested by any address in `[A2]`, so `arrAttestedAddresses` for `U` is empty.
5. `U`'s spend transaction fails validation with `"owner address is not attested"` [4](#0-3)  (or `"none of the authors is attested"` for public payments [7](#0-6) ), permanently freezing `U`'s previously legitimate balance with no advance warning or grace period.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
