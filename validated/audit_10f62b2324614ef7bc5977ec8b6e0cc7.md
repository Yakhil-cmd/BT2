### Title
Cross-organization webhook confusion allows forging commit statuses for any tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to validate a request against based on a field taken from the attacker-controlled JSON body itself, but the event handlers (in particular `StatusHandler`) then act on data from that same body with no cross-check that the acting organization matches the resource being written. This breaks the equality that should hold: `organization whose secret validated the signature == organization owning the resource being mutated`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization whose `webhook_secret` will be used to HMAC-verify the payload from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — a value fully controlled by whoever crafts the request body. Since Shipit is multi-tenant (`config/secrets.development.shopify.yml` shows multiple orgs, each with its own `webhook_secret`), any org admin who legitimately controls a GitHub App/webhook installed for **their own** org possesses a valid `webhook_secret` and can compute a correct `X-Hub-Signature` for **any JSON body they want**, as long as `repository.owner.login` (or `organization.login`) in that body names their own org.

Once the signature check passes, `WebhooksController#create` dispatches to the registered handler for the event with the raw, attacker-controlled JSON: [3](#0-2) 

Handlers such as `PushHandler` scope their side effects using `repository.full_name` from the same payload: [4](#0-3) [5](#0-4) 

Nothing ties `repository.full_name` (used to select the affected `Stack`/`Repository`) back to `repository.owner.login`/`organization.login` (used to select the signing secret) — they are independent, attacker-supplied fields in the same body. Worse, `StatusHandler` doesn't even scope by repository at all — it matches purely on commit SHA across the entire installation: [6](#0-5) 

So an attacker who legitimately controls Org A's webhook secret can send a `status` event where `organization.login` (or `repository.owner.login`) = `"org-a"` (to pass `verify_signature`), while `sha` is the commit SHA of a completely unrelated stack belonging to Org B, and `state`/`context`/`description` are fully attacker-chosen. `Commit.where(sha: params.sha)` will match any tracked commit with that SHA regardless of which organization/repository it belongs to, and `create_status_from_github!` will persist an attacker-chosen status for it.

### Impact Explanation
Commit statuses drive Shipit's CI-gating logic used for both the merge queue and deploy safety checks (`MergeRequest#all_status_checks_passed?`, blocking/required statuses, etc. — [7](#0-6) ). By forging a `success` status for an arbitrary commit belonging to another organization's repository that Shipit tracks, an attacker who only controls their own org's GitHub App/webhook secret can satisfy the CI-gating requirements for that unrelated stack, enabling an unauthorized automatic merge (via `ProcessMergeRequestsJob` / merge queue — [8](#0-7) ) or unblock a deploy that should have been held back on failing/missing CI. This matches the "escalation ... unauthorized deploy, rollback or merge" impact category — the attacker never needed a Shipit session, an `ApiClient` token, or write access to the victim's GitHub repository; only control of a different organization's webhook secret already configured on the same Shipit instance.

### Likelihood Explanation
Exploitability requires the attacker to already control a legitimate GitHub App/webhook installation for at least one organization tracked by the same multi-tenant Shipit instance (i.e., `Shipit.github_config` contains more than one org, as illustrated by `config/secrets.development.shopify.yml`). This is a realistic deployment scenario for Shipit as an internally-shared CI/CD platform serving multiple orgs/teams, where cross-org isolation of webhook trust is an implicit but unenforced assumption. The attacker also needs to know or guess a target commit SHA (obtainable from public commit history, PRs, or a prior webhook to the target repo), which is not a strong barrier.

### Recommendation
- In `WebhooksController#verify_signature`, after establishing which organization's secret verified the signature, enforce that every handler invoked for that request may only act on repositories belonging to that same organization.
- In `Shipit::Webhooks::Handlers::Handler`/`StatusHandler`, scope `Commit` lookups (and any other cross-cutting lookups) by the repository/organization that was authenticated, not merely by SHA, e.g. `stack.commits.by_sha(...)` restricted to repositories owned by `repository_owner`, and reject events where the payload's `repository.owner.login` doesn't match `repository.full_name`'s owner segment.
- Consider validating that `repository.full_name`'s owner segment equals the `repository_owner` used for verification before dispatching to any handler.

### Proof of Concept
1. Shipit instance is configured with two orgs, `org-a` and `org-b`, each with a distinct `webhook_secret` (as supported by `config/secrets.development.shopify.yml`), and each with a tracked `Stack`/`Repository`.
2. Attacker is a legitimate admin of `org-a`'s GitHub App and knows its `webhook_secret` (their own, not `org-b`'s).
3. Attacker learns (e.g., via GitHub's public commit page) the SHA of a commit belonging to `org-b/target-repo`, currently pending required CI status checks in Shipit.
4. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<org-b commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "organization": { "login": "org-a" }
   }
   ```
5. Attacker computes `X-Hub-Signature` using `org-a`'s `webhook_secret` (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`), sets `X-Github-Event: status`, and POSTs to `/github/webhooks`.
6. `WebhooksController#verify_signature` resolves `repository_owner` to `"org-a"`, verifies successfully against `org-a`'s secret.
7. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `org-b` commit — and calls `create_status_from_github!`, recording a forged `success` status on it, independent of `org-a`/`org-b` boundaries.
8. If this satisfies `org-b`'s stack's required/blocking statuses, the merge queue (`ProcessMergeRequestsJob`) or a pending deploy proceeds despite real CI never having passed.

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

          params.ref.gsub('refs/heads/', '')
        end
      end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
