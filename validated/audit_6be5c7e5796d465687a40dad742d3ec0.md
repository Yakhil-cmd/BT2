### Title
Api::CCMenuController#stack bypasses ApiClient stack scoping, letting a token authorized for one stack read the CCMenu state of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces token-to-stack scoping through a dedicated `stacks` scope method, but `Api::CCMenuController` overrides `#stack` to resolve directly against the global `Stack` relation, bypassing that scoping while still relying on the same coarse-grained `read:stack` permission check.

### Finding Description
`Api::BaseController#stacks` is the binding that is supposed to enforce "the stack a token authorizes == the stack it can touch": [1](#0-0) 
When `current_api_client.stack_id?` is set (i.e. the `ApiClient` is scoped to one specific stack, as created for CCMenu tokens themselves via `ccmenu_url_controller.rb`), `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)`, and `stack` resolves through that scoped relation.

`ApiClient#check_permissions!` only checks the operation/scope string (e.g. `read:stack`) and never considers `stack_id` at all: [2](#0-1) 
So the entire cross-stack protection for a stack-scoped token depends on controllers resolving `stack` through `stacks.from_param!`, as `TasksController`, `DeploysController`, etc. correctly do (inherited from `BaseController`).

`Api::CCMenuController`, however, defines its own `#stack` that ignores this scoping entirely: [3](#0-2) 
It still declares `require_permission :read, :stack` at the class level: [4](#0-3) 
Since `check_permissions!` never inspects the client's `stack_id`, any token that merely has the `read:stack` permission string - including one that was minted scoped to Stack A (e.g. via `CCMenuUrlController#client`, which creates an `ApiClient.create_with(permissions: %w[read:stack])` bound to a single stack) - passes the permission check regardless of which `stack_id` is requested in the URL, and `Stack.from_param!(params[:stack_id])` will then happily resolve to any other stack B.

### Impact Explanation
This breaks the binding "the stack a token authorizes == the stack the endpoint touches." A CCMenu token that a host application or user believes is confined to one stack can be replayed against `GET /api/stacks/*stack_id/ccmenu` for an arbitrary other stack and will succeed, returning that other stack's name, activity, last build status/label/time and web URL: [5](#0-4) 
This is an unauthorized cross-stack read of stack/deploy state using a token that was never granted access to that stack - matching the "unauthenticated/unauthorized read of stack state" High-impact category, since the token's scope grant is bypassed entirely for this one endpoint.

### Likelihood Explanation
Likelihood is straightforward for anyone who possesses any valid `ApiClient` token carrying `read:stack` (including narrowly-scoped CCMenu tokens that are routinely embedded in CI dashboards/URLs, as generated by `CCMenuUrlController`): they only need to know or guess another stack's `owner/repo/environment` path segment to read its build status, with no additional privilege needed. The stack path is often predictable/discoverable (repository names, environments like `production`/`staging`).

### Recommendation
Make `Api::CCMenuController#stack` resolve through the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])` directly, so stack-scoped tokens cannot escape their assigned stack.

### Proof of Concept
1. An operator generates a CCMenu URL/token for `stack-a` via the UI, which creates an `ApiClient` with `stack_id = stack-a.id` and `permissions: ['read:stack']` (`app/controllers/shipit/ccmenu_url_controller.rb`).
2. An attacker who obtains this token (it is embedded in a plain query-string URL meant for CI dashboards) sends `GET /api/stacks/other-org/stack-b/production/ccmenu?token=<token>`.
3. `authenticate_api_client` in `CCMenuController` authenticates the token successfully.
4. `require_permission :read, :stack` calls `check_permissions!('read', 'stack')`, which only checks that `'read:stack'` is in the token's `permissions` array — it never checks `stack_id`.
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` against the global `Stack` table, returning `stack-b` regardless of the token's `stack_id` binding.
6. The response renders `stack-b`'s CCMenu XML (name, last build status/label/time, web URL) even though the token was only ever authorized for `stack-a`.
