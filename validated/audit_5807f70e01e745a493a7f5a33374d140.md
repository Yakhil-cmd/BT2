### Title
Webhook signature verification is scoped to a GitHub organization taken from an unverified payload field, while event handlers act on a completely different, uncross-checked repository field, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is a structural analog of the "first depositor" bug class: a value used to satisfy a trust check (`repository_owner`, used to pick which HMAC secret authenticates the request) is not the same value that downstream logic actually acts on (`repository.full_name`, used to resolve the target `Stack`). Just as the GoGoPool exploit abused the gap between the value the exchange-rate check trusted (`totalSupply`) and the value actually redeemable (`totalAssets`), this gap lets an attacker "authenticate as org A" while "writing to repository B".

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to validate the HMAC signature against using a value pulled straight from the untrusted, attacker-supplied JSON body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Once the signature check passes, the payload is dispatched unchanged to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Every handler resolves its target `Stack` purely from a *different* field of the same payload — `repository.full_name` — with no cross-check against the `repository.owner.login`/`organization.login` value that was used to select the signing secret: [3](#0-2) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` then acts on whatever stacks match that (attacker-controlled) `full_name`: [4](#0-3) 

```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```

Shipit is explicitly designed to host multiple independently-configured GitHub organizations, each with its own `webhook_secret`: [5](#0-4) 

and `Shipit.github(organization:)` looks up the app/secret purely by the organization name string, with no binding back to which repositories that organization is allowed to reference: [6](#0-5) 

Additionally, `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization at all: [7](#0-6) 

**Binding broken (as an equality):**
`organization authenticated by verify_signature (payload.repository.owner.login) == repository actually written/acted upon by the handler (payload.repository.full_name)` — this equality is never enforced. GitHub itself would never send a payload where `repository.owner.login` and `repository.full_name`'s owner disagree, but nothing in Shipit forces a *forged* payload to respect that invariant.

### Impact Explanation
Before the attacker acts: signature verification and stack resolution are supposed to refer to the same GitHub repository, since real GitHub webhooks are internally consistent.

After the attacker's forged request: an attacker who is an admin/owner of *any one* GitHub organization/repository that is configured in this Shipit instance (and therefore legitimately knows, or can derive by observing real webhook deliveries, that organization's `webhook_secret`) — or who targets any configured organization whose `webhook_secret` is left unset — can craft a payload where:
- `repository.owner.login` = the organization whose secret they control (so `verify_signature` passes),
- `repository.full_name` = an arbitrary **other** stack/repository hosted on the same Shipit instance.

This is accepted and dispatched to handlers that never re-validate the owner/full_name relationship, letting the attacker drive `PushHandler` to call `stack.sync_github(expected_head_sha: <attacker-chosen sha>)` against a victim stack they have no GitHub permissions on, forcing Shipit's notion of "expected head" for that stack to an attacker-chosen commit. Since continuous-deployment and deploy-candidate logic in Shipit is driven by what `sync_github` records as the stack's head commit, this is a cross-repository write into another team's stack state and a path toward an unauthorized deploy trigger without ever holding push access, an `ApiClient` token, or the victim organization's webhook secret — matching the Critical/High impact bucket ("cross-repository writes" / "unauthorized deploy").

### Likelihood Explanation
Requires only: (a) admin/webhook access to any one GitHub organization already configured on the target Shipit instance (which may be the attacker's own org if the instance is multi-tenant, e.g. an internal PaaS offering Shipit to multiple teams), or (b) any configured organization with an unset `webhook_secret` (`verify_webhook_signature` returns `true` unconditionally in that case). No repository-write access to the victim repo, no `ApiClient` token, and no privileged Shipit account are needed — only the ability to POST a crafted JSON body to the public `/webhooks` endpoint.

### Recommendation
After signature verification succeeds, re-derive the organization from the same field the handlers use (`repository.full_name`'s owner segment, or the resolved `Repository`/`Stack` record) and reject the request (422) if it does not match the organization whose secret validated the signature. Do not treat `repository.owner.login` and `repository.full_name` as independent trust domains.

### Proof of Concept
1. Shipit instance is configured for two orgs, `attacker-org` (webhook_secret known to the attacker, who administers that org's GitHub App) and `victim-org` (hosts a stack `victim-org/secret-repo`).
2. Attacker computes `sha256=<hmac>` over a crafted JSON body using `attacker-org`'s `webhook_secret`:
```json
{
  "ref": "refs/heads/production",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/secret-repo"
  }
}
```
3. POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha256=<hmac>`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully because the signature matches `attacker-org`'s secret [1](#0-0) .
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/secret-repo")` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the attacker never having authenticated as, or been authorized by, `victim-org`.

Note: I was not able to inspect the full body of `Stack#sync_github` (only located its definition site) before the iteration limit was reached, so the exact downstream consequence (e.g., whether it can force an actual deploy trigger versus only corrupt commit-sync state) should be confirmed by a Devin session reading `app/models/shipit/stack.rb`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
