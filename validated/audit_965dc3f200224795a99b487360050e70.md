### Title
Webhook signature verification keys off `repository.owner.login`, but event handlers dispatch on the unrelated `repository.full_name` field, allowing cross-organization sync/writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. The `Handler` base class used by all event handlers (e.g. `PushHandler`) resolves the actual `Repository`/`Stack` to act on using a *different* field of the very same payload: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked against each other, so the HMAC only proves the sender knows the secret for the org named in `repository.owner.login` — it proves nothing about which repository `full_name` claims to be, since the whole payload (including `full_name`) is attacker-controlled plaintext once a valid signature for *some* configured org is produced.

### Finding Description
Shipit supports multiple GitHub orgs/apps, each with its own `webhook_secret` (`lib/shipit/github_app.rb`, `config/secrets.*.yml`). The controller flow is: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The HMAC check `verify_webhook_signature` validates the raw body against the secret configured for the org identified by `repository.owner.login` [2](#0-1) .

But every webhook handler resolves the target repository/stack through a completely different payload field: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then finds stacks matching `branch` under `repository_name` and calls `stack.sync_github(expected_head_sha: params.after)` [4](#0-3) , enqueuing `GithubSyncJob` for that stack.

Because `repository.owner.login` (used for signature selection) and `repository.full_name` (used for repository resolution) are independent JSON keys in the same attacker-supplied body, an attacker who can produce *any* validly-signed payload for organization A (e.g. because they operate a legitimate GitHub App/webhook integration for org A and thus know org A's `webhook_secret`) can set `repository.owner.login = "orgA"` while setting `repository.full_name = "orgB/private-repo"`. The signature check passes (it only depends on org A's secret and the raw body), yet the handler acts on `orgB/private-repo`, a repository/stack the attacker has no legitimate relationship with.

The binding that should hold is:
`organization whose webhook_secret produced a valid signature == organization that owns the repository the handlers act on`

This binding is broken because the two sides are read from unrelated, mutually inconsistent payload fields that are never validated against each other, even though both are covered by the same signature (the signature proves integrity of the bytes, not internal consistency of the JSON).

### Impact Explanation
This lets a party who possesses only one organization's webhook secret trigger `GithubSyncJob` (and other handler side effects: `pull_request`, `status`, `check_suite`, `membership` handlers) against stacks/repositories belonging to a *different* organization configured in the same Shipit instance. This is a cross-organization write: it can create/modify `Commit` records, `Team`/`Membership` records via the `membership` handler, and drive `sync_github` state transitions for a repository the attacker does not control, without ever needing that repository's own webhook secret. This matches "cross-repository writes" impact.

### Likelihood Explanation
Requires the attacker to already hold a legitimate `webhook_secret` for at least one organization configured in the Shipit instance (a real prerequisite, not "no credential"), but does not require any Shipit session, API token, or GitHub access to the *target* organization/repository — which is exactly the class of unprivileged-relative-to-target-repo attacker the scope calls for. Multi-org Shipit deployments are an explicitly supported configuration (`config/secrets.development.shopify.yml` shows multiple orgs, each with independent `webhook_secret`), so the precondition is realistic wherever more than one org is configured.

### Recommendation
Cross-validate the two fields before dispatching to handlers: reject (or clamp) any webhook whose `repository.full_name`'s owner segment does not match `repository.owner.login`/`organization.login` used for signature verification. Alternatively, resolve the target `Repository` using the same field validated during signature selection, and pass the already-authenticated organization identity into handlers rather than trusting `repository.full_name` unchecked.

### Proof of Concept
1. Attacker controls (legitimately or otherwise) org A's `webhook_secret` in a multi-org Shipit deployment (org A and org B both configured, per `config/secrets.*.yml`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/private-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against org A's secret [5](#0-4) .
5. `PushHandler.call(params)` resolves `Repository.from_github_repo_name("orgB/private-repo")` and triggers `sync_github` on its stacks [4](#0-3) , acting on org B's stack despite the signature only proving knowledge of org A's secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
