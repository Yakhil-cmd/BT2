### Title
`StatusHandler#process` ignores repository scoping and writes GitHub statuses onto any stack's commit by SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Handler#stacks` correctly derives an ActiveRecord scope from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, returning `Stack.none` when no repository matches, but `StatusHandler#process` never calls `stacks` at all. It queries `Commit.where(sha: params.sha)` globally, so a `status` webhook delivered from any repository the attacker owns can write a fabricated commit status onto a `Commit` belonging to a completely unrelated stack, as long as the attacker supplies a SHA that exists in the target stack.

### Finding Description
The claimed binding is: `Handler#repository_name == payload.dig('repository', 'full_name')` and `Handler#stacks == Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [1](#0-0) . This scoping mechanism is correctly used by other handlers, e.g. `PushHandler#process` restricts itself to `stacks.not_archived.where(branch:)` before touching any records [2](#0-1) .

`StatusHandler#process`, however, never references `stacks`/`repository_name` at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

`Commit#sha` is not scoped uniquely per repository at the DB query level here — `Commit.where(sha:)` runs against the entire `commits` table across every stack/repository tracked by the Shipit instance. `create_status_from_github!` then writes a new `Status` row and triggers hook/deployability recalculation on that commit regardless of which repository the webhook actually claims to originate from [4](#0-3) , and `add_status` re-evaluates `deployable_status`/`schedule_merges` based on the new status [5](#0-4) .

Since the `payload['repository']['full_name']` field is fully attacker-controlled content of the webhook body (per the rules, an unprivileged attacker can "emit webhooks from a repository they own"), and Shipit's GitHub App webhook secret is shared across all repositories serviced by the App (not per-repository), a validly-signed webhook from the attacker's own repository still passes signature verification. The `repository_name`/`stacks` scoping is exactly the mechanism meant to bind the webhook's claimed repository to the commits it's allowed to affect, and `StatusHandler#process` simply omits it — this is the isolated defect, not a framework-wide limitation, since `Handler#stacks` itself works correctly (as would be shown by a direct unit test).

### Impact Explanation
Any commit SHA that exists in a victim stack's `commits` table (commit SHAs are content-addressed and frequently public/known, e.g. via the public GitHub repository or a public fork sharing history) can be targeted. The attacker sends a forged `status` event naming that SHA with `state: 'success'`, `description`, `target_url` of their choosing. Shipit writes this as a real `Status` on the victim's `Commit`, recalculates `deployable?`/`blocked?`, and can trigger `schedule_continuous_delivery` / unblock a deploy for a stack the attacker never authenticated against [6](#0-5) . This is a cross-tenant write — "a payload for one repository mutating another's stack/commit" — matching the Critical severity category (unauthorized deploy / commit mutation across repositories).

### Likelihood Explanation
Preconditions are minimal: the attacker only needs a repository they own with a webhook configured against the Shipit host (using the shared App secret, which is not the victim-specific secret) and knowledge of a target commit SHA in the victim stack (often public). No Shipit session, API token, or GitHub team membership is required. The attack is fully repeatable against any stack/commit whose SHA is known.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through `stacks` (e.g. `stacks.flat_map(&:commits).find { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack: stacks)`), mirroring `PushHandler`, so that only commits belonging to the repository named in `payload['repository']['full_name']` can be updated.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (regression)
test "Handler#stacks scopes correctly and returns Stack.none for unmatched repository" do
  handler = Shipit::Webhooks::Handlers::StatusHandler.new(
    'repository' => { 'full_name' => 'no/such-repo' },
    'sha' => 'a' * 40,
    'state' => 'success'
  )
  assert_equal Shipit::Stack.none, handler.send(:stacks)
end

test "StatusHandler#process mutates a commit belonging to an unrelated repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'b' * 40, author: nil)

  # attacker's payload claims a different repository but reuses victim's commit sha
  payload = {
    'repository' => { 'full_name' => 'attacker/unrelated-repo' },
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker'
  }

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
The first test proves `Handler#stacks` correctly isolates by repository. The second proves `StatusHandler#process` writes to the victim commit despite the payload naming an unrelated repository, confirming the defect is isolated to `StatusHandler#process`.
