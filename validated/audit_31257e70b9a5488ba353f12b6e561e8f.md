### Title
Cross-repository status forgery leading to unauthorized deploy via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `WebhooksController` verifies a webhook's HMAC signature using the `GitHubApp` config selected by `repository_owner` (the org named in `repository.owner.login`/`organization.login` of the payload), but the `StatusHandler` that then acts on the payload does not verify that the signed/authenticated organization actually owns the repository/stack whose commit is being updated. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/webhook secret to check against using only the organization named inside the payload itself: [1](#0-0) [2](#0-1) 

This scheme is designed for multi-tenant deployments where each GitHub organization configures its own `app_id`/`webhook_secret` (see `config/secrets.development.shopify.yml` showing multiple orgs each with independent `webhook_secret`s). Because signature verification only proves "this request was HMAC-signed with organization `X`'s webhook secret," it says nothing about which repository the *content* of the payload targets, other than that `repository.owner.login` (used purely for secret selection) matches `X`.

The `StatusHandler`, however, does not use `repository.full_name`/owner at all to scope its effect — it looks up commits **globally** by SHA across the entire installation: [3](#0-2) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` has no `stack`/`repository` filter, unlike `Handler#stacks`/`Handler#repository_name` used by other handlers (`PushHandler`, etc.) which do scope to `Repository.from_github_repo_name(repository_name)`: [4](#0-3) 

Consequently, any organization `X` that has legitimately onboarded its own GitHub App/webhook secret into this Shipit instance (an ordinary, unprivileged act for a self-service multi-org Shipit deployment) can send a `status` event whose `repository.owner.login` is `X` (so it passes signature verification against `X`'s secret) but whose `sha`/`state`/`context` target a commit that actually belongs to a completely different organization's/repository's stack `Y`. `Commit.create_status_from_github!` will happily record a forged "success" status against `Y`'s commit.

### Impact Explanation
`Commit#deployable?` is gated by CI status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `status` is derived from `statuses_and_check_runs` (which includes forged `Status` records injected by `StatusHandler`): [5](#0-4) [6](#0-5) 

Forging a passing status on another organization's commit can make an otherwise CI-failing or CI-pending commit appear `deployable?`, and `add_status` even schedules merges/continuous delivery on state transitions: `stack.schedule_merges if new_status.pending? || new_status.success?` and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?`: [7](#0-6) [8](#0-7) 

This can cause an unauthorized/automatic deploy or merge to proceed on a stack that belongs to an org the attacker has no legitimate access to, matching the required Critical impact bucket ("unauthorized deploy, rollback or merge") and crossing a repository trust boundary the webhook signature was supposed to enforce.

### Likelihood Explanation
Requires only that the attacker legitimately controls one organization's own `webhook_secret`/GitHub App entry configured in a multi-tenant Shipit instance (a normal, unprivileged operator of their own org, not requiring any Shipit session, `ApiClient` token, or repository write access on the victim org) and knowledge/guessability of a target commit SHA on another tracked stack (commit SHAs are often public, e.g. via GitHub UI/API, PRs, CI logs). No collusion with the victim org and no privileged Shipit credentials are needed — only sending a crafted HTTP POST to `/webhooks` with a valid signature for the attacker's own configured org.

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already do so) to commits belonging to the repository named in the payload, consistent with `Handler#stacks`/`Handler#repository_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of unscoped `Commit.where(sha: params.sha)`. Additionally, cross-check that `repository_owner` used for signature verification matches `repository.full_name`'s owner before dispatching to handlers.

### Proof of Concept
1. Configure Shipit as multi-org (per `docs/setup.md`/`config/secrets.development.shopify.yml`): org `attacker-org` and victim org `victim-org` both have independent GitHub Apps/`webhook_secret`s registered in this single Shipit instance, each tracking their own stacks.
2. Attacker knows `attacker-org`'s own `webhook_secret` (they configured it) and the SHA of a commit belonging to a `victim-org` stack (public commit SHA, e.g. from a PR).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, `X-Hub-Signature` computed as `HMAC-SHA1(attacker-org's webhook_secret, raw_body)`, and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant-repo" }
}
```
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — globally finds the victim commit and calls `create_status_from_github!`, injecting a forged "success" status onto `victim-org`'s commit, potentially making it `deployable?` and triggering `schedule_merges`/`ContinuousDeliveryJob`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
