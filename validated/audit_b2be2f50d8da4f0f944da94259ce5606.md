### Title
Webhook signature verified against attacker-chosen organization while a different organization's repository is acted upon (organization/repository binding break) - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC signature against using an attacker-supplied field from the unparsed request body, while the downstream event handlers select the actual `Stack`/`Repository` to mutate using a *different*, independently-controlled field of the same body. Nothing binds the two, allowing a party who legitimately controls one onboarded GitHub organization's webhook secret to forge a payload that is "signed" by their own organization but whose repository/stack target belongs to a different organization on the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification purely from request content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves this attacker-supplied string to a per-organization app configuration (used in the documented "Using Multiple GitHub Applications" mode) and returns a `GitHubApp` scoped to that organization's `webhook_secret`: [3](#0-2) 

Verification itself is a straightforward HMAC-over-raw-body check using that resolved organization's secret: [4](#0-3) 

Once `head(422)` is *not* triggered, the full raw JSON body is parsed and dispatched, unmodified, to event handlers: [5](#0-4) 

However, the handlers do not use `repository.owner.login` (the field that determined which secret validated the signature) to select the target. They use a separate field, `repository.full_name`, to look up the repository/stack that will actually be mutated: [6](#0-5) 

For example `PushHandler#process` syncs and deploys against the stacks resolved from that (independently-controlled) `full_name`: [7](#0-6) 

The same pattern (locating the acted-upon repository via `params.repository.full_name`, decoupled from the field used for signature routing) recurs across pull-request handlers: [8](#0-7) [9](#0-8) 

The trust binding that should hold is: **organization whose secret validated the request == organization that owns the repository being written to**. This binding is never enforced. `repository.owner.login` and `repository.full_name`'s owner segment are two independent JSON fields inside the same signed byte-string; a valid HMAC only proves the bytes weren't tampered with by a party lacking the resolved organization's secret — it says nothing about internal consistency between these two fields.

### Impact Explanation
In a Shipit installation configured for multiple GitHub organizations (per `docs/setup.md`, "Using Multiple GitHub Applications"), any party who legitimately administers/controls one onboarded organization's GitHub App (and therefore knows that org's `webhook_secret`) can produce a validly-signed webhook payload whose `repository.owner.login` is set to their own organization (satisfying `verify_signature`) but whose `repository.full_name` names a repository belonging to a *different* onboarded organization. The push handler will then locate that other organization's `Stack` and trigger `GithubSyncJob`/deploy processing; pull-request handlers will archive/unarchive or create review stacks against that other organization's repository. This is a cross-organization/cross-repository write achieved without ever holding an `ApiClient` token, a Shipit session, or the target organization's own webhook secret — an unauthorized deploy/rollback/state-mutation surface across organization boundaries.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported) and requires the attacker to control the webhook secret of at least one onboarded organization — a realistic scenario since organizations are typically onboarded with less trust than "administrator of the whole Shipit instance." No Shipit credentials, GitHub App private key, or repository push access to the *target* organization are needed.

### Recommendation
Bind the two fields explicitly: after `verify_webhook_signature` succeeds, re-derive/require that `repository.full_name`'s owner segment (or `organization.login` for org-scoped events) matches the `repository_owner` value used to select the verifying `GitHubApp`, and reject (422) on mismatch, before dispatching to any handler.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-administered GitHub App, secret known to attacker) and `orgB` (victim, has a Stack tracking `orgB/victim-repo`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Attacker signs the raw body with `orgA`'s known `webhook_secret` using `sha1=HMAC-SHA1(secret, body)` and sends it as `X-Hub-Signature`, with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` = `orgA`, fetches `orgA`'s `GitHubApp`, and the signature validates.
5. `PushHandler` resolves the stack via `payload.dig('repository','full_name')` = `orgB/victim-repo` and enqueues `GithubSyncJob` for `orgB`'s stack, even though only `orgA`'s secret was ever proven.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
