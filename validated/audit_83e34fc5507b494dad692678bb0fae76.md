Based on my investigation, I found a concrete, in-scope analog of the reported bug class in Shipit's webhook signature verification.

### Title
Webhook signature verified against `repository.owner.login`/`organization.login` used only for secret selection, while `MembershipHandler` trusts a *different, unchecked* `organization.login` field to grant `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which tenant's `webhook_secret` to use for HMAC verification from `repository.owner.login` (falling back to `organization.login`) taken from the untrusted JSON body itself. Once the signature check passes, `MembershipHandler` re-reads a *separate* `organization.login` field from that same body to decide which GitHub organization's team is being modified, with no check that this value matches the organization whose secret actually validated the signature. This breaks the equality: `organization_whose_secret_verified_signature == organization_whose_team_state_is_written`.

### Finding Description
`repository_owner` picks the HMAC key/organization purely from attacker-controlled JSON: [1](#0-0) 

That value is fed into `Shipit.github(organization: repository_owner)` to fetch the corresponding `GithubApp` and verify the signature: [2](#0-1) 

`verify_webhook_signature` simply HMACs the raw body against the secret for whichever organization was selected: [3](#0-2) 

Once verified, the `membership` event is dispatched to `MembershipHandler`, which reads a **different key**, `organization.login`, from the very same payload to decide which team/organization gets the membership change - and never cross-checks it against `repository_owner`/the org whose secret validated the request: [4](#0-3) 

`Team.find_or_create_by!` matches purely on `github_id`, and `add_member`/`members.delete` mutate the `memberships` join table with no re-verification against GitHub's actual team roster: [5](#0-4) 

Local team membership rows are exactly what gate application access: [6](#0-5) 

The test fixtures confirm both `repository.owner.login` and `organization.login` are independent, attacker-suppliable JSON keys within the same webhook body, with no linkage enforced between them: [7](#0-6) 

### Impact Explanation
In any Shipit deployment configured for multiple GitHub organizations (as the engine explicitly supports, see `config/secrets.development.shopify.yml` listing several orgs each with independent `webhook_secret`), a party who legitimately controls (or can rotate) the `webhook_secret` for **one** low-value tenant organization can forge a `membership` webhook whose `repository.owner.login` names their own organization (so the signature check passes with the secret they know) but whose `organization.login`/`team.id` names a **different, high-value** target organization's team. `MembershipHandler` will happily create/find that target team locally and add an arbitrary GitHub login as a member of it. Since `User#authorized?` only consults the local `memberships` table against `Shipit.github_teams`, this grants that attacker-controlled account full authenticated access to the Shipit UI/actions gated by that team - i.e., escalation into `Shipit.github_teams` authorization, satisfying the report's "High" impact bar.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it only checks the forgeable HMAC), and cross-organization confusion requires nothing more than administrative control of any single tenant org's webhook secret already onboarded to the same Shipit instance - no GitHub App private key, no Shipit session, and no privilege on the victim organization is needed. This mirrors the reported bug class exactly: code assumes a value used for a privileged write (`organization.login`) is bound to the value that was actually authenticated (`repository_owner`), but this binding is never checked.

### Recommendation
In `MembershipHandler` (and any other handler that reads an org identifier from the payload for privileged writes), require that `params.organization.login` (or `params.repository.owner.login`, as applicable) equals the `repository_owner`/organization value that was actually used to select the webhook secret in `WebhooksController#verify_signature`, rejecting the request otherwise. More generally, `verify_signature` should pass the verified organization identity down to handlers rather than letting handlers re-derive it from independent, unauthenticated payload fields.

### Proof of Concept
1. Attacker is (or becomes) the legitimate administrator of GitHub organization `org-b`, which is configured as a tenant in this shared Shipit instance with a known `webhook_secret`.
2. Attacker crafts a JSON body:
```json
{
  "action": "added",
  "team": { "id": 999999, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/999999" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "org-b" } }
}
```
   (`team.id` set to the real `github_id` of a team listed in `Shipit.github_teams` for the victim org `shopify`, discoverable via GitHub's public/authorized API for that team or by observing an existing `Team` row.)
3. Attacker computes `X-Hub-Signature` using `org-b`'s known `webhook_secret` over the raw JSON body, and POSTs it to `/webhooks` with header `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"org-b"`, fetches `org-b`'s `GithubApp`, and the signature verifies successfully.
5. `MembershipHandler#process` runs, finds/creates the `Team` matching `github_id: 999999` (the real Shopify team) and sets/uses `organization: "shopify"`, then calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
6. The attacker's `User` record now has a `Membership` in the Shopify team; logging into Shipit via GitHub OAuth as `attacker-github-login`, `User#authorized?` returns true because a matching team id exists in `Shipit.github_teams`, granting full authenticated access despite the attacker having no real relationship to `shopify`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```

```ruby
    class << self
      def find_or_create_by_handle(handle)
        organization, slug = handle.split('/').map(&:downcase)
        find_by(organization:, slug:) || fetch_and_create_from_github(organization, slug)
      end

      def fetch_and_create_from_github(organization, slug)
        return unless github_team = find_team_on_github(organization, slug)

        create!(github_team:, organization:)
      end

      def find_team_on_github(organization, slug)
        gh_api = Shipit.github(organization:).api
        teams = Shipit::OctokitIterator.new(github_api: gh_api) { gh_api.org_teams(organization, per_page: 100) }
        teams.find { |t| t.slug == slug }
      rescue Octokit::NotFound
      end
    end

    def handle
      "#{organization}/#{slug}"
    end

    def add_member(member)
      members.append(member) unless members.include?(member)
    end
```
