## Confirmed root cause

`Shipit` supports a **multi-organization GitHub App configuration**, where each organization key under `secrets.github` (e.g. `OrgOne`, `OrgTwo`) can have its own independent `webhook_secret` [1](#0-0) [2](#0-1) .

`WebhooksController#verify_signature` selects **which** org's `webhook_secret` to verify the raw request against solely from `repository.owner.login` (or `organization.login`) inside the *unverified, attacker-controlled* JSON body:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

Once the signature check passes (using the secret belonging to `repository_owner`), `create` re-parses the same raw body and dispatches to handlers, e.g. `PushHandler`, which independently resolves the target repository/stacks from a **different field**, `repository.full_name`:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [4](#0-3) [5](#0-4) 

`repository.owner.login` (used to pick the trusted secret) and `repository.full_name` (used to pick the repository actually acted upon) are two **independent JSON fields with no cross-check** that they agree. GitHub itself always keeps them consistent, but nothing in this engine enforces that — the signature only proves the *bytes* were signed by *some* organization's configured secret, not that the org whose secret validated the signature is the same org whose repository is subsequently written to.

## The broken binding

`organization authenticated by verify_signature` ≠ `repository resolved and mutated by the event handler`.

Any party who is a legitimate, unprivileged owner/admin of **one** org configured in this multi-tenant Shipit install (i.e., they know their own org's `webhook_secret`, which they legitimately configured on their own GitHub org's webhook settings — not a Shipit credential) can POST directly to `/webhooks` (bypassing GitHub) with:
- `repository.owner.login = "attacker-org"` (or `organization.login`) → makes `verify_signature` pick `attacker-org`'s secret, which they sign correctly, so the signature passes,
- `repository.full_name = "victim-org/some-repo"` → makes the handler operate on a stack/repository belonging to an org they have no relationship with.

For `push` events this triggers `stack.sync_github(expected_head_sha:)` on a stack in `victim-org` via `PushHandler` [5](#0-4) , i.e. **cross-organization writes into a stack the attacker does not control**, forged through a signature that was never computed with that stack's real secret. This is the "organization that authenticated versus the repository that is written" binding mismatch called out explicitly by the scan rules.

Note: this requires the Shipit deployment to actually be configured with **multiple** organizations each having distinct webhook secrets configured on GitHub (the `github_organizations`/`github_app_config` multi-org path) [6](#0-5) ; in the common single-org deployment (`github_default_organization` nil, one shared secret) this analog collapses because there is only one secret to select from, so it can't be confused with another org's secret.

### Title
Cross-organization webhook authorization bypass via unchecked `repository.owner.login` vs `repository.full_name` mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login`/`organization.login`, but the event handlers that subsequently act on the payload resolve the target repository from the unrelated `repository.full_name` field. Because these two fields are never cross-validated, an attacker who legitimately controls one configured organization's webhook secret can forge a signed payload that authenticates as their own org while directing writes (e.g. triggering a `GithubSyncJob`/deploy sync) at a stack belonging to a different organization in the same Shipit install.

### Finding Description
`verify_signature` picks `Shipit.github(organization: repository_owner)` from the raw, unverified body [7](#0-6) , using `repository_owner` derived from `params.dig('repository','owner','login')` [8](#0-7) . Handler resolution instead uses `payload.dig('repository','full_name')` [9](#0-8) . `Shipit.github_app_config` shows organizations are independently keyed with their own `webhook_secret` in `secrets.github` [10](#0-9) , confirmed by the dummy multi-org fixture with two distinct `webhook_secret`/private key sets [2](#0-1) .

### Impact Explanation
This crosses the "unauthorized deploy" impact bar: an attacker with legitimate access to one org's webhook secret can spoof `push`/`status`/`check_suite` events that resolve to a stack under a different organization, causing that stack to sync to an attacker-chosen `expected_head_sha` or record spoofed CI statuses/check runs, all without any Shipit session or GitHub App credential for the victim org.

### Likelihood Explanation
Requires the operator to run Shipit with the multi-organization GitHub App configuration (`Shipit.github_organizations` with per-org secrets) and requires the attacker to legitimately administer at least one of the configured orgs. This is plausible for shared/multi-tenant Shipit deployments serving multiple GitHub orgs, but not applicable to the common single-org setup.

### Recommendation
After signature verification, require that the organization whose secret validated the signature matches the owner encoded in `repository.full_name` (and `organization.login` for org-scoped events) before dispatching to handlers, rejecting the request otherwise.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls `OrgA` and knows `OrgA`'s `webhook_secret` (legitimately, from configuring their own org's GitHub webhook).
3. Attacker crafts a `push` payload with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"`, signs it with `OrgA`'s secret, and POSTs it to `/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and the signature validates successfully.
5. `PushHandler` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)`, triggering a sync/deploy action on `OrgB`'s stack despite the signature never having been computed with `OrgB`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
