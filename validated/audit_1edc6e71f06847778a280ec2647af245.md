### Title
Cross-organization webhook event forgery via authentication/repository binding mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate an inbound webhook HMAC against based on `repository_owner` — a value taken from the *unverified* JSON body (`repository.owner.login`, or `organization.login`) — but the handlers that actually execute the event's side effects (which stack/repository gets a sync, status, or PR update) resolve their target from a completely different field, `repository.full_name`. Nothing ties the two together, so a caller who legitimately possesses the `webhook_secret` for *one* configured organization (Org A, in a Shipit instance hosting multiple GitHub Apps/organizations) can forge a payload whose `repository.owner.login` says "Org A" (to pass signature verification with Org A's secret) while `repository.full_name` points at an unrelated Org B repository, causing Org B's stacks to be acted on using a signature that never authenticated for Org B.

### Finding Description
`verify_signature` picks the `GitHubApp` instance — and therefore the `webhook_secret` used for HMAC verification — purely from the payload's declared owner: [1](#0-0) [2](#0-1) 

Once verification passes, the raw JSON body is handed, unmodified, to every registered handler for the event: [3](#0-2) 

The base `Handler` class (used by `PushHandler`, `StatusHandler`, `PullRequest::*` handlers, etc.) resolves the actual target repository/stacks using `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler#process` then triggers a real side effect (`stack.sync_github`) on whatever stack that lookup returns: [5](#0-4) 

`GitHubApp` instances are configured per-organization (`Shipit.github(organization: ...)`), confirming that `webhook_secret` is a per-tenant credential in multi-org deployments: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization whose webhook_secret validated the HMAC (repository.owner.login / organization.login)` == `organization owning the repository whose stacks are mutated (repository.full_name)`.

Before the attack: for a genuine GitHub-delivered webhook, `repository.owner.login` and `repository.full_name`'s owner segment are always the same value, so the binding holds implicitly and is never checked explicitly.

After the attack: an attacker who administers a legitimate, Shipit-configured GitHub organization "Org A" knows Org A's `webhook_secret` (it's a value they configured themselves when installing their own GitHub App). They can compute a valid HMAC over an arbitrary JSON body using that secret, set `repository.owner.login` (or `organization.login`) to `"Org A"` so `verify_signature` selects Org A's secret and the signature checks out, while setting `repository.full_name` to `"Org B/victim-repo"` so the handler acts on Org B's stack. `verify_signature` never checks that the two fields agree.

### Impact Explanation
This lets a tenant of a shared, multi-organization Shipit instance (a legitimate but unprivileged party with respect to other tenants) forge events on behalf of any other organization/repository/stack hosted on the same instance:
- `push` events force `Stack#sync_github` on an arbitrary victim stack.
- `status` events fabricate commit statuses on arbitrary commits/repositories (as exercised by the `:state create a Status` test path), which Shipit uses to gate whether a commit is "deployable." Poisoning this can make an unrelated, unauthorized commit appear green/deployable to operators or automation on Org B's stack.
- `pull_request`/`membership` handlers can similarly be triggered against the wrong repository/org.

This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope, and can lead to unauthorized state changes/deploy-gating manipulation on a repository the caller was never authenticated for — satisfying the High-impact bar for escalation into stack state that isn't the caller's own.

### Likelihood Explanation
Requires only: (1) the target Shipit instance hosts more than one GitHub organization/App (a documented, supported configuration), and (2) the attacker administers one of those organizations' GitHub App installations (so they legitimately know that org's own `webhook_secret`) but has no access to the victim organization. No Shipit session, `ApiClient` token, or GitHub write access to the victim repo is required — only an HTTP POST to the public `/webhooks` endpoint with a crafted, self-signed body. This is a realistic scenario for any shared/multi-tenant Shipit deployment.

### Recommendation
`verify_signature` should not derive the verification key solely from attacker-controlled JSON fields without cross-checking consistency, and handlers should not trust `repository.full_name` independently of the field used for authentication. Concretely: after selecting the organization/secret via `repository_owner`, require that `repository.full_name`'s owner segment (and any `organization.login`) match `repository_owner` before dispatching to handlers; reject the webhook (422) on mismatch.

### Proof of Concept
1. Shipit is configured with two orgs, e.g. `orgA` and `orgB`, each with its own GitHub App and `webhook_secret` (per `lib/shipit/github_app.rb#initialize`), and the same Shipit instance also hosts a stack for `orgB/victim-repo`.
2. Attacker administers `orgA`'s GitHub App and therefore knows `orgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'orgA')` (from `repository.owner.login`), and the HMAC validates successfully against `orgA`'s secret. [1](#0-0) 
6. `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"orgB/victim-repo"`, and calls `stack.sync_github` on `orgB`'s stack — despite the request never having been authenticated for `orgB`. [4](#0-3) [5](#0-4)
