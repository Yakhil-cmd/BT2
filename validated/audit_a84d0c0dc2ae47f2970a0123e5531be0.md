The Shardeum report describes a JavaScript/V8-specific defect: `parseInt()` on an out-of-range string produces a value where subsequent `i++` no longer changes the float due to IEEE-754 precision loss, so a `for` loop never terminates. This is an artifact of untyped/floating-point loop counters in a dynamically-typed environment coupled with a missing bounds check on user-supplied `fromBlock`/`toBlock` before using them as loop bounds.

Polkadot SDK does not have an analogous entry point. The equivalent block-range RPC/CLI code paths use statically-typed, fixed-width integers (`u64`, `NumberFor<B>`, etc.) rather than an unbounded double-precision float, so there is no "increment that never changes the value" failure mode — Rust's fixed-width integer arithmetic has well-defined (and in these code paths, checked/saturating) overflow/wraparound semantics, not the silent precision collapse that afflicts JS numbers near `Number.MAX_SAFE_INTEGER`. Furthermore, every block-range handler found already validates `from <= to` before iterating: [1](#0-0) [2](#0-1) [3](#0-2) 

These paths reject inverted/invalid ranges up front rather than looping on unchecked attacker-controlled bounds, and none of them are reachable via an unprivileged signed extrinsic, XCM message, or contract call — they are RPC/CLI/node-internal sync utilities, not runtime dispatch surfaces. There is no unsigned-extrinsic or public-proof entry point in FRAME whose dispatch logic runs an attacker-controlled unbounded loop counter derived from an unchecked numeric parse. This class of bug (unbounded loop / resource exhaustion from unchecked loop bounds) is also explicitly excluded from consideration per the assessment criteria, and no genuine FRAME/XCM analog with a measurable state-integrity or fund-loss impact was found.
