### Title
Missing authentication check on device "sign" message allows any paired correspondent to trigger a local signing-confirmation popup and probe local wallet/address ownership - (File: wallet.js)

### Summary
The `"sign"` subject handler in `handleMessageFromHub` (`wallet.js`) validates the shape and hashes of the unsigned unit but never confirms that `from_address` (the device that sent the `"sign"` request) is actually a legitimate cosigner of `body.address` before invoking `findAddress`'s `ifLocal` branch, which fires `callbacks.ifOk()` and the `"signing_request"` event that in most wallet UIs pops a signing confirmation dialog to the user.

### Finding Description
`findAddress` (`wallet.js:1233`) resolves `body.address`/`body.signing_path` to `ifLocal(objAddress)` whenever the signing path is controlled by a key on this device, regardless of who requested the signature. Inside the `"sign"` case (`wallet.js:247-339`), the `ifLocal` handler contains an explicit comment noting that the original design intended to verify `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?` to confirm the sender is a genuine cosigner of the wallet, but this check is commented out with the justification that it "would make multilateral signing impossible." As a result, `ifLocal` unconditionally calls `callbacks.ifOk()` and emits `"signing_request"` for *any* device that is paired with the victim (a correspondent), for *any* local address the victim controls in *any* wallet — even wallets/addresses the requesting device was never a member of.

This differs from the `ifRemote` branch a few lines below (`wallet.js:374-378`), which does check `other_device_addresses.includes(from_address)` and rejects requests from devices not listed as cosigners. The `ifLocal` branch has no equivalent authorization check.

### Impact Explanation
Any correspondent device (a device paired with the victim, which is a low-privilege relationship — pairing only requires exchanging a pairing code) can send fabricated `"sign"` requests for arbitrary local addresses/signing paths that happen to be controlled by the victim's own device, causing:
- Repeated unsolicited signing-confirmation popups (denial-of-service/annoyance and potential phishing vector: attacker crafts a `signed_message`/`unsigned_unit` designed to look benign but authorizes an unwanted spend if the victim user is tricked into approving it in the popup).
- Because `ifLocal` accepts before any ownership/authorization validation, an attacker can probe which of their crafted `{address, signing_path}` pairs resolve to real local keys on the victim's device (information leak about wallet composition), since a `signing_request` event/error behavior differs from the `ifUnknownAddress` path.
- If a victim's UI auto-approves multilateral/multisig-looking requests under some configurations, this is a path toward unauthorized signing of a spend that the victim did not initiate, i.e., unauthorized spending risk, since the check that would have enforced "sender is cosigner of this address" was deliberately removed.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to already be a paired correspondent (pairing is a lightweight, self-service process reachable by any wallet/device), and successful exploitation of the popup UX into an actual signature requires user interaction in most wallet clients. However, the repeated-request/probing and popup-spam impact requires no user cooperation at all and is reliably reachable by any paired device.

### Recommendation
Restore the authorization check in the `ifLocal` branch of the `"sign"` handler: before calling `callbacks.ifOk()`/emitting `"signing_request"`, verify that `from_address` is actually a member of `objAddress.wallet` (e.g., re-enable the `SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?` check), or otherwise verify `from_address` is a legitimate cosigner for the specific `signing_path` being requested, mirroring the check already present in the `ifRemote` branch.

### Proof of Concept
1. Attacker device pairs with victim device (via a valid pairing code, a normal wallet operation with no special privilege).
2. Attacker sends victim's hub a `hub/deliver` message addressed to the victim with `json.subject = "sign"` and `json.body = {address: <victim's real local address>, signing_path: "r", unsigned_unit: <fabricated valid-looking unit authored by that address>}`.
3. On the victim's device, `handleMessageFromHub` routes to the `"sign"` case; validation of the unit shape passes; `findAddress` resolves the address to `ifLocal` (since it's genuinely local to the victim).
4. `ifLocal` calls `callbacks.ifOk()` and emits `"signing_request"` without ever checking that the attacker device is a cosigner/member of that wallet, triggering the victim's UI confirmation flow for a transaction the attacker fully controls the content of.
