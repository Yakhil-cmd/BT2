### Title
Uncaught exception in `chash.isChashValid` on malformed base64 c-hash causes unhandled-exception crash - (File: chash.js)

### Summary
`chash.js`'s `isChashValid()` only wraps the base32/base64 *decode* step in a `try/catch`; the subsequent length-dependent processing (`buffer2bin`, `separateIntoCleanDataAndChecksum`) is executed unprotected and can throw an uncaught `Error` when the decoded buffer does not have the exact expected bit-length. This is analogous to the TCC bug class in the report: a parser performs a fixed-size decode/transform on attacker-supplied encoded data without validating that the intermediate buffer actually matches the length the downstream code assumes, and the "out of bounds" condition (here, a length mismatch that violates an internal invariant) is only caught in the wrong place.

### Finding Description
`isChashValid(encoded)` in [1](#0-0)  does:
```
if (encoded_len !== 32 && encoded_len !== 48) throw Error(...);
try { var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64'); }
catch(e){ return false; }
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);   // <-- unprotected
```
`separateIntoCleanDataAndChecksum` in [2](#0-1)  throws `Error("bad length=...")` whenever the bit-length of the decoded buffer is neither 160 nor 288.

For the 48-character (288-bit / base64) branch, `Buffer.from(str, 'base64')` in Node.js is lenient: it does **not** throw on invalid base64 characters — it silently stops decoding at the first non-alphabet character and returns a shorter buffer. Because `isChashValid` never validates that `encoded` actually consists of valid base64/base32 characters (it only checks `encoded.length === 48`), an attacker can supply a 48-character string containing characters outside the base64 alphabet. `Buffer.from` returns a buffer that is not exactly 36 bytes (288 bits), `buffer2bin` produces a bitstring of the wrong length, and `separateIntoCleanDataAndChecksum` then throws — **outside** the `try/catch`, propagating an uncaught exception out of `isChashValid`.

This function is the single validator of every chash (address or asset-definition chash) in the codebase, reached via `validation_utils.isValidChash` / `isValidAddressAnyCase` [3](#0-2) , which is used in `validation.js` and by 288-bit definition-chash checks used for asset definitions and shared/multisig addresses.

### Impact Explanation
Any code path that calls `isChashValid`/`isValidChash` on unsanitized, attacker-supplied 48-character strings (e.g., an "any case" chash/definition-chash check on a value taken from a posted unit, AA trigger, or message) can trigger an unhandled JavaScript exception during synchronous validation. Depending on whether the calling stack has a surrounding try/catch, this can crash the Node.js process handling unit/joint validation, which — if it affects hub/full-node validation of incoming units — can make the affected node unable to validate/confirm new units (denial of service on validation), satisfying the "network unable to confirm new units" impact class.

### Likelihood Explanation
Medium. The 32-character (base32) branch is generally safe because `isValidAddress` restricts the alphabet to `[A-Z2-7]` before calling `isChashValid`, and 32 characters of any content still decode to exactly 20 bytes with the `thirty-two` library. The risk is concentrated in the 48-character (base64/definition-chash, 288-bit) branch, which is exercised by asset-definition-chash validation and other 288-bit-chash checks that do not pre-filter the input to the base64 alphabet before calling `isChashValid`. I was not able to fully enumerate, within the remaining tool budget, every call site that passes fully unsanitized attacker-controlled strings into the 48-character branch versus sites that pre-validate charset/format (e.g. via `isValidBase64`) before calling it — this is the main residual uncertainty.

### Recommendation
- Wrap the entire body of `isChashValid` (decode + `buffer2bin` + `separateIntoCleanDataAndChecksum` + `bin2buffer`) in a single `try/catch` that returns `false` on any error, instead of only guarding the decode call.
- Additionally validate that the decoded buffer length exactly matches the expected byte length (20 or 36 bytes) before proceeding, returning `false` early otherwise.

### Proof of Concept
```js
const chash = require('./chash.js');
// 48-char string containing a character outside the base64 alphabet ('!' at the end)
const malformed = 'AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA!';
console.log(chash.isChashValid(malformed)); // throws uncaught Error("bad length=...") instead of returning false
```
This demonstrates the uncaught exception; whether it is reachable from a fully network-attacker-controlled value without any prior charset validation by the caller could not be exhaustively confirmed with the remaining investigation budget.
