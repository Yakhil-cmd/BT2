## Title
Asset definer can permanently freeze all previously-attested holders' funds by replacing the `asset_attestors` list — ([File: validation.js])

## Summary
For any asset created with `spender_attested: true`, the asset's **definer** (the address that authored the `asset` definition unit — a normal, unprivileged unit poster who is simply the issuer of that particular asset) retains permanent, unilateral control over the attestor list via the `asset_attestors` message, with no on-chain check that the change preserves access for holders who already received the asset. Because validators only ever consult the *most recent* attestor list to decide whether an address is attested, a definer can post a new `asset_attestors` unit that swaps out all previous attestors. Every address whose attestation was only ever issued by the now-removed attestors instantly and irreversibly loses the ability to spend the spender-attested coins they already hold — with no `sweep` mechanism or fallback path to recover the value, exactly mirroring the `clearExtraRewards` bug class where a privileged-but-legitimate actor deletes state that other users' already-staked/received funds depend on.

## Finding Description
When an asset is defined with `spender_attested: true`, spending it requires the spender's address to appear in the `attestations` table, signed by an address currently listed as an attestor for that asset. The **current** attestor list is not versioned per-holder or per-coin — it is a single global, mutable value that only the definer controls and that is overwritten wholesale by `asset_attestors` messages: [1](#0-0) 

This validator only checks that the sender is the `definer_address` and that the new list is well-formed (`checkAttestorList`); it performs no check whatsoever regarding existing holders, previously-issued attestations, or funds already transferred under the old list.

When resolving "is this asset's spender attested," the storage layer always looks up the **latest** attestor-list unit only, discarding all history: [2](#0-1) 

And `filterAttestedAddresses` only counts an address as attested if it was attested by an address in `objAsset.arrAttestorAddresses`, i.e. the current list: [3](#0-2) 

Both the payment-input validation path and the payment-output validation path enforce this attestation check using only the current attestor set: [4](#0-3) [5](#0-4) 

Consequently: a user X receives (via a normal payment) some amount of a `spender_attested` asset while attestor A currently attests X. Later, the definer posts an `asset_attestors` message that replaces attestor A with attestor B (who never attests X). From that point forward, X's existing outputs of the asset become permanently unspendable — X's address is no longer "attested" per the current list, and no combination of already-existing on-chain attestations from the removed attestor helps, since only the latest list is consulted. There is no way for X, the removed attestor, or anyone else to reverse this or reclaim the value; it is functionally identical to the reported `clearExtraRewards` issue where the manager deletes reward metadata and strands funds that were already earned/staked by users, with no sweep function to recover them.

## Impact Explanation
This causes permanent, unrecoverable loss/freezing of user funds (AA fund loss/freezing / asset-holder fund loss) for a legitimate on-chain actor (the asset definer) acting entirely within their documented privileges (updating the attestor list is an intended, permissionless-to-definer feature). Any holder who received the asset under a previous attestor configuration can be frozen out at any time by a subsequent, ordinary `asset_attestors` unit, with the coins becoming permanently stuck at their address (visible on the DAG, but unspendable). This matches the accepted "Medium" pattern from the analog report: privileged-but-legitimate action stranding funds with no sweep path.

## Likelihood Explanation
Likelihood is high in scenarios where a definer changes attestors for any legitimate reason (e.g., replacing a compromised attestor, migrating attestation providers, or reducing attestor set), since the protocol provides no safeguard, warning, or grace mechanism for holders already possessing coins under the old configuration. This can happen accidentally (definer intends only to add/rotate future attestors) or maliciously (definer deliberately locks out disfavored holders), and requires only a single ordinary `asset_attestors` unit — no coordination with victims, no hub/network-level compromise, and no violation of consensus rules.

## Recommendation
- When updating the attestor list, require that spending validation additionally accept attestations valid **at the time the coin was received/issued** (i.e., pin the attestor set per-output at creation time), or
- Require the definer to prove that previously-attested addresses remain attested (or explicitly migrate them) before an `asset_attestors` update is accepted, or
- Provide an explicit recovery/sweep path (e.g., allow spending if attested by *any* attestor that was valid at any point up to the last ball) so that funds already distributed under an old attestor configuration are not orphaned by a later, unrelated attestor-list change.

## Proof of Concept
1. Definer D posts an `asset` message defining asset `ASSET` with `spender_attested: true` and initial `attestors: [A]`.
2. Attestor A posts an `attestation` for address X (`validation.js` "attestation" handling / `attestations` table).
3. D pays X some amount of `ASSET` via a normal `payment` message; this is accepted because X is attested by A, which is in the current attestor list (validation.js:2115-2122).
4. D posts a new `asset_attestors` message for `ASSET` setting `attestors: [B]` (validation.js:2829-2848 allows this unconditionally since D is `definer_address`).
5. `storage.readAsset`'s `addAttestorsIfNecessary` now resolves `arrAttestorAddresses = [B]` for `ASSET` (storage.js:1917-1946), and `filterAttestedAddresses` no longer counts X as attested, since A is not in `[B]` (storage.js:1960-1974).
6. X attempts to spend the previously received `ASSET` coins; `validatePayment` rejects with "none of the authors is attested" (validation.js:2115-2119), and there is no way for X to become attested again under the new list unless B independently chooses to attest X — which D fully controls by choosing B. X's funds are permanently frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(

		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
