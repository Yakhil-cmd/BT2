### Title
Fail-open rule evaluation in hookify's PreToolUse/PostToolUse/Stop hooks lets one malformed condition bypass all configured block rules - (File: `plugins/hookify/core/rule_engine.py`, `plugins/hookify/hooks/pretooluse.py`)

### Summary
The reported bug class is "a single per-item failure inside a non-isolated batch loop cascades into total batch failure, and the surrounding harness has no per-item try/catch." The closest analog in this repo is `hookify`'s hook executors (`pretooluse.py`, `posttooluse.py`, `stop.py`), which evaluate a *list* of user-defined security rules (`RuleEngine.evaluate_rules`) atomically: if evaluating any single rule/condition throws, the exception propagates out of the entire batch, is caught by a single top-level `except Exception` in the hook script, and the script **still exits 0 and effectively allows the tool call** — meaning any properly-functioning "block" rule elsewhere in the batch (e.g., a `rm -rf` blocker) is silently skipped instead of being enforced.

### Finding Description
`RuleEngine.evaluate_rules` loops over all loaded rules and calls `self._rule_matches(rule, input_data)` for each one with no per-rule isolation: [1](#0-0) 

`_rule_matches` calls `_check_condition` for every condition in the rule: [2](#0-1) 

`_check_condition` extracts a field value via `_extract_field` and then applies the operator. For `MultiEdit`, `_extract_field` assumes every element of `tool_input['edits']` is a dict and calls `.get()` on it without any exception handling: [3](#0-2) 

`_regex_match` is the only place that defensively catches an exception (`re.error`); every other operator path (`contains`, `equals`, `not_contains`, `starts_with`, `ends_with`) and `_extract_field`'s MultiEdit branch have no exception handling at all: [4](#0-3) 

If evaluating any one rule/condition raises an unhandled exception (e.g., `AttributeError` from a malformed `edits` entry), it propagates all the way out of `evaluate_rules` into the hook script, where the top-level handler treats *any* exception the same as "no rules matched" — it prints a generic error message and always `sys.exit(0)`, which Claude Code interprets as "allow": [5](#0-4) 

This mirrors the reported bug's root cause exactly: a batch of independent checks (Chainlink reports / hookify rules) is evaluated non-atomically-in-intent but atomically-in-implementation, and the umbrella error handler's fallback behavior (proceed / fail-open) is the opposite of what the batch was meant to enforce (validate and possibly block).

### Impact Explanation
If a project has multiple hookify rules configured — for example a `block-dangerous-rm` rule and an unrelated `warn-console-log` rule on `file`/`MultiEdit` events — and the unrelated rule's condition evaluation throws (via the `MultiEdit`/`edits` type-confusion path or any other future non-regex operator bug), the entire rule set for that hook invocation is discarded and the operation is allowed, including the dangerous command that the blocking rule was supposed to stop. This is a direct approval-bypass of a user-configured safety control (PreToolUse deny), not just a degraded UX.

### Likelihood Explanation
This requires (a) at least one hookify rule targeting `MultiEdit`/`file` events with a `content`/`new_text` field condition, and (b) `tool_input.edits` containing a non-dict element when the hook is invoked. I could not confirm in the indexed code whether Claude Code performs JSON-schema validation of `tool_input` (rejecting malformed `edits` arrays) before PreToolUse hooks run, or whether hooks see raw, unvalidated tool arguments. This is an important open question that materially affects likelihood; I was unable to locate the relevant tool-input validation/dispatch code in the indexed portion of this repo. Absent schema pre-validation, prompt injection or a misbehaving MCP tool that induces Claude to construct a malformed `MultiEdit` call would be sufficient to trigger it. The broader fail-open pattern (any uncaught exception during rule evaluation → allow) is unconditionally true regardless of this specific trigger, since it's a structural property of `rule_engine.py` + the hook scripts' generic `except Exception` handlers.

### Recommendation
- In `RuleEngine.evaluate_rules`/`_rule_matches`, wrap evaluation of each individual rule in its own try/except so one rule's failure does not skip evaluation of the remaining rules (analogous to the per-report `try/catch` isolation recommended in the source report).
- In `_extract_field`'s `MultiEdit` branch, guard against non-dict entries in `edits` (e.g., `e.get('new_string', '') if isinstance(e, dict) else ''`).
- Change the hook scripts' top-level exception handling so that a rule-evaluation failure defaults to **fail-safe** (e.g., re-raise as a blocking decision, or at least surface a clear "rule evaluation failed — no rules were enforced" warning to the user) rather than silently defaulting to allow.

### Proof of Concept
1. Configure two hookify rules in `.claude/`:
   - `hookify.block-rm.local.md` — `event: bash`, `pattern: rm\s+-rf`, `action: block`.
   - `hookify.warn-multiedit.local.md` — `event: file`, `tool_matcher: MultiEdit`, condition `field: content`, `operator: contains`, `pattern: TODO`.
2. Trigger a `MultiEdit` tool call whose `tool_input.edits` array contains a non-dict element (e.g., via a crafted/injected tool call if upstream validation does not reject it).
3. `posttooluse.py`/`pretooluse.py` calls `RuleEngine.evaluate_rules`, which reaches `_extract_field` for the `warn-multiedit` rule and raises `AttributeError: 'str' object has no attribute 'get'`.
4. The exception propagates out of `evaluate_rules`, is caught by the hook script's blanket `except Exception`, and the script exits 0 with only a generic `systemMessage`, allowing the operation.
5. Separately, if the *same batch* also needed to evaluate `block-rm` for a concurrent/queued `Bash` invocation in the same rule set, that block would similarly never be reached whenever any earlier rule's evaluation throws — demonstrating the batch-wide fail-open.

**Note on uncertainty:** I could not verify (within index limits) whether Claude Code's core dispatch layer validates `tool_input` against each tool's JSON schema before invoking hooks — if it does, the specific `MultiEdit`/`edits` trigger in step 2 would be blocked upstream, though the underlying fail-open architecture in `rule_engine.py` and the hook scripts would remain a latent, exploitable design flaw for any future/other exception source (e.g., a bug in a custom regex, or a new operator addition). Confirming the tool-input validation path would require access to Claude Code's core tool-dispatch source, which does not appear indexed in this repo — starting a full Devin session against the complete codebase would let this be checked directly.

    def _regex_match(self, pattern: str, text: str) -> bool:
        """Check if pattern matches text using regex.

        Args:
            pattern: Regex pattern

        Returns:
            True if pattern matches
        """

            # Use cached compiled regex (LRU cache with max 128 patterns)
