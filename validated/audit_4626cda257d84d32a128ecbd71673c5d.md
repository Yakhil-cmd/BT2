### Title
`StatusHandler#process` updates commit statuses by SHA alone with no repository/stack scoping, allowing cross-repository commit-status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely via `Commit.where(sha: params.sha)` and never calls `#stacks` or `#repository_name`, unlike every other repository-scoped handler (`PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers, which all filter through `stacks`). Because a webhook's own `repository.full_name` is never checked against the commit being mutated, a `status` event emitted from an attacker-owned repository can flip the CI status of a commit that also exists (by identical SHA) in an unrelated victim's stack.

### Finding Description
The claimed binding is: `StatusHandler#process` must satisfy `repository_name(payload) == stack.repository.full_name` for every `Commit` it mutates, the same invariant enforced in `PushHandler#process` (`stacks.not_archived.where(branch:)`, `app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`, `app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`). Both call the base `Handler#stacks` method, which scopes to `Repository.from_github_repo_name(repository_name)&.stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`).

`StatusHandler#process`, however, does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This never touches `payload['repository']['full_name']`, so the incoming webhook's declared repository is completely irrelevant to which `Commit` rows get updated — the query matches any `Commit` in the entire Shipit database sharing that SHA, across every stack/repository/tenant.

Per the audit's own threat model, an attacker "can push to a fork... and emit webhooks from a repository they own." Such an attacker can install/configure the same GitHub App/webhook target on their own repository and receive a genuinely, correctly-signed `status` event for it (signature verification is per-app, not per-repository-content, so this passes `verify_signature`/`GitHubApp#verify_webhook_signature` with no forgery needed). If the attacker forks a victim's public repository (or otherwise obtains an identical commit object, e.g. via cherry-pick/rebase producing the same tree+parent+message hash) and pushes it into their own repo, the resulting commit has the exact same SHA as the one recorded against the victim's stack. The attacker then sets an arbitrary status (`state`, `context`, `description`) on that SHA in their own repo (via the GitHub API, using only their own token), triggering a legitimately-signed webhook whose `payload['repository']['full_name']` is the attacker's repo but whose `sha` collides with the victim's tracked commit. `StatusHandler` updates the `CommitStatus` for that SHA regardless of which repository actually owns it in Shipit's data model.

None of the existing guards prevent this: `verify_signature` only proves the event came from GitHub for *some* installation, not that the declared repository owns the referenced commit; `ExplicitParameters` validates payload shape, not repository/commit ownership; and `drop_unhandled_event` is irrelevant since `status` is a handled event type.

### Impact Explanation
A commit status forged this way is written via `Commit#create_status_from_github!` into the victim's `CommitStatus` table, which Shipit uses to gate merge/deploy readiness (statuses feed into stack "ready" checks). An attacker can therefore mark an unrelated victim's commit as passing CI/required checks without any access to the victim's repository, tokens, or Shipit account — this is a cross-tenant integrity violation matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any commit SHA the attacker can reproduce (any commit reachable in a public repo, or any commit the attacker independently authors that happens to match), across arbitrarily many victim stacks that happen to track that commit.

### Likelihood Explanation
Preconditions: the attacker needs (1) a repository they own with the webhook/App configured to deliver `status` events to the Shipit host (self-service, no privilege needed), and (2) the ability to produce a commit whose SHA matches one tracked in a target victim stack — trivially achievable by forking/cloning a public repo and pushing the same objects, or by controlling both ends of a shared commit history. No secrets, sessions, or GitHub App keys are required. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve the webhook's `repository_name` to its `Repository`/`stacks`, and only update `Commit` rows that belong to a stack of that repository (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or an equivalent scoped query), rejecting/ignoring commits whose SHA collides but whose owning repository does not match the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "StatusHandler does not scope commit lookup by repository" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, author: shipit_users(:bob))

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }, # not victim's repo
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert victim_commit.statuses.exists?(context: 'ci/attacker', state: 'success'),
    "commit belonging to victim/shipit was mutated by a webhook declaring an unrelated repository"
end
```
This demonstrates that `StatusHandler` writes a `CommitStatus` for `victim_stack`'s commit despite the payload declaring an entirely different `repository.full_name`, confirming the missing `#stacks`/`#repository_name` scoping present in `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) and `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`). module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
