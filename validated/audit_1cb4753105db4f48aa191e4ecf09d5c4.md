### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while handlers act on the independent `repository.full_name` field, letting a webhook valid for one configured GitHub organization drive writes against another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the inbound `X-Hub-Signature` against by reading `repository.owner.login` (falling back to `organization.login`) out of the untrusted JSON body itself. [1](#0-0)  Every downstream `Handlers::Handler` subclass, however, determines which `Repository`/`Stack` records to mutate using a completely different field of the same untrusted body: `repository.full_name`. [2](#0-1)  In multi-organization deployments (`Shipit.github(organization:)`), each organization has its own independent `webhook_secret`. [3](#0-2)  Because the field used to pick the verification key (`owner.login`) is never cross-checked against the field used to select the acted-upon repository (`full_name`), a webhook that is validly signed for organization A can carry a `repository.full_name` pointing at organization B's repository, and the handler will happily act on B's stacks/commits.

### Finding Description
The equality the engine implicitly relies on is:

`organization whose webhook_secret authenticated the request == organization that owns the repository the handler writes to`

This equality is never enforced. `verify_signature` computes:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it only to pick `Shipit.github(organization: repository_owner)` for HMAC verification. [4](#0-3)  Meanwhile every handler resolves the target purely from:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
which drives `Repository.from_github_repo_name(repository_name)&.stacks`. [2](#0-1) 

These two lookups read from independent, attacker-controlled JSON keys inside the same POST body: nothing forces `repository.full_name`'s owner segment to equal `repository.owner.login`/`organization.login`. In a single-organization deployment this is harmless because there is only one `webhook_secret` to check against regardless of what the payload claims. But the engine explicitly documents and supports per-organization webhook configuration with independently optional `webhook_secret` values (`webhook_secret: # nil` is shown as valid in the setup docs and dummy fixtures). [5](#0-4)  `GitHubApp#verify_webhook_signature` explicitly bypasses HMAC checking whenever a given organization has no secret configured: `return true unless webhook_secret`. [6](#0-5) 

Combining these two facts: any organization configured in `secrets.github` without a `webhook_secret` acts as an open door — anyone can send a webhook naming that organization's login in `repository.owner.login`/`organization.login` (satisfying signature "verification" trivially), while setting `repository.full_name` to any *other* configured organization's repository. The handler layer never re-derives or re-validates the acting organization; it trusts `full_name` outright.

### Impact Explanation
This breaks the "organization that authenticated vs. repository that is written" binding called out in scope. Depending on the event type, an attacker with no GitHub App credentials, no `ApiClient` token, and no repository access can:
- Force `PushHandler` to enqueue `GithubSyncJob` against a victim organization's stack with an attacker-chosen `expected_head_sha`. [7](#0-6) 
- Forge CI `status` events via `StatusHandler`, creating fabricated commit statuses (`commit.create_status_from_github!`) that gate merge-queue/deploy decisions on victim stacks. [8](#0-7) 
- Trigger `CheckSuiteHandler` to schedule check-run refreshes for victim commits. [9](#0-8) 
- Manipulate `MembershipHandler` team membership state, which underlies `Shipit.github_teams` authorization, by adding/removing arbitrary GitHub logins from teams recorded in Shipit. [10](#0-9) 

The most severe of these (forged CI status feeding merge-queue/deploy gating, and team-membership manipulation feeding `Shipit.github_teams` authorization) map to the "High" tier: escalation into `Shipit.github_teams` authorization and unauthenticated influence over stack/deploy state.

### Likelihood Explanation
Exploitability is conditional on the deployment running Shipit's documented multi-organization webhook mode where at least one configured organization deliberately omits `webhook_secret` (a state the shipped documentation and fixture files present as a legitimate, supported configuration, not a deviation from documented mounting). [5](#0-4)  Given that condition, exploitation requires only a raw unauthenticated HTTP POST to `/webhooks` with a forged `X-Github-Event` header and a crafted JSON body — no signature secret, no session, no `ApiClient` token, no repository access. There is no code path anywhere in `WebhooksController` or `Handler` that cross-checks the two fields, so likelihood is high whenever the qualifying multi-org/no-secret configuration exists.

### Recommendation
Derive the organization used for signature verification and the organization/repository acted upon from the *same* field, and make the handler layer reject events whose `repository.full_name` owner does not match the organization whose secret validated the signature. Concretely, thread the verified `repository_owner` (or the `GitHubApp` instance) into `Handler.call`, and in `Handler#stacks`/`#repository_name` assert that `full_name.split('/').first` case-insensitively equals the authenticating organization before resolving `Repository.from_github_repo_name`. Additionally, consider treating a missing `webhook_secret` for a configured organization as a hard misconfiguration (fail closed / warn loudly) rather than silently allowing unauthenticated events for that organization.

### Proof of Concept
Deployment configured per `docs/setup.md`'s "Using Multiple Github Applications" with:
```yaml
github:
  OrgTrusted:
    webhook_secret: "s3cret"
    ...
  OrgOpen:
    webhook_secret:     # left blank/nil, as shown valid in docs & test/dummy/config/secrets_double_github_app.yml
    ...
```
`Repository` records exist for both `OrgTrusted/victim-repo` and `OrgOpen/attacker-repo`.

1. Attacker sends, with no signature header (or any garbage value):
```
POST /webhooks
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgOpen" },
    "full_name": "OrgTrusted/victim-repo"
  }
}
```
2. `verify_signature` resolves `repository_owner == "OrgOpen"`, calls `Shipit.github(organization: "OrgOpen")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally. [6](#0-5) 
3. `PushHandler.call(params)` then computes `repository_name = "OrgTrusted/victim-repo"`, resolves the real, protected `OrgTrusted` stack, and enqueues `GithubSyncJob` with the attacker's chosen `expected_head_sha` against it — despite the request never being validated against `OrgTrusted`'s secret.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
