### Title
Missing future-timestamp bound in oracle freshness check permanently poisons the shared price cache - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`oracle-timestamp-fresh` treats any oracle timestamp that is greater than `stacks-block-time` as automatically "fresh" (delta forced to `u0`) instead of rejecting it as invalid, mirroring the exact bug class from the external report where a Chainlink-style aggregator's return data is not checked for future/invalid timestamps. Because the accepted timestamp is then persisted in the shared `last-update` map keyed only by `{type, ident}` (not per caller), a single price resolution call that stores a timestamp ahead of `stacks-block-time` poisons the shared cache for every other user of that asset.

### Finding Description
`oracle-timestamp-fresh` is defined as: [1](#0-0) 

If the oracle-reported timestamp `ts` (from Pyth's `publish-time` or DIA's timestamp) is greater than the chain's `stacks-block-time`, `delta` is forced to `u0`, so the `<= max-staleness` check is vacuously satisfied — the only remaining requirement is `ts >= prev`. This is the inverse of the correct behavior described in the external report, which explicitly calls for rejecting timestamps that are `0` or in the future rather than treating them as automatically fresh.

`price-resolve` then unconditionally writes this accepted, unbounded-future timestamp into the shared `last-update` map, which is not scoped to any individual account: [2](#0-1) 

Because `last-update` is keyed only by `{type, ident}` (i.e., per price feed, shared across the whole protocol), a single transaction from any caller that triggers `price-resolve` for an asset while the upstream oracle's timestamp momentarily exceeds `stacks-block-time` records that future value as `last-update-time` for everyone. Every subsequent legitimate call from any other user for that same asset must satisfy `ts >= prev` against this artificially-inflated `prev`; real, correctly-ordered oracle updates whose timestamps are less than the stored future value will fail `oracle-timestamp-fresh` and cause `price-resolve` to abort with `ERR-ORACLE-INVARIANT` until on-chain time catches up to the poisoned value.

### Impact Explanation
This is a shared-state bug: the `last-update` cache is primed by whichever unprivileged caller happens to trigger a price resolution and is then consumed by every other account borrowing, repaying, or being liquidated against that asset. Once poisoned, all price-dependent operations for the affected asset (borrow, withdraw collateral, liquidation, health checks) revert for all users, not just the caller who triggered the initial resolution, which is a temporary protocol-wide freezing of funds for that asset until the on-chain `stacks-block-time` advances past the incorrectly accepted future timestamp.

### Likelihood Explanation
The trigger condition is a normal clock/timestamp mismatch between the external oracle's reported publish time and the chain's own `stacks-block-time`, something the existing check is supposed to guard against but instead mishandles. Any account interacting with the market (not requiring any special privilege) can be the one whose transaction happens to record such a timestamp, so the affected asset's price feed can be stalled by ordinary usage without any deliberate attack, and the root cause is a logic defect in `oracle-timestamp-fresh` in this code, not third-party data being simply wrong.

### Recommendation
Reject timestamps greater than `stacks-block-time` outright instead of treating them as maximally fresh, e.g.:
```clarity
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (and
    (<= ts stacks-block-time)
    (<= (- stacks-block-time ts) max-staleness)
    (>= ts prev)))
```
This ensures future timestamps are always treated as invalid/stale rather than being accepted and persisted into the shared per-feed cache.

### Proof of Concept
1. An oracle feed's `publish-time`/timestamp is momentarily ahead of the chain's `stacks-block-time` (e.g., due to clock skew between the Pyth network and Stacks block production).
2. Any user calls a market function that triggers `price-resolve` for that asset; `oracle-timestamp-fresh` returns `true` because `delta` is forced to `u0`, so the future timestamp is accepted and written to the shared `last-update` map via `map-set last-update key timestamp` [3](#0-2) .
3. Any other, unrelated user subsequently calls borrow/repay/liquidate on the same asset; the real, correctly-ordered oracle timestamp is now less than the poisoned `prev`, so `(>= ts prev)` fails and `price-resolve` returns `ERR-ORACLE-INVARIANT`, freezing all price-dependent operations for that asset for every user until `stacks-block-time` catches up to the poisoned value.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
