### Title
Front-running `pallet-asset-conversion` pool initialization by donating tokens to the deterministic pool account skews the first `add_liquidity` price ratio - ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`pallet-asset-conversion` derives its LP-token price/ratio purely from the live token balances of the pool's sovereign account (`reserve1`/`reserve2` via `get_balance`), not from an internally-tracked accounting variable. Because the pool account address is deterministically computable from the asset pair before the pool is created or before any liquidity has been minted, an unprivileged attacker can pre-fund that account with an arbitrary asset ratio via ordinary `transfer` extrinsics. When the legitimate first liquidity provider later calls `add_liquidity`, the pallet computes the required paired amount using `quote()` against the attacker-controlled reserves rather than the caller's actual desired ratio, which can force the honest depositor to either pay an economically infeasible amount of the second asset or have the extrinsic revert.

### Finding Description
The reserve values used to price liquidity provision are read directly from the pool account's live balances: [1](#0-0) 

In `do_add_liquidity`, the branch selection that decides whether the caller's desired amounts are used as-is or whether they must be "quoted" against existing reserves is based solely on whether `reserve1`/`reserve2` are zero — not on whether the pool has ever actually had liquidity minted (`total_supply`): [2](#0-1) 

Since the pool's sovereign account is deterministic and derivable from the asset pair before pool creation (as demonstrated in the existing `cannot_block_pool_creation` test, where an attacker computes `PoolLocator::address(...)` and transfers assets to it), any account can `transfer`/`transfer_allow_death` arbitrary amounts of both `asset1` and `asset2` into that account. If the attacker deposits both assets in a skewed ratio (e.g. `reserve1 = 1`, `reserve2 = 1_000_000_000_000`) while `total_supply(lp_token) == 0`, the pool still has no actual liquidity minted, but `do_add_liquidity`'s zero-reserve fast path is bypassed because both reserves are non-zero: [3](#0-2) 

The legitimate first liquidity provider's `add_liquidity` call will then compute `amount2_optimal = quote(amount1_desired, reserve1, reserve2)`, which — under the attacker's skewed ratio — yields an amount of `asset2` vastly disproportionate to what a normal user intends to deposit, causing either `AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired` reverts or requiring the depositor to supply an economically prohibitive amount of the second asset to succeed: [4](#0-3) 

This is analogous to the reported StakedUSDe bug: in both cases, a share/LP-price calculation is derived from a raw on-chain balance that any unprivileged account can inflate via a plain token transfer to a known address, before the intended first depositor mints shares/LP tokens — skewing the price and forcing subsequent depositors into disproportionate deposits or reverts.

### Impact Explanation
The impact is a griefing/denial-of-service against the intended initial liquidity provider of a specific asset pair: the attacker can force the legitimate depositor to either abandon the pool, deposit an oversized/impractical amount of the paired asset, or accept an unfavorable minted-LP-token amount. This does not directly cause fund theft or unbacked issuance (the `MintMinLiquidity` and minimum-deposit checks still apply and `calc_lp_amount_for_zero_supply` is unaffected by the ratio, only the *paired amount* the caller must supply is affected), and the pool can still ultimately be created and used, so I assess this as Medium severity at most, matching the disclosed severity of the analogous StakedUSDe finding (front-running with a modest attacker cost that requires a large amount of capital to cause the more damaging outcomes, downgrading from a naive High assessment).

### Likelihood Explanation
Likelihood is Medium-to-High for any market that is created via a permissionless `create_pool` call and not seeded atomically in the same block/transaction as `add_liquidity`. The pool account address is fully computable off-chain by anyone who knows the asset pair via `PoolLocator::address`, so no privileged role, governance, or chain state observation beyond public information is needed — the attacker just needs ordinary signed `Assets::transfer`/`Balances::transfer` extrinsics executed before the target's `add_liquidity` extrinsic is included, which is a standard front-running scenario achievable via mempool observation or simply being first when a new pool is anticipated.

### Recommendation
Track pool reserves via internal pallet storage/accounting (or gate the “first mint” ratio-free path on `total_supply(lp_token) == 0` rather than `reserve.is_zero()`), so that unsolicited direct transfers into the pool's sovereign account cannot influence the price used for the first `add_liquidity` call. Alternatively, allow/require the first liquidity provider (or `create_pool`) to atomically seed initial liquidity in the same extrinsic, and treat any pre-existing balance in the pool account as a foreign/unaccounted-for donation to be swept, not counted as tradable reserve.

### Proof of Concept
I did not execute a new local Rust/FRAME integration test; execution status is **not run**. This assessment is based on static code review only. The reachability of pre-funding the deterministic pool account is already demonstrated by the existing repository test `cannot_block_pool_creation`, which shows an attacker computing the pool's sovereign account address and transferring assets to it before pool creation: [5](#0-4) 

That test only asserts that pool *creation* is not blocked, and does not check whether the *ratio* seen by the first `add_liquidity` call is skewed. To fully confirm the DoS/griefing impact described here, a background agent should extend this test (or write a new one) to:
1. Create a pool for `(Native, WithId(2))`.
2. As an attacker, transfer a skewed ratio of both `Native` and `WithId(2)` directly into the pool's sovereign account (both non-zero, e.g. ratio 1:1_000_000) while LP `total_issuance` is still zero.
3. As the honest first liquidity provider, call `add_liquidity` with a "normal" balanced `amount1_desired`/`amount2_desired` (e.g. equal amounts) and assert that the extrinsic either reverts with `AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired`, or requires an amount of the second asset far exceeding the depositor's intended balanced deposit, confirming the price-skew impact.

Because I could not run this reproduction in this environment, I flag this as an **unconfirmed but code-supported analog** — the control-flow evidence (`get_balance` reading live balances, and the reserve-zero-check bypassing the `total_supply`-based safe path) strongly suggests the vulnerability is real, but empirical confirmation via the suggested test should be performed by a Devin session with Rust/cargo test execution access before treating this as a confirmed, bounty-eligible finding.

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
