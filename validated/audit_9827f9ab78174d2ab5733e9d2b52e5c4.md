## Title
Cross-Organization Webhook Secret Confusion Allows Injection of Forged Commit Status / Push Events - (File: `app/controllers/shipit/webhooks_controller.rb`)

## Summary
`WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to validate the HMAC-SHA1 signature against by reading `repository.owner.login` (or `organization.login`) from the untrusted request body, but the handler that subsequently *acts* on the payload (`StatusHandler`, and to a lesser extent `PushHandler`/`Handler#stacks`) never re-checks that the organization whose secret validated the signature is the organization that owns the data being written. In a multi-organization Shipit deployment, this breaks the binding "organization that authenticated == organization/repository being written to."

## Finding Description
`Shipit` supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret` [1](#0-0) , configured as sibling keys under `github:` [2](#0-1) .

`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) to verify against purely from the attacker-controlled JSON body:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

Once the signature passes, `create` dispatches to handlers using the **same raw, attacker-controlled** `params` hash, with no re-derivation or cross-check against `repository_owner`:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

`StatusHandler` — the handler for the GitHub `status` event — does not consult `repository`/`full_name` at all; it matches by commit SHA globally, across every stack/organization hosted by the instance, and writes attacker-supplied `state`, `description`, `target_url`, and `context` straight into a `Status` record:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

`Status.replicate_from_github!` persists these fields verbatim [6](#0-5) , and other handlers (`PushHandler`, pull-request handlers) resolve the target `Stack`/`Repository` from `repository.full_name` [7](#0-6)  — a field that is completely independent of `repository.owner.login`, the field actually used to select the verifying secret.

**Binding broken (equality that should hold but doesn't):**
`organization whose webhook_secret validated X-Hub-Signature == organization that owns the repository/commit the handler writes to`

Before the exploit, this equality trivially holds because GitHub itself only ever sends a webhook for the org that installed the app, with `owner.login` and `full_name`'s prefix always consistent. After the attacker's forged request, the left side is the attacker's own organization (whose secret they legitimately possess, having installed the Shipit GitHub App on their own org per the setup docs) while the right side is a victim organization/stack hosted on the same Shipit instance — the two diverge, and the code never checks for that.

## Impact Explanation
An operator of any organization onboarded to a shared, multi-org Shipit instance (a routine, unprivileged position — they only need to have installed their own GitHub App integration and thus legitimately know their own `webhook_secret`) can forge a `status` webhook whose signature verifies (using their own org's secret) while its content targets a `Commit` belonging to a *different* organization's stack. Because `StatusHandler` looks up commits solely by SHA with no ownership check, the attacker can inject a fabricated `success` status (with an arbitrary `context`, e.g. one referenced in a victim stack's `ci.require`/`ci.blocking` list) for a real commit SHA in a victim repository whose SHA they can observe (commit SHAs are effectively public on GitHub). Since Shipit's CI-gating logic operates on locally recorded `Status` rows, this can satisfy required-CI conditions that were never actually met, enabling an unauthorized deploy of a commit that has not passed real CI — matching the "unauthorized deploy" impact category. It is a genuine authentication/authorization-scope bypass rather than a data-integrity nuisance, because the trust boundary "verified org == acted-upon org" is exactly what the webhook signature was supposed to enforce.

## Likelihood Explanation
Likelihood is Medium: it requires a Shipit deployment that hosts more than one GitHub organization (explicitly documented and supported as a first-class configuration [1](#0-0) ) and the attacker must control/administer at least one of those organizations (i.e., have installed a GitHub App for it and thus know its `webhook_secret`) while another organization on the same instance is the target. No Shipit session, `ApiClient` token, or GitHub token belonging to the victim org is needed — only knowledge of a target commit SHA, which is generally discoverable.

## Recommendation
In `WebhooksController`, after verifying the signature, re-validate that the organization used for verification matches the organization actually referenced by the payload fields the handlers will act on (i.e., assert `repository_owner == repository.full_name.split('/').first` and, for `StatusHandler`, restrict the `Commit` lookup to commits belonging to a stack whose `Repository#owner` equals the verified `repository_owner`, mirroring what `PullRequest` handlers already do via `Repository.from_github_repo_name`). Alternatively, thread the verified organization through to each handler and have `Handler#stacks`/`StatusHandler#process` filter strictly by that organization rather than trusting `full_name`/`sha` alone.

## Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgAttacker` (attacker-controlled, secret `S_A`) and `OrgVictim` (secret `S_V`), each with stacks tracked by Shipit, per the multi-org config shown in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, knowing `S_A` (they created the `OrgAttacker` GitHub App installation themselves), crafts a JSON body for a GitHub `status` event:
   ```json
   {
     "sha": "<real sha of a commit in OrgVictim/victim-repo>",
     "state": "success",
     "context": "ci/required-context",
     "repository": { "owner": { "login": "OrgAttacker" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, verifies successfully with `S_A`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (belonging to `OrgVictim`), and creates a `Status` with `state: "success"`, `context: "ci/required-context"` on it — with no relation to `OrgAttacker` ever checked.
6. If `OrgVictim`'s stack requires `ci/required-context` for deploy gating, the forged status can unblock deployment of that commit.

**Note:** I was unable to fully trace, within this session, the exact code path that consumes `ci.require`/`ci.blocking` at deploy time (e.g., in `app/models/shipit/stack.rb` or `deploy_spec.rb`) to confirm the precise mechanics by which a forged `Status` unlocks a deploy button; this should be verified directly in the repository (`app/models/shipit/deploy_spec.rb`, `app/models/shipit/commit.rb`, `app/models/shipit/status/group.rb`) before finalizing remediation, though the cross-organization commit-status injection itself is clearly demonstrated by the code cited above.
