### Title
Webhook signature is verified using the secret keyed by `repository.owner.login`, but events are dispatched against the repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured for multiple GitHub organizations (the documented "Using Multiple GitHub Applications" setup), each organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects which secret to validate the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the *unauthenticated* JSON body, then verifies the whole raw body against that org's secret. Once the signature check passes, every handler resolves the target repository/stack using a *different* field of the same body — `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, consumed via `Repository.from_github_repo_name`). Nothing binds these two fields together, so a request whose HMAC is valid for organization A can still name a repository owned by organization B, and the handler will happily act on B's stack.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-49`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is read from the same untrusted JSON payload being verified, and is used only to pick *which* `webhook_secret` (`lib/shipit/github_app.rb:76-83`, `lib/shipit.rb:170-200`) to HMAC-check the raw body against. Because the signature covers the full raw body, an attacker who already knows the `webhook_secret` configured for *any one* organization on the instance (e.g. their own org in a multi-tenant Shipit install, or a leaked/rotated secret) can construct an arbitrary payload — including a `repository.full_name` that names a stack belonging to a completely different organization — and produce a valid signature for it, because the secret used to sign is chosen from the very same attacker-controlled field (`repository.owner.login`) that they set to match the secret they know.

Every handler then determines the actual repository to act on via a *different, unverified* field:
`app/models/shipit/webhooks/handlers/handler.rb:32-38`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
and `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) simply splits `full_name` on `/` and looks up any `Repository` row, with no cross-check against `repository.owner.login` or the organization whose secret validated the request.

This is the same class of bug as the reported `computePoolAddress()` issue: one identity is authenticated (the organization/secret used for signature verification, analogous to the computed pool address) while a different, unauthenticated identity (the `repository.full_name` used by the callback/handler, analogous to the `msg.sender`/`getPool()` actual pool) is the one actually acted upon. The equality that should hold — `organization that authenticated == repository owner that is written` — is never enforced.

### Impact Explanation
An attacker who possesses (or leaks/rotates in) a valid `webhook_secret` for any organization configured on a multi-org Shipit instance can forge webhook deliveries that are dispatched against stacks belonging to a *different* organization entirely, without needing GitHub write access to that organization's repositories. Depending on which handler is targeted this enables: forcing `GithubSyncJob`/push processing, injecting fake commit statuses/check runs that influence deploy safety gates, or closing/merging pull requests and archiving review stacks (`ClosedHandler#process` → `review_stack.archive!`) for a stack the attacker has no legitimate relationship with. This crosses a repository/organization trust boundary that the multi-org webhook secret feature is explicitly meant to enforce, matching the "cross-repository writes" / "unauthorized deploy, rollback or merge" impact tier.

### Likelihood Explanation
Requires the attacker to already know a `webhook_secret` for at least one organization configured on the Shipit instance — this is a real precondition (not "no credential at all"), but it is far weaker than requiring GitHub write access to the *victim* organization/repository, session cookies, or an `ApiClient` token. In any multi-tenant deployment where several organizations (with different trust levels) share one Shipit instance and each holds its own webhook secret, this is a plausible and realistic scenario, and the report explicitly documents this configuration as supported (`docs/setup.md`, "Using Multiple Github Applications").

### Recommendation
After signature verification succeeds, re-derive the trusted organization from the secret that actually validated the request (not from attacker-controlled JSON), and require that `repository.owner.login` (or `organization.login`) used for secret selection matches the owner portion of `repository.full_name` used by handlers before processing. Alternatively, pass the authenticated organization down to `Shipit::Webhooks::Handlers::Handler` and have `Repository.from_github_repo_name`/`stacks` reject any repository whose owner differs from the organization that signed the request.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org setup), and each has a `Shipit::Stack` for a repository it owns.
2. Attacker knows/possesses `OrgA`'s `webhook_secret` (e.g. they administer the GitHub App installation for OrgA on this shared instance).
3. Attacker crafts a `pull_request` "closed" webhook JSON body with:
   - `repository.owner.login = "OrgA"` (so `WebhooksController#repository_owner` selects OrgA's app/secret)
   - `repository.full_name = "OrgB/victim-repo"` (the actual target used by `ClosedHandler#repository`/`Handler#repository_name`)
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: pull_request`.
5. `verify_signature` picks `Shipit.github(organization: "OrgA")`, validates the HMAC successfully (since it was computed with OrgA's real secret over this exact body), and the request proceeds.
6. `ClosedHandler#process` resolves `repository` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `review_stack.archive!` on OrgB's stack — a write action on an organization/repository the attacker never authenticated against.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
