### Title
Stack-scoped API token bypasses its own scope in the CCMenu endpoint — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the shared stack-lookup helper from `Shipit::Api::BaseController` and, in doing so, drops the scoping that limits a stack-bound `ApiClient` token to the single stack it was issued for. Any token with `read:stack` permission — including one deliberately created with `stack_id` set to a single stack — can be replayed against any other stack's CCMenu URL to read that stack's build/deploy state.

### Finding Description
`Shipit::ApiClient` supports scoping a token to one stack via its `stack_id` column, and `BaseController` enforces this scope centrally: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and the default `stack` method resolves `params[:stack_id]` only within that restricted set. Every controller that inherits `stack` from `BaseController` (e.g. `Api::TasksController`, `Api::StacksController`) is therefore bound by the equality `current_api_client.stack_id == stack.id` whenever the client is scoped.

`Api::CCMenuController` breaks this equality: it declares its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly, entirely bypassing the `stacks` scoping relation: [2](#0-1) 

`Stack.from_param!` performs an unscoped lookup by `repo_owner/repo_name/environment`: [3](#0-2) 

The only guard on the action is `require_permission :read, :stack`, which checks that the client's `permissions` array includes `read:stack` — it does not check that the token is authorized for the *specific* stack requested: [4](#0-3) [5](#0-4) 

Such single-stack tokens are minted by design for this very endpoint: `CCMenuUrlController#fetch` creates (or reuses) an `ApiClient` scoped to one stack with only `read:stack` permission and hands the caller a URL containing the token as a query-string parameter, intended for embedding in third-party CI dashboard tools: [6](#0-5) 

Because `CCMenuController#authenticate_api_client` also accepts the token straight from `params[:token]` (no Basic Auth required), anyone who obtains one such per-stack CCMenu URL (its whole design intent is to be shared with lightly-trusted external tooling) can swap the `stack_id` segment of the path and read any other stack in the installation, even ones the token was never scoped to.

Before the attacker's request: `ApiClient#stack_id == stack_A.id`, and only `stack_A`'s state is reachable via this token.
After: the same token, sent to `/api/stacks/<stack_B>/cc_menu.xml?token=...`, returns `stack_B`'s state — the binding "a stack a token authorises" vs "a stack it touches" is broken.

### Impact Explanation
The CCMenu XML response leaks stack name, activity, last build status/label/time, lock status, and web URL — i.e. unauthorized read of another stack's deploy/task state, obtained purely by reusing a token that was supposed to be constrained to a single stack. This matches the High-impact category "unauthenticated read of stack state" since the endpoint is explicitly designed to be queried with just a query-string token (no session, no per-request re-authorization), and the scope constraint that is supposed to bound that token's blast radius is silently bypassed.

### Likelihood Explanation
Exploitation requires only possession of a legitimately-obtained CCMenu token for one stack (these are routinely shared with external CI/monitoring dashboards over URLs, per the intended usage of `CCMenuUrlController`) and knowledge or guessing of another stack's `owner/name/environment` path (stack listings and repo names are commonly visible elsewhere in the app/GitHub). No privileged access, session, or additional secret is required to pivot from "authorized for stack A" to "read stack B."

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so that a stack-scoped `ApiClient` cannot resolve any stack other than the one it is bound to.

### Proof of Concept
1. As an authenticated Shipit user, visit `stack_A`'s page and trigger `GET /*stack_id/ccmenu_url` (`CCMenuUrlController#fetch`) to obtain a CCMenu URL: this creates/reuses an `ApiClient` named "CCMenu Client" with `permissions: ['read:stack']` and `stack_id: stack_A.id`, returning `.../api/stacks/<stack_A path>/cc_menu.xml?token=<TOKEN>`.
2. Take the same `<TOKEN>` and request `.../api/stacks/<stack_B path>/cc_menu.xml?token=<TOKEN>` for a different stack `stack_B` that the token was never scoped to.
3. Observe `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) unconditionally, resolving `stack_B` and rendering its `lastBuildStatus`, `lastBuildLabel`, activity and lock state — data the token was never authorized to read, contrary to the scoping enforced everywhere else via `BaseController#stacks`/`#stack` (app/controllers/shipit/api/base_controller.rb:74-80).

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
