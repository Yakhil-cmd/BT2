### Title
Unauthenticated Arbitrary RPC Dispatch via `ServiceChainCall` P2P Message Allows Unauthorized KAIA Transfer from Bridge Operator Account — (`File: node/sc/main_bridge_handler.go`)

---

### Summary

`MainBridgeHandler.handleCallMsg` in `node/sc/main_bridge_handler.go` receives a raw `ServiceChainCall` P2P message from any connected sub-bridge peer and writes its bytes verbatim into the main bridge's internal RPC server pipe. Because the internal RPC server has all public `kaia_*`/`klay_*` APIs registered — including `kaia_sendTransaction` and `kaia_sendRawTransaction` — a malicious or compromised sub-bridge peer can invoke any of those methods with attacker-controlled parameters, with no method-name or parameter validation at the bridge layer.

---

### Finding Description

**Setup — internal RPC server registration**

In `NewMainBridge`, a `net.Pipe()` is created and the RPC server is wired to one end:

```go
mb.rpcServer = rpc.NewServer()
p1, p2 := net.Pipe()
mb.rpcConn = p1
go mb.rpcServer.ServeCodec(rpc.NewCodec(p2), 0)
```

In `SetComponents`, every public `kaia`/`klay` API from the parent-chain CN node is registered on that server:

```go
if api.Public && (api.Namespace == "klay" || api.Namespace == "kaia") {
    mb.rpcServer.RegisterName("klay", api.Service)
    mb.rpcServer.RegisterName("kaia", api.Service)
}
```

This includes `KaiaTransactionAPI` which exposes `kaia_sendTransaction`, `kaia_sendRawTransaction`, and `kaia_sendTransactionAsFeePayer`. [1](#0-0) [2](#0-1) 

**Vulnerable handler — zero validation**

```go
func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
    data := make([]byte, msg.Size)
    err := msg.Decode(&data)
    ...
    _, err = mbh.mainbridge.rpcConn.Write(data)   // raw bytes → RPC server
    ...
}
```

The function decodes the P2P payload into a raw byte slice and writes it directly to `rpcConn`. There is no inspection of the JSON-RPC method name, no allowlist, and no parameter sanitization. [3](#0-2) 

**Dispatch path**

`HandleSubMsg` routes any `ServiceChainCall`-coded message to `handleCallMsg` without further checks: [4](#0-3) 

**Registered target — `kaia_sendTransaction`**

`KaiaTransactionAPI.SendTransaction` signs with the account manager and submits to the tx pool:

```go
func (s *KaiaTransactionAPI) SendTransaction(ctx context.Context, args SendTxArgs) (common.Hash, error) {
    signedTx, err := s.SignTransaction(ctx, args)
    ...
    return submitTransaction(ctx, s.b, signedTx.Tx)
}
```

`sign` looks up the wallet by address and calls `wallet.SignTx` — it succeeds whenever the target account exists in the keystore and is unlocked, which is the standard operating state for a bridge operator account. [5](#0-4) [6](#0-5) 

---

### Impact Explanation

A connected sub-bridge peer crafts a `ServiceChainCall` P2P message whose payload is a valid JSON-RPC request for `kaia_sendTransaction` with `from` set to the bridge operator address and `to` set to an attacker-controlled address. The main bridge's internal RPC server processes it identically to a local operator call:

- **Unauthorized KAIA transfer**: KAIA is deducted from the bridge operator's account and credited to the attacker's address. The bridge operator account holds KAIA to pay gas for all cross-chain value-transfer transactions; draining it halts bridge operations and steals funds.
- **`kaia_sendRawTransaction` abuse**: Even without an unlocked account, the attacker can inject arbitrary pre-signed transactions (e.g., replayed transactions, nonce-exhaustion transactions) into the parent chain's tx pool, corrupting the bridge operator's nonce sequence and blocking legitimate bridge transactions.
- **`kaia_sendTransactionAsFeePayer`**: If the bridge operator is also a fee payer, the attacker can co-sign fee-delegated transactions, causing unauthorized fee charges.

---

### Likelihood Explanation

The sub-bridge peer is authenticated at the P2P layer by node ID (ECDSA public key), so an external random attacker cannot connect. However:

- A **compromised child-chain node** (the sub-bridge) can trivially exploit this — the child chain is a separate, lower-security environment.
- A **MITM attacker** on the P2P link between sub-bridge and main bridge can inject `ServiceChainCall` messages.
- The bridge operator account is routinely kept unlocked in automated service-chain deployments.

The attack requires only a single crafted P2P message after a valid handshake.

---

### Recommendation

1. **Allowlist RPC methods**: In `handleCallMsg`, parse the JSON-RPC `method` field before writing to the pipe and reject any method not in an explicit allowlist (e.g., only `kaia_getBalance`, `kaia_getCode`, `kaia_call`, `kaia_getTransactionCount`, `kaia_sendRawTransaction`).
2. **Remove state-mutating methods from the internal server**: Do not register `kaia_sendTransaction`, `kaia_sendTransactionAsFeePayer`, or any signing-capable method on `mb.rpcServer`. The sub-bridge should only need read-only queries and `kaia_sendRawTransaction` (which still requires a valid external signature).
3. **Separate the internal RPC server's API surface** from the full public API set registered in `SetComponents`.

---

### Proof of Concept

```
// Attacker controls a sub-bridge node connected to the main bridge.
// Craft a ServiceChainCall P2P message whose RLP payload decodes to:
payload := []byte(`{"jsonrpc":"2.0","id":1,"method":"kaia_sendTransaction","params":[{
  "from":  "0x<bridge_operator_address>",
  "to":    "0x<attacker_address>",
  "value": "0x<bridge_operator_balance_hex>",
  "gas":   "0x5208"
}]}`)

// RLP-encode payload as a byte slice (matching msg.Decode(&data) expectation)
rlpPayload := rlp.EncodeToBytes(payload)

// Send via the P2P connection as ServiceChainCall (msg.Code = ServiceChainCall)
p2p.Send(rw, ServiceChainCall, rlpPayload)

// Result: main bridge's internal RPC server calls KaiaTransactionAPI.SendTransaction,
// signs with the unlocked bridge operator key, and submits the transfer to the tx pool.
// KAIA is transferred from the bridge operator to the attacker.
```

The root cause is `handleCallMsg` writing untrusted P2P bytes directly to the privileged RPC pipe with no method validation, exactly analogous to the external report's `prettyPrint` passing an unvalidated object to a privileged display context. [3](#0-2) [1](#0-0) [2](#0-1) [5](#0-4)

func (mbh *MainBridgeHandler) handleCallMsg(p BridgePeer, msg p2p.Msg) error {
	logger.Trace("mainbridge writes the rpc call message to rpc server", "msg.Size", msg.Size, "msg", msg)
	data := make([]byte, msg.Size)
	err := msg.Decode(&data)
	if err != nil {
		logger.Error("error in mainbridge message handler", "err", err)
		return err
	}

	// Write to RPC server pipe
	_, err = mbh.mainbridge.rpcConn.Write(data)
	if err != nil {
		logger.Error("failed to write to the rpc server pipe", "err", err)
		return err
	}
	return nil
}

	account := accounts.Account{Address: addr}

	wallet, err := s.b.AccountManager().Find(account)
	if err != nil {
		return nil, err
	}
	// Request the wallet to sign the transaction

func (s *KaiaTransactionAPI) SendTransaction(ctx context.Context, args SendTxArgs) (common.Hash, error) {
	if args.AccountNonce == nil {
		// Hold the addresse's mutex around signing to prevent concurrent assignment of
		// the same nonce to multiple accounts.
		s.nonceLock.LockAddr(args.From)
		defer s.nonceLock.UnlockAddr(args.From)
	}

	signedTx, err := s.SignTransaction(ctx, args)
	if err != nil {
		return common.Hash{}, err
	}

	return submitTransaction(ctx, s.b, signedTx.Tx)
