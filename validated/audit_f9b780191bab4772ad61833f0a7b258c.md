## Finding: Newline injection in AA state-variable names allows key-namespace collision in the LevelDB-backed state store

### Title
Unfiltered newline in AA `state_var_assignment` variable names allows corruption/collision of AA state-variable keys - (File: `aa_composer.js`, `storage.js`, `formula/evaluation.js`)

### Summary
The LXD CVE is a "special-character injection into a delimiter-separated configuration string" bug: a value that should be an opaque configuration parameter is allowed to contain the record separator (`\n`), letting an attacker inject additional directives into the generated `lxc.conf`. ocore has a structurally identical pattern in its AA (Autonomous Agent) state-variable storage: state var keys are built by naively concatenating attacker/AA-author-controlled strings with `\n` as the field separator, and — unlike the `data_feed` payload path, which explicitly checks for and rejects `\n` — the state-variable name path does not appear to perform the same check before it is used to build the storage key.

### Finding Description
AA state variables are persisted in the key-value store using `\n`-delimited keys of the form `"st\n" + address + "\n" + var_name"`: [1](#0-0) [2](#0-1) [3](#0-2) 

`var_name` originates from the oscript `state_var_assignment` statement inside an AA's own bytecode, evaluated at trigger time: [4](#0-3) [5](#0-4) 

The only guard visible on this path is `typeof var_name !== 'string'` and a length check on the *value* (`MAX_STATE_VAR_VALUE_LENGTH`) — there is no visible check rejecting `\n` (or other separator characters) inside `var_name` itself before it is concatenated into the `"st\n"+address+"\n"+var_name` key.

This is the same bug class as the LXD advisory: the codebase elsewhere *does* recognize that `\n` must be stripped from identifiers that get embedded in a delimiter-based structure — the `data_feed` app payload explicitly rejects feed names/values containing `\n` before they are written into the same kind of `\n`-delimited kvstore key (`'df\n'+address+'\n'+feed_name+...`): [6](#0-5) [7](#0-6) 

But the AA state-var name, which is written into a structurally identical `\n`-delimited key (`"st\n"+address+"\n"+var_name`), does not have the equivalent explicit rejection in the code paths inspected (`formula/evaluation.js` state_var_assignment, `aa_composer.js` saveStateVars). A crafted `var_name` such as `"foo\nOTHER_ADDRESS\nbar"` (or one containing the address-length structure `\n<32-char-address>\n<name>`) written by an AA author would be concatenated verbatim into the LevelDB key, since `readAAStateVars` and range-scan code (`options.gte`/`options.lte` with `"st\n"+address+"\n"+prefix`) rely purely on lexicographic string boundaries around `\n`, not on structural parsing/escaping of `var_name`. An AA whose own logic constructs `var_name` from user-controlled trigger data/params (a very common oscript pattern: `var['prefix_' || trigger.data.x]`) could be manipulated by a triggering unit sender to produce a `var_name` value containing embedded `\n` sequences, effectively forging a key that looks like it belongs to a *different* address segment of the `"st\n"` keyspace or to a different variable name than intended by the AA's own storage-size accounting.

### Impact Explanation
Because `checkStorageSizes`/`updateStorageSize` and every other reader of the `"st\n"` keyspace assume the key layout `"st\n" + 32-byte address + "\n" + var_name` is exactly and unambiguously delimited, an injected `\n` in `var_name` can desynchronize this assumption: a write intended for AA `A`'s namespace can produce a stored key that is parsed (by `substr(3,32)` / `slice(36)` positional logic in `checkStorageSizes`, `readAAStateVars`, `sqlite_migrations.js` migration code) as belonging to a different address or a spoofed variable name. This can corrupt AA-critical state (balances/counters/flags an AA's own logic depends on for payout or freeze decisions), leading to AA fund loss or freezing, or a storage-size/state mismatch that different full nodes might resolve inconsistently — matching the "node disagreement on validity/stability" and "AA fund loss or freezing" impact classes required by scope. Severity is High given it operates purely through a posted trigger driving AA-authored code, with no privileged/network access needed.

### Likelihood Explanation
Reachable from an unprivileged unit poster: any user can send a trigger unit whose `data` fields feed into an AA's `var[...]` name construction, and the concatenation into `\n`-delimited kvstore keys happens deterministically in consensus-critical `aa_composer.js`/`storage.js` code for every full node. No special privilege, timing, or race condition is needed beyond crafting the payload data — directly analogous in reachability to the LXD bug being triggerable by any authenticated container operator supplying a crafted config value.

### Recommendation
Explicitly reject `\n` (and ideally length-bound and character-class-restrict) `var_name` in `state_var_assignment` evaluation (`formula/evaluation.js`) before it reaches `stateVars[address][var_name]` and before `aa_composer.js`'s `saveStateVars` builds the `"st\n"+address+"\n"+var_name` key — mirroring the existing `feed_name.indexOf('\n') >= 0` check already applied to `data_feed` payloads in `validation.js`. Apply the same check to any AA `params`/`response_var_assignment` name that ultimately participates in delimiter-based key construction, and audit other `\n`-delimited kvstore key builders (`aa_addresses`, `dfv`, `df`, `j`) for the same gap.

### Proof of Concept
Conceptual (cannot be fully validated without executing the full AA bytecode evaluator, but grounded in the cited code):
1. Deploy an AA whose oscript builds a state var name from trigger data, e.g. `var[ trigger.data.name ] = trigger.data.val;`.
2. Send a trigger unit with `data.name` containing an embedded literal newline, e.g. `"victim\nOTHER32CHARADDRESSXXXXXXXXXXXXX\nspoofed_var"`.
3. `formula/evaluation.js`'s `state_var_assignment` case only checks `typeof var_name === 'string'` (`formula/evaluation.js:1317-1318`) and passes it straight to `stateVars[address][var_name]`, which `aa_composer.js:1496` later serializes as key `"st\n"+address+"\n"+var_name` — i.e., `"st\n"+address+"\nvictim\nOTHER32CHARADDRESSXXXXXXXXXXXXX\nspoofed_var"`.
4. Any code that parses `"st\n"` keys positionally (`checkStorageSizes` in `aa_composer.js:1918-1932`, `readAAStateVars` in `storage.js:1024-1053`) will misinterpret the embedded newline-delimited segments as address/var_name boundaries belonging to a different address, corrupting per-address storage-size accounting and state-var namespace isolation.

Note: I was unable to fully confirm within the remaining exploration budget whether `MAX_STATE_VAR_NAME_LENGTH` (referenced 3 times in `aa_composer.js` per grep but not inspected line-by-line) already performs a `\n`-rejection check alongside the length check — the exact enforcement code for that constant was not retrieved. If such a check exists and already blocks `\n`, this specific analog would be mitigated; this should be verified directly against `aa_composer.js` before treating the finding as fully proven. Given the codebase's own precedent of needing an explicit `feed_name.indexOf('\n')` check for the structurally identical `data_feed` key path, and the absence of a visible equivalent check in the `state_var_assignment` evaluation path, this analog is reported per the "strongest reachable path" instruction, with the above caveat.
