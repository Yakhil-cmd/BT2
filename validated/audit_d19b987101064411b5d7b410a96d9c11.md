Found the analog. The `reject_new_shared_address` message handler in `wallet.js` deletes a pending shared-address record identified only by a `chash` (a hash of the address definition template) supplied by the sender, with no check that the sender is actually one of the parties referenced in that pending shared address.

### Title
Cross-device IDOR in `reject_new_shared_address` lets any correspondent delete another user's pending shared-address negotiation - (File: wallet.js)

### Summary
Gitea's CVE-2026-58438 allowed removing an issue dependency without verifying the caller's access to the referenced (private) repository — a classic IDOR where an object is looked up and mutated purely by an attacker-supplied identifier, without checking that the caller is authorized over that object. The `ocore` analog is the `reject_new_shared_address` device-message handler, which deletes `pending_shared_addresses`/`pending_shared_address_signing_paths` rows solely by an attacker-supplied `address_definition_template_chash`, without verifying that `from_address` is actually one of the participants recorded for that pending shared address.

### Finding Description
In `wallet.js`'s `handleMessageFromHub`, the `reject_new_shared_address` case only validates that `body.address_definition_template_chash` looks like a valid address, then immediately calls `walletDefinedByAddresses.deletePendingSharedAddress(body.address_definition_template_chash)`: [1](#0-0) 

`deletePendingSharedAddress` performs unconditional deletes keyed only by the chash, with no `device_address` filter: [2](#0-1) 

Compare this to `approvePendingSharedAddress`, invoked from the `approve_new_shared_address` case, which correctly scopes its update `WHERE definition_template_chash=? AND device_address=?` — restricting the mutation to rows belonging to the actual sender: [3](#0-2) 

`reject_new_shared_address` has no equivalent `device_address`/`from_address` scoping. Because `address_definition_template_chash` is deterministically derived from the (predictable-once-known, or even guessable/broadcast) definition template via `objectHash.getChash160`, any correspondent (or any peer whitelisted for pairing/non-correspondent messages) who learns or guesses a pending shared-address chash belonging to a *different* multi-party negotiation can send a forged `reject_new_shared_address` message and wipe out that unrelated pending shared-address record — even though they are not one of the cosigners referenced by `pending_shared_address_signing_paths.device_address` for that chash.

### Impact Explanation
This lets an attacker unilaterally abort another set of parties' shared-address (multisig) creation process they are not a member of, by deleting the `pending_shared_addresses` and `pending_shared_address_signing_paths` rows out from under them. If exploited at the right moment (e.g., right before the last required approval arrives), it can prevent a legitimate multi-party shared address from ever being finalized, silently dropping in-flight approvals and forcing participants to restart the negotiation — a denial-of-service/griefing effect on wallet/contract setup between parties who did not include the attacker in their negotiation. It does not directly move funds since `shared_addresses` (the finalized table) is untouched, but it can interfere with device-to-device contract/wallet setup flows that other ocore-based wallets rely on for creating multisig or shared arbitration/contract addresses.

### Likelihood Explanation
The message handler is reachable directly via `handleMessageFromHub` on any paired correspondent device, and `reject_new_shared_address` performs no membership check at all (unlike its sibling `approve_new_shared_address`), so exploitation only requires learning/predicting the target `address_definition_template_chash` (derived from a definition template that may be shared among cosigners during negotiation or observed in transit). No signature over a specific pending-address row is required, and the delete uses only that hash as the key.

### Recommendation
In `wallet.js`'s `reject_new_shared_address` handler, verify that `from_address` is a listed `device_address` for the given `address_definition_template_chash` in `pending_shared_address_signing_paths` before calling `deletePendingSharedAddress`, mirroring the `WHERE ... AND device_address=?` scoping already used in `approvePendingSharedAddress`. Reject the request with an error if the sender is not among the recorded participants.

### Proof of Concept
1. Party A and Party B start creating a shared (multisig) address; A's device inserts a `pending_shared_addresses` row keyed by `address_definition_template_chash` and corresponding `pending_shared_address_signing_paths` rows for A and B (`createNewSharedAddressByTemplate` in `wallet_defined_by_addresses.js`, lines 106-146).
2. Attacker C, a paired correspondent of A but not part of this negotiation, obtains or derives the same `address_definition_template_chash` (e.g., by observing the `create_new_shared_address` offer sent to another device, or by re-deriving `objectHash.getChash160` over a guessed/known template).
3. C sends A a `reject_new_shared_address` device message with `{address_definition_template_chash: <the chash>}`.
4. In `wallet.js` (lines 228-234), A's node checks only `ValidationUtils.isValidAddress(body.address_definition_template_chash)` and calls `walletDefinedByAddresses.deletePendingSharedAddress(chash)`.
5. `deletePendingSharedAddress` (`wallet_defined_by_addresses.js`, lines 230-234) deletes the `pending_shared_addresses` and `pending_shared_address_signing_paths` rows unconditionally, aborting A and B's in-progress shared-address negotiation, without C ever being a recorded participant.
