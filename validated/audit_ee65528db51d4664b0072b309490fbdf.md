This is a valid analog: the multi-organization webhook signature check authenticates against `repository.owner.login`, but the resource actually mutated (`Repository.from_github_repo_name`, invoked via `Handler#stacks` in `app/models/shipit/webhooks/handlers/handler.rb#L32-L38`) is looked up from `repository.full_name` — a distinct, independently attacker-controlled field in the same unverified JSON body. Because signature verification happens on the raw payload as a whole (it doesn't bind `full_name`'s owner segment to `owner.login`), an attacker who holds a valid webhook secret for one configured GitHub organization can forge a `full_name` claiming a different organization/repository and trigger writes (queued `GithubSyncJob`, `Commit`/`Status` creation, etc.) against a stack that belongs to an organization whose secret they never had.

### Title
Webhook signature verified against `repository.owner.login` while writes are keyed on independently-attacker-controlled `repository.full_name`, enabling cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/repository.rb])

### Summary
In multi-organization deployments, `Shipit.github(organization:)` selects a distinct `webhook_secret` per GitHub organization [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to check the HMAC signature against using `repository_owner`, itself read straight out of the unverified JSON body (`params.dig('repository','owner','login')`) [2](#0-1) [3](#0-2) . However, once the signature "passes," the event handler resolves the target `Repository`/`Stack` not from `repository.owner.login`, but from the separate `repository.full_name` field, via `Handler#repository_name` → `Repository.from_github_repo_name` [4](#0-3) [5](#0-4) . Nothing enforces that `full_name`'s owner segment matches `owner.login`.

### Finding Description
The equality that should hold is: `organization whose secret authenticated the request == organization that owns the repository being written to`. Before the fix would apply, these are two independently-controlled JSON fields inside the same unsigned-until-verified request body — `repository.owner.login` (used only to pick the HMAC secret) and `repository.full_name` (used only to resolve the `Repository`/`Stack` to mutate). Since Rack/Rails parses `request.raw_post` once and HMAC-verifies the whole raw body, the signature does prove the *bytes* came from a holder of *some* configured organization's secret — but it does not prove which logical fields the request author is entitled to reference. An attacker who legitimately controls (or has leaked) the webhook secret for `OrgA` can set `repository.owner.login = "orga"` (satisfying `verify_signature`, since `Shipit.github(organization: "orga")` is the app whose secret matches) while setting `repository.full_name = "orgb/target-repo"`. `PushHandler#process` (or `StatusHandler`, `CheckSuiteHandler`, etc.) then calls `stacks` → `Repository.from_github_repo_name("orgb/target-repo")`, which is looked up purely by DB columns `owner`/`name` with no relation back to `owner.login` used at verification time [6](#0-5) .

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" binding: it lets an attacker who possesses valid credentials (webhook secret) for one onboarded GitHub organization forge webhook events that mutate state for stacks belonging to a *different* organization onboarded on the same Shipit instance — e.g. enqueuing `GithubSyncJob` for `OrgB`'s stack, injecting fabricated commit statuses (`StatusHandler`) that influence CI gating for deploys, or check-suite/PR events that affect merge/deploy eligibility for repositories they have no legitimate access to. This is a cross-repository/cross-organization write achieved without ever holding `OrgB`'s webhook secret, satisfying the "cross-repository writes" High/Critical impact bar for a multi-tenant Shipit deployment (multiple GitHub orgs configured under `secrets.github`, as documented in `config/secrets.development.example.yml#L18-L38`).

### Likelihood Explanation
Requires a Shipit instance configured for multiple GitHub organizations (each with its own `webhook_secret`) and an attacker who legitimately possesses (or has otherwise obtained) the webhook secret for at least one of those organizations — a scenario this multi-tenant feature explicitly exists to support, so it is a realistic configuration, not a hypothetical one. No GitHub App private key, `ApiClient` token, or `Shipit` session/`User` account is required — only the ability to POST a crafted, HMAC-signed body to the shared `/github/webhooks` endpoint.

### Recommendation
Bind organization/repository consistently: verify the signature using the same authoritative identity that will be used to resolve the target repository, or better, derive both from a single field. Concretely, in `WebhooksController#verify_signature`, resolve the target `Repository` first (from `repository.full_name`), derive its `owner` from that record, and require `repository.owner.login` (or the `organization.login` fallback) to match that resolved owner before selecting the GitHub app secret — rejecting the request otherwise. Alternatively, once a repository/stack is resolved in the handler, re-validate that its `owner` equals the organization whose secret validated the signature before performing any mutation.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with distinct `webhook_secret`s (per `config/secrets.development.example.yml` schema).
2. As an attacker who has `orga`'s webhook secret, craft a `push` event JSON body with:
   - `repository.owner.login = "orga"`
   - `repository.full_name = "orgb/target-repo"`
   - `ref = "refs/heads/<orgb-stack-branch>"`, `after = "<attacker-controlled sha>"`
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, raw_body)>` and POST to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orga")` and the signature validates successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgb/target-repo")`, matching `orgb`'s stack, and enqueues `GithubSyncJob` / triggers `sync_github` for it — despite the attacker never possessing `orgb`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
