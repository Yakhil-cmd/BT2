### Title
Webhook signature verification fails open when `webhook_secret` is unset, allowing unauthenticated forgery of `membership` events to escalate into `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever no `webhook_secret` is configured for the organization resolved from the *unauthenticated* payload, instead of failing closed. This mirrors the reported bug class ("a payload field acted on but never covered by the verified signature"): the `WebhooksController` treats the request as cryptographically verified even though no actual signature check occurred, and then hands the untrusted JSON body straight to `Shipit::Webhooks::Handlers::MembershipHandler`, which mutates `Team`/`Membership` records — the same records `User#authorized?` and `Shipit.github_teams` rely on for access control.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/org config from attacker-controlled JSON (`repository_owner`) and calls: [1](#0-0) 

The actual check lives in `GitHubApp#verify_webhook_signature`: [2](#0-1) 

Note line 77: `return true unless webhook_secret`. If the organization's `webhook_secret` config value is blank (`@webhook_secret = @config[:webhook_secret].presence`, so `nil`/empty strings collapse to `nil`), the method reports the request as verified without ever checking any HMAC — i.e., the "verified" boolean is disconnected from the actual payload content. The equality that should hold — `signature_verified == payload_is_authentic` — is broken: `signature_verified` is hardcoded `true`, while `payload_is_authentic` is attacker-controlled.

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw untrusted JSON to registered handlers: [3](#0-2) 

For the `membership` event, `Shipit::Webhooks::Handlers::MembershipHandler#process` trusts `params.team`, `params.organization.login`, and `params.member.login` completely to create/find a `Team` and add/remove members: [4](#0-3) 

`Team` records created/updated this way back `Shipit.github_teams`, which gate application-wide authorization via `User#authorized?`: [5](#0-4) [6](#0-5) 

Because the membership handler performs `User.find_or_create_by_login!(params.member.login)` and `team.add_member(member)` purely from payload fields, an attacker who can reach the public `WebhooksController#create` endpoint (no session, no API token, no repository access — a strictly unauthenticated HTTP POST) can add an arbitrary (or attacker-controlled/self-created) GitHub login as a member of a `Team` that maps onto one of `Shipit.github_teams`, thereby granting that login `authorized?` status in Shipit — as long as that org's `webhook_secret` is not configured (a state the engine allows and does not fail closed against).

### Impact Explanation
This is a High-impact finding: it is a direct escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-impact categories. An unauthenticated party can grant themselves (or any GitHub login they control) membership in the team(s) gating access to the whole Shipit instance, bypassing the entire authentication/authorization model (`force_github_authentication`) without possessing any credential, session, or GitHub org membership.

### Likelihood Explanation
Exploitability depends entirely on the runtime configuration state: it fires only for organizations whose `webhook_secret` is unset/blank in `secrets.yml`. The code path itself, however, is a genuine fail-open defect in `lib/shipit/github_app.rb` rather than a misconfiguration enforced by documentation-required steps in the engine's own runtime logic — the method silently treats "no secret configured" as "verified," rather than raising or rejecting. Given that `webhook_secret` is an optional field in the config schema (`.presence` gracefully accepts blank), any deployment that has not explicitly set it per-organization is silently exposed with no error or warning at boot or request time.

### Recommendation
Change `GitHubApp#verify_webhook_signature` to fail closed: if `webhook_secret` is blank, reject the request (return `false`) rather than short-circuiting to `true`, or raise a configuration error at boot time if any configured GitHub App/organization lacks a `webhook_secret`. Additionally, consider validating that the `organization`/`team`/`member` payload fields used by `MembershipHandler` are only trusted once the whole raw body has passed HMAC verification, and add explicit safeguards (e.g., a `Shipit.require_webhook_secret!` boot-time check) so silent fail-open configuration is not possible.

### Proof of Concept
1. Deploy Shipit with a GitHub App/organization entry in `secrets.yml` that omits `webhook_secret` (or sets it to an empty string) — a state the code accepts without error (`lib/shipit/github_app.rb:50`, `.presence`).
2. As an unauthenticated attacker, POST directly to the mounted `WebhooksController#create` endpoint with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": {"id": 999999, "name": "Fake Team", "slug": "fake-team", "url": "https://example.com"},
  "organization": {"login": "<victim-org>"},
  "member": {"login": "<attacker-github-login>"}
}
```
No `X-Hub-Signature` header is required to be valid — any value (or none) will pass because `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `MembershipHandler#process` creates a new `Team` record (or reuses one matching `github_id: 999999`) and adds the attacker's login as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
4. If an operator later configures `Shipit.github_teams` to include a team with that handle (or if the attacker can guess/target an existing required team's `github_id`), the attacker's `User` record now satisfies `User#authorized?` and can authenticate into the full Shipit UI/session, bypassing GitHub org-membership-based access control entirely.

Note: I was unable to fully verify from the index whether `docs/setup.md` explicitly marks `webhook_secret` as mandatory versus optional (the file content did not return in my search, likely due to index/citation constraints on `docs/**`, which is also explicitly out-of-scope for citation per the rules), so I cannot confirm whether this is purely a documentation gap or a pure code-level fail-open bug; the code-level behavior itself (`return true unless webhook_secret`) is confirmed directly from `lib/shipit/github_app.rb`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
