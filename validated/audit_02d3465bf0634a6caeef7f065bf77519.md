### Title
Self-beneficiary `DeleteAccount` action burns the deleted account's remaining balance instead of refunding it - (File: `runtime/runtime/src/actions.rs`)

### Summary
When an account is deleted via the `DeleteAccount` action with `beneficiary_id` set to the account itself (the natural/default choice when a user "deletes their own account and refunds themselves"), the account's leftover balance is permanently burned rather than returned to anyone. This mirrors the Unlock `transferFrom` `_from == _recipient` bug class: an unremarkable, easily-triggered self-referential input causes unintended, irreversible loss of user funds instead of a safe no-op or an explicit rejection.

### Finding Description
`action_delete_account` computes the account's remaining balance and, if positive, queues a refund receipt addressed to `delete_account.beneficiary_id`, then immediately removes the account from state: [1](#0-0) [2](#0-1) 

The refund receipt is built via `Receipt::new_balance_refund`, which sets `predecessor_id = "system"` and `receiver_id = beneficiary_id`: [3](#0-2) 

There is no check anywhere in `action_delete_account`, `check_account_existence`, or action validation that rejects `beneficiary_id == account_id`. The default helper used across the test/integration harness for "delete my own account" explicitly sets the beneficiary to the signer's own account id: [4](#0-3) 
This is exactly the pattern exercised by `test_delete_account_ok`, which deletes `eve_dot_alice_account()` with `beneficiary_id = eve_dot_alice_account()` (self): [5](#0-4) 
That test only asserts the delete succeeds and the account no longer exists - it never checks what happened to `money_used`, so this loss path is not covered by the existing test.

When the refund receipt is later processed, it targets an account that no longer exists (because it was just deleted). In `apply_action`, `is_refund` is computed from `predecessor_id().is_system()`, which is `true` for this receipt, forcing `implicit_account_creation_eligible = false`: [6](#0-5) 
`check_account_existence` for a `Transfer` action against a nonexistent account defers to `check_transfer_to_nonexisting_account`, which — because `implicit_account_creation_eligible` is `false` — returns `AccountDoesNotExist` instead of allowing implicit account creation: [7](#0-6) [8](#0-7) 

Finally, because this failing receipt is itself a system refund (`predecessor_id().is_system()`), the runtime's failure-handling path burns the deposit rather than generating any further refund: [9](#0-8) 

So the sequence is: user balance → refund receipt to self → account doesn't exist → transfer rejected as `AccountDoesNotExist` → deposit added to `other_burnt_amount` → funds permanently destroyed, with no error surfaced to the original `DeleteAccount` transaction (which still reports success).

### Impact Explanation
Any account holder (or anyone with a full-access key / permission to delete the account, analogous to Unlock's "key manager or approved user") who submits a `DeleteAccount` action with `beneficiary_id` equal to the very account being deleted — which is the natural, default choice for "delete my account and keep the leftover balance" — permanently loses that balance. There is no revert, no error surfaced on the original transaction, and no path to recovery. This is a genuine, protocol-level, unauthorized destruction of user balance (irreversible fund loss), reachable purely from a standard user-submitted transaction with no validator or node compromise required.

### Likelihood Explanation
High reachability, low complexity: this requires only a single ordinary `DeleteAccount` action from any account holder, exactly matching what the integration test helper `delete_account` produces by default (self as beneficiary). No malicious actor, network condition, or special privilege is needed — only the same kind of "input validation gap on self-reference" called out in the original Unlock report. The main mitigating factor is that this destroys the caller's own funds rather than enabling theft from a third party, similar to the "requires user error" caveat noted in the original report, but the ease of triggering it via the documented/default beneficiary pattern raises the likelihood that it happens accidentally in production tooling or wallets that default beneficiary to the account owner.

### Recommendation
Add an explicit check in `action_delete_account` (or in action validation prior to processing) rejecting `delete_account.beneficiary_id == *account_id` with a clear `ActionErrorKind` (e.g. `DeleteAccountBeneficiaryIsSelf`), mirroring the Unlock recommendation of `require(_from != _recipient, ...)`. Alternatively, if the balance refund is issued while the account still exists at that point in the state, credit it synchronously before deleting the account rather than emitting a follow-up receipt back to the now-removed account.

### Proof of Concept
1. Create account `eve.alice.near` with balance `money_used` (as in `test_delete_account_ok`): [10](#0-9) 
2. Submit `DeleteAccount { beneficiary_id: eve.alice.near }` from `eve.alice.near` itself (this is exactly what `NodeUser::delete_account(signer_id, receiver_id)` does by default): [4](#0-3) 
3. `action_delete_account` queues `Receipt::new_balance_refund(&eve.alice.near, account_balance)` and deletes the account: [1](#0-0) 
4. The DeleteAccount transaction reports `FinalExecutionStatus::SuccessValue(Vec::new())`, but the follow-up refund receipt to `eve.alice.near` fails with `AccountDoesNotExist` (via `check_transfer_to_nonexisting_account`), and because it is a system-originated receipt, the balance is added to `stats.balance.other_burnt_amount` and permanently lost, per the burn path in `apply_action_receipt`: [9](#0-8) 
5. Extending `test_delete_account_ok` to assert the total supply/`money_used` balance after deletion (instead of only checking the account no longer exists) would demonstrate that `money_used` is gone from circulation, credited to no account.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
