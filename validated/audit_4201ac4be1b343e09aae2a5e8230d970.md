### Title
Webhook Signature Verified Against Payload-Chosen Organization While Repository Written Is Taken From a Different Payload Field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit.github(organization:)` supports multi-tenant configuration where each GitHub organization has its own webhook secret (or none). `WebhooksController#verify_signature` selects *which* organization's secret to verify the HMAC signature against by reading an unauthenticated, attacker-controlled field from the same request body it is about to validate. The handler that actually processes the webhook (`Repository.from_github_repo_name`) then resolves the target repository from a *different* field of that same unauthenticated body. This creates a mismatch between "the organization whose secret was used to authenticate the request" and "the repository that is ultimately written to."

### Finding Description
`WebhooksController#verify_signature` computes the organization used for signature verification as: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the JSON body (`params.dig('repository','owner','login')`) before the signature has been checked, and is used to look up which `GitHubApp`/secret to validate with, via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly treats a blank/unconfigured `webhook_secret` for that organization as "always verified": [4](#0-3) 

Once the request passes this check, the actual event handler resolves the target `Repository`/`Stack` from a **different** field of the same payload — `repository.full_name` — with no relation back to `repository_owner`: [5](#0-4) 

For example `PushHandler` uses `stacks` (derived from `repository.full_name`) combined with `ref`/`after` from the body to trigger a GitHub sync against real commits/branches of the resolved stack: [6](#0-5) 

**The binding that should hold:** organization whose secret authenticated the webhook == organization owning the repository the handler acts on. In a multi-org deployment, an attacker can craft a body where `repository.owner.login` (or `organization.login`) names an organization configured with **no** `webhook_secret` (or one the attacker knows), while `repository.full_name` names an entirely different, unrelated repository/stack that the attacker does not control. Signature verification succeeds because it is keyed off the attacker-supplied `repository_owner`, not off the repository actually acted on. This is a confused-deputy pattern: "organization authenticated" ≠ "repository written."

### Impact Explanation
If any organization in the deployment's multi-org GitHub config has no `webhook_secret` configured (a supported, documented state — `verify_webhook_signature` explicitly returns `true` when blank), an unauthenticated network attacker can forge webhooks (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) for any repository tracked by Shipit, simply by setting `repository.owner.login` to the secret-less org and `repository.full_name` to the target repo. Depending on handler, this can trigger unauthorized `sync_github` calls (which can advance/rewrite `last_deployed_commit`/deploy-eligibility state), forged CI/check statuses accepted as real (`StatusHandler`/`CheckSuiteHandler` feed into deploy safety checks), or team/user membership mutations (`MembershipHandler`). Because Shipit deploy gating relies on these webhook-fed statuses and commit records, this can contribute to an unauthorized deploy path, matching the "unauthorized deploy" High/Critical impact bucket.

### Likelihood Explanation
Requires a deployment that configures more than one GitHub organization (`Shipit.github_organizations` with multiple entries) where at least one has no `webhook_secret` set, or where an attacker otherwise knows one organization's secret but wants to write to another organization's repositories. This is a realistic misconfiguration in a genuinely multi-tenant setup (a common documented use case for the `organization:` keyword arg), not a modification of how the engine is mounted. No authenticated session, API token, or GitHub write access is required — only network access to `POST /webhooks`.

### Recommendation
- After verifying the signature for the claimed `repository_owner`/`organization`, cross-check that the repository/organization actually referenced by the payload's `repository.full_name` (and any handler logic) belongs to that same verified organization before dispatching to handlers.
- Reject webhooks where `repository.full_name`'s owner does not match the verified `repository_owner`.
- Treat a blank/unconfigured `webhook_secret` for an organization as a hard misconfiguration (fail closed) rather than "always verified," at minimum logging/alerting so operators cannot unknowingly leave an org without a secret while other orgs are configured.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`: `org-a` (has repos with real Stacks, e.g. `org-a/critical-repo`) and `org-b` (no `webhook_secret` set, e.g. a low-security/test org onboarded later).
2. Attacker (no credentials) sends `POST /webhooks` with header `X-Github-Event: push` and body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha already known to be valid for org-a/critical-repo>",
     "repository": { "full_name": "org-a/critical-repo", "owner": { "login": "org-b" } }
   }
   ```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'org-b')`; since `org-b` has no `webhook_secret`, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `stacks` via `repository.full_name` = `org-a/critical-repo`, and triggers `stack.sync_github(expected_head_sha: params.after)` for `org-a`'s real stack — despite the request only ever being "authenticated" against `org-b`'s (non-existent) secret.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
