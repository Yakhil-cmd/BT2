### Title
Stale `current-total-staked` snapshot overwrites `protocol-bonds-total-staked` after intervening reward-settlement calls in `register-for-bond` - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond` reads the bond's total staked sats (`current-total-staked`) at the *top* of the function, before calling `settle-rewards` / `settle-staker-rewards`, `roll-sbtc`, and `add-staker-to-bond-cycles`. It then writes `protocol-bonds-total-staked` using that stale value plus the new stake, discarding any change those intervening calls made to the same map entry. This is structurally identical to the Flatcoin `checkSkewMax`/`updateGlobalPositionData` ordering bug: a value that a later state-mutating call is responsible for updating is captured *before* that call runs, and is then used to perform the final state write, silently reverting/ignoring the update.

### Finding Description
In `register-for-bond`: [1](#0-0) 

`current-total-staked` is fetched via `get-total-shares-staked-for-cycle` in the `let` bindings, i.e. at the very start of the transaction, before any state mutation.

Later, after `settle-rewards` and `settle-staker-rewards` are invoked (which mutate reward/settlement state for the signer and staker at this cycle/bond-index): [2](#0-1) 

and after `roll-sbtc` and other membership updates run, the function performs the final write to the shared total using the *already-stale* `current-total-staked`: [3](#0-2) 

If `settle-rewards`/`settle-staker-rewards` (or any other call executed between the initial read and the final `map-set`) touches `protocol-bonds-total-staked` for the same `bond-index` — e.g., to reconcile/settle a previous partial stake, roll over shares, or adjust totals as part of reward settlement — that update is clobbered by the `map-set` at line 793-795, which recomputes the new total from the pre-settlement snapshot rather than the current on-chain value. This is exactly the class of bug identified in the Flatcoin report: `checkSkewMax` used `stableCollateralTotal` captured before `updateGlobalPositionData` updated it, causing the guard/derived value to be inconsistent with post-update state.

### Impact Explanation
If the intervening settlement calls do modify `protocol-bonds-total-staked` (directly or via a helper that shares the same map), the final write in `register-for-bond` will either:
- double-count sats that were already reflected by the settlement step, inflating the recorded total staked for a bond beyond what is actually backed by locked STX/sBTC, or
- erase a legitimate decrement performed during settlement (e.g., removal of an expired/rolled-over staker's shares), causing the total to overstate real backing.

Either outcome breaks the equality between `protocol-bonds-total-staked` and the sum of individually locked/committed stakes — the exact "double-counting a commitment" impact category (Critical: double-counting a commitment or reward). This map is presumably used to gate reward-slot capacity and payouts for signers, so an inflated total could allow reward shares/slots to be allocated in excess of what is actually locked, or could cause the accounting ledger to diverge from real balances over repeated `register-for-bond` calls.

### Likelihood Explanation
Reachable by any unprivileged staker simply by calling `register-for-bond` — no elevated privileges are required. The likelihood that this manifests as a real bug hinges on whether `settle-rewards` / `settle-staker-rewards` actually mutate `protocol-bonds-total-staked` for the same `bond-index` before the final `map-set` at line 793-795; I was not able to confirm the body of `settle-rewards`/`settle-staker-rewards` within the remaining investigation budget. If those functions are pure reward-payout mechanisms that never touch `protocol-bonds-total-staked`, this ordering is harmless (merely a stale local read that happens to still be correct because nothing else wrote to that key in between). This uncertainty should be resolved by inspecting `settle-rewards`, `settle-staker-rewards`, and `get-total-shares-staked-for-cycle` in full before treating this as confirmed rather than a plausible analog.

### Recommendation
Re-read `protocol-bonds-total-staked bond-index` immediately before the `map-set` at line 793-795 (i.e., after `settle-rewards`, `settle-staker-rewards`, and `roll-sbtc` have run), rather than relying on the value captured in the initial `let` bindings — mirroring the Flatcoin fix of moving the read/check to occur after the state-mutating call rather than before it.

### Proof of Concept
Could not be concretely demonstrated without confirming that `settle-rewards`/`settle-staker-rewards` write to `protocol-bonds-total-staked` for the given `bond-index`; this requires reading their full definitions in `pox-5.clar`, which was not completed within the available tool budget. The structural pattern (stale read → intervening mutating calls → stale-based write) is confirmed by the cited line ranges, but the concrete state-corruption path is unverified.
