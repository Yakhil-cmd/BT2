## Analysis: Address-definition revocation is not enforced when validating off-chain signed packages (`is_valid_signed_package` / `signed_message.validateSignedMessage`)

### Title
Improper revocation check for address definitions in `is_valid_signed_package`/`validateSignedMessage` allows use of a superseded (revoked) signing definition - (File: signed_message.js)

### Summary
The Keystone CVE describes an authentication bypass where a PKI token's revocation status is not checked, so a revoked token is still accepted. In `ocore`, the analogous credential is an address **definition** (the on-chain-registered signing policy for an address, changeable via `address_definition_change`). The off-chain signed-message verifier `validateSignedMessage()` — used directly by AAs through the `is_valid_signed_package` oscript operator — resolves the signer's definition **as of an attacker-chosen historical `last_ball_unit`**, not the address's *current* definition, and never checks whether the definition has since been revoked/replaced.

### Finding Description
`signed_message.js`'s `validateOrReadDefinition()` looks up the definition to use for verifying a signed package like this: [1](#0-0) 

It takes `objSignedMessage.last_ball_unit` (fully attacker/sender-controlled), resolves its `main_chain_index`, and then calls `storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, ...)` — i.e. "what was this address's definition at that (arbitrary, possibly old) point in the DAG" rather than "what is this address's definition now." There is no lower bound / recency requirement on `last_ball_unit`, and no check equivalent to the `'seen definition change'` oscript operator (which does exist elsewhere in the codebase specifically to detect that an address's definition changed after a given point, see `definition.js` lines 835-853) is applied here.

This function is invoked directly from the AA formula evaluator's `is_valid_signed_package`: [2](#0-1) 

The only freshness constraint enforced is that `last_ball_unit`'s mci is `<= mci` (i.e., not from the future) — there is no check that the definition used to produce the signature is still the address's *current* definition, nor any requirement that no `address_definition_change` has occurred for that address since `last_ball_unit`.

`storage.readDefinitionByAddress` with an explicit historical `mci` is precisely how the DAG's own unit-authoring validation determines "the definition in force at that point," but on-chain unit validation additionally guards this with `checkNoPendingChangeOfDefinitionChash` / `checkNoPendingDefinition` (see `validation.js` lines 1345-1419) to stop a stale/soon-to-be-superseded definition from being used to author new units. `validateSignedMessage`/`is_valid_signed_package` has no equivalent safeguard — it is a completely separate, weaker verification path reachable by any AA trigger sender or private-payment counterparty who supplies an `is_valid_signed_package`-checked object.

### Impact Explanation
This flow is a first-class, documented AA authorization primitive: the bundled sample templates `payment_channels.oscript` and `order_book_exchange.oscript` use `is_valid_signed_package(trigger.data.sentByPeer, $addressA)` to authenticate off-chain instructions from a payment-channel counterparty or order signer, and act on the trusted message to move AA-held funds: [3](#0-2) [4](#0-3) 

If `addressA` is a shared/multisig address and its definition is later changed on-chain (e.g., a compromised or departing co-signer is removed via `address_definition_change`), anyone who could produce a valid signature under the *old* definition can still construct a package that references an old, still-stable `last_ball_unit` (from before the redefinition) and pass `is_valid_signed_package` indefinitely — the AA has no way to know the signing authority for that message was revoked. This can drive the "fraud proof"/"close channel" branches or order execution with authorization that the address owner explicitly revoked, causing AA fund loss/misdirection for any AA built on this exact, sample-endorsed pattern.

### Likelihood Explanation
Medium: it requires (a) an address whose definition changes over its lifetime (a normal, supported operation via `address_definition_change`) and (b) an AA that authenticates counterparties via `is_valid_signed_package` without independently re-checking `'seen definition change'` for that address — which is exactly the pattern shown in the repository's own reference oscript samples, making it a realistic design trap rather than a contrived edge case.

### Recommendation
`validateSignedMessage`/`is_valid_signed_package` should, at minimum, verify that no `address_definition_change` for the signer's address has been stabilized between `last_ball_unit` and the evaluation `mci` (mirroring the existing `'seen definition change'` check in `definition.js`), or require verification against the address's *current* definition and reject stale `last_ball_unit` references beyond a bounded recency window. Alternatively, document and enforce this as a mandatory combined check so AA authors cannot unknowingly rely on a revocable-but-unrevoked-in-practice credential.

### Proof of Concept
1. Address `SHARED` (e.g., channel party A) is defined as a 2-of-2 (or similar) multisig with keys `K1, K2`.
2. `SHARED` signs an off-chain `signed_message` package (e.g., channel state) with `K1+K2`, referencing an already-stable `last_ball_unit = L0`.
3. Owner rotates `SHARED`'s definition (e.g. removes `K1`, adds `K3`) via `address_definition_change`; this becomes stable at `mci M1 > mci(L0)`.
4. A party who possessed `K1` (now removed) crafts a new `trigger.data` payload embedding the old signed package (still referencing `last_ball_unit = L0`, still stable and `<= current mci`).
5. `is_valid_signed_package(trigger.data.sentByPeer, addressSHARED)` returns `true`, because `signed_message.validateSignedMessage` resolves the definition at `mci(L0)` (the old, revoked definition) rather than checking the currently-active definition or whether it was later revoked — allowing the AA to act on authorization from a party whose signing rights were explicitly revoked on-chain.
