### Title
Crafted AA-triggering unit can crash the entire full node via unguarded dry-run trigger execution - (File: network.js)

### Summary
An unprivileged unit poster can send a normal payment unit whose output pays a Cube.js-style crafted-request DoS analog: a payment to an existing AA address triggers a synchronous, unguarded "dry run" of the AA response logic on the hot validation path. If that dry run throws instead of routing the error through a callback, the resulting unhandled exception is intentionally re-thrown by the global exception handler, crashing the whole hub/full node process for all connected peers — matching the "improper handling of exceptional condition" (CWE-755) DoS pattern in the Cube.js advisory.

### Finding Description
When a new unit is validated and it triggers a primary AA (any payment message that has an output addressed to an AA), and `conf.bDryRunNewTriggers` is enabled (non-light node, unstable unit), `network.js`'s `ifOk` handler proactively "dry runs" the AA trigger before deciding whether to accept the submitting unit: [1](#0-0) 

The comment explicitly states the intent — *"if it would crash, let it crash now, not when we execute the trigger for real"* — meaning the code path deliberately allows an exception from `aa_composer.getTrigger`/`aa_composer.dryRunPrimaryAATrigger` to propagate rather than being funneled into a controlled error callback. Because `ifOk` is declared `async`, any *synchronous* throw inside this block (or a rejected promise from `dryRunPrimaryAATrigger`) turns into a rejected promise that is never awaited/caught by the caller in `validation.js`, which invokes `callbacks.ifOk(objValidationState, unlock)` fire-and-forget style: [2](#0-1) 

Any unhandled exception/rejection reaching the top level is deliberately fatal: the process installs a global handler that logs and then re-throws to intentionally crash the process "to avoid ending up in an inconsistent state": [3](#0-2) 

This mirrors the general pattern already present elsewhere in the codebase where AA-trigger validation paths use bare `throw Error(...)` for conditions assumed "impossible" but which are in fact influenced by attacker-supplied unit/trigger content, e.g. the analogous non-dry-run trigger-processing code in `aa_composer.js`: [4](#0-3) 

Because the dry run executes attacker-influenced formula/state evaluation (the AA definition plus the attacker-crafted trigger unit) ahead of the trigger actually being queued, any edge case in `getTrigger`, `dryRunPrimaryAATrigger`, or the oscript/formula evaluator (`formula/evaluation.js`) that throws synchronously instead of returning an error via callback will not be contained — it escapes to an unhandled rejection and crashes the node.

Note: I was not able to fully inspect the bodies of `aa_composer.getTrigger` and `aa_composer.dryRunPrimaryAATrigger` within this session (only call sites and neighboring functions with similar `throw Error(...)` patterns were retrieved), so the exact triggering payload/edge case inside those two functions is not confirmed from the index and would need direct code review to pin down a concrete PoC input.

### Impact Explanation
If reachable with a crafted (but otherwise valid-looking) payment unit targeting an AA address, this causes the entire full/hub node process to crash (`throw err` in the `uncaughtException` handler), taking down the network-facing service for all peers connected to that node — a "network unable to confirm new units" condition consistent with the required impact bar (concrete DoS of a validating node), analogous to the Cube.js advisory's "entire Cube API unavailable" impact.

### Likelihood Explanation
The reachability precondition is low-effort for an attacker: post a unit containing a payment message whose output address is a known/existing AA address, with `conf.bDryRunNewTriggers` enabled on the target node (this flag governs whether dry-run occurs) — this is the intended normal use path for interacting with AAs, not a privileged operation. The remaining uncertainty is whether `getTrigger`/`dryRunPrimaryAATrigger` (or the oscript evaluator they invoke) actually contain a reachable synchronous throw for some crafted trigger — this needs direct confirmation from the function bodies, which were not fully retrieved.

### Recommendation
- Wrap the dry-run block in `network.js` (`ifOk`) in a `try/catch` (and ensure `dryRunPrimaryAATrigger`'s returned/rejected promise is caught), converting any exception into a controlled validation error rather than letting it propagate as an unhandled rejection.
- Audit `aa_composer.getTrigger` and `aa_composer.dryRunPrimaryAATrigger` for any code path that can `throw` synchronously based on attacker-controlled trigger/unit content, and convert those into normal error returns.
- Reconsider the "let it crash now" design: a single attacker-influenced dry run should not be able to take down node availability; at minimum, isolate/catch failures from this pre-emptive dry run and log-and-continue instead of crashing the process.

### Proof of Concept
Conceptual (not independently executed, since the internals of `getTrigger`/`dryRunPrimaryAATrigger` could not be fully retrieved in this session):
1. Enable/target a full node running with `conf.bDryRunNewTriggers = true` and `conf.bLight = false`.
2. Identify or deploy an AA address with a definition that, when combined with an attacker-crafted trigger unit (e.g., malformed/edge-case `data` or `payload` values in the triggering payment unit), causes `aa_composer.getTrigger` or `aa_composer.dryRunPrimaryAATrigger` to throw synchronously instead of erroring through a callback.
3. Post a normal payment unit with an output to that AA address via the p2p/API unit-submission path.
4. During validation's `ifOk` handling in `network.js:1271-1281`, the dry run executes; the thrown/rejected exception is unhandled and reaches `process.on('uncaughtException', ...)` in `network.js:4530-4543`, which re-throws and crashes the node process, denying service to all its peers.
