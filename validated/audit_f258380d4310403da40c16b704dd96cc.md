### Title
Unwhitelisted environment-variable interpolation in `Shipit::Stack#links` leaks process `ENV` secrets into rendered stack page - (File: `app/models/shipit/stack.rb`, `lib/shipit/environment_variables.rb`)

### Summary
`Stack#links` interpolates `shipit.yml`-defined link URLs using `EnvironmentVariables#interpolate`, which falls back to Ruby's process `ENV` for any `$VARNAME` not present in the stack's own env hash, with no whitelist check. Unlike deploy/rollback/task variable interpolation, which is always passed through `EnvironmentVariables#permit` against a declared whitelist before being used, `links` skips `permit` entirely, so any `$SOME_SECRET` reference in a contributor-supplied `links:` template is resolved directly against Shipit's process environment and rendered as a clickable `href` on the stack page.

### Finding Description
The broken binding: the value substituted into the rendered link (`link_to name.humanize, url`) is claimed by design to be limited to `Stack#env` (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH` — [1](#0-0) ), but in practice it equals `stack.env.fetch(var) { ENV[var] }`, i.e. it can equal Shipit's raw process `ENV`, not a stack-approved variable.

Path:
- `Stack#links` builds `EnvironmentVariables.with(env)` (only the fixed `Stack#env` hash) and calls `context.interpolate(url)` for every `links_spec` entry taken straight from `cached_deploy_spec.links` — the parsed `shipit.yml` — with no `permit`/whitelist step: [2](#0-1) 
- `EnvironmentVariables#interpolate` replaces every `$VARNAME` token by `Shellwords.escape(@env.fetch(variable) { ENV[variable] })`, falling back to process `ENV` whenever the name isn't in the (small, fixed) `Stack#env` hash: [3](#0-2) 
- By contrast, deploy/rollback/task variable interpolation always goes through `EnvironmentVariables#permit`, which raises `NotPermitted` for any variable not in the declared whitelist: [4](#0-3) , [5](#0-4) , [6](#0-5) . `links` has no equivalent gate.
- The interpolated URL is rendered directly as an `href` on every stack page view: [7](#0-6) 

Attacker flow: a contributor opens a pull request adding/modifying `shipit.yml`'s `links:` section, e.g. `links: {monitoring: 'https://dash.example.com?token=$API_TOKEN'}`. Once this configuration is picked up as the stack's `cached_deploy_spec` (normal `shipit.yml` sync on push to the tracked branch), any user who can view that stack's page (`GET /stacks/:id`) will see `API_TOKEN` (or any other process-level secret name the attacker guesses, e.g. `GITHUB_TOKEN`, `SECRET_KEY_BASE`) substituted from Shipit's process `ENV` into the rendered link, exposing it in the page/HTML source.

Existing guards do not stop this: `EnvironmentVariables#permit` (the whitelist mechanism) exists but is never invoked by `Stack#links`; `Stack#env` is fixed and doesn't include arbitrary secrets, but the `interpolate` fallback bypasses that boundary; view/controller authentication (`force_github_authentication`, team membership check) gate who can view the page, but do not filter what `links` renders.

### Impact Explanation
Any process-level environment variable of the Shipit host (potentially `GITHUB_TOKEN`, database credentials, deploy API tokens, etc., depending on what the host app exports via `ENV`) can be exfiltrated into a rendered page reachable by any authenticated/authorized Shipit user, without needing access to the underlying secret store or to the specific repository's deploy credentials. This is a class of information disclosure that crosses the intended trust boundary between "declared, stack-scoped env vars" and "the whole Shipit process environment," and is repeatable against any stack whose `shipit.yml` a contributor can influence and that eventually gets merged/synced.

### Likelihood Explanation
Requires: (1) a `shipit.yml` change (a `links:` entry referencing an undeclared `$VAR`) to land on the branch the stack tracks — normally via a merged pull request, a routine and low-friction contribution flow; (2) the named variable to actually exist in Shipit's process `ENV`, which the attacker must guess or infer (e.g. common names like `GITHUB_TOKEN`); (3) a viewer with legitimate access to the stack page. No Shipit secrets, session, or elevated GitHub role are needed to author the payload itself — only normal PR/contribution capability plus a maintainer merge.

### Recommendation
Whitelist environment variables used for `links` interpolation the same way deploy/rollback/task variables are handled: run `links` values through `EnvironmentVariables#permit` (or otherwise restrict the substitution to the fixed `Stack#env` keys) and remove or gate the `ENV[variable]` fallback in `EnvironmentVariables#interpolate` for contexts where the URL/text ends up rendered to end users, so undeclared `$VAR` references raise/`NotPermitted` or resolve to empty instead of leaking process env.

### Proof of Concept
```ruby
# test/models/shipit/stack_test.rb
test "#links must not leak process ENV variables not declared in stack env" do
  previous = ENV['API_TOKEN']
  ENV['API_TOKEN'] = 'super-secret-value'

  @stack.cached_deploy_spec = create_deploy_spec(
    "links" => { "monitoring" => "https://dash.example.com?token=$API_TOKEN" }
  )

  url = @stack.links.fetch("monitoring")

  # Binding under test:
  #   substituted value == Stack#env-approved variable   (expected/secure)
  #   substituted value == Shipit process ENV['API_TOKEN'] (actual/insecure)
  refute_includes url, "super-secret-value",
    "Stack#links must not interpolate undeclared vars from process ENV"
ensure
  ENV['API_TOKEN'] = previous
end
```
Running this against the current code fails the `refute_includes` assertion, confirming `ENV['API_TOKEN']` is substituted into the rendered link URL.
