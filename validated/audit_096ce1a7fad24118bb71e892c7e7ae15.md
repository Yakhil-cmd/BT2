### Title
`StatusHandler#process` applies GitHub status webhooks to commits by SHA alone, letting a webhook from one repository certify CI for a same-SHA commit belonging to a different stack/repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no scoping to the repository that sent the webhook. Every other handler (e.g. `PushHandler`) uses the `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` from `payload.dig('repository', 'full_name')` to restrict effects to the sending repository's own stacks, but `StatusHandler` does not use it at all.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`identity(who caused commit.success? to flip true) == identity(authorized to certify CI for victim_commit.stack.repository)`.

Trace:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) validates the HMAC using `Shipit.github(organization: repository_owner)` — this proves the payload came from *some* legitimately configured GitHub organization/app installation, but it says nothing about which `Commit`/`Stack` rows the payload's `sha` is allowed to affect.
2. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)` → `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This query is **global across all stacks/repositories** in the Shipit instance — it is not filtered by `payload.dig('repository', 'full_name')`. Contrast with `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes via `stacks.not_archived.where(branch:)`, where `stacks` (`Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`) is derived from the webhook's own `repository_name`.
3. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)` and `add_status`, which recomputes `status` and can trigger `Hook.emit(:commit_status/:deployable_status, ...)` and `stack.schedule_merges` (`app/models/shipit/commit.rb:366-386`) — real side effects on the *victim's* stack.
4. `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, where `success?`/`blocked?` are delegated to `status`, which is now derived from the forged status row. If the victim commit is unlocked and not otherwise blocked, `deployable?` flips to `true` purely from the attacker's own CI signal.
5. The DB has a unique index on `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb:1-5`), confirming the schema explicitly anticipates the *same SHA existing in multiple different stacks* — i.e., this cross-tenant SHA collision is a known, supported data shape, not a theoretical edge case, yet `StatusHandler` treats `sha` as if it were globally unique/owned by one repository.

Attacker request: attacker owns (or controls a fork/branch in) their own GitHub repository that is also configured as a Shipit stack (or simply owns any repository whose commit content — tree, parents, author/committer dates, message — is crafted to reproduce the exact same SHA as the victim's pending commit; git SHAs are content-addressed, not repository-scoped, so duplicating a public commit's exact content in another repo reproduces the same SHA). Attacker then triggers their own repository's real CI (or POSTs a `status` API call from their own repo context) to fire a legitimately-signed `status` webhook with `state: success` for that SHA. GitHub delivers it to Shipit's `/webhooks`, `verify_signature` passes (correct secret for the attacker's own org/repo), and `StatusHandler` blindly attaches that "success" to every `Commit` row sharing that SHA — including the victim's row in an unrelated stack.

Existing guards do not prevent this: `verify_signature` only authenticates "a message from GitHub for org X," not "this status applies only to stacks belonging to repository X." `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, etc.), not repository scope. `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant to webhook ingestion. No model validation ties `Status`/`Commit` update to the payload's `repository.full_name`.

### Impact Explanation
A `status` webhook that is entirely legitimate for the attacker's own (unrelated) repository can flip `Commit#deployable?` to `true` for a commit belonging to a different tenant's stack, allowing that victim commit to be merged/deployed (via `stack.schedule_merges`, `ContinuousDeliveryJob`) without any real passing CI run against the victim's own repository/CI configuration. This is a CI-gate bypass / cross-tenant record mutation: one repository's webhook traffic mutates another repository's `Commit`/`Status` state and can trigger an unauthorized deploy or merge. This matches the "Critical" category: a payload for one repository mutating another's commit/stack, leading to an unauthorized deploy.

### Likelihood Explanation
Preconditions: (a) the Shipit instance must host stacks for both the attacker's and the victim's repositories (or the attacker's own repository must at least exist and be able to emit a real, properly-signed webhook to this Shipit instance's `/webhooks` endpoint), (b) a `Commit` row for the identical SHA must exist in the victim's stack (e.g., because the victim's Shipit stack already ingested that commit via push/PR sync), (c) the victim commit must be unlocked (`locked? == false`) and not blocked by other blocking statuses — matching the exact preconditions given in the question. No Shipit secrets, session, or elevated GitHub permissions are required by the attacker; they only need control over their own repository/webhook traffic and the ability to reproduce or align on the shared SHA. This is repeatable against any stack/commit sharing a SHA reachable this way, for as long as the attacker can keep sending real `status` events.

### Recommendation
Scope `StatusHandler#process` to the sending repository the same way `PushHandler` does: use the `stacks` helper (via `payload.dig('repository', 'full_name')`) to restrict the affected commits, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create two stacks backed by two different `Repository` records (`repo-a/attacker`, `repo-b/victim`).
2. Create `victim_commit` in the victim stack and `attacker_commit` in the attacker stack, both with the identical `sha` value (allowed by the unique `(sha, stack_id)` index, since `stack_id` differs).
3. Assert preconditions: `victim_commit.locked? == false`, `victim_commit.deployable? == false` (no success status yet), and no `Status` row exists on `victim_commit` created via `stack_b.github_api.statuses`.
4. Build a webhook payload with `repository.full_name = 'repo-a/attacker'`, `sha` = the shared SHA, `state: 'success'`.
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature concerns, since the bug is in the handler, not in `verify_signature`).
6. Assert `victim_commit.reload.deployable? == true` even though the only status ever created for it came from a webhook whose `repository.full_name` was `repo-a/attacker`, not `repo-b/victim` — i.e., `victim_commit.statuses.where(stack_id: stack_b.id).exists?` is `true` despite no call to `stack_b.github_api.statuses` ever having been made.
7. Assert the equality fails: `webhook_repository_full_name ('repo-a/attacker') != victim_commit.stack.repository.full_name ('repo-b/victim')`, yet the status was still applied.
