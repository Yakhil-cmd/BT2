### Title
Liquidation debt cap and seizure math use oracle feed decimals instead of the pool's market decimals - ([File: contracts/controller/src/positions/liquidation/math.rs](contracts/controller/src/positions/liquidation/math.rs))

### Summary
CVE-2018-16554 is a numeric type/precision inconsistency: `ProcessGpsInfo` formats the same GPS altitude through a path where `float` and `double` disagree, producing wrong output. The analog in XOXNO Lending is a decimals-precision inconsistency in the liquidation planner: debt balances, per-leg unit values, and held-unit checks are computed with `feed.asset_decimals` (the number reported by the price aggregator) while every non-liquidation path unscales the same shares with `PoolSyncData.params.asset_decimals`. When the two decimals sources disagree, the liquidator-facing debt cap, USD valuation, and whole-unit seizure logic are scaled by the wrong power of ten, reachable by any unprivileged liquidator calling `liquidate`.

### Finding Description
In `calculate_repayment_amounts`, the ceiling-rounded debt cap for each repaid leg is computed as `unscale_borrow_ceil(env, position.scaled_amount, market_index.borrow_index, feed.asset_decimals)`, where `feed` comes from `cache.cached_price(&hub_asset.asset)` — i.e., the aggregator's `PriceFeedRaw.asset_decimals`. [1](#0-0)  The same feed decimals are then used to value the kept repayment in USD via `feed.usd_value_wad` (`Wad::from_token(amount, feed.asset_decimals) * price`). [2](#0-1) 

By contrast, the canonical decimals for a market are `PoolSyncData.params.asset_decimals`, which is what the pool itself uses when unscaling the identical shares (`self.params.asset_decimals` in `Cache::unscale_borrow_ceil`) and what the controller's own views use (`collateral_amount_for_hub_asset` pulls `cache.cached_pool_sync_data(hub_asset).params.asset_decimals`). [3](#0-2) [4](#0-3) 

The inconsistency propagates further:

- `repays_every_debt_leg` decides whether a plan closed a debt leg by comparing `entry.amount` against `unscale_borrow_ceil(..., entry.feed.asset_decimals)` — again feed decimals, not market decimals. [5](#0-4) 
- `one_unit_per_leg_usd` / `one_unit_per_debt_leg_usd` compute the "one native unit" slack at `feed.asset_decimals`. [6](#0-5) 
- `whole_unit_repayment` decides the `MIN_BORROWABLE_ASSET_DECIMALS` whole-unit branch and computes `held_units` from `to_asset_floor(env, feed.asset_decimals)`. [7](#0-6) 
- `calculate_seized_collateral` explicitly documents that seizure token amounts are expressed "at the feed's decimals", while `actual_ray`/share conversion is the market's. [8](#0-7) 

`usd_value_wad` itself is just `Wad::from_token(token_amount, self.asset_decimals).mul(price)`, so any decimals disagreement multiplies every leg's USD value by `10^(feed_decimals - market_decimals)`. [9](#0-8)  Nothing in `Context::cached_price`/`fetch_prices` cross-checks the aggregator-reported `asset_decimals` against `cached_pool_sync_data(..).params.asset_decimals`. [10](#0-9) 

### Impact Explanation
If `feed.asset_decimals` differs from the market's true `params.asset_decimals` for a listed asset (e.g., a composite/LP fair-value feed on Aquarius whose decimals describe the LP instrument rather than the reserve token):

- `feed.asset_decimals > market decimals`: `unscale_borrow_ceil` returns a debt cap `10^k` times too small, so `calculate_repayment_amounts` truncates `payment_amount` far below the real debt, marks legs as fully repaid when they are not, and the seizure sizing in `usd_value_wad` is inflated by `10^k` — the liquidator seizes grossly excessive collateral relative to the tiny repayment kept, or `actual_debt` comparisons/reverts wedge the plan (temporary freezing / failed liquidations while HF < 1).
- `feed.asset_decimals < market decimals`: the debt cap is `10^k` too large, so no clamping occurs; `usd_value_wad` undervalues each repayment leg, the kept `repay_usd` under-backs the seizure pro-rata distribution, and borrowers' collateral is seized at effectively zero bonus cost — theft of user collateral and residual bad debt (protocol insolvency pressure).

Either direction breaks the accepted-impact set: theft of user funds or a liquidation path that cannot operate. Caveat: exploitation requires a feed whose decimals disagree with the pool market — I could not fully verify whether `price-aggregator` providers can emit such a mismatch for a listed reserve (LP fair-value feeds are the plausible source). If aggregator decimals are always forced equal to the token's `decimals()`, the inconsistency is latent rather than live, but the code still binds settlement to the wrong authority for the market's precision.

### Likelihood Explanation
Reachability is unprivileged: any liquidator calls `liquidate` on any account with HF < 1, and the feed-decimals path runs for every repayment leg. The trigger is a (hub, token) market whose aggregator feed reports `asset_decimals` different from `params.asset_decimals`. Because the codebase deliberately prices some assets via derived feeds (Aquarius stable/constant-product LP fair value), a mismatch is a realistic configuration rather than a purely hypothetical one, but I could not confirm an actual mismatched feed in the current listings, so likelihood is medium-low.

### Recommendation
Use a single source of truth for token precision at settlement: pass `cache.cached_pool_sync_data(hub_asset).params.asset_decimals` (or the decimals stored with the market) into `unscale_borrow_ceil`, `to_asset_floor`, `Wad::from_token`, and the `MIN_BORROWABLE_ASSET_DECIMALS` checks in `math.rs`, and/or assert in `Context::fetch_prices`/`cached_price` that `feed.asset_decimals == cached_pool_sync_data(hub_asset).params.asset_decimals` for every hub asset being priced, panicking on mismatch.

### Proof of Concept
1. Governance lists a hub asset whose reserve token has, say, 7 decimals, while the aggregator feed for that asset reports `asset_decimals = 18` (derived feed pricing a different instrument precision).
2. Attacker supplies collateral, borrows the asset, and lets HF drop below 1 (own price move or interest accrual); `can_be_liquidated` returns true.
3. Liquidator calls `liquidate` offering the full debt. In `calculate_repayment_amounts`, `unscale_borrow_ceil(scaled_debt, borrow_index, 18)` divides the RAY debt value by `10^(27-18) = 10^9` instead of `10^20`, producing a cap ~`10^11` times smaller than the true debt; `payment_amount` is clamped to that dust value and the excess refunded.
4. `repays_every_debt_leg` still reports the leg as fully repaid (same wrong decimals), the plan validates, and the borrower's debt is burned near-zero while the liquidator's kept repayment is minuscule — protocol eats the unpaid principal, or, with the decimals inverted, seizure USD is understated and collateral is taken under-backed.
