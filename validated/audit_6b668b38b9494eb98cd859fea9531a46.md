### Title
AA trigger senders can pick an old last-ball to read stale oracle data feed prices - (File: formula/evaluation.js)

### Summary
Autonomous Agent (AA) formulas resolve `data_feed[[...]]` and `in_data_feed[[...]]` lookups using the MCI of the *trigger unit's own `last_ball`* as the upper bound for the search. Because a unit's `last_ball`/`last_ball_unit` is chosen by whoever composes the unit (subject only to a "must not retreat below parents" rule, not a "must be the freshest known stable ball" rule), a malicious trigger sender can deliberately select an older, still-valid last ball. This lets them make the AA evaluate `data_feed`/`in_data_feed` as of an earlier point in the DAG, before a newer (less favorable to the attacker) oracle price update was posted — the direct analog of the Nabla report's "omit updating the price feed to use stale prices."

### Finding Description
When an AA formula is evaluated, the effective "current" MCI used for all data-feed lookups is `objValidationState.last_ball_mci`, taken straight from the trigger unit that the attacker composed: [1](#0-0) 

That `mci` is passed as the upper bound (`max_mci`) into `dataFeeds.readDataFeedValue()`/`dataFeeds.dataFeedExists()` for both the `data_feed` and `in_data_feed` operators: [2](#0-1) [3](#0-2) 

`readDataFeedByAddress`/`dataFeedByAddressExists` then only return the most recent feed value with `main_chain_index <= max_mci`, i.e. whatever oracle postings existed at the chosen last-ball point, ignoring anything posted after it: [4](#0-3) 

Crucially, unit validation does not require `last_ball_mci` to be the network's current tip — it only forbids it from *retreating* below the maximum `last_ball_mci` already included via the unit's parents: [5](#0-4) 

The rest of `validateParents()` only checks that the chosen `last_ball`/`last_ball_unit` is itself a valid, stable ball consistent with the parents (matching ball/unit, on the main chain, included in parents, stable in view of parents) — there is no requirement that the sender pick the *most recent* stable ball available to them: [6](#0-5) 

So a unit composer has legitimate freedom to pick older (but still valid/stable, not-retreating) parents and last-ball, and standard composer helpers like `pickParentUnitsAndLastBall`/`findLastStableMcBall` are optimizations, not protocol-enforced requirements — nothing in unit validation stops a custom-built joint from referencing an older last ball as long as it satisfies the monotonicity/stability constraints: [7](#0-6) 

For AAs that price actions (swaps, collateral valuations, liquidations, redemptions, etc.) via `data_feed[[oracles=..., feed_name=...]]` without an additional recency check (e.g., without also constraining `min_mci` to be close to the trigger's own MCI, or checking the ball's `timestamp`), an attacker can trigger the AA while deliberately anchoring their unit to an earlier ball, thereby reading a stale price that is more favorable to them than the current market price already published by the oracle.

### Impact Explanation
Any AA that uses oracle data feeds for pricing decisions (e.g., asset swaps, minting/redeeming against a price, liquidation thresholds) can be manipulated by an attacker who selects an old-but-valid `last_ball` for their trigger unit, effectively "skipping" a recent unfavorable price update. This allows the attacker to buy/sell/redeem at a stale price, extracting value from the AA/pool at the expense of other participants — directly analogous to the reported "receiving tokens at a discounted rate" impact, and can lead to fund loss for the AA or its users.

### Likelihood Explanation
Likelihood is Low-to-Medium: the attacker must construct a custom unit (not the default wallet flow, which normally picks the freshest stable last ball) referencing older, valid parents/last ball, which requires bypassing typical wallet/composer defaults but is not prevented by consensus rules. It also depends on the AA author not adding a freshness safeguard around `data_feed`/`in_data_feed` usage (e.g., binding `min_mci` tightly or checking timestamps), which is a common omission since the oscript documentation does not enforce this by default.

### Recommendation
- In `formula/evaluation.js`, when resolving `data_feed`/`in_data_feed`, consider warning/deterring AA authors (via documentation or a lint-like validation check) that oracle price reads are only as fresh as the trigger's own `last_ball_mci`, and that AAs performing pricing must explicitly bound `min_mci` (e.g., require the feed post to be within a small MCI window of the current trigger) rather than accepting the "last known value" unconditionally.
- Consider exposing/encouraging a `timestamp`-based freshness parameter for `data_feed[[...]]` so AA authors can reject stale prices (analogous to a `priceMaxAge` check) directly in oscript.
- Optionally, tighten unit validation so that AA trigger units must reference the sender's actual latest known stable ball rather than merely "not retreating," removing the protocol-level freedom to cherry-pick older last balls for pricing-sensitive triggers.

### Proof of Concept
1. An AA is defined that reads a price via `data_feed[[oracles="ORACLE_ADDR", feed_name="PRICE", ifseveral="last"]]` (see `formula/evaluation.js` `case 'data_feed'`, `formula/evaluation.js:600-664`) and uses it to compute a swap/redemption amount, without further bounding `min_mci`/timestamp.
2. The oracle posts an updated price in a `data_feed` message in a new unit, becoming stable and included on the main chain.
3. Instead of using the standard wallet flow (which would pick the newest stable last ball via `parent_composer.pickParentUnitsAndLastBall`), the attacker crafts a unit whose `parent_units`/`last_ball`/`last_ball_unit` reference an earlier, still-valid, stable point in the DAG — satisfying only the "must not retreat below parents' `last_ball_mci`" rule in `validation.js:668-674` and the stability/parent-inclusion checks in `validation.js:720-741`.
4. The attacker sends this unit as the AA trigger. During evaluation, `mci = objValidationState.last_ball_mci` reflects the attacker's chosen (older) last ball (`formula/evaluation.js:79`), so `data_feed[[...]]` returns the pre-update (stale) price via `dataFeeds.readDataFeedValue`/`readDataFeedByAddress` (`data_feeds.js:307-311`), letting the attacker transact at the stale, more favorable price even though the oracle already posted a newer value.
