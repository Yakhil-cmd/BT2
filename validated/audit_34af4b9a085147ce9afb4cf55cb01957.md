### Title
Unsigned `StackStxOp` lets an attacker lock a victim's STX and redirect PoX rewards to themselves - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` derives the `sender` Stacks address solely from `outputs[0]` of an arbitrary Bitcoin transaction, and `StackStxOp::parse_from_tx` derives `reward_addr` solely from `outputs[0]` of a second, attacker-authored transaction. Neither requires any cryptographic proof that the composer of these Bitcoin transactions controls the private key behind the `sender` address, so an attacker can force-lock a victim's STX balance while directing the resulting PoX rewards to an address they control.

### Finding Description
The claimed equality: `STX locked by sender == STX voluntarily committed by the private-key owner of sender's address, with rewards flowing to that same party's chosen reward_addr` is broken.

`PreStxOp::parse_from_tx` only checks `num_inputs != 0`, `num_outputs != 0`, opcode, and sunset height; it takes `outputs[0].address` verbatim and converts it to a `StacksAddress` via `try_into_stacks_address()` with no signature or key-possession check: [1](#0-0) 

A Bitcoin P2PKH/P2SH output only requires knowledge of the destination hash160 — publicly visible in any Stacks address — not the corresponding private key. So an attacker can construct a `PreStxOp` transaction with `outputs[0]` = the victim's address (at dust-limit value) and `outputs[1]` funded by the attacker's own UTXOs, exactly as the question hypothesizes.

The only binding check for the follow-up `StackStxOp` is that its first input spends `vout == 1` of the prior transaction: [2](#0-1) 

Since the attacker created and funded `outputs[1]` of the `PreStxOp` themselves, they trivially satisfy this by spending their own UTXO — this proves nothing about ownership of the `sender` address in `outputs[0]`. `StackStxOp::parse_from_tx` then sets `reward_addr` from `outputs[0]` of the *second* (attacker-controlled) transaction: [3](#0-2) 

`sender` itself is passed in from the caller (resolved via `PreStxOp.output`, i.e., the forged victim address) and copied unmodified into the resulting `StackStxOp`: [4](#0-3) 

Downstream, this `sender` is used as `tx-sender` in a direct `run_contract_call` into `pox-*.stack-stx`, with no Stacks-chain signature check at all: [5](#0-4) 

The Clarity `stack-stx` entry point only checks that the (attacker-chosen) `tx-sender` has sufficient *unlocked* balance — it has no notion of "was this call authorized by the sender": [6](#0-5) 

The `signer-sig`/`signer-key` machinery in `consume-signer-key-authorization` only proves the attacker owns the *signer key* they supply — it says nothing about who owns the STX being locked, so the attacker can trivially self-sign that portion with their own key and still stake the victim's balance.

**Exploit flow:**
1. Attacker observes a victim's Stacks address `V` with an unlocked STX balance `B` (public chain data).
2. Attacker crafts `PreStxOp` tx: `outputs[0]` = `V`'s hash160 at dust limit, `outputs[1]` = attacker-funded, normal value.
3. Attacker crafts `StackStxOp` tx spending `outputs[1]` of the `PreStxOp` (input vout=1, satisfying `get_sender_txid`), with `outputs[0]` = attacker's own address (becomes `reward_addr`), and payload `stacked_ustx <= B`, valid `num_cycles`, and a `signer_key` the attacker controls (self-signed).
4. Both ops parse successfully per the current code with no distinguishing signal between "V authorized this" and "attacker forged V as sender."
5. On block processing, the chain calls `stack-stx` with `tx-sender = V`; the contract locks `stacked_ustx` uSTX from V's balance, and future PoX BTC rewards for that commitment are paid to the attacker's `reward_addr`.

Existing guards (`num_inputs != 0`, `num_outputs != 0`, opcode checks, sunset height, `get_sender_txid`'s vout==1 check, `consume-signer-key-authorization`) only validate structural/self-consistency properties of the attacker's own transactions — none of them require proof that the party constructing the `PreStxOp`/`StackStxOp` pair controls the private key of the address named as `sender`.

### Impact Explanation
The attacker can (a) force-lock any known victim's unlocked STX for up to `POX_MAX_NUM_CYCLES` reward cycles without consent — a permanent-until-unlock freeze of the victim's funds — and (b) redirect the PoX Bitcoin rewards earned on that locked STX to their own `reward_addr`, i.e., theft of rewards backed by STX the attacker never locked. This matches the Critical bucket ("theft ... of locked STX or sBTC rewards", "permanent freezing of staked STX"). The attack is repeatable against any address with a nonzero unlocked balance and costs the attacker only two dust-limit-plus-fee Bitcoin transactions per victim/cycle.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (1) knowledge of a target Stacks address and its current unlocked balance (public), (2) enough BTC to pay dust-limit outputs and fees for two chained transactions, and (3) the ability to choose their own signer key for the `signer-key`/`signer-sig` fields. No privileged role, no compromise of the victim's keys, and no reliance on prepare-phase timing or reentrancy is required. This is fully within the declared attacker capability ("craft burnchain stacking ops from their own Bitcoin inputs").

### Recommendation
Do not derive `sender` (or `reward_addr`, when used to attribute economic benefit) purely from an unauthenticated Bitcoin output address. Require an on-chain, Stacks-signed authorization (e.g., a Clarity-verified signature from `sender`'s private key authorizing this specific stack-stx op, amount, and cycle) before the burnchain-derived `sender` is trusted to have its balance locked — analogous to how `signer-key` ownership is already verified via `consume-signer-key-authorization`. At minimum, gate the burnchain-based stacking path behind a requirement that the composer prove control of `sender` (e.g., via a signature embedded in the op payload, verified before calling `stack-stx`).

### Proof of Concept
Rust test in `stackslib/src/chainstate/burn/operations/stack_stx.rs::tests` (extends `test_parse_pre_stack_stx` / `test_parse_stack_stx`):
1. Build a `BitcoinTransaction` "prestx_tx" with `outputs[0].address` = `victim` hash160 (dust value, e.g. `units: 1`), `outputs[1]` funded normally by an attacker input.
2. Call `PreStxOp::parse_from_tx(...)` and assert it succeeds with `op.output == victim` (`op.output != attacker`), proving no ownership check occurred:
   `assert_eq!(&op.output, &victim);`
3. Build "stackstx_tx" whose `inputs[0].tx_ref == (prestx_tx.txid(), 1)` and `outputs[0].address` = attacker's own address.
4. Call `StackStxOp::parse_from_tx(..., sender=&victim, ...)` and assert success with:
   `assert_eq!(&op.sender, &victim);`
   `assert_eq!(&op.reward_addr, &PoxAddress::Standard(attacker_addr, ...));`
5. Both sides of the intended equality ("locked-account == authorizing key holder") diverge: `op.sender == victim` (whose key never signed anything) while `op.reward_addr == attacker`, confirming the forgery succeeds identically to a legitimate self-authorized flow.

        match tx.get_input_tx_ref(0) {
            Some((ref txid, vout)) => {
                if *vout != 1 {
                    warn!("Invalid tx: StackStxOp must spend the second output of the PreStxOp");
                    Err(op_error::InvalidInput)
                } else {
                    Ok(txid)
                }
            }
            None => {
                warn!("Invalid tx: StackStxOp must have at least one input");
                Err(op_error::InvalidInput)
            }
        }
    }
