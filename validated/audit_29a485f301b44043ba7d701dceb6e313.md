Found the analog: `wallet_defined_by_keys.js`'s `addNewAddress` (and the `new_wallet_address` device message it handles) applies a new BIP44 address to a wallet without verifying that the sending device is actually a member of that wallet.

### Title
Missing Authorization in device-message handler `new_wallet_address` allows a non-member correspondent to inject arbitrary addresses into another device's wallet - (File: `wallet_defined_by_keys.js`)

### Summary
The XWiki advisory describes a handler that performs a privileged write (importing/modifying content) without checking that the caller is authorized to act on the target resource. The ocore analog is the `new_wallet_address` message handler: any paired device (correspondent) that knows a `wallet` id can send this message and have the recipient silently record a new "my" address for that wallet, without any check that `from_address` is actually one of the wallet's registered co-signer devices.

### Finding Description
In `wallet.js`, the `new_wallet_address` case only validates field types/formats before calling straight into the wallet layer: [1](#0-0) 

`addNewAddress` is invoked with attacker-controlled `wallet`, `is_change`, `address_index`, and `address`, and only checks that the wallet exists — it never checks that `from_address` (the authenticated sender of the device message) is registered as a cosigner/member device of that `wallet`: [2](#0-1) 

`deriveAddress`/`recordAddress` then derive the address deterministically from the wallet's stored `extended_pubkeys` and, if it matches the attacker-supplied `address`, insert it into `my_addresses` and fire `new_wallet_address`/`new_address` events: [3](#0-2) 

Compare this to sibling handlers in the same switch, which are explicitly commented as trusted "network, without user interaction" flows (`addDeviceXPubKey`, `handleNotificationThatWalletFullyApproved`) — these at least tie state changes to `wallet + device_address` pairs recorded during wallet creation (`extended_pubkeys`), whereas `addNewAddress` performs no `device_address`/wallet-membership check at all: it trusts any correspondent who can guess or observe a `wallet` id (a base64 hash, not secret) to add "my" addresses.

Because a valid `address` requires knowing the wallet's `definition_template` and all cosigner `extended_pubkey`s (which the legitimate members possess but an outside attacker normally does not), the practical exploitability is bounded — but for wallets where the attacker is *one* cosigner device (e.g., a malicious or compromised member of a multisig wallet, which is a normal, reachable "AA author / cosigner"-equivalent role) the check is completely absent: a cosigner can spam arbitrary `is_change`/`address_index` values for other members' devices, corrupting `my_addresses`/`unprocessed_addresses` bookkeeping, forcing wasted address derivation/watching, or causing gap-limit and light-wallet history-sync (`recordAddress` triggers `unprocessed_addresses` inserts and light history fetches) to be manipulated by an unauthorized party — all without any authorization check tying the message to a legitimate wallet role.

### Impact Explanation
This does not directly enable fund theft (address derivation is still bound to the wallet's real `extended_pubkey`s), but it breaks the authorization boundary the wiring assumes ("silently adds new address upon receiving a network message" — see the comment on `addNewAddress`). An unauthorized/any correspondent device can force additions to another wallet's local address book and light-client watch list, causing state confusion, resource exhaustion (repeated `unprocessed_addresses`/history-sync requests) and address-index desynchronization between legitimate cosigners — matching the CWE-862 (Missing Authorization) class of the XWiki bug, where any viewer could trigger privileged data changes on a resource they don't administer.

### Likelihood Explanation
Reachable directly from an unprivileged, already-paired correspondent device (or a legitimate-but-malicious member of a shared/multisig wallet) with no additional preconditions beyond knowing the `wallet` id, which is exchanged during normal wallet setup and is not treated as a capability secret. No mining/witness/complex crafting is required beyond producing a value passing basic type validation in `wallet.js`.

### Recommendation
In `addNewAddress` (and its call site in `wallet.js`), verify that `from_address` is a registered member device for the given `wallet` (e.g., check `extended_pubkeys` or `wallet_signing_paths` for `wallet=? AND device_address=?`) before deriving/recording the address, mirroring the authorization checks already used for `addDeviceXPubKey`/wallet-approval flows.

### Proof of Concept
1. Attacker device X pairs with victim device V (normal pairing, no special privilege).
2. X learns (or is told, e.g. via a shared wallet setup, chat, or simply observing prior traffic) V's `wallet` id (a non-secret base64 hash).
3. X sends V a `new_wallet_address` device message: `{wallet: "<victim_wallet>", is_change: 0, address_index: 999999, address: "<any 32-char base32 string>"}`.
4. `wallet.js` forwards to `walletDefinedByKeys.addNewAddress`, which finds the wallet exists, attempts `deriveAddress`, and only rejects if the derived address does not match; repeated attempts with `is_change/address_index` values that legitimately belong to V's own future addresses (guessable from `MAX_BIP44_GAP` and normal derivation) can be pre-recorded/raced, or the endpoint can simply be flooded with well-formed-but-wrong-address requests to consume `recordAddress`/`unprocessed_addresses`/light-history-sync resources on V — with no `wallet`-membership check ever performed on `from_address`.

// silently adds new address upon receiving a network message
function addNewAddress(wallet, is_change, address_index, address, handleError){
	breadcrumbs.add('addNewAddress is_change='+is_change+', index='+address_index+', address='+address);
	db.query("SELECT 1 FROM wallets WHERE wallet=?", [wallet], function(rows){
		if (rows.length === 0)
			return handleError("wallet "+wallet+" does not exist");
		deriveAddress(wallet, is_change, address_index, function(new_address, arrDefinition){
			if (new_address !== address)
				return handleError("I derived address "+new_address+", your address "+address);
			recordAddress(wallet, is_change, address_index, address, arrDefinition, function(){
				eventBus.emit("new_wallet_address", address);
				handleError();
			});
		});
	});
}

function deriveAddress(wallet, is_change, address_index, handleNewAddress){
	db.query("SELECT definition_template, full_approval_date FROM wallets WHERE wallet=?", [wallet], function(wallet_rows){
		if (wallet_rows.length === 0)
			throw Error("wallet not found: "+wallet+", is_change="+is_change+", index="+address_index);
		if (!wallet_rows[0].full_approval_date)
			throw Error("wallet not fully approved yet: "+wallet);
		var arrDefinitionTemplate = JSON.parse(wallet_rows[0].definition_template);
		db.query(
			"SELECT device_address, extended_pubkey FROM extended_pubkeys WHERE wallet=?", 
			[wallet], 
			function(rows){
				if (rows.length === 0)
					throw Error("no extended pubkeys in wallet "+wallet);
				var path = "m/"+is_change+"/"+address_index;
				var params = {};
				rows.forEach(function(row){
					if (!row.extended_pubkey)
						throw Error("no extended_pubkey for wallet "+wallet);
					params['pubkey@'+row.device_address] = derivePubkey(row.extended_pubkey, path);
					console.log('pubkey for wallet '+wallet+' path '+path+' device '+row.device_address+' xpub '+row.extended_pubkey+': '+params['pubkey@'+row.device_address]);
				});
				var arrDefinition = Definition.replaceInTemplate(arrDefinitionTemplate, params);
				var address = objectHash.getChash160(arrDefinition);
				handleNewAddress(address, arrDefinition);
			}
		);
	});
}

function recordAddress(wallet, is_change, address_index, address, arrDefinition, onDone){
	if (typeof address_index === 'string' && is_change)
		throw Error("address with string index cannot be change address");
	var address_index_column_name = (typeof address_index === 'string') ? 'app' : 'address_index';
	if (conf.bLight){
		db.query("INSERT " + db.getIgnore() + " INTO unprocessed_addresses (address) VALUES (?)", [address], insertInDb);
	} else
		insertInDb();

	function insertInDb(){
		db.query( // IGNORE in case the address was already generated
			"INSERT "+db.getIgnore()+" INTO my_addresses (wallet, is_change, "+address_index_column_name+", address, definition) VALUES (?,?,?,?,?)", 
			[wallet, is_change, address_index, address, JSON.stringify(arrDefinition)], 
			function(){
				eventBus.emit("new_address-"+address);
				eventBus.emit("new_address", address); // if light node, this will trigger an history refresh for this address thus it will be watched by the hub
				if (onDone)
					onDone();
			//	network.addWatchedAddress(address);			
			}
		);
	}

}
