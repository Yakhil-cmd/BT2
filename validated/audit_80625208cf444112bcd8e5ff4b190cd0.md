### Title
Webhook signature verified against `repository.owner.login`'s org secret, but write target selected from `repository.full_name` — cross-organization/cross-repository forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify the HMAC against using `repository_owner`, which is read straight out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  The event handlers, however, resolve the *target* repository/stack from a different field of that same body: `repository.full_name`. [3](#0-2)  Because the signature is a pure HMAC over the raw body keyed by whatever secret corresponds to the attacker-chosen `owner.login`, a party who legitimately possesses one organization's webhook secret can forge a payload whose `owner.login` matches their own org (so verification passes) while `full_name` points at a completely different organization's repository, causing the handler to act on a stack it has no relationship with.

### Finding Description
Signature verification and target resolution are bound to two independent strings inside the same attacker-suppliable JSON body:

- Verification key: `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`. [1](#0-0) 
- Write target: `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, used by every handler's `stacks` helper. [3](#0-2) 

`verify_webhook_signature` only checks `HMAC(webhook_secret_for_that_org, raw_body) == header`; it never checks that the org's secret used matches the org embedded in `full_name`. [4](#0-3)  `Repository.from_github_repo_name` blindly splits `full_name` on `/` and looks the repo up in Shipit's database with no cross-check against `owner.login`. [5](#0-4) 

In genuine GitHub-originated deliveries these two fields always agree, because GitHub itself populates both from the same underlying repository object and signs the payload with the correct per-installation secret. The break happens when a party who legitimately administers organization A's GitHub App/webhook configuration (and therefore knows orgA's `webhook_secret`, a normal, documented, unprivileged capability of any Shipit-configured organization admin) constructs a raw HTTP POST directly to Shipit's public `/webhooks` endpoint instead of relying on GitHub to deliver it. They can set:
- `repository.owner.login = "orgA"` (or `organization.login = "orgA"`) so `verify_signature` picks orgA's secret and the attacker-computed HMAC validates,
- `repository.full_name = "orgB/victim-repo"` so the handler resolves and acts on organization B's `Repository`/`Stack`.

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: ...)` on every non-archived stack of `orgB/victim-repo` matching the forged branch. [6](#0-5)  Pull-request handlers go further and can archive/unarchive/deprovision or auto-create review stacks belonging to `orgB` using `params.repository.full_name` to resolve the target repository, again independent of the org whose secret authenticated the request. [7](#0-6) 

This is the direct analog of the M-13 bug class: a field that is *acted upon* (`repository.full_name`, which drives cross-repo state changes) is never bound to the credential (`repository.owner.login`/org secret) that authenticated the request — exactly the "organization that authenticated versus the repository that is written" mismatch called out as an in-scope binding.

### Impact Explanation
An entity that controls organization A's Shipit webhook configuration can trigger unauthorized cross-organization/cross-repository actions against any other organization's repositories configured on the same Shipit instance: forcing GitHub syncs, archiving/unarchiving/deprovisioning review stacks, or auto-provisioning review stacks for repositories it has no legitimate relationship to. This is a cross-repository write performed without the authorization normally required (owning/administering that specific repository/org), matching the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires only knowledge of one organization's webhook secret (a capability every organization onboarded onto a shared/multi-tenant Shipit instance legitimately has for its own webhook) plus the ability to send a crafted HTTP POST directly to the public `/webhooks` endpoint — no GitHub App private key, `ApiClient` token, session, or repository write access on Shipit itself is required. This is a realistic misuse of a documented multi-organization deployment pattern (`Shipit.github(organization:)` keyed per-org secrets), not a hypothetical misconfiguration.

### Recommendation
Bind the field used to resolve the write target to the same field used to select the verification secret: derive both the signing organization and the acted-upon repository from `repository.full_name` (or equivalently, verify that `repository.owner.login` matches the owner segment of `repository.full_name`) before dispatching to handlers, rejecting the payload on mismatch.

### Proof of Concept
1. Attacker administers organization `orgA`'s webhook settings on GitHub pointed at the shared Shipit instance, and thus knows `orgA`'s `webhook_secret`.
2. Attacker crafts a JSON body for a `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC-SHA1(orgA_webhook_secret, raw_body)` and sets it as `X-Hub-Signature`, then POSTs directly to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` looks up `Shipit.github(organization: "orgA")` and validates successfully against the attacker-computed signature. [1](#0-0) 
5. `PushHandler#process` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github` on its stacks, an action the attacker has no authority over. [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
