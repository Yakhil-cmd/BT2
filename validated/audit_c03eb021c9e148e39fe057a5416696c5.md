### Title
Cross-stack authorization bypass in CCMenu API endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the `stack` lookup method from `Api::BaseController` in a way that drops the stack-scoping check that the base controller enforces for every other API endpoint, letting any valid `ApiClient` token read build/deploy status for a stack it was never authorized to touch.

### Finding Description
`Api::BaseController` resolves the target stack through a scoped relation that restricts results to the stack the authenticated `ApiClient` is bound to: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the binding the engine relies on: `ApiClient#stack_id` (the stack a token authorizes) must equal the stack a request actually touches. `Api::CCMenuController`, however, overrides `stack` and bypasses that scoping entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks the permission string list (e.g. `"read:stack"`) and never checks `stack_id`: [3](#0-2) 

So any `ApiClient` with `read:stack` permission — including one created scoped to a single stack (as in the `here_come_the_walrus` fixture, `stack: shipit`, `permissions: read:stack`) — can supply an arbitrary `stack_id` param to `Api::CCMenuController#show` and read deploy/build status for a completely different stack it was never granted access to. Before the attacker's request, `stack_id_A == token.stack_id` holds for every authorized request; after hitting this endpoint with `stack_id_B`, the binding `token.stack_id == requested_stack_id` is broken while the request still succeeds.

Compounding this, the `CCMenuUrlController` that mints these tokens does not even set `stack:` on the created `ApiClient`, so tokens minted from the CCMenu "get URL" flow have no scoping at all: [4](#0-3) 

But even for tokens that *are* explicitly stack-scoped (e.g. via the API or an `ApiClient` created with `stack:` set, as used elsewhere in the app to restrict `Api::StacksController#index`), `CCMenuController`'s own override strips that protection.

### Impact Explanation
This is an unauthenticated-scope read of stack state/build output for stacks outside a token's granted authorization — matching the High-impact category "unauthenticated read of stack state, task streams or deploy output." A token minted for one repository/stack (e.g. shared with a low-trust CI dashboard integration) can be used to enumerate and read the deploy/build status of any other stack managed by the same Shipit instance.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (even one legitimately scoped to a single, low-sensitivity stack) and knowledge/guessing of another stack's `stack_id` parameter (stack ids/params are often predictable, e.g. `owner/repo/branch`). No privileged access beyond a normal scoped API token is required, and the request pattern is a single GET.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` lookup from `Api::BaseController` instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Additionally, have `Shipit::CCMenuUrlController#client` create the `ApiClient` scoped to the specific stack (`stack:` set) so minted CCMenu tokens are never globally valid.

### Proof of Concept
1. Obtain (or be issued) an `ApiClient` token scoped to `stack_id = A` with `read:stack` permission (e.g. via the legitimate CCMenu URL flow for stack A, or an API-created scoped client as in the `here_come_the_walrus` fixture).
2. Send `GET /api/stacks/:B/ccmenu.xml?token=<token-for-A>` where `B` is a different stack's param the client was never granted.
3. Observe the response returns stack B's build/deploy status (HTTP 200 with XML project data), even though the token's `stack_id` is `A`, because `CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) never checks `current_api_client.stack_id` against the requested stack.
