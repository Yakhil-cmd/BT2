### Title
`MembershipHandler` resolves teams solely by GitHub `team.id`, letting a webhook verified against one organization's secret grant `Shipit.github_teams` membership on another organization's team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`User#authorized?` grants Shipit access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [1](#0-0) , and membership in those teams is populated purely by the `membership` webhook handler. `WebhooksController#verify_signature` authenticates the request against the secret of the organization named in the payload itself (`repository_owner`, falling back to `params.dig('organization','login')`) [2](#0-1) [3](#0-2) , but `MembershipHandler#find_or_create_team!` and `Team#add_member` never verify that this authenticated organization matches the `organization` that actually owns the referenced `team.id` [4](#0-3) [5](#0-4) .

### Finding Description
Binding claimed to hold: `webhook.authenticated_organization == team.organization` for every call reaching `Team#add_member`. Tracing the code shows this binding is enforced nowhere.

- `verify_signature` computes `repository_owner` from the payload's own `repository.owner.login` or `organization.login` and authenticates using `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, i.e. it verifies the request against whichever organization the payload itself claims to be from [2](#0-1) . An attacker who legitimately controls (or is a GitHub App on) their own configured Shipit organization "A" can produce a fully valid signature for a `membership` payload where `organization.login = "A"`.
- Inside that valid, org-A-signed payload, the attacker sets `team.id` to the GitHub team ID belonging to a *different* organization "B" that is already tracked in Shipit (e.g. present in `Shipit.github_teams`), and sets `member.login` to their own account.
- `MembershipHandler#find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [6](#0-5) . Since `github_id` is looked up globally (not scoped to `organization`), if a `Team` row for org B's team already exists, `find_or_create_by!` returns that *existing* record without re-running the block — the record's `organization` column remains "B", untouched by the org-A payload.
- `MembershipHandler#process` then calls `team.add_member(member)` for `action == 'added'` [7](#0-6) , and `Team#add_member` performs no ownership/authorization check at all — it simply does `members.append(member) unless members.include?(member)` [5](#0-4) .
- Result: a webhook authenticated as organization A causes a `Membership` row to be written associating an attacker-controlled `User` with organization B's `Team`, with no check that A ever owned or was permitted to modify B's team.

Existing guards do not close this gap: `verify_signature` only proves the request came from org A's configured secret (or passes unconditionally if org A has no `webhook_secret` configured, since `verify_webhook_signature` returns `true` unless a secret is set) [8](#0-7) ; it makes no claim about org B at all. The `ExplicitParameters` schema on `MembershipHandler` only validates payload shape/types, not cross-organization ownership [9](#0-8) . `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.

### Impact Explanation
If `Shipit.github_teams` includes org B's team, this is a direct authorization escalation: `User#authorized?` becomes true for the attacker-controlled account because `teams.where(id: Shipit.github_teams.map(&:id)).exists?` now matches [1](#0-0) , granting them login/access to a Shipit instance gated by org B's team — despite the attacker never having any relationship with org B. This is repeatable against any `team.id` the attacker can enumerate (team IDs are small sequential integers, and Shipit's own `Team.find_or_create_by_handle`/rake tasks create/cache these rows, so guessing or observing them is low-cost). The blast radius crosses tenant boundaries: any organization "A" configured in Shipit can grant/revoke membership in any other organization "B"'s Shipit-tracked team, which maps to the "escalation into `Shipit.github_teams` authorization" High-severity category (and, where that access maps further into deploy/merge permissions gated by team membership, can reach Critical).

### Likelihood Explanation
Preconditions: the attacker must control (or send webhooks as) at least one organization that is itself configured in Shipit (i.e., has an entry with a webhook secret, or a misconfigured entry with none), and must know or guess the numeric `github_id` of the target team. Both are realistic for a multi-tenant Shipit deployment serving several organizations, or where a `webhook_secret` was left blank per the shipped example config [10](#0-9) . No Shipit session, API token, or GitHub secret for the *target* organization is required at any point — only the attacker's own valid organization signature (or no signature at all if the target/attacker org has no secret configured).

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise if a `Team` with that `github_id` already exists under a different `organization`. Additionally, harden `Team#add_member`/`#process` to assert `team.organization == params.organization.login` before mutating memberships, so the invariant is enforced at the model boundary rather than assumed by the caller.

### Proof of Concept
```ruby
# test/models/shipit/team_test.rb (or membership_handler_test.rb)
test "add_member performs no ownership check" do
  team_b = Shipit::Team.create!(github_id: 999, organization: 'org-b', slug: 'devs', name: 'Devs', api_url: 'http://example.com')
  attacker = Shipit::User.create!(login: 'attacker', name: 'Attacker')

  # No relationship between attacker/org-A and org-b asserted anywhere
  team_b.add_member(attacker)

  assert_includes team_b.members.reload, attacker
end

test "membership webhook signed by org-a can add a member to org-b's team" do
  team_b = shipit_teams(:org_b_team) # github_id known/guessed by attacker
  request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate valid org-A signature

  payload = {
    action: 'added',
    team: { id: team_b.github_id, name: team_b.name, slug: team_b.slug, url: team_b.api_url },
    organization: { login: 'org-a' }, # attacker's own org, authenticated
    member: { login: 'attacker' },
    repository: { owner: { login: 'org-a' } }
  }

  assert_difference -> { Shipit::Membership.where(team_id: team_b.id).count }, 1 do
    post :create, body: payload.to_json, as: :json
  end

  team_b.reload
  assert_equal 'org-b', team_b.organization # organization column unchanged, proving cross-tenant write
  assert_includes team_b.members, Shipit::User.find_by(login: 'attacker')
end
```
Both assertions demonstrate the equality `webhook.authenticated_organization ('org-a') == team.organization ('org-b')` is false yet the write still succeeds, confirming the binding is broken.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
