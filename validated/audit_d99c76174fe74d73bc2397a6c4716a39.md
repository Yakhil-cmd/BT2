## Finding: `min-ustx-for-sats-amount` rounds to zero for small `sats-amount`, letting a staker register for a bond with zero locked STX

### Summary
`pox-5.clar`'s `min-ustx-for-sats-amount` computes the minimum STX a staker must lock in order to back a given sBTC/L1-sats bond position. Like the TokenLocker penalty bug, it performs a *chain* of integer divisions on the input amount, so for small enough `sats-amount` the whole expression truncates to `0`. `register-for-bond` only asserts `amount-ustx >= (min-ustx-for-sats-amount ...)`, so once the floor computes to `0`, a staker can pass `amount-ustx = 0` and register real sats collateral while locking no STX at all, still receiving a `protocol-bond-memberships` entry and proportional sBTC bond rewards.

### Finding Description
`min-ustx-for-sats-amount` in `pox-5.clar`:

```
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
)
``` [1](#0-0) 

This nests two truncating divisions: first `(/ (* stx-value-ratio sats-amount) u100)`, then a second `/ u10000` after multiplying by `min-ustx-ratio`. Whenever `stx-value-ratio * sats-amount < 100`, the inner division alone already yields `0`, forcing the entire result to `0` regardless of `min-ustx-ratio`. Even when the inner division is non-zero, the outer `/u10000` can still round a small positive intermediate value down to `0`.

`register-for-bond` enforces the collateral floor using exactly this function:

```
(asserts!
    (>= amount-ustx
        (min-ustx-for-sats-amount sats-total (get stx-value-ratio bond)
            (get min-ustx-ratio bond)
        ))
    ERR_INSUFFICIENT_STX
)
``` [2](#0-1) 

There is no separate check that `amount-ustx > 0` or `sats-total > 0`; the only other STX-related check is `(>= total-balance amount-ustx)` [3](#0-2) , which trivially holds when `amount-ustx = 0`. Consequently a staker who picks a `sats-total` small enough that `stx-value-ratio * sats-total < 100` can call `register-for-bond` with `amount-ustx = 0`, still lock the (small) sats amount into the bond via `roll-sbtc` [4](#0-3) , and be recorded as a full bond member entitled to sBTC yield proportional to `sats-total` via `calculate-bond-rewards`'s `target-yield`/`accrued-rewards-per-sat` accounting [5](#0-4) , without ever locking the STX collateral the `min-ustx-ratio` was designed to require.

The test suite's own model of this function documents the intentional integer-division truncation ("Integer division at each step, matching the contract's truncation") [6](#0-5) , and a dedicated test explicitly constructs the smallest `sats` value for which the floor is `>= 1` uSTX, confirming that below that threshold the floor computes to `0` [7](#0-6) .

### Impact Explanation
This breaks the equality the protocol relies on: sBTC bond reward eligibility (and, correspondingly, sats-denominated "signing"/reward exposure) must be proportional to locked STX collateral (`amount-ustx >= min-ustx-for-sats-amount(sats, ratio)`). By choosing small `sats-total`, an attacker registers for a bond and receives sBTC rewards proportional to those sats while locking `0` STX — i.e. reward eligibility granted without the required locked value, matching the "signing weight or reward slots exceeding locked value" High-impact category. Because the register floor is computed per-call, this can be repeated across many `sats-total` chunks/many bond periods/many principals to accumulate uncollateralized sBTC exposure over time, though each individual call is bounded by the rounding error size (up to just under the point where `stx-value-ratio * sats < 100`, or where the outer `/10000` rounds away a fraction of a uSTX).

### Likelihood Explanation
Exploitation only requires being on the bond's allowlist (`protocol-bond-allowances`) and choosing a small `sats-total`/`amount-ustx` pair — no privileged role, admin, or other party's key is needed. The check is a straightforward, always-reachable public-entrypoint assertion, so likelihood is high for any allowlisted staker willing to work in small increments.

### Recommendation
Round the STX floor up rather than down (ceiling division) at each step of `min-ustx-for-sats-amount`, or perform the calculation without the intermediate truncating division (e.g. combine the multiplications before any division and divide once at the end with rounding up), and additionally reject `sats-total > 0` with a computed floor of `0` explicitly (require `amount-ustx > 0` whenever `sats-total > 0`).

### Proof of Concept
1. Attacker is allowlisted for a bond with `stx-value-ratio = 10` and `min-ustx-ratio` any nonzero value.
2. Attacker calls `register-for-bond` with `sats-total = 9` (via an sBTC `btc-lockup` of `9` sats) and `amount-ustx = 0`.
3. `min-ustx-for-sats-amount(9, 10, min-ustx-ratio)` evaluates `(/ (* 10 9) 100) = (/ 90 100) = 0`, so the outer expression is also `0`.
4. The `ERR_INSUFFICIENT_STX` assertion `(>= 0 0)` passes; `total-balance >= 0` trivially passes.
5. `register-for-bond` succeeds: attacker is added to `protocol-bond-memberships` with `amount-ustx: 0`, `amount-sats: 9`, and begins accruing proportional sBTC bond rewards via `calculate-bond-rewards`/`settle-staker-rewards` with zero STX ever locked.

/**
 * Contract's `min-ustx-for-sats-amount`: the floor uSTX a staker must lock for
 * `sats`. Integer division at each step, matching the contract's truncation.
 */
export function minUstxForSats(
  sats: bigint,
  stxValueRatio: bigint,
  minUstxRatio: bigint,
): bigint {
  return (((stxValueRatio * sats) / 100n) * minUstxRatio) / 10000n;
}
```
