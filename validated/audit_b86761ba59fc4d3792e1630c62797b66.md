### Title
Global `Commit.where(sha:)` lookup in `StatusHandler#process` allows cross-repository Status/Hook injection regardless of `Commit#locked?` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by matching `sha` across the entire database, with no scoping to the repository that authenticated the webhook. Because `Commit#locked?` only gates `schedule_continuous_delivery` (via `Commit#deployable?`) and never `Commit#create_status_from_github!`/`Commit#add_status`, an attacker who controls a repository already onboarded to the same Shipit instance can push a webhook-signed status for a sha that also exists in a *different, unrelated, and even locked* stack, causing a `Status` row (and `Hook.emit(:commit_status, ...)`/`Hook.emit(:deployable_status, ...)`) to be written for that other stack's commit.

### Finding Description
The broken binding: `repository_owner` used to authenticate the webhook signature in `WebhooksController#verify_signature` (`params.dig('repository','owner','login')`, app/controllers/shipit/webhooks_controller.rb:24-30, :59-62) must equal the repository that owns the `Stack`/`Commit` being mutated by the handler. It does not.

`StatusHandler#process` does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is a global, unscoped query. The base `Handler` class *does* provide a repository-scoped helper, `stacks`, derived from `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [2](#0-1)  — but `StatusHandler` never uses it to filter the `Commit` lookup. Any `Commit` row anywhere in the instance whose `sha` matches gets a status written and hooks fired, independent of which repository's webhook secret authenticated the request.

`verify_signature` only proves the request came from *some* org/repo already configured in Shipit (`Shipit.github(organization: repository_owner)`), it says nothing about which `Commit`/`Stack` that request is entitled to mutate [3](#0-2) .

`Commit#create_status_from_github!` → `add_status` writes the `Status` and fires hooks unconditionally:
```
def add_status
  already_deployed = deployed?
  previous_status = status
  yield
  reload
  new_status = status
  unless already_deployed
    payload = { commit: self, stack:, status: new_status.state }
    Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
  end
  ...
end
``` [4](#0-3) 
There is no check of `locked?` anywhere in this path.

`locked?` is only consulted in `Commit#deployable?` and consequently `Commit#schedule_continuous_delivery`:
```
def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [5](#0-4) 
and `deployable?`'s `!locked?` gate [6](#0-5)  (note: this citation is `Stack#deployable?`; `Commit#locked?` is checked similarly in `Commit#deployable?`, confirmed by the test `"#deployable? is false if commit is locked"` [7](#0-6) ). This only suppresses *scheduling a deploy* — it has zero effect on whether the `Status` row is written or whether `Hook.emit` fires.

Attacker flow: attacker controls (or forks) a repository whose owner org is already a recognized Shipit tenant (has a valid `github.webhook_secret`/App install configured on this instance). Attacker crafts/obtains a commit with an identical `sha` to a commit tracked in a victim stack (trivial if forking the victim's public repo history, or if the same commit is legitimately shared across multiple stacks/environments backed by different `Repository` records). Attacker triggers their own CI to POST a `status` webhook to `/webhooks`, correctly signed with their own org's real `webhook_secret`. `verify_signature` passes (it's a legitimate signature for the attacker's own org). `StatusHandler#process` then finds and mutates the victim's `Commit` too, since the lookup is global by `sha`, writing a forged `Status` (e.g., `state: "success"`) and firing `Hook.emit` outbound webhooks for the victim's stack — even if that victim commit is `locked?`.

None of the listed guards prevent this: `verify_signature` only checks organization-level HMAC validity, not commit ownership; `ExplicitParameters` schema in `StatusHandler.params` only validates payload shape, not repository scope; `drop_unhandled_event` is irrelevant; `Repository`/`Stack` validations don't constrain cross-repo sha collisions; and `Commit#locked?` is checked nowhere in the status-write/hook-emit path.

### Impact Explanation
An attacker-controlled webhook payload for their own (authenticated) repository mutates another repository's `Stack`/`Commit` state — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely: a `Status` row is created for a commit the attacker does not own/control, `Hook.emit(:commit_status, ...)` and `Hook.emit(:deployable_status, ...)` fire outbound webhooks with fabricated CI state for the victim stack, `stack.schedule_merges` may be triggered, `stack.enable_ci!` may be toggled, and (for non-locked commits) `Commit#schedule_continuous_delivery` can be influenced into eventually triggering `ContinuousDeliveryJob`/an unauthorized deploy. This is repeatable against any stack/commit whose sha the attacker can reproduce or predict, across tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: attacker needs a repository under an org that is already configured in Shipit (i.e. a legitimate tenant of this Shipit instance) so their webhook signature validates, and needs to produce/discover a commit sha that also exists in a target stack — trivially achievable by forking a public target repository (git shas are content-addressed and preserved across forks) or exploiting shared commits across multiple stacks tracking the same upstream history. No Shipit session, API token, or secret is required beyond what the attacker legitimately possesses for their own onboarded repo/CI. Cost is low and the attack is fully repeatable/scriptable per request.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to only the commits belonging to stacks of the repository that authenticated the webhook, using the existing `stacks` helper (`Repository.from_github_repo_name(repository_name)`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or add an explicit `stack_id`/`repository` join, instead of a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_cross_repo_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "cross-repo status webhook writes a Status for a locked commit in a different repository's stack" do
          stack_a = shipit_stacks(:shipit) # belongs to repository "shopify/shipit-engine" (stack_a's repo)
          commit_a = stack_a.commits.last
          commit_a.lock(shipit_users(:shipit))
          assert_predicate commit_a, :locked?

          # Simulate a webhook payload whose "repository" is NOT stack_a's repository,
          # but shares the same commit sha (e.g. attacker's fork with identical history).
          payload = {
            'sha' => commit_a.sha,
            'state' => 'success',
            'context' => 'attacker-ci',
            'repository' => { 'full_name' => 'attacker-org/attacker-repo',
                               'owner' => { 'login' => 'attacker-org' } }
          }

          assert_difference -> { commit_a.statuses.count }, 1 do
            StatusHandler.call(payload)
          end

          commit_a.reload
          assert_predicate commit_a, :locked?      # locked? is unchanged/true
          assert_equal 'success', commit_a.status.state # yet CI-visible state was corrupted
        end
      end
    end
  end
end
```
Binding checked: `repository_owner` authenticating the write (`attacker-org`) != `stack_a.repository`'s owner, yet `Status.count`/`commit_a.status.state` changed for `stack_a`'s commit despite `commit_a.locked? == true` both before and after — proving the `!locked?` gate in `Commit#deployable?` does not protect the Status/Hook write path.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
