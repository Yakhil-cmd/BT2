### Title
Webhook Organization-Authentication / Repository-Written Mismatch Enables Cross-Tenant Stack Manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, the webhook signature is verified against the `webhook_secret` of the organization named in `repository.owner.login` (or `organization.login`), but the event handlers that mutate state look up the target `Stack`/`Repository` using the *unrelated* `repository.full_name` field from the same attacker-supplied JSON body. Because these two fields are never cross-validated, a party who legitimately controls one tenant's `webhook_secret` (e.g., an admin of `OrgA` who configured their own GitHub App per `docs/setup.md`'s "Using Multiple Github Applications" section) can forge a validly-signed webhook that is verified as coming from `OrgA` but whose `repository.full_name` addresses a stack belonging to a completely different tenant, `OrgB`, sharing the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` derives the organization used for HMAC verification purely from payload data: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to the `GitHubApp` instance (and its `webhook_secret`) configured for that specific organization key in `secrets.yml`, as documented for multi-org setups: [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` dispatches the entire raw payload to handlers: [5](#0-4) 

The base `Handler` class resolves the target stacks using a *different* payload field, `repository.full_name`, with no relation enforced back to the organization that was actually authenticated: [6](#0-5) 

`Repository.from_github_repo_name` simply splits this attacker-controlled string on `/` and looks up any repository record by owner/name, regardless of which organization's secret validated the request: [7](#0-6) 

Because `repository.owner.login` (used for signature-org selection) and `repository.full_name` (used for target lookup) are independent JSON fields inside the same unauthenticated request body, GitHub itself would never produce an inconsistent pair, but nothing in `WebhooksController` or `Handler` enforces that `full_name` is prefixed by `owner.login`. An attacker who holds `OrgA`'s webhook secret can therefore sign a payload with `repository.owner.login = "OrgA"` (so it passes `verify_signature`) while setting `repository.full_name = "OrgB/some-repo"`, causing handlers to act on `OrgB`'s stacks.

This breaks the exact binding called out in scope: **organization that authenticated ≠ repository that is written**.

### Impact Explanation
Handlers dispatched this way include the `push` handler, which enqueues `GithubSyncJob` with an attacker-chosen `expected_head_sha` for the target stack, and the `check_suite`/`status` handlers, which can flip CI/status state used to gate auto-merge and continuous deployment. For any `OrgB` stack with `continuous_deployment: true`, injecting synthetic commits/status updates for a SHA of the attacker's choosing can trigger an **unauthorized deploy** of `OrgB`'s repository — a Critical-tier impact per the scan's own impact taxonomy — without the attacker ever having any credential, session, or GitHub permission on `OrgB`. This is a genuine cross-tenant boundary break in shared/multi-org Shipit deployments, not a design decision documented as acceptable (the multi-org feature is explicitly documented as isolating organizations from one another).

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with multiple GitHub organizations (an explicitly documented and supported configuration), and (2) the attacker being a legitimate but low-privilege holder of one tenant's `webhook_secret` (e.g., any org admin who set up their own GitHub App integration on the shared instance). No access to `OrgB`, no GitHub credentials for `OrgB`, and no Shipit session/API token are required. The only non-trivial precondition is multi-org hosting, which the project itself documents and supports as a first-class feature.

### Recommendation
Bind the two identities together: after computing `repository_owner` for signature verification, require that the `repository.full_name` (and `organization.login`, if present) used by downstream handlers is consistent with that same `repository_owner`/organization, e.g., verify `payload.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` before dispatching to handlers, or resolve handlers' target repository strictly from the already-verified organization context rather than re-parsing untrusted payload fields.

### Proof of Concept
1. Deploy Shipit with two configured GitHub orgs, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`), and a `Stack` tracking `OrgB/target-repo` with `continuous_deployment: true`.
2. As an entity that legitimately possesses `OrgA`'s `webhook_secret` (e.g., an `OrgA` admin), craft a `push` event JSON body:
   ```json
   {
     "repository": { "owner": {"login": "OrgA"}, "full_name": "OrgB/target-repo" },
     "after": "<attacker-chosen sha>",
     "ref": "refs/heads/<target branch>"
   }
   ```
3. Sign the raw body with `OrgA`'s `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner => "OrgA"`, verifies successfully using `OrgA`'s secret.
5. The `push` handler resolves stacks via `Repository.from_github_repo_name("OrgB/target-repo")`, finds the `OrgB` stack, and enqueues `GithubSyncJob`/triggers continuous deployment for it — despite the request never being authenticated against `OrgB`.
