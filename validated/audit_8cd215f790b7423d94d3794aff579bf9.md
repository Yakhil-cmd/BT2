### Title
Webhook organization-secret selection is not bound to the repository the payload actually targets, enabling cross-organization forged events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App secret to validate an inbound webhook against using `repository_owner`, a value read directly out of the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`). The signature check only proves that whoever crafted the raw POST body knows the secret for that claimed organization. Nothing then re-checks that the `repository.full_name` field — the field every event handler actually acts on to locate a `Stack`/`Repository` — belongs to that same organization. This breaks the binding "organization that authenticated versus the repository that is written."

### Finding Description
`verify_signature` resolves the app/secret purely from attacker-suppliable JSON: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')` — both are plain JSON fields inside the same raw body whose HMAC is being checked, but the verification logic never cross-validates them against `repository.full_name`.

Every handler, however, resolves the target `Stack`/`Repository` using `repository.full_name`, a completely independent field of the same JSON object: [3](#0-2) [4](#0-3) 

Because Shipit supports multiple organizations, each configured with its **own** independent `webhook_secret` (as documented in `config/secrets.development.shopify.yml`), the HMAC only proves the sender knows *one* organization's secret — not that the payload's target repository belongs to that organization. A legitimate GitHub-delivered webhook always keeps `repository.owner.login` and `repository.full_name` consistent, but the Shipit code never enforces that consistency itself; it merely trusts whatever JSON fields it is given for routing (`repository_owner`) versus acting (`repository.full_name`).

An attacker who is the legitimate holder of Organization A's webhook secret (e.g. they administer a small, low-value repo onboarded to the same Shipit instance under Org A) can therefore hand-craft an arbitrary raw POST body — HMAC-signed with Org A's secret — in which `repository.owner.login`/`organization.login` = `"orgA"` (so `verify_signature` selects and successfully validates against Org A's secret) while `repository.full_name` = `"orgB/high-value-repo"` (so the dispatched handler operates on Org B's stack). `Shipit::Webhooks.for_event` then dispatches this forged event to handlers such as `PushHandler`, which calls `stack.sync_github` on Org B's stacks, or the `pull_request` handlers, which can archive/unarchive review stacks, update PR state, or feed into the auto-merge pipeline for repositories the attacker has no legitimate access to.

### Impact Explanation
This crosses the trust boundary described in the rules as "an organization that authenticated versus the repository that is written." Depending on which handler is targeted, an attacker with only Org A's webhook secret gains write influence over Org B's Shipit-managed stacks (triggering `sync_github`, archiving/unarchiving review stacks, mutating pull-request/merge state) without ever having Org B's credentials — a cross-repository/cross-organization write, matching the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to already legitimately hold a valid `webhook_secret` for at least one organization configured on the shared Shipit instance (a realistic scenario in any multi-tenant/multi-org Shipit deployment, since organization admins configure and can see their own app's webhook secret) and the ability to send an arbitrary HTTP POST (no GitHub involvement needed, since the controller only checks the HMAC of the body it receives, not its provenance). No other privileged Shipit credential (session, `ApiClient` token, `api_clients_secret`, private key) is required.

### Recommendation
Bind the resolved signing organization to the repository actually referenced in the payload before dispatching to handlers: after `verify_signature` succeeds, assert that `repository.full_name`'s owner segment equals the `repository_owner`/`organization.login` used to select the secret (reject with 422 otherwise), or better, resolve the target `Repository`/`Stack` first and then verify the payload's signature specifically against the secret configured for that repository's owning organization, never trusting an attacker-suppliable "owner" field as the sole key for secret selection independent of the field used for routing.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with a distinct `webhook_secret` (per `config/secrets.development.shopify.yml` schema) and each having at least one onboarded `Stack`.
2. As the (legitimate) owner of `orgA`'s webhook secret, craft a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": { "full_name": "orgB/high-value-repo", "owner": { "login": "orgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` (from `repository_owner`), which succeeds because the signature matches `orgA`'s secret — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("orgB/high-value-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and invokes `stack.sync_github` on `orgB`'s stack — an action the attacker could never trigger with only `orgA`'s credentials against a legitimately-signed `orgB` webhook.
