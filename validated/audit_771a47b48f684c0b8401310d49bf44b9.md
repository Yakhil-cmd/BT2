### Title
Cross-Organization Forged Commit Status via Unscoped `StatusHandler` Webhook Processing - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a GitHub webhook against based on the `repository.owner.login` (or `organization.login`) field taken from the *same* untrusted JSON body it is about to verify. The event handler that actually mutates state for the `status` event, `StatusHandler`, never re-checks that the commit being updated belongs to the organization/repository whose secret was used for verification — it looks the commit up by a bare, globally-unscoped `sha`. This breaks the binding "organization that authenticated == repository that is written": any org onboarded onto a multi-tenant Shipit instance (and thus in possession of its own legitimate webhook secret) can forge a `status` webhook, signed with its *own* secret, that injects a fake `success` status onto a commit SHA belonging to a completely different organization's stack, potentially enabling an unauthorized deploy of that commit.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration (and thus the secret) purely from the payload's own `repository.owner.login` field: [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple independent GitHub organizations/Apps from one instance, each with its own `webhook_secret`, as documented: [3](#0-2) 

Once the signature is verified against the org selected by that attacker-controlled field, the raw JSON is dispatched to handlers keyed only by `X-Github-Event`: [4](#0-3) 

The generic `Handler` base class does scope most handlers to a repository via `payload.dig('repository', 'full_name')`: [5](#0-4) 

However, `StatusHandler` (used for the `status` event) does **not** use this repository scoping at all — it looks up commits globally by `sha` across the entire Shipit database: [6](#0-5) 

`Commit#create_status_from_github!` then unconditionally creates a `Status` record from the attacker-supplied `state`/`description`/`context`/`target_url` fields: [7](#0-6) 

The binding that should hold is: *organization whose secret authenticated the request* == *organization/repository owning the commit being mutated*. Because `StatusHandler` never checks repository ownership of the target commit, and the signature-selection field (`repository.owner.login`) is not cross-validated against anything else in the payload before being trusted, org A (a legitimate, but unprivileged-relative-to-org-B tenant, holding only its own valid `webhook_secret`) can:

1. Compute a valid HMAC-SHA1 signature over an arbitrary JSON body using **its own** `webhook_secret`.
2. Set `repository.owner.login` = `"org-A"` so `Shipit.github(organization: repository_owner)` resolves to org A's app/secret and the signature check passes.
3. Set `sha` to a commit SHA belonging to org B's stack (trivially obtainable, since commit SHAs of public/known repos are not secret) and `state` = `"success"`.
4. `StatusHandler#process` finds `Commit.where(sha: ...)` — which matches org B's commit regardless of which org "authenticated" the webhook — and creates a fake successful `Status` on it.

This is a direct structural analog to the reported ERC1155 `NFTVoucher` issue: the voucher's `tokenId` was validated but the effective mint quantity (`amount`) was not tied to a unique, unforgeable identifier, allowing the signed artifact to be replayed/misapplied beyond its intended scope. Here, the "signature" (webhook HMAC) is validated against an organization identity, but the actually-mutated resource (a `Commit`/`Status` row) is selected by a field (`sha`) that carries no binding back to that verified organization.

### Impact Explanation
Shipit commit statuses gate deploy readiness (`Commit#deployable?` requires `success?` and not `blocked?`, driven by `stack.blocking_statuses`/`required_statuses` computed from `statuses`). By injecting a forged `success` status for a target commit in a victim organization's stack, an attacker who legitimately controls a different, unrelated organization on the same multi-tenant Shipit instance can cause CI/required-status checks to appear satisfied for a commit they do not control, potentially enabling that commit to become deployable/mergeable via Shipit — this maps to the "unauthorized deploy" Critical-impact category defined in scope. It is also a cross-organization state write, since the mutation lands on a `Commit`/`Stack` outside the authenticating organization's own scope, which is the boundary the engine is supposed to enforce per-tenant.

### Likelihood Explanation
Requires only that the attacker's own organization be one of the (potentially many) GitHub orgs configured on a shared multi-tenant Shipit install — a scenario the engine explicitly documents and supports (`config/secrets.development.example.yml` multi-org example). No access to the victim organization's `webhook_secret`, GitHub token, or Shipit account is needed; the attacker only needs their own org's `webhook_secret` (which they legitimately possess as that org's app owner) and knowledge of a target commit SHA in the victim stack (commit SHAs are not secrets). The webhook endpoint is public and unauthenticated apart from the HMAC check.

### Recommendation
Bind the resource being mutated to the organization/repository that was actually authenticated:
- In `StatusHandler`, resolve the target `Stack`/`Commit` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (as other handlers do) instead of a bare, cross-tenant `Commit.where(sha: ...)`, and reject/ignore statuses for commits not belonging to that repository's stacks.
- In `WebhooksController#verify_signature`, after selecting the org via `repository_owner`, re-validate that `repository.full_name`'s owner segment matches `repository_owner` before trusting the payload, so the field used to pick the verification secret cannot silently diverge from the field(s) used to select what gets written.

### Proof of Concept
1. Attacker legitimately administers `org-A`, configured as one tenant of a shared Shipit instance with its own `webhook_secret_A` (per the documented multi-org config).
2. Attacker crafts:
```json
{
  "sha": "<known-commit-sha-in-victim-org-B-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-A/attacker-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>`.
4. `POST /github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `Shipit.github(organization: "org-A")` and the signature validates successfully (attacker's own secret over their own payload).
6. `StatusHandler#process` executes `Commit.where(sha: "<victim-sha>")`, finds the commit belonging to org-B's stack, and calls `create_status_from_github!`, creating a spoofed `success` status — with no check that the commit belongs to `org-A`.
