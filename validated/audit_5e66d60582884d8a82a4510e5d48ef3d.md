### Title
Cross-repository status webhook forgery satisfies required CI checks for unrelated stacks - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `sha` alone (`Commit.where(sha: params.sha)`) with no check that the webhook's `repository.full_name` matches the repository owning the commit's stack. Any GitHub repository whose owner has installed Shipit's GitHub App can therefore forge a `status` event that is recorded against a commit belonging to a *different* repository's stack, as long as the two repositories share a commit SHA (trivially achievable by forking), satisfying that stack's `required_statuses`.

### Finding Description
The binding that must hold is: `payload.dig('repository', 'full_name') == commit.stack.github_repo_name` (i.e., the webhook's originating repository must equal the repository that owns the target stack/commit) before a `Status` row is written for that commit. This binding is never checked.

Trace:
- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only validates that the payload's signature matches the webhook secret for `repository_owner` — i.e. it proves the payload genuinely came from *some* repository/org owned by the attacker (Repository B), nothing more. [1](#0-0) 
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this is a *global, unscoped* query across all stacks/repositories, with no filter on `repository_name`. [2](#0-1) 
- Notably, the base `Handler` class already defines a `stacks` helper that scopes lookups via `Repository.from_github_repo_name(repository_name)` [3](#0-2)  — but `StatusHandler` does not use it.
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)` using `commit.stack_id`, i.e. the real owning stack's id (Stack A), not anything derived from the forged payload's repository. [4](#0-3) 
- `Status.replicate_from_github!` just persists `state`, `context`, etc. against that `stack_id`/commit with no cross-check against the stack's actual repository. [5](#0-4) 

Exploit flow: attacker forks Repository A into Repository B (owned by the attacker), guaranteeing at least one shared commit SHA (fork commits are byte-identical, hence SHA-identical, until diverging). Attacker installs/has Shipit's GitHub App on Repository B (a normal, unprivileged action for a repo owner) and sends a `status` webhook (or triggers one via GitHub Actions/API against their own repo) with `sha` = the shared commit, `context: 'ci/required-check'`, `state: 'success'`. This request is legitimately signed by B's own webhook secret, so `verify_signature` passes. `StatusHandler#process` then finds Stack A's commit (same `sha`) and writes a `Status` row against Stack A's `stack_id`, satisfying Stack A's `required_statuses` for that commit, flipping `Commit#deployable?` / `MergeRequest#any_status_checks_missing?` to green.

None of the existing guards catch this: `verify_signature` authenticates the sender's own org, not the target stack's org; `drop_unhandled_event` only filters by event type; there is no `ExplicitParameters` validation tying `sha` to a specific repository; and `StatusHandler` bypasses the repository-scoped `stacks` helper that other parts of the codebase provide for exactly this purpose.

### Impact Explanation
This is a payload from one repository (attacker-controlled Repository B) mutating another repository's stack/commit state (Repository A / Stack A), forging satisfaction of a required CI gate and enabling an unauthorized deploy or merge — this matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge." The attack is repeatable against any target repository for which the attacker can obtain a shared commit SHA (fork relationship is the simplest vector, but any content-identical commit works), and generalizes across all tenants/stacks hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions are low-cost and fully within an unprivileged attacker's control: own/fork a public repository, get Shipit's GitHub App installed on it (self-service for any GitHub user for public/installable apps), and know the required context string (visible via the public `Api::StacksController#show` deploy spec or the target's public `shipit.yml`). No Shipit secrets, sessions, or team membership are needed. The only non-trivial requirement is a shared commit SHA between attacker and victim repo, which forking naturally provides for any commit that hasn't diverged, or which can be engineered by crafting a commit with identical tree/parent/author/committer/timestamp/message content offline and pushing it to the attacker's own repo.

### Recommendation
In `StatusHandler#process` (and any other handler exhibiting the same pattern, e.g. `CheckRunHandler`), scope the commit lookup by the webhook's own repository, e.g. use the base `Handler#stacks` helper: `stacks.flat_map(&:commits).where(sha: params.sha)` or explicitly verify `commit.stack.github_repo_name == repository_name` before calling `create_status_from_github!`. Reject/ignore statuses whose payload repository does not match the commit's owning stack's repository.

### Proof of Concept
Minitest plan (no live GitHub, using existing webhook test harness patterns from `test/controllers/webhooks_controller_test.rb`):
1. Create `Stack` A with `Repository` A (`full_name: 'org-a/repo-a'`), seed its cached deploy spec so `required_statuses` includes `'ci/required-check'`.
2. Create a `Commit` on Stack A with `sha: 'deadbeef...'`.
3. Create `Stack` B / `Repository` B (`full_name: 'org-b/repo-b'`), with a valid webhook secret for `org-b` configured in `Shipit.github`.
4. Also create a `Commit` (or none at all is not required — only the target commit's sha matters) — the key setup is that `Commit.where(sha: 'deadbeef...')` only needs to return Stack A's commit for the query to hit it, so this can be done directly without a Repository-B-side commit row.
5. POST to `/webhooks` with `X-Github-Event: status`, a valid signature computed using org-b's webhook secret, and payload: `{ "sha": "deadbeef...", "state": "success", "context": "ci/required-check", "repository": { "full_name": "org-b/repo-b", "owner": { "login": "org-b" } } }`.
6. Assert response is `200 OK`.
7. Reload Stack A's commit; assert a `Status` row now exists with `context: 'ci/required-check'`, `state: 'success'`, `stack_id: stack_a.id`.
8. Assert `commit.deployable?` (or `MergeRequest#any_status_checks_missing?` for an associated PR) is now satisfied/false, i.e. the binding `payload.dig('repository','full_name') == commit.stack.github_repo_name` (`'org-b/repo-b' == 'org-a/repo-a'`) is false, yet the status was written anyway — demonstrating the missing check.
