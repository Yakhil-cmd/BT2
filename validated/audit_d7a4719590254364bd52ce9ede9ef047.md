Webhook Signature Verification Is Scoped To The Wrong Organization, Allowing Cross-Repository Commit-Status Forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class ("a value that is checked/authorized is not the same value that is actually acted upon, leaving a residual gap between the two") maps onto a real trust-boundary break in `Shipit::WebhooksController`. The webhook signature is verified against the GitHub App belonging to the organization named in the *incoming payload itself*, but the handler that consumes that same payload (`Shipit::Webhooks::Handlers::StatusHandler`) writes to a `Commit` row selected **only by SHA**, with no re-check that the SHA belongs to a repository owned by the organization whose secret was used to authenticate the request.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to validate against using a field taken from the untrusted payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves per-organization `webhook_secret`s (multi-org GitHub App support), and `verify_webhook_signature` validates the HMAC using that org's own secret: [3](#0-2) 

Once the signature check passes, the raw payload (fully attacker-controlled JSON, since the attacker owns the organization/app whose secret produced the signature) is dispatched to every handler for the event, unmodified: [4](#0-3) 

For the `status` event, `StatusHandler#process` looks up commits **globally by SHA only**, with no scoping to a repository, stack, or the organization that just authenticated the request: [5](#0-4) 

This is the exact binding break called out in the rules: "an organization that authenticated versus the repository that is written." The `repository_owner` used for signature verification (`params.dig('repository','owner','login')`) is never checked against the repository/stack that the SHA in `Commit.where(sha: params.sha)` actually belongs to. Any organization that has its own Shipit GitHub App installed (and therefore knows its own legitimate `webhook_secret`) can sign an arbitrary JSON body with that secret, set `repository.owner.login` to its own org name (so `verify_signature` passes), and set `sha`/`state`/`context` to target a commit that belongs to a completely different, unrelated tracked stack.

The resulting write reaches `Commit#create_status_from_github!`, which affects `deployable?`/`blocked?` gating and can unblock the merge queue / continuous deployment: [6](#0-5) [7](#0-6) 

### Impact Explanation
By forging a `success` status for a required CI `context` on a victim commit SHA (SHAs are public information on GitHub, not secret), an attacker who only controls their own organization's Shipit GitHub App can flip `Commit#deployable?` to `true` for a stack they do not own. Because `add_status` calls `stack.schedule_merges` on transition to `success`/`pending`, and continuous-deployment/merge-queue automation reads `deployable?`, this can cause an **unauthorized deploy or merge** to proceed for a commit that never actually passed CI on GitHub — this is a cross-organization write with no repository ownership check, matching the "unauthorized deploy" / "cross-repository writes" impact tier.

### Likelihood Explanation
Exploitation requires only: (1) the deployment operates in the multi-org GitHub App configuration mode (`config/secrets.yml` with per-org `webhook_secret`s, as documented and covered by `test/dummy/config/secrets_double_github_app.yml`), and (2) the attacker controls (or has installed) a GitHub App for at least one organization that Shipit trusts — a routine, low-privilege setup step for any org onboarding itself to a shared Shipit instance. No `ApiClient` token, GitHub write access to the victim repo, or session is required; the attacker only needs their own valid webhook secret and the victim's public commit SHA.

### Recommendation
In `StatusHandler` (and other handlers relying on `Handler#stacks`/`Handler#repository_name`), scope the lookup to the repository named in the payload and cross-check that the resolved repository's owner matches the organization used for `verify_signature`, rejecting the webhook otherwise. Alternatively, pass the authenticated organization from `WebhooksController` down into each handler and require an exact match against the payload's `repository.owner.login` (and derived stack) before any write occurs.

### Proof of Concept
1. Attacker installs a Shipit-integrated GitHub App for `attacker-org` and knows its `webhook_secret`.
2. Attacker builds a JSON body:
```json
{
  "sha": "<victim commit sha, public on GitHub>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker signs this body with `attacker-org`'s `webhook_secret` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit in an entirely different stack/org — and calls `create_status_from_github!`, forging a passing CI status that was never reported by the victim's actual CI/GitHub integration. [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
