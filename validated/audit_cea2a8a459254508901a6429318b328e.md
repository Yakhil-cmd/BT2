### Title
Fee-on-Transfer Token Incompatibility in `requestERC20Transfer` Causes Bridge Asset Drain or DoS — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, then immediately passes the original `_value` and `_feeLimit` to `_requestERC20Transfer` without verifying how many tokens were actually received. When a fee-on-transfer (FoT) token is registered, the bridge receives `_value + _feeLimit - delta` (where `delta` is the transfer tax), but the cross-chain event records `_value` as the bridged amount. This creates a permanent accounting mismatch between the source bridge's actual holdings and the amount the counterpart bridge will release.

---

### Finding Description

In `requestERC20Transfer`:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public
{
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

The actual balance received by the bridge after `safeTransferFrom` is never measured. The original caller-supplied `_value` and `_feeLimit` are forwarded verbatim to `_requestERC20Transfer`, which then:

1. Calls `_payERC20FeeAndRefundChange` — spending `feeLimit` tokens from the bridge's balance for fee payment and refund.
2. In `modeMintBurn` mode, calls `ERC20Burnable(_tokenAddress).burn(_value)` — attempting to burn the full `_value`.
3. Emits `RequestValueTransfer` with `_value` as the canonical cross-chain amount. [2](#0-1) 

The `_payERC20FeeAndRefundChange` function in `BridgeFee.sol` transfers `fee` to `feeReceiver` and `feeLimit - fee` back to the caller, consuming exactly `feeLimit` tokens from the bridge: [3](#0-2) 

`registerToken` imposes no restriction on FoT tokens — any ERC20 address is accepted: [4](#0-3) 

---

### Impact Explanation

**Lock mode (`modeMintBurn = false`):**

| Step | Amount |
|---|---|
| Bridge receives via `safeTransferFrom` | `_value + _feeLimit - delta` |
| Bridge pays out (fee + refund) | `_feeLimit` |
| Bridge retains as collateral | `_value - delta` |
| `RequestValueTransfer` event records | `_value` |
| Counterpart bridge releases to recipient | `_value` |

The counterpart bridge releases `delta` more tokens than the source bridge locked. Each `requestERC20Transfer` call silently drains `delta` tokens from the bridge's liquidity pool. This is an unauthorized unlock of bridged assets — the invariant that `locked_source == released_counterpart` is broken.

**MintBurn mode (`modeMintBurn = true`):**

After paying fee and refund, the bridge holds `_value - delta` tokens. The subsequent `ERC20Burnable(_tokenAddress).burn(_value)` call attempts to burn `_value` but the bridge only holds `_value - delta`, causing a revert. Every `requestERC20Transfer` call with a FoT token in this mode reverts — complete DoS of the bridge's deposit path. [5](#0-4) 

---

### Likelihood Explanation

Any user can call `requestERC20Transfer` once a token is registered. The `registerToken` function is owner-only, but bridge operators routinely register tokens to enable cross-chain transfers. If any registered token implements a transfer tax (a common pattern in DeFi tokens), every deposit call is affected. The trigger requires no special privilege beyond having an approved balance of the FoT token.

---

### Recommendation

Use the balance-before/after (FoT) pattern to determine the actual received amount, and use that amount downstream:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public
{
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived == _value.add(_feeLimit), "FoT token: received less than expected");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Alternatively, explicitly document and enforce that FoT tokens must not be registered via `registerToken`.

---

### Proof of Concept

1. Deploy `Bridge` with `modeMintBurn = false` (lock mode).
2. Register a FoT token (e.g., 1% transfer tax) via `registerToken`.
3. Alice approves the bridge for `1000 + 100 = 1100` tokens (`_value = 1000`, `_feeLimit = 100`).
4. Alice calls `requestERC20Transfer(token, bob, 1000, 100, "0x")`.
5. `safeTransferFrom` pulls 1100 tokens but the bridge receives only `1100 * 0.99 = 1089` tokens (11 token tax).
6. `_payERC20FeeAndRefundChange` pays fee and refund, consuming 100 tokens → bridge holds `1089 - 100 = 989` tokens.
7. `RequestValueTransfer` event emits `valueOrTokenId = 1000`.
8. The counterpart bridge's operator calls `handleERC20Transfer` with `_value = 1000` and releases 1000 tokens to Bob.
9. The source bridge's actual collateral is 989, but it has committed to 1000 — a deficit of 11 tokens per transaction.
10. Repeated calls drain the bridge's liquidity, eventually causing `handleERC20Transfer` on the source side to fail for legitimate withdrawals. [6](#0-5) [7](#0-6)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
