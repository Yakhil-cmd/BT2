The bug in `network.js`'s `validateAndSave` function (inside `handleSavedPrivatePayments`) is directly analogous to CVE-2010-0211: a function's outcome (`objectHash.getBase64Hash`) is not properly gated on success before the code continues to use its result and to invoke a second, conflicting completion path. Compare with line 1027-1032 in `wallet.js`, where the identical operation correctly `return`s inside the `catch` block — the `network.js` copy is missing that `return`.

### Title
Missing `return` after caught hash exception causes double completion and undefined validation key in private-payment processing - (File: network.js)

### Summary
In `network.js`, function `handleSavedPrivatePayments` → inner `validateAndSave`, the code computes `json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` inside a `try/catch`. When `getBase64Hash` throws (e.g. because the payload contains data that fails the internal serialization/validation the way `getJsonSourceString`/`toWellFormedJsonStringify` guards against malformed content), the `catch` block logs the error, optionally notifies the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which itself invokes the `async.each` iteratee callback `cb()` to signal completion. However, execution does not `return` after this call, so the same tick continues to `var key = ... + json_payload_hash + ...` (now `undefined`) and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers will invoke `cb()` a second time for the same `async.each` item.

### Finding Description
The correct pattern, used in the same codebase in `wallet.js:1020-1032`, explicitly `return`s from the `catch` block on hash failure: [1](#0-0) 
By contrast, `network.js` omits this `return`: [2](#0-1) 
This is structurally the same root-cause pattern as CVE-2010-0211: a fallible operation's outcome is not checked/gated before the code proceeds to use the (now invalid/uninitialized) result and continue further processing, instead of aborting cleanly. Here, `json_payload_hash` remains `undefined` and is embedded into the `key` string used for `eventBus` deduplication (`'private_payment_validated-'+unit+'-undefined-'+output_index`), and — far more importantly — `deleteHandledPrivateChain(..., cb)` is called in the `catch` block while `privatePayment.validateAndSavePrivatePaymentChain(...)` is *also* invoked unconditionally right after, with its own callbacks each also invoking `deleteHandledPrivateChain(..., cb)` on completion: [3](#0-2) 
This produces `cb()` being called twice for the same `async.each` iteratee, and duplicate `DELETE FROM unhandled_private_payments` queries against the same row.

### Impact Explanation
Double-invocation of an `async.each` iteratee callback is undefined behavior for the `async` library and can cause the completion callback of `handleSavedPrivatePayments` to fire prematurely or multiple times, corrupting `unlock()` / mutex release timing (`lock(["saved_private"], ...)`) and the `assocNewUnits` aggregation, and can trigger duplicate `eventBus.emit("new_my_transactions", ...)` / `eventBus.emit(key, ...)` firings. Because `handleSavedPrivatePayments` processes queued private-payment chains (private-payment counterparty controlled data reaching a wallet or hub-connected full node), a private-payment counterparty can supply an `objHeadPrivateElement.payload` crafted to make `getBase64Hash`/`getJsonSourceString` throw (e.g. a payload containing `null`, an empty array/object under versions requiring non-empty, or invalid number), triggering this double-callback path on every affected node repeatedly. The risk is denial-of-service on private-payment processing (stuck/duplicated mutex state, duplicate DB writes) rather than direct fund loss, since `validateAndSavePrivatePaymentChain` still independently validates and would not accept invalid state without proper checks — but the double-completion and mutex-unlock corruption undermines the reliability of the node's private payment queue and can leave it unable to process new private payments.

### Likelihood Explanation
Reachable directly by an unprivileged private-payment counterparty sending payloads via `handleOnlinePrivatePayment` → `unhandled_private_payments` → `handleSavedPrivatePayments`, with no special privileges required, matching the "private-payment counterparty" actor explicitly in scope. Triggering the `getBase64Hash` exception requires crafting a payload shape that `getJsonSourceString` rejects (e.g. `null`, empty array without `bAllowEmpty`, or non-finite number) — feasible since the payload content originates from the peer's JSON without prior sanitization at this call site.

### Recommendation
Add a `return` immediately after `deleteHandledPrivateChain(...)` in the `catch` block of `network.js`'s `validateAndSave` (mirroring the pattern already used correctly in `wallet.js`), so that on hash-computation failure the function does not fall through to compute `key` from an `undefined` value or unconditionally call `privatePayment.validateAndSavePrivatePaymentChain`, which would produce a second `cb()` invocation for the same `async.each` item.

### Proof of Concept
1. As a private-payment sender/counterparty, send (via `handleOnlinePrivatePayment`) an `arrPrivateElements` array whose head element's `payload` is shaped so that `objectHash.getBase64Hash(payload, true)` throws — e.g. `payload` containing an empty array field (rejected by `getJsonSourceString` unless `bAllowEmpty`) or a non-finite number, while still passing the lighter checks in `handleOnlinePrivatePayment`/`savePrivatePayment` that only inspect `unit`, `message_index`, `output_index`. [4](#0-3) 
2. The payload is queued into `unhandled_private_payments` and later picked up by `handleSavedPrivatePayments`, which invokes `validateAndSave`.
3. `objectHash.getBase64Hash` throws inside the `try`; the `catch` block runs `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` (invoking `cb()` once the DELETE completes) but does not `return`.
4. Execution falls through to compute `key` using `json_payload_hash === undefined`, then calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` unconditionally; its callbacks (`ifOk`/`ifError`/`ifWaitingForChain`) each also call `deleteHandledPrivateChain(..., cb)` or `cb()` directly, so `cb` is invoked a second time for the same `async.each` item — violating the `async.each` iteratee contract and corrupting the surrounding `lock(["saved_private"], ...)` completion/unlock flow. [5](#0-4)
