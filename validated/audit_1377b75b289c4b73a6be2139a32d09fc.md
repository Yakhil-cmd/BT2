### Title
API identity attribution forgery via unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
The bug class in the Sherlock report is a state-tracking binding that can be forged/broken because a mapping (`epochsByBuyer[]`) is updated based on unverified assumptions about which records belong to which identity. The analogous binding in shipit-engine is between the GitHub identity that is supposed to author an action (deploy, rollback, lock) and the `User` record that actually gets attributed to that action in the database. In `Api::BaseController`, this attribution is derived from a client-supplied HTTP header rather than any verified credential.

### Finding Description
`Api::BaseController#current_user` resolves the acting user purely from the `X-Shipit-User` request header, with no cross-check against the authenticated `ApiClient`: [1](#0-0) 

```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

Authentication of the request only proves possession of a valid `ApiClient` token (`authenticate_api_client`, `ApiClient.authenticate`), which is a separate concept from *who* performed the action: [2](#0-1) 

`current_user` is then trusted as the authoritative actor identity throughout the deploy/rollback/lock write paths: [3](#0-2) [4](#0-3) [5](#0-4) 

The binding broken is: **GitHub identity == `User` bound to the request** should hold, but any holder of a valid `ApiClient` token (which may be a service token scoped only to `deploy:stack`/`lock:stack`, created for automation) can set `X-Shipit-User` to the login of *any* existing `Shipit::User` — including privileged users — and have all resulting `lock_author`, `aborted_by`, deploy/rollback trigger authorship permanently attributed to that impersonated user. Since `User#authorized?` gates access based on `Shipit.github_teams` membership elsewhere in the app (e.g., session-based web UI flows), downstream logic or audit trails that trust `deploy.trigger_deploy(user, ...)`/lock authorship as a proxy for "an authorized team member did this" are misled — no verification ties the header value back to the credential that authenticated the request.

### Impact Explanation
This does not grant a new capability beyond what the `ApiClient`'s own `permissions` scope already allows (e.g., it still needs `deploy:stack`/`lock:stack`/`write:stack`), so it is not a permission bypass by itself. However, it forges the recorded actor for every deploy, rollback, task-abort, and stack lock, letting a token-holder attribute privileged/destructive actions (deploys, rollbacks, force-unlocks-by-reason) to an arbitrary other `Shipit::User`, including admins or `Shipit.github_teams` members, poisoning audit trails and any authorization or notification logic downstream that keys off `lock_author`/`triggered_by`. This corresponds to escalation into identity/authorization context tied to `Shipit.github_teams`-adjacent trust decisions.

### Likelihood Explanation
Requires only a valid `ApiClient` token with narrow, otherwise-legitimate permissions (e.g., a low-privilege deploy bot token) — no GitHub App key, webhook secret, or session is needed, and the header value is trivial to set on any HTTP client. This is a low-effort, high-reliability forgery once any scoped API token is available.

### Recommendation
Do not let an arbitrary caller-supplied header silently determine attribution. Bind `X-Shipit-User` to the requesting `ApiClient`'s `creator`, require the `ApiClient` to explicitly declare/own an allowed set of impersonatable logins, or drop the header-based `current_user` mechanism in favor of deriving the actor solely from an authenticated identity (e.g., session-based `User`) for any action whose authorship has security or audit significance.

### Proof of Concept
1. Obtain any valid `ApiClient` token scoped only to `deploy:stack` for a given stack (e.g., an automation/CI token, per `ApiClient::PERMISSIONS`) — [6](#0-5) .
2. Send `POST /api/stacks/:stack_id/deploys` with header `X-Shipit-User: <victim-admin-login>` and a valid `sha`.
3. `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)` where `current_user` resolves to the victim `User` record purely from the header — [4](#0-3) .
4. The resulting `Deploy` (and any subsequent lock/rollback/abort) is permanently recorded as triggered/authored by the impersonated victim, not the actual token holder.

        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil

          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
