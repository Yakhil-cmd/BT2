### Title
Stack-scoped `ApiClient` tokens can read CCMenu status for any stack, bypassing stack authorization scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Finding Description
`Api::BaseController` implements stack-level authorization scoping for `ApiClient` tokens: when a client has a `stack_id` set, `#stacks` restricts the visible stack set to that single stack, and `#stack` resolves the requested `stack_id` param only from that restricted relation. [1](#0-0) 

`Api::CCMenuController`, however, overrides `#stack` and bypasses this scoping entirely — it resolves the stack directly from `Stack.from_param!(params[:stack_id])`, with no reference to `current_api_client.stack_id`: [2](#0-1) 

`require_permission :read, :stack` only checks that the string `read:stack` is present in `ApiClient#permissions` — it never checks whether the specific stack being accessed matches `current_api_client.stack_id`: [3](#0-2) [4](#0-3) 

The binding that is broken is: **the stack a token is authorized for (`ApiClient#stack_id`) ≠ the stack the request actually touches (`params[:stack_id]` resolved unscoped in `CCMenuController#stack`)**. Any valid token carrying `read:stack` — including one deliberately created and scoped to a single stack such as the `here_come_the_walrus` fixture (`stack: shipit`) — can be replayed against `GET /api/stacks/*stack_id/ccmenu` (routed in `config/routes.rb` line 28) for an arbitrary `stack_id`, and `CCMenuController#show` will happily render that other stack's latest deploy/rollback status. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is an authorization-scope bypass: a token intentionally minted with restricted access to one stack (e.g., via the "CCMenu Client" issuance flow in `CCMenuUrlController`, or any admin-created stack-scoped `ApiClient`) can be used to read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) for any other stack in the Shipit instance, including stacks belonging to different repositories/teams that the token holder was never granted access to. This matches the "unauthorized read of stack state / deploy output" impact class — the authorization boundary meant to be enforced by `stack_id` scoping is silently dropped for this one endpoint.

### Likelihood Explanation
High likelihood: exploitation requires only possession of any valid `read:stack` token (even a narrowly stack-scoped one, which is the normal/expected way such tokens are provisioned, e.g. by `CCMenuUrlController#client`) and knowledge/guessing of another stack's `owner/repo/environment` identifier, which is not secret information. No additional privilege or session is needed beyond having one legitimately-scoped API token.

### Recommendation
Have `Api::CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so stack-scoped tokens cannot escape their authorized stack. Audit other controllers that override `#stack`/`#stacks` for the same unscoped-lookup pattern.

### Proof of Concept
1. Create (or use) a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` pointing to Stack A (as in fixture `here_come_the_walrus`).
2. Using that client's `authentication_token`, issue `GET /api/stacks/<owner>/<repo>/<env-of-stack-B>/ccmenu?token=<token>` where Stack B is a different stack the client was never scoped to.
3. Observe HTTP 200 with Stack B's CCMenu XML payload (`lastBuildStatus`, `lastBuildLabel`, etc.), even though `BaseController#stacks` would have excluded Stack B for this client on every other API endpoint.
