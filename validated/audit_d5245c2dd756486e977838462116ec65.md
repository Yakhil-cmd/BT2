### Title
Cross-repository status webhook forgery via unscoped commit lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the commit(s) to update purely by SHA, with no scoping to the repository that the webhook signature was verified against. Any GitHub user who owns a repository (e.g., a public fork of the target project, which shares pre-fork commit SHAs) can send a legitimately-signed status webhook for *their own* repo and have it silently applied to the identically-shaed `Commit` row belonging to a completely different stack/repository, corrupting `blocking?`/`blocked?` computations used by deploy/merge/rollback gating.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:

`Status.create!` for a `Commit` row must only happen when `commit.stack.repository.full_name == verified_webhook.repository.full_name`.

In `WebhooksController`, `verify_signature` only proves the payload is legitimately signed by GitHub for the organization named in the payload (`repository_owner`), i.e. it authenticates *who sent the webhook*, not *which stack's commit table may be mutated*: [1](#0-0) 

The `status` event is dispatched unmodified to `StatusHandler#process`: [2](#0-1) 

Critically, `Commit.where(sha: params.sha)` is a **global, unscoped ActiveRecord query across the entire `commits` table**, not restricted to any repository or stack. Compare this to `CheckSuiteHandler`, which correctly scopes via the `stacks` helper (filtering by the webhook's own repository/branch) before touching any commit: [3](#0-2) 

`StatusHandler` has no equivalent repository/stack filter. Because git commit SHAs are content-addressed and forks share history up to the fork point (or an attacker can otherwise engineer a colliding tree/parent/timestamp/message to produce the same SHA1), an attacker who owns repository B can:

1. Fork or otherwise obtain a repository B that shares a commit SHA with an existing, tracked commit on stack A (trivial for any pre-fork commit of a public repo).
2. Set a real, GitHub-signed commit status on that SHA within repo B (e.g., via their own CI, or any integration they control on their own repo) — GitHub will emit a `status` webhook signed for repository B's organization.
3. Shipit's `verify_signature` succeeds because it only checks the signature belongs to organization B, which is a true and valid signature.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the row on stack A too (since it shares the SHA), and calls `commit.create_status_from_github!(params)` on it — writing a status attributed to stack A's commit even though the webhook was authenticated only for repository B.

This directly affects `Commit#blocked?`, which scans a whole range of commits, not just the current one: [4](#0-3) 

If the forged status flips the `state` of a commit in that reachable/undeployed range from a blocking state to `success`, `blocking?` (delegated to `status`) becomes false for that row, and `blocked?` for any later commit (including the revert/tip commit) silently becomes `false`, unblocking deploys and merges for stack A — a stack the attacker never authenticated against.

None of the listed guards prevent this: `verify_signature` validates webhook authenticity for the *sender's own org*, not authorization over the *target row*; `ExplicitParameters` only validates payload shape (`sha`, `state`, etc.), not repository ownership of the commit; there is no `stacks`/`repository` scoping in `StatusHandler#process` analogous to `CheckSuiteHandler`.

### Impact Explanation
A single crafted (but legitimately GitHub-signed) status webhook from an attacker-controlled repository can write a `Status` row onto a `Commit` belonging to an entirely different tenant's stack, as long as a SHA collision exists (trivially achievable via forking, since pre-fork commits share identical SHAs). This can flip `blocking?`/`blocked?` for any commit in the undeployed range of the victim stack — not merely the exact commit under deploy — enabling an unauthorized deploy or merge to proceed on stack A despite a blocking CI check that was never actually satisfied on repo A. This is a cross-tenant integrity violation matching the Critical category: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: own or fork any public repository whose history overlaps with the target stack's tracked commits (an extremely common scenario for open-source projects on Shipit), then trigger a legitimate GitHub status webhook on that shared SHA from the attacker's own repo/CI. No Shipit credentials, GitHub App keys, or webhook secrets are needed — GitHub itself signs the webhook because it originates from the attacker's own repository. The attack is repeatable against any stack whose tracked commits share history (forks, cherry-picks, or common ancestor commits) with a repository the attacker controls.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to stacks whose tracked repository matches the webhook's authenticated `repository.full_name`, mirroring the pattern used in `CheckSuiteHandler` (`stacks.where(...)`). E.g., resolve `stacks = Stack.where(...).where(repository: matching repo from payload)` first, then only touch `stack.commits.where(sha: params.sha)` for those stacks, rejecting commits belonging to any other repository even when SHAs collide.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_provenance_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerProvenanceTest < ActiveSupport::TestCase
        test "a status webhook for repo B must not flip blocking? for a commit belonging to stack A" do
          stack_a = shipit_stacks(:shipit) # tracks repo A
          shared_sha = 'deadbeef' * 5

          c1 = stack_a.commits.create!(sha: 'c1sha', message: 'base', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
          middle = stack_a.commits.create!(sha: shared_sha, message: 'middle blocking commit', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
          tip = stack_a.commits.create!(sha: 'tipsha', message: 'Revert "middle blocking commit"', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

          middle.statuses.create!(stack: stack_a, state: 'pending', context: stack_a.blocking_statuses.first || 'ci/required')
          assert_predicate middle, :blocking?
          assert_predicate tip, :blocked? # binding LHS: blocked? depends on middle staying blocking for stack A

          # Forged webhook: signed for repo B (attacker-owned), sha collides with `middle` on stack A
          params = ExplicitParameters::Params.new(sha: shared_sha, state: 'success', context: middle.statuses.first.context)
          StatusHandler.new.call(params.to_h.stringify_keys) # signature verified upstream only for repo B's org

          middle.reload
          tip.reload

          # Binding equality that should hold: middle.status was only ever set by webhooks authenticated for stack_a.repository
          # Actual: middle.status was mutated by a webhook authenticated for repo B only.
          refute_predicate middle, :blocking?   # FAILS as expected -> demonstrates the forged write landed on stack A's commit
          refute_predicate tip, :blocked?        # FAILS as expected -> deploy/rollback gating silently bypassed
        end
      end
    end
  end
end
```
