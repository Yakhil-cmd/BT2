### Title
Webhook authentication is fail-open when no `webhook_secret` is configured for an organization, letting an unauthenticated attacker forge a `membership` event and self-grant `Shipit.github_teams` authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as "signature valid" instead of "reject", and `WebhooksController#verify_signature` picks which organization's config (and therefore which secret) to check purely from an attacker-controlled JSON field. Combined with `MembershipHandler`, which blindly attaches any GitHub login the payload names to any team it names, this breaks the same trust binding described in the report's `quickSort` finding: a value used to make a security-relevant decision (which array element is trusted as pivot / which secret authenticates the request) does not actually cover all the cases it needs to, so the "sorted"/"verified" result silently becomes wrong. Here, the missing case is "no secret configured", which the code resolves in favor of the attacker instead of rejecting the request.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to check against solely from payload data: [1](#0-0) 

`repository_owner` is taken straight from the unauthenticated JSON body (`repository.owner.login` or, if absent — as for org-level events like `membership` — `organization.login`): [2](#0-1) 

The verification itself is fail-open when that organization has no `webhook_secret` configured, which the docs explicitly describe as optional: [3](#0-2) [4](#0-3) 

So for any organization where the operator followed the documented "optional" secret setup and left it blank, `verify_webhook_signature` returns `true` unconditionally — no signature, or any garbage `X-Hub-Signature` value, is accepted. The whole webhook pipeline (push, membership, pull_request, etc.) is then driven entirely by attacker-supplied JSON.

The `membership` handler uses exactly this unauthenticated payload to mutate authorization state: [5](#0-4) 

`find_or_create_team!` matches (or creates) a `Team` by the attacker-chosen `github_id`: [6](#0-5) 

If the attacker supplies the `github_id` of a team that is already one of `Shipit.github_teams` (these are the teams configured in `secrets.yml` as required for authorization, resolved and cached by handle), `find_or_create_by!` matches the existing `Team` row instead of creating a new, unrelated one: [7](#0-6) 

`team.add_member(member)` then appends a `User` (created/found purely by the attacker-supplied `member.login`) to that team: [8](#0-7) 

Finally, `User#authorized?` is exactly the membership check the attacker just forged: [9](#0-8) 

and `find_or_create_by_login!`/GitHub OAuth login binds `current_user` to whichever `User` row has that GitHub login, via `session[:user_id]` set from `User.find_or_create_from_github` on OAuth callback: [10](#0-9) [11](#0-10) 

**The equality that should hold but doesn't:** "GitHub team membership verified by GitHub" == "`Shipit::Team` membership recorded by Shipit". Before the attack, these are equal because `Team#refresh_members!` is the only legitimate path that populates membership, driven by real GitHub API data. After the forged `membership` webhook, `Shipit::Team` membership contains an attacker-chosen login that was never actually granted GitHub team membership, yet `User#authorized?` — the gate for the entire authenticated application — treats it as equivalent.

### Impact Explanation
This directly maps to the explicitly allowed High-impact category "escalation into `Shipit.github_teams` authorization." An attacker who has any real GitHub account can:
1. Send a forged `membership`/`action: added` webhook to `/webhooks` naming their own GitHub login and the public numeric `github_id` of a team already required by `Shipit.github_teams`.
2. Because that organization has no configured `webhook_secret` (a documented "optional" setting), `verify_webhook_signature` accepts the request unconditionally, with no header even required to be valid.
3. Their `User` record is now a member of a `Shipit.github_teams` team.
4. They complete the normal GitHub OAuth login flow (with their own real GitHub credentials — no privileged access needed) and `force_github_authentication` now lets them through, since `current_user.authorized?` is `true`.

This grants full authenticated access to Shipit (viewing stack state, triggering deploys/rollbacks depending on further authorization checks), i.e., an authentication-bypass-style escalation, without requiring any Shipit session, API token, or knowledge of any secret — it specifically works because no secret exists for that organization.

### Likelihood Explanation
Medium-High: it requires (a) at least one organization configured in Shipit without a `webhook_secret` — a state the documentation itself presents as an acceptable/optional configuration — and (b) the attacker knowing the numeric GitHub `id` of a required team, which is discoverable via GitHub's public teams API for many orgs, or simply by being a member of any team in that org. No privileged Shipit access, App private key, or webhook secret is needed.

### Recommendation
- Make `GitHubApp#verify_webhook_signature` fail closed: if no `webhook_secret` is configured, reject the webhook (or require `webhook_secret` to be mandatory at boot/config-validation time) instead of returning `true`.
- Do not let the organization used for signature verification be derived purely from unauthenticated JSON without cross-checking it consistently against the entity the handler will actually mutate (mirrors the report's fix of properly covering all pivot-selection branches instead of silently mis-selecting).
- In `MembershipHandler`, avoid trusting a client-supplied `team.id`/`github_id` and `organization.login` combination without confirming it actually matches records that were populated via `Team#refresh_members!`/an authenticated GitHub API call, or at minimum verify `organization.login` corresponds to the team’s already-stored `organization`.

### Proof of Concept
Assume `myorg` is configured in `secrets.yml` under `github:` with no `webhook_secret` set (documented as optional in `docs/setup.md` line 30), and `Shipit.github_teams` includes a team whose GitHub numeric id is `12345` (discoverable via `GET https://api.github.com/orgs/myorg/teams`).

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 12345, "name": "Required Team", "slug": "required-team", "url": "https://api.github.com/teams/12345" },
  "organization": { "login": "myorg" },
  "member": { "login": "attacker-github-login" }
}
```

Because `myorg`'s `webhook_secret` is unset, `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`. `MembershipHandler#process` finds the existing `Team` with `github_id: 12345` (one of `Shipit.github_teams`) and adds a `User` with `login: "attacker-github-login"` to it. The attacker then completes normal GitHub OAuth login using that same GitHub account; `User#authorized?` now returns `true` and `force_github_authentication` grants access to the full Shipit application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
