### Title
Cross-organization webhook forgery via mismatched signature-selection field and repository-write field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every downstream event handler, however, resolves the target repository/commit to write to using an entirely different field: `payload.dig('repository', 'full_name')` (e.g. `Handler#repository_name`, `StatusHandler#process`). In a multi-organization Shipit deployment (`Shipit.github(organization:)` supports one `webhook_secret` per configured GitHub org), an attacker who legitimately controls one configured organization's GitHub App/secret can craft an arbitrary JSON body, sign it with their own known secret, and set `repository.owner.login` to their own org (so `verify_signature` picks and matches their own secret) while setting `repository.full_name` (used by the handler) to any other repository name tracked by Shipit — including ones belonging to a different configured organization.

### Finding Description
The signature verification step and the "which repository is acted upon" step rely on two different, independently-attacker-controlled JSON fields inside the same signed body: [1](#0-0) 

`repository_owner` (used only to pick the org/secret for signature verification): [2](#0-1) 

`repository_name` / `full_name` (used by every handler to determine the actual `Repository`/`Stack` acted upon): [3](#0-2) [4](#0-3) 

`Shipit.github(organization:)` supports per-organization secrets when multiple orgs are configured: [5](#0-4) 

Because HMAC verification only proves "this body was signed by the secret belonging to whatever org `repository.owner.login` names," and not "the `repository.full_name` field belongs to that same org," an attacker who owns/administers one configured org (and thus knows that org's `webhook_secret`, since org admins configure their own GitHub App webhook secret) can sign a payload whose `repository.owner.login` is their own org (satisfying `verify_signature`) but whose `repository.full_name` names a repository under a completely different organization tracked by the same Shipit instance. Every handler after signature verification trusts `full_name` alone with no re-check that it belongs to the org whose secret validated the request — this is the exact "authenticated-field vs. acted-upon-field" mismatch pattern described in the report (a value trusted for authorization diverges from the value actually operated on).

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," which is explicitly listed as an in-scope binding. Concretely, using a forged, self-signed webhook an attacker can:
- Fabricate/inject `Status` records for arbitrary commits in a repository they don't own via `StatusHandler#process`, which trusts `params.sha` and creates a status without any org/ownership cross-check against the org whose secret verified the request.
- Trigger `GithubSyncJob`/`sync_github` for arbitrary stacks belonging to a repository they don't own via `PushHandler`.
- Manipulate `ReviewStack` archive/unarchive/provisioning state for other orgs' repositories via the pull_request handlers, all of which resolve `repository`/`stack` solely from `params.repository.full_name`.

Since commit statuses and check-run/CI signals gate Shipit's deploy/merge-queue safety checks (`ignore_ci`, `review.checklist`, merge queue divergence checks, etc.), forging statuses for a foreign repository could be leveraged to make CI appear green for commits belonging to a repo the attacker does not control, undermining the deploy-gating trust model — this crosses into unauthorized-deploy/cross-repository-write territory as defined in scope.

### Likelihood Explanation
Exploitability requires the target Shipit instance to be configured with multiple GitHub organizations (the multi-org config schema in `lib/shipit.rb`/`docs/setup.md`), and the attacker must legitimately control at least one of those configured orgs (i.e., know that org's `webhook_secret`). This is a realistic scenario for shared/multi-tenant Shipit deployments where several distinct GitHub organizations register their own GitHub Apps against one Shipit instance — a documented, supported configuration. No token, session, or GitHub write access to the *victim* repository is required; only knowledge of one's own org's webhook secret, which is a low bar for an org that is itself validly onboarded into the same Shipit instance.

### Recommendation
After verifying the HMAC signature, re-derive the organization strictly from the same field used by the handlers (`repository.full_name`'s owner segment, or `organization.login`) and confirm it matches the `repository_owner` value that selected the verifying secret. Reject the webhook if these two do not resolve to the same organization/App installation, ensuring the signing organization and the organization implied by the acted-upon repository are always the same value before any handler processes the payload.

### Proof of Concept
1. Configure Shipit with two organizations, `org-attacker` and `org-victim`, each with its own `github.webhook_secret` (multi-org schema per `lib/shipit.rb#github_app_config`).
2. Attacker (who administers `org-attacker`'s GitHub App) knows `org-attacker`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) event JSON body:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/some-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-attacker-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "org-attacker"`, fetches `Shipit.github(organization: "org-attacker")`, and the signature validates successfully because the attacker used the correct secret for `org-attacker`.
6. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which ignores `repository.owner.login` entirely and only checks `Commit.where(sha: params.sha)` — creating a forged CI status on `org-victim`'s commit despite the request being authenticated only for `org-attacker`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
