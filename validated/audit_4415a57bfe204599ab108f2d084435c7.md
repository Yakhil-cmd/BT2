## Title
Cross-Organization Commit Status Forgery via Webhook Signature/Repository-Scope Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
In a multi-organization Shipit deployment, the GitHub App (and thus the `webhook_secret`) used to verify an incoming webhook's HMAC signature is selected from a payload field (`repository.owner.login`, falling back to `organization.login`) that is **independent** of the field the event handler actually uses to decide which record in the database gets mutated. `StatusHandler` in particular performs no organization/repository scoping at all — it looks up commits globally by SHA. An attacker who legitimately controls one organization's GitHub App (and therefore knows that organization's `webhook_secret`) can forge a signed `status` webhook whose `sha` targets a commit that belongs to a completely different organization's stack, and inject a forged CI status for it.

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp`/`webhook_secret` to validate against using: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This binds the HMAC verification to whichever organization the attacker *names* in `repository.owner.login`/`organization.login` — not to any org that Shipit actually infers independently. Since the attacker controls the raw body being signed, as long as they know the `webhook_secret` for *some* org configured in Shipit (`Shipit.github(organization: ...)`, documented as a per-org config map in `docs/setup.md` "Using Multiple Github Applications"), they can produce a valid signature for a payload whose org-selector field says "OrgA" while other payload fields describe a completely different target.

Once past the signature check, `StatusHandler#process` performs the actual write with **no organization or repository scoping whatsoever**: [2](#0-1) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit.where(sha:)` searches across **all stacks in the whole Shipit installation**, regardless of which organization owns the repository. Compare this to `Handler#stacks`/`repository_name`, which correctly scopes via `payload.dig('repository', 'full_name')` for other handlers such as `PushHandler` and `CheckSuiteHandler`, but that field is also independent from the `repository.owner.login`/`organization.login` field used for signature verification — so nothing in the engine enforces that the org whose secret verified the signature matches the org whose repository/commit is ultimately written.

This mirrors the report's bug class: the binding that should hold — "the organization that authenticated the request equals the organization whose repository state is written" — is broken because the two are read from unrelated, attacker-controlled JSON fields inside the same signed payload.

### Impact Explanation
`create_status_from_github!` → `add_status` can flip a commit's simple state and, on success/pending, calls `stack.schedule_merges`, and fires `deployable_status` hooks that gate continuous deployment and the merge queue: [3](#0-2) 

An attacker who administers their own org's GitHub App (a legitimate, documented multi-tenant configuration) can therefore forge a "success" CI status for a commit belonging to an entirely different organization's tracked repository (SHAs of public GitHub repos are trivially discoverable), unblocking that stack's merge queue or continuous-deployment gate — an unauthorized cross-repository write and a step toward an unauthorized deploy/merge, which matches the Critical/High impact categories (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires only: (1) a Shipit instance configured with multiple GitHub organizations (explicitly supported and documented), and (2) the attacker being a legitimate admin/owner of the GitHub App for *any one* of those organizations (not the victim org). No GitHub App private key theft, no Shipit session, and no `ApiClient` token is required — just knowledge of one org's `webhook_secret`, which such an admin inherently has.

### Recommendation
Enforce a hard binding between the organization whose secret validated the signature and the repository/commit being mutated:
- After signature verification, re-derive the acting organization and pass it explicitly into the handler chain.
- In `StatusHandler` (and any handler that doesn't already scope through `Handler#stacks`), restrict `Commit.where(sha: ...)` to commits whose `stack.repository.owner` matches the verified `repository_owner`, instead of a global SHA lookup.
- Ensure every handler resolves the target repository/stack using the *same* payload field that was authenticated, and reject payloads where `repository.owner.login`/`organization.login` disagrees with the derived repository owner.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is a legitimate admin of `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`.
3. Attacker looks up a real commit SHA from `OrgB`'s public repository that Shipit tracks (e.g., visible on GitHub).
4. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "<real sha from OrgB's tracked repo>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "OrgA" } }
   }
   ```
5. Attacker computes `X-Hub-Signature` using `OrgA`'s `webhook_secret` over this exact raw body and POSTs it to `/webhooks` with `X-Github-Event: status`.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature verifies successfully (attacker computed it correctly).
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the commit belonging to `OrgB`'s stack (no org scoping), and calls `create_status_from_github!`, injecting a forged "success" status that can unblock `OrgB`'s merge queue/continuous deployment — despite the attacker having no legitimate access to `OrgB`.
