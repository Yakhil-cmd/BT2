### Title
Pool creation with `creator == Pubkey::default()` permanently locks accrued creator fees - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
In `initialize_with_permission`, the `creator` account is an unchecked, unconstrained `UncheckedAccount<'info>` supplied entirely by the transaction sender, and its key is written verbatim into `PoolState.pool_creator` with no validation that it is non-zero.

### Finding Description
`InitializeWithPermission::creator` is declared as `/// CHECK: creator of pool` `pub creator: UncheckedAccount<'info>` with no `constraint`, `address`, or non-default check. [1](#0-0) 
The instruction handler passes `ctx.accounts.creator.key()` straight into `pool_state.initialize(...)`, which assigns it to `self.pool_creator` without any zero-address (or any other) validation. [2](#0-1) [3](#0-2) 

By contrast, elsewhere in the codebase the developers do enforce a non-zero check when assigning a "beneficiary" pubkey to a config field, e.g. `set_new_protocol_owner`/`set_new_fund_owner` explicitly call `require_keys_neq!(new_owner, Pubkey::default())` before writing `amm_config.protocol_owner`/`amm_config.fund_owner`. [4](#0-3) 
No equivalent guard exists for `pool_creator` in `initialize_with_permission.rs` (or `initialize.rs`, though there `creator` is at least a `Signer`, making the zero-key case unreachable since the system program doesn't have a private key that can sign as `Pubkey::default()`). In `initialize_with_permission.rs`, however, `creator` is merely an `UncheckedAccount`, so any caller holding a valid `permission` PDA can pass `Pubkey::default()` (or any arbitrary address) as `creator`.

Every swap that accrues a creator fee for that pool subsequently increments `pool_state.creator_fees_token_0/1`, which is the pool-wide accounting ledger for money owed to the creator. The only paths to withdraw these fees are `collect_creator_fee` (requires `creator` to be a `Signer` matching `pool_state.pool_creator`) and `collect_creator_fee_permissionless`, whose `creator` account is constrained by `address = pool_state.load()?.pool_creator`. [5](#0-4) [6](#0-5) 

If `pool_creator == Pubkey::default()`, `collect_creator_fee` can never succeed because `Pubkey::default()` cannot be a real transaction `Signer` (no private key exists for the all-zero pubkey). `collect_creator_fee_permissionless` would still pass its `address` constraint (since `creator.key() == Pubkey::default() == pool_state.pool_creator`), and would try to `init_if_needed` an associated token account owned by `Pubkey::default()` to receive the fee — but this ATA is uncontrollable by anyone (no signer for `Pubkey::default()` exists to ever move the tokens out again), so the accumulated `creator_fees_token_0/1` become permanently inaccessible once swept into that ATA (or the vault balance is simply stuck as ever-growing unclaimable "creator fee" debt if the ATA creation itself is rejected by the token program).

### Impact Explanation
This mirrors the reported analog class ("delegation to the zero address permanently destroys value that should have gone to a real owner"): here, setting `pool_creator = address(0)` at pool-creation time permanently locks the pool's ongoing creator-fee stream. Every swap through that pool with `enable_creator_fee = true` sends real user/LP funds into an unrecoverable bucket, which is a permanent freezing-of-funds condition on protocol accounting (creator fee ledger), satisfying "permanent freezing of user funds / insolvent fee-ledger accounting."

### Likelihood Explanation
Reaching this requires only calling the unprivileged `initialize_with_permission` instruction (available to anyone holding a valid `permission` PDA created via `create_permission_pda`, which itself appears permissionless/self-serve based on the account list) with `creator = Pubkey::default()`. No elevated privileges, validator collusion, or off-chain component is needed — a single crafted transaction is sufficient to create a permanently fee-locked pool.

### Recommendation
Add an explicit non-default check on the `creator` account in `InitializeWithPermission`, e.g. `constraint = creator.key() != Pubkey::default() @ ErrorCode::InvalidOwner` (or reuse `require_keys_neq!` as done for `protocol_owner`/`fund_owner` in `update_config.rs`), before writing it into `pool_state.pool_creator`.

### Proof of Concept
1. Attacker (or any user) obtains a `permission` PDA via `create_permission_pda` for their own `payer` key.
2. Attacker calls `initialize_with_permission` with `creator = Pubkey::default()` and a valid token pair/mints; the instruction has no constraint rejecting this and stores `pool_state.pool_creator = Pubkey::default()`. [2](#0-1) 
3. Any user performs `swap_base_input`/`swap_base_output` against the pool with `enable_creator_fee = true`, accruing `pool_state.creator_fees_token_0/1`.
4. `collect_creator_fee` can never be invoked successfully because `Pubkey::default()` cannot sign a transaction as required by `#[account(mut, address = pool_state.load()?.pool_creator)] pub creator: Signer<'info>`. [7](#0-6) 
5. `collect_creator_fee_permissionless` succeeds in matching `creator.key() == pool_state.pool_creator == Pubkey::default()`, but the resulting `creator_token_0/1` ATAs are owned by an address with no controlling keypair, so the swept fee tokens become permanently unspendable — the funds are frozen indefinitely.
