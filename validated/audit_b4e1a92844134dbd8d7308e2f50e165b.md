### Title
Webhook signature verification selects the wrong GitHub App/secret based on an attacker-controlled field, decoupling "organization that authenticated" from "repository that is written" - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and therefore which `webhook_secret`) to validate the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unverified request body, *before* any signature check happens. The event handlers that subsequently run operate on a completely different field — `repository.full_name` — parsed from the same body. Nothing enforces that the organization whose secret validated the request is the same organization that owns the repository the handlers act on.

### Finding Description
`verify_signature` computes the organization used for verification purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-organization config via `github_app_config`, which is a simple hash lookup keyed by whatever organization name is supplied: [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` **trivially returns `true` when no `webhook_secret` is configured** for that organization: [4](#0-3) 

The multi-organization config schema documented in the engine explicitly allows some organizations to have `webhook_secret: # nil`: [5](#0-4) 

After `verify_signature` passes, `create` re-parses the raw body and dispatches to handlers using the full payload, including `repository.full_name`, which is never re-checked against the organization used for verification: [6](#0-5) 

**Binding that should hold (equality):**
`organization_whose_secret_authenticated_the_request == owner_of_repository(full_name)_that_handlers_act_on`

**Before an attack:** for a legitimate webhook, both sides come from the *same* GitHub-emitted payload, so they always match, and the payload is HMAC-signed by the org that owns the repo.

**After the attacker's forged request:** the attacker POSTs directly to the public `/webhooks` endpoint (no GitHub delivery required — this endpoint is unauthenticated by design, relying solely on the HMAC check) with a JSON body where:
- `repository.owner.login` (or `organization.login`) = an organization configured in Shipit with a blank/absent `webhook_secret`
- `repository.full_name` = `"<victim-org>/<victim-repo>"`, a completely different, properly-secured organization/stack

`verify_signature` resolves the GitHubApp for the attacker-chosen organization, finds `webhook_secret` blank, and returns `verified = true` unconditionally — no HMAC is even checked. Execution proceeds to `create`, which dispatches the (fully attacker-controlled, unsigned) payload to handlers (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) that act on `victim-org/victim-repo` as if it were a legitimate GitHub event.

### Impact Explanation
This lets an unprivileged, unauthenticated network attacker inject arbitrary, unsigned webhook events for any repository/stack tracked by the Shipit instance, as soon as *any* configured organization in a multi-org deployment lacks a `webhook_secret`. Depending on which handler is exercised this can:
- Forge commit `status` events, fabricating a passing CI/deployability status on an arbitrary commit of the victim repository/stack, which downstream deploy-gating logic in Shipit treats as legitimate — this can enable an unauthorized deploy/rollback of a commit that never actually passed CI.
- Trigger `GithubSyncJob`/`RefreshCheckRunsJob` for the victim stack, or create/modify `Team`/`User` membership records, using the victim organization's identity without ever presenting a valid signature for it.

This crosses the "organization that authenticated versus the repository that is written" trust boundary called out as in-scope, and the resulting forged deployability status maps to the Critical "unauthorized deploy/rollback" impact category.

### Likelihood Explanation
Exploitability depends entirely on the deployment having at least one configured organization with no `webhook_secret` set while other organizations are properly configured — a realistic misconfiguration explicitly supported by the shipped multi-org config template (`webhook_secret: # nil`). Given that, the attack requires only crafting one HTTP POST to a public, unauthenticated endpoint with attacker-chosen JSON — no credentials, tokens, or GitHub access required.

### Recommendation
- After selecting the organization from `repository_owner`, verify that the same organization owns the repository referenced by `repository.full_name`/`organization.login` used by the dispatched handlers; reject on mismatch.
- Do not treat a missing `webhook_secret` as "verification not required" in a multi-organization configuration — require every configured organization to have a non-blank `webhook_secret`, or fail closed if the resolved organization has no secret at all in multi-org mode.
- Consider binding webhook events to registered `Repository`/`Stack` records looked up by the *verified* organization rather than trusting owner/organization fields embedded in the still-unauthenticated payload used to pick the verification key.

### Proof of Concept
Assume Shipit is configured with a multi-org schema where organization `no-secret-org` is present but has no `webhook_secret`, and `victim-org` is a properly-secured organization owning stacks tracked by Shipit:

```
POST /webhooks HTTP/1.1
Host: shipit.example.com
Content-Type: application/json
X-Github-Event: status
X-Hub-Signature: sha1=deadbeef   # arbitrary/garbage, irrelevant

{
  "sha": "<attacker-chosen-sha-of-victim-repo-commit>",
  "state": "success",
  "context": "ci/tests",
  "description": "forged",
  "target_url": "https://example.com",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "no-secret-org" }
  }
}
```

`repository_owner` resolves to `no-secret-org`, `verify_webhook_signature` short-circuits `true` because `no-secret-org` has no configured secret, and the `status` handler then creates a `Status` record on `victim-org/victim-repo`'s commit as if GitHub itself reported it — without ever validating any signature tied to `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
