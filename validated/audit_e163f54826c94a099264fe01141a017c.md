### Title
CFS Silently Drops Failures for Candidates Entering CandTesting After a Checkpoint, Allowing Bypass of VRank Gate — (`kaiax/vrank/impl/scoring.go`)

---

### Summary

A candidate who enters `CandTesting` after the first intra-epoch checkpoint has been written will never have their failures accumulated in the CP matrix for the remainder of that epoch. The `if _, ok := cpMatrix[candidate]; !ok { continue }` guard in `applyBlocksForCPMatrix` silently discards every cfReport entry for that candidate, leaving them absent from the CFS map. Because `isPassVrankTest` is fail-open (`!ok → return true`), the candidate passes the VRank gate at epoch end and incorrectly transitions `CandTesting → ValActive`.

---

### Finding Description

**Checkpoint seeding — the root cause**

`lookupCFSSeed` resolves the CP matrix seed in priority order: in-memory cache → DB checkpoint → cold-start `newCPMatrix`. [1](#0-0) 

On a **cold start** (no cache, no checkpoint), `newCPMatrix(blockNum)` is called with the *queried* block number, so `GetCandTesting(blockNum)` returns the current candidate set — including any candidate who entered mid-epoch. Cold start is therefore **not vulnerable**. [2](#0-1) 

The vulnerability lives in the **checkpoint path**. Checkpoints are written every `scoreCheckpointInterval = VRankEpoch / 8 = 10800` blocks by `PostInsertBlock`. [3](#0-2) 

`calcCheckpointBlock` computes the checkpoint block as `blockNum - (blockNum % checkpointInterval)`, which is independent of `epochStart`. [4](#0-3) 

**Concrete scenario (epoch = 86400, interval = 10800):**

| Block | Event |
|---|---|
| 86400 | `epochStart` |
| 97200 | First intra-epoch checkpoint written; `GetCandTesting(97200)` does **not** include C1 |
| 97400 | C1 enters `CandTesting` |
| 97401–172799 | C1 appears in cfReports (validated by `VerifyHeader` against `GetCandTesting(N-1)`) |
| 172799 | Epoch-end: `GetCFS(172799)` called for state transition |

When `getCPMatrix(172799)` is called, `loadCPMatrixCheckpointInEpoch` finds the checkpoint at `97200` (C1 absent). `applyBlocksForCPMatrix(97201, 172799, checkpointSeed)` then processes every block in the range. [5](#0-4) 

For every block where C1 appears in a cfReport, the guard fires:

```go
if _, ok := cpMatrix[candidate]; !ok {
    logger.Warn("cfReport contains address not in candidates list; skipping", ...)
    continue
}
```

C1 is never added to the matrix. All failures are silently discarded. [5](#0-4) 

**Cache propagation amplifies the bug.** `PostInsertBlock` calls `getCPMatrix` for every block, building each cache entry on top of the previous one. Since the `97200` checkpoint lacks C1, every subsequent cache entry also lacks C1. The second checkpoint at `108000` is written from a cache entry that also lacks C1 — so C1's failures are dropped for the **entire remainder of the epoch**, not just until the next checkpoint. [6](#0-5) 

**Fail-open gate seals the bypass.** At epoch end, `isPassVrankTest` returns `true` when the address is absent from the CFS map: [7](#0-6) 

```go
func (ctx *TransitionContext) isPassVrankTest(addr common.Address) bool {
    cfs, ok := ctx.CFS[addr]
    if !ok { // no score recorded → pass
        return true
    }
    return cfs < ctx.CfsThreshold
}
```

C1 is absent → passes → `applyEpochTransition` routes C1 through `competeOrDemote` → `CandTesting → ValActive`. [8](#0-7) 

---

### Impact Explanation

An unreliable candidate (one that consistently fails to respond to `VRankPreprepare` messages) bypasses the VRank reliability gate and is promoted to `ValActive`. This is an **invalid state transition** — the protocol's explicit purpose is to prevent exactly this. An unreliable validator in the active set degrades consensus liveness and can cause round changes, increasing the risk of chain slowdowns or splits on honest nodes.

---

### Likelihood Explanation

The attack is **permissionless and timing-controlled**. Any candidate can observe the chain, wait until after the first intra-epoch checkpoint (`epochStart + 10800`), then trigger their `CandReady → CandTesting` transition (via the normal staking/governance flow). They then simply do nothing (ignore all `VRankPreprepare` messages). No privileged keys, validator collusion, or cryptographic breaks are required.

---

### Recommendation

In `lookupCFSSeed`, when falling back to a DB checkpoint, merge the checkpoint's candidate set with `GetCandTesting(blockNum)` so that candidates who entered after the checkpoint are added to the seed with zero scores before replay begins. Alternatively, when `applyBlocksForCPMatrix` encounters a cfReport address absent from the matrix, add it dynamically (with an empty reporter map) rather than silently skipping it.
