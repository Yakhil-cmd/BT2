### Title
Webhook signature verification authenticates the sender's organization but not the repository that handlers act on, allowing cross-repository status/webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks a GitHub App configuration by reading `repository.owner.login` (or `organization.login`) directly out of the *unauthenticated* JSON body, then verifies the HMAC signature against that organization's `webhook_secret`. Once the signature check passes, the full raw payload — including the `repository.full_name` field used by every downstream handler to resolve the target `Shipit::Repository`/`Stack` — is dispatched unmodified to the handlers. Nothing ties the organization whose secret validated the signature to the repository that the handlers subsequently act on.

### Finding Description
The controller determines which secret to verify against solely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only proves that the whole raw body was HMAC-signed with *some* configured organization's secret — it says nothing about which repository the payload describes: [3](#0-2) 

Every handler, however, resolves the target `Repository`/`Stack` from a *different* field of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Shipit explicitly supports multiple independently configured GitHub organizations/Apps, each with its own `webhook_secret`, as documented for multi-tenant installs: [7](#0-6) 

This is the binding-break the report class describes: the organization whose credential (`webhook_secret`) authenticated the request (`repository.owner.login`) is not the repository the code subsequently writes to/acts on (`repository.full_name`). An attacker who legitimately controls an organization/repo configured in Shipit (and thus knows that org's own `webhook_secret`, since they installed/administer that GitHub App) can:

1. Build a JSON body where `repository.owner.login` = `attacker-org` (so `Shipit.github(organization: 'attacker-org')` resolves their own known secret) and `X-Github-Event` = `status`, `push`, `pull_request`, `check_suite`, etc.
2. Set `repository.full_name` (and other nested repository identifiers used deeper in the handler, e.g. for `status`/`push`) to `victim-org/victim-repo`.
3. Sign the whole raw body with the attacker-org secret they know and POST it to `/github/webhooks`.
4. `verify_signature` validates successfully because the signature matches the attacker-org's real secret; the request is accepted and dispatched to `Shipit::Webhooks.for_event(event)` handlers with the forged `repository.full_name` intact.
5. `StatusHandler`/`PushHandler`/`PullRequest::*Handler` resolve `victim-org/victim-repo`'s `Stack` via `Repository.from_github_repo_name(params.repository.full_name)` and act on it as if GitHub itself had sent the event for that repository.

### Impact Explanation
This breaks the trust boundary between "which GitHub organization proved it sent this webhook" and "which repository's state gets modified", enabling a registered-but-unprivileged organization to forge events against a completely different, victim-owned stack that it has no push access to. Depending on handler reached, this can forge commit statuses (`StatusHandler`, potentially satisfying `ci.require`/`ci.blocking` gates and enabling an unauthorized deploy), forge `push`/`check_suite` events that trigger `RefreshCheckRunsJob` against the victim stack, or forge `pull_request` events that create/close/label review-stack pull requests for the victim repository — all without ever holding the victim's GitHub credentials. Because CI-status forgery can unblock Shipit's deploy gating for a victim stack, this reaches the "unauthorized deploy" impact tier.

### Likelihood Explanation
Requires only that the attacker control one Shipit-configured GitHub organization/App among potentially several (a documented, supported multi-org setup) and know that org's own `webhook_secret` — which is not privileged relative to their own org, and is something any org admin naturally has access to for their own installation. No access to the victim's secret, `GITHUB_TOKEN`, or a Shipit session is needed, satisfying the "unprivileged attacker" bar in-scope.

### Recommendation
After successfully verifying the HMAC signature for `repository_owner`, additionally verify that `repository.full_name`'s owner segment (and/or `organization.login`) matches the same `repository_owner` used to select the signing secret before dispatching to handlers; reject the request otherwise.

### Proof of Concept
1. Configure Shipit with two organizations (as in `test/dummy/config/secrets_double_github_app.yml`): `attacker-org` (secret known to attacker) and `victim-org` (secret unknown).
2. Craft body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "sha": "<victim commit sha>", "state": "success", ...}`.
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, body)>`.
4. POST to `/github/webhooks` with `X-Github-Event: status`.
5. Observe `verify_signature` passes (`Shipit.github(organization: 'attacker-org')` matches), and `StatusHandler` updates the commit status on `victim-org/victim-repo`'s stack, as resolved via `Repository.from_github_repo_name('victim-org/victim-repo')`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
