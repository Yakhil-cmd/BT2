### Title
`Shipit::Webhooks::Handlers::StatusHandler#process` matches statuses by SHA alone, allowing cross-repository status forgery that enqueues `ProcessMergeRequestsJob` for an unrelated stack - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no scoping to the repository/organization that the webhook signature was verified for. `Shipit::WebhooksController#verify_signature` only proves the payload was HMAC-signed with the webhook secret configured for `repository_owner` (the org named in the *attacker-controlled* payload body), it does not bind the `sha` field to that repository. Because git commit SHAs are content-addressed, an attacker who owns/controls a repository configured in Shipit (even an unrelated one, e.g. a fork with identical history) can emit a validly-signed `status` webhook naming their own repo, but containing a `sha` that also exists as the head commit of a victim's `Stack`'s pending `MergeRequest`, causing Shipit to write a `Status` onto the victim's commit and enqueue `ProcessMergeRequestsJob` for the victim's stack.

### Finding Description
The claimed binding is: `stack enqueued for merge processing == stack named by the verified webhook's repository`.

Tracing the code shows this equality is **not enforced**:

1. `WebhooksController#verify_signature` computes `repository_owner` from the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`) and verifies the HMAC signature against the webhook secret configured for that organization via `Shipit.github(organization: repository_owner).verify_webhook_signature`. [1](#0-0) [2](#0-1) 
This only proves "this payload was signed by an org Shipit knows about" (the org the attacker owns/controls, or any org whose webhook secret has leaked/is misconfigured to be shared) - it says nothing about the `sha` value inside the body.

2. `StatusHandler#process` then dispatches purely on `sha`, with **no filter on repository, stack, or organization**: [3](#0-2) 
`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` iterates over every `Commit` row in the entire database matching that SHA, across all stacks/tenants.

3. `Commit#create_status_from_github!` creates the `Status` using the commit's *own* `stack_id`, not anything derived from the webhook's `repository` field: [4](#0-3) [5](#0-4) 

4. `Status#after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery`, unrelated to `ProcessMergeRequestsJob` directly for CD, but the state transition on `Commit` (`pending`→`success`) is what the `commits_test.rb` fixture demonstrates triggers `ProcessMergeRequestsJob.perform_later(commit.stack)` via the `add_status` deployable-status transition logic: [6](#0-5) [7](#0-6) 

So, the exact broken equality is:
`repository_owner (verified, attacker-controlled org)` ≠ `commit.stack.repository (target of the mutation)`,
yet the code proceeds as if a verified webhook for org A automatically authorizes state mutation of any commit/stack whose SHA happens to collide, including stacks belonging to org B.

**Attacker's exact request:** a `POST /webhooks` with header `X-Github-Event: status`, `X-Hub-Signature` computed with the webhook secret of an organization/repo the attacker legitimately owns and has configured in Shipit (or any repo Shipit trusts), and body:
```json
{
  "sha": "<victim MergeRequest head sha>",
  "state": "success",
  "context": "ci/anything",
  "repository": {"owner": {"login": "attacker-org"}}
}
```
Because the SHA is content-addressed, the attacker can trivially produce a commit with an identical SHA to the victim's PR head (e.g., by forking/mirroring the same history, or by crafting a commit with matching tree/parent/message/timestamps — feasible whenever the victim's repository is public, as is typical for open-source Shipit setups), then flip its status via their own repo's CI/webhook.

Existing guards do not stop this: `verify_signature` only checks a valid signer for the *claimed* org, `drop_unhandled_event` only checks the event type is registered, and there is no `ExplicitParameters` validation tying `sha` to a specific stack — the `StatusHandler#params` schema only requires `:sha`, `:state`, etc., with no repository/stack binding at all. [8](#0-7) 

### Impact Explanation
An attacker who controls any single repository/organization onboarded into the same Shipit instance can:
- Forge a `success`/`pending` status against **any commit in any stack** across the whole Shipit instance whose SHA they can reproduce, regardless of tenant boundary.
- This can flip a victim `MergeRequest`'s head-commit status from `failure`/`pending` to `success`, causing `ProcessMergeRequestsJob.perform_later(victim_stack)` to run.
- The job then calls `merge_request.refresh!` and `merge_request.all_status_checks_passed?` / `merge_request.merge!` using **the victim stack's own `github_api`/`GITHUB_TOKEN`** credentials — an unauthorized merge action performed with the victim's credentials, triggered by an attacker who never had access to that org. [9](#0-8) 

This matches the "payload for one repository mutating another's stack/commit" and "unauthorized merge" Critical impact categories. It is repeatable against any stack whose commit SHAs are attacker-reproducible (most straightforwardly, any public-history repository), and the blast radius spans all tenants hosted by the same Shipit instance.

### Likelihood Explanation
Preconditions:
- Victim stack has `merge_queue_enabled: true` and a pending `MergeRequest` whose head SHA the attacker can reproduce (trivial for any public/open-source repository, since git SHAs are purely a function of commit content and ancestry, not the remote/org).
- Attacker needs to control (or have push/webhook access to) at least one repository/organization that Shipit already trusts (i.e., has a configured webhook secret) — this is the normal, low-privilege situation for any of Shipit's other onboarded users/orgs, not the victim's own credentials.
- No Shipit session, API token, or GitHub team membership is required; the attacker only needs the ability to make GitHub emit (or to directly POST) a correctly-signed webhook for their own org.

Attacker cost is low: this is a single crafted HTTP request per attempt, repeatable at will, and does not require guessing any secret — only reproducing a public SHA.

### Recommendation
Scope the `StatusHandler` (and analogous handlers) commit lookup to the repository named in the verified webhook payload, not just the SHA. For example, resolve the `Stack`/`Repository` from `params.repository` (already validated by the signature-verification step against `repository_owner`) and restrict `Commit.where(sha: params.sha, stack_id: stack.id)` (or filter through `stack.commits`) instead of a bare cross-tenant `Commit.where(sha:)`. The same repository-scoping check should be applied to any other webhook handler that resolves records purely by `sha` without tying it back to the verified repository/org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test ":status from an unrelated repository can move an unrelated stack's commit and enqueue ProcessMergeRequestsJob" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled stack with pending MergeRequest
  victim_commit = shipit_commits(:second) # head commit of a pending MergeRequest, current state 'failure'
  attacker_owned_org = 'attacker-org' # a *different* org configured in Shipit, e.g. fixtures' second github app config

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'owner' => { 'login' => attacker_owned_org } }
  }.to_json

  # Sign with attacker_owned_org's webhook secret, NOT victim_stack's org secret
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or compute real HMAC with attacker org's secret

  assert_enqueued_with(job: Shipit::ProcessMergeRequestsJob, args: [victim_stack]) do
    post :create, body:, as: :json
  end

  assert_equal 'success', victim_commit.reload.state
end
```
Assertion on both sides of the binding: `repository_owner` used for signature verification (`attacker_owned_org`) must **not** equal `victim_commit.stack.repository`/org, yet `ProcessMergeRequestsJob` is enqueued with `args: [victim_stack]` and `victim_commit.state` transitions to `success` — proving the mutation crossed the tenant boundary the binding claims exists.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
