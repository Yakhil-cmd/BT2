### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` binds an `ApiClient` token's authorization to a specific `Stack` via `current_api_client.stack_id`, filtering the queryable `stacks` relation accordingly before any `stack_id` param is resolved. `Shipit::Api::CCMenuController` overrides `#stack` and resolves `params[:stack_id]` directly against `Stack.from_param!`, never consulting `current_api_client.stack_id`. This mirrors the reported bug class: a value that should be checked against a trusted binding (the stack the token is scoped to) is instead accepted unchecked (the stack name supplied in the request), because a component (this controller) reimplements resolution without preserving the invariant enforced elsewhere.

### Finding Description
`Shipit::ApiClient` can be scoped to a single stack (`belongs_to :stack, optional: true`), and `Shipit::UnlimitedApiClient`/`ApiClient#stack_id?` is used by `Shipit::Api::BaseController` to restrict which stacks a scoped token may touch: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Every controller that inherits this default `#stack` (e.g. `DeploysController`, `RollbacksController`, `TasksController`) has its stack lookup filtered by the scoped stack when the client is stack-restricted, exactly like the `here_come_the_walrus` fixture (`stack: shipit`, `permissions: [read:stack]`) demonstrates in tests.

`Shipit::Api::CCMenuController`, however, overrides `#stack`: [2](#0-1) 

```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

This resolves `stack` directly from the unauthenticated `params[:stack_id]` path segment, completely bypassing the `current_api_client.stack_id?` check that `BaseController#stack` enforces. `check_permissions!` only validates the coarse `operation:scope` string (`"read:stack"`), never the specific stack id: [3](#0-2) 

So for a stack-scoped `ApiClient` (one with a non-nil `stack_id`), the *only* enforcement point that ties the token to its authorized stack is `BaseController#stacks`/`#stack`. `CCMenuController` re-derives `stack` independently and never re-applies that binding, so the equality `current_api_client.stack ID == stack being served` is never checked here, even though it is enforced everywhere else in the API.

### Impact Explanation
An attacker in possession of any valid, stack-scoped `ApiClient` token with `read:stack` permission (a low-privilege, single-stack read-only token, e.g. one meant only for a CI/CD dashboard integration on stack A) can pass a different stack's `stack_id` in the URL/path and successfully retrieve that stack's build/deploy status through `GET /:stack_id/cctray.xml`(routed to `CCMenuController#show`), which discloses `last_deployed_at`, deploy status (success/failure/running), and stack activity for *any* stack in the Shipit instance — not just the one the token was scoped to. This is an unauthorized cross-stack read of stack state, matching the "High" impact category ("unauthenticated/unauthorized read of stack state, task streams or deploy output").

### Likelihood Explanation
Any environment that issues stack-scoped `ApiClient` tokens (a supported, documented feature via `ApiClient#stack` and exercised in the `here_come_the_walrus` fixture) is affected. Exploitation requires only a valid, low-privilege stack-scoped token — no elevated privileges, no interception, and no social engineering — and a single unauthenticated GET request with a different `stack_id`. This is a straightforward, deterministic bypass of an existing access-control invariant, not a theoretical or best-practice concern.

### Recommendation
Do not override `#stack` in `CCMenuController` to bypass the base scoping. Reuse `BaseController#stack` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so `current_api_client.stack_id` continues to constrain which stack can be shown. If URL-based token authentication needs a different resolution path, explicitly re-check `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id` before rendering, mirroring the recommendation in the referenced report of enforcing the binding at the trusted source instead of trusting caller-supplied identifiers.

### Proof of Concept
1. Create (or have) a stack-scoped `ApiClient` for `stack_A` with `permissions: ['read:stack']` (as in fixture `here_come_the_walrus`), and note its `authentication_token`.
2. Request the CCMenu feed for a *different* stack `stack_B` using that token:
   `GET /stack_B_owner/stack_B_name/stack_B_env/cctray.xml?token=<stack_A-scoped-token>`
3. `CCMenuController#authenticate_api_client` accepts the token (it is valid), and `CCMenuController#stack` resolves `stack_B` directly via `Stack.from_param!(params[:stack_id])`, ignoring that the token's `stack_id` is `stack_A`'s id.
4. `#show` renders `stack_B`'s CCMenu XML (name, last build status, last build time, web URL), disclosing deploy state for a stack the token was never authorized to access. [4](#0-3) [5](#0-4) [6](#0-5)

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      end
