### Title
Private-asset payments sent to an AA address are permanently unspendable because AAs have no device to receive/reveal the private chain - ([File: aa_composer.js])

### Summary
The external report describes ERC-20 tokens becoming permanently stuck when sent to a contract that has no logic to receive/handle them. The closest concrete analog in `ocore` is the inverse direction of a safeguard the code already implements for the opposite flow: `aa_composer.js` explicitly forbids an AA from **sending** a private asset, because "it'll fail validation anyway due to lack of spend_proofs" [1](#0-0) . However, nothing in the codebase prevents a regular user or another AA from **sending** a private asset **to** an AA address, and an AA cannot participate in the private-chain reveal protocol at all (it has no `device` counterparty to which the encrypted chain elements are forwarded), so such funds become unrecoverable at the AA address.

### Finding Description
Private assets in Obyte are not spendable purely from public on-chain data: the payment's real amounts/addresses are only known through off-band "private chain" elements that must be forwarded between the sender's and recipient's *devices*, and later revealed on-chain (address populated in `outputs`) once the chain is validated and saved via `validateAndSavePrivatePaymentChain` [2](#0-1) . This reveal/forward mechanism is device-to-device: `forwardPrivateChainsToOtherMembersOfOutputAddresses` looks up wallets/devices that control the output address and pushes the private elements to them [3](#0-2) , and for shared/multisig addresses it walks `shared_address_signing_paths`/`my_addresses` to find real devices [4](#0-3) .

An Autonomous Agent (AA) address has none of this: it is a deterministic hash of an AA definition, not tied to any device, `my_addresses`, or `shared_addresses` entry. If someone sends a private-asset payment whose recipient output address is an AA:
- There is no device to receive the forwarded private chain, so the AA (and its "owner", who doesn't exist) never learns the amount/blinding/address needed to reveal or spend the output.
- Even if a chain were somehow force-revealed, `aa_composer.js`'s own trigger/response logic explicitly treats private assets as something an AA cannot handle when trying to pay them out, calling it a hard error ("sending private asset from AA") [5](#0-4) , confirming AAs are architecturally incapable of producing the `spend_proofs` required to move private-asset funds.
- Nothing on the receiving side blocks the deposit: `checkAAOutputs`/`readAADefinitions` in `aa_addresses.js` only validate `bounce_fees` amounts for outputs sent to AAs; they never inspect whether the asset is private or fixed-denomination [6](#0-5) . Likewise `validateAATrigger` in `validation.js` only inspects public payment payloads/outputs to detect AA triggers and count them, with no asset-type restriction [7](#0-6) .

The net effect mirrors the external report's bug class exactly: a token/asset type is transferred into an "account" (the AA address) that has no logic or capability (no device, no spend-proof generation path) to receive, reveal, or spend it, so the funds become permanently stranded.

### Impact Explanation
Funds of a private asset sent to any AA address (deliberately or by user/wallet-integration mistake, e.g. through a payment link, faucet, or dApp integration that resolves an AA address as a valid recipient) become permanently locked: they can never be revealed (no device backs the AA to run the private-chain reveal protocol) and even if revealed, the AA composer code path refuses to build a spend for private assets. This is an unconditional, irreversible fund-loss condition for anyone who is misled or scripted into targeting an AA address with a private-asset transfer — a medium/high severity fund-freezing issue, analogous to sending ERC-20 into a non-token-aware contract.

### Likelihood Explanation
Likelihood is moderate: private assets are less commonly used than public bytes/tokens, and most UI flows validate recipients, but nothing in `ocore` itself prevents constructing/broadcasting such a transaction (wallet-level checks such as `sendMultiPayment`'s handling of `objAsset.is_private` focus on forwarding logic for legitimate wallets, not on rejecting AA-address destinations) [8](#0-7) . Any third-party integration, custom script, or exchange withdrawal tool that composes a private-asset payment to an address without checking `aa_addresses` (as `checkAAOutputs` does only for bounce-fee purposes, not for private/fixed-denomination assets) can trigger permanent loss.

### Recommendation
Add an explicit check — symmetrical to the existing "AA cannot send private asset" guard in `aa_composer.js` — that rejects, at validation time (`validation.js`'s `validateAATrigger` / `validatePaymentInputsAndOutputs`) or at the wallet-composition layer (`aa_addresses.checkAAOutputs`), any payment message whose asset is `is_private` (or `fixed_denominations`, if similarly unreachable) when the output address resolves to a known AA (`aa_addresses` table). This prevents composing/broadcasting such payments and surfaces a clear error to the sender instead of silently stranding funds.

### Proof of Concept
1. Define/issue a private asset (`is_private: true`) and deploy any AA (`autonomous agent` definition) — no special `bounce_fees` or messages required.
2. Using `sendMultiPayment`/`divisibleAsset.composeAndSaveMinimalDivisibleAssetPaymentJoint`, send an output of that private asset to the AA's address as `to_address`.
3. Observe that `checkAAOutputs` (`aa_addresses.js:120-156`) only validates `bounce_fees` for the `base` asset default and does not reject the transaction for the private-asset case, so the payment is composed and broadcast successfully.
4. Because the AA address has no corresponding `my_addresses`/`shared_addresses`/device entry, `forwardPrivateChainsToOtherMembersOfOutputAddresses` (`wallet.js:1082-1116`) finds no wallet/device to forward the private chain to, so the funds are never revealed to any controlling party, and the AA itself can never produce spend proofs to move them (as confirmed by the AA-composer's own rejection of private-asset payouts at `aa_composer.js:1329-1330`). The private-asset output at the AA address is permanently unspendable.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
}
