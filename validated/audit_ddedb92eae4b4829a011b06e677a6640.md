`Api::CCMenuController#stack` bypasses `current_api_client.stack_id` scoping, allowing cross-stack read of build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides the private `stack` helper defined in `BaseController` and resolves the target stack via `Stack.from_param!(params[:stack_id])` against the entire `Stack` table, instead of the scoped `stacks` relation. This lets any client holding a `read:stack` token — even one restricted to a single stack — fetch the CCMenu XML status for any other stack by ID/slug.

### Finding Description
The intended binding is: `stack == a member of stacks`, where `stacks` is defined in `app/controllers/shipit/api/base_controller.rb:74-76` as:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This is the pattern every other API controller relies on (e.g. `StacksController#stack` at `app/controllers/shipit/api/stacks_controller.rb:87-89` calls `stacks.from_param!(params[:id])`).

`CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) instead defines:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This calls `from_param!` directly on the `Stack` class/full relation, never touching `current_api_client.stack_id`. `require_permission :read, :stack` (line 6) only checks that the token has the `read:stack` permission string via `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) — it performs no per-record scoping. So a token scoped to stack A (`current_api_client.stack_id == stack_a.id`) with `read:stack` permission passes the permission check, then `stack` resolves to whatever `params[:stack_id]` names, including stack B. After the divergence, `stack` (stack B) is not a member of `stacks` (which would only contain stack A), breaking the binding.

Exploit: attacker holding a valid `read:stack` API token scoped to stack A issues `GET /api/stacks/:stack_b_id/cc_menu.xml?token=<token>` (or whatever route maps to `CCMenuController#show`). The response renders `shipit/ccmenu/project` with stack B's latest deploy/rollback status, i.e. build/deploy state of a repository the client was never authorized to see.

### Impact Explanation
Any holder of a scoped `read:stack` token can enumerate/read build and deploy status (last deploy/rollback outcome, running state, timestamps) for every stack in the Shipit instance, not just their authorized one. This is a High-severity unauthorized read of stack/deploy state across tenants — the scoping mechanism (`ApiClient.stack_id`) that is supposed to constrain a client to one stack is completely ineffective for this endpoint, and the vulnerability is trivially repeatable against arbitrary stack IDs by simply changing `params[:stack_id]`.

### Likelihood Explanation
Preconditions: attacker must possess any valid `ApiClient` token with `read:stack` permission (even one deliberately scoped to a single stack via `stack_id`). No GitHub secrets, session, or elevated role needed. Cost is a single HTTP GET with a different `stack_id`; fully repeatable and requires no race condition or timing.

### Recommendation
Remove the overriding `stack` method in `CCMenuController` (or change it to use the scoped `stacks` helper): 
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the intended scoping consistent with every other API controller.
