### Title
Webhook Signature Verified Against Attacker's Own Organization While Handlers Act on a Different, Attacker-Chosen Repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a payload against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [2](#0-1) . However, once the HMAC check passes, the actual event handlers resolve the target `Repository`/`Stack` using a completely different field: `payload.dig('repository', 'full_name')` [3](#0-2)  (and similarly in `PushHandler`, `OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.).

### Finding Description
In a multi-tenant Shipit install, `Shipit.github(organization:)` loads a distinct config (including its own `webhook_secret`) per GitHub organization key in `secrets.github` [1](#0-0) . The binding the system relies on is: **organization that authenticated the webhook == organization that owns the repository the handlers act on**. This binding is never enforced.

`verify_signature` fetches `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` is `params.dig('repository', 'owner', 'login')` from the untrusted, attacker-supplied JSON body, then verifies `X-Hub-Signature` against **that org's** `webhook_secret` [4](#0-3) . An attacker who legitimately owns/administers a small, low-privilege GitHub organization/repo that is *also* configured in this same Shipit instance (e.g. a public open-source org with self-service webhook configuration, or any org where the attacker can read/set the webhook secret) can compute a valid HMAC for a payload whose `repository.owner.login` is their own org (so `verify_signature` picks their own org's secret and passes), while setting `repository.full_name` inside the same payload to a **different**, victim repository/stack that lives under another organization managed by the same Shipit deployment.

Because handlers such as `Handler#stacks` [3](#0-2)  and `PushHandler#process` [5](#0-4)  look up the acted-upon `Repository`/`Stack` purely from `full_name`/`ref` without cross-checking it against `repository_owner` (the field used for signature verification), the signature check enforces "this body was signed by *an* org I trust," not "this body concerns a repository owned by the org whose secret validated it."

This is a direct analog to the Cyfrin/Dolomite finding's root cause: a permissionless/less-trusted actor can trigger privileged-looking logic (`getRewardForUser`) whose target (`_user`) is not bound to who is actually authorized to trigger it, causing effects (reward transfer) on a target the caller was never authorized to act upon. Here, the identity used to authorize ("verify") the webhook is decoupled from the identity/target the resulting business logic operates on.

### Impact Explanation
Exploitation lets an attacker who controls a webhook secret for one tenant organization forge webhook events that are processed as valid for a target repository/stack belonging to a *different*, victim organization on the same Shipit instance. Depending on which webhook handler is triggered, this can enqueue `GithubSyncJob` to resync a victim stack against an attacker-chosen `expected_head_sha` (`PushHandler`) [5](#0-4) , forge commit `status`/`check_suite` state for a victim's commits (affecting CI-gated deploy/merge-queue decisions), or archive/unarchive victim review stacks via the `pull_request` label/opened/closed handlers. Forged CI status combined with the merge queue (`ProcessMergeRequestsJob` → `MergeRequest#merge!`) [6](#0-5)  could push a victim stack into merging/deploying based on attacker-controlled status data, i.e., an unauthorized/incorrectly-approved deploy or merge — this matches the "High: unauthenticated read of stack state" / potential "unauthorized deploy or merge" impact bar, contingent on the deployment hosting multiple orgs with independently-controllable webhook secrets.

### Likelihood Explanation
This requires: (1) the Shipit instance configured for multiple GitHub organizations (supported and documented, per `TOP_LEVEL_GH_KEYS`/`github_organizations` and the dummy `secrets_double_github_app.yml` fixture) [7](#0-6) , and (2) the attacker having knowledge of (or the ability to set) the `webhook_secret` for at least one of the configured organizations — plausible for self-service/public orgs where the attacker can register their own GitHub App/webhook with an arbitrary secret they choose. No repository write access, GitHub App private key, or Shipit session/API token is needed — only the ability to POST to the public `/webhooks` endpoint with a body signed by an org's own secret. Likelihood depends heavily on the multi-org deployment model being in use.

### Recommendation
In `WebhooksController#verify_signature`, after resolving `github_app` and verifying the signature, re-derive the organization actually referenced by `params.dig('repository', 'full_name')` (or `organization.login`) and assert it is equal to `repository_owner` before dispatch — i.e. bind the field used to select the verifying secret to the field the handlers subsequently act on, rejecting payloads where they diverge. Alternatively, have handlers resolve the `Repository` scoped to the verified `repository_owner` organization rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls `OrgOne`'s webhook secret (e.g. they set it when registering their own GitHub App/webhook against their own `OrgOne` repo).
3. Attacker crafts a `push` webhook JSON body: `repository.owner.login = "OrgOne"` (so `verify_signature` loads `OrgOne`'s app/secret) but `repository.full_name = "OrgTwo/victim-repo"` and `ref = "refs/heads/production"`, `after = "<attacker-chosen sha>"`.
4. Attacker computes `X-Hub-Signature` HMAC-SHA1 using `OrgOne`'s known secret over the raw body and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` passes (verified against `OrgOne`'s secret) [2](#0-1) ; `PushHandler#process` then resolves stacks via `Repository.from_github_repo_name("OrgTwo/victim-repo")` [3](#0-2)  and enqueues `GithubSyncJob` for the victim's `OrgTwo` stack with an attacker-chosen `expected_head_sha`, despite the attacker never having authenticated as, or received a signed payload from, `OrgTwo`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
