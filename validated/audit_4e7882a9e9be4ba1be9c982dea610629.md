This confirms the critical finding: this is a genuinely severe cross-organization binding break in the multi-tenant GitHub App configuration.

**Root cause chain:**

1. When Shipit is configured with multiple GitHub organizations (as documented and tested via `test/dummy/config/secrets_double_github_app.yml`), each org has its own `webhook_secret`. [1](#0-0) 

2. `WebhooksController#verify_signature` selects *which* secret to verify against based on `repository_owner`, parsed from the attacker-controlled JSON body (`repository.owner.login` or `organization.login`), and verifies the raw body's HMAC against that org's secret: [2](#0-1) 

3. Crucially, `Shipit.github(organization:)` looks up the app config strictly by that string, downcased: [3](#0-2) 

4. Once signature validation passes, `Handler#stacks` / `#repository_name` re-reads the repository identity from a **different** field of the *same attacker-controlled body* — `repository.full_name` — with no cross-check that its owner segment matches the `repository_owner` used for signature verification: [4](#0-3) 

Since an attacker only needs to know/possess the `webhook_secret` for *any one* configured organization (e.g. their own org, which they legitimately administer and can rotate/view in their own GitHub App settings), they can craft a payload where `repository.owner.login` = their org (so it signs/verifies correctly) but `repository.full_name` = `"other-org/other-repo"` (a different tracked repository). The signature check passes because it only binds to the raw bytes and the *claimed* owner, not to the *acted-upon* repository.

**Concrete exploitation via `PushHandler`:** [5](#0-4)  — this calls `stack.sync_github(expected_head_sha:)` for any stack matching `full_name`+`branch`, letting the attacker force-trigger a sync/continuous-deployment cycle for another organization's stack, potentially advancing `continuous_deployment: true` stacks to attacker-chosen states, or via `StatusHandler` [6](#0-5)  injecting fabricated commit statuses (`state: success`) for a targeted commit SHA in another org's repo — which `MergeRequest#reject_unless_mergeable!` / `all_status_checks_passed?` consumes to decide whether required CI checks passed [7](#0-6) , letting the attacker force a merge-queue PR to appear "green" and get auto-merged, or unblock an auto-deploy — an unauthorized deploy/merge crossing repository trust boundaries.

### Title
Webhook signature verification binds to a payload-declared organization while write actions act on an unvalidated `repository.full_name` from the same payload, enabling cross-organization forgery of push/status/pull_request events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects the HMAC secret to check using `repository.owner.login` (or `organization.login`) from the attacker-supplied JSON body, but every webhook `Handler` subsequently resolves the actual repository to act on from `repository.full_name` in that same body, without ever confirming the two agree.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and thus the `webhook_secret`) purely from a string taken out of the unauthenticated request body: [2](#0-1) . `verify_webhook_signature` then just HMACs the raw body against that chosen secret [8](#0-7) . Once verified, event dispatch hands the same parsed body to handlers, all of which derive the tracked `Repository`/`Stack` from `payload.dig('repository', 'full_name')` [4](#0-3) , a field that is never checked against the owner used in step one. Since an attacker who controls (or is a legitimate admin of) any one configured GitHub organization in a multi-org Shipit instance can compute a valid HMAC over an arbitrary body using their own `webhook_secret`, they can set `repository.owner.login` to their own org (to pass verification) while setting `repository.full_name` to `"victim-org/victim-repo"` (to pick the actual target of the write). The equality that should hold — `verified_signing_organization == owning_organization_of(acted_upon_repository)` — is broken.

### Impact Explanation
This crosses a repository-write boundary that the multi-org GitHub App feature is explicitly designed to prevent (`docs/setup.md` states an app "can only authenticate to the Github organization it's installed in"). Concretely: `PushHandler` triggers `sync_github`/`GithubSyncJob` for a victim org's stack [9](#0-8) ; `StatusHandler` injects arbitrary commit statuses for any commit SHA tracked anywhere in the instance, with no repository check at all [10](#0-9) , which feeds directly into `MergeRequest#all_status_checks_passed?`/`reject_unless_mergeable!` gating auto-merge [7](#0-6) ; and `PullRequest::OpenedHandler`/`ReviewStackAdapter` can create/archive/unarchive review stacks for the victim repository [11](#0-10) . This can result in an unauthorized deploy or merge on a repository outside the attacker's own organization — meeting the High/Critical "unauthorized deploy, rollback or merge" bar.

### Likelihood Explanation
Requires only that the instance is configured for multiple GitHub organizations (a documented, supported configuration) and that the attacker controls/has been granted a `webhook_secret` for at least one of them — a materially weaker precondition than repository write access or an `ApiClient` token to the victim's stack. The `StatusHandler` path additionally requires no repository field at all, only a matching commit SHA, making it broadly exploitable across any tracked repo whose commit SHAs are guessable or observable (e.g., open-source victim repos).

### Recommendation
When resolving `stacks`/`repository_name` in `Shipit::Webhooks::Handlers::Handler`, verify that `payload.dig('repository','owner','login')` (the value used to select the signing organization) matches the owner segment of `payload.dig('repository','full_name')` before acting; reject the webhook otherwise. More robustly, thread the verified organization from `WebhooksController` through to each handler and require repositories to belong to that organization.

### Proof of Concept
1. Configure Shipit with two orgs, `AttackerOrg` and `VictimOrg`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls `AttackerOrg`'s GitHub App and knows its `webhook_secret`.
3. Attacker crafts a `push` webhook body: `{"ref": "refs/heads/main", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/victim-repo"}}`.
4. Attacker computes `X-Hub-Signature` as `sha1=` HMAC-SHA1 of the raw body using `AttackerOrg`'s `webhook_secret`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"AttackerOrg"`, fetches `AttackerOrg`'s `GitHubApp`, and the signature check passes.
6. `PushHandler#process` reads `repository.full_name` = `"VictimOrg/victim-repo"`, finds `VictimOrg`'s tracked stacks, and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on them — a write action on a repository outside the attacker's authenticated organization.

      return true unless webhook_secret
