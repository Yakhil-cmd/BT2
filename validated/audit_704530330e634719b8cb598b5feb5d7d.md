### Title
Webhook signature verification keys off `repository.owner.login`, but every handler acts on the unverified `repository.full_name` — allows cross-organization forged webhooks in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App (`Shipit.github_organizations`) deployment, `WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to HMAC-verify the payload against using `repository_owner`, which is read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')`). Every webhook handler, however, resolves the repository/stack to act on using a *different* field of that same body — `payload.dig('repository', 'full_name')`. Because these two fields are never cross-checked against each other, a party who legitimately knows the `webhook_secret` for **one** configured organization can forge a validly-signed webhook whose `repository.owner.login` names their own org (to pass signature verification) while `repository.full_name` names a repository belonging to a **different** configured organization, causing Shipit to act on that other org's stacks.

### Finding Description
`WebhooksController#verify_signature` at [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived purely from the JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (`app_id`, `webhook_secret`, etc.) as documented for multi-org installs [3](#0-2) , a supported and documented configuration [4](#0-3) .

Once the signature check passes, `WebhooksController#create` dispatches the *same raw payload* to handlers: [5](#0-4) 

All handlers derive the target repository from `repository.full_name`, independent of the `repository.owner.login` used above for choosing the signing secret: [6](#0-5) 
This is used, for example, by `PushHandler`, which finds stacks by that repository and triggers a GitHub sync (`stack.sync_github`), which can lead to auto-deploy for continuously-deployed stacks: [7](#0-6) 

The binding that should hold is:
`organization whose secret validated the signature == organization owning the repository/stack acted upon`

but the implementation only checks: `HMAC(raw_body, secret_of(payload.repository.owner.login)) == X-Hub-Signature`, and separately, unconditionally: `act_on(payload.repository.full_name)`. Since `repository.owner.login` and `repository.full_name` are both attacker-controlled JSON fields inside the same signed body, an attacker who can produce *any* validly-signed body (i.e., who legitimately knows one configured org's `webhook_secret`) can set these two fields inconsistently to redirect the acted-upon repository to a different, unrelated organization's repository configured on the same Shipit instance. This is the same "verify one part of the structure, act on another" class of bug described in the reference report (verifying a non-leaf node while treating it as a leaf) — the field that gates cryptographic trust is not the field that is executed on.

### Impact Explanation
On a multi-tenant Shipit instance (the documented "Using Multiple Github Applications" configuration), each configured GitHub organization is meant to be isolated: an org's admin only controls their own app/webhook secret and should only be able to affect their own org's stacks. With this flaw, any org whose webhook secret is known to the attacker (i.e., the org's own GitHub App owner/administrator) can forge webhooks that are processed as if they came from **any other configured organization's repository**, causing:
- Unauthorized `GithubSyncJob` triggers / continuous-deployment pushes for another org's stacks (`PushHandler`) — potentially an unauthorized deploy.
- Forged commit statuses (`status` handler) affecting merge-queue/CI gating for another org's stacks.
- Forged pull-request events (open/close/label) causing review-stack creation/archival/deprovisioning for another org's repositories.
- Forged `membership` events creating/removing `Team`/`Membership` records, which feed into `Shipit.github_teams` authorization used by `User#authorized?` — this is a possible escalation vector into application authorization (High impact per the rules).

This is a cross-organization/cross-repository write triggered without any legitimate access to the target organization's repositories, satisfying the Critical "cross-repository writes"/"unauthorized deploy" bar (and at minimum the High "escalation into `Shipit.github_teams` authorization" bar).

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with more than one GitHub organization (a documented, supported feature, not a misconfiguration), and (2) the attacker to know the `webhook_secret` of at least one of those configured organizations — which they legitimately would, since they administer that org's GitHub App. No access to the victim organization's repository or GitHub App is required. The attacker only needs to POST a crafted JSON body with mismatched `repository.owner.login` vs `repository.full_name` to the shared `/webhooks` endpoint with a signature computed using their own secret. This is straightforward and repeatable, so likelihood is high in any multi-org deployment.

### Recommendation
After signature verification succeeds for organization `O` (chosen via `repository_owner`), re-derive the repository/stack strictly from data scoped to `O`, and reject (422) the webhook if `repository.full_name`'s owner segment does not match `repository_owner` (or, more robustly, don't trust `repository.owner.login` from the body at all — instead verify the payload against *all* configured organizations' secrets and only trust the organization whose secret actually validates, then assert that the resolved repository actually belongs to that same organization before dispatching to handlers).

### Proof of Concept
Assume a Shipit instance configured for two orgs per `docs/setup.md`'s multi-org format: `OrgA` (attacker-administered) and `OrgB` (victim), each with distinct `webhook_secret`s, both with stacks configured in Shipit.

1. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, e.g. a malicious/older commit or one that flips CI>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` using their own known `OrgA` secret.
3. POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`), verifies successfully since the attacker used `OrgA`'s real secret — see [1](#0-0) .
5. `WebhooksController#create` then dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository','full_name')` == `"OrgB/victim-repo"` — see [6](#0-5)  and [8](#0-7)  — triggering `stack.sync_github(expected_head_sha: ...)` for `OrgB`'s stack, despite the request never being signed by `OrgB`.

Note: I was not able to fully trace `app/models/shipit/webhooks.rb` (handler registration/dispatch table) or `membership_handler.rb` contents in this session due to a tool error on the final read attempts, so the membership/team-authorization escalation path is inferred from the test names (`":membership creates the mentioned team on the fly"`) rather than directly verified against the handler's source. If deeper confirmation of that specific handler's behavior is needed, a Devin session with full file access should inspect `app/models/shipit/webhooks/handlers/membership_handler.rb` and `app/models/shipit/webhooks.rb` directly.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
