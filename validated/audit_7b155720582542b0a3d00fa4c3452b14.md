### Title
`is_valid_signed_package` accepts a stale genesis definition when `last_ball_unit` is omitted, letting an evicted co-signer forge authentication for an address whose definition has since changed - ([File: formula/evaluation.js], [File: signed_message.js])

### Summary
`is_valid_signed_package(signed_package, address)` is used by AAs (payment channels, order-book exchanges, etc.) to authenticate an off-chain signed message as coming from a specific address. When the attacker-controlled `signed_package` omits the optional `last_ball_unit` field, evaluation skips the "network aware" branch and calls `signed_message.validateSignedMessage` in non-network-aware mode. In that mode, the only check performed is that the definition supplied in the package hashes to the target address (`chash(definition) === address`) — i.e. the *original, genesis* definition of the address. The code never checks whether the address later changed its definition via `address_definition_change` (e.g. rotating out a co-signer). This is directly analogous to the reported Sequence bug: an optional flag/field (`checkpointer usage` vs. `last_ball_unit`) that, when left unset, causes signature verification to fall back to a stale, unchecked configuration instead of the current one.

### Finding Description
`is_valid_signed_package` in `formula/evaluation.js` only performs MCI/staleness checks on `last_ball_unit` if it is present as a string: [1](#0-0) 
If `signedPackage.last_ball_unit` is absent, this whole block is skipped and `signed_message.validateSignedMessage` is invoked directly: [2](#0-1) 

Inside `validateSignedMessage`, `bNetworkAware` is derived purely from the presence of `last_ball_unit`: [3](#0-2) 

When `bNetworkAware` is false, `validateOrReadDefinition` takes the "else" branch, which requires the caller to supply `objAuthor.definition` and only checks that it hashes to the target address — it does **not** consult `storage.readDefinitionByAddress` (which would return the *current* definition, accounting for any `address_definition_change`): [4](#0-3) 

Compare this to the network-aware branch, which correctly resolves the definition that was active as of `last_ball_unit`'s MCI via `storage.readDefinitionByAddress`: [5](#0-4) 

Because `chash(D0) === address` is a permanent, immutable property of any address (the address literally *is* the chash of its genesis definition D0), any holder of a private key that was part of D0 can always produce a definition/signature pair that satisfies the non-network-aware check — even long after the address has legitimately rotated to a new definition D1 (e.g., removing that very signer) via `address_definition_change`. The validation never queries `address_definition_changes` in this code path, so the "current" configuration is completely bypassed, exactly like the checkpointer being ignored in the Sequence report.

Back in `formula/evaluation.js`, the returned `last_ball_mci` for the non-network-aware case is set to the current evaluation `mci` (or `-1`), which always passes the final check `last_ball_mci > mci` in the caller: [6](#0-5) [2](#0-1) 

### Impact Explanation
AA scripts such as `payment_channels.oscript` and `order_book_exchange.oscript` use `is_valid_signed_package(trigger.data.sentByPeer, $addressA_or_B)` (or `$order1.address`) purely as an authentication check on the *current* ownership/control of an address, to authorize state changes that lead to `payment` messages moving AA-held funds: [7](#0-6) [8](#0-7) 

If address A (a channel/order counterparty) ever rotates its signing key/definition (e.g., because a co-signer key was compromised, a device was lost, or ownership legitimately changed hands), the *old* signer — whose key was part of the original genesis definition — can still forge a `signed_package` with no `last_ball_unit` field and a definition equal to the genesis definition, and `is_valid_signed_package` will report it as valid. This lets the evicted signer claim a stale/favorable `amount_spent`, close a payment channel with fraudulent balances, place forged orders draining another party's AA-tracked balance, or otherwise cause the AA to release funds (`payment` message) to unintended parties — a direct AA fund-loss / unauthorized-spending scenario.

### Likelihood Explanation
This is triggerable purely by an unprivileged AA trigger sender: the attacker (an evicted signer of some address) crafts `trigger.data.sentByPeer` (or similarly-named field) as an ordinary JSON object without a `last_ball_unit` property, includes the genesis `definition` for the target address, signs with the still-known genesis private key, and posts a normal AA trigger unit. No cooperation from the counterparty, no privileged access, and no network/timing race is required — any AA design that relies on `is_valid_signed_package` to authenticate a persistent identity (address) rather than re-verifying the current definition on every call is affected. The bug is a code-level design gap (missing enforcement of `last_ball_unit`/network-aware mode), not a probabilistic race, so likelihood is high whenever an affected AA is deployed and the target address has ever changed its definition.

### Recommendation
- Require `last_ball_unit` (network-aware mode) whenever `is_valid_signed_package` is evaluated inside an AA, so that the definition used for verification is always resolved against the address's current/latest known definition via `storage.readDefinitionByAddress`, not merely checked against the immutable genesis chash.
- Alternatively, in the non-network-aware branch of `signed_message.js`, additionally check `address_definition_changes` for the address and reject if any definition change is recorded (i.e., only allow the genesis-definition shortcut for addresses that have never changed their definition).
- Add an explicit test case mirroring the PoC pattern: create an address, rotate its definition via `address_definition_change`, then verify that a `signed_package` built with the old (genesis) definition and no `last_ball_unit` is rejected by `is_valid_signed_package`.

### Proof of Concept
1. Create address `X` with initial definition `D0 = ["sig", {pubkey: pubA}]`, so `X = chash160(D0)`.
2. Post an `address_definition_change` message from `X` changing its definition to `D1 = ["sig", {pubkey: pubB}]` (evicting `pubA`), and let it become stable.
3. An attacker who still holds the private key for `pubA` crafts:
```
signed_package = {
  signed_message: { channel: <this_address>, period: <var['period']>, amount_spent: <favorable_value> },
  authors: [{
    address: X,
    definition: D0,
    authentifiers: { r: <sig over hash_to_sign using pubA's private key> }
  }]
  // no last_ball_unit field
}
```
4. Attacker posts an AA trigger with `trigger.data.sentByPeer = signed_package` to `payment_channels.oscript` (acting as the counterparty verifying the peer).
5. In `formula/evaluation.js`, `typeof signedPackage.last_ball_unit === 'string'` is false, so the MCI/staleness check block is skipped; `signed_message.validateSignedMessage` is called with `bNetworkAware=false`.
6. `validateOrReadDefinition`'s else-branch confirms `chash(D0) === X` (true, since `X` is defined as the chash of `D0`) and accepts the stale signature from `pubA`, even though `X`'s active definition is now `D1`.
7. `is_valid_signed_package` returns `true`, and the AA accepts the forged `amount_spent`/order data signed by the evicted key, leading to funds being released based on unauthorized data (fund loss/misallocation in the payment channel or order-book contract).
