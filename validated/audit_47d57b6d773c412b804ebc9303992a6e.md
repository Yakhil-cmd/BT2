### Title
Webhook signature verification is keyed to an attacker-controlled organization field that is independent of the repository/team actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The C4 report's root cause is a mismatch between the entity a check is performed *for* (a single low-risk recipient) and the entity the code actually *acts on* (N recipients, unbounded cost). The same class of "authenticated-for X, acted-on Y" mismatch exists in `WebhooksController`: the field used to pick which GitHub App/secret verifies the webhook is not the same field used to decide which repository, team, or user record actually gets created/mutated by the handler that runs afterwards.

### Finding Description
`WebhooksController#verify_signature` selects which configured GitHub App (and therefore which `webhook_secret`) is used to validate the inbound webhook based on a payload-controlled value: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository','owner','login')` or, if absent, `params.dig('organization','login')` — both attacker-supplied JSON fields in the raw POST body, not covered by any signature at the time they are read (the signature is only checked afterward, against whichever secret this field happens to select).

`Shipit.github(organization:)` uses that value to pick the org-specific config in the multi-org schema: [3](#0-2) 

Crucially, `GitHubApp#verify_webhook_signature` no-ops when the selected org has no `webhook_secret` configured: [4](#0-3) 

`webhook_secret` is documented as optional per-organization: [5](#0-4) 

Once `verify_signature` passes, `create` dispatches the *entire raw payload* to handlers with no further constraint tying it back to `repository_owner`: [6](#0-5) 

Handlers resolve the repository/stacks they act on purely from `repository.full_name`, a field completely decoupled from `repository_owner`: [7](#0-6) 

The equality the code implicitly assumes but never enforces is:
`organization_used_for_signature_verification == organization/repository actually written by the handler`

Before the report's analog: any handler action (push→`GithubSyncJob`, `membership`→`Team`/`User` creation, `status`, `pull_request`, etc.) is gated only on whether the *selected* org's secret validates. After: because that selection is payload-controlled and can resolve to an org whose `webhook_secret` is unset (returns `true` unconditionally), the field determining "was this authenticated" and the field determining "what repository/team/user is mutated" can point to two entirely different targets.

### Impact Explanation
If any organization configured on the instance (in the multi-org `secrets.yml` schema) has no `webhook_secret` set — an explicitly documented, supported configuration — an attacker can send a raw, unauthenticated HTTP POST naming that organization in `organization.login`/`repository.owner.login` (satisfying `verify_signature`'s no-op path) while setting `repository.full_name` (and other payload fields like `team`/`member` for the `membership` event) to reference a completely different, security-sensitive organization or team. This lets an unauthenticated party drive handlers such as `Webhooks::Handlers::MembershipHandler`, which creates `Team`/`User` records straight from payload content, potentially feeding into `Shipit.github_teams` OAuth authorization (`lib/shipit.rb`), or trigger `GithubSyncJob` for an arbitrary stack via the push handler. This matches the High-impact criterion "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Likelihood depends entirely on operational configuration: it is only reachable when the multi-org GitHub App schema is used and at least one configured organization has no `webhook_secret` set (a state the documentation explicitly allows and does not warn against as dangerous for *other* organizations' webhook processing). I was not able to fully trace, within the remaining budget, whether `MembershipHandler`'s `Team`/`User` writes alone are sufficient to grant dashboard access without an additional GitHub API confirmation step (the test suite stubs `Shipit.github.api` calls, suggesting some handlers do call back out to GitHub for confirmation) — this should be verified before treating this as a proven Critical/High finding.

### Recommendation
Bind the field used for signature verification to the field(s) later used to select the acted-upon repository/organization/team; e.g., require that `repository.full_name`'s owner matches `repository_owner` (or, better, resolve the owner solely from `repository.owner.login`/`installation.account.login`, not `organization.login`, and reject events where these disagree). Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank in a multi-organization deployment — treat a missing secret for one org as a hard misconfiguration rather than a signature bypass.

### Proof of Concept
```
POST /github/webhooks HTTP/1.1
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "action": "added",
  "organization": { "login": "org-with-no-webhook-secret" },
  "team": { "id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com" },
  "member": { "login": "attacker" },
  "repository": { "owner": { "login": "org-with-no-webhook-secret" }, "full_name": "victim-org/victim-repo" }
}
```
Because `webhook_secret` for `org-with-no-webhook-secret` is unset, `verify_webhook_signature` returns `true` for any signature value, and `MembershipHandler` (app/models/shipit/webhooks/handlers/membership_handler.rb) processes the `team`/`member` fields regardless of which org's secret was checked — demonstrated by the existing test asserting team/user creation purely from payload content: [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
