### Title
Cross-tenant Commit status forgery via unscoped sha lookup in StatusHandler#process - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits globally by `Commit.where(sha: params.sha)` and writes a status to every matching row, without ever resolving or checking `payload['repository']['full_name']` against the owning stack's repository. Every other webhook handler (`PullRequest::OpenedHandler`, `LabeledHandler`, `ClosedHandler`, etc.) resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` first and scopes all mutations to that repository's stacks; `StatusHandler` does not, and the base `Handler#stacks`/`repository_name` helpers are simply unused by this handler.

### Finding Description
The binding that should hold is: `payload['repository']['full_name']` (the repo whose GitHub App/webhook secret validated this specific request via `WebhooksController#verify_signature`, using `Shipit.github(organization: repository_owner)`) `== commit.stack.repository.full_name` (the repository whose Commit row is being mutated). `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only proves that the payload was genuinely sent by GitHub for the organization named in the payload — it says nothing about which stack/commit the handler is allowed to touch. That authorization step is left entirely to each `Handler` subclass.

Every `PullRequest::*` handler enforces it, e.g. `OpenedHandler#repository` (app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54) calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and scopes provisioning to `repository.review_stacks`.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does not:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`params.sha` is a bare 40-hex string with no repository binding. `Commit.where(sha:)` is a global, cross-stack query (the DB only enforces uniqueness of `(sha, stack_id)`, not global uniqueness of `sha`, per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`). `commit.stack` is never compared to any repository derived from the payload.

Exploit flow: git commit SHA-1 is content-addressed, not repository-addressed. If an attacker forks a public victim repository (or otherwise reconstructs an identical commit object — same tree/parent/author/committer/timestamps/message), pushing that commit into `attacker/own-repo` produces the exact same SHA that exists in `victim/private-repo`'s Shipit-synced `Commit` row. The attacker then uses GitHub's real Statuses API (`POST /repos/attacker/own-repo/statuses/:sha`) on their own repo/commit — a completely legitimate, unprivileged action on a repo they own. GitHub relays a real `status` webhook to Shipit, correctly signed for the `attacker` organization; `verify_signature` passes because it only checks that GitHub-attacker's webhook secret matches, not that the target commit belongs to attacker's repo. `StatusHandler#process` then finds the victim's `Commit` row (same sha, different stack) and calls `commit.create_status_from_github!(params)`, writing a `Status`/`CommitStatus` onto the victim's stack's commit — a write for a repository that never authenticated the mutation.

This bypasses `verify_signature` (proves origin, not authorization scope), `drop_unhandled_event` (irrelevant), and the `ExplicitParameters` schema (only validates shape, not repository binding) — none of these guards implement the repository-scoping that `from_github_repo_name` provides elsewhere.

### Impact Explanation
The attacker can inject arbitrary, attacker-controlled CI/status state (`state`, `context`, `description`, `target_url`) onto a commit belonging to a repository/stack they do not own and never authenticated for. `Commit#status` aggregates these statuses and gates `deployable?`/continuous delivery decisions (`app/models/shipit/commit.rb`), so this can be used to mark a victim commit "success" to unblock/trigger a deploy, or "failure" to block deploys — a write for one repository mutating another's stack/commit state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any Shipit-known commit sha the attacker can reproduce (any commit reachable from a public fork, or any commit whose exact object the attacker can reconstruct), and works across any number of victim stacks/tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: the victim repository/stack must already be synced into Shipit (`Repository`/`Commit` rows exist) and the specific commit sha the attacker targets must exist verbatim in a repository the attacker controls (trivial for public repos via forking; not feasible for a private repo whose object content the attacker has never seen, absent leaks or prior public exposure). The attacker needs only: a GitHub account, a repo they own, and standard GitHub API/UI access to set a commit status — no Shipit credentials, no webhook secrets, no team membership. Given the audit's stated precondition (victim repo exists in Shipit), this is a low-cost, fully repeatable attack limited only by the attacker's ability to reproduce/know the target sha.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, matching the pattern used by `PullRequest::*` handlers and `CheckSuiteHandler`:
```ruby
def process
  repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)
  return unless repository

  repository.stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
(or, more efficiently, `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))`), and add `requires :repository { requires :full_name, String }` to the handler's `params` schema so the repository is always present and validated before use.

### Proof of Concept
Add to `test/models/shipit/webhooks/handlers_test.rb` (or a new `status_handler_test.rb`):
```ruby
test "StatusHandler#process does not scope commits to the reporting repository" do
  victim_stack = shipit_stacks(:shipit)  # or create a stack for 'victim/private-repo'
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit', author: shipit_users(:walrus))

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/own-repo' },
  }

  # Prove no repository resolution happens at all
  Shipit::Repository.expects(:from_github_repo_name).never

  assert_difference -> { victim_commit.reload.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_equal 'success', victim_commit.status.state
end
```
This demonstrates that a payload whose `repository.full_name` is `attacker/own-repo` still mutates `victim_stack`'s commit, without `Shipit::Repository.from_github_repo_name` ever being invoked — confirming the missing binding. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
