### Title
Uncaught exception / process crash from `null` values in `trigger.data` reached via AA formula key-selectors - (File: formula/evaluation.js, function `selectSubobject`)

### Summary
The `TensorListScatter` advisory is a class of bug where an op accepts attacker-supplied data whose "shape"/type is outside the range the internal code implicitly assumes, and the resulting mismatch trips a low-level assertion (`CHECK`) that aborts the whole process instead of being handled as a normal error. `ocore`'s oscript/AA formula evaluator has an analogous gap: `selectSubobject()` in `formula/evaluation.js` walks into nested values coming straight from an untrusted unit's message/trigger data, and its type-narrowing logic treats `typeof value === 'object'` as proof that `value` is a "real" object, without excluding `value === null`. A single unprivileged unit poster (an AA trigger sender) can place a JSON `null` at a data path that is later indexed with a key-selector in an AA's oscript, causing the evaluator to try to read a property of `null`. Because ocore installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the daemon (`network.js`), any exception that escapes the async evaluation chain unhandled brings down the whole node, exactly like the TF `CHECK` fail causing a DoS.

### Finding Description
`selectSubobject(value, arrKeys, arr, cb)` in `formula/evaluation.js` (~lines 2908-2946) walks a chain of selector keys into a JSON value taken from AA trigger/state data:

```
function selectSubobject(value, arrKeys, arr, cb) {
    ...
    async.eachSeries(
        arrKeys || [],
        function (key, cb2) {
            if (typeof value !== 'object' || Decimal.isDecimal(value))
                return cb2('not an object while trying to access key ' + JSON.stringify(key));
            ...
            evaluate(key, function (evaluated_key) {
                ...
                if (!hasOwnProperty(value, evaluated_key) || Decimal.isDecimal(value))
                    return cb2("no such key in data");
                value = value[evaluated_key];
                cb2();
            });
        },
        ...
``` [1](#0-0) 

The guard `typeof value !== 'object'` is intended to reject "not an object" values before indexing into them, but in JavaScript `typeof null === 'object'`, so a JSON `null` embedded anywhere in the AA trigger's `data` (fully attacker-controlled, e.g. as `data.a = null` and then oscript expression `trigger.data.a.b`) passes this guard unmodified. Execution then falls through to `hasOwnProperty(value, evaluated_key)`/`value[evaluated_key]` with `value === null`, which throws a `TypeError` ("Cannot convert undefined or null to object" / "Cannot read properties of null") deep inside an `async.eachSeries` callback that is not wrapped in any `try/catch` at that layer.

This mirrors the reported bug class precisely: an operation (`selectSubobject`, the oscript "read key from object" primitive) makes an implicit assumption about the shape/type of attacker-supplied data (that `typeof x === 'object'` means "indexable, non-null object"), and when that assumption is violated it does not fail gracefully with a validation error — it throws an unguarded exception.

The formula evaluator is invoked from AA trigger handling (`aa_composer.js`, `formulaParser.evaluate`/`formula/evaluation.js` `exports.evaluate`), which is reached whenever any address sends a payment/message to an AA (an unprivileged, single-unit action). If the thrown `TypeError` is not intercepted anywhere along that call path, it becomes an "uncaught exception" at the process level, and `network.js` installs:

```
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [2](#0-1) 

which intentionally re-throws to kill the whole node process. This is the same end effect as the reported `CHECK`-fail DoS: an unprivileged sender can crash the full node just by posting a well-formed unit whose message data contains a `null` at the right nesting level and an AA whose oscript indexes into that path.

### Impact Explanation
Any account can trigger an AA by sending it a payment/message with a crafted `data` object containing `null` at a location the target AA's oscript subsequently indexes with a bracket/dot selector (`data.foo.bar`, `data['foo']['bar']`, etc.). If the AA's logic is public (most are, since AAs are permissionless smart-contract-like units on the DAG) and contains such a data access pattern, or if the attacker deploys their own AA specifically to hit this path (any user can define and trigger any AA, including one they wrote themselves), the AA execution — happening on every full node processing the unit — throws an unguarded `TypeError`. Because ocore's global uncaught-exception handler is written to deliberately re-throw and crash the process, this results in denial of service: the node crashes while validating/executing a legitimately-formed unit, and every honest full node that processes the same unit crashes in the same way, i.e. the network is unable to confirm new units built on top of / referencing that trigger until node operators intervene. This satisfies the "network unable to confirm new units" / node-crash-DoS bar required by the validation rules.

### Likelihood Explanation
The trigger is entirely attacker-controlled and requires no privileged role: any address can post a `data` payment/message to an AA (self-authored or third-party) with a `null` at a chosen JSON path, and no special network position, leaked keys, or malicious-peer/hub cooperation is needed. The only precondition is that some AA's oscript performs a selector-based read into that attacker-influenced data path, which is a common and idiomatic operation in AA definitions (e.g., `trigger.data.foo.bar`, `var[...]`, `params.abc[...]` all funnel into `selectSubobject`). Given AAs are deployed permissionlessly, an attacker can also write and instantiate their own minimal AA specifically shaped to hit this code path and then send it a trigger with the crafted `null`, making exploitation self-contained and fully reproducible without needing an existing vulnerable third-party AA.

### Recommendation
In `selectSubobject` (`formula/evaluation.js`), tighten the "must be an indexable object" guard to explicitly exclude `null`:
```
if (typeof value !== 'object' || value === null || Decimal.isDecimal(value))
    return cb2('not an object while trying to access key ' + JSON.stringify(key));
```
Audit all other places in `formula/evaluation.js` and `formula/validation.js` that use `typeof x === 'object'` (or `!== 'object'`) as a proxy for "safe to treat as object/array" without excluding `null`, since the same pattern can recur elsewhere (e.g. `concat`, `assignField`, dictionary/array literal handling). Additionally, wrap AA formula evaluation call sites in a defensive `try/catch` (or make `evaluate`/`selectSubobject` resilient against any thrown `TypeError`) so that unexpected type errors inside oscript evaluation are converted into a normal `fatal_error`/validation failure (AA bounce) rather than propagating to an uncaught exception that triggers the process-crashing handler in `network.js`.

### Proof of Concept
1. Deploy (or use an existing) AA whose oscript reads a nested field from `trigger.data`, e.g.:
```
{
  messages: {
    cases: [
      {
        if: "{ trigger.data.a.b }",
        messages: [ ... ]
      }
    ]
  }
}
```
2. Send a payment/trigger unit to this AA with:
```json
{ "data": { "a": null } }
```
3. When the AA is triggered, `evaluate` for `trigger.data.a.b` calls `selectSubobject` with `value = null` after resolving `data.a`; the guard `typeof value !== 'object'` is false for `null`, so execution proceeds to index into `null`, throwing an uncaught `TypeError`.
4. Because this exception is not caught anywhere in the async chain, it escapes to the process level; `network.js`'s `process.on('uncaughtException', ...)` handler logs it and re-throws, crashing the full node that processed the unit — reproducing on every honest node that validates/executes the same AA trigger.
