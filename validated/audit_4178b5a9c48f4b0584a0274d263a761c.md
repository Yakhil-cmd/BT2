Confirmed: `Shipit.github(organization:)` requires the org to be one of the operator's explicitly configured entries under `secrets.github` (each with its own `webhook_secret`); an org not present raises `GithubOrganizationUnknown` and the request is rejected with 422 [1](#0-0) [2](#0-1) . So a signed webhook can only be genuinely produced by an admin of one of the **already Shipit-configured** GitHub organizations, using that organization's own `webhook_secret` — not by an arbitrary internet attacker with no relationship to any configured org, and not by forging a different organization's identity.

### Title
Cross-organization Team membership forgery via unchecked `team.id` binding in `MembershipHandler#process` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up an existing `Team` purely by the numeric `params.team.id` (GitHub's team ID) supplied in the webhook JSON body, without verifying that this `team.id`, or the `organization.login` in the same payload, actually belongs to the organization whose signature was verified for the request (`repository_owner`, checked only against `Shipit.github(organization: repository_owner)`'s secret). An admin of any organization that Shipit has legitimately onboarded (i.e. has its own configured `webhook_secret`) can therefore emit a genuinely-signed `membership` event for **their own** org, but set `team.id` to the `github_id` of a `Team` row that actually belongs to a *different*, unrelated organization, and `member.login` to any arbitrary GitHub username, causing that user to be enrolled as a member of the target team.

### Finding Description
The broken binding: `params.team.id (verified only via signature of repository_owner) == Team#github_id (the actual GitHub team owned by a possibly different organization)` — these are never checked for equality/consistency against `repository_owner`/`organization.login`.

Path: `WebhooksController#verify_signature` validates the HMAC signature using the secret configured for `repository_owner` (the `organization.login` from the payload) [2](#0-1) , then dispatches to `MembershipHandler#process`, which does:
```
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member) if action == 'added'
``` [3](#0-2) 

`find_or_create_team!` is `Team.find_or_create_by!(github_id: params.team.id)` — it only sets `team.organization` from the payload's `organization.login` inside the `create` block, which only runs when no `Team` with that `github_id` already exists [4](#0-3) . If a `Team` row with that `github_id` already exists (created previously by the real target organization's genuine webhook), the lookup returns that pre-existing row regardless of what `organization.login` is asserted in the current, differently-signed payload. Downstream, `User#authorized?` grants access purely via `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) , with no re-check against GitHub — it trusts the local `Membership` row unconditionally.

Existing guards do not stop this: `verify_signature` only proves the payload came from *an* org with a valid secret, not that the payload's *content* (team id, org login) is consistent with that org [6](#0-5) ; `ExplicitParameters` schema only checks types/presence, not cross-field/ownership consistency [7](#0-6) .

Attacker requirement: they must be an admin/owner of some organization that Shipit already trusts (has a configured `webhook_secret`) — this is a real but non-trivial precondition; a completely uninvolved internet user with zero relationship to any configured org cannot produce a valid signature at all, since `Shipit.github(organization:)` raises `GithubOrganizationUnknown` for unconfigured orgs.

### Impact Explanation
If exploited by an admin of one legitimately-configured-but-otherwise-untrusted organization, they can inject arbitrary GitHub logins into `Membership` rows for a `Team` belonging to a completely different organization whose `github_id` matches Shipit's `Shipit.github_teams` — directly escalating those logins' `User#authorized?` status and granting them full access to stacks, deploys, and rollbacks across the whole Shipit installation, regardless of tenant/org boundaries. This matches the "High: escalation into `Shipit.github_teams` authorization" category. It is repeatable per login with no rate limiting in the handler itself.

### Likelihood Explanation
Requires the attacker to already control (own/administer) at least one organization onboarded into Shipit's multi-org `secrets.github` configuration with its own `webhook_secret` — this is not available to a fully anonymous internet actor with zero relationship to the Shipit deployment, but is plausible in any multi-tenant Shipit deployment serving multiple independent GitHub organizations, where one org's admin is otherwise meant to be isolated from another org's teams. The attacker also needs to know/guess the numeric `github_id` of the target `Team` (visible via GitHub's public team APIs/UI if team visibility allows, or via prior Shipit interactions). Given those preconditions, exploitation cost is a single crafted, self-signed HTTP POST per victim login, fully repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`/`#process`, cross-check that `params.organization.login` (verified as `repository_owner`) matches the `organization` column of the resolved `Team`, rejecting (or refusing to mutate membership on) any `Team` whose stored `organization` differs from the authenticated organization of the current webhook, rather than trusting `team.id` alone across organizational boundaries.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub, per repo scope caveat that `test/**` is out-of-scope for grading but is the reproduction vehicle to demonstrate the flaw):
1. Fixture setup: two orgs configured in test secrets, `org_a` (attacker-controlled, own `webhook_secret_a`) and `org_b` (target org owning `shipit_teams(:shopify_developers)`, `github_id: X`, `organization: "org_b"`).
2. Stub `Shipit.github(organization: 'org_a').verify_webhook_signature` to return `true` (simulating a genuinely signed payload from `org_a`).
3. POST a `membership` event payload: `{ action: 'added', team: { id: X, name: 'Developers', slug: 'developers', url: '...' }, organization: { login: 'org_a' }, member: { login: 'evil_login' }, repository: { owner: { login: 'org_a' } } }`.
4. Assert: `Team.find_by(github_id: X)` (== target `shopify_developers`) now has `evil_login` as a member — `Membership.exists?(team: shipit_teams(:shopify_developers), user: User.find_by(login: 'evil_login'))` is `true`.
5. Assert `User.find_by(login: 'evil_login').authorized?` is now `true` when `Shipit.github_teams` includes `shopify_developers`, despite `evil_login` never having a real relationship to `org_b`'s GitHub team.
6. Compare both sides of the binding explicitly: `params.organization.login ("org_a") != Team#organization ("org_b")` while the membership write still succeeds — proving the equality check is missing.
