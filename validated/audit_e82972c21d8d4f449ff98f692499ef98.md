### Title
Cross-organization team-membership escalation via unbound `team.id` lookup in `MembershipHandler` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves a `Team` purely by the attacker-supplied numeric `params.team.id`, while `WebhooksController#verify_signature` selects *which* organization's HMAC secret to check against using the equally attacker-supplied `params['organization']['login']` (or `repository.owner.login`). Nothing ties the organization whose secret validated the request to the organization that actually owns the numeric team id being mutated, so a webhook correctly signed for organization B can add a member to a `Team` record that belongs to organization A.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`organization_used_for_signature_verification (params.dig('organization','login'))` **must equal** `team.organization` **of the `Team` row identified by `params.team.id`** — but the code never checks this.

Path:
1. `WebhooksController#verify_signature` picks the GitHub App/secret to verify against solely from the JSON body: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')`, then `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) 
2. `MembershipHandler`'s `params do ... end` block only type-checks `team.id`/`team.name`/`team.slug`/`team.url`, `organization.login`, and `member.login` (all `Integer`/`String`), with no provenance check. [2](#0-1) 
3. `find_or_create_team!` looks the `Team` up **exclusively by `github_id: params.team.id`**, a global GitHub numeric identifier that is unrelated to which org's secret signed the request: [3](#0-2) 
If a `Team` row for that `github_id` already exists (which it does for every team referenced in `Shipit.github_teams`, since those are pre-created via `Team.find_or_create_by_handle`/`fetch_and_create_from_github` at boot), `find_or_create_by!` returns the *existing* record and the block (which would set `team.organization`) never runs — the forged `organization.login` in the payload is silently discarded for existing teams. [4](#0-3) [5](#0-4) 
4. `process` then unconditionally calls `team.add_member(member)` for `action == 'added'`, appending the attacker-chosen `member.login` (resolved/created via `User.find_or_create_by_login!`) to that team's `members` association — with no check that the org which signed the webhook is the org that owns the team. [6](#0-5) [7](#0-6) 
5. Authorization (`User#authorized?`) is gated purely on Shipit-internal `Team#id`/membership, so any account added to the members of one of the teams listed in `Shipit.github_teams` becomes authorized application-wide: [8](#0-7) 

Exploit flow (in a multi-organization Shipit deployment, which this engine explicitly supports — see `config/secrets.development.shopify.yml` and `TOP_LEVEL_GH_KEYS`/`GithubOrganizationUnknown` handling, i.e. each org has its own independent `webhook_secret`):
- Attacker legitimately controls/administers organization **B**, which is also onboarded to the same shared Shipit instance (so events from B are genuinely signed with B's real, attacker-known-or-triggerable webhook secret).
- Attacker knows the real numeric GitHub team id `X` of a privileged team belonging to target organization **A** (premise granted by the question).
- Attacker sends (or triggers, via a real membership event in their own org B that they then relay/modify before it reaches the wire — or, since GitHub signs exactly the raw body, they can only get a *genuinely* GitHub-signed payload for events that truly occurred in B; the more direct route is any case where B's `webhook_secret` is otherwise available to them, e.g., because they administer B's GitHub App settings) a `membership` webhook body:
  `{"action":"added","team":{"id": X, "name":"anything","slug":"anything","url":"anything"},"organization":{"login":"B"},"member":{"login":"attacker"}}`, signed with **B**'s secret, with `X-Github-Event: membership`.
- `verify_signature` resolves `repository_owner = "B"`, loads B's `GitHubApp`, and the signature checks out — the request is accepted.
- `find_or_create_team!` looks up `Team` by `github_id: X`, finds A's pre-existing privileged `Team` row, and `team.add_member(attacker)` adds the attacker to A's real team.
- Attacker is now a member of a team counted in `Shipit.github_teams`, and `User#authorized?` returns true for them application-wide, bypassing the entire access-control model — an authorization bypass.

Why existing guards fail: `verify_signature` only proves the *event came from some registered organization*, it does not, and structurally cannot, prove that the *team referenced inside the payload* belongs to that same organization, because the two lookups (`repository_owner` for signing, `team.id` for the record) use disjoint, independently attacker-controlled fields. `ExplicitParameters`' `requires` only enforces types, not cross-field provenance. No other guard (`drop_unhandled_event`, `force_github_authentication`, `Repository`/`Stack` validators) participates in this path since `Team`/`Membership` records have no repository/stack scoping validation at all.

### Impact Explanation
An attacker who legitimately controls (or can produce genuinely-signed webhook traffic for) any single organization onboarded to a shared multi-org Shipit instance can add arbitrary GitHub logins as members of a *different* organization's privileged `Shipit::Team`, as long as they know that team's numeric GitHub id. Since `Shipit.github_teams` membership is the sole authorization gate (`User#authorized?`), this is escalation into `Shipit.github_teams` authorization — matching the "High" impact category explicitly listed in the rules ("escalation into `Shipit.github_teams` authorization"). It is repeatable against any team id and any target login, and blast radius spans every tenant organization sharing the Shipit instance.

### Likelihood Explanation
Requires: (a) a multi-organization Shipit deployment (explicitly supported/documented configuration), (b) the attacker legitimately operating or able to produce genuinely-signed webhook deliveries for at least one onboarded organization, and (c) knowledge of the target's privileged team's numeric GitHub id (granted by the question's premise via public org team listing). No Shipit secrets, sessions, or API tokens are required beyond the attacker's own organization's legitimately-obtained signing capability. Cost is low and the request is trivially repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `repository_owner`/organization used to authenticate the current webhook (e.g., pass the verified organization into the handler and assert `team.organization == verified_organization` before calling `add_member`/`find_or_create_by!`), and additionally scope the `github_id` lookup by organization instead of using it as a global unscoped key. Reject the event (or create only, never mutate an existing cross-org record) when the payload's organization does not match the team's stored `organization`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub calls, mirrors existing helpers like `membership_params`/`payload`):
```ruby
test ":membership from org B cannot add a member to org A's team by forging team.id" do
  team_a = shipit_teams(:shopify_developers) # belongs to organization "shopify", pre-existing github_id
  refute team_a.members.include?(shipit_users(:bob))

  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    stub(verify_webhook_signature: true) # simulates a genuinely-signed request for attacker's own org "attacker-org"
  )

  request.headers['X-Github-Event'] = 'membership'
  forged_payload = {
    action: 'added',
    team: { id: team_a.github_id, name: 'forged', slug: 'forged', url: 'https://example.com/forged' },
    organization: { login: 'attacker-org' },
    member: { login: 'bob' }
  }

  assert_no_difference -> { Team.count } do
    post :create, body: forged_payload.to_json, as: :json
  end

  team_a.reload
  # Binding check: the org that signed ("attacker-org") must equal team_a.organization for add_member to be legitimate.
  refute_equal 'attacker-org', team_a.organization
  assert_includes team_a.members, shipit_users(:bob) # demonstrates the escalation: bob added despite mismatch
  assert shipit_users(:bob).authorized? # now bypasses Shipit.github_teams gate
end
```
This asserts both sides of the binding explicitly (`'attacker-org' != team_a.organization`) while showing `team.add_member` still executed and granted authorization, proving the provenance check is missing.
