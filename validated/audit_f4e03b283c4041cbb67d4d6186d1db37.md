### Title
Unbounded private-payment chain length/count causes excessive memory usage during processing - (File: wallet.js)

### Summary
`wallet.js:handlePrivatePaymentChains()` accepts a `chains` array from an arbitrary paired device (correspondent) over the hub and only validates each element's *shape*, never the number of chains nor the length of an individual chain, before doing expensive per-element JSON hashing, DB-backed validation, and repeated `_.cloneDeep`/`JSON.stringify` work down the whole chain.

### Finding Description
`handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0)  only checks that `arrChains` is a non-empty array and that each chain element is a non-empty object with the expected fields — there is no cap on `arrChains.length` or on the length of any individual chain `c`. This function is reachable by any correspondent device via `handleMessageFromHub`, i.e. an unprivileged paired device (anyone who has previously paired or a hub-relayed peer) can post the payload.

Each chain is processed with `async.eachSeries`, and for every chain, `network.handleOnlinePrivatePayment` is invoked [2](#0-1) . This in turn calls `privatePayment.validateAndSavePrivatePaymentChain` which walks the whole chain with `async.forEachOfSeries`, invoking `validatePrivatePayment` on every element [3](#0-2) . Each element triggers a DB round trip, a `JSON.stringify` for logging [4](#0-3) , and `_.cloneDeep(payload)` [5](#0-4) . On the light-wallet path (`conf.bLight`), the whole chain is additionally persisted as one JSON blob via `JSON.stringify(arrPrivateElements)` into `unhandled_private_payments` [6](#0-5)  and later re-parsed with `JSON.parse(row.json)` for every retry of `handleSavedPrivatePayments` [7](#0-6) , and `updateLinkProofsOfPrivateChain` is invoked whenever `arrPrivateElements.length > 1`, walking and validating the chain again.

Unlike unit-level anti-spam limits enforced in `validation.js` (e.g. `MAX_MESSAGES_PER_UNIT`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`, `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` in `constants.js` [8](#0-7) ), which bound processing cost of any single unit, `handlePrivatePaymentChains` has no analogous `MAX_CHAINS` or `MAX_CHAIN_LENGTH` constant, so both the number of chains in one hub message and the length of each chain are attacker-controlled and unbounded, mirroring the dovecot pattern where an attacker crafts a message with an unbounded number of structurally valid sub-elements that is accepted for later processing and only blows up memory/CPU during that later per-element pass.

### Impact Explanation
A malicious paired device (or any actor able to relay `private_payment_chains` through the hub) can submit a payload with a very large number of chains, or a single chain with a very large number of hops, each individually well-formed. Because the recipient wallet accepts the message and then processes every element (DB queries, JSON stringify/clone, and — for light wallets — repeated `JSON.stringify`/`JSON.parse` persistence and reprocessing on every retry), this can drive a sustained, attacker-controlled memory/CPU cost on the victim's wallet process, potentially exhausting memory and crashing the wallet (denial of service against the recipient), consistent with a resource-exhaustion vulnerability of Medium/High severity in the "wallet and contract message handling" category named in scope.

### Likelihood Explanation
Likelihood is High for any wallet that accepts private payments from arbitrary correspondents/hub-relayed peers, since no authentication beyond being a paired device (or hub relay) is required to reach `handlePrivatePaymentChains`, and constructing an arbitrarily long, well-formed chain of dummy transfer/issue elements requires no special privilege — the attacker only needs valid-looking objects satisfying the shallow shape check in the `arrChains.every(...)` guard.

### Recommendation
Add explicit bounds analogous to the unit-level anti-spam constants: cap `arrChains.length` and the length of each individual chain (e.g. `MAX_PRIVATE_CHAINS_PER_MESSAGE`, `MAX_PRIVATE_CHAIN_LENGTH`) in `handlePrivatePaymentChains` (and in `network.handleOnlinePrivatePayment`/`updateLinkProofsOfPrivateChain`) before doing any expensive parsing, cloning, or DB work, rejecting oversized payloads immediately.

### Proof of Concept
Not runnable in this analysis-only context; based on static review of `wallet.js:handlePrivatePaymentChains` (lines 955-1079), `network.js:handleOnlinePrivatePayment`/`handleSavedPrivatePayments` (lines 2375-2521), and `indivisible_asset.js:parsePrivatePaymentChain`/`validatePrivatePayment` (lines 187-235, 20-183), a correspondent could send a `private_payment_chains` hub message with `body.chains` containing thousands of chains, or a single chain with thousands of synthetic transfer hops (each referencing a plausible but fabricated prior unit/message/output index), to force the recipient to perform a proportionally large amount of cloning, hashing, and JSON (de)serialization work per received message.
