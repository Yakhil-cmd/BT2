### Title
ERC20Transactor credits/debits the fixed XCM-requested `amount` instead of the checking account's actual balance delta, causing accounting desync for non-standard (fee-on-transfer/deflationary) ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` (the XCM `TransactAsset` implementation that lets `pallet-xcm` move ERC20 tokens deployed on `pallet-revive`) trusts the boolean return value of the ERC20 `transfer` call and always books the exact instruction-supplied `amount` into `AssetsInHolding`/out of the shared checking account, rather than measuring the actual balance change of the checking account before/after the call. This is the exact bug class from the report: any ERC20 whose `transfer` moves less (or more) than `value` — the canonical case being a fee-on-transfer/deflationary token — desynchronizes the XCM executor's internal ledger from the real on-chain ERC20 balance of the shared `TransfersCheckingAccount`.

### Finding Description
`withdraw_asset_with_surplus` withdraws tokens by calling `IERC20::transfer(checking_account, amount)` from the user, and — as long as the call doesn't revert and decodes to `true` — unconditionally mints an `AssetsInHolding` credit of the full requested `amount`: [1](#0-0) 

Symmetrically, `deposit_asset_with_surplus` deposits by calling `IERC20::transfer(beneficiary, amount)` *from the shared checking account*, again trusting the boolean return value with no before/after balance verification of either the checking account or the beneficiary: [2](#0-1) 

Neither function ever reads `IERC20.balanceOf` before and after the transfer to determine the *actual* delta, unlike the recommended fix in the report (`balanceBefore`/`balanceAfter` diff). The `amount` variable used to build/consume the `Erc20Credit` imbalance always equals the value requested in the XCM `Asset`, not the real balance movement: [3](#0-2) 

The `TransfersCheckingAccount` is a single, persistent, shared account across every `withdraw`/`deposit` XCM operation for ERC20 assets on the chain (e.g. `ERC20TransfersCheckingAccount` wired into Asset Hub Westend's `xcm_config.rs`, as referenced by the test suite in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1876-1877`). Because the checking account's *real* ERC20 balance is only ever fed by `withdraw_asset_with_surplus` (crediting `AssetsInHolding` for the full nominal `amount` while the real balance received may be less, for a fee-on-transfer token) and only ever drained by `deposit_asset_with_surplus` (removing the full nominal `amount` from the real balance), the checking account's real balance will progressively fall behind the XCM ledger's bookkeeping whenever a fee-on-transfer/deflationary ERC20 asset is used. This is a direct analog of the reported `AaveV3YieldSource._depositAmount` bug: the code assumes the ERC20's `transfer`/`transferFrom` moves exactly the nominal `value`, instead of measuring the checking account's actual balance delta.

Any unprivileged user can reach this: they only need to deploy their own ERC20 contract (or use an existing fee-on-transfer token) on `pallet-revive` and reference it as `AccountKey20` in a self-executed XCM program via `pallet_xcm::execute`, exactly as demonstrated by the existing test `withdraw_and_deposit_erc20s`: [4](#0-3) 

### Impact Explanation
Because the shared `TransfersCheckingAccount` accumulates real-token deficits whenever a fee-on-transfer ERC20 asset is moved through XCM, its actual on-chain ERC20 balance can fall below what `AssetsInHolding` implicitly promised was backed. This can manifest as:
- Trapped/failed deposits for legitimate holders of the same token once the checking account's real balance is insufficient to satisfy a later `deposit_asset_with_surplus` transfer of the full nominal amount (denial of service / stuck funds for the *deposit* leg, matching an `AssetTrap`).
- Under specific sequencing (e.g. multiple users' withdrawals of the same fee-on-transfer token accumulating real balance in the checking account before any deposit fully drains it), a user's deposit call can successfully pull out more real tokens from the checking account than that user's own withdrawal actually contributed, at the expense of other users' contributed balance of the same asset — the "protocol leakage" pattern described in the report, not a total-funds-loss bug.

This is bounded to leakage/denial-of-service on ERC20-asset XCM transfers specific to non-standard-transfer-semantics tokens; it does not directly mint or steal native DOT/system-asset balances, and the affected surface (`assets-common::erc20_transactor`, wired only into `asset-hub-westend`'s ERC20 XCM support) is a comparatively narrow, newly-introduced feature.

### Likelihood Explanation
Likelihood is limited by adoption: the vulnerability is only triggered when a fee-on-transfer/deflationary/rebasing ERC20 is referenced through the ERC20Transactor, and today's runtime only wires this transactor on Asset Hub Westend. Any user, without privilege, can deploy such a contract via `pallet-revive` and invoke `pallet_xcm::execute`/`transfer_assets` themselves, so reachability is straightforward; the main constraint is that the impact requires either shared-checking-account state built up by prior legitimate transfers of the same token, or acceptance of the DoS/trapped-asset outcome, both of which are readily demonstrable in a local integration test using the existing `withdraw_and_deposit_erc20s` test harness with a custom fee-on-transfer ERC20 fixture instead of the standard `MyToken` fixture.

### Recommendation
Mirror the report's recommended fix inside `ERC20Transactor`:
- In `withdraw_asset_with_surplus`, read `balanceOf(checking_account)` before and after the `transfer` call and credit `AssetsInHolding` with the *actual* delta, not the nominal `amount`.
- In `deposit_asset_with_surplus`, read `balanceOf(beneficiary)` before and after the `transfer` call and only consider the operation successful (releasing the corresponding `AssetsInHolding` credit) for the *actual* delta received; if less than the nominal `amount` was moved, keep the shortfall in holding (return it as unspent) rather than reducing checking-account state by more than what was actually taken.
- Alternatively, explicitly restrict `Matcher`/documentation to standard-transfer (non-fee-charging) ERC20 tokens and defensively reject tokens whose `transfer` doesn't move the exact requested amount, failing the XCM instruction rather than silently desynchronizing accounting.

### Proof of Concept
Not executed. A concrete reproduction would extend the existing `withdraw_and_deposit_erc20s` test in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1935`, replacing the `MyToken` fixture with a custom Solidity ERC20 fixture whose `transfer` burns/withholds a fixed percentage of `value` (a standard fee-on-transfer implementation), then asserting: (1) `AssetsInHolding`/beneficiary balance shows the full nominal `erc20_transfer_amount` was deposited while (2) `IERC20.balanceOf(checking_account)` shows a lower real balance than what the ledger implies, and (3) a subsequent legitimate user's `deposit_asset` of the same token can be starved or over-drained relative to their own contribution. This PoC was not run against the actual code in this session — the analysis is based on static tracing of `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` and the shared `TransfersCheckingAccount` wiring; running the integration test with a crafted fixture is the recommended next step to confirm the exact failure/leak sequence and quantify attacker-achievable leakage versus mere denial of service.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))
	}
}

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
