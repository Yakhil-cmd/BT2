### Title
DoS via unbounded accumulation of dust outputs at an AA address can permanently block the AA's ability to spend/lock its balance - ([File: aa_composer.js])

### Summary
An attacker can flood an Autonomous Agent (AA) address with a large number of minimally-accepted payment outputs (just above the dust-filter threshold). When the AA later needs to send a response payment (e.g. returning change, paying out a claim, or moving locked capital), `aa_composer.js`'s `completePaymentPayload`/`iterateUnspentOutputs` reads and iterates **all** matching unspent outputs for the AA's address with no cap on the number of rows consumed while accumulating `target_amount`. If enough dust outputs exist, the number of inputs required to reach the target amount can exceed `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, causing the composed unit to fail `validation.js`'s input-count check, which bounces the AA response. Because the dust outputs are never spent (the response bounced), they remain in the unspent set forever, and the attacker can keep adding more, permanently preventing the AA from producing a valid spending unit.

### Finding Description
`sendUnit()` → `completePaymentPayload()` in `aa_composer.js` builds an AA's outgoing payment by pulling rows from the database with `readStableOutputs()`/`readUnstableOutputsSentByAAs()` and feeding them one-by-one into `iterateUnspentOutputs()`: [1](#0-0) 

The SQL queries backing these functions have no `LIMIT`, and there is no check inside the accumulation loop that stops once the number of inputs is about to exceed the protocol's per-message input limit: [2](#0-1) 

The code already acknowledges a dust-attack risk for very small (net-negative) outputs and filters those out with a fixed size threshold (`FULL_TRANSFER_INPUT_SIZE`): [3](#0-2) 

…but this filter only guards against negative-value dust; it does **not** bound the *count* of outputs an attacker can create that are each individually just above the threshold. Any user can freely send many small payments to the AA (a `payment` message app is unprivileged and requires no special authorization), each adding one row to the `outputs` table for that address.

`validation.js` enforces a hard cap on the number of inputs allowed in a single payment message, `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (confirmed present in `constants.js`, `inputs.js`, and `validation.js`). Because `iterateUnspentOutputs()` in `aa_composer.js` does not stop consuming outputs before this limit is reached (unlike `pickIndivisibleCoinsForAmount()` in `indivisible_asset.js`, which does explicitly check `arrPayloadsWithProofs.length >= constants.MAX_MESSAGES_PER_UNIT - 1`): [4](#0-3) 

…an AA whose balance is composed of enough small outputs will build a `payload.inputs` array that exceeds the protocol limit. The resulting unit then fails validation when `validateAndSaveUnit` is called: [5](#0-4) 

causing the whole response to `bounce(err)`. Since the response bounced, none of the dust outputs get spent (`is_spent` stays 0), so on every subsequent trigger the same (and growing) pile of dust outputs is read again, permanently reproducing the failure. This mirrors the reported bug class: an unbounded, attacker-growable array iterated on a critical spending/locking path leads to a hard failure that blocks legitimate fund movement.

### Impact Explanation
If an AA's normal operation requires it to spend/send back bytes or an asset (e.g., returning locked collateral, refunding a failed claim, or paying interest), an attacker can permanently prevent this by pre-flooding the AA address with many small payments. This is a fund-freezing DoS: capital held by the AA becomes unspendable because every attempt to construct an outgoing payment overflows `MAX_INPUTS_PER_PAYMENT_MESSAGE` and bounces. Any AA that pays counterparties from its address-level balance (rather than exclusively from a bounded state-var-tracked pool) is exposed. This satisfies the "AA fund loss or freezing" criterion for validity.

### Likelihood Explanation
The attack requires only unprivileged posting of ordinary payment units to a known AA address, which is fully permissionless and cheap relative to the amount of dust needed (each output just above `FULL_TRANSFER_INPUT_SIZE` in value). No special timing, race condition, or privileged access is required — any user who knows the AA's address can grief it. The severity depends on how many outputs must be accumulated for a given AA's spend, but since there is no bound on the number of attacker-controlled dust outputs, the condition is always reachable given enough attacker-supplied units.

### Recommendation
- In `aa_composer.js`'s `iterateUnspentOutputs`/`completePaymentPayload`, stop consuming additional outputs once `payload.inputs.length` approaches `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (mirroring the check already present in `indivisible_asset.js`'s `pickIndivisibleCoinsForAmount`), and consolidate/merge or explicitly fail with actionable diagnostics rather than silently exceeding the limit later at validation time.
- Add a `LIMIT` to `readStableOutputs`/`readUnstableOutputsSentByAAs` SQL queries so the number of rows fetched per attempt can't grow unbounded, and iterate in batches with periodic consolidation (auto-merge dust outputs opportunistically) so the AA's spendable output count stays bounded over time.
- Consider raising the dust-filtering threshold or introducing a maximum number of unspent outputs per AA address that can be created by external payments within a time window, to limit attacker-driven output-count growth.

### Proof of Concept
1. Deploy or identify a target AA whose logic causes it to send/refund bytes from its own balance to some address in response to a trigger.
2. Attacker repeatedly sends payment units to the AA's address, each containing an output whose amount is just above `FULL_TRANSFER_INPUT_SIZE` (the minimal accepted dust size) — e.g. thousands of such payments over time. This is unprivileged and only costs the attacker normal transaction fees.
3. Trigger the AA's normal spend/refund logic (as any user, per its own trigger-handling design).
4. In `completePaymentPayload`, `iterateUnspentOutputs` accumulates inputs from the flood of dust outputs without bound; once the required input count surpasses `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`, `validateAndSaveUnit` rejects the constructed unit (aa_composer.js:1408-1411), and the AA response is bounced.
5. Because the dust outputs are never spent (bounced unit), the same failure recurs on every subsequent attempt, permanently freezing the AA's ability to move its balance while the attacker can keep the pile growing with more dust units.

Note: exact numeric thresholds (`FULL_TRANSFER_INPUT_SIZE`, `MAX_INPUTS_PER_PAYMENT_MESSAGE`) were referenced but their concrete values were not retrieved in full from `constants.js` during this investigation; a Devin session with full file access should confirm these constants to quantify the exact number of dust outputs required for a successful attack.
