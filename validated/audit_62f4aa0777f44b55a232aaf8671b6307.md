### Title
Organization/repository binding confusion in multi-org webhook signature verification allows cross-tenant stack writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App deployment (`secrets.github.<org>.webhook_secret`), `WebhooksController#verify_signature` selects which organization's HMAC secret to verify the request against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (with a fallback to `params.dig('organization', 'login')`). [2](#0-1) [3](#0-2) 

However, once the signature is verified, `Handler#repository_name`—used by every event handler (`PushHandler`, `StatusHandler`, etc.) to locate the `Repository`/`Stack` to act on—reads a *different* JSON key: `payload.dig('repository', 'full_name')`. [1](#0-0) [4](#0-3) 

Because `repository.owner.login` and `repository.full_name` are independent keys within the same attacker-supplied JSON body, and the whole raw body is what gets HMAC-signed (not a validated/consistent structural relationship between these two fields), an attacker who possesses (or can obtain, e.g. by installing the Shipit-enabled GitHub App on their own low-privilege org) a valid `webhook_secret` for *one* configured organization can sign a payload where `repository.owner.login` names their own org (to pass verification) while `repository.full_name` names a *different* organization's repository that also has a Stack configured in the same Shipit instance.

### Finding Description
The binding that should hold is: **organization authenticated (via `repository_owner` → `webhook_secret`) == repository that is written (via `repository.full_name` → `Stack`)**. This equality is never enforced. `verify_signature` only proves "this body was signed by whichever org's secret matched `repository.owner.login`"; it says nothing about which repo `full_name` claims to be, since HMAC-SHA1 over the raw body only proves data integrity/origin from that keyholder, not internal cross-field consistency of arbitrary attacker-chosen JSON content. [5](#0-4) 

Since Shipit explicitly supports hosting stacks for multiple GitHub organizations behind one instance (`config/secrets.*.yml`, `Shipit.github_app_config`), this is a realistic configuration, not a contrived one. [6](#0-5) 

### Impact Explanation
An attacker who controls (or compromises) the GitHub App/webhook secret for Org A can forge push/status/check_suite events that are accepted as authentic by Shipit, but whose `repository.full_name` targets a Stack belonging to Org B (a different tenant on the same Shipit install). Depending on the handler this enables: triggering `GithubSyncJob`/`sync_github` for Org B's stack via `PushHandler`, or injecting fabricated `Status`/`CheckRun` records via `StatusHandler`/`CheckSuiteHandler`, which can influence merge-queue and deploy-safety decisions (e.g., forging CI-passing statuses to unlock a deploy) for a repository the attacker does not control. This is an authentication-boundary violation matching "escalation into cross-tenant state" / "unauthorized deploy/rollback" impact categories.

### Likelihood Explanation
Requires: (a) the Shipit instance configured for multiple GitHub organizations, and (b) the attacker to know one org's `webhook_secret` (e.g., because they own/administer that org's GitHub App installation, which is plausible if Org A is the attacker's own onboarded org). No repository write access or Shipit session/API token is required — only crafting an arbitrary HTTP POST to `/github/webhooks` (or the mounted path) with a custom signature computed over a custom body. This is squarely a within-scope, unprivileged-attacker forgery once one org's secret is known.

### Recommendation
Cross-check that `repository.owner.login` (or `organization.login`) used to select the signing organization matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request otherwise. Alternatively, verify the signature using the secret bound to `repository.full_name`'s owner directly, rather than a separately-read field, and reject when they cannot be reconciled to the same organization/config entry.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both with stacks tracked in this Shipit instance.
2. Attacker (who administers `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`) crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `OrgA`'s secret over the raw body.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'OrgA')` and successfully verifies the signature. [2](#0-1) 
5. `PushHandler#process` (via `Handler#repository_name`) looks up `Repository.from_github_repo_name('OrgB/target-repo')` and triggers `sync_github` on `OrgB`'s stacks, despite the request never being signed by `OrgB`'s secret. [1](#0-0) [4](#0-3)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
