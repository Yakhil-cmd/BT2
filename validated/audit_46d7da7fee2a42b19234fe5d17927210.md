### Title
Missing mutual exclusion between AA dry-run trigger evaluation and real AA trigger execution allows shared in-memory state corruption - ([File: aa_composer.js])

### Summary
The CVE describes a race caused by two operations (`sctp_udp_sock_start`/`sctp_udp_sock_stop`) that mutate shared kernel state without a common lock, letting them interleave and crash the kernel. Looking for a reachable analog in `ocore`, the closest candidate is `dryRunPrimaryAATrigger()` in `aa_composer.js`, which is invoked directly from an unprivileged, network-reachable code path (`network.js` `handleJoint`'s `ifOk` handler when `conf.bDryRunNewTriggers` is set) and mutates the same shared in-memory caches (`storage.assocUnstableUnits`, `storage.assocStableUnits`, AA state-var caches, etc.) that `handleAATriggers()`/`handlePrimaryAATrigger()` mutate during real trigger execution, but the two paths are not serialized by a common lock.

### Finding Description
`handleAATriggers()` serializes all *real* trigger executions under the `['aa_triggers']` mutex key [1](#0-0) , and unit persistence in `writer.js` is serialized under the `['write']` mutex key [2](#0-1) .

However, `dryRunPrimaryAATrigger()` calls `handleTrigger()` — the very same in-process formula/state evaluation engine used for real trigger execution — and then "reverts" its effects with `revertResponsesInCaches()`, all without acquiring either the `aa_triggers` or `write` mutex: [3](#0-2) .

This function is reachable by an ordinary unit poster: when `conf.bDryRunNewTriggers` is enabled, every incoming unit that is a primary AA trigger causes `network.js`'s `handleJoint` `ifOk` callback to call `aa_composer.dryRunPrimaryAATrigger()` *while only holding the `['handleJoint']` lock*, not `aa_triggers` or `write`: [4](#0-3) . It is also reachable directly by any light client via the `light/dry_run_aa` network request handler, again with no `aa_triggers`/`write` mutex around the call: [5](#0-4) .

Meanwhile, real trigger stabilization (`stabilizeMci` → `handleAATriggers`) and `saveJoint`'s post-commit trigger execution both run concurrently under only the `aa_triggers` lock, not the `handleJoint` lock: [6](#0-5) , [7](#0-6) . Because `dryRunPrimaryAATrigger` never takes the `aa_triggers` lock, and `handleAATriggers` never takes the `handleJoint` lock, the two code paths can run concurrently and interleave writes/reads on the same shared caches (e.g., `storage.assocUnstableUnits`, `storage.assocStableUnits`, `storage.assocBestChildren`, AA state-var caches touched by `handleTrigger`), exactly the "missing mutual exclusion between two state-mutating operations on shared data" pattern described in the CVE.

The project's own test suite acknowledges that `dryRunPrimaryAATrigger` must leave caches unchanged and explicitly diffs `storage.assocUnstableUnits`, `assocStableUnits`, `assocUnstableMessages`, `assocBestChildren`, and `assocStableUnitsByMci` before/after each dry run to confirm no leakage [8](#0-7) , which itself implies these caches are mutated during the dry run and relies on `revertResponsesInCaches` fully undoing all changes — a property that can only be guaranteed if no other real trigger execution mutates the same objects concurrently in the interim.

### Impact Explanation
If a real AA trigger for the same or a related AA address is being stabilized/executed (`handleAATriggers`) concurrently with a dry-run evaluation triggered by an incoming unit or a `light/dry_run_aa` request, both code paths read and mutate the same live JS objects (unstable/stable unit caches, AA balance/state caches referenced through `handleTrigger`). Because there is no shared lock, the dry run's "revert" step (`revertResponsesInCaches`) could undo or overwrite state that the concurrent real execution just committed to memory (or vice versa), leaving the node's in-memory cache of AA balances/state permanently inconsistent with the database. This can manifest as an AA computing balances or state from corrupted data on subsequent triggers (fund loss/freezing for the AA, or a crash/exception when accessing an unexpectedly missing/mutated cache entry), and since AA state execution is deterministic and consensus-critical, a diverging in-memory cache on one node versus another can cause that node to disagree with the network on the correct AA response/balance, i.e., a node-disagreement-on-validity/stability class of issue.

### Likelihood Explanation
`dryRunPrimaryAATrigger` from the `handleJoint` path is gated behind the `conf.bDryRunNewTriggers` configuration flag, so it is not on by default; whether this flag is enabled in the target deployment is unknown from the code alone. The `light/dry_run_aa` command, however, is reachable unconditionally by any connected light client/peer without this flag, making the race achievable by simply sending crafted/rapid dry-run requests for an address that is expected to receive a real AA trigger around the same time. Because both code paths are asynchronous with database round-trips of similar duration, achieving an actual overlapping window is plausible under load but not deterministic, similar to the syzkaller-detected timing window in the original CVE.

### Recommendation
Serialize `dryRunPrimaryAATrigger()` (and any other consumer of `handleTrigger()`) against the `aa_triggers` mutex key used by `handleAATriggers()`, e.g., wrap the body of `dryRunPrimaryAATrigger` with `mutex.lock(['aa_triggers'], ...)` (or a dedicated `dry_run` key that is mutually exclusive with `aa_triggers`), analogous to how the CVE fix added mutual exclusion between `sctp_udp_sock_start`/`sctp_udp_sock_stop`. Ensure the lock is held for the entire duration from cache mutation through `revertResponsesInCaches()`/rollback so no interleaving with real trigger execution can occur.

### Proof of Concept
Conceptual PoC (cannot be executed without live node access):
1. Enable `conf.bDryRunNewTriggers = true` (or use the always-available `light/dry_run_aa` request).
2. From a light client / peer connection, repeatedly send `light/dry_run_aa` requests for an AA address `A` that is expected to have real triggers processed frequently (e.g., an actively used AA), while simultaneously posting real trigger units to `A`.
3. Because `dryRunPrimaryAATrigger` (aa_composer.js:272-306) and `handleAATriggers`/`handlePrimaryAATrigger` (invoked from `main_chain.js` `stabilizeMci` and `writer.js`'s post-commit path) are not mutually exclusive, under sufficient request/trigger throughput the two executions interleave on shared caches (`storage.assocUnstableUnits`, `assocStableUnits`, state-var caches), which can be observed as inconsistent `updatedStateVars`/balance results returned to the light client, or as cache-consistency assertions like those in `test/aa_composer.test.js` failing/throwing when run concurrently rather than serially.

Note: I was not able to execute this PoC or confirm actual data corruption at runtime — this analysis is based on static code review of the locking discipline; the exact severity depends on further dynamic verification of interleaving outcomes on the specific cache structures touched by `handleTrigger`.
