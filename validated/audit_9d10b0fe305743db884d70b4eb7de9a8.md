### Title
Missing `return` after exception handler causes duplicate/undefined-state processing of private payment chains - ([File: network.js])

### Summary
The QEMU CVE-2023-6683 bug class is: a handler proceeds to use state that a prior error path failed to establish, because control flow falls through past an error branch instead of stopping. The closest reachable analog in `ocore--006` is in `network.js`, function `handleSavedPrivatePayments()`, inner function `validateAndSave`, which is triggered by processing of saved/unhandled private payment chains — a path reachable by a payment counterparty who sends a malformed private-payment chain.

### Finding Description
In `network.js` inside `handleSavedPrivatePayments()`: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...});
};
```

There is no `return` statement after the `catch` block calls `deleteHandledPrivateChain(..., cb)`. If `objectHash.getBase64Hash()` throws (which happens when the private element's `payload` cannot be canonically hashed, e.g. it contains structures that `object_hash.js` rejects — attacker-controlled, since `payload` originates from a peer-submitted private payment chain saved earlier via `handleOnlinePrivatePayment`), execution does **not** stop. Instead:
1. `deleteHandledPrivateChain(...)` is invoked, which itself eventually calls `cb()` (the `async.each` iteration callback) once the delete completes, asynchronously.
2. Immediately after, the same closure continues synchronously to build `key` using `json_payload_hash` which is `undefined` (a state variable that should only exist on the success path), and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same `arrPrivateElements` a second time, with its own `ifOk`/`ifError`/`ifQueued` callbacks that also eventually call `cb()`.

This mirrors the QEMU bug class exactly: a code path that should only run after successful "capability negotiation" (a valid computed hash / validated payload) is instead reached with default/undefined state because the error branch failed to stop execution, and the caller (`async.each`) has no guard against `cb()` being invoked more than once per iteration.

### Impact Explanation
Because `async.each`'s callback is invoked twice for the same private-payment row, the outer completion callback in `handleSavedPrivatePayments` can be triggered prematurely relative to other in-flight chain validations, and the same `arrPrivateElements` gets fed twice into `privatePayment.validateAndSavePrivatePaymentChain`, once via the delete path (no-op) and once via the direct validate/save path with corrupted `key` (using `"undefined"` as the hash component). This can lead to:
- Double processing of the same private payment record, and/or races with `deleteHandledPrivateChain` in `unhandled_private_payments`, since both branches operate on the same row concurrently.
- Corruption/collision of the `private_payment_validated-...-undefined-...` event key used to gate `checkIfAllValidated()` for other in-flight private chains (in `wallet.js`'s `handlePrivatePaymentChains`), potentially causing a private payment to be marked validated/accepted when it should not be, or causing legitimate chains to never resolve (stuck wallet state / frozen private funds).
- In the worst case, an attacker who can make `getBase64Hash` throw on a crafted `payload` (attacker-controlled private element data) can force this double-invocation deterministically, undermining the wallet's bookkeeping of private, unlinkable payments — the correctness guarantee that private payment amounts/outputs are validated exactly once before being trusted.

This does not reach kernel/QEMU-style crash territory (JS exceptions here are caught), but it does violate exactly-once processing invariants around private-payment fund tracking, which is the closest reachable node-disagreement/fund-integrity analog available in this codebase for the reported bug class.

### Likelihood Explanation
Reaching `objectHash.getBase64Hash()`’s throw path requires the attacker (a counterparty in a private payment / device correspondent) to submit a private-payment chain whose head `payload` cannot be canonically JSON-hashed (e.g., a payload shape that `object_hash.js`'s canonicalizer chokes on) that nonetheless passes the earlier lightweight structural checks in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains` (`isNonemptyObject`, `isNonemptyString`, `isNonemptyArray` checks only). This is plausible without special privileges — the private-payment flow is reachable from any correspondent/paired device sending a `private_payment` message, which is an unauthenticated-with-respect-to-content path once paired.

### Recommendation
Add a `return;` immediately after the `catch` block's `deleteHandledPrivateChain(...)` call in `network.js`'s `validateAndSave` (inside `handleSavedPrivatePayments`), so that execution does not fall through to compute `key` from an undefined `json_payload_hash` or call `privatePayment.validateAndSavePrivatePaymentChain` a second time on the same row. Audit other `try { ... } catch (e) { ...; } ` blocks in this file and `wallet.js` for similar missing-`return` fallthrough patterns that could cause double invocation of `cb`/`callbacks` in `async` control flow.

### Proof of Concept
1. A peer/paired device sends a private payment (`private_payment` justsaying or hub-forwarded chain) whose head element's `payload` is structurally valid enough to pass `isNonemptyObject`/array checks in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`, but is crafted so that `objectHash.getBase64Hash(payload, true)` throws inside `object_hash.js` (e.g., by exploiting a value type unsupported by the canonical hashing routine).
2. This chain gets persisted to `unhandled_private_payments` (light-client / queued path) and later reprocessed by `handleSavedPrivatePayments()` → `validateAndSave()`.
3. `getBase64Hash` throws; the `catch` block runs `deleteHandledPrivateChain(..., cb)` but does not return.
4. Execution falls through, builds `key` with `undefined` hash component, and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again on the same data, causing `cb()` from `async.each` to be invoked twice for one row and a stray `private_payment_validated-...-undefined-...` event to fire.

Note: full verification of `object_hash.js`'s exact throw conditions and downstream effects of a duplicate `cb()` in `async.each` (e.g., whether Node's `async` library tolerates double-callback silently or raises errors) could not be completed within the scope of this indexed search; a Devin session with full repository/test access would be needed to construct and run a concrete input that triggers the `getBase64Hash` exception and observe the resulting duplicate processing behavior.
