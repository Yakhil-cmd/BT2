### Title
AA that receives coins but whose cases produce no matching payment message silently absorbs the funds with no reclaim path - (File: aa_composer.js)

### Summary
The external report describes a Solidity `payable` function that accepts `msg.value` but never uses it, so any coins accidentally sent to it become permanently locked in the contract. The analogous root cause exists in ocore's AA (autonomous agent) trigger-handling logic: when a unit posts a payment to an AA address and none of the AA's `cases` evaluate to `true` (or the matching case has no payment output), `handleTrigger()` treats this as a valid, non-bounced response and permanently keeps the received funds in the AA's balance instead of returning them to the sender.

### Finding Description
Any unprivileged user can post a payment unit whose output goes to an AA address. Before any AA logic is evaluated, `updateInitialAABalances()` unconditionally credits the received amount to the AA's internal balance (`aa_balances`) [1](#0-0) . The trigger then goes through `evaluateAA()`; if the resulting `messages` array is empty after filtering (i.e., no `if` case matched, or the matched case had no valid payment message), the code takes the "eat the coins" path instead of bouncing the payment back to the sender: [2](#0-1) 

Unlike the `bounce()` path — which is only triggered on an explicit error and refunds the sender minus the bounce fee (see `bounce()` at [3](#0-2) ) — the "no messages after filtering" branch calls `handleSuccessfulEmptyResponseUnit(null)`, which finalizes the trigger as a *successful* response, keeps the previously credited balance from `updateInitialAABalances()`, and issues no payment message back to the sender. If the AA definition does not include a catch-all case such as the "silently accept coins" pattern seen in `test/samples/order_book_exchange.oscript` (which explicitly credits a per-user state variable) [4](#0-3) , the sent funds remain in the AA's on-chain balance with no state variable or output ever created to let the sender (or anyone) withdraw them, since AA definitions are immutable once posted.

### Impact Explanation
Funds sent by any ordinary trigger sender to an AA can become permanently and irrecoverably locked in the AA's balance if the AA's case set does not explicitly cover the trigger's shape (data, asset, or amount). This is a direct AA fund-loss/freezing condition reachable by any unprivileged unit poster who interacts with such an AA, matching the accepted "AA fund loss or freezing" impact class.

### Likelihood Explanation
This is easily triggered — any sender who posts a payment to an AA with data or amounts that don't satisfy any `if` condition in the AA's `cases` (a very plausible user error, e.g., mistyped data field, wrong asset, or unexpected amount) hits the empty-messages path and loses the funds, since the protocol's default behavior here is to accept silently rather than bounce.

### Recommendation
Change the default behavior when an AA case set produces no messages for a non-zero payment trigger: either always bounce (refund minus bounce fee) unless the AA definition explicitly opts to "accept" the coins, or require every AA `cases` list to end in a mandatory catch-all case validated at definition time. At minimum, document and strongly encourage (or enforce via `validateAADefinition`) that every AA definition include a fallback case (like `test/samples/order_book_exchange.oscript`'s "silently accept coins" case) that records or forwards any otherwise-unmatched payment, so that unmatched deposits are not silently absorbed with no way to reclaim them.

### Proof of Concept
1. Deploy an AA whose only case is `if: "{trigger.data.foo}"` with a `payment` message, i.e., it has no catch-all/else case.
2. Send a payment unit to the AA address without the `data.foo` field (e.g., no data message at all, or unrelated data).
3. `getTrigger()` records the output amount in `trigger.outputs` [5](#0-4) ; `updateInitialAABalances()` credits it to `aa_balances` for the AA address.
4. `evaluateAA()` finds no matching case, `messages` filters to an empty array, and `handleSuccessfulEmptyResponseUnit(null)` finalizes a non-bounced response [2](#0-1) .
5. No payment message is sent back to the sender; the sender's coins remain in the AA balance with no code path in the (immutable) AA definition ever created to release exactly this deposit.
