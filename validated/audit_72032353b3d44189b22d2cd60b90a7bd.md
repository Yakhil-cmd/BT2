### Title
Cross-repository status forgery — `StatusHandler#process` writes statuses by bare SHA with no repository binding - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table and calls `create_status_from_github!` on every match, regardless of which repository the authenticated webhook belongs to. This lets a `status` webhook, correctly signed for repository A (attacker-controlled), write a `success` status onto a same-SHA commit that actually belongs to repository B (victim), because unlike sibling handlers this handler never scopes to `Repository.from_github_repo_name(payload.repository.full_name)`.

### Finding Description
The broken binding is: **the repository that authorized the webhook signature must equal the repository whose commit/status is mutated**, i.e. `repository_owner(payload) == commit.stack.repository.full_name`. This is violated.

Code path:
- `WebhooksController#create` dispatches the raw JSON `params` to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks that the HMAC signature matches the GitHub App config keyed by `repository_owner` (`payload.dig('repository','owner','login')`) — see `app/controllers/shipit/webhooks_controller.rb:10-49`. This proves the webhook came from *some* app installation for that org/owner; it says nothing about which specific repository record in Shipit's DB should be touched.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It queries `Commit.where(sha: params.sha)` with **no join/filter on repository or stack**, unlike every other handler in the same directory (`PullRequest::OpenedHandler`, `EditedHandler`, `ClosedHandler`, `UnlabeledHandler`, etc.) which all resolve `repository = Repository.from_github_repo_name(params.repository.full_name)` and scope subsequent lookups (`repository.review_stacks`, `stacks: { repositories: { id: repository.id } }`) before mutating anything. The base `Handler` class even exposes a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) that does exactly this scoping, but `StatusHandler` never uses it.
- `commit.create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) creates a `Status` row scoped to that commit's own `stack_id`, so the write lands in whatever stack/repository the pre-existing `Commit` row belongs to — not the repository that sent the webhook.
- `Shipit::UndeployedCommit#deploy_state` then recomputes `deployable? ? 'allowed' : status.state` (`app/models/shipit/undeployed_commit.rb:18-19`), and `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` (`app/models/shipit/commit.rb:227-229`), which flips to `'allowed'` once the forged `success` status exists.

Exploit flow: attacker controls repository A (their own fork/repo, enrolled with a real Shipit GitHub App installation so `verify_signature` passes for A's org). Attacker crafts/produces a commit whose SHA collides with an existing commit SHA already tracked in victim's stack for repository B — the most realistic vector is a fork of B where a shared ancestor commit (unchanged tree/parents/author/committer/message/timestamps) has an identical SHA, or any workflow that reproduces identical git objects across repos (shared submodule commit, cherry-pick preserving all metadata, mono-repo split). Attacker then sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for A's org, `sha` = the shared SHA, and `state: success`. `StatusHandler` finds the `Commit` row for that SHA that belongs to victim's stack B and writes a `success` `Status` against it, even though the payload's `repository.full_name` refers to A, not B.

`verify_signature` does not fail here because it validates the org, not the specific repository or commit ownership; `drop_unhandled_event` and `ExplicitParameters` schema only validate shape, not authorization scope; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant to unauthenticated webhook ingestion by design.

### Impact Explanation
The attacker, without ever authenticating against `victim`, causes a `Shipit::Status` (state `success`) to be written on `victim`'s commit, changing `Commit#deployable?` and `UndeployedCommit#deploy_state`/`expected_to_be_deployed?` from `pending`/`missing` to `allowed`. If `victim`'s stack has `continuous_deployment: true`, `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) can trigger an actual deploy of that commit through `Stack#trigger_continuous_delivery`/`trigger_deploy`, i.e. an unauthorized deploy driven entirely by a payload for a different repository. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable against any stack/commit combination where a same-SHA collision can be arranged, and generalizes across tenants sharing the same Shipit instance.

### Likelihood Explanation
Preconditions: `victim` stack has `continuous_deployment: true` and lacks (or is bypassed for) required CI status; attacker needs their own legitimately configured GitHub App/webhook installation for some repository (cheap, self-service) and a same-SHA commit reachable in victim's tracked history (achievable by forking the victim repo before the point of divergence — forked commits retain identical SHAs). No Shipit secrets, session, API token, or team membership are required — only the ability to emit a webhook from a repository the attacker owns. Feasibility is moderate: it depends on finding/creating identical-SHA commits between attacker and victim repos, which is a normal git property (unchanged commits keep their SHA across forks), not a hash break.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring the other handlers: resolve `repository = Repository.from_github_repo_name(payload.dig('repository','full_name'))` (require it in the `params` schema), then restrict the commit lookup to `repository.stacks.flat_map(&:commits).where(sha: params.sha)` (or an equivalent join through `stacks: { repository_id: repository.id }`), so a status can only be attached to commits belonging to stacks of the authorized repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "#process does not write a status for a commit belonging to a different repository" do
  victim_repo   = shipit_repositories(:shipit) # or a second fixture repo
  attacker_repo_full_name = "attacker/other-repo"

  victim_commit = shipit_commits(:cyclimse_first) # belongs to victim_repo's stack, currently pending/missing
  before_state = UndeployedCommit.new(victim_commit, index: 0).deploy_state
  refute_equal 'allowed', before_state

  payload = {
    'sha' => victim_commit.sha, # SHA collision with victim's commit
    'state' => 'success',
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } },
    'branches' => [{ 'name' => victim_commit.stack.branch }]
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  after_state = UndeployedCommit.new(victim_commit.reload, index: 0).deploy_state
  assert_equal 'allowed', after_state, "status for attacker's repo should not have flipped victim's commit to allowed"
end
```
This asserts the binding `repository_owner(payload) == commit.stack.repository.full_name` before and after: before the call the equality holds trivially (no write occurs); after the call `StatusHandler` writes the status regardless of the mismatched `repository.full_name` in `payload`, proving the binding is not enforced in code and `deploy_state` transitions to `'allowed'`.
