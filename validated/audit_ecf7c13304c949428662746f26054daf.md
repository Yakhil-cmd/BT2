### Title
Hidden sub-invocation in a user-signed swap auth tree drains the signer's wallet — an innocuous `swap_collateral`/`multiply` signature silently authorizes an unrelated token transfer - (File: contracts/controller/src/strategies/swap.rs)

### Summary
CVE-2018-12374's class is "an innocuous user action implicitly commits a hidden, more dangerous action" (pressing Enter in a text field silently submitted an embedded form and leaked plaintext). The on-chain analog lives in the router-routed strategy entrypoints: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` each call `caller.require_auth()` once at the root and then execute an arbitrary, non-allowlisted `StrategySwap` route through the configured aggregator. Any contract reachable via that route can invoke `token.transfer(victim, attacker, victim_balance)`; Soroban records that call as a child of the victim's signed authorization entry, and it executes the moment the victim signs the tree the simulator returns. The user believes they authorized one swap; the signature actually commits a full wallet drain.

### Finding Description
- `swap_collateral` authenticates the caller with a single root `require_authorized_caller(env, caller)` (contracts/controller/src/strategies/swap_collateral.rs:40) and then routes the caller-supplied `swap` payload into `swap_tokens`.
- `swap_tokens` grants exactly one contract-side authorization — `authorize_transfer_as_current` for the controller's own `amount_in` — and invokes `router.execute_strategy(&controller, &amount_in, swap)` (contracts/controller/src/strategies/swap.rs:34-38). The controller imposes no allowlist on the venues/pools inside `swap`, and after execution it only checks controller balance deltas (`in_after <= in_before`, `received > 0`) — it cannot see, let alone constrain, what the route did under the *caller's* auth subtree (contracts/controller/src/strategies/swap.rs:41-54,75-84).
- The dedicated harness proves the mechanism end-to-end: a rogue hop pool in the route calls `RecordingToken::transfer(alice, attacker, WALLET_BALANCE)`; simulation records it as a sub-invocation of Alice's `swap_collateral` entry, and signing that returned tree moves her entire wallet balance while the swap still settles "fairly" (tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-269). The threat model confirms there is no contract-side bound: "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" (docs/explanation/threat-model.md:154-165).

### Impact Explanation
Theft of user funds, unbounded by the swapped amount: any token whose `transfer` auths `from` can be fully drained from the victim's wallet in the same transaction as a legitimate-looking collateral swap, multiply, or debt swap. The contract-level checks (positive output, final health factor) all pass because the theft is orthogonal to the position bookkeeping.

### Likelihood Explanation
Requires the victim to sign a route containing a malicious venue — i.e., signing whatever auth tree `simulateTransaction` returns without decoding its children. The threat model itself notes "an honest simulation… executes if the caller signs that tree" and assigns detection to the client. Given route bytes are opaque to users and wallets render limited detail, this is a realistic phishing/Malicious-route-provider vector — consistent with the CVE's Medium (4.3, user-interaction-required) profile.

### Recommendation
Constrain the blast radius contract-side where possible: pin or governance-allowlist the venue contracts a `StrategySwap` route may traverse (the pool router already keeps a token whitelist for fee placement — extend admission to venues), or split routed strategies so the sensitive ones only accept controller-constructed routes. At minimum, make the controller enforce that `token_in`/`token_out`/pool addresses named in the route are known market assets so a route cannot address arbitrary token contracts, and surface the full child-invocation list in the strategy's emitted event so wallets/indexers can flag poisoned trees.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `Scene::route_through_pool_stealing(WALLET_BALANCE)` builds a `swap_collateral` route whose hop pool calls `token.transfer(alice → attacker, WALLET_BALANCE)`. In recording mode the simulator returns Alice's auth entry with the theft as a child (line 222); signing that tree executes both the fair swap and the drain (lines 258-269: Alice's wallet → 0, attacker → `WALLET_BALANCE`).
