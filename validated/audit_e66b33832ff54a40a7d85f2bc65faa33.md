### Title
Webhook signature verification keys off `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-repository writes on a multi-organization Shipit instance - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which is read straight from the untrusted JSON body (`repository.owner.login`, or `organization.login`). Every webhook handler (`PushHandler`, `StatusHandler`, etc.), however, looks up which `Stack`/`Repository` to act on using a completely different field of the same body: `repository.full_name` (via `Handler#repository_name`). Since both fields are attacker-supplied and nothing enforces that `repository.owner.login` matches the owner encoded in `repository.full_name`, an attacker who legitimately owns a webhook secret for *their own* org can forge a payload whose `owner.login` matches their org (so the signature check passes with their own secret) while `full_name` points at a victim organization's repository. The action then executes against the victim's `Stack`.

### Finding Description
Signature verification: [1](#0-0) 
selects the app/secret via: [2](#0-1) 
i.e. `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and passes the *entire raw body* to `verify_webhook_signature`, keyed by that org's own `webhook_secret`: [3](#0-2) 

The dispatched handlers, however, resolve the target repository/stack from an entirely different JSON key: [4](#0-3) 
`repository_name = payload.dig('repository', 'full_name')`, then `Repository.from_github_repo_name(repository_name)` to find stacks: [5](#0-4) 

`PushHandler#process` then acts on the matching stacks by triggering `stack.sync_github`: [6](#0-5) 
which enqueues `GithubSyncJob`, fetches new commits from GitHub, appends them, and (if the sync changed anything) can drive continuous delivery / deploys for that stack: [7](#0-6) 

**Binding that should hold:** `organization that authenticated (repository.owner.login, checked against webhook_secret)` == `repository that is written (repository.full_name, used to resolve the target Stack)`.

**Before the attack:** these two fields normally match, because a real GitHub webhook delivery always has the repository's actual owner in `repository.owner.login` and the same owner in `repository.full_name`.

**After the attack:** an attacker who administers "attacker-org" (which is configured as one of the multiple organizations in Shipit's `github:` config, each with its own `webhook_secret`, as documented in `config/secrets.development.shopify.yml`) can POST a body where `repository.owner.login = "attacker-org"` (so the signature check uses attacker-org's own known secret and passes) but `repository.full_name = "victim-org/victim-repo"`. The signature-verifying org and the acted-upon repository diverge, breaking the equality above and causing Shipit to fetch/sync commits (and potentially deploy) for a repository the attacker has no access to.

### Impact Explanation
This is a cross-tenant boundary break in Shipit's supported multi-organization deployment (`github:` config keyed by org, each with independent `webhook_secret`, per `docs/setup.md` and `config/secrets.development.shopify.yml`). An attacker who controls only their own org's webhook secret can force `GithubSyncJob` to run against an unrelated organization's tracked `Stack`, fabricating commit history via `stack.commits.create_from_github!` and, if continuous deployment is enabled on that stack, trigger an unauthorized deploy of attacker-influenced commit metadata. This matches the required Critical impact of "cross-repository writes" / "an unauthorized deploy".

### Likelihood Explanation
Exploitability requires only that the deployment operate a multi-organization Shipit configuration (explicitly supported and documented) and that the attacker control (be an admin of) at least one of the configured organizations' GitHub Apps/webhook secrets — a scenario the engine explicitly supports as a legitimate, unprivileged-relative-to-other-tenants configuration. No repository write access, `ApiClient` token, or Shipit session is required; only the ability to send an HTTP POST to `/webhooks` with a self-signed payload.

### Recommendation
Do not use two different fields from the same untrusted payload for authentication vs. authorization. After signature verification succeeds for `repository_owner`, re-validate that every repository-identifying field used by handlers (`repository.full_name`, `repository.owner.login`) is consistent with the org whose secret validated the signature — e.g., in `WebhooksController#verify_signature`, additionally assert `params.dig('repository', 'full_name')&.split('/')&.first&.casecmp?(repository_owner)` and reject (422) on mismatch, or have `Handler#repository_name` derive the owner strictly from the same value that was cryptographically verified rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `github.webhook_secret` (as supported per `config/secrets.development.shopify.yml`), and `victim-org/victim-repo` is a tracked `Stack`.
2. Attacker, who administers `attacker-org` and knows its `webhook_secret`, builds a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker signed with their own secret.
5. `PushHandler#process` is invoked with the full payload; `Handler#repository_name` reads `payload.dig('repository','full_name') == "victim-org/victim-repo"`, resolves the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeef")`, enqueuing `GithubSyncJob` against the victim repository without any credential belonging to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
