### Title
Intra-Epoch Dual-Vote Race Condition Breaks `LowerBoundBaseFee ≤ UpperBoundBaseFee` Invariant, Corrupting Base-Fee Computation for All Blocks — (`kaiax/gov/headergov/impl/header.go`)

---

### Summary

`checkConsistency` validates each KIP-71 base-fee bound vote individually against the **current** `GetParamSet`, not against other votes already queued in the same epoch. Two individually-valid votes cast in the same epoch can jointly violate the invariant `LowerBoundBaseFee ≤ UpperBoundBaseFee`. Once ratified, `NextMagmaBlockBaseFee` produces incorrect values for every subsequent block, permanently corrupting the fee market until a corrective governance vote takes effect.

---

### Finding Description

`checkConsistency` in `kaiax/gov/headergov/impl/header.go` performs per-vote cross-parameter checks:

```go
case gov.Kip71LowerBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) > params.UpperBoundBaseFee {
        return ErrLowerBoundBaseFee
    }
case gov.Kip71UpperBoundBaseFee:
    params := h.GetParamSet(blockNum)
    if vote.Value().(uint64) < params.LowerBoundBaseFee {
        return ErrUpperBoundBaseFee
    }
``` [1](#0-0) 

Each vote is checked against `GetParamSet(blockNum)`, which returns the **currently ratified** parameters — not the pending votes accumulated in the same epoch. Votes are collected throughout an epoch and ratified together at the epoch boundary by `getExpectedGovernance`, which applies no cross-parameter validation:

```go
for _, voteBlock := range sortedVoteBlocks {
    vote := prevEpochVotes[voteBlock]
    govs.Add(string(vote.Name()), vote.Value())
}
``` [2](#0-1) 

`VerifyGov` only checks that the ratified governance data matches the locally-derived expected data — it performs no cross-parameter consistency check at ratification time. [3](#0-2) 

---

### Impact Explanation

Once `LowerBoundBaseFee > UpperBoundBaseFee` is ratified, `NextMagmaBlockBaseFee` in `params/kip71_config.go` enters a broken state. With, say, `LowerBound = 50 gwei` and `UpperBound = 30 gwei`:

- Line 82–86: `parentBaseFee` is clamped to `upperBoundBaseFee` (30) because `parentBaseFee ≥ 30`
- High-gas path (line 106–108): `nextBaseFee > upperBound` → returns `upperBoundBaseFee = 30`
- Low-gas path (line 124–126): `nextBaseFee < lowerBound` → returns `lowerBoundBaseFee = 50` [4](#0-3) 

The base fee oscillates between 30 and 50 gwei based on gas usage — a value that is simultaneously above the upper bound and below the lower bound depending on the branch taken. This is an invalid state.

`validateHeader` in `blockchain/block_validator.go` calls `VerifyMagmaHeader`, which checks that `header.BaseFee == NextMagmaBlockBaseFee(...)`:

```go
govParamSet := v.mGov.GetParamSet(header.Number.Uint64())
if err := govParamSet.ToKip71Config().VerifyMagmaHeader(header.BaseFee, parent.Number, parent.BaseFee, parent.GasUsed); err != nil {
    return err
}
``` [5](#0-4) 

Since all nodes compute the same broken `NextMagmaBlockBaseFee`, they agree on the wrong base fee — no consensus divergence occurs, but the fee market is permanently corrupted. Transactions with gas prices between the broken upper bound and the intended lower bound are accepted or rejected incorrectly, breaking the fee-market invariant and affecting KAIA fee collection for every block until a corrective vote is ratified.

---

### Likelihood Explanation

- **`none` governance mode**: Any two council members can independently vote for conflicting values in the same epoch with no coordination. Each vote passes its individual check against the current params. This is a straightforward, unprivileged trigger.
- **`single` governance mode** (Mainnet/Kairos): The governing node must cast two conflicting votes in the same epoch. This can happen by mistake (e.g., the operator intends to narrow the range but issues both votes without realizing their combined effect), or if the governing node key is compromised. The governing node is a semi-trusted actor, not a fully privileged one in the context of this invariant.

The epoch on Mainnet is 604,800 blocks (~1 week), giving ample time for two votes to be cast in the same epoch. [6](#0-5) 

---

### Recommendation

Add a cross-parameter consistency check at **ratification time** inside `getExpectedGovernance` (or equivalently in `VerifyGov`), after all votes for the epoch are collected and before the governance data is finalized:

```go
// After collecting all votes into govs:
lower, hasLower := govs[string(gov.Kip71LowerBoundBaseFee)]
upper, hasUpper := govs[string(gov.Kip71UpperBoundBaseFee)]
currentParams := h.GetParamSet(blockNum)

effectiveLower := currentParams.LowerBoundBaseFee
if hasLower { effectiveLower = lower.(uint64) }
effectiveUpper := currentParams.UpperBoundBaseFee
if hasUpper { effectiveUpper = upper.(uint64) }

if effectiveLower > effectiveUpper {
    // drop or reject the conflicting vote(s)
}
```

Alternatively, `checkConsistency` should also check the vote against **pending votes already recorded in the current epoch** for the counterpart parameter, not just against the currently-ratified params.

---

### Proof of Concept

**Setup**: Mainnet-like chain, `none` governance mode, epoch = 30 blocks, current params: `LowerBound = 25 gwei`, `UpperBound = 750 gwei`.

1. **Block 5 (epoch 0)**: Council member A votes `kip71.upperboundbasefee = 30 gwei`.
   - `checkConsistency`: `30 < 25 (current LowerBound)`? → **No** → vote accepted. [7](#0-6) 

2. **Block 20 (epoch 0)**: Council member B votes `kip71.lowerboundbasefee = 50 gwei`.
   - `checkConsistency`: `50 > 750 (current UpperBound)`? → **No** → vote accepted. [8](#0-7) 

3. **Block 30 (epoch boundary)**: `getExpectedGovernance` collects both votes, no cross-parameter check, ratifies `{LowerBound: 50, UpperBound: 30}`. [2](#0-1) 

4. **Block 31 onwards**: `NextMagmaBlockBaseFee` is called with `LowerBound=50 > UpperBound=30`. The base fee oscillates between 30 and 50 gwei depending on gas usage, violating both bounds simultaneously. [4](#0-3) 

5. All nodes agree on the broken base fee (no fork), but every block's fee market is incorrect. Transactions priced between 30 and 50 gwei are accepted or rejected incorrectly, corrupting KAIA fee accounting for all blocks until a corrective governance vote is ratified at the next epoch boundary.

// (1) governance must be empty in non-epoch block,

func (h *headerGovModule) VerifyGov(header *types.Header) error {
	// (1)
	if header.Number.Uint64()%h.epoch != 0 {
		if len(header.Governance) > 0 {
			logger.Error("governance is not allowed in non-epoch block", "num", header.Number.Uint64())
			return ErrGovInNonEpochBlock
		} else {
			return nil
		}
	}

	// (2), (3)
	expected := h.getExpectedGovernance(header.Number.Uint64())
	if len(header.Governance) == 0 {
		if len(expected.Items()) != 0 {
			return ErrGovVerification
		}

		return nil
	}

	// (4)
	var gb headergov.GovBytes = header.Governance
	actual, err := gb.ToGovData()
	if err != nil {
		logger.Error("DeserializeHeaderGov error", "num", header.Number.Uint64(), "governance", gb, "err", err)
		return err
	}

	// (5)
	if !reflect.DeepEqual(expected, actual) {
		logger.Error("Governance mismatch", "expected", expected, "actual", actual)
		return ErrGovVerification
	}

	return nil
}

func (h *headerGovModule) getExpectedGovernance(blockNum uint64) headergov.GovData {
	prevEpochIdx := calcEpochIdx(blockNum, h.epoch) - 1
	prevEpochVotes := h.getVotesInEpoch(prevEpochIdx)
	govs := make(gov.PartialParamSet)

	sortedVoteBlocks := slices.Collect(maps.Keys(prevEpochVotes))
	slices.Sort(sortedVoteBlocks)

	for _, voteBlock := range sortedVoteBlocks {
		vote := prevEpochVotes[voteBlock]
		govs.Add(string(vote.Name()), vote.Value())
	}

	// assert(len(headergov.NewGovData(govs).Items()) == len(govs))
	return headergov.NewGovData(govs)
}

```markdown
- _epoch_: a fixed period for header governance ratification. Defined in the genesis block. In Mainnet and Kairos, epoch is 604800 blocks (1 week).
- _epoch index_: the index of the epoch, starting from 0. Given a block number `N`, its epoch index is `floor(N / epoch)`. In other words, all blocks in `[k*epoch, (k+1)*epoch - 1]` belong to the `k`-th epoch.
- _parameter set at blockNum_: the governance parameter set that are effective when mining the given block.

### Header governance

Header governance is the process of changing the governance parameters among members of the GC via block header.
This module writes and interprets block header's `Vote` and `Governance` fields. Note that this module writes validator addition/removal votes to `header.Vote`, but does not read them from `header.Vote` which is left to the kaiax/valset module.

```
      vote         ratified    vote   vote   ratified
       V                V       V       V    V
   |---+----------------|-------+-------+----|

   *.....0th epoch......O
                        *......1st epoch.....O
                                             *....2nd epoch....
```

A vote is initiated by a governing member of the GC casting a vote.
The vote is cast by the `governance_vote` API, which is inscribed in the block header `header.Vote` when the node that received the API call becomes the proposer.
The voter casts a vote as a tuple `(parameter name, new value)`.
The vote is collected for the entire epoch.

At every epoch block (i.e., `k*epoch` blocks), the node that becomes the proposer will check if the vote has been ratified.
If the vote is ratified, the node will announce the ratification in the block header `header.Governance`.
In other words, `header.Governance` can contain data only at epoch blocks.
If there are no votes in an epoch, the next starting block of the epoch will have an empty `header.Governance`.
It contains a JSON object of `{name: value}` for each ratified parameter.

The ratification condition is determined by the `governance.governancemode` parameter. Mainnet and Kairos both operate in `single` mode. There are two governance modes:

- `none` mode: all members of the GC can vote. For each governance parameter, the last vote in the epoch will be ratified.
- `single` mode: only one member of the GC, stipulated in the parameter `governance.governingnode`, can vote. All valid votes from the governing node in the epoch are ratified in block order. For each governance parameter, the last vote in the epoch will be ratified.

Parameter change ratified at `k*epoch` block takes effect starting from `(k+1)*epoch` block.
It is worth noting that the effective time of the ratification is `(k+1)*epoch + 1` before Kore.
