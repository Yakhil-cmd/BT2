This confirms Shipit supports a **multi-tenant configuration** where each GitHub organization is configured with its own `webhook_secret` under `secrets.github` [1](#0-0) , and `Shipit.github(organization:)` picks the correct `GitHubApp` (and thus the correct HMAC secret) purely from the organization name string [2](#0-1) .

### Title
Webhook signature is validated against `repository.owner.login`, but event handlers act on the independent `repository.full_name` field — cross-organization stack takeover - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, read from the JSON body as `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [3](#0-2) . The base `Handler` class that actually processes the event and mutates state, however, resolves the target repository using a **different, independently-controlled field**: `payload.dig('repository', 'full_name')` [4](#0-3) . Because the HMAC only proves "this body was signed with organization X's secret" and Shipit picks organization X purely from `repository.owner.login`, nothing forces `repository.owner.login` to be consistent with `repository.full_name` inside that same signed body.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository/stack the handler writes to`

In practice:
- `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and validates the signature using that org's `webhook_secret` [5](#0-4) .
- `repository_owner` is taken from `params.dig('repository', 'owner', 'login')` [6](#0-5) .
- Every handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) resolves what to act on via `Handler#stacks` / `#repository_name`, which reads `payload.dig('repository', 'full_name')` — a sibling key in the same JSON body, but not required to match `repository.owner.login` [4](#0-3) .
- `PushHandler#process` uses `stacks` (derived from `repository.full_name`) to call `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) .
- `StatusHandler#process` looks up commits purely by `sha` (global, not repo-scoped) and calls `commit.create_status_from_github!(params)`, with no repository/organization check at all [8](#0-7) .

Since HMAC verification only certifies that the *entire byte string* was signed by a particular secret, and Shipit's own code chooses *which* secret to check against based on an attacker-controlled field (`repository.owner.login`) that is decoupled from the field the business logic actually trusts (`repository.full_name`), an actor who legitimately controls (or has been granted, e.g. as a normal GitHub org admin/installer) a webhook secret for **any one** organization configured in Shipit can craft an arbitrary JSON body where:
- `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")`'s secret is used to compute a valid HMAC),
- `repository.full_name = "victim-org/victim-repo"` (so the handler acts on a stack belonging to a completely different, unrelated organization/repository).

This breaks cross-repository/cross-organization isolation: an attacker in control of one tenant's webhook secret can inject fabricated push/status events into another tenant's stacks, e.g., forcing `sync_github` to run against an arbitrary `expected_head_sha`, or forging CI `status` events (`state: "success"`) for arbitrary commits by SHA, which can trigger continuous-deployment (`Stack#schedule_merges`, `ContinuousDeliveryJob`) per `app/models/shipit/commit.rb` `add_status` logic.

### Impact Explanation
This maps to "cross-repository writes" / "an unauthorized deploy": forged `status` events for known commit SHAs can flip commit state to `success`, which (per `Commit#add_status`) can trigger `ContinuousDeliveryJob` and merge scheduling for a victim organization's stack, effectively causing an unauthorized deploy/merge without ever needing the victim organization's webhook secret, `github_access_token`, or an `ApiClient` token.

### Likelihood Explanation
Requires the attacker to legitimately control a webhook secret for at least one organization onboarded onto the shared Shipit instance (a realistic scenario for a multi-tenant Shipit deployment, which the engine explicitly supports via `github_app_config(organization)`). No privileged Shipit account, session, or victim secret is required — only knowledge of one's own tenant's webhook secret plus the ability to send a raw POST to `/webhooks`.

### Recommendation
In `Handler#repository_name` (and everywhere handlers resolve targets), cross-validate that `payload.dig('repository', 'owner', 'login')` (the field used for signature verification) matches the owner portion of `payload.dig('repository', 'full_name')` before processing, or better, pass the already-verified organization from `WebhooksController` down to the handlers and use it (rather than re-deriving repository ownership from unverified payload fields) to scope any repository/stack lookups.

### Proof of Concept
1. Attacker controls organization `attacker-org`'s GitHub App / webhook secret configured under `secrets.github.attacker-org.webhook_secret` in the shared Shipit instance.
2. Attacker crafts body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` HMAC-SHA1 using `attacker-org`'s known webhook secret over this exact body.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature [5](#0-4) .
5. `StatusHandler#process` finds `Commit.where(sha: "<victim-commit-sha>")` — belonging to `victim-org/victim-repo` — and calls `create_status_from_github!`, forging a successful CI status for the victim stack's commit and potentially triggering continuous delivery [8](#0-7) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end
