### Title
Cross-tenant status write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit by bare SHA across the entire database instead of scoping through the authenticated repository, unlike `PushHandler`/`Handler#stacks` which resolve via `Repository.from_github_repo_name(repository_name)`. Since git commit SHAs are content-addressed and identical across a fork and its upstream, a `status` webhook that GitHub genuinely signs for a repository the attacker owns (a fork) can flip the state of a `Commit` record belonging to a different stack/repository (the upstream "victim" production stack) that happens to already track the same SHA.

### Finding Description
The broken binding is: the handler should enforce `commit.stack.repository == authenticated_repository`, but instead it only enforces `commit.sha == params.sha`.

- `Shipit::WebhooksController#verify_signature` validates the HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload (`params.dig('repository','owner','login')`) [1](#0-0) [2](#0-1) . This check only proves the payload was genuinely emitted by GitHub for *some* org/repo configured in Shipit — it says nothing about which `Stack`/`Commit` the event is allowed to mutate.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
This performs a global lookup by `sha` alone, with no join/filter on `repository_name`/`repository_owner` from the payload. Compare this to `PushHandler#process`, which resolves the target set through `Handler#stacks`, itself scoped via `Repository.from_github_repo_name(repository_name)` [4](#0-3) [5](#0-4) . `StatusHandler` uses no such scoping at all.
- `Commit#create_status_from_github!` → `add_status` writes the status, and if the state transitions to `success`/`pending`, unconditionally schedules `stack.schedule_merges` and fires `deployable_status`/`commit_status` hooks for **that commit's actual stack** [6](#0-5) .

Exploit flow: the attacker owns/forks a repository whose git history includes a commit SHA that is also tracked by a victim's production stack (e.g., attacker forks the victim's public repo; forks retain identical SHAs for shared history). The attacker sets a commit status (`context: ci/e2e`, `state: success`) on their own fork via the GitHub API — a genuine GitHub action they are entitled to perform on a repo they own. GitHub signs and delivers this webhook using the credentials/secret associated with the attacker's own repo/org, which passes `verify_signature` because that check is scoped to the org that legitimately triggered it, not to the record being mutated. `StatusHandler` then finds *every* `Commit` row across *all* stacks with that SHA — including the victim's production stack's commit row — and applies the attacker's `success` status to it, potentially satisfying the victim's `required_statuses` (e.g., `ci/e2e`) and driving `schedule_merges`/deploy eligibility.

The `commits` table is indexed on `(stack_id, sha)`, i.e., SHA is not a global unique key but only unique per stack [7](#0-6) ; multiple stacks can and do independently store their own `Commit` row for the same SHA, and `StatusHandler` writes to all of them indiscriminately.

None of the existing guards prevent this: `verify_signature` authenticates the *sender* org, not the *target* commit's stack; `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler#process`.

### Impact Explanation
A `status` webhook that is genuinely authenticated for repository A can write a `Status` record and trigger `deployable_status`/`schedule_merges` for a `Commit` belonging to repository B's stack, as long as both repositories share a commit SHA (naturally the case for forks/upstream pairs, or any repos with shared git history). If the affected stack B is a production environment requiring `ci/e2e`, this can flip a commit to deployable/mergeable state without any legitimate CI signal from B's actual pipeline — a payload for one repository mutating another repository's stack/commit, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy, rollback or merge"). This is repeatable for any SHA shared between an attacker-controlled repo and a victim stack, and generalizes to any tenant/stack pair in a multi-tenant Shipit instance that shares commit history with an attacker-reachable repository.

### Likelihood Explanation
Preconditions: (1) the victim stack must already have ingested/synced the shared commit as a `Commit` row (normal operation for any tracked branch/PR history), (2) the attacker needs a repository they control whose git history intersects with the victim's (trivially satisfied by forking a public repo), (3) the attacker needs the ability to set a commit status on their own repo/fork via the GitHub API (routine, unprivileged capability), and (4) that repo must be wired to send webhooks to the same Shipit instance (multi-tenant/self-service Shipit setups where forks or secondary orgs can register repositories). Attacker cost is low — no Shipit secrets, sessions, tokens, or team membership are required, only standard GitHub write access to their own fork. It is fully repeatable per shared SHA.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`Handler#stacks` do: resolve the target `Repository`/`Stack` set from `payload.dig('repository', 'full_name')` first, and constrain the `Commit` lookup to `stack_id`s belonging to that repository (e.g., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), rejecting or ignoring statuses for SHAs that don't belong to any stack of the authenticated repository.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style):
1. Create two stacks/repositories, `victim_repo` (production environment, `required_statuses` includes `ci/e2e`) and `attacker_repo`, each syncing/owning a `Commit` row with the **same** `sha` (simulate shared git history).
2. Assert precondition equality is broken: before processing, `victim_commit.stack.repository.full_name != attacker_repo.full_name`, yet both `Commit` rows share `sha`.
3. Build a `status` webhook payload with `repository.full_name = attacker_repo.full_name`, `sha = shared_sha`, `context: 'ci/e2e'`, `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST to `/webhooks` with a stubbed valid signature for `attacker_repo`'s org).
5. Assert `victim_commit.reload.state == 'success'` for `ci/e2e` and that `victim_commit.stack.deployable_commits`/merge scheduling changed, even though the webhook only authenticated `attacker_repo` — proving the write crossed repository boundaries.

Note: full verification of multi-tenant repository/org registration flow (whether Shipit's config restricts webhook-emitting orgs to a fixed allowlist not self-serviceable by arbitrary GitHub users) could not be completed within available tool calls; this affects only the *likelihood* of an attacker obtaining a validly-signed webhook for an arbitrary "attacker repo," not the underlying code defect in `StatusHandler#process`, which is confirmed unscoped by direct code reading.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
