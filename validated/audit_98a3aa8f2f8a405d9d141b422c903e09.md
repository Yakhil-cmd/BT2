### Title
Webhook signature verified with the secret of an attacker-controlled organization but acted upon a `repository.full_name` belonging to any other tracked repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `repository_owner`, a value read straight out of the attacker-supplied JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every downstream `Handler` (e.g. `PushHandler`, `StatusHandler`, PR handlers), however, resolves the actual `Repository`/`Stack` to act on using a *different* field of the same body: `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`. Nothing ties these two fields together, so the "organization whose secret authenticated the request" and the "repository that is written to" are never checked for equality.

### Finding Description
In a multi-organization Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), each organization has its own `webhook_secret` in `config/secrets.yml`, and `Shipit.github(organization:)` looks the secret up per-organization [1](#0-0) .

`verify_signature` picks which organization's secret to validate against purely from attacker-controlled JSON, before the signature has even been checked: [2](#0-1) 

Any GitHub org owner who has installed the Shipit GitHub App on their *own* organization (a normal, unprivileged, self-service action, and one that Shipit's own docs describe every tenant performing) legitimately knows their own org's `webhook_secret`. They can craft an arbitrary raw JSON body, set `repository.owner.login` (or `organization.login`) to their own org so that `verify_signature` selects and successfully validates against their own known secret, but set `repository.full_name` to any *other* organization/repo that Shipit tracks (e.g. `victim-org/victim-repo`). Because the HMAC only proves "this body was signed with org A's secret," not "this body only concerns org A's repositories," the request passes signature verification and is routed straight into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .

Every handler then resolves the target repository purely from `full_name`, never re-checking it against the organization that supplied the valid signature: [4](#0-3) [5](#0-4) 

Concretely exploitable handlers include:
- `PushHandler`, which triggers `stack.sync_github(expected_head_sha: params.after)` for any branch/stack under the forged `full_name` [6](#0-5) .
- `StatusHandler`, which creates a CI status (`create_status_from_github!`) for an attacker-chosen `sha`/`state` on any `Commit` matching that sha across all tracked repositories - the handler does not scope by repository at all, only by `sha` [7](#0-6) .
- Pull-request handlers (`opened_handler.rb`, `closed_handler.rb`, `labeled_handler.rb`, etc.), which archive/unarchive review stacks or update pull request state for `params.repository.full_name` regardless of who actually authenticated the signature.

### Impact Explanation
The binding broken is: `organization authenticated by verify_signature` (derived from `repository.owner.login`) ≠ `organization whose repository/stack is mutated by the handler` (derived from `repository.full_name`). This lets an attacker who only controls one organization's webhook secret forge commit statuses (`StatusHandler`) or push events (`PushHandler`) for repositories belonging to *other* organizations onboarded onto the same Shipit instance. Forged green CI statuses on a victim's commit can unlock deploy safety checks (e.g. `deployable_status` gating), and forged push events can trigger `GithubSyncJob` against a victim stack — an unauthorized deploy-relevant state change performed with credentials scoped to a different organization.

### Likelihood Explanation
Requires Shipit to be configured for multiple organizations (documented, supported configuration) and requires the attacker to be an owner/admin of at least one of those organizations able to install/configure the Shipit GitHub App and read its own `webhook_secret` — no access to the victim organization or its secret is needed. This is a realistic multi-tenant misuse case, not a theoretical one, given the engine explicitly documents and supports the multi-organization secret scheme.

### Recommendation
In `verify_signature`, after selecting the organization-specific secret and validating the HMAC, also assert that `params.dig('repository', 'owner', 'login')` (or `organization.login`) matches the owner segment of `params.dig('repository', 'full_name')` before dispatching to handlers, rejecting the request (422) on mismatch. Alternatively, bind handler repository resolution to the same verified organization value used for signature selection rather than trusting `full_name` independently.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (secret `S_A`, known to the attacker who installed the App) and `victim-org` (secret `S_V`, unknown to the attacker), each tracking repositories/stacks.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` — this is trivial since they know `S_A`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature [8](#0-7) .
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (belonging to `victim-org/victim-repo`) and calls `create_status_from_github!`, forging a passing CI status the attacker never had credentials for [7](#0-6) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
