### Title
Stale `shared_address_signing_paths` records let a cosigner removed via `address_definition_change` keep receiving forwarded private-payment previews - ([File: wallet_defined_by_addresses.js])

### Summary
The CVE describes a case where Nextcloud kept honoring an incoming share's *original* permissions even after those permissions were revoked, letting the ex-recipient still preview file content. In ocore, the analogous "share" is a shared/multi-signature address, and the analogous "content preview" is the plaintext private-payment payload (address, blinding, amount) that gets pushed to every device once registered as a cosigner. Cosigner registration is recorded once in `shared_address_signing_paths` when the shared address is created, and this table is never revisited when a member address's own definition is later changed (i.e., a cosigner removed) via an `address_definition_change` message.

### Finding Description
When a shared address is created, `wallet_defined_by_addresses.js` inserts one row per member/cosigner into `shared_address_signing_paths` [1](#0-0)  (row: `shared_address, address, signing_path, member_signing_path, device_address`).

All later distribution of private-payment data relies exclusively on this static snapshot:
- `readAllControlAddresses` walks `shared_address_signing_paths` to find every device that must receive private chains for a payment address, with no reference to whether that member address's definition has since changed. [2](#0-1) 
- `forwardPrivateChainsToOtherMembersOfAddresses` similarly joins `shared_address_signing_paths` with `correspondent_devices` and forwards the full plaintext private elements (`arrChains`) to every listed device_address. [3](#0-2) 
- `forwardPrivateChainsToOtherMembersOfSharedAddresses` in `wallet.js` calls `readAllControlAddresses` and forwards to every returned device address whenever a private payment is sent/received on that shared address. [4](#0-3) 

None of these paths consult `address_definition_changes`/`definitions` to verify that the recorded device is still actually part of the *current* definition of the member address. Contrast this with `readAdditionalSigningAddresses`, which explicitly checks the latest `address_definition_changes` row to see whether an address's definition has become NULL/invalid before treating it as a signing address [5](#0-4)  — showing that the codebase is aware such revocation checks are necessary, but this check is absent from the private-payment forwarding logic.

Since ocore addresses can self-update their own definition (`address_definition_change`, validated in `validation.js` [6](#0-5)  and persisted in `writer.js` [7](#0-6) ), a legitimate owner can drop a cosigner from a shared/multisig address by changing that member address's definition (e.g., converting a 2-of-2 to a solo definition). However, the shared address's `shared_address_signing_paths` rows — and the removed cosigner's device address inside them — are never pruned or re-validated. Every subsequent payment into or out of the shared address will still be forwarded, via `network.handleOnlinePrivatePayment`/`wallet.handlePrivatePaymentChains`, to the removed party's device, disclosing the plaintext output address, blinding factor and amount of every future private-asset (e.g., blackbytes) transaction on that address.

### Impact Explanation
This causes a genuine confidentiality violation over private-asset payment data: a party whose signing rights were cryptographically revoked continues to receive full plaintext previews (address, blinding, amount) of every future private payment touching the shared address, without any spending capability check. This matches the CVSS profile of the original report (confidentiality impact only, no integrity/availability impact), and directly maps to the "private payment chains" and "address definitions and authentifiers" reachable surfaces called out in the validation rules.

### Likelihood Explanation
Any user of a shared/multisig address who rotates out a cosigner by posting a self-referencing `address_definition_change` will trigger this automatically on the next private payment — no attacker action beyond normal wallet usage is required, and the forwarding code path (`forwardPrivateChainsToOtherMembersOfAddresses` / `readAllControlAddresses`) executes unconditionally for every private payment involving that shared address.

### Recommendation
Before forwarding private-payment chains to a `shared_address_signing_paths` device address, re-verify against the member address's most recent stable `address_definition_changes`/`definitions` entry (the same pattern already used in `readAdditionalSigningAddresses`) to confirm the device is still part of the address's current definition; alternatively, actively update or invalidate `shared_address_signing_paths` rows whenever an `address_definition_change` affecting a member address is stabilized.

### Proof of Concept
1. Alice and Bob create a 2-of-2 shared address `S` (rows inserted into `shared_address_signing_paths` mapping Bob's device to `S`).
2. Alice and Bob later agree Bob is no longer a signer; Alice posts an `address_definition_change` on her own member address changing it to a solo definition, effectively removing Bob's spending capability over `S` going forward (definition-level revocation, no change to `shared_addresses`/`shared_address_signing_paths`).
3. Alice sends/receives a private-asset (e.g., blackbytes) payment through `S`.
4. `forwardPrivateChainsToOtherMembersOfSharedAddresses` → `readAllControlAddresses` still returns Bob's device address (stale row), and `walletGeneral.forwardPrivateChainsToDevices` sends Bob the full private elements chain, disclosing the private payment's address, blinding, and amount despite Bob no longer having any spending rights.

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
