The reported issue is specific to the `AuraStakingMixin.sol` / `BalancerPoolMixin.sol` Solidity vault contracts, where `_isInvalidRewardToken()` checks a reward token against a hardcoded list of pool tokens (`TOKEN_1`..`TOKEN_5`) established at initialization, and the actual reward token used at runtime is never part of that list, causing `reinvestReward()` to permanently revert. This is a config/initialization mismatch bug confined to that specific external vault contract's Solidity code — it is not part of the polkadot-sdk codebase.

I searched the relevant FRAME analogs that deal with token/asset swap validation and reward distribution:
- `pallet_asset_conversion`'s swap path validation (`validate_swap_path`) checks path uniqueness and asset-pair validity dynamically against actual pool state, not against a static list fixed at a separate initialization step disconnected from the swap logic [1](#0-0) .
- `pallet_nomination_pools`'s reward payout mechanism (`do_reward_payout`, `claim_payout`) tracks a single native reward currency via `RewardPool` counters, with no separate "reward token whitelist" step that could mismatch against runtime execution [2](#0-1) .

Neither of these subsystems has a structurally equivalent flaw: a static "valid token" set fixed at pool/config setup time that is later checked against a dynamically-determined reward/swap token, causing a permanent DoS of a privileged reinvestment-style call. The bug class here is inherently about an EVM vault's config wiring between two separate contracts (`AuraStakingMixin` and `BalancerPoolMixin`), and forcing this onto FRAME's asset-conversion or nomination-pools code would not be a faithful analog — it would require inventing a mismatch that doesn't exist in the actual pallet logic.
