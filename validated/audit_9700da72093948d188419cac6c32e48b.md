### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while repository resolution and mutation are bound to the unrelated `repository.full_name` field, allowing cross-tenant event forgery in multi-organization deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
In multi-GitHub-App configurations, `Shipit.github(organization:)` selects a different `webhook_secret` per organization [1](#0-0) . `WebhooksController#verify_signature` picks which secret to check the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) [2](#0-1) . Once the signature check passes, the actual event handlers (e.g. `PushHandler`) resolve which `Repository`/`Stack` to act on using `payload.dig('repository', 'full_name')` via `Handler#repository_name` and `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . These are two different JSON fields inside the same signed body, verified against a secret chosen from one field but semantically applied via another.

### Finding Description
The equality that should hold is: `organization whose secret authenticated the payload == organization/repository the payload is allowed to mutate`. Because both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same request body (an attacker who owns/controls one configured GitHub organization on the same Shipit instance can freely craft the JSON payload sent to their own app's webhook endpoint), an attacker who is a legitimate GitHub App installer for `org-attacker` (with its own `webhook_secret` known to them because they configured that GitHub App) can send a webhook whose `repository.owner.login` is `org-attacker` (so the signature check uses and passes with the secret they know) but whose `repository.full_name` is `org-victim/some-repo` — a repository belonging to a different organization configured in the same multi-org `secrets.yml` (`github.somegithuborg`, `github.someothergithuborg`, etc., as documented in `config/secrets.development.example.yml`) hosted by the same Shipit instance.

Since `verify_signature` only checks the signature against the secret for `repository_owner` and never cross-checks that `repository_owner` matches `repository.full_name`'s owner segment, the forged payload passes verification. `Handler#repository_name`/`Repository.from_github_repo_name` then look up and act on the victim organization's `Repository`/`Stack` using `full_name`, with no re-validation against the authenticated organization.

### Impact Explanation
This breaks the credential/authentication boundary between separately configured GitHub Apps sharing one Shipit deployment: an entity that is only supposed to be trusted for events belonging to its own organization can trigger `GithubSyncJob`, `commit_status` updates, `check_suite` refreshes, `membership`/`Team`/`User` creation, and `merge_status` mutations against a different organization's repositories and stacks — i.e., cross-repository/cross-organization writes triggered by forged webhook events, satisfying the "Critical - cross-repository writes" bar for this engine, since the write is not scoped to the org whose secret validated the request.

### Likelihood Explanation
This requires the deployment to be configured with more than one GitHub organization/App (the documented multi-org `secrets.yml` schema), and the attacker must control (or have been granted an install of) at least one of those configured GitHub Apps/organizations to legitimately know its `webhook_secret`. This is a realistic, supported, documented configuration in this engine and does not require compromising any other tenant's secret — only crafting a JSON body with mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
After signature verification succeeds, cross-check that the owner segment of `repository.full_name` (or `organization.login` for org-scoped events) matches the `repository_owner` that was used to select and validate the signing secret. Reject the webhook (422) if they don't match, closing the gap between the field that authenticates the request and the field that determines what gets mutated.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations, `org-attacker` and `org-victim`, each with distinct `webhook_secret`s, both pointing at the same `/webhooks` endpoint (per documented multi-org `secrets.yml`).
2. As the owner/installer of the `org-attacker` GitHub App, craft a `push` (or other handled) event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/some-repo"
  }
}
```
3. Sign the raw body with `org-attacker`'s known `webhook_secret` using HMAC-SHA1, set it as `X-Hub-Signature`, set `X-Github-Event: push`, and POST to `/webhooks`.
4. `verify_signature` selects `Shipit.github(organization: 'org-attacker')` and the signature validates successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('org-victim/some-repo')`, which is unrelated to the authenticated organization, and triggers `sync_github` against `org-victim`'s stack — a write against a repository the attacker's credential/secret was never scoped to.
