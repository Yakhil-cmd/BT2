### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but every event handler dispatches on the independently-attacker-controlled `repository.full_name` field, allowing a payload signed with one organization's webhook secret to be applied to a different organization's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the incoming HMAC against using `repository_owner`, which is read straight from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks` (and every subclass, e.g. `PushHandler`) resolves the target `Repository`/`Stack` using a *different* field from the same body: `repository.full_name`. Nothing enforces that `full_name`'s owner matches `repository.owner.login`. In a multi-organization Shipit deployment (explicitly supported per `config/secrets.development.example.yml`, where each org has its own `webhook_secret`), an attacker who legitimately controls the webhook secret for one configured organization can forge a payload whose `owner.login` is their own org (so the HMAC check passes) while `full_name` names a repository belonging to a different, victim organization also tracked by the same Shipit instance.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to fetch the org-specific `GitHubApp` instance, whose `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) checks the `X-Hub-Signature` HMAC against that org's `webhook_secret`. **Binding broken (as an equality):**
`organization authenticated (repository.owner.login used to pick webhook_secret)` ≠ `organization/repository written (repository.full_name used by handler to select Stack)`.

Before the attack, both fields are expected to describe the same GitHub repository (as GitHub itself always sends a payload where they match). After the attacker's forged request, `owner.login` = attacker's own org (whose secret they know/control) while `full_name` = `victim-org/victim-repo`, and the code performs no cross-check between the two.

### Impact Explanation
This breaks the deployment-trust boundary between organizations hosted on the same Shipit instance. With a payload crafted this way an attacker who is only entitled to send events for their own organization can:
- Trigger `push`/`GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha` (`PushHandler#process`), which is used elsewhere to drive stack syncing/deploy state.
- Archive/unarchive review stacks, alter `PullRequest` labels/state, or force provisioning of review stacks for a `Stack` owned by a completely different organization (`opened_handler.rb`, `labeled_handler.rb`, `reopened_handler.rb`, `label_capturing_handler.rb`).

This is a cross-organization write into stack/task/pull-request state that the attacker has no authorization for, matching the "cross-repository writes" / unauthorized-state-mutation class in scope. It requires no compromise of the victim org's webhook secret, `ApiClient` token, or GitHub credentials — only that the attacker legitimately controls one org configured on the shared Shipit instance.

### Likelihood Explanation
Exploitability depends entirely on a deployment configuring more than one GitHub organization against a single Shipit instance (which is an explicitly documented and supported configuration, per `config/secrets.development.example.yml`'s multi-org `github:` block). In such setups, any org owner/admin who can configure a GitHub App/webhook for their own org (a routine, unprivileged-with-respect-to-Shipit action) can send this forged webhook directly to Shipit's public `/github/webhooks` endpoint without needing to intercept or brute-force anything — they simply reuse their own valid `X-Hub-Signature` on a body whose nested `repository.full_name` differs from `repository.owner.login`.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to resolve the webhook secret is the same organization embedded in `repository.full_name` for every handled event — e.g., derive `repository_owner` strictly from `full_name`'s prefix (or explicitly compare `full_name.split('/').first` against `owner.login` and reject on mismatch) before dispatching to handlers. Handlers should not trust `full_name` as authoritative for repository resolution unless it has been validated against the same organization whose secret authenticated the request.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as supported by the multi-org `github:` config block).
2. Attacker registers/owns a GitHub App or webhook pointed at Shipit for `attacker-org` and thus knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s webhook secret and POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` (from `owner.login`) and the HMAC check succeeds since the attacker signed with the correct secret for that org.
6. `PushHandler#process` runs `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` for `victim-org`'s stack with the attacker's chosen `expected_head_sha`, despite the request never being authenticated by `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
