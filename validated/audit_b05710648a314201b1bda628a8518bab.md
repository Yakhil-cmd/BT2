### Title
Cross-tenant Team hijack via `MembershipHandler` reusing `github_id` without re-validating `organization` ownership - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
In a multi-organization Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), each tenant organization has its own `webhook_secret` selected purely from attacker-controlled JSON fields (`repository.owner.login`/`organization.login`). `MembershipHandler#find_or_create_team!` looks up `Shipit::Team` solely by `github_id`, and only sets `team.organization` on record creation, so a legitimately-signed `membership` webhook from tenant org B referencing an existing team's `github_id` (belonging to tenant org A) will mutate org A's `Team` via `team.add_member(member)` without any check that the verified webhook organization still matches `team.organization`.

### Finding Description
The broken binding: `team.organization` (persisted at creation time) must equal `params.organization.login` of the currently verified webhook for every mutation, but the code never enforces this after the initial `find_or_create_by!`.

Path:
1. `Shipit::WebhooksController#verify_signature` picks the HMAC secret via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` — both attacker-supplied JSON fields [1](#0-0) .
2. `Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per configured organization key in `secrets.github` [2](#0-1) .
3. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` — the block (and thus the organization assignment) only executes on record **creation** [3](#0-2) .
4. If a `Team` with that `github_id` already exists (created earlier for org A), `find_or_create_by!` returns the existing record untouched, and `team.add_member(member)` (using `params.member.login`, arbitrary attacker-chosen) is executed against org A's team regardless of which organization actually signed the current webhook [4](#0-3) .

The base `Handler` class provides no cross-check between the verified webhook organization and any model already scoped to a different organization [5](#0-4) . `ExplicitParameters` schema only enforces types/presence, not that `params.team.id` corresponds to a team actually owned by `params.organization.login` [6](#0-5) .

Attacker requirement: control of (or being onboarded as) a legitimately configured second tenant organization "org-b" in the multi-org `secrets.github` config, with its own real `webhook_secret`. This is the documented "Using Multiple Github Applications" model. Using that org's own legitimate, correctly-signed webhook, the attacker crafts a `membership` "added" event with `organization.login: "org-b"` (so signature verification passes against org-b's own secret) but `team.id` set to a known/guessed `github_id` of an existing `Shipit::Team` belonging to a different tenant, org A, and `member.login` set to the attacker's own GitHub login. Shipit accepts the request (signature verified against org-b), and `MembershipHandler` adds the attacker as a `Membership` of org A's `Team`, while `team.organization` remains `"org-a"`, unchanged.

### Impact Explanation
The attacker gains an unauthorized `Membership` in a `Shipit::Team` that they were never invited to and do not administer, silently escalating `Shipit::User#authorized?` if that team is among `Shipit.github_teams` [7](#0-6) . This matches the "payload for one repository/tenant mutating another's team" Critical category — one tenant's legitimately signed webhook silently mutates another tenant's authorization-relevant record. It is repeatable for any `github_id` the attacker can guess or discover (team IDs are visible via various GitHub API responses) and is not limited to a single victim team; blast radius spans every cross-org `Team` collision reachable via the shared, per-org-keyed but globally-scoped `github_id` lookup.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where the attacker legitimately administers a second onboarded GitHub organization (with its own `webhook_secret` in `secrets.github`) — a configuration explicitly supported and documented by this engine. No Shipit session, API token, or victim-org secret is needed; only the attacker's own tenant's `webhook_secret`, and knowledge/guessing of a target team's numeric `github_id`. Cost is a single crafted, correctly-signed HTTP POST to `/webhooks`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, after resolving the team, validate `team.organization == params.organization.login` (raise/drop the event otherwise) rather than only setting `organization` on creation; alternatively scope the `find_or_create_by!` lookup by both `github_id` and `organization`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations

  end
