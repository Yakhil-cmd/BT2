### Title
Unsynchronized concurrent AA dry-runs corrupt shared unit caches — `light/dry_run_aa` race condition ([File: aa_composer.js])

### Summary
The `light/dry_run_aa` network command lets **any peer** trigger a full, unauthenticated execution of `aa_composer.dryRunPrimaryAATrigger()` for an arbitrary AA address and attacker-controlled trigger payload, with **no mutex protection** whatsoever. Every other code path that mutates the same global in-memory unit caches (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocStableUnitsByMci`) is serialized by a mutex — real joint validation/writing via `mutex.lock(['handleJoint'])`/`mutex.lock(['write'])`, and real AA-trigger execution via `mutex.lock(['aa_triggers'])`. `light/dry_run_aa` has none of these locks, so multiple concurrent dry-run requests (or a dry run racing a real unit write) can interleave their cache mutations/reverts, corrupting shared state that the rest of the node relies on for consensus-critical decisions (is_free flags, best-parent selection, stability).

### Finding Description
`network.js` dispatches the unauthenticated command directly to the AA composer without acquiring any lock: [1](#0-0) 

`dryRunPrimaryAATrigger` takes its own DB connection (each call gets a fresh one from the pool) and calls `handleTrigger`, which for real messages goes through `sendUnit` → `validateAndSaveUnit` → `writer.saveJoint`, mutating process‑global caches directly: [2](#0-1) [3](#0-2) 

Crucially, `validateAndSaveUnit` sets `objAAValidationState.bUnderWriteLock = true`, and `writer.saveJoint` explicitly skips acquiring the global `"write"` mutex whenever this flag is set: [4](#0-3) 

This design is safe for the legitimate call sites because they are each individually serialized by an outer lock (`mutex.lock(['aa_triggers'])` for real trigger processing, `mutex.lock(['handleJoint'])` for locally‑posted units). `light/dry_run_aa`, however, calls into this exact same "already under write lock" code path **without ever taking any lock**, so nothing prevents two (or more) concurrently-dispatched dry runs — or a dry run and a real unit write/trigger — from interleaving their mutations to the shared caches.

After the dry run finishes, cleanup is performed by `revertResponsesInCaches`, which assumes the response unit it created is still present in `storage.assocUnstableUnits`: [5](#0-4) 

If a second, concurrently-running dry run (or a real trigger/joint write happening in the interleaved gap) has already removed/rewritten that same unit key from `storage.assocUnstableUnits` — entirely plausible because both dry runs can pick overlapping temporary unit hashes derived from the same `objMcUnit`/`GENESIS_UNIT` placeholder logic (`trigger.unit = constants.GENESIS_UNIT`) and freely mutate the shared `assocUnstableUnits`/`assocBestChildren` maps — then `objFirstUnit` is `undefined` and `objFirstUnit.parent_units` throws, or, short of throwing, the shared caches end up holding stale/incorrect `is_free`, `best_parent_unit`, or `parent_units` bookkeeping that real unit validation subsequently reads from (`writer.js` reads/writes `storage.assocUnstableUnits[...]` and `storage.assocBestChildren[...]` unconditionally when saving any real unit): [6](#0-5) 

This is the same fundamental bug class as CVE‑2025‑8880 (a race in V8 caused by concurrently executing code paths mutating shared engine state without adequate synchronization): here, a remotely reachable, unauthenticated request path (`light/dry_run_aa`) mutates process‑wide shared state that the consensus‑critical write path assumes is exclusively guarded, without itself participating in that guard.

### Impact Explanation
Corruption of `storage.assocUnstableUnits` / `storage.assocBestChildren` / `storage.assocStableUnitsByMci` affects best‑parent selection, `is_free` bookkeeping, and witnessed‑level computation used by every subsequent real unit validation and AA trigger on that node. Depending on the exact interleaving:
- The node process can crash (uncaught `TypeError` from `objFirstUnit.parent_units` on `undefined`), a remotely triggerable DoS against a full node's ability to validate/relay new units.
- Silent corruption of the unstable-unit graph can cause the node to compute a different best parent / stability outcome than the rest of the network for legitimately posted units, i.e., **node disagreement on validity/stability** — one of the explicitly in-scope impacts.
- Because AA response construction, storage-size tracking, and balance updates flow through the same `handleTrigger`/`saveJoint` machinery, a corrupted cache state increases the risk of AA fund-accounting divergence (loss/freezing) on the affected node.

### Likelihood Explanation
`light/dry_run_aa` is reachable by any connected peer without authentication, requires no special privileges, and an attacker fully controls the `trigger` and `address` parameters (subject only to `validateAATriggerObject`). Triggering many concurrent dry runs against the same or interacting AAs (which is normal client behavior for wallets estimating AA responses before sending) is trivial and cheap. The race window exists on every call because the function performs multiple asynchronous DB round-trips (`BEGIN`, several `SELECT`s, formula evaluation, `ROLLBACK`) while directly mutating unlocked global JS objects.

### Recommendation
Serialize `light/dry_run_aa` (and any other unauthenticated caller of `dryRunPrimaryAATrigger`/`estimatePrimaryAATrigger`) behind the same lock domain used for real AA trigger execution (e.g., `mutex.lock(['aa_triggers'])`) or a dedicated `dry_run` lock that is mutually exclusive with `write`/`handleJoint`/`aa_triggers`, so cache mutation/reversion in `handleTrigger`/`revertResponsesInCaches` can never interleave with another dry run or a real write. Additionally, make `revertResponsesInCaches` defensive (no-op / log instead of throwing) if the expected unit is missing from `storage.assocUnstableUnits`, and audit `writer.saveJoint`'s `bUnderWriteLock` bypass to ensure it can only be reached from call sites that are provably serialized.

### Proof of Concept
1. Deploy or reference any valid AA definition.
2. As an unauthenticated peer, open a connection and rapidly fire many concurrent `light/dry_run_aa` requests (different `tag`s) with a valid `trigger`/`address`, interleaving requests that hit the same or chained AAs so their generated temporary response-unit hashes/cache keys collide or overlap in timing.
3. Observe that `revertResponsesInCaches` throws (crashing the node) or that subsequent normal joint validation reflects incorrect `is_free`/best-parent state derived from the corrupted `storage.assocUnstableUnits`/`assocBestChildren` maps — verifiable by comparing `storage.assocUnstableUnits` before/after concurrent dry runs against the same units.

(Note: I was unable to fully execute this against a live full node to confirm the exact crash trace due to the read-only nature of this analysis; the race window and missing lock are confirmed by direct code inspection of `network.js`'s `light/dry_run_aa` handler versus the locking discipline used by every comparable call site.)
