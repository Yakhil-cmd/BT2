### Title
`StatusHandler#process` mutates commits by SHA with no check that the webhook's `repository` matches the commit's own stack/repository — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!` on every match, with no join or check against `params['repository']['full_name']`, `stack_id`, or any tenant/org boundary. Because commit SHAs are public, deterministic and knowable without any secret, a caller who only holds a valid webhook signature for their own onboarded repository/organization can mutate the CI status of a commit that belongs to a completely different `Stack`/`Repository`, as long as that SHA string happens to already exist as a row in Shipit's `commits` table for some other tenant.

### Finding Description
The binding claimed broken is: `authenticated_repository(payload) == mutated_repository(commit.stack)`. Tracing the code:

- `WebhooksController#create` parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` passes. [1](#0-0) 
- `verify_signature` resolves `Shipit.github(organization: repository_owner)` from the attacker-supplied `repository.owner.login` field and verifies the HMAC signature against that organization's configured `webhook_secret` (a value only the Shipit operator/GitHub App owner controls, per `secrets.github`). [2](#0-1) [3](#0-2) 
- This authenticates "a request signed for organization X," not "a request scoped to repository Y." Once past that gate, `StatusHandler#process` does: [4](#0-3) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
There is no filter comparing `params.dig('repository','full_name')` (or the authenticated organization) to `commit.stack.repository`. `create_status_from_github!` then calls `add_status` → `statuses.replicate_from_github!(stack_id, github_status)`, directly writing a `Status` row (state/description/target_url/context) tied to that commit's `stack_id`. [5](#0-4) [6](#0-5) 

`Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, so injecting a `success` status on a blocking CI context can flip a victim commit into a deployable state. [7](#0-6) 

Neither `Shipit.github_teams`, `current_user`, nor any `require_permission!`-style check is ever consulted anywhere in this path — confirmed by `StatusHandler` inheriting only `Handler`'s `params` DSL and `process` contract, with no authorization override. [8](#0-7) 

**Correction to the premise in the question**: `webhook_secret` in this codebase is not a per-`Repository` secret that "any user who can add the Shipit webhook to a repo they administer" can set. It is a server-side value configured by the Shipit operator in `secrets.github[org].webhook_secret` (or a single global secret in legacy single-app mode), matched against the GitHub App configuration. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) genuinely cannot be forged by an attacker who does not already possess that operator-controlled secret — per the rules, such an attacker holds no `webhook_secret` at all, so a pure "signature forgery" reading of this question does not hold.

However, the underlying multi-tenant authorization gap is real: `Shipit.github` supports multiple organizations each with their own `webhook_secret` (`lib/shipit.rb:170-200`, `github_organizations`), meaning a party that legitimately administers *one* onboarded org/repo (and thus legitimately possesses that org's real webhook secret) can send a genuinely-signed `status` event whose `sha` field names a commit belonging to a *different* org/stack. Since `StatusHandler` never checks that the commit's stack/repository matches the payload's `repository`, that legitimately-signed-but-wrong-tenant request still mutates the victim's commit status.

### Impact Explanation
A tenant that legitimately controls only their own webhook credential can write `Status` rows against a commit belonging to an unrelated `Stack`/`Repository`, because `StatusHandler#process` performs a global, unscoped `Commit.where(sha:)` lookup. This can flip a victim commit's `deployable?` result (e.g., forging a `success` status on a blocking CI context), which is squarely in the "payload for one repository mutating another's stack, commit" Critical category. Blast radius is any commit anywhere in the instance whose SHA the attacker already knows (SHAs are public, non-secret git identifiers), and the write is repeatable per request with no rate limiting relevant here. The `Shipit.github_teams`/`current_user`/`require_permission!` layer is never consulted anywhere on this path, confirming there is no authorization boundary beyond "some valid signature for some org."

### Likelihood Explanation
Requires the attacker to legitimately control at least one org/repo already onboarded into the shared multi-tenant Shipit instance (so they possess a real, operator-issued `webhook_secret` for that org) — this is a normal, low-privilege situation for any customer of a shared Shipit deployment. It does not require guessing or brute-forcing the victim's secret, GitHub session, or any Shipit credential; only the target commit's SHA, which is typically public. Feasibility is high in any Shipit deployment shared across more than one team/org; repeatable per known SHA.

### Recommendation
In `StatusHandler#process` (and analogously in `CheckSuiteHandler`/other SHA-keyed handlers), scope the `Commit` lookup to the repository/organization actually authenticated by `verify_signature`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.dig('repository','full_name') })`, or thread the authenticated `repository_owner`/`full_name` through `Webhooks::Handlers::Handler.call` and assert it against `commit.stack.repository.full_name` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status from org A's authenticated webhook mutates org B's commit sharing the same sha" do
  victim_commit = shipit_commits(:first) # belongs to stack/repo "org-b/repo-b"
  attacker_repository_params = { 'repository' => { 'owner' => { 'login' => 'org-a' } } }

  body = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/blocking'
  }.merge(attacker_repository_params).to_json

  request.headers['X-Github-Event'] = 'status'
  # Only org-a's webhook_secret is used/verified — no reference to org-b or Shipit.github_teams
  Shipit.github(organization: 'org-a').stubs(:verify_webhook_signature).returns(true)

  assert_difference 'victim_commit.statuses.count', 1 do
    post :create, body:, as: :json
  end

  status = victim_commit.statuses.last
  assert_equal 'success', status.state
  assert_equal victim_commit.stack_id, status.stack_id # mutated org-b's stack despite org-a's credential
end
```
This demonstrates: (1) only `org-a`'s webhook signature is verified, (2) no call to `Shipit.github_teams`, `current_user`, or any permission check occurs on this path, and (3) `victim_commit` — belonging to a different repository/stack — is mutated anyway, confirming the `Commit.where(sha:)` lookup in `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` crosses tenant boundaries.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
