### Title
Stale `DelegateGrant` re-arms when the position NFT returns to the granting owner - ([File: contracts/controller/src/storage/account.rs](contracts/controller/src/storage/account.rs))

### Summary
The controller stores account delegates as a single `DelegateGrant` per account stamped with `granted_by`. On NFT transfer the grant is not deleted; `get_delegates` merely filters it out while `granted_by != current owner`. If the NFT later returns to the original granter (e.g., sold and repurchased, or transferred back), the stale delegate list silently reactivates, and every previously registered delegate regains full account authority — including `withdraw`/`borrow` to arbitrary recipients.

### Finding Description
`get_delegates` returns the stored delegate list only when `grant.granted_by == *owner` (`contracts/controller/src/storage/account.rs:176-181`). Nothing clears `ControllerKey::Delegates(account_id)` on NFT transfer: the NFT contract (`contracts/position-nft`) only moves ownership, and per its README, "the stale grant stays in storage and re-arms if the token returns to `granted_by`." An intervening owner's `add_delegate` overwrites the grant and `remove_delegate` deletes it (`account.rs:203-247`), but if the intervening owner never manages delegates — the common case — the original grant survives intact.

Delegates are granted via `add_delegate` (owner-called, requires a governance-activated position manager) and are authorized by `is_owner_or_delegate` on controller entrypoints (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, strategy ops). Delegates may specify arbitrary recipients, so a re-armed delegate can drain the account's collateral or take debt-funded withdrawals to an address it controls. Owner `A` delegates to `D` → `A` transfers NFT to `B` → `B` transfers back to `A` (or `A` buys the position NFT on a market) → `D`, now possibly adversarial or compromised, calls `withdraw(caller=D, account_id, withdrawals, to=D-controlled)` and steals collateral.

### Impact Explanation
Theft of user funds: a previously-approved delegate whose grant the owner reasonably believed dead can withdraw account collateral or borrow against it to an arbitrary recipient once ownership round-trips back to `granted_by`. Directly mirrors the confirmed OpenDollar `safeCan` finding: permissions stamped under an old owner persist through transfer and reactivate on return.

### Likelihood Explanation
Medium. Requires three conditions: (1) the owner granted a delegate that is never overwritten by an intervening owner, (2) the NFT returns to the original granter, (3) that delegate is now malicious. Delegates require active global position-manager registration, narrowing the attack surface to registered manager contracts. Still fully reachable by an unprivileged delegate address once re-armed.

### Recommendation
Clear `ControllerKey::Delegates(account_id)` on every ownership change — e.g., a controller callback invoked by `position-nft` `transfer`/`transfer_from`, or store the grant keyed/stamped per (owner, transfer epoch) rather than re-checking `granted_by` at read time. At minimum, document the re-arm risk at `add_delegate` and prefer deleting the stale entry instead of preserving it.

### Proof of Concept
1. Alice mints account NFT `id` via controller `supply` (creates account + position).
2. Governance activates manager `M` (`SetPositionManager`); Alice calls `add_delegate(id, M)` → `DelegateGrant{granted_by: Alice, delegates:[M]}` stored (`account.rs:185-199`).
3. Alice calls `position_nft.transfer(Alice → Bob, id)`. `get_delegates(id, Bob)` reads empty; `M` is denied.
4. Bob calls `position_nft.transfer(Bob → Alice, id)`. `granted_by == Alice` again → `M` is authorized (`account.rs:176-181`).
5. `M` calls `controller.withdraw(caller=M, account_id=id, withdrawals=[collateral], to=attacker_addr)` — `is_owner_or_delegate` passes, funds leave to `M`'s chosen recipient.
