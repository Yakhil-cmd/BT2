### Title
Membership webhook trusts attacker-supplied `team.id` and mutates any existing `Team` regardless of which org signed the payload - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `params.team.id` (`Team.find_or_create_by!(github_id: params.team.id)`) and `#process` then calls `team.add_member(member)` without ever verifying that `params.organization.login`/`repository_owner` (the org whose secret validated the webhook signature) matches the `organization` that owns the found `Team` record.

### Finding Description
The claimed binding — `repository_owner used to verify the signature` == `Team#organization for the github_id referenced in the payload` — is **false** in the code.

Path:
- `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves the org solely from `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`, line 61) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature`. This proves only that *some* org's configured `webhook_secret` matches — for a multi-tenant Shipit install (documented in `docs/setup.md` "Using Multiple Github Applications" and exercised by `test/dummy/config/secrets_double_github_app.yml`), each org has its own independent secret, so a payload can be legitimately signed by "attacker-org" while claiming to reference a team belonging to a completely different org.
- `MembershipHandler#process` and `#find_or_create_team!` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`) then do:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
```
`find_or_create_by!` looks up strictly by `github_id`. If a `Team` with that numeric id already exists (created for a legitimate, unrelated org), the block (which would set `organization`) never runs — the existing record is returned as-is — and `team.add_member(member)` (`Team#add_member`, `app/models/shipit/team.rb:41-43`) unconditionally appends the attacker-controlled `User` to that team's `memberships`.

Nowhere in this call chain is `params.organization.login` (or `repository_owner`) compared against the found `Team#organization`. The only real gate is the HMAC signature check, and that check authenticates "a message signed by org X's secret," not "a message about org X's teams." Since `team.id` is an attacker-supplied integer in the JSON body, an attacker who legitimately owns/administers any GitHub organization onboarded into the same multi-tenant Shipit instance (i.e., can produce a validly-signed membership webhook for their own org) can reference any other org's numeric `github_id`s in that payload.

### Impact Explanation
`Team` records referenced by `Shipit.github_teams` gate `User#authorized?` (`app/models/shipit/user.rb:80-82`) and are used across `Authentication#force_github_authentication` to grant access to the whole Shipit UI/API for stacks, deploys, rollbacks, etc. Successfully forging membership into such a team is a direct authorization-bypass escalation (matches the "escalation into `Shipit.github_teams` authorization" High-severity category). The blast radius is any tenant/org sharing the same Shipit instance in a multi-org configuration; the attacker's own org's signature is enough to mutate a `Team` belonging to a victim org. The attack is repeatable for every guessable/observed numeric `github_id`.

### Likelihood Explanation
Exploitability strictly requires: (1) the Shipit deployment to be multi-tenant (multiple GitHub orgs configured under `secrets.github`, each with independent `webhook_secret`), and the attacker controlling at least one of those onboarded orgs to legitimately trigger a correctly-signed `membership` webhook for it; or (2) a deployment where `webhook_secret` is left blank for the relevant org, in which case `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) returns `true` unconditionally (`return true unless webhook_secret`), letting anyone forge a signature entirely. In either configuration, the attacker only needs to know or guess the victim team's numeric `github_id` (GitHub team ids are often discoverable via the API/UI to team members or organization members, and are sequential/enumerable). No Shipit session, API token, or Shipit secret is required. This is a low-cost, fully repeatable attack once a signable payload is obtainable.

### Recommendation
In `find_or_create_team!`, scope the lookup by both `github_id` and the verified `organization` (e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: repository_owner)` derived server-side, not merely `params.organization.login`), and raise/reject if an existing `Team` with that `github_id` belongs to a different organization than the one that verified the webhook signature. `MembershipHandler` should receive/consult the verified `repository_owner` rather than trusting the payload's `organization.login` field for the org identity used in comparisons.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from a different org cannot escalate members into a team owned by another org" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: known value
  attacker_user_login = 'attacker-user'

  @request.headers['X-Github-Event'] = 'membership'
  # Signed validly for 'attacker-org' (stub/verify against attacker-org's own webhook_secret)
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'u' },
    organization: { login: 'attacker-org' },
    member: { login: attacker_user_login }
  }.to_json

  assert_no_difference -> { victim_team.members.count } do
    post :create, body: payload, as: :json
  end
  # Binding check: verified org != team.organization must be rejected
  refute victim_team.reload.members.exists?(login: attacker_user_login)
end
```
Currently this test would **fail** (the attacker's user is added to `victim_team.members`), demonstrating the broken binding between the org that signs the webhook and the org that owns the `Team` record being mutated.
