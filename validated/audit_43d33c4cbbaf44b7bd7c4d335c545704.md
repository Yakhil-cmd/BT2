### Title
Missing bounds/type validation on Merkle proof siblings in `in merkle` address-definition authentifier evaluation - (File: definition.js)

### Summary
The `in merkle` address-definition operator, used to authenticate an address/AA-trigger author against an oracle-posted data feed root, deserializes an attacker-supplied `serialized_proof` (the authentifier value for that path) and feeds it into `merkle.verifyMerkleProof` without the same length/shape validation that was later added to the analogous `is_valid_merkle_proof()` oscript function.

### Finding Description
In `definition.js`, the `in merkle` case of `validateAuthentifiers` takes the raw authentifier string supplied by the unit's/AA-trigger's author and deserializes it directly: [1](#0-0) 

`merkle.deserializeMerkleProof` performs no validation of its input at all — it simply splits the string on `-` and assigns `root`, `index`, and `siblings`: [2](#0-1) 

`verifyMerkleProof` then iterates over `proof.siblings` and hashes them together with the element, wrapped only in a generic try/catch that swallows any exception and treats it as an invalid proof: [3](#0-2) 

Contrast this with the AA/oscript equivalent, `is_valid_merkle_proof`, in `formula/evaluation.js`, where an explicit fix (`bPostPemCurvesFix`) was added to cap the serialized proof string length (1024 bytes) and to require that `siblings` be an array of non-empty strings with at most 50 elements: [4](#0-3) 

The `in merkle` authentifier path in `definition.js` never received this same hardening. The only general limit that applies to the raw authentifier string is `MAX_AUTHENTIFIER_LENGTH`, enforced generically for all authentifiers in `validateAuthor`/`validateSignedMessage`, not specifically tuned for Merkle-proof cost: [5](#0-4) 

Because `deserializeMerkleProof` does not sanitize `siblings`, malformed/degenerate authentifier strings (e.g., consecutive dashes producing empty-string siblings, or highly repetitive `-`-separated content up to the generic authentifier length cap) are processed unchecked by the hashing loop, and the number and shape of "siblings" is bounded only by the coarse generic authentifier length limit rather than the same tight, purpose-built limit (50 siblings / 1024 bytes) applied to the AA oscript equivalent.

### Impact Explanation
An address (or AA trigger sender / paired-device authentifier) using an `in merkle` condition in its definition is validated with a Merkle-proof evaluation path that is inconsistent with, and weaker than, the hardened `is_valid_merkle_proof` oscript function. This inconsistency means:
- Nodes evaluating the same authentifier could, in edge/degenerate cases (e.g., proof strings shaped to abuse the coercion of `proof.index` from string to number, or empty-string sibling segments), diverge in behavior from what the hardened oscript path would produce for structurally equivalent input, which is a node-disagreement-on-validity concern for units relying on `in merkle` authentication.
- The unbounded number of siblings (up to the size allowed by `MAX_AUTHENTIFIER_LENGTH`, which is much larger than the 50-sibling cap enforced for `is_valid_merkle_proof`) allows more expensive proof verification per authentifier evaluation than the AA path intentionally restricts to, undermining the purpose of the later-introduced cap.

Because the actual cryptographic verification is still performed with SHA-256 and wrapped in try/catch, this does not, on its own, produce a crash, and I could not establish a concrete forged-membership or fund-loss path (unlike the CVE-2012-2459-style duplicate-node malleability that the `verifyMerkleProof` comment itself flags as a known limitation, but exploiting that class of issue would require oracle cooperation and does not directly transfer into unauthorized spending here). Given the uncertainty about a concrete unauthorized-spend/double-spend/inflation/freeze outcome, this analog is best treated as Medium severity based on the code-inconsistency/hardening-gap alone, not on a demonstrated forged-authentication exploit.

### Likelihood Explanation
Any address, AA, or shared-wallet definition that uses `in merkle` as an authentication condition is affected. Reaching this code path only requires posting a unit/AA trigger whose author's authentifier map includes a value at the `in merkle` path — well within reach of any unprivileged unit poster or AA trigger sender that has such a definition. No special privileges are needed to supply the malformed/oversized `serialized_proof` value; the barrier is only the generic `MAX_AUTHENTIFIER_LENGTH` cap.

### Recommendation
Apply the same validation used for `is_valid_merkle_proof` to the `in merkle` authentifier evaluation in `definition.js`:
- Enforce a maximum length on `assocAuthentifiers[path]` before calling `merkle.deserializeMerkleProof` (mirroring the 1024-byte cap).
- After deserialization, validate that `proof.siblings` is an array of non-empty strings and cap its length (e.g., 50), and validate/coerce `proof.index` to a proper non-negative integer before use.
- Consider moving this validation into `merkle.deserializeMerkleProof`/`verifyMerkleProof` themselves so all call sites (both the definition-based authentifier path and the oscript function) share one hardened implementation, preventing future divergence.

### Proof of Concept
1. Create/observe an address (or AA) definition containing `["in merkle", [[oracle_address], "feed_name", "some_element"]]`.
2. As the unit author, compose a unit where the authentifier for that path is a crafted string such as `"0-----<many-empty-or-oversized-segments>--<root>"` (bounded only by `MAX_AUTHENTIFIER_LENGTH`, not by the 50-sibling/1024-byte limits enforced for `is_valid_merkle_proof`).
3. Submit the unit; `validateAuthentifiers`’s `in merkle` case (`definition.js:1004-1020`) will call `merkle.deserializeMerkleProof` and `merkle.verifyMerkleProof` on this oversized/malformed input without the checks present in `formula/evaluation.js:1786-1797`, demonstrating the validation gap between the two code paths that are meant to implement equivalent semantics.

*Note: I was unable to fully trace a concrete exploit chain resulting in unauthorized spending or consensus divergence within the available investigation budget; the finding is limited to demonstrating the unpatched-validation-gap itself, which is the closest reachable analog to the reported "unvalidated hash-like input" bug class in ocore.*

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
