### Title
Missing owner-authority check on withdrawal destination token accounts allows redirecting withdrawn funds to an attacker-controlled account - (File: programs/cp-swap/src/instructions/withdraw.rs)

### Summary
In the `Withdraw` instruction, the destination accounts `token_0_account` and `token_1_account` are only constrained by `token::mint = token_x_vault.mint`, unlike the equivalent `Deposit` instruction's accounts which additionally enforce `token::authority = owner`. This omission lets the transaction's account list direct the withdrawn underlying tokens to any token account of the correct mint, not necessarily one owned by the withdrawing user, mirroring the "user-chosen receiver" phishing pattern described in the reference report.

### Finding Description
`Withdraw` requires the `owner` to sign and burns the owner's LP tokens, but the accounts that actually receive the underlying `token_0`/`token_1` are only checked against the vault's mint: [1](#0-0) 
There is no `token::authority = owner` constraint on `token_0_account`/`token_1_account`, in contrast to `Deposit`, whose `token_0_account`/`token_1_account` explicitly require `token::authority = owner`: [2](#0-1) 
Because Anchor only validates the mint on the withdraw destination accounts, the `withdraw` handler burns the owner's LP tokens and then transfers the underlying tokens to whatever `token_0_account`/`token_1_account` was supplied in the instruction, using `transfer_from_pool_vault_to_user`: [3](#0-2) 
An attacker could phish/trick an LP into constructing (or signing via a malicious dApp/wallet UI) a `withdraw` transaction where `token_0_account`/`token_1_account` point to an account the attacker controls (of the correct mint), just as the original SolverVaults finding shows a user-supplied `receiver` field enabling redirection of withdrawn funds.

### Impact Explanation
If a user is tricked into signing a withdraw transaction with attacker-supplied destination token accounts, their LP tokens are burned and the corresponding token_0/token_1 amounts are transferred directly to the attacker's account in the same atomic transaction — resulting in a direct, unrecoverable loss of the user's underlying pool assets.

### Likelihood Explanation
This requires the owner to sign a transaction with attacker-crafted account inputs (e.g., via a malicious frontend, wallet-connect phishing site, or manipulated transaction), which is the same social-engineering vector described in the reference report. The on-chain program itself provides no protection since it doesn't validate that the destination accounts belong to the signer, unlike its own `Deposit` instruction which does enforce this.

### Recommendation
Add `token::authority = owner` constraints to `token_0_account` and `token_1_account` in the `Withdraw` account struct, matching the pattern already used in `Deposit`, so that withdrawn funds can only be sent to token accounts owned by the withdrawing signer.

### Proof of Concept
1. User holds LP tokens for a pool and wants to withdraw.
2. A malicious frontend/dApp constructs a `withdraw` instruction with `owner` = the user (signer), `owner_lp_token` = the user's real LP token account, but `token_0_account` and `token_1_account` set to token accounts owned by the attacker (same mints as the vaults, so the mint constraints pass).
3. The user signs the transaction, believing they are withdrawing to their own wallet.
4. `withdraw` burns the user's LP tokens via `token_burn` and transfers the resulting `token_0_amount`/`token_1_amount` to the attacker's accounts via `transfer_from_pool_vault_to_user`, as shown at [3](#0-2) , with no check that these accounts belong to `owner`.
