Cross-tenant commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that a `status` webhook was signed with the webhook secret of the organization named in `payload['repository']['owner']['login']`; it says nothing about which commit rows the payload is allowed to touch. `StatusHandler#process` then looks up commits globally by `sha` across the entire `commits` table, with no scoping to the repository/organization that produced the signature, so a webhook legitimately signed by Org A can mutate `Status`/`Commit` records belonging to Org B whenever both organizations happen to track a commit with the same SHA.

### Finding Description
The binding the exploit breaks: `Shipit.github(organization: repository_owner) resolving to Org A's GitHubApp/webhook_secret` should imply `authorization limited to Org A's own tracked repositories/commits`, but in the vulnerable code it actually implies `authorization to mutate any Commit row in the database sharing the submitted sha, in any organization`.

Path:
1. `verify_signature` derives `repository_owner` purely from the attacker-controlled JSON body (`params.dig('repository','owner','login')`), resolves `Shipit.github(organization: repository_owner)`, and validates `X-Hub-Signature` against that org's `webhook_secret` via `GitHubApp#verify_webhook_signature`. [1](#0-0) [2](#0-1) [3](#0-2) 

2. Once signature verification passes, `create` simply dispatches the raw JSON to registered handlers for the event, with no further linkage back to `repository_owner`. [4](#0-3) 

3. `StatusHandler#process` ignores `payload['repository']` entirely and queries `Commit.where(sha: params.sha)` — a global, unscoped lookup across every stack/organization in the database — then calls `create_status_from_github!` on every match. [5](#0-4) 

The base `Handler` class does provide a repository-scoped `stacks` helper keyed off `payload.dig('repository','full_name')`, but `StatusHandler` never uses it — unlike handlers that need repo context, it bypasses that scoping mechanism. [6](#0-5) 

`Commit#create_status_from_github!` unconditionally records the forged state/description/target_url and fires `commit_status`/`deployable_status` hooks and `stack.schedule_merges`, with no check that the commit's owning `stack.repository.owner` matches the authenticated `repository_owner`. [7](#0-6) [8](#0-7) 

Exploit flow: attacker owns a throwaway repo in Org A that Shipit tracks (so `Shipit.github(organization: 'org-a')` resolves to a real `GitHubApp` with a real `webhook_secret`). If Org A and victim Org B's tracked stacks ever contain a commit object with the identical SHA-1 (git SHAs are content-addressed, so this occurs whenever both stacks share history — a common fork/shared-upstream/vendoring scenario, not necessarily a cryptographic SHA-1 collision), the attacker can either push that exact commit to their own Org A repo and use the standard GitHub "create commit status" API (which they can call themselves, since they own the repo) to trigger a real, correctly-signed `status` webhook delivery from GitHub to Shipit naming Org A's repository. `verify_signature` accepts it because it was genuinely signed by Org A's secret. `StatusHandler#process` then matches every `Commit` row with that SHA regardless of organization, mutating Org B's commit status — e.g., forging a `success` state that can unlock `deployable?`/`schedule_merges` on the victim's stack.

None of the existing guards prevent this: `drop_unhandled_event` only filters by event type, the `ExplicitParameters` schema only validates the shape of `sha`/`state`/etc, and no code path anywhere compares the authenticated `repository_owner` to the `stack.repository.owner` of the commits being mutated.

### Impact Explanation
A payload correctly authenticated for one repository/organization can flip commit statuses and trigger deploy-readiness/merge-scheduling side effects (`commit_status`, `deployable_status` hooks, `stack.schedule_merges`) for a completely unrelated organization's stack, with zero credentials or access to that victim organization. This matches the Critical category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy". It is repeatable against any commit SHA the attacker can reproduce that is shared with a victim's tracked history, and the blast radius spans all organizations/stacks configured under the same Shipit instance.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub organizations (multi-tenant `secrets.github` config), the attacker must control at least one tracked repository in some organization known to Shipit (trivially satisfiable by adding a throwaway public repo), and the attacker must be able to produce a commit whose SHA collides with a commit tracked in the victim's stack. This last condition doesn't require a true SHA-1 cryptographic collision — it's satisfied whenever the two organizations' repositories share git history (forks of the same upstream, vendored/copied commits, shared templates) or when the specific commit content is otherwise known/reproducible to the attacker. Attacker cost is low (own a repo, know/reconstruct a target commit, call GitHub's own commit-status API), and the attack is fully repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) to only the commits belonging to stacks under the repository named in the authenticated payload, e.g. use the existing `stacks` helper from `Handler` (`Repository.from_github_repo_name(repository_name)&.stacks`) to constrain the `Commit.where(sha: ...)` query, and/or verify that `commit.stack.repository.full_name` matches `payload.dig('repository','full_name')` before calling `create_status_from_github!`.
