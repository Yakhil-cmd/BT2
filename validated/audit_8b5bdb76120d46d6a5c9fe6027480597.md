### Title
Cross-repository Commit status forgery via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `commits` table and calls `create_status_from_github!` on every match, without checking that the matched commit's stack/repository corresponds to the `repository.full_name` named in the verified webhook payload. Because webhook signature verification (`WebhooksController#verify_signature`) only proves the payload came from the organization it claims to be from, and not that the organization owns every `Commit` row sharing that SHA, an attacker who legitimately controls a repository's webhook can write a `Status` onto a `Commit` belonging to an unrelated stack whenever the SHA values coincide.

### Finding Description
The binding the code implicitly assumes is: `repository.full_name` in the verified payload == the repository owning every `Commit` row returned by `Commit.where(sha: params.sha)`. This does not hold, since SHA is not scoped to a stack/repository at the database level (git SHAs are content hashes, not globally unique namespaced identifiers, and a `Commit` row is created for the same SHA independently in each stack that observes it, e.g. via `Repository#stacks`).

Code path:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, passing the raw parsed payload.
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` using `repository_owner` **read from the unverified payload itself** (`params.dig('repository','owner','login')`), then checks the HMAC signature against that organization's configured `webhook_secret`. This only proves the request was signed by whoever holds `attacker-org`'s secret — it says nothing about which `Commit` rows in Shipit's database that organization is allowed to mutate.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This never calls the base class's `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`, which does `Repository.from_github_repo_name(repository_name)&.stacks`) to scope the lookup to the repository named in the verified payload. Other handlers in the same directory do scope correctly — `PushHandler#process` restricts to `stacks.not_archived.where(branch:)` and `CheckSuiteHandler#process` restricts to `stacks.where(branch:).commits.where(sha:)` — confirming `StatusHandler` is the outlier that omits this scoping.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) unconditionally creates a `Status` row (`statuses.replicate_from_github!`), triggers `Hook.emit(:commit_status, ...)`, and potentially `Hook.emit(:deployable_status, ...)` plus `stack.schedule_merges` — all against whichever stack the matched `Commit` belongs to, not the attacker's stack.

Exploit flow: the attacker registers/owns `attacker/decoy` in Shipit with a legitimate webhook_secret. They push a commit to their own repo whose SHA is identical to a commit already present in `victim-org/victim-repo`'s Shipit-tracked history (trivial for well-known content, e.g. an empty-tree commit, or by copying commit metadata/tree/parent hashes byte-for-byte to reproduce the same SHA1). GitHub (or a raw HTTP client, since no live GitHub server relationship is actually required to POST to `/webhooks`) sends a `status` event signed with `attacker/decoy`'s own secret, with `repository.full_name: 'attacker/decoy'`. `verify_signature` passes because the signature correctly matches attacker's own secret. `StatusHandler#process` then matches `Commit.where(sha: 'SHA-X')`, which includes the victim's `Commit` row, and writes a `Status` onto it.

Existing guards fail because: signature verification is org-scoped, not commit/stack-scoped; `ExplicitParameters` schema only validates parameter types/presence, not cross-referencing repository identity to the specific `Commit` rows touched; and the `Handler#stacks` scoping mechanism exists in the base class but is simply not invoked by this specific subclass.

### Impact Explanation
A successful request creates a forged `Status` (e.g., `state: 'success'`) on a `Commit` belonging to a repository/stack the attacker does not control and never authenticated for. This can flip `Commit#deployable?` / `Commit#status` results, which factor into `Stack#schedule_merges`, continuous-delivery scheduling (`Commit#schedule_continuous_delivery`), and merge-request status gating — potentially causing an unauthorized deploy or merge decision on the victim stack to proceed based on a fabricated "success" status. This is a cross-repository write where a payload for one repository mutates another repository's commit/stack state, matching the Critical category explicitly listed in scope ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: Shipit must track both the attacker's repository (with any configured webhook, which is standard for any registered repo) and the victim repository, and both must have a `Commit` row for the colliding SHA (which happens naturally once each stack observes/syncs the commit, e.g. via push events, PR merges, or scheduled refreshes). The attacker needs no Shipit credentials, no access to the victim repo, and no knowledge of the victim's webhook secret — only ownership of their own repo and its legitimate webhook secret, which is trivially available to any GitHub user who can register a repo/webhook. Producing a SHA collision is feasible either via a natural content collision (e.g., identical empty/trivial commits are common) or, in adversarial scenarios, forging a full SHA1 collision (computationally expensive but publicly demonstrated); the simplest and fully realistic vector is when both stacks/forks already share commit history (e.g., attacker forked victim-repo, and the shared commit SHA already exists in both `Commit` tables) — this is a common real-world Shipit deployment pattern and requires no cryptographic attack at all.

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the commit lookup to the repository asserted in the verified payload, consistent with `PushHandler` and `CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures the `Commit` rows mutated are always scoped to `Repository.from_github_repo_name(repository_name)`, matching the org whose signature was verified.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or integration test against `WebhooksController`):
1. Create two `Stack`/`Repository` fixtures: `victim_stack` for `victim-org/victim-repo`, and `attacker_stack` for `attacker/decoy`, each with a `Commit` row sharing the same `sha: 'SHA-X'` (e.g., `shipit.production` and a second stack fixture, both with a commit at that SHA — reuse of existing commit fixtures across stacks already models this).
2. Stub/allow `GitHubApp#verify_webhook_signature` (or `Shipit.github(organization: 'attacker').verify_webhook_signature`) to return `true`, simulating a legitimately-signed request from `attacker/decoy`'s own secret.
3. POST to `/webhooks` with header `X-Github-Event: status` and body `{ sha: 'SHA-X', state: 'success', repository: { full_name: 'attacker/decoy', owner: { login: 'attacker' } } }`.
4. Assert the binding before the request: `victim_commit.statuses.count == 0` and `victim_commit.stack.repository.full_name != 'attacker/decoy'`.
5. After the request, assert the binding is violated: `victim_commit.reload.statuses.count == 1` and the created `Status`'s commit belongs to `victim_stack`, even though the verified payload named `attacker/decoy` — proving the repository-in-payload does not equal the repository owning the mutated `Commit`.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

      ].join(' '))
    end
