### Title
Unbounded/attacker-sized `RemoteProxyProof::RelayChain::proof` trie-node data causes `do_remote_proxy` to under-charge for `StorageProof::into_memory_db`/`read_trie_value` hashing cost - ([File: pallets/remote-proxy/src/lib.rs])

### Summary
`Pallet::remote_proxy` charges a fixed benchmarked weight (`WeightInfoOf::<T, I>::remote_proxy()` plus the inner call weight) that was measured against the small, "realistic" proof produced by `create_remote_proxy_proof` in benchmarking, not against the actual size of the caller-supplied `proof: Vec<Vec<u8>>`. In `do_remote_proxy`, `sp_trie::StorageProof::new(proof).into_memory_db(...)` unconditionally hashes every byte blob in the attacker-controlled `proof` vector before any validity check happens, so an attacker can submit a large, entirely bogus proof (bounded only by extrinsic/block length limits) and force disproportionate CPU work relative to the fixed charged weight.

### Finding Description
The dispatchable is declared with a size-independent weight: [1](#0-0) 

`proof` has no `MaxEncodedLen`/length bound anywhere in the pallet — `RemoteProxyProof` only derives `Decode`/`Encode`/`TypeInfo`, not `MaxEncodedLen`: [2](#0-1) 

In `do_remote_proxy`, the entire attacker-supplied `proof: Vec<Vec<u8>>` is converted into a `MemoryDB` (hashing every supplied node) *before* `read_trie_value` even attempts to look up the root: [3](#0-2) 

`StorageProof::into_memory_db` inserts and hashes every element of the `proof` vector unconditionally, so its cost scales linearly with the total bytes supplied, independent of whether the proof is valid for the claimed `storage_root`. If the root node hash isn't present, `read_trie_value` fails fast with `InvalidProof` immediately after — but the hashing of the full (possibly huge) attacker-supplied proof vector has already been paid for in CPU time before that failure.

Meanwhile, the benchmark that determines `WeightInfoOf::remote_proxy()` uses a single minimal, valid proof from `T::RemoteProxy::create_remote_proxy_proof`: [4](#0-3) 

There is no scaling term (e.g., `.saturating_add(Weight::from_parts(proof.len() as u64 * X, 0))`) added in the `#[pallet::weight]` expression to account for the size of the actually submitted `proof`. The only external limit on `proof` size is the generic extrinsic/`BlockLength` normal-class byte limit, and the standard per-byte transaction length fee — neither of which is calibrated to the hashing cost of a `Vec<Vec<u8>>` trie proof, and neither of which is the `ref_time` weight metric that block authors use to bound how much CPU work an extrinsic may perform. Because `di.class`/weight checks (`frame_system::CheckWeight`) only compare the *declared* fixed weight against block weight limits, they cannot detect or reject an extrinsic whose *actual* execution cost exceeds what was declared.

### Impact Explanation
An attacker who is a normal signed account (no special privilege needed — `ensure_signed` is the only origin check) can submit `remote_proxy` extrinsics with a large, invalid `proof` targeting any `block` present in `BlockToRoot` (a public value updated every relay-chain block). Because the charged weight is fixed and doesn't scale with `proof` size, each such call spends real CPU time hashing (potentially near the block-length limit's worth of) node data while only "costing" the small fixed benchmarked weight. Packing multiple such extrinsics into a block lets an attacker cause the block's *actual* execution/proof time to exceed its *declared* weight budget, slowing down block authoring/import and crowding out other extrinsics that would otherwise fit within the (falsely believed) remaining weight budget — a block-level resource-accounting/DoS issue matching the scoped impact.

### Likelihood Explanation
The attacker needs only: (1) a signed account able to pay the base fee (relatively cheap; the length fee scales linearly with bytes, but is a monetary cost not tied to actual verification CPU cost), (2) knowledge of a currently valid `block` value in `BlockToRoot` (public/derivable from relay-chain state), and (3) the ability to submit a `proof: Vec<Vec<u8>>` up to the normal extrinsic length limit filled with junk byte blobs. All of this is achievable via the ordinary `remote_proxy` extrinsic path with no special permissions, making the issue readily repeatable by any user, limited only by their willingness to pay per-byte transaction fees.

### Recommendation
Add an explicit weight component (and/or hard cap) proportional to the actual size/number of nodes in `proof` before or as part of the `#[pallet::weight]` calculation for `remote_proxy`/`remote_proxy_with_registered_proof`/`register_remote_proxy_proof`, e.g. benchmark `into_memory_db` + `read_trie_value` cost as a function of proof length/bytes and add `Weight::from_parts(proof_size_factor * total_proof_bytes, 0)` to the declared weight. Additionally, enforce a sane maximum bound on the number/size of proof nodes (reject via `ensure!` before calling into `sp_trie`) independent of the generic extrinsic length limit, so verification cost is always bounded by a pallet-specific, benchmarked constant rather than the full block-length allowance.

### Proof of Concept
Rust benchmark/integration test plan:
1. In `pallets/remote-proxy/src/benchmarking.rs`, add a worst-case benchmark variant that builds a `RemoteProxyProof::RelayChain { proof, block }` where `proof` is a `Vec<Vec<u8>>` filled with many large, non-matching random byte blobs (e.g., near the `BlockLength` normal-class limit), targeting a real `block`/`storage_root` pair inserted into `BlockToRoot`.
2. Measure wall-clock time (or benchmarking's `execution_time`) of `Pallet::<T, I>::remote_proxy` dispatch with this adversarial proof versus the currently declared `WeightInfoOf::<T, I>::remote_proxy()` weight (converted to time via the runtime's `WEIGHT_REF_TIME_PER_SECOND`).
3. Assert: `measured_ref_time_for_large_invalid_proof > declared_weight.ref_time() * tolerance_factor` — demonstrating the fixed weight under-charges for large invalid proofs.
4. As an integration test, submit N such extrinsics inside one block via the test externalities' block-building harness and assert cumulative measured execution time exceeds the block's configured `MAX_BLOCK_WEIGHT.ref_time()` while `CheckWeight`/on-chain weight accounting reports the block as still within its declared budget.

		let caller: T::AccountId = account("target", 0, SEED);

			&caller,
			BalanceOf::<T>::max_value() / 2u32.into(),

		// ... and "real" is the traditional caller. This is not a typo.
		let real: T::AccountId = whitelisted_caller();

		let call: <T as pallet_proxy::Config>::RuntimeCall =
			frame_system::Call::<T>::remark { remark: vec![] }.into();
		let (proof, block_number, storage_root) =
			T::RemoteProxy::create_remote_proxy_proof(&caller, &real);
		BlockToRoot::<T, I>::set(BoundedVec::truncate_from(vec![(block_number, storage_root)]));

		#[extrinsic_call]
		_(RawOrigin::Signed(caller), real_lookup, None, Box::new(call), proof);

		assert_last_event::<T>(pallet_proxy::Event::ProxyExecuted { result: Ok(()) }.into());

		Ok(())
