### Title
Cross-repository CI-status confusion via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` applies an incoming GitHub `status` webhook to **every** `Commit` row in the database whose `sha` matches the payload, with no check that the webhook originated from the repository/stack that commit belongs to. Combined with `Commit#create_status_from_github!` / `Status.replicate_from_github!`, which always writes the new `Status` against the target commit's own `stack_id`, this lets a legitimately-signed webhook from any GitHub org/repo that Shipit trusts forge a CI status on an unrelated stack's commit, driving `Commit#deployable?` and `schedule_continuous_delivery` to trigger an unauthorized deploy.

### Finding Description
The broken binding is: `Shipit::Commit#success?` (used inside `deployable?`, `app/models/shipit/commit.rb:227-229`) should equal *"outcome of CI run against Victim's own tracked repository for this exact commit"*, but the code actually computes it from *"the last webhook payload whose `sha` field textually matches this commit's `sha`, regardless of which repository sent it."*

Path:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON body and dispatches to handlers for the `status` event.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks the HMAC over the raw body using the webhook secret for `repository_owner` (itself read straight out of attacker-controlled JSON `params.dig('repository','owner','login')`). It verifies the payload was sent by *some* GitHub org Shipit is configured for — it does **not** verify that the `sha` inside the payload belongs to a commit in a repository owned by that org/repo.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This query is global across the entire `commits` table — not scoped by `stack_id`, `repository`, or any binding to the webhook's origin repo.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) calls `statuses.replicate_from_github!(stack_id, github_status)`, and `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) persists the forged state using the **found commit's own `stack_id`**, not anything derived from the webhook payload's repository.
- `add_status` (`app/models/shipit/commit.rb:366-386`) then calls `stack.schedule_merges` when the new status is `success?`/`pending?`, and the `after_commit` `schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) checks `deployable?` (`app/models/shipit/commit.rb:227-229`) which is now true because of the injected status, enqueuing `ContinuousDeliveryJob.perform_later(stack)`.

Exploit flow: Attacker controls (or has push access / PR access to) any GitHub repository whose organization is configured in Shipit (satisfies `verify_signature`). Attacker constructs a git commit object with identical content (author, committer, timestamps, tree, message, parent) to a real commit already present in Victim's tracked stack — this is not a cryptographic hash break, it is simply reproducing a git object attacker can read from Victim's public repo, so the resulting SHA-1 is identical by construction. Attacker pushes/creates that commit inside their own trusted repo and has any CI (their own, attacker-controlled) POST a `status` webhook with `state: success` for that sha. GitHub signs this webhook correctly because it is a real webhook from a repository under an org Shipit already trusts. `StatusHandler#process` finds the matching `Commit` row belonging to Victim's stack (because `Commit.where(sha:)` is global) and writes a `success` `Status` against it, and `deployable?`/`schedule_continuous_delivery` proceed as if Victim's own CI passed.

None of the existing guards close this gap: `verify_signature` only authenticates *who sent the request*, not *which repository the sha belongs to*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of the payload; there is no `Repository`/`Stack` scoping validation anywhere in `StatusHandler` or `Status.replicate_from_github!`.

### Impact Explanation
A `success` status is written for Victim's stack from a webhook Victim's repository never sent, causing `Shipit::Commit#deployable?` to return true and `ContinuousDeliveryJob.perform_later(stack)` to be enqueued — an unauthorized deploy trigger for code whose real CI is pending/failing on GitHub. This is a cross-tenant write: a payload originating from Attacker's own trusted repository mutates state (`Status`, effectively `Commit#state`) belonging to an entirely different stack/repository. Because the lookup is global (`Commit.where(sha:)` with no stack filter), this is repeatable against any stack in the same Shipit instance whose commit sha attacker can reproduce, not limited to one victim. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy."

### Likelihood Explanation
Preconditions: Victim stack has `continuous_deployment?` enabled and is otherwise deployable (`!locked?`, not blocked) — a common Shipit configuration. Attacker needs only: (1) legitimate write/CI access to some repository within a GitHub organization that Shipit already trusts (satisfying `verify_signature`), and (2) the ability to construct a git commit object byte-identical to a commit already present in Victim's tracked history (feasible since git commit metadata — author, committer, timestamp, tree, parent, message — are all public via GitHub's API/UI, so the attacker can losslessly reproduce the exact object and its SHA-1, no actual hash collision required). No Shipit session, API token, or GitHub App secret is needed. This is a repeatable, low-cost attack for anyone who can get a status webhook fired from a trusted org.

### Recommendation
Scope the `StatusHandler` (and the analogous check-run/check-suite handlers, and `Commit.by_sha`/`refresh_statuses!` call sites) lookup by the repository that actually sent the webhook, not just by `sha`. Concretely: resolve the target `Stack`/`Repository` from the webhook's `repository.full_name` payload field first, then find only commits belonging to that repository's stacks (`stack.commits.where(sha: params.sha)`), and reject/ignore the event if the repository named in the payload doesn't match a stack tracking that sha. Additionally, `Status.replicate_from_github!` should assert the `stack_id` it's given corresponds to a stack whose `repository` matches the webhook's repository before persisting.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
```ruby
test "a status webhook from an unrelated repository must not mark another stack's commit as successful" do
  victim_stack = shipit_stacks(:shipit) # continuous_deployment enabled, ignore_ci false
  victim_commit = shipit_commits(:first)
  victim_commit.update!(locked: false)
  refute victim_commit.reload.deployable?, "precondition: victim commit should not be deployable before forged status"

  # Attacker's payload: legitimately signed (simulated via stubbed verify_signature),
  # but 'repository' points to an org/repo the attacker controls, unrelated to victim_stack.
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  ContinuousDeliveryJob.expects(:perform_later).with(victim_stack) # assert unauthorized deploy trigger enqueued

  request.headers['X-Github-Event'] = 'status'
  body = {
    'sha' => victim_commit.sha,                 # colliding/duplicated sha
    'state' => 'success',
    'context' => 'ci/attacker',
    'created_at' => Time.now.iso8601,
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  post :create, body:, as: :json

  victim_commit.reload
  assert_equal 'success', victim_commit.state, "forged status from unrelated repo applied to victim commit"
  assert victim_commit.deployable?, "victim commit became deployable due to forged cross-repo status"
end
```
Both sides of the binding to assert explicitly: `victim_commit.success?` (should equal `Victim's own CI result on Victim's repository for victim_commit.sha`) actually equals `attacker_payload.state == 'success'` after the forged webhook — proving the equality is broken, and the enqueued `ContinuousDeliveryJob.perform_later(victim_stack)` demonstrates the unauthorized-deploy impact.     def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end
