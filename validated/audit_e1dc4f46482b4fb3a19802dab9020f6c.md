### Title
Fork-controlled `machine.environment` in `shipit.yml` injects `LD_PRELOAD` into `deploy.override` command execution - (File: lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`DeploySpec::FileSystem` parses `shipit.yml` from the checked-out review-stack branch (the fork PR's head), and `DeploySpec#machine_env` returns `config('machine','environment')` completely unfiltered. `TaskCommands#env` merges this hash into the process environment that `Command#start` eventually passes to `PTY.spawn`, with no key allow-list or denylist, so a PR author can set `LD_PRELOAD` (or any other env var) and have it inherited by every command the `deploy.override` step runs on the Shipit host.

### Finding Description
The broken binding: the set of environment variable *names* reaching `PTY.spawn` for a review-stack deploy is claimed to be restricted to Shipit-controlled keys, i.e. `keys(Command#unbundled_env) == keys(Shipit-defined env)`. In reality `keys(Command#unbundled_env) ⊇ keys(config('machine','environment'))` where that config comes straight from the attacker's `shipit.yml`.

Path:
1. A `ReviewStack` is provisioned for a fork PR under `provisioning_behavior = prevent_with_label` (the PR is dynamically provisioned unless labeled) — see `app/models/shipit/webhooks/handlers/pull_request/*_handler.rb`, `app/models/shipit/review_stack.rb`.
2. The stack's `branch` is the PR's head ref, owned by the fork author. When a deploy runs, `TaskCommands#deploy_spec` builds `DeploySpec::FileSystem.new(@task.working_directory, @stack)` [1](#0-0)  reading `shipit.yml` checked out from that fork branch.
3. `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` verbatim, with no key filtering [2](#0-1) .
4. `TaskCommands#env` merges `deploy_spec.machine_env` into the environment hash used to build the `deploy.override` `Command` [3](#0-2) .
5. `Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — `@env` (attacker-influenced) is merged **last**, so it wins over `BASE_ENV`/`Bundler.unbundled_env` for any key, including `LD_PRELOAD` [4](#0-3) .
6. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [5](#0-4) , so the injected `LD_PRELOAD` is inherited by the spawned `deploy.override` process (and any subprocess it forks) on the Shipit deploy host.

Attacker's exact PR: fork the repo, open/push a branch containing
```yml
machine:
  environment:
    LD_PRELOAD: /tmp/payload.so
deploy:
  override:
    - "true"
```
and open a PR (label rules under `prevent_with_label` mean simply not applying the provisioning label is enough to get a review stack auto-provisioned; see `app/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb` / `opened_handler_test.rb` fixtures confirming stacks are created by default under `prevent_with_label`).

Existing guards do not stop this: `EnvironmentVariables#permit` exists only to validate task-definition-declared variables against an explicit allow-list (used elsewhere, e.g. for `stack.env` from the UI/API) [6](#0-5) ; it is never invoked on `deploy_spec.machine_env` in `TaskCommands#env`. `EnvironmentVariables#interpolate`, used by `Command#interpolate_environment_variables`, only escapes values substituted into shell arguments — it does not filter the process env hash passed to `PTY.spawn`. No repository/stack model validation restricts the content of `machine.environment` keys.

### Impact Explanation
Any environment variable name is fork-controllable and lands in the actual OS process environment of the `deploy.override` step's spawned process via `PTY.spawn`. `LD_PRELOAD` specifically causes the dynamic linker to load an attacker-supplied shared object into that process (and further child processes that inherit the environment), which is arbitrary code execution on the Shipit deploy host under the Shipit worker's OS user. This is Remote Code Execution on the deploy host, matching the Critical severity category described in the rules. Because the vulnerable code path (`TaskCommands#env` / `Command#unbundled_env`) is shared by all stacks, this affects any repository that enables review stacks with `provisioning_behavior = prevent_with_label` (or `allow_all`), i.e. it is repeatable against any such repository/tenant that an attacker can fork and open a PR against.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior` set to `prevent_with_label` (or `allow_all`) so that an unlabeled fork PR auto-provisions a review stack and the deploy pipeline runs against the fork's `shipit.yml`. No Shipit credentials, GitHub App keys, or maintainer status are required — only the ability to open a public PR from a fork, which is the baseline capability of any GitHub user. This is highly feasible and fully repeatable: each new PR/branch is an independent injection opportunity.

### Recommendation
Do not let `deploy_spec.machine_env` pass through Command#unbundled_env unfiltered for stacks whose `shipit.yml` is untrusted (e.g. `ReviewStack`/fork-sourced specs). Concretely:
- Apply an explicit key allow-list (reusing `EnvironmentVariables#permit`) to `deploy_spec.machine_env` before merging it in `TaskCommands#env`, rejecting/stripping dangerous names such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `BUNDLE_*`, `PATH`, `RUBYOPT`, etc.
- Alternatively (or additionally), have `Command#unbundled_env` merge `@env` onto an explicit denylist filter, or spawn deploy processes through a wrapper that clears/`unsetenv`s dangerous preload-related variables regardless of what `@env` contains.
- Consider treating review-stack `shipit.yml` as untrusted input distinctly from maintainer-authored default-branch specs, and disabling arbitrary `machine.environment` keys entirely for review stacks.

### Proof of Concept
minitest plan (`test/unit/task_commands_test.rb` or similar), no live GitHub required:
```ruby
test "deploy.override does not inherit fork-controlled LD_PRELOAD from machine.environment" do
  stack = shipit_review_stacks(:some_review_stack) # or build one with provisioning_behavior: prevent_with_label
  task  = create_deploy_task(stack) # any Task/Deploy fixture

  commands = TaskCommands.new(task)
  commands.stubs(:deploy_spec).returns(
    stub(
      machine_env: { 'LD_PRELOAD' => '/tmp/payload.so' },
      dependencies_steps!: [],
      deploy_steps!: ['true'],
      directory: nil,
      clear_working_directory?: true
    )
  )

  command = commands.perform.first
  # Binding under test: keys(command.env) should NOT include fork-controlled LD_PRELOAD
  assert_nil command.env['LD_PRELOAD'], "expected no LD_PRELOAD in TaskCommands#env"

  # Confirm it actually reaches PTY.spawn via Command#unbundled_env
  assert_equal '/tmp/payload.so', command.unbundled_env['LD_PRELOAD'],
    "LD_PRELOAD from shipit.yml machine.environment reaches the spawned process env"
end
```
Both assertions demonstrate the equality violation: the expected binding (`deploy.override` inherits no fork-controllable key) is false, while `command.unbundled_env['LD_PRELOAD']` shows the actual value that would be passed to `PTY.spawn`.

        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)

        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"

      end
      @started = true
      self
    end
