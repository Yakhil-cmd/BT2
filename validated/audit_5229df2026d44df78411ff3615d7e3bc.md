### Title
`StatusHandler` writes GitHub status updates to commits in any tenant's stack because `Commit.where(sha:)` is unscoped by repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/status.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike `PushHandler` which restricts to `stacks` (`Repository.from_github_repo_name(repository_name).stacks`). Any commit matching the attacker-supplied `sha`, regardless of which repository/stack it belongs to, gets a new `Status` row written via `Commit#create_status_from_github!` → `Shipit::Status.replicate_from_github!(stack_id, github_status)`, where `stack_id` is `self.stack_id` of the pre-existing (potentially unrelated) `Commit`.

### Finding Description
Binding claimed: `Status#stack_id written == stack_id authorized by the incoming webhook's repository`.

Traced code:
- `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) dispatches `params` (parsed JSON body) to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`.
- `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only checks that the payload is HMAC-signed by the `GithubApp` associated with `repository_owner = params.dig('repository','owner','login')`. This authenticates that the request genuinely came from GitHub for *that organization/app installation*, but does not scope which repository or commit sha inside that org can be referenced.
- `Handler#initialize` (`app/models/shipit/webhooks/handlers/handler.rb:21-24`) wraps the raw payload into an `ExplicitParameters::Parameters` object (`params`), exposing `params.sha`, `params.state`, etc., but this object carries no ownership/repository binding of its own.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This is a *global*, unscoped query — it does not call the `stacks` helper (`Handler#stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-34`) that other handlers such as `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`, `stacks.not_archived.where(branch:)`) use to restrict to stacks tied to `payload.dig('repository','full_name')`.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`):
  ```ruby
  def create_status_from_github!(github_status)
    add_status do
      statuses.replicate_from_github!(stack_id, github_status)
    end
  end
  ```
  `stack_id` here is `self.stack_id`, i.e., the stack owning the *pre-existing* `Commit` row found by the unscoped SHA lookup — not anything derived from the authenticated webhook's `repository_owner`/`repository.full_name`.
- `Status.replicate_from_github!` (`app/models/shipit/status.rb:24-33`) takes `stack_id` as a raw positional argument and performs `find_or_create_by!(stack_id:, state: ..., ...)` with zero cross-check that `stack_id` corresponds to any stack owned by the organization that authenticated the webhook.

Because commit SHAs are content-addressed and identical across forks/mirrors that share history, an attacker who owns a fork (or any repository under an organization/app installation registered with Shipit) can send a genuinely-signed `status` webhook naming the SHA of a commit that exists in a victim stack under a *different* repository/organization. `Commit.where(sha: params.sha)` will match that victim `Commit` regardless of which org signed the request, and a new `Status` (state/description/context/target_url all attacker-controlled) is written against the victim's `stack_id`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `EnvironmentVariables#permit`, model validations) do not prevent this: `verify_signature` only proves the payload's authenticity for *an* organization, and none of the model validations on `Status` (`state` inclusion) check `stack_id` against the requesting repository. The `stacks` scoping helper exists in `Handler` precisely for this purpose but `StatusHandler` does not use it.

### Impact Explanation
An attacker (unprivileged, only owning/controlling a repository connected to any Shipit-integrated GitHub App organization) can inject arbitrary CI status records (`state`, `description`, `context`, `target_url`, `created_at`) onto commits belonging to a completely different stack/tenant, as long as they can produce/guess a matching commit SHA (trivially true for forked repositories sharing history, or any case where the same commit SHA is tracked by more than one Shipit stack). Since `Status` rows drive `Commit#state`, required-status gating, and continuous delivery/merge automation (`schedule_continuous_delivery`, `ProcessMergeRequestsJob`, ci/deploy gating), this can force a victim stack's commit to appear "success" (bypassing CI/status gating for deploys/merges) or "failure"/"error" (denial of legitimate deploys) for a stack the attacker never authenticated against. This is a cross-repository write of a `Status` record with no ownership check, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy, rollback or merge" (via forged success status enabling auto-deploy/merge flows).

### Likelihood Explanation
Preconditions: attacker needs any repository connected through a Shipit GitHub App installation (so their own webhook can be validly signed), and a commit SHA that also exists in the target victim's tracked commit history (e.g., via fork-sharing, cherry-pick, or copy of the exact same tree — very feasible for public/forked repos, which is exactly the population of "unprivileged" attackers described in scope). No secrets, sessions, or elevated GitHub roles are required. The attack is trivially repeatable (one webhook POST per desired status), cheap, and does not require guessing anything secret—only knowledge of a shared SHA, which is often public (e.g., visible in a victim's public repo commit history or PR).

### Recommendation
Scope `StatusHandler#process` to the stacks belonging to the authenticated `repository_name` before looking up commits, e.g. restrict via `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern already used by `PushHandler`. Additionally, `Status.replicate_from_github!` (and `Commit#create_status_from_github!`) should not blindly trust `self.stack_id`; the caller should verify the commit's stack corresponds to the webhook's authenticated repository before writing.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new)
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossStackTest < ActiveSupport::TestCase
        test "status webhook writes into a commit's stack regardless of the webhook's own repository" do
          victim_commit = shipit_commits(:first)
          victim_stack_id = victim_commit.stack_id

          # Payload claims to come from a totally different repository than the one owning victim_commit
          payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'description' => 'forged',
            'context' => 'attacker/ci',
            'branches' => [{ 'name' => 'master' }],
            'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
          }.deep_stringify_keys

          assert_difference -> { Status.where(stack_id: victim_stack_id).count }, 1 do
            StatusHandler.call(payload)
          end

          status = victim_commit.statuses.order(:id).last
          assert_equal victim_stack_id, status.stack_id # binding broken: no check that attacker-org owns victim_stack_id
          assert_equal 'attacker/ci', status.context
        end
      end
    end
  end
end
```
This demonstrates `StatusHandler` → `Commit#create_status_from_github!` → `Status.replicate_from_github!(stack_id, github_status)` writes a `Status` row with `stack_id == victim_commit.stack_id` even though the payload's `repository.full_name`/`owner.login` never referenced that stack — confirming zero cross-check between the authenticated repository and the target `stack_id`.
