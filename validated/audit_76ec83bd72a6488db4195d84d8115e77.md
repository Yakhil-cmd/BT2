### Title
AA `balance[asset]` includes the trigger's own current transfer, enabling reserve manipulation in pool-style AAs - (File: aa_composer.js, formula/evaluation.js)

### Summary
Ocore's autonomous-agent (AA) formula engine exposes a `balance[asset]` operator meant to represent an AA's current reserve of an asset. In `updateInitialAABalances`, the coins carried by the very trigger unit that is currently being processed are added to `assocBalances[address][asset]` *before* the AA's oscript logic runs. Consequently, any formula that reads `balance[asset]` inside a triggered response already sees the attacker-controlled inbound amount baked into the "reserve" figure. This is exactly the reserve-manipulation bug class described in the report: an amount controlled by the caller is folded into the pool's balance before pricing/burn logic executes, letting the caller move the effective price in the same call that exploits it.

### Finding Description
`updateInitialAABalances` credits the trigger's outputs into `trigger_opts.assocBalances`/`objValidationState.assocBalances` for the AA address before any of the AA's `init`/`messages` formulas are evaluated: [1](#0-0) 

The formula engine's `balance` operator (`case 'balance'` in the evaluator) simply reads whatever is currently in `objValidationState.assocBalances[address][asset]`: [2](#0-1) 

Because of this ordering, `balance[asset]` inside a triggered AA response is **not** a pre-trigger snapshot of reserves — it already contains the coins the attacker is sending in with the very same trigger. Any AMM/pool-style AA that naively uses `balance[asset]` (or `balance[base]`) as "the reserve" for a constant-product/price computation will compute the price using a reserve that the caller has already inflated by their own deposit, allowing the classic "manipulate-then-trade-against-your-own-manipulation" attack — structurally identical to the AM/USDT incident, where the attacker adjusted the pool's AM balance (via a burn side-effect) and then immediately traded against the now-distorted reserve.

The official reference AMM sample in the ocore repo is aware of this and defensively subtracts the trigger's own output before using the balance as the AMM reserve: [3](#0-2) 

The fact that this subtraction (`balance[$asset] - trigger.output[[asset=$asset]]`) is required in every reserve-dependent formula demonstrates that `balance[asset]` itself does not give a stable, pre-trigger reserve value — it is a live, attacker-influenced quantity for the duration of the response that produced it. A test even documents that `balance[]` reflects live database state independent of the current trigger only when the trigger's outputs are not yet applied to `objValidationState.assocBalances` (i.e., in isolated unit tests), confirming that in real trigger processing the value is trigger-inclusive: [4](#0-3) 

### Impact Explanation
Any live or future oscript AA implementing a pool/AMM/vault pattern that references `balance[asset]` (or `balance[base]`) directly as "current reserves" — without subtracting `trigger.output[[asset=...]]` — computes swap/exchange/burn amounts using a reserve value already polluted by the attacker's own inbound payment in the same unit. This lets an unprivileged trigger sender manipulate the perceived reserve and immediately extract value from the pool in the same operation, i.e., concrete unauthorized fund loss from the AA, matching the reported Medium/High severity reserve-manipulation attack class. Because triggers are ordinary payment+data units postable by any address, no special privilege is required.

### Likelihood Explanation
Likelihood is High for any deployed AA that omits the subtraction pattern, since triggering it requires nothing more than crafting a normal multi-output unit (base/asset payment plus data) addressed to the AA — the same capability every wallet user already has. The engine provides no built-in safeguard or warning distinguishing "pre-trigger" vs "post-trigger" balance; the correctness burden rests entirely on the AA author remembering to subtract `trigger.output[[asset=X]]`, a footgun proven necessary by the shipped reference sample.

### Recommendation
- Provide a dedicated formula primitive (e.g. `old_balance[asset]` or `balance_before_trigger[asset]`) that reflects the AA's balance strictly prior to crediting the current trigger's outputs, removing the need for AA authors to manually subtract `trigger.output[[asset=...]]`.
- Update `aa_validation.js`/documentation to explicitly warn AA authors that `balance[asset]` includes the current trigger's inbound funds, and require/encourage the subtraction pattern for any reserve-based pricing logic.
- Consider adding static/lint-time detection in `aa_validation.js` for AMM-like patterns (payment amount formulas referencing `balance[X]` without a corresponding `trigger.output[[asset=X]]` subtraction) to flag likely reserve-manipulation vulnerabilities before AA deployment.

### Proof of Concept
1. Deploy a simplified AMM AA that (incorrectly) uses `balance[$asset]` directly instead of `balance[$asset] - trigger.output[[asset=$asset]]`, e.g. adapting `test/samples/uniswap_like_market_maker.oscript` but removing the subtraction in the "exchange bytes to asset" case:
   `$p = balance[$asset] * balance[base]; $new_asset_balance = round($p / (balance[base] + trigger.output[[asset=base]])); $amount = balance[$asset] - $new_asset_balance;`
2. Attacker sends a single trigger unit carrying both a large `base` payment and, in the same response evaluation, benefits because `balance[$asset]`/`balance[base]` at formula-evaluation time already include this inbound payment (per `updateInitialAABalances`, aa_composer.js:474-489), letting the attacker pick input sizes that skew the computed exchange rate in their favor within one atomic call.
3. Compare against the correct reference implementation in `test/samples/uniswap_like_market_maker.oscript` lines 102-123, which must subtract `trigger.output[[asset=...]]` from `balance[...]` specifically to neutralize this effect — demonstrating the underlying primitive's live/trigger-inclusive semantics is the root cause.
