Confirmed: `here_come_the_walrus` fixture demonstrates the real, supported feature — an `ApiClient` can be created with `stack: shipit` to scope it to exactly one stack, granted only `read:stack`. This scoping is enforced everywhere through `Api::BaseController#stacks`/`#stack`, but `Api::CCMenuController` overrides `#stack` to bypass it entirely.

### Title
Stack-scoped ApiClient token can read CCMenu status of any stack, not just its authorized one - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` supports scoping a token to a single `Stack` (`belongs_to :stack, optional: true`), as shown by the `here_come_the_walrus` fixture which is scoped to the `shipit` stack with only `read:stack` permission [1](#0-0) . Every other API controller resolves the target stack through `Api::BaseController#stack`, which restricts the resolvable set of stacks to `current_api_client.stack_id` when the client is scoped [2](#0-1) . `Api::CCMenuController`, however, overrides `#stack` to fetch the stack directly by `Stack.from_param!(params[:stack_id])`, completely bypassing the client-scoping check [3](#0-2) .

### Finding Description
`require_permission :read, :stack` only verifies that the string `"read:stack"` is present in `ApiClient#permissions`; it never checks which specific stack the client is authorized for [4](#0-3) . The per-stack restriction is implemented separately, in `Api::BaseController#stacks`/`#stack`, which is meant to be the single place stacks get resolved for scoped clients:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController` redefines `stack` to call `Stack.from_param!(params[:stack_id])` directly — the unscoped class method — instead of going through `stacks.from_param!(...)` [5](#0-4) . This breaks the binding: `current_api_client.stack_id` (the stack the token authorizes) ≠ the stack the `show` action actually reads (any stack selected by the attacker via the `stack_id` param).

This is directly analogous to the auction bug class in the report: a security-relevant field (which stack is authorized) is checked in one place (permission bitmask) but a different, attacker-controlled field (`params[:stack_id]`) determines what is actually acted upon, with no cross-check between the two — the same "authorized value vs. acted-upon value" mismatch, just realized as a stack-scope binding instead of a bid-amount binding.

### Impact Explanation
An attacker who holds (or obtains) a stack-scoped, read-only `ApiClient` token — e.g. the CCMenu token created and exposed by `CCMenuUrlController` for embedding in third-party CI dashboards [6](#0-5)  — can supply an arbitrary `stack_id` query parameter to read the CCMenu XML status (last build status, last build label/time, activity, web URL) of any stack in the Shipit installation, including stacks it was never authorized to see. This is a read-only cross-stack information disclosure that defeats the intended per-stack token isolation, matching the "unauthorized read of stack state" High-impact category in the rules.

### Likelihood Explanation
Exploitation only requires possession of any valid, stack-scoped `ApiClient` token with `read:stack` permission (the exact kind of restricted-scope credential the feature is designed to hand out to lower-trust integrations, e.g. embedding a CCMenu badge on an external CI dashboard) and the ability to change one query-string parameter (`stack_id`). No additional privilege, signature, or session is required beyond the token itself, which is the credential the feature deliberately scopes down.

### Recommendation
Change `Api::CCMenuController#stack` (and audit any other controller overriding `#stack`) to resolve through the scoped `stacks` collection rather than the unscoped `Stack` class method, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

so it inherits the same `current_api_client.stack_id` restriction enforced in `Api::BaseController`.

### Proof of Concept
1. Create an `ApiClient` scoped to `Stack A` with only `read:stack` permission (as in the `here_come_the_walrus` fixture), and obtain its `authentication_token`.
2. Request `GET /api/stacks/:stack_a_id/ccmenu.xml?token=<token>` — succeeds as expected.
3. Request `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<token>` for an unrelated `Stack B` the token was never scoped to.
4. Observe that `CCMenuController#stack` resolves `Stack B` via the unscoped `Stack.from_param!`, and the request returns `200 OK` with `Stack B`'s CCMenu status data instead of the expected 404/403, as confirmed by `test/controllers/api/ccmenu_controller_test.rb` which never exercises the stack-scoping restriction for this controller (unlike `Api::StacksController`'s equivalent test at [7](#0-6) ).
