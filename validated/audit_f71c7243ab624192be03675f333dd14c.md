### Title
Floating-point overflow in fixed-denomination asset cap validation allows declared cap to diverge from actual issuable supply - ([File: validation.js])

### Summary
`validateAssetDefinition()` computes the total capacity of a fixed-denomination asset by summing `count_coins * denomination` for each declared denomination and requires this sum to exactly equal the declared `payload.cap`. Because `count_coins` has no upper bound check and JavaScript numbers lose integer precision beyond `Number.MAX_SAFE_INTEGER` (2^53-1), an attacker who authors an asset-definition message can construct denomination entries whose true product vastly exceeds safe-integer range. The resulting float-imprecise sum can still pass the strict `!==` equality check against `payload.cap`, analogous to the CVE-2021-37600 integer-overflow pattern where a large untrusted numeric value overflows an internal accumulator used for a size/consistency check.

### Finding Description
In `validateAssetDefinition()`, for each denomination entry only `isPositiveInteger` is enforced on both `denomination` and `count_coins`; `denomination` is additionally capped by `MAX_CAP` (9e15) but only when the network has activated `pemCurvesFixMci`, and `count_coins` is never bounded at all: [1](#0-0) 

The accumulator that is supposed to represent total supply is built purely via floating-point multiplication and addition: [2](#0-1) 

and is then compared for exact equality with the attacker-supplied `payload.cap` (already independently bounded to `<= MAX_CAP`, i.e., representable precisely): [3](#0-2) [4](#0-3) 

Because `count_coins` can be an arbitrarily large positive integer (bounded only by JS's own numeric range, not by any protocol constant), `count_coins * denomination` can exceed `Number.MAX_SAFE_INTEGER`, causing IEEE-754 rounding. An attacker can search for combinations where the rounded sum coincidentally equals the intended (smaller, precisely representable) `payload.cap`, while the denomination table actually persisted (`asset_denominations`) encodes a materially different, larger true capacity. Downstream issuance validation (`validateIndivisibleIssue` in `validation.js`) checks issued amounts strictly against the stored per-denomination `count_coins` in `asset_denominations`, not against the (corrupted) `cap` consistency check, so the true issuable total for the asset can diverge from what the `cap` field advertises to wallets, exchanges, and AAs that treat `cap` as the definitive supply ceiling.

### Impact Explanation
This falls into the "asset issuance and transfer conditions" reachable surface: any unprivileged unit poster acting as an asset issuer can post a malformed-but-valid asset-definition unit that is accepted by all full nodes (since the check is deterministic and passes network-wide), producing an asset whose declared `cap` does not match its true issuable supply. Consumers of the `cap` field (exchanges pricing the asset, AAs enforcing supply-based logic) can be misled, and the true circulating supply after full issuance across all denominations can exceed the advertised cap — a supply-inflation-class outcome relative to what validators and downstream consumers believe is the fixed ceiling.

### Likelihood Explanation
Exploitation requires only posting one asset-definition unit with a `fixed_denominations` payload and carefully chosen `denomination`/`count_coins` pairs designed to trigger float rounding equal to a smaller `payload.cap`; no special privileges, hub cooperation, or node compromise are needed. Finding a colliding combination is a mechanical search problem (choose values near/above `Number.MAX_SAFE_INTEGER`), making it feasible for a motivated attacker.

### Recommendation
- Bound `count_coins` (and the resulting per-denomination product) with an explicit protocol constant analogous to `MAX_CAP`, independent of `pemCurvesFixMci` gating.
- Use exact/arbitrary-precision arithmetic (e.g., BigInt) instead of native floating point when accumulating `total_cap_from_denominations`, and reject sums that cannot be represented exactly as a JS safe integer before the equality comparison.
- Apply the `denomination > MAX_CAP` check unconditionally rather than only after the `pemCurvesFixMci` activation.

### Proof of Concept
1. Craft an asset-definition message with `fixed_denominations: true` and `denominations` containing two entries, e.g. `{denomination: D1, count_coins: N1}` and `{denomination: D2, count_coins: N2}`, where `D1*N1 + D2*N2` computed in double-precision floating point rounds to a chosen safe value `C` (`C <= MAX_CAP`), while the mathematically exact sum is materially larger.
2. Set `payload.cap = C`.
3. Post the unit; `validateAssetDefinition()` computes `total_cap_from_denominations` via the vulnerable code at [2](#0-1)  and the equality check at [4](#0-3)  passes because of float rounding, even though the true combined denomination capacity exceeds `C`.
4. The asset is accepted network-wide with a `cap` field inconsistent with its actual per-denomination issuable totals stored in `asset_denominations`, which govern real issuance via `validateIndivisibleIssue`.
