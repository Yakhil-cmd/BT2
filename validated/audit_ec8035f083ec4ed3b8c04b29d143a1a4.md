### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no repository/stack scoping, even though the base `Handler` class already provides a repository-scoped `stacks` helper that this handler never uses. Any webhook delivered from an attacker-controlled repository whose commit `sha` collides with a commit that exists in another tenant's stack will mutate that other tenant's commit status.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`Commit.where(sha: params.sha)` should equal `Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))` (i.e., commits belonging only to the stacks of `payload.dig('repository', 'full_name')`), but it is scoped by nothing beyond the raw `sha` value: [1](#0-0) 

The `Handler` base class defines exactly the scoping primitive that should be used: [2](#0-1) 

`StatusHandler` never calls `stacks`; it queries the `commits` table across all stacks/repositories. Since GitHub's `sha` is a 40-character SHA-1 that is a pure function of an attacker-reproducible commit object (tree, parents, author/committer identity+timestamp), an attacker who can learn a victim commit's exact metadata (commit messages, author/committer names, emails, timestamps — routinely public) can replicate a commit object with an identical SHA in a repository they control, push it, and cause GitHub to emit a `status` event referencing that SHA to Shipit's `/webhooks` endpoint for their own repository.

`StatusHandler#process` then finds every `Commit` row in the database — across all stacks belonging to all tenants — with that SHA, and calls `commit.create_status_from_github!(params)` on each one, which writes a new `Status`, potentially changes `commit.status`, and can trigger `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges`, all attributed to the victim stack.

No control anywhere in the chain narrows this by repository: `StatusHandler` does not call `stacks`, and `Commit` has no uniqueness constraint tying `sha` to a specific repository across the whole table (only within a stack's own history is a sha typically unique in practice, not enforced against other stacks). Signature verification (`verify_signature`/webhook secret check) only proves the payload came from GitHub for *some* registered repository — it says nothing about whether the `sha` inside that payload actually belongs to that repository, and `StatusHandler` performs no post-verification repository check.

### Impact Explanation
A single crafted GitHub `status` webhook, delivered from a repository the attacker fully controls, can cause Shipit to write a `Status` record and flip the computed status/deployability of a commit belonging to an arbitrary, unrelated victim stack, without ever authenticating against that victim's repository. This can toggle `deployable?` state, trigger `schedule_continuous_delivery` and merge scheduling (`stack.schedule_merges`) on the victim stack, and fire hooks that downstream systems trust for deploy automation — a payload for one repository mutating another's stack/commit, matching the Critical "cross-tenant write" category defined in scope.

### Likelihood Explanation
Practical exploitation costs the attacker: (1) discovering a target commit's exact sha and full commit metadata (tree hash implicitly, author, committer, timestamps, message, parent shas) — the message/author/timestamps are typically public via Shipit's own commit UI/API or GitHub's public commit view; (2) reconstructing an identical git commit object and pushing it to an attacker-owned repository, which is purely a `git` operation requiring no Shipit or GitHub secret; (3) having that repository connected to Shipit's webhook endpoint (the attacker can create a Shipit stack for their own repository if the instance allows arbitrary repo registration, or the webhook is delivered via GitHub's normal signed delivery for a repo already registered with Shipit). No `Shipit.github_teams` membership, API token, or session is required. This is fully repeatable against any known/inferable sha.

### Recommendation
Scope the lookup by the reporting repository, mirroring the `stacks` helper already defined in `Handler`:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures a status payload can only affect commits belonging to stacks tied to `payload.dig('repository', 'full_name')`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` for repository `"victim/repo"` and `stack_b` for repository `"attacker/repo"`.
2. Create `commit_a` on `stack_a` and `commit_b` on `stack_b`, both with the same `sha = "a" * 40`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha = "a" * 40`, `state = "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert both `commit_a.reload.status.state` and `commit_b.reload.status.state` become `"success"` — proving the equality `Commit.where(sha:)` == `Commit.where(sha:, stack: victim_stack)` does NOT hold, since `commit_a` (belonging to `stack_a`/"victim/repo") was mutated by a payload declaring `repository.full_name = "attacker/repo"`.
