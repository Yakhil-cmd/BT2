### Title
Fork PR label `IFS` reaches `bash script/release.sh` subprocess env via `ReviewStack#env` / `Command#unbundled_env` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an env var with value `"true"` with no allowlist or denylist, and `Command#unbundled_env` merges `@env` last (highest precedence) into the hash passed to `PTY.spawn`. An unprivileged fork PR author can label their own PR `ifs` to inject `IFS=true` into any step (e.g. `bash script/release.sh`) run for that review stack.

### Finding Description
The broken binding: `PTY.spawn` environment for a step SHOULD equal `BASE_ENV` merged with only Shipit-defined/task-defined keys, but it actually equals `BASE_ENV.merge(PATH).merge(@env.stringify_keys)` where `@env` includes attacker-controlled label names uppercased, per `Command#unbundled_env` [1](#0-0) . The path is: webhook `labeled`/`pull_request` event → `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim onto `PullRequest#labels` [2](#0-1)  → `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` with no key filtering [3](#0-2)  → `TaskCommands#env` merges `@stack.env` into the task's step env [4](#0-3)  → each step (including `bash script/release.sh`) is spawned as `Command.new(command_line, env:, chdir: ...)` [5](#0-4)  → `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` where `unbundled_env` merges `@env` last [6](#0-5) . Existing tests confirm this merge behavior explicitly (`WIP`/`BUG` labels become env vars) [7](#0-6) [8](#0-7) . Nothing in `EnvironmentVariables`, `Command`, or `ReviewStack` denies specific keys like `IFS`, `BASH_ENV`, `LD_PRELOAD`, `PATH`, etc.

However, whether this is exploitable to change bash's word-splitting behavior on `script/release.sh` depends on how `bash script/release.sh` is invoked: GitHub label names are arbitrary strings but must satisfy GitHub's label-name constraints (no strict format restriction is enforced server-side by Shipit; GitHub itself allows most characters). The label name `ifs` uppercases to `IFS`, which is a legitimate, unblocked env var key that would get set to `"true"`. Bash's `IFS` variable does affect word splitting of unquoted variable expansions and command substitution within the script's own shell, but the deploy step string `bash script/release.sh` itself is a fixed argv passed through `interpolated_arguments` and `Shellwords`-safe invocation — it is not passed through a shell that would re-split it based on `IFS` at the `Command` level (the argv is already an array of strings, not re-parsed by a shell using `$IFS`). The actual impact is that `IFS` becomes an environment variable inherited by the `bash script/release.sh` process, potentially altering behavior of that script if the script itself uses unquoted variable expansions relying on default `IFS` — this is a property of the arbitrary user-controlled `script/release.sh`, not a guaranteed RCE primitive introduced by Shipit itself. Regardless of the specific `IFS` semantics, the underlying, demonstrable vulnerability is real and matches the target's own "Fast validation": `Command#unbundled_env` passes attacker-controlled `IFS` to the spawned process unfiltered.

### Impact Explanation
Any fork PR author who can label their own PR can inject arbitrary environment variable keys (uppercased) into every step run for that review stack's deploy/task, including `bash script/release.sh`. This is scoped to the review stack created for that specific PR/repository (the label name is stored on that PR's `labels` and merged only into that stack's `env`), so it does not cross-contaminate other repositories' stacks, but within the affected review stack it allows env-var injection into scripts executed on the Shipit deploy host — matching the "Critical: RCE on deploy host via `Command`/`PTY.spawn`" category if the injected variable (e.g. `IFS`, `BASH_ENV`, or other shell-behavior-altering variables) is leveraged by the specific `script/release.sh` implementation to alter parsing/execution. This is repeatable on every deploy of that review stack as long as the label remains applied.

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled (`review_stacks_enabled`), the attacker must be able to open a PR and add a label to it (labeling permission is often available to PR authors, or automatically applied via GitHub Actions/bots depending on repo config — this varies per repository and is not solely gated by Shipit). No Shipit credentials are required beyond triggering the standard `pull_request`/`labeled` webhook that Shipit already processes. The cost is trivial (open PR, add label). Exploitability of the `IFS`-specific attack further depends on `script/release.sh` unsafely relying on default `IFS` in unquoted expansions, which is outside Shipit's own code.

### Recommendation
In `ReviewStack#env` (app/models/shipit/review_stack.rb, lines 84-93), filter label-derived environment variable keys against an allowlist (e.g. only alphanumeric/underscore keys not colliding with reserved/dangerous shell variables such as `IFS`, `PATH`, `BASH_ENV`, `LD_PRELOAD`, `ENV`, `SHELLOPTS`), or prefix all label-derived keys with a fixed namespace (e.g. `LABEL_<NAME>`) so they can never collide with security-sensitive environment variable names.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb`):
```ruby
test "#env allows a pull request label to inject IFS" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["ifs"]

  assert_equal "true", stack.env["IFS"]

  task = shipit_tasks(:shipit_restart)
  task.stack = stack
  command = Shipit::Command.new("bash script/release.sh", env: Shipit::TaskCommands.new(task).env, chdir: ".")

  assert_equal "true", command.unbundled_env["IFS"]
end
```
This demonstrates `Command#unbundled_env` passes the attacker-controlled `IFS` key unfiltered to the spawned process, confirming the binding break the question describes. Full weaponization into RCE depends on the specific content of `script/release.sh`, which is outside this engine's code.
