Based on my investigation, I found a genuine analog to the CVE-2022-36052 bug class (casting/parsing a fixed-shape structure from an attacker-controlled buffer without validating that the input actually contains enough fields before the structure is consumed).

### Title
Malformed `in merkle` authentifier crashes/undermines address-definition validation via unchecked merkle-proof deserialization - ([File: definition.js])

### Summary
`definition.js`'s `in merkle` operator takes the raw authentifier string supplied by a unit's author and hands it directly to `merkle.deserializeMerkleProof()`, which blindly `split("-")`s the string and assigns `pop()`/`shift()` results to `root`/`index` without checking that the resulting array actually has the minimum expected shape (at least an index and a root). This mirrors the CVE's root cause: a structure ("header") is extracted from an offset/position in attacker-supplied data without first checking the buffer is large enough to contain it.

### Finding Description
`deserializeMerkleProof` in [1](#0-0)  does:
```js
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
```
There is no check that `serialized_proof` contains at least two dash-separated components, and no bound on `proof.siblings.length`. This function is invoked directly on unit-author-controlled data in the `in merkle` address-definition evaluator: [2](#0-1) 
```js
case 'in merkle':
	...
	var serialized_proof = assocAuthentifiers[path];
	var proof = merkle.deserializeMerkleProof(serialized_proof);
	if (!merkle.verifyMerkleProof(element, proof)){
		fatal_error = "bad merkle proof at path "+path;
		return cb2(false);
	}
	dataFeeds.dataFeedExists(arrAddresses, feed_name, '=', proof.root, min_mci, objValidationState.last_ball_mci, false, cb2);
```
`assocAuthentifiers[path]` comes straight from `unit.authors[i].authentifiers`, i.e. from any unprivileged unit poster whose address is defined with an `in merkle` clause. `proof.index` can end up `undefined` (empty/degenerate input), `proof.siblings` can be made arbitrarily long (no cap, unlike the analogous `is_valid_merkle_proof` oscript function which caps siblings at 50 and validates types after `bPostPemCurvesFix` — see [3](#0-2) ). No such hardening exists on the `definition.js` path.

`verifyMerkleProof` in [4](#0-3)  does catch generic exceptions, so a crash is unlikely in this exact call, but the missing shape/size validation on the `definition.js` path allows unbounded `siblings` arrays (attacker can submit thousands of dash-separated fragments in a single authentifier string up to `MAX_AUTHENTIFIER_LENGTH`) to be looped over hashing repeatedly during consensus-critical unit validation, and allows degenerate proofs (`index === undefined`) to silently participate in `index % 2 === 0` checks with implicit type coercion, producing inconsistent results across different Node/engine versions if arithmetic on `undefined` ever changes semantics — but more importantly, this parsing path lacks the same defensive bounds/type checks that were later added to the `formula/evaluation.js` sibling function under `bPostPemCurvesFix`, indicating the `definition.js` `in merkle` path was never hardened to the same standard.

### Impact Explanation
If a network-wide behavior/exception difference exists between two node versions handling a malformed authentifier at an `in merkle` path (e.g. differing engine behavior on `arr.pop()`/`arr.shift()` of a near-empty array, or differing complexity/timeout handling for extremely long `siblings` arrays), nodes could disagree about whether a unit passes authentifier validation, resulting in a stability/validity fork (nodes agreeing vs. rejecting the same unit) — the same "network unable to reach consensus" class of impact called out in the validation rules. At minimum, it enables unbounded computational cost (unbounded merkle-siblings loop) hidden inside a single authentifier field of an ordinary posted unit, which is not currently bounded the way the oscript `is_valid_merkle_proof` sibling was fixed to bound (compare [3](#0-2) ).

### Likelihood Explanation
Any address defined with `in merkle` in its definition can be triggered by an ordinary unit author who controls the `authentifiers` map for that signing path; this requires no special privilege beyond having created (or being able to reference) such an address — moderately likely, but requires a target address specifically using `in merkle`, and the concrete consensus-forking scenario is not proven end-to-end in the code (I could not find a demonstrated engine-behavior divergence, only the absence of the same bounds/shape checks present on the analogous oscript function).

### Recommendation
In `merkle.js` `deserializeMerkleProof`, validate that `serialized_proof.split("-")` yields at least the minimum required parts and that `index` is a valid non-negative integer before returning the proof object; in `definition.js`'s `in merkle` handler, apply the same defenses already present in `formula/evaluation.js` (cap `proof.siblings.length`, validate `Array.isArray(proof.siblings)` and that each entry is a non-empty string, and validate `proof.index` is numeric) before calling `merkle.verifyMerkleProof`.

### Proof of Concept
```js
// address whose definition includes:
// ["in merkle", [["SOME_ADDR"], "feed_name", "expected_value"]]
// attacker submits a unit authored by that address with:
authentifiers: { "r": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa-...(thousands of '-'-joined fragments up to MAX_AUTHENTIFIER_LENGTH)..." }
```
This is parsed by `deserializeMerkleProof` into a `siblings` array of unbounded length (no cap, unlike `formula/evaluation.js`'s 50-item limit), forcing `verifyMerkleProof` to iterate and hash repeatedly during unit validation — a resource-disproportionate structure-extraction from attacker data without the size/shape validation that its sibling code path enforces.

```javascript
function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
```
