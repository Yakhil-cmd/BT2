### Title
Cross-tenant `ReviewStack` mutation via divergent `organization` vs `repository.full_name` fields on `pull_request` `reopened` webhook - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#repository_owner` selects the webhook secret to verify against using `params.dig('repository','owner','login') || params.dig('organization','login')`, while `ReopenedHandler` and downstream `ReviewStackAdapter` act on `params.repository.full_name`. Because these are two independent, attacker-controlled JSON paths in the same raw payload, an attacker can get the request authenticated as organization A while the handler mutates a repository/stack belonging to organization B.

### Finding Description
The broken invariant is: `repository_owner (used to select verifying secret) == owner(repository.full_name) (used by the handler to select the mutated repository)`. This must always hold for signature verification to be meaningful, but the code enforces no such linkage.

- `verify_signature` resolves the verifying `GitHubApp` via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) .
- `ReopenedHandler` and `ReviewStackAdapter` never look at `organization.login` or `repository.owner.login`; they derive the acted-upon repository strictly from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , and locate/create the `ReviewStack` scoped to that repository's `review_stacks` and `pr#{params.number}` environment [3](#0-2) .
- The `ReopenedHandler`'s `ExplicitParameters` schema only `requires :repository { requires :full_name }` — it never requires `repository.owner.login`, so a payload can legally omit that sub-key while still supplying `repository.full_name` [4](#0-3) . When `repository.owner.login` is absent, `repository_owner` silently falls back to `organization.login`, a completely separate top-level key the attacker also controls.
- `Shipit.github(organization:)` resolves per-organization config (`github_app_config(organization)`), each of which can have its own `webhook_secret`; `verify_webhook_signature` compares the request's signature only against that specific organization's secret [5](#0-4) [6](#0-5) .

Exploit flow (multi-organization Shipit deployment, i.e. `github_default_organization` is not `nil`): the attacker administers organization A (onboarded to the same Shipit instance) and knows A's `webhook_secret` (it is a value they/their org configured on both the GitHub and Shipit sides, not a Shipit- or GitHub-internal secret). They POST directly to `/webhooks` with:
- `X-Github-Event: pull_request`, a valid `X-Hub-Signature` computed with A's `webhook_secret`,
- body: `action: "reopened"`, `organization: { login: "org-A" }`, `repository: { full_name: "victim-org/victim-repo" }` (note: no `repository.owner.login`), plus attacker-chosen `pull_request.head.{sha,ref}`, `number`, `labels`, `sender.login`.

`repository_owner` computes to `"org-A"` (fallback), so `verify_signature` authenticates the request using org A's secret and succeeds. `ReopenedHandler#repository` resolves to the victim's `Repository` record (`victim-org/victim-repo`) because it reads `params.repository.full_name` directly, bypassing any relationship to the authenticating organization. If that victim repository has `review_stacks_enabled` and a matching `provisioning_behavior`, `stack.unarchive!`/`create!` creates or unarchives a `ReviewStack` under the victim repository, populated with the attacker-supplied PR fields, and enqueues it for provisioning [7](#0-6) .

None of the existing guards close this gap: `drop_unhandled_event` and `check_if_ping` only filter by event type; `verify_signature` verifies a signature against the *wrong* selector, not against the repository the handler will actually mutate; the `ExplicitParameters` schema validates shapes but never cross-checks `organization.login`/`repository.owner.login` against `repository.full_name`.

The "shared commit SHA" amplification described in the exploit idea does not apply specifically to `ReopenedHandler`: the `ReviewStack` lookup in `ReviewStackAdapter#stack` is scoped by `environment: "pr#{params.number}"` within `repository.review_stacks` (already scoped to the resolved victim repository), not by a global bare-SHA lookup [8](#0-7) . The core, demonstrable cross-tenant issue is the `organization`/`repository.full_name` divergence itself, independent of any shared-SHA collision.

### Impact Explanation
An attacker who legitimately controls one organization onboarded to a multi-tenant Shipit instance can cause `ReviewStack` records to be created or unarchived under a victim organization's repository, using PR metadata (branch ref, head SHA, labels) they fully control. This is a payload authenticated for organization A mutating organization B's stack/PR state, matching the "Critical — a payload for one repository mutating another's stack" category. The action is repeatable against any victim repository whose `full_name` the attacker knows and which has review-stacks enabled, as long as the attacker's own organization remains configured in Shipit with a distinct `webhook_secret`.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (`github_default_organization` not `nil`, i.e. `secrets.github` keyed by multiple organizations) — in single-organization/legacy config, `Shipit.github` ignores the `organization:` argument and always uses the single global config, closing this path; (2) the attacker's own organization is one of the configured tenants, with a `webhook_secret` the attacker knows (a normal condition for a legitimate tenant who set up the webhook themselves); (3) the victim repository exists in Shipit with `review_stacks_enabled` and a matching `provisioning_behavior`. Given those preconditions — realistic for a genuinely multi-tenant Shipit install — the attack is cheap (a single crafted HTTP POST) and fully repeatable.

### Recommendation
Bind signature verification to the same repository the handler will act on: derive `repository_owner` exclusively from `params.dig('repository','owner','login')` (or, better, from the resolved `repository.full_name`'s registered owner) and reject the webhook if that key is absent, rather than falling back to the independent `organization.login` field. Additionally, after verifying the signature, assert that the organization used for verification matches the owner of `repository.full_name` before invoking any handler.

### Proof of Concept
Minitest plan (`test/controllers/shipit/webhooks_controller_test.rb`, hypothetical, requires multi-org Shipit config fixture):
1. Configure two organizations in test credentials: `org-a` (`webhook_secret: 'secret-a'`) and `victim-org` (`webhook_secret: 'secret-victim'`).
2. Create `Shipit::Repository` for `victim-org/victim-repo` with `review_stacks_enabled: true`, `provisioning_behavior: allow_all`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, signature computed as `HMAC-SHA1('secret-a', raw_body)`, and body:
   ```json
   {
     "action": "reopened",
     "number": 42,
     "organization": {"login": "org-a"},
     "repository": {"full_name": "victim-org/victim-repo"},
     "pull_request": {"id":1,"number":42,"url":"...","title":"x","state":"open","additions":1,"deletions":1,
       "head":{"sha":"deadbeef","ref":"attacker-branch"},"user":{"login":"attacker"},"assignees":[],"labels":[]},
     "sender": {"login": "attacker"}
   }
   ```
4. Assert response is `200 OK` (signature accepted under `org-a`'s secret).
5. Assert `Shipit::ReviewStack.find_by(environment: "pr42")` exists and is scoped to the `victim-org/victim-repo` repository — i.e. `equality: repository_owner ("org-a") != owner_of(repository.full_name) ("victim-org")`, yet the mutation still occurred against `victim-org`'s repository, proving the divergence and the cross-tenant write.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
