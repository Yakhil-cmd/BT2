### Title
Terminal escape-sequence injection via unsanitized `X-Accepted-Oauth-Scopes` header in `generateScopesSuggestion` - ([File: api/client.go])

### Summary
`generateScopesSuggestion` builds a user-facing suggestion string using a scope value taken directly from the attacker-controllable `X-Accepted-Oauth-Scopes` response header, and while the first placement of that value uses the safe `%q` verb (which escapes control characters), a second placement in the same format string uses the raw `%s` verb, embedding the unescaped header value into text that is ultimately printed to the user's terminal. This allows a malicious/compromised API host to inject raw ANSI/terminal control sequences into `gh`'s error/suggestion output.

### Finding Description
`generateScopesSuggestion` iterates over the comma-separated values of the `endpointNeedsScopes` parameter (populated from the `X-Accepted-Oauth-Scopes` response header) and, for the first scope not already present in the token's granted scopes, formats a message: [1](#0-0) 

The format string is:
```
"This API operation needs the %[1]q scope. To request it, run:  gh auth refresh -h %[2]s -s %[1]s"
```
The value `s` (attacker-controlled scope string from the trimmed header) is used twice with argument index `[1]`: once as `%[1]q` (Go's quoted-string verb, which escapes non-printable/control bytes into literal `\xNN`/`\n` textual sequences — safe), and once as `%[1]s` in the `-s %[1]s` clause, which performs no escaping and inserts the raw bytes verbatim, including any ANSI escape sequences (e.g., cursor movement, screen clear, hidden text, fake prompt sequences) the attacker places in the header value.

This function is reached from `handleResponse` (called by `HandleHTTPError`, `REST`, `GraphQL`, `Mutate`, `Query`, `QueryWithContext`) which passes `restErr.Headers.Get("X-Accepted-Oauth-Scopes")` and `restErr.Headers.Get("X-Oauth-Scopes")` straight from the HTTP response headers with no sanitization: [2](#0-1) 

and from the standalone `ScopesSuggestion` helper used elsewhere (e.g. `pkg/cmd/ssh-key/list/list.go`, `internal/ghcmd/cmd.go`) which does the same header-to-string pass-through: [3](#0-2) 

No host allowlist, character filtering, or output sanitization exists between the raw header value and the final printed string. Since HTTP response headers are fully controlled by the server `gh` is talking to (a malicious/compromised host the victim points `gh` at, or any GHES-like endpoint), the attacker can set `X-Accepted-Oauth-Scopes: \x1b[2J\x1b[H<spoofed text>` (or similar) to have raw escape bytes flow through the `-s %[1]s` substitution into the message printed on the user's terminal.

### Impact Explanation
This enables terminal escape-sequence injection / prompt spoofing in `gh`'s own error output: an attacker-controlled host can clear/rewrite terminal content, hide or alter displayed text, or attempt to spoof a fake success/prompt message when the victim's `gh` command hits a 4xx response from that host. This maps to a low/informational client-side output-spoofing issue (terminal injection / misleading UI) rather than code execution or credential exfiltration — the impact is limited to what can be achieved by injecting ANSI control codes into a terminal (visual deception, potentially tricking a user into taking an action based on spoofed text), not remote code execution, since `gh` does not execute the resulting string as a shell command; it only prints it.

### Likelihood Explanation
Requires the victim to run any `gh` command (REST/GraphQL) against a host that returns a 4xx (excluding 422) response with a crafted `X-Accepted-Oauth-Scopes` header not already covered by `X-Oauth-Scopes`. This is trivially achievable by anyone who controls the API endpoint (custom GHES host, malicious proxy, or a compromised legitimate host) the victim is configured to talk to — no auth, no privileges needed beyond controlling response headers. Feasibility is high given the header value is copied without validation.

### Recommendation
Use the same escaped/quoted representation (`%q`) for the `-s` flag placeholder as well, or explicitly sanitize the scope string (strip non-printable/control characters, restrict to an expected charset such as `[A-Za-z0-9_:-]`) before formatting it into the suggestion message. Since OAuth scope names are inherently constrained to a small known set of tokens, validating against an allowlist/regex before use in any user-facing string is the safest fix.

### Proof of Concept
Go test (httpmock-based) sketch:
```go
func TestGenerateScopesSuggestion_EscapeInjection(t *testing.T) {
    // Craft header value with raw ESC (0x1b) bytes
    malicious := "repo\x1b[2J\x1b[Hfake-prompt"
    msg := generateScopesSuggestion(404, malicious, "public_repo", "github.com")
    if strings.Contains(msg, "\x1b[2J") {
        t.Fatalf("raw escape sequence leaked into suggestion string: %q", msg)
    }
}
```
Expected (current/vulnerable) behavior: `msg` contains the literal ESC byte sequence unescaped in the `-s %[1]s` portion (since `%[1]s` doesn't escape it), even though the `%[1]q` portion escapes it correctly — demonstrating the inconsistency and the leak point. After the fix (using `%q` for both, or sanitizing), the assertion should pass with no raw control bytes present in `msg`.
