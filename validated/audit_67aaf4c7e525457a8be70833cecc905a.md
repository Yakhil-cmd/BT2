### Title
KLAY Permanently Locked When Smart Contract Triggers Bridge Fallback With Undeliverable Destination — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

The fallback function in `BridgeTransferKLAY` hardcodes `msg.sender` as the `_to` (recipient) address on the destination chain. If `msg.sender` is a smart contract that does not exist on the destination chain, or exists but cannot receive native KLAY, the bridge operator's `handleKLAYTransfer` call will always revert, permanently locking the deposited KLAY in the source bridge with no recovery path.

### Finding Description

The fallback function in `BridgeTransferKLAY.sol` is:

```solidity
// () requests transfer KLAY to msg.sender address on relative chain.
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [1](#0-0) 

`msg.sender` is passed directly as the `_to` argument, which becomes the recipient address on the counterpart chain. There is no check that `msg.sender` is an EOA, and no way for the caller to specify a different recipient.

On the destination chain, operators call `handleKLAYTransfer`, which performs:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [2](#0-1) 

If `_to` is a contract address that reverts on receiving KLAY (no `receive()`/`fallback()`, or one that explicitly reverts), the `require` causes the entire `handleKLAYTransfer` transaction to revert. Because all state changes — including `_setHandledRequestTxHash`, `handleNoncesToBlockNums`, and `_updateHandleNonce` — occur before the transfer and are rolled back on revert, the nonce is never marked as handled. [3](#0-2) 

The value transfer recovery system (`vt_recovery.go`) will detect the pending nonce and repeatedly re-submit the handle transaction, but every attempt will revert for the same reason. [4](#0-3) 

### Impact Explanation

- The user's KLAY deposited into the source bridge is permanently locked: the source bridge holds the funds, the destination handle always fails, and there is no refund or cancel mechanism in the bridge contract.
- The `lowerHandleNonce` cannot advance past the stuck nonce, which also prevents the recovery block number from advancing for that slot, degrading the recovery system's accounting.
- Affected asset: native KLAY bridged via the service-chain bridge.

### Likelihood Explanation

Any smart contract can trigger the bridge fallback by sending KLAY to the bridge address. This is a normal pattern (e.g., a multisig, a DeFi protocol, or a contract-based wallet initiating a cross-chain transfer). The child chain and parent chain may be entirely different EVM deployments where the same contract address either does not exist or has different bytecode. No special privilege is required.

### Recommendation

Remove the hardcoded `msg.sender` as `_to` in the fallback function, or require the caller to be an EOA (`require(msg.sender == tx.origin)`). Alternatively, mirror the `requestKLAYTransfer` pattern and require an explicit `_to` argument even for the fallback path. The named function already does this correctly:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
``` [5](#0-4) 

The fallback should either be removed or restricted to EOA callers only, since there is no way to pass a safe recipient address through a plain KLAY transfer.

### Proof of Concept

1. Deploy a smart contract `Caller` on the child chain that has no `receive()` function (or one that reverts).
2. From `Caller`, send KLAY to the child bridge address, triggering the fallback:
   ```solidity
   bridgeAddress.call{value: 1 ether}("");
   ```
3. The bridge emits `RequestValueTransfer` with `from = Caller`, `to = Caller`.
4. The bridge operator observes the event and calls `handleKLAYTransfer` on the parent bridge with `_to = Caller`.
5. The parent bridge attempts `Caller.call{value: 1 ether}("")` — this reverts because `Caller` has no payable fallback.
6. `require(ok, "handleKLAYTransfer: transfer failed")` causes the entire operator transaction to revert.
7. The nonce is never marked handled; the 1 KLAY is permanently locked in the child bridge with no recovery path. [1](#0-0) [2](#0-1)

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))

		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))

	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))

	}
