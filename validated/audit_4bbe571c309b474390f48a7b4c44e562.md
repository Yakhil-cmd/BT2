### Title
Vote-account `pending_delegator_rewards` pool is never decremented after being distributed as `block_reward`, allowing repeated re-distribution of the same deposit - (File: `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
The `DepositDelegatorRewards` vote instruction lets **any signer** move lamports into a vote account and increment a shared pool field, `pending_delegator_rewards` [1](#0-0) . Each epoch, `calculate_block_reward` reads this pool value and pays out `pending_delegator_rewards * stake / total_active_stake` to *every* currently-delegated stake account [2](#0-1) . Across all searched call sites (`vote_state/handler.rs`, `vote_state/mod.rs`, `vote_processor.rs`, `calculation.rs`, `distribution.rs`) the only mutator of `pending_delegator_rewards` found is `add_pending_delegator_rewards` [3](#0-2) ; no corresponding subtraction/reset of the vote account's own `pending_delegator_rewards` field after a `block_reward` payout was located in the distribution path (`store_stake_accounts_in_partition` / `build_updated_stake_reward`) [4](#0-3) . This mirrors the reported `Rewards.sol` pattern: a shared, externally-fundable pool whose "amount owed" bookkeeping is not kept in sync with what has actually been paid out to participants, so the same pool balance is repeatedly consumed to compute proportional payouts to a changing set of participants.

### Finding Description
`deposit_delegator_rewards` is a permissionless, single-transaction-reachable instruction: any signer can transfer lamports to a vote account and call `add_pending_delegator_rewards`, which only ever `checked_add`s to the `pending_delegator_rewards` u64 field [3](#0-2) [5](#0-4) .

At each epoch boundary, `calculate_block_reward` reads `pending_delegator_rewards` from the vote account and computes, for every stake delegated to that vote account, `block_reward = pending_delegator_rewards * stake / total_active_stake` (clamped to `pending_delegator_rewards`) [6](#0-5) . This is invoked once per stake delegation from `calculate_stake_rewards_and_commissions` [7](#0-6) , and the resulting `block_reward` lamports are credited directly to each stake account by `checked_add_lamports` during distribution [8](#0-7) , funded by increasing bank `capitalization` rather than by debiting the vote account's actual lamport balance [9](#0-8) .

Nowhere in the reachable distribution code (`store_stake_accounts_in_partition`, `build_updated_stake_reward`, `distribute_epoch_rewards_in_partition`) does the vote account's own `pending_delegator_rewards` field get reduced by the amount just paid out as `block_reward`. The only bookkeeping observed elsewhere is the *withdraw*-side check that reserves `pending_delegator_rewards` lamports so the vote-account's authorized withdrawer cannot pull out that reserve [10](#0-9) . Because that same value also feeds `calculate_block_reward` every epoch, and I did not find code that clears/decrements it after a distribution round, the pool behaves exactly like the vulnerable `Rewards.sol` accessory pool: a single `addRewardsForAccessory`-style deposit (`DepositDelegatorRewards`) is redistributed on every subsequent epoch to whichever set of stake accounts happens to be delegated at that time, since the "amount already paid" state is never subtracted from the pool that governs future proportional splits.

**Caveat on verification:** I was not able to fully inspect every code path that touches vote-account serialization during distribution (e.g. whether `store_commission_accounts_partitioned` / `update_reward_commissions` incidentally touches `pending_delegator_rewards`); if such a decrement exists elsewhere it would need to be confirmed by directly reading `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` (`distribute_reward_commissions`) and `runtime/src/bank/partitioned_epoch_rewards/sysvar.rs` in full. This should be validated in a live/Devin session before treating the finding as fully proven.

### Impact Explanation
If confirmed, this is an unbounded lamport-minting bug reachable from a single unprivileged transaction: one `DepositDelegatorRewards` call (or block-revenue commission deposit) would be redistributed as `block_reward` to the vote account's delegators every epoch indefinitely, each time increasing bank `capitalization` [9](#0-8) . This breaks the lamport/rent conservation invariant that stake-reward accounting is supposed to preserve, corrupting stake-account balances cluster-wide and effectively minting SOL out of thin air with no signature/authorization requirement beyond a one-time small deposit.

### Likelihood Explanation
The pool is populated by an instruction (`DepositDelegatorRewards`) that any signer can invoke without special privilege, and consumption of the pool happens automatically every epoch via `calculate_block_reward` for any stake delegated to that vote account — no further transactions are required to trigger repeated payouts once the initial deposit is made. This makes the bug, if the missing decrement is real, trivially and repeatedly triggerable.

### Recommendation
Verify whether `pending_delegator_rewards` is decremented (or reset to the un-distributed remainder) as part of `distribute_reward_commissions` / `store_stake_accounts_in_partition` / a dedicated `subtract_pending_delegator_rewards` handler call at distribution time. If no such decrement exists, add one so that each vote account's `pending_delegator_rewards` field is reduced by exactly the sum of `block_reward` amounts paid out across all partitions for that vote account before the next epoch's `calculate_block_reward` reads it, ensuring the pool cannot be redistributed more than once per deposited lamport.

### Proof of Concept
Conceptual reproduction (pending confirmation that no decrement exists):
1. Attacker submits `VoteInstruction::DepositDelegatorRewards { deposit: X }` for a vote account with active stake delegations, transferring `X` lamports and setting `pending_delegator_rewards = X` [1](#0-0) .
2. At the next epoch boundary, `calculate_block_reward` pays out `~X` lamports total (proportional to stake) to all delegators of that vote account, funded by increasing `capitalization` [11](#0-10) , [9](#0-8) .
3. If `pending_delegator_rewards` in the vote account is not reduced after step 2, the next epoch's `calculate_block_reward` reads the same (unchanged) `pending_delegator_rewards = X` and pays out `~X` lamports again to the (possibly different) set of currently-delegated stakers.
4. Repeat indefinitely: a single one-time deposit of `X` lamports results in unbounded repeated minting of `X`-sized rewards every epoch, with capitalization growing without bound from a single transaction.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

    fn build_updated_stake_reward(
        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
        use_fixed_point_stake_math: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;

        let mut new_stake = partitioned_stake_reward.inflation.stake;
        if adjust_delegations_for_rent {
            let minimum_balance = rent.minimum_balance(account.data().len());
            // The rewarded epoch is right before the distribution epoch
            let rewarded_epoch = distribution_epoch.saturating_sub(1);
            // The entry in `partitioned_stake_reward` contains the rewards,
            // calculated during the calculation phase
            let delegation_with_rewards = new_stake.delegation.stake;
            adjust_delegation_for_rent(
                &mut new_stake.delegation,
                rewarded_epoch,
                delegation_with_rewards,
                account.lamports(),
                minimum_balance,
            );
        } else {
            let expected_delegation = stake
                .delegation
                .stake
                .saturating_add(partitioned_stake_reward.inflation.stake_reward);
            assert_eq!(
                expected_delegation, new_stake.delegation.stake,
                "stake reward delegation must be consistent with the updated stake account \
                 lamport balance"
            );
        }
        account
            .set_state(&StakeStateV2::Stake(meta, new_stake, flags))
            .map_err(|_| DistributionError::UnableToSetState)?;

        let stake_at_distribution_epoch = delegation_effective_stake(
            &new_stake.delegation,
            distribution_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        let reward_type = if stake_at_distribution_epoch == 0 {
            RewardType::DeactivatedStake
        } else {
            RewardType::Staking
        };
        Ok(StakeReward {
            stake_pubkey: partitioned_stake_reward.stake_pubkey,
            stake_reward_info: StakeRewardInfo {
                reward_type,
                lamports: i64::try_from(
                    partitioned_stake_reward.inflation.stake_reward
                        + partitioned_stake_reward.block_reward,
                )
                .unwrap(),
                post_balance: account.lamports(),
                commission_bps: partitioned_stake_reward.inflation.commission_bps,
            },
            stake_account: account,
        })
    }
