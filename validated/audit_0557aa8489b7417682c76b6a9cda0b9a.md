## Title
Emergency OP-list vote count treats still-unstable (non-final) votes as final, allowing OP-list hijack while MC stability is stalled - ([File: main_chain.js])

### Summary
The emergency OP-list change mechanism in `main_chain.js` is intended to unblock the network if MC stability gets stuck because the `op_list` vote can't reach consensus. When triggered (after the chain has been "stuck" longer than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT`), it counts not only stable votes but also *unstable* votes that are merely older than `EMERGENCY_COUNT_MIN_VOTE_AGE` (1 hour), treating their current tentative `sequence='good'` status as final. This is structurally identical to the TaikoL1 bug class: a mechanism meant to recover from a paused/stalled state ends up skipping the normal "contest window" (here, full MC stabilization / double-spend resolution) for pending state, allowing a not-yet-final vote to be baked into a permanent, security-critical protocol parameter (the OP list).

### Finding Description
Any unprivileged unit author can post a `system_vote` (`op_list`) message and a `system_vote_count` message (`app: 'system_vote_count', payload: 'op_list'`), as validated in [1](#0-0)  and composed the same way for genesis in [2](#0-1) .

When a `system_vote_count` unit for `op_list` is written, `writer.js` calls `main_chain.applyEmergencyOpListChange` with the *author-supplied* unit timestamp: [3](#0-2) 

`applyEmergencyOpListChange` only checks that the last **stable** unit is older than `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) — i.e., that MC stability is "paused"/stuck — and then immediately triggers an emergency vote count: [4](#0-3) 

`countVotes` with `is_emergency=1` pulls in **unstable** votes via `getUnstableVotes`, which only requires that the voting unit currently has `sequence === 'good'` and is older than `EMERGENCY_COUNT_MIN_VOTE_AGE` (1 hour) — it does **not** require the unit to be stable/final: [5](#0-4) 

These unstable votes are merged with the persisted `op_votes` and used to compute a brand-new OP list, which is written permanently into `system_vars` with `is_emergency=1`: [6](#0-5) [7](#0-6) [8](#0-7) 

`sequence='good'` is only a *tentative* classification made during initial validation; a unit's finality (and thus whether it truly counts, e.g. after double-spend resolution turns it `final-bad`) is normally only established once the unit becomes **stable**, which is exactly the mechanism that is stuck when this emergency path fires. In other words, the very condition that triggers the emergency count (MC stability being stalled) is the condition under which "good-but-unstable" units can never be safely trusted to remain good — there is no time/opportunity left for the network to "contest" (resolve conflicting branches/double-spends) before the vote is counted, just like `verifyBlocks()` in the TaikoL1 report being callable on a pending state transition without allowing the normal `cooldownWindow` for contestation.

### Impact Explanation
The OP list (Order Providers / witnesses) is the most security-critical protocol parameter in ocore — it determines majority witnessing, MC stability determination (`storage.getOpList`), and thus finality itself. Baking a still-contestable (non-final) vote into this list via the emergency path means:
- A faulty/malicious voter's unit that is currently "good" but could later be resolved to `final-bad` (e.g. part of a losing branch in a double-spend) can permanently alter consensus witnesses.
- Because the trigger condition is precisely "MC stability stuck," the normal resolution path (stabilization that would flip a bad unit to `final-bad`) is unavailable exactly when the emergency path is exercised, so there is no way for honest nodes to later detect/undo the tainted vote's effect on the finalized OP list.
- This can cause the network to disagree on validity/stability going forward (different nodes computing different OP lists if the unstable-vote set they see differs), a direct node-disagreement-on-validity impact.

### Likelihood Explanation
Triggering requires MC stability to be stalled for 3 days, which is an unusual but reachable condition (e.g., if the community's op_list vote is split without majority, or an attacker intentionally causes the stall via non-converging votes). Once the timeout elapses, **any single unprivileged unit poster** can send the `system_vote`/`system_vote_count` pair; there is no timelock, governance approval, or additional access control gating the emergency count itself — the only gate is the elapsed-time check based on the (attacker-supplied) unit timestamp.

### Recommendation
Require unstable votes counted under the emergency path to be confirmed as final (or at least require a much stronger guarantee than `sequence='good'`, e.g., require the voting unit to be free of any currently-known conflicting spends and re-validate `sequence` again right before applying `system_vars`, or hold off counting a vote until it is provably not part of any unresolved conflict). Alternatively, do not allow emergency-counted votes to overwrite the canonical `op_votes`/`system_vars` state that would otherwise require standard stabilization; instead require a longer, non-bypassable minimum age tied to actual absence of conflicting branches rather than wall-clock time alone.

### Proof of Concept
1. Cause (or wait for) the `op_list` vote to fail to reach majority for `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days), so `applyEmergencyOpListChange`'s early-return condition is bypassed [9](#0-8) .
2. As an unprivileged author, post a unit containing a `system_vote` message (`op_list`, favoring your own set of OPs, potentially derived from a currently-unresolved conflicting branch) followed at least `EMERGENCY_COUNT_MIN_VOTE_AGE` (1 hour) later by a `system_vote_count` (`op_list`) unit.
3. `writer.js` invokes `applyEmergencyOpListChange` → `countVotes(..., is_emergency=1, ...)`, which pulls your still-unstable vote via `getUnstableVotes` (only age- and current-sequence-gated) [5](#0-4)  and folds it into the emergency-computed OP list, permanently written to `system_vars` [8](#0-7) .
4. Because MC stability is (by construction) still stuck, there is no subsequent stabilization step that could flip your vote's unit to `final-bad` in time — the tainted OP list stands.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}

async function applyEmergencyOpListChange(conn, emergency_count_command_timestamp, cb) {
	// last stable unit
	const [{ timestamp, main_chain_index }] = await conn.query("SELECT timestamp, main_chain_index FROM units WHERE is_stable=1 AND is_on_main_chain=1 ORDER BY main_chain_index DESC LIMIT 1");
	if (emergency_count_command_timestamp < timestamp + constants.EMERGENCY_OP_LIST_CHANGE_TIMEOUT) {
		console.log(`too early to apply emergency OP list change yet`);
		return cb();
	}
	console.log(`applying emergency vote count after being stuck at mci ${main_chain_index}`);
	await countVotes(conn, main_chain_index - 1, 'op_list', 1, emergency_count_command_timestamp);
	cb();
}
