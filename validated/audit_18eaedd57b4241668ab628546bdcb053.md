### Title
Unscoped `StatusHandler#process` writes CI status to commits across all repositories by bare SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike the `Handler#stacks` helper used elsewhere which resolves stacks via `Repository.from_github_repo_name(repository_name)`. Because SHA is the only key and Git SHAs of shared history (e.g. forks, cherry-picks, or common base commits) can appear in multiple repositories' `Commit` rows across stacks, a webhook authenticated for one repository can flip the CI status (`shipit/checks` or any context) of a commit belonging to a different, victim stack.

### Finding Description
The broken binding the code should enforce is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` mutated by a `status` webhook. Instead, `StatusHandler#process` does: [1](#0-0) 
which iterates `Commit.where(sha: params.sha)` — every commit row in the entire database sharing that SHA, regardless of which repository/stack it belongs to — and calls `commit.create_status_from_github!(params)` on each, unconditionally writing a `Status` for that commit's stack: [2](#0-1) 

Compare this to the pattern used by every other handler category (e.g. `pull_request` handlers), which resolves the affected stacks by repository name before acting: [3](#0-2) 

The only authentication performed by `WebhooksController` is HMAC signature verification keyed by `repository_owner`, which proves the payload came from *some* GitHub org/app for *a* repository, but does nothing to constrain which `Commit` rows the handler is permitted to touch: [4](#0-3) 

Attack flow: an attacker who owns/controls a repository configured in Shipit (or any repository under an org configured in `Shipit.github_teams`/`Shipit.github`) sends a legitimately-signed `status` webhook (`context: "shipit/checks"`, `state: "success"` or `"failure"`, `sha: <shared-sha>`) for their own repository. If a victim's production stack has a `Commit` row with that same `sha` (plausible for shared base commits, cherry-picked hotfixes, or squashed merges across forks/mirrors of the same upstream repo), `StatusHandler#process` will match and update the victim commit's status via `add_status`, which triggers `stack.schedule_merges` and continuous delivery evaluation: [5](#0-4) [6](#0-5) 

This can cause `deployable?`/`blocked?` state to flip for the victim's production stack: [7](#0-6) 

None of the existing guards prevent this: `verify_signature` authenticates the sender's own repository, not the target of the mutation; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape (`sha`, `state`, `context`, etc.), not repository identity; there is no `require_permission!`/`User#authorized?` check in the unauthenticated webhook path at all.

### Impact Explanation
A payload authenticated for repository A can flip the CI/status state of a `Commit` belonging to repository/stack B, whenever B has a commit row with the same SHA — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. If stack B is a production environment gated on `shipit/checks`, this status flip can unblock (`deployable?` becomes true) or block an otherwise-good deploy, and can trigger `schedule_merges`/`ContinuousDeliveryJob`, i.e., an unauthorized deploy/merge decision made on attacker-controlled input. The blast radius spans every stack/repository in the installation whose commit history shares a SHA with an attacker-controlled repository (common for forks, mirrors, or shared monorepo history), and the attack is repeatable at will since it only requires signing a webhook for the attacker's own repository.

### Likelihood Explanation
Preconditions: attacker needs a repository that is itself registered/monitored by the Shipit instance (or under an org whose webhook secret they can obtain by owning a repo in that org) so their `status` webhook passes `verify_webhook_signature`; they need a SHA that also exists as a `Commit` row in the victim's stack (achievable via forking, cherry-picking, or shared upstream history — no secrets required). Given that, the attacker cost is a single unauthenticated-content HTTP webhook triggered by normal GitHub repository actions (pushing a commit with a chosen SHA lineage and setting its status), which is fully repeatable and requires no Shipit session, API token, or GitHub App key beyond what any repository owner already has for their own repo.

### Recommendation
Scope `StatusHandler#process` to only update commits belonging to the repository that authenticated the webhook, mirroring the `Handler#stacks`/`repository_name` pattern: restrict the query to `Commit.joins(:stack).merge(stacks)` (or equivalently `where(stack_id: stacks.select(:id))`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status handler only updates commits for the authenticated repository" do
  attacker_repo = shipit_repositories(:shipit) # attacker-controlled repo A
  victim_stack = shipit_stacks(:shipit) # production stack B, requires 'shipit/checks'
  victim_stack.update!(environment: 'production')
  shared_sha = 'a' * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared')
  # binding under test: commit.stack.repository.full_name == payload['repository']['full_name']
  assert_not_equal victim_commit.stack.repository.full_name, attacker_repo.full_name

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'shipit/checks',
    'repository' => { 'full_name' => attacker_repo.full_name, 'owner' => { 'login' => attacker_repo.owner } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  # FAILS today: victim_commit picks up the status even though payload authenticated a different repo
  assert_not victim_commit.statuses.exists?(context: 'shipit/checks'),
    "commit belonging to repository #{victim_commit.stack.repository.full_name} " \
    "was mutated by a webhook authenticated for #{attacker_repo.full_name}"
end
```

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
