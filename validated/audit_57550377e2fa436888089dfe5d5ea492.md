## Analysis

The reported bug class centers on a signature-verification primitive (`isValidSignature`) that checks only "is this signature valid for this hash" without binding the hash to who is checking it (no chain-id / verifying-contract binding), enabling a signature produced in one context to be replayed and accepted in another.

ocore has a directly analogous primitive: the oscript function `is_valid_signed_package(signed_package, address)`, used inside AA formulas to let an AA verify an off-chain/relayed signature from `address` over a `signed_message`. It is implemented via `signed_message.validateSignedMessage` in `signed_message.js` and wired into the evaluator in `formula/evaluation.js`. [1](#0-0) 

The hash that is actually signed, `objectHash.getSignedPackageHashToSign(objSignedMessage)`, is computed over `signed_message`, `authors`, `last_ball_unit`, `timestamp`, and `version` — it never includes the **verifying** address (the `address_expr`/AA that is calling `is_valid_signed_package`). It only encodes the *signer's own* address (inside `authors`). [2](#0-1) [3](#0-2) 

Because no verifier/domain identifier is baked into the hash, the exact same signed package (same `signed_message`, `authors`, `last_ball_unit`) that validates for one AA's `is_valid_signed_package(pkg, addr)` check will validate identically for **any other AA** that expects a signature from the same `addr` over a matching `signed_message` shape. The protocol pushes the responsibility for domain separation entirely onto the AA author, exactly mirroring the report's core complaint that "insufficient checks... allow an attacker to reuse a historical transaction hash and signature... across different accounts."

This is not hypothetical: the shipped reference sample explicitly has to work around the missing binding by manually stuffing a `channel: this_address` field into the signed message and checking it before calling `is_valid_signed_package`: [4](#0-3) [5](#0-4) 

If an AA author omits this manual `this_address`/nonce binding (which the protocol itself does not enforce or even warn about at the `is_valid_signed_package` call site), a counterparty-signed message intended for use with AA #1 can be replayed against AA #2 (or a redeployed/cloned AA with an identical schema) as long as AA #2 also expects a signature from that same address over a matching message — directly enabling unauthorized fund movement or state changes, analogous to the ERC1271Handler cross-contract replay described in the report.

An even lower-level, zero-binding version of the same primitive is `is_valid_sig(message, pem_key, sig)`, which performs a raw signature check with no built-in binding whatsoever (no address, no chain/network context, no nonce) — the AA author must supply 100% of the replay protection themselves: [6](#0-5) 

### Title
Missing domain separation in `is_valid_signed_package`/`getSignedPackageHashToSign` enables cross-AA signature replay - (File: signed_message.js, object_hash.js, formula/evaluation.js)

### Summary
`is_valid_signed_package` lets any AA verify a counterparty's off-chain signature over an application-chosen `signed_message`. The hash actually signed (`getSignedPackageHashToSign`) binds the signer's address, `last_ball_unit`, `timestamp`, and `version`, but never binds the identity of the AA/address performing the verification. A signed package accepted by one AA is therefore also valid input to any other AA (or a copy of the same AA at a different address) that checks for a signature from the same signer over a structurally similar message.

### Finding Description
`validateSignedMessage` (`signed_message.js:117-303`) computes `unit_hash_to_sign = objectHash.getSignedPackageHashToSign(objSignedMessage)` purely from fields the *signer* controls/produces (`signed_message`, `authors`, `last_ball_unit`, `timestamp`, `version`). The verifying AA's own address, passed as `address_expr` to `is_valid_signed_package` in `formula/evaluation.js:1660-1701`, is used only to pick which `author` entry to check against — it is never mixed into the hash that was actually signed. This is the same defect class as the ERC1271Handler report: the low-level signature-check primitive omits a verifier/domain-scoping component (analogous to EIP-712's chain-id + verifying-contract binding), leaving replay protection entirely up to the calling application. The shipped `payment_channels.oscript` sample demonstrates this gap is real by manually re-implementing binding via a `channel: this_address` field checked before calling `is_valid_signed_package` — proving the primitive itself provides no such protection.

### Impact Explanation
Any AA author who uses `is_valid_signed_package` (or the even lower-level `is_valid_sig`) to authorize value transfer, state changes, or order execution — without manually embedding an AA-specific or purpose-specific tag inside `signed_message` — is exposed to signature replay: a legitimately obtained signature for one AA/purpose can be resubmitted as trigger data to a different AA (or a redeployed clone) expecting a signature from the same key, causing unauthorized fund transfers or state mutation in that second AA. This matches "AA fund loss" impact criteria.

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender: they only need to obtain (via public unit data, since signed packages are typically embedded in `trigger.data`) a previously-broadcast signed package intended for one AA and resubmit it as trigger data to another AA using a structurally-compatible message schema. Likelihood depends on AA authors reusing message shapes and omitting manual binding fields, which the official example itself needed to add — indicating this is not an obvious requirement to AA developers.

### Recommendation
Bind the verifying AA's address (or an explicit `app_id`/`aa_address` domain field) and ideally a per-purpose nonce into `getSignedPackageHashToSign`'s hashed structure, or require/enforce that `is_valid_signed_package` callers pass a `context`/`domain` parameter that gets mixed into the hash before validation, following the ERC-7739-style nested/defensive rehashing approach cited in the report, so a signature is cryptographically scoped to the specific AA and purpose it was issued for by default rather than relying on every AA author to remember to add such a field manually.

### Proof of Concept
1. User signs a package with `signed_message = {amount_spent: 100, ...}`, `authors: [{address: signerAddr, ...}]`, no AA-specific field, intended for AA_A's `is_valid_signed_package(trigger.data.pkg, signerAddr)` check that authorizes a withdrawal.
2. Attacker captures this package from public unit data (it was submitted as `trigger.data` to AA_A).
3. Attacker deploys/uses AA_B with an identical or compatible check: `is_valid_signed_package(trigger.data.pkg, signerAddr)`, expecting the same signer to authorize a similarly-shaped action.
4. Attacker submits the captured package unmodified as trigger data to AA_B; `validateSignedMessage`/`getSignedPackageHashToSign` recompute the same hash (since none of the fields differ) and the signature verifies successfully in AA_B's context, even though the signer never intended to authorize anything in AA_B.
