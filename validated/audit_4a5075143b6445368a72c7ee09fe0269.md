### Title
Unhandled exception in `replaceInTemplate()` (via `'definition template'` address-definition evaluation) crashes the entire node — (File: `definition.js`)

### Summary
`definition.js`'s `evaluate()` function, used both when validating a new address definition and when validating authentifiers for every unit spent from an address, supports a `'definition template'` operator that fetches a stored `definition_template` message and fills in `$var` placeholders via `replaceInTemplate()`. When `replaceInTemplate()` throws anything other than its own `NoVarException`, the surrounding code re-throws the exception instead of converting it into a validation error. Because this happens inside an asynchronous `conn.query()` callback, the exception cannot be caught by any caller and propagates to Node's `uncaughtException` handler, which explicitly re-throws to crash the whole process — exactly the same failure mode as the Qwik CVE-2025-53620 (an unhandled error from processing attacker/user-controlled input takes down the entire server).

### Finding Description
`replaceInTemplate()` recursively walks the template array/object structure: [1](#0-0) 

For any value whose `typeof` is not `number`, `boolean`, `string`, or `object`, it does `throw Error("unknown type")`, and, more importantly, it recurses without any depth limit for arrays/objects — an unbounded recursive call for every nesting level of the stored template.

This function is invoked from two `'definition template'` handlers in `definition.js`:

1. In `validateDefinition()` (invoked while validating any address definition that uses `['definition template', [unit, params]]`): [2](#0-1) 
Here, only `NoVarException` is converted to a soft validation error (`cb(e.toString())`); any other exception (e.g. a `RangeError: Maximum call stack size exceeded` from deep recursion) is explicitly re-thrown with `throw e;` inside the `conn.query()` callback.

2. In `validateAuthentifiers()` (invoked every time a unit is spent from an address using this definition, i.e. on every subsequent payment): [3](#0-2) 
This path has **no try/catch at all** around `replaceInTemplate()`, so *any* exception it throws propagates directly out of the DB callback.

The `definition_template` payload itself is user-controlled content stored by an ordinary `definition_template` app message — any unprivileged unit poster can post an arbitrarily deeply nested JSON array/object as this payload (subject only to normal unit size/message limits, not to a dedicated JSON-nesting-depth cap enforced at insertion time for this app type). Once stored and stable, any address (the same poster or a different unprivileged user) can define an address using `['definition template', [that_unit, params]]`. Every time a unit signed by/spending from that address is validated by **every full node on the network**, `validateAuthentifiers()`/`validateDefinition()` re-fetches the template and calls `replaceInTemplate()` on it. A sufficiently deep nesting structure exceeds V8's call-stack limit, producing a `RangeError` that is not a `NoVarException` and is therefore re-thrown (or thrown unguarded in the authentifiers path), reaching the top-level `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the process: [4](#0-3) 

This mirrors the Qwik advisory precisely: an operation that can throw on attacker-influenced/malformed input (`Dynamic require` failure in Qwik vs. `RangeError`/`throw Error("unknown type")` in ocore) is not defensively caught, and the resulting unhandled exception brings down the whole server process rather than being converted into a rejected/invalid unit.

### Impact Explanation
A single crafted `definition_template` message plus a follow-up address definition and a single spend from that address can crash every full node that validates the transaction — this is a network-wide denial of service, not merely a local node quirk, because `validateAuthentifiers()` runs on **every** node validating any unit spent from the affected address, and the crash is deterministic (stack depth is a function of the stored template's nesting, which is fixed once stored on the DAG). Repeated posting/crashing can keep nodes down indefinitely, preventing new units from being confirmed — squarely in the "network unable to confirm new units" impact category from the validation rules.

### Likelihood Explanation
High. The only prerequisites are: (1) post a `definition_template` message with a deeply nested JSON structure (no privileged role required — any unit poster can send it), and (2) use `['definition template', [unit, params]]` in an address definition, then post one spend from it. No race condition, no privileged key, and no reliance on peer/network misbehavior is needed — a single unprivileged user can trigger it deterministically.

### Recommendation
- Add an explicit depth/size limit check on `definition_template` payloads at validation time (similar to `isTooDeeplyNestedOrHasTooManyNodes`), so overly deep templates are rejected as invalid units rather than accepted and later crashing consumers.
- Convert `replaceInTemplate()` to an iterative (non-recursive) implementation or add an explicit depth counter that fails gracefully (`cb("template too deeply nested")`) instead of relying on the JS call stack.
- Wrap the `replaceInTemplate()` call in `validateAuthentifiers()`'s `'definition template'` handler (`definition.js:815`) in a try/catch, and change the `else throw e;` branch in `validateDefinition()`'s handler (`definition.js:334-338`) to return a validation error (`cb(e.toString())`) for any exception type rather than only `NoVarException`.

### Proof of Concept
1. As any unprivileged user, post a unit with a `definition_template` app message whose `payload` is a JSON array nested deeply enough to exceed V8's default stack size when recursively walked (e.g., thousands of levels of `[[[[...]]]]`), reference-able via its unit hash.
2. Create a new address whose definition includes `['definition template', ['<hash_of_step_1_unit>', {"name": "value"}]]` and post it as the definition of an author in a subsequent unit (address definitions are validated via `validateDefinition()` / `evaluate()` at `definition.js:306-343`).
3. Send a payment from that address (any subsequent spend goes through `validateAuthentifiers()`'s `'definition template'` branch at `definition.js:802-819`, which has no try/catch).
4. Every node validating this unit calls `replaceInTemplate()` on the deeply nested template; the recursive `for` loop in `replaceInVar()` (`definition.js:1482-1489`) exceeds the JS call stack, throwing a `RangeError`, which propagates unguarded out of the `conn.query()` callback, is caught only by `process.on('uncaughtException', ...)` in `network.js:4530-4543`, and the process crashes (`throw err;`).

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
