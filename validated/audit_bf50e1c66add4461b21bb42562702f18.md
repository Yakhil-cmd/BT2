### Title
ERC20Transactor trusts requested transfer amount instead of actual balance delta for fee-on-transfer/deflationary/rebasing ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens (deployed via `pallet-revive`) between a user account and a shared `TransfersCheckingAccount` by calling `IERC20::transfer` and only checking the boolean `bool` return value of the call. They never verify that the checking account's actual token balance changed by the nominal `amount` requested. This is the exact bug class described in the external report (fee-on-transfer / deflationary / rebasing ERC20 tokens whose `transfer()` moves a different amount than requested while still returning `true`).

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the transactor:
1. Extracts `(asset_id, amount)` from the XCM `Asset` via `Matcher::matches_fungibles`.
2. Calls `IERC20::transferCall { to: checking_address, value: amount }` on the user's own signed origin.
3. Decodes only the boolean success flag from the call return data.
4. If `true`, it unconditionally credits `AssetsInHolding` with `Erc20Credit(amount)` — i.e., the **full nominal amount**, regardless of how many tokens the checking account actually received.

Symmetrically, in `deposit_asset_with_surplus` [2](#0-1) , the checking account calls `transfer(beneficiary, amount)` and again only checks the boolean return, never confirming the beneficiary actually received `amount`.

No balance-before/balance-after check (`balanceOf` diff) is performed anywhere in this file, and no `SafeERC20`-equivalent invariant is enforced. This directly matches the reported invariant violation: "transfers tokens ... but does not check the return value, nor how many tokens were actually transferred."

`ERC20Transactor` is wired into the live `AssetTransactors` tuple for Asset Hub Westend, alongside `FungibleTransactor`/`FungiblesTransactor`, and is reachable through ordinary, permissionless XCM execution (`pallet_xcm::execute`/reserve-transfer instructions such as `WithdrawAsset`/`DepositAsset`) since `type XcmExecuteFilter = Everything` and `AllowTopLevelPaidExecutionFrom<Everything>` is in the barrier [3](#0-2) [4](#0-3) .

### Impact Explanation
Because the amount credited into `AssetsInHolding` on withdraw (and debited on deposit) is the caller-supplied nominal value rather than the measured balance delta, an attacker who deploys and uses a non-standard ERC20 contract (fee-on-transfer/deflationary, e.g. burns X% per `transfer`) as the traded asset in an XCM program can create a mismatch between the token amount actually held by `TransfersCheckingAccount` and the amount the runtime's XCM holding/accounting believes it received. If this "credited" amount is then used to satisfy a subsequent XCM instruction (e.g. `DepositAsset` to a different beneficiary, or forwarded in a reserve-backed cross-chain transfer where the destination mints wrapped representation based on the reported amount), it introduces unbacked/over-reported value relative to what the checking account actually custodies — an accounting integrity break rather than a pure gas/UX inconvenience. In the more benign case it simply causes deterministic failed transfers/DoS for that asset path when the checking account under- or over-shoots its expected balance.

The severity depends heavily on whether arbitrary/permissionlessly-deployed ERC20 contracts can be matched by `assets_common::ERC20Matcher` and accepted as reserve/holding assets in a live XCM program (e.g., via `pallet_xcm::execute` or as part of a trusted-reserve asset list) — I could not fully verify `ERC20Matcher`'s matching restrictions within the available tool budget, so I cannot confirm whether this is exploitable end-to-end on a live network versus only reachable for governance-whitelisted ERC20s.

### Likelihood Explanation
Reaching this code path requires only: (1) deploying an arbitrary ERC20 contract with fee-on-transfer/deflationary semantics via `pallet-revive` (a normal, unprivileged user action), and (2) issuing an XCM program that withdraws/deposits that asset (via `pallet_xcm::execute`, reachable by any signed account under `EnsureXcmOrigin<RuntimeOrigin, LocalOriginToLocation>` with `XcmExecuteFilter = Everything`). No governance, validator, or privileged role is required for the attacker to trigger the mismatched accounting on their own asset. What remains unverified is whether `ERC20Matcher` unconditionally matches any ERC20 contract address as a valid XCM asset id for this transactor, or whether some pallet/registry gate limits it — this materially affects likelihood and I was unable to confirm this within the current investigation.

### Recommendation
- In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the relevant account's actual ERC20 balance (via `balanceOf`) before and after the `transfer` call, and use the measured delta (not the nominal `amount`) both for the amount credited into/removed from `AssetsInHolding` and for deciding success/failure.
- Alternatively/additionally, explicitly document (and, if possible, enforce via the asset registration/matching path) that only "standard-conforming" ERC20 tokens (no fees, no rebasing, exact balance semantics) are permitted to be used through `ERC20Transactor`, and reject/flag any mismatch between requested and observed transfer amounts as `XcmError::FailedToTransactAsset`.

### Proof of Concept
No executable PoC was run. Based on static review of `erc20_transactor.rs`, `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` credit/debit the nominal `amount` parameter without any `balanceOf` before/after check — this is directly demonstrable by inspecting lines 159–216 and 225–306 of that file. Full end-to-end exploitation would require constructing a fee-on-transfer ERC20 contract, deploying it via `pallet-revive`, and executing an XCM program (e.g. through `pallet_xcm::execute`) on an Asset-Hub-Westend-like runtime to observe the accounting mismatch; this integration reproduction was not executed due to tool/time constraints, and confirmation of `ERC20Matcher`'s asset-acceptance scope (governance-gated vs. permissionless) is still outstanding.

			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");

						))
					},
