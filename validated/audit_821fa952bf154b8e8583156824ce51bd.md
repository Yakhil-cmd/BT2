### Title
`MembershipHandler` binds a privileged `Team` by GitHub-global `github_id` without verifying the payload's `organization` owns that team, allowing a foreign org's webhook to grant `Membership` in another org's `Shipit.github_teams` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::User#authorized?` trusts `Membership`/`Team` rows populated by the `membership` webhook path, and that path's `find_or_create_team!` looks up the target `Team` solely by `github_id`, never checking that the payload's `organization.login` matches the `Team#organization` already stored on that row. Because `WebhooksController#verify_signature` derives the organization used for signature verification entirely from attacker-controlled payload fields, a webhook that is validly signed for one (lower-privilege) organization can still reference and mutate a `Team` belonging to a different, higher-privilege organization.

### Finding Description
The claimed binding, stated as an equality, is: *"the organization whose `webhook_secret` verified the membership payload == the organization owning the `Team` row referenced by that payload."* Tracing the code shows this equality is never enforced.

- `WebhooksController#verify_signature` picks the app/secret to validate against using `repository_owner`, which is read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) [2](#0-1) . This only proves the request was signed by *some* organization configured in Shipit (the one named in the payload) — it says nothing about the org that owns the `Team` referenced later in the same payload.
- `Handlers::MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` [3](#0-2) . The `organization:` assignment only executes inside the block, which Rails only runs when a **new** record is being created. If a `Team` with that `github_id` already exists (e.g., a real, privileged team belonging to `Shipit.github_teams`), the existing row is returned unchanged — its `organization` is never compared to `params.organization.login`.
- The handler then does `team.add_member(member)` where `member = User.find_or_create_by_login!(params.member.login)` [4](#0-3) , creating a `Membership` for whatever login the attacker names in `member.login` — which the attacker can set to their own real GitHub login (the same one bound to their `session[:user_id]` via the normal OAuth flow, per `find_current_user` in `app/controllers/concerns/shipit/authentication.rb:40-42`).
- `Shipit::User#authorized?` then reads exactly this table: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [5](#0-4) , so the forged `Membership` immediately flips the attacker's genuinely-authenticated session to authorized.

Existing guards do not prevent this: `verify_signature` only proves *a* configured org's secret matched, `drop_unhandled_event`/`check_if_ping` are irrelevant, and the `ExplicitParameters` schema on `MembershipHandler` only validates types/presence of `team.id`, `organization.login`, `member.login` — it never cross-checks `organization.login` against the resolved `Team#organization` [6](#0-5) . `Team#github_hooks` association is scoped by `organization` for other purposes (fetching required hooks) but is not consulted here to gate the membership mutation [7](#0-6) .

### Impact Explanation
An attacker who controls a repository/organization already onboarded to the same Shipit instance (and therefore possesses a valid webhook secret for *that* org) can send a `membership` event naming `team.id` equal to the `github_id` of a `Team` that is part of `Shipit.github_teams` for a *different* organization, and `member.login` equal to their own GitHub login. This creates a `Membership` row for their real, correctly-bound `User`, which `authorized?` reads directly — escalating their genuinely-authenticated session into full access to deploy/merge on stacks gated by `Shipit.github_teams`. This matches the "escalation into `Shipit.github_teams` authorization" High-severity category, and is repeatable against any `Team` whose `github_id` the attacker can learn/guess, across any tenant organization sharing the Shipit instance.

### Likelihood Explanation
Requires: (1) a multi-tenant Shipit deployment where the attacker legitimately owns/administers at least one onboarded organization/repository (giving them a valid webhook secret to pass `verify_signature`), and (2) knowledge of the `github_id` (GitHub's numeric team ID) of a privileged team in another org — team IDs are often discoverable via the GitHub API/UI to broader audiences than the org's own membership. Given those, the attack is a single crafted HTTP POST to `/webhooks`, fully repeatable, at negligible cost.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team#organization` equals `params.organization.login` before performing any mutation; reject (or raise) if they diverge instead of silently reusing an existing team from a different org. Additionally, `find_or_create_by!` should scope the lookup by both `github_id` and `organization` (or better, verify `repository_owner`/`params.organization.login` used for signature verification match the team's org before calling `team.add_member`/`team.members.delete`).

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership from a foreign org cannot add a member to a team owned by another org" do
  foreign_org_team = shipit_teams(:shopify_developers) # belongs to org "shopify", is in Shipit.github_teams
  attacker_login = 'attacker_real_login'

  @request.headers['X-Github-Event'] = 'membership'
  # Signed/validated against "othercorp" (attacker's own onboarded org), NOT "shopify"
  payload = {
    action: 'added',
    team: { id: foreign_org_team.github_id, name: foreign_org_team.name, slug: foreign_org_team.slug, url: foreign_org_team.api_url },
    organization: { login: 'othercorp' },
    member: { login: attacker_login },
    repository: { owner: { login: 'othercorp' } }
  }

  assert_no_difference -> { Membership.where(team: foreign_org_team).count } do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end
end
```
Both sides of the equality — `repository_owner`/`params.organization.login` ("othercorp", the org that verified the signature) vs `Team#organization` ("shopify", the org owning the referenced `Team`) — diverge, and the assertion demonstrates the current code fails to prevent the `Membership` write, confirming the vulnerability.
