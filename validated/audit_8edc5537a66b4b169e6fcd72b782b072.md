## Title
Updating an asset's attestor list retroactively freezes previously-attested holders' transfers — ([File: validation.js])

### Summary
The Sherlock report describes a class of bug where a mutable access-control parameter, when tightened after the fact, permanently blocks legitimate actions (withdraw/transfer) for actors who already satisfied the *old* constraint, because the check is always evaluated against the *current* value instead of the value that applied when the funds were acquired. Ocore has a structurally identical pattern in the `spender_attested` asset mechanism: the attestor whitelist for a divisible/indivisible asset can be updated at any time via the `asset_attestors` message, and every subsequent payment check re-evaluates attestation against only the *current* list, not the list valid when the recipient/holder was attested.

### Finding Description
An asset can be defined with `spender_attested: true` and an initial `attestors` list [1](#0-0) . The definer can freely replace this list later using the `asset_attestors` app, the only requirement being that the sender is the asset's definer address: [2](#0-1) 

When any payment in this asset is validated, `storage.readAsset` -> `addAttestorsIfNecessary` looks up only the **latest** attestor-list unit (`ORDER BY level DESC LIMIT 1`) and loads that list into `objAsset.arrAttestorAddresses`: [3](#0-2) 

`validatePaymentInputsAndOutputs` then requires every payment output address to be currently attested against this latest list: [4](#0-3) 

`filterAttestedAddresses` performs the actual check by querying attestations whose `attestor_address` is `IN (objAsset.arrAttestorAddresses)` — i.e., only attestors that are still on the *current* list: [5](#0-4) 

Because the check is always against the live/current attestor set, and there is no grandfathering of holders who were validly attested under a previous list, a definer changing (shrinking, rotating, or replacing) the attestor list breaks spendability for every wallet whose only valid attestation came from an attestor that is no longer on the list — even though those wallets already legitimately hold the asset. This mirrors the reported bug exactly: “Any decrease…shouldn’t affect what a wallet is already holding, just that their amount can’t increase” — but here a change to the constraint (attestor list) retroactively blocks transfers of funds already held.

### Impact Explanation
Any wallet (human or another AA) holding units of a `spender_attested` asset can be locked out of transferring or receiving change for those units the moment the definer rotates the attestor list, without any action or fault of the holder. If a smart-contract AA (e.g., an escrow, vault, or DEX AA) is the counterparty that must send outputs of this asset (e.g., a refund/change output back to itself), and its own address's current attestation was granted by an attestor later removed from the list, the AA's payment message will fail validation with "some output addresses are not attested." This can permanently strand AA-held funds of that asset, since the failing message cannot be excised from an otherwise-valid trigger response and there is no way for the AA to obtain retroactive attestation from a removed attestor. This is a fund-freezing condition triggerable purely by the (potentially unprivileged, non-consensus) act of the asset definer updating its own attestor list — a routine, permitted administrative action that the protocol does not flag as dangerous to existing holders.

### Likelihood Explanation
`asset_attestors` updates require no special network privilege — any address that defined a `spender_attested` asset can issue this message at any time, and it is a single, cheap, always-valid unit as long as the sender is the definer. Attestor rotation (e.g., replacing a compromised attestor, adding a compliance provider) is a normal and expected operational action, not an unusual edge case, so the freeze condition is easily triggered unintentionally during normal asset lifecycle management, exactly like decreasing `perWalletLimit` in the referenced report.

### Recommendation
When validating `spender_attested` transfers, honor attestations issued by attestors that were valid at the time the attestation was produced (or at the time the wallet received the funds) rather than only the attestor set current at validation time — e.g., check attestations against the attestor list unit that was in effect at the attestation's own `main_chain_index`, and/or provide an explicit mechanism to "grandfather" already-attested addresses when the attestor list changes so that outstanding balances remain transferable even after the list is updated.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Attestor `X` attests address `W`. `W` receives units of `A` (output to `W` passes the check against `arrAttestorAddresses = [X]`).
3. `D` sends an `asset_attestors` message changing the attestor list to `[Y]` (dropping `X`) — allowed unconditionally per `validateAttestorListUpdate` (only requires `D` to be the definer).
4. `W` now tries to spend/transfer its existing balance of `A` (even just to itself as change). `storage.readAsset` loads the new latest list `[Y]`; `filterAttestedAddresses` finds no attestation from `Y` for `W`; `validatePaymentInputsAndOutputs` rejects the payment with "some output addresses are not attested," even though `W` legitimately holds the asset and did nothing wrong. `W`'s balance of `A` is now stuck unless `Y` chooses to attest `W`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
