### Title
Webhook signature verification is bound to the attacker-controlled `repository.owner.login` field, not to the repository/commit actually written by the handler - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on a value read out of the very payload it is about to verify (`repository.owner.login` / `organization.login`). The handlers that subsequently act on that payload (e.g. `StatusHandler`, `PushHandler`, `CheckSuiteHandler`) determine *which stack/commit to mutate* from a different part of the same payload (`repository.full_name`, or for `StatusHandler`, no repository scoping at all — just a global `sha` lookup). Because Shipit supports multiple organizations, each with its own independently configured `webhook_secret`, an operator who legitimately controls one onboarded organization's webhook secret can forge a payload whose "authenticating" fields point to their own org while the "acted upon" fields point at a victim stack, breaking the binding `organization_that_authenticated == repository_that_is_written`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 

It picks the `github_app` (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using `repository_owner`, which is read straight from the untrusted JSON body: [2](#0-1) 

Signature verification itself only proves that *some* keyholder of the secret associated with that self-declared organization signed the raw body — it does not verify that the organization is the one that actually owns the resources being modified: [3](#0-2) 

Once the request passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that resolve the target stack/commit from a *different* payload field, `repository.full_name`: [4](#0-3) 

`StatusHandler` is the most severe case: it does not even use `stacks`/`repository_name` scoping — it updates the CI status of **any commit in the entire installation** whose SHA matches the attacker-supplied `sha`, regardless of which repository/organization it belongs to: [5](#0-4) 

`PushHandler` and `CheckSuiteHandler` at least scope through `Repository.from_github_repo_name(repository_name)`, but that lookup uses `repository.full_name`, a field wholly independent from `repository.owner.login`/`organization.login` used for secret selection: [6](#0-5) [7](#0-6) 

Because the HMAC covers the raw body, this is not "an unsigned field" in the strict sense — but the vulnerability is that the verified identity (webhook_secret owner) is never checked for consistency with the identity implied by the fields the handlers actually trust to select what to mutate. An attacker who has a legitimately configured organization/repo in the same Shipit instance (and therefore knows or can compute a valid signature using that organization's `webhook_secret`) can freely craft the rest of the JSON body — including `repository.full_name` (and for `status`, simply the `sha`) — to reference a victim's stack/commit, since nothing ties the verified secret's organization to the fields consumed downstream.

### Impact Explanation
This lets an attacker who only controls one onboarded GitHub organization (with a real webhook secret) forge webhook deliveries that act on stacks/commits belonging to a completely different organization on the same Shipit instance:
- Via `StatusHandler`, the attacker can set an arbitrary commit's CI status to `success` for any SHA in any repository tracked by Shipit (`Commit.where(sha: params.sha)` with no repo scoping), which can satisfy `required_statuses`/CI gating and enable an **unauthorized deploy** of a commit that never actually passed CI — matching the "Critical: unauthorized deploy" impact category.
- Via `PushHandler`/`CheckSuiteHandler`, an attacker can force out-of-band `sync_github`/check-run refresh operations on a victim's stack.

This crosses an authentication boundary (a signature/organization binding) without requiring any Shipit session, `ApiClient` token, or GitHub write access to the victim repository — only knowledge of a webhook secret for some organization already configured in the shared Shipit instance.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly supported per `config/secrets.development.example.yml`'s multi-org schema) where the attacker legitimately administers one of the onboarded organizations/webhook secrets, and knows or can guess/target a victim commit SHA or stack's `repository.full_name` tracked in the same instance. This is a realistic configuration for shared/multi-tenant Shipit installations.

### Recommendation
After verifying the HMAC signature, re-derive the "acting" organization strictly from the verified `github_app`'s bound organization (not from payload fields), and require that the repository/stack resolved for mutation (`repository.full_name` in `Handler#repository_name`, and the repo of any commit matched in `StatusHandler`) actually belongs to that same verified organization before applying any state change. For `StatusHandler` specifically, scope the `Commit` lookup by the repository that the verified webhook's organization owns, rather than doing a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per the documented multi-org `github:` config).
2. Attacker crafts a JSON body with `X-Github-Event: status`, setting `repository.owner.login` = `attacker-org` and `sha` = the SHA of a real, un-passed commit belonging to a stack in `victim-org`'s repository (guessable/known from public GitHub commit history), with `state: "success"`.
3. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly, then POSTs to `/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (valid HMAC for that secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's commit (no organization-scoping check), calling `commit.create_status_from_github!(params)`, marking it as CI-passing even though `attacker-org`'s secret was the only thing ever verified.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
