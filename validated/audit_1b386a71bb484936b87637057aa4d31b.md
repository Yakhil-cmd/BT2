### Title
Webhook signature verification selects the GitHub App/secret from an unverified `repository.owner.login` field, decoupling the authenticating organization from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which configured GitHub App (and therefore which `webhook_secret`) to check the signature against by reading `repository.owner.login`/`organization.login` straight out of the unverified request body, before the signature has been validated. Downstream, the actual event handlers resolve the target `Stack`/`Repository` from a *different* unverified field in the same body (`repository.full_name`). In a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret` set, this lets an attacker who knows any one org has signature verification effectively disabled forge events for repositories belonging to a *different*, properly secured organization.

### Finding Description
`WebhooksController#verify_signature` resolves the signing app like this: [1](#0-0) 

`repository_owner` is taken directly from the untrusted JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (multi-app deployments are supported via `github_app_config`/`github_organizations`): [3](#0-2) 

Critically, `GitHubApp#verify_webhook_signature` unconditionally returns `true` (bypasses verification) whenever that organization's `webhook_secret` is blank/unset: [4](#0-3) 

The test fixtures confirm this is a supported, real configuration shape — a second organization configured with no `webhook_secret` at all: [5](#0-4) 

Once the controller decides "verified" (using the org picked from `repository.owner.login`), it dispatches the *entire* payload to handlers, which resolve the actual `Stack`/`Repository` from an independent field, `repository.full_name`, that is never cross-checked against `repository.owner.login`: [6](#0-5) 

So the equality the code is implicitly assuming is:
`organization that authenticated the request (repository.owner.login → webhook_secret used)` == `repository that is written to (repository.full_name → Stack resolved by handlers)`

Nothing in `verify_signature` or `Handler` enforces this. An attacker can set `repository.owner.login` to an organization whose `webhook_secret` is blank (verification bypassed, "authenticated" for free) while setting `repository.full_name` to a repository belonging to an entirely different, properly-secured organization whose stacks they want to tamper with.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credential authorized the request" and "the repository whose state gets mutated," directly matching the class of binding the task calls out. Concretely, an attacker can forge, for arbitrary repositories under any configured org:
- `push` events, driving `PushHandler` to enqueue `GithubSyncJob` with an attacker-chosen `expected_head_sha` for stacks matching the targeted branch.
- `status` events, letting an attacker fabricate a commit's CI/deploy status (`state`, `target_url`, `description`), which Shipit uses to gate mergeability/deployability of commits.
- `check_suite`, `membership`, and `pull_request` events, all resolved via the same unauthenticated `repository.full_name`/`organization` fields.

Because Shipit gates real actions (sync, merge-queue eligibility, deployable status) on these webhook-driven signals, an attacker able to spoof status/push events for a target repository can influence what gets merged/deployed — this rises to the "unauthorized deploy" tier described in the impact rubric, since it can cause Shipit to treat attacker-controlled commits/statuses as legitimate signals driving the deploy/merge pipeline.

### Likelihood Explanation
Exploitation requires only unauthenticated HTTP access to the `/webhooks` endpoint (no session, no `ApiClient` token, no repository write access) plus knowledge that some organization in the multi-app configuration has no `webhook_secret` configured — a state the engine itself supports and ships fixtures/docs for (`webhook_secret` is documented as optional). This is a realistic, not theoretical, deployment configuration for any Shipit instance managing more than one GitHub organization where only some orgs have set up webhook secrets.

### Recommendation
- After signature verification, cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner/org of the repository resolved by the handler (`repository.full_name`'s owner segment) before dispatching to any handler.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with a blank `webhook_secret` when the engine is configured in multi-organization mode; either require a secret per org or scope such "unverified" organizations so they cannot be used to authorize events for other organizations' repositories.

### Proof of Concept
Given a multi-org config where `OrgSecure` has a `webhook_secret` set and `OrgWeak` does not (as in `test/dummy/config/secrets_double_github_app.yml`):

```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # ignored, OrgWeak has no webhook_secret

{
  "repository": {
    "owner": { "login": "OrgWeak" },       // selects Shipit.github(organization: "OrgWeak") -> verification bypassed
    "full_name": "OrgSecure/critical-repo" // actually resolved repository/stack, belongs to a different org
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "target_url": "https://attacker.example/fake-ci",
  "description": "forged CI success",
  "branches": [{ "name": "master" }]
}
```

`verify_signature` calls `Shipit.github(organization: "OrgWeak")`, whose `verify_webhook_signature` returns `true` unconditionally (blank `webhook_secret`), so the request is accepted. `StatusHandler` then resolves the target repository/stack purely from `repository.full_name` = `OrgSecure/critical-repo`, letting the attacker inject a forged commit status for a repository that belongs to `OrgSecure`, which never authenticated this request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
