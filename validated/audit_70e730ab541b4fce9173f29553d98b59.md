### Title
Stack-scoped API client tokens bypass their stack authorization in the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The external report's core pattern is a trust binding that is asserted in one place (KYC/sanctions checks at the "front door") but silently detached from the actual capital/execution that is exercised (limit orders filled through an unrelated execution path). The structurally equivalent binding in this engine is: *the stack an `ApiClient` token is authorized for* vs. *the stack the controller actually operates on*. `Shipit::Api::BaseController` establishes this binding via its `stacks`/`stack` helpers, but `Shipit::Api::CCMenuController` re-implements `stack` in a way that drops the scoping, breaking the binding for that one endpoint.

### Finding Description
`Shipit::Api::BaseController` defines the authorization binding that every API controller is supposed to inherit: an `ApiClient` scoped to a specific stack (`current_api_client.stack_id?`) must only be able to resolve stacks from that restricted set: [1](#0-0) 

This is the binding: `current_api_client.stack_id == stack.id` (or, if unscoped, any stack). It is enforced consistently in controllers such as `Api::StacksController`, and is explicitly covered by a passing test ("an api client scoped to a stack will only see that one stack").

`Api::CCMenuController`, however, overrides `stack` to resolve directly from `params[:stack_id]` without going through the `stacks` scoping helper: [2](#0-1) 

It still calls `require_permission :read, :stack`, but `check_permissions!` only checks the `ApiClient`'s permission list (`read:stack`), never its `stack_id` scope: [3](#0-2) 

Consequently, any credential holding a `read:stack`-scoped token — even one explicitly restricted to a single stack via `ApiClient#stack_id` (as modeled by the `here_come_the_walrus` fixture) — can query the CCMenu status of *any* stack in the installation by supplying an arbitrary `stack_id` in the URL, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This is a scope-escalation read of stack state: a credential deliberately restricted to one stack (the "authorized" stack) can read `lastBuildStatus`, `lastBuildLabel`, `activity`, and `webUrl` for every other stack in the deployment (the "touched" stack), including stacks belonging to other repositories/teams that the token was never meant to see. This matches the "High" impact bucket defined by the rules: escalation beyond the authorization granted to a credential, yielding unauthenticated (from the target stack's perspective) read of stack build/deploy state.

### Likelihood Explanation
The bug is triggered purely by supplying a different `stack_id` query parameter to an existing, already-reachable endpoint (`GET /api/:stack_id/ccmenu.xml`), using any valid `read:stack` token — including the one legitimately issued to a stack-scoped client. No additional infrastructure, secrets, or privilege beyond possessing *some* valid API token is required to attempt cross-stack access; the only prerequisite is that a stack-scoped client exists (a supported model feature, exercised by the `here_come_the_walrus` fixture and covered by dedicated tests elsewhere in the suite for other controllers).

### Recommendation
Make `Api::CCMenuController#stack` resolve through the same `stacks` scoping used elsewhere (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that `current_api_client.stack_id` scoping is honored consistently across all API controllers.

### Proof of Concept
1. Create two stacks, `stack_a` and `stack_b`.
2. Create an `ApiClient` with `permissions: ['read:stack']` and `stack: stack_a` (scoped only to `stack_a`), analogous to the `here_come_the_walrus` fixture: [4](#0-3) 
3. Authenticate with this client's Basic Auth token and request:
`GET /api/stack_b/ccmenu.xml?token=<client_token>` (or with Basic Auth headers).
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks.from_param!`), the request succeeds and returns `stack_b`'s build status, despite the client being scoped only to `stack_a`.

*Note: I could not find any additional guard (e.g., a stack-scope check duplicated elsewhere in `CCMenuController` or a shared concern) that would prevent this; the override at lines 29-31 is the only place `stack` is resolved for this controller.*
