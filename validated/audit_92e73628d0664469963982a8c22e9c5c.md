### Title
Unbounded oracle-address array in `in data feed` / `in merkle` definition conditions allows expensive, unlimited synchronous validation loops - (File: definition.js)

### Summary
The address/asset-definition evaluator in `definition.js` validates the `in data feed` and `in merkle` opcodes by iterating over an attacker-supplied `arrAddresses` array with a plain, synchronous `for` loop. Unlike other structural checks in the same file (which are capped by `MAX_COMPLEXITY`/`MAX_OPS`, `args.required <= 1000`, `MAX_DATA_FEED_NAME_LENGTH`, etc.), this specific array has no upper bound on its length — only `isNonemptyArray(arrAddresses)` is enforced.

### Finding Description
In `validateDefinition`'s `evaluate()` function, the `in data feed` and `in merkle` cases each do: [1](#0-0) [2](#0-1) 

Both blocks only require `isNonemptyArray(arrAddresses)`, then run a synchronous `for` loop calling `isValidAddress()` on every element, and add `arrAddresses.length - 1` to `complexity` only *after* the loop has already executed for that call — i.e., the complexity/ops guard (`complexity > constants.MAX_COMPLEXITY`, `count_ops > constants.MAX_OPS`) is checked once at the *start* of `evaluate()`, before this per-element work is spent, so it does not prevent the loop from running with an arbitrarily long array in a single evaluation step: [3](#0-2) 

This is analogous to the reported "Multiple Unbounded loops" pattern: a length-controlled attacker input drives an in-line loop whose cost scales linearly (and here, additionally recurses through nested definitions) with no explicit cap, unlike sibling opcodes such as `weighted and`/`r of set` which do cap `set.length`/`weight`/`required` (≤1000) before iterating: [4](#0-3) 

Any unprivileged user can define such an address definition (or an asset spending condition) and get it validated by every node that has to validate it, either:
- directly, when they first spend from an address whose definition contains `in data feed`/`in merkle` with a very large `arrAddresses` array (`validateDefinition` is invoked from `validateAuthor` in `validation.js`), or
- indirectly, as an asset issuance/transfer condition, since `evaluateAssetCondition`/`validateDefinition` is reused for asset conditions.

### Impact Explanation
Because Node.js validation of a unit runs synchronously per opcode evaluation, a single crafted definition can force every validating node to burn CPU time proportional to the number of addresses packed into the array before the complexity/ops limits are effectively applied. This increases per-unit validation cost in an attacker-controlled, effectively unbounded way relative to the sibling opcodes that are explicitly capped, creating a disproportionate-cost vector during unit/definition validation that other, similarly-shaped opcodes in the same file were specifically hardened against (e.g., `weighted and`/`r of set` caps, `search_param_list` field-count caps, `array`/`dictionary` literal length caps in the formula validator). This can degrade a node's ability to keep up with validating/confirming other units while processing such a definition.

### Likelihood Explanation
Likelihood is limited by the fact that the arrays must fit inside a single unit's definition, which is bounded by `MAX_UNIT_LENGTH`/message size limits, and each address string is only tens of bytes, so thousands of entries are plausible but not unlimited. The per-element cost (`isValidAddress`) is small, so the practical DoS magnitude is likely modest rather than catastrophic — this is a real but bounded-impact instance of the reported bug class, not a proven unauthorized-spend/inflation/freezing bug.

### Recommendation
Add an explicit maximum length check for `arrAddresses` in both the `in data feed` and `in merkle` cases (mirroring the caps already used for `weighted and`, `r of set`, and formula `array`/`dictionary` literals), and move the `complexity`/`count_ops` accounting to occur before the loop executes so oversized arrays are rejected without doing the per-element work first.

### Proof of Concept
1. An attacker composes a unit defining a new address (or a private-asset spending condition) whose definition is:
   `['in data feed', [<arrAddresses with N distinct valid-looking base32 addresses>, 'feed_name', '=', 'value']]`.
2. `N` is chosen as large as the unit-size limits allow (thousands of ~34-byte address strings).
3. The attacker later spends from that address (or issues/transfers the asset), causing every full node to call `validateAuthor` → `Definition.validateDefinition`/`validateAuthentifiers`, which executes the unbounded `for (var i=0; i<arrAddresses.length; i++) if (!isValidAddress(arrAddresses[i])) ...` loop synchronously, without any length cap, unlike the analogous `weighted and`/`r of set` opcodes in the same file.

Given the uncertainty about the practically achievable array size and its real-world DoS magnitude, this should be validated further (e.g., by measuring actual unit-size limits vs. address-count tradeoffs) before treating it as more than a Medium-severity hardening gap.
