### Title
Webhook status/push handlers apply attacker-signed events to victim repositories because commit/repository lookup ignores the organization used to authenticate the signature - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `payload.dig('repository', 'owner', 'login')` (falling back to `payload.dig('organization', 'login')`), while the handlers that actually mutate application state key off a *different* payload field: `payload.dig('repository', 'full_name')` — or, in the case of `StatusHandler`, no repository field at all. Because both fields are attacker-controlled inside the same unsigned-until-verified JSON body, a party who legitimately controls the webhook secret for *any* organization configured in Shipit can forge events that are accepted as authentic but are applied to a repository/commit belonging to a completely different organization/stack.

### Finding Description
`verify_signature` picks the org whose secret is used for HMAC comparison: [1](#0-0) [2](#0-1) 

This uses `repository.owner.login` (or `organization.login`) purely to pick `Shipit.github(organization: ...)`'s `webhook_secret` for `verify_webhook_signature`: [3](#0-2) 

Once the signature validates, the generic `Handler` base class resolves the actual repository/stacks to operate on from a *separate* field, `repository.full_name`: [4](#0-3) 

Nothing ties `repository.owner.login` (used for the signature check) to `repository.full_name` (used to select which `Repository`/`Stack` is mutated) — they are independently supplied JSON fields under the sole control of the request sender. Shipit supports exactly this kind of multi-organization configuration (`Shipit.github_organizations`, `github_app_config`), so an attacker who legitimately owns/administers the GitHub App or webhook for Org A (and therefore knows Org A's `webhook_secret`) can sign a payload whose `repository.owner.login` is `"OrgA"` (so it passes signature verification against Org A's secret) while `repository.full_name` is `"OrgB/victim-repo"`, causing the event to be dispatched against Org B's stacks.

`StatusHandler` is worse: it doesn't even go through the `repository_name`/`stacks` scoping at all — it looks up commits globally by SHA and writes a status directly: [5](#0-4) 

Since git SHAs of a target commit are public (visible on GitHub), an attacker who controls any org's valid webhook secret in the Shipit installation can forge a `status` event carrying a victim commit's SHA and `state: "success"`, and Shipit will create a passing CI status for that commit on the victim's stack — with no relationship whatsoever between the signing organization and the repository being written to.

`PushHandler` similarly resolves stacks via `repository_name` derived from the unauthenticated `full_name` field and triggers `stack.sync_github` for any stack of the (attacker-claimed) target repo: [6](#0-5) 

This is a direct analog of the reported bug class: two different actors/inputs (the "buyer who overwrites" vs the "buyer who originally placed the offer") are conflated because the code never binds the identity that was checked/authorized (the organization whose secret validated the signature) to the resource that is actually acted upon (the repository/commit named in the payload).

### Impact Explanation
This breaks the binding "organization authenticated == repository/stack written," letting an attacker with legitimate control of only their own org's webhook secret forge a CI status (`success`) on an arbitrary victim commit tracked by any other stack in the same Shipit instance, or trigger a `GithubSyncJob`/sync against an arbitrary victim stack. A forged passing status can satisfy `required_statuses`/`deployable?` checks and enable an unauthorized deploy of a commit that never actually passed CI review in the victim's own CI system — this is a cross-repository write and can lead to an unauthorized deploy, matching the Critical impact bar.

### Likelihood Explanation
Exploitability requires only: (1) the target Shipit instance is configured with more than one GitHub organization (a documented, supported configuration via `Shipit.github_organizations`), and (2) the attacker legitimately controls the webhook/App credentials for at least one of those organizations (not the victim's). No Shipit session, `ApiClient` token, or victim credentials are required — the attacker only needs their own webhook secret and the public SHA of the victim's commit, both of which are attacker-obtainable without any privileged access to the victim.

### Recommendation
Bind the field used for signature-organization selection to the field used for resource resolution: after verifying the HMAC, re-derive `repository_name`/`stacks` strictly from `repository.owner.login` (the same field used to select the signing organization), and reject the request if `repository.full_name`'s owner segment does not match `repository.owner.login`. Additionally, scope `StatusHandler`'s `Commit.where(sha: params.sha)` lookup to commits belonging to stacks under the verified repository/organization instead of a global SHA lookup.

### Proof of Concept
1. Attacker administers Org A's GitHub App/webhook in a Shipit instance that also hosts stacks for Org B (`Shipit.github_organizations` includes both), and thus knows Org A's `webhook_secret`.
2. Attacker finds a public commit SHA belonging to a stack in Org B (e.g., from GitHub's public UI/API).
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. `verify_signature` looks up `repository_owner` = `"OrgA"`, fetches Org A's `webhook_secret`, and validates the HMAC — which the attacker computed correctly since they know Org A's secret. [1](#0-0) 
5. `StatusHandler#process` finds the commit by SHA globally (no org/repo check) and creates a `success` status on it, potentially satisfying Org B's `required_statuses` and enabling deployment of that commit. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
