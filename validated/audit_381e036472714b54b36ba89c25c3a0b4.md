### Title
Cross-repository CI status forgery via unscoped `Commit` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub `status` webhook against the GitHub App/organization derived from `repository.owner.login` in the payload [1](#0-0) , but `StatusHandler#process` never checks that the commit it writes to actually belongs to that verified repository — it queries `Commit` globally by `sha` alone [2](#0-1) . This breaks the binding `verified_organization/repository == repository written`.

### Finding Description
The base `Handler` class defines the intended scoping mechanism: handlers should resolve the target `Repository`/`Stack`s from `payload.dig('repository', 'full_name')` via the `stacks` helper [3](#0-2) , and `PushHandler` correctly uses this scoping (`stacks.not_archived.where(branch:)`) [4](#0-3) .

`StatusHandler`, however, ignores this pattern entirely:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`WebhooksController` only verifies the signature against the webhook secret configured for the organization named in `repository.owner.login` (or `organization.login`) [5](#0-4) . It does not further restrict which repository's data the handler may mutate. Because `StatusHandler` looks up `Commit` records by `sha` across the entire `commits` table — with no `repository_id`/`stack_id` filter — any organization/repository that has a legitimately configured Shipit webhook (i.e., any tenant onboarded to a multi-tenant Shipit instance) can send a validly-signed `status` event whose `sha` matches a commit belonging to a completely different, unrelated stack/repository, and have Shipit record an attacker-controlled CI status (`state`, `context`, `target_url`, `description`) against that foreign commit.

### Impact Explanation
Commit `Status` records feed directly into merge-queue and deploy gating logic: `MergeRequest::StatusChecker`/`all_status_checks_passed?`/`any_status_checks_missing?` consult `head.statuses_and_check_runs` [6](#0-5) , and `ProcessMergeRequestsJob` automatically merges a pending PR once `all_status_checks_passed?` returns true [7](#0-6) . An attacker who controls a legitimately-onboarded organization/repository in the same Shipit instance can forge a "success" status for a commit sha they don't own (SHAs are often public, e.g. via GitHub UI/API, PR pages, or CI logs), potentially causing an unauthorized merge/deploy of a change to a stack outside their authorization boundary. This crosses the "organization authenticated vs. repository written" trust boundary and matches the Critical bar for "cross-repository writes" / "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitability requires only: (1) the attacker's own organization/repository already has a legitimate Shipit webhook configured (a normal, documented onboarding step, not a stolen secret), and (2) knowledge of a target commit SHA in another tenant's repository, which is often public information (SHAs are not secrets). No `ApiClient` token, session, or GitHub App private key is needed. This is realistic in any multi-tenant Shipit deployment serving multiple organizations/repositories.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/other handlers do: restrict the `Commit` lookup to commits belonging to `stacks` (derived from `payload.dig('repository', 'full_name')`), e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a webhook verified for organization/repository X can never write status data for commits belonging to a different repository.

### Proof of Concept
1. Attacker controls `github.com/attacker-org/attacker-repo`, which is configured in Shipit with its own valid `webhook_secret` for `attacker-org`.
2. Attacker discovers (via public GitHub UI/API) a commit SHA `deadbeef...` that belongs to `victim-org/victim-repo`, tracked by a Shipit stack with a pending merge request gated on CI status `ci/required`.
3. Attacker sends a GitHub `status` webhook to Shipit, signed with `attacker-org`'s own valid `webhook_secret`, with body:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/attacker-repo" }
}
```
4. `verify_signature` succeeds (correct secret for `attacker-org`) [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (ignoring the fact the payload's own `repository` field says `attacker-repo`), and creates a "success" status on it [2](#0-1) .
6. `ProcessMergeRequestsJob` subsequently sees `all_status_checks_passed?` true for the victim's PR and merges it.
