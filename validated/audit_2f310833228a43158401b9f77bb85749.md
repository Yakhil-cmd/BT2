The reported bug is specific to the NounsBuilder Solidity `Token.sol` contract's founder-vesting mechanism, where a missing `% 100` on `reservedUntilTokenId` causes a token-id modulo arithmetic mismatch between the ID a founder's first vesting slot is stored at (`tokenRecipient[200]`) and the ID range actually checked during claiming (`tokenId % 100` in `_isForFounder`). This bug class requires a specific pattern: a reserved-slot NFT ID space cycled via modulo arithmetic where the storage write and the later read use inconsistent modulus reduction.

I searched the FRAME `pallet-vesting` implementation and the `nfts` pallet for anything structurally similar:

- `pallet-vesting`'s `Vesting` storage map is keyed directly by `AccountId`, not by a modulo-reduced numeric ID, and vesting schedules are stored/read via `Vesting::<T>::get(&who)` and `write_vesting` — there is no modulo-based slot derivation at all. [1](#0-0) [2](#0-1) 
- `pallet-nfts`'s `do_mint` takes an explicit `item: T::ItemId` supplied by the caller (or derived via `Incrementable` for auto-IDs) and stores it directly in `Item`/`ItemConfigOf` maps — there is no reserved-slot cycling or modulo-based ID assignment scheme comparable to `_getNextTokenId`/`_addFounders` in the report. [3](#0-2) 
- `polkadot/runtime/common/src/claims` (another vesting-adjacent pallet) also keys vesting data by `EthereumAddress`/`AccountId` with no modulo-based ID reservation. [4](#0-3) 

None of these FRAME pallets implement the "reserved token-id slot cycled via `% 100`" pattern that the original bug depends on. Since the underlying invariant violated in the report (inconsistent modulus reduction between write-path and read-path for a cyclic ID scheme) does not have a corresponding structural analog anywhere in the reachable, user-facing entry points of `pallet-vesting`, `pallet-nfts`, or the claims pallet, there is no demonstrable Polkadot SDK analog to report.
