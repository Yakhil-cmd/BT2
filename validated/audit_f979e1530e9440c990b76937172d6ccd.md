### Title
Webhook signature is verified against an attacker-selected GitHub organization's secret, but the repository the payload writes to is never checked against that organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` supports Shipit's documented multi-organization GitHub App configuration (`config/secrets.*.yml`, each org having its own `webhook_secret`) [1](#0-0) . The organization used to select which HMAC secret verifies the request is parsed directly from the untrusted, not-yet-verified payload, but the repository that the resulting handlers act on is parsed independently from the same payload with no cross-check that it belongs to the org whose secret validated the signature.

### Finding Description
`verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), looks up `Shipit.github(organization: repository_owner)`, and verifies `X-Hub-Signature` against **that organization's** `webhook_secret`: [2](#0-1) 

`Shipit.github` resolves the config strictly by the caller-supplied organization key, and each organization in the multi-org schema has its own independent `webhook_secret`: [3](#0-2) 

Once the signature check passes (using whatever org's secret matched), the same raw payload is dispatched to all registered handlers with no further scoping to that organization: [4](#0-3) 

Handlers determine the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` — a completely separate field from `repository.owner.login` used for signature-org selection — with no validation that this repository belongs to the organization that authenticated the request: [5](#0-4) [6](#0-5) 

This is the same class of trust-binding break as the referenced report: the field used to select/verify the credential (`repository.owner.login`) is not bound to the field the privileged action is actually performed on (`repository.full_name`). Because Shipit can host stacks for multiple organizations under one instance, each with its own GitHub App and `webhook_secret` (a secret that legitimately belongs to, and is known by, the administrators of that organization's own GitHub App — not a Shipit-privileged credential), an attacker who administers **their own** onboarded organization's GitHub App can:
1. Set `repository.owner.login` (or `organization.login`) in the payload to their own org name X, so `Shipit.github(organization: "X")` resolves to their own known `webhook_secret`.
2. Compute a valid `X-Hub-Signature` over the full raw body using their own secret — this passes `verify_signature`.
3. Set `repository.full_name` in the same body to `"OTHER_ORG/other-repo"` — a repository/stack tracked under a different organization entirely.
4. The handler (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolves the stack via `Repository.from_github_repo_name("OTHER_ORG/other-repo")` and performs the corresponding write actions (triggering `sync_github`, updating commit statuses, archiving/unarchiving review stacks, updating PR metadata) against that unrelated organization's stack — none of which the attacker's org or webhook_secret should ever be authoritative for.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written," letting an attacker who legitimately controls only their own onboarded GitHub organization forge cross-organization state changes: fake CI/commit statuses, forced `sync_github` triggers, and review-stack archive/unarchive/label actions on repositories belonging to a different tenant/organization of the same Shipit instance. Depending on downstream handler logic (e.g., commit status handling feeding into deploy gating, or review-stack provisioning/deprovisioning), this can influence or unblock deploy decisions on a stack the attacker does not own, which is a cross-repository write achieved purely by controlling one's own tenant's webhook credential — no Shipit session, API token, or the true `webhook_secret` of the target org is required.

### Likelihood Explanation
Requires (a) a Shipit deployment configured with the multi-organization GitHub schema (explicitly documented and supported), and (b) attacker control of at least one onboarded organization's own GitHub App/webhook_secret — a low bar for a multi-tenant setup, since organization admins routinely know their own app's webhook secret. No additional privilege inside Shipit is needed.

### Recommendation
After verifying the signature, cross-check that `repository.full_name` (or `organization.login` for org-level events) actually belongs to the organization (`repository_owner`) whose secret was used to validate the signature, and reject/drop the event otherwise. Alternatively, scope handler repository/stack lookups to only repositories owned by `repository_owner`, rejecting any handler resolution outside that organization boundary.

### Proof of Concept
1. Onboard organization `attacker-org` to the shared Shipit instance with its own GitHub App and known `webhook_secret` (`SECRET_A`).
2. Craft a JSON push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(SECRET_A, body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner == "attacker-org"`, fetches `SECRET_A`, and the signature matches → request passes.
6. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [7](#0-6)  and triggers `stack.sync_github(expected_head_sha: "deadbeef")` on the victim organization's stack, despite the request only being authenticated for `attacker-org`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
