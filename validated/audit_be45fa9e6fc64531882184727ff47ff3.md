This confirms the vulnerability: `CheckSuiteHandler` and `PushHandler` both scope their lookups through `stacks` (which resolves via `Repository.from_github_repo_name(repository_name)`), but `StatusHandler` does not — it queries `Commit.where(sha: params.sha)` globally across the entire `commits` table with no repository filter at all.

### Title
Cross-repository status forgery via unscoped commit lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no constraint tying the webhook's `payload.repository` to the commit's owning stack/repository, unlike `PushHandler` and `CheckSuiteHandler`, which both scope through the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`). Any signed `status` webhook whose `sha` happens to match a commit tracked by a *different* repository's stack will create a `Status` on that unrelated commit, which can trigger `Commit#schedule_continuous_delivery` and enqueue `ContinuousDeliveryJob` for the victim stack.

### Finding Description
The broken binding is: `params.repository.full_name == commit.stack.repository.full_name` is never checked, while the correct binding for every other handler is enforced via `stacks = Repository.from_github_repo_name(repository_name)&.stacks`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:24` (`verify_signature`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken straight from the attacker-controlled JSON payload (`params.dig('repository', 'owner', 'login')`) [1](#0-0) [2](#0-1) . This only proves the request was signed by *some* GitHub App/organization already connected to Shipit — it says nothing about which specific repository within that scope the event concerns.
- `Shipit::Webhooks::Handlers::Handler#stacks` correctly scopes further lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [3](#0-2) .
- `PushHandler#process` and `CheckSuiteHandler#process` both use this `stacks` scope before touching any commit [4](#0-3) [5](#0-4) .
- `StatusHandler#process`, however, does **not** use `stacks` at all: it runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, a global, repository-unscoped query [6](#0-5) .
- `create_status_from_github!` creates a `Status` record tied to `commit.stack_id` (the commit's own stack, not the payload's repository) [7](#0-6) .
- `Status` has `after_commit :schedule_continuous_delivery, ... on: :create`, which calls `commit.schedule_continuous_delivery` [8](#0-7) .
- `Commit#schedule_continuous_delivery` checks `deployable? && stack.continuous_deployment? && stack.deployable?` and enqueues `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)` [9](#0-8) .

Exploit flow: sha values are content-addressed and identical across any repository sharing the same git history (e.g. a fork, or a repository whose history was seeded from/merged with the victim's). An attacker who owns (or is a collaborator on) any GitHub repository already connected to Shipit — i.e., under an organization for which `Shipit.github(organization: ...)` resolves — pushes/creates a commit whose sha matches a commit already tracked in the victim's stack (trivial via `git fetch` from the victim's public repo and pushing to their own fork, then emitting a `status` event via GitHub or a raw HTTP POST that GitHub would sign, or via GitHub's real status API on their own repo containing that same commit). GitHub (or the attacker, if they control the webhook config on their own connected repo) sends the signed `status` webhook with `repository.full_name` = attacker's repo but `sha` = the shared commit hash. `verify_signature` passes because the signature matches the attacker's own legitimately configured organization/app. `StatusHandler` then finds **every** `Commit` row in the database with that sha — including the victim's — and creates a `success` `Status` scoped to the victim's `stack_id`, satisfying `deployable?` and triggering `ContinuousDeliveryJob` for the victim's stack.

Existing guards do not prevent this: `verify_signature` only authenticates the org/app that sent the request, not the specific repository-to-commit binding; `drop_unhandled_event` and `ExplicitParameters` (`StatusHandler`'s `params do ... end`) only validate shape, not repository ownership; there is no `subset`/repository validator on `Status` creation tying it back to `params.repository.full_name`.

### Impact Explanation
An attacker with a webhook signed for any Shipit-connected organization/repository can write a `Status` for, and trigger unauthorized continuous deployment/rollback scheduling on, a completely unrelated tenant's stack whose commit sha happens to coincide (fork scenario, shared monorepo history, or cherry-picked/rebased commits). This is a cross-repository write ("a payload for one repository mutating another's stack, commit ... an unauthorized deploy") — Critical severity per the given categories. It is repeatable against any stack whose repository shares commit history with a repository the attacker can get a signed webhook for.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment? == true`, `ignore_ci? == false`, is currently `deployable?`, and shares at least one commit sha with a repository connected to a Shipit-verified GitHub App/organization that the attacker controls or can trigger events from (a fork is the natural, low-cost way to guarantee shared shas). The attacker needs no Shipit credentials, session, or secret — only the ability to get a `status` webhook fired for a repository already integrated with Shipit. This is a realistic setup in any organization-wide Shipit deployment with multiple teams/repos and open forking.

### Recommendation
Scope `StatusHandler#process` (and `create_status_from_github!`) through the same repository-derived `stacks` helper used by `PushHandler`/`CheckSuiteHandler`, e.g. `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })` or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status can only be attached to commits belonging to stacks whose `Repository` matches `params.repository.full_name`.

### Proof of Concept
```ruby

require 'test_helper'

module Shipit
  class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
    include ActiveJob::TestHelper

    test "status webhook for repo A must not create a Status/deploy for repo B's commit sharing the same sha" do
      victim_repo = shipit_repositories(:shipit)
      victim_stack = shipit_stacks(:shipit)
      victim_stack.update!(continuous_deployment: true)
      shared_commit = shipit_commits(:first) # belongs to victim_stack, deployable preconditions met

      attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'evil-fork')

      forged_payload = {
        'sha' => shared_commit.sha,
        'state' => 'success',
        'context' => 'ci/travis',
        'branches' => [{ 'name' => victim_stack.branch }],
        'repository' => { 'full_name' => attacker_repo.full_name, 'owner' => { 'login' => 'attacker' } },
      }

      assert_no_difference -> { shared_commit.statuses.count } do
        assert_no_enqueued_jobs(only: ContinuousDeliveryJob) do
          Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)
        end
      end
    end
  end
end
```
Both sides of the binding: expected `params.repository.full_name == "attacker/evil-fork"` must not equal `shared_commit.stack.repository.full_name == "shopify/shipit-engine"` (victim), so no `Status` and no `ContinuousDeliveryJob` should result. Against current code, `StatusHandler#process`'s unscoped `Commit.where(sha:)` lookup finds `shared_commit` anyway, creates the `Status` under `victim_stack`, and `assert_no_enqueued_jobs` fails, demonstrating the forged cross-repository deploy trigger.
