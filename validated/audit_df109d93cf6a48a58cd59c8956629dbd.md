## Confirmed vulnerability

The bug-class analog to the staking report ("a value the code trusts is not the same value the signature actually protected") maps directly onto `Shipit::WebhooksController#verify_signature` combined with `Shipit::GitHubApp#verify_webhook_signature`.

### Title
Webhook signature check is keyed off an attacker-controlled, unverified payload field and silently passes when that organization has no webhook secret configured, allowing forged webhooks to be dispatched to any stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects **which** `GitHubApp`/secret to validate the incoming signature against using `repository_owner`, a value read straight out of the *unauthenticated* JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1)  That same field is never re-checked against the field the downstream handlers actually act on (`repository.full_name`) once verification "succeeds". [3](#0-2) 

Additionally, `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved app has no `webhook_secret` configured: `return true unless webhook_secret`. [4](#0-3) 

### Finding Description
The binding that should hold is: **"the organization whose secret authenticated the signature" == "the repository the code writes/updates on behalf of that request."** This engine breaks that binding:

1. `verify_signature` computes `repository_owner` from the raw, unverified payload, then does `Shipit.github(organization: repository_owner)` to pick a `GitHubApp` and validate the signature against *that* organization's secret. [1](#0-0) 
2. If a multi-org deployment (`Using Multiple Github Applications`, documented in `docs/setup.md`) has any organization configured with `webhook_secret` blank/omitted — which the docs explicitly mark optional — `verify_webhook_signature` returns `true` for **any** signature header value for that org. [4](#0-3) 
3. Once `verify_signature` passes, `WebhooksController#create` re-parses the same raw body and dispatches it to handlers using the `repository.full_name`, `sha`, `ref`, etc., fields — none of which are required to match `repository_owner` used in step 1. [5](#0-4) [3](#0-2) 
4. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. resolve target `Stack`/`Commit` records purely from these payload fields with no re-verification that they belong to the organization actually authenticated. [6](#0-5) [7](#0-6) 

So an unprivileged attacker who knows (or controls) an org configured with no `webhook_secret` can set `repository.owner.login` to that org (or omit it and use the `organization.login` fallback) to sail through `verify_signature` with an arbitrary/empty signature, while setting `repository.full_name` to a **different, secured** organization's repository to trigger `GithubSyncJob`, status updates, or `RefreshCheckRunsJob` against stacks that belong to an org that *does* have a proper webhook secret. This crosses the "an organization that authenticated versus the repository that is written" equality named in the rules.

Before the attack: signature verification is meant to gate all mutations for a given stack/repo to requests genuinely originating from that repo's org.
After the attack: verification is satisfied by an unrelated no-secret organization, while the mutation target (`repository.full_name`) is a different, protected org/repo — the equality "authenticated org == written repo org" is broken.

### Impact Explanation
This allows push/status/check_suite spoofing against stacks owned by properly-secured organizations, as long as any other org in the same Shipit instance has a blank `webhook_secret` (an officially supported, documented configuration — see `docs/setup.md`'s "Webhook secret (optional)"). Concretely: `push` events can trigger `stack.sync_github(expected_head_sha:)`, and `status` events can inject arbitrary commit statuses via `Commit#create_status_from_github!`, both without the requester ever proving anything about the target org. This maps to an unauthorized write against a stack the attacker doesn't control — i.e., unauthorized deploy-trigger surface — which fits the "cross-repository writes" / "unauthorized deploy" bar.

### Likelihood Explanation
Requires (a) a multi-org Shipit deployment, and (b) at least one configured org with no `webhook_secret` (explicitly documented as optional in `docs/setup.md`). Given the docs present `webhook_secret` as optional and even show it as a commented-out/blank field in the double-github-app test fixture, this misconfiguration is realistic and not a hypothetical edge case, though it does depend on operator configuration rather than being universally exploitable out of the box.

### Recommendation
- Require `webhook_secret` to be non-blank for every configured GitHub App/org; fail closed (reject request) rather than `return true` when it's absent.
- After signature verification, cross-check that `repository.owner.login`/`organization.login` used to select the verifying secret matches the `repository.full_name` owner actually used by the handlers before dispatching.

### Proof of Concept
1. Configure two orgs in `secrets.yml` per `docs/setup.md`'s "Using Multiple Github Applications": `OrgNoSecret` (no `webhook_secret`) and `OrgSecured` (with a real `webhook_secret`), each with stacks.
2. POST to `/webhooks` with header `X-Github-Event: push`, `X-Hub-Signature: sha1=anything`, and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgNoSecret" },
    "full_name": "OrgSecured/target-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgNoSecret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus signature. [4](#0-3) 
4. `create` dispatches to `PushHandler`, which looks up stacks via `Repository.from_github_repo_name("OrgSecured/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on `OrgSecured`'s stack — despite `OrgSecured`'s secret never being checked. [8](#0-7) [3](#0-2)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
