### Title
Webhook signature is verified against the payload's declared organization while the affected Stack is resolved from the payload's declared repository, letting a mismatched payload update stacks the verified organization never owns - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates the incoming webhook by looking up `Shipit.github(organization: repository_owner)` where `repository_owner` is taken from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), then verifies the HMAC using that organization's configured `webhook_secret`. Once verification passes, `#create` dispatches the *entire raw payload* to `Shipit::Webhooks.for_event(event)` handlers, which independently resolve the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')` in `Handler#stacks`/`#repository_name`. Nothing ties the `full_name` used by the handler to the `owner.login`/`organization.login` used for signature verification, so the "organization whose signature was checked" and the "repository actually written to" are two independently-controlled fields inside the same signed body.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes: [1](#0-0) 
using `repository_owner`, defined as: [2](#0-1) 

`Shipit.github(organization:)` fetches a *per-organization* config and builds a `GitHubApp`, whose `verify_webhook_signature` checks the HMAC using that org's `webhook_secret`: [3](#0-2) 

If the request is verified, `#create` forwards the same raw JSON body, unmodified, to all registered handlers for the event: [4](#0-3) 

Every handler resolves its target `Stack`/`Repository` from a *different* field of the same payload — `repository.full_name` — via `Handler#stacks`/`#repository_name`: [5](#0-4) 

For example, `PushHandler#process` uses this to select stacks and immediately trigger a sync against attacker-influenced parameters: [6](#0-5) 

The binding broken is:
`organization authenticated (repository.owner.login / organization.login, checked against org X's webhook_secret)` == `repository/stack actually written (repository.full_name, resolved independently by the handler)`

Nothing in `verify_signature` or in `Handler` enforces that `full_name` belongs to the organization whose secret validated the signature. Multi-tenant Shipit deployments configure one `webhook_secret` per organization (`github_app_config`/`TOP_LEVEL_GH_KEYS` in `lib/shipit.rb:63,196-200`), precisely so that org A's GitHub App installation cannot forge events for org B's repositories. Because the two fields are decoupled, a webhook correctly signed for org A (whose secret the attacker legitimately possesses, e.g. as an admin of their own GitHub App installation on org A) can carry `repository.full_name` pointing at a stack belonging to org B. The signature check passes (org A's secret matches), yet the handler acts on org B's stack.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. A party who controls a legitimately-configured GitHub App/organization webhook secret for one tenant can cause writes (triggering `GithubSyncJob`, creating `Status`/`Commit` records, unarchiving/archiving review stacks, mutating labels, etc.) against a *different* organization's stacks that they do not control or have any authorization over — an unauthorized cross-repository/cross-organization state change reachable purely from a webhook request, without ever needing the victim organization's own `webhook_secret`, an `ApiClient` token, or a Shipit session.

### Likelihood Explanation
Exploitability depends entirely on the attacker possessing *a* valid `webhook_secret` for *some* organization configured in the multi-tenant Shipit instance — e.g., because they administer their own GitHub organization/App installation that is legitimately onboarded to the same Shipit instance. This is a realistic scenario for any Shipit deployment serving multiple, mutually-untrusted organizations (the exact scenario the per-org `webhook_secret` design in `github_app_config` is meant to isolate). The attacker does not need the target organization's secret, a session, or an `ApiClient` token — only control of the JSON body of a webhook signed with their own org's key, which they can freely construct.

### Recommendation
In `Handler` (or a shared step before dispatch), require that the organization owning `repository.full_name` (or `organization.login`) match the organization whose `webhook_secret` was used to verify the signature (i.e., the same `repository_owner` computed in `WebhooksController`), and reject/drop the event otherwise. Concretely, thread the verified `repository_owner` into `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }`, and have `Handler#stacks`/`#repository_name` assert that the resolved repository's owner equals `verified_organization` before returning any records.

### Proof of Concept
1. Deploy Shipit multi-tenant with two configured GitHub orgs, `orgA` (attacker-controlled installation, secret `secretA`) and `orgB` (victim, secret `secretB`), each tracking stacks for their own repos.
2. Attacker crafts a `push` webhook JSON body with:
   - `repository.owner.login = "orgA"` (or `organization.login = "orgA"`)
   - `repository.full_name = "orgB/victim-repo"`
   - `ref = "refs/heads/main"`, `after = <attacker-chosen sha>`
3. Attacker signs the raw body with `secretA` (`HMAC-SHA1`) and sends it as `X-Hub-Signature` to `POST /webhooks`.
4. `verify_signature` computes `repository_owner = "orgA"`, calls `Shipit.github(organization: "orgA")`, and `verify_webhook_signature` succeeds because the signature matches `secretA`.
5. `#create` dispatches the payload to `PushHandler`, whose `stacks` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and enqueues `GithubSyncJob`/triggers `sync_github(expected_head_sha: attacker-chosen sha)` on `orgB`'s stack — a write against org B triggered solely by org A's credentials, with no cross-organization check performed anywhere in the request path.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
