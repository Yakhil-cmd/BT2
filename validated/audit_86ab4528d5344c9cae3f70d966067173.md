### Title
Scoped `ApiClient` tokens bypass stack authorization via `Api::CCMenuController` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`stack_id` present) can only resolve `Stack` records through the scoped `stacks` collection. `Api::CCMenuController` overrides the `stack` accessor to look up the target `Stack` directly via `Stack.from_param!`, bypassing the scoping that every other API controller relies on. This is structurally the same bug class as the reported ERC20 issue: a restriction ("only your own stack") is enforced in the primary access path but a second, inherited/overridden access path performs the same operation without going through that restriction.

### Finding Description
`Api::BaseController` defines the scoping used by nearly every stack-scoped endpoint: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` resolves the `:stack_id` param through that restricted relation. `TasksController`, `StacksController`, `DeploysController`, `RollbacksController`, `MergeRequestsController`, etc. all rely on this inherited `stack`/`stacks` implementation (confirmed via `grep` — none of them redefine `stack`).

`Api::CCMenuController`, however, redefines `stack` to query the unscoped `Stack` model directly: [2](#0-1) 

The only guard on this action is `require_permission :read, :stack`, which checks that the token *has* the `read:stack` permission string — it never checks *which* stack the permission applies to: [3](#0-2) 

So a token created with `stack_id` set to stack A (intended, by the operator who issued it, to only read/act on stack A) and the `read:stack` permission can call `GET /api/stacks/:any_stack/ccmenu` for stack B, C, … — any stack in the Shipit instance — because `Stack.from_param!` performs no ownership check. This is the same class of bug as approve+transferFrom bypassing a disabled `transfer`: the restriction (`stacks` scoping in `BaseController`) is enforced on the "normal" path but a sibling method inherited from the same base class re-implements the lookup without the restriction.

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches." A token deliberately scoped to a single, presumably less-sensitive stack can be used to read deploy/build status (`lastBuildStatus`, `activity`, lock state, latest deploy) for any stack managed by the Shipit instance, including stacks the token issuer never intended to expose to that credential. This matches the documented High-impact category of "unauthenticated read of stack state, task streams or deploy output" in the sense that it is a read of stack state entirely outside the authorization boundary the token was supposed to be limited to.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with the `read:stack` permission (a routine, low-privilege credential meant to be restricted to one stack, comparable to a lender that merely holds shares in the original report) can trivially trigger this by substituting a different `stack_id` in the URL — no additional secrets, sessions, or elevated roles are required beyond the token that was already scoped down specifically to prevent this access.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the scoped `stacks` relation (i.e. delegate to `super`, or use `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the CCMenu endpoint respects the same `current_api_client.stack_id` scoping enforced everywhere else.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to `stack_id` = stack A with permission `read:stack` (e.g. as configured via the `api_clients` admin UI, fixture `here_come_the_walrus` illustrates this scoping pattern: `stack: shipit`, `permissions: ['read:stack']`).
2. Confirm the token is properly scoped: `GET /api/stacks?...` with this token only lists stack A (per `BaseController#stacks`).
3. Call `GET /api/stacks/<org>/<stack-B-repo>/<env>/ccmenu` with the same Basic-Auth token, where stack B is a different, unrelated stack.
4. Observe a `200 OK` XML response containing stack B's `lastBuildStatus`, `lastBuildLabel`, `activity`, and lock state — data the token was never authorized to read, because `CCMenuController#stack` resolved it via unscoped `Stack.from_param!` rather than the scoped `stacks.from_param!` used elsewhere.
