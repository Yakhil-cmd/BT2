### Title
Unvalidated swap routes can attach a nested caller-authorized token transfer and drain unrelated wallet assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary
A malicious `swap` payload can route execution through an unallowlisted contract that performs an additional `token.transfer` from the account owner to an attacker. [1](#0-0)  Soroban records that transfer as a child of the caller's `swap_collateral` authorization; if the caller signs the simulated authorization tree, the transaction succeeds while draining unrelated wallet tokens. [2](#0-1) 

### Finding Description
`swap_collateral` authenticates the caller and account owner, then passes the attacker-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [3](#0-2) [4](#0-3)  `swap_tokens` narrowly authorizes only the controller-to-router input transfer, but then invokes the configured router with the opaque route payload. [5](#0-4)  The post-call checks only bound the controller's input spend and require positive output; they do not prevent a route-selected contract from requesting additional authorization from the original caller. [6](#0-5) 

A route-selected contract can therefore call `transfer(victim, attacker, amount)` on an unrelated token held by the victim. [1](#0-0)  Because the invocation is nested below the victim's controller call, simulation places that token transfer in the victim's authorization tree rather than treating it as a separate top-level authorization. [2](#0-1) 

### Impact Explanation
This is theft of user funds beyond the collateral amount intentionally routed through the strategy. [2](#0-1)  The demonstrated exploit leaves the attacker with the victim's unrelated wallet token while the position operation still completes and deposits the expected swap output. [7](#0-6) 

### Likelihood Explanation
Likelihood is Medium: an unprivileged attacker can construct and route through a malicious venue, but execution requires the victim to submit the poisoned route and sign the authorization tree containing the extra transfer. [8](#0-7)  The condition is realistic when users sign opaque routes produced by an attacker-controlled quoter or a client that does not reject unexpected child authorizations. [9](#0-8) 

### Recommendation
Do not allow strategy routes to invoke arbitrary route-selected contracts that can request caller authorization; restrict venues and pool addresses to protocol-approved contracts or otherwise enforce an authorization boundary that prevents child calls from joining the caller's auth tree. [8](#0-7)  Until protocol enforcement exists, clients must decode the route and reject any simulated `swap_collateral`, `multiply`, `swap_debt`, or `repay_debt_with_collateral` authorization containing child invocations beyond the expected controller-authorized input flow. [10](#0-9) 

### Proof of Concept
1. Deploy a malicious contract whose route entrypoint calls `token.transfer(victim, attacker, WALLET_BALANCE)` on an unrelated token held by the victim. [11](#0-10) 
2. Construct a `swap` route that invokes that contract while still returning enough output for the controller's positive-receipt and final-risk checks. [12](#0-11) 
3. Have the victim call `swap_collateral(caller, account_id, current, from_amount, new, swap)`. [13](#0-12) 
4. Simulation records the malicious token transfer as a child of the victim's `swap_collateral` authorization. [14](#0-13) 
5. Signing that tree drains the victim's unrelated wallet token while crediting the expected strategy output. [15](#0-14)
