### Title
Webhook signature verified against attacker-chosen organization while event is applied to an unrelated repository/stack, enabling cross-repository status/commit forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using one payload field (`repository.owner.login`), while `Shipit::Webhooks::Handlers::Handler` resolves the repository/stack that the event actually mutates from a *different* payload field (`repository.full_name`). Because both fields are attacker-controlled JSON in the same unauthenticated POST body, and because signature verification unconditionally passes when the selected organization has no `webhook_secret` configured, an attacker can make the "authenticated organization" and the "repository written" diverge.

### Finding Description
`verify_signature` derives the organization used to pick the verifying secret purely from the untrusted payload: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` treats a blank `webhook_secret` as an automatic pass: [3](#0-2) 

The Shipit multi-org config format explicitly supports organizations with no `webhook_secret` set (shown as `webhook_secret: # nil` in the shipped sample config): [4](#0-3) 

Once past `verify_signature`, every event handler resolves the actual `Repository`/`Stack` to act on from a *separate* field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`/the organization whose secret validated the request: [5](#0-4) 

`PushHandler` then mutates a victim stack's tracked head commit using attacker-supplied `after` (SHA): [6](#0-5) 

`StatusHandler` is even less scoped — it looks up commits globally by `sha` with no repository/stack filter at all, and writes a forged CI status onto any matching commit tracked anywhere in the Shipit instance: [7](#0-6) 

This breaks the intended trust binding: `organization whose signature was verified == organization/repository the event is applied to`. Before the attacker's request, this equality holds implicitly because GitHub only ever delivers events where `repository.owner.login` and `repository.full_name` are consistent for the real originating repo. After a forged request, an attacker sets `repository.owner.login` to an org they control (or to any org with no configured `webhook_secret`) to pass `verify_signature`, while setting `repository.full_name` to point at a victim stack tracked under a completely different organization/repository.

### Impact Explanation
This allows an unauthenticated third party (no Shipit session, no `ApiClient` token, no GitHub App key) to inject forged GitHub events (`push`, `status`, `check_suite`, `pull_request`, `membership`) against a stack they do not own, as long as any organization configured in the Shipit deployment lacks a `webhook_secret` (or the attacker owns/knows the secret for one org while other orgs' repos are also tracked). Concretely:
- `StatusHandler` lets the attacker forge a passing/failing CI status on any commit SHA tracked by the instance, regardless of which repository it belongs to, which can influence `deployable?`/`commit.create_status_from_github!` used by continuous delivery/merge automation, potentially triggering an unauthorized deploy or merge for a repository the attacker doesn't control.
- `PushHandler` lets the attacker force `stack.sync_github(expected_head_sha:)` for a victim stack with an attacker-chosen SHA.

This maps to the report's underlying bug class of an unsafe binding between what is verified/authorized and what is actually acted upon, and lands in the Critical bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires (a) the target Shipit instance to track stacks/repositories across more than one GitHub organization/app configuration, and (b) at least one configured organization with no `webhook_secret` (a state explicitly supported and shown as the default in the shipped sample config) or one whose secret the attacker can obtain by owning a repo/webhook in that org. Given multi-tenant Shipit deployments and that `webhook_secret` is optional per organization, this is a realistic configuration, making the likelihood moderate-to-high in such deployments.

### Recommendation
Bind the event to the same organization/repository that was verified: derive `repository_name`/stack resolution in `Handler` from the same trusted identifier used in `verify_signature` (e.g., pass the verified `repository_owner`/organization through to handlers and require `repository.owner.login == repository.full_name`'s owner segment), and reject events where these disagree. Additionally, `StatusHandler` should scope its `Commit.where(sha:)` lookup by the resolved/verified repository instead of searching globally. Do not allow signature verification to unconditionally pass for organizations without a configured `webhook_secret`; require an explicit, non-blank secret for every organization intended to receive webhooks.

### Proof of Concept
1. Configure (or observe) a Shipit instance tracking stacks for two GitHub orgs, `org-attacker` (no `webhook_secret` set, or secret known to attacker) and `org-victim` (tracked stack `org-victim/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` calls `Shipit.github(organization: "org-attacker")` and `verify_webhook_signature` returns `true` (blank secret / attacker-known secret) — request passes.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and writes a forged "success" status onto the victim commit, independent of `org-victim`'s actual CI/webhook secret, potentially unlocking deploy/merge automation gated on that status.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
