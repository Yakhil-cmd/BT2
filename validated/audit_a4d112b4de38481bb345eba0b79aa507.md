### Title
Permissionless `pallet-asset-rewards` pool creation + unbounded reward-per-token accumulator lets an attacker permanently freeze other stakers' funds via arithmetic overflow - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a Synthetix-style "reward-per-token" accumulator (`reward_per_token_stored`) that is structurally identical to the XDEFI `_pointsPerUnit` accumulator in the referenced report: it is computed as `reward_rate_per_block * elapsed_blocks * PRECISION_SCALING_FACTOR / total_tokens_staked` and monotonically accumulates into pool storage [1](#0-0) . Just like the XDEFI contract, this pallet has no floor on the divisor (`total_tokens_staked`) and no cap on the attacker-supplied multiplier (`reward_rate_per_block`), and pool creation is not actually privileged in the shipped runtimes despite the pallet doc claiming it is "restricted to a configured Origin" [2](#0-1) : every runtime that wires this pallet sets `CreatePoolOrigin = EnsureSigned<AccountId>` [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) , i.e. any ordinary signed account can create a pool and set an arbitrary `reward_rate_per_block`.

### Finding Description
1. **Entry point / attacker capability.** Any signed, unprivileged account can call `create_pool(reward_rate_per_block, expiry, ...)` because `CreatePoolOrigin = EnsureSigned<AccountId>` in every wired runtime [7](#0-6) . The attacker fully controls `reward_rate_per_block` (no maximum enforced) and `expiry` (arbitrarily far in the future), via the public extrinsic [8](#0-7) .
2. **Attacker becomes the first/dust staker.** `stake()` enforces no minimum stake amount at all (unlike `pallet-nomination-pools`, which enforces `MinJoinBond`/`MinCreateBond` and uses `checked_from_rational` guarded by `OverflowRisk`) [9](#0-8) . The attacker stakes `1` unit, keeping `total_tokens_staked` minimal — the exact analog of Alice locking `1 wei` in the XDEFI report.
3. **Unbounded accumulator.** `reward_per_token()` computes `reward_per_token_stored + reward_rate_per_block * elapsed_blocks * PRECISION_SCALING_FACTOR / total_tokens_staked` using `ensure_mul`/`ensure_div`/`ensure_add`, which return `ArithmeticError::Overflow` on overflow rather than saturating [10](#0-9) . `PRECISION_SCALING_FACTOR` is a constant `4096` [11](#0-10) . With `total_tokens_staked = 1` and an attacker-chosen `reward_rate_per_block` close to `Balance::MAX / 4096`, the multiplication overflows within a single block (or a small, attacker-controlled number of blocks for smaller rates).
4. **Every mutating call is gated by this computation.** `stake`, `unstake`, and `harvest_rewards` all call `update_pool_and_staker_rewards` → `reward_per_token` *before* performing any freeze/unfreeze/transfer [9](#0-8) [12](#0-11) . Once this computation overflows, the enclosing extrinsic returns `Err(ArithmeticError::Overflow)` and no state mutates — critically, this failure recurs on **every subsequent call to that pool** for **any staker**, because `total_tokens_staked` never grows enough to fix the ratio before the arithmetic is evaluated (a would-be large new stake is applied only *after* the reward computation that already reverts).
5. **Fund freeze.** Any legitimate staker who joined the pool before the overflow point has their tokens locked via `T::AssetsFreezer::increase_frozen` [13](#0-12) . Once the accumulator overflows, `unstake()` — which must also pass through `update_pool_and_staker_rewards` before calling `decrease_frozen` [14](#0-13)  — permanently fails, so the victim can never retrieve their frozen stake from that pool. This is the direct analog of Bob's `unlock()` permanently reverting in the XDEFI PoC.

This differs from `pallet-nomination-pools`, which explicitly hardens against this exact class of bug via `MinJoinBond`, `checked_from_rational` (not raw multiply-then-divide) and documented accuracy analysis [15](#0-14) , and via `pallet-staking-async`'s `Perbill`-based reward split which cannot overflow the same way [16](#0-15) . `pallet-asset-rewards` has neither protection.

### Impact Explanation
An unprivileged attacker can create a pool, dust-stake it, and drive the pool's `reward_per_token` accumulator into permanent arithmetic-overflow territory in a small, attacker-controlled number of blocks. Any other user who staked assets into that pool before the overflow threshold is crossed can never unstake — their frozen tokens are permanently stuck, and `harvest_rewards` is likewise permanently blocked. This matches the reported bug class: "malfunction the contract and even freeze users' funds," reachable purely through public, unprivileged extrinsics (`create_pool`, `stake`) with no governance, no stolen keys, and no malicious infrastructure component involved.

### Likelihood Explanation
High for any deployment that actually exposes `pallet-asset-rewards` with pool creation open to any signed account (as configured in the Asset Hub Westend/Rococo runtimes, the reference node runtime, and the staking-async parachain runtime). The attack requires only: (1) a `create_pool` call with an attacker-chosen `reward_rate_per_block`, (2) staking 1 unit, and (3) waiting the number of blocks needed for the deterministic checked-arithmetic overflow — entirely within the attacker's control and requiring no interaction with, or cooperation from, any other party. The main variable affecting likelihood is the actual deployed value ranges for `Balance`/`reward_rate_per_block`, but since the pallet enforces no upper bound on `reward_rate_per_block` at `create_pool` time, the attacker can always select a rate that guarantees overflow well within a practical time horizon.

### Recommendation
- Enforce a minimum non-dust stake and/or a "virtual"/offset floor on `total_tokens_staked` similarly to `pallet-nomination-pools`'s `MinJoinBond`/`MinCreateBond`, or seed pools with a non-zero minimum stake (the Uniswap V2 / XDEFI-team style mitigation).
- Replace the raw `mul` → `mul` → `div` chain in `reward_per_token()` with a rational/fixed-point primitive (e.g. `multiply_by_rational_with_rounding` or `FixedU128`-based accounting as used in `pallet-nomination-pools`) that fails gracefully/saturates instead of guaranteeing a permanent, unrecoverable freeze.
- Bound `reward_rate_per_block` relative to `Balance::MAX`/`PRECISION_SCALING_FACTOR`/pool lifetime at `create_pool`/`set_pool_reward_rate_per_block` time, or reduce `PRECISION_SCALING_FACTOR`/scale reward computation defensively.
- Provide an emergency/administrative path (as XDEFI ultimately implemented) allowing users to withdraw their principal stake even if the reward-accounting math is in an unrecoverable overflow state, decoupling `unstake` mechanically from `reward_per_token` computation success.
- Reconsider whether `CreatePoolOrigin = EnsureSigned<AccountId>` is intended in production runtimes, since the pallet's own documentation states pool creation "is restricted to a configured Origin," implying permissioned creation was the intended security model.

			T::AssetsFreezer::decrease_frozen(

				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);

			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}

	/// Get the current reward counter, based on the given `bonded_points` being the state of the
	/// bonded pool at this time.
	fn current_reward_counter(
		&self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(T::RewardCounter, BalanceOf<T>), Error<T>> {
		let balance = Self::current_balance(id);

		// Calculate the current payout balance. The first 3 values of this calculation added
		// together represent what the balance would be if no payouts were made. The
		// `last_recorded_total_payouts` is then subtracted from this value to cancel out previously
		// recorded payouts, leaving only the remaining payouts that have not been claimed.
		let current_payout_balance = balance
			.saturating_add(self.total_rewards_claimed)
			.saturating_add(self.total_commission_claimed)
			.saturating_sub(self.last_recorded_total_payouts);

		// Split the `current_payout_balance` into claimable rewards and claimable commission
		// according to the current commission rate.
		let new_pending_commission = commission * current_payout_balance;
		let new_pending_rewards = current_payout_balance.saturating_sub(new_pending_commission);

		// * accuracy notes regarding the multiplication in `checked_from_rational`:
		// `current_payout_balance` is a subset of the total_issuance at the very worse.
		// `bonded_points` are similarly, in a non-slashed pool, have the same granularity as
		// balance, and are thus below within the range of total_issuance. In the worse case
		// scenario, for `saturating_from_rational`, we have:
		//
		// dot_total_issuance * 10^18 / `minJoinBond`
		//
		// assuming `MinJoinBond == ED`
		//
		// dot_total_issuance * 10^18 / 10^10 = dot_total_issuance * 10^8
		//
		// which, with the current numbers, is a miniscule fraction of the u128 capacity.
		//
		// Thus, adding two values of type reward counter should be safe for ages in a chain like
		// Polkadot. The important note here is that `reward_pool.last_recorded_reward_counter` only
		// ever accumulates, but its semantics imply that it is less than total_issuance, when
		// represented as `FixedU128`, which means it is less than `total_issuance * 10^18`.
		//
		// * accuracy notes regarding `checked_from_rational` collapsing to zero, meaning that no
		//   reward can be claimed:
		//
		// largest `bonded_points`, such that the reward counter is non-zero, with `FixedU128` will
		// be when the payout is being computed. This essentially means `payout/bonded_points` needs
		// to be more than 1/1^18. Thus, assuming that `bonded_points` will always be less than `10
		// * dot_total_issuance`, if the reward_counter is the smallest possible value, the value of
		//   the
		// reward being calculated is:
		//
		// x / 10^20 = 1/ 10^18
		//
		// x = 100
		//
		// which is basically 10^-8 DOTs. See `smallest_claimable_reward` for an example of this.
		let current_reward_counter =
			T::RewardCounter::checked_from_rational(new_pending_rewards, bonded_points)
				.and_then(|ref r| self.last_recorded_reward_counter.checked_add(r))
				.ok_or(Error::<T>::OverflowRisk)?;
