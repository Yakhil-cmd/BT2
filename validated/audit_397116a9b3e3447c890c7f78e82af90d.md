### Title
Webhook signature verification falls back to `organization.login`, allowing cross-organization forgery of webhook events targeting an unrelated repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `repository_owner`, which falls back to the top-level `organization.login` field whenever `repository.owner.login` is absent from the payload. Because Shipit supports hosting multiple GitHub organizations (`Shipit.github(organization: ...)`), an attacker who legitimately controls their own onboarded organization's app installation (and therefore knows their own org's `webhook_secret`) can craft a payload whose `repository.full_name` points at a victim organization's repository while omitting `repository.owner.login`, causing the signature to be verified against the attacker's own (valid) secret while the event body still references — and is processed against — the victim's repository/stack.

### Finding Description
`verify_signature` computes the organization to check the signature against like this: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
end

def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up per-organization configuration (`app_id`, `installation_id`, `webhook_secret`) — this engine explicitly supports "Using Multiple Github Applications" where each configured organization has its own independent `webhook_secret`, as documented in `docs/setup.md`. The signature check therefore authenticates *which organization's secret* produced the HMAC, not which repository the payload claims to act on.

After signature verification passes, `create` dispatches the *entire* JSON payload to registered handlers, which act on whatever repository/stack is named inside the body: [4](#0-3) 

```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```

The `repository_owner` fallback only engages `organization.login` when `repository.owner.login` is missing — but the presence/absence of that one nested key is entirely attacker-controlled in the raw JSON body, independent of `repository.full_name`, which the downstream handlers use to resolve the target stack/repository (as seen in the `pull_request/*` handlers, which explicitly key off `full_name`). This breaks the intended binding: **organization authenticated (via `webhook_secret`) == repository written (via handler dispatch)**. An attacker who is a legitimate owner/installer of their *own* Shipit-configured GitHub organization knows their own `webhook_secret` (they configured it themselves when creating their GitHub App), and can freely POST arbitrary JSON to the public `/webhooks` endpoint with a valid HMAC computed against that known secret, while pointing `repository.full_name` at a victim organization's repository/stack that Shipit also hosts.

### Impact Explanation
This allows an attacker who only controls their own onboarded GitHub organization to forge webhook events (e.g. `push`, `status`, `check_suite`, `membership`) that are processed as if legitimately delivered for a victim organization's stack, without ever possessing the victim's `webhook_secret`, an `ApiClient` token, or repository write access. Depending on which handler is targeted, this can: enqueue `GithubSyncJob`/`RefreshCheckRunsJob` against the victim stack, forge CI `status` records that make otherwise-unreviewed commits appear `deployable?`, or otherwise corrupt commit/deploy state used to gate an unauthorized deploy — this crosses the "authorization crossing repository" boundary called out as in-scope (escalation into stack state / unauthorized deploy gating).

### Likelihood Explanation
Medium: it requires the attacker to control at least one legitimate organization configured in Shipit's `github` multi-org secrets (a normal, documented, supported configuration for shared Shipit instances hosting many orgs/teams) and to know that Shipit hosts a target victim repository/stack. No privileged Shipit credentials, sessions, or GitHub write access to the victim repo are needed — only the ability to craft an arbitrary JSON POST with a signature computed from the attacker's own known secret.

### Recommendation
Do not derive the verification-organization from an unauthenticated fallback field (`organization.login`) that is independent of the field(s) the handlers actually act upon (`repository.full_name`/`repository.owner.login`). Instead:
1. Require `repository.owner.login` (or equivalently derive the owner strictly from `repository.full_name`) for any event type where handlers act on a repository, and reject events lacking it rather than falling back to `organization.login`.
2. After selecting the GitHub App/organization used for signature verification, cross-check that the resolved organization actually matches the owner of the repository the payload claims to mutate, before dispatching to handlers.

### Proof of Concept
1. Attacker legitimately configures/owns a GitHub organization `attacker-org` with its own Shipit-registered app and knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` (or `status`/`check_suite`) JSON body where:
   - `organization.login` = `"attacker-org"`
   - `repository` = `{"full_name": "victim-org/victim-repo", ...}` with no `owner` sub-key
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body and POSTs it to `/webhooks`.
4. `repository_owner` returns `"attacker-org"` (fallback branch) because `repository.owner.login` is absent; `Shipit.github(organization: "attacker-org")` verifies the signature successfully.
5. `create` dispatches the parsed body to `Shipit::Webhooks.for_event('push')`, whose handlers resolve the target stack from `repository.full_name` = `"victim-org/victim-repo"`, processing the forged event against the victim's stack despite the signature never having been checked against `victim-org`'s secret.
