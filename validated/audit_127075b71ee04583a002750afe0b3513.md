### Title
`MembershipHandler#find_or_create_team!` grants team membership based on `github_id` alone, letting any organization overwrite/join teams owned by another organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `params.team.id` (the numeric GitHub team id), with no check that `params.organization.login` matches the `organization` column already stored on that `Team` row. Because `WebhooksController#verify_signature` authenticates the *organization* sending the webhook, not the *team* being referenced inside the payload, any organization configured in this Shipit instance (as documented for the "Using Multiple GitHub Applications" setup) can add its own users to a `Team` that legitimately belongs to a different organization, as long as it can produce/guess a matching `team.id`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`organization.login of the signer that verified the webhook body == team.organization column of the Team row that add_member is applied to`.

Code path:
- `WebhooksController#verify_signature` [1](#0-0)  resolves the HMAC key via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization','login')` [2](#0-1) . This only proves the payload was signed by *some organization's* webhook secret registered in Shipit — it does not bind or scope the payload's `team.id` to that same organization.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does the lookup purely by `github_id`: [3](#0-2) 
  If a `Team` row with that `github_id` already exists (e.g. one of the privileged teams pre-populated via `Shipit.github_teams`, see `lib/shipit.rb` line 256-258), the `find_or_create_by!` block (which sets `team.organization`) is **not** executed — the existing row, with its original `organization`, is returned unchanged.
- `process` unconditionally calls `team.add_member(member)` on whichever `Team` row was returned [4](#0-3) , and `add_member` simply appends the membership with no organization check [5](#0-4) .
- Because `User#authorized?` grants app-wide access whenever the current user belongs to any team enumerated in `Shipit.github_teams` [6](#0-5) , membership added by any signed org's forged `membership` webhook is sufficient to flip `authorized?` to `true` for an arbitrary attacker-controlled login.

The existing test suite only exercises this handler with a single, trusted organization ("shopify") and never validates cross-organization behavior — `test/controllers/webhooks_controller_test.rb` `membership_params` always sends `organization: { login: 'shopify' }` [7](#0-6) , so the missing organization/team binding is not covered.

None of the standard guards intervene: `verify_signature` authenticates the sender org but doesn't scope the payload's team id to it; `ExplicitParameters` (the `params do ... end` schema) only validates types/presence, not cross-field relationships; there is no `require_permission!`/`stacks` scope check inside a webhook handler since these run outside normal session/API-token authentication paths.

### Impact Explanation
A signed `membership` webhook from any organization onboarded into this Shipit instance's `github` config (per the documented multi-org setup) can add an arbitrary GitHub login to any pre-existing `Team` row simply by naming that team's known/guessed numeric `github_id`. If that `Team` is one of the entries in `Shipit.github_teams` (the authorization allow-list), the attacker's account becomes `authorized?` for the entire Shipit instance, i.e., full application access across every stack gated by that team — this matches the "High: escalation into `Shipit.github_teams` authorization" impact category. The attack is repeatable per attacker-controlled login and does not require compromising any Shipit or victim-org secret.

### Likelihood Explanation
Exploitability strictly depends on the attacker's own organization already being a trusted, independently-configured GitHub App installation in this specific Shipit deployment (as in the documented multi-organization secrets layout). Given that precondition, the attacker needs only: (1) knowledge/guessing of the target privileged `Team`'s numeric `github_id` (GitHub team ids are not secret and may be discoverable via public team pages/API or observed traffic), and (2) the ability to compute an HMAC-SHA1 signature with their own org's `webhook_secret`, which they legitimately possess. No Shipit session, API token, or victim-org secret is required.

### Recommendation
In `find_or_create_team!`, verify that `params.organization.login` matches the existing `team.organization` before allowing any mutation, and reject (or no-op) the webhook when the organization named in the payload does not own the team with that `github_id`. Additionally, consider looking up/creating the team scoped by `(organization, github_id)` rather than by `github_id` alone, mirroring the uniqueness index on `(organization, slug)`.

### Proof of Concept
Minitest plan (add to `test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/membership_handler_test.rb`):
1. Create a privileged `Team` fixture `victim_team` with `organization: 'shopify'`, `github_id: 999`, and add it to `Shipit.github_teams` (stub `Shipit.github_teams` to include it).
2. Stub `Shipit.github(organization: 'evil-org')` (or add an `evil-org` entry to test secrets) so `verify_webhook_signature` returns `true` for a payload signed with `evil-org`'s own secret.
3. POST a `membership` webhook with `X-Github-Event: membership`, body `{ action: 'added', team: { id: 999, name: 'x', slug: 'x', url: 'http://x' }, organization: { login: 'evil-org' }, member: { login: 'attacker' } }`, signed with `evil-org`'s secret.
4. Assert `response` is `:ok`, `Shipit::Team.find_by(github_id: 999).organization` is still `'shopify'` (binding claim: should equal `'evil-org'` if this were legitimate, showing the mismatch), and `Shipit::User.find_by(login: 'attacker').authorized?` is `true` — demonstrating unauthorized escalation from an org that does not own the team.
