### Title
CCMenu status token minted for one stack grants unauthenticated read access to all stacks - ([File: app/controllers/shipit/ccmenu_url_controller.rb], [File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The CCMenu integration mints an `ApiClient` token intended to expose the deploy status of a single requested stack via an unauthenticated URL, but the generated token is never bound to that stack, and the endpoint that consumes it explicitly bypasses the stack-scoping mechanism used everywhere else in the API. The result is a cross-stack authorization break: a token authorized (by the requesting user's intent, and by the URL that was generated) for stack `A` also grants unauthenticated read of deploy/lock status for every other stack in the Shipit instance.

### Finding Description
`Shipit::CCMenuUrlController#fetch` builds a "CCMenu URL" containing an authentication token for one specific stack: [1](#0-0) 

The `client` method that produces this token does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — it never sets `stack_id`. Because `ApiClient#stack_id` is left blank, the standard scoping helper in `Api::BaseController` (`stacks` → `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) treats this client as globally scoped: [2](#0-1) 

Independently, `Api::CCMenuController` doesn't even use that scoped helper — it overrides `stack` to resolve directly against `Stack.from_param!(params[:stack_id])`, completely bypassing any `stack_id` scoping the token might carry: [3](#0-2) 

So the binding that should hold — "the stack a CCMenu token authorises == the stack it can be used to read" — is broken on both sides: the token is minted unscoped, and the consuming controller ignores scoping entirely.

Additionally, because `find_or_create_by!` keys only on `(creator, name: 'CCMenu Client')` and not on the requested stack, every CCMenu link a given user ever generates — for any stack — resolves to the exact same underlying `ApiClient` record and its one reusable `authentication_token`.

### Impact Explanation
CCMenu/CCTray links are designed to be consumed by third-party CI dashboard software without any further login (`token` is passed as a query string, `authenticate_api_client` in `Api::CCMenuController#authenticate_api_client` accepts `params[:token]` directly). This makes such links commonly pasted into wikis, status dashboards, chat channels, or embedded in build-status widgets, i.e., treated as low-sensitivity, single-purpose credentials. Because the minted token is unscoped and the controller ignores stack scoping, possession of a single CCMenu URL (generated for one, possibly low-sensitivity, stack) grants an unprivileged holder unauthenticated read access to the deploy status, lock status, and last-build metadata of every stack managed by the Shipit instance — not just the one for which the link was created. This matches the "unauthenticated read of stack state" High-impact category.

### Likelihood Explanation
No privileged Shipit session, API client secret, or GitHub credential is required to exploit this once a CCMenu URL is obtained — obtaining such a URL only requires it to be shared/leaked in the ordinary, expected use of the CCMenu feature (embedding in dashboards, wikis, browser history, referrer headers, etc.), which is the feature's intended low-friction, no-login use case. The bug is deterministic (not timing-dependent) and requires no race condition or special configuration.

### Recommendation
- When minting the CCMenu `ApiClient`, set `stack_id` to the requested stack and key `find_or_create_by!` on `(creator, stack, name: 'CCMenu Client')` so a distinct, stack-scoped token is issued per stack.
- Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-aware `stacks.from_param!(params[:stack_id])` from `Api::BaseController` so a stack-scoped token cannot be used to query other stacks.

### Proof of Concept
1. User Alice (has access to `stack-low-sensitivity`) visits the CCMenu link generator for that stack; `CCMenuUrlController#fetch` returns `.../api/<owner>/<stack-low-sensitivity>/ccmenu.xml?token=T`.
2. Token `T` corresponds to an `ApiClient` with `permissions: ["read:stack"]` and `stack_id: nil` (created via `find_or_create_by!(creator: Alice, name: 'CCMenu Client')`).
3. Alice shares/embeds this URL in a public or semi-public dashboard (the standard CCMenu use case, since it requires no login).
4. Anyone in possession of `T` requests `.../api/<other-owner>/<stack-highly-sensitive>/ccmenu.xml?token=T`.
5. `Api::CCMenuController#authenticate_api_client` accepts `T` via `ApiClient.authenticate(params[:token])`, and `stack` resolves `Stack.from_param!(params[:stack_id])` for the *other* stack without any scope check, returning its full deploy/lock status — a stack `T` was never intended to authorize access to.
