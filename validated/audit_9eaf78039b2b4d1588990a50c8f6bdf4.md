### Title
Caller-supplied route executes arbitrary contracts under the caller's own authorization, letting a malicious hop drain the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's strategy verbs (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) accept a `swap: Bytes` route from the caller and forward it to the swap aggregator. The router keeps no venue allowlist, so the route can name any contract as a hop "pool." That contract runs on the call stack *below the caller's own `require_auth` subtree*, so it can invoke `token.transfer(caller -> attacker, ...)` on any token the caller holds. The theft transfer is recorded as a child of the caller's `swap_collateral` authorization entry and executes if the caller signs that tree — the exact analog of IPython executing attacker-planted files with the victim's privileges.

### Finding Description
`process_swap_collateral` authorizes the caller as owner or delegate and then calls `withdraw_and_swap_from_supply`, which reaches `swap_tokens` [1](#0-0) . `swap_tokens` grants the router exactly one self-authorized input transfer and invokes `router.execute_strategy(&controller, &amount_in, swap)` with caller-controlled payload bytes [2](#0-1) . The controller's post-swap guards only check measured input/output deltas (`RouterOverspend`, `NoSwapOutput`) and final account risk; nothing bounds what the routed contracts do with the ambient caller authorization [3](#0-2) .

The threat model itself documents the hole: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." [4](#0-3) 

The in-repo adversarial test proves it end-to-end: a `RogueHopPool` registered inside an `UnlistedPoolRouter` performs `transfer(alice -> attacker, WALLET_BALANCE)` during `swap_collateral`, and the recorded authorization tree shows the stolen transfer nested directly under Alice's `swap_collateral` entry — Alice ends with a wallet balance of 0 while the swap itself produces a fair output [5](#0-4) [6](#0-5) .

### Impact Explanation
Theft of user funds: any token balance in the victim's wallet (not just the routed amount) can be moved to the attacker inside a single `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral` call, because the malicious hop contract executes with the caller's signed authorization. The victim's account can still pass every risk check and the swap can still produce a "fair" output, so nothing on-chain flags the theft.

### Likelihood Explanation
Routes are opaque XDR bytes built off-chain and passed verbatim as the `swap` argument; a malicious quote provider, compromised frontend, or phishing dapp can embed a rogue hop contract. The only defense is the caller/wallet decoding the packed payload and refusing authorization trees with unexpected children — the docs explicitly push this to the client. A single unprivileged attacker only needs to register a contract and serve a poisoned route.

### Recommendation
Do not run arbitrary caller-supplied route contracts under the caller's `require_auth` tree. Options: have the router authenticate the swap with `execute_strategy`'s `sender` = controller only (never expose the end caller's auth subtree to venue code by splitting the strategy into a caller-auth step and a router step), or enforce a venue/token allowlist in the controller or router so route-named contracts are restricted to known DEX pools that cannot initiate third-party token transfers. At minimum, document loudly and add a simulation-side check; today the only mitigation is client-side route decoding.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Alice has 10,000 USDC supplied and holds `WALLET_BALANCE` of an unrelated token.
2. Attacker registers `RogueHopPool` whose hop executes `token.transfer(alice -> attacker, WALLET_BALANCE)`, and a router that routes through it without an allowlist.
3. Alice calls `swap_collateral(alice, account_id, USDC, SWAP_IN_USDC, ETH, poisoned_route)`; the swap returns a fair ETH output and Alice's account remains healthy.
4. The recorded auth tree contains the stolen `transfer` as a sub-invocation of Alice's `swap_collateral` authorization; once signed, `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` [6](#0-5) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
