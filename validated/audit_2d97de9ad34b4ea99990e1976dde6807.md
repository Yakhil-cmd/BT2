### Title
Frontrunning a supplier's withdrawal with a borrow that lands utilization exactly on `max_utilization` freezes all exits - ([File: contracts/pool/src/guards.rs](contracts/pool/src/guards.rs))

### Summary
The pool applies `require_utilization_below_max` to non-liquidation withdrawals, and the check is a post-state test: burning supply shares raises utilization, so once utilization reaches the market's `max_utilization` cap, every withdrawal reverts with `UtilizationAboveMax`. An unprivileged attacker can frontrun a large supplier's `withdraw` with a `borrow` sized to land utilization exactly on the cap — borrows at the cap are admissible — and keep it there, blocking the victim's exit for as long as the borrow remains open.

### Finding Description
In `contracts/pool/src/ops/withdraw.rs`, `gate_and_debit` runs `guards::require_utilization_below_max` for non-liquidation withdrawals after the supply burn has already been applied to the cache (`burn_position` → `cache.burn_supply`). [1](#0-0) 

The guard admits utilization `<= max_utilization` (rounded up), inclusive: [2](#0-1) 

Because the bound is inclusive, a `borrow` that lands utilization *exactly* on `max_utilization` succeeds — the test `withdraw_that_lands_exactly_on_max_utilization_passes_and_one_unit_more_fails` pins this boundary explicitly: a borrow/withdraw resulting in utilization == cap passes, one raw unit more reverts. [3](#0-2) 

Once utilization sits at the cap, any withdrawal strictly raises `borrowed/supplied` (the denominator shrinks while the numerator is unchanged or grows via accrual), so every supplier withdrawal — even 1 unit — reverts. The repository's own documentation confirms the mechanics: "burning supply shares raises utilization, so once utilization reaches the cap no withdrawal of any size passes." [4](#0-3) 

Attack path (single unprivileged address):
1. Victim (large supplier) submits controller `withdraw` for their position.
2. Attacker observes it and submits controller `supply` (collateral asset) + `borrow` on the victim's asset, sized so post-state utilization equals `max_utilization`. Both are unprivileged entrypoints; `borrow` is reachable by any address with sufficient collateral and a healthy HF.
3. Victim's `withdraw` reverts with `UtilizationAboveMax` (127), as does any retry of any size while utilization stays at the cap.
4. Attacker can keep the borrow open (paying only borrow interest on collateral they still control), or repeatedly re-land utilization on the cap after any repay/release, griefing the victim's exit indefinitely.

Liquidations bypass the guard (`is_liquidation` skips it), and `require_liquidation_buffer` doesn't help the victim — it constrains the attacker's borrow depth, not the cap-lock.

### Impact Explanation
Temporary freezing of user funds: a targeted supplier (or all suppliers of that market) cannot withdraw any amount while the attacker holds utilization at the cap. The freeze persists for the duration of the attacker's borrow — potentially unbounded, since only accrual-driven utilization drift or a repayment unlocks exit, and the attacker can top up collateral to stay healthy. This matches the report's bug class: frontrunning exit via `borrow`.

### Likelihood Explanation
Medium. The attacker needs real collateral sufficient for a borrow large enough to reach `max_utilization`, and pays borrow interest for the duration — so this is a griefing/grief-or-extortion vector rather than profitable theft. However, it requires no privilege, no oracle manipulation, and no timing exoticism beyond frontrunning a public mempool transaction, and the lock is total (no partial withdrawal escapes). Motivations include delaying a competitor's exit, or holding a large supplier hostage during price volatility.

### Recommendation
- Make the utilization check on withdrawals *pre-state* relative to the caller's own position rather than a post-state market bound — i.e., allow a withdrawal if pre-withdrawal utilization was already at/above the cap (don't punish exiters for a state they didn't create).
- Alternatively, exempt withdrawals that reduce the caller's position without reducing utilization below a pre-existing at-cap state, or introduce a strictly-less-than bound for borrows (`< max_utilization`) while keeping `<=` for withdrawals, so a borrow can never itself seal the exit window.
- Short of a code change, document that suppliers must batch-withdraw before utilization approaches the cap, or use smaller positions to keep per-tx withdraw granularity below the cap gap.

### Proof of Concept
Pinned by existing tests:

- `tests/test-harness/tests/controller/max_utilization.rs:162-184` — a withdrawal landing utilization exactly on `max_utilization` (80%) succeeds; one unit more reverts. Symmetrically, a borrow landing exactly on the cap succeeds (the same inclusive bound governs `borrow`).
- `contracts/pool/tests/flows.rs:2924-2948` — `test_withdraw_above_max_utilization_panics_but_within_cap_succeeds`: after utilization reaches the cap, `try_withdraw` reverts with `UtilizationAboveMax`.
- `tests/test-harness/tests/controller/max_utilization.rs:64-77` — `test_withdraw_pushing_above_max_utilization_rejected`: supplier withdraw of 200 of 1000 reverts once utilization is at the 85% cap.

Concrete scenario: market `max_utilization = 95%`, supplied = 100 ETH, borrowed = 80 ETH. Victim holds 100% of supply. Attacker supplies USDC collateral and borrows 15 ETH → utilization = 95%. Victim's `withdraw` of any amount > 0 now pushes utilization above 95% and reverts. Attacker's debt accrues interest but the position stays open; exit is frozen until the attacker repays or the position is liquidated.

pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
```

fn withdraw_that_lands_exactly_on_max_utilization_passes_and_one_unit_more_fails() {
    let mut t = LendingTest::new()
        .standard_two_asset()
        .with_market_params("USDC", |p| p.max_utilization = RAY * 80 / 100)
        .with_min_borrow_collateral_disabled()
        .build();
    t.supply(ALICE, "USDC", 100_000.0);
    t.supply(BOB, "ETH", 1_000.0);
    t.borrow(BOB, "USDC", 40_000.0);
    // Supplied 100_000, borrowed 40_000. Utilization hits 80 percent when
    // supplied falls to 50_000: ALICE may withdraw exactly 50_000.
    let unit = 10_000_000i128;
    let exact = 50_000 * unit;
    assert_contract_error(
        t.try_withdraw_raw(ALICE, "USDC", exact + 1),
        errors::UTILIZATION_ABOVE_MAX,
    );
    t.try_withdraw_raw(ALICE, "USDC", exact)
        .expect("landing exactly on the ceiling is admissible");
    assert_contract_error(
        t.try_withdraw_raw(ALICE, "USDC", 1),
        errors::UTILIZATION_ABOVE_MAX,
    );
```
