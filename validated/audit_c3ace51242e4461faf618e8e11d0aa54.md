### Title
Webhook signature verification keys on `repository.owner.login`, but handlers act on the unverified `repository.full_name` - cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multiple GitHub organizations sharing one instance, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`). The webhook signature is validated per-organization, but the organization used to select the verification secret and the repository the payload is actually applied to are read from two different, independently attacker-controlled JSON fields in the same unauthenticated body. Nothing binds them together.

### Finding Description
`WebhooksController#verify_signature` picks which org's secret to verify against using `repository_owner`, taken from the raw JSON body before signature verification: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner)` and then `verify_webhook_signature(signature, request.raw_post)` using that org's `webhook_secret`: [3](#0-2) 

Once the signature check passes, `create` hands the *entire* parsed body to the registered handlers: [4](#0-3) 

But every handler resolves the target `Stack`/`Repository` from a **different** field, `repository.full_name`, via `Handler#stacks`/`#repository_name`, or `Repository.from_github_repo_name(params.repository.full_name)`: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

The equality the design implicitly assumes but never enforces is:
`org(repository.owner.login)` (used to pick the signing secret) `==` `org(repository.full_name)` (used to pick the acted-upon repository/stack).

Nothing in `verify_signature` or in `Handler` checks that these two independently-supplied JSON fields agree. An operator who runs a multi-tenant Shipit instance for several GitHub organizations (a documented, supported configuration) lets any organization that has *its own* legitimately-configured `webhook_secret` forge a validly-signed webhook body whose `repository.full_name` names a repository belonging to a *different* organization on the same instance. The HMAC only proves the body was signed by *some* configured org's secret — it says nothing about which repository within that body is authoritative.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out as in-scope. An attacker who controls (or is simply a legitimate low-privilege member/owner of) one tenant organization on a shared Shipit instance can:
- Forge a `pull_request` "opened"/"closed"/"reopened" event naming a victim org/repo's `repository.full_name`, causing `ReviewStackAdapter.find_or_create!` or `stack.archive!`/`unarchive!` to run against the victim's stacks (`opened_handler.rb`, `closed_handler.rb`, `reopened_handler.rb`).
- Forge a `push` event with the victim's `full_name`, causing `PushHandler#process` to call `stack.sync_github(expected_head_sha: ...)` on the victim's stack, which can drive the merge/CD pipeline for a repository the attacker never has GitHub write access to.

This is a cross-repository write into a stack/repository outside the attacker's authenticated organization, without any Shipit session, `ApiClient` token, or GitHub write access to the victim repo — satisfying the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment serves more than one GitHub organization with independently configured `webhook_secret`s — a setup the engine explicitly documents and ships test fixtures for (`test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.shopify.yml`). Any org owner able to configure/know their own org's webhook secret (which they legitimately possess, since they are the one who created the GitHub App/webhook for their own org) can compute a valid HMAC and simply set `repository.full_name` in the JSON body to a victim repository's full name. No additional secrets, tokens, or privileged access to the victim org are needed.

### Recommendation
In `WebhooksController#verify_signature`, require that the organization derived from `repository.full_name` (and/or `organization.login`) matches the organization used to select the signing secret, and reject the request otherwise. Alternatively, have each `Handler` (or `Handler#stacks`) verify that the resolved `Repository`'s owner matches the already-authenticated `repository_owner` before acting, so a validly-signed payload for org A cannot be used to mutate resources scoped to org B.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
