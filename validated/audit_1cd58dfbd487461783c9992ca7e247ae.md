## Analysis: Front-running analog found in the System Program's nonce account initialization

### Title
Unauthenticated `InitializeNonceAccount` instruction allows front-running to hijack nonce authority and drain funds - ([File: programs/system/src/system_instruction.rs])

### Summary
The reported bug is a class of vulnerability where a "registration"/"ownership-assignment" instruction accepts the intended owner as caller-supplied instruction data instead of deriving it from a verified signer, and is callable by anyone as a standalone step, letting an attacker front-run the legitimate initializer. The same pattern exists in Agave's System Program `InitializeNonceAccount` instruction: the nonce `authority` is taken directly from unauthenticated instruction data, and unlike every other nonce-account instruction, no signature check is performed at all.

### Finding Description
`SystemInstruction::InitializeNonceAccount(authorized)` is dispatched in `system_processor.rs` to `initialize_nonce_account`: [1](#0-0) 

The handler itself only checks writability, uninitialized state, and rent-exemption — it never verifies that any account (not even the nonce account itself) is a transaction signer, and it blindly writes the caller-supplied `nonce_authority` into the account's `Data`: [2](#0-1) 

This is inconsistent with every other nonce-mutating instruction in the same file, which explicitly enforce a `check_signer` against either the account key or the recorded authority, e.g. `withdraw_nonce_account`: [3](#0-2) 

The intended safe flow bundles `CreateAccount` (which *does* require the new account to sign, per `test_create_unsigned`) together with `InitializeNonceAccount` atomically in a single transaction, as done by the `create_nonce_account` helper: [4](#0-3) [5](#0-4) 

However, nothing in the runtime enforces this atomicity. A user can create the nonce-sized, system-owned, zero-initialized account in one transaction and call `InitializeNonceAccount` in a later, separate transaction — exactly the CLI flow (`create_nonce_account_with_seed`/`create_nonce_account`) supports two independently submittable instructions. Because `InitializeNonceAccount` requires no signature check whatsoever, any unprivileged third party can observe the freshly created (but not-yet-initialized) nonce account on-chain and submit their own `InitializeNonceAccount(authorized=attacker)` first, becoming the recorded nonce authority before the legitimate owner's initialize transaction lands (which will then fail with `InvalidAccountData` since state is `Initialized`).

### Impact Explanation
Once the attacker becomes the recorded `authority` of the victim's nonce account, they can immediately call `WithdrawNonceAccount` to drain the full rent-exempt balance funded by the victim, since `withdraw_nonce_account` only checks that the signer matches `data.authority` — which now is the attacker: [6](#0-5) 

This produces concrete unsigned/unauthorized fund movement: lamports the victim deposited to create their nonce account can be stolen by a completely unprivileged third party with a single transaction, with no need to compromise any private key belonging to the victim.

### Likelihood Explanation
Exploitation requires only observing public on-chain state (an uninitialized, system-owned account sized for `nonce::state::State`) between the victim's `CreateAccount` transaction and their subsequent `InitializeNonceAccount` transaction, and winning the race to submit `InitializeNonceAccount` first — a standard mempool front-running scenario requiring no special privileges, and directly enabled by the missing signer check in `initialize_nonce_account`.

### Recommendation
Add a signer check in `initialize_nonce_account` analogous to `withdraw_nonce_account`/`authorize_nonce_account`, e.g. requiring the nonce account itself (or the designated `nonce_authority`) to be a signer of the transaction before allowing state to transition from `Uninitialized` to `Initialized`. This closes the front-running window regardless of whether `CreateAccount` and `InitializeNonceAccount` are submitted atomically.

### Proof of Concept
1. Alice submits `SystemInstruction::CreateAccount` creating `nonce_pubkey` (signed by Alice's `nonce_pubkey` keypair), with `space = nonce::state::State::size()` and `owner = system_program`. Account data is zero-initialized ⇒ `State::Uninitialized`.
2. Before Alice's follow-up `InitializeNonceAccount(authorized = Alice)` transaction lands, Bob observes the account on-chain and submits `SystemInstruction::InitializeNonceAccount(authorized = Bob)` with `nonce_pubkey` as a writable, non-signer instruction account — only Bob's own fee-payer key signs the transaction.
3. `initialize_nonce_account` (system_instruction.rs L163-211) sees `State::Uninitialized`, sufficient rent, and unconditionally sets `Data{ authority: Bob, ... }` — no signer check is performed.
4. Alice's later `InitializeNonceAccount(authorized = Alice)` now fails with `InstructionError::InvalidAccountData` because the state is already `Initialized`.
5. Bob submits `SystemInstruction::WithdrawNonceAccount(lamports = all)` with himself as signer; `withdraw_nonce_account`'s `check_signer(&data.authority)` succeeds because `data.authority == Bob`. All lamports Alice funded into the account are transferred to Bob's chosen destination — concrete unauthorized fund theft achieved from a single unprivileged transaction.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
