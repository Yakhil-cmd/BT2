### Title
ServiceChain Bridge ERC20 Transfer Incompatible with Fee-on-Transfer Tokens, Causing Recipient Fund Loss and Deposit Revert — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

The Kaia ServiceChain bridge's ERC20 transfer functions (`requestERC20Transfer`, `onERC20Received`, `handleERC20Transfer`) do not account for fee-on-transfer (FOT) tokens. The bridge assumes the amount pulled from the sender equals the amount it holds, and that the amount it sends equals the amount the recipient receives. Both assumptions break for FOT tokens, producing three distinct broken-invariant outcomes: a revert that blocks all deposits, double-charging of the bridge fee, and a permanent shortfall in the recipient's balance on the destination chain.

---

### Finding Description

**Path 1 — `requestERC20Transfer` (2-step deposit, source bridge)** [1](#0-0) 

The bridge pulls `_value + _feeLimit` from the caller via `safeTransferFrom`. For a FOT token with rate `r`, the bridge actually receives `(_value + _feeLimit) × (1 − r)`. Immediately after, `_payERC20FeeAndRefundChange` is called: [2](#0-1) 

This function attempts to push `feeOfERC20[_token]` to `feeReceiver` (line 74) and `_feeLimit − fee` back to the caller (line 78). Both outbound transfers also incur the FOT deduction. Three concrete failures result:

1. **Revert / DoS**: If `(_value + _feeLimit) × (1 − r) < feeOfERC20[_token]`, the bridge's balance is insufficient for the fee transfer and the entire transaction reverts. Any user depositing a registered FOT token with a non-zero bridge fee is permanently blocked.
2. **Double-charging**: Even when the balance is sufficient, the refund transfer on line 78 deducts another FOT fee from the caller's refund, so the caller loses `feeRefund × r` extra tokens.
3. **Inflated `RequestValueTransfer` event**: The event emits the caller-supplied `_value` (line 97–106), not the amount the bridge actually locked after FOT deductions. The counterpart bridge will attempt to release the full `_value` to the recipient. [3](#0-2) 

**Path 2 — `handleERC20Transfer` (destination bridge, non-mintBurn mode)** [4](#0-3) 

The destination bridge calls `safeTransfer(_to, _value)`. For a FOT token, `_to` receives `_value × (1 − r)` while the bridge's balance is debited by the full `_value`. The `HandleValueTransfer` event records `_value` as the settled amount, but the recipient is permanently short by `_value × r`. Over many transfers the destination bridge's reserve is drained at the correct rate while recipients collectively receive less than was bridged, constituting an unrecoverable loss of bridged assets.

**Path 3 — `onERC20Received` (1-step deposit)** [5](#0-4) 

The 1-step path calls `_requestERC20Transfer` with the caller-supplied `_value` and `_feeLimit` after the token contract has already transferred `_amount + _feeLimit` to the bridge (with FOT deducted). The same inflated-event and fee-payment failures from Path 1 apply here.

---

### Impact Explanation

- **Unauthorized asset loss**: Recipients on the destination chain receive fewer tokens than the bridge event records. The shortfall (`_value × r` per transfer) is unrecoverable and accumulates with every cross-chain transfer of a FOT token.
- **Revert / bridge DoS**: Any deposit of a FOT token where `feeOfERC20[token] > 0` will revert when the bridge's actual balance falls below the configured fee, blocking all users of that token pair.
- **Double bridge-fee charge**: The refund path in `_payERC20FeeAndRefundChange` transfers tokens back to the caller through the FOT hook, silently extracting an extra `feeRefund × r` from the caller beyond the declared bridge fee.

---

### Likelihood Explanation

The ServiceChain bridge explicitly supports arbitrary ERC20 tokens registered by operators. FOT tokens (e.g., tokens with a deflationary burn on transfer, or tokens with a protocol fee) are a well-known token class. Any operator who registers such a token, or any user who bridges one, triggers the vulnerability without any privileged action beyond normal bridge usage. The trigger is a standard `requestERC20Transfer` or `requestValueTransfer` call from an unprivileged user.

---

### Recommendation

1. **Measure actual received amount** in `requestERC20Transfer` using a balance-before / balance-after pattern:
   ```solidity
   uint256 before = IERC20(_tokenAddress).balanceOf(address(this));
   IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
   uint256 received = IERC20(_tokenAddress).balanceOf(address(this)).sub(before);
   // Use `received` instead of `_value.add(_feeLimit)` for all subsequent accounting
   ```
2. **Emit the actual locked value** in `RequestValueTransfer`, not the caller-supplied `_value`.
3. **Measure actual received amount** in `handleERC20Transfer` (non-mintBurn) using the same pattern, and emit the actual transferred amount in `HandleValueTransfer`.
4. **Document** that FOT tokens are not supported if the above changes are not made, and add a token-registration guard that rejects known FOT tokens.

---

### Proof of Concept

**Setup**: Deploy a FOT ERC20 token that deducts 10% on every transfer. Register it on both source and destination bridges. Set `feeOfERC20[token] = 100` (bridge fee). User calls `requestERC20Transfer` with `_value = 1000`, `_feeLimit = 200`.

**Source bridge execution**:
1. `safeTransferFrom(user, bridge, 1200)` → bridge receives `1200 × 0.9 = 1080` (FOT deducts 120).
2. `_payERC20FeeAndRefundChange`: tries `safeTransfer(feeReceiver, 100)` → feeReceiver gets `90`, bridge balance = `980`.
3. Refund: `safeTransfer(user, 100)` → user gets `90`, bridge balance = `880`.
4. `RequestValueTransfer` emits `valueOrTokenId = 1000` — but bridge only holds `880`.

**Destination bridge execution**:
5. Operators call `handleERC20Transfer(..., _value=1000, ...)`.
6. `safeTransfer(recipient, 1000)` → recipient receives `900` (FOT deducts 100).
7. `HandleValueTransfer` emits `valueOrTokenId = 1000`.

**Result**: User sent 1000 tokens worth of value; recipient received 900. The 100-token shortfall is permanently lost. Additionally, the user was charged an extra 10 tokens (FOT on refund) beyond the declared bridge fee. [6](#0-5) [7](#0-6) [2](#0-1)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
