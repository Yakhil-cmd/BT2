### Title
API clients can impersonate arbitrary Shipit users via the `X-Shipit-User` header, forging deploy/task/lock/merge authorship - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
`Shipit::Api::BaseController` authenticates the caller as an `ApiClient` (a bearer token scoped only by `permissions` and optionally a `stack_id`), but then separately derives `current_user` — the identity that is recorded as the *author* of privileged actions — purely from an attacker-controlled request header, with no verification that this identity is actually bound to the authenticated `ApiClient`.

### Finding Description
`authenticate_api_client` verifies only the `ApiClient` bearer token via HTTP Basic Auth: [1](#0-0) 

Separately, `current_user` / `identify_user` looks up an arbitrary `Shipit::User` record by trusting the `X-Shipit-User` request header, with no cross-check against the authenticated `ApiClient`'s `creator`: [2](#0-1) 

`ApiClient` records are created independently of any specific user identity binding at request time — the model only enforces `creator`/permission fields at creation, not at request-time impersonation: [3](#0-2) 

This `current_user` value is then trusted as the acting principal for privileged, audited operations across the API surface:
- Deploys: `stack.trigger_deploy(commit, current_user, ...)` [4](#0-3) 
- Task triggers/aborts: `stack.trigger_task(params[:task_name], current_user, ...)` and `task.abort!(aborted_by: current_user)` [5](#0-4) 
- Stack locks: `stack.lock(params.reason, current_user)` [6](#0-5) 
- Merge requests: `MergeRequest.request_merge!(stack, params[:id], current_user)` [7](#0-6) 

This breaks the trust binding between the **GitHub-derived identity that legitimately owns/authorizes an action** and the **`User` record actually attributed to and used to gate that action**. Any holder of a valid `ApiClient` token (even one scoped to `deploy:stack`/`lock:stack` only, created for a narrow automation purpose) can set `X-Shipit-User` to the login of any other Shipit user — e.g., a team lead, an on-call engineer, or a user whose `authorized?` (team membership) status differs from the token holder's own — and have deploys, rollbacks, locks, task runs and merges recorded and attributed as performed by that impersonated identity, with no verification that the impersonated user actually initiated or approved the action.

### Impact Explanation
This produces an unauthorized action performed under a forged identity: an attacker who legitimately possesses a narrowly-scoped `ApiClient` token can cause deploys, rollbacks, task executions, and stack locks to be recorded as authored by an arbitrary other `User`, and can request merges via `MergeRequest.request_merge!` on that user's behalf. This falls under the "unauthorized deploy, rollback or merge" and "escalation into `Shipit.github_teams` authorization" impact categories, since audit trails, notifications, and any downstream logic keyed off `current_user.login`/`current_user.authorized?` (team membership) are all forgeable by header value alone.

### Likelihood Explanation
Any party in possession of a valid `ApiClient` authentication token (which is explicitly the class of credential this scan's rules permit analyzing, as the token itself is not "privileged" beyond the granted `permissions`) can trivially set an arbitrary `X-Shipit-User` header value on every write endpoint under `Shipit::Api::BaseController`. No additional secret, session, or GitHub credential is required beyond the token already needed to reach these endpoints; the impersonation step itself requires nothing further.

### Recommendation
Do not derive `current_user` from a client-supplied header. Either bind `ApiClient` records to a specific acting user server-side (e.g., always attribute actions to `current_api_client.creator`, or an explicitly and cryptographically-verified user reference stored on the `ApiClient`), or remove the `X-Shipit-User` impersonation path entirely from `Shipit::Api::BaseController#identify_user` and require a separately authenticated principal (e.g., OAuth session) for any action whose authorship matters.

### Proof of Concept
1. Obtain (or be granted) an `ApiClient` token scoped only to `deploy:stack` for a given stack, e.g. via `ApiClient.create!(creator: attacker, permissions: ['deploy:stack'], stack: target_stack)`.
2. Send: `POST /api/stacks/:id/deploys` with `Authorization: Basic <base64(token)>` and header `X-Shipit-User: victim_admin_login`.
3. `identify_user` resolves `current_user` to the `victim_admin_login` `User` record purely from the header [8](#0-7) .
4. `DeploysController#create` calls `stack.trigger_deploy(commit, current_user, ...)`, creating a deploy permanently attributed to `victim_admin_login` [9](#0-8) , even though that user never made the request.

        @current_api_client = if Shipit.disable_api_authentication
                                UnlimitedApiClient.new
                              else
                                BasicAuth.authenticate(request) do |*parts|
                                  token = parts.select(&:present?).join('--')
                                  ApiClient.authenticate(token)
                                end
                              end

        headers['WWW-Authenticate'] = 'Basic realm="Authentication token"'
