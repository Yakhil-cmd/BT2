### Title
Unauthenticated registration of shared addresses lets a paired correspondent silently subscribe to (and thus view) a user's private payment data — (File: `wallet_defined_by_addresses.js`)

### Summary
`handleNewSharedAddress()` accepts a `new_shared_address` device message from any paired correspondent and, without any local-user approval step, inserts the proposed multisig/shared-address definition into `shared_addresses` / `shared_address_signing_paths` as long as the definition's address leaves are syntactically valid and one of them happens to be an address the recipient already owns. This mirrors the Wagtail flaw where an action gated by a lower privilege ("add") silently grants a higher-privilege capability ("view") without re-checking authorization — here, being a paired device (a low-trust relationship, analogous to “add” permission) is enough to make the victim's wallet treat the attacker as a legitimate cosigner, which subsequently causes the victim's own private-payment chains to be auto-forwarded to the attacker.

### Finding Description
The intended workflow for creating a shared address requires an explicit local approval round-trip: `create_new_shared_address` → `approve_new_shared_address`, tracked in `pending_shared_addresses`/`pending_shared_address_signing_paths`, and only finalized by `approvePendingSharedAddress()` once every party has approved. [1](#0-0) 

However, `wallet.js` also dispatches a second, independent path — the `new_shared_address` message — straight into `handleNewSharedAddress()`, with no confirmation/approval gate at all: [2](#0-1) 

`handleNewSharedAddress()` only checks structural validity of the definition (hash matches, signer addresses are syntactically valid addresses, and each address-leaf in the definition has a matching signer entry) and that the recipient's own address is referenced somewhere in the definition (`determineIfIncludesMeAndRewriteDeviceAddress`). It never verifies that the local user actually agreed to form this shared address with this particular counterpart: [3](#0-2) 

`addNewSharedAddress()` then unconditionally persists the attacker-supplied definition and registers every listed device (including the attacker's own device) as a `shared_address_signing_paths` cosigner of the new shared address: [4](#0-3) 

Once this shared address exists in the DB, any future private payment whose output address resolves (directly or through nested shared addresses) to the victim's address is recognized as belonging to the victim via `readWalletsByAddresses()`, which recursively walks `shared_address_signing_paths`: [5](#0-4) 

The wallet then automatically forwards the full private-payment chain (amounts, blinding factors, addresses) to *every* device registered as a cosigner of that shared address — including the attacker's device, which the attacker itself inserted via the unauthenticated `new_shared_address` message: [6](#0-5) [7](#0-6) 

In effect, the low-privilege capability of being a paired correspondent (equivalent to Wagtail's "add" permission) is sufficient to fabricate a "shared address" naming the victim as a member, bypassing the intended mutual-approval "change/view" gate, and this silently escalates into ongoing visibility into the victim's private-asset payment history for that address — the exact CWE-280 pattern (missing check of a stronger permission before granting access) described in the advisory.

### Impact Explanation
Any paired device (which typically requires only a one-time pairing secret exchanged out of band, not a rigorous trust relationship) can force itself into being treated as a legitimate cosigner over one of the victim's addresses without any confirmation UI or explicit consent by the victim's wallet software. This is a confidentiality breach of private assets: amounts, output addresses, and blinding factors of subsequent private payments involving that address are automatically leaked to the attacker's device via `forwardPrivateChainsToOtherMembersOfAddresses`/`forwardPrivateChainsToOtherMembersOfWallets`. This satisfies the "private payment chains" impact category explicitly in scope, causing loss of the confidentiality guarantee that private/indivisible assets are supposed to provide.

### Likelihood Explanation
Exploitation only requires an existing device pairing (a routine, low-friction step in Obyte wallets) and sending a single crafted `new_shared_address` message referencing the victim's real address as one leaf of the definition, plus a bogus dummy address controlled by the attacker as another leaf. No cryptographic secret of the victim is needed, and no interactive confirmation is enforced by `handleNewSharedAddress()`, making this straightforward to trigger against any paired correspondent.

### Recommendation
`handleNewSharedAddress()` should not silently finalize a shared address purely from a direct `new_shared_address` message. Either:
- require that a shared address only be created through the existing approval flow (`pending_shared_addresses` + `approvePendingSharedAddress`) so the local device explicitly agreed to be included, or
- require explicit, non-bypassable local user confirmation before calling `addNewSharedAddress()` when the `new_shared_address` message is unsolicited (i.e., no matching prior `create_new_shared_address`/pending record initiated by the local user), and refuse to forward any private-payment chains to devices registered via such unsolicited shared addresses until confirmed.

### Proof of Concept
1. Attacker device `D2` pairs with victim device `D1` (standard low-trust pairing).
2. `D2` learns `D1`'s real payment address `A_victim` (addresses are not secret; they can be observed from any past interaction, e.g. asking `D1` to pay them once).
3. `D2` builds `arrDefinition = ["and", [["address","A_victim"], ["address","A_attacker"]]]`, computes `address = getChash160(arrDefinition)`, and sends:
   `{"address": address, "definition": arrDefinition, "signers": {"r.0": {"address": "A_victim"}, "r.1": {"address": "A_attacker", "device_address": D2}}}` as a `new_shared_address` message to `D1`.
4. `D1`'s `wallet.js` case `"new_shared_address"` dispatches directly to `handleNewSharedAddress()`, which validates structure only, recognizes `A_victim` as one of `D1`'s own addresses, and calls `addNewSharedAddress()` — persisting the shared address and registering `D2` as a cosigner in `shared_address_signing_paths`, with no confirmation shown to `D1`'s user.
5. Later, when anyone sends a private payment to the newly created shared `address`, `D1`'s wallet resolves it to its own wallet via `readWalletsByAddresses()` and calls `forwardPrivateChainsToOtherMembersOfAddresses()`, which forwards the full private payment chain (amount, blinding, addresses) to `D2` — leaking private transaction data to the attacker without `D1`'s consent.

							db.query(
								"INSERT INTO shared_addresses (shared_address, definition) VALUES (?,?)",

												"INSERT INTO shared_address_signing_paths \n\
												(shared_address, address, signing_path, member_signing_path, device_address) VALUES(?,?,?,?,?)",

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function readWalletsByAddresses(conn, arrAddresses, handleWallets){
	conn.query("SELECT DISTINCT wallet FROM my_addresses WHERE address IN(?)", [arrAddresses], function(rows){
		var arrWallets = rows.map(function(row){ return row.wallet; });
		conn.query("SELECT DISTINCT address FROM shared_address_signing_paths WHERE shared_address IN(?)", [arrAddresses], function(rows){
			if (rows.length === 0)
				return handleWallets(arrWallets);
			var arrNewAddresses = rows.map(function(row){ return row.address; });
			readWalletsByAddresses(conn, arrNewAddresses, function(arrNewWallets){
				handleWallets(_.union(arrWallets, arrNewWallets));
			});
		});
	});
}
