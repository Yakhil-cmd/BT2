### Title
Non-structural byte-pattern scanning in `verifyMessageWithSecp256k1PemPubKey` can extract the wrong public key from a PEM blob used in `is_valid_sig`/`vrf_verify` - (File: `signature.js`)

### Summary
The external report is about `zcrypt_msgtype6_send_ep11_cprb()` in the Linux kernel relying on fragile, position-unaware struct overlays to read fields out of an ASN.1-encoded CPRB payload instead of doing real ASN.1 parsing with bounds/position validation, letting a field be misread. `signature.js` contains the same bug class in JavaScript: it uses ad-hoc buffer scanning instead of a real ASN.1/DER decoder to locate the algorithm identifier and the public-key bit string inside a PEM-encoded key that is fully reachable from oscript (`is_valid_sig`, `vrf_verify`), i.e. from an AA trigger sender.

### Finding Description
`verifyMessageWithPemPubKey()` locates the secp256k1 OID by computing `algIdStart` from the outer SEQUENCE length byte and then comparing bytes at that single computed offset: [1](#0-0) 

`verifyMessageWithSecp256k1PemPubKey()` then locates the public key bit string not by validating that it is at the expected structural position (immediately after the algorithm identifier), but by scanning the *entire* DER buffer for the first occurrence of the byte pattern `03 42 00`: [2](#0-1) 

The source comment on `SECP256K1_ALG_ID` explicitly claims this is "checked at the correct structural position in the DER to avoid false matches against key material" [3](#0-2) , but the actual implementation of the bit-string lookup (`der.indexOf(...)`) does not verify structural position at all — it just finds the first matching byte sequence anywhere in the buffer, including inside key material, integer padding, or attacker-crafted filler bytes placed earlier in the DER blob. This is the same root-cause pattern as the CVE: fragile, non-validating byte-overlay/scanning logic substituting for real ASN.1 parsing with explicit tag/length/position checks at every step.

`validateAndFormatPemPubKey()` similarly hand-decodes the outer SEQUENCE/length bytes at fixed offsets (`der[1]`, `der[3]`/`der[4]`, etc.) without a generic ASN.1 length-of-length walk, and only checks the OID hex against a table — it does not itself verify that the bit string used later by `verifyMessageWithSecp256k1PemPubKey` is the one truly associated with that OID: [4](#0-3) 

Both `is_valid_sig` and `vrf_verify` in oscript evaluation feed attacker-controlled, trigger-derived strings straight into `validateAndFormatPemPubKey` → `verifyMessageWithPemPubKey` → `verifyMessageWithSecp256k1PemPubKey`: [5](#0-4) [6](#0-5) 

### Impact Explanation
If an AA's authorization logic pins a specific PEM-encoded secp256k1 public key as a constant (e.g. a hardcoded "authorized signer" key baked into the AA's oscript/definition) and relies on `is_valid_sig(message, signature, PEM_KEY)` to gate fund release, the non-structural bit-string scan means the extracted "pubkey" for verification purposes is not provably bound to the OID/structure the comment assumes. An attacker who can influence any part of a DER blob preceding the legitimate bit string (through crafted padding, wrapped encodings, or a maliciously constructed but syntactically-accepted PEM key that happens to embed an earlier `03 42 00` byte sequence) could cause the verifier to extract and check against an unintended 65-byte region, potentially one under attacker control, rather than the genuine key material. This would let a trigger/AA author's signature-based authorization check accept a signature not actually produced by the intended key holder, leading to unauthorized fund release from an AA (fund loss) if such a construction is achievable. All full nodes execute the same deterministic JS, so this is not a fork-inducing bug per se, but it is a spend-authorization bypass class of the same root cause as the CVE (structural validation missing).

### Likelihood Explanation
`is_valid_sig` and `vrf_verify` are ordinary, unrestricted oscript primitives usable by any AA author and triggerable by any unprivileged sender who can send a trigger to the AA (`formula/evaluation.js:1704-1734`, `1736-1761`). The PEM key and message/signature can be fully or partially derived from trigger data, meaning an attacker-controlled input reaches the vulnerable scanning code directly, with no special privilege required. The likelihood of the specific byte-collision needed to substitute a wrong key region is nontrivial to engineer but not implausible given DER's byte-oriented encoding and the attacker's control over surrounding bytes in a validly-shaped PEM key.

### Recommendation
Replace the manual offset math and `indexOf`-based byte scanning in `signature.js` (`validateAndFormatPemPubKey`, `verifyMessageWithPemPubKey`, `verifyMessageWithSecp256k1PemPubKey`) with a proper ASN.1/DER decoder that walks each SEQUENCE/OID/BIT STRING node explicitly, validating tag, length, and *position relative to the preceding validated field* at every step — mirroring the ASN.1-parsing rework described in the referenced kernel fix. Specifically, the bit-string extraction should only accept a `03 42 00 04` bit string that immediately follows the already-validated AlgorithmIdentifier SEQUENCE, not the first such pattern anywhere in the buffer.

### Proof of Concept
Not independently reproducible from the index alone: confirming actual key-substitution requires constructing a concrete DER byte sequence where an earlier spurious `03 42 00` occurs before the legitimate bit string while still parsing successfully through `validateAndFormatPemPubKey`'s OID/length checks, and verifying that `ecdsa.ecdsaVerify` on the substituted 65 bytes succeeds for an attacker-chosen signature. This construction should be validated in a Devin session with test execution against `test/pem_sig.test.js` and the `signature.js` functions, since the index does not provide enough certainty to hand-craft and verify the exact byte sequence here.

```javascript
function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);
```

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;
```
