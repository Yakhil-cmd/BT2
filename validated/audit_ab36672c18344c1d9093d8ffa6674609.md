## Title
Missing cosigner-authorization check in wallet `sign` message handler allows any paired device to request unauthorized signing of attacker-crafted transactions - (File: `wallet.js`)

## Summary
CVE-2021-40327 describes TF-M's Crypto service authorizing access to a secure key based solely on knowledge of the key's ID, without verifying the relationship between the caller and the key owner. The analogous flaw in `ocore` exists in the `handleMessageFromHub` handler for the `"sign"` subject: the code that is supposed to verify that the requesting device is actually a registered cosigner of the target (shared/multisig) address is explicitly commented out, so any paired correspondent device can trigger a private-key signing flow for an address purely by knowing its `address` and `signing_path`.

## Finding Description
In `wallet.js`, the `"sign"` case of `handleMessageFromHub` accepts `{address, signing_path, unsigned_unit, private_payloads}` from any paired device and, after basic structural validation, calls `findAddress(body.address, body.signing_path, {...})`. [1](#0-0) 

When the address/signing_path resolve to a **local** signing key (`ifLocal`), the handler proceeds directly to fire the `"signing_request"` event (or validate/broadcast the joint) without checking whether the device that sent the request (`from_address`) is actually one of the recognized cosigners of that address. The check that would enforce this is present in the code but deliberately disabled: [2](#0-1) 

Note the comment directly above the `ifLocal` callback:
```
// the commented check would make multilateral signing impossible
//db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
//    if (sender_rows.length !== 1)
//        return callbacks.ifError("sender is not cosigner of this address");
```

By contrast, the `ifRemote` branch (used when the address is hosted by yet another device) *does* enforce this relationship: [3](#0-2) 
```
ifRemote: function(device_address, other_device_addresses){
    if (device_address === from_address)
        return callbacks.ifError("looping signing request for address "+body.address+", path "+body.signing_path);
    if (!other_device_addresses.includes(from_address))
        return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
```

This asymmetry means: for the very common case where the target address's signing key lives on the receiving device itself, ANY correspondent (paired device) — not just an actual cosigner of that shared address — can construct a `sign` request naming a victim's address and a guessable `signing_path` (e.g. `r`, `r.0`, `r.1`) together with a fully attacker-crafted `unsigned_unit` (arbitrary outputs, arbitrary amounts). The wallet will accept it, resolve the local key via `findAddress`, and surface a `"signing_request"` event to the UI as if it originated from a legitimate cosigner requesting a multisig/multilateral signature. `findAddress` itself only verifies that the address/path maps to a key this device holds — it does not verify the caller's authorization to request that operation: [4](#0-3) 

This mirrors the CVE root cause precisely: the "key" (signing capability for an address) is reachable using only its public identifiers (address + signing_path), with no check that the caller is in the authorized relationship (cosigner) with that key's owner.

## Impact Explanation
Any paired device correspondent of a wallet can spoof a cosigning/multilateral-signing request for that wallet's addresses, presenting an attacker-controlled transaction (arbitrary outputs/amounts, potentially private payment payloads) to the user's signing UI disguised as a legitimate cosigner request. If the user approves it — a realistic expectation given multisig/multilateral-contract workflows normally originate from trusted cosigners — this leads directly to unauthorized spending from the victim's address. The disabled check is exactly the control designed to prevent this deception; without it, the "known cosigner" trust assumption that the signing UI relies on is broken for any correspondent, not just actual address cosigners.

## Likelihood Explanation
Any device that has completed device pairing with the victim (a common, low-barrier occurrence for hub/multisig users) can send this message directly; `signing_path` values follow a small predictable grammar (`r(\.\d+)*`) and are easy to guess or learn from prior legitimate shared-address setup traffic. No cryptographic secret needs to be broken — only the disabled authorization check needs to be exploited, matching the CVE's "no authorization check based solely on knowledge of ID" pattern.

## Recommendation
Re-enable (and correctly implement) the cosigner-membership check that was commented out: before emitting `signing_request` or validating/broadcasting `objUnit` in the `ifLocal` branch, verify that `from_address` is actually listed as a cosigner/device for the target `wallet`/`shared_address` (e.g., via `wallet_signing_paths` / `shared_address_signing_paths`), analogous to the check already performed in the `ifRemote` branch.

## Proof of Concept
1. Attacker device pairs with the victim's wallet device (ordinary correspondent pairing, no cosigner relationship established).
2. Attacker learns/guesses one of the victim's local addresses (`address`) that is part of a shared/multisig definition, and a plausible `signing_path` (e.g. `"r.0"`).
3. Attacker sends a `"sign"` message to the victim's device via the hub:
```json
{
  "subject": "sign",
  "body": {
    "address": "<victim_shared_address>",
    "signing_path": "r.0",
    "unsigned_unit": {
      "authors": [{"address": "<victim_shared_address>"}],
      "messages": [{"app":"payment","payload_location":"inline","payload_hash":"...",
        "payload":{"inputs":[...],"outputs":[{"address":"<attacker_address>","amount": <amount>}]}}]
    }
  }
}
```
4. `handleMessageFromHub` reaches the `"sign"` case, calls `findAddress`, resolves `ifLocal` (since the key lives on the victim's device), and — because the cosigner check is commented out — proceeds to emit `"signing_request"` for the attacker-crafted unit, presenting it to the victim as a legitimate cosigning request instead of rejecting it with "sender is not cosigner of this address".
