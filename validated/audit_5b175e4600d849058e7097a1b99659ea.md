### Title
Attacker-controlled PR label name reaches `bundle install` process env as `BUNDLE_GEMFILE` with no allowlist, enabling Ruby code execution via a repo-committed file named `true` - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the process environment with a hardcoded value of `"true"` and no key allowlist, and this merged env reaches `Command#start`/`PTY.spawn` for the `bundle install` dependency step generated in `TaskCommands#install_dependencies`. An attacker who opens a PR from their own fork on a repository with `provisioning_behavior=allow_all`, labels it `bundle_gemfile`, and commits both a `Gemfile` and a file literally named `true` containing malicious Ruby, causes `bundle install` to run with `BUNDLE_GEMFILE=true`, making Bundler evaluate the attacker's Ruby file as the Gemfile.

### Finding Description
The broken binding: `stack.env['BUNDLE_GEMFILE']` should equal only what the maintainer/operator configures via `Stack#environment_variables` or `Shipit.env`; instead it equals `"true"` whenever the attacker names a PR label `bundle_gemfile` (case-insensitive, since it is upcased), because `ReviewStack#env` merges raw label names as keys with no allowlist: [1](#0-0) 

Labels reach here via the webhook path: `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` directly from the webhook body onto `pull_request.labels` with no filtering: [2](#0-1) 

This env is merged into `TaskCommands#env`, which is used to build the `Command` for each dependency step, including `bundle install`: [3](#0-2) 

`Command#start` passes this merged env straight to `PTY.spawn` via `unbundled_env`, with no key restriction (unlike `EnvironmentVariables#permit`, which is not applied here): [4](#0-3) 

The dependency step itself (`bundle install ...`) is generated by `BundlerDiscovery#bundle_install`, gated only on `bundler?` (does a `Gemfile` file exist in the checked-out repo): [5](#0-4) 

Important correction to the question's framing: the label value is not attacker-chosen text — `ReviewStack#env` always sets the value to the fixed string `"true"`, not an arbitrary path. So `BUNDLE_GEMFILE` cannot literally be pointed at an arbitrary attacker-chosen absolute path or URL through this mechanism. However, Bundler treats `BUNDLE_GEMFILE` as a relative-or-absolute file path, and Gemfiles are evaluated as Ruby. Because the attacker also controls the checked-out repository contents (their own PR branch), they can commit a file literally named `true` in the working directory containing arbitrary Ruby. With `BUNDLE_GEMFILE=true` set, Bundler will attempt to load `./true` as the Gemfile in the step's `chdir`, executing that Ruby code during `bundle install`.

For this to trigger, `opened_handler.rb`'s `provision?` must allow the review stack to be created — true when `repository.provisioning_behavior_allow_all?` is set by the maintainer: [6](#0-5) 

None of the existing guards prevent this: `LabelCapturingHandler`'s `ExplicitParameters` schema only validates types (`String`/`Array`), not values; there is no allowlist equivalent to `EnvironmentVariables#permit` applied to `ReviewStack#env`; and `Command#start` has no environment-key filtering before `PTY.spawn`.

### Impact Explanation
An unprivileged GitHub user who can open a PR against a repository configured with review stacks + `provisioning_behavior=allow_all` can, by labeling their own PR and committing a file named `true`, achieve remote code execution on the Shipit deploy host during the `bundle install` dependency step — this is Critical (RCE on the deploy host via `Command`/`PTY.spawn`). This is scoped to the review-stack process for that repository/PR/task, so it only affects deploy-host processes acting on behalf of that repository's review stack, but since the deploy host is shared infrastructure, RCE there can affect other tenants' secrets/credentials present on that host (e.g., `GITHUB_TOKEN`).

### Likelihood Explanation
Requires: (1) the target repository has review stacks enabled with `provisioning_behavior_allow_all` (an operator/maintainer configuration choice, not attacker-controlled), and (2) the attacker's own PR/fork actually triggers the `bundle install` dependency step (a `Gemfile` must exist so `bundler?` is true) and the checked-out working directory must contain a file literally named `true`. Both are fully within the attacker's control since it's their own fork/PR content and label. No secrets, tokens, or privileged roles are needed — cost is low (open a PR, add one label, commit one file) and it is repeatable per-PR/per-review-task.

### Recommendation
Do not merge raw pull-request label names as environment variable keys in `ReviewStack#env`. Either (a) prefix all label-derived keys with a fixed, collision-safe namespace (e.g., `SHIPIT_LABEL_<NAME>`) so they can never collide with toolchain-sensitive variable names like `BUNDLE_GEMFILE`, `RUBYOPT`, `GEM_PATH`, `LD_PRELOAD`, etc., or (b) apply an explicit allowlist (similar to `EnvironmentVariables#permit`) to strip any label-derived key that collides with a reserved/denylisted set of interpreter/toolchain-loader variable names before merging into `Command` env.

### Proof of Concept
minitest plan (`test/models/shipit/review_stack_test.rb` or `test/lib/shipit/task_commands_test.rb`):
1. Set up a `review_stack` fixture with an associated `pull_request`.
2. Set `stack.pull_request.labels = ["bundle_gemfile"]` (simulating a webhook-driven `LabelCapturingHandler#capture_labels` write).
3. Assert `stack.env["BUNDLE_GEMFILE"] == "true"` — proving the fork-controllable label key reaches the stack env unfiltered.
4. Build `Shipit::TaskCommands.new(task).install_dependencies` (with a deploy spec stubbing `bundler?` true) and assert the resulting `Command#env["BUNDLE_GEMFILE"] == "true"`, proving the value reaches the process env that `Command#start` passes to `PTY.spawn` for the `bundle install` step.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
