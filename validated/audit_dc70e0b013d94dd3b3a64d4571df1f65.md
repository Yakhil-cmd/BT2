### Title
Cross-Organization Team Hijack via `MembershipHandler#find_or_create_team!` Lookup by `github_id` Alone - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler` resolves the `Team` to mutate by looking it up solely on the GitHub-assigned numeric `team.id`, without verifying that the `organization` that authenticated the webhook (via the per-organization `webhook_secret`) actually owns that team. This breaks the equality that should hold between "the organization whose GitHub App signed this webhook" and "the team record that gets its membership written."

### Finding Description
The webhook signature is authenticated per-organization: `repository_owner` is read from the JSON body (`organization.login` for membership events) and used to pick which GitHub App/`webhook_secret` verifies `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Once the signature check passes for *some* configured organization, the `membership` event is dispatched to `MembershipHandler`, which locates the `Team` to modify like this: [3](#0-2) 

`Team.find_or_create_by!(github_id: params.team.id)` matches purely on the numeric `github_id`. The `organization` assignment only happens inside the block that runs **on creation** of a new record; if a `Team` with that `github_id` already exists (belonging to a *different* organization), the existing record is returned unchanged and then mutated by `team.add_member`/`team.members.delete`: [4](#0-3) 

`Shipit.github_teams` (used to gate application-wide authorization) is populated from configured `oauth.teams` handles, resolved into `Team` records, and users are authorized purely by team membership: [5](#0-4) [6](#0-5) [7](#0-6) 

Because a Shipit instance can be configured with multiple GitHub organizations, each with its own GitHub App and `webhook_secret`: [8](#0-7) 

an attacker who administers *any* onboarded, lower-privilege organization (call it Org B) can generate a legitimately-signed `membership` webhook from GitHub for their own org, with `team.id` set to the numeric GitHub team ID of a privileged team belonging to Org A (the org actually gating access via `Shipit.github_teams`). Since GitHub team IDs are simple sequential integers exposed via the GitHub API/UI on teams the attacker may have visibility into, guessing or discovering the target ID is feasible. `MembershipHandler` finds Org A's existing `Team` row by `github_id` alone, ignoring that the webhook was authenticated as coming from Org B, and adds the attacker (or any user of their choosing) as a member of Org A's authorization-gating team.

**Equality broken**: `verified_organization (from webhook_secret used to authenticate the request) == team.organization (the org whose membership is actually mutated)`. The code enforces this only at team-creation time, not at team-lookup time, exactly mirroring the reported bug class where a "consent"/authorization artifact obtained in one context (verified for Org B) is silently applied to a different context (Org A's team) that never participated in that authentication event.

### Impact Explanation
Successful exploitation adds an attacker-controlled GitHub user to a `Team` whose handle is listed in `Shipit.github_teams`, which is the sole gate in `force_github_authentication` deciding whether a logged-in GitHub user may use the Shipit application at all. This is a direct escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes — potentially granting the attacker full access to trigger deploys, rollbacks, and merges on stacks gated behind that team, without ever needing credentials for Org A.

### Likelihood Explanation
The attacker only needs administrative control of any one of the (possibly many) organizations onboarded to the same Shipit deployment — this does not require compromising Org A's `webhook_secret`, GitHub App private key, or any Shipit session/API token, satisfying the "unprivileged attacker" bar relative to Org A. The main friction is discovering/guessing Org A's target team's numeric `github_id`, which is a small integer often obtainable via the GitHub API (`GET /orgs/{org}/teams`) if the attacker has any visibility into Org A (e.g., is an outside collaborator, or via API endpoints that leak team IDs), or is brute-forceable given the small ID space GitHub currently uses.

### Recommendation
Scope the `Team` lookup in `MembershipHandler#find_or_create_team!` by both `github_id` and `organization` (i.e., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that the authenticated webhook's organization matches `params.organization.login` before applying any membership mutation. Consider enforcing a uniqueness constraint on `(github_id, organization)` or migrating team identity to `(organization, slug)` composite keys to make cross-org collisions impossible by construction.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` (the trusted org listed in `Shipit.github_teams`, e.g. `org-a/admins` with numeric GitHub team id `4242`) and `org-b` (any organization the attacker administers, also onboarded with its own GitHub App/`webhook_secret`).
2. Attacker creates/renames a team in `org-b` and, via GitHub's real webhook delivery (validly signed with `org-b`'s `webhook_secret`), triggers a `membership` event where the JSON body contains:
   ```json
   {
     "action": "added",
     "team": { "id": 4242, "name": "...", "slug": "...", "url": "..." },
     "organization": { "login": "org-b" },
     "member": { "login": "attacker" }
   }
   ```
3. `WebhooksController#verify_signature` authenticates this request against `org-b`'s `webhook_secret` (using `repository_owner` -> `organization.login` -> `org-b`) and passes.
4. `MembershipHandler#process` calls `find_or_create_team!`, which finds the existing `Team` row for `org-a`'s `admins` team (matching `github_id: 4242`), and calls `team.add_member(User.find_or_create_by_login!("attacker"))`.
5. The attacker's Shipit `User` is now a member of `org-a/admins`; `user.authorized?` returns true via `Shipit.github_teams`, granting them full access to the Shipit instance's stacks gated by that team — without any credentials from `org-a`.
