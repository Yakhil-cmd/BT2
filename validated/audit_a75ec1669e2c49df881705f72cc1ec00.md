Based on my investigation, I found a clear analog to the reported vulnerability in the `snowbridge-pallet-system-frontend` code.

### Title
`CrosschainDistributor`-style missing slippage protection: `Pallet::swap_and_burn` passes `None` as `amount_out_min` to `Swap::swap_exact_tokens_for_tokens` - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
The `snowbridge-pallet-system-frontend` pallet's `swap_and_burn` function, reachable from the user-callable `register_token` and `add_tip` extrinsics, calls `T::Swap::swap_exact_tokens_for_tokens` with `None` explicitly passed as the `amount_out_min` parameter, disabling slippage protection on an AMM swap whose output is subsequently burned/teleported to Ethereum as a fee/tip.

### Finding Description
`Pallet::add_tip` (callable by any signed account) and `Pallet::register_token` (callable by any origin with a nested asset, per `RegisterTokenOrigin`) both call `Self::swap_fee_asset_and_burn`, which calls `Self::swap_and_burn` when the supplied fee/tip asset differs from the `EthereumLocation` asset: [1](#0-0) 

Inside `swap_and_burn`, the call to `T::Swap::swap_exact_tokens_for_tokens` explicitly passes `None` for `amount_out_min` with the comment `// No minimum amount required`: [2](#0-1) 

`T::Swap` is configured as `pallet_asset_conversion::Swap`, whose `swap_exact_tokens_for_tokens` treats `None` as "accept any output amount" - the swap will succeed regardless of price, with no floor: [3](#0-2) [4](#0-3) 

The full `fee_amount` supplied by the caller is unconditionally withdrawn/consumed by the swap, and whatever (possibly near-zero) `ether_gained` results is what gets burned via `burn_for_teleport` and reported onward as the `amount` field in the `RegisterToken`/`AddTip` calls dispatched to BridgeHub: [5](#0-4) 

This mirrors the report's root cause exactly: an unconditional, unchecked ("zero"/absent) slippage bound is passed into an AMM-mediated cross-domain fee-conversion step, whose result is relayed onward and consumed in a subsequent (cross-chain) settlement path, with no ability for the caller to bound the acceptable output.

### Impact Explanation
Because `amount_out_min` is hardcoded to `None`, the pool's spot price at execution time entirely determines how much ether is burned for the user's tip/registration fee. A thinly-liquidated or manipulated pool for the `(tip_asset, ether)` pair can cause the full input fee/tip amount to be consumed for an arbitrarily small ether output, since there's no minimum output enforced by the caller. The withdrawn `fee_amount`/`tip_amount` is always fully spent, but the resulting `ether_gained` used for the on-chain teleport/reward has no floor, so users can be economically shortchanged (in the case of `add_tip`, honest relayer rewards) with no protection and no way for the extrinsic caller to specify their own acceptable minimum.

### Likelihood Explanation
This is reachable through a real user entry point without any privileged prerequisites — any signed account can call `add_tip`, and `register_token` is open to any origin as long as the `asset_id` is nested in the calling origin. The vulnerable code path (`swap_and_burn`) executes on every fee/tip conversion where the fee asset differs from the configured Ethereum asset location, which is the common case.

### Recommendation
Do not hardcode `None` for `amount_out_min`. Either compute an acceptable minimum via `QuotePrice`/`quote_price_exact_tokens_for_tokens` with a configurable tolerance, or expose an `amount_out_min`/slippage parameter on `register_token`/`add_tip` so callers can bound acceptable swap output, consistent with how `pallet_asset_conversion::swap_exact_tokens_for_tokens` and `SingleAssetExchangeAdapter` correctly thread through `Some(want_amount)`/`Some(amount_out_min)` elsewhere in the codebase.

### Proof of Concept
No executable PoC was run against a live network. The finding is based on static code reachability analysis: `Pallet::add_tip` (signed-callable) → `swap_fee_asset_and_burn` → `swap_and_burn` → `T::Swap::swap_exact_tokens_for_tokens(..., None, ...)`, confirmed against `pallet_asset_conversion`'s `Swap`/`SwapCredit` trait definitions and `do_swap_exact_tokens_for_tokens` implementation, which treat `None` as "no minimum enforced" (guard at lines 988-991 of `substrate/frame/asset-conversion/src/lib.rs` only validates `amount_out_min` when `Some` is supplied). No test harness in `bridges/snowbridge/pallets/system-frontend/src/tests.rs` was located exercising a minimum-output/slippage-bound path for `add_tip`/`register_token`, consistent with the absence of any such protection in production code.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
