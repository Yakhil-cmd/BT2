### Title
Attacker-controlled DER ECDSA signature bytes are fed to native `secp256k1` signature-parsing routine without pre-validation, reachable from `is_valid_sig()` in oscript - ([File: signature.js])

### Summary
The oscript function `is_valid_sig(message, pem_key, sig)` allows any unit poster, AA trigger sender, or private-payment/AA author to supply an arbitrary hex/base64 string (up to 1024 characters) as `sig`. When the PEM key resolves to a secp256k1 curve, this raw, attacker-chosen byte blob is passed directly into the native `secp256k1` module's `signatureImport()` DER parser with no prior structural (ASN.1/DER) validation, mirroring the CVE-2024-33454 bug class: a "crafted script" driving unvalidated attacker input into a native buffer-parsing routine.

### Finding Description
`is_valid_sig` is evaluated in `formula/evaluation.js` and only performs shallow checks on the signature string before handing it to signature verification: [1](#0-0) 

The only guards are that the string is non-empty, `<=1024` chars, and passes `isValidHexadecimal`/`isValidBase64` (encoding checks only — no length or structural validation of the decoded bytes). It is then forwarded to `signature.verifyMessageWithPemPubKey`, which for secp256k1 PEM keys dispatches to `verifyMessageWithSecp256k1PemPubKey`: [2](#0-1) 

Inside `verifyMessageWithSecp256k1PemPubKey`, the raw signature bytes are decoded and — if not exactly 64 bytes (the compact-signature length) — passed unvalidated straight into the native `secp256k1` library's `signatureImport()` DER parser: [3](#0-2) 

```
var sigBytes = Buffer.from(signature, encoding);
var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
```

There is no check that `sigBytes` is a well-formed DER SEQUENCE containing two INTEGER components before it is handed to the native binding's ASN.1 parser. Any string the attacker likes (up to ~512 raw bytes after decoding) reaches this native parsing code path. This is structurally identical to the reported CVE class: a remote, low-privilege actor supplies a "crafted" data blob that is consumed by a native/binary buffer-parsing routine (there, the Bluetooth GATT/L2CAP stack; here, the `secp256k1` DER signature importer) without the calling code first validating the blob's internal structure/lengths.

`is_valid_sig` is directly reachable by:
- Any AA author who includes `is_valid_sig(...)` in their AA formula.
- Any unprivileged party who can trigger that AA by sending a payment/data trigger, supplying the `sig` (and optionally `pem_key`/`message`) values via `trigger.data`.

This makes the unvalidated bytes fully attacker-controlled at evaluation time, with no privileged/network/hub role required — satisfying the "unprivileged trigger sender" reachability requirement.

### Impact Explanation
If the underlying native `secp256k1` binding used in this deployment has (or later reintroduces) a buffer-handling bug in its DER signature-import path when fed malformed/adversarial byte sequences (a well-documented historical bug class in ECDSA DER parsers, including libsecp256k1's lax DER parsing routines), the impact could range from a crash of the node process evaluating the AA (denial of service against nodes evaluating that AA, i.e., "network unable to confirm new units" involving that AA) to memory corruption in the native module process, which is a High/Critical-class impact if achievable. Even absent a specific present-day bug in the pinned `secp256k1` version, this code path is the exact place where such a class of vulnerability would manifest, and it directly parallels the reported CVE's root cause (unvalidated crafted data reaching native buffer parsing).

### Likelihood Explanation
Likelihood is Medium: exploitation requires (a) an AA definition that calls `is_valid_sig` with attacker-influenced `sig`/`pem_key` arguments (common pattern for external signature verification in AAs), and (b) an exploitable bug in the specific native `secp256k1` binding version installed. The application-level reachability is trivial and always present in any AA using this construct; the exact severity is contingent on the state of the underlying native dependency, which is outside static review here.

### Recommendation
- Validate the decoded `sigBytes` structure (minimum/maximum length, leading `0x30` SEQUENCE tag, and length-field consistency) before calling `ecdsa.signatureImport()`, rejecting malformed DER blobs early in pure JS.
- Wrap the `signatureImport`/`ecdsaVerify` calls in a try/catch that treats any native exception as verification failure (already partially done at the outer function level, but ensure it also covers native crashes/segfaults, which try/catch cannot mitigate — hence structural pre-validation is the primary fix).
- Pin and audit the `secp256k1` dependency version for known DER-parsing CVEs, and consider fuzzing `signature.verifyMessageWithSecp256k1PemPubKey` with malformed inputs.
- Apply the same DER pre-validation to `signatureNormalize` usage and to any other oscript/AA-reachable entry points that pass externally supplied byte strings into native crypto bindings (e.g., `vrf_verify`).

### Proof of Concept
1. Deploy an AA whose formula includes: `is_valid_sig(trigger.data.message, trigger.data.pem_key, trigger.data.sig)`.
2. Send a trigger unit to the AA with `data.pem_key` set to a valid secp256k1 PEM public key (or any that satisfies `validateAndFormatPemPubKey`'s post-curves-fix constraint), `data.message` any non-empty string, and `data.sig` set to a crafted hex/base64 string (≤1024 chars) that is *not* a well-formed DER signature but decodes to a byte sequence engineered to abuse edge cases in the native `secp256k1` DER length-field handling (e.g., declared inner length fields exceeding the actual buffer size).
3. Observe evaluation of `is_valid_sig` in `formula/evaluation.js` (lines 1704–1730) invoking `signature.verifyMessageWithSecp256k1PemPubKey` (`signature.js` lines 50–70), which calls `ecdsa.signatureImport(sigBytes)` on the crafted bytes without prior structural validation — confirming the unvalidated data flow into native parsing code identified above.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}
