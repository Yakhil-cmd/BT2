### Title
Silent payout failure on `claim_child_bounty` permanently strands beneficiary/curator funds in the child-bounty sub-account - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`pallet-child-bounties::claim_child_bounty` pays the curator fee and beneficiary payout via `T::Currency::transfer(..., AllowDeath)` and only checks the result with `debug_assert!`, which compiles to a no-op in release builds. Regardless of whether the transfer succeeds, the function unconditionally deletes the `ChildBounties` storage entry (`*maybe_child_bounty = None`) and the description entry. If either `Currency::transfer` call fails (e.g. destination cannot be created because the payout is below the Existential Deposit and the beneficiary account does not yet exist, per `TokenError::BelowMinimum`/`Error::ExistentialDeposit`), the funds remain in the `child_bounty_account_id` sub-account with no on-chain record left to reclaim them, and the event `Claimed` is still emitted as if the payout succeeded.

### Finding Description
The relevant code: [1](#0-0) 

Key points:
- `payout = balance - curator_fee` is computed from the sub-account's actual balance, so it can be an arbitrary small amount, including below the runtime's `ExistentialDeposit`.
- `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` is the classic (non-`fungible::Mutate`) `Currency` trait. If `beneficiary` does not already exist as an account and `payout < ExistentialDeposit`, the transfer fails with `Error::<T,I>::ExistentialDeposit` (see the deposit-side check pattern in `substrate/frame/balances/src/impl_currency.rs:486-509` and the dispatchable test confirming this failure mode: `substrate/frame/balances/src/tests/dispatchable_tests.rs:31-45`, `TokenError::BelowMinimum`).
- The error is discarded: `let payout_transfer_result = T::Currency::transfer(...); debug_assert!(payout_transfer_result.is_ok());`. `debug_assert!` is stripped out in `--release` builds (which is how production runtimes are compiled), so a failed transfer causes **no dispatch error** and the extrinsic returns `Ok(())`.
- Immediately after, the code unconditionally removes the `ChildBounties` entry and description, and decrements `ParentChildBounties`. There is no other dispatchable in `pallet-child-bounties` that can re-target a payout to the now-orphaned sub-account; the parent bounty's own accounting (`ParentChildBounties`) has already been decremented, so the child-bounty is considered fully resolved from the pallet's perspective.
- This mirrors the reported bug's structure precisely: a "receiver" address is fixed at award time (`beneficiary` set in `award_child_bounty`), and if the payout to that receiver cannot land (analogous to a blacklisted/incompatible receiver in the original report), there is no path back to reclaim the value — it is permanently orphaned in the child-bounty sub-account, and the on-chain record needed to even identify the stuck funds is deleted.

The reachable entry point is the plain signed extrinsic `claim_child_bounty`, callable by anyone once the child bounty is `PendingPayout` and the unlock delay has elapsed — no privileged role is required.

### Impact Explanation
Funds allocated to a child bounty (backed by the parent Treasury/Bounties funding) become permanently unrecoverable: the sub-account balance is orphaned, the storage record that references it is deleted, and there is no governance or root-level recovery call in `pallet-child-bounties` for this specific case. This is a fund-freezing / loss-of-funds defect, though it requires a specific precondition (payout amount below ED, destination account non-existent) rather than being trivially triggerable on every claim, and it is a silent failure only in release builds (a debug build would panic during the `try_state`/test harness, which is likely why this has not been caught by existing tests).

### Likelihood Explanation
Moderate-to-low likelihood in practice: it requires (a) a child bounty whose final payout amount, after subtracting the curator fee, is smaller than the chain's `ExistentialDeposit`, and (b) the beneficiary account not pre-existing on chain. Both conditions are plausible for small child bounties awarded to fresh accounts, and nothing in `award_child_bounty` or `claim_child_bounty` validates that the payout will clear the ED for a non-existent destination before deleting the record.

### Recommendation
Propagate the `DispatchResult` of both `Currency::transfer` calls instead of using `debug_assert!`, and abort the mutation (do not delete the `ChildBounties` entry) if either transfer fails, so the claim can be retried (e.g. after the beneficiary account is funded/created) or handled via a dedicated recovery path.

### Proof of Concept
Not executed against a live network. No test run was performed; this is a static-analysis-derived reproduction plan for a background engineer, not a completed PoC:
1. In a `pallet-child-bounties` mock runtime, set `ExistentialDeposit` > 0.
2. Create parent bounty, add and accept a child bounty with a small `fee` such that `child_bounty_account balance - fee < ExistentialDeposit`.
3. Set `beneficiary` to a fresh `AccountId` with zero balance and no existing entry in `System::Account`.
4. Call `award_child_bounty`, advance blocks past `unlock_at`, then call `claim_child_bounty` from any signed origin, built with `--release` (or with `debug_assertions` disabled) so `debug_assert!` is compiled out.
5. Expected (buggy) result: `Ok(())` returned, `Claimed` event emitted, `ChildBounties` entry removed, but `Balances::free_balance(&beneficiary) == 0` and the payout amount remains stuck in `child_bounty_account_id`.
6. Compare against a debug build, where the same sequence should trigger the `debug_assert!` panic, confirming the transfer indeed fails under these conditions.

This has not been executed in this session; the analysis is based on code inspection of `substrate/frame/child-bounties/src/lib.rs`, `substrate/frame/balances/src/impl_currency.rs`, and existing balances tests showing the ED-triggered transfer failure (`TokenError::BelowMinimum`).
