### Title
Signature verification fails open when a per-organization `webhook_secret` is unset, allowing forged webhooks to grant `Shipit.github_teams` membership - (File: lib/shipit/github_app.rb)

### Summary
`GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic verification success instead of rejecting the request, exactly mirroring the M-1 analog: a mandatory validation input that is absent gets silently coerced into "valid" rather than causing a hard failure. Combined with `WebhooksController#verify_signature` selecting the verification secret from an attacker-supplied organization name, and `MembershipHandler` trusting the webhook body to add arbitrary GitHub logins to `Team` records used for authorization, this breaks the binding: **GitHub identity that authenticated a webhook == the identity that is granted `Shipit.github_teams` membership**.

### Finding Description
`verify_webhook_signature` fails open when no secret is configured for the resolved organization: [1](#0-0) 

The organization used to pick the secret is derived directly from attacker-controlled JSON body fields, with no cross-check against anything else that was actually signed: [2](#0-1) 

Unlike an unknown organization (which raises `GithubOrganizationUnknown` and returns 422), an organization that is configured but simply has no `webhook_secret` set silently passes verification for *any* payload body, because `@webhook_secret = @config[:webhook_secret].presence` leaves it `nil` and nothing enforces it must be present: [3](#0-2) 

Once verification is bypassed, `MembershipHandler#process` fully trusts the payload to create/find a `Team` by an attacker-chosen `github_id` and to add an attacker-chosen GitHub `login` as a member — with no call back to GitHub to confirm any of this is real: [4](#0-3) 

The `Team` located by the forged `github_id` can be one of the very teams gating access, since `Shipit.github_teams` is derived from configured team handles and matched to `Team` rows by `(organization, slug)`: [5](#0-4) [6](#0-5) 

Authorization itself is a pure DB check against team membership, with no re-verification against GitHub at login time: [7](#0-6) [8](#0-7) 

**Binding broken:** GitHub identity that authenticated the webhook (via HMAC over `request.raw_post`, keyed by organization) == GitHub identity/User that is bound to `Shipit.github_teams` membership. Before the attack, a `User` row for the attacker's real GitHub login is unauthorized (no `Membership` to any team in `Shipit.github_teams`). After a forged, unauthenticated `membership` webhook is delivered for an organization whose `webhook_secret` is unset, a `Membership` is created linking the attacker's `User` to an authorizing `Team`, with zero cryptographic proof this action originated from GitHub.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization (explicitly listed as High severity): an unauthenticated attacker who can reach the `WebhooksController#create` endpoint can grant themselves membership in a team that gates access to the entire Shipit instance, then complete a normal GitHub OAuth login to obtain a fully authorized session — all without ever needing a `Shipit` session, `ApiClient` token, or the real `webhook_secret`.

### Likelihood Explanation
Exploitability is conditioned on one configured organization having no `webhook_secret` set — a state the code explicitly permits (`.presence` returns `nil`, no validation requires it) rather than one that requires misusing/deviating from documented deployment. Multi-organization installs (`config/secrets.*.yml` supporting a `github:` hash keyed by org) are common, and it is easy for an operator to add an organization entry without a webhook secret while still relying on `Shipit.github_teams` for authorization on that same org. The attacker also needs to know/guess the target `Team#github_id` (obtainable from GitHub's public API for many orgs/teams) and the org login name, both of which are not secret.

### Recommendation
- In `GitHubApp#verify_webhook_signature`, never return `true` when `webhook_secret` is blank; instead treat it as verification failure (return `false`), and add a startup/config check that raises if an organization used for authorization (`Shipit.github_teams`) lacks a `webhook_secret`.
- In `WebhooksController#verify_signature`, explicitly halt (`return` after `head(422)`) rather than relying on implicit filter-halting behavior, to avoid any future refactor silently allowing `create` to run after a failed check.
- In `MembershipHandler`, avoid trusting `params.team.id` / `params.member.login` verbatim for teams that participate in `Shipit.github_teams`; cross-check membership changes against the GitHub API before mutating `Membership` rows used for authorization decisions.

### Proof of Concept
1. Operator configures multi-org secrets with organization `acme` present under `secrets.github.acme` but with no `webhook_secret` key (a permitted, undocumented-as-forbidden configuration), while `Shipit.github_teams` includes `acme/core`.
2. `Team` row for `acme/core` already exists (created by `Team.find_or_create_by_handle` via `bin/rake teams:fetch`), with a known `github_id` (discoverable via GitHub's public team API if the org exposes it, or via other means).
3. Attacker sends, without any valid `X-Hub-Signature` (or any arbitrary value), an unauthenticated POST to `/github/webhooks` (or engine-mounted webhook path) with header `X-Github-Event: membership` and body:
   ```json
   {
     "action": "added",
     "team": { "id": <acme/core github_id>, "name": "Core", "slug": "core", "url": "https://api.github.com/teams/123" },
     "organization": { "login": "acme" },
     "member": { "login": "attacker-real-login" }
   }
   ```
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "acme")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` regardless of body/signature.
5. `MembershipHandler#process` finds the existing `acme/core` `Team` by `github_id`, creates/finds `User` for `attacker-real-login`, and appends a `Membership`.
6. Attacker logs in normally via GitHub OAuth with the `attacker-real-login` account; `current_user.authorized?` now returns `true` because the `Membership` created in step 5 satisfies `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, granting full authenticated access to the Shipit instance.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
