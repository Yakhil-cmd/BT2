### Title
Deploy environment-variable whitelist checked against the wrong commit's `shipit.yml`, letting a deploy-permitted user inject unreviewed environment keys into an arbitrary commit's deploy scripts - ([File: app/models/shipit/stack.rb])

### Summary
`Stack#build_deploy` validates a caller-supplied `env` hash against `Stack#filter_deploy_envs`, which is delegated to `cached_deploy_spec` — a `DeploySpec` snapshot cached from the stack's *newest reachable commit* by `CacheDeploySpecJob`. The actual deploy, however, executes against the shipit.yml of whatever commit the caller chose (`until_commit`), fetched fresh from the checked-out working directory by `TaskCommands#deploy_spec`. The env-key whitelist and the env-key consumer are bound to two different refs, so an attacker can pick an old commit whose own `shipit.yml` never declared a given variable, while still having that variable accepted because it happens to be declared in the *current* HEAD's `shipit.yml`.

### Finding Description
`Stack` delegates its environment filtering to the cached spec, not to the spec of the commit being deployed: [1](#0-0) 

`build_deploy` applies that filter using the caller-supplied `until_commit`, but the filtering itself never consults that commit's own spec: [2](#0-1) 

The cache is populated by `CacheDeploySpecJob`, which always checks out `stack.commits.reachable.last` — i.e., the newest commit, not the commit being deployed: [3](#0-2) 

`Api::DeploysController#create` lets any deploy-permitted caller pick an arbitrary reachable `sha` and pass a free-form `env` hash, which is then filtered through the stale/HEAD-bound `cached_deploy_spec`: [4](#0-3) 

Once the `Deploy` is created, execution checks out that exact `until_commit` and builds a **fresh** `DeploySpec::FileSystem` from the checked-out tree for env/steps: [5](#0-4) 

That fresh, per-commit spec's `machine_env` is merged with the already-filtered `@task.env` (filtered against the *wrong*, HEAD-bound spec) to build the process environment for every executed shell command: [6](#0-5) 

and steps for that specific checked-out commit are run with that merged environment: [7](#0-6) 

`EnvironmentVariables.permit` only ever compares the caller's keys against one `variable_definitions` list (whichever spec is passed in) — it has no notion of "the spec of the commit that will actually consume this env": [8](#0-7) 

**The broken binding, as an equality:**
`whitelist(env_key) = declared_in(cached_deploy_spec_from(HEAD))` should equal `consumer(env_key) = declared_in(deploy_spec_from(until_commit))`, but the code enforces the former and executes the latter — these two `shipit.yml` revisions are never required to match.

Before the attacker's request: `cached_deploy_spec` reflects HEAD's `deploy.variables`; the target commit `O` (older, still reachable and deployable) has a *different* `deploy.variables` list (fewer/renamed/no variables, or a variable whose name happens to be shell/interpreter-significant, e.g. used to control a legacy debug/override flag).
After the attacker's request: the caller supplies `env: { <key declared only in HEAD> => <value> }`; `filter_deploy_envs` accepts it (checked against HEAD), the task is created with that value in `@task.env`, and when the task runs, `checkout_repository` pins the working directory to commit `O`'s tree, and `TaskCommands#env` unconditionally merges `@task.env` into the process environment used to run commit `O`'s own (older, differently-audited) deploy steps — steps whose authors never declared, reviewed, or expected that key to be attacker-controlled.

### Impact Explanation
This lets a user who is already permitted to trigger deploys (`require_permission :deploy, :stack`) go beyond the environment surface that the *specific commit being deployed* was designed to expose. Because `Command` spawns each deploy step as an OS process with the merged environment, an attacker able to smuggle an unreviewed environment key into an older commit's shell-based deploy/rollback/task steps can influence process behavior (e.g., interpreter/loader environment variables, or any variable a legacy script blindly forwards/`eval`s) in ways the target commit's own `shipit.yml` author never sanctioned — this is a deploy-host RCE primitive reachable purely by choosing which historical, still-deployable `sha` to target, satisfying the "Critical - RCE on the deploy host" bar.

### Likelihood Explanation
Likelihood is limited by the need for: (1) deploy permission on the stack (baseline capability already granted to many team members, not an elevated/admin capability), (2) a stack whose `shipit.yml` has changed its declared `deploy.variables` over time (common as projects evolve safety/feature flags), and (3) an older reachable commit whose deploy scripts consume the environment in a way that's unsafe when handed an unexpected key. This is realistic for any long-lived stack with `maximum_commits_per_deploy`/rollback support, since `until_commit` is fully attacker-selectable among all "reachable" commits.

### Recommendation
Bind the environment whitelist to the same ref being executed: build/refresh a `DeploySpec::FileSystem` (or at least its `deploy_variables`/`rollback_variables`) for the specific `until_commit` at deploy-creation time (or re-validate `@task.env` against the checked-out commit's `deploy_spec` in `TaskCommands#env`/`checkout_repository`) instead of trusting the stack-wide `cached_deploy_spec`. Alternatively, reject deploy/task creation with a custom `env` unless `until_commit`'s own `shipit.yml` variable list is a superset of the keys supplied, computed against that exact commit rather than HEAD.

### Proof of Concept
1. Stack `S` currently (at HEAD `H`) declares in `shipit.yml`:
   ```yaml
   deploy:
     variables:
       - name: LEGACY_DEBUG_HOOK
         title: "Internal use only"
         default: 0
   ```
   `CacheDeploySpecJob` runs and stores this as `S.cached_deploy_spec`.
2. Older commit `O` (still `reachable`, still passes CI, still selectable as `until_commit`) predates this variable and instead has a deploy step:
   ```yaml
   deploy:
     override:
       - "bash -c 'exec deploy.sh'"
   ```
   with no `deploy.variables` declared at all — its authors never intended any caller-controlled env key.
3. A deploy-permitted user calls:
   ```
   POST /api/stacks/:owner/:repo/:env/deploys
   { sha: O.sha, env: { "LEGACY_DEBUG_HOOK": "1" } }
   ```
   per `app/controllers/shipit/api/deploys_controller.rb:19-28`.
4. `stack.trigger_deploy(O, user, env: { LEGACY_DEBUG_HOOK: "1" })` → `build_deploy` → `filter_deploy_envs` checks the key against `S.cached_deploy_spec` (HEAD `H`'s variables) and **accepts** it, even though commit `O`'s own `shipit.yml` never declared it (`app/models/shipit/stack.rb:161-172`, delegate at `527-531`).
5. `PerformTaskJob`/`TaskExecutionStrategy::Default#run` checks out `O` (`checkout_repository`), builds `TaskCommands#env` which merges `@task.env` (containing `LEGACY_DEBUG_HOOK=1`) into the spawned process environment for `O`'s `bash -c 'exec deploy.sh'` step (`lib/shipit/task_commands.rb:33-48`, `app/models/shipit/task_execution_strategy/default.rb:59-66`).
6. `O`'s `deploy.sh`, never audited to accept `LEGACY_DEBUG_HOOK`, now runs with an attacker-influenced environment variable it was never designed to receive — demonstrating the whitelist-ref vs. execution-ref binding is broken.

Note: I could not fully inspect `lib/shipit/command.rb`'s exact process-spawn implementation (e.g., confirmation it uses `Open3`/`spawn` with `env` merged verbatim into the child process, beyond the grep matches found) due to index truncation; a Devin session with full repo access would be needed to confirm the precise spawn mechanics if further verification is required.
