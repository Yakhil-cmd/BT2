## Title
Webhook signature verification is keyed to `repository.owner.login`, letting attackers pick an unsecured org's context to forge events (push / status / pull_request) against any repository named in the same payload's `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects **which** GitHub App/organization secret to validate a webhook against using an attacker-controlled field from the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`), while the event handlers that actually act on the payload key off a **different** field, `repository.full_name`. [1](#0-0) [2](#0-1) [3](#0-2) 

Because Shipit explicitly supports multi-organization deployments where each org has its own, independently-optional `webhook_secret` [4](#0-3) [5](#0-4) , and `verify_webhook_signature` treats a blank/absent secret as automatically verified (`return true unless webhook_secret`) [6](#0-5) , an attacker who knows (or can guess) that **any** configured organization lacks a webhook secret can forge signed-looking webhooks for a *completely different, secured* organization's repositories by mismatching `repository.owner.login` (used for verification) against `repository.full_name` (used to locate the `Stack`/`Repository` acted upon).

### Finding Description
The binding broken is: *the organization whose secret authenticates the payload* ≠ *the repository the payload's handlers actually write to*.

1. `verify_signature` computes `repository_owner` purely from the unverified request body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and uses it to fetch a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`. [1](#0-0) 
2. `Shipit.github` looks up per-organization app config by that name; each org can have its own `webhook_secret`, and it can legitimately be `nil` (shown as a supported, documented state in `config/secrets.development.example.yml` and `config/secrets.development.shopify.yml`). [7](#0-6) [5](#0-4) 
3. `verify_webhook_signature` short-circuits to `true` whenever that selected org has no `webhook_secret` configured — no HMAC check occurs at all. [6](#0-5) 
4. Once "verified", `create` re-parses the raw body and dispatches to handlers (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) that resolve the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')` — a field entirely independent of the one used to pick the verifying organization. [3](#0-2) [8](#0-7) [9](#0-8) 

An attacker can therefore submit a body with `repository.owner.login: "org-with-no-secret"` (satisfying verification for free) but `repository.full_name: "secured-org/target-repo"` (the field the handler actually uses), forging events against a repository belonging to a completely different, secured organization.

Concretely reachable, unauthenticated effects:
- **Forged `push`**: `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for any stack matching `repository.full_name`, queuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`. [10](#0-9) 
- **Forged `status`**: `StatusHandler#process` creates a `Status` record (`state`, `context`, etc., all attacker-controlled) for *any* commit matching `params.sha`, regardless of stack/org, via `commit.create_status_from_github!`. Statuses feed directly into `deployable?`/`blocking?`/merge-queue and continuous-delivery decisions. [11](#0-10) [12](#0-11) [13](#0-12) 
- **Forged `pull_request`** events can archive/unarchive review stacks or update stored PR metadata for repositories the attacker doesn't own, via the same `repository.full_name`-keyed lookup pattern used across the `PullRequest::*Handler` classes. [14](#0-13) 

### Impact Explanation
Forging a `success` status via `create_status_from_github!` can flip `Commit#deployable?`/`blocked?` and trigger `schedule_merges`/continuous-delivery scheduling for a commit in a stack the attacker does not control, effectively enabling an unauthorized deploy decision to be reached without real CI having passed. [12](#0-11) [15](#0-14)  This satisfies the "unauthorized deploy" impact bar, since it lets an unprivileged, unauthenticated network attacker manipulate CI/status state that gates deploys, and forge sync/push activity for stacks outside the organization whose credentials were actually checked.

### Likelihood Explanation
Exploitability is conditioned on the deployment running Shipit's documented multi-organization mode with at least one configured organization lacking a `webhook_secret` — a configuration explicitly shown as valid in the shipped example/dev secrets files. In that state, no credential, GitHub App private key, or webhook secret of any kind is needed by the attacker: a single unauthenticated `POST /webhooks` with a crafted JSON body and any `X-Github-Event` header (no valid `X-Hub-Signature` required) is sufficient. The root cause is a field-binding gap intrinsic to the code (verification keyed off `repository.owner.login`/`organization.login`, action keyed off `repository.full_name`), not a misuse of the app by the host.

### Recommendation
- Verify webhook signatures using a single, deployment-wide secret determination that cannot be steered by attacker-supplied JSON, or require the resolved verifying organization to exactly match `repository.full_name`'s owner before dispatching to handlers.
- Do not treat a missing `webhook_secret` for a given organization as automatic verification success; either require a secret for all configured organizations or reject payloads whose selecting-field organization has no secret rather than silently trusting them.
- Add a post-verification assertion in `WebhooksController#create` that `repository.full_name`'s owner equals the `repository_owner` used to verify the signature, rejecting mismatches with 422.

### Proof of Concept
1. Configure Shipit with two organizations: `secured-org` (has a `webhook_secret`) and `no-secret-org` (no `webhook_secret`), both installed as documented in "Using Multiple Github Applications". [4](#0-3) 
2. Send, with no `X-Hub-Signature` header (or any garbage value):
```
POST /webhooks
X-Github-Event: status

{
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "secured-org/target-repo"
  },
  "sha": "<sha of a real commit tracked by a stack under secured-org/target-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally. [6](#0-5) 
4. `create` re-parses the body and dispatches to `StatusHandler`, which looks up commits by `sha` (global, not org-scoped) and calls `create_status_from_github!`, creating a forged "success" status for `secured-org/target-repo`'s commit despite the attacker never presenting any valid credential for `secured-org`. [11](#0-10)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
