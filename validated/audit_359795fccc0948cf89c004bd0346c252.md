### Title
`remove_liquidity` hard-reverts (rather than gracefully returning) when a holder's proportional share rounds to zero, permanently freezing small LP token balances - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion`'s `do_remove_liquidity` computes the withdrawable amounts of `asset1`/`asset2` for a given `lp_token_burn` using floor division (`mul_div`), then unconditionally requires both results to be non-zero via `ensure!(!amount1.is_zero() ...)` / `ensure!(!amount2.is_zero() ...)`. Any signed, permissionless caller whose entire LP token balance is too small relative to the pool's `reserve/total_supply` ratio to redeem at least 1 raw unit of either asset will have every `remove_liquidity` call revert, with no way to lower the requested amount below their own balance to work around it. This mirrors the C4 finding [M-02] in `SfrxEth`/`SafEth`, where `redeem`'s `require((assets = previewRedeem(shares)) != 0, "ZERO_ASSETS")` blocked withdrawal of a share that rounded to zero assets.

### Finding Description
`do_remove_liquidity` computes: [1](#0-0) 

```
let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);

let amount1 = Self::mul_div(&lp_redeem_amount, &reserve1, &total_supply)?;
let amount2 = Self::mul_div(&lp_redeem_amount, &reserve2, &total_supply)?;

ensure!(
    !amount1.is_zero() && amount1 >= amount1_min_receive,
    Error::<T>::AssetOneWithdrawalDidNotMeetMinimum
);
ensure!(
    !amount2.is_zero() && amount2 >= amount2_min_receive,
    Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum
);
``` [2](#0-1) 

`mul_div` performs plain integer (floored) division with no rounding-up option: [3](#0-2) 

Because the `ensure!` requires `!amount1.is_zero()` **unconditionally** (not merely `amount1 >= amount1_min_receive`), a caller cannot opt in to receiving zero of one side even by setting `amount1_min_receive = 0`/`amount2_min_receive = 0`. If a member's remaining `lp_token_burn` (bounded above by their own balance, since `T::PoolAssets::burn_from(..., Exact, Polite)` cannot burn more than they own) is small enough that `lp_redeem_amount * reserveX / total_supply == 0` for either asset, `remove_liquidity` will always revert with `AssetOneWithdrawalDidNotMeetMinimum` or `AssetTwoWithdrawalDidNotMeetMinimum`, for that account, forever (or until the pool's ratio moves favorably, which does not happen in a healthy/growing pool).

This differs from `pallet-nomination-pools`'s analogous `point_to_balance`, which explicitly returns `Zero::zero()` gracefully instead of reverting: [4](#0-3) 
demonstrating that the hard-revert behavior in `asset-conversion` is avoidable but was not avoided.

A concrete trigger requires no privileged actor, governance, or admin config change (unlike the original report's admin-set-weight-to-0 scenario) — it can arise naturally:
- Repeated partial `remove_liquidity` calls over time by an LP holder, leaving a residual dust balance (directly analogous to the original bug's "percentage of remaining balance" unstaking pattern).
- Pools pairing assets of very different raw-unit magnitudes (e.g. a low-decimal asset vs. the 12-decimal native token), where `total_supply` (≈ `sqrt(reserve1*reserve2)`) is large relative to one reserve, so a modest-looking LP balance still floors to 0 of that asset.
- Receiving a small transferred LP token amount from a third party (LP tokens are ordinary transferable pool assets).

### Impact Explanation
Affected accounts permanently lose the practical ability to withdraw their own remaining liquidity position (their assets stay pool-locked with no operational way for that account alone to reclaim them), unless they can acquire additional LP tokens from another holder to push their `lp_token_burn` above the rounding threshold — which is not guaranteed and not something the frozen account controls. This is a freezing-of-funds condition, analogous in structure and mechanism to the referenced Medium-severity report (funds becoming unstakeable due to a hard revert on rounding-to-zero of a proportional redemption).

### Likelihood Explanation
Reachable by any ordinary signed account with no special privileges, purely through normal usage patterns (partial withdrawals over time, or holding a disproportionately small LP balance relative to pool reserves/supply for a given asset side). No malicious peer, governance action, or privileged role is required — only organic pool state evolution, matching the "no privileged role, no malicious peer/validator" constraint.

### Recommendation
Do not require `!amount1.is_zero()`/`!amount2.is_zero()` unconditionally. Instead, only enforce the `amountX >= amountX_min_receive` check the caller opted into (so a caller can explicitly permit receiving 0 of a side, similar to how the sFrxETH bug was recommended to be fixed by returning early rather than reverting), or provide a "burn full remaining LP balance" path/rounding mode that rounds in the withdrawer's favor for their final, full-balance redemption so dust can always be reclaimed.

### Proof of Concept
Failed guard demonstrated by the existing repo test showing the strict revert semantics of `remove_liquidity`/`do_remove_liquidity`: [5](#0-4) 

A minimal reproduction path (not executed against a live network, described for a local FRAME integration test using the existing `pallet-asset-conversion` mock/test harness):
1. Create a pool between a low-decimal asset (`asset2`, e.g. minimum_balance small raw units) and the native asset, then `add_liquidity` such that `total_supply` (≈ `sqrt(reserve1*reserve2) - MintMinLiquidity`) is large relative to `reserve2` (e.g. reserve2 = 1e7 raw units, total_supply ≈ 1e10).
2. Have a second LP provider join with a proportionally tiny share, or have the first provider partially `remove_liquidity` repeatedly until their remaining `lp_token_burn` balance satisfies `lp_redeem_amount * reserve2 / total_supply == 0` (e.g. balance < `total_supply / reserve2` ≈ 1000 LP tokens in the example above).
3. Call `remove_liquidity` with `lp_token_burn` = the account's full remaining LP balance and `amount2_min_receive = 0`.
4. Observe the call reverts with `Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum` even though `amount2_min_receive` was set to `0`, and this holds for any `lp_token_burn` up to the account's balance — the account cannot execute `remove_liquidity` at all until the pool's reserve/supply ratio shifts favorably (not under the account's control), demonstrating the funds-freezing condition. This has not been run against a live network; execution status is a proposed local FRAME test, pending confirmation by running the existing `pallet-asset-conversion` test suite with these parameters.

		/// Remove liquidity from a pool.
		pub(crate) fn do_remove_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			lp_token_burn: T::Balance,
			amount1_min_receive: T::Balance,
			amount2_min_receive: T::Balance,
			withdraw_to: &T::AccountId,
		) -> Result<(T::Balance, T::Balance), DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(lp_token_burn > Zero::zero(), Error::<T>::ZeroLiquidity);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;
			let (reserve1, reserve2) = Self::get_reserves(asset1.clone(), asset2.clone())?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
			let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
			let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);

			let amount1 = Self::mul_div(&lp_redeem_amount, &reserve1, &total_supply)?;
			let amount2 = Self::mul_div(&lp_redeem_amount, &reserve2, &total_supply)?;

			ensure!(
				!amount1.is_zero() && amount1 >= amount1_min_receive,
				Error::<T>::AssetOneWithdrawalDidNotMeetMinimum
			);
			ensure!(
				!amount2.is_zero() && amount2 >= amount2_min_receive,
				Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum
			);
			let reserve1_left = reserve1.saturating_sub(amount1);
			let reserve2_left = reserve2.saturating_sub(amount2);
			ensure!(
				reserve1_left >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);
			ensure!(
				reserve2_left >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);

			// burn the provided lp token amount that includes the fee
			T::PoolAssets::burn_from(
				pool.lp_token.clone(),
				who,
				lp_token_burn,
				Expendable,
				Exact,
				Polite,
			)?;

			T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;
			T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)?;

			Self::deposit_event(Event::LiquidityRemoved {
				who: who.clone(),
				withdraw_to: withdraw_to.clone(),
				pool_id,
				amount1,
				amount2,
				lp_token: pool.lp_token,
				lp_token_burned: lp_token_burn,
				withdrawal_fee: T::LiquidityWithdrawalFee::get(),
			});

			Ok((amount1, amount2))
		}

		fn mul_div(a: &T::Balance, b: &T::Balance, c: &T::Balance) -> Result<T::Balance, Error<T>> {
			let a = T::HigherPrecisionBalance::from(*a);
			let b = T::HigherPrecisionBalance::from(*b);
			let c = T::HigherPrecisionBalance::from(*c);

			let result = a
				.checked_mul(&b)
				.ok_or(Error::<T>::Overflow)?
				.checked_div(&c)
				.ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}

	fn point_to_balance(
		current_balance: BalanceOf<T>,
		current_points: BalanceOf<T>,
		points: BalanceOf<T>,
	) -> BalanceOf<T> {
		let u256 = T::BalanceToU256::convert;
		let balance = T::U256ToBalance::convert;
		if current_balance.is_zero() || current_points.is_zero() || points.is_zero() {
			// There is nothing to unbond
			return Zero::zero();
		}

		// Equivalent of (current_balance / current_points) * points
		balance(
			u256(current_balance)
				.saturating_mul(u256(points))
				// We check for zero above
				.div(u256(current_points)),
		)
	}
