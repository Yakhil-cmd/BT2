### Title
Signature verified against `repository.owner.login` while state-mutating handlers act on the unbound `repository.full_name` / global commit `sha` — cross-repository status/stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` is used to validate the HMAC signature based solely on `repository.owner.login` (or `organization.login`) from the still-unverified JSON body. Once verification passes, the event handlers that actually mutate state resolve their target using a *different* field of the same body — `repository.full_name` in `Shipit::Webhooks::Handlers::Handler#repository_name`, or, worse, no repository scoping at all in `StatusHandler`, which matches purely on the global `sha`. Nothing binds the authenticating owner to the repository/commit being written to.

### Finding Description
`verify_signature` computes the signing organization like this: [1](#0-0) [2](#0-1) 

It picks `Shipit.github(organization: repository_owner)` and validates the raw body's HMAC against that organization's `webhook_secret`. This only proves "whoever holds organization A's webhook secret sent this request" — it does not constrain which repository the payload's other fields describe.

Once the signature check passes, `create` dispatches the whole (attacker-controlled) JSON to the registered handler for the event: [3](#0-2) 

The base `Handler` resolves the target repository from an independent field, `repository.full_name`, not from `repository.owner.login`: [4](#0-3) 

`Repository.from_github_repo_name` splits `owner/name` straight out of this field and looks up the `Stack` to mutate: [5](#0-4) 

Because the signature check and the repository-resolution step read two different sub-fields of the same signed body, a party that legitimately controls organization A's `webhook_secret` (e.g., an org admin who configured Shipit's webhook for their own org — an ordinary, unprivileged-relative-to-other-tenants action) can submit a request where `repository.owner.login == "orgA"` (so the signature validates) but `repository.full_name == "orgB/target-repo"` (so the handler operates on a completely different tenant's `Stack`). This breaks the binding: `organization authenticated == repository written`.

`PushHandler` would then call `stack.sync_github` on org B's stack: [6](#0-5) 

`StatusHandler` is even less constrained — it never calls the `stacks` scoping helper at all and matches purely on the global commit `sha`, which is public GitHub data an attacker can easily know: [7](#0-6) 

This lets an org-A-authenticated request write a `Status` (e.g., a forged "success" CI status) onto any `Commit` row in the entire multi-tenant Shipit installation, regardless of which repository that commit belongs to, purely by supplying that commit's known `sha`.

### Impact Explanation
This is a cross-repository/cross-tenant write: a party trusted only for organization A's webhook traffic can inject synchronization events and forge commit statuses for stacks belonging to organization B. Forged/success commit statuses feed into `Commit#deployable?`/required-status checks that gate `stack.trigger_deploy`, so this can be leveraged to make an otherwise-blocked commit appear deployable in another tenant's stack, i.e., an unauthorized deploy — squarely inside the "Critical" bucket (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Any entity that has configured (or compromised) one organization's webhook integration on a shared Shipit instance can exploit this without any additional privilege — they only need to craft a JSON body where the `owner.login` used for authentication diverges from the `full_name`/`sha` used for the actual write. No GitHub App private key, `ApiClient` token, or additional repository access is required beyond the one org's `webhook_secret` they legitimately hold.

### Recommendation
After signature verification, re-derive the repository from the exact same field used for verification (`repository.owner.login`) and require it to match the owner segment of `repository.full_name` used by handlers (or pass the authenticated organization down into `Handler` and assert equality before any lookup). For `StatusHandler`, scope the `Commit` lookup to the authenticated repository/organization instead of a bare, cross-tenant `sha` match.

### Proof of Concept
1. Organization A has a Shipit-configured GitHub App with `webhook_secret = S_A`, used only for `orgA/*` repos.
2. Attacker (or malicious org-A admin) POSTs to `/webhooks` with header `X-Github-Event: status`, HMAC-signs the body with `S_A`, and sets:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "sha": "<known sha of orgB commit>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")` and validates successfully against `S_A`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — global, unscoped — and creates a forged success `Status` on org B's commit, potentially satisfying org B's required-status deploy gate.
