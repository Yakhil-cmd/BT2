## Title
Private asset payment blinding factors and addresses are unconditionally written to logs during validation and saving - (File: `indivisible_asset.js`)

### Summary
`ocore`'s indivisible-asset private-payment code path logs the full unhidden content of private payment elements — including the address, amount, and secret `blinding` factor — via `console.log`, unconditionally, on every validation and save of a private-asset transfer. This mirrors the Elastic Beats bug class (CVE-2023-49922): sensitive per-event data that must stay confidential is nevertheless written to persistent logs whenever the code path is exercised, rather than being kept out of logs or gated behind a debug-only flag.

### Finding Description
When a private (indivisible) asset payment is validated, `validatePrivatePayment` computes a `spend_proof` and then immediately dumps the object used to compute it — which contains `address` (the owner address) and `blinding` (the secret blinding factor that keeps outputs unlinkable) — to `console.log`: [1](#0-0) 

This happens for every transfer input processed while validating a private-asset chain element, not just on error, and not gated by any debug/verbosity flag — it always executes. Later, when the whole private payment chain is accepted and persisted, the code logs the entire array of private elements (again including address/blinding/amount for every output) and, separately, each individual revealed output: [2](#0-1) [3](#0-2) 

The `blinding` value and revealed `address`/`amount` are precisely the data elements that the private-asset protocol is designed to keep confidential (outputs are normally represented only as `output_hash` until deliberately revealed to a specific chain participant). Writing them to the process log means anyone with read access to node logs (log aggregation services, shared hosting, backup systems, support/debugging tooling, crash reporters that scrape stdout, etc.) can deanonymize private-asset transaction history and link addresses/amounts that were meant to stay hidden from third parties — the same class of confidentiality loss the Beats CVE addresses, but occurring unconditionally rather than only on 4xx errors.

### Impact Explanation
This is reachable by any unprivileged party that causes a private-asset payment to be validated on a node — e.g., a user's own wallet processing a received private payment, or a full/hub node relaying/validating private payment chains it forwards for others (`network.js`'s `handleOnlinePrivatePayment` / `handleSavedPrivatePayments`, and `wallet.js`'s `handlePrivatePaymentChains`, all of which funnel into `validateAndSavePrivatePaymentChain` → `indivisible_asset.js`). The blinding factors and addresses of private-asset outputs are exactly the secret material that keeps such payments unlinkable/confidential; their appearance in plaintext logs undermines the confidentiality guarantee of the private-payment feature for every party whose payment happens to be processed by a node with these code paths enabled, regardless of whether the log-reader is the payment’s legitimate counterparty.

### Likelihood Explanation
High likelihood of triggering: this is not an error path, it fires on the normal, successful validation and saving of every private indivisible-asset transfer input and every output being persisted. Any private-asset transaction naturally exercises this logging.

### Recommendation
- Remove or heavily redact the `console.log` calls in `indivisible_asset.js` (lines 125-133, 243, 272) that print `blinding`, `address`, and other output-revealing fields.
- If diagnostic logging of this data is required, gate it behind an explicit, disabled-by-default debug flag (analogous to Elastic's fix of moving such logs to DEBUG level, disabled by default), and ensure secret fields (`blinding`) are never logged even at debug level.
- Audit other private-payment modules (`divisible_asset.js`, `private_payment.js`, `network.js`, `wallet.js`) for similar unconditional logging of private payload contents (e.g., `console.log("saving private chain "+JSON.stringify(arrPrivateElements))`, `console.log("inserting output "+JSON.stringify(output))`) and remove/redact them as well.

### Proof of Concept
1. Run a node (full or light wallet) with default logging to stdout/file.
2. Send or receive a private-asset (indivisible, fixed-denomination) payment through the normal wallet flow so that `validateAndSavePrivatePaymentChain` → `indivisibleAsset.validateAndSavePrivatePaymentChain` → `validatePrivatePayment` is invoked.
3. Observe the node's logs: the line `"validation spend proof: " + JSON.stringify({... address, amount, blinding})` at [1](#0-0)  and `"saving private chain " + JSON.stringify(arrPrivateElements)` at [4](#0-3)  print the previously-secret `blinding` value and revealed `address`/`amount` in plaintext, exposing data that the private-asset design intends to keep confidential.
