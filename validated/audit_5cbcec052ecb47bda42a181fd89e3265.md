### Title
`StatusHandler#process` mutates `Commit`/`Status` rows for every repository sharing a sha, with no per-repository or per-stack scoping - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no scoping to the repository named in the webhook payload, unlike `PushHandler`/`PullRequest` handlers which resolve `Stack`/`Repository` by owner+name before acting. Because GitHub webhook signatures are verified per-organization (via `Shipit.github(organization: repository_owner)` in `WebhooksController#verify_signature`) rather than per-repository, and `Commit.sha` has no repository-scoped uniqueness constraint, a single valid webhook for one repository can write forged CI status onto `Commit` rows belonging to unrelated stacks/repositories that happen to share that sha.

### Finding Description
Broken binding: `number of repositories authorized by the webhook that fired this event (1, the repo in `params.dig('repository','full_name')`)` should equal `number of repositories whose Commit rows get `create_status_from_github!` called (currently unbounded N, driven only by `sha` collisions)`.

Code path:
1. `Shipit::WebhooksController#create` parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [1](#0-0) .
2. `verify_signature` only checks that the HMAC signature matches the secret configured for the organization inferred from `params.dig('repository','owner','login')` — it never checks that the specific `repository.full_name` in the payload is the one the caller is authorized to speak for; it just proves "some event for this GitHub org, signed with the org's webhook secret" arrived [2](#0-1) .
3. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no `.joins(:stack)` filter on `stack.repository`, no check that `commit.stack.repository.full_name == params.repository.full_name` [3](#0-2) .
4. `Commit#create_status_from_github!` unconditionally appends the forged status and re-evaluates deployability, triggering `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` side effects [4](#0-3) [5](#0-4) .

Root cause: `Commit.sha` is a raw git sha with no repository/stack scoping in this query, and repositories can legitimately share commits (shared history via fork/import, or degenerate shared shas like an empty init commit). Anyone able to trigger a genuinely signed status event for their own repository (which only requires push access to their own low-value repo registered under the same GitHub org/App installation) supplies a `sha` value that, if it also exists in another stack's commit table, gets that other stack's commit forged with the attacker-chosen `state`/`description`/`target_url`.

Existing guards do not prevent this: `verify_signature` authenticates the org-level webhook secret, not the specific repository named in the payload; `drop_unhandled_event` only filters by event type; there is no `ExplicitParameters`-level repository check in `StatusHandler`; no `stacks`/`by_repository` scope is applied to the `Commit.where` query, unlike patterns used elsewhere in the pull-request handlers that resolve repository first.

### Impact Explanation
A single legitimately-signed webhook for one repository can flip the recorded CI `state`/`description`/`target_url` on `Commit` rows belonging to unrelated stacks in unrelated repositories that happen to share the same sha, which can unblock `deployable?` checks and trigger `stack.schedule_merges` / `ContinuousDeliveryJob` for those foreign stacks — i.e., a payload for one repository mutating another's stack/commit state, matching the "Critical" impact category (cross-tenant record mutation not authorized by the authenticating repository). The blast radius scales with however many stacks share a colliding sha (e.g. all repos initialized/forked from a shared root commit), and is repeatable per webhook.

### Likelihood Explanation
Preconditions: attacker needs push/webhook-triggering access to at least one repository registered with Shipit under the same GitHub App/org installation (a normal, unprivileged capability for repo owners), and needs a sha collision with a target repository's commit (achievable deliberately by forking/rebasing onto a shared ancestor commit, or naturally common for initial/empty commits). No Shipit session, API token, or webhook secret knowledge is required — the webhook signature is generated by GitHub itself for the attacker's own repo event. This is feasible without any secret compromise, purely by exploiting the missing repository scoping in the `Commit.where(sha:)` query.

### Recommendation
Scope the query by the repository named in the payload, e.g. resolve the `Stack`/`Repository` from `params.repository` (owner+name) first, then restrict to `Commit.joins(:stack).merge(Stack.where(repository: repo)).where(sha: params.sha)`, mirroring the repository-resolution pattern already used in the `pull_request/*` handlers.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "status event scoped to one repository must not mutate commits in other repositories' stacks" do
  shared_sha = 'deadbeef' * 5

  stacks = 5.times.map do |i|
    repo = Shipit::Repository.create!(owner: "tenant#{i}", name: "repo#{i}")
    stack = Shipit::Stack.create!(repository: repo, environment: 'production')
    Shipit::Commit.create!(stack: stack, sha: shared_sha, message: 'init')
  end

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'description' => 'forged',
    'context' => 'ci/forged',
    'repository' => { 'full_name' => 'tenant0/repo0', 'owner' => { 'login' => 'tenant0' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  # Binding under test: only tenant0/repo0's commit should have a new status.
  assert_equal 1, stacks[0].reload.commits.first.statuses.count
  stacks[1..4].each do |stack|
    commit = stack.commits.first.reload
    assert_equal 0, commit.statuses.count,
      "commit in #{stack.repository.full_name} was mutated by a webhook authenticated only for tenant0/repo0"
  end
end
```
This test currently fails against `StatusHandler#process` as implemented, because `Commit.where(sha: params.sha)` matches all 5 rows and calls `create_status_from_github!` on each, confirming the unbounded cross-tenant write.

      verified = github_app.verify_webhook_signature(

        request.raw_post
      )

      ].join(' '))

      already_deployed = deployed?
