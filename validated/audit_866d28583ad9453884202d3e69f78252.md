### Title
Missing `nonReentrant` Guard and CEI Violation in `_requestERC20Transfer` Enables Double-Spend of Bridged Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20._requestERC20Transfer` (and its public entry points `requestERC20Transfer` / `onERC20Received`) lacks the `nonReentrant` modifier and increments `requestNonce` **after** external calls to the token contract. A registered ERC20 token with a transfer-callback hook (e.g., ERC-777 `tokensReceived`, or a custom `_afterTokenTransfer`) can re-enter `onERC20Received` during fee payment, causing the bridge to emit two `RequestValueTransfer` events with distinct nonces for a single deposit. The bridge operator processes both events and transfers/mints the bridged value twice on the destination chain.

`BridgeTransferKLAY` explicitly carries `nonReentrant` on both `handleKLAYTransfer` and `_requestKLAYTransfer`, and `BridgeFee.sol` even documents "Caller of this function must be nonReentrant." The ERC20 and ERC721 paths never received the same protection.

### Finding Description

**`BridgeTransferERC20._requestERC20Transfer` — CEI violation + missing guard** [1](#0-0) 

Execution order inside `_requestERC20Transfer`:

1. `_payERC20FeeAndRefundChange(...)` → calls `IERC20(_token).safeTransfer(feeReceiver, fee)` ← **external call**
2. `ERC20Burnable(_tokenAddress).burn(_value)` ← **external call** (mint/burn mode)
3. `emit RequestValueTransfer(..., requestNonce, ...)` ← reads `requestNonce`
4. `requestNonce++` ← **state update happens last** [2](#0-1) 

The comment on line 41 of `BridgeFee.sol` acknowledges the reentrancy risk: *"Caller of this function must be nonReentrant."* `_requestKLAYTransfer` honours this contract; `_requestERC20Transfer` does not. [3](#0-2) 

`onERC20Received` is `public` with no guard: [4](#0-3) 

`requestERC20Transfer` is also `public` with no guard: [5](#0-4)

### Impact Explanation

**Lock mode (destination bridge holds tokens):**

Attacker deposits `value + feeLimit` tokens. During `safeTransfer(feeReceiver, fee)` in `_payERC20FeeAndRefundChange`, the token's hook re-enters `onERC20Received` exactly once (attacker controls hook depth). The inner call completes first: emits `RequestValueTransfer(nonce=N)`, increments `requestNonce` to `N+1`. The outer call then emits `RequestValueTransfer(nonce=N+1)`, increments to `N+2`. The bridge operator submits both `handleERC20Transfer` calls to the destination bridge. Each passes `_lowerHandleNonceCheck` and `_voteValueTransfer` independently (different nonces, different tx hashes). The destination bridge transfers `value` tokens **twice**. Net attacker gain: `value − feeLimit`.

**Mint/burn mode:**

Same re-entry path. Two `RequestValueTransfer` events with distinct nonces cause the bridge operator to call `handleERC20Transfer` twice on the destination chain, minting `value` tokens twice. The source-chain burn of `value` tokens happens once per re-entrant frame; the attacker must supply enough balance for both burns, but the destination-chain mint is unbounded by source-chain liquidity.

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
    }
