### Title
Webhook signature is verified against the organization named in `repository.owner.login`, while the mutated repository/stack is selected from `repository.full_name` — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks *which organization's* `GithubApp`/`webhook_secret` to validate the HMAC signature against using `repository_owner`, a value read straight out of the still-unverified JSON body (`repository.owner.login` or `organization.login`). Once the signature check passes, the `create` action hands the *same* raw payload to event handlers that instead key off a *different* field, `repository.full_name`, to decide which `Repository`/`Stack` in the datastore to act on. Because these are two independent, attacker-controlled sub-fields of the same JSON body, an attacker who legitimately controls one organization (and therefore knows that organization's `webhook_secret`) can craft a payload whose `repository.owner.login` matches their own org (so the correct secret is selected and the signature validates) while `repository.full_name` names a completely unrelated repository/stack tracked by the same Shipit instance. The forged event is then processed against that unrelated stack.

Every handler resolves the target `Repository`/`Stack` using a different field of the payload, `repository.full_name`, not the `repository.owner.login`/`organization.login` value that gated signature verification: [4](#0-3) 

This is structurally identical to the reported `WUSDA` bug class: a value is used for one purpose (here, choosing the signing key that authorizes the request) while a *different* value governs the actual state mutation (here, which repository/stack is written to), and both values live inside the same attacker-supplied blob evaluated *before* trust is established. Just as the audit finding shows `_usdaAmount` and the resulting `_wusdaAmount` diverging under attacker-chosen inputs, here `repository.owner.login` (used to select the verification key) and `repository.full_name` (used to select the mutated resource) can be made to diverge by an attacker who controls the payload and possesses a valid key for only one of the two.

### Impact Explanation
Handlers reachable this way include `PushHandler`, which invokes `stack.sync_github(expected_head_sha:)`: [5](#0-4) 
and `StatusHandler`, which creates arbitrary CI/commit statuses on a commit: [6](#0-5) 

Forging commit statuses (e.g. marking a check as `success`) for a stack the attacker does not own can satisfy `required_statuses`/CI gating used elsewhere in the engine to authorize deploys and merges, meaning an attacker who only controls organization A's GitHub App/webhook secret can influence deploy/merge eligibility for organization B's stacks tracked by the same Shipit instance. This crosses the "cross-repository writes" / "unauthorized deploy" bar.

### Likelihood Explanation
Exploitation requires the Shipit instance to be configured for multiple organizations (each with its own `webhook_secret`, as implied by `Shipit.github(organization:)` and the `GithubOrganizationUnknown` handling), and requires the attacker to legitimately control (or have compromised) at least one of those organizations' webhook secrets — a scenario that is plausible in shared/multi-tenant Shipit deployments but not universal. I was not able to fully trace the multi-org secrets-loading code (`Shipit.github` beyond `lib/shipit.rb`'s partial listing) within the available tool budget, so the exact mechanics of how many/which orgs can have distinct secrets in a given deployment is not fully confirmed from the index; this should be verified against `lib/shipit/github_app.rb`/`lib/shipit.rb` secrets-loading code in a full session.

### Recommendation
Verify the webhook signature independently of any payload-derived organization selection, or, after signature verification succeeds, re-derive `repository_owner` from the *same* field (`repository.full_name`'s owner segment) that handlers use to resolve `Repository`/`Stack`, rejecting the webhook if `repository.owner.login` and the owner segment of `repository.full_name` disagree. Alternatively, scope `Repository.from_github_repo_name` lookups to only repositories belonging to the organization whose secret validated the signature.

### Proof of Concept
1. Shipit is configured with `webhook_secret` values for organization `attacker-org` (which the attacker legitimately administers) and organization `victim-org` (tracked stacks the attacker does not control).
2. Attacker crafts a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/some-repo"}, "sha": "<forged>", "state": "success", ...}` and signs it with `attacker-org`'s webhook secret.
3. `verify_signature` computes `repository_owner` → `"attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes because the attacker used the correct secret for that org.
4. `create` dispatches the same payload to `StatusHandler`, whose `repository_name` resolves to `"victim-org/some-repo"` via `payload.dig('repository', 'full_name')`, and a forged commit status is written against `victim-org`'s tracked commit — despite the signature never having been validated against `victim-org`'s credentials.
