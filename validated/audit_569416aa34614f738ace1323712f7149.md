## Title
Attacker-controlled secondary AA can force `revert()` of an entire primary AA trigger, permanently blocking settlement/payout and causing fund loss - (File: `aa_composer.js`)

## Summary
The reported Solidity bug (H-3) shows that an attacker (`bull`) who controls the recipient contract of a mandatory `safeTransferFrom()` call inside `settleContract()` can force the whole settlement transaction to revert, permanently preventing the victim (`bear`) from exercising their rights. The analogous root cause exists in ocore's Autonomous Agent (AA) engine: when a primary AA trigger causes a chain of AA-to-AA payments ("secondary triggers"), a failure ("bounce") of *any* downstream AA in that chain is propagated up and forces the **entire** primary AA response to be rolled back via `revert()`, exactly like an attacker-controlled `to` address causing a revert that blocks the honest party's transaction.

## Finding Description
When a primary AA sends a payment to an address that is itself an AA, `handleSecondaryTriggers()` synchronously re-enters `handleTrigger()` for that address [1](#0-0) . If any AA in this chain bounces, the error propagates back through `async.eachSeries`, and for the *primary* (non-secondary) trigger this results in a call to `revert()`: [2](#0-1) 

`revert()` then undoes **all** work already performed by the primary AA — restoring its state variables, rolling back the DB savepoint, discarding all previously generated responses in the chain — and finally calls `bounce(err)`: [3](#0-2) 

`bounce()` only sends funds back to the original trigger sender if the trigger's outputs cover the configured `bounce_fees`; otherwise it silently swallows the incoming funds with `finish(null)` and no response is produced at all: [4](#0-3) 

This is the direct analog of the reported bug: any AA-based application (marketplace, escrow, settlement AA, etc.) that forwards a payment to a user- or counterparty-supplied address, which the counterparty can register as a maliciously-crafted AA that unconditionally bounces (e.g., a template whose `messages` formula deliberately throws or fails a condition), can force the entire primary AA's settlement logic for that trigger to be reverted — not just the isolated payment leg, because oscript AA templates have no equivalent of Solidity's `try/catch` to isolate a failing downstream call from the rest of the primary AA's state changes.

## Impact Explanation
- If the primary AA's trigger includes enough base bytes to cover `bounce_fees`, the whole operation reverts and the original sender's funds are bounced back, meaning the counterparty attack completely blocks any settlement/payout that must route through the attacker-chosen address — the victim can never complete the action, analogous to the bear never being able to `settleContract()`.
- If the trigger's outputs are insufficient to cover `bounce_fees` (a case the AA author cannot always control, e.g. when computed dynamically based on collateral/premium sizes), the AA silently keeps the funds and produces **no** response at all — outright freezing/loss of the victim's funds inside the AA, since revert() has already erased any accounted state that would let the funds be reclaimed later.
- Because the AA logic is Turing-incomplete but deterministic, every full node computes the exact same reverted outcome, so this does not cause a fork/consensus disagreement — but it does cause deterministic denial of settlement and possible fund freezing for any AA design (escrow, marketplace, options/derivatives AA, etc.) that pays out to an address chosen or controllable by an untrusted counterparty.

## Likelihood Explanation
Any address format in Obyte is potentially an AA address (the chash160 of an AA definition); an attacker who is a counterparty to an escrow/marketplace/derivative AA can pre-compute and register a malicious AA definition matching an address they present as their "beneficiary"/"seller"/"payout" address before interacting with the victim AA. This requires no privileged access — only posting an ordinary AA-definition unit and then engaging in a normal deal, making the likelihood high for any composable AA design that performs AA-to-AA payouts to third-party-supplied addresses.

## Recommendation
Mirror the Solidity fix pattern for AA design guidance and, ideally, framework-level mitigation:
- At the framework level, consider not propagating a secondary AA's bounce as an automatic `revert()` of the entire primary chain; instead, let the primary AA optionally continue (e.g., treat the failed leg's funds as retained by the primary AA, similar to the `withdrawableCollectionTokenId` pattern in the Solidity fix) rather than unconditionally rolling back all already-completed state changes.
- Document/require that AA authors who forward payments to externally-supplied recipient addresses isolate that leg (e.g., send it as the very last message and design the state machine so that failure of a downstream secondary trigger does not need to undo the primary AA's already-finalized business logic), and avoid relying on `bounce_fees` sized in a way that leaves an under-funded silent-swallow path.

## Proof of Concept
1. Attacker crafts a malicious AA template `M` whose `messages` block always fails to satisfy a condition (or omits any valid `messages`, guaranteeing a bounce), and computes its address `addr_M = chash160(M)`; attacker posts `M`'s definition.
2. Attacker engages with a victim "settlement" AA `S` (e.g., an escrow/options AA) as a counterparty, supplying `addr_M` as the address that should receive the payout leg of the deal (as is common for "send proceeds to seller/counterparty address" patterns).
3. When the deal's trigger unit becomes stable and `S` executes, `S`'s `messages` include a payment to `addr_M` alongside `S`'s state changes recording the deal as settled. This produces a secondary trigger to `addr_M` (`aa_composer.js:1702-1741`).
4. AA `M` bounces on its secondary trigger; `handleSecondaryTriggers`'s `async.eachSeries` callback receives an error and, since this is the primary (non-secondary) trigger, calls `revert(...)` (`aa_composer.js:1749`).
5. `revert()` rolls back all of `S`'s state changes and responses (`aa_composer.js:1759-1783`) and calls `bounce()`, which either returns the trigger's funds to the original sender (undoing the entire settlement) or, if bounce fees are insufficient, silently keeps the funds with no response produced (`aa_composer.js:909-945`).
6. The victim can never complete settlement through `S` against this counterparty/address, and depending on the fee math may permanently lose the deposited funds — the AA analog of the bear never being able to `settleContract()`.
