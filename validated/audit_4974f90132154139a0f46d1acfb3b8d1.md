### Title
Borrow-index growth past the RAY value ceiling makes `scaled_to_original` panic inside accrual, permanently freezing a market - (File: contracts/pool/src/interest.rs)

### Summary
CVE-2016-3178 is a crash DoS where an out-of-domain magnitude (a negative length) reaches unchecked arithmetic. The on-chain analog here is an out-of-domain magnitude — the borrow index itself — reaching a checked `checked_mul` inside `scaled_to_original`, which panics before the intended `MAX_BORROW_INDEX_RAY` index cap can clamp it. Because every mutating entrypoint runs `global_sync` (accrual) first, once a market crosses the RAY value ceiling every verb — `withdraw`, `repay`, `liquidate`, even `update_indexes` — panics permanently. Suppliers' funds are frozen forever.

### Finding Description
`interest::global_sync` (contracts/pool/src/interest.rs:20-33) chunks elapsed time and calls `accrue_chunk`, which invokes `common::rates::accrue_step` with the live `borrowed` shares and `borrow_index`. `accrue_step` computes the accrued value via `scaled_to_original(borrowed, borrow_index)` — a RAY×RAY multiply. The protocol intends to cap index growth at `MAX_BORROW_INDEX_RAY`, but the harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361) proves the multiply overflows `i128` inside `scaled_to_original` *before* the index reaches that cap, so the cap never engages:

- After enough accrual, `update_indexes` for the market fails with `MathOverflow`.
- `withdraw` and `repay` fail identically — the test asserts both panic with `MATH_OVERFLOW` (lines 355-356) and comments: *"Every verb accrues first, so the market freezes: no repay, no withdraw, no liquidation."*

An unprivileged attacker seeds this by supplying a huge notional to an 18-decimal market and borrowing ~98% of it on a curve with a steep high-utilization segment (`supply`/`borrow` on the controller, then waiting; `update_indexes` is permissionless). No admin action, oracle manipulation, or special parameters beyond a steep rate model are required.

### Impact Explanation
Permanent freezing of funds: once the panic threshold is crossed, no call that touches the market can succeed — suppliers cannot withdraw, borrowers cannot repay, liquidators cannot act, and `clean_bad_debt`/`recapitalize` paths that accrue also fail. The market is bricked in-place with all cash locked in the pool.

### Likelihood Explanation
Low-to-moderate. It requires whale-scale notional (~10^27 base units in the test) and sustained ~98% utilization on a steep rate curve for multiple years before the index crosses the overflow point — which is why it rates Medium, matching the CVE. However it is fully reachable by unprivileged `supply`/`borrow`/`update_indexes` calls, requires no privileged action, and there is no recovery path once reached (the panic is permanent, not a temporary revert).

### Recommendation
Order the index cap before the overflow point: in `accrue_step` (common/src/rates), clamp the computed `borrow_index`/`supply_index` to `MAX_BORROW_INDEX_RAY` *before* any `scaled_to_original` multiply that can overflow, or compute accrual in a widened type / use `saturating_mul`-style semantics so the cap can engage. Alternatively, bound per-market `borrowed` share totals so `shares × index` can never exceed the RAY value ceiling within the index-cap domain.

### Proof of Concept
Already present and reproducible in the repo: tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361 —

```rust
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));          // unprivileged supply
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);            // ~98% utilization
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }  // MathOverflow
}
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW); // frozen
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);    // frozen
assert!(book(&t, "BIG18").borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
```

Uncertain: the exact overflow point inside `common::rates::accrue_step`/`scaled_to_original` was inferred from the test's own documentation rather than read line-by-line (index coverage of `common/src/rates` was partial); the mechanism, error, and frozen-state assertions are nonetheless fully supported by the cited test.
