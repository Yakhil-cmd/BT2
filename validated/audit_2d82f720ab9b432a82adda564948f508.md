### Title
Sensitive Private-Payment and Device-Message Secrets Written to Debug Log via `console.log` - (File: device.js, indivisible_asset.js)

### Summary
Multiple code paths that process attacker/counterparty-supplied data — decrypted device messages and private-payment chains — write the full sensitive payload to `console.log`, mirroring the NiFi bug class (CWE-532: sensitive values logged in debug output) where Parameter Context values leaked into application logs.

### Finding Description
`device.js`'s `decryptPackage()` decrypts an incoming device message (whose ciphertext, sender ephemeral pubkey, etc. are fully attacker/peer-controlled fields) and then logs the entire decrypted plaintext: [1](#0-0) 
This is invoked from `handleJustsaying` on `hub/message`, i.e. for every message a paired device or counterparty sends: [2](#0-1) . Device messages carry sensitive content such as private-payment chains, pairing/wallet-approval data, and other private message payloads forwarded between correspondent devices.

Separately, `indivisible_asset.js` logs the components of a private-payment spend proof — including the source address, amount, and blinding factor of a private output — before it has even been validated: [3](#0-2) 
and logs the entire private-payment chain (including hidden outputs' addresses and blinding) once validated: [4](#0-3) 
and each output's decrypted amount/blinding while saving: [5](#0-4) 
These logging calls execute on private-payment chains fully controllable by a private-payment sender (asset issuer or private-payment counterparty), analogous to how a NiFi administrator's routine flow-sync process unexpectedly logged Parameter values.

### Impact Explanation
`blinding` factors and hidden output addresses are the confidentiality mechanism for ocore private/blackbytes-style assets — knowledge of blinding + amount + address lets anyone reconstruct/verify a specific private output and correlate transaction graphs, defeating the privacy guarantee of private assets. Similarly, logging full decrypted device-message plaintext exposes the content of private payment chains and other sensitive correspondent-to-correspondent data to anyone with read access to node logs (operators, log aggregation systems, crash reporters). This is a confidentiality-only leak (CWE-532 class); it does not by itself enable double-spend, inflation, or fund loss, so it falls short of the "Validate" bar requiring concrete unauthorized spending/inflation/freezing/consensus-disagreement impact.

### Likelihood Explanation
Any node that runs with default `console.log` output captured to a file (as full/hub nodes commonly do) would record this data automatically and unconditionally — no special debug flag needs to be enabled by an administrator, unlike the NiFi case which required explicitly raising a log level. Triggering it requires only sending a private payment chain or a device message to the victim node, something an unprivileged private-payment counterparty or paired device can always do.

### Recommendation
Remove or redact the `console.log` calls that print decrypted device-message plaintext (`device.js:466`) and private-payment internals such as `blinding`, `amount`, and `address` fields (`indivisible_asset.js:125-133, 243, 272`). If such logging is needed for debugging, gate it behind an explicit, disabled-by-default debug flag and ensure blinding/amount/address values are omitted or hashed.

### Proof of Concept
1. Pair two wallets/devices (or become a private-asset counterparty).
2. Send a private payment (indivisible or divisible private asset) or any device message to the victim node.
3. On the victim node's console/log output, observe the plaintext decrypted device message (`device.js:466`) and, for indivisible private assets, the full spend-proof components and private-chain outputs including `blinding` and `address` fields logged via `indivisible_asset.js`.
4. Anyone with access to the node's stdout/log file can now read this otherwise-private information. [6](#0-5) [7](#0-6) [8](#0-7) 

**Note on confidence:** I was unable to locate a definitive `console.log`-to-file redirection mechanism in this checkout (searches for `LOG_FILENAME`, `createWriteStream`, and console overrides outside `profiler.js`/`sqlite_pool.js` returned nothing), so whether this data lands in a persistent, more broadly-accessible log file (raising real-world exposure) versus ephemeral stdout could not be confirmed with the available tools.
