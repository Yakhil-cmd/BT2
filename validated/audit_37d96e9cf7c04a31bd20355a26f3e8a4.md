### Title
Path traversal in `gh repo read-file --output` via unsanitized `file.Name` in `writeToOutput` `asDir` branch - ([File: pkg/cmd/repo/read-file/read_file.go])

### Summary
`writeToOutput`'s `asDir` branch builds the destination path with `filepath.Join(dest, file.Name)` where `file.Name` is taken verbatim from the Contents API JSON `name` field, with no `safepaths`-style confinement to the output directory. A malicious/compromised host that the victim points `gh` at (custom `--hostname`/GHES, or any server the API request resolves to) can return a crafted `name` value such as `"../../evil.txt"`, causing the write to escape the user-specified `--output` directory.

### Finding Description
`fetchFile` -> `fetchContent` in `pkg/cmd/repo/read-file/http.go` unmarshals the Contents API response directly into `contentsResponse.Name` [1](#0-0)  and copies it unmodified into `repoFile.Name` [2](#0-1) . This value is never validated to be a plain basename.

In `writeToOutput`, when the target `output` path is (or is treated as) a directory, the destination is computed as `dest = filepath.Join(dest, file.Name)` [3](#0-2) . `filepath.Join` normalizes `..` segments, so a `file.Name` of `"../../evil.txt"` will resolve `dest` to a location outside the directory the user passed via `--output`. The subsequent symlink/clobber checks only re-`lstat` the final joined `dest` [4](#0-3)  and do not verify `dest` remains inside the original `output` directory, then `writeFileF` performs the write [5](#0-4) .

This is in contrast to other output paths in the same codebase — e.g. `pkg/cmd/run/download`, `internal/zip/zip.go`, and `internal/skills/installer/installer.go` — which all use `internal/safepaths` to confine extracted/joined paths to the intended base directory before writing. `read_file.go` has no such usage of `safepaths` anywhere in the package.

### Impact Explanation
This allows an arbitrary file write to a location of the attacker's choosing outside the `--output` directory the victim specified, up to the privileges of the `gh` process. This matches GitHub's "file write outside intended path" bounty impact class. The severity is bounded by the fact that the attacker needs to control the API response itself (i.e., the "name" field returned by the Contents endpoint), not merely the repository's real file/directory names — for github.com, the genuine API constrains `name` to the basename of the requested path, so this is exploitable primarily when the victim points `gh` at an attacker-influenced/malicious host (custom hostname, GHES instance, or a MITM'd/attacker-controlled server), which is within the stated threat model ("controls responses from a host the victim points gh at").

### Likelihood Explanation
Requires: (1) victim runs `gh repo read-file <path> --output <dir>/` with a trailing separator (or an existing directory) against a host controlled or spoofable by the attacker, and (2) that host's Contents API response for the requested path includes a crafted `name` field containing `..`/path-separator sequences. Given this is a preview command and requires a non-default host trust relationship, likelihood is limited to the malicious-host/GHES scenario rather than plain github.com repos, but it is deterministic and repeatable once that precondition holds.

### Recommendation
Sanitize `file.Name` before use in the `asDir` branch — reject or strip any path separators / `..` (e.g., use `filepath.Base(file.Name)` and reject if it differs from a clean basename, or reject names equal to `"."`/`".."`/containing `filepath.Separator`). Alternatively, adopt `internal/safepaths.Absolute.Join` (as used in `pkg/cmd/run/download`, `internal/zip`, and `internal/skills/installer`) to confine the joined destination to the resolved output directory and return an error if the result would escape it.

### Proof of Concept
Add to `pkg/cmd/repo/read-file/read_file_test.go`:

```go
func TestWriteToOutput_PathTraversalInName(t *testing.T) {
    file := &repoFile{
        Name:    "../../evil.txt",
        Content: []byte("pwned"),
    }
    // simulate output ending in "/" so asDir is true, and the dir doesn't exist yet
    dest, err := writeToOutput(file, "safe-dir/", false)
    if err == nil {
        // Assert the resulting dest is still contained within "safe-dir"
        abs, _ := filepath.Abs(dest)
        base, _ := filepath.Abs("safe-dir")
        if !strings.HasPrefix(abs, base+string(os.PathSeparator)) {
            t.Fatalf("path escaped output directory: dest=%q", dest)
        }
    }
}
```
Running this against current `writeToOutput` shows `dest` resolves outside `safe-dir` (e.g., to `../evil.txt` relative to the working directory) and no error is returned, confirming the missing confinement described above.
