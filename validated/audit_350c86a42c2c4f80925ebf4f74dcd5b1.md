### Title
CCMenu API endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` lookup to bypass the per-`ApiClient` stack authorization scope enforced everywhere else in the API, allowing a token that is authorized for only one stack to read build/deploy state for any stack.

### Finding Description
Every other API controller resolves the target stack through `Shipit::Api::BaseController#stack`, which first narrows the queryable stacks to those the authenticated `ApiClient` is bound to: [1](#0-0) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client has a bound `stack_id`, so `stack.from_param!(params[:stack_id])` will raise `RecordNotFound` if the requested stack differs from the one the token authorizes — this is the intended equality: `ApiClient.stack_id == stack acted upon`.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves directly against the global `Stack` relation: [2](#0-1) 

The `require_permission :read, :stack` check only validates that the token has the `read:stack` permission string in its `permissions` array — it never checks which specific stack the permission applies to: [3](#0-2) 

So the binding the rest of the API enforces — "the stack a token authorises == the stack it touches" — is broken specifically for this controller. A token created with `stack: some_stack_A` and `permissions: ['read:stack']` (the exact shape of the `here_come_the_walrus` fixture) is meant to only ever see `some_stack_A`, as confirmed by the existing test suite: [4](#0-3) 

But hitting `GET /api/stacks/*stack_id/ccmenu` with `stack_id` pointing at a *different* stack B, using that same token (`Authorization` header or the `token` query param CCMenu also accepts), succeeds and returns stack B's data because `CCMenuController#stack` never consults `current_api_client.stack_id`.

### Impact Explanation
This is a genuine authorization-scope escalation for an already-authenticated but narrowly-scoped API credential: a client meant to be restricted to a single stack can read deploy/build status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state, etc.) for every other stack in the Shipit instance. This matches the "escalation into … unauthenticated read of stack state" impact class — the token is not authorized to read that stack's state, yet the controller lets it.

### Likelihood Explanation
Likelihood is high wherever stack-scoped `ApiClient` tokens are issued (a documented, supported feature — see the `here_come_the_walrus` fixture and `stack.rb`'s `belongs_to :stack`). Any holder of such a restricted token — which by design is meant to be handed to less-trusted integrations (e.g., a single team's CI dashboard) — can enumerate other stacks' `to_param` values (`owner/repo/environment`, which are not secret) and pull their CCMenu XML.

### Recommendation
Make `CCMenuController#stack` respect the same scoping as the rest of the API, e.g. reuse `stacks.from_param!(params[:stack_id])` (from `BaseController`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is enforced consistently.

### Proof of Concept
1. Create two stacks, A and B.
2. Create an `ApiClient` scoped to stack A only: `ApiClient.create!(creator: user, name: 'ci', stack: stack_a, permissions: ['read:stack'])`.
3. Using that client's `authentication_token`, request `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu` (or with `?token=<authentication_token>`).
4. Observe a `200 OK` response containing stack B's CCMenu XML (build status, activity, etc.), despite the token only authorizing stack A — contrast with the same request made against, e.g., `Api::StacksController#show` for stack B, which correctly 404s for this token per [4](#0-3) .
