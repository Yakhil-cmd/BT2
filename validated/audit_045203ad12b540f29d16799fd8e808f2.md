Based on my investigation, I found a concrete analog: an uncapped, complexity-undercounted oracle-address list in the `data_feed`/`in_data_feed` oscript functions, mirroring the CVE's root cause (a single "valid" query/formula triggering disproportionate, unbounded server work that hangs/crashes the processing node).

### Title
Formula `data_feed`/`in_data_feed` oracle list is unbounded and complexity-uncounted, allowing a single AA trigger to force unbounded per-node work - (File: `formula/evaluation.js`, `formula/validation.js`, `data_feeds.js`)

### Summary
The `data_feed` and `in_data_feed` oscript functions accept an `oracles` parameter as a colon-separated string of addresses that is split with `.split(':')` and validated only for address format, with no upper bound on the number of addresses [1](#0-0) . Each address in that list triggers a separate, sequential key-value store scan via `dataFeeds.dataFeedExists`/`readDataFeedValue` (which iterate `arrAddresses` with `async.eachSeries`, each doing an independent LevelDB stream read) [2](#0-1) [3](#0-2) . Critically, the formula validator that assigns a fixed "complexity"/op cost to this call has the line that would scale cost with the number of oracle addresses explicitly commented out: `//complexity += addresses.length;` in both `validateDataFeed` and `validateDataFeedExists` [4](#0-3) [5](#0-4) . This means a single `data_feed[[...]]` call is charged only 1 complexity/op unit no matter how many oracle addresses are packed into the string, even though the actual runtime work (number of KV-store scans) scales linearly with the address count. By contrast, the equivalent light-client RPC path `readDataFeedValueByParams` explicitly caps oracle count at 10 [6](#0-5) , showing the limit was known to be necessary but was not applied to the oscript formula path used inside AA definitions.

### Finding Description
An AA author can define (and any unprivileged trigger sender can then invoke) an AA whose formula builds the `oracles` string dynamically from the AA's own definition/state so that it contains a very large number of colon-separated valid addresses, up to the limit of `MAX_AA_STRING_LENGTH`. Every time this formula runs (including inside `foreach`/`map`/function-call constructs, which are permitted and only charge complexity per call, not per embedded work), the AA executor performs one full KV-store scan per oracle address [7](#0-6) [8](#0-7) , and additionally an O(n) linear scan of all unstable unit messages in `storage.assocUnstableMessages` for the AA-specific fast path [9](#0-8) . Because the validator's complexity/op accounting (`MAX_COMPLEXITY`/`MAX_OPS`) does not scale with the number of oracle addresses, the static complexity gate that is supposed to bound the amount of work a formula can perform is bypassed for this specific construct, similar to how the MySQL optimizer bug (CVE-2024-20961) let a crafted-but-otherwise-valid query trigger disproportionate optimizer work leading to a hang/crash.

AA trigger execution is deterministic and must be reproduced identically by every full node to agree on the AA's state changes and response unit before the unit can be marked stable. A trigger designed to repeatedly invoke this call (bounded by `MAX_OPS`, e.g. tens/hundreds of times) each with a maximal oracle list packed into the allowed string length multiplies the number of KV-store scans a single trigger causes every validating node to perform.

### Impact Explanation
Because AA execution is mandatory and identical across all full nodes for consensus on unit validity/stability, a trigger that forces excessive KV-store scanning work can significantly slow down or stall processing of that unit on every node that validates it, delaying stabilization of the main chain around that point and, in the worst case, causing per-node hangs while the (single-threaded, callback-serialized) AA executor works through the scans. This matches the accepted impact category "a network unable to confirm new units" / "node disagreement on validity or stability" if some nodes time out or diverge in behavior while others do not, since there's no length-scaled complexity charge, timeout, or node-level cap tying the accepted-formula's complexity to its real cost.

### Likelihood Explanation
Exploitability requires only the ability to author/trigger an AA with a formula using `data_feed`/`in_data_feed` — an unprivileged capability documented as reachable in-scope for this exercise (AA definitions and triggers, oscript/ojson evaluation, data feeds). The formula validator (`formula/validation.js`) currently permits arbitrarily long oracle lists at cost 1, and the vulnerable lines (commented-out `complexity += addresses.length`) show this was foreseeably a design gap rather than a hardened, intentional limit.

### Recommendation
Reinstate and enforce `complexity += addresses.length` (or an equivalent op-count charge) in `validateDataFeed` and `validateDataFeedExists` in `formula/validation.js`, and/or add an explicit cap on the number of oracle addresses allowed in the `oracles` parameter of `data_feed`/`in_data_feed` (mirroring the existing `oracles.length > 10` cap already used in `readDataFeedValueByParams` in `data_feeds.js`), so that the complexity/ops budget actually bounds the amount of KV-store scanning work a single AA trigger can cause across every validating node.

### Proof of Concept
Not independently executed against a running node in this session; the PoC construction, based on code inspection, would be an AA whose formula computes:
```
$oracles = "<addr1>:<addr2>:...:<addrN>";   // N chosen to fill MAX_AA_STRING_LENGTH
data_feed[[oracles=$oracles, feed_name='x']]
```
repeated inside a `foreach`/function call up to the `MAX_OPS` limit, submitted as an AA trigger by any unprivileged wallet address. I was not able to confirm the exact numeric values of `MAX_AA_STRING_LENGTH`, `MAX_COMPLEXITY`, and `MAX_OPS` from `constants.js` within the available tool budget, nor whether an independent execution-time watchdog exists elsewhere that would abort excessively slow AA runs; these would need to be checked in a full Devin session to quantify the exact achievable amplification and confirm there is no compensating timeout.

function readDataFeedByAddress(address, feed_name, value, min_mci, max_mci, ifseveral, objResult, handleResult){
	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	var bAbortIfSeveral = (ifseveral === 'abort');
	var key_prefix;
	if (value === null){
		key_prefix = 'dfv\n'+address+'\n'+feed_name;
	}
	else{
		var prefixed_value;
		if (typeof value === 'string'){
			var float = string_utils.toNumber(value, bLimitedPrecision);
			if (float !== null)
				prefixed_value = 'n\n'+string_utils.encodeDoubleInLexicograpicOrder(float);
			else
				prefixed_value = 's\n'+value;
		}
		else
			prefixed_value = 'n\n'+string_utils.encodeDoubleInLexicograpicOrder(value);
		key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value;
	}
	var options = {
		gte: key_prefix+'\n'+string_utils.encodeMci(max_mci),
		lte: key_prefix+'\n'+string_utils.encodeMci(min_mci),
		limit: bAbortIfSeveral ? 2 : 1
	};
	var handleData = function(data){
		if (bAbortIfSeveral && objResult.value !== undefined){
			objResult.bAbortedBecauseOfSeveral = true;
			return;
		}
		var mci = string_utils.getMciFromDataFeedKey(data.key);
		if (objResult.value === undefined || ifseveral === 'last' && mci > objResult.mci){
			if (value !== null){
				objResult.value = string_utils.getValueFromDataFeedKey(data.key);
				objResult.unit = data.value;
			}
			else{
				var arrParts = data.value.split('\n');
				objResult.value = string_utils.getFeedValue(arrParts[0], bLimitedPrecision); // may convert to number
				objResult.unit = arrParts[1];
			}
			objResult.mci = mci;
		}
	};
	kvstore.createReadStream(options)
	.on('data', handleData)
	.on('end', function(){
		handleResult(objResult.bAbortedBecauseOfSeveral);
	})
	.on('error', function(error){
		throw Error('error from data stream: '+error);
	});
}
