### Title
`StatusHandler#process` matches commits by `sha` alone, letting a webhook for one repository write GitHub statuses onto another repository's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no filter on the owning stack's repository. Any `status` webhook payload that is validly signed for the sender's own repository/organization can therefore create a `Status` row on a `Commit` belonging to a completely different stack/repository, as long as the two repos happen to share a commit `sha`.

### Finding Description
The binding that should hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` a webhook payload is allowed to mutate. In `StatusHandler#process`: [1](#0-0) 

the query `Commit.where(sha: params.sha)` is global across the entire `commits` table — it is never scoped to `Repository.from_github_repo_name(repository_name)` or to `stacks`, unlike the base `Handler#stacks` helper which does perform that scoping: [2](#0-1) 

`StatusHandler` simply never uses `stacks`/`repository_name` at all, so the repository-scope guard that exists elsewhere in the codebase (e.g. `PullRequest::ClosedHandler`, `LabeledHandler`, which look up `Repository.from_github_repo_name(params.repository.full_name)` before touching records) is absent here.

`WebhooksController#verify_signature` only proves the payload was signed by the GitHub App for `repository_owner` (the org named in the payload) — it says nothing about which `sha` values the sender is authorized to reference: [3](#0-2) 

So an attacker who owns/controls a repository connected to the same Shipit instance (a legitimate, if unprivileged, "GitHub App installed on their own repo" scenario) can send a real, validly-signed `status` event from their own repo but set `sha` to a value that also exists as a `Commit` on a victim stack (trivially achievable by forking a public target repo, since forked commits retain identical SHA-1 hashes). `Commit.where(sha: ...)` matches both the attacker's own commit and the victim's commit, and `create_status_from_github!` is invoked on all of them, injecting a forged CI status (e.g., a fake `success`) into the victim stack's commit history.

### Impact Explanation
This is a cross-repository record mutation: a webhook authenticated only for repository A causes a `Shipit::Status` row to be written against a `Commit` owned by repository B's stack. Since commit/status state feeds directly into merge-queue and deploy eligibility logic (`add_status` schedules `stack.schedule_merges`, emits `deployable_status`/`commit_status` hooks), a forged "success" status can make an otherwise-blocked commit appear deployable, or a forged "failure"/"error" can block a legitimate deploy — matching the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any repository sharing a discoverable commit SHA with the attacker's own connected repository (most easily via forks of public repos), and can be replayed for every subsequent identical webhook.

### Likelihood Explanation
Preconditions: attacker needs at least one repository connected to the same Shipit installation that they control (to receive a validly-signed webhook for it), and needs a commit `sha` that is shared with the target stack — trivially satisfied by forking the public target repository (git preserves commit hashes across forks) or by knowing/guessing a shared sha in monorepo/template scenarios. No Shipit credentials, session, API token, or GitHub App secret are required beyond what the attacker already legitimately has for their own connected repo. This is low-cost and fully repeatable.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to only commits belonging to stacks of the repository named in the payload, mirroring the pattern used by other handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(stack: :repository).merge(stacks).where(sha: params.sha)`, using the existing `stacks` helper from `Handler`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook for repository A does not create a status on repository B's commit with the same sha" do
  repo1 = shipit_repositories(:shipit)
  repo2 = create_repository(name: 'other', owner: 'other-owner')
  stack1 = create_stack(repository: repo1)
  stack2 = create_stack(repository: repo2)

  shared_sha = 'a' * 40
  commit1 = stack1.commits.create!(sha: shared_sha, ...)
  commit2 = stack2.commits.create!(sha: shared_sha, ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => repo1.full_name },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # binding under test: commit.stack.repository.full_name == payload['repository']['full_name']
  assert_equal repo1.full_name, commit1.stack.repository.full_name  # true, expected
  assert_empty Shipit::Status.where(commit_id: commit2.id)          # FAILS on current code: a Status row is created
end
```
This currently fails because `StatusHandler#process` writes a `Status` for `commit2` even though the webhook's `repository.full_name` is `repo1.full_name`, not `repo2.full_name`.
