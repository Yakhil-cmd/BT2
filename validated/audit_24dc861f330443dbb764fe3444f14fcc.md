### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the affected repository/stack is looked up from the unverified `repository.full_name` field, allowing a cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit` supports hosting multiple GitHub organizations under one instance, each with its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC against using a value taken straight from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and only checks that the signature is valid for *that* organization's secret [2](#0-1) . However, once the signature check passes, every downstream `Handler` determines which repository/stack to act on using a *different, still-unverified* field of the same JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . Nothing ties these two fields together, and the HMAC signature covers the whole raw body but only proves that *some* configured organization's secret produced it — not that the org whose secret matched is actually the owner of the repository named elsewhere in the same payload.

### Finding Description
The verified binding should be: `organization whose webhook_secret authenticated the request == organization that owns the repository/stack being acted upon`. The code instead computes these two values from two independent, attacker-controlled JSON paths in the same request body:

- Signature org: `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) [4](#0-3) 
- Acted-upon repository: `payload.dig('repository', 'full_name')` [3](#0-2) 

`Shipit.github(organization:)` looks up per-org config (`github_app_config`) by exact organization key and raises only if the org is *unknown* to this Shipit instance, not if it mismatches the repository named elsewhere in the payload [5](#0-4) .

Concretely, an actor who is a legitimate administrator of `org-b` (a second organization configured in the same multi-tenant Shipit instance, with a `webhook_secret` they know because they configured it themselves) can craft a payload where:
- `repository.owner.login = "org-b"` and `organization.login = "org-b"` (so `verify_signature` looks up and validates against `org-b`'s known secret — this check passes because they control that secret),
- but `repository.full_name = "org-a/victim-repo"` (a repository they have no access to, belonging to a different, unrelated organization tracked by the same Shipit install).

`PushHandler`, and every other handler, resolve the target purely from `full_name` via `Repository.from_github_repo_name(repository_name)` [6](#0-5) [7](#0-6) , so the forged event is processed as a legitimate GitHub-originated event for `org-a/victim-repo`, even though the signature only proved knowledge of `org-b`'s secret.

### Impact Explanation
This breaks the trust boundary between tenants of a multi-organization Shipit deployment: signing with organization B's webhook secret should only authorize events for organization B's repositories, but it is accepted for events naming any repository tracked anywhere in the instance. Depending on the handler triggered, this can:
- Force a `GithubSyncJob` for the victim's `push` event, which resyncs commits/branch state and can trigger auto-deploys (`stack.sync_github`) [7](#0-6) .
- Inject fabricated `status`/`check_run` results that influence `deployable_status`/merge gating for the victim stack.
This constitutes an unauthorized cross-repository/cross-organization write into another tenant's stack state, meeting the "cross-repository writes" / "unauthorized deploy" impact bar, without the attacker ever holding a Shipit session, API token, or write access to the victim repository.

### Likelihood Explanation
Requires the deployment to be configured for multiple GitHub organizations (the multi-org `secrets.github` schema documented in `docs/setup.md` and supported by `github_app_config`) and for the attacker to control (be an admin/owner of) at least one of those onboarded organizations — which is plausible for shared/internal Shipit instances serving several teams or business units, none of which should be able to affect each other's repositories. No access to the victim org, no Shipit account, and no GitHub App private key are required — only the attacker's own org's `webhook_secret`, which they legitimately possess.

### Recommendation
After signature verification, re-derive (or cross-check) the organization from the *same* field used to route the event (`repository.full_name`'s owner segment, or `repository.owner.login`) and reject the request (422) if it does not match the organization whose secret validated the signature. Alternatively, look up the `Repository`/`Stack` by `full_name`, then verify the signature specifically against *that* repository's owning organization's configured secret rather than trusting `repository.owner.login`/`organization.login` as the selector before the repository is resolved.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (multi-org schema, see `docs/setup.md`).
2. As an authorized admin of `org-b`'s GitHub App/webhook, compute `sha1=HMAC(org-b-secret, body)` for a crafted body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": {"login": "org-b"},
    "full_name": "org-a/victim-repo"
  },
  "organization": {"login": "org-b"}
}
```
3. `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `repository_owner` = `"org-b"`, fetches `org-b`'s `GitHubApp`, and the signature matches — request is accepted [8](#0-7) .
5. `PushHandler` resolves `repository_name` = `"org-a/victim-repo"` from the same body and enqueues `GithubSyncJob` for the victim stack [7](#0-6) , even though the request was never signed by `org-a`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```
