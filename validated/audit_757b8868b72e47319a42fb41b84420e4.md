### Title
Webhook signature verified against the organization named in the (untrusted) payload rather than against the repository the event actually acts upon - allows cross-repository forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multiple independent GitHub App installations, each bound to its own organization and its own `webhook_secret` (see the multi-tenant config in `test/dummy/config/secrets_double_github_app.yml`, which defines separate `OrgOne` / `OrgTwo` entries each with `app_id`, `installation_id`, and `webhook_secret`). When a webhook is received, `WebhooksController` picks which of these per-organization secrets to verify the payload against by reading the organization name **out of the untrusted request body itself**, not from any authenticated channel. The subsequent event handlers, however, act on the repository named by `repository.full_name` in the same untrusted body, which is a value never bound to (or cross-checked against) the value that was used to select the signing secret.

### Finding Description
`WebhooksController#verify_signature` computes which GitHub App/secret to validate against like this: [1](#0-0) 

and `repository_owner` is derived purely from the JSON payload: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app/secret keyed by that organization name (as configured per-org in `secrets_double_github_app.yml`). Crucially, `verified = ... head(422) unless verified` does not halt request processing (no `return`) — but more fundamentally, the *selection* of which secret is authoritative is itself computed from attacker-controlled JSON (`repository.owner.login`, or `organization.login` as fallback), before that same JSON's `repository.full_name` field is later used by the event handlers (e.g. the push handler that queues `GithubSyncJob` for the `Stack` matching the repository) to determine which `Stack`/repository the event is applied to.

Because the organization used to *authenticate* the payload and the repository used to *act on it* are read from two different, independently attacker-forgeable fields of the same unauthenticated JSON body, an attacker who legitimately controls a GitHub App installation on their own organization (and therefore legitimately knows that organization's `webhook_secret`) can craft a payload where:
- `repository.owner.login` (or `organization.login`) = the attacker's own org, so `verify_signature` selects the attacker's own known secret and the HMAC check passes, and
- `repository.full_name` = a victim org/repo that Shipit tracks as a `Stack`,

producing a request that passes signature verification yet is processed by handlers as an event belonging to the victim's repository/stack. This is the same class of bug as the reported one: a payload field (`full_name`) that is *acted on* is never covered by the field (`owner.login`) that the *trust decision* (signature verification) is actually bound to.

### Impact Explanation
A forged webhook accepted this way lets an unprivileged outsider (who only needs to control their own, legitimately-installed GitHub App) inject GitHub-originated events — pushes, statuses, check-suite results, pull_request events, merge/lock signals — into a victim `Stack` they do not own. Depending on the handler, this can trigger `GithubSyncJob`, fabricate commit `Status` rows that feed into deployability checks, or drive merge-queue/review-stack state, ultimately influencing whether an unauthorized deploy/merge proceeds on the victim's stack. This crosses the "authentication versus repository written" trust boundary explicitly called out as in-scope.

### Likelihood Explanation
Requires only that the attacker operate their own GitHub organization with a GitHub App installed and configured for the same multi-tenant Shipit instance (a scenario the codebase explicitly supports, per the double-app secrets fixture), no privileged access to the victim's repository, org, or Shipit account is needed. The signature check itself is bypassed by design, not broken cryptographically.

### Recommendation
Do not let the payload determine which secret is authoritative for the payload. Instead:
- Verify the webhook signature against the secret of the GitHub App installation that Shipit itself expects to deliver events for the `repository.full_name` / `Stack` in question (looked up from Shipit's own configuration/DB record of which org owns which repo), not from `repository.owner.login`/`organization.login` taken from the request.
- Alternatively, after verification, assert that `repository.owner.login` (used for the signature lookup) matches the owner embedded in `repository.full_name` before any handler is allowed to act, rejecting mismatches.

### Proof of Concept
1. Attacker configures/owns a GitHub App on `AttackerOrg`, with Shipit multi-tenant config entry `AttackerOrg: { webhook_secret: S, ... }`.
2. Attacker crafts a `push` (or other handled) event JSON body with:
   - `repository.owner.login` = `"AttackerOrg"`
   - `repository.full_name` = `"victim-org/victim-repo"` (a repo Shipit tracks via a `Stack`)
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S, body)` using their own known secret `S`.
4. POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` looks up `Shipit.github(organization: "AttackerOrg")`, verifies successfully against `S`, and the request proceeds to `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }`, which resolves and acts on the `Stack` for `victim-org/victim-repo`, per `app/controllers/shipit/webhooks_controller.rb:10-15`.
