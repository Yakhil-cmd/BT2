### Title
Webhook signature is verified against `repository.owner.login` while the mutated `Stack` is selected via `repository.full_name`, letting a payload "signed by org-A" mutate org-B's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` resolves the `GitHubApp` (and therefore the `webhook_secret` used to validate the HMAC) from `params.dig('repository','owner','login')` (or `organization.login`), but `Handler#stacks` resolves the target `Stack`/`Repository` from the independent `payload.dig('repository','full_name')` field. Because the attacker crafts the raw POST body themselves rather than relying on GitHub to keep these two fields consistent, they can make the two fields diverge, passing signature verification under an organization they control while writing to a `Stack` owned by a victim organization.

### Finding Description
The claimed binding is: `organization(secret used to verify HMAC) == organization(owner of Stack mutated by handler)`. Tracing the code shows this is false by construction.

- `verify_signature` looks up the signing organization purely from attacker-supplied JSON: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then `Shipit.github(organization: repository_owner).verify_webhook_signature(header, raw_post)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` just HMAC-SHA1s the raw request bytes with whatever `webhook_secret` was configured for that resolved organization. [3](#0-2) 
- Once past that gate, `Handler#stacks` (used by `PushHandler#process`) resolves the target repository/stacks from a **different** field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. [4](#0-3) 
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every `not_archived` stack on that branch, for whatever repository `full_name` named. [5](#0-4) 

Nothing in this path checks that `repository.owner.login` (used for signing) matches the owner encoded in `repository.full_name` (used for the write). Since the request is a raw HTTP POST to `/webhooks` fabricated by the attacker - not a real GitHub-relayed webhook where GitHub itself guarantees these fields describe the same repo - the attacker is free to set them independently: `repository.owner.login = "org-A"` (an org they control and for which they therefore know the configured `webhook_secret`) and `repository.full_name = "org-B/victim-repo"` (the victim stack they want to mutate). The HMAC is computed over the entire raw body including the mismatched `full_name`, but that's fine because the attacker knows org-A's secret and simply signs whatever bytes they send.

None of the listed guards close this gap: `drop_unhandled_event` only checks the event type exists as a handler; `ExplicitParameters` (`params do requires :ref; requires :after end`) only validates presence/shape of `ref`/`after`, not repository ownership consistency; there is no `force_github_authentication`, `User#authorized?`, or `stacks` scope check involved in the webhook path at all - it's server-to-server and pre-session.

### Impact Explanation
A successful request causes `Stack#sync_github` to run against org-B's stack with an attacker-chosen `expected_head_sha`, seeding an attacker-named commit SHA as the expected head to deploy on a tenant the attacker never authenticated against. This is a cross-tenant authenticated-boundary bypass: a payload for one organization's webhook credential mutates another organization's `Stack`/`Commit` state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any `not_archived` stack whose `branch` and repository `full_name` the attacker can guess/know, across arbitrarily many victim organizations, as long as the attacker holds a valid `webhook_secret` for at least one configured organization (including their own).

### Likelihood Explanation
Preconditions: Shipit must have at least two `GitHubApp` configurations (multi-tenant setup, which is exactly the deployment model this app supports), and the attacker needs to know a `webhook_secret` for at least one configured organization - trivially true if the attacker is a legitimate operator of their own onboarded org (they can see/set their own webhook secret in their GitHub org settings, since Shipit's GitHub App integration typically has the org admin configure the shared secret). No GitHub-side interaction is required at all; the attacker sends a raw HTTP POST directly to the Shipit host's `/webhooks` endpoint with a hand-crafted JSON body and a correctly computed `X-Hub-Signature` header using their own known secret. This requires no session, no API token, no private keys of the victim, and is fully repeatable.

### Recommendation
Verify the webhook signature using the same repository identity that is used to select the mutated `Stack`. Concretely, derive `repository_owner` from `repository.full_name`'s owner segment (or cross-check that `repository.owner.login` matches the owner parsed out of `repository.full_name`) before calling `Shipit.github(organization:).verify_webhook_signature`, and reject the request (422) if they diverge. Alternatively, resolve the `Stack`/`Repository` for mutation using the same `repository_owner` value that was authenticated, not a separately-read field of the same untrusted payload.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` style (no live GitHub):
1. Configure two `GitHubApp`s in `Shipit.github_apps`/config: `org-a` with `webhook_secret: 'secret-a'`, `org-b` with `webhook_secret: 'secret-b'`.
2. Create `Repository` owned by `org-b` (e.g. `org-b/victim-repo`) and a `Stack` on branch `main` for it, `archived: false`.
3. Build a raw JSON body: `{"ref":"refs/heads/main","after":"<attacker-chosen-sha>","repository":{"owner":{"login":"org-a"},"full_name":"org-b/victim-repo"}}`.
4. Compute `X-Hub-Signature` as `"sha1=" + OpenSSL::HMAC.hexdigest('sha1', 'secret-a', raw_body)`.
5. `POST /webhooks` with headers `X-Github-Event: push` and the above signature, and this raw body.
6. Assert response is `200 OK` (signature accepted because it was checked against `org-a`'s secret, `repository_owner == 'org-a'`).
7. Stub/mock `Stack#sync_github` on the `org-b` stack and assert it was invoked with `expected_head_sha: '<attacker-chosen-sha>'` — demonstrating `organization(secret verified) = "org-a" != organization(stack mutated) = "org-b"`, confirming the binding is broken.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
