This confirms the analog: in ocore's oscript formula evaluator, arithmetic operators explicitly coerce a `boolean` result into a `Decimal` (`res ? dec1 : dec0`, i.e. `false → 0`), and `with_selectors`/`selectSubobject` silently returns plain `false` (not a fatal error) when a key does not exist in a `params`/state/getter-returned object. This exactly mirrors the reported bug class: code written against one interface (expected field names such as `COLAT_ADDRESS`/`PRICE_FEED`) silently receives a default/zero value instead of a hard failure when the real interface (the actual `base_aa`/getter/state) doesn't expose that field.

### Title
Silent `false`→`0` coercion on missing `params`/state/getter keys enables interface-mismatch fund manipulation in parameterized AAs - (File: formula/evaluation.js)

### Summary
`selectSubobject()` in `formula/evaluation.js` returns plain `false` (not a fatal error) when a selector key does not exist on an object, and arithmetic operators (`+`, `-`, etc.) explicitly convert a boolean into `Decimal(0)`/`Decimal(1)` before computing. Consequently, if a base AA's oscript formula references a `params.<name>` (or a state var / remote-getter field) that a caller/parameterized AA does not actually supply — the oscript equivalent of "the interface doesn't have this member" — the missing lookup does not abort, it silently becomes `0` (or `false`) and the computation proceeds with an unintended value, exactly like the reported Solidity bug where `COLAT_ADDRESS`/`PRICE_FEED` didn't exist on the vault interface and the call silently proceeded with wrong data instead of reverting.

### Finding Description
Autonomous Agents in ocore support template/`base_aa` composition: a "parameterized AA" supplies a `params` object that the base AA's formulas reference via `params.<key>`. This is functionally the same trust boundary as a proxy/interface call in the reported Solidity bug — the base AA's code is written assuming a certain "interface" (a fixed set of param/state names), but the actual caller (the parameterized AA definition, or an upgraded/different base AA) may not supply a member with that name, or supply it under a different name. [1](#0-0) 

When such a missing key is looked up via `with_selectors` (e.g. `params.fee`, `stateVar.subfield`, or a remote getter's returned object field), `selectSubobject()` treats "no such key in data" as a plain miss and calls `cb(false)` rather than raising a fatal/validation error: [2](#0-1) 

That `false` is not surfaced to the user as an error — it flows on as a normal oscript value. When later used inside an arithmetic expression (e.g. `trigger.output[[asset=base]] - params.fee`, or a price/collateral computation using a missing feed/param), the evaluator explicitly coerces booleans to `Decimal` zero/one before performing the operation: [3](#0-2) 

This is structurally identical to the reported class of bug: a function/interface member (`COLAT_ADDRESS`, `PRICE_FEED`) that the calling code assumes exists is actually absent on the real target, and instead of the call failing loudly, it silently resolves to a default/zero value, and the code continues operating on that wrong value (e.g., collateral address defaults to zero-value, computed price defaults to zero).

### Impact Explanation
If a base AA is (re)used by multiple parameterized AAs, or a base AA's code is updated/deployed expecting new `params`/state keys that some already-deployed parameterized AAs never supplied (an interface mismatch, analogous to the reported vault ABI mismatch), the base AA's formulas will silently treat the missing field as `0`/`false` rather than bouncing. Depending on how that field is used (fee subtraction, collateral price/threshold, payout amount conditionals), this can cause the AA to pay out more bytes/assets than intended (effectively waiving fees), miscompute solvency/liquidation conditions, or otherwise let a trigger sender manipulate AA fund flows by deliberately choosing/observing which base AA + params combination yields a "missing key ⇒ 0" outcome. This can result in AA fund loss.

### Likelihood Explanation
Exploitability requires a specific AA author/design pattern (base_aa + params architecture, or state vars/remote getters referenced by name) where a numeric field can be legitimately absent and its absence is not explicitly checked with `exists()`/`is_valid_amount()` before use. Given `exists()` is available specifically to distinguish "value not present" from real 0, well-written AAs mitigate this, but the underlying language semantics silently normalize missing values to falsy/zero rather than erroring, so any AA author who assumes a stricter "must revert on missing interface member" semantic (as the external report criticizes) is at risk once a base_aa/param naming mismatch occurs (e.g., through AA reuse, upgrade of a shared base AA, or a typo in `params` keys of a newly deployed parameterized AA instance). Reachability is via an ordinary AA-trigger sender/AA author, no privileged role needed.

### Recommendation
Require AA authors to use `exists()`/explicit presence checks (already provided in the language, see `case 'exists'`) before consuming `params.*`/state/getter fields that are semantically required, and consider adding a stricter mode/lint warning in `aa_validation.js` when a required-looking field in a formula (used in arithmetic/address context) has no accompanying `exists()`/`typeof` guard, so interface mismatches between a base AA and its parameterized instances fail validation or bounce instead of silently defaulting to `0`/`false`.

### Proof of Concept
1. Deploy a base AA `B` whose payment formula is `outputs: [{address: trigger.address, amount: "{trigger.output[[asset=base]] - params.fee}"}]`, intending every parameterized instance to define `params.fee`.
2. Deploy a parameterized AA `P` with `base_aa: B` but `params: { fee_typo: 2000 }` (wrong key name — i.e., an "interface mismatch" identical in spirit to `COLAT_ADDRESS`/`PRICE_FEED` not existing on the vault).
3. Send a trigger to `P`. `params.fee` resolves via `selectSubobject` to `false` (per `formula/evaluation.js:2908-2946`), which the subtraction operator coerces to `Decimal(0)` (per `formula/evaluation.js:336-356`), so the AA pays out the full trigger amount with zero fee deducted, instead of bouncing due to a missing required parameter.
