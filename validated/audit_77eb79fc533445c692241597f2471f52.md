### Title
Stack-scoped ApiClient token bypasses its stack authorization in `CCMenuController#stack` - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve the target stack from the raw `Stack` collection instead of the token-scoped `stacks` collection defined in `BaseController`, letting a `read:stack` token that was issued for one specific stack read the CI status of *any* stack in the installation.

### Finding Description
`Api::BaseController` enforces a binding between an `ApiClient`'s `stack_id` and the stacks it may touch: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

If an `ApiClient` record has a `stack_id` set (as the `here_come_the_walrus` fixture does, scoped to the `shipit` stack with `read:stack` permission), `stack` can only ever resolve to that one stack — this is how the rest of the API (e.g. `Api::TasksController`, `Api::StacksController`) enforces "token authorizes stack A" == "token touches stack A".

`Api::CCMenuController`, however, overrides `stack` and bypasses this scoping entirely: [2](#0-1) 

```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only checks that `"read:stack"` is present in `current_api_client.permissions` via `ApiClient#check_permissions!`: [3](#0-2) 

```
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

This is exactly the same bug class as `OperatorVCS::removeVault`: a scoping/authorization mapping (`ApiClient.stack_id` ↔ the stack a request may act on) exists and is enforced in one code path (`BaseController#stack`), but a sibling code path (`CCMenuController#stack`) re-implements the same "resolve stack" step without re-applying that mapping — the equivalent of `vaultMapping[vault]` never being flipped to `false`. The binding broken is: *the stack a token authorises* (`current_api_client.stack_id`) *≠ the stack it actually touches* (`params[:stack_id]` resolved against `Stack.all`).

### Impact Explanation
Any holder of a legitimately-issued, narrowly stack-scoped `read:stack` `ApiClient` token (e.g. a CI system given read-only access to one stack's build status via `CCMenuUrlController`/`ApiClient.create_with(permissions: %w[read:stack])`, or any admin-issued scoped token) can use that same token to query `GET /api/stacks/:any_stack/ccmenu.xml` for *every other stack in the installation*, not just the one it was authorized for. This discloses stack build/deploy status information (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock status) for stacks the token was never granted access to — an unauthorized read of stack state across a trust boundary the token system is explicitly designed to enforce. This matches the "High" impact bucket: unauthenticated/unauthorized read of stack state.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped API tokens (the engine ships fixtures and helper flows, e.g. `CCMenuUrlController`, specifically to create such tokens) and mounts `Api::CCMenuController` as documented — no privileged access, TLS interception, or social engineering is required, only possession of one legitimately scoped token and knowledge/guessing of another stack's slug/param.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the scoped `stacks` collection from `BaseController`) so the same stack_id-based authorization enforced everywhere else in the API is applied consistently:

```diff
 def stack
-  @stack ||= Stack.from_param!(params[:stack_id])
+  @stack ||= stacks.from_param!(params[:stack_id])
 end
```

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack: <stack_A>` (mirrors fixture `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml`).
2. Authenticate with that token via Basic Auth (or `?token=`) against `GET /api/stacks/:stack_B_param/ccmenu.xml`, where `stack_B` is a different stack the token was never scoped to.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!` directly instead of `stacks.from_param!`, `require_permission :read, :stack` only checks the permission string (not the stack id), and the request succeeds, returning `stack_B`'s CCMenu status/build data — despite the token being authorized only for `stack_A`.
