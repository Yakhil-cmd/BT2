### Title
Webhook signature verification is bound to `repository.owner.login` while the handler acts on `repository.full_name`, allowing cross-tenant stack archival - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb, app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb)

### Summary
`WebhooksController#verify_signature` derives `repository_owner` solely from `params.dig('repository','owner','login')` to select which org's `webhook_secret` validates the HMAC signature, but `ClosedHandler`/`ReviewStackAdapter#archive!` resolve and mutate the target `Repository`/`ReviewStack` using the independently attacker-controlled `repository.full_name` field. Because these two JSON fields are never checked for consistency, an attacker who legitimately controls one org's `webhook_secret` can sign a `pull_request` `closed` payload with their own org's login in `repository.owner.login` while setting `repository.full_name` to `victim-org/victim-repo`, causing the victim's real `ReviewStack` to be archived/deprovisioned.

### Finding Description
The broken binding: `params.dig('repository','owner','login')` (used in `repository_owner` for signature selection) must equal the owner segment of `params.dig('repository','full_name')` (used by the handler to find the target repo/stack) — but this equality is never enforced.

- `WebhooksController#verify_signature` computes `repository_owner` from `repository.owner.login` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, using that org's `webhook_secret` to validate the HMAC signature over the raw JSON body. [2](#0-1) 

- Once verification passes, the full parsed `params` (including the attacker-controlled `full_name`) is dispatched unchanged to `ClosedHandler`. [3](#0-2) 

- `ClosedHandler#repository` resolves the repository purely from `params.repository.full_name`, via `Shipit::Repository.from_github_repo_name`, then calls `review_stack.archive!`. [4](#0-3) 

- `Repository.from_github_repo_name` looks up the DB record purely by the owner/name parsed out of that string, with no reference to which org's secret verified the request. [1](#0-0) 

- `ReviewStackAdapter#archive!` then deprovisions and archives whatever stack was found in that scope, using `params.sender.login` (also attacker-controlled) as the acting user. [5](#0-4) [6](#0-5) 

Exploit flow: In a multi-tenant deployment (`Shipit.github_apps` configured per-organization, as documented for "Using Multiple Github Applications"), the attacker registers/owns org `A` and knows its `webhook_secret`. They craft a `pull_request` `closed` JSON body with `repository.owner.login = "A"` (so `verify_signature` selects org A's real secret and the HMAC checks out) but `repository.full_name = "victim-org/victim-repo"` and a `number` matching an existing PR/environment for the victim's `ReviewStack`. They compute the HMAC over this exact body using org A's secret and POST it to `/webhooks` with the correct `X-Hub-Signature` and `X-Github-Event: pull_request` headers. The signature check passes because it only ever inspects `repository.owner.login`, never comparing it to `full_name`. The `ClosedHandler` then resolves the real victim `Repository`/`ReviewStack` from `full_name` and archives/deprovisions it.

No other guard closes this gap: `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema on `ClosedHandler` only requires `repository.full_name` and `sender.login` be strings, it does not require or check `repository.owner.login` at all; there is no model validation or scope tying the resolved `Repository` to the verifying organization.

### Impact Explanation
This is a cross-tenant stack mutation: a payload cryptographically valid only for org A causes a real record write (archive + deprovision) against org B's `ReviewStack`, without org A ever having any relationship, membership, or permission on org B's repository. This matches the "payload for one repository mutating another's stack" Critical category. The attack is repeatable against any PR number/environment for any victim repository hosted on the same multi-tenant Shipit instance, as long as the attacker can guess or observe the victim's `full_name` and an active PR number (both are typically public/observable on GitHub).

### Likelihood Explanation
Requires: (1) the Shipit instance configured with `Shipit.github_apps`/multiple orgs sharing one instance (documented, supported configuration), and (2) attacker legitimately owns/controls one of those orgs' GitHub App registrations and thus its real `webhook_secret` — both explicitly granted under the stated attacker model. Given those, the attack costs only computing an HMAC-SHA1 over an attacker-crafted JSON body and one HTTP POST; it is fully repeatable and requires no interaction with the victim or any secret belonging to them.

### Recommendation
In `WebhooksController#verify_signature` (or in each handler, e.g. `ClosedHandler`, `OpenedHandler`, `LabeledHandler`, etc.), enforce that `params.dig('repository','owner','login')` equals the owner segment parsed from `params.dig('repository','full_name')` before processing; reject the request (422) on mismatch. Alternatively, derive `repository_owner` used for org/secret selection directly from `full_name`'s owner segment rather than from the separate `owner.login` field, so the two values cannot diverge.

### Proof of Concept
Minitest plan (e.g., in a webhooks/handler test file under `test/`):
1. Configure two orgs (`OrgA`, `OrgB`) in `Shipit.github_apps` with distinct `webhook_secret`s (mirroring `test/dummy/config/secrets_double_github_app.yml`).
2. Create `Repository` `OrgB/victim-repo` with an existing `ReviewStack` for PR number `N` (environment `prN`), owned by `OrgB`.
3. Build a `pull_request` `closed` JSON body where `repository.owner.login == "OrgA"` and `repository.full_name == "OrgB/victim-repo"`, `number == N`.
4. Sign the exact raw JSON with `OrgA`'s real `webhook_secret` (HMAC-SHA1), set `X-Hub-Signature` header, POST to `/webhooks` with `X-Github-Event: pull_request`.
5. Assert response is `:ok` (signature accepted) — i.e., `repository.owner.login` (`"OrgA"`) equals the org whose secret verified the request, satisfying side one of the binding.
6. Assert `Shipit::Repository.find_by(owner: "orgb", name: "victim-repo").review_stacks.find_by(environment: "prN").reload.archived?` is `true` — i.e., the owner segment of `repository.full_name` (`"OrgB"`) differs from the verifying org (`"OrgA"`), proving the equality is violated and the victim's stack was archived using org A's signature alone.

      verified = github_app.verify_webhook_signature(
