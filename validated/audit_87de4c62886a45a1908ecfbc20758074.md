### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from one repository mutate commit status for a same-SHA commit belonging to any other stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)`, with no filter tying the update to the repository/owner that authenticated the webhook. On a Shipit instance with multiple stacks (including auto-provisioned review stacks for repositories with `provision_on_pull_request`/similar flags), if a commit SHA is shared between two different `Stack` records — which is a normal git occurrence for forked/branched history rather than a hash collision — a legitimately-signed webhook for one repository will silently write a `Status` row onto the *other* stack's commit, potentially flipping the `review/approved`-style required status and unblocking a ship/merge/block decision.

### Finding Description
The broken binding: the intended invariant is `commit.stack.repository == webhook.repository` for every `Status` created from a `status` webhook. The actual code enforces no such equality: [1](#0-0) 

`process` iterates `Commit.where(sha: params.sha)` — a global, cross-stack, cross-repository query on the shared `commits` table — and calls `commit.create_status_from_github!(params)` on every match, without ever checking `params.dig('repository', ...)`, `commit.stack.repository`, or `commit.github_repo_name`. `Commit` belongs to a `Stack` (which in turn belongs to a `Repository`), and rows are not deduplicated by repository: [2](#0-1) 

`WebhooksController#verify_signature` only proves that the payload was signed for the *organization owning the request's `repository_owner`* — it says nothing about which `Commit` rows the handler is permitted to touch: [3](#0-2) 

So the guard that exists (`verify_signature`) authenticates "this event genuinely came from GitHub for repo X," but the handler itself performs no authorization/scoping step of "and therefore may only affect stacks belonging to repo X." Since `sha` is attacker-controlled input inside an otherwise-legitimate webhook, and the `commits` table is shared globally across all stacks/repositories tracked by the Shipit instance, any commit SHA that happens to coincide across two different `Stack` rows (e.g., a shared ancestor commit between a mainline stack and an auto-provisioned review stack, or between two repositories that share history/mirrors) causes the status write to leak across the boundary.

Combined with `Repository#review_stacks_enabled?`/PR auto-provisioning flags [4](#0-3)  which cause external pull requests to auto-create review stacks that execute `shipit.yml`, a spoofed/incidental `review/approved` (or any required) status landing on the wrong stack's commit can flip that stack's deployability via `Commit#deployable?`/`#blocked?` and trigger `stack.schedule_merges` inside `add_status`: [5](#0-4) 

### Impact Explanation
A status payload that is authenticated only for the attacker's own repository/org can create or overwrite a `Status` record for a commit belonging to an unrelated stack, if that commit's SHA is also present in the attacker-controlled repository's history. This can flip a required check (e.g. `review/approved`) from failing to passing (or vice versa) on the victim stack, altering `deployable?`/`blocked?` and triggering `schedule_merges`/continuous delivery — i.e., "a payload for one repository mutating another's stack/commit," which the ruleset classifies as Critical (unauthorized deploy/merge/block). The blast radius is bounded by the practical requirement of a shared SHA between the attacker's repo and the victim stack's commit history; it is not an unconditional "any SHA, any repo" write.

### Likelihood Explanation
Exploitability requires:
- A Shipit instance with multiple stacks and review-stack auto-provisioning enabled for a repository the attacker can open PRs against.
- A genuine SHA collision between a commit already recorded in the victim stack and a commit reachable/provable by the attacker's own repository (e.g. shared history/ancestor commit, monorepo mirrors, or repos forked from a common base) — this is achievable without a cryptographic hash break, but it is a specific structural condition, not automatically true for "any SHA the attacker names."
- The attacker still needs a validly signed webhook, which they get "for free" by triggering real GitHub events (e.g. their own CI posting a status) on a repository/org already connected to this Shipit instance's GitHub App.

Given these preconditions, the attack is repeatable per matching SHA and does not require any Shipit credentials, but it is not universally exploitable against arbitrary, unrelated repositories without a shared commit history — the write is confined to whatever stacks happen to contain a `Commit` row with that exact SHA.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits by bare `sha`) to only the repository that authenticated the webhook, e.g. filter through `Stack` → `Repository` matching `params.dig('repository', 'full_name')`/`repository_owner`, or join `Commit` to `Stack`/`Repository` and require `stack.repository.full_name == payload_repository_full_name` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan:
1. Create two `Repository`/`Stack` fixtures, `repo_a` (attacker-controlled) and `repo_b` (victim, `review_stacks_enabled: true`, required status `review/approved`).
2. Create a `Commit` with `sha: "deadbeef..."` under `repo_b`'s stack with no statuses (so `deployable?` is false / blocked).
3. Create a second `Commit` row with the *same* `sha` under `repo_a`'s stack (simulating shared ancestor history).
4. Post a `status` webhook payload with `repository.full_name = repo_a`'s name, `sha: "deadbeef..."`, `context: "review/approved"`, `state: "success"`, signed correctly for `repo_a`'s org.
5. Assert: before, `repo_b`'s commit `status.success?` is false / `deployable?` is false. After processing, assert `repo_b`'s commit now has a `Status` row with `context: "review/approved"`, `state: "success"`, and `deployable?`/`blocked?` flipped — despite the webhook only being authenticated for `repo_a`.
6. Assert the equality that should hold but doesn't: `commit.stack.repository.full_name == payload["repository"]["full_name"]` is `false` for the mutated `repo_b` commit.
