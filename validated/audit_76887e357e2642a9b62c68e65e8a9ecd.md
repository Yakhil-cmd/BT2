### Title
Missing complexity/depth bound in `validateAuthentifiers` allows crafted address-forwarding chains to bypass `MAX_COMPLEXITY`/`MAX_OPS` and cause deep unbounded recursion on every unit that spends from the address - ([File: definition.js])

### Summary
`definition.js` enforces `MAX_COMPLEXITY`/`MAX_OPS` limits when an address definition is first created (`validateDefinition`'s inner `evaluate`), but `validateAuthentifiers`'s own `evaluate` function — which re-walks the same definition tree every single time a unit spends from that address — has no such limit at all. By staging the creation of a chain of "forwarding" address definitions (`['address', <next-address>]`) in an order where the referenced address does not yet exist at definition time, an attacker can make each individual `validateDefinition` call see only O(1) complexity, completely skipping the compounding complexity check that would otherwise catch a deep chain. Once every address in the chain is defined, a single unit spending from the outermost address forces `validateAuthentifiers` to recursively resolve the entire chain with unbounded recursion and unlimited DB queries, since that code path has no complexity/depth guard.

### Finding Description
`definition.js` has two structurally similar tree-walking evaluators over an address definition:

1. `validateDefinition`'s inner `evaluate(arr, path, bInNegation, cb)` (used to validate a *new* address/asset definition) explicitly enforces complexity limits on every node visited: [1](#0-0) 

2. `validateAuthentifiers`'s inner `evaluate(arr, path, cb2)` (used to verify signatures every time a unit spends from an address) has **no** such check anywhere in its `switch` — it directly dispatches on `op` with no complexity/op-count/depth guard: [2](#0-1) 

The `'address'` op in `validateDefinition` recursively resolves a referenced address's definition via `storage.readDefinitionByAddress`, but only if that address's definition is already resolvable (either stored on-chain, or supplied inline by a co-author of the *same* unit). If the referenced address cannot be resolved at all, resolution is skipped and `cb(null, true)` is returned without contributing to the complexity count: [3](#0-2) 

This means: if address `Z_n` is defined with body `['address', Z_{n-1}]` at a time when `Z_{n-1}` does not yet exist anywhere in the DAG, `validateDefinition`'s complexity check for `Z_n` never expands into `Z_{n-1}`'s tree — the check is essentially free (O(1)) regardless of how deep the eventual chain will be. An attacker can build a chain `Z_n -> Z_{n-1} -> ... -> Z_1 -> Z_0` (with `Z_0` a real `['sig', ...]` condition) strictly top-down, defining each `Z_i` before `Z_{i-1}` exists, so that **no single `validateDefinition` call ever sees more than one or two levels of nesting**, entirely bypassing `constants.MAX_COMPLEXITY` / `constants.MAX_OPS` for the chain as a whole.

Once all addresses in the chain are established (each now independently resolvable in the DB), any subsequent unit spending from `Z_n` must have its signature checked via `validateAuthentifiers`. Its `'address'` case (mirrors the definition-time one but requires resolvability, since this is signature verification, not open-ended definition validation) recurses fully into each successively resolved address: [4](#0-3) 

Because `validateAuthentifiers`'s `evaluate` has no complexity/op/depth ceiling, this recursion depth equals the full chain length `n`, chosen entirely by the attacker, and it is executed by **every full node** that validates the spending unit (this is the live consensus-critical authentifier check, not a one-time definition check). Each level also issues a fresh `storage.readDefinitionByAddress` DB query, so the attack additionally amplifies I/O cost per node with chain length.

This is directly analogous to CVE-2023-39328/CVE-2019-6988 in OpenJPEG: an existing protection mechanism (bounds/complexity limiting) is bypassed by structuring the malicious input (here, a chain of address definitions posted over time) so that the limiting check never sees the full picture, and the bypass leads to unbounded processing/crash at consumption time.

### Impact Explanation
Every node that validates a unit spending from the crafted address `Z_n` must execute the unbounded recursive `validateAuthentifiers` walk. Depending on chosen chain depth this causes:
- Excessive CPU/DB-query consumption per validated unit, scaling linearly (or worse, given async callback nesting) with attacker-chosen chain length.
- Node.js call-stack growth proportional to chain depth (no `setImmediate`/`count % 100` interrupt like the formula evaluators use), risking `RangeError: Maximum call stack size exceeded` crashes on full nodes attempting to validate/relay the unit.
- Because this failure occurs during authentifier verification of an otherwise well-formed unit reachable by any unpermissioned actor (the attacker just needs a handful of ordinary address-definition-establishing units plus one spending unit), it can cause nodes to crash or hang while validating a single unit, undermining the network's ability to consistently validate and confirm new units — matching the required "network unable to confirm new units" / node crash impact class.

### Likelihood Explanation
Reachable by any unprivileged user: address definitions are created via ordinary units (multi-authored or self-authored with inline definitions), a completely standard, permissionless operation; no elevated trust, hub cooperation, or protocol upgrade is required. The only skill required is sequencing the definitions top-down so that each intermediate reference is initially unresolved, then spending from the outermost address. This is a pure oscript/definition-structure crafting exercise, well within reach of any wallet author.

### Recommendation
Add the same complexity/op-count accounting used in `validateDefinition`'s evaluator to `validateAuthentifiers`'s `evaluate` function (a shared counter incremented on every node visit, including nested address resolutions and `definition template` expansions), and reject with an error once it exceeds `constants.MAX_COMPLEXITY`/`constants.MAX_OPS`. Additionally, close the definition-time bypass by ensuring `validateDefinition`'s `'address'` case counts *some* minimal complexity cost even when the referenced address is unresolved at definition time (e.g., treat it as a fixed-size sub-tree for budgeting purposes), so that chains built via staged/forward references cannot circumvent the original complexity cap. Consider also interrupting the call stack (e.g. `setImmediate` every N recursive calls) in `validateAuthentifiers`'s `evaluate`, matching the pattern already used in `formula/evaluation.js` and `formula/validation.js`.

### Proof of Concept
1. Attacker controls (or can generate) keys for `n` addresses `Z_0..Z_n`.
2. Post a unit establishing `Z_0`'s definition as `['sig', {pubkey: PK0}]` (an ordinary signature address).
3. Post a unit establishing `Z_1`'s definition as `['address', Z_0]` — fine so far, and cheap.
4. Repeat, defining `Z_{i}` as `['address', Z_{i-1}]`, but crucially choose the ORDER of definition so that at the moment `Z_i` is defined, `Z_{i-1}` does *not yet exist anywhere on the DAG* (i.e., define outer addresses first: `Z_n`, then `Z_{n-1}`, ..., down to `Z_0`). Each such `validateDefinition` call hits the `ifDefinitionNotFound` branch in `definition.js:284-303` and skips resolving/counting the (still nonexistent) inner address, so `MAX_COMPLEXITY`/`MAX_OPS` is never triggered no matter how large `n` is.
5. After the full chain exists, post a unit whose author is `Z_n`, supplying the real signature under path corresponding to `Z_0`'s `sig` condition.
6. Every validating node must call `validateAuthentifiers` on `Z_n`'s definition, recursing `n` levels deep through `definition.js:774-800` with no complexity/depth bound, issuing `n` DB lookups and `n` nested async callback/stack frames — for arbitrarily large attacker-chosen `n`.

**Uncertainty**: I could not directly execute this scenario against a live node/test harness (no runtime access), and I did not find the exact numeric value of `constants.MAX_COMPLEXITY`/`MAX_OPS` in the excerpts retrieved, though their existence and usage in `validateDefinition` (but not `validateAuthentifiers`) is clearly confirmed by the code shown above. Confirming actual crash behavior (stack overflow vs. just slow validation) would require running the sequence in a test environment.
