### Title
Webhook signature verification is scoped to `repository.owner.login`, but event processing acts on the unrelated `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, every registered handler (e.g. `PushHandler`) resolves the target `Stack`/`Repository` using a completely different payload field, `repository.full_name`, via `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing binds these two fields together, so the organization whose secret validated the request is not required to equal the organization of the repository actually acted upon.

### Finding Description
In a multi-organization Shipit deployment (explicitly documented and supported in `docs/setup.md` / `config/secrets.development.example.yml`, where each GitHub organization has its own `app_id`/`webhook_secret`), the controller picks the verification secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`), and `Shipit.github(organization: repository_owner)`'s `webhook_secret` is used to verify `X-Hub-Signature` against the raw request body.

Once verification succeeds, the actual event handling never re-checks `repository.owner.login`. Instead it uses `repository.full_name`: [3](#0-2) [4](#0-3) 

Because a JSON HTTP body is fully attacker-controlled, an attacker who legitimately administers a GitHub App/organization that is one of the tenants configured on this Shipit instance (and therefore knows that organization's `webhook_secret`) can craft a payload where:
- `repository.owner.login` = the attacker's own organization (used only to pick the verification secret they know), and
- `repository.full_name` = `"victim-org/victim-repo"` (used to resolve the actual `Repository`/`Stack` acted on).

The HMAC is computed over the raw body with the attacker's own known secret, so `verify_webhook_signature` succeeds even though the payload's semantic content targets a repository owned by a different, unrelated organization/tenant.

The broken binding, expressed as an equality that should hold but doesn't:
`organization authenticated via webhook_secret (repository.owner.login)` == `organization/repository actually written to (repository.full_name)`

### Impact Explanation
For the `push` event, this lets the attacker have `PushHandler#process` invoke `stack.sync_github(expected_head_sha: params.after)` on any stack belonging to a victim organization/repository tracked by the same Shipit instance: [5](#0-4) 

`sync_github` pulls github state and, for stacks with `continuous_deployment` enabled, this synchronization is what drives automatic deploys (see `Stack.schedule_continuous_delivery` / `ContinuousDeliveryJob` in `app/models/shipit/stack.rb` and `app/jobs/shipit/continuous_delivery_job.rb`). An attacker who controls a completely unrelated, unprivileged tenant organization on the same Shipit installation can therefore force GitHub-sync/refresh cycles — and downstream deploy triggers for continuously-deployed stacks — for a repository/organization they have no legitimate access to, crossing a tenant/authorization boundary using only credentials for their own tenant. This lines up with the "unauthorized deploy" / "cross-repository writes" impact bucket.

Other handlers (`MembershipHandler`, `PullRequestHandler` family, `CheckSuiteHandler`) exhibit the same pattern: signature verification is keyed off `owner.login`/`organization.login`, while the effective target repository/stack is resolved from `repository.full_name` inside the handler, with no cross-check between the two.

### Likelihood Explanation
Exploitability requires the attacker to know a valid `webhook_secret` for *some* organization configured on the shared Shipit instance — which is a normal, low-privilege capability for anyone administering that organization's GitHub App installation (they are simply configuring their own tenant's webhook, not the victim's). No access to the victim's repository, no `ApiClient` token, and no Shipit user session is needed. This is realistic specifically in the documented multi-org configuration mode; single-organization deployments are not affected since there is only one `webhook_secret` to begin with.

### Recommendation
After signature verification passes, re-validate that the organization used to select the `webhook_secret` matches the organization implied by `repository.full_name` (and `organization.login` for org-level events) before dispatching to any handler — i.e., enforce `repository.full_name.split('/').first == repository_owner` (case-insensitively) or equivalently resolve the `Repository`/`Stack` only within the same GitHub App/organization context that produced a valid signature. Reject the webhook (422) if these disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (per `docs/setup.md` multi-org config), and a tracked stack for `victim-org/victim-repo`.
2. As the administrator of `attacker-org`'s GitHub App (a legitimate, unprivileged capability with respect to `victim-org`), craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw body.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and verifies successfully (attacker knows this secret) — see `app/controllers/shipit/webhooks_controller.rb:24-31`.
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — an action the attacker was never authorized to trigger.
