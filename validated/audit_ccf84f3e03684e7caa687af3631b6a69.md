## Analog Assessment

I found a genuine architectural analog to the CNote "act-then-account" reentrancy pattern, in the `security-guidance` plugin's git-automation trust boundary. It is not a smart-contract fund-drain, but it fits the same root cause: **an irreversible external action is allowed to complete before the state used to gate/verify it is durably recorded**, and the recording step runs asynchronously afterward, admitting a race window.

### Title
Security review/baseline state is updated only *after* `git push`/`git commit` has already executed, admitting a TOCTOU window where malicious/vulnerable code reaches the remote before any block can apply - (File: plugins/security-guidance/hooks/security_reminder_hook.py)

### Summary
The security-guidance plugin's commit/push review runs as a `PostToolUse` hook — i.e., strictly *after* the Bash tool has already executed `git commit`/`git push` [1](#0-0) . The "accounting" step — recording reviewed SHAs, updating `previous_findings`, and advancing `baseline_sha` — happens in a locked state update that runs concurrently with (and can race) the next turn's `UserPromptSubmit` baseline capture [2](#0-1) [3](#0-2) . This is explicitly the "asyncRewake" design the code documents: `Stop` fires in the background after Claude's turn ends, and a new user prompt can be submitted before the review's state write lands [4](#0-3) .

### Finding Description
- The `git push`/`git commit` (the equivalent of `doTransferOut`) is executed unconditionally by the Bash tool. Only afterward does `PostToolUse` fire the review scripts (`handle_commit_review_posttooluse` / `handle_push_sweep_posttooluse`), gated by a de-dup sentinel for compound commands [5](#0-4) .
- The only enforcement mechanism afterward is the `Stop` hook, which can force Claude to "continue and fix" via `sys.exit(2)` [6](#0-5)  — but by that point the push has already reached the remote and cannot be undone by this mechanism, exactly as CNote's `doTransferOut` already sent funds before `accountBorrows` was updated.
- The state that tracks what has/hasn't been reviewed (`baseline_sha`, `previous_findings`, `touched_paths`, `stop_hook_fire_count`) is snapshotted and cleared with an explicit TOCTOU-aware design (`consume_stop_state`), and the code comments acknowledge a genuine race: "The user can submit a new prompt before this hook finishes its initial state read" and a share of reviews were previously lost to this race [4](#0-3) .
- `restore_unreviewed_stop_state` exists specifically to patch over cases where `Stop` exits early (transient API failure) after having already cleared `touched_paths`, which otherwise would silently drop the review obligation entirely and let the next `UserPromptSubmit` re-baseline past unreviewed, already-pushed edits [7](#0-6) .

### Impact Explanation
Unlike CNote's issue (funds directly drained), this pattern's impact is scoped to the git-automation trust boundary: an untrusted or malicious workflow/turn can get vulnerable or malicious code committed and pushed to a real remote repository before the enforcement/blocking mechanism (the `Stop` hook's `exit(2)` "fix it" loop) has any chance to act, and if that `Stop` hook errors out (API error) or the session is interrupted, `restore_unreviewed_stop_state`'s recovery path is a best-effort patch, not a guarantee — meaning a push can permanently evade review under certain failure/race timing. This is a genuine "act before account" bug, but the consequence is limited to unreviewed code reaching the remote, not fund loss or privilege escalation, since the plugin is a best-effort advisory reviewer, not an access-control gate.

### Likelihood Explanation
The condition requires a background/async `Stop` hook to lose a race against a new prompt or an API transient error at the same time as vulnerable code was committed/pushed in the current turn. The code's own comments confirm this race was observed in telemetry ("Telemetry showed a meaningful share of would-be reviews lost") [8](#0-7) , indicating it is a real, previously-encountered condition rather than a purely theoretical one, though the plugin's own developers have already added partial mitigations (`consume_stop_state`, `restore_unreviewed_stop_state`).

### Recommendation
Given this is an advisory security-guidance plugin rather than a funds/permission gate, the most direct mitigation mirrors CNote's recommended fix: move the "accounting" (recording that a push/commit needs review, or blocking outright) to occur synchronously *before* the external action (i.e., gate `git push` on a `PreToolUse` decision rather than reviewing only in `PostToolUse`), or ensure `restore_unreviewed_stop_state`-style compensations are guaranteed (not best-effort) whenever a review is interrupted, so that an unreviewed push can never silently fall out of tracking.

### Proof of Concept
Not independently reproducible from static code alone: the race depends on precise timing between the asynchronous `Stop` hook's state snapshot/clear and either (a) a new `UserPromptSubmit` firing, or (b) a transient API failure during `handle_stop_hook`. The code's own inline documentation and the existence of dedicated repair functions (`restore_unreviewed_stop_state`, `consume_stop_state`) are the concrete evidence of the underlying race condition; I was not able to fully trace `handle_commit_review_posttooluse`/`handle_push_sweep_posttooluse` bodies within the remaining tool budget to confirm whether a compound `git commit && git push` could bypass review entirely via the sentinel de-dup path — this remains unverified and should be checked by reading `security_reminder_hook.py` lines ~1700–2075 in full, along with `handle_stop_hook`'s complete body.

```python
    # cannot tell which `if` fired it.
    #
    # Routing therefore MUST check commit FIRST so that compound commit+push

    # the commit-matcher invocation. The push-matcher invocation of the SAME
    # compound command is deduped by `_claim_bash_hook_once` below: the second
    # spawn loses the tool_use_id sentinel race and exits early with
    # `bash_hook_dedup`, so commit-review runs exactly once. The alternative —

    # on `git commit && git push`, which is a regression.
    #
    # The push-sweep does NOT run on the compound call. That's acceptable: the
    # just-made commit is recorded by commit-review, so the next standalone

            print(json.dumps({"metrics": {"bash_hook_dedup": True}}), flush=True)
            sys.exit(0)
```

```python
def consume_stop_state(session_id):
    """Atomically snapshot all state the Stop hook needs and clear touched_paths.

    The Stop hook is asyncRewake — it runs in the background after Claude's
    turn ends. The user can submit a new prompt before this hook finishes its
    initial state read. Telemetry showed a meaningful share of would-be reviews lost when
    the next turn's UPS wiped touched_paths before Stop read it.

    Single locked read-then-clear closes that window: PostToolUse appends
    after this clear go into the next snapshot; UPS overwrites of baseline_sha
    after this snapshot are invisible to this Stop fire.
    """
    import time as _time
    now = _time.time()

    def _snap(state):
        fire_ts = state.get("stop_hook_fire_count_ts", 0)
        expired = (now - fire_ts) > STOP_LOOP_STATE_TTL_SEC
        findings_ts = state.get("previous_findings_ts", fire_ts)
        findings_expired = (now - findings_ts) > PREVIOUS_FINDINGS_TTL_SEC
        snap = {
            "touched_paths": list(state.get("touched_paths", [])),
            "baseline_sha": state.get("baseline_sha"),
            "head_at_capture": state.get("head_at_capture"),
            "untracked_at_baseline": (
                dict(state["untracked_at_baseline"])
                if isinstance(state.get("untracked_at_baseline"), dict) else {}
            ),
            "fire_count": 0 if expired else state.get("stop_hook_fire_count", 0),
            "fire_count_expired": expired and state.get("stop_hook_fire_count", 0) > 0,
            "previous_findings": [] if findings_expired else list(state.get("previous_findings", [])),
        }
        state["touched_paths"] = []
        return snap

    return with_locked_state(session_id, _snap) or {
        "touched_paths": [], "baseline_sha": None, "head_at_capture": None,
        "untracked_at_baseline": {},
        "fire_count": 0, "fire_count_expired": False, "previous_findings": [],
    }
```

```python
def restore_unreviewed_stop_state(session_id, paths, baseline_sha):
    """Put consumed touched_paths back so the next Stop reviews them.

    consume_stop_state cleared touched_paths on disk; if Stop then exits
    early for a transient reason (CCR API unreachable, Haiku HTTP error)
    the next UPS would see an empty list, fall through the preservation
    guard, and re-baseline past the unreviewed edits. Restoring keeps the
    guard armed. Prepend+dedupe so any concurrent next-turn PostToolUse
    appends survive.
    """
    if not paths:
        return

    def _restore(state):
        existing = state.get("touched_paths", [])
        merged = list(dict.fromkeys(list(paths) + list(existing)))
        if len(merged) > 200:
            merged = merged[:200]
        state["touched_paths"] = merged
        if baseline_sha and not state.get("baseline_sha"):
            state["baseline_sha"] = baseline_sha
    with_locked_state(session_id, _restore)
```
