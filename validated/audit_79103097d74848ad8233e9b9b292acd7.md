### Title
Cross-organization webhook forgery via mismatch between the organization used to verify the webhook signature and the repository field used to route the event - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Every webhook handler, however, resolves the `Repository`/`Stack` to act upon using an entirely different field, `payload.dig('repository', 'full_name')`, via `Shipit::Repository.from_github_repo_name`. Because Shipit supports hosting multiple GitHub organizations in one instance (`docs/setup.md`, "Using Multiple GitHub Applications"), an org that legitimately owns its own GitHub App/webhook secret can forge a payload whose `repository.owner.login` matches its own org (so the signature check passes with a secret it legitimately controls) while `repository.full_name` names a repository belonging to a completely different tenant organization hosted on the same Shipit instance.

### Finding Description [1](#0-0)  shows `verify_signature` picking the `GitHubApp` (and its `webhook_secret`) purely from `repository_owner`: [2](#0-1) 

Meanwhile every handler (push, status, pull_request, etc.) resolves the target `Stack`/`Repository` using a *different* JSON key from the same attacker-controlled body: [3](#0-2) [4](#0-3) 

Both `repository.owner.login` and `repository.full_name` are independent, attacker-supplied fields inside the same JSON body; nothing in the controller or in `Handler#repository_name`/`Repository.from_github_repo_name` cross-checks that the organization used to select the verifying secret matches the organization encoded in `repository.full_name`. Since the HMAC signature is computed over the *entire* raw request body, whoever holds a valid `webhook_secret` for **any** onboarded organization can produce a validly-signed payload for that org while embedding a `repository.full_name` that points at a Stack belonging to a **different** organization/tenant on the same Shipit instance, e.g. `PushHandler`: [5](#0-4) 

This breaks the intended equality: "organization whose secret authenticated the request" == "organization/repository the request is allowed to mutate."

### Impact Explanation
An operator of one tenant organization's GitHub App (who legitimately knows only their own org's `webhook_secret`, configured per `docs/setup.md` lines 182-209) can trigger `GithubSyncJob` (via `PushHandler#process` → `stack.sync_github`), post fabricated commit `Status`es, close/archive/unarchive review stacks, or trigger PR-driven provisioning for repositories belonging to a completely different organization/tenant that happens to share the same Shipit deployment. This is a cross-repository/cross-tenant write achieved without ever possessing the target organization's webhook secret — matching the Critical "cross-repository writes" / "unauthorized deploy" impact bucket, since `sync_github` calls can feed into `trigger_continuous_delivery` and downstream deploy triggering for a stack the attacker does not own.

### Likelihood Explanation
Exploitability requires the host to run Shipit in the documented multi-organization mode (a supported, documented configuration, not a misconfiguration) and for the attacker to control a legitimate GitHub App installation/webhook secret for at least one of the onboarded organizations — a realistic scenario for any shared/managed Shipit instance serving several teams or customers. No access to the target organization's secret, session, or GitHub credentials is required.

### Recommendation
Cross-validate that the organization whose secret validated the signature (`repository_owner`) is consistent with the organization embedded in `repository.full_name` (and `organization.login`) before dispatching to handlers; reject the webhook otherwise. Alternatively, derive the target `Repository`/`Stack` scope strictly from the same field used for signature verification instead of a separately-controlled `full_name` string.

### Proof of Concept
1. Shipit is configured with multiple GitHub Apps, e.g. `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md` multi-org section).
2. An operator who controls `OrgA`'s GitHub App (and therefore knows `OrgA`'s `webhook_secret`) crafts a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" }
   }
   ```
3. They compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)` and POST it to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` and validates successfully because the signature does correspond to `OrgA`'s secret over this exact body.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for a stack belonging to `OrgB`, an organization the attacker does not administer.
