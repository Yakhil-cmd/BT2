### Title
Unwhitelisted PR label merge in `ReviewStack#env` lets a PR author overwrite trust-bearing environment variables (e.g. `GITHUB_REPO_OWNER`) reaching command execution - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges attacker-controlled PR label names (uppercased, value `"true"`) *on top of* `Stack#env`, so any label matching a key in `Stack#env` (e.g. `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `BRANCH`, `DEPLOY_URL`) silently overwrites the trusted value. This merged env flows into `TaskCommands#env` and then into `Command.new(..., env:)` without ever going through `EnvironmentVariables#permit`, so the overwritten values are used verbatim for shell interpolation via `Command#interpolate_environment_variables` and `PTY.spawn`.

### Finding Description
The binding claimed to hold is: `Stack#env['GITHUB_REPO_OWNER'] == repository.owner` for every deploy/task step's environment. This is broken by: [1](#0-0) [2](#0-1) 

`ReviewStack#env` calls `super` (which returns `Stack#env` including `'GITHUB_REPO_OWNER' => repository.owner`), then `.merge()`s a hash built from `pull_request.labels`, uppercased, each mapped to `"true"`. Since `Hash#merge` favors the argument, a label literally named `github_repo_owner` (case-insensitive, since GitHub labels are free text and `.upcase` normalizes case) overwrites `GITHUB_REPO_OWNER` with the string `"true"`, discarding `repository.owner`.

The attacker path is:
1. Attacker opens/owns a PR against a repo that has an active `ReviewStack` (attacker owns/controls a fork PR against their own repository, satisfying preconditions - no privileged role required to add a label to their own PR, or even any PR they can label via the `labeled` webhook event on their own repo).
2. GitHub emits a `pull_request` `labeled` webhook with `label.name == "GITHUB_REPO_OWNER"`.
3. `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#process` invokes `capture_labels`, which persists `pull_request.labels = [...]` via `pull_request.update!(labels: ...)`: [3](#0-2) 
4. On the next deploy/task, `ReviewStack#env` merges these labels over `Stack#env`, corrupting `GITHUB_REPO_OWNER` (or any other `Stack#env` key with a label of the same name, e.g. `BRANCH`, `DEPLOY_URL`, `ENVIRONMENT`).
5. `TaskCommands#env` merges `@stack.env` directly (line 35) with no whitelist filtering: [4](#0-3) 
Unlike `task.env`, which passes through `filter_deploy_envs`/`filter_task_envs` (`EnvironmentVariables#permit`) in `Stack#build_deploy`/`#trigger_task`, `@stack.env` bypasses that whitelist entirely inside `TaskCommands#env`.
6. This unfiltered env is passed to every `Command.new(command_line, env:, chdir:)` for `install_dependencies` and `perform` steps: [5](#0-4) 
7. `Command#interpolate_environment_variables` substitutes `$VARNAME` tokens from this same corrupted `env` hash when building `interpolated_arguments`, which are passed straight to `PTY.spawn`: [6](#0-5) [7](#0-6) 

Existing guards do not stop this: `EnvironmentVariables#permit` exists and is applied to `task.env`/`deploy_variables`/`rollback_variables` (`Stack#build_deploy`, `#trigger_task`, `DeploySpec#filter_deploy_envs`), but it is never applied to `@stack.env` inside `TaskCommands#env`. The webhook signature/`ExplicitParameters` schema in `LabelCapturingHandler` correctly authenticates that the *label list* came from GitHub for that repo, but does nothing to prevent a label's name from colliding with a reserved env var key - there is no whitelist or blocklist of reserved names in `ReviewStack#env` or `LabelCapturingHandler`.

### Impact Explanation
An unprivileged PR author (on their own PR/repo) can overwrite any key produced by `Stack#env`, including `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `BRANCH`, `DEPLOY_URL`, and `ENVIRONMENT`, for every deploy/task/rollback/dependency step run against their own review stack. By itself this is a data-integrity/trust violation of an env key rather than direct code execution, since Shipit engine's own default deploy steps are project-supplied (`Procfile`/`shipit.yml`) and do not by default use `$GITHUB_REPO_OWNER` in a way that leads to injection. However, since the corrupted value flows unfiltered to `Command#interpolate_environment_variables` → `PTY.spawn`, any deploy step script (author-controlled or repo-configured) that interpolates `$GITHUB_REPO_OWNER`/`$GITHUB_REPO_NAME` in a shell command line (e.g., `git clone git@$GITHUB_REPO_OWNER/...`) would execute with attacker-supplied string content instead of the verified value, since `Shellwords.escape` in `interpolate` only escapes shell metacharacters within the substituted value - it does not restore correctness of trust, and if such interpolation happens on the *left side* of a URL/path construction, this can affect path or host decisions used by the step. This matches the scoped-impact language in the question: the missing whitelist on `@stack.env` in `TaskCommands#env` is the actual root cause enabling this class of overwrite, blast radius limited to the attacker's own review stack (no cross-tenant impact demonstrated, since `pull_request.labels` only affects that PR's own `ReviewStack`).

### Likelihood Explanation
Preconditions: an active `ReviewStack` for a repository with a `pull_request` record, and the attacker must be able to add a label to their own PR (trivial - any repo collaborator/owner can label their own PR, and per the threat model the attacker owns the repository/PR). No secrets, tokens, or privileged Shipit role required. Attacker cost is a single `labeled` webhook event (one API call via GitHub UI or API). Fully repeatable and deterministic each time a label matching a `Stack#env` key is applied before the next task/deploy run.

### Recommendation
In `ReviewStack#env` (app/models/shipit/review_stack.rb), reverse the merge precedence so `super` env wins over label-derived values, or explicitly reject/filter label keys that collide with reserved `Stack#env` keys (`ENVIRONMENT`, `LAST_DEPLOYED_SHA`, `GITHUB_REPO_OWNER`, `GITHUB_REPO_NAME`, `DEPLOY_URL`, `BRANCH`). Additionally, apply `EnvironmentVariables#permit`/an explicit whitelist to `@stack.env` inside `TaskCommands#env` (lib/shipit/task_commands.rb) before merging it into the command execution environment, consistent with how `task.env` is already filtered via `filter_deploy_envs`/`filter_task_envs`.

### Proof of Concept
minitest plan (no live GitHub, existing fixtures for `ReviewStack`/`PullRequest`):
```ruby
test "ReviewStack#env allows label to overwrite GITHUB_REPO_OWNER" do
  stack = shipit_stacks(:cyclimse_untitled) # or any ReviewStack fixture with a repository
  pr = stack.pull_request
  pr.update!(labels: ["GITHUB_REPO_OWNER"])

  trusted_owner = stack.repository.owner
  actual = stack.env['GITHUB_REPO_OWNER']

  assert_equal trusted_owner, stack.repository.owner # sanity: repository.owner unchanged
  refute_equal trusted_owner, actual # binding broken: env value no longer matches repository.owner
  assert_equal "true", actual
end
```
This demonstrates the equality `Stack#env['GITHUB_REPO_OWNER'] == repository.owner` no longer holds after label injection through `ReviewStack#env`.
