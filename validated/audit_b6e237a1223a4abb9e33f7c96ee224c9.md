### Title
`StatusHandler#process` writes CI status to any commit matching `sha` with zero repository binding, ignoring `repository.full_name` entirely - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits purely with `Commit.where(sha: params.sha)`, never calling the `stacks`/`repository_name` helpers defined on the parent `Handler` class, and never validating that `payload.dig('repository', 'full_name')` corresponds to the stack that owns the matched commit. Any correctly-signed `status` webhook whose `sha` collides with a commit row belonging to a different, unrelated stack will mutate that stack's commit status.

### Finding Description
The broken binding is: `payload.dig('repository', 'full_name')` == the repository whose stack actually gets mutated. Tracing the code shows this equality is never enforced for `status` events:

- `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup with no `stack_id`/`repository` filter. [1](#0-0) 
- The base `Handler` class *does* define `stacks` (scoped via `Repository.from_github_repo_name(repository_name)`) and `repository_name` (`payload.dig('repository', 'full_name')`), but `StatusHandler` never calls either. [2](#0-1) 
- `WebhooksController#verify_signature` only resolves the GitHub App/webhook secret via `repository_owner` (`params.dig('repository', 'owner', 'login')` or `organization.login`), and only checks that the raw HMAC signature matches that org's `webhook_secret`. It performs no check that the specific `repository.full_name` in the payload matches the stack that will be mutated. [3](#0-2) 
- Compare with `CheckSuiteHandler`, which correctly scopes via `stacks.where(branch: ...)` before touching commits — proving repository scoping is an established, intentional pattern elsewhere in this same handler family that `StatusHandler` omits. [4](#0-3) 

Exploitable request: an attacker who owns/controls any GitHub repository that shares the organization's GitHub App installation (and thus produces a correctly HMAC-signed `status` webhook using the org's `webhook_secret`, computed by GitHub itself — the attacker never needs to know the secret) can trigger a `status` event whose `repository.full_name` names their own (or an arbitrary) repository, while `sha` is a commit SHA that also exists as a row in `commits` belonging to a completely unrelated, victim-owned stack (e.g., via a shared git history/fork within the same org, or any other means of sha collision with an existing tracked commit). Because `Commit.where(sha: ...)` is unscoped, the victim's commit's status gets updated, driven entirely by attacker-controlled `state`/`description`/`target_url`/`context` fields, even though `repository.full_name` never named the victim's repository.

Existing guards do not stop this: `verify_signature` only authenticates that the payload came from *some* legitimate installation of the org's app — it says nothing about which repository within that org the event concerns, and `ExplicitParameters` for `StatusHandler` only requires `sha`/`state`/etc., not `repository`. Since the handler doesn't consult `repository_name`/`stacks` at all, no downstream check exists either.

### Impact Explanation
A forged/mismatched `status` payload lets an attacker write an arbitrary CI status (`state`, `description`, `target_url`, `context`) onto a commit belonging to a stack/repository that the attacker's payload does not claim to be, and does not control. `Commit#create_status_from_github!` can flip a commit's `state` (e.g., to `success`), which is exactly what other parts of Shipit use to gate CI-based deploy eligibility (`ignore_ci`, deployable-status hooks). This is a cross-repository/cross-tenant write into another party's commit/status table rows, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). It's repeatable per request against any commit sha the attacker can reproduce, across every stack/repository hosted on the same Shipit instance whose GitHub App shares that webhook secret scope.

### Likelihood Explanation
Preconditions: the attacker needs a route to generate a *validly signed* `status` webhook (i.e., control of a repository under the same GitHub App/organization installation as the victim stack, e.g. via a fork or duplicate repository sharing commit history) and knowledge of a `sha` that also exists as a commit row for the victim stack. This is highly feasible for public/open-source orgs where the GitHub App is installed org-wide and forks naturally share commit SHAs with the upstream repository being tracked by Shipit. No Shipit session, API token, or secret is required from the attacker — GitHub computes and attaches the valid signature on their behalf when the event fires on their own repo. The attack is trivially repeatable for every shared commit.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the resolved `stacks` (via `repository_name`/`Repository.from_github_repo_name`) instead of a bare `Commit.where(sha: ...)`, mirroring the pattern already used in `CheckSuiteHandler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `stack_id` to the repository resolved from `payload.dig('repository', 'full_name')`, and require `repository.full_name` in the `StatusHandler` params schema.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` pattern, no live GitHub calls, signature stubbed as in existing setup):

```ruby
test ":status payload with a mismatched repository.full_name still mutates a commit in an unrelated stack" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first) # belongs to victim_stack, has a real sha

  # Binding under test (BEFORE):
  #   payload.dig('repository', 'full_name') == repository owning the mutated commit
  # i.e. "attacker/unrelated-repo" != victim_stack.repository.full_name
  assert_not_equal "attacker/unrelated-repo", victim_stack.repository.full_name

  request.headers['X-Github-Event'] = 'status'
  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'shopify' } }
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body: forged_payload, as: :json
  end

  status = victim_commit.statuses.last
  assert_equal 'success', status.state

  # Binding under test (AFTER): still mismatched, proving repository.full_name was never consulted
  assert_not_equal "attacker/unrelated-repo", victim_stack.repository.full_name
end
```

This demonstrates that `StatusHandler#process` writes a `Status` row against `victim_commit` (owned by `victim_stack`) despite the payload's `repository.full_name` claiming an entirely different, attacker-named repository, confirming `Handler#stacks`/`repository_name` are dead for this handler.
