## Title
Webhook organization used to select the HMAC secret is not bound to the repository the payload writes to, allowing a valid signature from one organization's app to trigger writes against any repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This mirrors the Dinari `DirectBuyIssuer` bug class: a state check is performed against one part of the data structure while an unrelated part is later trusted and acted upon, so the check does not actually bind the action to the value it is supposed to guard. In Dinari, escrow accounting checked `remainingOrder` and `getOrderEscrow[orderId]` but the actual transfer used stale/unrelated bookkeeping that was never cleared. In Shipit, the webhook signature is verified using a secret selected from a specific field of the *unverified* JSON payload (`repository.owner.login` / `organization.login`), while the handlers that perform the actual database write use a *different* field of that same unverified payload (`repository.full_name`) to pick the target `Stack`/`Repository`. There is no requirement that these two fields refer to the same GitHub organization/repository.

### Finding Description
`WebhooksController#verify_signature` derives the organization solely from the raw, not-yet-verified JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` is used to fetch that organization's `webhook_secret` to verify `X-Hub-Signature`. This binds "the org whose secret validated the HMAC" to one narrow field of the payload.

The `create` action then hands the *entire* parsed body to whichever handler is registered for the event, unconstrained by the organization used above: [3](#0-2) 

Handlers such as `PushHandler` resolve which `Repository`/`Stack` to mutate using an entirely different field of the same payload, `repository.full_name`: [4](#0-3) [5](#0-4) 

Because Shipit is explicitly designed to be multi-tenant (`Shipit.github(organization:)` supports per-organization GitHub Apps/secrets, as also reflected in `GithubOrganizationUnknown` handling), an attacker who legitimately controls one onboarded GitHub organization (with their own valid `webhook_secret`) can send a webhook whose `repository.owner.login`/`organization.login` field names *their own* org (so the signature check passes with their own secret) while setting `repository.full_name` to a *different* repository/stack entirely. The signature never covers "this payload is authorized to act on repository X" — it only covers "this raw body was HMAC'd with organization Y's secret" — and the code that performs the action keys off a field the signature-selection step ignored.

This is the same class of bug as the Dinari escrow issue: two pieces of state that should be tied together by an invariant (which org's key signs vs. which repository gets written) are read from independent, attacker-influenced locations, so the equality "signing org == acted-upon repository's org" is never enforced.

Binding broken (per the analog list): "an organization that authenticated versus the repository that is written."

Before the attacker's payload: signature verification org == acted-upon repository's org (assumed, not enforced).
After: signature verification org (from `repository.owner.login`) can differ from the repository actually written to (from `repository.full_name`), because nothing ties them together.

### Impact Explanation
`PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)`, which can advance a stack's known commits/HEAD state under attacker control for a repository the attacker does not own, using a signature they legitimately possess for an unrelated org. Depending on which handler is hit (`push`, `pull_request`, `status`, `check_suite`, `membership`), this can inject fabricated commit statuses / check-run results / membership changes / pull-request metadata into another tenant's stack, influencing which commits are considered deployable or mergeable — i.e., cross-repository/cross-organization writes performed via a forged trust boundary. This matches the "cross-repository writes / unauthorized deploy" High/Critical impact bucket, since deploy eligibility (CI status, merge queue) can be manipulated for a repository the attacker does not control.

### Likelihood Explanation
Exploitability requires the attacker to be an onboarded, legitimate GitHub organization admin/webhook operator for *some* org configured in the Shipit instance (i.e., they must possess a valid `webhook_secret` for at least one org) — this is not a fully anonymous, zero-credential attack, but it is far short of "repository write access" or "Shipit session" to the *victim* repository, which is the actual target. Given Shipit is built for multi-tenant use (many organizations/repos onboarded to one instance), this is a realistic scenario, but it does depend on the deployment onboarding more than one organization and an attacker being one of them.

### Recommendation
Bind signature verification to the same repository/organization identifier that handlers act on: verify the signature using a secret keyed by `repository.full_name` (or verify that `repository.owner.login`/`organization.login` matches the owner embedded in `repository.full_name`) before dispatching to handlers. Alternatively, look up the `Stack`/`Repository` from `repository.full_name` first, resolve its owning organization's app/secret from that, and only use that to verify — never let the payload's stated owner field diverge from the payload's stated repository field without a match check.

### Proof of Concept
1. Onboard/attacker-control GitHub organization `attacker-org` in the multi-tenant Shipit instance, with a valid webhook secret `S_attacker`.
2. Craft a `push` event JSON body where:
   - `repository.owner.login = "attacker-org"` (or `organization.login = "attacker-org"`)
   - `repository.full_name = "victim-org/victim-repo"`
   - `ref = "refs/heads/main"`, `after = "<attacker-chosen sha>"`
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(S_attacker, raw_body)`.
4. POST to `/github/webhooks`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature with `S_attacker`.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)`, mutating the victim stack's state despite the signature only proving authorization for `attacker-org`.

Note: I could not fully trace `Shipit.github(organization:)`'s multi-org secret-lookup implementation or `Repository.from_github_repo_name` within the indexed context (grep for `def self.github` returned no matches), so I cannot confirm from code alone whether a single-tenant deployment (one org, one secret) would also be affected, or whether there is an additional implicit check elsewhere tying `repository_owner` to `repository.full_name` that I did not locate. Given index size limits, some file contents (e.g., `lib/shipit.rb`, `app/models/shipit/repository.rb`) may not have been available to fully verify; starting a full Devin session against the repo would allow direct inspection of those files to confirm the exact secret-lookup and repository-resolution logic.
