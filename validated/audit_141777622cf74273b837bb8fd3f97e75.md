### Title
StatusHandler processes commits by SHA with no repository binding, letting an attacker's status webhook mutate a victim stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without ever checking that the matched commit's `stack`/`repository` corresponds to the `repository` named in the webhook payload. Any commit sharing that SHA in any other stack — including a victim's — gets a `Status` record created from an unrelated repository's webhook, which can flip `Commit#deployable?` to true and trigger `Stack#trigger_continuous_delivery`.

### Finding Description
The claimed binding is: `commit.stack.repository == payload['repository']['full_name']` for every commit mutated by a given webhook. Tracing the code shows this equality is never enforced for status events.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only authenticates that the payload was signed with the webhook secret configured for `Shipit.github(organization: repository_owner)`. That secret is keyed by **organization**, not by individual repository (`GitHubApp#initialize` stores `@webhook_secret` per organization config, `lib/shipit/github_app.rb:44-51`, and `verify_webhook_signature` at lines 76-83 checks only the HMAC against that shared secret). It proves "GitHub sent this for some repo of this org," not "for repo X."
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper (app/models/shipit/webhooks/handlers/handler.rb:32-38) that correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17) uses exactly that scoped `stacks` relation before acting.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does **not** use `stacks`. It queries the global `Commit` table by `sha` alone:
  ```
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  There is no reference to `params.repository` or `repository_name` anywhere in this handler.
- `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (app/models/shipit/commit.rb:165-169, app/models/shipit/status.rb:24-33) creates a `Status` scoped to the matched commit's own `stack_id` — i.e., the victim stack, not the attacker's.
- `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` (app/models/shipit/status.rb:18-19, 38-44) call `commit.schedule_continuous_delivery`, which (per `app/jobs/shipit/continuous_delivery_job.rb` and `Stack#trigger_continuous_delivery`, app/models/shipit/stack.rb:210-229) evaluates `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`, app/models/shipit/commit.rb:227-229) and, if true, calls `trigger_deploy` on the **victim** stack.
- The `Commit.sha` column has an index on `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`) but no uniqueness validation on `sha` alone across stacks — nothing in the model (`app/models/shipit/commit.rb`) enforces global SHA uniqueness. So two unrelated stacks can each contain a `Commit` row with the same `sha` value, and `Commit.where(sha: ...)` will return both.

Exploit flow: attacker (who owns or controls a repo already tracked as a Shipit stack under the same GitHub organization, so their webhooks carry a validly-signed payload) crafts/rebases a commit whose SHA1 collides with the victim's head commit SHA (attacker fully controls tree, parents, author/committer timestamps on their own side to force the match), then triggers (or directly POSTs) a `status` event with `state: success` naming their own repository. `StatusHandler#process` ignores the repository field entirely and updates every `Commit` row with that SHA — including the victim's — flipping the victim commit to `success`, and continuous delivery ships it.

None of the listed guards catch this: `verify_signature` authenticates org-level HMAC only; `drop_unhandled_event` and `ExplicitParameters` schema only validate the `status` event has the shape `{sha, state, ...}` (no repository requirement is even declared for `StatusHandler#params`, unlike `PullRequest` handlers which do `requires :repository`); there is no `require_permission!`/`stacks` scoping in this handler at all.

### Impact Explanation
A webhook payload for repository A causes a write (`Status` creation) and a state transition (`deployable?` → true → deploy) on a stack belonging to unrelated repository B. This is a payload-for-one-repository-mutating-another's-stack/commit vulnerability leading to an unauthorized deploy — matching the Critical impact category explicitly listed in scope. It is repeatable against any stack whose commit SHA the attacker can reproduce, and the blast radius spans every stack sharing the org-level webhook secret with the attacker's tracked repo.

### Likelihood Explanation
Preconditions: (1) the attacker must control (or have push access to) a GitHub repository that is already tracked as a Shipit stack sharing the same organization-level `webhook_secret` as the victim stack — common in single-org, multi-repo Shipit deployments; (2) the victim stack must have `continuous_deployment`/`continuous_delivery` enabled and its target commit's SHA must be reproducible by the attacker via legitimate git content-addressing tricks (matching tree, parents, author/committer identities and timestamps), which is a non-trivial but demonstrated, purely git-side crafting effort with no need for any Shipit/GitHub secret. Given those preconditions, the attack costs a single signed webhook POST and is fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring `PushHandler`/`Handler#stacks`:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Also add `requires :repository { requires :full_name, String }` to `StatusHandler.params` so the repository is mandatory in the schema, and consider adding a uniqueness validation/composite key so a SHA collision across stacks cannot be leveraged even accidentally.

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "status webhook for repo A does not deploy stack of repo B sharing the same commit sha" do
          shared_sha = 'a' * 40

          victim_repo = Repository.create!(owner: 'victim-org', name: 'victim-repo')
          victim_stack = Stack.create!(repository: victim_repo, environment: 'production',
                                        continuous_deployment: true)
          victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim head',
                                                         author: Shipit::AnonymousUser.new,
                                                         committer: Shipit::AnonymousUser.new,
                                                         authored_at: Time.now, committed_at: Time.now)
          victim_stack.update!(cached_deploy_spec: DeploySpec.new({}))

          attacker_repo = Repository.create!(owner: 'attacker', name: 'throwaway')
          attacker_stack = Stack.create!(repository: attacker_repo, environment: 'production')
          attacker_stack.commits.create!(sha: shared_sha, message: 'attacker throwaway',
                                          author: Shipit::AnonymousUser.new,
                                          committer: Shipit::AnonymousUser.new,
                                          authored_at: Time.now, committed_at: Time.now)

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'created_at' => Time.now.to_s,
            'repository' => { 'full_name' => 'attacker/throwaway' }
          }

          # Binding under test, stated before tracing:
          # victim_commit.stack.repository.full_name ('victim-org/victim-repo')
          #   != payload['repository']['full_name'] ('attacker/throwaway')
          refute_equal victim_commit.stack.repository.full_name, payload['repository']['full_name']

          assert_no_enqueued_jobs(only: Shipit::PerformTaskJob) do
            Shipit::Webhooks::Handlers::StatusHandler.call(payload)
          end

          victim_commit.reload
          # If the bug exists, victim_commit is now 'success' and deployable despite the
          # webhook naming an unrelated repository -> binding was violated.
          refute_equal 'success', victim_commit.state,
            "victim commit was updated by a webhook naming an unrelated repository"
        end
      end
    end
  end
end
```
