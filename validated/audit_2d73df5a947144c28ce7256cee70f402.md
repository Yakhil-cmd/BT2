### Title
Cross-tenant stack disclosure via unscoped `stack` lookup - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` overrides the tenant-scoped `stack` helper from `Api::BaseController` with an unscoped `Stack.from_param!(params[:stack_id])`, so an `ApiClient` token that is restricted to a single stack via `stack_id` can be replayed against any other stack's CCMenu endpoint. This bypasses the multi-tenant isolation that `stacks`/`stack` in the base controller is designed to enforce.

### Finding Description
The broken binding: `stack_touched (params[:stack_id]) ∈ stacks_authorized_by(current_api_client.stack_id)` should hold, but does not.

In `Api::BaseController`, the scoped accessor is: [1](#0-0) 
`stacks` restricts to `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`, and `stack` resolves via that scoped relation's `from_param!`.

`Api::CCMenuController` overrides `stack` to bypass this scope entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped model, ignoring `current_api_client.stack_id`. `#show` then uses this unscoped `stack` for `deploys_and_rollbacks.last` and rendering: [3](#0-2) 

Authentication is handled by the also-overridden `authenticate_api_client`, which merely verifies the token via `ApiClient.authenticate(params[:token])` and does not perform any stack-scope check itself: [4](#0-3) 

`require_permission :read, :stack` only checks the string permission `read:stack` on the client via `check_permissions!`, and never validates *which* stack: [5](#0-4) 

So a token that is `read:stack`-permissioned and `stack_id`-scoped to stack B is accepted as valid, permission-checked as `read:stack` (true), and then handed a completely attacker-chosen `params[:stack_id]` that resolves against the global `Stack` table instead of the client's restricted scope. Existing guards (`require_permission!`, `ApiClient.authenticate`, `check_permissions!`) all pass because none of them look at `params[:stack_id]` vs `current_api_client.stack_id` — that comparison only happens inside the base `stack`/`stacks` methods, which this controller does not use.

Attack: obtain (or be given, e.g. via `CCMenuUrlController#fetch`) a CCMenu URL/token scoped to stack B, then issue `GET /api/ccmenu/OWNER_A/NAME_A/production?token=<token-for-B>`. The controller authenticates the token (valid), checks `read:stack` permission (present), and resolves `stack` as stack A regardless of the token's `stack_id`.

### Impact Explanation
Any holder of a stack-scoped `read:stack` CCMenu token can enumerate and read the latest deploy/rollback status, build label, activity, and lock status of *any* stack on the instance, not just the one the token was scoped to — an unauthenticated (relative to the target stack) cross-tenant information disclosure. This matches the "High - unauthenticated read of stack state" impact category. It is fully repeatable against arbitrary `owner/name/environment` combinations since `Stack.from_param!` is a normal lookup by repository/environment params, with no rate limiting tied to scope.

### Likelihood Explanation
Preconditions: attacker needs a valid CCMenu API token whose backing `ApiClient` has `read:stack` and a `stack_id` restricted to some stack (this is exactly what `CCMenuUrlController#fetch` mints for any user who can view a stack's CCMenu integration URL). No GitHub or Shipit secrets, no elevated role, and no changes to preconditions between requests are needed — only substituting `params[:stack_id]` in the URL. This is low-cost and trivially repeatable.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or make it delegate to the inherited scoped `stacks.from_param!`) so CCMenu lookups respect `current_api_client.stack_id` the same way every other API controller does.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing suite pattern using `ApiControllerTestCase`):
```ruby
test "a client scoped to one stack cannot fetch ccmenu status for another stack" do
  other_stack = shipit_stacks(:cyclimse)
  @client.update!(stack_id: other_stack.id, permissions: %w[read:stack])

  get :show, params: { stack_id: @stack.to_param, token: @client.authentication_token }

  # Expected (secure) behavior: request should be rejected/not_found
  # Actual (vulnerable) behavior: assert_response :ok and payload matches @stack (shipit), not cyclimse
  assert_response :not_found # currently fails: returns 200 with @stack's (shipit) data
end
```
This demonstrates that `current_api_client.stack_id == other_stack.id` while the resolved `stack` is `@stack` (`shipit`), violating the intended binding `stack ∈ stacks scoped by current_api_client.stack_id`.
