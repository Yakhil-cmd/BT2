### Title
`machine.environment` from `shipit.yml` is merged into deploy/task command env unfiltered, allowing `BUNDLE_GEMFILE` (and other) injection - (File: app/models/shipit/deploy_spec.rb, lib/shipit/task_commands.rb, lib/shipit/deploy_commands.rb)

### Summary
`DeploySpec#machine_env` reads `config('machine', 'environment')` directly from `shipit.yml` with no whitelist, and `TaskCommands#env`/`DeployCommands#env` merge it straight into the environment hash passed to `Command.new`, which flows unfiltered into `Command#unbundled_env` and `PTY.spawn`. Unlike deploy/task `env` params (which go through `EnvironmentVariables#permit` against `deploy_variables`/`rollback_variables`/`variables`), `machine_env` has no such filter, so any key present in `shipit.yml`'s `machine.environment`, including `BUNDLE_GEMFILE`, reaches the spawned process's environment.

### Finding Description
The broken binding: attacker expects `env_reaching_PTY_spawn == filtered(env, allowed_variables)` for every source of environment data, but in fact `env_reaching_PTY_spawn = filtered(deploy.env/task.env) ∪ machine_env(unfiltered)`.

Trace:
- `DeploySpec#machine_env` returns `config('machine', 'environment') || {}` with no validation [1](#0-0) .
- `TaskCommands#env` merges `deploy_spec.machine_env` and then `@task.env` (the latter having already passed through `filter_task_envs`/`EnvironmentVariables#permit` at the controller/model layer) directly into the hash handed to `Command.new` [2](#0-1) .
- `Command#initialize` stores `@env` as-is, and `Command#unbundled_env` merges `BASE_ENV` with `@env.stringify_keys` with no whitelist re-check, then this is passed straight to `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [3](#0-2) [4](#0-3) .
- Contrast this with the explicit filtering path that exists for the `env`/`deploy.env` params, confirmed by `filter_deploy_envs`/`filter_task_envs` delegating to `EnvironmentVariables.with(env).permit(...)` [5](#0-4) [6](#0-5) , and by tests demonstrating rejection of non-whitelisted keys for those paths [7](#0-6) . No equivalent permit/whitelist call exists for `machine_env`.
- Existing tests explicitly confirm `machine_env` is merged unfiltered into the command environment: `"#install_dependencies merges machine_env in ENVIRONMENT"` and `"#perform merges shipit.yml machine_env in ENVIRONMENT"` [8](#0-7) .

Root cause: `machine.environment` in `shipit.yml` is treated as trusted operator configuration, with no distinction made between a repo whose `shipit.yml` is controlled by a trusted maintainer versus a Review Stack whose deploy spec can be sourced from the working directory checked out for the task/deploy (a location that can include content originating from a PR branch, depending on how the working directory is populated for review stacks).

However, the specific attack described in the question — injecting `BUNDLE_GEMFILE` via a **PR label** — does not hold: PR labels only drive `archive?`/`unarchive?`/`provision?` decisions in `OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, etc. [9](#0-8) [10](#0-9)  — labels never populate any environment map that reaches `Command`. There is no code path from `pull_request.labels` to `deploy_spec.machine_env`, `Task#env`, or `Deploy#env`. That part of the question's exploit idea is unsubstantiated.

The `shipit.yml machine_env` vector is more plausible in principle (the merge is genuinely unfiltered), but confirming it is fork-exploitable requires establishing that an unprivileged fork PR's `shipit.yml` content is actually the one loaded/used when the review stack's deploy/task commands execute (i.e., that the working directory checked out for `TaskCommands`/`DeployCommands`/`DeploySpec::FileSystem` reflects the fork's branch content and not a repository-owner-controlled base). That checkout/fetch logic (`Stack#repo_git_url`, clone/fetch commands, and whether review stacks fetch `refs/pull/<n>/head` from a fork vs. only branches that exist in the origin remote) could not be verified within the available tool budget — repeated `read_file` attempts on `app/models/shipit/review_stack.rb`, `app/models/shipit/stack.rb`, and `lib/shipit/deploy_commands.rb` failed due to tool errors, and this is the single fact needed to determine whether a fork's `shipit.yml` (as opposed to the base repo owner's `shipit.yml`) is ever loaded for review-stack deploys/tasks.

### Impact Explanation
If confirmed, this would let a fork's `shipit.yml` set arbitrary environment variables (via `machine.environment`) that reach the deploy host process spawned by `PTY.spawn`, including `BUNDLE_GEMFILE` pointed at an attacker-controlled Gemfile whose evaluation runs arbitrary Ruby (RCE), or other dangerous variables (`RUBYOPT`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, etc.). This would be Critical (RCE on the deploy host).

### Likelihood Explanation
Cannot be established as reachable without confirming that Shipit checks out the fork's actual `shipit.yml` (as opposed to the base repository's `shipit.yml`, which is maintainer-controlled and out of scope for an "unprivileged" attacker) for review-stack deploys/tasks. Given typical shipit-engine review-stack architecture, review stacks generally deploy the base repository's deploy scripts against the PR's commit/branch, and `shipit.yml` discovery in `DeploySpec::FileSystem` reads from the working directory populated by `git checkout`/`clone` of the tracked repository — whether that includes fork content depends on remote/fetch configuration not confirmed here. The PR-label injection vector claimed in the question is not supported by the code (labels don't touch any env hash).

### Recommendation
- Apply `EnvironmentVariables#permit` (or an explicit denylist of dangerous keys such as `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD`, `GIT_SSH_COMMAND`) to `DeploySpec#machine_env` before merging it into `TaskCommands#env` / `DeployCommands#env`, regardless of whether the source is trusted, since the merge point in `Command#unbundled_env` is the last line of defense.
- Independently, verify and, if necessary, harden the review-stack checkout logic so that `shipit.yml` used to build task/deploy commands can never be sourced from fork-controlled content for repositories with `provisioning_behavior=allow_all`.

### Proof of Concept
Cannot provide a fully validated minitest without first confirming (a) whether fork `shipit.yml` content is actually loaded for review-stack task/deploy execution, and (b) the exact `Stack`/`ReviewStack` checkout/fetch code, which could not be read due to tool errors in this session. A partial, already-existing test demonstrates the missing filter on `machine_env` (not fork-specific):
```ruby
# test/unit/deploy_commands_test.rb (existing pattern, extend with BUNDLE_GEMFILE)
@deploy_spec = stub(
  ...,
  machine_env: { 'GLOBAL' => '1', 'BUNDLE_GEMFILE' => '/tmp/attacker/Gemfile' },
  ...
)
@commands.stubs(:deploy_spec).returns(@deploy_spec)
command = @commands.install_dependencies.first
assert_equal '/tmp/attacker/Gemfile', command.env['BUNDLE_GEMFILE']  # currently passes - no filter
```
This confirms `machine_env` is unfiltered, but does not by itself prove the fork-PR/label reachability claimed in the question; that requires reading `app/models/shipit/review_stack.rb` and the git-fetch/checkout commands used for review stacks, which was not accessible in this session.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end
