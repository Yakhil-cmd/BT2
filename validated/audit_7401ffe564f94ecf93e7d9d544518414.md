Based on the investigation of the webhook signature-verification path, I can identify a valid analog to the smart-contract "mitigation not covering all scenarios" bug class: a binding gap between the GitHub organization used to select/verify the HMAC key and the repository the payload actually acts on.

### Title
Webhook signature verification selects the HMAC key from an unverified payload field, allowing cross-organization/repository spoofing - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App's `webhook_secret` to use for HMAC validation based on `repository.owner.login` (or `organization.login`) read directly out of the *unauthenticated* raw JSON body, before that body's signature has been validated against any key. [1](#0-0) [2](#0-1) 

### Finding Description
`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` configured for whatever organization login string appears in the JSON body, then calls `verify_webhook_signature` on that app. [3](#0-2)  shows that when the resolved app's `webhook_secret` is blank (a documented, supported configuration state — see `config/secrets.development.shopify.yml` where `webhook_secret: # nil` is a valid example), `verify_webhook_signature` **short-circuits and returns `true` unconditionally**: [4](#0-3) 

The equality this mitigation is supposed to enforce is: *`organization whose secret authenticated the request` == `repository the handler subsequently mutates`*. Nothing in `WebhooksController#create` or the downstream handlers re-derives `repository.owner.login` from a trusted source after signature check; the same untrusted body used to pick the verification key is passed straight to the handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`). [5](#0-4) 

In a multi-organization deployment (the documented "Using Multiple Github Applications" setup, `docs/setup.md`), each org has its own independent `webhook_secret`. Because the picking of *which* secret to check is itself driven by attacker-controlled JSON (`repository.owner.login`), an attacker only needs to find **one** configured organization whose `webhook_secret` is blank/unset (a state the engine explicitly supports, e.g. for local/dev orgs sharing the same instance) to make `verify_webhook_signature` return `true` for arbitrary payload content — including a `repository.full_name`/fields pointing at a completely different, fully-configured organization's repository. The handler layer then acts on that forged repository/stack (e.g., syncing pushes, posting commit statuses, or team membership changes) without any re-validation that the "authenticated" org matches the repository actually referenced by the rest of the payload.

### Impact Explanation
This breaks the credential/repository binding required by the engine: a request can be accepted as authentic for one organization while the payload content and downstream side effects (queued jobs, membership/team mutations, commit statuses) target a different repository/org entirely, none of whose secret was ever checked. Depending on which webhook event is exploited, this can enable unauthorized state changes on stacks/repositories the attacker does not control (e.g. `membership` handler creating/removing `Team`/`Membership` records, or `push`/`status` handlers driving `GithubSyncJob`/status updates) — a cross-repository write, satisfying the Critical impact bar for this engine.

### Likelihood Explanation
Requires: (1) a multi-org Shipit deployment (documented, supported configuration), and (2) at least one configured organization with a blank/nil `webhook_secret` — a state the shipped example config (`config/secrets.development.shopify.yml`) treats as normal/expected, not merely theoretical misconfiguration. Given that, exploitation requires no authentication, no `ApiClient` token, and no GitHub App private key — only crafting a raw HTTP POST to the public `/github/webhooks` endpoint with a mismatched `owner.login` vs. other repository identifiers in the body.

### Recommendation
Do not let untrusted payload content select the verification key when the resolved organization has no `webhook_secret` configured; treat a missing secret as verification failure rather than an implicit bypass. Additionally, after verifying the signature for organization `X`, assert that every repository/organization reference used later in the handler pipeline for that request is scoped to `X` before dispatching to handlers, rather than trusting the raw payload again downstream.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orgA` (no `webhook_secret` set) and `orgB` (real repo, real `webhook_secret`).
2. POST to `/github/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `orgA`; `Shipit.github(organization: 'orgA').verify_webhook_signature` returns `true` unconditionally because `orgA.webhook_secret` is blank — no valid `X-Hub-Signature` is required.
4. `Shipit::Webhooks.for_event('push')` handlers receive the full payload and act on `full_name: "orgB/victim-repo"`, triggering sync/deploy-adjacent jobs for a stack the attacker never authenticated against.

**Uncertainty note:** I was unable to open `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, `membership_handler.rb`, and `handler.rb` directly in this final iteration (tool calls were cut off), so the exact field(s) (`full_name` vs. separately-looked-up `Repository.from_github_repo_name`) each handler uses to resolve the target `Stack`/`Repository` could not be pinned to exact line numbers. The root cause in `WebhooksController#verify_signature` / `GitHubApp#verify_webhook_signature` (the key-selection-from-untrusted-data plus blank-secret bypass) is confirmed directly from source, but confirming the precise downstream handler code path would benefit from a follow-up read of the `app/models/shipit/webhooks/handlers/*.rb` files.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
