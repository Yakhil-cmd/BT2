### Title
Cross-org signature/authorization confusion in `WebhooksController#verify_signature` lets an org verified by its own webhook secret overwrite a victim repository's `PullRequest#labels` via `LabelCapturingHandler`, injecting attacker-chosen env KEYs into the victim's `ReviewStack#env` - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the per-organization `GitHubApp`/webhook secret using `repository.owner.login` from the unverified JSON body, then verifies the raw body's HMAC against that org's secret. Every downstream `pull_request` handler, including `LabelCapturingHandler`, instead resolves the target `Repository`/`Stack` using a *different* field, `repository.full_name`, with no check that its organization segment matches the `owner.login` used for signature selection. In a multi-tenant deployment (`config/secrets.yml` with per-organization `github:` sub-keys, as documented in `docs/setup.md` "Using Multiple Github Applications"), this lets an org that legitimately controls its own webhook secret forge a `labeled`/`unlabeled` payload that is cryptographically valid for its own org but names a victim org's repository, causing `LabelCapturingHandler#capture_labels` to overwrite the victim's `PullRequest#labels` with attacker-chosen strings, which are later merged as environment variable KEYs into `ReviewStack#env` and ultimately `TaskCommands#env`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:

`Shipit.github(organization: repository_owner).webhook_secret` (used to verify the signature) **should equal** `the org that owns Shipit::Repository.from_github_repo_name(params.repository.full_name)` (the org whose `Stack`/`PullRequest` is actually mutated).

Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)`, verifying the raw HMAC-signed body against that org's `webhook_secret` [1](#0-0) .
- In multi-org config, `Shipit#github` looks up `github_app_config(organization)` keyed strictly by the `organization` argument (i.e. `repository.owner.login`), and raises only if that org is *unknown*, not if it mismatches anything else [2](#0-1) .
- `LabelCapturingHandler#repository` and `#capture_labels` instead resolve the target repository/stack using `params.repository.full_name`: `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and then `stack.pull_request.update!(labels: params.pull_request.labels.map(&:name))` [3](#0-2) .
- `repository.owner.login` and `repository.full_name` are independent JSON fields in the same unsigned-until-delivery body; nothing in `ExplicitParameters` schema, `drop_unhandled_event`, or the handler enforces that the org segment of `full_name` matches `owner.login`. The HMAC only proves the body was signed with *some* org's secret, not that the org named in `full_name` is the signing org.
- `ReviewStack#env` merges `pull_request.labels` into the environment as `label_name.upcase => "true"` [4](#0-3) .
- `TaskCommands#env` merges `@stack.env` (and thus the label-derived keys) into the final environment passed to `Command.new(command_line, env:, ...)` for `deploy`/task execution [5](#0-4) , confirmed by `test/lib/shipit/task_commands_test.rb` and `test/lib/shipit/deploy_commands_test.rb` showing labels become literal env keys (`WIP`, `BUG`) [6](#0-5) .

Attacker request: attacker owns/administers "attacker-org" (which has legitimately been onboarded into the same multi-tenant Shipit instance, with its own configured `webhook_secret`). Attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, a body where `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` and thus `verify_webhook_signature` succeeds using attacker-org's own secret) but `repository.full_name = "victim-org/victim-repo"` and `pull_request.labels = [{"name" => "arbitrary_key"}]`, `action: "labeled"` (or `unlabeled`), targeting a PR `number` that matches a real, existing victim `ReviewStack`'s `PullRequest`. `verify_signature` passes; `LabelCapturingHandler` finds the real victim repository/stack via `full_name` and overwrites `PullRequest#labels`.

Existing guards do not stop this: `drop_unhandled_event` only checks the event name is registered; the `ExplicitParameters` schema only validates types/presence, not cross-field consistency; `Repository` validations don't validate that `full_name`'s org matches any request-level claim; there is no code anywhere comparing `repository_owner` (verification key) against `repository.full_name`'s owner segment (mutation target).

### Impact Explanation
The attacker, holding only their own org's webhook secret (in a multi-org Shipit deployment), can overwrite an arbitrary victim `PullRequest#labels`, which are injected as environment variable KEYs into `ReviewStack#env` and subsequently `TaskCommands#env`, reaching `Command#run`/`PTY.spawn` during the victim's own deploy/task execution. This is a payload from one org mutating another org's stack/PR state and injecting attacker-chosen data into the victim's deploy environment - matching the Critical category ("a payload for one repository mutating another's stack ... env-key injection reaching PTY.spawn"). The attack is repeatable against any victim repository/stack that already has a `PullRequest` row, for every `labeled`/`unlabeled`/`reopened` event the attacker chooses to forge, and generalizes across all victim tenants sharing the same multi-org Shipit instance.

### Likelihood Explanation
Preconditions: (1) Shipit configured in the multi-org mode (`github:` with per-org sub-keys) — single-org deployments are not affected since `Shipit#github` ignores the `organization` argument when `github_default_organization` is nil and always resolves the single global config [7](#0-6) . (2) Attacker controls at least one onboarded org's webhook secret (i.e., is a legitimate tenant of the shared instance). (3) A victim `ReviewStack` with a `PullRequest` row must already exist. Given these, attacker cost is a single crafted HTTP POST with no live GitHub interaction required, fully scriptable, and repeatable at will.

### Recommendation
In `LabelCapturingHandler` (and all `pull_request`/`push`/`status` handlers that resolve repository via `params.repository.full_name`), require that the organization segment of `repository.full_name` matches the `repository_owner` used to select and verify the webhook secret in `WebhooksController#verify_signature`. Concretely, pass the verified `repository_owner` (or the resolved `GitHubApp` organization) through to the handler dispatch and have `Handler#repository`/`#stacks` reject any payload whose `full_name` org segment differs from the verified org, or centrally enforce this equality check in `WebhooksController#create` before dispatching to handlers.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, using `secrets_double_github_app.yml`-style multi-org config):
```ruby
test "labeled event verified with OrgOne's secret cannot mutate OrgTwo's stack" do
  # Setup: multi-org secrets with OrgOne and OrgTwo, each with distinct webhook_secret
  victim_stack = create_review_stack(repo_full_name: "OrgTwo/victim-repo", pr_number: 42)
  attacker_secret = Shipit.github(organization: "OrgOne").webhook_secret

  payload = payload_parsed(:pull_request_labeled)
  payload["repository"]["owner"]["login"] = "OrgOne"     # selects OrgOne's secret for verification
  payload["repository"]["full_name"] = "OrgTwo/victim-repo"  # names victim repo/stack
  payload["number"] = 42
  payload["pull_request"]["labels"] = [{ "name" => "injected_key" }]
  body = payload.to_json
  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)}"

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = signature

  post :create, body:, as: :json
  assert_response :ok  # verify_signature passes using OrgOne's secret

  # Equality check BEFORE: verified_org ("OrgOne") != owning_org("OrgTwo/victim-repo") -> "OrgOne" != "OrgTwo"
  assert_not_equal "OrgOne", victim_stack.repository.full_name.split("/").first

  victim_stack.reload
  assert_includes victim_stack.pull_request.labels, "injected_key"  # victim's labels mutated by attacker-org's request

  task = shipit_tasks(:shipit_restart)
  task.stack = victim_stack
  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["INJECTED_KEY"]  # attacker-chosen KEY reaches env passed to PTY.spawn
end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
