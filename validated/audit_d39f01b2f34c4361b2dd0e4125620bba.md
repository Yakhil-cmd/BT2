### Title
Unbounded route contracts can inject hidden authorization children and steal unrelated caller assets - (File: contracts/controller/src/strategies/swap.rs)

### Summary
User-controlled swap routes can cause the configured router to invoke arbitrary pool contracts. During that nested call, a malicious pool can request authorization for an unrelated token transfer from the caller; Soroban records it as a child of the caller’s strategy authorization and executes it if the poisoned authorization tree is signed. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept opaque `swap` bytes and ultimately call `router.execute_strategy(&controller, &amount_in, swap)`. The controller authorizes only its own exact input-token transfer, but does not restrict the contract addresses reached through the route. [3](#0-2) [4](#0-3) 

The router obtains pool, token-in, and token-out addresses from the payload’s address registry and dispatches the selected venue without a pool allowlist. [5](#0-4)  A malicious contract implementing the selected venue ABI can therefore execute arbitrary code in the nested call and invoke `token.transfer(victim, attacker, amount)`, where `victim` is the strategy caller rather than the controller. [6](#0-5) 

The repository’s threat model confirms that such a transfer is recorded as a child of the caller’s authorization entry and succeeds when the caller signs the recorded tree. [7](#0-6)  The controller’s measured input/output checks and final account-risk checks do not inspect or constrain unrelated transfers from the caller’s wallet. [8](#0-7) 

### Impact Explanation
An attacker who gets a victim to submit an attacker-crafted route can steal arbitrary token balances held directly by the victim, including assets unrelated to the lending position or routed input. [9](#0-8) [10](#0-9) 

This is theft of user funds beyond the declared swap amount, while the route can still return sufficient output for all protocol settlement and solvency checks to pass. [10](#0-9) 

### Likelihood Explanation
The attacker must convince the victim to use a malicious route and sign the simulation-generated authorization tree containing the extra transfer. [11](#0-10)  The required route is otherwise fully permissionless: pool addresses are supplied through the payload and no venue allowlist prevents an attacker-deployed contract from being reached. [5](#0-4) 

Clients that present only the top-level strategy call or treat simulation output as authoritative can expose users to the hidden child authorization, matching the user-interaction-dependent nature of the source vulnerability. [12](#0-11) 

### Recommendation
Restrict route execution to explicitly allowlisted venue contracts, or bind each route operation to a governance-approved venue/pool registry before dispatch. [5](#0-4) 

Until routes are constrained, transaction builders and wallets must reject any strategy authorization tree containing unexpected child invocations; an honest composed swap should not contain a caller-owned token transfer beyond the protocol’s expected authorization surface. [13](#0-12) 

### Proof of Concept
The repository test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the complete behavior using `swap_collateral(caller, account_id, current, amount, new, swap)`: Alice supplies USDC, holds an unrelated wallet token, and submits a route containing an attacker-controlled pool. [14](#0-13) [15](#0-14) 

The rogue pool calls `token.transfer(alice, attacker, WALLET_BALANCE)` from inside the route execution. [6](#0-5)  Recording-mode simulation attaches that unrelated transfer as a child under Alice’s `swap_collateral` authorization, while the route still pays fair ETH output. [16](#0-15) 

An honest signed tree rejects the transfer, but the simulation-produced poisoned tree executes it, reducing Alice’s unrelated wallet balance to zero and crediting the attacker. [17](#0-16)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
