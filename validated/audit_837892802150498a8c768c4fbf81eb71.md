### Title
Task-declared `PATH` environment variable overrides the safe `PATH` prefix in `Command#unbundled_env`, enabling RCE via PATH hijacking - ([File: lib/shipit/command.rb])

### Summary
`Command#unbundled_env` builds the environment for `PTY.spawn` by merging `BASE_ENV`, then a safe `PATH` (`Shipit.shell_paths.join(':')` prefix), and finally `@env.stringify_keys` **last**. Because `EnvironmentVariables#permit` only checks a variable name against the task's own whitelist and has no reserved-name blacklist, a task author can declare `PATH` as a permitted variable in `shipit.yml`, and any caller of `Api::TasksController#trigger` can then set `env: {'PATH' => '/tmp/attacker'}` to overwrite the safe `PATH` used to spawn every step's command.

### Finding Description
The claimed invariant is:
`Command#unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for all `@env`.

This is broken by the following chain:
- `lib/shipit/command.rb:103-105`: `unbundled_env` computes `BASE_ENV.merge('PATH' => safe_path).merge(@env.stringify_keys)` — `@env` is merged **last**, so if `@env` contains a `PATH` key, it wins. [1](#0-0) 
- `lib/shipit/environment_variables.rb:35-44` (`sanitize_env_vars`, called from `permit`): only checks `allowed_variables.include?(k)` against the task/stack's own declared variable names — there is no blacklist of reserved names such as `PATH`, `LD_PRELOAD`, `BUNDLE_PATH`, etc. [2](#0-1) 
- `app/models/shipit/task_definition.rb:63-65` (`filter_envs`) calls `EnvironmentVariables.with(env).permit(variables)` with the task's own `variables` list from `shipit.yml`. If `shipit.yml` declares `variables: [{name: 'PATH'}]`, `PATH` is a permitted key. [3](#0-2) 
- `lib/shipit/task_commands.rb:33-48` (`TaskCommands#env`) merges `@task.env` **last**, after all other safe defaults (`SHIPIT_USER`, `GIT_COMMITTER_*`, etc.), so a task-declared `PATH` here also overrides everything upstream. [4](#0-3) 
- `app/controllers/shipit/api/tasks_controller.rb:17-26` (`trigger`) accepts an arbitrary `env` Hash param from the API caller and passes it straight to `stack.trigger_task(...)`, ultimately reaching `Task#env`/`filter_envs`. [5](#0-4) 

Attack: a user with deploy permission on the stack (required by `require_permission :deploy, :stack, only: %i[trigger abort]`) who controls or has committed a `shipit.yml` declaring `variables: [{name: 'PATH'}]` for a task, calls `POST /stacks/:owner/:repo/:branch/api/tasks/:task_name/trigger` with `env: {'PATH' => '/tmp/attacker'}`. `filter_envs` permits it (whitelist match), `Task#env` stores it, `TaskCommands#env` and `Command#unbundled_env` both merge it last, and any step command resolved via bare name (`git`, `bundle`, `cap`, etc.) executes the attacker's binary from `/tmp/attacker` instead of the trusted path.

Existing guards (`require_permission!`, `EnvironmentVariables#permit`, model validations) check only *authorization to trigger the task* and *whitelist membership*, not *semantic safety of the variable name*. None of them block `PATH` specifically.

### Impact Explanation
This allows the triggering user (who must already have deploy permission on the stack, and control/influence over the stack's `shipit.yml` task variable declarations) to achieve RCE with the privileges of the Shipit worker process, on the deploy host, by hijacking `PATH` for any subsequently-invoked bare command name in the task's steps. This matches the "Critical - RCE on the deploy host via Command/PTY.spawn" category. The blast radius is scoped to the stack whose `shipit.yml` opts a task into a `PATH` variable, but it directly compromises the deploy host running that stack (and potentially secrets/tokens available to other stacks' commands if the host is shared).

### Likelihood Explanation
The attacker needs: (1) a `shipit.yml` for the target stack that declares `PATH` as a permitted task variable (this requires either repo-write access sufficient to introduce the `shipit.yml` change and get it merged/deployed, or that such a definition already exists), and (2) deploy permission on the stack to call the `trigger` API. This is not achievable by a fully unprivileged, unauthenticated GitHub user with no stack access — it requires someone who can both shape the stack's `shipit.yml` and trigger tasks, i.e., a deploy-permitted stack user. Given those preconditions, the exploit is trivial and 100% reliable/repeatable against any task in that stack.

### Recommendation
In `Command#unbundled_env`, do not allow `@env` to override `PATH` (and other security-sensitive variables like `BUNDLE_*`, `LD_PRELOAD`, `RUBYOPT`, `GIT_ASKPASS` if externally set). Reorder the merge so the safe `PATH` is applied last, or explicitly strip disallowed keys from `@env` before merging:
```ruby
def unbundled_env
  BASE_ENV.merge(@env.stringify_keys).merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}")
end
```
Additionally, add a reserved-name blacklist in `EnvironmentVariables#permit` / `TaskDefinition#filter_envs` / `VariableDefinition` validation to reject variable declarations named `PATH` or other environment variables that affect process/interpreter resolution.

### Proof of Concept
```ruby
# test/unit/command_test.rb (minitest)
def test_unbundled_env_path_is_not_overridable_by_task_env
  command = Shipit::Command.new('git --version', env: { 'PATH' => '/tmp/attacker' }, chdir: '.')
  safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"

  assert_equal safe_path, command.unbundled_env['PATH'],
    "PATH must not be overridable by task/deploy-declared env vars"
  refute_equal '/tmp/attacker', command.unbundled_env['PATH']
end
```
This assertion currently fails against `lib/shipit/command.rb:103-105`, confirming `unbundled_env['PATH']` equals `/tmp/attacker` rather than the safe prefix, demonstrating the PATH-hijack RCE finding.
