### Title
Webhook signature verification keys off an attacker-controlled `repository.owner.login`/`organization.login` field, allowing cross-organization forged webhooks that escalate into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App configuration (and therefore the `webhook_secret` used to validate the HMAC) using an organization name that is read directly out of the *unverified* request body, before the signature is checked. Verification itself is a no-op whenever that organization's configured `webhook_secret` is blank. Because the field used to choose the verification key (`repository.owner.login`) is never bound to the field the downstream handlers use to decide which repository/stack to mutate (`repository.full_name`), an attacker can pick any organization configured on the instance with no (or an easily satisfied) webhook secret to make verification pass trivially, while still supplying an arbitrary `repository.full_name` targeting a different, victim-owned stack. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` derives the organization purely from payload content: [1](#0-0) 

That value is used to fetch the app config and verify the signature: [2](#0-1) 

`verify_webhook_signature` unconditionally returns `true` when the resolved app has no `webhook_secret` configured: [3](#0-2) 

Once verification "passes," `params` (the entire attacker-controlled JSON body) is dispatched unchanged to every registered handler for the event: [4](#0-3) 

Handlers, however, do **not** use `repository.owner.login` (the field that gated signature verification) to select the target — they use `repository.full_name`: [5](#0-4) 

So the identity used to authenticate the webhook (owner login of an org that may have no secret configured) is completely decoupled from the identity used to decide what gets mutated (`repository.full_name`, which can point at any stack tracked by the Shipit instance, including one that belongs to a different, properly-secured organization).

This is directly exploitable through the `membership` event, whose handlers create `Team`, `User`, and `Membership` records straight from payload content (as exercised by `":membership creates the mentioned team on the fly"` / `":membership creates the mentioned user on the fly"` style flows in the controller). Because Shipit's authorization model gates privileged actions on membership in `Shipit.github_teams` (the OAuth-configured trusted teams), an attacker who can get a forged `membership` webhook accepted can create/attach a `Membership` linking an arbitrary GitHub login (including their own) to a `Team` whose handle matches one of `Shipit.github_teams`, without ever needing real GitHub organization membership or a session/token on the instance.

### Impact Explanation
This crosses a credential/authentication boundary with no attacker-held Shipit credential: an unauthenticated caller who only needs to guess or discover one organization configured on the instance without a webhook secret can forge events that are dispatched as if legitimately verified. The most severe outcome is privilege escalation into `Shipit.github_teams` authorization via the `membership` event handlers, which is explicitly listed as a "High" qualifying impact. A push-event variant of the same flaw can also force `stack.sync_github` on stacks unrelated to the "authenticating" organization, priming unauthorized deploy/merge flows.

### Likelihood Explanation
Requires only that at least one GitHub App organization configured on the multi-tenant Shipit instance has a blank/absent `webhook_secret` (a state the configuration format explicitly supports per-organization) — a realistic scenario for instances onboarding new orgs before wiring up their secret, or intentionally running one low-security/test org alongside production orgs. No repository write access, API token, or session is needed; the request is a plain unauthenticated HTTP POST to the public webhooks endpoint.

### Recommendation
Bind the field used for signature verification to the same field used for authorization/mutation: verify the signature using the app/organization derived from `repository.full_name` (or otherwise cryptographically tie `repository.owner.login` to `repository.full_name`) rather than trusting a payload-supplied owner login independently. Additionally, do not treat a missing `webhook_secret` as an automatic pass — require an explicit, operator-acknowledged "insecure" flag per organization, and reject webhooks whose declared repository does not belong to the organization used for verification.

### Proof of Concept
1. Instance is configured with `Shipit.github` entries for `OrgA` (has `webhook_secret` set, owns the victim stack `OrgA/prod-app`) and `OrgB` (no `webhook_secret` configured).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "Shipit Deployers", "slug": "shipit-deployers", "url": "https://github.com/..." },
  "member": { "login": "attacker" },
  "repository": null,
  "organization": { "login": "OrgB" }
}
```
3. `repository_owner` resolves to `OrgB` (`app/controllers/shipit/webhooks_controller.rb:61`), `Shipit.github(organization: 'OrgB')` returns the app config with no `webhook_secret`, so `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header (`lib/shipit/github_app.rb:76-83`).
4. The membership handler processes the forged payload and creates a `Membership` linking GitHub user `attacker` to a `Team` matching one of `Shipit.github_teams`, without the attacker ever holding a Shipit session, API token, or real GitHub org membership.
5. Attacker now satisfies Shipit's team-based authorization checks for actions gated on `Shipit.github_teams`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
