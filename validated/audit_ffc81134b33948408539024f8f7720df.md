### Title
Webhook signature check is keyed off an attacker-controlled organization field that is decoupled from the repository the push handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the incoming signature against using a field taken directly from the unauthenticated request body, while the actual `Shipit::Webhooks::Handlers::PushHandler` that executes the event resolves the target `Repository`/`Stack` from a completely different field of the same body. These two fields are never cross-checked against each other, so the "organization used to authenticate" and the "repository written to" are not the same binding.

### Finding Description
`verify_signature` computes the organization to verify against straight from the JSON payload before any signature has been validated: [1](#0-0) [2](#0-1) 

It then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. In `GitHubApp#verify_webhook_signature`, if that organization's config has no `webhook_secret` configured, verification is skipped entirely: [3](#0-2) 

`webhook_secret` is an optional, per-organization setting (`nil` by default in every documented configuration template): [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (either because a legitimate signature was forged for an org whose secret the attacker knows, or, more importantly, because the selected org has no `webhook_secret` set at all), the request proceeds to `WebhooksController#create`, which dispatches to `PushHandler`. Crucially, the handler identifies which `Repository`/`Stack` to act on using an entirely different payload field — `repository.full_name` — with no relation to `repository.owner.login` used for signature selection: [6](#0-5) [7](#0-6) 

This is precisely the "organization authenticated versus repository written" binding break called out in the rules: `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the target `Stack`) are independent, attacker-controlled fields of the same unauthenticated JSON body. In a multi-organization Shipit deployment (`Shipit.github_organizations`, `github_app_config`, described in `docs/setup.md`), an attacker can pick any configured organization name that has `webhook_secret` unset (`nil`) and put an arbitrary `repository.full_name` (belonging to a different, secured organization) in the same payload. `verify_webhook_signature` returns `true` unconditionally for that org since `webhook_secret` is blank, and the handler then acts on the unrelated repository's stack. [8](#0-7) 

This calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the branch matching the attacker-supplied `ref`, which enqueues `Shipit::GithubSyncJob` with an attacker-chosen `expected_head_sha`: [9](#0-8) 

### Impact Explanation
This lets an unauthenticated attacker trigger sync/deploy-adjacent actions (`GithubSyncJob`, `CacheDeploySpecJob`) against a stack belonging to an organization/repository the attacker does not control, purely by naming an org with no `webhook_secret` as the "owner" while pointing `repository.full_name` at the victim repo. Depending on the target stack's continuous-deployment configuration, this can escalate to an unauthorized deploy, matching the "unauthorized deploy" Critical impact bucket in the rules.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured with multiple GitHub organizations where at least one has no `webhook_secret` set — a configuration explicitly supported and documented, and the default/example value for `webhook_secret` is `nil` — and (2) no other cross-check between `repository.owner.login` and `repository.full_name`. Given `webhook_secret` is optional and commonly left unset for orgs added later or in staging, this is plausible in real deployments, but it does depend on this specific multi-org + unset-secret configuration, which lowers overall likelihood somewhat.

### Recommendation
- In `WebhooksController#verify_signature`, additionally verify that `repository.owner.login` matches the owner embedded in `repository.full_name` (or otherwise ensure the org used for secret lookup is authoritative for the repository the handler will act on) before dispatching to handlers.
- Consider making `webhook_secret` mandatory (fail closed) rather than optional per organization, since `verify_webhook_signature` currently treats an absent secret as an automatic pass.

### Proof of Concept
Configuration (multi-org, per `docs/setup.md`):
```yaml
production:
  github:
    attacker-org:
      app_id: 1
      installation_id: 1
      webhook_secret: # left blank
    victim-org:
      app_id: 2
      installation_id: 2
      webhook_secret: real-secret
```
Request (no signature needed):
```
POST /webhooks
X-Github-Event: push
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/private-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
`repository_owner` resolves to `attacker-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (absent/garbage) `X-Hub-Signature` header. `PushHandler` then resolves the stack via `repository.full_name = "victim-org/private-repo"` and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, unrelated to `attacker-org`'s permissions.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
