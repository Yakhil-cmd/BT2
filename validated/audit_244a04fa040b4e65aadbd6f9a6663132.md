### Title
Race condition in concurrent private-payment chain validation allows double-spend of a private-asset output - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments` processes multiple pending private payment chains **in parallel**, each through its own independent DB connection/transaction, with no mutex serializing validation of the *same* private output across those parallel branches. This mirrors the CVE-2020-6575 bug class (a race across an IPC/validation boundary that lets a malicious party win a TOCTOU race and bypass an integrity check), but here the racing party is a private-payment counterparty who can submit two conflicting private chains spending the same hidden coin.

### Finding Description
Private payment chains delivered peer-to-peer (not yet part of a fully broadcast/validated on-chain unit) are queued and later validated by `handleSavedPrivatePayments`, which explicitly fans them out concurrently: [1](#0-0) [2](#0-1) 

Each chain is handed to `privatePayment.validateAndSavePrivatePaymentChain`, which opens its **own** DB connection and its own `BEGIN`/`COMMIT` transaction — with no address- or output-scoped mutex around it: [3](#0-2) 

That function ultimately calls `divisibleAsset.validateAndSavePrivatePaymentChain` / `indivisibleAsset.validateAndSavePrivatePaymentChain`, which run `validation.initPrivatePaymentValidationState` + `validation.validatePayment` and then directly `INSERT`/`UPDATE` the `inputs`/`outputs` rows for the spent output: [4](#0-3) [5](#0-4) 

This is a *separate* code path from the standard unit-validation pipeline in `validation.js`'s `validate()`, which serializes all validation of a given unit under `mutex.lock(arrAuthorAddresses, ...)`: [6](#0-5) 

The private-payment ingestion path does not take that (or any equivalent) lock, so two chains that both spend the *same* private output (classic double-spend forged by the payer, sent to two different recipients/cosigners) can be validated by two concurrent connections at the same time. The double-spend detection logic itself, `checkInputDoubleSpend`, only takes a mutex (`"private_write"`) around the final `UPDATE ... SET is_unique=NULL` that demotes a losing conflicting spend — the preceding `SELECT` that decides whether a conflict even exists runs unguarded, on each connection's own transaction snapshot: [7](#0-6) 

Because each parallel private-chain validation has its own connection/transaction and the pre-lock detection query can see a snapshot in which the other transaction's write is not yet visible, two conflicting chains spending the same hidden coin can both pass the double-spend check and both get their `inputs`/`outputs` rows committed as valid spends of the same source output, exactly the TOCTOU race pattern described in the Chrome CVE (racing a validated action against a state change to slip past a security boundary).

### Impact Explanation
A malicious private-payment counterparty (payer) can construct two private payment chains spending the same private-asset output/coin and deliver both concurrently (e.g., to two cosigners on the same device, or by re-queuing while the first is mid-validation). If both are accepted as valid locally due to the race, the wallet/node ends up believing two independent, conflicting spends of the same private coin are each legitimate — a double-spend of a private-asset output, i.e., private-asset supply/ownership inconsistency and potential loss of funds for the victim recipient who believes they received a valid, unique coin.

### Likelihood Explanation
The race window requires two connections opening near-simultaneously and validating conflicting chains before either commits — feasible given `async.each` explicitly runs "different chains in parallel," and an attacker fully controls timing of chain delivery to the victim (per the queuing/`unhandled_private_payments` mechanism in `network.js`). This is a narrow but attacker-triggerable timing race rather than a reliably one-shot exploit, consistent with a "High" (not "Critical") race-condition class similar to the referenced Mojo race.

### Recommendation
Serialize validation/saving of private payment chains that could conflict — e.g., acquire a mutex keyed by the spent output (`src_unit`/`src_message_index`/`src_output_index`, or owner address) for the *entire* validate-then-write sequence in `validateAndSavePrivatePaymentChain` (both `divisible_asset.js` and `indivisible_asset.js`), not just around the final `UPDATE` in `checkInputDoubleSpend`. Extend the same lock scope used by `handleSavedPrivatePayments`'s parallel `async.each` to prevent two chains touching the same source output from running concurrently, mirroring the `mutex.lock(arrAuthorAddresses, ...)` protection already used for standard on-chain unit validation.

### Proof of Concept
1. Attacker (payer) owns a private-asset coin (hidden output O).
2. Attacker crafts two private payment chains, Chain A and Chain B, each spending output O to a different recipient/cosigner, and sends both nearly simultaneously (e.g., via hub relay to two devices, or forcing both into `unhandled_private_payments` before either is processed).
3. `handleSavedPrivatePayments` picks up both rows and validates them concurrently via `async.each`, each opening an independent DB connection/transaction as shown in `network.js:2458-2504` and `private_payment.js:45-59`.
4. Both connections run `checkInputDoubleSpend`'s unguarded SELECT (`validation.js:2258-2296`) against their own transaction snapshot before either has committed; each observes no existing conflicting spend and both proceed to `INSERT` their respective `inputs`/`outputs` rows.
5. Both chains commit successfully, leaving two conflicting valid spends of the same private output O recorded across the two recipients' devices/nodes — a private-asset double-spend.
