### Title
Unauthenticated webhook spoofing via missing per-organization `webhook_secret` bypasses signature verification and forges events for any repository - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the organization resolved from the *inbound* payload's `repository.owner.login` field. In a multi-organization Shipit deployment, an attacker who can reach the `/webhooks` endpoint can select which organization's `GitHubApp` instance is used for verification simply by setting `repository.owner.login` in the JSON body to an organization that has no `webhook_secret` configured, while pointing the actual target of the action (`repository.full_name`, used by every event handler) at a completely different, legitimately-registered repository/stack. This breaks the intended binding: "the organization whose credential validated this delivery" must equal "the repository the event handlers act on."

### Finding Description
`WebhooksController#verify_signature` selects the verifying `GitHubApp` using attacker-controlled payload data: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the unverified JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), *before* any signature is checked, and is used to fetch `Shipit.github(organization: repository_owner)`.

`GitHubApp#verify_webhook_signature` then bypasses verification entirely if that organization's config has no `webhook_secret`: [3](#0-2) 

The sample multi-org secrets file in this repo explicitly shows organizations configured with a blank/`nil` `webhook_secret` as a supported configuration shape: [4](#0-3) 

Meanwhile, every webhook handler resolves the actual target repository/stack from a *different* payload field, `repository.full_name`, which is never cross-checked against the `repository.owner.login` used for verification: [5](#0-4) [6](#0-5) 

So the binding actually enforced is: `verified_organization(payload.repository.owner.login) == true (if org has no secret)`, while the binding that should hold for a trusted action is `verified_organization == owner_of(payload.repository.full_name)`. These are never compared. An attacker only needs to know (or guess) the name of one org configured without a `webhook_secret` (`repository.owner.login`) to fabricate an entirely unsigned, unauthenticated webhook body whose `repository.full_name`, `after` SHA, commit `state`, `check_suite`, `membership`, or `pull_request` fields target any other organization's stacks tracked by this Shipit instance.

### Impact Explanation
This is an unauthenticated-read/unauthorized-write class issue on core Shipit state:
- `push` events let an attacker force `stack.sync_github(expected_head_sha:)` for arbitrary stacks with an attacker-chosen `after` SHA [7](#0-6) .
- `status`/`check_suite` handlers let an attacker inject fabricated commit statuses/check runs, which feed directly into deploy-gating and merge-queue logic (`MergeRequest::StatusChecker`, `required_statuses`), potentially allowing an unauthorized deploy or merge to be unblocked by forged CI-green statuses [8](#0-7) .
- `membership` events allow arbitrary team/user membership creation/removal [9](#0-8) , which can affect `Shipit.github_teams` authorization if teams influence access control.

This matches the required "High" bar: escalation into `Shipit.github_teams` authorization and/or an unauthorized deploy/merge via forged status checks, achievable entirely unauthenticated.

### Likelihood Explanation
Requires a Shipit deployment configured for multiple GitHub organizations where at least one organization entry has no `webhook_secret` set — a configuration explicitly shown as valid in this repo's own sample secrets file (`config/secrets.development.shopify.yml`) and permitted by `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` fallback. Given the engine's own example config demonstrates this shape and provides no validation preventing it in production multi-org setups, it is a realistic operational configuration rather than a purely theoretical one.

### Recommendation
- Require `webhook_secret` to be present for every organization when more than one organization is configured, and fail closed (reject the request) rather than `return true` when it is absent.
- Bind webhook trust to the actual acted-upon repository: derive the verifying organization from `repository.full_name`'s resolved `Repository`/`Stack` record (already-registered, trusted mapping) rather than from the unverified `repository.owner.login`/`organization.login` fields in the raw payload, or explicitly assert `repository.owner.login` matches the owner implied by `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Deploy Shipit with two organizations configured: `trusted-org` (has `webhook_secret` set, hosts real tracked repositories/stacks) and `no-secret-org` (no `webhook_secret`, as shown valid in `config/secrets.development.shopify.yml`).
2. POST to `/webhooks` with header `X-Github-Event: push` and no `X-Hub-Signature` (or any garbage value), and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "no-secret-org" },
    "full_name": "trusted-org/some-real-repo"
  }
}
```
3. `verify_signature` resolves `github_app = Shipit.github(organization: "no-secret-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (missing/invalid) signature [3](#0-2) .
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("trusted-org/some-real-repo")` [5](#0-4)  and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the real, unrelated `trusted-org` stack — despite the request never being authenticated by `trusted-org`'s credentials.

Note: I could not fully verify from the index whether host applications typically configure multi-org Shipit deployments with a mix of secreted/non-secreted orgs in production (only the bundled sample/dev config was inspectable), so likelihood should be validated against real deployment configuration before treating this as confirmed-exploitable in a specific instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
