### Title
Session Fixation via Missing Session Regeneration on GitHub OAuth Login - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a newly authenticated GitHub identity to the *existing* Rack session simply by writing `session[:user_id]`, without ever calling `reset_session` (or otherwise rotating the session identifier) as part of the login flow. This breaks the intended binding "GitHub identity == the `User` bound to the session," because the session container itself (and therefore its cookie/id) is never rotated at the authentication boundary.

### Finding Description
On successful OmniAuth GitHub callback, the controller does: [1](#0-0) 
It looks up/creates the `User` from the GitHub profile and simply assigns `session[:user_id] = sign_in_github(auth)` plus `session[:authenticated] = true`, then redirects. There is no `reset_session` call anywhere in this method.

Compare this to `logout`, which explicitly calls `reset_session`: [2](#0-1) 

The only place `reset_session` is invoked elsewhere in the authentication path is when a user's stored GitHub token is stale (`requires_fresh_login?`), which is unrelated to a normal fresh login: [3](#0-2) 

Because the session id (and its underlying cookie, in a typical Rails cookie/DB-backed session store) is never regenerated at the moment of authentication, any pre-existing session — including one fixated by an attacker before the victim authenticates — becomes a fully authenticated session for the victim's GitHub identity once the OAuth flow completes. The "identity → session" binding that should be established atomically at login is instead just an in-place mutation of whatever session already existed.

### Impact Explanation
If an attacker can get a victim's browser to carry an attacker-known session identifier prior to login (a classic session-fixation setup — e.g. via a session cookie set over HTTP before HTTPS is enforced, a subdomain-scoped cookie, or any mechanism that plants a session id in the victim's browser), then once the victim completes the GitHub OAuth dance on that same session, the attacker's known session id becomes authenticated as the victim. This grants the attacker full access to the victim's Shipit account — including whatever deploy/rollback/lock privileges the victim's GitHub team membership confers — which the rules explicitly recognize as a valid High-severity impact ("session fixation / forced OAuth completion").

### Likelihood Explanation
Exploiting this does not require possessing any Shipit session, ApiClient token, webhook secret, or GitHub App key — it only requires the ability to plant a session identifier in the victim's browser before they authenticate, a standard prerequisite for session-fixation attacks. Whether that prerequisite is trivially achievable depends on the deployment's cookie/session-store configuration (e.g., `secure`/`SameSite` flags, whether the session cookie is scoped to a broader domain), which is outside the engine's own code, but the engine itself provides no defense-in-depth (session regeneration) at the login boundary regardless of that configuration.

### Recommendation
Call `reset_session` (or otherwise rotate/regenerate the session id) at the start of `GithubAuthenticationController#callback`, before assigning `session[:user_id]` and `session[:authenticated]`, so that a fresh session is always issued at the point of authentication, consistent with the pattern already used in `logout`.

### Proof of Concept
1. Attacker visits the Shipit host (unauthenticated) and captures/plants a known session cookie value `S` in the victim's browser (e.g., via a fixation vector external to this engine, or any shared subdomain cookie scoping).
2. Victim, using the browser holding session `S`, visits Shipit and completes the GitHub OAuth login flow.
3. `GithubAuthenticationController#callback` sets `session[:user_id] = <victim's user id>` on the *same* session `S` without regenerating it. [4](#0-3) 
4. The attacker, still holding session `S`, is now authenticated as the victim and can perform deploys/rollbacks/locks per the victim's team authorization.

```ruby
    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
```

```ruby
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end
```
