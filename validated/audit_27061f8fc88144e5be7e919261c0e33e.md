### Title
Webhook signature verification is keyed on attacker-controlled `repository.owner.login` while stack mutation is keyed on a different attacker-controlled field `repository.full_name`, letting a no-secret organization forge `pull_request` events for any other repository/stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` config using `params.dig('repository','owner','login')`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's config has no `webhook_secret`. Every downstream `pull_request` handler (including `LabelCapturingHandler`) instead resolves the affected `Repository`/`Stack` using a *different* body field, `params.repository.full_name`. Because these two attacker-controlled fields are never checked for consistency, an attacker can pick a registered-but-secret-less organization to pass verification while pointing `repository.full_name` at an entirely different (secret-protected) org/repo, forging writes to that victim's stack.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`params.dig('repository','owner','login')` (used to authenticate) == prefix of `params.repository.full_name` (used to locate the mutated stack).

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` returns `true` immediately when the selected org's `webhook_secret` is blank, with no HMAC check at all: `return true unless webhook_secret` [3](#0-2) .
3. On success, `WebhooksController#create` parses the raw body and dispatches it, unmodified, to every registered `pull_request` handler [4](#0-3) , including `LabelCapturingHandler` [5](#0-4) .
4. `LabelCapturingHandler#repository` resolves the target `Repository` from `params.repository.full_name` — a field that was never used or cross-checked during verification: `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [6](#0-5) .
5. `#capture_labels` then persists attacker-supplied label names directly onto that resolved stack's `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [7](#0-6) .
6. Those labels later surface as uppercased, `"true"`-valued environment variables merged into every subsequent deploy/task for that stack via `ReviewStack#env`: `labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` [8](#0-7) , consumed by `DeployCommands`/`TaskCommands` at `PTY.spawn` time (confirmed by `DeployCommandsTest`/`TaskCommandsTest` asserting `env["WIP"]`/`env["BUG"]`) [9](#0-8) .

Root cause: the controller trusts the requester only to the extent of matching an org name string that the attacker also supplies, and every handler's repository lookup uses an entirely separate, equally attacker-supplied string (`repository.full_name`), with no invariant tying the two together and no requirement that the authenticating org actually own the target repository. `require_permission!`, `User#authorized?`, and the `ExplicitParameters` schema (`params.repository.full_name` merely `requires ... String`) do nothing to enforce this relationship — the schema only validates types/presence, not ownership consistency [10](#0-9) . The existing test suite only ever sends internally-consistent payloads (`repository_params` sets `owner.login: 'shopify'` matching `full_name` in fixtures), so it never exercises this divergence [11](#0-10) .

Attacker request: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, body `{"action":"labeled","number":<n>,"pull_request":{...,"labels":[{"name":"MALICIOUS_FLAG"}]},"repository":{"owner":{"login":"<no-secret-org>"},"full_name":"<victim-org>/<victim-repo>"},"sender":{"login":"attacker"}}`, with any (or no) `X-Hub-Signature`. Precondition: `<no-secret-org>` must be a key present in `secrets.github` (multi-org mode) whose per-org config omits `webhook_secret` — this makes `Shipit.github(organization: "<no-secret-org>")` resolve without raising `GithubOrganizationUnknown` and `verify_webhook_signature` return `true` unconditionally.

### Impact Explanation
The attacker can write to `PullRequest#labels` for the victim's review stack — a record belonging to a repository/organization that did **not** authenticate the request — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Because those labels become environment variables merged into every subsequent deploy/task command for that stack, the attacker gains a persistent, repeatable environment-variable injection primitive into the victim stack's deploy pipeline, which (depending on the victim's `shipit.yml`/deploy scripts) can influence deploy behavior. This is repeatable against any repository/stack in the installation, as long as one no-secret org exists in the multi-org config, and is not confined to that no-secret org's own repos — the blast radius spans the entire Shipit tenant. The `bot_login` (`Shipit.user`) configuration itself is not directly read by `LabelCapturingHandler`; its relevance is limited to how downstream automated actions (e.g., archiving/unarchiving via sibling `LabeledHandler`/`UnlabeledHandler`, which are dispatched from the exact same forged request since they share the `pull_request` handler chain) are attributed to the bot identity — this compounds the blast radius but is a secondary effect, not the direct mechanism of this handler.

### Likelihood Explanation
Preconditions: Shipit must be running in multi-organization GitHub App mode (`secrets.github` keyed by org) with at least one configured organization lacking `webhook_secret` — a state explicitly supported and reachable via ordinary configuration (the README documents `webhook_secret` as something you "should copy... here" if you set one, implying it is optional) [12](#0-11) . Given that precondition, the attack costs a single unauthenticated HTTP POST, requires no GitHub session, token, or secret, and is fully repeatable against arbitrary target repositories by simply changing `repository.full_name` while keeping `repository.owner.login` fixed to the no-secret org.

### Recommendation
Bind webhook authentication to the same repository identity used for stack resolution: derive the organization used for `Shipit.github(organization:)` from the same `repository.full_name` (or an equivalently canonical field) that handlers use to resolve `Repository`/`Stack`, and reject/require a `webhook_secret` for every configured organization (fail closed instead of `return true unless webhook_secret`). Additionally, after signature verification, re-validate that `params.repository.owner.login` matches the owner portion of `params.repository.full_name` before dispatching to handlers.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "no-secret organization cannot forge pull_request labeled events for a different org's stack" do
  # Arrange: victim stack belongs to org "shopify" (has webhook_secret in test config)
  victim_stack = shipit_stacks(:review_stack)
  victim_repo_full_name = victim_stack.repository.github_repo_name # e.g. "shopify/shipit-engine"

  # Attacker forges owner.login to a different, no-secret org while pointing
  # repository.full_name at the victim's repo.
  payload = payload_parsed(:pull_request_labeled)
  payload["repository"]["owner"] = { "login" => "no-secret-org" }
  payload["repository"]["full_name"] = victim_repo_full_name
  payload["pull_request"]["labels"] = [{ "name" => "attacker-controlled-label" }]

  Shipit.stubs(:github).with(organization: "no-secret-org").returns(
    Shipit::GitHubApp.new("no-secret-org", { webhook_secret: nil })
  )

  @request.headers['X-Github-Event'] = 'pull_request'
  # No valid X-Hub-Signature is supplied / does not matter, since webhook_secret is blank.
  post :create, body: payload.to_json, as: :json

  assert_response :ok
  # Assert the equality that should have held (repository_owner authenticated == repository that got mutated)
  # is broken: victim_stack's PullRequest was mutated despite "no-secret-org" (not "shopify") authenticating.
  assert_includes victim_stack.reload.pull_request.labels, "attacker-controlled-label"
end
```

This demonstrates that `repository_owner` (`"no-secret-org"`, used to authenticate) diverges from the actual organization owning the mutated stack (`"shopify"`, derived from `repository.full_name`), and that the divergence is not caught anywhere in the request lifecycle.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
