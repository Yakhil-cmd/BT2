### Title
`hop_submit`'s guardian-style signature excludes the `recipients` parameter, allowing recipient substitution - ([File: substrate/client/hop/src/rpc.rs])

### Summary
This is a structural analog of LID-5: a signature that is meant to authorize an entire user action only covers a subset of the action's parameters. In the `DepositSecurityModule` case, guardian signatures covered block/root/nonce but not `depositCalldata`. In `substrate/client/hop`, the `hop_submit` RPC signature covers only `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp)` and never binds the `recipients` list that is submitted alongside it, even though `recipients` is exactly the field that later determines who is authorized to `hop_claim`/`hop_ack` (i.e., who receives the payload).

### Finding Description
`HopApi::submit` accepts `data`, `recipients`, `signature`, `signer`, `submit_timestamp` as independent, separately-encoded RPC parameters: [1](#0-0) 

The signed payload is derived only from the content hash and timestamp: [2](#0-1) 

Signature verification in `do_submit` re-derives exactly that same payload and never touches `recipients`: [3](#0-2) 

`recipients` is decoded into `RecipientVec` earlier in the same function purely from the unauthenticated wire bytes, with no cryptographic binding to `signer`'s signature: [4](#0-3) 

`HopDataPool::insert` stores whatever `recipients` were passed to it verbatim alongside the *same* signature/signer/timestamp tuple that would also validate for a different `recipients` set: [5](#0-4) 

Downstream, `claim`/`ack` authorize access purely by checking whether the caller's signature matches one of the `Recipient.signer` entries stored in `meta.recipients` — i.e., `recipients` is the actual access-control list for the payload, yet it was never part of what the sender cryptographically committed to: [6](#0-5) 

Because `(data, signature, signer, submit_timestamp)` is valid for *any* `recipients` value, any party who obtains that public tuple (e.g. it is submitted to more than one independent full node, each of which runs its own local, unsynchronized `HopDataPool`/parity-db instance — there is no global consensus dedup until/unless the maintenance task promotes it on-chain) can resubmit the identical signed tuple with a substituted `recipients` list to a node that has not yet seen the legitimate submission. That node's local dedup only checks `blake2_256(data)` per-node, so the tampered submission is accepted as valid, and an attacker's own ephemeral key becomes an authorized recipient able to `hop_claim`/`hop_ack` the payload from that node.

Note on the on-chain path: the maintenance task's `promote()` call to the runtime carries only `(data, signer, signature, submit_timestamp)` — not `recipients` — so `recipients` never becomes part of runtime/consensus state at all: [7](#0-6) 
This means the vulnerability is confined to the node-local HOP data-pool/RPC layer (`substrate/client/hop`), not to a FRAME pallet dispatched through consensus.

### Impact Explanation
An unprivileged party (not a guardian, not a validator/collator, not requiring stolen keys) who can observe a valid `hop_submit` tuple (e.g., because a client broadcasts the same submission to multiple public RPC endpoints for redundancy, or a relaying service holds the tuple before forwarding it) can redirect who is treated as an authorized recipient on any node that has not yet recorded that content hash, causing sensitive handed-off data to be delivered to (or acknowledged by) an unintended party on that node. This is an integrity/confidentiality break of the "hand-off" guarantee the HOP RPC is documented to provide, directly analogous to the Lido report's "malicious user can front-run and submit arbitrary calldata that is used downstream by the module."

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to obtain a still-valid, not-yet-locally-committed `(data, signature, signer, submit_timestamp)` tuple and race a resubmission to a node that hasn't recorded that hash — feasible in a multi-node RPC-fanout or relay setting, but it is not exploitable purely from on-chain observation, since `recipients` never reaches consensus state. This constrains the blast radius to node-local pools rather than the whole network, and the affected component (`substrate/client/hop`) is not observed elsewhere in the reviewed history of mainline `polkadot-sdk`; I was unable to confirm with available tools whether this module maps to any currently live Parity/Snowbridge bug-bounty program scope or deployed network, which is required for bounty eligibility per the review method.

### Recommendation
Bind `recipients` (e.g. its SCALE-encoding or its hash) into `submit_signing_payload` so the signer's signature commits to the exact recipient set, the same remediation Lido applied by including `keccak256(depositCalldata)` in the guardian signature: `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || blake2_256(recipients.encode()) || submit_timestamp.to_le_bytes())`, and reject any `hop_submit` whose recomputed payload (with the actually-supplied `recipients`) does not match.

### Proof of Concept
No test was executed against a live network or existing harness; this is a static-analysis-derived finding from the code paths cited above, not an executed reproduction. A minimal integration reproduction would: (1) construct a `(data, recipients_A, signature, signer, submit_timestamp)` tuple that passes `do_submit`'s checks against a fresh `HopDataPool`; (2) verify `multi_sig.verify(&submit_payload[..], &account_id)` returns `true`; (3) call `HopDataPool::insert` a second time on a separate pool instance with the identical `signature`/`signer`/`submit_timestamp`/`data` but a different `recipients_B` set and confirm it succeeds (no error), demonstrating the same signature authorizes two different recipient sets. This was not executed here; existing unit tests in `substrate/client/hop/src/rpc.rs` (`tests` module, e.g. `submit_sig`) and `substrate/client/hop/src/pool.rs::insert` provide the harness scaffolding needed to run such a reproduction, but no execution/results are claimed.

**Caveat on scope/eligibility:** I could not verify that `substrate/client/hop` corresponds to a component of any currently live Parity/Snowbridge bug-bounty program or a deployed Polkadot/Kusama/parachain runtime — it appears to be a bespoke addition in this repository rather than part of upstream mainline `polkadot-sdk`. This should be confirmed before treating the finding as bounty-eligible.

/// Compute the 32-byte payload signed at `hop_submit` time.
///
/// The runtime pallet re-derives this exact byte sequence to verify the
/// signature on-chain, so the construction must remain byte-identical to the
/// pallet's `signing_payload(data, submit_timestamp)`:
/// `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
pub fn submit_signing_payload(hash: &HopHash, submit_timestamp: u64) -> [u8; 32] {
	let mut buf = [0u8; HOP_SUBMIT_CONTEXT.len() + 32 + 8];
	buf[..HOP_SUBMIT_CONTEXT.len()].copy_from_slice(HOP_SUBMIT_CONTEXT);
	buf[HOP_SUBMIT_CONTEXT.len()..HOP_SUBMIT_CONTEXT.len() + 32].copy_from_slice(hash.as_bytes());
	buf[HOP_SUBMIT_CONTEXT.len() + 32..].copy_from_slice(&submit_timestamp.to_le_bytes());
	blake2_256(&buf)
}

	/// Decode `signature` and return the index of the matching recipient in
	/// `meta.recipients`. `context` is the operation's domain separator (claim
	/// / ack). Returning an index keeps a single implementation for both
	/// shared- and exclusive-borrow callers (`meta.recipients[idx]` works in
	/// either case).
	fn find_recipient_idx(
		meta: &HopEntryMeta,
		hash: &HopHash,
		signature: &[u8],
		context: &[u8],
	) -> Result<usize, HopError> {
		let multi_sig =
			MultiSignature::decode(&mut &signature[..]).map_err(|_| HopError::InvalidSignature)?;
		let payload = signing_payload(context, hash);

		meta.recipients
			.iter()
			.position(|r| multi_sig.verify(&payload[..], &r.signer.clone().into_account()))
			.ok_or(HopError::NotRecipient)
	}

	/// Claim data from the pool (read-only). Verifies the signature against recipient
	/// public keys. Returns the data if the signature matches a recipient.
	///
	/// This does NOT mark the recipient as claimed — call `ack` after receiving the data
	/// to confirm receipt.
	///
	/// Returns `AlreadyClaimed` if the recipient has already acked (data may be deleted).
	pub fn claim(&self, hash: &HopHash, signature: &[u8]) -> Result<Vec<u8>, HopError> {
		let meta = self.fetch_meta(hash)?.ok_or(HopError::NotFound)?;
		// Map NotRecipient → NotFound so callers cannot probe whether a hash
		// exists by observing different error codes.
		let idx = Self::find_recipient_idx(&meta, hash, signature, HOP_CLAIM_CONTEXT)
			.map_err(|_| HopError::NotFound)?;

		// If this recipient already acked, the data may be gone.
		if meta.recipients[idx].claimed {
			return Err(HopError::AlreadyClaimed);
		}
		// Read blob from disk and verify its content hash. May be gone if
		// concurrently acked and deleted, in which case we surface NotFound.
		self.read_and_verify_blob(hash)
	}
