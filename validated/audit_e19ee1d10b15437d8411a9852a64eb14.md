### Title
Webhook signature verification keyed on `repository.owner.login` while acted-upon repository is selected from a different field (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while every webhook `Handler` selects which `Repository`/`Stack` to act on based on a different, independently attacker-controlled field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so the "identity that authenticated" and the "repository that is written" are not the same equality that the code implicitly assumes.

### Finding Description
`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

`repository_owner` is derived purely from the JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once verification succeeds, the same raw payload is dispatched to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) . Handlers resolve the target `Repository`/`Stack` from a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

Shipit supports multiple installed GitHub Apps, one per organization, each with its own `webhook_secret`, configured under `secrets.yml`'s `github` map keyed by organization name [5](#0-4) , and `Shipit.github(organization:)` looks up the app config purely by the organization string extracted from the payload [6](#0-5) .

Because HMAC verification derives *which secret to check against* from an attacker-supplied field (`repository.owner.login`) rather than from the field the handlers subsequently trust (`repository.full_name`), an operator of any GitHub App installed on the Shipit instance (e.g., an org "attacker-org" whose GitHub App the attacker created and therefore knows the `webhook_secret` for) can craft a webhook payload where:
- `repository.owner.login` = `"attacker-org"` (so `Shipit.github(organization: 'attacker-org')` picks the attacker's own known secret to verify, and the HMAC computed with that secret over the full raw body will legitimately match since the attacker signs it themselves), and
- `repository.full_name` = `"victim-org/victim-repo"` (a repository actually tracked by Shipit under a completely different, victim-owned GitHub App installation).

The webhook will pass `verify_signature` (because it's checked against the attacker's own secret, which the attacker controls) and then be routed to handlers that operate on `victim-org/victim-repo` because they only look at `repository.full_name`, e.g., `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on stacks resolved from that `full_name` [7](#0-6) , and `PullRequest::ClosedHandler#process` calls `review_stack.archive!` on a repository resolved the same way [8](#0-7) .

This is the structural analog of the sandwich-attack bug class: the contract validated one parameter (deposit amount / slippage) while acting on another, unbound parameter (actual swap execution price). Here, the signature check validates against an identity (`repository.owner.login`) that is never cryptographically or logically bound to the identity the handlers actually operate on (`repository.full_name`).

### Impact Explanation
If this can be exploited, it constitutes cross-repository writes/actions against a repository the attacker does not own — an unauthorized deploy/sync/merge-queue trigger on a victim's stack sourced entirely from a webhook whose signature was validated against an unrelated, attacker-controlled secret. That maps to the "Critical: cross-repository writes / unauthorized deploy" criteria.

### Likelihood Explanation
Exploitability requires the attacker to control (or have installed) at least one GitHub App entry in the Shipit instance's `secrets.yml` `github` map — i.e., be a legitimate/authorized organization on that specific Shipit deployment (this is standard, documented multi-org configuration, not a privileged internal secret). No repository write access to the victim repo, no `ApiClient` token, and no Shipit session is required — only the ability to POST a crafted JSON body to the public `/webhooks` endpoint with a signature computed from the attacker's own known `webhook_secret`. This is a realistic configuration for any Shipit deployment mounted for more than one GitHub organization, as explicitly documented in `docs/setup.md` [5](#0-4) .

### Recommendation
Bind webhook signature verification and repository resolution to the *same* identity. Concretely, verify that the organization/owner used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner of the repository resolved via `repository.full_name` before any handler acts, or better, resolve the target `Repository` first and verify the signature using the secret configured for that repository's actual persisted `owner`, not a value taken directly from the untrusted payload.

### Proof of Concept
1. Attacker creates/owns a GitHub App/org "attacker-org" that is installed on the shared Shipit instance (per multi-org setup in `docs/setup.md`) and knows its `webhook_secret`.
2. Attacker crafts a `push` (or `pull_request`) webhook JSON body with:
   - `repository.owner.login = "attacker-org"`
   - `repository.full_name = "victim-org/victim-repo"` (a repo/stack actually tracked by Shipit under a different installation)
   - `ref`, `after`, etc. as required by `PushHandler`'s param schema [9](#0-8) 
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker_webhook_secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` [1](#0-0)  and the HMAC matches (attacker signed with their own known secret) → request is accepted (not 422).
5. `PushHandler.call(params)` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [4](#0-3)  and triggers `stack.sync_github` for the victim's stack, despite the signature never having been checked against victim-org's secret.

**Note:** I was not able to fully verify from the available index whether `Repository.from_github_repo_name` or `stack.sync_github`/`review_stack.archive!` perform any additional, independent ownership check that would prevent this cross-organization action (e.g., re-verifying against the persisted `Repository#owner`'s GitHub App before executing). This would need to be confirmed with a full read of `app/models/shipit/repository.rb`'s `from_github_repo_name` and `Stack#sync_github` to rule out a secondary binding check I could not locate in the indexed context.
