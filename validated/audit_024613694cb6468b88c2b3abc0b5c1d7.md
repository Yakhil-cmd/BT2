### Title
Webhook signature is verified against `repository.owner.login`, but the Stack/repository actually acted upon is looked up via the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's webhook secret to check the HMAC against using `params.dig('repository', 'owner', 'login')`, while every webhook `Handler` (which actually performs the mutating action - syncing commits, writing commit `Status`, creating review stacks, etc.) resolves the target `Stack`/`Repository` from a *different* JSON field, `payload.dig('repository', 'full_name')`. Because the HMAC only guarantees "this byte-for-byte JSON body was signed by whoever holds `owner.login`'s secret" and not "the fields inside this body are internally consistent", any tenant who legitimately knows their own organization's webhook secret can forge a body where `repository.owner.login` names their own org (to pass signature verification) while `repository.full_name` names a completely different, victim organization's repository (to select which `Stack` gets acted upon).

### Finding Description
`Shipit.github(organization: repository_owner)` is used to fetch the `GitHubApp`/secret used to verify the signature: [1](#0-0) , and the org used for that lookup comes from `repository.owner.login` (or `organization.login`) inside the attacker-controlled JSON body: [2](#0-1) .

Once the signature passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the raw parsed body to handlers [3](#0-2) . Every handler's base class resolves the affected `Stack`s via a **different** path in the same payload: [4](#0-3) .

Concretely, `PushHandler` triggers a real sync/deploy pipeline action (`stack.sync_github`) purely based on that `full_name`-derived stack lookup, with no re-check that `full_name`'s owner matches `owner.login` used for the signature: [5](#0-4) .

The two fields (`repository.owner.login` and `repository.full_name`) are never cross-validated anywhere in the engine. GitHub's own webhooks always keep them consistent, but nothing here enforces that; the HMAC only proves that the raw bytes were signed by the holder of one org's secret, not that the values inside are self-consistent.

### Impact Explanation
In a shared/multi-tenant Shipit deployment (which the `GithubOrganizationUnknown` handling and per-org `Shipit.github(organization:)` lookup imply is a supported configuration), a user who is an unprivileged attacker with respect to a victim repository but who legitimately controls their own organization's GitHub App installation (hence knows their own org's `webhook_secret`, which is not itself a privileged Shipit credential) can:
1. Sign an arbitrary JSON body with their own valid secret (satisfying `verify_signature`).
2. Set `repository.full_name` inside that body to `victim-org/victim-repo`.
3. Have `PushHandler`/`StatusHandler`/etc. act on the victim's `Stack` (trigger `GithubSyncJob`, write commit `Status` records that gate the merge queue's "blocking statuses", or drive `check_suite` processing) as if it were a legitimate GitHub-originated event for that repository.

This breaks the trust binding "organization that authenticated == repository that is written." Forged commit `Status`/`check_suite` events can flip CI gating results relied on by the merge queue, enabling an unauthorized merge/deploy on a repository the attacker has no legitimate access to - matching the Critical impact bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood depends on Shipit being configured for more than one GitHub organization (multi-tenant), which the codebase explicitly supports (`Shipit.github(organization:)`, `GithubOrganizationUnknown`). Any tenant of such a shared instance can exploit this against any other tenant's tracked repository without needing that victim's secret, GitHub App key, or Shipit session - only their own legitimately-issued webhook secret, which is not treated as a sensitive, cross-tenant-trust credential by the engine's authorization model.

### Recommendation
In `Handler#repository_name` (and equivalently wherever a `Stack`/`Repository` is resolved from webhook payload), require that the resolved repository's owner matches the organization whose secret verified the request (i.e., cross-check `payload.dig('repository','owner','login')` against `payload.dig('repository','full_name')`'s owner segment, or better, resolve the target repository through the same `repository_owner` value used for signature verification instead of trusting `full_name` independently).

### Proof of Concept
1. Attacker legitimately installs/administers the Shipit GitHub App on `attacker-org` (a real, distinct tenant of the shared Shipit instance) and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/main",
  "after": "<victim-commit-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(attacker-org secret, body)` and sends it as `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `attacker-org`'s secret: [1](#0-0) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` from `full_name` and triggers `stack.sync_github(expected_head_sha: params.after)` on the victim's stack: [6](#0-5) , without the victim organization's secret ever being involved.
