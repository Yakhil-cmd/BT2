### Title
Stack-scoped ApiClient tokens can read CCMenu status of any stack, bypassing the token's stack binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` re-implements the `stack` lookup instead of reusing the scoped version inherited from `Shipit::Api::BaseController`. The base implementation restricts an `ApiClient` to the single `Stack` it is bound to (`stack_id`), but `CCMenuController` looks the stack up unscoped, so a token that is only supposed to authorize `read:stack` on one stack can be replayed against the CCMenu endpoint of any other stack.

### Finding Description
`Shipit::Api::BaseController` defines the authorization-scoping contract for every API endpoint: an `ApiClient` bound to a specific stack (`stack_id` set) is only allowed to resolve stacks from that restricted relation. [1](#0-0) 

`CCMenuController` inherits from `BaseController` and enforces `require_permission :read, :stack`, but it overrides `stack` to bypass the scoping and also swaps in a bespoke authentication path that authenticates purely from a query-string `token` param: [2](#0-1) 

`require_permission` only checks the `ApiClient`'s permission list via `check_permissions!(operation, scope)`, it never checks whether the requested `stack_id` matches the client's bound `stack_id`: [3](#0-2) 

Other stack-scoped fixtures/tests confirm the intended binding: a client created with `stack: shipit` should only see that one stack when going through the properly-scoped `stacks`/`stack` helpers. [4](#0-3) [5](#0-4) 

The binding broken is: **stack a token authorizes (its bound `stack_id`) ≠ stack it touches (`params[:stack_id]` resolved by the unscoped `Stack.from_param!` in `CCMenuController`)**. Every other API controller that needs a stack (tasks, deploys, locks, hooks, release statuses) relies on the inherited scoped `stack`/`stacks` methods, but `CCMenuController` does not.

### Impact Explanation
An attacker holding a valid, permission-limited `ApiClient` token that was intentionally scoped to a single stack (a legitimate, low-privilege use case — e.g. giving a CI dashboard read access to only its own stack) can use that same token to read the CCMenu status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) of any other stack in the Shipit instance, including stacks belonging to other teams/repositories that the token was never granted access to. This is an unauthorized read of another stack's state, matching the High-impact category "escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state."

### Likelihood Explanation
Exploitation only requires possessing any valid `read:stack`-permissioned `ApiClient` token that is bound to a stack (a normal, supported configuration — see `test/fixtures/shipit/api_clients.yml`), and issuing a GET request to `/api/stacks/*stack_id/ccmenu?token=<token>` for a different stack. No additional credentials, session, or privileged access is required beyond the token itself, which the attacker is assumed to already legitimately hold for their own stack.

### Recommendation
Remove the bespoke `stack` and `authenticate_api_client` overrides in `CCMenuController`, or make them respect the same scoping as `BaseController#stacks`/`#stack` (i.e., resolve the stack from `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) before calling `from_param!`. Alternatively, have `require_permission!`/`check_permissions!` also validate that `stack.id == current_api_client.stack_id` whenever the client is stack-scoped.

### Proof of Concept
1. As an authorized user, obtain (or have an admin create) an `ApiClient` scoped to `stack_id: <A>` with permission `read:stack` (as in the `here_come_the_walrus` fixture).
2. Issue: `GET /api/stacks/<other_org>/<other_repo>/<other_env>/ccmenu?token=<token>`.
3. Observe the response returns valid CCMenu XML with `lastBuildStatus`/`lastBuildLabel`/`activity` for stack `<other_org>/<other_repo>/<other_env>`, a stack the token was never authorized for, because `CCMenuController#stack` resolves via unscoped `Stack.from_param!` rather than the client-scoped `stacks` relation used everywhere else in the API.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
