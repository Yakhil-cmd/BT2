### Title
Unauthenticated Pub/Sub event stream mount bypasses `Shipit::Authentication` - (File: `config/routes.rb`)

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack app at `/events` in `config/routes.rb`, which means it never passes through any `Shipit::ShipitController`-derived controller and therefore never runs `force_github_authentication`. Any unauthenticated request to `/events?channels=stack.<id>` receives the SSE stream Rails publishes for that channel, including `Stack#broadcast_update` payloads.

### Finding Description
The binding that should hold is: `every payload delivered over the SSE connection == payload gated by force_github_authentication` (i.e. only requests that already passed `Shipit::Authentication#force_github_authentication` should be able to subscribe to a channel). This binding is broken because `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [1](#0-0)  attaches a plain Rack endpoint to the routing tree, and `Shipit::Authentication` is implemented as an `ActiveSupport::Concern` with `before_action :force_github_authentication` that is only included into controllers, never into arbitrary Rack apps [2](#0-1) . There is no `before_action`, Rack middleware, or route constraint checking `session[:user_id]`/`current_user.authorized?` in front of the `/events` mount, so the equality fails: an anonymous GET to `/events?channels=stack.42` reaches `Pubsubstub::StreamAction` directly and is streamed data without any check of `current_user.logged_in?` or `current_user.authorized?`.

Concretely, `Shipit::Stack#broadcast_update` publishes to a channel named `"stack.#{id}"` on every stack update: `Pubsubstub.publish("stack.#{id}", { id:, updated_at: }.to_json, name: 'update')` [3](#0-2) . Because `id` is a sequential integer, an attacker can enumerate `stack.1`, `stack.2`, … and receive `update` events (id + `updated_at`) for every stack in the installation without any session, `ApiClient` token, or GitHub team membership.

I was not able to locate, within the files I could inspect, a code path that publishes `Task#chunk_output` (live command output, which could contain `GITHUB_TOKEN`-bearing command output) through `Pubsubstub.publish`. `Task#write` only appends to Redis and to the logger [4](#0-3) ; the only `Pubsubstub.publish` call found in `app/models/**` is `Stack#broadcast_update`, which carries only `id` and `updated_at`, not command output. I could not fully confirm or rule out other publish paths (e.g. background jobs, JS-side channel construction for task tail streaming) because they were not reachable in the index within the remaining investigation budget.

### Impact Explanation
Confirmed impact: any unauthenticated party can subscribe to `/events?channels=stack.<id>` and receive real-time `update` notifications (`{id, updated_at}`) for any stack in the deployment, for arbitrary/enumerable stack IDs, with no session or credentials — this is a repeatable, unauthenticated read of stack state across every tenant/stack hosted by the instance, matching the "High – unauthenticated read of stack state" category. The broader claim in the prompt — that this also exposes `Task#chunk_output` / `GITHUB_TOKEN`-bearing command output — is **not substantiated** by any `Pubsubstub.publish` call for task output that I could find in the model/controller code inspected; that portion of the claimed impact should be treated as unconfirmed rather than proven.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host are required: the mount is unconditional in `config/routes.rb` and ships as part of the engine's default routing, regardless of `Shipit.authentication_disabled?` or team configuration. The attacker cost is a single unauthenticated HTTP GET with a guessed/enumerated numeric stack ID in the `channels` param, fully repeatable against every stack.

### Recommendation
Do not mount `Pubsubstub::StreamAction` unauthenticated. Wrap the mount so it runs through `Shipit::Authentication` (e.g., mount inside an authenticated controller action that validates the requested channel belongs to a stack the current user is authorized to view, using signed/opaque per-stack channel tokens instead of the raw numeric `stack.<id>`), or add a `before` hook / Rack middleware in front of the mount enforcing `current_user.logged_in? && current_user.authorized?` and per-channel authorization before allowing a subscription.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require 'test_helper'

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    test "unauthenticated request to /events can subscribe to a stack's channel" do
      stack = shipit_stacks(:shipit)

      # No session, no ApiClient token, no api_clients_secret
      get "/events", params: { channels: "stack.#{stack.id}" }

      # Binding under test: unauthenticated access to Pubsubstub mount ==
      # unauthenticated access to a Shipit::ShipitController action
      assert_response :success # or :ok / streaming, NOT redirect_to(github_authentication_path) or :forbidden
      refute_redirected_to Shipit::Engine.routes.url_helpers.github_authentication_path
    end
  end
end
```
Assertion pair to validate the broken binding: before the fix, `response.status` is `200`/streaming and `session[:user_id]` is `nil`; on a properly gated controller endpoint hitting the same data (e.g. `stacks#show`), an anonymous request instead redirects to `github_authentication_path` or returns `403`. The divergence between these two outcomes for equivalent unauthenticated requests demonstrates the bypass.
