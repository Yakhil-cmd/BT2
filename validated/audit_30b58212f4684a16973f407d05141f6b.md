### Title
Uncontrolled Resource Consumption via Unbounded Attestor Array in Address `attested` Definition - ([File: definition.js])

### Summary
The `keycloak-core` advisory describes an unbounded `size` parameter that lets an unauthenticated caller force expensive resource generation. The analogous pattern in `ocore` is the `attested` address-definition operator, whose `arrAttestors` array has no length limit and no complexity cost proportional to its size, unlike the sibling `in data feed` operator which explicitly charges `complexity += arrAddresses.length-1` for the same kind of oracle/address list.

### Finding Description
When an address (or asset spending condition) is defined with the `attested` operator, `validateDefinition()` in [1](#0-0)  validates the `arrAttestors` array only by checking that each entry is a syntactically valid address — it does **not** add any complexity for the size of the array (contrast with the `in data feed` case a few lines below at [2](#0-1) , which explicitly does `complexity += arrAddresses.length-1`). Because `complexity` is incremented only once per AST node (`complexity++` in the generic `evaluate()` entry at [3](#0-2) ), an address definition containing an `attested` condition with a very large `arrAttestors` array can pass the `MAX_COMPLEXITY` check (`constants.MAX_COMPLEXITY = 100`, [4](#0-3)  ) at definition-post time regardless of how many attestor addresses are listed. The only real bound is the overall unit-size limit (`MAX_UNIT_LENGTH = 5e6`, [5](#0-4) ), which still permits tens of thousands of base64 addresses to be embedded.

Later, whenever a unit actually spends from (or otherwise authenticates against) that address, `validateAuthentifiers()` evaluates the same `attested` branch at [6](#0-5) , calling `storage.filterAttestedAddresses(conn, {arrAttestorAddresses: arrAttestors}, ..., [attested_address], ...)` with the full, unbounded attestor list. Every full node that validates the unit must process this call with the attacker-chosen array size — the array length plays the same role as the `size` parameter in the QR-code advisory: it is fully attacker-controlled and directly drives the cost of a downstream operation performed by every validator, not just the poster.

I was not able to inspect the body of `storage.filterAttestedAddresses` (in `storage.js`) within the available tool budget, so the exact per-call cost (e.g., SQL `IN(...)` clause size, additional joins) could not be confirmed; this should be verified directly in `storage.js`.

### Impact Explanation
If `filterAttestedAddresses` cost scales with the size of `arrAttestorAddresses` (e.g., a SQL `IN` clause built from the full array, or per-address lookups), an unprivileged address owner can craft an address definition with an oversized `attested` condition and then post an ordinary payment (or trigger AA logic through an asset condition) from that address. Every full node validating the resulting unit is forced to perform the expensive check, degrading validation throughput network-wide — the class of impact the rules require ("a network unable to confirm new units" / node-wide resource exhaustion from a single posted unit).

### Likelihood Explanation
Likelihood is moderate: creating the address definition and spending from it requires no special privilege beyond controlling one's own keys, and the address/definition size is only bounded by the general 5 MB unit-size cap, allowing tens of thousands of entries. However, the actual severity is contingent on the (unverified) cost profile of `filterAttestedAddresses`; if that function already caps or streams efficiently, the practical impact could be much smaller. This uncertainty could not be resolved with the tools available.

### Recommendation
- Add an explicit size cap (analogous to `MAX_ATTESTORS_PER_ASSET` already used for asset definitions in `aa_validation.js`) to the `attested` operator's `arrAttestors` array validated in `definition.js`.
- Alternatively/also, charge `complexity` proportionally to `arrAttestors.length` (mirroring the `in data feed` branch) so oversized attestor lists are rejected by the existing `MAX_COMPLEXITY` budget at definition-post time.
- Confirm and, if necessary, harden `storage.filterAttestedAddresses` so that its cost does not scale unbounded with the attestor array size regardless of the above front-end fixes.

### Proof of Concept
1. Attacker creates a new address whose definition is `['attested', ['this address', [addr1, addr2, ..., addrN]]]` combined with a signature branch (`bHasSig` requirement satisfied elsewhere in the `or`), with `N` as large as the ~5 MB unit-size budget allows (tens of thousands of valid-looking base64 addresses).
2. Because no complexity is charged per attestor, `validateDefinition()` ( [1](#0-0) ) accepts the definition as long as total `complexity <= MAX_COMPLEXITY`.
3. Attacker posts a payment authenticated via this address; every validating node calls `storage.filterAttestedAddresses` with the full oversized `arrAttestors` array ( [6](#0-5) ), incurring cost proportional to `N` on each node during unit validation — repeatable at will by re-spending from the same or newly created addresses of the same shape.
