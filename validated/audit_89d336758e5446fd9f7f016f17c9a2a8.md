### Title
Permissionless malicious asset creator can permanently freeze co-mingled liquidity in `pallet-asset-conversion` pools by blocking the deterministic pool account - (File: substrate/frame/asset-conversion/src/lib.rs)

### Summary
The reported bug is that an immutable, protocol-controlled `STADIUM_ADDRESS` can be blacklisted by a third-party ERC-20 operator (USDC), and because the reward-distribution code unconditionally `safeTransfer`s to that fixed address with no alternative recovery path, funds already escrowed in the (non-upgradeable) Proxy become stuck forever. The FRAME/Substrate analog is `pallet-asset-conversion`'s deterministic `pool_account`. That account is a fixed, non-owner-controlled address derived from `T::PoolLocator`, and any of the two paired assets can independently be a `pallet-assets` instance whose `freezer`/team is fully controlled by the (adversarial) asset creator — a role obtainable by anyone with no chain privilege. If that creator calls `Assets::block` against the pool account for their own asset, `do_remove_liquidity` (and swaps) unconditionally call `T::Assets::transfer(asset, &pool_account, withdraw_to, amount, ...)` which reverts with `TokenError::Blocked`, and because the call is atomic, the whole extrinsic — including withdrawal of the *other*, unrelated asset (e.g. native DOT) held in the same pool — fails. There is no root/governance override in the pallet to force-drain or fix a blocked pool account.

### Finding Description
`pallet_assets` allows any signed account to permissionlessly create an asset via `Assets::create`/`force_create` paths where the creator becomes `owner`/`admin`/`freezer` by default (`substrate/frame/assets/src/lib.rs`). The `freezer` role can call `block` on any account holding that asset: [1](#0-0) 
which sets `AccountStatus::Blocked` for the target account/asset pair: [2](#0-1) 
Blocked accounts cannot send or receive that asset, producing `TokenError::Blocked` (an unprivileged, protocol-defined error, not something the pool or its LPs can bypass): [3](#0-2) [4](#0-3) 

`pallet-asset-conversion` lets anyone create a permissionless liquidity pool pairing an arbitrary `AssetKind` (including a newly created malicious asset) with the native token or any other asset: [5](#0-4) 
The pool's holding account, `pool_account`, is a fixed address deterministically derived by `T::PoolLocator::address(&pool_id)` — analogous to the immutable `STADIUM_ADDRESS`/Proxy address in the report, in that it cannot be changed or "un-blacklisted" by protocol governance: [6](#0-5) 

When a liquidity provider (who may be an unrelated, honest user who only wanted exposure to the native token side of the pool) calls `remove_liquidity`, `do_remove_liquidity` unconditionally attempts to transfer *both* assets out of `pool_account`: [7](#0-6) 
If the malicious asset's freezer has called `Assets::block(origin, malicious_asset_id, pool_account)`, the `T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)` call fails with `TokenError::Blocked`. FRAME dispatchables are atomic on error, so this reverts the entire extrinsic — including the transfer of the paired asset (e.g. native DOT) that has nothing to do with the malicious asset. The LP token was already burned attempt aside (also rolled back), so LPs are left holding LP tokens for a pool whose account can never again satisfy `remove_liquidity`, `swap_exact_tokens_for_tokens`, or `swap_tokens_for_exact_tokens` for that pair, because every one of those paths must move the blocked asset through `pool_account`. There is no `force_remove_liquidity`, admin override, or root-level rescue call in `pallet-asset-conversion` to bypass this and let LPs recover the unaffected paired asset.

### Impact Explanation
This is a permanent, irrecoverable freezing of funds for any pool paired with an attacker-created asset, matching the report's "High" impact rationale (funds stuck in the contract forever with no rescue path). Crucially, it also freezes the *other, unrelated* asset side of the pool (e.g. native DOT contributed by innocent third-party liquidity providers), because `remove_liquidity`/swap operations are all-or-nothing across the pair. The attacker requires no privileged role, governance power, or stolen keys — only the ability to create an asset (a permissionless, deposit-gated action) and become its own freezer, then create/join a pool and block the pool account for that asset.

### Likelihood Explanation
Likelihood is high in principle for chains that expose `pallet-assets` asset creation and `pallet-asset-conversion` pool creation to permissionless signed extrinsics (e.g., Asset Hub-style runtimes), since both actions require nothing beyond deposits any user can pay. However, I could not confirm from the indexed files whether the specific production runtimes that ship `pallet-asset-conversion` (e.g. Asset Hub Westend, as seen in the emulated tests) actually configure `pallet_assets` (local `Assets`) to allow *fully permissionless* `create` (vs. requiring some elevated/whitelisted origin) for assets that get paired into AMM pools, nor whether there is a `SafeCallFilter` or root-only creation restriction on the specific asset instance used in swap paths — the integration tests I found (`swap_locally_on_chain_using_local_assets`) use a normal signed `Assets::create`, suggesting no special privilege is required there.

### Recommendation
- In `pallet-asset-conversion`, add a rescue/force path (callable by root or pool-specific mechanism) allowing LPs to redeem only the non-blocked asset from a pool when the other asset's pool-account transfer fails, instead of reverting the whole extrinsic.
- Alternatively, make `do_remove_liquidity`/swap paths tolerant of a single-asset `TokenError::Blocked` by best-effort transferring the non-blocked asset and crediting the blocked asset via an escrow/claimable balance that the LP can retrieve once un-blocked, so that one malicious asset instance cannot lock unrelated collateral.
- Consider disallowing (or requiring extra scrutiny/insurance for) assets whose `freezer`/team is not permanently fixed to a neutral party from being paired into pools whose failure mode can strand third-party liquidity.

### Proof of Concept
No local Rust/FRAME integration reproduction was executed in this session (tool budget exhausted before an actual `#[test]` could be written and run). The control-flow chain establishing the vulnerability is fully traced through source:
1. `Assets::create`/`force_create` → creator becomes freezer (referenced generically; exact `create` extrinsic body not re-quoted here due to search-tool limits).
2. `Assets::block` sets `AccountStatus::Blocked` on `pool_account` for the malicious asset — [1](#0-0) .
3. `AssetConversion::create_pool`/`add_liquidity` — pool account created and funded with both assets — [8](#0-7) .
4. `AssetConversion::remove_liquidity` → `do_remove_liquidity` → unconditional dual `T::Assets::transfer` from `pool_account` — [7](#0-6) , which reverts atomically once the blocked-asset leg returns `TokenError::Blocked` (confirmed by existing unit test behavior for blocked accounts in `pallet-assets`: [9](#0-8) ).

This is a code-path-level demonstration (not an executed test) — I recommend a background Devin session write and run a `#[test]` in `substrate/frame/asset-conversion/src/tests.rs` that: creates a malicious asset with the test user as freezer, creates a pool pairing it with `NativeOrWithId::Native`, adds liquidity from a second, honest account, has the malicious freezer call `Assets::block` on the pool account, and then asserts that `remove_liquidity` from the honest account fails with `TokenError::Blocked`, verifying the native-side funds cannot be withdrawn.

#[derive(Clone, Encode, Decode, Eq, PartialEq, Debug, MaxEncodedLen, TypeInfo)]
pub enum AccountStatus {
	/// Asset account can receive and transfer the assets.
	Liquid,
	/// Asset account cannot transfer the assets.
	Frozen,
	/// Asset account cannot receive and transfer the assets.
	Blocked,
}
impl AccountStatus {
	/// Returns `true` if frozen or blocked.
	pub fn is_frozen(&self) -> bool {
		matches!(self, AccountStatus::Frozen | AccountStatus::Blocked)
	}
	/// Returns `true` if blocked.
	pub fn is_blocked(&self) -> bool {
		matches!(self, AccountStatus::Blocked)
	}
}
