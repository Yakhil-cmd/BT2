### Title
KAIA Permanently Locked in Service-Chain Bridge When Recipient Contract Has No Fallback/Receive — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer()` unconditionally executes a low-level KAIA transfer via `_to.call.value(_value)("")` with no guard for the case where `_to` is a contract that implements neither a `fallback` nor a `receive` function. The call reverts, the nonce is never consumed, and because the `_to` address is immutably fixed by the original `RequestValueTransfer` event on the source chain, no operator can ever deliver the KAIA. The funds are permanently locked in both the destination bridge (undeliverable) and the source bridge (no recall path).

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` performs the following unconditional low-level call at line 98:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

There is no guard of the form `if (_value == 0) return;` and no check that `_to` is capable of receiving native KAIA. In Solidity 0.5.6, a `.call.value(N)("")` to a contract that has neither a `fallback` nor a `receive` function will return `ok = false` regardless of `N`, causing the `require` to revert the entire transaction.

The nonce accounting (`_setHandledRequestTxHash`, `handleNoncesToBlockNums`, `_updateHandleNonce`) is written before the transfer: [2](#0-1) 

Because the `require` reverts the whole transaction, those writes are also rolled back. The nonce is therefore never consumed, and operators can retry — but they must supply the same `_to` address that was recorded in the source-chain `RequestValueTransfer` event. There is no on-chain mechanism to redirect the transfer to a different address or to recall the KAIA to the sender.

A second instance of the same class exists in `BridgeFee._payKLAYFeeAndRefundChange()`:

```solidity
(bool ok, ) = feeReceiver.call.value(fee)("");
require(ok, "transfer fee failed");
``` [3](#0-2) 

If `feeReceiver` is set to a contract without a fallback/receive function, every `requestKLAYTransfer` / fallback call will revert, completely blocking the bridge for all users.

---

### Impact Explanation

- **Unauthorized asset loss / permanent lock**: KAIA deposited by a user on the source chain via `requestKLAYTransfer` is held by the source bridge. On the destination chain, `handleKLAYTransfer` will always revert when `_to` is a contract without fallback/receive. The KAIA cannot be delivered and cannot be recalled. Both pools are permanently frozen for that nonce.
- **`feeReceiver` variant**: If the bridge owner (or a compromised owner key) sets `feeReceiver` to a contract without fallback/receive, the entire KAIA bridge is DoS'd — every `requestKLAYTransfer` call reverts at the fee-payment step.

---

### Likelihood Explanation

- Any user who specifies a smart-contract `_to` address (e.g., a multisig, a DAO treasury, a DeFi vault) that does not explicitly implement a payable fallback will trigger this path. This is a realistic and common deployment pattern.
- The `feeReceiver` variant requires a privileged misconfiguration, so its likelihood is lower, but the blast radius (all bridge users) is higher.

---

### Recommendation

1. **In `handleKLAYTransfer`**: Add a zero-value guard and, for non-zero values, consider emitting a `TransferFailed` event and allowing the bridge owner to redirect or refund rather than reverting:

```solidity
if (_value > 0) {
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
```

A more robust fix is to add a `rescueKAIA(address payable _to, uint256 _value)` owner-only function so that stuck KAIA can be recovered when delivery is impossible.

2. **In `_payKLAYFeeAndRefundChange`**: Validate that `feeReceiver` is either an EOA or a contract that accepts KAIA before setting it, or apply the same zero-value guard.

---

    function _payKLAYFeeAndRefundChange(uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfKLAY;

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            (bool ok, ) = feeReceiver.call.value(fee)("");
            require(ok, "transfer fee failed");

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                (bool ok, ) = msg.sender.call.value(feeRefund)("");
                require(ok, "refund fee failed");
            }

            return fee;
        }

        if (_feeLimit > 0) {
            (bool ok, ) = msg.sender.call.value(_feeLimit)("");
            require(ok, "refund fee failed");
        }
        return 0;
