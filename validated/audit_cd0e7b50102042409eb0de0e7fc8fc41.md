### Title
Uncaught `throw` on crafted payment input crashes every full node — network-wide DoS ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs()` in `validation.js` contains a `throw Error(...)` reachable from an attacker-crafted payment input, executed inside a DB-query callback with no enclosing `try/catch`. Because the top-level exception handler in `network.js` is configured to deliberately crash the whole node process on any uncaught exception, a single maliciously crafted unit posted to the network can be broadcast to every full node and crash all of them simultaneously — an analog of CVE-2015-8926's "crafted-input causes crash" bug class, but amplified to a network-wide denial-of-confirmation event rather than a single-process crash.

### Finding Description
When validating a `transfer` input, the code queries the source output and then checks its `sequence`: [1](#0-0) 

Unlike the sibling check for `'final-bad'` sequence (which gracefully calls `return cb("spending a stable final-bad output " + input.unit)`), the `'temp-bad'` branch does `throw Error("spending a stable temp-bad output " + input.unit)`. This throw occurs inside a `conn.query(...)` result callback, several async layers deep inside `validate()` (`validation.js:118` onward), with no `try/catch` wrapping this specific call site.

`'temp-bad'` is a legitimate, reachable sequence value assigned to units involved in a double-spend that has not yet been resolved as `'good'`/`'final-bad'` (see `writer.js`, `main_chain.js`, `joint_storage.js` references to `temp-bad`). An attacker can create this state deterministically by posting two conflicting units that spend the same output (a standard double-spend), producing a stable output whose owning unit has `sequence='temp-bad'`. The attacker then crafts and broadcasts a *third* unit whose payment input references that stable `temp-bad` output.

Any full node — attacker's own node, or any other full/hub node on the network — that receives and validates this crafted unit via `network.js`'s `handleJoint()` → `validation.validate()` path will hit this `throw` uncaught. It propagates to Node's global handler: [2](#0-1) 
which explicitly logs the exception and then re-`throw`s it to terminate the process ("crash the process to avoid ending up in an inconsistent state").

### Impact Explanation
Because every full node runs identical validation code and this crafted unit is deterministically reproducible (no node-specific state is required beyond the shared, already-stable double-spend history), rebroadcasting the single malicious unit to the network can crash every full node/hub that processes it in relatively short order. This is a direct network-wide denial of the network's ability to validate/confirm new units — satisfying the "network unable to confirm new units" impact bar, and going beyond a simple local DoS (which alone would be excluded by the rules).

### Likelihood Explanation
Likelihood is Medium: the attacker needs to (1) get a `temp-bad`-sequenced stable output into the DAG, which requires performing an ordinary double-spend that is subsequently resolved to `temp-bad` for one of the conflicting branches, and (2) craft a follow-up unit spending that output. Both steps use fully standard, unprivileged unit-posting capability — no special network position, hub cooperation, or leaked keys are required. The main uncertainty is the exact timing/persistence window during which a `temp-bad` output remains queryable as "stable" per `bStableInParents` before other cleanup logic intervenes; this could not be fully confirmed with the available index and would need direct testing.

### Recommendation
Replace the `throw Error("spending a stable temp-bad output " + input.unit)` at `validation.js:2458` with `return cb("spending a stable temp-bad output " + input.unit)`, matching the adjacent `final-bad` branch, so that a crafted unit is rejected as invalid via the normal `ifUnitError`/`ifJointError` path instead of crashing the process. More broadly, audit all `throw Error(...)` statements inside the `validate()` call graph (`validation.js`, `definition.js`, etc.) that are reachable from attacker-controlled unit content to ensure they cannot fire on merely "unexpected but attacker-reachable" states, since the global `uncaughtException` handler treats any such throw as fatal.

### Proof of Concept
1. Attacker address A posts unit U1 spending output O.
2. Attacker double-spends O with unit U2 (same output, different unit) so that after stabilization one of {U1, U2} is resolved with `sequence = 'temp-bad'` on a stable output (standard doublespend resolution logic in `main_chain.js`/`writer.js`).
3. Attacker crafts unit U3 whose payment input references the `temp-bad` unit's stable output (`input.unit` = the temp-bad unit, matching `message_index`/`output_index`).
4. Attacker broadcasts U3 to the network.
5. Every full/hub node that receives U3 executes `validation.validate()` → hits `validation.js:2457-2458`, throws uncaught, triggers `network.js:4530-4543`'s handler, and crashes.
