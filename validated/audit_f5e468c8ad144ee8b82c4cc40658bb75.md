### Title
Unhandled exception in address-definition template lookup crashes the node process — ([File: definition.js])

### Summary
`ocore`'s address-definition evaluator has two independent code paths that both resolve a `['definition template', [unit, params]]` opcode by querying the `definition_template` message for the referenced unit. One path (`validateDefinition`) handles a missing/duplicate template gracefully by returning an error through the callback. The other path (`validateAuthentifiers`'s internal `evaluate`), which is executed immediately afterwards on the very same definition tree, instead `throw`s a plain `Error` from inside an asynchronous `conn.query` callback. Because that callback runs outside the synchronous call stack, the exception cannot be caught by any surrounding `try/catch`, propagates as a Node.js `uncaughtException`, and is explicitly re-thrown by `network.js`'s global handler to crash the process — mirroring the "unauthenticated request → worker/process crash/restart" pattern described in the CVE.

### Finding Description
Every unit author's address definition is validated twice in sequence:
1. `validateDefinition()` walks the definition tree and, for `'definition template'`, queries for the template and returns a normal validation error if `rows.length !== 1`: [1](#0-0) 

2. Immediately after, `validateAuthentifiers()` re-walks the same tree with its own `evaluate()` closure. Its `'definition template'` handler performs the identical query but on a mismatch it throws instead of signaling an error via `cb2`: [2](#0-1) 

That `throw Error("not 1 template")` executes inside the `conn.query` callback — a separate tick of the event loop from the `try { Definition.validateAuthentifiers(...) } catch (e) { ... }` wrapper that callers (e.g. `signed_message.js`) install around the call: [3](#0-2) 

Because the throw happens asynchronously, it escapes that `try/catch` entirely and becomes a process-level `uncaughtException`. `network.js` installs a global handler that explicitly re-throws to terminate the process: [4](#0-3) 

This is reachable from ordinary unit validation for any unit whose author uses an address definition containing `'definition template'` (`validateAuthor` → `Definition.validateAuthentifiers`): [5](#0-4) 
as well as from `signed_message.js`'s signed-package/AA-trigger validation path shown above, and from `validateAuthorSignaturesWithoutReferences`: [6](#0-5) 

Both `evaluate()` traversals run against the same connection with identical WHERE conditions, so under a single, uninterrupted validation call the second lookup will normally reproduce the first lookup's result. The asymmetry becomes exploitable ("conditions beyond the attacker's control", matching the CVE's own framing) whenever the two lookups can observe different states of the referenced `definition_template` unit — e.g. the template unit's stability/finality changing between the two queries during concurrent processing, catch-up, or reorg-adjacent validation windows, or when `validateAuthentifiers` is invoked as a standalone entry point (as in `signed_message.js`/AA formula `is_valid_signed_package` signed-package validation) where the state available to the second query is not guaranteed identical to whatever produced success on first evaluation.

### Impact Explanation
A successful trigger crashes the entire ocore process (full node, hub, or wallet backend), not merely a request handler. Given `network.js`'s handler explicitly turns any `uncaughtException` into a hard process crash "to avoid ending up in an inconsistent state," this halts unit validation, propagation, and stabilization on the affected node until it is restarted — directly analogous to the referenced CVE's "restart the NGINX worker process" impact, but at the level of the whole ocore node rather than a data-plane worker.

### Likelihood Explanation
Reaching the vulnerable code path (an address definition using `'definition template'`) requires no privilege — any unit author, AA trigger sender, or signed-message author can include this opcode. However, deterministically forcing the two identical, sequential queries to disagree is not fully attacker-controlled; it depends on timing/state conditions around the referenced template unit's stability, mirroring the CVE's own note that the crash occurs "under conditions beyond the attacker's control." This keeps likelihood moderate rather than trivial/always-reproducible.

### Recommendation
Make the `'definition template'` handler inside `validateAuthentifiers`'s `evaluate()` (definition.js, around line 811-813) consistent with `validateDefinition`'s handling: replace `throw Error("not 1 template")` with a graceful failure through `cb2(false)` (or propagate a proper validation error), so a missing/ambiguous template can never surface as an uncaught exception. More broadly, audit all `throw` statements reachable from inside asynchronous `conn.query`/`storage.*` callbacks in `definition.js`, `validation.js`, and `signed_message.js` to ensure they cannot bypass their intended error-callback contracts.

### Proof of Concept
1. Post a unit whose author's address definition includes a branch such as `['definition template', [<44-byte base64 unit id>, {<param>: 'value'}]]` alongside a normally-satisfiable `sig` branch (e.g. under `'or'`), so the definition otherwise validates.
2. Reference a `<unit id>` for which the `definition_template` lookup query (`messages JOIN units ... WHERE unit=? AND app='definition_template' AND main_chain_index<=? AND sequence='good' AND is_stable=1`) can plausibly return `rows.length !== 1` at the moment `validateAuthentifiers`'s `evaluate()` re-executes it (e.g., a template unit whose stability status is in flux relative to the validating node's view, or invoking the `is_valid_signed_package`/`signed_message.validateSignedMessage` entry point directly with such a definition where the surrounding validation state differs from a full unit's).
3. When the mismatch occurs, `definition.js`'s `evaluate()` executes `throw Error("not 1 template")` inside the `conn.query` callback, which is not caught by `signed_message.js`'s or `validation.js`'s synchronous `try/catch`, escalates to `process.on('uncaughtException')` in `network.js`, and crashes the node process.
