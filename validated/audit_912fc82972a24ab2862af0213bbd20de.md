### Title
Cross-repository commit-status write via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA with `Commit.where(sha: params.sha)`, with no scoping to the repository/organization that authenticated the webhook. Because commit SHAs are content-addressed and can be identical across independent repositories/forks, an attacker who controls a repository that shares a commit SHA with a victim's Shipit stack can send a validly-signed `status` webhook for context `review/approved` (or any required/blocking context) from their own repo and have it applied to the victim's commit record, potentially unblocking a deploy or merge.

### Finding Description
The broken binding the code should enforce is: `commit.stack.repository == Repository(from webhook payload)`, i.e., a status update should only be written to commits belonging to the repository/stack that authenticated the webhook. Instead, the actual binding enforced is only `sha == commit.sha`, with no repository check at all.

Trace:
- `Shipit::WebhooksController#create` parses the payload and dispatches to handlers per event, after `verify_signature` succeeds. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` only checks that `X-Hub-Signature` is valid for `Shipit.github(organization: repository_owner)` — i.e., it verifies the webhook came from *some* org/app the Shipit instance trusts for the repo named in the payload. It does not scope the payload's effect to that repository once inside the handler. [1](#0-0) [2](#0-1) 
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a bare SHA lookup across the entire `commits` table, with no filter on repository or organization. [3](#0-2) 
- `create_status_from_github!` calls `add_status`, which replicates the GitHub status into `statuses` and, if the state transition changes deployability, emits `deployable_status` and calls `stack.schedule_merges`. [4](#0-3) [5](#0-4) 
- `Commit#blocked?`/`#deployable?` and merge-request logic in `Stack` consult exactly these `statuses` rows scoped only by commit id, so a forged status attached to a victim commit changes what the victim stack considers "blocked" or "approved" — e.g. a stack requiring `review/approved` before deploy/merge would see that context satisfied. [6](#0-5) 

Root cause: SHAs are attacker-controllable in the sense that an attacker can create a commit with an SHA equal to a victim's commit only if they have prior knowledge of that content (identical tree/parent/commit metadata), or more practically, they can fork/mirror a public repository containing the victim's actual commits, making the SHA collision trivially real for any commit the victim repo shares with a public upstream (common in mirrored/forked open-source stacks). Because `Commit` records are not deduplicated by `(stack_id, sha)`-only in this lookup (`where(sha:)` is stack-agnostic), any repository — including one the attacker fully controls — that happens to contain a commit with the same SHA can trigger a validly-signed webhook that mutates the victim stack's commit status.

None of the listed guards prevent this: `verify_signature` authenticates the webhook to the *sender's own* repository/org, not to the commit being modified; `drop_unhandled_event` only filters event types; there's no `ExplicitParameters` repository field checked against `commit.stack.repository`; `force_github_authentication`, `User#authorized?`, `require_permission!` are irrelevant since this is an unauthenticated webhook path with no `current_user`.

### Impact Explanation
A payload authenticated for the attacker's own repository writes a `Shipit::Status` record on a commit belonging to a different repository's stack, satisfying `Critical` — "a payload for one repository mutating another's stack, commit, task or team." Concretely, if the victim stack requires context `review/approved` before deploy/merge (via `required_statuses`/`deploy_spec`), the attacker can forge that status on a shared-SHA commit and trigger `stack.schedule_merges`/deployability change, leading to an unauthorized deploy or merge. This is repeatable against any stack/commit sharing a SHA with an attacker-controlled repo, and is not limited to one victim — any public commit mirrored into a Shipit-tracked stack is exposed.

### Likelihood Explanation
Preconditions: the attacker needs a repository (owned or forked by them) that is registered with the same GitHub App/org trusted by the Shipit instance (so `verify_signature` succeeds for their own repo), and a commit SHA that also exists in the victim's tracked stack — trivially achievable by forking/mirroring public upstream repositories, which is a very common Shipit deployment pattern (mirrors, vendored branches, cherry-picks). Attacker cost is a single webhook POST with a valid signature for their own repo; no elevated privileges, tokens, or secrets are required beyond controlling one legitimate (even free/public) repository under the same trusted org/app. This is fully repeatable and does not require live GitHub access to reproduce in tests, since `StatusHandler#process` can be exercised directly against seeded `Commit`/`Stack` fixtures.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and other webhook handlers using bare-SHA lookups, e.g. `refresh_statuses!`/check-run handlers) to the repository named in the webhook payload: resolve the `Repository`/`Stack` from `params.dig('repository', 'full_name')` (or equivalent) first, then filter `Commit.where(sha: params.sha, stack_id: stack.id)` (or join through `stacks.repository_id`), rejecting/ignoring statuses whose payload repository does not match the commit's owning stack's repository.

### Proof of Concept

2. Seed `Repository` B (`attacker/repo`) — no stack requirement needed — and construct a `status` webhook payload with `sha: "deadbeef..."` (same SHA as C), `context: "review/approved"`, `state: "success"`, `repository.full_name: "attacker/repo"`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing controller-level signature check, as the vulnerability is inside the handler regardless of valid signature).
4. Assert BEFORE: `commit.stack.repository.full_name != payload_repository_full_name` (i.e., `"victim/repo" != "attacker/repo"`) yet `Commit.where(sha: "deadbeef...").count == 1` and it equals `C` — proving the collision reaches the victim's commit.
5. Assert AFTER: `C.reload.statuses.exists?(context: "review/approved", state: "success")` is `true`, and `C.blocked?`/deployability flips accordingly — demonstrating the victim stack's state changed from an unauthenticated repository's payload, confirming the equality `commit.stack.repository == webhook_repository` is violated.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
