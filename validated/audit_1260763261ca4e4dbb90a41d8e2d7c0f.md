### Title
Webhook provenance bypass in `MembershipHandler#find_or_create_team!` lets any org's webhook secret mutate another org's `Team` — ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request body was signed by the `webhook_secret` of the organization named in `repository_owner`/`organization.login`, but `MembershipHandler#find_or_create_team!` looks up the `Team` to mutate solely by `github_id`, ignoring which organization was actually authenticated. Because GitHub team IDs are attacker-choosable integers in the payload and not verified against the authenticating org, an attacker who controls their own GitHub org (and thus its `webhook_secret`) can forge a `membership` webhook whose `team.id` collides with a `Team.github_id` already present for a different, privileged organization, causing their own GitHub login to be added to that privileged team.

### Finding Description
The broken binding is: the org that authenticated the request (`repository_owner` used in `Shipit.github(organization: repository_owner)` at [1](#0-0) ) MUST equal the org that owns the `Team` row being mutated. It does not.

Trace:
- `WebhooksController#create` parses the raw JSON and dispatches to registered handlers for the event: [2](#0-1) 
- `verify_signature` resolves `Shipit.github(organization: repository_owner)` — where `repository_owner` is read directly from attacker-supplied `params.dig('repository','owner','login')` or `params.dig('organization','login')` — and verifies the HMAC signature against that org's configured `webhook_secret` only: [3](#0-2) . This only proves "the body was signed by org A's secret"; it never checks that `team.id` inside the body actually belongs to org A.
- `Shipit::Webhooks.for_event('membership')` routes to `MembershipHandler`: [4](#0-3) 
- `MembershipHandler#process` calls `find_or_create_team!` then `team.add_member(member)` for `action == 'added'`: [5](#0-4) 
- `find_or_create_team!` performs `Team.find_or_create_by!(github_id: params.team.id)`, using only `github_id` as the lookup key, with `organization` only set on the create-block path (never checked/enforced when a row already exists): [6](#0-5) 

Exploit: attacker owns org A, configured in `Shipit.github` with a known `webhook_secret` they control. Org B (unrelated, e.g. `shopify`) has a `Team` row already persisted with `github_id: N` and is listed in `Shipit.github_teams` (as demonstrated in `Shipit#github_teams`, which builds authorization from `Team.find_or_create_by_handle`: [7](#0-6) ). Attacker crafts a `membership` payload: `{"action":"added","team":{"id":N,"name":"x","slug":"x","url":"..."},"organization":{"login":"org-a"},"member":{"login":"attacker"},"repository":{"owner":{"login":"org-a"}}}`, signs it with org A's `webhook_secret`, and POSTs to `/webhooks` with `X-Github-Event: membership`. `verify_signature` succeeds against org A. `find_or_create_by!(github_id: N)` finds org B's existing `Team` row (since IDs collide) and `team.add_member(member)` links `attacker` to it.

`User#authorized?` then evaluates true for `attacker`, since it checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`: [8](#0-7) , and `force_github_authentication` grants access accordingly: [9](#0-8) .

No existing guard prevents this: `verify_signature` checks signature validity per-org but never cross-checks `team.id`'s owning organization; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not organization consistency; `Team#organization` is set only in the create block of `find_or_create_by!`, and is never used as part of the lookup or as a post-lookup assertion.

### Impact Explanation
This directly maps to escalation into `Shipit.github_teams` authorization (High/Critical bound in the rubric): the attacker's GitHub login gains full Shipit access without ever being a legitimate member of the privileged org's team, purely by controlling an unrelated org's webhook secret. The attack is repeatable against any `Team` row whose `github_id` the attacker can guess or brute-force (GitHub team IDs are sequential integers, not secrets), and blast radius spans every tenant/org configured in the multi-org `Shipit.github` setup, since the vulnerable lookup ignores organizational boundaries entirely.

### Likelihood Explanation
Preconditions: Shipit configured with multiple GitHub orgs in `Shipit.github` (a documented supported configuration, see `docs/setup.md` "Using Multiple Github Applications"), and at least one other org has a `Team` in `Shipit.github_teams`. The attacker needs only to own/administer one GitHub org integrated with the same Shipit instance and know (or guess) a `github_id` used by a privileged team — no privileged secrets are required, satisfying the stated attacker model. Feasibility is high and the attack is trivially repeatable (one HTTP POST per attempt, no rate limiting bypass needed).

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` AND `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches the org that authenticated the webhook (`repository_owner`) before trusting `params.organization.login` for the lookup/creation, to prevent an attacker from also spoofing the `organization.login` field itself while forging as another org.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":membership cannot hijack a team belonging to another organization via github_id collision" do
  # Setup: org-a and org-b both configured in Shipit.github with distinct webhook_secrets
  Shipit.stubs(:github).with(organization: 'org-a').returns(github_app_a) # verify_webhook_signature stubbed true for org-a secret only
  Shipit.stubs(:github).with(organization: 'org-b').returns(github_app_b)

  privileged_team = Team.create!(github_id: 42, organization: 'org-b', slug: 'admins', name: 'Admins', api_url: 'https://x')
  Shipit.stubs(:github_teams).returns([privileged_team])

  @request.headers['X-Github-Event'] = 'membership'
  # Signature verified against org-a's secret (attacker-controlled), but team.id=42 belongs to org-b
  payload = {
    action: 'added',
    team: { id: 42, name: 'Admins', slug: 'admins', url: 'https://x' },
    organization: { login: 'org-a' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'org-a' } }
  }.to_json

  post :create, body: payload, as: :json
  assert_response :ok

  # BEFORE (broken): attacker is added to org-b's privileged team
  assert_equal 'org-b', Team.find_by(github_id: 42).organization
  assert Membership.exists?(team: privileged_team, user: User.find_by(login: 'attacker'))
  assert User.find_by(login: 'attacker').authorized? # should be false, but is true — proves the vulnerability
end
```
