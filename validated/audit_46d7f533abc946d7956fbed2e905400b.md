### Title
`Command#start` embeds interpolated (secret-bearing) command text in `NotFound`/`Denied` exception messages - (File: lib/shipit/command.rb)

### Summary
`Command#start` rescues `Errno::ENOENT`/`Errno::EACCES` by re-parsing the already-interpolated command string with `Shellwords.split` and reporting the first token as the "command name," but because interpolation substitutes `$VAR` in place without inserting a token boundary, a secret value glued to the executable name is included verbatim in the raised exception message, which is written into task/review-check output visible to the PR author.

### Finding Description
The binding that should hold is: `NotFound/Denied` message content == command-name-only, i.e. `Shellwords.split(interpolated_arguments.first).first == basename(executable)`, never containing any substituted environment value. This is violated because `EnvironmentVariables#interpolate` performs `argument.gsub(/(\$\w+)/) { Shellwords.escape(@env.fetch(variable) { ENV[variable] }) }` at [4](#0-3) , substituting the variable's value directly into the surrounding string without adding a delimiter. If a step's first word is written as e.g. `nonexistent-$SECRET_KEY`, the whole interpolated string becomes `nonexistent-<secretvalue> ...`, and `Command#start`'s rescue clauses at [5](#0-4)  take `Shellwords.split(interpolated_arguments.first).first`, which is the merged token `nonexistent-<secretvalue>` — the secret leaks into the raised `NotFound`/`Denied` message.

This message is captured and written into task output by `Command#stream!` via `Failed`, and explicitly by `EphemeralCommitChecks#capture`'s `rescue Command::Error => e; write(e.message)` at [3](#0-2) , which runs `deploy_spec.review_checks`/`dependencies_steps` from an **unmerged commit's checkout** (`StackCommands#with_temporary_working_directory(commit:)` at [6](#0-5) ). This is the "commit status check" flow that Shipit runs automatically on pull request commits per the README's `review.checks`/CI documentation, meaning an attacker who can merely push a commit/open a PR (no merge, no maintainer role) controls the `shipit.yml` content read by `DeploySpec::FileSystem.new(directory, stack)` for that ephemeral check run.

Combined with the separately-identified `EnvironmentVariables#interpolate` ENV-fallback bug (`@env.fetch(variable) { ENV[variable] }`), if `SECRET_KEY` is not in the whitelisted stack/task env, interpolation silently falls back to the Shipit server process's raw `ENV`, which may hold `GITHUB_TOKEN`, `secret_key_base`, database credentials, etc. The attacker names their check step's first token as `nonexistent-$GITHUB_TOKEN` (or any live process env var); when `PATH` lookup fails for that non-existent merged binary name, `Errno::ENOENT` is raised, `Command::Error#message` embeds the literal fetched secret, and it is written into the check output that the PR author (attacker) can view via the Shipit API/UI (`EphemeralCommitChecks#output`).

Existing guards do not catch this: `EnvironmentVariables#permit`/whitelist enforcement (`sanitize_env_vars`) only applies where explicitly invoked to filter accepted env keys, but `interpolate` itself does not call `permit` and falls back to the host process `ENV` regardless of any whitelist. Nothing in `Command#start`'s rescue path sanitizes or truncates the interpolated string before embedding it in the exception message.

### Impact Explanation
An attacker with no Shipit privileges (able only to open a PR / push a commit to a repo that has Shipit review-checks/CI configured) can exfiltrate arbitrary environment variables of the Shipit server process — including deploy-time secrets such as `GITHUB_TOKEN` or `secret_key_base` — by crafting a single check-step string and reading the resulting check output. This matches "Critical - exfiltration of `GITHUB_TOKEN` ... or deploy-time secrets" since the leak occurs via a normal, attacker-triggerable commit-check run and is repeatable against any repository connected to Shipit that runs `review.checks`/dependency steps, with the blast radius extending to any secret reachable from the Shipit worker process's environment (not scoped to a single tenant/stack).

### Likelihood Explanation
Preconditions: the target Shipit stack must have `shipit.yml` configured with `review.checks` (or `dependencies` steps) that are executed automatically for incoming commits/PRs (a common, documented configuration), and the leaked variable name must be guessable/known (e.g. standard names like `GITHUB_TOKEN`) or discoverable. No GitHub App private key, session, or API token is required — only push/PR access to a monitored repository. Attacker cost is low: a single crafted commit with a malformed step string; feasibility is high given `EphemeralCommitChecks` runs on unmerged commits by design, and the exploit is fully repeatable per commit/PR.

### Recommendation
In `Command#start`'s rescue branches, never derive the reported command name from `interpolated_arguments`; instead use the original, non-interpolated `@args.first` (or a pre-computed, un-substituted executable name) for the `NotFound`/`Denied` messages. Additionally, fix `EnvironmentVariables#interpolate` to never fall back to the raw process `ENV` for unwhitelisted variables (raise `NotPermitted` or substitute empty string instead), and ensure interpolation always inserts a token boundary or is only ever applied to fully-resolved argument arrays, not to sub-token positions, so secret material can never be concatenated into an executable-name string in an error message.

### Proof of Concept
```ruby
# test/unit/command_test.rb (minitest)
test "#start does not leak interpolated secret value in NotFound message" do
  secret = "sekrit-value-12345"
  command = Command.new("nonexistent-$SECRET_KEY", env: { "SECRET_KEY" => secret }, chdir: Dir.mktmpdir)

  PTY.expects(:spawn).raises(Errno::ENOENT)

  error = assert_raises(Command::NotFound) { command.start }
  refute_includes error.message, secret
  assert_equal "nonexistent-$SECRET_KEY: command not found", error.message
end
```
This asserts the binding `NotFound#message == command-name-only` (no interpolated secret substring) both before (would fail today, message contains `secret`) and after the fix.
