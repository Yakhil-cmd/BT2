### Title
Private Textcoin Payload Written to Disk with World-Readable Default Permissions - (File: wallet.js)

### Summary
`storePrivateAssetPayload()` in `wallet.js` persists the full private-payment payload for a private-asset textcoin (the claim mnemonic plus the private element chains needed to spend the coin) to a file on disk using `fs.writeFile(fullPath, zipFile, cb)` without ever specifying a restrictive file mode. This mirrors the Beego advisory's root cause (CWE-276): sensitive session/secret data written with the platform default permissions, allowing any other local, unprivileged OS user to read it.

### Finding Description
When a wallet sends a private-asset payment to a textcoin address (i.e., the recipient is not reachable by device message and must claim the coin later via a mnemonic), `sendMultiPayment`'s `preCommitCb` calls `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, cb)`: [1](#0-0) 

The function zips an object containing `{ mnemonic, chains }` — the exact secret material required to claim/spend the private asset unit — and writes it out with the bare Node `fs.writeFile` call, with no `{ mode: 0o600 }` option: [2](#0-1) 

Because no explicit mode is passed, Node.js creates the file with the default mode `0666` masked by the process umask (commonly resulting in `0644` on typical Linux/desktop configurations). This makes the file group/world-readable, i.e. any other local, unprivileged account on the same machine (a common scenario on shared/multi-user hosts, CI machines, or systems with unrelated compromised low-privilege services) can read the file and recover the mnemonic and private chain, exactly as in the Beego session-file disclosure (GHSA-hf4p-4j9r-3cvx / CVE-2019-16355), where session files were created with overly permissive default modes and could be read by any local user.

This is the private-payment counterparty flow explicitly in scope: the wallet owner, acting as sender in `sendMultiPayment` for a private asset, is the "private-payment counterparty" who triggers this code path when constructing and sending a private textcoin.

### Impact Explanation
The stored file contains the mnemonic and the recipient's private element chains for a private (confidential) asset. Anyone able to read this file — for example another unprivileged local account on a shared machine — obtains everything needed to redeem the textcoin via `handlePrivatePaymentFile`/`receiveTextCoin` before the intended recipient does. This is a direct unauthorized-spending / theft-of-funds primitive: the attacker races the legitimate holder of the mnemonic (who may have received it out of band, e.g. via email or messaging) and claims the private asset for themselves, permanently depriving the rightful recipient of the funds.

### Likelihood Explanation
Exploitation requires local access to the same machine as the wallet process (a second unprivileged OS account), which is a realistic scenario on shared hosting, VPS providers, lab/kiosk machines, or Cordova/desktop deployments with lax OS-level user isolation. No cryptographic weakness is needed — the vulnerability is a straightforward default-permission oversight in file creation, i.e., the same class of bug and same ease of exploitation as the referenced Beego CVE.

### Recommendation
When writing `storePrivateAssetPayload` (and any other function persisting mnemonics/private chains/private keys to disk, e.g. `handlePrivatePaymentFile`'s companion writes), explicitly pass a restrictive mode, e.g. `fs.writeFile(fullPath, zipFile, { mode: 0o600 }, cb)`, and consider creating the parent directory with `0700` as is already done elsewhere (see the `mode = parseInt('700', 8)` pattern used in `kvstore.js`). Additionally, verify/tighten permissions after write (`fs.chmod`) to defend against umask misconfiguration.

### Proof of Concept
1. On a shared multi-user machine, User A runs an ocore-based wallet and sends a private-asset payment as a textcoin, triggering `sendMultiPayment` → `storePrivateAssetPayload(fullPath, ...)` in `wallet.js`.
2. The resulting zip file at `fullPath` is created via `fs.writeFile` with default mode (no `mode` option), typically yielding `-rw-r--r--` (0644) given a standard `022` umask.
3. User B, an unprivileged local account on the same host, reads the file at `fullPath` (world/group readable), unzips it, and extracts `mnemonic` and `chains` from the JSON payload.
4. User B calls into the same `handlePrivatePaymentFile`/`receiveTextCoin` logic (or an equivalent client) using the stolen mnemonic/chains to claim the private asset before the intended recipient, resulting in theft of the funds.
