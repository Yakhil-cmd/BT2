### Title
Readiness flag `repoReady` is monotonic and never resets on sync failure, causing the HTTP health endpoint to report stale "ready" status - (File: main.go)

### Summary
The external report describes `estimatedAPR()` returning a stale value because the underlying state (`vestingProfit`/`lastUpdate`) is only updated conditionally (`accrue()` skipped when collateral ratio stays within a stable band), so a stale computed value keeps being reported as current after the real state has already changed to zero. The same "computed indicator lags real state" pattern exists in `git-sync`'s readiness tracking.

### Finding Description
`git-sync` exposes a boolean readiness indicator `repoReady`, guarded by `readyLock`, with `getRepoReady()`/`setRepoReady()` helpers [1](#0-0) . `setRepoReady()` is called once a sync succeeds, both in the initial "first loop as a sync" path and inside `SyncRepo` after a successful publish [2](#0-1) [3](#0-2) .

Crucially, there is no corresponding call that clears `repoReady` back to `false` when subsequent syncs fail. The main sync loop increments `failCount` and logs/retries on error, but never resets the readiness state that was set by an earlier successful sync [4](#0-3) . This means once the repo has synced successfully a single time, the HTTP readiness/health endpoint (which is backed by `getRepoReady()`) will keep reporting "ready"/healthy indefinitely, even if every sync attempt afterward fails and `failCount` grows without bound (up to `--max-failures`), analogous to `estimatedAPR()` continuing to report a stale non-zero APR after `lockedProfit()` has actually dropped to zero because the state-updating function (`accrue()` / a hypothetical `resetRepoReady()`) is never invoked on the relevant transition.

### Impact Explanation
Because `repoReady` is a one-way latch, an orchestrator (e.g., Kubernetes) polling the readiness/health HTTP endpoint would continue to see a healthy/ready sidecar even while the working copy has stopped updating due to persistent fetch failures, expired credentials, or ref/branch issues. Downstream consumers (mounted volume readers) would keep being told the sync is healthy while actually consuming an increasingly stale checkout, which matches the "persistent sync denial" / "publishing wrong or partial content" impact class — the tool silently stops making progress but never signals unhealthiness once it has been ready at least once.

### Likelihood Explanation
This requires no attacker privilege beyond normal operational conditions that cause `SyncRepo` to start failing after at least one prior success (e.g., credential expiry, remote unreachability, or a maliciously/accidentally corrupted upstream ref causing repeated fetch/checkout errors) — no special flags are required beyond the default HTTP health endpoint being enabled. This is a reachable, code-provable condition rather than a hypothetical, since the code path that would need to reset `repoReady` on failure simply does not exist [4](#0-3) .

### Recommendation
Reset `repoReady` to `false` (via a `clearRepoReady()`/`setRepoReady(false)` call) whenever a sync attempt fails inside the main loop's error branch, so the readiness endpoint accurately reflects the current sync health rather than the historical "has it ever succeeded" state. Optionally, incorporate `failCount`/`lastSuccessfulSync` staleness thresholds into the readiness computation instead of a simple monotonic boolean.

### Proof of Concept
1. Start `git-sync` against a reachable repo; it completes an initial successful sync, calling `setRepoReady()` [2](#0-1) , so the health endpoint returns 200.
2. Make the remote unreachable or revoke credentials so subsequent `SyncRepo` calls fail; the loop's failure branch runs, incrementing `failCount` and logging, but never calling any function to clear `repoReady` [4](#0-3) .
3. Query the HTTP health endpoint repeatedly — it will keep returning "ready"/200 (backed by `getRepoReady()`) indefinitely, even though the working tree has not been updated for an arbitrarily long time and no further syncs are succeeding, until `--max-failures` is hit and the process exits.

```go
// repoReady indicates that the repo has been synced.
var readyLock sync.Mutex
var repoReady = false

func getRepoReady() bool {
	readyLock.Lock()
	defer readyLock.Unlock()
	return repoReady
}

func setRepoReady() {
	readyLock.Lock()
	defer readyLock.Unlock()
	repoReady = true
}
```
