### Title
Membership webhook handler binds `Team#organization` to `params.organization.login` without verifying it matches the organization whose secret authenticated the request - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, which falls back from `repository.owner.login` to `organization.login` only if `repository` is absent. `MembershipHandler#find_or_create_team!` however always trusts `params.organization.login` directly to create/mutate a `Team`, without ever checking it against the organization that actually verified the signature. When both keys are present with different values, the signature is checked against one organization while the `Team` mutated belongs to a completely different one.

### Finding Description
Binding claimed to hold: `repository_owner` (the org whose `webhook_secret` verified the HMAC in `WebhooksController#verify_signature`) == `params.organization.login` (the org used by `MembershipHandler#find_or_create_team!` to create/mutate a `Team`).

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and uses it to pick the `GitHubApp` config to verify the signature: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `MembershipHandler#find_or_create_team!` never reads `repository_owner`/`repository`; it takes `params.organization.login` verbatim and assigns it to `team.organization` while finding/creating the `Team` by `github_id: params.team.id` [3](#0-2) .
- The `params` schema for the handler only `requires` fields; it does not forbid an additional `repository` key, so a request can legally carry both `repository.owner.login` (used by the controller to pick the verifying app/secret) and a different `organization.login` (used by the handler to select/mutate the `Team`) [4](#0-3) .
- `Team::REQUIRED_HOOKS`/`github_hooks` (the `GithubHook::Organization` association scoped to `:membership`) exists on the model [5](#0-4)  but is never referenced by `MembershipHandler`, the controller, or anywhere else in the searched codebase - it plays no role in gating team creation.

Exploit flow: an attacker who controls/administers an organization that is also configured as a tenant of this Shipit instance (multi-org support is demonstrated by `test/dummy/config/secrets_double_github_app.yml`, `OrgOne`/`OrgTwo`) and knows that organization's own `webhook_secret` (or targets an org configured with no `webhook_secret`, in which case `verify_webhook_signature` returns `true` unconditionally per `GitHubApp#verify_webhook_signature` [6](#0-5) ) sends:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<valid HMAC for OrgA's secret>
{
  "action": "added",
  "team": {"id": <victim_team_github_id>, "name":"x","slug":"x","url":"x"},
  "organization": {"login": "OrgB"},
  "member": {"login": "attacker_or_target_user"},
  "repository": {"owner": {"login": "OrgA"}}
}
```
`repository_owner` resolves to `OrgA`, the signature check passes using `OrgA`'s app/secret, and the request reaches `Webhooks.for_event('membership')`. Inside the handler, `params.organization.login` is `OrgB`, so the `Team` for `OrgB` is created/mutated and the attacker-chosen member is added to it - a payload that "authenticated" as belonging to org A ends up mutating org B's `Team`.

Existing guards do not catch this: `verify_signature` only checks the HMAC for whichever org `repository_owner` resolves to; it never compares that org to `params.organization.login` used downstream by the handler. `drop_unhandled_event`, `ExplicitParameters` schema and `force_github_authentication` are unrelated to this check.

### Impact Explanation
The `Team` model backs `Shipit.github_teams` and `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6) , i.e., team membership directly gates who is allowed to use the Shipit application. An attacker who legitimately controls (or whose org's webhook_secret they know) any single tenant organization configured on the same Shipit instance can add arbitrary GitHub users as members of a `Team` belonging to a different organization, by crafting a `membership` payload with mismatched `repository.owner.login` vs `organization.login`. This directly matches the explicitly listed Critical impact: "a payload for one repository mutating another's stack, commit, task or team," and can escalate into `Shipit.github_teams` authorization (a High-listed impact) by adding a user to a privileged team. The blast radius spans tenants on multi-org Shipit deployments.

### Likelihood Explanation
Requires: (a) Shipit configured for more than one GitHub organization (a supported and documented configuration, per `secrets_double_github_app.yml`), and (b) attacker either administers one of those orgs (knows its own `webhook_secret`) or targets a configured org whose `webhook_secret` is left blank (an explicitly supported, non-error configuration per `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret`). Neither precondition requires possessing the victim org's secret, a Shipit session, or any privileged Shipit role - fully consistent with the stated attacker model. Given multi-tenant Shipit is a real supported topology, this is feasible and repeatable per request against any known target `github_id`/organization pair.

### Recommendation
In `MembershipHandler` (and any other handler that reads an `organization`/`repository` sub-object), verify that `params.organization.login` (or `repository.owner.login`) equals the `repository_owner` that the controller used to select the verifying `GitHubApp`/webhook secret before creating or mutating any record. Reject the webhook (422) on mismatch. More generally, the controller should pass the verified organization identity into the handler dispatch so handlers cannot substitute a different organization value from elsewhere in the payload.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs (mirroring `secrets_double_github_app.yml`) - `OrgA` with a known `webhook_secret`, `OrgB` with an existing `Team` fixture.
2. Build a `membership` payload: `organization.login = "OrgB"`, `repository.owner.login = "OrgA"`, valid HMAC signature computed with `OrgA`'s secret.
3. Assert: `Shipit.github(organization: 'OrgA').expects(:verify_webhook_signature).returns(true)` is what gets invoked (i.e., `repository_owner` resolved to `OrgA`).
4. `assert_difference -> { Shipit::Membership.count }, 1 do post :create, body: payload, as: :json end` and then `assert_equal 'OrgB', Shipit::Team.find_by(github_id: payload_team_id).organization` - proving the `Team` mutated belongs to `OrgB` even though only `OrgA`'s secret verified the request.
5. Contrast with a control test where `repository.owner.login` and `organization.login` are equal, confirming normal behavior is unaffected - isolating the divergence to the mismatched-key case.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
