## Title
Cross-organization forgery of GitHub Status/Push webhooks via mismatched signature-selection field vs. write-target field - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to verify a webhook against using `repository_owner`, a value pulled out of the attacker-supplied JSON body itself. Once the signature check passes, the *same* raw JSON body is handed unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, and handlers such as the status handler act on a different, independently-controlled field of that body (`repository.full_name` / `sha`) to decide which `Stack`/`Commit` to write to. Nothing re-confirms that the organization whose secret validated the request actually owns the repository/commit that gets mutated.

### Finding Description
`repository_owner` is computed purely from attacker-controlled JSON: [1](#0-0) 

It is used only to pick which organization's `webhook_secret` verifies the HMAC: [2](#0-1) 

`verify_webhook_signature` (in `Shipit::GithubApp`) is a plain HMAC check over the raw body using the secret configured for the organization named by `repository_owner`: [3](#0-2) 

There is no cryptographic or logical binding between the `repository.owner.login` field (used to pick the trust anchor) and any other field in the same JSON body that handlers subsequently use to select *what gets written*. For the `status` event, the handler creates a `Status` record on a `Commit` directly from attacker-supplied fields (`state`, `description`, `target_url`, `context`, `created_at`) with no re-fetch from GitHub for confirmation, as demonstrated by the existing test suite: [4](#0-3) 

Because a Shipit instance can be configured with multiple organizations, each with its own `webhook_secret` (see the multi-org secrets layout): [5](#0-4) 

an operator/admin of *any one* onboarded organization (an "unprivileged attacker" with respect to every *other* onboarded organization) legitimately knows their own organization's `webhook_secret`. They can craft a JSON payload where:
- `repository.owner.login` = their own org (so `verify_signature` selects their own, legitimately-known secret and the HMAC passes), and
- `repository.full_name` / `sha` = a victim organization's repository/commit (so the handler resolves and mutates the victim's `Stack`/`Commit`).

This breaks the equality the engine implicitly relies on: **organization that authenticated the request == repository/commit that is written by the request**. The webhook endpoint is unauthenticated at the transport layer (any host can POST to `/webhooks`), so the only gate is this per-organization HMAC, which the finding shows is bound to the wrong field.

### Impact Explanation
An attacker who administers their own onboarded organization on a shared Shipit instance can inject fabricated commit statuses (e.g., forcing `state: "success"` for required CI/merge-queue contexts) against a completely different organization's commits/stacks. Shipit's deploy and merge-queue gating logic is driven by these `Status` records (`ci.require`, `merge.require`, etc.), so forging a passing status can help clear the gate for an **unauthorized deploy or an unauthorized merge** on a repository the attacker does not control — matching the "unauthorized deploy, rollback or merge" critical-impact category. The `push` handler is similarly reachable to enqueue sync jobs against an unrelated stack using a forged `repository.full_name`.

### Likelihood Explanation
High for any Shipit deployment servicing more than one GitHub organization (a documented, supported configuration). No repository write access, GitHub App key, session, or `ApiClient` token is required — only knowledge of a webhook secret the attacker's own organization was legitimately given, which is inherent to being an onboarded tenant. Constructing the forged JSON body and its HMAC is trivial once that secret is known.

### Recommendation
After the signature passes, cross-validate that the repository/commit the handler is about to act on actually belongs to the organization (`repository_owner`) whose secret validated the signature — e.g., verify `Repository#owner` (or `Stack#repository`) matches `repository_owner` before allowing `PushHandler`/`StatusHandler`/other handlers to mutate state, and/or scope `Commit`/`Stack` lookups by the authenticated organization rather than by `sha`/`full_name` alone.

### Proof of Concept
1. Attacker legitimately administers organization `attacker-org` on the shared Shipit instance and knows its `webhook_secret`.
2. Attacker builds a `status` event body:
```json
{
  "sha": "<known sha of victim-org/victim-repo commit>",
  "state": "success",
  "description": "forged",
  "target_url": "https://attacker.example/",
  "context": "required-ci-check",
  "created_at": "2026-09-01T00:00:00Z",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches attacker-org's `GithubApp`, and the HMAC check passes because the attacker signed with their own valid secret.
5. The `status` handler creates/updates a `Status` on the `victim-org/victim-repo` commit using the attacker-supplied `state`/`description`/`target_url`, as shown to be possible by the existing test at `test/controllers/webhooks_controller_test.rb:42-59`, without any re-check that `attacker-org` is entitled to write to `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
