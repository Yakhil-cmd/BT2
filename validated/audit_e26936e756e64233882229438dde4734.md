### Title
API token scoped to a single stack can read CI/deploy status of any stack via CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`ApiClient` records can optionally be bound to a single `stack_id`, restricting the stacks the token is meant to expose [3](#0-2) . `BaseController` enforces this binding for all other API endpoints by scoping the resolvable stacks through `stacks`/`stack` [2](#0-1) . `Api::CCMenuController`, however, overrides `stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id?` restriction [4](#0-3) .

### Finding Description
The binding broken here is: `token.stack_id (if present) == stack.id being touched`.

- Before the attacker's action: a token such as fixture `here_come_the_walrus` is created with `stack: shipit` and permission `read:stack` only [5](#0-4) . This is precisely the pattern used by `CCMenuUrlController`, which creates a `read:stack`-only `ApiClient` intended to be embedded in external CI dashboards/tools [6](#0-5) . Anywhere else in the API (e.g. `Api::StacksController`, `Api::DeploysController`), such a scoped token can only resolve `stack` from within `Stack.where(id: current_api_client.stack_id)`, per `BaseController#stacks`.
- `Api::CCMenuController#authenticate_api_client` accepts the token from a plain query-string `params[:token]` (no basic auth, no CSRF), then `require_permission :read, :stack` only checks the permission list, not the stack scope: `current_api_client.check_permissions!(operation, scope)` in `ApiClient#check_permissions!` never consults `stack_id` [7](#0-6) .
- After the attacker's action: `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly, so a request `GET /api/stacks/OTHER_STACK/ccmenu?token=<walrus-scoped-token>` returns CI status, last deploy state, and lock state for `OTHER_STACK`, even though the token was created/scoped for a different stack.

This breaks the "stack a token authorizes vs. a stack it touches" binding: the token authorizes only the `shipit` stack, but the endpoint lets it touch any stack in the installation.

### Impact Explanation
Any holder of a `read:stack`-scoped token intended to be exposed publicly for a single stack's CI badge/status (the exact use case `CCMenuUrlController` supports) gains unauthorized read access to the CI/build/deploy status of every other stack in the Shipit installation, including stacks belonging to different repositories/teams. This is an authorization-scope escalation and an unintended disclosure of stack state (build status, lock reason exposure via "locked stacks show as failed", deploy timing) to a party who was only supposed to see one stack.

### Likelihood Explanation
High. Exploitation requires only possessing any valid `read:stack` token (even one intentionally scoped to a single stack and often distributed to external, less-trusted CI-badge consumers) and changing the `stack_id` route/query parameter — no additional privileges, signature, or session are needed.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the scoped `stacks` collection (i.e., `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id?` restriction from `BaseController` is honored the same way it is for every other API controller.

### Proof of Concept
1. Create (or observe) an `ApiClient` scoped to stack A with only `read:stack` permission (this is exactly what `CCMenuUrlController#client` provisions for public CI badges) [6](#0-5) .
2. Obtain that client's `authentication_token` (it is embedded directly in the generated CCMenu URL, e.g. as returned by `GET /ccmenu_url?stack_id=A`).
3. Send `GET /api/stacks/B/ccmenu?token=<tokenScopedToA>` for any other stack `B` in the installation.
4. Observe that the response renders `B`'s project status (name, lastBuildStatus, lastBuildLabel, etc.) via `shipit/ccmenu/project`, confirming the token scoped to stack A was used to read stack B's state [8](#0-7) .
