## Confirmed

`app/models/shipit/api_client.rb:24-27` confirms `ApiClient.authenticate` only verifies the signed id and returns the matching record — it performs no scope check itself; scope enforcement is expected to happen in the controller via `stacks`/`stack`. [1](#0-0) 

### Title
Stack-scoped API token bypasses its stack restriction in `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds a token's authorised stack via `stacks`/`stack`, restricting a scoped `ApiClient` to `current_api_client.stack_id` [2](#0-1) . `Shipit::Api::CCMenuController` re-implements `stack` to load `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id` [3](#0-2) . This breaks the binding: *the stack a token authorises* (its `stack_id` column) *versus the stack it touches* (any `stack_id` param).

### Finding Description
`BaseController#stacks` is the single place scope is enforced: if `current_api_client.stack_id?` is true, only that stack is in scope; otherwise all stacks are visible [4](#0-3) . Every other API controller derives `stack` from this scoped relation (`stacks.from_param!(...)`) [5](#0-4) .

`CCMenuController` overrides `authenticate_api_client` to accept a `token` query parameter instead of Basic-Auth [6](#0-5) , and overrides `stack` to bypass the `stacks` scoping entirely, resolving any `stack_id` param against the global `Stack` relation [7](#0-6) . The only permission check performed is `require_permission :read, :stack` [8](#0-7) , which merely checks that `read:stack` is in the client's permission list (`ApiClient#check_permissions!`) [9](#0-8)  — it does not verify the requested stack matches `current_api_client.stack_id`.

Tokens intended to be stack-scoped are routinely generated this way: `CCMenuUrlController#client` creates/finds an `ApiClient` with `permissions: %w[read:stack]` per user (no explicit `stack:` scope is even set here, but the same `read:stack`-scoped `ApiClient` model is also usable — and expected to be restrictable — via the generic `here_come_the_walrus`-style scoped token pattern exercised in `stacks_controller_test.rb`, where a client scoped to one stack is asserted to see only that stack through the normal `stacks` method) [10](#0-9) . Because `CCMenuController` never calls the shared `stacks` method, any `read:stack`-permissioned token — including one an administrator deliberately scoped to a single stack via `ApiClient#stack_id` to limit exposure — can be replayed with a different `stack_id` to read the name, last build status/label/time, and lock status of an unrelated stack via `GET /api/:stack_id/ccmenu.xml?token=...` [11](#0-10) .

### Impact Explanation
This is an authorization-scope bypass: a token an administrator restricted to stack A (`ApiClient.stack_id = A`) can be used to read build/deploy status of stack B, C, ... — an unauthenticated-for-that-stack read of stack state, matching the engine's own "unauthorized read of stack state" high-impact category. The mismatch is entirely within engine code (`CCMenuController`), not a host-application misconfiguration, and requires only possession of a stack-scoped `read:stack` token, not elevated privilege.

### Likelihood Explanation
Any holder of a valid, intentionally stack-scoped `ApiClient` token (e.g., a CI status widget token meant for one stack) can trivially probe other numeric/`owner/repo/env` stack params, since the controller performs zero comparison between `current_api_client.stack_id` and `params[:stack_id]`.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) exactly as `BaseController#stack` does, so the `read:stack` permission check is paired with the actual stack-scope restriction bound to the token.

### Proof of Concept
1. Admin issues (or a client creates) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to `Stack A`'s id.
2. Using that token, request `GET /api/<Stack B id_or_owner-name-env>/ccmenu.xml?token=<tokenA>` where Stack B ≠ Stack A.
3. `CCMenuController#authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])` [6](#0-5) ; `require_permission :read, :stack` passes because the client has `read:stack` [9](#0-8) ; `stack` resolves Stack B via the unscoped `Stack.from_param!` [7](#0-6) .
4. The response renders Stack B's CI/deploy status (`shipit/ccmenu/project`), even though the token was only supposed to authorise Stack A.
