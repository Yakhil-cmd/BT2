### Title
Cross-organization commit-status forgery via webhook signature/repository binding mismatch - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates an inbound webhook by resolving a GitHub organization from attacker-supplied JSON fields and checking the HMAC against *that organization's* `webhook_secret`. However, the `status` event handler (`StatusHandler#process`) then acts on **any** commit in the entire Shipit database matching a raw `sha` string, with no scoping to the repository or organization that was actually authenticated. This breaks the intended binding: "organization that authenticated" ≠ "repository/commit that is written."

### Finding Description
`WebhooksController#verify_signature` picks the signing organization purely from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including a distinct `webhook_secret`) in a multi-tenant Shipit deployment, confirming that separate GitHub organizations can be configured with separate secrets on the same Shipit instance: [3](#0-2) 

Once the HMAC passes for *some* configured organization, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs with the full, attacker-controlled JSON body: [4](#0-3) 

Most handlers at least scope their side effects by `repository.full_name` from the same payload (e.g. `PushHandler`/`Handler#stacks`): [5](#0-4) 

But `StatusHandler` does not scope by repository or organization at all — it matches commits globally by `sha`: [6](#0-5) 

Because `sha` values are 40-hex-character git object IDs that are public information (visible on GitHub, in PRs, commit links, CI logs, etc.), an attacker who can get a validly HMAC-signed webhook accepted for *any one* configured organization (e.g. their own legitimately onboarded organization/repository in the same multi-tenant Shipit instance) can forge a `status` event carrying the `sha` of a commit belonging to a **completely different organization's repository**, and set `state: "success"` (or any other CI state) for it. `Commit#create_status_from_github!` writes this as if it were a real CI status reported by GitHub, which subsequently feeds `Stack#branch_status`/`#merge_status`/deployability checks used to gate deploys and merges.

This is exactly the class of binding violation called out in the rules: the entity that authenticated the request (organization A, via A's `webhook_secret`) is decoupled from the entity the code actually writes to (a commit that may belong to organization B's repository/stack), because `StatusHandler` never re-checks that the commit's owning repository matches the authenticated organization.

### Impact Explanation
By forging a fake "success" CI status for a commit sha belonging to another organization's stack, an attacker with legitimate but unrelated webhook credentials for one tenant can unblock `branch_status`/`deployable?` gates that depend on commit status, and potentially trigger an automatic/queued deploy or unblock a merge on a repository they have no authorization over. This satisfies the "unauthorized deploy or merge" impact category, since it circumvents the CI-gating trust boundary that Shipit relies on to decide when a commit is safe to deploy.

### Likelihood Explanation
This requires the attacker to possess (or forge) a valid `X-Hub-Signature` for *some* organization configured on the Shipit instance — which is realistic in any multi-tenant deployment where multiple GitHub organizations onboard their own webhooks (each org administrator legitimately knows their own `webhook_secret`, and can point their own configured hook's payload at arbitrary JSON since the WebhooksController accepts a raw POST, not a strict GitHub-only webhook proxy). No repository write access, GitHub App key, or Shipit session/API token is needed — only a legitimately configured organization's own webhook secret, which is a real credential available to that organization's administrators. The victim's `sha` is public GitHub information, and `StatusHandler` performs zero repository/org cross-check, making exploitation straightforward once one valid secret is known.

### Recommendation
In `StatusHandler#process` (and more generally in `Handler`), scope the target commit(s) by the repository resolved from the same authenticated payload (`Repository.from_github_repo_name(repository_name)` as done in `Handler#stacks`) and reject/ignore statuses for commits that don't belong to a stack under that repository. More fundamentally, `WebhooksController#verify_signature` should ensure the resolved `repository_owner` used for signature verification is the *same* organization that owns the `repository.full_name`/commit being mutated, rather than trusting them as independent, unlinked fields of the same unauthenticated-until-verified JSON body.

### Proof of Concept
1. Attacker legitimately configures/owns GitHub organization `AttackerOrg`, which is a valid tenant on the shared Shipit instance with its own `webhook_secret` (`S_A`).
2. Attacker identifies a commit `sha = X` belonging to `VictimOrg/victim-repo`, a repository tracked by the same Shipit instance under a different stack (sha's are public via GitHub UI/API).
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_A, body)` for a payload:
```json
{
  "sha": "X",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"AttackerOrg"`, calls `Shipit.github(organization: "AttackerOrg")`, and the HMAC check succeeds because it was signed with `S_A`. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: "X").each { |commit| commit.create_status_from_github!(params) }`, which matches the commit belonging to `VictimOrg/victim-repo` regardless of the fact that only `AttackerOrg`'s secret was verified. [6](#0-5) 
6. The forged "success" status is now recorded against `VictimOrg`'s commit, potentially unblocking deploy/merge gating logic that depends on `Commit#status`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
