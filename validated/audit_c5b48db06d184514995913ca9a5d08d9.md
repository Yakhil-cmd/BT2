### Title
`StatusHandler#process` writes commit statuses without checking `repository_name`/`stacks`, enabling cross-tenant status forgery via SHA collision - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` never calls `Handler#repository_name` or `Handler#stacks`, unlike `PushHandler#process`, which scopes every write through `stacks.not_archived.where(branch:)`. `StatusHandler` instead resolves target rows globally via `Commit.where(sha: params.sha)`, so any signed webhook for a repository the attacker owns can mutate a commit-status row belonging to a different stack/repository as long as the SHA matches.

### Finding Description
The binding that should hold for every handler is `repository_name == payload.dig('repository', 'full_name')` gating the records mutated, implemented in the base class as: [1](#0-0) 

`PushHandler#process` respects this binding by scoping through `stacks`, which is derived from `Repository.from_github_repo_name(repository_name)`: [2](#0-1) 

`StatusHandler#process`, however, resolves its target purely by SHA, with no reference to `repository_name` or `stacks` anywhere in its body: [3](#0-2) 

`Commit.where(sha: params.sha)` is a global, cross-stack query — `sha` is not scoped by `repository_id`/`stack_id` in this lookup. Since git commit hashes are content-addressed, identical commits (e.g., a shared history, cherry-pick, or a public commit forked/mirrored into another tracked repository) produce identical SHAs in unrelated repositories/stacks. `create_status_from_github!` then writes a new `Status` row scoped to whichever stack the matched `Commit` actually belongs to: [4](#0-3) 

The attacker's exact request: send `POST /webhooks` with `X-Github-Event: status` and a body whose `repository.full_name`/`repository.owner.login` are the attacker's own repository (so `verify_signature` passes with a legitimately GitHub-signed payload for a repo the attacker owns), but whose `sha` field is the SHA of a commit that also exists in a victim stack's `commits` table. `WebhooksController#verify_signature` only authenticates that the payload came from GitHub for `repository_owner` — it never checks that the `sha` inside the payload belongs to that same repository: [5](#0-4) 

Because `StatusHandler` never dereferences `repository_name`/`stacks`, this signature check is the only gate, and it does not bind the mutated commit to the authenticated repository. The victim's commit gets a forged status (e.g., `success`), which `add_status` broadcasts and which feeds `deployable?`/`schedule_continuous_delivery`, potentially causing an unauthorized deploy of the victim's stack: [6](#0-5) 

### Impact Explanation
An attacker who owns any repository wired to the Shipit webhook endpoint can forge a `success`/`failure` CI status on a commit belonging to an entirely different tenant's stack, as long as a SHA collision exists between the two repositories' commit histories. This can mark an otherwise-unverified commit as `deployable?` in the victim stack, triggering `ContinuousDeliveryJob` and an unauthorized deploy — matching the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy." The attack is repeatable against any stack/commit for which the attacker can produce or discover a matching SHA.

### Likelihood Explanation
Preconditions: the attacker must own/control a repository that has a working, correctly signed webhook delivery path to the Shipit host (explicitly granted by the threat model), and must find/produce a commit whose SHA also exists in a victim's tracked stack (achievable via forking a publicly tracked repository, subtree/mirror workflows, or cherry-picking identical trees — well within reach for a determined but unprivileged attacker). No Shipit secrets, sessions, or team memberships are required. This is directly testable at the code level: `StatusHandler.instance_method(:process).source_location`'s body never calls `repository_name` or `stacks`, while `PushHandler#process` does.

### Recommendation
Scope `StatusHandler#process`'s `Commit` lookup by the authenticated repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, mirroring the gating already used in `PushHandler`, so a status payload can only mutate commits belonging to stacks whose repository matches `payload.dig('repository','full_name')`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual additions)
test "PushHandler#process scopes via Repository.from_github_repo_name" do
  payload = { 'ref' => 'refs/heads/main', 'after' => 'deadbeef', 'repository' => { 'full_name' => 'org/attacker-repo' } }
  Shipit::Repository.expects(:from_github_repo_name).with('org/attacker-repo').returns(nil)
  Shipit::Webhooks::Handlers::PushHandler.call(payload)
end

test "StatusHandler#process never scopes via Repository.from_github_repo_name (cross-tenant write)" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = shipit_commits(:first, stack: victim_stack, sha: 'collided_sha')

  payload = {
    'sha' => 'collided_sha',
    'state' => 'success',
    'repository' => { 'full_name' => 'org/attacker-repo' } # attacker's own repo, not victim's
  }

  Shipit::Repository.expects(:from_github_repo_name).never

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 'success', victim_commit.reload.status.state
end
```
This demonstrates that `StatusHandler.call` mutates `victim_commit` (belonging to `org/victim-repo`'s stack) using a webhook payload authenticated only for `org/attacker-repo`, with zero calls to `Repository.from_github_repo_name`, in direct contrast to `PushHandler`.
