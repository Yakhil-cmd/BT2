### Title
Deletion of Protocol Treasury Account Permanently Halts Chunk Application via Unrecoverable `StorageInconsistentState` Error — ([File: runtime/runtime/src/lib.rs])

### Summary
The protocol treasury account (`protocol_treasury_account`, default `"near"`) is a fixed "reward recipient" configured once in genesis with no mechanism to change, disable, or protect it. `action_delete_account` in `runtime/runtime/src/actions.rs` allows any account — including the treasury account itself — to be deleted via a normal `DeleteAccount` transaction as long as its storage usage is below `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, with no special-case check preventing deletion of the treasury account. If the treasury account is deleted, the very next epoch's `update_validator_accounts` call fails with an unrecoverable `StorageError::StorageInconsistentState`, mirroring the reported bug class: a "fee recipient" that cannot be removed/reconfigured, and whose invalidity causes the reward-distribution machinery to fail entirely.

### Finding Description
`RewardCalculator::calculate_reward` unconditionally inserts a reward entry for `protocol_treasury_account` into the rewards map every epoch: [1](#0-0) .

At the first block of every epoch, `Runtime::update_validator_accounts` processes this `ValidatorAccountsUpdate`. For the treasury account specifically, it does an unconditional lookup and treats a missing account as a fatal, unrecoverable storage inconsistency rather than a recoverable/skippable condition: [2](#0-1) 

There is no code path in `configureFeeRecipient`-equivalent logic (i.e. genesis/runtime config) to remove or replace `protocol_treasury_account`, and critically, `action_delete_account` — the general-purpose account deletion handler used for any account, including this one — contains no special-case guard preventing the treasury account from being deleted: [3](#0-2) 

Because the treasury account is a normal named account (holding an access key, like any other account), whoever controls its access key can submit an ordinary, unprivileged `DeleteAccount` transaction against it (subject only to the generic `MAX_ACCOUNT_DELETION_STORAGE_USAGE` limit, which a low-usage account like a treasury account will easily satisfy). Once deleted, the next epoch boundary's `update_validator_accounts` call will find no account for `protocol_treasury_account_id`, invoke `.ok_or_else(|| StorageError::StorageInconsistentState(...))`, and propagate a `RuntimeError` out of `apply()`. This exactly parallels the original report's core flaw: the protocol has no way to safely disable/remove a hardcoded reward recipient, and the reward-distribution logic blindly assumes its continued validity, so an invalidated recipient breaks the entire distribution path for that block/shard.

### Impact Explanation
`update_validator_accounts` runs at the first block of every epoch for the shard containing the treasury account, and its failure is propagated as a hard `RuntimeError`/`StorageError`, which is treated in the node as an unrecoverable state — this is squarely in the "storage staking/balance accounting" surface excluded from being benign: it can produce a chain stall (chunk application for that shard can never succeed again post-deletion) or trigger node panics on all nodes attempting to apply that chunk, since every honest validator computing the same state transition hits the identical fatal path deterministically. Unlike a single validator bug, this affects state transition validity network-wide (state divergence is not possible since all correct nodes fail identically, but the chain is unable to progress — a liveness/DoS impact matching "chain stall").

### Likelihood Explanation
Likelihood depends on whether the private key(s) controlling the protocol treasury account (`"near"`) are held by a party willing/able to delete the account, and whether the account's on-chain storage usage stays below the deletion threshold (treasury accounts holding only a balance and access keys, no contract, typically qualify). No special protocol-level protection exists in `action_delete_account` to block this for the treasury account specifically, so the condition is fully reachable through a standard, unprivileged transaction path (`DeleteAccount` action) without requiring any validator or node-level compromise.

### Recommendation
Add an explicit guard in `action_delete_account` (or upstream in transaction/receipt validation) rejecting `DeleteAccount` actions targeting the configured `protocol_treasury_account_id`, analogous to the suggested fix of removing invalid fee recipients rather than silently allowing an unrecoverable state. Additionally, `update_validator_accounts` should not treat a missing treasury account as a hard `StorageInconsistentState` panic-class error; it should either fail the specific action gracefully or the protocol should provide a governance mechanism to reconfigure/replace the treasury account before it can become invalid.

### Proof of Concept
1. Observe that `protocol_treasury_account` (default `"near"`) is a normal named account with its own access keys, per `PROTOCOL_TREASURY_ACCOUNT` constant: [4](#0-3) .
2. Using the treasury account's access key, submit a standard `DeleteAccount` transaction; `action_delete_account` performs no check for this special account and deletes it via `remove_account`: [5](#0-4) .
3. At the next epoch boundary, `Runtime::update_validator_accounts` is invoked with `validator_accounts_update.protocol_treasury_account_id = Some("near")`. Since the account no longer exists, `get_account(...).ok_or_else(...)` triggers `StorageError::StorageInconsistentState("Protocol treasury account near is not found")`: [6](#0-5) .
4. This error propagates out of `apply()` as a `RuntimeError`, breaking reward distribution/chunk application for that shard at every subsequent epoch boundary, consistent with the reported bug class of an un-removable/invalid reward recipient permanently breaking distribution logic.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
