### Title
Rounding in per-recipient headers-commission split allows over-distribution (bytes inflation) - (File: `headers_commission.js`)

### Summary
`headers_commission.js::calcHeadersCommissions` splits a fixed, already-collected `headers_commission` amount among multiple `earned_headers_commission_recipients` by independently rounding each recipient's share with `Math.round()`. Because rounding is applied per-recipient instead of allocating the remainder to a single recipient, the sum of the rounded per-recipient amounts can exceed the original `full_amount` that was actually paid as a fee by the parent unit(s). The excess bytes are inserted into `headers_commission_outputs` and become spendable, effectively minting bytes that were never removed from anyone's balance — this is the direct analog of the reported rounding bug, except instead of funds being stuck/lost, here rounding can create tokens out of thin air (supply inflation), which is a more severe impact.

### Finding Description
When headers commission for a payer unit is won by a child unit, the earned amount (`full_amount`) is fixed by the payer's `headers_commission` field. If the winning child unit is multi-authored (or otherwise declares `earned_headers_commission_recipients`), the commission is split among recipients according to declared integer percentage shares that must sum to exactly 100, enforced only by `validateHeadersCommissionRecipients`: [1](#0-0) 

The actual split is computed independently per recipient using `Math.round`, both in the in-RAM path and the SQL/DB path: [2](#0-1) [3](#0-2) 

and equivalently in the MySQL variant: [4](#0-3) 

Because each recipient's share is rounded independently instead of computing all-but-last shares and assigning the remainder to the last recipient, `Σ Math.round(full_amount * share_i / 100)` is not guaranteed to equal `full_amount`. For example, with 2 recipients each declaring a 50% share and `full_amount = 3` (a perfectly legal, commonly occurring small headers-commission amount), each recipient receives `Math.round(1.5) = 2`, for a total of `4` — one extra byte credited beyond what was ever collected as a fee. The validation code only checks that the shares sum to `100`, not that resulting rounded amounts are internally consistent, so this configuration is fully accepted.

These per-address contributions are aggregated into `headers_commission_outputs` and become spendable via `headers_commission`-type inputs, verified against `SUM(amount)` for the claimed MCI range (see `mc_outputs.calcEarnings`/`headers_commission_outputs` consumption path used by `validatePaymentInputsAndOutputs` for `type: "headers_commission"`): [5](#0-4) 

Once inserted, these outputs are treated as legitimate spendable byte balances by every node, indistinguishable from correctly-collected commission.

### Impact Explanation
This results in genuine network-wide byte supply inflation, not merely a display or bookkeeping issue: the extra bytes created by rounding become real, spendable outputs credited to addresses chosen entirely by the attacker (the recipient list in `earned_headers_commission_recipients` is attacker-controlled on their own multi-authored unit). While each occurrence creates a small amount (bounded by the number of recipients minus one, each at most ~1 unit per rounding step), it is:
- Deterministic and repeatable — the attacker can compose an unlimited number of multi-authored units with the "beneficial" share configuration (e.g., 50/50, or other splits with odd `full_amount`) to accumulate inflation over time across every payer whose commission the attacker's units win.
- A consensus-relevant computation performed identically by every full node during stabilization (`calcHeadersCommissions`), so it does not create disagreement between honest nodes — instead it uniformly inflates the supply, which every node will accept as valid.

This matches the "supply inflation" impact class explicitly permitted for this analysis.

### Likelihood Explanation
This is not a rare fork/rounding edge case requiring adversarial network conditions — a single unprivileged unit poster can trigger it, deterministically, by:
1. Composing a multi-authored unit (2+ authors) and specifying `earned_headers_commission_recipients` with shares chosen to maximize aggregate rounding-up (e.g., splitting evenly among 2+ addresses under the attacker's control).
2. Getting that unit's headers commission to be won repeatedly (any unit whose parents pay `headers_commission`, which is a normal, unavoidable part of unit composition — see `composer.js`'s default `earned_headers_commission_recipients` handling).

Since `validateHeadersCommissionRecipients` only enforces `total_earned_headers_commission_share === 100`, there is no obstacle to selecting share values that maximize rounding drift, making the likelihood high and the exploit trivially repeatable at scale (limited only by the attacker's ability to post units and win headers commission, which is inherent to normal DAG participation).

### Recommendation
Change the per-recipient allocation in `headers_commission.js::calcHeadersCommissions` (both the RAM path and the SQL path for MySQL/SQLite) to guarantee `Σ amounts === full_amount`:
- Sort recipients deterministically (already sorted by address).
- Compute `Math.round`/`Math.floor` amounts for all recipients except the last.
- Assign the last recipient `full_amount - Σ(previous amounts)` so the total is exactly conserved regardless of rounding.

Apply the same remainder-based allocation to the MySQL `ROUND(...)` SQL variant to keep both storage backends consistent, and add a regression check (as already done via `_.isEqual` cross-checks in this file) asserting `SUM(contribution amounts per full_amount group) === full_amount`.

### Proof of Concept
1. Attacker controls addresses A and B.
2. Attacker composes/authors a 2-author unit and sets `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` — this passes `validateHeadersCommissionRecipients` since shares sum to 100. [6](#0-5) 
3. This unit becomes the winning child unit for a parent whose `headers_commission` (`full_amount`) is an odd number, e.g. `3` (small headers commissions of this magnitude are common for small units).
4. During `calcHeadersCommissions`, for each recipient: `amount = Math.round(3 * 50/100.0) = Math.round(1.5) = 2`. [7](#0-6) 
5. Total credited to A and B: `2 + 2 = 4`, i.e., 1 more byte than the `3` actually paid by the parent unit — these 4 bytes are inserted into `headers_commission_contributions`/`headers_commission_outputs` and become independently spendable by A and B once mature, an outright 33% inflation on this single payer's commission.
6. Repeating this pattern across many units/parents lets the attacker accumulate inflated byte supply over time, entirely from posting ordinary units with a chosen (fully valid) recipient-share configuration.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
