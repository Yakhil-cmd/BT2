Confirmed: this is a real cross-tenant vulnerability, distinct from the exact framing in the question, but rooted in the same handler code.

### Title
Webhook `repository.owner.login` used only for HMAC-secret selection while handlers trust unrelated `repository.full_name` for repository resolution, allowing cross-organization `PullRequest#labels` corruption - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`) from the JSON body, but nothing ties that same field to the `repository.full_name` value later consumed by `LabelCapturingHandler#repository` and other PR handlers. In a Shipit deployment configured for multiple GitHub organizations (the documented multi-org `github:` secrets schema), an attacker who controls one organization's GitHub App/webhook secret (because they own that org and configured the App themselves) can craft a raw webhook body whose `repository.owner.login` matches their own org (so `verify_signature` passes with their own secret) but whose `repository.full_name` names a repository belonging to a different, victim organization, causing `Shipit::Repository.from_github_repo_name` to resolve to and mutate the victim's `PullRequest#labels`.

### Finding Description
The intended binding is: **the organization whose `webhook_secret` verified the request body == the organization owning the repository whose records the handler mutates**, i.e. `repository_owner (used for HMAC) == owner segment of repository.full_name (used for mutation)`.

Tracing the code:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and uses it purely to pick which `GitHubApp` config (and thus which `webhook_secret`) to verify the raw body against: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [2](#0-1) .
- `Shipit.github(organization:)` looks up per-organization config via `github_app_config(organization)` when the multi-org schema is used [3](#0-2) .
- Once the signature check passes, `LabelCapturingHandler#repository` resolves the *target* repository using a completely different field: `Shipit::Repository.from_github_repo_name(params.repository.full_name) || NullRepository.new` [4](#0-3) , and `capture_labels` calls `pull_request.update!(labels: ...)` on whatever stack/PR that resolves to [5](#0-4) .
- `Repository.from_github_repo_name` performs a strict `owner`+`name` lookup with no cross-check against the org that authenticated the request: `repo_owner, repo_name = github_repo_name.downcase.split('/'); find_by(owner: repo_owner, name: repo_name)` [6](#0-5) . So `from_github_repo_name` does correctly return `nil`/no match for a repo it can't find by owner+name — but that's not the vulnerable step. The vulnerable step is that **nothing in the controller or handler verifies that the owner segment of `repository.full_name` equals `repository_owner`/the HMAC-verifying org**.

Exploit flow (requires a multi-org Shipit deployment, i.e. `secrets.github` keyed by multiple organizations, each with its own `webhook_secret` — this is a documented, supported configuration): an attacker who owns/administers `org-attacker` and has configured (or otherwise obtained) that org's own `webhook_secret` in Shipit's multi-org config can POST directly to `/webhooks` with:
- `X-Github-Event: pull_request`
- body: `{"action":"labeled","repository":{"owner":{"login":"org-attacker"},"full_name":"org-victim/victim-repo"}, "pull_request": {...}, ...}`
- `X-Hub-Signature` computed with `org-attacker`'s `webhook_secret` over that exact raw body.

`verify_signature` selects `org-attacker`'s secret (via `repository_owner`), signature matches, request passes. `LabelCapturingHandler` then resolves `repository` via `full_name = "org-victim/victim-repo"`, unrelated to the org that authenticated, and if `org-victim/victim-repo` has an active/open review-stack PR, `capture_labels` overwrites that PR's `labels` — a write to a repository the attacker does not own and never authenticated for.

Existing guards do not prevent this: `verify_signature` only authenticates that *some* organization's secret matches the body, not that the *body's target repository* belongs to that organization [7](#0-6) ; `ExplicitParameters` only enforces types/presence of `repository.full_name`, not ownership consistency [8](#0-7) ; and `Repository.from_github_repo_name` performs an honest lookup with no notion of "requesting org" to cross-check against [6](#0-5) .

Note on the question's exact proof idea ("App A's webhook_secret but repository.full_name naming an App B-owned repo, asserting resolution goes to nil/NullRepository"): as literally stated, that specific test would in fact **pass** (no vulnerability) in the common single-organization deployment, because `verify_signature` ties the *signing* secret to `repository_owner`, and if App A's webhook_secret is used, `repository_owner` was necessarily App A's org from the same payload's `repository.owner.login` field — but `from_github_repo_name` doesn't care about that; it only depends on `full_name`. If `full_name` names a real "App B" repository that exists in the database and `repository.owner.login` was forged to say "App A" in the same request, `verify_signature` would try to verify using App A's secret, which the attacker does not have (per the rules, they hold no `webhook_secret`), so the request is rejected before reaching the handler. The genuinely exploitable variant requires the attacker to legitimately hold a webhook secret for *some* org (their own, in a multi-tenant config) and mismatch that org's login against a different `full_name` — this is the scenario proven above.

### Impact Explanation
An attacker who administers their own GitHub organization in a multi-org Shipit deployment can overwrite `Shipit::PullRequest#labels` for pull requests belonging to *any other tenant organization* configured on the same Shipit instance, purely by crafting a raw HTTP POST to `/webhooks`. This is a cross-tenant write to a resource (`PullRequest#labels`) that the attacker never authenticated for, matching the Critical criterion "a payload for one repository mutating another's stack" (labels drive archive/unarchive and provisioning decisions in `LabeledHandler`/`ReopenedHandler`, so label corruption can cascade into unintended stack archival/unarchival for the victim's review stacks). The attack is repeatable at will against any repository/PR the attacker can guess or enumerate the `full_name` of, across all tenants sharing the Shipit host.

### Likelihood Explanation
This requires the Shipit deployment to use the multi-organization `github:` secrets schema (documented, supported) with at least one organization's App/webhook secret controlled by, or leaked to, the attacker (e.g., the attacker is a legitimate onboarded tenant of a shared Shipit instance). Given that precondition, the attacker's cost is trivial: one crafted HTTP POST with a correctly computed HMAC using their own known secret. No GitHub interaction, no privileged Shipit role, no other tenant's secret is needed. Likelihood is moderate-to-high specifically for shared/multi-tenant Shipit deployments; it is not exploitable in the common single-org deployment where only one `webhook_secret` exists.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the signature, assert that the owner segment of `params.dig('repository','full_name')` matches `repository_owner` (the org whose secret verified the request) before dispatching to any handler; reject with `422` on mismatch. This restores the binding `repository_owner == full_name.split('/').first` for every webhook-driven mutation, not just label capturing.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, functional-level test consistent with existing style):
```ruby
test "cross-organization full_name is not rejected when owner login matches the signing org" do
  # Simulate multi-org config: org "attacker-org" has its own webhook_secret.
  Shipit.stubs(:github_default_organization).returns("attacker-org")
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    Shipit::GitHubApp.new("attacker-org", webhook_secret: "attacker-secret")
  )
  victim_repo = shipit_repositories(:shipit) # owner: "shopify", name: "shipit-engine"
  victim_stack = create_review_stack_with_open_pr(victim_repo)

  payload = {
    "action" => "labeled",
    "number" => victim_stack.pull_request.number,
    "repository" => {
      "owner" => { "login" => "attacker-org" },       # used to select signing secret
      "full_name" => victim_repo.github_repo_name       # "shopify/shipit-engine" - different org
    },
    "pull_request" => pull_request_payload_for(victim_stack, labels: [{ "name" => "attacker-label" }]),
    "sender" => { "login" => "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", payload)

  request.headers["X-Github-Event"] = "pull_request"
  request.headers["X-Hub-Signature"] = signature

  post :create, body: payload, as: :json

  assert_response :ok
  # BROKEN BINDING: attacker-org's secret authenticated a mutation on shopify's PR.
  assert_includes victim_stack.pull_request.reload.labels, "attacker-label"
end
```
Assertion on both sides of the equality: `repository_owner` (`"attacker-org"`, used for HMAC secret selection) is asserted to differ from the owner segment of `full_name` (`"shopify"`, used for the mutated record), while the test still observes `assert_response :ok` and the victim's `pull_request.labels` changed — demonstrating the two values are never checked against each other despite one gating authentication and the other selecting the mutation target.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
