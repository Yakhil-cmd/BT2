## Finding confirmed

The signature-verification binding and the repository-write binding use **two different fields from the same attacker-supplied JSON body**, and nothing enforces that they agree.

`Shipit::WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the request against using:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up per-organization app config from `secrets.github`, which explicitly supports multiple independent orgs each with their own `webhook_secret` (see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`) [3](#0-2) .

Once signature verification passes, event handlers (e.g. `PushHandler`) resolve the repository to act on using a **different** field, `repository.full_name`:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) [5](#0-4) 

Because the whole POST body is attacker-controlled JSON (not a real GitHub-signed structure Shipit is regenerating), an attacker who is the admin/owner of "OrgA" — and therefore legitimately knows OrgA's `webhook_secret` because they configured the Shipit-side webhook for their own org's repos — can sign a payload where `repository.owner.login = "OrgA"` (satisfies signature check against OrgA's secret) but `repository.full_name = "OrgB/victim-repo"` (a repository belonging to a different, unrelated organization also configured in the same Shipit instance). `verify_signature` only checks the HMAC against OrgA's secret and the `repository_owner` fallback value; it never checks that `repository.full_name`'s owner segment matches `repository.owner.login`. This breaks the binding: *organization whose secret authenticated the request* ≠ *organization/repository actually written to*.

## Impact

This lets an attacker with legitimate control of one configured GitHub organization inject cross-organization webhook events (`push`, `status`, `check_suite`, `pull_request`, etc.) against stacks belonging to a different organization hosted on the same Shipit instance, e.g. forcing `PushHandler` to call `stack.sync_github(expected_head_sha:)` on a victim org's stack, or injecting fake commit statuses via `StatusHandler` that could satisfy `ci.require` checks and enable an unauthorized deploy of the victim's stack.

## Caveat

I could not fully verify how far this can be escalated (e.g., whether `sync_github` alone can trigger a deploy, or whether merge-queue / status-injection paths chain into an actual unauthorized ship) within the available context, since the `Stack#sync_github` implementation and merge queue trigger conditions weren't inspected in depth. This would need to be confirmed by tracing `Stack#sync_github`, `Commit#create_status_from_github!`, and the merge-queue/deploy-trigger logic before finalizing severity — I recommend validating this end-to-end with a background Devin session rather than relying solely on this static analysis, given the multi-file trace required and the size limits on what could be indexed here.

### Title
Cross-organization webhook forgery due to mismatched organization-secret and repository-owner binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, while the event handlers that act on the payload identify the target repository using the separate `repository.full_name` field. No code path enforces that these two fields refer to the same organization.

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` supporting per-org `github` blocks, as documented in `docs/setup.md`), each organization has an independent `webhook_secret`. `verify_signature` picks the app/secret to verify against based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` [6](#0-5) . Handlers separately look up the stacks to mutate via `payload.dig('repository', 'full_name')` [4](#0-3) . Since the whole request body is attacker-supplied and unauthenticated GitHub metadata (Shipit trusts the HMAC, not any internal consistency of the JSON), an attacker can set `repository.owner.login` to an org whose secret they know, while setting `repository.full_name` to `OtherOrg/some-repo`.

### Impact Explanation
An attacker who legitimately administers one organization configured in a shared Shipit instance can forge webhook events that are processed as if they came from a different organization's repository, causing `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, or pull-request handlers to execute against stacks/commits/teams that belong to that other organization — an authorization boundary the per-org webhook secret model is meant to enforce.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one organization configured on a shared multi-org Shipit install, and for that install to host stacks from another organization the attacker wants to target. This is a realistic operator configuration per `docs/setup.md`'s own multi-org guidance.

### Recommendation
Validate that `repository.owner.login` (used to select the verifying secret) matches the owner segment of `repository.full_name` (used by handlers to resolve the target stack/repository) before dispatching to handlers, or derive both values from a single canonical field.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s, both with stacks tracked in the same instance (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an admin of `OrgA`, craft a JSON body: `{"repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"}, "ref": "refs/heads/main", "after": "<attacker sha>"}`.
3. Sign it with `HMAC-SHA1(OrgA_webhook_secret, body)` and send it as `X-Hub-Signature`, `X-Github-Event: push`.
4. `verify_signature` passes (OrgA's secret matches). `PushHandler` resolves stacks via `repository.full_name = "OrgB/victim-repo"` and calls `sync_github` on OrgB's stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)

  end
