### Title
Attacker-controlled `Status#created_at` lets a cross-repo forged status displace the legitimate CI result for the same context - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits by raw SHA (`Commit.where(sha: params.sha)`) with no scoping to the webhook's own repository/stack, and it passes the attacker-supplied `created_at` String straight through to `Status.replicate_from_github!`, which persists it verbatim as the `Status#created_at` column. Because `Commit#statuses` is ordered `created_at: :desc` and `Status::Group#initialize` deduplicates same-`context` statuses by keeping the first (i.e. most-recent-`created_at`) entry, an attacker who can get any validly-signed `status` webhook from a repository they own can inject a `Status` row with the same `context` string as the legitimate CI, backdate/forward its `created_at`, and guarantee it wins the dedup, becoming the value `Commit#status` (`Status::Group.compact`) returns.

### Finding Description
Binding claimed: `commit.status_for(context)` should equal `most_recent_status_written_by_the_stack's_authorized_CI_for(context)`, i.e. the row with `Status#stack_id == commit.stack_id` and provenance from that stack's own GitHub integration.

Actual code path:
- `app/models/shipit/webhooks/handlers/status_handler.rb:7-24` declares `accepts :created_at, String` (fully attacker-controlled, no bound/monotonicity check), and `process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This does **not** use the `Handler#stacks`/`Repository.from_github_repo_name` scoping that other handlers use — any commit anywhere in the DB whose `sha` matches is touched, regardless of which repository's webhook it came from [1](#0-0) .
- `app/models/shipit/status.rb:24-33` `replicate_from_github!` writes `created_at: github_status.created_at` directly from the attacker's string, with no validation forcing it to be ≤ `Time.current` or ≥ existing statuses [2](#0-1) .
- `app/models/shipit/commit.rb:12` `has_many :statuses, -> { order(created_at: :desc) }` — the collection is ordered purely by that attacker-writable column [3](#0-2) .
- `app/models/shipit/status/group.rb:24-32` `Group#initialize` does `statuses.to_a.uniq(&:context)` on that DESC-ordered collection, so for any given `context` string the entry with the greatest `created_at` silently wins and the legitimate one is dropped from the visible set entirely [4](#0-3) .
- `app/models/shipit/commit.rb:304-306` `Commit#status` is `Status::Group.compact(self, statuses_and_check_runs)`, which if the group collapses to one visible status (e.g. attacker reuses the sole existing context) returns that single forged `Status` object directly as the commit's authoritative status [5](#0-4)  and [6](#0-5) .

Exploit flow: attacker owns a repository under a GitHub org already configured in Shipit (so `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` passes with that org's shared webhook secret) [7](#0-6) . They obtain (or fabricate, since only signature is checked, not sha ownership) a `status` webhook whose `sha` equals a victim commit's SHA in a different stack (e.g. shared git ancestry from a fork), set `context` equal to the victim stack's real CI context (e.g. `"ci/travis"`), `state: "success"`, and `created_at` set arbitrarily in the future. `StatusHandler` finds the victim `Commit` purely by `sha` (ignoring which repo the webhook actually came from) and creates the forged `Status`, which then outranks/replaces the legitimate entry for that context due to the `created_at` ordering, so `Commit#status` returns the forged, attacker-authored result.

None of the existing guards stop this: `verify_signature` only proves the webhook came from *some* trusted org, not that it concerns the commit's actual stack/repo; `ExplicitParameters` only validates types (`String`), not value bounds on `created_at`; there is no `stacks`/`repository_name` filter inside `StatusHandler#process`.

### Impact Explanation
A successful forged/backdated (or, as here, forward-dated) status write can flip the effective CI state (`Commit#status`) of an arbitrary victim commit in any stack, for a context the attacker doesn't control, to `success`. If that context is a `required_statuses` entry, this can make `Commit#deployable?` true and enable an unauthorized deploy/merge for a repository the attacker does not own, satisfying the Critical "payload for one repository mutating another's stack/commit" and "unauthorized deploy" categories. This is repeatable against any commit whose SHA can be matched (shared fork history, cherry-picks, etc.) and against any stack reachable via that SHA.

### Likelihood Explanation
Preconditions: attacker needs (a) a repository under a GitHub org that Shipit already trusts (so `Shipit.github(organization:)` resolves and webhook signature verification succeeds), and (b) a commit SHA that also exists in the victim's stack (plausible via forks/shared history, or any commit already synced into Shipit). No Shipit session, API token, or secret is required — only the ability to trigger (or send) a `status` webhook that passes org-level signature verification. Cost is low and the attack is fully repeatable per target commit/context.

### Recommendation
Scope `StatusHandler#process` to commits belonging to stacks of the webhook's own repository (reuse `Handler#stacks`, matching by `stack_id`/`repository`) instead of a bare `Commit.where(sha:)`. Additionally, do not trust the attacker-supplied `created_at` for ordering/authoritativeness — either ignore it and use server-assigned timestamps, or validate it is monotonic/not in the future and tie dedup/ranking to `stack_id` plus insertion order rather than an attacker-controlled column.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "cross-repo status with matching context and future created_at overrides legitimate status" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  commit = shipit_commits(:first) # belongs to stack A, context 'ci/travis'
  legit = commit.statuses.create!(stack_id: commit.stack_id, state: 'failure', context: 'ci/travis', created_at: Time.current)
  commit.reload
  assert_equal legit.id, commit.status.id # binding holds before attack

  request.headers['X-Github-Event'] = 'status'
  forged_body = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/travis', # same context as legit
    'created_at' => 1.hour.from_now.iso8601,
    'repository' => { 'owner' => { 'login' => 'attacker-owned-repo-under-trusted-org' } }
  }.to_json

  post :create, body: forged_body, as: :json
  commit.reload

  refute_equal legit.id, commit.status.id
  assert_equal 'success', commit.status.state # forged entry now authoritative, binding broken
end
```
