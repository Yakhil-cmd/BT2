### Title
Cross-organization webhook signature bypass via mismatched trust fields (`repository.owner.login` vs `repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`), a field read directly out of the attacker-controlled JSON body. Every webhook `Handler`, however, resolves the actual `Repository`/`Stack` that gets mutated using a *different* field from the same body: `repository.full_name`. In a multi-organization Shipit deployment (a documented, supported configuration), these two fields are never cross-checked against each other, so a signature that is valid for organization A's secret can carry a payload whose `repository.full_name` points at organization B's repository.

### Finding Description
`Shipit.github(organization:)` looks up a per-organization config block and constructs a `GitHubApp` bound to that organization's own `webhook_secret`: [1](#0-0) 

The controller picks *which* organization's secret to verify against straight from the untrusted payload: [2](#0-1) 

`repository_owner` is only used to select the verifying secret. It is never compared to the field the handlers actually act on. Every handler resolves its target repository via `repository.full_name`: [3](#0-2) 

and this is used, e.g., by `PushHandler` to sync a Stack: [4](#0-3) 

and by every pull-request handler to locate the repository/pull request/review stack to mutate: [5](#0-4) 

The multi-organization secret schema is a first-class, documented configuration: [6](#0-5) 

**The broken binding:** `verify_signature` proves "this body was signed with the secret belonging to the organization named in `repository.owner.login`", but `process` acts on "the repository named in `repository.full_name`". Nothing forces these two attacker-supplied strings to refer to the same repository/organization. An entity that legitimately owns/administers *any one* organization configured in this Shipit instance (and therefore knows that organization's own `webhook_secret`, since they configured the GitHub App webhook for their own org) can forge a payload where:
- `repository.owner.login` = their own org (selects their own known secret for verification), and
- `repository.full_name` = `"victim-org/victim-repo"` (drives the actual database lookup/mutation).

The HMAC only proves knowledge of *some* configured secret, not that the signer controls the repository being acted upon.

### Impact Explanation
This is a cross-repository write: an attacker who administers one org onboarded to a shared Shipit instance can forge signed webhook events targeting a completely unrelated org/repository's `Stack`/`PullRequest` records — triggering GitHub sync jobs (`stack.sync_github`), archiving/unarchiving review stacks, and overwriting `pull_request.github_pull_request` state for a victim repository they have no access to. This satisfies the Critical "cross-repository writes" criterion.

### Likelihood Explanation
Requires only that the Shipit deployment use the multi-organization `github:` secrets schema (explicitly documented and supported) and that the attacker administers a GitHub App/webhook for at least one of the onboarded organizations — no Shipit session, API token, or GitHub write access to the victim repository is needed.

### Recommendation
After selecting the verifying `GitHubApp` and validating the signature, re-derive the organization strictly from the same field the handler will use (`repository.full_name`'s owner segment, or `organization.login`) and reject the request if it doesn't match the organization whose secret validated the signature; alternatively, verify the signature using a secret bound to the resolved target repository's organization rather than to the attacker-supplied `repository_owner`.

### Proof of Concept
1. Deploy Shipit with the multi-org secrets schema, onboarding `attacker-org` (secret `S_a`) and `victim-org` (secret `S_v`), both installed on the same Shipit instance.
2. Attacker crafts a `push` webhook JSON body: `{"ref": "refs/heads/master", "after": "<sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(S_a, body)` using their own known `S_a`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies since `S_a` is correct for that org.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [7](#0-6)  and enqueues a sync against the victim's actual Stack, despite the request only ever being signed with the attacker's own organization secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
