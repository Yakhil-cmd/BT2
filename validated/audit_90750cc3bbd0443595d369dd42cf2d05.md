### Title
Base AA (Autonomous Agent) Templates Can Be Triggered Directly, Bypassing Required `params` Initialization from the Parameterized Wrapper - (File: aa_composer.js)

### Summary
Obyte's "parameterized AA" feature works like a proxy/implementation pattern: a lightweight parameterized AA (`{base_aa: <address>, params: {...}}`) forwards its trigger to a "base AA" that contains the real logic, and executes it with the `params` supplied by the wrapper [1](#0-0) . Just like the `L1ERC20Bridge` implementation contract in the external report, the base AA is a fully independent, separately deployed/addressed contract that validation only requires to be "a regular AA" containing a `messages` field [2](#0-1) . Nothing in the protocol prevents an unprivileged unit poster from sending a trigger directly to the base AA's own address, in which case the AA executes with no `params` object at all, instead of the parameters the AA author intended to always be supplied by the wrapper.

### Finding Description
When a trigger is sent to a parameterized AA, `handleTrigger` detects `template.base_aa`, rejects any externally-supplied `params` (`if (params && Object.keys(params).length > 0) throw Error("unexpected params")`), then re-invokes itself against the base AA's own definition while substituting in the wrapper's fixed `template.params` [1](#0-0) . This design assumes the base AA is *only ever* reached this way, with `params` always populated by a specific wrapper's fixed configuration.

However, the base AA is registered on the DAG under its own address exactly like any other AA [3](#0-2) , and `validateAADefinition`/`aa_addresses` place no restriction preventing a trigger unit from being posted to it directly [4](#0-3) . When triggered directly (not via the base_aa redirect branch), `handleTrigger` runs the base AA's `messages`/`init` formulas with whatever `params` was passed into the top-level call (typically empty/undefined for a primary trigger), rather than the parameter set the author assumed would always exist. This is directly analogous to the `L1ERC20Bridge` bug: a contract meant to be used only through a wrapper (proxy) can be invoked directly, executing its logic while critical inputs (`l2Bridge` in the Solidity case, `params.*` here) are effectively uninitialized/zero-valued.

The `test/aa_composer.test.js` "parameterized AA" test illustrates the intended flow: the base AA's payment message computes `amount = trigger.output[[asset=base]] - params.fee` and a data message emits `params.expiry` [5](#0-4) . If this same base AA address is triggered directly, `params.fee` and `params.expiry` are absent, so the formula evaluates these property references against an undefined/empty object rather than the fee and expiry the author configured.

### Impact Explanation
AA authors writing a base AA can reasonably assume, based on how the parameterized-AA feature is documented and tested, that fields like `params.fee`, `params.min_amount`, `params.destination`, etc. are always populated by the accompanying wrapper. If a base AA's logic relies on `params` to gate spending conditions or compute fees/outputs (as in the sample test), direct triggering with no `params` bypasses those safeguards. Depending on how the specific base AA's formulas are written, this can result in:
- Payments computed without the intended fee deduction or bound checks, causing AA fund loss to the direct caller.
- State transitions or asset issuance logic executing with default/falsy substitutes for `params` values, producing outcomes the AA author never intended and cannot correct after the fact (state changes are permanent).

This matches the "AA fund loss or freezing" impact class validated for this scan.

### Likelihood Explanation
Likelihood is moderate: it requires the existence of a specific base AA whose author assumed indirect-only invocation, and it requires that AA's formulas to not explicitly guard against missing `params` (e.g. by checking `params.fee` is a number before using it). This is a bug-class risk baked into the parameterized-AA design rather than a guaranteed exploit against every base AA, mirroring Matter Labs' own assessment of the analogous Solidity issue as low-severity-but-real. Any unprivileged unit poster can trigger it by simply sending a payment/data unit directly to the base AA's address — no special privilege, key leak, or network position is required.

### Recommendation
Consider one or more of:
- Allow a base AA definition to declare that it must only be invoked via a parameterized wrapper (e.g., a flag rejecting direct triggers when the AA has ever been referenced as a `base_aa`), enforced in `aa_composer.js`'s `handleTrigger`.
- When a trigger reaches a regular AA definition directly (not via `template.base_aa` redirection) and that AA's formulas reference `params.*`, either require `params` to already be validated/non-empty or provide clear guidance so authors treat `params` access defensively.
- Document explicitly for AA authors that any AA that can serve as a `base_aa` is independently and directly triggerable by anyone, and that formulas must not assume `params` is always populated.

### Proof of Concept
1. Author deploys `base_aa` per the pattern in `test/aa_composer.test.js`'s "parameterized AA" test: a base AA whose payment output amount is `trigger.output[[asset=base]] - params.fee` [6](#0-5) .
2. Author deploys a parameterized wrapper AA `{base_aa: <base_aa_address>, params: {fee: 2000, ...}}` intending all end users to interact only with the wrapper address.
3. An unprivileged user instead posts a trigger unit directly to `base_aa_address`. In `aa_composer.js`, `handleTrigger` is invoked with `arrDefinition` equal to the base AA's own definition (no `template.base_aa` present), so the `base_aa` redirection branch at [1](#0-0)  is never entered, and `params` remains empty/undefined for the rest of execution.
4. The base AA's formulas evaluate `params.fee` against an undefined object, producing a different (unintended) output amount than the wrapper's configured fee logic — funds are paid out without the expected fee deduction, causing loss for the AA (or an inconsistent/broken invariant the author relied on `params` to maintain).
