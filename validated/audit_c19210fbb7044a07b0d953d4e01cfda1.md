### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes GitHub commit statuses to every `Commit` record whose `sha` matches the webhook payload, with no scoping to the repository that authenticated the webhook. Every other webhook handler in the engine restricts writes to the commits belonging to the `stacks` scoped by the payload's `repository.full_name`, but `StatusHandler` bypasses this pattern entirely, allowing a status delivered by an attacker-owned repository to mutate CI state on any other stack that happens to share the same commit SHA.

### Finding Description
The broken binding: for every other handler, mutation target = `stacks` (derived from `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`), as defined in the base class [1](#0-0) . `StatusHandler` instead uses mutation target = `Commit.where(sha: params.sha)` with no repository or stack filter at all: [2](#0-1) 

These two targets are not equal — `Commit.where(sha: params.sha)` can span every stack/repository in the Shipit database that has ever ingested a commit with that SHA, whereas the authenticated repository is only the one named in `payload['repository']['full_name']` and validated by `verify_signature`.

`WebhooksController#verify_signature` only proves the payload was legitimately signed for the organization named in the payload's own `repository.owner.login` / `organization.login` field [3](#0-2) . It does not, and cannot, prove that the `sha` in the payload actually belongs to that repository — it only proves that GitHub genuinely delivered this event for a repository the attacker controls (i.e., their own repo, if the GitHub App/webhook is installed there).

Since git commit SHAs are content-addressed, an attacker can trivially cause a genuine SHA collision with a victim's stack: fork the victim's repository, keep an unmodified upstream commit (identical SHA is guaranteed by git's content-addressing across the fork and upstream), then set a `status` on that SHA in their own fork via the GitHub API (any repo owner can create statuses on their own repo). GitHub delivers this event, correctly HMAC-signed, to the Shipit webhooks endpoint. `verify_signature` passes because the event is genuinely for the attacker's own repo/org. `StatusHandler#process` then finds and mutates any `Commit` row anywhere in the Shipit database with that SHA — including the victim stack's commit row — via `commit.create_status_from_github!(params)`, which calls `add_status` and can flip `previous_status.simple_state != new_status.simple_state`, triggering `stack.schedule_merges` and downstream `ContinuousDeliveryJob`/auto-merge logic [4](#0-3) [5](#0-4) .

None of the listed guards prevent this: `verify_signature` authenticates the org/repo of the *sender*, not the SHA's true owner; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; there is no `require_permission!`/`stacks`-scope check in `StatusHandler` unlike other handlers that use the base class's `stacks` helper.

### Impact Explanation
An attacker who owns any repository with the Shipit GitHub App/webhook installed can, by sharing a commit SHA with a victim stack (e.g., via forking without rebasing), forge CI status transitions on the victim's stack that they do not own and did not authenticate. Because `add_status` triggers `stack.schedule_merges` when status becomes `success`, and continuous delivery (`schedule_continuous_delivery`) is gated on `deployable?`/`stack.continuous_deployment?`, this can cause an unauthorized deploy or merge to proceed on the victim stack using attacker-influenced CI state, with the deploy running under whatever identity (including a configured bot/`Shipit.user`) the victim stack uses. This is a write to a repository/stack record that the attacker's webhook never authenticated for, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy."

### Likelihood Explanation
Preconditions: the attacker needs a repository with Shipit's GitHub App/webhook installed (commonly self-serve for any GitHub org/repo depending on deployment), and a commit SHA shared with the victim stack (trivially achievable by forking a victim's public repo and not modifying the shared commits, or otherwise causing a genuine content-address collision). No Shipit credentials, session, or API token are required — only the ability to trigger a real GitHub `status` event on a repo the attacker controls. This is realistic and repeatable against any stack that happens to share commit history with a repository where the attacker can install the app or trigger webhooks.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the base `Handler#stacks` pattern used elsewhere, e.g. restrict the query to `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently join `Commit` through `Stack`/`Repository` derived from `payload.dig('repository','full_name')`) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (under `test/`, no live GitHub required):
1. Create `repo_a` (attacker-controlled, full_name `attacker/repo`) and `repo_b` (victim stack, full_name `victim/repo`), each with their own `Stack`.
2. Create a `Commit` with SHA `"a" * 40` under `repo_b`'s stack, with `stack.required_statuses` including `shipit/checks`, and set it as the pending "next" commit for auto-merge (`stack.continuous_deployment?` true, `ignore_ci?` false).
3. Create a `Commit` with the SAME SHA `"a" * 40` under `repo_a`'s stack (simulating the shared fork history).
4. POST to `/webhooks` with `X-Github-Event: status`, `repository.full_name` = `attacker/repo`, `sha` = `"a" * 40`, `context` = `shipit/checks`, `state` = `success`, with a valid signature computed using `repo_a`'s (attacker-controlled) org secret.
5. Assert: **before** — `repo_b`'s commit status for `shipit/checks` is `pending`/absent and `stack_b.commits.last.deployable?` is `false`.
6. Assert: **after** processing — `repo_b`'s commit now has a `success` status for `shipit/checks` and `deployable?` returns `true` (or `stack.schedule_merges` was invoked for `repo_b`'s stack), proving the equality "status only affects the repository that authenticated it" is violated (`repo_a`'s webhook mutated `repo_b`'s commit).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
