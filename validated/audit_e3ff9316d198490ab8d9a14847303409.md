This confirms the core mismatch: `Handler#stacks` resolves the target `Stack` using `payload.dig('repository', 'full_name')` while `WebhooksController#verify_signature` selects which GitHub App/secret to verify against using `payload.dig('repository', 'owner', 'login')` (or `organization.login`). Let me confirm `Shipit.github` resolution logic and confirm there's no cross-check binding these two fields together.### Title
Webhook signature verification is keyed to a payload-controlled organization field that is decoupled from the repository field used to dispatch actions - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC against using a value taken from the same untrusted request body it is about to authenticate (`repository.owner.login`, falling back to `organization.login`), while the actual event handlers resolve the target `Stack`/`Repository` to act on using a *different* field of that same body: `repository.full_name`. In a multi-organization Shipit deployment (`config/secrets.yml` keyed per GitHub org), these two fields are never checked for consistency.

### Finding Description
`verify_signature` computes the "authenticating" identity like this: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is passed to `Shipit.github(organization: repository_owner)`, which — for multi-org configs — looks up a distinct `webhook_secret` per organization key in `secrets.github`: [3](#0-2) 

The signature itself is only verified against the raw request body as a whole using that org's `webhook_secret`, via `GitHubApp#verify_webhook_signature`: [4](#0-3) 

Once verification succeeds, the whole JSON body — including the (also attacker-controlled) `repository.full_name` field — is dispatched to the registered handlers: [5](#0-4) 

Handlers then resolve which `Stack`/`Repository` to mutate purely from `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used earlier for signature selection: [6](#0-5) [7](#0-6) 

The binding that should hold is: **organization authenticated (secret selected by `repository.owner.login`) == organization whose repository is acted upon (`repository.full_name`'s owner segment)**. Nothing in `WebhooksController` or `Handler` enforces this equality — the two lookups walk different, independently attacker-supplied JSON paths of the same unsigned-until-verified body.

In a legitimate multi-org setup, an operator who controls a GitHub organization "OrgB" onboarded to this Shipit instance knows OrgB's `webhook_secret` (it is set by that org's own GitHub App admin, per `docs/setup.md`). That operator can craft an arbitrary JSON payload, set `organization.login`/`repository.owner.login` to `OrgB` (so `Shipit.github(organization: "OrgB")` picks their known secret and the HMAC check passes) while setting `repository.full_name` to `"OrgA/some-repo"` — a completely unrelated organization/repository also hosted on the same Shipit instance whose secret they do not know. The forged, correctly-signed-with-OrgB's-secret request is then processed as if it targeted OrgA's stack.

### Impact Explanation
Depending on which webhook handler is triggered, this cross-organization confusion can drive unauthorized state changes on a `Stack` the attacker does not control, e.g. queuing a `GithubSyncJob` for a victim stack, creating fabricated commit `Status`es (`ci.require` results consumed for deploy gating), or acting on `check_suite`/`pull_request`/`membership` events (the latter can create arbitrary `Team`/`User` records, as shown by `test/controllers/webhooks_controller_test.rb:129-148`). This maps to "escalation into `Shipit.github_teams` authorization" and potentially "unauthorized deploy" (High), since fabricated CI status/commit-status webhooks can satisfy deploy safety checks (`ci.require`) for a stack the attacker was never granted access to.

### Likelihood Explanation
This requires the attacker to have legitimate control of at least one GitHub organization/App already configured in this Shipit instance's multi-org `secrets.yml` (so they know that org's `webhook_secret`), and for the deployment to actually host stacks from multiple organizations. This is a real, supported configuration (`docs/setup.md`, "Using Multiple Github Applications" in README) but is a non-default setup, so likelihood is moderate — plausible in any shared/multi-tenant Shipit instance but not present in single-org deployments.

### Recommendation
- Short term: after `verify_signature` succeeds, re-derive `repository_owner` from the verified organization and require that `params.dig('repository','full_name')`'s owner segment (or `Repository.from_github_repo_name` result's `owner`) matches the organization whose secret validated the signature; reject (422) on mismatch.
- Long term: bind webhook secrets to `Repository`/`Stack` records at the data layer (not solely by an org string parsed out of the unverified payload) and add regression tests asserting that a payload signed with org A's secret cannot mutate a stack belonging to org B.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
