The Sudoswap issue you referenced — trusting an ERC20 `transfer()`'s return value/success without verifying the *actual* balance delta — has a direct, wired-in analog in this codebase's new **ERC20 Asset Transactor**, used by `pallet-xcm`/the XCM executor on Asset Hub Westend.

### Title
Missing balance-delta verification in `ERC20Transactor` allows ERC20 transfer-amount mismatches to desync XCM holding accounting from real token balances - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens by calling the token contract's `transfer()` via `pallet_revive::Pallet::<T>::bare_call` and treat the call as fully successful whenever it does not revert and the ABI-decoded boolean return is `true`. Neither function checks that the ERC20 contract's balance actually changed by the requested `amount` before crediting/debiting the XCM `AssetsInHolding` register with that exact nominal `amount`. This is architecturally identical to the LSSVMPairERC20 bug: trusting a token's self-reported success instead of measuring the real balance delta.

### Finding Description
`ERC20Transactor` is registered as a `TransactAsset` in the production `AssetTransactors` tuple for Asset Hub Westend: [1](#0-0) 

`withdraw_asset_with_surplus` transfers `amount` from the user to `TransfersCheckingAccount` via `IERC20::transferCall`, and unconditionally mints `AssetsInHolding` credit of the *requested* `amount` as soon as the call doesn't revert and decodes to `true`: [2](#0-1) 

`deposit_asset_with_surplus` mirrors this on the way out, transferring from the checking account to the beneficiary and again trusting the boolean return rather than measuring the checking account's actual balance change: [3](#0-2) 

Contrast this with `fungibles_adapter.rs`'s native-asset transactor, which relies on `fungibles::Mutate`/`Balanced` primitives that enforce exact balance accounting rather than trusting an external contract's self-reported result: [4](#0-3) 

The `TransfersCheckingAccount` is a single, shared account across *all* users and *all* ERC20 contracts wired through this transactor: [5](#0-4) 

Because the accounting is nominal (trusting `amount`) rather than measured (checking real balance deltas), any ERC20 contract that doesn't move exactly `amount` tokens on `transfer()` while still returning `true` — e.g. fee-on-transfer tokens, rebasing tokens, or tokens with rounding/dust behavior, all commonly seen non-standard ERC20 patterns (as cited in the original Qubit-Finance-style report) — causes the XCM holding register's recorded amount to diverge from the real balance of the shared checking account. Since the checking account is shared, a discrepancy introduced by one user's non-standard token interaction can affect the checking account's real balance available for subsequent, unrelated users' deposits of that same contract, or cause deposits to revert/fail after the holding register already believes the withdrawal succeeded (funds get trapped by `AssetTrap`).

### Impact Explanation
This breaks the invariant that XCM's `AssetsInHolding` register must reflect real, verified token custody. With a non-standard ERC20 token registered via `AccountKey20` locations and routed through this transactor:
- Assets can become trapped (lost to the depositor) when the nominal nofollowup deposit amount can't be satisfied by the real checking-account balance.
- The shared `TransfersCheckingAccount` can end up under- or over-collateralized relative to what the holding register believes it holds, impacting other users' subsequent transfers of the same ERC20 asset.

This matches the same risk class Spearbit flagged as Medium for Sudoswap: silent divergence between assumed and real token movement due to trusting a `transfer()` success signal alone.

### Likelihood Explanation
The path is reachable by any signed user who can submit `pallet_xcm::execute`/XCM messages that reference an `AccountKey20` location matching an ERC20 contract on `pallet-revive`, as demonstrated by the existing test `withdraw_and_deposit_erc20s`: [6](#0-5) 

No privileged role or governance action is required — a user only needs a token contract exhibiting non-standard `transfer()` semantics (fee-on-transfer/rounding), which is common among real-world ERC20 tokens, not just intentionally malicious ones.

### Recommendation
Follow the same recommendation Spearbit gave Sudoswap: measure the actual balance change of the relevant account (checking account on deposit, sender/checking account on withdraw) via `balanceOf()` calls before and after the `transfer()` call, and use the *measured* delta — not the nominal `amount` — when constructing/consuming `AssetsInHolding` credits in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`.

### Proof of Concept
No independent Rust integration test was executed by this analysis; findings are based on direct code review of the wired-in production path. A minimal reproduction path, following the existing `withdraw_and_deposit_erc20s` test harness at `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1871-1936`, would deploy a fee-on-transfer or otherwise non-standard ERC20 contract (returning `true` from `transfer()` while moving a different amount than requested) in place of `MyToken`, execute the same `withdraw_asset`/`deposit_asset` XCM program, and assert that the `AssetsInHolding` amount credited by `withdraw_asset_with_surplus` and consumed by `deposit_asset_with_surplus` diverges from the real ERC20 `balanceOf` delta of `ERC20TransfersCheckingAccount`. This was not executed as part of this review; a background engineering session would be needed to build and run this concrete integration test against the cited functions.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
}
