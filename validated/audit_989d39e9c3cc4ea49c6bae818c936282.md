## Analog Found

### Title
DOS of ratio-based Autonomous Agents (e.g. Uniswap-like market maker) via balance-manipulation front-running of `balance[...]` reads - (File: `test/samples/uniswap_like_market_maker.oscript`, engine support in `aa_composer.js` / `formula/evaluation.js`)

### Summary
The Obyte AA (Autonomous Agent) reference implementation bundled with `ocore` includes a "Uniswap-like market maker" AA that computes exchange ratios directly from the AA's *live* on-chain balance (`balance[asset]`, `balance[base]`), the same way the reported Solidity `AccountingManager` computed `neededAssetsForWithdraw()` from `baseToken.balanceOf(address(this))`. Because any unprivileged user can post a unit that sends funds to the AA's address before a specific trigger is processed, an attacker can shift the AA's balance and make a pending, in-flight investor trigger's exact-match check fail, causing the AA to `bounce()` the payment. This is architecturally identical to the reported DoS: reliance on a spendable balance that any third party can alter, combined with a strict equality/threshold check that reverts (bounces) instead of gracefully accommodating deviations.

### Finding Description
The `balance` formula opcode is evaluated by reading the current confirmed+pending balance of the AA address, either from `objValidationState.assocBalances` (already-updated state) or from `aa_balances` table: [1](#0-0) 

Any unprivileged party can affect this balance simply by sending a payment unit to the AA's address — the same way `neededAssetsForWithdraw()` in the Solidity report used `baseToken.balanceOf(address(this))`, which any account can inflate with a plain `transfer`.

The bundled reference AA `uniswap_like_market_maker.oscript` uses this balance directly to gate an investor's deposit: [2](#0-1) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
...
$current_ratio = $asset_balance / $bytes_balance;
$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
if ($expected_asset_amount != trigger.output[[asset=$asset]])
    bounce('wrong ratio of amounts, expected ' || $expected_asset_amount || ' of asset');
```

An investor composes a trigger unit off-chain using the AA's balance *at the time of composition* to compute the exact asset amount to send along with bytes, exactly as the Noya `emergencyManager`/withdrawer would compute `withdrawAmount` from `neededAssetsForWithdraw()`. Before this trigger unit stabilizes and is executed, AA triggers are processed strictly in deterministic MCI/level order: [3](#0-2) 

Because units propagate through the network and become visible before they are stable/executed (an on-DAG analog of a public mempool), an attacker who observes the pending investor unit can broadcast a small competing payment to the same AA address, engineered (via parent selection/fee/witness timing) to be included and stabilize with an earlier `(mci, level, unit)` ordering. This changes `balance[$asset]`/`balance[base]` seen by `handleTrigger`/`updateInitialAABalances` when the victim's trigger is finally executed: [4](#0-3) 

causing `$current_ratio` and therefore `$expected_asset_amount` to differ from what the investor pre-computed, triggering `bounce(...)`, which reverts all state changes and refunds bytes minus the bounce fee via the `revert`/`bounce` machinery: [5](#0-4) 

This mirrors the reported bug's mechanics precisely: a public, freely-manipulable "balance" read is used for a strict equality/threshold gate whose failure path is a full revert rather than a tolerant fallback.

### Impact Explanation
An attacker can repeatedly and cheaply (cost of a minimal payment plus network fee) DOS legitimate investors/divestors of any AA that follows this exact-match balance-ratio pattern — a pattern that is the *official example* shipped with `ocore` and is representative of real "bonding curve" / AMM-style AAs deployed on the Obyte network. Every such deposit attempt bounces, refunding the investor minus the bounce fee, so victims lose the bounce fee on every failed attempt and can be permanently prevented from investing while the attacker keeps front-running. This is a fund-griefing/availability impact reachable by any unprivileged AA trigger sender.

### Likelihood Explanation
Likelihood is proportional to how close the attacker's added balance needs to be to flip the ratio check — the smaller the deposit needed, the cheaper and more repeatable the attack, exactly as noted in the original report ("the amount that the attacker transfers need not be much"). Any observer of the DAG can see an investor's pending trigger unit before it stabilizes and race a minimal competing payment to the AA address; this requires no special privilege, matching the "AA trigger sender" reachable class allowed by the rules.

### Recommendation
- AA authors should avoid gating on an exact/strict equality between a caller-supplied amount and a value derived from the AA's *external* mutable balance; instead, compute amounts entirely from internal state (`var[...]`) not affected by unsolicited transfers, or clamp/refund the difference rather than bouncing.
- Consider documented guidance (and update the reference `uniswap_like_market_maker.oscript` sample) to snapshot balances via an intermediate state variable updated only by the AA's own logic, or to accept any received amount and compute the appropriate share/refund instead of reverting on mismatch.
- More generally, AA developers relying on `balance[...]` for price/ratio calculations should treat it as adversarially controllable within the same trigger-processing window, similar to how DeFi contracts must treat `token.balanceOf(address(this))` as spoofable via direct transfers.

### Proof of Concept
1. Investor A computes `$expected_asset_amount` off-chain using the AA's current `balance[$asset]`/`balance[base]`, then broadcasts a trigger unit sending exactly the matching amounts to the market-maker AA (`test/samples/uniswap_like_market_maker.oscript`, "invest in MM" case).
2. Before A's unit stabilizes, attacker B observes it in the DAG and broadcasts a payment unit sending funds (base or the traded asset) to the same AA address, engineered to stabilize with an earlier `(mci, level, unit)` per the deterministic ordering in `main_chain.js` (`handleAATriggers`, lines 1691-1706).
3. When A's trigger is finally processed, `updateInitialAABalances` (`aa_composer.js` lines 474-490) and the `balance[...]` opcode (`formula/evaluation.js` lines 1510-1528) reflect B's added funds, changing `$asset_balance`/`$bytes_balance` and thus `$current_ratio`/`$expected_asset_amount`.
4. `$expected_asset_amount != trigger.output[[asset=$asset]]` becomes true, the AA calls `bounce('wrong ratio of amounts...')`, and A's deposit is refunded minus the bounce fee (`aa_composer.js` `revert`/`bounce`, lines 1759-1783).
5. B repeats this for every subsequent investor attempt at negligible cost, achieving a persistent DOS on deposits.
