### Title
Webhook organization authentication is never bound to the repository/commit the handlers act on, enabling cross-tenant forgery of commit statuses and stack events - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check against using an organization name that is itself read out of the untrusted JSON payload, but none of the event handlers verify that this same organization actually owns the repository/commit they subsequently mutate. In a multi-tenant Shipit deployment (the officially documented "Using Multiple GitHub Applications" mode), any tenant that legitimately knows their own organization's webhook secret can forge a payload whose `repository.owner.login`/`organization.login` matches their own org (so the signature check passes) while embedding a `repository.full_name` or a bare commit `sha` belonging to a *different* tenant's stack. `StatusHandler` is the worst case: it doesn't scope by repository at all.

### Finding Description
`WebhooksController#verify_signature` picks which `GitHubApp`/secret to validate against based on a value taken straight from the unauthenticated payload: [1](#0-0) [2](#0-1) [3](#0-2) 

In multi-org installations, `Shipit.github(organization:)` resolves a *different* secret per organization key: [4](#0-3) 

So the HMAC check only proves "the sender knows the webhook secret configured for the organization named in this payload" - it says nothing about which repository/commit the rest of the payload references. Downstream handlers never re-validate that binding.

`StatusHandler` looks up the target commit purely by SHA, with **no repository scoping whatsoever**: [5](#0-4) 

Other handlers (e.g. `PushHandler`, `CheckSuiteHandler`) do scope to a repository, but only via the `repository.full_name` field taken from the same untrusted payload, through `Handler#stacks`/`#repository_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

`repository.full_name` and `repository.owner.login` (used for the signature-organization lookup) are independent fields inside the same JSON body; nothing forces them to be consistent. The equality that must hold and is never checked is:

`organization_whose_secret_authenticated_the_request == organization_that_owns_the_repository/commit_the_handler_mutates`

Before the attacker's request: for a legitimate webhook, both fields always agree because GitHub itself populates them from the real event's repository. After the attacker's crafted request: `repository.owner.login`/`organization.login` = attacker's own tenant (whose secret they legitimately know), while `repository.full_name` (or, for `status` events, just the raw `sha`) references a victim tenant's stack/commit. The signature check succeeds and the handler writes state for the victim tenant.

### Impact Explanation
- `StatusHandler#process` will attach an attacker-chosen `state`/`context`/`description` to **any** commit in the database matching an attacker-supplied SHA, regardless of which stack/repository/organization it belongs to. Since `Commit#deployable?` and `Status::Group` treat these statuses as authoritative CI results (`ci.require` contexts), an attacker can falsely mark a victim's commit as CI-`success`, satisfying `commit.deployable?` and enabling an unauthorized deploy of that commit on the victim's stack (directly, or via `continuous_deployment`).
- `PushHandler`/`CheckSuiteHandler`/PR handlers can be made to run `sync_github`, `schedule_refresh_check_runs!`, archive/unarchive review stacks, etc. against a victim tenant's stack that the attacker's own webhook secret was never meant to authorize.
- This is a cross-tenant integrity break exploitable by any organization onboarded onto a shared, multi-org Shipit instance - it requires no `ApiClient` token, no session, and no GitHub write access to the victim repository, satisfying the "unauthorized deploy" high-impact bar.

### Likelihood Explanation
Requires Shipit to be configured with the documented multi-organization GitHub App schema (`docs/setup.md` "Using Multiple Github Applications", exercised by `test/dummy/config/secrets_double_github_app.yml`) so that distinct, attacker-knowable webhook secrets exist per tenant. Any tenant onboarded to such a shared instance can mount the attack purely by POSTing a crafted, correctly-signed webhook body - no additional privilege escalation is needed, making likelihood medium-to-high in that (officially supported) deployment mode.

### Recommendation
After signature verification, re-derive the organization/repository from the payload used by `verify_signature` and assert it matches the repository the handler is about to act on (e.g., compare `repository.owner.login` against the owner segment of `repository.full_name`, and reject if they differ). For `StatusHandler`, scope the `Commit` lookup by the webhook's own repository (via `Handler#stacks`) instead of a bare global `sha` lookup across all stacks.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (e.g., `OrgOne` and `OrgTwo`, per `test/dummy/config/secrets_double_github_app.yml`), each with its own `webhook_secret`.
2. As the legitimate administrator of `OrgOne` (who therefore knows `OrgOne`'s `webhook_secret`), build a `status` event payload:
```json
{
  "sha": "<sha of a commit belonging to OrgTwo's tracked stack>",
  "state": "success",
  "context": "ci/required-context",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgOne/some-repo" }
}
```
3. Sign the raw body with `OrgOne`'s webhook secret and set `X-Hub-Signature`, `X-Github-Event: status`.
4. POST to `/webhooks`. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgOne"`, validates successfully against `OrgOne`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` and creates a `success` status on the matched commit even though it belongs to `OrgTwo`, marking it as CI-passing and potentially unlocking an unauthorized deploy on `OrgTwo`'s stack.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
