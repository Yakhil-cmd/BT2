### Title
Permanent Pairing Secret Reused as a Bearer "API Key" Is Disclosed to Untrusted Third Parties via Arbiter Contract Flow, Enabling Device‑Pairing Authentication Bypass - (File: `arbiter_contract.js`, `device.js`)

### Summary
`ocore`'s device‑pairing mechanism treats knowledge of a device's **permanent `pairing_secret`** as sufficient proof of authorization to become a fully‑trusted "correspondent device" of a wallet — functionally equivalent to a personal API key that grants the holder the ability to exchange `sign`, `new_wallet_address`, and other high‑privilege messages with that wallet. The `arbiter_contract.js` module embeds this same permanent secret (`my_pairing_code`) into dispute/appeal/cosigner-sharing payloads and transmits it to arbiters, arbstore HTTP servers, and cosigners — parties that are not already paired correspondents and that only need to be reachable by an unprivileged private-payment counterparty. Anyone who obtains this leaked secret (an arbiter, arbstore operator, or malicious cosigner) can replay it to `handlePairingMessage` and pair as a permanently trusted device of the victim, mirroring the RAGFlow flaw where a single derivable/reusable token intended for a lower-trust channel could be used to obtain full account control.

### Finding Description
`device.getOrGeneratePermanentPairingInfo` generates (or reuses) a single **permanent** `pairing_secret` per wallet, stored with `is_permanent=1` and an expiry of `'2038-01-01'`: [1](#0-0) 

This permanent secret is presented as `pairing_secret` in `handlePairingMessage`. Presenting a *valid, unexpired* `pairing_secret` — permanent or not — is the **only** check performed before a sender is unconditionally added as a fully confirmed correspondent device: [2](#0-1) 

Once `is_confirmed=1`, that correspondent device is treated as fully trusted: it can request signatures (`wallet.js` `case "sign"`), receive `wallet_fully_approved` / textcoin claim notices, and exchange arbitrary encrypted device messages indefinitely (the permanent secret is never rotated or expired, unlike one‑time pairing secrets which are deleted after use).

`arbiter_contract.js` treats this **same permanent secret** as an ordinary application field and repeatedly discloses it outside the pairing context to parties who are not yet correspondents:
- On contract creation, it is embedded in the contract row and sent to the peer: `createAndSend` (`objContract.my_pairing_code = pairingInfo.device_pubkey + "@" + pairingInfo.hub + "#" + pairingInfo.pairing_secret;`) — [3](#0-2) 
- On dispute submission it is sent via plaintext JSON body over HTTPS to the **arbstore** server, an operator not necessarily already paired with the wallet owner: [4](#0-3) 
- On appeal it is sent again to the arbstore: [5](#0-4) 
- It is also persisted/shared with contract cosigners via `store`/`shareContractToCosigners` (`my_pairing_code` column in `wallet_arbiter_contracts`): [6](#0-5) 

Because the pairing secret is **permanent** and reused across all these channels (instead of a fresh, single-use secret being minted for each context), any of these unprivileged recipients — the arbiter, the arbstore operator, or a cosigner on a shared multi-sig contract — can extract it and later present it to the wallet owner's home hub to pair as a full correspondent device, exactly like the RAGFlow flaw where a low-trust, publicly reachable channel (the shared assistant URL) let a viewer derive/replay a high-trust secret (the personal API key) to gain full account control.

### Impact Explanation
An attacker (arbiter, arbstore server operator, or malicious cosigner in a shared-address arbiter contract) who merely receives a normal dispute/appeal submission or cosigner share obtains the victim's permanent pairing secret. They can then pair as a trusted device correspondent and:
- Send `sign` requests for attacker-crafted units to the victim's wallet UI, potentially tricking the user (already-trusted UX) into co-signing malicious payments from shared/multisig addresses — leading to unauthorized spending.
- Receive/exchange sensitive wallet protocol messages (`text`, `object`, contact/xpubkey exchange) as a long-lived trusted peer, since the permanent secret never expires or rotates.
This exceeds the wallet owner's/AA counterparty's expectation that only a device they explicitly consented to pair with is trusted, and can result in fund loss through social-engineered signing or leakage of private-payment metadata to an unauthorized party.

### Likelihood Explanation
Any counterparty who legitimately participates in an arbiter contract flow — as the arbiter, an arbstore host, or a contract cosigner — automatically receives the `my_pairing_code` field as part of normal protocol data with no additional privilege required. No cryptographic attack is needed; the secret is handed over in cleartext as ordinary business data. The only prerequisite is that the victim initiates or accepts an arbiter contract, dispute, or appeal, or shares a contract with cosigners, which is standard usage of `arbiter_contract.js`.

### Recommendation
- Never reuse the permanent, long-lived pairing secret as an item of business data. Generate a fresh, single-use, short-expiry pairing secret (via `startWaitingForPairing`) specifically for each arbiter-contract exchange context (peer, arbstore, cosigners) instead of `getOrGeneratePermanentPairingInfo`.
- Scope any device-pairing performed through a leaked/shared `my_pairing_code` to a restricted trust tier (e.g., unable to originate `sign` requests) rather than full correspondent trust.
- Rotate/invalidate the permanent pairing secret if it is ever found to have been transmitted to a third-party HTTP endpoint (arbstore) or persisted in a shareable database row.

### Proof of Concept
1. Alice creates an arbiter contract with Bob, choosing arbiter Mallory: `createAndSend` embeds Alice's permanent `my_pairing_code` in the contract and stores/sends it (`arbiter_contract.js:21-35`).
2. The contract proceeds to a dispute: Alice calls `openDispute`, which POSTs `my_pairing_code: objContract.my_pairing_code` to the arbstore server controlled by/reachable to Mallory (`arbiter_contract.js:275-296`).
3. Mallory parses the `device_pubkey@hub#pairing_secret` string and sends a `pairing` device message directly to Alice's hub using that `pairing_secret` (`device.js:758-763`, `798-848`).
4. Because the secret is valid and unexpired (`is_permanent=1`, expiring 2038), `handlePairingMessage` unconditionally inserts Mallory's device as a confirmed correspondent of Alice's wallet (`device.js:816-846`).
5. Mallory, now a trusted correspondent, sends a crafted `sign` request (`wallet.js` case `"sign"`) hoping Alice's wallet UI prompts her to approve a malicious payment, or otherwise abuses the ongoing trusted channel.

function handlePairingMessage(json, device_pubkey, callbacks){
	var body = json.body;
	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");
	if (!ValidationUtils.isNonemptyString(json.device_hub)) // home hub of the sender
		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))
		return callbacks.ifError("invalid device_hub URL");
	if (!ValidationUtils.isNonemptyString(body.device_name))
		return callbacks.ifError("no device_name when pairing");
	if (body.device_name.length > 100)
		return callbacks.ifError("device_name too long");
	if ("reverse_pairing_secret" in body && !ValidationUtils.isNonemptyString(body.reverse_pairing_secret))
		return callbacks.ifError("bad reverse pairing secret");
	eventBus.emit("pairing_attempt", from_address, body.pairing_secret);
	db.query(
		"SELECT is_permanent FROM pairing_secrets WHERE pairing_secret IN(?,'*') AND expiry_date>"+db.getNow()+" ORDER BY (pairing_secret=?) DESC LIMIT 1", 
		[body.pairing_secret, body.pairing_secret], 
		function(pairing_rows){
			if (pairing_rows.length === 0)
				return callbacks.ifError("pairing secret not found or expired");
			// add new correspondent and delete pending pairing
			var safe_device_name = body.device_name.replace(/<[^>]*>?/g, '');
			db.query(
				"INSERT "+db.getIgnore()+" INTO correspondent_devices (device_address, pubkey, hub, name, is_confirmed) VALUES (?,?,?,?,1)", 
				[from_address, device_pubkey, json.device_hub, safe_device_name],
				function(){
					db.query( // don't update name if already confirmed
						"UPDATE correspondent_devices SET is_confirmed=1, name=? WHERE device_address=? AND is_confirmed=0", 
						[safe_device_name, from_address],
						function(){
							db.query("UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?", [from_address], function(){
								eventBus.emit("paired", from_address, body.pairing_secret);
								if (pairing_rows[0].is_permanent === 0){ // multiple peers can pair through permanent secret
									db.query("DELETE FROM pairing_secrets WHERE pairing_secret=?", [body.pairing_secret], function(){});
									eventBus.emit('paired_by_secret-'+body.pairing_secret, from_address);
								}
								if (body.reverse_pairing_secret)
									sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null);
								callbacks.ifOk();
							});
						}
					);
				}
			);
		}
	);
}

function store(objContract, bFromCosigner, cb) { // contracts shared by cosigners are trusted to reflect their true status
	const me_is_cosigner = bFromCosigner ? 1 : 0;
	const status = bFromCosigner ? (objContract.status || status_PENDING) : status_PENDING;
	var fields = "(hash, peer_address, peer_device_address, my_address, arbiter_address, me_is_payer, my_party_name, peer_party_name, amount, asset, is_incoming, creation_date, ttl, status, title, text, peer_pairing_code, peer_contact_info, my_pairing_code, my_contact_info, me_is_cosigner";
	var placeholders = "(?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?";
	var values = [objContract.hash, objContract.peer_address, objContract.peer_device_address, objContract.my_address, objContract.arbiter_address, objContract.me_is_payer ? 1 : 0, objContract.my_party_name, objContract.peer_party_name, objContract.amount, objContract.asset, 1, objContract.creation_date, objContract.ttl, status, objContract.title, objContract.text, objContract.peer_pairing_code, objContract.peer_contact_info, objContract.my_pairing_code, objContract.my_contact_info, me_is_cosigner];
	if (bFromCosigner) {
		if (objContract.shared_address) {
			fields += ", shared_address";
			placeholders += ", ?";

		}
		if (objContract.unit) {

			placeholders += ", ?";

	placeholders += ")";
	db.query("INSERT "+db.getIgnore()+" INTO wallet_arbiter_contracts "+fields+" VALUES "+placeholders, values, function(res) {
		if (cb) {

		}
	});
}
