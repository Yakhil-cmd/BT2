### Title
Unbounded dust-account creation fills ledger state with permanent entries no one can cheaply remove — (File: contracts/controller/src/positions/supply.rs)

### Summary
The Discourse CVE class — an unprivileged request that forces the server to write unbounded durable data at near-zero cost — maps directly onto `controller.supply` with `account_id == 0`. Any caller can create a brand-new lending account with a deposit of a single stroop-like unit. Each account mints a position NFT and writes a fixed set of persistent ledger entries that only the owner can ever delete, and that the protocol's own keeper must renew forever. There is no minimum-deposit floor, no per-caller account cap, and no way for anyone but the spammer to reclaim the entries.

### Finding Description
`process_supply` accepts `account_id == 0` as the "create account" sentinel and routes through `account::load_or_create_account` with `AccountGuard::Supply`, which mints an NFT and initializes account state. `payments::aggregate_positive_payments` only requires each amount to be strictly positive — a `1i128` raw unit is accepted. [1](#0-0) 

The README confirms `supply` with `account_id` 0 creates a new account owned by the caller, and that an account's spoke binding is permanent. [2](#0-1) 

Each account writes persistent state on both contracts:

- Controller: `AccountMeta`, `SupplyPositions` map, `Delegates` map.
- Position-NFT: `Owner(token_id)`, holder `Balance`, and OpenZeppelin `Enumerable` owner/global index entries. Ids are sequential and never reused — burning does not shrink the id space. [3](#0-2) 

Deletion is owner-only: `remove_account_and_burn_nft` runs on full withdrawal/cleanup paths the attacker simply never invokes, so the entries persist. [4](#0-3) 

The existing harness test proves the primitive: one actor minted 64 distinct persistent accounts with 1-unit deposits each — `poc_single_actor_spams_unbounded_dust_accounts`. [5](#0-4) 

The keeper renews all account state discovered via a scan of the NFT counter, so every spammed account becomes a recurring renewal cost line item for the protocol indefinitely. [6](#0-5) 

### Impact Explanation
This is the on-chain equivalent of filling the log disk: one unprivileged address converts a cheap, repeatable transaction into permanent ledger state and an unbounded, recurring renewal obligation borne by the protocol's keeper. Concretely:

- Permanent ledger bloat: ~6+ persistent entries per spammed account across two contracts, removable only by the attacker.
- Recurring cost drain: the keeper's per-user and account renewal groups scale linearly with spammed accounts; renewal fees are paid by the keeper/operator, not the attacker. A sufficiently large spam campaign makes the keeper's renewal transactions exceed per-transaction footprint limits and drains its funding — the "contract unable to operate from lack of token funds" outcome, plus TTL lapse for victim accounts if coverage is dropped.
- The dust tokens themselves are negligible — the damage is the asymmetry: attacker pays once (1 unit + one tx fee per account), the protocol pays renewal rent forever.

### Likelihood Explanation
Fully permissionless and economically cheap: `supply` requires only `caller.require_auth`, the payment vector just needs positive amounts, and `account_id = 0` has no rate limit or minimum. Cost per account is ~1 raw token unit plus one transaction fee. No timing, oracle, or liquidity prerequisites. The only thing limiting scale is the attacker's fee budget — identical to the Discourse case where the only limit was the attacker's request rate.

### Recommendation
Enforce a minimum first-deposit value when `account_id == 0` (e.g., a USD floor via the price context, or a per-market raw minimum), and/or cap accounts per owner via the NFT `balance` of the caller. Alternatively, add a permissionless cleanup path that burns accounts whose total collateral value is below a dust floor and has no debt, so spammed state can be reclaimed.

### Proof of Concept
From the existing test `poc_single_actor_spams_unbounded_dust_accounts` in `tests/test-harness/tests/controller/supply.rs:312-344`: an attacker minted 64 units of USDC, then looped `ctrl.supply(attacker, 0, spoke, [(hub_asset, 1)])`; each call returned a fresh `id > last_id` with `account_exists(id) == true` — demonstrating unbounded account/state creation at 1 unit each with no minimum-deposit rejection.

        env,
        acct_id,

        &mut cache,
        PositionSides::Supply,

    );

#[test]
fn poc_single_actor_spams_unbounded_dust_accounts() {
    let mut t = LendingTest::new().with_market(usdc_preset()).build();

    let attacker = t.get_or_create_user("attacker");
    let usdc = t.resolve_market("USDC");

    const N: u64 = 64;
    usdc.token_admin.mint(&attacker, &(N as i128));
    let asset = usdc.asset.clone();

    let ctrl = t.ctrl_client();
    let mut created: u64 = 0;
    let mut last_id: u64 = 0;
    for _ in 0..N {
        let dust = vec![&t.env, (hub_asset(asset.clone()), 1i128)];
        let id = ctrl.supply(&attacker, &0u64, &1u32, &dust);
        assert!(id > 0, "1-unit deposit must be accepted (no dust floor)");

        assert!(id > last_id, "each supply(id=0) must mint a new account id");
        assert!(
            ctrl.account_exists(&id),
            "spammed account persists in storage"
        );
        last_id = id;
        created += 1;
    }

    assert_eq!(
        created, N,
        "one actor created {N} distinct accounts with dust deposits"
    );
}
