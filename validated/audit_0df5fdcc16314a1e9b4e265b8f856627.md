### Title
Webhook signature verification keyed on attacker-controlled `repository.owner.login` while stack resolution uses `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App / webhook secret to validate a webhook's HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')`). Every webhook `Handler`, however, resolves the `Repository`/`Stack` that will actually be mutated using a *different* field of the same body: `repository.full_name`. Because these two fields are not required to agree, and because an organization with no `webhook_secret` configured causes signature verification to be unconditionally skipped, an attacker who knows of (or is themselves) an unsecured organization on the same Shipit instance can forge a webhook whose `repository.owner.login` points at that unsecured org while `repository.full_name` points at a completely different, secured victim repository/stack.

### Finding Description
`WebhooksController#verify_signature` in [1](#0-0)  does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is taken from the raw, attacker-supplied JSON payload before any signature check has succeeded, and used purely to pick *which* per-organization secret to check the signature against (`Shipit.github(organization:)`, see [2](#0-1) ).

`GitHubApp#verify_webhook_signature` unconditionally passes when the selected organization has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

This "optional" webhook secret is explicitly documented and shown in the shipped example config with `webhook_secret: # nil` [3](#0-2) , so a multi-organization Shipit deployment that has at least one organization configured without a secret (e.g., a legacy/internal org) will accept **any** payload claiming to originate from that organization, without validating `X-Hub-Signature` at all.

Once `verify_signature` passes, `WebhooksController#create` dispatches the payload to the registered `Shipit::Webhooks` handler for the event [4](#0-3) . Every handler resolves the target `Repository`/`Stack` using `repository.full_name`, a field that is completely independent of `repository.owner.login`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [5](#0-4) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up by `owner`/`name` columns [6](#0-5) , with no cross-check against `repository.owner.login` or the organization used for signature verification.

`PushHandler#process`, for example, will enqueue a real sync for any stack matching `repository.full_name` and the pushed branch [7](#0-6) , which in turn schedules `GithubSyncJob`, fetching commits via the *stack's own* GitHub App (`Shipit.github(organization: owner)`, derived from the `Repository` row, not from the payload) [8](#0-7) .

**The broken binding:** the organization that *authenticated* the request (`repository.owner.login`, selected for signature verification) is not required to equal the organization/repository that is actually *written to* (`repository.full_name`, used by every handler). Both fields live in the same unauthenticated JSON body prior to verification, so an attacker can freely diverge them.

### Impact Explanation
This allows an unauthenticated attacker to trigger real side effects (unauthorized deploy pipeline actions) against a victim's stack/repository that they have no legitimate access to, by "borrowing" the trust of any organization on the same Shipit instance that happens to have no `webhook_secret` configured. Depending on which webhook event/handler is targeted (e.g. `push` → `GithubSyncJob`, `status`, `check_suite` → `RefreshCheckRunsJob`, `membership` → team/user membership mutation which feeds into `Shipit.github_teams` authorization), this can affect commit tracking, CI/status state, or team membership records that gate deploy authorization — i.e., escalation into `Shipit.github_teams` authorization / spoofed repository state, without ever possessing a valid webhook secret for the targeted repository's organization.

### Likelihood Explanation
Exploitability depends on the deployment having at least one configured GitHub organization with a blank/nil `webhook_secret` (explicitly supported and shown as the example configuration), while other organizations on the instance are secured. In such (documented-as-valid) multi-org configurations, exploitation requires only a single crafted, unauthenticated HTTP POST to `/webhooks` — no credentials, no repository access, no GitHub App key needed.

### Recommendation
Cross-validate that the organization used to select and verify the webhook signature is consistent with the organization embedded in `repository.full_name` (or any other field acted upon by handlers) before processing. Additionally, reconsider whether an organization with no `webhook_secret` should be allowed to implicitly authorize actions on repositories belonging to a different, secured organization — at minimum, scope such "no secret" organizations so they can only affect their own repositories.

### Proof of Concept
1. Configure two organizations in `secrets.yml`: `victim-org` (has `webhook_secret` set, owns a tracked `Stack` for `victim-org/app`) and `open-org` (no `webhook_secret`, i.e., `webhook_secret: nil`).
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "open-org" },
    "full_name": "victim-org/app"
  }
}
```
No `X-Hub-Signature` header (or any bogus value) is required.
3. `verify_signature` calls `Shipit.github(organization: "open-org")`; since `open-org` has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally — the request passes verification.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/app")`, matching the real victim stack, and enqueues `GithubSyncJob`/stack sync for it, entirely bypassing `victim-org`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
