### Title
Permissionless asset creation lets an attacker-controlled `freezer` DoS `pallet-asset-conversion` pool accounts, permanently locking liquidity providers' funds - (File: `substrate/frame/asset-conversion/src/lib.rs`, `substrate/frame/assets/src/lib.rs`, `substrate/frame/assets/src/functions.rs`)

### Summary
`pallet-asset-conversion::create_pool` is callable by any signed account for arbitrary `T::AssetKind` pairs, with no vetting of the asset's mint/freeze configuration when `T::Assets` is backed by `pallet-assets`. `pallet-assets` lets the account that creates an asset designate itself as the asset's `freezer` (or `admin`, who can reassign `freezer`), and the `freeze`/`freeze_asset` dispatchables let that freezer mark any account — including the pool's own reserve account — as `AccountStatus::Frozen`. `reducible_balance`/`can_withdraw` in `pallet-assets` treat a frozen account as unable to transfer out funds. This is a direct structural analog of the Solana report's "arbitrary input token with freeze authority" issue: instead of an SPL mint's freeze authority freezing the pool's token vault, a FRAME asset's `freezer` role freezes the pool's reserve account for that asset, blocking `remove_liquidity`/`swap_*` and locking LP funds.

### Finding Description
- `create_pool` performs no check on whether `asset1`/`asset2` (when they are `pallet-assets` ids) have a freezer under attacker control, and simply creates the pool and its dedicated `pool_account`: [1](#0-0) 
- Liquidity and swap operations transfer tokens into/out of `pool_account`, which is the pool's single reserve account for both assets: [2](#0-1) [3](#0-2) 
- In `pallet-assets`, the account holding the asset's `freezer` role (set at asset creation, or later changed by the asset `admin`/`owner`) can call `freeze` to mark **any** account (including `pool_account`) as `Frozen`: [4](#0-3) 
- Once frozen, `reducible_balance` treats the account's transferable balance as zero (`Error::<T,I>::Frozen`), so `T::Assets::transfer`/`withdraw` from `pool_account` fails: [5](#0-4) 
- `do_remove_liquidity` calls `T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)` unconditionally after burning the LP tokens — if that asset's pool-account balance is frozen, the transfer fails **after** the LP tokens have already been burned in the same call attempt (transactional rollback applies per-call, but the LP holder is permanently unable to redeem as long as the freeze exists), effectively bricking withdrawal for that pool: [6](#0-5) 

The violated invariant mirrors the Solana report exactly: the pool logic implicitly assumes the input/pooled token asset has no third-party authority capable of freezing the pool's own reserve account. Nothing in `create_pool`, `add_liquidity`, or the `Config::Assets` bound enforces "no freezer" or "freezer == pool/none" for the asset kinds accepted into a pool.

### Impact Explanation
If a pool is created for an asset whose `freezer` is not trusted/controlled by the pool operator (e.g., an attacker creates their own `pallet-assets` asset via the standard permissionless `create` call, sets themselves as `freezer`, pairs it with DOT/USDT in a pool, waits for liquidity to be added, then calls `freeze` on `pool_account`), all further `swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`, and `remove_liquidity` calls touching that asset in that pool fail with `Error::Frozen`. Liquidity providers' funds in the pool become permanently stuck for as long as the freeze is active — a Denial-of-Service with real, unbounded fund lock, matching the "permanent loss of funds" impact class of the original report.

### Likelihood Explanation
Requires no privileged role: any signed account can create a `pallet-assets` asset (standard permissionless asset creation, subject only to a deposit) and become that asset's `freezer`; any signed account can call `create_pool` for arbitrary asset pairs; freezing is a one-line dispatchable call by the freezer with no pool-side veto. However, this depends on runtime configuration: production networks such as Asset Hub use `pallet-asset-conversion` with `Config::Assets`/`PoolAssets` wired to `pallet-assets`, and asset creation there may be gated by root/admin origins or a curated `AssetKind` filter (this repository snapshot did not let me confirm the exact `Config::Assets` origin filters or whether Asset Hub's live runtime restricts which `AssetKind`s are poolable, e.g. only vetted foreign/local assets). This is analogous to the original report's own team response — the risk is real, but mitigated in practice for "official" pools by curation of accepted assets outside the protocol logic itself.

### Recommendation
- Do not allow `create_pool`/`add_liquidity` to accept an asset kind that currently has (or could later be assigned) a `freezer` distinct from the pool/protocol itself, or explicitly document/gate this as a permissioned pool-creation flow (e.g., restrict `create_pool` origin, or require asset kinds to pass an allowlist check before being poolable), mirroring the report's recommendations of validating absence of a freeze authority and using an allowlist of trusted assets.
- Alternatively, have `pallet-asset-conversion` surface a way to detect and react to a frozen pool account (e.g., a permissionless "unstick"/migration path, or refusing new liquidity into pools whose reserve account is frozen) so a single malicious asset cannot lock funds of unrelated LPs indefinitely.

### Proof of Concept
No executable PoC was run; this is a code-level structural analog derived from the cited source. A concrete reproduction (not executed here) would:
1. As account A (no privilege), call `pallet_assets::create` for asset `X`, becoming its `owner`/`admin`/`freezer`.
2. As account A or B, call `pallet_asset_conversion::create_pool(DOT, X)`, then `add_liquidity(...)` from a victim LP account.
3. As account A, call `pallet_assets::freeze(X, pool_account)`.
4. Attempt `remove_liquidity`/`swap_exact_tokens_for_tokens` touching `X` from the victim — expect `DispatchError::Token(TokenError::Frozen)` / `Error::<T,I>::Frozen`, confirming funds are stuck in `pool_account` while the freeze persists.
Guards not present: no check in `create_pool`/`do_add_liquidity` on the poolable asset's freezer/admin trust, and `reducible_balance` unconditionally honors `AccountStatus::Frozen` for any account including the pool's own reserve account.

		pub(crate) fn do_remove_liquidity(
			who: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			lp_token_burn: T::Balance,
			amount1_min_receive: T::Balance,
			amount2_min_receive: T::Balance,
			withdraw_to: &T::AccountId,
		) -> Result<(T::Balance, T::Balance), DispatchError> {
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			ensure!(lp_token_burn > Zero::zero(), Error::<T>::ZeroLiquidity);

			let pool = Pools::<T>::get(&pool_id).ok_or(Error::<T>::PoolNotFound)?;

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;
			let (reserve1, reserve2) = Self::get_reserves(asset1.clone(), asset2.clone())?;

			let total_supply = T::PoolAssets::total_issuance(pool.lp_token.clone());
			let withdrawal_fee_amount = T::LiquidityWithdrawalFee::get() * lp_token_burn;
			let lp_redeem_amount = lp_token_burn.saturating_sub(withdrawal_fee_amount);

			let amount1 = Self::mul_div(&lp_redeem_amount, &reserve1, &total_supply)?;
			let amount2 = Self::mul_div(&lp_redeem_amount, &reserve2, &total_supply)?;

			ensure!(
				!amount1.is_zero() && amount1 >= amount1_min_receive,
				Error::<T>::AssetOneWithdrawalDidNotMeetMinimum
			);
			ensure!(
				!amount2.is_zero() && amount2 >= amount2_min_receive,
				Error::<T>::AssetTwoWithdrawalDidNotMeetMinimum
			);
			let reserve1_left = reserve1.saturating_sub(amount1);
			let reserve2_left = reserve2.saturating_sub(amount2);
			ensure!(
				reserve1_left >= T::Assets::minimum_balance(asset1.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);
			ensure!(
				reserve2_left >= T::Assets::minimum_balance(asset2.clone()),
				Error::<T>::ReserveLeftLessThanMinimal
			);

			// burn the provided lp token amount that includes the fee
			T::PoolAssets::burn_from(
				pool.lp_token.clone(),
				who,
				lp_token_burn,
				Expendable,
				Exact,
				Polite,
			)?;

			T::Assets::transfer(asset1, &pool_account, withdraw_to, amount1, Expendable)?;
			T::Assets::transfer(asset2, &pool_account, withdraw_to, amount2, Expendable)?;

			Self::deposit_event(Event::LiquidityRemoved {
				who: who.clone(),
				withdraw_to: withdraw_to.clone(),
				pool_id,
				amount1,
				amount2,
				lp_token: pool.lp_token,
				lp_token_burned: lp_token_burn,
				withdrawal_fee: T::LiquidityWithdrawalFee::get(),
			});

			Ok((amount1, amount2))
		}

		#[pallet::call_index(11)]
		pub fn freeze(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Frozen;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Frozen { asset_id: id, who });
			Ok(())
		}

	// Maximum `amount` that can be passed into `can_withdraw` to result in a `WithdrawConsequence`
	// of `Success`.
	pub(super) fn reducible_balance(
		id: T::AssetId,
		who: &T::AccountId,
		keep_alive: bool,
	) -> Result<T::Balance, DispatchError> {
		let details = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(details.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);

		let account = Account::<T, I>::get(&id, who).ok_or(Error::<T, I>::NoAccount)?;
		ensure!(!account.status.is_frozen(), Error::<T, I>::Frozen);

		let untouchable = match (
			T::Holder::balance_on_hold(id.clone(), who),
			T::Freezer::frozen_balance(id.clone(), who),
			keep_alive,
		) {
			(None, None, true) => details.min_balance,
			(None, None, false) => Zero::zero(),
			(maybe_held, maybe_frozen, _) => {
				let held = maybe_held.unwrap_or_default();
				let frozen = maybe_frozen.unwrap_or_default();
				frozen.saturating_sub(held).max(details.min_balance)
			},
		};
		let amount = account.balance.saturating_sub(untouchable);

		Ok(amount.min(details.supply))
	}
