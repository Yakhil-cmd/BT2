### Title
Cross-organization webhook signature confusion allows spoofed commit statuses on another organization's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate `X-Hub-Signature` based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while every `Handler` subclass resolves which `Repository`/`Stack` records to mutate using a completely different, unvalidated field: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so in a multi-organization Shipit deployment, an attacker who legitimately owns/administers one onboarded GitHub organization (and therefore knows that organization's `webhook_secret`) can compute a valid HMAC signature for their own org while setting `repository.full_name` to point at a *different* organization's repository/stack.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30` derives the signing organization strictly from attacker-controlled JSON: [1](#0-0) 
and `repository_owner`: [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks a per-organization `GitHubApp` instance (and its distinct `webhook_secret`) as documented for the "Using Multiple Github Applications" setup: `docs/setup.md:182-209`. Each onboarded organization's operator supplies/knows its own `webhook_secret` when creating the GitHub App, per `docs/setup.md:20-30` and `config/secrets.development.example.yml`.

Once the signature is accepted, `WebhooksController#create` dispatches to handlers using the *raw* payload, not the fields used for signature selection: [3](#0-2) 

Every handler resolves the target `Stack`s via `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — an entirely separate JSON path from the one used for signature verification: [4](#0-3) 

Because `repository.owner.login` (used to select the signing secret) and `repository.full_name` (used to select the write target) are independent, attacker-controlled fields in the same JSON body, an attacker who knows organization A's `webhook_secret` can:
1. Set `repository.owner.login` = `org-A` (or `organization.login` = `org-A`) so `verify_signature` picks org A's secret and the attacker's correctly-computed HMAC passes.
2. Set `repository.full_name` = `org-B/some-repo`, an unrelated organization's repository that has Stacks registered in the same Shipit instance.

The webhook is accepted and processed against `org-B`'s stack — a binding break between "the organization that authenticated" and "the repository that is written."

### Impact Explanation
The clearest concrete write path is `StatusHandler`, which creates a `Status` for any commit matching an attacker-chosen `sha`, using attacker-supplied `state`/`context`/`description`: [5](#0-4) 
This is not scoped by repository at all — it matches on `Commit.where(sha: params.sha)` — so once past `verify_signature`, an attacker only needs a valid signature from any org they control to inject fabricated `success` statuses for arbitrary commit SHAs used by other stacks' `ci.require` checks (`app/models/shipit/deploy_spec.rb`, `app/models/shipit/status/group.rb`), which gate whether a commit is deployable/mergeable. `PushHandler` and `CheckSuiteHandler` are similarly gated only by the forgeable `repository.full_name`/`organization` fields with no cross-check against the signing org, allowing forced `sync_github` or check-run refresh calls against another org's stacks.

This can escalate to an unauthorized deploy: an attacker spoofs a passing CI status for a required context on a commit belonging to a stack they don't administer, allowing that commit to satisfy `ci.require` and clear the review/merge gate for a deploy that should have been blocked, without ever obtaining that organization's own webhook secret or GitHub credentials.

### Likelihood Explanation
Exploitability requires the deployment to use the documented multi-organization `github:` configuration (`docs/setup.md`) with the attacker being a legitimate operator/admin of at least one onboarded organization's GitHub App (and thus knowing its `webhook_secret`) — this is a real, documented, supported configuration, not a hypothetical misconfiguration. No repository write access, no Shipit session, and no target org's secret are required; only the attacker's own org's already-known secret and the public `/webhooks` endpoint. This satisfies the "unprivileged attacker breaking a deployment-trust binding" scope (organization that authenticated vs. repository that is written).

### Recommendation
Bind signature verification and write-target resolution to the same, single field. Concretely, in `verify_signature` and `Handler#repository_name`, derive the organization from the same canonical source (e.g., always require `repository.full_name`'s owner segment, or `organization.login`, to match), and reject webhooks where `repository.owner.login`/`organization.login` does not match the owner segment of `repository.full_name`. Additionally, `Repository.from_github_repo_name` lookups triggered by handlers should assert that the resolved `Repository#owner` equals the organization whose `webhook_secret` validated the request.

### Proof of Concept
1. Deploy Shipit with multi-org config: `org-A` and `org-B` each with distinct `webhook_secret`s (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker legitimately administers the GitHub App for `org-A` and knows `org-A`'s `webhook_secret`.
3. `org-B` has a Stack tracking `org-B/victim-repo`, with `ci.require: [ci/required]` gating deploys, and a pending commit with `sha=X`.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "X",
  "state": "success",
  "context": "ci/required",
  "organization": { "login": "org-A" },
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-B/victim-repo" }
}
```
5. Signs `X-Hub-Signature` using `org-A`'s known `webhook_secret` (HMAC-SHA1 over the raw body).
6. `verify_signature` calls `Shipit.github(organization: 'org-A')` and the signature validates.
7. `StatusHandler#process` runs `Commit.where(sha: 'X').each { |c| c.create_status_from_github!(params) }`, creating a spoofed `success` status for commit `X` on `org-B`'s stack, satisfying `ci.require` despite the attacker having no relationship to `org-B` or `victim-repo`.
