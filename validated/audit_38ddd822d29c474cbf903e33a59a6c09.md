### Title
Webhook signature verified against the payload's `repository.owner.login` organization while event processing acts on the payload's `repository.full_name` — cross-organization webhook forgery in multi-tenant configurations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an inbound webhook against using `repository_owner`, a field taken directly from the untrusted, attacker-supplied JSON body [1](#0-0) . All the actual downstream handlers that decide *which stack/repository* to act on, however, key off a different field in the same body — `repository.full_name` — via `Shipit::Webhooks::Handlers::Handler#repository_name` [2](#0-1) . In a multi-organization Shipit deployment (explicitly supported and documented) each organization has its own independent `webhook_secret` [3](#0-2) . Nothing ties the organization used to select/verify the signature to the repository the handler subsequently mutates, so a party who legitimately controls the webhook secret for *one* configured organization can forge a validly-signed payload whose `repository.owner.login` matches their own org (so signature verification passes) while `repository.full_name` names a completely different organization's stack.

### Finding Description
`verify_signature` computes `repository_owner` from the payload before any authenticity check is performed, then fetches the corresponding `GitHubApp` and verifies the HMAC using that organization's own secret:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

Once verification succeeds, `Handler#stacks` — used by `PushHandler` and other default handlers — resolves the target repository from a *different* field of the same payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process` then syncs the stack it finds using the attacker-controlled `after` SHA:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

The engine's own `github_teams`/organization-authorization model implicitly assumes that "the org whose secret validated this webhook" and "the repository being written to" are the same trust domain (this is exactly the binding the app relies on when configuring per-organization GitHub Apps: `github.somegithuborg.webhook_secret` is meant to authorize only events for `somegithuborg`'s repositories). Nothing in `WebhooksController` or `Handler` enforces `repository.owner.login == repository.full_name.split('/').first`, so:

**Binding that should hold:** `organization authenticated by webhook_secret == organization of the repository being written by the handler`.
**Binding that actually holds:** `organization authenticated by webhook_secret` is read from `repository.owner.login`/`organization.login`, while `repository written` is read from the unrelated `repository.full_name` field — both attacker-controlled prior to verification, and never cross-checked.

Before the attacker's request: legitimate installer of org A (with its own valid `webhook_secret`) can only affect stacks under org A's repositories, because GitHub itself would never emit a webhook where `repository.owner.login` and `repository.full_name`'s owner differ.
After the attacker's request: since the attacker crafts the raw payload directly and computes the HMAC themselves (they know org A's secret), they can set `repository.owner.login = "orgA"` and `repository.full_name = "orgB/victim-repo"` in the same payload. Signature verification passes (uses org A's secret against org A's owner login), but `PushHandler` operates on `orgB/victim-repo`'s stack, invoking `Stack#sync_github` with an attacker-chosen `after` SHA for a repository/organization the attacker has no access to.

### Impact Explanation
This breaks the authentication boundary between organizations in a multi-tenant Shipit install: an attacker who only controls (or is an admin of) one configured GitHub organization/app installation can forge webhook events attributed to any other organization's repositories tracked by the same Shipit instance. Depending on stack configuration (continuous delivery enabled, CI status spoofing via forged `status`/`check_suite` events which follow the identical `repository_owner` vs `repository.full_name` pattern), this can force `GithubSyncJob` to treat an attacker-chosen SHA as the head of a victim stack and, combined with continuous delivery, trigger an unauthorized deploy of a repository outside the attacker's authorized scope — matching the "unauthorized deploy" / "cross-repository writes" Critical/High impact bar.

### Likelihood Explanation
Medium: requires the Shipit instance to be configured for multiple GitHub organizations (`github.<org>.webhook_secret` per docs), and requires the attacker to already have legitimate access to at least one configured organization's webhook secret (e.g., because they administer that org's GitHub App installation or previously received a genuine webhook and can rotate/know its secret). No access to Shipit sessions, `ApiClient` tokens, or the target organization's own webhook secret is required.

### Recommendation
After verifying the HMAC signature, require that the organization resolved for signature verification (`repository_owner`) matches the organization actually referenced by `repository.full_name` (and by `organization.login` for org-scoped events) before dispatching to handlers. Reject the request if they diverge, e.g. in `WebhooksController#verify_signature` or centrally in `Handler#repository_name`/`Handler#stacks`, cross-check `repository.full_name.split('/').first == repository_owner`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org example) and each having Shipit stacks tracking repositories in their respective orgs.
2. As an entity that legitimately knows `orgA`'s `webhook_secret` (e.g., an admin of orgA's GitHub App installation), craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` and send it with `X-Github-Event: push` to the Shipit webhooks endpoint.
4. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, fetches `orgA`'s `GitHubApp`, and successfully verifies the signature computed with `orgA`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")`, unrelated to `orgA`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on orgB's stack — despite the attacker having no credentials for orgB.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
