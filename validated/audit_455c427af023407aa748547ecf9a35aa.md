### Title
Webhook signature is verified against the organization named in the payload, not against the repository the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from a field the attacker fully controls inside the same unauthenticated request body, and never checks that this "authenticating organization" matches the repository that the downstream `Handler` subclasses actually act on. This is the same class of bug as the Talos report: a check is performed on one value (`protocolFees`/balance) while the actual state-changing effect operates on a different, unguarded value (the raw `transfer`). Here, the check is performed against `repository_owner`/`organization.login`, while every handler (`PushHandler`, `StatusHandler`, `PullRequest::OpenedHandler`, `PullRequest::ClosedHandler`, etc.) resolves the target `Stack`/`Repository` from `repository.full_name` or `Commit.where(sha:)`, fields that are not cryptographically bound to the "authenticated" organization at all.

### Finding Description
`verify_signature` picks the app/secret using only a value taken from the untrusted JSON body: [1](#0-0) [2](#0-1) [3](#0-2) 

`Shipit::GithubApp#verify_webhook_signature` only proves that the requester can produce a valid HMAC for *some organization's* configured `webhook_secret` — and if that organization has no `webhook_secret` configured, it returns `true` unconditionally: [4](#0-3) 

Meanwhile, every handler resolves the repository/stack to mutate from a *different, independent* field of the same attacker-supplied JSON body — `repository.full_name` — with no cross-check against the organization that was used to validate the signature: [5](#0-4) 
`PushHandler` triggers a GitHub sync for any stack matching that `full_name`+branch: [6](#0-5) 
`StatusHandler` writes commit statuses purely by `sha`, with no repository binding at all: [7](#0-6) 
`PullRequest::OpenedHandler`/`ClosedHandler` provision or archive review stacks based solely on `params.repository.full_name`: [8](#0-7) [9](#0-8) 

**The binding that breaks (as an equality):**
`organization authenticated by verify_signature (repository_owner/organization.login from payload)` ≠ `repository/stack acted upon by the Handler (repository.full_name from the same payload)`.

Because `/webhooks` is a public, unauthenticated HTTP endpoint (only `verify_signature` gates it, and it is entirely attacker-constructed JSON, not a value GitHub itself vouches for beyond the HMAC), nothing stops a request whose `repository.owner.login` is set to Org A (whose secret the attacker knows, e.g. because they administer their own small GitHub organization that is also onboarded to this Shipit instance, or because Org A has no `webhook_secret` configured) while `repository.full_name` is set to `victim-org/victim-repo`, a stack that belongs to a completely different, unrelated organization tracked by the same Shipit instance.

### Impact Explanation
An attacker who can produce a validly "signed" (or unsigned, in the no-`webhook_secret` case) webhook body for *any single* organization configured in this Shipit instance can forge push/status/pull_request events that act on *any repository/stack tracked by the same instance*, regardless of organization. Concretely this allows:
- Injecting arbitrary commit statuses on victim commits via `StatusHandler`, which can be used to satisfy `ignore_ci`/status-gated deploy requirements.
- Forcing `PushHandler` to trigger a `GithubSyncJob`/`sync_github` against a victim stack.
- Forging `PullRequest::OpenedHandler`/`ClosedHandler` to provision or archive review stacks on a victim repository.

This crosses the "cross-repository writes" / unauthorized-deploy-adjacent boundary called out in the rules, since the organization whose credentials were checked is not the repository whose Shipit state is mutated.

### Likelihood Explanation
Requires only the ability to send an HTTP POST to the Shipit instance's public `/webhooks` endpoint and knowledge of (or the absence of) one configured organization's `webhook_secret` in a multi-organization deployment — no `ApiClient` token, session, or GitHub write access to the victim repository is needed. Multi-organization configuration is a documented, supported setup. [10](#0-9) 

### Recommendation
After `verify_signature` resolves the authenticating organization, `Handler#stacks`/`repository_name` (and `StatusHandler`'s bare `sha` lookup) should require that the resolved repository's owner matches the organization the signature was verified against, rejecting any payload where `repository.full_name`'s owner differs from `repository_owner`.

### Proof of Concept
1. Attacker controls (or knows the blank/absent `webhook_secret` for) organization `attacker-org`, configured in this Shipit instance's `github:` section.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
signed (or left unsigned, if `webhook_secret` is blank for `attacker-org`) using `attacker-org`'s webhook secret.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository_owner`) and successfully verifies the signature against that org's secret — see `app/controllers/shipit/webhooks_controller.rb:24-30,59-62`.
4. `PushHandler#process` then resolves stacks purely from `repository.full_name = "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `push_handler.rb:12-17`) and enqueues a sync/job for the victim's stack, even though the signature was never verified against `victim-org`'s secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
