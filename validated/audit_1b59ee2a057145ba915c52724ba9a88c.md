### Title
Uncaught exception in chash validation causes node crash on malformed address string - (File: chash.js)

### Summary
`chash.isChashValid()` can throw an uncaught `Error` when processing an attacker-supplied address/chash string whose length passes the initial 32/48-character check but whose base32/base64-decoded byte length does not match the expected 160/288-bit structure. This throw occurs outside the function's `try/catch` block and propagates through `isValidChash`/`isValidAddress`, which are called while validating every posted unit, AA trigger, asset definition, and definition-chash in the codebase.

### Finding Description
`chash.isChashValid()` first checks the string length (32 or 48 characters) and wraps only the decode step in `try/catch`: [1](#0-0) 

The subsequent call to `separateIntoCleanDataAndChecksum(binChash)` is **not** protected by the try/catch, and it explicitly throws if the resulting bit-length isn't exactly 160 or 288: [2](#0-1) 

The encoded-length check (`encoded_len !== 32 && encoded_len !== 48`) assumes that a 32-character base32 string always decodes to exactly 20 bytes (160 bits) via the `thirty-two` package, and a 48-character base64 string always decodes to exactly 36 bytes (288 bits) via `Buffer.from`. This assumption depends entirely on the leniency/strictness of the underlying decoders (e.g., `thirty-two`'s handling of invalid characters, missing padding, or non-canonical encodings) — this repo does not include its own strict format validation before calling `separateIntoCleanDataAndChecksum`, so any decoder edge case that yields a buffer of unexpected length turns into an unhandled synchronous throw.

`isChashValid` is reached via `validation_utils.isValidChash` → `isValidAddress`/`isValidAddressAnyCase`: [3](#0-2) 

These helpers are invoked pervasively while validating externally supplied data from a single posted unit: author/output/definition addresses in `validation.js`, address literals inside AA definitions and oscript/ojson evaluation (`definition.js`, `formula/validation.js`, `formula/evaluation.js`, `aa_composer.js`), and wallet/device address fields. Any of these call sites that do not themselves wrap the address check in `try/catch` will let the exception bubble up.

### Impact Explanation
An uncaught synchronous exception thrown deep inside unit/AA/definition validation, if not caught by an enclosing `try/catch` in the calling module, terminates the Node.js event loop / process (Node's default behavior for an uncaught exception is to crash unless a global handler intervenes). Because address/chash strings appear in units, AA triggers, asset definitions, and oscript literals — all postable by any unprivileged network participant — a single crafted unit could crash any full node that processes it, matching a "network unable to confirm new units" denial-of-service outcome, analogous to the referenced CVE's kernel-mode DoS from improper pointer/length validation.

### Likelihood Explanation
Exploitability hinges on two unverified points I could not confirm further within available tooling: (1) whether the `thirty-two` base32 decoder (or `Buffer.from(..., 'base64')`) can actually be coerced into producing a buffer whose bit-length differs from 160/288 given a 32/48-character input, and (2) whether every call site that reaches `isValidAddress`/`isValidChash` during unit/AA validation is wrapped in an outer `try/catch` that would prevent process termination. Without confirming a concrete malformed-string input that survives the length check yet fails the internal offset assertion, this remains a plausible but unconfirmed root cause.

### Recommendation
Wrap the entire body of `chash.isChashValid()` (not just the decode step) in `try/catch`, returning `false` on any internal exception (including from `separateIntoCleanDataAndChecksum`) rather than letting it propagate. Additionally, audit all call sites of `isValidAddress`/`isValidChash` in unit, AA, and definition validation paths to ensure none can let an exception from this function escape to the top level uncaught.

### Proof of Concept
Could not be fully constructed without confirming the exact malformed-input behavior of the `thirty-two` decoder; a working PoC would require crafting a 32-character string that `thirty-two.decode()` accepts but that yields a buffer whose length in bits isn't 160 (e.g., via non-standard padding or mixed-case/invalid symbols the decoder silently tolerates), then submitting a unit/AA definition containing that string as an address field to `validate()` in `validation.js` and observing an uncaught `Error: bad length=...` crash the node process.
