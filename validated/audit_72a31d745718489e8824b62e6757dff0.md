### Title
Private Textcoin Spending Key Stored Together With Private Payment Data in a Single File - (File: wallet.js)

### Summary
When a user sends a private asset as a textcoin to a non-device recipient (e.g., to be shared via file, USB, cloud, or messaging app), `sendMultiPayment` invokes `storePrivateAssetPayload` to persist the transfer artifact. This function bundles the `mnemonic` — which is the spending secret controlling the textcoin's temporary address — together with the private payment chain data (`chains`) into a single zip entry (`private_textcoin`) and writes it to a single file. Anyone who obtains this one file has both the proof of the private payment and the key required to immediately claim/spend it, with no separation between secret and payload.

### Finding Description
`storePrivateAssetPayload` builds `storedObj = { mnemonic, chains }` and writes it as a single JSON blob inside a zip file: [1](#0-0) 

The `mnemonic` here is not incidental metadata — `expandMnemonic` derives the actual private key (`xPrivKey`) and address (`addrInfo.address`) used to sign and claim the textcoin: [2](#0-1) 

`receiveTextCoin` later uses exactly this mnemonic to sign a unit that spends the funds at `addrInfo.address`: [3](#0-2) 

The `chains` field holds `arrChainsOfRecipientPrivateElements`, the actual private-payment chain (amounts, blinding factors, spend proofs) needed to prove and later transfer the private asset — this is triggered from `sendMultiPayment`'s private-asset branch: [4](#0-3) 

On the receiving side, `handlePrivatePaymentFile` reads the same file back and extracts both `data.mnemonic` and `data.chains` from the single unzipped payload to validate and claim the chain: [5](#0-4) 

This is structurally identical to the reported bug class: the decryption/spending key (`mnemonic`) is stored alongside the sensitive payload (`chains`) in the same container, so possession of the container alone is sufficient for full compromise — there is no separation ensuring that access to the payload requires a separate, independently-protected key retrieval step (e.g., a hardware-backed keystore, as `react-native-keychain` would provide for the original finding).

### Impact Explanation
The private-textcoin file is explicitly designed to be moved off-device (via `opts.getPrivateAssetPayloadSavePath`, meant for file-sharing/NFC/cloud/USB transfer to the recipient). Because it contains both the spending mnemonic and the private payment chain in one artifact, any party that intercepts, backs up, or otherwise gains access to that single file — during transfer, in a shared folder, in a cloud sync, or via device compromise — can immediately reconstruct the private key and independently call the equivalent of `receiveTextCoin` to claim the funds before the intended recipient does. This is concrete unauthorized spending of value that the legitimate recipient believed only they could claim.

### Likelihood Explanation
This path is reachable by any ordinary wallet user who sends a private asset as a textcoin without a paired recipient device (a standard, documented wallet feature, not a privileged operation). No malicious peer, hub, or node cooperation is required — the vulnerability is purely in how the sender's own wallet packages the transfer artifact, so likelihood is driven only by how the resulting file is transmitted/stored, which is inherently outside the application's control once created.

### Recommendation
Do not co-locate the mnemonic (spending key) with the private payment chain in the same file/container. Instead:
- Transmit or store the mnemonic via a separate, independently protected channel from the `chains` payload (e.g., require it to be typed/scanned separately, or encrypt the `chains` blob using a key derived from data not present in the same file).
- If a single-file transfer mechanism is required for UX reasons, encrypt `chains` under a key that is not stored in the file at all (e.g., derived from a PIN/passphrase communicated out-of-band), so that possession of the file alone is insufficient to claim funds.

### Proof of Concept
1. Sender calls `wallet.sendMultiPayment` with a private, non-transferrable-to-device asset and a `textcoin:` output (no recipient device paired).
2. This triggers `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, cb)` (`wallet.js:2850`), producing a zip file whose single entry `private_textcoin` contains `{ mnemonic, chains }`.
3. The sender transfers this file to the recipient through any external channel (email attachment, cloud drive, USB stick, messaging app).
4. Any third party who obtains a copy of this file (e.g., through the transfer channel, a cloud backup, or device access) can call `handlePrivatePaymentFile` / `expandMnemonic(data.mnemonic)` + `receiveTextCoin(data.mnemonic, attacker_address, ...)` themselves, claiming the asset before the intended recipient — with no need to compromise any additional secret, since everything required is in the one file.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
