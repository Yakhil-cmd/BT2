### Title
`StatusHandler#process` attaches CI status by SHA alone, letting an attacker's own repo fake success for a victim stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)` with no repository check, while `WebhooksController#verify_signature` only proves the payload was signed by *some* GitHub organization known to Shipit — the one named in the payload's own `repository.owner.login`, which the attacker controls. This breaks the required binding `payload['repository']['full_name'] == commit.stack.repository.full_name`, letting an attacker's own repo's status webhook mark a victim stack's commit as `success`, feeding directly into `Commit#deployable?` → `Stack#next_commit_to_deploy` → `Stack#trigger_continuous_delivery` → `trigger_deploy`.

### Finding Description
The required binding is:
`payload.dig('repository','full_name') == commit.stack.repository.full_name`

`StatusHandler` is defined without any repository scoping: [1](#0-0) 
It simply looks up every `Commit` row whose `sha` matches the attacker-supplied `params.sha` and calls `commit.create_status_from_github!(params)` on each, regardless of which repository the commit's stack points to. Note that the base `Handler` class actually provides a repository-scoping helper (`stacks`, built from `payload.dig('repository','full_name')`) that other handlers use, but `StatusHandler#process` never calls it: [2](#0-1) 

`WebhooksController#verify_signature` only validates that the payload is authentically signed by the GitHub org named inside the payload itself (`repository_owner`), not that it corresponds to the specific commit/stack being updated: [3](#0-2) 
If the attacker owns/controls a GitHub organization/repository that has its own valid webhook secret configured in Shipit (a normal, unprivileged, self-service scenario for any onboarded org), `verify_signature` passes for a webhook whose `repository` block names the attacker's own org/repo — signature validity says nothing about which `sha`/commit the `state`/`sha` fields inside the JSON body refer to, since those fields are freely chosen by whoever crafts the payload for their own repo/org.

Once `Commit.where(sha: params.sha)` matches the victim's commit (SHA values are public, e.g. visible on a PR/commit page, so the attacker can supply the exact victim SHA as the `sha` field in their own signed request), `commit.create_status_from_github!(params)` runs: [4](#0-3) 
`add_status` recomputes `status` and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`: [5](#0-4) 

With the new `success` status persisted, `Commit#deployable?` becomes true if the commit isn't locked and isn't blocked: [6](#0-5) 
`schedule_continuous_delivery` (invoked after commit creation, but also re-triggerable through the periodic `Stack.schedule_continuous_delivery` sweep or `ProcessMergeRequestsJob`) enqueues `ContinuousDeliveryJob`, which calls `Stack#trigger_continuous_delivery`: [7](#0-6) [8](#0-7) 
`trigger_continuous_delivery` calls `next_commit_to_deploy`, which selects the first (from the tail) commit for which `deployable?` is true, and then calls `trigger_deploy`: [9](#0-8) [10](#0-9) 
`trigger_deploy`/`build_deploy` then creates and enqueues a real `Deploy` for the victim stack: [11](#0-10) 

Guards that do NOT stop this: `verify_signature` checks org authenticity, not sha/repo correspondence; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema on `StatusHandler` only validates types (`sha: String`, `state: String`), not repository ownership; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant since this path is unauthenticated webhook ingestion; model validations on `Repository`/`Stack` don't constrain cross-repository status writes because `Status` records are simply attached to whatever `Commit` row matches the sha, with no FK check against the payload's repository.

### Impact Explanation
An attacker who controls any GitHub organization/repository onboarded to the same Shipit instance (a routine, unprivileged action — any org can be onboarded and issue its own genuinely-signed webhooks) can forge a `status` webhook naming the victim's public commit SHA and marking it `success`. This causes Shipit to create an unauthorized `Deploy` for the victim stack of a commit that never passed CI in its own repository — matching the "unauthorized deploy" Critical impact category and "a payload for one repository mutating another's stack/commit". The attack is repeatable against any stack/commit whose SHA the attacker can observe (SHAs are public GitHub data), and generalizes across all tenants sharing the Shipit instance, since the vulnerable lookup (`Commit.where(sha: ...)`) is global and not partitioned by repository.

### Likelihood Explanation
Preconditions: victim stack must have `continuous_deployment: true`, a `cached_deploy_spec`, no active task, and not be locked (fairly standard configuration for actively deployed stacks) as required by `Stack#deployable?`/`trigger_continuous_delivery`. The attacker needs an org/repo already connected to the same Shipit instance with a valid webhook secret (achievable via normal self-service onboarding, no elevated Shipit permissions). No Shipit session, API token, or GitHub secret of the victim's org is required — the attacker only signs with their own org's secret. Cost is a single crafted HTTP POST to `/webhooks`, fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository named in the webhook payload (mirroring the `stacks`/`repository_name` helper already provided by `Handler`), e.g. resolve commits only within `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack`/`Repository` filtered by `payload.dig('repository', 'full_name')`, rejecting/ignoring any status whose payload repository does not match the commit's own stack repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook from an unrelated repository cannot mark another stack's commit as deployable" do
  victim_repo  = shipit_repositories(:shipit)                 # e.g. "shopify/shipit-engine"
  victim_stack = create_stack(repository: victim_repo, continuous_deployment: true)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'pending head')

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker-org/attacker-repo' }, # different repo entirely
  }

  assert_equal 0, Shipit::Deploy.where(stack: victim_stack).count

  # Simulate a genuinely-signed webhook from the attacker's own org
  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  victim_commit.reload

  assert victim_commit.deployable?, "commit incorrectly became deployable via cross-repo status"

  perform_enqueued_jobs # runs ContinuousDeliveryJob -> Stack#trigger_continuous_delivery

  assert_equal 1, Shipit::Deploy.where(stack: victim_stack).count,
    "an unauthorized deploy was triggered for victim_stack using CI status from an unrelated repository"
end
```
Both sides of the binding (`attacker_payload['repository']['full_name']` = `"attacker-org/attacker-repo"` vs `victim_commit.stack.repository.full_name` = victim repo) diverge, confirming the vulnerability: `StatusHandler` never checks them, and a `Deploy` is created for `victim_stack` from a status that was never posted against its own repository.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def trigger_deploy(*args, **kwargs)
      if changed?
        # If this is the first deploy since the spec changed it's possible the record will be dirty here, meaning we
        # cant lock. In this one case persist the changes, otherwise log a warning and let the lock raise, so we
        # can debug what's going on here. We don't expect anything other than the deploy spec to dirty the model
        # instance, because of how that field is serialised.
        if changes.keys == ['cached_deploy_spec']
          save!
        else
          Rails.logger.warning("#{changes.keys} field(s) were unexpectedly modified on stack #{id} while deploying")
        end
      end

      run_now = kwargs.delete(:run_now)
      deploy = with_lock do
        deploy = build_deploy(*args, **kwargs)
        deploy.save!
        deploy
      end
      run_now ? deploy.run_now! : deploy.enqueue
      continuous_delivery_resumed!
      deploy
    end

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin

      rescue Task::ConcurrentTaskRunning
      end
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
