### Title
Cross-repository status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table and writes a `Status` for every match, without ever checking that the commit's stack belongs to the repository that authenticated the webhook. Since the base `Handler` class does expose a `repository_name`/`stacks` helper for this exact purpose but `StatusHandler` never calls it, a webhook validly signed for `attacker/repo` can write a `Status` row onto a commit belonging to `victim-org/victim-repo` whenever the SHAs collide (accidentally or by design, e.g. the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical across all git repositories).

### Finding Description
The required binding is: `repository_name` (the `repository.full_name` from the payload that the HMAC signature was verified against) must equal `c.stack.repository.full_name` for every `Commit` `c` mutated by the handler. `StatusHandler#process` does not enforce this: [1](#0-0) 

Compare with `Handler#stacks`/`repository_name`, which exists precisely to scope handler actions to the authenticated repository, but is unused here: [2](#0-1) 

`Commit.where(sha: params.sha)` matches on the `sha` column alone, which is not globally unique in the schema — the empty-tree SHA (or any deliberately colliding SHA, e.g. copied from a public commit) will match rows across unrelated stacks/repositories. For each match, `commit.create_status_from_github!(params)` is called, which writes into that commit's `statuses` association regardless of which repository the webhook was signed for: [3](#0-2) 

The GitHub webhook signature (`X-Hub-Signature`) verified by `WebhooksController` only proves the payload came from the repository named in `payload['repository']['full_name']` (i.e., that the sender controls `attacker/repo`'s webhook secret) — it does not prove anything about which commit rows should be affected. Since `StatusHandler` never consults `repository_name`, this authentication boundary is not carried into the mutation, letting the attacker mutate any stack whose commit table happens to contain the same `sha`.

Attack flow:
1. Attacker onboards `attacker/repo` as a Shipit stack (this is a documented, unprivileged onboarding action available to any GitHub repo owner).
2. Attacker pushes a commit whose SHA equals a commit already present in `victim-org/victim-repo`'s stack (trivially achievable with the empty-tree SHA, which is identical in every git repo, or by cherry-picking an identical tree/parent/timestamp to force a SHA collision).
3. Attacker POSTs `X-Github-Event: status` with `{state: 'success', sha: SHARED_SHA, repository: {full_name: 'attacker/repo'}}`, signed with `attacker/repo`'s own valid `webhook_secret`.
4. Signature verification succeeds (it's a legitimately signed webhook for `attacker/repo`).
5. `StatusHandler#process` finds all `Commit` rows with that `sha`, including the victim's, and calls `create_status_from_github!` on each, writing a forged `Status` row tied to `victim_stack`/`victim_commit`.

### Impact Explanation
The attacker can write arbitrary status data (`state`, `context`, `description`, `target_url`) onto a commit in a stack they do not own, using only a webhook signed for their own repository. Because deployability and CI-gating logic (`Commit#deployable?`, `blocked?`, continuous delivery scheduling) reads from `statuses`/`status`, a forged `success` status can help unblock or mislead deploy gating on the victim stack, and `add_status` also emits `Hook.emit(:commit_status, ...)`/`:deployable_status` and can call `stack.schedule_merges`, potentially triggering downstream automation (merges) tied to the victim stack. This is a cross-tenant integrity break — a payload authenticated for one repository mutates another repository's stack/commit data — matching the "payload for one repository mutating another's stack, commit, task or team" Critical category. It is repeatable against any stack/repository pair that shares a colliding SHA (trivial and repeatable via the well-known empty-tree SHA, which every git repository contains and can trigger a `status` event for).

### Likelihood Explanation
Preconditions: the attacker needs a Shipit stack onboarded for a repo they control (a documented, unprivileged, self-service action) and a commit SHA collision with the target. Empty-tree/empty-commit SHA collisions make this trivial and require no cryptographic SHA-1 collision attack — every git repository contains the same empty-tree object hash, and GitHub will emit a `status` event for it if the attacker sets a commit status on that SHA within their own repo. No Shipit secret, session, or elevated privilege is needed; the attacker only needs their own valid `webhook_secret`, which they receive automatically upon onboarding their own repo. This is low-cost and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to stacks of the authenticated repository, mirroring other handlers' use of `stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or equivalently filter `Commit.where(sha: params.sha)` by `stack: stacks`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook signed for one repository must not create a status on another repository's commit" do
  shared_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee4904' # empty tree SHA

  attacker_stack = shipit_stacks(:shipit)
  attacker_stack.update!(repository: create_repository(owner: 'attacker', name: 'repo'))

  victim_stack = shipit_stacks(:cyclimse) # or a separately seeded stack
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/repo' },
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  refute Shipit::Status.where(stack_id: victim_stack.id, commit_id: victim_commit.id).exists?
end
```
This test currently fails against the existing implementation (the status IS created), demonstrating the cross-repository write; after applying the recommended fix scoping to `stacks`, it passes.
