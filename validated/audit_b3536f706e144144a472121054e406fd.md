### Title
Pull request label named `path` overrides the sanitized `PATH` in `Command#unbundled_env`, enabling RCE - (File: lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every pull-request label name, upcased, into the environment hash with no key allowlist, so an unprivileged fork PR can inject a `PATH` key. `Command#unbundled_env` merges the caller-supplied `@env` *after* it computes the safe base `PATH`, so this attacker-controlled key silently replaces the safe `PATH` for every command Shipit spawns for that stack, including checkout/build/deploy/task steps whose working directory is the attacker's own fork checkout.

### Finding Description
The invariant that should hold is: `Command#unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"` for every task/deploy Command, i.e. `PATH` must never be attacker-influenced.

Trace:
- `ReviewStack#env` [1](#0-0)  merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into the stack env with **no allowlist on the resulting keys**.
- `LabelCapturingHandler#capture_labels` persists label names taken verbatim from the unauthenticated webhook payload (`params.pull_request.labels.map(&:name)`) into `pull_request.labels` [2](#0-1) , and this handler runs on `opened`/`labeled`/`unlabeled`/`reopened` events for any active (non-archived) review stack [3](#0-2) . Under `prevent_with_label`, the stack is active/provisioned exactly while the "prevent" label is absent, i.e. the default, attacker-controlled case.
- `TaskCommands#env` (inherited by `DeployCommands`) merges `@stack.env` into the final env hash passed to every `Command.new` for the task [4](#0-3) . This env is used for `install_dependencies`, `perform` (deploy/rollback steps), and it is also the source that later gets merged with `deploy_spec.machine_env` — the `PATH` key from labels survives all subsequent merges because none of them strip or re-fix `PATH`.
- `Command#unbundled_env` computes: `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)` [5](#0-4) . Because `@env` is merged **last**, a `PATH` key present in `@env` (originating from the label) wins over the deliberately constructed safe `PATH`.
- `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` [6](#0-5) , where `@chdir` is the task's working directory — a checkout of the attacker's own fork/PR branch.

Exploit flow: the attacker opens a PR against a repo with `provisioning_behavior=prevent_with_label` (no prevent-label attached, so the review stack is provisioned) and attaches a label literally named `path`. `ReviewStack#env` turns this into `{"PATH" => "true"}`. This key flows unfiltered into every `Command`'s `@env`, and `unbundled_env` lets it override the sanitized `PATH`, producing `PATH=true`. Since the attacker also controls the checked-out working directory contents (it's their fork's branch), they can commit a relative directory literally named `true/` containing executables named after bare commands referenced in `shipit.yml` (e.g. `bundle`, `rake`, dependency/deploy step binaries). When Shipit's steps invoke those bare command names, the shell resolves them via `PATH=true`, a relative directory relative to `chdir`, and executes the attacker's binary instead of the real one — RCE on the Shipit deploy host.

Existing guards do not stop this: `EnvironmentVariables#permit` [7](#0-6)  is only used for shipit.yml-declared deploy/rollback "variables" interpolation, not for the label-derived env hash or for `Command#unbundled_env`. `ExplicitParameters` in the webhook handlers only validates types/shape of `labels[].name` as a `String` [8](#0-7) , not content — any string, including `"path"`, is accepted. There is no webhook signature check visible in the code excerpted, and none of the merges in `TaskCommands#env`/`DeployCommands#env` remove or re-fix a `PATH` key after `@stack.env` is merged in.

### Impact Explanation
An unprivileged fork PR author (no Shipit session, no API token, no GitHub team membership) can achieve remote code execution on the Shipit deploy host during that repository's own review-stack task/deploy/rollback execution, by naming a label `path` and placing a matching relative directory of malicious executables in their fork branch. This is Critical severity (RCE via `Command`/`PTY.spawn`) per the stated impact classes. The blast radius is scoped to the specific review stack/repository whose PR triggers the tainted env (the attacker's own PR and its associated working directory), but it runs with the full privileges of the Shipit deploy host process for that stack (potentially exposing `GITHUB_TOKEN`, deploy secrets, or providing a foothold to pivot to other stacks/repos on the same host).

### Likelihood Explanation
Preconditions: the repository must have review stacks enabled with `provisioning_behavior` of `prevent_with_label` (or `allow_with_label`/`allow_all`, since the label-merge bug is not specific to `prevent_with_label` — any active review stack is affected) so a stack is provisioned for the attacker's PR. The attacker needs only: open a PR from their own fork, add a label named `path` (any GitHub user with write access to their own fork PR can typically add labels to their own PRs, or in `allow_all`/permissive configs no label gymnastics is even needed to get a build), and commit a `true/` directory containing malicious binaries matching bare command names actually used in `shipit.yml`. This requires no secrets and is fully repeatable against any repository configured this way. Feasibility depends on knowing/guessing the bare command names invoked by the target's `shipit.yml` steps (typically discoverable, since `shipit.yml` is often public in the same repo).

### Recommendation
In `Command#unbundled_env`, compute the final `PATH` deterministically last, or strip/ignore any `PATH` key coming from `@env` (and generally validate/allowlist which environment variable names may originate from stack/label-derived env, e.g. via `EnvironmentVariables#permit` with an explicit allowlist) before merging into `unbundled_env`. Additionally, `ReviewStack#env` should not allow pull request label names to inject arbitrary/reserved environment variable keys (`PATH`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, etc.) — apply a denylist/allowlist on the upcased label-derived keys.

### Proof of Concept
```ruby
# test/lib/shipit/command_test.rb (or similar)
test "PATH injected via a pull request label overrides the sanitized PATH" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["path"]

  env = Shipit::TaskCommands.new(shipit_tasks(:shipit_restart).tap { |t| t.stack = stack }).env

  # Broken binding: the injected label-derived PATH survives into the task env
  assert_equal "true", env["PATH"]

  command = Shipit::Command.new("some-command", env: env, chdir: Dir.mktmpdir)

  # This should equal Shipit's sanitized PATH, but instead equals the attacker value
  refute_equal "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}", command.unbundled_env["PATH"]
  assert_equal "true", command.unbundled_env["PATH"]
end
```
This demonstrates the exact broken equality: `Command#unbundled_env['PATH']` should always equal the Shipit-constructed safe path but instead equals attacker-controlled `stack.env['PATH']` derived from an uppercased PR label name.
