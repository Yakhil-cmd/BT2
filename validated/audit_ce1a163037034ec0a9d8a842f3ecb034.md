This confirms the vulnerability. Multi-org `Shipit.github(organization:)` (`lib/shipit.rb:170-181`) selects a `GitHubApp` config keyed strictly by `repository.owner.login`/`organization.login` in `WebhooksController#repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`), and `GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever that org's `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`, `@webhook_secret = @config[:webhook_secret].presence` at line 50). Every event handler, however, resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, and every handler like `push_handler.rb`, `opened_handler.rb`, `labeled_handler.rb`, etc.) with **no re-check that `full_name`'s owner matches `repository_owner`**.

### Title
Webhook org-signature scope is not bound to the repository acted upon, allowing cross-organization webhook forgery when any configured org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-GitHub-App deployment (`docs/setup.md:182-209`), the equality that must hold is: *"organization whose signature was verified" == "organization owning the repository the event mutates"*. `WebhooksController#verify_signature` verifies the payload against the `GitHubApp` selected by `repository.owner.login` alone [1](#0-0) , while every handler independently resolves the acted-upon `Repository` from the unrelated `repository.full_name` field [2](#0-1) . These two fields are never cross-checked.

### Finding Description
`Shipit.github(organization:)` supports per-organization `GitHubApp` configs, each with its own optional `webhook_secret` [3](#0-2) . `GitHubApp#verify_webhook_signature` intentionally treats a blank `webhook_secret` as "always verified": `return true unless webhook_secret` [4](#0-3) , and the docs describe the webhook secret as merely "optional" [5](#0-4) .

The controller picks *which* app/secret to verify against solely from the attacker-controlled `repository.owner.login` (with an `organization.login` fallback) field of the JSON body: `Shipit.github(organization: repository_owner)` [6](#0-5) . Once verification passes (trivially, if that named org has no secret configured), `WebhooksController#create` dispatches the *entire* payload to handlers unchanged [7](#0-6) . Handlers never look at `repository.owner.login` again — they resolve their target exclusively via `Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) , e.g. in `PushHandler#process` [8](#0-7) , `OpenedHandler#repository` [9](#0-8) , `LabeledHandler#repository` [10](#0-9) , and others.

Consequently, in an installation with ≥2 configured GitHub organizations where at least one has no `webhook_secret` set (an explicitly supported, "optional" configuration per the docs), an attacker with no credentials can craft a raw HTTP POST to `/webhooks` where `repository.owner.login` names the unsecured organization (satisfying `verify_signature` unconditionally) while `repository.full_name` names any *other* tracked repository — including one belonging to an organization that *does* have a real `webhook_secret`. The handler acts on that other repository/stack without ever checking that its owner matches the organization that "authenticated" the request.

### Impact Explanation
This breaks the "organization that authenticated" == "repository that is written" binding called out in the rules. Concretely: `push` events trigger `stack.sync_github(expected_head_sha:)` via `GithubSyncJob` for a foreign repository's stacks [8](#0-7) ; `status` events forge commit statuses used by the merge queue; `pull_request` `opened`/`labeled`/`unlabeled`/`reopened` events archive/unarchive review stacks and mutate `PullRequest` records for arbitrary tracked repositories the attacker does not own [11](#0-10) . This can drive unauthorized stack state changes (archive/unarchive, provisioning) and spoofed CI/status signals that downstream merge/deploy logic may rely on — satisfying the "cross-repository writes" / "unauthorized deploy" impact bar, achievable by a completely unauthenticated network attacker as soon as one org in the fleet omits its optional webhook secret.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: the webhook secret is documented as optional [5](#0-4) , multi-org configs are an explicitly documented, supported feature [12](#0-11) , and no code path anywhere cross-validates `repository.owner.login` against `repository.full_name`'s owner before a handler acts. An operator who configures several orgs and leaves the secret blank on even one of them (e.g. a low-traffic/test org) exposes every other org's repositories to forged events.

### Recommendation
In `WebhooksController#verify_signature`, after selecting the `GitHubApp` by `repository_owner`, also assert that `repository_owner` matches the owner segment of `repository.full_name` (and of `organization.login` for org-level events) before dispatching to handlers; reject with `422` on mismatch. Additionally, consider treating a missing `webhook_secret` as a hard misconfiguration (fail closed) rather than "always verified," at least when more than one GitHub App/organization is configured.

### Proof of Concept
1. Configure Shipit with two organizations per `docs/setup.md:182-209`: `OrgA` (no `webhook_secret`) and `OrgB` (real `webhook_secret`), both with tracked repositories.
2. POST to `/webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/protected-repo" }
   }
   ```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` → `verify_webhook_signature` returns `true` immediately because `OrgA`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-77`).
4. `PushHandler#process` resolves `stacks` from `repository.full_name = "OrgB/protected-repo"` and triggers `sync_github` for `OrgB`'s stack, even though the request was only "authenticated" for `OrgA` [8](#0-7) .
