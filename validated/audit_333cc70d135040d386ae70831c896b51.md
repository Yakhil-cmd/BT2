### Title
Webhook signature is verified against the payload's claimed organization while the acted-upon repository is derived from a separate, unbound field, allowing cross-organization stack sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GithubApp`/`webhook_secret` to check the HMAC against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) . Handlers, however, resolve which `Repository`/`Stack` to act on using a *different* field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Repository.from_github_repo_name` [2](#0-1) [3](#0-2) . Nothing in the engine enforces that `repository.owner.login` (the value bound into the signature-selection lookup) matches the owner segment of `repository.full_name` (the value bound into the actual stack lookup/write). This breaks the intended equality `organization_that_authenticated == organization_whose_repository_is_written`.

### Finding Description
The whole raw request body is HMAC-signed with the secret configured for one specific GitHub organization in `Shipit.secrets.github`, and `GitHubApp#verify_webhook_signature` only proves that *some* configured organization's secret produced that signature [4](#0-3) . Which organization's secret gets used for that check is picked from `repository.owner.login`/`organization.login` inside the same attacker-supplied JSON body [5](#0-4) .

Once verified, `WebhooksController#create` hands the full parsed payload to every registered handler for the event [6](#0-5) , and `PushHandler` (and other handlers) resolve the target `Stack`s purely from `repository.full_name` [7](#0-6) [2](#0-1) . In a multi-org Shipit deployment (as documented in `docs/setup.md`'s "Using Multiple Github Applications" section, each org has its own `webhook_secret`), an entity who legitimately controls org A's webhook secret (e.g. an org admin who can view/rotate the GitHub App's webhook secret for org A) can craft a `push` payload where `repository.owner.login` = `"orgA"` (so the correct-but-unrelated secret is selected and the signature validates) while `repository.full_name` = `"orgB/target-repo"`. Because the two fields are never cross-checked, the request is routed to `orgB`'s stacks even though it was authenticated using `orgA`'s credentials.

This is directly analogous to the reported bug class: a value used for one accounting/authorization purpose (org secret selection, analogous to the lockup's rebase-sensitive balance snapshot) diverges from the value actually acted upon (the repository/stack written to, analogous to the withdrawable amount), because the code assumes an invariant (owner segment of `full_name` equals `owner.login`) that the untrusted payload does not have to satisfy.

### Impact Explanation
This lets an org-A-scoped actor trigger `GithubSyncJob` (which calls `stack.github_commits`/`stack.github_api` for the org-B stack, using org B's own GitHub App/API credentials as resolved by `Repository#github_app` -> `Shipit.github(organization: owner)`) with an attacker-chosen `expected_head_sha` [8](#0-7) [9](#0-8) . This is a cross-organization interaction: an actor authenticated as org A can force sync/commit-append activity against org B's stack it should have no access to at all, without ever needing org B's webhook secret, API token, or repository write access. Whether this escalates further (e.g., forcing `stack.lock_reverted_commits!`, altering deploy eligibility, or affecting `CacheDeploySpecJob`) depends on org B's actual git history and settings, so I could not fully confirm an end-to-end unauthorized deploy/rollback in the time available — this should be validated experimentally.

### Likelihood Explanation
Requires the engine to be configured with multiple GitHub organizations sharing one Shipit instance (an explicitly supported, documented configuration) and requires the attacker to already hold a legitimate webhook secret for at least one of those organizations. That is a meaningfully lower bar than compromising org B's credentials, but it is not a fully "zero-privilege, single-org" attack, which affects overall exploitability.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler#repository_name`, enforce that the owner segment of `repository.full_name` (or `organization.login`) used to resolve the target `Stack`/`Repository` is identical to the `repository_owner` value used to select the verifying `GithubApp`/secret; reject the webhook (422) on mismatch rather than silently trusting `full_name` as-is.

### Proof of Concept
Could not be fully constructed/validated within the available tools (no request-execution or multi-org fixture environment was available to confirm end-to-end stack takeover); the code paths cited above demonstrate the missing invariant but a live PoC against a two-organization Shipit deployment is recommended to confirm exploitability and blast radius before treating this as fully validated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
