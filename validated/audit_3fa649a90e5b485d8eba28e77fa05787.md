## Title
CCMenu API endpoint bypasses per-token stack scoping, allowing a stack-scoped `ApiClient` to read the deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds every "touched" stack to the authenticated `ApiClient`'s authorized scope by resolving `stack` through the `stacks` helper, which filters by `current_api_client.stack_id` when the client is scoped to a single stack. [1](#0-0)  `Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` relation, ignoring the `ApiClient`'s `stack_id` restriction entirely. [2](#0-1) 

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` and `stack_id`. [3](#0-2)  The intended binding is: `stack a token authorises == stack the controller touches`. This is enforced in `BaseController#stacks`, which restricts the queryable set of stacks to `Stack.where(id: current_api_client.stack_id)` whenever the client has a `stack_id`, and `BaseController#stack` builds on that scoped relation. [1](#0-0) 

`Api::CCMenuController` inherits from `BaseController` and enforces only the generic `read:stack` permission check via `require_permission :read, :stack`. [4](#0-3)  Crucially, it redefines `stack` to bypass the scoped `stacks` helper entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [5](#0-4) 

Since `Stack.from_param!` queries across all stacks rather than the scoped relation, an `ApiClient` created with `stack_id` set to stack A (e.g., via `CCMenuUrlController`, which mints exactly this kind of scoped, `read:stack`-only client) [6](#0-5)  can still successfully call `GET /api/1/stacks/:stack_id/ccmenu` for an arbitrary stack B it was never authorized for, because `require_permission!` only checks the presence of the `read:stack` string in `permissions` and never that `stack.id == current_api_client.stack_id`. [7](#0-6) 

This mirrors the audited bug class: a value that authorization logic is supposed to bind/limit (here, the stack a token is scoped to) is checked in one code path (`BaseController#stacks`/`#stack`) but silently diverges in another path (`CCMenuController#stack`) that acts on a different, unchecked value (`params[:stack_id]` resolved against the full `Stack` table).

### Impact Explanation
This allows unauthorized, authenticated read access to another stack's deploy/task state (last deploy id, running status, timestamps) rendered in the CCMenu XML, which is exactly the "unauthenticated/unauthorized read of stack state" class called out as High severity. Every `ApiClient` scoped to any single stack (a common, low-privilege pattern used specifically to hand out narrowly-scoped tokens, e.g. via `CCMenuUrlController`) can be used to enumerate and read the build/deploy status of every other stack in the Shipit instance, defeating the purpose of stack-scoping tokens.

### Likelihood Explanation
Any holder of a valid, stack-scoped API token (the least-privileged, most commonly distributed type of token, since `CCMenuUrlController` mints them automatically for CI-status badges) can trivially exploit this by requesting `/api/1/stacks/<other-stack>/ccmenu` with their own token and an arbitrary `stack_id` path parameter. No special conditions or races are required.

### Recommendation
Make `Api::CCMenuController#stack` use the scoped `stacks` relation from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the token's authorized stack scope is always enforced consistently across all API controllers.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` (this is exactly what `CCMenuUrlController#client` creates for any logged-in user requesting a CCMenu URL for Stack A).
2. Using that client's `authentication_token`, issue `GET /api/1/stacks/<stack-B-id>/ccmenu?token=<tokenA>` where Stack B is a different, unrelated stack.
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), and `require_permission :read, :stack` only checks the string permission (not stack identity) (`app/models/shipit/api_client.rb:38-45`), the request succeeds and returns Stack B's deploy status, even though the token was only ever authorized for Stack A.
