### Title
Cross-organization commit-status forgery bypasses CI gating for queued merges - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the repository/organization that the webhook was signed for. Because git commit SHAs are content-addressed and identical across forks/mirrors, an attacker who owns a repository inside *any* organization onboarded to this Shipit instance can produce a commit with the same SHA as a victim's queued PR head, receive a genuinely-signed status webhook from GitHub for their own org, and have that status attached to the victim's `Commit`, satisfying `MergeRequest#all_status_checks_passed?` and triggering `MergeRequest#merge!` with the victim organization's own GitHub token.

### Finding Description
The claimed-safe binding is: `signing_org(webhook) == owning_org(commit_updated)`. Tracing the code shows this is never enforced.

`WebhooksController#verify_signature` correctly authenticates the webhook against the org named in the payload's `repository.owner.login`/`organization.login` via `Shipit.github(organization: repository_owner)` [1](#0-0) . That only proves the payload really came from that org's installed GitHub App — it says nothing about which `Commit` rows in the database that status is allowed to touch.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This lookup is global across the entire Shipit installation — it is not scoped by `stack_id`, `repository`, or the `repository_owner` that was just verified. The `commits` table even enforces `sha`+`stack_id` uniqueness rather than global `sha` uniqueness [3](#0-2) , meaning the schema explicitly anticipates the same SHA existing under multiple stacks/organizations — yet `StatusHandler` does not filter on it.

Downstream, `MergeRequest#all_status_checks_passed?` and `#any_status_checks_failed?` read directly off `head.statuses_and_check_runs` [4](#0-3) , and `ProcessMergeRequestsJob` calls `merge!` once that check passes [5](#0-4) . `MergeRequest#merge!` then calls `stack.github_api.merge_pull_request(...)` [6](#0-5) , where `stack.github_api`/`stack.github_app` resolve to `Shipit.github(organization: repository.owner)` — the **victim** organization's token, not the attacker's [7](#0-6) .

Exploit flow: attacker forks or otherwise reproduces a byte-identical commit (same tree, parents, author/committer timestamps and message — trivial for a fork of an existing public commit, e.g. a shared upstream commit or a PR base commit that both org's repos already contain) inside a repository they control within any org that has the Shipit GitHub App installed. Attacker sets a commit status (success) on that commit via GitHub's normal API for their own repo — GitHub signs and delivers this webhook validly for that org. `verify_signature` passes because the signature genuinely matches that org's secret. `StatusHandler#process` then finds the *victim's* `Commit` row (same SHA, different stack/org) and writes the forged "success" status onto it via `create_status_from_github!`, all without validating that the payload's `repository` matches the commit's stack repository.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, the `ExplicitParameters` schema on `StatusHandler`) check repository/stack ownership of the target commit — they only validate the shape of the payload and the authenticity of the sending org, not the relationship between the sending org and the record being mutated.

### Impact Explanation
A forged, cross-organization CI signal can flip `MergeRequest#all_status_checks_passed?` to true for a PR in an org the attacker never authenticated to, causing `ProcessMergeRequestsJob` to invoke `merge_request.merge!`, which calls `stack.github_api.merge_pull_request` using the **victim** organization's own GitHub App token [8](#0-7) . This is an unauthorized merge executed with a credential belonging to a party (the victim org) that never validated the CI signal used to justify it — the attack payload for one repository is mutating merge-eligibility state (and ultimately triggering a privileged GitHub API call) for a different, victim repository/stack. This is repeatable against any stack whose head commit SHA the attacker can reproduce, and the blast radius spans every stack in a multi-tenant Shipit deployment sharing the same install. It matches the Critical category "a payload for one repository mutating another's stack/commit" and "an unauthorized ... merge."

### Likelihood Explanation
Preconditions: `merge_queue_enabled` on the victim stack, a `MergeRequest` already `pending` and not stale/conflicting (i.e., someone with normal Shipit merge-request privileges already queued the PR) [9](#0-8) ; the attacker must control a repository inside an organization that already has the Shipit GitHub App installed (this instance's `Shipit.github_organizations` list — a real precondition, satisfiable in any genuinely multi-tenant Shipit deployment, which this engine explicitly supports per `lib/shipit.rb`'s multi-org config and `secrets.development.shopify.yml`) [10](#0-9) ; and the attacker must reproduce an identical commit SHA, which is trivial for shared/forked history. No Shipit secrets, sessions, or API tokens are required — only ordinary GitHub repository control within an onboarded org. It is fully repeatable per target commit/PR.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `CheckSuiteHandler`/other webhook handlers) to the repository that was authenticated in `verify_signature`, e.g. join through `Stack`/`Repository` and filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: repository_owner, name: repo_name })`, so a status can only be attached to commits belonging to stacks whose repository matches the webhook's verified organization/repo.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_cross_org_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossOrgTest < ActiveSupport::TestCase
        test "a status signed for org B is applied to a commit owned by org A's stack" do
          victim_stack = shipit_stacks(:shipit) # owned by org "shopify" per fixtures
          shared_sha = victim_stack.commits.create!(
            sha: 'deadbeef' * 5,
            author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now, message: 'shared commit'
          )

          # Simulate a webhook whose signature is verified against a DIFFERENT org
          # (verify_signature already passed in the controller because it matched
          # attacker_org's own webhook secret -- StatusHandler itself never checks
          # repository_owner at all).
          params = ExplicitParameters::Parameters.new(
            sha: shared_sha.sha, state: 'success', context: 'ci/attacker',
            description: nil, target_url: nil, created_at: Time.now.to_s
          )

          assert_difference -> { shared_sha.statuses.count }, 1 do
            StatusHandler.new(params).process
          end

          status = shared_sha.statuses.last
          assert_equal 'success', status.state
          # Binding under test: the org that authenticated the webhook (attacker_org)
          # is never equal to victim_stack.repository.owner ("shopify"), yet the
          # status was still written onto victim_stack's commit.
          assert_not_equal 'attacker_org', victim_stack.repository.owner
        end

        test "forged status enables merge! using the victim org's own github token" do
          merge_request = shipit_merge_requests(:cocoapods) # pending, mergeable
          merge_request.head.statuses.create!(stack: merge_request.stack, state: 'success', context: 'ci/attacker')

          merge_request.stack.github_api.expects(:merge_pull_request).with(
            merge_request.stack.github_repo_name, merge_request.number, anything,
            sha: merge_request.head.sha, commit_message: 'Merged by Shipit',
            merge_method: merge_request.stack.merge_method
          ).returns(true)

          assert_predicate merge_request, :all_status_checks_passed?
          assert merge_request.merge!
        end
      end
    end
  end
end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
