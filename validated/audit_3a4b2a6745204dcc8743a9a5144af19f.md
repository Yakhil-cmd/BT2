## Title
Repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook for one repository poison CI status on another repository's commit/stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`StatusHandler#process` resolves the target commit(s) purely by `sha`, with no repository/stack scoping, unlike every other webhook handler in the codebase (which use the `Handler#stacks` helper scoped via `Repository.from_github_repo_name(repository_name)`). Because GitHub SHAs are shared identically across forks, an attacker who owns a fork of a victim repository can send a `status` webhook for their own fork - signed with their own valid webhook secret - carrying a SHA that also exists in the victim's tracked repository, causing `Commit#create_status_from_github!` to write a status onto the victim's commit and trigger `stack.schedule_merges`.

## Finding Description
The broken binding, stated explicitly:

`authenticated_repository (payload.repository.full_name / repository_owner used by WebhooksController#verify_signature)` **should equal** `commit.stack.repository (the repository that owns the Commit record matched by sha)`.

In `StatusHandler#process`, this equality is never checked: [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, unscoped query across every stack/repository tracked by the Shipit instance. Contrast this with the base `Handler` class's `stacks` helper, which every other handler (pull_request handlers) uses to scope work to the repository named in the payload: [2](#0-1) 

`WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App/webhook secret belonging to `repository_owner` (the org in the payload) - it says nothing about which specific repository/commit the payload's `sha` is allowed to reference: [3](#0-2) 

Root cause: git SHAs are content-addressed and identical across forks that share history. If a victim repository A is forked by the attacker to repository B (a routine, unprivileged GitHub action), unmodified commits (e.g., the PR's base commit, or any commit not yet diverged) have the exact same SHA in both A and B. The attacker:
1. Forks repo A to repo B (their own repository, with their own legitimate webhook secret configured by GitHub/Shipit for that org).
2. Identifies a commit SHA that is queued in Shipit's merge queue for repo A (e.g., visible via the PR's head SHA, which is public) and a required check context for repo A (context strings are conventional/public, e.g. `ci/circleci`, `continuous-integration/travis-ci/push`, or discoverable from the PR's checks UI).
3. Sends `POST /webhooks` for repo B with `X-Github-Event: status`, a valid signature for repo B's org, and body `{ sha: <shared-sha>, state: 'success', context: '<repo-A-required-context>', repository: {...B...} }`.
4. `verify_signature` passes because it only validates against repo B's org secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the `Commit` record belonging to repo A's stack (not B's, since B may not even be tracked by Shipit).
6. `Commit#create_status_from_github!` → `add_status` writes the forged `success` status, and because the state transitioned, `stack.schedule_merges` fires for **stack A** (`app/models/shipit/commit.rb:383`).
7. `ProcessMergeRequestsJob` for stack A runs, `MergeRequest#all_status_checks_passed?` (`app/models/shipit/merge_request.rb:193-197`) now sees the forged required status as satisfied, and if other conditions hold, `merge_request.merge!` executes a real GitHub merge on repo A.

No existing guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) checks that the resolved `Commit`'s `stack.repository` matches the webhook's `repository` payload.

## Impact Explanation
An attacker who controls only their own fork/repository can inject a forged CI status onto a **different** repository's commit and stack, mutating state (`Status` records, `Commit` status, potentially triggering `stack.schedule_merges` → `ProcessMergeRequestsJob` → `MergeRequest#merge!`) that was never authenticated by that victim repository's webhook secret. This matches the Critical impact category: "a payload for one repository mutating another's stack, commit... or an unauthorized deploy, rollback or merge." It is repeatable against any repository whose commits are reachable (shared history via fork, or any other means SHAs coincide), and any stack tracking that repository.

## Likelihood Explanation
Preconditions are low-cost and fully within an "unprivileged attacker" capability set per the rules: fork a public repo (trivial, standard GitHub action), configure a webhook on the fork (or rely on GitHub App installation automatically covering the fork depending on Shipit/GitHub App setup), and send one `POST /webhooks` request with a SHA shared by history and a guessed/observed required status context. The main variable is knowing/guessing the exact required context string, which is often public (visible in the PR checks UI or `shipit.yml`/README conventions) or can be brute-forced with a small set of common CI context names. This is significantly more practical than a SHA-1 collision - it just relies on ordinary fork mechanics sharing identical commit objects.

## Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks owned by the webhook's authenticated repository, mirroring the pattern used by other handlers via `Handler#stacks`, e.g. resolve `stacks` from `repository_name` and restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or equivalent join), rejecting/ignoring commits whose owning stack's repository doesn't match the payload's repository.

## Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or via `WebhooksControllerTest`), no live GitHub:

1. Create two stacks/repositories, `stack_a` (repository "victim/repo") and `stack_b` (repository "attacker/repo"), each with a `Commit` sharing the same `sha` value (simulating a forked, shared-history commit).
2. Assert the binding before: `commit_a.stack.repository.full_name != commit_b.stack.repository.full_name` (they are different repositories) yet share the same `sha`.
3. Stub `GithubHook#verify_signature` (or the app-level signature check) to return true only for "attacker/repo"'s org, simulating a legitimately signed webhook from the attacker's own repo.
4. POST a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha = <shared sha>`, `state: "success"`, `context:` matching `stack_a`'s configured required status.
5. Assert `commit_a.reload.status.state == "success"` even though the authenticated repository was "attacker/repo", proving the equality `authenticated_repository == commit.stack.repository` is violated.
6. Assert `ProcessMergeRequestsJob` was enqueued with `stack_a` (`assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_a])`), demonstrating downstream merge-queue processing was triggered for the victim stack based solely on the attacker-controlled webhook.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
