### Title
Webhook Signature Verified Against `repository.owner.login` But Event Handlers Act On The Unbound `repository.full_name` Field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to validate the HMAC against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, every event handler (`PushHandler`, the `PullRequest::*Handler`s, `CheckSuiteHandler`, etc.) resolves the target `Repository`/`Stack` using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. Nothing in the request pipeline verifies that `repository.owner.login` (the field the signature check keys off) and `repository.full_name` (the field the write path acts on) refer to the same repository. This is the same class of bug as the Vault report: a value is validated/partially consumed on one field (`restToReimbourse` vs. `amountDeposited`), but the code then acts unconditionally on a different, un-reconciled piece of state (`deposit.amount = 0`) — here, a value is authenticated on one field (`owner.login`) while the state-mutating action is driven by a sibling field (`full_name`) that was never bound to it by the signature check.

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to fetch the per-organization webhook secret, then checks `X-Hub-Signature` with `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`). [1](#0-0) [2](#0-1) 
- Shipit explicitly supports multiple GitHub organizations, each presumably configured with its own webhook secret (`CHANGELOG.md:132` "Support multiple GitHub organisations (#1151)"). [3](#0-2) 
- Every handler's `stacks` lookup, however, is keyed on `repository.full_name`, not on the organization that was authenticated: [4](#0-3) 
- `Repository.from_github_repo_name` blindly splits `owner/name` out of that field and looks up any repository row regardless of which organization's secret validated the request: [5](#0-4) 
- `PushHandler` (and the pull-request handlers) act on the resolved stack/repository directly, e.g. triggering a GitHub sync: [6](#0-5) 

Because the HMAC covers the whole raw body, an attacker cannot forge a webhook for an organization whose secret they don't possess. But in a multi-organization Shipit deployment, an attacker who legitimately controls (or has push access producing real webhook deliveries from) **one** onboarded organization's secret can set `repository.owner.login` to their own org (so `verify_signature` authenticates against their own known-good secret) while independently setting `repository.full_name` to any other tracked `owner/repo` string, since nothing ties the two fields together after the signature check. The signature only proves "this body was signed by organization X's secret"; it does not prove "the repository referenced inside this body belongs to organization X."

### Impact Explanation
This breaks the intended trust binding "organization authenticated == repository written," which the rules explicitly call out. A holder of one organization's webhook secret in a multi-tenant Shipit install can drive `GithubSyncJob`/`RefreshCheckRunsJob`/pull-request review-stack creation, closing, labeling, and merge-status logic for a **different** organization's stacks that they have no legitimate relationship with, e.g. forcing an out-of-band `sync_github` to run against an arbitrary stack (`Stack#sync_github`, invoked from `PushHandler#process`), or creating/mutating review stacks via `ReviewStackAdapter` for repos they don't own. This is a cross-organization write into stack state driven by an unauthenticated correlation between two payload fields — matching the High/Critical "cross-repository writes" impact bucket.

### Likelihood Explanation
Requires the target Shipit instance to be configured with multiple GitHub organizations (a documented, supported configuration) and requires the attacker to be able to produce a validly-signed webhook body for at least one of those organizations (e.g. by being the administrator of a smaller/less-trusted org that is also onboarded to the same Shipit instance, or by replaying/crafting deliveries once they know that org's secret through legitimate access to its GitHub App settings). Given that, forging the `repository.full_name` field to target another organization's repository requires no further privilege — it's a single JSON field with no additional validation, format constraint tying it to `owner.login`.

### Recommendation
In `WebhooksController#verify_signature`, after resolving the organization used to fetch the webhook secret, also require that `payload.dig('repository', 'full_name')` (when present) begins with `"#{repository_owner}/"`, rejecting (422) any payload where the two disagree. Equivalently, have `Handler#repository_name`/`Repository.from_github_repo_name` be passed the already-authenticated `repository_owner` and cross-check it against the owner segment parsed out of `full_name` before doing the lookup.

### Proof of Concept
1. Shipit instance is configured with two organizations, `org-a` (attacker-controlled, webhook secret known to attacker) and `org-b` (victim, has a tracked stack e.g. `org-b/prod-service`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/prod-service" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` using the secret they legitimately know for `org-a`.
4. `POST /webhooks` with `X-Github-Event: push` — `verify_signature` resolves `repository_owner == "org-a"`, fetches `org-a`'s secret via `Shipit.github(organization: "org-a")`, and the HMAC check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`, `lib/shipit/github_app.rb:76-83`).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` helper resolves `Repository.from_github_repo_name("org-b/prod-service")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and calls `stack.sync_github(expected_head_sha: ...)` on the victim's `org-b/prod-service` stack — an action the attacker was never authorized to trigger.
