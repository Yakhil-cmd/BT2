### Title
Cross-organization webhook forgery via mismatched signature-verification and repository-lookup fields - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate an incoming webhook against using the `repository.owner.login` (or `organization.login`) field of the *attacker-supplied, unauthenticated* JSON body, while the event handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used to resolve the target `Repository`/`Stack`) read a *different* field, `repository.full_name`. Because both fields live in the same unauthenticated JSON body and nothing enforces that they agree, an attacker who knows (or controls) the webhook secret for **any one** organization configured on the Shipit instance can craft a signed payload whose `repository.owner.login` matches that known organization (so signature verification passes) while `repository.full_name` points at a completely different, victim organization's repository, causing handlers to execute writes against that victim's stacks.

### Finding Description
`verify_signature` in [1](#0-0)  computes:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

where `repository_owner` is [2](#0-1) :
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This picks the `GitHubApp` instance (and thus the `webhook_secret` used for HMAC comparison) based on a value that is part of the same untrusted body being verified. `Shipit.github_app_config` looks this org name up in the multi-org `secrets.github` map, as documented in the "Using Multiple Github Applications" section of the setup docs [3](#0-2) .

Once the signature check passes, `create` dispatches the *entire* payload to handlers [4](#0-3) . Handlers resolve the target repository/stack independently, from a different key in the same payload:

```ruby
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [5](#0-4) 

`PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the target branch [6](#0-5) , which is precisely the trigger the test suite documents (`GithubSyncJob`) as fetching/syncing new commits for continuous delivery [7](#0-6) .

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login)` == `repository whose Stacks are written by the handler (repository.full_name)`.

Before the attacker's request: for legitimate GitHub-originated webhooks, both fields are populated consistently by GitHub itself, so the org that "owns" the signing secret is always the org whose repository is acted upon.

After the attacker's crafted request: the attacker controls both fields independently in the raw JSON body. They set `repository.owner.login` to an organization for which they can compute a valid HMAC (either because they know that org's `webhook_secret`, or because that org has no `webhook_secret` configured at all, in which case `verify_webhook_signature` unconditionally `return true unless webhook_secret` [8](#0-7) ), while setting `repository.full_name` to `victim-org/victim-repo`. The signature check authenticates "org A", but the handler acts on "org B"'s stack.

### Impact Explanation
This breaks the deployment-trust binding between the GitHub organization whose credentials are checked and the repository whose Shipit state is mutated — an unauthenticated attacker (with respect to the victim org) can trigger `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and `MembershipHandler` behaviors against a target stack they do not control the GitHub webhook secret for. Concretely this can force `Stack#sync_github`/`GithubSyncJob` runs, inject fabricated commit statuses via `StatusHandler` (`Commit#create_status_from_github!`), or refresh check runs, any of which can influence whether a commit is considered deployable and thereby the continuous-deployment/merge pipeline of a victim's stack — an unauthorized action on a repository the attacker was never authenticated against. This corresponds to the Critical bucket ("cross-repository writes" / "an unauthorized deploy") in the campaign's impact list.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance to be configured with the multi-organization `github:` schema serving more than one organization (documented as a supported configuration in `docs/setup.md`), and (2) the attacker to know a valid `webhook_secret` for at least one hosted organization — which is plausible if that organization intentionally omits a `webhook_secret` (documented as optional in setup docs) or if the attacker is a legitimate member/integrator of one of the several orgs but targets another org's stacks. The webhook endpoint (`/webhooks`) is unauthenticated by design (it must be reachable by GitHub), so no session, `ApiClient` token, or repository write access is required — the entire attack surface is a single crafted, self-consistent-looking HTTP POST.

### Recommendation
After signature verification, validate that `repository.owner.login` (the identity used to select the verifying `webhook_secret`) matches the owner segment of `repository.full_name` used by handlers to resolve `Repository`/`Stack`, rejecting the request (422) on mismatch. Alternatively, derive `repository_owner` from `repository.full_name` itself (single source of truth) rather than from a separate `owner.login` field, so the value used for authentication is identical to the value used to select the object being written.

### Proof of Concept
Assume a multi-org Shipit instance configured for `orgA` (attacker knows `orgA`'s `webhook_secret`, e.g. it was left blank) and `orgB` (victim, hosts a Shipit stack for `orgB/victim-repo`).

```http
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<valid-for-orgA-secret-or-blank>

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```

1. `WebhooksController#verify_signature` reads `repository_owner` = `"orgA"`, loads `Shipit.github(organization: "orgA")`, and verifies the signature against `orgA`'s secret — which the attacker knows/controls — so verification succeeds.
2. `create` dispatches `params` to `Handlers::PushHandler`, which computes `repository_name` from `repository.full_name` = `"orgB/victim-repo"`, resolves `Repository.from_github_repo_name("orgB/victim-repo")`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `orgB`'s stack — a write triggered by a payload never actually signed by `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
