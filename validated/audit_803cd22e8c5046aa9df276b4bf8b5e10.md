Based on my research, I found a structural analog of this bug pattern in `polkadot-sdk`'s `ERC20Transactor`, which mirrors the exact same missing "actual transferred amount" check found in the Teller `CollateralManager`.

### Title
XCM `ERC20Transactor` credits/debits the nominal transfer `amount` instead of the actually-moved balance, breaking accounting for fee-on-transfer/deflationary ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens by calling `transferCall` and only check the boolean success return value, never comparing balances before/after the call. This is the same root cause as the reported Teller bug: the code assumes `amount transferred == amount requested`, which is false for any ERC20 implementing a fee-on-transfer, deflationary/rebasing, or otherwise non-standard transfer semantics. [1](#0-0) 

### Finding Description
`withdraw_asset_with_surplus` calls the ERC20 contract's `transfer(checking_address, amount)` to move tokens from the user into the pallet's `TransfersCheckingAccount`, then unconditionally mints an `AssetsInHolding` credit of the full requested `amount` into the XCM holding register based solely on the boolean success of the call: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` out of `TransfersCheckingAccount` to the beneficiary and reports success based only on the boolean return value: [3](#0-2) 

Neither function reads `balanceOf` before/after the transfer to determine the *actual* amount moved. If the underlying ERC20 contract deducts a fee, burns a percentage, or otherwise transfers less than `amount` to the recipient (a pattern explicitly supported by the Solidity ERC20 standard and common in real-world tokens), the XCM holding register's bookkeeping diverges from the `TransfersCheckingAccount`'s real on-chain balance:
- On `withdraw`: holding register believes it holds `amount`, but `TransfersCheckingAccount` only received `amount - fee`. This creates phantom holding-register liquidity backed by fewer real tokens.
- On `deposit`: `TransfersCheckingAccount` is debited the same way, but the beneficiary receives less than `amount`, while any later accounting that assumed `amount` was delivered (e.g. XCM instructions downstream, or invariant checks elsewhere) is now wrong.

This is structurally identical to the reported bug's missing "before/after balance delta" check around `transferFrom`, just moved into a different subsystem (XCM `TransactAsset` for ERC20-backed assets instead of Solidity loan collateral).

`ERC20Transactor` is wired into a real Asset Hub XCM configuration as an `AssetTransactor`: [4](#0-3) 
(I confirmed references to `ERC20Transactor` in `asset-hub-westend/src/xcm_config.rs`, but I could not fully verify from the indexed content how the `Matcher: MatchesFungibles<H160, u128>` type derives the asset `Location`/contract address, i.e. whether it is a permissionlessly-derived mapping from any deployed `pallet-revive` contract address, or gated behind a governance-curated asset registry. This distinction determines whether an attacker can trivially deploy their own fee-on-transfer ERC20 contract and target it via ordinary XCM `WithdrawAsset`/`DepositAsset`/reserve-transfer instructions, or whether only pre-vetted tokens are reachable.)

### Impact Explanation
If the asset/contract mapping is permissionless (attacker can deploy an arbitrary `pallet-revive` ERC20 contract and reference it as an XCM fungible asset), the impact is a genuine accounting break: the holding register/`TransfersCheckingAccount` balance can be permanently inflated relative to real token backing, or downstream XCM steps (e.g. subsequent `DepositAsset`, `BuyExecution`, refunds) can operate on amounts that were never actually received, leading to loss of funds for other holders of the same `TransfersCheckingAccount`-pooled asset over time. If instead only governance/asset-manager-registered tokens can reach this transactor, the severity is reduced to a functional/DoS issue (transfers of such tokens silently under-fulfill) rather than a cross-user fund-safety issue.

### Likelihood Explanation
Likelihood depends entirely on the unresolved gating question above. I could not confirm from the available index whether arbitrary attacker-deployed ERC20 contracts can be targeted without a privileged registration step. Fee-on-transfer/deflationary ERC20 patterns are common and would trivially trigger the mismatch if reachable.

### Recommendation
Read the `TransfersCheckingAccount`'s (or beneficiary's) `balanceOf` before and after the `transfer`/`transferFrom` call in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, and use the observed balance delta — not the requested `amount` — when constructing the `AssetsInHolding` credit or reporting success, mirroring the fix pattern recommended in the source report.

### Proof of Concept
No PoC was executed. I did not have terminal/build access, and I could not verify the exact `Matcher`/asset-registration wiring in `asset-hub-westend`'s `xcm_config.rs` needed to construct a concrete, non-privileged reproduction path (deploy a fee-on-transfer `pallet-revive` contract → reference it via XCM `WithdrawAsset`/`DepositAsset` → observe holding-register vs. `TransfersCheckingAccount` balance mismatch). This finding should be treated as a code-pattern analog requiring further investigation into the asset-registration gating before being escalated with certainty as an in-scope, unprivileged Critical/High-severity bug.
