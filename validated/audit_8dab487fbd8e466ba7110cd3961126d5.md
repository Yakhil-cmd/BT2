### Title
Zero trade/creator fee configuration permanently breaks `swap_base_input`/`swap_base_output` via a spurious 0/0 division in `Fees::split_creator_fee` - (File: `programs/cp-swap/src/curve/fees.rs`)

### Summary
When an `AmmConfig`'s `trade_fee_rate` is set to `0` (a legitimate, admin-reachable configuration for a "zero-fee" pool) while `creator_fee_rate` is also `0` (the default) and the pool's `creator_fee_on` setting causes `is_creator_fee_on_input` to be `true` for a given trade direction, every subsequent swap in that direction permanently fails with `ErrorCode::ZeroTradingTokens`, even though the fee amount involved is trivially zero. This mirrors the reported bug class: an admin-controlled configuration parameter reaching `0` silently breaks a core, unprivileged-user-reachable function (here, swap) rather than the intended "no fee" behavior.

### Finding Description
`Fees::split_creator_fee` divides by `trade_fee_rate + creator_fee_rate`: [1](#0-0) 

and the shared helper `floor_div` explicitly guards against a zero denominator by returning `None`: [2](#0-1) 

In `CurveCalculator::swap_base_input`, when `is_creator_fee_on_input` is `true`, the code first computes `total_fee` for `trade_fee_rate + creator_fee_rate` and then unconditionally calls `split_creator_fee(total_fee, trade_fee_rate, creator_fee_rate)`: [3](#0-2) 

If both `trade_fee_rate` and `creator_fee_rate` are `0` (a valid "no fee" configuration reachable by `update_amm_config` with `param = 0`, which only asserts `trade_fee_rate + creator_fee_rate < FEE_RATE_DENOMINATOR_VALUE`, i.e. it does not forbid the sum being `0`): [4](#0-3) 

then `total_fee` is `0`, and `split_creator_fee(0, 0, 0)` divides `0/0` — hitting the `fee_denominator == 0` guard and returning `None`. This `None` propagates up through `swap_base_input`'s `?` operator, causing the whole `CurveCalculator::swap_base_input` call to return `None`. The instruction handler converts this into a hard error: [5](#0-4) 

The same pattern exists in `swap_base_output` via the same `split_creator_fee` call: [6](#0-5) 

Whether `is_creator_fee_on_input` is `true` for a given swap direction is determined purely by the pool's fixed `creator_fee_on` setting and the trade direction, independent of the fee rates: [7](#0-6) 

So any pool created with `creator_fee_on` covering a direction (`BothToken`, `OnlyToken0`, or `OnlyToken1`) whose `AmmConfig` is later updated (or created) with `trade_fee_rate = 0` and default `creator_fee_rate = 0` will have that swap direction permanently revert for every unprivileged caller, purely due to the spurious `0/0` division rather than any real fee-calculation need (the correct result of `creator_fee` in this case is trivially `0`).

### Impact Explanation
This is a config-driven Denial-of-Service of the core `swap_base_input`/`swap_base_output` instructions, analogous to the referenced report where a config value reaching its "empty"/default state (`0`) breaks a core function that unprivileged users rely on, rather than a real precondition-based revert. Because the transfer of tokens happens after the `CurveCalculator` call, no direct fund loss occurs and LP withdrawals/deposits remain unaffected, but the affected trade direction becomes completely unusable for as long as the zero-fee configuration persists on that `AmmConfig`, impacting every pool using it.

### Likelihood Explanation
Zero-fee configurations are a realistic and normal administrative choice (e.g. promotional zero-trade-fee pools), and the assertions in `update_amm_config`/`create_amm_config` never forbid `trade_fee_rate + creator_fee_rate == 0`. Combined with a pool's fixed `creator_fee_on` setting selecting a direction where `is_creator_fee_on_input` is `true`, this condition is easy to reach without any malicious intent, making it a plausible operational hazard rather than a purely theoretical edge case.

### Recommendation
In `Fees::split_creator_fee` (and equivalently in the callers), short-circuit and return `Some(0)` when `total_fee == 0` (or when `trade_fee_rate + creator_fee_rate == 0`) instead of relying on the generic `floor_div` zero-denominator guard to reject the operation. This avoids treating the legitimate "no fee" case as an error.

### Proof of Concept
1. Create an `AmmConfig` and a pool with `creator_fee_on = CreatorFeeOn::BothToken` (or the variant matching the intended swap direction).
2. Call `update_amm_config` with `param = 0, value = 0` to set `trade_fee_rate = 0` (allowed by the assertion `trade_fee_rate + creator_fee_rate < FEE_RATE_DENOMINATOR_VALUE`, satisfied since `creator_fee_rate` defaults to `0`).
3. Any unprivileged user calls `swap_base_input` (or `swap_base_output`) in the direction where `is_creator_fee_on_input` is `true`.
4. `CurveCalculator::swap_base_input` computes `total_fee = 0`, then calls `Fees::split_creator_fee(0, 0, 0)`, hitting `floor_div`'s `fee_denominator == 0` check and returning `None`.
5. The swap instruction converts this to `ErrorCode::ZeroTradingTokens`, and the transaction reverts — permanently, for every subsequent swap attempt in that direction, until the admin manually changes the fee configuration again.

/// Helper function for calculating swap fee
pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(fee_numerator)?
        .checked_div(fee_denominator)
}

        Ok(match (fee_on, direction) {
