### Title
Webhook signature verification selects the GitHub App/secret using an unverified payload field, decoupling the authenticated organization from the repository actually written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` config (and therefore which `webhook_secret`) to HMAC-verify the request against by reading `repository_owner`, which is parsed straight out of the untrusted, not-yet-verified JSON body. The equality that must hold is: **organization whose secret authenticated the request == organization whose repository/stack the handlers subsequently act on**. Because both sides of that equality are derived from the same attacker-supplied body, an operator running Shipit in multi-organization mode (`Shipit.github(organization: ...)` per-org secrets) can be tricked: a request signed with Org A's `webhook_secret` is accepted as authentic for Org A, but the event handlers invoked in `#create` re-parse `repository.full_name` / other fields from the same body to locate `Stack`/`Commit`/`Repository` records, which are not necessarily scoped back to the same `repository_owner` used for verification.

### Finding Description
`verify_signature` computes `repository_owner` from the raw JSON body before any cryptographic check has occurred: [1](#0-0) 
This value is used to select the `GitHubApp` instance, and thus the `webhook_secret` used for HMAC comparison: [2](#0-1) 
`verify_webhook_signature` performs a straightforward HMAC-SHA1 compare against `webhook_secret` for that organization only: [3](#0-2) 

After the `before_action` passes, `create` re-parses the same raw body and dispatches it to event handlers keyed only by `X-Github-Event`, with no re-binding to the `repository_owner` that was used for signature selection: [4](#0-3) 

Handlers such as `GithubSyncJob` then resolve the target `Stack` from fields inside that same body (e.g. `repository.full_name`) independent of which organization's secret validated the request: [5](#0-4) 

The security-relevant binding — "the org whose key signed the payload" must equal "the org/repository whose state is mutated by the payload" — is never enforced beyond the initial `repository_owner` dig used purely to pick a key. If the fields inside the JSON body describing which repository/stack to act on can be made to diverge from `repository.owner.login` (e.g., a `repository` object without matching `owner.login`, or additional/nested repository references consumed by specific handlers), the request would still pass signature verification under Org A's secret while causing writes against Org B's tracked repositories.

### Impact Explanation
If this divergence is reachable, it allows a party who legitimately holds Org A's `webhook_secret` (a value that, per the docs, is optional and configured per-organization) to forge events that get accepted as valid for—and act upon—Org B's `Stack`s, `Commit`s, `Team`s, or `Membership`s, i.e., a cross-organization / cross-repository write using another organization's authenticated identity. That maps to the engine's Critical bucket ("cross-repository writes / unauthorized deploy") because the trust boundary being crossed is exactly "organization that authenticated" vs. "repository that is written."

### Likelihood Explanation
This requires: (1) a multi-org Shipit deployment with distinct `webhook_secret`s per organization (documented as a supported config, see `config/secrets.development.example.yml` commented multi-org block) and (2) an attacker who already possesses a valid `webhook_secret` for at least one configured organization. Given rule constraints excluding anything requiring possession of secrets/tokens, this scenario is borderline: it does require holding *a* webhook secret (for org A), which is arguably a privileged credential. I was not able to confirm within the available files a concrete handler where the acted-upon repository identifier is structurally distinct from `repository.owner.login` used for `repository_owner` — in all handlers inspected (`GithubSyncJob`, webhook controller test fixtures) the same `repository` object field is reused for both purposes, meaning the two sides of the equality are currently populated from the very same JSON key in every code path I could verify.

### Recommendation
- After signature verification succeeds for organization `O`, re-validate that every repository/organization reference used by the dispatched handler within the same request also resolves to `O` (or to a `Stack`/`Repository` explicitly owned by `O`), rather than trusting the handler to independently re-derive scope from the same untrusted body.
- Consider binding the verified organization into the params passed to `Shipit::Webhooks.for_event(event)` handlers so record lookups can assert `stack.repository.owner == verified_organization`.

### Proof of Concept
Could not construct a concrete, fully-verified PoC: examining `app/controllers/shipit/webhooks_controller.rb`, `app/jobs/shipit/github_sync_job.rb`, and the webhook test fixtures, every code path found derives both the signature-selection organization and the record-lookup repository from the identical `repository` JSON key, so I could not demonstrate the two values actually diverging with the code visible in this index. This finding should be treated as unconfirmed/uncertain pending inspection of all other webhook handlers under `Shipit::Webhooks.handlers` (e.g. `membership`, `pull_request`, `status`, `check_suite` handlers), which were not fully retrievable through the available search tools.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
