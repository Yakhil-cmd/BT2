### Title
Multisig transaction execution can run with an unapproved payload when `abort_if_multisig_payload_mismatch` feature is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::validate_multisig_transaction`, the VM-invoked prologue check for multisig transactions, only cross-checks the caller-supplied `payload` argument against what owners actually approved when the transaction was stored as a hash (`transaction.payload_hash`). When the transaction was instead stored with its full `payload` on-chain (no hash), the byte-for-byte comparison against the approved `stored_payload` is gated behind the `abort_if_multisig_payload_mismatch_enabled` feature flag. If that flag is not enabled, an executor can pass an arbitrary `payload` argument at execution time that differs from what the owners actually voted to approve, and it will pass admission unchecked.

### Finding Description
`validate_multisig_transaction` is the VM-only prologue function invoked both during mempool validation and at the start of transaction execution: [1](#0-0) 

After quorum/timelock checks, the function validates the caller-provided `payload` against what was actually approved: [2](#0-1) 

There are two disjoint code paths here:
1. If `transaction.payload_hash.is_some()` (transaction was created via the hash-only storage path), the provided `payload` is hashed and compared unconditionally — this path is always enforced.
2. If the transaction was instead created with the full payload stored on-chain (`transaction.payload.is_some()`, `payload_hash` is `None`), the byte-equality check against the approved `stored_payload` only runs `if (features::abort_if_multisig_payload_mismatch_enabled() ...)`.

This means the integrity of "what the owners approved" vs. "what actually gets executed" for the full-payload-storage case depends entirely on a feature flag being turned on. Without it, `validate_multisig_transaction` will accept any `payload` byte string the executing owner supplies — including one that encodes a completely different function call/target/arguments than what was voted on by the multisig owners — as long as quorum and timelock checks pass for the *stored* transaction record. Since it is this same `payload` argument that is subsequently decoded and executed as the actual entry-function call (the multisig VM flow decodes and dispatches based on the argument passed into the prologue/execution call, not by re-deriving it from `stored_payload`), owners' approvals for one payload are silently repurposed to authorize execution of a different, unapproved payload.

This mirrors the bug class in the external report: a check that should keep two derived/tracked quantities (`distributed` vs `netVest`, here `payload` vs `stored_payload`) in sync is bypassed under certain conditions, and the "lost" enforcement isn't recovered later — any subsequent code (multisig execution) proceeds using the unvalidated, diverging value.

### Impact Explanation
This breaks the "Authenticator/multisig approval validation accepting the wrong approval set" and "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" invariants. A multisig owner who has enough voting power to trigger execution of a queued transaction (but not necessarily the specific payload other owners approved) could substitute a different payload — e.g., different target module, function, or arguments — and have it execute under the multisig account's authority. This is a state-transition executed under the wrong "approved" authorization set: the on-chain multisig quorum believes it approved payload A, but payload B actually executes with the multisig account's privileges (e.g., moving funds to a different destination or invoking a different function than approved).

### Likelihood Explanation
Likelihood depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active for the target network/deployment. If disabled (e.g., not yet enabled on a given chain, or disabled for compatibility reasons), any transaction created via `create_transaction` (full payload storage rather than `create_transaction_with_hash`) is exposed. No special privileges beyond being one of the multisig owners with quorum-triggering rights are required, and the divergence can be exploited by whichever owner submits the final execution transaction — no cooperation from other owners is needed since the check is simply absent for that code path when the flag is off.

### Recommendation
Do not gate the payload/stored_payload comparison behind a feature flag for the full-payload-storage case; always enforce that `payload == *stored_payload` (or require `payload` to be empty when the stored payload should be used, so there's no way to substitute a different payload) whenever `transaction.payload.is_some()`. If the feature flag was intended purely as a rollout mechanism, ensure it's confirmed enabled on all networks (mainnet/testnet) and consider removing the flag once fully rolled out so the check is a permanent invariant.

### Proof of Concept
Not independently verified against a live network — the default/activation status of `abort_if_multisig_payload_mismatch_enabled` was not confirmed within the scope of the search. Conceptual PoC: 
1. Owners create a multisig transaction via `create_transaction` (payload stored in full, `payload_hash == None`) proposing payload `A` (e.g., transfer 1 APT to address X).
2. Owners vote/approve to reach quorum for this transaction as identified by its `sequence_number`.
3. An owner (or the executor) submits the actual execution transaction supplying a different `payload` argument `B` (e.g., transfer 1000 APT to address Y) instead of `A`.
4. If `abort_if_multisig_payload_mismatch_enabled` is disabled, `validate_multisig_transaction` skips comparing `B` against the approved `A`, admission succeeds, and `B` executes with the multisig account's authority instead of the approved `A`. [3](#0-2)

        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {

            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.

            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
