### Title
Webhook signature verification keys off `repository.owner.login`, but Stack/Commit selection keys off `repository.full_name` — unauthenticated cross-organization webhook forgery when any configured GitHub org omits `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` resolves which GitHub App's secret to check against using `repository_owner`, a value read from the payload's `repository.owner.login` (or `organization.login`) field [1](#0-0) . That field is looked up with a fallback helper [2](#0-1) . Every downstream handler, however, resolves the target `Repository`/`Stack` (or `Commit`) using a *different* payload field, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks` [3](#0-2)  and equivalently in `PushHandler#process` [4](#0-3) . These two fields are never cross-checked against each other.

### Finding Description
The binding that should hold is: *organization whose webhook secret authenticated the request* == *organization/repository whose Stack data is mutated*. `Shipit.github(organization: repository_owner)` selects the `GitHubApp` instance used to verify the HMAC signature [5](#0-4) , and `GitHubApp#verify_webhook_signature` explicitly **short-circuits to `true` when no `webhook_secret` is configured** for that resolved org: `return true unless webhook_secret` [6](#0-5) . Leaving `webhook_secret` unset is a documented, supported configuration (shown as `webhook_secret: # nil` in `docs/setup.md` and `config/secrets.development.example.yml`) for multi-organization Shipit deployments, since a GitHub App only authenticates to the org it is installed in [7](#0-6) .

Because verification is keyed by `repository.owner.login`, and the actual Stack/Commit that gets written is keyed by the independent `repository.full_name` field, an attacker who knows (or can guess) the name of *any* org configured in Shipit without a `webhook_secret` can send a fully unauthenticated `POST /github/webhooks` where:
- `repository.owner.login` (or `organization.login`) = the secret-less org → `verify_webhook_signature` returns `true` unconditionally, no secret needed.
- `repository.full_name` = `"OtherOrg/some-private-repo"` → the handler resolves and mutates that completely unrelated repository's Stack via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [3](#0-2) .

This lets an unauthenticated attacker trigger handlers (e.g. `PushHandler#process`, which enqueues `stack.sync_github(expected_head_sha:)` for any not-archived stack matching the forged branch) [4](#0-3)  against a Stack belonging to an org the attacker never authenticated against, purely because the "authenticated organization" and "mutated repository" bindings are drawn from two independent, unvalidated fields of the same attacker-controlled JSON body.

### Impact Explanation
For handlers whose written content is attacker-controlled (as opposed to `PushHandler`, which only re-fetches commits from GitHub's real API for the resolved stack), this crosses into cross-repository/cross-organization writes performed with data the attacker fully controls, satisfying the "cross-repository writes" / "unauthorized... deploy or rollback trigger" impact tier. Even limited to `PushHandler`, it is an unauthenticated trigger of `GithubSyncJob` against an arbitrary tenant's Stack, which is itself a break of the "org authenticated vs. repository written" binding the prompt calls out. I was not able to fully confirm, within the available iterations, whether other handlers such as `StatusHandler` scope their `Commit`/`Stack` lookups strictly by the same `full_name`-derived repository or by a global `sha` lookup; this would materially change the severity (global `sha` lookup would allow directly forging arbitrary commit status content on any tenant's commit) and should be verified directly in `app/models/shipit/webhooks/handlers/status_handler.rb`.

### Likelihood Explanation
Exploitability depends on the deployment: the engine must be configured for **multiple GitHub organizations** (the `github: { org1: {...}, org2: {...} }` schema is a first-class supported configuration in `lib/shipit.rb`'s `github_app_config`/`github_organizations` [8](#0-7) ), and at least one of those orgs must have `webhook_secret` unset — a state the docs present as normal/expected rather than exceptional. No credential of any kind (no `ApiClient` token, no `webhook_secret`, no session) is required by the attacker; only knowledge of the login of the secret-less org and the `owner/repo` full name of the victim stack, both of which are typically public.

### Recommendation
`WebhooksController#verify_signature` should validate that the organization derived from `repository.owner.login`/`organization.login` (used to select the verifying secret) matches the organization implied by `repository.full_name` (used by handlers to select the target Stack) before dispatching to handlers, and this equality should be enforced independent of whether a `webhook_secret` happens to be configured. Additionally, `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` should not be treated as ambient trust for events tied to a *different* organization's data — signature verification and repository resolution must use the same, single field.

### Proof of Concept
1. Deploy Shipit with two configured GitHub organizations, e.g. `OrgA` (no `webhook_secret` configured) and `OrgB` (has stacks tracking `OrgB/secret-app`), following the documented multi-org config shown in `docs/setup.md` lines 181-209.
2. As an unauthenticated attacker, send:
   ```
   POST /github/webhooks
   X-Github-Event: push
   (no X-Hub-Signature required/validated because OrgA has no webhook_secret)

   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/secret-app" }
   }
   ```
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` and `verify_webhook_signature` returns `true` unconditionally (no secret configured) [6](#0-5) .
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/secret-app")` [3](#0-2)  and enqueues a sync job against `OrgB`'s Stack, despite the request never being authenticated for `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
