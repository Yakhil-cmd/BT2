### Title
Global, cross-tenant sha lookup in `StatusHandler` writes Status records to unrelated stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` with no repository/stack scoping, then calls `create_status_from_github!` on every match. Because the `commits` table only enforces sha uniqueness per-stack (`add_index :commits, [:sha, :stack_id], unique: true`), a webhook legitimately signed for repository B can create/update a `Status` row on a commit belonging to a completely unrelated stack A that happens to share the same sha (e.g. the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee491`).

### Finding Description
Broken binding: the code behaves as if `sha uniqueness across the Commit table (global)` == `sha uniqueness within a single stack (Commit.where(sha:, stack_id:))`, which is false — the schema (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, mirrored in `test/dummy/db/schema.rb` as `index_commits_on_sha_and_stack_id`, unique on `[sha, stack_id]`) only guarantees uniqueness per stack, not globally.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` authenticates the webhook against the GitHub App config for `repository_owner` (the org owning the *sending* repository), and `#create` dispatches to `Shipit::Webhooks.for_event('status') => [StatusHandler]`.
- `app/models/shipit/webhooks/handlers/handler.rb` provides `stacks`/`repository_name` helpers that scope lookups to the repository named in the payload (used correctly by `PushHandler#process`, which does `stacks.not_archived.where(branch:).find_each { ... }`).
- `app/models/shipit/webhooks/handlers/status_handler.rb#process`, however, ignores `repository_name`/`stacks` entirely and does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This queries the entire multi-tenant `Commit` table across every stack/repository, not just commits belonging to the repository that sent the webhook.
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `statuses.replicate_from_github!(stack_id, github_status)`, writing a `Status` scoped to whatever `stack_id` the matched commit belongs to — i.e., the victim stack's `stack_id`, not the sender's.

Exploit flow: attacker owns/controls repository B under a GitHub organization that already has the Shipit GitHub App installed (a "signed org"), satisfying `verify_signature`. Attacker pushes an empty commit (or any commit) to B whose sha collides with a commit sha already tracked by Shipit for an unrelated victim stack — trivially achievable with the git empty-tree sha, which naturally recurs across unrelated histories (e.g., from squash-merge no-ops) without any cryptographic effort. GitHub (or the attacker directly, since no secret is needed beyond what GitHub itself supplies for a legitimately configured org) sends a genuinely signed `status` webhook for repository B with that sha and `state: success`. `StatusHandler` matches the victim's pre-existing commit row purely by sha and writes a `Status` onto it, with no check that the commit's stack corresponds to repository B.

Existing guards do not stop this: `verify_signature` only proves the payload's *organization/repository* is authentic — it says nothing about which stack's commits the payload's sha is permitted to affect. `ExplicitParameters` validates the shape of `sha`/`state`/etc., not tenant scope. The `Handler#stacks` helper exists specifically to enforce repository scoping but is never invoked in `StatusHandler`.

### Impact Explanation
A payload authenticated for repository B mutates data belonging to a different, unrelated stack/repository — writing a `Status` row (state, target_url, description, context) that the victim stack's UI, CI-gating logic, and deploy eligibility checks (`Commit#state`, `deployable?`) will treat as authoritative. This can flip a victim's commit into `success` state, potentially unblocking a merge/deploy on the victim stack that should be blocked pending real CI results — matching "a payload for one repository mutating another's stack, commit, task or team" (Critical). It is repeatable against any commit sha already present in the victim's history that also occurs (or can be engineered to occur) in a repository the attacker controls; the empty-tree sha is a zero-effort collision path but is not the only one (any two repos containing a naturally shared commit sha, e.g. from a shared upstream, cherry-pick, or coincidental empty commit, are equally exploitable).

### Likelihood Explanation
Preconditions: (1) the attacker's repository must belong to a GitHub organization/App installation already configured in Shipit (`Shipit.github(organization: ...)` must resolve, i.e. not raise `GithubOrganizationUnknown`) so `verify_signature` passes; (2) a victim stack must already contain a `Commit` row whose sha matches one the attacker can produce a legitimately-signed status event for. Given the empty-tree sha is extremely common in git history (any no-op squash merge, `git commit --allow-empty-message` cleanups, CI placeholder commits, etc.), condition (2) is plausible without any attacker-side computation. No secrets, sessions, or elevated privileges are required — only ordinary push/CI access to a repo in an already-onboarded org, which is a realistic position for a low-privilege internal contributor or any repo owner under a shared org. This is repeatable per victim stack that happens to hold the colliding sha.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the sending repository, mirroring the `Handler#stacks` pattern used by `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally, consider tightening the `commits` uniqueness constraint/lookup patterns generally so sha-based queries app-wide are always stack/repository-scoped, since sha uniqueness is only per-stack by design.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a dedicated `status_handler_test.rb`):
```ruby
test ":status from repository B writes a Status onto an unrelated victim stack sharing the same sha" do
  empty_tree_sha = '4b825dc642cb6eb9a060e54bf8d69288fbee491'

  victim_stack = shipit_stacks(:shipit) # unrelated to the sending repo below
  victim_commit = victim_stack.commits.create!(
    sha: empty_tree_sha,
    author: shipit_users(:walrus),
    committer: shipit_users(:walrus),
    authored_at: Time.now,
    committed_at: Time.now,
    message: "empty tree collision"
  )

  request.headers['X-Github-Event'] = 'status'
  # payload claims to originate from an unrelated repository (attacker-owned, in a signed org)
  body = {
    'sha' => empty_tree_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'shopify' } }
  }.to_json

  assert_difference -> { victim_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  # binding check: sha uniqueness is only per-stack, yet a cross-repo payload
  # was accepted as authoritative for victim_stack's commit
  assert_equal 'success', victim_commit.reload.status.state
end
```
