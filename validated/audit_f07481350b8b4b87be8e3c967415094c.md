### Title
Membership webhook grants team membership across tenants via `github_id`-only lookup - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` records solely by `github_id`, ignoring the `organization` field in the payload, while `WebhooksController#verify_signature` only checks that the signature matches the webhook secret of the organization named in the payload itself. An attacker who owns any legitimate GitHub org configured in Shipit can therefore sign a `membership` webhook naming their own org, but reference the `team.id` of an existing team belonging to a different (victim) org, causing themselves to be added as a member of that victim team.

### Finding Description
The broken binding: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` (verified against `attacker-org`'s secret) should equal the organization that owns the `Team` row being mutated (`victim-org`'s `Team#organization`), but the handler never checks this.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('organization','login')` [1](#0-0) , then verifies the raw body's HMAC against `Shipit.github(organization: repository_owner)`'s configured secret [2](#0-1) . Since attacker legitimately owns `attacker-org` as a tenant, this verification passes with attacker's own secret.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` — the lookup key is `github_id` alone, not scoped by `organization` [3](#0-2) . If a `Team` row with that `github_id` already exists (created previously for `victim-org`), it is found and returned as-is; the block that would set `team.organization = params.organization.login` only runs on creation, not lookup.
3. `team.add_member(User.find_or_create_by_login!(params.member.login))` is then called on that pre-existing victim-org `Team` [4](#0-3) , adding the attacker-controlled user as a member via `Team#add_member` [5](#0-4) .
4. If that `Team` is one of `Shipit.github_teams`, `User#authorized?` becomes true for the attacker's user (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [6](#0-5) .

No existing guard prevents this: `verify_signature` authenticates only that the *sender org* is who it claims, not that the *team/org referenced inside the payload* matches the sender org; the `ExplicitParameters` schema in the handler requires `organization.login` and `team.id` but never cross-checks them against the found `Team#organization` [7](#0-6) .

### Impact Explanation
A single crafted, self-signed webhook lets an attacker add an arbitrary Shipit `User` (including a newly created one, or one for a name they don't even control since `User.find_or_create_by_login!` will fetch/create a user by that login) into any pre-existing `Shipit::Team` whose `github_id` is known or guessable, as long as that `github_id` is one of `Shipit.github_teams`. This escalates `User#authorized?` to true, bypassing the organization-wide authorization gate for the whole app — matching the High severity category ("escalation into `Shipit.github_teams` authorization"). It is repeatable for any team `github_id` the attacker can learn (team IDs are often not secret, e.g., visible via prior API responses, org listings, or the initial legitimate webhook that created the row), and does not require compromising victim-org's secret at all.

### Likelihood Explanation
Preconditions required: attacker must control a real Shipit-configured GitHub organization (to have a valid `webhook_secret` and pass `Shipit.github(organization: ...)`), a target `Team` row must already exist (created by a genuine prior membership event for the victim org) with a known `github_id`, and that team must be listed in `Shipit.github_teams`. These are plausible in a multi-tenant Shipit deployment; team IDs are numeric and low-entropy, and could be discovered through other means (e.g., prior legitimate webhook logs, public org API). Attacker cost is a single unauthenticated HTTP POST with correct HMAC signed with their own secret — trivial and fully repeatable.

### Recommendation
Scope the `Team` lookup by both `github_id` and `organization` (i.e., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and additionally verify that `params.organization.login` matches `repository_owner`/the org whose secret validated the signature before mutating any `Team` row. Reject the webhook if an existing `Team` with that `github_id` belongs to a different organization than the one that signed the request.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot hijack a team belonging to another organization" do
  victim_team = shipit_teams(:my_team) # organization: 'victim-org', github_id: 4242
  # simulate Shipit.github_teams including victim_team
  Shipit.stubs(:github_teams).returns([victim_team])

  attacker_org = 'attacker-org'
  # attacker-org is a legitimately configured tenant with its own webhook_secret
  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker-login' },
  }.to_json

  post shipit.github_webhooks_path,
    params: payload,
    headers: {
      'X-Github-Event' => 'membership',
      'X-Hub-Signature' => "sha1=#{OpenSSL::HMAC.hexdigest('sha1', webhook_secret_for(attacker_org), payload)}",
      'Content-Type' => 'application/json',
    }

  assert_response :ok
  attacker_user = Shipit::User.find_by(login: 'attacker-login')
  # Binding check: attacker's signing org != victim_team.organization, yet team membership was granted
  assert_not_equal attacker_org, victim_team.organization
  assert victim_team.members.include?(attacker_user)
  assert attacker_user.authorized?
end
```
