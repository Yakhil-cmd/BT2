### Title
Asset attestor list can be replaced by the definer, permanently freezing outstanding attested asset holdings - (File: validation.js)

### Summary
For any `spender_attested` asset, the asset definer can post an `asset_attestors` message that completely replaces the list of trusted attestors. The validation logic for this update never checks whether existing (already-issued, already-held) coins of the asset are owned by addresses that were attested only by the *old* attestor list. Once the new list is stable, every payment spending those previously-valid outputs is rejected, freezing the funds with no way to spend them until (and unless) one of the *new* attestors chooses to re-attest the same addresses.

### Finding Description
`validateAttestorListUpdate()` only checks that the message is single-authored, that the caller is the asset's definer, and that the new attestor array is well-formed and sorted: [1](#0-0) 

There is no check on `netAssetDeposits`-equivalent state — i.e. no verification that current holders of the asset remain attestable, and no requirement of continuity with the previous attestor list. The update is persisted unconditionally in `writer.js`: [2](#0-1) 

At read time, `storage.readAsset()` / `addAttestorsIfNecessary()` always uses only the *latest* (most recent stable) `asset_attestors` unit for the asset — old attestor lists are completely discarded once a newer one stabilizes: [3](#0-2) 

Every payment of a `spender_attested` asset is validated against this latest list via `filterAttestedAddresses()`, which joins `attestations` against `objAsset.arrAttestorAddresses` (the new list) and requires the attestation to be newer than the address's most recent definition change: [4](#0-3) 

Both issuance and transfer/spend paths enforce this: an issuer must be attested by the current attestor set, and every spending owner address must appear in `arrAttestedAddresses` computed from the *current* attestor list: [5](#0-4) [6](#0-5) 

Consequently, as soon as the definer swaps the attestor list (for any reason — key rotation, compromise recovery, business change, or malicious intent), any address that already holds unspent outputs of the asset but was attested only under the old list can no longer produce a valid payment message spending those outputs: `filterAttestedAddresses` will not find a matching attestation from any of the new attestors, so `arrAttestedAddresses` for that holder is empty and `validatePaymentInputsAndOutputs`/`validatePayment` reject the transaction with "owner address is not attested" / "none of the authors is attested". This is structurally the same defect as the reported `UXDRouter.unregisterDepository()` issue: a privileged, unchecked state-mutating action (removing/replacing a registration list) silently strands funds that were valid under the prior state, with no built-in safeguard requiring the mutation to preserve spendability of already-issued balances.

### Impact Explanation
Any holder of a `spender_attested` asset can have their existing, previously-valid balance made permanently unspendable the moment the definer updates the attestor list, unless a new attestor independently chooses to attest that exact address again. This is a fund-freezing condition triggered by an ordinary, validation-accepted protocol message (`asset_attestors`), not requiring any bug in the attesting/attestation logic itself — merely the absence of a continuity/impact check when the list changes. Because this can happen for any asset with `spender_attested=true` (including AA-issued assets, since AAs can emit `asset_attestors` messages, per `aa_validation.js` case `'asset_attestors'`), the impact scope covers both user-issued and AA-issued attested assets.

### Likelihood Explanation
Likelihood is high given normal, benign operational conditions: an asset definer might rotate its attestor list for legitimate business reasons (revoking a compromised attestor's key, replacing a KYC provider) without realizing that doing so instantly invalidates the ability of unrelated existing holders to move their already-received coins. No malicious behavior is required to trigger the freeze — a single, well-formed `asset_attestors` unit posted by the legitimate definer is sufficient, and it passes all existing validation checks in `validateAttestorListUpdate()`.

### Recommendation
When validating an `asset_attestors` update (or providing tooling/warnings around it), require or check that outstanding non-zero balances of the asset held by addresses attested under the old list are also attestable/re-attestable, or provide an explicit transition/grace mechanism (e.g., accepting attestations from either the old or new list for some period, or requiring the new attestor list to include the addresses/attestors needed to keep existing holders valid) before allowing the attestor list replacement to take effect. At minimum, document/emit a warning to definers that changing the attestor list can strand existing holders' funds, and consider validating that the new list is a superset extension rather than a full replacement unless explicitly intended.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial `attestors: [X]`.
2. Attestor `X` attests holder `H`'s address via an `attestation` message; `H` receives issued/transferred coins of asset `A` and holds them as unspent outputs.
3. Definer `D` posts an `asset_attestors` message for asset `A` with `attestors: [Y]` (dropping `X`). This passes `validateAttestorListUpdate()` (single-authored by `D`, non-empty sorted list) and is written to `asset_attestors` table.
4. Once this unit is stable, `storage.readAsset()` now returns `arrAttestorAddresses = [Y]` for asset `A` as the "latest" list.
5. `H` attempts to spend its existing output of asset `A` in a `payment` message. `validatePayment()` → `loadAssetWithListOfAttestedAuthors()` → `filterAttestedAddresses()` finds no attestation of `H` by `Y`, so `arrAttestedAddresses` is empty; the payment is rejected with `"none of the authors is attested"` / `"owner address is not attested"`, permanently freezing `H`'s funds until `Y` independently attests `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
