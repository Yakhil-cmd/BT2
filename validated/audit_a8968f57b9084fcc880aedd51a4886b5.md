### Title
Attacker-supplied swap route executes arbitrary contract code inside a victim's authorized `swap_collateral`/`multiply` call, appending wallet-draining transfers to the signed auth tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The PlaySMS import.php bug class — attacker-controlled input (User-Agent / filename) reaching a privileged execution context — maps directly onto XOXNO Lending's route handling. The permissionless strategy entrypoints accept fully attacker-craftable `swap: Bytes` (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct `execute_strategy`), and the router invokes whatever pool/token contracts the payload names with no allowlist. A malicious venue contract called beneath the victim's `caller.require_auth()` entry can issue `token.transfer(victim, attacker, X)` for *any* token in the victim's wallet — tokens the protocol never listed — and Soroban simulation records that transfer as a child of the victim's authorization entry. A client that signs the simulated tree authorizes the theft. This is proven by the in-repo PoC `rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 13–55) is invoked by every swap-bearing verb. It authorizes exactly one input transfer (`authorize_transfer_as_current`, line 34) and then calls `router.execute_strategy(controller, amount_in, swap)` with the caller-supplied `swap` bytes (line 37). Nothing in the controller constrains which contracts the route names; the threat model explicitly states "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md`, lines 154–160).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end:

- `RogueHopPool::swap` (lines 62–71) calls `token::Client::transfer(victim, attacker, amount)` on an unrelated wallet token while running as a route hop.
- The simulation test (lines 194–227) shows the recorded auth tree for Alice's `swap_collateral` contains exactly one child: the wallet-draining `transfer` — indistinguishable in structure from a legitimate nested pull. Alice's wallet balance of `WALLET_BALANCE` moves to the attacker and her position still receives fair output, so all controller-side checks (`RouterOverspend`, `NoSwapOutput`, final HF gates) pass.
- The enforcement test (lines 229–269) shows the transfer executes iff the signed tree lists it — and the tree that `simulateTransaction` produces *does* list it.

Root cause: untrusted, off-chain-produced `swap` XDR is treated as executable instructions inside a transaction authorized by the caller's account signature, and neither the controller nor the router restricts the set of contracts the payload may invoke (INV-STRAT-03 covers only Blend migration pools, not route venues). Analogous to CVE-2017-9101, attacker-supplied bytes (filename/UA → route XDR) are interpreted by a privileged context (web server → caller's auth tree).

### Impact Explanation
Theft of user funds. The victim loses arbitrary balances of arbitrary tokens held in their wallet — bounded by wallet contents, not by the routed amount — while the protocol leg settles "correctly" (`swap.rs` lines 40–54 all pass). The loss is entirely outside the controller's measured input/output deltas, so no protocol-side bound (payload `min_out`, `RouterOverspend`, post-swap solvency) limits it. Severity: High — critical-class impact conditioned on the victim signing a crafted route.

### Likelihood Explanation
A single unprivileged attacker needs only to get the victim to submit one `swap_collateral`/`multiply`/`execute_strategy` call carrying the malicious route — e.g., via a compromised or phishing quote source, since route bytes are produced off-chain and passed opaquely (`skills/xoxno-swap-aggregator/composition.md` notes routes "come from the quote service; do not construct on-chain"). The auth tree poison is silent: simulation records the rogue transfer as a normal-looking child and the swap itself delivers fair output, so nothing in the transaction outcome signals the theft. Mitigation exists only client-side (decode the route, reject unexpected auth children), which the threat model itself assigns to integrators rather than enforcing on-chain — meaning any client that skips it exposes users fully. Not rated Critical because it requires the victim to sign a transaction containing the poisoned authorization.

### Recommendation
- Enforce a venue/pool allowlist on the controller or router: reject routes whose hop `pool`/`token` addresses are not governance-registered, so payload-named contracts cannot reach the call stack under user auth.
- Alternatively/additionally, execute strategy swaps through a router-held auth model that never puts arbitrary contracts beneath the caller's signature scope (the controller already uses `authorize_as_current_contract`; end-user direct `execute_strategy` calls remain exposed).
- At minimum, document and enforce client-side route decoding: refuse any simulated auth tree containing children other than the single expected input `transfer`.

### Proof of Concept
Provided in-repo at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Register `RogueHopPool` with a stored plan `(victim, wallet_token, attacker, WALLET_BALANCE)` (`lines 52–72`).
2. Build `RoutedSwap` naming that pool as `hop_pool` with `token_in=USDC`, `token_out=ETH`, fair `min_out` (`lines 111–125`).
3. Victim calls `controller.swap_collateral(alice, account_id, USDC, 50_000_000_000, ETH, route)`; controller authorizes the input transfer and invokes the router, which invokes the rogue pool.
4. Inside the hop, `RogueHopPool` executes `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` under Alice's auth entry. Simulation records it as the sole child of the `swap_collateral` root (`lines 206–222`); signing that tree executes the theft (`lines 264–268`): Alice's wallet goes to 0, attacker holds `77_770_000_000`, and the position still books the fair ETH output.

The same exposure applies to `multiply`, `swap_debt`, `repay_debt_with_collateral`, and direct `execute_strategy` calls, since all funnel through `swap_tokens` / `router.execute_strategy` with caller-supplied route bytes. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
